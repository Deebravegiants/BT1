### Title
Webhook shop identity spoofing via HMAC that only covers the raw body, not the shop-domain header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity using an HMAC computed over the raw request body only, while the shop identity used downstream by consuming apps (`WebhookMetadata#shop`) is read from the unsigned `X-Shopify-Shop-Domain` header. Because the header is not covered by the HMAC, an attacker who possesses one valid signed webhook body/HMAC pair can replay it with a different `shop-domain` header value and still pass validation, causing the tenant identity attached to the event to be attacker-controlled.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`Webhooks::Request#shop` is read directly from an HTTP header outside the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` to compute the expected signature and compares it with `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` gates only on this body-only HMAC check, then forwards `request.shop` (the unauthenticated header) straight into `WebhookMetadata`, which is the object handed to the app's `WebhookHandler#handle`: [4](#0-3) 

`WebhookMetadata#shop` is a plain `String` field with no further validation or binding back to the signed body: [5](#0-4) 

**Broken binding (equality that should hold but doesn't):**
`hmac_verify(secret, raw_body ‖ shop) == received_hmac` is the property an app relying on `WebhookMetadata#shop` implicitly assumes. In reality the gem only checks `hmac_verify(secret, raw_body) == received_hmac`, with `shop` supplied independently and unauthenticated. Before the attacker's request: `raw_body` and `shop` are both genuine and consistent (the original webhook for the attacker's own shop A). After the attacker's replay: `raw_body`/`hmac` are unchanged (still valid for shop A) but `shop` header is swapped to victim shop B — the HMAC check still passes because it never examined `shop` at all.

### Impact Explanation
Any unprivileged internet user who is a merchant that has installed the app (and can therefore receive/subscribe legitimately-signed webhooks for their own shop) can capture a genuine `raw_body` + `X-Shopify-Hmac-Sha256` pair and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to any target shop. The app's `WebhookHandler#handle` implementation will receive `WebhookMetadata` claiming the event belongs to the victim shop, while HMAC validation reports success — this is a cross-tenant identity confusion where the shop binding that determines which tenant's session/data the app acts on is entirely decoupled from what was actually authenticated by Shopify's signature. Depending on how the consuming app uses `data.shop` (e.g., session lookup, data mutation, redact/deletion handling for mandatory GDPR topics), this can enable cross-tenant data corruption or forged mandatory compliance events for a shop the attacker does not own.

### Likelihood Explanation
High: obtaining a valid signed webhook for one's own shop only requires being a legitimate merchant/installer of the app, which is trivial for an unprivileged internet user to become. No secrets, tokens, or privileged access are required — only capturing traffic to their own endpoint (or Shopify's webhook delivery to their own shop) and replaying it with a modified header.

### Recommendation
Bind the shop identity into the material that is HMAC-verified, or otherwise cryptographically tie the header value to the signed body:
- Include the `shop-domain` header (and ideally `topic`, `webhook-id`) in `to_signable_string`, verified against a signature scheme that covers them, or
- Cross-check `request.shop` against an independently retrieved, trusted record (e.g., the session/shop the app expects for that specific webhook subscription/topic) before invoking the handler, rejecting mismatches, or
- At minimum, document/enforce that `WebhookMetadata#shop` must never be trusted as an authenticated tenant identifier unless corroborated by application-level state established through OAuth, not a raw incoming header.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and configures a webhook subscription (e.g. `orders/create`).
2. Shopify sends a real webhook to the app's endpoint:
   - Headers: `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`
   - Body: `{"id": 123, ...}` (attacker fully controls the content of orders/products/etc. in their own store, so the body content is attacker-influenced within the topic's schema)
3. Attacker intercepts/replays this exact `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint again, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, raw_body)` — identical to before — and passes, per [3](#0-2) .
5. `Registry.process` proceeds and constructs `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)`, handing it to the app's handler as if Shopify genuinely reported this event for `victim-shop`, per [4](#0-3) .
6. Any app logic keyed off `data.shop` (session retrieval, tenant-scoped writes, mandatory redact processing) now operates under a forged tenant identity supplied entirely by the attacker.
