## Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant shop-domain spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` (tenant identity) is read from an unauthenticated header and passed straight through to the app's webhook handler. This breaks the binding `hmac == HMAC(secret, body)` ⇒ `shop is authentic`, because `shop` is never part of what is signed.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac`/`Request#shop` are both derived independently from HTTP headers: [1](#0-0) [2](#0-1) 

`Registry.process` validates the HMAC over the body via `Utils::HmacValidator.validate(request)`, but that validator only checks `verifiable_query.to_signable_string` (the body) against `verifiable_query.hmac` — it never touches `verifiable_query.shop`: [3](#0-2) 

After the HMAC check passes, `request.shop` (from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is forwarded, unverified, as the tenant identity into `WebhookMetadata`, which is handed to the app's business logic: [4](#0-3) 

Because Shopify webhook HMACs are computed with the app's single `api_secret_key`, which is identical for every shop that has installed the app, a valid `(body, hmac)` pair captured from a webhook delivered for one shop (e.g., attacker's own store, or one from any publicly-observable delivery/log) remains cryptographically valid for that body under the same secret regardless of which shop header accompanies it. The `shop` value carried in the `x-shopify-shop-domain` header is never included in `to_signable_string`, so an attacker who controls or can reuse a `(body, hmac)` pair can attach an arbitrary `shop` header and have it authenticated as an entirely different, victim tenant.

The identity binding that should hold is:
`hmac_valid(body) == true` should imply `shop` is the shop that actually produced `body`.
In this implementation, `hmac_valid(body)` only proves the body was signed by *the app's* secret (shared across all installed shops), not which shop it came from — so `shop` is effectively an attacker-controlled label riding along with a validly-signed body.

### Impact Explanation
This crosses a tenant boundary: `Registry.process` dispatches to the app's `WebhookHandler#handle` with a `WebhookMetadata` object whose `shop` field is unauthenticated. Any app logic that keys off `data.shop` (e.g., to look up per-shop settings, update per-shop database rows, issue actions using a shop-specific session, or attribute mandatory GDPR webhooks like `shop/redact`/`customers/redact`/`customers/data_request` to the wrong shop) can be manipulated into acting on/against a different merchant than the one that actually sent the payload — a cross-tenant data integrity and confidentiality issue. This aligns with the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitability requires the attacker to have (or capture) one valid `(raw_body, hmac)` pair signed under the app's shared `api_secret_key` — for example from their own shop's webhook deliveries, which any developer/merchant installing the app can generate at will since they only need a store installing the same app. No access to `api_secret_key`, tokens, or the victim shop is required; only the ability to relay/craft an HTTP request with a spoofed `x-shopify-shop-domain` header alongside a previously-observed valid body+hmac combination for the same app.

### Recommendation
Bind the tenant identity into the signed payload verification path, e.g.:
- Since Shopify's own signature scheme only covers the raw body (this is Shopify-side behavior the gem cannot change), the gem should not treat `request.shop`/header-derived shop as trusted merely because the body HMAC validates. Document this explicitly and/or require consumers to cross-check `request.shop` against a shop that is independently known to have this webhook subscription (e.g., via `webhook_id` lookup or a stored expected-shop mapping) before trusting it, similar to how `AuthQuery`'s `to_signable_string` folds `shop` and `host` into the signed string: [5](#0-4) 

- At minimum, `Registry.process` should not implicitly grant trust to `request.shop`; it should be clearly surfaced to consumers that only the body is authenticated, not the shop attribution, or the library should perform an authoritative shop-binding check (e.g., verifying `webhook_id` belongs to the claimed shop via the Admin API) before invoking handlers.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g., `orders/create`).
2. Attacker triggers/receives a legitimate webhook delivery for `attacker-shop.myshopify.com`, capturing the raw body and its valid `x-shopify-hmac-sha256` value (both computed with the app's shared `api_secret_key`).
3. Attacker (or a network intermediary able to reach the app's public webhook endpoint) replays the exact same `raw_body` and `hmac` header, but substitutes `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers normally; `Utils::HmacValidator.validate` succeeds because it only checks the body/hmac pair, per [6](#0-5) .
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, per [7](#0-6) , causing the app to process attacker-supplied data as if it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
