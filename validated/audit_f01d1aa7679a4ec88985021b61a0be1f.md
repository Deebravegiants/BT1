### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook data spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before invoking the app's handler with a `WebhookMetadata` object whose `shop` field is described as trustworthy ("The shop domain of the webhook"). In reality, the HMAC only authenticates the raw request body; the `shop-domain` header that is later trusted as the tenant identifier is never part of the signed content, so any bytes that produce a valid signature for one shop can be replayed with a different, attacker-chosen `shop` value.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `to_signable_string` (the raw body), never incorporating `shop`, `topic`, or any header: [3](#0-2) 

`Registry.process` uses this same HMAC check as the sole authenticity gate, then immediately passes the unverified `request.shop` value straight into the handler's trusted `WebhookMetadata`: [4](#0-3) 

The equality this code implicitly claims to enforce is:
`bytes covered by HMAC == bytes the app acts on as the tenant identity (shop)`

That equality does not hold: HMAC covers `{raw_body}`, while the app acts on `{raw_body, shop-domain header, topic header, webhook_id header, api_version header}`. Any attacker who can obtain one genuine, validly-signed webhook body (e.g., by installing the app — a public action any unprivileged merchant can perform — on their own store and receiving a real webhook for a topic they control) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` still returns `true` because it never looks at the header, and `Registry.process` forwards `data.shop = "<victim-shop>"` together with attacker-controlled `data.body` to the host app's handler.

The library's own documentation reinforces that this is treated as a security boundary rather than an incidental convenience: it states `Registry.process` "will verify the request did indeed come from Shopify" and that `data.shop` is "The shop domain of the webhook," implying downstream trust of that field for tenant-scoped side effects (e.g., persisting order/customer data keyed by shop, as shown in the library's own usage example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`).

### Impact Explanation
This breaks the multi-tenant isolation boundary that the gem is documented to provide: an unprivileged internet user with nothing more than their own (attacker-owned) shop installation can inject attacker-controlled webhook payloads that the host application will process as if they originated from an arbitrary victim shop. Any app that keys persistence, authorization, or business logic off `WebhookMetadata#shop` (the exact pattern shown in this gem's own documentation) is exposed to cross-tenant data injection/corruption — satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high: the webhook endpoint is necessarily public-facing (Shopify must be able to reach it over the internet), no credentials beyond a self-serve app installation are required to obtain a validly-signed body, and no other check in `Registry.process` or `Request` cross-checks the header against the signed content.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the signable content, or independently authenticate the shop by cross-referencing it against a value obtained through a trusted, signed channel (e.g., validate that the shop has an active session/registration and reject webhooks whose header shop does not match any known signed source). At minimum, document prominently that `data.shop` is unauthenticated and must not be used as a sole tenant-scoping key without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a real webhook (e.g. `customers/update`) with attacker-controlled body content (e.g. crafted customer email/address fields).
2. Shopify delivers the webhook to the app's public endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw body>`.
3. Attacker replays the exact same raw body and HMAC header to the same endpoint, but rewrites `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` → `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the HMAC.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: attacker_controlled_body, ...)`, and the host app persists/acts on this data under the victim tenant's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
