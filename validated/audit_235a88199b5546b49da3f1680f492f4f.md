Audit Report

## Title
Unauthenticated flooding of `MethodPublicKeyGet` requests causes unbounded growth of the gateway vault handler's `activeRequests` map - ([File: core/services/gateway/handlers/vault/handler.go])

## Summary
`HandleJSONRPCUserMessage` explicitly skips authorization for `vaulttypes.MethodPublicKeyGet` and, whenever `getCachedPublicKey()` returns `nil`, calls `h.newActiveRequest(req, callback)` before any authentication or rate limiting is applied, inserting an entry into `h.activeRequests` keyed by the caller-supplied `req.ID`. Tracing the full request path (`gateway.ProcessRequest` → `multiHandler.HandleJSONRPCUserMessage` → `vault.handler.HandleJSONRPCUserMessage`) confirms there is no authentication or per-IP/per-sender rate limiting anywhere upstream of this insertion for this method.

## Finding Description
In `core/services/gateway/handlers/vault/handler.go`, `HandleJSONRPCUserMessage` validates only that `req.ID` is non-empty and ≤200 characters: [1](#0-0) . For `MethodPublicKeyGet`, the code explicitly documents that these requests "don't require authorization" and relies on caching alone to prevent DoS, then calls `newActiveRequest` on a cache miss: [2](#0-1) . `newActiveRequest` inserts unconditionally into the shared map with only a duplicate-ID check, no auth/rate-limit gate: [3](#0-2) .

Tracing the caller chain confirms no upstream authentication or rate limiting exists for this path. `gateway.ProcessRequest` decodes the request, resolves a handler by service name, and calls `h.HandleJSONRPCUserMessage(ctx, jsonRequest, callback)` directly with no auth check or rate limiter applied before dispatch: [4](#0-3) . `multiHandler.HandleJSONRPCUserMessage` simply routes by method name to the underlying handler with no additional gating: [5](#0-4) . A search of the gateway's HTTP network layer (`core/services/gateway/network`) found no rate-limiting middleware. Thus the only gates before map insertion are the empty-check and the 200-character length check.

Cleanup runs periodically via a ticker (`defaultCleanUpPeriod = 5s`, confirmed in code — not 30s as stated in the original claim's PoC description) and removes entries older than `requestTimeout` (`RequestTimeoutSec`, default 30s): [6](#0-5) [7](#0-6) . This is a bounded delay, not a bound on the number of entries: an attacker submitting requests faster than the 5-second reaper cycle (or simply faster than the DON can resolve/expire each of them within 30 seconds) can grow `h.activeRequests` without limit, each entry carrying a `responses` map and a reference to the callback.

The window where `getCachedPublicKey()` returns `nil` is real and recurring: it exists at every startup before the first successful `fetchVaultPublicKey()` (triggered on a 1-minute ticker and via lazy on-demand fetch), and can persist indefinitely if node responses to `secrets_getPublicKey` are slow, unavailable, or fail quorum. During this window, every request for this method — including ones with attacker-controlled unique `req.ID`s — reaches the unauthenticated insertion path.

Comparable code elsewhere in the codebase (`GatewayVaultRequestProcessor`, `ValidateCiphertextSizes`) explicitly documents the "unauthenticated callers create unbounded ... tenants" bug class and defers such state creation until after authorization [8](#0-7) [9](#0-8) , but the `MethodPublicKeyGet` fast path was not brought under this same protection.

## Impact Explanation
This is an unauthenticated memory-exhaustion (denial of service) vector against the gateway's Vault handler component. An external, unauthenticated caller who can reach the gateway's Vault JSON-RPC endpoint can force unbounded growth of server-side state (`activeRequests` map, per-entry `responses` maps, and captured callbacks) with only unique strings up to 200 bytes as attacker-controlled input, no credentials, and no valid workflow owner/JWT required. Sustained flooding during the (recurring) uncached window can exhaust gateway memory, degrading or crashing the process — a legitimate node/gateway availability impact.

## Likelihood Explanation
The precondition ("public key not currently cached") is not a narrow race — it occurs on every gateway restart before the first successful key fetch and can recur if node responses fail or are delayed, and the vulnerable code path requires zero credentials to reach. The attack is trivially repeatable: an attacker only needs to vary `req.ID` per request and hit the gateway's public HTTP endpoint faster than the cleanup ticker/timeout reaps entries.

## Recommendation
- Apply rate limiting (e.g., per-IP or per-connection) to unauthenticated `MethodPublicKeyGet` requests before `newActiveRequest` is invoked.
- Cap the number of concurrently outstanding unauthenticated `activeRequests` entries, or use a separate bounded structure for public-key-get bookkeeping.
- Coalesce concurrent unauthenticated public-key-get fetches into a single in-flight request (e.g., using `singleflight.Group`, as already used elsewhere in the gateway) instead of one `activeRequest` per caller.
- Revisit the comment/assumption that caching alone prevents DoS; explicitly handle the "cache not yet populated" and "cache fetch failing" windows with bounded resource consumption.

## Proof of Concept
1. Start (or observe) a gateway Vault handler instance where `cachedPublicKeyGetResponse`/`cachedPublicKeyObject` are not yet populated (e.g., immediately after startup, or by making `secretsService.GetPublicKey` on nodes unreachable/slow so `fetchVaultPublicKey` fails/times out).
2. As an unauthenticated client, repeatedly send JSON-RPC requests to the gateway's user-facing HTTP endpoint:
```json
{"jsonrpc":"2.0","id":"<unique-value-N>","method":"secrets_getPublicKey","params":{}}
```
varying `<unique-value-N>` on every request (≤200 chars, e.g., random UUIDs), at a rate exceeding `defaultCleanUpPeriod` (5s) and the request's expiry (`RequestTimeoutSec`, default 30s).
3. Each request enters `HandleJSONRPCUserMessage`, finds `cachedPublicKey == nil`, and calls `newActiveRequest`, adding an entry to `h.activeRequests` with no authentication check.
4. A Go unit test instantiating `handler` directly (as done in `handler_test.go`), calling `HandleJSONRPCUserMessage` in a loop with unique IDs while leaving `cachedPublicKeyGetResponse` nil, and asserting `len(h.activeRequests)` grows without bound (or beyond any reasonable cap), would demonstrate the unbounded map growth concretely.

// removeExpiredRequests removes expired requests from the pending requests map
func (h *handler) removeExpiredRequests(ctx context.Context) {
	h.mu.RLock()
	var expiredRequests []*activeRequest
	now := h.clock.Now()
	for _, userRequest := range h.activeRequests {
		if now.Sub(userRequest.createdAt) > h.requestTimeout {
			expiredRequests = append(expiredRequests, userRequest)
		}
	}
	h.mu.RUnlock()

	for _, er := range expiredRequests {
		responses := er.copiedResponses()
		var nodeResponses strings.Builder
		for nodeKey, nodeResponse := range responses {
			_, _ = fmt.Fprintf(&nodeResponses, "%s ---::: %v               ", nodeKey, nodeResponse)
		}
		nodeResponsesStr := nodeResponses.String()
		err := h.sendResponse(ctx, er, h.errorResponse(er.req, api.RequestTimeoutError, errors.New("request expired without getting quorum of responses from nodes. Available responses: "+nodeResponsesStr), []byte(nodeResponsesStr)))
		if err != nil {
			h.lggr.Errorw("error sending response to user", "requestID", er.req.ID, "error", err)
		}
	}
}

func (h *handler) newActiveRequest(req jsonrpc.Request[json.RawMessage], callback gwhandlers.Callback) (*activeRequest, error) {
	h.mu.Lock()
	defer h.mu.Unlock()
	if h.activeRequests[req.ID] != nil {
		h.lggr.Errorw("request id already exists", "requestID", req.ID)
		return nil, errors.New("request ID already exists: " + req.ID)
	}
	ar := &activeRequest{
		Callback:  callback,
		req:       req,
		createdAt: h.clock.Now(),
		responses: map[string]*jsonrpc.Response[json.RawMessage]{},
	}
	h.activeRequests[req.ID] = ar
	return ar, nil
}
