### Title
`Webhooks::Request#shop` is read from an unauthenticated header, letting a replayed genuinely-signed webhook be attributed to any victim shop - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read from the `x-shopify-shop-domain` header independently of the signed payload [2](#0-1) . `Utils::HmacValidator.validate` only recomputes HMAC over `to_signable_string` and compares it to the `hmac-sha256` header [3](#0-2) , so the `shop` value never enters the authenticated signature coverage. An attacker who legitimately owns a shop and receives a genuinely-Shopify-signed webhook for it can replay that exact `(raw_body, hmac)` pair directly to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header, and `HmacValidator.validate` will still return `true`.

### Finding Description
The intended binding is: **`hmac` authenticates `shop`**, i.e. `valid_hmac(raw_body) == true` should imply `shop` in that request is the shop Shopify actually generated the webhook for. In this codebase that binding does not hold: `to_signable_string` (the HMAC-covered value) is strictly `@raw_body` [1](#0-0) , and `shop` is derived from `shopify_header("shop-domain")`, a header entirely outside that signable string [2](#0-1) , `path="lib/shopify_api/webhooks/request.rb" start="67" end="70" />.

Exploit path, using only unprivileged capabilities (own dev shop, own genuine webhook, ability to send arbitrary raw HTTP requests):
1. Attacker installs the app on their own shop and registers a webhook, causing Shopify to deliver a genuine, correctly-signed webhook to the attacker's own receiver: `raw_body = B`, `hmac-sha256 = HMAC(B, api_secret_key)` — the attacker legitimately captures this real `(B, HMAC)` pair without ever learning `api_secret_key`.
2. The attacker sends their own raw HTTP POST directly to the target app's webhook endpoint (not through Shopify) with `HTTP_X_SHOPIFY_HMAC_SHA256` and body set to the captured genuine pair `(B, HMAC)`, but with `HTTP_X_SHOPIFY_SHOP_DOMAIN` rewritten to `victim-shop.myshopify.com`.
3. `Webhooks::Request.new` normalizes headers per its documented `sub("http_","").gsub("_","-")` rule and stores them [4](#0-3) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` [5](#0-4) , which recomputes `HMAC(B, api_secret_key)` and compares against the received value — since `B` and the HMAC are the real, Shopify-produced pair, validation **succeeds** regardless of the `shop-domain` header value.
5. `Registry.process` then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and dispatches it to the registered handler [6](#0-5)  — the handler receives `shop = "victim-shop.myshopify.com"` attached to attacker-controlled `body`, having passed the gem's own authenticity check.

No existing guard closes this gap: `HmacValidator.validate` only checks the byte-for-byte body [7](#0-6) ; there is no cross-check between `shop` and any value inside `to_signable_string`; Sorbet typing only enforces `String` types, not provenance. This requires no compromised intermediary — the attacker sends the forged request themselves, using headers/body they already legitimately possess from their own shop's real webhook delivery, satisfying the stated threat model exactly (attacker "may register their own webhook endpoint... receive their own validly signed webhooks... control headers").

### Impact Explanation
Any handler logic keyed on `WebhookMetadata#shop` (e.g., looking up per-shop state, triggering shop-scoped side effects, or processing mandatory compliance topics like `customers/data_request`/`shop/redact`) can be made to execute attributed to an arbitrary victim shop chosen by the attacker, using attacker-controlled body content. This is a **cross-tenant** confusion: data or actions the app believes originated from `victim-shop` actually originate from, and are fully controlled by, the attacker. It is trivially repeatable against arbitrary victim shop domains (any string can be placed in the header, no per-victim secret needed) and requires only one genuine webhook ever obtained by the attacker for their own shop, which can then be replayed indefinitely with different forged `shop` values. This matches the **Critical - cross-tenant access** category.

### Likelihood Explanation
- Preconditions: app must pass raw Rack headers into `Webhooks::Request.new` as documented (standard usage) and expose the webhook route to accept POSTs from any source IP (Shopify webhook endpoints are typically not IP-restricted).
- Attacker cost: install the app on a free/dev shop, trigger one webhook topic to capture a real `(body, hmac)` pair, then issue an arbitrary crafted POST with `curl`/HTTP client. No secrets, no interception, no social engineering required.
- Fully feasible and repeatable; the only work-around limitation is the attacker's own body content is fixed to whatever their own shop's webhook produced (they can't put arbitrary attacker-chosen text in the body without breaking HMAC), but they fully control which victim shop's identity to stamp on it.

### Recommendation
Include `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) in the HMAC-covered signable content, or otherwise cryptographically bind the shop identity to the signature — e.g., have `to_signable_string` incorporate the normalized header values alongside `@raw_body`, matching Shopify's actual webhook verification model where the shop is not meant to be trusted from an unsigned header. At minimum, document/enforce that `request.shop` must never be trusted for authorization decisions without independently verifying it corresponds to a session already associated with that shop.

### Proof of Concept
```ruby
# test/webhooks/shop_header_confusion_test.rb
require_relative "../test_helper"

class ShopHeaderConfusionTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", host_name: "app.com",
      scope: "read_products", is_embedded: false, is_private: false, api_version: "2023-01"
    )
  end

  def test_hmac_still_valid_after_shop_header_is_swapped
    raw_body = '{"id": 123, "owner": "attacker-shop"}'
    hmac = Base64.encode64(
      OpenSSL::HMAC.digest("sha256", ShopifyAPI::Context.api_secret_key, raw_body)
    ).strip

    headers_shop_a = {
      "HTTP_X_SHOPIFY_TOPIC" => "orders/create",
      "HTTP_X_SHOPIFY_HMAC_SHA256" => hmac,
      "HTTP_X_SHOPIFY_SHOP_DOMAIN" => "attacker-shop.myshopify.com",
      "HTTP_X_SHOPIFY_API_VERSION" => "2023-01",
      "HTTP_X_SHOPIFY_WEBHOOK_ID" => "1",
    }

    request_a = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers_shop_a)
    assert ShopifyAPI::Utils::HmacValidator.validate(request_a)
    assert_equal "attacker-shop.myshopify.com", request_a.shop

    # Attacker replays identical body+hmac but swaps the shop header to the victim
    headers_shop_b = headers_shop_a.merge("HTTP_X_SHOPIFY_SHOP_DOMAIN" => "victim-shop.myshopify.com")
    request_b = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers_shop_b)

    # HMAC validation still succeeds even though shop changed -> shop is unauthenticated
    assert ShopifyAPI::Utils::HmacValidator.validate(request_b)
    assert_equal "victim-shop.myshopify.com", request_b.shop
  end
end
```
This demonstrates the broken binding: `valid_hmac(raw_body) == true` before and after swapping `x-shopify-shop-domain`, proving `request.shop` carries no authenticity guarantee despite `HmacValidator.validate` returning `true`.

            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
