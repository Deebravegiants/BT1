### Title
Direct token donations to a curve `Pair` can permanently disable the overflow-buy-cap safety valve, bricking the curve's exhaustion/graduation path - (File: `packages/contracts/src/Router.sol`)

### Summary
CVE-2024-21055 is a MySQL optimizer bug that lets a (moderately privileged) attacker submit crafted input that reliably crashes/hangs the server — an availability-only, repeatable-DoS class. alt.fun's analog is in the bonding-curve AMM's "overflow buy cap" math: `Router._computeBuy` assumes the invariant `pair.tokenBalance() < pair.tokenReserve()` (virtual reserve strictly exceeds real balance) always holds, and reverts unconditionally with `OverflowCapDegenerate()` if that gap is ever driven to zero. An unprivileged holder can shrink that gap to zero by donating curve tokens directly to the `Pair` via plain ERC20 `transfer`, permanently converting every subsequent oversized buy on that token into a hard revert instead of a graceful cap-and-refund.

### Finding Description
`Router._computeBuy` caps `tokensOut` at `pair.tokenBalance()` when the uncapped curve math would exceed it, then back-computes `amountInUsed`: [1](#0-0) 

The `cappedReserveToken == 0` branch reverting with `OverflowCapDegenerate` is documented as relying on a hard invariant — that the virtual `tokenReserve` always exceeds the real `tokenBalance()` by the constant `LP_RESERVE` gap (250M tokens): [2](#0-1) 

That invariant is maintained only through the `Router.swap`-mediated buy/sell path, where `_pool.tokenReserve` and the pair's real token balance always move together by the same `tokensOut`/`tokensIn`. It is **not** enforced against a direct ERC20 `transfer(pair, amount)` of the launched `Token` (a plain donation), which increases `pair.tokenBalance()` (read live in `_computeBuy`/`tokenBalance()`) without touching `_pool.tokenReserve` (only mutated by `Pair.swap`, gated to `Router`/`BONDING_ROLE`): [3](#0-2) 

Because the virtual gap (`tokenReserve - tokenBalance()`) is initialized at exactly `LP_RESERVE = 250M` and is only ever *reduced* by donations (never increased), an attacker who accumulates and donates a cumulative 250M tokens (bought from the curve over time, at whatever price the curve offers, then `transfer`'d straight to the pair) can drive the gap to exactly zero. Once that happens, `pair.tokenBalance() == pair.tokenReserve()` becomes a fixed point that is preserved by every future ordinary swap (both sides always move by the same amount), so it never self-heals. From that point forward, **any** buy sized to request more tokens than currently remain (the completely normal "buy near the top of the curve" case that the overflow cap exists specifically to handle) hits `tokensOut > realBalance`, computes `cappedReserveToken = reserveToken - realBalance = 0`, and reverts unconditionally instead of capping and refunding as designed: [4](#0-3) 

This defeats the documented purpose of the overflow cap (`AGENTS.md`'s "Overflow buy cap" section) and the invariant test that assumes it can never be forced by an unprivileged party: [5](#0-4) 

### Impact Explanation
Once the gap is zeroed, the curve's supply-exhaustion graduation trigger (`IPair.tokenBalance() == 0`) can never be reached via a normal user buy again: the final buy that would drain the pair now reverts instead of executing a capped fill. Remaining curve tokens become effectively unbuyable in the exact quantity needed to empty the pool, the token can be permanently stuck unable to graduate via the supply path (only the independent, LT-price-driven USD trigger remains available, and only if it happens to fire on a non-overflowing buy), and any trader/creator whose exit depends on a full sellout or on a pending closing buy is frozen out of that path. This is a direct, on-chain-provable freezing of the curve's normal operation — a repeatable "crash" of the AMM math for that token, matching the CVE's hang/repeatable-crash/availability-impact class.

### Likelihood Explanation
The attack requires no privileged role — any address can buy tokens on the curve and `transfer` them to the `Pair` address. The cost is real (the attacker must acquire and burn/donate a cumulative 250M tokens, i.e. 1/3 of total supply and the entirety of `LP_RESERVE`), which bounds this to a Medium-severity, capital-gated griefing vector rather than a cheap one — consistent with the CVE's own "high privileged... easily exploitable... availability impact only" profile. It is more attractive against low-cap/early tokens where accumulating a third of supply is cheaper, and it can be executed opportunistically by a creator or early whale who wants to grief their own or a competitor's token.

### Recommendation
Do not trust `pair.tokenBalance()` as an unconditionally-safe cap input in `_computeBuy`. Either (a) track a router/pair-internal "real tokens transferred so far" counter independent of live `balanceOf`, so donations cannot shrink the virtual gap, or (b) sweep/burn any token balance in excess of the expected `reserveToken - soldSoFar` at the top of `_computeBuy`/`buy` (mirroring the donation-burn already done defensively at graduation time in `_prepareGraduationLiquidity`) before computing the overflow cap, so the invariant `tokenBalance() < tokenReserve()` is actively restored rather than passively assumed.

### Proof of Concept
1. Launch a token normally; curve seeds `reserveToken = totalSupply (1B)`, `realTokenBalance = curveSupply (750M)`, virtual gap = `LP_RESERVE = 250M` (`Bonding.launch` / `Router.addInitialLiquidity`).
2. Attacker repeatedly calls `Bonding.buy`/`Zap.buy` to acquire curve tokens, then `Token.transfer(pairAddr, amount)` directly (bypassing `sell`), accumulating donations until cumulative donated tokens equal the full 250M gap (`pair.tokenBalance() == pair.tokenReserve()`234 verifiable via `Router.getAmountOut`/pair reserve reads).
3. Any subsequent buy sized so that `_computeBuy`'s uncapped `tokensOut` (per the constant-product formula) exceeds the now-equal `realBalance` triggers `cappedReserveToken = reserveToken - realBalance == 0` and `Router.buy` reverts with `OverflowCapDegenerate()` — verifiable by adapting `test_inv_overflowCap_refundsLt` (`packages/contracts/test/GraduationInvariants.t.sol:330-351`) to insert a direct `Token.transfer(pairAddr, LP_RESERVE)` donation step before the oversized buy and observing the previously-successful capped buy now revert instead of returning a capped `tokensOut`/`amountInUsed`.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
