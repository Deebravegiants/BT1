### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
Shopify webhook HMAC signatures are computed over the raw request body using the app's `client_secret`, and that same secret is shared across every shop that has installed the app. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `ShopifyAPI::Utils::HmacValidator.validate` checks the signature exclusively against that body string. The `shop` accessor (`x-shopify-shop-domain` header) is never included in the signed bytes, yet `ShopifyAPI::Webhooks::Registry.process` passes this unauthenticated value straight into `WebhookMetadata` and to the host app's handler as the tenant identifier.

### Finding Description
The identity binding broken is: `bytes verified by HMAC (raw_body only)` ≠ `bytes/fields acted on by the handler (shop header)`. Because the HMAC secret is per-app rather than per-shop, any actor who can install the app on a shop they control (a normal, unprivileged action — e.g. a free Shopify dev/trial store) will receive genuine, correctly-signed webhook deliveries for their own store's events. Since the `shop-domain` header is excluded from `to_signable_string`, that attacker can replay/forward the identical body+HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain. `Utils::HmacValidator.validate` will still succeed because it only recomputes the HMAC over the untouched body, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` claims to be the victim, even though nothing cryptographically ties the shop to the payload. [5](#0-4) [6](#0-5) 

Host applications are documented and expected to key their session/data lookups off `data.shop` from `WebhookMetadata` (per `docs/usage/webhooks.md`'s example, which does `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), so this gem's own contract funnels an unauthenticated field into tenant-scoped operations.

### Impact Explanation
This breaks a tenant boundary: the app processes a request as belonging to shop B's tenant while the cryptographic proof (HMAC) only proves the payload came from a shop that installed the app (shop A, attacker-controlled) — cross-tenant access/confusion, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Requires no privileged access, no secrets, and no TLS interception — only that the attacker is able to install the target app on any shop (including a free/dev store) and can intercept/replay their own legitimately-delivered webhook while editing an HTTP header, which is trivial for the operator of that shop.

### Recommendation
Bind the `shop` claim into the material verified by the HMAC (e.g., include the shop-domain header in the signed string, or require the caller to separately verify that the delivered `shop` matches a shop known to have an active, verified session/installation before trusting it), mirroring how session tokens bind `dest`/`iss` into the signed JWT payload rather than trusting an unsigned header.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, completing OAuth normally.
2. Attacker triggers an event (e.g., updates a product) causing Shopify to deliver a webhook to the app's registered endpoint, signed with the app's shared `client_secret`:
   `x-shopify-hmac-sha256: <valid HMAC over raw body>`, `x-shopify-shop-domain: attacker.myshopify.com`, body `B`.
3. Attacker intercepts this HTTP request and re-sends it to the same endpoint unmodified except for the header:
   `x-shopify-shop-domain: victim.myshopify.com` (HMAC header and body `B` left untouched).
4. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` see only body `B`; `Utils::HmacValidator.validate` recomputes HMAC over `B` and it matches, so `Registry.process` at `lib/shopify_api/webhooks/registry.rb:190` passes validation.
5. `Registry.process` invokes the host's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, causing the host application to act on attacker-supplied data under the victim shop's identity.
