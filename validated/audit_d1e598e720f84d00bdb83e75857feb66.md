### Title
Webhook shop identity is not covered by HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` (tenant identifier) that `Registry.process` hands to application handlers comes from a separate, unsigned header. A valid HMAC/body pair obtained from one shop's own legitimate webhook delivery can be replayed against the app's webhook endpoint with a forged `shop-domain` header, and the signature will still validate, causing the handler to attribute attacker-controlled payload data to an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header independently of that signed string: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` only checks that `HMAC(secret, to_signable_string) == hmac`, i.e. it only binds the body, never the shop header: [3](#0-2) 

`Webhooks::Registry.process` trusts `request.shop` as the tenant identity forwarded to the handler as soon as the (body-only) HMAC check passes: [4](#0-3) 

The identity binding that should hold is: `verified_bytes == bytes acted upon as the tenant key`. Here, the verified bytes are `raw_body` (signed with the app's shared secret), but the tenant key acted upon by `handler.handle(... shop: request.shop ...)` is the unsigned `shop-domain` header — these two are never bound together.

### Impact Explanation
An unprivileged internet user who controls any shop that has this app installed receives genuine webhook deliveries for their own shop, each with a valid `hmac-sha256` header computed over the raw body using the app's `client_secret`. Because the header set (`shop-domain`, `topic`, `webhook-id`, `api-version`) is not part of the signed content, the attacker can replay the exact same `raw_body` + `hmac` pair directly to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body against the secret), so `Registry.process` invokes the handler with `shop: <victim shop>` and attacker-chosen `body`. Any app logic that uses the webhook's `shop` to select which tenant's data to create/update/delete (a common pattern for webhook-driven state sync) will act on the victim tenant using attacker-supplied content — a cross-tenant data-integrity/access issue reachable without the attacker ever possessing the app's `client_secret` or credentials belonging to the victim.

### Likelihood Explanation
Likelihood is high for any installed app: the attacker needs only to run their own shop (already an app installer, i.e., an "unprivileged" party relative to the target victim shop), capture one legitimate webhook delivery (trivial via any HTTP proxy/log), and resend it with one header changed. No cryptographic secret needs to be recovered, and no interaction with the victim is required.

### Recommendation
Bind the tenant identity into the signed content, or otherwise cryptographically tie the shop header to the verified payload. Concretely, `HmacValidator`/`Request` should incorporate `shop`, `topic`, and `webhook-id` into `to_signable_string` (or Shopify's headers-plus-body scheme used by Shopify's own webhook verification), and `Registry.process` should reject the payload if the declared shop cannot be shown to correspond to the verified content. At minimum, document (and enforce in-library where possible) that consuming applications must not treat `WebhookMetadata#shop` as trustworthy on its own without an out-of-band correlation (e.g., matching against a registered/expected shop for the specific webhook subscription) since the HMAC in this gem's implementation never covers it.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`) with a body `raw_body`.
2. Shopify sends: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid_hmac_of_raw_body>`, plus `raw_body`.
3. Attacker replays this exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged headers; `Utils::HmacValidator.validate` recomputes `HMAC(secret, raw_body)` and it matches the replayed signature (body unchanged), so validation passes.
5. `Webhooks::Registry.process` calls `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...))`, causing the app to process attacker data under the victim's tenant identity.
