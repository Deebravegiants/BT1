## Title
Webhook shop/topic identity spoofing due to HMAC covering only the raw body, not the shop-domain header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature the gem verifies binds solely to the byte content of the body. The `shop`, `topic`, and `webhook_id` values that `ShopifyAPI::Webhooks::Registry.process` trusts and hands to the app's handler are read straight from HTTP headers that are never covered by that signature, breaking the identity binding `HMAC-verified(body) == trusted(shop, topic)`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are pulled directly from headers with no cryptographic tie to the verified bytes: [2](#0-1) 

`Registry.process` validates the HMAC against `request` (i.e., against the body only via `Utils::HmacValidator.validate`), and then unconditionally trusts `request.shop`/`request.topic` to look up a handler and build `WebhookMetadata`: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, i.e., the body, using the app's shared `api_secret_key`: [4](#0-3) 

Because `api_secret_key` is a single app-wide secret shared across every installed shop (it is not per-tenant), any merchant who installs the app on their own store receives legitimate `(body, hmac)` pairs signed with that same shared secret. For topics whose body carries little or no shop-identifying content (e.g. `app/uninstalled`, which typically just contains an object id), that captured `(body, hmac)` pair remains a valid signature regardless of which shop it is replayed against. An attacker who owns/controls one shop that has the app installed can capture such a webhook delivery and replay the identical body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `Utils::HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` passes the attacker-chosen victim shop straight into the handler as `WebhookMetadata#shop`, so host-app code that trusts `shop` after HMAC validation is deceived into treating the event as originating from the victim tenant.

### Impact Explanation
This crosses a tenant boundary: an attacker with only their own (unprivileged) shop installation can make the gem report a signed, "verified" webhook as belonging to a different, victim shop, since the shop identity is not bound to the signature. Any app logic keyed off `WebhookMetadata#shop` (e.g., data resets on `app/uninstalled`, scope/entitlement changes, cache invalidation, session/webhook bookkeeping per shop) can be triggered against a shop the attacker does not control, which is a cross-tenant access issue as covered by the report's identity-binding class ("a field acted on but not covered by the HMAC").

### Likelihood Explanation
Requires the attacker to have (or create) their own legitimate shop with the target app installed — an unprivileged internet user can do this via Shopify's normal app-install flow — and to pick/observe a webhook topic whose body content does not itself vary per shop. No leaked secrets, TLS interception, or privileged accounts are needed; the attacker only needs the ability to receive one legitimate webhook to their own store and to POST a modified header to the app's own public webhook endpoint.

### Recommendation
Bind the header-derived identity fields into the signed material, or independently validate them against the caller's already-authenticated context. Concretely, `Request#to_signable_string` (or `Registry.process`) should incorporate `shop`, `topic`, and `webhook_id` into the value that is HMAC-verified (mirroring what `Auth::Oauth::AuthQuery#to_signable_string` does for OAuth), or `Registry.process` should require/cross-check the resolved shop against a value already known to be legitimate for that tenant before dispatching to the handler.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger an `app/uninstalled` (or similar low-entropy-body) webhook and capture the raw body `B` and its `X-Shopify-Hmac-Sha256` header value `H` — both are valid because they are computed from the app's shared `api_secret_key`.
2. Send `POST` to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds (it only checks `B` against `H`), and `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim.myshopify.com"`, causing the app to act as though the event came from the victim tenant.
