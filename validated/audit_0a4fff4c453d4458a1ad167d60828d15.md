**Reasoning:**

`Bytecode::new_move_function` in `api/types/src/bytecode.rs` sets `is_entry: def.is_entry` directly from the `FunctionDefinition.is_entry` field of the `CompiledModule` [1](#0-0) . This is a single value deserialized once from the module bytes at publish time (or query time when re-parsing the same on-chain module) — the API does not independently compute or re-derive this flag; it echoes the exact byte read from the binary format.

The same `is_entry` flag is the authoritative value the VM itself uses to decide whether a function can be invoked as an entry function. The Move bytecode verifier's `script_signature.rs` checks entry-function signature validity based on this same flag at module-publish time, and the VM's entry-function dispatch path relies on it to permit or reject direct invocation. Since both the API's reported classification and the VM's execution-time gating read the identical `is_entry` bit from the identical deserialized `FunctionDefinition`, there is no way to craft a module where the function is `is_entry: true` for execution purposes (i.e., directly callable via a normal transaction) while simultaneously reporting `is_entry: false` through the API. The two consumers are not independent code paths with different trust boundaries — they consume the same verified field.

Because there is no divergence surface between what the VM enforces as "directly callable" and what the API reports as `is_entry`, an attacker cannot make a multisig-control-transferring entry function appear as `is_entry=false` while remaining directly invocable. This also means no custody boundary is crossed: the finding describes a hypothetical metadata/classification mismatch used by external tooling, not an actual change to who can own, transfer, freeze, or recover an asset on-chain, which the review's Decision Standard requires to reject.
