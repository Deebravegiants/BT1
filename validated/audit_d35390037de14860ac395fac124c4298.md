## Title
Stale cross-seed address cache served via `connectedOrigins.getConnectedAccounts` when a wallet account's underlying seed changes without changing its name key - ([File: features/connected-origins/module/connections.js])

### Summary
This is a direct analog of the reported Yearn bug class: a cache (`_cachedVaults` there, `connectedAccountsAtom` here) is refreshed by copying/reusing previously cached entries, and the cache-invalidation check only looks at whether the *set of keys* changed, not whether the *underlying value* behind an existing key changed. Because `WalletAccount.toString()` deliberately excludes `seedId` for `exodus`-sourced accounts, the same cache key (e.g. `exodus_0`) can persist across a change of the underlying seed, causing a previously-cached address for a different seed to be served to a connected dApp as if it belonged to the currently active seed's account.

### Finding Description
`WalletAccount.toString()` intentionally omits `seedId` when `source === EXODUS_SRC` (only `SEED_SRC`/`PASSKEY_SRC` accounts include `seedId` in the string key): [1](#0-0) 

Yet `seedId` is still a real, distinguishing field that gets set per-account during creation, tied to `primarySeedId`: [2](#0-1) 

`connections.js` caches derived addresses per wallet-account key in `#connectedAccountsAtom` and reuses the cached address without checking if the account behind that key still corresponds to the same seed: [3](#0-2) 

The refresh trigger for this cache, `updateConnectedAccounts`, only recomputes when the **set of keys** (`Object.keys(walletAccounts)` vs `Object.keys(connectedAccounts)`) differs — exactly analogous to the Yearn `allVaults`/`setRegistry` bug where only additions/removals of the top-level list are considered, and the “prefix” (existing keys whose underlying value changed) is never refreshed: [4](#0-3) 

Because the `exodus_0` key is seed-agnostic in its string form, if the primary seed used to derive the default `exodus_0` wallet account changes (e.g. via a wallet reset/import flow that re-creates the same-named default account under a new `primarySeedId`, without going through a full `clear()`/`onClear` reset of `connectedOrigins`), `updateConnectedAccounts`'s `xor` check sees no key-level difference and skips recomputation, leaving the stale, previous-seed address cached under `exodus_0` in `connectedAccountsAtom`.

`getConnectedAccounts`, which is exposed to any connected/trusted dApp origin and can run while the wallet is even locked, then returns this stale cached address as the current active account's address: [5](#0-4) 

### Impact Explanation
A dApp that is already connected/trusted for an origin can be handed an address that belongs to a previously-active seed rather than the currently active seed for the same named wallet account (`exodus_0`). Since the user is asserting the returned address represents their current wallet, they (or the dApp) may direct fund transfers to it — resulting in funds going to a wallet the user no longer controls (an old/replaced seed), or the wrong account context bleeding into a supposedly fresh session. This satisfies the "cross-origin/account privilege bleed" bar: the connected-origins cache does not correctly scope by the actual seed identity, only by a seed-agnostic label.

### Likelihood Explanation
This requires a specific but realistic sequence: an origin must already be trusted/connected, and the wallet's default account (or another exodus-source account) must be re-derived under a different `primarySeedId` while keeping the same index/name, without the connected-origins module's caches being flushed. Whether the app's reset/import UX always calls `connectedOrigins.clear()` in every such transition is uncertain from the available code — `onClear` (triggered by `plugin/index.js`) does call `connections.clear()`, but it's not verified from indexed code whether every "seed replaced under the same account name" path always triggers that specific `onClear` hook versus e.g. a lighter update path that leaves `connectedOriginsAtom`/`connectedAccountsAtom` intact. This is a real design gap (cache invalidation keyed on wrong identity) rather than a fully proven exploited runtime chain from the indexed code alone.

### Recommendation
Do not rely solely on `xor(Object.keys(walletAccounts), Object.keys(connectedAccounts))` to decide when to refresh `#connectedAccountsAtom`. Instead, detect value-level changes (e.g., compare `seedId`/`compatibilityMode`/full `toJSON()` per key, not just key presence) similar to how the Yearn recommendation calls for refreshing the full cached prefix, not just appended entries. Alternatively, include `seedId` in the cache key derivation for all wallet-account sources (or explicitly invalidate/evict cached addresses whenever `wallet-accounts` module persists an update where `seedId` changes for an existing name) so that stale seed-scoped data can never be served under a reused name.

### Proof of Concept
1. Connect/trust `dapp.example` for the default wallet account `exodus_0` (seed A); `connectedAccountsAtom` caches `{ exodus_0: { addresses: { <asset>: <addr-derived-from-seed-A> } } }` via `#getAccounts`/`#getWalletAccountAddresses` (features/connected-origins/module/connections.js:108-138).
2. Trigger a flow that recreates/updates the default `exodus_0` wallet account under a new `primarySeedId` (seed B) without invoking the connected-origins `clear()` path — `WalletAccount.toString()` for `exodus_0` stays identical (libraries/models/src/wallet-account/index.ts:217-225), so `Object.keys(walletAccounts)` is unchanged.
3. Call `connectedOrigins.updateConnectedAccounts()` (features/connected-origins/module/connections.js:299-314) — the `xor` check finds no difference and returns early, skipping recomputation.
4. `dapp.example` calls `getConnectedAccounts({ origin: 'dapp.example' })` and receives the address still derived from seed A, even though the active/default account is now backed by seed B — a stale, wrong-seed address is exposed as the current account.

```javascript
  #getWalletAccountAddresses = async (walletAccount, assetNames) => {
    const connectedAccounts = await this.#connectedAccountsAtom.get()
    const entries = await Promise.all(
      assetNames.map(async (assetName) => {
        const existingAddress = connectedAccounts[walletAccount]?.addresses[assetName]
        if (existingAddress) {
          return [assetName, existingAddress]
        }

        const address = await this.#addressProvider.getDefaultAddress({ assetName, walletAccount })
        return [assetName, address.toString()]
      })
    )

    return Object.fromEntries(entries)
  }
```

```javascript
  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
```

```javascript
  updateConnectedAccounts = async () => {
    const walletAccounts = await this.#enabledWalletAccountsAtom.get()
    const connectedAccounts = await this.#connectedAccountsAtom.get()

    const difference = xor(Object.keys(walletAccounts), Object.keys(connectedAccounts))
    if (difference.length === 0) {
      // up-to-date
      return
    }

    const connectedOrigins = await this.#connectedOriginsAtom.get()
    const assetNames = this.#getConnectedAssets(connectedOrigins)
    const updatedAccounts = await this.#getAccounts(assetNames)

    await this.#connectedAccountsAtom.set(updatedAccounts)
  }
```
