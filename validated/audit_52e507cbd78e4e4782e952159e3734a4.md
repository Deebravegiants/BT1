### Title
Unchecked-length copy from ABI-decoded BEEFY `Vote.signature` into fixed 65-byte buffer panics on malformed input - (File: `evm/rust/src/conversions.rs`)

### Summary
`impl From<Vote> for SignatureWithAuthorityIndex` in `evm/rust/src/conversions.rs` copies an ABI-decoded, attacker-controlled `bytes` field directly into a fixed-size `[u8; 65]` array with `copy_from_slice` and no length check first, exactly the same bug class as CVE-2017-10971 (fixed-size buffer written from a length that was never validated against the buffer size during endianness/format conversion).

### Finding Description
`Vote` is a Solidity-ABI type (`evm/src/consensus/Types.sol`) whose `signature` field is a dynamic `bytes`, decoded from a submitted BEEFY consensus proof. The Rust-side conversion assumes it is always exactly 65 bytes: [1](#0-0) 

```rust
impl From<Vote> for SignatureWithAuthorityIndex {
    fn from(value: Vote) -> Self {
        let sig_bytes = value.signature.to_vec();
        let mut signature: TSignature = [0u8; 65];
        signature.copy_from_slice(&sig_bytes);
        SignatureWithAuthorityIndex {
            signature,
            index: value.authorityIndex.try_into().expect("authority index out of bounds"),
        }
    }
}
```

`copy_from_slice` panics ("source slice length does not match destination slice length") whenever `sig_bytes.len() != 65`. Since `Vote.signature` originates from ABI-decoded bytes supplied inside a submitted consensus proof (the naive/`PROOF_TYPE_NAIVE` BEEFY proof path decoded via `abi_decode` as seen for `BeefyConsensusProof` in `parachain/simtests/src/pallet_beefy_consensus_proofs.rs`), an attacker can submit a proof whose vote signature is any length other than 65 and trigger a panic during conversion, before any cryptographic verification occurs.

This is the same root-cause pattern the codebase has already had to fix in multiple other places precisely because it is treated as security-relevant: [2](#0-1) [3](#0-2) 

The `host.rs` regression comment explicitly documents that an unchecked `copy_from_slice` into a fixed array is "a wasm trap reachable from untrusted input ... in the runtime", and the fix there was to check the length before copying. The identical unchecked pattern in `conversions.rs` for BEEFY `Vote.signature` was not found to have an equivalent length guard.

### Impact Explanation
A panic/trap triggered from a value derived directly from a submitted, unsigned consensus proof is a denial-of-service vector against the BEEFY consensus verification path: any relayer able to submit a naive BEEFY proof can craft a `Vote` with a malformed signature length and crash the conversion routine that runs as part of processing that proof, rather than being cleanly rejected with a verification error. Depending on where in the pipeline this executes (validate_unsigned / on-chain dispatch vs. off-chain worker), this can degrade or halt the BEEFY consensus-update route, which the rules explicitly count as impact ("a route unable to deliver messages").

### Likelihood Explanation
The `Vote` struct's `signature` is ABI `bytes`, so nothing enforces a 65-byte length at decode time; any submitter of a naive-format consensus proof controls this value entirely. No signature or cryptographic check occurs before this conversion, so the panic is trivially reachable pre-verification, similar to how the X.Org bug allowed an authenticated-but-unprivileged client to hit an endianness/length-assumption violation before any deeper validation.

### Recommendation
Validate `value.signature.len() == 65` before constructing the fixed array (return an error / `Result` instead of `From`, or use `TryFrom` with `try_into()` to fail gracefully), matching the fix pattern already applied in `modules/ismp/core/src/host.rs` and `modules/utils/serde/src/lib.rs` for the same class of unchecked `copy_from_slice`.

### Proof of Concept
1. Construct a `BeefyConsensusProof` (or the relevant naive-proof ABI payload) whose `Vote.signature` field is ABI-encoded as a `bytes` value of length ≠ 65 (e.g., 64 or 66 bytes), with `authorityIndex` set to any valid value.
2. Submit it via the proof-submission path that ultimately decodes to `Vote` and calls `SignatureWithAuthorityIndex::from(vote)` (the naive BEEFY consensus proof path, as exercised in `parachain/simtests/src/pallet_beefy_consensus_proofs.rs`).
3. Observe that `signature.copy_from_slice(&sig_bytes)` panics with a length-mismatch trap instead of returning a decode/verification error, before any signature or authority-set validation is performed.

**Note on completeness:** I was not able to fully trace, within the available tool budget, the exact caller chain that invokes `From<Vote> for SignatureWithAuthorityIndex` end-to-end (i.e., confirm whether it is only exercised in an off-chain prover context vs. directly in the on-chain unsigned-proof validation path). The `evm/rust/src/conversions.rs` module is compiled with `feature = "substrate"`, and given the project's own regression tests/fixes for identical unchecked `copy_from_slice` patterns elsewhere (`host.rs`, `serde/src/lib.rs`) explicitly citing "reachable from untrusted input" via consensus/RPC data, this is flagged as a genuine unresolved instance of the same bug class, but full reachability confirmation would benefit from a broader codebase search than the index currently allowed.

	///
	/// The string must be exactly 4 bytes long (bytes, not chars — a 4-char string of
	/// multi-byte codepoints is rejected). Anything else is a deserialization error; this
	/// runs on untrusted RPC input, so it must never panic.
	pub fn deserialize<'de, D, T>(deserializer: D) -> Result<T, D::Error>
	where
		D: serde::Deserializer<'de>,
		T: From<[u8; 4]>,
	{
		let s = <String>::deserialize(deserializer)?;

		// `s.len()` is the utf-8 byte length, which is what the `[u8; 4]` needs to match.

			.try_into()
