Audit Report

## Title
CORS Wildcard-Origin Suffix Validation Bypass Allows Any Attacker Domain Ending in the Allowed Suffix to Read Gateway Responses - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway's `isAllowedOrigin` function performs a raw `strings.HasSuffix` check when matching wildcard CORS entries (e.g. `*.ethereum.org`), without requiring a `.` label boundary before the suffix. This lets any attacker-controlled domain merely ending in the configured suffix (e.g. `evilethereum.org`) be treated as an allowed origin, causing the server to reflect it into `Access-Control-Allow-Origin` and grant cross-origin read access to gateway responses.

## Finding Description
In `isAllowedOrigin` [1](#0-0) , once the `*.` prefix is stripped from a configured wildcard entry, the code checks `strings.HasSuffix(originHost, allowedHost)` with no verification that the match begins at a subdomain boundary. Given `CORSAllowedOrigins = ["https://*.ethereum.org"]`, `allowedHost` becomes `ethereum.org`, and `strings.HasSuffix("evilethereum.org", "ethereum.org")` returns `true`, incorrectly treating `evilethereum.org` as trusted. This bug is directly analogous to a `startsWith()`-based prefix bypass but anchored on the suffix side. The result feeds directly into `handleRequest` [2](#0-1) , which reflects the forged `Origin` header value into `Access-Control-Allow-Origin`, allowing a browser on the attacker's domain to read `ProcessRequest`'s [3](#0-2)  JSON response cross-origin. No other authentication, redaction, or boundary check exists in this path to prevent the bypass — the exact/host match check above it (`originHost == allowedHost`) does not cover this branch. The wildcard-matching feature itself is a documented, tested capability of the codebase, confirmed by the existing test suite [4](#0-3) , so this is a code-logic flaw in a supported feature, not a pure misconfiguration.

## Impact Explanation
This is a concrete CWE-601-class allowlist bypass reachable by any unprivileged web client capable of sending a cross-origin request (or luring a victim's browser) to the Gateway's internet-facing `UserServerConfig` endpoint. Once bypassed, the attacker's page gains browser-enforced read access to gateway JSON-RPC responses that should be restricted to legitimate allowed origins, which can include workflow/job results tied to other users' requests — matching the in-scope "gateway request impersonation / cross-user response corruption" impact category.

## Likelihood Explanation
Exploitability is gated on the operator using a wildcard entry in `CORSAllowedOrigins` with `CORSEnabled = true`, which is a supported and tested configuration pattern rather than an unusual or prohibited misconfiguration. No credentials or special privileges are needed by the attacker — only control of a domain sharing the allowed suffix and the ability to trigger a cross-origin request against the gateway, which is standard unprivileged client behavior.

## Recommendation
Require a proper subdomain boundary before applying the suffix match, e.g.:
```go
if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
    return true
}
```
or parse and compare host labels explicitly rather than doing raw substring/suffix comparisons.

## Proof of Concept
1. Configure the Gateway with:
```toml
[UserServerConfig]
CORSEnabled = true
CORSAllowedOrigins = ["https://*.ethereum.org"]
```
2. Send a cross-origin request to the Gateway's configured `Path` (e.g. `/user`) with header `Origin: https://evilethereum.org`.
3. Observe the response includes `Access-Control-Allow-Origin: https://evilethereum.org`, confirmed via the `strings.HasSuffix` branch at [5](#0-4) , proving the attacker-controlled origin was incorrectly trusted.
