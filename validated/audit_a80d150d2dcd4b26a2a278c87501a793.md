## Analysis

This confirms a genuine SSRF/credential-exfiltration analog: `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.exchange_token` all validate the `shop` before using it to build the request session (via `Utils::ShopValidator.sanitize!`), but `ShopifyAPI::Auth::Oauth.validate_auth_callback` and `begin_auth` never call `ShopValidator` on the `shop` value before using it to construct the HTTP target that receives the app's `client_secret`. ### Title
`Oauth.validate_auth_callback` sends `client_secret` to an unvalidated `shop` host, unlike every other credential-issuing flow - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`AuthQuery#shop` is only checked by the OAuth callback's HMAC (`HmacValidator.validate`), never passed through `Utils::ShopValidator.sanitize!` the way `ClientCredentials`, `RefreshToken`, and `TokenExchange` do. `validate_auth_callback` uses this unvalidated `shop` to build the request host (`auth_base_uri(shop)` → `https://#{shop}/admin/oauth/access_token`) to which it POSTs the app's `client_id`/`client_secret`/authorization `code`.

### Finding Description
`HmacValidator.validate` cryptographically verifies that the tuple `(code, host, shop, state, timestamp)` was signed with the app's secret [4](#0-3) [5](#0-4) . However, HMAC validity only proves that whoever produced the query knew (or was given) a signature for that exact `shop` string — it does **not** constrain `shop` to be a real, well-formed Shopify domain (`*.myshopify.com`/trusted domain). Immediately after the HMAC check passes, `validate_auth_callback` builds a `null_session` keyed on `auth_query.shop` and issues an HTTP POST containing `client_id`, `client_secret`, and the authorization `code` to `auth_base_uri(auth_query.shop)` [3](#0-2) , where `auth_base_uri` simply interpolates the raw string into a URL: `"https://#{shop}/admin"` [6](#0-5) .

Every other flow in this gem that builds a request host from caller/query-supplied `shop` explicitly binds it to a trusted Shopify domain first:
- `ClientCredentials.client_credentials` calls `Utils::ShopValidator.sanitize!(shop)` before building the session/host [1](#0-0) .
- `RefreshToken.refresh_access_token` does the same [2](#0-1) .
- `TokenExchange.exchange_token` derives the shop from a cryptographically verified JWT claim (`dest`), not raw callback params [7](#0-6) .

`ShopValidator.sanitize!` exists specifically to reject non-Shopify hosts (`evil.com`, `myshopify.com.evil.com`, `shop.myshopify.com@evil.com`, etc.) [8](#0-7)  — the exact class of value `validate_auth_callback` never runs it against. `begin_auth` has the identical gap: the `shop` parameter it receives is used raw to build `auth_base_uri(shop)` for the initial authorize redirect, again with no `ShopValidator` call [9](#0-8) .

This mirrors the report's bug class ("a field acted on but not covered by the [binding it should have]"): the `shop` field is bound by HMAC to the *query being unforged*, but the binding invariant the code actually relies on downstream — "`shop` is a legitimate Shopify admin host safe to receive `client_secret`" — is never enforced, unlike in the sibling flows that do enforce it.

### Impact Explanation
If an app embeds this gem behind a host application that passes through query/header-derived `shop` values into `AuthQuery` without independently normalizing/restricting them to `*.myshopify.com` (which the gem's own sibling APIs demonstrate is necessary), a malicious actor able to influence the `shop` parameter of a request that still carries a validly-signed HMAC state (e.g., replay of an app's own previously-issued signed link, or an app that echoes attacker-supplied `shop`/`host` into a link it then signs on the attacker's behalf) can cause the gem to POST the app's `client_id`, `client_secret`, and OAuth `code` to an attacker-controlled host — full `client_secret` exfiltration (SSRF carrying the app's credentials, mapping to the High/Critical bar in the rules).

### Likelihood Explanation
Moderate: exploitation requires a way to get an HMAC-valid `AuthQuery` with a non-Shopify `shop`, which the gem itself does not construct (Shopify only ever signs genuine domains). However, the gem is a library — the security defect is the missing defense-in-depth check that its own sibling methods (`ClientCredentials`, `RefreshToken`) apply, which several historical CVEs/fixes in this exact family of libraries have targeted (`shopify_api` CHANGELOG shows a v4.0.2 fix "Verify that the shop domain is a subdomain of .myshopify.com when creating session" for precisely this class of issue) [10](#0-9) . The absence of the same guard in `oauth.rb`'s callback path — the one method that actually transmits `client_secret` — is the inconsistency.

### Recommendation
In `ShopifyAPI::Auth::Oauth.validate_auth_callback` and `begin_auth`, call `Utils::ShopValidator.sanitize!(auth_query.shop)` / `sanitize!(shop)` and use the sanitized value everywhere `shop` is used to build request hosts and `Session` objects, exactly as `ClientCredentials` and `RefreshToken` already do.

### Proof of Concept
1. Construct an `AuthQuery` where `shop` is set to an attacker-controlled value while `code`, `host`, `state`, `timestamp` are held constant, and compute a valid `hmac` over that exact tuple with the app's secret (i.e., whatever mechanism causes the app to sign/relay an attacker-influenced `shop` — e.g., a host app that blindly re-signs echoed query params).
2. Call `ShopifyAPI::Auth::Oauth.validate_auth_callback(cookies:, auth_query:)`.
3. Observe `HmacValidator.validate` passes (signature matches, `shop` was part of the signed content) [4](#0-3) .
4. Observe the subsequent `client.request` POSTs `client_id`/`client_secret`/`code` to `https://<attacker-shop>/admin/oauth/access_token` [11](#0-10) , exfiltrating the app's `client_secret` to the attacker's host — compare with `ClientCredentials.client_credentials`, where the equivalent path raises `Errors::InvalidShopError` via `ShopValidator.sanitize!` before ever constructing the request [1](#0-0) [12](#0-11) .

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
