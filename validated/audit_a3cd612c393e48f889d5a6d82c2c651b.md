### Title
User-centric signups report local success without backend enrollment/duplicate-check confirmation - (File: `src/plans/mod.rs`)

### Summary
In `do_signup`, when a signup's `user_centric_signup` flag is `true` (and the orb config `ignore_user_centric_signups` is `false`), the code skips the backend enrollment round-trip (`enroll_user::Plan::run`, which posts to `signup_post`/`signup_poll` and performs backend-side duplicate/fraud confirmation) and instead derives `success` purely from the orb's own local `signup_reason`. The same "successful signup" reporting/telemetry path (`report_signup_reason`, `debug_report.signup_successful()`, success counters, UI/DBus completion signals) still fires as if the signup had been verified by the backend, creating a discrepancy between what is recorded/broadcast by the orb and what has actually been confirmed server-side — directly analogous to the reported Seaport issue where `OrderFulfilled` is emitted for a `CONTRACT` order whose numerator/denominator validity check was skipped.

### Finding Description
For a normal (non-user-centric) signup, `do_signup` calls `self.enroll_user(...)`, which invokes `enroll_user::Plan::run` to `POST` the signup to the backend (`signup_post::request`) and then poll (`signup_poll::request`) until the backend confirms completion, including backend-side duplicate detection and fraud checks [1](#0-0) . Only a backend `Completed`/`success: true` response yields `Status::Success` [2](#0-1) .

However, when `qr_codes.user_data.user_centric_signup` is `true` and the backend-configured `ignore_user_centric_signups` flag is `false`, this entire backend confirmation step is bypassed: [3](#0-2) 

Instead, `success` is set to `signup_reason == SignupReason::Normal`, i.e., purely based on the orb's own local pipeline/fraud-check outcome computed earlier in the same function [4](#0-3) . The identical downstream success-reporting logic is then invoked regardless of which path was taken: [5](#0-4) 

That call records `debug_report.signup_successful()` and increments `main.count.signup.result.success.successful_signup`, and `result.success` is derived from `debug_report.enrollment_status` [6](#0-5) . This report/telemetry, plus the UI completion event and `dbus::Signup::signup_finished` signal consumed by other on-orb processes, is emitted the same way whether or not the backend ever actually confirmed the signup as valid/unique.

Notably, the PCP (Personal Custody Package containing biometric templates) is already built and uploaded to the backend *before* this branch executes (lines 574-637), independent of whether the enrollment/duplicate-check call happens afterward. So for `user_centric_signup` signups, biometric data upload proceeds, but the check that the backend actually accepted/deduplicated this particular signup is skipped, while the orb still declares and broadcasts "signup successful."

### Impact Explanation
This produces a state where the orb's local record (`debug_report`, telemetry counters, UI feedback, and DBus signal to other local processes) claims a completed/successful signup that the backend has not verified for duplication or fraud. This is a direct analog of the reported bug class: a validity check (backend confirmation) is skipped for a particular order/signup "type," yet the success-signaling/event-emission logic proceeds unconditionally, creating a discrepancy between the recorded outcome and the actual backend-confirmed state. Downstream consumers of these signals (operators relying on UI success state, other local daemons subscribed to the DBus `signup_finished`/UI events, and off-orb systems relying on the uploaded debug report) may treat this as a confirmed, unique enrollment when the backend has not verified it, which can result in misattributed or duplicate signups being treated as successful.

### Likelihood Explanation
The `user_centric_signup` flag is attacker/app-influenced input: it originates from `authenticated_app_data.user_centric_signup` returned by the `user_status` backend response tied to the scanned user QR code [7](#0-6) , and the orb only overrides this behavior if the `ignore_user_centric_signups` config is explicitly set to `true` [8](#0-7) . If that config defaults to `false` (as it does by default: `ignore_user_centric_signups: false` [9](#0-8) ), any signup flow where the associated app reports `user_centric_signup = true` will hit this code path on every signup, making this a normal/expected condition rather than an edge case.

### Recommendation
Do not let the "successful signup" reporting path (`report_signup_reason`, `debug_report.signup_successful()`, success counters, UI/DBus completion signals) diverge in meaning between the backend-confirmed and locally-inferred paths. Either:
1. Always perform the backend `enroll_user` confirmation round-trip (even for user-centric signups, using a lightweight backend confirmation call) before marking a signup as successful, or
2. If the local-only success determination for user-centric signups is intentional, tag/emit a differentiated status/event (e.g., distinct from `SignupReason::Normal`/`signup_successful`) so downstream consumers of debug reports, telemetry, and DBus/UI signals can distinguish backend-confirmed signups from locally-declared ones, avoiding any assumption that the signup was deduplicated/validated by the backend.

### Proof of Concept
1. Configure the backend to return `authenticated_app_data.user_centric_signup = true` for a given user QR code status request (`src/backend/user_status.rs`), and leave `ignore_user_centric_signups` unset/`false` in the orb config.
2. Trigger a signup on the orb; the local pipeline completes without triggering orb-side fraud detection (`signup_reason == SignupReason::Normal`).
3. Observe in `do_signup` (`src/plans/mod.rs`, lines 639-662) that `enroll_user`/`signup_post`/`signup_poll` (the backend duplicate/fraud confirmation flow) is never invoked, yet `report_signup_reason` marks the debug report as `signup_successful()`, increments the success counter, and the UI/DBus signal a completed successful signup — despite the backend never having confirmed uniqueness or accepted the enrollment for this signup ID.

    fn report_signup_reason(
        success: bool,
        signup_reason: SignupReason,
        debug_report: &mut debug_report::Builder,
    ) {
        if signup_reason == SignupReason::Failure {
            tracing::info!("User enrollment failed due to a failure in the pipeline");
            debug_report.signup_orb_failure();
        } else if signup_reason == SignupReason::Fraud {
            tracing::info!("User enrollment failed due to fraud");
            debug_report.signup_fraud();
