### Title
Overflow in market accrual permanently freezes a high-utilization market - (File: common/src/rates/simulate.rs)

### Summary

**Medium.** A market can reach a state where converting aggregate debt or supply shares back to RAY-denominated value overflows `i128`; because every market operation performs accrual first, subsequent `update_indexes`, `borrow`, `repay`, `withdraw`, and liquidation paths revert indefinitely. [1](#0-0) 

### Finding Description

`accrue_step` begins by multiplying aggregate scaled debt and supply by their respective indexes through `scaled_to_original`. [2](#0-1)  `scaled_to_original` is a checked `Ray::mul`, so a representable scaled-share balance multiplied by a sufficiently grown index panics once the RAY value exceeds `i128::MAX`. [3](#0-2)  Although `update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY`, that cap is applied only after calculating the new index and does not prevent the aggregate value multiplication from overflowing before the cap is reached. [4](#0-3) 

The pool invokes this function from `global_sync`, which is the accrual phase used before market mutations. [5](#0-4)  The integration test creates an 18-decimal market, supplies `10^27` base units, borrows 98% of it, advances accrual until `update_indexes` fails with `MathOverflow`, and confirms that withdrawal and repayment then fail with the same error. [6](#0-5) 

### Impact Explanation

Once the product crosses the representable RAY-value boundary, the failing transaction cannot commit the new `last_timestamp`, so every later accrual attempts the same overflowing calculation again. [5](#0-4)  Because the panic occurs before repay, withdrawal, liquidation, or market settlement logic runs, suppliers cannot recover liquidity and borrowers cannot reduce debt through ordinary permissionless paths. [7](#0-6)  This is permanent freezing of market funds and leaves the protocol unable to resolve the affected market. [8](#0-7) 

### Likelihood Explanation

An unprivileged attacker can establish the precondition through normal `controller::supply`, `controller::borrow`, and `controller::update_indexes` calls if governance lists a sufficiently large, high-decimal market and the attacker controls enough collateral to sustain near-full utilization. [9](#0-8)  The condition requires extreme market size and sustained high utilization, so it is less likely than an ordinary theft path, but it does not require privileged execution, leaked keys, or malformed contract state. [10](#0-9) 

### Recommendation

Bound aggregate scaled share balances against the maximum value representable at the current and capped indexes before allowing additional supply or debt, and make accrual commit a safe capped state rather than attempting an overflowing aggregate conversion. [11](#0-10)  Repayment and withdrawal resolution should also avoid requiring a complete `i128` valuation when the caller requests a smaller partial amount, so capped or saturated markets remain unwindable. [12](#0-11)

// Once index growth makes borrowed * borrow_index / RAY exceed i128::MAX,

// Both ordinary settlement paths still accrue first and therefore remain blocked.
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);

The test asserts that the stored borrow index remains below `MAX_BORROW_INDEX_RAY`, proving that the aggregate value overflows before the intended index cap provides protection. [10](#0-9)
