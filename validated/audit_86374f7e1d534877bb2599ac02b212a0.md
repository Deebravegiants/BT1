This confirms the vulnerability: the docs explicitly instruct developers to trust `data.shop` as "The shop domain of the webhook" for routing logic (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), yet this value is read straight from the unauthenticated `x-shopify-shop-domain` header and is never included in the HMAC-covered signable string.### Title
Webhook `shop` identity is trusted for tenant routing but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw body, then hands the caller-supplied `x-shopify-shop-domain` header straight through to the app's handler as the trusted tenant identifier, even though that header is never part of the signed data.

### Finding Description
This mirrors the M-10 bug class: a value that is *acted on* (used to make an authorization/attribution decision) is not the same value that was *actually verified*. In `_updateVirtualPrice`, the time value used to advance state (`_currentBlockTime`) differs from the value actually accounted for in the interest math (the truncated `threeMinuteDelta`), breaking the invariant `elapsed_time_used == elapsed_time_verified`. Here the analogous equality that should hold is `shop_verified == shop_used`, and it does not.

- `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
- `Webhooks::Request#shop` is read directly from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header, independent of the signed body: [2](#0-1) 
- `HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body only) and compares it to the `hmac-sha256` header: [3](#0-2) 
- `Registry.process` treats a passing HMAC check as proof the *entire request* (including `shop`) is legitimate, then forwards `request.shop` unmodified into `WebhookMetadata` for the app's handler: [4](#0-3) 
- The library's own documentation instructs developers to trust `data.shop` as "The shop domain of the webhook" and use it directly for tenant-scoped work (e.g. `shop_domain: data.shop`), reinforcing that this field is meant to be the authoritative tenant identity: [5](#0-4) 

Because `shop`, `topic`, `api_version`, and `webhook_id` are excluded from `to_signable_string`, the HMAC only proves "this body byte-string was produced with knowledge of `client_secret`" - it proves nothing about which shop, topic, or delivery the body belongs to. Anyone who can obtain one validly-signed `(raw_body, hmac)` pair for *any* shop (e.g., by installing the app - even a free/dev store install counts as "unprivileged") can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will dispatch the handler with `shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker who is a legitimate (but unprivileged, e.g. free-trial) merchant of the app can cause the app to process a forged event body under a *different* shop's identity. Since the library explicitly documents `data.shop` as the field apps should use to route/persist webhook data per-tenant, this enables cross-tenant data injection/corruption (e.g. attacker's own `orders/create` payload being written into the victim shop's records), satisfying the "cross-tenant access" Critical impact criterion.

### Likelihood Explanation
Moderate-to-high. The attacker needs only:
1. The ability to install the app on any shop they control (satisfies "unprivileged internet user" - no `api_secret_key`, access token, or victim credentials required).
2. To trigger one webhook delivery for a topic the app subscribes to, capture the raw body + `hmac-sha256` header, and replay the HTTP request to the app's own webhook endpoint with the `shop-domain` header changed. No secret material or MITM is needed since `shop` is never bound to the signature.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-covered signable string, or otherwise independently bind the `shop` value used by the handler to a value cryptographically verified as originating with the signed payload (e.g., derive/validate `shop` from a session already associated with the specific webhook subscription rather than trusting the request header verbatim).

### Proof of Concept
1. Attacker installs the target app on their own dev store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`). They capture the resulting raw POST body `B` and its `x-shopify-hmac-sha256: H` header (a valid signature since it was genuinely computed by Shopify for that body).
2. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only [1](#0-0)  and succeeds since `B`/`H` is unchanged.
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's parsed body>, ...)` [6](#0-5) , causing the app to process attacker-controlled data as if it belonged to the victim tenant.
