### Title
Webhook shop-domain not covered by HMAC allows cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity using only the HMAC of the raw request body, while the `shop` (and `topic`) values that are handed to the app's handler are read directly from unauthenticated HTTP headers. This is the same class of defect as the reported "approve before safeTransfer" bug: an action is performed (dispatching the webhook to a handler *as coming from shop X*) using a value (`shop`) that is not bound/covered by the cryptographic check that is supposed to guarantee integrity of the whole request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` (and `topic`) are pulled straight from headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates only this body-only HMAC, then forwards `request.shop` (header-derived, unverified) to the handler as if it were an authenticated fact about the request: [3](#0-2) 

`HmacValidator.validate` simply recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header — it never incorporates `shop` or `topic`: [4](#0-3) 

Because every shop installed on an app shares the same `api_secret_key` (it is an app-level secret, not a per-shop secret — see the OAuth/token-exchange code which always uses the single `Context.api_secret_key`), the HMAC only proves "this body was signed with the app's secret," not "this body/shop-domain pair came from Shopify for this particular shop." The equality the app is implicitly relying on — `shop_covered_by_hmac == shop_delivered_to_handler` — does not hold, because `shop` is never part of the signed material.

The gem's own documentation instructs handler authors to trust `data.shop` as "The shop domain of the webhook" with no caveat that it is unauthenticated: [5](#0-4) 
and to use it directly for tenant-scoped operations such as looking up which shop a job belongs to: [6](#0-5) 

### Impact Explanation
This enables cross-tenant confusion within a single app: an attacker who operates their own shop installed on the target app (an "unprivileged internet user" with respect to any other merchant's tenant) can trigger a legitimate webhook for their own store, capture the valid `X-Shopify-Hmac-Sha256` header (which only signs the JSON body) and the raw body, then resend the same body/HMAC pair to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. Since `Registry.process` never checks that the signed body is bound to the claimed shop, the request passes HMAC validation and is dispatched to the handler with `data.shop` set to the victim's domain. Any downstream logic that uses `data.shop` to select per-tenant state (webhook idempotency keys, job routing, notifications, feature flags, cached credentials, etc.) can be manipulated to act on/for the wrong tenant — a cross-tenant access primitive.

### Likelihood Explanation
Any merchant/developer who can install the target app on their own store (a standard, non-privileged action) can obtain a validly-signed body/HMAC pair for arbitrary webhook topics/content they can trigger (e.g., by creating an order or updating a product in their own store), then replay it with an arbitrary `shop` header value. No access to `api_secret_key`, access tokens, or the target victim's credentials is required — only the ability to observe a webhook delivered to one's own controlled endpoint and to send an HTTP request with a modified header to the app's public webhook route.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) as part of the material verified against the HMAC — or at minimum, do not treat header-derived `shop`/`topic` as trusted, tenant-authenticated data in `WebhookMetadata`. If Shopify's webhook signing scheme does not cover these headers, the gem should not present `shop` to handlers without a documented warning, and `Registry.process` should provide/require a mechanism (e.g., cross-checking the shop against the app's own installed-shops list, or verifying the request originates from the expected Shopify IP range/registered endpoint for that shop) so that handlers cannot be tricked into acting on a mismatched shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g., `products/update`) for their own shop and captures the raw POST: body `B`, headers including `x-shopify-hmac-sha256: H` (HMAC of `B` with the app's `api_secret_key`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same `body: B` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`, to the app's webhook endpoint.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: modified_headers)` yields `shop == "victim-shop.myshopify.com"`. [2](#0-1) 
5. `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and it matches `H`, so validation succeeds. [7](#0-6) 
6. `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, even though the body/content actually originated from the attacker's own shop. [3](#0-2)

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
