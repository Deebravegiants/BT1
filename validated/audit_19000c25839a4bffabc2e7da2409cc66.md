Audit Report

## Title
CORS Origin Wildcard Bypass via Suffix-Matching Instead of Subdomain-Boundary Check - (File: core/services/gateway/network/httpserver.go)

## Summary
The gateway's `isAllowedOrigin` function in `core/services/gateway/network/httpserver.go` validates wildcard CORS entries (e.g. `*.remix.ethereum.org`) using a raw `strings.HasSuffix(originHost, allowedHost)` check with no `.` boundary enforcement [1](#0-0) . This allows an attacker-controlled domain that merely ends with the same character sequence (e.g. `evilremix.ethereum.org`) to be treated as an authorized subdomain, even though it is a structurally unrelated domain.

## Finding Description
`isAllowedOrigin` splits the incoming `Origin` header and each configured allowed origin into scheme/host/port via `splitURL` [2](#0-1) , then for wildcard entries strips the `*.` prefix and performs a plain suffix comparison:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
``` [1](#0-0) 

For an allowed entry `*.remix.ethereum.org`, `allowedHost` becomes `remix.ethereum.org`. `strings.HasSuffix("evilremix.ethereum.org", "remix.ethereum.org")` evaluates to `true` because there is no requirement that the preceding character be `.` (i.e., no label-boundary check), so a domain like `evilremix.ethereum.org` (attacker-registrable, not a subdomain of `remix.ethereum.org`) is incorrectly treated as trusted.

This function is called directly from `handleRequest`, the handler wired to the gateway's public, unauthenticated user-facing path [3](#0-2) , and the mux registration shows this handler serves `config.Path` on the gateway's HTTP server [4](#0-3) . No authentication or prior credential is required to send a request with a spoofed `Origin` header — this is purely a header-driven decision evaluated on every request, and there is no other check (label-boundary, exact suffix component match, etc.) anywhere in the file that would catch this.

## Impact Explanation
When exploited, the attacker's non-subdomain origin gets `Access-Control-Allow-Origin` reflected back [5](#0-4) , granting a page hosted on the attacker's domain the ability to make CORS-permitted cross-origin requests to the gateway's JSON-RPC endpoint and read the responses via a victim's browser. This is a genuine allowlist-bypass class issue matching the "allowlist bypass" impact category, though actual severity depends on what session context/credentials a victim's browser would attach to such requests — the report itself acknowledges this uncertainty.

## Likelihood Explanation
Exploitation requires only that an operator configure a wildcard entry in `CORSAllowedOrigins` (a supported, documented configuration option, confirmed present in sample configs and covered explicitly by existing wildcard test cases such as `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` and `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`), and that the attacker registers a domain sharing the suffix. Notably, the existing negative test cases in the repo test unrelated bypass attempts (different label structure, wrong scheme, missing port) but do **not** test the "shares trailing substring without label boundary" case (e.g. `evilremix.ethereum.org` against `*.remix.ethereum.org`), confirming this specific gap is untested and unaddressed in the current code [6](#0-5) .

## Recommendation
Replace the raw suffix check with a boundary-aware comparison, requiring that `originHost` either equals the base domain or ends with `.` + the base domain:
```go
if strings.HasPrefix(allowedHost, "*.") {
    base := allowedHost[2:]
    if originHost == base || strings.HasSuffix(originHost, "."+base) {
        return true
    }
}
```

## Proof of Concept
1. Configure `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Send `POST` to the gateway user path with header `Origin: https://evilethereum.org` is not exploitable (wrong boundary case would be against `*.remix.ethereum.org`); using the exact wildcard `*.ethereum.org`, send `Origin: https://notethereum.org` — note this does NOT share the suffix. The correct minimal PoC: configure `CORSAllowedOrigins = ["https://*.remix.ethereum.org"]`, then request with `Origin: https://evilremix.ethereum.org`.
3. Following the logic in `isAllowedOrigin`, `allowedHost` becomes `remix.ethereum.org`, and `strings.HasSuffix("evilremix.ethereum.org", "remix.ethereum.org")` returns `true`, so the server responds with `Access-Control-Allow-Origin: https://evilremix.ethereum.org`.
4. This can be directly validated by adding a Go unit test to `core/services/gateway/network/httpserver_test.go` following the pattern of `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards`, but asserting that `evilremix.ethereum.org` is currently (incorrectly) accepted when allowed origins is `["https://*.remix.ethereum.org"]`.

func (s *httpServer) splitURL(rawURL string) (string, string, string, error) {
	// lowercase the URL to avoid case sensitivity issues
	parsedURL, err := url.Parse(strings.ToLower(rawURL))
	if err != nil {
		return "", "", "", fmt.Errorf("error parsing URL: %w", err)
	}

	host, port, err := net.SplitHostPort(parsedURL.Host)
	if err != nil {
		// if there's no port, the host itself is returned
		if parsedURL.Host != "" {
			return parsedURL.Scheme, parsedURL.Host, "", nil
		}
		return "", "", "", fmt.Errorf("error splitting host and port: %w", err)
	}

	return parsedURL.Scheme, host, port, nil
}
