### Title
Stale "not-blocked" queue check allows silent, permanent loss of already-captured biometric custody data before upload - (File: `src/agents/data_uploader.rs`)

### Summary
The data-uploader agent gates new signups on `wait_queues()`, which only checks that the PCP tier queues are below a *blocking* threshold before letting `do_signup()` push a new signup's Tier‑1/Tier‑2 personal-custody package. That "safe to proceed" check has no relationship to the *dropping* threshold that actually determines whether an existing, not-yet-uploaded package gets silently deleted. Because the two thresholds are independently configured (and, in the default configuration, one of them is effectively disabled), a signup can pass the `wait_queues()` check and still cause an earlier, still-pending signup's un-uploaded biometric package to be evicted and deleted from disk/memory without ever reaching the backend. This mirrors the audited pattern where a balance/state check performed at one point in time is invalidated by state-changing operations that happen afterward.

### Finding Description
`do_signup()` calls `data_uploader::wait_queues()` before enqueuing a signup's Tier‑1/Tier‑2 PCP packages: [1](#0-0) 

`wait_queues()` only resolves once `check_blocking()` reports the queues are under `blocking_thresholds`: [2](#0-1) [3](#0-2) 

However, the actual eviction of an existing queue entry is governed by a *separate* `dropping_thresholds` check that runs on every subsequent `Input::Pcp` push, independent of whether `wait_queues()` was ever satisfied for that particular item: [4](#0-3) 

`drop_oldest()` removes the oldest queued (i.e., not-yet-uploaded) package outright: [5](#0-4) 

The default configuration makes this concretely reachable: Tier‑2's blocking threshold is effectively infinite while its dropping threshold is a small, fixed number, so `wait_queues()` will never actually pause new signups on Tier‑2 backlog, yet Tier‑2 packages will still start getting dropped once the queue passes 12 entries: [6](#0-5) 

This is structurally the same bug class as the reported smart-contract issue: a guard (`wait_queues`/`_redeemable`) is evaluated against aggregate/point-in-time state, but a later, independent state-changing operation (`drop_oldest`/fee withdrawal) that isn't accounted for by that guard invalidates the assumption for entries that were already considered "safe" (queued/redeemable), permanently destroying data (funds) that a prior, legitimate caller (burn/signup) was relying on.

Because `upload_pcp()` retries uploads indefinitely on network errors and only gives up on client (4xx) errors, a package can legitimately sit in the queue for a long time waiting to be retried — during which several new signups arriving in sequence (each individually passing `wait_queues()`) can push it past the dropping threshold and get it evicted before it is ever uploaded to the backend.

### Impact Explanation
A user's captured iris/face self-custody biometric material (Tier‑1/Tier‑2 PCP) can be silently and permanently deleted from the orb without ever being uploaded to the backend, and without the signup flow or the user being informed — the drop happens fire-and-forget inside the agent loop, disconnected from the `success` result returned to the signup plan (`src/plans/mod.rs` lines 639-663 never observe this). This is a genuine biometric-retention integrity failure: data the system is contractually supposed to retain/upload for the user's self-custody package is lost due to a check (`wait_queues`) that gives false assurance about queue safety.

### Likelihood Explanation
This does not require a malicious actor — it is triggered by normal, unprivileged operation of the orb under ordinary conditions: intermittent backend connectivity (causing retries to pile up) combined with a burst of legitimate signups, which is a realistic operational scenario, especially given the default configuration where the Tier‑2 blocking threshold is disabled (`u32::MAX`) while its dropping threshold is a small fixed value (12).

### Recommendation
Make `wait_queues()`'s blocking condition and `drop_oldest()`'s dropping condition consistent for the same tier (e.g., ensure `blocking_threshold <= dropping_threshold`, and validate this invariant in `Config::validate`), or eliminate the silent drop path entirely in favor of always blocking new pushes until there is queue capacity, so that no in-flight biometric package a previous signup relied on can be evicted after a subsequent signup was told it was safe to proceed.

### Proof of Concept
1. Use default config: `pcp_tier2_blocking_threshold = u32::MAX`, `pcp_tier2_dropping_threshold = 12` (`src/config.rs` lines 432-435).
2. Simulate a flaky backend so `upload_pcp()` retries indefinitely for Tier‑2 uploads (`src/agents/data_uploader.rs` lines 176-217).
3. Run 13+ sequential signups; each call to `do_signup()` awaits `wait_queues()` (`src/plans/mod.rs` line 599), which always resolves immediately for Tier‑2 since its blocking threshold is `u32::MAX`.
4. On the 13th signup's `Input::Pcp` push, `queues[1].len() == dropping_thresholds[1]` (12) triggers `drop_oldest()` (`src/agents/data_uploader.rs` lines 142-145), deleting signup #1's still-unuploaded Tier‑2 package permanently, even though signup #1 was told (implicitly, via `wait_queues()` completing for it) that its queue slot was safe.

    async fn drop_oldest(&mut self) {
        match self {
            Self::Memory { queue } => {
                queue.pop_back();
            }
            Self::Persistent { path, queue, .. } => {
                let Some(id) = queue.pop_back() else { return };
                match ssd::perform_async(fs::remove_dir_all(path.join(id.to_string()))).await {
                    None => {
                        tracing::error!(
                            "Persistent queue is failed during drop_oldest, switching to memory"
                        );
                        *self = Self::new_memory();
                    }
                    Some(()) => {}
                }
            }
        }
    }
