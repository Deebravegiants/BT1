### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before dispatching to the app's handler with the shop identity attached. In reality, the HMAC signature only binds the raw request body — the `shop` (tenant) field is read directly from an unauthenticated HTTP header and is never included in the signed data. Because the HMAC secret (`api_secret_key`) is shared across every shop that installs the app, any merchant who has the app installed on their own store can capture one of their own legitimately-signed webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop, causing the app to process/attribute that webhook body under a different tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop` is read straight from the (unauthenticated) `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes and compares the signature over `to_signable_string` (i.e., the raw body), so it can never detect that the `shop` header has been altered: [3](#0-2) 

`Registry.process` performs exactly this check and then forwards `request.shop` straight into the `WebhookMetadata` handed to the app's handler as the trusted tenant identifier: [4](#0-3) 

The gem's own documentation tells integrators that `process` "will verify the request did indeed come from Shopify" and that the resulting `data.shop` is "The shop domain of the webhook" that they should key their business logic on: [5](#0-4) 

Because `api_secret_key` is the app's single client secret (identical for all shops using the app, not a per-shop secret), any shop that has installed the app can generate a validly-HMAC'd `(body, signature)` pair simply by triggering a webhook-eligible event on their own store. That attacker then replays the exact same body+signature to the app's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. `HmacValidator.validate` passes (body/signature match), and `Registry.process` dispatches the handler with `data.shop == "<victim-shop>"`, `data.body == <attacker-controlled/attacker-triggered content>`. This breaks the equality that should hold: `shop authenticated by HMAC == shop the app acts on`.

### Impact Explanation
This is a cross-tenant identity-binding bypass: the app is misled into associating an attacker-supplied or attacker-timed payload with a different, victim tenant (shop). Depending on how the host app's webhook handler uses `data.shop` (e.g., looking up the victim's session/access token to react to the event, updating shop-scoped records, triggering uninstall/reinstall logic, etc.), this enables cross-tenant data corruption or actions performed against a shop the attacker does not control — a direct violation of the multi-tenant isolation the gem is supposed to guarantee via HMAC verification, matching the "cross-tenant access" impact class.

### Likelihood Explanation
Any user who can install the target app on their own Shopify store (an ordinary, unprivileged action available to any merchant) can trigger a real webhook delivery for a topic with attacker-influenced content (e.g., `products/update`, `orders/create` with a chosen body), capture the legitimate `(body, hmac)` pair from their own store, and replay it to the app's public webhook endpoint with a forged `shop-domain` header naming any other shop using the app. No access token, `client_secret`, or privileged credential is required — only participation as a normal merchant of the target app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the HMAC-verified data instead of trusting it purely from headers: e.g., require the app to independently confirm the shop against a known/installed-shop record before acting, or extend the signable payload/verification to incorporate the shop header, and document clearly in `docs/usage/webhooks.md` that `data.shop` is unauthenticated and must be revalidated by the integrator against their own installed-shops list before use.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `products/update`) with a body they control.
2. Shopify sends the webhook to the app's endpoint with headers including a valid `x-shopify-hmac-sha256` computed over the raw body using the app's shared `api_secret_key`, and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same raw body and `x-shopify-hmac-sha256` value to the same endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this; `Utils::HmacValidator.validate` succeeds because it only checks the body against the secret (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` calls the app's handler with `WebhookMetadata`, where `shop == "victim-shop.myshopify.com"` and `body` is the attacker's data (`lib/shopify_api/webhooks/registry.rb:188-200`), even though the actual data originated from the attacker's own store.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
