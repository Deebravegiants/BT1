I now have sufficient evidence to validate this claim. Key findings:

1. The gateway's HTTP endpoint (`handleRequest` in `network/httpserver.go`) accepts requests from any caller and forwards to `gateway.ProcessRequest`, which routes by method name to `HandleJSONRPCUserMessage` — confirmed this is a public-facing endpoint with no mandatory auth beyond an optional JWT header that isn't checked by the ConfidentialRelay handler.

2. `HandleJSONRPCUserMessage` in `core/services/gateway/handlers/confidentialrelay/handler.go` indeed performs no authorization check and keys `activeRequests` purely by the caller-supplied `req.ID`, exactly as claimed, and the duplicate-ID rejection is real and tested.

3. Critically, the actual security-sensitive verification (`verifyAttestationHash`, `verifyEnclaveConfigMatchesDON`, `verifyWorkflowAuthorization` requiring a 2F+1/F+1 Workflow-DON-signed quorum) happens **downstream on the relay DON nodes** in `core/capabilities/confidentialrelay/handler.go`, not at the gateway. The gateway is explicitly documented as "a dumb relay" that "makes no trust decision" and does not interpret params beyond best-effort logging labels — this is by design, not an oversight.

4. This means the collision claim is real as a mechanism, but it is a **pure denial-of-service against a single specific request ID**, not any authentication/authorization bypass, secret exfiltration, fund movement, or impersonation. The downstream Workflow-DON quorum check is untouched and unaffected by the ID squat.

5. Feasibility of the attack: the attacker must supply the *exact* `req.ID` string chosen by the enclave for a specific in-flight execution before that request lands on the gateway. This ID is not shown to be derived from or predictable from any public value in the codebase (the enclave issues it internally per relay attempt), so the "learn or guess" precondition in the report's PoC is speculative and unsubstantiated by any concrete code path showing ID predictability or leakage.

Audit Report

## Title
Global request-ID collision in ConfidentialRelay gateway handler enables denial-of-service on a specific in-flight relay request - (File: core/services/gateway/handlers/confidentialrelay/handler.go)

## Summary
`newActiveRequest` in `core/services/gateway/handlers/confidentialrelay/handler.go` keys the shared `activeRequests` map by the raw, caller-supplied `req.ID` with no owner/session scoping, and `HandleJSONRPCUserMessage` performs no authorization check before this insertion, unlike the sibling Vault handler. [1](#0-0)  An attacker who first submits a request using a victim's exact `req.ID` value causes the victim's later legitimate request with that same ID to fail with "request ID already exists," as reproduced by the existing `TestConfidentialRelayHandler_DuplicateRequestID` test. [2](#0-1) 

## Finding Description
The confidential relay gateway is intentionally a "dumb relay" — it does not authenticate or authorize requests, and does not interpret request params beyond best-effort logging labels; all trust decisions (TEE attestation, DON-config matching, and 2F+1/F+1 Workflow-DON-signed quorum authorization) are deferred to the relay-DON nodes in `core/capabilities/confidentialrelay/handler.go`'s `handleSecretsGet`/`handleCapabilityExecute` and `verifyWorkflowAuthorization`. [3](#0-2)  Because the gateway layer has no authorization gate, `newActiveRequest` allows any caller reaching the gateway's public HTTP endpoint (`network/httpserver.go`'s `handleRequest` → `gateway.ProcessRequest` → `HandleJSONRPCUserMessage`) to occupy an arbitrary `req.ID` key in the shared map before the legitimate holder of that ID does. [4](#0-3) [5](#0-4)  The victim's subsequent submission with the same ID is rejected outright, before any authenticity or authorization check ever runs on the relay-DON side.

## Impact Explanation
This is a genuine gap, but its blast radius is narrow: it can deny exactly one specific gateway-level `req.ID` (i.e., one relay attempt of one workflow execution), and only if the attacker can supply that exact ID before the legitimate caller does. It cannot bypass authentication, forge a Workflow-DON quorum, exfiltrate secrets, or move funds — those protections live entirely on the relay-DON side and are untouched by this bug. The report itself frames the impact correctly as "targeted denial-of-service on a specific legitimate request," which is a much narrower impact than the report's title/summary implies ("deny their relay request," "brick another actor's operation") and does not map cleanly to any of the higher-severity in-scope impact classes (auth/role bypass, key/secret exfiltration, unauthorized fund movement, request impersonation, allowlist bypass, cross-user response corruption) — it is closest to a limited, single-request DoS.

## Likelihood Explanation
The report's exploit narrative depends on the attacker being able to "predict or learn" the victim's exact `req.ID` string ahead of time. No code path was found in this codebase showing that these IDs are derived from, or leak via, any value visible to an unprivileged external caller — the ID is generated internally by the enclave per relay attempt (retried IDs change per attempt per the code comments), and nothing in the reviewed code exposes it before the enclave submits its request. Without a concrete, demonstrated mechanism for an attacker to learn or predict a specific victim's `req.ID` in advance, the described attack is not shown to be practically exploitable — it is a "if you can guess/observe the ID" scenario with no supporting evidence that this ID is guessable/observable in practice.

## Recommendation
If this DoS surface is considered worth closing, scope the gateway's `activeRequests` key to include a component derived from an authenticated component of the request (e.g., a session/connection identity from the gateway↔enclave channel) rather than solely the caller-chosen `req.ID`, mirroring how the Vault handler namespaces by authorized owner. However, note that the confidential relay gateway is designed to be a trust-free relay by architecture; any fix should preserve that property rather than adding an authorization dependency the design intentionally avoids.

## Proof of Concept
`TestConfidentialRelayHandler_DuplicateRequestID` demonstrates the ID-collision rejection mechanically: [2](#0-1)  — but no test or code path in the codebase demonstrates an unprivileged attacker actually learning or predicting a victim's real, in-use `req.ID` value ahead of time, which is the missing link required to turn this into a realistic, targeted DoS against a specific victim.

// verifyWorkflowAuthorization is the PRIV-433 check beyond attestation. Attestation only
// proves the request came from genuine enclave code; it does not prove the Workflow DON
// authorized fetching this owner's secrets. A compromised TEE would still pass attestation
// while self-asserting a victim's owner.
//
// The enclave forwards the Workflow-DON-signed compute requests it executed (a 2*F+1 quorum,
// where F is the Workflow DON fault tolerance). Each node signs the same ComputeRequest.Hash();
// we reconstruct that hash, verify each signature against the onchain Workflow DON signer set,
// and require the quorum of unique signers. The signed PublicData names the authorized owner
// and workflow, which must match this request. A breached enclave cannot forge a Workflow DON
// quorum over a different owner.
//
// All failures here are client errors: the request is unauthorized. The caller fetches the
// Workflow DON (a server-side concern) and passes it in, so registry failures stay internal.
func (h *Handler) verifyWorkflowAuthorization(don capabilities.DON, params confidentialrelaytypes.SecretsRequestParams) error {
	if len(params.SignedComputeRequests) == 0 {
		return errors.New("missing signed compute requests")
	}

	// Match the enclave's own quorum. With requireBFTQuorum the relay demands a
	// Byzantine quorum of 2*F+1 unique signers; otherwise a crash-fault quorum of
	// F+1 suffices.
	threshold := int(don.F) + 1
	if h.requireBFTQuorum {
		threshold = 2*int(don.F) + 1
	}

	// The forwarded requests differ only in their signature; they all sign one shared
	// ComputeRequest hash. Reconstruct that hash once and verify each signature over it.
	hash := params.SignedComputeRequests[0].Hash()
	payload := confidentialrelaytypes.SignedComputeRequestSignaturePayload(hash)

	signers := make(map[string]struct{})
	for _, scr := range params.SignedComputeRequests {
		if scr.Hash() != hash {
			return errors.New("forwarded signed compute requests do not share one compute request")
		}
		for _, member := range don.Members {
			if ed25519.Verify(ed25519.PublicKey(member[:]), payload, scr.Signature) {
				signers[member.String()] = struct{}{}
				break
			}
		}
	}
	if len(signers) < threshold {
		return fmt.Errorf("insufficient Workflow DON signatures: %d unique signers, need %d", len(signers), threshold)
	}
