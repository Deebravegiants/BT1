### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), event `topic`, and `webhook_id` from unauthenticated HTTP headers, while the HMAC signature verified by `HmacValidator` only covers the raw request body. Any party who can obtain one genuinely HMAC-signed webhook body (e.g., by installing the app on their own store) can replay that exact body against the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to impersonate a different, victim tenant. `HmacValidator.validate` still returns `true` because it never inspects the headers, so `Registry.process` dispatches the forged request to the app's handler tagged with the attacker-chosen shop.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string` and compares it to the `hmac` value: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw JSON body: [2](#0-1) 

But the identity fields that the gem exposes and that the host application relies on — `shop`, `topic`, and `webhook_id` — come exclusively from HTTP headers that are **not** part of the signed string: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The equality that should hold is:
`shop authenticated by the HMAC == shop acted upon by the handler`

Because the HMAC only signs `@raw_body`, this equality does not hold — an attacker can keep the body (and its valid signature) fixed while swapping the `shop-domain`/`topic` header value, breaking the binding between "who Shopify claims sent this" and "what data was actually cryptographically endorsed."

### Impact Explanation
Any merchant/developer can install the target app on their own store and legitimately receive a validly HMAC-signed webhook (e.g., `app/uninstalled`, `customers/data_request`, `shop/redact`). They can then replay that exact signed body to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `Registry.process` will accept it as authentic (`Utils::HmacValidator.validate` passes because only the body is checked) and hand the handler a `WebhookMetadata` claiming the event is `for` the victim shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to mark a tenant uninstalled, purge a tenant's data for a redaction request, or trigger GDPR compliance actions), this results in cross-tenant data manipulation triggered by an unprivileged, unauthenticated-for-that-tenant actor — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that lets outside merchants install it (the normal Shopify app model): obtaining one validly-signed webhook body requires nothing more than installing the app on any store, which is the baseline unprivileged-user capability for this ecosystem. No secret material, leaked tokens, or privileged access is required — only a forged HTTP header on replay.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., verify the shop domain embedded in the payload itself matches the header, and reject webhooks whose header-derived shop was never associated with an active session/registration for this app). At minimum, document that `Request#shop`/`#topic` are unauthenticated and must be independently verified by the host application before being used for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a real webhook, e.g. topic `app/uninstalled`, with body `raw_body` and header `X-Shopify-Hmac-Sha256: <valid_hmac>` computed by Shopify over `raw_body` using the app's `client_secret`.
2. Attacker POSTs the identical `raw_body` and the identical `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. In the app, `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed and passed to `Registry.process`:
   - `Utils::HmacValidator.validate(request)` recomputes HMAC over `request.to_signable_string` (`== raw_body`) and it matches — validation passes.
   - `request.shop` returns `"victim-shop.myshopify.com"` (from the forged header).
4. `Registry.process` calls the app's `app/uninstalled` handler with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)`, causing the app to treat the victim shop as uninstalled/redacted even though the victim never sent this webhook and Shopify never issued it for that shop.
