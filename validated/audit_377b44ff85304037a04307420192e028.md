### Title
Out-of-bounds `body[0]` read in `ExtrinsicIntents.onAccept` panics on empty-body messages from Hyperbridge - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`onAccept` in `ExtrinsicIntents.sol` decodes `RequestKind` by indexing `incoming.request.body[0]` before validating that `body` is non-empty [1](#0-0) . This mirrors the CVE-2014-8716 bug class: a decoder indexes into attacker-influenced input without a length/bounds check first, causing an out-of-bounds access/crash on malformed input.

### Finding Description
`onAccept` is the `IIsmpModule` callback invoked by the `IsmpHost` (`onlyHost`) whenever a `PostRequest` targeting this contract is delivered [1](#0-0) . The very first operation on the request payload is:
```
RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
```
There is no check that `incoming.request.body.length > 0` before this indexing. In Solidity, indexing a zero-length `bytes calldata` array reverts with a `Panic(0x32)` (array out-of-bounds access) — the same underlying bug class as the JPEG decoder reading past the end of its buffer in CVE-2014-8716: a length-prefixed/variable-length decoder that indexes the buffer before validating its size.

Reachability: `body` is fully attacker/source-chain controlled. The dispatching source chain constructs the `PostRequest.body` (e.g. a compromised or malicious counterpart gateway on another chain, or any account able to dispatch a POST request whose `dest` targets this contract and whose `from` happens to match `_supportedChains`/gateway checks downstream — but critically the crash happens *before* any of the `RequestKind`-based authentication branches at lines 333-340, so the OOB read is unconditional on any inbound message that reaches `onAccept` with an empty body). Since `_checkRelayer` runs first but does not touch `body`, and the indexing precedes all `RequestKind`-based auth splits (`_authenticate`, hyperbridge-only checks), a message with an empty body reaches the vulnerable line regardless of source authentication.

### Impact Explanation
A crafted PostRequest with an empty `body` delivered to this contract causes `onAccept` to revert via an out-of-bounds panic rather than a clean, typed rejection. Per ISMP/Hyperbridge semantics, a request whose module callback always reverts cannot be successfully delivered — the message is stuck (undeliverable) unless/until it times out, and repeated attempts by a griefer can be used to force relayers to waste gas on reverting deliveries. This matches the "route unable to deliver messages" impact category: a normal user's genuine order/withdrawal message routed to this contract could be starved by interleaved malicious empty-body messages, and more importantly any legitimate relayer/dispatcher path that could produce a zero-length body (e.g. a misbehaving or bugged upstream encoder) bricks message processing with an unhandled panic instead of a graceful error.

### Likelihood Explanation
Likelihood is high for a griefing/DoS scenario: constructing an ISMP `PostRequest` with `body = ""` targeting this contract's address on the destination chain requires only the ability to dispatch a cross-chain POST request from some source chain (no privileged role, no governance, no admin key) — squarely within the "unprivileged token bridger/intent solver/relayer" reachability the scan rules require. The check is missing entirely (not merely under-restrictive), so this is deterministic rather than probabilistic.

### Recommendation
Add an explicit length check before indexing, mirroring the pattern already used elsewhere in the codebase (e.g. `require(body.length > 0)` or a `revert InvalidBody()`), so that empty or truncated bodies are rejected with a typed error instead of panicking:
```solidity
if (incoming.request.body.length == 0) revert InvalidBody();
RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
```
This is consistent with the defensive-decoding pattern already applied elsewhere in this codebase (e.g. the RLP/SCALE decoders in `modules/trees/ethereum/src/node_codec.rs` and `modules/consensus/pharos/primitives/src/spv.rs`, which were hardened against exactly this class of unchecked-index panic) [2](#0-1) [3](#0-2) .

### Proof of Concept
1. On the source state machine, dispatch (or have a malicious/misbehaving counterpart dispatch) a `PostRequest` whose `dest` is the `ExtrinsicIntents` contract address and whose `body` is the empty byte string `""`.
2. Hyperbridge relays and the destination `IsmpHost` calls `ExtrinsicIntents.onAccept(incoming)` with `incoming.request.body.length == 0`.
3. Execution reaches `RequestKind kind = RequestKind(uint8(incoming.request.body[0]));` at [1](#0-0)  and reverts with `Panic(0x32)` (array out-of-bounds) instead of a typed/handled error, causing the message delivery to fail unconditionally.
