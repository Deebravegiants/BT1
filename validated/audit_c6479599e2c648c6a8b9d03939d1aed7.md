### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate(request)`. However, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `process` and forwarded to the app's handler are read directly from unauthenticated HTTP headers via `shopify_header`. Because the app's `client_secret` (`api_secret_key`) is shared across every shop that installs the app, any shop owner (an unprivileged internet user who installs the app in their own store) can obtain a body/HMAC pair that is valid for that shared secret, then replay it directly to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header claiming to be a different shop. ### Finding Description
The intended identity binding is: `shop` (and `topic`) delivered to the handler == `shop` (and `topic`) that Shopify actually cryptographically attested to. The HMAC is meant to authenticate the entire webhook delivery — that a specific event, for a specific shop, was genuinely emitted by Shopify for this app.

In this gem, that binding is broken: `hmac` covers `@raw_body` only, per `to_signable_string`:
```ruby
def to_signable_string
  @raw_body
end
```
`shop`, `topic`, `webhook_id`, `api_version` are pulled from headers with no cryptographic tie to the signed body:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```
`Registry.process` validates only the body/HMAC pair, then unconditionally forwards the attacker-controllable header values into `WebhookMetadata` and the app's handler:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
`api_secret_key` is the app's single shared secret across all installing shops (not a per-shop secret) — the same key used in `HmacValidator.validate` for every tenant. Consequently, an attacker who installs the target app on their own (attacker-owned) shop can:
1. Trigger any webhook topic in their own shop to receive a legitimately-signed `(raw_body, hmac)` pair from Shopify — the attacker fully controls the JSON body content (e.g., custom `note` fields, metafields, or other webhook payload fields) for their own shop's resources.
2. Replay that exact raw body and HMAC directly to the app's public webhook endpoint URL, substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain (and/or spoofing the `topic`/`webhook_id`).
3. `HmacValidator.validate` succeeds because it never checks the header values, only `raw_body` against the shared secret.
4. The app's handler receives `WebhookMetadata` claiming the event came from the victim shop, when the body content is entirely attacker-authored.

This is the exact same class of failure as the referenced report: an identity field ("shop") acted upon by downstream authorization/business logic is not covered by the integrity check that gates the operation, letting the attacker substitute the identity while keeping the cryptographic check green.

### Impact Explanation
This enables cross-tenant confusion/attack in any multi-tenant app built on this gem's documented pattern (`docs/usage/webhooks.md`), where handlers key business logic, database writes, or session/token lookups off `data.shop`. An attacker with only unprivileged access to install the app on their own store can cause the app to process attacker-authored webhook content attributed to an arbitrary victim shop (any myshopify.com domain string, not limited to installed shops), potentially corrupting the victim's stored data, triggering unintended actions against the victim's Shopify data using the app's stored session/access token for that shop, or being used to inject false data/records (e.g., forged `customers/redact` or `orders/create` payloads) into the victim's tenant records. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires no privileged credentials, no access token, and no interaction with the victim — only self-service installation of the target app (a normal, unprivileged action for any Shopify merchant/developer) plus direct HTTP requests to the app's public webhook URL, which is typically discoverable/predictable (e.g., `/webhooks`, `/callback/orders/create` as shown in the gem's own docs). This is fully exploitable by any internet user able to install a public app.

### Recommendation
Bind the shop/topic identity to the cryptographic check: either (a) include `shop`, `topic`, and `webhook_id` in the HMAC signable string / verify them against a per-request expected value derived from a trusted source, or (b) require callers to independently verify that `request.shop` matches a shop for which the app holds a session before trusting `WebhookMetadata#shop`, and document this requirement prominently since the gem currently implies the header value is trustworthy once `HmacValidator.validate` passes.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, registering a webhook handler for `orders/create`.
2. Attacker triggers an order creation in their own shop with attacker-chosen values in fields forwarded by the webhook (e.g., `note`, custom line item properties).
3. Shopify delivers the webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` computed over the raw body using the app's shared `api_secret_key`, and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
4. Attacker captures this exact `raw_body` + `hmac` value, then sends a new HTTP POST directly to the app's public webhook endpoint with the same body/HMAC but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-computes HMAC over `raw_body`.
6. The app's handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, causing the application to treat attacker-authored content as authentic data from the victim shop.

          received_signature = verifiable_query.hmac
