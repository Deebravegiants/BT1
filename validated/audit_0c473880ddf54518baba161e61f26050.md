### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for an incoming webhook from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. The shop-domain header is never part of the signed material, so the binding "HMAC-authenticated request == request acting on shop X" does not hold.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while the shop used to route/attribute the webhook is read straight from the (unauthenticated) header: [2](#0-1) 

Validation is performed with `Utils::HmacValidator.validate`, which calls `to_signable_string` on the `VerifiableQuery` and compares it against the `hmac` header using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` trusts this validation and then dispatches the handler using `request.shop` as the tenant identifier, without any secondary check that the shop matches the one the HMAC/body was actually issued for: [4](#0-3) 

This breaks the intended identity binding: **HMAC-valid(body) == body genuinely destined for shop-domain header value**. In reality, HMAC-valid(body) only proves the body bytes were signed by Shopify for *some* delivery — it says nothing about which shop that delivery was for, because `shop` is not part of `to_signable_string`.

Contrast this with the OAuth callback flow, where `shop` **is** included in the signed payload: [5](#0-4) 

The webhook path lacks the equivalent binding.

### Impact Explanation
An attacker who is a legitimate merchant/user of the host application (i.e., they install the app on their own shop and thus legitimately receive genuine Shopify webhooks — no `api_secret_key`, access token, or privileged account required) can capture one valid `(raw_body, hmac)` pair addressed to their own shop. Because `shop-domain` is excluded from the signed content, the attacker can replay the exact same body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (body unchanged), and `Registry.process` will invoke the registered handler with `WebhookMetadata` attributing the event to the victim shop. Any host application logic keyed off `data.shop` (e.g., GDPR `shop/redact`/`customers/redact` processing, per-shop data mutation, cache/state keyed by shop) will act on/for a shop the attacker does not own — a cross-tenant identity binding bypass. This matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Moderate-to-high: exploitation requires an attacker to have received at least one genuine webhook of a chosen topic to their own shop (trivial — anyone can install a public app or trigger topics like `app/uninstalled`, `orders/create`, etc. on their own store), then replay it with a forged header to the app's public webhook endpoint. No secret material, TLS interception, or social engineering is required — only the ability to send an unauthenticated HTTP POST with attacker-chosen headers, which satisfies the "unprivileged internet user" threat model.

### Recommendation
Include the `shop-domain` header value in the HMAC-signed material verification, or, at minimum, require the host application to independently verify that `request.shop` corresponds to a shop with an active installation/session before trusting it in `WebhookMetadata`. A minimal fix is to make `Webhooks::Request#to_signable_string` (or a companion validation step) bind the shop header, e.g. verify the shop against a separately-tracked, per-installation mapping rather than trusting the header verbatim, since HMAC coverage over the raw body alone cannot be extended without breaking Shopify's fixed webhook signing scheme — so the mitigation must happen at the `Registry.process` level (or documented as a mandatory caller responsibility) by cross-checking `request.shop` against known/installed shops before dispatch.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook topic the app registers for (e.g., `app/uninstalled`), capturing the genuine request: body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker sends a new POST to the app's public webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`= B`) — this matches `H`, so validation passes: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata` whose `shop` is `victim-shop.myshopify.com`, even though the payload/HMAC were never issued for that shop.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
