### Title
Zap sells permanently DoS'd when BounceTech (RESTRICTED admin) drains or halts replenishment of the LT's idle USDC redemption buffer, with no fallback queue - (File: packages/contracts/src/Zap.sol)

### Summary
`Zap._sellInternal` exits every curve/post-graduation sell through a single, atomic `IBounceLeveragedToken.redeem()` call gated by the LT's `baseAssetBalance()` (its idle USDC buffer). There is no `prepareRedeem`/queue fallback. This is the same shape as the FRAX `SFrxETHAdapter` bug: withdrawal is entirely dependent on a RESTRICTED external admin keeping a redemption resource funded, and if that admin drains or stops replenishing it, users' only exit path reverts with no recourse.

### Finding Description
`Zap._sellInternal` redeems the LT for USDC atomically and unconditionally: [1](#0-0) 

The team's own documentation acknowledges this dependency and frames the risk as temporary because "BounceTech automation replenishes the buffer in ~10s after each redeem": [2](#0-1) 

and [3](#0-2) 

Per contest rules, the admins/automation of integrated external protocols like BounceTech are RESTRICTED — any admin action (or a halt of the "automation" the design leans on) that harms Napier-style protocols/users is in scope, exactly as in the FRAX `recoverEther` report. If BounceTech's admin/keeper stops replenishing `baseAssetBalance()` (or an admin-only sweep function drains it, analogous to FRAX's `recoverEther`), every `Zap.sell` for that LT reverts inside `redeem()`. Since `Zap` implements **no** fallback queue (`prepareRedeem` is explicitly not implemented), affected users have no on-chain path to convert their held Token/LT back to USDC through the protocol — mirroring the FRAX case where `burnRedemptionTicketNft` reverts once the admin drains the redemption queue's ETH.

Unlike the LT-retirement case documented at `contracts-scope.md` line 77 — where the code explicitly reasons "holders can always exit via redeem, so no funds are stranded" — this scenario removes exactly that redeem exit, and the design has no secondary mechanism to fall back on.

### Impact Explanation
If BounceTech's off-chain automation or admin action causes the idle USDC buffer to stay empty, holders of the associated Token/LT are unable to sell through `Zap` — their funds are frozen in the affected pair/LT for as long as the external admin's action/inaction persists, with no in-protocol remedy (no queue, no partial-redemption retry mechanism beyond hoping the buffer refills). This satisfies the "permanent freezing of trader/creator/LP funds" bar the contest treats as Medium, matching the judged severity of the source FRAX report.

### Likelihood Explanation
The team's own comments show they are aware this dependency exists but assume the 10-second auto-replenishment always holds; they made no allowance for the RESTRICTED admin/automation failing or acting adversarially, which is precisely the condition the audit's admin-trust rules ask reviewers to consider. No exploit is required — this triggers passively any time BounceTech's off-chain process is disrupted or an on-chain admin action (analogous to `recoverEther`) removes the buffer.

### Recommendation
Add a fallback withdrawal path in `Zap` (e.g., support BounceTech's two-step `prepareRedeem`/claim queue if one exists, or an escrow/IOU mechanism) so that sells can still be settled once the LT's buffer is eventually replenished, rather than depending solely on the atomic `redeem()` call succeeding on every attempt. At minimum, document this as an accepted risk with a contingency plan, consistent with the Sherlock judgment on the analogous FRAX finding.

### Proof of Concept
1. A trader buys `Token` via `Zap.buy`, minting LT held by the `Pair`/`Zap` flow as backing.
2. BounceTech's admin/automation stops topping up (or drains) the LT's idle USDC buffer, so `baseAssetBalance()` == 0 (or too low) for the LT.
3. Trader calls `Zap.sell(tokenAddress, tokenAmount, minUsdcOut)`; `_sellInternal` sells on the curve/HyperSwap to receive LT, then calls `IBounceLeveragedToken(lt).redeem(address(this), ltReceived, 0)` at `packages/contracts/src/Zap.sol:452`, which reverts because BounceTech's `redeem` "Reverts if the computed USDC output exceeds `baseAssetBalance()`" (see `packages/contracts/src/interfaces/IBounceLeveragedToken.sol:18`).
4. Every subsequent sell attempt reverts identically for as long as the admin/automation withholds the buffer; `Zap` has no alternate redemption path, so the trader cannot exit to USDC.
