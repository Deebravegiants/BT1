### Title
Webhook tenant identity (`shop`) is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, then immediately trusts `request.shop` (from the `X-Shopify-Shop-Domain` header) to build `WebhookMetadata` and dispatch it to the app's handler. The HMAC, however, is computed only over the raw request body, never over the `shop-domain`, `topic`, `api-version`, or `webhook-id` headers. This breaks the intended binding "HMAC-authenticated request == shop attributed to the request," since the shop identity is parsed from unauthenticated bytes.

### Finding Description
`Registry.process` performs authentication like this:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [2](#0-1) 

`Utils::HmacValidator.validate` calls `validate_signature`, which computes the HMAC over `verifiable_query.to_signable_string`: [3](#0-2) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers without any cryptographic binding to that body:

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
``` [4](#0-3) 

Consequently, `validate_signature` verifies "this HMAC matches this body under our secret," but it never verifies "this HMAC/body was generated for this particular shop." Any HTTP client that can produce (or replay) *one* valid `(raw_body, hmac)` pair — e.g., an attacker who runs their own store and receives genuine webhook deliveries for it — can resend that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a different, victim shop. `HmacValidator.validate` still returns `true` because it never looks at the header, so `Registry.process` proceeds to call the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

This is precisely the class of bug flagged by the external report: a field that is *acted on* (`shop`, used to route/attribute the event to a tenant) is not covered by the authentication primitive (`HMAC` over `raw_body` only). The equality the code implicitly assumes is:
`hmac_valid(raw_body) == shop_header_is_authentic`
but the actual guarantee is only `hmac_valid(raw_body) == raw_body_is_authentic_for_some_shop`, so the equality is false whenever the header and body are decoupled by an attacker.

### Impact Explanation
This allows a "cross-tenant" event injection: an unprivileged internet user who has visibility into any single valid `(body, hmac)` pair for one shop (trivially their own store, since webhooks for many topics have fixed or predictable minimal bodies, e.g., `{}` for `app/uninstalled`, or by simply installing/uninstalling the app in their own dev store to harvest a legitimately signed payload) can forge a webhook request that the library will report as "HMAC verified" for an arbitrary victim `shop` domain. Depending on how the host application wires webhook handling (e.g., acting on `app/uninstalled` to purge merchant data, disable a shop, or revoke access), this can cause unauthorized cross-tenant state changes attributed to a shop the attacker does not control, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likely and practical: no access token, `api_secret_key`, or privileged account is required. An attacker only needs their own store to receive a single legitimate webhook (which they are fully entitled to receive, e.g. by installing the merchant's own test app or the target app itself in a store they control), then replay the exact bytes with a modified `shop-domain` header to the app's public webhook endpoint. The gem performs no defense against this because `to_signable_string` intentionally/accidentally omits headers from the signed material.

### Recommendation
Bind the tenant-identifying header into the HMAC verification, or otherwise cryptographically tie `shop`, `topic`, `webhook_id`, and `api_version` to the signed payload. At minimum, `Webhooks::Request#to_signable_string` (or the validation call site in `Registry.process`) should incorporate the `shop-domain` (and ideally `topic`/`webhook-id`) into the signable string, or the caller should independently confirm that the `shop` header corresponds to a session/shop the app has actually installed with a token obtained via the app's own OAuth flow before trusting `WebhookMetadata#shop` for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the vulnerable app (or any app using this gem) in their own store `attacker.myshopify.com`, and receives a real webhook delivery for topic `app/uninstalled` with body `{}` and a valid `X-Shopify-Hmac-Sha256` header, e.g. as constructed in [5](#0-4) .
2. Attacker resends the exact same raw body and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` [6](#0-5) , which succeeds because it only checks the body against the secret, per `to_signable_string` returning `@raw_body` [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the host application to perform shop-scoped logic (e.g., data deletion/deauthorization for `app/uninstalled`) against the victim tenant, despite the attacker never having accessed the victim's credentials.
