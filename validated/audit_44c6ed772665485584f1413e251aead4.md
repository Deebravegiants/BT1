### Title
Unauthenticated NULL Pointer Dereference (Node Crash) via Missing `params` in Vault `public_key_get` Gateway Message — (`File: core/capabilities/vault/gw_handler.go`)

### Summary
The node-side vault gateway handler dereferences `req.Params` without a nil check when handling the `MethodPublicKeyGet` JSON-RPC method, unlike every other vault method which is routed through `GatewayVaultRequestProcessor` and explicitly nil-checked. This mirrors the CVE-2021-33442 bug class: a malformed/incomplete external message reaching a JSON-value dereference path that assumes a non-nil pointer, causing a crash (`SIGSEGV`/panic) on NULL pointer dereference.

### Finding Description
In `core/capabilities/vault/gw_handler.go`, `HandleGatewayMessage` dispatches based on `req.Method`: [1](#0-0) 

For `MethodSecretsCreate/Update/Delete/List`, requests are routed through `h.requestProcessor.ProcessRequest`, whose per-method handlers in `gateway_vault_request_processor.go` explicitly validate `req.Params == nil` before ever dereferencing it: [2](#0-1) 

However, `MethodPublicKeyGet` bypasses `ProcessRequest` entirely and goes straight to `handlePublicKeyGet`, which unmarshals `*req.Params` with no nil guard: [3](#0-2) 

If `req.Params` is `nil`, `*req.Params` is a dereference of a nil `*json.RawMessage`, which panics with a nil pointer dereference — the direct analog of `json_printf()` dereferencing a NULL pointer in the CVE.

This request originates from an unprivileged, unauthenticated external client. The public-facing gateway handler `core/services/gateway/handlers/vault/handler.go` explicitly special-cases `MethodPublicKeyGet` as not requiring authorization ("Public key requests don't require authorization") and forwards the request (including a potentially nil/absent `Params`, since JSON-RPC 2.0 `params` is an optional field) straight to the DON member nodes: [4](#0-3) 

Those forwarded requests are read by each node's connector `readLoop`, decoded via `json.Unmarshal` into `jsonrpc.Request[json.RawMessage]`, and dispatched straight into `HandleGatewayMessage`: [5](#0-4) 

Nothing in this path guarantees `Params` is non-nil for `public_key_get` — the gateway does not require or validate the presence of `params` for this method before relaying it to nodes.

### Impact Explanation
An unauthenticated external actor who can submit a request to the public gateway HTTP API for the vault DON can send a `public_key_get` JSON-RPC message with `params` omitted (or explicitly `null`). This causes `handlePublicKeyGet` on every receiving Chainlink node to dereference a nil pointer and panic when handling the forwarded gateway message, crashing (or at minimum disrupting) the node process/goroutine handling gateway messages — a Denial-of-Service against the vault-capable node fleet, achievable without any authentication or allowlisting, matching the "unprivileged-actor" and "internet-facing gateway (handlers)" analog criteria.

### Likelihood Explanation
High: the `public_key_get` method is explicitly documented in code as not requiring authorization, and it is trivial for any external client to submit a request through the public gateway endpoint that reaches `handleSingleNodeRequest`/`SendToNode` and thus `HandleGatewayMessage` on the node with `Params == nil`. No cryptographic signature, allowlist membership, or session token is needed to trigger it.

### Recommendation
Add an explicit nil check for `req.Params` in `handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go` (mirroring the checks already present in `gateway_vault_request_processor.go`'s `processCreateSecretsRequest`, `processUpdateSecretsRequest`, etc.), returning a `UserMessageParseError` response instead of dereferencing a nil pointer. Consider unifying `MethodPublicKeyGet` handling through the same validated-params helper used by other vault methods so this class of bug cannot recur for any future method added to the switch in `HandleGatewayMessage`.

### Proof of Concept
1. As an unauthenticated client, submit an HTTP request to the vault gateway's public JSON-RPC endpoint with a JSON-RPC request whose `method` is the vault `public_key_get` method name and whose `params` field is omitted (valid per JSON-RPC 2.0, since `params` is optional).
2. The gateway's `handler.go` `HandleJSONRPCUserMessage` treats `public_key_get` as not requiring authorization and forwards the request (uncached case) to DON member nodes via `SendToNode`.
3. Each receiving node's `gatewayConnector.readLoop` unmarshals the message and calls `GatewayHandler.HandleGatewayMessage`, which routes to `handlePublicKeyGet`.
4. `handlePublicKeyGet` executes `json.Unmarshal(*req.Params, r)` with `req.Params == nil`, causing a nil pointer dereference panic on the node.

Note: I could not fully verify from the indexed code whether the outer `jsonrpc2.DecodeRequest`/gateway codec layer (`core/services/gateway/api` codec, not fully retrieved) enforces `params` non-nullness for all methods before reaching the vault handler; if such a generic guard exists upstream, it would need to be confirmed to fully validate reachability. I recommend a Devin session with full file access to trace `jsonrpc2.DecodeRequest` and `codec.DecodeJSONRequest` to close this gap definitively, given index size limits may have truncated some of that package's contents.
