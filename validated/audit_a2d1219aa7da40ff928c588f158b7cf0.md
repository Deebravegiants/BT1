### Title
DirectBridge's storage-deposit cache key collision lets one withdrawal's cached result be served for a different (token, account) pair - ([File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts])

### Summary
`DirectBridge.getCachedStorageDepositValue` builds its LRU cache key by naively concatenating `contractId` and `accountId` with no delimiter (`` `${contractId}${accountId}` ``). Because both values are attacker-influenced strings (the NEP-141 token id and the NEAR destination account), two different `(contractId, accountId)` pairs can produce an identical cache key, causing the cached storage-balance result for one pair to be returned for a completely different pair on a **shared, bridge-instance-wide cache** used by all callers.

### Finding Description
`DirectBridge` maintains a single `storageDepositCache: LRUCache<string, [MinStorageBalance, StorageDepositBalance]>` per bridge instance: [1](#0-0) 

The cache is read/written keyed purely by string concatenation: [2](#0-1) 

`key = `${contractId}${accountId}`` has no separator. This means for two distinct pairs `(contractId_A, accountId_A)` and `(contractId_B, accountId_B)` where `contractId_A + accountId_A === contractId_B + accountId_B` (e.g. `contractId_A = "token.near"`, `accountId_A = "sub.alice.near"` vs `contractId_B = "token.nearsub.alice.near"`... more realistically any split point along the concatenated string can be produced by choosing a different, but still valid, NEP-141 asset whose contract id is a prefix/suffix boundary match with another account id), the second lookup returns the first caller's cached `[minStorageBalance, userStorageBalance]` tuple instead of performing a fresh RPC lookup for the real target account.

This value directly feeds `estimateWithdrawalFee`, which is the sole place that decides whether a NEAR storage-deposit fee must be added to the withdrawal: [3](#0-2) 

If a poisoned/cached tuple erroneously reports `minStorageBalance <= userStorageBalance` (i.e. "already funded, no fee needed") for a victim's real `(contractId, destinationAddress)` pair that in fact lacks sufficient storage balance, `estimateWithdrawalFee` returns `feeAmount = 0n` and skips the storage-deposit fee that should have been included in the withdrawal intent (`createWithdrawIntentPrimitive` -> `storageDeposit`): [4](#0-3) 

The cache only ever stores "sufficient balance" results (`if (result[1] >= result[0])`), so the only way it gets poisoned is with a false-positive "no fee needed" entry, which is exactly the dangerous direction (under-provisioning storage, not over-provisioning).

This breaks the equality the fee-estimation step is supposed to guarantee: *the storage-deposit fee reported for account X must be derived from account X's actual on-chain storage balance*, not from a different account's cached result that happens to share a concatenated key.

### Impact Explanation
Because `storageDepositCache` is scoped to the `DirectBridge` instance (typically a long-lived singleton shared across all SDK consumers/users in a server process), an unprivileged party can submit an NEP-141 withdrawal request with a crafted `(assetId, destinationAddress)` pair engineered so its concatenation collides with another (past or future) legitimate `(assetId, destinationAddress)` pair. Once their own request populates the cache with a "sufficient" (zero-fee) entry, a subsequent legitimate withdrawal that maps to the same key will skip the required storage deposit intent, even though the real destination account is not registered/funded for storage on that token contract.

The practical consequence is an on-chain NEP-141 `ft_transfer_call`/withdraw execution that fails because `storage_balance_of` on the real destination account is insufficient — the withdrawal intent settles on the intents contract, but the destination-chain (NEAR) leg fails to land, leaving funds in the withdrawal pipeline until manual intervention/replay with a corrected amount. This matches the "stuck withdrawal until manual intervention" / fee miscalculation category described as High impact.

### Likelihood Explanation
Exploitability requires: (1) the attacker to control both `assetId` (in practice limited to real, supported NEP-141 tokens routed via `DirectBridge`, i.e. `RouteEnum.NearWithdrawal`) and `destinationAddress` for their own request, and (2) the ability to predict or brute-force a concatenation collision with a target `(contractId, accountId)` pair. Since NEAR account ids and NEP-141 contract ids are ordinary strings with a small, guessable structure (both typically end in `.near`), constructing a colliding pair is a straightforward string-manipulation exercise, not a cryptographic collision — this is a realistic, low-effort attack for anyone who can submit withdrawal requests through the shared SDK/bridge instance (e.g., a public-facing withdrawal service).

### Recommendation
Use a collision-free composite key, e.g. include an explicit delimiter and/or lengths: `` `${contractId.length}:${contractId}:${accountId}` `` or a `JSON.stringify([contractId, accountId])`. Apply the same fix pattern to any other cache keys built via bare string concatenation in the bridges (audit `getCachedDestinationTokenAddress`, `getCachedTokenDecimals`, `getCachedSupportedTokens` in `omni-bridge.ts`/`poa-bridge.ts` for the same anti-pattern, even though only the `DirectBridge` storage-deposit cache was confirmed vulnerable here).

### Proof of Concept
1. Attacker calls `estimateWithdrawalFee`/`validateWithdrawal` on `DirectBridge` with `assetId` resolving to `contractId = "token.near"` and `destinationAddress = "sub.victim.near"` such that the concatenation `"token.nearsub.victim.near"` is engineered to equal a victim's real pair's concatenation, e.g. victim's real pair is `contractId = "token.nearsub.victim.near"`-prefixed differently (attacker picks any supported token contract id `T` and any destination account id `D` under their control such that `T + D` textually equals `contractId_victim + accountId_victim`).
2. Because the attacker's own account (`D`) is funded with sufficient NEP-141 storage balance for token `T`, `getCachedStorageDepositValue` computes `result[1] >= result[0]` and caches `(key, result)` under the collided key.
3. Victim later withdraws `contractId_victim` token to `accountId_victim`, which is *not* storage-registered. `getCachedStorageDepositValue` computes the same collided key, finds the attacker's cached "sufficient" tuple, and returns it — `estimateWithdrawalFee` reports `feeAmount = 0n`, and `createWithdrawalIntents` omits the storage deposit.
4. The resulting withdrawal intent settles on `intents.near` but the destination NEP-141 `ft_transfer`/withdraw call on NEAR fails due to missing storage registration, leaving the victim's withdrawal stuck.

*Note: I was not able to fully verify the exact character-level string needed to force a collision against a specific real-world token contract id without executing code; this PoC describes the mechanism and required conditions rather than a concrete collision string, since that depends on runtime-supported token contract id values not enumerable from the indexed source alone.*

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
	}
