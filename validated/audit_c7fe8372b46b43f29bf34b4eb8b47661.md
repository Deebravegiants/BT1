### Stale cached spoke config lets a flash-position callback bypass a freshly executed governance risk change - (File: contracts/controller/src/strategies/flash_position.rs)

### Summary

`process_flash_position` caches spoke asset risk configuration before it invokes the user-selected flash receiver. That receiver can execute a ready governance operation that changes the collateral’s spoke listing. When control returns, the controller continues using the stale `Context::spoke_assets` entry for entry checks, position stamping, and final solvency evaluation.

### Finding Description

`Context::cached_spoke_asset` loads a `SpokeAssetConfig` once and returns the cached value for the rest of the invocation. [1](#0-0) 

`process_flash_position` calls `validate_collaterals`, which reaches `require_can_supply` and caches each collateral’s spoke config, before invoking `execute_flash_position` on an attacker-selected receiver. [2](#0-1) 

The callback can execute a ready governance operation such as `EditAssetInSpoke`, lowering the collateral’s LTV or liquidation threshold. Afterward:

- `process_deposit` obtains the stale cached `AssetConfig`.
- `get_or_create_supply_position` stamps that obsolete config into the new position.
- `strategy_finalize` uses `enforce_post_pool_solvency`, which again reads the stale cached listing through `restamp_listed_supply_ltv`. [3](#0-2) [4](#0-3) 

This is the same bug class as the advisory: an accessor continues returning a value tied to stale backing state after that backing state has changed.

### Impact Explanation

An attacker can open leveraged debt against collateral stamped with obsolete, more favorable LTV/liquidation parameters after governance has already tightened those parameters. The final solvency check values the account using the stale stamp, so a position that should be rejected can persist.

If the tightened listing reflects current risk, the position can be left undercollateralized or immediately liquidatable with terms more favorable than intended. Repeated or large positions can produce protocol bad debt and insolvency.

### Likelihood Explanation

The path is permissionless once a suitable governance operation is ready:

1. Attacker calls `flash_position` with a receiver contract they control.
2. During `execute_flash_position`, the receiver calls governance `execute` for the ready `EditAssetInSpoke` operation.
3. The callback returns normally.
4. The controller completes collateral deposit and finalization using the stale config.

The flash receiver is explicitly caller-selected, and the callback occurs inside `with_flash_guard`. [5](#0-4) 

The exploit depends on governance having already created and matured the tightening operation, but executing that operation is an allowed unprivileged path. No leaked key or privileged attacker is required.

### Recommendation

Invalidate or refresh mutable spoke state after external callbacks.

At minimum:

- Clear `Context::spoke_assets` and `Context::spoke_config` after `invoke_receiver` returns.
- Re-run collateral listing and flag checks before `process_deposit`.
- Ensure `restamp_listed_supply_ltv` reads post-callback storage rather than pre-callback cached config.
- Add a regression test where `execute_flash_position` executes a ready `EditAssetInSpoke` tightening and assert that the new listing governs the resulting position.

/// Refreshes stored LTV snapshots in memory for listed supply assets, skipping
/// unlisted assets. Returns whether any position changed.
pub(crate) fn restamp_listed_supply_ltv(cache: &mut Context, account: &mut Account) -> bool {
    let mut changed = false;
    let keys = account.supply_positions.keys();
    for hub_asset in keys.iter() {
        let Some(listed) = cache.cached_spoke_asset(account.spoke_id, &hub_asset) else {
            continue;
        };
        let config: AssetConfig = (&listed).into();
        let Some(raw) = account.supply_positions.get(hub_asset.clone()) else {
            continue;
        };
        let mut position = AccountPosition::from(&raw);
        if position.loan_to_value.raw() == config.loan_to_value.raw() {
            continue;
        }
        position.loan_to_value = config.loan_to_value;
        update_or_remove_supply_position(account, &hub_asset, &position);
        changed = true;
    }
    changed
}
