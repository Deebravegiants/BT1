### Title
Unchecked arithmetic panics in `calc_take_pnl` permanently brick Deposit/Withdraw once pool balances reach overflow-inducing magnitudes - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` and the surrounding Deposit/Withdraw logic use `.checked_mul()/.checked_add()/.checked_sub().unwrap()` instead of returning a graceful program error. Because `calc_take_pnl` is invoked on every `Deposit`, `Withdraw`, and `WithdrawPnl` instruction, a pool whose vault balances (fully attacker-controlled via `Initialize2` + custom SPL mints, or via direct token "donation" transfers straight to the vault accounts) reach the magnitude that overflows the internal `u128` product will panic on every future call to these instructions, permanently freezing the pool's liquidity.

### Finding Description
`calc_take_pnl` computes:
```rust
let pool_pc_amount = U128::from(*total_pc_without_take_pnl);
let pool_coin_amount = U128::from(*total_coin_without_take_pnl);
if pool_pc_amount.checked_mul(pool_coin_amount).unwrap()
    >= (calc_pc_amount).checked_mul(calc_coin_amount).unwrap()
``` [1](#0-0) 
`total_pc_without_take_pnl`/`total_coin_without_take_pnl` are derived directly from the live SPL token vault balances via `calc_total_without_take_pnl_no_orderbook`: [2](#0-1) 
Both values are `u64` (SPL token amount is `u64`), and their `U128` product can reach up to `~1.8e19 * 1.8e19 ≈ 3.4e38`, essentially the ceiling of `u128::MAX` (`~3.4e38`). If both vault balances are pushed close to `u64::MAX` (achievable by an unprivileged pool creator who mints two custom SPL tokens with near-maximum raw supply and deposits them into a freshly created pool via `Initialize2`, or by anyone directly transferring tokens into the vault accounts — vaults are ordinary SPL token accounts with no restriction on who can send tokens to them), `checked_mul` returns `None` and `.unwrap()` panics.

The same function chains additional `.unwrap()`s on `checked_sub`/`checked_add`/`checked_mul`/`checked_div` for `x2_power`, `diff_x`, `diff_y`, `delta_x`, `delta_y`, `need_take_pnl_pc/coin` updates: [3](#0-2) 
Because `calc_take_pnl` is called unconditionally inside `process_deposit`, `process_withdraw`, and `process_withdrawpnl`: [4](#0-3) [5](#0-4) 
once the vault state (which persists on-chain) satisfies the overflow condition, every subsequent Deposit/Withdraw/WithdrawPnl transaction against that pool will hit the same `.unwrap()` panic and abort — there is no way to reduce the vault balances back down using instructions that don't themselves hit this code path, so the failure is permanent for that pool.

### Impact Explanation
This is analogous to the reported bug class: attacker-controlled input drives an arithmetic overflow through an assertion/`unwrap()`-based check instead of a validated error path, aborting execution. On-chain, this does not crash a validator, but it permanently disables `Deposit` and `Withdraw` for the affected pool once the overflow condition is reached, since both instructions unconditionally execute `calc_take_pnl`. Any liquidity already deposited by the pool creator or other LPs before the vault balances cross the overflow threshold becomes permanently locked — a **permanent freezing of LP funds**, which is an accepted High-impact outcome under the review scope.

### Likelihood Explanation
Reaching balances near `u64::MAX` for both vault token accounts requires an attacker/pool-creator to control (or acquire) an SPL mint with sufficiently large raw supply and to deposit/transfer large amounts into a pool they create via `Initialize2`. This is entirely within reach of an unprivileged pool creator (SPL mints allow up to `u64::MAX` raw supply, and many high-decimal/meme tokens on Solana already have supplies in this range), so likelihood is non-trivial though it requires a specific extreme token/pool configuration rather than a generic swap.

### Recommendation
Replace the `.unwrap()` calls in `calc_take_pnl` (and related `checked_*` chains in `process_deposit`/`process_withdraw`) with `.ok_or(AmmError::...)?` so overflow conditions return a program error instead of panicking, and consider bounding acceptable vault balances / normalized values before performing `u128` multiplications, mirroring the `U256`-based approach already used in `Calculator::calc_x_power` for the same class of computation. [6](#0-5) 

### Proof of Concept
1. As an unprivileged user, create two new SPL token mints and mint raw supply close to `u64::MAX` for each.
2. Call `Initialize2` to create a new Raydium AMM pool using these two mints, depositing large enough amounts into the coin/pc vaults such that `pool_pc_amount * pool_coin_amount` (as computed in `calc_take_pnl`) exceeds `u128::MAX`.
3. Call `Deposit` (or `Withdraw`/`WithdrawPnl`) on this pool: `calc_take_pnl` executes `pool_pc_amount.checked_mul(pool_coin_amount).unwrap()` at processor.rs:190, which returns `None` and panics, aborting the transaction.
4. Because the vault balances that caused the overflow persist on-chain, every subsequent `Deposit`/`Withdraw`/`WithdrawPnl` call against this pool hits the identical panic, permanently freezing any LP tokens already minted for the pool.

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
