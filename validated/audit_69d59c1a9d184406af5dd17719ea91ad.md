### Title
Unguarded external token call before escrow-accounting write in `withdraw()` allows reentrant over-drain of escrow — ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements its own `withdraw()` function with a checks-effects-interactions ordering that is inverted relative to the canonical EVM implementation. It performs the external, attacker-influenced token transfer *before* writing back the authoritative escrow-accounting state, and the entry points that reach it (`onAccept` for `RedeemEscrow`/`RefundEscrow`, `onGetResponse`) are not reentrancy-guarded. This is the same bug class as CVE-2019-5736 at its core: an operation resolves and acts on a mutable resource (the escrow ledger for a token address that is fully attacker-chosen at order placement) but only commits the authoritative state change *after* handing control to that resource, leaving a window where the check ("is anything escrowed") is stale relative to the write that is supposed to make it safe.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` (lines 691–730) does: [1](#0-0) 

```
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        ...
```

The check is only `_orders[...][token] == 0` (nonzero), not "is `amount` available." The external call — to `token`, an address fully controlled by whoever placed the order (`order.inputs[i].token` is user-supplied at `placeOrder`) — happens first, and the accounting decrement `_orders[body.commitment][token] -= amount` happens only afterward. Neither `withdraw()` nor its callers (`onAccept` for `RedeemEscrow`/`RefundEscrow`, and `onGetResponse`) use a reentrancy guard, confirmed by the absence of any `nonReentrant`/`ReentrancyGuard` usage in this file: [2](#0-1) [3](#0-2) 

Contrast with the canonical EVM implementation of the same routine in `IntentsBase.sol`, which decrements the escrow *before* the external transfer — correct CEI ordering: [4](#0-3) 

```
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```

The Tron fork reintroduces the vulnerable ordering that the main contract already avoids.

### Impact Explanation
Because `order.inputs[i].token` can be any address the order placer chooses, an attacker can place an order whose escrowed "token" is a malicious contract implementing `transfer()` with a callback (e.g. a TRC20/hook-style token, or a contract that performs an arbitrary re-entrant call inside `transfer`). When a solver fills the order and the destination side later dispatches a `RedeemEscrow`/`RefundEscrow` message back to this contract, `withdraw()` calls into the attacker's `token.transfer()` while `_orders[commitment][token]` still reflects the pre-withdrawal (undecremented) escrow balance. If the malicious token's `transfer` re-enters any reachable external function that can trigger another `withdraw()` (or a partial-fill/cancel path sharing the same accounting map) before the first call unwinds and performs its own decrement, the same escrowed balance can be drained more than once — a concrete theft of escrowed funds, matching the "concrete theft ... unbacked mint ... unauthorized app action" bar in the validation criteria.

### Likelihood Explanation
Reaching this path only requires: (1) placing an order whose input token is an attacker-deployed malicious contract — fully permitted, since `order.inputs` is user-supplied and unchecked against any allowlist in `placeOrder`; and (2) having that order legitimately filled and settled through the normal cross-chain `RedeemEscrow`/`RefundEscrow`/GET-response flow, which any solver or the user's own cancellation path can trigger. No privileged role, governance action, or off-protocol compromise is needed — a single attacker-controlled token address dispatched through the intent flow is sufficient to open the window.

### Recommendation
Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to update `_orders[body.commitment][token]` (and `_filled`/fee accounting) *before* making the external `token.call`/native `.call`, mirroring `IntentsBase._withdraw`. Additionally, add a reentrancy guard to `onAccept`/`onGetResponse` (or `withdraw` itself) for defense in depth, and strengthen the escrow check from a bare nonzero test to `_orders[body.commitment][token] >= amount` before any transfer.

### Proof of Concept
1. Attacker deploys `EvilToken`, whose `transfer(to, amount)` re-enters the gateway (e.g., calling a reachable function that again reaches `withdraw()` for the same `commitment`/`token` pair) before returning.
2. Attacker calls `placeOrder` with `order.inputs = [{token: EvilToken, amount: X}]`, escrowing `X` EvilTokens.
3. Order is filled normally by a solver; the corresponding `RedeemEscrow` (or a self-triggered `RefundEscrow`/GET-response cancel path) reaches `withdraw()`.
4. Inside `withdraw()`, the check `_orders[commitment][EvilToken] == 0` passes (balance is `X`, not yet decremented), and `token.call(transfer(beneficiary, X))` transfers into `EvilToken.transfer`, which re-enters before `_orders[commitment][EvilToken] -= X` executes.
5. The re-entrant call sees the same pre-decrement balance and triggers a second transfer of up to `X` again, effectively withdrawing more than what was escrowed. [1](#0-0)
