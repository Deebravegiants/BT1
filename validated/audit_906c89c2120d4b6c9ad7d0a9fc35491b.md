This confirms the root-cause analysis: the `ShopifyAPI::Webhooks::Request#hmac` HMAC signature is computed only over the raw body via `to_signable_string`, which returns `@raw_body` and nothing else [1](#0-0) . The `shop` field, read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, is never included in the signed material [2](#0-1) . `Registry.process` validates only the HMAC and then trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler [3](#0-2) . The gem's own documentation instructs apps to use `data.shop` directly as the tenant/store identifier for the received webhook [4](#0-3) .

### Title
Webhook `shop` field is not covered by HMAC, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body against the HMAC header, but the `shop` (store) identity is taken from a separate, unsigned header (`shopify-shop-domain` / `x-shopify-shop-domain`). Because the app's `api_secret_key` is the same for every shop that has installed the app, a valid HMAC computed for a webhook delivered to one shop remains valid if the shop-domain header is swapped for a different shop, letting a merchant who has installed the app forge webhooks that `Registry.process` will accept as coming from an arbitrary other shop.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string`, which for a webhook `Request` is defined as just `@raw_body` [5](#0-4) [1](#0-0) . The `shop` accessor reads straight from the `shopify-shop-domain` header without any cryptographic binding to the signature [2](#0-1) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [3](#0-2) . Since the HMAC secret (`api_secret_key`) is a single per-app secret shared across all shops that install the app (not a per-shop secret), any store owner who installs the app can legitimately trigger a real webhook, capture the valid `(raw_body, hmac)` pair from their own shop, and then replay the identical HTTP request to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain. `to_signable_string` and thus the HMAC computation is unaffected by that header change, so `HmacValidator.validate` still returns true, and the forged request is delivered to the app's handler labeled as originating from the victim shop.

This breaks the identity binding: `shop authenticated == shop stored/acted upon` should hold, but here `shop verified by HMAC` (nothing, since shop isn't covered) `!= shop passed to the handler` (attacker-controlled header value).

### Impact Explanation
Any host application that follows the gem's documented pattern of using `WebhookMetadata#shop` to key its per-tenant data (as shown in the gem's own docs example: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to attribute an attacker's own webhook payload to a different, victim tenant/shop. This is a cross-tenant access primitive: a merchant who installed the app can inject data (e.g., fake `orders/create`, `app/uninstalled`, `customers/data_request`, etc.) that the app processes as if it belonged to another merchant's store, potentially corrupting or leaking that victim's data, triggering unintended actions (e.g., a forged `app/uninstalled` for a victim shop causing the app to purge that victim's data), or bypassing tenant isolation checks that rely on `data.shop`.

### Likelihood Explanation
The attacker only needs to be a legitimate but unprivileged install of the app on their own store (which is essentially free/unprivileged to obtain via the Shopify App Store or a dev store) to capture a genuinely-signed `(body, hmac)` pair, then can replay it with a forged `shop-domain` header directly to the app's public webhook callback URL. No access token, `api_secret_key`, or privileged credentials are required — only observation of one legitimate webhook delivery to their own shop and the ability to send an HTTP POST to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the verified material. Either:
- Include the shop domain (and ideally topic) in the HMAC-signed payload verification (Shopify webhooks don't sign headers, but the library should require the app to independently confirm that `shop` belongs to a shop with an active, stored session/installation before trusting `data.shop`), or
- Update `Registry.process`/docs to explicitly warn that `data.shop` is unauthenticated and must be cross-checked against the app's own installation/session store (e.g., verify a session exists for that shop before acting on webhook data attributed to it), rather than trusted at face value.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and registers a webhook handler for `orders/create`.
2. Shopify sends a legitimate webhook to the app for `attacker-shop.myshopify.com`:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, body `B`.
3. Attacker replays the exact same request to the app's public callback endpoint, changing only the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`, same `x-shopify-hmac-sha256`, same body `B`.
4. `Utils::HmacValidator.validate` recomputes the HMAC using only `to_signable_string` (the raw body `B`), which matches, so validation passes [5](#0-4) .
5. `Registry.process` calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)` [6](#0-5) , and the app processes attacker-controlled data as belonging to `victim-shop.myshopify.com`.
