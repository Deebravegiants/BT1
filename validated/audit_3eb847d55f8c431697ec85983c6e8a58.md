Confirmed critical finding: in `MainEVMCircuit.circom`, the `calldataHash` signal (declared line 52) is never consumed by any constraint in the template — it is not wired into `sigVerifier.signedMessageHash`, not used in the Poseidon hash forming `message` (line 98, which is derived solely from the private `messageSeed`), and not referenced anywhere else in the loop/constraint logic. It exists purely as an unconstrained public input.

### Title
Unconstrained `calldataHash` public signal allows spending-key holder's signature to be detached from transaction calldata (relay/fee/hook/asset fields) - (File: circuits/MainEVMCircuit.circom)

### Summary
`calldataHash` is declared as a circuit public input but is never used inside any circuit constraint, so any value can be supplied for it while still producing a valid proof.

### Finding Description
On-chain, `HinkalHelper.performHinkalChecks` recomputes `getHashedCalldata(circomData)` and requires it to equal `circomData.calldataHash` [1](#0-0) , and this value is fed as a public signal into the Groth16 verifier via `formInputForCircom`/`formBasicInput` (`input[index++] = circomData.calldataHash;`) [2](#0-1) . The protocol's intended security model is that `calldataHash` binds the entire off-chain `CircomData` (including `relay`, `feeStructure`, `hookData`, `externalActionData`, `originalSender`, `emporiumMessage`) to the transaction that the spending-key holder authorized via the EdDSA signature verified inside the circuit (`SignatureVerifier`, using `signedMessageHash`) [3](#0-2) .

However, inspecting `MainEVMCircuit` shows `calldataHash` is declared as `signal input calldataHash;` [4](#0-3)  but is never assigned into any component input, never compared (`===`) against any other signal, and never used in the loop that establishes commitments, nullifiers, or the signed-message hash [5](#0-4) . The `signedMessageHash` fed to `SignatureVerifier` is a raw public input (line 33/95) that circom never derives from `calldataHash`; and `message` (line 62/98) is derived only from the private `messageSeed` via `Poseidon(1)([messageSeed])`, again independent of `calldataHash`.

This breaks the intended equality: the ZK proof's public-input vector includes `calldataHash`, but the circuit imposes zero constraints on it, so it is effectively a dangling/free public signal. Consequently, a valid Groth16 proof generated for one `CircomData` payload (with one `signedMessageHash` computed off-chain from a specific set of `relay`, `feeStructure`, `hookData`, `originalSender`, etc.) can be replayed with `a,b,c` unchanged while the caller substitutes an entirely different `circomData` — as long as the caller recomputes a `calldataHash` value that happens to hash-match their new payload via `getHashedCalldata`. Since `getHashedCalldata` is a plain deterministic keccak256/mod function of the calldata fields (not tied to anything secret) [6](#0-5) , any party (a relay, or any observer of a submitted transaction) can freely choose their own `relay` address, `feeStructure` (rates/fee token/flat fee), `hookData` (arbitrary `preHookContract`/`postHookContract`), or `originalSender`, compute the matching `calldataHash`, and reuse the victim's Groth16 proof — because the circuit never checks that this `calldataHash` is the one the spending-key holder actually intended to sign.

This is the same trust-boundary violation as the "operator implicitly trusted" report: there, the operator (an entity outside the buyer/seller trust boundary) could unilaterally decide outcomes affecting funds because nothing tied the operator's role to a specific, unforgeable, signed transaction. Here, the "relay"/fee/hook fields play the analogous untrusted-operator role, and the unconstrained `calldataHash` signal is the missing binding that should have tied those fields to the signer's authorization — exactly mirroring the missing equality check the report flagged.

### Impact Explanation
This is Critical: it is a proof/public-input soundness bypass at the circuit level. An attacker (e.g., a malicious relay observing a pending or replayable proof) can redirect `relayFee` payouts to themselves via `circomData.relay` in `Hinkal._internalTransact` [7](#0-6) , inflate `feeStructure.variableRate`/`flatFee` to drain more of the withdrawn/refunded funds than the shielded owner authorized, or substitute an arbitrary `hookData.postHookContract` that executes with the transaction's `circomData` and moves tokens after the balance-equality check has already passed (`Hinkal.transact` line 149 calls `postHookContract.afterTransact` after the balance-equation check at lines 92-147, so hook-driven fund movement is not constrained by that equation at all) [8](#0-7) . This directly threatens theft of shielded user funds/relay fees without the shielded owner's authorization — an unauthorized asset movement enabled purely by the fact that the calldata a user "signed" (via the circuit-embedded intent) is not actually bound to the value verified by the SNARK.

### Likelihood Explanation
High likelihood if the observation is confirmed by tracing the exact generated verifier's public-input ordering (out of scope to inspect further here, since `contracts/verifiers/**` is excluded per the rules) to make sure `calldataHash`'s slot in the public-input vector is indeed unused by the R1CS — the circom source strongly indicates it is a free/unconstrained signal, since no constraint operator (`<==`, `===`) ever touches it after declaration. No privileged role, admin key, or relayer/node trust assumption is needed to exploit this — only knowledge of one valid proof and freedom to alter `CircomData`'s non-circuit-checked fields and recompute `calldataHash`.

### Recommendation
Add an explicit constraint inside `MainEVMCircuit` binding `calldataHash` into the signed message actually verified by `SignatureVerifier` (e.g., fold it into `signedMessageHash`'s pre-image, or force `signedMessageHash === Poseidon(...)` including `calldataHash`), so that any change to relay/fee/hook/original-sender data invalidates the existing proof and requires a new signature from the spending-key holder.

### Proof of Concept
1. User (spending-key holder) constructs a shielded withdrawal with `circomData.relay = RelayA`, `feeStructure.flatFee = X`, and generates `signedMessageHash`/`calldataHash` off-chain, then a Groth16 proof `(a,b,c)` for `MainEVMCircuit`.
2. Because `calldataHash` is not constrained in-circuit, attacker (e.g. `RelayB`, or any mempool observer) intercepts the transaction before inclusion, and re-encodes a new `CircomData'` with `relay = RelayB` and/or an inflated `feeStructure.flatFee`, recomputing `calldataHash' = getHashedCalldata(CircomData')` per `CircomDataBuilder.getHashedCalldata` (a pure deterministic function of public fields) [6](#0-5) .
3. Attacker submits `transact(a, b, c, dimensions, CircomData')` to `Hinkal.sol`. `hinkalHelper.performHinkalChecks` recomputes the hash and it matches `CircomData'.calldataHash` (self-consistent, attacker controlled) [9](#0-8) , then feeds `calldataHash'` into `inputForCircom`. Because the circuit never constrains `calldataHash`, `verifyProof(a,b,c,inputForCircom,...)` still succeeds despite `calldataHash' != calldataHash` used to build `signedMessageHash`.
4. `Hinkal._internalTransact` executes with the attacker's `relay`/`feeStructure`, paying `relayFee` to `RelayB` instead of `RelayA`, or draining more funds than the user authorized [7](#0-6) .

Note: full end-to-end confirmation would require inspecting the generated Groth16 verifier contract (`contracts/verifiers/**`) to confirm the public-input slot for `calldataHash` is passed through unconstrained at the R1CS level — that file class is explicitly out of scope per the rules, so this finding is based on the circom source, which is in scope and shows no constraint on `calldataHash`.
