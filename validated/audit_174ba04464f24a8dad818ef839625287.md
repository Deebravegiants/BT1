### Title
Block-reward recalculation after partial distribution can overpay a straggling delegator by mixing an already-updated numerator with a stale denominator - (File: runtime/src/bank/partitioned_epoch_rewards/calculation.rs)

### Summary
`calculate_block_reward` (SIMD-0123 block-revenue-sharing) computes a delegator's share of a vote account's `pending_delegator_rewards` as `stake / total_active_stake`, where `total_active_stake` is a fixed, epoch-boundary snapshot (`reward_epoch_delegated_stakes`) but `stake` is read live from `delegation_effective_stake()` against the current `StakesCache`. This mirrors the Wild Credit "reward computed before totals/individual state are consistently updated" bug class: the numerator can reflect state mutated by an intervening operation (a prior partition's distribution, which mutates the stake delegation lamports in `StakesCache` via `build_updated_stake_reward`) while the denominator does not, breaking the fair-share invariant that partitioned distributions are supposed to preserve.

### Finding Description
`calculate_block_reward` computes:
```
(pending_delegator_rewards * stake / total_active_stake).clamp(...)
``` [1](#0-0) 

- `total_active_stake` comes from `reward_epoch_delegated_stakes.delegated_stakes`, a value snapshotted once for the whole rewarded epoch [2](#0-1) .
- `stake` is computed via `delegation_effective_stake(delegation, rewarded_epoch, stake_history, ...)`, where `delegation` is taken live from the current `StakesCache` entry, not from a point-in-time-of-calculation copy [3](#0-2) .

During multi-block partitioned distribution, when a stake account is paid in an earlier partition, `build_updated_stake_reward` mutates that account's `delegation.stake` in place (adding the inflation reward) and stores it back into `StakesCache` via `store_stake_accounts_in_partition` [4](#0-3) [5](#0-4) .

If `recalculate_partitioned_rewards_if_active` runs afterward (e.g., after a bank/fork transition mid-distribution), it re-derives stake rewards using `calculate_stake_rewards_and_commissions` → `calculate_block_reward`, again reading `delegation_effective_stake` from the now-mutated `StakesCache`, but reusing the **original**, unmutated `total_active_stake` denominator from `reward_epoch_delegated_stakes` [6](#0-5) . The code's own comment concedes the resulting mismatch: "During recalculation, if stake account has already received rewards, it's possible to have `stake > total_active_stake`," relying on a `.min(pending_delegator_rewards)` clamp to avoid an outright panic/overflow, calling it merely "harmless in practice" [7](#0-6) .

This is structurally identical to the reported bug class: an already-mutated per-account balance (numerator, inflated by a reward that was applied "out of turn") is divided by a stale aggregate total (denominator), so the resulting share no longer represents the account's true proportional stake. Unlike the sibling `calculate_alpenglow_points`/tower-points path — which the code base explicitly regression-tests to guarantee recalculation "must use the same AG delegated stake denominator as the original epoch-boundary calculation" (`test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator`) [8](#0-7)  — there is no equivalent regression test or invariant check confirming `calculate_block_reward` produces the correct residual split for delegators not yet paid when recalculation occurs mid-distribution.

### Impact Explanation
Because `pending_delegator_rewards` on the vote account is a single shared pool for all of that validator's delegators for block-revenue-sharing rewards, a numerator inflated by an already-applied inflation reward causes the not-yet-paid stakers in later partitions to receive a disproportionately larger (or, depending on relative sizes, smaller) share of the remaining `pending_delegator_rewards` than their true stake fraction warrants at the block-reward calculation point — a real, on-chain lamport misallocation among delegators of the same validator, not merely a display/metrics issue, since the computed amount is minted directly into the stake account's lamports via `checked_add_lamports` in `build_updated_stake_reward` [9](#0-8) .

### Likelihood Explanation
Recalculation of partitioned rewards mid-distribution is a bank-commit/fork-replay path (`recalculate_partitioned_rewards_if_active`) exercised on ordinary validator restarts/replays whenever a distribution spans multiple blocks (`REWARD_CALCULATION_NUM_BLOCKS`/`num_partitions` > 1), which is common in production given large validator sets. No attacker action or special role is required; it is triggered by normal bank-forks handling during an in-progress epoch-reward distribution window, matching the "bank commit paths" scope for this analog. Whether the resulting drift is large enough to matter in practice depends on stake sizes and reward magnitudes, and the code's own comment treats the overflow-adjacent symptom as "harmless," so likelihood of an economically significant misallocation is uncertain without further quantitative analysis.

### Recommendation
Apply the same fix pattern already used for `calculate_alpenglow_points`/tower points: when recomputing block rewards during `recalculate_stake_rewards`, use a stake snapshot consistent with the original calculation point (i.e., the delegation stake as of the epoch boundary, or subtract already-distributed stake reward amounts from both numerator and denominator symmetrically) rather than mixing a live, partially-mutated `StakesCache` numerator with the frozen `reward_epoch_delegated_stakes` denominator. Add a regression test analogous to `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` but targeting `calculate_block_reward`/`block_revenue_sharing`, asserting that unpaid delegators' recalculated block rewards match the original epoch-boundary calculation after a partial distribution has occurred.

### Proof of Concept
1. Enable `block_revenue_sharing` and `AlpenglowEpochType::Alpenglow` for a validator with two stake delegations, `A` and `B`, of equal stake, delegated to the same vote account with a nonzero `pending_delegator_rewards`.
2. Configure `partitioned_epoch_rewards_config` so distribution spans ≥2 partitions, with `A` in partition 0 and `B` in partition 1, following the pattern in `test_recalculate_alpenglow_rewards_after_partial_distribution_uses_original_denominator` [10](#0-9) .
3. Distribute partition 0, which mutates `A`'s stake delegation lamports upward via `store_stake_accounts_in_partition`/`build_updated_stake_reward`.
4. Trigger `recalculate_partitioned_rewards_if_active` (e.g., via a bank-forks parent/child transition before partition 1 is processed).
5. Compare `B`'s recalculated `block_reward` (from `calculate_block_reward`) to the value computed in the original, pre-distribution calculation for `B`; observe that the denominator (`total_active_stake`) is unchanged from `reward_epoch_delegated_stakes` while `A`'s stake (used only implicitly through the shared `pending_delegator_rewards` pool being partially drawn down) has already grown, showing the numerator/denominator inconsistency the code's own comment acknowledges.

    fn calculate_stake_rewards_and_commissions<'a>(
        &self,
        stake_history: &StakeHistory,
        stake_delegations: Vec<(&'a Pubkey, &'a StakeAccount<Delegation>)>,
        cached_vote_accounts: CachedVoteAccounts<'_>,
        rewarded_epoch: Epoch,
        point_value: PointValue,
        ag_epoch_type: &AlpenglowEpochType,
        thread_pool: &ThreadPool,
        reward_calc_tracer: Option<impl RewardCalcTracer>,
        metrics: &mut RewardsMetrics,
    ) -> (RewardCommissions, StakeRewardCalculation) {
        let new_warmup_cooldown_rate_epoch = self.new_warmup_cooldown_rate_epoch();
        let feature_snapshot = self.feature_set.snapshot();
        let use_fixed_point_stake_math = feature_snapshot.upgrade_bpf_stake_program_to_v5_1;
        let delay_commission_updates = feature_snapshot.delay_commission_updates;
        let commission_rate_in_basis_points = feature_snapshot.commission_rate_in_basis_points;
        // Name intentionally doesn't match -- "adjust delegations for rent" is
        // part of relaxing post-exec min balance checks.
        let adjust_delegations_for_rent = feature_snapshot.relax_post_exec_min_balance_check;
        let custom_commission_collector = feature_snapshot.custom_commission_collector;
        let block_revenue_sharing = feature_snapshot.block_revenue_sharing;

        let mut measure_redeem_rewards = Measure::start("redeem-rewards");
        // For N stake delegations, where N is >1,000,000, we produce:
        // * N stake rewards,
        // * M reward commission accounts, where M is a number of stake nodes.
        //   Currently, way smaller number than 1,000,000. And we can expect it
        //   to always be significantly smaller than number of delegations.
        //
        // Producing the stake reward with rayon triggers a lot of
        // (re)allocations. To avoid that, we allocate it at the start and
        // pass `stake_rewards.spare_capacity_mut()` as one of iterators.
        let stake_delegations_len = stake_delegations.len();
        let mut stake_rewards = PartitionedStakeRewards::with_capacity(stake_delegations_len);
        let rewards_accumulator: RewardsAccumulator = thread_pool.install(|| {
            stake_delegations
                .par_iter()
                .zip(&mut stake_rewards.spare_capacity_mut()[..stake_delegations_len])
                .with_min_len(500)
                .filter_map(|((stake_pubkey, stake_account), reward_ref)| {
                    let block_reward = if block_revenue_sharing {
                        calculate_block_reward(
                            rewarded_epoch,
                            stake_account.delegation(),
                            stake_history,
                            cached_vote_accounts.distribution_epoch_vote_accounts,
                            ag_epoch_type,
                            new_warmup_cooldown_rate_epoch,
                            use_fixed_point_stake_math,
                        )
                    } else {
                        0
                    };
                    let maybe_reward_record = self.redeem_delegation_rewards(
                        rewarded_epoch,
                        stake_pubkey,
                        stake_account,
                        &point_value,
                        stake_history,
                        &cached_vote_accounts,
                        reward_calc_tracer.as_ref(),
                        new_warmup_cooldown_rate_epoch,
                        delay_commission_updates,
                        commission_rate_in_basis_points,
                        adjust_delegations_for_rent,
                        ag_epoch_type,
                        custom_commission_collector,
                        use_fixed_point_stake_math,
                    );

    fn recalculate_stake_rewards(
        &self,
        epoch_rewards_sysvar: &EpochRewards,
        thread_pool: &ThreadPool,
    ) -> (Arc<PartitionedStakeRewards>, Vec<Vec<usize>>) {
        assert!(epoch_rewards_sysvar.active);
        // If rewards are active, the rewarded epoch is always the immediately
        // preceding epoch.
        let rewarded_epoch = self.epoch().saturating_sub(1);

        let point_value = PointValue {
            rewards: epoch_rewards_sysvar.total_rewards,
            points: epoch_rewards_sysvar.total_points,
        };

        let stakes = self.stakes_cache.stakes();
        let EpochRewardCalculateParamInfo {
            stake_history,
            stake_delegations,
            cached_vote_accounts,
        } = self.get_epoch_params_for_recalculation(rewarded_epoch, &stakes);
        let ag_epoch_type = AlpenglowEpochType::get(self, rewarded_epoch, || {
            RewardEpochDelegatedStakes::get(self)
        });

        // On recalculation, only the `StakeRewardCalculation::stake_rewards`
        // field is relevant. It is assumed that reward commission accounts have
        // already been calculated and delivered, while
        // `StakeRewardCalculation::total_rewards` only reflects rewards that
        // have not yet been distributed.
        //
        // NOTE: the `RewardCommissionAccounts` will NOT have a correct
        // post_lamport amount if the commission account is NOT the vote account,
        // because the commission account is loaded from the current bank, and
        // not the start of the epoch. We don't have a snapshot of all commission
        // accounts from the start of the epoch. For this reason, the
        // `RewardCommissionAccounts` calculated in this function call should
        // NOT be used ever.
        let (_, StakeRewardCalculation { stake_rewards, .. }) = self
            .calculate_stake_rewards_and_commissions(
                &stake_history,
                stake_delegations,
                cached_vote_accounts,
                rewarded_epoch,
                point_value,
                &ag_epoch_type,
                thread_pool,
                null_tracer(),
                &mut RewardsMetrics::default(), // This is required, but not reporting anything at the moment
            );
