### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted despite not being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-validating only the raw request body, then reads `shop`, `topic`, `webhook_id`, and `api_version` straight from unauthenticated HTTP headers. Since a single `api_secret_key` is shared across every shop that installs an app, an attacker who has legitimately installed the app on their own store can capture a valid `(body, hmac)` pair from their own webhook deliveries and replay it with forged `shop-domain`/`topic`/`webhook-id` headers, causing the host application to process the webhook as if it belongs to a different merchant.

### Finding Description
`Request#hmac` and `Request#to_signable_string` show that only the raw body is covered by the signature: [1](#0-0) 

Concretely: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers, which are not part of `to_signable_string`, so they are never authenticated: [3](#0-2) 

`Registry.process` validates the HMAC against the body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` when building `WebhookMetadata` for the handler: [4](#0-3) 

`HmacValidator.validate_signature` computes the expected signature purely from `verifiable_query.to_signable_string` (i.e., the raw body) and the shared `Context.api_secret_key`: [5](#0-4) 

Because `Context.api_secret_key` is a single value shared by the app across all installed shops (it is not shop-specific), any shop that has installed the app can legitimately obtain a `(raw_body, hmac)` pair valid under that shared secret from its own genuine webhook deliveries. That same body+HMAC pair remains valid when replayed with the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers changed to arbitrary values, since none of those fields are covered by the signature. This breaks the intended binding: `shop reported in the request == shop the HMAC actually authenticates`, which the library implicitly assumes is one and the same.

### Impact Explanation
This is a cross-tenant confusion: an attacker who is a legitimate (but unprivileged relative to other merchants) installer of the app can cause the host application's webhook handler to execute business logic (e.g., data updates, inventory/order sync, uninstall handling) attributing an event to a shop the attacker does not control, purely by forging headers on an HTTP request whose body/HMAC pair they obtained honestly from their own store. Depending on how the host application persists/acts on `WebhookMetadata#shop`, this can lead to cross-tenant data corruption or state confusion, which matches the "cross-tenant access" impact category.

### Likelihood Explanation
Any developer/merchant can install a public app to become a legitimate webhook sender for their own shop and thus obtain a valid body+HMAC pair signed by the app's shared `client_secret`(equivalent). The webhook endpoint is by design open to the internet with no other authentication layer expected before `Registry.process` is invoked. Forging headers (`shop-domain`, `topic`, `webhook-id`) in an otherwise-valid HTTP POST requires no special access.

### Recommendation
Extend `to_signable_string` (or add a separate verification step in `Registry.process`) so the `shop`, `topic`, and `webhook_id` header values are cryptographically bound to the signed payload, or require the caller to cross-check `request.shop` against a known/installed shop list before invoking the handler, so a shop's identity cannot be substituted independently of the HMAC-verified body.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g., `app/uninstalled`) to receive a legitimate `raw_body` and `X-Shopify-Hmac-SHA256` value, both valid under the app's shared `api_secret_key`.
2. Send a POST to the host application's webhook endpoint with the same `raw_body` and `hmac-sha256` header, but replace `shopify-shop-domain` with `victim-shop.myshopify.com` and/or `shopify-topic`/`shopify-webhook-id` with values relevant to the target integration.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which only checks the body against the HMAC — validation succeeds.
4. The registered handler is invoked with `WebhookMetadata.new(topic: <forged>, shop: "victim-shop.myshopify.com", body: <attacker's own body>, ...)`, causing the host app to process attacker-supplied data as if it originated from the victim shop. [4](#0-3)
