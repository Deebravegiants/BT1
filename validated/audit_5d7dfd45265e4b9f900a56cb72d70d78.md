### Title
`request.topic` and `request.shop` are trusted by `Registry.process` despite not being covered by the webhook HMAC - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` computes/compares the HMAC over exactly that string using the app-wide `Context.api_secret_key` [2](#0-1) . `Registry.process` treats a successful `HmacValidator.validate(request)` as authorizing use of `request.topic` and `request.shop` (read straight from attacker-controllable headers) to select the handler and build `WebhookMetadata`, with no additional binding of those fields to the signature [3](#0-2) .

### Finding Description
The claimed equality is: `request.topic == topic-authenticated-by-HMAC` and `request.shop == shop-authenticated-by-HMAC`. Tracing the code confirms both fail to hold, because neither field is part of the signable material.

- `topic` and `shop` are pulled directly from the `x-shopify-topic` / `x-shopify-shop-domain` headers with no cross-check against the body: [4](#0-3) .
- `to_signable_string` is `@raw_body` only: [1](#0-0) .
- `HmacValidator.validate` → `validate_signature` HMACs `verifiable_query.to_signable_string` (i.e., the body) against `Context.api_secret_key` and compares to `verifiable_query.hmac` (the `x-shopify-hmac-sha256` header): [5](#0-4) .
- `Registry.process` does: validate HMAC → look up handler by `request.topic` → invoke `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`, with no further checks: [3](#0-2) .

Given a body that was legitimately signed by Shopify for the attacker's own dev shop (e.g., `orders/create` for `attacker-shop.myshopify.com`, body `{}`), `OpenSSL::HMAC.hexdigest(sha256, secret, "{}")` depends only on the shared `api_secret_key` and the raw body bytes. Swapping `x-shopify-topic` to `customers/data_request` and `x-shopify-shop-domain` to `victim-shop.myshopify.com` does not change `raw_body`, so `validate_signature` still succeeds. `Registry.process` then dispatches to whatever handler is registered for `customers/data_request`, constructing `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` — a value the app never actually verified as authentic, yet is exactly what a legitimate mandatory-webhook GDPR handler (`customers/data_request`, `customers/redact`, `shop/redact`) would use to select/erase/export a specific merchant's data.

Existing guards were checked and do not close this gap:
- `HmacValidator.validate` only checks the body signature, never shop/topic [6](#0-5) .
- `Registry.process` performs no lookup of `request.shop` against any known/installed-shop table, and no comparison of `request.topic` against anything derived from the body [3](#0-2) .
- `VerifiableQuery` is a generic interface (`hmac`, `to_signable_string`) shared with the OAuth `AuthQuery` flow; it has no notion of binding auxiliary metadata to the signature [7](#0-6) .
- `WebhookMetadata` is a plain `T::Struct` that simply stores whatever `Registry.process` passes it, providing no independent verification [8](#0-7) .
- Sorbet typing only enforces that `topic`/`shop` are `String`; it does nothing to enforce their authenticity.

Important caveat on root cause: this signature scheme (HMAC over body only, using the app's single shared `client_secret`/`api_secret_key` for every installed shop) mirrors Shopify's own documented webhook verification algorithm — Shopify itself does not include the shop domain or topic inside the signed payload, and the same secret is used for every shop that installs the app. This gem faithfully implements that documented mechanism rather than inventing a new flaw; the `to_signable_string`/`HmacValidator` pairing cannot unilaterally add shop/topic into the signed content without breaking compatibility with real Shopify-issued webhooks, since Shopify would never produce a signature that matches such an extended string. The exploitable weakness is therefore in how `Registry.process` in this gem treats `request.shop`/`request.topic` as if verifying the HMAC also verifies them — passing possibly-forged tenant/topic identifiers straight into `WebhookMetadata` for the handler to act on. That gap in `Registry.process` is gem code (not an upstream protocol necessity), and it is the piece exploitable purely through HTTP requests to the app's webhook endpoint (no secrets required), independent of TLS interception or any other out-of-scope vector.

### Impact Explanation
Any attacker who can install the app on their own dev shop (unprivileged action available to anyone) receives a validly HMAC-signed webhook payload signed with the app's single, shop-independent `api_secret_key`. They can replay that exact body/HMAC pair to the app's public webhook endpoint while freely choosing `x-shopify-topic` and `x-shopify-shop-domain`. Because `Registry.process` uses those headers, unauthenticated by the HMAC, to route to a handler and populate `WebhookMetadata#shop`/`#topic`, an app whose `customers/data_request`, `customers/redact`, or `shop/redact` handler (or any topic-specific handler) acts on `data.shop` will act on an attacker-chosen, arbitrary victim shop domain string, and under an attacker-chosen topic that differs from what was actually signed. This is a cross-tenant data-integrity/authenticity issue: the handler believes it received an authentic `customers/data_request` for `victim-shop.myshopify.com`, when in fact only the JSON body `{}` was ever cryptographically verified. Repeatable against any shop domain the attacker chooses to type into the header, for every request the attacker sends, matching "Critical – cross-tenant access."

### Likelihood Explanation
Preconditions: the app must register a handler for at least one topic via `Registry.add_registration` (baseline app requirement, always true for a functioning app, and mandatory for `customers/data_request`/`customers/redact`/`shop/redact` per Shopify's GDPR requirements). The attacker needs only: (1) their own dev shop with the app installed (self-service, free), (2) ability to trigger one webhook delivery to themselves (e.g., create an order, `{}` body works for many topics too), (3) ability to POST to the app's public webhook endpoint with custom headers (trivial, no credentials needed). No `api_secret_key`, access token, or any secret is required. This is at attacker cost `~zero`, fully repeatable, and requires no race conditions or timing.

### Recommendation
`Registry.process` should not treat `request.shop`/`request.topic` as authenticated merely because the body HMAC matched. At minimum: (1) look up `request.shop` against the app's own store of installed/known shop sessions before dispatching, rejecting shops the app has no session/installation record for; (2) where feasible, cross-check `request.topic` against the topic the handler was registered under and log/alert on mismatches rather than blindly trusting the header; (3) document clearly (and enforce where possible) that `WebhookMetadata#shop`/`#topic` are Shopify-supplied hints, not values verified by `HmacValidator.validate`, so host apps do not assume otherwise when writing handlers such as GDPR redaction/data-request handlers.

### Proof of Concept
```ruby
# test/webhooks/registry_cross_tenant_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistryCrossTenantTest < Test::Unit::TestCase
      def test_shop_and_topic_are_not_bound_to_hmac
        raw_body = "{}"
        hmac = OpenSSL::HMAC.digest(
          OpenSSL::Digest.new("sha256"),
          ShopifyAPI::Context.api_secret_key,
          raw_body,
        )

        # Attacker "receives" a validly signed webhook for their own shop/topic.
        attacker_headers = {
          "x-shopify-topic" => "orders/create",
          "x-shopify-hmac-sha256" => Base64.encode64(hmac),
          "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
        }
        signed_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: attacker_headers)
        assert(ShopifyAPI::Utils::HmacValidator.validate(signed_request))

        # Attacker replays identical raw_body/hmac but swaps topic/shop headers.
        forged_headers = attacker_headers.merge(
          "x-shopify-topic" => "customers/data_request",
          "x-shopify-shop-domain" => "victim-shop.myshopify.com",
        )
        forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

        # Same HMAC still validates: shop/topic are outside to_signable_string.
        assert(ShopifyAPI::Utils::HmacValidator.validate(forged_request))
        assert_equal(signed_request.to_signable_string, forged_request.to_signable_string)

        received_shop = nil
        handler = TestHelpers::FakeWebhookHandler.new(
          lambda { |data| received_shop = data.shop },
        )
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "customers/data_request", path: "path", delivery_method: :http, handler: handler,
        )

        ShopifyAPI::Webhooks::Registry.process(forged_request)

        # Binding is broken: handler acted on victim-shop despite HMAC never covering "shop" or "topic".
        assert_equal("victim-shop.myshopify.com", received_shop)
      end
    end
  end
end
```

This test requires no live shop, no WebMock stubbing (no HTTP call is made by `Registry.process` for the `:http` delivery method's `process`), and directly demonstrates that `request.shop`/`request.topic` diverge from what was actually HMAC-authenticated while `Registry.process` still dispatches successfully.
