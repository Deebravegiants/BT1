### Title
Webhook shop/topic/webhook-id identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, while `Registry.process` trusts the `shop-domain`, `topic`, and `webhook-id` headers to identify the tenant and dispatch the event — even though none of these header values are covered by the HMAC signature that is validated.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC solely over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop`, `topic`, and `webhook_id` — the values that identify *which tenant and event* the webhook belongs to — are read straight from HTTP headers that are never mixed into the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts these unauthenticated header fields to build the dispatched metadata: [4](#0-3) 

The identity binding that should hold is:

`HMAC-verified bytes == bytes the handler acts on for tenant identification`

Here that equality is broken: the HMAC only proves "this body was produced with our `client_secret`" (the body could be, e.g., a mandatory-compliance payload like `shop/redact` or an ordinary resource-update payload with a fixed/predictable shape), but it proves nothing about *whose* shop, topic, or webhook-id the request claims to be for. Any raw body + valid HMAC pair — which an unprivileged internet user can legitimately obtain by installing the app on their own store and receiving a real webhook — can be replayed with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header rewritten to name a different, victim shop. `HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will hand the attacker-chosen `shop` straight to the app's webhook handler as authenticated `WebhookMetadata`.

### Impact Explanation
This is a cross-tenant identity confusion: an app author's webhook handler is expected to trust `data.shop` (and `data.topic`) as coming from Shopify for that specific shop, because the gem has already "validated" the request. In reality, an attacker who owns any shop that has the app installed can capture one legitimate `(raw_body, hmac)` pair for a topic and then submit it directly to the app's webhook endpoint with the `shop-domain` header changed to an arbitrary victim `myshopify.com` domain (or an arbitrary `webhook-id`/`topic`). Depending on how the host application keys its webhook processing (e.g. `shop/redact`, `customers/redact`, `customers/data_request`, `app/uninstalled`, `shop/update`), this can trigger tenant-scoped side effects (data deletion/redaction, uninstall handling, record updates) attributed to a shop the attacker does not own — a cross-tenant impact.

### Likelihood Explanation
The webhook endpoint is a public HTTP endpoint by design (no additional authentication beyond the HMAC), and the only "credential" needed to forge the header is a single previously-seen valid `(body, HMAC)` pair, which any merchant/user of the app can obtain by installing it once. No access to `api_secret_key`, `client_secret`, or a privileged account is required — the attack only needs a normal internet-reachable POST to the app's webhook callback with rewritten headers.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified payload, or otherwise cryptographically bind them to the body before dispatch — e.g., have `to_signable_string` concatenate the raw body together with these header values (in a canonical, unambiguous encoding), and validate the resulting composite string with the HMAC.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `shop/redact` with body `{}` and header `X-Shopify-Hmac-Sha256: <valid-hmac-for-{}>`.
2. Attacker replays this exact `(body, hmac)` pair to the app's webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: shop/redact` (or any other registered topic whose body shape is predictable)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the HMAC of `{}` [5](#0-4) .
4. The handler for the topic is invoked with `WebhookMetadata` built from `request.shop == "victim-shop.myshopify.com"` [6](#0-5) , causing the app to process a compliance/redaction/update event for a shop the attacker never authenticated as.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
