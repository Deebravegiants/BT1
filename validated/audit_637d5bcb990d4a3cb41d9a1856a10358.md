### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, while the tenant-identifying `shop` value (and `topic`/`webhook_id`) is read straight from HTTP headers that are never included in the signed material. An attacker who owns any Shopify shop can capture a genuinely-signed webhook delivery for their own store and replay the same body+HMAC to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop, and the request will pass `HmacValidator.validate` and be dispatched to the handler as if it originated from the victim tenant.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` to build the string that is HMAC-verified: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, and `webhook_id` — the identifiers the app relies on to know *which* tenant/event the payload belongs to — are pulled unauthenticated straight out of headers: [3](#0-2) 

`Registry.process` validates the HMAC (which only proves the body bytes are untampered/came from someone holding `api_secret_key` for *some* shop's webhook), then unconditionally trusts `request.shop` and hands it to the handler as the tenant identifier: [4](#0-3) 

This breaks the intended binding `hmac(secret, body) proves shop == header.shop-domain`. In reality the equality that holds is only `hmac(secret, body) proves body == raw_body`; the `shop-domain` header is never part of the signed bytes, so `shop_used_by_handler != shop_that_actually_sent_the_webhook` can be forced by anyone who possesses one valid `(raw_body, hmac)` pair for any shop that uses the app (e.g., their own store, which they can freely install/uninstall to generate a real signed webhook, including sensitive ones like `customers/data_request` or `shop/redact`).

### Impact Explanation
This falls in the Critical bucket ("cross-tenant access"): the app-supplied `WebhookHandler` receives `WebhookMetadata` whose `shop` field is attacker-controlled despite HMAC verification succeeding. Any host application that uses `request.shop`/`WebhookMetadata#shop` to select which tenant's data to update, delete, or redact (as is expected for mandatory `customers/data_request`, `customers/redact`, `shop/redact` topics) can be tricked into acting on a different merchant's data using a signature that was never computed over that merchant's identity.

### Likelihood Explanation
The attacker only needs to be an unprivileged internet user who can install the target app on their own (attacker-controlled) shop to receive a legitimately-signed webhook body/HMAC pair for a topic of interest, then replay that exact body to the app's webhook endpoint with a forged `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) header. No `api_secret_key`, access token, or privileged account is required — only the gem's own documented `HmacValidator`/`Registry.process` flow, which is exactly what's reachable here.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, e.g. via a signed envelope) instead of relying solely on the raw body for HMAC computation, mirroring how `AuthQuery#to_signable_string` binds `shop`/`host`/`state` for OAuth. At minimum, document and enforce that `WebhookMetadata#shop`/`#topic` must not be trusted for cross-tenant authorization decisions unless corroborated by a signed value.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a genuine webhook for topic `customers/data_request` with body `B` and valid header `X-Shopify-Hmac-Sha256: H = HMAC(secret, B)`.
2. Attacker captures `(B, H)` and sends a new POST to the app's webhook endpoint with the same body `B`, same `X-Shopify-Hmac-Sha256: H`, but header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` (line 190 of `registry.rb`), which passes because `to_signable_string` only checks `B` against `H`.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and performs the topic's action (e.g., a data-subject request/redaction workflow) against `victim-shop`, even though `victim-shop` never sent this webhook. [4](#0-3)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
