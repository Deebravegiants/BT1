### Title
Bonding-curve trade DoS via unchecked underflow in `Router._computeBuy` / `Router._computeSell` after `Pair.swap`'s `+1` K-slack drift — ([File: packages/contracts/src/Router.sol])

### Summary
`Pair.swap` enforces the curve invariant with a rounding-tolerant check (`(newTokenReserve+1)*(newAssetReserve+1) >= _pool.k`) rather than an exact re-derivation of `k`, and never updates `_pool.k` after `mint`. This "+1 slack" is the same class of bug as ALPINE-CVE-2023-34323: an accounting quantity that the code trusts to stay non-negative/monotonic (`reserveToken * reserveAsset` staying ≥ the immutable `k`) is allowed to drift slightly below its expected bound by design, while downstream consumers (`Router._computeBuy` / `Router._computeSell`) still do plain unchecked-by-intent subtraction against the *original, fixed* `k`, assuming that drift can never invert the inequality they depend on.

### Finding Description
`Pair.swap` accepts any post-state whose product is within 1 unit of `_pool.k` on each side: [1](#0-0) 

Because `_pool.k` is fixed once at `mint` and `swap` only checks `(newTokenReserve+1)*(newAssetReserve+1) >= _pool.k`, the *actual* reserve product `reserveToken * reserveAsset` is permitted to fall strictly below `_pool.k` by up to `reserveToken + reserveAsset + 1` on every trade — this is the exact "+1 K slack" the scoping rules call out as load-bearing curve math.

`Router._computeBuy` and `Router._computeSell` both derive their output by re-solving the curve against the *stored, immutable* `k` and the *current* `(reserveToken, reserveAsset)`, using plain Solidity-checked subtraction: [2](#0-1) [3](#0-2) 

Both `tokensOut = reserveToken - (k / newReserveAsset)` and `assetOut = reserveAsset - (k / newReserveToken)` implicitly assume `k / newReserve<X> <= reserve<Y>` always holds. That assumption is only true if the *current* reserves still satisfy the exact `reserveToken * reserveAsset >= k` identity. Once enough swaps have exploited the `+1` slack to push the actual product below `k` (a state `Pair.swap` explicitly permits), a subsequent small trade (`amountIn` on the order of the accumulated drift) makes `k / newReserve<X>` round up to a value *larger* than the current opposite-side reserve. Since Solidity 0.8's default checked arithmetic reverts (Panic 0x11) rather than asserting, this manifests as an unconditional revert of `Router.buy` / `Router.sell` — i.e. the AMM "crashes" for that trade, exactly mirroring the Xenstored bug class: an accounting value trusted to stay non-negative goes transiently negative due to a deliberately-tolerated slack elsewhere in the system, and the consuming code has no defensive check for it (unlike `Bonding.finalizeGraduation`'s deliberately saturating `protectedLT` subtraction at [4](#0-3) , which the team explicitly hardened against exactly this failure mode — `_computeBuy`/`_computeSell` were not).

### Impact Explanation
If a curve's reserves drift into this state, every subsequent `Bonding.buy()`/`Bonding.sell()` (i.e. `Zap.buy`/`Zap.sell`) on that token's curve reverts with an arithmetic Panic instead of executing or producing a sane error. Traders holding tokens on that curve can no longer sell to exit, and no further buys can push it toward either graduation trigger (`canGraduate`) — permanently freezing both trader exit liquidity and the token's path to graduation, since `Router.sell`/`Router.buy` are the only curve-side entry points and neither `Bonding.triggerGraduation` nor anything else can route around a reverting `_computeSell`/`_computeBuy`.

### Likelihood Explanation
This requires the slack to accumulate to a magnitude comparable to a subsequent trade's `amountIn`; each individual swap only drifts the product by at most `reserveToken + reserveAsset + 1`, which is tiny relative to typical reserve sizes, so many precisely-sized trades (all executable by ordinary unprivileged buyers/sellers with no special privilege — `Zap.buy`/`Zap.sell` are open to anyone) would be needed to walk the actual product down far enough for a legitimate small trade to trip the underflow. This makes the likelihood **Medium**: reachable purely through unprivileged trading activity, but requiring an adversary (or unlucky organic trading pattern) to deliberately or repeatedly exploit the rounding slack over many transactions rather than in one shot.

### Recommendation
Replace the `+1`-tolerant check in `Pair.swap` with an exact invariant re-derivation, or have `Router._computeBuy`/`_computeSell` clamp their outputs (`tokensOut`/`assetOut`) to `0`/cap them against the live reserve rather than relying on unchecked subtraction against the immutable `k`, mirroring the saturating-subtract pattern already used defensively in `Bonding.finalizeGraduation`.

### Proof of Concept
Conceptually (exact numeric PoC needs to be constructed against the deployed constants):
1. Launch a token/LT curve via `Bonding.launch`, establishing `_pool.k = tokenReserve0 * assetReserve0` in `Pair.mint`.
2. Execute a long sequence of minimum-size buys/sells (each within `Pair.swap`'s permitted `+1` tolerance) via `Zap.buy`/`Zap.sell`, each time letting the actual `reserveToken * reserveAsset` product creep just under `_pool.k` by the maximum slack `Pair.swap` allows.
3. Once the drift accumulates near the reserve magnitude, submit one more small `Zap.buy` (or `Zap.sell`); `Router._computeBuy`'s `tokensOut = reserveToken - (k / newReserveAsset)` (or `_computeSell`'s analogous subtraction) underflows and the transaction reverts with a Panic, rather than a graceful curve error — reproducing the crash class described in ALPINE-CVE-2023-34323 within the trading path.

        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
