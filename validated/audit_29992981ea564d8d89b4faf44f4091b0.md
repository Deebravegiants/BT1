### Title
Fishermen dispute-game blacklist can be raced by a permissionless `OpFaultProofGames`/`ArbitrumOrbit`/`ArbitrumBold` consensus proof, letting a fraudulent state commitment land before the blacklist takes effect - (File: `modules/pallets/fishermen/src/lib.rs`, `modules/ismp/clients/ismp-optimism/src/lib.rs`)

### Summary
`pallet-fishermen::blacklist_dispute_game` / `blacklist_arbitrum_claim` are the only defense against a fraudulent opstack dispute-game or Arbitrum claim being accepted as a valid consensus update. The blacklist check is a plain storage read performed inside `verify_consensus` at proof-processing time [1](#0-0) , and the blacklist entry itself is written by an ordinary signed extrinsic from a collator [2](#0-1) . Because consensus-proof submission for the same dispute game is permissionless (any relayer can submit an `OpFaultProofGames` proof referencing a proxy, the same way anyone can call `addBlackList()`'s counterpart transaction and be front-run), an attacker who has created a fraudulent dispute game and sees the fisherman's `blacklist_dispute_game` extrinsic land in the mempool can race ahead and get their consensus proof for that same proxy included and finalized first, exactly as the report's front-run of `addBlackList()`.

### Finding Description
The off-chain fisherman watcher in `tesseract/messaging/fisherman/src/opstack.rs` detects a quorum mismatch and submits `blacklist_dispute_game` [3](#0-2) . This is a normal signed extrinsic that sits in the transaction pool before inclusion, visible to anyone monitoring the mempool — the same window the Telcoin report exploits against `addBlackList()`. Meanwhile, `verify_consensus` in `ismp-optimism` only rejects a dispute-game proxy if `FishermanBlacklist::is_dispute_game_blacklisted` already returns `true` at the moment the proof is processed [1](#0-0) . There is no reservation, lock, or pending-blacklist state that blocks proofs for a proxy while a blacklist extrinsic for it is in flight. An attacker who controls (or colludes with) the entity that created the fraudulent dispute game can submit the `OpFaultProofGames` consensus-update extrinsic for that same proxy with higher priority/tip, or simply race the mempool, and get it included in an earlier block than the fisherman's `blacklist_dispute_game` call. Once included, `verify_consensus` sees the blacklist storage as still empty, passes the check, and if the storage-proof/game state checks (`verify_optimism_dispute_game_proof`, `verify_not_challenged`) also pass, the fraudulent L2 state root is accepted and finalized into `state_machine_map`, becoming a trusted state commitment for message verification. The same TOCTOU gap exists symmetrically for `blacklist_arbitrum_claim` versus the Arbitrum consensus client.

### Impact Explanation
A successfully raced dispute game/claim results in an attacker-controlled state root being accepted as Hyperbridge's trusted view of the L2/L3 chain. Because Hyperbridge's state-membership proofs for message dispatch/delivery, token bridging, and intents settlement are all verified against the finalized state commitment, an unsound state root that lands ahead of the blacklist enables forged message delivery, unbacked mint, or unauthorized withdrawal proofs against that state — a concrete route to theft or permanent freezing of funds, matching the "unsound state commitment" / "forged message delivery" acceptance criteria.

### Likelihood Explanation
Likelihood is constrained: it requires the attacker to already control a dispute-game factory registration for a fraudulent claim (a non-trivial and detectable action) and to win a mempool/inclusion race against the fisherman extrinsic within the same or an adjacent block, which is time-sensitive but realistically achievable by an attacker monitoring the chain and paying higher priority — directly analogous in mechanism to the front-run window described in the source report. The permanence of the blacklist (no `unblacklist`) and the "any single collator finalizes" design mean the intended defense is fast, but the storage write is not applied atomically with, or ahead of, proof submission, leaving the window open every time a new fraud is discovered.

### Recommendation
Close the TOCTOU window rather than relying purely on reactive blacklisting: introduce a "pending review" / provisional-hold state for a dispute-game proxy or claim as soon as an off-chain fisherman flags a mismatch (e.g., an extrinsic that immediately halts acceptance of that specific proxy's proofs pending finalization of the blacklist, or require an extra challenge-period delay before a freshly observed dispute game's state commitment can be treated as final, giving the fisherman network a guaranteed window to submit the blacklist first). Alternatively, batch the blacklist check together with per-block ordering guarantees (e.g., process all `blacklist_dispute_game` extrinsics before any consensus-update extrinsics referencing the same target within a block), or extend the challenge period so that the fisherman's off-chain quorum check is guaranteed to complete and land on-chain before a proof for the same proxy can be finalized.

### Proof of Concept
1. Attacker creates a fraudulent `FaultDisputeGame` on the target OP-stack chain's `DisputeGameFactory` with a false root claim, satisfying `claimData.length == 1` (unchallenged) as required by `verify_not_challenged` [4](#0-3) .
2. The off-chain fisherman watcher polls, detects the quorum mismatch, and submits `blacklist_dispute_game(state_machine_id, proxy)` to Hyperbridge's mempool [3](#0-2) .
3. Before that extrinsic is included, the attacker (or a colluding relayer) submits an `OpFaultProofGames` consensus-update referencing the same `proxy` with a higher tip/priority.
4. `verify_consensus` reads `is_dispute_game_blacklisted` — still `false` — passes the check, verifies the (still valid, since factory-side data is real) storage proofs, and finalizes the fraudulent state root [5](#0-4) .
5. The fisherman's `blacklist_dispute_game` lands one block later — too late, since it has no effect on the already-finalized state commitment, and there is no revert/unwind mechanism tied to the blacklist for commitments already accepted [6](#0-5) .

		/// against the configured `DisputeGameFactory` for `state_machine_id`) is fraudulent
		/// — typically because the off-chain fisherman watcher verified the claimed L2 output
		/// root against a supermajority (2/3·N + 1) of L2 RPC endpoints and observed a
		/// mismatch (or a quorum of the L2 height being absent).
		///
		/// Any single collator finalizes the blacklist. The entry is permanent (there is no
		/// `unblacklist` extrinsic) — the consensus verifier will refuse any future
		/// `OpFaultProofGames` consensus proof that references this proxy.
		///
		/// Dispatches with `Pays::No`. The on-chain `IsCollator` check is the DOS guard.
		#[pallet::call_index(1)]
		#[pallet::weight((<T as frame_system::Config>::DbWeight::get().reads_writes(1, 1), Pays::No))]
		pub fn blacklist_dispute_game(
			origin: OriginFor<T>,
			state_machine_id: StateMachineId,
			proxy: H160,
		) -> DispatchResult {
			let account = ensure_signed(origin)?;
			ensure!(T::IsCollator::contains(&account), Error::<T>::UnauthorizedAction);

			// Idempotent: a second call for the same (chain, proxy) is silently Ok and does
			// not overwrite the original fisherman.
			if BlacklistedDisputeGames::<T>::contains_key(state_machine_id, proxy) {
				return Ok(());
			}

			BlacklistedDisputeGames::<T>::insert(state_machine_id, proxy, account.clone());
			Self::deposit_event(Event::DisputeGameBlacklisted {
				state_machine_id,
				proxy,
				fisherman: account,
			});
			Ok(())
		}
