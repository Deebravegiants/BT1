## Analysis

The ERC-2612 permit front-running bug class maps to a concrete analog in nearcore's meta-transaction (NEP-366) implementation: `SignedDelegateAction` processing performs an unconditional, unprotected validation of a client-supplied nonce/signature with no fallback, and gas is burned for the attempt regardless of whether that validation succeeds — exactly the "unconditional permit() call with no error handling" pattern described in the report.

### Title
Front-running a broadcast `SignedDelegateAction` invalidates its nonce and burns the legitimate relayer's gas - (File: runtime/runtime/src/actions.rs)

### Summary
A `SignedDelegateAction` (NEP-366 meta-transaction) is, by protocol design, a self-contained signed payload that any party can wrap into their own transaction and submit as a "relayer" — it is not bound to a specific relayer's transaction. Once the intended relayer's transaction reaches the mempool, an unrelated third party can extract the embedded `SignedDelegateAction` bytes and resubmit them first (with higher gas price) as their own transaction. This advances the sender's access-key (or gas-key) nonce, so when the original relayer's transaction is later processed, `validate_delegate_action_key` unconditionally rejects it with `DelegateActionInvalidNonce`, after the relayer has already paid for converting the transaction into a receipt and for the delegate action's own send/exec fees.

### Finding Description
`apply_delegate_action` in [1](#0-0)  calls `validate_delegate_action_key`, which unconditionally checks the delegate action's nonce against the current access-key (or gas-key) nonce and fails hard with no fallback path if the nonce was already consumed: [2](#0-1) .

Because a `SignedDelegateAction` only requires knowledge of its bytes to be replayed by any account acting as relayer, and this data is publicly visible once the intended relayer's transaction is broadcast, an attacker can front-run it with their own wrapping transaction containing the identical `SignedDelegateAction`. This mirrors the ERC-2612 pattern: an unconditional call that consumes a nonce/signature (`token.permit(...)` vs. `validate_delegate_action_key`'s nonce check), with no `try/catch`-equivalent fallback (e.g., checking whether the intended action can still proceed via an already-updated nonce) before continuing execution.

The docs explicitly acknowledge relayers bear the gas cost regardless of downstream failure: [3](#0-2) , and that "Relayer should verify DelegateAction before submitting it" [4](#0-3)  — an acknowledgment that this griefing surface exists but is left to relayer-side mitigation rather than protocol-side handling.

### Impact Explanation
The legitimate relayer's transaction still burns the transaction-conversion `SEND` fees and the delegate action's `EXEC`/`SEND` fees (billed to the relayer as transaction signer, per [5](#0-4) ) even though `apply_delegate_action` ultimately fails and returns `Ok(())` with a `DelegateActionInvalidNonce` result. This is a direct, repeatable gas-griefing DoS against relayers/users of meta-transactions: any observer of pending transactions can invalidate any pending `SignedDelegateAction` at minimal cost (their own transaction's base fee), causing certain and permanent loss for the original submitter with no recourse, exactly matching the reported bug class' impact (gas loss + broken reliability of a signature-based operation).

### Likelihood Explanation
No special privileges are required — this is purely an unprivileged-account, mempool-visibility attack requiring only the ability to submit a transaction, matching the report's "basic mempool monitoring capability and gas fees" prerequisite. It is automatable and repeatable against any user of NEP-366 meta-transactions/relayers.

### Recommendation
Consider adding an idempotency check comparable to a try/catch fallback: before treating a nonce mismatch as fatal, check whether the delegate action's intended state change was already applied by an equivalent submission (which NEAR's nonce model doesn't naturally support since actions aren't idempotent), or alternatively document/require relayers to check nonce state immediately before submission and to use tight nonce windows to minimize the front-running window. At minimum, this griefing vector and its gas-cost implications should be explicitly documented for relayer implementers as a security consideration, since currently `validate_delegate_action_key` provides no fallback and the loss falls entirely on the honest relayer.

### Proof of Concept
1. Alice signs a `DelegateAction { nonce: N, ... }` and hands it to Relayer A off-chain.
2. Relayer A wraps it in a transaction and broadcasts it to the network.
3. Attacker Bob observes the pending transaction in the mempool, extracts the identical `SignedDelegateAction`, and wraps it in his own transaction (paying gas himself) with a higher gas price.
4. Bob's transaction is included first; `validate_delegate_action_key` advances Alice's access-key/gas-key nonce to N, per [6](#0-5) .
5. Relayer A's transaction is then processed; `validate_delegate_action_key` rejects it with `DelegateActionInvalidNonce` at [2](#0-1) , after Relayer A has already been charged the transaction/delegate action's send and exec fees.
6. Relayer A's gas expenditure is permanently lost; the attack is repeatable against any future meta-transaction submitted by Alice or other users of any relayer.

pub(crate) fn apply_delegate_action(
    state_update: &mut TrieUpdate,
    apply_state: &ApplyState,
    action_receipt: &VersionedActionReceipt,
    sender_id: &AccountId,
    signed_delegate_action: VersionedSignedDelegateActionRef<'_>,
    result: &mut ActionResult,
) -> Result<(), RuntimeError> {
    // The inner delegate signature is verified below, here on the receiver shard.
    // Meter its verification compute against this shard's `compute_limit`; the gas
    // for it was already burnt at tx conversion on the signer shard. Without the
    // fix the compute is instead mis-charged on the signer shard (which never runs
    // this verify), letting the work escape the receiver shard's budget. See
    // `signature_verification_cost`.
    if apply_state.config.wasm_config.fix_ml_dsa_cost_charging {
        let verify_compute = delegate_signature_verification_compute(
            &apply_state.config.fees,
            signed_delegate_action.delegate_action().public_key(),
        );
        result.compute_usage = safe_add_compute(result.compute_usage, verify_compute)?;
    }
    if !signed_delegate_action.verify() {
        result.result = Err(ActionErrorKind::DelegateActionInvalidSignature.into());
        return Ok(());
    }
    let delegate_action = signed_delegate_action.delegate_action();
    if apply_state.block_height > delegate_action.max_block_height() {
        result.result = Err(ActionErrorKind::DelegateActionExpired.into());
        return Ok(());
    }
    if delegate_action.sender_id().as_str() != sender_id.as_str() {
        result.result = Err(ActionErrorKind::DelegateActionSenderDoesNotMatchTxReceiver {
            sender_id: delegate_action.sender_id().clone(),
            receiver_id: sender_id.clone(),
        }
        .into());
        return Ok(());
    }

    validate_delegate_action_key(state_update, apply_state, delegate_action, result)?;
    if result.result.is_err() {
        // Validation failed. Need to return Ok() because this is not a runtime error.
        // "result.result" will be return to the User as the action execution result.
        return Ok(());
    }
