### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, using the app's single `api_secret_key`. The `shop` identity that is handed to the app's handler, however, comes from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never included in the signed material. This breaks the intended binding "shop for which Shopify computed the HMAC == shop the app processes the webhook as."

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Utils::HmacValidator.validate` computes/compares the HMAC purely against that signable string with the app's `api_secret_key` (or `old_api_secret_key`): [2](#0-1) 

`Registry.process` only checks this body HMAC and then immediately trusts `request.shop` (parsed from the unauthenticated header) to build the `WebhookMetadata` passed to the merchant's handler: [3](#0-2) 

`Request#shop` is read directly from the `shop-domain` header with no cross-check against the signed body: [4](#0-3) 

Because the `api_secret_key` used to sign webhook bodies is the app-level secret (identical for every shop that installs the app), any unprivileged party who installs the app on their own store can legitimately receive an HMAC-valid `(raw_body, hmac)` pair from Shopify. That pair remains HMAC-valid no matter which `x-shopify-shop-domain` header value is attached to the replayed request, since the header is outside the signed data. An attacker can therefore replay their own captured webhook body+HMAC to the app's webhook endpoint while forging the `x-shopify-shop-domain` header to name a victim merchant's shop domain, and `Registry.process` will accept it and invoke the handler with `WebhookMetadata#shop` set to the victim's domain.

The equality that should hold but does not:
`shop that Shopify's signature attests to == shop value trusted by the handler`
In this implementation the right-hand side is taken from an unauthenticated header field, while the HMAC only binds the left-hand side to the request body.

### Impact Explanation
This is a scope/identity-binding bypass affecting any host application whose webhook handler branches on `WebhookMetadata#shop` (e.g., to look up a merchant `Session`/access token, update per-shop billing state, disable/enable features, or invalidate data) without independently verifying shop identity. An attacker with no privileges beyond installing the app on their own store can cause the host app to attribute attacker-controlled webhook data to an arbitrary victim shop, i.e., cross-tenant data confusion/impersonation through the gem's own webhook-processing API. This matches the "cross-tenant access" class of impact called out as in-scope Critical impact.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that relies on `ShopifyAPI::Webhooks::Registry.process` as its sole authentication mechanism for webhooks (as documented) and trusts `WebhookMetadata#shop`. The prerequisite (own-store install to obtain a valid signed body+HMAC pair) is trivially available to any unprivileged internet user who can install a public/dev app, and forging headers on an HTTP replay requires no special access, credentials, or the app's `client_secret`.

### Recommendation
Bind the shop identity into the material that is actually verified: either (a) include the `shop-domain` header (and ideally `topic`, `api-version`, `webhook-id`) in the signable string used for HMAC computation, matching them against a value looked up from a merchant session/store rather than trusting the header verbatim, or (b) cross-validate `request.shop` against the shop encoded in the (currently unsigned) body/metadata Shopify sends, rejecting requests where the header shop does not match a shop the app can independently confirm owns that webhook subscription (e.g., by correlating `webhook-id` to a shop-scoped record). At minimum, document prominently that `Request#shop`/`WebhookMetadata#shop` is not authenticated by the HMAC check and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, subscribes to a webhook topic (e.g. `orders/create`), and triggers an event, capturing the resulting request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`), from `lib/shopify_api/webhooks/request.rb` this HMAC covers only `B`.
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which succeeds because the check only validates `B` against `H` (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the app's handler, which now processes attacker-controlled data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
