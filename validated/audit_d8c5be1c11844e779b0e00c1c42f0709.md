## Title
Silent ERC20 sweep failures inside `CallDispatcher` strand funds that anyone can then steal via `CallDispatcher.dispatch()` - (File: evm/src/utils/CallDispatcher.sol, evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder()`'s predispatch flow and `IntentsBase._execute()`'s postdispatch flow "sweep" tokens out of the `CallDispatcher` using a raw, unchecked `IERC20.transfer` call encoded as low-level calldata, rather than `SafeERC20.safeTransfer`. `CallDispatcher.dispatch()` only checks that the low-level `.call` itself didn't revert — it never inspects the ABI-decoded boolean return value of the token transfer. This is exactly the bug class flagged in the reference report (unchecked ERC20 return values), but here it is compounded by `CallDispatcher` being a shared, access-control-free singleton, turning a silent transfer failure into a theft vector reachable by any unprivileged transaction.

### Finding Description
In `IntentGatewayV2.placeOrder()`, when an order has predispatch calldata, tokens are first sent to the shared `dispatcher` (a `CallDispatcher` instance), the predispatch call executes, and then a "sweep" `Call` is built to move the resulting balance back to the gateway: [1](#0-0) 

This sweep call encodes a raw `IERC20.transfer.selector` call and is executed via `ICallDispatcher(dispatcher).dispatch(...)`: [2](#0-1) 

`CallDispatcher.dispatch` only reverts when the low-level call itself reverts (`success == false`); it never decodes/validates the boolean return value that ERC20 `transfer` is expected to return. Any ERC20 that returns `false` on failure instead of reverting (a well-known non-standard-but-existent pattern) will make the sweep "succeed" from `CallDispatcher`'s point of view while the tokens never actually move.

Back in `placeOrder`, the code only detects the shortfall by comparing balances, and silently accepts a lower (even zero) input amount rather than reverting: [3](#0-2) 

Because `CallDispatcher.dispatch(bytes memory encoded)` is `external` with **no access control whatsoever**: [4](#0-3) 

any tokens left stranded in `CallDispatcher` after a failed/silent sweep are immediately available to be drained by *anyone* — not just the gateway — via a direct, permissionless call to `dispatcher.dispatch()` with a `Call` that transfers the stranded balance to an attacker-controlled address. The same unchecked-transfer sweep pattern (`IERC20.transfer.selector` executed through `CallDispatcher`, with only balance-delta accounting) also appears in the postdispatch flow: [5](#0-4) 

### Impact Explanation
This breaks the intended atomicity/custody model of `CallDispatcher`: it is meant to hold tokens only transiently within a single transaction, with the escrowing `IntentGatewayV2`/`IntentsBase` contracts being the sole legitimate mover of those funds. A silently-failing (non-reverting-false) ERC20 transfer during the sweep leaves real funds sitting in an unprotected, shared contract, immediately stealable by any third party who calls `dispatch()` directly. This is a concrete theft-of-funds path, not merely an accounting inconsistency — user-escrowed input tokens (or output tokens from `_execute`) can be permanently lost to an attacker.

### Likelihood Explanation
Exploitation requires an ERC20 token registered as a predispatch/output asset that returns `false` on transfer failure rather than reverting (a real, if minority, ERC20 behavior class), or any circumstance (fee-on-transfer/blacklist/pausable token) causing such a token's transfer to fail without reverting. Any user who places an order using such a token as a predispatch/output asset — or an attacker who deliberately does so — can trigger the stranding, then race to call `CallDispatcher.dispatch()` before the affected funds are otherwise recovered. Given `dispatch()` requires no privilege and no proof, exploitation is straightforward once the precondition (a non-reverting-false token) is met.

### Recommendation
Use `SafeERC20.safeTransfer`/`safeTransferFrom` (already imported and used elsewhere in `IntentGatewayV2.sol` and `IntentsBase.sol`) instead of raw `IERC20.transfer.selector` calldata for the sweep `Call`s, so a failed transfer reverts the entire `dispatch()` batch instead of silently succeeding. Additionally, restrict `CallDispatcher.dispatch()` so only the authorized `IntentGatewayV2`/`IntentsBase` caller (or an allowlisted set of gateways) can invoke it, removing the ability for arbitrary third parties to drain any balance the contract might ever hold.

### Proof of Concept
1. Deploy/select an ERC20 token `T` whose `transfer` returns `false` on failure instead of reverting (e.g., due to an internal blacklist or paused state activated after approval but before the sweep).
2. Call `IntentGatewayV2.placeOrder()` with `order.predispatch.assets` containing `T`, and `order.inputs` also containing `T` as the swept input.
3. Arrange (e.g., via the predispatch call itself, or external state) for `T.transfer(gateway, balance)` to return `false` without reverting during the sweep step at `evm/src/apps/IntentGatewayV2.sol:276-281`.
4. `CallDispatcher.dispatch` sees `success == true` (the call didn't revert) and returns normally; `placeOrder` measures `received == 0` and sets `order.inputs[i].amount = 0`, completing without reverting, while the actual `T` balance remains sitting in `_params.dispatcher`.
5. Any external account calls `CallDispatcher(_params.dispatcher).dispatch(abi.encode([Call({to: T, value: 0, data: transfer(attacker, balance)})]))` directly, stealing the stranded `T` balance — no relationship to the original order or gateway required.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
