### Title
Webhook shop-domain identity spoofing due to HMAC covering only the request body, not the `shop`/`topic` headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verified by `Utils::HmacValidator.validate` in `Registry.process` authenticates the JSON body bytes but never binds the `x-shopify-shop-domain` (or `x-shopify-topic`) header to that signature. `Registry.process` nonetheless trusts `request.shop` and `request.topic`, taken verbatim from headers, to construct the `WebhookMetadata` delivered to the host application's handler. This breaks the identity equality `shop_verified_by_hmac == shop_used_by_handler`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
def to_signable_string
  @raw_body
end
``` [3](#0-2) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from headers via `shopify_header`, entirely outside the signed material:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [4](#0-3) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. `@raw_body` only) using the app's single, shared `Context.api_secret_key`:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [5](#0-4) 

`Registry.process` then validates the HMAC and, on success, unconditionally trusts `request.shop`/`request.topic` to build the metadata delivered to the app's business logic:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [2](#0-1) 

Because `api_secret_key` (the `client_secret`) is a single value shared across **all** shops that install the app, any merchant who installs the app can obtain a validly-signed webhook (raw body + HMAC) for their own store by triggering an event (e.g., creating an order). Since the header carrying the shop domain is not part of the signed bytes, that merchant can replay the captured `raw_body`/HMAC pair directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header to name a victim shop. The HMAC still validates (it only checks the body), and `Registry.process` passes the attacker-chosen `shop` value through to `WebhookMetadata`, which the host application's handler treats as authenticated per the documented contract ("`shop`, `String` - The shop domain of the webhook").

### Impact Explanation
This crosses the tenant boundary the gem is meant to enforce: an unprivileged installer of the app (no `api_secret_key` access, no leaked credentials, no privileged account required) can inject webhook events attributed to a different (victim) shop. Because `shopify_app`-style host applications commonly use `data.shop` to select which tenant's records to update (see the documented pattern `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this enables cross-tenant data confusion/corruption. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any merchant who installs the app can trivially trigger a real webhook for their own shop and capture the raw body plus `X-Shopify-Hmac-Sha256` header (both visible to them as the endpoint operator's own traffic, or by simply causing an event and inspecting delivery logs on the receiving side, or by controlling the body content of, e.g., a custom app or a webhook whose body they influence). No secret material or privileged access is needed — only the ability to receive/observe one legitimately signed webhook and replay it with a forged shop-domain header to the same public endpoint.

### Recommendation
Include the shop domain (and topic) in the signed/verified material, or otherwise cryptographically bind them to the HMAC before trusting `request.shop`/`request.topic`. At minimum, host application guidance and this gem's `Registry.process` should not treat `request.shop` as authenticated; the library should either incorporate the header values into `to_signable_string`, or explicitly document/enforce that `data.shop` must be cross-checked against an out-of-band installation record (e.g., verify the shop is one that has an active session/access token on file) before being trusted as a tenant identifier.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers any registered webhook topic (e.g. `orders/create`), causing Shopify to POST a validly HMAC-signed body to the app's webhook endpoint using the app's single `client_secret`.
2. Attacker captures the raw request body and the `X-Shopify-Hmac-Sha256` header value from this legitimate delivery.
3. Attacker sends a new HTTP POST directly to the same public webhook endpoint with the identical raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this successfully (all required headers present), and `Utils::HmacValidator.validate` succeeds because it only checks the raw body against the shared secret — the shop-domain header was never covered by the signature (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` to the app's handler, which processes/attributes the (attacker-supplied) webhook body under the victim shop's identity.
