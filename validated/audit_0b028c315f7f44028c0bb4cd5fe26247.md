### Title
Webhook `shop` tenant identifier is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` verifies is computed only over the raw request body. Because the `shop` value is never part of the signed bytes, an attacker who possesses one valid `(body, hmac)` pair can replay it against the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the signature check will still pass. This breaks the identity binding `hmac(body) over shop == shop delivered to handler`, letting an attacker inject data that the host application will process as belonging to a victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 

`shop` is read straight from a header that is never part of what gets signed: [2](#0-1) 

`Registry.process` validates the HMAC over the body only and then forwards the header-derived `request.shop` directly to the app's handler as the trusted tenant key, with no additional binding check: [3](#0-2) 

Contrast this with the OAuth callback path, where `shop` *is* explicitly included in the signed payload and therefore cryptographically bound to the request: [4](#0-3) 

So in OAuth, the equality `hmac_signed(shop) == shop_used_for_token_exchange` holds. In the webhook path, that equality does not hold: `hmac_signed(body only) != shop_used_by(handler.handle(... shop: request.shop ...))`. Any two requests with the same body but different `shop-domain` headers produce the identical valid signature, so the signature carries no proof about which shop the payload is really for.

### Impact Explanation
An attacker who can obtain one legitimate `(raw_body, hmac)` pair — trivially achievable by installing the app on their own development/trial store and capturing a real webhook delivery, or even by simply reusing a previously delivered webhook to their own shop — can replay that exact body/HMAC combination to the target app's webhook endpoint while setting the `shopify-shop-domain` header to a victim merchant's domain. `Utils::HmacValidator.validate(request)` will accept it because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim>`. Any host application logic that uses this `shop` value to key database writes, trigger tenant-specific side effects, or otherwise act on behalf of "the shop that sent this webhook" will act on forged, attacker-chosen data attributed to a shop the attacker does not control — a cross-tenant data-integrity violation reachable by any unprivileged internet user with app access to at least one shop.

### Likelihood Explanation
The precondition (having valid credentials/relationship for *some* shop, e.g. a free development store) is low-cost and readily available to any developer, matching the "unprivileged internet user" threat model. No `api_secret_key`, access token, or privileged Shopify account access is required — only the ability to install the app once on an attacker-controlled store to harvest a legitimately-signed body/HMAC pair, then replay it with a forged header at the shared webhook endpoint.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material verified for webhooks, or otherwise cryptographically tie the header-derived shop to the payload before trusting it (e.g., include the shop-domain header in `to_signable_string`, or require the host application to independently confirm that `shop` corresponds to a session/shop it has actually installed for this exact webhook delivery). At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be treated as tenant-trusted without an independent lookup against known installed shops.

### Proof of Concept
1. Install the target app on an attacker-owned development store `attacker.myshopify.com`; trigger any webhook topic the app subscribes to and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Replay that exact body to the app's webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` (called from `Registry.process`, `lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only hashes `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`).
4. The app's registered handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker-controlled body>, ...)` and processes it as authentic data belonging to `victim.myshopify.com`.
