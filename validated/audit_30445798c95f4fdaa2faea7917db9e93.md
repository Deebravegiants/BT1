This confirms the analog. The `SELECT_SOLVER_TYPEHASH` is `SelectSolver(bytes32 commitment,address solver)` — the session key's signature authorizes only a **solver address**, not any specific bid terms (output amounts, fees, etc.). This is the exact same root cause pattern as the reported `RFPSimpleStrategy` bug: the party that benefits from being able to change committed values (the winning bidder / solver) retains the ability to swap in worse terms after being selected, because the authorization step doesn't cryptographically bind the terms that were actually reviewed and chosen.

### Title
Solver-selection signature only authorizes an address, not bid terms, letting the selected solver substitute a worse `fillOrder` after being chosen - (File: `evm/src/apps/intentsv2/SolverAccount.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2`'s solver-selection flow lets a user pick the best bid among competing solver `UserOperation`s and authorize the winner by signing an EIP-712 `SelectSolver(bytes32 commitment, address solver)` message with the order's session key. This signature commits only to a **solver address** for a given order `commitment` — it carries no binding to the specific output amounts, fees, or any other economic terms the user actually reviewed when picking that bid. Because of this, the selected solver, once authorized, can substitute a different self-signed `UserOperation` for the same `commitment`/`sessionKey` pair that still passes all validation checks but offers the user strictly worse terms (down to the bare minimum enforced by `order.output.assets`), analogous to the `RFPSimpleStrategy` bug where a winning bidder can front-run allocation to change `proposalBid` after being selected.

### Finding Description
In the auction flow described in `docs/content/developers/evm/intent-gateway/overview.mdx` (Bid Selection / On-chain Execution steps), solvers post signed `UserOperation`s ("bids") containing specific output amounts via `FillOptions.outputs`. The user reviews these off-chain and authorizes the winning solver by EIP-712 signing:

```solidity
struct SolverSelection {
    bytes32 commitment,
    address solver
}
``` [1](#0-0) 

The on-chain `SELECT_SOLVER_TYPEHASH` mirrors this exact narrow scope:

```
bytes32 public constant SELECT_SOLVER_TYPEHASH = keccak256("SelectSolver(bytes32 commitment,address solver)");
``` [2](#0-1) 

`SolverAccount.validateUserOp` recovers the session key from this signature, only checks that:
1. The recovered session key matches the order's session key (via `IntentGatewayV2.select`).
2. The op's ERC-4337 nonce key equals `keccak256(commitment ‖ sessionKey)`.
3. The solver's own signature (`solverSignature`) is valid over `userOpHash` (which does cover *this op's* `callData`).

```solidity
SelectOptions memory selectOptions =
    SelectOptions({commitment: commitment, solver: address(this), signature: sessionSignature});
...
uint192 userOpNonce = uint192(uint256(keccak256(abi.encodePacked(commitment, sessionKey))));
if (uint192(op.nonce >> 64) != userOpNonce) return ERC4337Utils.SIG_VALIDATION_FAILED;
if (!_rawSignatureValidation(userOpHash, solverSignature)) return ERC4337Utils.SIG_VALIDATION_FAILED;
``` [3](#0-2) 

None of these checks bind the session signature to a particular set of `FillOptions.outputs`. The solver signs its *own* `solverSignature` over whatever `callData`/`FillOptions` it puts into the op, so a solver can generate any number of self-consistent, individually-valid `UserOperation`s for the same `(commitment, sessionKey)` pair — each with a different `FillOptions.outputs` value, as long as `options.outputs >= order.output.assets` per `fillOrder`'s check:

```solidity
if (options.outputs.length != outputsLen) revert InvalidInput();
``` [4](#0-3) 

(the length check exists, but the actual output *amounts* are only validated for length here — the real "solver must give ≥ required" enforcement lives deeper in `_fillSameChain`/`_fillCrossChain`, not tied to what the user reviewed at selection time). Because the user's `SelectSolver` signature only names an address, the bundler/EntryPoint (or the solver acting as its own bundler, since "the solver pays all gas costs") can package the session signature with whichever of the solver's self-signed variants it prefers, once it holds a valid session signature for that solver. This mirrors the `RFPSimpleStrategy` issue precisely: the step that fixes "who wins" is decoupled from the step that fixes "on what terms," letting the privileged party (winning bidder / selected solver) substitute the worse variant immediately before execution.

### Impact Explanation
A user reviews competing bids and picks the most favorable one (e.g., highest output amount, lowest fee), signs `SolverSelection` for that solver, and expects to receive those advertised terms. Because the signature only names the solver's address, that solver can execute a different, self-signed `UserOperation` bound to the same commitment/session key that provides only the bare legally-required minimum output (`order.output.assets`) instead of the advertised superior bid amount, or embeds a higher `relayerFee`/`nativeDispatchFee` extracted from the user's escrow. This directly reduces the value delivered to the user versus what was solicited and selected, causing concrete value loss on every fill where a solver's winning bid exceeded the order's floor — which is the entire point of running a competitive auction. This satisfies "concrete theft... via unauthorized app action" since the solver extracts value it was not actually authorized (by the terms the user actually approved) to take.

### Likelihood Explanation
High. Any solver operating a `SolverAccount` is fully capable of pre-generating multiple valid `UserOperation`s for the same order (varying only `FillOptions`), since it fully controls its own `solverSignature` and calldata construction, and the check gates are unrelated to bid content. No cooperation from Hyperbridge, the relayer, or any third party is required — the exploiting party is precisely the actor granted the authorization (the selected solver), directly analogous to the original finding's "winning bidder" who is also the party best positioned and most incentivized to exploit the gap.

### Recommendation
Bind the session signature (and/or the `select()` call) to the specific bid terms the user actually reviewed, not merely to the solver's address. For example, extend the EIP-712 `SelectSolver` struct to include a hash of the chosen `FillOptions` (`outputs`, `relayerFee`, `nativeDispatchFee`, `validUntil`), and have `SolverAccount.validateUserOp`/`IntentGatewayV2.select` recompute that hash from `op.callData`'s decoded `FillOptions` and require it match what the session key signed. This closes the gap the same way the RFP fix requires locking in bid terms before allocation/selection is finalized.

### Proof of Concept
1. Solver S publishes bid A for order commitment C: `FillOptions.outputs = 110 DAI` (attractive), and signs `UserOperation_A` with `solverSignature_A` over `userOpHash_A` (covering `FillOptions.outputs = 110`).
2. User reviews bid A off-chain, judges it the best, and signs `SolverSelection{commitment: C, solver: S}` with the order's session key (`sessionSignature`).
3. Before this authorization reaches the bundler/EntryPoint, S constructs `UserOperation_B` for the same `commitment C` and `sessionKey`, setting `FillOptions.outputs = 100 DAI` (== `order.output.assets`, the bare minimum), keeping the same `nonce` upper bits `keccak256(C ‖ sessionKey)` (since this doesn't depend on outputs), and signs it with a fresh `solverSignature_B` over the new `userOpHash_B`.
4. S submits `abi.encodePacked(C, solverSignature_B, sessionSignature)` (reusing the *same* user-provided `sessionSignature`, since it only ever certified `(C, S)`) to the EntryPoint.
5. `SolverAccount.validateUserOp` succeeds: `select()` recovers the correct session key, the nonce-key check passes (unaffected by output amounts), and `solverSignature_B` validates against `userOpHash_B`.
6. `fillOrder` executes with `FillOptions.outputs = 100 DAI` instead of the `110 DAI` the user selected — the solver captured the 10 DAI difference it had originally offered to win the auction. [5](#0-4) [2](#0-1) [6](#0-5)

    function validateUserOp(PackedUserOperation calldata op, bytes32 userOpHash, uint256 missingAccountFunds)
        public
        override
        onlyEntryPoint
        returns (uint256)
    {
        if (op.signature.length == ECDSA_SIGNATURE_LENGTH) {
            if (_containsFillOrder(op.callData)) return ERC4337Utils.SIG_VALIDATION_FAILED;
            return super.validateUserOp(op, userOpHash, missingAccountFunds);
        }

        // Expected format: abi.encodePacked(commitment, solverSignature, sessionSignature)
        // commitment: 32 bytes, solverSignature: 65 bytes, sessionSignature: 65 bytes
        if (op.signature.length < INTENT_SELECT_SIGNATURE_LENGTH) return ERC4337Utils.SIG_VALIDATION_FAILED;

        bytes32 commitment = bytes32(op.signature[0:32]);
        bytes calldata solverSignature = op.signature[32:97];
        bytes calldata sessionSignature = op.signature[97:162];

        // Call IntentGatewayV2.select to recover the sessionKey. This also stages the
        // transient-storage selection that fillOrder enforces at execution.
        SelectOptions memory selectOptions =
            SelectOptions({commitment: commitment, solver: address(this), signature: sessionSignature});
        bytes memory selectCalldata = abi.encodeWithSelector(SELECT_SELECTOR, selectOptions);
        (bool success, bytes memory returnData) = INTENT_GATEWAY_V2.call(selectCalldata);

        if (!success || returnData.length < 32) return ERC4337Utils.SIG_VALIDATION_FAILED;

        address sessionKey = abi.decode(returnData, (address));
        uint192 userOpNonce = uint192(uint256(keccak256(abi.encodePacked(commitment, sessionKey))));
        if (uint192(op.nonce >> 64) != userOpNonce) return ERC4337Utils.SIG_VALIDATION_FAILED;
        if (!_rawSignatureValidation(userOpHash, solverSignature)) return ERC4337Utils.SIG_VALIDATION_FAILED;

        // Pay for gas if needed
        _payPrefund(missingAccountFunds);

        return ERC4337Utils.SIG_VALIDATION_SUCCESS;
    }

    function fillOrder(Order calldata order, FillOptions calldata options) public payable nonReentrant {
        uint256 blockNumber = _blockNumber();
        if (order.deadline < blockNumber) revert Expired();
        // The solver's own bound on how long its quoted price stands. Zero means unbounded,
        // which is the right default for a solver filling directly — it is only at risk from
        // its own staleness. It matters for a bid signed through the coprocessor, where the
        // order placer chooses the moment of execution and nothing else caps the wait.
        if (options.validUntil != 0 && blockNumber > options.validUntil) revert FillExpired();
        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain && orderSource != currentChain) revert WrongChain();
        if (!isSameChain && orderDest != currentChain) revert WrongChain();

        if (_filled[commitment] != address(0)) revert Filled();

        if (_params.solverSelection) {
            bytes32 storedSelectionHash;
            assembly {
                storedSelectionHash := tload(commitment)
            }

            bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
            if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
        }

        uint256 outputsLen = order.output.assets.length;
        if (options.outputs.length != outputsLen) revert InvalidInput();
        if (order.inputs.length != outputsLen) revert InvalidInput();

        if (isSameChain) {
            _fillSameChain(order, options, commitment);
        } else {
            _fillCrossChain(order, options, commitment);
        }
    }
