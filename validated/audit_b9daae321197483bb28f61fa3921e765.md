### Title
Gas-to-fee-token fallback conversion assumes the fee token is worth $1, breaking fee estimation for any non-stablecoin fee token - (File: `sdk/packages/sdk/src/protocols/intents/utils.ts`)

### Summary
The Sherlock report describes `ChainlinkAdapterOracle` being unable to price wstETH because the oracle model only supports single, directly-quoted assets, silently breaking any strategy built on that asset. The same class of bug — a price-conversion routine that hard-codes an assumption valid only for one specific class of asset (USD stables) — exists in Hyperbridge's cross-chain intents fee-conversion path.

### Finding Description
`convertGasToFeeToken` and its inverse `convertFeeTokenToWei` are used to translate a gas estimate into the chain's configured ISMP/IntentGateway fee token, and vice versa, for every cross-chain order fee and relayer-fee calculation. The primary pricing path quotes through Uniswap V2 (`ctx.swap.findBestProtocolWithAmountIn`), but on any failure or a zero-amount quote (thin liquidity, no pool, RPC hiccup) both functions fall back to: [1](#0-0) 

```
} catch {
    const nativeCurrency = client.chain?.nativeCurrency
    ...
    const feeTokenPriceUsd = new Decimal(1)
    const gasCostInFeeToken = gasCostUsd.dividedBy(feeTokenPriceUsd)
```

This fallback unconditionally treats the fee token as pegged 1:1 to USD, exactly like `ChainlinkAdapterOracle` unconditionally treating every asset as directly quotable against USD. There is no check that the configured `feeToken` for a given chain is actually a USD stablecoin. The docstring itself admits the assumption: [2](#0-1) 

The same $1 assumption is repeated in the inverse direction (`convertFeeTokenToWei`), used to size cross-chain cancellation/relayer fees. [3](#0-2) 

`convertGasToFeeToken` feeds directly into the fee actually attached to a cross-chain order (`GasEstimator.estimateFillOrder` and `estimateCrossChainFees`, which computes `order.fees`/`relayerFeeInSourceFeeToken` used by `IntentGateway.quoteOrderFees`/`execute()`), so a wrong price here directly determines the relayer fee paid out of escrow for message delivery. [4](#0-3) 

### Impact Explanation
If a deployment's fee token is not a USD stable (e.g. a wrapped/staking-derivative or any volatile asset configured as the ISMP fee token on a given chain) and the Uniswap V2 quote path is unavailable (thin/absent liquidity — the same condition the original report calls out as "dangerous" for wstETH), the fallback silently mispirces gas cost by the true USD value of the fee token vs. $1:
- If the fee token is worth materially less than $1, the relayer fee computed is far too small, so the actual on-chain relayer that must deliver the cross-chain `RedeemEscrow`/settlement POST is underpaid and has no economic incentive to relay it — the order's escrow can become permanently stuck (a route unable to deliver messages), mirroring the "protocol is non-functional in this area" reasoning that made the original wstETH issue a valid Medium.
- If the fee token is worth materially more than $1, users/solvers are overcharged, though this direction is less severe.

This is a functional-break/fund-freezing risk on the relayer-fee accounting path reachable by any order placer or solver, not a privileged-actor bug.

### Likelihood Explanation
Triggering requires: (1) a chain configured with a non-$1-pegged fee token, and (2) the Uniswap V2 route for that token being unavailable or thin enough to revert/return zero — a realistic condition for any newly-added or low-liquidity fee token, exactly the scenario the original report flags for wstETH-class assets. No malicious actor is needed; it degrades naturally as soon as a non-stable fee token is deployed.

### Recommendation
Do not hard-code `feeTokenPriceUsd = 1`. Either require an explicit price oracle mapping per fee token (with staleness/sanity checks, similar to how Chainlink adapters should special-case derivative assets), or fail closed (revert / skip fee-token conversion) when the Uniswap quote is unavailable rather than silently substituting an incorrect USD peg. At minimum, gate the $1 fallback behind an explicit "is-stablecoin" flag in `ChainConfigService` so it only applies to fee tokens actually pegged to USD.

### Proof of Concept
1. Configure a chain's ISMP fee token to a non-USD-pegged asset (e.g. an LST/derivative token) with no/thin WETH↔feeToken Uniswap V2 pool.
2. Call `GasEstimator.estimateFillOrder` for a cross-chain order on that chain; internally `estimateCrossChainFees` → `convertGasToFeeToken` is invoked.
3. The Uniswap quote call throws or returns `amountOut == 0n`, driving execution into the `catch` block at `sdk/packages/sdk/src/protocols/intents/utils.ts:205-214`, which computes `gasCostInFeeToken` assuming `feeTokenPriceUsd = 1`.
4. Because the fee token's real USD value differs from $1, the resulting `order.fees`/`relayerFeeInSourceFeeToken` is wrong by that ratio; a sufficiently below-market relayer fee leaves the destination-to-source settlement message with no profitable relayer, stalling escrow redemption indefinitely.
