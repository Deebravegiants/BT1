### Title
`removeChain()` in `HyperFungibleToken`/`HyperFungibleTokenUpgradeable` freezes already-burned tokens for in-flight, zero-timeout transfers - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`removeChain()` deletes a peer's `_supportedChains[chainId]` entry without checking whether there are any in-flight cross-chain transfers still targeting (or originating from) that chain. This mirrors the referenced Tapioca finding where `unregisterSingularity()` deletes registry state without verifying `totalDeposited == 0`, permanently locking positions that depended on that entry.

### Finding Description
`send()` burns the caller's tokens synchronously and then dispatches a `PostRequest` to the destination chain via the configured `IDispatcher`/`EvmHost`. The burn happens up front, before the message is ever delivered: [6](#0-5) 

The only way the sender recovers these tokens if delivery never succeeds is `onPostRequestTimeout`, which re-mints the burned amount back to the original sender — but this callback is only ever invoked by the ISMP host after the request's `timeoutTimestamp` has elapsed: [7](#0-6) 

Per the protocol's own documentation and `Message.timeout()`, a `timeout` of `0` means "no timeout" — the message is normalized to `type(uint64).max` and will never expire: [1](#0-0) [2](#0-1) 

Meanwhile, `onAccept()` on the destination side unconditionally reverts with `UnsupportedChain` if the source chain's entry has been removed: [8](#0-7) 

and `removeChain()` performs this deletion with no check for outstanding/in-flight requests still addressed to or from that chain: [5](#0-4) 

If the owner calls `removeChain()` for a peer while transfers dispatched with `timeout=0` are still in flight to (or from) that chain, every delivery attempt for those requests will permanently revert at `onAccept` (`UnsupportedChain`), and since the request never times out, `onPostRequestTimeout` can never fire either. The already-burned tokens on the source side are stuck: neither minted on the destination nor refunded on the source. Unlike a simple config change, there is no code path that can recover funds for these specific pending zero-timeout requests once the peer entry backing them has been removed while they're outstanding — the only mitigation is the owner re-adding the exact same `chainId → moduleId` mapping before any relayer submission is attempted, which is not something the protocol enforces or verifies before allowing removal. The same pattern exists in `HyperFungibleTokenUpgradeable.sol` (`removeChain` at lines 237-239) and any subclass built on this base (`WrappedHyperFungibleToken.sol` / `WrappedHyperFungibleTokenUpgradeable.sol`).

### Impact Explanation
Tokens burned via `send()` for a zero-timeout transfer become permanently unrecoverable if the destination chain's registration is removed before the message is delivered: they cannot be minted (destination rejects with `UnsupportedChain`) and cannot be refunded (no timeout ever elapses). This is a concrete, permanent freezing of user funds reachable by any unprivileged user simply calling `send()` — the vulnerability is triggered by ordinary (non-malicious) governance/administration of the bridge deployment failing to account for in-flight transfers, exactly analogous to the referenced report where `unregisterSingularity()` was a legitimate maintenance action that neglected to check `totalDeposited`.

### Likelihood Explanation
Likelihood is moderate: `removeChain()` is a documented, intended maintenance operation ("Transfers to/from this chain will revert after removal") that project operators are expected to use when deprecating or migrating peer deployments. Any transfer dispatched with `timeout=0` — which the docs explicitly describe as a supported, normal usage pattern for self-relayed or trust-based integrations — that is still in flight at the moment of removal is affected. There is no on-chain safeguard (e.g., checking a pending-request counter, or requiring a timeout window before removal) to prevent this.

### Recommendation
Before deleting `_supportedChains[chainId]` in `removeChain()`, require either: (1) a bookkeeping mechanism (e.g., a per-chain pending-request counter incremented in `send()`/`_buildDispatchPost()` and decremented on successful delivery ack or timeout) that must be zero before removal is permitted, similar to the recommended `require(activeSingularities[singularity].totalDeposited == 0)` check in the referenced report; or (2) disallow `timeout=0` for `send()` entirely so every dispatched transfer is guaranteed a timeout-based refund path regardless of subsequent `removeChain()` calls; or (3) enforce a mandatory delay/quarantine period on `removeChain()` at least as long as the maximum allowed timeout, so all pending zero-timeout-adjacent requests can be drained first.

### Proof of Concept
1. Owner configures chain B as a supported peer via `addChain(chainB, moduleIdB)`.
2. Alice calls `send({dest: chainB, to: bob, amount: 100, timeout: 0, ...})`. Her 100 tokens are burned immediately (`_burn(msg.sender, params.amount)`), and a `PostRequest` with `timeoutTimestamp = 0` is dispatched.
3. Before the relayer delivers the request to chain B, the owner of the chain-B deployment calls `removeChain(chainA)` to deprecate the source chain (e.g., due to a security incident or migration), deleting `_supportedChains[chainA]`.
4. The relayer submits the pending request to chain B; `onAccept()` reverts with `UnsupportedChain` because `_supportedChains[request.source]` is now empty.
5. Because `timeoutTimestamp == 0` normalizes to `type(uint64).max` (`Message.timeout()`), the request can never be proven timed out via `handlePostRequestTimeouts`, so `onPostRequestTimeout` on chain A is never invoked and Alice's 100 tokens are never re-minted.
6. Alice's 100 tokens are permanently lost — burned on chain A, never minted on chain B, never refunded.

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
