### Title
Silently discarded MCU error acknowledgements allow signup-critical hardware commands to be treated as successful - (File: `src/mcu/can.rs`)

### Summary
The `swap-router` report describes a class of bug where a failure is detected and logged but no corrective action is taken, leaving the system in an inconsistent state that the caller believes succeeded. The same bug class exists in orb-core's CAN MCU transport layer: when the microcontroller returns an acknowledgement carrying a non-`Success` error code, the code logs the error but does not propagate it, so the caller receives `Ok(())` as if the command had succeeded.

### Finding Description
In `Can::<I>::handle_input` [1](#0-0) , the completion result defaults to `Ok(())` and is only overwritten with an `Err` in the timeout branch: [2](#0-1) 

When the MCU responds with a recognized error code, or an unrecognized/incompatible error code, the code only calls `tracing::error!` — the lines that would set `completion_result = Err(...)` are commented out with the explicit acknowledgement `// TODO: return Error on MCU Errors and add better Error handling for the callers (f.e. on arguments out of range)`. The still-`Ok(())` `completion_result` is then sent back to the caller via `completion_tx.send(completion_result)` [3](#0-2) .

This propagates upward into `Mcu::send`, which relies on `completion_rx.await?` returning `Err` to trigger its retry logic [4](#0-3) . Because a real MCU-reported failure is masked as success, no retry occurs and the caller proceeds under the false assumption that the hardware command it issued (e.g. mirror positioning, cone/IR illumination sequencing, focus, or other MCU-mediated actions used during biometric capture) was actually executed and acknowledged correctly by the MCU.

### Impact Explanation
Biometric capture (`src/plans/biometric_capture/mod.rs`, `mirror_sweep.rs`, `focus_sweep.rs`, etc.) issues MCU commands that control physical capture conditions (mirror sweep, focus/illumination timing) which are relied upon to obtain a genuine, correctly-conditioned iris/face capture. If the MCU rejects one of these commands (out-of-range argument, unexpected state, etc.) but the orb-core caller is told it succeeded, capture proceeds on the assumption that hardware state matches the commanded state. This is analogous to the swap-router issue: an operation silently fails, the failure is not surfaced or compensated for, and downstream logic continues as though everything completed correctly — creating an unverified/inconsistent state that could affect the integrity of the capture pipeline feeding into signup and enrollment decisions.

### Likelihood Explanation
This code path executes on every MCU command sent over CAN whenever the MCU returns an error acknowledgement, which is a normal (if uncommon) hardware condition rather than a crafted attack — no privileged access or malicious peer is required to trigger it; it is a defect in the error-handling logic itself, matching the report's root cause (log-only error handling with no corrective action).

### Recommendation
Restore and complete the commented-out error propagation in `handle_input`: set `completion_result = Err(...)` for both the recognized MCU-error and unknown-error-code branches, as the existing TODO comment states, so that `Mcu::send`'s retry/abort logic is correctly triggered. Callers that depend on MCU command success (mirror, focus, illumination control used during biometric capture) should treat this as a hard failure and abort/retry rather than silently continuing.

### Proof of Concept
Not independently reproducible from static analysis alone — the assessment is based on directly reading the commented-out error-propagation lines in `src/mcu/can.rs:122-136` and tracing how `completion_result` is consumed by `Mcu::send` in `src/mcu/mod.rs:87-109`. Exercising this in practice requires triggering an MCU-side error acknowledgement (e.g., a firmware-reported `ErrorCode` other than `Success`) during a live/hardware-in-the-loop CAN session, which is outside the scope of static repository review.

    fn send(&mut self, input: I::Input) -> Pin<Box<dyn Future<Output = Result<()>> + Send + '_>> {
        Box::pin(async move {
            let mut retries = SEND_RETRY_COUNT;
            'retry: loop {
                let (completion_tx, completion_rx) = oneshot::channel();
                self.tx_mut().send((input.clone(), Some(completion_tx))).await?;
                if let Err(error) = completion_rx.await? {
                    if retries > 0 {
                        tracing::warn!("Retrying last µC message... [{}]", retries);
                        retries -= 1;
                        continue 'retry;
                    }
                    tracing::error!("Maximum µC send retries reached, aborting with Error");
                    return Err(error);
                };
                break 'retry;
            }
            if let Some(log) = self.log_mut() {
                I::log_input(log, &input);
            }
            Ok(())
        })
    }
