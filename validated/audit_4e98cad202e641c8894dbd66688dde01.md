Webhook HMAC does not bind the `shop-domain` header, allowing shop-identity spoofing in delivered webhooks - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by HMAC-validating the raw request body, then trusts the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header as the tenant identity passed to the host application's handler. The HMAC signature never covers this header, so the "shop that was authenticated" (implicitly, "the sender of a validly HMAC-signed body") and the "shop the handler is told to act on" are not the same value bound cryptographically — breaking the equality `authenticated_shop == header_shop`.

### Finding Description
`Utils::VerifiableQuery`-based validation in `Utils::HmacValidator.validate` computes and compares an HMAC only over `request.to_signable_string`, which for webhooks is defined as: [1](#0-0) 

This returns only `@raw_body`. Meanwhile, `shop` is read directly from an HTTP header, independent of the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC over the body and, if valid, immediately forwards `request.shop` (i.e., the header value, never covered by the signature) to the host app's webhook handler as trusted tenant metadata: [3](#0-2) 

Because the app's `client_secret`/`api_secret_key` signs only the JSON body, any party who can produce a body whose HMAC matches (e.g., a legitimate webhook for the app's own installed shop, or any body an attacker fully controls together with the ability to compute a valid HMAC using a compromised/leaked secret) could pair that valid `(body, hmac)` pair with an arbitrary `shopify-shop-domain` header value. The `Request` constructor performs no check that the declared `shop` corresponds to the shop that actually owns the signed payload; there's no shop-domain-format check comparable to `Utils::ShopValidator` applied here at all.

This matches the report's bug class: "a field acted on but not covered by the HMAC" — the `shop` identity field drives downstream tenant-scoped handling (e.g. `shop/redact`, `customers/redact`, `customers/data_request` mandatory topics, or app-defined handlers keyed by shop) but is excluded from the integrity check.

### Impact Explanation
If a host application's webhook handler trusts `WebhookMetadata#shop` to select or scope which merchant's data record to modify/delete/query (a common pattern, especially for the mandatory GDPR topics `customers/redact`, `shop/redact`, `customers/data_request`), an attacker who can get any validly-signed webhook body accepted (for instance by replaying/reusing a webhook they legitimately receive for their own shop, or if the shared secret is otherwise available to them for constructing bodies) can cause the handler to execute with a spoofed `shop` value pointing at a different tenant, causing cross-tenant data leakage or a cross-tenant data-deletion / redaction action — a cross-tenant access impact.

### Likelihood Explanation
Exploitability is bounded by needing a `(body, valid hmac)` pair, and normally the shared secret is only known to Shopify and the app. This significantly limits practical exploitation to scenarios where an app receives/replays its own webhooks or the body space allows attacker influence while HMAC still matches (unlikely without the secret). This keeps likelihood low/moderate rather than trivially exploitable by an anonymous internet user, but the root cause — the identity field being outside the integrity envelope entirely — is a genuine design gap in the gem's own verification logic, distinct from any host-application misuse.

### Recommendation
Include the shop/tenant identity (and ideally the topic and webhook id) as part of the HMAC-covered payload check, or require the caller to supply the expected shop and assert `request.shop == expected_shop` before calling the handler in `Registry.process`. At minimum, document clearly that `request.shop` is unauthenticated and must not be used as the sole tenant-scoping key without corroboration from `session`/API lookups.

### Proof of Concept
1. Attacker (or a party who has previously received a legitimately-signed webhook body B, e.g., a `themes/publish` webhook for their own installed shop) captures `(B, HMAC(secret, B))`.
2. Attacker replays a POST to the app's webhook endpoint with body `B`, its original valid `shopify-hmac-sha256` header, but a modified `shopify-shop-domain` header value naming a different, victim shop.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body since only the `hmac-sha256`, `topic`, `shop-domain` headers presence is checked [4](#0-3) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the HMAC [5](#0-4) .
5. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with the attacker-chosen `shop` value [6](#0-5) , causing the host handler to act on the wrong tenant if it trusts this field.
