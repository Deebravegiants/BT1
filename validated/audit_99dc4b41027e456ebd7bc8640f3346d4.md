### Title
Emporium wallet signature never binds `feeStructure.feeToken`/`relay`, letting an unprivileged relay redirect an arbitrary token to itself under a signed `maxFee` value - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`verifyWallet` recovers the wallet owner's EIP-712 signature over only `(emporiumMessage, opsHash, maxFee, deadline)`, but `payRelayFees` uses `circomData.feeStructure.feeToken` and `circomData.relay` — both fully attacker-controlled, unsigned fields — to pull tokens straight out of the signer's wallet via `IHinkalWallet.doSendToRelay`. Because `maxFee` is a bare numeric bound with no token/unit binding, an attacker who crafts `CircomData` can attach a valid, previously-observed signature to a `feeStructure.feeToken` the signer never contemplated and route the pulled funds to an arbitrary `relay` address.

### Finding Description
The equality that should hold is: *(token, amount, destination) of any fee pulled from the wallet == what the owner's EIP-712 signature authorised*. Tracing `verifyWallet` in `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol` (lines 302-349):

```

        stack.maxFee,
        stack.deadline

);
...

``` [1](#0-0) 

Only `flatFee` is checked against `maxFee`; `circomData.feeStructure.feeToken`, `feeStructure.variableRate`, and `circomData.relay` are never included in the signed digest and never checked against anything the ops imply. `runAction` calls `verifyWallet(stack, circomData)` and then `payRelayFees(circomData, stack.signerAddress, deltaAmountChanges)`: [2](#0-1) 

In `payRelayFees`, when the signer's fee token is not among `circomData.erc20TokenAddresses` (i.e. unrelated to the actual ops), the fallback branch still moves `feeStructure.flatFee` of `feeStructure.feeToken` straight from the wallet to `circomData.relay`:
```

    require(signerAddress != address(0), "Gas Token in Emporium is not found");
    payRelay(circomData.relay, signerAddress, feeStructure.flatFee, feeStructure.feeToken);
}
``` [3](#0-2) 

which ultimately calls `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)` via `sendToRelayFromWallet`: [4](#0-3) 

Since the attacker (acting as the transaction submitter) fully controls `CircomData.feeStructure` and `CircomData.relay` per the threat model, they can take any validly signed `EmporiumStack` (same `emporiumMessage`, `ops` hash, `maxFee`, `deadline` — nothing about token/relay is bound) and re-present it with:
- `feeStructure.feeToken` = a valuable token held by the wallet that has nothing to do with the signed `ops` (e.g., WBTC/WETH instead of the low-value token the signer assumed),
- `feeStructure.flatFee` = `stack.maxFee` (the numeric cap, satisfied regardless of which token it denominates),
- `circomData.relay` = attacker's own address.

The only guard, `flatFee > maxFee` revert, is purely numeric and token-agnostic, so a `maxFee` the signer thought was denominated in a cheap/low-decimal token is silently reinterpreted in a different, more valuable token, and the resulting amount is sent to a relay address the signer never approved. `onlyAllowedRecipient` and `nonReentrant` (in `ExternalActionBaseUpgradeable`) do not constrain `feeToken`/`relay` selection, and the nullifier/root/proof machinery is not engaged for this wallet-fee path (`signerAddress != address(0)` skips proof-bound circuit checks on this token choice entirely — the wallet call is authorized purely by the EIP-712 signature, not by the ZK proof's public inputs).

### Impact Explanation
An attacker relay can drain protocol-fee-labeled but attacker-chosen tokens directly from a wallet owner's `IHinkalWallet` contract to an address of their choosing, up to the *numeric* `maxFee` value the owner signed, but under a token denomination the owner never selected. This is theft of wallet-held funds routed to an unauthorised destination (the attacker's own "relay") that the owner's EIP-712 signature never actually authorised for that token/destination combination — matching the High severity category "executing calls or moving assets a wallet owner ... never authorised" (and can reach Critical-adjacent value depending on token chosen, since the amount is capped only numerically, not by value). The attack is repeatable for every distinct `emporiumMessage` the attacker can observe or induce a signature for, as long as `usedMessages[emporiumMessage]` hasn't been consumed yet.

### Likelihood Explanation
Preconditions: the attacker must be the party constructing/submitting `CircomData` for a `runAction` call with `stack.signerAddress != address(0)` (a stateful wallet-authorized Emporium call) using a signature they possess (e.g., relayed on behalf of a user, or a leaked/observed signed stack that hasn't been consumed via `usedMessages`). No special role is required — `runAction` is reachable by anyone acting as the allowed recipient/relay path through `Hinkal.transact`. The wallet must hold the attacker-targeted token. This does not depend on Merkle tree state, leaf count, or `roots[MINIMUM_INDEX]`; the questioned "tree has exactly one prior leaf" condition is not applicable here — `verifyWallet`/`payRelayFees` involve no Merkle root or tree-index logic at all, so that part of the question does not correspond to any real code path in this contract.

### Recommendation
Include `feeStructure.feeToken`, `feeStructure.variableRate`/`flatFee` semantics, and `circomData.relay` (or at least an allow-list commitment for the fee token and relay) inside the EIP-712 typed data signed by the wallet owner in `verifyWallet`, so `maxFee` is unambiguously bound to a specific token and the relay destination is authorised by the signer, not chosen freely by whoever submits the transaction.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a mock `IHinkalWallet`, and two ERC20 tokens: `OpToken` (used in the signed `ops`) and `ValuableToken` (unrelated, held by the wallet).
2. Wallet owner signs an `EmporiumStack` with `ops` referencing only `OpToken`, `maxFee = 1000`, some `deadline`.
3. Attacker calls `runAction` with `CircomData.erc20TokenAddresses = [OpToken]` (so `ValuableToken` is not in the array, `foundToken = false`), `feeStructure.feeToken = ValuableToken`, `feeStructure.flatFee = 1000`, `circomData.relay = attacker`.
4. Assert: `verifyWallet` succeeds (no `FeeExceedsSignedMax` revert) even though the signer never mentioned `ValuableToken`.
5. Assert: wallet's `ValuableToken` balance decreases by 1000 and attacker's `relay` balance of `ValuableToken` increases by 1000 — i.e. `(token, amount, destination)` actually moved != anything present in `(ops, maxFee)` that the owner's signature covers, proving the broken equality.
