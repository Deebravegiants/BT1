Confirmed. Docs explicitly state: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook," implying the `shop` field is trusted as authenticated—but the HMAC only covers `raw_body`, not the `shop-domain`/`topic`/`webhook_id` headers.

### Title
Webhook `shop` (and `topic`/`webhook_id`) attribution is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by checking the HMAC over the raw body only, then unconditionally trusts the `shop`, `topic`, and `webhook_id` values pulled straight from HTTP headers to build the `WebhookMetadata` passed to the app's handler. Because the shared secret used to compute the HMAC is the same across every shop that installs the app, the signature never binds the request to a particular shop, topic, or webhook id.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `#hmac` is derived purely from the `hmac-sha256` header [2](#0-1) . The `shop`, `topic`, and `webhook_id` accessors read directly from headers with no cryptographic binding at all [3](#0-2) .

`Registry.process` validates only that HMAC and then builds `WebhookMetadata` straight from these unauthenticated header fields, handing it to the app's handler as trusted data: [4](#0-3) .

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the header value [5](#0-4) . For webhooks, `secret` is `Context.api_secret_key` — the app's single `client_secret`, identical for every shop that has the app installed. Consequently, `HMAC(secret, body)` for a webhook delivered to Shop A is bit-for-bit identical to what would be required for the same body attributed to Shop B, since the shop identity is never part of the signed material.

This breaks the intended identity binding:
`shop_authenticated_by_signature == shop_used_by_handler`

The left side is actually always `nil` (nothing about `shop`/`topic`/`webhook_id` is verified), while the right side is whatever an attacker puts in the `x-shopify-shop-domain` (or `shopify-shop-domain`), `x-shopify-topic`, and `x-shopify-webhook-id` headers.

### Impact Explanation
An unprivileged internet user who legitimately installs the app on their own shop will receive real webhook deliveries with valid HMACs (computed with the app's single shared `client_secret`). Because the signature covers only the JSON body, that same `(body, hmac)` pair remains valid if replayed to the app's webhook endpoint with the `shop-domain`, `topic`, or `webhook_id` headers swapped to point at a victim shop or a different topic. The gem-level `Registry.process` will accept it as authentic (`Utils::HmacValidator.validate(request)` passes) and hand the attacker-chosen `shop`/`topic`/`webhook_id` to the app's `WebhookHandler#handle`, which per the documented contract is expected to be a `shop` "that is has already stored a session for" [6](#0-5) . Any host application that keys off `data.shop` to select which merchant's data/session to act on (a pattern the gem's own docs encourage, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [7](#0-6) ) is exposed to cross-tenant confusion — a shop-A body processed and applied as if it belonged to shop B, or a body accepted under a fabricated `topic`/`webhook_id`, all without needing the app's `client_secret`, an access token, or any privileged credential; the attacker only needs to be a legitimate (or trial) installer of the app on one shop.

### Likelihood Explanation
Medium-High. Any developer/tenant of a multi-tenant app can capture one legitimate webhook delivery to their own shop (no privileged access, no interception required — they own that delivery) and then freely replay/modify the unsigned headers against the app's public webhook endpoint. The gem's `Registry.process`/`HmacValidator.validate` provide no defense against this because they never verify `shop`, `topic`, or `webhook_id`.

### Recommendation
Extend `VerifiableQuery#to_signable_string` for webhook requests to bind the header-derived identity fields (`shop`, `topic`, `webhook_id`) into the signed material, or otherwise document/enforce that host apps must independently verify the `shop`/`topic` against records associated with the specific `webhook_id`/subscription before trusting `WebhookMetadata#shop`. At minimum, `Registry.process` should cross check that the claimed `shop` corresponds to a shop that has an active registration/session for the claimed `topic`/`webhook_id`, rather than passing raw header values straight through to the handler as if HMAC-verified.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; trigger a real webhook (e.g., `orders/create`) and capture the raw POST body plus its `x-shopify-hmac-sha256` header — this signature is valid because it is `HMAC(app.client_secret, raw_body)`, and `client_secret` is shared across all installs, not scoped to `attacker.myshopify.com`.
2. Resend the identical body and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com` (and/or change `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [8](#0-7) , which passes because it only checks `HMAC(secret, raw_body)`.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built from the forged headers and delivered to the app's `handle` method as if it were an authentic webhook for `victim.myshopify.com` [9](#0-8) .

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
