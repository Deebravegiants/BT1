## Analog Found

### Title
Absolute `balanceOf(dispatcher)` accounting in `IntentGatewayV2.placeOrder` (Tron) enables escrow/dust manipulation via direct token donation to the shared CallDispatcher - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Sherlock report's root cause is using a raw, unguarded `token.balanceOf(contract)` read as the basis for a fund-accounting calculation, letting an attacker inflate that balance by donating tokens directly to the contract before the state-dependent calculation runs. The Tron variant of `IntentGatewayV2.placeOrder` reproduces exactly this pattern: it reads `IERC20(token).balanceOf(dispatcher)` as an absolute value to decide how much to sweep and how much "dust" was collected, instead of snapshotting the balance before the predispatch call and computing a delta, as the mainline EVM contract correctly does.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the predispatch escrow path computes: [1](#0-0) 

```
balance = IERC20(token).balanceOf(dispatcher);
if (balance < requiredAmount) revert InvalidInput();
transferCalls[i] = Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)});
...
uint256 dust = balance - requiredAmount;
if (dust > 0) emit DustCollected(token, dust);
_orders[commitment][token] += reducedInputs[i].amount;
```

`dispatcher` is `_params.dispatcher` — a shared `ICallDispatcher` contract used by every `placeOrder` call, not a fresh per-order deployment [2](#0-1) . Because `balance` is read as the dispatcher's *total* token balance rather than a before/after delta around the predispatch `dispatch()` call, anything sitting on the dispatcher — tokens directly donated by any external actor, or residual balance left over from another user's predispatch call that wasn't fully swept in the same block — is folded into `balance` and swept wholesale into the gateway, while the escrow credited to `_orders[commitment][token]` is fixed at the order's declared `reducedInputs[i].amount`, completely decoupled from what was actually transferred in.

This is a direct architectural regression relative to the corrected mainline EVM contract, `evm/src/apps/IntentGatewayV2.sol`, which snapshots `balancesBefore[i]` immediately prior to the predispatch call and computes `received = balanceOf(address(this)) - balancesBefore[i]` [3](#0-2) , correctly isolating what this specific call actually moved and treating any pre-existing/donated balance as protocol dust rather than folding it into escrow bookkeeping tied to an absolute read.

### Impact Explanation
Because the dispatcher is shared across all `placeOrder` calls system-wide, any unprivileged user (an intent placer) can call `placeOrder` with a predispatch call while the dispatcher happens to hold another party's tokens (from a concurrent/prior predispatch that left tokens unswept, or from a direct donation). The `balance < requiredAmount` check only enforces a lower bound — it never verifies that `balance` corresponds to tokens this order's predispatch call actually produced. The full balance is then swept into the gateway under this order's `transferCalls`, and the excess over `requiredAmount` is logged as "dust" and effectively absorbed by the gateway, while the party whose tokens were actually on the dispatcher loses them. This mirrors the reported bug class: fund accounting keyed off manipulable `balanceOf()` reads instead of tracked deltas, producing fund loss/fund misattribution for a genuine escrow.

### Likelihood Explanation
Reachable directly by any unprivileged caller of `placeOrder` with a nonzero `predispatch.call`/`predispatch.assets` — no privileged role required. Exploitability depends on the dispatcher holding a residual/attacker-donated balance at the moment `dispatch(transferCalls)` runs, which is plausible given the dispatcher is a shared, publicly-known contract address reused across all orders and reachable for a plain ERC-20 `transfer` from anyone.

### Recommendation
Mirror the mainline EVM contract's fix: snapshot `balanceOf(dispatcher)` (or `balanceOf(address(this))`) immediately before dispatching the predispatch call, then use the post-call delta (`balanceAfter - balanceBefore`) as the amount actually produced by this order's predispatch call, rather than reading `balanceOf(dispatcher)` as an absolute value. Do not sweep or emit dust based on an untracked absolute balance shared across unrelated orders.

### Proof of Concept
1. Dispatcher `D` is the single shared `_params.dispatcher` used by all `placeOrder` calls.
2. Attacker/other user directly `transfer()`s `X` tokens to `D` (or a prior order's predispatch call leaves residual tokens on `D` unswept within the same block).
3. Victim/attacker calls `placeOrder` with a predispatch call and `order.inputs[i].amount = requiredAmount` for that token.
4. The transfer-back loop reads `balance = IERC20(token).balanceOf(D)` which now includes the extra `X` tokens; passes the `balance >= requiredAmount` check trivially.
5. `transferCalls[i]` sweeps the *entire* `balance` (including the unrelated `X`) into the gateway.
6. `_orders[commitment][token] += reducedInputs[i].amount` only credits the order's own declared amount — the extra `X` tokens are absorbed as "dust" rather than returned to their rightful owner, causing fund loss to whoever's tokens were actually on the dispatcher.
