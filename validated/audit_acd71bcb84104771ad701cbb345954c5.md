### Title
Stale state-commitment-queue index causes premature eviction of a live, freshly-honest `StateCommitment` after a veto — (`File: modules/pallets/ismp/src/host.rs`)

### Summary
The CVE describes a use-after-free caused by an "inappropriate pointer order": `map_sub_` is freed/dereferenced after the object it points into (`map_`) has already been freed, so a stale reference is later acted upon as if it were still valid. The structural analog in Hyperbridge is in the ISMP state-commitment queue: `delete_state_commitment` in [1](#0-0)  removes a `StateMachineHeight -> StateCommitment` entry but deliberately leaves behind its stale index in the eviction queue (`StateCommitmentQueue` / `CommitmentQueueStates`), as the code comment itself documents. When the vetoed height is the latest height, the "reset" logic re-opens that height for honest resubmission, creating a second, live queue entry for the same height while the stale (already-consumed) index remains ahead of it in the queue. The stale index is a dangling reference to logical state that has already changed underneath it — the same "outdated pointer used against changed backing state" bug class as the CVE.

### Finding Description
`delete_state_commitment` removes `BoundedStateCommitments` and `BoundedStateMachineUpdateTime` at a vetoed height, and if that height was `LatestStateMachineHeight`, resets the latest pointer back to `PreviousStateMachineHeight` [2](#0-1) . It never touches the height's existing entry in the bounded eviction queue used by `insert_bounded_state_commitment`, explicitly to avoid the cost of scanning the queue [3](#0-2) .

This is confirmed and reproduced by the pallet's own test suite: `vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early` [4](#0-3) . The sequence is:
1. Commitments are stored honestly for heights 10 and 11.
2. Height 11 (the latest) is vetoed via `delete_state_commitment`; the latest pointer resets to 10, but the queue still holds a stale index pointing at height 11.
3. Height 11 is honestly resubmitted — a *second*, live queue entry for height 11 is created, sitting behind the stale one.
4. On the next honest insertion (height 12), queue eviction processes the stale index for height 11 first and deletes the **live, valid** commitment for height 11 — one insertion earlier than it should have been evicted — even though a second, still-valid queue entry for 11 exists.

The eviction path acts on a stale reference (the leftover queue index) as though it still faithfully described current storage state, when the storage underneath it had already been freed and reallocated (re-stored) — exactly the "inappropriate pointer order" pattern in the CVE, translated to a logical/storage-index dangling reference rather than a raw memory pointer.

### Impact Explanation
`BoundedStateCommitments` backs `state_machine_commitment()`, which is the source of truth every ISMP request/response state (non-)membership proof is checked against [5](#0-4) . Premature, out-of-order eviction of a live commitment means relayers can no longer produce valid proofs against that height even though the queue's live entry believes the height is still retained — any request/response requiring proof at that height becomes permanently unprovable, i.e., a route unable to deliver messages for the affected state-machine height. Because state-commitment caps are typically small and each veto burns exactly one retention slot and shifts the queue by one, an adversary (or even unintentional operation) that repeatedly triggers a veto-then-resubmit cycle on the "latest" height can compound the effect, permanently starving retention for a target chain.

### Likelihood Explanation
Reaching this path only requires the standard, expected flow: a relayer submits a state-commitment update via a consensus proof (dispatched, unprivileged relaying), and that update is later vetoed through the fisherman mechanism because it turns out to be invalid, followed by an honest resubmission of the same height and one further honest commitment insertion. No malicious governance, malicious collator, or privileged action is required beyond the normal veto workflow the protocol itself exposes to fishermen; the bug is triggered by ordinary, expected sequences of honest operations, as the pallet's own regression test demonstrates deterministically.

### Recommendation
When resetting `LatestStateMachineHeight` back to `PreviousStateMachineHeight` in `delete_state_commitment`, also invalidate or actively locate/evict the stale queue index for the vetoed height (e.g., maintain a `height -> queue index` map on insert, as the code comment itself suggests) so a later resubmission cannot be shadowed by a leftover index from the vetoed submission. Alternatively, tag queue entries with a monotonically increasing generation/nonce per height so eviction can detect and skip stale entries instead of deleting whatever commitment currently occupies that height slot.

### Proof of Concept
The existing test is a complete PoC: [6](#0-5)  stores heights 10 and 11, vetoes 11 (`delete_state_commitment`), re-stores 11, then stores 12 — after which `state_machine_commitment(11)` fails (`is_err()`), proving the live, honestly-resubmitted commitment for height 11 was destroyed one insertion earlier than the queue's cap should have allowed.

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())

#[test]
fn vetoed_latest_height_that_is_resubmitted_evicts_one_insertion_early() {
	let mut ext = new_test_ext();
	ext.execute_with(|| {
		let host = Ismp::default();
		let id = queue_test_state_machine();
		let store = |height: u64| {
			host.store_state_machine_commitment(
				StateMachineHeight { id, height },
				queue_test_commitment(),
			)
			.unwrap();
			host.store_latest_commitment_height(StateMachineHeight { id, height }).unwrap();
		};

		pallet_ismp::Pallet::<Test>::update_commitment_caps(
			RuntimeOrigin::root(),
			BTreeMap::from([(id, 2)]),
		)
		.unwrap();

		store(10);
		store(11);

		// Vetoing the latest height rolls the latest pointer back to 10, so the
		// consensus handler would accept 11 again: it is not below the latest and
		// its commitment is now absent.
		host.delete_state_commitment(StateMachineHeight { id, height: 11 }).unwrap();
		assert_eq!(host.latest_commitment_height(id).unwrap(), 10);

		store(11);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_ok());
		// Two queue entries now point at height 11: the stale one and the live one.
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 1), Some(11));
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));

		// Evicting the stale entry at index 1 deletes the live commitment for 11,
		// one insertion before the entry at index 2 would have.
		store(12);
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 11 }).is_err());
		assert!(host.state_machine_commitment(StateMachineHeight { id, height: 12 }).is_ok());
		// The queue still counts index 2 as live, so the burnt slot leaves this
		// chain retaining one fewer commitment than its cap of 2.
		assert_eq!(
			CommitmentQueueStates::<Test>::get(id),
			CommitmentQueueState { head: 2, tail: 4 }
		);
		assert_eq!(StateCommitmentQueue::<Test>::get(id, 2), Some(11));
	})
}
