### Title
Session fixation via predictable, unauthenticated `SessionCookie` value used as the sole session identity binding - ([File: lib/shopify_api/utils/session_utils.rb], [File: lib/shopify_api/auth/oauth.rb])

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` issues a session cookie whose *value* is simply the deterministic `Session#id` (`"offline_#{shop}"` or `"#{shop}_#{associated_user_id}"`), not a random opaque secret. `ShopifyAPI::Utils::SessionUtils.current_session_id`/`cookie_session_id` then treats whatever value is present in that cookie as the authoritative session identity, with no cryptographic binding (no signature, no server-side nonce check) tying the cookie's bytes to the actual OAuth-authenticated browser.

### Finding Description
`ShopifyAPI::Auth::Session.from` builds session IDs deterministically from public/guessable inputs: [1](#0-0) 

For non-embedded apps, `Oauth.validate_auth_callback` puts this exact deterministic ID directly into the browser cookie as its *value* (not a random nonce): [2](#0-1) 

`ShopifyAPI::Auth::Oauth::SessionCookie` is a plain struct with no signature/MAC field at all — it carries only `name`, `value`, `expires`: [3](#0-2) 

Finally, `SessionUtils.current_session_id`/`cookie_session_id` reads that raw, unauthenticated cookie value and returns it as *the* session id used by the calling application to look up the stored `Session`/access token: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: *the bytes returned by `cookie_session_id`/`current_session_id` == a value only derivable by the party who actually completed OAuth for that specific browser session*. Instead the equality that actually holds is: *the bytes returned == `"offline_#{shop}"` or `"#{shop}_#{user_id}"` for any shop/user, computable by anyone who knows (or guesses) the target shop's domain and, for online sessions, the associated user's numeric id* — both of which are non-secret (shop domains are public; Shopify user ids are small sequential integers frequently observable from Shopify admin URLs, GraphQL responses, or export files).

Because the cookie is unsigned and the "session id" is not a random secret, any mechanism that lets an attacker place an arbitrary cookie value into a victim's browser under the app's cookie scope (e.g., a sibling subdomain that shares cookie scope, a cookie-setting endpoint, or simply an app that doesn't mark the cookie `Secure`/`HttpOnly`/`SameSite` as strictly as the docs merely *recommend* rather than the library *enforcing*) is sufficient to fixate the victim's session identity to a value of the attacker's choosing — e.g., the attacker's own previously-known `offline_<shop>` id, or a guessed victim id. This is a "session id derived from unauthenticated bytes" bug per the class of issue the analog highlights: unlike the JWT session-token path (`JwtPayload`), which is cryptographically signed with the app's `client_secret` and thus not forgeable by an outside party, this cookie-based fallback path has no such binding at all.

### Impact Explanation
If a host application relies on this library's documented `SessionCookie`/`SessionUtils.current_session_id` contract as its sole session lookup key (as shown in this gem's own docs and tests), an attacker who can inject/fixate this cookie value can cause the victim's browser to operate under a session id chosen by the attacker (session fixation). If the attacker fixates the victim to a session id the attacker also possesses (e.g., their own `offline_<attacker-shop>` id, obtained by legitimately installing the app on a shop they control), subsequent actions the victim performs in the app UI could be attributed to/act upon the attacker's session, or conversely the attacker could pre-provision a session id and later access whatever gets stored under it once the victim's flow completes — a classic session-fixation pattern that leads to cross-tenant confusion of which shop/token is used for API calls. This maps to the High-severity category "session fixation or forced OAuth completion."

### Likelihood Explanation
Likelihood is moderate: exploitation depends on the host application's exact cookie scoping/attributes (which this gem does not control or enforce) and on the attacker being able to set a cookie value in the victim's browser under the relevant cookie domain/path (e.g., via a shared parent domain, misconfigured `SameSite`/domain settings, or another injection point in the host app). The library-level root cause — a non-random, deterministic session identifier embedded verbatim in an unsigned cookie — is present regardless of host app configuration, and is a clear deviation from best practice (session identifiers should be unpredictable, opaque, and bound to the issuing transaction), but full exploitation requires an additional, host-app-specific cookie-injection primitive that is outside this gem's code.

### Recommendation
- Do not use a deterministic, guessable value (`shop` + user id) as the raw cookie value that also doubles as the storage lookup key. Instead, generate a random opaque session identifier at cookie-creation time, store the mapping `random_id -> Session` server-side, and never expose the deterministic `Session#id` to the browser.
- Alternatively/additionally, HMAC-sign the cookie value with `Context.api_secret_key` (similar to `Utils::HmacValidator`) so that `SessionUtils` can verify the cookie was actually issued by the app for that shop/session before trusting it as an identity binding.
- Document/enforce `Secure`, `HttpOnly`, and strict `SameSite` cookie attributes as a hard requirement (or provide a helper that sets them), rather than leaving it solely to downstream app code as in the current docs example.

### Proof of Concept
1. Attacker legitimately installs the target app on their own store `attacker-shop.myshopify.com`, completing OAuth as a non-embedded install. The library returns cookie value `offline_attacker-shop.myshopify.com` (deterministic, per `Session.from`/`Oauth.validate_auth_callback`).
2. Separately, attacker learns/guesses the victim's shop domain `victim-shop.myshopify.com` (public) and, for an online/per-user session, the victim's numeric Shopify user id (often observable, e.g. from GraphQL `associatedUser.id` responses or admin URLs).
3. Attacker computes the victim's would-be session id deterministically: `offline_victim-shop.myshopify.com` or `victim-shop.myshopify.com_<user_id>` using the exact same formulas in `Session.from` (`lib/shopify_api/auth/session.rb:107-140`).
4. Via any cookie-injection primitive available against the host app's cookie scope (subdomain takeover, related-domain XSS, insecure cookie attributes, etc.), attacker sets the `shopify_app_session` cookie in the victim's browser to this computed value.
5. When the victim's browser next hits the app, `SessionUtils.cookie_session_id`/`current_session_id` (`lib/shopify_api/utils/session_utils.rb:19-36,68-71`) returns this attacker-chosen id verbatim, and the host app looks up/activates a `Session` for that id — with no verification that this cookie value was actually issued as a result of a real OAuth completion for the current browser.

Note: I could not verify from the indexed files exactly how downstream consumers (e.g. `shopify_app`) wire `SessionCookie`/`SessionUtils` end-to-end at the HTTP layer (cookie attribute enforcement, `SameSite` defaults, etc.), since that logic lives outside this gem; that part of the chain is asserted based on the documented usage pattern (`docs/usage/oauth.md`) and the gem's own test fixtures, not on code I could directly inspect in a host app.
