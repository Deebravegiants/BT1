### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC over the body only and then hands the unauthenticated `shop` header straight to the host app's handler as the tenant identifier. Because the app's `client_secret` (used to compute the HMAC) is shared across every shop that installs the app, a body+HMAC pair that is valid for one shop is also a valid HMAC for the same body under a different `shop-domain` header, breaking the binding `shop-domain header == shop that produced the HMAC-authenticated body`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the `@raw_body` is included in the signable string. In contrast, `shop`, `topic`, `api_version`, and `webhook_id` are parsed straight from headers: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely over `to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` then trusts this HMAC-only check and forwards the caller-supplied, unauthenticated `shop` header to the host app's webhook handler as if it were verified tenant identity: [4](#0-3) [5](#0-4) 

Crucially, the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is the same for every shop that installs a given app — it is not shop-specific. This means the equality the gem is implicitly relying on:

```
valid_hmac(raw_body, client_secret) == true  ⇒  shop-domain header is trustworthy
```

does not hold, because `valid_hmac` never binds `shop-domain` into the signed content. Any two webhook deliveries (from any two shops that have installed the same app) that happen to carry an identical raw body will produce an identical HMAC, since the signature depends only on `(raw_body, client_secret)` and not on `shop`.

### Impact Explanation
This is a cross-tenant confusion vector inside the gem's own webhook verification path. An attacker who controls a shop that has installed the victim's app (e.g., an attacker-owned development/test store) can capture a legitimately signed webhook body+HMAC pair emitted by Shopify for their own store, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` will still return `true`, because it never inspected `shop`, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the event originated from the victim shop: [6](#0-5) 
Any host app that uses `data.shop` from the gem's webhook handler API to select which merchant's records to update/create/delete (the intended and documented use of `WebhookMetadata#shop`) will act on the victim tenant's data using attacker-supplied body content believed to be "verified." This is a cross-tenant access primitive delivered entirely through the gem's own signature-verification code, not a misuse of an undocumented API by the host.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own store having the target app installed (a normal, low-privilege action available to anyone who can install a public/free app), (2) the ability to trigger a webhook event on their own store to obtain a genuine `(raw_body, hmac)` pair, and (3) the ability to POST an HTTP request to the app's public webhook endpoint with a forged `shop-domain` header — no possession of `api_secret_key`, access tokens, or other privileged material is needed. Some engineering constraint exists in that the forged body must exactly match a body the attacker can legitimately obtain (limiting arbitrary payload content), which lowers likelihood somewhat, but the binding failure itself is unconditional and reachable by any unprivileged internet user who can install the app once.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the raw body) in the signed content verified by `to_signable_string`/`HmacValidator`, or otherwise have `Registry.process` independently confirm that the `shop-domain` header corresponds to a shop session/installation record already known to the host app before treating the payload as authoritative for that shop. At minimum, document prominently that `WebhookMetadata#shop` is not itself covered by the HMAC and must not be used as the sole tenant-selection key without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event they control (e.g., `products/create`) with body `B`; Shopify sends the app `POST /webhooks` with header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: H = HMAC_SHA256(client_secret, B)`.
3. Attacker replays the exact bytes of body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(client_secret, B)` and finds it equal to `H` — validation passes because `shop` was never part of the signed string (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. `Registry.process` invokes the host handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body_from_B, ...)` — the app now processes attacker-controlled body content attributed to the victim tenant.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
