### Title
Permissionless finalization of a hostile-mint-pre-seeded HyperSwap pair can compute `liquidity == 0` and revert on `LPLock.recordLock`, permanently bricking graduation and freezing the curve's raised LT and 250M reserved tokens - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` is a **permissionless, one-shot** phase-2 call that seeds a HyperSwap V2 pair and hands the resulting LP tokens to `LPLock.recordLock`. `_routerDepositAndDispose` only calls `addLiquidity` when *both* `remToken > 0 && remLT > 0` [1](#0-0) ; when that condition is false, `liquidity` stays `0` and is passed straight through to `LPLock.recordLock(tokenAddress, lpPair, liquidity)` [2](#0-1) , which unconditionally reverts with `ZeroAmount` for `amount == 0` [3](#0-2) . Because `AlreadyLocked`/`lockedAt` state is only ever set on success, a reverting call leaves the token stuck in `Lifecycle.Graduating` forever — `finalizeGraduation` requires `Lifecycle.Graduating` [4](#0-3)  and there is no other function that can move it out of that state or rescue the funds already drained into `Bonding` and the pending-graduation escrow.

### Finding Description
Phase 1 (`_enterGraduating`) drains the curve's real LT via `Router.graduate` and freezes the token in `Lifecycle.Graduating`, caching `(tokensForLP, ltFromPair)` [5](#0-4) . Phase 2 (`finalizeGraduation`) is deliberately permissionless (`test_phase2_anyone_can_finalize` [6](#0-5) ) so anyone — including an attacker who front-ran the HyperSwap pair — can trigger it. The comment block on `_swapBudget` explicitly documents this exact failure mode as a known risk that the 1% swap-budget reservation is supposed to prevent:

> "Without this, an extreme hostile pre-seed... drives the unconstrained `_noFeeSwapInput` past our per-side budget, `_pairRebalance` clamps to the full budget, and the swap consumes 100% of one side. `_routerDepositAndDispose` then skips `addLiquidity` (`remToken == 0` or `remLT == 0`), `finalizeGraduation` returns `liquidity = 0`, and `LPLock.recordLock(...)` records a zero-sized lock" [7](#0-6) 

The mitigation reserves 1% of the swap budget so the deposit "always" has non-zero amounts on both sides [8](#0-7) , and `_swapBudget`'s input (`_ltSwapInventory` / `IERC20.balanceOf`) is derived from this graduation's own escrowed `ltFromPair`/`tokensForLP`, not from the attacker's pre-seed size. But the actual zero-liquidity outcome in `_routerDepositAndDispose` is gated on the **post-swap remaining balances** (`remToken`, `remLT`), which depend on `addLiquidity`'s router-side `quote()`-based optimal split against the pre-seeded pool ratio, not merely on whether the swap consumed 100% of the swap-side inventory. `_noFeeSwapInput` itself can independently return `0` (dust-rounding, handled by falling back to `_seedDirectMint` — but `_seedDirectMint` in turn does a raw `pair.mint` whose only guard against a zero liquidity mint is the underlying V2 pair reverting internally with `INSUFFICIENT_LIQUIDITY_MINTED`, which is *also* an unhandled revert that would permanently brick `finalizeGraduation` for that token [9](#0-8) . The developer's own commentary that dedicated hostile-pre-seed regression tests (`test/HostilePreSeed.t.sol`) covering "wrong-opening-price / LP-capture... attacker-no-profit, leftover recovery" were removed "for runtime reasons after deployment" and are "no longer enforced by automated tests" [10](#0-9)  means this exact brick-resistance property is currently unverified in CI.

This is the direct analog of the external CVE-2021-41524 class: a specially crafted external input (here, an attacker pre-creating and mint-pre-seeding the HyperSwap TOKEN/LT pair with an extreme ratio before `finalizeGraduation` runs) drives execution down an under-defended internal path (`_seedRebalancing` → `_routerDepositAndDispose` / `_seedDirectMint`) that hits an unhandled revert (`LPLock.ZeroAmount` or V2's `INSUFFICIENT_LIQUIDITY_MINTED`) instead of a graceful outcome, causing a permanent denial of service on that specific piece of state — exactly like the null-pointer dereference DoS-ing a specific HTTP/2 request path in httpd.

### Impact Explanation
`Lifecycle.Graduating` has no owner-controlled or permissionless recovery path — `finalizeGraduation` reverts `NotGraduating` for any lifecycle other than `Graduating` [4](#0-3) , `triggerGraduation` reverts `TokenIsGraduating` [11](#0-10) , and normal `buy`/`sell` are frozen once trading stops. If `finalizeGraduation` permanently reverts for a given token, that token's entire curve-raised LT (already drained into `Bonding` via `Router.graduate` in phase 1) and its 250M reserved LP tokens are permanently frozen with no on-chain recovery — matching the "permanent freezing of trader, creator or LP funds" impact bar in the validation criteria.

### Likelihood Explanation
The attack requires only unprivileged, permissionless actions reachable by any address: pre-creating the HyperSwap pair, transferring an extreme TOKEN:LT ratio into it and calling `pair.mint(attacker)`, then calling (or waiting for the keeper to call) the permissionless `finalizeGraduation`. The protocol's own AGENTS.md flags this as "the most subtle code in the package" and notes the dedicated integration tests for this exact scenario have been removed from CI, so regressions or edge cases in the swap-budget/rebalance math are not currently caught automatically.

### Recommendation
Add an explicit guard in `finalizeGraduation`/`_seedUniswapV2Direct` (or in `LPLock.recordLock`) that treats `liquidity == 0` as a recoverable condition rather than a hard revert — e.g., retry with a direct-mint fallback that is guaranteed non-zero, or introduce a bounded lifecycle-recovery path (owner or delayed permissionless rescue) so a pathological pre-seed cannot permanently brick a token's graduation. Reinstate or re-derive the removed `test/HostilePreSeed.t.sol` coverage, specifically the zero-liquidity / `INSUFFICIENT_LIQUIDITY_MINTED` and `LPLock.ZeroAmount` revert paths under extreme pre-seed ratios, per `packages/contracts/AGENTS.md`'s own guidance.

### Proof of Concept
1. Attacker calls `Bonding.launch`/watches for a token entering `Lifecycle.Graduating` (phase 1 fired by a normal buy).
2. Before the keeper's `finalizeGraduation` lands, attacker calls `factory.createPair(token, lt)` then transfers an extreme, budget-exceeding TOKEN:LT ratio into the pair and calls `pair.mint(attacker)`, per the documented exploit primitive in `AGENTS.md` [12](#0-11) .
3. Anyone calls `Bonding.finalizeGraduation(token)`. `_seedRebalancing` computes a rebalance swap capped by `_swapBudget`, and depending on the pre-seed magnitude and rounding in `addLiquidity`'s `quote()` split, `_routerDepositAndDispose` can still land on `remToken == 0` or `remLT == 0` (skipping `addLiquidity` and returning `liquidity = 0`), or `_seedDirectMint`'s raw `pair.mint` call reverts with V2's `INSUFFICIENT_LIQUIDITY_MINTED`.
4. `LPLock.recordLock(token, pair, 0)` reverts `ZeroAmount` (or the mint revert propagates), so `finalizeGraduation` reverts. The token is permanently stuck in `Lifecycle.Graduating` — no function can move it forward, and the LT already drained via `Router.graduate` plus the 250M reserved tokens held in `Bonding` are permanently unreachable.

**Note:** I could not fully trace every rounding branch of the router's `addLiquidity` `quote()` logic (external HyperSwap contract, out of scope) to construct exact numeric parameters that force `remToken`/`remLT` to zero without tripping the 1% reservation; this would require deployment-specific fuzzing/PoC execution in a Devin session to confirm the precise pre-seed ratio that defeats `_swapBudget`'s guarantee, which the maintainers themselves flag as no longer covered by automated tests.

```text
    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }
```

**File:** packages/contracts/AGENTS.md (L132-148)
```markdown
A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.
```
