## Finding: Missing `return` after failed email-claim extraction allows session creation with an empty/unverified identity in OIDC authentication flow

### Title
Missing `return` on email-claim extraction failure allows valid, role-bearing sessions to be created without an authenticated identity - (File: `core/sessions/oidcauth/oidc.go`)

### Summary
`handleTokenExchange` in `core/sessions/oidcauth/oidc.go` extracts the `email` claim from the verified ID token but fails to `return` when that extraction fails, allowing execution to continue and create a fully valid, role-bearing session keyed to an empty email value.

### Finding Description
In `oi.handleTokenExchange`, after verifying the ID token and parsing claims, the email claim is extracted with a type assertion: [1](#0-0) 

If `claims["email"]` is missing or not a string (e.g., the identity provider's response omits or nulls the `email` claim), `ok` is `false`, an error is logged, and an HTTP 500 body is written — but there is no `return` statement. Execution falls through with `email` left as its zero value (`""`).

The code then proceeds unconditionally to map group claims to an RBAC role and persist a new session row keyed on this empty email: [2](#0-1) 

The role mapping (`IDClaimsToUserRole`) operates on separately-extracted group claims (`idClaims`), independent of the `email` field, so a missing/empty email does not block a legitimate role match (e.g., Admin/Edit) from succeeding. The resulting `oidc_sessions` row stores `user_email = ""` alongside the resolved role, and the gin session cookie is still set and saved as if authentication succeeded (`c.JSON(http.StatusOK, ...)` at the end of the handler is reached because there's no early return).

`AuthorizedUserWithSession` later trusts this row directly without any secondary validation that the email is non-empty or corresponds to a real, distinct identity: [3](#0-2) 

This mirrors the CVE-2017-14337 root cause: an external identity/claims source (analogous to MISP's external user-management API) returning an empty value for the user identifier is not rejected, and the local application proceeds to grant an authenticated session with a role derived independently of that identity check.

### Impact Explanation
Any session created this way is a real, valid, role-bearing session (able to pass `AuthenticateBySession`/`AuthorizedUserWithSession`) that is not tied to a distinguishable user identity — the session's `user_email` is `""`. This breaks the authentication/authorization invariant that a session always corresponds to a specific, identifiable, verified user. Depending on group-claim mapping at the IdP, this can result in a session carrying an Admin/Edit role while the audit trail and user-scoped functionality (which key off `Email`) silently operate on an empty identity, undermining accountability and potentially enabling cross-session/cross-user confusion if multiple such empty-email sessions coexist.

### Likelihood Explanation
Exploitability depends on the configured OIDC provider's claims response omitting or nulling the `email` claim while still supplying the configured RBAC group claim — a scenario an operator misconfiguring claim scopes, or an IdP bug/edge case, could trigger. Because chainlink's own code does not validate the email presence before continuing, this is a reachable, locally-verifiable bug given the observed control flow. Deliberate exploitation requires influence over the IdP's claims content.

### Recommendation
Add a `return` statement (or otherwise abort the flow) immediately after detecting `!ok` for the email claim in `handleTokenExchange`, before role mapping and session creation occur:
```go
email, ok := claims["email"].(string)
if !ok {
    oi.lggr.Errorf("Failed to get email from claims")
    c.String(http.StatusInternalServerError, "Failed to get email from claims")
    return
}
```
Additionally, consider validating that `email` is non-empty before persisting the `oidc_sessions` row, and reject role mapping when the identity cannot be established.

### Proof of Concept
1. Configure the node with OIDC auth and RBAC group claims (`AdminClaim`, etc.).
2. Complete the OAuth2 code exchange against an IdP (or a proxy/testing IdP) whose ID token includes the configured admin group claim but omits the `email` claim (or returns it as `null`/non-string).
3. Observe in `handleTokenExchange` that `claims["email"].(string)` fails (`ok == false`), the error branch executes but does not `return`, and execution continues to `IDClaimsToUserRole`, `INSERT INTO oidc_sessions`, and `c.JSON(http.StatusOK, ...)`.
4. The resulting session cookie authenticates via `AuthorizedUserWithSession`, returning a `sessions.User{Email: "", Role: <mapped role>}`, despite no verified email identity being established.
