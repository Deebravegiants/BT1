## Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC-verifiable query, but the signable string used for HMAC verification consists **only of the raw body**. The `shop-domain` header — which is handed to webhook handlers as the trusted tenant identifier — is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an unauthenticated header with no relationship to the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC and, once it passes, hands `request.shop` straight to the app's handler as the authoritative tenant identifier, with no additional binding check: [3](#0-2) 

The identity binding this breaks: `shop authenticated by HMAC` should equal `shop delivered to the handler as WebhookMetadata#shop`, but the gem only proves `HMAC(api_secret_key, raw_body)` — it never proves that the `shop-domain` header belongs with that body. Since every shop that has this app installed shares the **same** `api_secret_key`/HMAC (per Shopify's webhook signing model, which is app-wide, not shop-specific), a legitimate merchant of the app (an "unprivileged internet user" relative to *other* tenants) can:
1. Receive a genuine webhook for their own store (valid `body` + valid `X-Shopify-Hmac-Sha256`).
2. Replay that exact body/HMAC pair to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds, because the header isn't part of `to_signable_string`.
4. `Registry.process` invokes the handler with `WebhookMetadata#shop` equal to the victim's domain.

Any host application that uses `WebhookMetadata#shop` (as the documented public API surface directs) to look up the corresponding merchant record/session and perform actions — e.g., update local order/inventory records, trigger cross-tenant data mutation, or fan out a stored access token for that shop — will act on the wrong tenant using attacker-supplied data.

### Impact Explanation
This is a cross-tenant confusion: a valid signature for one tenant's payload can be attributed to a different tenant simply by changing an unauthenticated header. Any downstream logic keyed off `WebhookMetadata#shop` (the field this gem explicitly exposes for that purpose) can be manipulated by any party that already has one legitimate installation of the app, to inject spoofed events for arbitrary victim shops.

### Likelihood Explanation
Requires only that the attacker install the app on any shop they control (a normal, low-privilege action) and replay one webhook with a swapped header — no `api_secret_key` or other privileged secret is needed by the attacker, and no code beyond documented use of `Registry.process`/`WebhookMetadata#shop` is needed on the host-app side.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook-id`) into the HMAC-verified signable string, or otherwise cryptographically tie the header-derived identifiers to the signed body (e.g., require the host app to cross-check `shop` against a known-installed shop list before trusting `WebhookMetadata#shop`), and document that `shop-domain` is currently unauthenticated.

### Proof of Concept
1. App is installed on `attacker.myshopify.com`; attacker receives a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `HMAC(api_secret_key, B)`), header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker POSTs the same `B`/`H` to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` since it only checks `HMAC(api_secret_key, B) == H` [4](#0-3) .
4. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` [5](#0-4) , causing the host app to act on the victim tenant using attacker-controlled body content.
