### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the tenant identity (`shop`) from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that authenticates the webhook covers only the raw request body. Since `shop` is not part of the signed material, any holder of one genuine, validly-signed webhook can replay it with a forged shop header and have it accepted as coming from a different, arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`shop` is read straight from an unauthenticated header: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and secure-compares it to the received `hmac`: [3](#0-2) 

`Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` — which only proves the body bytes are untampered and signed with the app's secret — and then forwards `request.shop` (from the unauthenticated header) straight to the handler as the tenant identifier: [4](#0-3) 

The binding the code implicitly assumes is: `HMAC-verified bytes == the shop that the webhook data belongs to`. In reality the HMAC only proves `HMAC-verified bytes == raw_body`; the `shop` field is never part of what is verified. Because the app's `api_secret_key` is shared across every shop that has installed the app, any shop that has installed the app (an "unprivileged" tenant relative to other tenants) legitimately receives real webhooks from Shopify with a valid HMAC computed over the body using that same shared secret. That tenant can capture one such genuine webhook (body + HMAC unchanged) and re-POST it to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because the body is untouched, but `WebhookMetadata.shop` now reports the victim's domain to the host application's handler.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as documented/intended) to key per-tenant records, credentials, or business logic (e.g., updating order/inventory data, revoking access, or driving tenant-scoped side effects), an attacker-controlled tenant can inject data or trigger effects attributed to a victim shop — a cross-tenant integrity/isolation break carried entirely by this gem's webhook-verification API surface, without needing the victim's or the app's own credentials beyond having installed the app once.

### Likelihood Explanation
Exploitation requires only that the attacker's shop has installed the app (a normal, unprivileged occurrence) and can trigger any webhook topic to receive one genuinely-signed payload, then replay it to the same public webhook endpoint with a modified shop header — an operation reachable by any internet-facing HTTP client, with no need for the `api_secret_key` or any victim credential.

### Recommendation
Include the shop domain (and other trust-relevant headers such as topic/api-version) in the signable content, or otherwise independently verify that the `shop` header matches the tenant the webhook subscription was registered for, before trusting it as the record's identity in `Webhooks::Registry.process`.

### Proof of Concept
1. App has two installed shops: `attacker.myshopify.com` and `victim.myshopify.com`.
2. Shopify sends a real webhook to the app for `attacker.myshopify.com`, with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
3. Attacker replays the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` decodes the still-valid signature; `HmacValidator.validate` succeeds because it only checks `raw_body` per `to_signable_string`.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, even though the payload actually originated from the attacker's own shop.
