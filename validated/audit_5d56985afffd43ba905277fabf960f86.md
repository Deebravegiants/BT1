### Title
Persistent ERC20 allowances left on the shared `CallDispatcher` allow theft of unrelated users' funds - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` executes arbitrary attacker-supplied `Call[]` on behalf of any order's `predispatch`/`postdispatch` calldata (from `IntentGatewayV2`) or `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution, with no restriction on the target address or calldata content other than "target must be a contract." Because `CallDispatcher` is a single shared, stateless contract reused across all orders/messages, a malicious order can make it execute `IERC20(token).approve(attacker, type(uint256).max)`. That allowance is persistent ERC20 state that outlives the transaction. Any later order/message that causes real value (predispatch assets, or solver output tokens sent to the dispatcher as beneficiary) to land on the dispatcher for that same token is then stealable by the attacker via `transferFrom`, exactly analogous to the Sense `Periphery._fillQuote` bug where an attacker-controlled `spender` is blindly approved by the protocol.

### Finding Description
`CallDispatcher.dispatch()` has no access control and no whitelist of callable targets/selectors: [1](#0-0) 

It is invoked by `IntentGatewayV2`/`IntentsBase` for both `predispatch` (before escrow) and `postdispatch`/output `call` (after fill) calldata: [2](#0-1) [3](#0-2) 

and by the `HyperFungibleToken`/`WrappedHyperFungibleToken` `onAccept` calldata-execution path documented here: [4](#0-3) 

The docs explicitly acknowledge the risk of unlimited approvals left on the dispatcher ("Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution") but this is only advisory — there is no on-chain enforcement preventing a user from crafting `predispatch`/`postdispatch` calldata containing `IERC20.approve(attackerAddress, type(uint256).max)`: [5](#0-4) 

The test suite itself demonstrates the pattern of routing tokens through the shared dispatcher via approve+swap+sweep, confirming the dispatcher regularly holds meaningful token balances mid-flow and that `approve()` calls to arbitrary spenders are a normal, unrestricted part of the calldata payload: [6](#0-5) 

Because `CallDispatcher` is one shared, address-invariant contract reused by every order and every HFT/WrappedHFT message (its address is fixed in `Params.dispatcher`/configured dispatcher and referenced by all orders/messages), an `approve()` granted during one malicious order's predispatch/postdispatch execution is not scoped to that order — the ERC20 allowance mapping is keyed only by `(owner=dispatcher, spender=attacker)` and persists indefinitely in the token contract's own storage, independent of the dispatcher's internal state or any particular order's lifecycle.

### Impact Explanation
Once the attacker holds an infinite allowance from the shared `CallDispatcher` for a given token, any subsequent transaction that moves that token onto the dispatcher — e.g. another user's `predispatch` assets sent to `dispatcher` before predispatch calls run, or a solver's output tokens sent to the dispatcher when `beneficiary == dispatcher` (as in the `testPostdispatchTokenSweep` pattern), or tokens minted/unlocked by HFT calldata flows that route through the same dispatcher — can be immediately swept away by the attacker via `transferFrom` before the legitimate sweep-back-to-gateway call executes (or even after, since the approval isn't tied to a specific transfer). This is concrete theft of funds belonging to other users/solvers/the protocol, satisfying High severity.

### Likelihood Explanation
Any unprivileged user can place an `IntentGatewayV2` order (or trigger HFT calldata execution) with attacker-chosen `predispatch`/`postdispatch`/`data` calldata; nothing in `placeOrder`, `_execute`, or `CallDispatcher.dispatch` inspects or restricts the encoded calls beyond "target has code." The attacker needs only one transaction to plant the infinite approval, then waits for/front-runs the next transaction that lands funds on the dispatcher for that token — a routine, expected occurrence given the dispatcher's designed role in swap-then-escrow and fill-then-act flows. Likelihood is high because exploitation requires no special permissions or race with any privileged actor.

### Recommendation
- Do not allow arbitrary open-ended `approve` targets to persist: have `CallDispatcher` revoke any allowance it granted at the end of `dispatch()` (loop over tokens touched and reset `approve(spender, 0)`), or
- Deploy/scope a fresh, disposable `CallDispatcher`-like proxy per order/message (e.g. via `CREATE2`/minimal proxy) so no allowance state can be shared across unrelated orders, or
- Restrict `dispatch()` calldata to disallow `approve`/`increaseAllowance`/`permit`-style selectors entirely, forcing token movement to occur only via `transfer`, and requiring swaps to use routers that pull funds through `transferFrom` with per-call, single-use permissions (e.g. Permit2 with tightly scoped, short-lived allowances) rather than durable ERC20 `approve`.
- At minimum, assert that the `CallDispatcher`'s balance and outstanding allowances for every token touched by a batch are zero at the end of `dispatch()`/`_execute()`, reverting otherwise.

### Proof of Concept
1. Attacker calls `IntentGatewayV2.placeOrder` with `order.predispatch.call` (or `output.call`) encoding a single `Call{ to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attackerEOA, type(uint256).max) }`. Predispatch assets can be `amount == 0`-free/minimal to satisfy input requirements, or the attacker uses the postdispatch/output path where a self-filled trivial order triggers `_execute()`.
2. `IntentsBase._execute` (or `IntentGatewayV2.placeOrder`) calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` / `dispatch(order.output.call)`, which blindly executes the approve call because `dispatch()` performs no validation beyond `extcodesize(USDC) > 0`: [7](#0-6) 
3. `USDC.allowance(dispatcher, attackerEOA)` is now `type(uint256).max`, permanently, in USDC's own storage — unaffected by the fact that the attacker's own order finished and its escrow was reduced/settled.
4. Later, a legitimate solver fills a different, unrelated order whose `PaymentInfo.beneficiary` is set to the dispatcher address (a pattern the codebase itself uses, see `testPostdispatchTokenSweep`), transferring USDC into the dispatcher before `_execute`'s sweep step runs: [8](#0-7) 
5. The attacker races (or simply calls immediately after, since no other actor spends the allowance) `USDC.transferFrom(dispatcher, attackerEOA, balance)` before the gateway's sweep-back `transfer` call executes, draining the unrelated order's output tokens.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```

```text
## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
```
