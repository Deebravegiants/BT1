### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that host applications are expected to use to determine which tenant a webhook belongs to, but the HMAC signature verified via `Utils::HmacValidator` only covers the raw request body, not the `shop`, `topic`, `webhook_id`, or `api_version` headers. This breaks the identity binding `verified_bytes == acted_upon_identity`, allowing an attacker who possesses one valid `(body, hmac)` pair (e.g. from their own shop's legitimate webhook delivery) to replay it against the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header, causing the host application to process the payload under a victim shop's identity.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC purely against `to_signable_string`: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly and unverified from HTTP headers: [3](#0-2) [4](#0-3) 

The gem's own header-normalization logic in `initialize` only checks for the *presence* of `shopify-shop-domain`/`x-shopify-shop-domain`, never that its value is bound to the signature: [5](#0-4) 

This is the equality that should hold but doesn't: `bytes_verified_by_hmac == bytes_the_host_app_uses_to_identify_the_tenant`. In this gem, `bytes_verified_by_hmac = raw_body` while `tenant_identity = shop_header`, and the two are never bound together. Any party that legitimately receives a valid webhook (i.e., holds a valid `(raw_body, hmac)` pair for their own shop) can replay that exact body+hmac to the same endpoint while forging the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) headers to name a different, victim shop. `Utils::HmacValidator.validate` will still return `true` because it only re-derives the HMAC over `@raw_body`, which is unchanged. The host application — following the gem's documented pattern of calling `request.shop` after `HmacValidator.validate(request)` succeeds to look up/act on that shop's session or data — will process the request as belonging to the attacker-chosen victim shop.

### Impact Explanation
This crosses a tenant boundary using only the gem's exposed API: an attacker with any legitimate `(body, hmac)` webhook pair for a shop they control can cause the host application to attribute and act on that payload for a different merchant's shop, without possessing that merchant's `client_secret` or access token. This matches the Critical "cross-tenant access" impact criterion, since verification success is decoupled from the identity field the application uses to select the tenant.

### Likelihood Explanation
Likelihood is moderate-to-high in realistic deployments: any unprivileged party who can install an app instance (or otherwise cause a legitimate webhook to be delivered to them, e.g. via their own store) obtains a valid `(raw_body, hmac)` pair trivially, since the HMAC never binds to the shop domain. No secret material or privileged access is required beyond the ability to send an arbitrary HTTP request to the app's public webhook endpoint with attacker-controlled headers — something webhook endpoints must accept by design.

### Recommendation
Include the identity-bearing headers (`shop`, and ideally `topic`/`webhook_id`) in the signed/verified material, or explicitly document and enforce that `Request#shop` must never be trusted as tenant identity unless independently cross-checked against a shop the app already has an authenticated session for (rather than trusted purely because `HmacValidator.validate` returned true). At minimum, `HmacValidator.validate` should be changed to also verify that the `shop-domain` header used by the caller matches an expected/known value, or `VerifiableQuery#to_signable_string` for `Webhooks::Request` should incorporate the shop/topic headers so a replay with altered headers invalidates the signature.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), receiving a legitimate request with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(secret, B)`.
2. Attacker replays an HTTP POST to the app's webhook endpoint with the same body `B` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. The host application constructs `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: attacker_headers)` and calls `ShopifyAPI::Utils::HmacValidator.validate(request)`.
4. `validate` recomputes `HMAC(secret, B)` — identical to `H` — via `to_signable_string`, which never includes the shop header, so validation returns `true`. [6](#0-5) 
5. The host app then reads `request.shop` (`"victim-shop.myshopify.com"`) and `request.parsed_body` (the attacker's own order data) and processes/stores it as belonging to the victim shop — a cross-tenant data confusion achieved purely by header forgery, with signature verification unaffected. [7](#0-6)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
