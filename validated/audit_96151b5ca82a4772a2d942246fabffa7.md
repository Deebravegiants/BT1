### Title
RAY-value overflow in accrual math permanently freezes every market operation before the borrow-index cap can engage - (File: common/src/rates/scaling.rs, common/src/rates/compound.rs)

### Summary
The external report is a Hotspot JIT miscompilation: correct high-level inputs produce a corrupted numeric result inside the arithmetic engine. The analog in XOXNO Lending is the fixed-point accrual engine in `common/src/rates`. On a sufficiently large market, `accrue_step` evaluates `scaled_to_original(borrowed, borrow_index)` / `scaled_to_original(supplied, supply_index)` over `i128` RAY intermediates. Debt value grows multiplicatively while the share count is fixed, so the half-up product `borrowed × borrow_index` exceeds `i128::MAX` and panics with `MathOverflow` long before `update_borrow_index` reaches the `MAX_BORROW_INDEX_RAY` clamp. Because every state-changing entrypoint runs `interest::global_sync` first, the market becomes permanently frozen: supply, withdraw, borrow, repay, liquidate, `clean_bad_debt`, `claim_revenue`, and `update_indexes` itself all trap on the same overflow.

### Finding Description
`accrue_step` (`common/src/rates/simulate.rs:51-60`) computes utilization from `scaled_to_original(env, borrowed, borrow_index)`, which is `scaled.mul(env, index)` — a checked half-up `i128` multiply-divide (`common/src/rates/scaling.rs:14-16`). The mutating path `accrue_chunk` in `contracts/pool/src/interest.rs:39-53` calls it unconditionally on every operation via `global_sync` (`contracts/pool/src/interest.rs:20-33`). `update_borrow_index` (`common/src/rates/index.rs:13-19`) clamps the *index* at 10^36 raw RAY, but nothing bounds the *product* `borrowed × borrow_index`; the debt-value ceiling is hit first on a whale-scale market. The test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360`) demonstrates exactly this: `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all fail with `MATH_OVERFLOW` while `borrow_index < MAX_BORROW_INDEX_RAY`. There is no recovery path — the panic is recomputed deterministically on every subsequent call, and governance cannot lower the index because accrual is also the gate for parameter updates that touch the market.

### Impact Explanation
Permanent freezing of funds. All supplied and collateral value in the affected market is locked forever: suppliers cannot withdraw, borrowers cannot repay (repay accrues first), liquidators cannot liquidate, and unclaimed yield (`claim_revenue` also accrues through the same cache path) is unrecoverable. The token balances sit in the pool contract with no code path that skips accrual.

### Likelihood Explanation
Triggering requires a very large market (on the order of 10^20+ base units, i.e., ~170B whole tokens at 18 decimals) sustained at high utilization on a steep curve segment for a multi-year accrual gap. An unprivileged caller does not need special permissions — `update_indexes` is permissionless and any supplier/borrower interaction executes the same accrual — but the capital requirement means this is a tail risk for cap-lifted or cap-disabled markets rather than something an attacker can force on a small book. Medium likelihood, high impact when reached.

### Recommendation
Bound the market earlier rather than letting the product overflow:
- Enforce, at `supply`/`borrow` entry, that `borrowed × borrow_index` and `supplied × supply_index` cannot reach `i128::MAX / safety_factor` before the next accrual, i.e., derive the cap from index headroom rather than the static `i128::MAX / 10^(27-d)` asset-domain bound in `docs/reference/formulas.md`.
- Alternatively, make `scaled_to_original` in the accrual path saturate/clamp the index growth per chunk (or short-circuit accrual once the index reaches `MAX_BORROW_INDEX_RAY`) so repay and withdraw paths remain operable instead of trapping.
- At minimum, provide an emergency accrual-skip path for `repay`/`liquidate`/`clean_bad_debt` so positions can be wound down even when index accrual overflows.

### Proof of Concept
The codebase already contains the executable proof: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-360` builds a market with a `BILLION × 10^18`-unit supply and ~98% borrowed, advances time in one-year steps calling `update_indexes`, and asserts:
- `try_update_indexes_for(&["BIG18"])` fails with `GenericError::MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY` (the index cap never engages),
- `try_withdraw_raw(BOB, "BIG18", 1)` fails with `MATH_OVERFLOW`,
- `try_repay(ALICE, "BIG18", 1.0)` fails with `MATH_OVERFLOW`.

Root cause chain: `global_sync` → `accrue_chunk` → `accrue_step` (`common/src/rates/simulate.rs:60`) → `scaled_to_original` (`common/src/rates/scaling.rs:14`) → checked half-up `borrowed × borrow_index` exceeds `i128::MAX` → panic. The equivalent overflow exists in `compound_interest`'s exponent computation (`common/src/rates/compound.rs:36-42`) as a second panic site.
