Confirmed the root cause. The finding is solid and matches the report's bug class exactly: a value the application acts on (`shop` identity) is not part of what the HMAC covers.

### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing shop-identity spoofing on otherwise-valid webhook payloads - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `topic`, `shop`, `api_version`, and `webhook_id` values purely from unauthenticated HTTP headers, while `to_signable_string` (the bytes the HMAC actually signs) returns only `@raw_body` [1](#0-0) . `Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)` and then passes the caller-supplied `request.shop` straight into the handler as the tenant identity, without the `shop` value ever being covered by the signature [2](#0-1) .

### Finding Description
The identity binding that should hold is:
`shop header value used by the handler == shop that the HMAC signature actually authenticates`

`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the `hmac` value [3](#0-2) . For `Webhooks::Request`, `to_signable_string` returns `@raw_body` only [4](#0-3) ; none of `topic`, `shop`, `api_version`, or `webhook_id` — all read from HTTP headers via `shopify_header` — are included in the signed bytes [5](#0-4) [6](#0-5) .

Because Shopify webhook HMACs are computed with the app's single shared `client_secret` (not a per-shop secret), any `(raw_body, hmac)` pair that is valid for one shop's webhook remains a cryptographically valid pair for **any** header set, since the headers never enter the signed string. An attacker who controls a store that has installed the app (trivial: any developer/free trial store) can capture a legitimate webhook delivery `(body B, hmac H)` sent to their own endpoint, then replay it against the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to a victim shop's domain. `Registry.process` still calls `Utils::HmacValidator.validate(request)` which only checks `B` against `H` — this passes — and then dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` to the handler with the forged `shop` value [2](#0-1) .

Any host application that trusts `data.shop` from `WebhookMetadata` to select which tenant's session/store record to act on (the documented and expected usage pattern for this gem) will act on attacker-controlled data while believing it passed HMAC authentication for that shop.

### Impact Explanation
This breaks the identity binding between "HMAC-authenticated sender" and "shop the handler believes it is for," letting an attacker with only a free/trial store cause the webhook handler to execute logic attributed to an arbitrary victim shop — a cross-tenant confusion condition. Since the gem's own `HmacValidator.validate` reports success, the host application has no signal that the `shop` field is unauthenticated, satisfying the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
Requires only an installed app on any store the attacker controls (no privileged credentials, no leaked secrets, no TLS interception) plus the ability to POST to the app's public webhook endpoint with attacker-chosen headers — both are standard, unprivileged capabilities of any merchant/developer.

### Recommendation
Include `topic`, `shop`, `api_version`, and `webhook_id` in the signable string bound by the HMAC (or otherwise cryptographically bind the shop domain to the signed payload), so `to_signable_string` cannot be satisfied by a replayed body under forged headers.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw POST: headers including `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`, and raw body `B`.
2. Replay the exact same body `B` and `hmac` header `H` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a request whose `to_signable_string` is still `B`; `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` which equals `H`, so validation succeeds [3](#0-2) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata` carrying `shop: "victim.myshopify.com"` despite the payload never having been authenticated for that shop [7](#0-6) .
