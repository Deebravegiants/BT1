### Title
Webhook `shop-domain` header is trusted for tenant attribution without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` (and `topic`/`webhook_id`) are read straight from unauthenticated HTTP headers. `Registry.process` validates the HMAC over the body alone and then dispatches the handler using the unverified `shop` header, breaking the binding `bytes_verified_by_hmac == identity_attributed_to_request`.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

but its `to_signable_string` — the value that actually gets HMAC-verified — only returns the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature strictly from `to_signable_string`: [3](#0-2) 

`Registry.process` accepts any request whose HMAC over the body validates, then immediately trusts `request.shop` (and `request.topic`) — values that were never part of the signed payload — to build `WebhookMetadata` for the handler: [4](#0-3) 

Because the app's `client_secret` (used as the webhook signing key) is the same across every shop that installs the app, an attacker who controls (or installs the app on) their own store can legitimately receive webhooks HMAC-signed with that same secret. They can then replay the exact `raw_body` + `hmac-sha256` header to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` still passes because it only checks the body bytes, so `Registry.process` dispatches the payload to the handler under the spoofed victim shop identity. This is exactly the "bytes verified versus identity attributed" binding break: `to_signable_string` (verified) ⊄ `shop` (acted on).

### Impact Explanation
This is a cross-tenant data confusion vector: an app's webhook handlers (order/customer/inventory processors, GDPR redact handlers, etc.) key their side effects (DB writes, redaction, notifications) off `WebhookMetadata#shop`. An attacker who has any legitimately-signed webhook body (trivially obtainable by installing the same public app on their own store) can cause the app to process/store that data as if it originated from a different, victim shop — a cross-tenant access impact within the defined severity criteria.

### Likelihood Explanation
Requires only: (1) installing the target public app on an attacker-controlled store to receive one genuinely-signed webhook, and (2) sending a forged HTTP request to the host app's webhook endpoint with the captured `raw_body`/`hmac-sha256` and an arbitrary `shopify-shop-domain` value. No access token, `api_secret_key`, or privileged account is required — only unprivileged use of the same publicly installable app, which matches the "unprivileged internet user" threat model.

### Recommendation
Include the shop domain (and ideally the topic/webhook-id) in the signed material, or otherwise cryptographically bind the header claims to the verified body — e.g., verify HMAC over a canonical string built from `shop + topic + raw_body`, or require callers to independently authenticate the shop against installation records for that specific `shop` before trusting `WebhookMetadata#shop`. At minimum, document that `request.shop` is unauthenticated and must be cross-checked against the shop that is currently permitted to be receiving this app's webhooks.

### Proof of Concept
1. Install/subscribe the target app on attacker's own store `attacker.myshopify.com`; capture a legitimate webhook delivery: raw body `B`, header `x-shopify-hmac-sha256: H` (valid because signed with the app's shared `client_secret`).
2. Send a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) validates because it only hashes `B`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) invokes the handler with `shop: "victim.myshopify.com"`, causing the app to process/store attacker-supplied data under the victim shop's identity.
