Audit Report

## Title
CORS wildcard-origin matching in the Gateway HTTP server accepts non-subdomain hosts sharing a suffix, allowing Origin allowlist bypass - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` in `core/services/gateway/network/httpserver.go` strips the `*.` prefix from a configured wildcard CORS origin and then performs a raw `strings.HasSuffix` comparison against the client-supplied `Origin` header, without verifying a domain-label boundary. [2](#0-1)  As a result, an operator who configures `CORSAllowedOrigins = ["https://*.example.com"]` will unintentionally also accept any origin whose host merely ends with the literal string `example.com`, such as `evilexample.com`, which is not a subdomain of `example.com`.

## Finding Description
`isAllowedOrigin` parses both the incoming `Origin` header and each configured allowed origin into scheme/host/port via `splitURL`, matches scheme and port exactly, then checks for an exact host match or, for wildcard entries prefixed with `*.`, does `strings.HasSuffix(originHost, allowedHost)` after removing the `*.` prefix. [3](#0-2)  This comparison lacks a check that `originHost` ends with `"."+allowedHost` (or equals `allowedHost` itself), so any host string that happens to share the trailing bytes — not just true subdomains — will incorrectly match. This function directly gates whether `Access-Control-Allow-Origin`, `Access-Control-Allow-Methods`, and `Access-Control-Allow-Headers` are set in `handleRequest`, and the reflected origin value comes straight from the unauthenticated, client-controlled `Origin` header. [4](#0-3)  There is no other origin-boundary validation elsewhere in the file, and the existing test suite for wildcard matching only exercises true subdomain positives and clearly-differing-domain negatives, never the "shares-suffix-without-dot" boundary case that this bug exploits. [5](#0-4) [6](#0-5) 

## Impact Explanation
This is a legitimate CORS allowlist bypass in the Gateway's HTTP server: an operator using the documented wildcard-origin feature (e.g., to permit `*.example.com`) will inadvertently also authorize any attacker-controlled domain ending in that suffix (e.g., `evilexample.com`), letting a malicious web page issue browser-based cross-origin requests that the browser will treat as CORS-authorized. This maps to the in-scope "cross-user response corruption / allowlist bypass" impact class, since it undermines the intended origin-restriction security boundary of an internet-facing Gateway endpoint.

## Likelihood Explanation
The flaw is triggerable by any unprivileged web client simply by sending a crafted `Origin` header — no credentials, node compromise, or admin access are required. The only precondition is that the Gateway operator has `CORSEnabled = true` with a wildcard entry in `CORSAllowedOrigins`, which is a normal, documented, supported configuration pattern (shown in `sample_config.toml`) rather than a misconfiguration; the bug lies in the code's flawed implementation of this standard feature, not in operator error.

## Recommendation
Require a proper label boundary when matching wildcard hosts, e.g., after stripping `*`, check `originHost == allowedHost[1:] || strings.HasSuffix(originHost, allowedHost)` where `allowedHost` retains the leading `.` (so it matches `example.com` exactly or any `*.example.com` subdomain delimited by a dot), instead of a bare suffix check.

## Proof of Concept
1. Configure the Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.example.com"]`.
2. Send `POST` to the Gateway's configured `Path` with header `Origin: https://evilexample.com`.
3. In `isAllowedOrigin`, `allowedHost` becomes `example.com` after stripping `*.`, and `strings.HasSuffix("evilexample.com", "example.com")` returns `true`, incorrectly matching.
4. `handleRequest` sets `Access-Control-Allow-Origin: https://evilexample.com` in the response, granting CORS authorization to a domain that is not a subdomain of the intended allowlist entry — verifiable as a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` but asserting the header IS set (bug) for an origin like `https://evilexample.com` against allowed origin `https://*.example.com`.

func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}
