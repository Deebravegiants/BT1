### Title
Non-canonical, truncated `user_id` accepted by `QR_CODE_V2` regex and bound as signup identity (`userId`) without UUID validation - ([File: src/plans/qr_scan/user.rs])

### Summary
`QR_CODE_V2`'s `user_id` capture group makes the trailing `-XXXX-XXXXXXXXXXXX` UUID segment optional, so a string like `userid:3bcf883d-ce22-4a03:1` (18 chars, not a valid UUID) is accepted by `Data::try_parse` / `Data::from_v2`, as demonstrated by the existing `test_v2_shortened` test. That truncated, non-canonical string is stored verbatim in `Data::user_id` with no subsequent UUID validation, and is later passed unchanged into `backend::signup_post::request`'s `userId` multipart form field.

### Finding Description
The regex in `src/plans/qr_scan/user.rs` defines the `user_id` group as: [1](#0-0) 
The final `-XXXX-XXXXXXXXXXXX` block is wrapped in a non-capturing `(?:...)?` group, making it optional. This means both a full canonical UUID (`8-4-4-4-12`) and a truncated `8-4-4` string satisfy the pattern. `Data::try_parse` dispatches matches of this regex directly to `Data::from_v2`, which copies the captured string into `Data::user_id` verbatim with no additional validation: [2](#0-1) 
The test `test_v2_shortened` in the same file explicitly documents that `"3bcf883d-ce22-4a03"` — an 18-character, non-canonical, truncated identifier — is accepted and returned as `data.user_id`: [3](#0-2) 
No downstream code re-validates that `user_id` is a well-formed 36-character UUID before use. In `backend::signup_post::request`, the `user_qr_code.user_id` (this same `Data` produced from the user's QR-scan schema) is placed directly into the `userId` multipart field sent to the signup backend: [4](#0-3) 
This is the identity-binding value the backend associates with the uploaded iris codes/biometric custody material for that signup. Since the value is attacker-controlled input from a scanned QR code and is never checked against UUID canonical form (`Uuid::parse_str` or equivalent) anywhere in this parsing/binding path, an attacker can present a QR code encoding an arbitrary short alphanumeric string satisfying `[a-z0-9]{8}-[a-z0-9]{4}-[a-z0-9]{4}` and have it accepted as the "user_id" bound to their own signup session.

### Impact Explanation
This breaks the "identity binding is exact" invariant: the value transmitted as `userId` to the backend signup endpoint, and thus associated with the captured iris biometric custody material, is not guaranteed to be a canonical UUID. Depending on how the backend or downstream systems key/index signups by `userId` (e.g., collision with another shortened prefix, or string-based lookups assuming UUID format), this could lead to identity confusion, malformed custody records, or ambiguity in which biometric data is bound to which nominal identity. It matches a Worldcoin/Orb bounty impact of "wrong identity binding to signup/custody material" — however, this is limited to the orb-core client-side acceptance issue; whether the backend itself rejects malformed UUIDs is outside this repo's visibility.

### Likelihood Explanation
Trivially reproducible by any attacker able to present a QR code to the Orb during their own signup flow (unprivileged, no operator/root access needed). The QR content is entirely attacker-chosen and only needs to match the permissive regex. The existing unit test `test_v2_shortened` already demonstrates the acceptance behavior, confirming this is not a hypothetical edge case but an exercised code path.

### Recommendation
Make the trailing UUID segment mandatory in `QR_CODE_V2` (remove the `?` on the `(?:-[a-z0-9]{4}-[a-z0-9]{12})` group), and/or validate the captured `user_id` string with `uuid::Uuid::parse_str` (rejecting non-canonical or truncated values) in `Data::from_v2` before constructing `Data`, ensuring only a full, valid UUID can ever be bound as `userId` in `backend::signup_post::request`.

### Proof of Concept
Add a fuzz/property test asserting the invariant:
```rust
#[test]
fn qr_code_v2_only_accepts_full_uuid() {
    use rand::Rng;
    let mut rng = rand::thread_rng();
    for _ in 0..10_000 {
        let candidate: String = /* generate random ascii-ish "userid:...:digits" strings,
                                    including 8-4-4 truncated forms */;
        if let Some(captures) = QR_CODE_V2.captures(&candidate) {
            let user_id = captures.name("user_id").unwrap().as_str();
            assert!(
                uuid::Uuid::parse_str(user_id).is_ok(),
                "accepted non-UUID user_id: {user_id}"
            );
        }
    }
}
```
Expected current result: fails immediately, since `"userid:3bcf883d-ce22-4a03:1"` (as in `test_v2_shortened`) is accepted with `user_id == "3bcf883d-ce22-4a03"`, which is not a valid UUID, and that same string would be forwarded as the `userId` field in `backend::signup_post::request`.
