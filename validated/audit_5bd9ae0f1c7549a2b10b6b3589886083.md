Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `X-Shopify-Shop-Domain` header as the tenant identity handed to the app's handler. Because the app-wide `client_secret` (`Context.api_secret_key`) is the same across every shop that installs the app, any unprivileged user who legitimately installs the app on their own store can capture a validly-signed webhook and replay it with a forged shop-domain header, causing the host application to process attacker-controlled data under a victim tenant's identity.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string` [1](#0-0) . For webhooks, `to_signable_string` returns only the raw body, `@raw_body`, and never includes the shop domain: [2](#0-1)  The `shop` accessor is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material at all: [3](#0-2) 

`Registry.process` validates only the HMAC (which covers the body), then forwards `request.shop` unchanged straight to the app's handler as the authoritative tenant identity: [4](#0-3) 

This is documented as a trusted field: the gem's own docs instruct app authors to key their tenant lookups off `data.shop` [5](#0-4) , and `WebhookMetadata` exposes `shop` as a plain `String` const with no indication it is unauthenticated [6](#0-5) .

The broken identity binding is:
`hmac_valid_for(body) == hmac_valid_for(body, shop)` — the gem treats these as equivalent, but only the former is actually checked.

Because `Context.api_secret_key` is a single app-wide secret shared by every shop installation (not a per-shop secret), any unprivileged user who has installed the app on their own store receives genuine webhooks with a valid HMAC computed over a body they fully control (e.g. by editing a product/order on their own store to shape the body). They can then replay that exact `body` + `hmac-sha256` value to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still succeeds (it never looked at the shop header), and `Registry.process` hands the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant/authentication boundary the webhook mechanism is supposed to guarantee: a value that host applications use to decide *which merchant's data store to write to* is never authenticated, letting one merchant inject attacker-chosen webhook payloads into another merchant's tenant context. This is a cross-tenant access primitive, matching the "Critical - cross-tenant access" impact tier.

### Likelihood Explanation
Any user can obtain the app's client_secret-signed webhooks simply by installing the app themselves (a normal, unprivileged action) — no credential theft or leaked secret is required. Constructing and sending the replay request is trivial HTTP tampering (changing one header) once a legitimate webhook is captured.

### Recommendation
Include the shop domain (and ideally webhook id / topic) inside the HMAC-covered signable string for webhooks — e.g. concatenate `shop-domain` with the raw body before computing/verifying the HMAC — or, if the current header cannot be changed for backward compatibility with Shopify's real signing scheme, require host applications to independently verify that `shop` corresponds to a shop that actually has this specific `webhook_id`/topic registered (e.g. via a lookup or a secondary signed claim) before trusting it for tenant routing, and document this requirement prominently instead of presenting `WebhookMetadata#shop` as trusted.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, obtaining valid webhook deliveries signed with the app's single shared `api_secret_key`.
2. Attacker triggers/receives a webhook whose body is fully under their control (e.g. `orders/create` for an order they place), capturing `raw_body` and the valid `x-shopify-hmac-sha256` value.
3. Attacker replays the request to the app's webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged but setting `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the untouched body [7](#0-6) .
5. The handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` and attacker-controlled `body`, and the host app processes/stores this as if it were genuine data from the victim tenant.
