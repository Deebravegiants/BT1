### Title
Read-only reentrancy in Tron `IntentGatewayV2.withdraw()` — escrow balance decremented after external transfer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` decrements the public per-commitment escrow mapping `_orders[commitment][token]` **after** it sends the corresponding assets via a low-level external call, instead of before. This is the same class of bug as Bond Protocol's `BondFixedTermTeller` M-3 finding: state (`_orders`), which downstream integrators can legitimately read to price/attest to escrowed amounts, is stale for the duration of the external call, letting a beneficiary-controlled receiver observe or act on outdated escrow accounting during the callback window.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` loops over the tokens to release and, for each one, performs the external transfer *before* updating the corresponding escrow-accounting slot: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    // redeem escrowed tokens
    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;
        ...
```

The native-ETH branch (`beneficiary.call{value: amount}("")`) hands control to `beneficiary` **before** `_orders[body.commitment][token]` is decremented. `_orders` is a `public` mapping, exposed to any off-chain or on-chain consumer via `_orders(commitment, token)`.

For comparison, the audited/production EVM path already applies the correct checks-effects-interactions ordering: [2](#0-1) 

```solidity
_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```

Here the accounting is updated **before** the transfer, exactly the "Recommendation" pattern in the referenced Bond Protocol report (update supply/state first, then perform the effect that hands control away). The Tron contract's `withdraw()` reverses this order and thus reintroduces the same bug class the EVM contracts were already hardened against.

`withdraw()` is reachable directly and unauthenticated-beneficiary-controlled through:
- `cancelOrder()` for same-chain orders, where `body.beneficiary = order.user` and `msg.sender`/`order.user` is fully attacker chosen — an attacker can place a same-chain order naming a malicious contract as beneficiary and immediately self-cancel, triggering `withdraw()` with that contract as the ETH recipient: [3](#0-2) 
- `onAccept()` for `RedeemEscrow`/`RefundEscrow` cross-chain settlement, where the beneficiary is `msg.sender` of the original `fillOrder` or `order.user`, again attacker-controllable: [4](#0-3) 

`_filled[body.commitment]` is set at the very top of `withdraw()` (line 693), which blocks a reentrant call back into `cancelOrder`/`onAccept` **for the same commitment**. This prevents direct fund-draining reentrancy on the same order. However, it does **not** protect the *read* side: while `_orders[body.commitment][token]` is still un-decremented, any other on-chain contract that reads this public mapping (e.g., a lending/collateral integration, a UI/quoting contract, or another protocol's accounting logic that trusts `_orders` to reflect currently-escrowed, unclaimed funds) observes a stale, overstated escrow balance during the attacker's callback. This mirrors exactly the read-only reentrancy scenario described in the Bond Protocol report, where the vulnerable contract itself is not directly drained but third parties relying on its exposed state can be manipulated into miscalculating.

### Impact Explanation
Per the same class as the referenced report, `IntentGatewayV2` (Tron) itself is not directly at risk of theft because of the `_filled` reentrancy gate, but this is a state/accounting integrity bug: any Hyperbridge-integrated protocol (solver contracts, price oracles, treasury/collateral managers, or any external contract reading `_orders(commitment, token)`) that queries escrow state mid-callback will see funds as still escrowed when they have effectively already been paid out, or vice versa depending on how they interpret the value. This can cause double-counting of escrowed collateral, incorrect solver accounting, or manipulation of any downstream logic gated on `_orders`, i.e. unsound state exposed by a core dispatch/settlement contract, satisfying "unsound state commitment" / unauthorized-app-action-adjacent impact for any consumer relying on this public accounting mapping.

### Likelihood Explanation
Any user can trigger the vulnerable code path without special privileges: placing a same-chain order with a malicious contract as `order.user`/beneficiary and calling `cancelOrder()` (or being the fill beneficiary on a cross-chain `RedeemEscrow`/`RefundEscrow` settlement) is sufficient to force `withdraw()` to hand control to attacker code via a native-ETH `.call` before the escrow mapping is updated. No governance, relayer, or admin cooperation is required — a single unprivileged transaction reaches this path.

### Recommendation
Apply the same checks-effects-interactions fix already present in `evm/src/apps/intentsv2/IntentsBase.sol` to the Tron `withdraw()`: decrement `_orders[body.commitment][token]` (and the `TRANSACTION_FEES` entry) *before* performing the external `.call`/ERC20 transfer, e.g.:

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;

if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
```
Apply the identical fix to the transaction-fee release block later in the same function.

### Proof of Concept
1. Attacker deploys `MaliciousBeneficiary` with a `receive()` hook that, on first invocation, calls a victim/integrator contract's function that reads `IntentGatewayV2._orders(commitment, address(0))` (or performs any logic dependent on that value) to demonstrate the observed value is still the pre-withdrawal (stale) amount.
2. Attacker calls `placeOrder` with a same-chain `Order` where `order.user = MaliciousBeneficiary`, `order.source == order.destination`, and a native-ETH input amount `X`.
3. Attacker (as `order.user`) calls `cancelOrder(order, options)`.
4. `cancelOrder` → `withdraw(body, true)` sets `_filled[commitment] = beneficiary`, then in the loop sends `X` wei to `MaliciousBeneficiary` via `beneficiary.call{value: amount}("")` **before** `_orders[commitment][address(0)] -= amount` executes.
5. Inside `receive()`, `MaliciousBeneficiary` reads `intentGateway._orders(commitment, address(0))` and observes it still equals `X` (not yet zeroed), demonstrating the read-only reentrancy window; any integrator contract making decisions off this value during the callback is misled.

        bytes32 commitment = keccak256(abi.encode(order));

        address hostAddr = host();

            // Same-chain: validate locally and refund immediately
