The contract does have a `withdraw` path, so the analog must be narrower. Let me check whether tokens sent directly to the pool (not via `supply`) are recoverable, since `cash` is credited only on the controller's word.### Title
Tokens transferred directly to the liquidity pool are permanently locked — the pool has no recovery path and withdraw gates on tracked `cash`, never the real balance - ([File: contracts/pool/src/cache/cash.rs])

### Summary
The USSD report describes a contract that can take user funds but offers no redemption function, locking deposits forever. The same shape exists in XOXNO Lending's liquidity pool for any tokens that arrive outside the controller-mediated flows: `cash` is a pure bookkeeping number credited only on the controller's word, and every outbound leg (`withdraw`, `borrow`, `claim_revenue`, `recapitalize` refund, `flash_loan`) is gated on `cash` rather than the real token balance. Tokens sent directly to the pool address therefore inflate `token.balance(pool)` above `cash` with no code path that can ever move them out.

### Finding Description
The pool's README states the invariant explicitly: "`supply`, `repay` and `recapitalize` all credit `cash` on the controller's word, without verifying the transfer. `cash` is a bookkeeping number." Every outbound gate uses that number:

- `withdraw` → `gate_and_debit` → `cache.require_reserves(net_transfer)` compares against `self.cash`, then `debit_cash` (`contracts/pool/src/ops/withdraw.rs:111-119`, `contracts/pool/src/cache/cash.rs:15-41`).
- `borrow` and `claim_revenue` likewise check `InsufficientLiquidity`/`PoolInsolvent` against tracked `cash`, and `flash_loan` reconciles balances only for strict equality of its own principal+fee pull, not for sweeping excess (`contracts/pool/README.md:56-63`).
- `recapitalize` is the only function that compares bookkeeping to reality, but it only *credits* `cash` up to the backing shortfall — it never transfers stray tokens out; it refunds only what the payer just sent (`contracts/pool/src/ops/recapitalize.rs:44-67`).
- There is no `sweep`/`rescue`/`skim` entrypoint on the pool ABI: the fourteen `#[only_owner]` functions are enumerated in `contracts/pool/README.md:7-14` and none returns untracked balance to anyone.

So once an unprivileged address calls `token.transfer(pool, amount)` on a listed market asset, those tokens are inside the contract forever: `cash` never reflects them, no withdrawal can be sized against them, and no governance or owner function can eject them either.

### Impact Explanation
Permanent freezing of funds: any user who transfers tokens directly to the pool contract (a realistic mistake on Soroban, where the pool address is discoverable and the token ABI allows transfers to any address) loses them irrecoverably. The stranded balance also cannot even serve as an emergency backstop, since `backing_shortfall` is computed on `cash`, not `token.balance`.

### Likelihood Explanation
Requires an externally-triggered user error rather than an attacker's profitable action, so likelihood is low-to-moderate — but the freeze is absolute with no remediation path, matching the "locked funds forever" impact of the reference finding. Severity: Medium.

### Recommendation
Add an owner-only `sweep(asset, to)` entrypoint that transfers `token.balance(pool) - cash - accrued obligations` (or, for non-market assets, the full balance) out of the pool, or document and enforce that the pool must never hold direct-transfer balances by measuring `balance_delta` in `supply`/`repay` the way `flash_loan` already does with strict equality.

### Proof of Concept
1. `controller.supply(...)` normally so a market for `hub_asset` exists; pool `cash` = C, `token.balance(pool)` = C.
2. Any address calls `token::Client::transfer(user, pool, 1_000)` directly — succeeds; `cash` is still C, balance is now C + 1_000.
3. Attempt every exit: `withdraw`/`borrow` revert with `InsufficientLiquidity` (112) the moment `net_transfer > cash`; `recapitalize` with `backing_shortfall == 0` refunds the entire payment; `claim_revenue` is bounded by revenue shares inside `cash`.
4. `token.balance(pool)` remains C + 1_000 permanently; the 1_000 is unrecoverable by any account, including the owner.
