### Title
Webhook `shop` (tenant) identity is trusted from an unauthenticated header while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), `topic`, `api_version`, and `webhook_id` from HTTP headers that are never included in the HMAC signature computation. `Registry.process` validates only the raw request body against the HMAC and then unconditionally trusts these header-derived values (in particular `shop`) when constructing `WebhookMetadata` and dispatching to the app's handler.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for a webhook request `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, none of which are folded into the signable string used for verification: [2](#0-1) 

`Registry.process` checks HMAC validity of the body only, then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's own webhook handler, with no cross-check that the header-derived `shop` corresponds to what was authenticated: [3](#0-2) 

This is the same class of bug as the external report: an identity-relevant field (`shop`, i.e., the tenant binding) is *acted on* by the code but is *not covered* by the cryptographic binding (HMAC) that is supposed to authenticate the request. The bytes that are verified (the body) are not the same as the bytes that are parsed for tenant identity (the `shop` header).

Because HMAC validation succeeds for any request whose body matches a signature computed with the app's secret over that exact body, and the `shop` header is completely independent of that signature, a party who can obtain one legitimately-signed webhook delivery for a body (e.g., by installing the app on their own shop and receiving a real webhook, or by replaying/relaying a previously captured webhook) can resend that same body with an arbitrary `X-Shopify-Shop-Domain` / `shopify-shop-domain` header. The gem will report the HMAC as valid and the app's handler will be invoked believing the data belongs to the attacker-chosen shop, when in fact the shop identity was never authenticated.

### Impact Explanation
This breaks the tenant-identity binding: `shop` (header, unauthenticated) ≠ `shop` (the value actually bound by the HMAC, which is none — the HMAC binds nothing about shop at all). Any app logic that keys per-tenant state, feature flags, billing, or session lookup off `WebhookMetadata#shop` can be tricked into applying one merchant's webhook payload to a different merchant's tenant context — a cross-tenant confusion. Per the rubric this falls under "Critical - cross-tenant access" since it lets an attacker misattribute authenticated-looking webhook data to an arbitrary shop of their choosing without holding that shop's credentials.

### Likelihood Explanation
Medium: the attacker needs at least one legitimately HMAC-signed webhook body (trivially obtainable by installing the app, even on a free/dev store, and capturing any webhook delivery, since the body itself carries no shop-binding), and network access to POST it to the app's webhook endpoint with a forged shop header — no access to `api_secret_key`, tokens, or the target merchant's credentials is required.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, not just the raw body — e.g., verify against `shop + raw_body` or otherwise cryptographically tie the header-derived shop to the signed payload, mirroring how the OAuth `AuthQuery`/`HmacValidator` binds `shop` into `to_signable_string`. At minimum, document and encourage host applications to independently confirm `WebhookMetadata#shop` against a shop known to be associated with the specific webhook subscription/callback endpoint before trusting it for tenant-scoped operations.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and receive a real webhook, e.g. body `{}` with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of "{}">`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
2. Resend the exact same request to the app's webhook endpoint, only changing the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `Utils::HmacValidator.validate` recomputes the HMAC solely from the untouched raw body `{}` and it still matches, per: [4](#0-3) 
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `shop` header, and the app's handler executes believing the payload originated from `victim-shop.myshopify.com`: [5](#0-4)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
