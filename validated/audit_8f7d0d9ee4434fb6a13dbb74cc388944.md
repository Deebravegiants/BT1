This confirms the vulnerability path. `Registry.process` (line 189-200 in `lib/shopify_api/webhooks/registry.rb`) only validates `Utils::HmacValidator.validate(request)`, which computes the signature over `request.to_signable_string` — and `Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`). The `shop-domain` header, however, is read separately via `request.shop` (`lib/shopify_api/webhooks/request.rb:21-23`) and passed straight into `WebhookMetadata.new(... shop: request.shop ...)` at `lib/shopify_api/webhooks/registry.rb:198-199`, with no cross-check that the signed body actually belongs to that shop.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for a given shop once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC signature is computed only over the raw request body [1](#0-0) . The `shop` value handed to the application's webhook handler comes from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header [2](#0-1) , which is never included in the signable string.

### Finding Description
The identity binding that should hold is: `shop domain used for tenant routing == shop domain cryptographically bound to the signed payload`. In this gem that equality does not hold.

`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it against the `hmac` field using `OpenSSL.secure_compare` [3](#0-2) . For webhooks, `to_signable_string` is defined as just `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all parsed from HTTP headers that are completely outside the signed material [4](#0-3) .

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)` — and then immediately builds `WebhookMetadata` using `request.shop` (the header value) as the tenant identifier passed to the host application's handler [5](#0-4) .

Critically, `Context.api_secret_key` — the HMAC key — is the app's single `client_secret`, shared across every merchant that has installed the app; it is not per-shop. Any unprivileged internet user can install the app on a store they control (a normal, unprivileged action) and thereby legitimately receive genuine webhook deliveries: valid `(body, hmac)` pairs signed with that same shared secret. Because the signature never binds `shop`, that attacker can replay the exact same body+HMAC to the app's webhook endpoint while substituting `x-shopify-shop-domain` for a victim shop they do not control. `HmacValidator.validate` will pass (the body and secret are unchanged), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` equal to the victim's domain, causing the host application to process attacker-controlled data (order/customer/product payloads, etc., that the attacker fully authored on their own shop) as though it originated from the victim tenant.

### Impact Explanation
This breaks tenant isolation ("cross-tenant access"): the gem hands the application forged data associated with a shop that never sent it, using only actions available to any unprivileged app-installer. Depending on how the host app consumes `WebhookMetadata#shop` (e.g., to key database writes, to trigger fulfillment/inventory actions, or to look up which merchant's records to mutate), an attacker can inject or corrupt data attributed to a shop that isn't theirs, entirely from the outside, without ever needing the app's `api_secret_key`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Likelihood is high for any app that has more than one merchant installed (the normal case for any public/multi-tenant Shopify app). The only prerequisite is that the attacker installs the target app on a shop they control — a routine, unprivileged action — and then crafts a raw HTTP request to the app's registered webhook endpoint with a spoofed `shop-domain` header while reusing the legitimately-received `hmac` and body. No secret material belonging to the victim or the app owner is required.

### Recommendation
Bind the shop identity into the material that is verified. At minimum, `Webhooks::Request#to_signable_string` (or the validation step in `Registry.process`) should incorporate the `shop-domain` header (and ideally `webhook-id`) into what is HMAC-checked, or `Registry.process` should independently confirm that the resolved `shop` corresponds to a shop actually known/subscribed to that specific `webhook_id`/topic (e.g., by querying Shopify for the webhook subscription's owning shop, or requiring the host app to correlate `webhook_id` against its own registration records) before trusting `request.shop` to select tenant context.

### Proof of Concept
1. Attacker creates their own dev store `attacker-shop.myshopify.com` and installs the target app (normal, unprivileged flow).
2. The app registers, e.g., `orders/create` webhooks via `ShopifyAPI::Webhooks::Registry.register` for their own shop.
3. Shopify delivers a legitimate webhook to the app's endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC over body, using Context.api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   x-shopify-webhook-id: <id>
   Body: {"id": 1, ... attacker-authored order payload ...}
   ```
4. Attacker captures this `(body, hmac)` pair and replays it directly to the same public webhook endpoint, only changing the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
   (same body, same `x-shopify-hmac-sha256`).
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-hashes `@raw_body` — this succeeds because the body was not altered [1](#0-0) .
6. `Registry.process` then invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-authored data>, ...)` [6](#0-5) , causing the host application to process attacker-controlled data under the victim shop's identity.
