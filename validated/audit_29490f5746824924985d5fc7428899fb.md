Based on the code I reviewed, the closest structural analog to this bug class exists in the ISMP request/response handlers, where a **single bad element inside a batch of otherwise-independent messages aborts delivery of the entire batch**, exactly mirroring the oracle bug where one stale/reverting oracle blocks the whole `_getData()` call.

### Title
Single expired/stale leaf in a batched `handlePostRequests`/`handleGetResponses` call reverts delivery of all other valid requests in the batch - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`handlePostRequests` and `handleGetResponses` in `HandlerV2.sol` process an array of independent, unrelated POST requests / GET responses bundled under a single merkle proof. Both functions loop over every leaf and `revert` immediately if any single leaf fails a per-item check (timeout, unknown request, duplicate), before any of the batch is dispatched. Because delivery of the *entire* batch is gated on *every* item passing, one bad/expired element denies delivery of all the other, still-valid, unrelated messages bundled alongside it — the same "one failing data source reverts everything" pattern as the reported oracle bug.

### Finding Description
In `handlePostRequests`, the function first loops over all requests to validate destination and timeout, then verifies a single MMR multiproof covering the whole batch, and only afterward dispatches each request: [1](#0-0) 

If timestamp progresses (e.g. due to mempool delay, gas-price congestion, or an attacker front-running the relayer's transaction with filler transactions) such that even one request in the batch crosses its `timeout()` before the transaction lands, the `revert MessageTimedOut()` fires and the whole call reverts — the other requests in the same batch, which are still within their timeout window, are never dispatched via `host.dispatchIncoming`.

The same pattern exists in `handleGetResponses`, where an unknown/duplicate response for a single leaf reverts the whole set: [2](#0-1) 

This mirrors `UpdateWeightRunner._getData()` in the referenced report, where a single oracle result timing out (`INVORCLVAL`/`INVLDDATA`) reverts the aggregate call that other, live oracle values also depend on. Here, one leaf's failure (timeout/duplicate/unknown) similarly reverts the shared multiproof-verified batch, even though the merkle-proof verification and per-leaf state are otherwise entirely independent per request.

Additionally, `batchCall` is documented as atomic — any single failed sub-call reverts the entire multi-call batch: [3](#0-2) 

compounding the effect: relayers who batch several `handlePostRequests`/`handleGetResponses` calls together (e.g. across different destination applications) via `batchCall` see the whole set fail if a single one contains a stale item.

### Impact Explanation
This causes a denial of service to message delivery: a single expired or already-known request/response embedded in a relayer's batch blocks delivery of every other, unrelated, still-valid message batched alongside it. Since relayers batch for gas efficiency, this increases the likelihood that legitimate messages destined for unrelated applications are delayed or repeatedly fail to land, especially under network congestion or if an adversary can grief by delaying inclusion of the transaction until one leaf expires. This does not directly enable theft, but it is a genuine route-unable-to-deliver-messages condition affecting `handlePostRequests`/`handleGetResponses`, which are the sole permissionless code paths for delivering POST requests and GET responses into `HandlerV2`.

### Likelihood Explanation
Timeout races are a normal, expected occurrence for relayers batching many messages with varying timeout windows; and mempool delay or front-running to push a transaction past a request's timeout is a realistic, low-cost griefing vector. No special privilege is needed — any observer of the mempool can attempt to delay inclusion of a relayer's batch. The likelihood of accidental occurrence (network congestion) is high in practice; the likelihood of deliberate griefing is moderate.

### Recommendation
Do not perform per-leaf timeout/duplicate/unknown checks that abort the entire batch. Instead, evaluate each leaf independently in the dispatch loop: for a leaf that fails an individual check (e.g., timed out), skip dispatching that item (optionally emitting an event) and continue processing the remaining leaves so the merkle proof verification (which covers the whole set) and dispatch of still-valid items are not blocked by one stale entry. Alternatively, encourage relayers to homogenize timeout windows within a single batch and reserve the current fail-fast behavior only for genuinely batch-wide invariants (e.g. proof height/root validity), not per-item timeouts or duplication.

### Proof of Concept
1. A relayer submits `handlePostRequests(host, request)` with `request.requests` containing N leaves from different applications, all within their timeout windows at broadcast time, all committed under one merkle root.
2. Due to network congestion or an attacker submitting cheap filler transactions to delay inclusion, the transaction lands after leaf `k`'s `timeout()` has elapsed while leaves `1..N` excluding `k` are still valid.
3. Execution reaches the destination/timeout check loop [4](#0-3) , hits `revert MessageTimedOut()` for leaf `k`, and the entire call reverts.
4. None of the N-1 still-valid requests are dispatched via `host.dispatchIncoming`, even though their proofs and states are perfectly valid — the relayer must now reconstruct and resubmit a new batch excluding leaf `k`, and if congestion persists, another leaf may expire before resubmission lands, repeating the denial.

    /**
     * @dev Process a batch of encoded handler calls in a single transaction.
     * Uses delegatecall to self so msg.sender is preserved and storage writes
     * happen in this contract's context. Atomic, any failure reverts the entire batch.
     * @param calls - array of ABI-encoded handler function calls
     */
    function batchCall(bytes[] memory calls) external {
        uint256 len = calls.length;
        for (uint256 i = 0; i < len; ++i) {
            (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
            if (!success) revert BatchCallFailed(i, returnData);
        }
    }
