Root cause identified. The webhook HMAC only signs the raw request body, while the `shop-domain` (and `topic`, `webhook-id`) headers used downstream are not part of the signed content, breaking the binding between "who Shopify says the payload is for" and "what the signature actually vouches for."

### Title
Webhook shop-domain header is not covered by HMAC signature, enabling cross-tenant webhook data spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `HmacValidator.validate` only proves the integrity of the JSON body — not the `shop-domain`, `topic`, or `webhook-id` headers that `ShopifyAPI::Webhooks::Registry.process` subsequently trusts to route and label the event.

### Finding Description
`Utils::HmacValidator.validate` computes/compares the signature over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw body, while `shop`, `topic`, and `webhook_id` are read directly and unauthenticated from HTTP headers: [2](#0-1) 

`Registry.process` validates the HMAC (covering body only) and then trusts `request.shop`/`request.topic`/`request.webhook_id` — none of which are covered by that signature — to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

The identity binding that should hold is: `hmac_valid(raw_body) == data_is_authentically_for(shop_header, topic_header)`. Because the signature only certifies `raw_body`, an attacker who possesses one legitimate `(raw_body, hmac)` pair — trivially obtainable by owning any shop that installs the app and receiving one webhook for it — can resend that exact body/hmac pair with an arbitrary `shopify-shop-domain` (or `shopify-topic`/`shopify-webhook-id`) header. `Utils::HmacValidator.validate` still returns `true` because it only re-derives the signature from the unchanged body, and `Registry.process` will hand the attacker-chosen `shop` value to the app's handler alongside the original body content.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook delivery: an unprivileged, self-onboarded merchant (attacker) can cause the host application to process a webhook body as if it originated from a different shop, corrupting per-shop application state, triggering shop-scoped side effects (e.g. app-subscription/billing state changes, inventory sync, order fulfillment records) under another tenant's identity. This is a cross-tenant access issue caused entirely by the gem's incomplete signable content, matching the Critical bar for cross-tenant access.

### Likelihood Explanation
Any developer/attacker can register their own free/dev shop, install the target app, and receive at least one genuine webhook with a valid `(raw_body, hmac)` pair for a topic that's also meaningful for other shops (e.g. `app/uninstalled`, `shop/update`). Replaying it against the app's public webhook endpoint with a forged `shopify-shop-domain` header requires no secret, token, or privileged access — only knowledge of this gem's documented behavior that the signature check ignores headers.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the signable content used for HMAC verification, or independently verify that `request.shop` matches an expected/known shop for the installation before dispatching to the handler in `Registry.process`. At minimum, document and defensively re-validate that the `shop` passed into `WebhookMetadata` corresponds to a shop with an active, matching webhook registration rather than trusting the header verbatim.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers/receives one legitimate webhook, e.g. `app/uninstalled`, capturing the exact `raw_body` and the `shopify-hmac-sha256` header value.
2. Attacker (or any internet user with this pair) sends a POST to the app's public webhook endpoint with the identical `raw_body`, identical `shopify-hmac-sha256`, but `shopify-shop-domain: victim-shop.myshopify.com` and/or a different `shopify-topic`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` [4](#0-3)  which succeeds because only `@raw_body` is signed [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's body content, even though Shopify never sent this event for that shop.
