### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes the shop identity from an unauthenticated HTTP header (`X-Shopify-Shop-Domain`), while the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. Any actor who can obtain one legitimately-signed webhook body (e.g. by installing the app on their own store) can replay that exact body/signature pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the gem will pass that spoofed shop value on to the host application's webhook handler as authenticated data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are read straight from HTTP headers, with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e. the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` performs exactly this HMAC check and then immediately forwards `request.shop` — the unauthenticated header value — into the webhook handler as the tenant identity, alongside the (HMAC-verified) body: [4](#0-3) 

The broken identity binding is:

`bytes verified by HMAC (raw_body signed with api_secret_key)` ≠ `shop claimed and acted upon (shop-domain header, unauthenticated)`

Because Shopify apps use a single `api_secret_key` shared across every shop that installs the app, a legitimately-signed webhook obtained from *any* one installation (including the attacker's own store) is a valid `(body, hmac)` pair for *every* other installation of the same app. The gem provides no mechanism (and the header is not part of the signed payload) to prevent that same valid pair from being replayed with a different `shop-domain` claim.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook delivery. An attacker with a normal, unprivileged merchant account (their own shop, on which the target app is installed) can:
1. Trigger a real webhook from Shopify to capture a valid `(raw_body, hmac)` pair signed with the app's shared secret.
2. Send that same body and HMAC directly to the app's webhook endpoint, replacing only the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain.
3. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC successfully (it was legitimately signed) and calls the registered handler with `shop: <victim-shop>` and the attacker's chosen body content.

Depending on how the host application consumes `WebhookMetadata#shop` (e.g. selecting the victim's DB row/session to update inventory, mark orders paid, process `app/uninstalled`, GDPR/data-request topics, etc.), this enables cross-tenant data corruption or state manipulation attributed to a shop the attacker does not own — no `api_secret_key`, access token, or privileged account is required beyond a normal one-store merchant/app install.

### Likelihood Explanation
High: the attacker only needs an ordinary install of the target app on any shop they control (a completely standard, unprivileged action for any Shopify merchant/developer), the ability to trigger at least one webhook of the topic they want to abuse, and the ability to send an arbitrary HTTP request to the app's public webhook endpoint (which is, by design, internet-reachable). No secret material or credential theft is needed.

### Recommendation
**Short term:** Include the shop identity (and other trust-relevant headers such as `topic`, `api-version`, `webhook-id`) as part of the HMAC-signed material, or otherwise verify with the Admin API/session store that the `shop-domain` claimed in the header actually corresponds to a shop with a currently valid installation before trusting `request.shop` in `Registry.process`. At minimum, document that `WebhookMetadata#shop` must not be trusted without an independent authorization check tying it to an existing offline session for that exact shop.

**Long term:** Adopt a signing scheme (or wrapper contract) where every field the host application is expected to act on is cryptographically bound to the signature, consistent with how `AuthQuery#to_signable_string` already includes `shop` in its signed parameters for OAuth callbacks.

### Proof of Concept
1. Install the target Shopify app on `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Trigger any subscribed webhook topic (e.g. update a product to fire `products/update`), and capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256: H` header sent to the app's webhook endpoint (this HMAC is valid because it's signed with the app's shared `api_secret_key`, the same secret used for all shops).
3. Send a new HTTP POST to the same app webhook endpoint with:
   - Body: `B` (unmodified)
   - `X-Shopify-Hmac-Sha256: H` (unmodified)
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (attacker-controlled)
   - `X-Shopify-Topic`: unmodified or attacker's choice
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `H` against `B`.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process attacker-supplied data under the victim shop's identity.
