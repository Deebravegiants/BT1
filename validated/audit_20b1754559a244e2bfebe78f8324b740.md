### Title
PoaBridge.describeWithdrawal mismatches same-asset withdrawals in a batch, causing cross-reported status/txHash - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the correct withdrawal record only by `assetId`, never by the `WithdrawalIdentifier.index`. When a single NEAR intent transaction contains two `ft_withdraw` intents for the same POA asset, both `watchWithdrawal(wid0)` and `watchWithdrawal(wid1)` receive the same POA API response array and both `findMatchingWithdrawal` calls deterministically return the same array element, so the two logically independent withdrawals are reported with identical `(status, txHash)`.

### Finding Description
The broken equality: `describeWithdrawal(wid0).status` should equal the on-chain outcome of physical withdrawal 0, and `describeWithdrawal(wid1).status` should equal the on-chain outcome of physical withdrawal 1. Because matching ignores `index`, both calls can return the outcome of the *same* physical withdrawal.

Code path:
- `describeWithdrawal` (poa-bridge.ts:313-343) calls `getWithdrawalStatusWithRetry` (poa-bridge.ts:345-372), which hits `poaBridge.httpClient.getWithdrawalStatus({ withdrawal_hash: args.tx.hash }, ...)`. For a batch intent, `args.tx.hash` is the *same* NEAR tx hash for every withdrawal in that tx, so both `wid0` and `wid1` fetch an identical `response.withdrawals` array.
- `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` (poa-bridge.ts:418-427) does `withdrawals.find((w) => \`nep141:${w.data.near_token_id}\` === assetId)`. When two withdrawals share the same `assetId`, this always returns the *first* array element that matches, for both `wid0` and `wid1` — the `index` field on `WithdrawalIdentifier` (set per-route in `createWithdrawalIdentifier`, poa-bridge.ts:295-311, and assigned in `createWithdrawalIdentifiers`, withdrawal-watcher.ts:80-107) is never consulted in `describeWithdrawal` or `findMatchingWithdrawal`.
- The code even documents this as a known limitation: "NOTE: Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported." (poa-bridge.ts:409-417, and duplicated in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts:135-143`).

Nothing in `supports()`, `validateWithdrawal`, `createWithdrawalIdentifiers`, or `watchWithdrawal` rejects or reorders same-asset PoA batches; `createWithdrawalIdentifiers` (withdrawal-watcher.ts:80-107) happily assigns `index: 0` and `index: 1` to two same-asset PoA withdrawals and proceeds. Since the POA API "withdrawals" array is documented as unsorted relative to submission order, whichever element the API happens to place first is returned for *both* logical withdrawals, so a PENDING withdrawal (wid0) can be reported as COMPLETED with wid1's `transfer_tx_hash`, while the actually-completed wid1 is reported as PENDING/whatever the other array element's status is. ### Impact Explanation
An integrator's automated flow (via `watchWithdrawal`/`sdk.createWithdrawalCompletionPromises`) can be told the wrong withdrawal has `status: "completed"` with a real `txHash` belonging to a *different* physical withdrawal, while the actually-completed one is reported pending. This causes the integrator to credit/settle/unlock funds tied to a withdrawal that never landed on-chain, and to potentially treat the actually-landed withdrawal as still pending indefinitely (stuck until manual reconciliation). This matches the "High" impact category: "a status or hash misreport making an integrator credit or refund twice" / "a withdrawal stuck until manual intervention." It is deterministic and repeatable for every batch containing ≥2 same-asset PoA withdrawals, not merely a race condition.

### Likelihood Explanation
Preconditions: an ordinary unprivileged user (or integrator-forwarded batch) submits a single NEAR intents transaction containing two `ft_withdraw` intents for the same POA asset (same `near_token_id`), both routed to PoaBridge. This requires no special privilege — any user can submit such a batch. Attacker cost is a single transaction with two withdrawal intents to two different destination addresses; no admin/relayer/RPC compromise needed. Because matching is purely by `assetId` and ignores `index`, the mismatch occurs deterministically whenever the two withdrawals differ in on-chain completion timing (one pending, one completed) — a very plausible race in normal bridge operation given asynchronous chain confirmations.

### Recommendation
Track per-withdrawal correlation explicitly instead of matching by `assetId` alone: use `WithdrawalIdentifier.index` combined with a stable ordering key from the POA API response (e.g., sort both the withdrawal params sent in the intent and the returned `withdrawals` array by amount/creation order, as the existing code comment suggests) or, preferably, request that the POA bridge API return an explicit per-withdrawal correlation id (e.g., intent index) so `findMatchingWithdrawal` can disambiguate multiple same-asset withdrawals within one tx hash. Until the API supports this, `PoaBridge` should detect and reject (throw) when a batch contains more than one withdrawal with the same `assetId` routed to PoaBridge, rather than silently misreporting status.

// vitest, mocking only poaBridge.httpClient.getWithdrawalStatus (HTTP layer)
import { PoaBridge } from "./poa-bridge";
import { poaBridge } from "@defuse-protocol/internal-utils";

it("reports identical (status, txHash) for two independent same-asset withdrawals", async () => {
  const assetId = "nep141:zec.omft.near";
  const txHash = "0xSHARED_NEAR_TX";

  vi.spyOn(poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({
    withdrawals: [
      {
        status: "COMPLETED",
        data: { near_token_id: "zec.omft.near", transfer_tx_hash: "0xA", chain: "zec" },
      },
      // In reality this element represents wid0's *actual* pending withdrawal,
      // but the API/array ordering is not guaranteed to align with intent index.
    ],
  });

  const bridge = new PoaBridge({ envConfig: /* ... */, xrplRpcUrls: [] });

  const wid0 = { landingChain: "zec", index: 0, withdrawalParams: { assetId }, tx: { hash: txHash } };
  const wid1 = { landingChain: "zec", index: 1, withdrawalParams: { assetId }, tx: { hash: txHash } };

  const status0 = await bridge.describeWithdrawal(wid0 as any);
  const status1 = await bridge.describeWithdrawal(wid1 as any);

  // BROKEN EQUALITY: both report the same completed status/txHash
  // even though wid0 and wid1 represent two independent signed withdrawals,
  // one of which is actually still PENDING on-chain.
  expect(status0).toEqual({ status: "completed", txHash: "0xA" });
  expect(status1).toEqual({ status: "completed", txHash: "0xA" }); // should differ from status0 in a correct implementation
});

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
