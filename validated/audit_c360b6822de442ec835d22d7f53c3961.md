### Title
POA Bridge misreports withdrawal status/txHash when multiple same-asset withdrawals share a transaction - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status of a specific withdrawal by matching entries returned from the POA bridge status API using `findMatchingWithdrawal`, which selects a record purely by `assetId`, ignoring the `index` that uniquely identifies which withdrawal within a batched transaction the caller is asking about. When a single NEAR intents transaction contains two or more withdrawals of the same asset (same `assetId`), every `describeWithdrawal` call for that asset — regardless of which withdrawal `index` it belongs to — resolves to the same, single matched record. This breaks the equality "status/txHash reported for withdrawal N == the on-chain outcome for withdrawal N."

### Finding Description
`describeWithdrawal` fetches the withdrawal list for a NEAR tx hash and then calls `findMatchingWithdrawal`: [1](#0-0) 

The matching function itself: [2](#0-1) 

The comment on `findMatchingWithdrawal` explicitly acknowledges the gap: "multiple withdrawals of the same token in a single transaction are not supported." Despite this documented limitation, `describeWithdrawal` is invoked once per `WithdrawalIdentifier` — one per withdrawal `index` — from `watchWithdrawal`: [3](#0-2) 

and identifiers are constructed per-withdrawal with a distinct `index`: [4](#0-3) 

Because `findMatchingWithdrawal` never consults `index`, two different `WithdrawalIdentifier`s that share an `assetId` (e.g., two `ft_withdraw` intents for the same NEP-141 token to different destinations/amounts, batched in one `signAndSendIntent` call) both resolve to `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)` — the exact same array element. Both `watchWithdrawal` polls therefore observe identical `status`/`txHash`, even though only one of the two withdrawals has actually completed on POA's side, and the associated Bitcoin/other-chain transfer amount/destination for the "matched" record may not correspond to the withdrawal actually being polled.

The public API explicitly promises index-based correspondence between input params and completion promises: "Index correspondence: `promises[i]` corresponds to `withdrawalParams[i]`" (README), which this matching logic violates for same-asset batches.

### Impact Explanation
This is a status/hash misreport: `describeWithdrawal` can report `{status: "completed", txHash: X}` for a withdrawal that has not actually settled, using the txHash that belongs to a *different* withdrawal in the same batch. An integrator relying on `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` to confirm a specific withdrawal (by index) before crediting a user or marking it settled could credit/confirm two distinct withdrawals against a single settlement, or mark a not-yet-settled withdrawal as settled with a txHash that belongs to a sibling withdrawal — matching the "status or hash misreport making an integrator credit or refund twice" impact category.

### Likelihood Explanation
Any caller (or the SDK's own multi-withdrawal batching flow) that issues two or more withdrawals of the same POA-bridged asset (same `assetId`) within one intents transaction triggers this: no attacker action beyond normal multi-withdrawal usage is required, only that the withdrawals share an asset. The code path is on the default polling flow (`watchWithdrawal` → `describeWithdrawal`), not a rare error branch.

### Recommendation
Extend `findMatchingWithdrawal` (and the POA bridge status API usage) to disambiguate withdrawals sharing an `assetId` within the same transaction — e.g., by matching on `amount` and `destinationAddress` combined with `assetId`, or by tracking per-asset occurrence counts consistent with the `index` assigned in `createWithdrawalIdentifiers`, so each `describeWithdrawal` call resolves to the specific withdrawal it was asked about rather than the first same-asset match.

### Proof of Concept
1. Build and sign a single intent containing two `ft_withdraw` primitives for `nep141:usdc.omft.near`: withdrawal A (100 USDC → address1) and withdrawal B (50 USDC → address2).
2. Call `sdk.createWithdrawalCompletionPromises` (or equivalent) for both `withdrawalParams`, yielding `wid` objects with `index: 0` and `index: 1` respectively (per `createWithdrawalIdentifiers` in `packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`).
3. Suppose only withdrawal A has settled and appears in the POA API's withdrawal list for the tx hash; withdrawal B is still pending and not yet listed.
4. `PoaBridge.describeWithdrawal` for `index: 1` (withdrawal B) still calls `findMatchingWithdrawal(response.withdrawals, "nep141:usdc.omft.near")`, which returns withdrawal A's completed record (same assetId, `.find()` picks the first/only match) — reporting `{status: "completed", txHash: <A's tx hash>}` for withdrawal B, which has not actually settled.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
