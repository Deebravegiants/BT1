### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and attribute the webhook are read from unsigned HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then trusts these header-derived values (in particular `shop`) to build the `WebhookMetadata` object that is dispatched to the app's handler, without any cryptographic binding between the signed body and the claimed shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled straight from request headers, which are never included in the signable string: [2](#0-1) 

`Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` to construct `WebhookMetadata` that is handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` in turn only signs whatever `to_signable_string` returns (the raw body), never the headers: [4](#0-3) 

This breaks the intended identity binding: `shop == request.shop` (the tenant the app believes the event is for) should be equal to `shop == HMAC-authenticated-origin(shop)`, but the HMAC never authenticates which shop the body belongs to — it only authenticates that the body bytes were produced by someone holding the app's `client_secret`.

Because `client_secret` is shared across *all* shops that have the app installed, any shop that has installed the app can legitimately obtain a body+HMAC pair signed with that same secret (from its own genuine webhook deliveries). That attacker-controlled shop can then replay the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `shop-domain` (and/or `topic`/`webhook-id`) header for a different, victim shop's domain. The HMAC check still passes because it only verifies the untouched body bytes, so `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim shop and attacker-chosen body content.

### Impact Explanation
Any handler that uses `data.shop` from `WebhookMetadata` to scope writes, cache updates, or business logic (as documented and shown in `docs/usage/webhooks.md`) can be tricked into applying attacker-supplied webhook bodies to a different, victim tenant's identity. This is a cross-tenant confusion/injection primitive: a legitimate but malicious merchant of the app (an "unprivileged internet user" with respect to other tenants) can forge events attributed to any other shop simply by knowing that shop's domain, without needing that shop's access token or credentials. [5](#0-4) 

### Likelihood Explanation
Likelihood is high: it requires only (a) being able to install the target app on an attacker-controlled shop to obtain one genuine, validly-signed webhook body/HMAC pair, and (b) sending an HTTP request to the app's public webhook endpoint with a substituted `shop-domain` header — no secrets, tokens, or privileged access are needed beyond ordinary app installation.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-signed material, or otherwise cryptographically bind the header-derived `shop` value to the signed body before constructing `WebhookMetadata`. At minimum, `Utils::HmacValidator`/`Request#to_signable_string` should incorporate the `shop-domain` header (and other identity-bearing headers) into the signature computation so that `Registry.process` cannot be tricked into attributing a validly-signed body to an arbitrary shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker sends a forged HTTP request to the app's webhook endpoint reusing body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B, client_secret) == H` — this passes because `B` and `H` are unchanged (see `lib/shopify_api/utils/hmac_validator.rb#L12-31` and `lib/shopify_api/webhooks/request.rb#L35-38`).
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` and dispatches it to the app's handler (`lib/shopify_api/webhooks/registry.rb#L198-199`), which now acts on attacker-supplied data under the identity of `victim-shop.myshopify.com`.
