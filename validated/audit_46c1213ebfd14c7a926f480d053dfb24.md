### Title
Position NFT can be permanently frozen by transferring to a contract address that cannot authorize `transfer` — (File: contracts/position-nft/src/contract.rs)

### Summary
The position NFT exposes the stock OpenZeppelin `transfer` / `transfer_from` entrypoints with no receiver validation. On Soroban, a contract `Address` can only satisfy `from.require_auth()` by being the invoker of the call itself. If a user (or a delegated manager / approved spender) moves a position token to a contract that has no logic to call `transfer` back out, the NFT — and therefore the entire lending account it owns, collateral and debt included — is permanently locked. This is the direct Soroban analog of the ERC721 `transferFrom`-to-unsupported-receiver freeze, except no `safeTransferFrom` equivalent exists to prevent it.

### Finding Description
`PositionNft` implements the OpenZeppelin `NonFungibleToken` trait unchanged (`contracts/position-nft/src/contract.rs:131-173`). `transfer(from, to, token_id)` and `transfer_from(spender, from, to, token_id)` write `to` into `Owner(token_id)` with no check on what `to` is. The controller resolves authority exclusively through `owner_of` (`contracts/position-nft/README.md:39-41`), so whoever/whatever holds the token controls the whole position: collateral, debt, delegates.

Because Soroban contract addresses cannot sign, the only way a contract-held token ever moves again is if that contract itself invokes `nft.transfer` (invoker contract auth satisfies `require_auth` for its own address). A contract without such a function — e.g., any SAC token contract, a pool, a price aggregator, the controller itself, or a custom contract lacking an NFT-rescue entrypoint — becomes a black hole for the token. There is no `safe_transfer` variant and no on-chain way to reject such a recipient.

The allowed entrypoint list explicitly includes "position-nft transfer/approve", so `PositionNft::transfer` / `transfer_from` with an attacker- or victim-chosen `to` is a reachable path for a single unprivileged call.

### Impact Explanation
Permanent freezing of user funds. A position token frozen at an incapable contract address means:
- the collateral and unclaimed yield inside the account can never be withdrawn (`withdraw`, `repay_debt_with_collateral`, etc. all gate on `owner_of` via `try_account_owner` returning error 44 `NotAuthorized` for anyone else);
- the account cannot be cleaned up while solvent — `burn` is controller-only and only runs on account deletion paths (full withdrawal or liquidation/bad-debt cleanup), so the shares stay accounted and the underlying tokens stay locked in the pool forever;
- if the position is underwater, liquidation still works (liquidators don't need owner auth), but a healthy or collateral-only position simply bricks.

This matches the accepted severity of the source report (Medium): user-reachable, irreversible loss of the whole position's value.

### Likelihood Explanation
Low-to-moderate likelihood, consistent with Medium severity: it requires a user (or their approved spender/manager via `transfer_from`) to specify a contract recipient that lacks an NFT escape hatch. Realistic vectors: smart wallets/multisig contracts that don't implement a generic NFT-forwarding call, marketplace or escrow contracts that custody the token during a listing without a withdrawal function for it, and typo'd or deliberately incorrect `to` addresses. Note that the protocol itself encourages contract-held positions — the script-runner and production flows show contracts legitimately holding position NFTs — so contract recipients are not an exotic edge case; any such contract missing an `nft.transfer` hook freezes the position.

### Recommendation
There is no ERC721-style receiver hook on Soroban, so the mitigation is procedural/documentation-level plus an escape hatch:
- Document prominently that transferring a position NFT to a contract that cannot itself call `transfer` permanently freezes the position (collateral, debt, and yield).
- Consider an owner-gated recovery path: e.g., a controller function (behind the governance timelock, or a time-delayed self-service rescue initiated by the previous owner) that transfers a token out of a demonstrably stuck contract address, or a `burn`-and-`mint`-to-new-owner migration for accounts whose `Owner` is a contract that has been inert for a defined period.
- Alternatively restrict `transfer`/`transfer_from` at the wrapper level for known-bad recipients (e.g., the controller, pool, and other protocol contracts that never move NFTs).

### Proof of Concept
1. Alice calls controller `supply` with `account_id = 0`, opening account `id`; `mint(alice)` issues token `id`. The account holds, say, 10,000 USDC of supply shares.
2. Alice calls `position_nft.transfer(from = alice, to = <pool contract address>, token_id = id)` — or an approved operator calls `transfer_from`. The call succeeds; `Owner(id)` now holds the pool's contract address (`Base::update` in OZ `transfer` performs no recipient check).
3. Alice attempts `controller.withdraw(caller = alice, account_id = id, …)` → `try_account_owner` resolves owner = pool ≠ alice → error #44 `NotAuthorized`. The pool contract has no entrypoint that calls `position_nft.transfer`, and no signature auth exists for a contract address, so no transaction can ever move the token.
4. `owner_of(id)` still resolves, positions remain healthy, `burn` never runs (it fires only on full withdrawal/liquidation paths the owner can't reach) → the 10,000 USDC of collateral is permanently locked in the pool. Even `renew(id)` keeps the entry alive indefinitely, preserving the freeze.

Severest reachable variant in one call: `transfer` on `contracts/position-nft` (`NonFungibleToken` impl in `contracts/position-nft/src/contract.rs`), `to` = any contract lacking an NFT-transfer hook; equivalent reachability via `transfer_from` for approved spenders/operators.
