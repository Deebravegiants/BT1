### Title
Token Exchange trusts the unsanitized JWT `dest` claim as the request host, sending the app's `client_secret` to that host - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the Shopify admin host it POSTs to (carrying `client_id`/`client_secret`) directly from the `dest` claim of the caller-supplied session token, without ever passing it through `Utils::ShopValidator.sanitize!` the way every sibling OAuth flow does.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` from the raw `dest` claim value with no domain allow-listing: [1](#0-0) 

`exchange_token` takes this unsanitized value and uses it verbatim to build the `Session` that is fed to `HttpClient`, which in turn builds the request base URI as `https://#{session.shop}`: [2](#0-1) [3](#0-2) 

That POST body includes `client_id` and `client_secret` in plaintext: [4](#0-3) 

Contrast this with every other credential-issuing flow in the same file/module, which all call `Utils::ShopValidator.sanitize!(shop)` before constructing the request host: [5](#0-4) [6](#0-5) [7](#0-6) 

`ShopValidator.sanitize!` is exactly the guard designed to prevent an untrusted string from being used as a request host — it restricts to `TRUSTED_SHOPIFY_DOMAINS` (`myshopify.com`, `myshopify.io`, `spin.dev`, `shop.dev`, `shopify.com`): [8](#0-7) [9](#0-8) 

The identity binding that is broken is: *"host validated" (the value the library was supposed to check against `TRUSTED_SHOPIFY_DOMAINS`) versus "host that receives the `client_secret`"* (the raw `dest` claim, used unchecked). `exchange_token` skips the check entirely, so the equality `sanitize!(dest) == dest_shop_used_for_request` does not hold — the latter is used raw.

### Impact Explanation
If a value under attacker influence ever reaches the `dest` claim of a session token that the app hands to `exchange_token` (e.g., a session token obtained/relayed from a non-Admin embedded context, a spin/dev domain the caller controls, or any code path where `session_token` is not exclusively the exact Admin-issued App Bridge token but a caller-supplied string, since `exchange_token` takes `session_token:` directly from the caller with no restriction on where it came from), the resulting request — carrying the app's `client_id`/`client_secret` in the POST body — is sent to `https://#{dest}/admin/oauth/access_token`, an attacker-influenced host. This is SSRF carrying the app's own OAuth `client_secret` to a non-Shopify endpoint, matching the High-impact criterion "SSRF with the app's credentials."

### Likelihood Explanation
Exploitability depends on how permissively an integrating application passes `session_token` into `exchange_token` and on whether the JWT signature check in `JwtPayload.new` (HMAC over `Context.api_secret_key`) can be satisfied for an attacker-influenced `dest` value. Since JWT decoding is HMAC-verified with the app's own secret, a token must be validly signed by Shopify (or the app's secret) for `dest` to be trusted content, which constrains the practical attack surface. This is a plausible but not fully proven exploit path within this gem alone; the missing `ShopValidator.sanitize!` call is a clear code-level defect (inconsistent with three sibling methods) but I could not fully verify from this gem's code alone whether any code path allows an attacker to supply a validly-signed token with a non-Shopify `dest` value.

### Recommendation
Apply `Utils::ShopValidator.sanitize!` to `dest_shop` before using it to build the request session/host in `exchange_token`, exactly as done in `client_credentials`, `refresh_access_token`, and `migrate_to_expiring_token`:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```

### Proof of Concept
Not independently reproducible from this gem's code alone without confirming an upstream path that lets an attacker control the `dest` claim of a session token that is HMAC-verifiable by the app's secret; flagging as a code-level gap (missing `ShopValidator.sanitize!` call, inconsistent with the three sibling OAuth methods) rather than a demonstrated end-to-end exploit.
