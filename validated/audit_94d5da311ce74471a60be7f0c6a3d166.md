### Title
Premature `last-update` reset in vault `accrue()` lets an attacker freeze `lindex` growth while `index` (debt) keeps compounding - ([File: mainnet/contracts/vault/v0-vault-stx.clar], and identically in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`)

### Summary
Each vault's `accrue()` computes two independently-rounded indices from the same elapsed `time-delta` — `index` (round-up, debt owed by borrowers) and `lindex` (round-down, value backing depositors' `zft` shares and, via `resolve-ztoken` in the market oracle, the price of the corresponding `zToken` collateral). `last-update` is reset to `stacks-block-time` if *either* index changed, not only when both have. Because `index` rounds up and `lindex` rounds down from the same integer time-delta, an attacker can repeatedly call `accrue()` (or any action that triggers it, e.g. `deposit`/`redeem`/`system-borrow`) at intervals just large enough to tick `index` up by the smallest unit but too small to tick `lindex` at all. Each such call resets `last-update`, discarding the elapsed time before it can accumulate enough for `lindex` to round up. This mirrors the reported debasing bug: rounding-down truncation of a periodic accrual is exploitable by resetting the time reference before a full period accrues.

### Finding Description
`next-index` and `next-liquidity-index` both derive `time-delta` from the same `(- stacks-block-time (var-get last-update))` and feed it into `calc-multiplier-delta`, which rounds up for `index` and down for `lindex`: [1](#0-0) 

The commit logic in `accrue()` resets the shared time anchor `last-update` whenever *either* index moved, even if the other one did not: [2](#0-1) 

Because `calc-multiplier-delta` rounds `index` up (`round-up true`) and `lindex` down (`round-up false`) from the exact same `time-delta`, there exist time-deltas for which `index` increments by the smallest representable unit while `lindex`'s floor-division still yields zero change: [3](#0-2) 

When that happens, the `(or ...)` condition is true (because `index` changed) and `last-update` is overwritten with the current timestamp — discarding all elapsed time for the purpose of the *next* `lindex` computation, exactly as in the reported debasing exploit where resetting the "last time" reference before a full period elapses prevents the truncated remainder from ever being counted. By repeatedly triggering `accrue()` at these carefully chosen intervals (any public entry point that calls `accrue()`, e.g. `deposit`, `redeem`, `system-borrow`), an attacker can force `index` (what borrowers owe) to compound close to its full expected rate, while `lindex` (what backs `zft` share redemption and what prices the corresponding `zToken` as market collateral via `resolve-ztoken`) never accumulates the corresponding interest, since its clock is being reset before a full accrual period ever completes.

The value identity broken:
```
debt-delta (interest paid by borrowers, driven by `index`)  ==  lindex growth (interest paid to depositors) + reserve-inc (protocol fee)
```
Note that `reserve-inc`/`treasury-lp` minting is computed purely from `debt-delta` (driven by `index`), independent of whether `lindex` grew: [4](#0-3) 

So even while `lindex` is starved of accrual, `treasury-lp` shares are still minted based on `index`'s growth, diluting existing `zft` holders' claim on `total-assets` without depositors ever receiving the yield that `lindex` was supposed to represent, and without the `zToken` price used elsewhere in the market ever reflecting that accrued value.

### Impact Explanation
This is a rounding-driven, permanent freezing of unclaimed yield for depositors/`zft` holders: interest that borrowers are charged (via `index`) is not matched by growth in `lindex`, meaning the yield depositors are entitled to is permanently withheld while the vault simultaneously dilutes them via `treasury-lp` minting driven off the same (unmatched) debt growth. It also skews the `zToken` price computed in the market's `resolve-ztoken` (used to value `zToken` as loan collateral), since that price is derived directly from the frozen `lindex`, meaning any position using such a `zToken` as collateral is undervalued relative to the true economic value backing it as long as the attacker keeps the accrual clock reset. This fits the "temporary/permanent freezing of unclaimed yield" impact class.

### Likelihood Explanation
The attack requires only unprivileged calls to any public function that invokes `accrue()` (all vault instances share this identical logic) at attacker-chosen intervals, with no special permissions, similar to the original report's requirement of calling `getSynthScalingUpdate()` at chosen intervals. The precise interval needed depends on the current `interest-rate()`, `INDEX-PRECISION`, and `SECONDS-PER-YEAR-BPS` constants, which are public/derivable, so the attacker can always compute a window where `index` ticks but `lindex` does not, making the exploit computable and repeatable indefinitely.

### Recommendation
Do not tie the shared `last-update` reset to either index individually. Track the un-applied elapsed time (or track `last-update` per index) so that fractional remainders are preserved across calls rather than discarded whenever only one of the two differently-rounded indices moves. Concretely, either (a) maintain separate `last-update-index` and `last-update-lindex` timestamps updated independently based on whether *that* index changed, or (b) accumulate leftover time-delta remainder in a persisted variable and add it back on the next accrual instead of resetting to `stacks-block-time` whenever any index moves.

### Proof of Concept
1. Attacker computes the current `interest-rate()` for `lindex` (round-down) and finds a `time-delta` `T` such that `mul-div-up` (for `index`) crosses to the next integer multiplier tick but `mul-div-down` (for `lindex`) does not (analogous to `4320*2-1` in the source report).
2. Attacker calls any vault entrypoint that triggers `accrue()` (e.g. a no-op `deposit` of the minimum unit, or directly if `accrue` is callable) after waiting `T` seconds each time. [2](#0-1) 
3. Each call ticks `index` (and mints `treasury-lp` off `debt-delta`) but leaves `lindex` unchanged, then resets `last-update` to the current time, discarding the fractional remainder that would otherwise have contributed to the next `lindex` accrual.
4. Repeating this indefinitely keeps `lindex` (and the market's `zToken` price derived from it via `resolve-ztoken`) permanently below its true accrual-based value, while `index`-driven debt and treasury dilution proceed largely unaffected. [5](#0-4)

(define-private (calc-multiplier-delta (rate uint) (time-delta uint) (round-up bool))
  (+ INDEX-PRECISION
    (if round-up
      (mul-div-up rate
                  (* time-delta INDEX-PRECISION)
                  SECONDS-PER-YEAR-BPS)
      (mul-div-down rate
                  (* time-delta INDEX-PRECISION)
                  SECONDS-PER-YEAR-BPS))))

(define-private (calc-cumulative-debt (principal-amount uint) (idx uint))
  (mul-div-up principal-amount idx INDEX-PRECISION))

(define-private (calc-index-next (index-curr uint) (multiplier uint))
  (mul-div-down index-curr multiplier INDEX-PRECISION))
