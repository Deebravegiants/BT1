Confirmed: the `walletAccount` field stored on a connection in `#addNewItem` and `add` is never read back by any authorization/consumption logic. `isTrusted`, `isAutoApprove`, `connect`, `disconnect`, `updateConnection`, and `getConnectedAccounts` all key exclusively by `origin`, and `getConnectedAccounts` returns addresses for **every** enabled wallet account (not just the one the connection was scoped to) once the origin is trusted.### Title
Origin trust/authorization is keyed only by `origin`, not by the specific wallet account it was granted for, causing cross-account address disclosure to dApps - ([File: features/connected-origins/module/connections.js])

### Summary
`ConnectedOrigins` allows a dApp origin to be marked `trusted` for a specific `walletAccount`, but every downstream authorization/consumption method (`isTrusted`, `isAutoApprove`, `connect`, `disconnect`, `updateConnection`, `getConnectedAccounts`) looks up state solely by `origin`, ignoring `walletAccount`. This mirrors the `OnlyEOAPolicy` bug class: a permission/allow-state (`allowedContracts` there, `trusted`/`walletAccount` here) is stored globally instead of being scoped to the specific principal it was intended for, so a grant made in one context silently applies to all others.

### Finding Description
`add()` accepts an optional `walletAccount` and persists it on the connection record [1](#0-0) , and `#addNewItem` stores it as a field on the stored origin object [2](#0-1) . However, `walletAccount` is never read back anywhere in the class. Authorization checks such as `isTrusted` and `isAutoApprove` key exclusively on `origin`: [3](#0-2) .

Most significantly, `getConnectedAccounts` — the method that returns wallet addresses to a connected dApp — checks only `isTrusted({ origin })` and then, once trusted, iterates over **every** account in `#connectedAccountsAtom` (i.e., every enabled wallet account in the entire wallet, not just the one account the origin was originally connected/trusted for) and returns all of their addresses for the connected asset names: [4](#0-3) . This is confirmed by the test `'returns connected accounts with active wallet account first'`, which trusts an origin for `solana` and receives back addresses for both `exodus_0` and `exodus_1` — accounts never explicitly authorized individually — with only the "active" one reordered to the front: [5](#0-4) .

The root cause matches the analog bug class exactly: a state field intended to scope a permission to a specific principal (`walletAccount`, analogous to `allowedContracts`/`consumer` in `OnlyEOAPolicy`) is stored but never consulted by the enforcement logic, so the coarser `origin`-only trust flag becomes the de facto authorization boundary across all wallet accounts.

### Impact Explanation
A user who connects/trusts a dApp for one wallet account (e.g., a low-value "throwaway" account) unintentionally exposes the addresses of every other enabled wallet account in the same wallet to that dApp via `getConnectedAccounts`. This breaks the account-isolation model a user expects when explicitly scoping a connection to a single account, and leaks addresses (a privacy/account-linkage issue) across account boundaries without a corresponding explicit grant for each account.

### Likelihood Explanation
High likelihood of triggering under normal usage: this occurs automatically whenever `getConnectedAccounts` is called for any trusted origin with more than one enabled wallet account — no attacker action beyond a legitimately-approved connection is required, and the multi-account return behavior is exercised and asserted by existing unit tests, confirming it is the intended current behavior rather than a rare edge case.

### Recommendation
Enforce the `walletAccount` scope that is already stored: `getConnectedAccounts`, `isTrusted`, `isAutoApprove`, `connect`, and `disconnect` should filter/restrict by the `walletAccount` associated with the connection record instead of returning/considering all enabled wallet accounts. If cross-account visibility is an intentional design choice, `walletAccount` should be removed to avoid the false impression of per-account scoping, and documentation/API should clearly state that trust is origin-wide across all wallet accounts.

### Proof of Concept
1. Call `connectedOrigins.add({ origin: 'evil.dapp', walletAccount: 'exodus_0', trusted: true, connectedAssetName: 'solana' })`, intending to expose only `exodus_0`.
2. Ensure a second wallet account `exodus_1` is enabled (`enabledWalletAccountsAtom`).
3. Call `connectedOrigins.getConnectedAccounts({ origin: 'evil.dapp' })`.
4. Observe the returned array includes both `exodus_0` and `exodus_1` addresses (as demonstrated by the existing test at [5](#0-4) ), even though the connection was only supposed to be scoped to `exodus_0`.

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
