## Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by computing an HMAC over the raw request body only, then dispatches to the app's handler using a `shop` value taken directly from the unauthenticated `shopify-shop-domain` (or legacy `x-shopify-shop-domain`) header. The gem never binds the `shop` field into the signed material, so any request whose *body* carries a valid signature for the app's secret will be accepted regardless of which shop's domain is asserted in the header. This breaks the identity binding: `shop-that-produced-the-signed-body == shop-that-the-handler-is-told-owns-the-webhook`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the (attacker-controllable, unsigned) header with no cross-check against anything cryptographically bound to the request: [2](#0-1) 

`Utils::HmacValidator.validate` computes/verifies the signature exclusively over `verifiable_query.to_signable_string`, i.e. only the body: [3](#0-2) 

`Registry.process` gatekeeps solely on this body-only HMAC check, then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the host application's handler: [4](#0-3) 

`WebhookMetadata.shop` is the field the host app's `WebhookHandler#handle` implementation is expected to use to scope the data to a tenant (look up sessions, persist per-shop records, etc.): [5](#0-4) 

Because `shop` is a dynamic field that sits *outside* the HMAC-covered material (analogous to the report's "second dynamic element not covered by the packed hash"), an attacker who legitimately obtains one correctly-signed webhook body (e.g., by installing the target app on their own store and receiving a real webhook) can replay that exact body while substituting an arbitrary victim `shopify-shop-domain` header value. The HMAC check in `HmacValidator.validate` still passes because it never inspects the header, and `Registry.process` forwards the attacker-chosen shop straight to the handler as if Shopify itself vouched for that shop/body pairing.

### Impact Explanation
This is a cross-tenant identity-binding failure: the gem lets an unprivileged holder of any one valid signed webhook body assert that body belongs to any other shop of their choosing, with no cryptographic tie between the two. Any host application that trusts `WebhookMetadata#shop` (as the gem's own documentation and interface encourage) to select the tenant record to update will process/write data under the wrong shop, i.e., cross-tenant access/injection using another merchant's `shop` identity while only spending the attacker's own legitimately-signed payload.

### Likelihood Explanation
The prerequisite is simply having installed the app on any (even attacker-owned) shop and capturing one webhook delivery — no leaked secrets, TLS interception, or privileged account access is required. Forging the `shopify-shop-domain` header on the replayed HTTP request is trivial once the attacker controls the client sending it to the app's webhook endpoint, since the gem performs no additional header authentication.

### Recommendation
Bind the shop identity into the value that gets HMAC-verified, or otherwise cryptographically tie the header to the signed body — e.g., include the `shop-domain` header (and/or `topic`, `webhook-id`) as part of `to_signable_string`, or independently verify the claimed shop against session/installation state before trusting it in `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-scoping key without corroboration from a previously stored session/shop record.

### Proof of Concept
1. Install the target app on attacker-owned store `attacker.myshopify.com`; trigger any subscribed webhook topic to receive a legitimately Shopify-signed request with headers `x-shopify-hmac-sha256: <sig>` and `x-shopify-shop-domain: attacker.myshopify.com`, body `B`.
2. Replay the exact same request to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`, keeping body `B` and `x-shopify-hmac-sha256: <sig>` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) only — validation succeeds because `B` and `<sig>` are unchanged. [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and any host app that scopes its side effects by `data.shop` performs them against the victim shop's tenant data, despite Shopify never having signed a webhook for `victim.myshopify.com` with this body. [7](#0-6)
