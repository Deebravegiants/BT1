### Title
Weak identity binding for QR-session validation via GPS location instead of operator identity - ([File: src/backend/user_status.rs])

### Summary
The reported bug class is: an authorization decision is bound to a coarse/shared attribute (hostname) instead of a strong, unique identifier (origin), letting an attacker with a weaker credential inherit permissions meant for a stronger one. In `orb-core`, the analogous pattern occurs in the user-QR-code validation request: by default the orb asks the backend to validate a user's signup session using only the **operator's GPS coordinates**, not the operator's unique QR identity, weakening the binding between "this session" and "this specific operator."

### Finding Description
When validating a scanned user QR-code, `verify_user_qr_code` calls `backend::user_status::request` with two independent config flags read from `Config`: `user_qr_validation_use_full_operator_qr` and `user_qr_validation_use_only_operator_location`. [1](#0-0) 

`do_request` branches on these flags to build the validation query:
- If `use_only_operator_location` is set, the request sends only `lat`/`lon` (`operator_data.location_data.session_coordinates`) and the user_id — no operator identity at all.
- If `use_full_operator_qr` is set, the request includes `operator_id` (the operator's unique QR-derived ID).
- Otherwise, only `user_id` is sent. [2](#0-1) 

Critically, the default configuration enables the *weakest* binding mode:
```
user_qr_validation_use_full_operator_qr: false,
user_qr_validation_use_only_operator_location: true,
``` [3](#0-2) 

This mirrors the report's root cause exactly: a strong, unique identifier (`operator_id`, analogous to "origin") is available and even implemented (`use_full_operator_qr` path), but the default/production behavior instead relies on a coarser, more easily duplicated attribute (GPS coordinates, analogous to "hostname") to authorize/bind the session. GPS coordinates are not unique per operator/session — many operators can share the same location (e.g., a large deployment site, or a spoofed/replayed coordinate), just as many origins share the same hostname.

Additionally, the QR-code parsing path (`qr_scan::user::Data::try_parse`) accepts a legacy unsigned `userid:<uuid>:<policy>` format (`QR_CODE_V2` regex) with no `user_data_hash`, alongside the newer cryptographically signed `decode_qr` format: [4](#0-3) 
When `user_data_hash` is `None`, the signature-verification step in `user_status::request` is skipped entirely and a default/unauthenticated `UserData` is returned: [5](#0-4) 

### Impact Explanation
If the location-only binding is exploited (e.g., an attacker replays or forges GPS coordinates matching a legitimate operator's session, or two concurrent signup sessions occur at the same physical location — plausible at busy verification sites), the backend's session-status lookup could validate a user QR-code against the wrong operator session. Combined with the unauthenticated legacy QR format, this could lead to cross-signup state bleed: a user's signup session data (self-custody keys, `orb_relay_app_id`, data policy) being validated/bound under the wrong operator context, potentially enabling unauthorized signup attribution or interference between concurrent sessions.

### Likelihood Explanation
Exploitation requires the attacker to control or predict GPS coordinates reported in the operator QR-code payload and have the target orb configured with default settings (`use_only_operator_location: true`), which is the shipped default. It also depends on backend-side session-matching logic which is not visible in this repo (the actual matching happens server-side at `/api/v2/session/{user_id}/status`), so full confirmation of exploitability requires backend code not present in `orb-core`. This constrains likelihood to moderate/uncertain without backend visibility.

### Recommendation
- Make `user_qr_validation_use_full_operator_qr` (binding to the unique `operator_id`) the default and required mode rather than location-only matching.
- Treat `user_qr_validation_use_only_operator_location` as deprecated/legacy and require operator identity binding for all new signups.
- Require `user_data_hash`-backed (signed) QR codes exclusively, disabling the unauthenticated `QR_CODE_V2` legacy fallback in production configurations.

### Proof of Concept
Not independently verifiable from `orb-core` alone: the vulnerability requires observing/replaying an operator's `location_data.session_coordinates` and confirming the backend's `/api/v2/session/{user_id}/status?lat=...&lon=...` endpoint accepts location-only proof of operator authorization instead of `operator_id`. This backend behavior is outside `orb-core`'s codebase and could not be confirmed with available tools — flagged here as an architectural weak-binding pattern analogous to the reported hostname/origin confusion, not as a fully demonstrated exploit chain.

    qr_code: &qr_scan::user::Data,
    operator_data: &OperatorData,
    use_full_operator_qr: bool,
    use_only_operator_location: bool,
) -> Result<Response> {
    let request = if use_only_operator_location {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id,))
            .query(&[
                ("lat", operator_data.location_data.session_coordinates.latitude),
                ("lon", operator_data.location_data.session_coordinates.longitude),
            ])
    } else if use_full_operator_qr {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
            .query(&[("operator_id", &operator_data.qr_code.user_id)])
    } else {
        super::client()?
            .get(format!("{}/api/v1/user/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
    }
    .basic_auth(&*ORB_ID, Some(get_orb_token()?));
