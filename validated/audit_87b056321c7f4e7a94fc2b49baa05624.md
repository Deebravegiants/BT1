## Analysis

I found a direct analog in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()` function, which lacks a zero-amount guard that its mainline counterpart (`evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw()`) already implements — exactly the bug class described in the report.

### Title
Missing zero-amount skip in Tron `IntentGatewayV2.withdraw()` allows a revert-on-zero-transfer token to permanently DoS escrow release/refund - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()` in the Tron `IntentGatewayV2` contract unconditionally calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` for every entry in `body.tokens`, even when `amount == 0`. The mainline EVM contract already patches this exact pattern with an explicit `if (amount == 0) continue;` guard, but the Tron variant does not carry that fix.

### Finding Description
`withdraw()` is invoked from `onAccept()` for both `RedeemEscrow` and `RefundEscrow` request kinds: [1](#0-0) 

Inside `withdraw()`, each token in the withdrawal body is transferred with a raw low-level call and no zero-amount short-circuit: [2](#0-1) 

Compare this to the mainline (non-Tron) `IntentsBase._withdraw()`, which explicitly skips zero-amount entries before touching the escrow accounting or issuing a transfer: [3](#0-2) 

The mainline `if (amount == 0) continue;` guard exists precisely to avoid calling `transfer`/`safeTransfer` with a zero value — which several real ERC-20 tokens revert on (e.g. LEND, per the `weird-erc20` "revert-on-zero-value-transfers" catalogue cited in the original report). The Tron contract omits this guard, so if any `body.tokens[i].amount == 0` for a token that reverts on a zero-value transfer, the low-level `.call` returns `success = false` and the function reverts with `TransferFailed()`.

### Impact Explanation
`onAccept()` is called by `EvmHost`/the host dispatch pipeline after a relayer delivers a `RedeemEscrow` or `RefundEscrow` `PostRequest` — a permissionless, relayer-driven delivery path, not an admin action. If the failing call causes `onAccept` to revert, the host's request-handling deletes the receipt so the message can be retried, but since the token's zero-value-revert behavior is deterministic, every future retry fails identically. This permanently freezes the escrowed funds for that commitment (all tokens bundled in the same `WithdrawalRequest`, not just the zero-amount one, since the whole call reverts), matching the "permanent freezing of funds" / "route unable to deliver messages" criteria — a Medium-severity, order-book-halting DoS on the Intent Gateway's settlement path.

### Likelihood Explanation
This requires: (1) an order whose input tokens include a zero-value-revert ERC-20, and (2) a `WithdrawalRequest.tokens` array containing a zero-amount entry for that token while `_orders[commitment][token]` accounting is still exercised through the same code path used for legitimate partial/session-based redemptions (the exact scenario the mainline `if (amount==0) continue` guard was added to handle). Given the mainline contract had to add this defense, the underlying zero-amount-entry condition is a real, reachable state in this codebase's intents flow — the Tron deployment simply never received the corresponding fix, making this a straightforward parity gap rather than a purely theoretical one.

### Recommendation
Port the mainline guard into `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()`: skip any token entry with `amount == 0` before performing the escrow-zero check and the token transfer, mirroring `IntentsBase._withdraw()`:
```solidity
uint256 amount = body.tokens[i].amount;
if (amount == 0) { unchecked { ++i; } continue; }
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
...
```

### Proof of Concept
1. Deploy/list a weird ERC-20 as an intent-gateway input token that reverts on `transfer(to, 0)` (e.g., mirroring LEND's behavior).
2. Place and progress an order such that a `WithdrawalRequest` is dispatched cross-chain with `body.tokens` containing a zero-amount entry for that token (e.g., via a session/partial redemption path that legitimately zeroes out one token's remaining share while other tokens in the same commitment still carry balance — the same condition the mainline contract's `continue` guard was written to tolerate).
3. A relayer delivers the `RedeemEscrow`/`RefundEscrow` proof; `EvmHost` calls `onAccept()` → `withdraw()`.
4. `withdraw()` calls `token.call(...transfer(beneficiary, 0)...)`, which returns `success = false` for the weird token; `withdraw()` reverts with `TransferFailed()`.
5. The request receipt is deleted for retry, but the same deterministic revert recurs on every subsequent relay attempt, permanently freezing the escrowed tokens for that commitment.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
