### Title
Single global `maxOracleAge` in `SimplexPaymaster` cannot bound staleness for oracles with heterogeneous Chainlink heartbeats - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-4337 gas payments using two Chainlink feeds — a single `nativeOracle` and a per-token `tokenOracle` — but validates freshness of *both* against one shared, governance-configured `maxOracleAge` [1](#0-0) . The contract's own documentation acknowledges that Chainlink heartbeats vary drastically per chain/token ("BSC stablecoins ~27s, Base/Ethereum stablecoins up to 24h") [2](#0-1) , yet there is no per-oracle staleness bound — exactly the root cause identified in the referenced Noya report, where one shared `chainlinkPriceAgeThreshold` cannot correctly bound staleness for feeds with different heartbeats.

### Finding Description
`_getOraclePrice` is the sole staleness gate for both the native/USD and token/USD feeds:

```solidity
function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
    (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();
    if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
    if (block.timestamp - updatedAt > maxOracleAge) {
        revert StaleOraclePrice(address(oracle), updatedAt);
    }
    ...
}
``` [3](#0-2) 

`maxOracleAge` is one storage slot shared by `nativeOracle` and every entry in `tokenConfigs`, set wholesale by governance's `UpdateParams` request via `_setParams`, which only enforces `0 < maxOracleAge <= MAX_ORACLE_AGE (7 days)` — it does not, and structurally cannot, vary per feed:

```solidity
uint256 public constant MAX_ORACLE_AGE = 7 days;
...
if (p.maxOracleAge == 0 || p.maxOracleAge > MAX_ORACLE_AGE) revert InvalidOracleAge(p.maxOracleAge);
``` [4](#0-3) [5](#0-4) 

Because tokens with fast heartbeats (e.g. a ~27s BSC stablecoin feed) and tokens/native assets with slow heartbeats (e.g. 24h feeds) are registered under the *same* `TokenConfig`/`nativeOracle` staleness bound, governance is forced into one of two unsafe configurations:
- Set `maxOracleAge` tight enough for the fast feed → operationally brittle/DoS for slow feeds, or
- Set `maxOracleAge` loose enough for the slow feed (up to the 7‑day hard cap) → a fast-heartbeat feed can silently stop updating for a long window while `_getOraclePrice` keeps accepting its last (stale) answer as fresh, since `block.timestamp - updatedAt > maxOracleAge` never trips within that window.

This price is used directly in `_fetchDetails` → `_tokenPrice`, which every unprivileged UserOperation sender reaches when paying gas through this paymaster (e.g., solvers funding bids via the intents/Simplex paymaster flow referenced across the SDK docs, or any permissionless account submitting a mode `0x00`/`0x02` UserOp):

```solidity
tokenPrice = _tokenPrice(cfg);
``` [6](#0-5) [7](#0-6) 

`_tokenPrice` feeds `PaymasterERC20`'s `erc20Cost = weiCost * tokenPrice / 1e18` computation, which determines exactly how many ERC-20 units the paymaster charges for gas.

### Impact Explanation
Any unprivileged UserOperation sender can submit a UserOp at the moment a fast-heartbeat oracle's price has diverged from its stale on-chain value (e.g. depeg, or a sharp native-asset price move) while `block.timestamp - updatedAt` is still within the shared, loosely-configured `maxOracleAge`. Because the paymaster computes the ERC-20 charge directly from this stale price, an attacker can systematically underpay for gas relative to the token's real value, draining the paymaster's markup buffer/treasury balance over repeated UserOps, or, in the reverse price movement, overcharge solvers/users funding UserOps through Simplex. This is a direct loss of funds vector reachable from a single permissionless UserOperation, with no privileged action required — matching the reachable "bandwidth purchaser"/fee-accounting class explicitly in scope.

### Likelihood Explanation
The condition requires only that governance configure `maxOracleAge` to accommodate the slowest registered feed (an entirely reasonable, likely operational choice given the documented 24h heartbeats on some chains, and the 7‑day hard ceiling), while at least one other registered token or the native asset feed has a materially shorter heartbeat (the contract's own comment cites ~27s for BSC stablecoins) [2](#0-1) . Any deployment supporting tokens across multiple chains/heartbeats under one `Params.maxOracleAge` value is exposed, and the exploit itself requires no special privilege — just submitting a UserOp when the fast oracle's price has silently gone stale but the shared threshold hasn't yet tripped.

### Recommendation
Replace the single `maxOracleAge` with a per-oracle staleness bound: extend `TokenConfig` (and the native-oracle parameters) with an oracle-specific `maxAge` set at `RegisterToken`/`UpdateParams` time, matching each feed's actual heartbeat, and have `_getOraclePrice` accept and check that oracle's own bound rather than a single shared field. Retain a protocol-wide hard ceiling (`MAX_ORACLE_AGE`) only as an upper limit on the per-oracle value, not as the enforced threshold itself.

### Proof of Concept
1. Governance registers `usdcOracle` (heartbeat ~27s on BSC) and `nativeOracle`/another token oracle with a 24h heartbeat, and sets `maxOracleAge` to a value close to `MAX_ORACLE_AGE` (or any value ≫ 27s) to avoid spurious reverts on the slow feed, as allowed by `_setParams` [5](#0-4) .
2. `usdcOracle`'s `updatedAt` stalls (e.g., sequencer/keeper issue) for longer than its 27s heartbeat but less than the configured `maxOracleAge`.
3. USDC's real market price moves (e.g. depegs).
4. Any user submits a UserOp paying with USDC through `SimplexPaymaster`; `_getOraclePrice` for `usdcOracle` does not revert because `block.timestamp - updatedAt <= maxOracleAge` [3](#0-2) .
5. `_tokenPrice`/`_fetchDetails` charge gas based on the stale price, letting the attacker pay less (or the paymaster overcharge) than the token's true value, repeatable until the oracle updates or `maxOracleAge` elapses.

This mirrors the referenced test in the report (`testUpdateParamsTightensOracleAge`) which itself demonstrates that the paymaster's single `maxOracleAge` field governs staleness for every oracle uniformly [8](#0-7) .

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }
