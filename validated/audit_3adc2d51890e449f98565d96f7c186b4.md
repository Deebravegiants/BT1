### Title
Unchecked TRC20/ERC20 `transfer()` return value in escrow withdrawal and dust-sweep paths permanently freezes user funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron fork of `IntentGatewayV2` uses raw low-level `.call()` invocations of `IERC20.transfer` for all outbound token payouts (`withdraw()`, the fee-token payout inside `withdraw()`, and the `SweepDust` handler in `onAccept()`), checking only that the call did not revert (`success`) and never inspecting the ABI-decoded boolean return value. On TRC20/ERC20 tokens that signal failure by returning `false` instead of reverting, this silently "succeeds" while the beneficiary receives nothing, and the contract has already permanently decremented/deleted the escrow accounting for that order.

### Finding Description
In `withdraw()`, escrow release for intent inputs and protocol fees is done via: [1](#0-0) 

Specifically:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
and
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
```

`success` from a raw `.call()` only reflects whether the callee reverted — it is `true` even if the token's `transfer()` function returns `false` (the standard EIP-20/TRC20 pattern for signaling a failed, non-reverting transfer, e.g. insufficient allowance-independent internal checks some tokens implement, blacklists, or non-compliant tokens). The return `data` (the actual `bool` result) is never decoded or checked.

The same unchecked pattern is used in the `SweepDust` branch of `onAccept`: [2](#0-1) 

Crucially, in `withdraw()`, the escrow state is mutated regardless of whether the token actually moved:
```solidity
_orders[body.commitment][token] -= amount;
```
and `_filled[body.commitment] = beneficiary;` is set at the top of the function before any transfer occurs. Once these state changes commit, `_orders[body.commitment][token]` reaches zero and `_filled[commitment]` is non-empty, so no retry path exists — a subsequent `RedeemEscrow`/`RefundEscrow` for the same commitment will revert with `UnknownOrder` (escrow already zero) or be treated as already filled. The escrowed tokens remain locked in the contract, unreachable by the intended beneficiary.

By contrast, the inbound side of the same contract and the mainline EVM `IntentsBase._withdraw`/`ExtrinsicIntents` correctly use `SafeERC20.safeTransferFrom`/`safeTransfer`, which decode and require the boolean return value: [3](#0-2) 
This confirms the raw-call pattern in the Tron variant is an inconsistency/regression relative to the audited pattern used elsewhere in the same protocol.

### Impact Explanation
This is reachable by any relayer/filler delivering a legitimate `RedeemEscrow`/`RefundEscrow` POST request or GET response to `IntentGatewayV2` on Tron for a TRC20 token that returns `false` on failure rather than reverting (a documented and common non-compliance pattern on TRC20/ERC20, including some widely used stablecoins deployed with legacy semantics). When this occurs:
- The escrow accounting (`_orders[commitment][token]`) is decremented to zero and the order is marked filled/refunded, even though the beneficiary received no tokens.
- The tokens remain stuck in the `IntentGatewayV2` contract with no code path to reclaim them for that commitment (permanent freezing of user/solver funds), and events (`EscrowReleased`/`EscrowRefunded`/`DustSwept`) misreport a successful payout.

This satisfies "permanent freezing of funds" for the intents escrow application, qualifying as Medium severity, consistent with the original LINK-transfer report's impact class.

### Likelihood Explanation
Likelihood depends on interacting with a non-standard-but-common TRC20 token (return-false-on-failure rather than revert) as an intent input/output/fee asset, which is a realistic deployment scenario for a general-purpose intents gateway that is not restricted to a single whitelisted token. No privileged role is required — any relayer delivering a normal cross-chain redeem/refund message, or any protocol dust sweep, can trigger the unchecked path.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()` for both token payout and fee-token payout, and the `SweepDust` branch in `onAccept`) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. This reverts on both call failure and a `false` boolean return, ensuring escrow state is only mutated when the transfer genuinely succeeds.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a TRC20 token `T` whose `transfer()` implementation returns `false` (instead of reverting) when, e.g., the recipient is blacklisted or an internal invariant fails, without reverting.
2. User places an order escrowing `T` via `placeOrder`, which uses `safeTransferFrom` (succeeds normally).
3. Filler fills the order on the destination chain; Hyperbridge delivers a `RedeemEscrow` `onAccept` call to the source-chain `IntentGatewayV2`, invoking `withdraw(body, false)`.
4. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (call didn't revert) but the ABI-decoded `bool` result is `false` — no tokens are actually moved to `beneficiary`.
5. `_orders[body.commitment][token] -= amount` executes, zeroing escrow; `_filled[body.commitment] = beneficiary` is set; `EscrowReleased` is emitted.
6. Beneficiary's balance of `T` is unchanged, yet the order is now permanently marked filled with zero escrow remaining — the tokens are stuck in the contract with no code path to recover them.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
