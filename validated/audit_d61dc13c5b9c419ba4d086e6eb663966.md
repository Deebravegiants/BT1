### Title
Webhook shop/topic identity fields are not bound to the HMAC, enabling cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-validated "signable string" from the raw body only, but the `shop`, `topic`, `webhook_id`, and `api_version` fields used by application handlers to decide *which tenant* the payload belongs to are read from separate, unsigned HTTP headers.

### Finding Description
The intended identity binding is: `HMAC(secret, signed_bytes) == received_hmac` should authenticate every field the application acts on, in particular the shop the webhook is attributed to. Here, `to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is derived independently from the `x-shopify-shop-domain`/`shopify-shop-domain` header [4](#0-3) , and `topic`/`webhook_id`/`api_version` similarly come from headers [2](#0-1) .

`HmacValidator.validate` only checks the HMAC over `to_signable_string` (the body) against `verifiable_query.hmac` [5](#0-4) , so it never verifies that `shop`/`topic` headers correspond to the signed body. `Registry.process` trusts this validation and then dispatches the raw header-derived `shop`/`topic` to the registered handler [3](#0-2) .

Because the (body, HMAC) pair is valid for *any* headers, an unprivileged attacker who legitimately receives one authentic webhook delivery (e.g., by installing the app on their own development/trial store, which is normal, unprivileged access) can capture that `(raw_body, hmac-sha256)` pair and replay it to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a victim shop's domain or a different topic. The HMAC still validates because it only covers the untouched body bytes, so `Registry.process` will invoke the handler believing the payload is for the victim shop/topic — a violation of the equality `hmac_signed_shop == acted_upon_shop`.

### Impact Explanation
This breaks the tenant identity binding the HMAC is supposed to enforce: the field the application acts on (`shop`, and secondarily `topic`) is not the field verified by the signature. Depending on how a consuming application's webhook handler uses `WebhookMetadata#shop` (e.g., to look up/mutate a specific merchant's session, data, or trigger shop-scoped side effects), an attacker can cause data intended for their own shop to be attributed to and processed under an arbitrary victim shop domain, or cause a payload to be dispatched to the wrong topic handler. This matches the "cross-tenant access" class of impact, since the confusion crosses the shop/tenant boundary that the gem is expected to enforce on the app's behalf.

### Likelihood Explanation
Requires no secret, token, or privileged access — only receipt of one legitimate webhook (trivially obtainable by any developer/merchant installing the app on their own store) and the ability to send an arbitrary HTTP request with modified headers but identical body/HMAC to the app's public webhook endpoint.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify shop/topic against out-of-band knowledge, or compute the HMAC over a canonical representation that includes these headers), matching Shopify's actual webhook verification guidance to treat headers as authenticated metadata only after being tied to the signed payload.

### Proof of Concept
1. Attacker installs the target app on their own Shopify dev store (unprivileged, normal app installation) and triggers a webhook delivery for a topic they can control the content of (e.g., `app/uninstalled` or any topic where body content matters less than the `shop` attribution).
2. Attacker's endpoint (or a proxy they control) captures the raw POST body and the `x-shopify-hmac-sha256` header value delivered by Shopify — this pair is valid because it was genuinely signed by Shopify with the app's `client_secret`.
3. Attacker resends this exact `(raw_body, x-shopify-hmac-sha256)` pair to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com` (and optionally changes `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Request.new` builds successfully (all required headers present) [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the unchanged body [7](#0-6) .
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` where `shop` is `victim-shop.myshopify.com` even though the body/content actually originated from the attacker's own store [8](#0-7) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
