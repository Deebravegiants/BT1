### Title
Webhook HMAC only covers the request body, not the `shop-domain` header, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC solely against that body. None of the Shopify-supplied HTTP headers — including `shop-domain`, `topic`, `webhook-id`, and `api-version` — are part of the signed payload, yet `shop` is trusted and forwarded as the tenant identifier to the app's webhook handler. An attacker who can obtain any one genuine `(body, HMAC)` pair for the app (trivially available by installing the app on their own shop and triggering a webhook) can replay that exact body/HMAC pair while substituting an arbitrary victim `shop-domain` header, since the shop header is never part of what is authenticated.

### Finding Description
The webhook signature verification chain is:
- `Request#to_signable_string` returns `@raw_body` only: [1](#0-0)  — no header, including `shop-domain`, is included.
- `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cross-check against the signed content: [2](#0-1) .
- `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) and secure-compares it to the received HMAC: [3](#0-2) .
- `Registry.process` only checks this body-only HMAC, then immediately trusts `request.shop` to construct `WebhookMetadata` handed to the app's handler: [4](#0-3) .
- The gem's own documentation asserts that `Registry.process` "will verify the request did indeed come from Shopify" and shows the app trusting `data.shop` directly for tenant routing (`shop_domain: data.shop`) without independent verification: [5](#0-4)  and [6](#0-5) .

The binding broken is: **the byte range verified by the HMAC (`raw_body` only) ≠ the byte range acted upon for tenant identification (`shop-domain` header)**. Because the same `api_secret_key` is shared across all shops that install a given app, and because the merchant who owns the payload (their own shop) legitimately controls webhook body contents and can capture Shopify's genuine `(body, hmac)` for their own webhooks, that merchant can resend the identical body+HMAC to the app's webhook endpoint with a forged `shop-domain` header pointing at any other shop that has the app installed. The signature still validates because the signature never covered the shop header.

### Impact Explanation
This is a cross-tenant data injection: an unprivileged merchant (who only needs their own working installation of the app, not any victim credentials) can inject arbitrary webhook events — with attacker-chosen body content within Shopify's schema, since Shopify's real webhook payload content is largely dictated by the resource the attacker owns — into the processing pipeline of a completely different, unrelated shop (the "victim" tenant). Any host application that follows the gem's documented pattern and keys per-tenant behavior (job routing, database writes, cache invalidation, order/inventory sync, deduplication by `shop`) off of `data.shop` will attribute attacker-controlled data to the victim shop. This matches the "cross-tenant access" critical-impact category.

### Likelihood Explanation
Likelihood is high for any app that has more than one merchant installation (the normal case for public/multi-tenant Shopify apps). The only prerequisite is that the attacker has (or creates) their own shop and installs the target app — a fully unprivileged action requiring no access to the victim's or the app's credentials. Capturing a genuine `(body, hmac)` pair is trivial (log the raw request the app receives, or sniff their own webhook deliveries), and replaying an HTTP POST with a modified header requires no special tooling.

### Recommendation
Bind the header-derived identity fields into the HMAC-verified surface:
- Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the value passed to `Utils::HmacValidator.validate`, e.g. by having `to_signable_string` concatenate the canonical header values with the body, matching Shopify's documented HMAC computation guidance, or
- After HMAC validation, require the host application (and ideally the gem itself) to check that `request.shop` corresponds to a shop with a stored, verified session/installation before trusting it, and document this requirement prominently instead of asserting that `process` fully "verifies the request did indeed come from Shopify."

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` (fully unprivileged, self-service).
2. Attacker triggers a webhook for a topic they control (e.g., `products/update`) and captures the raw POST body `B` and the resulting `X-Shopify-Hmac-Sha256` header value `H` that Shopify legitimately computed with the app's shared `api_secret_key`.
3. Attacker sends a new POST to the app's webhook endpoint with the *same* body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a request where `shop == "victim.myshopify.com"`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` (`B`) only and matches `H`, since headers are excluded — validation succeeds: [7](#0-6) .
6. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: <attacker-controlled>, ...)`, and the host app (per the gem's documented pattern) processes/stores this data as belonging to the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
