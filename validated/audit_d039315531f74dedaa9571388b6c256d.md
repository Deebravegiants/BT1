### Title
Webhook `shop` (and `topic`/`webhook_id`) Identity Fields Are Not Covered by HMAC Verification, Enabling Cross-Tenant Shop Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers when constructing the `WebhookMetadata` passed to the app's handler. Because these header-derived identity fields are never included in the signed payload, the equality the gem implicitly guarantees — "authenticated shop == body's true origin shop" — does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are read straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC (which covers `raw_body`), and then immediately treats `request.shop` as a trusted, verified value for the handler's tenant context: [4](#0-3) 

`HmacValidator.validate` confirms only that `to_signable_string` (i.e., the raw body) matches the HMAC computed with the app's secret — it says nothing about which shop that body was originally sent for: [5](#0-4) 

The identity binding the gem should guarantee is:
`shop delivered in WebhookMetadata == shop that Shopify actually generated/signed this body for`

What is actually checked is only:
`HMAC(raw_body, api_secret_key) == received_hmac`

These are not equivalent, because `shop` (and `topic`/`webhook_id`) are outside the signed content. Any party who can obtain one genuine, validly-signed webhook delivery (raw body + HMAC) — for example, a merchant who legitimately installs the app on their own store and receives a real webhook — can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header. The HMAC still validates (it only checks the body), but `Registry.process` hands the handler a `WebhookMetadata` claiming the payload belongs to a victim shop chosen by the attacker.

### Impact Explanation
This breaks the tenant isolation the library is expected to provide to any app built on top of it: an unprivileged merchant/installer of the app (who never needs any privileged credential, access token, or the app's `client_secret`) can cause data to be attributed to another merchant's shop. Any app logic that uses `WebhookMetadata#shop` to select which tenant's records to update/delete/create (a standard multi-tenant pattern) can be tricked into cross-tenant writes/reads, satisfying the "cross-tenant access" Critical impact category defined in scope.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate, unprivileged installer of the target app (to obtain one genuine signed body/HMAC pair) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header — both trivially available to any internet user who installs a Shopify app. No secret material, TLS interception, or social engineering is needed; the flaw is purely that the gem never binds `shop` into the signed content it validates.

### Recommendation
Bind the identity-critical fields (`shop`, `topic`, and ideally `webhook_id`) into the HMAC-verified content rather than relying on unauthenticated headers, e.g. by including them in `to_signable_string`, or by requiring callers to independently verify `request.shop` against the shop associated with the persisted webhook registration/session before trusting it. At minimum, document that `shop`/`topic`/`webhook_id` are unauthenticated and must not be used as a sole tenant-selection key.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers/receives one legitimate webhook delivery, capturing the raw request body `B` and its valid header `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's real `api_secret_key`).
2. Attacker sends a new POST request to the app's public webhook endpoint with the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(B) == H` [6](#0-5) .
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` and dispatches it to the app's handler as an authenticated event for that shop [7](#0-6) , even though the body was never generated by/for that shop.
