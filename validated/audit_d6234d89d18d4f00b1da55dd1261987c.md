Based on my investigation, I found a valid analog: the webhook HMAC signature in this gem covers only the raw request body, while the `shop` and `topic` identity fields that the app's handler logic acts on come from unauthenticated headers.

### Title
Webhook HMAC signs only the raw body, leaving `shop`/`topic`/`webhook_id` headers unauthenticated, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` so that `Utils::HmacValidator.validate` can authenticate inbound webhooks using the app's shared `client_secret`. However, `to_signable_string` returns `@raw_body` alone [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never included in the signed material [2](#0-1) . `Registry.process` validates only the HMAC of the body and then dispatches to a handler using the unauthenticated `request.shop` and `request.topic` values [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop attributed to the authenticated webhook == shop the HMAC was actually computed for`. Because `HmacValidator.validate` calls `verifiable_query.to_signable_string`, and `Webhooks::Request#to_signable_string` returns only the raw body bytes [4](#0-3) , the cryptographic proof (`OpenSSL::HMAC.hexdigest` over `secret + raw_body`, computed in `HmacValidator.compute_signature`) says nothing about which shop or topic the request claims to represent [5](#0-4) .

Since every shop that installs the app shares the same app-level `client_secret` (`Context.api_secret_key`), any merchant who installs the app on their own store legitimately receives real webhooks with valid `(raw_body, hmac)` pairs signed with that same shared secret. An attacker can capture one such legitimate `(body, hmac)` pair from their own shop's webhook deliveries, then replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers with values of their choosing. `HmacValidator.validate` will still return `true`, because it only re-derives the HMAC of `raw_body` — it never checks that the claimed `shop`/`topic` headers match what was actually signed. `Registry.process` then builds `WebhookMetadata` with the forged `shop`/`topic`/`webhook_id` and hands it to the app's handler as if it were an authentic event for that shop [3](#0-2) .

### Impact Explanation
This breaks the shop-identity binding the handler relies on for authorization/attribution decisions (e.g., mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics, or any app-specific handler keyed by `data.shop`). An attacker-controlled shop installation can forge webhook events that the app attributes to an arbitrary victim shop domain, causing the app to execute shop-scoped business logic (data deletion, resyncs, entitlement changes, audit logging, etc.) against a shop the attacker does not control. This is a cross-tenant impact, matching the "Critical: cross-tenant access" category since the attacker crosses the tenant/shop boundary the app trusts by supplying only unauthenticated headers.

### Likelihood Explanation
Any unprivileged internet user can install the target app on a shop they control (free/dev store) to legitimately receive real, validly-signed webhook payloads. No `api_secret_key`, access token, or other privileged material is needed — the attacker never learns the secret, they simply reuse a legitimate `(body, hmac)` pair while forging the identity headers, which requires only standard HTTP request tooling against the app's public webhook endpoint.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed material used by `to_signable_string`, or otherwise cryptographically bind them to the HMAC (e.g., verify Shopify's `X-Shopify-Shop-Domain` against a shop known to be associated with the installation before trusting it, and never rely on header values without including them in the signature check). At minimum, downstream handlers should not treat `request.shop`/`request.topic` as trustworthy unless they are demonstrably covered by the HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, and captures a legitimately delivered webhook, e.g. `POST /webhooks` with `raw_body = "{}"`, header `x-shopify-hmac-sha256: <valid-hmac-of-"{}">`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: shop/redact`.
2. Attacker resends the identical HTTP body `"{}"` and identical `x-shopify-hmac-sha256` value to the same endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com` (and optionally the topic/webhook-id headers).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: "{}", headers: forged_headers)` builds a request object whose `to_signable_string` is still `"{}"` [1](#0-0) .
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC of `"{}"` with the shared `api_secret_key` and matches the attacker-supplied (unmodified) HMAC, so validation passes [6](#0-5) .
5. The registered handler is invoked with `WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", ...)`, causing the app to perform shop-redaction (or any other registered handler logic) against `victim-shop.myshopify.com`, a shop the attacker never installed on or was authorized to act on behalf of [7](#0-6) .
