### Title
Sustained large-market interest accrual overflows `i128` and permanently freezes repayments, withdrawals, and liquidations - (File: common/src/rates/index.rs)

### Summary
The pool’s accrual path multiplies scaled debt by the borrow index using checked `i128` arithmetic. On a sufficiently large, highly utilized market, the scaled debt value can overflow before `MAX_BORROW_INDEX_RAY` caps the index. Every pool mutation invokes `global_sync` before changing the market, so once this state is reached, `withdraw`, `repay`, `seize`/liquidation, and `update_indexes` all trap with `MathOverflow`.

### Finding Description
`global_sync` is called by `synced_market` before each market leg (`contracts/pool/src/ops/mod.rs:29-46`). `accrue_chunk` delegates index growth to `accrue_step` (`contracts/pool/src/interest.rs:39-53`). During interest calculation, `calculate_supplier_rewards` computes both `borrowed * old_borrow_index` and `borrowed * new_borrow_index` using checked multiplication (`common/src/rates/index.rs:73-88`). Utilization likewise unscales both totals through `scaled_to_original` (`contracts/pool/src/cache/scale.rs:19-27`), which is a checked `Ray::mul` (`common/src/rates/scaling.rs:12-16`).

Although `update_borrow_index` clamps the resulting index to `MAX_BORROW_INDEX_RAY` (`common/src/rates/index.rs:11-19`), that cap does not prevent the earlier RAY-denominated debt-value multiplication from exceeding `i128::MAX`. A scaled debt principal near `1e36` RAY only requires an index around 170× to cross the `i128` ceiling.

The existing regression test demonstrates this exact failure: after supplying `1_000_000_000` whole 18-decimal tokens and borrowing 98%, repeated `update_indexes` calls eventually fail with `MATH_OVERFLOW`; subsequent `withdraw` and `repay` calls fail for the same reason because they accrue first (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:315-356`).

### Impact Explanation
All user funds in the affected market become permanently frozen. Suppliers cannot withdraw because `withdraw::accounting` loads a synced market before burning shares (`contracts/pool/src/ops/withdraw.rs:57-65`). Borrowers or third parties cannot repay because `repay::accounting` also loads a synced market before reducing debt (`contracts/pool/src/ops/repay.rs:40-55`). Liquidation debt seizure also calls `synced_market` before socializing debt (`contracts/pool/src/ops/seize.rs:18-28`). Since the overflow occurs before any debt-reducing state is committed, there is no permissionless recovery path.

### Likelihood Explanation
The attacker needs a market configuration with sufficiently high supply/borrow caps, an 18-decimal asset, and sustained high utilization. An unprivileged user can supply the large balance through `Controller::supply`, borrow through `Controller::borrow`, and later trigger the failure through `Controller::update_indexes`. The precondition is economically expensive and requires prolonged high-utilization accrual, but it uses only normal permissionless entrypoints and does not rely on privileged behavior, oracle dishonesty, or an external service failure.

### Recommendation
Use saturating or widened intermediate arithmetic for RAY-denominated scaled totals in accrual and utilization paths, or cap the effective scaled debt/index product before checked `i128` multiplication. At minimum, compute the capped `new_borrow_index` before deriving `new_total_debt`, and ensure debt-value calculations cannot overflow when the index remains within `MAX_BORROW_INDEX_RAY`. Add a regression test based on `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` proving that repayment and withdrawal remain executable after the index approaches its cap.

### Proof of Concept
1. Configure or use an 18-decimal market whose supply and borrow caps permit a `1_000_000_000`-token position and whose `max_utilization` permits 98% utilization.
2. Call `Controller::supply` with:
   - `caller`: attacker address
   - `account_id`: `0`
   - `spoke_id`: active spoke
   - `assets`: `[(target_hub_asset, 1_000_000_000 * 10^18)]`
3. Supply enough collateral on a second listed market to satisfy `min_borrow_collateral_usd`.
4. Call `Controller::borrow` with:
   - `caller`: attacker address
   - `account_id`: the created account
   - `borrows`: `[(target_hub_asset, 980_000_000 * 10^18)]`
   - `to`: attacker address
5. Maintain this high utilization until `scaled_borrowed * borrow_index` approaches `i128::MAX`.
6. Call `Controller::update_indexes` with the target `HubAssetKey`.
7. The call traps with `MathOverflow`; subsequent `Controller::repay`, `Controller::withdraw`, and liquidation calls against the same market also trap before committing any state change.
