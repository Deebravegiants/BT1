### Title
Attacker-crafted Emporium stateless op can grant itself unlimited, permanent ERC20 approval over Emporium's holdings - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s "stateless" op path executes `op.endpoint.call{value: op.value}(op.callData)` directly from the persistent Emporium contract's own address, with only two selectors blacklisted. Since the ZK circuits never constrain the contents of `externalActionMetadata`, and the balance-accounting loops iterate only over the caller-supplied `circomData.erc20TokenAddresses` array, an attacker can submit `erc20TokenAddresses = []` together with an op `{endpoint: <token>, invokeWallet:false, value:0, callData: approve(attacker, type(uint256).max)}` and cause Emporium to grant the attacker unlimited, standing `transferFrom` rights over that token — with zero balance checks ever firing.

### Finding Description
Broken equality: **assets Emporium can move** (now includes unlimited `transferFrom` rights for the attacker over `token`) **≠ assets accounted for in this tx's `balancesBefore`/`balancesAfter`** (empty set, because `circomData.erc20TokenAddresses = []`). This divergence is written into ERC20 allowance storage and persists across every future block, independent of Hinkal's Merkle-tree/UTXO accounting.

Code path:
1. Attacker calls `Hinkal.transact()` with a self-generated proof, setting `circomData.externalActionData.externalActionId`/`externalAddress` to Emporium, and `circomData.erc20TokenAddresses = []`. Because no circuit in `circuits/**` constrains `externalActionMetadata` (confirmed: no reference to `externalActionMetadata` anywhere in any `.circom` file), the attacker is free to encode any `EmporiumStack` inside it. [1](#0-0) 
2. `_externalTransact` builds `deltaAmountChanges` over the (empty) `erc20TokenAddresses` array and calls `IExternalActionV2(externalAddress).runAction(circomData, deltaAmountChanges)`. [2](#0-1) 
3. `onlyAllowedRecipient` only checks `msg.sender == Hinkal`; it places zero restriction on the op content, so `EmporiumUpgradeable.runAction` executes with the attacker's chosen `EmporiumStack`. [3](#0-2) 
4. `runAction` computes `balancesBefore = getBalancesForArray([])` (empty), then for `op.invokeWallet == false`, only checks the selector isn't `callHinkalWallet`/`doSendToRelay` before calling `op.endpoint.call{value: op.value}(op.callData)` — so `token.approve(attacker, type(uint256).max)` executes with `msg.sender == Emporium`. [4](#0-3) 
5. Because `circomData.erc20TokenAddresses` is empty, the post-call balance loop (`balancesAfter`, `BalanceChangeShouldBePositive`) never executes for any token, so the approval side-effect is never scrutinized. [5](#0-4) 
6. Back in `Hinkal.transact`, the top-level balance-diff/slippage loop at lines 97-147 also only iterates `circomData.erc20TokenAddresses`, so with an empty array it likewise never fires. [6](#0-5) 

Root cause: the "stateless" call path lets Emporium (a long-lived, shared custodial contract holding pooled shielded balances for all users) make arbitrary calls as itself, gated only by a two-selector blacklist, while the only safety net (`erc20TokenAddresses`/balance diff checks) is fully attacker-controlled and can be emptied to skip verification entirely. `verifyWallet` does not help either: with `stack.signerAddress == address(0)` it returns immediately after marking the (attacker-chosen) message used, imposing no signature requirement on stateless ops. [7](#0-6) 

### Impact Explanation
The attacker obtains a permanent, unlimited `transferFrom` allowance over Emporium's holdings of an arbitrary ERC20 token, at essentially zero cost (one proof + one transaction, no deposit required for the malicious op itself). Any future funds of that token that flow through Emporium (from legitimate swap/deposit flows of other users) can be drained directly via `token.transferFrom(emporium, attacker, amount)`, bypassing Hinkal's proof/nullifier system entirely. This is direct theft of pooled/shielded funds via an action the depositing users and the protocol never authorized — matching the Critical severity bar ("direct theft of shielded or in-flight user funds ... executing calls or moving assets ... never authorised").

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's capability: they need only (a) Emporium already registered as an allowed `externalActionId` in `Hinkal` (standard production configuration), and (b) the ability to generate their own valid ZK proof for their own (trivial/empty) UTXO change set, which the rules explicitly grant. No signature, deposit, or privileged role is required for the stateless approve op. The attack is repeatable per token and can be executed ahead of time, waiting dormant until Emporium accrues balance of the targeted token.

### Recommendation
Do not allow arbitrary, attacker-defined `callData` to be executed directly from Emporium's own persistent address. Specifically:
- Expand the selector blacklist (or switch to an allow-list) for the stateless path to reject state-changing approval/permit-style calls (`approve`, `increaseAllowance`, `permit`, `setApprovalForAll`, etc.) on arbitrary tokens, or
- Require all approvals granted during an op to be reset to zero within the same call sequence (approve-exact-amount-then-consume-then-revoke pattern) and enforce this on-chain, and/or
- Route all externally-supplied, potentially state-changing calls through ephemeral, single-use `HinkalWallet` instances (as already done for the `invokeWallet=true` path) rather than ever letting `op.endpoint.call` execute with `msg.sender == Emporium` itself.
- Independently, do not let `circomData.erc20TokenAddresses` being empty bypass all balance verification for external actions that make arbitrary external calls; require any op targeting a token contract to include that token in `erc20TokenAddresses` so balance-based sanity checks cannot be trivially skipped.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (as an allowed `externalActionId`), and a mock ERC20 `token`.
2. As attacker (unprivileged EOA), generate a proof for a `transact()` call with:
   - `circomData.externalActionData.externalActionId/externalAddress` = Emporium
   - `circomData.erc20TokenAddresses = []`
   - `circomData.externalActionData.externalActionMetadata` = `abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: address(token), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.approve, (attacker, type(uint256).max))})]}))`
3. Call `hinkal.transact(...)`; assert it succeeds and `token.allowance(address(emporium), attacker) == type(uint256).max`.
4. Assert `getBalancesForArray([])` never diverged — i.e., no `BalanceChangeShouldBePositive` revert and no slippage/balance-diff require in `Hinkal.transact` was evaluated (both loops iterate zero times), demonstrating the equality break: allowance state changed while the tx's tracked balance set is empty.
5. Simulate an unrelated legitimate flow depositing `amount` of `token` into `emporium` (e.g., mint tokens directly to `emporium` to emulate accrued/deposited balance).
6. As attacker, directly call `token.transferFrom(address(emporium), attacker, amount)` (bypassing Hinkal entirely) and assert it succeeds and `token.balanceOf(attacker) == amount`, proving theft of funds the attacker never deposited or was authorized to move.
