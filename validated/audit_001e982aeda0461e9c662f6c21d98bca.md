### Title
Missing Access Control on the Shared `CallDispatcher.dispatch()` Allows Any Unprivileged Caller to Drain Its Held Balance - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` is a fully public, unauthenticated function that executes arbitrary attacker-supplied `Call[]` payloads with the `CallDispatcher` contract itself as `msg.sender`. This single `CallDispatcher` instance is shared across every Hyperbridge EVM app that supports calldata execution — `IntentGatewayV2`/`IntentsBase` (predispatch/postdispatch), `HyperFungibleTokenUpgradeable`, and `WrappedHyperFungibleTokenUpgradeable` — and each of these flows temporarily routes user or protocol assets through it before sweeping the balance back. Because `dispatch()` has no caller restriction and no reentrancy guard, any unprivileged address (an ordinary EOA, a bandwidth purchaser, a relayer, or a malicious contract invoked as one of the `Call.to` targets) can call it directly to move out whatever token, ETH, or dust balance the dispatcher currently holds — bypassing every one of the intended callers entirely.

### Finding Description
`CallDispatcher.dispatch()` is declared with no modifier at all: [1](#0-0) 

It is invoked by all calldata-execution apps as an unrestricted, shared utility. `IntentGatewayV2.placeOrder` transfers the order's predispatch assets to this shared `dispatcher` address, then invokes `dispatch()` with the order author's own attacker-controllable `predispatch.call` payload, before a second `dispatch()` call sweeps the resulting balance back to the gateway: [2](#0-1) 

The same dispatcher is reused by `IntentsBase._execute` for postdispatch calldata on fills, and by `HyperFungibleTokenUpgradeable.onAccept` / `WrappedHyperFungibleTokenUpgradeable.onAccept` to run arbitrary calldata immediately after minting or unlocking bridged tokens: [3](#0-2) [4](#0-3) 

Because `dispatch()` accepts `bytes memory params` decoded into raw `Call[]` and performs `to.call{value: call.value}(call.data)` with no `msg.sender` gate, any address that knows the deployed `CallDispatcher` address (published on the public contract-addresses page) can call `dispatch()` directly at any time, supplying a `Call[]` that transfers out whatever native ETH or ERC20 balance the dispatcher currently holds to an attacker-chosen recipient. This is functionally the same class of flaw as the referenced advisory: a component intended to run inbound "customization" logic under an implicit trust boundary (the Fides sandbox; here, the assumption that only the calling app's own escrowed assets ever pass through the dispatcher and only during the app's own atomic flow) has no actual protection mechanism (CWE-693) preventing an outside party from driving that execution primitive directly, with the dispatcher's currently-held funds standing in for the "root process owner" context in the original report.

Two exploitable consequences follow directly from this missing check:
1. Direct external theft: the `receive()` function is unrestricted and payable, and dust/overpay/stuck balances can be left in the dispatcher (the code itself emits `DustCollected` events acknowledging that leftover balances occur). Any external, unprivileged party can call `dispatch()` before the legitimate sweep transaction to redirect that balance to themselves.
2. Reentrant hijack within a single order's own flow: because `order.predispatch.call` / `PaymentInfo.call` targets are attacker-supplied and executed with the dispatcher as caller, a call target that itself makes an external callback (e.g., a malicious "router") can reenter `CallDispatcher.dispatch()` before the intended sweep-back step runs, since there is no reentrancy guard on `dispatch()`.

### Impact Explanation
This allows theft/permanent loss of any tokens, native ETH, or protocol dust the shared `CallDispatcher` is holding, reachable by any unprivileged on-chain actor (no special role, no governance access, and no privileged scope required — unlike the `CONNECTOR_TEMPLATE_REGISTER`-gated scope in the original advisory, this is reachable by literally anyone). Given the dispatcher is shared across the Intent Gateway, HyperFungibleToken, and WrappedHyperFungibleToken apps, funds in flight through calldata-execution paths across the whole EVM deployment are at risk.

### Likelihood Explanation
High. Exploitation requires only calling a single public function (`dispatch`) on a known, publicly-listed contract address with attacker-chosen `Call[]` data — no proof, no consensus interaction, and no privileged role. The dust/leftover-balance windows are explicitly acknowledged in the code's own comments and events (`DustCollected`), confirming that non-zero balances routinely and predictably sit in the dispatcher.

### Recommendation
Restrict `CallDispatcher.dispatch()` to an explicit allowlist of authorized callers (the specific `IntentGatewayV2`/`IntentsBase`, `HyperFungibleTokenUpgradeable`, and `WrappedHyperFungibleTokenUpgradeable` instances configured to use it), and add a reentrancy guard so a single logical calldata-execution flow cannot be re-entered through the same dispatcher instance before it completes its sweep.

### Proof of Concept
1. Read the `CallDispatcher` address from any deployed app's `params()`/public config (it is also listed on the public contract-addresses page).
2. Monitor the dispatcher's ETH/ERC20 balances (dust naturally accrues there per the `DustCollected` events emitted by `IntentGatewayV2`/`IntentsBase`, or send it stray ETH directly since `receive()` is unrestricted).
3. Call `CallDispatcher.dispatch(abi.encode(Call[]({to: attacker, value: currentBalance, data: ""})))` directly — no relationship to any gateway or app is required, and the call succeeds because `dispatch()` performs no caller check.
4. Alternatively, place an `IntentGatewayV2` order whose `predispatch.call` array includes a call to an attacker-controlled contract; have that contract, when invoked by the dispatcher, reenter `dispatch()` before the gateway's own sweep-back call executes, redirecting the escrowed predispatch assets before they reach the intended token-transfer sweep in `evm/tron/contracts/apps/IntentGatewayV2.sol:417-449`.

     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
