### Title
Webhook `shop-domain` and `topic` headers are not covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC verification string solely from the raw request body, while the shop identity and event topic are read from separate, unsigned HTTP headers. Any low-privilege actor who legitimately receives one authentic, correctly-signed webhook (e.g., by installing the app on their own store) can replay that body/HMAC pair to the app's webhook endpoint with the `shop-domain` (and `topic`) header swapped to a victim shop, and the signature check still passes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from headers that are not part of the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (the body) against the `hmac` header, using the app's shared `api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` then trusts `request.shop` and `request.topic` — values that were never part of the HMAC input — to route the payload to a handler and construct the `WebhookMetadata` that the app acts on: [4](#0-3) 

The binding this breaks, expressed as an equality that should hold but doesn't:
`shop_bound_by_hmac == shop_acted_on_by_handler`

Before the attack: for a genuine webhook, `shop_bound_by_hmac` (implicitly, whichever shop Shopify signed the body for) happens to equal `shop_acted_on_by_handler` because Shopify itself sets the header. After the attack: an attacker replays a *validly-signed body* (obtained legitimately from their own store's real webhook, since `api_secret_key`/`client_secret` is shared by the app across every installed shop) but swaps the `shopify-shop-domain` header to a victim's shop. `HmacValidator.validate` still returns `true` because it only checks the body, so `shop_acted_on_by_handler` (victim shop) no longer equals the shop the signature was actually computed for (attacker's own shop) — the identity binding is broken while the HMAC check passes.

This is the direct analog of the reported bug class: a field that is acted on (here, the tenant-identifying `shop` header and the `topic` header used for dispatch) is not covered by the authentication primitive (here, HMAC) that is supposed to bind the whole message together, exactly as the LayerZero report describes a gas parameter that influences execution but is outside the enforced minimum-gas check.

### Impact Explanation
This crosses a tenant boundary: an attacker who is merely a user of the app on their own (unprivileged) shop can forge webhook deliveries that the app's registered handler will process as if they originated from an arbitrary victim shop, without possessing the victim's access token or any Shopify-side secret. Depending on the handler's logic (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, order/customer webhooks that write to per-shop records), this can lead to cross-tenant data corruption, unauthorized session teardown, or injection of attacker-chosen data attributed to a victim shop — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The prerequisite — obtaining one valid `(raw_body, hmac)` pair — is trivial for any unprivileged actor because the same app `client_secret` signs every shop's webhooks and anyone can install a public app on a shop they control (a free/test store) to receive genuine, correctly-signed deliveries. Swapping only the unsigned `shop-domain`/`topic` headers and POSTing to the app's public webhook endpoint requires no cryptographic material and no privileged access, so likelihood is high wherever the host app trusts `request.shop`/`request.topic` in its handler logic (which `Webhooks::Registry.process` is explicitly designed to encourage).

### Recommendation
Bind the identity fields into the verified signable content rather than trusting unsigned headers: either canonicalize `shop`, `topic`, and `webhook_id` into the string that is HMAC-verified (mirroring how `Auth::Oauth::AuthQuery`/`VerifiableQuery` signs the full parameter set for OAuth), or, at minimum, require the caller to supply and check the expected shop out-of-band (e.g., against a known/allow-listed installed-shop list) before dispatching to a handler, so a signature valid for shop A's body cannot be replayed under shop B's identity.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to. Capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — this HMAC is valid because `HmacValidator.validate_signature` only signs `@raw_body` with the shared `api_secret_key` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:36-38`).
2. Replay the identical `(raw_body, x-shopify-hmac-sha256)` pair to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic` to a different registered topic).
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which still returns `true` since only the body is checked (`lib/shopify_api/webhooks/registry.rb:190`).
4. The registered handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) with `shop == "victim.myshopify.com"`, even though the body/signature was never generated for that shop — demonstrating the cross-tenant spoof.

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
