This confirms the finding: `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the request purely via `Utils::HmacValidator.validate(request)`, which delegates to `Request#to_signable_string` — and that method returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`). The `shop` field (`lib/shopify_api/webhooks/request.rb:20-23`, sourced from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is never included in the HMAC-signed bytes, yet it is passed straight into `WebhookMetadata#shop` (`lib/shopify_api/webhooks/webhook_handler.rb:6-12`) and handed to the host app's handler as the authoritative tenant identifier.

Because Shopify webhook HMACs are computed with the app's single `client_secret` (identical for every merchant/shop using that app), any merchant who receives a legitimately signed webhook for their own shop can replay that exact `raw_body` + `hmac-sha256` header pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) will still succeed because it only recomputes/compares the HMAC over the body, never over the shop header, so `Registry.process` treats the forged request as authentic and invokes the host app's handler with `WebhookMetadata.shop` set to whatever the attacker chose.

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing tenant spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `hmac` and `to_signable_string` solely from the raw body, while `shop` is read from an unauthenticated HTTP header. `Registry.process` only validates the body's HMAC and then passes the unauthenticated `shop` value into the handler as the trusted tenant identifier.

### Finding Description
The identity binding broken is: `shop` used by `WebhookMetadata` (and thus by the host app's per-tenant logic) ≠ `shop` actually covered by the cryptographic signature. `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is attacker-controlled input on the HTTP request [2](#0-1) . `HmacValidator.validate`/`validate_signature` recompute the HMAC only over `to_signable_string` (the body) and compare it to the `hmac` header [3](#0-2) . `Registry.process` gates entirely on this body-only HMAC check and then constructs `WebhookMetadata` directly from `request.shop`, handing it to the app's handler as authoritative [4](#0-3) , and `WebhookMetadata` has no independent verification of `shop` [5](#0-4) .

Because Shopify signs webhooks with the app's single `client_secret`/`api_secret_key`, which is identical for all shops that install that app, a valid `(raw_body, hmac)` pair obtained from a genuine webhook for shop A remains cryptographically valid when replayed with the `shop-domain` header changed to shop B. The gem's verification logic cannot detect this because it never binds `shop` into the signed bytes.

### Impact Explanation
This breaks cross-tenant isolation: a webhook handler that uses `data.shop` (from `WebhookMetadata`) to look up/update per-shop records, sessions, or trigger side effects can be tricked into acting on behalf of, or attributing data to, a shop the attacker does not own. In apps that key their persistence or authorization decisions off the webhook's reported `shop`, this enables cross-tenant data confusion/corruption — matching the Critical "cross-tenant access" impact category, since the gem's own documented contract (`Registry.process` verifies request "did indeed come from Shopify" per `docs/usage/webhooks.md:125`) is violated for the `shop` field specifically.

### Likelihood Explanation
Any user who can install the app on their own shop (a normal unprivileged action) automatically receives real, validly-signed webhooks for that shop and can capture the raw body and `hmac-sha256` value. No secrets, tokens, or privileged access are required — only a normal merchant install and the ability to send an HTTP request with a modified header to the app's public webhook endpoint.

### Recommendation
Bind the shop domain into the verified material: either include the `shop` header value in the bytes covered by the HMAC signature check performed for webhook requests, or have `Registry.process`/`HmacValidator` require and cross-check `shop` against a separately-verified source (e.g., an authenticated per-shop lookup) rather than trusting the raw header value, and document that host apps must not treat `WebhookMetadata#shop` as trusted without additional verification.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; trigger any event that causes Shopify to send a real webhook to the app's callback URL. Capture the raw JSON body and the `X-Shopify-Hmac-Sha256` header value — both are valid under the app's shared `client_secret`.
2. Replay the request to the same webhook endpoint, keeping `raw_body` and `X-Shopify-Hmac-Sha256` identical, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds `shop` from the forged header [2](#0-1) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unchanged) body/hmac [6](#0-5) .
4. The registered handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` reporting `victim-shop.myshopify.com` [7](#0-6) , even though the payload actually originated from `attacker-shop.myshopify.com`.
