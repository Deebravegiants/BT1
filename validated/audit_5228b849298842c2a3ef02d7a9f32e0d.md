### Title
Signup success/failure for "user-centric" signups is determined by local device state instead of the authoritative backend enrollment check, bypassing backend identity dedup/fraud verification - (File: `src/plans/mod.rs`)

### Summary
In the yAxis vault, deposits and withdrawals were computed as if every accepted asset had identical value, letting an attacker swap tokens at parity via the cheap withdrawal fee instead of going through an authoritative price oracle. The orb-core analog is in `MasterPlan::do_signup`: when the QR-linked app data marks a signup as `user_centric_signup`, the Orb treats a purely local, unauthenticated pipeline result (`signup_reason`) as equivalent to a backend-verified, deduplicated enrollment, instead of routing the signup through the authoritative backend enrollment endpoint that performs identity dedup/fraud checks.

### Finding Description
`MasterPlan::do_signup` computes `signup_reason` purely from local pipeline state (`SignupReason::Normal`, `Failure`, or `Fraud`), where the local `detect_fraud` step is stubbed out and unconditionally returns `Ok(false)` in this build: [1](#0-0) 

The `qr_codes.user_data.user_centric_signup` flag (originating from `orb_qr_link::UserData` supplied by the user's app and only checked against a hash carried in the QR code) is then used to decide how enrollment success is determined: [2](#0-1) 

When `user_centric_signup` is `true` (and the orb config does not set `ignore_user_centric_signups`), the code **skips** the call to `enroll_user`, which is the only path that talks to the backend's authoritative signup endpoints (`signup_post::request` + polling `signup_poll::request`) that create the backend signup record and perform server-side duplicate/fraud detection: [3](#0-2) [4](#0-3) 

Instead, `debug_report.enrollment_status` and thus `result.success` are set to `Success`/`Error` purely from `signup_reason == SignupReason::Normal`, i.e., from the orb's own (currently no-op) fraud detection, without the backend ever confirming the signup and running its own dedup/fraud logic. The `user_centric_signup` flag itself comes from backend-relayed app data that is only checked with a local hash comparison, not tied to any biometric or backend-side confirmation of enrollment authenticity: [5](#0-4) [6](#0-5) 

This mirrors the vault bug: two conceptually different-value paths — a backend-verified enrollment (analogous to a price-oracle-checked swap) and a locally-declared "success" (analogous to at-parity accounting) — are treated as interchangeable, letting the less-verified path stand in for the authoritative one.

### Impact Explanation
Because the local fraud-check step (`detect_fraud`) always returns `false` in this build, any signup routed through the `user_centric_signup` branch will be reported as `SignupReason::Normal` and therefore `Success`, entirely bypassing the backend's authoritative signup creation/dedup/fraud pipeline (`signup_post`/`signup_poll`) that the non-user-centric branch relies on. This can result in the Orb locally attesting to (and via `dbus::Signup::signup_finished`, UI, and debug report marking as successful) a signup that the backend never actually validated or deduplicated, i.e., misattributed/unauthorized signup completion without the backend's core identity-uniqueness enforcement.

### Likelihood Explanation
The determining flag (`user_centric_signup`) is supplied by the user's own app via QR-linked data and is validated on-orb only by comparing a hash, not by any cryptographic backend attestation tied to enrollment outcome. Any unprivileged user controlling their own signup app-session can request `user_centric_signup = true`, causing the Orb to take the locally-determined success path for every one of their signups, reliably reaching this code path.

### Recommendation
- Do not allow local, app-supplied state (`user_centric_signup`) to substitute for the authoritative backend enrollment/dedup check; always route enrollment decisions through `enroll_user`/`signup_post`/`signup_poll` (or an equivalent backend-verified attestation) regardless of the `user_centric_signup` flag.
- If a "user-centric" fast-path is required for UX, still require a backend round-trip that authoritatively confirms uniqueness/fraud status before marking `result.success = true`.
- Given `detect_fraud` currently performs no checks (`N_FRAUD_CHECKS = 0`), do not treat its `Ok(false)` result as proof of a non-fraudulent, unique signup for any code path.

### Proof of Concept
1. A user (with a modified/self-controlled app) initiates a signup and, via the app-linked QR data, is reported by `user_status::request` with `user_centric_signup: true` (see `backend/user_status.rs:203-212`).
2. During the signup, biometric capture and pipeline succeed normally; `detect_fraud` returns `Ok(false)` unconditionally (`plans/mod.rs:1390-1406`), so `signup_reason = SignupReason::Normal`.
3. In `do_signup` (`plans/mod.rs:639-656`), since `user_centric_signup` is true and `ignore_user_centric_signups` is false, the code sets `enrollment_status = Success` and `success = true` **without** ever calling `enroll_user` (i.e., without calling `signup_post`/`signup_poll` against the backend's signup endpoint).
4. The Orb reports the signup as fully successful (UI, dbus `signup_finished`, debug report) despite the backend never being asked to authoritatively verify or deduplicate this specific enrollment through its signup pipeline.

pub async fn request(signup_id: &str) -> Result<Response> {

    tracing::debug!("Sending request {:#?}", request);
    let response = request.send().await?;
    tracing::debug!("Received response {:#?}", response);
    response.error_for_status_ref()?;

    let response_body = response.text().await?;
    let parsed_response = serde_json::from_str::<Response>(&response_body)
        .inspect_err(|_| {
            tracing::error!("Failed to parse response JSON. Response body: {:#?}", response_body);
        })
        .wrap_err("Failed to parse response JSON")?;

    tracing::debug!("Received response {:#?}", parsed_response);
    Ok(parsed_response)
}
