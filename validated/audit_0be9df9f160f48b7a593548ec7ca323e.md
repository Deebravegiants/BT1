### Title
Reentrancy in Tron `IntentGatewayV2.withdraw()` violates checks-effects-interactions, allowing escrow/fee double-spend - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.withdraw()` sends native ETH/TRX and ERC-20 tokens to a caller-controlled `beneficiary` **before** decrementing the corresponding `_orders[commitment][token]` escrow balance, and the enclosing entry points (`onAccept`, `onGetResponse`, `fillOrder` paths) carry no reentrancy guard. This is the same bug class as the historical Vyper `Crowfund.refund()` reentrancy: external call executed prior to state effects, permitting the callee to re-enter and drain escrow/fees multiple times for the same order.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the internal `withdraw()` function (called from `onAccept` for `RedeemEscrow`/`RefundEscrow` and from `onGetResponse` for cancel-from-source flows) performs, for each token in the withdrawal body: [1](#0-0) 

```
if (_orders[body.commitment][token] == 0) revert UnknownOrder();

if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

The check only asserts the escrow slot is non-zero (not that it covers `amount`), the value transfer (`.call{value: amount}`) happens next, and only afterward is `_orders[body.commitment][token]` decremented. The same unfixed ordering repeats for transaction fees: [2](#0-1) 

Neither `withdraw()` nor its callers (`onAccept`, `onGetResponse`) nor `fillOrder`/`placeOrder` import or apply any `ReentrancyGuard`/`nonReentrant` modifier in this file, confirmed by the absence of any `nonReentrant` occurrence in `evm/tron/contracts/apps/IntentGatewayV2.sol`. This is a direct regression compared to the maintained EVM implementation, `evm/src/apps/intentsv2/IntentsBase.sol`, whose `_withdraw()` decrements `_orders` **before** performing the native/ERC20 transfer (checks-effects-interactions compliant): [3](#0-2) 

and whose `cancelOrder` entry point is explicitly `nonReentrant`: [4](#0-3) 

The project's own Foundry reentrancy regression tests (`evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`) explicitly document that the CEI ordering (`_filled`/escrow decrement before external call) is what blocks a `ReentrantBeneficiary` from re-entering and stealing escrow/fees on the mainline EVM contracts: [5](#0-4) 

The Tron contract lacks this ordering for `withdraw()`, so a `beneficiary` that is a malicious contract (attacker fully controls this address — it is `order.user` on refund paths or the solver-designated recipient on fill/redeem paths) can, in its `receive()`/fallback triggered by the native transfer, re-enter the gateway (e.g. call another view/mutating function that reads the not-yet-decremented `_orders[commitment][token]`, or interact with `placeOrder`/`fillOrder`/other escrow accounting that shares state) before the balance is updated, similar to Crowfund's `refund()` sending Ether before zeroing the contributor's balance.

### Impact Explanation
A successful reentrant call during the escrow/fee payout can result in unauthorized additional withdrawals of the same order's escrowed input tokens or transaction fees, i.e. direct theft of user/protocol funds held by the gateway — a High severity impact under the required "concrete theft ... of funds" bar, since the value transfer precedes the state effect that is supposed to prevent double payout.

### Likelihood Explanation
`withdraw()` is reached by unprivileged, attacker-influenced paths: any user can place an order with themselves (or an attacker-controlled contract) as `beneficiary`/`order.user`, then trigger `RedeemEscrow`/`RefundEscrow` delivery via a relayed Hyperbridge message (`onAccept`) or a GET-response cancellation (`onGetResponse`), both of which are dispatched from ordinary user actions (`cancelOrder`, cross-chain fill settlement). No privileged role is required, matching the "single relayed proof / dispatched request" reachability bar.

### Recommendation
Apply checks-effects-interactions in `withdraw()`: decrement `_orders[body.commitment][token]` (and validate `amount <= escrowed`, not just `!= 0`) and clear `_orders[...][TRANSACTION_FEES]` **before** performing the native/ERC-20 transfer, mirroring the fixed pattern already used in `IntentsBase.sol::_withdraw`. Additionally add a reentrancy guard (`nonReentrant`) to `onAccept`/`onGetResponse`/`withdraw` in the Tron contract for defense in depth, consistent with the mainline EVM `IntentGatewayV2.sol::cancelOrder`.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.user` (or destination `beneficiary`) set to `AttackerContract`, escrowing native TRX/ETH as input.
2. Attacker triggers cancellation such that a `RefundEscrow`/`RedeemEscrow` cross-chain message settles on the source chain, invoking `onAccept` → `withdraw(body, isRefund)`.
3. Inside `withdraw`, `beneficiary.call{value: amount}("")` invokes `AttackerContract.receive()`.
4. Before `_orders[body.commitment][token] -= amount` executes, `AttackerContract.receive()` re-enters the gateway (e.g., a second `onAccept` call re-processing a message referencing the same still-nonzero `_orders[commitment][token]`, or any function reading that slot) to trigger another payout of the same escrow, resulting in `amount` being paid out more than once for the same commitment/token.
