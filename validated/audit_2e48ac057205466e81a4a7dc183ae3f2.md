### Title
Unbounded returndata copy in `CallDispatcher.dispatch` permanently freezes cross-chain token deliveries with embedded calldata - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch()`, invoked from `HyperFungibleToken`/`WrappedHyperFungibleToken` (and their upgradeable variants) `onAccept()` handlers, executes attacker-supplied `Call[]` entries via `to.call{value: call.value}(call.data)` and captures the full returndata into a `bytes memory result` variable regardless of call outcome. Because the destination `to` address and its bytecode are fully attacker-controlled (encoded in the cross-chain message body's `data` field), an attacker can deploy a malicious contract on the destination chain that returns an arbitrarily large blob of data. The `RETURNDATACOPY` needed to populate `result` incurs quadratic memory-expansion gas costs, which can exhaust all gas forwarded to `onAccept`, causing the entire `onAccept` execution (including the token mint/unlock that preceded it) to revert.

### Finding Description
`HyperFungibleToken.onAccept` and its sibling implementations mint/unlock tokens for the beneficiary first, then unconditionally forward `message.data` to `CallDispatcher.dispatch()` when non-empty: [3](#0-2) . The same pattern exists in `WrappedHyperFungibleTokenUpgradeable.onAccept`: [4](#0-3) .

Inside `CallDispatcher.dispatch`, each `Call` in the array is executed with a plain low-level `.call`, and the return value is captured into memory: `(bool success, bytes memory result) = to.call{value: call.value}(call.data);` [5](#0-4) . This capture happens unconditionally — Solidity generates a `RETURNDATACOPY` to populate `result` before the `if (!success)` check is even evaluated. There is no cap on the size of the returned data, so a malicious `to` contract can return megabytes of data (e.g. via an assembly `return(0, hugeSize)`), forcing the caller to pay for memory expansion that grows quadratically with size.

This call is reached from `EvmHost.dispatchIncoming`, which delivers the POST request to the token contract via a low-level call: `destination.call(abi.encodeWithSelector(IApp.onAccept.selector, ...))` [6](#0-5) . If the internal `CallDispatcher.dispatch` call runs out of gas while copying the malicious returndata, the revert propagates up through `onAccept` (undoing the mint/unlock as well), causing `dispatchIncoming` to observe `success == false`, delete the request receipt, and `return` — leaving the request retryable [7](#0-6) .

Because the malicious `data` payload (and the malicious contract's bytecode) is fixed and embedded in the original cross-chain message body, every retry of the same request deterministically hits the same OOG condition. The request can never be successfully delivered by any relayer, regardless of how much gas they supply, since the attacker can size the returned data to exceed any economically/practically feasible gas limit (memory expansion cost is quadratic, e.g. ~1M-word return can already consume tens of millions of gas, more than any block gas limit if made large enough).

### Impact Explanation
The bridged tokens for that specific transfer become permanently undeliverable: the mint/unlock and the beneficiary's expected `data` execution can never complete because the transaction deterministically reverts on every replay attempt. This is a permanent freezing-of-funds condition for the affected transfer — the user's tokens are stuck in transit forever (the source-chain side already burned/locked them, and the destination-chain side can never successfully mint/unlock because delivery always reverts). This matches "permanent freezing of funds" impact criteria and is reachable by any unprivileged sender constructing a `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain transfer with malicious calldata-execution payload — no privileged role is required.

### Likelihood Explanation
Likelihood is high: any user of the HFT bridge can call `send()` with a non-empty `data` field pointing to a contract they deploy on the destination chain. No special permissions, timing, or race conditions are required — this is a self-contained griefing/DoS vector fully controllable by the attacker in a single crafted transfer.

### Recommendation
Cap the returndata size copied from the external call in `CallDispatcher.dispatch`, e.g. by using a low-level call with a `gas` limit and manually truncating returndata via `returndatacopy` with a bounded size, or by wrapping the external call so that only a bounded number of bytes (e.g. via `abi.decode`-independent assembly capturing only the first N bytes) are ever copied into memory, regardless of how much the target contract returns.

### Proof of Concept
1. Attacker deploys `Evil` contract on the destination chain with a fallback/function that does `assembly { return(0, 20000000) }` (returns ~20MB of zeroed memory, all read from unallocated memory which is free to "return" without initializing but still costs gas to copy on the caller side).
2. Attacker calls `HyperFungibleToken.send()` (or the equivalent `WrappedHyperFungibleToken`/upgradeable variant) on the source chain with `data` set to an ABI-encoded `Call[]` containing one entry: `{ to: <Evil address>, value: 0, data: "" }`.
3. When a relayer delivers the POST request via `HandlerV2`/`EvmHost.dispatchIncoming`, `onAccept` mints tokens then calls `CallDispatcher.dispatch(message.data)`, which calls `Evil`, triggering the massive `RETURNDATACOPY` and exhausting all forwarded gas.
4. `onAccept` reverts (undoing the mint), `dispatchIncoming` observes failure, deletes the receipt, and returns — the request remains "pending" but every future relayer attempt hits the identical OOG condition, permanently blocking delivery of that transfer.
