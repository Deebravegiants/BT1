### Title
Shared `CallDispatcher` balance treated as exclusive order funds in `IntentGatewayV2.placeOrder` predispatch sweep - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder`'s predispatch flow reads the *entire* current token balance of the shared, singleton `CallDispatcher` contract via `IERC20(token).balanceOf(dispatcher)` and sweeps that whole balance into the gateway, then attributes anything above the order's declared `amount` to "dust" that the protocol keeps [1](#0-0) . Because `dispatcher` is one shared address (`_params.dispatcher`) used by this function's sweep logic and is documented elsewhere as a general-purpose call executor also reachable from other apps (e.g. `HyperFungibleToken`'s calldata-execution path forwards bridged tokens to the same kind of `CallDispatcher`) [2](#0-1) , any tokens that land on the dispatcher address from a source other than the current order's own predispatch transfer are swept in and reclassified as "dust" for this order/caller, rather than returned to their rightful owner.

### Finding Description
This mirrors the Hedera root cause: a shared custody account's real token balance (`balanceOf`) is trusted directly as ground truth for "how much belongs to me right now," rather than tracking a per-operation delta or exclusively-owned escrow. In the Hedera incident, Uniswap-V2-derived pair contracts' balance-based accounting, combined with HTS's independent custody semantics, let an attacker manipulate/read the pool's actual token balance and drain funds that the pair's internal accounting assumed were exclusively its own reserves.

Here, `placeOrder`'s predispatch branch:
1. Transfers only `order.predispatch.assets[i].amount` from `msg.sender` to `dispatcher` [3](#0-2) .
2. Executes arbitrary calldata (`order.predispatch.call`) via `ICallDispatcher(dispatcher).dispatch(...)` [4](#0-3) .
3. Then reads `balance = IERC20(token).balanceOf(dispatcher)` — the dispatcher's **total** balance, not the amount produced by step 1/2 — and constructs a sweep call transferring that entire `balance` to the gateway [5](#0-4) .
4. Anything above `order.inputs[i].amount` is emitted as `DustCollected` and effectively retained by the protocol/gateway rather than returned to whoever actually owned it [6](#0-5) .

`nonReentrant` on `placeOrder` only prevents a reentrant call into `placeOrder` itself; it does nothing to guarantee that the `dispatcher`'s balance at sweep time reflects only this order's funds. Since `CallDispatcher` is a shared, address-known utility contract intended to be reused across many flows (predispatch/postdispatch on `IntentGatewayV2`, and calldata execution for `HyperFungibleToken` bridging), any residual balance parked there — from a prior transaction's incomplete sweep, a different app's in-flight calldata execution, or simply a third party sending tokens directly to the well-known dispatcher address — is unconditionally claimed by the next `placeOrder` predispatch call as "dust," effectively transferring someone else's tokens into the caller's order/protocol accounting without their authorization.

### Impact Explanation
Any tokens or dust sitting at the shared `CallDispatcher` address for reasons unrelated to the current order (from another user's earlier transaction, a griefing transfer, or overlap with another app's use of the same dispatcher) can be unilaterally claimed by an attacker who crafts a `placeOrder` call with matching `predispatch`/`inputs` token addresses. This is a concrete loss-of-funds / theft-of-funds vector for whichever party's tokens were transiently resting at the dispatcher, satisfying the "concrete theft" bar. Severity is Medium because it requires the dispatcher to actually be holding foreign balance at the moment of the attacker's sweep (a timing/race condition), not an unconditional drain of the gateway's own escrow.

### Likelihood Explanation
Exploitability depends on being able to get or observe tokens sitting at the known `dispatcher` address before calling `placeOrder`. This is plausible because: (a) the dispatcher address is public/discoverable via `_params.dispatcher`; (b) the same generic `CallDispatcher` pattern is documented for reuse by other bridging flows (`HyperFungibleToken` calldata execution), so cross-application balance collisions are a realistic operational scenario, not a purely theoretical one; and (c) an attacker can also directly `transfer` tokens to the dispatcher themselves in one transaction and sweep them via `placeOrder` predispatch in the same or a subsequent transaction to force a specific "dust" outcome, though this self-funded case mainly griefs the attacker rather than others — the real risk is when a legitimate third party's tokens land there.

### Recommendation
Do not use the dispatcher's absolute `balanceOf` as the sweep amount. Instead, track and sweep only the delta produced by the current predispatch call (balance-before/balance-after around the `dispatch(order.predispatch.call)` invocation, mirroring the pattern already used for `order.inputs[i].amount` accounting on lines 292–306, but computed relative to a balance snapshot taken immediately before the predispatch dispatch rather than trusting the dispatcher's total balance at sweep time). Alternatively, have `CallDispatcher` operations transfer to a fresh, order-scoped/ephemeral address (e.g., a minimal proxy or CREATE2 sub-account keyed by order commitment) so no shared balance can ever exist across unrelated calls.

### Proof of Concept
Conceptual sequence (requires the dispatcher to hold or be made to hold foreign token balance):
1. Party A's tokens end up on the `CallDispatcher` address `D` for token `T` (e.g., a stuck/partial transfer from another app's calldata-execution flow, or a direct `transfer(D, X)`).
2. Attacker calls `placeOrder` with `order.predispatch.assets` and `order.inputs` referencing token `T`, sending only enough of their own funds to satisfy `requiredAmount` for the predispatch leg.
3. At the sweep step, `balance = IERC20(T).balanceOf(D)` includes Party A's `X` tokens in addition to the attacker's transferred amount [5](#0-4) .
4. The full `balance` (attacker's funds + Party A's `X`) is swept to the gateway; the excess over `order.inputs[i].amount` is emitted as `DustCollected` and retained by the protocol rather than returned to Party A [7](#0-6) .

Note: I was not able to fully verify, within the available index, whether `CallDispatcher.sol`'s implementation clears or isolates balances between calls, or whether deployment configuration guarantees a dedicated (non-shared) dispatcher per app instance — the file `evm/src/utils/CallDispatcher.sol` was located but its full contents were not retrieved before the tool budget was exhausted. If `CallDispatcher` is deployed as a strictly per-`IntentGatewayV2`-instance, single-purpose contract with no other callers, the cross-application collision scenario would not apply, though the same-chain race/timing risk (dust from a prior partially-executed order, or a directly-sent-in griefing transfer) would still hold. Confirming this requires reading the full `CallDispatcher.sol` source, which a Devin session with full repository access could verify.

## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
