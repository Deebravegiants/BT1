### Title
Webhook shop domain header is not covered by HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from unauthenticated HTTP headers, while `to_signable_string`—the value that `HmacValidator` actually verifies—is bound only to the raw request body. `Registry.process` treats a valid HMAC as proof of authenticity for the whole request and then forwards the header-derived `shop` value to the app's webhook handler unchecked.

### Finding Description
`Webhooks::Registry.process` performs a single authenticity check: [1](#0-0) 

which delegates to `Utils::HmacValidator.validate`, comparing the `hmac-sha256` header against an HMAC computed only over `to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw JSON body: [3](#0-2) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers that are never included in the signed string: [4](#0-3) 

After the HMAC check passes, `Registry.process` builds `WebhookMetadata` straight from these unauthenticated header values and hands it to the app-registered handler: [5](#0-4) 

This breaks the identity binding the HMAC is supposed to provide: `shop_authenticated_by_hmac == shop_delivered_to_handler` does not hold. The gem verifies "these bytes were signed by our secret" but the handler acts on "this shop-domain header," and the two are never tied together. Because Shopify's HMAC for webhooks is computed over the body only (this mirrors Shopify's own webhook signing scheme), any entity capable of triggering one genuinely-signed webhook delivery to the app (e.g., a developer installing the app on their own store and triggering an event) obtains a `(body, valid-hmac)` pair whose validity is completely independent of the `x-shopify-shop-domain` header value. That pair can be replayed to the same endpoint with the shop-domain header swapped to any other tenant's `myshopify.com` domain, and `Registry.process` will accept it and dispatch it to the handler as if it originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: an attacker who legitimately controls one shop (and thus can generate valid signed webhook payloads targeting the app's webhook endpoint) can cause the app to process/attribute webhook data to an arbitrary other shop domain, because the shop identifier is not part of the authenticated payload. Downstream app logic that uses `WebhookMetadata#shop` (e.g., to look up a merchant record, update state, or trigger side effects) can be manipulated into acting on behalf of a tenant the attacker does not control, i.e., cross-tenant access/injection facilitated directly by this gem's verification logic.

### Likelihood Explanation
Exploitation requires the attacker to be able to produce at least one `(raw_body, valid hmac)` pair for the target app's secret. Any developer/merchant who installs the app on their own store and can trigger a webhook (many topics are attacker-controllable, e.g., creating a product/order on their own store) obtains such a pair without needing the app's `client_secret`. Replaying it against the same public webhook endpoint with a modified `shop-domain` header is trivial once the pair is captured.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that gets HMAC-verified, or otherwise cryptographically bind the header-derived shop to the signed body (e.g., require the host app to verify `shop` against a known/registered shop list per webhook, or have `to_signable_string` incorporate the shop header). At minimum, document prominently that `request.shop`/`request.topic` are NOT authenticated by `HmacValidator.validate` and must be independently validated by the host application against its known-shops table before use.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — both legitimately signed with the app's secret.
2. Attacker replays this exact body/HMAC pair to the same app webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the spoofed shop header; `Utils::HmacValidator.validate` succeeds because it only checks the unchanged raw body against the unchanged HMAC (`lib/shopify_api/webhooks/request.rb` `to_signable_string`, `lib/shopify_api/utils/hmac_validator.rb` `validate_signature`).
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the host app to process attacker-controlled data as if it came from the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
