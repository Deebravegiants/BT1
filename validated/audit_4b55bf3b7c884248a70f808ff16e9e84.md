## Title
Login endpoint (`POST /sessions`) is vulnerable to a timing side-channel enabling user (email) enumeration - (File: `core/sessions/localauth/orm.go`)

### Summary
The reported xrdp bug is a timing side-channel in the login path: responses differ measurably in processing time depending on whether the submitted username exists, letting a remote unauthenticated attacker enumerate valid accounts. The chainlink node's local authentication login flow, exposed unauthenticated at `POST /sessions`, exhibits the exact same bug class: a fast-fail path for non-existent emails and a slow, bcrypt-gated path for existing emails.

### Finding Description
`SessionsController.Create` accepts unauthenticated credentials and forwards them to `AuthenticationProvider().CreateSession`: [1](#0-0) 

In the default local-auth ORM implementation, `CreateSession` first looks up the user by email. If the email does not exist, the DB query returns an error and the function returns immediately — no bcrypt work is performed. If the email exists, execution proceeds to `utils.CheckPasswordHash`, which invokes `bcrypt.CompareHashAndPassword`, a deliberately slow (tens-of-milliseconds), computationally expensive operation: [2](#0-1) [3](#0-2) 

The email-equality check performed just before the password check (`constantTimeEmailCompare`) only protects against a *sub-microsecond* string-compare timing leak; it does nothing to mask the multi-millisecond delta introduced by bcrypt, which only executes when the row was actually found. This produces two clearly distinguishable response-time populations: fast (email unknown → early DB-error return) vs. slow (email known → bcrypt executed), independent of the password's correctness.

The identical pattern is duplicated in the LDAP and OIDC local-admin fallback paths, which are also reachable unauthenticated through the same `CreateSession`/`Create` entry point: [4](#0-3) [5](#0-4) 

### Impact Explanation
An unauthenticated network attacker who can reach the node's web UI/API (`POST /sessions`) can measure response latency across a list of candidate email addresses to determine which ones correspond to real operator/administrator accounts on the node. Because chainlink node operators typically have a very small number of admin accounts, and knowledge of a valid email is a prerequisite for credential-stuffing, password-guessing, or social-engineering attacks against the node's admin panel, this is a genuine (if lower-severity) unauthorized information disclosure — directly analogous to the CVE-2026-42218 username enumeration bug class. It does not by itself grant authentication bypass or fund movement, consistent with the CVSS 5.3 (confidentiality-only) severity of the source report.

### Likelihood Explanation
Exploitation requires only unauthenticated HTTP access to the node's login endpoint and a moderate number of timed requests to statistically distinguish the two latency populations (bcrypt cost factor is fixed and default, so the gap is consistent and easily measurable, especially averaged over repeated requests). No special privileges, race conditions, or internal knowledge are required, making this a highly practical timing side-channel similar in nature and exploitability to the referenced xrdp vulnerability.

### Recommendation
Ensure constant-time behavior regardless of whether the account exists:
- Always perform a bcrypt comparison (e.g., against a fixed dummy hash) when the user lookup fails, so the fast/slow branches are balanced in cost.
- Alternatively, add a randomized/fixed artificial delay to the "user not found" branch so on average it matches the cost of the bcrypt comparison branch.
- Apply the same fix uniformly to `core/sessions/localauth/orm.go` `CreateSession`, and to the LDAP/OIDC `localLoginFallback` functions.

### Proof of Concept
1. Send repeated `POST /sessions` requests with a known-valid email and an incorrect password; record response latency (dominated by the bcrypt comparison in `utils.CheckPasswordHash`).
2. Send repeated `POST /sessions` requests with a random/nonexistent email and any password; record response latency (fast DB-miss return path in `orm.CreateSession`).
3. Compare the two latency distributions — the valid-email set will show a consistent, statistically significant additional delay corresponding to the bcrypt cost factor, allowing an attacker to reliably distinguish valid from invalid emails without needing the correct password.

func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	lggr := o.lggr.With("user", user.Email)
	lggr.Debugw("Found user")

	// Do email and password check first to prevent extra database look up
	// for MFA tokens leaking if an account has MFA tokens or not.
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}

// CheckPasswordHash wraps around bcrypt.CompareHashAndPassword for a friendlier API.
func CheckPasswordHash(password, hash string) bool {
	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	return err == nil
}
