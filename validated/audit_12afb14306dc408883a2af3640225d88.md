### Title
Webhook shop/topic/webhook-id headers are not covered by HMAC verification, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from raw HTTP headers, but `to_signable_string` — the value actually checked by `Utils::HmacValidator.validate` — returns only `@raw_body`. This means the HMAC signature authenticates the request body bytes but not the shop/topic identity fields that `Registry.process` and the host app's webhook handler rely on to attribute the event to a tenant.

### Finding Description
`Registry.process` gates all webhook handling on `Utils::HmacValidator.validate(request)`: [1](#0-0) 

The validator computes the HMAC over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Request`, `to_signable_string` returns only the raw body — none of `shop`, `topic`, `webhook_id`, or `api_version`, which are all read straight from unauthenticated headers via `shopify_header`: [3](#0-2) [4](#0-3) 

After HMAC validation passes, `Registry.process` uses `request.topic` (unauthenticated) to select the handler and forwards `request.shop`, `request.webhook_id`, `request.api_version` (all unauthenticated) into `WebhookMetadata`, which is the only tenant-identifying data the host application's `handle` method receives: [5](#0-4) [6](#0-5) 

This breaks the identity binding: `shop authenticated-by-HMAC` should equal `shop the handler acts on`, but here `shop the handler acts on` is taken from an HTTP header that carries no cryptographic binding to the signed body.

### Impact Explanation
An unprivileged internet user who obtains any one legitimate `(raw_body, hmac)` pair for the app's webhook endpoint — for example a merchant who installed the app and can observe webhooks Shopify sends to their own store — can replay that exact body/HMAC combination while swapping the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id` headers to name a different, victim shop. `Utils::HmacValidator.validate` still succeeds because it only checks the raw body against the secret, so `Registry.process` will dispatch the forged event to the host app's handler tagged with the attacker-chosen `shop`/`topic`. Any host application logic that trusts `WebhookMetadata#shop` to key per-tenant records (session lookup, data updates, redaction bookkeeping, billing state, etc.) can be manipulated into acting on data attributed to a shop the attacker does not control — a cross-tenant integrity/access issue.

### Likelihood Explanation
Requires only network access to the app's public webhook endpoint plus possession of one valid body/HMAC pair, which is obtainable by any merchant that installs the app (no privileged credentials, no `api_secret_key`, no TLS interception). This is a low-effort, low-privilege attack path.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and any other field the host handler is expected to trust) in the signable string used for HMAC computation/verification, or otherwise cryptographically bind them to the signed payload, so that `Utils::HmacValidator.validate` fails if any of these identity fields are altered relative to what Shopify originally signed.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and capture a legitimate webhook POST, including its raw JSON body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify over `B` with the app's shared secret).
2. Replay a POST to the app's webhook endpoint with the same body `B` and header `H`, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`= B`) and matches `H` — validation passes.
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: JSON.parse(B), ...)`, i.e., the host app processes attacker-supplied body content under the victim shop's identity.
