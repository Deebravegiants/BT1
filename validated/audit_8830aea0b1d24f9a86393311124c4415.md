Audit Report

## Title
Unverified ERC20 transfer amounts allow fee-on-transfer/rebasing tokens to desynchronize XCM holding credits from actual checking-account balance - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` call a token's `IERC20::transfer` and only inspect the boolean return value before crediting/debiting the exact requested `amount` in XCM holdings, never checking the actual balance delta on the `TransfersCheckingAccount` [1](#0-0) [2](#0-1) . This lets fee-on-transfer or rebasing ERC20 contracts desynchronize the credited XCM amount from what the checking account actually holds.

## Finding Description
In `withdraw_asset_with_surplus`, the transactor issues `transfer(checking_address, amount)` and, if the call succeeds (`is_success == true`), unconditionally mints `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` for the full requested `amount`, regardless of how many tokens the checking account actually received [3](#0-2) . Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the checking account to the beneficiary and treats a `true` return as full success without confirming the beneficiary balance increased by `amount` [4](#0-3) .

The `ERC20Matcher`/`IsLocalAccountKey20` combination used to decide which contracts this transactor handles matches any location of the form `(0, [AccountKey20 { .. }])`, with no allow-list restricting it to vetted, standard-conformant ERC20 contracts [5](#0-4) . This transactor is wired into `AssetTransactors` on Asset Hub Westend [6](#0-5) . Since `pallet-revive` contract deployment is permissionless and `pallet_xcm::execute` is available to ordinary accounts, any user can deploy a non-conformant fee-on-transfer/rebasing ERC20 and immediately have XCM operations recognize it through this path. There is no balance-before/balance-after reconciliation anywhere in either function — only the boolean success flag is checked.

## Impact Explanation
Every successful withdraw against a fee-on-transfer/rebasing ERC20 mints an XCM holding credit larger than what is actually locked in the checking account for that specific token. If the same non-standard token is subsequently used across multiple operations (e.g., withdraw followed by deposit to a different beneficiary, or a reserve-transfer that mints a derivative elsewhere), the checking account's real balance will fall short of the sum of credits already issued, causing later legitimate `deposit_asset_with_surplus` calls for that token to fail once the shortfall surfaces. This is a genuine accounting-invariant break (credited holding amount != actual token balance moved) confined to whichever ERC20 contract is used through this transactor, not a compromise of DOT/native asset accounting.

## Likelihood Explanation
Reachable by any unprivileged user: `pallet-revive` contract deployment and `pallet_xcm::execute` are both available without special privileges, and `ERC20Matcher`/`IsLocalAccountKey20` impose no whitelist on which contract addresses are treated as valid assets. An attacker only needs to reference a non-standard ERC20 contract address via an `AccountKey20` location in an XCM program exercising `WithdrawAsset`/`DepositAsset` through `ERC20Transactor`.

## Recommendation
After each `transfer` call in `withdraw_asset_with_surplus`/`deposit_asset_with_surplus`, read back the checking/beneficiary account's actual balance delta (e.g., via `balanceOf` before/after) and mint/return an `AssetsInHolding` credit reflecting the actual amount moved rather than the requested `amount`, or restrict `ERC20Matcher` to a whitelist of vetted standard-conformant ERC20 contracts.

## Proof of Concept
1. Deploy a minimal ERC20-like contract via `pallet-revive` whose `transfer` deducts a fee (e.g., 1%) but still returns `true`.
2. Use `pallet_xcm::execute` with a program: `WithdrawAsset` for this contract's `AccountKey20` location with amount `100`, then `DepositAsset` to a different local beneficiary.
3. Observe that `withdraw_asset_with_surplus` mints `Erc20Credit(100)` [7](#0-6)  even though the checking account's real balance only increased by `99`; the subsequent `deposit_asset_with_surplus` attempts to move `100` out of the checking account [8](#0-7) , which fails once the checking account's real balance becomes insufficient relative to credits already issued.

/// `Contains<Location>` implementation that matches locations with no parents,
/// a `PalletInstance` and an `AccountKey20` junction.
pub struct IsLocalAccountKey20;
impl Contains<Location> for IsLocalAccountKey20 {
	fn contains(location: &Location) -> bool {
		matches!(location.unpack(), (0, [AccountKey20 { .. }]))
	}
}

/// Fallible converter from a location to a `H160` that matches any location ending with
/// an `AccountKey20` junction.
pub struct AccountKey20ToH160;
impl MaybeEquivalence<Location, H160> for AccountKey20ToH160 {
	fn convert(location: &Location) -> Option<H160> {
		match location.unpack() {
			(0, [AccountKey20 { key, .. }]) => Some((*key).into()),
			_ => None,
		}
	}

	fn convert_back(key: &H160) -> Option<Location> {
		Some(Location::new(0, [AccountKey20 { key: (*key).into(), network: None }]))
	}
}

/// [`xcm_executor::traits::MatchesFungibles`] implementation that matches
/// ERC20 tokens.
pub type ERC20Matcher =
	MatchedConvertedConcreteId<H160, u128, IsLocalAccountKey20, AccountKey20ToH160, TryConvertInto>;
