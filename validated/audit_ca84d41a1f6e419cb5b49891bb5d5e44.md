### Title
`Request#shop` returns the unsigned `X-Shopify-Shop-Domain` header and `Registry.process` forwards it as trusted tenant identity, unbound to the HMAC-covered body - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` returns `shopify_header('shop-domain')` verbatim, and `to_signable_string` only returns `@raw_body`, so the shop-domain header is never covered by the HMAC that `HmacValidator.validate` checks. `Registry.process` passes this unauthenticated `request.shop` straight into `WebhookMetadata.shop` with no call to `ShopValidator` anywhere in the webhook path, even though `ShopValidator.sanitize!` is used consistently in the OAuth/token-exchange code paths.

### Finding Description
The broken binding: `HmacValidator.validate` verifies `HMAC(secret, request.to_signable_string) == request.hmac`, where `to_signable_string` returns only `@raw_body` [1](#0-0) . The value trusted downstream as the tenant identifier, `request.shop`, comes from `shopify_header("shop-domain")` [2](#0-1) , which is **not** part of that signed string. The equality the code implicitly assumes — `shop-domain header value == the shop that produced/authorized raw_body` — is never enforced anywhere in this file or in `HmacValidator`.

`HmacValidator.validate` computes the signature using `Context.api_secret_key`, which is the app's single client secret shared across *every* shop that installs the app, not a per-shop secret [3](#0-2) . Consequently, a valid `(raw_body, hmac)` pair obtained from one legitimately-delivered webhook (e.g., one the attacker's own shop receives at their own registered endpoint) is valid HMAC-wise for that body value regardless of which `shop-domain` header accompanies it, because the header isn't part of the signed content.

`Registry.process` then does:
```ruby
raise ... unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
``` [4](#0-3) 
No call to `Utils::ShopValidator.sanitize!` or any cross-check against a known/registered shop occurs. This is inconsistent with the rest of the gem: `ShopValidator` is deliberately invoked in `lib/shopify_api/auth/token_exchange.rb`, `lib/shopify_api/auth/client_credentials.rb`, `lib/shopify_api/auth/refresh_token.rb`, and `lib/shopify_api/clients/graphql/storefront.rb`, but never in the webhook request/registry path.

Exploit flow: the attacker creates their own development shop, installs the app, and registers a webhook endpoint on their own server (permitted per the threat model). They capture a legitimately-delivered webhook — a real `(raw_body, X-Shopify-Hmac-Sha256)` pair Shopify sent for their own shop. They then POST that exact `raw_body` and `X-Shopify-Hmac-Sha256` byte-for-byte to the target app's public webhook endpoint, but replace `X-Shopify-Shop-Domain` with the victim's domain (or `admin.shopify.com/victim-shop`, which the host app's `sanitize_shop_domain` resolves to `victim-shop.myshopify.com`). `HmacValidator.validate` still passes because it only checks the body against the shared secret. `Registry.process` calls the handler with `data.shop == "victim-shop..."` and `data.body` equal to the attacker's own webhook payload — the handler processes attacker-controlled content under the victim's identity.

### Impact Explanation
This is cross-tenant confusion in the webhook pipeline: a party with no privilege on the victim shop can cause the host app's webhook handler to execute business logic (e.g., updating records, enqueueing jobs, cache invalidation, `data.shop`-keyed lookups as shown in the documented handler pattern `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) tagged with the victim's shop domain while the actual payload is attacker-controlled. The blast radius covers any app relying on `WebhookMetadata#shop` (or `Request#shop` directly) as an authenticated tenant key, and it is repeatable against any target shop domain the attacker can guess/know (myshopify domains are often predictable/enumerable), for every webhook topic the attacker's own shop is subscribed to. This matches "cross-tenant access" under the Critical category.

### Likelihood Explanation
Preconditions are minimal and fully within the described unprivileged attacker capabilities: create a dev shop, install the target app, register one webhook endpoint, and receive one real webhook delivery. No secrets are needed — the attacker never touches `api_secret_key`. The only host-app dependency is that it trusts `data.shop`/`request.shop` for tenant-scoped operations, which is exactly the pattern the gem's own documentation shows. Cost per attack is a single captured request replayed with one header changed; it is fully repeatable against arbitrary target shop domains.

### Recommendation
Do not treat `request.shop`/`WebhookMetadata#shop` as authenticated. At minimum: (1) include the shop domain in the signable string covered by the HMAC (not currently supported by Shopify's webhook protocol, so this alone may not be feasible), and/or (2) require host apps to cross-check `request.shop` against a shop known to have an active webhook registration/session before trusting it, and (3) route `request.shop` through `Utils::ShopValidator.sanitize!` in `Registry.process` before constructing `WebhookMetadata`, and document explicitly that `shop` is unauthenticated header data that must be corroborated against stored installation state before being used as a tenant key.

### Proof of Concept
```ruby
# test/webhooks/registry_cross_tenant_test.rb
require "test_helper"

class RegistryCrossTenantTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_secret_key: "shared_secret", ...)
    ShopifyAPI::Webhooks::Registry.clear
  end

  def test_shop_domain_header_not_bound_to_hmac
    body = '{"id":1,"note":"attacker shop payload"}'
    hmac = Base64.encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "shared_secret", body)
    )

    # Simulate: attacker's own shop legitimately received this (body, hmac) pair
    # then replays it to the target endpoint with a spoofed shop-domain header.
    forged_headers = {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "admin.shopify.com/victim-shop",
    }

    request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

    # Binding under test: HMAC validity says nothing about shop-domain authenticity.
    assert ShopifyAPI::Utils::HmacValidator.validate(request), "hmac unexpectedly invalid"
    assert_equal "admin.shopify.com/victim-shop", request.shop

    received_shop = nil
    handler = TestHelpers::FakeWebhookHandler.new(lambda { |data| received_shop = data.shop })
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", path: "path", delivery_method: :http, handler: handler,
    )

    ShopifyAPI::Webhooks::Registry.process(request)

    # Demonstrates the gem hands the attacker-controlled body to the handler
    # tagged with an arbitrary, attacker-chosen shop label - no ShopValidator call occurred.
    assert_equal "admin.shopify.com/victim-shop", received_shop
    assert_equal "victim-shop.myshopify.com",
      ShopifyAPI::Utils::ShopValidator.sanitize!(received_shop)
  end
end
```
This test uses only the shared `api_secret_key` (never an attacker secret), constructs a real HMAC over an attacker-chosen body, and shows `HmacValidator.validate` and `Registry.process` accept an arbitrary, attacker-controlled `shop-domain` header — proving the header is unauthenticated and gets forwarded as a trusted tenant label without any `ShopValidator` check in this file.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
