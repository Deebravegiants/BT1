### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw` and `SweepDust` lets escrow release/refund fail silently while accounting still updates - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw` (used for both `RedeemEscrow` and `RefundEscrow`) and the `SweepDust` handler in `onAccept` move escrowed tokens with a raw low-level `.call` to the ERC20 `transfer` selector, and only check the boolean `success` returned by `.call` (i.e. whether the call reverted). They never inspect/decode the ABI-encoded return data of `transfer` itself. Any ERC20/TRC20 token that signals failure by returning `false` instead of reverting will make the `.call` report `success = true` even though no tokens moved, so the code proceeds as if the transfer succeeded.

### Finding Description
In `withdraw`:
```solidity
// evm/tron/contracts/apps/IntentGatewayV2.sol:706-707
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

and the fee-transfer branch immediately after:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [2](#0-1) 

use the raw `.call` result instead of `SafeERC20.safeTransfer`, even though the contract already imports and uses `SafeERC20` elsewhere (`using SafeERC20 for IERC20;`). [3](#0-2)  `SafeERC20` exists precisely to decode and validate the boolean `transfer`/`transferFrom` return value for tokens that return `false` on failure rather than reverting — the same class of bug flagged in the external report about Compound's `redeem` returning a non-zero error code instead of reverting.

The same pattern recurs in `SweepDust`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [4](#0-3) 

Because the outer `withdraw` function unconditionally marks escrow state as settled regardless of whether the underlying token actually moved:
```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    _orders[body.commitment][token] -= amount;
``` [5](#0-4) 

a token that returns `false` on a failed transfer (a legacy/non-standard behavior common on Tron's TRC20 tokens and several legacy ERC20s) makes the code treat the `RedeemEscrow`/`RefundEscrow` request as fully honored: `_filled[body.commitment]` is set and `_orders[...][token]` is decremented, even though the beneficiary received nothing.

### Impact Explanation
This is reachable from an ordinary, unprivileged relayed ISMP POST request delivered to `onAccept` (the standard cross-chain delivery path any relayer submits after solving/filling an intent). If it fires on the escrow-release/refund path, the intended beneficiary (solver or user) never receives their tokens even though:
- the commitment is marked `_filled`, permanently preventing any retry or re-delivery of the same withdrawal, and
- the internal escrow accounting (`_orders[body.commitment][token]`) is decremented as if funds were paid out.

The tokens remain stuck in the `IntentGatewayV2` contract with no accounting path left to reclaim them for that commitment — a permanent freezing/loss of escrowed intent funds. This directly damages the intents escrow accounting invariant reachable from a single relayed message.

### Likelihood Explanation
Likelihood depends on encountering a non-standard token (or a token that legitimately returns `false` rather than reverting) among the input/output assets an order can specify. Given this is the Tron-chain deployment of `IntentGatewayV2` — where TRC20 tokens are more likely to exhibit non-reverting failure semantics than mainstream EVM ERC20s — this raises the practical likelihood above negligible, and no attacker privilege beyond normal relayer/solver interaction with the gateway is required to trigger the code path.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw` (both the token loop and the fee transfer) and in `SweepDust` with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in this contract (`using SafeERC20 for IERC20;`). This ensures both call-revert and false-return failure modes cause the entire transaction (and therefore the escrow-state mutation) to revert instead of silently succeeding.

### Proof of Concept
1. An order is placed and later solved such that its output/input token is a non-standard ERC20/TRC20 that returns `false` on a failed `transfer` (e.g., due to being paused, blacklisted-recipient, or otherwise reverting-avoidant by design) instead of reverting.
2. Hyperbridge delivers a `RedeemEscrow` (or `RefundEscrow`) POST request to `IntentGatewayV2.onAccept`, which calls `withdraw(body, ...)`.
3. Inside `withdraw`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call itself does not revert) but the encoded return data is `false`.
4. The code only checks `success`, so it does not revert; `_filled[body.commitment]` is set and `_orders[body.commitment][token] -= amount` executes.
5. The beneficiary's on-chain token balance is unchanged (transfer failed), yet the commitment is now permanently marked filled and the escrow debited — the tokens are stranded in the contract with no remaining accounting path to release them for that commitment.
