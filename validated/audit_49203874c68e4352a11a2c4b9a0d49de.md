### Title
Missing sufficiency check before escrow debit causes permanent freezing of intent funds - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`'s escrow-release path (`_withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol` and its Tron twin `withdraw` in `evm/tron/contracts/apps/IntentGatewayV2.sol`) validates only that an escrow entry is *non-zero* before debiting it, never that it is *sufficient* to cover the amount being redeemed. This is the same root-cause class as the reported `FulfillableRegistry.removeServiceAddress()` issue: an accounting variable is checked for "exists" rather than "is large enough," so a subsequent unchecked-context-free subtraction underflows and reverts. Because this debit sits on the only code path that finalizes a cross-chain `RedeemEscrow`/`RefundEscrow` delivery, a single instance of `amount > escrowed` permanently and irrecoverably bricks that specific message — the escrowed input tokens can never be released to the filler nor refunded to the user.

### Finding Description
`_withdraw` in `evm/src/apps/intentsv2/IntentsBase.sol` (lines 451-470):
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();

_orders[body.commitment][token] = escrowed - amount;
``` [1](#0-0) 

and the equivalent Tron `withdraw()`:
```solidity
if (_orders[body.commitment][token] == 0) revert UnknownOrder();
...
_orders[body.commitment][token] -= amount;
``` [2](#0-1) 

Both guard only `escrowed == 0`, never `escrowed >= amount`. In Solidity ^0.8.24 (no `unchecked` wrapper around the subtraction in either function), any call where `amount` exceeds the stored `_orders[commitment][token]` balance reverts the entire `onAccept`/`onGetResponse`/`withdraw` call with a stock arithmetic-underflow panic rather than a clean, catchable error.

This function is the sole finalization point for:
- `RedeemEscrow` — dispatched by `_fillCrossChain` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` after a solver has already paid the beneficiary on the destination chain [3](#0-2) , and
- `RefundEscrow` — dispatched by `_cancelFromDest` [4](#0-3) ,

both delivered on the source chain via `onAccept` after ISMP proof verification (`evm/src/apps/intentsv2/ExtrinsicIntents.sol:330-337`) [5](#0-4) , i.e., reachable by any relayer delivering an already-dispatched cross-chain message — no privileged role is required.

Because `_filled[body.commitment]` is written *before* the loop that can revert, a reverting delivery leaves `_filled` unset on the source chain while the destination chain has already recorded `_filled[commitment] = msg.sender` and paid the solver [6](#0-5) . Since the ISMP request body (commitment, token list, amounts) is immutable once dispatched, every redelivery attempt of the same request replays the identical underflowing subtraction and reverts identically — there is no retry path that succeeds, and no alternate function releases `_orders[commitment][token]`.

### Impact Explanation
Any transaction, relay, or code path that produces a `WithdrawalRequest.tokens[i].amount` exceeding the corresponding `_orders[commitment][token]` balance (e.g., a rounding/accounting drift between the value used to construct the redeem/refund message and the value actually escrowed) permanently freezes that order's escrowed funds: the source chain can never release them to the filler or refund them to the user, while on the destination side the filler has already paid out — a genuine, permanent freezing-of-funds condition and a broken message-delivery route, matching the accepted impact classes (permanent freezing of funds / route unable to deliver messages).

### Likelihood Explanation
The check is on the single, fully generic redemption path used by every cross-chain intent fill and cancellation, and is triggered by ordinary relayer message delivery — no admin, governance, or malicious-node assumption is required. Likelihood of the exact triggering condition (an `amount` desynchronized from the stored escrow) depends on whether the surrounding order/fee/partial-fill arithmetic can ever diverge from the escrow ledger (e.g., fee-on-transfer tokens, protocol-fee rounding, or future code paths that construct `WithdrawalRequest.tokens` independently of `_orders`), which is plausible given the codebase already special-cases fee-on-transfer tokens and rounding at other call sites (`evm/tron/contracts/apps/IntentGatewayV2.sol` protocol-fee deduction logic).

### Recommendation
Replace the existence check with a sufficiency check, and use `unchecked` only after confirming `amount <= escrowed`, e.g.:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed < amount) revert InsufficientEscrow();
_orders[body.commitment][token] = escrowed - amount;
```
Apply the same fix to the Tron `withdraw()` implementation. Additionally, consider capping `amount` to `escrowed` (rather than reverting) for redemption paths so a benign rounding overshoot degrades gracefully instead of permanently bricking the delivery.

### Proof of Concept
1. A cross-chain order escrows `X` units of token `T` for commitment `C` (`_orders[C][T] = X`).
2. A filler calls `_fillCrossChain`, which pays the beneficiary on the destination chain and dispatches a `RedeemEscrow` `WithdrawalRequest{commitment: C, tokens: [{token: T, amount: Y}]}` with `Y > X` (any code path — current or future — that computes `Y` independently of the live `_orders[C][T]` value, e.g. rounding/fee drift).
3. On the source chain, the relayer delivers the proof; `onAccept` calls `_withdraw`, which reads `escrowed = X`, passes the `escrowed == 0` check, then executes `_orders[C][T] = X - Y`, underflowing and reverting the whole call.
4. Every subsequent delivery attempt of the same committed request replays the identical revert. `_filled[C]` is never set on the source chain, `_orders[C][T]` remains permanently locked at `X`, while the destination chain has already paid the filler — funds are permanently frozen and the message route can never deliver.
