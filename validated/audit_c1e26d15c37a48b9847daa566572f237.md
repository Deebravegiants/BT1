### Title
Webhook Shop-Domain Header Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop` attribute used to attribute a webhook to a tenant is read from an unauthenticated HTTP header. This breaks the identity binding `hmac-verified bytes == shop attribution bytes`, allowing a webhook that is HMAC-valid for one shop to be replayed with a forged shop-domain header and be processed by the host app as belonging to a different shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, which is passed downstream to app handlers, is derived from the `shop-domain` header, which is never part of the signed content: [2](#0-1) 

`HmacValidator.validate` only checks `to_signable_string` (i.e., the raw body) against the HMAC secret, never the `shop`, `topic`, `webhook_id`, or `api_version` headers: [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build the metadata that is handed to the app's webhook handler: [4](#0-3) 

This is exactly analogous to the reported bug class: a field that is acted upon (`shop`, which determines whose session/token/data the handler operates on) is not covered by the integrity check (`hmac`) that is supposed to authenticate the request. An unprivileged attacker who can install the app on their own store (a normal, unprivileged action) receives legitimately HMAC-signed webhooks for their own shop. They can then replay that exact signed body to the victim app's public webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain. Because the HMAC only covers the body, `HmacValidator.validate` still returns `true`, and `Registry.process` will invoke the handler with `data.shop` set to the attacker-chosen victim shop — a cross-tenant confusion where data intended/authenticated for the attacker's own shop is attributed to another tenant.

### Impact Explanation
This crosses a tenant boundary: the app-provided webhook handler receives a request that is cryptographically valid (from Shopify's perspective, since it was HMAC-signed by the real API secret for the attacker's own shop) but is attributed to an arbitrary victim shop domain chosen by the attacker. Depending on how the host application keys its stored sessions/data by `shop` (which is the gem's documented and expected usage pattern, per `SessionUtils.offline_session_id`/`jwt_session_id` keying data by shop), this enables cross-tenant access/data confusion — satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic: any actor can install the app on a shop they control (no special privilege required beyond having a Shopify store), capture one of the resulting legitimate webhook deliveries (raw body + valid HMAC), and replay it against the app's public webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or other secret is required — only observation of one's own legitimately received webhook traffic.

### Recommendation
Include the shop domain (and topic/webhook id, if they are also relied upon by handlers) in the HMAC-signed content, or otherwise cryptographically bind the shop attribute to the signed payload before trusting it in `Registry.process`/`WebhookMetadata`. At minimum, document that `request.shop` is unauthenticated header data and must be cross-checked by the host application against a shop it already has an active, HMAC/OAuth-established session for, rather than trusted on its own.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app registers for.
2. Capture the delivered HTTP request: raw body `B` and header `x-shopify-hmac-sha256: H` (valid, since Shopify signed it with the real `api_secret_key` for this legitimate delivery).
3. Replay a new HTTP request to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes HMAC over `B` only and matches `H`, returning `true`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) proceeds and invokes the handler with `WebhookMetadata` whose `shop` is `"victim.myshopify.com"`, despite the payload and signature originating from the attacker's own shop.
