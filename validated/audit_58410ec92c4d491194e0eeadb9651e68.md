## Title
Webhook `Registry.process` verifies only the request body HMAC, not the `shop` used to route the event — enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before dispatching it to the app's handler with the shop identity attached. In reality, the computed HMAC only covers the raw request body; the `shop` value used to identify *which tenant* the webhook belongs to is read from an HTTP header that is completely outside the signed content. This breaks the identity binding `HMAC(secret, signed_bytes) == received_hmac` ⇒ `shop_bound_by_signature == shop_used_by_handler`, allowing any existing (legitimately installed, unprivileged) merchant to relabel their own genuinely-signed webhook as belonging to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is parsed straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never fed into `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the received signature: [3](#0-2) 

`Registry.process` gates entirely on that body-only HMAC check, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The gem's own documentation instructs developers to treat this as an authenticated request and to key their downstream processing off `data.shop`: [5](#0-4) [6](#0-5) 

Because all shops installed on a given app share the same `api_secret_key` (it's a per-app secret, not per-shop), any merchant who has legitimately installed the app can:
1. Trigger a real Shopify event in their own store (e.g., `orders/create`), receiving a webhook with a valid `x-shopify-hmac-sha256` for the (attacker-controlled) body.
2. Replay that exact body + HMAC to the app's webhook endpoint, but with the `x-shopify-shop-domain` header rewritten to a victim shop's domain.
3. `HmacValidator.validate` still succeeds because the signature check never touched the shop header, so `Registry.process` proceeds and hands the handler a `WebhookMetadata` claiming `shop: <victim-domain>`.

This is exactly the "field acted on but not covered by the HMAC" identity-binding failure described in the reference bug class: the equality that must hold — *the tenant identified by the verified bytes equals the tenant the app acts on behalf of* — does not hold here, since `shop` is parsed independently of the signed bytes.

### Impact Explanation
Any application built per this gem's documented pattern (keying stored data, job scheduling, or session lookups off `data.shop`) can be made to ingest attacker-controlled webhook payloads under a victim merchant's identity. This is a cross-tenant boundary crossing driven entirely by this gem's own verification logic (`HmacValidator` + `Registry.process`), not by the host app ignoring documented API — the host app is following the documented `data.shop` contract exactly as instructed in `docs/usage/webhooks.md`.

### Likelihood Explanation
Requires only an unprivileged actor who has installed the app on their own shop (a normal, low-privilege prerequisite, not `api_secret_key` or any stolen credential) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint. No brute-forcing of the secret is required since a valid HMAC is obtained legitimately for the attacker's own tenant.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-covered signable content in `Request#to_signable_string`, or otherwise cryptographically bind the `shop` header to the signed body before it is trusted. At minimum, document prominently that `data.shop` is unauthenticated and must be cross-checked by the host app against a known list of installed shop domains before use.

### Proof of Concept
```ruby
# Attacker has legitimately installed the app on "attacker-shop.myshopify.com"
# and receives a real webhook for that shop, e.g. body = '{"id":1,"note":"payload"}'
# with a valid HMAC computed by Shopify using the app's shared api_secret_key.

real_body = '{"id":1,"note":"payload"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, real_body)

# Attacker replays the same body+hmac but swaps the shop-domain header to the victim's shop
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unverified
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: real_body, headers: forged_headers)

# This succeeds: HMAC validation only checks the body, not the shop header
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: {...}, ...))
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
