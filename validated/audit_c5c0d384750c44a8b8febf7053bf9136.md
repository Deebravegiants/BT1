### Title
Unsigned Emporium Min-path calls drain Emporium's ERC20 holdings via zero-length token accounting - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol / contracts/CircomDataBuilder.sol)

### Summary
When `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which only constrains `emporiumMessage`, `timeStamp`, and `calldataHash` in the SNARK public inputs. Any unprivileged caller can supply an `EmporiumStack` (decoded from `externalActionData.externalActionMetadata`) with `signerAddress == address(0)`, which causes `verifyWallet` to skip signature verification entirely, and then have `EmporiumUpgradeable.runAction` execute arbitrary low-level calls (`op.endpoint.call{value: op.value}(op.callData)`) from the Emporium contract's identity, while the balance-accounting loops in both `Hinkal.transact` and `EmporiumUpgradeable.runAction` iterate zero times because `circomData.erc20TokenAddresses.length == 0`.

### Finding Description
The broken equality is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`**. This invariant is expected to hold via the per-token loop at [1](#0-0)  and the mirrored loop in `Hinkal.transact` at [2](#0-1) , but both loops are driven by `circomData.erc20TokenAddresses.length`, which the attacker sets to `0`.

Root cause chain:
1. `formInputForCircom` selects the minimal proof path whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [3](#0-2) . `formInputEmporiumMin` only emits `emporiumMessage`, `timeStamp`, `calldataHash` as public signals — it does not constrain `amountChanges`, `erc20TokenAddresses`, nullifiers, or `outCommitments` at all, since those are simply absent from the circuit's public/private input vector for this branch.
2. `dimensionsCheck` in `HinkalHelper.sol` only enforces that array lengths equal `dimensions.tokenNumber`; setting `tokenNumber = 0` is self-consistent and passes: [4](#0-3) .
3. In `Hinkal.transact`, since `erc20TokenAddresses.length == 0`, the `oldBalances`/`newBalances`/slippage-check loop never executes: [5](#0-4) .
4. `_externalTransact` builds `deltaAmountChanges` with length 0 and calls `EmporiumUpgradeable.runAction`: [6](#0-5) .
5. Inside `runAction`, `balancesBefore`/`balancesAfter` are computed over the empty `erc20TokenAddresses` array (both empty arrays), and the per-token accounting loop at lines 132-151 never runs, so no `BalanceChangeShouldBePositive` check or `handleOut` transfer-back accounting occurs for whatever the ops actually moved: [7](#0-6) .
6. `verifyWallet` is called before the ops execute. If the attacker sets `stack.signerAddress == address(0)`, the function marks the `emporiumMessage` as used and returns immediately — **no ECDSA signature check is performed at all**: [8](#0-7) .
7. The ops loop then executes attacker-supplied `EmporiumOperation[]`. Because `stack.signerAddress == address(0)`, every op falls into "CASE 2: Stateless Interaction," performing `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own address as `msg.sender`: [9](#0-8) . The only restriction is that the call's selector can't be `callHinkalWallet`/`doSendToRelay`; an ERC20 `transfer(attacker, amount)` selector passes this check freely.

Attacker's exact call: call `Hinkal.transact` with `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, `dimensions.tokenNumber = 0`, and `externalActionData.externalActionMetadata = abi.encode(EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: victimToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, emporiumTokenBalance))}], ...})`. Since `runAction` is only reachable via `onlyAllowedRecipient`, and `_externalTransact` in `Hinkal.sol` is the only legitimate caller registered as an allowed recipient, the attacker must go through `Hinkal.transact`, but a valid proof for the min-path circuit is trivial to generate for any self-chosen `emporiumMessage` (e.g. `Poseidon(messageSeed)`), since it constrains nothing about the ops or the token being drained.

Existing guards fail to prevent this because:
- `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` never inspect Emporium's internal `stack.ops` or `signerAddress` — those are opaque bytes (`externalActionMetadata`) to `Hinkal`/`HinkalHelper`.
- `verifyProof` only checks the 3 min-path signals, none of which encode the ops or token balances.
- `rootHashExists` is unrelated to this path (no nullifiers spent).
- The only guard meant to bind `stack.ops` to something authorized is `verifyWallet`'s ECDSA check, which is explicitly skipped for `signerAddress == address(0)`.

### Impact Explanation
Any unprivileged caller can drain the entire ERC20 (and ETH, via `op.value`) balance held by the `EmporiumUpgradeable` contract to themselves in a single transaction, with zero signature requirement and zero balance-accounting check. This is direct theft of protocol-held / in-flight user funds (funds temporarily sitting in Emporium as part of a multi-step signed flow, or any residual balance), matching the Critical severity category "direct theft of shielded or in-flight user funds." The exploit is fully repeatable for as long as Emporium holds any token balance and requires no special preconditions beyond a valid, self-generated min-path proof.

### Likelihood Explanation
Preconditions are minimal: the attacker needs (a) the Emporium contract registered as an external action (a normal, expected deployment state, not a privileged action by the attacker), (b) any nonzero ERC20/ETH balance sitting in Emporium (which arises naturally whenever a signed op deposits funds there mid-flow, e.g. before a subsequent withdrawal op executes), and (c) the ability to generate a proof for the trivial min-circuit (only 3 public signals, no relation to fund movement). Attacker cost is a single transaction plus gas; no relayer or admin cooperation is required since `originalSender == msg.sender` with `relay == address(0)` is a valid, permitted combination per `performHinkalChecks`. This is fully repeatable and requires no race condition.

### Recommendation
Do not allow `signerAddress == address(0)` (unsigned) Emporium stacks to reach `runAction` when there is any possibility of asset movement. Specifically:
- Require a valid signature verification path even when `signerAddress == address(0)`, or disallow value-transferring/arbitrary-call ops entirely when unsigned.
- Do not special-case away balance accounting when `erc20TokenAddresses.length == 0`; if the Min proof path is meant only for "message-only, no fund movement" actions, enforce at the Solidity level that `stack.ops` cannot target token contracts or transfer value when `erc20TokenAddresses.length == 0`, or better, always compute `balancesBefore`/`balancesAfter` for a fixed, protocol-known set of sensitive tokens/native ETH regardless of `erc20TokenAddresses.length`, and revert on any unaccounted decrease.
- Alternatively, restrict `formInputEmporiumMin` usage to a whitelisted subset of actions/endpoints that provably cannot exfiltrate funds (e.g., only allow `invokeWallet` ops or a "cancel" style operation), enforced on-chain rather than left to the prover's choice of proof path.

### Proof of Concept

1. 2. Fund `EmporiumUpgradeable` with `1000e6` of a mock 6-decimal ERC20 (`victimToken`) directly (simulating funds in flight).
3. Craft `circomData`: `erc20TokenAddresses = []`, `amountChanges = []`, `dimensions.tokenNumber = 0`, `externalActionData = {externalAddress: emporium, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack({v:0, r:0, s:0, signerAddress: address(0), ops: [EmporiumOperation({endpoint: victimToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e6))})], maxFee: 0, deadline: type(uint256).max}))}`, `emporiumMessage = Poseidon(messageSeed)` (attacker-chosen), `calldataHash` computed via `getHashedCalldata`.
4. Generate a valid proof `(a,b,c)` for the min circuit with public inputs `[emporiumMessage, timeStamp, calldataHash]`.
5. Call `hinkal.transact(a,b,c,dimensions,circomData)` from an attacker EOA with no special role.
6. Assert: `victimToken.balanceOf(emporium) == 0` (before was `1000e6`) and `victimToken.balanceOf(attacker) == 1000e6`, while `oldBalances == newBalances == []` in `Hinkal.transact` (the accounting arrays are empty and never flagged the drain) — proving the equality "assets moved == assets accounted" is broken (`1000e6 moved != 0 accounted`).

    function formInputForCircom(
        uint256 chainId,
        address verifyingContract,
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory) {
        if (
            circomData.externalActionData.externalActionId ==
            HINKAL_EMPORIUM_ACTION_ID &&
            circomData.erc20TokenAddresses.length == 0
        ) {
            return formInputEmporiumMin(circomData);
        } else {
            return formInputNormal(chainId, verifyingContract, circomData);
        }
    }

    function formInputEmporiumMin(
        CircomData calldata circomData
    ) internal pure returns (uint256[] memory input) {
        input = new uint256[](circomData.publicSignalCount);

        uint16 index = 0;

        input[index++] = circomData.emporiumMessage;

        input[index++] = circomData.timeStamp;
        input[index++] = circomData.calldataHash;
    }
