## Finding: Webhook shop-tenant attribution is not bound to the HMAC signature

### Title
Webhook Shop Identity Not Covered by HMAC, Enabling Cross-Tenant Event Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary

The bug report's root cause pattern — a value that is *acted upon* by privileged logic but *not included* in the value that is HMAC-verified — has a direct analog in this gem's webhook processing pipeline. The `shop` (tenant) attribution of an inbound webhook is taken from an HTTP header that is never covered by the HMAC signature check, breaking the intended equality: `shop the HMAC was computed for == shop the handler believes it received`.

### Finding Description

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, deliberately excluding the `shop` header from the signed material: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate_signature` verifies the request strictly against `verifiable_query.to_signable_string`, i.e. the body alone: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` accepts the request once the (body-only) HMAC check passes, then trusts `request.shop` — sourced from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header — to attribute the event to a tenant and hands it to the host application's handler: [3](#0-2) 

Because the HMAC secret (`Context.api_secret_key`) is the **app's** shared secret and is identical across every shop that installs the app (not a per-shop secret), any shop that installs the app can generate a request with a **valid** HMAC for arbitrary content it controls (e.g. by triggering its own `orders/create` webhook). That attacker then has a legitimate `(raw_body, hmac)` pair. Since the `shop` header is not part of the signed string, the attacker can replay that exact body/HMAC pair directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC match), and `Registry.process` will invoke the handler with `WebhookMetadata.new(... shop: request.shop ...)` pointing at the victim shop, even though the payload actually originates from the attacker's own shop.

This breaks the identity binding: **shop for which the HMAC was computed ≠ shop attributed to the event by the host application**, directly matching the "field acted on but not covered by the HMAC" class of bug called out in the report (analogous to the queue's `head`/`tail` accounting mismatch causing state to be attributed to the wrong logical owner).

### Impact Explanation

Any downstream host application that relies on `WebhookMetadata#shop` (as documented and demonstrated in `docs/usage/webhooks.md`) to scope side effects per tenant — updating that shop's local order/product records, crediting that shop's usage, triggering per-shop business logic — can be made to apply attacker-controlled webhook content under a victim shop's identity. This is a cross-tenant confusion primitive reachable by any unprivileged party who can install the app on their own store (a normal, unprivileged flow), without needing the victim's access token, the app's `client_secret`, or any interception of Shopify's traffic.

### Likelihood Explanation

Exploitation only requires: (1) installing the target app on an attacker-controlled shop (ordinary unprivileged action), (2) triggering a webhook topic that produces attacker-influenced body content, and (3) replaying the resulting `(body, hmac)` pair to the app's public webhook URL with a forged `shop-domain` header. No secrets, tokens, or elevated access are needed — only knowledge of the app's public webhook endpoint, which is necessarily discoverable/exposed for Shopify to call it.

### Recommendation

Bind the tenant identity into the verified material: include the `shop-domain` (and ideally `webhook-id`/`topic`) header value in `to_signable_string`, or independently verify that `request.shop` corresponds to a shop with a currently active, known installation/session before dispatching to handlers, rather than trusting the header standalone once body-HMAC passes.

### Proof of Concept

1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers/receives a legitimate `orders/create` webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC(api_secret_key, B)` — this HMAC is valid because `api_secret_key` is shared app-wide, per `HmacValidator.validate_signature`: [2](#0-1) 
2. Attacker crafts a raw HTTP POST to the app's public webhook route with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body normally (no cross-check between `shop` and `hmac`): [4](#0-3) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds since only `B` and `H` are checked, then dispatches `handler.handle(data: WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...))`: [5](#0-4) 
5. The host application's handler processes attacker-controlled data believing it came from `victim-shop.myshopify.com`.

          end
        end
        unless missing_headers.empty?

        end
