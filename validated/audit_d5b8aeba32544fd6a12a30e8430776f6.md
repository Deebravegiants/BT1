### Title
Unchecked ERC20 `transfer` Return Value in `IntentGatewayV2.withdraw`/`SweepDust` Permits Permanent Loss of Escrowed Funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2` (Tron variant) redeems and refunds escrowed order funds using raw low-level `.call()` invocations of `IERC20.transfer` and only checks that the *call itself* did not revert (`success`). It never decodes/validates the boolean return value that the ERC20 standard uses to signal transfer failure. This is the exact "unchecked return value" bug class described in the external report for `IComptroller.exitMarket`/`enterMarkets`, applied here to escrow token transfers instead of a Comptroller call.

### Finding Description
In `withdraw()` and the `SweepDust` branch of `onAccept()`, escrow release/refund/dust-sweep is implemented as: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        ...
        (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
        if (!success) revert TransferFailed();
        _orders[body.commitment][token] -= amount;
        ...
    }
    ...
    (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
    if (!success) revert TransferFailed();
    ...
}
```

`success` here only reflects whether the low-level call reverted, not whether the token's own `transfer` logic actually succeeded. Many ERC20 tokens (paused tokens, tokens with blacklists, tokens with custom failure semantics, or tokens that historically return `false` instead of reverting) return `abi.encode(false)` on failure while the call itself still succeeds (`success == true`). The code treats this as a successful transfer: it marks `_filled[body.commitment] = beneficiary` (irreversibly marking the order as settled) and decrements `_orders[body.commitment][token] -= amount` (erasing the escrow bookkeeping), even though the beneficiary received nothing.

The same unchecked pattern appears in the `SweepDust` handling of the same `onAccept` function: [2](#0-1) 

Notably, the contract elsewhere correctly uses OpenZeppelin's `SafeERC20.safeTransferFrom`/import for deposits, but deliberately switches to raw, return-data-blind `.call` for the withdrawal/dust-sweep paths (likely to accommodate TRC20 tokens on Tron that don't return a bool at all), which removes the safety check that `SafeERC20` would otherwise provide against tokens that *do* return `false`.

### Impact Explanation
This is reachable from an unprivileged relayed message: `RedeemEscrow`/`RefundEscrow` requests are delivered via `onAccept` from the ISMP host (authenticated cross-chain message, not admin-gated) and route into `withdraw()`, and the `onGetResponse` timeout-refund path also calls `withdraw()`. Once a token used as an order's input/fee asset returns `false` instead of reverting on transfer, the contract:
1. Marks the order as permanently filled/refunded (`_filled[...] = beneficiary`), preventing retry.
2. Decrements/erases the escrow record for those tokens without delivering them to the beneficiary.

The escrowed tokens become permanently stranded in the `IntentGatewayV2` contract with no accounting path left to recover them — a permanent freezing/loss of user funds, matching an intents-escrow fund-loss vulnerability.

### Likelihood Explanation
This does not require a malicious admin, governance, or relayer — it is triggered purely by the behavior of the escrowed ERC-20 token itself (e.g., a token that pauses, blacklists a beneficiary, or returns `false` on insufficient balance/allowance edge cases instead of reverting), combined with a normal, permission-less `RedeemEscrow`/`RefundEscrow` message flow. Given IntentGatewayV2 is designed to support arbitrary tokens configured by users placing orders, this is a realistic and directly reachable condition rather than a contrived edge case.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` handler with a transfer helper that both checks call success **and** decodes/validates the returned boolean (à la `SafeERC20.safeTransfer`, with a fallback for zero-return-data tokens if Tron TRC20 compatibility is required). At minimum, decode `returndata` when non-empty and require it to be `true` before mutating `_filled`/`_orders` state.

### Proof of Concept
1. An order is placed using an ERC20 token `T` where `T.transfer()` returns `false` (rather than reverting) when the transfer is disallowed (e.g., `beneficiary` is blacklisted, or the token is paused for transfers), while `T` remains a valid, allowed asset for orders.
2. `RedeemEscrow` (or `RefundEscrow`) is relayed for the order's commitment via the normal cross-chain message flow, invoking `onAccept` → `withdraw(body, ...)`.
3. Inside `withdraw`, `token.call(...)` returns `(true, abi.encode(false))` — the low-level call succeeds, so `success == true` and no revert occurs.
4. `_filled[body.commitment] = beneficiary` and `_orders[body.commitment][token] -= amount` execute, permanently marking the order settled and erasing the escrow accounting, while the beneficiary received zero tokens.
5. The escrowed tokens remain locked in the `IntentGatewayV2` contract balance with no remaining code path to reclaim them for the affected order.
