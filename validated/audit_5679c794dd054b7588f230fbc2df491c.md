### Title
Webhook HMAC Signature Does Not Bind `shop`/`topic`/`webhook-id` Headers, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` computes/verifies the HMAC solely over that body [1](#0-0) . However, `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` and `request.topic` — both read straight from unauthenticated HTTP headers — to select the handler and to populate `WebhookMetadata` passed to application code [2](#0-1) . Because the signature never binds these header fields, a valid `(body, hmac)` pair produced for one shop/topic can be replayed with different `shop-domain`/`topic`/`webhook-id` headers and still pass `HmacValidator.validate` [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`hmac == HMAC(secret, body ++ shop ++ topic)`, i.e. the verified bytes must equal the bytes the application acts on.

Instead, the gem verifies:
`hmac == HMAC(secret, body)` while acting on `shop`, `topic`, `webhook_id`, `api_version` taken from headers that are excluded from `to_signable_string` [4](#0-3) .

`ShopifyAPI::Context.api_secret_key` (the app's client secret) is the same HMAC key for every installed shop — it is not shop-specific [5](#0-4) . Any unprivileged user who installs the target app on their own (attacker-controlled) shop can trigger a legitimate Shopify webhook delivery, capturing a valid `(raw_body, hmac)` pair signed with the app's shared secret. Because the signature covers only `raw_body`, that exact pair remains valid regardless of what `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers are sent alongside it.

`Registry.process` then:
1. Validates only the HMAC of the body [6](#0-5) .
2. Looks up the handler using the (unauthenticated) `topic` header.
3. Constructs `WebhookMetadata` using the (unauthenticated) `shop` header and hands it to the application's handler [7](#0-6) .

This is directly analogous to the go-f3 bug class: a verification result (the HMAC check) is cached/trusted without validating the specific context (shop/topic) it is being applied to, allowing reuse of a valid credential (HMAC over body) in a context where it should be invalid.

### Impact Explanation
Multi-tenant apps commonly key their tenant/session lookup off `WebhookMetadata#shop` before processing order/customer/GDPR data. Because `shop` is not bound by the signature, an attacker who legitimately installs the app on their own store can forge webhook deliveries that the gem will report as authentically signed for an arbitrary other shop, or for an arbitrary topic. This is a cross-tenant boundary break — the gem itself vouches for `request.shop`/`request.topic` as HMAC-verified when they are not.

### Likelihood Explanation
Any user can install a public/free Shopify app to obtain a legitimately-signed `(body, hmac)` pair, since the same `api_secret_key` is used across all merchants of that app. No access token, `client_secret`, or privileged credential is required — only normal use of a shop and the app's public webhook endpoint.

### Recommendation
Include the fields the application relies on (`shop`, `topic`, `webhook_id`) in the signable string used for HMAC verification, e.g., have `to_signable_string` incorporate the `x-shopify-shop-domain`/`x-shopify-topic` header values in addition to the raw body, or otherwise cryptographically bind the header-derived identity to the verified payload before exposing it via `WebhookMetadata`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`. Trigger any webhook event (e.g., `products/create`) to receive a real request with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC_SHA256(api_secret_key, B)`.
2. Replay the captured request to the app's webhook endpoint, but replace:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <any topic the app registered a handler for>`
   - keep `x-shopify-hmac-sha256: H` and body `B` unchanged.
3. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H` [3](#0-2) .
4. `Registry.process` dispatches to the handler registered for the spoofed topic and passes `shop: "victim-shop.myshopify.com"` in `WebhookMetadata`, even though that shop never sent this webhook [7](#0-6) .
