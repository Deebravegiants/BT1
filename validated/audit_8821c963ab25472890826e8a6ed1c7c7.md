Confirmed: `Registry.process` passes `request.shop` directly into `WebhookMetadata` handed to the app's handler, and `Request#hmac`/`to_signable_string` only cover the raw body — the `shop-domain` header is never part of the signed payload.### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC over the raw request body only, while the `shop-domain` header — which the gem hands to the app's handler as the authoritative tenant identifier — is never included in the signed material. Any party who possesses one valid `(body, hmac)` pair for the shared `api_secret_key` can replay it with an arbitrary `shop-domain` header and have it accepted as an authentic webhook "from" any shop.

### Finding Description
`Request#to_signable_string` returns only the raw body, and `Request#hmac` is read from the `hmac-sha256` header: [1](#0-0) 

`Utils::HmacValidator.validate` (shared with OAuth) only checks that `HMAC(secret, verifiable_query.to_signable_string) == hmac`, i.e. it verifies the *body bytes*, never the `shop` field: [2](#0-1) 

`Registry.process` validates the HMAC and then trusts `request.shop` verbatim, forwarding it into `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

The documented usage pattern confirms `data.shop` is meant to be trusted as the tenant identifier for downstream processing (e.g. enqueuing per-shop jobs): [5](#0-4) 

The identity binding that should hold is: `hmac == HMAC(secret, body ++ shop)`, i.e. the shop the handler acts on must be cryptographically bound to the signature. Instead the gem only enforces `hmac == HMAC(secret, body)`, leaving `shop` free of any binding.

**Attack sequence:**
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (a normal, unprivileged install — no leaked secret needed).
2. Shopify sends the attacker a legitimate webhook with a valid `x-shopify-hmac-sha256` for some body (e.g. an `orders/create` payload the attacker fully controls, since they can create orders in their own store).
3. Attacker replays that exact `raw_body` + `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` passes (body/hmac pair is genuinely valid for `api_secret_key`, since the secret is shared across all installs of the app, not shop-specific).
5. `Registry.process` dispatches to the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled-body, ...)`.

The app-provided handler will now perform shop-scoped actions (updating records, queuing jobs, cache invalidation, etc.) attributed to the victim shop, using data the attacker fully controls — a cross-tenant identity-binding break analogous to the ANTE report's core pattern: a field acted upon (`shop`) that is not covered by the authentication check (`hmac` over body only).

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: `shop` is trusted as an authenticated field but is not part of the signed payload. Any merchant who has installed the app (an unprivileged party with respect to other merchants) can inject attacker-controlled webhook data attributed to any other shop, causing cross-tenant data corruption/impersonation in the host app. This maps to the required impact category of cross-tenant access.

### Likelihood Explanation
Requires only an ordinary app install (no leaked credentials, no TLS interception) plus the ability to trigger one genuine webhook for the attacker's own shop and replay it with a modified header to the app's endpoint. This is realistic and low-effort.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the material that is HMAC-verified, or otherwise cryptographically tie the shop-domain header to the signed body — e.g. Shopify's own model relies on the webhook path/URL per shop being unguessable/registered per shop, but if this gem accepts an arbitrary `shop-domain` header as authoritative, it must include that header in `to_signable_string` for validation, or the docs/API must make clear that host apps must independently verify `shop` against their own registration record before trusting it as a tenant key.

### Proof of Concept
```ruby
# Attacker owns "attacker.myshopify.com" and receives one genuine webhook, e.g.:
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, '{"id":1}')
headers_from_shopify_to_attacker = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker.myshopify.com",
}

# Attacker replays same body+hmac but swaps shop-domain header to the victim:
forged_headers = headers_from_shopify_to_attacker.merge(
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
)

request = ShopifyAPI::Webhooks::Request.new(raw_body: '{"id":1}', headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation passes (body unchanged); handler receives
#    WebhookMetadata(shop: "victim-shop.myshopify.com", body: {"id"=>1}, ...)
```
