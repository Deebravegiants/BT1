### Title
Webhook `shop-domain` header is trusted as the authenticated tenant identity while only the raw body is covered by the HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC over that same object and then, once it passes, forwards `request.shop` straight into the handler as trusted tenant metadata [3](#0-2) . The identity binding broken is: `shop_authenticated_by_hmac == shop_used_by_handler_for_tenant_selection` is assumed true, but the HMAC signature never actually covers the `shop` field.

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the `hmac` header [4](#0-3) . For webhook requests, `to_signable_string` is only the raw JSON body — the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are excluded from what's signed [5](#0-4) . `Registry.process` treats a passing HMAC check as proof that the *entire request*, including `request.shop`, is authentic, and hands `request.shop` to the app's handler as `WebhookMetadata#shop` without further validation [3](#0-2) . The gem's own documentation reinforces this trust by telling integrators to key their downstream processing off `data.shop` directly (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) with no caveat that this field is unauthenticated [6](#0-5) .

Critically, the shared secret (`api_secret_key`) used to sign the HMAC is the **app's** secret, identical for every shop that installs the app — it is not shop-specific. Any attacker who can install the app on their own (attacker-controlled) shop can legitimately trigger a webhook and thereby obtain a raw body + valid HMAC pair signed with the app's secret. Because the `shop-domain` header is not part of the signed content, the attacker can replay that same body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `X-Shopify-Shop-Domain` header. `Registry.process` will validate successfully (the HMAC over the body is still correct) and will invoke the handler believing the event legitimately originated from the victim shop.

### Impact Explanation
This breaks the tenant/shop identity binding in a multi-tenant app: the HMAC proves body authenticity from *some* installation of the app, not authenticity of the claimed shop. Any app logic that uses `WebhookMetadata#shop` to select which shop's stored offline session/access token to act on, or to write per-shop state, is subject to cross-tenant confusion — an attacker-controlled event can be attributed to (and drive actions against) a victim shop's context. This matches the Critical "cross-tenant access" impact category, since it originates entirely from processing logic inside this gem (`Registry.process` / `Webhooks::Request`), not from the host app ignoring documented behavior — the gem's own docs actively encourage trusting `data.shop`.

### Likelihood Explanation
Likelihood is bounded by needing legitimate app installation on an attacker-owned shop (any developer/merchant can install a public app on their own store to obtain a validly-signed payload) and requires the target app to route/authorize business logic by the webhook's `shop` field, which is the pattern explicitly demonstrated in this gem's own documentation. No access to `api_secret_key`, tokens, or credentials belonging to the victim is required.

### Recommendation
Either bind the shop domain into the signed payload verification (e.g., cross-check `request.shop` against the shop associated with the specific registered `webhook_id`/subscription retrieved from Shopify, or maintain a server-side mapping of webhook IDs to shops established at registration time) or explicitly document that `shop` on `WebhookMetadata` is unauthenticated and must be cross-checked against the app's own installation/session records before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, and triggers a subscribed webhook topic (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — both are valid because they are signed with the app's real `api_secret_key`.
2. Attacker replays the exact same raw body + HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body, `Utils::HmacValidator.validate(request)` succeeds because it only checks the raw body against the HMAC [7](#0-6) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` set to `victim-shop.myshopify.com` [8](#0-7) , causing the app to process an attacker-fabricated event as if it came from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
