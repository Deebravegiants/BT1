### Title
Unvalidated swap-route pool can add a victim token transfer to the signed authorization tree - ([File: contracts/swap-aggregator/src/execute/mod.rs](contracts/swap-aggregator/src/execute/mod.rs))

### Summary
A swap route chooses an arbitrary `pool` address for each hop, and the router invokes that address beneath `sender.require_auth()`. A malicious pool can therefore invoke `token.transfer(sender, attacker, amount)` during route execution. Soroban simulation records that transfer as a child of the victim’s authorization entry; if the victim signs the simulated tree, the malicious hop drains unrelated wallet tokens even when the route otherwise produces valid output. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`execute_strategy` authenticates only the top-level `sender` before decoding and executing the caller-supplied route. [4](#0-3) 

Every `Swap` instruction constructs `SwapHop.pool` directly from the payload’s `assets` registry and dispatches to that address through the selected venue adapter. There is no pool allowlist, expected-pool validation, or restriction preventing the selected contract from making further calls while the sender’s authorization context is active. [2](#0-1) [5](#0-4) 

The router’s settlement checks only enforce a positive measured output and exact input spend. They do not prevent third-party route code from invoking a token transfer from the `sender` to an attacker. [6](#0-5) 

This is reachable both through direct `execute_strategy` calls and controller strategy paths such as `swap_collateral`, which pass user-controlled route bytes into the configured router. [7](#0-6) [8](#0-7) 

### Impact Explanation
An attacker can steal arbitrary SEP-41 tokens held by the victim, including assets that are not listed by the lending protocol and are outside the routed `amount_in`. The theft amount is bounded by the victim’s token balance, not by the swap input, minimum output, collateral value, or final health-factor checks. [9](#0-8) [10](#0-9) 

The repository’s test demonstrates the complete effect: a malicious hop transfers the victim’s entire unrelated wallet-token balance to the attacker while the swap still credits the expected output. [11](#0-10) 

### Likelihood Explanation
Exploitation requires the victim to submit and sign a malicious route. A quoting service, route UI, or attacker-supplied route can return a simulation containing an extra child authorization for the token theft. If the wallet or user signs that tree, the host accepts it and executes the transfer. [12](#0-11) [3](#0-2) 

No privileged role, leaked key, token approval, upgrade, or existing allowance is required. The attacker needs only to convince a user to execute the poisoned route; the victim’s normal transaction signature supplies the authorization. [1](#0-0) [13](#0-12) 

### Recommendation
Constrain route execution so user-selected pool addresses cannot run arbitrary code under the sender’s authorization context. Prefer a governance-maintained pool/venue registry and resolve hops to registered pool IDs rather than arbitrary `Address` values. For each venue, validate that the selected pool is the canonical pool for `token_in` and `token_out` before dispatch.

Until protocol-level validation exists, clients must simulate the route, decode the complete authorization tree, and reject any child invocation other than the expected input-token transfer. This mitigates user signing but does not remove the contract-level arbitrary-code surface. [14](#0-13) 

### Proof of Concept
The repository already contains a working proof in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Alice supplies USDC and owns `77_770_000_000` units of an unrelated token. [15](#0-14) 
2. The attacker deploys `RogueHopPool` with a plan containing Alice, the unrelated token, the attacker recipient, and the full wallet balance. [16](#0-15) 
3. The malicious route names that contract as `hop_pool` while otherwise requesting a fair USDC-to-ETH swap. [17](#0-16) 
4. During `swap_collateral`, the router invokes the route-selected pool, and that pool calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)`. [18](#0-17) [10](#0-9) 
5. Simulation records the theft as a child invocation beneath Alice’s `swap_collateral` authorization. [12](#0-11) 
6. With an honest tree containing no child transfer, the host rejects the rogue transfer and rolls back the call. With the simulated poisoned tree, the swap succeeds, Alice’s wallet balance becomes zero, and the attacker receives the full balance. [19](#0-18)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's

final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
