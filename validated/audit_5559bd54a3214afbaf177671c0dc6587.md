### Title
`Wallet#updateSeed` mutates seed metadata without checking wallet lock state - ([File: features/wallet/module/wallet.js])

### Summary
`updateSeed({ seedId, label })` in `Wallet` class writes to `#seedMetadataAtom` without calling `#assertWalletIsUnlocked()`, unlike `addSeed` and `removeManySeeds` which both invoke this guard before mutating state. This allows an unprivileged caller to update seed labels (and inject arbitrary `label` string content) into persisted wallet metadata even while the wallet is locked.

### Finding Description
`addSeed` and `removeManySeeds` both call `await this.#assertWalletIsUnlocked()` as their first statement [1](#0-0) , [2](#0-1) . `updateSeed`, however, only asserts that `seedId` and `label` are truthy and then directly mutates `#seedMetadataAtom` — no lock check exists anywhere in the method: [3](#0-2) 

This method is exposed on the public wallet API surface as `wallet.updateSeed` [4](#0-3)  and typed for external SDK consumption [5](#0-4) , meaning any code path that can invoke the wallet API (RPC/dapp bridge) can call `updateSeed` regardless of `isLocked()` state.

Regarding the "unsanitized label" portion of the question: the `label` field is stored as an opaque string in `#seedMetadataAtom` with no length/content validation at the storage layer (`createStorageAtomFactory`) [6](#0-5) . However, I found no evidence in the codebase of any UI consumer rendering `SeedMetadata.label` via `dangerouslySetInnerHTML`, raw HTML injection, or any other unsafe-render sink — a repo-wide search for `dangerouslySetInnerHTML`/`innerHTML` returned no matches. The analogous `wallet-accounts` label field is rendered through plain string interpolation/selectors (`get-proper-name.ts`) with no HTML injection sink [7](#0-6) . Therefore the "stored XSS" claim is speculative and unsupported by evidence in this codebase — this part of the question cannot be validated.

### Impact Explanation
The confirmed impact is limited to unauthorized metadata mutation: an attacker able to call `wallet.updateSeed` while the wallet is locked can rewrite a seed's `label`/`dateUpdated` fields in persisted `#seedMetadataAtom` state without needing to unlock the wallet, violating the "locked means locked" invariant that `addSeed`/`removeManySeeds` enforce. This does not disclose secrets, bypass signing, or grant privileged wallet state access — it is a metadata integrity/authorization gap, not a key-compromise vector. The stored-XSS component of the question is not substantiated by any rendering sink found in the repo.

### Likelihood Explanation
High feasibility for the missing-lock-check portion: `updateSeed` is directly reachable via the public `walletApi` with no preconditions beyond having `seedId` and `label` values, and is trivially reproducible via a unit test comparable to the existing lock-check test for `removeSeed` [8](#0-7) , which has no analog for `updateSeed` in the test suite.

### Recommendation
Add `await this.#assertWalletIsUnlocked()` as the first statement in `updateSeed`, matching `addSeed`/`removeManySeeds`. Optionally enforce a max length / sanitize `label` input consistently with `LABEL_MAX_LENGTH` used in `wallet-accounts` [9](#0-8)  for defense-in-depth, even though no exploitable rendering sink was found for this field.

### Proof of Concept
```js
// features/wallet/module/__tests__/index.test.js
it('does not allow updating seed metadata while wallet is locked', async () => {
  await wallet.create()
  await wallet.unlock()
  const seedId = await wallet.addSeed({ mnemonic: otherMnemonic, label: 'Metamask Savings' })
  await wallet.lock()

  await expect(
    wallet.updateSeed({ seedId, label: 'Attacker Controlled' })
  ).rejects.toThrow('locked')

  const metadata = await seedMetadataAtom.get()
  expect(metadata[seedId].label).toBe('Metamask Savings')
})
```
Expected current behavior: the assertion fails because `updateSeed` succeeds and overwrites the label even though the wallet is locked, confirming the missing `#assertWalletIsUnlocked()` check. The content-sanitization/XSS portion of the question could not be validated with a reproducible sink in this codebase and should be excluded from the finding unless a rendering consumer using unsafe HTML injection of `SeedMetadata.label` is identified.
