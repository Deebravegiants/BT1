## #Vulnerability found

### Title
Webhook `shop` domain is trusted for tenant routing but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw body, then hands the handler a `shop` value read from an HTTP header that is never included in the signed bytes. The binding the gem's own documentation claims to provide — "this will verify the request did indeed come from Shopify" — does not extend to the `shop` field that host apps use to select which tenant's data to act on.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 
`shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, while `to_signable_string` returns only `@raw_body`. `HmacValidator.validate` computes/compares the HMAC exclusively over `to_signable_string`: [2](#0-1) 
`Registry.process` performs only this body-HMAC check before dispatching the handler with the header-derived `shop`: [3](#0-2) 

The equality the gem should guarantee is:
`shop bound inside the HMAC-signed bytes == shop delivered to the handler`

What actually holds is:
`shop present in an unsigned HTTP header == shop delivered to the handler`

Because the HMAC secret (`Context.api_secret_key` / `client_secret`) is a single, app-wide secret shared across every merchant shop that has installed the app (as shown by its use in `Oauth.validate_auth_callback` and `TokenExchange.exchange_token`, which are not shop-scoped), a valid `(raw_body, hmac)` pair for one tenant is cryptographically indistinguishable from a valid pair for any other tenant signed by the same app secret. The documentation for `Registry.process` explicitly asserts it "will verify the request did indeed come from Shopify," which developers reasonably read as "the whole payload, including which shop it's for, is verified" — but the `shop` header is not covered by that check at all. [4](#0-3) 

### Impact Explanation
An attacker who legitimately installs the app on their own store receives genuine `(body, shopify-hmac-sha256)` pairs signed with the app's shared secret for events they control (e.g., `orders/create`, `customers/data_request`). By replaying that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain, the request still passes `HmacValidator.validate` (body unchanged) and `Registry.process` calls the handler with `WebhookMetadata` claiming the victim's `shop`. Any host application relying on `data.shop` from `WebhookMetadata` for tenant-scoped writes/lookups (as shown in the gem's own documented handler example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) will process attacker-controlled webhook content under an incorrect merchant identity — a cross-tenant data-injection/confusion primitive. [5](#0-4) 

### Likelihood Explanation
Exploitation requires only: (1) the attacker be a legitimate, unprivileged installer of the app on their own shop (no elevated access, no leaked credentials, no access to `api_secret_key`), and (2) the ability to send an arbitrary HTTP POST with attacker-chosen headers to the app's public webhook endpoint (standard capability of any internet client). No secret material needs to be known or brute-forced — only a previously-observed, still-valid `(body, hmac)` pair is replayed with a modified header. This is a low-effort, no-privilege attack path.

### Recommendation
Bind the shop identity to the HMAC-verified payload rather than to an independent header. Options: include `shop-domain` in the bytes covered by the HMAC signature check (impossible without protocol changes), or — more practically — have `Registry.process` cross-check that the received `shop` corresponds to a shop for which this exact `webhook_id`/topic combination was actually registered (e.g., verify against Shopify via the webhook subscription rather than trusting the header at face value), and document clearly that `data.shop` is currently derived from an unauthenticated header so host apps must not treat it as cryptographically bound.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for `orders/create`.
2. Shopify sends a legitimate webhook: body `B`, header `shopify-hmac-sha256: H` (valid for the app's shared `client_secret`), `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays `POST /callback/orders/create` with the same body `B` and header `H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checks `B`/`H`. [6](#0-5) 
5. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)` — attacker-controlled content processed under the victim's tenant identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
