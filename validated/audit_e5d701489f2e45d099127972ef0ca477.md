### Title
Silent `U256`-to-`u128` truncation of accumulated relayer fees on substrate withdrawal - ([File: modules/pallets/relayer/src/withdrawal.rs])

### Summary
`Pallet::<T>::withdraw` stores relayer fees as `U256` in `Fees<T>` but truncates the value to `u128` via `.low_u128()` when the withdrawal destination is a substrate chain, silently discarding any bits above `u128::MAX` instead of erroring or using a checked conversion. This mirrors the reported pattern of using an undersized integer type for a monetary `amount`, which can silently corrupt/lose value instead of failing safely.

### Finding Description
`Fees<T>` accumulates relayer rewards as `U256` via `accumulate_fee_and_deposit_event` in `modules/pallets/relayer/src/accumulate.rs` (`*inner += fee;`), with no upper bound enforced on the accumulated value. When a relayer calls `withdraw_fees` → `Pallet::<T>::withdraw` (`modules/pallets/relayer/src/withdrawal.rs`), for substrate destinations the code does:

```rust
Message::WithdrawRelayerFees(WithdrawalRequest {
    amount: available_amount.low_u128(),
    ...
})
```

`U256::low_u128()` takes only the lowest 128 bits and drops the rest with **no error, no saturation, and no revert** if `available_amount > u128::MAX`. The EVM-destination branch instead uses `available_amount.into()` into the EVM manager's `U256`-shaped ABI type, so only the substrate withdrawal path is affected. [1](#0-0) [2](#0-1) 

This is structurally the same defect class as the referenced report: a value that is legitimately represented in a wide integer type (`U256`, analogous to the report's `u128`) is coerced into a narrower type (`u128`, analogous to the report's `u64`) at the point of withdrawal, with no bounds check, so a value that exceeds the narrower type's capacity is silently mangled rather than rejected.

### Impact Explanation
If a relayer's accumulated `Fees<T>` entry for a substrate destination ever exceeds `u128::MAX` (~3.4×10^38), `low_u128()` wraps the value, and the pallet dispatches a withdrawal for the wrong (truncated) amount while zeroing out the full, correct `U256` balance in storage (`Fees::<T>::insert(..., U256::zero())`). The relayer would receive a smaller amount than they are entitled to and the difference becomes permanently unrecoverable — the storage is cleared regardless of the truncated value actually paid out, which is a permanent freezing/loss of legitimately earned relayer funds.

### Likelihood Explanation
This is far less likely to trigger in practice than the referenced report. The original bug used `u64` (max ≈ 1.8×10^19), which a single 18-decimal token deposit can realistically exceed (as demonstrated by the cited $5,000–$50,000 rental deposit scenarios). Here the narrowing target is `u128` (max ≈ 3.4×10^38), a value that is essentially unreachable through any realistic combination of per-request relayer fees accumulating over time, even with pathological fee-setting by a malicious requester repeatedly paying enormous `fee.fee` values on dispatch. No other reachable amount-truncation instance of comparable severity (e.g., a `u64`/`u32` amount field with realistically reachable overflow) was found elsewhere in the token-bridge mint/burn (`HyperFungibleToken`, `pallet-hyper-fungible-token`), intents escrow/bid, or bandwidth-purchase code paths — those consistently use `U256`/`u128`/checked `try_into` conversions that reject rather than silently truncate.

### Recommendation
Replace `available_amount.low_u128()` with a checked conversion (e.g., `u128::try_from(available_amount)` or `TryInto`) that returns a dispatch error (or splits the withdrawal into multiple bounded payouts) instead of silently truncating, and only zero the `Fees<T>` entry for the amount actually dispatched, mirroring the fix recommended in the referenced report (use a type wide enough for the value, and never let a lossy narrowing conversion silently execute on a fund-moving path).

### Proof of Concept
1. A relayer's `Fees<StateMachine::Kusama(_), address>` entry accumulates via `accumulate_fee_and_deposit_event`, which performs unchecked `U256` addition with no upper bound.
2. Over a very large number of accumulations (theoretically, if fee amounts and/or count are large enough), the stored `U256` value exceeds `u128::MAX`.
3. The relayer calls `withdraw_fees` with a valid signature; `Pallet::<T>::withdraw` reads `available_amount` (the full `U256`), computes `amount: available_amount.low_u128()` for the substrate branch, dispatches the ISMP `WithdrawRelayerFees` message with the truncated amount, and unconditionally zeroes `Fees::<T>` for the full original `U256` value.
4. The destination chain's `HyperbridgeWithdrawalModule::on_accept` transfers only the truncated `u128` amount to the relayer; the remainder is permanently lost since the source-side ledger has already been zeroed. [3](#0-2)
