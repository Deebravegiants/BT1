### Title
Webhook `shop` (and `topic`/`webhook-id`) values are trusted for tenant dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the shop domain (and topic/webhook id) used to authorize and dispatch the webhook are taken from unauthenticated HTTP headers. This breaks the identity binding `hmac_signed_bytes == bytes_acted_on`: the HMAC only proves the body was signed by Shopify with the app's shared secret, but it proves nothing about which shop the body belongs to. Any app user who receives one legitimately signed webhook (for their own installed shop) can replay that exact body against the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop, and `Utils::HmacValidator.validate` will still accept it.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are read straight from headers with no cryptographic binding to that body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely over `to_signable_string`: [3](#0-2) 

`Webhooks::Registry.process` then trusts `request.shop` (and `request.topic`) as the tenant identity for dispatch after this HMAC check passes: [4](#0-3) 

Since the app's `api_secret_key` is shared across all shops that install the app, an HMAC computed over a given body is valid for that body under any shop domain header — the shop domain is never part of the signed material. This equality that should hold — `shop_used_for_dispatch == shop_authenticated_by_hmac` — does not, because the HMAC only authenticates `(secret, body)`, not `(secret, body, shop)`.

### Impact Explanation
This is a cross-tenant confusion vector: a merchant who has installed the app (an "unprivileged internet user" with respect to other tenants) can capture a legitimately-signed webhook delivered to their own endpoint and replay it with a forged `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header pointing at a different, victim shop. `HmacValidator.validate` still returns `true` because it only checks the raw body bytes against the shared secret. The host application's webhook handler then processes this payload believing it originates from the victim shop, potentially triggering tenant-scoped side effects (data writes, session/state changes, business logic keyed by `shop`) attributed to the wrong tenant — a cross-tenant access impact.

### Likelihood Explanation
Any actor who can install the app on a shop they control (the normal, unprivileged path for any Shopify app) can obtain real, correctly-signed webhook deliveries for arbitrary events/bodies they can produce in their own store (e.g., creating an order or product with attacker-chosen content). Replaying that body against the app's public webhook endpoint with a modified shop header requires no access to `api_secret_key`, access tokens, or any other credential — only the ability to send an HTTP request, which matches the "unprivileged internet user" threat model.

### Recommendation
Bind the tenant-identifying fields into the signed material verified by the gem, or explicitly document/enforce that host applications must not use `request.shop`/`request.topic`/`request.webhook_id` as a trust boundary independent from the HMAC. Concretely, make `Webhooks::Request#to_signable_string` (or a parallel verification step) include the shop domain, topic, and webhook id alongside the body, or have `HmacValidator`/`Registry.process` cross-check `request.shop` against the shop already known to be associated with that specific `webhook_id`/subscription before dispatch, so that a valid HMAC for one shop's body cannot be replayed under a different shop's identity.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal, unprivileged flow).
2. Attacker triggers a webhook event (e.g., `orders/create`) with a body they fully control, and Shopify delivers it to the app's webhook endpoint with headers:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>`
3. Attacker captures the raw body and valid HMAC, then re-POSTs the identical body to the same endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (topic/webhook-id can also be altered).
4. `Webhooks::Request#to_signable_string` returns the same `@raw_body`, so `HmacValidator.validate` recomputes the same HMAC and it matches (`lib/shopify_api/utils/hmac_validator.rb` lines 12-31), since the shop header is never part of the signed data.
5. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb` lines 188-199) passes `request.shop` = `victim-shop.myshopify.com` to the handler, causing the host application to process attacker-controlled data as if it came from the victim tenant.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
