## Analysis

The Beanstalk report reduces to one custody invariant: **a migration/reconciliation path that silently overwrites authoritative custody state (recapitalization amount) using a value that does not match reality, instead of re-deriving/asserting the true value.**

I looked for an Aptos-native analog where a migration path silently overwrites a custody-control field (not a balance, but an *authority* field like `frozen`) based on stale/secondary state rather than the authoritative one, in `coin.move`, `fungible_asset.move`, `object.move`, `multisig_account.move`, and `resource_account.move`.

- `object.move` transfer/burn/ownership logic is well-guarded (owner checks, `Untransferable`, `LinearTransferRef` binding, tombstone reclaim logic) — no analog found.
- `multisig_account.move` owner add/remove/swap logic is properly gated to only be invocable through the multisig's own signer (`entry fun` non-public convention) — no analog found.
- `resource_account.move` / `account::create_resource_account` correctly zero out the auth key and gate signer capability — no analog found.
- `dispatchable_fungible_asset.move` / `confidential_asset.move` already defensively re-measure balances before/after dispatchable transfers (`assert!(amount == before - fungible_asset::balance(...))`) — this pattern is the *fix* for the Beanstalk-style bug, already applied here, so no analog found.
- The strongest candidate is in `coin::maybe_convert_to_fungible_store`, where the frozen-status reconciliation logic overwrites the Fungible Asset primary store's `frozen` flag using the legacy `CoinStore.frozen` field, without checking whether the FA-side freeze was independently and more recently applied via `FreezeRef`/`TransferRef` on the paired Fungible Asset.

### Title
Coin-to-Fungible-Asset migration can silently unfreeze a compliance-frozen primary fungible store - (File: aptos-move/framework/aptos-framework/sources/coin.move)

### Summary
`coin::maybe_convert_to_fungible_store` reconciles the legacy `CoinStore<CoinType>.frozen` flag with the paired Fungible Asset primary store's frozen flag by force-overwriting the FA store's frozen state to match the (stale) `CoinStore` value, whenever they differ, rather than treating the FA-side freeze as authoritative.

### Finding Description
`maybe_convert_to_fungible_store` [1](#0-0)  is invoked by the user-callable entry functions `migrate_to_fungible_store` (self-triggered, any signer on their own account) and `migrate_coin_store_to_fungible_store` (batch, any address vector) [2](#0-1) .

When a `CoinStore<CoinType>` still exists for an account and it is migrated, the function does:
```
if (frozen != fungible_asset::is_frozen(store)) {
    fungible_asset::set_frozen_flag_internal(store, frozen);
}
``` [3](#0-2) 

This forces the FA primary store's frozen bit to match the legacy `CoinStore.frozen` value. The code comment itself acknowledges the intent is only to handle the case where the CoinStore was frozen and the FA store wasn't yet — but the same code path unconditionally runs in the reverse case too: **if the CoinStore is unfrozen (the common/default case) but the FA-side primary store was frozen independently** (e.g., an issuer holding a `FreezeCapability`/`TransferRef` used `primary_fungible_store`/`fungible_asset` freeze APIs directly on the paired FA store for compliance reasons, while the legacy CoinStore was never separately frozen), calling `migrate_to_fungible_store` will **unfreeze** the FA store, because `frozen (false) != is_frozen(store) (true)`.

Because `migrate_to_fungible_store` is a self-callable entry function requiring no special privilege beyond the account's own signer, any account whose FA-side primary store has been frozen by an issuer/compliance authority but which still retains a non-empty, non-frozen `CoinStore<CoinType>` can call this function themselves to flip their own store back to unfrozen, bypassing the freeze authority's decision — a broken custody invariant (freeze control leaking to the unprivileged account owner).

### Impact Explanation
This breaks the "freeze control must not leak to unprivileged callers" custody pivot: an issuer's `FreezeRef`/`TransferRef`-based freeze on a Fungible Asset primary store is meant to be irreversible by the store owner. If this migration path can silently clear that state, a frozen account can regain the ability to transfer/withdraw the underlying fungible asset, defeating compliance freezes (e.g. sanctions, exploit-recovery freezes, stablecoin issuer controls) purely by self-triggering a coin migration. This is a genuine authority-control corruption (frozen: bool field) directly gating custody/transferability of the asset.

### Likelihood Explanation
This requires a specific but plausible precondition: the account must (a) still hold a legacy, un-migrated `CoinStore<CoinType>` with `frozen == false`, and (b) already have a Primary Fungible Store for the paired metadata that was independently frozen via the FA-side freeze mechanism. This is realistic for any `CoinType` that has been "paired" with an FA (all coins on Aptos eventually get a paired FA via `ensure_paired_metadata`) where an issuer freezes accounts at the FA layer without also freezing/clearing the legacy CoinStore. I was not able to fully verify from the indexed code how commonly issuers freeze via the FA-side vs. legacy `CoinStore`-side freeze functions (I could not locate/exhaustively review a `coin::freeze_coin_store`-equivalent counterpart within the given context), so likelihood should be validated against actual issuer freeze tooling before treating this as confirmed-exploitable in production.

### Recommendation
Do not force-reconcile the FA frozen flag downward (unfreeze) during migration. Only propagate the frozen state from `CoinStore` to the FA store in the "freeze" direction (i.e., if `CoinStore.frozen == true`, freeze the FA store), and never clear an existing FA-side freeze based on the CoinStore's value:
```move
if (frozen && !fungible_asset::is_frozen(store)) {
    fungible_asset::set_frozen_flag_internal(store, true);
}
```
This preserves any independently-applied FA-side freeze while still correctly propagating a legacy CoinStore freeze forward.

### Proof of Concept
1. Issuer holds `FreezeCapability<CoinType>`/equivalent FA `TransferRef` and directly freezes victim's primary fungible store for the paired metadata of `CoinType` (FA-side freeze), while victim's legacy `CoinStore<CoinType>` remains unfrozen with `coin.value > 0`.
2. Victim (or anyone, via `migrate_coin_store_to_fungible_store`) calls `coin::migrate_to_fungible_store<CoinType>(victim)`.
3. Inside `maybe_convert_to_fungible_store`, `frozen` (from `CoinStore`) is `false`, `fungible_asset::is_frozen(store)` is `true` (from the issuer's freeze) — the condition `frozen != is_frozen(store)` is true, so `set_frozen_flag_internal(store, false)` executes, unfreezing the store.
4. Victim's primary fungible store is now unfrozen and transferable, despite the issuer's freeze never having been lifted. [4](#0-3) 

**Note on confidence**: This finding is based on static review of `coin.move`; I could not exhaustively trace every possible caller of `fungible_asset::set_frozen_flag_internal` and every issuer-facing freeze API in this pass, so I recommend a Devin session cross-check all freeze/unfreeze entry points that operate on primary fungible stores paired with legacy coins to confirm the precondition is reachable in practice before treating this as a fully confirmed, exploitable bug.

    fun maybe_convert_to_fungible_store<CoinType>(
        account: address
    ) acquires CoinStore, CoinConversionMap, CoinInfo {
        if (exists<CoinStore<CoinType>>(account)) {
            let CoinStore<CoinType> { coin, frozen, deposit_events, withdraw_events } =
                move_from<CoinStore<CoinType>>(account);
            if (is_coin_initialized<CoinType>() && coin.value > 0) {
                let metadata = ensure_paired_metadata<CoinType>();
                let store =
                    primary_fungible_store::ensure_primary_store_exists(
                        account, metadata
                    );

                event::emit(
                    CoinStoreDeletion {
                        coin_type: type_info::type_name<CoinType>(),
                        event_handle_creation_address: guid::creator_address(
                            event::guid(&deposit_events)
                        ),
                        deleted_deposit_event_handle_creation_number: guid::creation_num(
                            event::guid(&deposit_events)
                        ),
                        deleted_withdraw_event_handle_creation_number: guid::creation_num(
                            event::guid(&withdraw_events)
                        )
                    }
                );

                if (coin.value == 0) {
                    destroy_zero(coin);
                } else {
                    fungible_asset::unchecked_deposit_with_no_events(
                        store.object_address(),
                        coin_to_fungible_asset(coin)
                    );
                };

                // Note:
                // It is possible the primary fungible store may already exist before this function call.

                    fungible_asset::set_frozen_flag_internal(store, frozen);
                }
            } else {
                destroy_zero(coin);
            };
            event::destroy_handle(deposit_events);
            event::destroy_handle(withdraw_events);
        };
    }
