### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` fields are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values, which are read from unauthenticated HTTP headers, are never included in the signed payload. These header-derived values are nonetheless handed directly to the app's handler as trusted tenant-identifying data, breaking the intended binding `shop authenticated == shop attributed to the webhook payload`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, and its `to_signable_string` method returns only the raw HTTP body: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body only) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` uses this same validation, then immediately forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` header values into `WebhookMetadata`, which is passed to the app's handler as trusted identity data: [4](#0-3) 

The gem's own documentation instructs integrators to use `data.shop` directly as the tenant key (e.g. `shop_domain: data.shop`), confirming this is the intended, documented usage pattern rather than a misuse of the library: [5](#0-4) 

Critically, Shopify apps use a single `client_secret` (`api_secret_key`) shared across **every shop** that installs the app — it is not shop-specific. Because the HMAC only signs the raw body, and the same secret authenticates webhooks for all shops of the app, an attacker who controls one shop (e.g., their own free/dev store) installing the target app receives genuinely-signed webhook deliveries (valid body + HMAC) for events on their own shop. They can replay that exact raw body and HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` will hand the handler `data.shop == "victim-shop.myshopify.com"` with attacker-chosen body content signed under the attacker's own legitimate event.

### Impact Explanation
This breaks the tenant-isolation guarantee that a webhook's `shop` value can be trusted once HMAC validation passes. Any app built to this gem's documented pattern (keying per-tenant records off `data.shop`) can be induced to ingest attacker-crafted data (including replayed real order/customer/product payloads) attributed to a shop the attacker does not control — a cross-tenant data injection primitive, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker install the target app on a shop they control (or otherwise trigger any real webhook delivery for their own shop) and can send arbitrary HTTP requests to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the victim's shop is required, making this practical for any unprivileged internet user with a Shopify Partner account.

### Recommendation
Include `shop`, `topic`, and any other identity-bearing fields in the HMAC-signed material (or independently verify `shop` against the session/shop that Shopify's registration API originally reported for that specific `webhook_id`) before trusting them in `WebhookMetadata`. At minimum, document prominently that `data.shop`/`data.topic`/`data.webhook_id` are unauthenticated and must be independently verified (e.g., against a known list of installed shops) before being used for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`, from Shopify to the app's webhook endpoint. Shopify signs it with the app's single shared `api_secret_key`:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid-hmac-of-body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   X-Shopify-Webhook-Id: <id>
   Body: {"id": 1, "note": "hello"}
   ```
2. Attacker captures the raw body and its valid `X-Shopify-Hmac-Sha256` value.
3. Attacker replays the identical body/HMAC pair to the same endpoint but rewrites the domain header:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — validation succeeds because the body/HMAC pair is unmodified.
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to process attacker-controlled data as if it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
