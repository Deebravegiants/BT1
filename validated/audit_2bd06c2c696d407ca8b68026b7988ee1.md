## Analysis Result [1](#0-0) 

### Title
`CallDispatcher.dispatch` is a permissionless call-forwarder with no caller restriction, letting anyone drain tokens/native currency it holds mid-flow for `IntentGatewayV2` orders - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch(bytes)` executes an arbitrary `Call[]` (arbitrary `to`, `value`, `data`) with **no access control whatsoever** — any address can call it directly. `IntentGatewayV2.placeOrder` uses this exact shared, permissionless contract as a temporary holding address for user assets during the `predispatch` flow: it transfers the user's assets to `dispatcher`, invokes a user-supplied arbitrary call via `dispatcher.dispatch(...)`, and only afterward sweeps whatever balance is currently sitting at `dispatcher` back into escrow using `balanceOf(dispatcher)` rather than a tracked, per-order amount.

### Finding Description
In `placeOrder`, when an order uses `predispatch`:
1. `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)` moves the user's assets to the shared `dispatcher` address. [2](#0-1) 
2. `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` executes attacker/user-controlled calldata from the dispatcher's context. [3](#0-2) 
3. The gateway then computes a sweep based on the **current** `balanceOf(dispatcher)` (or `address(dispatcher).balance` for native), not the amount specifically attributable to this order, and calls `dispatch()` again to pull that balance into the gateway. [4](#0-3) 

Because `CallDispatcher.dispatch` has no `onlyOwner`/`onlyGateway`/caller check, it is a shared, globally-reachable holding-and-forwarding contract, exactly like `ThreeDNSReqControl` in the referenced report, which relied on a WETH balance sitting in a shared contract between two legitimate steps. Any residual balance left at `dispatcher` — e.g., token/ETH amounts not fully consumed by a predispatch swap, output tokens of a predispatch call that aren't part of `order.inputs`, or balance sent there for any other reason (including by other apps configured with the same `_params.dispatcher` address) — can be swept out by **any unprivileged external account** simply by calling `CallDispatcher.dispatch()` directly with a `Call` that transfers the balance to themselves. There is no ownership/escrow tracking per depositor inside `CallDispatcher`; balance-based accounting (`balanceOf(dispatcher)`) is the sole source of truth, identical in root cause to the report's `makeCommitmentV2`/WETH pattern where balance sitting in a shared contract, reachable by an unrelated permissionless call, is not bound to the depositor.

### Impact Explanation
Any assets left in the shared `CallDispatcher` between the deposit step and the gateway's sweep step (or dust/output amounts a predispatch call doesn't fully account for in `order.inputs`) are unprotected and can be permanently stolen by any unprivileged caller directly invoking `dispatch()`. This is concrete theft of funds reachable from a single external transaction targeting a shared, permissionless intermediary contract used by `IntentGatewayV2`'s escrow flow.

### Likelihood Explanation
`dispatch()` is public with zero access control, so exploitation requires only knowledge of the `CallDispatcher` address (which is public via `IntentGatewayV2.params()`) and observing a non-zero balance on it (via a public RPC call), then submitting one transaction. This is trivially automatable and requires no privileged role, matching the "unprivileged intent solver/order submitter" reachable-path criteria.

### Recommendation
Restrict `CallDispatcher.dispatch` to be callable only by the contract(s) that are supposed to own the funds transiting through it (e.g., an `onlyAuthorized`/`onlyGateway` modifier, or deploy a dedicated, per-order/per-caller instance instead of a shared singleton). Alternatively, redesign `IntentGatewayV2.placeOrder`'s predispatch accounting so it never depends on `balanceOf(dispatcher)` snapshots that can include funds unrelated to the current order, and ensure the entire predispatch-deposit-sweep sequence cannot leave exploitable residual balance in a globally reachable contract.

### Proof of Concept
1. Governance/deployer configures `IntentGatewayV2._params.dispatcher` to a `CallDispatcher` instance shared across orders (and potentially other apps). [5](#0-4) 
2. A user places an order with `predispatch.call` that swaps input token A for token B via the dispatcher, but token B is not one of `order.inputs` (or leftover token A dust isn't fully swept because it's below `requiredAmount` handling); this residual balance remains on the `CallDispatcher` contract after the transaction completes.
3. Attacker observes the non-zero balance on `CallDispatcher` (any RPC `balanceOf`/`eth_getBalance` call) and calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value:0, data: transfer(attacker, balance)})]))` directly, with no relation to `IntentGatewayV2` at all.
4. Because `dispatch()` has no caller restriction, the call succeeds and the attacker walks away with the residual funds that were transiting through the shared dispatcher for the legitimate user's order.

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
