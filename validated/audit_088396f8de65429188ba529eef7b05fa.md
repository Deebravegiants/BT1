This confirms the core issue. The docs explicitly document `data.shop` as "The shop domain of the webhook" — an authenticated identity value that a handler is expected to trust for tenant-scoping decisions (e.g. `perform_later(shop_domain: data.shop, ...)` in the doc's own example). But the `shop` value is read purely from the `x-shopify-shop-domain` header, and the HMAC (`Request#hmac`/`to_signable_string`) only ever signs `@raw_body`.### Title
`ShopifyAPI::Webhooks::Registry.process` treats the unauthenticated `shop-domain` header as verified tenant identity — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by checking `Utils::HmacValidator.validate(request)`, but the HMAC only covers the raw request body. The `shop` (and `topic`/`webhook_id`) values that are extracted from HTTP headers and handed to the app's handler as trusted, per-tenant identity are never part of the signed material, so a valid HMAC does not bind the request to the shop domain the app will act on.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` reads the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header, and `#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are pulled straight from separate, unsigned HTTP headers with no cryptographic relationship to the HMAC: [2](#0-1) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and only compares that against the received HMAC — i.e., it verifies "some request with this exact body was signed by our secret," not "this body came attached to this shop": [3](#0-2) 

`Registry.process` accepts the request once `HmacValidator.validate` passes, and then forwards the **header-derived, unauthenticated** `shop` value into `WebhookMetadata`, which is passed to the app's handler as if it were an authenticated identity: [4](#0-3) 

`WebhookMetadata.shop` is a `T::Struct` field with no further validation: [5](#0-4) 

The gem's own documentation instructs app authors to trust `data.shop` as "The shop domain of the webhook" and to use it directly for tenant-scoped work (e.g. `perform_later(shop_domain: data.shop, webhook: data.body)`), reinforcing that this field is meant to be treated as an authenticated tenant identifier delivered by this gem: [6](#0-5) 

The binding that should hold but doesn't:
`HMAC-verified(shop, topic, webhook_id, body)` ⇏ actually only `HMAC-verified(body)`, while the app is told `WebhookMetadata.shop == the shop the signed body pertains to`.

This is a direct structural analog of the reported bug class: an identity field (`sender`/`shop`) that is *acted upon* by downstream trust decisions is not the field that is actually *covered* by the cryptographic check (`sender == address(this)` vs. HMAC over body only). Just as `notionalCallback`'s `sender` parameter could be freely chosen by the caller while the authorization check verified something else, here the `shop` header can be freely chosen by whoever sends the HTTP request, while the authorization check (the HMAC) verifies only the body bytes.

### Impact Explanation
Any actor capable of obtaining one genuine `(raw_body, hmac)` pair signed by the app's own secret — which happens routinely for shops that legitimately use the app, including an attacker's own test/trial shop — can resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value (e.g., a victim shop's domain) and/or `x-shopify-topic`/`x-shopify-webhook-id` headers. `Registry.process` will still consider the HMAC valid (it only checks the body) and will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. If the host application uses `data.shop` (as this gem's own docs recommend) to route the payload to per-tenant processing — e.g., writing order/customer data into the victim's tenant record, or triggering shop-scoped side effects — this results in cross-tenant data injection/confusion driven entirely by an identity value this gem asserts is trustworthy after HMAC validation. This matches the Critical "cross-tenant access" impact category, since the mechanism responsible for authenticating the tenant boundary provides no actual guarantee about that boundary.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs at least one legitimately-signed `(body, hmac)` pair from the target app's webhook secret, which is realistically obtainable by any unprivileged party who installs the app on their own store (a normal, self-service action for public apps) and then replays their own webhook body/HMAC with a forged shop header. No access to `api_secret_key`, access tokens, or the victim's credentials is required — only the ability to receive one webhook for one's own shop and resend it with modified headers to the app's public webhook endpoint.

### Recommendation
Bind the identity fields into the signed material instead of trusting side-channel headers:
- Extend `to_signable_string` (or a new signing scheme) to include `shop`, `topic`, and `webhook_id`/timestamp values, so the HMAC covers the full identity tuple, not just the body.
- Alternatively/additionally, cross-check `shop` against the session/shop the app expects to be receiving a webhook for before acting on `WebhookMetadata.shop`, and document this requirement explicitly for consumers of `WebhookHandler`.
- At minimum, update `docs/usage/webhooks.md` to warn that `data.shop`/`data.topic`/`data.webhook_id` are **not** covered by the HMAC and must not be treated as authenticated tenant identifiers without additional verification (e.g., correlating against a known/expected shop for the installation).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and legitimately receives a webhook, capturing the exact `raw_body` and the corresponding `x-shopify-hmac-sha256` value computed by Shopify with the app's real secret.
2. Attacker sends a new HTTP request to the app's webhook endpoint reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - (optionally) `x-shopify-topic`/`x-shopify-webhook-id` to any value they want the handler to process under.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only checks presence, not correlation), and `Registry.process` calls `Utils::HmacValidator.validate(request)`:
   ```ruby
   # lib/shopify_api/utils/hmac_validator.rb
   computed_signature = compute_signature(verifiable_query.to_signable_string, secret) # = HMAC(raw_body)
   OpenSSL.secure_compare(computed_signature, received_signature) # matches, since raw_body unchanged
   ```
4. Validation succeeds because it never inspected `shop`/`topic`/`webhook_id`. `Registry.process` builds:
   ```ruby
   WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)
   ```
   with `shop == "victim-shop.myshopify.com"` even though the payload actually originated from, and was signed for, the attacker's own shop.
5. The host application's handler, following this gem's documented pattern (`perform_later(shop_domain: data.shop, webhook: data.body)`), processes the attacker's data under the victim's tenant context.
