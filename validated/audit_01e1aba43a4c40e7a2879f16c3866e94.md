### Title
Stale delegate grant silently re-arms when a position NFT returns to its original owner, letting a former manager drain the account - (File: contracts/controller/src/storage/account.rs)

### Summary
Delegate authority on a lending account is stored as a `DelegateGrant { granted_by, delegates }` keyed only by `account_id`, and `get_delegates` filters solely on `granted_by == current NFT owner`. An NFT transfer disables the grant without deleting it, and the same grant becomes live again if the NFT ever returns to the address that created it — with no nonce, epoch, or re-consent. A previously removed-from-power delegate (who must still hold an active global position-manager registration) can then call `borrow`, `withdraw`, and all strategy entrypoints on the reacquired account, routing proceeds to itself via the `to` parameter.

### Finding Description
`DelegateGrant` is stamped with the granter's address rather than a transfer epoch (`common/src/types/controller.rs` `DelegateGrant`). `get_delegates` returns the stored list whenever `grant.granted_by == owner`, so validity is determined purely by the current NFT holder's identity (`storage/account.rs:176-181`). The NFT transfer itself performs no controller-side cleanup — the position NFT has no hook into the controller, and `transfer`/`transfer_from` only move the token.

`is_owner_or_delegate` then admits any caller on that re-armed list that is still an active `PositionManagerConfig` (`account.rs:114-127`), which gates `borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`, and `SeizeMode::Credit` receivers (`liquidation/mod.rs:180`). Delegates may pick any `to`/`recipient` for borrowed or withdrawn funds (`debt.rs:45`), and the threat model itself notes the gates "do not constrain them to acting in the owner's economic interest."

Revocation hygiene exists only on the write paths: `remove_delegate` by an intervening owner deletes the stale entry (`storage/account.rs:236-239`), and a new owner's `add_delegate` overwrites it. But if the intermediate holder performs neither write — which is typical, since most holders never touch delegates — the dormant grant survives intact.

### Impact Explanation
Theft of user funds. Once the NFT returns to the original granter, the stale delegate can `borrow` against the account's collateral with `to = attacker`, and `withdraw` collateral to itself, up to the solvency gates. The victim regains an account believing only they control it, while a counterparty they may have sold the position away from months earlier — precisely because they wanted the delegate gone — silently regains full spending authority.

### Likelihood Explanation
Requires: (1) owner A once granted delegate M; (2) the NFT leaves A and returns without any intermediate owner calling `add_delegate`/`remove_delegate`; (3) M is still an active position manager. Position NFTs are transferable collateral (sold positions, OTC deals, wallet rotation between a user's own addresses are all plausible), and an intermediate holder has no reason to write to a delegate list that reads empty for them. Medium likelihood, high impact per occurrence.

### Recommendation
Stamp the grant with an ownership epoch instead of an address: e.g., store a monotonically increasing `owner_epoch` per `account_id` that the controller bumps on every ownership change it observes (or lazily: store `granted_by` plus a transfer counter), and compare against it in `get_delegates`. Alternatively, have the controller subscribe to NFT transfers — or make `renew_account`/`owner_of` resolution overwrite stale grants — so a grant can never outlive a change of holder.

### Proof of Concept
1. Alice owns `account_id` X with USDC collateral; governance marks `manager` active; Alice calls `add_delegate(X, manager)`.
2. Alice transfers NFT X to Bob. Under Bob the grant reads empty; Bob does not call `add_delegate` or `remove_delegate`.
3. Bob transfers NFT X back to Alice (resale, refund, or Alice rotating wallets).
4. `get_delegates(X, alice)` returns `[manager]` again — `grant.granted_by == owner` — with no fresh consent from Alice.
5. `manager` calls `borrow(X, [(USDC, amt)], to = manager)` and `withdraw(X, [...], to = manager)`; `is_owner_or_delegate` passes because `manager` is still an active position manager and the stale list contains it.

This is documented as current behavior ("The stale grant stays in storage and re-arms if the token returns to `granted_by`" — `contracts/position-nft/README.md`), but it converts a one-time delegation into a permanent latent credential over the account whenever the NFT round-trips, which is the on-chain analog of session-hijack via a resurrected auth token.
