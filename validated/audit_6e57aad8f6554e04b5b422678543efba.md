This confirms the finding: the webhook HMAC (`Digest.hexencode(Base64.decode64(...))` in [1](#0-0) ) is validated only over `to_signable_string`, which returns `@raw_body` alone [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values used downstream come straight from unauthenticated HTTP headers [3](#0-2) , and `Registry.process` passes `request.shop` directly into the handler after only checking the body HMAC [4](#0-3) .

### Title
Webhook `shop-domain` (and topic/webhook-id) headers are not covered by the HMAC, allowing shop-identity spoofing on replayed webhook bodies - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates its HMAC exclusively over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` hands to the application's webhook handler are read directly from HTTP headers that participate in no cryptographic binding at all.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` accessor: [5](#0-4) 

`Registry.process` accepts a request the moment this body-only HMAC check passes, then builds `WebhookMetadata` straight from `request.shop`, `request.topic`, and `request.webhook_id`, which are parsed from the `x-shopify-shop-domain` / `shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers respectively — none of which are part of the signed bytes: [4](#0-3) [3](#0-2) 

The binding the code is supposed to establish is:
`shop_identity_used_by_handler == shop_that_the_secret-holder(Shopify)_attested_to`

But what is actually verified is only:
`HMAC(secret, raw_body) == received_hmac`

These are not equivalent because `raw_body` never encodes which shop the payload came from — the shop attribution lives entirely in an unsigned header. Since the same `api_secret_key` is shared across every shop that installs a given app, any party who can obtain one legitimately-signed `(body, hmac)` pair for the app (e.g., by installing the app on their own store and receiving a real webhook) can replay that exact body/hmac pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will invoke the registered handler with `WebhookMetadata#shop` set to the attacker-chosen shop, and `topic`/`webhook_id` similarly forgeable.

### Impact Explanation
Any application logic in a webhook handler that trusts `WebhookMetadata#shop` to select or scope the record being read/written (which is the documented and expected usage pattern — handlers are meant to use `data.shop` to route to the correct tenant) can be made to apply attacker-controlled webhook data under a victim shop's identity, or vice versa to have an attacker's data attributed to itself under a different shop and topic in the app's cross-tenant store. This crosses the tenant isolation boundary the HMAC is presumed to enforce, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires: (1) being able to install the target app on any shop (including the attacker's own, or a trial/free-plan shop) to legitimately receive a real signed webhook body/hmac pair for a chosen topic, and (2) being able to POST that captured body and its signature to the app's public webhook endpoint with a modified `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header. No possession of `api_secret_key`, no access token, and no TLS interception is required — this is reachable by any unprivileged internet user who can reach the app's webhook endpoint, which is by design a public, unauthenticated endpoint.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) inside the HMAC-signed material, or otherwise cryptographically bind them to the verified payload before they are trusted (e.g., compare `request.shop` against a shop already resolved from a previously-established, HMAC/OAuth-verified session for that install, or require the app to independently confirm the header's shop is one it has an active installation/session for, rather than trusting the header value as the sole shop identifier passed to handlers). At minimum, document clearly in `docs/usage/webhooks.md` that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated header values and must not be trusted as the sole tenant/topic identifier without additional server-side verification against a known/active installation record.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled shop `attacker.myshopify.com` (or otherwise obtain any real webhook delivery for the app).
2. Capture the raw request body `B` and the corresponding `x-shopify-hmac-sha256` header value `H` from a real webhook delivery for topic `T` (e.g., `orders/create`).
3. Replay the exact same request to the app's public webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com` (and/or an arbitrary `x-shopify-topic`/`x-shopify-webhook-id`).
4. `Utils::HmacValidator.validate` in [5](#0-4)  succeeds because it only re-hashes `B`.
5. `Registry.process` in [4](#0-3)  invokes the app's handler with `WebhookMetadata#shop == "victim.myshopify.com"`, even though the payload `B` was never issued by Shopify for that shop.
