Webhook `shop-domain` and `topic` headers are trusted for tenant/event routing without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then forwards the `shop`, `topic`, `webhook_id`, and `api_version` values — all read from unauthenticated HTTP headers — to the app's handler as trusted tenant/event identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only checks that `verifiable_query.hmac` matches HMAC-SHA256 of `to_signable_string` (i.e. the raw body) using `Context.api_secret_key`: [4](#0-3) 

`Registry.process` uses this body-only check as the sole authentication gate, then passes the header-derived `shop`/`topic`/`webhook_id`/`api_version` straight into `WebhookMetadata` for the app's handler: [5](#0-4) 

The identity binding that breaks: `hmac_valid(raw_body) == true` is treated as equivalent to `shop_header == actual_originating_shop`, but the HMAC only proves knowledge of `(raw_body, api_secret_key)` — it says nothing about which headers accompanied that body. A merchant who has legitimately installed the app on their own store receives real webhook deliveries with valid HMACs computed over their own store's JSON body. Because headers are excluded from the signature, that same attacker can resend the identical `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` and/or `x-shopify-topic` header. `HmacValidator.validate` still returns `true` (the body/hmac pair is unchanged and correctly signed with the real `api_secret_key`), so `Registry.process` accepts the request and dispatches it to the handler tagged with the attacker-chosen `shop` and/or `topic` — an event that never actually originated from that shop or under that topic.

### Impact Explanation
This breaks the tenant/event identity binding at the point the library hands data to the app: `handler.handle` receives `WebhookMetadata` whose `shop` and `topic` fields are attacker-controlled despite the request having passed HMAC "verification." Any host application that relies on this gem's documented `Registry.process`/`WebhookMetadata` contract to attribute incoming webhook data to the correct merchant (a very common and expected usage pattern, since the gem explicitly exposes `shop` on the metadata as the identity for the event) can be made to process or persist data under the wrong shop, or process a benign topic's body as if it were a different (potentially higher-trust) topic. This is a cross-tenant identity confusion issue reachable by any unprivileged internet user who can install the app on a store they control (no `api_secret_key`, access token, or privileged account needed).

### Likelihood Explanation
Reasonably likely to be reachable: creating a store and installing a public/free app is normal unprivileged access, and Shopify webhook endpoints are, by design, unauthenticated public HTTP endpoints protected only by the HMAC-over-body scheme this gem implements. Capturing a legitimate `(raw_body, x-shopify-hmac-sha256)` pair from one's own store's webhook deliveries requires no special privilege, and replaying it with edited headers to the same public endpoint is trivial for anyone who can send HTTP requests.

### Recommendation
Do not treat header-derived `shop`, `topic`, `webhook_id`, or `api_version` as authenticated merely because the body HMAC validated. At minimum, document/require that consuming applications independently verify `request.shop` against the shop associated with the webhook subscription/session before acting on the payload, or extend `Request#to_signable_string`/`HmacValidator` (or `Registry.process`) to bind the `shop-domain` and `topic` headers into the value that is authenticated, so a mismatch invalidates the request.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, e.g. for `orders/create`:
   - Body: `{"id": 123, ...}`
   - Headers include a correctly computed `x-shopify-hmac-sha256` for that body, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but replaces:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes HMAC over the unchanged `raw_body` with the app's real `api_secret_key` and it matches, so validation passes: [6](#0-5) 
4. `Registry.process` dispatches to the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {...attacker's own order data...}, ...)`, causing the host app to act as though `victim-shop.myshopify.com` produced this event/body.
