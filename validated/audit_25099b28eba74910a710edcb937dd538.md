### Title
Reentrancy in `IntentGatewayV2.withdraw()` (Tron variant) transfers escrowed tokens before updating internal accounting - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron build of `IntentGatewayV2` still contains the exact bug class reported for `withdrawLend`: the escrow-release function performs external token/native transfers **before** decrementing the internal escrow accounting, rather than following checks-effects-interactions. The main EVM `IntentsBase._withdraw()` was already hardened against this class of bug (decrement happens before transfer), but the Tron contract regressed to the unsafe ordering.

### Finding Description
`withdraw()` in the Tron contract iterates the withdrawal request's token list, and for each token performs the transfer **first**, only decrementing `_orders[commitment][token]` afterward: [1](#0-0) 

The same unsafe ordering repeats for the transaction-fee payout inside the same function: [2](#0-1) 

Compare this with the already-fixed CEI pattern in the main EVM `IntentsBase._withdraw()`, where the escrow balance is decremented **before** any external transfer occurs: [3](#0-2) 

The `tokens` array processed by `withdraw()` is attacker-controlled: it comes directly from `order.inputs`/`order.output.assets` that the user supplies at `placeOrder()` time, and an order's beneficiary/inputs can point at an arbitrary ERC20/TRC20 contract with transfer-hook behavior (Tron's TRC20/TRC10 tokens and any adversarial token contract can execute arbitrary code during a `token.call(...transfer...)`). Because the balance decrement in `_orders[body.commitment][token] -= amount` only happens after the external call returns, any reentrant call that can reach `withdraw()` again for the same commitment (via `onAccept`/`onGetResponse`) before the decrement executes would see a stale, non-zero `_orders[commitment][token]` value and could siphon the same escrow twice.

The Foundry test suite explicitly documents that this exact reentrancy pattern was previously exploitable in `IntrinsicIntents._fillSameChain` and was fixed via CEI (`_filled[commitment]` set before any transfer, escrow decremented before transfer): [4](#0-3) 

That fix was applied to `IntentsBase.sol` (the primary EVM implementation) but not mirrored into the parallel Tron implementation, which still uses `token.call(...)` for transfers before updating `_orders`.

### Impact Explanation
If a reentrant path into `withdraw()` (or a duplicate/malicious token entry within a single `WithdrawalRequest.tokens` array) is reachable, an attacker can drain escrowed input tokens or transaction fees beyond what was actually deposited, directly stealing funds from the gateway/other users — a concrete theft-of-funds impact matching the report's "High" severity classification.

### Likelihood Explanation
Exploitability is gated by `onAccept`/`onGetResponse` being `onlyHost`-restricted, so the primary entry point cannot be called directly by an attacker. However, since `body.tokens` is derived from user-supplied `order.inputs` and can reference an attacker-deployed token contract, and since the internal accounting update is deferred until after the external call completes, any secondary reentrancy surface into `withdraw()`/`onAccept` (e.g., via the host's request-delivery bookkeeping not being finalized before invoking the app callback) would be immediately exploitable. This is a strict regression relative to the CEI-hardened `IntentsBase._withdraw()`, so it should be treated as a real, reachable defect requiring the same fix rather than a purely theoretical one.

### Recommendation
Apply the same checks-effects-interactions fix used in `IntentsBase._withdraw()` to the Tron `IntentGatewayV2.withdraw()`: decrement `_orders[body.commitment][token]` (and delete the `TRANSACTION_FEES` entry) **before** performing the native/TRC20 transfer, mirroring: [5](#0-4) 

### Proof of Concept
1. User places an order via `placeOrder()` with `order.inputs` referencing a malicious TRC20 token whose `transfer()` hook re-enters the gateway.
2. Order is filled/cancelled cross-chain; Hyperbridge relayer delivers the corresponding `RedeemEscrow`/`RefundEscrow` post request, triggering `onAccept()` → `withdraw()`.
3. Inside `withdraw()`'s loop, the malicious token's `transfer()` executes before `_orders[body.commitment][token] -= amount` runs.
4. If any path (duplicate delivery of the same message before the host records it as handled, or another reentrant surface) allows `withdraw()`/`onAccept()` to run again for the same commitment while `_orders[commitment][token]` is still non-zero, the `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` check passes again and a second transfer of `amount` is issued, double-paying the escrow.

**Note:** I could not fully verify from the indexed code whether `EvmHost`'s message-delivery bookkeeping marks a request as "handled" strictly before or after invoking `IApp.onAccept`, which determines whether the deeper reentrant-redelivery vector is actually reachable end-to-end. This would require reviewing the full `handleIncoming`/`handlePostRequests` flow in `EvmHost.sol` beyond what the index surfaced. Confirming that ordering is necessary to fully validate exploitability of the redelivery path described above.
