### Title
Reward tokens accrued during zero-stake periods become permanently unclaimable in `pallet-asset-rewards` - (`File: substrate/frame/asset-rewards/src/lib.rs`)

### Summary
`pallet-asset-rewards` implements the Synthetix `StakingRewards.sol`-style reward accounting algorithm — the same design lineage as the vulnerable `Staking.sol` in the Wenwin report [1](#0-0) . The pallet's `reward_per_token` function skips reward accrual entirely whenever `total_tokens_staked == 0`, but the companion `update_pool_rewards` function unconditionally advances `last_update_block` to the current block. This reproduces exactly the Wenwin bug class: reward budget intended for a "no stakers" window is silently dropped from the accounting formula, while any reward-asset tokens already sitting in (or later deposited to) the pool's pot account for that period become permanently unclaimable by any staker.

### Finding Description
The core reward math is: [2](#0-1) 

When `total_tokens_staked.is_zero()`, the function returns the stale `reward_per_token_stored` without accounting for the blocks elapsed while there were no stakers.

The pool state is then updated with: [3](#0-2) 

`update_pool_rewards` sets `last_update_block = now` and `reward_per_token_stored = reward_per_token` **unconditionally**, regardless of whether `total_tokens_staked` was zero. This means the "clock" for reward accrual always advances to the present block, so once a staker joins later, the pallet computes rewards only from that point forward — the reward-rate-implied budget for the zero-stake window is never re-attributed to anyone.

This code path is exercised on every stake/unstake/harvest operation via `update_pool_and_staker_rewards`: [4](#0-3) 

Reward tokens can enter the pool's pot account (`pool_info.account`) either through the convenience extrinsic or a direct transfer by anyone: [5](#0-4) 

The only mechanism to recover stranded balance is `cleanup_pool`, which explicitly requires the pool to have **zero current stakers**: [6](#0-5) 

This directly mirrors both flows from the Wenwin report:
- **Flow 1 analog**: a pool is created and reward tokens are deposited (e.g. via `deposit_reward_tokens`) before anyone stakes. `total_tokens_staked == 0`, so `reward_per_token` never advances and `last_update_block` catches up to "now" as soon as the first `stake()` call runs `update_pool_and_staker_rewards` — pre-existing pot balance is never reflected in `reward_per_token_stored` and is not owed to any future staker's accounting.
- **Flow 2 analog**: all stakers `unstake()` down to `total_tokens_staked == 0`. During the idle window, `reward_rate_per_block`-implied rewards (and any tokens transferred into the pot in the interim) are dropped from the formula once the pool becomes active again with a new staker, because `last_update_block` is advanced with no accrual having happened. If a new staker joins before the admin calls `cleanup_pool` (which requires *zero* stakers), the admin has no way to reclaim the stranded balance, and it remains locked in the pot account indefinitely — funds are neither distributed to stakers nor recoverable by the admin.

### Impact Explanation
Reward-asset tokens funded into a pool's pot account for the duration it has zero staked tokens become permanently stuck: they are not credited to any staker's `reward_per_token_paid`/`rewards` accounting, and `cleanup_pool` — the sole recovery path — is unusable once any staker is enrolled again. This is a direct loss of funds for the pool admin/reward-asset depositor, analogous to Medium-severity in the original Wenwin C4 report.

### Likelihood Explanation
This is realistic and does not require a privileged role to trigger: any unprivileged staker can cause `total_tokens_staked` to hit zero simply by unstaking all their tokens (`unstake`), and any account can call `deposit_reward_tokens` or directly transfer reward assets to the pot account at any time, including during a zero-stake window. Reward-rate-based pools with intermittent participation (e.g., LP incentive pools where liquidity is temporarily fully withdrawn) will realistically encounter this condition without any adversarial intent, and once a new staker joins, the stranded funds are locked with no recovery path.

### Recommendation
When `total_tokens_staked.is_zero()` in `reward_per_token`/`update_pool_rewards`, either:
1. Do not advance `last_update_block` past the point where `total_tokens_staked` last became zero, so that once staking resumes the unaccrued reward-rate budget for that idle window is retroactively distributable (careful design needed to avoid unbounded backdated payouts), or
2. Route/hold reward-rate emissions destined for zero-stake windows separately (e.g., accumulate into a claimable-by-admin surplus) instead of implicitly dropping them, and allow the admin to reclaim such surplus regardless of current staker count (not gated behind `PoolStakers` being empty).

### Proof of Concept
1. Admin calls `create_pool` with `reward_rate_per_block = R` and no stakers yet (`total_tokens_staked = 0`).
2. Someone (anyone) calls `deposit_reward_tokens(pool_id, amount)` to fund the pot, or the pot is pre-funded directly via transfer — see [7](#0-6) .
3. `N` blocks pass with `total_tokens_staked` still `0`. `reward_per_token` returns the stale stored value every time it's evaluated — see [8](#0-7) .
4. A user calls `stake(pool_id, amount)`. This invokes `update_pool_and_staker_rewards` → `update_pool_rewards`, which sets `last_update_block = now` (i.e., skips crediting the `N` idle blocks) — see [9](#0-8) .
5. The staker only starts earning from block `now` onward; the reward-asset balance corresponding to `R * N` (or any pre-deposited amount) sitting in `pool_info.account` is never attributed to `reward_per_token_stored`.
6. Because there is now an active staker, `cleanup_pool` cannot be called (`ensure!(stakers.is_none())` fails) — see [10](#0-9) . The stranded reward tokens remain locked in the pot account with no path to distribution or admin recovery for the lifetime of the pool.

		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
