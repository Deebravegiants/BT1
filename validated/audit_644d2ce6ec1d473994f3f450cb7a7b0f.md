Confirmed: `stretchPassphrase` in `libraries/secure-container/src/crypto.js` passes `n`, `r`, `p` straight through from the caller-supplied `scryptParams` into the underlying `scrypt` call with no floor/ceiling validation, and `boxDecrypt`/`decryptBlobKey` do the same, deriving parameters entirely from the untrusted metadata block decoded from the imported `.seco` file. `decrypt` in `libraries/secure-container/src/index.js` decodes the `metadata` straight from `fileObj.metadata` (attacker-controlled bytes) and passes it unmodified into `conMetadata.decryptBlobKey`, so an attacker who crafts the `.seco` file's `scrypt` struct (`n`, `r`, `p`) fully controls the KDF cost used to derive the key that decrypts `blobKey`.

### Title
Unvalidated attacker-controlled scrypt cost parameters allow KDF downgrade in SECO backup decryption - ([File: libraries/secure-container/src/crypto.js])

### Summary
`stretchPassphrase`, `boxDecrypt`, and `metadata.decryptBlobKey` accept `n`, `r`, `p` scrypt parameters directly from the decoded, attacker-supplied metadata block of an imported `.seco` file with no minimum-strength validation. An attacker who crafts a malicious backup file with weak scrypt parameters (e.g., `n=1`) can force the victim's real passphrase to be stretched with negligible cost, drastically weakening the KDF protecting `blobKey`/`authTag` for any offline brute-force performed against captured ciphertext.

### Finding Description
The call chain `index.decrypt` → `conMetadata.decode` → `conMetadata.decryptBlobKey` → `boxDecrypt` → `stretchPassphrase` is fully traceable: [1](#0-0)  decodes the file, decodes `metadata` from raw bytes, and calls `decryptBlobKey(metadata, passphrase)` without any check on `metadata.scrypt`. `decryptBlobKey` forwards `metadata.scrypt` (attacker-controlled `salt`, `n`, `r`, `p` decoded via the `vsf`/`UInt32BE` struct) straight to `boxDecrypt`: [2](#0-1) . `boxDecrypt` merges these values with `createScryptParams()` defaults (which only fills missing fields, not weak ones) and calls `stretchPassphrase`: [3](#0-2) . `stretchPassphrase` passes `n`, `r`, `p` unchecked into the underlying `scrypt` call: [4](#0-3) . The metadata struct itself declares `n`, `r`, `p` as plain `UInt32BE` fields with no bounds: [5](#0-4) . Nowhere in this path is there a floor check (e.g., minimum `N`/cost-factor) before the KDF runs.

### Impact Explanation
This matches Hydra's "secrets stay secret" invariant for KDF strength: an attacker who can get a victim to import a malicious `.seco` backup (e.g., via a shared/imported wallet backup file, QR/import payload, or file sharing) and who additionally can capture the resulting AEAD ciphertext + authTag for `blobKey` (e.g., by observing/exfiltrating the crafted file itself, since the attacker created it) is able to perform offline brute-force of the real passphrase at trivial cost, since scrypt effectively becomes single-iteration PBKDF-like work. This is a genuine KDF-downgrade weakness enabling passphrase recovery and thus wallet secret disclosure, scoped exactly to the described impact.

### Likelihood Explanation
Feasibility is high and fully reproducible: the attacker only needs to construct a `.seco` file with a valid header/checksum and arbitrary `n=1, r=1, p=1` in the scrypt block (checksum is computed over metadata+blob by the attacker themselves, so it will validate) and get the victim to import it and enter their real passphrase into `decrypt`. No privileged state, leaked keys, or social engineering beyond "user imports a file and enters their passphrase" is required — this is exactly the "malicious import payload" class of attack in scope.

### Recommendation
Enforce a minimum acceptable scrypt cost (`n`/N, `r`, `p`) in `stretchPassphrase`/`boxDecrypt`/`decryptBlobKey` before invoking the KDF, rejecting metadata whose parameters fall below a safe floor (e.g., `n >= 16_384`, `r >= 8`, `p >= 1`, and reasonable upper bounds to avoid DoS). Alternatively, do not trust cost parameters from imported files at all for security-critical decisions — always re-derive/verify using a pinned minimum policy set by the application rather than fully attacker-supplied values.

### Proof of Concept
Unit test to add to `libraries/secure-container/src/__tests__/crypto.test.js` / `metadata.test.js`:
1. Build a metadata object via `metadata.create()` then override `metadata.scrypt = { salt: randomBytes(32), n: 1, r: 1, p: 1 }`.
2. Call `metadata.encryptBlobKey(metadata, passphrase, blobKey)` to produce ciphertext under these weak parameters (simulating attacker-crafted file), then call `metadata.decryptBlobKey(metadata, passphrase)`.
3. Assert that decryption succeeds without error/rejection despite `n=1` — i.e., `decryptBlobKey` does not throw and returns the correct `blobKey`, proving no floor enforcement exists.
4. Additionally, benchmark `stretchPassphrase(passphrase, {salt, n:1, r:1, p:1})` vs default params (`n:16_384`) to show orders-of-magnitude timing difference, demonstrating a real brute-force-cost reduction.
Expected (fixed) behavior: `decryptBlobKey`/`boxDecrypt` should reject `n`/`r`/`p` below the safety floor with a thrown error rather than proceeding to decrypt.

export async function decrypt(encryptedData, passphrase) {
  const fileObj = conFile.decode(encryptedData)

  const checksum = await conFile.computeChecksum(fileObj.metadata, fileObj.blob)
  if (!fileObj.checksum.equals(checksum))
    throw new Error('seco checksum does not match; data may be corrupted')

  const metadata = conMetadata.decode(fileObj.metadata)
  const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)
  const header = conHeader.decode(fileObj.header)
  const data = await conBlob.decrypt(fileObj.blob, metadata, blobKey)

  return { data, blobKey, metadata, header }
}
