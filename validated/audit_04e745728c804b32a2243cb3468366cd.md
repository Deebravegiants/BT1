### Title
Unchecked ERC-20 `transfer` return value in `CallDispatcher`'s postdispatch sweep silently strands non-standard-ERC20 output tokens and mis-emits `DustCollected` - (File: `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/src/utils/CallDispatcher.sol`)

### Summary
`IntentsBase._execute` (used by both same-chain and cross-chain fills) sweeps residual token balances out of the shared `CallDispatcher` after an order's postdispatch calldata runs, by building a raw `IERC20.transfer` call and routing it through `CallDispatcher.dispatch`. `CallDispatcher.dispatch` only checks that the low-level `.call()` did not revert — it never inspects the ABI-decoded boolean return value of `transfer`. For any ERC-20 that follows the historical (non-reverting) pattern of returning `false` on failure instead of reverting (e.g. ZRX-style tokens), the sweep silently "succeeds" while the tokens never leave the `CallDispatcher`, and the code unconditionally emits `DustCollected(token, balance)` as if the sweep worked.

### Finding Description
`_execute` in `evm/src/apps/intentsv2/IntentsBase.sol:498-545` builds `sweepCalls` for every non-zero residual ERC-20 balance left on the dispatcher after `order.output.call` executes: [1](#0-0) 

```
} else {
    uint256 balance = IERC20(token).balanceOf(dispatcher);
    if (balance > 0) {
        sweepCalls[sweepCount] = Call({
            to: token,
            value: 0,
            data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
        });
        sweepCount++;
        emit DustCollected(token, balance);
    }
}
```

`DustCollected` is emitted *before* the sweep call is even dispatched, and the actual execution happens via `ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls))`. `CallDispatcher.dispatch` only validates that the raw call didn't revert: [2](#0-1) 

There is no `require(success && (data.length == 0 || abi.decode(data, (bool))))` pattern here (the pattern `SafeERC20` uses). If the output token contract returns `false` on a failed `transfer` (rather than reverting), `to.call(...)` returns `success = true` with `result` decoding to `false`; `CallDispatcher` treats this as a fully successful sweep. The token balance remains stuck on the `CallDispatcher` contract while the protocol's accounting (the `DustCollected` event, and the absence of any post-sweep balance re-check) assumes it was moved to the gateway.

This is exactly the bug class from the referenced report (`FootiumPrizeDistributor.claim`): a raw `transfer()` call whose boolean return value is never checked, letting a non-reverting failed transfer be treated as a success. Every other token movement in this codebase (`safeTransfer`/`safeTransferFrom` via OpenZeppelin's `SafeERC20`, used throughout `IntentGatewayV2.sol`, `ExtrinsicIntents.sol`, `IntrinsicIntents.sol`, `EvmHost.sol`) correctly reverts on a false return; this sweep path is the one place that bypasses that protection by using raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` through the unchecked-return `CallDispatcher`.

Contrast this with the sibling sweep logic in `IntentGatewayV2.placeOrder`'s predispatch flow, which snapshots `balancesBefore` and computes `received = balanceAfter - balanceBefore` to detect a no-op transfer: [3](#0-2) 

The postdispatch sweep in `_execute` has no equivalent balance-diff verification — it trusts the `transfer` call unconditionally.

### Impact Explanation
For any non-standard ERC-20 configured as an order's output asset that returns `false` instead of reverting on failed transfer (a known real-world token pattern, historically true of tokens like ZRX and still present in some deployed tokens/wrapped assets), a solver's output tokens routed through postdispatch calldata (`order.output.call`) can become permanently stuck in the shared, permissionless `CallDispatcher` contract:
- The tokens are never actually swept back to the `IntentGatewayV2`/gateway.
- `DustCollected` is emitted as if the sweep succeeded, corrupting protocol accounting/telemetry used for treasury sweeps.
- Because `CallDispatcher.dispatch` is a shared, unauthenticated entrypoint (no `msg.sender` restriction) used by multiple integrations (`IntentGatewayV2`, `HyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`), any token balance left stranded there is also at risk of being swept out by an unrelated third party via a subsequent `dispatch()` call before the protocol notices and remediates — this constitutes a permanent, unrecoverable freezing (or loss) of solver/order funds. This satisfies "permanent freezing of funds" impact criteria.

### Likelihood Explanation
Likelihood is bounded by adoption of non-conforming ERC-20 tokens as intent output assets, but the Intent Gateway is explicitly designed to support arbitrary user/solver-supplied ERC-20 tokens as `order.output.assets`, and `order.output.call` (postdispatch calldata) is a documented, supported feature for composable fills through DEXes/lending protocols — meaning any order using postdispatch calldata with a non-standard-return-value output token deterministically triggers this bug, with no special attacker positioning required beyond selecting/using such a token as an output asset.

### Recommendation
Use `SafeERC20.safeTransfer` (as done everywhere else in the codebase) instead of raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` for the sweep call built in `_execute`, or make `CallDispatcher.dispatch` validate the ABI-decoded return value for ERC-20 transfer-like calls (e.g., `require(result.length == 0 || abi.decode(result, (bool)))` in addition to `success`). Additionally, verify actual balance movement (as already done in `IntentGatewayV2.placeOrder`'s predispatch sweep) before emitting `DustCollected`, and consider restricting `CallDispatcher.dispatch` callers or ensuring no token balance can persist across separate transactions.

### Proof of Concept
1. Configure an `Order.output.assets[i].token` to be a non-standard ERC-20 that returns `false` (does not revert) on a failed `transfer`, and set `order.output.call` to some valid calldata (postdispatch) that leaves a residual balance of this token on the `CallDispatcher` (e.g., a swap that doesn't fully consume the input).
2. Solver calls `fillOrder`; `_fillCrossChain`/`_fillSameChain` executes the fill and calls `_execute(order, outputsLen)`.
3. Inside `_execute`, `order.output.call` runs via `ICallDispatcher(dispatcher).dispatch(order.output.call)`, leaving `balance > 0` of the token on `dispatcher`.
4. `_execute` builds a sweep `Call` with `abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)` and emits `DustCollected(token, balance)`.
5. `ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls))` executes the sweep call; the token's `transfer` returns `false` without reverting (simulate by deploying a mock ERC20 whose `transfer` returns `false` when, e.g., an internal condition is unmet, without a `revert`).
6. `CallDispatcher.dispatch` sees `success = true` (the call itself did not revert) and does not check the decoded `false` return value, so the loop completes without error.
7. Verify: `IERC20(token).balanceOf(dispatcher)` is unchanged (still holds `balance`), while `DustCollected` was already emitted claiming it was collected — the tokens are now stuck in the permissionless `CallDispatcher`, unreachable via normal gateway accounting.
