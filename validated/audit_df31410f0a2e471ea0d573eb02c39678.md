## Title
Webhook Shop/Topic Identity Spoofing via HMAC Signature Not Covering Request Headers - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` trusts and hands to the app's webhook handler are taken from unauthenticated HTTP headers that are never included in the HMAC computation. This breaks the identity binding `hmac(body) == hmac(body)` vs. `shop header == actual originating shop`, letting an attacker who possesses any valid `(body, hmac)` pair replay it with forged `shop`/`topic` headers and have it accepted as genuine.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from headers that are not part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which only checks `request.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., against the body alone: [3](#0-2) 

After that check passes, `Registry.process` immediately trusts the unauthenticated header-derived `request.topic` and `request.shop` to select the handler and construct the metadata handed to the app: [4](#0-3) 

Because `shop` (and `topic`) are acted upon (used for handler dispatch and as the tenant identifier passed to the app) but are not covered by the HMAC, any party who can obtain one valid `(body, hmac)` pair — for example by owning a shop that has the app installed and observing the genuine webhook delivered to their own endpoint — can resend that exact body/HMAC combination while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for an arbitrary target shop. `Registry.process` will accept it as authentic because the signature check never inspects those fields, and the host application's handler will process data believing it originated from, and pertains to, the spoofed shop.

### Impact Explanation
This breaks the tenant-identity binding "shop asserted in the trusted webhook == shop that actually produced/signed the payload," enabling cross-tenant data/event confusion: the receiving app can be made to attribute one merchant's webhook body to a different merchant, or to invoke a handler for a different topic than the body actually represents (e.g., causing an uninstall/data-deletion handler to run for a shop that never sent that event). This falls under the Critical "cross-tenant access" impact category defined in scope.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint plus possession of a single valid `(body, hmac)` pair, which is trivial to obtain by installing the app on an attacker-controlled development/test shop and observing genuinely delivered webhooks. No access to the app's `client_secret`, access tokens, or any privileged account is needed — this is exactly the "unprivileged internet user" scenario in scope, since the gem itself performs no binding between the signed bytes and the header-derived shop/topic it acts on.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, and ideally `webhook_id`) in the signable content verified by `HmacValidator`, or otherwise cryptographically bind them to the HMAC (e.g., have `Request#to_signable_string` concatenate the canonicalized headers with the body before hashing, matching however Shopify computes/verifies delivery-specific integrity). At minimum, document and enforce that consuming applications must not treat `shop`/`topic` from `WebhookMetadata` as authenticated unless they independently verify that the shop is one with an active app installation session correlated by other means.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger a webhook event and capture the raw POST body `B` and its `x-shopify-hmac-sha256` header value `H` (valid because it was computed by Shopify over `B` with the app's real secret).
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but set:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - (optionally) `x-shopify-topic: <different-topic>`
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes `HMAC(secret, B)` and finds it matches `H`, so validation passes.
4. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` looks up the handler for the (possibly forged) topic and invokes it with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host application to process attacker-supplied data as though it were a legitimate event from the victim shop.
