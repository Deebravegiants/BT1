Based on the webhook signature-verification code, I found a genuine identity-binding gap analogous to the reported bug class.## Title
Webhook shop/topic/webhook-id headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop`, `topic`, and `webhook_id` values that are handed to the host application's handler are read directly from unauthenticated HTTP headers. The binding the gem is supposed to enforce — "the bytes verified by HMAC == the identity fields acted upon" — does not hold, because those identity fields are never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all sourced from HTTP headers that are never mixed into the signable string: [2](#0-1) 

`Registry.process` verifies the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac-sha256` header value: [4](#0-3) 

Because the signature check never binds `shop-domain` (or `topic`/`webhook-id`) to the signed content, any request carrying a body+HMAC pair that is valid for *some* legitimate webhook (e.g., one the attacker's own store received, since the app-wide `client_secret` is shared across all shops using the app, not per-tenant) will pass `HmacValidator.validate` unchanged even if the `X-Shopify-Shop-Domain` (or topic/webhook-id) header is swapped to a different, victim shop domain. The gem then reports this forged identity to the host application as authenticated fact via `WebhookMetadata#shop`.

This is the same defect class as the reported withdrawal-processing bug: a check treats a field as validated ("`amountShares`"/"`queuedWithdrawalHead`" there, "`shop`" here) when the validation logic never actually covers that field, letting an unprivileged caller drive the acted-upon identity independently of what was authenticated.

### Impact Explanation
A host application that (as encouraged by this gem's own `WebhookMetadata`) uses `data.shop` to key which tenant's records a webhook affects will process attacker-supplied data under the wrong tenant's identity — a cross-tenant data-integrity/confidentiality breach, satisfying the "Critical — cross-tenant access" bar. No access token, `client_secret`, or privileged credential of the *victim* shop is required; the attacker only needs a body+HMAC pair that is valid under the app's shared secret (obtainable from any shop where the same third-party app is installed, including the attacker's own store, if they can observe traffic reaching the webhook endpoint) and free control over the request headers.

### Likelihood Explanation
Exploitability depends on the host application trusting `WebhookMetadata#shop`/`#topic`/`#webhook_id` for tenant/topic routing — which is exactly the documented, expected usage pattern of this API — and on the attacker being able to POST directly to the app's public webhook endpoint with custom headers (webhook endpoints are plain HTTP endpoints exposed to the internet, not behind Shopify's network). This is a realistic, low-effort attack path once a legitimate signed body is captured from any tenant using the app.

### Recommendation
Bind the identity fields into the verified material instead of trusting bare headers: include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (or independently re-derive/verify shop identity against a known session/shop registered for the app before dispatching to handlers), so that the HMAC check enforces `verified_bytes == (body, shop, topic, webhook_id)` rather than `verified_bytes == body` alone.

### Proof of Concept
1. Attacker installs (or has access to) the target app on their own store `attacker.myshopify.com`, and legitimately triggers a webhook event, capturing the raw request: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`).
2. Attacker resends the identical `B`/`H` to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and finds it matches `H` — validation succeeds because the header values were never part of the signed string.
4. `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)` is passed to the app's handler, which (per the gem's own documented pattern) uses `shop` to identify which tenant's records to update — resulting in cross-tenant data injection despite a "successfully verified" webhook.
