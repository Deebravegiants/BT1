## Finding: No mechanism to recover tokens mistakenly transferred directly to the AMM's coin/pc vaults

### Title
Tokens sent directly to `coin_vault`/`pc_vault` are permanently unrecoverable and get silently merged into pool reserves - ([File: program/src/processor.rs](program/src/processor.rs))

### Summary
Raydium's AMM computes pool reserves by reading the *live* SPL token balance of `amm_coin_vault` / `amm_pc_vault` on every deposit, withdraw, and swap call, rather than maintaining an internally tracked reserve variable that is reconciled against actual balances. There is no `skim`/`sweep` instruction analogous to Uniswap's `skim()` that lets a user recover tokens accidentally sent straight to the vault token accounts (via a plain SPL `Transfer`, bypassing `Deposit`/`Swap`). Such tokens are irreversibly absorbed into pool accounting with no path back to the sender.

### Finding Description
`process_deposit`, `process_withdraw`, and all four swap handlers derive `total_coin_without_take_pnl` / `total_pc_without_take_pnl` directly from `Self::unpack_token_account(&amm_coin_vault_info, ...)` / `amm_pc_vault_info` balances via `Calculator::calc_total_without_take_pnl_no_orderbook`, e.g.: [1](#0-0) 

This same pattern (reading `amm_coin_vault.amount` / `amm_pc_vault.amount` directly as the reserve) is repeated in swap paths: [2](#0-1) 

Because these functions treat "whatever is physically in the vault" as canonical reserves, any tokens transferred directly into `coin_vault`/`pc_vault` by a user (bypassing the `Deposit`/`SwapBaseIn`/`SwapBaseOut` instructions) become indistinguishable from legitimate LP-contributed liquidity. They are folded into `total_coin_without_take_pnl`/`total_pc_without_take_pnl` and thus diluted pro-rata into the LP pool the moment any subsequent deposit/withdraw/swap recomputes the invariant — with no LP tokens minted to the sender and no instruction available to reclaim the specific amount.

The only "excess" recovery instruction that exists, `WithdrawExcessLamports`, is scoped exclusively to native lamports/WSOL sync-native drift and requires a privileged signer (`config_feature::collect_lamports::id()`); it is not a general-purpose skim for arbitrary SPL coin/pc token donations, and even if it were, it is only callable by a privileged account, not by the mistaken sender: [3](#0-2) [4](#0-3) 

No equivalent instruction exists in `instruction.rs` for coin/pc token accounts — the full instruction set includes only `Deposit`, `Withdraw`, `Swap*`, `WithdrawPnl`, `SetParams`, and `WithdrawExcessLamports`: [5](#0-4) 

### Impact Explanation
Any user (human error, wallet UI misconfiguration, or bridging/relayer mistake) who sends SPL coin or pc tokens directly to `amm.coin_vault` / `amm.pc_vault` instead of going through `Deposit` permanently loses ownership of those tokens: they are merged into the constant-product invariant and effectively donated to existing LPs (or, on the next `Withdraw`, redistributed pro-rata to whichever LP happens to withdraw), with zero recourse for the original sender. This is a permanent freezing/loss of user funds with no privileged or unprivileged instruction path to reclaim them, satisfying the "permanent freezing of user funds" bar. It is a systemic gap present across every deployed pool, not a one-off.

### Likelihood Explanation
Likelihood is driven by user error rather than an active attacker, but it requires no special conditions: a normal SPL `Transfer` CPI/instruction to a publicly-known vault address (found by anyone querying `AmmInfo.coin_vault`/`pc_vault`) is sufficient. Given the vault addresses are public and are the natural target for anyone manually "topping up" or interacting incorrectly with a pool, and the pattern is confirmed to appear on all pools using this codebase, the likelihood of this occurring per-pool over time is realistic (as evidenced by it being a general, medium-severity finding class widely reported against constant-product AMMs lacking a skim function).

### Recommendation
Add a `Skim` instruction, mirroring Uniswap V2, that:
1. Reads the current vault balances (`amm_coin_vault.amount`, `amm_pc_vault.amount`).
2. Computes the excess over the amount implied by tracked reserves/LP accounting (e.g., difference vs. `total_coin_without_take_pnl` / `total_pc_without_take_pnl` computed the same way as in `process_deposit`/`process_swap_base_in`).
3. Transfers only that excess out to a caller-specified destination, signed by the AMM authority PDA (reusing `Invokers::token_transfer_with_authority`), without touching LP-backing reserves.

This preserves pool solvency invariants while giving users (or a controlled sweep authority) a legitimate way to recover mistakenly-sent tokens instead of having them silently absorbed into LP value with no recovery path.

### Proof of Concept
1. Attacker/user obtains `amm.coin_vault` pubkey (public, part of `AmmInfo`).
2. User issues a standard `spl_token::instruction::transfer` sending `X` coin tokens directly to `amm.coin_vault`, without invoking any Raydium instruction.
3. On the next `Deposit`, `Withdraw`, or `Swap*` call, `Self::unpack_token_account(&amm_coin_vault_info, ...).amount` includes the donated `X`, so `Calculator::calc_total_without_take_pnl_no_orderbook` (processor.rs:1148-1153) folds `X` into `total_coin_without_take_pnl` used for LP mint/redeem math.
4. The sender's `X` tokens are now permanently part of pool reserves; no instruction in `instruction.rs` allows the sender to withdraw exactly `X` back — `Withdraw` only returns tokens proportional to burned LP tokens the sender does not have, and `WithdrawExcessLamports` is privileged and SOL/lamports-only (processor.rs:2816-2842).
