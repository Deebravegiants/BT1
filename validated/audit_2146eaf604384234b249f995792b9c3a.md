This confirms the mechanics described in the claim: `jsonRequest.ID` becomes `msg.Body.MessageID` at [1](#0-0) , and the gateway only checks length (≤200 chars), not uniqueness or ownership, before routing into `HandleLegacyUserMessage`. The `MessageID` is client-chosen and only validated for length/null-suffix in `Message.Validate()` [2](#0-1) , and the client's own signature covers only their own message body — it does not prove exclusive ownership of that ID relative to other clients [3](#0-2) . `savedCallbacks` is a single global map keyed only by `MessageID` [4](#0-3) , and `handleWebAPITriggerMessage` resolves it via first-response-wins with an explicit TODO about missing quorum, with no cross-check that the response payload matches the original request's payload [5](#0-4) . The only check on node responses is signature validity and `Sender == nodeAddr` [6](#0-5) , which authenticates the node but does nothing to bind the response content to a specific original request.

The claim's uncertainty note is resolved: `ProcessRequest` shows the `MessageID` is exactly `jsonRequest.ID`, fully attacker-controlled up to 200 characters, with no per-client namespacing or uniqueness enforcement anywhere before it reaches `h.savedCallbacks[msg.Body.MessageID]` [7](#0-6) . This confirms the full exploit path end-to-end as described in the report: an unprivileged HTTP client can choose an arbitrary `MessageID`, collide with a concurrently in-flight legitimate request from another user, and receive that user's DON node response (or cause the other user to receive the attacker's), since resolution is keyed purely by that unauthenticated, collision-prone string and completes on the first matching node reply without quorum or content binding.

Audit Report

## Title
Cross-user response confusion via unauthenticated, client-controlled MessageID collision in legacy WebAPI capabilities gateway handler - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
The legacy WebAPI trigger callback flow (`HandleLegacyUserMessage` → `handleWebAPITriggerMessage`) resolves a pending user callback using a single global map keyed solely by the client-supplied, unauthenticated `MessageID` (which is exactly the JSON-RPC request `ID` passed through `ProcessRequest`), accepting the first DON node response for that ID without quorum or without verifying the response corresponds to the original request's payload. Two different unprivileged callers who use (or collide on) the same `MessageID` can have their pending callbacks and DON responses cross-delivered.

## Finding Description
`gateway.ProcessRequest` sets `msg.Body.MessageID` directly from the caller-supplied `jsonRequest.ID`, validating only its length (≤200 characters) before dispatching to `HandleLegacyUserMessage`. [1](#0-0)  `HandleLegacyUserMessage` stores the caller's callback keyed purely by this `MessageID` in the handler-global `h.savedCallbacks` map: [4](#0-3) . `handleWebAPITriggerMessage`, invoked when any DON node responds, looks up and deletes the entry keyed by `msg.Body.MessageID` and delivers whichever response arrives first back to that callback, with an explicit TODO acknowledging the lack of a 2F+1 quorum check: [5](#0-4) . The only authentication performed on the incoming node message is that its signature resolves to a real DON member and `Sender == nodeAddr` [6](#0-5)  — this proves the message came from a legitimate node, but does nothing to prove the *content* of that response corresponds to the specific request that created the currently-stored callback for that ID. `Message.Validate()` only checks length/null-suffix constraints on `MessageID`, not uniqueness or ownership [2](#0-1) , and the message signature only proves the sender authored their own message body; it does not reserve the ID against use by other unrelated senders [3](#0-2) . Consequently, an unprivileged HTTP client can choose an arbitrary `MessageID`, collide with another in-flight request using the same ID (whether by chance or by picking IDs an attacker can predict/observe/control), and cause `savedCallbacks` to resolve to the wrong requester's response.

## Impact Explanation
This enables cross-user response corruption/confusion at the gateway: a victim's request can be answered with data resulting from an attacker's unrelated request (or vice versa), and because the callback map entry is deleted on first match, the "losing" party's request will simply hang until timeout with no error signaling the collision. This maps to the "gateway request impersonation / cross-user response corruption" impact category referenced in scope.

## Likelihood Explanation
Exploitation requires only unprivileged access to the gateway's public HTTP JSON-RPC endpoint plus the ability to submit a request with a chosen `ID`/`MessageID` — no privileged role, malicious node, or network-layer trust assumption is needed. The code's own TODO comment ("in practice, we should wait for at least 2F+1 nodes to respond") confirms this is a known placeholder/single-node-trust design rather than a hardened path, and the newer `v2` HTTP trigger and `vault` handlers use per-request unique-ID enforcement and quorum aggregation, underscoring that this legacy path lacks equivalent protections.

## Recommendation
- Reject or scope `MessageID` collisions across distinct senders/sessions (mirroring the `newActiveRequest`-style uniqueness check used in `v2/http_trigger_handler.go` and `vault/handler.go`).
- Require BFT quorum (2F+1) matching node responses before resolving a callback, replacing the current first-responder-wins logic and its TODO.
- Bind the callback key to a hash of the original request payload/sender (not just the raw client-chosen `MessageID`) so a node's response can only satisfy the callback for the request it was actually generated from.

## Proof of Concept
1. Attacker sends a legacy gateway JSON-RPC request (`method = web_api_trigger`) with `id = "X"` and attacker payload; `HandleLegacyUserMessage` stores `h.savedCallbacks["X"]`.
2. Concurrently, victim sends a legitimate request also using `id = "X"` (predictable/observable/colliding value), overwriting `h.savedCallbacks["X"]` with the victim's callback.
3. A DON node responds to the attacker's forwarded request first; `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]` (now the victim's callback), deletes it, and delivers the attacker-derived response to the victim's callback — demonstrable via a Go unit test in `handler_test.go` that calls `HandleLegacyUserMessage` twice with the same `MessageID` from two different callbacks, then calls `HandleNodeMessage`/`handleWebAPITriggerMessage` once, and asserts which callback received the response.
