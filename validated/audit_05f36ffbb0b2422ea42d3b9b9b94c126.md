### Title
Emporium Min-path proof with `signerAddress == 0` and empty `erc20TokenAddresses` lets an attacker drain any ERC20 held by Emporium with no accounting - ([File: contracts/CircomDataBuilder.sol], [File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `emporiumMessage == Poseidon(messageSeed)`, `timeStamp`, and `calldataHash` — nothing about tokens, amounts or ops. Combined with `EmporiumUpgradeable.verifyWallet` skipping all signature checks when `stack.signerAddress == address(0)`, an unprivileged attacker can supply an arbitrary `EmporiumStack` whose stateless op (`op.endpoint.call{value: op.value}(op.callData)`) transfers any ERC20 token that Emporium holds to themselves, while both `EmporiumUpgradeable.runAction`'s balance loop and `Hinkal.transact`'s balance/slippage loop iterate the empty `erc20TokenAddresses` array and therefore account for nothing.

### Finding Description
The invariant that should hold is: *every asset Emporium can move in a transaction must be included in `circomData.erc20TokenAddresses` and therefore constrained by `balancesBefore`/`balancesAfter` in `EmporiumUpgradeable.runAction` (lines 85-87, 122-151) and by the balance/slippage loop in `Hinkal.transact` (lines 97-147)*. This equality is broken when `erc20TokenAddresses.length == 0`.

Path:
1. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks`, which calls `CircomDataBuilder.formInputForCircom` [1](#0-0) . Because the attacker sets `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and passes an empty `erc20TokenAddresses` array, `formInputEmporiumMin` is used, which only encodes `emporiumMessage`, `timeStamp`, `calldataHash` as public signals [2](#0-1) . The attacker can freely choose `emporiumMessage = Poseidon(messageSeed)` for a `messageSeed` they pick themselves, so this circuit is trivially satisfiable — no UTXO, nullifier, root, or token constraint is enforced by the ZK proof for this path.
2. `Hinkal.transact` calls `_externalTransact`, which forwards to `EmporiumUpgradeable.runAction` (guarded only by `onlyAllowedRecipient`, satisfied because the caller is the Hinkal contract itself) [3](#0-2) .
3. `runAction` decodes the attacker-controlled `EmporiumStack` from `externalActionData.externalActionMetadata` [4](#0-3) . It calls `verifyWallet`, which for `stack.signerAddress == address(0)` returns immediately after only marking `emporiumMessage` as used — **no signature or authorization check is performed on `stack.ops`** [5](#0-4) .
4. The ops loop then executes CASE 2 "Stateless Interaction": `op.endpoint.call{value: op.value}(op.callData)`, with `msg.sender == Emporium contract` [6](#0-5) . The attacker sets `op.endpoint` to an ERC20 token that Emporium already holds a balance of, and `op.callData` to `transfer(attacker, amount)`. Only the boolean `success` of the raw `.call` is checked — the ERC20's own return value (which some non-compliant tokens set `false` on failure without reverting) is never inspected, so this path bypasses SafeERC20-style checks entirely.
5. Because the stolen token is not in `circomData.erc20TokenAddresses` (empty by construction of the Min path), it never appears in `balancesBefore`/`balancesAfter` in `runAction` (lines 85-87, 122-151), so `BalanceChangeShouldBePositive` cannot fire, and it never appears in `Hinkal.transact`'s balance/slippage accounting loop (lines 97-147) either.

Existing guards fail because: `performHinkalChecks`/`dimensionsCheck` only validate calldata-hash integrity and dimension bounds for the *declared* arrays, not that all tokens actually touched during external-action execution are declared; `verifyWallet`'s early return for `signerAddress == 0` was evidently intended for a scenario where accounting is unnecessary, but it is reachable together with arbitrary stateless calls and an unconstrained ("Min") token list.

### Impact Explanation
An attacker can steal any ERC20 balance held by the `EmporiumUpgradeable` contract (accumulated relay fees, dust, tokens transiently held mid-transaction) by crafting a single self-signed, trivially provable Min-circuit proof and an `EmporiumStack` with `signerAddress == address(0)` whose op calls `transfer` on the target token from Emporium to the attacker. This is direct theft of protocol/relay funds or funds transiently custodied by Emporium, repeatable every time Emporium holds a non-zero balance of any ERC20 not enumerated in the attacker's `erc20TokenAddresses`, i.e., on every transaction (severity: Critical, per the rubric's "direct theft of shielded or in-flight user funds").

### Likelihood Explanation
Preconditions: Emporium must hold some non-zero ERC20 balance (routine, since relay fees and cross-op leftovers accumulate there) and an `emporiumMessage` nonce not yet used. Attacker cost is a single transaction with a self-generated Min-circuit proof (computationally trivial — the only constraint is `message == Poseidon(messageSeed)`, both chosen by the attacker) plus normal gas. No privileged role, relay cooperation, or victim action is required, making this fully attacker-controlled and repeatable.

### Recommendation
Do not allow `verifyWallet` to skip authorization when `stack.signerAddress == address(0)` unless the op set is proven empty or otherwise cryptographically bound to the (necessarily minimal) public inputs of the Min circuit. At minimum: (1) forbid CASE 2 "stateless" calls entirely when `erc20TokenAddresses.length == 0` and `signerAddress == address(0)`, or (2) require that every token touched/transferred by any op in `stack.ops` be included in and accounted against `circomData.erc20TokenAddresses`, restoring the invariant that Emporium's `balancesBefore`/`balancesAfter` loop and Hinkal's balance/slippage loop cover every asset the transaction can move. Additionally, check the actual ERC20 boolean return value (not just call `success`) for `transfer`/`transferFrom` invocations dispatched through Emporium.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, and a test ERC20 (`TestToken`). Register Emporium as an allowed external action and allowed recipient.
2. Fund the Emporium contract directly with `TestToken.transfer(emporiumAddress, 1000e18)` to simulate accumulated fees/leftover balance.
3. As an unprivileged attacker EOA, construct `CircomData` with: `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `emporiumMessage = Poseidon(attackerChosenSeed)` (computed locally), `externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: testToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e18))})], maxFee: 0, deadline: type(uint256).max}))`.
4. Generate a valid Min-circuit proof locally for these public inputs (trivial, no UTXO/tree dependency).
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker EOA.
6. Assert: `TestToken.balanceOf(attacker)` increased by `1000e18` and `TestToken.balanceOf(emporiumAddress)` decreased by `1000e18`, while `Hinkal.transact`'s balance/slippage loop and `EmporiumUpgradeable.runAction`'s `balancesBefore`/`balancesAfter` arrays remain length-0 and impose zero constraints on this movement — demonstrating the equality "assets Emporium can move == assets accounted in balancesBefore/balancesAfter" is broken.
