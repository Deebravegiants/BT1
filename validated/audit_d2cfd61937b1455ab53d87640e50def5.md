### Title
Webhook `shop-domain` (and `topic`/`webhook_id`/`api_version`) headers are trusted for tenant routing but are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by HMAC-verifying the raw JSON body, then dispatches to the app's handler using `shop`, `topic`, `webhook_id`, and `api_version` values that are read from HTTP headers which are never included in the signed payload.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from headers, none of which participate in signing: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header — it has no knowledge of `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic`/etc. to build the `WebhookMetadata` passed to the app's handler, with no cross-check that these header values are bound to the authenticated body: [4](#0-3) 

This breaks the identity binding: **authenticated bytes (body) ≠ bytes acted on for tenant identity (`shop` header)**. The HMAC only proves "this body was signed with our secret"; it proves nothing about which shop, topic, or webhook the body belongs to. Any request whose body+HMAC pair validates (e.g., a genuinely-received webhook body/HMAC pair, replayed with a different `shop-domain`/`topic` header) will pass `HmacValidator.validate` and be routed to the handler under an attacker-chosen shop/topic instead of the shop/topic that Shopify actually signed for.

### Impact Explanation
An unprivileged actor who can obtain one legitimately-signed webhook body+HMAC pair for a shop they control (e.g., a merchant installing the app on their own store and capturing the webhook Shopify sends to the app's public endpoint) can resend that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to reference a different, victim shop. Because the gem hands the handler a `WebhookMetadata` whose `shop`/`topic` come from the unauthenticated header rather than anything the HMAC covers, host applications that key their per-tenant data mutation (order/product/customer updates, uninstall handling, etc.) off `WebhookMetadata#shop` will process attacker-supplied data under the wrong tenant's identity — a cross-tenant data-integrity/spoofing issue satisfying the Critical "cross-tenant access" bar, since the shop identity binding used for routing/authorization is not the shop identity that was cryptographically verified.

### Likelihood Explanation
No access token, `api_secret_key`, or privileged access is required. The attacker only needs a single genuine webhook delivery aimed at the target app's public webhook endpoint (trivially obtainable by installing the app on a shop the attacker controls) and the ability to POST to that same public endpoint with modified headers — both are within reach of any unprivileged internet user interacting with a publicly reachable app endpoint.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the value that is HMAC-verified (or otherwise cryptographically bind them to the authenticated body), so header spoofing after body capture cannot redirect a validly-signed payload to a different tenant/topic. At minimum, `VerifiableQuery#to_signable_string` for webhook requests should incorporate the header fields the handler relies on for identity/routing, not just the raw body.

### Proof of Concept
1. Attacker installs the target app on shop `attacker-shop.myshopify.com` and registers/receives a legitimate webhook (e.g., `orders/create`).
2. Shopify POSTs to the app's public webhook URL with a valid `x-shopify-hmac-sha256` computed over the raw body, plus headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker captures this body + HMAC (available to them because it was sent for their own shop).
4. Attacker replays the identical body and HMAC to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the raw body against the HMAC — it passes.
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though Shopify never signed anything for that shop, and the host application performs cross-tenant data mutation using attacker-controlled body content attributed to the victim shop.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
