Based on my investigation, I found a concrete analog to the reported bug class: **an identity-binding field (`shop`) that is acted upon but not covered by the HMAC signature**.

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header fields are not covered by the HMAC, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate`, which verifies an HMAC computed only over the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values are all read straight from unauthenticated HTTP headers [2](#0-1)  and are never included in `to_signable_string`, so they are not covered by the signature check performed in `HmacValidator.validate_signature` [3](#0-2) .

### Finding Description
`Registry.process` does:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [4](#0-3) 

`request.shop` is populated from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the signed payload [5](#0-4) . The identity binding the library implicitly promises hosts is: `HMAC(raw_body, client_secret) valid ⇒ (shop, topic, webhook_id) in WebhookMetadata are authentic for that shop`. In reality the equality only holds for `raw_body`; `shop == request.shop` is unauthenticated user input.

Because the HMAC secret (`client_secret`) is identical for every shop that has the app installed, any shop that has legitimately installed the app receives genuinely-signed webhooks (valid `(raw_body, hmac)` pairs) for its own tenant. That shop's operator — an otherwise unprivileged merchant with no access to any other tenant's data — can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and `topic`/`webhook-id`) header with an arbitrary victim shop's domain. `HmacValidator.validate` recomputes the HMAC only over `raw_body`, which still matches, so `Registry.process` accepts the request and calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop [6](#0-5) .

Since `WebhookMetadata#shop` is the only tenant-identifying field the library exposes to host applications for webhook processing (per the documented usage pattern) [7](#0-6) , and hosts have no other means within this gem to independently verify which shop actually generated the event, this breaks the equality `shop authenticated == shop acted upon`, which is exactly the reported bug class ("a field acted on but not covered by the HMAC").

### Impact Explanation
This is a cross-tenant integrity issue: a legitimate but unprivileged merchant of the app can spoof events (e.g. `orders/create`, `app/uninstalled`, `customers/redact`, `shop/redact`) as coming from a different, victim shop, causing the host application to execute tenant-scoped business logic (data mutation, redaction, deprovisioning, notifications) against the wrong tenant. Depending on the handler, this can lead to cross-tenant data corruption or unauthorized state changes attributed to a shop the attacker does not control — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker install the target app on their own store (a normal, unprivileged action available to anyone) to obtain one genuinely-signed `(raw_body, hmac)` webhook, then replay it with a modified `shop-domain`/`topic`/`webhook-id` header to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the victim's data is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable string (or otherwise cryptographically bind them, e.g. by deriving/validating them from a value that is part of the signed body, or by requiring hosts to cross-check `shop` against an out-of-band registered webhook endpoint/shop mapping) so that `HmacValidator.validate` fails whenever any of these header-derived identity fields are altered relative to what Shopify actually signed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining a valid client_secret-bound relationship (no special privilege).
2. Shopify sends a genuine webhook to the app's endpoint, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of raw_body>
x-shopify-shop-domain: attacker-shop.myshopify.com
Body: {"id": 1, ...}
```
3. Attacker replays the identical body and `hmac` header, but changes only the shop header:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <same valid HMAC, body unchanged>
x-shopify-shop-domain: victim-shop.myshopify.com
Body: {"id": 1, ...}
```
4. `ShopifyAPI::Webhooks::Request.new` parses headers unmodified [8](#0-7) ; `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches [9](#0-8) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)`, and the host application performs its tenant-scoped logic against `victim-shop.myshopify.com` even though Shopify never sent this event for that shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
