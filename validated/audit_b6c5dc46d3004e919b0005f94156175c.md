## Verdict: Valid vulnerability confirmed

### Title
Emporium Min-proof path lets anyone drain Emporium's native/ERC-20 balance via unaccounted, unsigned `EmporiumOperation` calls - (File: contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, whose circuit only needs to prove knowledge of `emporiumMessage` (Poseidon preimage) plus a hash-integrity commitment, with zero constraints on real UTXOs, nullifiers, or amounts. Because `erc20TokenAddresses` is empty, both `EmporiumUpgradeable.runAction`'s balance-accounting loop and `Hinkal.transact`'s post-action balance/slippage checks execute zero iterations, and `verifyWallet` skips ECDSA verification entirely whenever `EmporiumStack.signerAddress == address(0)`. An attacker can therefore submit a trivially-generated Min proof together with an `EmporiumStack{signerAddress:0, ops:[{endpoint: attacker, value: <emporium's balance>, callData: ...}]}` and have Emporium execute an arbitrary, value-carrying, unsigned external call from its own identity with no accounting anywhere in the call graph.

### Finding Description
The broken equality is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`** (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`, lines 85-151) and, at the top level, **balance change per token == `deltaAmountChanges`/UTXO amount reconciled in `Hinkal.transact`** (`contracts/Hinkal.sol`, lines 78-147).

Path:
1. `CircomDataBuilder.formInputForCircom` (lines 134-148) selects `formInputEmporiumMin` (lines 150-161) whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`. That function only emits `emporiumMessage`, `timeStamp`, `calldataHash` as public signals — no nullifiers, no amountChanges, no token addresses are constrained by the circuit at all. [1](#0-0) 
2. `HinkalHelper.dimensionsCheck` (lines 64-171) is trivially satisfied when every dimension is `0`, so an all-empty `circomData` (no tokens, no nullifiers, no commitments) passes checks unconditionally. [2](#0-1) 
3. In `Hinkal.transact`, `oldBalances`/`newBalances` are computed over the empty `erc20TokenAddresses` array, and the post-action reconciliation loop (balanceDif, slippage, UTXO amount checks) at lines 97-147 runs zero times — nothing is verified about value moved during the call. [3](#0-2) 
4. `_externalTransact` builds `deltaAmountChanges` of length 0 and calls `EmporiumUpgradeable.runAction` (external, attacker-crafted `externalActionMetadata`). [4](#0-3) 
5. Inside `runAction`, `balancesBefore`/`balancesAfter` are again computed over the empty token array (lines 85-87, 122-151), so the per-token accounting loop never executes. [5](#0-4) 
6. `verifyWallet` (lines 302-349) returns immediately with **no signature check** when `stack.signerAddress == address(0)`, only marking `emporiumMessage` used. [6](#0-5) 
7. The op loop then executes CASE 2 ("Stateless Interaction"): `op.endpoint.call{value: op.value}(op.callData)`, sourcing `op.value` from Emporium's own native-token balance, msg.sender being Emporium itself. [7](#0-6) 

Root cause: the Min-proof shortcut and the empty-array accounting shortcut are two independent optimizations that were not designed to compose safely — combined, they let an unprivileged party author `EmporiumStack.ops` with arbitrary `endpoint`/`value`/`callData` and zero signature or balance-diff enforcement anywhere in the call chain. Existing guards do not catch this: `performHinkalChecks`'s `calldataHash` check only ensures self-consistency of the attacker's own crafted calldata, not its legitimacy; `rootHashExists` only requires citing any valid public root, not ownership of value; `onlyAllowedRecipient` only checks that `msg.sender` is the legitimate Hinkal/Emporium contract, not that the payload is safe.

### Impact Explanation
Any ETH (or, via `callData` targeting an ERC-20 token as `endpoint` with `transfer(attacker, amount)`, any ERC-20) balance held by the Emporium contract — whether from direct sends to its `receive()`, residual dust from prior legitimate ops, or funds transiently routed to Emporium by other in-flight Hinkal transactions — can be transferred out to an attacker-chosen address with a self-authored proof and no signature. This is direct theft of protocol/relay/user funds resident in the Emporium contract, matching **Critical: direct theft of shielded or in-flight user funds**. The attack is repeatable for every distinct `emporiumMessage` (trivially generated by the attacker) and every time Emporium accrues a balance.

### Likelihood Explanation
Preconditions are minimal for an unprivileged attacker: they need to (a) know the deployed Emporium address (public), (b) generate a proof for the Min circuit (only requires knowledge of a self-chosen `messageSeed`, trivially satisfiable), and (c) craft `CircomData` with all dimensions zero and `externalActionData.externalActionMetadata` encoding a malicious `EmporiumStack`. No real UTXO, deposit, or relay whitelisting is required (attacker can set `relay = address(0)` and `originalSender = msg.sender`). Cost is just gas plus proof generation. The only limiting factor is Emporium's actual held balance at attack time, but any nonzero balance is fully drainable.

### Recommendation
Do not allow the Min proof path to be used with `signerAddress == address(0)` operations that move value — require either: (1) a non-zero `erc20TokenAddresses` list whose balance deltas are constrained by a full-circuit proof whenever `EmporiumStack.ops` contains any `op.value > 0` or targets external `endpoint` calls, or (2) mandatory signature verification (`stack.signerAddress != address(0)`) for every op regardless of Min/Normal path selection. Additionally, enforce that Emporium's `runAction` balance-accounting loop cannot be bypassed by an empty `erc20TokenAddresses` array when `stack.ops` is non-empty — e.g., require `erc20TokenAddresses.length > 0` (or explicitly account for native ETH) whenever any op has `value > 0` or a non-trivial `callData`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as in existing test fixtures), register Emporium as `HINKAL_EMPORIUM_ACTION_ID` in `externalActionMap`, and register Emporium as an allowed recipient.
2. Fund Emporium with 10 ETH (simulate residual/in-flight balance via `receive()` or a prior legitimate op).
3. As an attacker EOA with no prior Hinkal deposits, locally generate a Min-circuit proof for a self-chosen `messageSeed` (`emporiumMessage = Poseidon(messageSeed)`), and craft `CircomData` with: `erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, `inputNullifiers = []`, `outCommitments = []`, `encryptedOutputs = []`, `externalActionData = {externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalAddress: <Emporium>, externalActionMetadata: abi.encode(EmporiumStack{signerAddress:address(0), ops:[{endpoint:attacker, invokeWallet:false, value:10 ether, callData:""}], maxFee:0, deadline:0})}`, `rootHashHinkal`/`rootHashHinkalIndex` set to any existing valid root, `calldataHash = getHashedCalldata(circomData)`.
4. Call `Hinkal.transact(a,b,c,dimensions{tokenNumber:0,nullifierAmount:0,outputAmount:0}, circomData)` from the attacker.
5. Assert: (a) `address(Emporium).balance` before == 10 ether, after == 0; (b) `attacker.balance` increases by 10 ether; (c) transaction succeeds without reverting on any balance/slippage/signature check — proving the equality "assets moved == assets accounted" is violated (accounted amount is 0, moved amount is 10 ether).
