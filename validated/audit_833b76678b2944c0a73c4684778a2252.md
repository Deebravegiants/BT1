### Title
`findMatchingWithdrawal` matches only by `assetId`, so batched same-token withdrawals get each other's status/txHash - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the status of a `WithdrawalIdentifier` by calling `findMatchingWithdrawal`, which selects the first entry in the PoA API's `withdrawals` array whose `nep141:<near_token_id>` equals the target `assetId`. When a batch contains two or more withdrawals of the same token (same `assetId`, e.g. `nep141:adi.omft.near`) to different destinations/amounts, both `WithdrawalIdentifier`s resolve to the same (first-matching) entry, so one payout's `completed` status and `transfer_tx_hash` get attached to the other identifier.

### Finding Description
The broken equality is: `describeWithdrawal(wid_A).txHash/status` should correspond to the on-chain payout matching `wid_A.withdrawalParams.{destinationAddress, amount}`, but instead it corresponds to whichever entry `withdrawals.find(w => nep141:${w.data.near_token_id} === assetId)` returns first [1](#0-0) .

`describeWithdrawal` calls `getWithdrawalStatusWithRetry` (keyed only by the shared `tx.hash` of the batch intent transaction, not by destination) and then `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` [2](#0-1) . The function's own docstring admits the limitation: "multiple withdrawals of the same token in a single transaction are not supported... POA API doesn't currently support this case either" [3](#0-2) .

Nothing upstream prevents an integrator/attacker from constructing a batch with two `nep141:adi.omft.near` withdrawals to different destination addresses: `createWithdrawalIdentifiers` iterates `withdrawalParams` and assigns a per-route incrementing `index`, but that `index` is never used by `PoaBridge` to disambiguate — only `assetId` is used [4](#0-3) . `supports()` and `validateWithdrawal()` validate each withdrawal independently (destination address format, min amount, token support) and do not reject duplicate-assetId batches [5](#0-4) . `watchWithdrawal` in `withdrawal-watcher.ts` directly consumes whatever `describeWithdrawal` returns as the truth for that specific `wid`, converting a `completed` status into a resolved `{hash}` result [6](#0-5) .

Exploit flow: an integrator (or a counterparty whose params get forwarded) submits a batch withdrawal with two `nep141:adi.omft.near` legs — one to address X (amount 100) and one to address Y (amount 5, dust). The relayer processes both; the PoA API's `withdrawal_status` endpoint returns both entries in arbitrary/unsorted order. When `IntentsSDK.waitForWithdrawalCompletion` polls both `WithdrawalIdentifier`s, `findMatchingWithdrawal` returns the *same* entry (say, Y's completed transfer) for both identifiers, because matching only checks `assetId`. The integrator watching X's `WithdrawalIdentifier` sees `status: "completed"` with Y's `txHash`, while X's actual transfer may still be pending, or vice versa.

### Impact Explanation
This is a status/hash misreport: the SDK reports a withdrawal as `completed` with a `txHash` that does not correspond to the destination/amount the caller specified. An integrator that credits an off-chain ledger or releases funds based on this `completed` status could credit the wrong leg twice, or fail to notice that the intended payout hasn't landed — matching the "status or hash misreport making an integrator credit or refund twice" High-severity category from the rules.

### Likelihood Explanation
Preconditions: a batch withdrawal (or two overlapping withdrawal identifiers being watched concurrently) using the same POA token (`nep141:<x>.omft.near`) to two different destinations. Nothing in `supports()`, `validateWithdrawal()`, or `createWithdrawalIdentifiers` blocks constructing or watching such a batch — the code explicitly documents this as an unhandled, accepted case rather than a rejected one. This is fully attacker/caller-controlled: any unprivileged user can submit such a batch, and it's repeatable on every occurrence of duplicate-token batches while both legs are outstanding (the ambiguity clears once only one of the two entries remains unmatched-elsewhere, i.e., transient but real).

### Recommendation
Extend `findMatchingWithdrawal` to disambiguate same-token withdrawals using additional fields present in the PoA response (destination address and/or amount) matched against `withdrawalParams.destinationAddress`/`amount`, or reject/throw when multiple candidates match the same `assetId` rather than silently returning `.find()`'s first hit. At minimum, when more than one candidate matches an `assetId`, `describeWithdrawal` should throw an explicit "ambiguous withdrawal match" error instead of returning a possibly-wrong status.

### Proof of Concept
Vitest plan (mock only the HTTP client `poaBridge.httpClient.getWithdrawalStatus`):
1. Mock `getWithdrawalStatus` to return two `withdrawals` entries for `near_token_id: "adi.omft.near"`: entry1 `{status:"COMPLETED", data:{near_token_id:"adi.omft.near", transfer_tx_hash:"0xHASH_Y", destination_address:"Y"}}`, entry2 `{status:"PENDING", data:{near_token_id:"adi.omft.near", destination_address:"X"}}`.
2. Build two `WithdrawalIdentifier`s, `widX` (`withdrawalParams.assetId="nep141:adi.omft.near"`, `destinationAddress:"X"`) and `widY` (same assetId, `destinationAddress:"Y"`), sharing the same `tx.hash`.
3. Call `poaBridge.describeWithdrawal(widX)` and `poaBridge.describeWithdrawal(widY)`.
4. Assert the broken equality: both calls currently return the *same* result (`{status:"completed", txHash:"0xHASH_Y"}`) instead of `widX` resolving to pending (matching entry2) and `widY` resolving to completed with `0xHASH_Y` (matching entry1) — i.e., assert `describeWithdrawal(widX).status !== describeWithdrawal(widY's expected match)` fails today, demonstrating the misreport.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };

				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
