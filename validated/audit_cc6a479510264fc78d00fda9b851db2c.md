## #Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only and then trusts the header-derived `shop` value to attribute the event to a tenant, breaking the binding `HMAC-signed bytes == identity bytes acted upon`.

### Finding Description
`Utils::HmacValidator.validate(request)` computes `OpenSSL::HMAC.hexdigest(secret, request.to_signable_string)` and compares it to the `hmac-sha256` header. [1](#0-0) 
`to_signable_string` for a webhook request is defined as just `@raw_body`: [2](#0-1) 
Meanwhile `shop`, `topic`, and `webhook_id` are pulled straight from HTTP headers that are not part of the signed bytes at all: [3](#0-2) 
`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e. body integrity) and then immediately forwards `request.shop` — an unauthenticated header value — to the app's handler as the tenant identity for the event: [4](#0-3) 

This is exactly the analog bug class described in the report: a field (`renewalCutoffTime`/here, `shop`) is acted upon by downstream logic but is not covered by the same authenticity check (`HMAC`) that guards the rest of the message. The library's own documentation claims `process` "will verify the request did indeed come from Shopify" — implying full authenticity of the webhook, including its stated shop — but only the body bytes are actually bound to the signature: [5](#0-4) 

Because every shop installed on an app shares the same webhook secret (`Context.api_secret_key`) and the same callback endpoint/path, any merchant who can trigger a webhook delivery to their own store (e.g. by performing an action that fires a registered topic with a body content they influence, or simply replaying a previously captured legitimate webhook payload with a valid HMAC for that body) can resend that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` will still pass (it never looks at the header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This breaks the tenant/shop binding that the app relies on to route webhook data (e.g., orders, customer data, GDPR redact topics) to the correct shop's session/storage. An attacker-controlled shop can inject events attributed to another merchant's shop, which is a cross-tenant data-integrity/authentication issue: the app processes attacker-supplied data believing it is authenticated data from a different tenant. For handlers that write, delete, or redact merchant data keyed by `shop`, this allows a malicious merchant to corrupt or exfiltrate-adjacent state of another shop's data path, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any app owner (an unprivileged Shopify merchant who installs the target app) can register/receive their own legitimate webhooks and control at least part of the resulting body (for topics whose payload includes attacker-influenced fields, or by using a topic whose body is constant/predictable, as shown by the test fixture using body `"{}"`). Replaying that valid `raw_body` + `hmac` with a forged `shopify-shop-domain` header requires no credentials beyond normal merchant access to the app, and no interaction with `api_secret_key` is needed by the attacker.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop to the verified body — e.g., include the header fields in the canonical signable string, or require host applications to cross-check `request.shop` against a shop that is known to have an active session/installation before trusting it. At minimum, update `to_signable_string` so the shop-domain header cannot be swapped independently of the signed body, and update `docs/usage/webhooks.md` to clarify that only body integrity, not sender identity, is verified by `process`.

### Proof of Concept
1. Malicious merchant `attacker.myshopify.com` installs the app and triggers a webhook with body `B` for a topic they control the content of (or captures any legitimately delivered webhook with a known/reproducible body).
2. Attacker computes/observes the valid `hmac-sha256` header `H = HMAC_SHA256(api_secret_key, B)` for that request (the same secret is shared across all shops of that app).
3. Attacker crafts a new HTTP POST to the app's public webhook endpoint with:
   - body = `B`
   - `x-shopify-hmac-sha256` = `H`
   - `x-shopify-shop-domain` = `victim-shop.myshopify.com`
   - `x-shopify-topic` = original topic
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`. [6](#0-5) 
5. The handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and processes `B` as if it were sent by `victim-shop`, even though `victim-shop` never sent this request.
