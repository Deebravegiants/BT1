### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on otherwise validly-signed webhook deliveries - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value that is forwarded to the app's handler is read from an HTTP header that is never included in that signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is derived from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header: [1](#0-0) 

`shop` is read independently from the `shop-domain` header, with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body and then hands `request.shop` straight to the app's handler as the tenant identifier: [3](#0-2) 

The identity binding that should hold is: `hmac == HMAC(secret, body) AND shop == the shop that produced body`. In this implementation only the first half is checked; `shop` is accepted from an unauthenticated header. Because the webhook signing secret (`Context.api_secret_key`, i.e. the app's `client_secret`) is the same for every shop/tenant that installs the app, any party who can obtain one validly-signed webhook delivery (e.g., by installing the app on their own shop/dev store, which any unprivileged internet user can typically do for a public app) can replay that exact `body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header value. `HmacValidator.validate` will still pass, because it checks `compute_signature(verifiable_query.to_signable_string, secret) == hmac`, and `to_signable_string` never includes the header: [4](#0-3) 

The result is a `WebhookMetadata` record delivered to the app's handler where `shop` (attacker-chosen victim shop) is decoupled from `body` (attacker's own, validly-signed content).

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for webhook processing: an attacker with no access to any victim's credentials or access tokens can cause the host application to process attacker-controlled webhook payloads (e.g., `shop/redact`, `customers/redact`, `app/uninstalled`, `shop/update`, etc.) under an arbitrary victim shop's identity. Depending on how the host app's handler trusts `shop` (most integrations key their persistence/session lookup and data-processing paths by this exact field), this can lead to cross-tenant data corruption, spurious app deauthorization/uninstall side effects, or injection of forged shop-scoped events. This falls under the "cross-tenant access" impact category since the identity used to select/act on tenant data is authenticated only via the body signature, while the tenant discriminator (`shop`) itself is not covered.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to have at least one genuine account/dev-store installation of the target app so they can capture a validly HMAC-signed webhook delivery from Shopify (`client_secret` is shared across all shops of the same app, and HMAC is computed only over body content, independent of shop). No secret, token, or privileged access is required beyond a normal, unprivileged install that any internet user can typically perform for a public app; the "signed body" material is trivially obtainable via the attacker's own store's webhook deliveries. The main constraint on impact is what the host application does with `shop`/`body` once it reaches the handler, which is outside this gem, but the gem provides no protection against the spoofed binding itself.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) header value as part of the signable payload verified by `Utils::HmacValidator`, or independently verify that the shop the webhook claims via the header is authenticated against the same secret/session used for that shop, rather than trusting the header value in `WebhookMetadata` purely because the body's HMAC checks out. At minimum, document that `request.shop` is not authenticated and must be cross-checked by the host app against its own stored shop record before use.

### Proof of Concept
1. Attacker installs the target (public) app on their own dev/test shop `attacker.myshopify.com`. Shopify delivers a legitimately-signed webhook, e.g.:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid HMAC over body B>`
   - Body: `B`
2. Attacker replays the exact same `body: B` and `x-shopify-hmac-sha256` value to the target app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new` parses headers/body successfully; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches the replayed signature — validation succeeds because `to_signable_string` never included the shop header.
4. The handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim.myshopify.com", body: parsed(B), ...)`, and any host-application logic keyed on `shop` (e.g., marking the victim's app installation deauthorized, deleting victim data on `shop/redact`) executes against the victim tenant using attacker-controlled body content.
