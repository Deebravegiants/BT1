### Title
`begin_auth` builds `auth_route` from an unsanitized `shop` string, allowing CRLF/host injection into the redirect URL - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`Oauth.begin_auth` interpolates the caller-supplied `shop` value directly into `auth_base_uri` (`"https://#{shop}/admin"`) without ever calling `Utils::ShopValidator.sanitize!`, unlike every other OAuth entry point in this gem (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`). Because the resulting `auth_route` is documented and intended to be placed directly into a `Location` response header by the host app, any control characters or extra host content in `shop` propagate unsanitized into that header/URL.

### Finding Description
The broken binding: `shop` bytes accepted by `begin_auth` == `shop` bytes safe to place in a single URL host component / HTTP header value. This does not hold.

Code path:
- [1](#0-0)  takes `shop:` directly from the caller with no validation, builds `query_string`, and computes `auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"`.
- [2](#0-1)  returns `"https://#{shop}/admin"` (or a dev-server variant) with plain string interpolation - no escaping, no call to `Utils::ShopValidator.sanitize!`.
- By contrast, `sanitize!` in [3](#0-2)  is used elsewhere in the gem (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`) to constrain `shop` to a trusted Shopify domain, but `oauth.rb`'s `begin_auth` never calls it.
- The gem's own documentation instructs host apps to take `shop` straight from an inbound header and hand the resulting `auth_route` to `response.set_header("Location", ...)`: [4](#0-3) .

Attacker request: An unauthenticated visitor hitting the app's login route supplies a crafted `shop` value, e.g. `shop=real-shop.myshopify.com\r\nSet-Cookie: hijacked=1` (via whatever header/param the host app forwards into `begin_auth`, exactly as shown in the gem's own documented usage pattern). Because `begin_auth` performs no sanitization, `auth_route` returned to the host app contains the raw CRLF sequence embedded in the string. When the host app follows this gem's documented pattern and puts that string into a response header, the injected bytes are carried along whatever the underlying HTTP layer permits (some Rack/webserver stacks reject raw CRLF in header values, but that protection is external to this gem and not guaranteed for all deployment stacks or for other uses of `auth_route`, e.g. rendering it in an HTML template as a redirect target).

Existing guards do not intervene: `Context.setup?` and `Context.private?` checks only gate whether OAuth is configured/allowed, not the content of `shop`; there is no `state`/HMAC/JWT check performed at this stage since `begin_auth` runs before any callback is received; `ShopValidator.sanitize!` exists in the codebase but is simply never invoked from this method.

### Impact Explanation
An attacker can inject arbitrary control characters/content into the URL string that this gem returns as `auth_route`, which is the value the gem's own documentation instructs developers to place directly into a `Location` header. This enables response header/URL injection (redirect target manipulation, potential cookie injection on stacks that don't independently reject CRLF) targeting any victim who is induced to hit the crafted login URL - a per-request, repeatable issue affecting any shop value the attacker supplies, i.e. matching the High severity category (response header/URL injection enabling redirect/cookie manipulation for the victim's browser).

### Likelihood Explanation
Preconditions: the host app must pass through attacker-influenced `shop` input to `begin_auth` and then propagate `auth_route` into a header/redirect, which is exactly the pattern shown in this gem's own docs. No credentials, secrets, or privileged access are needed - only the ability to control the `shop` parameter of an unauthenticated login request, which per the threat model is available to any internet user.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop, myshopify_domain: ShopifyAPI::Context.myshopify_domain)` (or equivalent) at the top of `begin_auth`, before it is used in `auth_base_uri`, exactly as is already done in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, and raise `Errors::InvalidShopError` for any value that isn't a trusted Shopify domain.

### Proof of Concept
```ruby
# test/auth/oauth_test.rb (new test)
def test_begin_auth_rejects_or_sanitizes_crlf_in_shop
  malicious_shop = "real-shop.myshopify.com\r\nSet-Cookie: hijacked=1"

  result = ShopifyAPI::Auth::Oauth.begin_auth(shop: malicious_shop, redirect_path: "/cb")

  # Binding under test: shop accepted by begin_auth == shop safe to embed in Location header/URL host.
  refute_match(/\r\n/, result[:auth_route],
    "auth_route must not contain raw CRLF sequences from unsanitized shop input")
end
```
Running this against the current code fails: `result[:auth_route]` contains the literal `\r\n` sequence unsanitized, confirming the gem returns attacker-controlled control characters embedded in the value it documents for direct use in a `Location` header.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
