### Title
Wrapped bridge locks nominal `params.amount` instead of actual tokens received, allowing fee-on-transfer/deflationary underlying tokens to drain the destination-side pool - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` transfers the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` but never verifies how many tokens the contract actually received. It then unconditionally encodes `params.amount` into the cross-chain `Message` that is dispatched to the destination chain, where `onAccept()` unlocks/transfers exactly that amount from the destination-side underlying pool. This is the exact bug class described in the external report (`LSSVMPairERC20._validateTokenInput`): trusting the requested transfer amount instead of the actually-received balance delta.

### Finding Description
In `send()`: [1](#0-0) 

The non-WETH branch calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and then immediately builds the dispatch body with `params.amount`, with no balance-before/balance-after check: [2](#0-1) 

On the destination chain, `onAccept()` trusts `message.amount` and transfers/unlocks that exact amount from its own locked underlying balance: [3](#0-2) 

If `_underlying` is a fee-on-transfer, deflationary, or rebasing ERC20 (a `Config.underlying` chosen at deployment by the wrapper's owner, but the pool is shared across all users of that deployment), the source-side wrapper contract will hold strictly less than `params.amount` after the `safeTransferFrom` call, yet the message committed to Hyperbridge still promises the full nominal `params.amount`. Every `send()` therefore creates a deficit between what is actually escrowed on the source chain and what the destination side pays out, progressively draining the destination pool's real token balance — an unbacked-mint/permanent-freezing-of-funds outcome (subsequent, legitimate users on the destination side cannot redeem because the pool has already been over-paid out).

This is the same root cause identified in the report: two token-intake paths exist in the codebase, `IntentGatewayV2.placeOrder()` explicitly measures `balanceOf` before/after transfers and mutates `order.inputs[i].amount` to the actual received value for exactly this reason (see the fee-on-transfer handling and tests), but `WrappedHyperFungibleToken.send()` (and its upgradeable counterpart) does not apply the same check. [4](#0-3) [5](#0-4) 

### Impact Explanation
Any deployment of `WrappedHyperFungibleToken` (or `WrappedHyperFungibleTokenUpgradeable`) that wraps a non-standard ERC20 (fee-on-transfer, deflationary burn, or rebasing token) allows a caller to dispatch a cross-chain message that overstates the amount actually locked. The destination-side `onAccept()` will pay out the overstated amount from its own locked balance, which is a direct loss of funds for the bridge/pool (theft/permanent freezing of other users' funds), matching the "unbacked mint" / "concrete theft of funds" impact category.

### Likelihood Explanation
Exploitability depends on the wrapper being configured for a non-standard-behaving ERC20. Since `configure()` sets `_underlying` at deployment/owner discretion and is a normal supported feature (not a misconfiguration/malicious-admin scenario — the contract is explicitly designed to wrap "existing ERC20 tokens" generically), any unprivileged user calling `send()` on such a deployment can trigger the shortfall on every single call, with no special permissions required. This is a routine, reachable path from a single transaction.

### Recommendation
In `send()` (and the upgradeable variant), measure `IERC20(_underlying).balanceOf(address(this))` before and after the `safeTransferFrom` call and use the actual received delta (not `params.amount`) when building the dispatched `Message`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder()`.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` with `configure()` pointing `_underlying` to a fee-on-transfer ERC20 (e.g., 1% burn on transfer).
2. User calls `send({amount: 1000e18, ...})`. `safeTransferFrom` moves only 990e18 into the wrapper contract, but `_buildDispatchPost` encodes `amount: 1000e18` in the `Message` and dispatches it.
3. On the destination chain, `onAccept()` decodes `message.amount = 1000e18` and calls `IERC20(_underlying).safeTransfer(beneficiary, 1000e18)`, paying out 10e18 more than was ever escrowed on the source chain.
4. Repeating this drains the destination-side locked-token pool relative to what was actually deposited, eventually causing later legitimate transfers to fail or be under-collateralized (as demonstrated by the equivalent fee-on-transfer test harness already present for `IntentGatewayV2`, e.g. `FeeOnTransferToken` and `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, which shows the correct received-amount handling that is missing here).     function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

/// @dev ERC20 with a configurable transfer fee (in basis points).
contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
