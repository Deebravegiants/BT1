### Title
Protocol fee rounds down to zero on small `placeOrder` inputs, letting users split orders to avoid the intent protocol fee - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` deducts a protocol fee from each order input using floor-division basis-point arithmetic, mirroring the exact rounding-down defect described in the external report's `HoneyQueen::computeFees`. Because the division truncates toward zero, any input amount small enough relative to the configured `protocolFeeBps` produces a `protocolFee` of exactly `0`, letting an unprivileged user dispatch a full-value transfer as a sequence of fee-free micro-orders.

### Finding Description
When a user calls `placeOrder`, the contract computes the protocol fee per input token as:

```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps) / 10_000;
uint256 reducedAmount = originalAmount - protocolFee;
``` [1](#0-0) 

This is integer (floor) division. For any `originalAmount` such that `originalAmount * protocolFeeBps < 10_000`, `protocolFee` evaluates to `0` and the full amount is escrowed with no fee deducted, exactly the rounding-down class described in the report ( `49 * 200 / 10000 = 0` ). Whenever `protocolFee == 0`, no `DustCollected` event is emitted and the protocol receives nothing for that order:

```solidity
if (protocolFee > 0) emit DustCollected(token, protocolFee);
``` [2](#0-1) 

The same pattern is duplicated verbatim in the Tron variant of the contract. [3](#0-2) 

An unprivileged user — anyone calling `placeOrder` (a directly reachable, single-transaction entry point into the intents escrow) — can therefore split a large transfer into many small orders, each individually falling below the fee-rounding threshold, and have the entire value delivered to a solver while paying zero protocol fee across the whole set of orders.

### Impact Explanation
Impact is proportional to token value/decimals and fee configuration: for low-bps fees (deployments currently run 5–30 bps per the docs) the zero-fee threshold is `10_000 / protocolFeeBps` units of the token's smallest denomination. For high-value, low-decimal tokens (or fee configurations with small bps), this threshold can represent a non-trivial dollar amount per order, and repeated dust-sized orders let a user permanently avoid paying the protocol its designed revenue on that value — a direct, sustained loss of protocol fee revenue, the same impact class the external report rates Medium.

### Likelihood Explanation
Likelihood is Medium: exploitation requires no special privilege, only that the attacker place many orders below the rounding threshold, and gas costs must be weighed against the fee saved (viable mainly for high-value/low-decimal tokens or higher-bps fee configurations, as the external report notes for the analogous case).

### Recommendation
Round the protocol fee calculation up (ceiling division) rather than down, or enforce a minimum non-zero fee/minimum order size so that `protocolFee` can never be `0` for a non-zero `originalAmount`, e.g.:
```solidity
uint256 protocolFee = (originalAmount * protocolFeeBps + 9_999) / 10_000;
```
applied consistently in both `evm/src/apps/IntentGatewayV2.sol` and `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Deploy `IntentGatewayV2` with `protocolFeeBps = 5` (0.05%, matching current mainnet deployments per docs).
2. The zero-fee threshold is `amount < 10_000 / 5 = 2_000` (token base units).
3. Call `placeOrder` repeatedly with `order.inputs[0].amount = 1_999` (or any amount under the threshold) for a token with few decimals/high unit value; each call computes `protocolFee = (1_999 * 5) / 10_000 = 0`.
4. No `DustCollected` event fires and the full `1_999` is escrowed and eventually paid out to the solver via `fillOrder`, exactly as demonstrated by the existing protocol-fee tests that assert `expectedFee = (inputAmount * PROTOCOL_FEE_BPS) / 10_000` [4](#0-3)  — repeating with `inputAmount` below the rounding threshold instead of `1000 * 1e6` yields `expectedFee == 0` for every call, letting the full transfer amount go through fee-free when split across enough orders.
