### Title
BEEFY consensus proof accepts duplicate authority signatures to satisfy the supermajority threshold, allowing forged consensus state updates - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
The BEEFY consensus verifier counts raw signature entries to determine whether a commitment meets the 2/3+1 supermajority threshold, but never deduplicates by authority index. A relayer can submit a `ConsensusMessage` whose `signed_commitment.signatures` vector repeats a single, genuinely valid signature multiple times. Each duplicate independently passes ECDSA recovery (it is the same valid signature recovering to the same authority), inflating `signatures_length` past the supermajority threshold while the number of *distinct* signing authorities can be far below 2/3 of the authority set — in the extreme, just one real signer.

### Finding Description
`verify_mmr_update_proof` computes the participation count purely from the length of the raw signature list and passes it unchanged to the threshold check: [1](#0-0) 

The loop that builds `authority_leaves`/`authority_indices` for the subsequent merkle multi-proof check does not deduplicate `sig.index` either — it simply pushes one entry per signature, duplicates included: [2](#0-1) 

`check_participation_threshold` only compares a raw count to the authority-set size, with no notion of "distinct signer": [3](#0-2) 

Because `commitment_hash` is bound to the specific commitment being verified, an attacker cannot reuse signatures across different commitments — the recovered address always ties back to the same real authority. But nothing prevents the same `(index, signature)` pair from appearing multiple times in the *same* signature vector for the *same* commitment. Each repetition recovers successfully and is counted, so `signatures_length` (and the merkle multi-proof leaf/index arrays, which merely re-verify the same true leaf against the authority-set commitment tree) can be inflated arbitrarily from as few as one genuinely signing authority, bypassing the intended "supermajority of distinct authorities" security assumption entirely.

This is the same root-cause class as the reported GnuTLS DTLS advisory: a counting/ordering routine that is not resilient to duplicate identifiers (sequence numbers there, authority indices here), allowing an attacker to manipulate the accounting logic into an incorrect, exploitable state.

### Impact Explanation
This breaks the fundamental security guarantee of the BEEFY light client: that a new MMR root / authority-set rotation is accepted only when signed by a real supermajority of the relay chain's authorities. With duplicate-signature inflation, an attacker who obtains even a single valid signature over an attacker-favorable (or merely premature) commitment can get `pallet-ismp`'s consensus handler to accept it as finalized, updating `trusted_state.latest_beefy_height` and potentially rotating `current_authorities`/`next_authorities`. This unsound state commitment can then be used to forge state/membership proofs for cross-chain messages, resulting in forged message delivery and unauthorized application actions across all chains that rely on this BEEFY consensus client for message verification — the strongest reachable impact in the specified scope (unsound state commitment / forged message delivery).

### Likelihood Explanation
The consensus message is submitted as an unsigned extrinsic by any relayer and reaches this verification path without additional gating (validated only by `validate_unsigned`/`pallet-ismp`'s message dispatch). No special privileges, governance, or malicious-node assumptions are required — a normal relayer merely needs to obtain one legitimate authority signature (e.g., by observing gossip, or being a validator themselves) and repeat it in the signatures vector before submission.

### Recommendation
Deduplicate `mmr.signed_commitment.signatures` by `sig.index` (e.g., collect into a `BTreeSet`/`BTreeMap` keyed by index) before computing `signatures_length` and before building `authority_leaves`/`authority_indices`, and reject the proof if any duplicate indices are present. The participation threshold must be computed over the count of distinct authority indices, not the raw signature count.

### Proof of Concept
1. Wait for (or obtain) one valid BEEFY signature `sig` from a single authority over a commitment `C` (via normal relay-chain gossip, since this is public information any relayer can capture).
2. Construct a `ConsensusMessage`/`MmrProof` whose `signed_commitment.signatures` vector contains `sig` repeated `k` times, where `k` is chosen so that `k >= (2 * total_authorities) / 3 + 1`.
3. Submit this as an unsigned `Message::Consensus` extrinsic to `pallet-ismp`.
4. `verify_mmr_update_proof` recovers the same valid authority address `k` times, `signatures_length = k` passes `check_participation_threshold`, and the merkle multi-proof re-verifies the same true leaf `k` times successfully — the forged/insufficiently-attested commitment is accepted as finalized despite only one real authority having signed it.
