### Title
`payRelayFees` fallback lets a replayed Emporium signature drain the signer's wallet in an arbitrary, unsigned `feeToken` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.payRelayFees`'s fallback branch (`!foundToken && feeStructure.flatFee != 0`) pulls `feeStructure.flatFee` of `feeStructure.feeToken` from `stack.signerAddress`'s wallet whenever `signerAddress != address(0)`, with no requirement that `feeToken` relate to the tokens/deltas actually declared for the action. Because the EIP-712 hash signed in `verifyWallet` only commits to `emporiumMessage`, the hash of `ops`, `maxFee`, and `deadline`, an attacker who obtains any validly signed `EmporiumStack` can resubmit it with attacker-chosen `circomData.erc20TokenAddresses`, `deltaAmountChanges`, and `circomData.feeStructure` (including an arbitrary `feeToken`), forcing this fallback to pull `flatFee` of that unrelated token straight out of the victim's `HinkalWallet`.

### Finding Description
The claimed equality — "tokens leaving an action == `-deltaAmountChanges` it received" — is broken by design in the fallback path: `payRelay(circomData.relay, signerAddress, feeStructure.flatFee, feeStructure.feeToken)` executes at [1](#0-0)  purely based on `foundToken` being false and `signerAddress != address(0)`, with `feeToken`/`flatFee` having zero relation to any entry in `erc20TokenAddresses`/`deltaAmountChanges`.

Critically, `verifyWallet` only binds the signature to `emporiumMessage`, the op-list hash, `maxFee`, and `deadline`: [2](#0-1) . It never includes `circomData.feeStructure`, `circomData.erc20TokenAddresses`, or `deltaAmountChanges` in the signed payload, only checking `feeStructure.flatFee > stack.maxFee` as a numeric cap: [3](#0-2) . This means the same valid signature over a given `emporiumMessage`/`ops`/`maxFee`/`deadline` tuple authorizes *any* `feeToken` chosen by whoever submits the call, as long as `flatFee <= maxFee` (a bare magnitude, not tied to any specific asset).

`usedMessages[emporiumMessage]` is single-use, so the signature can be submitted only once [4](#0-3) , but nothing stops an attacker from front-running/harvesting a not-yet-submitted signed stack (e.g., from mempool, a relay, or a UI that broadcasts the signature before executing) and calling `runAction` themselves with a `circomData` whose `erc20TokenAddresses` are deliberately unrelated to the real fee token and whose `feeStructure.feeToken` is set to any ERC20 the victim wallet holds.

On the wallet side, `doSendToRelay` is `onlyEmporium`-gated but performs no validation of `erc20TokenAddress` beyond that gate [5](#0-4) , so it will happily transfer whatever token Emporium instructs it to.

None of the existing guards catch this: `verifyWallet`'s signature check only verifies the signer controls `signerAddress` for the signed `ops`/`maxFee`/`deadline`, not the token accounting; the `foundToken` loop only reasons over `erc20TokenAddresses` supplied by the caller, which is exactly the attacker-controlled field; and the `require(signerAddress != address(0), ...)` check is a red herring that doesn't validate the token relationship at all.

### Impact Explanation
An attacker who intercepts/harvests any legitimately signed `EmporiumStack` (regardless of what operations it authorizes) can drain `flatFee` of an arbitrary ERC20 token from the signer's `HinkalWallet` to a relay address of the attacker's choosing (or to themselves if they control the relay), with no relationship to the declared token/amount set of the action. This is theft of shielded/in-flight user funds via the wallet, executing an asset movement the wallet owner never authorized for that specific token — a Critical-severity finding per the stated categories ("direct theft of shielded or in-flight user funds," "executing calls or moving assets a wallet owner or prover never authorised"). It is repeatable once per harvested signature (each `emporiumMessage` is single-use, but an attacker can harvest many).

### Likelihood Explanation
Preconditions: attacker needs access to a validly signed `EmporiumStack` before it's consumed (e.g., observing pending transactions/relayer traffic, or a relay that leaks signed payloads) — feasible since these payloads must be transmitted to a relay/submitter to be executed. Attacker cost is low: no privileged role required, only the ability to call `runAction` as `onlyAllowedRecipient` (presumably reachable via the normal relay/entry flow) and to craft `circomData` fields, both explicitly allowed to unprivileged actors per the threat model. The only constraint is `flatFee <= maxFee`, a numeric bound the legitimate signer already agreed to, so any `flatFee` within that bound and any token can be targeted.

### Recommendation
Bind `circomData.feeStructure` (at minimum `feeToken`, `flatFee`, `variableRate`) and the token/delta arrays relevant to fee computation into the EIP-712 signed payload verified in `verifyWallet`, so a signature cannot be replayed against a different fee token or unrelated token set. Alternatively, require that `feeStructure.feeToken` be present among `circomData.erc20TokenAddresses` even in the `signerAddress != address(0)` fallback branch, removing the unconditional out-of-band pull from the wallet.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, `HinkalWallet` for a victim signer, and two ERC20 tokens: `TokenA` (intended fee token per victim's original signed intent) and `TokenB` (unrelated dust token, held by the victim's wallet in some balance).
2. Have the victim sign an `EmporiumStack` (`ops`, `maxFee = X`, `deadline`) via EIP-712 for `emporiumMessage = M`, intending it to be used with `erc20TokenAddresses = [TokenA]`, `deltaAmountChanges = [-Y]`, `feeStructure.feeToken = TokenA`.
3. Before that intended call lands, attacker (not the signer, holds no keys) calls `runAction` directly with the *same* signed `stack` (`emporiumMessage = M`, same ops/maxFee/deadline/v/r/s) but crafted `circomData.erc20TokenAddresses = [TokenB]`, `deltaAmountChanges = [0]`, `circomData.feeStructure.feeToken = TokenB`, `flatFee <= X`.
4. Assert: `verifyWallet` passes (signature still recovers correctly since `feeStructure`/token arrays aren't part of the signed hash), `foundToken` stays `false` (TokenB not in a matching position with negative delta, or trivially unrelated), fallback branch fires, `doSendToRelay` is called on the victim's wallet for `TokenB`.
5. Assert `TokenB.balanceOf(victimWallet)` drops by `flatFee` and `TokenB.balanceOf(relay)` increases by `flatFee`, while `erc20TokenAddresses`/`deltaAmountChanges` never reference `TokenB` as part of any positive fee-bearing entry — demonstrating the broken equality and unauthorized fund movement.
