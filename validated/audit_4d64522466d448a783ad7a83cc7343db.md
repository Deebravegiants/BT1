### Title
`WeightFeeHandler::on_executed` skips the per-message weight fee whenever a delivered message's `signer` cannot be decoded as a valid Sr25519 signature, letting messages execute for free - (File: `modules/pallets/ismp/src/fee_handler.rs`)

### Summary
This is the same bug class as the Carousel deposit-fee bypass: two paths reach the same end state (a message is fully executed and its effects applied), but only one of those paths actually charges the fee. In Carousel, `mintDepositInQueue` bypassed the deposit fee that `_deposit` charged. In `pallet-ismp`'s `WeightFeeHandler`, the fee is charged only if the fee handler can independently re-derive an Sr25519 signer from the message's `signer` bytes; if it cannot (wrong signature scheme, malformed encoding, or any decode/verify failure), the fee silently drops to zero while the message itself was already accepted and fully processed.

### Finding Description
`WeightFeeHandler::on_executed` is invoked by `pallet-ismp` after a batch of messages has already been successfully executed via `handle_unsigned` [1](#0-0) . For each message it computes a weight-based fee and then tries to recover the paying account by decoding `msg.signer` strictly as the `Signature::Sr25519` variant and calling `verify_and_get_sr25519_pubkey`: [2](#0-1) 

`verify_and_get_sr25519_pubkey` explicitly rejects any non-Sr25519 signature variant: [3](#0-2) 

If `Signature::decode` fails, or the enclosed signature is `Signature::Evm`/`Signature::Ed25519`, or the Sr25519 verification simply fails, `originator` becomes `None`, and the transfer step is skipped entirely: [4](#0-3) 

Crucially, the message has already been executed successfully by this point — `on_executed` is a post-execution accounting hook, not a gate on whether the message is valid or processed. Message validity/inclusion is governed by proof verification in `handle_unsigned`, not by whether `signer` is a well-formed Sr25519 signature usable for fee attribution. This means a relayer submitting a batch can encode `signer` with a scheme other than Sr25519 (or malformed bytes) and still have the message processed and finalized, while completely avoiding the weight-based fee that the runtime intends to charge.

This mirrors the Carousel report precisely: the fee-charging logic is coupled to a side-channel (deposit fee tied to being in the "direct deposit" branch; here, the fee tied to being able to decode a specific signature variant) rather than to the actual state transition that always happens (shares are minted; the message is executed). An attacker who controls how the message is submitted can choose the path (or malformed encoding) that skips the fee check while still getting the underlying operation performed.

### Impact Explanation
This falls under "relayer fee and reward accounting" in scope. The protocol loses expected weight-based fee revenue on `pallet-ismp` deployments configured with `WeightFeeHandler` and `POLICY = true`, and any message submitter can bypass the fee entirely by controlling the `signer` field's encoding/scheme, denying the treasury its due income on otherwise successfully processed cross-chain messages. This is a Medium-severity fee/reward accounting flaw: no funds are stolen from users, but the fee mechanism meant to charge originators for processing weight can be trivially and permanently bypassed by any unprivileged submitter of ISMP messages.

### Likelihood Explanation
High likelihood of being exercised: any account submitting an unsigned `handle_unsigned` message batch controls the `signer` bytes on the message. There's no requirement in `handle_unsigned`/proof-verification path that ties `signer` scheme to Sr25519, so submitting a message with `Signature::Evm` or corrupted signer bytes is a routine choice, not an exotic edge case, and does not affect message validity/execution — only fee attribution.

### Recommendation
Decouple message validity/finality from fee attribution correctness: either (a) require the `signer` field to be a valid, verifiable signature (of any supported scheme) as a precondition for `handle_unsigned` acceptance, so an unattributable signer can never reach `on_executed`, or (b) fall back to charging a well-known default payer (e.g., treat unattributable-signer messages as if signed by a bonded/self-relayer address, or reject the batch) rather than silently skipping the fee when the originator can't be recovered. At minimum, add an `Err`/reject path in `WeightFeeHandler::on_executed` for messages whose signer cannot be resolved to an account, instead of silently `continue`-ing past the fee charge.

### Proof of Concept
1. A relayer submits an unsigned extrinsic `handle_unsigned` with a `Message::Request` (or `Message::Response`) whose message-level `signer` field encodes `Signature::Evm { address, signature }` (or arbitrary bytes that fail `Signature::decode`), instead of `Signature::Sr25519`.
2. `handle_unsigned` validates state proofs for the request/response content (unrelated to `signer` scheme) and executes the message, updating all downstream commitments/receipts as normal.
3. `WeightFeeHandler::on_executed` runs afterward: `Signature::decode` on `msg.signer` either fails or yields a non-Sr25519 variant, so `verify_and_get_sr25519_pubkey` errors out and `originator` is `None`.
4. The `if let Some(originator_bytes) = originator` branch is skipped — no `C::transfer` call occurs, and no fee is deducted from anyone — while the message has been fully and successfully processed.
5. Repeated across every message in every batch, this fully and permanently bypasses the weight-based fee for any submitter willing to set `signer` to a non-Sr25519/malformed value, at zero cost and with no detectable failure (batch still returns `Ok(...)`).
