### Title
Webhook shop-domain header is trusted for tenant attribution without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, but the `shop` value that is forwarded to the app's handler (and used to attribute the payload to a specific merchant/tenant) is taken from an unsigned HTTP header.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor, by contrast, is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the signed payload: [2](#0-1) .

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)` — which, per `HmacValidator#validate_signature`, computes `HMAC(secret, request.to_signable_string)` (i.e., HMAC over body only) and compares it against the `hmac` header — and then immediately builds a `WebhookMetadata` object using `request.shop`, `request.topic`, etc., handing them to the app's handler unauthenticated: [3](#0-2) [4](#0-3) .

The identity binding that should hold is:
`shop asserted in signed payload == shop attributed to the webhook by the handler`

Because `shop` (and `topic`, `webhook_id`, `api_version`) sit entirely outside `to_signable_string`, this equality is never enforced by the gem. Any request whose body+HMAC pair is valid for the app's shared `api_secret_key` will pass validation regardless of which shop-domain header accompanies it. Since the `api_secret_key` is shared across all shops that install the same app, a user who has legitimately installed the app on their own store receives a real webhook (body + valid HMAC) from Shopify. That same body/HMAC pair remains valid if replayed to the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop's domain — `Registry.process` will still accept it and hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant-identity binding that the rest of the gem relies on for session/access-token lookups (`shop` is the session key elsewhere in the library, e.g. `Utils::SessionUtils.offline_session_id(shop)` / `jwt_session_id(shop, ...)`). A handler that uses `data.shop` to select which merchant's stored access token/session to act on, or to attribute incoming order/customer/GDPR payloads to a merchant record, can be tricked into cross-tenant data injection or misattribution using only a webhook that the attacker legitimately received for their own store. This qualifies as cross-tenant access under the stated Critical impact category.

### Likelihood Explanation
Exploitation requires only that the attacker have (or previously had) their own real, active installation of the target app — an "unprivileged internet user" capability, not a privileged credential, TLS interception, or leaked secret. No knowledge of `api_secret_key` is needed since the attacker reuses a genuine, previously-issued HMAC/body pair rather than forging one. The only additional requirement is that the host application trusts `WebhookMetadata#shop` for tenant attribution, which is exactly the field and pattern this gem exposes to handlers as authoritative webhook metadata.

### Recommendation
Bind `shop` (and ideally `topic`/`api_version`) into the HMAC-covered signable string, or otherwise cryptographically verify that the `shop-domain` header matches the shop the request was actually delivered for (e.g., by cross-checking against Shopify's known-good IP ranges or requiring correlation with an active, verified session/webhook-id record) before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used alone to select which merchant's credentials/data to act upon.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Shopify delivers a real webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body B computed with the app's shared api_secret_key>`, and body `B`.
3. Attacker captures this raw body `B` and HMAC value, then sends a new HTTP request to the same webhook endpoint with the same body `B` and same HMAC header, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)`, which still matches, since `shop` is not part of `to_signable_string`.
5. `Registry.process` proceeds to call the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the host application to process/store data `B` as if it originated from `victim-shop.myshopify.com`.

Note: I was unable to fully inspect `lib/shopify_api/webhooks/webhook_handler.rb` and `WebhookMetadata`'s exact field list (file not indexed under that path), so the precise shape of the metadata object handed to handlers is inferred from `registry.rb`'s call site rather than directly confirmed.
