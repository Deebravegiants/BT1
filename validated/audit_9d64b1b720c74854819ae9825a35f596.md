### Title
Webhook shop identity spoofing via HMAC that covers only the request body, not the `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` value used to identify the tenant is read from the unsigned `shop-domain` header. `Registry.process` trusts the header-derived `shop` after validating only the body's HMAC, so the equality the code implicitly assumes — "HMAC-authenticated payload" == "payload for `request.shop`" — does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)` (which hashes `to_signable_string`, i.e. only the body) and then immediately hands `request.shop` to the registered handler as trusted tenant identity: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` computes `HMAC(secret, to_signable_string)` and secure-compares it to the header HMAC — again, this only proves the *body* bytes are untampered, it says nothing about which shop the body belongs to: [4](#0-3) 

Because the `shop-domain` header is outside the signed content, any two requests with the same body and the same (valid) HMAC will pass validation regardless of what `shop-domain` header accompanies them. An attacker who controls one shop that has legitimately installed the app receives genuinely-signed webhook deliveries for their own shop (signed with the app's real `client_secret` by Shopify). They can capture such a `(body, hmac)` pair and POST it directly to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop that also uses the same app. `Registry.process` will validate the HMAC successfully (since it never touched the header) and dispatch `WebhookMetadata` with `shop: <victim-shop>` — a tenant identity supplied by the attacker but not authenticated — to the app's handler.

This breaks the binding: `shop authenticated (via HMAC) == shop stored/acted on by the handler`. In reality, HMAC validity only proves body integrity for *some* shop that installed the app; it does not prove the body belongs to the shop named in the header.

### Impact Explanation
Downstream app handlers (using `WebhookMetadata#shop`) typically use this value as the tenant key to write/update per-shop state (e.g. update products, mark shop redacted, etc., especially for the mandatory `shop/redact`/`customers/redact`/`customers/data_request` topics, which are dispatched with no additional verification): [5](#0-4) 
An attacker who is a legitimate (even free/trial) merchant of the same app can forge webhook deliveries "as" any other shop, causing the app to apply attacker-supplied webhook content to a victim shop's tenant data — a cross-tenant access/data-integrity issue.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the target app on their own shop (no special privilege), (2) they trigger and capture one legitimate webhook delivery to their own shop, (3) they replay the exact `(body, hmac)` to the app's public webhook endpoint with a different `shop-domain` header naming a different shop. No secrets, tokens, or elevated access are needed — this is reachable by any unprivileged app-installer.

### Recommendation
Bind the shop identity into the authenticated content: either include `shop-domain` (and other trust-relevant headers such as `topic`) in `to_signable_string` used for HMAC verification, or have `Registry.process`/consumers independently verify that `request.shop` corresponds to a shop with a known/active session/installation for this app before trusting it, rejecting mismatches.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook: body `B`, header `x-shopify-hmac-sha256: H` (where `H = Base64(HMAC-SHA256(client_secret, B))`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint with the same `B` and `H`, but header `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers/body: [6](#0-5) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `B` and compares to `H`, both unchanged.
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, believing the (attacker-controlled) body content belongs to `victim-shop`.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
