### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing shop-spoofing on otherwise-valid webhook deliveries - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Registry.process` validates covers only the raw request body. The equality that should hold — `bytes_covered_by_hmac == bytes_the_app_trusts_for_tenant_identity` — is broken: the header carrying `shop` is parsed and handed to the app's webhook handler without ever being part of the signed data.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop` is read straight out of the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed payload: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (i.e., only `@raw_body`) and compares it against `request.hmac` (derived from the `X-Shopify-Hmac-Sha256` header): [4](#0-3) [5](#0-4) 

Because `shop` is not part of `to_signable_string`, the HMAC only proves the body byte-for-byte came from Shopify (using `client_secret`) — it proves nothing about which shop the body is for. `Registry.process` then unconditionally forwards `request.shop` to the app-supplied `WebhookHandler#handle` as trusted tenant metadata: [6](#0-5) 

This matches the bug class in the report exactly: a field that is *acted on* (`shop`, used to attribute the webhook to a tenant) is not covered by the authentication mechanism (HMAC) that is supposed to bind the payload to its source.

### Impact Explanation
This is a **cross-tenant** binding break within the gem's own webhook-verification API surface: the gem itself computes and presents `request.shop` as a verified attribute of an HMAC-validated `Request` object, but the shop value was never authenticated. Any consumer of this library relying on `Registry.process`'s HMAC check plus `WebhookMetadata#shop` (exactly the documented usage pattern) to decide which merchant's data a webhook body belongs to can be made to process/store a legitimate Shopify-signed payload (real, valid HMAC) under an attacker-chosen shop label, since a MITM-less network attacker (or a malicious intermediary/log-replay actor with access to any single valid webhook delivery for shop A) can replay that exact body/HMAC pair while altering the `X-Shopify-Shop-Domain` header to shop B — the signature still validates because it is header-independent. This can lead to cross-tenant data confusion in the calling application.

### Likelihood Explanation
Requires the attacker to control or intercept how headers reach the app's webhook endpoint (e.g., an attacker who can replay a previously observed valid delivery through a different route, or any component that forwards webhook headers/bodies without re-verifying provenance of the shop header specifically). It does not require the `client_secret`, an access token, or a privileged account — it only needs a previously-observed, HMAC-valid `(raw_body, hmac)` pair, which is not treated as secret and is delivered over the public internet on every real webhook call.

### Recommendation
Include `shop` (and ideally `topic`, `api_version`, `webhook_id`) in `to_signable_string`, or otherwise cryptographically bind the shop-domain header to the payload before trusting it — e.g. compute the HMAC over `raw_body + shop-domain header` (matching what Shopify actually signs, per Shopify's webhook verification spec) rather than raw body alone, or require the caller to additionally verify `shop` against a known/authorized shop list before dispatching to `handler.handle`.

### Proof of Concept
1. Capture (or receive) a legitimate Shopify webhook delivery for `shop-a.myshopify.com`: headers `X-Shopify-Hmac-Sha256: <H>`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`, `X-Shopify-Topic: orders/create`, body `B`.
2. Construct a new request to the app's webhook endpoint with the same body `B` and the same `X-Shopify-Hmac-Sha256: <H>`, but with `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. `Webhooks::Request.new(raw_body: B, headers: {...})` builds successfully; `request.shop` returns `shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes HMAC over `request.to_signable_string` == `B` only, matches `<H>`, and returns `true` — because the shop header was never part of the signed material. [1](#0-0) [7](#0-6) 
5. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(..., shop: "shop-b.myshopify.com", body: parsed_body(B), ...))`, attributing shop-a's data to shop-b in the app relying on this gem's verification.
