### Title
Escrow release to an arbitrary `beneficiary` address can permanently revert, freezing escrowed cross-chain funds and blocking Hyperbridge message delivery - (File: `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentsBase._withdraw()` — the function that releases or refunds escrowed native-token input tokens for the Intent Gateway — pays native ETH to an arbitrary, attacker/user-controlled `beneficiary` address using a raw low-level call that reverts the whole transaction if the recipient does not accept ETH. Because this function is invoked from `onAccept()` when Hyperbridge delivers a `RedeemEscrow`/`RefundEscrow` cross-chain settlement message, and the `beneficiary` value baked into that message is immutable once the order/commitment has been created, a beneficiary that cannot receive native ETH turns every delivery attempt of that settlement message into a guaranteed, unrecoverable revert.

### Finding Description
`_sendValue()` is a bare low-level call that bubbles up as a hard revert if the transfer fails: [1](#0-0) 

`_withdraw()` uses this helper to pay out escrowed native-token inputs to `beneficiary`, which is decoded directly from the cross-chain `WithdrawalRequest.beneficiary` field with no restriction on what kind of address it can be: [2](#0-1) 

This function is the terminal step of Hyperbridge's intent settlement flow: on the source chain, the ISMP host delivers a `RedeemEscrow` (solver payout) or `RefundEscrow` (user refund/cancel) POST request via `onAccept()`, which authenticates the sender and then calls `_withdraw()` for the encoded `WithdrawalRequest`: [3](#0-2) [4](#0-3) 

The `beneficiary` in a `RedeemEscrow` message is `msg.sender` of the solver's `fillOrder` call, and the `beneficiary` in a `RefundEscrow`/cancel message is `order.user` — both are fixed, non-upgradable values embedded in the commitment/order and cannot be changed after the fact. If that address is a smart-contract wallet, multisig, or any contract without a working `receive`/`fallback` (or one that intentionally/accidentally reverts, runs out of gas, or is paused), `_sendValue()` reverts every single time `_withdraw()` is invoked for that commitment — there is no fallback to a wrapped-ETH payout or any other recovery mechanism, unlike the ERC-20 branch of the same function which uses `safeTransfer`.

The same pattern also exists in the same-chain fill path (native ETH sent directly to `beneficiary` inline) and in dust sweeping: [5](#0-4) [6](#0-5) 

This is the same root-cause bug class as the referenced report: an arbitrary, unvalidated recipient address for a native-ETH payout with no fallback path (e.g., WETH) if the recipient rejects the transfer.

### Impact Explanation
For cross-chain orders, once a solver has filled the order on the destination chain (delivering output tokens to the user), the *only* way the solver is compensated with the escrowed input tokens on the source chain is via the `RedeemEscrow` message processed through `onAccept -> _withdraw`. If the solver's own address (or, in the refund/cancel case, the order creator's own address) cannot accept a raw ETH transfer, the settlement message can never be successfully delivered — every relay attempt of the same proof reverts identically, because the beneficiary and amount are fixed in the commitment. This satisfies the "route unable to deliver messages" / permanent freezing of escrowed funds criteria: the native-token escrow becomes permanently stuck in the `IntentsBase` contract with no code path able to redirect or recover it (ERC-20 legs of the same order settle fine via `safeTransfer`, but the native-ETH leg is stuck forever). This can also be used to grief legitimate counterparties: a user can construct an order whose native-token output goes to a hostile/broken contract, making it impossible for any solver to ever successfully call `fillOrder`, wasting solver gas and preventing any settlement of that leg.

### Likelihood Explanation
Any account is free to place orders or fill orders using a smart-contract address (AA wallet, multisig, or any contract) as `order.user`, `order.output.beneficiary`, or as `msg.sender` for filling — no code enforces that these addresses can actually accept plain ETH transfers. Contract wallets that reject bare-value calls (e.g., wallets requiring calldata, paused proxies, or wallets that intentionally do not implement `receive`/`fallback`) are common, making accidental triggering realistic, and deliberate griefing (an order creator picking a beneficiary/output address that reverts) is trivial and costs nothing extra to execute.

### Recommendation
Do not let a native-ETH payout revert the entire settlement/withdrawal flow. Use a non-reverting transfer pattern: attempt the raw ETH transfer with a fixed gas stipend and, on failure, wrap the ETH into WETH and deliver that via `safeTransfer` instead (the common "safe transfer" pattern also suggested in the referenced report), or credit the amount to an internal pull-based balance the beneficiary can withdraw later. This should be applied consistently to `_withdraw()`, `_sweepDust()`, and the same-chain native-output payout in `IntrinsicIntents.sol`/`ExtrinsicIntents.sol` so that a broken/malicious beneficiary contract can never permanently block release of escrowed funds or block delivery of a Hyperbridge settlement message.

### Proof of Concept
1. Deploy a `Rejecter` contract with no `receive`/`fallback` function (or one that `revert()`s).
2. As a solver, call `fillOrder` on the destination chain for a cross-chain order whose native-token input leg will pay the solver on the source chain, using `Rejecter` as `msg.sender`'s delivery address is not directly settable, but as order creator, set `order.user` (refund beneficiary) or arrange for `order.output.beneficiary` (fill payout) to be the `Rejecter` contract address for a native-token leg.
3. Trigger `RedeemEscrow`/`RefundEscrow` delivery via Hyperbridge (`onAccept`) or same-chain `fillOrder`.
4. Observe that `_withdraw()`'s `_sendValue(beneficiary, amount)` reverts with `InsufficientNativeToken()` on every attempt — the message can be resubmitted indefinitely by any relayer and will revert identically every time, permanently freezing the escrowed native-token input for that commitment.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
