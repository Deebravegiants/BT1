### Title
Rotating a `BandwidthManager` via `pallet-bandwidth::set_manager` permanently strands treasury fee tokens in the old manager contract - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth::set_manager` overwrites the `BandwidthManager<T>` storage entry for a source chain in a single step, with no step that first sweeps the fee-token treasury accumulated in the currently registered manager contract. Because `dispatch_withdraw` can only address the *currently registered* manager (it looks the address up from the same `BandwidthManager<T>` map), once `set_manager` points governance at a new contract, the fee tokens sitting in the old, now-unregistered `BandwidthManager` contract can never again be reached by governance's withdrawal path.

### Finding Description
`BandwidthManager.purchase()` on the EVM side pulls the fee token from buyers and holds it in the manager contract itself until governance drains it: [1](#0-0) 

Governance withdraws that treasury with `dispatch_withdraw`, which resolves the destination address by looking up the *current* `BandwidthManager<T>` entry for the target chain — it takes no explicit manager address: [2](#0-1) 

`set_manager` (and by extension a manager redeployment) simply overwrites that same storage map entry with the new contract's address, with no check or attempt to first drain the old manager's balance: [3](#0-2) 

The pallet's own storage doc even foreshadows the issue — `BandwidthManager<T>` is described purely as the "authorised purchase contract per source chain," with no notion of preserving access to a displaced address: [4](#0-3) 

The redeployment runbook in the docs confirms the old contract becomes unreachable, but only calls out the *approve allowance* as "dead weight" — it misses that the treasury fee tokens purchase() collected are stranded the same way, because `dispatch_withdraw` has no way to address anything but the newly-registered manager: [5](#0-4) 

This is the same bug class as the reported Arrakis issue: a manager-rotation operation does not first collect/withdraw pending value held by the outgoing manager, and the outgoing manager becomes permanently unreachable for withdrawal once the rotation completes — resulting in fund loss with no remediation path, exactly as `_withdrawManagerBalance` was skipped on manager change in `ArrakisV2Storage.setManager`.

### Impact Explanation
Any fee-token balance sitting in a `BandwidthManager` contract at the moment `set_manager` is called for its chain (whether from normal purchase inflow between withdrawal cycles, or from a chain redeployment as documented) becomes permanently frozen: there is no pallet call that can address a withdrawal to an address other than the one currently stored in `BandwidthManager<T>`. This is a permanent freezing-of-funds bug affecting protocol treasury revenue, satisfying the "concrete... permanent freezing of funds" impact bar. Given that `BandwidthManager` deployments are per-chain and redeployments are an explicitly documented, expected operational event, this is not a hypothetical edge case.

### Likelihood Explanation
This triggers on the routine, documented "Redeploy `BandwidthManager`" governance flow (deploy → `setHost` → `set_manager` → `dispatch_set_tiers`) whenever there is any unwithdrawn purchase revenue in the old manager at rotation time — no attacker or malicious governance is required, just the absence of a "withdraw old manager's balance first" step before/atomically-with `set_manager`. Given purchases can occur continuously and withdrawals are a separate manual/periodic call, non-zero balances at rotation time are the expected common case, not an edge case.

### Recommendation
Before (or atomically with) overwriting `BandwidthManager<T>` in `set_manager`, require/force a `dispatch_withdraw` of the full remaining balance from the currently registered manager, or alternatively let `dispatch_withdraw` accept an explicit manager address (rather than looking it up from the live map) so governance retains the ability to drain orphaned managers after rotation.

### Proof of Concept
1. Governance registers `BandwidthManager` `M1` for `StateMachine::Evm(8453)` via `set_manager(source, M1)`.
2. Buyers call `M1.purchase()` repeatedly; fee tokens accumulate in `M1`'s balance [1](#0-0) .
3. Governance redeploys and calls `set_manager(source, M2)` to rotate to a new manager, per the documented redeployment procedure [5](#0-4) . This overwrites `BandwidthManager::<T>::insert(source, M2)` [6](#0-5) .
4. Governance later calls `dispatch_withdraw(target=Evm(8453), token, beneficiary, amount)` to collect the outstanding treasury. `manager` is resolved as `BandwidthManager::<T>::get(&target)`, which now returns `M2`, not `M1` [7](#0-6) .
5. The withdrawal message is dispatched to `M2`, which holds none of the pre-rotation treasury; `M1`'s balance can never be targeted again through this pallet — the funds are permanently frozen.

			BandwidthManager::<T>::insert(source, manager);

		#[pallet::call_index(5)]
		#[pallet::weight(T::DbWeight::get().writes(1))]
		pub fn dispatch_withdraw(
			origin: OriginFor<T>,
			target: StateMachine,
			token: H160,
			beneficiary: H160,
			amount: U256,
		) -> DispatchResult {
			<T as pallet_ismp::Config>::AdminOrigin::ensure_origin(origin)?;
			let manager = BandwidthManager::<T>::get(&target).ok_or(Error::<T>::UnknownManager)?;

			let payload = Withdrawal {
				token: alloy_primitives::Address::from(token.0),
				beneficiary: alloy_primitives::Address::from(beneficiary.0),
				amount: to_alloy_u256(amount),
			};
			let mut body = vec![ACTION_WITHDRAW];
			body.extend(payload.abi_encode_params());

			let commitment = Self::dispatch_governance(target, manager, body)?;
			Self::deposit_event(Event::WithdrawalDispatched {
				target,
				token,
				beneficiary,
				amount,
				commitment,
			});
			Ok(())
		}
