### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header fields are excluded from HMAC verification, enabling cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` only proves the request body was signed by Shopify with `api_secret_key`. However, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never included in the signed payload. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to build `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle` and is documented/used by integrators to key per-tenant work (e.g., `perform_later(shop_domain: data.shop, ...)`).

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, shop || body)` (i.e., the shop the app acts on must be cryptographically bound to the same bytes that were verified). Instead the binding actually enforced is `hmac == HMAC(secret, body)` while `shop = header["shopify-shop-domain"]` — an unauthenticated, unbound field.

- `Request#to_signable_string` returns `@raw_body` only: [2](#0-1) 
- `Request#shop` is derived purely from a header, never mixed into the signable string: [5](#0-4) 
- `HmacValidator.validate_signature` only ever calls `verifiable_query.to_signable_string`, so it never touches `shop`: [4](#0-3) 
- `Registry.process` validates the HMAC over the body, then immediately trusts `request.shop` for downstream handler dispatch, without ever checking that `shop` is consistent with anything cryptographically verified: [3](#0-2) 

Because Shopify computes the HMAC over the raw JSON body only (this is Shopify's own signing scheme, not something this gem can change), a webhook body for shop A that is captured (e.g., a merchant/developer testing their own webhook endpoint, request logging, browser dev tools, a reverse proxy log, or any other legitimate channel that doesn't require possession of `api_secret_key`) can be replayed to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to shop B. `HmacValidator.validate` still returns `true` (the body and HMAC are unchanged and valid), so `Registry.process` proceeds and calls the handler with `WebhookMetadata#shop == "shop-B"` even though the payload never originated from, nor was ever signed for, shop B.

### Impact Explanation
This breaks the tenant boundary the gem is expected to enforce for the app: any code that keys persistence, authorization, or side effects off `WebhookMetadata#shop` (exactly as the gem's own documentation instructs) can be tricked into attributing another shop's data/webhook body to an attacker-chosen shop domain, resulting in cross-tenant data being recorded, processed, or acted upon under the wrong tenant's identity — a cross-tenant access impact, since no part of the shop's identity is bound to what was HMAC-verified.

### Likelihood Explanation
No possession of `api_secret_key`, access tokens, or any privileged credential is required — only a previously delivered, valid webhook body+HMAC pair (obtainable through the app's own logs, an intermediate proxy, or a webhook the attacker's own shop legitimately received) and the ability to POST to the app's public webhook endpoint with a modified `shopify-shop-domain` header. This is a straightforward unprivileged replay once one legitimate webhook payload/signature pair is available.

### Recommendation
Bind the shop (and any other field used for authorization/routing decisions, such as `topic`) to the HMAC-verified data before trusting it: either require the app-provided `to_signable_string` to include the shop header value combined with the body, or independently verify `request.shop` against a shop already established for that specific `webhook_id`/registration before invoking the handler, rejecting mismatches.

### Proof of Concept
1. Register a webhook handler for topic `orders/create` that calls `perform_later(shop_domain: data.shop, webhook: data.body)` as shown in the gem's own documented usage.
2. Obtain one legitimate webhook delivery for `victim-a.myshopify.com` (its raw body and valid `X-Shopify-Hmac-Sha256` value) via any non-privileged means (e.g., inspect it in your own shop's webhook receiver logs, since Shopify sends the same body/HMAC to whatever endpoint is registered).
3. Send a POST to the app's webhook endpoint with the exact same raw body and `X-Shopify-Hmac-Sha256` header, but replace the `X-Shopify-Shop-Domain` header with `victim-b.myshopify.com`.
4. `Utils::HmacValidator.validate` returns `true` because it only checks `Digest.hexencode(...) == HMAC(secret, raw_body)`, per `lib/shopify_api/utils/hmac_validator.rb` line 30, and `Registry.process` proceeds to call the handler with `data.shop == "victim-b.myshopify.com"` for content that was never issued for that shop, per `lib/shopify_api/webhooks/registry.rb` lines 188-199.
