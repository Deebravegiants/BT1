Audit Report

## Title
CORS Wildcard Origin Bypass via Missing Domain-Boundary Check in Gateway HTTP Server - (File: core/services/gateway/network/httpserver.go)

## Summary
`isAllowedOrigin` in [1](#0-0)  strips the `*.` prefix from a configured wildcard origin and then checks `strings.HasSuffix(originHost, allowedHost)` without requiring a literal `.` boundary before the suffix. As a result, an attacker-controlled domain like `evilethereum.org` satisfies the suffix check for an allowed pattern of `*.ethereum.org`, even though it is not an actual subdomain.

## Finding Description
The wildcard match logic is:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
``` [2](#0-1) 

There is no dot-boundary check, so any `originHost` that ends with the same character sequence as `allowedHost` — not just true subdomains separated by a `.` — passes. This function is called directly from `handleRequest`, which sets `Access-Control-Allow-Origin` to the exact (attacker-supplied) `Origin` value when `isAllowedOrigin` returns true: [3](#0-2) . This is the code path exercised by the internet-facing `UserServerConfig` (`CORSEnabled`, `CORSAllowedOrigins` fields defined in `HTTPServerConfig`): [4](#0-3) .

The existing tests only check that `ethereum.remix.org` (which doesn't end in `ethereum.org`) is rejected, but never test a domain that ends with the allowed suffix without a dot separator (e.g., `evilethereum.org`), so this boundary-bypass class is untested and unfixed.

## Impact Explanation
This is a CWE-668 (Exposure of Resource to Wrong Sphere) class issue, analogous to CVE-2021-33330: a gateway operator who configures a wildcard CORS allowlist (a supported, documented configuration pattern exercised in the test suite) unintentionally grants CORS access to any domain that merely ends with the same substring as the intended base domain. This allows a browser-based attacker who registers a look-alike domain to have a victim's browser send requests to the Gateway's user API and read back the JSON-RPC response cross-origin, defeating the intended origin restriction and enabling gateway request impersonation / cross-user response exposure.

## Likelihood Explanation
Exploitation only requires (1) an operator to enable CORS with a wildcard entry — a legitimate, supported feature demonstrated in the codebase's own test suite — and (2) an attacker to register an inexpensive domain ending in the same suffix (e.g., `evilethereum.org`, `xethereum.org`). No special privileges, node access, or victim credentials are needed beyond luring a browser to the attacker's page; the request itself is unauthenticated at the Gateway's public HTTP endpoint.

## Recommendation
Require a dot boundary in the suffix check:
```go
if strings.HasSuffix(originHost, "."+allowedHost) || originHost == allowedHost {
    return true
}
```
Add regression tests asserting hosts like `evilethereum.org`/`xethereum.org` are rejected against a `*.ethereum.org` allow entry.

## Proof of Concept
1. Configure `UserServerConfig.CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. From a browser hosted at `https://evilethereum.org`, send a `fetch()`/XHR request to the Gateway's `/user` endpoint with header `Origin: https://evilethereum.org`.
3. Observe the server responds with `Access-Control-Allow-Origin: https://evilethereum.org` because `strings.HasSuffix("evilethereum.org", "ethereum.org")` evaluates true in [2](#0-1) , letting the attacker page read the JSON-RPC response cross-origin despite not being a genuine `ethereum.org` subdomain.
4. Add a Go unit test alongside `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go` using origin `https://evilethereum.org` against allowlist `https://*.ethereum.org` and assert `Access-Control-Allow-Origin` is empty (currently it will fail, proving the bug).
