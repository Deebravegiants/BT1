### Title
Webhook `shop-domain` and `topic` headers are trusted for tenant/handler dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC signature validated by `Utils::HmacValidator.validate` never covers the `shop-domain` or `topic` headers. `Registry.process` nonetheless uses these unauthenticated header values (`request.topic`, `request.shop`) to select the webhook handler and to populate `WebhookMetadata` that host applications use as the authoritative tenant identifier for the payload.

### Finding Description
The binding that should hold is: **bytes verified by HMAC == bytes acted on for tenant/topic dispatch**. That binding is broken here.

- `to_signable_string` signs only `@raw_body`: [1](#0-0) 
- `shop` and `topic` are read straight from unauthenticated headers, with no cryptographic tie to the body or its signature: [2](#0-1) 
- `Registry.process` validates only the body's HMAC, then dispatches the handler keyed on `request.topic` and forwards `request.shop` to the handler as trusted tenant metadata: [3](#0-2) 

Because `HmacValidator.validate` only proves that `@raw_body` was signed with the app's secret (`compute_signature(verifiable_query.to_signable_string, secret)`), and `to_signable_string` for a webhook request never includes `shop` or `topic`: [4](#0-3) 

...any request bearing a *previously valid* raw body + HMAC pair (e.g. one an attacker legitimately received for their own shop by installing the same public app) can be replayed with the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers rewritten to arbitrary values, and `Registry.process` will still accept it and dispatch it as if it came from the spoofed shop/topic.

### Impact Explanation
This breaks the identity binding "shop/topic acted upon == shop/topic cryptographically authenticated," letting an attacker who can obtain any one genuine signed webhook (trivially available since any user can install a public embedded app on a development store) forge the `shop-domain` to point at a victim shop and/or the `topic` to a different registered topic. Host applications built on this gem's documented `WebhookMetadata.shop`/`topic` contract will process attacker-controlled events under a victim tenant's identity — a cross-tenant confusion/impersonation primitive (e.g. triggering `app/uninstalled` or `customers/redact` logic attributed to a shop the attacker does not own).

### Likelihood Explanation
Requires only a public app install (no leaked credentials, no privileged account, no TLS interception) and knowledge of the webhook HTTP header format, which is documented. The only "cost" is obtaining one legitimately-signed body from the attacker's own tenant, which is trivial for any unprivileged internet user with a Shopify development store.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` (or equivalent) in the signed/verified byte string, or otherwise cryptographically bind these headers to the signature (e.g. compute HMAC over `headers + body` rather than body alone), so `Registry.process` cannot be made to dispatch a validly-signed body under a spoofed shop or topic.

### Proof of Concept
1. Install the target public app on an attacker-controlled development store; capture one legitimate webhook POST (raw body `B`, valid `X-Shopify-Hmac-Sha256: H` computed over `B` with the app's shared secret, `X-Shopify-Topic: T1`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`).
2. Replay the exact same body `B` and header `H` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and optionally `X-Shopify-Topic` to another registered topic.
3. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `B`, so `Utils::HmacValidator.validate` still returns `true` (per `lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
4. `Registry.process` (lines 188-200 of `lib/shopify_api/webhooks/registry.rb`) selects the handler for the spoofed topic and builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, which the host app's handler trusts as the authoritative tenant for processing.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
