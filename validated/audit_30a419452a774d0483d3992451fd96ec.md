### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` verifies the HMAC over the body only, then trusts the header-derived `shop` value and hands it straight to the app's webhook handler. This breaks the intended identity binding `HMAC-signed bytes == bytes acted upon`, letting anyone who can produce one valid `(body, HMAC)` pair (trivially obtainable by installing the app on their own store) replay it to the app's public webhook endpoint with an arbitrary `shop-domain` header, causing the app to process the event as if it came from a different, victim tenant.

### Finding Description
The webhook HMAC validator computes and checks the signature only against the raw body: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`HmacValidator.validate` then only ever verifies this `to_signable_string` value against `verifiable_query.hmac`: [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` validates only the HMAC (over the body) and then unconditionally forwards `request.shop` (an unauthenticated header) to the registered handler as the tenant identity for the event: [4](#0-3) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

The webhook HTTP endpoint hosted by the app is a public, unauthenticated internet-facing route (any user can POST to it — this is the whole design of webhook delivery), and the only thing protecting it is the HMAC over the body. Because `shop-domain` is not part of the signed content, the equality that should hold — `shop asserted in the signed payload == shop the app acts on` — is broken: an attacker can keep a legitimately-signed `(body, hmac)` pair (obtained by simply installing the app, even for free, on a store the attacker controls, or observing/replaying an app-triggered webhook from their own shop) and swap only the `x-shopify-shop-domain`/`shopify-shop-domain` header to any other shop domain, e.g. a victim tenant that also has the app installed. `Registry.process` will accept it (HMAC still matches, since HMAC only covers the body) and dispatch the event to the handler tagged with the victim's `shop`.

This is documented in `docs/usage/webhooks.md` / `BREAKING_CHANGES_FOR_V15.md` as the canonical pattern app authors are told to trust: `data.shop` is presented to handlers as the authoritative tenant identifier for scoping side effects (e.g. session lookups, per-shop data mutation, enqueuing per-shop jobs) — see [5](#0-4) . The gem gives app authors no signal that `shop` is unauthenticated, and no built-in mechanism (e.g., binding `shop` into the signable string, or validating against a known/registered shop list) to prevent this confusion.

### Impact Explanation
This is a cross-tenant identity-binding break: the entity (shop) that the signature semantically vouches for (the body) is not the same entity the app code keys its actions on (the header). An attacker controlling their own shop installation — an "unprivileged" party with respect to any other tenant — can cause the app to process arbitrary webhook topics (including sensitive ones such as `app/uninstalled`, `customers/redact`, `shop/redact`, or resource-mutation topics) attributed to a shop they do not control, since only the body needs a valid signature and the shop label is freely selectable. Depending on how the host app uses `data.shop` (which the gem's own documentation instructs apps to trust directly for lookups/actions), this can result in cross-tenant data corruption, spurious app-uninstall/redact processing for a victim shop, or state confusion between tenants — matching the Critical "cross-tenant access" impact bucket.

### Likelihood Explanation
Any developer can register as a partner and install a public/development version of the target app on their own store to legitimately receive a validly-HMAC'd webhook body/signature pair for a topic of their choosing. Because the webhook endpoint is a public HTTP endpoint with no additional authentication beyond the HMAC check, replaying that same `(body, hmac)` while altering the `shop-domain` header requires nothing but a simple HTTP client — no leaked secrets, no TLS interception, no privileged access to the victim account. The likelihood of triggering the vulnerable path is high for any app that installs on multiple merchants and trusts `WebhookMetadata#shop` as the gem's documentation instructs.

### Recommendation
Bind the shop identity to the signature, or otherwise verify it out-of-band before trusting it:
- Extend `Request#to_signable_string` (or the value passed to `HmacValidator`) so it commits to `shop`/`topic`/`webhook_id` in addition to the body, if Shopify's signing scheme is extended to support this, or
- Have `Registry.process`/apps cross-check `request.shop` against the set of shops that have an active session/webhook registration for that specific `webhook_id`/topic (e.g., via a `GET` lookup against Shopify using a stored per-shop session) before invoking the handler, and
- Document explicitly in `docs/usage/webhooks.md` that `WebhookMetadata#shop` is derived from an unauthenticated header and must not be used as the sole tenant key for side-effecting operations without additional verification (e.g., confirming the shop is present in the app's own shop/session store before acting).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop the attacker legitimately controls).
2. Attacker triggers a webhook topic the app subscribes to (e.g. `orders/create`) on `attacker-shop`, causing Shopify to POST a genuinely-signed webhook to the app's public webhook endpoint:
   - Headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC over body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{...order json...}`
3. Attacker (or a script sitting in front of/instead of Shopify, since this is just an ordinary internet POST to the app's public route) resends the exact same body and `x-shopify-hmac-sha256` value directly to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` computes the HMAC solely over `@raw_body` (`lib/shopify_api/webhooks/request.rb`, `to_signable_string`), which is unchanged, so validation succeeds.
5. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the app's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from `attacker-shop`. Any handler logic keyed on `data.shop` (per the gem's own documented usage pattern) now acts on behalf of the victim shop using attacker-supplied data.
