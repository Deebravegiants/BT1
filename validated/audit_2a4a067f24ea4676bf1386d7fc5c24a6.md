### Title
Deletion of the protocol treasury account permanently halts chunk application at every epoch boundary - (File: runtime/runtime/src/lib.rs)

### Summary
The FortaStaking report shows a class of bug where a critical fund-distribution routine unconditionally assumes a designated system address is valid/usable, and fails hard when that address is invalid. The nearcore analog is `Runtime::update_validator_accounts`, which unconditionally assumes the `protocol_treasury_account` exists in state whenever it is due a reward, and returns a fatal `StorageInconsistentState` error if it does not, rather than degrading gracefully.

### Finding Description
At every epoch boundary, `EpochManager::calculate_reward` (`chain/epoch-manager/src/reward_calculator.rs:78-84`) inserts a reward entry for `protocol_treasury_account` into the rewards map unconditionally. When the runtime later applies this via `update_validator_accounts` (`runtime/runtime/src/lib.rs:1663-1759`), if the treasury account is not part of `stake_info` (which is the normal case, since the treasury does not stake), the code does: [1](#0-0) 

If `get_account(state_update, account_id)?` returns `None` — i.e., the treasury account does not exist in state — the function returns `Err(StorageError::StorageInconsistentState(...))` rather than skipping the credit or handling the missing account gracefully. This is the same root-cause pattern as the FortaStaking bug: a payout path that blindly trusts a configured recipient account/address is valid, with no validation or fallback, causing the whole distribution operation to fail.

The treasury account can become nonexistent in an ordinary, unprivileged way: any account can delete itself via a standard `DeleteAccountAction` (`runtime/runtime/src/actions.rs`, `action_delete_account`), provided it has no locked stake. There is no special protection preventing the account currently configured as `protocol_treasury_account` (a normal `AccountId` fixed in genesis, e.g. `treasury.near`/`near` — see `utils/mainnet-res/res/mainnet_genesis.json:245`) from issuing this action against itself, or from having its storage balance driven so low that it is otherwise removed. Once that treasury account is gone, this is not a one-time failure: `calculate_reward` inserts a reward entry for it every single epoch, so `update_validator_accounts` will deterministically hit the missing-account branch and return an error at every subsequent epoch boundary, forever.

### Impact Explanation
`update_validator_accounts` runs as part of normal chunk/epoch-boundary application. A `StorageInconsistentState` returned from the runtime is a "should never happen" fatal-invariant error class; it propagates as a `RuntimeError`/`StorageError` out of chunk application and is not something ordinary chunk producers can simply skip past — it would cause block/chunk application to fail deterministically on every node re-applying that epoch boundary, since it is a pure function of on-chain state (not evidence of some other node's misbehavior). Because *every* honest node hits the identical error at the identical block deterministically, this results in a chain-wide halt/stall at the next epoch boundary rather than an isolated node crash — this satisfies the "chain stall" / "node panic" acceptance criteria. Unlike a validator misbehavior (which is node/validator-only and out of scope), this is triggered purely by a state condition (treasury account absence) reachable through an ordinary `DeleteAccountAction` transaction issued by the holder of that account's keys.

### Likelihood Explanation
Likelihood is constrained by the fact that only the entity controlling the `protocol_treasury_account` keys (or whoever can drive its storage balance to zero, e.g. via an authorized withdrawal drain) can trigger the deletion — this is analogous to the original report's precondition that only `DEFAULT_ADMIN_ROLE` can zero the treasury. It is not exploitable by a fully arbitrary unprivileged attacker against someone else's funds, but it is exploitable by anyone with signing authority over that single, statically-configured account using nothing more than a standard, always-available transaction action (`DeleteAccountAction`), with no additional protocol-level guard preventing it. There is no code path validating "this account is the protocol treasury, refuse deletion" anywhere in `action_delete_account`.

### Recommendation
Add an explicit check in `action_delete_account` (or in `check_actor_permissions`) rejecting attempts to delete the account matching the configured `protocol_treasury_account`, or alternatively make `update_validator_accounts` treat a missing treasury account as a case to skip/burn the reward instead of returning `StorageInconsistentState`. This mirrors the fix pattern in the report: validate the treasury/recipient invariant proactively so a single missing/invalid designated account cannot deterministically halt the reward-distribution (and thus chunk-application) pipeline.

### Proof of Concept
1. Take control of the account configured as `protocol_treasury_account` in genesis (e.g. `treasury.near`).
2. Ensure it has zero `locked` balance (true by default, since the treasury does not stake).
3. Submit a normal `DeleteAccountAction` transaction from that account to itself/any beneficiary, removing it from state.
4. At the next epoch boundary, `EpochManager::calculate_reward` again inserts a reward for `protocol_treasury_account` (`chain/epoch-manager/src/reward_calculator.rs:84`).
5. `Runtime::update_validator_accounts` calls `get_account(state_update, account_id)?` for the treasury account and gets `None`, hitting the `StorageError::StorageInconsistentState("Protocol treasury account {} is not found", ...)` branch (`runtime/runtime/src/lib.rs:1731-1736`).
6. Every node applying this epoch-boundary block deterministically hits the same fatal error, halting chain progress at that point.
