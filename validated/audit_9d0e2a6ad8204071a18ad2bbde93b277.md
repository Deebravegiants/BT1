### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its HMAC-verifiable content solely from the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` (tenant identity) is read from the unauthenticated `x-shopify-shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the body only and then trusts `request.shop` as the tenant identifier passed to the app's handler, breaking the binding `hmac_signed_bytes == bytes_used_for_tenant_identification`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed content: [2](#0-1) 

`Registry.process` verifies the HMAC via `Utils::HmacValidator.validate(request)` (which only checks `request.to_signable_string`, i.e. the body) and then forwards `request.shop` unchecked to the app-defined handler as the tenant identity: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body for webhooks) and the app's `api_secret_key`: [4](#0-3) 

Because the `api_secret_key` for a given app installation is a single shared secret used to sign webhooks for *every* shop/tenant that has installed that app, any unprivileged merchant who has installed the app can capture one of their own legitimately-signed webhooks (valid `body` + valid `hmac`) and replay it to the app's webhook endpoint after only changing the `x-shopify-shop-domain` header to a victim shop's domain. Since the HMAC never covers the `shop` header, `HmacValidator.validate` still returns `true`, and `Registry.process` passes the attacker-chosen `shop` value straight into `WebhookMetadata` for the handler: [5](#0-4) 

Any host application that uses `data.shop` from `WebhookMetadata` to key per-tenant storage, trigger tenant-scoped side effects, or route data will process attacker-controlled webhook data under a victim tenant's identity — a cross-tenant identity binding break (`hmac_signed_bytes == "raw_body"` but the trust decision is made on `header["shop-domain"]`, which is disjoint from the signed set).

### Impact Explanation
This breaks tenant isolation between shops sharing the same app installation (same `api_secret_key`), which maps to the "Critical - cross-tenant access" category: an attacker who is a legitimate (but unprivileged w.r.t. other tenants) merchant can inject arbitrary webhook payloads that the host application will process as if they originated from a different, victim shop.

### Likelihood Explanation
Likelihood is non-trivial: exploitation requires only (1) being a legitimate installer of the target app on any shop (an "unprivileged internet user" relative to other tenants) and (2) capturing one real webhook delivery for their own shop, which is a routine, unauthenticated-from-the-gem's-perspective HTTP POST that any installed merchant receives. No access to `api_secret_key`, access tokens, or other tenants' credentials is required.

### Recommendation
Do not trust `x-shopify-shop-domain` (or any other webhook header) as an authenticated tenant identifier unless it is cryptographically bound to the signed content. Either:
- Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed payload validation by cross-checking it against a value obtained from a trusted, separately-authenticated source (e.g., resolving the tenant via the API version + your own webhook subscription registry / stored subscription-to-shop mapping) rather than the header, or
- At minimum, document prominently that `Webhooks::Request#shop` is unauthenticated and instruct consuming applications to independently verify shop ownership (e.g., match against a known, previously-registered webhook address/subscription id for that shop) before using it as a tenant key.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery, e.g.:
```
POST /webhooks HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <valid-hmac-for-body>
X-Shopify-Shop-Domain: attacker.myshopify.com
X-Shopify-Webhook-Id: ...
X-Shopify-Api-Version: 2024-01

{"id":123,"malicious":"payload"}
```
2. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value, only changing the shop header:
```
POST /webhooks HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <same-valid-hmac-for-body>
X-Shopify-Shop-Domain: victim-shop.myshopify.com
X-Shopify-Webhook-Id: ...
X-Shopify-Api-Version: 2024-01

{"id":123,"malicious":"payload"}
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) — validation succeeds because the header was never part of the signed content: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`, causing the attacker's data to be processed under the victim's tenant identity.
