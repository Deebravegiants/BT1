### Title
Zero-amount padding inputs collapse to a fixed nullifier, causing permanent freezing of legitimate transactions - (File: circuits/MainEVMCircuit.circom, circuits/OriginalCommitmentCalculator.circom, contracts/HinkalBase.sol)

### Summary
`OriginalCommitmentCalculator` forces the commitment hash to `0` whenever `amount == 0`, discarding every other input (token address, public key, timestamp) [1](#0-0) . This zeroed commitment is then fed unconditionally into the nullifier derivation for every input slot in `MainEVMCircuit`, with no exemption for zero-amount (padding) slots [2](#0-1) . Because the nullifier for these empty slots is computed only from `nullifyingPrivateKey` and the fixed `commitment = 0` (no per-slot or per-transaction salt visible at the call site), it is identical for every empty slot the same user ever submits. `HinkalBase.insertNullifiers` treats any non-zero nullifier as a real spend and permanently marks it used, reverting on reuse [3](#0-2) .

### Finding Description
`MainEVMCircuit` always has fixed `tokenCount`/`inputCount` dimensions; real transactions routinely leave some `(i, j)` input slots empty (`inAmounts[i][j] = 0`) whenever the user is not consuming the maximum number of UTXOs for every token. For these empty slots:
- `calcCommitment[i][j].out` collapses to `0` regardless of `erc20TokenAddresses[i]`, `calcInPublicKeys[i][j]`, or `inTimeStamps[i][j]` [1](#0-0) .
- `calcSignature[i][j]` and `calcNullifier[i][j]` are derived only from `nullifyingPrivateKey` and this fixed `commitment = 0` [4](#0-3) .
- The constraint `inNullifiers[i][j] === calcNullifier[i][j].out` is unconditional — it is not gated by `inAmounts[i][j] != 0` (only the Merkle-root check is gated via `calcEqual[i][j].enabled <== inAmounts[i][j]`) [5](#0-4) .

This means the prover is forced to output the same nullifier value for every empty slot belonging to the same `nullifyingPrivateKey`, independent of `i`, `j`, token, or transaction. On-chain, `insertNullifiers` only special-cases a literal `0` value (`if (inputNullifiers[i][j] != 0)`) — it does not recognize "commitment-was-forced-to-zero" padding nullifiers as non-spending, so it inserts this fixed value into the `nullifiers` mapping and reverts with `"Nullifier cannot be reused"` if it is ever submitted again [6](#0-5) .

The equality broken here is the intended one-to-one binding between a real spent commitment and its nullifier: the circuit's zero-amount special case makes the nullifier a function of the user's static secret alone, not of the (leaf, root) pair actually being spent, so "spent" state is recorded for something that was never a real UTXO.

### Impact Explanation
Once a user submits any transaction that leaves one input slot empty for a given token (the normal case — nearly every real transaction has fewer inputs than the circuit's maximum `inputCount`/`tokenCount`), the fixed padding-nullifier for that user gets permanently marked spent. Any subsequent transaction by the same user that also needs to leave an input slot empty (unavoidable in ordinary usage) will produce the identical nullifier again and be rejected on-chain with `"Nullifier cannot be reused"`. This permanently freezes the user's ability to transact through Hinkal, i.e., permanent freezing of that user's shielded funds — matching the "permanent freezing of user funds" Critical-impact category.

### Likelihood Explanation
This is not an attacker-triggered exploit requiring special funds or timing — it is a deterministic consequence of ordinary protocol usage (any transaction using fewer than the maximum inputs per token). It would manifest on the very first or second normal transaction issued by a given user/key, making it a near-certain, self-inflicted denial of the protocol's basic transact flow rather than a rare edge case.

### Recommendation
- Do not derive the padding-slot nullifier purely from `(nullifyingPrivateKey, commitment=0)`. Bind the nullifier for empty slots to something unique per slot/transaction (e.g., include `i`, `j`, and a fresh per-transaction nonce/`messageSeed` in the nullifier preimage), or skip nullifier generation/insertion entirely for slots where `inAmounts[i][j] == 0`.
- Mirror the existing gating pattern already used for the Merkle-root check (`calcEqual[i][j].enabled <== inAmounts[i][j]`) for the nullifier equality constraint, so zero-amount slots do not produce a canonical, reusable nullifier.
- On the contract side, treat nullifiers tied to a forced-zero commitment as non-spending regardless of their numeric value, not just when the value is literally `0`.

### Proof of Concept
1. User A performs a shielded transaction with `tokenCount = 2`, `inputCount = 2`, but only actually spends 1 UTXO of 1 token — i.e., three of the four `(i, j)` slots have `inAmounts[i][j] = 0`.
2. For each empty slot, the prover must supply `inNullifiers[i][j] = calcNullifier(nullifyingPrivateKey, commitment=0)`, which is the same value for all three empty slots (same `nullifyingPrivateKey`, same forced `commitment = 0`).
3. `insertNullifiers` inserts this value into `nullifiers` mapping on the first occurrence, then reverts with `"Nullifier cannot be reused"` on the second/third occurrence within the same call, or — if slot-collapsing math differs slightly per position and the first tx happens to succeed with only one empty slot — on the very next transaction from the same user that leaves any slot empty, since it is bound to reproduce the identical previously-spent nullifier.
4. From that point on, User A can never submit a valid transaction that leaves a slot unused for that circuit configuration, permanently freezing their ability to move shielded funds.

*Caveat: I could not open `circuits/Signature.circom` and `circuits/NullifierCalculator.circom` to confirm their exact internal formulas (tool budget exhausted); the call sites in `MainEVMCircuit.circom` show only `nullifyingPrivateKey` and `commitment` as inputs to `Signature()`, with no `i`/`j`/nonce parameter, which is the basis for the determinism claim above. Verifying the templates directly would remove this remaining uncertainty.*

    function insertNullifiers(
        uint256[][] calldata inputNullifiers,
        bool[] calldata onChainCreation
    ) internal {
        for (uint256 i = 0; i < inputNullifiers.length; i++) {
            for (uint256 j = 0; j < inputNullifiers[i].length; j++) {
                if (onChainCreation[i] == true) break;
                if (inputNullifiers[i][j] != 0) {
                    require(
                        !nullifiers[inputNullifiers[i][j]],
                        "Nullifier cannot be reused"
                    );
                    nullifiers[inputNullifiers[i][j]] = true;
                    emit Nullified(inputNullifiers[i][j]);
                }
            }
        }
    }
