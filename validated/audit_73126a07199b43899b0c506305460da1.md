### Title
Webhook HMAC Only Covers the Request Body, Not the Shop/Topic/Webhook-ID Headers Used for Tenant Attribution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature that `Registry.process` validates never authenticates the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Those unauthenticated header values are nevertheless trusted downstream to build `WebhookMetadata` and dispatch it to the app's handler, breaking the binding "bytes verified == bytes acted on."

### Finding Description
`Request#to_signable_string` is defined to return `@raw_body` only: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over that signable string and compares it against the `hmac-sha256` header: [2](#0-1) 

`Registry.process` gates on this body-only HMAC check, then unconditionally trusts the unauthenticated `topic`, `shop`, `webhook_id`, and `api_version` accessors (all sourced from HTTP headers, never covered by the signature) to build and dispatch `WebhookMetadata` to the app's registered handler: [3](#0-2) 

Those accessors are all read straight from request headers with no cryptographic binding: [4](#0-3) 

The equality being broken here is: `bytes verified by HMAC(shopify-hmac-sha256)` should equal `bytes acted upon in WebhookMetadata (topic, shop, webhook_id, api_version, body)`. Instead, only `body` is in both sets; `shop`, `topic`, `webhook_id`, and `api_version` are acted upon without ever being part of the signed data.

### Impact Explanation
Because the app's HMAC secret (`api_secret_key`) is shared across all shops that install the app, any account that can trigger even one legitimate webhook delivery to itself (an ordinary, unprivileged merchant installing the app on their own store — no elevated access required) obtains a valid `(raw_body, hmac)` pair. That pair remains cryptographically valid regardless of which `shop-domain`, `topic`, or `webhook-id` headers accompany it, since those fields are excluded from the signed content. The attacker can then resend the request to the app's webhook endpoint with a forged `shop-domain` header pointing at a victim tenant (and/or a forged `topic`/`webhook-id`), and `Registry.process` will pass HMAC validation and dispatch the payload to the handler attributed to the victim shop. This is a cross-tenant identity-attribution break: the app's business logic (e.g., billing state changes, GDPR/customer-data callbacks, uninstall handling) executes against the wrong tenant using attacker-supplied identity fields, satisfying the "cross-tenant access" impact class.

### Likelihood Explanation
Exploitability only requires the ability to install the target app on an attacker-controlled shop (a standard, unprivileged capability for any Shopify merchant/developer) to capture one valid `(body, hmac)` pair, plus network access to POST to the app's public webhook endpoint with altered headers — no `api_secret_key`, access token, or other privileged credential is needed. The vulnerable code path (`Registry.process` trusting `request.shop`/`request.topic`/`request.webhook_id` without them being part of the signed payload) is exercised on every webhook delivery an app using this gem's `Webhooks::Registry` processes.

### Recommendation
Bind the identity-critical header values (`shop-domain`, `topic`, `webhook-id`, `api-version`) into the signed/verified data path — e.g., by having `Registry.process` cross-check `request.shop` against the session/shop the app expects for that delivery, or by requiring the host application to independently verify shop attribution before trusting `WebhookMetadata.shop`. At minimum, document prominently that `WebhookMetadata.shop`/`topic`/`webhook_id` are unauthenticated and must not be trusted for authorization decisions without independent verification (e.g., checking that the shop has an active installed session before acting on the webhook).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook subscribed by the app (e.g. `orders/create`), capturing the raw POST body and its `x-shopify-hmac-sha256` header — both are legitimately signed by Shopify with the app's `api_secret_key`.
2. Attacker replays the exact same body and `hmac-sha256` header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, and `Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) raw body against the HMAC: [5](#0-4) 
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` is `"victim.myshopify.com"` — an attacker-controlled, unauthenticated value — causing the handler to execute victim-tenant logic based on attacker-forged input. [6](#0-5)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
