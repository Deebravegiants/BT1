## Title
Silent failure of low-level ERC20 `transfer` calls in IntentGatewayV2 (Tron) escrow withdrawal — funds can be permanently frozen without reverting - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed input tokens using a raw `.call()` with the `IERC20.transfer` selector and only checks the low-level `success` boolean, never decoding/verifying the token's returned `bool` value. This is the same bug class as the reported Curve issue: a call that does not revert can still silently fail to move funds, while all internal accounting (escrow debit, `_filled` marking, event emission) proceeds as if the transfer succeeded.

### Finding Description
`withdraw()` — called from `onAccept()` for `RedeemEscrow`/`RefundEscrow` messages, and from `onGetResponse()` for source-chain cancellations — moves escrowed ERC20 tokens to the beneficiary like this: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;
    ...
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
    _orders[body.commitment][token] -= amount;
    ...
}
```

The only thing validated is that the low-level call did not revert. It never decodes returned data to confirm the ERC-20 function actually reports success (`abi.decode(data, (bool))`), nor does it check `data.length == 0 || abi.decode(data,(bool))` the way OpenZeppelin's `SafeERC20` does. Many real-world and non-standard ERC20/TRC20 tokens (older/legacy token implementations, tokens with bugs, or contracts calling an unrecognized selector that hits a permissive fallback) return `false` instead of reverting on failure — the low-level `.call` still reports `success == true` in that case, exactly the "silent failure" behavior flagged in the reference Curve report for old Vyper pools.

The identical unchecked pattern recurs in the same contract for:
- `SweepDust` handling: [2](#0-1) 
- transaction-fee payout inside `withdraw()`: [3](#0-2) 
- predispatch sweep-back-to-gateway transfer construction: [4](#0-3) 

By contrast, the non-Tron `IntentsBase._withdraw()` in the EVM implementation correctly uses `SafeERC20.safeTransfer`, which reverts on a `false` return value: [5](#0-4) . The Tron variant diverges from this safe pattern.

### Impact Explanation
Because `_filled[body.commitment] = beneficiary` and `_orders[body.commitment][token] -= amount` execute unconditionally once `success == true`, a token whose `transfer()` call succeeds at the call-level but returns `false` (or does nothing because the destination has no matching function and merely doesn't revert) will:
1. Mark the order as permanently filled/refunded (`_filled` set), preventing any retry or re-claim through `fillOrder`/`cancelOrder` paths.
2. Debit the escrow accounting as if funds were paid out.
3. Never actually deliver tokens to the beneficiary (solver or user).

The result is permanent freezing of the escrowed funds inside the gateway contract — the user/solver who was entitled to the tokens receives nothing, and no on-chain mechanism exists to retry or reclaim them since the commitment is already marked filled. This is directly reachable by any user placing an order with such a token as escrowed input, or by a relayer delivering a legitimate `RedeemEscrow`/`RefundEscrow` message for such an order — no privileged role required.

### Likelihood Explanation
Any user (or attacker acting as "user") can pick the escrowed input token when calling `placeOrder`. Tokens that return `false` on failure instead of reverting are common among older/legacy tokens and are explicitly why `SafeERC20` exists; on Tron in particular, TRC20 return-value conventions are frequently non-standard, increasing the likelihood of a legitimate token triggering this path unintentionally, in addition to any deliberately crafted "fail-silently" token.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()`, the `SweepDust` handler, and the predispatch sweep-back logic) with OpenZeppelin's `SafeERC20.safeTransfer`, matching the pattern already used correctly in `evm/src/apps/intentsv2/IntentsBase.sol`. `SafeERC20` verifies both call success and that returned data (if any) decodes to `true`, converting silent failures into explicit reverts.

### Proof of Concept
1. Deploy a TRC20/ERC20-like token whose `transfer(address,uint256)` function returns `false` (or is missing/mis-signatured such that a fallback silently accepts the call) instead of reverting when it cannot fulfill the transfer.
2. User calls `placeOrder` using this token as an input asset; tokens are escrowed via `safeTransferFrom` (which works normally on deposit).
3. Solver fills the order; the gateway's cross-chain `RedeemEscrow` message triggers `withdraw()` on the source chain.
4. `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `(true, <data decoding to false>)`; the low-level `success` flag is `true`, so `TransferFailed()` is never raised.
5. `_orders[commitment][token] -= amount` executes and `_filled[commitment] = beneficiary` is set, but `beneficiary` never receives the tokens — they remain stuck in the `IntentGatewayV2` contract with no path to recovery.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
