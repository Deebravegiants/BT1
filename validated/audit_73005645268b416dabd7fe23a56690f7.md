### Title
Webhook `shop` Identity Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating an HMAC that covers only the raw request body, then hands the handler a `shop` identity taken from an unauthenticated HTTP header. This breaks the equality the library implicitly promises: `hmac_verified(payload) == shop_is_authentic`. An unprivileged attacker who can obtain any genuine `(raw_body, hmac)` pair signed with the app's shared secret (e.g., by installing the app on their own free Shopify dev store) can replay that pair to the app's webhook endpoint while forging the `shopify-shop-domain` header to name a victim shop, and the library will report that forged shop as authenticated.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only the raw body:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

Meanwhile `shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of the signed material at all:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

`HmacValidator.validate_signature` confirms only the body/secret pairing:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [4](#0-3) 

The identity binding broken is: `hmac_valid(raw_body) == shop_domain_authenticated`. Because the same app secret is shared across every shop that has the app installed, any body+hmac pair valid for shop A is equally "valid" (from the library's perspective) when replayed with shop B's domain in the header — the signature never binds a particular shop to a particular payload. `Registry.process` nonetheless forwards `request.shop` to the handler as if it were verified, alongside an already-passed HMAC check, creating false confidence for host applications that build tenant-routing logic on it.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to select which merchant's data/session to act on (a extremely common and encouraged pattern, since the library exposes this field as the canonical shop identity right after HMAC validation) is exposed to cross-tenant confusion: an attacker-controlled shop identity can be attached to a Shopify-signed payload for an unrelated topic, letting the attacker trigger tenant-scoped side effects (e.g., data deletion/redaction handlers for `shop/redact`, `customers/redact`, `customers/data_request`, or app-specific business logic) under a victim shop's name. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
The attacker only needs a genuine `(body, hmac)` pair signed with the target app's shared secret. This is trivially obtainable by any unprivileged internet user: install the target app on a free Shopify development store, capture any real webhook delivery, then replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to the victim's shop. No access token, `client_secret`, or leaked credential is required — only public app installation, which is available to anyone.

### Recommendation
Do not treat `request.shop` as authenticated based solely on the body HMAC. The library should either (a) require the host application be told explicitly that `shop` is unauthenticated and must be cross-checked against the app's own store of shops that have valid, matching webhook subscriptions/sessions, or (b) bind the shop domain into the signed material used for verification (not possible without protocol changes on Shopify's side, since Shopify only signs the body), or at minimum document prominently in `Webhooks::Request`/`WebhookMetadata` that `shop` is derived from an unauthenticated header and must not be used for tenant routing without additional verification (e.g., confirming an active, previously-stored session exists for that shop before acting).

### Proof of Concept
1. Attacker creates a free Shopify development store (`attacker-shop.myshopify.com`) and installs the target app.
2. Shopify delivers a genuine webhook to the app, e.g. `POST /webhooks` with body `{}` and headers:
   - `x-shopify-hmac-sha256: <valid HMAC of "{}" with app secret>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: customers/redact`
3. Attacker captures this exact `body` + `hmac` pair.
4. Attacker crafts a new HTTP request to the same app endpoint, replaying the identical `body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `HmacValidator.validate` passes (HMAC only covers the body, unchanged), and `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", ...)`, so the app's handler executes redaction/tenant logic as though the request genuinely originated from `victim-shop.myshopify.com`.
