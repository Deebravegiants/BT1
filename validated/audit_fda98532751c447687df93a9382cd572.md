### Title
Emporium `runAction` moves arbitrary tokens outside all balance accounting when `erc20TokenAddresses.length == 0` (`EMPORIUM_MIN` proof path) - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `circomData.erc20TokenAddresses.length == 0`, `Hinkal.transact` routes proof verification through `formInputEmporiumMin`/`VerifierEVMMin0v4`, which only constrains `emporiumMessage`, `timeStamp`, and `calldataHash` — no signature, no Merkle root, no amount fields at all [1](#0-0) . With that empty token array, every balance-accounting loop in `Hinkal.transact` and `EmporiumUpgradeable.runAction` iterates zero times, so `handleOut` is never invoked and `balanceChange`/`deltaAmountChanges` are never computed for any token, even though `stack.ops[]` (fully attacker-controlled, and completely unsigned when `stack.signerAddress == address(0)`) can still execute arbitrary external calls from Emporium's own context.

### Finding Description
The claimed broken equality is: **tokens leaving Emporium during the action == `-Σ deltaAmountChanges` accounted for that action**. With `erc20TokenAddresses.length == 0` this equality is computed as `0 == 0` trivially in `EmporiumUpgradeable.runAction`'s loop at [2](#0-1) , since the loop bound is `circomData.erc20TokenAddresses.length` — it simply does not run.

Path traced:
1. Attacker calls `Hinkal.transact` with `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `circomData.erc20TokenAddresses = []`, and `dimensions.tokenNumber = 0`. `dimensionsCheck` passes trivially since all length checks compare against `dimensions.tokenNumber == 0` [3](#0-2) .
2. `formInputForCircom` detects this exact condition and calls `formInputEmporiumMin`, producing only 3 public inputs (`emporiumMessage`, `timeStamp`, `calldataHash`) [1](#0-0) . `buildVerifierId` derives the verifier from `dimensions` (all zero) + `externalActionId`, routing to `VerifierEVMMin0v4`, whose circuit contains no ownership/UTXO/nullifier/signature constraints on token movement — the attacker can freely generate a valid proof for this input since none of it depends on privileged data [4](#0-3) .
3. In `Hinkal.transact`, `getBalancesForArray(circomData.erc20TokenAddresses)` is called on an empty array (no-op), `_externalTransact` runs with an empty `deltaAmountChanges` array, and the post-loop balance-diff/slippage/accounting loop at [5](#0-4)  never executes for any real token.
4. Inside `EmporiumUpgradeable.runAction`, `verifyWallet` is called; if the attacker sets `stack.signerAddress == address(0)`, it returns immediately after marking the message used — **no signature is checked at all** [6](#0-5) . The `ops[]` loop then executes attacker-supplied `op.endpoint.call{value: op.value}(op.callData)` from Emporium's own address (CASE 2, stateless) [7](#0-6) . Since `circomData.erc20TokenAddresses.length == 0`, the subsequent balance-check/`handleOut` loop is skipped entirely (lines 132–151), so nothing constrains what `op.callData` does with tokens Emporium is currently holding.
5. The attacker crafts `op.endpoint = <any ERC20 token Emporium holds>` and `op.callData = abi.encodeCall(IERC20.transfer, (attacker, emporiumBalance))`. This is a direct `token.transfer` initiated by Emporium (the caller), draining Emporium's balance to the attacker, with zero balance-diff computation, zero UTXO creation, and zero on-chain nullifier/commitment trail referencing the stolen amount.

Existing guards fail because: `dimensionsCheck`/`checkOnchainCreation` only validate internal length consistency among attacker-supplied arrays, not that `tokenNumber > 0` is required whenever `stack.ops` performs external calls; `verifyWallet`'s signature check is bypassed entirely when `signerAddress == address(0)`; and the balance-accounting loops in both `Hinkal.sol` and `EmporiumUpgradeable.sol` are keyed off `circomData.erc20TokenAddresses.length`, so an attacker who declares zero tokens removes all accounting for the transaction while still being able to execute arbitrary calls through the Emporium contract.

### Impact Explanation
Critical — direct theft of any ERC20/ETH balance currently held by the Emporium contract (from any other user's in-flight Emporium flow, unclaimed dust, or fee residue), executed by an unprivileged attacker with zero matching on-chain accounting trail. Repeatable for every unique `emporiumMessage` value (guarded only by `usedMessages` replay protection, not value limits), and can be repeated against any token Emporium happens to hold at the time.

### Likelihood Explanation
Preconditions: Emporium must hold a nonzero balance of some token (plausible during normal operation, since intermediate/stateful Emporium flows and swap remnants pass through it). Attacker cost is a single `transact` call with a self-generated proof for the minimal circuit (`VerifierEVMMin0v4`), which requires no privileged secrets, no signature (via `signerAddress == address(0)`), and no valid Merkle root/nullifier data. This is fully within the reach of the described unprivileged attacker and is a straightforward, deterministic exploit, not probabilistic.

### Recommendation
Require `circomData.erc20TokenAddresses.length > 0` (or otherwise enforce balance-neutrality) whenever `stack.ops` is non-empty in the Emporium-min path, or disallow the `erc20TokenAddresses.length == 0` / signerless (`signerAddress == address(0)`) combination from executing arbitrary `op.endpoint.call` targets. At minimum, add an explicit post-execution invariant in `runAction` that total token balance held by Emporium cannot decrease for any token not declared in `circomData.erc20TokenAddresses`, or require the "min" circuit path to disable arbitrary calldata execution entirely (only allow it for wallet-signed, value-neutral stateful interactions).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (as allowed recipient), and a mock ERC20; seed Emporium's balance directly (simulate leftover funds from a prior legitimate flow).
2. Build `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `dimensions.tokenNumber = 0`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` = ABI-encoded `EmporiumStack{ signerAddress: address(0), ops: [EmporiumOperation{endpoint: mockToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, emporiumBalance))}] }`.
3. Generate a valid proof locally for `VerifierEVMMin0v4` over `(emporiumMessage, timeStamp, calldataHash)` — no ownership secrets needed.
4. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from attacker EOA.
5. Assert: `utxoSet.length == 0` returned from `runAction` (confirms `0 == 0` trivial accounting), while `mockToken.balanceOf(attacker)` increased by `emporiumBalance` and `mockToken.balanceOf(Emporium)` dropped to 0 — demonstrating actual value moved that was never reflected in any `balanceChange`/`deltaAmountChanges`/UTXO/commitment.
