### Title
Borrow-index accrual overflows before `MAX_BORROW_INDEX_RAY` clamps, permanently freezing a market's repay/withdraw/liquidate paths - (File: `common/src/rates/index.rs`)

### Summary
The Frankencoin H-05 bug class — a position owner poisoning a user-controlled value so every liquidation path reverts on an overflow — maps onto XOXNO Lending's borrow-index accrual. `update_borrow_index` multiplies `old_index` by the interest factor and *then* clamps the result at `MAX_BORROW_INDEX_RAY`, but the downstream valuation in `calculate_supplier_rewards` (`borrowed.mul(new_borrow_index)`) overflows `i128` long before the index itself reaches the cap when the scaled `borrowed` book is large. Since every pool verb accrues first via `global_sync`, once the index crosses the RAY-value ceiling the market is bricked: no repay, no withdraw, no liquidation — exactly the liquidation-denial impact of the report, achieved through overflow rather than an explicit poison price. ### Finding Description
`accrue_chunk` in `contracts/pool/src/interest.rs` calls `accrue_step` (shared with `simulate_update_indexes`) which internally calls `update_borrow_index` and `calculate_supplier_rewards` in `common/src/rates/index.rs`. The intended guard is `MAX_BORROW_INDEX_RAY`: `update_borrow_index` clamps `new_index` to the cap. However, the overflow does not occur in the index itself — it occurs when the capped-but-huge index is multiplied by the scaled `borrowed` amount (`borrowed.mul(env, new_borrow_index)` at line 81), producing `GenericError::MathOverflow` before the index ever reaches its cap.

Because `global_sync` runs at the head of every mutating pool entrypoint (supply, borrow, withdraw, repay, liquidation repayment leg, bad-debt cleanup), the panic makes the entire market inoperable. A borrower who keeps a whale-scale market at sustained high utilization (≈98% on the steep segment of the rate curve) drives the index past the overflow threshold and locks the market — their position can never be liquidated and suppliers can never exit, mirroring the Frankencoin owner's `adjustPrice(type(uint256).max)` denial.

The harness regression test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates exactly this: after iterated yearly accrual, `try_update_indexes_for` returns `MATH_OVERFLOW`, `last.borrow_index < MAX_BORROW_INDEX_RAY` proves the cap never engaged, and both `try_withdraw_raw` and `try_repay` revert with the same error.

### Impact Explanation
Permanent freezing of funds and a contract unable to operate: once the RAY product `borrowed × borrow_index` exceeds `i128::MAX`, every entrypoint that accrues — which is all of them — panics. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate the offending position, and `clean_bad_debt`/`recapitalize` cannot run on that market. The attacker keeps the borrowed assets while supplier collateral sits stuck, the same outcome as H-05 (owner keeps the tokens, collateral frozen).

### Likelihood Explanation
Reachable by a single unprivileged address through ordinary `supply`/`borrow` calls, but requires whale-scale capital (the test uses ~10⁹ whole tokens at 18 decimals with lifted caps) and sustained ~98% utilization long enough for the index to compound past the value ceiling — the test bounds it within 40 years, reachable much sooner on high-rate curves. No privileged action, oracle manipulation, or leaked key is needed; the attacker merely supplies liquidity, borrows it almost fully, and lets accrual run, optionally nudging utilization with `update_indexes`. Severity: Medium — high impact when triggered, gated by capital cost and accrual horizon.

### Recommendation
Make the index cap actually protective: in `accrue_step`/`update_borrow_index`, clamp `borrowed` value computation to saturation or cap the index early enough that `borrowed.mul(index)` cannot overflow — e.g., compute the maximum index admissible for the current `borrowed` (`max_index = i128::MAX / borrowed`) and `min(new_index, max_index)`, or use `mul_div_floor_saturating`-style saturating multiplication for `new_total_debt`. Add a fuzz/property assertion that `update_indexes` never reverts for any `(borrowed, index)` pair storable on the book.

### Proof of Concept
The existing harness test is the PoC (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs`):

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
// advance time; accrual eventually panics with MathOverflow
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

The borrower's debt can never be liquidated or repaid, and BOB's supply is permanently frozen — the overflow-based liquidation denial of the source report, expressed through the index ceiling rather than a user-set price.

Caveat: I could not read `common/src/constants/pool.rs` to confirm the exact `MAX_BORROW_INDEX_RAY` value or inspect `accrue_step`'s internals directly, so the precise overflow site (the `borrowed.mul` in `calculate_supplier_rewards` vs. another RAY multiplication inside `accrue_step`) is inferred from the test's comment naming `scaled_to_original` — either way, the cap ordering defect and its freeze effect are confirmed by the checked-in regression test.

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
}
