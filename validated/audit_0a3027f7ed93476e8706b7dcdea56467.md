### Title
Webhook `shop-domain` (and other identity headers) are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the HMAC signature over the raw request body only. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read from HTTP headers that are never included in the signed payload, yet `Registry.process` trusts these header-derived values (in particular `shop`) to identify the tenant the webhook belongs to when dispatching to the app's handler.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it to the `hmac` value: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw HTTP body — none of the Shopify headers are part of the signed data: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated headers via `shopify_header`: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then forwards the header-derived `request.shop` (and `request.topic`) directly into `WebhookMetadata`, which is handed to the app's webhook handler as the tenant/shop identity for the event: [4](#0-3) 

The binding this breaks (equality that should hold but doesn't): `shop-that-was-HMAC-verified == shop-that-the-handler-acts-on`. Only the body bytes are verified; the `shop` (and `topic`/`webhook_id`) bytes that the handler actually consumes to select which merchant's data to act on are parsed from headers that sit entirely outside the HMAC's scope. This is the same class of bug as the reported Chainlink issue: one thing is checked (the body signature) while a different, unchecked thing (the header claiming which shop/tenant this is) is what's actually acted upon.

### Impact Explanation
An unprivileged internet user who can reach the app's public webhook endpoint (by definition internet-facing) and who has observed or obtained even one legitimate `(body, hmac)` pair — e.g. from their own trial/development store's webhook deliveries, which is trivial to obtain since anyone can install a public app and receive real webhooks signed with the app's secret for their own shop — can replay that exact body/HMAC combination while substituting an arbitrary victim `shop-domain` header. `HmacValidator.validate` will accept it because only the body is checked, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop. If the host application's handler uses `data.shop` to select which merchant's session/record to update, provision, deprovision, or bill (a common and documented pattern, see the mandatory `app/uninstalled` and `shop/redact` topics), this results in cross-tenant data corruption/impersonation using only the attacker's own legitimately-signed traffic replayed with a different shop claim — no access token, `client_secret`, or leaked credential required.

### Likelihood Explanation
Any developer using an app can subscribe to real webhooks for their own shop and observe genuine `(body, X-Shopify-Hmac-Sha256)` pairs for topics with predictable/static or attacker-controlled bodies (e.g. `app/uninstalled`, `shop/redact`, or any topic where the attacker's own store produces the exact same body they want to replay against a victim). Because the webhook endpoint is unauthenticated by design (that's the point of the HMAC), and the shop header is not bound to the signature at all, exploitation requires no special access beyond the ability to send HTTP requests to the app's own public webhook endpoint.

### Recommendation
Bind the tenant-identifying values into the signed payload, not just the body. At minimum, include `shop-domain`, `topic`, and `webhook-id` in the HMAC-signed string (or verify them against out-of-band trusted state, such as a shop that already has an installed session), so the shop attribution used by `Registry.process`/`WebhookMetadata` cannot be forged independently of the message body.

### Proof of Concept
1. Install the app on an attacker-owned development store `attacker.myshopify.com`, or otherwise obtain a legitimate webhook delivery for a topic whose body content is attacker-known/fixed (e.g. `app/uninstalled` with a fixed `{}` body).
2. Capture the legitimate `X-Shopify-Hmac-Sha256` header Shopify computed for that body using the app's real `client_secret`.
3. Send a POST directly to the app's public webhook endpoint with:
   - The same raw body captured in step 1
   - The same valid `X-Shopify-Hmac-Sha256` value
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (any target shop)
   - `X-Shopify-Topic: app/uninstalled`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only the body is checked: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though nothing about that shop's identity was ever verified, letting the attacker trigger the app's uninstall/redact/tenant-scoped logic against a shop they don't control.
