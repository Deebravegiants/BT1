### Title
Iris-code signature omits `signup_id` binding, enabling signature reuse/collision across distinct signup sessions - (File: src/plans/enroll_user.rs)

### Summary
`make_signature` in `enroll_user.rs` builds the secure-element-signed attestation from `ORB_ID`, the user QR `user_id`, and the raw iris/mask codes and versions for both eyes, but never incorporates the per-attempt `signup_id` (or any nonce/timestamp) that uniquely identifies the specific signup transaction being submitted to the backend.

### Finding Description
`make_signature` hashes only `ORB_ID`, `user_qr_code.user_id`, and the iris pipeline's version/code/mask fields for both eyes with SHA-256, then signs the digest via the secure element: [1](#0-0) 

This signature is passed as the `signature` form field to `signup_post::request`, which posts it to `POST /api/v2/signups/{signup_id}` alongside the `signup_id` taken from the URL path rather than from the signed payload itself: [3](#0-2) 

Because the signed payload never binds to `signup_id`, any two signup attempts that reuse the same `user_qr_code.user_id` and produce the same iris/mask codes (e.g., the same user's QR code and iris data captured across two separate enrollment attempts/sessions, which is a routine and expected occurrence for repeated signups, retries, or an attacker replaying a previously observed signup form) will yield byte-for-byte identical `signature` values. This is structurally the same root cause as the referenced report: a hash/signature payload that omits the field meant to disambiguate distinct transactions (there `srcChain`/`srcAddr`; here `signup_id`), so the resulting value collides across otherwise-distinct transactions and the receiving system cannot use it to bind the attestation to the specific transaction it accompanies.

### Impact Explanation
If the backend relies on this `signature` value as proof that the accompanying `signup_id`'s biometric data was freshly captured and signed by the orb's secure element for that specific signup, the missing binding lets a previously captured, valid `(user_id, iris_code, mask_code)` signature be resubmitted verbatim against a different `signup_id` path. This enables cross-signup replay/misattribution of a biometric attestation - the same signed proof could be attached to more than one signup transaction, undermining the integrity guarantee the signature is meant to provide for signup approval.

### Likelihood Explanation
This is reachable within the normal unprivileged signup flow: any user/operator pair performing repeated or retried signups with the same underlying QR/iris data will naturally generate colliding signatures, and an attacker that can capture one such signature payload (e.g., by observing/replaying a signup POST) can attempt to attach it to a separate `signup_id`. No privileged access is required to trigger the collision.

### Recommendation
Include `signup_id` (and ideally a monotonically increasing nonce or timestamp) inside the hashed context in `make_signature`, so the signed digest cryptographically binds to the exact signup transaction it is submitted for, preventing any reuse of the signature across distinct `signup_id`s.

### Proof of Concept
1. Perform a signup with `user_qr_code.user_id = X` and a given iris/mask code set; capture the resulting `signature` computed by `make_signature`.
2. Perform a second, distinct signup attempt (different `signup_id`) with the same `user_qr_code.user_id = X` and the same iris/mask codes (e.g., a retried enrollment for the same person, or a replayed capture).
3. Observe that `make_signature` produces an identical signature for both attempts, since `signup_id` never enters the hashed context: [1](#0-0) 
4. Because `signup_post::request` sends this identical signature alongside whatever `signup_id` is placed in the URL path, the same signed attestation can accompany more than one signup transaction.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
