### Title
Silent sign-flip on unchecked `int256(uint256)` cast in `VWAPOracle.recordSpread` can corrupt or brick spread accounting - (File: evm/src/utils/VWAPOracle.sol)

### Summary
`VWAPOracle.recordSpread` normalizes user/filler-supplied `TokenInfo.amount` values (`uint256`) to 18 decimals and then explicitly casts them to `int256` with `int256(outputAmountNormalized)` / `int256(inputAmountNormalized)` to compute a signed spread. Just like the `Fixed6`/`Fixed18` `from` functions in the referenced report, this code implicitly assumes the `uint256` value is always representable as a positive `int256`. Solidity's explicit same-width `uint256 -> int256` conversion is a raw bit-reinterpretation with **no range check** — it does not revert on overflow, it silently flips sign when the value exceeds `type(int256).max`.

### Finding Description
In `evm/src/utils/VWAPOracle.sol`: [1](#0-0) 

```solidity
uint256 inputAmountNormalized = _normalizeAmount(inputs[i].amount, inputDecimals);
uint256 outputAmountNormalized = _normalizeAmount(outputs[i].amount, outputDecimals);

int256 spreadBps = 0;
if (inputAmountNormalized > 0) {
    int256 amountDiff = int256(outputAmountNormalized) - int256(inputAmountNormalized);
    spreadBps = (amountDiff * int256(BPS_DENOMINATOR)) / int256(inputAmountNormalized);
}

int256 weightedSpread = spreadBps * int256(inputAmountNormalized);
_updateCumulativeSpread(_tokenSpreads[sourceChainHash][inputToken], weightedSpread, inputAmountNormalized);
```

`inputs[i].amount` and `outputs[i].amount` originate from `TokenInfo` structs supplied as part of an intent order's inputs/outputs (`evm/src/apps/IntentGatewayV2.sol` / `IntentGatewayV2.TokenInfo`), and are passed through unchanged except for `_normalizeAmount` decimal scaling: [2](#0-1) 

```solidity
function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
    if (_decimals == 18) {
        return amount;
    } else if (_decimals < 18) {
        return amount * (10 ** (18 - _decimals));
    } else {
        return amount / (10 ** (_decimals - 18));
    }
}
```

There is no upper bound check anywhere on `amount` before or after normalization. If a token has fewer than 18 decimals (e.g., a 6-decimal token), `_normalizeAmount` multiplies by `10**12`, and if the raw `amount` exceeds roughly `type(int256).max / 10**12 ≈ 5.79e46`, the normalized `uint256` value will exceed `type(int256).max` (≈5.79e76). The subsequent explicit cast `int256(outputAmountNormalized)` (and `int256(inputAmountNormalized)`) does **not** revert in Solidity ≥0.8 — same-width `uint<->int` conversions are unchecked bit reinterpretations — so a sufficiently large amount silently becomes a negative `int256`. This flips the sign of `amountDiff`, `spreadBps`, and `weightedSpread`, corrupting the VWAP spread accumulator (`_tokenSpreads[...].weightedSpreadSum`), or causes the downstream division/multiplication to revert due to genuine arithmetic over/underflow once the value is reinterpreted as a large negative number multiplied by `BPS_DENOMINATOR`.

`recordSpread` is only callable by the registered `_intentGateway` (`restrict(_intentGateway)` modifier), so the reachable trigger is any order routed through `IntentGatewayV2` whose filler supplies (or a user requests) input/output token amounts large enough to overflow after normalization — well within the `uint256` range permitted by `TokenInfo.amount`, and not otherwise validated for an upper bound anywhere in the intents flow reachable by an unprivileged solver/filler settling an order.

### Impact Explanation
A corrupted `weightedSpreadSum`/`totalVolume` state permanently poisons the VWAP oracle's `spread()` output for that `(sourceChain, token)` pair (Medium impact — data integrity / potential downstream mispricing for any consumer of `IIntentPriceOracle.spread`, e.g. relayer fee or filler risk logic that reads this oracle). It can also cause `recordSpread` to revert deterministically once a poisoned state feeds a division by a corrupted denominator, effectively bricking spread recording for that token going forward — a persistent state corruption stemming from an unprivileged, single-transaction order fill.

### Likelihood Explanation
Requires normalized order amounts that exceed `type(int256).max` (~5.79 * 10^76 in 18-decimal terms). This is a very large but not impossible value within `uint256`'s range, and nothing in `IntentGatewayV2`/`TokenInfo` enforces an economically sane upper bound on `amount`. Because `recordSpread` is invoked automatically as part of intent order settlement flow and both filler and user control the amounts making up an order, an attacker-influenced filler/solver could construct an order with an extreme (but decodable) amount to trigger the bad cast deliberately, or it could occur accidentally with a pathological order. Likelihood is Low-Medium given the extreme value threshold required, but the root cause — an unchecked, non-reverting narrowing-equivalent cast on attacker-influenced input — mirrors exactly the flagged bug class.

### Recommendation
Replace the raw `int256(uint256)` casts in `recordSpread` with a checked conversion (e.g., OpenZeppelin's `SafeCast.toInt256`) that reverts when the value exceeds `type(int256).max`, and/or bound `TokenInfo.amount` (or the normalized amount) to a sane maximum before use in signed arithmetic.

### Proof of Concept
1. Governance/admin configures a source-chain token with `decimals < 18` (e.g., 6) via `_processTokenDecimalsUpdates` — a normal setup step.
2. An order is settled through `IntentGatewayV2`, invoking `VWAPOracle.recordSpread` with `inputs[i].amount` (or `outputs[i].amount`) set to a raw value such that after `_normalizeAmount` scaling (`amount * 10**12`) the normalized `uint256` exceeds `type(int256).max` (≈5.79 * 10^76).
3. `int256(outputAmountNormalized)` (or `inputAmountNormalized`) silently reinterprets as a negative number instead of reverting.
4. `spreadBps` and `weightedSpread` are computed with the wrong sign / corrupted magnitude, and `_tokenSpreads[sourceChainHash][inputToken].weightedSpreadSum` is permanently poisoned, or the transaction reverts on a subsequent arithmetic check, bricking further `recordSpread` calls for that token pair.
