Webhook Shop-Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the HMAC signature only over the raw request body, while the `shop` (and `topic`, `api_version`, `webhook_id`) values are read from unauthenticated HTTP headers. `Registry.process` trusts these header-derived values when invoking the app's webhook handler, so an attacker who can produce one valid `(raw_body, hmac)` pair for a shop they control can replay it with a forged `X-Shopify-Shop-Domain` header claiming to be a different, victim shop. The equality that should hold — "the shop the handler processes data for" == "the shop whose secret produced the HMAC" — is broken because the header is never part of the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled directly from HTTP headers without any cryptographic binding to that body: [2](#0-1) 

`HmacValidator.validate` only ever signs/verifies `verifiable_query.to_signable_string`, i.e., the raw body — it has no knowledge of the shop header at all: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and other headers) to build the metadata handed to the app's business logic: [4](#0-3) 

Because the HMAC only proves "this body was signed by someone holding `api_secret_key`" and says nothing about which shop it was signed for, any party capable of triggering a legitimate webhook delivery to themselves (e.g., an attacker who installs the app on their own store, or any other flow that yields one authentic `(body, hmac)` pair) can resend that exact body/HMAC pair to the app's webhook endpoint with the `shop-domain` header rewritten to name a different, victim shop. The signature check still passes because it never examined the header, and the handler receives `WebhookMetadata` claiming the victim shop as the source.

This is a direct analog of the reported Solidity bug: there, `claimFees` acted on an attacker-supplied `to` address that was never bound to the value actually authorized/computed for `msg.sender`. Here, the webhook pipeline acts on an attacker-supplied `shop` header that was never bound to the HMAC-authenticated body.

### Impact Explanation
Any application built on this gem that branches its webhook-handling logic on `WebhookMetadata#shop` (e.g., to look up per-shop data, credentials, or to update per-tenant records) can be made to process attacker-controlled webhook bodies under an arbitrary victim shop's identity. This is a cross-tenant identity-confusion vector reachable by an unprivileged internet user who can obtain (via any legitimate delivery to a shop they control) one valid signed webhook body and then replay it with a different shop header — meeting the Critical "cross-tenant access" impact bar defined in the scope rules.

### Likelihood Explanation
Likelihood is high for any app that relies on `WebhookMetadata#shop` for tenant scoping, since: (1) obtaining one valid signed body only requires installing the app on an attacker-owned shop and triggering any webhook topic; (2) resending an HTTP POST with a modified header requires no special access, credentials, or the `api_secret_key`; and (3) the HMAC check as implemented in this gem provides no protection against this replay because the shop is fundamentally outside the signed payload.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed body before it is trusted by `Registry.process`/`WebhookMetadata`. At minimum, document and/or enforce that consumers must cross-check `request.shop` against an independently known, already-authenticated shop (e.g., the shop associated with the specific webhook subscription/session) rather than trusting the header value as the sole source of tenant identity.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`) so Shopify sends a legitimately signed request:
   - Headers: `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>`, `X-Shopify-Topic: orders/create`
   - Body: `{"id": 1, ...}`
2. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
3. Attacker resends the same body and HMAC header to the app's webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates only `to_signable_string` (`@raw_body`) — this still matches, so validation passes.
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, causing the app to process attacker-controlled data as if it originated from the victim shop.
