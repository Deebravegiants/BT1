### Title
msg.value double-counted across duplicate `address(0)` entries in `erc20TokenAddresses` mints unbacked shielded ETH - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` computes the ETH balance delta independently for every index of `circomData.erc20TokenAddresses`, adding `msg.value` back in on every occurrence of `address(0)` rather than once for the whole call [1](#0-0) . If an attacker lists `address(0)` twice, both indices are validated against the *same* single ETH payment, letting the attacker back two independent `amountChanges` entries (i.e., two shielded UTXOs) with only one real ETH inflow.

### Finding Description
The broken equality is: `Σ(amountChanges[i] over all i where erc20TokenAddresses[i]==address(0)) + Σ(utxoAmount[i] over those i) == msg.value` (exactly one real ETH inflow should back exactly one accounting slot). Instead the contract enforces the equality **separately per index**:

```solidity
if (circomData.erc20TokenAddresses[i] == address(0)) {
    balanceDif = int256(newBalances[i]) + int256(msg.value) - int256(oldBalances[i]);
}
...
require(
    balanceDif == (circomData.onChainCreation[i] ? int256(0) : circomData.amountChanges[i]) + int256(utxoAmount),
    ...
);
``` [2](#0-1) 

`oldBalances`/`newBalances` are computed once for the whole `erc20TokenAddresses` array via `getBalancesForArray`, so for two indices both equal to `address(0)` the raw `newBalances[i]-oldBalances[i]` is identical at both indices [3](#0-2) . Because `msg.value` is added back in the loop at every `address(0)` occurrence, `balanceDif` evaluates to the same value `X = msg.value` (assuming no other real ETH movement) at **both** duplicate indices.

For the internal path (`_internalTransact`), a positive `amountChanges[i]` (deposit) is checked via `transferERC20TokenFromOrCheckETH`, which for ETH only asserts `msg.value == _value` and performs no actual transfer when `_to == address(this)` [4](#0-3) . This check is satisfied trivially for both duplicate indices as long as `amountChanges[i1] == amountChanges[i2] == msg.value`, since it just compares against the global `msg.value`, not a per-index budget [5](#0-4) .

The attacker crafts their own proof (fully within their rights as an unprivileged depositor of their own funds) so that the circuit constraint `inTotal + amountChanges === outTotal` is independently satisfied at both index slots, producing two off-chain output UTXOs of value `X` each. Nothing in `performHinkalChecks`/`dimensionsCheck` in the visible code path enforces uniqueness of `erc20TokenAddresses` entries, and the per-index balance loop has no running total that would catch that the same `msg.value` was already "spent" satisfying the first duplicate index.

Result: attacker sends `msg.value = X` once, but mints two independent shielded UTXOs of value `X` (total `2X`) via `insertCommitments`, i.e., unbacked shielded ETH equal to `X`.

### Impact Explanation
This mints shielded value without ETH backing — direct protocol insolvency, matching the **Critical** category (minting shielded value without backing). The attacker can repeat this with `N` duplicate `address(0)` entries to multiply unbacked minted value roughly by `N` per call, subject to gas/array-size limits, and is repeatable across transactions/blocks with no special preconditions beyond generating a self-consistent proof for their own deposit.

### Likelihood Explanation
Preconditions: attacker needs only to (1) call `transact` with `erc20TokenAddresses` containing `address(0)` at 2+ indices, matching `amountChanges` at each such index, and (2) generate a valid SNARK proof for their own new UTXOs satisfying the circuit's local `inTotal+amountChanges===outTotal` constraint at each slot independently. No tree state, no other users' keys, and no privileged role are required — well within the stated attacker capability ("craft every field of CircomData... deposit arrays"). The only unresolved uncertainty is whether `dimensionsCheck`/`performHinkalChecks` (not fully retrievable within the available context) enforces token-address uniqueness in `erc20TokenAddresses`; based on the visible `Hinkal.sol` logic, no such uniqueness check exists in the balance-accounting loop itself.

### Recommendation
Aggregate the ETH inflow check once per call instead of per index: track a single `ethCredited` accumulator, add `msg.value` to it only once (e.g., outside the loop, or the first time `address(0)` is seen), and require the loop's `address(0)` branches to draw from that shared budget so the sum of all `address(0)` balance-difference terms across the array cannot exceed `msg.value` plus the real balance delta. Alternatively, reject `circomData.erc20TokenAddresses` containing duplicate entries in `performHinkalChecks`/`dimensionsCheck`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal` with test verifier/helper (or mock `verifyProof`/`performHinkalChecks` to accept the crafted proof/circomData, since generating a real SNARK proof requires the local circuit toolchain).
2. Construct `circomData.erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, `externalActionData.externalActionId = 0`, `externalActionData.externalAddress = attacker`.
3. Call `hinkal.transact{value: X}(a, b, c, dimensions, circomData)`.
4. Assert both per-index `require` checks at contracts/Hinkal.sol lines 111-114 and 137-146 pass.
5. Assert `insertCommitments` is invoked with two output UTXOs each valued `X` (total minted shielded ETH `2X`), while `address(this).balance` only increased by `X` — i.e., assert `mintedShieldedETH (2X) > address(this).balance delta (X)`, proving unbacked minting.
