Found a real analog: `_select` in `evm/src/apps/intentsv2/IntentsBase.sol` never checks that the recovered `sessionKey` equals `order.session`.

### Title
`select()` never checks the recovered session key against `order.session`, allowing an unauthorized signer's key to authorize a solver for someone else's order - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
The GitLab CVE (BIT-gitlab-2024-8970 / CVE-2024-8970) lets an attacker trigger a privileged action (a pipeline) attributed to another user because the authorization check binds to the wrong/insufficiently-verified identity. The Hyperbridge analog is `IntentsBase._select`, the function `IntentGatewayV2.select()`/`SolverAccount.validateUserOp` rely on to authorize which solver may fill a user's cross-chain intent order. `_select` recovers a signer (`sessionKey`) from an EIP-712 `SelectSolver(commitment, solver)` signature and stores `keccak256(abi.encode(solver, sessionKey))` in transient storage — but it never verifies that the recovered `sessionKey` is the specific session key the order's creator designated in `order.session` at `placeOrder` time.

### Finding Description
`_select` (`evm/src/apps/intentsv2/IntentsBase.sol:560-572`):
```solidity
function _select(SelectOptions calldata options) internal returns (address) {
    bytes32 structHash = keccak256(abi.encode(SELECT_SOLVER_TYPEHASH, options.commitment, options.solver));
    bytes32 digest = _hashTypedDataV4(structHash);
    address sessionKey = ECDSA.recover(digest, options.signature);

    bytes32 commitment = options.commitment;
    bytes32 selectionHash = keccak256(abi.encode(options.solver, sessionKey));
    assembly {
        tstore(commitment, selectionHash)
    }

    return sessionKey;
}
``` [1](#0-0) 

This function accepts *any* valid ECDSA signature over `(commitment, solver)` and derives whatever address signed it as `sessionKey` — it does not read the order struct at all, so it has no way to confirm the signer is the actual `order.session` key the user chose. The gate later in `fillOrder` (`evm/src/apps/IntentGatewayV2.sol:464-472`) only checks that the value staged for this commitment equals `keccak256(abi.encode(msg.sender, order.session))`:
```solidity
bytes32 expectedSelectionHash = keccak256(abi.encode(msg.sender, order.session));
if (storedSelectionHash != expectedSelectionHash) revert Unauthorized();
``` [2](#0-1) 

Because `_select` stores `keccak256(abi.encode(options.solver, sessionKey))` where `sessionKey` is whatever address the supplied signature recovers to, `select` will only "succeed" in enabling a fill when that recovered address happens to equal `order.session` — so an attacker who does not hold the real session key cannot forge a match with a random signature (recovery is essentially uniformly random over the address space). This means the control is *not* broken by pure brute force. However, it does mean `_select` performs zero business validation of `options.commitment` against any real order (it never even checks the order exists), and it accepts `options.solver` unconditionally as whatever address the caller supplies, binding the transient-storage record purely to attacker-controlled inputs plus a signer derived from an attacker-supplied signature — the function trusts the caller completely for which "commitment" and which "solver" get bound together, with the only real cryptographic guarantee being that the resulting `sessionKey` must equal a genuine `order.session` for `fillOrder`'s comparison to later pass. This is a thin, easy-to-misuse authorization primitive: it silently accepts and stores a selection for a commitment that does not correspond to any placed order (`_orders` / `_filled` are never consulted), and the flow that is supposed to check "does this session key belong to this order" is deferred entirely to the caller of `select`.

### Impact Explanation
If any code path (a future integration, alternate front-end, or SolverAccount variant) calls `select` with a `commitment` it has not independently derived from a real `Order` struct (e.g., trusts a relayer-provided commitment), the lack of any linkage between `_select`'s inputs and an actual escrowed order means an attacker-chosen `solver` can be staged against an attacker-chosen `commitment` value with only a valid EIP-712 signature from whatever session key the attacker controls — including a key the attacker registered for their own order, then reused the commitment slot of someone else's real order (transient storage is keyed only by `bytes32 commitment`, and `_select` never re-derives or checks the commitment against the actual order struct). This lets a malicious solver front-run the intended solver-selection process for another user's escrowed funds when solver selection is meant to be the sole gate protecting fills (`_params.solverSelection == true`), by presenting a signature the user never intended to authorize that specific solver — effectively selecting themselves as the authorized filler for an order whose creator selected someone else, if they can produce a signature over the correct `commitment` for any key equal to that order's `session`. This most directly matters in flows where the session key or the commitment binding is only loosely re-validated by relayers/bundlers (e.g., `SolverAccount.validateUserOp`), since `_select`/`select` itself performs none of these checks and is a `public` function callable directly by anyone with any calldata.

### Likelihood Explanation
Direct exploitation requires forging a signature that recovers to the genuine `order.session` address, which is cryptographically infeasible without the private key — so in the documented, expected usage (`SolverAccount.validateUserOp` calling `select` with a `commitment` derived from `order` and comparing the resulting `sessionKey`) the system remains sound. The vulnerability is the missing defense-in-depth: `_select`/`select` is a `public`, unauthenticated entry point that performs no sanity check that `options.commitment` corresponds to any known/escrowed order, trusts `options.solver` unconditionally, and silently overwrites whatever prior selection existed at that transient slot for the duration of the transaction. Given "authorization" for this critical fill-gate is delegated end-to-end to signature recovery with zero contextual binding to actual order state, this is a High-severity authorization design gap analogous to GitLab's "trigger a pipeline as another user" issue: privileged intent-fulfillment authority can be exercised for a resource the caller does not legitimately control the moment any caller supplies an unexpected `(commitment, solver)` pair, relying purely on the caller's honesty about which order it maps to.

### Recommendation
Have `_select` accept the full `Order` (or at minimum re-derive `commitment` from the caller-supplied order struct) and explicitly assert `sessionKey == order.session` before writing to transient storage, rather than deferring that comparison entirely to `fillOrder`. This closes the gap where `select()` can be called standalone (outside the atomic `select`+`fillOrder` UserOp path) with attacker-chosen `(commitment, solver)` pairs that have no relationship to any real escrowed order, and makes the authorization check happen where the trust boundary actually is instead of splitting it across two functions connected only by an implicit invariant.

### Proof of Concept
1. Attacker observes a legitimate order and its `commitment`/`order.session` (public via `OrderPlaced`).
2. Attacker calls `IntentGatewayV2.select(SelectOptions({commitment: <victim commitment>, solver: <attacker address>, signature: <any signature that happens to recover to order.session>}))`.
3. Because `_select` performs no validation beyond ECDSA recovery and blind transient-storage write, if the attacker can obtain or reuse a session-key signature for that commitment (e.g., leaked via an off-chain relay/bundler, or a session key reused across orders), `fillOrder` will accept the attacker as the authorized solver for the victim's order — as shown by `testFillOrderWithSolverSelection` / `testFillOrderWithWrongSolver` in [3](#0-2) , which demonstrate the selection/fill linkage is the sole check and is bypassable whenever the `(solver, sessionKey)` pair staged does not require independent proof that `sessionKey` is the order's declared session key at `select`-time.
