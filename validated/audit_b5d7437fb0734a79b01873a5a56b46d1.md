### Title
Fee-token accounting mismatch: `IntentGatewayV2`/`IntentsBase` records escrowed relayer fees as a raw amount but pays them out using the *current* `host().feeToken()`, causing frozen or mispaid funds if the fee token is updated between order placement and settlement - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2.placeOrder` collects `order.fees` in whatever ERC20 token is `IDispatcher(hostAddr).feeToken()` *at placement time*, and stores only the numeric amount under the sentinel key `TRANSACTION_FEES` in `_orders[commitment]`, with no record of which token was actually collected. `IntentsBase._withdraw` later releases those fees by calling `IDispatcher(host()).feeToken()` again — evaluated at *redemption time* — and transferring that many units of whatever token is currently configured as the fee token. If the host's `feeToken` is changed via `EvmHost.updateHostParams` (a routine, non-malicious governance operation explicitly supported by the protocol) between order placement and order redemption, the escrow accounting for the fee portion of in-flight orders becomes desynchronized from the token that was actually deposited.

### Finding Description
At order placement, in `IntentGatewayV2.sol`: [1](#0-0) 
the contract reads the *current* fee token from the host, pulls `order.fees` units of it from the user (or swaps native token into it), and stores it in escrow with no token identifier — only the raw amount: [2](#0-1) 

At redemption (via `RedeemEscrow` requests processed through `onAccept`, or same-chain cancellation/refund), `_withdraw` looks up the fee token again, at the *current* state: [3](#0-2) 

Because the stored `_orders[commitment][TRANSACTION_FEES]` value is a bare `uint256` amount decoupled from any token address, and the token used to transfer it out is resolved dynamically from `IDispatcher(host()).feeToken()` at redemption time rather than the token actually escrowed, any change to `HostParams.feeToken` between `placeOrder` and settlement causes the wrong ERC20 to be transferred to the beneficiary in the amount originally denominated in the old token. `EvmHost.updateHostParams` is a normal, expected cross-chain governance action (only guarded against changing the fee token while the *old* token still has a nonzero balance on the host, not against pending intents fee balances held by `IntentGatewayV2`): [4](#0-3) 
this check only inspects the host's own balance, not the `IntentGatewayV2` contract's escrowed fee balances, so it does not prevent the mismatch described here.

### Impact Explanation
Depending on the gateway's token balances at redemption time:
- If the gateway holds insufficient balance of the *new* fee token, `safeTransfer` reverts, and since `finalize` bundles the fee transfer together with the release of the escrowed principal tokens in the same `_withdraw` call, the entire redemption reverts — permanently freezing the user's/solver's principal escrow funds along with the fee, since `RedeemEscrow`/refund flows cannot be retried with a different code path.
- If the gateway happens to hold sufficient balance of the new fee token (e.g., accumulated from other orders' fees or dust), the beneficiary is paid out in the new token using the old token's numeric amount, effectively minting value at the expense of other users' escrowed fee/dust balances in that token — a direct value-extraction bug.

### Likelihood Explanation
`feeToken` changes are a deliberate, supported, and periodically expected host-governance operation (as reflected by the very existence of the `CannotChangeFeeToken` guard and the comment "It's important that before changing this parameter, that all funds have been drained from the previous feeToken"), reachable purely through the normal cross-chain governance-request → `HostManager` → `updateHostParams` path, with zero cooperation required from the `IntentGatewayV2` operator. Any intent that has fees escrowed and is still pending settlement when the fee token rotates is affected — an ordinary, foreseeable operational sequence rather than an edge case.

### Recommendation
Store the fee token address alongside the escrowed fee amount at `placeOrder` time (e.g., `_orders[commitment][actualFeeTokenAddress] += order.fees` instead of a fixed sentinel key resolved to the current `feeToken()`), and use that recorded token address — not `host().feeToken()` at redemption time — when releasing fees in `_withdraw`. Alternatively, require `EvmHost.updateHostParams` to also verify (or the `IntentGatewayV2` to expose/require draining) that no outstanding intents fee escrow exists in the old fee token before allowing the fee token to change.

### Proof of Concept
1. User calls `IntentGatewayV2.placeOrder` with `order.fees = 100e6` while `host().feeToken() == USDC`; the gateway pulls 100 USDC from the user and stores `100` under `_orders[commitment][TRANSACTION_FEES]` (no token tag) as shown in `evm/src/apps/IntentGatewayV2.sol:375-392`.
2. Before the order is filled/redeemed, Hyperbridge governance dispatches a routine `updateHostParams` request changing `feeToken` from USDC to DAI; `EvmHost.updateHostParamsInternal` succeeds because the *host's own* USDC balance is zero (the fees sit in `IntentGatewayV2`, not the host) — see `evm/src/core/EvmHost.sol:617-621`.
3. The order is later settled via `onAccept`/`RedeemEscrow`, invoking `_withdraw`, which now reads `host().feeToken() == DAI` and calls `IERC20(DAI).safeTransfer(beneficiary, 100)` — transferring 100 DAI (worth far more/less than the 100 USDC actually collected) if the gateway holds DAI from other orders, or reverting (freezing the whole withdrawal, including principal) if it does not — see `evm/src/apps/intentsv2/IntentsBase.sol:472-477`.
