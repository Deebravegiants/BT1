### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) identity fields are not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value delivered to app webhook handlers from the `shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. This breaks the binding `verified_bytes == acted_upon_identity` for the tenant (`shop`) field, mirroring the report's bug class of "a field acted on but not covered by the HMAC."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an HTTP header, independent of the body: [2](#0-1) 

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (i.e., the body) and compares it against the `hmac` field, never incorporating `shop`, `topic`, `webhook-id`, or `api-version`: [3](#0-2) 

`Registry.process` accepts any request whose body HMAC validates, then hands `request.shop` (the unauthenticated header) straight to the app's handler as the authoritative tenant identifier: [4](#0-3) 

The identity binding that should hold is: `shop_authenticated_by_hmac == shop_used_by_handler`. In reality, `shop_authenticated_by_hmac` doesn't exist (HMAC signs bytes independent of shop), while `shop_used_by_handler = header("shopify-shop-domain")`, an attacker-controlled value at the HTTP layer.

Because a single app's `client_secret` (used as the HMAC key) is shared across every merchant who installs the app — it is not shop-specific — any unprivileged user who installs the app on their own store legitimately receives correctly-HMAC-signed webhook deliveries for their own shop's body content. That same person can then re-POST the identical `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header value with a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspected those headers), and `Registry.process` forwards `WebhookMetadata.new(shop: <spoofed value>, ...)` to the handler as if it were an authentic delivery for the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the gem provides no cryptographic binding between the verified bytes (body) and the shop identity that the host application uses to select per-tenant behavior (e.g., writing GDPR redact records, invalidating/creating per-shop cached data, triggering per-shop business logic) — exactly the class of finding the rules classify as Critical (cross-tenant access) because the webhook consumer of this gem's documented API (`WebhookMetadata#shop`) is given an identity value with no authentication guarantee.

### Likelihood Explanation
Exploitation only requires the ability to install the target app on an attacker-controlled shop (a normal, unprivileged action any Shopify merchant/developer can perform) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-chosen headers — both trivially available to an "unprivileged internet user" per the threat model. No access token, `client_secret`, or privileged account is needed.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used by `HmacValidator`, or otherwise cryptographically bind them to the HMAC-verified body (e.g., append them to the HMAC input, or require the host app to cross-check `shop` against the URL/session context rather than trusting the header). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be used as a sole tenant-selection key.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, obtaining valid webhook deliveries signed with the app's shared `client_secret`.
2. Attacker captures one such delivery: raw body `B` and its valid `x-shopify-hmac-sha256` value `H = HMAC(secret, B)`.
3. Attacker re-sends `POST /webhooks` with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` — validation succeeds because `shop` is never part of the signed material: [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes it as a legitimate event for the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
