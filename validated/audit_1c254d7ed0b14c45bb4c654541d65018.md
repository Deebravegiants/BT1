### Title
Webhook `topic`/`shop`/`webhook_id`/`api_version` are dispatched to handlers without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which validates the HMAC over `Request#to_signable_string`. That method returns only `@raw_body` [1](#0-0) . The `topic`, `shop`, `webhook_id`, and `api_version` values, however, are read directly from HTTP headers [2](#0-1)  and are never included in the signed bytes. After HMAC validation passes, `Registry.process` dispatches to the handler using these unauthenticated header values as if they were verified: [3](#0-2) .

### Finding Description
The binding that should hold is:
`bytes verified by HMAC == bytes the application trusts to identify topic/shop/webhook_id`.

In this gem that equality is broken: `HmacValidator.validate_signature` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the header-supplied `hmac` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` is exactly `@raw_body` — no header value is folded into the signed string [1](#0-0) .

`Registry.process` treats a passing HMAC check as authorization to trust the entire request, including headers that were never signed:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler = @registry[request.topic]&.handler
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [3](#0-2) 

Because only `@raw_body` is bound to the HMAC, any `(raw_body, hmac)` pair that was legitimately produced once (e.g. from a webhook Shopify sent for a store the attacker legitimately controls, such as a free development/partner test store) remains cryptographically valid forever for that body — regardless of which `shopify-topic`, `shopify-shop-domain`, `shopify-webhook-id`, or `shopify-api-version` headers accompany it. An attacker who owns a store (an unprivileged internet user with respect to any *other* merchant's tenant) can capture one genuine webhook delivery to their own endpoint, then replay the identical body+HMAC to the target app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop's domain (and/or the `shopify-topic`/`webhook_id` headers changed), and `HmacValidator.validate` will still return `true` because it never inspected those headers.

This root cause is structural and independent of `Context.api_secret_key` secrecy for the *replay* step: the attacker does not need to know the secret to perform the replay — they only need to have received one legitimately-signed body once, then reuse it under attacker-chosen headers.

### Impact Explanation
This breaks the shop-tenant identity binding: `WebhookMetadata#shop` is supposed to identify which merchant's data the payload belongs to, but that value is attacker-controllable independent of the signed body. Any host application that uses `data.shop` from `WebhookHandler#handle` to select which tenant's records to create/update/delete (the documented and expected usage pattern per `docs/usage/webhooks.md` and `WebhookMetadata`) will process/attribute the replayed payload under a **different, victim tenant**, i.e. cross-tenant data injection/confusion. Additionally, since `topic` and `webhook_id` are also unauthenticated, an attacker can also make the reused body dispatch to an arbitrary registered handler by claiming a different topic, further amplifying which code path and data model receives attacker-influenced content. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High reachability, moderate practical likelihood: any actor capable of installing/creating a Shopify development or trial store (no privileged access to the target app or its secrets required) can obtain one legitimately HMAC-signed webhook body/hmac pair, then freely resend it to the target app's public webhook endpoint with forged headers, since the endpoint is by design internet-reachable and unauthenticated apart from the HMAC check. No knowledge of `api_secret_key`, access tokens, or the victim's credentials is required for the replay step itself.

### Recommendation
Bind the identity-relevant headers into the HMAC-verified material, or otherwise reject/ignore header trust when they aren't cryptographically tied to the payload. Concretely:
- Extend `Webhooks::Request#to_signable_string` to include `topic`, `shop`, `webhook_id`, and `api_version` (in a canonical, delimiter-safe form) so that `HmacValidator.validate` fails if any of them are altered, or
- Require the host application to separately verify `shop` against the currently expected/authorized store for that endpoint before trusting `WebhookMetadata#shop`, and document this requirement explicitly, since the library's `HmacValidator` does not perform this binding today.

### Proof of Concept
```ruby
# Step 1: Attacker installs app on their own store (no special privileges needed)
# and captures one legitimate webhook delivery to a controlled listener:
#   raw_body = '{"id":123}'
#   hmac     = <valid Base64 HMAC-SHA256 over raw_body using the app's secret, computed by Shopify>
#   headers  = {
#     "x-shopify-topic" => "orders/create",
#     "x-shopify-hmac-sha256" => hmac,
#     "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
#     "x-shopify-webhook-id" => "attacker-webhook-id",
#     "x-shopify-api-version" => "2024-01",
#   }

# Step 2: Attacker replays the identical body+hmac to the target app's public
# webhook endpoint, only changing the shop-domain (and/or topic) header:
forged_headers = headers.merge(
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
)

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HmacValidator only checks `raw_body`, so this still succeeds:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process happily dispatches with the forged shop:
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(topic: "orders/create",
#   shop: "victim-shop.myshopify.com", body: {"id"=>123}, ...))
```
This demonstrates that `request.shop` (and `request.topic`/`webhook_id`/`api_version`) can be freely set by the caller while `HmacValidator.validate` still returns `true`, confirmed against `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb`. [5](#0-4) [6](#0-5)
