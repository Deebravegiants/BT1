**Analysis:**

The premise is incorrect: `new_signature_from_bytes` (aptos-move/framework/aptos-stdlib/sources/cryptography/ed25519.move:90-93) only checks the length as a preliminary sanity gate, but the actual cryptographic rejection of malformed signatures happens entirely inside the native function `signature_verify_strict_internal`, not in Move. [1](#0-0) 

That native function deserializes the signature/pubkey and calls `sig.verify_arbitrary_msg(msg, &pk)`: [2](#0-1) 

`verify_arbitrary_msg` is implemented to perform the full RFC 8032 "strict" verification, explicitly including scalar malleability checking (`check_s_malleability`) and small-subgroup/cofactor-8 checks on both the signature's R-component and the public key via `verify_strict`: [3](#0-2) 

This is exactly the class of attack the question describes (identity element, cofactor-8 torsion signatures) — `verify_strict` is specifically designed to reject these, not merely check byte length. There is no "latent difference" between the Move wrapper's assumption and native behavior: the Move doc comment for `signature_verify_strict_internal` explicitly documents that it returns `false` for wrong sizes, failed points-on-curve, small-subgroup public keys, small-subgroup signatures, or failed verification: [4](#0-3) 

There is also an existing regression/fuzzer test confirming that an all-zero 64-byte signature (passes the length assert but is cryptographically invalid) is correctly rejected by `signature_verify_strict`: [5](#0-4) 

Since the length-only check in `new_signature_from_bytes` is not the security boundary — the native "strict" verifier is — there's no path by which a length-conforming but curve/subgroup-invalid signature bypasses rejection and reaches `account::rotate_authentication_key`, which itself relies on `signature_verify_strict_t` built on the same native primitive. The custody boundary (authentication-key rotation approval) remains protected by cryptographically sound point and malleability checks performed natively, not by Move-level assertions.

    /// Checks that `self` is valid for an arbitrary &[u8] `message` using `public_key`.
    /// Outside of this crate, this particular function should only be used for native signature
    /// verification in Move.
    ///
    /// This function will check both the signature and `public_key` for small subgroup attacks.
    fn verify_arbitrary_msg(&self, message: &[u8], public_key: &Ed25519PublicKey) -> Result<()> {
        // NOTE: ed25519::PublicKey::verify_strict already checks that the s-component of the signature
        // is not mauled, but does so via an optimistic path which fails into a slower path. By doing
        // our own (much faster) checking here, we can ensure dalek's optimistic path always succeeds
        // and the slow path is never triggered.
        Ed25519Signature::check_s_malleability(&self.to_bytes())?;

        // NOTE: ed25519::PublicKey::verify_strict checks that the signature's R-component and
        // the public key are *not* in a small subgroup.
        public_key
            .0
            .verify_strict(message, &self.0)
            .map_err(|e| anyhow!("{}", e))
            .and(Ok(()))
    }
