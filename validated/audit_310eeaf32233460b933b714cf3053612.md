### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the HMAC only over the raw request body, while the `shop` (tenant identity) is read directly from the `X-Shopify-Shop-Domain` header, which is never included in the signed material. Any component of the request payload that a receiving app uses to route processing to a specific merchant/tenant — the shop domain — is therefore unauthenticated with respect to the cryptographic signature the gem exposes as its authenticity guarantee.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#hmac` decodes the `hmac-sha256` header for comparison: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` verifies `computed_signature(to_signable_string) == received hmac`, i.e., it authenticates the body bytes only: [3](#0-2) 

Meanwhile `Request#shop`, which callers use to determine which merchant/tenant a webhook belongs to (e.g. to load that shop's session/access token before processing), is taken straight from an unauthenticated header: [4](#0-3) 

The identity binding that should hold is:
`shop-domain header used to select the tenant == shop that produced/authorized the signed body`

Because `to_signable_string` never includes the `shop-domain` (or `webhook-id`/`topic`) header, this equality is never checked. `HmacValidator.validate(request)` only proves "this body byte sequence was signed by *some* holder of `api_secret_key`" — for a multi-shop app scenario or a replay/header-substitution scenario, an attacker who can influence or capture a validly-signed body+hmac pair (e.g. from a webhook to their own shop, or via a man-in-the-middle before TLS termination at the app's ingress) can present the same raw body and hmac digest together with a different `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` will still return `true`, and the host application, trusting `request.shop`, will process the payload as belonging to a different tenant.

This maps directly to the report's bug class: an "an authenticated boundary attribute (shop identity) accepted from parsed/unauthenticated bytes rather than the bytes actually covered by the cryptographic check."

### Impact Explanation
If a host application uses `Webhooks::Request#shop` to select which merchant record, session, or access token to associate the incoming webhook payload with (which is the documented use case for this accessor), an attacker able to supply an arbitrary `shop-domain` header alongside a validly-HMAC'd body can cause the application to attribute webhook data (order/customer/product changes, GDPR/compliance events, etc.) to the wrong tenant. This is a cross-tenant integrity issue: data intended for shop A gets processed under the identity of shop B, potentially triggering unauthorized actions, cache poisoning, or state corruption scoped to the wrong merchant. This satisfies the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one validly signed `(raw_body, hmac)` pair for the target app's `api_secret_key` — normally only Shopify can produce this, but the attacker only needs *any* valid signed body (e.g., delivered to their own registered shop, since apps commonly serve many merchants under one `api_secret_key`), then replay it with a substituted `shop-domain` header value pointing at a different (victim) shop. Because the gem performs no correlation between the signed bytes and the header-derived `shop` value, and downstream code in this repository (`lib/shopify_api/webhooks/registry.rb`) forwards `request` — including `request.shop` — to handler callbacks without any independent shop verification, likelihood is elevated whenever a single app instance serves multiple shops (the standard SaaS embedded-app model that this gem targets).

### Recommendation
Include the shop domain (and ideally `topic`/`webhook-id`) in the value protected by the signature check, or otherwise cryptographically bind them, e.g.:
```diff
 sig { override.returns(String) }
 def to_signable_string
-  @raw_body
+  "#{shop}\n#{topic}\n#{@raw_body}"
 end
```
Note this specific change is illustrative only — Shopify's actual webhook signature is computed over the raw body per their spec, so the correct fix must live at the point where `request.shop` is consumed: the gem should document/enforce that callers must additionally verify the `shop` header value against a known/expected shop for the given app installation (e.g., cross-checking against the shop stored for the resolved session) rather than trusting the header value merely because the body-only HMAC passed.

### Proof of Concept
```ruby
require "shopify_api"

# Attacker captures a legitimately signed webhook delivered to their own shop
raw_body = '{"id":123,"email":"victim-order@example.com"}'
valid_hmac = OpenSSL::HMAC.hexdigest(
  OpenSSL::Digest.new("sha256"),
  ShopifyAPI::Context.api_secret_key,
  raw_body,
)
hmac_b64 = Base64.strict_encode64([valid_hmac].pack("H*"))

# Attacker resends the same body+hmac but swaps the shop-domain header
headers = {
  "X-Shopify-Topic" => "orders/create",
  "X-Shopify-Hmac-Sha256" => hmac_b64,
  "X-Shopify-Shop-Domain" => "victim-shop.myshopify.com", # arbitrary, unauthenticated
  "X-Shopify-Webhook-Id" => "1",
  "X-Shopify-Api-Version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

ShopifyAPI::Utils::HmacValidator.validate(request) # => true
request.shop # => "victim-shop.myshopify.com" (fully attacker-controlled, unauthenticated)
```
The `HmacValidator.validate` call returns `true` because only `raw_body` is signed; `request.shop`, which the host app uses for tenant routing, is fully attacker-controlled and unauthenticated.
