### Title
`EvmHost` constructor accepts an unvalidated `_admin` address, permanently bricking the host and blocking `initialize` - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost`'s constructor stores the caller-supplied `_admin` parameter into `_hostParams.admin` with no validation, unlike the analogous `HostManager` constructor which explicitly rejects a zero admin. Since `initialize()` — the only function that can ever set the rest of `HostParams` (handler, consensusClient, hostManager, feeToken, stateMachines, hyperbridge id) — is gated by `_msgSender() == _hostParams.admin`, an incorrect (especially zero) `_admin` value at deployment makes the host permanently uninitializable.

### Finding Description
The `EvmHost` constructor only sets `_admin` and the consensus timestamp, deferring all other configuration to a one-shot `initialize`: [1](#0-0) 

```solidity
constructor(address _admin) {
    _consensusUpdateTimestamp = block.timestamp;
    _hostParams.admin = _admin;
}

function initialize(HostParams memory params) external {
    if (_msgSender() != _hostParams.admin) revert UnauthorizedAction();
    if (_initialized) revert UnauthorizedAction();
    _initialized = true;
    updateHostParamsInternal(params);
}
```

There is no `address(0)` check on `_admin` in the constructor. If `_admin` is ever passed as `address(0)` (e.g. deployment script misconfiguration, a bad `vm.envAddress`/CLI argument, or a CREATE2 factory forwarding a default/zero value), `_hostParams.admin` becomes `address(0)`. Because no externally-owned account or contract can ever have `msg.sender == address(0)` in a real transaction, `initialize` becomes permanently uncallable: `_msgSender() != _hostParams.admin` is always true, so it always reverts with `UnauthorizedAction`.

This is the direct on-chain analog of the reported "no validation of address parameter in constructor" bug class (originally about `BaseStrategy`'s `vault`): a constructor-supplied address that gates all subsequent initialization/configuration is never checked, so an incorrect value (most severely, zero) leaves the contract unable to complete setup.

Contrast this with `HostManager`, which validates the identical kind of admin parameter in its constructor: [2](#0-1) 

```solidity
constructor(HostManagerParams memory managerParams) {
    if (managerParams.admin == address(0)) revert InvalidAdmin();
    _params = managerParams;
}
```

`EvmHost` has no equivalent guard, despite `_hostParams.admin` playing the same "sole key that can ever configure this contract" role.

### Impact Explanation
`EvmHost` is the core dispatcher/receiver contract for ISMP messages on the EVM side — all outgoing dispatch, incoming request/response delivery, consensus updates, and state-commitment storage flow through it, and it is meant to hold and route fee-token/native revenue (`withdraw`, `_requestCommitments`). If `initialize` can never be called because `_admin` was deployed as zero (or any address the deployer does not control), then:
- `_hostParams` (handler, consensusClient, hostManager, feeToken, stateMachines, hyperbridge id) can never be set, so the host can never process any request/response, permanently freezing the route for that chain.
- Any funds sent to the host (native token via `receive()`, or fee tokens transferred to it in anticipation of use) become permanently stuck, since `withdraw` requires `_hostParams.hostManager` to be set and reachable via cross-chain governance, which is impossible pre-`initialize`.
- Redeployment is the only remedy, and CREATE2 address parity across chains (the stated purpose of deferring params to `initialize`) is broken for the affected chain.

This satisfies the "permanent freezing of funds" / "route unable to deliver messages" bar for Medium/High severity in an unprivileged-message-dispatch-reachable core contract.

### Likelihood Explanation
This is a deployment-time misconfiguration, not an attacker-triggered exploit, so likelihood is low but the blast radius given it happens is total loss of that host deployment's usability. The `DeployIsmp.s.sol` script currently reads `admin` from an env var and passes it straight to the constructor with no zero check before broadcasting — a single bad env value, a typo, or a factory/tooling default of `address(0)` is enough to trigger it irreversibly (the constructor argument cannot be changed after deployment).

### Recommendation
Add a zero-address (and ideally EOA/contract sanity, matching `HostManager`'s pattern) check to `EvmHost`'s constructor:
```solidity
constructor(address _admin) {
    if (_admin == address(0)) revert InvalidAdmin();
    _consensusUpdateTimestamp = block.timestamp;
    _hostParams.admin = _admin;
}
```
This mirrors the existing `HostManager.InvalidAdmin` guard and prevents an unrecoverable host deployment.

### Proof of Concept
1. Deploy `EvmHost` (or `TestnetHost`/`MainnetTestHost`, which share the constructor) with `_admin = address(0)`:
   ```solidity
   EvmHost host = new EvmHost(address(0));
   ```
2. Attempt to call `initialize(params)` from any account, including `address(this)`/deployer:
   ```solidity
   host.initialize(params); // reverts UnauthorizedAction, since _msgSender() != address(0)
   ```
3. Every subsequent call reverts identically — there is no path to set `_hostParams.handler`, `.consensusClient`, `.hostManager`, `.feeToken`, `.stateMachines`, or `.hyperbridge`. The contract is permanently non-functional; any tokens sent to it are unrecoverable since `withdraw` is gated behind an unset `hostManager`.
