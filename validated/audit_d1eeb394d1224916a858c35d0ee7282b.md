### Title
Unvalidated zero-address `output.beneficiary` in `IntentGatewayV2` orders causes solver-supplied native ETH output to be permanently burned - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol, evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`IntentGatewayV2.placeOrder` accepts an `Order.output.beneficiary` field fully controlled by the order-creating user, with no validation against `address(0)`. When a solver later fills that order via `_fillSameChain` or `_fillCrossChain`, native-ETH outputs are sent to the decoded beneficiary through `_sendValue`, a raw low-level `.call{value:}` that does not revert when the target is `address(0)`. This mirrors the reported bug class where a destination address of zero permanently traps funds because nothing can ever "withdraw" from `address(0)`.

### Finding Description
`Order.output.beneficiary` is a `bytes32` supplied by the user at `placeOrder` time and is decoded directly to an `address` without a zero check: [1](#0-0) [2](#0-1) 

Both fill paths call `_sendValue(beneficiary, amount)` for native-token outputs: [3](#0-2) 

```solidity
function _sendValue(address to, uint256 amount) internal {
    (bool sent,) = to.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
}
```

A low-level `.call{value:}` to `address(0)` succeeds (returns `sent = true`) since there is no receive/fallback requirement for EOAs or non-existent addresses — the call simply transfers ether with no code executed. This is unlike `IERC20.safeTransfer`/`transferFrom` to `address(0)`, which OpenZeppelin's `ERC20._transfer` explicitly reverts on. So while ERC20 outputs to a zero beneficiary would revert (protecting solvers there), native ETH outputs do not, and the ETH is irrecoverably sent to `address(0)` — permanently destroyed, with no path to reclaim it via `withdraw`, `cancelOrder`, or any other function in `IntentsBase`.

Additionally, the escrow release path `IntentsBase._withdraw` decodes `WithdrawalRequest.beneficiary` the same unchecked way and calls `_sendValue` for native-token escrow releases: [4](#0-3) 

If an order's native-token input is escrowed and the associated withdrawal beneficiary resolves to zero (e.g., a user places an order with `order.user`/beneficiary fields that later decode to zero on refund), the same permanent-loss pattern applies on the source chain.

### Impact Explanation
Funds sent as native-ETH order outputs (solver-provided) or as native-ETH escrow refunds/releases can be permanently and unrecoverably lost if the order's `output.beneficiary` (or refund beneficiary) resolves to `address(0)`, whether due to user error when constructing the order or a wallet/integration bug that zero-fills the beneficiary field. This is a permanent freezing-of-funds condition matching the "Medium/High — permanent freezing of funds" impact category, since:
- There is no recovery mechanism once `_sendValue` succeeds against `address(0)`.
- The solver providing the output (their own capital) bears the loss with no path to reverse it, and the transaction does not revert to signal the mistake (unlike the ERC20 path, which reverts safely).

### Likelihood Explanation
Any user submitting an order through `placeOrder` fully controls `order.output.beneficiary`; no additional privilege is required to reach `_fillSameChain`/`_fillCrossChain`. A malformed integration (e.g., an SDK bug zero-padding an address, or a user copy-pasting an incomplete address) is a realistic, low-effort trigger, exactly analogous to the original `depositFor(address(0), amount)` scenario. The condition requires only that the output asset be native ETH (`token == address(0)` in `TokenInfo`), which is an explicitly supported path in both same-chain and cross-chain fills, and is exercised directly by existing tests (e.g. `testSameChainSwap_WithProtocolFee`-style native-output tests).

### Recommendation
Add an explicit zero-address check at the point orders/withdrawals decode their beneficiary, failing closed:
- In `IntentsBase` (or `IntentGatewayV2.placeOrder`), require `order.output.beneficiary != bytes32(0)` when validating a submitted order.
- In `_fillSameChain`, `_fillCrossChain`, and `_withdraw`, require the decoded `beneficiary != address(0)` before dispatching any `_sendValue` or token transfer, reverting with a clear `InvalidBeneficiary()` error instead of silently succeeding.
- Alternatively/also, harden `_sendValue` itself to revert when `to == address(0)`.

### Proof of Concept
1. User calls `placeOrder` with `order.output.assets = [{token: bytes32(0), amount: X}]` (native ETH output) and `order.output.beneficiary = bytes32(0)` (either mistakenly or via a buggy client).
2. Escrow of `order.inputs` succeeds normally (unaffected by the beneficiary field).
3. A solver calls `fillOrder` (same-chain path `_fillSameChain` or cross-chain path `_fillCrossChain`), providing native ETH `msg.value >= totalRequired`.
4. Internally, `beneficiary = address(uint160(uint256(order.output.beneficiary))) == address(0)`.
5. `_sendValue(address(0), totalRequired + beneficiaryShare)` executes `address(0).call{value: amount}("")`, which returns `sent = true` — the ETH is sent and permanently lost; the call does not revert.
6. The order is nonetheless marked filled (`_filled[commitment] = msg.sender`), and the solver's escrowed input release (`RedeemEscrow`) proceeds normally — the solver has paid real ETH into the void while still "successfully" filling the order.
