### Title
Webhook HMAC only covers the raw body, not the `shop-domain`/`topic`/`webhook-id` headers, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only `@raw_body`, and `Utils::HmacValidator` verifies the HMAC exclusively against that body. The `shop`, `topic`, `api_version`, and `webhook_id` values — all read straight from HTTP headers — are never included in the signed data, yet `Registry.process` trusts them unconditionally and hands them to the app's handler via `WebhookMetadata`.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 
The HMAC validator checks the received signature against that signable string only: [2](#0-1) 
`Registry.process` validates the HMAC, then immediately builds `WebhookMetadata` from unauthenticated headers (`request.shop`, `request.topic`, `request.api_version`, `request.webhook_id`) and passes it to the app's handler: [3](#0-2) 
Those accessors simply read directly from the caller-supplied header hash with no cryptographic binding to the signed body: [4](#0-3) 

The binding that breaks is: `hmac(raw_body)` should equal `hmac(raw_body ‖ shop ‖ topic ‖ webhook_id)`, but only the former is checked while the latter fields are trusted as if they were signed. This is the exact bug class from the referenced report — a security-relevant identifier (`shop`) is used as though covered by the cryptographic check when it is not.

Because the app's own `api_secret_key` is identical across every shop that installs the app, any merchant (an ordinary, unprivileged internet user who can freely install a public/development app) can:
1. Install the target app on their own shop and receive a genuine Shopify webhook (valid `raw_body` + valid `x-shopify-hmac-sha256`, both computed with the app's shared `client_secret`).
2. Replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain.
3. `HmacValidator.validate` still passes because it only checks the body, so `Registry.process` invokes the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain while the body content is the attacker's own data.

The gem's own documentation confirms `data.shop` is meant to be trusted as the shop identity for downstream per-tenant processing: [5](#0-4) 

### Impact Explanation
This breaks the tenant identity binding between the cryptographically-verified payload and the shop it is attributed to. An app that uses `data.shop` (as the gem's own documented example does) to route data, update per-shop records, or key background jobs can be made to process attacker-supplied webhook content under an arbitrary victim shop's identity — a cross-tenant data-integrity/confidentiality issue reachable without the app's `access_token`, `api_secret_key`, or any privileged access; the attacker only needs the ability to install the app once as a normal merchant.

### Likelihood Explanation
Moderate. It requires the attacker to have installed the target app at least once to obtain a validly-signed `(body, hmac)` pair, which is trivial for any public/free app and typically requires only a free Shopify development store. No secret material, TLS interception, or privileged account is needed; the header/HMAC decoupling exists in every deployment of the gem's webhook processing code path.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed payload used for HMAC verification, or otherwise cryptographically bind them to the verified body (e.g., re-derive/validate the shop domain from a source that is itself authenticated, such as looking up the webhook subscription by `webhook_id` via the Admin API rather than trusting the header directly), so that `Registry.process` cannot be induced to attribute verified body content to an unauthenticated shop.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop and captures a genuine webhook:
#    body   = '{"id":1,"note":"attacker controlled"}'
#    hmac   = Base64(HMAC-SHA256(app_client_secret, body))   # computed by real Shopify for attacker's own shop

# 2. Attacker replays the exact body+hmac to the app's public webhook endpoint,
#    but swaps the shop header to the victim's domain:
headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => captured_hmac,       # unchanged, still valid for `body`
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id"   => "anything",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only `raw_body` is checked)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: attacker_body, ...))
``` [3](#0-2)
