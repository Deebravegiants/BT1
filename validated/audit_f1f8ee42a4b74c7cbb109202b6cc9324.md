### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  and `ShopifyAPI::Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string [2](#0-1) . However, `Registry.process` trusts `request.shop` — sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [3](#0-2)  — as the tenant identity for the webhook and hands it directly to the app's handler [4](#0-3) . The shop-domain header is never part of the HMAC-signed material, so it can be modified freely without invalidating the signature.

### Finding Description
The identity binding that should hold is:

`shop_header_used_for_attribution == shop_bound_by_hmac_signature`

In this gem, `HmacValidator.validate(request)` only checks that `hmac == HMAC(secret, raw_body)` [5](#0-4) , because `Request#to_signable_string` is defined as just `@raw_body` [1](#0-0) . The `shop` accessor reads the `shopify-shop-domain` header independently of that signed content [3](#0-2) .

`Registry.process` does:
1. Validate the HMAC over the body only.
2. Look up the handler by `request.topic`.
3. Call `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

Because `shop` is never included in the signable string, any request with a body+HMAC pair that is valid for the app's secret (for example, a webhook the attacker legitimately received for their own, attacker-controlled shop where the app is installed) remains HMAC-valid when the `shopify-shop-domain` header is swapped to an arbitrary victim shop domain. The documented usage pattern explicitly passes `data.shop` on to application logic (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [6](#0-5) , so host applications built per this gem's own documented API will store/act on the (unauthenticated) header value as the tenant identifier.

### Impact Explanation
This breaks the identity binding between the cryptographically-verified payload and the tenant (shop) the host application will attribute that payload to. Since the app's persistence/business logic keys off `data.shop` as returned by this gem's own `Registry.process`/`WebhookMetadata`, an attacker who controls one shop (and therefore can generate valid signed webhook bodies for that shop) can inject data into another merchant's records by simply changing the shop-domain header on replay — resulting in cross-tenant data injection/contamination, which maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is Medium: it requires an attacker to have or install the app on at least one shop they control (a low bar — creating a Shopify development/partner store is free), capture a body+HMAC pair for a webhook topic of interest, and replay it to the app's webhook endpoint with a modified shop-domain header. No possession of the app's `client_secret` or any merchant's access token is needed, and the request path is exactly the one this gem's own `Registry.process` documents and supports.

### Recommendation
Bind the shop identity into the verified material, or otherwise cryptographically tie the `shop-domain` header to the signed payload before trusting it:
- Extend `VerifiableQuery#to_signable_string` for `Webhooks::Request` to include the shop-domain header (and other trust-sensitive headers) in the signed string, matching how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`/`host` into its signature [7](#0-6) ; or
- Cross-check `request.shop` against the shop embedded in the parsed webhook body (when present) and reject mismatches before invoking the handler in `Registry.process` [4](#0-3) .

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers the `orders/create` webhook (supported by the app via `Registry.add_registration`).
2. Attacker triggers an order-create event on their own shop, capturing the resulting webhook POST: `raw_body = B`, header `shopify-hmac-sha256 = HMAC(secret, B)`, header `shopify-shop-domain = attacker-shop.myshopify.com`.
3. Attacker resends the exact same request to the app's webhook endpoint but replaces the header value with `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — unaffected by the header change — and the check passes [2](#0-1) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes/persists the attacker's payload `B` as if it belonged to `victim-shop.myshopify.com` [8](#0-7) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
