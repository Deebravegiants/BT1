### Title
Unvalidated swap routes can inject unauthorized token transfers into a victim’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The reflected-XSS bug class maps to untrusted route data being interpreted inside the victim’s trusted authorization context. `swap_collateral`, `multiply`, `swap_debt`, and `repay_debt_with_collateral` accept caller-controlled `swap: Bytes` and pass it to the configured router while the account owner’s authorization is active. A route can name attacker-controlled venue code, which may request an unrelated token transfer from the victim; transaction simulation then records that transfer as a signed child of the victim’s controller authorization. [1](#0-0) [2](#0-1) 

### Finding Description
`Controller::swap_collateral(caller, account_id, current, amount, new, swap)` requires owner or delegate authorization, then forwards `swap` into `withdraw_and_swap_from_supply`. [3](#0-2) [4](#0-3) 

The controller correctly restricts its own router grant to one exact token transfer, but it does not decode the route, constrain route-selected venue contracts, or prevent venue code from introducing another victim-authorized call beneath the signed root. [5](#0-4) 

The route’s venue and token addresses come from caller-controlled payload data, and each swap hop is dispatched to the venue-specific call path using the payload-selected pool address. [6](#0-5) [7](#0-6) 

The regression test demonstrates the resulting injection: a rogue route pool calls `token.transfer(victim, attacker, amount)` during route execution, simulation attaches it as a child of the victim’s `swap_collateral` authorization, and signing the simulated tree transfers the victim’s entire unrelated wallet balance. [8](#0-7) [2](#0-1) 

### Impact Explanation
A victim who signs the poisoned authorization tree can lose arbitrary wallet tokens beyond the collateral or borrowed amount intended for the strategy. [9](#0-8) 

The normal measured-output and residual checks do not bound this loss because the injected child transfer is outside the routed token balances and can succeed while the strategy still returns fair output and remains solvent. [10](#0-9) [11](#0-10) 

### Likelihood Explanation
The attacker needs no privileged role: they can deploy the malicious venue and submit a crafted quote or route to the victim. [12](#0-11) 

Exploitation requires victim interaction because the malicious child authorization must appear in the signed transaction tree; an unsigned rogue transfer is rejected. [13](#0-12) 

This is therefore a medium-severity theft primitive rather than an unauthenticated direct drain: it depends on the victim accepting route data and signing the simulated authorization tree without detecting the extra child transfer. [9](#0-8) 

### Recommendation
Restrict executable route venues to governance-approved pool contracts, or make the controller validate that strategy authorization cannot include unrelated token transfers. [14](#0-13) 

At minimum, the client and protocol documentation should enforce a signed-tree invariant: `multiply`, `swap_debt`, `swap_collateral`, and `repay_debt_with_collateral` must not contain token-transfer children unrelated to the explicitly expected initial payment and router pull. [15](#0-14) 

### Proof of Concept
1. Deploy `RogueHopPool`, configured to call `token.transfer(victim, attacker, victim_balance)` from inside its venue callback. [12](#0-11) 
2. Give the victim a debt-free collateral account and an unrelated wallet token not listed by the lending market. [16](#0-15) 
3. Construct `swap_collateral(victim, account_id, USDC_market, 50_000_000_000, ETH_market, crafted_route)`, where the route names the rogue pool but still promises enough ETH output to satisfy settlement. [17](#0-16) 
4. Simulate the transaction; the host records the unrelated `token.transfer(victim, attacker, wallet_balance)` beneath the victim’s `swap_collateral` authorization. [18](#0-17) 
5. If the victim signs that simulated tree, the transaction succeeds: the unrelated wallet token moves to the attacker while the strategy deposits the expected ETH output. [11](#0-10) [9](#0-8)

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],

    let poisoned_root = AuthorizedInvocation {

            s.t.controller.clone(),
