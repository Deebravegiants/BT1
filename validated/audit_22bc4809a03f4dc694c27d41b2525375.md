### Title
Value Conservation Bypass via Empty `erc20TokenAddresses` in Min-Circuit Emporium Path Allows ETH Theft from Emporium - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When a transaction uses the `Min` verifier (`dimensions.tokenNumber == 0` → `circomData.erc20TokenAddresses.length == 0`), `EmporiumUpgradeable.runAction`'s balance-accounting loops are skipped entirely (0 iterations), while the `EmporiumOperation` execution loop still runs based on `stack.ops.length`, which is fully attacker-controlled and unconstrained by the Min circuit. This lets an attacker drain any ETH sitting on the Emporium contract to an arbitrary endpoint with zero UTXO minted and no revert.

### Finding Description
The claimed equality is: `sum(balancesAfter[i] - balancesBefore[i] + (deltaAmountChanges[i]<0 ? -deltaAmountChanges[i] : 0))` for `i` in `erc20TokenAddresses` must equal the ETH/token value actually moved by `stack.ops`. When `erc20TokenAddresses.length == 0`, both sides of this accounting are vacuously computed over an empty set: `balancesBefore`/`balancesAfter` are empty arrays [1](#0-0)  and `deltaAmountChanges` is length 0 (computed in `_externalTransact` by looping over `circomData.erc20TokenAddresses.length`) [2](#0-1) .

However, the operation-execution loop iterates over `stack.ops.length`, not `erc20TokenAddresses.length`, and can still call `op.endpoint.call{value: op.value}(op.callData)`, moving ETH out of the Emporium contract's own balance whenever `invokeWallet` is false or `signerAddress == address(0)` [3](#0-2) . The post-loop reconciliation loop that would normally catch a negative/unaccounted balance change also iterates over `erc20TokenAddresses.length` (0 in this path), so it never executes and never reverts [4](#0-3) .

Critically, `stack` (including `ops`, `signerAddress`, `value`, `callData`) is decoded from `circomData.externalActionData.externalActionMetadata`, which the attacker fully controls when generating their own proof and calldata [5](#0-4) . The only binding checks are: (1) `getHashedCalldata(circomData) == circomData.calldataHash`, which just prevents post-proof tampering of calldata the attacker itself authored [6](#0-5) [7](#0-6) ; and (2) the Min circuit `MainEVMCircuitMin`, whose only constraint is `message <== Poseidon(1)([messageSeed])` — `calldataHash` and `outTimeStamp` are public inputs with **no constraint tying them to any private signal**, so a valid Groth16 proof can be generated for literally any `calldataHash`/ops content the attacker chooses [8](#0-7) . Setting `stack.signerAddress = address(0)` (attacker's own choice, not enforced by any circuit) additionally skips the EIP-712 signature check in `verifyWallet`, requiring only an unused `emporiumMessage` nonce [9](#0-8) .

Exploit call: attacker submits `Hinkal.transact` with `dimensions.tokenNumber = 0` (so `erc20TokenAddresses`, `amountChanges`, etc. are all empty arrays, satisfying `dimensionsCheck`) [10](#0-9) , `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{ endpoint: attackerEOA, invokeWallet: false, value: <emporium ETH balance>, callData: "" }`. The attacker generates a trivially valid Min-circuit proof (any `messageSeed` works) and calls `transact`. `EmporiumUpgradeable.runAction` executes the op, sending Emporium's pre-existing ETH balance to the attacker, and returns an empty `utxoSet` with no revert, no nullifier consumption reflecting the stolen value, and no accounting failure.

Existing guards do not stop this: `performHinkalChecks`/`dimensionsCheck` only enforce internal array-length consistency, not that `erc20TokenAddresses` covers all value moved by `ops`; `verifyProof` succeeds because the Min circuit doesn't constrain `calldataHash`; `rootHashExists` is irrelevant since no nullifiers are spent; `onlyAllowedRecipient` only checks the caller is the Hinkal contract itself, not `stack.ops` contents; and the balance-based reconciliation is vacuous when the token array is empty.

### Impact Explanation
Any ETH held by the Emporium proxy — from dust left by `receive()`, partial/failed prior sessions, or any other source — can be stolen in full by an unprivileged attacker with a single `transact` call, with zero cost beyond gas and zero UTXOs burned. This is direct theft of protocol/other-users' funds parked at Emporium, matching the Critical severity bar (theft of shielded or in-flight funds / minting value without backing via unaccounted asset movement). It is fully repeatable any time Emporium holds a nonzero ETH balance.

### Likelihood Explanation
Preconditions: Emporium contract must hold ETH (highly plausible given its `receive()` fallback and its role as an intermediary in multi-op flows). Attacker cost: gas plus generating a trivially satisfiable Min-circuit proof (no real secret knowledge required since public inputs are unconstrained). No special role, tree state, or timing is needed — this is exploitable by any EOA that can deposit, generate its own proofs, and craft `CircomData`/`EmporiumStack` fields, exactly per the defined threat model.

### Recommendation
Do not let the `EmporiumOperation` execution loop run independent of the token accounting arrays. Specifically:
- Require `circomData.erc20TokenAddresses` to include every asset (including `address(0)` for ETH) that any `op.value` or token transfer inside `stack.ops` can touch, and enforce this on-chain (e.g., by summing `op.value` for native transfers and requiring `address(0)` be present with a corresponding balance check when `stack.ops` contains any `op.value > 0`).
- Alternatively, disallow the Min-circuit path from carrying any `EmporiumOperation` with non-zero `op.value` or any state-changing `callData` at all — restrict `Min` to strictly zero-value / signature-only flows — and re-verify balances-before/after using a fixed, non-empty accounting basis (including native ETH) regardless of `erc20TokenAddresses.length`.
- More generally, make `balancesBefore`/`balancesAfter` always include native ETH tracking independent of `circomData.erc20TokenAddresses`, so `runAction`'s conservation check can never be bypassed by an empty token array.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (registered under `HINKAL_EMPORIUM_ACTION_ID`), and register a Min verifier under `buildVerifierId({tokenNumber:0,...}, HINKAL_EMPORIUM_ACTION_ID)` that accepts any valid Groth16 proof for `MainEVMCircuitMin` (use snarkjs to generate one witness/proof for arbitrary `calldataHash`/`outTimeStamp`/`messageSeed`).
2. Fund the Emporium proxy with e.g. 1 ETH via a raw `.call{value: 1 ether}("")` to simulate leftover/dust balance (hits `receive()`).
3. Craft `CircomData` with `dimensions.tokenNumber = 0`, all token-dimensioned arrays empty, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionData.externalAddress = <Emporium address>`, `externalActionMetadata = abi.encode(EmporiumStack({signerAddress:address(0), ops:[EmporiumOperation({endpoint: attacker, invokeWallet:false, value:1 ether, callData:""})], ...}))`, set `calldataHash = getHashedCalldata(circomData)`.
4. Generate the Min-circuit proof and call `hinkal.transact(a,b,c,dimensions,circomData)` from the attacker EOA.
5. Assert: `attacker.balance` increased by exactly 1 ether (pre-existing Emporium balance), `emporium.address.balance == 0` after the call, and `utxoSet.length == 0` / no `Commitment` events emitted for that amount — proving the ETH left Emporium with no corresponding `deltaAmountChanges` or minted shielded UTXO to account for it.
