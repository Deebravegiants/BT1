Audit Report

## Title
LDAP DN injection via `ldap.EscapeFilter` misuse when constructing bind DN and search-base DN strings - (File: core/sessions/ldapauth/ldap.go)

## Summary
The unauthenticated login handler `CreateSession`, as well as `TestPassword` and `FindUser`, take attacker-controlled email input and escape it with `ldap.EscapeFilter` before splicing it directly into an LDAP Distinguished Name string used as the bind DN or as part of a filter's DN-like value. `EscapeFilter` only implements RFC 4515 filter-value escaping and does not escape RFC 4514 DN-structural metacharacters (`,`, `+`, `"`, `<`, `>`, `;`), so a crafted email containing these characters can alter the DN structure passed to `conn.Bind`/`conn.Search`.

## Finding Description
In `CreateSession`, the code lowercases and filter-escapes `sr.Email`, then builds `searchBaseDN` by string concatenation and passes it as the actual bind DN to `conn.Bind`: [1](#0-0) . Because a bind DN is parsed by the server according to RFC 4514 DN syntax, not RFC 4515 filter syntax, `EscapeFilter`'s escaping of `(`, `)`, `\`, `*`, NUL is the wrong character class for this context — DN delimiters like comma remain unescaped and can inject additional RDN components. The identical pattern exists in `TestPassword`: [2](#0-1) , and a DN-like value is embedded in a filter in `FindUser`: [3](#0-2) . The `SessionRequest.Email` field is a plain, unvalidated JSON string with no character-set restriction: [4](#0-3) , and `SessionsController.Create` binds this JSON body directly and forwards `sr` unmodified to `CreateSession` with no additional sanitization: [5](#0-4) . No DN-escaping helper or input validation exists anywhere in this path to compensate for `EscapeFilter`'s insufficiency in a DN context.

## Impact Explanation
This maps to an in-scope node API authentication/role manipulation issue: an attacker who can reach the `/sessions` create endpoint (unauthenticated, since this is the login endpoint itself) can inject extra RDN components into the DN used for `conn.Bind`, potentially altering which directory entry the LDAP server treats as the bind target, and consequently which roles get resolved via `FindUser`'s group-membership DN/filter construction, which uses the same unescaped pattern.

## Likelihood Explanation
The path requires only that the operator has configured LDAP authentication (`ldapAuthenticator`) — a supported, documented configuration — and that an attacker submit a normal, unauthenticated POST to the session-creation endpoint with a crafted `email` value containing DN metacharacters such as `,`. No credentials, prior session, or elevated privilege are needed to reach this code.

## Recommendation
Implement and use a proper RFC 4514 DN-escaping function for any user-controlled value interpolated into a DN string (the `searchBaseDN` construction in `CreateSession`, `TestPassword`, and the `uniquemember=...` value in `FindUser`), escaping `,`, `+`, `"`, `\`, `<`, `>`, `;`, leading/trailing spaces, and a leading `#`. `ldap.EscapeFilter` should be reserved only for values placed inside filter expressions, never for DN components.

## Proof of Concept
1. Configure chainlink with LDAP auth enabled, `BaseUserAttr=uid`, `UsersDN=ou=users`, `BaseDN=dc=example,dc=com`, against a test LDAP directory.
2. POST to the session-creation endpoint (`SessionsController.Create`) with `email = "victim,ou=admins,dc=example,dc=com"` and an arbitrary password.
3. Trace execution into `CreateSession` at `core/sessions/ldapauth/ldap.go:406-408`: the resulting `searchBaseDN` becomes `uid=victim,ou=admins,dc=example,dc=com,ou=users,dc=example,dc=com`, demonstrating that the unescaped comma injects an additional RDN segment into the DN passed to `conn.Bind`, confirming attacker control over DN structure rather than confinement to a single attribute value.
