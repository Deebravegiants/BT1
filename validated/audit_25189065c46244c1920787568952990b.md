### Title
Unrestricted `superApprove` in `HyperFungibleTokenImpl` allows any caller to grant unlimited allowance over any holder's tokens - (File: evm/src/utils/HyperFungibleTokenImpl.sol)

### Summary
`HyperFungibleTokenImpl` (the cross-chain fungible token implementation used by Hyperbridge's token-bridge tooling, referenced from `evm/script/DeployIsmp.s.sol` and `evm/src/utils/TokenFaucet.sol`) exposes a `public`, access-control-free function that grants `type(uint256).max` allowance from an arbitrary owner to an arbitrary spender.

### Finding Description
The function: [1](#0-0) 

```solidity
function superApprove(address owner, address spender) public {
    _approve(owner, spender, type(uint256).max);
}
```

is marked `public` with no `msg.sender == owner` check, no role gate, and no caller restriction at all. It directly invokes OpenZeppelin's internal `_approve(owner, spender, amount)` on behalf of an arbitrary `owner` address supplied as a function parameter, setting an unlimited allowance for an arbitrary `spender`, also supplied as a parameter. Unlike a normal ERC-20 `approve`, which is scoped to `msg.sender`, this function lets *any* unprivileged caller set the allowance mapping for *any other account's* balance.

This directly matches and exceeds the reported bug class of "unjustified unlimited (`type(uint).max`) approvals": rather than a contract over-approving its *own* funds to a trusted router (as in the original Bebop report), here a completely unprivileged actor can grant an unlimited allowance over *someone else's* funds to *any* spender of their choosing.

### Impact Explanation
Any address can call `superApprove(victim, attacker)` to obtain unlimited spending allowance over `victim`'s balance of the `HyperFungibleTokenImpl` token, then call the standard ERC-20 `transferFrom(victim, attacker, balance)` to drain the victim's entire token balance. Since this is the cross-chain fungible token implementation used for bridged/wrapped assets, this results in concrete, complete theft of funds for any holder of the token, with no privileged or trusted precondition required by the attacker.

### Likelihood Explanation
The function is `public`, requires no signature, permission, or state precondition beyond the token being deployed and the victim holding a balance. It is reachable from a single, ordinary transaction by any unprivileged EOA or contract, matching the "single submitted transaction" reachability bar. The function is present in the production `evm/src/utils/` directory (not a test-only file) and the contract is referenced from deployment scripts and utility contracts, indicating it is part of the shipped/deployable codebase rather than purely test scaffolding.

### Recommendation
Remove `superApprove` from the production contract entirely, or if a similar helper is genuinely needed for testing, gate it behind `msg.sender == owner` (mirroring standard `approve` semantics) or move it into a test-only mock contract that is never part of a deployed bytecode path. Approvals should only ever be settable by the token owner themselves, and only for the exact amount intended to be spent, consistent with the referenced report's recommendation.

### Proof of Concept
1. Deploy or use an existing `HyperFungibleTokenImpl` instance where `victim` holds a nonzero balance (e.g., minted via cross-chain bridge mint).
2. Attacker (any unprivileged address) calls `superApprove(victim, attacker)`.
3. `_approve(victim, attacker, type(uint256).max)` executes unconditionally, setting `allowance[victim][attacker] = type(uint256).max`.
4. Attacker calls `transferFrom(victim, attacker, victim.balanceOf())`, draining `victim`'s full token balance with no consent from `victim`. [1](#0-0)
