### Title
Bandwidth gate's per-message FIFO sweep imposes unbounded, uncompensated relayer processing cost that an attacker can inflate via unvalidated cross-chain sponsorship — ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth`'s `BandwidthGate::try_consume` is invoked on *every* inbound POST request routed through `ProxyModule::on_accept` before the message is delivered to its destination module. Each call performs an O(n) sweep (`retain`), sum, and FIFO drain over the entire `Allowance` subscription list for the `(source, app)` pair, where `n` can be up to `MAX_SUBSCRIPTIONS` (1024). This is structurally the same "lost positions inflate the shared batch-processing cost" pattern as the Y2K Carousel report: entries that provide no economic benefit to future callers remain in a list that every subsequent, unrelated operation must pay to traverse. [1](#0-0) 

### Finding Description
The subscription-purchase flow lets a payer on any source chain credit *any* `(app_chain, app)` pair — the `chain` field inside the purchase message is explicitly **not validated against the source chain that sent it** (this is the documented "sponsorship" feature). Anyone can therefore call `BandwidthManager.purchase()` repeatedly, targeting a victim app on an arbitrary chain, to push new `Subscription` rows onto that app's FIFO `Allowance` list. [2](#0-1) 

`push_subscription` appends unconditionally and only evicts the oldest entry once the list hits the 1024 cap — it never merges, coalesces, or removes low-value/near-expired entries proactively: [3](#0-2) 

Every subsequent non-purchase message from that app — sent by the app's legitimate users/relayers, not the attacker — pays the full cost of iterating the (now maximally long) list inside `try_consume`: sweeping expired entries with `list.retain(...)`, summing `remaining_bytes` across all live entries, and draining from the head: [1](#0-0) 

This gate call happens unconditionally inside `ProxyModule::on_accept`, which is exercised by `handle_unsigned` — the permissionless, unsigned extrinsic anyone (a relayer) submits to deliver a proven cross-chain message: [4](#0-3) [5](#0-4) 

Crucially, `on_accept`'s bandwidth-purchase path returns `Weight::zero()`, meaning the pallet does not charge/account weight proportional to the size of the list it just grew, and there is no fee mechanism at all on the consume side — "There's no per-message fee path on dispatch" is explicit in the design docs. So the cost of iterating a bloated list is never priced into either the attacker's purchase transactions or the relayer's delivery transaction; it is a free-to-inflict, unbounded-relative-to-the-relayer's-compensation cost, exactly mirroring the Y2K report's core defect: a shared batch/queue structure whose "dead weight" entries are never charged to the party that created them, but are paid for by every future, unrelated caller that must traverse the structure. [6](#0-5) [7](#0-6) 

### Impact Explanation
Once an attacker fills a targeted app's `Allowance` list to the 1024 cap with subscriptions (any tier, since only the count matters for the gate's iteration cost, not their byte value), every legitimate relayer delivering that app's future messages incurs the maximum sweep/sum/drain cost on each and every request — a cost the relayer's `handle_unsigned` extrinsic is not compensated for and which pallet's stated weight for the message-handling call does not account for. Because relayers are profit-driven and self-select messages based on estimated gas/weight cost versus fee/incentive received, an attacker can use this to make delivering that app's messages consistently unprofitable or push per-call weight past the effective limit apportioned to message execution, degrading or denying the app's message route entirely — "a route unable to deliver messages," one of the explicitly accepted impact classes. Because sponsorship is cross-chain and unauthenticated against the actual source, the attack requires no privileged position and can be aimed at any app on any registered chain from a completely unrelated chain.

### Likelihood Explanation
The purchase path is fully permissionless (`purchase()` on `BandwidthManager.sol`, dispatched as a normal ISMP POST with `fee: 0`), requires no special role, and the sponsorship model is explicitly designed to let any payer target any `(app_chain, app)` pair. The only cost to the attacker is the tier price × 1024 purchases (bounded, one-time, and independent of the app's usage), a modest and repeatable cost to permanently degrade every future relayer's processing cost for the targeted app. Likelihood is Medium-High given the low barrier to entry and the explicit design choice not to validate the sponsorship chain against the request source.

### Recommendation
- Charge (and account) `Allowance` list length in the weight returned from `try_consume`/`on_accept`, so the cost of a bloated FIFO list is priced into the extrinsic that must traverse it, rather than being an unaccounted, uncompensated cost absorbed silently by relayers.
- Consider bounding the *effective* number of entries a single low-value purchase can add relative to what it credits (e.g., reject or coalesce purchases that would push the list length disproportionately relative to the bytes actually purchased), or cap growth rate per source/payer.
- Re-evaluate the unauthenticated cross-chain sponsorship model: require some binding between the paying chain and either the app owner's consent or a minimum per-purchase byte/duration threshold so an attacker cannot cheaply create maximal list-length griefing with minimal bytes purchased.
- Alternatively, switch the subscription store to a structure where sweeping/expiry does not require linear traversal proportional to attacker-injected volume (e.g., an expiry-indexed structure) so the per-message gate cost is not attacker-controllable independent of legitimate usage.

### Proof of Concept
1. Attacker deploys/uses any `BandwidthManager` on a low-fee source chain (or any registered chain) and calls `purchase({ app: victimAppBytes, tier: TierOne, months: 1, chain: victimAppChainBytes })` 1024 times, targeting the victim app's `(app_chain, app)` bucket. Each purchase dispatches an ISMP POST to `pallet-bandwidth`'s `on_accept`, which calls `push_subscription`, appending a new `Subscription` and eventually evicting only the oldest entry once at cap — never proactively cleaning attacker-added entries. [7](#0-6) 
2. The victim app's `Allowance::<T>` list for `(victimAppChain, victimApp)` is now at `MAX_SUBSCRIPTIONS` (1024), fully attacker-controlled.
3. Any legitimate user of the victim app dispatches a normal message from `victimAppChain`. A relayer submits `handle_unsigned` to deliver it. `ProxyModule::on_accept` calls `try_consume`, which must `retain`-sweep, sum, and potentially drain across up to 1024 entries — for every single future message from this app, indefinitely, until enough of the attacker's junk entries expire/are consumed (which the attacker can perpetually refresh at will since purchases are always accepted). [1](#0-0) 
4. Because the pallet's weight accounting for `on_accept`/`try_consume` does not scale with list length, and there is no relayer fee tied to gate-processing cost, relayers absorb this inflated, uncompensated cost on every delivery attempt for the targeted app — degrading or effectively denying its message route.

		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

		fn on_accept(&self, request: PostRequest) -> Result<Weight, anyhow::Error> {
			let manager = BandwidthManager::<T>::get(&request.source).ok_or_else(|| {
				anyhow::anyhow!(format!("no bandwidth manager registered for {:?}", request.source))
			})?;

			if request.from != manager.0.to_vec() {
				return Err(anyhow::anyhow!(format!(
					"purchase from unauthorised sender on {:?}: expected {:x?}, got {:x?}",
					request.source, manager.0, request.from
				)));
			}

			let msg = PurchaseMessage::try_from(request.body.as_slice())?;
			let tier = TierIndex::try_from(msg.tier)
				.map_err(|_| anyhow::anyhow!(format!("unknown tier discriminant {}", msg.tier)))?;
			let cfg = Tiers::<T>::get(tier)
				.ok_or_else(|| anyhow::anyhow!(format!("tier {:?} is not configured", tier)))?;

			let bytes = cfg.bytes.saturating_mul(msg.months as u128);
			let duration = cfg.duration_secs.saturating_mul(msg.months as u64);

			let key = AppKey::truncate_from(msg.app);
			let expires_at = Self::push_subscription(&msg.chain, &key, tier, bytes, duration);

			Self::deposit_event(Event::BandwidthCredited {
				app_chain: msg.chain,
				app: key,
				paid_from: request.source,
				tier,
				bytes,
				expires_at,
			});

			Ok(Weight::zero())
		}

impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

## Sponsoring Another Chain

The `chain` argument is **not validated against the source chain** — see [Overview → Sponsorship](/developers/evm/bandwidth/overview#sponsorship) for the model. A buyer on Ethereum credits an app on Base by passing the credit chain id in `chain`:

```solidity
manager.purchase({
    app:    abi.encodePacked(appAddressOnBase),
    tier:   2,
    months: 6,
    chain:  bytes("EVM-8453")
});
```

The pallet keys allowance storage on `(msg.chain, msg.app)`, so the credit lands on Base regardless of which chain sent the payment. The recommended pattern for teams running a central treasury is to deploy `BandwidthManager` on one low-fee chain and sponsor bandwidth for app instances elsewhere.

```text
Per-message protocol fees price each dispatch in isolation. That works for occasional cross-chain traffic but is awkward for apps that send a steady stream of small messages — every dispatch pays the same overhead and there's no way to commit upfront to a usage budget.

Bandwidth swaps that model for a subscription. An app buys a tier once, the pallet tracks the remaining byte balance, and the gate silently passes messages until the balance is exhausted. There's no per-message fee path on dispatch — the cost was paid at purchase time.
