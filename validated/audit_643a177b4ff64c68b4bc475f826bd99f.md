### Title
Webhook `shop` (and other Shopify headers) are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](file))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates the *body bytes* but never authenticates the `shop`, `topic`, `webhook-id`, or `api-version` values that are pulled from HTTP headers. `Webhooks::Registry.process` nonetheless treats `request.shop` as trusted tenant identity when dispatching to the handler. This breaks the equality: *shop bytes verified by HMAC* ≠ *shop bytes acted on by the handler*.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns `@raw_body` only — none of the `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, or `shopify-api-version` headers are folded into the signed string. `HmacValidator.validate` computes the HMAC solely over that signable string: [3](#0-2) 

`Registry.process` then uses the unauthenticated `request.shop` header value directly as the tenant identity handed to the app's handler: [4](#0-3) 

Because the signature only binds the JSON body, any request whose body+HMAC pair was legitimately produced by Shopify for shop A (e.g. because the attacker owns shop A and registered the same webhook topic) can be replayed verbatim to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to victim shop B. `HmacValidator.validate` still returns `true` because the body/HMAC pair is unchanged, and `Registry.process` forwards `shop: "shop-b.myshopify.com"` (attacker-controlled) to the handler as if it were authenticated. This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the equality *authenticated body* == *authenticated shop* does not hold, only *authenticated body* == *authenticated body* holds, while `shop` is taken from a completely unauthenticated header.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to key per-tenant state (token lookups, order/customer writes, cache invalidation, GDPR redaction, etc. — which is the documented purpose of this field) can be made to apply attacker-supplied webhook payloads to an arbitrary victim shop's tenant context, because the shop attribution is not cryptographically bound to the signed payload. This is a cross-tenant identity confusion vulnerability reachable by any unprivileged internet user who can obtain one legitimately-signed webhook body (e.g., by registering a webhook on their own store) and replay it against the app's public endpoint with a forged `shop-domain` header.

### Likelihood Explanation
Medium-High: the attacker only needs to run their own Shopify store (trivial, free), subscribe to any webhook topic the target app registers, capture one genuine `body + x-shopify-hmac-sha256` pair, and POST it to the app's public webhook URL with a modified `x-shopify-shop-domain` header. No secrets or privileged access are required.

### Recommendation
Bind the tenant-identifying headers into the HMAC-signed material (or otherwise independently verify `shop` against a Shopify-issued, cryptographically-verifiable source, such as looking up an existing session/access token for that shop before trusting the payload), rather than deriving `shop`, `topic`, `webhook_id`, and `api_version` purely from unauthenticated headers in `ShopifyAPI::Webhooks::Request`.

### Proof of Concept
1. Attacker registers `orders/create` (or any topic the target app supports) on their own shop `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook POST to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `(B, H)` and replays a POST to the same endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `H`, so validation passes.
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data under the victim's tenant identity. [5](#0-4) [4](#0-3)

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
