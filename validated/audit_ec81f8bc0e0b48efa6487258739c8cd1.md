### Title
Webhook `shop`, `topic`, and `webhook_id` identity fields are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` straight from HTTP headers, but `to_signable_string` (the value fed into HMAC verification) is only the raw request body. `Registry.process` validates the HMAC and then dispatches the handler using the unauthenticated header values, so the cryptographic proof of authenticity never binds the tenant (`shop`) or event type (`topic`) to the verified bytes.

`lib/shopify_api/webhooks/registry.rb` then validates only that body-based HMAC before trusting the header-derived identity fields to route and label the event: [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string`: [4](#0-3) 

This reproduces the report's core defect class ("a field acted on but not covered by the HMAC"): the equality the code implicitly assumes is
`HMAC-verified(raw_body) == HMAC-verified(shop, topic, webhook_id, raw_body)`,
but only the left side is actually true. The `shop-domain`, `topic`, and `webhook-id` headers are never included in the signed content, so anyone who can present a `(raw_body, valid-hmac)` pair - which is trivially obtained by any unprivileged account that legitimately installs the app on their own store and receives one real, validly-signed webhook delivery - can replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting arbitrary `shop-domain` and `topic` headers. `Registry.process` will accept the HMAC (it only checks the body) and hand the forged `shop`/`topic` straight to the app's handler via `WebhookMetadata`: [5](#0-4) 

Because the shop identity is the tenant key most host applications use to route webhook side effects (e.g. deleting sessions on `app/uninstalled`, updating billing state, invalidating tokens), an attacker who owns a legitimate low-privilege store can generate real webhook bodies at will (by taking normal actions on their own store) and then relabel them as originating from a victim's shop or a different (higher-impact) topic, since neither value is bound by the signature.

### Impact Explanation
This breaks the tenant/topic identity binding that the HMAC is meant to establish, enabling cross-tenant confusion: an attacker-controlled webhook body can be attributed to any `shop` and any `topic` of the attacker's choosing, without needing the app's `client_secret`, `api_secret_key`, or any elevated privilege - only network access to the app's public webhook endpoint and one legitimate delivery from their own store. Depending on how the host application's webhook handlers key their logic off `WebhookMetadata#shop`/`#topic` (a documented, expected usage pattern of this gem), this can lead to cross-tenant state corruption (e.g., spoofing an `app/uninstalled` or `shop/redact` event for a victim shop, or replaying a benign topic's body as a sensitive topic). This matches the Critical "cross-tenant access" bar since the tenant boundary (`shop`) is not authenticated at all by the verification primitive the library provides.

### Likelihood Explanation
High. No secret material is required. Any actor who can install the app on even a free/trial store - i.e., any unprivileged internet user - automatically receives real, correctly signed webhook deliveries for their own body content, and can then re-send that exact `(raw_body, hmac)` to the app's public webhook callback URL with forged `x-shopify-shop-domain`/`x-shopify-topic`/`x-shopify-webhook-id` headers. `Registry.process` performs no additional check that ties the verified body to those headers.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify against Shopify's per-shop webhook secret if available, or require the caller to additionally confirm `shop`/`topic` against an out-of-band record such as an active session or the app's own webhook registration for that topic/shop pair) before dispatching to `WebhookHandler#handle`. At minimum, document prominently that `shop` and `topic` returned by `ShopifyAPI::Webhooks::Request` are not authenticated by `Utils::HmacValidator.validate` and must not be trusted as tenant identifiers without independent verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and performs an action that triggers a real webhook (e.g. `products/create`), receiving a legitimately signed delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(app_secret, B)`, independent of headers).
2. Attacker replays the exact same `B`/`H` to the app's public webhook endpoint, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: app/uninstalled` (or any registered topic)
   - `x-shopify-webhook-id: <arbitrary>`
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only (`to_signable_string`) - it matches `H`, so validation passes. [3](#0-2) 
4. The registered handler for `app/uninstalled` (or whichever topic was set) is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`, `topic: "app/uninstalled"`, and the attacker's own body content - despite the request never having been produced or signed by Shopify for the victim's shop or that topic.
