### Title
Unbounded length-prefixed allocation in livestream `Upstream` before deserialization causes memory exhaustion - ([File: src/agents/livestream/upstream.rs])

### Finding Description
`Agent`'s upstream network reader in `EventReader::poll_stream` reads a 4-byte big-endian length prefix directly from an unauthenticated TCP connection accepted on port 9201, then immediately allocates a buffer of that size with no upper bound check: `self.buf = vec![0; u32::from_be_bytes(self.len) as usize];` [1](#0-0) . The listener binds to `0.0.0.0:{PORT}` (port 9201) and accepts any connecting client without authentication [2](#0-1) [3](#0-2) . Since the length field is a `u32`, an attacker who can reach this TCP port can send a 4-byte header declaring up to ~4 GiB, forcing an immediate `Vec<u8>` allocation of that size before a single byte of the actual payload is read or validated, and before `rkyv::from_bytes` deserialization even begins [4](#0-3) . There is no cap comparing the declared length against a sane maximum message size anywhere in `Agent`, `Upstream`, or `EventReader`.

### Impact Explanation
Repeated connections each declaring a near-4 GiB length can exhaust orb-core process memory or trigger OOM, causing denial of service to the livestream agent and potentially the whole `orb-core` process (since allocation failure / OOM killer action affects the process as a whole). This matches an "Memory exhaustion from routine attacker-shaped input" DoS impact class.

### Likelihood Explanation
The only precondition is network reachability to TCP port 9201 on the orb, which the listener binds on all interfaces (`0.0.0.0`) with no authentication or handshake before the length-prefixed frame is read. Sending a single 4-byte header per connection is trivial and fully repeatable, requiring no privileged access, tokens, or social engineering.

### Recommendation
Enforce a maximum allowed message size constant before allocating the buffer in `EventReader::poll_stream`, e.g. reject/close the connection if `u32::from_be_bytes(self.len) as usize` exceeds a defined `MAX_LIVESTREAM_MESSAGE_SIZE`, rather than unconditionally calling `vec![0; len]`. Additionally consider binding the listener to a loopback/trusted interface only, or adding authentication, if the protocol is not intended to be reachable by arbitrary network peers.

### Proof of Concept
Integration/fuzz test plan for `EventReader::poll_stream` (or an end-to-end test against `Upstream`):
1. Start `Upstream::new()` and connect a `TcpStream` to port 9201.
2. Write a 4-byte big-endian length header equal to `u32::MAX` (or another very large value) and no further payload bytes.
3. Assert that the process does not attempt to allocate a buffer of that size — i.e., assert `poll_stream`/`Upstream::poll_next` returns an error (connection rejected) instead of blocking on `vec![0; len]`.
4. As a stronger fuzz invariant: for random `u32` length values above a defined cap (e.g., typical livestream event payload size), assert the reader errors out before allocation, and does not proceed to fill `self.buf`.
