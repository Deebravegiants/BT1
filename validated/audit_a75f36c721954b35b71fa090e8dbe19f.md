### Title
Unrefunded/sandwichable native-token swap in `EvmHost.dispatch()` and `fundRequest()` lets any user's leftover ETH be permanently trapped and value-extracted via Uniswap sandwich - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch()`, `dispatch(DispatchGet)`, and `fundRequest()` accept native token payment and swap it for `feeToken` via `swapETHForExactTokens` on a local Uniswap V2 pool at execution time, with no minimum-output/slippage guard and no refund of any leftover ETH back to the caller. This is directly analogous to the original report's root cause: an unprivileged actor can manipulate on-chain state (here, the Uniswap pool price) between the time a user forms their transaction and the time it executes, causing the user to consume more value than intended - and unlike the referenced Teller bug, here the "overpayment" is not even returned to the payer, it is silently retained by the host contract.

### Finding Description
In `evm/src/core/EvmHost.sol`, `dispatch(DispatchPost)` performs: [1](#0-0) 
When `msg.value > 0`, the host calls `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`. This swap only guarantees the *exact output* (`post.fee` feeToken) is produced; the *input* ETH consumed is whatever the current pool price dictates, capped only by `msg.value`. Uniswap's router refunds any unspent ETH to `msg.sender` of the swap call - which is `EvmHost` itself, not the original transaction sender. Reviewing the rest of `dispatch()` (lines 933-959) shows no logic that forwards this refunded ETH back to `_msgSender()`/`post.payer`. The identical pattern (swap with no refund) is repeated in `dispatch(DispatchGet)` at lines 974-985 and in `fundRequest()` at lines 1031-1042.

By contrast, `IntentGatewayV2.placeOrder` performs the same kind of native-to-feeToken swap but explicitly tracks and refunds unspent `msgValue` back to `msg.sender`: [2](#0-1) 

`EvmHost` has no equivalent accounting or refund step for its own `dispatch`/`fundRequest` swaps. Because the swap has no explicit `amountInMax` slippage bound beyond the caller's own `msg.value`, any user who (as the project's own documentation recommends) sends a buffered `msg.value` to cover fee-estimate imprecision or price movement will have the buffer permanently consumed/trapped rather than returned - and this exposure is worsened by an attacker who front-runs the pending `dispatch`/`fundRequest` transaction to move the pool price unfavorably (a classic sandwich), maximizing the ETH actually consumed by the exact-output swap up to the user's full `msg.value`, with the difference between what was truly needed and what was consumed never coming back to the user.

The project's own docs acknowledge the sandwich risk of this Uniswap-based fee quoting model but only warn against using `quote()` on-chain; they do not address that the actual `dispatch()`/`fundRequest()` swap path itself lacks slippage protection and a refund path: [3](#0-2) 

### Impact Explanation
This is reachable by any unprivileged user who dispatches a message or funds a pending request with native token - no admin/governance action is required, satisfying the "unprivileged message dispatcher" reachability requirement. The impact is a concrete, permanent loss of user funds: ETH sent as a reasonable buffer above the exact fee requirement is not returned to the sender and is not credited toward any protocol accounting the user can later reclaim (unlike the relayer-fee `feeToken` amount, which is tracked in `_requestCommitments` and refundable on timeout). Combined with attacker-controlled front-running of the AMM swap, the amount unrecoverably lost can be driven up to the full `msg.value` supplied, which for pool-based fee dispatch can be a meaningful, attacker-amplified loss across many dispatchers using the native-payment path.

### Likelihood Explanation
Likelihood is high for the loss-of-buffer issue, since it triggers on ordinary usage whenever a user supplies `msg.value` larger than the exact ETH-to-feeToken swap requirement (which is unavoidable without perfect price knowledge, and which the SDK/docs themselves recommend buffering for, e.g. the `HyperbridgeLzEndpoint`'s "generous 2x buffer" pattern). The sandwich-amplification component requires an attacker to front-run a specific pending `dispatch`/`fundRequest` transaction in the mempool, which is standard, low-cost MEV activity against any unprotected on-chain AMM swap and does not require any privileged role.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, track the ETH actually consumed by `swapETHForExactTokens` (its return value) and refund `msg.value - amountConsumed` to `_msgSender()` (or the designated `payer`), mirroring the pattern already used in `IntentGatewayV2.placeOrder`. Additionally, consider adding an explicit `amountInMax`/slippage parameter so callers can bound the ETH cost of the swap and revert rather than silently overpay when the pool price has moved.

### Proof of Concept
1. A user calls `IDispatcher(host).dispatch{value: X}(post)` where `X` is intentionally set above the current quoted cost of `post.fee` feeToken (a reasonable buffer, as recommended by Hyperbridge's own SDK docs for native-token fee payment).
2. `EvmHost.dispatch()` executes `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)`. Suppose the true cost is `Y < X`; the Uniswap V2 router refunds `X - Y` ETH to `address(this)` (the `EvmHost` contract), not to the user.
3. `dispatch()` returns without any code path that forwards `X - Y` back to the caller; the ETH remains stuck in the host's balance, inaccessible to the user who sent it.
4. An attacker can amplify the loss by front-running step 1 with a trade that moves the pool price against the user, increasing `Y` up to `X` (a standard AMM sandwich against an exact-output swap with no slippage bound), while the user's un-refunded ETH is fully consumed instead of contributing any dispatchable fee benefit back to them.
