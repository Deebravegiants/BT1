## Analog Found: Non-atomic check-then-record TOCTOU in JWT replay protection

The reported Sherlock issue is a **checks-effects-interactions violation**: the "check" (`collateral._amount == 0`) and the "effect" (writing new state) happen *after* an external interaction, leaving a window where the guard can be bypassed. The closest reachable analog in this codebase is the JWT replay-protection cache used by the internet-facing HTTP-trigger gateway path, where the replay "check" and the replay "record" are two separate, non-atomically-locked operations, leaving an exploitable TOCTOU window for an unprivileged caller.

### Title
Non-atomic JWT replay check-and-record in `WorkflowMetadataHandler.Authorize` allows duplicate workflow-trigger execution via concurrent replay - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

### Summary
`WorkflowMetadataHandler.Authorize` is the JWT-based authorization gate for the unprivileged, internet-facing HTTP trigger gateway handler. It checks `jwtCache.isReplay(claims.ID)` and, only after performing the signer/authorized-key lookup, calls `jwtCache.recordUsage(claims.ID)`. These two operations acquire the cache's `sync.RWMutex` independently rather than atomically, so the "check" and the "effect" of marking a JWT as used are separated by an unguarded window (analogous to the reported CEI violation where the check/effect for `collateral._amount` is separated from the state mutation by an external call).

### Finding Description
`jwtReplayCache` guards its map with a `sync.RWMutex`, but exposes `isReplay` and `recordUsage` as two independent, separately-locked methods rather than a single atomic check-and-set: [1](#0-0) 

`Authorize` calls these two methods in sequence, with unrelated authorization-lookup work (map lookups over `h.authorizedKeys`) executed in between the check and the record: [2](#0-1) 

This mirrors the reported bug class precisely: the "check" (`isReplay`) is not followed immediately by the "effect" (`recordUsage`) under the same lock/atomic operation — intervening logic runs in between, creating a window during which a second, concurrent call with the *same* JWT can also pass the `isReplay` check before the first call finishes and records usage. This is reachable from an unprivileged client: `Authorize` is invoked directly from the HTTP-trigger request path with attacker-controlled `req.Auth` (the JWT) on every incoming user trigger request: [3](#0-2) [4](#0-3) 

The existing test suite only validates the *sequential* replay case, never the concurrent race: [5](#0-4) 

By contrast, the sibling vault subsystem correctly implements this pattern as a single atomic operation (`CheckAndRecord`), demonstrating the intended, safe pattern that `jwtReplayCache` fails to follow: [6](#0-5) 

### Impact Explanation
An unprivileged caller holding one valid, signed JWT for a workflow's HTTP trigger can fire multiple concurrent trigger requests with the identical `jti`. Due to the non-atomic check/record, more than one of these concurrent requests can pass the replay check before any of them records the `jti`, letting the same JWT authorize more than one workflow execution. This defeats the single-use guarantee of the JWT replay protection and results in duplicate, unauthorized workflow-trigger executions (extra job runs) dispatched to the DON — a duplicated-fund/duplicated-action class impact similar in spirit to what checks-effects-interactions ordering is meant to prevent.

### Likelihood Explanation
The race window only requires two (or more) requests bearing the same JWT to arrive close together — trivially achievable by any external caller who can send a couple of HTTP requests in quick succession/parallel. No privileged access or malicious node/peer behavior is required; only unprivileged network client input via the public HTTP-trigger gateway endpoint is needed.

### Recommendation
Make the JWT replay check-and-record atomic: add a single method (e.g. `checkAndRecord(jti)`) on `jwtReplayCache` that takes the write lock once, checks for existence, and inserts the entry within the same critical section, returning whether the token was already used. Have `Authorize` call this single atomic method instead of the separate `isReplay`/`recordUsage` calls, mirroring the pattern already used correctly in `core/capabilities/vault/request_replay_guard.go`.

### Proof of Concept
1. Register a workflow and its authorized signer key as in `TestWorkflowMetadataHandler_Authorize`.
2. Create a single signed JWT for a given `jsonrpc.Request`.
3. Concurrently invoke `handler.Authorize(workflowID, tokenString, req)` from two goroutines instead of sequentially (as the existing "JWT replay protection" test does).
4. Observe that both goroutines can return successfully (no error), because both can pass `isReplay` before either calls `recordUsage`, resulting in the same JWT authorizing two separate workflow trigger executions instead of one. [5](#0-4)

```go
func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
```

```go
func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
```

```go
func (h *httpTriggerHandler) HandleUserTriggerRequest(ctx context.Context, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback, requestStartTime time.Time) error {
	triggerReq, err := h.validatedTriggerRequest(ctx, req, callback)
	if err != nil {
		return err
	}

	workflowID, err := h.resolveWorkflowID(ctx, triggerReq, req.ID, callback)
	if err != nil {
		return err
	}

	if err != nil {
		return err
	}

	if err = h.checkRateLimit(ctx, workflowID, req.ID, callback); err != nil {
		return err
	}

	strippedWorkflowID := strings.TrimPrefix(workflowID, "0x")
	legacyExecutionID, err := workflows.EncodeExecutionID(strippedWorkflowID, req.ID) //nolint:staticcheck // legacy ID kept for observability comparison
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID: " + err.Error())
	}
	// Workflows shouldn't use more than one HTTP trigger. If we ever need to support multiple triggers, we'd need to pass
	// trigger index to the Gateway handler and somehow allow senders to pick. For now, we use trigger index 0.
	// Execution IDs here are used only for logging.
	executionIDWithTriggerIndex, err := workflows.GenerateExecutionIDWithTriggerIndex(strippedWorkflowID, req.ID, 0)

		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error generating execution ID with trigger index: " + err.Error())
	}
	h.lggr.Debugw("processing request",
		"legacyExecutionID", legacyExecutionID,
		"executionIDWithTriggerIndex", executionIDWithTriggerIndex,
		"requestID", req.ID,
		"workflowID", workflowID)

	reqWithKey, err := reqWithAuthorizedKey(triggerReq, *key)
	if err != nil {
		h.handleUserError(ctx, req.ID, jsonrpc.ErrInternal, internalErrorMessage, callback)
		return errors.New("error marshaling trigger request: " + err.Error())
	}

	doneCh, err := h.setupCallback(ctx, req.ID, callback, requestStartTime, workflowID)
	if err != nil {
		return err
	}

	return h.sendWithRetries(ctx, legacyExecutionID, executionIDWithTriggerIndex, reqWithKey, workflowID, doneCh)
```

```go
func (h *httpTriggerHandler) authorizeRequest(ctx context.Context, workflowID string, req *jsonrpc.Request[json.RawMessage], callback handlers.Callback) (*gateway_common.AuthorizedKey, error) {
	h.lggr.Debugw("authorizing request", "workflowID", workflowID, "requestID", req.ID)

	return key, nil
```

```go
func (g *RequestReplayGuard) CheckAndRecord(digest string, expiresAtUnix int64) error {
	g.mu.Lock()
	defer g.mu.Unlock()

	g.clearExpiredLocked()

	if _, exists := g.seen[digest]; exists {
		return ErrRequestAlreadySeen
	}

	g.seen[digest] = expiresAtUnix
	return nil
}
```
