This is a valid analog. The core bug class — "funds always sent to `msg.sender` with no recipient override, so a blacklisted address can never retrieve them" — maps directly onto `FeeVault.claim()`.

`FeeVault.claim()` reads the caller's balance and pays it straight to `msg.sender` with no recipient parameter: [1](#0-0) 

The balance is keyed strictly on the creator address inside `accrue()`, and there is no mechanism to move an already-accrued balance to another address — only future fee attribution can be redirected: [2](#0-1) 

`Bonding.transferCreator` only reassigns `tokenInfo.creator` for future fee routing; it cannot rescue a balance already sitting in `FeeVault.creatorBalance[oldCreator]`, and the creator alone (not an operator) is authorized to call it: [3](#0-2) 

`Zap._accrueFee` credits the creator address on record at the time of each trade to `FeeVault.accrue`, which is the sole entry point writing `creatorBalance`: [4](#0-3)  `Zap.sell` and `Zap.buy` similarly hardcode `msg.sender` as the recipient for every USDC/token/LT payout leg, with no recipient override anywhere in the file: [5](#0-4) [6](#0-5) 

However, the `Zap` paths are not a true freeze: the launched `Token` (and LT) are ordinary transferable ERC20s with no blacklist logic of their own, so if `msg.sender` is later blacklisted by USDC, any pending `safeTransfer` to it simply reverts the whole transaction, leaving the trader's tokens untouched and freely movable to a clean wallet to retry the trade. `FeeVault.claim()` is different: the unclaimed balance is a *persistent on-chain liability* against one specific address (`creatorBalance[creator]`), it isn't restored or transferable if that address is later blacklisted by USDC, and `claim()` provides no way to redirect the payout — this is a genuine permanent freeze of creator funds, exactly matching the reported bug class.

### Title
Blacklisted creator can never claim already-accrued USDC fees from `FeeVault` — ([File: packages/contracts/src/FeeVault.sol])

### Summary
`FeeVault.claim()` pays a creator's entire accrued USDC balance to `msg.sender` with no recipient parameter. If a creator's address is later blacklisted by USDC (a real, centrally-controlled stablecoin with blacklist functionality), their `creatorBalance[creator]` entry becomes permanently unclaimable — `Bonding.transferCreator` only redirects future fee attribution, it does not move the already-accrued balance sitting in `FeeVault`.

### Finding Description
Every buy/sell in `Zap` forwards the creator's share of the fee into `FeeVault` and calls `accrue(token, creator, creatorShare, protocolShare, isBuy)`, crediting `creatorBalance[creator]` keyed on the creator address recorded in `Bonding.tokenInfo` at trade time (`packages/contracts/src/Zap.sol:476-487`). The only way to withdraw that balance is `FeeVault.claim()`, which reads `creatorBalance[msg.sender]` and unconditionally transfers to `msg.sender` (`packages/contracts/src/FeeVault.sol:127-135`) — there is no `claimTo(address recipient)` variant and no admin override.

`Bonding.transferCreator(tokenAddress, newCreator)` lets a creator redirect *future* fee attribution to a new address (`packages/contracts/src/Bonding.sol:738-748`), but it only mutates `TokenInfo.creator`; it never touches `FeeVault.creatorBalance[oldCreator]`. Any USDC already accrued to the old address before the transfer remains stuck under that address's key forever.

If USDC (the sole fee asset here) blacklists the creator's address, `claim()`'s `safeTransfer(msg.sender, amount)` will revert on every call, and since `msg.sender` is cryptographically the creator's own address (not adjustable), the accrued balance is permanently frozen — there is no path, even via `transferCreator`, to move that specific already-accrued balance to a clean address.

### Impact Explanation
Permanent freezing of creator funds held in `FeeVault`. Any creator whose wallet becomes blacklisted by USDC loses irrevocable access to all USDC fees accrued to that address prior to the blacklist event, with no recovery mechanism in the contract (`claim()` has no recipient override, and role transfer doesn't migrate historical balances).

### Likelihood Explanation
Requires only that USDC blacklist an address that happens to hold accrued creator fees — a realistic, externally-triggerable event (USDC's issuer can blacklist any address for compliance reasons) requiring no protocol-side privilege or bug beyond the missing recipient parameter.

### Recommendation
Add a recipient parameter to `FeeVault.claim()` (e.g., `claim(address to)` restricted to paying out `msg.sender`'s own balance but to an arbitrary `to`), or add an owner/creator-authorized `claimTo`/`migrateBalance(oldCreator, newCreator)` path so `transferCreator` can optionally sweep the outstanding `creatorBalance` to the new address atomically.

### Proof of Concept
1. Creator `A` launches a token via `Zap.createToken`; trades accrue creator fees to `FeeVault.creatorBalance[A]` via `Zap._accrueFee` → `FeeVault.accrue`.
2. USDC's issuer blacklists address `A` (external, out-of-protocol event).
3. `A` calls `Bonding.transferCreator(tokenAddress, B)` to redirect future fees to `B` — this succeeds and updates `TokenInfo.creator`, but `FeeVault.creatorBalance[A]` is untouched.
4. `A` calls `FeeVault.claim()`; `amount = creatorBalance[A]` is nonzero, but the internal `usdc.safeTransfer(A, amount)` reverts because USDC's `transfer` checks its blacklist for the recipient.
5. `A`'s accrued balance in `FeeVault` is now permanently unreachable — no function exists to redirect or reclaim it.
