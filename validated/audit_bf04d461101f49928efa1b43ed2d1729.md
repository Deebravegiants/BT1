### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` identifier that the gem hands to the app's webhook handler is read from an unauthenticated header and is never included in the signed material. An attacker who owns their own Shopify store (an unprivileged internet user from the host app's perspective) can capture a genuine webhook body+HMAC pair for their own shop and replay it with a forged `shop-domain` header claiming to be a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an HTTP header with no cryptographic binding: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` verifies `verifiable_query.to_signable_string` (the raw body) against the HMAC secret — it never touches `shop`, `topic`, `webhook_id`, or `api_version`: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` using `request.shop` — the unauthenticated header value — and passes it to the host application's handler: [5](#0-4) 

The documented contract instructs app authors to trust `data.shop` as the tenant identifier for the webhook (e.g. to select which shop's data to enqueue/update): [6](#0-5) 

The identity binding that should hold is:
`shop authenticated by Shopify's HMAC == shop the gem reports to the handler as the webhook's tenant`

Because the `shop-domain` header sits outside the signed payload, this equality does not hold. An attacker who legitimately owns a store (or subscribes any store to a webhook topic with a body they can predict, e.g. a topic whose body content they control or is otherwise reproducible) can:
1. Receive (or replay) a genuine `orders/create` (or any registered topic) webhook for their own shop, capturing `raw_body` and the corresponding valid `hmac-sha256` header.
2. Re-POST that exact `raw_body` + `hmac-sha256` pair to the app's webhook endpoint, but substitute the `shop-domain` (or `x-shopify-shop-domain`) header with the victim shop's domain.
3. `HmacValidator.validate` passes because the body and HMAC are still a valid pair for the shared `api_secret_key`. `Registry.process` then invokes the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`.

This is exactly the bug class in the report: a field that is *acted on* by downstream logic (`shop`, used as the tenant/session key by the host app) is not covered by the integrity check (`HMAC` over `raw_body` only), just as the NEAR fix addressed a shard identity that was checked one way but acted on another way, breaking the equality between "what was verified" and "what was used."

### Impact Explanation
This breaks tenant isolation (cross-tenant access) for any app relying on this gem's documented `WebhookMetadata#shop` contract: an attacker's webhook payload can be attributed to another merchant's shop, causing the host application to process/store/act on attacker-controlled data under a different tenant's identity. This satisfies the "Critical — cross-tenant access" impact bucket, since the merchant-identity boundary that the gem is responsible for enforcing (HMAC-authenticated shop attribution) is crossed using only a legitimately-obtained webhook from the attacker's own store — no access token, `client_secret`, or privileged credential is required.

### Likelihood Explanation
Medium-High. The attacker needs a real Shopify store (trivial to obtain, e.g. a free development store) subscribed to a webhook topic whose body is either attacker-controlled (custom app installed on their own dev store triggering `orders/create`, `products/update`, etc. with content they choose) or otherwise reusable, and network reachability to the target app's public webhook endpoint (which is, by design, a public unauthenticated HTTP endpoint). No secrets belonging to the victim or the target app are required.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook-id`, `api-version`) headers into the HMAC-verified signable string, or otherwise authenticate the shop domain against a separately-established relationship (e.g. verify the shop is one this app is genuinely installed on with a stored session) before dispatching `WebhookMetadata` to handlers. At minimum, document prominently that `data.shop` is not covered by Shopify's HMAC and must not be trusted as an authentication signal by itself.

### Proof of Concept
```ruby
# Attacker has a legitimate dev store "attacker-shop.myshopify.com" and captures
# a real webhook delivery for it:
raw_body = '{"id":1,"note":"hi"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# Attacker replays the same body+hmac to the target app's public webhook
# endpoint, substituting the shop header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) succeeds (only raw_body is checked),
# and the handler receives data.shop == "victim-shop.myshopify.com".
```

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
