### Title
Webhook `shop`, `topic`, and `webhook_id` are read from unauthenticated headers not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` values from raw HTTP headers, but `Utils::HmacValidator.validate` (invoked by `Registry.process`) only verifies the HMAC over `to_signable_string`, which is the raw request body — never the headers. This breaks the identity binding: `HMAC(raw_body, client_secret) == hmac_header` is verified, but `header.shop == actual_source_shop` is never checked. Anyone who can obtain one genuinely Shopify-signed webhook payload (e.g., by installing the target app on their own store) can replay that exact body+HMAC pair to the app's webhook endpoint while freely rewriting the `shop-domain`, `topic`, and `webhook-id` headers, since none of those fields are part of the signed content.

### Finding Description
`Registry.process` treats a request as authentic solely based on HMAC validity: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [2](#0-1) 

For a webhook `Request`, `to_signable_string` is defined as only the raw body — the `shop`, `topic`, and `webhook_id` accessors read separate, unsigned HTTP headers: [3](#0-2) 

Because the app's `Context.api_secret_key` (the app's single `client_secret`) is shared across every shop that installs the app, a genuinely Shopify-signed body+HMAC pair obtained from one shop (the attacker's own store) remains valid when replayed against the same endpoint with `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) headers rewritten to any value. `HmacValidator.validate` will still pass because only the byte-identical raw body is checked. The handler then receives `WebhookMetadata` built directly from these unauthenticated headers: [4](#0-3) 

The gem's own documentation confirms host apps are expected to trust this validation step as proof the request "did indeed come from Shopify" for that shop/topic, i.e., the `shop` field is treated as authenticated: [5](#0-4) 

### Impact Explanation
This crosses a tenant boundary: an unprivileged internet user who has installed the target app on their own (attacker-controlled) shop can forge webhook deliveries that the host application will attribute to an arbitrary other shop domain (and/or an arbitrary topic) while still passing this gem's HMAC verification. Depending on how the host app consumes `WebhookMetadata#shop`/`#topic` (e.g., to key data updates, trigger uninstall cleanup, or process GDPR/orders events), this enables cross-tenant data injection or corruption purely through this gem's documented "verified" webhook processing path.

### Likelihood Explanation
Any developer/attacker can sign up for a Shopify app that uses this gem, install it on a store they control, capture one legitimately Shopify-signed webhook body+HMAC, and freely replay it to the app's public webhook endpoint with modified `shop-domain`/`topic`/`webhook-id` headers — no secrets, tokens, or privileged access are required beyond normal app installation.

### Recommendation
Bind the identifying fields into the verified signature space, or otherwise re-derive/verify `shop` independently of the header (e.g., cross-check against the shop that is authorized to receive that specific `webhook_id`/topic, or require the host app to look up an active, previously-registered subscription matching topic+shop before trusting `WebhookMetadata`). At minimum, document prominently that `shop`, `topic`, and `webhook_id` are NOT covered by the HMAC and must not be treated as authenticated without additional server-side verification.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and registers for topic `orders/create`.
2. Shopify sends a legitimately HMAC-signed webhook: raw body `B`, header `shopify-hmac-sha256: H` (valid for `B` under the app's shared `client_secret`), `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-topic: orders/create`.
3. Attacker replays the exact same `B`/`H` to the same webhook endpoint but changes headers to `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different registered `shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate`, which recomputes HMAC over `B` only and matches `H` — validation succeeds.
5. `WebhookMetadata` is built with `shop: "victim-shop.myshopify.com"`, and the host app's handler processes it as an authentic event from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          received_signature = verifiable_query.hmac
