## #Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field straight from an unauthenticated HTTP header, while the HMAC signature that `Webhooks::Registry.process` verifies only covers the raw request body. Because the app's webhook signing secret (`Context.api_secret_key`) is shared across *every* shop that installs the app rather than being shop-specific, any merchant who installs the app can capture a legitimately-signed `(body, hmac)` pair delivered to their own shop and replay it to the app's webhook endpoint with the `shop-domain` header changed to point at a victim shop. The signature still validates, and the handler executes business logic attributing the (attacker-controlled) event to a tenant the attacker never had access to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are read directly from headers with no cryptographic binding: [2](#0-1) 

`Webhooks::Registry.process` validates only that the body's HMAC matches, then trusts `request.shop`/`request.topic` to build the data passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` (used for both webhooks and OAuth) computes the HMAC only over `verifiable_query.to_signable_string`: [4](#0-3) 

The identity binding that should hold is:
`hmac_signed_bytes == bytes_that_determine_the_tenant`

but here `hmac_signed_bytes == raw_body` while `tenant == header["shop-domain"]`, i.e. the equality is broken: the signature never covers the value used to route the event to a specific merchant. Because `Context.api_secret_key` is the same secret for all shops that install a given app, a legitimate `(raw_body, hmac)` pair generated for shop A remains a valid signature for the identical body when replayed with shop B's domain in the header — the gem has no mechanism to reject this cross-tenant substitution.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged attacker who is simply a merchant that installed the app (no elevated privileges, no leaked credentials) can trigger events on their own store, capture the resulting signed webhook payload, and replay it against the same app's webhook endpoint while claiming to be a different, victim shop. Any host application relying on `WebhookMetadata#shop` (populated straight from `request.shop`, see `Registry.process`) to select which tenant's data/session to act on will process the forged data as if it originated from the victim shop, corrupting or leaking cross-tenant state. This matches "cross-tenant access" in the Critical impact bucket.

### Likelihood Explanation
Likelihood is meaningful but not trivial: it requires the attacker to install the target app themselves (a normal, unprivileged action any Shopify merchant can take), trigger a webhook-generating action on their own store, capture the raw POST (body + `x-shopify-hmac-sha256` header), and resend it to the app's public webhook endpoint with a modified `x-shopify-shop-domain` header. No secrets, tokens, or elevated access are required — only the ability to install the app and intercept traffic reaching one's own server (or the app's, if publicly logged/echoed).

### Recommendation
Bind the identifying headers into the signed payload verification, e.g. include `shop-domain`, `topic`, and `webhook-id` in the string that is HMAC-verified (or independently cross-check `request.shop` against the shop associated with the specific `webhook_id`/session before dispatching to a handler). At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant selection without an additional server-side check (e.g., verifying the shop already has an active, stored session before acting on webhook data).

### Proof of Concept
1. App is installed by attacker on `attacker.myshopify.com`.
2. Attacker performs an action on their store that fires a webhook (e.g. `app/uninstalled` with an empty `{}` body, or any webhook whose body does not itself contain the shop domain).
3. Shopify POSTs to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid signature of body>`.
4. Attacker replays the exact same body and `hmac` header to the same endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) verifies the HMAC successfully (it only checks the body) and calls the handler with `shop: "victim.myshopify.com"`, causing the host app to act as if the event came from the victim shop.
