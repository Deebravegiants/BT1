### Title
Consensus-proof front-running lets an unprivileged relayer steal another relayer's `RelayerRewarded` payout by re-signing a copied, publicly-visible `ConsensusMessage` - (File: modules/pallets/consensus-incentives/src/impls.rs)

### Summary
`pallet-consensus-incentives::on_executed` attributes the BEEFY/GRANDPA consensus-relay reward to whatever account's signature happens to be embedded in the `signer` field of the `ismp::messaging::ConsensusMessage`, not to the actual extrinsic submitter and not to whoever fetched/assembled the underlying consensus proof. Since `handle_unsigned` (`modules/pallets/ismp/src/lib.rs`) accepts these messages from `OriginFor::None`, and the consensus proof bytes themselves are public relay-chain/BEEFY data, any unprivileged party who observes a pending `handle_unsigned` transaction in the mempool can copy the `consensus_proof`, re-sign `keccak256(consensus_proof)` with their own key, and resubmit it as their own message before the original submitter's transaction lands — winning the entire `$BRIDGE` reward and reputation mint for consensus relaying that someone else sourced.

### Finding Description
The reward-attribution logic lives in `Pallet::on_executed`: [1](#0-0) 

It recovers `relayer_account` purely from data *inside* the message payload — a self-supplied `signer` bytes field that is verified only as "a valid signature over `keccak256(consensus_proof)`", with no binding to `msg.sender`/the extrinsic's actual submitter (there is none, since the call is unsigned) and no binding to who produced or first observed the proof: [2](#0-1) 

The dispatch path is `pallet_ismp::handle_unsigned`, gated only by `ensure_none(origin)`: [3](#0-2) 

Crucially, the txpool dedup/priority tag in `validate_unsigned` is derived from the `state_machine_id`, not from the full message contents or the embedded signer: [4](#0-3) 

Consensus proof bytes (BEEFY/GRANDPA/etc.) are inherently public — they are reconstructible from the source chain's own finality data, and once one relayer submits them as an unsigned extrinsic they are visible in Hyperbridge's mempool before inclusion. This is architecturally identical to the reported `ZkEvmV2.finalizeBlocks` bug: the "hard work" (fetching/assembling the consensus proof) is done by relayer A, but the credit-binding value (the `signer`/beneficiary) is a caller-controlled field that isn't cryptographically tied to who did that work. Relayer B can:

1. Watch the mempool (or an RPC broadcast) for relayer A's pending `Message::Consensus { consensus_proof, ... }`.
2. Re-sign `keccak256(consensus_proof)` with B's own key, producing B's own `signer` bytes.
3. Submit `handle_unsigned` with the same `consensus_proof` but B's `signer`, at higher gas priority (or just win the race), before A's transaction is included.

The docs explicitly acknowledge the general race ("only the first relayer to submit a proof ... is rewarded") as the *intended* competitive model for genuinely independent provers, but this specific reward pallet keys attribution to a self-declared, arbitrary key inside the *same reused proof bytes*, meaning it rewards whoever wins the race to sign someone else's already-produced artifact — not whoever produced it. Contrast this with `pallet-beefy-consensus-proofs`, which the codebase's own comments describe as explicitly hardened against exactly this attack by binding the SP1 proof's committed nonce to the extrinsic signer so a copied proof cannot be re-attributed: [5](#0-4) 

`pallet-consensus-incentives` (used for ECDSA/GRANDPA-style consensus messages processed via `pallet-ismp::handle_unsigned`) has no equivalent binding: the `signer` field inside the `ConsensusMessage` is fully attacker-controlled and independent of the extrinsic origin, so it is trivially forgeable by anyone who can see the proof bytes.

### Impact Explanation
This is a reward/fee-accounting theft: the honest relayer who fetched and first assembled the valid consensus proof performs the real work and network cost, but a front-runner who merely copies the public proof bytes and re-signs them can steal the `$BRIDGE` treasury payout and the 1:1 reputation-asset mint (which additionally feeds collator selection, per `docs/content/developers/explore/provers.mdx`). Because the honest relayer's later transaction becomes a no-op (state already advanced, `calculate_reward` computes zero new blocks), the honest relayer is not just under-compensated but receives nothing while paying gas, discouraging honest participation and centralizing consensus relaying around whoever monitors the mempool most aggressively. This qualifies as unauthorized theft of relayer/reward-account funds under the "relayer fee and reward accounting" in-scope category.

### Likelihood Explanation
The attack requires no privilege beyond mempool visibility and the ability to sign an arbitrary message with a locally-controlled key — something every relayer already does. The consensus proof itself carries no secrecy (it is derived from public relay-chain finality artifacts), so any observer can extract it from a pending `handle_unsigned` extrinsic before it's finalized. This is realistically exploitable today by any of the "decentralized"/permissionless consensus relayers this pallet is designed to incentivize, exactly the scenario flagged in the original report ("when sequencer is decentralized").

### Recommendation
Bind the reward-eligible `signer` to something the front-runner cannot forge without doing the underlying work, mirroring the fix already applied in `pallet-beefy-consensus-proofs`:
- Require the `signer`'s signature to cover data that is unique to the *submission* (e.g., a nonce/account binding, or require it to equal the actual extrinsic's dispatch origin once signed extrinsics are supported for this path), so copying `consensus_proof` bytes alone is insufficient to claim credit.
- Alternatively, change `validate_unsigned`'s `provides` tag to include a hash of the full message (including `signer`), and additionally require the reward-processing logic to reject/ignore any `ConsensusMessage` whose `signer` does not match a previously-registered submission tied cryptographically to the proof's provenance — analogous to committing a `nonce == signer` bound value into the proof as done for SP1 BEEFY proofs.

### Proof of Concept
1. Relayer A constructs a valid `Message::Consensus(ConsensusMessage { consensus_proof, signer: sig_A })` and broadcasts `pallet_ismp::handle_unsigned([msg])` as an unsigned extrinsic.
2. Relayer B observes this pending extrinsic in Hyperbridge's transaction pool (unsigned extrinsics are visible pre-inclusion) and extracts `consensus_proof`.
3. B signs `keccak256(consensus_proof)` with its own key to produce `sig_B`, builds `Message::Consensus(ConsensusMessage { consensus_proof, signer: sig_B })`, and submits its own `handle_unsigned([msg_B])`, with higher priority/at an earlier ready slot.
4. B's transaction lands first; `pallet_ismp::Pallet::execute` applies the (identical) state update; `on_executed` in `pallet-consensus-incentives` recovers `relayer_account = B` from `sig_B` and pays B the full `RelayerRewarded` amount plus reputation mint, per `modules/pallets/consensus-incentives/src/impls.rs:112-156`.
5. A's original transaction, once included, computes `blocks = latest_height.saturating_sub(baseline)` as zero (state already advanced by B), so A receives no reward for work it actually performed, per `modules/pallets/consensus-incentives/src/impls.rs:89-97`.
