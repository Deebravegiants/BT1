## Analysis

The reported bug class — a callback function gated only by a coarse "trusted caller" check (`onlyLendingPool`) with no verification of who actually *initiated* the privileged action (`_initiator`) — has a direct analog in Hyperbridge's `CallDispatcher`.

### Title
Unauthenticated `CallDispatcher.dispatch()` allows anyone to drain any token/ETH balance held by the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, shared, non-upgradeable contract reused by every Hyperbridge app that supports calldata execution — `IntentGatewayV2`/`IntentsBase` (predispatch/postdispatch calls), `HyperFungibleToken`/`WrappedHyperFungibleToken` (`onAccept` calldata execution), and any third-party integrator. Its `dispatch()` function executes attacker-suppliable `Call[]` arrays *in the dispatcher's own context* (not `delegatecall`), yet it has **no access control at all** — not `onlyHost`, not `onlyGateway`, not even a caller allowlist. [1](#0-0) 

### Finding Description
`dispatch()` decodes an arbitrary `Call[]` and low-level `call`s each target with the dispatcher itself as `msg.sender`, with zero restriction on who may invoke it: [2](#0-1) 

Every legitimate flow that uses this contract first moves value into it and only *afterwards* calls `dispatch()`, then sweeps back whatever remains for the *known* set of tokens declared in the order/message:

- `IntentsBase._execute` sends order output assets to the dispatcher, calls `dispatch(order.output.call)`, then sweeps only the tokens listed in `order.output.assets`: [3](#0-2) 
- `IntentGatewayV2`'s predispatch flow transfers assets to the dispatcher, calls `dispatch(order.predispatch.call)`, then sweeps only the tokens listed in `order.inputs`: [4](#0-3) 
- `WrappedHyperFungibleToken.onAccept` forwards bridged funds and then dispatches arbitrary `message.data` to it: [5](#0-4) 

Because the sweep step is scoped only to the order's *declared* output/input tokens, any token that ends up on the dispatcher outside that declared set (e.g. a swap that returns a different token than expected, ETH accepted via the dispatcher's payable `receive()`, or dust from a partially-successful multi-call) is never recovered by the protocol and simply sits on the dispatcher. The project's own documentation acknowledges the dispatcher "holds tokens temporarily during execution" and warns against unlimited approvals for exactly this reason — the test suite even shows a postdispatch call granting the dispatcher's Uniswap router an unlimited (`type(uint256).max`) approval that is never revoked: [6](#0-5) 

Since `dispatch()` has no caller restriction, *any* address — not the host, not the gateway, not the order's beneficiary — can call `CallDispatcher.dispatch()` directly at any time with a `Call{to: token, data: transfer(attacker, dispatcher.balanceOf(token))}` (or `to: address(this), value: dispatcher.balance` for ETH) and pull out whatever balance the dispatcher is currently holding, because the `to.call()` inside `dispatch()` executes with the dispatcher as `msg.sender`, giving the caller of `dispatch()` full command of the dispatcher's current asset balance without ever needing to be part of the flow that put those assets there. This mirrors the reported flaw precisely: a shared execution/callback surface (`executeOperation` / `dispatch`) that is reachable by an unprivileged caller because the contract checks *how* it was called (flashloan pool / any relayer) but never checks *who* is entitled to trigger the resulting privileged action.

### Impact Explanation
Any residual balance on the singleton `CallDispatcher` — dust from an incomplete sweep, ETH sent to its payable `receive()`, tokens returned by a DeFi call that fall outside the order's declared output-token list, or any mis-sent/donated tokens — is unconditionally stealable by any address that races to call `dispatch()` first. Because the same dispatcher instance is shared across `IntentGatewayV2`, `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `ExtrinsicIntents`, this is a protocol-wide, permanent theft primitive rather than an isolated app bug, and it directly benefits from MEV/front-running since the balance appears mid-block before the legitimate app can complete its own sweep.

### Likelihood Explanation
Exploitation requires no special privilege, no proof, and no relayer role — a plain EOA transaction calling `CallDispatcher.dispatch()` is sufficient whenever the dispatcher holds any non-zero balance. Given that multiple apps route user/solver-supplied calldata through this exact contract, and that at least one documented usage pattern (unlimited router approval) and the sweep's fixed-token-list design both create realistic conditions for stray balances, the likelihood of exploitable balances accumulating is non-trivial and grows with adoption of calldata-enabled cross-chain transfers/intents.

### Recommendation
Restrict `CallDispatcher.dispatch()` to a caller allowlist (e.g., only the registered `IntentGatewayV2`, `HyperFungibleToken`/`WrappedHyperFungibleToken`, and `ExtrinsicIntents` instances), or make the dispatcher single-use/ephemeral per call (e.g., deploy a minimal-proxy dispatcher per invocation via `CREATE2`/`CREATE` so no shared, persistent balance ever exists), and additionally sweep *all* token balances the dispatcher can plausibly acquire (not just the declared output/input set) back to the calling app before returning control.

### Proof of Concept
1. A solver fills a cross-chain order whose `output.call` swaps USDC for DAI via Uniswap and sends the DAI onward, similar to `testPostdispatchTokenSweep`, in the process granting the `CallDispatcher` an unlimited USDC approval to the router and leaving refunded USDC on the dispatcher pending sweep: [7](#0-6) 
2. Before `_execute`'s sweep step runs (or if any token outside `order.output.assets` is produced by the swap), an attacker submits `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, IERC20(token).balanceOf(dispatcher))})]))` directly.
3. Because `dispatch()` has no access control, the call succeeds and moves the dispatcher's current token balance to the attacker instead of it being swept back to the gateway/beneficiary, as would occur in the legitimate flow.

     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
