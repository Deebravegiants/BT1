## Title
Single-Step `transferCreator` Allows Irrecoverable Loss of Future Creator Fee Revenue - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.transferCreator` reassigns a launched token's fee-attribution role in a single transaction with no acceptance step from the incoming address. All four owner-controlled contracts in this protocol (`Bonding`, `Zap`, `LPLock`, `FeeVault`) intentionally use `Ownable2StepUpgradeable` specifically to prevent exactly this class of bug for the protocol-owner role, but the creator role — which also gates ongoing revenue via `FeeVault` — is transferred with a plain one-step write.

### Finding Description
`transferCreator` only checks that `newCreator` is non-zero and different from the current creator before overwriting `info.creator` in a single call: [1](#0-0) 

This is the same "no transfer of ownership pattern" flagged in the external report: a privileged role is moved to a nominated address without that address confirming it can control the destination, so a fat-fingered or otherwise uncontrolled `newCreator` permanently loses access to the role's associated rights.

The contract's own documentation and test suite show the developers are aware of this exact bug class and deliberately protect the *owner* role against it: [2](#0-1) 

`OwnershipTransfer.t.sol` exists purely to enforce the two-step pattern on `Bonding`, `Zap`, `LPLock`, and `FeeVault`: [3](#0-2) 

Yet `transferCreator` — which controls where all future creator-share fee income for a token is routed — was left as a single-step write with no equivalent safeguard.

The creator role isn't cosmetic: `Zap` reads `Bonding.tokenInfo(token).creator` at every trade and calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`, which credits `creatorAmount` into `FeeVault.creatorBalance[creator]`: [4](#0-3) 

Only the address that actually holds `creatorBalance[creator]` can retrieve it via `claim()`: [5](#0-4) 

If `newCreator` is fat-fingered or is a contract/address nobody controls, every subsequent trade on that token accrues its 0.25% creator-share fee into a `creatorBalance` slot that can never be claimed — the funds sit in `FeeVault` forever, backed by real USDC but permanently unreachable.

### Impact Explanation
This is a permanent freezing of creator funds: once `transferCreator` is called with a mistaken or uncontrolled `newCreator`, every future creator fee accrual for that token (0.25% of every buy/sell, indefinitely, for the life of the token) is locked in `FeeVault` with no recovery path — there is no admin override, no two-step acceptance, and no way to redirect `creatorBalance[newCreator]` back to a controllable address. Given the protocol already treats this exact bug class as severe enough to warrant `Ownable2StepUpgradeable` on all four owner-controlled proxies, the unprotected creator-role transfer is an inconsistency with real, ongoing financial impact for token creators. This meets Medium severity under the "permanent freezing of ... creator ... funds" acceptance criterion.

### Likelihood Explanation
Likelihood is driven purely by user error, which is common in practice: any creator calling `transferCreator(tokenAddress, newCreator)` — e.g., to hand a launched token to a team wallet or multisig — can mistype the address or target a not-yet-deployed/incompatible contract, with no confirmation step to catch it before the switch takes effect and future fee flow is silently misdirected.

### Recommendation
Add a two-step creator transfer, mirroring the `Ownable2StepUpgradeable` pattern already used elsewhere in the codebase: store a `pendingCreator[token]` on `transferCreator`, and only update `info.creator` once the nominated address calls a corresponding `acceptCreatorTransfer(token)` from `msg.sender == pendingCreator[token]`.

### Proof of Concept
1. A creator launches a token via `Zap.createToken`, becoming `Bonding.tokenInfo(token).creator`.
2. The creator calls `Bonding.transferCreator(token, newCreator)` intending to move the role to their multisig, but mistypes the address (or the multisig deployment reverts/changes address later), per [1](#0-0) .
3. `info.creator` is now permanently `newCreator`, an address nobody controls.
4. Every subsequent trade on the token via `Zap.buy`/`Zap.sell` accrues the creator-share fee into `FeeVault.creatorBalance[newCreator]` via `FeeVault.accrue`, per [4](#0-3) .
5. Since no one holds the key to `newCreator`, `FeeVault.claim()` can never be called for that balance — the accrued USDC is permanently stuck in the vault, unlike `transferOwnership` on `Bonding`/`Zap`/`LPLock`/`FeeVault`, which is protected against exactly this scenario by `Ownable2StepUpgradeable` and exercised in [6](#0-5) .

    function transferCreator(
        address tokenAddress,
        address newCreator
    ) external {
        if (newCreator == address(0)) revert ZeroAddress();
        TokenInfo storage info = _s().tokenInfo[tokenAddress];
        if (msg.sender != info.creator) revert NotCreator();
        if (newCreator == info.creator) revert InvalidInput();
        info.creator = newCreator;
        emit CreatorTransferred(tokenAddress, msg.sender, newCreator);
    }
```

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
```

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
