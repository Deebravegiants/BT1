### Title
Unrestricted `op.endpoint`/`op.callData` in CASE 2 lets any user hijack state left in external protocols under Emporium's shared identity - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` gates only the caller of `runAction` itself (`onlyAllowedRecipient`, which only allows Hinkal) but places no restriction on `op.endpoint` or `op.callData` for CASE 2 ("Stateless") operations. Because CASE 2 executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract, every user's CASE 2 interaction with a given `op.endpoint` shares the exact same on-chain identity (`msg.sender == Emporium`), so any state a protocol associates with "the depositor" is not isolated per user - it is a single shared slot that any subsequent caller can also address.

### Finding Description
The claimed equality is: `operator/owner-of(position recorded by ProtocolX under identity Emporium)` should remain `none`/unaffected by any address other than the original depositing user (the "victim"). Instead, because CASE 2 calls are always made as `msg.sender = address(this)` (the Emporium contract) regardless of which user's proof triggered `runAction`, that equality is broken by construction: any user who can produce a valid Hinkal proof for their own UTXOs can submit an `EmporiumStack.ops[0]` targeting the identical `op.endpoint` a victim previously used, and invoke an operator/ownership-style function on it.

Code path:
- `runAction` is only gated at the top by `onlyAllowedRecipient`, which checks `msg.sender` (i.e., Hinkal) against an allow-list - it says nothing about `op.endpoint`: [1](#0-0) 
- For CASE 2 (`stack.signerAddress == address(0)` or `!op.invokeWallet`), the call is made directly by the Emporium contract with only a selector check against `callHinkalWallet`/`doSendToRelay` - `op.endpoint` and the rest of `op.callData` are completely attacker-controlled: [2](#0-1) 
- The only post-condition check is that the Emporium contract's own ERC20/ETH balance did not decrease (`balanceChange < 0` revert): [3](#0-2) . A call such as `setOperator(attacker)` that mutates only the external protocol's internal state (no ERC20/ETH balance movement at all) trivially satisfies `balanceChange == 0` and passes.

Exploit flow:
1. Victim previously ran a CASE 2 op against `ProtocolX` at address `E`, which recorded some position/allowance keyed by `msg.sender` (i.e., keyed by the Emporium contract address, since that's who called `ProtocolX`).
2. Attacker builds their own valid Hinkal proof over their own UTXOs (fully within attacker's normal, unprivileged capability) and submits `EmporiumStack.ops[0] = {endpoint: E, invokeWallet: false, value: 0, callData: abi.encodeCall(ProtocolX.setOperator, (attacker))}`.
3. `runAction` executes this op as `E.call(...)` with `msg.sender == Emporium`, so from `ProtocolX`'s perspective this is the same depositor identity that made the victim's earlier deposit. `ProtocolX.setOperator(attacker)` succeeds, scoped to "the caller's own deposits" - which is the shared Emporium identity, now containing the victim's funds.
4. Balance checks pass (zero ERC20/ETH movement), `payRelayFees` and UTXO accounting complete normally, and the transaction succeeds with no error.
5. In any later transaction, the attacker (now a recognized operator of `ProtocolX`'s position under the Emporium identity) can withdraw/transfer the victim's funds out of `ProtocolX`, either through another crafted Emporium op or, if the protocol recognizes the operator address itself for calls, directly from their own EOA - fully bypassing Hinkal's proof/nullifier system for this withdrawal.

No existing guard in `runAction`, `verifyWallet`, `payRelayFees`, or the balance-diff check inspects or restricts `op.endpoint`/`op.callData` for CASE 2, and none of them are aware of state a third-party protocol keeps keyed by the shared Emporium address.

### Impact Explanation
This allows direct theft of victim funds that are resting in any external protocol integrated via CASE 2 "stateless" interactions, because Emporium provides no per-user isolation of the calling identity - all CASE 2 calls to a given protocol share one on-chain identity (Emporium itself). An attacker can seize operator/ownership control over that shared identity's position and drain it in a subsequent transaction. This is repeatable against any protocol that grants durable rights (operator, approval, ownership) to the depositing address and is reachable by any unprivileged Hinkal user submitting their own valid proof. Severity: Critical - direct theft of user funds routed through Hinkal/Emporium.

### Likelihood Explanation
Preconditions: a victim must have previously used a CASE 2 Emporium op against a protocol that (a) leaves a durable position/balance associated with the calling address and (b) exposes some operator/ownership-transfer style function scoped to "caller's own deposits." Given that, the attack requires only that the attacker generate a proof for their own UTXOs (their normal capability) and craft an `EmporiumOperation` with the victim's known `endpoint` address and the appropriate `callData` - both fully attacker-controlled fields, at negligible cost (one transaction with zero balance change). This makes the attack cheap, deterministic, and repeatable across any protocol integrated this way.

### Recommendation
Do not let CASE 2 ("stateless") interactions share a single on-chain identity across users. Either (a) route every CASE 2 external call through a per-user proxy/wallet identity (similar to `HinkalWallet` used for CASE 1) so state in third-party protocols is namespaced per depositor, or (b) restrict CASE 2 strictly to a per-endpoint allow-list of protocols that are verified to be stateless/atomic (no persistent position, ownership, or operator concept tied to the caller), rejecting any call whose target or function selector is not on that list.

### Proof of Concept
Foundry test plan:
1. Deploy a `MockStatefulProtocol` with `deposit()` (payable/ERC20, tracks `balances[msg.sender]`) and `setOperator(address op)` (sets `operators[msg.sender] = op`, scoped to caller) and `withdrawAsOperator(address depositor, uint256 amount)` (checks `operators[depositor] == msg.sender`, transfers `balances[depositor]` to caller).
2. Deploy `EmporiumUpgradeable`, allow-list Hinkal as the only `onlyAllowedRecipient` caller (per existing setup).
3. Victim: submit a valid Hinkal proof causing `runAction` to execute CASE 2 op `{endpoint: MockStatefulProtocol, invokeWallet:false, value: X, callData: deposit()}`. Assert `MockStatefulProtocol.balances[address(Emporium)] == X` and `operators[address(Emporium)] == address(0)`.
4. Attacker: submit their own valid Hinkal proof (their own UTXOs, zero value) causing `runAction` to execute CASE 2 op `{endpoint: MockStatefulProtocol, invokeWallet:false, value:0, callData: setOperator(attacker)}`. Assert the transaction succeeds (balanceChange == 0, no revert), and now `operators[address(Emporium)] == attacker`.
5. Attacker later calls `MockStatefulProtocol.withdrawAsOperator(address(Emporium), X)` directly from their EOA (or via another Emporium op). Assert attacker receives `X` and `MockStatefulProtocol.balances[address(Emporium)] == 0`, proving theft of the victim's deposited funds without ever holding the victim's keys or nullifiers.
6. Assert the broken equality explicitly: before step 4, `operators[address(Emporium)] == address(0)` (== victim/none); after step 4, `operators[address(Emporium)] == attacker`, violating the expected invariant.
