### Title
Getter-named `stateMachineCommitment` is unnecessarily `payable`, causing accidental native token lock - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.stateMachineCommitment(StateMachineHeight)` is a read-style function (its name and NatSpec `@return the state commitment at height` say it only returns data) but it is declared `external payable` even though it performs no transfer, refund, or accounting of `msg.value`. [1](#0-0) 

### Finding Description
Every other read-only accessor on `EvmHost` (`latestStateMachineHeight`, `requestReceipts`, `responseReceipts`, `requestCommitments`, `vetoes`, `stateMachineCommitmentUpdateTime`) is correctly `external view`. [2](#0-1) 

`stateMachineCommitment` breaks this pattern: it is `external payable` instead of `external view`, despite doing nothing with any ETH sent to it — it simply reads and returns `_stateCommitments[...]`. [3](#0-2) 

`HandlerV2` itself calls this getter internally (e.g. in `handleGetResponses` / `handlePostRequestTimeouts` / `handleGetRequestTimeouts`) without sending value, which is why the bug has gone unnoticed operationally — the misuse only surfaces when an external caller (a relayer, integrator, or a batched/multicall context) mistakenly attaches `msg.value` to this call, expecting a normal `view` semantics. [4](#0-3) 

This matches the report's bug class: a function named/expected to behave as a pure getter that actually diverges from getter semantics (here, by silently accepting and retaining ETH) — the misleading interface causes unintended, invisible state effects (native balance held by the contract) that integrators would not expect from a "get" call.

### Impact Explanation
Any native token sent along with a call to `stateMachineCommitment` is accepted into the `EvmHost` contract's balance with no bookkeeping, no event, and no path back to the sender. The only way to recover it is via `EvmHost.withdraw()`, which is `restrict(_hostParams.hostManager)` — callable only through governance/cross-chain HostManager, not by the original sender. [5](#0-4) 

Since `msg.value` on this call is fully unaccounted for and un-refundable by the user themselves, any accidental or tooling-driven `value` attached to this "getter" (e.g. wallets/relayers that pass a nonzero value by convention, or code paths built assuming standard `view` getter behavior) results in permanent loss of funds from the caller's perspective, recoverable only at governance's discretion and to an arbitrary beneficiary, not the original payer.

### Likelihood Explanation
Low-to-moderate likelihood of accidental triggering: most callers (SDKs, `HandlerV2`) call it as a `view`-style read with `value = 0`, so this requires either a misconfigured integration, a batching library that defaults to forwarding `msg.value`, or manual misuse. However, given the function is `external payable` and publicly documented as a getter in the API docs (`docs/content/developers/evm/api/ihost.mdx`), the naming clearly invites developers to treat it as a free, side-effect-free read, increasing the chance an integrator would not think twice about attaching value in a generic call-forwarding wrapper.

### Recommendation
Remove the `payable` modifier and mark `stateMachineCommitment` as `view`, consistent with every other read accessor on `EvmHost`:
```solidity
function stateMachineCommitment(StateMachineHeight memory height)
    external
    view
    returns (StateCommitment memory)
{
    return _stateCommitments[height.stateMachineId][height.height];
}
```
This eliminates the possibility of native token being sent to and stranded by a function whose name and documentation promise pure read behavior, matching the report's broader recommendation to make function signatures reflect their actual state-mutation semantics.

### Proof of Concept
1. Any external account calls `EvmHost.stateMachineCommitment{value: 1 ether}(height)` directly (bypassing `HandlerV2`, which never attaches value).
2. The call succeeds and returns the state commitment as normal — no revert, since the function is `payable` and never checks `msg.value == 0`. [3](#0-2) 
3. The 1 ETH is now part of the `EvmHost` contract's balance with no record of who sent it or why.
4. The sender has no function to reclaim it; only `withdraw()`, restricted to `_hostParams.hostManager` (cross-chain governance), can move the balance out, and it pays to whatever `beneficiary` governance specifies — not necessarily the original sender. [5](#0-4)

            // this is safe because re-entrancy is mitigated before dispatching requests
