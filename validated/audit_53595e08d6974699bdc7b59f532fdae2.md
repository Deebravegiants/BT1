### Title
Webhook shop-identity spoofing — the `X-Shopify-Shop-Domain` (and topic/webhook-id) header is trusted for tenant attribution but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to that body [2](#0-1) . `Registry.process` validates the HMAC and, if it passes, unconditionally trusts `request.shop` and `request.topic` to dispatch the payload to the app's handler as `WebhookMetadata` [3](#0-2) . This breaks the intended identity binding: `HMAC(body)` should equal `authenticate(shop, topic, body)`, but here `HMAC(body)` only equals `authenticate(body)` — the shop and topic are unauthenticated.

### Finding Description
The equality this mechanism is supposed to enforce is:

`valid_hmac(request) == (body came from Shopify) AND (shop, topic bound to that body)`

What is actually enforced is only:

`valid_hmac(request) == (body came from Shopify for *some* shop/topic combination)`

Because `HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, and for webhook requests that string is `@raw_body` alone [4](#0-3) [1](#0-0) , an attacker who is a legitimate merchant of a shop they control can:

1. Trigger a real webhook delivery to their own app instance (e.g., `orders/create`) and capture the raw body plus the genuine `X-Shopify-Hmac-Sha256` value that Shopify computed with the app's real `api_secret_key`.
2. Replay that exact raw body and HMAC value to the app's webhook endpoint, but with `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) rewritten to point at a victim shop that also uses the app.
3. `Utils::HmacValidator.validate(request)` recomputes the signature over `@raw_body` only, which still matches, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [3](#0-2)  — attributing attacker-controlled body content to the victim's shop.

Any host application that uses `data.shop` from `WebhookMetadata` to look up a per-tenant session, write to a tenant-scoped record, or otherwise act "as" that shop (which is exactly the documented purpose of this field, per `docs/usage/webhooks.md` usage patterns and the `WebhookMetadata` shape consumed by handlers) will process attacker-supplied data under an identity it did not choose and cannot distinguish from a genuine Shopify-signed event for that shop.

### Impact Explanation
This is a cross-tenant identity-binding break: a request cryptographically proven to originate from Shopify's servers for *some* shop is processed as if it originated from a *different, arbitrary* shop chosen by the attacker. Any app that keys webhook side effects (order sync, GDPR compliance actions, inventory updates, billing events, etc.) off `WebhookMetadata#shop` will attribute attacker-authored payloads to a victim tenant, which matches the "cross-tenant access" Critical impact category — the confidentiality/integrity boundary between tenants is enforced only by the header value, not by the signature.

### Likelihood Explanation
Exploitation requires only: (a) the attacker to be a legitimate, unprivileged installer of the same app on any shop (trivial for public apps, and even relevant for apps with only a handful of merchants), and (b) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers — both are unprivileged-internet-user capabilities requiring no access token, no `client_secret`, and no interception of Shopify's traffic. The only constraint is that the attacker needs the raw body + HMAC pair from a webhook fired against their own shop, which they fully control and can trigger on demand (e.g., create their own order/product/etc.).

### Recommendation
Bind the shop (and ideally topic) into the signed material, or otherwise cryptographically verify shop identity independent of headers:
- Compute/verify the HMAC over `shop-domain + topic + raw_body` (or equivalent canonicalized string) rather than `raw_body` alone, if the app controls both signing and verification sides is not possible here since Shopify signs only the body — in that case the gem should not expose `shop`/`topic` from unauthenticated headers as if they were vetted; document/require that consuming apps additionally cross-check `request.shop` against an existing installed-shop record before trusting it for tenant attribution, and consider exposing a helper that fails closed if the shop encoded in the headers doesn't match a shop the app has legitimately installed/has an offline session for.
- At minimum, add a prominent safety note/API (or a `Registry.process` option) requiring callers to verify `data.shop` against their own session/store table before acting on the payload, since the gem's own docs and `WebhookMetadata` currently present `shop` as if it were an already-authenticated field.

### Proof of Concept
```ruby
# Attacker owns shop-a.myshopify.com and has installed the target app there.
# Step 1: Attacker triggers a real webhook (e.g. by placing an order) and
# captures the raw POST body + genuine "X-Shopify-Hmac-Sha256" header that
# Shopify computed with the app's real api_secret_key.
captured_body = '{"id": 1, "note": "malicious payload"}'
captured_hmac = "X-Shopify-Hmac-Sha256 value from the genuine delivery"

# Step 2: Attacker replays the same body/hmac to the app's webhook endpoint,
# but swaps the shop-domain header to the victim's shop.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: headers)

# HmacValidator only checks the raw body, which is unchanged, so validation succeeds:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process therefore dispatches attacker-controlled body content
# to the handler as if it belongs to "victim-shop.myshopify.com".
ShopifyAPI::Webhooks::Registry.process(request)
```
Since `lib/shopify_api/webhooks/request.rb:35-38` signs only `@raw_body`, and `lib/shopify_api/webhooks/registry.rb:188-199` trusts `request.shop`/`request.topic` unconditionally once the HMAC passes, this PoC demonstrates the shop-domain header is fully attacker-controlled while still passing HMAC validation.
