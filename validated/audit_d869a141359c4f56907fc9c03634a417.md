### Title
Crafted strategy routes can attach arbitrary wallet-token transfers to a caller-signed swap - (File: contracts/controller/src/strategies/swap.rs)

### Summary

The controller accepts opaque, caller-supplied `swap` bytes and executes the configured router under the caller’s top-level authorization without constraining the contracts reached by that route. A malicious route can therefore make a route-selected contract request an unrelated `token.transfer(victim, attacker, amount)` and include it as a child of the caller’s signed authorization tree. [1](#0-0) [2](#0-1) 

### Finding Description

Entrypoints such as `swap_collateral(caller, account_id, current, amount, new, swap)`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` expose `swap: Bytes` to the account caller. [3](#0-2) 

`require_authorized_caller` performs a top-level `caller.require_auth()`, and `process_swap_collateral` then passes the caller-controlled route into `withdraw_and_swap_from_supply`. [4](#0-3) [5](#0-4) 

`swap_tokens` checks only that the route is non-empty, snapshots the controller’s selected input and output balances, grants the router one exact controller-token transfer, and calls `execute_strategy(controller, amount_in, swap)`. [1](#0-0) 

The controller’s authorization helper intentionally permits only the controller’s input transfer, but it does not inspect, decode, or restrict the downstream venues encoded in `swap`. [6](#0-5) 

Consequently, a route-selected contract can request an unrelated token transfer from the original caller; the host records that request beneath the caller’s authorization for the strategy call, and enforcing mode executes it when the caller signs the poisoned tree. [7](#0-6) [8](#0-7) 

### Impact Explanation

An attacker can steal wallet assets unrelated to the lending position while the requested strategy still returns a plausible output and passes the controller’s balance and solvency checks. [9](#0-8) [10](#0-9) 

The loss is not bounded by the strategy’s input amount, output minimum, or final account risk checks because those controls measure only the selected collateral/debt tokens. [9](#0-8) [11](#0-10) 

### Likelihood Explanation

The attacker must induce the victim to submit or sign a crafted route whose simulated authorization tree contains the extra transfer, so this is not an unauthenticated protocol drain. [12](#0-11) 

That precondition is nevertheless realistic for opaque router bytes consumed by wallets or integrations that sign the simulation result without independently decoding and rejecting unexpected child invocations. [8](#0-7) 

The same authorization shape applies to every strategy entrypoint that accepts `swap: Bytes`, giving the attacker several delivery paths. [3](#0-2) 

### Recommendation

Decode and validate the complete route before authorization, and reject any route that can invoke contracts outside a governance-approved venue allowlist. [1](#0-0) 

The router execution boundary should also cryptographically constrain its authorization footprint so route code cannot add a caller-funded token transfer beneath the strategy invocation. [6](#0-5) 

Until routes are constrained on-chain, clients should decode `swap`, compare every destination contract with an approved venue set, simulate the transaction, and reject any authorization tree containing children other than the expected strategy flow. [13](#0-12) 

### Proof of Concept

The harness deploys a router that accepts a caller-supplied hop-pool address and deploys a rogue hop contract whose `swap` function calls `token.transfer(victim, attacker, amount)`. [14](#0-13) 

The victim invokes `swap_collateral(alice, account_id, usdc_hub_asset, SWAP_IN_USDC, eth_hub_asset, crafted_route)`, where `crafted_route` names the rogue hop. [15](#0-14) 

Simulation records the rogue wallet-token transfer as a child invocation under Alice’s `swap_collateral` authorization, and the demonstration shows Alice’s unrelated wallet token balance dropping to zero while the attacker receives the full balance. [2](#0-1) 

In enforcing mode, signing the honest root-only tree rejects the extra transfer, while signing the poisoned tree returned by simulation executes both the strategy and the theft. [16](#0-15)

#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);

/// Authorizes, on behalf of the current contract, one `transfer(from, to, amount)`
/// call on `token_addr` made deeper in the next contract call (for example by
/// the pool). The entry allows no further sub-invocations.
pub fn authorize_transfer_as_current(
    env: &Env,
    token_addr: &Address,
    from: &Address,
    to: &Address,
    amount: i128,
) {
    let entry = InvokerContractAuthEntry::Contract(SubContractInvocation {
        context: ContractContext {
            contract: token_addr.clone(),
            fn_name: symbol_short!("transfer"),
            args: (from.clone(), to.clone(), amount).into_val(env),
        },
        sub_invocations: Vec::new(env),
    });
    env.authorize_as_current_contract(vec![env, entry]);
}
