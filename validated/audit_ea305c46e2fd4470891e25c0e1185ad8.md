Audit Report

## Title
Legacy Web API trigger handler lets any unauthenticated user hijack another user's pending callback via `MessageID` collision - (File: `core/services/gateway/handlers/capabilities/handler.go`)

## Summary
`HandleLegacyUserMessage` stores a pending callback in the shared `savedCallbacks` map keyed solely by the client-supplied `msg.Body.MessageID`, with no uniqueness or ownership check before insertion. On the response side, `handleWebAPITriggerMessage` looks up and deletes the callback purely by that same attacker-controlled ID and delivers the DON's response to whatever callback currently occupies the slot.

## Finding Description
The gateway's HTTP server accepts requests without mandatory authentication — the `Authorization` header is optional and merely forwarded as a raw JWT string to `ProcessRequest`, which is not required to be present. [3](#0-2)  For legacy DON-ID requests, `ProcessRequest` only performs `msg.Validate()` — a structural/signature check (signature length, ID length/charset, method/DonID validity) — with no per-caller identity binding, before calling `h.HandleLegacyUserMessage`. [1](#0-0) 

Inside `HandleLegacyUserMessage`, after payload/timestamp/method validation (none of which relate to `MessageID` collisions), the handler unconditionally overwrites the shared map entry:
```go
h.mu.Lock()
h.savedCallbacks[msg.Body.MessageID] = &savedCallback{id: msg.Body.MessageID, createdAt: time.Now(), Callback: callback}
``` [4](#0-3) 

There is an explicit code comment acknowledging the missing protections: `// TODO: apply allowlist and rate-limiting here`. [5](#0-4) 

On the response path, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `msg.Body.MessageID` and forwards the response to whichever `Callback` object currently occupies that map key: [6](#0-5) 

`msg.Validate()` does check `MessageID` for length bounds and a trailing-null-byte restriction, but performs no uniqueness or ownership check tied to session/connection identity. [7](#0-6) 

## Impact Explanation
If an attacker submits a `web_api_trigger` request with a `MessageID` equal to a victim's still-pending request, the victim's `savedCallback` entry in the shared map is silently replaced by the attacker's own callback. The victim's HTTP call to the gateway then blocks until `RequestTimeoutError` fires in `ProcessRequest`'s `callback.Wait(ctx)` path, while the attacker's callback receives whichever DON response arrives first for that `MessageID`. This is a legitimate cross-user response corruption / denial-of-correct-delivery bug in an unauthenticated code path, falling within the "cross-user response corruption" impact class.

## Likelihood Explanation
Exploitability is real but has a nontrivial precondition: the attacker must know or predict a victim's exact `MessageID` value while that victim's request is still in-flight (window bounded by `defaultCallbackMaxAgeSec` = 120s). `MessageID` is fully attacker/caller-supplied with no server-side entropy requirement, and there is no protection comparable to the vault handler's duplicate-request-ID rejection. Since `MessageID`s are typically chosen by well-behaved clients to be unique/random (e.g., UUIDs), practical exploitation requires either weak client-side ID generation, leakage of another party's chosen ID, or a race where the attacker can observe/guess the pattern — this is a real gap in defense-in-depth even though it is not trivially exploitable against a client using high-entropy IDs.

## Recommendation
- Reject registration if `msg.Body.MessageID` already exists in `savedCallbacks` rather than silently overwriting it, mirroring the vault handler's duplicate-ID rejection behavior.
- Alternatively, bind the map key to a value derived from the connection/session (not fully attacker-controlled) so cross-caller collisions are impossible by construction.
- Add the TODO'd allowlist/rate-limiting to reduce the pool of anonymous callers who could attempt collisions.

## Proof of Concept
1. Send `POST` to the gateway user endpoint with a signed legacy JSON-RPC message body containing `MessageID = "X"`, method `web_api_trigger`, and a valid DON ID/payload/timestamp — this is "victim" request A; the gateway registers `savedCallbacks["X"] = calbackA` and forwards to DON members via `HandleLegacyUserMessage`.
2. Before the DON responds, send a second signed legacy request (any valid signer/key, since the handler does not restrict senders) with the same `MessageID = "X"` — `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with `callbackB`.
3. When a DON node responds with `MessageID = "X"`, `handleWebAPITriggerMessage` looks up and deletes `savedCallbacks["X"]`, now finding `callbackB`, and delivers the result there instead of to the original request A, which times out with `api.RequestTimeoutError`.
4. This can be verified with a Go test extending `handler_test.go`'s `TestHandlerReceiveHTTPMessageFromClient`: call `HandleLegacyUserMessage` twice with two different callbacks but the same `msg.Body.MessageID`, then call `HandleNodeMessage`/`handleWebAPITriggerMessage` once, and assert that the second callback (not the first) receives the response while the first callback's `Wait` times out.
