### Title
Donation-inflated `tokenBalance()` panics `Router._computeBuy`'s overflow cap, permanently bricking flat/bear-market graduation and trapping curve-raised LT — (File: `packages/contracts/src/Router.sol`)

### Summary
`Router._computeBuy` caps `tokensOut` at the pair's live `tokenBalance()` and back-calculates `amountInUsed` via `cappedReserveToken = reserveToken - tokensOut`. This subtraction implicitly assumes the protocol invariant `tokenBalance() <= reserveToken` (the virtual-reserve design deliberately keeps `reserveToken` = `totalSupply` above the real, sellable `curveSupply`). That invariant is enforced only by the *expected* seeding pattern — it is never re-checked at the point of use. An unprivileged wallet can violate it for free by directly `transfer()`-ing a launched `Token` into its `Pair` (an explicitly in-scope action per this task's rules), inflating `tokenBalance()` above `reserveToken`. Once inflated, any buy whose uncapped output would exceed the (now-larger) `realBalance` drives the cap branch into `reserveToken - realBalance`, which underflows and reverts with a raw Solidity Panic instead of the intended `OverflowCapDegenerate` guard (which only checks `== 0`, not negativity). This mirrors the ksmbd bug class exactly: a boundary/invariant check that is *necessary but insufficient* for the access pattern that follows — here, an arithmetic "access" instead of a memory access.

### Finding Description
`Router._computeBuy` (called by `Router.buy`, `Router.previewBuy`, and `Router.getAmountOut`'s buy branch): [1](#0-0) 

```solidity
function _computeBuy(address pairAddr, uint256 amountIn) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
    ...
    uint256 realBalance = pair.tokenBalance();
    if (tokensOut > realBalance) {
        tokensOut = realBalance;
        uint256 cappedReserveToken = reserveToken - tokensOut;   // <-- assumes reserveToken >= realBalance
        if (cappedReserveToken == 0) revert OverflowCapDegenerate();
        uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
        amountInUsed = cappedReserveAsset - reserveAsset;
    }
}
```

The zero-gap graduation design relies on the hard invariant `pair.tokenBalance() < reserveToken`, which the test suite itself pins as `test_inv_virtualReserveAlwaysExceedsRealBalance` (only asserted "while the curve is still trading," i.e., not proven unconditionally): [2](#0-1) 

However, the codebase's own regression test proves this invariant is *not* unconditional — a caller can drain the curve for real tokens and then donate them directly back into the pair via a plain ERC20 `transfer`, driving `tokenBalance()` strictly above the stored `reserveToken`: [3](#0-2) 

That test only demonstrates the effect on `Bonding.previewLtUntilGraduation`'s supply leg (which the developers patched with a guard, per the surrounding comments about a "donation attack regression"). `Router._computeBuy`'s overflow-cap branch was not given the equivalent guard: once `pair.tokenBalance()` exceeds `reserveToken`, the very next buy that is large enough to trip the `tokensOut > realBalance` cap branch computes `reserveToken - realBalance` on two values where `realBalance > reserveToken`, causing an unconditional Solidity arithmetic Panic (0.8.24 checked math) rather than a clean revert or a correctly capped value.

### Impact Explanation
- This breaks the "supply trigger" that `Bonding`/docs describe as the mechanism to guarantee graduation in flat/bear markets where the USD trigger never fires: "Supply trigger: `IPair.tokenBalance() == 0`… handles flat/bear markets where $9K is never reached." [4](#0-3) 
- Once an attacker donates enough tokens to invert the invariant, any buy that should exhaust the remaining real balance and drive `tokenBalance()` to `0` instead panics inside `Router.buy` (and its `previewBuy`/`getAmountOut` siblings used for quoting), so the curve can never reach `tokenBalance() == 0` through the cap path again.
- In a market where LT's `exchangeRate()` never rises enough to trip the USD trigger, the token becomes **permanently stuck in `Lifecycle.Curve`**: `_enterGraduating` / `_prepareGraduationLiquidity` / `finalizeGraduation` are unreachable, so the curve-raised LT and the 250M `LP_RESERVE` tokens sitting in `Bonding`/`Pair` for the promised HyperSwap seeding can never be moved into an LP — a permanent freeze of protocol/LP-bound funds, which is one of the explicitly accepted impact categories for this analog.
- It is triggerable purely with unprivileged transactions: `Zap.buy`/`Bonding.buy` to acquire real tokens, a plain `Token.transfer(pair, amount)` donation, and one more oversized buy to hit the (now-broken) overflow-cap branch.

### Likelihood Explanation
High reachability, no special privileges, no timing dependency, and cheap to execute (the attacker only needs to acquire real curve tokens once and donate them back — the donation itself costs nothing beyond gas since the tokens are simply transferred, not burned). The only requirement is that the LT's `exchangeRate()` doesn't independently trip the USD trigger before the attack completes, which the docs themselves identify as a realistic ("flat/bear market") scenario the supply trigger exists specifically to cover.

### Recommendation
Guard `Router._computeBuy`'s cap branch the same way `Bonding.previewLtUntilGraduation`'s supply leg was patched: use a saturating subtraction (`realBalance > reserveToken ? 0 : reserveToken - realBalance`) or explicitly clamp/revert with a descriptive error before computing `cappedReserveAsset`, and add a regression test mirroring `test_donation_realBalanceExceedsReserveToken` that exercises `Router.buy`/`previewBuy` after a token-donation inflates `tokenBalance()` above `reserveToken`.

### Proof of Concept
1. Attacker (or anyone) buys real `Token` on the curve via `Zap.buy` until they hold a large amount, then `Token.transfer(pair, donatedAmount)` — pushing `pair.tokenBalance()` above `reserveToken`, exactly as done in `_stageDonationAttack`: [3](#0-2) 
2. Any subsequent buyer (or the attacker themselves) submits a `Zap.buy`/`Bonding.buy` large enough that `_computeBuy`'s uncapped `tokensOut` exceeds the now-inflated `realBalance`.
3. `_computeBuy` enters the cap branch, computes `reserveToken - realBalance` with `realBalance > reserveToken`, and the call reverts with a raw arithmetic Panic instead of completing or cleanly reverting with `OverflowCapDegenerate`.
4. As long as `exchangeRate()` doesn't independently satisfy the USD trigger, the token can never graduate — the curve-raised LT and `LP_RESERVE` tokens remain permanently stranded.

**Note on completeness:** I was unable to fully re-verify within the available tool calls whether any other call site guards against this exact panic (e.g., a wrapping `try/catch` in `Bonding.buy`), so it is possible — but not confirmed by anything found in the indexed contract code — that `Bonding.buy` swallows this specific revert path; no such handling was found in the `Router.sol` or `Bonding.sol` snippets retrieved. If deeper verification is needed, a Devin session with full repository access should trace every caller of `Router.buy`/`previewBuy`/`getAmountOut` to confirm none of them catches or otherwise neutralizes this Panic.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
