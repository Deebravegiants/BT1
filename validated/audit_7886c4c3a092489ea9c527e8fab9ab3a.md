### Title
Permanently frozen market: `scaled_to_original` overflows `i128` on the accrual path before `MAX_BORROW_INDEX_RAY` can cap growth, bricking every verb on the market - (File: contracts/pool/src/interest.rs, common/src/rates/scaling.rs, common/src/rates/simulate.rs)

### Summary
CVE-2022-27406 is a crash (segfault) reached by passing an unchecked size into `FT_Request_Size`. The analog in XOXNO Lending is a reachable, state-poisoning arithmetic panic: once a market's `borrowed * borrow_index` (RAY-scaled value) exceeds `i128::MAX`, the very first computation inside `accrue_step` — `scaled_to_original(env, borrowed, borrow_index)` — raises `MathOverflow` via `mul_div_half_up`. Because `global_sync` accrues before every mutating verb, the panic permanently bricks `supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `flash_loan`, and `update_indexes` for that (hub, token) book: no user can ever exit or repay again, and even liquidation is unreachable, so suppliers' funds are frozen forever.

The defense that is supposed to stop this, `MAX_BORROW_INDEX_RAY` in `update_borrow_index`, caps the *index* — but the overflow happens on the *value* (`borrowed × index`), which reaches `i128::MAX` (~1.7e38) when a whale-scale book's index reaches ~170×, far below the 10^36 index cap. The codebase's own test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321) demonstrates exactly this: the market dies with `MATH_OVERFLOW` while `last.borrow_index < MAX_BORROW_INDEX_RAY`, and subsequent `try_withdraw_raw` / `try_repay` both fail with the same error — confirming permanent freeze, not a transient revert.

### Finding Description
- `accrue_step` (common/src/rates/simulate.rs:60-62) computes `borrowed_original = scaled_to_original(env, borrowed, borrow_index)` before any rate/index bounding. `scaled_to_original` → `Ray::mul` → `mul_div_half_up` (common/src/math/fp_core.rs), which returns `GenericError::MathOverflow` when the product's quotient does not fit `i128`.
- `global_sync` (contracts/pool/src/interest.rs:20-33) runs `accrue_chunk` unconditionally at the head of every state-changing pool operation when any time has elapsed.
- `update_borrow_index` (common/src/rates/index.rs:13-19) clamps the index at `MAX_BORROW_INDEX_RAY`, but the clamp is applied *after* the value computation that overflows, and the overflow threshold (value > `i128::MAX`) is independent of the index cap.
- Utilization is value-based, and debt compounds while supply grows more slowly, so an untouched market drifts toward higher utilization and the steep slope of the rate curve — the runaway is self-reinforcing once it starts. There is no circuit breaker: no verb skips accrual, and `clean_bad_debt`/liquidation (the intended recovery paths for a stuck market) hit the same panic.

An unprivileged attacker can set up the precondition: `supply` a position up to the governance cap (`max_cap_for_decimals` permits ray-scaled books whose token-unit totals approach `i128::MAX / 10^(27-d)` — for 18-decimal assets ~1.7e11 whole tokens, for low-decimal high-value assets correspondingly fewer), then `borrow` at high utilization. From that point, *no further attacker action is required*: ordinary time passage plus any organic `update_indexes` call drives the index up until the next accrual traps.

### Impact Explanation
Permanent freezing of user funds and a contract unable to operate: every supplier's deposit in the affected market becomes unwithdrawable forever, borrowers cannot repay, liquidations cannot run, and the market's entire pool balance is locked in the contract. This is not a per-transaction revert (which would be no-impact); the panic is a function of stored state (`borrowed`, `borrow_index`) that only grows, so it can never be cleared once crossed. The same class also applies on the supply side through `supplied * supply_index` inside `update_supply_index`/`scaled_to_original`.

### Likelihood Explanation
Medium-low. The trigger needs a book whose ray-scaled value approaches `i128::MAX` — whale-scale deposits (billion-token scale at 18 decimals, or proportionally less for high-value/low-decimal assets) at sustained high utilization on a steep curve, compounded over many years. Caps bound the setup but `max_cap_for_decimals` explicitly allows ray values up to the `i128` ceiling, so governance cap policy does not rule it out on large markets. Once a book drifts past the optimal-utilization knee, the rate curve accelerates the approach without further attacker input. The in-repo stress test reaches the cliff, confirming it is a real domain edge rather than a theoretical bound — the gap is that the index cap was assumed to bound growth, but the value-domain overflow fires first.

### Recommendation
- In `accrue_step`, compute the value projections with saturating arithmetic (e.g., `mul_div_floor_saturating` or a checked variant that returns the capped borrow index directly) so that hitting the `i128` value ceiling clamps `borrow_index`/`supply_index` to their max constants instead of trapping. Concretely: when `borrowed` or `supplied` is large enough that `scaled_to_original` would overflow, utilization saturates at 100% anyway — clamp it explicitly and continue.
- Alternatively, short-circuit accrual when `borrow_index == MAX_BORROW_INDEX_RAY` *before* computing `borrowed_original` (the cap check currently happens inside `update_borrow_index`, after the overflowing value computation), so capped markets keep operating.
- Add a regression asserting that once a market reaches the value ceiling, `withdraw`/`repay`/`liquidate` still succeed rather than panicking in the accrual preamble.

### Proof of Concept
Sketched from the repo's own harness (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360):

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve())) // 175% max rate, opt 75%
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);

// Unprivileged setup: whale supply + 98% borrow.
t.supply_raw(BOB, "BIG18", BILLION * 10i128.pow(18));
t.supply_raw(ALICE, "COL", 3 * BILLION * 10_000_000);
t.borrow_raw(ALICE, "BIG18", BILLION * 10i128.pow(18) / 100 * 98);

// Any permissionless update_indexes call advances accrual.
loop {
    t.advance_time(YEAR_SECS);
    if t.try_update_indexes_for(&["BIG18"]).is_err() { break; } // -> MATH_OVERFLOW
}

// Permanent freeze: every verb accrues first and hits the same panic.
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0),  errors::MATH_OVERFLOW);
// liquidate, clean_bad_debt, flash_loan fail identically.
// last.borrow_index < MAX_BORROW_INDEX_RAY: the index cap never engaged.
```

Attacker entrypoints used: `controller.supply`, `controller.borrow`, `controller.update_indexes` — all unprivileged. Root cause is `scaled_to_original(borrowed, borrow_index)` panicking inside `accrue_step` (common/src/rates/simulate.rs:60) before `update_borrow_index`'s cap can fire, with `global_sync` (contracts/pool/src/interest.rs:20) forcing accrual ahead of every exit path.
