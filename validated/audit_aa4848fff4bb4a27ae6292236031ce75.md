Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers that are never included in the HMAC-signed content [2](#0-1) . `Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)` and then dispatches to the handler using these unauthenticated header values as the tenant/topic identity [3](#0-2) .

### Title
Webhook tenant/topic identity spoofing via unsigned headers despite valid body HMAC - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, but the `shop`, `topic`, `webhook_id`, and `api_version` values that the host application relies on for tenant routing and business logic are taken from HTTP headers that are excluded from that signature. This breaks the intended binding: `shop-domain header == the shop the HMAC actually authenticates`.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` value [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns `@raw_body` exclusively [1](#0-0) . The `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` accessors are all sourced from the `shopify-*`/`x-shopify-*` headers via `shopify_header` [5](#0-4) [6](#0-5) . None of these headers are part of the signed content.

`Registry.process` trusts these header-derived values directly: it validates only the body HMAC, then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id)` and hands it to the registered handler [3](#0-2) . The equality the code implicitly assumes is: `shop header presented at request time == shop the body's HMAC was generated for`. But since the signature covers only `@raw_body`, this equality is never enforced — an unprivileged actor who obtains any one validly-signed body/HMAC pair (e.g., from a webhook legitimately delivered for their own shop, which any merchant installing the app can trigger) can resend that exact body+HMAC to the app's webhook endpoint while substituting arbitrary `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` header values. The signature still validates because it never covered those fields, and the host handler processes the (real) body as if it belongs to a different shop and/or a different event topic.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: an app built on this library and following its documented `Registry.process` API will attribute genuinely-signed webhook payload data to an attacker-chosen `shop` value, and/or dispatch it to a handler registered for a different `topic` than the one the payload was actually signed/intended for. This matches the "Critical - cross-tenant access" impact category, since the shop identity used to key storage/session lookups downstream of the handler is attacker-controlled despite HMAC validation passing.

### Likelihood Explanation
Any merchant who installs the app (a normal, unprivileged action) can trigger a real webhook delivery to their own configured endpoint and thus obtain a body+HMAC pair that is valid under the app's `client_secret` — without ever needing to know the secret itself. Replaying that pair with modified headers against the app's public webhook endpoint requires no further privilege, matching the "unprivileged internet user" threat model.

### Recommendation
Include the header-derived identity fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signable string, or otherwise separately bind them cryptographically (e.g., verify `shop` against the session/shop the webhook subscription was registered for) before dispatching to handlers in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own development shop (`attacker.myshopify.com`) and registers a webhook subscription for a topic such as `orders/create`.
2. Attacker triggers the event on their own shop, capturing the raw POST body and the `shopify-hmac-sha256` header — both fully valid since they were computed by Shopify using the real `client_secret`.
3. Attacker resends this exact `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com` (and optionally a different `shopify-topic`).
4. `HmacValidator.validate` passes because it only checks the body against the HMAC. `Registry.process` calls the handler with `shop: "victim.myshopify.com"`, causing the app to process attacker-supplied order data under the victim's tenant context. [3](#0-2)
