### Title
Webhook HMAC only signs the raw body, letting attacker-forged `shop-domain`/`topic` headers impersonate another shop's webhook — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC verification performed by `ShopifyAPI::Webhooks::Registry.process` never covers the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Any party that can obtain one legitimately-signed `(body, hmac)` pair for the app (e.g. by installing the public app on their own shop and letting Shopify deliver a real webhook) can replay that exact body/HMAC pair to the app's public webhook endpoint while freely rewriting the `shop-domain` and `topic` headers to impersonate a different shop or a different event type.

### Finding Description
Webhook authenticity is established purely by: [1](#0-0) 
which signs `@raw_body` only, while: [2](#0-1) 
exposes `topic`, `shop`, `api_version`, and `webhook_id` purely as pass-through header reads, none of which participate in `to_signable_string`.

`Registry.process` trusts these unauthenticated header values directly to route and attribute the event: [3](#0-2) 

The identity binding that should hold is:
`hmac == HMAC(secret, raw_body ‖ shop ‖ topic)` (i.e., the shop and topic the app *acts on* should be part of what's cryptographically verified).

What actually holds is:
`hmac == HMAC(secret, raw_body)` while `shop`/`topic` are taken from unauthenticated headers — breaking the binding between "bytes verified" and "bytes acted on."

Since `api_secret_key` is shared by the app across every shop that installs it, any shop (an ordinary, unprivileged app installer) can trigger a real webhook delivery for its own shop, capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair, and then send a forged HTTP request directly to the app's public webhook endpoint with that same body/HMAC but with `shopify-shop-domain` (and optionally `shopify-topic`) rewritten to a victim shop/topic of the attacker's choosing. `Utils::HmacValidator.validate` will still pass because it only checks the raw body: [4](#0-3) 

### Impact Explanation
This is a cross-tenant identity confusion: the app's webhook handler receives an event it believes to be authenticated data from shop B, but it is actually attacker-controlled data (topic and shop chosen by the attacker) merely wrapped in a validly-signed body belonging to shop A. Any app logic that keys state, tenant records, or trust decisions off `WebhookMetadata#shop`/`#topic` (exactly the fields `Registry.process` forwards to `handler.handle`) can be manipulated to write/act on behalf of an arbitrary victim shop — a cross-tenant access impact.

### Likelihood Explanation
Any user who can install the app on a shop they control (a normal, unprivileged action) and passively receive one real webhook delivery has everything needed: a valid `(body, hmac)` pair. No access token, `client_secret`, or TLS interception is required — only the ability to POST an HTTP request to the app's public webhook endpoint with custom headers, which is inherent to how HTTP webhook endpoints work.

### Recommendation
Include `shop`, `topic`, and other security-relevant identity headers in the signed material Verified against `X-Shopify-Hmac-Sha256`, or — since Shopify's real HMAC scheme only ever signs the raw body — have `Registry.process`/`WebhookMetadata` require the caller to independently cross-check `request.shop` against the shop the request was routed to (e.g., an authenticated per-tenant endpoint path/token) rather than trusting the `shop-domain`/`topic` headers as authenticated identity.

### Proof of Concept
1. Install the (target) app on an attacker-controlled shop `attacker.myshopify.com` and trigger any webhook topic (e.g. `orders/create`), capturing the raw POST body `B` and the real `X-Shopify-Hmac-Sha256: H` header Shopify sends.
2. Resend that exact request to the app's public webhook endpoint, keeping `B` and `H` unchanged, but replace the `X-Shopify-Shop-Domain` header with `victim.myshopify.com` (and, if desired, `X-Shopify-Topic` with another registered topic whose handler accepts body shape `B`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `B`, so it validates successfully: [5](#0-4) 
4. The registered handler executes with `WebhookMetadata` reporting `shop: "victim.myshopify.com"`, even though the payload actually originated from and was signed for the attacker's own shop.
