The pool's `supply` mints shares deterministically at the live `supply_index`; let me check whether any unprivileged call can move that index adversely (the analog of a manipulated `mintRatio`), and whether controller entrypoints carry min-out/deadline params.### Title
`withdraw` and `supply` have no min-out / index-slippage protection; unprivileged bad-debt socialization can cut the `supply_index` before execution - (File: contracts/pool/src/interest.rs)

### Summary
The controller's `supply` and `withdraw` entrypoints convert token amounts to scaled supply shares (and back) purely at the live `supply_index`, with no `min_shares`/`min_amount_out` parameter and no deadline. Unlike ordinary interest accrual (which only raises the index, in the user's favor at withdraw time and predictably), the index can be forced down inside the same ledger by `apply_bad_debt_to_supply_index`, reachable by any unprivileged caller via `liquidate` or `clean_bad_debt` → pool `seize_positions`. A user who signs a withdrawal expecting payout X can receive strictly less if a bad-debt write-down is ordered first.

### Finding Description
- `withdraw` burns scaled shares and pays `unscale_supply_floor(scaled)` at the committed `supply_index`; there is no `min_out` argument anywhere in the controller/pool ABI (`contracts/pool/src/ops/withdraw.rs`, `interfaces/controller/src/lib.rs`, `interfaces/pool/src/lib.rs`).
- `supply` mints `calculate_scaled_supply(amount)` = `floor(amount·RAY·K / supply_index)`, so a lower index mints fewer shares for the same tokens (`contracts/pool/src/ops/supply.rs:28-33`, `contracts/pool/src/cache/scale.rs:30-37`).
- The index is not monotone: `apply_bad_debt_to_supply_index` multiplies it by `remaining/total_supplied_value` and floors it at `RAY/1000` (`contracts/pool/src/interest.rs:73-88`). This is invoked from `seize_positions` on the `Borrow` side (`contracts/pool/src/ops/seize.rs:23-28`), which the controller calls from `execute_bad_debt_cleanup` (`contracts/controller/src/positions/liquidation/bad_debt.rs:35-49`) — reachable by the unprivileged `clean_bad_debt` and `liquidate` entrypoints.
- No deadline/expiration exists on any entrypoint; a stale signed intent executes whenever sequenced.

### Impact Explanation
A supplier's withdrawal payout is `shares × supply_index` floored at two conversion steps. If a bad-debt seizure lands first (e.g., a liquidator observing the mempool, or any user calling `clean_bad_debt` on a dust-threshold underwater account), the victim's fixed share count is re-priced at a lower index and they permanently receive less underlying — the loss is shifted to them rather than to the suppliers who remain. The same applies to a supplier depositing through `supply` in the same ordering window (fewer shares minted than expected). This is the direct analog of the DODO `buyShares` report: share mint/burn priced by an on-chain mutable ratio with no user-set bound or deadline.

### Likelihood Explanation
Ordering-dependent and requires a liquidation/cleanup producing actual bad debt in the same market the victim is exiting — not freely manufacturable, since the write-down requires a real underwater account past the dust threshold. Impact per event is bounded by the bad-debt size but can be large (up to `1 − SUPPLY_INDEX_FLOOR` of supplier value in extreme insolvency). Medium severity: real user-fund loss, conditional trigger.

### Recommendation
- Add a `min_amount_out` (or `min_supply_index`) parameter to `withdraw` and a `min_shares` parameter to `supply` on the controller, threaded through to the pool ops; revert if the committed `supply_index` or computed payout/shares fall below the caller's bound.
- Optionally check a `deadline` (ledger timestamp) argument and revert stale executions.

### Proof of Concept
1. Victim holds `S` scaled supply shares in `(hub, USDC)`; index = `I`.
2. Victim submits `controller.withdraw(...)`; expected payout ≈ `floor(S·I/RAY)` tokens.
3. In the same ledger, an attacker calls `clean_bad_debt(account_id)` on an underwater account; `seize_positions` runs `apply_bad_debt_to_supply_index`, setting `I' = I·(1 − bad_debt/total_supplied_value)`.
4. Victim's withdraw executes at `I' < I`, paying strictly fewer USDC — with no parameter in the calldata that could have prevented it.
