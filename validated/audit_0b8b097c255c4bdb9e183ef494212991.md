### Title
Stale delegate grant reactivates when the position NFT returns to its original owner — dangling authorization analog of missing-unregister use-after-free - (File: contracts/controller/src/storage/account.rs)

### Summary
The CVE class is "a registered entry survives the teardown of the object it references and can still be invoked." The lending analog is the controller's delegate registry. `DelegateGrant` is stored under `ControllerKey::Delegates(account_id)` and is *not* deleted when the position NFT (which is the account) changes owner; it is only filtered out by checking `grant.granted_by == current_owner` in `get_delegates`. A stale grant is purged only if the *new* owner happens to call `remove_delegate` (`grant.granted_by != *owner` → `persistent().remove`). If the NFT is transferred away and then transferred back to the original owner without that purge ever running, the old delegate's authorization silently becomes live again — the "unregistered" command is invocable on the reconstituted account.

### Finding Description
- `get_delegates` returns delegates only when `grant.granted_by == *owner`, so ownership change "invalidates" the grant logically but leaves it in storage (`storage/account.rs:176-181`).
- `remove_delegate` deletes a stale grant only when invoked with the *current* owner, and this is the only purge path for an ownership change (`storage/account.rs:226-247`).
- `remove_account_entry` removes the `Delegates` key, but only on account deletion — a plain NFT `transfer`/`approve` does not touch it (`storage/account.rs:249-256`).
- The test `remove_delegate_purges_stale_grant_preventing_resurrection` proves the behavior: resurrection is prevented *only because* the intermediate owner purged the key (`tests/storage/account.rs:180-226`). Without that purge, `get_delegates(account_id, alice)` returns the original list the moment `owner_of` resolves to Alice again.
- Since NFT token ids are sequential and the token id is the account id (`position-nft/src/contract.rs:68-76`), the same `account_id` — and therefore the same `Delegates(account_id)` key — legitimately rebinds to Alice.

Attack path (single unprivileged address plus a normal transfer): Alice grants delegate D; Alice transfers the position NFT to Bob (sale/collateral move); Bob never calls `remove_delegate` (he has no incentive to); the NFT later returns to Alice (repurchase, protocol unwind, `transfer` back). D's registration — which Alice believes died with the transfer — is live again, and D can exercise every entrypoint that accepts the delegate-auth path (account.rs routes delegate-authorized calls through `get_delegates`) on Alice's reconstituted account without any new consent.

### Impact Explanation
A previously revoked-in-practice delegate regains full delegated authority over the account: it can open borrows against Alice's collateral, reorder/withdraw positions through the delegate-authorized entrypoints (supply/borrow/withdraw paths accept delegate callers per `account.rs`), or push the account toward liquidation — theft of user funds and forced insolvency of Alice's position. The authorization was never explicitly re-granted; it resurrected from storage that should have been invalidated at transfer time.

### Likelihood Explanation
Medium. It requires (a) Alice to have granted a delegate, (b) an NFT transfer round-trip back to Alice, and (c) no intermediate `remove_delegate` purge — all plausible for accounts used as transferable collateral. The trigger (NFT `transfer`) is an unprivileged, in-scope entrypoint.

### Recommendation
Invalidate delegate grants eagerly on ownership change instead of relying on the `granted_by` filter plus an optional purge: have the controller hook NFT transfer (or check-and-clear on first account access after an owner change) to remove `ControllerKey::Delegates(account_id)` whenever `granted_by != owner_of(account_id)`, so the grant cannot resurrect even if the token round-trips.

### Proof of Concept
1. Alice owns account `id`; calls the delegate-grant entrypoint so `add_delegate(env, id, alice, D)` writes `DelegateGrant{granted_by: alice, delegates: [D]}` under `Delegates(id)`.
2. Alice calls `position_nft.transfer(alice → bob, id)`. The `Delegates(id)` entry is untouched; `get_delegates(id, bob)` yields `[]` only because `granted_by != bob`.
3. Bob performs only normal actions (supply/withdraw) — never `remove_delegate` — so `Delegates(id)` survives.
4. Bob calls `position_nft.transfer(bob → alice, id)`. Now `granted_by == alice` again and `get_delegates(id, alice)` returns `[D]`.
5. D invokes a delegate-authorized account operation (e.g., `borrow` on `id`) and it succeeds, demonstrating the dangling registration was reactivated without any re-authorization by Alice.
