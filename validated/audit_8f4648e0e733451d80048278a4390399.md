### Title
`ExternalActionSwap.swap` never verifies the router actually consumed only `inputAmount`, letting an attacker sweep residual/stray input-token balance left by `approveUnlimited` into their own output UTXO - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`ExternalActionSwap.swap`/`LifiExternalAction.callRouter` size the swapped amount purely from the **output**-token balance delta (`getERC20OrETHBalance(outputToken)` before/after the router call) and never check how much of the **input** token the router actually pulled. Because `approveUnlimited` (`contracts/TransfererBase.sol:32-43`) leaves a standing max allowance from the action contract to the LI.FI router that persists across transactions, an attacker who supplies their own `externalActionMetadata` can make the router consume more input token than the `inputAmount` derived from `-deltaAmounts[0]`, pulling any stray/leftover input-token balance sitting in the action contract and having the resulting extra output fully credited to their own minted UTXO.

### Finding Description
The equality that should hold is:

`tokens leaving the action to Hinkal this tx == -deltaAmountChanges Hinkal sent into the action this tx (converted 1:1 through the swap, output-side)`

In `swap()`:
```
contracts/external-actions/swaps/ExternalActionSwap.sol:44-68
address inputToken = circomData.erc20TokenAddresses[0];
uint256 inputAmount = uint256(-deltaAmounts[0]);
...
uint256 swappedAmount = callRouter(inputToken, inputAmount, outputToken, circomData.externalActionData.externalActionMetadata);
```
`inputAmount` is passed to `callRouter`, but `LifiExternalAction.callRouter` (`contracts/external-actions/swaps/LifiExternalAction.sol:16-36`) never uses `inputAmount` to bound what the router is allowed to pull — it only:
1. calls `approveUnlimited(inputToken, router)`, which sets allowance to `type(uint256).max` whenever the existing allowance is below `type(uint256).max/2` (`contracts/TransfererBase.sol:32-43`), so the allowance is effectively unlimited and persists across calls/transactions once set;
2. executes `router.call(externalActionMetadata)` with attacker-supplied calldata (attacker controls `externalActionMetadata` per the threat model);
3. measures `swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore` — purely an output-side balance delta.

Because the allowance is unlimited and persists, and the amount actually pulled by the router is dictated solely by the attacker-crafted `externalActionMetadata`, the router can be instructed to consume more of `inputToken` than the `inputAmount` implied by the caller's `-deltaAmounts[0]` — as long as the action contract's actual `inputToken` balance (e.g., dust/stray/residual balance left behind by rounding, a partially-filled prior swap, or any other stranded balance) covers it. Whatever extra output this yields is entirely captured by `swappedAmount`, then propagated unmodified into:
```
contracts/external-actions/swaps/ExternalActionSwap.sol:89-101
uint256 amountToSendToHinkal = swappedAmount - totalFee;
transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal);
utxoSet[0] = UTXO({ amount: amountToSendToHinkal, ... stealthAddressStructure: circomData.stealthAddressStructure, ...});
```
The minted UTXO amount (and the tokens sent to `msg.sender`/Hinkal) is never checked against `-deltaAmounts[0]`; only a minimum output slippage floor (`circomData.slippageValues[1] != 0` — merely non-zero, not enforced as an actual floor comparison in this snippet) is required. There is no assertion anywhere in `swap()` that the router consumed exactly `inputAmount` of `inputToken`, nor that `swappedAmount` corresponds 1:1 to the declared `-deltaAmounts[0]`.

None of the standard guards catch this: `performHinkalChecks`/`dimensionsCheck` validate array shapes and public-input binding for the current proof, not post-hoc balance reconciliation inside the external action; `verifyProof`/circuit constraints (`inTotal + amountChanges === outTotal`) constrain the *shielded* pool accounting for the attacker's own declared amounts, but have no visibility into what the external action contract actually did on-chain with its ERC20 balance/allowance; `onlyAllowedRecipient` only checks the caller is Hinkal, not that the swap consumed the declared amount.

### Impact Explanation
An attacker can direct value that is not part of their own `-deltaAmountChanges` (residual balance stranded in the `ExternalActionSwap`/`LifiExternalAction` contract from prior interactions) into their own freshly-minted output UTXO, i.e. direct theft of value the protocol/other users left in the action contract. This matches "Critical: direct theft of shielded or in-flight user funds." It is repeatable any time stray balance accumulates in the action contract and the standing allowance to the router remains unlimited.

### Likelihood Explanation
The exploit requires: (1) some non-zero residual `inputToken` balance already sitting in the `LifiExternalAction` contract (from rounding, partial fills, or any prior operation that didn't fully sweep balances), and (2) the standing unlimited allowance from `approveUnlimited` (which persists by design once granted). The attacker only needs to submit an ordinary swap transaction with custom `externalActionMetadata` that instructs the LI.FI router to pull more than their declared `inputAmount`. This is low-cost (one transaction, standard proof generation for the attacker's own UTXOs) and fully repeatable whenever residual balance exists.

### Recommendation
In `swap()`/`callRouter`, explicitly measure and cap the input token consumed by the router call (e.g., check `balanceBefore(inputToken) - balanceAfter(inputToken) == inputAmount`, or use `approveERC20Token` with the exact `inputAmount` instead of `approveUnlimited`, resetting allowance to zero after each call) so the router can never draw on any balance beyond what was declared for the current transaction's `-deltaAmounts[0]`.

### Proof of Concept
Foundry plan:
1. Deploy `LifiExternalAction` with a mock router and mock ERC20 `inputToken`/`outputToken`.
2. Seed a residual balance of `inputToken` directly into the action contract (simulate stranded dust from a prior tx), and trigger one prior `swap()` so `approveUnlimited` sets the max allowance to the mock router.
3. As the attacker, craft `externalActionMetadata` for the mock router that calls `transferFrom(action, router, residual + inputAmount)` then mints `outputToken` proportional to the full pulled amount back to the action contract (simulating LI.FI actually swapping more than declared).
4. Call `runAction` via the allowed recipient (Hinkal mock) with `deltaAmounts[0] = -inputAmount` (i.e., the attacker only declared `inputAmount`).
5. Assert: `utxoSet[0].amount` (and tokens sent to `msg.sender`) is strictly greater than what a correct 1:1 accounting of `-deltaAmounts[0]` through the swap rate would produce — i.e., `swappedAmount` includes the seeded residual, violating `tokens leaving action == -deltaAmountChanges` and directly crediting the attacker's own UTXO with unaccounted value.
