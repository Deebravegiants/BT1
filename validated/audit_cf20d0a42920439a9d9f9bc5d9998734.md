### No vulnerability found for this question.

The `implied_scope` logic in [1](#0-0)  intentionally expands `write_X` (and `unauthenticated_write_X`) to also imply `read_X`, and `covers?` checks against this expanded set as shown in [2](#0-1)  and [3](#0-2) . This mirrors Shopify's actual OAuth/API access-scope semantics, where granting a `write_*` scope during installation genuinely also grants the corresponding `read_*` access on Shopify's side — it is not something this gem invents or misrepresents. The equality the question poses ("the scope the merchant granted == the scope the code treats as authorized") holds true precisely because Shopify's real authorization server implements write-implies-read, so there is no divergence between what was actually granted and what this code trusts. This is documented, intended behavior of Shopify's scope system, not a bug in the gem's code, and the question itself concedes this by stating "this is intended for write->read."

      def store_scopes(scope_names)
        scopes = scope_names.map(&:strip).reject(&:empty?).to_set
        implied_scopes = scopes.map { |scope| implied_scope(scope) }.compact

        @compressed_scopes = scopes - implied_scopes
        @expanded_scopes = scopes + implied_scopes
      end
