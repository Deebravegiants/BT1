### Title
Attacker-controlled flash-position receiver can add wallet-draining calls to the caller's signed authorization tree - ([File: contracts/controller/src/strategies/flash_position.rs](contracts/controller/src/strategies/flash_position.rs))

### Summary
`flash_position` accepts an arbitrary Wasm `receiver` supplied by the caller, invokes it before final settlement, and does not constrain the authorization requests made inside that callback. A malicious receiver can therefore request a token transfer from the caller's wallet to the attacker. Soroban simulation records that nested transfer beneath the caller's `flash_position` authorization; if the caller signs the resulting tree, the host executes the theft even though the protocol only intended to authorize the flash-position call.

### Finding Description
`process_flash_position` begins by authenticating the supplied `caller`, but authentication only establishes who is executing the strategy; it does not establish that the `receiver` is trusted or benign. [1](#0-0) 

The receiver validation is limited to requiring a Wasm contract and excluding the controller and pool addresses. There is no allowlist, bytecode hash, interface attestation, or other integrity check that limits what code the caller-selected receiver executes. [2](#0-1) 

After minting and forwarding the debt proceeds, the controller invokes that arbitrary receiver inside the transaction. [3](#0-2) 

The receiver receives the `initiator`, `account_id`, asset, borrowed amount, measured amount received, controller address, and opaque `data`, so it has enough context to run attacker-selected logic during the still-active caller authorization. [4](#0-3) 

The repository's authorization-tree test demonstrates the relevant Soroban behavior: a nested `token.transfer(caller, attacker, amount)` is recorded as a child of the caller's authorized root invocation, and signing that poisoned tree causes the host to accept and execute the transfer. [5](#0-4) [6](#0-5) 

This is the same trust-boundary failure as dereferencing a package symlink during installation: the caller nominally authorizes a flash-position operation, while an attacker-selected indirection causes content outside that operation—the victim's unrelated wallet token transfer—to be folded into the authorized result.

### Impact Explanation
An attacker can steal arbitrary token balances from a victim who submits or signs a transaction containing the malicious receiver. The stolen asset does not need to be listed by the lending protocol, deposited as collateral, or otherwise related to the flash position.

The victim's signed authorization is still required, so this is a user-interaction exploit rather than an unauthenticated protocol drain. That does not eliminate the impact: the malicious transfer is introduced by code reached through the protocol's caller-controlled callback and is represented as part of the authorization tree for the transaction being simulated.

### Likelihood Explanation
The exploit requires the victim to choose the attacker's receiver contract and sign the simulated authorization tree containing the extra token transfer. A malicious frontend, integration, copied example, or misleadingly advertised receiver can supply that address. Once supplied, the controller enforces only `caller.require_auth()`, Wasm-receiver checks, measured collateral receipts, and post-callback risk checks; none of those conditions bounds unrelated wallet movement requested by the receiver. [7](#0-6) [8](#0-7) 

The same authorization-tree mechanism is directly demonstrated by the repository's rogue-hop test: an honest root-only signature rejects the unauthorized transfer, while signing the simulation-produced poisoned tree moves the victim's full wallet balance to the attacker. [9](#0-8) 

### Recommendation
Do not allow arbitrary production receivers to execute under a caller-authorized flash-position operation without an integrity boundary. Prefer one of:

- restrict `flash_position` to governance-approved receiver bytecode hashes or deployed receiver addresses;
- require the caller to authorize an explicit, separately visible callback operation before invoking a non-approved receiver;
- derive the receiver from a caller-controlled account contract whose code has previously been attested;
- at minimum, expose and enforce a signed authorization-tree policy in all SDK/UI paths that rejects children unrelated to the expected collateral and refund token transfers.

Any fix should include a regression test where `execute_flash_position` calls `token.transfer(caller, attacker, amount)` for an unrelated token and assert that simulation does not silently fold that transfer into a legitimate-looking `flash_position` authorization.

### Proof of Concept
1. Victim Alice owns a `flash_position`-eligible account and holds `WALLET_BALANCE` units of an unrelated token `T`.
2. Attacker deploys `MaliciousReceiver`, a Wasm contract implementing `execute_flash_position`.
3. In that callback, the receiver executes:

```rust
token::Client::new(&env, &wallet_token).transfer(
    &initiator,
    &attacker,
    &WALLET_BALANCE,
);
```

It separately sends enough declared collateral to `controller` for the flash position to satisfy the callback receipt and final risk checks.

4. Alice submits or signs:

```text
flash_position(
    caller = alice,
    account_id,
    spoke_id,
    mode = Multiply,
    debt = listed_debt_asset,
    amount,
    receiver = malicious_receiver,
    data,
    collaterals = acceptable_collateral_minimums,
    refund_assets = [],
)
```

5. `caller.require_auth()` succeeds at the controller root, `require_wasm_receiver` accepts the contract, and the controller invokes `execute_flash_position`. [10](#0-9) [4](#0-3) 
6. Simulation records `T.transfer(alice, attacker, WALLET_BALANCE)` as a child of Alice's `flash_position` authorization. If Alice signs that returned tree, the host executes the transfer. The repository's equivalent authorization-tree test shows that the poisoned signed tree succeeds and leaves Alice's unrelated wallet balance at zero. [11](#0-10) [6](#0-5) 
7. The callback can still transfer valid collateral to the controller, so the later measured-deposit and account-risk checks do not repair the already-authorized wallet theft. [8](#0-7)

```rust
pub(crate) fn process_flash_position(
    env: &Env,
    caller: &Address,
    params: FlashPositionParams<'_>,
) -> u64 {
    require_authorized_caller(env, caller);

    let FlashPositionParams {
        account_id,
        spoke_id,
        mode,
        debt,
        amount,
        receiver,
        data,
        collaterals,
        refund_assets,
    } = params;

    require_positive_amount(env, amount);
    config::require_hub_active(env, debt.hub_id);
    assert_with_error!(
        env,
        matches!(
            mode,
            PositionMode::Multiply | PositionMode::Long | PositionMode::Short
        ),
        CollateralError::InvalidPositionMode
    );
    require_wasm_receiver(env, receiver);

    let controller = env.current_contract_address();
    assert_with_error!(
        env,
        *receiver != controller,
        FlashLoanError::InvalidFlashloanReceiver
    );

    let mut cache = Context::new(env);
    let pool_addr = cache.cached_pool_address();
    assert_with_error!(
        env,
        *receiver != pool_addr,
        FlashLoanError::InvalidFlashloanReceiver
    );
```

```rust
#[test]
fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
}
```
