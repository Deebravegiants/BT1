I have sufficient evidence to confirm the finding. The `Webhooks::Request` class binds a tenant-identifying field (`shop`) that is read directly from an HTTP header but is not part of the HMAC-signed payload.

### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but the HMAC signature it validates against only covers the raw request body, never the `shop` header. This breaks the identity binding `hmac_signed_bytes == bytes_the_app_acts_on`, allowing an attacker who possesses one genuine, validly-signed webhook payload to relabel it as belonging to a different (victim) shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) , and `Request#shop` is read straight from the (unsigned) `shop-domain` header: [2](#0-1) .

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header, then dispatches to the handler using `request.shop` and `request.topic` taken from headers that were never included in the signature: [3](#0-2) . `HmacValidator.validate_signature` only checks `to_signable_string`, never the headers used for tenant/topic identification: [4](#0-3) .

This is exactly the pattern flagged in the report — "a field acted on but not covered by the HMAC." Notably, the gem's own OAuth callback path does this correctly: `Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters: [5](#0-4) , showing the intended binding contract that the webhook path fails to uphold. The `WebhookMetadata` struct handed to the app's handler carries this unverified `shop` value forward as ground truth: [6](#0-5) .

### Impact Explanation
An attacker who controls (or is) a legitimate merchant on the platform receives genuine Shopify-signed webhooks for their own shop (e.g. `orders/create`, `customers/data_request`). Because the HMAC covers only the body — not the shop domain — the attacker can replay that exact valid `(body, hmac)` pair to the host application's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Registry.process` will still validate successfully (body unchanged, HMAC matches), and the host application's `handler.handle` will be invoked with `WebhookMetadata.shop` set to the victim's shop rather than the attacker's. Any host logic that uses `data.shop` to look up sessions, tokens, or per-tenant records for processing then operates under a falsified tenant identity — a cross-tenant integrity violation directly caused by the gem's identity binding failure.

### Likelihood Explanation
Exploitation requires the attacker to be a legitimate merchant with an installed app (no stolen credentials or `client_secret` needed) and to know or guess a target shop's domain, which is often public (`*.myshopify.com`). Capturing one's own valid webhook body+HMAC pair is trivial, and crafting an HTTP POST with a substituted header requires no special access. This is a realistic, low-effort exploitation path.

### Recommendation
Include the shop domain (and topic) in the HMAC-signed payload verification, or otherwise cryptographically bind the `shop`/`topic` values to the signed body before dispatching to the handler — analogous to how `AuthQuery#to_signable_string` binds `shop` for the OAuth flow. At minimum, `Utils::HmacValidator` should be extended so that webhook verification incorporates all fields the handler will subsequently trust (`shop`, `topic`), not just the raw body.

### Proof of Concept
1. App receives a genuine Shopify webhook for `attacker-shop.myshopify.com` with body `B` and valid header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` with the app's `client_secret`).
2. Attacker replays the request to the app's webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`= B`) and matches `H` — validation succeeds: [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though Shopify never issued this webhook for that shop.
