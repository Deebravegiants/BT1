### Title
Camera pipeline `Reset`/`Pause` state confusion can leak biometric frames from a prior signup into a subsequent signup - (File: `src/agents/camera/rgb/mod.rs`)

### Summary
The DeFi report's root cause is a calculation/state-handling gap: an intermediate quantity (leftover token balance) is computed but never explicitly cleared/reimbursed, so it silently persists and becomes available to an unrelated, unintended party in a later operation. The closest unprivileged-user analog in `orb-core` is the RGB camera pipeline's `Stop`/`Pause` vs. `Reset` command handling: after a capture session ends, the pipeline is left in a `Pause` state rather than explicitly `Reset`, and the code's own comments acknowledge frames can leak across state transitions.

### Finding Description
When a capture cycle (`Command::Start`) ends normally, the manager sends `worker::Command::Pause` to the underlying GStreamer worker rather than `Reset`: [1](#0-0) 

The worker's own `Command` documentation explicitly states that pausing (as opposed to resetting) can leak buffered frames into the next playing state: [2](#0-1) 

Separately, `Sensor::Command::Reset` is documented as the mechanism that "ensures no stale frames leak into the next capture by fully restarting the internal gstreamer pipeline," implying that absent an explicit `Reset` call, stale frames from a previous capture session can survive into the next one: [3](#0-2) 

This mirrors the DeFi bug's structure precisely: a subsystem computes/holds an intermediate quantity (buffered PSM/WETH balance vs. buffered camera frames), the "happy path" clean-up step (`_addLiquidity` mint vs. `Pause`) does not fully drain/clear that intermediate state, and only an explicit, separately-invoked corrective action (refund vs. `Reset`) removes the residual. If the reset step is skipped, deferred, or raced by the master-plan signup loop, biometric frame data belonging to one signup session (Alice) could be delivered as part of the next signup session's capture stream (Bob), which is a "cross-signup state bleed" impact directly analogous to the attacker in the report capturing Alice's leftover PSM.

### Impact Explanation
If stale RGB frames from one signup are consumed as part of a different signup's biometric capture, this could cause a misattribution of biometric enrollment data between two different signup sessions/users — i.e., data captured for one person's signup ends up being associated with, or influencing, a different person's enrollment. This falls within the accepted "cross-signup state bleed" impact category, since it involves biometric image data crossing an isolation boundary that the `signup_id`-scoped design (see `image_notary::Agent::initialize_signup`, which explicitly resets per-signup state) is meant to enforce: [4](#0-3) 

### Likelihood Explanation
This requires the specific combination of ending a capture without a subsequent explicit `Reset`, and a new capture starting quickly enough that the previously-buffered frame is delivered instead of a freshly captured one — a race/timing-dependent condition, not a directly attacker-triggerable exploit in the way the DeFi PoC is. I could not verify, within the available index, whether `master_plan.rs`/`reset_hardware`/`reset_hardware_except_led` reliably issue `Command::Reset` on every signup boundary before the next `Start`; confirming this requires reading the full call sequence in `src/plans/mod.rs` around `reset_hardware_except_led`, which was only partially covered by search results.

### Recommendation
Ensure the RGB (and any other frame-buffering) camera pipeline is unconditionally reset (not merely paused) between signup sessions, and add an explicit guard/assertion that no frame with a timestamp older than the current session's start is ever forwarded to `image_notary`/biometric capture consumers. Tie this to `signup_id` so any frame received outside its owning session is rejected rather than silently accepted.

### Proof of Concept
Not independently verified against live behavior — based on static code/comment evidence only:
1. Signup A starts biometric capture; RGB camera `Start` → `capture()` loop buffers/produces frames.
2. Signup A's capture ends; manager sends `worker::Command::Pause` (not `Reset`) per `src/agents/camera/rgb/mod.rs:229`.
3. Master plan transitions to idle/next signup without guaranteeing a `Command::Reset` is issued before the next `Start`.
4. Signup B's biometric capture begins; per the documented behavior in `worker.rs:75-77` and `mod.rs:80-82`, stale frames buffered during Signup A's session can be delivered as Signup B's first frames, mixing biometric data across signups. [5](#0-4)

    async fn run(mut self) -> Result<()> {
        while let Some(command) = self.port.next().await {
            match command.value {
                Command::Fisheye { fisheye_config: new_fisheye_config, undistortion_enabled } => {
                    self.fisheye_config = undistortion_enabled.then_some(new_fisheye_config);
                    self.fisheye_sent = false;
                }
                Command::Start { fps } => {
                    if let Some(state_tx) = &mut self.state_tx {
                        state_tx.send_now(super::State::Capturing)?;
                    }
                    let mut retry = true;
                    while retry {
                        (self, retry) = self.capture(fps).await?;
                    }
                    if let Some(state_tx) = &mut self.state_tx {
                        state_tx.send_now(super::State::Idle)?;
                    }
                }
                Command::Reset => {
                    (self, _) = self.worker_send_or_restart(worker::Command::Reset).await?;
                }
                Command::Stop => bail!("rgb camera already stopped"),
            }
        }
        Ok(())
    }
