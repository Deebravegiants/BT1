### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from the raw body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used to route and identify the webhook come from unauthenticated HTTP headers. `HmacValidator` only proves the body was signed by Shopify — it proves nothing about which shop the header claims the webhook is for. An attacker who legitimately receives one valid webhook (e.g., by installing the target app on their own store) can replay that exact body+HMAC pair while substituting an arbitrary victim `x-shopify-shop-domain` header, and the registry will process it as if it came from the victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from caller-supplied headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (the raw body) and compares it to the received `hmac`: [3](#0-2) 

`Registry.process` checks only that HMAC validity, then immediately trusts `request.shop` (and `request.topic`) as the authenticated tenant identity when constructing the payload handed to the app's webhook handler: [4](#0-3) 

The identity binding that should hold is: `hmac-authenticated bytes == bytes that determine the shop the webhook is attributed to`. Because the header-derived `shop` is outside the signed content, this equality breaks — the body's signature says "Shopify sent this body," but the header's `shop` value is attacker-controlled and unverified.

### Impact Explanation
This crosses a tenant boundary: any user who can install the app on a shop they control (an ordinary, unprivileged action available to any merchant) receives legitimate webhook deliveries with valid HMACs for that shop. Because the HMAC never binds to the shop identity, that same body+HMAC pair remains valid when replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop. The app's webhook handler (e.g., handling `app/uninstalled`, `shop/redact`, or order/product topics) then executes shop-scoped side effects (deleting sessions, revoking access, mutating data) attributed to the victim shop, which the attacker does not control and has no credentials for. This is a cross-tenant impact reachable by an unauthenticated/unprivileged internet actor with no access token, `client_secret`, or credential of the victim.

### Likelihood Explanation
The attacker only needs: (1) the ability to install the target public/free app on a store they control (trivial, no special privilege), and (2) network access to POST to the app's public webhook endpoint (which is inherently internet-facing). No secret material or privileged account is required to forge the victim's shop attribution — only replay of a previously legitimate body/HMAC pair with a modified header.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the HMAC-verified content, or otherwise verify the header-derived shop against an independent authenticated source before dispatching to handlers. At minimum, `to_signable_string` (or an additional check in `Registry.process`) should incorporate the `shop`, `topic`, and `webhook_id` header values so that tampering with those headers invalidates the HMAC, closing the gap between "bytes verified" and "identity acted upon."

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a shop they own) and triggers a webhook topic the app subscribes to (e.g., `products/update`).
2. Attacker captures the resulting webhook POST: raw body `B`, and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`), along with `x-shopify-topic`, `x-shopify-webhook-id`.
3. Attacker resends the identical POST body `B` and `x-shopify-hmac-sha256: H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds (it only checks `B` against `H`), and `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"`, causing the app to perform shop-scoped actions against a shop the attacker never installed on or authenticated with.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
