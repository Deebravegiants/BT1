### Title
Unrestricted stateless-op calls in `EmporiumUpgradeable.runAction` allow theft of any residual/stranded token balance outside the declared token accounting - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `EmporiumStack.signerAddress == address(0)`, `EmporiumUpgradeable.runAction` executes attacker-supplied `op.endpoint.call(op.callData)` from the Emporium contract's own context with no restriction other than blocking the two wallet selectors. Because the post-call balance reconciliation only iterates over the caller-chosen `circomData.erc20TokenAddresses` array, an attacker can craft an op that transfers any ERC20 balance the Emporium contract holds (e.g. stranded/refunded surplus from a prior transaction's router call) directly to their own address by simply omitting that token from `erc20TokenAddresses`, completely bypassing the `-deltaAmountChanges` accounting invariant.

### Finding Description
The invariant that should hold for every transaction is:

`tokens leaving the Emporium action in this tx == -deltaAmountChanges Hinkal sent it in this tx` (as enforced, for *declared* tokens, by the loop at [1](#0-0) ).

This invariant is only checked for indices `i` present in `circomData.erc20TokenAddresses`. In the stateless branch (`stack.signerAddress == address(0)`), `op.endpoint` and `op.callData` are fully attacker-controlled and unrestricted beyond blocking `callHinkalWallet`/`doSendToRelay` selectors: [2](#0-1) 

Because `stack` comes from `abi.decode(circomData.externalActionData.externalActionMetadata, (EmporiumStack))` (line 80-83) and this metadata field is not constrained by the ZK circuit (only `erc20TokenAddresses`, `amountChanges`, and the nullifier/commitment set are circuit public inputs used in `Hinkal.transact`'s balance checks), an attacker can submit a normal, self-consistent proof for their own trivial UTXO operation (e.g. depositing/withdrawing 1 wei of a throwaway token, satisfying `inTotal + amountChanges === outTotal` in the circuit) while attaching an `EmporiumStack` whose `ops[]` contains a call directly to any token contract that the Emporium proxy happens to be currently holding a balance of (e.g. `Token.transfer(attacker, strandedAmount)`), where that token address is **not included** in `circomData.erc20TokenAddresses` for this transaction.

Since the runAction balance-reconciliation loop (lines 132-151) only computes `balanceChange` for indices in the declared `erc20TokenAddresses` array, and the direct `transfer` happens on a token that was never declared, this theft is invisible to both:
- The internal `BalanceChangeShouldBePositive` check (line 142), which never runs for the undeclared token.
- Hinkal's outer balance/slippage/equality checks in `Hinkal.transact` (lines 97-147), which likewise only iterate `circomData.erc20TokenAddresses`.

The stranded balance itself is plausible: `handleOut` (lines 162-184) and the compensation formula at lines 136-139 only capture the *net delta* of declared tokens produced by ops during a *given* transaction; router refunds, partial fills, or bonus/positive-slippage transfers of tokens not anticipated/declared by the originating transaction's `erc20TokenAddresses` list remain permanently parked in the Emporium contract's balance, since nothing ever sweeps or accounts for them. A later, unrelated, unprivileged transaction can then target that specific token via a crafted op and pull it straight to the attacker's EOA, with `deltaAmountChanges` for that token effectively being `0` (it isn't even in the array), while the actual outflow is the full stranded amount — breaking the invariant.

### Impact Explanation
Direct theft of shielded/in-flight protocol-held funds: any ERC20 balance sitting in the `EmporiumUpgradeable` proxy that is not part of the attacker's declared token list can be drained to the attacker's own address via an unrestricted stateless op call, with the transfer entirely untracked by Hinkal's UTXO/nullifier/balance-diff invariants. This matches Critical severity ("direct theft of shielded or in-flight user funds"). The attack is repeatable for every distinct residual/stranded balance that accumulates in the contract over time (e.g., from refunds, dust, positive-slippage router bonuses on tokens not declared by the originating tx).

### Likelihood Explanation
Preconditions: (1) some non-zero ERC20 balance must be present/stranded in the `EmporiumUpgradeable` contract for a token not tracked by the transaction that stranded it (a plausible and likely occurrence with router refunds / partial fills / bonus outputs on multi-hop swaps); (2) attacker must submit a valid Hinkal proof for their own trivial UTXO operation, which any unprivileged user can generate for themselves. No signature, wallet ownership, or privileged role is required because `stack.signerAddress == address(0)` selects the stateless path (Case 2), which imposes essentially no restriction on `op.endpoint`/`op.callData`. Cost to the attacker is minimal (gas plus a trivial self-contained deposit/withdraw to obtain a valid proof); the exploit is directly reproducible whenever a stranded balance exists, and repeatable indefinitely as more residual balances accumulate.

### Recommendation
- Require that every ERC20 token address touched by any `op.endpoint.call` (or at minimum, restrict `op.endpoint` to a router/DEX allowlist) is included in `circomData.erc20TokenAddresses`, so its balance is always reconciled against `deltaAmountChanges`.
- Alternatively, sweep/measure balances of ALL tokens the contract could plausibly hold (or maintain an explicit ledger of "swept" balances) rather than relying solely on the caller-supplied `erc20TokenAddresses` array to determine which balances are audited.
- For the stateless path (`signerAddress == address(0)`), disallow arbitrary `op.endpoint` targets entirely, or require them to be pre-approved routers with call-data validated to only invoke swap/approve functions, never raw token transfers to arbitrary recipients.
- Ensure any token balance change caused by `ops` execution is fully captured within the same transaction's declared token set, eliminating the possibility of stranded/undeclared residuals.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (as an allowed recipient), a mock ERC20 `TokenA`.
2. Simulate a "stranding" event: directly mint/transfer `TokenA` tokens to the `EmporiumUpgradeable` proxy address (representing a router refund/dust from a prior, unrelated transaction) — record `strandedBalance = TokenA.balanceOf(emporium)`.
3. As an unprivileged attacker, generate a valid Hinkal proof for a trivial self-contained operation using an unrelated `TokenB` (e.g., depositing 1 wei of `TokenB`, `amountChanges` and `erc20TokenAddresses` referencing only `TokenB`).
4. Craft `externalActionMetadata` decoding to an `EmporiumStack` with `signerAddress = address(0)` and `ops = [{ endpoint: TokenA, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, strandedBalance)) }]`.
5. Call `Hinkal.transact` with this proof/circomData.
6. Assert: `TokenA.balanceOf(attacker) == strandedBalance` after the call, `TokenA.balanceOf(emporium) == 0`, while `circomData.erc20TokenAddresses` never referenced `TokenA` and no `deltaAmountChanges` entry accounted for the `strandedBalance` outflow — demonstrating the invariant `tokens leaving the action == -deltaAmountChanges Hinkal sent it` is violated for `TokenA`.
