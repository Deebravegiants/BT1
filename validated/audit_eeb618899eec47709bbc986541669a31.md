Audit Report

## Title
Trusting unchecked ERC20 `transfer()` return values in `ERC20Transactor` causes phantom asset accounting - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `deposit_asset_with_surplus` credit/permit XCM `AssetsInHolding` amounts based solely on the decoded boolean return value of an ERC20 `transfer()` call, never verifying the actual `balanceOf` delta of the `TransfersCheckingAccount` (or beneficiary). Any ERC20 with non-standard transfer semantics (fee-on-transfer, rebasing, deflationary, or a token that simply lies in its return value) will desynchronize the runtime's internal `Erc20Credit` accounting from the real on-chain balance of the checking account.

## Finding Description
On withdraw, `ERC20Transactor::withdraw_asset_with_surplus` calls `transfer(checking_address, amount)` and, upon `Ok(true)` from `abi_decode_returns_validate`, mints `AssetsInHolding::new_from_fungible_credit(..., Box::new(Erc20Credit(amount)))` for the full requested `amount` [1](#0-0) . On deposit, `deposit_asset_with_surplus` performs the mirrored `transfer(beneficiary, amount)` from the checking account and returns success purely on `Ok(true)` [2](#0-1) . Neither path reads `balanceOf` before/after the call, so there is no verification that the checking account's or beneficiary's real token balance changed by the reported `amount`. The `Erc20Credit` type's own doc comment confirms this design intentionally defers balance enforcement to the ERC20 contract itself rather than the runtime [3](#0-2) . This transactor is wired into Asset Hub Westend's `AssetTransactors` tuple, so it is reachable by any XCM program referencing an ERC20 contract's `AccountKey20` location [4](#0-3) .

## Impact Explanation
For a non-conforming ERC20 (fee-on-transfer, rebasing, or one that returns `true` without moving the full amount), the internal `Erc20Credit` ledger will diverge from the checking account's real balance over repeated withdraw/deposit cycles. This can lead to later legitimate `deposit_asset_with_surplus` calls failing once the checking account's real balance is exhausted relative to outstanding phantom credits, or an early withdrawer capturing more value than deposited, at later users' expense. The blast radius is scoped to the specific ERC20's `TransfersCheckingAccount` solvency, not to shared `pallet-asset-conversion` pools (no bridge between `Erc20Credit` and those pools was found).

## Likelihood Explanation
Exploitation requires only that a non-standard/malicious ERC20 be referenced via XCM's `AccountKey20` location — no governance, privileged origin, or special registration step is needed, since `ERC20Matcher` matches any deployed ERC20 by address. Fee-on-transfer and rebasing tokens are common in real-world ERC20 deployments, making the precondition realistic rather than purely theoretical.

## Recommendation
Read `balanceOf` of the `TransfersCheckingAccount` (and the beneficiary, for deposits) immediately before and after the `transfer()` call, and use the observed delta — not the trusted boolean return value — to determine the `AssetsInHolding` credit/debit amount, mirroring the balance-delta check already used in `substrate/frame/asset-conversion/precompiles/src/tests.rs`.

## Proof of Concept
1. Deploy an ERC20 via `pallet-revive` whose `transfer()` always returns `true` but delivers less than `value` to the recipient (fee-on-transfer).
2. Submit an XCM `WithdrawAsset` for amount `N` referencing this token's `AccountKey20` location; `withdraw_asset_with_surplus` credits `AssetsInHolding` with the full `N` even though the checking account's real balance only increased by `N - fee`.
3. Repeat withdraw/deposit cycles until the checking account's real balance is less than the sum of outstanding phantom credits; subsequent `deposit_asset_with_surplus` calls begin failing (DoS) or an attacker who withdraws first captures a disproportionate share of the account's real balance.
