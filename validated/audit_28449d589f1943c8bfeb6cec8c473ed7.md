### Title
Path traversal via unsanitized `prefix` in `FilesystemStorage.namespace()` allows escaping the intended root directory - ([File: adapters/storage-mobile/src/helpers/with-filesystem-fallback.ts])

### Finding Description
`FilesystemStorage.namespace()` builds the new instance's root directory by naive string concatenation with no validation of `prefix`: [1](#0-0) 

This differs from `StorageMobile#namespace`, which at least calls `assertValidIdentifier(prefix)` before composing the key prefix: [2](#0-1) 

However, `assertValidIdentifier` itself only rejects the `!` character and does nothing about `/` or `..`: [3](#0-2) 

The public `withFilesystemFallback(...).namespace(prefix)` wrapper likewise concatenates `prefix` unsanitized into `rootDir` before constructing the nested `FilesystemStorage`: [4](#0-3) 

Once a `FilesystemStorage` is rooted at an attacker-influenced path (e.g. `${rootDir}/../otherNamespace`), individual key writes still go through `asFilesystemKey`, which hashes the key and validates the hashed output with a safe-character regex: [5](#0-4) [6](#0-5) 

That per-key validation only protects the *filename* component, not the *directory* component (`this.rootDir`), which is exactly what `namespace()` controls. So if `prefix` contains `../`, the entire namespace's storage directory can be redirected outside the intended sandbox, and every subsequent `set`/`get`/`delete`/`clear` call for that namespace operates against the attacker-chosen directory instead of the isolated one.

### Impact Explanation
If a caller passes an attacker-influenced identifier (e.g., dapp origin, imported account id, deeplink parameter) directly into `.namespace()` without prior sanitization, the resulting `FilesystemStorage` root can be pointed at a sibling namespace's directory (or any directory reachable via relative traversal from `rootDir`). This could allow cross-namespace data corruption/disclosure — e.g., an origin-scoped namespace colliding with or overwriting a different namespace's directory. This matches "wrong-account/origin storage isolation break" style impact, contingent on a concrete unsanitized call site.

### Likelihood Explanation
This is a **conditional/latent** vulnerability: the root cause (missing `/`/`..` validation) is confirmed in code for both `FilesystemStorage.namespace` and `assertValidIdentifier`. However, I could not confirm within the available context an actual production call site where a fully attacker-controlled string (dapp origin, deeplink value, etc.) is passed directly and unsanitized into `.namespace()`. The `namespace()` calls found in the codebase (`features/wallet`, `features/blockchain-metadata`, `features/address-provider`, `features/connected-origins`, etc.) generally use internally-defined identifiers (asset names, wallet account keys) rather than raw external input, but I was not able to fully trace every call site (e.g., `features/connected-origins`) to rule out an origin string reaching this function unsanitized, due to tool-call budget limits. This is a real gap in defense-in-depth even if no exploitable call site was confirmed.

### Recommendation
Add identifier validation to `FilesystemStorage.namespace()` (and reuse/extend `assertValidIdentifier` to reject `/`, `\`, and `..` sequences, not just `!`), consistent with `StorageMobile#namespace`, before concatenating `prefix` into `rootDir`. Apply the same validation in the public `withFilesystemFallback(...).namespace()` wrapper.

### Proof of Concept
```ts
// adapters/storage-mobile/test/with-filesystem-fallback.namespace.spec.ts
it('should not allow prefix to escape rootDir via path traversal', () => {
  const fakeFs = { mkdirp: jest.fn(), readUtf8: jest.fn(), writeUtf8: jest.fn(), rimraf: jest.fn() }
  const storage = withFilesystemFallback({
    filesystem: fakeFs,
    hashString: (s) => s,
    rootDir: '/data/app/namespaceA',
    storage: mockStorage, // StorageMobile-like with .namespace()
  })

  const escaped = storage.namespace('../namespaceB')
  // Assert internal rootDir used for filesystem writes does not resolve outside
  // '/data/app/namespaceA', e.g. by inspecting fakeFs.mkdirp call args
  expect(fakeFs.mkdirp).not.toHaveBeenCalledWith(
    expect.stringMatching(/^(?!\/data\/app\/namespaceA\/).*$/)
  )
})
```
Expected (current, vulnerable) behavior: `fakeFs.mkdirp` is called with `/data/app/namespaceB`, outside the intended `namespaceA` root — demonstrating the traversal. After the fix, `namespace('../namespaceB')` should throw.
