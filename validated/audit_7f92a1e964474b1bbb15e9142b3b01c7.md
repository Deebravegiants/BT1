### Title
`VersionedNonceBuilder.encodeNonce` silently wraps u64 deadline on far-future dates, causing `IntentsSDK.invalidateNonces` to sign an already-expired cancellation intent - ([File: packages/intents-sdk/src/intents/expirable-nonce.ts])

### Summary
`encodeNonce` computes `deadlineBigInt = BigInt(deadline.getTime()) * 1_000_000n` and writes it into a fixed 8-byte (u64) field with `DataView.setBigUint64`, which does not throw on overflow — it silently reduces the value modulo 2^64. Any valid JS `Date` whose millisecond value exceeds roughly `18,446,744,073,709` ms (≈ year 2554, far short of the JS `Date` ceiling of year ~275760) produces a wrapped, effectively unrelated deadline once decoded, which can land in the past relative to "now".

### Finding Description
The claimed equality is: `decodeNonce(encodeNonce(salt, deadline)).inner.deadline / 1e6 === deadline.getTime()`. This holds for ordinary near-term deadlines but breaks for any deadline whose nanosecond representation exceeds `2^64 - 1`: [1](#0-0) 

`setBigUint64` per spec reduces the BigInt modulo 2^64 instead of throwing, so `encodeNonce` never validates or rejects out-of-range deadlines — there is no bounds check on `deadline` anywhere in the function.

This is directly reachable because `VersionedNonceBuilder` is a public, exported API documented for external callers to construct nonces themselves: [2](#0-1) 

and the README explicitly instructs callers to pick their own `deadline` for this builder: [3](#0-2) 

A "far future / never expire" sentinel date (e.g. year 9999, a common convention, or any date past ~year 2554) is a perfectly valid `Date` object but overflows the u64 field once multiplied by `1_000_000n`. The wrapped result is deterministic but semantically arbitrary relative to the caller's intent, and can decode to a timestamp earlier than "now".

Downstream, `IntentsSDK.invalidateNonces` trusts this decoded value to cap the invalidation intent's deadline: [4](#0-3) 

If the wrapped `nonceDeadline` is earlier than `now`, `min(oneMinuteFromNow, nonceDeadline)` picks the past `nonceDeadline`, and `builder.setDeadline(...)` accepts it unchecked — `IntentPayloadBuilder.setDeadline` performs no validation: [5](#0-4) 

The SDK proceeds to sign and locally believe the invalidation succeeded (no error is thrown), producing a signed empty intent whose own `deadline` field is already in the past. Once submitted, the intents.near contract's ordinary deadline enforcement will reject this cancellation intent as expired, so the nonce is never actually marked used on-chain. Meanwhile the original payload tied to that nonce (whose own separate `deadline` field is set independently and is not affected by this overflow) remains valid and executable, because the contract's replay check only cares about the literal, unaffected nonce bytes actually embedded in the originally-signed payload — not the metadata deadline extracted here.

Since `nonce` is an explicitly attacker-controlled field forwarded from a counterparty into the SDK (per the threat model), a counterparty could hand an integrator a nonce deliberately encoded with a far-future sentinel deadline, so that when the integrator calls `sdk.invalidateNonces` believing they are safely cancelling it, the operation silently no-ops.

### Impact Explanation
The integrator's application locally believes a signed payload/authorization has been invalidated (no thrown error, matching the existing test pattern for expirable nonces), but the on-chain cancellation never lands because its own deadline is already expired. The original signed intent, whose real nonce bytes and real deadline are untouched by this bug, remains executable and can later move the caller's funds without further authorization — matching the Critical category ("intent manipulation moving funds the user did not authorise"). This is repeatable for any nonce encoded with a deadline beyond ~year 2554.

### Likelihood Explanation
No special privileges are required — only calling the exported `VersionedNonceBuilder.encodeNonce` with an out-of-range `Date`, something plausible via a common "never expire" sentinel convention (e.g., year 9999) rather than an obscure `Number.MAX_SAFE_INTEGER` edge case. `encodeNonce` performs no bounds validation, `decodeNonce`/`saltedNonceSchema` accept the wrapped value without complaint, and `invalidateNonces`/`setDeadline` never sanity-check that the resulting deadline is in the future. The bug is fully deterministic and reproducible offline.

### Recommendation
In `encodeNonce`, validate that `deadlineBigInt` fits within `[0, 2**64 - 1]` (or more conservatively, bound `deadline` to a sane maximum, e.g. a few years out) and throw instead of silently wrapping. Additionally, `invalidateNonces` should sanity-check the decoded `nonceDeadline` (reject/ignore it if it is not sensibly in the future, e.g. `nonceDeadline < new Date()`) rather than blindly trusting decoded nonce metadata, and `IntentPayloadBuilder.setDeadline`/`buildWithSalt` should reject deadlines that are already in the past.

### Proof of Concept
```ts
import { describe, it, expect } from "vitest";
import * as v from "valibot";
import {
  VersionedNonceBuilder,
  saltedNonceSchema,
} from "./expirable-nonce";

describe("encodeNonce u64 overflow", () => {
  it("far-future deadline wraps and round-trip mismatches", () => {
    const salt = Uint8Array.from([1, 2, 3, 4]);
    // valid JS Date, common "never expire" sentinel, still far below Date's year ~275760 ceiling
    const deadline = new Date(Date.UTC(9999, 11, 31));

    const encoded = VersionedNonceBuilder.encodeNonce(salt, deadline);
    const decoded = VersionedNonceBuilder.decodeNonce(encoded);
    const value = v.parse(saltedNonceSchema, decoded.value);
    const decodedMs = Number(value.inner.deadline / 1_000_000n);

    // Equality claimed by the round trip is broken:
    expect(decodedMs).not.toBe(deadline.getTime());
  });
});

### Versioned Nonce Builder

By default, the nonce is generated during the intent construction process, but it is possible to generate and pass the nonce within the builder independently. All of the nonces have specific [requirements](https://github.com/near/intents/tree/main/defuse#nonces) for the structure reflecting their validity.

```typescript
import {VersionedNonceBuilder} from '@defuse-protocol/intents-sdk';

// Fetch current salt from the verifier contract
const salt_hex = await nearRPC.viewFunction({
  contractId: "intents.near",
  methodName: "current_salt",
});

// Example: 5-minute deadline, but actual deadline should not be greater than intent's deadline
const deadline = new Date(Date.now() + 5 * 60 * 1000)

// Create ready to use versioned nonce from salt and deadline
const versionedNonce = VersionedNonceBuilder.encodeNonce(
  Uint8Array.from(Buffer.from(salt_hex, "hex")),
  deadline
);

// Create intent builder with specified nonce
const builder = await sdk.intentBuilder().setNonce(versionedNonce);
