### Title
Missing `__gap` storage-reservation in `IntentsBase`/`IntrinsicIntents`/`ExtrinsicIntents` risks corrupting hardcoded escrow storage slots on future governance upgrades - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2` is deployed behind an `ERC1967Proxy` and is upgraded exclusively through a cross-chain governance path (`onAccept` → `RequestKind.Execute`/`UpgradeContract` → `ERC1967Utils.upgradeToAndCall`). [1](#0-0)  Its concrete storage lives in the diamond `IntentsBase → {IntrinsicIntents, ExtrinsicIntents} → IntentGatewayV2`. [2](#0-1)  Unlike `SimplexPaymaster`, which explicitly reserves `uint256[48] private __gap;` after its own state, [3](#0-2)  none of `IntentsBase`, `IntrinsicIntents`, or `ExtrinsicIntents` declare a storage gap. [4](#0-3) 

### Finding Description
`IntentsBase` holds all of the gateway's escrow-critical state: `_filled`, `_nonce`, `_params`, `_orders`, `_instances`, `_partialFills`, `_destinationProtocolFees`, `_paused`, `_relayer`. [4](#0-3)  The codebase's own history shows this layout is append-only by convention and manually tracked: `_paused` was "Appended last to preserve existing storage slots" and `_relayer` was placed "after `_paused`" specifically because inserting a field earlier (e.g. into the `Params` struct) "would push every mapping behind it and corrupt escrow on the live proxy." [5](#0-4) 

Critically, `_filled`'s slot is not just implicit—it is hardcoded as a protocol constant, `FILLED_SLOT_BIG_ENDIAN_BYTES = 0x...02`, used to build cross-chain storage proof keys for cancel verification. [6](#0-5)  Off-chain SDK/indexer code and tests independently hardcode `mappingSlot = 2` to read `_filled` via `eth_getStorageAt` for order-status checks. [7](#0-6) 

Because there is no `__gap` reserved in `IntentsBase` (or in the intermediate abstract contracts `IntrinsicIntents`/`ExtrinsicIntents`, which currently declare zero state variables of their own), any future implementation shipped through the live `UpgradeContract`/`Execute` governance path that adds a new state variable to `IntentsBase` — the natural place to add shared gateway state — has no structural protection against being inserted in the wrong position or against colliding with additional variables a maintainer might add to the abstract subclasses in between. Since Solidity's storage layout is fixed by C3-linearization order at compile time (`IntentsBase` → `IntrinsicIntents`/`ExtrinsicIntents` → `IntentGatewayV2`), correctness today depends entirely on the discipline of manually appending new fields at the exact end of `IntentsBase`, as the changelog for `_paused`/`_relayer` documents was already required once. A `__gap` array converts this fragile manual discipline into a structural guarantee (per the OpenZeppelin upgradeable-contracts pattern the project already applies in `SimplexPaymaster`).

### Impact Explanation
If a future governance-approved implementation (delivered via the exact same `onAccept`/`Execute` delegatecall to `ERC1967Utils.upgradeToAndCall` that already exists in production) shifts the slot of `_filled`, `_orders`, `_nonce`, or `_relayer` — e.g., by adding a new field to `IntentsBase` without extending it at the true tail, or by adding state to `IntrinsicIntents`/`ExtrinsicIntents` — the consequences are severe and match the "unsound state commitment" / "permanent freezing of funds" criteria:
- The hardcoded `FILLED_SLOT_BIG_ENDIAN_BYTES` proof key used for cross-chain cancel verification would silently point at the wrong storage word, breaking or forging fill/refund verification for escrowed orders.
- Existing escrow accounting (`_orders`, `_filled`, `_nonce`) could be corrupted/misread across the entire proxy fleet in one upgrade transaction, since `IntentGatewayV2` is deployed via `ERC1967Proxy` on multiple chains and the same implementation is pushed to every deployment.
- `_relayer`, which gates all `onAccept`/`onGetResponse` deliveries, could be misread, potentially reopening the relayer allowlist or bricking legitimate delivery.

### Likelihood Explanation
Medium. This is not a bug triggerable in the current bytecode by an external attacker with a single transaction; it requires a future code change. However, likelihood is non-trivial because: (1) the project already had to correct storage-layout risk twice by hand (`_paused`, then `_relayer`) precisely because there is no gap, showing this is a live maintenance hazard, not a hypothetical; (2) the upgrade path is real, governance-controlled, and already exercised in tests/deploy scripts (`DeployIntentGateway.s.sol`, `IntentGatewayV2Test.sol`); (3) `SimplexPaymaster` in the very same repo demonstrates the team is aware of and applies the `__gap` pattern elsewhere, but omitted it for the more storage-sensitive `IntentGatewayV2` diamond.

### Recommendation
Add an explicit `uint256[N] private __gap;` as the final declaration in `IntentsBase` (sized to round the total up to a fixed slot budget, e.g. 50), and consider adding empty gaps to `IntrinsicIntents`/`ExtrinsicIntents` as well if they are expected to ever hold their own state. Document the reserved budget and require future additions to consume the gap rather than being appended ad hoc, consistent with the pattern already used in `evm/src/utils/SimplexPaymaster.sol`.

### Proof of Concept
Not applicable as a live exploit — this is a defense-in-depth/structural gap, not a directly triggerable bug in the current bytecode. The concrete risk is demonstrated by the project's own precedent: `_relayer` had to be manually placed "after `_paused`" specifically because inserting it elsewhere "would push every mapping behind it and corrupt escrow on the live proxy," [5](#0-4)  and the same layout is separately hardcoded off-chain (`mappingSlot = 2`) for `_filled` in `OrderStatusChecker.ts` and test helpers, [7](#0-6)  confirming that any accidental slot shift in a future upgrade delivered through the live `onAccept`/`Execute`→`upgradeToAndCall` path [1](#0-0)  would corrupt escrow accounting and break cross-chain proof verification across every deployed proxy.

# 2026-09-03 — The relayer is a separate storage variable, not a `Params` field

Chosen: `address _relayer` appended after `_paused` in `IntentsBase`, set through its own
`setRelayer` call.

`Params` occupies slots 4 to 8 and `_orders` starts at slot 9. Adding a field to the struct would
push every mapping behind it and corrupt escrow on the live proxy. Reusing `UpdateParams` was
therefore never available, quite apart from it being a Hyperbridge-relayed message: the whole point
is to hold even if Hyperbridge's consensus is compromised, so the setter must not depend on it.
