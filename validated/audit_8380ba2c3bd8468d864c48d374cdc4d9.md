Based on my review, I found a legitimate analog in `WrappedHyperFungibleToken.sol` (and its identical upgradeable counterpart). Here is the analysis.

### Title
`WrappedHyperFungibleToken.send()` trusts the requested `params.amount` instead of the actual transferred balance, causing accounting mismatch for non-standard ERC20 underlying tokens - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken` locks an underlying ERC20 on the source chain and instructs the destination chain to unlock/mint the exact same `params.amount`, without ever measuring how much of the underlying token it actually received via `safeTransferFrom`.

### Finding Description
In `send()`, the ERC20 lock path does: [1](#0-0) 

The contract calls `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` and then unconditionally builds the cross-chain `Message` with `amount: params.amount` (via `_buildDispatchPost`), regardless of how many tokens the wrapper actually received. Compare this to `IntentGatewayV2`, which explicitly snapshots balances before/after a transfer and uses the observed delta as the accounted amount: [2](#0-1) 

`WrappedHyperFungibleToken` has no equivalent before/after balance check. If the configured `underlying` token has fee-on-transfer, deflationary, or rebasing behavior (any ERC20 where `balanceOf` delta after `transferFrom` differs from the nominal transfer amount), the wrapper locks strictly less than `params.amount` but still dispatches a message committing to mint/unlock the full `params.amount` on the destination chain via `onAccept`: [3](#0-2) 

This is the same root-cause class as the reported issue: the contract's balance/amount bookkeeping is decoupled from the token's actual transfer semantics, producing systemic accounting drift over the custody pool.

### Impact Explanation
Each `send()` call on such a token creates a shortfall between the underlying locked in the wrapper and the liability represented by outstanding cross-chain messages/minted representations. Over repeated transfers this shortfall compounds, so that when honest users on other chains attempt to bridge back (`onAccept` calls `IERC20(_underlying).safeTransfer(beneficiary, message.amount)`), the wrapper's custody balance becomes insufficient to honor legitimate unlock/refund requests, permanently freezing funds for other users of the same wrapper deployment. Since a single wrapper instance is meant to service all users of that token pair, this is a protocol-wide (not attacker-isolated) shortfall.

### Likelihood Explanation
Triggering this requires only that the wrapper's `underlying` be configured as a token with non-1:1 transfer semantics (fee-on-transfer, deflationary burn-on-transfer, or rebasing tokens), which is a legitimate, non-privileged configuration decision made once at deployment via `configure()`, not an admin acting maliciously. Any regular user calling `send()` afterward triggers the mismatch — no special permissions or contrived conditions are needed beyond the token choice.

### Recommendation
Measure the actual amount received by snapshotting `IERC20(_underlying).balanceOf(address(this))` before and after the `safeTransferFrom` call in `send()`, and use that delta (not `params.amount`) both for the dispatched `Message.amount` and for any fee/relayer accounting, mirroring the pattern already used in `IntentGatewayV2`.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` and calls `configure()` with `underlying` set to a fee-on-transfer ERC20 (e.g., 2% fee token) and `isWeth = false`.
2. User A calls `send({ amount: 100, ... })`. `safeTransferFrom` pulls 100 nominal units but the wrapper's balance only increases by 98 (2 lost to fee).
3. The dispatched cross-chain `Message.amount` is still `100`; the destination chain HFT mints/unlocks 100 units to the recipient.
4. The wrapper now backs 100 units of destination-side liability with only 98 units of actual underlying custody.
5. Repeat across many `send()` calls; eventually a legitimate `onAccept` (unlock) call reverts or under-pays because `IERC20(_underlying).balanceOf(address(this))` is less than the sum of `message.amount` owed, freezing funds for whichever user's redemption exhausts the shortfall.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
