### Title
Unbounded, spot-price Uniswap V4 pool oracle with an optional deviation guard lets a flash-loan price manipulation drain a Simplex solver's vault on fill - ([File: sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts])

### Summary
Sturdy Finance was drained ~$800k because its `SturdyOracle` derived a collateral price from a manipulable on-chain source (a Balancer pool state) with no defense against a same-block flash-loan price shift. Hyperbridge's Simplex intent-filler has an analogous pattern: when a cross-asset pair has no static curve, `UniswapV4FundingPlanner.getExoticTokenPrice` / `computeDirectPoolPriceUsd` prices the exotic token directly off a Uniswap V4 pool's current `sqrtPriceX96` (a single-block spot read via `getSlot0`), and the only defense — `checkPriceGuard`'s reference-price/deviation band — is explicitly optional configuration.

### Finding Description
`UniswapV4FundingPlanner.computeDirectPoolPriceUsd` computes the USD price of an exotic token as the raw pool mid derived from the pool's `sqrtPriceX96`/tick read via `StateView.getSlot0`: [1](#0-0) 

This value is read fresh every pricing call via `UniswapV4LiquidityState.refresh`, which pulls `getSlot0`/`getLiquidity` straight from the chain with no TWAP or historical averaging: [2](#0-1) 

The flow is documented internally as: `resolveLegRates` → `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd` → `checkPriceGuard`, and the documentation itself states this is a raw pool mid with no size/impact term, and that the guard is "the only defense on this path": [3](#0-2) 

Crucially, `checkPriceGuard` is optional: a chain with no configured `referencePrice`/`maxDeviationBps` prices every quote unguarded, as proven by the filler's own unit tests: [4](#0-3) [5](#0-4) 

Even where a guard is configured, it only checks deviation from a static reference (not execution cost or manipulation resistance), and the docs for the product feature confirm this is "the only defense" and that the two guard fields "must be set together; omit both to leave the chain unguarded": [6](#0-5) 

### Impact Explanation
An attacker with a flash loan can move the spot price of a thin/exotic-token Uniswap V4 pool that a Simplex solver uses as its sole price oracle for an unguarded or wide-banded pair, then place (or induce a placement of) an `IntentGatewayV2` order sized against the manipulated rate within the same block. Because `computeDirectPoolPriceUsd` reads the live tick with no TWAP and `resolveLegRates`/`checkPriceGuard` can be entirely unguarded per-chain, the solver's on-chain `fillOrder` calldata commits to output amounts derived from the manipulated price, causing the solver's escrowed/vault funds to be paid out at a wrong rate — a direct capital loss to the filler analogous to Sturdy's oracle-driven drain, reachable purely from an order placement/fill on the intents path.

### Likelihood Explanation
Likelihood is Medium: it requires (a) an operator to configure a venue-priced pair (no curves) with either no `priceGuard` for that chain or a loose `maxDeviationBps`, and (b) a thin-liquidity pool the attacker can move within a flash-loan-sized single transaction. Since pool pricing is explicitly designed for "exotic" low-liquidity assets (e.g. cNGN) — the exact conditions that make flash-loan manipulation cheap — and the guard is opt-in per chain, misconfiguration or an operator leaving a new chain unguarded is a realistic, low-cost precondition rather than a contrived edge case.

### Recommendation
Make the price guard mandatory (not optional) for any venue-priced pair, source the pool price from a manipulation-resistant TWAP (e.g. Uniswap V4's observation/oracle mechanism) rather than the instantaneous `sqrtPriceX96`, and additionally bound quotes against liquidity depth/impact rather than a static reference alone.

### Proof of Concept
1. Operator configures a `[vault.uniswapV4]` position for a thin exotic/USDC pool without setting `referencePrice`/`maxDeviationBps` (or with a wide band), per `docs/content/developers/evm/simplex/pricing.mdx`.
2. Attacker flash-loans the pool's counter-asset and swaps to push `sqrtPriceX96` far from the true price within one block.
3. Attacker (or a colluding user) places/fills an order against `IntentGatewayV2` sized so that `resolveLegRates`'s `getVenueUsdPrice` reads the manipulated `getSlot0` tick via `UniswapV4FundingPlanner.computeDirectPoolPriceUsd`, and `checkPriceGuard` passes (guard absent or band wide enough).
4. The solver's `fillOrder` calldata commits to an output amount computed off the manipulated rate; escrow/vault funds are released at the bad price in the same block the attacker restores the pool via the flash-loan repay swap, netting profit at the solver's expense — as verified directly by the guard's own unit test showing quotes pass unguarded when no reference is configured (`sdk/packages/simplex/src/tests/strategies/fx.price-guard.test.ts:140-144`).

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

# Venue pricing (Uniswap V4 funded pairs)

Verified 2026-08-19.

```
resolveLegRates(...)
  curveless pair && token0 is a USD stable
    -> venuePriceMemo() -> getVenueUsdPrice(chain, token1)
         -> UniswapV4FundingPlanner.getExoticTokenPrice
              picks the position with the largest pool liquidity
              -> computeDirectPoolPriceUsd -> sdkPool.token0Price / token1Price
    -> checkPriceGuard(...)   reject if outside maxDeviationBps of the static reference
    -> rate = 1 / venueUsd
  otherwise -> the pair's ask/bid curve at the leg's notional
```

`computeDirectPoolPriceUsd` returns the **raw pool mid** derived from `sqrtPriceX96`. The pool's
fee tier is read and stored on the hydrated position (`pos.fee`) but never applied to the price,
and there is no size or impact term — `computeLegPolicyOutput` extends the mid linearly across the
whole priced quantity. `checkPriceGuard` is the only defense on this path, and it checks deviation
from a static reference, not execution cost. A venue-priced pair that has to swap through its own
pool to source inventory pays a fee tier it never quoted against.

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
