### Title
Cross-chain refund on timeout mints/unlocks funds to the address that dispatched `send()`, not a specifiable owner — misdirected to intermediary contracts - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken.send()`, `HyperFungibleTokenUpgradeable.send()`, and `WrappedHyperFungibleToken(Upgradeable).send()` record `msg.sender` as the `Message.from` field at dispatch time [1](#0-0) . If the request times out, a later, permissionless transaction (`onPostRequestTimeout`, invoked by the ISMP host after anyone submits a valid timeout proof) mints/unlocks the refund to whatever address was recorded as `msg.sender` during the original `send()` call, not to a caller-specified beneficiary [2](#0-1) . This mirrors the reported bug class: an address captured as `msg.sender` during one transaction is used, in an unrelated later transaction that any third party can trigger, to force-deliver value — with no parameter to designate a different, safe recipient.

### Finding Description
`SendParams` has no field to specify who should receive a timeout refund; the protocol always derives it from `msg.sender` of the original `send()` call:
- `_buildDispatchPost` embeds `from: abi.encodePacked(msg.sender)` into the dispatched `Message` body [1](#0-0) .
- `send()` burns tokens from `msg.sender` and dispatches the request [3](#0-2) .
- On timeout, `onPostRequestTimeout` decodes `message.from` from the original dispatch body and mints the refund to that address unconditionally [2](#0-1) .

If `send()` is invoked by an intermediary contract on a user's behalf (e.g., a router, paymaster, multicall/batching helper, or any composability contract that pulls the user's tokens and calls `send()` itself so it becomes `msg.sender`), the recorded refund target is the intermediary contract's address, not the end user. Because the timeout callback is triggered later by an unrelated, permissionless transaction (anyone can submit the timeout proof once the timeout window elapses), the refunded tokens land in the intermediary contract's balance. If that intermediary contract has no mechanism to forward/rescue arbitrary token balances (common for ephemeral batching/router contracts, or contracts without owner-sweep functions), the refund is unrecoverable — an exact structural analog of the `DEPLOYER`/`forceSafeTransferETH` misuse in the reference report, where `msg.sender` captured during one call is later used to force-deliver value with no way to redirect it to the intended recipient.

The identical pattern also exists in `HyperFungibleTokenUpgradeable.sol` and in the WETH-wrapping variants `WrappedHyperFungibleToken.sol` / `WrappedHyperFungibleTokenUpgradeable.sol`, where the timeout handler attempts a native ETH push to `refundee` and, only on failure, falls back to an ERC-20 WETH transfer [4](#0-3) ; if the intermediary happens to accept the ETH push (e.g., a payable proxy/multicaller without a sweep function), the funds are similarly stranded there.

### Impact Explanation
Loss of user funds is possible whenever a `send()` call is not made directly by an EOA but routed through an intermediary contract (a realistic and common integration pattern for aggregators, meta-transaction relayers, or DeFi composability wrappers). The refund is forcibly delivered to that intermediary on timeout with no way for the protocol or the original user to redirect it, matching the "High impact" classification of the reference report (permanent loss of escrowed/refunded value to an unintended recipient).

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires `send()` to be called through an intermediary contract that becomes `msg.sender`, and it requires the cross-chain message to subsequently time out (either organically due to relayer inactivity, or because the timeout is short and a relayer chooses/fails to deliver in time — timeout submission is permissionless, so any actor, including one colluding with an MEV/griefing party, can trigger the timeout path once the window has elapsed).

### Recommendation
Add an explicit `refundTo` (or `payer`/`sender`) field to `SendParams`/`Message` that the caller can set independently of `msg.sender`, analogous to how `DispatchPost.payer` is already an explicit, caller-supplied field elsewhere in the codebase [5](#0-4) . Validate that this address is capable of holding the refunded asset, or default to `msg.sender` only when the caller is an EOA, and document that composable/intermediary integrations must explicitly set the refund recipient rather than relying on `msg.sender`.

### Proof of Concept
1. Deploy `HyperFungibleToken` and an intermediary `RouterHelper` contract that: (a) receives the user's tokens via `transferFrom`, (b) calls `HyperFungibleToken.send(params)` itself (becoming `msg.sender`), with a very short `timeout`.
2. `_buildDispatchPost` records `from = abi.encodePacked(address(RouterHelper))` [6](#0-5) ; tokens are burned from `RouterHelper`'s balance.
3. Let the message time out (or have a relayer submit a timeout proof before delivery).
4. The host's `dispatchTimeOut` machinery calls `HyperFungibleToken.onPostRequestTimeout`, which mints the refund to `RouterHelper` [2](#0-1) .
5. If `RouterHelper` has no sweep/rescue function for arbitrary ERC-20 balances, the refunded tokens are permanently stuck, and the original user recovers nothing.

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
