### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw request body only, while the `shop` identity used to route and attribute the webhook payload comes from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header, which is never included in the HMAC-verified bytes. Because the webhook HMAC secret (`api_secret_key`) is shared by the app across *all* installed shops rather than being shop-specific, any user who has installed the app on their own store can capture one of their own legitimately-signed webhook deliveries and replay the identical body/HMAC pair while substituting an arbitrary `shop-domain` header value. `ShopifyAPI::Webhooks::Registry.process` accepts this as valid and hands the attacker-controlled `shop` value straight to the host application's handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read from an unauthenticated header and is completely independent of the signed content: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only recomputes the HMAC over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header, using the app-wide `Context.api_secret_key`: [3](#0-2) 

`Registry.process` trusts the HMAC result as sufficient authorization and forwards `request.shop` — the unverified header — directly into `WebhookMetadata` for the app's handler to act on, with no additional check that the header matches the shop that actually owns the body: [4](#0-3) 

The identity binding that should hold is:
`verified(shop, body) == acted_upon(shop, body)`

What is actually verified is only `HMAC(body)`, while what is acted upon (attributed to a tenant) is `(header_shop, body)`. Since the webhook signing secret is the app's single `client_secret`, not a per-shop secret, any shop that installs the app can obtain a body+HMAC pair that is valid for *any* shop, not just its own. This breaks the tenant-isolation guarantee that webhook data delivered for "shop A" actually originated from shop A.

### Impact Explanation
An unprivileged user who installs the app on a shop they control receives real, correctly-signed webhook deliveries (e.g., `orders/create`, `customers/data_request`, etc.). They can capture the raw body and HMAC from their own webhook, then POST that exact body/HMAC pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a different (victim) shop. `Utils::HmacValidator.validate` will report the request as valid because it only checks the body against the shared secret, and `Registry.process` will invoke the host app's webhook handler with `shop` set to the victim's domain. Any app that keys data storage, order/customer records, or business logic off `WebhookMetadata#shop` (as the gem's own documentation examples do, e.g. storing sessions/records by shop) can have attacker-supplied data injected, corrupted, or misattributed under another merchant's identity — a cross-tenant integrity/isolation violation.

### Likelihood Explanation
Any developer/merchant account is sufficient to obtain one legitimate signed webhook from their own store — no access to `api_secret_key`, access tokens, or other privileged credentials is needed. Forging the additional header on replay requires only basic HTTP tooling. The likelihood is high for any app whose webhook handlers trust the header-derived `shop` value for storage or business logic, which is the pattern encouraged in this gem's own webhook documentation.

### Recommendation
Bind the shop identity into the verified data instead of trusting an unauthenticated header:
- Include the `shop-domain` header (and ideally `topic`/`webhook-id`) in the HMAC-signed content, or
- Cross-check `request.shop` against the shop recorded for that webhook subscription/access token before invoking the handler, or
- Document and require that host applications independently verify `data.shop` against their own installed-shop registry before trusting it, and add this check inside `Registry.process` by default so it isn't opt-in.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook topic the app subscribes to. Capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` (`H` is `HMAC-SHA256(api_secret_key, B)`, which is valid because `api_secret_key` is the same for every install of the app).
2. Send a new request to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256`: `H` (unchanged)
   - `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic`: same topic as captured
3. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `B` against `H`.
4. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` calls the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's own body content, causing the host application to process attacker data under the victim shop's identity.
