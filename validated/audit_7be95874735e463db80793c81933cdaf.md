### Title
Webhook `shop` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, excluding the `shop`-domain header from the HMAC-signed material. `Registry.process` validates the HMAC of the body but then unconditionally trusts `request.shop` (parsed straight from the header) to build the `WebhookMetadata` passed to the app's handler for tenant attribution.

### Finding Description
The identity binding that should hold is: `shop header value == shop that produced/authorized the signed body`. In this gem it does not, because:

- `Request#to_signable_string` returns `@raw_body` only [1](#0-0) .
- `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the signed material [2](#0-1) .
- `HmacValidator.validate_signature` computes the signature solely over `to_signable_string` (the body) [5](#0-4) .
- `Registry.process` raises only if the HMAC over the body is invalid, then immediately passes `request.shop` into `WebhookMetadata` for the handler [4](#0-3) .

Because the shop identifier is never part of the signed content, any request whose body happens to produce a valid HMAC (most directly, one legitimately generated by Shopify for the attacker's own merchant/dev store, since HS256 with the shared `api_secret_key` is fully deterministic on the body) will pass validation with `shop` set to whatever value the header carries. An attacker who controls the delivery of the HTTP request to the app's webhook endpoint (e.g., because they operate their own trial/dev shop with the app installed and can trigger the webhook delivery, or replay/proxy the request) can substitute the `shopify-shop-domain` header for a different tenant's domain while keeping the same signed body, and `Registry.process` will accept it as valid, handing the handler a `WebhookMetadata` claiming to belong to the victim shop.

### Impact Explanation
This breaks the tenant boundary the app relies on webhook processing to preserve. If a host application uses `WebhookMetadata#shop` to select which merchant's records to update (a documented, expected usage pattern), the attacker can inject or overwrite data attributed to a shop they do not control — a cross-tenant access. This matches the Critical impact bucket: cross-tenant access via a spoofable identity field not covered by the cryptographic binding meant to protect it.

### Likelihood Explanation
Exploitation requires only the ability to deliver an HTTP request to the app's webhook endpoint with a body that hashes correctly (trivially available to anyone who can operate their own store on the same app, a scenario open to any unprivileged internet user who installs the app on a free development store) and the ability to set/replay the `shop`-domain header. No access to `api_secret_key`, tokens, or the target merchant's credentials is required.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signed material used by `HmacValidator`, or independently verify that `request.shop` matches an expected/registered shop before invoking handlers. At minimum, document that `request.shop` is unauthenticated and must not be trusted for tenant attribution without separate verification (e.g., cross-checking against a known/installed shop list) in `lib/shopify_api/webhooks/registry.rb` and `lib/shopify_api/webhooks/request.rb`.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) shop `attacker.myshopify.com`.
2. Attacker triggers an event that causes Shopify to deliver a legitimately HMAC-signed webhook to the app's endpoint, e.g. body `{"id":1}` with header `x-shopify-shop-domain: attacker.myshopify.com` and a valid `x-shopify-hmac-sha256` computed by Shopify over that body using the shared `api_secret_key`.
3. Attacker intercepts/replays this request to the app's webhook endpoint but rewrites the header to `x-shopify-shop-domain: victim.myshopify.com`, leaving body and HMAC untouched.
4. `HmacValidator.validate` recomputes the HMAC over the unchanged body and it matches, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: {"id"=>1}, ...)` [6](#0-5) .
5. Any host app logic keyed on `data.shop` now processes attacker-supplied data under the victim shop's tenant context.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
