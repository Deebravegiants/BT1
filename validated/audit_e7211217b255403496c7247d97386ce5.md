### Title
Webhook `shop` (and `topic`, `api-version`, `webhook-id`) header values are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC of the body only, then forwards the unauthenticated `shop` header straight to the app's webhook handler as the tenant identifier. Any actor who can obtain one validly-signed webhook body (trivial for an attacker who installs the app on their own shop) can replay it with an arbitrary `x-shopify-shop-domain` header and have it accepted as coming from a different, victim shop.

### Finding Description
The HMAC binding is: `HMAC_valid == true` should imply "this exact set of claims (topic, shop, body) was produced by Shopify for this specific shop." In this gem, however:

- `to_signable_string` only returns `@raw_body`: [1](#0-0) 
- `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are excluded from the signed payload: [2](#0-1) 
- `Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop`/`request.topic` to build `WebhookMetadata` and dispatch to the app's handler: [3](#0-2) 
- `HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string` (the body) and the shared `api_secret_key`: [4](#0-3) 

Because `api_secret_key` is the same for every shop that installs the app, an attacker who runs the app on their own shop receives genuinely HMAC-valid webhook deliveries for their own body. Since `shop` is not part of the signed bytes, the attacker can strip and replace the `x-shopify-shop-domain` header with any victim shop's domain, and `Utils::HmacValidator.validate` will still return `true`, because it only re-derives the signature from `@raw_body` and the secret — it never binds the signature to the `shop` header. `Registry.process` passes this unauthenticated `shop` value on to the handler as ground truth: [5](#0-4) 

This breaks the identity binding: `shop authenticated by HMAC == shop attributed to the event`. The gem provides no mechanism (e.g., checking `shop` against a registered/known-session shop list) to close this gap, and downstream host apps built on this library's documented `WebhookMetadata` API (`topic`, `shop`, `body`, ...) have no means, using this gem alone, to detect the mismatch.

### Impact Explanation
Any app logic that keys off `WebhookMetadata#shop` (e.g., to look up the merchant's session/access token, update per-tenant state, or trigger merchant-specific side effects) can be made to act on data attributed to an arbitrary victim shop, using only a webhook payload the attacker legitimately received from their own shop. This is a cross-tenant identity confusion vulnerability reachable by any unprivileged internet user who can install the app on a shop they control (which is the normal, unprivileged installation flow for a public Shopify app) — satisfying the Critical "cross-tenant access" impact category.

### Likelihood Explanation
High. No secrets need to be stolen: an attacker only needs to (1) install the target app on their own shop to receive a real, HMAC-valid webhook, and (2) POST that same body to the app's webhook endpoint with a forged `x-shopify-shop-domain` header. The HMAC check in `Utils::HmacValidator` and `Webhooks::Request` performs no validation that ties the signature to the shop header, so the forged request passes verification exactly as the genuine one would.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed payload verification path, or independently verify that the `shop` header corresponds to a shop with a known, previously-established session/installation for this app before dispatching to handlers in `Registry.process`. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must be cross-checked by the host application against its own tenant records before being trusted.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) for their own shop, capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` (computed as `HMAC-SHA256(api_secret_key, B)`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with:
   - Body: same `B`
   - `x-shopify-hmac-sha256`: same `H`
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - `x-shopify-topic`: unchanged
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`) and compares it to `H` — this succeeds because the shop header is not part of the signed bytes: [6](#0-5) 
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `shop` value and dispatches it to the registered handler, which now believes the event legitimately originated from `victim-shop.myshopify.com`: [5](#0-4)
