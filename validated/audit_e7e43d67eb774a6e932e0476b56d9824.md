### Title
Duplicate `erc20TokenAddresses` entries let the same real balance delta/UTXO satisfy two independent balance equations, minting unbacked shielded value - (File: `contracts/Hinkal.sol`, `contracts/HinkalHelper.sol`)

### Summary
`Hinkal.transact` checks the balance equation `balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]` independently for every index `i` of `circomData.erc20TokenAddresses`, and nowhere is uniqueness of the addresses in that array enforced. Because `oldBalances`/`newBalances` are re-read per index and `utxoAmount` re-scans the *entire* `utxoSet` for every index, an attacker who inserts the same token address (e.g. `address(0)`) twice makes one real balance change (and one physical output UTXO produced by `ExternalActionSwap.swap`) satisfy two separate equations, causing two `OnChainCommitment`s (or two independently-proved `amountChanges` legs) to be created from a single real inflow.

### Finding Description
Broken equality: for a single physical ETH inflow `Δ` (the swap output transferred back to Hinkal), the protocol invariant should be
`Σ over unique tokens (real balance change for that token) == Σ (amountChanges/onChainCreation contributions + utxo amounts for that token)`, i.e. one unit of real value backs exactly one unit of accounted shielded value.

The code instead enforces the check per **array index**, not per **unique token**: [1](#0-0) 

- `oldBalances`/`newBalances` come from `getBalancesForArray(circomData.erc20TokenAddresses)`, which simply calls `getERC20OrETHBalance` once per array slot; duplicate addresses just re-read the same balance twice, giving identical values at both indices.
- For `address(0)`, `balanceDif = newBalances[i] + msg.value - oldBalances[i]`; this same formula, with the same `msg.value`, is evaluated again at every duplicate `address(0)` index.
- `utxoAmount` is computed by re-scanning the whole `utxoSet` for matches against `erc20TokenAddresses[i]`; if two indices share the same address, the *same* `utxoSet[j]` entry matches at both indices, so `utxoAmount` (and the `createOnchainCommitment` call, which increments `onChainCommitmentCounter`) is counted a second time for the same physical output.

`ExternalActionSwap.swap` only ever returns a single UTXO for the swap's `outputToken`: [2](#0-1) 

Nothing in `dimensionsCheck` or `checkOnchainCreation` rejects duplicate addresses in `circomData.erc20TokenAddresses`: [3](#0-2) [4](#0-3) 

Attacker's call: craft `circomData.erc20TokenAddresses = [WETH (input), address(0) (real output index), address(0) (padding index)]`, with `onChainCreation[1] = onChainCreation[2] = true`, and drive the LiFi router call so the swap output is realized as ETH (`address(0)`). After `swap()` returns the single output UTXO with `erc20Address == address(0)` and `amount == amountToSendToHinkal`:
- index 1: `balanceDif[1] == 0 + utxoAmount[1]` → `amountToSendToHinkal == amountToSendToHinkal` ✓ (legitimate leg, one `OnChainCommitment` created).
- index 2 (duplicate): the same `utxoSet[0]` matches again, so `utxoAmount[2] == amountToSendToHinkal` again, and `balanceDif[2]` — read from the identical `address(0)` balance snapshot — is also `amountToSendToHinkal`. The equation `balanceDif[2] == 0 + utxoAmount[2]` holds trivially, **with no additional real ETH ever moving**, and a **second** `OnChainCommitment` for `amountToSendToHinkal` is appended to `onChainCommitments`.

The `msg.value` variant described in the question (listing `address(0)` alongside WETH and unwrapping mid-call) is a specific instantiation of the same root cause: because the `+msg.value` correction and the `utxoAmount` re-scan are applied per-index rather than per-unique-token, any single real ETH movement (whether from `msg.value` or from a swap payout) can be replayed across every duplicate `address(0)` slot the attacker chooses to add, each replay independently satisfying its own balance equation. None of `performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, or the balance/slippage `require`s reject duplicate token addresses, so the guard set described in the audit checklist does not close this gap.

### Impact Explanation
Each duplicated index yields one extra `OnChainCommitment`/accounted shielded amount backed by zero additional real asset inflow — this is a direct "minting shielded value without backing" scenario (Critical per the provided severity table), since committed on-chain UTXOs (or equivalently doubled `amountChanges` legs) can later be spent by the attacker as real, redeemable shielded balance while Hinkal's actual token/ETH reserves only ever received the value once. The attack is repeatable per transaction and scales with the number of duplicate indices the attacker adds to `erc20TokenAddresses` (bounded only by `dimensions.tokenNumber`/gas), so an attacker can multiply the shielded credit for a single real swap output several-fold in one call.

### Likelihood Explanation
The attacker needs only: (1) their own funds/UTXOs to run a normal LiFi swap external action, (2) full control over `circomData.erc20TokenAddresses`, `onChainCreation`, and `amountChanges` (explicitly listed as attacker-controlled fields), and (3) a self-consistent zk proof, which is achievable since the circuit's public inputs simply echo the token-address list per index (`formBasicInput` in `contracts/CircomDataBuilder.sol`, lines 203-207) without any uniqueness constraint enforced on-chain either. No relayer/owner privilege, no oracle assumption, no external dependency defect is required — only that the attacker structures their own proof/calldata to include a duplicate token slot. This makes the attack low-cost and fully repeatable.

### Recommendation
Enforce uniqueness of `circomData.erc20TokenAddresses` in `dimensionsCheck` (or immediately in `Hinkal.transact`), rejecting any transaction where the same token address appears more than once. Additionally, refactor the balance/UTXO accounting loop in `Hinkal.transact` to aggregate real balance changes and `utxoSet` matches keyed by *unique* token address rather than by raw array index, and ensure `msg.value` is added to the `address(0)` balance-difference calculation exactly once regardless of how many times `address(0)` might otherwise appear.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, a mock LiFi router, `LifiExternalAction`, and a WETH mock; register the external action.
2. Fund an attacker EOA with WETH-equivalent shielded UTXOs (via a legitimate deposit/transact) sufficient to back one swap leg.
3. Locally generate a valid Groth16 proof for a `transact` call whose `CircomData` sets:
   - `erc20TokenAddresses = [WETH, address(0), address(0)]`
   - `amountChanges = [-inputAmount, 0, 0]`, `onChainCreation = [false, true, true]`
   - `externalActionData` pointing at the LiFi swap action with router calldata that swaps WETH → ETH.
4. Call `Hinkal.transact(...)` and assert:
   - Before: record `address(this).balance` on the Hinkal contract (`oldBalanceETH`).
   - After: record `newBalanceETH` and the number of `OnChainCommitment`s emitted/inserted for `address(0)`.
   - Assert `newBalanceETH - oldBalanceETH == amountToSendToHinkal` (only one real inflow), **but** assert two separate on-chain commitments each encoding `amountToSendToHinkal` were created/inserted into the tree (i.e., total minted shielded ETH `== 2 * amountToSendToHinkal > (newBalanceETH - oldBalanceETH)`), proving the equality `msg.value/ETH inflow backing == exactly one accounting term` is violated.
