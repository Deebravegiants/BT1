## Title
Optional (bypassable) slippage protection on `Withdraw` allows LPs to be sandwiched when redeeming LP tokens - (File: `program/src/processor.rs`)

### Summary
The `Withdraw` instruction's slippage-protection fields (`min_coin_amount` / `min_pc_amount`) are optional and are only checked when *both* are present in the instruction data. Because the instruction is unpacked directly from raw, attacker/user-controlled bytes with no enforced minimum length beyond the base `amount`, a withdrawal can be submitted with these fields entirely omitted, and `process_withdraw` will silently skip the check and pay out whatever the pool's current spot ratio computes to. This mirrors the KyberSwap `Pool.sol#burnRTokens` finding, where redemption paths that bypass a "protected" wrapper (a position manager that enforces min amounts/deadlines) have zero slippage protection.

### Finding Description
`WithdrawInstruction` declares its protection fields as `Option<u64>`: [1](#0-0) .

The unpacker only fills in `min_coin_amount`/`min_pc_amount` when at least 16 extra bytes are supplied after the base `amount`; otherwise both are set to `None`: [2](#0-1) .

`process_withdraw` only enforces the slippage bound when **both** options are `Some`: [3](#0-2) 

If either or both are `None` (i.e., the caller submits `Withdraw` instruction data with just the 8-byte `amount` and nothing else), the check block is skipped entirely and the withdrawal proceeds at whatever `coin_amount`/`pc_amount` the current pool reserves compute to via `Calculator::calc_total_without_take_pnl_no_orderbook` and `InvariantPool::exchange_pool_to_token`: [4](#0-3) .

This is directly reachable by any unprivileged LP (the only signer check is `source_lp_owner_info.is_signer`) in a single transaction with attacker/user-chosen instruction data: [5](#0-4) . There is no deadline check anywhere in `process_withdraw` either.

Because Raydium's constant-product pool price moves with every swap in the same or preceding transaction/slot, an MEV searcher can sandwich an unprotected `Withdraw` call: push the pool's spot price against the withdrawer with a swap immediately before, let the `Withdraw` (with no min amounts) execute at the skewed ratio, then swap back afterward, extracting value that would otherwise have gone to the LP.

### Impact Explanation
Unlike `SwapBaseIn`/`SwapBaseOut`, which hard-code mandatory `minimum_amount_out`/`max_amount_in` fields (non-optional), `Withdraw` allows the caller to opt out of protection entirely, and any wallet/integration that builds the minimal 9-byte payload (or a malicious relayer that strips the trailing 16 bytes) exposes LPs to sandwich attacks that directly steal value from liquidity providers during redemption — a real loss of user/LP funds, matching the Medium severity of the original report.

### Likelihood Explanation
This requires no privileged role, no malicious validator, and no off-chain assumptions — an ordinary LP transaction that omits (or is stripped of) the optional slippage fields is sufficient, combined with a searcher capable of ordering a swap before/after it in the same block, which is standard MEV capability on Solana.

### Recommendation
Make `min_coin_amount` and `min_pc_amount` mandatory (non-optional) fields in `WithdrawInstruction`, always enforce the `ExceededSlippage` check regardless of whether they are supplied, and consider adding an explicit deadline parameter to `process_withdraw`, consistent with the mandatory checks already present in `SwapBaseIn`/`SwapBaseOut`.

### Proof of Concept
1. Attacker observes a pending `Withdraw` instruction (or crafts their own withdrawal client) that encodes only the 9-byte payload `[tag=4][amount:u64]` with no trailing `min_coin_amount`/`min_pc_amount` bytes, per the unpack logic at [2](#0-1) .
2. Before the withdrawal lands, attacker submits a large `SwapBaseIn`/`SwapBaseOut` that skews the pool's coin/pc ratio.
3. The victim's `Withdraw` executes; since `withdraw.min_coin_amount`/`min_pc_amount` are `None`, the slippage-check branch at [3](#0-2)  is bypassed and the LP is paid out `coin_amount`/`pc_amount` computed from the skewed reserves.
4. Attacker swaps back immediately after, restoring the price and pocketing the value extracted from the victim's redemption.
