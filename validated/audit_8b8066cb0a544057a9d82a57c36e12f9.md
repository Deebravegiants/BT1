### Title
Webhook `shop-domain` header is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the tenant identifier (`shop-domain` header, exposed via `#shop`) is read separately from an unauthenticated HTTP header and never included in the HMAC-signed material. `ShopifyAPI::Webhooks::Registry.process` validates only that the body's HMAC is correct and then dispatches the (unauthenticated) `shop` value straight to the app's handler as the tenant key.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) [2](#0-1) 

`#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is *not* part of `to_signable_string`. `Registry.process` verifies the HMAC and then forwards `request.shop` unchecked to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, to_signable_string)`, i.e. `HMAC(api_secret_key, raw_body)` only: [4](#0-3) 

Because `api_secret_key` is a single, app-wide secret shared across every shop that installs the app (it is not per-shop), the resulting HMAC is a function of `(app_secret, body)` only — it carries no cryptographic binding to the shop that produced it. The equality the code implicitly (and incorrectly) relies on is:

`HMAC_valid(body) == true` ⟹ `shop header == shop that generated body`

but the actual guarantee provided by the HMAC is only:

`HMAC_valid(body) == true` ⟹ `body was HMAC'd with this app's secret` (by *some* shop running this app)

This is exactly the "field acted on but not covered by the HMAC" class from the report: `PowerPod`'s bug let state changes (balance updates) occur despite the identity-relevant call failing/being ignored; here, the identity field (`shop`) is allowed to flow into application logic despite never being part of what the HMAC actually authenticates.

### Impact Explanation
An unprivileged attacker who can install the target app on their own store (e.g., a free Shopify dev/partner store — no special privilege, no access token, no leaked secret required) can trigger a legitimate webhook delivery for their own shop, capturing a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair. Because the HMAC is not shop-scoped, the attacker can replay that exact body+HMAC pair directly to the app's public webhook endpoint while substituting `X-Shopify-Shop-Domain: victim-shop.myshopify.com`. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches the event to the app's handler tagged with the victim's shop domain — see `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` at `lib/shopify_api/webhooks/registry.rb:198`. Any app logic keyed off `data.shop` (updating shop-scoped records, honoring `customers/redact`/`shop/redact` compliance topics, triggering `app/uninstalled` side effects, etc., as documented in `docs/usage/webhooks.md:12-17`) is now operating on attacker-chosen data attributed to a different tenant — this is cross-tenant access/data confusion, which is explicitly a Critical-severity outcome under the scoped impact list.

### Likelihood Explanation
Moderate-to-high: it requires only (1) the ability to install the app on an attacker-controlled shop to legitimately obtain one `(body, hmac)` pair for a topic of choice, and (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with forged headers — both are unprivileged, internet-accessible actions with no dependency on the app's `api_secret_key`, access tokens, or any credential leak.

### Recommendation
Bind the shop identity into the material that is verified, not merely into the value that is trusted afterward. Concretely: after HMAC validation, cross-check `request.shop` against a shop already known to be legitimately associated with the app (e.g., verify a corresponding webhook subscription/id was actually registered for that shop via a lookup that isn't attacker-controllable), or include the shop domain in the value the app additionally authenticates before dispatch (e.g., require the caller to also present the `webhook_id`, which should be validated against Shopify via API, or maintain a local registry per shop and reject unknown shop/webhook_id combinations). At minimum, document prominently that `data.shop` from `WebhookMetadata` is not cryptographically bound by the HMAC and must not be trusted as a tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (free/unprivileged action) and triggers a webhook, e.g. `orders/create`, receiving from Shopify a POST with:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - `raw_body: {"id":1,...}`
2. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
3. Attacker sends a new HTTP POST directly to the app's public webhook route (bypassing Shopify) with the same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers (`lib/shopify_api/webhooks/request.rb:45-63`); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, and acts on it as if it were a genuine event from the victim tenant.

          received_signature = verifiable_query.hmac
