Webhook `shop-domain` identity is trusted without HMAC coverage, breaking the shop-binding invariant - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to the app's webhook handler from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `ShopifyAPI::Utils::HmacValidator.validate` checks only covers the raw request body. The `shop` field the handler acts on is never bound to the value that was cryptographically verified.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, which requires two methods: `hmac` and `to_signable_string`. Its implementation is: [1](#0-0) 

- `hmac` reads the `X-Shopify-Hmac-Sha256` header.
- `to_signable_string` returns only `@raw_body`.
- `shop` is a separate accessor that simply reads the `shop-domain` header, entirely outside of `to_signable_string`.

`Registry.process` validates the webhook using exactly this interface: [2](#0-1) 

`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` header: [3](#0-2) 

Since `to_signable_string` for a webhook request is only the raw JSON body, the HMAC proves that the *body bytes* came from someone holding `api_secret_key` (i.e., Shopify), but it proves nothing about which shop sent them. `request.shop` — the value passed straight into `WebhookMetadata.new(... shop: request.shop ...)` and handed to the app's `handler.handle` — is taken from a header that is not part of the signed material at all.

This breaks the intended binding `hmac-verified-bytes == shop-attributed-to-handler`. In the real Shopify webhook contract, `X-Shopify-Shop-Domain` is delivered by Shopify's own infrastructure over a channel the app never sees directly (it's re-derived by whatever transport puts the raw HTTP request in front of this constructor), so in the normal Shopify→app path this is not by itself exploitable. But within the scope of this gem, `Webhooks::Request.new` and `Registry.process` accept `headers` as a plain hash with no requirement that they originate from a genuine Shopify delivery channel, and nothing in this gem cross-checks `shop-domain` against the signed body content (e.g., there is no requirement that the body itself carry the shop, nor any comparison against a known/expected shop for the topic).

### Impact Explanation
If the host application's webhook endpoint ever forwards attacker-influenced headers into this constructor (e.g., a shared endpoint behind a proxy that does not strip/override `X-Shopify-Shop-Domain`, or a bug that copies headers verbatim from an inbound request whose HMAC was valid for a *different*, replayable body/shop combination), an attacker can cause `WebhookMetadata#shop` to report an arbitrary shop while the HMAC only vouches for the body. Any handler logic that uses `shop` to select per-tenant credentials, look up a session/access token, or gate multi-tenant data access would then act under the wrong tenant identity — a cross-tenant confusion rooted entirely in this gem's `Request`/`HmacValidator` design, since the gem itself never binds `shop` to the signed bytes.

### Likelihood Explanation
Exploitability depends on how the host application wires raw request headers into `Webhooks::Request.new`. This gem does not enforce a canonical source for the `shop-domain` header, does not sign it, and does not cross-validate it against the body — it treats a header value as trustworthy identity for the entire downstream tenant-dispatch flow. This is a design gap in the gem's own webhook-verification abstraction (`VerifiableQuery`/`HmacValidator`), independent of any particular host bug, since a correctly-implemented signing scheme would include the shop (or a body field it maps to) inside `to_signable_string`.

### Recommendation
Include `shop` (and ideally `topic`) inside `to_signable_string`, or otherwise cryptographically bind the shop identity to the verified payload, so that `HmacValidator.validate` fails whenever the `shop-domain` header does not match what was actually signed by Shopify. At minimum, document and enforce that `shop-domain` must be taken from a channel that cannot be independently manipulated relative to the signed body.

### Proof of Concept
```ruby
require "shopify_api"

ShopifyAPI::Context.setup(
  api_key: "key",
  api_secret_key: "secret",
  host_name: "host",
  api_version: "2024-01",
  scope: [],
  is_private: false,
  is_embedded: true,
)

body = "{}"
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, body)
)

# Attacker (or a misconfigured proxy) supplies an arbitrary shop-domain header;
# the HMAC only ever certifies `body`, never `shop`.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen value
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, even though `shop` was never signed
request.shop # => "victim-shop.myshopify.com", trusted downstream by Registry.process/WebhookMetadata
```
This demonstrates that `HmacValidator.validate` returning `true` says nothing about the authenticity of `request.shop`, confirming the missing binding between the HMAC-verified bytes and the shop identity that this gem hands to application webhook handlers.
