### Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted for tenant routing but excluded from the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop-domain`, `topic`, and `webhook-id` headers are read directly from unauthenticated HTTP headers and then handed to the app's webhook handler as trusted tenant-identifying data. This breaks the binding between "bytes verified by the HMAC" and "identity acted upon by the handler," allowing a valid webhook signature captured from one shop to be replayed against the endpoint with a forged `shop-domain` header, causing the app to process attacker-controlled data under a different merchant's identity.

### Finding Description
`Utils::HmacValidator.validate` verifies a request by HMAC-signing `verifiable_query.to_signable_string` and comparing it to the received signature [1](#0-0) . For webhooks, `Webhooks::Request#to_signable_string` returns only the raw JSON body, and none of the identity-carrying headers are folded into the signed string: [2](#0-1) 

Compare this to `Auth::Oauth::AuthQuery#to_signable_string`, which explicitly folds `shop` and `host` into the signed payload so those fields are cryptographically bound to the signature [3](#0-2) . The webhook path has no equivalent binding: `shop`, `topic`, and `webhook_id` are all pulled straight from HTTP headers with no HMAC coverage [4](#0-3) .

`Webhooks::Registry.process` validates only the body's HMAC and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the metadata object dispatched to the app-defined handler: [5](#0-4) 

The equality that should hold is:
`hmac_verified(bytes)` == `bytes acted upon as (shop, topic, webhook_id, body)`

but in reality:
`hmac_verified(bytes)` == `body only`, while `shop`/`topic`/`webhook_id` are accepted from unauthenticated headers and used as the tenant/topic identity for dispatch.

### Impact Explanation
An unprivileged internet user who can install the target app on their own (attacker-controlled) shop can trigger a legitimate webhook delivery, capturing a valid `(raw_body, hmac)` pair signed with the app's real `client_secret`/`api_secret_key`. Because the signature covers only the body, the attacker can replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain. The signature still validates (since it only checks the body), but the handler receives and processes the payload as if it originated from the victim shop — a cross-tenant confusion that can corrupt or exfiltrate state keyed by shop domain in the host application (e.g., updating the wrong merchant's order/customer records, or triggering privileged per-shop side effects). This matches the Critical "cross-tenant access" impact category, since the attacker crosses a tenant boundary using only their own legitimately obtained webhook payload.

### Likelihood Explanation
Likelihood is moderate-to-high: any developer/tester can register an app on their own store and receive real webhook traffic with a valid HMAC, and nothing in `HmacValidator` or `Webhooks::Request` prevents header tampering before HMAC verification since headers were never part of the signed content. No access token, `client_secret`, or privileged account is required — only the attacker's own (free) shop installation, which is the intended, unprivileged use case for this gem's webhook consumers.

### Recommendation
Bind the shop, topic, and webhook id to the signature verification path — e.g., have `Webhooks::Request#to_signable_string` include (or otherwise cryptographically bind) the `shop-domain`, `topic`, and `webhook-id` headers, or have `Registry.process` independently cross-check these header values against the shop/topic pairing that was registered/expected, rejecting mismatches before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery, e.g.:
```
POST /callback/orders/create
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of body>
x-shopify-shop-domain: attacker-shop.myshopify.com
x-shopify-webhook-id: abc-123
Body: {"id": 1, "note": "hello"}
```
2. Attacker replays the identical body and `x-shopify-hmac-sha256` value to the same endpoint, only changing:
```
x-shopify-shop-domain: victim-shop.myshopify.com
```
3. `Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) body against the (unchanged) HMAC — see `to_signable_string` returning `@raw_body` in [6](#0-5) .
4. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` to the app's handler [5](#0-4) , causing the host application to act on `attacker-shop`'s payload under `victim-shop`'s tenant identity.
