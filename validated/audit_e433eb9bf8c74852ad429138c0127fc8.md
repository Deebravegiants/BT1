### Title
Webhook shop-domain identity spoofing via header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then unconditionally trusts the `shop` field taken from the `x-shopify-shop-domain`/`shopify-shop-domain` header when dispatching to the merchant's handler. Because the HMAC signature only covers the raw body bytes and never the shop-domain header, an attacker who possesses any one valid `(body, hmac)` pair signed with the app's shared `client_secret` — trivially obtainable by installing the app on their own development/trial store and capturing a genuine webhook — can replay that body to the app's public webhook endpoint while forging the `shop` header to name an arbitrary victim shop. The gem will report the request as HMAC-valid and hand the handler a `WebhookMetadata` object claiming to originate from the victim shop.

### Finding Description
`Webhooks::Registry.process` performs the only authenticity check: [1](#0-0) 

The HMAC is verified against `to_signable_string`, which for a webhook `Request` is defined as just the raw body — the `shop` accessor (sourced from the `shop-domain` header) is never part of the signed material: [2](#0-1) 

The broken identity binding is:
`HMAC_valid(raw_body, client_secret) == true` is treated as proof that `request.shop == "the shop that actually sent this webhook"`, when in fact `HMAC_valid` only proves `raw_body` was signed by *some* installation of the app (any tenant using the same `client_secret`) — it says nothing about which shop the header claims.

Because every shop that installs a given Shopify app shares the same `client_secret`/`api_secret_key`, any attacker who is a legitimate (even trial) merchant of the app can obtain a real `(raw_body, hmac)` pair from Shopify's own webhook delivery to their store, then POST that exact body/hmac pair to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header naming a different, victim shop. `HmacValidator.validate` will succeed because it only recomputes the HMAC over `@raw_body`, and `Registry.process` will hand `WebhookMetadata.new(... shop: request.shop ...)` to the app's registered handler as if the event genuinely came from the victim shop.

### Impact Explanation
This crosses a tenant boundary using only unauthenticated header bytes: the attacker fully controls both the claimed `shop` and (subject to needing a validly-signed body) can choose which topic/body combination to replay, since attackers can generate their own genuinely-signed webhooks for any topic on their own store and then relabel them. Depending on how the host app's webhook handler trusts `WebhookMetadata#shop` (e.g., `app/uninstalled` cleanup, `shop/redact` GDPR processing, order/customer upserts keyed by shop), this enables cross-tenant data corruption, spurious deletion of another merchant's stored session/data, or injection of attacker-controlled data attributed to a victim shop — a cross-tenant access impact.

### Likelihood Explanation
Any user can register as a merchant/install the target app on a free development store to receive genuinely-signed webhooks, satisfying the prerequisite of obtaining one valid `(body, hmac)` pair without needing the app's `client_secret` itself. The webhook receiving endpoint is by definition internet-reachable and unauthenticated aside from the HMAC check. No privileged credential or access token is required — only the "unprivileged internet user" ability to install the app once and then send arbitrary HTTP POSTs to the app's public endpoint.

### Recommendation
Bind the authenticated shop identity to the signed payload rather than to a separate, unsigned header. Options: include the shop domain in the HMAC-signed material (matching how OAuth's `AuthQuery#to_signable_string` binds `shop`), or require the host application to independently establish/validate `request.shop` against a shop that is already known to have this webhook/topic combination registered (e.g., cross-check against stored webhook registrations before dispatch) rather than trusting the header value directly in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering a genuine `app/uninstalled` (or other) webhook signed by Shopify with the app's `client_secret`. Attacker captures the raw body `B` and the `x-shopify-hmac-sha256` header `H`.
2. Attacker sends a POST directly to the app's public webhook endpoint with:
   - Body: `B` (unmodified — byte-identical to the captured original)
   - Header `x-shopify-hmac-sha256: H` (unmodified)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic:` matching the original topic
3. `ShopifyAPI::Webhooks::Request.new` parses these headers/body successfully.
4. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only [3](#0-2)  — validation succeeds because `B`/`H` are unmodified.
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from `attacker-shop.myshopify.com`, confirming the shop-identity spoof.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
