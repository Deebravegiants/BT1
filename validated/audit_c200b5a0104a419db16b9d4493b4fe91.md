### Title
Webhook `shop` domain is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" [1](#0-0)  before handing the webhook off to the app's handler, but the HMAC signature computed by `HmacValidator` only ever covers the raw request body — never the `shop` (or `topic`/`webhook_id`) header. This breaks the identity binding: `shop-authenticated == shop-header` is assumed by callers, but the gem never enforces it.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) . The `shop` accessor simply reads the `x-shopify-shop-domain`/`shopify-shop-domain` header directly with no cross-check against the signed payload: [3](#0-2) .

`HmacValidator.validate` computes the HMAC solely over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it with `OpenSSL.secure_compare`: [4](#0-3) . `Registry.process` calls this validator, and on success immediately forwards `request.shop` — the unauthenticated header value — straight to the app-supplied handler as if it were verified: [5](#0-4) .

Because the shop domain is never part of the signable string, any request with a *valid* HMAC for a given body (which an attacker can legitimately obtain for their own shop, since they can install the app in their own shop and receive real, correctly-signed webhooks) still validates successfully if the `x-shopify-shop-domain` header is swapped to any other value — including a victim merchant's domain — after the fact. This is exactly the identity-binding gap described in the bug class: "a shop authenticated versus the shop stored as a session key" is never actually asserted equal.

### Impact Explanation
This crosses a tenant boundary: `Registry.process` presents `data.shop` to the handler with the implicit (and doc-stated) guarantee that "the request did indeed come from Shopify" for *that* shop, when in fact only the body bytes are authenticated. A host application that (reasonably, given the gem's documented behavior) uses `data.shop` to route/attribute webhook data to a specific merchant's tenant (e.g., updating that shop's local order/product records, as shown in the gem's own example `perform_later(topic: data.topic, shop_domain: data.shop, ...)` in `docs/usage/webhooks.md`) can be made to write or process data under an attacker-chosen shop domain, i.e., cross-tenant data injection — a Critical-class impact per the given classification.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint plus possession of one validly HMAC-signed webhook payload for *any* shop (trivially obtainable by installing the app on an attacker-controlled development/test shop and capturing the real webhook Shopify sends). No `api_secret_key`, access token, or privileged account is required — the attacker never needs to compute a new HMAC, only to replay a legitimately-signed body with a substituted `shop` header. The gem performs no correlation between the signed bytes and the shop header, so the request passes `HmacValidator.validate` unmodified.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`) values into the HMAC-signable representation, or otherwise require callers to compare `request.shop` against an independently-verified set of installed shops before trusting it. At minimum, update `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to incorporate the shop-domain header (matching Shopify's actual signing behavior only if it in fact includes headers — otherwise the documentation in `docs/usage/webhooks.md` should be corrected to explicitly warn that `data.shop` is unauthenticated and must be cross-checked by the host app against its own session/shop store before being trusted).

### Proof of Concept
1. Attacker installs the target app on their own development shop `attacker.myshopify.com` and subscribes to a webhook topic (e.g., `orders/create`).
2. Shopify sends the attacker a legitimately HMAC-signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`), and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays this exact request to the victim app's webhook endpoint but changes only the header to `x-shopify-shop-domain: victim-shop.myshopify.com`, leaving body `B` and `H` untouched.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and compares it to `H` — this still matches, since `shop` is never part of the signed string (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though this webhook never originated from Shopify for that shop.
