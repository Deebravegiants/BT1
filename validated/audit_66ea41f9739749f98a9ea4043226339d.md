### Title
No valid vulnerability — nonce close-and-reopen replay is already prevented (SIMD-0083 re-validation)

### Summary
The scenario described (close a nonce account, re-fund/re-initialize it within the same slot, and have a stale pre-signed nonce transaction validate against the new state) is explicitly anticipated and defended against in the codebase. `validate_transaction_nonce` in `svm/src/transaction_processor.rs` re-validates every nonce transaction's stored `durable_nonce`, owner, size and authority against the *current* on-chain account state at actual load/execution time (not just an earlier admission-time check), and dedicated integration tests confirm the exact close+reopen scenario is rejected.

### Finding Description
The claim rests on two false premises:

1. **A new `DurableNonce` derived at re-initialization would equal the stale one.** `initialize_nonce_account` computes `DurableNonce::from_blockhash(&invoke_context.environment_config.blockhash)` using the *current* bank blockhash [1](#0-0) . A stale, previously-signed nonce transaction was signed against a durable nonce derived from an *earlier* blockhash (from whenever the nonce was last advanced/initialized). Unless close+reopen literally happens in the very same slot the nonce was originally minted (which additionally requires the attacker be the account's own nonce authority — see below), the values differ and `verify_nonce_account` fails, returning `None` → `TransactionError::BlockhashNotFound` [2](#0-1) .

2. **Closing requires signer authority, and closing is itself blocked in the same slot the nonce was already advanced.** `withdraw_nonce_account`'s full-balance-close path explicitly checks `data.durable_nonce == durable_nonce` (i.e., the nonce's already-advanced state for the current slot) and rejects with `NonceBlockhashNotExpired` if so, and separately requires `check_signer(&data.authority)` [3](#0-2) . An unprivileged attacker without the account's authority cannot close it at all.

3. **Re-validation happens at actual execution time, not just admission time.** `validate_transaction_nonce` is explicitly documented to defend against "the nonce account was used, closed, closed and reopened, closed and spoofed by a non-system program, or had its authority changed," concluding "Such a transaction cannot be processed, even as fee-only" [4](#0-3) . This check loads the account fresh via `AccountLoader` (reflecting any same-batch mutations), applies `strict_nonce_size_check`, `verify_nonce_account` (owner=system_program + `Initialized` state + blockhash match), and requires the authority signer set in the transaction to match the *current* stored authority [5](#0-4) .

The `svm/tests/integration_test.rs::simd83_nonce_reuse` test suite directly encodes this exact attack scenario and asserts rejection:
- Batch 7: close nonce, reopen with proper nonce size at same address, then reuse stale nonce tx → `ExecutionStatus::Discarded` [6](#0-5) .
- Batch 8: close nonce, recreate as a nonce account, then reuse stale nonce tx → `Discarded` [7](#0-6) .
- Batch 9: close nonce, re-fund the address as a spoofed non-system-owned account that parses as `Initialized`, then reuse stale nonce tx → `Discarded`, with comment "check_age would never let such a transaction through validation" [8](#0-7) .
- Batch 10: change authority, then reuse stale nonce tx signed by old authority → `Discarded` [9](#0-8) .

### Impact Explanation
None. No value transfer, double settlement, or divergence is possible: the stale transaction is uniformly dropped (`BlockhashNotFound`/`Discarded`), never executed against re-created state.

### Likelihood Explanation
Not applicable — the described precondition (matching `DurableNonce` across a close/reopen boundary against a stale, differently-blockhash-signed transaction) cannot occur given `DurableNonce::from_blockhash` always uses the bank's *current* blockhash at initialize time, and closing requires the attacker already control the account's authority, which is not "unprivileged attacker vs. victim's nonce" as posited.

### Recommendation
No code change required. The existing `validate_transaction_nonce` re-validation (SIMD-0083) and the `strict_nonce_size_check` + owner/state/authority checks in `verify_nonce_account` already fully mitigate this class of issue, backed by explicit regression tests.

### Proof of Concept
The requested PoC already exists and passes in-repo: `svm/tests/integration_test.rs::simd83_nonce_reuse`, batches 7–10 [10](#0-9) , which construct the close+reopen-same-batch scenario and assert `ExecutionStatus::Discarded` for the replayed stale nonce transaction, and `final_accounts` reflecting only the legitimate first transaction's effect.
