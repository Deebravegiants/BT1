### Title
Post-validation growth of Action/Data receipts (`output_data_receivers`, return-value data payload) allows receipts above `max_receipt_size` to be persisted and forwarded across shards - ([File: runtime/runtime/src/verifier.rs])

### Summary
`validate_receipt` only enforces `limit_config.max_receipt_size` when `mode == ValidateReceiptMode::NewReceipt`, and `ValidateReceiptMode::ExistingReceipt` explicitly skips the size check to tolerate a known bug (tracked as near/nearcore#12606). An attacker-controlled contract can construct a promise chain where a receipt passes `NewReceipt` validation at/near the size limit, but is later mutated (via `output_data_receivers` appended by a dependent promise, or via a returned value wrapped into a `Data`/`PromiseResume` receipt) after that validation point, producing a final on-chain/cross-shard receipt that exceeds `max_receipt_size` without ever being re-validated in `NewReceipt` mode.

### Finding Description
`validate_receipt` in `runtime/runtime/src/verifier.rs` gates the size check on the validation mode: [1](#0-0) 
The `ExistingReceipt` variant is documented as intentionally tolerating receipts created above the size limit due to a known bug: [2](#0-1) 

The receipt-generation flow lets a contract call `promise_then`/`promise_return`, which appends `output_data_receivers` (in `ReceiptManager::create_action_receipt`) to an already-created action receipt after that receipt was initially sized/validated as `NewReceipt`: [3](#0-2) 
Similarly, when a promise resolves, its return value is wrapped into a `Data`/`PromiseResume` receipt (`create_promise_resume_receipt`) whose payload size is derived from the contract's return value: [4](#0-3) 

This is not a hypothetical - it is already demonstrated and acknowledged in the repository's own test suite. `test-loop-tests/src/tests/max_receipt_size.rs` contains `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return`, both of which construct a promise DAG (`A -then-> B`, where `A` creates a new promise `C` and does `promise_return`, or `A` returns a large value) that pass initial `NewReceipt` validation at exactly `max_receipt_size`, but whose `output_data_receivers`/data payload push the actual receipt over the limit: [5](#0-4) [6](#0-5) 
Both tests then assert that an oversized receipt does in fact appear in the persisted chain data / cross-shard incoming receipts via `assert_oversized_receipt_occurred`, which scans blocks (or receipt proofs, in Spice mode) for a receipt whose `borsh::object_length` exceeds `max_receipt_size`: [7](#0-6) 

The root cause is that the "new" receipt validated in `NewReceipt` mode is a snapshot before further mutation (adding output data receivers or resolving data payloads), and once such an oversized receipt exists, it is treated everywhere downstream as an "existing" receipt (`ExistingReceipt` mode), which explicitly does not re-check size. There is no re-validation step after the mutation and before persistence into the delayed-receipt queue or being forwarded cross-shard.

### Impact Explanation
This matches the "unbounded resource use" / node storage-and-bandwidth exhaustion class: an oversized receipt bypasses the `max_receipt_size` invariant, gets persisted to chain state and/or forwarded as an incoming receipt across shard boundaries, and is processed by nodes without the intended size cap, growing chunk/witness/state sizes and network payloads. The repo's own tests confirm actual receipts above the configured limit end up stored in blocks/receipt proofs. It does not permit fund theft or direct authorization bypass but does defeat a resource-bound invariant, one of the explicitly enumerated impact classes (unbounded resource use).

### Likelihood Explanation
Fully attacker-reachable with unprivileged capabilities only: deploy a contract, call a function that builds a promise chain via `promise_batch_create`/`promise_then`/`promise_return` or returns a large value, sized so the initially-created receipt is at/just under `max_receipt_size` and the subsequent mutation (added `output_data_receivers`, or resolved return-value `Data` receipt) pushes it over. This requires no special privileges, no validator/node access, and is deterministic/repeatable - it is already reproduced by the repository's dedicated regression tests, and the maintainers have an open tracking issue (#12606) acknowledging the bug rather than treating it as by-design behavior.

### Recommendation
Re-validate receipts in `NewReceipt` mode (or a new stricter mode) after any post-creation mutation that can change size - specifically after `output_data_receivers` are appended in `ReceiptManager::create_action_receipt`/`create_promise_yield_receipt`, and after `Data`/`PromiseResume` payloads are finalized in `create_promise_resume_receipt` - before the receipt is queued for processing/persisted/forwarded cross-shard. Alternatively, bound the total size contribution of `output_data_receivers` and data payload separately with per-field limits enforced at construction time (e.g., cap the aggregate size of `output_data_receivers` added to any receipt, and cap resolved value/payload size) so that no post-validation mutation can push a receipt above `max_receipt_size`, closing the loophole that `ExistingReceipt` mode currently tolerates as a workaround for issue #12606.

### Proof of Concept
The vulnerability already has reproducer tests in-repo:
- `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs` (lines 124-267) construct contract calls that generate receipts sized to `max_receipt_size` before mutation, then trigger `output_data_receivers` growth / large return-value data-receipt wrapping. [8](#0-7) 
- `assert_oversized_receipt_occurred` (lines 350-428) confirms an oversized receipt (`borsh::object_length(receipt) > max_receipt_size`) is actually found among persisted blocks / cross-shard incoming receipt proofs, proving the bypass is not merely theoretical but produces on-chain oversized receipts.
- Recommended additional PoC: add a unit test directly in `runtime/runtime/src/verifier.rs` that constructs a `Data` receipt exceeding `max_receipt_size`, asserts `validate_receipt(.., ValidateReceiptMode::ExistingReceipt)` returns `Ok(())`, and asserts that it is either rejected before reaching `process_receipts`/`ReceiptSink`'s delayed-receipt queue insertion or that a dedicated size-based congestion/backpressure check exists there - currently no such check exists in that pipeline, confirming the gap.

fn test_max_receipt_size_promise_return() {

    // User calls a contract method

    // When promise A is executed, it creates a third promise - `C` and does a `promise_return`.
    // The DAG changes to: [C ->then-> B]
    // The receipt for promise C is a maximum size receipt.
    // Adding the `output_data_receivers` to C's receipt makes it go over the size limit.
    let base_receipt_template = Receipt::V0(ReceiptV0 {
        predecessor_id: account.clone(),
        receiver_id: account.clone(),
        receipt_id: CryptoHash::default(),
        receipt: ReceiptEnum::Action(ActionReceipt {
            signer_id: account.clone(),
            signer_public_key: account_signer.public_key().into(),
            gas_price: Balance::ZERO,
            output_data_receivers: vec![],
            input_data_ids: vec![],
            actions: vec![Action::FunctionCall(Box::new(FunctionCallAction {
                method_name: "noop".into(),
                args: vec![],
                gas: Gas::ZERO,
                deposit: Balance::ZERO,
            }))],
        }),
    });
    let base_receipt_template = action_receipt_v1_to_latest(&base_receipt_template);
    let base_receipt_size = borsh::object_length(&base_receipt_template).unwrap();

    let args_size = max_receipt_size - base_receipt_size;

    // Call the contract
    let large_receipt_tx = SignedTransaction::call(
        102,
        account.clone(),
        account.clone(),
        &account_signer,
        Balance::ZERO,
        "max_receipt_size_promise_return_method1".into(),
        format!("{{\"args_size\": {}}}", args_size).into(),
        Gas::from_teragas(300),
        env.rpc_node().head().last_block_hash,

        account,

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
