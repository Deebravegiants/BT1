### Title
Permanent market freeze from `i128` overflow during interest accrual - ([File: common/src/rates/simulate.rs])

### Summary
A market with sufficiently large scaled debt can become permanently unusable when `accrue_step` converts `borrowed` shares to their current value before applying the borrow-index ceiling. [1](#0-0) [2](#0-1) 

### Finding Description
`Controller::update_indexes(caller, assets)` is callable by any address willing to authorize the call and forwards the requested `HubAssetKey` list to the pool. [3](#0-2) [4](#0-3) 

The pool accrues each requested market through `global_sync`, which calls `accrue_step` for each elapsed-time chunk. [5](#0-4) [6](#0-5) 

Inside `accrue_step`, `scaled_to_original(env, borrowed, borrow_index)` computes `borrowed * borrow_index / RAY` and returns `MathOverflow` when the resulting RAY value exceeds `i128::MAX`. [7](#0-6) [8](#0-7) [9](#0-8) 

The overflow happens before `update_borrow_index` can clamp the next index to `MAX_BORROW_INDEX_RAY`, because the product uses the already-stored `borrow_index`. [1](#0-0) [2](#0-1) 

`MAX_BORROW_INDEX_RAY` is `10^36`, while `i128::MAX` is approximately `1.70 * 10^38`, so a scaled debt greater than roughly `1.70 * 10^29` can overflow before the index reaches its ceiling. [10](#0-9) 

Once this condition is reached, repayment and withdrawal still begin with `ops::load_leg`, which loads and interest-syncs the market before resolving the requested action. [11](#0-10) [12](#0-11) [13](#0-12) 

### Impact Explanation
The market is permanently frozen absent a code fix because every state-changing pool path that can repay debt, withdraw collateral, or otherwise repair the market performs the same overflowing accrual first. [14](#0-13) [12](#0-11) [13](#0-12) 

The repository’s regression test demonstrates that both withdrawal and repayment revert with `MathOverflow` after the accrual failure, permanently locking supplier principal and preventing borrower repayment or liquidation-driven recovery. [15](#0-14) 

### Likelihood Explanation
No privileged call is required to trigger the frozen state because users can create debt through `borrow`, and any caller can subsequently invoke `update_indexes` after the borrow index has grown enough. [16](#0-15) [3](#0-2) 

The condition requires a large outstanding scaled-debt book and sufficient index growth rather than malformed input, so it is not an immediate attack on an empty market but is reachable through ordinary supply and borrow activity. [17](#0-16) [18](#0-17) 

The checked-in test reaches this condition with a billion-token, 18-decimal market borrowing at 98% utilization and confirms that the stored borrow index remains below `MAX_BORROW_INDEX_RAY` when the overflow occurs. [19](#0-18) 

### Recommendation
Compute the new debt using a widened `I256` intermediate or cap `borrow_index` before converting `borrowed` to its original value, and handle over-`i128` debt values with an explicit bounded result instead of allowing `scaled_to_original` to panic. [1](#0-0) [20](#0-19) 

At minimum, cap the usable accrual domain by enforcing `borrowed <= i128::MAX / index_ratio` before persisting new debt and add a recovery path that can settle or write down debt without first evaluating the overflowing total-debt expression. [18](#0-17) [11](#0-10) 

### Proof of Concept
The checked-in regression test constructs a market with `principal = 1_000_000_000 * 10^18`, supplies that amount, supplies collateral, and borrows `98%` of the supplied market. [21](#0-20) 

It then advances ledger time and repeatedly calls `update_indexes` until the call returns contract error `MathOverflow`, while asserting that the stored borrow index is still below `MAX_BORROW_INDEX_RAY`. [22](#0-21) 

After that point, both `withdraw` and `repay` fail with the same `MathOverflow` because they perform the overflowing accrual before reaching their action-specific logic. [23](#0-22) [11](#0-10)

```rust
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```
