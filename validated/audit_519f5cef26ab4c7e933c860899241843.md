### Title
Sender verification bypass for `RequestState` messages allows unauthenticated replay of the last relayed signup message - (File: orb-relay-client/src/client.rs)

### Summary
The `PollerAgent::main_loop` function in `orb-relay-client/src/client.rs` checks that an incoming message's `src.id` matches the expected paired peer (`self.config.dst_id`) before processing it, but this check is completely skipped for messages matching `self_serve::app::v1::RequestState`. Any entity able to reach the same relay stream can send a spoofed `RequestState` payload and force the Orb (or App) client to immediately resend its last transmitted message, without any sender identity validation.

### Finding Description
In `main_loop`, when a message arrives from the relay server it is dispatched as follows: [1](#0-0) 

The `if self_serve::app::v1::RequestState::matches(&payload).is_some()` branch is evaluated *before* the `else if src.id != self.config.dst_id` sender check, and on a match it unconditionally replies with `self.last_message.clone()` over the current stream. This is the exact bug class described in the external report: a specific gossip/message type ("gossip-final-state" there, `RequestState` here) is exempted from the sender-verification logic that every other message type goes through, letting an unverified sender influence protocol state/behavior.

The code's own comment acknowledges the trust boundary this check is meant to protect: the relay server multiplexes messages from multiple sources onto the same logical channel, and the client-side `src.id` filtering is what is supposed to reject messages from unintended senders: [2](#0-1) 

`last_message` is updated every time the client sends any outgoing payload (e.g. `AnnounceOrbId`, `SignupEnded`, `CaptureStarted`, `CaptureTriggerTimeout`), so an attacker triggering the bypass causes retransmission of whatever the most recent self-serve/signup protocol message was: [3](#0-2) 

The `dst_id` used for this comparison is the session/app identifier the Orb paired with for this specific signup: [4](#0-3) 

Because the `RequestState` branch never checks `src.id`, this pairing guarantee is bypassed for that message type.

### Impact Explanation
An unprivileged party capable of connecting to the relay backend and sending a `self_serve::app::v1::RequestState` payload (a legitimate, unauthenticated-with-respect-to-pairing message type used by the App during self-serve signup, see `proceed_with_biometric_capture` / `orb_relay_announce_orb_id` in `src/plans/mod.rs`) can force retransmission of the last signup-state protocol message intended for a different, legitimate session pairing. This can cause:
- Disclosure of signup/session state (e.g. `SignupEnded`, `AnnounceOrbId`, `CaptureStarted`/`CaptureTriggerTimeout`) to an unintended recipient.
- Cross-signup state bleed/confusion, since the response is generated purely from `last_message` without confirming the requester is the paired App for that session, mirroring the "gossip-final-state" bug class where a message type skips sender/receiver restrictions and lets an unauthorized party influence protocol outcome. [5](#0-4) 

### Likelihood Explanation
Exploitability depends on whether the relay server multiplexes messages for other sessions/entities onto the same client-visible response stream, which is exactly the concern the code's own TODO comment raises ("avoid multiplexing messages from different sources"). Given that concern is explicitly documented in the code as an open issue, and the `RequestState` special case is the one path that skips the mitigating `src.id` check entirely, this is a concretely reachable gap rather than a purely theoretical one.

### Recommendation
Apply the same `src.id != self.config.dst_id` sender verification to the `RequestState` branch before responding with `last_message`, so only the legitimately paired peer for the current session can trigger a resend of protocol state.

### Proof of Concept
1. Establish a relay connection as an arbitrary entity (any valid auth token, but for a different/unassociated session than the target Orb-App pairing).
2. Send a message whose payload matches `self_serve::app::v1::RequestState` (via `self_serve::app::v1::W { w: Some(RequestState(...)) }`), addressed so it is delivered on the target Orb client's stream.
3. Because the check at [6](#0-5)  executes before the sender-identity check, the Orb's `PollerAgent` immediately resends `self.last_message` (its most recent outbound self-serve/signup message) back on the stream, regardless of the requester's `src.id`, disclosing/replaying that message to the unverified requester.
