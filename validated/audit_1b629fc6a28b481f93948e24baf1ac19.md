I found a plausible divide-by-zero DoS analog in `Zap._executeBuy`.

### Title
Divide-by-zero DoS in `Zap._executeBuy` when the floor-bumped mint returns `ltMinted == 0` - (File: packages/contracts/src/Zap.sol)

### Summary
`Zap._executeBuy`'s fee-proration step divides by `ltMinted`, the amount of LT actually minted from the user's USDC in that call. If `ltMinted` can be zero while the function still reaches this line, the division reverts with a bare arithmetic panic, denying the buy — the same bug class as CVE-2017-11546's `insert_note_steps` divide-by-zero crash triggered by attacker-supplied input.

### Finding Description
In the curve (non-graduated) buy path, `Zap._executeBuy` computes `baseToConvert` (the USDC amount to mint into LT) and then calls `IBounceLeveragedToken(lt).mint(address(this), baseToConvert, 0)` to get `ltMinted` [1](#0-0) . Immediately after, the fee-proration logic divides by `ltMinted` unconditionally:
```
uint256 effectiveBaseSpent = (amountInUsed * baseToConvert) / ltMinted;
``` [2](#0-1) 

There is no `ltMinted == 0` guard anywhere along this path, unlike the two other division sites in the same file/family that are explicitly guarded (`if (exchangeRate == 0) revert ZeroExchangeRate();` in `Bonding._deployAndSeed`, and `if (exchangeRate > 0)` before dividing in `Bonding.previewLtUntilGraduation`) [3](#0-2) [4](#0-3) .

The only pre-check on `baseToConvert` before minting is `netUsdc < minUsdcAmount()` revert and, in the floor-bump branch, `baseToConvert < floor` bump-up [5](#0-4) . Both of these bound the USDC amount away from zero, but neither bounds the LT amount produced by `mint()` — that conversion is entirely determined by the external BounceTech LT's `exchangeRate()`/`baseToLtAmount()` rounding, which alt.fun's contracts do not control and cannot cap.

If a BounceTech LT's `exchangeRate()` is ever extremely large relative to `minUsdcAmount()`'s floor (e.g., a highly leveraged/rebased LT whose price has drifted far from 1e18), `baseToLtAmount(floor)` can floor-round to `0` even though `baseToConvert >= floor > 0`. Since `mint()` is defined as `baseToLtAmount(baseAmount)` [6](#0-5) , that same rounding applies to the real `mint()` return value, so `ltMinted` can legitimately come back as `0` even though `msg.sender`'s USDC was pulled and spent.

### Impact Explanation
When `ltMinted == 0`, the subsequent `/ ltMinted` division panics and reverts the whole transaction (Panic(0x12), division/modulo by zero). This does not by itself steal funds since the whole tx reverts atomically (USDC pull is undone), but it is a **denial-of-service on `Zap.buy`** for the affected token/LT pair: every buy attempt at or near the minimum-USDC floor for that LT permanently reverts, and (per the docs) BounceTech LTs cannot be un-paused/adjusted by alt.fun, so once a rate makes `baseToLtAmount(floor)` round to zero, that curve is bricked for small buys until the LT's rate moves back — with no recovery path exposed to alt.fun. This matches the CVE's DoS class (crash-on-crafted-input) rather than a fund-theft class, and per report rules only counts if it results in permanent freezing of trader funds; here the freeze is transaction-scoped (revert, not lock), and it is unclear the described extreme exchange-rate condition is reachable for the LTs alt.fun actually pairs with — the effect depends entirely on BounceTech LT internals outside alt.fun's contracts, which the rules also instruct to reject.

### Likelihood Explanation
Low-to-uncertain. The `minUsdcAmount()` floor and the LT's own `minTransactionSize` floor (`BelowMinTransactionSize`) are designed precisely to prevent dust mints, and the docs note the floor-bump path exists to keep mints above the LT's floor [7](#0-6) . Whether any live BounceTech LT's `exchangeRate()` can realistically reach a magnitude that makes `baseToLtAmount(minUsdcAmount())` round to zero is not verifiable from the in-scope contracts alone — it depends on BounceTech's own price feed and rounding behavior, which is explicitly out of scope per the rules ("bugs inside BounceTech LT... themselves" are rejected).

### Recommendation
Add an explicit `if (ltMinted == 0) revert` check immediately after each `mint()` call in `Zap._executeBuy` (both the graduated and curve branches), producing a clean, named revert instead of a raw arithmetic panic, and consider surfacing this as a distinguishable error so the frontend can explain "amount too small for this LT's current price" rather than an opaque panic.

### Proof of Concept
Not concretely reproducible within the in-scope contracts alone: triggering `ltMinted == 0` requires an external BounceTech LT configured/priced such that `baseToLtAmount(baseToConvert)` rounds to zero for a `baseToConvert >= minUsdcAmount()`. This condition lives entirely in BounceTech LT's exchange-rate/rounding logic, not in `packages/contracts/src`, so the report cannot fully validate reachability from alt.fun's own code — flagged as the main uncertainty in this analog.
