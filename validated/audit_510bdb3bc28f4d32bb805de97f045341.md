## Title
Fee-payment swaps in `EvmHost.dispatch`/`fundRequest` use `deadline: block.timestamp`, giving zero MEV/staleness protection - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept native token payment and internally swap it for the protocol fee token via `IUniswapV2Router02.swapETHForExactTokens`, passing `block.timestamp` as the swap's `deadline` argument. This mirrors the reported Vyper `SwapRouter` bug class: a deadline computed as `block.timestamp` is evaluated against the timestamp of the block the transaction actually lands in, not the timestamp at submission time, so the check is always satisfied and provides no real protection against a delayed/held transaction being executed at a stale price.

### Finding Description
Any unprivileged caller can invoke `dispatch()` with `msg.value > 0` to pay the outbound message fee in native token. `EvmHost` performs the conversion itself: [1](#0-0) 

The same pattern recurs for GET dispatch and for `fundRequest`: [2](#0-1) [3](#0-2) 

In all three cases, `deadline: block.timestamp` is passed straight through to the UniswapV2 router. Because the EVM evaluates `block.timestamp` at execution time (i.e., when the transaction is finally mined), this "deadline" can never be exceeded — a block producer/validator/searcher can withhold the transaction in the mempool and include it whenever the price of `feeToken()` relative to native token is most unfavorable to the caller, entirely within the bounds of `msg.value` (the implicit `amountInMax`), before it either executes at the worst attainable rate or reverts. This is functionally identical to the reported issue in `SwapRouter.vy`: a "deadline" that always equals the current execution time gives none of the deadline's intended protection.

### Impact Explanation
Every unprivileged dispatcher paying the Hyperbridge fee in native token is exposed to this: their fee-conversion swap can be timed by a block producer/searcher to extract maximum value (worse effective ETH-to-feeToken rate) up to the full `msg.value` supplied, or to be executed only once conditions are most adverse to the sender. This affects a core, permissionless entry point (`EvmHost.dispatch`/`fundRequest`, the message dispatch path referenced in scope), and the loss is borne directly by whoever is paying the cross-chain message fee — a fund-loss issue on a widely reachable unprivileged path, consistent with a Medium-severity finding.

### Likelihood Explanation
Any account with mempool visibility (validator, builder, or a colluding searcher) can trivially reorder/delay inclusion of any `dispatch`/`fundRequest` call carrying `msg.value`; this requires no special privilege and happens on ordinary user-initiated dispatch calls, so likelihood is high whenever such calls are made with native-token fee payment on non-instant-inclusion chains.

### Recommendation
Do not compute the swap deadline as `block.timestamp` inside the contract. Accept an explicit `deadline` (or max-staleness) parameter from the caller in `DispatchPost`/`DispatchGet`/`fundRequest`, validate it is in the future relative to the calling transaction's submission context, and forward that caller-supplied value to `IUniswapV2Router02` so a transaction that sits too long in the mempool genuinely reverts instead of always passing the deadline check.

### Proof of Concept
1. A user calls `EvmHost.dispatch(DispatchPost)` with `msg.value` sized to just cover the current expected fee-token price via `swapETHForExactTokens`.
2. A validator/searcher observes the pending transaction and withholds it while the ETH/feeToken price moves unfavorably (up to the bound of `msg.value`).
3. The validator includes the transaction once price is worst for the user; since `deadline == block.timestamp` at execution, `require(deadline >= block.timestamp)` in the Uniswap router trivially passes regardless of how long the tx was held.
4. The user pays the maximum attainable price for the fee token (bounded only by their own `msg.value`), which a genuine time-bound deadline would have prevented by causing a revert once the quote went stale, instead of silently executing at the worst rate within range.

```text
    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }
```
