### Title
Unchecked ERC20 return-data in `IntentGatewayV2.withdraw`/`SweepDust` lets a non-reverting-false-returning token mark escrow released without paying the beneficiary - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2` (Tron variant) pays out escrowed ERC20 tokens with raw `.call()` invocations of `transfer` instead of `SafeERC20.safeTransfer`, and only checks the low-level `success` flag, never decoding/validating the returned `bool` payload.

### Finding Description
In `withdraw()` and the `SweepDust` branch of `onAccept()`, token payouts are performed as:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 
and identically for dust sweeps: [2](#0-1) 

This only checks that the call did not revert; it never inspects `returnData` to confirm the token itself signaled success via the ERC20 `bool` return. Per ERC20 semantics, a compliant token is permitted to `return false` on a failed transfer instead of reverting. With this pattern, such a `false` return is indistinguishable from success — `success` is `true` (the call didn't revert) even though the beneficiary received nothing. Immediately after, the code decrements `_orders[body.commitment][token] -= amount`, marks `_filled[commitment] = beneficiary`, and emits `EscrowReleased`/`DustSwept`, permanently closing out the escrow accounting.

This directly parallels the referenced M-08 finding: low-level calls whose result is not fully validated, letting the caller believe a transfer succeeded when it did not. Here the rest of the codebase (e.g. `EvmHost.dispatchIncoming`, `CallDispatcher.dispatch`, `IntentsBase`) is careful to check `success`, but none of these payout sites validate the ERC20 return payload the way `SafeERC20.safeTransfer` does.

### Impact Explanation
If the escrowed/fee token ever returns `false` on failure (rather than reverting) — a legitimate ERC20 pattern — the beneficiary receives no tokens while the contract's internal escrow ledger is decremented and the order is marked filled/released. The tokens remain stuck in the `IntentGatewayV2` contract with no accounting entry left to reclaim them, and the beneficiary has no path to re-trigger the transfer (the order/commitment is already marked as `_filled`). This is a permanent loss/freezing of user funds triggered purely by a relayed cross-chain message (`RedeemEscrow`, `RefundEscrow`, `SweepDust`), reachable by any relayer delivering a validly-proven message — no privileged role required.

### Likelihood Explanation
Likelihood depends on the specific ERC20 token configured for a given deployment behaving this way (return-false-on-failure rather than revert). This is a known, sanctioned ERC20 pattern (not just non-standard tokens), so it is a realistic risk for any token whose implementation follows it, especially given this is the Tron contract variant where token implementations commonly diverge from strict OZ ERC20 semantics (which is presumably why raw `.call` was used here instead of `SafeERC20` in the first place).

### Recommendation
Decode and validate the ERC20 return payload in all three payout sites (`withdraw`'s main loop, the tx-fee redemption, and `SweepDust`), matching `SafeERC20`'s check: after `success`, additionally verify `returnData.length == 0 || abi.decode(returnData, (bool))`. If the Tron USDT-style token requires raw calls because it doesn't return a bool at all, this should be handled as a special case with an explicit allowlist/branch, not silently accepted for every token via a bare `success` check.

### Proof of Concept
1. Configure an input/output token for `IntentGatewayV2` (Tron) that implements `transfer` per spec but returns `false` on certain failures (e.g. paused/blacklisted transfers) instead of reverting.
2. A relayer delivers a `RedeemEscrow` message whose target beneficiary triggers the token's `false`-return failure path.
3. `withdraw()` executes `token.call(...)`, which returns `(true, abi.encode(false))`.
4. The `if (!success)` check passes (call didn't revert), so `_orders[commitment][token] -= amount` executes and `EscrowReleased` is emitted, while the beneficiary's balance is unchanged.
5. The escrow amount is now permanently unaccounted for and unrecoverable — the beneficiary got nothing, and the commitment is already marked filled.
