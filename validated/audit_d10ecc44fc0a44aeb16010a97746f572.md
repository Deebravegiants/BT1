## Title
Attacker can pre-create the LP-token Associated Token Account to permanently DoS `Initialize2` for a target pool - (File: `program/src/processor.rs`, `program/src/invokers.rs`)

### Summary
`process_initialize2` creates the pool creator's LP-token Associated Token Account (ATA) by invoking the standard, non-idempotent `spl_associated_token_account::instruction::create_associated_token_account` CPI. Because that ATA address is fully deterministic (derived from the creator's wallet pubkey, the pool's LP mint, and the SPL Token program) and the LP mint address is itself deterministically derivable from the public `market` account before the pool is ever initialized, any third party can permissionlessly create that exact ATA in advance. Since the CPI fails whenever the target address already holds data, the legitimate `Initialize2` transaction will always fail for that wallet/market combination, permanently blocking pool creation for that specific target.

### Finding Description
In `process_initialize2`, after computing/creating the LP mint PDA, the code creates the user's LP token account via: [1](#0-0) 

which calls `Invokers::create_ata_spl_token`: [2](#0-1) 

This wraps `spl_associated_token_account::instruction::create_associated_token_account(funding, wallet, mint, token_program)` — the classic, non-idempotent ATA-creation instruction that aborts if an account already exists at the derived address (unlike `create_associated_token_account_idempotent`).

The LP mint address (`amm_lp_mint_info`) passed into this call is derived deterministically from `program_id`, the `market` pubkey, and `LP_MINT_ASSOCIATED_SEED`: [3](#0-2) 

An OpenBook `market` account must already exist and is public before anyone calls `Initialize2` for it (a precondition documented in the README): [4](#0-3) 

Because the Associated Token Account program allows *any* funder to create the ATA for a given `(wallet, mint)` pair without the wallet owner's signature, an attacker who knows (a) the target market (hence the deterministic future LP mint address) and (b) the wallet that will call `Initialize2` (either a known/public deployer wallet, or observed via mempool front-running of the pending `Initialize2` transaction) can pre-create that exact LP-token ATA beforehand. When the legitimate `Initialize2` transaction later executes `Invokers::create_ata_spl_token`, the CPI will fail because the account already exists, aborting the whole instruction (all account creations in `process_initialize2`, including the AMM/target-orders/vault PDAs, are gated behind this same all-or-nothing instruction, so the transaction reverts).

This is the exact bug class described in the external report: use of a non-idempotent ATA-creation constraint on a deterministically-derivable address, which lets an unprivileged attacker "squat" the account ahead of time and cause a permanent instruction failure for the legitimate caller.

### Impact Explanation
This causes a permanent Denial of Service for `Initialize2` targeting a specific `(wallet, market)` pair: pool creation can never succeed for that combination because the LP mint address (bound to the market) is fixed and the ATA squat is irreversible (the account cannot be closed by anyone but its owner/authority, and the attacker owns/controls it as its authority). No funds are stolen and no already-created pool's funds are put at risk, but a project attempting to launch an AMM pool for a given market from a known wallet can be permanently blocked from doing so, which is a concrete availability impact on pool creation — matching the reported severity class (Medium).

### Likelihood Explanation
Likelihood is high for any scenario where the future creator wallet or a planned market is publicly known or can be observed pending in the mempool before confirmation (standard Solana front-running pattern), since creating an ATA is a cheap, permissionless, unprivileged operation requiring only the wallet pubkey and mint pubkey — both derivable without any special access.

### Recommendation
Replace the non-idempotent ATA creation in `Invokers::create_ata_spl_token` with the idempotent variant (`create_associated_token_account_idempotent`), or explicitly check whether the account already exists (owned by the token program with the expected mint/owner) and skip creation in that case, similar to the `owner == system_program` guard already used for the program's own PDAs in `generate_amm_associated_account`/`generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint`.

### Proof of Concept
1. Observe (or already know) that a wallet `W` intends to call `Initialize2` for `market M` on the Raydium AMM program `P`.
2. Compute `lp_mint = get_associated_address_and_bump_seed(P, M, LP_MINT_ASSOCIATED_SEED, P)` (same derivation as `program/src/processor.rs:399-408`) — this is possible before `Initialize2` is ever sent, as soon as `M` is public.
3. Compute the LP ATA address `ata = get_associated_token_address(W, lp_mint)`.
4. As any unprivileged attacker wallet, submit `spl_associated_token_account::instruction::create_associated_token_account(attacker, W, lp_mint, token_program)` before `W`'s `Initialize2` transaction lands (front-run it, or simply act ahead of time if `W` is a known/reused deployer wallet).
5. When `W`'s `Initialize2` transaction executes `Invokers::create_ata_spl_token` (`program/src/processor.rs:816-825`), the CPI fails because `ata` already exists, causing the whole `Initialize2` instruction to fail permanently for this `(W, M)` pair.
