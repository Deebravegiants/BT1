### Title
Silent u128→u64 truncation via `.as_u64()` in `SwapBaseOut` lets an attacker drain a pool's reserves while paying a near-zero input - (File: program/src/processor.rs)

### Summary
The `sendMessage` report's bug class — casting a large integer to a smaller type without validating the range — has a direct, reachable analog in the `SwapBaseOut`/`SwapBaseOut2` instruction handlers. The computed required input amount (`swap_in_after_add_fee`) is derived from a `U128` calculation and truncated with the unchecked `.as_u64()` method instead of the checked `Calculator::to_u64()` helper used elsewhere in the same file.

### Finding Description
In `process_swap_base_out` (and the duplicate `process_swap_base_out2`/v2 variant), the amount the user must pay is computed as: [3](#0-2) 

`swap_token_amount_base_out` computes `amount_in = coin * amount_out / (pc - amount_out)` (or the symmetric PC2Coin formula) in `U128` [4](#0-3) . When the attacker-chosen `swap.amount_out` is close to `total_pc_without_take_pnl` (or `total_coin_without_take_pnl`), the denominator `pc - amount_out` shrinks toward zero, causing `swap_in_before_add_fee` (and subsequently `swap_in_after_add_fee`) to blow up to values far larger than `u64::MAX`. This is a legal `U128` value (no panic from `checked_mul`/`checked_ceil_div`), but the final `.as_u64()` call at line 2191 (and 2570 in the v2 handler) silently truncates it to an arbitrary, attacker-influenceable small `u64` value instead of erroring out.

The only guard against `amount_out` being too close to the reserve is `swap.amount_out >= total_pc_without_take_pnl` (strict `>=`), which still permits `amount_out = total_pc_without_take_pnl - 1`, driving the denominator to `1` and the computed `amount_in` to a huge value that will wrap when truncated [5](#0-4) .

The truncated (small) `swap_in_after_add_fee` is then used both for the `user_source.amount < swap_in_after_add_fee` / `max_amount_in < swap_in_after_add_fee` checks and for the actual `Invokers::token_transfer` of the user's deposit — so both the sanity checks and the real fund transfer use the corrupted, wrapped value: [6](#0-5) 

Meanwhile the full, un-truncated `swap.amount_out` (near the entire pool reserve) is transferred out to the user via `Invokers::token_transfer_with_authority`: [7](#0-6) 

By contrast, other math helpers in the file consistently route through the checked `Calculator::to_u64` (e.g. `convert_out_pc_lot_size`, `convert_in_vol`, `get_max_buy_size_at_price`) [8](#0-7) , but the `SwapBaseOut` handlers bypass this and call `.as_u64()` directly on the fee-adjusted `U128` result.

### Impact Explanation
An attacker can submit a single `SwapBaseOut` transaction requesting an `amount_out` just below the full PC (or coin) reserve. The truncated `swap_in_after_add_fee` can wrap to a value far smaller than the attacker's actual token balance, letting all the slippage/insufficient-funds checks pass trivially and letting the attacker pay a negligible, wrapped-around amount while receiving nearly the entire opposite-side reserve. This is a direct theft of LP/pool funds and results in insolvent pool accounting (the AMM invariant `x*y=k` is broken because the deposited amount does not match what the math intended).

### Likelihood Explanation
This is reachable from a single, unprivileged swap transaction with attacker-chosen `amount_out` and `max_amount_in` — no special roles, no off-chain component, and it hits code paths (`SwapBaseOut`, `SwapBaseOut2`) that are part of the four core swap instructions explicitly in scope. The only precondition is choosing `amount_out` sufficiently close to the pool's current reserve to force the intermediate `U128` value above `u64::MAX`, which is trivially computable off-chain from public vault balances before submitting the transaction.

### Recommendation
Replace the unchecked `.as_u64()` truncation with the checked `Calculator::to_u64(...)` conversion (which already exists in the codebase and returns `AmmError::ConversionFailure` on overflow) at both truncation sites: [9](#0-8) [10](#0-9) 
Additionally, tighten the reserve-exhaustion guard so that `amount_out` cannot approach the reserve closely enough to make the denominator degenerate before the conversion is even attempted (e.g., enforce a minimum remaining-reserve margin, not just strict inequality).

### Proof of Concept
1. Observe a pool's `amm_pc_vault.amount` (`total_pc_without_take_pnl`), e.g. 1_000_000_000_000 (u64).
2. Submit `SwapBaseOut` with `swap_direction = Coin2PC`, `swap.amount_out = total_pc_without_take_pnl - 1`, and `swap.max_amount_in = u64::MAX`.
3. `swap_token_amount_base_out` computes `amount_in = total_coin_without_take_pnl * amount_out / 1`, i.e. roughly `total_coin_without_take_pnl` (potentially already exceeding `u64::MAX` for large pools, or ballooning further after the fee-adjustment multiplication by `swap_fee_denominator`) — see the formula at [3](#0-2) .
4. The `.as_u64()` call truncates this value to `computed_value mod 2^64`, which can be an arbitrarily small number depending on the exact reserve figures the attacker picks.
5. Checks at lines 2202/2205 pass because the truncated value is small.
6. The attacker's token account is only debited the small truncated amount at line 2223, while the AMM's PC vault sends out `swap.amount_out` (≈ the entire PC reserve) to the attacker at line 2233 — resulting in the AMM being drained for a fraction of its true value.

```rust
    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
```
