### Title
Pooled shielded balances for rebasing/elastic-supply ERC20 tokens desynchronize from real contract balance, permanently freezing other users' UTXOs - (File: contracts/Hinkal.sol, contracts/Transferer.sol)

### Summary
Hinkal is a fully permissionless multi-asset shielded pool: any address can be supplied as `circomData.erc20TokenAddresses[i]`, with the only on-chain constraint being that addresses in the same call are distinct [1](#0-0)  and that array lengths line up with `dimensions.tokenNumber` [2](#0-1) . There is no allowlist rejecting non-standard tokens such as rebasing/elastic-supply tokens (e.g. AMPL-style tokens whose `balanceOf` changes for every holder without any `transfer` call). Because all deposits of the same token address share one pooled `balanceOf(address(hinkal))`, and each shielded UTXO permanently records a fixed `amount` field that is never revised, a negative rebase of a pooled token can reduce the real contract balance below the sum of outstanding UTXO claims, permanently locking the last withdrawer(s) out of funds that were legitimately committed and nullifier-proven.

### Finding Description
Every deposit/withdrawal in `transact()` is checked only against balances measured live within the same atomic transaction: [3](#0-2) 

`oldBalances`/`newBalances` come from `getBalancesForArray`, which simply calls `IERC20.balanceOf(address(this))` [4](#0-3) . This atomic-balance check correctly prevents a single transaction from being cheated, but it provides no guarantee across transactions that the pooled `balanceOf` for a token stays equal to the sum of every outstanding UTXO `amount` for that token, because:

- The UTXO commitment's `amount` is fixed at creation time and is never adjusted for balance changes that occur outside of Hinkal-mediated transfers (see `OriginalCommitmentCalculator`/`amount` usage in `MainEVMCircuit.circom`, lines 116, 154-164).
- There is no per-token supported-type restriction (unlike Axelar ITS's `TokenManagerType`), so a rebasing/elastic-supply ERC20 can be deposited freely by any unprivileged EOA via `_internalTransact`/`transferERC20TokenFromOrCheckETH` [5](#0-4) .
- Withdrawals pay out exactly `sumAbs` (the prover-committed `amountChanges[i]`) via `transferERC20TokenOrETH` [6](#0-5) , which relies on the pool actually holding that many tokens.

If the pooled token undergoes a negative rebase (its `balanceOf(hinkal)` decreases automatically, without any `transfer`), the real balance can fall below the sum of all valid, nullifier-provable UTXOs for that token. The first withdrawers to submit valid proofs successfully drain the (now insufficient) real balance; the remaining, equally valid UTXOs can never be redeemed in full because their withdrawal calls will revert inside `transferERC20TokenOrETH` → `IERC20.transfer`, as the contract no longer holds enough tokens. Unlike the Axelar analog, there is no ledger with a `checked_sub` that reverts gracefully and preserves the invariant "reject if insufficient" cleanly per-message — here, insolvency is silent until the exact moment a legitimate holder tries to exit, at which point their fully valid proof and nullifier are correct, but the transfer itself cannot be completed and never can be completed unless a future positive rebase happens to restore the deficit.

This breaks the intended equality that the balance-difference check in `transact()` is meant to enforce over the lifetime of the pool: `sum(live UTXO.amount for token T)` should always be redeemable against `balanceOf(hinkal, T)`, but the contract only verifies this per-transaction, not as an invariant of the shared pool across time.

### Impact Explanation
This is a permanent freezing of legitimately committed user funds: a shielded UTXO with a valid proof, valid nullifier, and valid Merkle root becomes permanently unspendable through no fault of its owner, purely because another pooled depositor's token later underwent a negative rebase and other users withdrew first. This is not a mistake by the affected user (they did nothing wrong — they deposited a token the protocol permissionlessly accepted), and it directly maps to the "permanent freezing of user funds" and "value moved... but not counted in the balance equation" analog categories.

### Likelihood Explanation
Likelihood depends on end users or integrators listing an elastic-supply/rebasing token for use with Hinkal (there is no on-chain allowlist preventing it), which is a realistic occurrence given the protocol's explicit design goal of supporting "any" ERC20 the same way the original Axelar report's target did. Once such a token is in use, a single negative rebase event (common for elastic-supply tokens by design) is sufficient to trigger the shortfall; no attacker action, admin key, or malicious relayer is required — ordinary sequential withdrawals by unprivileged EOAs deterministically produce the freeze for the last withdrawer(s).

### Recommendation
- Explicitly reject rebasing/elastic-supply tokens at the protocol layer (e.g., via a maintained per-token type similar to Axelar's `TokenManagerType`), or
- For any token type where `balanceOf` can change outside of transfers, track and reconcile the pooled balance against total outstanding UTXO amount before allowing further deposits/withdrawals of that token, reverting (rather than allowing) any transaction that would leave the pool under-collateralized relative to already-committed UTXOs.

### Proof of Concept
1. Users A and B each deposit 100 units of a negatively-rebasing token `R` into Hinkal via `transact()`; each receives a UTXO with `amount = 100` [5](#0-4) . Contract's `balanceOf(R)` = 200.
2. Token `R` undergoes a negative rebase; `balanceOf(hinkal, R)` autonomously drops to 150 (no transfer call, no Hinkal logic invoked).
3. User A submits a valid withdrawal proof for their UTXO of `amount = 100`. `_internalTransact` calls `transferERC20TokenOrETH(R, A, 100)` [6](#0-5) , succeeding because 150 ≥ 100. Contract balance now 50.
4. User B, holding an equally valid UTXO of `amount = 100` with a correct nullifier and Merkle proof, submits their withdrawal. `transferERC20TokenOrETH(R, B, 100)` reverts because the contract only holds 50 units of `R`.
5. User B's funds are now permanently unspendable unless token `R` later rebases positively enough to cover the shortfall — an event outside Hinkal's or User B's control.

    function getERC20OrETHBalance(
        address _erc20TokenAddress
    ) internal view returns (uint256) {
        if (_erc20TokenAddress == address(0)) {
            return address(this).balance;
        } else {
            IERC20 outToken = IERC20(_erc20TokenAddress);
            return outToken.balanceOf(address(this));
        }
    }

    function getBalancesForArrayMemory(
        address[] memory erc20TokenAddresses
    ) internal view returns (uint256[] memory balances) {
        balances = new uint256[](erc20TokenAddresses.length);
        for (uint64 i; i < erc20TokenAddresses.length; i++) {
            balances[i] = getERC20OrETHBalance(erc20TokenAddresses[i]);
