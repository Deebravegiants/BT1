### Title
Webhook Shop-Domain Spoofing via HMAC Not Binding to `shop-domain` Header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a specific shop once the HMAC check passes, but the HMAC signature only covers the raw request body — it never binds the `shop-domain` (or `topic`) header. Any party who can obtain one valid `(body, hmac)` pair signed with the app's shared `client_secret` can replay it with an arbitrary `shop-domain` header and have the library accept it as a legitimate webhook "from" a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers and are excluded from the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then unconditionally trusts `request.shop` and `request.topic` to build the metadata handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the supplied `hmac` — for webhooks this is `HMAC(secret, raw_body)`, with no header material folded in: [4](#0-3) 

The identity binding that should hold is:

`hmac_valid(secret, request) == true` ⇒ `request.shop == <the shop Shopify actually sent this webhook for>`

What the code actually enforces is only:

`HMAC(secret, raw_body) == received_hmac`

which is independent of `shop`. Because the `client_secret`/`api_secret_key` is the same for every shop that has installed the app (it identifies the *app*, not the *tenant*), any user who installs the public app on their own store receives genuinely-signed webhooks — i.e., a valid `(body, hmac)` pair for a body they fully control (e.g. by editing a product to control the `orders/create` / `products/update` payload). That user can then POST this valid `(body, hmac)` pair directly to the app's public webhook endpoint while substituting `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`). `Utils::HmacValidator.validate` still returns `true` because it only re-derives the HMAC from `raw_body`, and the docs explicitly claim `Registry.process` "will verify the request did indeed come from Shopify," which is not true for the shop/topic identity — only for the body's integrity.

The app's handler then receives `WebhookMetadata` claiming to be from the victim shop, with attacker-controlled body content, and will act on it as if it were genuine data belonging to the victim tenant.

### Impact Explanation
This breaks the cross-tenant identity boundary the webhook handler relies on: an unprivileged attacker (any developer who can install the target public app on their own store, or capture one genuine webhook) can forge webhook events that host apps will process as belonging to an arbitrary victim shop, with attacker-chosen body contents and topic. Depending on how the host app's `WebhookHandler` uses `data.shop`/`data.body` (e.g., updating local tenant records, triggering uninstall/GDPR cleanup flows for `shop.redact` / `app.uninstalled`, writing order/customer data under the wrong tenant), this can cause cross-tenant data corruption or trigger privileged per-tenant actions for a shop the attacker doesn't own — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires: (1) the ability to obtain one valid `(body, hmac)` pair signed with the app's `client_secret` — trivially achievable by installing the (public) app on an attacker-owned store and capturing any real webhook, and (2) network access to the app's public webhook endpoint, which is a normal input Shopify itself posts to and is therefore internet-reachable by design. No access token, `api_secret_key`, or victim credentials are needed. This is straightforward for any developer familiar with the app.

### Recommendation
Bind the shop/topic identity into the HMAC verification, or otherwise cryptographically or transport-level tie the claimed `shop-domain` header to the signed body — for example, include the shop domain in `to_signable_string`, or require deliveries only via mutually-authenticated channels (mTLS/IP allow-list to Shopify's published webhook IP ranges) before trusting header-derived `shop`/`topic` values, consistent with the pattern where the queried commit data must match the queried height rather than being retrieved independently of it.

### Proof of Concept
1. Install the target public Shopify app on an attacker-owned development store; enable an `orders/create` webhook.
2. Trigger an order creation to receive a genuine webhook delivery with body `B` and header `x-shopify-hmac-sha256: H`, where `H = Base64(HMAC-SHA256(client_secret, B))`.
3. Replay the captured request directly to the app's public webhook endpoint, keeping `B` and `H` unchanged but replacing the shop header:
```
POST /callback/orders/create HTTP/1.1
Host: victim-app.example.com
x-shopify-topic: orders/create
x-shopify-hmac-sha256: H
x-shopify-shop-domain: victim-shop.myshopify.com
Content-Type: application/json

B
```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes `HMAC(client_secret, B)` and matches `H`, so validation succeeds.
5. The app's `WebhookHandler#handle` is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker-controlled>, topic: "orders/create", ...)`, even though the data never originated from `victim-shop`.
