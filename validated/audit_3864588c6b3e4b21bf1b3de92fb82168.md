Audit Report

## Title
Gas-ratio starvation of nested EVM calls under large `deposit_limit` is only partially fixed by the `u64::MAX` cap on `remaining_gas` — non-maximal gas requests still round to ~0 weight - (File: `substrate/frame/revive/src/metering/math.rs`)

## Summary
`substrate_execution::new_nested_meter` computes `ratio = gas_limit / remaining_gas` to proportionally split leftover weight/deposit into a nested EVM call frame, where `remaining_gas` is the ethereum-gas-equivalent of the caller's remaining weight and storage deposit. [1](#0-0)  The existing fix caps `remaining_gas` to `u64::MAX` to prevent the ratio from collapsing to near-zero when `deposit_left` is enormous, but this cap only fully corrects the case where the nested call requests `gas == u64::MAX`; for any smaller/realistic requested `gas`, the ratio `gas / u64::MAX` remains vanishingly small and still truncates the derived nested `weight_limit` to zero via `saturating_mul_int`. [2](#0-1) 

## Finding Description
`deposit_left` is converted to a gas-equivalent through `SignedGas::from_adjusted_deposit_charge`, which scales linearly with the deposit amount and has no independent upper bound tied to `u64` semantics. [3](#0-2)  If a caller sets a very large `storage_deposit_limit`, `deposit_gas_left` can be many orders of magnitude larger than any realistic `weight_gas_left`. The sum is capped with `remaining_gas.min(u64::MAX)`, and `gas_limit = remaining_gas.min(*gas)`, then `ratio = gas_limit / remaining_gas`. [4](#0-3)  When the caller-provided `gas` is small relative to `u64::MAX` (e.g. `100_000` vs `~1.8e19`), the ratio is on the order of `5×10⁻¹⁵`, which when multiplied into `weight_left.ref_time()`/`proof_size()` via `FixedU128::saturating_mul_int` truncates to `0` for any realistically-sized `weight_left`. [2](#0-1)  The existing regression test only exercises the `gas == u64::MAX` boundary case and asserts `nested_weight_left.eq(&weight_left_before)`, i.e., it validates the fix works when the ratio collapses to 1, but does not test smaller, more common gas values. [5](#0-4)  This nested-meter path is used by the Substrate-native `call`/`instantiate` dispatch path (`TransactionLimits::WeightAndDeposit`), and is reached whenever an EVM contract executes `CALL`/`STATICCALL`/`DELEGATECALL` with a caller-chosen gas stipend via `CallResources::from_ethereum_gas`. [6](#0-5) 

## Impact Explanation
This is a real, but narrower, residual of the underlying design flaw already acknowledged and partially patched by the codebase's own comment ("Without this, large deposit_left … causes ratio ≈ 0, giving nested calls almost no weight"). [7](#0-6)  The impact is a spurious `OutOfGas` for nested calls when the outer caller supplies a large `deposit_limit` and the inner contract forwards a moderate, explicit gas amount to a sub-call — a standard Solidity gas-forwarding pattern. This is a self-inflicted denial-of-service against the caller's own transaction (the contract call fails/traps), not a cross-account fund-loss or consensus-safety bug; it degrades usability/availability of contract calls under a specific combination of parameters rather than breaking an accounting or security invariant of the pallet.

## Likelihood Explanation
Reproducible deterministically and requires no special privilege — any signed account can call `pallet_revive::Pallet::call`/`instantiate` with a large `storage_deposit_limit` against a contract using fixed, non-maximal gas sub-calls. The scaling math in the report (`ratio ≈ 5.4e-15` for `gas=100_000` against `remaining_gas=u64::MAX`) is arithmetically consistent with the source code reviewed.

## Recommendation
Avoid deriving the nested weight limit via a ratio against an artificially capped denominator. Instead, directly bound the requested gas-to-weight/deposit conversion by the true convertible capacity (e.g., compute weight/deposit portions from `gas_limit` directly using the known per-unit gas-to-weight and gas-to-deposit conversion rates, clamped by `weight_left`/`deposit_left`, rather than scaling by `gas_limit / remaining_gas` where `remaining_gas` has been artificially truncated).

## Proof of Concept
The reported PoC (extending `substrate_nesting_with_large_deposit_and_max_gas_request` to request a moderate `gas` value such as `100_000` under a large `deposit_limit`, and asserting `nested_weight_left.ref_time() > 0`) follows directly from the code path reviewed and should reproduce the described truncation to zero weight, given `FixedU128::saturating_mul_int`'s behavior and the magnitudes involved.

	/// Transform a storage deposit into a gas value. The value will be adjusted by dividing it
	/// through the next fee multiplier. Charges are treated as a positive numbers and refunds as
	/// negative numbers.
	pub fn from_adjusted_deposit_charge(deposit: &StorageDeposit<BalanceOf<T>>) -> Self {
		let multiplier = T::FeeInfo::next_fee_multiplier_reciprocal();

		match deposit {
			StorageDeposit::Charge(amount) => Positive(multiplier.saturating_mul_int(*amount)),
			StorageDeposit::Refund(amount) => {
				Self::safe_new_negative(multiplier.saturating_mul_int(*amount))
			},
		}
	}

/// Regression test for proxy contract delegatecall with large deposit limits.
///
/// When deposit_left is very large (u128::MAX in production), remaining_gas becomes huge,
/// causing ratio = gas_limit / remaining_gas ≈ 0. This resulted in nested calls receiving
/// almost no weight. The fix caps remaining_gas to u64::MAX since Ethereum gas is u64.
#[test]
fn substrate_nesting_with_large_deposit_and_max_gas_request() {
	use super::math::substrate_execution;

	ExtBuilder::default()
		.with_next_fee_multiplier(FixedU128::from_rational(1, 5))
		.build()
		.execute_with(|| {
			let weight_limit = Weight::from_parts(1_000_000_000, 10_000);
			let deposit_limit: u128 = u64::MAX as _;

			let mut root_meter =
				substrate_execution::new_root::<Test>(weight_limit, deposit_limit).unwrap();

			root_meter.charge_weight_token(TestToken(1000, 100)).unwrap();
			root_meter.charge_deposit(&StorageDeposit::Charge(1000)).unwrap();

			let weight_left_before = root_meter.weight_left().unwrap();
			let nested = root_meter
				.new_nested(&CallResources::Ethereum { gas: u64::MAX as _, add_stipend: false })
				.unwrap();

			let nested_weight_left = nested.weight_left().unwrap();
			assert!(nested_weight_left.eq(&weight_left_before));
		});
