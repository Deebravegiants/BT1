### Title
Unmetered `handle_unsigned` ISMP message processing during mempool validation enables computational-cost Denial of Service - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic lets any unprivileged relayer submit an arbitrary batch of ISMP messages (`Vec<Message>`) containing unbounded-size fields — `PostRequest.body: Vec<u8>`, `RequestMessage.requests: Vec<PostRequest>`, `GetRequest.keys: Vec<Vec<u8>>`, and MMR/trie proof vectors — for free, unsigned execution [1](#0-0) . Critically, `ValidateUnsigned::validate_unsigned` fully *executes* the message batch (`Self::execute(messages.clone())`) as part of transaction-pool admission — i.e., every full node on the network runs full proof verification and dispatch logic on a gossiped, unsigned transaction before it is even included in a block, and before any weight/fee accounting applies [2](#0-1) . This mirrors the reported bug class in imartinez/privategpt (CVE-2024-12063): an attacker-controlled, unbounded-size field is processed by the server before any resource/size validation, exhausting server (here, node/validator) compute.

### Finding Description
`handle_unsigned` is declared with a fixed weight `Weight::from_parts(300_000_000, 0)` regardless of the actual size or content of the submitted `messages: Vec<Message>` [3](#0-2) [4](#0-3) . This static weight is only "overridden by the FeeHandler" after execution completes — it does not gate execution up front.

The actual per-message cost is proportional to attacker-controlled inputs with no length caps found in the searched code:
- `PostRequest.body: Vec<u8>` and `DispatchPost.body: Vec<u8>` — no `BoundedVec`/max-length enforcement [5](#0-4) .
- `RequestMessage.requests: Vec<PostRequest>` and `GetRequest.keys: Vec<Vec<u8>>` — unbounded batch sizes [6](#0-5) [7](#0-6) .
- `HandlerV2.handlePostRequests`/`handleGetResponses` on the EVM side loop over `request.requests`/`message.responses` with no length bound, running an MMR multiproof verification whose cost scales with leaf count [8](#0-7) [9](#0-8) .

Because `validate_unsigned` performs the *complete* `execute()` path (proof verification, trie/state-proof reads for every `GET` key, module callback dispatch) purely to decide pool admission, and this validation runs on every peer that receives the gossiped transaction, an attacker can craft a single unsigned `handle_unsigned` call with a very large `requests`/`keys`/`body` payload (bounded only by the runtime's generic max extrinsic/block length, not by any ISMP-specific limit) to force disproportionate CPU/verification work on every full node in the network relative to the fixed 300_000_000 weight units charged. Codebase evidence shows the project is aware of and has already patched this exact bug class elsewhere: `pallet-call-decompressor::decompress` was fixed specifically because "the unsigned `validate_unsigned` mempool path called `decompress` directly with no bound, so a fee-less attacker could claim `encoded_call_size = u32::MAX` and have a tiny zstd bomb expanded to gigabytes during transaction-pool validation, before any size check" [10](#0-9) . No equivalent up-front size gate exists for `pallet_ismp::handle_unsigned`'s message batch/body/keys before `Self::execute` runs in `validate_unsigned`.

### Impact Explanation
An unprivileged relayer (anyone able to submit an unsigned extrinsic / gossip a transaction) can degrade or stall validator/full-node performance across the network by repeatedly broadcasting oversized, otherwise-well-formed `handle_unsigned` messages that are expensive to validate (large request/key/body counts) but cheap to construct, since the transaction is free and the declared weight does not reflect true cost. This is a route-unable-to-deliver-messages / network-availability impact matching the "Medium/High, no low/resource-only" bar for this scan, and directly analogous to the reachable-path categories called out (pallet-ismp `handle_unsigned`, message encoding, HandlerV2 dispatch).

### Likelihood Explanation
Likelihood is credible but not fully confirmed from static review alone: exploitation depends on (a) the actual `frame_system::BlockLength`/extrinsic size limits configured in `parachain/runtimes/{gargantua,nexus}` (found but not read in depth) still allowing multi-MB unsigned calls, and (b) whether `validate_unsigned` in production nodes is invoked per-gossip-peer (typical Substrate behavior) rather than only once. I was not able to fully trace the concrete `BlockLength`/`BlockWeights` values configured for Gargantua/Nexus runtimes within the available iterations, so the precise achievable payload size (and thus severity magnitude) is unconfirmed.

### Recommendation
- Add explicit, cheap up-front bounds checks (before calling `execute`) in `handle_unsigned`'s `validate_unsigned` on: number of messages in the batch, number of requests/leaves/keys per message, and the byte length of each `body`/`context`/key, similar to the fix already applied in `pallet-call-decompressor::decompress`.
- Make the declared `#[pallet::weight]` for `handle_unsigned` a function of the actual message batch size (counts and byte lengths) rather than a fixed constant, so block-weight accounting reflects true cost.
- Consider a lightweight pre-check (e.g., total encoded length threshold) executed prior to full proof verification in `validate_unsigned`, so obviously-oversized submissions are rejected without running MMR/trie verification.

### Proof of Concept
Conceptual (not executed): an attacker submits an unsigned `pallet_ismp::Call::handle_unsigned` extrinsic containing a `Message::Request(RequestMessage { requests, proof, signer })` where `requests` contains the maximum number of `PostRequest` entries permitted by the runtime's extrinsic/block length limit, each with a large `body: Vec<u8>`, and/or a `Message::Response` with a `GetRequestMessage` containing many `keys`. Because `ValidateUnsigned::validate_unsigned` calls `Self::execute(messages.clone())` directly [11](#0-10) , every node receiving this gossiped transaction performs full request validation/dispatch (`handlers::request::handle`, `handlers::response::handle`) — including per-request checks and, if using `HandlerV2` on the EVM side, MMR multiproof verification over the whole leaf set [12](#0-11)  — at a cost far exceeding the fixed 300_000_000 weight units the call is charged, and at zero cost to the attacker since the transaction executes for free.
