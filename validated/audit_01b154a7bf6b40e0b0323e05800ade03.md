Chainlink's debug/profiling routes mirror Bolt's `_profiler` access-control flaw: they require *authentication* but not any *role* check, so any authenticated user — including the lowest-privilege `view` role — can reach sensitive debug/profiling data intended for operators/admins.### Title
Sensitive debug/profiling endpoints (`/v2/debug/pprof/*`, `/debug/vars`) lack role-based access control, allowing any authenticated low-privilege user to access them - (File: core/web/router.go)

### Summary
Chainlink's web router registers debug/profiling routes (`expvar` at `/debug/vars` and Go `net/http/pprof` handlers at `/v2/debug/pprof/*`) behind only the generic `Authenticate` middleware, with no `RequiresEditRole`/`RequiresRunRole`/`RequiresAdminRole` wrapper. This mirrors the Bolt CVE-2017-16754 bug class (`_profiler` routes reachable without proper access restriction) — the difference here is Chainlink requires *authentication* but not the *appropriate privilege level*, so the lowest-privileged `view`-role user can reach operator/admin-grade debug tooling.

### Finding Description
`debugRoutes` mounts `/debug/vars` (Go `expvar`) with only session authentication, no role check: [1](#0-0) 

`metricRoutes`, which mounts the full `net/http/pprof` handler set (`/`, `/cmdline`, `/profile`, `/symbol`, `/trace`, `/allocs`, `/block`, `/goroutine`, `/heap`, `/mutex`, `/threadcreate`), is called as `metricRoutes(authv2)`: [2](#0-1) [3](#0-2) 

`authv2` itself is only wrapped in the generic `Authenticate` middleware (token or session), not in any role check: [4](#0-3) 

Compare this to every other sensitive admin-adjacent route in the same block (`/users`, `/keys/*`, `/transfers/*`), which are explicitly wrapped with `auth.RequiresAdminRole`, `auth.RequiresEditRole`, or `auth.RequiresRunRole`: [5](#0-4) [6](#0-5) 

The role-check helpers exist and are the standard enforcement mechanism (`RequiresRunRole`, `RequiresEditRole`, `RequiresAdminRole`), confirming they were simply omitted for the debug/pprof group: [7](#0-6) 

Further, the project's own RBAC regression test suite (`routesRolesMap` in `auth_test.go`), which enumerates every route and its minimum required role, does not include `/v2/debug/pprof/*` or `/debug/vars` at all — meaning there is no automated coverage verifying these are properly role-restricted: [8](#0-7) 

### Impact Explanation
Any authenticated node UI/API user regardless of role — including a `view`-only account meant to have read-only, non-sensitive access — can pull full goroutine stack dumps, heap profiles, CPU profiles, and `cmdline`/`expvar` runtime data from the running Chainlink node. These outputs can leak internal file paths, memory addresses, goroutine stack traces (potentially exposing internal logic/state, in-flight request data, or environment details), and can be used to degrade node availability (CPU/heap/goroutine profiling under `seconds=N` consumes CPU and can be abused for a mild DoS). This is a horizontal privilege escalation: a role explicitly meant to be restricted (`view`) gets operator-grade debugging capability, which is the same "improper access control on profiler/debug endpoints" bug class as the Bolt advisory (CWE-732).

### Likelihood Explanation
High for any tenant/operator who legitimately holds a low-privilege API credential or session (e.g., `view` role users, which Chainlink explicitly supports as a restricted tier). No exploit is required beyond a normal authenticated HTTP request to `/v2/debug/pprof/heap`, `/v2/debug/pprof/goroutine?debug=2`, or `/debug/vars` — these are exact, unmodified stdlib debug endpoints, well known and trivially enumerable.

### Recommendation
Wrap the debug/pprof route groups in `auth.RequiresAdminRole` (or at minimum `RequiresEditRole`) exactly as done for other sensitive routes, e.g.:
```go
pprofGroup.GET("/heap", auth.RequiresAdminRole(ginHandlerFromHTTPFunc(pprof.Handler("heap").ServeHTTP)))
```
and similarly gate `/debug/vars`. Add corresponding entries to `routesRolesMap` in `auth_test.go` so RBAC regression tests cover these routes going forward.

### Proof of Concept
1. Create/obtain a Chainlink API user with `view` role (lowest privilege) via `/v2/users` (admin-only) or standard onboarding.
2. Authenticate as that `view` user (session cookie or API token).
3. Issue: `GET /v2/debug/pprof/goroutine?debug=2` or `GET /debug/vars`.
4. Observe HTTP 200 with full goroutine dump / runtime expvar data returned — confirmed by the route wiring in `debugRoutes`/`metricRoutes` ( [9](#0-8) ), which applies only `auth.Authenticate`/session auth and never any `Requires*Role` gate, unlike sibling routes in the same file.

// RequiresRunRole extracts the user object from the context, and asserts the user's role is at least
// 'run'
func RequiresRunRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}

// RequiresAdminRole extracts the user object from the context, and asserts the user's role is 'admin'
func RequiresAdminRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role != clsessions.UserRoleAdmin {
			c.Abort()
			addForbiddenErrorHeaders(c, "admin", string(user.Role), user.Email)
			jsonAPIError(c, http.StatusForbidden, errors.New("Forbidden"))
			return
		}
		handler(c)
	}
}
