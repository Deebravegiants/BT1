### Title
Webhook `shop-domain` and `topic` identity fields are trusted by handlers without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the `shop` and `topic` fields that are handed to application webhook handlers as the tenant/routing identity come from unauthenticated HTTP headers that are never part of the signed bytes.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`: [2](#0-1) 

However, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are not included in the HMAC-signed string at all: [3](#0-2) 

After the HMAC check passes, `Registry.process` forwards `request.shop` and `request.topic` straight into `WebhookMetadata`, which the app's `WebhookHandler#handle` implementation uses to identify which merchant/tenant and which event the payload belongs to: [4](#0-3) [5](#0-4) 

The identity binding that should hold is:

`bytes covered by HMAC (raw_body only)` **≠** `bytes the app uses to attribute the webhook to a tenant (shop-domain header, topic header)`

Because the HMAC only authenticates the JSON body's integrity/origin (that it was produced with the app's `client_secret`), it says nothing about which shop or topic the header claims to be for. An attacker who is able to observe or receive one legitimately-signed webhook delivery for their own shop (a normal, unprivileged action — installing the app on their own store and receiving a webhook) can replay the identical `raw_body` + valid `hmac` pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `Utils::HmacValidator.validate` will still pass, because it only checks the body bytes, not the header bytes, and `Registry.process` will invoke the handler with the attacker-chosen `shop`.

### Impact Explanation
This breaks the shop/tenant identity binding at the point where the merchant's webhook is dispatched to application logic. Depending on how the host application's `WebhookHandler#handle` implementation uses `data.shop` (e.g. to look up which merchant's data to update, to key a mailbox/notification, or to select a session/access token to act with), an attacker can cause the app to process and record webhook content under an arbitrary target shop domain of their choosing — i.e., cross-tenant data injection/confusion using only a valid HMAC obtained from their own, legitimately-installed shop. This matches the Critical "cross-tenant access" impact category, since the gem itself provides no verification that the claimed `shop`/`topic` headers correspond to the entity that produced the signed body.

### Likelihood Explanation
Requires only an unprivileged actor who has installed the app on a shop they control (or has otherwise observed one valid webhook delivery) and can freely craft raw HTTP requests with arbitrary headers to the app's public webhook endpoint. No access token, `client_secret`, or privileged credential is needed — the attacker reuses a body+hmac pair they legitimately received. The success of the attack depends on the host application actually keying tenant-specific behavior off `WebhookMetadata#shop`/`#topic` without independent verification, which is the intended and documented usage pattern of this API (`data.shop` is the only shop-identifying field the library exposes to handlers).

### Recommendation
Include `shop`, `topic`, and other identity-bearing headers (or a `shop`-scoped registration lookup) in the HMAC-signable string, or, alternatively, cross-check `request.shop` against the recipient path/session context the webhook was registered under before invoking the handler, so headers used for tenant routing are within the cryptographically verified bytes rather than trusted as unauthenticated metadata.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the raw POST body and the valid `X-Shopify-Hmac-Sha256` header Shopify computed with the app's real `client_secret`.
2. Attacker resends the exact same raw body and HMAC header to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` and/or the topic header.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body`: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` where `shop` is the attacker-supplied `victim-shop.myshopify.com`, and the app processes/attributes the payload to the wrong tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
