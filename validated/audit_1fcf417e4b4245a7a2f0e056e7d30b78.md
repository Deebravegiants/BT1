### Title
Unspent `msg.value` is never refunded or validated in `IntentGatewayV2.placeOrder` (Tron) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron variant of `IntentGatewayV2`, `placeOrder` is `payable` and accepts native token (`msg.value`) alongside ERC20 order inputs and/or fee payments, but unlike the canonical EVM implementation, it never refunds or validates leftover `msg.value` after escrowing inputs and collecting fees. This mirrors the reported OpenQ class of bug where a `msg.value`-accepting function that is meant to fund ERC20 assets doesn't check/zero-out unused native value, causing users to permanently lose attached native tokens.

### Finding Description
`placeOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 338–506) is declared `payable`. It tracks a local `msgValue` variable that is decremented as native-token inputs (`token == address(0)`) are consumed for predispatch assets (lines 394-411), regular inputs (lines 450-469), and fee-token swaps via Uniswap (lines 471-488). However, at no point after these deductions does the function check that the remaining `msgValue` is zero, nor does it forward/refund any leftover amount to `msg.sender`.

This is in stark contrast to the canonical EVM implementation `evm/src/apps/IntentGatewayV2.sol`, which explicitly performs a refund at the end of `placeOrder`: [1](#0-0) 

The Tron version has no equivalent logic — the function simply emits the `OrderPlaced` event and returns after fee handling: [2](#0-1) 

Since all of `placeOrder`'s input-escrow branches (predispatch-assets branch and the plain-transfer branch) and the fee-collection branch only consume as much of `msgValue` as needed and never assert it is fully spent nor refund the remainder, any native token sent in excess of what the order actually requires (e.g., a user funding a purely-ERC20 order who mistakenly/inadvertently attaches `msg.value`, or overestimates the native amount needed for a partial-native order or fee swap) is retained by the contract with no accounting entry (`_orders[commitment][...]` is not credited for it) and no path to reclaim it.

### Impact Explanation
Any unspent native token sent to `placeOrder` is permanently stranded in the `IntentGatewayV2` contract balance — it is not escrowed against the order (so it can't be claimed via order fill/cancel flows) and is not refunded to the sender. This is a direct, unrecoverable loss of user funds for anyone who calls `placeOrder` with `msg.value` exceeding the exact sum consumed by native inputs/predispatch assets/fee swap, which can easily happen for ERC20-only orders funded with any accidental non-zero `msg.value`, or when `order.fees > 0` and the Uniswap swap consumes less than the full `msgValue` (the swap uses `swapETHForExactTokens`, which typically doesn't spend the entire supplied value — the main EVM version explicitly captures `amounts[0]` returned by the router and refunds the rest, while the Tron version discards this information entirely).

### Likelihood Explanation
Highly likely to be triggered in normal usage: any solver/user integrating with the Tron `IntentGatewayV2` who slightly overestimates the native value to attach to `placeOrder{value: X}(...)` — a common pattern since `swapETHForExactTokens` refunds unused ETH by design in Uniswap itself, but this contract never receives that refund back into its accounting, nor forwards it to the caller — will lose the difference. No malicious actor or special conditions are required; a single ordinary `placeOrder` call from an unprivileged user is sufficient to trigger permanent loss of the unspent value.

### Recommendation
Mirror the canonical EVM implementation: track the actual amount consumed from `msgValue` in every native-token branch (including capturing `amounts[0]` from `swapETHForExactTokens` and reducing `msgValue` by that value), and after all consumption is complete, refund any remaining `msgValue` back to `msg.sender` (as done in `evm/src/apps/IntentGatewayV2.sol` lines 394-397) instead of letting it remain in the contract unaccounted for.

### Proof of Concept
1. User calls `placeOrder{value: 1 ether}(order, graffiti)` on the Tron `IntentGatewayV2`, where `order.inputs` consists solely of an ERC20 token (no native-token input) and `order.fees == 0`.
2. In the escrow loop (lines 450-469), since `token != address(0)` for all inputs, `msgValue` is never decremented from its initial `msg.value = 1 ether`.
3. Since `order.fees == 0`, the fee-collection block (lines 471-488) is skipped entirely.
4. The function completes, emitting `OrderPlaced`, having transferred the ERC20 input from `msg.sender` normally, but the entire `1 ether` sent via `msg.value` remains in the contract's balance with no on-chain record crediting it to the user's order or any other claimable entry.
5. There is no function in the contract that allows the user to reclaim this stranded native balance — it is permanently lost. [3](#0-2) [4](#0-3)
