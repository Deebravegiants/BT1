## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies only the raw request body against the `X-Shopify-Hmac-Sha256` signature. The `shop` (tenant identity) that is handed to the app's webhook handler comes from the `X-Shopify-Shop-Domain` header, a value that is **not** part of the signed payload. This breaks the identity binding: `hmac_verified_bytes == raw_body` but `tenant_identity_used_by_handler == shop_domain_header`, and the header is never checked against anything cryptographically bound to the signature.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`. For webhooks, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely outside the HMAC's coverage: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the *body bytes* were signed by Shopify with the app's secret) and then immediately forwards the unverified `request.shop` to the handler as the tenant context: [3](#0-2) 

Because the signature never binds `shop` to the payload, two different shops delivering byte-identical webhook bodies (e.g., both shops create a product with the exact same field values, or a shop replays a webhook payload it legitimately received from Shopify for itself and resends it to the app's endpoint with a modified `X-Shopify-Shop-Domain` header) produce the exact same valid HMAC. The app has no way to detect that the `shop` header was substituted, since the check `Utils::HmacValidator.validate(request)` never inspects `shop` at all.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged holder of one shop's valid webhook (any merchant who installed the app, since they can capture their own legitimate webhook deliveries) can resend that payload with the `shop-domain` header swapped to a victim shop. Application code that trusts `WebhookMetadata#shop` for tenant-scoped side effects (looking up/updating records keyed by shop, without an independent verification) will act on the victim's account with attacker-supplied data — matching the "Critical - cross-tenant access" bucket, since the trust boundary between tenants is defined entirely by this gem's webhook processing contract.

### Likelihood Explanation
Any app installer/merchant already receives real webhooks addressed to their own shop and can capture body+HMAC pairs without any special privilege, then replay them with an altered shop header — no `api_secret_key` or access token is needed, only observation of the app's own webhook traffic for their own store, which they legitimately control.

### Recommendation
Include the shop domain (and other identity-critical headers such as `topic` and `webhook_id`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body, so that spoofing the `X-Shopify-Shop-Domain` header invalidates the signature the same way tampering with the body does.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the app and lets Shopify send it a real webhook, e.g. body `{"id":1}` with header `x-shopify-shop-domain: attacker.myshopify.com` and a valid `x-shopify-hmac-sha256`.
2. Attacker captures the raw body and HMAC header, then resends the request to the app's webhook endpoint with `x-shopify-shop-domain: victim.myshopify.com` (same body, same HMAC).
3. `Registry.process` runs `Utils::HmacValidator.validate(request)` which passes because it only checks `raw_body`: [4](#0-3) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled body content, believing it originated from Shopify for that tenant.
