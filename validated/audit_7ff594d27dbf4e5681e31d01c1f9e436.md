### Title
Webhook shop/topic identity is trusted from unauthenticated headers while only the raw body is HMAC-verified - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the webhook's authenticity by computing an HMAC over the raw request body only, but the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's webhook handler — and that many host applications use to key their tenant data — are read directly from HTTP headers that are never covered by that HMAC.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are all derived from headers via `shopify_header`, which are never part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`, i.e., the body: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC passes, then forwards the header-derived `shop`/`topic`/`webhook_id` straight into `WebhookMetadata` for the handler to act on, with no separate binding check that ties `shop` (or `topic`) to the signed body: [4](#0-3) 

This is the same class of bug as the reported issue: the artifact that is cryptographically verified (`raw_body`) is not the same as the artifact that is subsequently trusted and acted upon (`shop`, `topic`, `webhook_id` from headers). The identity binding "verified bytes == acted-upon bytes" is broken: `hmac(raw_body) == valid` is checked, but `shop header == the shop the body actually belongs to` is never checked.

### Impact Explanation
The `api_secret_key` used to compute the webhook HMAC is a single secret shared across all shops that have the app installed — it is not shop-specific. Any actor who controls a shop that has the app installed (an "unprivileged" tenant relative to other tenants) can generate a `(raw_body, valid hmac)` pair for their own shop, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers to name a different shop or topic. Because `Registry.process`/`Request` treat header-derived `shop` and `topic` as authoritative once the body HMAC checks out, this can cause the host application to process attacker-supplied webhook data under another tenant's identity — a cross-tenant data-confusion/spoofing condition, matching the report's "identity/timestamp not bound to the verified artifact" bug class.

### Likelihood Explanation
Requires only that the attacker be able to install the app on at least one shop they control (a normal, unprivileged merchant) and can reach the app's public webhook endpoint directly (webhook endpoints are typically public HTTP endpoints, and this gem performs no source-IP or mTLS pinning). No access token, `client_secret`, or privileged credential is required — only observation of one legitimate webhook delivery HMAC/body pair generated for their own shop.

### Recommendation
- Short term: Include `shop`, `topic`, and any other security-relevant metadata inside the HMAC-signed material (or otherwise cryptographically bind headers to the body), rather than trusting them purely from unauthenticated headers.
- Long term: Have `Webhooks::Registry.process` cross-check that the header-derived `shop`/`topic` are consistent with what Shopify's delivery for that specific subscription/topic would produce, and document that host apps must not treat webhook headers as authenticated unless bound to the signed payload.

### Proof of Concept
1. Install the app on Shop A (attacker-controlled). Trigger a webhook (e.g., `orders/create`) and capture the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header value `H` — both are produced using the app's single `api_secret_key`.
2. Replay a POST to the app's webhook endpoint with body `B`, header `H`, but set `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a different tenant) and/or a different `X-Shopify-Topic`.
3. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) succeeds because it only checks `HMAC(secret, B) == H`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the handler with `WebhookMetadata` built from the forged `shop`/`topic` headers, causing the host app to process/store attacker body content as if it originated from shop-b.
