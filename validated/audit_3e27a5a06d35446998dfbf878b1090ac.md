This confirms the vulnerability path: `WebhookMetadata.shop` is populated directly from `request.shop` (the `x-shopify-shop-domain` header), and `to_signable_string` for the webhook `Request` returns only `@raw_body` — the shop header is never part of the HMAC-signed material.

### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0) , while `shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header without ever being included in the signed material [2](#0-1) . `Utils::HmacValidator.validate` verifies the HMAC only against `to_signable_string` (the body) [3](#0-2) , so the equality the gem should enforce — `shop asserted in the trusted payload == shop the app acts on` — is never checked; only `body used to compute HMAC == body received` is checked, and `shop` is smuggled in unauthenticated.

### Finding Description
`Registry.process` validates the webhook solely via `Utils::HmacValidator.validate(request)` and then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the application's handler: [4](#0-3) . Since `hmac` validation only covers `@raw_body` [5](#0-4)  and `shop` is a separate, unsigned header field [2](#0-1) , any actor who can produce one valid `(body, hmac)` pair for the app's shared `api_secret_key` — for instance a merchant who has legitimately installed the app on their own store and thus receives real, correctly-signed webhook deliveries — can capture that `(body, hmac)` pair and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to any other tenant's shop domain. The HMAC check in `HmacValidator.validate` [6](#0-5)  still passes because it never inspects the `shop` value, and `WebhookMetadata.shop` [7](#0-6)  is populated from that attacker-controlled header. The gem hands this forged, "verified" `WebhookMetadata` to the application's `WebhookHandler#handle`, so any host application that (reasonably, per the documented API) trusts `data.shop` after `Registry.process` succeeds will apply the attacker's own webhook body to a victim tenant's record.

### Impact Explanation
This breaks the tenant-identity binding the HMAC check is supposed to provide: an unprivileged, already-onboarded merchant (no `api_secret_key`, no access token, no privileged account needed) can inject arbitrary webhook payloads attributed to a different, unrelated shop. Depending on the topic (e.g., `app/uninstalled`, `shop/redact`, `customers/data_request`, order/fulfillment topics), this enables cross-tenant data corruption or triggers privileged actions (like session/data deletion) against a shop the attacker does not control — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is limited by the fact that the attacker needs at least one legitimately-signed webhook delivery to reuse (trivial for any merchant who installs the app, since all shops share the same app `api_secret_key`), and needs to know/guess a victim's `myshopify.com` domain (often discoverable/public). No secret material is required. This is a realistic, unprivileged attack path reachable purely by interacting with the app as an ordinary installed merchant.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC-verified material, or otherwise cross-check the header-derived `shop` against a value derived from a trusted, per-tenant secret/session before constructing `WebhookMetadata`, so that `to_signable_string` used in `HmacValidator.validate` cannot pass for a body whose declared `shop` was altered after signing.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook: body `B`, valid header `x-shopify-hmac-sha256: HMAC(secret, B)`, and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same `B` and `hmac` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body successfully [8](#0-7) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against the HMAC, ignoring `shop` [4](#0-3) .
5. The handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed(B) ...)`, and the host application, trusting a "verified" webhook, applies attacker-controlled data to the victim tenant.
