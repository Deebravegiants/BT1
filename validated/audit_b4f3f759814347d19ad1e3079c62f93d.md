## Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) fields are not covered by the HMAC signature, allowing a malicious merchant to spoof another shop's identity on webhook delivery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC-verified webhook, but the signature only covers the raw request body. The `shop`, `topic`, `api_version`, and `webhook_id` values — all taken from HTTP headers — are never included in the signed material, yet `Registry.process` treats a validated HMAC as proof that the entire webhook, including the `shop` field, is authentic and hands it to the app's handler unchanged.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` and compares it to the `hmac` header value: [2](#0-1) 

`Registry.process` only checks that this body HMAC is valid, then immediately trusts `request.shop` (and `topic`, `api_version`, `webhook_id`, all sourced from unauthenticated headers) and forwards them to the handler: [3](#0-2) 

The identity binding that should hold is:
`HMAC(secret, signed_material) == received_hmac` should imply `signed_material` (including the shop identity) is authentic.

In this gem, `signed_material == raw_body` only, while `shop` is read from `x-shopify-shop-domain`/`shopify-shop-domain` headers with no cryptographic tie to the body: [4](#0-3) [5](#0-4) 

Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-tenant), any merchant who installs the app can legitimately trigger a webhook event on their own store and receive a body + HMAC pair that is valid for that exact body under the app's secret. That merchant, acting as an unprivileged internet user with respect to every *other* tenant of the app, can then POST that exact body and HMAC directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and optionally `topic`/`webhook_id`) with a victim shop's domain. `HmacValidator.validate` still returns `true` because it never looks at the shop header, and `Registry.process` calls the topic handler with `WebhookMetadata` claiming the event originated from the victim shop: [6](#0-5) 

The documented usage pattern instructs apps to construct `Request` from raw headers/body and rely on `Registry.process` for verification before dispatching to shop-scoped handler logic, with no warning that `shop` is unauthenticated: [7](#0-6) 

Any host app following this documented flow and using `WebhookMetadata#shop` to select which tenant's data/session/state to mutate (the expected pattern, since webhooks are inherently per-shop) is exposed to cross-tenant webhook spoofing, without ever needing the victim's credentials.

### Impact Explanation
This breaks the tenant-isolation guarantee the gem's webhook HMAC is supposed to provide: an attacker who legitimately controls one tenant (their own shop) can inject events attributed to a different, victim tenant purely by manipulating unauthenticated headers while keeping a body+HMAC pair that remains valid under the shared secret. Depending on how the host app uses `shop` (e.g., to look up sessions/access tokens or update per-shop records, which is the standard and encouraged pattern), this can lead to cross-tenant access or data corruption attributed to a shop the attacker doesn't own — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on a shop the attacker controls (the normal, unprivileged path any merchant can take), (2) triggering a webhook event to capture a valid body+HMAC pair, and (3) replaying that pair to the app's public webhook endpoint with a forged `shop-domain` header. No access to the victim's credentials, `client_secret`, or access token is needed, and no interaction with Shopify's own infrastructure is required since the endpoint is a normal internet-reachable HTTP route.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the signed material, e.g., by validating the `shop` header against session/shop records already known to be associated with the specific webhook topic/id via a server-side round trip to Shopify (as Shopify's newer verification guidance recommends), or by requiring host apps to cross-check the delivered `shop` against an independently retrieved value (e.g., re-querying the webhook subscription by `webhook_id` via the Admin API) rather than trusting the header. At minimum, document prominently that `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are NOT covered by HMAC verification and must not be used as the sole tenant-selection key without additional server-side confirmation.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a shop they own).
2. Attacker triggers a webhook (e.g. `orders/create`) and captures the raw POST: body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(app_secret, B)`.
3. Attacker sends a new POST request directly to the app's public webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body; `HmacValidator.validate` recomputes `HMAC(app_secret, B)` and it matches `H`, so validation passes (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` dispatches to the registered handler with `WebhookMetadata` reporting `shop: "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:196-200`), even though the request never originated from Shopify on behalf of that shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
