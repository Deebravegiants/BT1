### Title
Webhook `shop`/`topic`/`webhook_id` headers are trusted by handlers without being covered by the HMAC signature, enabling cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then dispatches the handler using `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers. This is the same bug class as the report: a value the business logic depends on (`shop`) is not bound by the same authentication check that is claimed to protect the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string and secure-compares it to the `hmac`/`hmac-sha256` header: [2](#0-1) 

`Registry.process` uses this single check as the sole authentication gate, then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all parsed straight from headers that are never included in the signed bytes — and forwards them to the app's handler as the identity/tenant context of the event: [3](#0-2) [4](#0-3) 

The binding that should hold is: `shop header == shop bound by HMAC`. In reality: `HMAC covers raw_body only`, while `shop (and topic/webhook_id) are read from headers outside the signed bytes`. Because the app's `api_secret_key` is a single, non-shop-specific value shared across every store that installs the app, any party who can obtain one legitimately-signed `(raw_body, hmac)` pair for the app — e.g., their own store (any merchant can freely install a public app, or use Shopify's Partner Dashboard "send test webhook" feature against their own development store) — possesses a signature that remains valid for that exact body no matter what `shop-domain`/`topic`/`webhook-id` header values are sent alongside it. This is documented as the trust boundary handlers rely on: the docs tell handler authors that `data.shop` is "The shop domain of the webhook" without noting it is unauthenticated relative to the signature: [5](#0-4) 

### Impact Explanation
An attacker who is any low-privilege merchant that can install the target app (or trigger a legitimate test webhook against their own store) can capture a valid `(raw_body, hmac-sha256)` pair issued by Shopify for their own shop, then replay it to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header naming a victim shop. `Registry.process` will pass HMAC validation (body and secret are unchanged) and hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop. Any app logic keyed on `data.shop` (e.g., updating per-shop billing/plan state, processing `shop/redact`/`customers/redact` compliance actions, writing order/customer records under the wrong tenant, or triggering uninstall/cleanup flows) is executed against the wrong tenant's data — a cross-tenant integrity/confidentiality violation satisfying the "Critical - cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires no privileged credentials, no `client_secret`, and no interception of TLS traffic — only possession of one legitimately-delivered webhook body+signature pair, which is trivially obtainable by any actor able to install the app on a free/dev store or ask Shopify (via Partner tooling) to send a sample webhook. The replay itself is a single unauthenticated HTTP POST to the app's own public webhook route. This makes the likelihood high for any app that keys authorization or data-partitioning decisions on the `shop` field surfaced by `WebhookMetadata` without independently re-verifying it (e.g., against a stored session/shop for that installation).

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the bytes that are HMAC-verified (or otherwise cryptographically bind them to the body), or have `Registry.process`/`Request` cross-check the header-derived `shop` against a shop already known to be associated with a valid, stored session/installation before dispatching to the handler. At minimum, the gem's documentation and `WebhookMetadata` API should make explicit that `shop`/`topic`/`webhook_id` are **not** covered by the HMAC and must be revalidated by the host application against its own tenant records before being trusted.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own (attacker-controlled) shop,
#    or requests a "send test webhook" from Shopify Partners for that shop.
#    They capture the raw POST body and the `x-shopify-hmac-sha256` header
#    Shopify sends — both are valid and signed with the app's single, shared
#    api_secret_key.

raw_body = '{"id":1,"note":"hi"}'          # captured from a real webhook to attacker's shop
hmac_header = "Base64(HMAC-SHA256(api_secret_key, raw_body))"  # captured, valid

# 2. Attacker replays the exact same body/hmac to the app's own public
#    webhook endpoint, but swaps the shop-domain header to a victim shop.
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac_header,      # unchanged, still matches raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# 3. Registry.process only checks HMAC over raw_body — it passes — then calls
#    the handler with shop: "victim-shop.myshopify.com", i.e. an unauthenticated,
#    attacker-controlled tenant identifier.
ShopifyAPI::Webhooks::Registry.process(request)
```
`Utils::HmacValidator.validate` succeeds because `to_signable_string` never included the shop header in the signed material: [6](#0-5) [7](#0-6)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
