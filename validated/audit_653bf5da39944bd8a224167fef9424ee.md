### Title
Division-by-zero panic in `Calculator::calc_x_power` permanently freezes pool Deposit/Withdraw once reserves normalize to zero - (File: `program/src/math.rs`)

### Summary
`Processor::calc_take_pnl`, invoked from `process_deposit`, `process_withdraw` and `process_withdrawpnl`, calls `Calculator::calc_x_power(last_x, last_y, current_x, current_y)`, which performs `checked_div(current_y).unwrap()` with no protection against `current_y == 0`. The `current_y` argument (`y1`) is `Calculator::normalize_decimal_v2(total_coin_without_take_pnl, ...)`, a value derived from live vault balances that can floor to `0` after decimal rescaling even when the underlying coin balance is a small positive dust amount. This is directly analogous to the reported `SparseDenseCwiseDiv` division-by-zero bug class: an arithmetic division routine that fails to special-case a zero divisor that is reachable with attacker-controlled/attacker-influenced inputs.

### Finding Description
`calc_x_power` is defined as: [1](#0-0) 

It is called from `Processor::calc_take_pnl` using `x1`/`y1` normalized reserve values: [2](#0-1) 

`x1`/`y1` are produced by `normalize_decimal_v2`, which floors (integer division) when rescaling from native token decimals to the pool's `sys_decimal_value`: [3](#0-2) 

`total_coin_without_take_pnl`/`total_pc_without_take_pnl` come straight from the live SPL vault balances minus already-accrued PnL, computed in every call to `calc_take_pnl` via `Deposit`, `Withdraw`, and `WithdrawPnl`: [4](#0-3) [5](#0-4) 

If a token's native decimals exceed `log10(sys_decimal_value)` (e.g., a 9-decimal SPL token against the commonly used `sys_decimal_value = 10^6`), any positive vault balance below `1000` raw units normalizes to `0`. The constant-product swap math (`swap_token_amount_base_in`) never fully drains a side of the pool to `0`, but it can leave an arbitrarily small positive remainder (down to `1` raw unit) after repeated large swaps in one direction: [6](#0-5) 

Once such a dust remainder exists, `y1` (or `x1`) normalizes to `0`, and the very next call to `Deposit`, `Withdraw`, or `WithdrawPnl` invokes `calc_x_power` with `current_y = 0` (or `current_x = 0`), triggering `checked_div(...).unwrap()` on `None`, which panics/aborts the transaction. Because this state is persisted in the vault balances (not reverted by the panicking transaction itself, since the panic occurs before any state mutation on that call, but the underlying dust condition remains), every subsequent `Deposit`/`Withdraw`/`WithdrawPnl` call against that pool will hit the identical zero-divisor and panic deterministically — permanently freezing all LP funds in that pool. The only escape is if `amm.status == WithdrawOnly`, which skips `calc_take_pnl` in `process_withdraw`, but transitioning to that status is a privileged admin operation (`SetParams`), not something an ordinary swapper/LP can trigger.

### Impact Explanation
Once the dust condition is reached, LPs cannot withdraw their liquidity via `Withdraw` (unless the pool owner separately transitions the pool to `WithdrawOnly`), and no one can `Deposit` more liquidity. This satisfies the "permanent freezing of user or LP funds" bar: an unprivileged actor (swapper) can, through a sequence of ordinary swap transactions that push one side's reserve to a decimal-normalized value of `0`, cause every future `Deposit`/`Withdraw`/`WithdrawPnl` transaction on that pool to panic and revert, locking LP capital in the pool indefinitely absent manual admin intervention.

### Likelihood Explanation
Reaching a 1-raw-unit dust balance on one side requires large, capital-intensive swaps and is easier on pools with small total liquidity and high-decimal tokens (9-decimal SPL tokens paired against a low `sys_decimal_value`), which are common in the Raydium AMM ecosystem. The attacker needs no special privileges — only the ability to submit swap transactions with attacker-chosen amounts, which is the exact threat model in scope (Swap instructions, unprivileged swapper). This makes the precondition realistically achievable, though it is more likely on low-liquidity or newly created pools rather than deep, high-liquidity ones.

### Recommendation
- In `Calculator::calc_x_power` (and the related `y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` in `calc_take_pnl`), replace `.unwrap()` on `checked_div` with proper error propagation (e.g., return `AmmError::CalcPnlError` or similar) when the divisor is `0`.
- Guard `calc_take_pnl` to explicitly check `x1 != 0 && y1 != 0` (or the pre-normalization raw balances) before invoking the pnl/x-power calculation, returning a graceful error rather than panicking.
- Consider disallowing/blocking `Deposit`/`Withdraw` pnl-taking when either normalized reserve floors to zero, and provide a permissionless fallback path (not requiring admin `WithdrawOnly`) so LPs can never be permanently locked out of a pool.

### Proof of Concept
1. Pool P is created via `Initialize2` with coin decimals = 9 and `amm.sys_decimal_value = 10^6` (a common Raydium configuration).
2. Attacker repeatedly calls `SwapBaseIn`/`SwapBaseOut` (`process_swap_base_in`/`process_swap_base_in_v2`) in the `PC2Coin` direction with large `amount_in`, driving `total_coin_without_take_pnl` down toward its dust floor (the constant-product formula guarantees it approaches but does not reach `0`, e.g., leaves `1` raw coin unit) — see `swap_token_amount_base_in` at `program/src/math.rs:289-325`.
3. Once `total_coin_without_take_pnl` (raw) is small enough that `normalize_decimal_v2(total_coin_without_take_pnl, 9, 10^6)` floors to `0` (true for any raw balance `< 1000`), any account calls `Deposit` (`process_deposit`) or `Withdraw` (`process_withdraw`).
4. `Processor::calc_take_pnl` is invoked with `y1 = 0` (`program/src/processor.rs:1160-1173` / `1726-1748`), which calls `Calculator::calc_x_power(..., current_y = y1 = 0)` (`program/src/processor.rs:199-204`), hitting `checked_div(current_y).unwrap()` in `program/src/math.rs:57-58` with `current_y = 0`, causing `Option::unwrap()` on `None` to panic and abort the transaction.
5. Every subsequent `Deposit`/`Withdraw`/`WithdrawPnl` transaction against pool P deterministically repeats this panic, permanently freezing all LP funds in the pool until a privileged admin sets the pool to `WithdrawOnly` status.

    pub fn calc_x_power(last_x: U256, last_y: U256, current_x: U256, current_y: U256) -> U256 {
        // must be use u256, because u128 may be overflow
        let x_power = last_x
            .checked_mul(last_y)
            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();
        x_power
    }

        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)

        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_out;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_out = pc - coin * pc / (coin + amount_in)

                amount_out = total_pc_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)

                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
        }
