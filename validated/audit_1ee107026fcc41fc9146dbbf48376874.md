### Title
Webhook HMAC in `Webhooks::Request` signs only the raw body, leaving `shop`, `topic`, `webhook-id`, and `api-version` headers unauthenticated and usable for cross-tenant data injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`. For `Webhooks::Request`, that method returns only `@raw_body` [1](#0-0) . The HMAC therefore certifies the body bytes only, never the `shop`, `topic`, `webhook-id`, or `api-version` values, all of which are pulled straight from HTTP headers [2](#0-1) . Those same unauthenticated fields are then handed straight to the app's handler as tenant/topic identity: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))` [3](#0-2) .

### Finding Description
The identity binding that should hold is: `HMAC(secret, signed_bytes) == received_hmac` implies `signed_bytes` (including which shop and topic the payload is attributed to) are authentic. In this gem, `signed_bytes = raw_body` only [4](#0-3) [1](#0-0) , while `shop`, `topic`, and `webhook_id` are read from headers with no cryptographic tie to the body or to each other [5](#0-4) . `HmacValidator.validate` only ever inspects `verifiable_query.hmac` and `verifiable_query.to_signable_string`, so it never touches the header-derived accessors at all [6](#0-5) .

Any actor who legitimately receives at least one genuinely signed webhook body/HMAC pair (e.g., by installing the merchant's own test/dev shop and letting Shopify deliver a real webhook to the app) can capture that `(raw_body, hmac)` pair and resend it to the app's webhook endpoint with the `shop-domain`, `topic`, and/or `webhook-id` headers swapped to arbitrary values. `Registry.process` will still call `HmacValidator.validate` successfully (body unchanged, HMAC unchanged), then dispatch using the now-attacker-controlled `topic` for handler lookup and pass the attacker-controlled `shop` straight into `WebhookMetadata` [7](#0-6) . Any host application that (as documented) uses `WebhookMetadata#shop` to decide which merchant record to update, or `WebhookMetadata#topic`/`webhook_id` to dedupe/attribute the event, is now trusting attacker-controlled tenant identity for data it believes was HMAC-verified.

### Impact Explanation
This breaks the shop-to-payload binding across tenants: a payload validated as "signed by Shopify for my app" can be relabeled to appear as if it belongs to any other shop, satisfying the "cross-tenant access" impact category — a merchant-A-originated (or attacker-forged-from-their-own-install) webhook body can be replayed and attributed to merchant B, causing the host app to apply merchant-B-labeled side effects (e.g., record updates, uninstall/deauthorization handling for `app/uninstalled`) using attacker-supplied shop identity, without needing merchant B's credentials.

### Likelihood Explanation
Medium: it requires the attacker to obtain at least one valid `(raw_body, hmac)` pair for the target app, which is trivially available to anyone who can install the app on a shop they control (a normal, unprivileged flow) and capture the resulting webhook delivery, then replay it against the app's public webhook endpoint with modified headers.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified material, or otherwise cryptographically bind them to the body before trusting them for dispatch/tenant attribution — e.g., have `Registry.process` (or the host app via documented guidance) independently verify `request.shop` against the shop associated with the stored session/access token used to originally register that webhook, rather than trusting the header value as authenticated solely because the body's HMAC matched.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) and capture the raw request: headers (`x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`) and raw body.
2. Resend the identical raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim.myshopify.com` (and optionally change `x-shopify-topic` to another registered topic, since only the body bytes are checked, not topic/body correspondence).
3. `Registry.process` builds `Webhooks::Request` from `raw_body`/`headers`, computes `to_signable_string == raw_body`, and `HmacValidator.validate` succeeds because the body/HMAC pair is unchanged [1](#0-0) [6](#0-5) .
4. The handler registered for the (possibly attacker-chosen) topic is invoked with `WebhookMetadata.shop == "victim.myshopify.com"` even though the payload actually originated from the attacker's shop [3](#0-2) .
