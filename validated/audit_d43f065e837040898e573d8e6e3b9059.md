## Title
Webhook shop/topic/webhook_id identity spoofing via HMAC binding only the raw body, enabling cross-tenant webhook forgery — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers. `Registry.process` validates only that HMAC and then unconditionally forwards the unauthenticated `shop` header to the app's handler as the tenant identity, breaking the equality `shop_authenticated == shop_acted_upon`.

### Finding Description
`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string` using `Context.api_secret_key`. [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from attacker-controllable HTTP headers, none of which are part of the HMAC-covered content: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then trusts `request.shop`, `request.topic`, and `request.webhook_id` unconditionally, dispatching them straight to the app's handler as tenant-identifying metadata: [4](#0-3) 

Shopify's `api_secret_key` (`Context.api_secret_key`) is a single, app-wide secret shared across every shop that installs the app — it is not per-shop. That means any merchant who has installed the app is capable of generating a body+HMAC pair that Shopify's servers will legitimately sign (e.g., by triggering a `products/update` webhook containing attacker-chosen field values within their own store). Because the `shop-domain`, `topic`, and `webhook-id` headers are excluded from the signed content, that same legitimately-signed `(raw_body, hmac)` pair remains valid when replayed directly to the app's webhook endpoint with the `shop-domain` header rewritten to name a *different* shop (and/or the `topic` header rewritten to route to a different handler).

The documentation explicitly promises this gem "will verify the request did indeed come from Shopify," implying the returned `data.shop` can be trusted as the origin tenant: [5](#0-4) 

but the implementation only proves the body originated from an app-secret-holder (i.e., any installed merchant), not that it originated from the claimed `shop`.

### Impact Explanation
This breaks the tenant identity binding `shop_hmac_authenticated == shop_used_for_tenant_dispatch`. Any unprivileged merchant who has installed the app can forge webhook deliveries that a downstream handler will attribute to an arbitrary victim shop, since the shop field is never covered by the signature. Apps that use `data.shop` from `WebhookMetadata` to look up per-tenant records, write data, or trigger tenant-scoped side effects (exactly as the shipped example handler does: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process attacker-supplied content under a victim tenant's identity — a cross-tenant access violation. The `topic` header being similarly unauthenticated additionally lets an attacker route a valid-body payload into any handler registered in `@registry`.

### Likelihood Explanation
Requires only that the attacker be a legitimate (unprivileged) installer of the target app to obtain one genuinely HMAC-signed webhook body, and the ability to POST arbitrary headers directly to the app's public webhook endpoint (which is, by design, an internet-facing route). No access token, `client_secret`, or privileged account is required beyond ordinary app installation — this matches the "unprivileged internet user" threat model.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable content (or otherwise cryptographically bind them to the payload), so that `Utils::HmacValidator.validate` fails if any of these values are altered independently of the signed body. At minimum, `Registry.process` should cross-check `request.shop` against the set of shops that have `Session`s/registrations known to the host app before dispatch, rather than passing the raw header value straight through as trusted tenant metadata.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, obtaining a valid installation.
2. Attacker triggers a webhook event they control content for (e.g., updates a product's `note` field to arbitrary text), causing Shopify to POST `{raw_body, X-Shopify-Hmac-Sha256}` to the app's webhook endpoint — this HMAC is valid because it's signed with the app's shared `api_secret_key`.
3. Attacker captures this `(raw_body, hmac)` pair and replays it directly to the same webhook endpoint, but modifies the `X-Shopify-Shop-Domain` header to `victim.myshopify.com` (and optionally `X-Shopify-Topic` to a different registered topic).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — validation succeeds.
5. `handler.handle` receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, even though the payload never originated from the victim's store, confirming the identity-binding break at `lib/shopify_api/webhooks/registry.rb:190-199` and `lib/shopify_api/webhooks/request.rb:20-38`.
