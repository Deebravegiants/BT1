### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from the unauthenticated `shopify-shop-domain` HTTP header, while the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body. `Registry.process` treats a valid HMAC as proof that "the request did indeed come from Shopify" for the shop asserted in the header, but that header is never part of the signed data, breaking the binding between "HMAC-verified" and "shop claimed."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` signs/verifies exactly `to_signable_string` (i.e., the raw body only) using the app's shared `api_secret_key`: [3](#0-2) 

`Registry.process` gates entirely on this body-only HMAC check and then forwards the *unauthenticated* `request.shop` value straight to the app's handler as the trusted tenant identifier: [4](#0-3) 

The documented guarantee to app developers is that `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler with `data.shop` — developers are shown using `data.shop` directly as the tenant key (e.g., `shop_domain: data.shop`) for downstream job dispatch. In reality, the equality the gem is supposed to guarantee is:

`shop_verified_by_hmac == shop_delivered_to_handler`

but the actual behavior is:

`shop_verified_by_hmac (∅, not in signed bytes) ≠ shop_delivered_to_handler (attacker-controllable header)`

Because `shop` is completely excluded from `to_signable_string`, any request whose `raw_body` + `hmac-sha256` header forms a valid signature (e.g., a genuine webhook delivery the attacker legitimately receives for their own store, since Shopify signs webhooks with the single shared `client_secret` across all merchants of an app) can be replayed to the same endpoint with the `shopify-shop-domain` header rewritten to any other merchant's shop domain. `HmacValidator.validate` will still return `true`, `Registry.process` will not raise `InvalidWebhookError`, and the handler will receive `WebhookMetadata` claiming to be from the victim shop while carrying the attacker's own (or otherwise chosen) topic/body content.

### Impact Explanation
This is a cross-tenant identity-confusion vulnerability: an unprivileged internet user who merely has access to one valid signed webhook body (trivially obtainable as any merchant of the app, since they legitimately receive webhooks with a valid HMAC for their own store) can cause the host application to process/act on that payload under a different, arbitrary shop's identity. Applications following the gem's documented pattern (using `data.shop` to select which tenant's records to update, which job queue/shop context to dispatch into, etc.) will attribute attacker-controlled webhook data to a victim tenant, enabling cross-tenant data corruption or disclosure — a Critical-severity outcome per the cross-tenant access category, achieved purely through this gem's own verification logic (`HmacValidator` + `Registry.process`), not through any host-application misuse.

### Likelihood Explanation
Likelihood is high for any app author following the gem's documented API: the vulnerability requires no access to `api_secret_key`, no privileged account, and no TLS interception — only a single legitimately-received webhook (any merchant/attacker can trivially obtain one for their own shop by simply having the app installed) and the ability to POST an HTTP request with a modified `shopify-shop-domain` header to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the verified signature space, or otherwise cryptographically tie `request.shop` to the verification step, e.g. by including the `shopify-shop-domain` header value in `to_signable_string`, or by having `Registry.process` independently authenticate the claimed shop (for instance, by validating it against a value derived from signed data) before constructing `WebhookMetadata`. At minimum, document explicitly that `data.shop` is unauthenticated header data and must not be trusted as a tenant boundary without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` (a normal, unprivileged action) and receives a legitimate webhook delivery for topic `orders/create`, capturing the raw body `B` and the valid `shopify-hmac-sha256` header `H` (both computed by Shopify using the app's shared secret).
2. Attacker POSTs to the app's webhook endpoint with:
   - `raw_body = B`
   - `shopify-hmac-sha256 = H` (unchanged, still valid since `to_signable_string` only depends on the body)
   - `shopify-shop-domain = victim-shop.myshopify.com` (rewritten)
   - `shopify-topic`, `shopify-webhook-id` unchanged or forged similarly (also outside the signed data)
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed, `Utils::HmacValidator.validate(request)` returns `true` since it only re-derives the HMAC over `B`.
4. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)`, causing the host app to act on victim-shop's tenant context with attacker-supplied data. [5](#0-4) [6](#0-5)

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
