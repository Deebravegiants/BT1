Confirmed: the webhook HMAC in this gem covers only the raw request body (`to_signable_string` returns `@raw_body`), while `topic`, `shop`, `api_version`, and `webhook_id` are all read straight from HTTP headers that are never included in the signed bytes.### Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` are trusted from unauthenticated headers while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing/replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `ShopifyAPI::Webhooks::Registry.process` verifies covers exclusively the JSON body bytes. All other identity-bearing fields the app relies on — `shop`, `topic`, `api_version`, and `webhook_id` — are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never part of the signed material, and `Registry.process` hands them, unauthenticated, to the app's handler as trusted `WebhookMetadata`.

### Finding Description
- `Request#hmac` decodes the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 
- `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all derived from headers, independent of the signed body: [3](#0-2) 
- `HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` field — i.e., it authenticates only the body bytes, never the headers: [4](#0-3) 
- `Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic`/`request.api_version`/`request.webhook_id` to build `WebhookMetadata`, which is passed to the app's handler as the authenticated identity of the event: [5](#0-4) [6](#0-5) 

The identity binding that should hold is:
`HMAC-verified bytes == bytes that determine which shop/topic the event is attributed to`

But in this implementation:
`HMAC-verified bytes == raw_body only`, while `shop/topic/api_version/webhook_id (attributed identity) == unauthenticated header values`

Because the signature never covers the headers, any bearer of one genuinely-signed body+HMAC pair (trivially obtainable by installing the app on an attacker-controlled shop and capturing its own legitimate webhook deliveries) can resend that exact body and HMAC to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header. `HmacValidator.validate` still succeeds (it only re-hashes the untouched body), and `Registry.process` dispatches the payload to the handler labeled as belonging to the victim shop. This breaks the "shop authenticated == shop used as tenant key" invariant that host applications rely on this gem to provide.

### Impact Explanation
This is a cross-tenant identity confusion: an app built on this gem receives a webhook body that passes signature verification but is falsely attributed to a shop the attacker does not control. Any handler logic keyed on `WebhookMetadata#shop` (e.g., looking up/loading that shop's session or access token, updating that shop's records, deduplicating by `webhook_id`) can be manipulated to act on a victim shop's data using attacker-supplied content, or to poison per-shop caches/idempotency records keyed by the spoofed `webhook_id`. This matches the "cross-tenant access" Critical impact category, since it defeats a tenant-isolation boundary that the gem's `process` API is documented and expected to enforce via HMAC verification.

### Likelihood Explanation
The prerequisite — a valid HMAC over some body — is trivially satisfiable by an unprivileged attacker: install the target app on a shop they control (or use any shop's public app), capture a real webhook delivery to their own endpoint (a normal, unprivileged action), and then replay that exact body+HMAC to the target app's real webhook endpoint with a forged `shop-domain` header. No `api_secret_key`, access token, or privileged account is required for the attacker's own actions; the secret is only used server-side to verify, which still passes because the body itself is untouched.

### Recommendation
Bind the header-derived identity fields into the signed material, or independently authenticate `shop` against the app's known/installed shops before dispatch:
- Include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (this requires coordinating with Shopify's delivery signing scheme, since Shopify currently signs only the body — so at minimum, this gem should document and/or provide a hook for host apps to cross-check `request.shop` against a session store before trusting it), and/or
- In `Registry.process`, require callers to supply a set of expected/authorized shops (or validate against `SessionStorage`) before invoking `handler.handle`, rather than passing header-derived `shop` through unchecked.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app,
# so they receive a legitimate webhook with a valid HMAC over the body:
raw_body = '{"id": 12345, "note": "malicious payload"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, raw_body)
encoded_hmac = Base64.encode64(valid_hmac)

# Attacker replays the SAME body+hmac to the app's webhook endpoint,
# but swaps the shop-domain header to a victim shop they don't own:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => encoded_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # not the attacker's shop
  "x-shopify-webhook-id" => "attacker-controlled-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes HMAC validation because only raw_body is checked:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Dispatches to the app's handler as if it were victim-shop's event:
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", ...))
```
This demonstrates that `Registry.process` accepts and forwards attacker-chosen `shop`/`topic`/`webhook_id` values as long as the (unrelated) body hash matches, confirming the header fields are not bound to the HMAC.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
