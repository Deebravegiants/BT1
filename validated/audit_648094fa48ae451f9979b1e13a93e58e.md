### Title
Webhook shop identity spoofing due to `shop-domain` header not covered by HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `ShopifyAPI::Webhooks::Registry.process` validates the webhook exclusively against that HMAC. The `shop` value that is subsequently handed to the app's webhook handler as the tenant identifier is read from the `X-Shopify-Shop-Domain` header, which is never part of the signed content. Because the HMAC secret (`Context.api_secret_key`) is the app's single shared `client_secret` — identical for every shop that installs the app — any tenant that can obtain one validly-signed webhook body can replay it against the app's endpoint while freely substituting the `shop-domain` header to impersonate any other tenant.

### Finding Description
`Request#hmac` decodes `shopify-hmac-sha256`, and `Request#to_signable_string` signs only `@raw_body`: [1](#0-0) 

`Registry.process` validates the request using this body-only HMAC and then trusts `request.shop` (parsed straight from the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler: [2](#0-1) 

`Request#shop` is read purely from the header, with no cryptographic tie to the HMAC: [3](#0-2) 

The equality the gem should enforce is: `shop authenticated by the HMAC == shop delivered to the handler`. Instead, only `raw_body authenticated by the HMAC` is checked, while `shop delivered to the handler` comes from an independent, unsigned header — breaking that binding.

Because `Context.api_secret_key` is the app's own `client_secret`, shared across every shop installation (unlike per-shop access tokens), the HMAC computed from any legitimate webhook delivered to a merchant who has installed the app is valid for the *same body* regardless of which shop it is claimed to belong to. This lets a low-privileged actor who merely installs the app on their own store capture a validly-signed request and re-send it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value, impersonating any other tenant of the app.

### Impact Explanation
This crosses a tenant boundary: an attacker who legitimately installs the target app on their own shop can forge webhook deliveries that the app attributes to a different, victim shop. Since mandatory topics such as `shop/redact`, `customers/redact`, and `customers/data_request` are dispatched through the exact same `Registry.process` path with no additional tenant check, this can be abused to trigger shop-specific side effects (e.g., data redaction/deletion or business logic keyed off `data.shop`) against a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that keys behavior off `WebhookMetadata#shop` (a very common pattern, e.g., looking up per-shop settings or triggering shop-scoped actions): the attacker only needs to be a normal merchant who installs the target app (no special privilege, no access to the app's `client_secret` or another merchant's access token) to obtain one validly HMAC-signed body/secret pair, then replay it with a modified header.

### Recommendation
Include the shop domain (and other routing-critical fields such as topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind the header-derived `shop` to the signed payload before it is trusted in `Registry.process`/`WebhookMetadata`. At minimum, `HmacValidator`/`Request#to_signable_string` should not allow a field consumed by application logic (`shop`) to bypass the same integrity check applied to the body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and lets a webhook (e.g., `orders/create`) fire, capturing the raw POST body `B` and the resulting `X-Shopify-Hmac-Sha256: H` header, computed with the app's shared `client_secret`.
2. Attacker resends the exact same request to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` while leaving the body `B` and HMAC header `H` untouched.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)` — [4](#0-3)  — which passes because it only checks `raw_body` against `H` using the shared secret.
4. `request.shop` returns `"victim-shop.myshopify.com"` and is passed into the app's handler via `WebhookMetadata`, causing the app to process the webhook as if it originated from the victim tenant.
