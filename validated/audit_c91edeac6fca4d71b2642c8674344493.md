The gem's own documentation explicitly instructs handlers to trust `data.shop` (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that `shop` is treated as an authenticated tenant identifier — yet it is derived purely from an unauthenticated HTTP header.

### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then dispatches to the app's handler with a `shop` value read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in the signed material. [1](#0-0) [2](#0-1) 

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `HmacValidator.validate_signature` computes/compares the HMAC exclusively over that signable string using the app's shared `client_secret`. [3](#0-2) [4](#0-3)  The `shop` accessor, however, is read straight from a request header with no cryptographic binding to that body or its signature. [2](#0-1) 

`Registry.process` verifies only `Utils::HmacValidator.validate(request)` and then constructs `WebhookMetadata` using `request.shop` (the unauthenticated header) as the tenant identity passed to the app's handler. [5](#0-4) 

The identity binding that should hold is: `shop header used by the handler as tenant context == shop whose install/client_secret actually produced this signed body`. Because the HMAC secret (`client_secret`) is per-app, not per-shop, any shop that has installed the app shares the same signing secret as every other shop of that app. Attack sequence:
1. Attacker installs the target app on their own shop (`attacker-shop.myshopify.com`), a fully legitimate, unprivileged action.
2. Shopify sends the attacker a genuine webhook: some `raw_body` plus a valid `x-shopify-hmac-sha256` computed with the app's shared `client_secret`, along with `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but substitutes `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` still succeeds, because the HMAC never covered the shop header — only the body. [3](#0-2) 
5. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled/attacker's-own body, which the app treats as authentic data belonging to the victim tenant. [6](#0-5) 

The gem's own documentation reinforces that `data.shop` is meant to be trusted as the webhook's tenant identity for downstream dispatching (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), so this is the intended, documented usage pattern of the library, not host misuse. [7](#0-6) 

### Impact Explanation
This breaks the tenant boundary between two independent unprivileged merchants installed on the same app: an attacker with a legitimate, low-privilege install can inject a validly-HMAC'd webhook payload that is attributed to an arbitrary victim shop domain. Depending on how the host app's handler uses `data.shop` (e.g., to look up a session/store record and apply the webhook body's data), this can lead to cross-tenant data injection/corruption or triggering of shop-scoped side effects for a shop the attacker does not control — satisfying the "cross-tenant access" impact category, since it crosses the security boundary between two merchant tenants of the same app without requiring the app's `client_secret`, an access token, or any privileged credential beyond an ordinary app install.

### Likelihood Explanation
Likelihood is high in any app that keys per-shop processing off `WebhookMetadata#shop` — which is the exact pattern shown in the gem's own documentation — because the only prerequisite is that the attacker be able to install the app on a shop they control (the normal, unprivileged path for any merchant) and capture one legitimately-delivered webhook to replay with a forged header.

### Recommendation
Bind the shop identity into the material that is HMAC-verified, or otherwise independently authenticate the shop claim before trusting it:
- Include the `shop-domain` header (and ideally `topic`, `webhook-id`) in `to_signable_string` so the HMAC covers the full identity tuple, not just the body; or
- Cross-check `request.shop` against a shop-scoped secret/session record (e.g., verify the shop is actually subscribed to receive this `webhook_id`/topic) before dispatching to the handler, instead of trusting the raw header value as-is.

### Proof of Concept
1. Install the target Shopify app on `attacker-shop.myshopify.com` (ordinary, unprivileged merchant action).
2. Capture a real webhook delivery: `raw_body` (e.g., `{"id":1,...}`) and its `x-shopify-hmac-sha256` header, both computed by Shopify using the app's shared `client_secret`.
3. Send a forged HTTP request to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim-shop.myshopify.com` and matching `x-shopify-topic`/`x-shopify-webhook-id`.
4. Observe that `ShopifyAPI::Webhooks::Registry.process` (via `Utils::HmacValidator.validate`) accepts the request as valid, per: [8](#0-7)  and dispatches `handler.handle` with `shop: "victim-shop.myshopify.com"`, per: [6](#0-5) , despite the request never having come from Shopify on behalf of that shop.
