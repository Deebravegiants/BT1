### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body when validating a webhook's authenticity, while the `shop` (tenant) identifier, `topic`, and `webhook_id` are all taken from HTTP headers that are excluded from the signed content. `Registry.process` treats a passing HMAC check as proof that the entire request — including `request.shop` — came unmodified from Shopify, then forwards that unauthenticated `shop` value to the application's webhook handler.

### Finding Description
`Request#hmac` is computed over the header value, and the value it is compared against is derived solely from `@raw_body`: [1](#0-0) 
Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from attacker-controllable HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate` recomputes the HMAC only from `to_signable_string` (the raw body) and compares it against the received `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` uses a successful HMAC check as the sole authentication gate, then immediately trusts `request.shop` (along with `request.topic`) and hands it to the registered handler via `WebhookMetadata`: [4](#0-3) 

This breaks the intended identity binding: `shop asserted in header` should equal `shop covered by the cryptographic proof`, but in this implementation `shop` is never part of the signed material. Since the same secret (`Context.api_secret_key`) is used to sign webhooks for every shop the app is installed on, any body+HMAC pair genuinely produced for one tenant remains a valid signature for a forged request claiming to be from a different tenant, because the header carrying the tenant identity is outside the signed scope.

### Impact Explanation
This is a cross-tenant identity-binding failure of a Critical impact class: an attacker who controls one tenant (any shop where they've installed the app themselves) can produce webhook payloads whose body+HMAC pair passes validation for a request whose `shop` header is a different, target tenant's domain. Any host application that follows the gem's documented usage pattern of trusting `WebhookMetadata#shop` (i.e., every documented handler pattern in `docs/usage/webhooks.md`) to determine which tenant's data to create, update, or delete will act on behalf of the wrong shop, resulting in cross-tenant data corruption/injection under a spoofed tenant identity.

### Likelihood Explanation
Exploitation requires only: (1) installing the app on an attacker-controlled shop to obtain one legitimately signed webhook (trivial for any developer app on the Shopify App Store or dev store), and (2) replaying the identical raw body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint with a modified `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. No access to the app's `client_secret`, access tokens, or any privileged credential is required — this is purely an unprivileged-internet-user replay against the gem's own verification logic.

### Recommendation
Include the tenant-identifying and routing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material used by `HmacValidator`/`Request#to_signable_string`, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`. At minimum, document prominently that `request.shop`/`WebhookMetadata#shop` is unauthenticated header data and must not be used as a sole tenant-selection key without additional server-side verification (e.g., cross-checking against the shop of a known, already-authenticated session/installation record).

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger any webhook topic (e.g. `orders/create`) and capture the raw POST body `B` and its `X-Shopify-Hmac-Sha256: H` header — both are valid because `H = HMAC-SHA256(api_secret_key, B)`.
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which still equals `H`, so validation succeeds (`lib/shopify_api/webhooks/registry.rb:190`).
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the application to process attacker-controlled data as if it originated from the victim tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
