### Title
Outbound delivery rewards are priced at claim-time, not delivery-time, letting relayers arbitrage governance reward changes for old deliveries - (File: `modules/pallets/relayer/src/outbound_consensus.rs`, `modules/pallets/relayer/src/outbound_request.rs`)

### Summary
`claim_outbound_consensus_delivery_reward` and `claim_outbound_request_delivery_reward` are unsigned, permissionless extrinsics that let any relayer redeem a reward for a delivery it can prove with a state proof. Neither claim has a deadline or a snapshot of the reward rate at delivery time — both read the *current* governance-configured reward from storage at the moment the claim transaction executes, no matter how long ago the underlying delivery happened. This mirrors the reported bug class: rewards for a past event can be claimed at any time, with no timestamp binding the payout to the rate that applied when the qualifying action occurred.

### Finding Description
The reward for a mandatory consensus rotation is read live from `OutboundConsensusDeliveryReward` at claim time: [1](#0-0) 

Likewise, the reward for a hyperbridge-originated request delivery is read live from `OutboundRequestDeliveryReward` at claim time: [2](#0-1) 

Both storage maps are freely mutable by governance at any time: [3](#0-2) 

The verification pipelines for both claims (source/hash checks, idempotency, state-proof verification, signature attribution) contain no expiry window, no claim deadline, and no capture of the reward amount that was in effect at the time the delivery actually happened (i.e. at the block that emitted `NewEpoch` on the EVM `EvmHost`, or the block that populated `RequestReceipts[commitment]`). Idempotency is enforced only via `OutboundConsensusRotationsClaimed`/`OutboundRequestsClaimed`, which prevents double-payment of the *same* commitment, but does nothing to bind the *rate* to the delivery time. The docs explicitly describe this as a "claim at any time" design, matching the same window of exposure that the reported Ajna bug exploited: no timestamp validation ties a reward payout to the epoch/rate that should govern it.

### Impact Explanation
Because the reward rate is a live governance parameter rather than a value locked in at the time of delivery, a relayer that has already performed (or can predict) a qualifying delivery has an economic incentive to withhold submission of its claim until governance raises `OutboundConsensusDeliveryReward[destination]` or `OutboundRequestDeliveryReward[module_id]`. When governance does raise the rate (e.g., a routine adjustment for a different destination/module or a temporary bump to attract relayers), every outstanding, unclaimed-but-eligible delivery for that same key becomes claimable at the new, higher rate, over-paying the treasury relative to what was budgeted for those historical deliveries. Since the treasury account is a shared `TreasuryPalletId` pool funding all such claims, this allows unbounded historical claims to be revalued upward, resulting in unintended fund drain from the treasury (a High severity fund-drain path per the escrow/reward-accounting scope), beyond what governance intended when it set the higher rate going forward.

### Likelihood Explanation
Any relayer capable of delivering a mandatory consensus proof or a hyperbridge-originated request is, by design, unprivileged and permitted to submit the corresponding claim extrinsic (`ensure_none(origin)`). No special access is required beyond normal relayer operation; the only condition needed is a reward-rate change over time, which is a routine governance action (rewards are explicitly described as tunable, e.g. "10 tBRIDGE" testnet example, and are expected to be adjusted as market conditions change). Because there is no deadline enforcing "claim within N blocks of delivery," and no rate-snapshotting at delivery time, this is trivially reachable whenever any rate change occurs while unclaimed deliveries are outstanding — a state that is the normal, expected operating condition of the relayer incentive system (docs describe fee/reward claims as claimable "at any time").

### Recommendation
Snapshot the applicable reward amount at the time the qualifying event is verified as having occurred, rather than reading a mutable governance value at arbitrary claim time. Concretely:
- For `OutboundConsensusDeliveryClaim`, derive the reward from the value of `OutboundConsensusDeliveryReward[destination]` that was in effect at (or record it separately keyed by) the destination block height carrying the `NewEpoch` event, not the reward map's current value.
- For `OutboundRequestDeliveryClaim`, snapshot `OutboundRequestDeliveryReward[module_id]` at request-dispatch time (e.g., store it alongside the request commitment when it is inserted into `RequestCommitments`) instead of reading the live map at claim time.
- Alternatively, impose a claim deadline (a maximum number of blocks/epochs between delivery and claim) so that historical claims cannot be revalued by a subsequent governance rate change.

### Proof of Concept
1. Governance sets `OutboundConsensusDeliveryReward[Evm(X)] = R1` (low).
2. Relayer delivers a mandatory rotation to `Evm(X)`, earning attribution in `EvmHost._epochs[set_id]`, but does not submit `claim_outbound_consensus_delivery_reward` yet.
3. Time passes; governance later raises `OutboundConsensusDeliveryReward[Evm(X)] = R2` (high), intending this to apply to new, future rotations.
4. The relayer now submits the previously-unclaimed proof via `process_outbound_consensus_delivery_claim`, which reads `OutboundConsensusDeliveryReward::<T>::get(destination)` fresh — see `modules/pallets/relayer/src/outbound_consensus.rs` lines 174–186 — and pays out `R2` instead of the `R1` that was in effect (and presumably budgeted) when the rotation was actually delivered.
5. Repeat for every unclaimed historical rotation/request against that destination/module, extracting `(R2 - R1)` extra from the treasury per stale claim, with no on-chain mechanism preventing it.
