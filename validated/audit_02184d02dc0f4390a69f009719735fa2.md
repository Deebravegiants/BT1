Audit Report

## Title
Unbounded `topics` array in `WebAPITrigger` payload allows a single sender to force O(registeredWorkflows × topics) work per gateway message - (File: `core/capabilities/webapi/trigger/trigger.go`)

## Summary
`triggerConnectorHandler.processTrigger` iterates every registered `webapiTrigger` and, for each, every entry in the attacker-supplied `payload.Topics` slice, performing a map lookup per (trigger, topic) pair before any per-trigger sender authorization gates that specific trigger's cost. Neither `TriggerRequestPayload.topics` in the JSON schema nor the underlying gateway `Message`/`MessageBody` validation imposes any bound on array length or overall payload size, so a caller who can produce a validly-signed gateway message can force `O(N×M)` map-lookup work per message.

## Finding Description
`HandleGatewayMessage` validates the envelope via `hc.ValidatedMessageFromReq` → `msg.Validate()`, which only checks fixed-length fields (`MessageID`, `Method`, `DonID`, `Receiver`, `Signature`) and never inspects `Payload` size: [1](#0-0) . It then unmarshals `body.Payload` into `webapicap.TriggerRequestPayload` and dispatches to `processTrigger` for `MethodWebAPITrigger`: [2](#0-1) .

`processTrigger` snapshots all registered triggers and nests a loop over `topics` inside a loop over `triggers`, doing a map lookup (`trigger.allowedTopics[topic]`) for every combination, and only after a topic hit does it check `trigger.allowedSenders[sender.String()]`: [3](#0-2) . The `TriggerRequestPayload.topics` field is declared as an unbounded JSON array with no `maxItems`: [4](#0-3) , and `TriggerConfig.allowedSenders`/`allowedTopics` used at registration time are likewise unbounded: [5](#0-4) . `RegisterTrigger` only enforces a minimum of one `AllowedSenders` entry, not a maximum on either array: [6](#0-5) .

This confirms the mechanics of the claim: cost scales with the product of registered-trigger count and attacker-controlled topic-array length, and per-trigger authorization is not checked before the expensive comparison for that trigger. The only practical ceiling on `len(topics)` is the WebSocket/JSON-RPC message-size limit enforced at the transport layer, not an application-level bound on the `topics` array itself, so a moderately sized message (well within typical multi-MB websocket frame limits) can carry tens of thousands of short topic strings.

## Impact Explanation
This is a CPU-amplification / algorithmic-complexity issue on the gateway's DON-facing trigger ingestion path, not a straightforward authentication or fund-movement bypass. Worst case with `N` registered triggers and `M` topics in one message, the node performs `N×M` map lookups per inbound message before rejecting/accepting it, which could increase gateway node CPU load and add latency to the processing of concurrently arriving trigger messages, including from legitimate, allowlisted senders. It does not, by itself, bypass authentication, exfiltrate secrets, or move funds — the ultimate effect is a resource-consumption/soft-DoS on a single gateway node's message-processing loop, bounded by realistic values of `N` (registered triggers) and `M` (topics per message, itself bounded by the transport message-size limit). This maps most closely to a low/moderate-severity availability concern on the gateway trigger handler rather than a critical impact class (no impersonation, no auth bypass, no fund movement demonstrated).

## Likelihood Explanation
Any party able to produce a validly-signed `WebAPITrigger` gateway message (a modest bar — it does not need to be on any trigger's allowlist) can submit an oversized `topics` array, since `msg.Validate()` does not inspect the `Payload` contents beyond envelope-field lengths. Amplification scales with the number of currently registered triggers, which is deployment-dependent and outside attacker control. The severity is bounded by the transport-level websocket message-size limit and by realistic `N`; it is a plausible but not severe DoS vector.

## Recommendation
1. Add `maxItems` bounds to `TriggerRequestPayload.topics` and `TriggerConfig.allowedSenders`/`allowedTopics` in the JSON schema, and enforce them in `ValidateConfig`/`RegisterTrigger`/payload validation.
2. Reorder `processTrigger` to check `trigger.allowedSenders[sender.String()]` once per trigger before iterating `topics` for that trigger, avoiding full topic-array iteration against triggers the sender cannot match.
3. Consider capping total request payload size independent of the JSON-RPC/WS frame limit, and/or applying a lightweight per-sender rate limit prior to the nested loop.

## Proof of Concept
1. Register a trigger via `RegisterTrigger` with a modest `allowedTopics`/`allowedSenders` set.
2. Send a `WebAPITrigger` gateway message with a validly-signed envelope whose `TriggerRequestPayload.topics` contains a very large number of distinct strings (bounded only by the websocket/JSON-RPC frame size limit).
3. Observe that `processTrigger`'s nested loop performs `N×len(topics)` map lookups per message and that repeated submissions from an unauthorized sender can consume disproportionate CPU relative to a normal single-topic request — measurable via a Go benchmark/unit test comparing processing time for `len(topics)=1` vs. `len(topics)=100000` against `N` registered triggers.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

func (h *triggerConnectorHandler) HandleGatewayMessage(ctx context.Context, gatewayID string, req *jsonrpc.Request[json.RawMessage]) error {
	msg, err := hc.ValidatedMessageFromReq(req)
	if err != nil {
		h.lggr.Errorw("error validating message from request", "err", err, "request", req)
		return nil
	}
	body := &msg.Body
	sender := ethCommon.HexToAddress(body.Sender)
	var payload webapicap.TriggerRequestPayload
	err = json.Unmarshal(body.Payload, &payload)
	if err != nil {
		h.lggr.Errorw("error decoding payload", "err", err)
		err = h.sendResponse(ctx, gatewayID, body, ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: fmt.Errorf("error %s decoding payload", err.Error()).Error()})
		if err != nil {
			h.lggr.Errorw("error sending response", "err", err)
		}
		return nil
	}

	switch body.Method {
	case ghcapabilities.MethodWebAPITrigger:
		resp := h.processTrigger(ctx, gatewayID, body, sender, payload)
		var response ghcapabilities.TriggerResponsePayload
		if resp == nil {
			response = ghcapabilities.TriggerResponsePayload{Status: "ACCEPTED"}
		} else {
			response = ghcapabilities.TriggerResponsePayload{Status: "ERROR", ErrorMessage: resp.Error()}
			h.lggr.Errorw("Error processing trigger", "gatewayID", gatewayID, "body", body, "response", resp)
		}
		err = h.sendResponse(ctx, gatewayID, body, response)
		if err != nil {
			h.lggr.Errorw("Error sending response", "body", body, "response", response, "err", err)
		}
		return nil
