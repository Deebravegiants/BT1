### Title
Aliased-balance "double-entry" token lets `Hinkal.transact` mint on-chain UTXOs backed by an already-counted deposit - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` computes `balanceDif` per `erc20TokenAddresses[i]` independently via `getBalancesForArray` (a plain `balanceOf`/ETH-balance snapshot), and the only anti-duplication guard is the circuit's `distinctErc20AddressChecks` in `circuits/MainEVMCircuit.circom`, which merely checks that the raw address *values* differ, not that the balances they expose are independent. An attacker who deploys two distinct contract addresses that alias the same underlying balance storage can list both as separate `erc20TokenAddresses` entries, causing one real token transfer to be counted twice against the balance-equality check, letting a second entry mint an on-chain UTXO with no corresponding real inflow.

### Finding Description
The invariant the code intends to enforce per token index `i` is:
```
balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]
``` [1](#0-0) 

`balanceDif[i]` is derived purely from `newBalances[i] - oldBalances[i]`, where both snapshots come from `getBalancesForArray`, which calls `getERC20OrETHBalance(erc20TokenAddresses[i])` — i.e., `IERC20(addr).balanceOf(address(this))` for non-zero addresses [2](#0-1) . Nothing ties this observed delta to a *unique* pool of assets — it only assumes each listed address represents an independent ERC20 balance.

The only guard against duplicate/colluding entries is in the circuit, `distinctErc20AddressChecks`, which force-checks `erc20TokenAddresses[i] != erc20TokenAddresses[j]` as raw field values for every pair in a `transact` call [3](#0-2) . This prevents literally repeating the same address twice, but does **not** prevent two *different* attacker-deployed contract addresses (token A and token B) whose `balanceOf(address(this))` both read from the same underlying storage (a "double-entry"/aliased token pair the attacker fully controls). There is no token allow-list anywhere in the contracts (`Hinkal.sol`, `HinkalHelper.sol`, `Transferer.sol`) restricting which ERC20 addresses may be used — `erc20TokenAddresses` is entirely attacker-supplied and unchecked.

Exploit flow (internal transact, `externalActionId == 0`, the same logic and `_calculateDeltaAmount`/`checkOnchainCreation` path also governs the Emporium external-action branch where the deltaAmountChanges vector is computed identically before `runAction` is invoked) [4](#0-3) :
1. Attacker deploys token A (a real ERC20) and token B, a thin wrapper/alias contract whose `balanceOf(address)` reads the exact same storage slot/mapping that token A's `transfer`/`transferFrom` mutates (fully attacker-controlled contracts, no privileged role needed).
2. Attacker calls `transact` with `erc20TokenAddresses = [tokenA, tokenB]`, `amountChanges = [X, 0]`, `onChainCreation = [false, true]`, and off-chain/on-chain UTXO data such that: for index 0 (token A) the off-chain outputs consume `X` (a normal deposit, satisfying `checkOnchainCreation`'s requirement that `amountChanges[i]==0` only applies when `onChainCreation[i]` is true — here it's false so `X` is fine), and for index 1 (token B) `onChainCreation[1]=true` mints an on-chain UTXO of amount `X` with `amountChanges[1]` forced to `0` per `checkOnchainCreation` [5](#0-4) .
3. Inside `_internalTransact`, the positive `deltaAmountChange` for index 0 pulls `X` real tokenA units from the attacker into the vault via `transferERC20TokenFromOrCheckETH` [6](#0-5) . Because token B aliases the same storage, `tokenB.balanceOf(vault)` also rises by `X`, with **no separate transfer for token B**.
4. Back in `transact`'s post-loop, for `i=0`: `balanceDif == X == amountChanges[0](X) + utxoAmount[0](0)` ✓. For `i=1`: `balanceDif == X == 0 + utxoAmount[1](X)` ✓ — the check passes even though token B received zero *independent* backing; its apparent inflow is just a mirror of token A's single real transfer.
5. Result: a single real transfer of `X` units justifies `X` worth of shielded UTXO conversion for token A **and** an additional `X` on-chain UTXO minted for token B, i.e., `2X` of shielded value created backed by only `X` of real assets.

None of the existing guards catch this: `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only validate array-length and field consistency, not balance independence; `verifyProof`/circuit constraints (`inTotal + amountChanges === outTotal`, `OverflowPreventer`) operate per-token-index on values the prover controls and never cross-check against real on-chain balances beyond the same flawed `balanceDif` equality; `distinctErc20AddressChecks` only rejects identical address values.

### Impact Explanation
This lets an unprivileged attacker mint shielded/on-chain UTXO value in the Hinkal vault that is not backed by an equivalent real asset inflow, directly causing protocol insolvency — a Critical-severity impact ("minting shielded value without backing"). The attack is repeatable: each call using the same aliased token pair, or newly deployed pairs, can mint additional unbacked value proportional to the attacker's chosen `X`, limited only by gas and whatever downstream external-action or later redemption path is used to realize the minted UTXOs as real token withdrawals.

### Likelihood Explanation
Preconditions are fully within attacker control: deploying two contracts is trivial and requires no special role, no whitelist restricts `erc20TokenAddresses`, and the attacker fully controls `CircomData` fields (`amountChanges`, `onChainCreation`, `slippageValues`, encrypted outputs) and can generate a valid proof for their own UTXOs. The only added cost is deploying the alias-token pair and the real `X` tokens moved once. This is straightforward and repeatable, making likelihood high once the aliasing token design is built (feasibility of constructing such a token is standard Solidity coding, not requiring any protocol dependency).

### Recommendation
Do not rely solely on address-value distinctness. Track and require that each listed `erc20TokenAddresses[i]` corresponds to a canonical/registered token identity (e.g., require balances to be measured against a single trusted implementation per logical asset, or enforce a token allow-list with vetted contracts), and/or measure aggregate balance deltas keyed by verified token bytecode/canonical address rather than trusting `balanceOf` calls on arbitrary attacker-supplied addresses. At minimum, sum all real net inflows/outflows across the whole transaction against the sum of all `amountChanges`/`utxoAmount` globally in addition to (not instead of) the per-token check, so that aliasing that inflates one token's apparent delta without a matching real decrease elsewhere is caught.

### Proof of Concept
Foundry test plan:
1. Deploy `TokenA` (standard ERC20 with a `mapping(address=>uint256) balances`) and `TokenB` (a contract whose `balanceOf(a)` returns `TokenA.balances(a)` directly, e.g., by sharing a `SharedLedger` contract or having `TokenB` read `TokenA`'s public state via an exposed getter), such that transferring `TokenA` to the Hinkal vault increases `TokenB.balanceOf(vault)` identically.
2. Mint `X` TokenA to attacker, approve Hinkal.
3. Craft `CircomData` with `erc20TokenAddresses = [TokenA, TokenB]`, `amountChanges = [X, 0]`, `onChainCreation = [false, true]`, valid off-chain output UTXOs for TokenA summing to `X`, and an on-chain UTXO for TokenB of amount `X`; generate a locally valid proof for this data (only proof-generation for attacker's own UTXOs, satisfying circuit constraints including `distinctErc20AddressChecks` since `TokenA != TokenB` as addresses).
4. Call `Hinkal.transact(...)`.
5. Assert: vault's real net asset inflow == `X` (only `TokenA` transferred), while total credited shielded value == `2X` (X converted via TokenA off-chain UTXO change + X minted on-chain UTXO for TokenB) — i.e., assert `X (real transfer) < X (offchain credit) + X (onchain UTXO amount)`, demonstrating `balanceDif[1] == amountChanges[1] + utxoAmount[1]` holds on-chain while no independent value backs `utxoAmount[1]`.
