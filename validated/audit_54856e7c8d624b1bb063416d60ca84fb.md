### Title
Webhook `shop-domain` and `topic` identity is trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the raw HTTP body against the HMAC, then blindly trusts the `shop-domain`, `topic`, and `webhook-id` headers — none of which are covered by that signature — to decide which tenant and which handler the payload is dispatched to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` (shared with the OAuth `AuthQuery` flow) verifies solely that the body bytes match a valid HMAC for the app's `client_secret`: [1](#0-0) [2](#0-1) 

`Registry.process` then reads `request.shop`, `request.topic`, and `request.webhook_id` straight from headers and forwards them, unverified, as the tenant/topic identity to the app's handler: [3](#0-2) 

The equality the code implicitly (and incorrectly) assumes is:

`shop that produced this HMAC-valid body == shop asserted in the shop-domain header`

But nothing binds these two together. The HMAC secret (`client_secret`) is the same for every shop that installs a given public app, and Shopify itself computes the webhook HMAC over the body only — the shop domain, topic, and webhook id travel as separate, unsigned headers, matching Shopify's own webhook design. Consequently, an attacker who controls one installation of the app (e.g., their own development store, which is unprivileged relative to any other merchant's tenant) legitimately receives real, validly signed webhook deliveries (body + HMAC) from Shopify for their own shop. Nothing in `Request` or `Registry.process` prevents that attacker from replaying the same valid `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `shop-domain` header (and/or `topic`/`webhook-id`) for a victim shop. `HmacValidator.validate` still returns `true`, because it only checks the body/HMAC pair, and `Registry.process` will hand `WebhookMetadata` carrying the attacker's body but the victim's `shop` to the app's handler.

### Impact Explanation
If the hosting application uses `WebhookMetadata#shop` (as documented/intended) to select which tenant's records to update, this allows cross-tenant data injection/corruption using an unprivileged attacker's own legitimately-issued webhook — i.e., an attacker-controlled payload gets attributed to and processed against another merchant's tenant data. This matches the "Critical - cross-tenant access" impact category, since the trust boundary between tenants is broken purely through this gem's own webhook processing logic.

### Likelihood Explanation
Any developer/attacker can install a public app (or observe its own installed app's) webhook deliveries to obtain valid `(raw_body, hmac)` pairs signed with the shared `client_secret`. Replaying that request with a forged `shopify-shop-domain` header requires no secret material, no privileged account, and no interception of TLS — only observing traffic to one's own store, which is fully within an "unprivileged internet user" threat model.

### Recommendation
Do not treat `shop-domain`, `topic`, or `webhook-id` as trusted merely because the HMAC over the body validates. At minimum:
- Bind the shop domain into signature validation context, e.g., verify `request.shop` corresponds to a shop that has an active, previously-registered subscription with the topic/webhook id combination it claims, rather than trusting the header verbatim.
- Document prominently (and enforce where possible) that consumers of `WebhookMetadata` must independently verify `shop` against their own known/installed-shop record before applying any write using the webhook body, since it is not cryptographically bound to the signature.

### Proof of Concept
1. Install the target public app on an attacker-owned development store `attacker-shop.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g., `orders/create`) and capture the legitimate webhook HTTP request Shopify sends, including the `X-Shopify-Hmac-Sha256` header and raw body — both valid because they're genuinely signed for `attacker-shop`.
3. Replay the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Webhook-Id`) to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) returns `true` because it only checks the body, and the handler is invoked with `shop: "victim-shop.myshopify.com"` alongside the attacker's crafted body content — demonstrating the broken shop/HMAC identity binding.
