### Title
Session ID derivation trusts JWT `sub` claim without verifying it originates from an admin session token - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
`ShopifyAPI::Utils::SessionUtils.session_id_from_shopify_id_token` builds an "online" session identifier as `"#{shop}_#{sub}"` using the `sub` claim from any Shopify-issued JWT sharing the app's `aud` (client_id), without checking that the token's `iss` indicates it is an admin/embedded-app session token. `ShopifyAPI::Auth::JwtPayload` already implements this exact check elsewhere (`admin_session_token?`) for its `shopify_user_id` accessor, but `session_id_from_shopify_id_token` bypasses it and uses the raw `sub` claim directly.

### Finding Description
`ShopifyAPI::Auth::JwtPayload#initialize` verifies only the signature and the `aud` claim before exposing `sub`: [1](#0-0) 

The gem itself distinguishes admin session tokens from other Shopify-issued tokens (e.g. Checkout UI Extension session tokens, confirmed as a supported token shape in the test fixtures) via `admin_session_token?`, and gates `shopify_user_id` on that check: [2](#0-1) [3](#0-2) 

However, `SessionUtils.session_id_from_shopify_id_token` — the documented entry point for embedded-app authentication — never calls `admin_session_token?`; it takes `payload.sub` unconditionally and folds it into the online session id: [4](#0-3) 

Both an admin session token (`iss` ending in `/admin`, `sub` = staff numeric id) and a Checkout UI Extension token (`iss` ending in `/checkouts`, `sub` = `gid://shopify/Customer/...`) share the same `aud` (the app's client_id) and are both signed with the app's `api_secret_key`, so both pass `JwtPayload`'s only identity check (`aud == Context.api_key`). The equality the code should enforce — "token used to mint an admin session id" == "token whose `iss` proves it is an admin session token" — is not enforced. The `sub` claim is trusted for identity binding without being bound to the token's type/context.

### Impact Explanation
Any legitimate, low-privilege actor who can obtain a Shopify-issued, non-admin JWT for the same app (e.g., a shopper who receives a Checkout UI Extension session token) can present that token as `shopify_id_token` and have this gem mint a syntactically valid "online" session id for that shop, `"#{shop}_gid://shopify/Customer/...`, using a claim that was never asserted to represent an authenticated admin/staff user. If a host application relies on `current_session_id`/`session_id_from_shopify_id_token` as its sole authentication check before looking up or creating a session, this breaks the intended binding between "is an admin embedded-app session" and "the id used to key admin session storage," and could enable a non-admin, unprivileged token holder to be treated as if they completed the embedded admin OAuth flow.

### Likelihood Explanation
Requires only a Shopify-issued token that is not the intended admin session token type but shares the same `aud`; such tokens (checkout extension session tokens) are obtainable by ordinary, unauthenticated shop customers, with no access to `api_secret_key` or any privileged credential.

### Recommendation
In `SessionUtils.session_id_from_shopify_id_token`, reject tokens where `JwtPayload#admin_session_token?` is false (mirroring the check already applied in `shopify_user_id`), and use a verified admin user identifier (e.g., `payload.shopify_user_id`) rather than the raw `sub` claim when constructing the online session id.

### Proof of Concept
1. Obtain a valid Checkout UI Extension session token for shop `test-shop.myshopify.io`, signed with the app's `api_secret_key`, e.g. payload: `{ iss: "https://test-shop.myshopify.io/checkouts", dest: "test-shop.myshopify.io", aud: <api_key>, sub: "gid://shopify/Customer/123456789", exp:, nbf:, iat:, jti: }` (this shape is exactly the `@checkout_ui_extension_jwt_payload` fixture used in `test/auth/jwt_payload_test.rb`).
2. Call `ShopifyAPI::Utils::SessionUtils.session_id_from_shopify_id_token(id_token: token, online: true)`.
3. Observe it returns `"test-shop.myshopify.io_gid://shopify/Customer/123456789"` — a syntactically valid "online" session id — without ever verifying the token was an admin session token, unlike `JwtPayload#shopify_user_id`, which would have rejected it via `admin_session_token?`.

          end
