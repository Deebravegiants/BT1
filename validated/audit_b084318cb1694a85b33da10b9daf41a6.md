### Title
Precision-loss division-by-zero panic in `calc_take_pnl` permanently freezes Deposit/Withdraw on low-decimal pools - ([File: program/src/processor.rs])

### Summary
`Processor::calc_take_pnl` [1](#0-0)  is invoked on every unprivileged `Deposit`, `Withdraw`, and `WithdrawPnl` call [2](#0-1) [3](#0-2) [4](#0-3) . Inside it, `y2` is computed with an unchecked `.unwrap()` on `checked_div(x1)` [5](#0-4) . `x1`/`y1` are the *normalized* (decimal-scaled) pool balances, produced by `normalize_decimal_v2` [6](#0-5) , which performs `val * sys_decimal_value / 10^native_decimal` and floors to 0 whenever the actual token balance is small relative to `10^native_decimal / sys_decimal_value`. If the outer comparison at line 190 (`pool_pc_amount*pool_coin_amount >= calc_pc_amount*calc_coin_amount`, computed in raw un-normalized units) is still true while the normalized `x1` has floored to 0, `x2_power` becomes 0, `x2` becomes 0, and the later `y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` divides by the normalized zero, returning `None`, and `.unwrap()` panics.

### Finding Description
This mirrors the CVE-2021-2056 bug class of an unprivileged, reachable DML-style operation causing a repeatable crash/hang of the server: here, a standard user-facing instruction (`Deposit`/`Withdraw`) triggers an unhandled Rust panic due to insufficient input/state validation before performing arithmetic, instead of returning a graceful `ProgramError`.

Root cause chain:
1. `normalize_decimal_v2` truncates towards zero and can legitimately return `0` for a non-zero token balance whenever `pc_decimals` (or `coin_decimals`) is large relative to `sys_decimal_value` (e.g. for a 9-decimal mint against the fixed `sys_decimal_value`), if the residual pool balance after PnL accounting (`total_pc_without_take_pnl`/`total_coin_without_take_pnl`) is small [6](#0-5) .
2. `calc_take_pnl`'s guard condition at line 190 is evaluated on raw (non-normalized) `u64` amounts, so it does not detect that the normalized `x1` fed into `calc_x_power`/the division is zero [7](#0-6) .
3. Every code path in `calc_take_pnl`'s "if" branch uses unchecked `.unwrap()` on `checked_div`, `checked_sub`, `checked_mul` [8](#0-7)  instead of propagating an `AmmError`.
4. Because `calc_take_pnl` is invoked unconditionally at the start of `process_deposit`, `process_withdraw` (unless status is `WithdrawOnly`), and `process_withdrawpnl` [9](#0-8) [10](#0-9) [11](#0-10) , once the pool's residual PC or coin balance is in this "normalizes-to-zero" regime, *every subsequent Deposit/Withdraw/WithdrawPnl on that pool panics*, since no legitimate transaction can complete calc_take_pnl to update `target_orders.calc_pnl_x/y` out of that state.

This is distinct from a normal `Err(...)` return (which safely aborts the transaction without side effects); a Rust panic in on-chain BPF code aborts the transaction similarly, but the underlying pool state (vault balances vs `need_take_pnl_*`, and `target_orders.calc_pnl_x/y`) remains stuck in the same triggering condition, so the failure is deterministic and repeatable on every future attempt — a de-facto permanent denial of Deposit/Withdraw functionality (LP funds become effectively frozen because withdrawals can no longer be processed).

### Impact Explanation
Any unprivileged liquidity provider or the natural evolution of swap activity can drive a pool's `total_pc_without_take_pnl` (or coin equivalent) down to a small residual value through the normal swap fee/PnL accrual mechanics (`need_take_pnl_pc`/`need_take_pnl_coin` subtracted from vault balances in `calc_total_without_take_pnl_no_orderbook` [12](#0-11) ). Once the residual value normalizes to zero relative to the pool's decimals, all subsequent `Deposit`/`Withdraw`/`WithdrawPnl` transactions against that pool panic, permanently freezing LP funds locked in the pool (LPs can no longer withdraw their share) — matching the "Availability" impact class of the CVE analog (repeatable crash/hang caused by a reachable, unprivileged operation).

### Likelihood Explanation
Reaching the exact boundary condition requires the pool's un-normalized residual balance to fall into the specific narrow range where `normalize_decimal_v2` floors to zero while the raw-unit guard at line 190 is still satisfied. This is state-dependent and more likely on pools using higher-decimal mints (e.g. 9 decimals) paired with typical `sys_decimal_value` scaling, and after enough pnl has accrued (`need_take_pnl_pc`/`coin`) or the pool has been drained close to that boundary via repeated swaps. It is not a single-transaction, arbitrary-input trigger — it depends on the pool reaching a specific residual-balance state — but once reached, it is deterministically and repeatably triggered by any subsequent unprivileged Deposit/Withdraw call, satisfying "frequently repeatable" per the CVE analog.

### Recommendation
- Replace all `.unwrap()` calls on `checked_mul`/`checked_div`/`checked_sub` inside `calc_take_pnl` [8](#0-7)  with proper `.ok_or(AmmError::...)?` propagation so a degenerate state returns a graceful error instead of panicking.
- Before performing the division at line 208, explicitly check `x1 != 0` (and `y1`/`x2` as applicable) and short-circuit to a defined error (e.g., skip PnL taking, matching the `else` branch behavior) instead of allowing an implicit division-by-zero.
- Align the branch condition at line 190 to operate on the same units/precision used later in the function (normalized `x1`/`y1`) so the guard reliably prevents entering the div-by-zero path.

### Proof of Concept
Conceptual PoC (state-dependent, not single-instruction-only):
1. Create a pool with a coin or pc mint of high decimals (e.g., 9) relative to `sys_decimal_value`.
2. Through repeated ordinary swaps (unprivileged `SwapBaseIn`/`SwapBaseOut`), let PnL accrue via `need_take_pnl_pc`/`need_take_pnl_coin` until `total_pc_without_take_pnl` (or coin) computed by `calc_total_without_take_pnl_no_orderbook` [12](#0-11)  is small enough that `Calculator::normalize_decimal_v2(total_pc_without_take_pnl, pc_decimals, sys_decimal_value)` floors to `0` [6](#0-5) , while `pool_pc_amount*pool_coin_amount >= calc_pc_amount*calc_coin_amount` still holds at processor.rs:190.
3. Submit an ordinary `Deposit` or `Withdraw` instruction as any user; `process_deposit`/`process_withdraw` call `calc_take_pnl` with `x1=0`, causing `checked_div(x1)` to return `None` and the `.unwrap()` at line 208 to panic, aborting the transaction.
4. Repeat step 3: every future Deposit/Withdraw against this pool will hit the identical panic, since the underlying vault/pnl state is unchanged by the aborted transaction — the pool's liquidity is now non-withdrawable.

    pub fn normalize_decimal_v2(val: u64, native_decimal: u64, sys_decimal_value: u64) -> U128 {
        // e.g., amm.sys_decimal_value is 10**6, native_decimal is 10**9, price is 1.23, this function will convert (1.23*10**9) -> (1.23*10**6)
        //let ret:u64 = val.checked_mul(amm.sys_decimal_value).unwrap().checked_div((10 as u64).pow(native_decimal.into())).unwrap();
        let ret_mut = (U128::from(val))
            .checked_mul(sys_decimal_value.into())
            .unwrap();
        let ret = ret_mut
            .checked_div(U128::from(10).checked_pow(native_decimal.into()).unwrap())
            .unwrap();
        ret
    }

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
