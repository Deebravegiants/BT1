### Title
Arithmetic overflow during market accrual permanently freezes a heavily utilized market - (File: `common/src/rates/simulate.rs`)

### Summary
A market whose scaled borrow balance multiplied by its borrow index exceeds `i128::MAX` can no longer complete `accrue_step`; subsequent calls to `update_indexes`, withdrawals, repayments, and liquidations revert before the balances can be reduced. [1](#0-0) [2](#0-1) 

### Finding Description
Each accrual first reconstructs `borrowed_original` and `supplied_original` with `scaled_to_original`, which executes `scaled * index / RAY` through `Ray::mul`. [3](#0-2) [4](#0-3) [5](#0-4) 

The intermediate multiplication is safely widened to `I256`, but conversion of a quotient larger than `i128::MAX` returns `None`, and `mul_div_half_up` converts that failure into `GenericError::MathOverflow`. [6](#0-5) [7](#0-6) 

The index ceiling does not prevent this condition because the RAY-denominated position value can overflow while `borrow_index` remains below `MAX_BORROW_INDEX_RAY`. [8](#0-7) 

### Impact Explanation
An attacker can leave a large market at high utilization until ordinary compounding pushes `borrowed * borrow_index / RAY` beyond `i128::MAX`; from that point, any operation that simulates or persists accrual fails before debt or supply can be reduced. [9](#0-8) [10](#0-9) 

The repository’s directed regression test demonstrates that both `withdraw` and `repay` fail with `MATH_OVERFLOW` after the cliff is reached. [11](#0-10) [2](#0-1) 

This permanently freezes all supplied cash and collateral-dependent exits in the affected market, not merely the attacker’s own position. [12](#0-11) [13](#0-12) 

### Likelihood Explanation
The exploit requires a very large listed position and enough elapsed time at high utilization for the borrow index to multiply the scaled debt beyond the `i128` domain. [14](#0-13) 

A single unprivileged caller can create multiple accounts, supply the borrowable asset to one account, supply collateral to another, and invoke the public `supply`, `borrow`, and `update_indexes` entry points. [15](#0-14) [16](#0-15) [17](#0-16) 

The repository’s test reaches the condition using a one-billion-whole-token 18-decimal market at approximately 98% utilization and a steep configured rate curve; therefore, the path is capital-intensive but permissionless once such caps and market parameters exist. [18](#0-17) 

### Recommendation
Bound stored scaled balances against the largest index that can still be unscalescaled, and enforce the lower of the market cap and `floor(i128::MAX * RAY / current_index)` during supply and borrow share creation. [19](#0-18) 

Accrual should also handle a value-domain overflow deliberately, for example by clamping the borrow index before calculating scaled totals or by reducing the total using a bounded liquidation/recovery path. [20](#0-19) 

### Proof of Concept
For a listed 18-decimal market `M` with a supply/borrow cap of at least one billion whole tokens and a second listed collateral `C`:

```text
supply(attacker, 0, spoke_id, [(M_key, 1_000_000_000 * 10^18)])
    -> liquidity_account_id

supply(attacker, 0, spoke_id, [(C_key, sufficient_collateral)])
    -> borrower_account_id

borrow(
    attacker,
    borrower_account_id,
    [(M_key, 980_000_000 * 10^18)],
    Some(attacker)
)
```

Leave the market at high utilization until its steep borrow curve compounds `borrow_index` enough that `state.borrowed * borrow_index / RAY` exceeds `i128::MAX`. [21](#0-20) [22](#0-21) 

Then invoke the permissionless accrual entry point:

```text
update_indexes(attacker, [M_key])
```

The call reaches `accrue_step`, where `scaled_to_original(state.borrowed, borrow_index)` panics with `MathOverflow`. [10](#0-9) [3](#0-2) 

Subsequent attempts such as `withdraw(attacker, liquidity_account_id, [(M_key, 1)], None)` and `repay(attacker, borrower_account_id, [(M_key, 1)])` re-enter the same accrual calculation and revert, leaving all user balances in that market inaccessible. [23](#0-22) [2](#0-1)

pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}
