### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that Shopify computes and that `Utils::HmacValidator.validate` checks in `ShopifyAPI::Webhooks::Registry.process` binds only the payload bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers are read directly from attacker-controllable request headers and passed straight into `WebhookMetadata` used by the app's handler, without being part of the signed content.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled from HTTP headers via `shopify_header`, which reads directly from the `headers` hash passed into `initialize` — i.e., attacker/transport-controlled data: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC-over-body via `Utils::HmacValidator.validate(request)`, then forwards `request.shop` (an unvalidated header) as the tenant identifier into `WebhookMetadata`, which the app-supplied `handler.handle` consumes to decide which shop's data to act on: [4](#0-3) [5](#0-4) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string`: [6](#0-5) 

This breaks the identity binding: `shop-domain header == tenant the payload actually belongs to` is never enforced, because the HMAC only certifies `raw_body == body signed by Shopify`, not `shop-domain header == shop that Shopify signed the body for`. Any request whose body was legitimately signed by Shopify for *some* shop (e.g., the attacker's own store, which can trigger `orders/create`, `customers/data_request`, etc.) will pass HMAC validation in this gem's `Registry.process` even if the `shop-domain` header is swapped to a victim shop's domain, since Shopify's HMAC computation for webhooks is `HMAC(secret, raw_body)` and does not include the shop header.

### Impact Explanation
An unprivileged internet user who controls (or has captured) one legitimate, validly-signed webhook body for their own shop can replay it to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header. `Registry.process` will accept it as valid (HMAC check passes because it only covers the body) and dispatch `WebhookMetadata` claiming the payload is `for` a different, victim shop. Any app handler that trusts `data.shop` to select which tenant's records to update/redact/create (e.g., mandatory `shop/redact`, `customers/redact`, `customers/data_request` topics, or ordinary order/customer webhooks) will perform cross-tenant actions using attacker-supplied data attributed to a shop the attacker does not own. This matches the Critical "cross-tenant access" impact category — data intended for shop A ends up processed under shop B's identity purely because the binding between the signed bytes and the claimed tenant is never checked.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs a validly HMAC-signed body from Shopify, which they can obtain by installing/using the app on their own shop (unprivileged) and capturing any of the app's registered webhook deliveries, then replaying that exact body with a forged `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only the ability to trigger a webhook to one's own store, a capability any Shopify merchant/developer has.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the signed content checked against Shopify's HMAC, or independently verify that the `shop-domain` header matches an app-tracked, previously-authorized shop before dispatching `WebhookMetadata` to handlers. At minimum, document and enforce that `WebhookHandler` implementers must not trust `data.shop` unless it is cross-checked against known installed shops, since the gem itself provides no such binding.

### Proof of Concept
1. As an unprivileged attacker, install/enable the target app on the attacker's own shop `attacker-shop.myshopify.com`, triggering a legitimate webhook delivery for topic `customers/data_request` (or any registered topic) with body `B`. Shopify computes `hmac = HMAC-SHA256(client_secret, B)` and sends headers `X-Shopify-Hmac-Sha256: hmac`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: customers/data_request`.
2. Capture this request (body `B` and `hmac`).
3. Replay the same body `B` and `hmac` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — this still matches `hmac`, since the header is not part of `to_signable_string`: [7](#0-6) 
5. `process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"`, even though the payload/body was never actually signed for that shop: [8](#0-7) 
6. Any handler that uses `data.shop` to select the tenant record to act on (e.g., writing attacker-controlled body content into "victim-shop"'s data store) executes a cross-tenant write/read using attacker data under the victim's identity.
