### Title
Webhook `shop`, `topic`, `webhook_id` and `api_version` identity fields are not covered by the HMAC signature, allowing forged tenant metadata on a validly-signed webhook body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authenticated once `Utils::HmacValidator.validate(request)` passes, and then hands `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to the app's handler as trusted identity metadata. However, the HMAC only ever covers the raw JSON body — none of these header-derived fields are part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

That signable string is what `Utils::HmacValidator.validate` HMAC-verifies against the app's `api_secret_key`: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, which are never part of `to_signable_string`: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then forwards the unauthenticated header fields — including `shop` — directly into `WebhookMetadata`, which is passed to the app's handler as the trusted tenant identity for the event: [4](#0-3) [5](#0-4) 

This is the exact identity-binding gap called out in the scan rules: *"a field acted on but not covered by the HMAC."* Contrast this with the OAuth callback path, where `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters, so `shop` cannot be swapped without invalidating the HMAC: [6](#0-5) 

The equality that should hold but doesn't:
`shop_bound_by_hmac == shop_delivered_to_handler`

For OAuth this equality holds (shop is part of the signed string). For webhooks it does not — `shop` (and `topic`/`webhook_id`/`api_version`) are asserted by the sender's headers alone, decoupled from the cryptographic proof over the body.

### Impact Explanation
Because a single app-level `api_secret_key` (the `client_secret`) is shared across every merchant install, any unprivileged internet user who can trigger a legitimately-signed webhook for *their own* shop (e.g., by installing the target app on their own dev store and generating an event with attacker-chosen JSON content) obtains a `(body, hmac)` pair that is valid HMAC-wise. They can then replay that exact body+HMAC to the app's public webhook endpoint while forging the `x-shopify-shop-domain` header to name a victim shop, and/or forging the `x-shopify-topic` header to route it to a different handler than the one that produced it. `Registry.process` will accept it (`HmacValidator.validate` only checks the body) and deliver `WebhookMetadata#shop`/`#topic` naming the victim tenant/topic to the app's handler. Any host application that uses `data.shop` to key its per-tenant data (a normal, encouraged pattern) can be tricked into attributing attacker-controlled content to a different merchant — a cross-tenant confusion/injection vector. This maps to the "cross-tenant access" Critical-impact category in scope.

### Likelihood Explanation
Requires only: (1) ability to install the target app on an attacker-owned store to receive a validly-signed webhook (a normal, unprivileged action — installing a public app), and (2) the ability to POST arbitrary headers to the app's public webhook receiving endpoint, which by definition is internet-reachable and unauthenticated aside from the HMAC. No access token, `api_secret_key`, or privileged account is needed. Likelihood is bounded mainly by whether the target host app trusts `data.shop`/`data.topic` for tenant-sensitive logic without independently confirming the shop is registered/known — the gem itself provides no such secondary binding.

### Recommendation
Include the identity-critical headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable string for webhook requests, or otherwise cryptographically bind them (e.g., by having `Registry.process` cross-check `request.shop` against a shop known to be associated with the delivering topic/subscription before constructing `WebhookMetadata`). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must not be trusted as tenant identity without additional verification by the host app.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com`, causing Shopify to deliver a real webhook, e.g. `orders/create`, with attacker-controlled order JSON as the body `B`, signed as `HMAC(secret, B) = H` (the shared `client_secret` is the same for every install).
2. Attacker captures `(B, H)` from the legitimate delivery to their own endpoint/logging.
3. Attacker crafts a new HTTP POST to the target app's public webhook endpoint with:
   - Body: `B` (unchanged, so HMAC still verifies)
   - Header `x-shopify-hmac-sha256`: `H`
   - Header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - Header `x-shopify-topic`: unchanged or altered to route to a different registered handler
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) succeeds because it only checks `B` against `H`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed(B), ...)` and calls the app's handler, which now processes attacker-controlled data under the victim shop's identity.
