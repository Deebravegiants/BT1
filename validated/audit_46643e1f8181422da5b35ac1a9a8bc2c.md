### Title
Receipt size validated before `output_data_receivers`/promise-return mutation, allowing receipts to exceed `max_receipt_size` - (File: `runtime/runtime/src/receipt_manager.rs`)

### Summary
Analogous to the block-sdk MEV lane bug (where bundled transaction bytes were excluded from the size check before being unpacked into the block), nearcore's receipt size validation is performed on a receipt snapshot *before* additional bytes (`output_data_receivers` entries and returned promise values) are appended to it via `ReceiptManager::create_action_receipt` and related promise-return/value-return paths. This causes the actual outgoing receipt to exceed `max_receipt_size` while having passed the size check.

### Finding Description
`ReceiptManager::create_action_receipt` [1](#0-0)  pushes a `DataReceiver` onto an *already validated* receipt's `output_data_receivers` list when a dependent promise is created (`promise_then`/`promise_return` style chaining). Because this mutation happens after the receipt was checked against `max_receipt_size`, the final serialized receipt can grow past the configured limit. This exact scenario — and its outcome — is explicitly reproduced and documented in the test suite: `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` in `test-loop-tests/src/tests/max_receipt_size.rs`, whose comments state "The receipt should be rejected, but currently isn't because of a bug (See https://github.com/near/nearcore/issues/12606)" [2](#0-1) .

The runtime's congestion-control forwarding path (`try_forward`) has a defensive workaround for this exact defect: it clamps any receipt whose measured size exceeds `max_receipt_size` down to `max_receipt_size` for bandwidth-limit accounting purposes, with a comment directly referencing issue #12606 [3](#0-2) . This clamp only prevents the receipt from getting permanently stuck in the outgoing/buffered queue due to bandwidth accounting — it does not fix the root cause that an oversized receipt was allowed to be created and included in a chunk in the first place.

### Impact Explanation
An oversized receipt inflates the actual bytes carried in `ChunkStateWitness` and cross-shard receipt proofs beyond the `max_receipt_size` bound that the rest of the size-budget math (`docs/misc/state_witness_size_limits.md`) assumes [4](#0-3) . This is the direct structural analog of the MEV lane's block-size underestimation: a size check that is performed before further growth is applied, allowing serialized artifacts (there: blocks, here: receipts/chunk witnesses) to exceed the intended maximum. The impact is bounded by the size of the mutation (a `DataReceiver`, or the promise-return value) rather than unbounded, and the runtime does not crash on this path per the test comments ("Runtime shouldn't die when it encounters a large receipt"), so consensus/liveness impact is limited but the invariant "`max_receipt_size` bounds every serialized receipt" is violated.

### Likelihood Explanation
This is trivially reachable from a normal contract call: any contract using promise chaining (`.then()`, cross-contract calls returning large values, or `promise_return`) whose base receipt is already near `max_receipt_size` can trigger it, as demonstrated by the existing regression tests. No validator or privileged access is required — a plain transaction submitted by any account can produce the oversized receipt.

### Recommendation
Re-validate (or account for) the final receipt size after all mutations (`output_data_receivers` additions, promise-return value attachment) are applied, before the receipt is committed to `new_receipts`/outgoing receipts, rather than only checking size at creation time. Remove the reliance on the `try_forward` clamp as the sole mitigation, since it only affects bandwidth-limit bookkeeping, not the underlying oversized artifact.

### Proof of Concept
The existing repository tests already constitute a proof of concept and are documented as reproducing the bug: `test_max_receipt_size_promise_return` and `test_max_receipt_size_value_return` [5](#0-4) , which construct a receipt right at `max_receipt_size`, then trigger a promise chain that appends `output_data_receivers` or an oversized returned value, and assert (via `assert_oversized_receipt_occurred`) that a receipt above `max_receipt_size` does end up in the chain [6](#0-5) .

            self.action_receipts

                .ok_or(HostError::InvalidReceiptIndex { receipt_index })?

        }

            receiver_id,
            refund_to: None,
            output_data_receivers: vec![],
            input_data_ids,
            actions: vec![],
            is_promise_yield: false,
        };
        let new_receipt_index = self.action_receipts.len() as ReceiptIndex;
        self.action_receipts.push(new_receipt);
        Ok(new_receipt_index)
    }

/// Assert that there was an incoming receipt with size above max_receipt_size
fn assert_oversized_receipt_occurred(node: &TestLoopNode<'_>) {
    let client = node.client();
    let chain = &client.chain;
    let epoch_manager = &*client.epoch_manager;

    let tip = chain.head().unwrap();
    let epoch_id = epoch_manager.get_epoch_id(&tip.last_block_hash).unwrap();
    let protocol_version = epoch_manager.get_epoch_protocol_version(&epoch_id).unwrap();
    let runtime_config = client.runtime_adapter.get_runtime_config(protocol_version);
    let max_receipt_size = runtime_config.wasm_config.limit_config.max_receipt_size;

    let mut block = chain.get_block(&tip.last_block_hash).unwrap();

    // Go over all blocks down to genesis looking for a receipt above max_receipt_size.
    loop {
        if block.header().is_genesis() {
            panic!("Didn't find receipt with size above max_receipt_size!");
        }
        let prev_block = chain.get_block(block.header().prev_hash()).unwrap();

        let shard_layout = epoch_manager
            .get_shard_layout(&epoch_manager.get_epoch_id(block.hash()).unwrap())
            .unwrap();

        let oversized = if ProtocolFeature::Spice.enabled(protocol_version) {
            // With spice chunks are executed asynchronously and their produced receipts are
            // persisted as receipt proofs keyed by the block in which the chunk was applied,
            // rather than as incoming receipts on the following block.
            shard_layout.shard_ids().any(|shard_id| {
                chain
                    .chain_store()
                    .iter_receipt_proofs_for_shard(block.hash(), shard_id)
                    .iter()
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        } else {
            block.chunks().iter_new().any(|new_chunk| {
                let shard_id = new_chunk.shard_id();
                let prev_shard_index = epoch_manager
                    .get_prev_shard_id_from_prev_hash(block.header().prev_hash(), shard_id)
                    .unwrap()
                    .2;
                let prev_height_included =
                    prev_block.chunks().get(prev_shard_index).unwrap().height_included();
                let incoming_receipts_proofs = get_incoming_receipts_for_shard(
                    &chain.chain_store,
                    epoch_manager,
                    shard_id,
                    &shard_layout,
                    *block.hash(),
                    prev_height_included,
                    ReceiptFilter::TargetShard,
                )
                .unwrap();
                incoming_receipts_proofs
                    .iter()
                    .flat_map(|response| response.1.iter())
                    .flat_map(|proof| proof.0.iter())
                    .any(|receipt| receipt_is_oversized(receipt, max_receipt_size))
            })
        };

        if oversized {
            return;
        }

        block = prev_block;
    }
}

fn receipt_is_oversized(receipt: &Receipt, max_receipt_size: u64) -> bool {
    let receipt_size: u64 = borsh::object_length(receipt).unwrap().try_into().unwrap();
    if receipt_size > max_receipt_size {
        tracing::info!(%receipt_size, %max_receipt_size, "found receipt above max size");
        return true;
    }
    false
}
