### Title
Session ID Derived From Unauthenticated, Predictable Cookie Bytes Enables Cross-Tenant Session Hijack - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
For non-embedded apps, `SessionUtils.current_session_id` trusts the raw `shopify_app_session` cookie value verbatim as the session identifier, with no cryptographic binding to the browser that legitimately received it. Because `Session#id` for offline/online sessions is a deterministic, guessable string derived only from the shop domain (and, for online sessions, the numeric Shopify user id), any unprivileged internet user who learns or guesses a target shop's domain can set that exact string as their own cookie value and be treated by the host application's session store lookup as that shop's session.

### Finding Description
`Auth::Session.from` builds the session id as `"offline_#{shop}"` for offline tokens or `"#{shop}_#{associated_user.id}"` for online tokens [4](#0-3) . `SessionUtils.offline_session_id` and `jwt_session_id` reproduce the exact same deterministic formulas independently [5](#0-4) , confirming the id contains no secret or random component tying it to a specific browser/session-establishment event.

For the non-embedded OAuth flow, `validate_auth_callback` sets the browser cookie's value directly to `session.id` — i.e., the plain, predictable string — with no HMAC or signature over it [6](#0-5) . `SessionCookie` is a plain `T::Struct` with no signing capability [7](#0-6) .

Later, when the host app wants to identify "the current session", `SessionUtils.current_session_id` for non-embedded (and even for embedded-without-id-token) cases just returns `cookie_session_id(cookies)`, i.e. `cookies[SessionCookie::SESSION_COOKIE_NAME]` unmodified — no signature check, no HMAC, no correlation to server state [8](#0-7) [3](#0-2) .

This breaks the intended identity binding: `cookie_value == the exact bytes issued to this specific browser after this specific user completed OAuth` is supposed to hold, but in reality only `cookie_value == f(shop [, user_id])`, a value computable by anyone who knows/guesses the target `shop` domain (trivially enumerable, since shop domains are `{name}.myshopify.com` and often publicly known/guessable from the merchant's storefront). The host application, following this gem's documented pattern (`MyApp::SessionRepository.store_session(auth_result[:session])` keyed by `session.id`, per docs) [9](#0-8) , will resolve this attacker-forged cookie to the real merchant's stored session — including its access token — and use it for authenticated API calls on the attacker's request.

### Impact Explanation
An unprivileged internet user can set a browser cookie `shopify_app_session=offline_<target-shop>.myshopify.com` (or the online variant with a guessed user id) against a vulnerable non-embedded app and be authenticated as that shop's installed session, gaining cross-tenant access to that merchant's data/access token without ever completing OAuth or possessing any credential. This matches the "cross-tenant access" / "session fixation" Critical/High impact categories.

### Likelihood Explanation
Likelihood is high for any app built on this gem's documented non-embedded flow: no attacker secret is required, shop domains are public/guessable, and the vulnerable code path (`cookie_session_id`) is the gem's only mechanism offered for non-embedded session lookup — it is not an incidental host-app misuse but the library's own designed behavior.

### Recommendation
Do not use the raw, predictable session id as the sole session-cookie value trusted for identity. Either (a) sign/HMAC the cookie value with `Context.api_secret_key` and verify that signature in `cookie_session_id`/`current_session_id`, or (b) use a cryptographically random, unguessable session cookie value (e.g., `SecureRandom`) that is separately mapped server-side to the deterministic `session.id`, rather than embedding the deterministic id directly into the cookie that unauthenticated clients can set at will.

### Proof of Concept
1. App installs for `victim.myshopify.com` via the documented non-embedded OAuth flow; the app stores the resulting `Session` (id `offline_victim.myshopify.com`) via `MyApp::SessionRepository.store_session`.
2. Attacker, with no prior interaction with the app, sends a request to any authenticated route with `Cookie: shopify_app_session=offline_victim.myshopify.com`.
3. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` → returns `"offline_victim.myshopify.com"` unchanged [10](#0-9) .
4. Host app loads the real victim session/access token from storage using that id and serves the attacker's request as the victim shop.
