### Title
Nested Emporium call to `DepositOnChainUtxosExternalAction.runAction` drains a victim's ERC20 allowance with zero proof-verified debit - (contracts/external-actions/DepositOnChainUtxosExternalAction.sol)

### Summary
`DepositOnChainUtxosExternalAction.runAction` trusts `circomData.originalSender` and `circomData.externalActionData.externalActionMetadata` unconditionally to decide whose tokens to pull and how much, with no cryptographic binding to any Groth16 proof that actually gated this call. When it is invoked through `EmporiumUpgradeable.runAction`'s stateless op path (`op.endpoint.call{value: op.value}(op.callData)`), the attacker fully controls both `circomData` and `deltaAmounts` inside that nested calldata, independent of anything proven for the outer `Hinkal.transact` call. `msg.sender` inside the nested call is the Emporium contract, which satisfies `onlyAllowedRecipient` if Emporium is registered as an allowed recipient on the deposit action.

### Finding Description
Equality claimed to hold, but actually broken: `tokenTotal` (ERC20 amount pulled via `transferERC20TokenFrom(tokenAddress, V, msg.sender, tokenTotal)`) should equal a `utxoAmounts`/`amountChanges` sum that victim `V` proved via a verified Groth16 proof that they authorize spending. In this path, no such proof exists for `V` at all.

Code path:
- `EmporiumUpgradeable.runAction` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:91-113) executes `stack.ops`, where for a "stateless" op it does `(success, err) = op.endpoint.call{value: op.value}(op.callData);` with `op.endpoint`/`op.callData` fully attacker-controlled via the `EmporiumStack`/`EmporiumOperation` decoded from `circomData.externalActionData.externalActionMetadata` [1](#0-0) .
- The attacker sets `op.endpoint` = `DepositOnChainUtxosExternalAction` address and crafts `op.callData` as an arbitrary, self-contained call to `runAction(CircomData, int256[])`, embedding a forged `CircomData` (with `originalSender = V`, and `externalActionData.externalActionMetadata` = attacker-chosen `uint256[][]`) and `deltaAmounts` = all zeros. This forged `CircomData` is entirely independent from the outer proved `circomData` — nothing about it was ever a public input to `verifyProof` in `Hinkal.transact` (contracts/Hinkal.sol:44-56) [2](#0-1) .
- Inside `DepositOnChainUtxosExternalAction.runAction`, `msg.sender` is the Emporium contract (the direct caller in this low-level `.call`). The `onlyAllowedRecipient` check (contracts/external-actions/ExternalActionBaseV2.sol:16-22) only verifies `isAllowedRecipient[msg.sender]`, which passes if Emporium was ever registered as an allowed recipient for the deposit action [3](#0-2) .
- `userAddress = circomData.originalSender = V`; `deltaAmounts[i]==0` trivially passes (attacker controls this array entirely); `tokenTotal` is summed from attacker-chosen `utxoAmounts` up to `allowance(V, depositAction)`; `transferERC20TokenFrom(tokenAddress, V, msg.sender, tokenTotal)` pulls `V`'s tokens directly into the Emporium contract [4](#0-3) .
- Back in `EmporiumUpgradeable.runAction`, this inflow raises `balancesAfter[i]` for token `i`; since the outer `deltaAmountChanges[i]` (from the real proof) is unrelated and likely `>= 0`, `handleOut` treats the entire stolen `tokenTotal` as legitimate profit and sends it to `msg.sender` of the outer call (the `Hinkal` contract), minting a UTXO under the **attacker's own** `circomData.stealthAddressStructure` [5](#0-4) .
- `Hinkal.transact`'s balance-conservation check (`balanceDif == amountChanges[i] + utxoAmount`) is satisfied because the stolen tokens are counted both as the measured `balanceDif` and as the newly created `utxoAmount` — the check only verifies internal self-consistency of the transaction, not that every token inflow was proof-authorized by its true owner [6](#0-5) .

Root cause: `DepositOnChainUtxosExternalAction` derives `userAddress`, `tokenTotal`, and UTXO fields solely from a `CircomData` parameter that is never itself constrained by a ZK proof at this call site — it relies entirely on `onlyAllowedRecipient` (a coarse `msg.sender` check) as its only access control, and that guard does not distinguish between a legitimately-proof-gated call and an attacker-forged nested call routed through another allowed recipient (Emporium) that itself forwards arbitrary calldata to arbitrary endpoints.

### Impact Explanation
Critical — direct theft of a victim's approved ERC20 balance up to `allowance(V, depositAction)`, converted into a shielded UTXO owned by the attacker inside Hinkal, with no nullifier or proof ever committing `V` to this spend. This is repeatable for every victim who has an outstanding approval to `DepositOnChainUtxosExternalAction`, and repeatable multiple times up to the remaining allowance in successive transactions.

### Likelihood Explanation
This requires: (1) `DepositOnChainUtxosExternalAction` and `EmporiumUpgradeable` to be cross-registered such that Emporium is an `isAllowedRecipient` on the deposit action (an admin/owner configuration state, not attacker-controlled) — this is the "cross-registration setup" precondition carried over from the prior established finding in this audit chain; (2) a victim `V` to have a nonzero, unspent ERC20 `approve` to `DepositOnChainUtxosExternalAction` (a realistic residual-approval scenario for any prior legitimate depositor); (3) the attacker only needs to submit one otherwise-valid `Hinkal.transact` call for their own funds with `externalActionId` = Emporium's ID, embedding the malicious `EmporiumOperation`. No victim signature, relay privilege, or admin role is needed from the attacker.

### Recommendation
`DepositOnChainUtxosExternalAction.runAction` must not trust an unauthenticated `originalSender`/`externalActionMetadata` for pulling third-party funds. Bind the deposit amounts and depositor identity to the zero-knowledge proof's public inputs (e.g., require `msg.sender == originalSender` for the pull, or require the call to originate directly from `Hinkal.transact` with `circomData` that was itself the proof-verified struct, not one nested/forged inside another action's arbitrary sub-call). Additionally, `EmporiumUpgradeable`'s stateless op path should not be allowed to target other registered `IExternalActionV2` contracts' `runAction` entrypoints with attacker-supplied `CircomData`, or those entrypoints should independently authenticate the true depositor (e.g., via `msg.sender == originalSender` combined with `transferERC20TokenFrom` always pulling from `tx.origin`/an explicitly signed source, never from an arbitrary `circomData.originalSender`).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, `DepositOnChainUtxosExternalAction`; register both as external actions on `Hinkal`; configure `DepositOnChainUtxosExternalAction.setAllowedRecipients([emporiumAddress])` (the precondition cross-registration).
2. Victim `V` calls `IERC20(token).approve(depositAction, X)` for some `X > 0` (simulating a legitimate prior interaction with the deposit action).
3. Attacker builds a valid proof for their own trivial UTXO deposit/transaction with `externalActionId = EMPORIUM_ACTION_ID`, and crafts `EmporiumStack.ops[0]` = `{ endpoint: depositAction, invokeWallet: false, value: 0, callData: abi.encodeCall(IExternalActionV2.runAction, (forgedCircomData, zeroDeltaAmounts)) }`, where `forgedCircomData.originalSender = V`, `forgedCircomData.erc20TokenAddresses = [token]`, and `forgedCircomData.externalActionData.externalActionMetadata = abi.encode([[X]])`.
4. Call `Hinkal.transact(...)` as the attacker.
5. Assert: `IERC20(token).balanceOf(V)` decreased by `X` (or up to `X`), `IERC20(token).allowance(V, depositAction)` decreased accordingly, and no nullifier associated with `V`'s keys was ever inserted (`insertNullifiers` only recorded the attacker's own `inputNullifiers`) — proving `X` left `V`'s balance with no corresponding proof-verified debit, satisfying the broken value-conservation equality.
