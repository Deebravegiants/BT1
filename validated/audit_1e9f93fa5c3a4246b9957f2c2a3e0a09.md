## Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone, while the `shop` field that identifies which tenant a webhook belongs to is read straight from an unauthenticated HTTP header. Any unprivileged user who can get one legitimately-signed webhook body (e.g. by installing the target app on their own low-privilege dev/test shop) can replay that body with a forged `shop-domain` header to any endpoint running `ShopifyAPI::Webhooks::Registry.process`, and the forged shop value will pass HMAC validation and be handed to the app's webhook handler as if it came from a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are entirely attacker-controlled at the HTTP layer and are never part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` only re-derives the signature from `to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient proof of authenticity for the *entire* request, then forwards the unauthenticated `request.shop` value straight into the handler's `WebhookMetadata` as the tenant identifier: [4](#0-3) 

The identity binding that should hold is: `shop the HMAC secret was computed for == shop delivered to the handler`. Because the secret (`Context.api_secret_key`) is shared across every tenant of the app (it is the app's single `client_secret`, not a per-shop secret), and because the `shop` header is excluded from the signed bytes, this equality does not actually hold — any body/HMAC pair valid for shop A is equally valid when replayed with shop B's domain in the header. The gem's own documentation presents `data.shop` from `WebhookMetadata` as a trustworthy per-request tenant identifier with no caveat about verifying it independently: [5](#0-4) 

### Impact Explanation
An unprivileged internet user who can obtain any single legitimately-HMAC-signed webhook payload for the target app (trivially done by installing the target app, which is a public/embedded app, on their own attacker-controlled or free development shop) can forge the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name a victim shop and replay the request directly to the app's public webhook endpoint. `Registry.process` will accept it as authentic and dispatch it to the handler tagged with the victim's shop domain. Any host application that uses `data.shop` from `WebhookMetadata` to route effects (e.g., looking up the victim's session/access token, updating the victim's local records, triggering per-shop business logic) will act on attacker-controlled data believing it originated from the victim shop — a cross-tenant identity confusion.

### Likelihood Explanation
High for any publicly installable app: the attacker needs no access token, no `client_secret`, and no privileged account — only their own free/self-service shop installation to capture one valid `(body, hmac)` pair, after which the webhook endpoint (which by design is a public, unauthenticated HTTP route) can be hit directly with a forged shop header.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g. verify `shop` against a value obtained through an authenticated channel, such as the session/access-token store, before trusting `WebhookMetadata#shop`). At minimum, document clearly that `request.shop` is not covered by the HMAC and must not be trusted as an unauthenticated tenant identifier.

### Proof of Concept
1. Attacker creates their own development/partner shop and installs the target app so that a real webhook is delivered to the app, with header `x-shopify-shop-domain: attacker-shop.myshopify.com`, body `{}`, and a valid `x-shopify-hmac-sha256` computed with the app's shared `api_secret_key`.
2. Attacker replays the exact same raw body and HMAC header to the app's public webhook endpoint, but substitutes `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(sha256, secret, raw_body)` against the header — this passes because the body is unchanged.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though the actual event came from the attacker's own shop, achieving cross-tenant spoofing of the webhook's shop identity. [6](#0-5)
