### Title
Accounting drift between `need_take_pnl_pc/coin` trackers and real vault balances can permanently brick deposit/withdraw/swap on a pool - (File: program/src/math.rs, program/src/processor.rs)

### Summary
Raydium's classic AMM tracks, per pool, a "reserved for protocol PnL" amount (`amm.state_data.need_take_pnl_pc` / `need_take_pnl_coin`) that must always be less than or equal to the actual SPL token balance held in the pool's vaults. Every user-facing instruction (`process_deposit`, `process_withdraw`, `process_swap_base_in`, `process_swap_base_out`, their `_v2` variants, and `process_withdrawpnl`) begins by computing the "real" tradable/withdrawable reserves via `Calculator::calc_total_without_take_pnl_no_orderbook`, which does a hard `checked_sub` of the tracked PnL amount from the raw vault balance and reverts with `AmmError::CheckedSubOverflow` if the tracked amount ever exceeds the vault balance. This mirrors the FlatCoin `_getCollateralNet` invariant check (`InvariantChecks.sol` L97) that reverted whenever tracked collateral exceeded actual collateral, bricking all user-facing entrypoints.

### Finding Description
`calc_total_without_take_pnl_no_orderbook` subtracts the tracked, not-yet-withdrawn PnL amounts from the live vault balances and errors out on underflow: [1](#0-0) 

This function is invoked as the very first accounting step in every liquidity/trading instruction:
- deposit: [2](#0-1) 
- withdraw: [3](#0-2) 
- swap_base_in / swap_base_in_v2: [4](#0-3)  and [5](#0-4) 
- withdrawpnl: [6](#0-5) 

`amm.state_data.need_take_pnl_pc/coin` is only ever incremented by `calc_take_pnl`, which grows the tracked amount via `checked_add` any time the pool's implied invariant `x*y` has increased relative to the `target_orders.calc_pnl_x/calc_pnl_y` checkpoint: [7](#0-6) 

This accounting is only reconciled against real vault balances inside `process_withdrawpnl`, which additionally guards the *token transfer* with an explicit `<=` check before moving funds: [8](#0-7) 

However, that guard only protects the transfer in `process_withdrawpnl` — it does nothing to protect `calc_total_without_take_pnl_no_orderbook`, which is called *earlier*, unconditionally, in every other instruction (deposit/withdraw/swap). The whole scheme depends on the invariant `vault.amount == need_take_pnl_x + total_x_without_take_pnl` being preserved exactly across every deposit, withdraw, and swap, through several chained floor/ceiling roundtrip conversions (`normalize_decimal_v2`, `restore_decimal`, `exchange_pool_to_token`, `exchange_coin_to_pc`/`exchange_pc_to_coin`, and the `pnl_numerator/pnl_denominator` fee split) — this is structurally the same class of bug as FlatCoin's M-6, where the loss of one side (LP) and the gain tracked for the other side (protocol PnL) were not perfectly symmetric, so accumulating divergence eventually pushed the tracked amount above the real balance and permanently reverted every state-mutating instruction that touches that pool (`InvariantChecks.sol` `_getCollateralNet`).

### Impact Explanation
If `need_take_pnl_pc` or `need_take_pnl_coin` for a pool ever exceeds the corresponding SPL vault balance (through accumulated rounding drift across many deposit/withdraw/swap cycles, or through any code path that increments the tracker faster than the real balance grows), `calc_total_without_take_pnl_no_orderbook` will return `AmmError::CheckedSubOverflow` on every subsequent `Deposit`, `Withdraw`, `SwapBaseIn`, `SwapBaseOut` (and `_v2` variants) call for that pool. This permanently freezes all LP and trader funds held in that pool's vaults, since none of these instructions can complete, exactly matching the "long traders/LPs unable to withdraw" impact described in the source report.

### Likelihood Explanation
Similar to the original finding (downgraded to Medium by Sherlock judges because it requires an extreme, low-probability external condition — a 5x price move), this Raydium analog requires the tracked `need_take_pnl_pc/coin` values to drift above the real vault balance, which under normal, exactly-conserved arithmetic should not happen but can occur due to the accumulation of rounding across many rounds of `calc_take_pnl`/deposit/withdraw over the life of a heavily-traded pool, particularly pools with atypical/extreme decimal configurations (`pc_decimals`/`coin_decimals` far from `sys_decimal_value`) that maximize truncation in `restore_decimal`/`normalize_decimal_v2`. This makes it a state/condition-dependent Medium-severity issue rather than a guaranteed one-shot exploit.

### Recommendation
- Make the balance-vs-tracked-PnL invariant check in `calc_total_without_take_pnl_no_orderbook` saturating (clamp to zero) rather than a hard revert, matching the fix suggested for FlatCoin (cap the loss/gain split symmetrically instead of allowing divergence to brick the pool).
- Add a recovery/administrative path (or self-correcting logic) so that if `need_take_pnl_pc/coin` ever exceeds the real vault balance, the pool can still service deposit/withdraw/swap instead of being permanently bricked.
- Audit all decimal round-trip conversions (`normalize_decimal_v2`/`restore_decimal`) and the `pnl_numerator/pnl_denominator` split for worst-case rounding direction to ensure `need_take_pnl_pc/coin` can never structurally exceed the real vault balance.

### Proof of Concept
Because triggering this requires accumulating rounding drift over many deposit/withdraw/swap cycles (or an as-yet-unidentified single-transaction miscalculation in `calc_take_pnl`), a concrete minimal single-transaction PoC could not be constructed with confidence from static review alone; this is presented as a structural analog of the FlatCoin M-6 bug class (tracked-vs-real-balance invariant reverting and bricking all user-facing instructions), reachable by any unprivileged depositor/swapper/withdrawer once the divergence condition is met, via the unconditional `calc_total_without_take_pnl_no_overflow` call in `process_deposit`/`process_withdraw`/`process_swap_base_in`/`process_swap_base_out`.

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
