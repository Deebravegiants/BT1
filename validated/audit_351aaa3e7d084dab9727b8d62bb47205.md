## Title
Webhook `shop` (and `topic`/`webhook-id`) header fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only, while the `shop`, `topic`, and `webhook_id` values used by the registry/handler dispatch are taken from unauthenticated HTTP headers. An attacker who can obtain any one genuinely-signed webhook payload (e.g., by installing the app on their own shop and triggering an event) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop, and the gem will accept it as valid and dispatch it to the handler as if it came from the victim tenant.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only ever sign `@raw_body`: [1](#0-0) 

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are simply read from HTTP headers, which are never part of the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then dispatches the handler using the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

The identity binding that should hold is: `shop header == shop that produced the HMAC-signed body`. Because the HMAC only covers `@raw_body`, this equality is never checked — the `shop` header is a field acted upon (used to attribute the webhook to a tenant) but not covered by the HMAC, exactly matching the disclosed bug class (identity binding broken between an acted-upon field and the HMAC-covered bytes).

### Impact Explanation
An attacker who legitimately installs the target app on their own shop (an unprivileged, self-service action requiring no special credentials) can capture a genuine webhook delivery — valid `raw_body` + valid HMAC, both computed by Shopify using the app's real `client_secret`. Because the signature never binds to the `shop` header, the attacker can resend the identical body/HMAC pair to the app's webhook endpoint with the `shopify-shop-domain` header changed to an arbitrary victim shop domain. `Utils::HmacValidator.validate` will pass, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event belongs to the victim shop. Any app logic keyed off `WebhookMetadata#shop` (order/customer processing, GDPR data requests, subscription/billing events, per-tenant data writes, etc.) will then act on forged data attributed to a tenant the attacker does not control — a cross-tenant data-integrity/confidentiality breach.

### Likelihood Explanation
Moderate-to-high: any internet user can register a Shopify partner/development store and install an app that supports webhooks, then capture and replay a real signed payload against the target's public webhook endpoint with a single header changed. No secret key, access token, or privileged access is required — only observation of one's own legitimately delivered webhook.

### Recommendation
Bind the header-derived identity fields into the signed material: include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the HMAC-signable string (as Shopify's own header-based HMAC scheme intends, using body **and** header context), or independently corroborate the `shop` header against a known/trusted value (e.g., cross-check `X-Shopify-Shop-Domain` against the shop recorded for the given `X-Shopify-Webhook-Id` via the Admin API) before dispatching to handlers. At minimum, document that consumers must not trust `WebhookMetadata#shop` without their own verification, and update `Request#to_signable_string` to incorporate the header fields it exposes as trusted API.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook event, capturing:
   - `raw_body` (e.g., `{"id":123,...}`)
   - `x-shopify-hmac-sha256` (valid HMAC of `raw_body` under the app's real secret)
2. Attacker sends a POST to the app's webhook endpoint with the same `raw_body`/`x-shopify-hmac-sha256`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic`: any registered topic
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the HMAC: [4](#0-3) 
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and processes attacker-controlled data as though it originated from the victim tenant.
