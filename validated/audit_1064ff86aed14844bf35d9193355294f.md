This confirms the design: `load_transaction_account` at `svm/src/account_loader.rs:522-620` re-fetches the nonce account fresh from the account_loader cache when building `LoadedTransaction.accounts` for the `TransactionContext`, independent of whatever `validate_transaction_nonce` computed for `RollbackAccounts`. Both are deterministic pure functions of the same pre-transaction on-chain state and message content, so every node (banking stage leader and replaying nodes) computes byte-identical results.

### Analysis

For the scenario described — a transaction with two `AdvanceNonceAccount` instructions targeting the same account, where instruction 1 succeeds and instruction 2 fails with `SystemError::NonceBlockhashNotExpired` — the mechanism does not produce inconsistent or divergent state:

1. Both instructions execute against the **same shared `TransactionContext`** created once per transaction in `execute_loaded_transaction` [1](#0-0) , via `InvokeContext::process_message`, which stops at the first instruction error and returns `Err((index, err))` [2](#0-1) .
2. When the overall transaction status is `Err`, the SVM does **not** persist any of the `TransactionContext`'s intra-transaction mutations (including instruction 1's successful advance). Instead, `update_accounts_for_failed_tx` writes back only the pre-computed `RollbackAccounts` (fee payer state after fee deduction, and, if the transaction is itself a "durable nonce transaction", the nonce state that was advanced during pre-execution validation) [3](#0-2) [4](#0-3) .
3. `RollbackAccounts` for the nonce is only populated when the transaction uses a durable nonce as its blockhash and the first instruction is the required `AdvanceNonceAccount` marker instruction, computed deterministically in `validate_transaction_nonce` purely from the pre-transaction on-chain state and message content [5](#0-4) . If the transaction is *not* a durable-nonce transaction (ordinary recent-blockhash tx with two `AdvanceNonceAccount` instructions embedded), `RollbackAccounts::new` is called with `nonce=None`, producing `FeePayerOnly` [6](#0-5)  — meaning the nonce account address is **not included at all** in the accounts written back on failure, so its on-chain state simply remains exactly as it was before the transaction (full atomic rollback, discarding instruction 1's mutation entirely).
4. This entire computation — pre-tx state lookup, `NonceBlockhashNotExpired` detection in `advance_nonce_account` [7](#0-6) , and `RollbackAccounts` construction — is a deterministic pure function of on-chain state that is identical in banking stage and replay, so there is no cross-node divergence possible.

The existing test suite explicitly validates exactly this "nonce reuse" scenario (multiple advance attempts within the failure/rollback path) and asserts the nonce is restored to its pre-transaction value on failure [8](#0-7) , and dedicated rollback tests for `SeparateNonceAndFeePayer`/`SameNonceAndFeePayer` confirm the rollback nonce account equals the pre-execution durable nonce, not any intermediate state [9](#0-8) .

No partial-commit or "on-chain nonce out of sync with independently recomputed state" condition exists — the described exploit relies on a false premise that intra-transaction instruction successes are individually persisted before the overall transaction's pass/fail status is determined, which is not how `execute_loaded_transaction`/`RollbackAccounts` work.
