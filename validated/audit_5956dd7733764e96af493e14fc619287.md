### Title
Stale `ContractToAsset` Minting-Authority Entries Survive Contract Re-registration in `pallet-hyper-fungible-token` - (File: modules/pallets/hyper-fungible-token/src/lib.rs)

### Summary
`register_token` writes `TokenContracts[chain, asset_id] = new_contract` and `ContractToAsset[chain, new_contract] = asset_id` without first removing the previous `ContractToAsset[chain, old_contract]` entry when the same `asset_id`/`chain` pair is registered again with a different contract address. `on_accept` authorizes incoming mint/release operations solely by reverse-looking-up the message's source contract in `ContractToAsset`. Consequently, an address that was ever registered for an asset retains permanent minting/unlocking authority for that asset even after governance moves the asset to a new contract, because only `update_token`'s `add_chains`/`remove_chains` path clears the stale reverse mapping — `register_token` never does.

### Finding Description
`ContractToAsset` is documented as the map `on_accept` uses to attribute an inbound `Send` message to a local asset: [3](#0-2) [4](#0-3) 

`register_token` (call index 1) inserts into `TokenContracts` and `ContractToAsset` unconditionally on every call, with no check for, or removal of, a prior contract address already bound to the same `(chain, asset_id)`: [5](#0-4) 

By contrast, `update_token` explicitly removes the old reverse-mapping entry before writing the new one, and again on chain removal: [6](#0-5) [7](#0-6) 

There is nothing in `register_token`'s dispatch logic that prevents it from being called a second time for an `asset_id` that already has chain configuration (it is not gated to "new assets only" beyond re-inserting `NativeAssets`). If governance re-runs `register_token` for an existing asset to rotate its EVM contract address on a given chain (rather than using `update_token`), the old contract address's entry in `ContractToAsset` is left in place, still mapping to the asset. Since `on_accept` trusts `ContractToAsset` to decide which asset an inbound message credits, the old (now supposedly deprecated/decommissioned) contract retains permanent authority to trigger minting or escrow release for that asset.

### Impact Explanation
This is the direct analog of GHSA-9x5g-62gj-wqf2: a stale reference tied to a previously-valid configuration is never cleaned up, and continues to grant access/authority that the current configuration no longer intends. Here the "permission" is EVM-contract minting/unlock authority over a cross-chain fungible asset. If a contract is deprecated for security reasons (e.g., compromised, upgraded, migrated to a new address) and governance re-registers via `register_token` instead of `update_token`, the old contract keeps the ability to forge `Send` deliveries that mint fresh (non-native) tokens or release escrowed (native) tokens to arbitrary beneficiaries — an unbacked mint / theft-of-funds class impact reachable purely from a relayed ISMP message crafted by whoever controls the stale contract address.

### Likelihood Explanation
Requires a privileged `CreateOrigin` action (re-registration), but the resulting exploitation path (crafting/relaying a `PostRequest` from the stale contract) is fully within reach of any external relayer/attacker who still controls the deprecated contract — no further privilege needed to trigger the unauthorized mint once the stale entry exists. This matches the report's "misconfiguration by an operator who assumes old permissions are cleared" scenario precisely.

### Recommendation
In `register_token`, before inserting a new `TokenContracts`/`ContractToAsset` entry for a `(chain, asset_id)` pair, look up and remove any existing `ContractToAsset` entry for that chain/asset the same way `update_token` already does, or reject re-registration of an already-configured `(chain, asset_id)` pair and require `update_token` to be used for changes.

### Proof of Concept
1. Governance calls `register_token` for `asset_id = A`, chain `Evm(1)`, contract `X`. State: `TokenContracts[Evm(1), A] = X`, `ContractToAsset[Evm(1), X] = A`.
2. Contract `X` is later deemed compromised; governance calls `register_token` again for the same `asset_id = A`, chain `Evm(1)`, with new contract `Y` (instead of using `update_token`). State becomes: `TokenContracts[Evm(1), A] = Y`, `ContractToAsset[Evm(1), Y] = A`, but `ContractToAsset[Evm(1), X] = A` is **never removed**.
3. Anyone who still controls/operates contract `X` (or a message purportedly `from = X`) submits a `PostRequest` to `pall_hft`'s `on_accept`.
4. `on_accept` resolves the asset via `ContractToAsset[Evm(1), X]`, still returning `A`, and mints/releases asset `A` to the attacker-chosen beneficiary — despite `X` no longer being the registered contract in `TokenContracts`.

		#[pallet::call_index(1)]
		#[pallet::weight(T::WeightInfo::register_token(registration.chains.len() as u32))]
		pub fn register_token(
			origin: OriginFor<T>,
			registration: TokenRegistration<AssetId<T>>,
		) -> DispatchResult {
			T::CreateOrigin::ensure_origin(origin)?;

			let local_decimals = if registration.local_id == T::NativeAssetId::get() {
				T::Decimals::get()
			} else {
				<T::Assets as fungibles::metadata::Inspect<T::AccountId>>::decimals(
					registration.local_id.clone(),
				)
			};

			NativeAssets::<T>::insert(registration.local_id.clone(), registration.native);

			let chains: Vec<StateMachine> = registration.chains.keys().cloned().collect();
			for (chain, config) in registration.chains {
				// This pallet bridges substrate <-> EVM only; reject non-EVM peers.
				if !matches!(chain, StateMachine::Evm(_)) {
					return Err(Error::<T>::NonEvmPeerChain.into());
				}
				ensure!(
					config.decimals >= local_decimals,
					Error::<T>::ErcDecimalsBelowLocal
				);
				let token_contract = config.token_contract.0.to_vec();
				TokenContracts::<T>::insert(
					chain,
					registration.local_id.clone(),
					token_contract.clone(),
				);
				ContractToAsset::<T>::insert(
					chain,
					token_contract,
					registration.local_id.clone(),
				);
				Precisions::<T>::insert(registration.local_id.clone(), chain, config.decimals);
			}
