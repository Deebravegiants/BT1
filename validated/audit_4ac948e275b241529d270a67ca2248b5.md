## Title
Silent no-op decimal scaling in `convert_to_erc20`/`convert_to_balance` causes unbacked mint / fund loss when a registered asset's EVM precision is lower than its local precision - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s decimal-conversion helpers use `saturating_sub` to compute the scaling exponent between an asset's local decimals and its registered remote (EVM) decimals. When the remote decimals are *lower* than the local decimals — a normal, documented configuration ("Decimals between this chain and each remote chain may differ") — the exponent saturates to zero and the helper silently skips scaling entirely instead of scaling in the correct direction. This is the same bug class as the reported `GSP.sol` issue: a plausible, non-malicious configuration value (here, asset decimals; there, oracle price) is combined with math that has no bound/behavior for the "large divisor / large decimal gap" case, and the calculation silently degenerates instead of reverting, producing wildly wrong output.

### Finding Description
The conversion helpers are: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(value: U256, erc_decimals: u8, local_decimals: u8) -> Result<B, B::Err> {
    let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

`convert_to_erc20` is called from the permissionless, signed `send` extrinsic to scale a user's local balance up to the ERC20 amount before dispatching to the paired EVM contract: [2](#0-1) 

`convert_to_balance` is used symmetrically in `on_accept` (mint/release path) when tokens arrive from the EVM side: [3](#0-2) 

Both functions only ever *multiply/divide by `10^(erc_decimals.saturating_sub(local_decimals))`* — i.e., they only handle the case `erc_decimals >= local_decimals`. When `erc_decimals < local_decimals` (the registered EVM contract has fewer decimals than the local asset, e.g. `local_decimals = 18`, `erc_decimals = 6`), `saturating_sub` clamps to `0`, so `10^0 = 1` and **no scaling is applied at all**. The raw local balance value (already expressed in 18-decimal units) is transmitted verbatim as the ERC20 `amount`, and the EVM contract mints that many raw token units of a token that only has 6 decimals — a `10^12` amplification. `Precisions` is set per-`(asset, chain)` by governance via `register_token`/`update_asset_precision`, but nothing prevents (or is documented to forbid) registering an asset whose remote decimals are lower than local decimals, and the pallet README explicitly states decimals "may differ."

### Impact Explanation
Any signed account can call `send()` for an asset registered with `erc_decimals < local_decimals` and, in a single extrinsic, cause the paired `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract to mint (non-native asset) or release from escrow (native asset) an amount inflated by `10^(local_decimals - erc_decimals)` relative to what was actually locked/burned locally. This is an unbacked mint of bridged value with no economic backing — the attacker locks/burns a negligible local amount and receives an arbitrarily larger amount on the destination EVM chain, which can then be redeemed/sold. This is a direct fund-theft / unbacked-mint primitive reachable from a single unprivileged extrinsic, matching the accepted impact class (concrete theft / unbacked mint).

### Likelihood Explanation
The trigger condition (an asset whose EVM-side decimals are lower than its local decimals) is not a malicious-governance scenario — it's the ordinary, documented configuration path for tokens with differing precision across chains (e.g., a locally 18-decimal asset paired with a 6-decimal stablecoin representation on an EVM chain). Once such a pairing exists, any holder of that asset can trigger the bug with a normal `send()` call — no proof forgery, no privileged role, no governance compromise required.

### Recommendation
Rewrite `convert_to_balance`/`convert_to_erc20` to handle both directions explicitly instead of relying on `saturating_sub`:
```rust
if erc_decimals >= local_decimals {
    // multiply/divide by 10^(erc_decimals - local_decimals) as today
} else {
    // divide (for convert_to_erc20) / multiply (for convert_to_balance) by 10^(local_decimals - erc_decimals)
}
```
Additionally, add regression tests exercising `erc_decimals < local_decimals` for both `send` and `on_accept`, and consider validating at `register_token`/`update_asset_precision` time that the configured decimals round-trip correctly (or at minimum documenting/enforcing the direction the helper actually supports).

### Proof of Concept
1. Governance registers a non-native asset `X` with `local_decimals = 18` (via `pallet-assets`) and sets `Precisions::<T>::insert(X, dest_chain, 6)` (a plausible config for a 6-decimal stablecoin bridged in).
2. Attacker holds `1` unit of `X` in local raw terms (`value = 1`, negligible, or any small amount `V`).
3. Attacker calls `send(SendParams { asset_id: X, destination: dest_chain, amount: V, ... })`.
4. In `send`, `erc20_amount = convert_to_erc20(V, erc_decimals=6, local_decimals=18)` computes `10u128.pow(6u8.saturating_sub(18) as u32) = 10^0 = 1`, so `erc20_amount = V` unchanged — i.e., still expressed in 18-decimal terms.
5. The dispatched `Message.amount = V` (interpreted by the destination `HyperFungibleToken` contract, whose token has 6 decimals, as `V` raw units).
6. On the EVM side, `_mint(beneficiary, V)` mints `V` raw units — if `V` was, say, `1_000_000_000_000` (a fraction of 1 token in 18-decimal terms, i.e. `1e-6` of a whole `X`), the EVM contract mints `V / 10^6 = 1_000_000` whole tokens (since its ERC20 uses 6 decimals) instead of the intended negligible fraction — a `10^12` blow-up, unbacked by any real value burned/escrowed locally.
