### Title
Webhook shop-domain identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body against the app's shared `api_secret_key`, but the `shop` (and `topic`/`webhook_id`) values that are handed to the app's webhook handler as the event's tenant identity are taken from unauthenticated HTTP headers. This breaks the binding: `bytes verified (raw body via HMAC) != identity acted on (shop header trusted by handler)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read straight from HTTP headers with no cryptographic tie to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then forwards the header-derived `request.shop` directly to the app's handler as the authoritative tenant identifier: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body) and the app's single, shared `Context.api_secret_key`: [4](#0-3) 

Because `api_secret_key` is one value shared across every shop that installs the app (not a per-shop secret), any shop that installs the app can generate an arbitrary number of legitimately-HMAC'd `(body, hmac)` pairs for itself (e.g. by triggering `orders/create` events with attacker-chosen order data). Since the `x-shopify-shop-domain` header is never covered by that HMAC, the attacker can replay the same valid `(body, hmac)` pair to the app's public webhook endpoint while substituting the `shop-domain` header with a different, real, installed victim shop's domain (shop domains are public/guessable, not secret). `Utils::HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will happily dispatch the attacker-controlled body to the handler tagged with the victim shop's identity: [3](#0-2) 

The gem's own documentation confirms that `data.shop` is meant to be trusted as "The shop domain of the webhook" and used by the host application to key work (e.g. session lookup, job dispatch) to that shop: [5](#0-4) 

This satisfies the required identity-binding-break pattern from the rules: "a field acted on but not covered by the HMAC" — here the `shop` field is acted upon (used as the tenant key for downstream processing) but is completely outside the scope of the cryptographic verification performed by `Utils::HmacValidator`.

### Impact Explanation
This is a cross-tenant data-injection vector: an attacker who is merely an app-installing merchant (an "unprivileged internet user" relative to other tenants of the same app) can cause the shared app backend to process attacker-controlled webhook payloads as if they originated from an arbitrary victim shop, without ever needing the app's `client_secret`, an access token, or any credential belonging to the victim. Depending on how the host application's handler uses `data.shop` (typically to look up the victim's session/access token and perform automated actions, per the gem's documented usage pattern), this can lead to cross-tenant state corruption, forged business events attributed to another merchant, or triggering of backend automation using the victim's session — a cross-tenant access impact as defined in the assessment's Critical bucket.

### Likelihood Explanation
Likelihood is high for any publicly-installable app: the only prerequisite is that the attacker themselves install the app (a normal, unprivileged action) to obtain a valid `(body, hmac)` pair, and know a target shop's domain (public information, often just `{store-name}.myshopify.com`). No secrets, tokens, or elevated access are required, and the vulnerable code path (`Registry.process` / `HmacValidator.validate` / `Webhooks::Request`) is exercised on every webhook delivery handled by any app built on this gem exactly as documented.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable material, or otherwise cryptographically bind them to the verified body (e.g., verify that the shop domain in the header matches a shop the app has an active, previously-authenticated installation/session for before trusting it), rather than passing header-derived values straight through to handlers as authenticated identity.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`.
2. Attacker triggers (or has Shopify deliver) a legitimate `orders/create` webhook; the delivery contains `raw_body` and a valid `x-shopify-hmac-sha256` computed by Shopify using the app's shared secret, per `Registry.process`/`HmacValidator.validate`: [6](#0-5) 
3. Attacker captures this `(raw_body, hmac)` pair (they can generate many, with content of their choosing, by manipulating their own store's orders).
4. Attacker replays the exact same `raw_body` and `hmac` to the app's public webhook endpoint, but changes the `x-shopify-shop-domain` header to `victim.myshopify.com`.
5. `Request#shop` returns `"victim.myshopify.com"` while `Request#to_signable_string` still returns the same valid `raw_body`: [7](#0-6) 
6. `Utils::HmacValidator.validate` passes (body+hmac match), and `Registry.process` dispatches `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: attacker_controlled_body, ...)` to the app's handler, which processes attacker-controlled data as belonging to the victim shop: [8](#0-7)

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
