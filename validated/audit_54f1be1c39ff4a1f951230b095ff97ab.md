## Title
Webhook `shop` (and `topic`/`webhook_id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated for a given shop as soon as `Utils::HmacValidator.validate(request)` succeeds, then hands the handler the shop, topic, and webhook id taken straight from unauthenticated HTTP headers. The HMAC, however, is computed solely over the raw request body, never over those headers. Any party that can obtain one valid `(raw_body, hmac)` pair for the app's shared `client_secret` (e.g. a merchant who installs the app themselves) can replay that body with the `X-Shopify-Shop-Domain` header changed to a victim shop, and the library will report the event as verified and belonging to the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` derives its signable content only from the body: [1](#0-0) 

and derives `shop`, `topic`, `webhook_id`, and `api_version` purely from HTTP headers with no cryptographic binding to the body/HMAC: [2](#0-1) 

`HmacValidator.validate` recomputes the signature only over `to_signable_string`, i.e. `@raw_body`: [3](#0-2) 

`Registry.process` accepts the request as authentic once that body-only check passes, and forwards the header-derived, unauthenticated `shop`/`topic`/`webhook_id` values to the app's handler as trusted metadata: [4](#0-3) 

The gem's own documentation reinforces the false assumption that this call "will verify the request did indeed come from Shopify" and describes `data.shop` as simply "The shop domain of the webhook" with no caveat that it is unauthenticated, encouraging host apps to treat it as the verified tenant identifier: [5](#0-4) [6](#0-5) 

The broken binding, stated as an equality that should hold but doesn't:
`shop used to route/attribute the webhook (header, `request.shop`)` == `shop that actually produced this HMAC signature (nothing — HMAC only covers body bytes)`.

Because a single app has one shared `api_secret_key` across every shop that installs it, any merchant who installs the app can generate a legitimate `(raw_body, hmac)` pair addressed to their own shop, then resend that exact body/HMAC to the app's webhook endpoint with the `shop-domain` (and/or `topic`/`webhook-id`) header swapped to a different, victim shop the attacker does not control. `HmacValidator.validate` still succeeds (the body bytes and secret are unchanged), so `Registry.process` invokes the handler believing the event is a verified webhook for the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC check is supposed to enforce: an attacker who is merely a customer/merchant of the app (unprivileged with respect to other tenants) can inject attacker-controlled, "verified" webhook payloads attributed to any other shop. Depending on host-app logic built on top of `WebhookMetadata`, this enables cross-tenant data poisoning, forged `app/uninstalled` events (triggering token/session teardown for a shop the attacker doesn't own), or forged GDPR webhooks (`customers/data_request`, `shop/redact`) against arbitrary shops — a cross-tenant access impact.

### Likelihood Explanation
Requires the attacker to be an installer of the same app (trivial to obtain — anyone can install a public Shopify app) and to capture one legitimate webhook delivery to their own endpoint (which they control), then replay it with a modified header. No secret material or privileged account for the *victim* shop is needed, only participation as a normal, unprivileged tenant of the app.

### Recommendation
Include the routing-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content, or otherwise cryptographically bind them to the verified body (e.g., verify `shop` against the session/shop that is expected to have generated this specific webhook subscription) before trusting `WebhookMetadata#shop` as an identity key. At minimum, update documentation to make clear that `data.shop` is not covered by the HMAC and must be independently validated by the host application against its own known-shops list.

### Proof of Concept
1. App AppX has shops A (attacker-controlled) and B (victim) both installed, sharing one `api_secret_key`.
2. Attacker triggers a webhook delivery to their own endpoint for shop A, capturing `raw_body` and the valid `X-Shopify-Hmac-Sha256` header Shopify sent.
3. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the shared secret (`hmac_validator.rb:26-31`).
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, causing the host app to process attacker-supplied data as an authenticated event for shop B.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
