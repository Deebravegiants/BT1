### Title
Unallowlisted route pools can execute arbitrary token transfers inside the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
An attacker can craft a `swap` payload that routes through a malicious pool contract. Although the controller only authorizes one exact input transfer to the configured router, the payload-selected pool is invoked below the caller’s `swap_collateral`/strategy authorization. If transaction simulation reports and the caller signs the poisoned authorization tree, that pool can call `token.transfer(victim, attacker, amount)` for tokens entirely outside the routed swap.

### Finding Description
The controller authorizes only the router’s exact input pull, then passes the attacker-controlled route bytes to `router.execute_strategy`:

```rust
authorize_transfer_as_current(env, token_in, &controller, &router_addr, amount_in);
storage::with_flash_guard(env, || {
    let _ = router.execute_strategy(&controller, &amount_in, swap);
});
``` [1](#0-0) 

Route assets are raw `Address` registry entries, not pool allowlist entries:

```rust
pub struct SwapHop {
    pub pool: Address,
    pub token_in: Address,
    pub token_out: Address,
    pub venue: SwapVenue,
}
``` [2](#0-1) 

The repository’s host-level regression test proves the authorization-tree behavior. A route-selected contract is invoked below the caller’s authorization, and that contract can perform a `token.transfer(alice, attacker, WALLET_BALANCE)`; simulation attaches it as a child of Alice’s `swap_collateral` invocation, while enforcing mode accepts it if Alice signs that child:

```rust
token::Client::new(&env, &wallet_token).transfer(&victim, &to, &amount);
``` [3](#0-2) 

The test records the rogue transfer under Alice’s root authorization and shows Alice’s unrelated wallet token balance becoming zero while the attacker receives it: [4](#0-3) 

In enforced authentication, the same child invocation makes the otherwise unauthorized transfer succeed: [5](#0-4) 

### Impact Explanation
High: theft of user funds. A malicious route can drain wallet tokens unrelated to the lending collateral and outside the declared `amount_in`. The protocol’s measured input/output checks and positive-output requirement still pass because the rogue pool theft is an authorization side effect, not a controller/router balance transition. The proof uses `swap_collateral`, an explicitly reachable caller-authorized entrypoint.

### Likelihood Explanation
Medium-to-high once a victim is induced to sign a malicious route. The attacker does not need a privileged role or stolen key: they deploy the pool, construct the route, and cause the victim’s client to submit it. The victim’s signature is required, but the dangerous call is embedded below the top-level swap authorization, and clients that do not compare every simulated child invocation against the expected route can present it as an ordinary swap.

### Recommendation
- Restrict route execution to a governance-managed venue/pool allowlist, or validate and bind each hop pool to a known venue contract before dispatch.
- Ensure no arbitrary contract address decoded from route bytes can be invoked below the caller’s authorization.
- At minimum, expose a canonical simulation/auth-tree verifier that rejects any child invocation other than the single expected input transfer and documents that users must not sign additional children.
- Add a regression check asserting that a route containing an unexpected child invocation cannot be submitted through normal client construction.

### Proof of Concept
The repository already contains a focused PoC in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:

1. Deploy `UnlistedPoolRouter`, which pulls the swap input and invokes the payload-selected `hop_pool`.
2. Deploy `RogueHopPool` with `(victim, wallet_token, attacker, WALLET_BALANCE)`.
3. Build a route whose `hop_pool` is the rogue contract while still paying `min_out`.
4. Call `swap_collateral` as Alice.
5. Simulation records `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` as a child of Alice’s authorization.
6. Signing that returned tree makes the transfer succeed; Alice loses `77_770_000_000` units of a token unrelated to the swap.
