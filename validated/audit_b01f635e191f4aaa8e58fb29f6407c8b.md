### Title
Unhandled arithmetic panic in `calc_take_pnl` can permanently freeze deposit/withdraw operations - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` performs pnl-rebalancing math using `checked_sub(...).unwrap()` on values whose ordering (`x1 >= x2`, `y1 >= y2`) is not always guaranteed by preceding checks, allowing an attacker to drive the pool into a state where the subtraction underflows and the Solana program panics. Because `calc_take_pnl` is invoked as a required step inside `process_deposit` and `process_withdraw` before any state mutation is committed, an attacker-induced imbalance between the pool reserves and the stored `TargetOrders.calc_pnl_x/calc_pnl_y` values can make every subsequent deposit/withdraw transaction hit the same panic path, permanently freezing LP funds in the pool.

### Finding Description
`calc_take_pnl` computes `x2` (the coin-side reserve "after taking pnl") via an integer square root of `x2_power`, and `y2 = x2 * y1 / x1`: [1](#0-0) 

It then immediately subtracts without any bounds re-check: [2](#0-1) 

`x2_power = calc_x_power(target.calc_pnl_x, target.calc_pnl_y, x1, y1)`, and the invariant `x2 <= x1` (and thus `y2 <= y1`) relies on the *current* reserve ratio (`x1/y1`, derived from live vault balances via `normalize_decimal_v2`) staying reasonably close to the ratio implied by the stored `target.calc_pnl_x/calc_pnl_y` snapshot recorded at the last successful deposit/withdraw. Both `process_deposit` and `process_withdraw` recompute `x1`/`y1` from the *current* on-chain vault balances (attacker-influenced via swaps) before calling `calc_take_pnl`: [3](#0-2) 

Because swaps (`process_swap_base_in`/`process_swap_base_out` and their v2 variants) can move the coin/pc vault balances arbitrarily far in either direction without updating `target.calc_pnl_x/calc_pnl_y` (those are only updated inside `calc_take_pnl`'s caller on success — i.e., after the very computation that may panic), an attacker can:
1. Perform a series of swaps that drastically shift the reserve ratio away from the ratio implied by the last recorded pnl snapshot.
2. Trigger `x2 > x1` (or `y2 > y1`) in `calc_take_pnl`, causing `checked_sub(...).unwrap()` to panic.

Since the panic occurs before `target_orders.calc_pnl_x`/`calc_pnl_y` or any vault state is updated (the update only happens after `calc_take_pnl` returns `Ok`, e.g. `program/src/processor.rs:1818-1838`), the on-chain state that causes the mismatch persists across transactions. Every subsequent call to `process_deposit` or `process_withdraw` will recompute the same mismatched `x1/y1` vs. stale `target.calc_pnl_x/calc_pnl_y`, hit the identical underflow, and panic again — with no way to reset the imbalance because a successful deposit/withdraw (which would refresh the pnl snapshot) can never complete.

This is directly analogous to CVE-2016-9394 (JasPer `jas_seq2d_create` assertion failure): an attacker supplies data (here, a sequence of swap transactions, i.e., "crafted file" analog) that violates an implicit invariant the target function assumes holds, causing an unchecked assertion/unwrap to abort execution instead of gracefully validating and rejecting the malformed state.

### Impact Explanation
If reachable, this results in a permanent denial-of-service against `Deposit` and `Withdraw` for the affected pool: LPs would be unable to add or remove liquidity indefinitely, since every attempt reprocesses the same faulty math and aborts. This matches the "permanent freezing of user or LP funds" impact criterion. Swaps could still function unless they too invoke `calc_take_pnl` indirectly (they do not appear to call it directly in the reviewed code), so the primary impact is on deposit/withdraw liquidity operations.

### Likelihood Explanation
Reachability requires only unprivileged, permissionless actions: submitting swap transactions to shift the pool ratio, then any account attempting `Deposit`/`Withdraw`. No privileged signer or off-chain component is needed. However, whether the underflow is *actually* achievable depends on the precise bounds enforced by `Calculator::calc_x_power` and the accumulated effect of `pnl_numerator/pnl_denominator` scaling in `delta_x`/`delta_y`, which was not fully verifiable from the retrieved snippets — I could not confirm the exact mathematical conditions under which `x2 > x1` becomes possible, since `Calculator::calc_x_power`'s implementation was not available in the indexed context.

### Recommendation
Replace the `.unwrap()` calls on `checked_sub` (and other `checked_*` operations) in `calc_take_pnl` with proper error propagation (e.g., return `AmmError` on `None`), and add an explicit invariant check (`x2 <= x1` and `y2 <= y1`) before performing the subtraction, returning a descriptive error instead of panicking. This ensures malformed/extreme pool states degrade gracefully (reject the specific pnl-taking step) rather than permanently blocking deposit/withdraw operations.

### Proof of Concept
Due to indexing limits I could not retrieve the full implementation of `Calculator::calc_x_power` and `Calculator::normalize_decimal_v2`/`restore_decimal` to construct a concrete numeric example proving the underflow is reachable with attacker-controlled swap sizes alone. A definitive PoC would require:
1. Reading `program/src/math.rs` (or wherever `Calculator` is defined) in full to derive the exact conditions under which `x2_power`'s integer square root can exceed `x1`.
2. Simulating a sequence of `SwapBaseIn`/`SwapBaseOut` calls against a test pool to move `total_pc_without_take_pnl`/`total_coin_without_take_pnl` while keeping `target.calc_pnl_x/calc_pnl_y` fixed, then calling `process_deposit` to observe whether the panic is triggered.

I recommend a Devin session with full repository and test-harness access to confirm this concretely before treating it as a confirmed finding rather than a plausible bug-class analog.
