### Title
Webhook shop-domain header is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop` as an unauthenticated HTTP header, while the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. Any attacker who can obtain one validly-signed `(body, hmac)` pair for their own shop (by simply installing the app on a shop they control and capturing the webhook Shopify sends them) can replay that exact body/hmac pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The library will accept it as valid and hand the forged `shop` value to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`HmacValidator.validate` computes/compares the HMAC exclusively against `to_signable_string`: [2](#0-1) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from unauthenticated headers and are never included in the signed material: [3](#0-2) 

`Registry.process` only checks the body HMAC before dispatching the handler with the attacker-controllable `shop` field: [4](#0-3) 

The identity binding that should hold is: `shop header == shop that is cryptographically bound to the signed payload`. Because `shop` is never part of `to_signable_string`, this equality is never enforced — the gem authenticates the *bytes of the body* but the calling application is handed a *shop identity* that was never verified. Any two values `(body, hmac)` that pass validation remain valid for **any** `shop` header value, so an attacker who legitimately obtains one valid `(body, hmac)` pair (e.g., by installing the app on a shop they control and receiving Shopify's own outbound webhook call) can resubmit that same pair with a different `shop-domain` header pointing at a victim tenant.

### Impact Explanation
Because `WebhookMetadata.shop` is derived from this unauthenticated header and passed directly to the host application's handler, an app that uses this field to key persistence, trigger tenant-scoped side effects (e.g., `app/uninstalled` cleanup, order sync, GDPR data requests) can be made to act on a shop the attacker does not control — i.e., cross-tenant action/confusion using only data the attacker was able to generate for their own tenant. This matches the Critical "cross-tenant access" impact category, since the tenant boundary (`shop`) is not cryptographically bound to the authenticated payload.

### Likelihood Explanation
Exploitation requires only an unprivileged internet user to install the app on a shop they control (a routine, permission-less action for any Shopify Partner/dev shop), capture one webhook delivery, and replay it against the app's public webhook endpoint with a modified `shop-domain` header — no access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind `shop` (and ideally `topic`/`api_version`/`webhook_id`) into the signed material verified by `HmacValidator`, or have `Registry.process`/the consuming application independently confirm the claimed shop via an authenticated lookup (e.g., verify the `shop` header corresponds to a shop with a known, previously stored webhook secret/session) before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers/receives any webhook (e.g. `orders/create`).
2. Attacker's own endpoint logs the raw POST: body `B` and header `x-shopify-hmac-sha256: H` (a validly Shopify-computed HMAC of `B` using the app's real secret).
3. Attacker sends a new POST to the same public webhook endpoint with identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`: [5](#0-4) 
5. The handler is invoked with `shop: "victim-shop.myshopify.com"`, even though nothing about this shop was ever cryptographically verified.
