### Title
Webhook shop/topic identity spoofing via headers excluded from HMAC verification - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that identify *which merchant and event* the webhook belongs to are read from HTTP headers that are never included in the signed material. Any actor who can obtain one genuinely-signed `(body, hmac)` pair for the shared `api_secret_key` — which any merchant using the app legitimately receives for their own store's webhook traffic — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` (and `topic`) header, causing the host application to process attacker-supplied webhook data attributed to a different tenant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all derived from headers, which are never fed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string` (i.e., the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient authorization to dispatch the webhook, then builds `WebhookMetadata` directly from the unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` header values: [4](#0-3) 

The root cause is a broken identity binding: the equality that should hold is `hmac_authenticates(shop, topic, body) == (shop, topic, body) delivered to the handler`. In this implementation, `hmac_authenticates(body) only`, while `(shop, topic, webhook_id, api_version)` are trusted from headers with no cryptographic binding to the signed payload at all. Because the app's `api_secret_key` is shared across *all* shops that install the app, any merchant using the app legitimately receives real `(body, hmac)` pairs for their own shop. That same pair remains HMAC-valid when replayed with a different `shopify-shop-domain` (and/or `shopify-topic`) header, since neither is part of the signed bytes.

### Impact Explanation
This crosses a tenant boundary without requiring the app's `client_secret`, an access token, or any privileged credential — only requiring that the attacker be a legitimate (if malicious) merchant/user of the app who has their own valid webhook traffic to capture and replay. If the host application's webhook handler uses `data.shop` to decide which merchant's records to create/update/delete (a standard and expected usage pattern per this gem's own documentation), an attacker can inject fabricated webhook events (e.g., `orders/create`, `app/uninstalled`, `customers/redact`) attributed to an arbitrary victim shop, corrupting or exfiltrating data across tenants. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
The attack requires no secrets beyond what a normal, unprivileged app-installing merchant already legitimately possesses (their own valid webhook deliveries), and the replay itself is a trivial HTTP request with a modified header — no cryptography needs to be broken since the header fields simply aren't covered by the signature at all. This is directly reachable through the gem's public `Webhooks::Registry.process` entry point exactly as documented for host applications to use.

### Recommendation
Include the identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified body (e.g., derive/validate `shop` independently via a per-shop webhook secret, or require the caller to supply the expected shop and assert it against a value obtained through an authenticated channel) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and legitimately receives a real webhook delivery with headers:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: <valid-hmac-of-body>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - body: `{"id": 1, ...}`
2. Attacker resends the identical raw body and identical `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replaces the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `Utils::HmacValidator.validate` recomputes the HMAC over the (unchanged) body and finds it matches the (unchanged) `hmac` header — validation passes, per `HmacValidator#validate_signature` in [5](#0-4) .
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <attacker body>, ...)`, per [6](#0-5) , causing the host app to process attacker-controlled data as if it belonged to `victim.myshopify.com`.
