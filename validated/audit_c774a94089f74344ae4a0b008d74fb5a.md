### Title
Unchecked ERC20 `transfer()` return value in `IntentGatewayV2.withdraw()` permanently freezes escrowed intent funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed intent tokens by making a raw low-level `.call()` with the `IERC20.transfer.selector` and only checking that the call did not revert (`success`), never decoding/verifying the returned boolean. Any ERC20 that returns `false` on failure instead of reverting (a very common non-standard-but-legal ERC20 pattern) will be treated as a successful withdrawal even though no tokens moved, while the escrow accounting is unconditionally decremented.

### Finding Description
In `withdraw()`, escrow release/refund/fee payout uses:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 
and identically for protocol fees: [2](#0-1) 
and for governance dust sweeps in the same file: [3](#0-2) 

`success` here only reflects whether the call reached and executed the target contract without reverting — it does not verify the ABI-encoded `bool` return data that `IERC20.transfer` is supposed to return. Several widely-used ERC20 tokens (and Tron/TRC20-style tokens especially, given this is the Tron-targeted contract) return `false` on a failed transfer rather than reverting. For such tokens, `success` would be `true` (the call executed), `TransferFailed()` would never trigger, yet `beneficiary` never actually receives the tokens.

Directly after this unchecked transfer, the escrow accounting is unconditionally decremented:
```solidity
_orders[body.commitment][token] -= amount;
``` [4](#0-3) 

This is the same bug class flagged in the source report — use of `transfer()` (here via low-level call to the selector) without checking/enforcing the actual boolean success — applied to `IntentGatewayV2`'s escrow settlement path, which is reachable by any unprivileged relayer delivering a `RedeemEscrow`/`RefundEscrow` ISMP message or by a solver calling the fill/refund flow.

By contrast, the primary EVM `IntentsBase._withdraw()` correctly uses OpenZeppelin's `SafeERC20.safeTransfer`, which reverts on a `false` return: [5](#0-4) . The Tron variant diverges from this safe pattern.

### Impact Explanation
When the escrowed token silently fails to transfer (returns `false`):
- The `_orders[commitment][token]` accounting is permanently decremented as if the beneficiary was paid.
- The actual tokens remain stuck in the `IntentGatewayV2` contract with no accounting entry pointing to them, and no path exists to retry the withdrawal (the escrow slot is now zero/decremented).
- This results in permanent loss of the solver's/user's escrowed funds for the affected order — a fund-freezing/loss condition directly matching the accepted impact criteria (permanent freezing of funds due to unchecked ERC20 transfer failure).

The dust-sweep failure mode is analogous but limited to protocol-owned residual balances rather than user escrow.

### Likelihood Explanation
This path is reachable by ordinary intent settlement traffic — any solver fill or user refund on an order denominated in a token that returns `false` instead of reverting on failure (e.g., due to insufficient allowance/balance edge cases in non-standard tokens, blacklist/pausable tokens common on Tron, or other legacy-style ERC20/TRC20 implementations) will trigger this. Given IntentGatewayV2 is meant to support arbitrary listed input/output tokens across chains including Tron, and Tron's ecosystem includes many non-standard token implementations, the likelihood of encountering at least one such token is realistic rather than purely theoretical.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the dust-sweep handler with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the non-Tron `IntentsBase._withdraw()` implementation, so that a `false` return value causes a revert instead of being silently accepted as success.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an escrowed ERC20/TRC20 token whose `transfer()` returns `false` on failure rather than reverting (e.g., due to a paused/blacklisted state for the beneficiary, or insufficient gateway balance from a rounding edge case).
2. Place and fill/refund an intent order denominated in that token so `withdraw()` is invoked with `body.tokens` referencing it.
3. Force the underlying `transfer()` to return `false` (e.g., blacklist the beneficiary in the token contract) — the low-level `.call()` still returns `success = true` since the call itself did not revert.
4. Observe `_orders[body.commitment][token] -= amount;` executes normally and `TransferFailed()` is never raised, even though the beneficiary's token balance never increased — the escrowed tokens are now stuck in the contract with no accounting record left to reclaim them.
