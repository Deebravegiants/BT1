### Title
Missing L2 sequencer-uptime check in `SimplexPaymaster`'s Chainlink price oracle reads - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices gas payment in ERC-20 stablecoins using two Chainlink `AggregatorV3Interface` feeds (native/USD and token/USD), consulted via `_getOraclePrice` on every `fetchDetails`/`validate`/`estimateTokenCost` call from any UserOperation "bandwidth purchaser" (gas-fee payer) using the paymaster. The staleness check only compares `block.timestamp - updatedAt` against `maxOracleAge`; it never checks whether the underlying L2's sequencer is up, matching exactly the bug class in the referenced DODO V3 `D3Oracle` report.

### Finding Description
`_getOraclePrice` reads `latestRoundData()` and enforces only positivity and heartbeat staleness: [1](#0-0) 

This is the sole price source used for `_tokenPrice`, which drives `getTokenPrice`, `estimateTokenCost`, and the prefund calculation reachable from any account's `PackedUserOperation` (an unprivileged "bandwidth purchaser" of gas sponsorship) submitted through the EntryPoint: [2](#0-1) 

On an L2 with a sequencer (e.g. an OP-stack chain such as Base, or Arbitrum) a sequencer outage freezes the Chainlink aggregator's `updatedAt`/answer at the last value seen before the outage. When the sequencer resumes, aggregators typically catch up with a burst of updates, but during the outage window (and often for a grace period after recovery) the last-reported price can be stale-but-within-`heartBeat`, or, once the sequencer restarts, immediately "fresh" with a price that does not reflect the true, potentially manipulated on-chain conditions during the gap. The code has no equivalent of Chainlink's `L2_SEQUENCER_UPTIME_FEED` check (`isSequencerUp` + grace period), so it cannot distinguish "genuinely fresh price" from "sequencer just came back online with unfavorable pricing."

The deployment configuration explicitly targets multi-chain rollout (deployment script comments reference "Ethereum and Base" heartbeats, and the bandwidth-purchasing docs reference EVM chain ids such as `EVM-8453` for Base), so the paymaster is intended to run on L2s with sequencer risk: [3](#0-2) 

### Impact Explanation
Any unprivileged user constructing a `PackedUserOperation` against this paymaster is exposed to mispriced gas sponsorship during/after an L2 sequencer outage: the contract could accept an ERC-20 payment computed from a stale/manipulable price ratio, letting an attacker underpay for gas sponsorship (draining the paymaster's EntryPoint deposit and stablecoin surplus relative to actual gas cost) or overcharge honest users. This is a direct funds-drain/mispricing vector on a contract whose stated security model assumes correct oracle pricing bounds all economic exposure ("the residual allowance" and markup surplus), so a broken price assumption breaks that bound. Severity is Medium, consistent with prior Sherlock validations of the same bug class.

### Likelihood Explanation
Likelihood is tied to L2 sequencer downtime events, which are infrequent but have occurred historically on Arbitrum and OP-stack chains. The paymaster is permissionless — any address can submit a UserOperation through the paymaster with no gating — so exploitation requires no special privilege, only timing around a sequencer incident, which raises the practical likelihood above a purely theoretical edge case for a multi-chain-deployed contract.

### Recommendation
Add an L2 sequencer-uptime Chainlink feed check (mirroring Chainlink's documented `L2_SEQUENCER_UPTIME_FEED` pattern) to `_getOraclePrice`, reverting or degrading gracefully when the sequencer is down or within its grace period after restart, for every chain deployment that runs behind a centralized sequencer (Arbitrum, Optimism/Base, etc.). On chains without a sequencer (e.g. Ethereum mainnet, BSC), this check can be conditionally skipped via a per-deployment configuration flag.

### Proof of Concept
1. Deploy `SimplexPaymaster` on an OP-stack/Arbitrum-style L2 with `nativeOracle`/token oracles pointing at real Chainlink feeds, per `DeploySimplexPaymaster.s.sol`. [4](#0-3) 
2. Simulate a sequencer outage: the Chainlink aggregator's `updatedAt` stops advancing while `block.timestamp` keeps advancing on the L1-anchored L2 clock (or, upon sequencer restart, the aggregator posts a fresh-looking round whose price reflects a stale off-chain market snapshot).
3. Call `fetchDetails`/`validate` with a `PackedUserOperation` during this window; `_getOraclePrice` passes both the `answer > 0` and `heartBeat` checks because `updatedAt` is either within tolerance or has just been refreshed post-outage. [5](#0-4) 
4. The attacker's UserOperation is priced using this unreliable value, letting them pay less ERC-20 than the true gas cost, draining the paymaster's markup surplus/EntryPoint deposit over repeated operations.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
