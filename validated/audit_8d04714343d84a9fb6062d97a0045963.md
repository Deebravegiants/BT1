Based on this analysis, the `Webhooks::Request` class computes its HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body` only), while `topic`, `shop`, `api_version`, and `webhook_id` are all pulled unauthenticated from HTTP headers. This is the exact bug class from the report: a field acted upon (`shop`) is not covered by the identity-binding check (HMAC).### Title
Webhook shop identity is not bound to the HMAC signature, allowing cross-tenant webhook data spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity via `Utils::HmacValidator.validate`, but the signature only covers the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers and passed straight through to the host application's handler, so a party who possesses one genuine `(raw_body, hmac)` pair can attribute that body to a different, arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `api_version`, and `webhook_id` are all parsed from headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates only the HMAC of the request and then forwards `request.shop` (header-derived) straight into `WebhookMetadata`, which is handed to the app's `WebhookHandler`: [3](#0-2) 

`HmacValidator.validate` calls `validate_signature`, which computes the HMAC over `verifiable_query.to_signable_string` — i.e., the raw body only, never the shop header: [4](#0-3) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field consumed by the handler and, per the gem's own documented usage, is expected to identify "the shop domain of the webhook" for routing/tenant-scoped processing: [5](#0-4) [6](#0-5) 

**Identity binding broken (equality that should hold but doesn't):**
`shop` header validated by HMAC == `shop` header acted on by the handler.

In reality: `HMAC` covers `raw_body` only; `shop` (and `topic`/`webhook_id`) are unauthenticated inputs from the HTTP layer that the handler trusts as-is. Anyone who can obtain one genuine `(raw_body, hmac)` pair for the app's secret (which they can, e.g., by installing the app to their own shop and receiving a real webhook) can replay that exact body/hmac pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) headers to point at a different (victim) shop that also uses the same app. `Registry.process` will accept the request as valid (the HMAC check passes because the body is untouched) and will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen (victim) shop, while `body` still contains the attacker's own shop's data.

### Impact Explanation
This breaks the tenant identity boundary the gem is supposed to enforce for webhook processing. Any host application that uses `WebhookMetadata.shop` to route processed webhook data to per-tenant records (the pattern explicitly shown in the gem's own docs: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) is vulnerable to having a legitimate merchant's webhook data misattributed to a different shop, corrupting or injecting cross-tenant data into that shop's records. This satisfies the "cross-tenant access" criterion — an unprivileged app installer can cause data belonging to their own tenant to be processed as if it belonged to another tenant, without any credential theft.

### Likelihood Explanation
Moderate-to-high. The attacker needs only:
1. The app installed on their own shop (an ordinary, unprivileged action any merchant can take), which lets them legitimately receive one or more real `(raw_body, hmac)` webhook deliveries signed with the app's `client_secret`.
2. Network access to POST to the app's webhook endpoint with the captured body/hmac and a forged `shop-domain` header pointing at any other shop that also has the app installed.

No access token, `api_secret_key`, or privileged account is required — only ordinary merchant self-service access, which matches the "unprivileged internet user" threat model.

### Recommendation
Bind the trust-sensitive header fields (`shop`, and ideally `topic`/`webhook_id`) into the value that is verified, or otherwise cross-check them against context established through an authenticated channel (e.g., verify that the `shop` header corresponds to a shop for which this exact webhook (`webhook_id`) was actually registered/expected, tracked server-side) before handing them to `WebhookHandler#handle`. At minimum, document prominently that `WebhookMetadata.shop`/`topic`/`webhook_id` are NOT covered by the HMAC and must not be trusted for tenant-scoping decisions without additional server-side verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid_hmac_of_body>`, and some `raw_body`.
2. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
3. Attacker (or any party who can reach the app's public webhook endpoint) resends an HTTP POST with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present); `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body`. [3](#0-2) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)` and, following the gem's documented pattern, persists/enqueues data keyed to `victim-shop.myshopify.com` — a cross-tenant data injection.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
