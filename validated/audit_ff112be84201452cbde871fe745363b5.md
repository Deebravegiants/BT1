### Title
Withdrawal status matched by `assetId` alone causes status/hash misreport for batch withdrawals of the same token - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts; packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts)

### Summary
`PoaBridge.describeWithdrawal` and `waitForWithdrawalCompletion` both resolve the status of a specific withdrawal by calling `findMatchingWithdrawal`, which selects the first entry in the API response whose `near_token_id` matches the requested `assetId` — it ignores the `index`/amount that uniquely identifies which withdrawal in a batch is being queried. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This mirrors the M-30 bug class: shared/aliased state that should be tracked per-item (per-vault `lastTimeStamp`) is instead tracked/queried by a single coarse key shared across multiple items (per-`assetId` lookup shared across all withdrawals of the same token in a batch), breaking the intended one-to-one equality between a withdrawal request and its reported outcome.

`createWithdrawalIdentifiers` in `withdrawal-watcher.ts` explicitly assigns a per-bridge sequence `index` to disambiguate multiple withdrawals of the same asset within one intent transaction: [4](#0-3) 

However, `PoaBridge.describeWithdrawal` explicitly discards that index ("Response list is unsorted, so we match by assetId instead of index") and calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which returns the *first* array element whose `near_token_id` matches, regardless of `args.index`: [5](#0-4) 

The comment in the code acknowledges the limitation explicitly: "multiple withdrawals of the same token in a single transaction are not supported." [6](#0-5) 

The same pattern exists independently in `internal-utils`' `waitForWithdrawalCompletion`, which matches purely on `assetId` criteria as well: [7](#0-6) 

Equality broken: the caller expects `describeWithdrawal({index: i, assetId, ...})` to report the on-chain outcome of withdrawal `i` specifically. Instead, it reports the on-chain outcome of *whichever* same-asset withdrawal happens to be first in the (explicitly unsorted) API response — which may be a *different* withdrawal in the same batch, at a different amount/destination, at a different completion status.

### Impact Explanation
When an intent contains two or more withdrawals of the same token (e.g., two USDC withdrawals to different destinations in one batch, both routed through PoA bridge), `createWithdrawalCompletionPromises`/`watchWithdrawal` polls `describeWithdrawal` per index, but both calls resolve to the same matched entry: [8](#0-7) 

This can cause:
- Both withdrawal-completion promises reporting the same `txHash` even though only one withdrawal has actually landed on the destination chain — this is a "status/hash misreport" that can make a caller/integrator believe both withdrawals are settled, potentially triggering a duplicate credit/refund decision for the withdrawal that has not actually completed.
- If the first-matched entry has failed while a later one of the same asset actually succeeded (or vice versa), the wrong outcome (`completed`/`failed`) is attributed to the wrong withdrawal identifier.

This matches the High-severity category "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This is triggerable without any privileged or malicious actor — simply by constructing a legitimate multi-withdrawal intent that withdraws the same PoA-bridged token twice (e.g., to two different addresses) in a single transaction, which the SDK's public `createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` API explicitly documents as supported for batch withdrawals. The bug is deterministic whenever the underlying POA API returns an unsorted array containing 2+ entries for the same token in one tx — the code comments confirm the API's response ordering isn't guaranteed and isn't handled.

### Recommendation
Disambiguate withdrawals of the same asset within a batch instead of matching on `assetId` alone:
- Use the `index` supplied via `WithdrawalIdentifier` together with amount/destination to select the correct entry, e.g., sort both the API response and the local `withdrawalParams` deterministically (as the existing comment suggests) by `(assetId, amount, destinationAddress)` and match on `index` within that sorted order.
- Until the POA API supports returning a stable index/withdrawal ID, throw or return `pending`/an explicit "ambiguous match" error when multiple entries share the same `assetId`, rather than silently picking the first one, to avoid misreporting sibling withdrawals' status.
- Apply the same fix to `findMatchingWithdrawal` in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`.

### Proof of Concept
1. Build an intent with two `ft_withdraw` withdrawals of the same PoA-bridged token (e.g. `usdc.omft.near`) to two different destination addresses/amounts, submitted as one NEAR transaction.
2. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams: [w0, w1], intentTx })`. Internally each promise calls `PoaBridge.describeWithdrawal({ index: 0 or 1, assetId: 'nep141:usdc.omft.near', tx })`.
3. Suppose the POA bridge processes `w1` (the second withdrawal) first and completes it, while `w0` is still pending. `getWithdrawalStatus` returns an array where the completed entry for `usdc.omft.near` appears first (order is explicitly documented as unsorted).
4. `findMatchingWithdrawal(response.withdrawals, 'nep141:usdc.omft.near')` returns the completed entry regardless of whether `describeWithdrawal` was called for index 0 or index 1.
5. Both `promises[0]` and `promises[1]` resolve to `{ status: "completed", txHash: <w1's hash> }`, even though `w0` has not actually settled — an integrator relying on this to release/credit funds for `w0` would incorrectly treat it as completed using `w1`'s transaction hash.

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,

	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
