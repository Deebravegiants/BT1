This confirms the vulnerability. The HMAC in `Utils::HmacValidator.validate(request)` verifies only `request.to_signable_string`, which returns `@raw_body` alone [1](#0-0) . Meanwhile, `Registry.process` trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` — all sourced directly from unauthenticated HTTP headers — and passes them straight into the handler's `WebhookMetadata` as the tenant identity, without any binding to the HMAC-verified body [2](#0-1) . The `shop` accessor simply reads the `shop-domain` header with no cross-check against the signed payload [3](#0-2) .

### Title
Webhook `shop` (and `topic`/`webhook_id`) header is not covered by the HMAC signature, allowing cross-tenant webhook replay/spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates the request body bytes but not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` nonetheless treats `request.shop` as the authenticated tenant identity when dispatching to the app's webhook handler.

### Finding Description
The identity binding that should hold is: `shop value verified by HMAC == shop value used as tenant identity by the handler`. In this gem it does not hold:

- `Request#hmac` reads the `X-Shopify-Hmac-Sha256` header, and `Request#to_signable_string` returns just `@raw_body` [4](#0-3) .
- `HmacValidator.validate` computes an HMAC over `to_signable_string` (i.e., raw body only) using `Context.api_secret_key` and compares it to the supplied `hmac` [5](#0-4) .
- `Registry.process` validates the HMAC, then immediately reads `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` — all plain header getters with no relation to the signed body — and forwards them as the trusted `WebhookMetadata` passed to the app's registered handler [2](#0-1) .

Because none of `shop-domain`, `topic`, or `webhook-id` are part of the signed bytes, any entity that has ever obtained one valid `(raw_body, hmac)` pair for a webhook delivered to their own shop (e.g., an app-installing shop owner receiving their own webhooks, or a webhook logged/exposed anywhere) can resend that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. The HMAC check still passes (it only checks the body), and the handler will process the event as if it belongs to the attacker-chosen shop — a cross-tenant identity confusion.

### Impact Explanation
This crosses a tenant boundary without needing the app's `client_secret` or any merchant access token — only a previously-observed legitimate webhook payload for *any* shop (including the attacker's own store, which they can trivially install the app on and capture their own webhooks from). Depending on the handler logic, this can be used to inject/replay data attributed to a victim shop, trigger shop-scoped side effects (e.g., mandatory `shop/redact`, `customers/redact` handling) for the wrong tenant, or desynchronize per-shop state the host app maintains keyed by `WebhookMetadata#shop`. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker needs at least one authentic `(raw_body, hmac)` pair, which is easy to obtain by installing the target app on their own development/trial store and capturing the resulting webhook HTTP request, then replaying it against the same endpoint with modified `shop-domain`/`topic`/`webhook-id` headers. No secrets are required — headers are attacker-controlled on the HTTP request the gem's `Registry.process`/`Request.new` accepts as-is.

### Recommendation
Include the tenant-identifying header values (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed string, or otherwise cryptographically bind them to the body, so `to_signable_string` cannot be satisfied by a replayed body with substituted headers. At minimum, document that host applications must independently verify `WebhookMetadata#shop` against the shop that installed the app / the session under which the webhook was registered, since the gem itself does not bind the header-derived shop to the HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body and the genuine `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker crafts a new HTTP POST to the same app webhook endpoint, reusing the exact captured `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (a shop they don't control).
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`; `Utils::HmacValidator.validate(request)` passes because it only checks `raw_body` against the HMAC [6](#0-5) .
4. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [7](#0-6) , causing the host app to process attacker-supplied data as belonging to the victim shop.
