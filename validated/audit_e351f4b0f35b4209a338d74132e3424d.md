### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, but the shop identity (`shop-domain` header) that the gem hands to the app's webhook handler is taken from an unauthenticated HTTP header. This breaks the identity binding `shop authenticated == shop acted upon`: the HMAC proves who signed the *body*, not who the *shop* is, yet `Registry.process` treats the header-derived `shop` as trustworthy and passes it straight into `WebhookMetadata`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates only this body-only HMAC and then trusts `request.shop` (and the other header fields) to construct the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

Because `HmacValidator.validate` (used identically for both OAuth callbacks and webhooks) only checks the signable string returned by `to_signable_string`, and that signable string for webhooks excludes the shop-identifying header entirely, `OpenSSL.secure_compare(computed_signature, received_signature)` will succeed for **any** value of the `shop-domain` header as long as the raw body and its HMAC match: [5](#0-4) 

This is precisely the identity-binding gap called out in the rules: "a field acted on but not covered by the HMAC." A party who has legitimately received a validly-HMAC'd webhook body/signature pair for their own shop (e.g., their own store's install of the app, or any shop whose webhook payload they can observe) can resend that exact `raw_body` + `x-shopify-hmac-sha256` pair to the app's real webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` still returns `true` because it never inspects the shop header, and the handler is invoked believing the (attacker-chosen) `shop` field is authentic.

### Impact Explanation
This allows an unprivileged actor (any merchant/attacker who can obtain one valid `(body, hmac)` pair, e.g. from their own shop's install) to make the host application process fabricated webhook events under an arbitrary victim shop identity. Any app logic that keys data storage, entitlement changes, or triggers on `WebhookMetadata#shop` (order/customer/app-uninstalled processing, GDPR triggers, billing state changes, etc.) can be manipulated cross-tenant — satisfying the "cross-tenant access" Critical impact category, since the app's own trusted identity field for the webhook is forgeable without any secret material.

### Likelihood Explanation
Likelihood is significant for any consumer of this gem's webhook module: no access token, `client_secret`, or privileged credentials are required — only a single genuine `(body, hmac)` pair from any shop (trivially obtainable by the attacker's own store webhook delivery, or from a shop that logs/exposes such payloads). The forged request is a straightforward HTTP replay with one header changed.

### Recommendation
Include the shop-identifying header (and ideally topic/webhook-id/api-version) in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind the shop domain to the signature (e.g., verify the shop domain against session/shop state independently established via OAuth, not solely from the unauthenticated header) before constructing `WebhookMetadata` and invoking the handler.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the shared `client_secret`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker crafts a new POST to the app's webhook endpoint with the same `B` and `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`, which calls `Utils::HmacValidator.validate(request)`; validation only checks `request.to_signable_string` (== `B`) against `H`, which passes: [6](#0-5) 
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"` even though the payload actually originated from the attacker's shop, and the handler processes it as if it were a genuine event for the victim shop.
