Based on my investigation, I've confirmed the key finding.### Title
Webhook shop/topic identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken directly from unauthenticated HTTP headers. The identity binding the app relies on — "this body belongs to shop X" — is never actually verified; only "this body was HMAC-signed with our secret" is verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are read straight from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then trusts `request.topic` and `request.shop` from the headers to route and label the payload for the handler: [3](#0-2) 

`HmacValidator.validate` confirms only that `verifiable_query.to_signable_string` (the body) matches the HMAC — it says nothing about which shop the body came from: [4](#0-3) 

The broken equality is:
`hmac_valid(raw_body) == true` is treated by the caller as if `shop_header == actual_originating_shop`, but the gem never verifies that equality — the HMAC computation excludes the `shop-domain` header entirely.

### Impact Explanation
Any developer can install the target app on their own (even free/dev) Shopify store — this requires no privileged access, no `api_secret_key`, and no leaked credentials. Once installed, Shopify will deliver genuinely, validly-HMAC-signed webhooks to the app for events on that attacker-owned store (e.g. `app/uninstalled`, `orders/create` with attacker-chosen content). Because the HMAC covers only the body, the attacker can capture one such signed request and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers rewritten to name a different, victim shop. `Utils::HmacValidator.validate` still passes because the body/HMAC pair is untouched, and `Registry.process` hands the handler a `WebhookMetadata` claiming `shop: <victim-shop>` with attacker-controlled body content. Any host application that uses `data.shop` to select which merchant's records to write/update (the intended and documented use of this field) can be made to apply attacker-controlled data under another tenant's identity — a cross-tenant integrity/confusion vulnerability rooted entirely in this gem's `Webhooks::Request`/`Registry` implementation.

### Likelihood Explanation
High likelihood: this requires only a self-serve app installation (available to any internet user who can install a public/dev app or is even just an existing merchant using the app) and a basic HTTP replay with header modification. No TLS interception, no credential theft, and no access to `api_secret_key` are needed.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or independently corroborate the `shop-domain` header against known/expected tenants before dispatch:
- Extend `to_signable_string` (or add a secondary check in `Registry.process`) to incorporate the `shop-domain` header, or
- Require host applications/this gem to verify that the shop asserted in the webhook belongs to a shop with an active, previously-registered session/installation before trusting `WebhookMetadata#shop`, rejecting webhooks for shops that never completed an install/have no known offline token.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering Shopify to send a real webhook, e.g. `orders/create`, with headers:
   - `X-Shopify-Hmac-Sha256: <valid HMAC over body B>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Topic: orders/create`
   - Body `B` (attacker fully controls content, e.g. by placing a crafted order in their own store).
2. Attacker replays the exact same body `B` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully (all required headers present); `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `B`, which is unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)`, exactly as demonstrated by the passing test flow at: [5](#0-4) 
   confirming that only body content is checked and the shop header is trusted unconditionally by the framework.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
