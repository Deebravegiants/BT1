### Title
Webhook shop attribution (`shop-domain` header) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC computed by `Utils::HmacValidator.validate` authenticates the payload bytes but not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` nevertheless trusts `request.shop` (read straight from the unauthenticated header) as the tenant identity forwarded to the app's webhook handler. This breaks the equality `shop authenticated-by-HMAC == shop attributed-to-payload`, letting an attacker who legitimately receives webhooks for their own shop replay a valid `(raw_body, hmac)` pair while swapping the `shop-domain` header to impersonate a different shop.

### Finding Description
The webhook signature check is: [1](#0-0) 

`to_signable_string` returns `@raw_body` only, and `shop`/`topic`/`webhook_id`/`api_version` are pulled straight from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

The validator computes the HMAC purely over `to_signable_string`: [3](#0-2) 

And `Registry.process` uses the unauthenticated `request.shop` to build the tenant identity passed to the app's handler, gated only by the body-only HMAC check: [4](#0-3) 

Since a single app has one `api_secret_key` shared across **every** shop that installs it, any shop that installs the app can capture a legitimate, validly-signed webhook (raw body + `x-shopify-hmac-sha256`) that Shopify sent for its own store, then resend the identical body and HMAC to the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header changed to name a different, victim shop. `Utils::HmacValidator.validate` still succeeds because it only checks the body bytes against the shared secret; `Registry.process` then dispatches `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-controlled/attacker-shop body>, ...)` to the app's handler, which trusts `data.shop` as the tenant to act on.

### Impact Explanation
This is a cross-tenant integrity break: an unprivileged actor who only controls one shop's installation of the app can inject arbitrary webhook payloads (bounded to bodies they can legitimately obtain a valid signature for) attributed to any other shop using the app, since the tenant-identifying header is never covered by the signature. Depending on how the host app's `WebhookHandler#handle` uses `data.shop` (commonly to look up/update the tenant's stored record, trigger tenant-scoped side effects, or key a data store), this enables cross-tenant data corruption/injection — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high: no secrets or victim credentials are needed. The attacker only needs to be a legitimate, unprivileged merchant/developer who installs the target app on their own store (a normal, unprivileged path) to obtain valid `(raw_body, hmac)` pairs, then replay them with a forged `shop-domain` header at the app's public webhook endpoint.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind them to the request (e.g., verify them via a signed field inside the JSON payload, or require the app to independently verify the shop is the one associated with the delivery via Shopify's out-of-band webhook metadata). At minimum, document that `request.shop` must not be trusted for tenant attribution without additional verification, since Shopify's own signature does not cover it in this gem's implementation.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC-SHA256(secret, B)`).
2. Attacker resends to the app's webhook endpoint:
   - Body: `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
3. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(secret, B)`, matches `H`, and returns `true` (per `lib/shopify_api/utils/hmac_validator.rb#L12-L31`), since only the body is checked.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` (per `lib/shopify_api/webhooks/registry.rb#L188-L200`) and dispatches it to the app's handler, which now processes attacker-supplied data under the victim shop's identity.
