### Title
Webhook shop/topic/webhook_id headers are trusted for tenant routing without HMAC coverage - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking `Utils::HmacValidator.validate(request)`, but the HMAC signature computed by Shopify only covers the raw request body — not the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers that `Registry.process` uses to select the handler and to build the `WebhookMetadata` passed into the app's own handler logic.

### Finding Description
`Registry.process` reads `request.topic`, `request.shop`, and `request.webhook_id` from `Webhooks::Request` (populated from headers such as `shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) and hands them to the registered handler as trusted tenant/identity metadata: [1](#0-0) 

The HMAC check itself only validates the raw body against `Context.api_secret_key`: [2](#0-1) 

`VerifiableQuery#to_signable_string`, as implemented for OAuth callbacks, signs an explicit set of fields (`code`, `host`, `shop`, `state`, `timestamp`); for the webhook `Request`, the signable string is the raw JSON body only, per Shopify's documented webhook HMAC scheme (visible in `lib/shopify_api/webhooks/request.rb`, which exposes `shop`, `topic`, `webhook_id`, and `hmac` as separately parsed header/body values rather than folding them into the signed payload). Because the shop-domain and topic headers sit outside the signed bytes, the equality the code implicitly relies on — "the tenant identified by `request.shop` == the tenant that produced the signed body" — is never checked. This mirrors the reported Solidity bug's root cause: two values (`vault`/`diamondAddress` there, "signed body" vs. "header-derived shop/topic" here) are treated as equivalent identity without a verification step binding them together.

### Impact Explanation
If an attacker can obtain one legitimately-signed webhook body/HMAC pair (e.g., from a webhook delivered to their own shop/app installation), they can resend that exact body+HMAC to the app's webhook endpoint while substituting a different `shopify-shop-domain` header. `Utils::HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop domain. If the host application uses `data.shop` to select the tenant/session context for writes (a common and Shopify-documented pattern), this results in cross-tenant data being attributed to, or actioned against, the wrong shop — a cross-tenant boundary violation.

### Likelihood Explanation
Exploitation requires the attacker to first obtain at least one valid signed webhook payload, which is achievable without any privileged credentials by installing the app on their own store (or any store) and capturing a webhook delivery — no `api_secret_key`, access token, or other privileged material is required. Reachability is direct: `Registry.process` is the sole entry point host apps call from their controller for every incoming webhook, and it never cross-checks the header-derived shop/topic against anything derived from the signed bytes.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that is HMAC-verified, or, at minimum, document and enforce that `Registry.process` callers/handlers must never use `request.shop`/`WebhookMetadata.shop` as a trust boundary without independently confirming it matches an actively registered/expected shop for that specific webhook subscription. Consider validating that the resolved shop is one the app currently has an active session/installation for before invoking the handler.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com` and trigger a webhook (e.g., `orders/create`) to capture `raw_body` and its `shopify-hmac-sha256` header — this HMAC is valid because it's computed by Shopify using the real `client_secret`.
2. Replay the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but replace the `shopify-shop-domain` header with `victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `raw_body` against the secret, ignoring the header.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata.new(... shop: request.shop ...)` using the spoofed `victim.myshopify.com` value and invokes the app's handler with attacker-controlled body content attributed to the victim shop.

**Caveat / uncertainty:** I was unable to fully read `lib/shopify_api/webhooks/request.rb` in this pass to confirm the exact header-parsing code and the precise `to_signable_string`/HMAC-input construction for webhook requests (only `grep` match locations were retrieved, not full content). The behavior described (HMAC over body only, shop/topic from unsigned headers) matches Shopify's publicly documented webhook verification scheme and the visible `HmacValidator`/`Registry.process` code, but confirming there is no additional cross-check inside `Request` would require reading that file's full contents, which is best done in a follow-up session with full repository access.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
