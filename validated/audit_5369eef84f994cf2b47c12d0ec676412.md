Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header value straight through as the tenant identity for handler dispatch. The identity binding an unprivileged internet user can break is:

`bytes verified (raw_body) == bytes trusted for shop identity (shop-domain header)`

These are not the same bytes, so the shop value that the application logic acts on is never bound to the signature that proves the request came from Shopify.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` and `topic` are read from HTTP headers (`shopify-shop-domain`/`x-shopify-shop-domain`, `shopify-topic`/`x-shopify-topic`) and are never included in `to_signable_string`: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC generically via `Utils::HmacValidator.validate(request)`, which calls `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., it only proves the body bytes are authentic, saying nothing about the headers: [4](#0-3) 

Yet immediately after this check passes, `Registry.process` builds `WebhookMetadata` — the tenant-identifying payload delivered to the host application's handler — directly from `request.shop` (the unauthenticated header), with no cross-check against the body content or against any known session/shop record: [5](#0-4) 

Because the gem hands `WebhookMetadata.shop` (and `.topic`) to the app's handler as trusted values once `HmacValidator.validate` returns `true`, an unprivileged attacker who is themselves a legitimate merchant (and therefore possesses a stream of genuinely-Shopify-signed webhook bodies for their own store) can capture one of their own valid webhook deliveries (a valid `raw_body` + valid `hmac-sha256` header pair) and simply resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still return `true`, because it only checks the (attacker-controlled but genuinely Shopify-signed) body — the header is outside the signed scope. `Registry.process` then invokes the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, causing the application, which relies on this gem's parsed/verified `WebhookMetadata`, to process attacker-supplied webhook content under the identity of a shop the attacker doesn't own.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook consumers: the `shop` value that reaches the handler after "verification" is not actually bound to the cryptographic proof of authenticity. Any host application that uses `WebhookMetadata.shop` to select which merchant's data/session/store record to update (the documented and expected usage pattern of `Registry.process`) can be made to write, delete, or otherwise mutate data under an arbitrary victim shop's identity using attacker-controlled body content. This is a cross-tenant access primitive achieved purely by an internet-facing HTTP header manipulation, requiring no access token, no `client_secret`, and no privileged account — it only requires the ability to be a legitimate webhook source for *some* shop (i.e., running any app-installed store) and the ability to POST arbitrary headers to the app's public webhook endpoint.

### Likelihood Explanation
High. Obtaining a valid `(raw_body, hmac)` pair is trivial for any merchant with the app installed — every real webhook delivery to their own shop qualifies. Webhook endpoints are, by design, public unauthenticated HTTP endpoints reachable directly by an internet user (they are not behind Shopify's TLS-pinned infrastructure once they leave Shopify — an attacker can capture and replay them freely), and nothing in this gem's `Request`/`Registry` code restricts the `shop-domain` header value to match the body's actual originating shop.

### Recommendation
Include the shop-identifying and topic headers inside the signed material, or otherwise independently verify `request.shop` against out-of-band trusted state (e.g., cross-check that `request.shop` corresponds to a shop with an active, known session/installation, and reject if it doesn't correlate with the delivery) before constructing `WebhookMetadata`. At minimum, document loudly that `WebhookMetadata.shop`/`.topic` are *not* part of the HMAC-verified payload and must not be trusted for authorization decisions without additional verification, or extend `to_signable_string` to incorporate topic/shop so `HmacValidator.validate` actually authenticates the full tuple the handler receives.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers any webhook delivery (e.g., `orders/create`), capturing the raw HTTP request Shopify sends to the app's webhook endpoint — this includes a genuinely valid `X-Shopify-Hmac-Sha256` header for that `raw_body`.
2. Attacker resends that exact `raw_body` and `X-Shopify-Hmac-Sha256` header to the same endpoint, but replaces `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`. `Utils::HmacValidator.validate(request)` returns `true` because it only hashes `@raw_body`: [1](#0-0) [4](#0-3) 
4. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...))`: [5](#0-4) 
5. The app's handler, trusting the gem's HMAC-validated `WebhookMetadata.shop`, performs an action (e.g., updates order/customer data, triggers redaction, changes settings) against the victim shop's records using attacker-supplied body content — a cross-tenant write/action the attacker does not have legitimate access to.
