## Title
Client-Controlled MessageID Allows Cross-User Response Hijacking in Gateway WebAPI Handler - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
The gateway's legacy WebAPI trigger handler indexes in-flight user callbacks by a client-supplied `MessageID` with no uniqueness enforcement and no binding to the request's sender/owner. An unprivileged client can supply the same `MessageID` as another user's concurrently in-flight request, overwriting the pending callback entry. When the DON node's response arrives echoing that shared `MessageID`, it is delivered to whichever callback currently occupies the map slot — potentially the attacker's — resulting in the victim's response (or the attacker receiving the victim's, or vice versa) being misdelivered. This mirrors the report's core bug class: an unvalidated, externally influenced value ("swap outcome"/state check) is trusted to resolve which party receives the benefit of an in-flight operation, and an unprivileged actor can race to claim it.

### Finding Description
`ValidatedMessageFromReq` sets the internal `MessageID` directly from the raw, attacker-supplied JSON-RPC request ID with no server-side generation or uniqueness guarantee: [1](#0-0) 

The only constraint enforced anywhere upstream is a length cap: [2](#0-1) 

`HandleLegacyUserMessage` then stores the callback for that ID with a plain, unconditional map write — no check for an existing (still in-flight) entry, and no binding of the entry to the requester's identity/sender: [3](#0-2) 

When a DON node later responds (echoing the same `MessageID`), the handler looks the ID up in the shared map and forwards whatever it finds to "the first response," deleting the entry: [4](#0-3) 

If a second, unrelated request from a different (potentially malicious) sender reuses the same `MessageID` while the first request is still in flight (analogous to Bob observing Alice's transaction and racing it with the same "identifying" value), the second `HandleLegacyUserMessage` call overwrites `savedCallbacks[ID]`. The eventual node response tied to the first sender's `MessageID` is then delivered to the second sender's callback — a direct cross-user response confusion, structurally identical to the report's scenario where an unvalidated post-condition check (`balanceOf`) is exploited via a race to redirect the beneficiary of an in-flight operation. The identical unconditional-overwrite-by-shared-key pattern also exists in the legacy dummy handler: [5](#0-4) 

### Impact Explanation
An unprivileged gateway client can obtain another user's WebAPI trigger response (which may contain data intended only for the victim's registered workflow, e.g. trigger event payloads passed through `web_api_trigger`) by racing a request with a colliding `MessageID`, or conversely cause a victim to silently swallow the attacker's response, corrupting request/response correlation for arbitrary DON-connected callers. This is a request/response impersonation and cross-user confusion bug reachable from any unauthenticated (pre-allowlist-check) gateway client, since the ID collision happens before any per-message authorization/business logic executes.

### Likelihood Explanation
`MessageID` is fully client-controlled and unconstrained beyond a 200-character length limit; there is no per-sender namespacing of the `savedCallbacks` map. Many client implementations use short, low-entropy, or sequential IDs (test/script code in this very repo defaults to `"12345"`), making collisions plausible even without deliberate targeting, and trivial to force deliberately by an attacker who simply submits requests with a chosen ID while a target request is in flight (a race window on the order of the DON round-trip time, i.e. up to `CallbackMaxAgeSec`, default 120s).

### Recommendation
Scope `savedCallbacks` keys by both `MessageID` and the authenticated sender/DON identity (e.g., key by `(sender, donID, messageID)` or a server-generated nonce bound to the connection), and reject/overwrite-protect map inserts when an active, non-expired entry already exists for a colliding key rather than silently overwriting it. Additionally, verify that the responding node's echoed `MessageID`/sender corresponds to the same sender that originally submitted the request before dispatching the callback.

### Proof of Concept
1. Victim (Alice) sends a `web_api_trigger` legacy request through the gateway with `MessageID = "42"`; `HandleLegacyUserMessage` stores `savedCallbacks["42"] = aliceCallback` and forwards the signed request to all DON members.
2. Before any node responds, attacker (Bob) sends his own legacy request also using `MessageID = "42"`; this overwrites `savedCallbacks["42"] = bobCallback` (see `core/services/gateway/handlers/capabilities/handler.go:411-414`, no existing-key check).
3. A DON node responds to Alice's original request; the response message carries `MessageID = "42"` (echoed from the original signed message body).
4. `handleWebAPITriggerMessage` looks up `savedCallbacks["42"]`, finds `bobCallback` (since it overwrote Alice's), deletes the entry, and delivers Alice's trigger response payload to Bob via `bobCallback.SendResponse(...)` (`core/services/gateway/handlers/capabilities/handler.go:148-162`).
5. Bob receives data destined for Alice; Alice's original HTTP call to the gateway times out or never resolves, demonstrating cross-user response confusion caused purely by client-supplied, non-unique `MessageID` values.

func ValidatedMessageFromReq(req *jsonrpc.Request[json.RawMessage]) (*api.Message, error) {
	if req.Version != "2.0" {
		return nil, errors.New("incorrect jsonrpc version")
	}
	if req.Method == "" {
		return nil, errors.New("empty method field")
	}
	if req.Params == nil {
		return nil, errors.New("missing params attribute")
	}
	var m api.Message
	err := json.Unmarshal(*req.Params, &m)
	if err != nil {
		return nil, fmt.Errorf("failed to unmarshal request params: %w", err)
	}
	m.Body.Method = req.Method
	m.Body.MessageID = req.ID
	err = m.Validate()
	if err != nil {
		return nil, err
	}
	return &m, nil

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (d *dummyHandler) HandleLegacyUserMessage(ctx context.Context, msg *api.Message, callback Callback) error {
	d.mu.Lock()
	d.savedCallbacks[msg.Body.MessageID] = &savedCallback{msg.Body.MessageID, callback}
	don := d.don
	d.mu.Unlock()
	params, err := json.Marshal(msg)
	if err != nil {
		return err
	}
	rawParams := json.RawMessage(params)
	req := &jsonrpc.Request[json.RawMessage]{
		Version: "2.0",
		ID:      msg.Body.MessageID,
		Method:  msg.Body.Method,
		Params:  &rawParams,
	}
	for _, member := range d.donConfig.Members {
		err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
	}
	return err
}
