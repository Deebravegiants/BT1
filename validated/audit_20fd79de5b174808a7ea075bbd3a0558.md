### Title
Order-fee escrow trusts a swap-router's Uniswap V2 exact-output call without verifying the actual `feeToken` received - (File: `evm/src/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.placeOrder` escrows `order.fees` worth of the protocol `feeToken` for later payout to whoever finalizes the order. When the user pays this fee in native token, the gateway swaps it through `IDispatcher(hostAddr).uniswapV2Router()` using `swapETHForExactTokens`, then unconditionally records `_orders[commitment][TRANSACTION_FEES] = order.fees` regardless of what the swap actually delivered. This is the same bug class as the external report: a governance/host-configurable external contract (the router) is trusted to transfer an exact token amount, but no before/after balance check confirms it, so bookkeeping can diverge from the gateway's real `feeToken` holdings.

### Finding Description
In `placeOrder`, the fee-escrow branch is: [1](#0-0) 

`swapETHForExactTokens` is called with `order.fees` as the exact output amount, and the code only consumes `amounts[0]` (the ETH actually spent) to adjust the native refund — it never checks `IERC20(feeToken).balanceOf(address(this))` before/after the swap to confirm that `order.fees` units of `feeToken` were actually credited to the gateway. It then unconditionally sets the escrow ledger entry `_orders[commitment][TRANSACTION_FEES] = order.fees`.

`uniswapV2Router()` is read from `EvmHost`, i.e., it is a governance/admin-configurable address — functionally the same trust boundary as the "whitelisted router" in the original report. If this router is misconfigured, upgraded to a non-standard implementation, or otherwise does not deliver the exact requested output (a plausible operational mistake, not requiring the router to be adversarial in the classic sense — any router whose `swapETHForExactTokens` semantics differ even slightly, or that skims/rounds down, breaks the invariant), the gateway records a `TRANSACTION_FEES` liability it does not actually hold.

This liability is paid out later from the same shared `feeToken` balance pool used for all orders: [2](#0-1) 

Because `_orders[...][TRANSACTION_FEES]` is not backed by a verified balance, a shortfall on one order's fee escrow is effectively socialized: `_withdraw` will pull `feeToken` from the gateway's pooled balance to pay this order's beneficiary, potentially consuming `feeToken` that was legitimately escrowed for other orders' fees — leading either to insolvency for later beneficiaries (revert / theft of funds) or silent under/over-payment. The identical unchecked pattern exists in the Tron variant: [3](#0-2) 

By contrast, the surrounding input-transfer logic in the same function does apply the safer before/after balance-check pattern (matching what the original LSSVMPair report recommended) for the actual `order.inputs`: [4](#0-3) 
but this pattern is missing for the fee-token swap path, exactly mirroring the gap flagged in the original report between `_assetRecipient` checks (present) and royalty/fee checks (absent).

### Impact Explanation
Medium: a misconfigured or non-conforming `uniswapV2Router` (set by the host/factory owner, whether by mistake or maliciously) causes the gateway to record more `feeToken` in escrow than it actually received. Since `TRANSACTION_FEES` payouts are drawn from the gateway's shared `feeToken` balance across all orders, this can lead to under-collateralization of the fee pool — later legitimate fee withdrawals can revert (freezing funds/DoS for solvers/relayers awaiting their fee) or, if enough headroom exists from other users' correctly-paid fees, effectively steal fee tokens that back other orders. This directly maps to the report's core concern: fee-recipient accounting depends on an external, reconfigurable, non-audited-per-call component with no balance verification.

### Likelihood Explanation
Low-to-medium likelihood in the strict adversarial sense (requires router misconfiguration or a non-standard router being set by the host owner), but reachable by any user via a single `placeOrder` transaction with `order.fees > 0` paid in native token, with zero additional privilege needed to trigger the accounting divergence once such a router is in place. This mirrors the original report's own risk framing: "the factory owner has no incentive... but if they do (e.g., by accident)..." — the same operational-mistake threat model applies here to `uniswapV2Router()`.

### Recommendation
Snapshot `IERC20(feeToken).balanceOf(address(this))` immediately before and after the `swapETHForExactTokens` call, and set `_orders[commitment][TRANSACTION_FEES]` to the actual measured delta (or revert if it is less than `order.fees`), exactly as already done for `order.inputs` in the fee-on-transfer-token handling elsewhere in the same function. Apply the same fix to the Tron variant of `IntentGatewayV2.sol`.

### Proof of Concept
1. Host owner configures `EvmHost.uniswapV2Router()` to a router implementation that, for whatever reason (bug, non-standard exact-output accounting, partial fill semantics), delivers less than the requested `feeToken` output for a given ETH input while still returning without reverting.
2. A user calls `placeOrder` with `order.fees = X`, paying in native token.
3. `swapETHForExactTokens` delivers `Y < X` of `feeToken` to the gateway, but `_orders[commitment][TRANSACTION_FEES]` is still set to `X`.
4. When the order is later finalized via `_withdraw(..., finalize = true)`, the contract attempts `safeTransfer(beneficiary, X)` of `feeToken`, drawing on the gateway's total `feeToken` balance — which includes fee escrow legitimately backing other unrelated orders — causing either a revert (freezing those other orders' fee payouts) or a shortfall once multiple such orders exist, up to insolvency of the shared fee pool.
