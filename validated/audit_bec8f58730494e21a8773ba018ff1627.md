### Title
Duplicate fee-token entries in `erc20TokenAddresses` let `payRelayFees` charge a signer's wallet a multiple of the EIP-712-signed `maxFee` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`verifyWallet` binds the owner's EIP-712 signature only to `emporiumMessage`, the hash of `ops`, `maxFee`, and `deadline`, and enforces the fee cap with a single check `feeStructure.flatFee > stack.maxFee`. `payRelayFees` iterates `circomData.erc20TokenAddresses` (an array fully controlled by whoever builds the proof/`CircomData`, not covered by the wallet owner's signature) and calls `payRelay`→`sendToRelayFromWallet`→`IHinkalWallet.doSendToRelay` once per array index whose token matches `feeStructure.feeToken` and whose `deltaAmountChanges[i] < 0`. If the fee token is duplicated across multiple indices with negative deltas, the wallet is charged `flatFee` once per occurrence, i.e. a multiple of the signed `maxFee`, even though the single-check cap only ever validates one `flatFee` instance.

### Finding Description
The invariant the question asks to validate is: *(assets leaving the wallet, destination) == (ops, maxFee) the owner signed*.

`verifyWallet` computes the signed hash as: [2](#0-1) 

and enforces the cap with a single scalar comparison: [3](#0-2) 

This check assumes `flatFee` is charged from the wallet at most once per `runAction` call. But `payRelayFees` charges it once *per matching array index*, not once per call: [4](#0-3) 

`circomData.erc20TokenAddresses` and `deltaAmountChanges` are supplied by whoever assembles the `CircomData`/proof for the transaction — not by the signer of the `EmporiumStack`, and not bound by `EMPORIUM_SIGNATURE_TYPEHASH` at all. Nothing prevents the same `feeStructure.feeToken` address from appearing at two (or more) indices of `erc20TokenAddresses`, each with its own negative `deltaAmountChanges[i]` (i.e., each corresponding to a distinct "withdrawal leg" backed by a distinct nullifier/UTXO on the attacker's own shielded side). For each such index, `isFeeToken` is true, `flatFee` is added again, and `payRelay(..., stack.signerAddress, flatFee, feeToken)` is invoked again, each time calling `IHinkalWallet(stack.signerAddress).doSendToRelay(relay, flatFee, feeToken)`, which unconditionally transfers `flatFee` out of the wallet: [1](#0-0) 

So a stack signed with `maxFee = flatFee` can be executed once, on-chain, with `erc20TokenAddresses = [feeToken, feeToken, ...]` (N duplicates) to extract `N * flatFee` from `stack.signerAddress`'s wallet to `circomData.relay` — an amount the owner's signature never authorized (`maxFee` bound only a single flat fee, not the sum across duplicated legs). This does not even require a message replay: it can be achieved on the very first (and only) legitimate use of a valid signed stack, by whoever constructs the `CircomData` for that submission.

Existing guards do not catch this:
- `verifyWallet`'s cap only ever compares one `flatFee` scalar, never a running total actually paid.
- `usedMessages[circomData.emporiumMessage]` only prevents reusing the exact message twice; it does nothing to bound how many times the fee token can repeat inside a single, first-and-only use.
- The EIP-712 hash never includes `circomData.erc20TokenAddresses`, `deltaAmountChanges`, or `feeStructure`, so the owner's signature cannot constrain how many times the fee is charged.
- The circuit-side `signedMessageHash`/EdDSA signature authorizes the shielded-note owner's own balance changes, but that party is not necessarily `stack.signerAddress`, so it provides no protection to the Hinkal-wallet owner whose wallet actually pays the fee.

### Impact Explanation
This lets whoever submits the transaction (the relay/prover building `CircomData`) drain a multiple of the `maxFee` the wallet owner authorized, directly from `stack.signerAddress`'s `HinkalWallet` to `circomData.relay`. This is "theft of protocol/relay fees" beyond what was signed and "moving assets a wallet owner ... never authorised," matching the **High** severity bucket. It is repeatable on every distinct `emporiumMessage` a wallet owner signs (any fee-charging Emporium action), scaling linearly with the number of duplicated fee-token indices the attacker chooses (bounded only by how many distinct UTXO nullifiers/legs the attacker can supply on the shielded side).

### Likelihood Explanation
Preconditions: the attacker needs (a) a valid `EmporiumStack` signature from a wallet owner authorizing some ops with `maxFee = flatFee` and a far-future/valid `deadline`, and (b) the ability to build the accompanying `CircomData`/proof for that submission (i.e., be the party assembling and submitting the `Hinkal.transact` call, which is normal for a relay or for the owner's own submission pipeline if intercepted). Since `erc20TokenAddresses`/`deltaAmountChanges` are freely chosen by whoever builds `CircomData`, and duplicating the fee token merely requires spending additional real nullifiers/UTXOs on the attacker's own shielded side to produce extra negative `deltaAmountChanges[i]` entries, this is straightforward and cheap for anyone in the relay/prover role for that submission. It requires no privileged role.

### Recommendation
Bind the fee cap to the total, not to a single occurrence: sum all `flatFee`/`relayFee` amounts actually paid out of `stack.signerAddress` across the whole `erc20TokenAddresses` loop in `payRelayFees`, and revert if that running total exceeds `stack.maxFee`. Additionally, consider deduplicating/validating `erc20TokenAddresses` (reject duplicate token entries) or including `erc20TokenAddresses`/`feeStructure` in the EIP-712 signed payload so the owner's signature actually constrains which tokens and how many fee-charging legs are permitted.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable`, a `HinkalWallet` for a victim signer, fund the wallet with the fee token.
2. Have the victim sign an `EmporiumStack` (via `_hashTypedDataV4`/`EMPORIUM_SIGNATURE_TYPEHASH`) with `ops` = a harmless op, `maxFee = X` (equal to `feeStructure.flatFee`), `deadline` far in future.
3. Build `CircomData` with `erc20TokenAddresses = [feeToken, feeToken]`, `deltaAmountChanges = [-Y, -Y]` (Y>0, corresponding to two locally-generated valid proof legs backed by attacker's own UTXOs), `feeStructure.feeToken = feeToken`, `feeStructure.flatFee = X`, `relay = attackerRelay`.
4. Call `runAction`/`Hinkal.transact` once with this stack+circomData.
5. Assert: wallet's fee-token balance decreased by `2*X` (not `X`), i.e. `flatFee` was paid twice even though `verifyWallet` only checked `flatFee (X) > maxFee (X)` once and passed. This demonstrates `(assets leaving wallet) = 2*maxFee ≠ maxFee` that the owner's signature authorized.

```text
    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }
```
