## Title
Webhook `shop` header is not covered by the HMAC signature, enabling cross-tenant impersonation via webhook replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read from HTTP headers that are never included in the signed payload, so an attacker who possesses any one valid `(raw_body, hmac)` pair from Shopify can swap the `shop-domain` header to any other tenant's shop and the request still passes HMAC validation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC (which covers `raw_body`) and then dispatches the handler using `request.shop` taken straight from the unauthenticated header: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and compares it to the `hmac` header; it never binds `shop`, `topic`, or `webhook_id`: [4](#0-3) 

This breaks the identity binding: `HMAC(secret, signed_content) == received_hmac` is verified as `HMAC(secret, raw_body)`, while the tenant identity acted upon is `request.shop`, a value entirely outside that signed content. Any entity capable of obtaining one legitimately-signed `(raw_body, hmac)` pair for a given topic — e.g. a merchant who has installed the same app and thus legitimately receives webhooks to their own endpoint — can capture that pair and replay it toward the host application's webhook endpoint with the `shop-domain` header changed to a victim shop. The HMAC still validates because it only ever checked the body, not the header claiming whose shop the event belongs to.

### Impact Explanation
`WebhookMetadata.shop` is the only per-request tenant identifier passed to host-application handlers registered via `Registry.add_registration`/`Registry.process`: [5](#0-4) 

Because the gem hands host applications a "verified" webhook whose `shop` attribute is not actually bound to the signature, any tenant-scoped logic built on `request.shop`/`WebhookMetadata#shop` (e.g., session lookup, data sync, uninstall handling) can be triggered for the wrong tenant using a signature that was only ever valid for the attacker's own shop's body. This is a cross-tenant access issue: a legitimate but unprivileged merchant of the app can cause the host app to act on/for another merchant's shop identity.

### Likelihood Explanation
Any merchant who installs the same third-party app is, by design, a valid recipient of webhooks (Shopify sends real HMAC-signed events to their endpoint for topics such as `app/uninstalled`, whose body content is often generic/empty or has no shop-specific payload). Capturing one such payload+HMAC pair from their own tenant and replaying it with a different `shop-domain` header is trivial and requires no knowledge of `api_secret_key`/`client_secret` — the HMAC used is the one Shopify itself already computed and delivered to the attacker's own endpoint.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-covered signable content, or otherwise cryptographically bind the shop header to the verified payload (e.g., require the handler layer to cross-check `request.shop` against a shop that was independently established via an authenticated session/access-token lookup) before dispatching to webhook handlers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook, e.g. `app/uninstalled`, to the app's public webhook endpoint. They capture the raw request: headers (`x-shopify-hmac-sha256: <hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: app/uninstalled`) and body (e.g. `{}`).
2. Attacker resends the exact same body and `hmac` header to the same endpoint, but rewrites `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches the attacker's legitimate `hmac` — validation passes.
4. The registered handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)`, causing the host application to process an uninstall/event for `victim-shop.myshopify.com` even though Shopify never sent that event for that shop.
