### Title
Malicious swap routes can attach wallet-draining transfers to the caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
A caller-supplied swap route can place attacker-controlled contract code inside a controller strategy invocation; that code can request unrelated `token.transfer` authorization from the original caller, and a poisoned authorization tree will satisfy it. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` funnel caller-controlled `swap: Bytes` into `swap_tokens`, which invokes the configured router after authorizing only the intended input transfer from the controller. [3](#0-2) [4](#0-3) 

The router decodes that XDR payload into a strategy and executes venue contracts named by the route; venue adapters invoke `ctx.hop.pool` directly rather than resolving a protocol-owned pool registry. [5](#0-4) [6](#0-5) 

An attacker-controlled venue can therefore execute arbitrary logic while the original account owner remains an authorized ancestor on the invocation stack, including `unrelated_token.transfer(victim, attacker, amount)`. [7](#0-6) 

Soroban simulation records that nested transfer as a child of the victim’s root controller authorization, and enforcing mode executes it when the victim signs the returned tree. [8](#0-7) [9](#0-8) 

### Impact Explanation
A victim who signs the simulated authorization tree loses tokens unrelated to the lending position, while still receiving a valid swap output and passing the controller’s collateral checks. [10](#0-9) [11](#0-10) 

This is theft of user funds because the attacker controls the recipient and amount through the rogue venue rather than merely receiving the declared swap input. [12](#0-11) [13](#0-12) 

### Likelihood Explanation
The attacker must get the victim to submit a crafted route and sign the authorization tree returned by simulation, but no privileged role, leaked key, upgrade, malicious oracle, or protocol-owned-contract compromise is required. [14](#0-13) [15](#0-14) 

The controller’s exact input authorization does not bound the attack because the rogue transfer uses the victim’s separate address authorization rather than the controller’s contract authorization. [1](#0-0) [16](#0-15) 

### Recommendation
Do not rely on output measurement or the exact controller input grant to bound user-supplied route execution. [10](#0-9) 

Clients and route builders should reject any authorization tree containing children other than the expected input transfer, and contracts should prefer allowlisted venue contracts or a route representation that cannot substitute arbitrary executable addresses. [16](#0-15) [2](#0-1) 

### Proof of Concept
1. Deploy a rogue venue whose hop handler calls `victim_token.transfer(victim, attacker, victim_balance)` when the router invokes its `swap` function. [17](#0-16) 
2. Build a `swap_collateral` transaction for the victim that routes a normal collateral token to a normal output token through that rogue venue. [18](#0-17) [12](#0-11) 
3. Simulate the transaction; the rogue `transfer` is recorded beneath the victim’s root `swap_collateral` authorization. [19](#0-18) 
4. Have the victim sign and submit that authorization tree; the route returns the promised output while the extra transfer moves the unrelated wallet token to the attacker. [9](#0-8) 
5. The controller succeeds because it only verifies that the router did not overspend the declared input and that positive output was received. [10](#0-9)

```rust
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
```

**File:** docs/explanation/threat-model.md (L154-164)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
```
