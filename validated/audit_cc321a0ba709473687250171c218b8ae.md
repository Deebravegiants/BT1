### Title
Webhook shop-domain header is not covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw body against the app's shared `client_secret`. The `shop` (and `topic`/`webhook_id`) values used to build `WebhookMetadata` and dispatch to the app's handler are taken straight from HTTP headers that are never included in the signable string, so the identity binding "the shop asserted by the request" == "the shop the HMAC actually vouches for" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors simply read unauthenticated headers: [2](#0-1) .

`Registry.process` validates the HMAC of the body against the single, app-wide `Context.api_secret_key` (shared across every shop that installs the app), and, on success, immediately builds `WebhookMetadata` from the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, and hands it to the registered handler: [3](#0-2) . The HMAC check itself only proves the body/secret pair is valid — it says nothing about which shop the body belongs to, because `secret` is the same for all shops using this app: [4](#0-3) .

Because any merchant can install the same app on their own store and receive a legitimately Shopify-signed `(raw_body, X-Shopify-Hmac-Sha256)` pair for their own shop, that unprivileged merchant can replay the exact same body/HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. `Utils::HmacValidator.validate` still returns `true` (the HMAC only covers the body, which is unchanged), and the handler is invoked with `data.shop` set to the attacker-chosen victim shop domain — despite the request never having come from, or being about, that shop.

The broken identity binding is exactly the class flagged in the source report: a field (`shop`) that is acted upon by the handler but not covered by the HMAC that "authenticates" the request.

### Impact Explanation
This is a cross-tenant identity-spoofing primitive: an unprivileged internet user who is merely a legitimate (even free/trial) installer of the target app on their own store can cause the app's webhook handler to process attacker-controlled webhook bodies while asserting them to originate from another merchant's shop (`data.shop`). Depending on what the host application does with `data.shop` (e.g., looking up that shop's stored session/access token to act on the webhook, writing data keyed by shop, billing, GDPR-related flows such as `customers/redact` handling, etc.), this can lead to cross-tenant data corruption or actions being taken against a victim shop's account using only content the attacker legitimately signed for their own shop. This satisfies the "cross-tenant access" Critical-impact category, since the tenant boundary (`shop`) that host applications are documented to rely on (`docs/usage/webhooks.md`, "`shop` — The shop domain of the webhook") is not actually authenticated by this gem.

### Likelihood Explanation
Likelihood is high for any application that trusts `WebhookMetadata#shop` as an authenticated tenant identifier, which is exactly what the gem's own documentation instructs (`data.shop` is documented as trustworthy webhook metadata, and `Registry.process` is documented as verifying "the request did indeed come from Shopify"). No secrets, tokens, or privileged access are required beyond installing the app once as an ordinary merchant, which is the normal, expected way to interact with any Shopify app.

### Recommendation
Bind the shop identity to the authenticated payload instead of trusting the raw header:
- Include `shop` (and ideally `topic`/`webhook_id`) inside the HMAC-signed material, or
- Cross-check the `X-Shopify-Shop-Domain` header value against the shop embedded in the webhook body payload itself (most Shopify webhook payloads include shop-identifying fields), or
- Require callers of `Registry.process` to independently verify that the shop domain in the request maps to a shop that actually has this specific webhook subscription registered (e.g., via the `webhook_id`, cross-checked against Shopify's Admin API), rather than trusting the header outright.
At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not itself authenticated by the HMAC check and must not be treated as a verified tenant identifier without additional server-side verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, obtaining legitimate webhook deliveries signed with the app's single `client_secret`.
2. Shopify delivers a webhook to the app for `attacker.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker replays an HTTP POST to the app's webhook endpoint with the same body `B` and same header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` reads `H` from the header, `to_signable_string` returns `B` unchanged, so `Utils::HmacValidator.validate` succeeds. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., the app now believes body `B` originated from `victim-shop.myshopify.com`.
