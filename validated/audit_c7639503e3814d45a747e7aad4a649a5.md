Found it. Every other flow that takes an untrusted `shop` string (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) calls `Utils::ShopValidator.sanitize!(shop)` before building the session/HTTP client that will carry `client_id`/`client_secret` to `https://#{shop}/admin/oauth/access_token`. `TokenExchange.exchange_token`, however, takes `dest_shop = jwt_payload.shop` straight from the JWT `dest` claim and never runs it through `ShopValidator`, then does `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` and `Clients::HttpClient.new(session: shop_session, ...)`, whose `initialize` builds `@base_uri = "https://#{session.shop}"` unconditionally.

### Title
`TokenExchange.exchange_token` sends `client_secret` to an unvalidated host taken from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the token-exchange request host solely from the session token's `dest` claim, without ever validating it against `ShopifyAPI::Utils::ShopValidator`, unlike every sibling OAuth flow (`ClientCredentials`, `RefreshToken`, `TokenExchange.migrate_to_expiring_token`) in the same file/module, which explicitly call `Utils::ShopValidator.sanitize!(shop)`.

### Finding Description
`JwtPayload#shop` returns `@dest.gsub("https://", "")` verbatim [1](#0-0) , with only `aud == Context.api_key` checked [2](#0-1) ; there is no check that `dest` (or `iss`) is a trusted `*.myshopify.com`/`*.myshopify.io`/etc. domain, the way `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` enforces elsewhere [3](#0-2) .

`exchange_token` takes this unvalidated value directly as `dest_shop` and builds a session from it: [4](#0-3) . That session is passed to `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`, which builds `@base_uri = "https://#{api_host || session.shop}"` from `session.shop` with no validation of its own [5](#0-4) . The subsequent POST body contains `client_id` and `client_secret` in cleartext [6](#0-5) .

Contrast this with `migrate_to_expiring_token` in the very same module, which validates first: [7](#0-6) , and with `ClientCredentials.client_credentials` [8](#0-7)  and `RefreshToken.refresh_access_token` [9](#0-8) , which do the same.

The binding this breaks is: **the host that receives the app's `client_id`/`client_secret` must equal a host validated as belonging to Shopify's trusted domain set**. In `exchange_token`, "host that receives the secret" = raw JWT `dest` claim, while "host validated as trusted" = nothing — the equality is never checked, unlike the other three sibling methods.

### Impact Explanation
The library's own JWT decoding (`JWT.decode(token, api_secret_key, ..., algorithm: "HS256")`) means a session token cannot be forged without the app's `api_secret_key`, so in the fully-correct deployment this is inert. However, because `JwtPayload` performs no domain allow-listing on `dest`/`iss` the way `ShopValidator` does everywhere else in this codebase, this method is the sole exception to the gem's own consistent, self-imposed invariant that any shop-derived host used to transmit `client_secret` must first pass `ShopValidator`. Should a signed session token ever carry a `dest` that is not a genuine, trusted Shopify admin host (e.g., due to a host-side bug composing the JWT, a non-shopify-controlled issuer accepted by a misconfigured relying app, or any future change in how `dest` values are produced/validated upstream), this code path would silently send the app's `client_id` and `client_secret` to that host — an SSRF carrying the app's OAuth client credentials. This is a real gap relative to the rest of the codebase's defense-in-depth, even though today's exploitability is bounded by JWT signature integrity.

### Likelihood Explanation
Low-to-moderate on its own (bounded by JWT signature verification), but the missing validation is a genuine inconsistency in this gem's code: three of four `client_secret`-transmitting host-selection sites here validate the shop domain, and this one — which is exactly the code path most directly triggerable via untrusted, browser-supplied App Bridge session tokens — does not.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalently validate `dest`/`iss` inside `JwtPayload`) before constructing `shop_session`/`HttpClient`, mirroring the pattern already used in `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`.

### Proof of Concept
Not independently exploitable purely from within this gem without also controlling a validly-signed JWT whose `dest` is not a genuine Shopify host — which requires either the app's `api_secret_key` or an upstream defect in how Shopify (or a relying party) issues/validates the `dest` claim. The concrete code-level gap is demonstrable by diffing `exchange_token` against its sibling `migrate_to_expiring_token` in the same file: [4](#0-3)  vs. [7](#0-6) .
