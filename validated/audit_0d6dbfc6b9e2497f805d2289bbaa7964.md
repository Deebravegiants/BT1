### Title
Permanent market freeze from unbounded RAY-value accrual overflow - (File: `contracts/pool/src/interest.rs`)

### Summary

A sufficiently large market can accrue until `borrowed * borrow_index` or `supplied * supply_index` no longer fits in `i128`, after which every market operation reverts during mandatory pre-operation accrual. Once this state is reached, suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot act on the affected market. [1](#0-0) 

### Finding Description

`update_indexes` is permissionless and forwards caller-selected `HubAssetKey`s to the pool after only ordinary caller authorization. [2](#0-1)  The pool loads each market and invokes `interest::global_sync`, which compounds interest in bounded time chunks until `elapsed_ms` reaches zero. [3](#0-2) [4](#0-3) 

The vulnerable boundary is not the configured borrow-index ceiling: the intermediate scaled market value can exceed `i128::MAX` before the index reaches `MAX_BORROW_INDEX_RAY`. [5](#0-4)  At that point, checked fixed-point conversion panics with `MathOverflow`, and the accrual rolls back without advancing `last_timestamp`, so the same overflow is encountered on every later attempt. [6](#0-5) [7](#0-6) 

All ordinary pool mutations use `synced_market`, which loads state and calls `global_sync` before the requested operation. [8](#0-7)  Consequently, `supply`, `borrow`, `withdraw`, `repay`, `net_settle`, `seize_positions`, `recapitalize`, `flash_loan`, `create_strategy`, `claim_revenue`, and even rate-model replacement all traverse the same failing accrual path. [9](#0-8) [10](#0-9) 

An unprivileged attacker who controls enough assets can create the necessary state through `supply(caller, account_id, spoke_id, hub_asset, amount)`, collateralize an account, call `borrow(caller, account_id, spoke_id, hub_asset, amount)` near maximum utilization, wait while interest accrues, and then trigger the terminal overflow with `update_indexes(caller, vec![hub_asset])`. [11](#0-10)  The repository’s test demonstrates this sequence using one billion 18-decimal tokens at 98% utilization and shows that a later `update_indexes` fails before the index cap engages. [12](#0-11) 

### Impact Explanation

This is a permanent freezing-of-funds condition for the affected market: repayment, withdrawal, liquidation, bad-debt handling, and recapitalization all fail before they can reduce the unrepresentable book value. [8](#0-7) [13](#0-12)  Because failed transactions roll back `last_timestamp`, waiting cannot move the market past the overflow; increasing time only enlarges the target accrual. [4](#0-3) [7](#0-6) 

Rate-model changes also cannot provide a non-upgrade recovery path because `replace_rate_model` first commits a synced market under the old model. [10](#0-9)  The result therefore satisfies the permanent-freezing impact class for every supplier and borrower using that market, subject to the market reaching the representable-value boundary. [1](#0-0) 

### Likelihood Explanation

The trigger requires an unusually large book and sustained high utilization, but it does not require privileged access, oracle manipulation, malformed parameters, a token defect, or control over governance. [11](#0-10)  The admitted domain allows very large token amounts and indexes, while the project documentation explicitly notes that accrued market values can overflow before the index ceiling and block repayment or withdrawal. [14](#0-13) 

The existing harness test uses a billion-token 18-decimal market, raised caps, 98% utilization, and repeated yearly advances to reach the cliff, so practical likelihood depends heavily on token supply, admitted caps, collateral availability, and the configured rate curve. [15](#0-14)  Once those preconditions exist, the terminal call is reliably executable by any authorized address through `update_indexes`. [2](#0-1) 

### Recommendation

Cap each accrual step by the maximum index that keeps both `borrowed * borrow_index` and `supplied * supply_index` representable, before evaluating interest or protocol revenue. [16](#0-15)  The cap should be derived from the larger scaled balance as approximately `i128::MAX / scaled_balance`, with equivalent handling for every intermediate value used by `accrue_step`, rather than relying only on `MAX_BORROW_INDEX_RAY`. [17](#0-16) 

Alternatively, perform accrual on wider intermediary values or calculate interest from scaled balances without materializing an overflowing RAY market value, then clamp indexes to the highest safe value. [16](#0-15)  Add a regression test proving that a market approaching the value ceiling reaches a stable interest-free plateau and still accepts at least one repayment and withdrawal. [1](#0-0) 

### Proof of Concept

The repository already contains a deterministic proof of concept in `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`. [18](#0-17) 

1. Configure an 18-decimal market with the steep `xlm_curve`, disable maximum-utilization enforcement, and raise the supply and borrow caps enough to admit the position. [19](#0-18) 
2. Supply `principal = 1_000_000_000 * 10^18` base units of the debt asset and borrow `principal * 98 / 100` against sufficient separate collateral. [20](#0-19) 
3. Advance ledger time year by year and call `controller::update_indexes(caller, vec![HubAssetKey { hub_id, asset }])`. [21](#0-20) 
4. The call eventually returns contract error `MathOverflow` while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [22](#0-21) 
5. Subsequent `withdraw` and `repay` calls fail with the same `MathOverflow` because both paths accrue the market before mutating positions. [13](#0-12) [8](#0-7)

```rust
/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```

```rust
/// Adds two raw values, panicking with `GenericError::MathOverflow` on overflow.
fn checked_add_raw(env: &Env, a: i128, b: i128) -> i128 {
    a.checked_add(b)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Subtracts `b` from `a`, panicking with `GenericError::MathOverflow` if either
/// operand is negative or the subtraction would go negative.
fn checked_sub_nonneg(env: &Env, a: i128, b: i128) -> i128 {
    if a < 0 || b < 0 || b > a {
        panic_with_error!(env, GenericError::MathOverflow);
    }
    a - b
```

```markdown
| Bound | Consequence |
|---|---|
| Asset decimals 0..=18 | Exact token-to-RAY upscaling. Below 3: collateral only, no flash loans, no liquidation fee, its account's only supply position, at least 2 whole units while in debt |
| Both indexes initially RAY; ceiling 10^36 | 10^9 times initial index; protocol constants |
| Supply-index floor 10^24 | At most 1,000 times the shares minted at index one for the same deposit |
| Borrow APR maximum 2 RAY | 200% annual rate; not a bound on balance growth alone |
| Token-to-RAY input maximum `i128::MAX / 10^(27-d)` | About 170.14 billion whole tokens, before other limits |
| Deposit conversion at the supply-index floor | About 170.14 million whole tokens before scaled-share overflow |

The token-to-RAY maximum is also the admitted cap maximum. Accrued position
values and market totals must independently fit the RAY domain; valid caps and
bounded indexes do not guarantee that future accrual fits. Value overflow can
occur before the index ceiling and block repayment/withdrawal because those
operations accrue first. At the borrow-index ceiling, further accrual produces
no borrower interest. No dedicated ceiling alarm is emitted.
```
