## Title
Webhook `shop`/`topic` identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying that the HMAC header matches `HMAC(client_secret, raw_body)`. The `shop`, `topic`, and `webhook_id` values — which are the fields the handler actually acts on (tenant routing, event dispatch) — come from plain HTTP headers that are **not** part of the signed material. This breaks the identity binding `shop_header == shop_that_produced_the_signed_body`, allowing an attacker who possesses any one valid `(raw_body, hmac)` pair for the app's shared secret to relabel it as belonging to an arbitrary shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are read straight from headers with no cryptographic linkage to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then trusts the unrelated header-derived `shop`/`topic` to route and label the event: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the supplied HMAC — for a `Request`, `to_signable_string` is `raw_body` alone: [4](#0-3) 

The intended identity binding is:
```
hmac == HMAC(secret, raw_body ∧ shop ∧ topic)
```
The actual check is:
```
hmac == HMAC(secret, raw_body)   // independent of shop/topic
```
So the same `(raw_body, hmac)` pair is valid for **every** shop header value, because both sides of the app's per-secret signature are identical regardless of which shop the header claims. This is the same bug class as the referenced report: a field the caller acts on (`shop`) is not covered by the authentication check that is supposed to bind it.

### Impact Explanation
This is a cross-tenant confusion vector (Critical, per the accepted impact list: "cross-tenant access"). An unprivileged actor who can install the app on their own (attacker-controlled) shop — a normal, free action requiring no special credential — receives genuine webhook deliveries signed with the app's shared `client_secret`. Because the signature never binds `shop`/`topic`, the attacker can replay the exact same `raw_body` + `hmac` to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for a victim shop. `Registry.process` accepts it as authentic and dispatches `WebhookMetadata` labeled with the victim shop's identity to the app's handler, letting attacker-controlled body content be processed and stored under another tenant's identity (forged `orders/create`, `app/uninstalled`, `customers/redact`, etc.).

### Likelihood Explanation
Likelihood is high for any multi-tenant app using this gem's webhook `Registry`: obtaining one valid `(body, hmac)` pair only requires installing the app on any shop (including a free development store), which is available to any internet user. No access to `client_secret`, tokens, or TLS interception is required — only observation of one's own legitimately-delivered webhook, then a single forged HTTP POST to the public webhook endpoint with a different `shop-domain` header.

### Recommendation
Bind the authenticated identity fields into the signed material verified by `HmacValidator`, e.g. include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (or otherwise cryptographically bind them, mirroring how `AuthQuery#to_signable_string` includes `shop`/`host`/`state`), so that `HmacValidator.validate` fails if any header used for tenant routing is altered relative to what was actually signed by Shopify for that specific shop/topic.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (unprivileged, free action) and triggers any webhook topic the app subscribes to.
2. Attacker's endpoint (or a network capture on the attacker's own traffic) records the delivered `raw_body` and its `X-Shopify-Hmac-Sha256` header — both are valid under `HMAC(client_secret, raw_body)`.
3. Attacker crafts a new HTTP POST to the victim app's public webhook route with the **same** `raw_body` and `hmac`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and any desired `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — unchanged — and succeeds: [3](#0-2) 
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-supplied body, processing forged data under the victim tenant's identity.
