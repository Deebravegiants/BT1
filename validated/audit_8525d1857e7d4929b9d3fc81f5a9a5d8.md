Based on the investigation, I found a genuine cache key scoping issue in the HTTP capability gateway's response cache, which is analogous to the Squid "Collapsed Forwarding" bug class (private response served to wrong client due to incorrect request-identity comparison).

### Title
Response cache key omits WorkflowID, allowing cross-workflow response confusion within the same owner - (File: `core/services/gateway/handlers/capabilities/v2/response_cache.go`)

### Summary
The `responseCache` used by the HTTP Action capability caches outbound HTTP responses keyed by `req.Hash()`. The test suite explicitly documents and asserts that `WorkflowID` is **excluded** from that hash, while `WorkflowOwner`, method, URL, headers, and body are included: [1](#0-0) . This means two different workflows belonging to the same owner (e.g. two separate CRE workflow deployments, versions, or concurrently running workflow instances under one owner) that issue outbound HTTP Action requests with identical method/URL/headers/body will collapse onto the same cache entry.

### Finding Description
`responseCache.Fetch` and `responseCache.Set` compute the cache key purely from `req.Hash()` [2](#0-1) , and `Set` stores a response keyed only by that same hash [3](#0-2) . The struct comment states the hash is derived from "method, URL, headers, body, workflowOwner" [4](#0-3) , and the accompanying test explicitly verifies WorkflowID is dropped from the hash while WorkflowOwner is retained [5](#0-4) .

However, the module's own README claims stronger isolation than the code provides: "**Workflow Isolation**: Cache entries are scoped by workflow ID to prevent cross-workflow data leakage" [6](#0-5) . This is a direct contradiction between documented intent and actual behavior — the cache is scoped by owner, not by workflow.

The request flow (`makeOutgoingRequest` → `createHTTPRequestCallback` → `responseCache.Fetch`/`Set`) treats `req` as fully attacker/node-controlled input parsed from an unmarshaled JSON-RPC payload sent by a workflow node [7](#0-6) . Because `WorkflowID` isn't part of the key, a workflow (or a malicious/compromised workflow acting on the same owner's behalf) with `CacheSettings.MaxAgeMs > 0` and matching method/URL/headers/body can retrieve a cached response that was generated for, or intended to be scoped to, a different workflow of the same owner. This mirrors the Squid Collapsed Forwarding bug class: an incorrect/incomplete identity comparison (workflow-scope omitted) causes a response meant for one logical requester context to be served to another.

### Impact Explanation
If per-workflow context (e.g. distinct workflow instances issuing structurally identical requests, such as identical third-party API calls with owner-level shared credentials in headers/body) is intended to be isolated for correctness or confidentiality reasons — as the README explicitly promises — this gap allows cross-workflow response reuse. Depending on what the cached body contains (e.g., data meant only for a specific workflow's logic, or responses whose freshness/context matters per-workflow), this can lead to stale/foreign data being fed into a different workflow's decision logic, potentially affecting on-chain actions taken by that workflow.

### Likelihood Explanation
Likelihood is moderate: it requires two workflows under the same owner to issue byte-identical outbound HTTP requests (method, URL, headers, body) with `CacheSettings.Store=true`/`MaxAgeMs>0`, which is plausible for workflows re-using common request templates or multiple versions/instances of the same workflow logic operated by one owner.

### Recommendation
Include `WorkflowID` (or a workflow-scoped identifier) in the cache key computed by `OutboundHTTPRequest.Hash()`, or otherwise composite the cache key with `WorkflowID` in `responseCache.Fetch`/`Set`, so the implementation matches the documented "Workflow Isolation" guarantee in the README. At minimum, reconcile the README claim with the actual per-owner (not per-workflow) scoping so operators aren't relying on isolation guarantees the code doesn't provide.

### Proof of Concept
1. Workflow A (owner `X`, workflowID `wf-A`) issues an `HTTPAction` request: `GET https://api.example.com/data`, headers `{Content-Type: application/json}`, `CacheSettings{Store: true, MaxAgeMs: 600000}`. Response `R1` is fetched and cached under `req.Hash()` (which incorporates owner `X` but not `wf-A`).
2. Workflow B (same owner `X`, workflowID `wf-B`, different workflow logic) issues a structurally identical outbound request (same method/URL/headers/body) with `CacheSettings{MaxAgeMs: 600000}`.
3. `responseCache.Fetch` computes the same `req.Hash()` (owner matches, workflowID ignored) and returns cached response `R1` to Workflow B without making a fresh request — confirmed directly by the test asserting identical hashes despite different `WorkflowID` values [1](#0-0) .

func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {

	defer rc.cacheMu.Unlock()
