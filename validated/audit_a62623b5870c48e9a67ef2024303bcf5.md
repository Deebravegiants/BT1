### Title
`removeChain` on `HyperFungibleToken`/`WrappedHyperFungibleToken` can permanently freeze burned tokens - ([File: sdk/packages/core/contracts/apps/HyperFungibleToken.sol])

### Summary
`HyperFungibleToken.removeChain()` (and its `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` counterparts) lets the owner delete a `_supportedChains[chainId]` entry with no check for outstanding in-flight transfers to or from that chain, mirroring the reported `StakingModule.removePlugin()` issue where removing an active component with claimable/owed funds strands user assets with no recovery path.

### Finding Description
`HyperFungibleToken.send()` burns the caller's tokens on the source chain and dispatches an ISMP POST request to the destination chain's peer contract [1](#0-0) . The corresponding tokens are only re-created either by `onAccept()` minting on the destination once the message is delivered, or by `onPostRequestTimeout()` re-minting to the original sender if the message times out without delivery [2](#0-1) .

Both of these recovery paths depend on `_supportedChains[chainId]` still being populated for the relevant chain at the time the message is processed:
- `onAccept()` reverts with `UnsupportedChain()` if `_supportedChains[request.source]` is empty [3](#0-2) .
- `_buildDispatchPost()` (used by `send()`/`quote()`) also reverts if the destination is unregistered [4](#0-3) .

`removeChain()` performs an unconditional `delete _supportedChains[chainId]` with no check for pending/in-flight requests that still reference that chain: [5](#0-4) 

If the owner calls `removeChain(sourceChainId)` on the destination chain after a user has already burned tokens on the source chain and dispatched a POST request (i.e., after `send()` executed on the source, before delivery completes on the destination), the subsequent `onAccept()` call for that in-flight request will revert on the destination with `UnsupportedChain()` — because `expectedSource.length == 0` — even though the tokens were already irreversibly burned on the source. This is the destination-chain analog of `EvmHost`/`ismp-grandpa`'s pattern of removing a whitelisted counterpart mid-flight (`docs/content/developers/polkadot/solochains.mdx` documents the identical remove-whitelist hazard for consensus proofs) [6](#0-5) . Unlike the timeout path, which relies on the *source* chain's `_supportedChains` mapping remaining valid to accept the timeout callback (`onPostRequestTimeout` itself has no such check), the failure occurs entirely on the destination side and outside the sender's control.

Because the token is "its own bridge application" with "no shared custody pool" and burns on the source with no escrow, once tokens are burned there is no other path to recreate them for the user besides either successful `onAccept()` delivery or a timeout-triggered refund — both of which are gated by the mutable `_supportedChains` mapping the owner can wipe unilaterally and without any check for requests still in flight.

### Impact Explanation
Any owner-initiated `removeChain()` call executed while a legitimate cross-chain transfer is in flight (dispatched but not yet delivered, and if the timeout is set long or `0`/never-expiring) can cause user funds to be burned on the source chain with no matching mint on the destination and no refund, permanently destroying user value. This matches the "Impact" criteria of concrete permanent freezing/loss of funds. Given the multi-chain, asynchronous nature of ISMP delivery (relayer-dependent timing), a normal governance/config change (removing a deprecated or misconfigured peer) can unintentionally strand any transfer that was mid-flight at that moment.

### Likelihood Explanation
This requires the privileged owner to call `removeChain()`, which the report rules explicitly permit as an "unprivileged message dispatcher" reachable analog only insofar as the *end-user* who dispatched the `send()` is unprivileged and has no way to prevent or foresee the config change; the vulnerable action's trigger (owner reconfiguration) is a normal, expected maintenance operation (e.g., deprecating a compromised or migrated peer) rather than requiring malicious intent, and the resulting fund loss is triggered purely by the ordinary sequence of a user's `send()` racing an unrelated administrative `removeChain()`.

### Recommendation
Before deleting a chain entry in `removeChain()`, either (a) require a delay/cool-down at least as long as the maximum in-flight message timeout before the mapping is cleared, (b) retain the old peer mapping long enough to still validate/deliver in-flight `onAccept()`/timeout callbacks for that chain while blocking new `send()`s to it (split "disabled for new sends" from "removed for delivery validation"), or (c) track outstanding dispatched-but-undelivered commitments per chain and require they be zero (or explicitly expired/refunded) before allowing full removal, analogous to checking `totalClaimable()`/pending balances before removing a plugin.

### Proof of Concept
1. Owner calls `addChain(destChainId, peerModuleId)` on the source-chain deployment and the mirror `addChain(sourceChainId, peerModuleId)` on the destination-chain deployment.
2. User calls `send({dest: destChainId, to: recipient, amount: X, timeout: T, ...})` on the source chain: `_burn(msg.sender, X)` executes and a POST request commitment is emitted (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol` lines 264-282).
3. Before a relayer delivers the request to the destination chain, the destination-chain owner calls `removeChain(sourceChainId)`, clearing `_supportedChains[sourceChainId]`.
4. When the relayer later delivers the request, `onAccept()` reads `expectedSource = _supportedChains[request.source]`, finds it empty, and reverts with `UnsupportedChain()` — the message can never be successfully processed on the destination.
5. If `T` is large or the timeout window has not yet elapsed, the user cannot yet claim a timeout refund either; even after timeout, the refund path re-mints on the *source* chain via `onPostRequestTimeout`, which is independent of the destination's `removeChain` call, but if the owner also symmetrically removed the chain on the source side (a natural companion action when deprecating a peer), no future delivery/timeout handling for that route is guaranteed and the burned `X` tokens are unrecoverable.

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout memory incoming) public virtual override onlyHost whenNotPaused {
        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
        emit Refunded({to: refundee, amount: message.amount});
    }
