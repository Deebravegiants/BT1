### Title
Webhook `shop`, `topic`, and `webhook-id` headers are trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies solely that the request *body* was signed with `Context.api_secret_key`. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are never included in the signed payload, yet `Registry.process` reads them straight off the unauthenticated headers and forwards them to the app's handler as `WebhookMetadata`, which the host application uses to identify the tenant (`shop`) that the event belongs to.

### Finding Description
The identity binding that should hold is:

`shop bound by HMAC == shop delivered to the handler`

Instead, the code produces:

`shop delivered to handler == shop-domain header (unauthenticated) != shop covered by HMAC (none)`

- `Request#to_signable_string` only returns the raw body: [1](#0-0) 
- `Request#shop`, `#topic`, and `#webhook_id` are parsed directly from headers with no cryptographic tie to the body: [2](#0-1) 
- `HmacValidator.validate_signature` only ever hashes `verifiable_query.to_signable_string` (the body), never the headers: [3](#0-2) 
- `Registry.process` validates the HMAC and then unconditionally trusts `request.shop`/`request.topic`/`request.webhook_id` to build `WebhookMetadata`, which is the only tenant/shop information passed to the app-supplied handler: [4](#0-3) 
- `WebhookMetadata.shop` is a plain, unauthenticated `String` field consumed by every `WebhookHandler#handle`: [5](#0-4) 

Because the HMAC only binds the body bytes, any two webhook deliveries that happen to carry the same body (e.g., an empty `{}` payload, or a payload an attacker can otherwise obtain together with its valid HMAC from a webhook legitimately delivered to their own shop/app installation) produce an *identical, still-valid* signature no matter what `shop-domain`, `topic`, or `webhook-id` header values are substituted. An unprivileged internet user who can capture one genuine `(raw_body, hmac)` pair — for instance from webhooks Shopify sends for their own store/installation — can replay that exact body+HMAC to the app's webhook endpoint while swapping the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header to name a different shop. `HmacValidator.validate` still returns `true` because it never looks at those headers, and `Registry.process` dispatches the handler with the attacker-chosen `shop` value, causing the host application to process/attribute the event to a shop the attacker does not control.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is meant to establish: the HMAC is supposed to prove "this event genuinely happened for shop X," but shop attribution is derived from an unauthenticated header. A host application that (as intended by this gem's own `WebhookMetadata.shop` API) uses `data.shop` to look up per-tenant state, credentials, or to gate business logic can be made to act on/for a shop the attacker doesn't own, using only a body+HMAC pair the attacker legitimately possesses for a webhook of their own. This is a cross-tenant identity-confusion vulnerability rooted entirely in this gem's signature-verification code, not misuse by the host app of a documented contract (the gem itself asserts `shop` was validated by the same `process` call that checked the HMAC).

### Likelihood Explanation
High for an attacker who can obtain any one valid `(body, hmac)` pair — trivially available to anyone who installs the app on their own development/test shop and observes the webhooks Shopify sends them (or any topic/body combination is fixed, e.g., empty-body topics). No access to `api_secret_key`, access tokens, or privileged accounts is required; the attacker only needs to control the raw HTTP headers of the forged webhook POST, which any unprivileged internet user can do since Shopify webhook endpoints are public HTTP endpoints.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC computation, or otherwise cryptographically bind them (e.g., derive/validate `shop` from a value embedded in the HMAC-covered body, or require the host application to additionally verify `shop` against a known-registered shop list keyed by webhook subscription id fetched from Shopify, not from client-supplied headers). At minimum, document clearly that `WebhookMetadata.shop` is unauthenticated and must not be trusted for tenant selection without independent verification.

### Proof of Concept
1. Attacker installs the app on shop `attacker.myshopify.com` (or otherwise obtains any legitimate webhook delivery) and captures a delivered webhook: `raw_body = "{}"`, `x-shopify-hmac-sha256 = Base64(HMAC-SHA256(api_secret_key, "{}"))`.
2. Attacker sends the same body and HMAC header to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
3. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, "{}")` — identical to the captured value — so validation passes: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the event never originated from Shopify for that shop: [7](#0-6)
