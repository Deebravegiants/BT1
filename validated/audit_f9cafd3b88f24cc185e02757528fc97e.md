### Title
Webhook shop identity spoofing due to HMAC not covering the `shopify-shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC-signable content solely from the raw request body, while the `shop` (tenant) value is read unauthenticated from an HTTP header. `Registry.process` then forwards this unauthenticated `shop` value straight to the app's handler as the trusted tenant identity, breaking the equality `HMAC-authenticated-sender == shop-attributed-to-webhook`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [2](#0-1)  and `HmacValidator.validate` computes/compares the HMAC exclusively over that signable string using the app's `client_secret`: [3](#0-2) . Meanwhile `Request#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the body or to the HMAC computation at all: [4](#0-3) .

`Registry.process` validates the HMAC and then, without any further check binding the shop to that HMAC, constructs `WebhookMetadata` using `request.shop` as the shop of record and dispatches it to the registered handler: [1](#0-0) .

Because every shop that installs the same app shares the same `client_secret`, a genuine webhook delivery that Shopify sends to the app's endpoint for shop A (valid body + valid HMAC, both attacker-observable since the delivery targets the attacker's own installation/endpoint) can be re-submitted to the same webhook endpoint with the `shopify-shop-domain` header rewritten to shop B. The HMAC check still passes (it only verifies the body was signed with the app's secret, which is true), but the shop identity used by the handler is now attacker-controlled and unauthenticated. The equality that should hold — "the shop identity trusted by the handler" == "the shop bound by the verified signature" — does not hold, matching the class of bug where a field acted on (here, the routing/tenant-identity field `shop`) is not covered by the HMAC that is otherwise treated as an integrity/authenticity guarantee for the whole request.

### Impact Explanation
This is a cross-tenant confusion vulnerability: any user who can get the target app installed on their own store (an unprivileged action available to any merchant) can capture a real, validly-signed webhook payload delivered to the app and replay it against the app's own webhook endpoint while spoofing the `shop` header to point at a different, victim shop. Any host application logic that trusts `WebhookMetadata#shop` (e.g., using it to look up/update per-shop records, trigger per-shop side effects, or as an implicit access-control key) can be manipulated into acting on data attributed to a shop the attacker does not own, i.e., cross-tenant access/write, without needing the victim's access token or `client_secret`.

### Likelihood Explanation
Likelihood is high: no special privileges are needed beyond installing the app on any shop (a normal unprivileged flow), the webhook endpoint is a public HTTP endpoint, and forging/replaying the header requires only basic HTTP tooling. The only "hard" part — producing a valid HMAC — is trivially satisfied because the attacker reuses a genuine Shopify-signed body/HMAC pair they legitimately received for their own shop.

### Recommendation
Bind the shop identity to the authenticated payload instead of trusting the header value directly. Options include: (1) verifying the delivered `shop` header value against Shopify's `shop-domain` claim as part of the HMAC-signable string (i.e., include the shop domain in `to_signable_string`), or (2) requiring host applications to cross-check `request.shop` against a shop that is actually known/installed for this app before dispatching to the handler, and rejecting/flagging deliveries whose header shop does not match any expected tenant. At minimum, this trust boundary should be explicitly documented so implementers do not treat `WebhookMetadata#shop` as cryptographically authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook (e.g., `orders/create`) to the app's shared HTTP endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of raw body>`, and some `raw_body`.
3. Attacker captures this request (they control the network path from Shopify to their own installed endpoint context, or can otherwise obtain the raw body/HMAC pair) and re-sends it to the app's webhook endpoint, only replacing the `x-shopify-shop-domain` header value with `victim-shop.myshopify.com`.
4. `HmacValidator.validate` in [5](#0-4)  succeeds because it only checks the (unmodified) body's HMAC.
5. `Registry.process` in [1](#0-0)  dispatches `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...)` to the handler, causing the app to process/store data as if it originated from the victim shop.
