## Analysis Result

The external EthStaker TOCTOU/file-permission report is not a plausible bug class for this gem — no in-scope file in `lib/shopify_api/**` (excluding generated REST resources) creates or `chmod`s files at all, so a literal analog does not exist. However, per the rules, the report is only used as a *bug-class hint*: "sensitive data associated to the wrong owner/identity due to an unenforced binding between the data and the entity it's checked against." The strongest reachable analog in this gem is a genuine binding break in the webhook HMAC verification path, where the `shop` field is trusted and acted upon without being covered by the same HMAC that authenticates the payload.

### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` computes/compares the HMAC solely over that body against `Context.api_secret_key`. The `shop` value read by `Registry.process` and handed to the app's handler comes from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed material. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The identity binding that should hold is: `shop == the shop whose secret produced this HMAC`. In practice, only `body == HMAC(body, secret)` is checked; `shop` is read out-of-band from an unauthenticated header and passed straight into `WebhookMetadata` for the handler to act on:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [3](#0-2) 

Because `to_signable_string` is only `@raw_body`, any valid `(body, hmac)` pair generated for shop A's webhook remains a valid `(body, hmac)` pair no matter what `shop` header accompanies it:

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [4](#0-3) 

### Impact Explanation
A merchant/developer who legitimately installs the app on their own store (an unprivileged, non-victim tenant) can capture a genuinely-signed webhook delivery (body + valid HMAC) from their own shop, then replay the identical body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still passes because it only checks the body against the secret, and `Registry.process` forwards the attacker-chosen `shop` value to the handler unaltered. Any host application logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop state, triggering shop-scoped side effects, or session/store lookups) is executed under the wrong tenant identity — a cross-tenant access condition.

### Likelihood Explanation
Exploitation requires only an account that can generate at least one legitimate webhook from Shopify (any merchant installing the app), plus the ability to POST to the app's public webhook endpoint with attacker-controlled headers — both of which are available to an ordinary unprivileged internet/app user, satisfying the "unprivileged internet user" and "no leaked credentials" constraints.

### Recommendation
Include the `shop`/`shop-domain` header (and ideally `topic`, `webhook-id`) in the signed/verified material, or independently re-derive and pin the shop identity from a value that is cryptographically bound to the HMAC before dispatching to handlers, rather than trusting the header verbatim in `ShopifyAPI::Webhooks::Request#shop`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g., `orders/create`) and capture `raw_body` and the `X-Shopify-Hmac-Sha256` header — a valid `(body, hmac)` pair for the configured `api_secret_key`.
2. Replay a POST to the app's webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `HmacValidator.validate` passes (body/HMAC match), `Registry.process` invokes the handler with `shop: "victim.myshopify.com"`, causing the application to process attacker-supplied data under the victim tenant's identity. [5](#0-4)
