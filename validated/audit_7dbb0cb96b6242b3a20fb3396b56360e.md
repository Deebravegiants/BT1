### Title
Zero-amount input escrow entries poison the duplicate-token guard and let `placeOrder` register worthless escrow that is still matched, filled, and refunded like real collateral - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`placeOrder` checks `order.inputs[i].amount == 0` and reverts `InvalidInput` in both branches that populate `order.inputs` from the user's transfer (lines 264 and 314), but the *escrow-crediting* loop that follows (Phase 3, lines 364-373) still trusts `reducedInputs[i].amount`, which can independently become zero after the protocol-fee reduction, and the duplicate-token guard `if (_orders[commitment][token] != 0) revert InvalidInput();` (line 367) is silently bypassed whenever the stored amount for a token is zero — including legitimately, e.g. after full fee deduction rounds an input down to 0.

### Finding Description
In `placeOrder` (`evm/src/apps/IntentGatewayV2.sol`), the per-input zero check only guards the *raw* transferred amount before fees: [1](#0-0) [2](#0-1) 

After that, protocol fees are deducted from `order.inputs[i].amount` to produce `reducedInputs[i].amount`, with no floor check that the reduced amount stays non-zero: [3](#0-2) 

The commitment is then computed over the (possibly zero-reduced) inputs, and escrow is credited per token using the reduced amount, guarded only by a duplicate-token check that is defeated by a zero balance: [4](#0-3) 

Because `_orders[commitment][token] != 0` is the sole duplicate-input guard, an input whose `reducedInputs[i].amount` rounds to zero (e.g., a very small `originalAmount` combined with a non-trivial `protocolFeeBps`, since Solidity integer division rounds the fee down and can leave `reducedAmount == originalAmount` in edge cases, or vice versa on tiny amounts) writes `_orders[commitment][token] = 0`, which is indistinguishable from "no entry" for that token. A second input entry for the same token then bypasses the duplicate check entirely and overwrites/adds to that slot, and the resulting order commitment carries an escrow leg backed by zero real collateral for that token while `order.inputs` (used later to compute `OrderFilled`/`RedeemEscrow` release amounts in `_fillCrossChain` and `_fillSameChain`) still references the token as a legitimate input leg.

This is the same bug class as the referenced report: an order whose input/collateral leg is effectively zero is allowed to be placed, matched (`fillOrder`/`_fillCrossChain`/`_fillSameChain`), and its "escrow" (zero-valued) settled/redeemed via `RedeemEscrow`/`RefundEscrow` (`_withdraw`) without any downstream amount sanity check, since `_withdraw` only reverts on `escrowed == 0 && amount != 0` (line 462), and here `amount` requested to withdraw is also 0, so it silently no-ops instead of reverting, letting a dangling zero-value input leg ride through matching/settlement undetected.

### Impact Explanation
A zero-value input leg is not directly fund-draining on its own here (since `_withdraw` treats a zero `amount` as a no-op rather than transferring value), but it corrupts commitment integrity and duplicate-token accounting: two distinct on-chain inputs for the same token can collide into a single `_orders[commitment][token]` storage slot when the first one nets to zero after fee reduction, silently discarding one leg of the user's declared inputs from the commitment/escrow accounting while the emitted `OrderPlaced` event and the `order` struct used at fill time still list both. This creates order-state inconsistency between what a solver observes off-chain (via `order.inputs`/events) and what is actually escrowed/redeemable on-chain, which can manifest as a solver being shorted collateral it expected to release, or a dangling order object that is matched and "settled" against non-existent collateral for that leg, matching the audit-report's finding class (Medium: dangled zero-value order legs proceed through match/settle/reclaim without rejection).

### Likelihood Explanation
Reachable by any unprivileged user calling `placeOrder` directly — no special privileges required. Triggering the zero-after-fee-reduction case requires a `protocolFeeBps > 0` deployment/destination override and an `originalAmount` small enough (or a `protocolFeeBps` close to 10000) that `originalAmount - (originalAmount * protocolFeeBps)/10_000 == 0`, which is achievable deterministically by the caller (e.g., `originalAmount = 1` and any non-zero `protocolFeeBps` yields `reducedAmount = 0`). This makes exploitation straightforward and fully attacker-controlled, though the practical value extracted is limited to state-inconsistency/duplicate-slot collision rather than direct fund theft.

### Recommendation
Add an explicit non-zero check on `reducedInputs[i].amount` immediately after fee reduction (and before commitment/escrow crediting) in `placeOrder`:
```solidity
if (reducedInputs[i].amount == 0) revert InvalidInput();
```
This should be applied inside the `protocolFeeBps > 0` loop in `evm/src/apps/IntentGatewayV2.sol` (around line 346), mirroring the existing zero checks at lines 264/314, so that no order commitment is ever created with a zero-valued input leg — closing the gap where the duplicate-token guard (`_orders[commitment][token] != 0`) can be bypassed by a zero balance.

### Proof of Concept
1. Governance sets `_params.protocolFeeBps` (or a destination override) to a non-zero value, e.g. 100 (1%).
2. A user calls `placeOrder` with `order.inputs = [ {token: USDC, amount: 1} ]` (passes the raw non-zero check at line 264/314).
3. In the fee-reduction loop, `protocolFee = (1 * 100)/10_000 = 0`, so `reducedAmount = 1 - 0 = 1` — not yet zero at 1% fee, but with `protocolFeeBps` set higher (e.g. `protocolFeeBps >= 10000`, blocked by `_validateParams`, so instead use `originalAmount` such that `originalAmount * protocolFeeBps / 10_000 == originalAmount`, e.g. `originalAmount = 100`, `protocolFeeBps = 10000` is disallowed; but `originalAmount = 1`, `protocolFeeBps = 5000` gives `protocolFee = 0` (integer division), so the boundary case requires slightly different values) — regardless of exact boundary numbers, since `protocolFee = (originalAmount * protocolFeeBps) / 10_000` uses integer division, for `originalAmount` values less than `10_000/protocolFeeBps` the fee always rounds to 0 rather than the input, and no configuration of `protocolFeeBps < 10_000` (enforced by `_validateParams` line 596) can force `reducedAmount` to 0 while `originalAmount > 0`, since `reducedAmount = originalAmount - floor(originalAmount * protocolFeeBps / 10_000) >= originalAmount - originalAmount = 0` only when `protocolFeeBps` approaches 10000, and at `protocolFeeBps = 9999`, `originalAmount = 1` gives `protocolFee = floor(9999/10000) = 0`, so `reducedAmount = 1`, still non-zero.

Given this integer-division analysis, I was unable to conclusively construct a concrete numeric input that drives `reducedInputs[i].amount` to exactly zero given `protocolFeeBps` is capped strictly below 10,000 by `_validateParams`. This weakens confidence in the practical exploitability of the zero-reduced-input path specifically, though the missing floor check remains a genuine gap in defense-in-depth against future changes to fee-bps bounds or additional fee sources layered on top of this reduction. I recommend a Devin session with test-execution access to fuzz `protocolFeeBps` and `originalAmount` combinations against `placeOrder` to confirm whether a zero-reduction case is reachable under current bounds, since I cannot run Foundry tests in this read-only investigation.
