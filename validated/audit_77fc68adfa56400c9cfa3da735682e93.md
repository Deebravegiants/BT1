### Title
Webhook shop-domain identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to application webhook handlers from the unauthenticated `shopify-shop-domain` HTTP header, while `Utils::HmacValidator.validate` only verifies the raw request body against the app's `client_secret`. The `shop` value is never part of the signed material, so the equality the gem implicitly asserts — "HMAC-authenticated request" == "request originating from the shop named in `request.shop`" — does not actually hold.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from attacker-controllable HTTP headers and are excluded from the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the body) using the app's shared `client_secret`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to dispatch the request, then forwards the unauthenticated `request.shop` straight into `WebhookMetadata`, which is the only tenant identifier available to the handler: [4](#0-3) 

Because the `client_secret` is a single shared value used for every shop that installs the app, any shop that installs the app can obtain a validly-signed `(body, hmac)` pair for a webhook delivered to its own endpoint (attacker fully controls the raw body value and its resulting HMAC by controlling data in their own store that Shopify serializes into the webhook payload, e.g. via `orders/create`, `products/update`, etc.). The attacker can then replay that same `raw_body` + `hmac` directly to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and `x-shopify-shop-domain`) with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` because it never inspects the shop header, and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim's domain. This breaks the identity binding: **shop authenticated by the HMAC ≠ shop the application logic treats as the tenant of record**, exactly analogous to a session id trusted without being bound to the data that produced it.

### Impact Explanation
Any application built on this gem that uses `WebhookMetadata#shop` (or `Request#shop`) to select which merchant's data to read, write, or delete — a documented and intended use of the API returned by this gem — can be tricked into applying an attacker-supplied payload against a victim shop's tenant record. Depending on the topic (e.g. `app/uninstalled`, `shop/update`, `customers/redact`, or custom topics that drive data sync), this can result in cross-tenant data corruption, deletion, or disclosure without ever compromising the victim's credentials, satisfying the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
The attacker only needs to be a legitimate, unprivileged installer of the app on any shop (including a free development store) — no access to the victim's credentials, `client_secret`, or infrastructure is required. They control the raw body of at least one webhook delivered to themselves, capture the resulting valid `hmac`, and can freely replay the same bytes with a forged `shop-domain` header directly to the app's public webhook endpoint, since nothing in the gem binds the header to the signature.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material verified for webhooks, or, at minimum, require `Registry.process`/`WebhookMetadata` consumers to cross-check `request.shop` against a shop that is independently known to have an active, previously-established session/installation before trusting it as a tenant identifier. Document prominently that `request.shop` is unauthenticated header data and must not be used as the sole tenant key.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a shop they fully control).
2. Attacker triggers a webhook topic whose body they can influence (or simply captures any legitimately delivered webhook), recording the exact `raw_body` bytes and the `x-shopify-hmac-sha256` value Shopify sent.
3. Attacker sends a POST request directly to the app's webhook endpoint with:
   - `raw_body` = the captured body
   - `x-shopify-hmac-sha256` = the captured (still valid) HMAC
   - `x-shopify-shop-domain` = `victim-shop.myshopify.com`
   - `x-shopify-topic` = the same topic
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the HMAC, per `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
5. `ShopifyAPI::Webhooks::Registry.process` dispatches the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the host application to act on the victim shop's tenant data using attacker-controlled body content.
