### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing in `Registry.process` - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, never over the `shop-domain` header, and `Registry.process` trusts `request.shop` after validating that HMAC. This breaks the identity binding "shop authenticated == shop delivered to the handler."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is read straight from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cross-check against anything HMAC-covered: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the signature purely from `verifiable_query.to_signable_string` (i.e., the raw body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately hands `request.shop` — a value that was never part of the signed material — to the application's webhook handler: [4](#0-3) 

This is precisely the injected bug class from the reference report generalized to this gem: an attacker-controlled field (`shop-domain` header) is *acted on* (used to populate `WebhookMetadata.shop`, dispatched to the tenant-specific handler) but is *not covered by the HMAC* that is supposed to authenticate the whole request as genuinely originating from Shopify for a specific shop. The equality that should hold — `shop bound by HMAC == shop delivered to handler` — does not hold; instead the code only guarantees `body bound by HMAC`, and `shop` is parsed independently and unauthenticated.

By contrast, note that the OAuth callback path does correctly include `shop` inside `AuthQuery#to_signable_string`, so that flow is not affected: [5](#0-4) 

### Impact Explanation
Any party who can obtain one valid, HMAC-signed webhook delivery for topic T with body B (e.g., a merchant who installs the app and receives ordinary webhooks for their own shop, or anyone who can replay/capture such a request) can resubmit that exact body and HMAC value while altering only the `X-Shopify-Shop-Domain` header to name a different, victim shop. Since the HMAC does not cover the header, `HmacValidator.validate` still succeeds, and the host application's webhook handler will process the (attacker-supplied) `shop` value as if the data genuinely originated from that victim tenant. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up the tenant record, invalidate/update tenant state, or trigger tenant-scoped side effects), this enables cross-tenant data confusion/injection — a High-severity identity-binding break, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate: this gem's own webhook processing code does not enforce a binding between the authenticated body and the claimed shop, so exploitability depends entirely on how deterministic/predictable the webhook body is and how the host application uses the `shop` field from `WebhookMetadata`. If the host trusts `data.shop` for tenant-scoped actions (a documented, expected usage pattern per `docs/`), any attacker capable of obtaining one valid signed webhook (e.g., their own installed app instance) can immediately exploit this by resending with a spoofed shop header — no secrets or privileged access are required beyond what any installed merchant already has.

### Recommendation
Include the shop/tenant identity in the HMAC-signed material, or otherwise cryptographically bind the shop header to the payload before use. Concretely, `Webhooks::Request#to_signable_string` should be constructed (or `HmacValidator`/`Registry.process`) to also authenticate `shop-domain` — e.g., by having the caller separately verify that the resolved `shop` matches a shop the app has an active session/installation for, in addition to (not instead of) requiring the body HMAC to match. At minimum, document clearly that `WebhookMetadata#shop` is not authenticated by the gem's HMAC check and must not be trusted for tenant selection without independent verification (e.g., cross-referencing against a known/installed shop list) in the host application.

### Proof of Concept
1. App installs on `shop-a.myshopify.com` and receives a legitimate webhook delivery with body `B`, header `X-Shopify-Shop-Domain: shop-a.myshopify.com`, and header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(secret, B)`.
2. Attacker (who can observe/capture this delivery, e.g. because they control `shop-a` themselves) constructs a new HTTP POST to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "shop-victim.myshopify.com", "shopify-hmac-sha256" => H, ...})` is constructed; `HmacValidator.validate(request)` succeeds because it only recomputes over `B`. [6](#0-5) 
4. `Registry.process(request)` calls the registered handler with `WebhookMetadata.new(..., shop: "shop-victim.myshopify.com", body: parsed(B), ...)`, even though `B` was never actually signed for `shop-victim`. [7](#0-6)

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
