### Title
Webhook shop domain is trusted for tenant identification without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the caller-supplied `shop-domain` header straight through to the app's handler as the tenant identifier, without that header ever being covered by the HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed string: [2](#0-1) .

`Registry.process` verifies the HMAC (`Utils::HmacValidator.validate(request)`) and, if it matches, immediately builds `WebhookMetadata` using `request.shop` — the unauthenticated header value — and dispatches it to the registered handler: [3](#0-2) .

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (i.e. the raw body) using the app's shared `api_secret_key`: [4](#0-3) .

The identity binding that should hold is: `shop-domain header used to select tenant == shop that actually produced/owns this signed body`. Because the header is excluded from the signed content, and the same `api_secret_key` is shared across every shop that has installed the app, any party who can obtain one validly-HMAC'd webhook body for shop A (e.g., by installing the app on their own store and receiving their own real webhooks) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` value (e.g., shop B's domain). `Utils::HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will pass the forged `shop` value on to the handler as though it were authenticated.

### Impact Explanation
Any host application that relies on `WebhookMetadata#shop` (as returned by this gem) to select which merchant's session/data to mutate is exposed to cross-tenant data corruption or disclosure: an attacker-controlled shop can trigger webhook side effects (e.g., inventory updates, order processing, uninstall/GDPR handling, metafield writes) attributed to a victim shop it never installed the app on or has no legitimate relationship with. This is a cross-tenant authentication/identity-binding bypass consistent with the "Critical - cross-tenant access" category, since the vulnerable field (`shop`) is the sole tenant-selection key exposed by this gem's webhook API and is not authenticated at all.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the target app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer) in order to obtain a validly-signed webhook body, and then send a crafted HTTP request with a modified `shop-domain` header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account for the victim shop is needed — only network access to the app's webhook receiver, which is by definition internet-reachable. This matches the required "unprivileged internet user" analog exactly: a field acted on (`shop`) that is not covered by the HMAC.

### Recommendation
Bind the shop identity to the signed payload instead of trusting an unauthenticated header:
- Include the topic/shop/webhook-id in the signable string used for HMAC verification, or
- Require host applications to cross-check `request.shop` against a shop the app has an active, previously-established installation/session record for before acting on webhook data, and document this requirement prominently in `docs/usage/webhooks.md`.
- At minimum, expose a way for `Registry.process` callers to assert an expected shop, and refuse to dispatch when it does not match a known/installed shop.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`. Shopify sends a real webhook, e.g. `orders/create`, HMAC-signed with the app's shared `api_secret_key` over the JSON body, with header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this raw body + valid `x-shopify-hmac-sha256` value.
3. Attacker sends this exact body and HMAC header, but with `x-shopify-shop-domain: victim-shop.myshopify.com`, directly to the app's public webhook route.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body successfully: [5](#0-4) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over the (unchanged) raw body and secret and matches — validation passes despite the shop header being forged: [6](#0-5) .
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes the order-creation body as if it belonged to the victim shop: [7](#0-6) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
