### Title
Emporium `verifyWallet` grants unauthenticated, fee-free arbitrary-call execution via the min-circuit path, draining any funds held by `EmporiumUpgradeable` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`MainEVMCircuitMin` only constrains `message === Poseidon(messageSeed)` and never binds `calldataHash` (hence the `EmporiumStack.ops` payload) into any circuit signal, and `verifyWallet` only checks `usedMessages[emporiumMessage]` while skipping every EIP-712 authentication when `signerAddress == 0`. Since the min-circuit path is selected whenever `circomData.erc20TokenAddresses.length == 0` (forcing `dimensions.tokenNumber == 0` and thus no nullifier/root/balance checks at all in `Hinkal.transact`), any unprivileged EOA can generate a trivial, self-satisfying proof for any `messageSeed` they choose, pick a fresh `emporiumMessage`, and pair it with any attacker-chosen `EmporiumStack.ops`, causing `EmporiumUpgradeable.runAction` to execute arbitrary `op.endpoint.call{value: op.value}(op.callData)` as `msg.sender == Emporium`.

### Finding Description
The claimed broken equality holds: `calldataHash` (derived from `getHashedCalldata(circomData)` over `externalActionData.externalActionMetadata`, i.e. the `ops` payload) is passed into the min-circuit as a public signal in `formInputEmporiumMin` [1](#0-0) , but `MainEVMCircuitMin` never uses `calldataHash` in any constraint — it only computes `message <== Poseidon(1)([messageSeed])` [2](#0-1) . So `calldataHash`/`ops` is a free, unconstrained public input: the prover need not know or commit to the `ops` content via any nullifier, root, or signature.

`verifyWallet` then only guards against replay of a message value and, when `signerAddress == address(0)`, returns immediately without any EIP-712 signature check tying `ops` to `emporiumMessage`: [3](#0-2) . Because `message = Poseidon(messageSeed)` is a forward-computable hash (attacker picks `messageSeed` first, derives `message`), the attacker can freely mint an arbitrary number of unused `emporiumMessage` values, defeating the only check.

Critically, the min-circuit path is reachable with **zero legitimate fund backing**: `formInputForCircom` selects it only when `circomData.erc20TokenAddresses.length == 0` [4](#0-3) , which forces `dimensions.tokenNumber == 0` via `dimensionsCheck` [5](#0-4) , meaning `amountChanges`, `inputNullifiers`, `outCommitments`, and `slippageValues` are all empty and none of `Hinkal.transact`'s balance/nullifier machinery executes (all loops in `Hinkal.transact` iterate zero times) [6](#0-5) . `_externalTransact` therefore also performs zero token transfers before calling `runAction` [7](#0-6) .

Inside `EmporiumUpgradeable.runAction`, with `signerAddress == 0` the loop executes `op.endpoint.call{value: op.value}(op.callData)` for every attacker-chosen `EmporiumOperation` [8](#0-7) , with `msg.sender == EmporiumUpgradeable`. Since `Emporium` is designed to custody user token/ETH balances across multi-step operations ("tokens deposited into Emporium are not charged", `receive() external payable {}`), any balance the contract legitimately holds for in-flight user sessions is directly exposed: an attacker can set `op.endpoint = <any ERC20 held by Emporium>` and `op.callData = transfer(attacker, allBalance)`, executed with `msg.sender = Emporium`, draining it.

Existing guards fail specifically because: `onlyAllowedRecipient` only restricts the caller of `runAction` to the `Hinkal` contract, not the content of `ops` [9](#0-8) ; `performHinkalChecks`'s `calldataHash` equality check only verifies calldata self-consistency, never that it's cryptographically bound in the circuit [10](#0-9) ; and `verifyProof`/`buildVerifierId` only confirm the trivial Poseidon-preimage statement is satisfied, which is free for anyone to satisfy.

### Impact Explanation
Any unprivileged attacker can force `EmporiumUpgradeable` to execute arbitrary external calls as itself, with no fund backing, no signature, and no meaningful ZK constraint. This is a direct theft vector against any ERC20/ETH balance the Emporium contract custodies on behalf of users during multi-op sessions — categorized Critical: direct theft of in-flight user funds and a proof/verification bypass (the min-circuit "proof" provides no real authentication). The exploit is fully repeatable (each call just needs a fresh `messageSeed`/`emporiumMessage`, both freely generated by the attacker) at negligible cost (one Groth16 proof generation + gas).

### Likelihood Explanation
Preconditions are minimal: the attacker needs no deposit, no prior UTXO, no wallet keys, and no relay/owner privilege — only the ability to call `Hinkal.transact()` with `externalActionId` pointing to the deployed `EmporiumUpgradeable` and `erc20TokenAddresses = []`. The only "cost" is generating a Groth16 proof for `MainEVMCircuitMin`, which is trivial since the statement is self-satisfying (`message = Poseidon(messageSeed)` for any chosen seed). This makes the attack highly feasible and repeatable as long as `Emporium` holds any residual balance at the time of attack.

### Recommendation
Bind `calldataHash` (and thus `ops`) cryptographically inside `MainEVMCircuitMin` (e.g., include it in the Poseidon preimage so `message` commits to both `messageSeed` and `calldataHash`), and/or remove the `signerAddress == address(0)` bypass in `verifyWallet` so that stateless (self-authorized) Emporium calls are only permitted when the underlying main proof (not the min-circuit) actually ties nullifiers/root/signature to the specific `ops` being executed. At minimum, disallow the min-circuit path entirely for any `externalActionId` that can move funds already held in `Emporium`, or require `Emporium` to never custody balances across transactions (settle to user UTXOs atomically every call) so there is nothing for an unauthenticated call to steal.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and `EmporiumUpgradeable` (as allowed recipient), and register the min-circuit verifier for `HINKAL_EMPORIUM_ACTION_ID`.
2. Fund `EmporiumUpgradeable` with a test ERC20 balance (simulating in-flight user funds from a prior legitimate multi-op session).
3. As an attacker with no deposits/UTXOs, generate a valid Groth16 proof for `MainEVMCircuitMin` with an arbitrary `messageSeed`, deriving `emporiumMessage = Poseidon(messageSeed)`.
4. Craft `EmporiumStack{ signerAddress: address(0), ops: [{endpoint: token, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, tokenBalance))}] }`, embed in `externalActionMetadata`, set `erc20TokenAddresses = []`, `amountChanges = []`, and call `Hinkal.transact(a,b,c,dimensions,circomData)`.
5. Assert the call succeeds, `token.balanceOf(Emporium) == 0` and `token.balanceOf(attacker) == tokenBalance` — confirming the equality "calldataHash commits to ops" vs. "min-circuit constrains only Poseidon(messageSeed)" is broken, and funds moved with no authentic authorization.
6. Repeat with a second `messageSeed`/`emporiumMessage` and a different malicious `ops` to show `usedMessages` provides no protection against replay-with-different-payload.
