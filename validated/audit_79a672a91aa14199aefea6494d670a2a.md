### Title
Unguarded subtraction in `canGraduate`/`_prepareGraduationLiquidity` can underflow and permanently brick a token's `buy`/`sell`/graduation path - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.sol` derives the "real" LT raised by a curve as `assetReserve - _launchTimeVirtualLtReserve(...)` in two places — `canGraduate` and `_prepareGraduationLiquidity` — with no floor/guard, unlike every other subtraction of the same shape in the same file (`protectedLT`, `_ltSwapInventory`, `_sweepLTToOwner`, `_routerDepositAndDispose`), which are all explicitly written as saturating subtractions (`a > b ? a - b : 0`) specifically to avoid a Panic. If `assetReserve` ever reads even 1 wei below the recovered `virtualLtReserve`, both call sites revert with an arithmetic-underflow panic instead of degrading gracefully, and because `canGraduate` is invoked unconditionally inside both `buy()` and `sell()`, the revert propagates to every future trade on that token.

### Finding Description
`_launchTimeVirtualLtReserve` recovers the launch-time virtual LT reserve from the pair's immutable `k`: [1](#0-0) 

`canGraduate` uses that value in an unguarded subtraction: [2](#0-1) 

`_prepareGraduationLiquidity` repeats the exact same unguarded pattern: [3](#0-2) 

Contrast this with every *other* "protected balance" subtraction in the very same contract, all of which are explicitly saturating to avoid a Panic: [4](#0-3) [5](#0-4) 

The invariant the code assumes — that `assetReserve` (the curve `Pair`'s stored LT reserve) can never fall below the launch-time virtual reserve baked into `k` — is not actually enforced by `Pair.swap`. `Pair.swap`'s K-invariant check contains a `+1` slack on both sides of the product, so the post-trade reserves are only required to satisfy `(newTokenReserve+1)*(newAssetReserve+1) < k` rather than `>= k` on the nominal (non-off-by-one) reserves: [6](#0-5) 

This `+1` slack is the same rounding surface called out in the report's mapping guidance (`Pair.swap`'s `+1` K slack), and it permits `newAssetReserve` to end up marginally lower than the no-slack constant-product result would allow across a sequence of buys and sells driven through `Router._computeBuy`/`_computeSell`. Once accumulated rounding pushes the stored `assetReserve` even 1 wei under `_launchTimeVirtualLtReserve(token, pair)`, the unguarded subtraction in `canGraduate` panics instead of returning `false`.

The severity comes from where `canGraduate` is called: it is invoked unconditionally, every single trade, inside both the buy path and the sell path: [7](#0-6) [8](#0-7) 

Because it is called *after* the buy/sell has already executed against the `Pair`/`Router` (state already mutated), a revert here does not just fail cleanly — it means the underlying trade's state-mutating calls (`Router.buy`/`Router.sell`, which move real LT/tokens) get rolled back along with it, but on the *next* trade attempt the same unguarded subtraction is evaluated again against reserves that are now permanently below the virtual floor, so the revert repeats forever. The token becomes permanently un-tradeable (`buy` and `sell` both revert) and can never reach `triggerGraduation` either, since that function calls `canGraduate` too: [9](#0-8) 

This is structurally the same bug class as the Ledger `path_advance_in_struct` report: a value is computed via subtraction/pointer arithmetic that is only safe under an invariant the surrounding code does not actually guarantee, and the guard that exists elsewhere in the same codebase for the identical pattern (saturating subtraction) is missing at this specific call site — an inconsistency, not a one-off typo, since three sibling functions in the same file got the defensive treatment and two (the graduation-critical ones) did not.

### Impact Explanation
If reachable, this permanently freezes all trader and creator funds locked in the curve's `Pair` for the affected token: `buy()` and `sell()` both revert on entry (via `canGraduate`), and `triggerGraduation()`/`finalizeGraduation()` can never run, so LT and tokens already deposited in the `Pair` become permanently stranded — no path in `Bonding.sol` can move the token out of `Lifecycle.Curve`. This matches the "permanent freezing of trader, creator or LP funds" impact bar in the validation criteria.

### Likelihood Explanation
The trigger condition — `assetReserve` drifting by a small amount below the recovered `virtualLtReserve` due to the `+1` K-invariant slack accumulating over many buy/sell cycles — requires unprivileged users to simply trade normally (`Zap.buy`/`Zap.sell` → `Bonding.buy`/`sell` → `Router` → `Pair.swap`) over a sequence of trades chosen (or naturally occurring) to walk the rounding slack in the unfavorable direction. No special privileges are needed; only enough trade volume/sequencing to accumulate the rounding drift. I was not able to fully re-derive `Router._computeBuy`/`_computeSell`'s exact rounding formulas in this session to prove the precise sequence of trades that forces the underflow, so the exact number of trades required and whether `_computeSell` additionally floors `assetOut` in a way that independently prevents this drift could not be confirmed from the code read so far — this is the main open uncertainty. It should be validated directly against `Router.sol`'s buy/sell math.

### Recommendation
Make the two graduation-critical subtractions saturating, matching the defensive style already used elsewhere in `Bonding.sol`:
```solidity
uint256 virtualLt = _launchTimeVirtualLtReserve(token_, pair);
uint256 realLtRaised = assetReserve > virtualLt ? assetReserve - virtualLt : 0;
```
Apply the same fix in both `canGraduate` and `_prepareGraduationLiquidity` (and `previewLtUntilGraduation`, which has the identical pattern). Separately, audit `Pair.swap`'s `+1` slack to confirm whether `assetReserve` can legitimately drop below the launch-time virtual reserve at all under honest trading, since that would indicate a K-invariant soundness gap independent of this specific panic.
