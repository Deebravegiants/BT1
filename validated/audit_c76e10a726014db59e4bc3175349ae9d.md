### Title
Aquarius LP collateral price manipulable by direct token transfers within a single transaction - ([File: contracts/price-aggregator/src/providers/aquarius.rs])

### Summary
The price-aggregator derives the fair value of an Aquarius LP share token from the pool's *live* token reserves (`get_reserves`, i.e. raw `balanceOf` on the pool) at read time, with no TWAP, cumulative-price accumulator, or internal reserve tracking. An unprivileged attacker can donate (or flash-loan-and-donate) one pool token directly to the Aquarius pool in the same transaction as a controller `borrow`, inflating `sqrt(value_a * value_b)` and therefore the LP-share price used for collateral valuation, then recover most of the donation by burning the LP position. This is the direct-transfer price-manipulation class from the Caviar `Pair.price` report, mapped onto XOXNO's Aquarius LP oracle path.

### Finding Description
`read` in `contracts/price-aggregator/src/providers/aquarius.rs` fetches reserves at call time via `aquarius_pool_reserves_call` (`common/src/oracle/providers/aquarius.rs:45-57`), which forwards `pool.get_reserves()` — a spot balance read, not an internally tracked reserve. Those reserves feed `fair_lp_price_wad` (`common/src/oracle/lp.rs:57-87`), which computes `price = 2 * sqrt(value_a * value_b) * WAD / share_supply_wad`.

The geometric-mean form neutralizes *swaps* (a swap moves `va` up and `vb` down, leaving the product roughly unchanged — the stable-pool test even asserts this), but it does **not** neutralize *donations*. Transferring token A directly to the pool raises `reserve_a` while `reserve_b` is untouched, so the LP price scales by `sqrt(1 + donation/reserve_a)`. There is no `_update`/`reserve0`/`reserve1` internal tracking and no time-weighted accumulator anywhere in this path — exactly the gap the original report identifies, and the `sync()` rebuttal does not apply because nothing here even snapshots reserves.

The controller consumes this observation through the normal oracle resolution path when valuing collateral for `borrow` / `multiply` / health-factor checks, so a price inflated inside one transaction is used at face value. `min_pool_value_wad` only floors total pool value; the donation *raises* pool value, so it cannot trigger `InsufficientAquariusLiquidity`. Sanity bands (`min_sanity_price_wad`/`max_sanity_price_wad`) and dual-source tolerance may bound the exploit for some market configs, but nothing in the code requires two independent sources (`1 <= len(values) <= 2` per the resolution semantics), and any in-band inflation remains fully usable.

### Impact Explanation
Theft of user funds / protocol insolvency: an attacker holding (or freshly minting) Aquarius LP shares used as collateral inflates their USD value, borrows more than the true collateral supports, and withdraws liquidity to reclaim most of the donation. The protocol is left with under-collateralized debt that becomes bad debt written down via `seize_positions`, i.e. a direct loss to suppliers.

### Likelihood Explanation
- Reachable by any unprivileged address: direct token transfer to the Aquarius pool + `supply`/`borrow` on the controller in one transaction; flash liquidity can fund the donation via `flash_loan` or an external lender.
- Cost of manipulation ≈ donation × (1 − attacker's LP share fraction), recoverable by `remove_liquidity`; gain is the excess borrowed amount.
- Attenuated where market config enforces two heterogeneous sources with tight tolerance or narrow sanity bands, but single-source AquariusLp or wide-band configs are fully exposed.

### Recommendation
Do not price LP shares from raw spot reserves alone. Mitigations, in increasing strength:
1. Require at least two independent price sources for LP collateral and enforce the existing tolerance check against them (single-source LP oracles should be rejected).
2. Add a manipulation-resistance bound: cap the implied LP price against a configured `min_factor`/`max_factor`-style band relative to a feed of the underlying, or reject reads where the reserve ratio deviates sharply from a recently observed ratio.
3. Prefer Aquarius-reported virtual price / invariant-derived TVL that is donation-robust (e.g., stable `D` from the pool contract rather than recomputed balances), or track reserves with a time-weighted accumulator analogous to Uniswap V2's `price*CumulativeLast`.

### Proof of Concept
1. Attacker holds LP shares of Aquarius pool P (constant-product), registered as collateral via an `AquariusLp` oracle.
2. In one transaction: flash-borrow a large amount of token A; `token.transfer(attacker → pool P, D)` (a direct donation, no swap); call controller `supply`/`borrow` (or `multiply`) with the LP collateral — the aggregator `read` calls `get_reserves`, sees inflated `reserve_a`, and returns `price ≈ fair * sqrt(1 + D/reserve_a)`; borrow up to the inflated LTV.
3. Call `remove_liquidity` on P to reclaim a pro-rata share of the donation (only the diluted fraction is lost).
4. Position is left under-collateralized at the true price; profit = borrowed excess − donation dilution cost − flash fee.
