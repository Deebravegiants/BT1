### Title
Unsigned cross-chain calldata lets an attacker dispatch arbitrary runtime calls as *any* account - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler, invoked for every incoming token-transfer `PostRequest` delivered through Hyperbridge, executes an attacker-supplied `SubstrateCalldata.runtime_call` under `RawOrigin::Signed(origin)`. When the cross-chain message omits a `signature` (an attacker-controlled, optional field), `origin` is derived directly from the message's `from` field with **no cryptographic verification that the controller of `from` authorized the call**. This mirrors the Starlette bug class (CWE-470/unsafe reflection): a value fully controlled by an unprivileged caller is used, without validation against a trusted set, to select and invoke a privileged handler/identity, letting the attacker reach functionality (arbitrary runtime dispatch as an arbitrary account) that was never meant to be attacker-reachable.

### Finding Description
In `on_accept`: [1](#0-0) 

the pallet decodes optional calldata attached to a bridged token message and dispatches it as a runtime call:

- If `substrate_data.signature` is `Some(...)`, the code verifies an Ed25519/Sr25519/Ecdsa signature over `(nonce, runtime_call)` against the beneficiary derived from `message.to`, and only then sets `origin = beneficiary`.
- If `substrate_data.signature` is `None`, `origin` is computed purely from `message.from` — an attacker-supplied field inside the same ABI-encoded `Message` that also carries `to`/`amount`/`data` — with **zero signature check**: [2](#0-1) 

The resulting `runtime_call` (also fully attacker-controlled, only gated by `BaseCallFilter`) is then dispatched as that `origin`: [3](#0-2) 

The entire `Message` (including `from`) is ABI-encoded by whoever calls the source-chain Gateway contract to initiate the transfer — it is not tied to `msg.sender` on the source chain and is not otherwise authenticated on the destination. `on_accept` is reachable by any relayer delivering a valid ISMP proof for a message that any user can construct and submit through the Hyperbridge messaging path (the same unprivileged path documented for `IsmpModule::on_accept`): [4](#0-3) 

Because `from` selects the dispatch origin without any proof of key ownership, an attacker can set `from` to an arbitrary victim `AccountId32`/EVM address encoding and pair it with any `runtime_call` permitted by the runtime's `BaseCallFilter` (e.g., `Balances::transfer_all`, asset transfers, staking/governance votes if not filtered, etc.), causing the victim's account to execute that call without the victim's consent.

### Impact Explanation
This is unauthorized-action / theft-of-funds class impact: an unprivileged actor who can only send a bridged token message (a normal, permissionless cross-chain transfer) can impersonate any account on the destination chain and force it to execute an arbitrary, filter-permitted runtime call, including balance transfers. This satisfies "unauthorized app action" / "concrete theft… of funds" from a single relayed message, matching Medium-to-High severity analogous to the Starlette advisory (unauthenticated attribute/identity selected by attacker input reaches functionality bypassing intended authorization).

### Likelihood Explanation
High likelihood of reachability: the vulnerable branch is taken whenever `substrate_data.signature` is `None`, which is entirely the caller's choice when constructing the message (no code path forces the signed branch). Triggering it requires only crafting and dispatching one PostRequest with a real (attacker-controlled) HFT transfer plus optional calldata — no privileged role, admin action, or malicious relayer needed; a normal relayer honestly delivering the message suffices.

### Recommendation
- Require the `signature` to always be present and verified whenever `substrate_data.data` (i.e., `runtime_call`) is non-empty; reject messages with calldata but no signature.
- When no signature is supplied, the runtime call must not be dispatched as an arbitrary attacker-chosen `origin`; either restrict the unsigned path to a fixed, known origin (e.g., the beneficiary that actually received minted/transferred funds, i.e. `message.to`, never `message.from`) or remove the unsigned dispatch path entirely.
- Ensure the nonce/replay-protection scheme used in the signed branch also fully covers the case being exploited, and add a regression test that a message with `from` set to a victim account and no signature is rejected rather than dispatched.

### Proof of Concept
1. Attacker calls the source-chain Gateway (e.g., the EVM `HyperERC20Gateway`/equivalent) to send a normal cross-chain token transfer, ABI-encoding a `Message` where:
   - `to` = attacker's own beneficiary (or anything, receives the minted/transferred token amount),
   - `from` = the SS58/AccountId32 bytes of a **victim** account on the destination chain,
   - `data` = SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <Balances::transfer_all(attacker_account, keep_alive=false)> }`.
2. Any relayer delivers the resulting ISMP `PostRequest` with a valid consensus/state proof to the destination chain's `pallet-ismp`, which routes it to `pallet_hyper_fungible_token::on_accept`.
3. In `on_accept`, `substrate_data.signature` is `None`, so `origin` is computed from `message.from` (the victim's account bytes) with no signature check: [2](#0-1) 
4. `runtime_call.dispatch(RawOrigin::Signed(victim))` executes `Balances::transfer_all` from the victim's account to the attacker, draining the victim's balance, entirely without the victim's participation. [5](#0-4)
