This confirms the vulnerability. `Utils::VerifiableQuery` requires only `hmac` and `to_signable_string`, and for `Webhooks::Request` (`lib/shopify_api/webhooks/request.rb:35-38`), `to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers (`shopify_header`) and are never included in the signed data, so `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) only proves the body's integrity/authenticity — not which shop it belongs to.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as only the raw request body (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to the signature. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` to identify the tenant the webhook belongs to, after only checking that the body's HMAC is valid.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` alone [1](#0-0) , and `#shop` is derived purely from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` header [2](#0-1) . `Utils::HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., the body only) and compares it to the `hmac` header [3](#0-2) . `Registry.process` gates entirely on this HMAC check and then forwards `request.shop` unmodified to the app's handler [4](#0-3) .

Because every shop that installs the app shares the same app-level `api_secret_key` (this is not a per-shop secret — see `Context.api_secret_key` used uniformly in `HmacValidator.validate`), any tenant that legitimately receives a webhook for their own shop possesses a body+HMAC pair that is valid for *any* shop-domain header value. The equality the gem should enforce is: `shop header == shop the HMAC signature was actually generated to authenticate`. Instead, the gem only proves `hmac == HMAC(body)`, entirely decoupled from `shop`. An attacker (a legitimate but malicious merchant/tenant of the multi-tenant app, i.e., an unprivileged internet user relative to other tenants) can capture a real webhook delivered to their own shop and replay the identical body/HMAC to the app's shared webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Registry.process` will accept it as valid and dispatch it to the handler labeled as coming from the victim shop.

### Impact Explanation
This breaks the tenant identity binding relied upon by any app built on this gem: `WebhookMetadata#shop` (built directly from `request.shop`) is handed to the app's own webhook handler as an authenticated fact [5](#0-4) , but it isn't actually authenticated. Depending on how the host app uses this value (e.g., looking up the shop's stored access token/session to act on `data.shop`, or writing merchant data keyed by `data.shop`), this can result in cross-tenant data injection or actions being attributed to/executed against the wrong shop.

### Likelihood Explanation
Likelihood is high in any real-world multi-tenant app: obtaining a genuine `(body, hmac)` pair only requires being any one of the app's installed merchants (a low bar — anyone can install a public app), and no other check (IP allow-listing, mTLS, topic/shop binding) is performed by this gem before the header value is trusted.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable representation (or otherwise cryptographically bind the headers to the payload) instead of signing the raw body alone, so a captured signature for one shop/topic cannot be replayed with different header claims:

```diff
 sig { override.returns(String) }
 def to_signable_string
-  @raw_body
+  URI.encode_www_form(shop: shop, topic: topic, webhook_id: webhook_id, api_version: api_version, body: @raw_body)
 end
```

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the target app; Shopify sends it a real webhook (e.g. `orders/create`) with body `B`, headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(app_secret, B)`.
2. Attacker replays a POST to the app's shared webhook endpoint with the exact same body `B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(app_secret, B)` and matches `H` — validation succeeds because `shop` is not part of the signed content [6](#0-5) .
4. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: B, ...)`, spoofing the webhook as belonging to the victim shop [5](#0-4) .
