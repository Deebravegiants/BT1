### Title
Refund of Relayer Fees on Timeout Sent to Attacker-Controlled `payer` Address Decoupled from Actual Fee Payer - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost memory post)` accepts an arbitrary, caller-supplied `post.payer` address that is stored as the refund recipient for the relayer fee, while the actual fee (when paid in the fee token) is pulled from `_msgSender()`. On timeout, the fee is refunded to the stored `payer` rather than to whoever actually paid it, exactly mirroring the `updatePythPrice(address sender, ...)` bug class where a configurable "who gets the money back" parameter is never checked against the true payer.

### Finding Description
In `dispatch()`, when the fee-token path is used, the host pulls the fee from the transaction's real sender: [1](#0-0) 

Yet the refund beneficiary recorded for that payment is not `_msgSender()` — it is the caller-supplied struct field `post.payer`, with no validation that it equals `_msgSender()`: [2](#0-1) 

That `FeeMetadata.sender` value is later used verbatim to route refunds when a request times out, both for POST and GET requests: [3](#0-2) [4](#0-3) 

`dispatch()` is a public, unprivileged entry point (`IDispatcher.dispatch`) that any EOA or integrating contract can call directly. Because `post.payer` is just an ABI-encoded struct field, it is fully independent of `msg.sender`/`_msgSender()`, which is the actual fee-token payer. Any front-end, relayer-assembled transaction, or intermediary contract that constructs the `DispatchPost` calldata on behalf of a user (the normal pattern shown throughout the SDK/docs, e.g. `payer: msg.sender` is only a *convention*, not an enforced invariant) can substitute an attacker-controlled address in `payer` while the unsuspecting caller's own tokens are debited for the fee. If the destination request subsequently times out, the relayer-fee refund is silently redirected to the attacker's address instead of the party who actually paid it.

### Impact Explanation
This is a direct fund-misdirection vector: the entity whose tokens were spent (`_msgSender()`, via `safeTransferFrom`) is not guaranteed to be the entity that receives the refund on timeout. An attacker able to influence the constructed calldata (e.g., a malicious dApp/relayer front-end assembling `DispatchPost` for the user, or a wrapper/integration contract that forwards a user-chosen `payer`) can steal the relayer-fee refund that rightfully belongs to the fee payer. This is a concrete theft-of-funds scenario reachable from a single dispatched request through `IDispatcher`/`EvmHost`, matching the required "concrete theft ... of funds" impact bar.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the fee payer to submit a transaction whose `DispatchPost.payer` field was set by an untrusted intermediary (front-end, integrator contract, or relaying service) rather than the trusted caller. This mirrors the original Pyth report's exact assumption — the value of the "sender/payer" parameter is trusted implicitly by callers even though nothing in the host enforces `payer == _msgSender()`. Given how many downstream apps (intent gateways, token bridges, LZ endpoint adapter) call `dispatch`/`dispatchWithFeeToken` with a hardcoded `payer: msg.sender`, a compromised or malicious integration is the main attack surface, but the host itself provides zero defense-in-depth against it.

### Recommendation
Enforce `post.payer == _msgSender()` in `EvmHost.dispatch(DispatchPost memory post)` (and the analogous `DispatchGet` dispatch path) before persisting `FeeMetadata`, or remove the `payer` field entirely and always use `_msgSender()` as the refund recipient, consistent with the original report's two suggested fixes for `updatePythPrice`.

### Proof of Concept
1. A malicious front-end/integration contract builds `DispatchPost{ ..., fee: F, payer: attacker }` and asks the victim to sign/submit the transaction that calls `IDispatcher(host).dispatch(post)` with `msg.value == 0`.
2. `EvmHost.dispatch` executes `IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee)` — debiting `F` fee tokens from the victim (`_msgSender()` is the victim, since they signed the tx). [1](#0-0) 
3. `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})` stores the attacker's address as the refund recipient. [5](#0-4) 
4. If the destination chain never delivers (or the request otherwise times out) and a timeout proof is submitted, `dispatchTimeOut` refunds the fee to `meta.sender`, i.e., the attacker, not the victim who paid it. [6](#0-5)
