Audit Report

## Title
JWT/Bearer auth token logged in plaintext when the Vault gateway handler receives a JSON-RPC message - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` unconditionally logs the full inbound `*jsonrpc.Request[json.RawMessage]` struct at Debug level via `reqLggr.Debugw("received message from gateway", "req", req)`, before any authorization occurs. Since `req.Auth` carries the caller's raw bearer/JWT token and no redaction wrapper exists for this type in the repo, the token is written to node logs in cleartext whenever Debug logging is enabled.

## Finding Description
The handler at [1](#0-0)  logs the entire `req` object as a structured field immediately upon receiving a gateway-forwarded JSON-RPC message, prior to calling `h.requestProcessor.ProcessRequest` or any `AuthorizeRequest` check. The `Auth` field of `jsonrpc.Request[json.RawMessage]` is confirmed elsewhere in the codebase to hold the caller's raw token — it is read directly in `jwtBasedAuth.AuthorizeRequest` via `v.validateToken(ctx, req.Auth)` [2](#0-1) , and other code paths deliberately avoid logging it, instead logging only a `hasAuth` boolean in `GatewayVaultRequestProcessor.authorizeAndStamp` [3](#0-2) , and stripping it before re-serialization in test helpers [4](#0-3) . No `MarshalLogObject`/redaction method for `jsonrpc.Request` was found in this repo, so the zap-based `Debugw` call serializes the struct, including the `Auth` field, wholesale. This confirms the codebase treats `Auth` as sensitive elsewhere but the `HandleGatewayMessage` log line bypasses that discipline.

## Impact Explanation
When Debug-level logging is enabled on a node — a supported, documented operational mode rather than an attacker privilege — every caller's bearer token authenticating Vault secret operations (`SecretsCreate`, `SecretsUpdate`, `SecretsDelete`, `SecretsList`) is persisted to node logs in cleartext. Anyone with read access to those logs can extract and replay a valid token to impersonate the token's owner for Vault secret operations within its validity window, mapping to the in-scope "key/secret exfiltration" and "gateway request impersonation" impact classes.

## Likelihood Explanation
The vulnerable log statement executes unconditionally on the hot path for every gateway-forwarded message reaching the handler, with no additional preconditions, sampling, or gating, and fires regardless of whether the token later passes or fails authorization. The only precondition is that Debug logging is enabled — a normal, non-privileged operational configuration — combined with read access to node logs, which is a plausible operational scenario (log aggregation/monitoring/support tooling).

## Recommendation
Remove the raw `req` object from the log call in `HandleGatewayMessage`, and instead log only non-sensitive fields (e.g., `req.Method`, `req.ID`) or an explicit `hasAuth` boolean, consistent with the pattern already used in `gateway_vault_request_processor.go`.

## Proof of Concept
1. Enable Debug-level logging on a Chainlink node running the Vault gateway handler.
2. As any client, send a JSON-RPC request (e.g., `secrets_list`) to the gateway with `Bearer <JWT>` set in the request's `Auth` field.
3. `GatewayHandler.HandleGatewayMessage` executes `reqLggr.Debugw("received message from gateway", "req", req)` at [5](#0-4)  before authorization completes.
4. Inspect node logs: the full raw JWT token appears in the `req` field of the "received message from gateway" log entry in cleartext, regardless of whether the token is later accepted or rejected.
