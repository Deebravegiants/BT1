# Title
Webhook Shop-Domain Spoofing via Unsigned Header Field Bypassing HMAC Identity Binding - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC over the raw request body, then dispatches to the app's handler using the `shop-domain` header value as the authoritative tenant identity. That header is never covered by the HMAC signature, so the "shop the signature was computed for" and "shop the handler is told the data belongs to" are two independent values that an attacker can make diverge.

### Finding Description
`Utils::HmacValidator.validate` computes and compares a signature over `verifiable_query.to_signable_string` only: [1](#0-0) 

For webhooks, `to_signable_string` returns solely the raw JSON body — no header, including `shop-domain`, is included in the signed material: [2](#0-1) 

`Registry.process` validates that HMAC and, once it passes, immediately trusts `request.shop` (sourced purely from the `x-shopify-shop-domain`/`shopify-shop-domain` header) as the tenant identity handed to the app's business logic: [3](#0-2) 

The identity binding that should hold is:
`shop that produced the HMAC-signed body == shop attributed to the data by the handler`

Because the header is outside the signed payload, this equality is not enforced. Any actor who can obtain one genuinely HMAC-signed `(body, hmac)` pair for a shop under the same app (trivially available by installing the app themselves — no `api_secret_key`, access token, or privileged access needed) can resend that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary value in the `shop-domain` header. The signature still validates (it never covered that header), and the app's handler receives `WebhookMetadata#shop` claiming to be a different, victim merchant while the body content is fully attacker-controlled.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-acted-upon binding and enables cross-tenant data injection/attribution: an app relying on `WebhookMetadata#shop` (as the gem's own webhook example/tests do) to route webhook effects to per-tenant storage can be made to process attacker-supplied payloads under another merchant's identity (e.g., faking `app/uninstalled`, `orders/create`, or `shop/redact` events attributed to a shop the attacker does not own). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires: (1) installing the app on any shop the attacker controls (a normal, unprivileged action), to obtain one valid `(raw_body, hmac)` pair, and (2) replaying that pair to the app's public webhook endpoint with a forged `shop-domain` header. No secret material, tokens, or elevated access are required, making this readily reachable by any actor with legitimate but unprivileged access to the app.

### Recommendation
Bind the shop domain into the authenticated material, or otherwise re-derive/verify shop identity from a source covered by the signature (e.g., include the header in the signed string using a scheme aligned with Shopify's canonical HMAC computation, or cross-check `shop-domain` against a shop already associated with the specific webhook subscription/session on the app side) before trusting `WebhookMetadata#shop` for tenant-scoped operations. At minimum, document prominently that `shop` is unauthenticated and must be independently validated by consuming apps before use in tenant-sensitive logic.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and receives a real, correctly-signed webhook from Shopify:
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
signature_b64 = Base64.encode64(hmac)  # matches x-shopify-hmac-sha256 sent by Shopify

# 2. Attacker replays the exact same body+signature to the app's public
#    webhook endpoint, but swaps the shop-domain header for a victim shop
#    they do not control:
headers = {
  "x-shopify-topic"       => "orders/create",
  "x-shopify-hmac-sha256" => signature_b64,     # still valid: HMAC never covered shop
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) succeeds (body signature intact)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
#    even though the body/signature came from the attacker's own shop.
```

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end
