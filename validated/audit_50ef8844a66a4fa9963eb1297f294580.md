### Title
OAuth callback sends `client_secret` to an unvalidated `shop` host, unlike every other grant flow in the gem - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token request session directly from `auth_query.shop` without ever passing it through `Utils::ShopValidator`, whereas every sibling credential-exchange flow (`client_credentials.rb`, `refresh_token.rb`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before using the shop value as the request host that receives `client_id`/`client_secret`.

### Finding Description
The identity binding that should hold is: **"the host that receives `client_secret` == a shop domain restricted to `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`."** This equality is enforced in `client_credentials.rb` and `refresh_token.rb`: [1](#0-0) [2](#0-1) 

Both call `Utils::ShopValidator.sanitize!(shop)` and only use `validated_shop` to build the `Auth::Session` whose `shop` attribute becomes the request host in `Clients::HttpClient`: [3](#0-2) 

`HttpClient#initialize` builds `@base_uri` directly from `session.shop` — this is exactly where `client_secret` ends up being POSTed.

In `Oauth.validate_auth_callback`, however, the session used to send the access-token request is built straight from `auth_query.shop`, with **no call to `Utils::ShopValidator`** anywhere in the file: [4](#0-3) 

The only check applied to `auth_query.shop` is `Utils::HmacValidator.validate(auth_query)`, which verifies that `code`, `host`, `shop`, `state`, and `timestamp` were jointly signed with the app's own `api_secret_key`: [5](#0-4) [6](#0-5) 

This HMAC binds `shop` to *something Shopify signed*, but — unlike `client_credentials`/`refresh_token` — it never restricts the resulting value to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`): [7](#0-6) 

### Impact Explanation
If a shop value that is not a `*.myshopify.com` host (e.g. a custom domain, or a value from a non-standard installation path) reaches `validate_auth_callback` with a passing HMAC, `client_secret` and `client_id` are sent verbatim to `https://#{auth_query.shop}/admin/oauth/access_token` via `HttpClient`, with no independent host allow-list check. This is precisely the "host validated versus the host that receives … `client_secret`" binding called out as the analog class: the gem validates the *bytes* (HMAC) but not the *identity* (trusted domain) of the destination host, for this one flow only, while doing both checks everywhere else the app's `client_secret` is transmitted.

### Likelihood Explanation
Exploitability is constrained: forging a valid HMAC requires knowledge of `api_secret_key`, which an unprivileged attacker does not have. I was not able to confirm within the available code whether Shopify's own OAuth server can ever be induced to sign a callback for a non-`myshopify.com` `shop` value (e.g. via custom-domain installs) that an app developer's callback route would blindly accept — that would require testing against Shopify's live OAuth backend, which is outside what I can verify from this repository alone. The vulnerability is therefore a **defense-in-depth inconsistency** rather than a confirmed, self-contained, unauthenticated exploit chain: the missing `ShopValidator` call in `oauth.rb` is a real gap relative to the other grant flows, but I cannot prove from this codebase alone that an attacker without `api_secret_key` can supply an untrusted `shop`/host value that still passes `HmacValidator.validate`.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(auth_query.shop)` in `ShopifyAPI::Auth::Oauth.validate_auth_callback` before constructing `null_session`, matching the pattern already used in `client_credentials.rb` and `refresh_token.rb`, so the host that receives `client_id`/`client_secret` is always restricted to the trusted-domain allow-list regardless of grant type.

### Proof of Concept
Not constructible from the gem alone: reproducing the issue requires a way to make Shopify's OAuth server (or a test harness standing in for it) produce a valid HMAC over an `AuthQuery` whose `shop` value is outside `Utils::ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, then observe `ShopifyAPI::Auth::Oauth.validate_auth_callback` POST `client_id`/`client_secret` to that host via `Clients::HttpClient`. This requires either access to `api_secret_key` (out of scope per the rules) or confirmation of Shopify server-side behavior that is outside this repository's code, so I can state the code-level inconsistency with certainty but cannot supply a fully unprivileged, self-contained PoC.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
```

```ruby
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
```
