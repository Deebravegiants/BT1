### Title
Webhook `shop-domain` header is trusted by handlers but is not covered by the HMAC signature, enabling cross-tenant spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, and `HmacValidator.validate` only checks that HMAC against the body. The `shop` value the registry hands to the app's handler is read from the `x-shopify-shop-domain` header, which is never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then dispatches to the handler using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`, all of which come straight from HTTP headers: [1](#0-0) 

`Request#shop` reads the unauthenticated header, and `Request#to_signable_string` deliberately excludes it (and every other header) from the signable content used for HMAC verification: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only ever compares the computed HMAC of `to_signable_string` (the body) to the received HMAC — it never binds the header-derived `shop` (or `topic`, `webhook_id`) into that signature: [3](#0-2) 

This is exactly the analog called out in the rules: "a field acted on but not covered by the HMAC." The `shop` field is acted on (it becomes the tenant identity forwarded to `WebhookMetadata`/the app's handler via `handler.handle(data: WebhookMetadata.new(... shop: request.shop ...))`), yet it is never bound cryptographically to the payload that the HMAC actually protects.

### Impact Explanation
Any user who operates their own (even a free/trial) shop connected to the app receives genuinely-signed webhooks for their own shop — a valid `(raw_body, hmac)` pair they legitimately possess. Because the `shop-domain` header is not part of the signed content, that same attacker can resend the identical body+HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g., a victim's shop). `HmacValidator.validate` still returns `true` (the body/HMAC pair is authentic), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain. Any host application that uses `data.shop` from the processed webhook as the tenant key (a documented and expected usage per this gem's own webhook-processing flow) will act on attacker-controlled body content while believing it originates from the victim's shop — a cross-tenant identity confusion delivered entirely through this gem's own verification primitive (`HmacValidator`/`Webhooks::Request`), not through host-app misuse of an undocumented API. This satisfies the "Critical - cross-tenant access" impact bucket, since the boundary broken is: `shop` claimed in the header != `shop` actually covered by the cryptographic proof.

### Likelihood Explanation
Requires only an unprivileged actor who can install/operate a shop on the target app (to obtain one genuine signed webhook) and can send arbitrary HTTP POSTs to the app's public webhook endpoint (which is inherently internet-reachable by design). No access to `api_secret_key`, access tokens, or privileged accounts is needed — the attacker reuses a body+HMAC pair they legitimately received for their own shop and only forges the header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the HMAC-verified material, or otherwise cryptographically tie the header-derived shop identity to the signed body (e.g., include it in `to_signable_string`, or independently verify the header against a value embedded in the signed payload) before exposing it as `WebhookMetadata#shop` to handlers.

### Proof of Concept
1. Attacker owns/operates Shop A, which is installed on the target app. The app receives a legitimate webhook for Shop A: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B`), and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker replays the exact same request to the app's public webhook endpoint but changes only the header: `x-shopify-shop-domain: shop-victim.myshopify.com`, keeping body `B` and `x-shopify-hmac-sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`= B`) and compares to `H` — validation succeeds because `B`/`H` were never altered. [4](#0-3) 
4. The registered handler receives `WebhookMetadata` with `shop: "shop-victim.myshopify.com"` even though the body content belongs to Shop A, demonstrating the header-vs-signed-content mismatch that a host app relying on `data.shop` for tenant scoping would fall victim to.
