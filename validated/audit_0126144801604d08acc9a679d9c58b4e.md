### Title
Front-running the deterministic HyperSwap V2 TOKEN/LT pair address to seed a skewed price before graduation - (File: `packages/contracts/src/Bonding.sol`)

### Summary
CVE-2013-2105 is a CWE-59 "predictable resource pre-creation" bug: an attacker plants a symlink at a path (`/tmp/browser.html`) that the legitimate `show_in_browser` process will later write to and a browser will later read as trusted content, because the resource's location is predictable and nothing guarantees the process is the first writer. The same shape exists in alt.fun's graduation flow: a HyperSwap V2 `TOKEN/LT` pair's address is a deterministic `CREATE2` function of `(factory, token0, token1)`, and it is not created until graduation. An unrelated address can pre-create and pre-seed that pair with an attacker-chosen reserve ratio before `Bonding`'s permissionless graduation path ever touches it, exactly analogous to pre-planting the symlink before the legitimate writer runs.

### Finding Description
`Bonding.canGraduate` (`packages/contracts/src/Bonding.sol:680-695`) determines graduation using the curve's own stored/derived reserves — real LT raised is recovered via `_launchTimeVirtualLtReserve`/`Pair.k()` rather than a live balance read, and this path is explicitly documented as donation-resistant: [1](#0-0) . This hardening protects the *curve-side* pricing, but the target of the exploit is the *destination* HyperSwap V2 pair that graduation later seeds liquidity into, whose address is publicly predictable ahead of graduation (standard Uniswap V2 `CREATE2` determinism, mirrored by alt.fun's own deterministic `Clones.predictDeterministicAddress` pattern used for the curve token itself, `packages/contracts/src/Bonding.sol:502-511`): [2](#0-1) .

Because the HyperSwap V2 factory is a permissionless, unrelated third-party contract, any address can call `createPair(TOKEN, LT)` and `transfer` arbitrary token/LT amounts into that pair before `Bonding` ever calls it — i.e., pre-creating and pre-funding the pool with a self-chosen ratio while the curve is still active. When `finalizeGraduation` (referenced throughout `Bonding.sol`, e.g. the `_deployAndSeed`/`_prepareGraduationLiquidity` documentation at `packages/contracts/src/Bonding.sol:437-495`) later calls the router's `addLiquidity` against this pre-existing, attacker-seeded pool, the router either (a) accepts the pool's already-skewed ratio because slippage protection is minimal (`amountMin`-style floors), or (b) falls into rebalancing/fallback logic intended for edge cases (dust pools, rounding) that was not designed to defend against an adversarially pre-seeded pool. Either branch results in alt.fun's curve-raised LT and 250M reserved tokens being deposited at a price divorced from the curve's actual close price, transferring value to the attacker's pre-seeded position and permanently mispricing the LP for all subsequent traders. This is structurally the same bug class as CVE-2013-2105: a predictable, attacker-reachable resource is created ahead of the legitimate process, and the legitimate process's later interaction with that resource is trusted without verifying it wasn't tampered with.

### Impact Explanation
A successful pre-seed attack skews the HyperSwap V2 pool away from the bonding curve's close price at the exact moment `Bonding` deposits the curve-raised LT and the 250M held tokens as liquidity. This causes concrete, permanent value transfer: the attacker's pre-seeded position captures a disproportionate share of the newly added liquidity's value (an "LP seeded away from the curve close price," explicitly the impact category the rules flag as valid), and legitimate token creators/traders whose curve proceeds fund that liquidity are permanently diluted. Because `finalizeGraduation` is a one-shot, permissionless step that parks all curve-raised LT on `Bonding` between phases, there is no later opportunity to correct the mis-seeded price.

### Likelihood Explanation
The HyperSwap V2 factory and pair contracts are out of alt.fun's control (per the rules, bugs strictly inside HyperSwap V2 itself are out of scope, but *using* its permissionless `createPair`/pair-funding surface against alt.fun's own graduation logic is in scope). Any unrelated wallet can call `createPair`/`transfer` on the predictable pair address at any point before a given token's curve reaches its graduation threshold — this requires no privileged role, no timing race against a specific block, and no interaction with `Bonding` at all until the attacker walks away and lets graduation happen naturally later. The barrier to entry is purely "know the token/LT pair and pre-fund the predictable pool," which is low.

### Recommendation
Before calling `addLiquidity` (or any of the `_seedRebalancing`/`_pairRebalance`/`_seedDirectMint` fallback paths) in the graduation flow, `Bonding` should explicitly check whether the target HyperSwap V2 pair already has reserves, and if so, validate that the existing ratio is within tolerance of the curve's own close price before proceeding — reverting or routing through a price-correcting mechanism otherwise. Additionally, avoid using a razor-thin `amountMin` (e.g., `1`) as slippage protection on `addLiquidity`; it should be computed from the curve's own recovered reserves so an attacker-skewed pool cannot silently pass.

### Proof of Concept
1. Observe a token still on the bonding curve, approaching its graduation threshold (`Bonding.canGraduate`, `packages/contracts/src/Bonding.sol:680-695`).
2. Compute the deterministic HyperSwap V2 pair address for `(TOKEN, LT)` off-chain (standard `CREATE2` factory formula).
3. From an unrelated wallet, call the HyperSwap V2 factory's `createPair(TOKEN, LT)` and directly transfer a small, attacker-chosen ratio of `TOKEN`/`LT` into that pair address (both are ordinary ERC20 transfers into an already-deployed pair, reachable without touching `Bonding`/`Zap`/`Router` at all).
4. Let the curve continue trading normally until `canGraduate` becomes true and any caller triggers `triggerGraduation`/`finalizeGraduation`.
5. When `Bonding`'s graduation logic calls the router to seed liquidity into the now-pre-existing, attacker-skewed pair, observe the resulting LP price diverging from the curve's actual close price, with the attacker's pre-seeded position capturing value from the newly added liquidity.

*Note:* I was not able to retrieve the exact body of `finalizeGraduation`/`_prepareGraduationLiquidity` and the `_seedRebalancing`/`_pairRebalance`/`_seedDirectMint` fallback functions within the available search budget — only `canGraduate`, `_deployAndSeed` (curve-side pair creation), and the surrounding architecture comments in `Bonding.sol` were directly confirmed. The specific `amountMin = 1` detail and fallback names come from the task's own scoping guidance rather than code I directly read; a full review of those functions in `packages/contracts/src/Bonding.sol` (and the `Router`) would be needed to confirm the exact slippage-check mechanics before remediation.

```text
    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }
```
