### Title
Unauthenticated `CallDispatcher.dispatch` lets anyone execute arbitrary calls under the shared dispatcher's identity - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher.dispatch` is `external` with **no access control** — it does not check `msg.sender`, does not require the ISMP host, and is not restricted to the token/gateway contracts that are supposed to be its only legitimate callers. [1](#0-0) 

### Finding Description
`HyperFungibleToken.onAccept`, `HyperFungibleTokenUpgradeable.onAccept`, `WrappedHyperFungibleToken.onAccept`, and `WrappedHyperFungibleTokenUpgradeable.onAccept` all forward the attacker-controlled `message.data` field of an incoming cross-chain transfer directly into `ICallDispatcher(_dispatcher).dispatch(message.data)` once the source/amount checks pass: [2](#0-1) 

The design intent is that only these `onAccept` callbacks (gated by `onlyHost` and source-address checks) should ever reach `CallDispatcher.dispatch`. However, `dispatch` itself has no restriction on its caller:
```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
``` [3](#0-2) 

Because there is no caller-authentication analogous to the `onlyHost`/source-verification gates used everywhere else in the ISMP app layer, **any unprivileged EOA or contract** can call `CallDispatcher.dispatch()` directly with a crafted `Call[]` array, bypassing the entire cross-chain message-verification pipeline (no ISMP proof, no relayer, no consensus check needed at all). This mirrors the CVE-2014-4931 bug class: unsanitized/unauthenticated attacker-supplied data (there, a locale string; here, an ABI-encoded call list) is fed straight into a privileged execution sink (there, PHP code generation; here, arbitrary low-level `.call`) without validating who is allowed to supply it.

The practical impact hinges on what identity `CallDispatcher` holds in the broader system. Since the same `CallDispatcher` instance is configured as the shared `_dispatcher` for multiple `HyperFungibleToken`/`IntentGatewayV2` deployments, any state that trusts the `CallDispatcher`'s own address (e.g., token approvals granted to it, roles, or contracts that gate logic on `msg.sender == CallDispatcher`) can be exploited by directly invoking `dispatch()` with attacker-chosen `to`/`data`/`value`, executing calls "as" the CallDispatcher without ever going through a legitimate ISMP-verified message.

### Impact Explanation
Any contract or infrastructure in the ecosystem that grants the `CallDispatcher` address privileges (token allowances, role-based permissions, or that simply treats calls originating from `CallDispatcher` as trusted "post-verified-message" calldata) can have those privileges abused directly and permissionlessly, since the dispatch entrypoint performs zero authentication of its caller. This is a High-severity unauthorized-action / potential fund-theft primitive reachable by a single unprivileged transaction, independent of the token-bridge minting logic it was meant to gate.

### Likelihood Explanation
Trivial and always reachable: `dispatch()` is a plain `external` function with no modifier, callable in a single transaction by anyone, requiring no relaying, no proof, and no privileged role. The barrier to exploitation is only the value the attacker can extract from whatever privileges the deployed `CallDispatcher` address happens to hold.

### Recommendation
Restrict `CallDispatcher.dispatch` to only be callable by the specific set of app contracts authorized to relay verified message calldata (e.g., an `onlyAuthorizedCaller` allowlist configured at construction/owner time), or move the check into a required caller parameter validated against a registry, rather than leaving `dispatch` open to any caller.

### Proof of Concept
1. Attacker identifies a `CallDispatcher` instance shared by one or more `HyperFungibleToken` deployments (its address is public via `dispatcher()`). [4](#0-3) 
2. Attacker ABI-encodes a `Call[]` array targeting any contract that trusts `msg.sender == CallDispatcher` (e.g., a contract that has approved token spend to, or granted a role to, the `CallDispatcher` address).
3. Attacker calls `CallDispatcher.dispatch(encodedCalls)` directly — no ISMP proof, no relayer fee, no host verification required. [3](#0-2) 
4. The call executes with `CallDispatcher`'s identity, exercising whatever trust that identity has been granted elsewhere in the deployment, entirely outside of the intended "only after a verified cross-chain message" flow.

Note: I was unable to fully confirm within the available context whether any deployed contract in this repo currently grants `CallDispatcher`'s address specific approvals/roles beyond being invoked by the `onAccept` callbacks — that would require checking deployment/configuration scripts not covered here. The root-cause finding (missing access control on `dispatch`) is, however, directly confirmed in the source.
