Confirmed: the gem's docs explicitly state `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md:125`), and the shop domain is documented as trusted output for the app to key its tenant records on (`docs/usage/webhooks.md:14`, `docs/usage/webhooks.md:25-26`). ### Title
Webhook shop-domain identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) authenticates solely the request body. The `shop` (and `topic`) values consumed by `Registry.process` and handed to the app's handler as tenant identity come straight from HTTP headers, which carry no HMAC coverage at all.

### Finding Description
`ShopifyAPI::Webhooks::Request` reads `shop` directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding to the signed payload: [1](#0-0) 
The HMAC is computed and verified using only the raw body: [2](#0-1) 
`Registry.process` calls `Utils::HmacValidator.validate(request)` — which recomputes the HMAC over `to_signable_string` (i.e. the raw body only) and compares it to the `hmac` header — then immediately trusts `request.shop` (and `request.topic`) to build `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop_header == shop_bound_by_hmac`. Before the attack, a legitimate webhook for shop A has `raw_body_A` signed with `HMAC(secret, raw_body_A)` and headers `shop=A`. After the attack, an attacker who has observed (or received, as the legitimate owner of shop A) one authentic webhook delivery replays the exact same `raw_body_A` and `hmac` value but substitutes `x-shopify-shop-domain: B` (or any other shop string). `HmacValidator.validate` only checks `HMAC(secret, raw_body_A) == received_hmac`, which still passes because the body and HMAC are unchanged — the shop header was never part of the signed material. `Registry.process` then dispatches the handler with `shop: "B"` even though the payload's HMAC proves nothing about which shop it belongs to.

This is the "field acted on but not covered by the HMAC" class of bug: the shop identity used by the host application to attribute webhook data to a tenant (as documented in `docs/usage/webhooks.md`: `data.shop` is "The shop domain of the webhook") is fully attacker-controlled while the gem's documentation and API surface imply that `Registry.process` "will verify the request did indeed come from Shopify," implicitly including the shop attribution.

### Impact Explanation
This breaks the tenant/shop identity binding validated by the gem before dispatching to the host app's handler. An attacker who controls one legitimate installation (any merchant/shop can install most Shopify apps) can capture their own valid webhook deliveries (body + hmac) and replay them against the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header, causing the host app — relying on the gem's stated verification guarantee — to process/store the payload under a different shop's tenant context. Depending on how the host app keys data by `data.shop` (order sync, inventory updates, uninstall/GDPR events, etc.), this enables cross-tenant data injection/corruption, which falls under "cross-tenant access."

### Likelihood Explanation
Any unprivileged internet user who can install the app once (a standard, unauthenticated action available to any Shopify merchant) can capture a legitimate webhook delivery and byte-for-byte replay its body+hmac with a forged shop header, requiring no access to `api_secret_key`, access tokens, or any other credential — it exploits only a gap in what the gem signs.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the HMAC-signed material verified by `HmacValidator`, or otherwise cryptographically bind the `x-shopify-shop-domain` header value to the request signature before trusting it in `WebhookMetadata`. At minimum, `Registry.process` should cross-check the header-derived shop against an out-of-band trusted value (e.g., looked up via `webhook_id`) rather than trusting the header outright.

### Proof of Concept
1. App owner installs the app for `shop-a.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid_hmac_for_body>`, and some `raw_body`.
3. Attacker (the same installer, or anyone who intercepts this legitimate request) resends an HTTP request to the same endpoint with the identical `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` from the forged header; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only covers `raw_body`.
5. `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the host application processes/stores the attacker-supplied body under the victim shop's tenant record.

          received_signature = verifiable_query.hmac
