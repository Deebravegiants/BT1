### Title
`Oauth.auth_base_uri` builds the OAuth authorize URL from the raw, unsanitized `shop` argument, enabling SSRF/host redirection of the authorization flow - (`lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.auth_base_uri` interpolates the `shop` argument directly into `"https://#{shop}/admin"` without ever calling `ShopValidator.sanitize!`/`sanitize_shop_domain`. Since the documented usage pattern has host apps pass an attacker-influenced `shop` value (e.g. from a request header/param) straight into `begin_auth`, an attacker can cause the generated `auth_route` to point at an arbitrary host.

### Finding Description
The binding that should hold is: `URI(auth_route).host == ShopValidator.sanitize!(shop)`. Tracing the code shows this is false because `sanitize!` is never invoked in this path.

- `begin_auth` (`lib/shopify_api/auth/oauth.rb:22-52`) takes `shop:` as a plain `String` with no validation beyond Sorbet's type check (which only asserts it's a `String`, not that it's a legitimate Shopify domain).
- It calls `auth_base_uri(shop)` (`lib/shopify_api/auth/oauth.rb:117-128`):
  ```ruby
  def auth_base_uri(shop)
    return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
    ...
  end
  ```
  This is a raw string interpolation of the attacker-controlled `shop` value into the host position of a URL, with **no call anywhere to `ShopifyAPI::Utils::ShopValidator.sanitize!` or `.sanitize_shop_domain`**, unlike other parts of the codebase where the shop domain matters for security decisions (`lib/shopify_api/utils/shop_validator.rb`).
- `begin_auth` then appends `/oauth/authorize?...` to this attacker-influenced base and returns it as `auth_route` (`lib/shopify_api/auth/oauth.rb:49`), which the docs (`docs/usage/oauth.md:180-201`) explicitly instruct the host app to use as an HTTP redirect `Location` header, without any additional gem-side sanitization step.

Attacker's exact request: a normal HTTP request to the app's login route (e.g. `/login?shop=attacker.example.com`) where the host app takes the `shop` param verbatim (as shown in the documented example `shop = request.headers["Shop"]` then `begin_auth(shop: domain, ...)`) and passes it to `begin_auth`. The resulting `auth_route` becomes `https://attacker.example.com/admin/oauth/authorize?client_id=...&redirect_uri=...&state=...`. The app redirects the victim's browser there. Because `client_id` and the legitimate `redirect_uri` are also leaked in that URL to the attacker's server, and because a merchant might mistakenly trust the app's redirect (open redirect/SSRF-of-flow), this diverts the start of the OAuth flow away from Shopify's real authorization host.

Existing guards do not stop this:
- `Context.setup?`/`Context.private?` checks (lines 31-34) only ensure the app is configured and not a private app — they do nothing to validate `shop`.
- `ShopValidator.sanitize!` exists and is used elsewhere in the codebase (e.g., `token_exchange.rb`, `refresh_token.rb`, `client_credentials.rb` per the earlier grep) but is conspicuously **not** called in `auth_base_uri`/`begin_auth`.
- The `DevServer`-specific branch only triggers when `shop.include?(".my.shop.dev")`; for any other attacker string, execution falls through to the raw, unsanitized interpolation.
- Note: this differs from `validate_auth_callback`, where the shop actually returned in `auth_query.shop` comes from Shopify's callback and is checked via HMAC (`Utils::HmacValidator.validate`) — but that only protects the *callback* path, not the *initiation* (`begin_auth`) path, which is what constructs the redirect URL in the first place.

### Impact Explanation
This is a **High** severity SSRF/open-redirect of the OAuth initiation flow, matching the "SSRF driving an authenticated (or in-flow) request to an unintended host" category. The attacker can:
- Redirect a victim's browser (whoever clicks the manipulated login link) to an attacker-controlled host for the "authorize" step, leaking the app's `client_id` and the configured `redirect_uri` to that attacker-controlled server via the query string.
- Potentially escalate toward token theft if the flow can be chained with a lookalike phishing page mimicking Shopify's OAuth consent screen and misdirecting `redirect_uri` handling, though full escalation to code/token theft depends on the merchant being fooled or on further weaknesses in `redirect_uri` allow-listing, which are outside this gem.
- Repeatable against any victim who can be induced to click a crafted login link containing a malicious `shop` value; blast radius is limited to that single OAuth flow instance per request but is trivially repeatable at scale (no secrets required).

### Likelihood Explanation
- Precondition: the host app must be using `ShopifyAPI::Auth::Oauth.begin_auth` (Authorization Code Grant flow) and pass an externally-supplied `shop` value without doing its own domain validation before calling `begin_auth` — this matches the documented example in `docs/usage/oauth.md`, which pulls `shop` from `request.headers["Shop"]` and passes it straight through with no sanitize step shown.
- Attacker cost is trivial: no credentials, secrets, or special access needed — only the ability to control the `shop` value sent to the app's own login route and get a victim to visit the crafted link.
- Feasibility is high; this is a one-line reachable code defect (`lib/shopify_api/auth/oauth.rb:119`), not dependent on timing or race conditions.

### Recommendation
In `auth_base_uri` (and/or at the top of `begin_auth`), validate/normalize `shop` using `ShopifyAPI::Utils::ShopValidator.sanitize!(shop)` (raising `Errors::InvalidShopError` for untrusted domains) before using it to build `auth_route`, mirroring how `ShopValidator` is already used by other Auth flows (`client_credentials.rb`, `refresh_token.rb`, `token_exchange.rb`).

### Proof of Concept
```ruby
# test/auth/oauth_ssrf_test.rb
require "test_helper"

class OauthBeginAuthSsrfTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", host_name: "app.example.com",
      scope: "read_products", is_embedded: false, api_version: "unstable",
      is_private: false,
    )
  end

  def test_begin_auth_does_not_sanitize_shop
    malicious_shop = "attacker.example.com#@real-shop.myshopify.com"

    # Confirm ShopValidator rejects this value
    assert_nil ShopifyAPI::Utils::ShopValidator.sanitize_shop_domain(malicious_shop)

    result = ShopifyAPI::Auth::Oauth.begin_auth(shop: malicious_shop, redirect_path: "/callback")
    host = URI.parse(result[:auth_route]).host

    # BROKEN BINDING: host should equal sanitize! result (which would raise), but instead
    # equals the raw attacker-controlled shop value.
    assert_equal malicious_shop.split("#").first, host,
      "auth_route host was built from unsanitized shop, demonstrating SSRF/open-redirect"
  end
end
```
This demonstrates that `auth_base_uri`/`begin_auth` produce an `auth_route` whose host is attacker-controlled and diverges from what `ShopValidator.sanitize!` would allow (which would raise `Errors::InvalidShopError` for this input).
