### Title
Prepaid bandwidth subscriptions keep ticking toward expiry while `EvmHost` freeze prevents both consumption and top-up, causing permanent, unrecoverable loss of paid-for bandwidth - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`pallet-bandwidth` sells time-boxed byte allowances (`Subscription.expires_at`) that are fixed at purchase time and expire purely by wall-clock time on Hyperbridge, independent of whether the paying app's source chain is able to dispatch messages at all. `EvmHost` can be frozen (`FrozenStatus.Outgoing`/`All`) by the admin/handler for emergency reasons, which blocks both the `dispatch()` call apps use to consume their bandwidth and the `purchase()` call used to top up or extend it. During that freeze window the subscription's clock keeps running on Hyperbridge and can fully expire, permanently destroying value the app already paid for, with no compensating pause or refund mechanism. This mirrors the GMX finding: an emergency-disable of the action path (order creation/decrease) does not pause the time-based fee/allowance accounting (borrowing/funding fees), penalizing users for something outside their control.

### Finding Description
`Subscription.expires_at` is computed once at purchase and never extended: [1](#0-0) 

Read/consumption paths only ever compare against `now`, with no notion of "paused" time: [2](#0-1) [3](#0-2) 

The gate itself sweeps and rejects strictly by `expires_at > now`, with no override for source-chain unavailability: [4](#0-3) 

The test suite explicitly documents (and asserts as intended behavior) that an unused subscription "expires on its own clock" regardless of whether it was ever reachable for consumption — "what you don't reach in time, you lose": [5](#0-4) 

Meanwhile, on the EVM source chain, both the consumption path (`dispatch`) and the top-up/purchase path funnel through `IDispatcher.dispatch`, which is gated by `notFrozen`: [6](#0-5) [7](#0-6) 

`setFrozenState` can put the host into `FrozenStatus.Outgoing` or `All`, which is a legitimate emergency-response action (analogous to GMX disabling order creation/execution), but there is no corresponding mechanism to pause the bandwidth subscription's expiry clock on Hyperbridge while that freeze is active: [8](#0-7) [9](#0-8) 

Because `BandwidthManager.purchase()` on the EVM side also dispatches through the same frozen `IDispatcher.dispatch` path, an app cannot even top up or extend its allowance during the freeze — it is fully locked out of both consuming and renewing its paid-for bandwidth while the clock on Hyperbridge continues to run down toward `expires_at`.

### Impact Explanation
An app that has prepaid for a tier (e.g., the $1000/8MB tier) loses the unconsumed portion of its allowance permanently and with no refund if `EvmHost` on its source chain is frozen for any duration approaching or exceeding the remaining subscription window. Since freezing is an emergency admin action that can legitimately last an unpredictable amount of time (until the incident is resolved), and subscriptions are not extendable/refundable (`expires_at` is "fixed at purchase, never extends" per the pallet's own doc comments), users bear an unbacked, permanent loss of already-paid protocol fees through no fault of their own — the same causal pattern as the GMX report (fee/time accounting oblivious to an availability pause), applied to Hyperbridge's prepaid-bandwidth economics rather than borrowing/funding fees.

### Likelihood Explanation
Emergency freezes are an intended, documented operational tool (`FrozenStatus`), not a hypothetical or malicious-admin scenario — the report explicitly frames this class of bug as arising from legitimate emergency pauses. Any app using prepaid bandwidth on a chain where the host is frozen for a period comparable to its subscription duration will trigger this loss deterministically; no adversarial timing or race condition is required, only ordinary occurrence of a freeze event during an active subscription window.

### Recommendation
Track cumulative "frozen time" on the source chain (or accept freeze-duration extension messages from `EvmHost`/host-executive) and extend `expires_at` for affected `(chain, app)` subscriptions by that duration, or expose an explicit pause primitive in `pallet-bandwidth` that stops the expiry clock while the corresponding `BandwidthManager`'s host is frozen, mirroring the alternative recommended (but ultimately rejected in the GMX case) fix of "tracking and accounting for disabling, and adjusting fees/allowances based on whether things were paused."

### Proof of Concept
1. App on chain `C` purchases a bandwidth tier: `BandwidthManager.purchase()` dispatches a `BandwidthPurchaseMsg`, and `pallet-bandwidth::on_accept` calls `push_subscription`, setting `expires_at = now + duration_secs` (`modules/pallets/bandwidth/src/lib.rs:404-437`).
2. Governance/handler calls `EvmHost.setFrozenState(FrozenStatus.Outgoing)` on chain `C` for an emergency incident (`evm/src/core/EvmHost.sol:354-357`, `IHost.setFrozenState`).
3. While frozen, the app cannot call `dispatch()` (reverts `FrozenHost`, per `evm/tests/foundry/EvmHostTest.sol:118-139`) to consume its allowance, and cannot call `BandwidthManager.purchase()` to extend/renew it, since `purchase()` also routes through `IDispatcher(_host).dispatch(...)`.
4. On Hyperbridge, `Allowance::<T>` for `(C, app)` continues to age; once wall-clock time passes `expires_at`, the next gate touch (`try_consume`) sweeps it (`modules/pallets/bandwidth/src/lib.rs:523-535`), matching the test `unused_subscription_expires_independently` (`modules/pallets/testsuite/src/tests/pallet_bandwidth.rs:317-342`).
5. Freeze is lifted after the incident, but the app's prepaid allowance is gone — no refund path exists, resulting in a real, permanent loss of funds paid for bandwidth that could never be used.

/// Critical ISP-style property: a sub whose drain never starts (because
/// older subs are still being consumed) still expires on its own clock.
/// What you don't reach in time, you lose.
#[test]
fn unused_subscription_expires_independently() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		register_manager(APP_CHAIN);
		// sub#0 is fat + long: drain stays inside it the whole test.
		configure_tier(TIER1, 1_000_000, QUARTER_SECS);
		// sub#1 is thin + short: nominally available, but never reached.
		configure_tier(TIER2, 500, MONTH_SECS);
		buy(TIER1).unwrap();
		buy(TIER2).unwrap();

		// Light usage stays inside sub#0.
		assert_eq!(consume(100), Ok(()));
		assert_eq!(sub_count(APP_CHAIN), 2);

		// Cross sub#1's expiry; first gate hit after that prunes it.
		jump_to(T0 + MONTH_SECS + 1);
		assert_eq!(consume(100), Ok(()));
		assert_eq!(sub_count(APP_CHAIN), 1, "unused sub#1 expired and was swept");
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().tier, TIER1);
	});
}

/**
 * @title FrozenStatus
 * @notice Represents the frozen state of the Host for security and emergency situations
 * @dev Used to halt specific protocol operations during security incidents or upgrades
 */
enum FrozenStatus {
    /// @notice Normal operation - all functions are enabled
    None,
    /// @notice Incoming messages are blocked - prevents receiving cross-chain messages
    Incoming,
    /// @notice Outgoing messages are blocked - prevents sending cross-chain messages
    Outgoing,
    /// @notice All operations are frozen - complete protocol halt
    All
}
