### Title
Public `superApprove` in `HyperFungibleTokenImpl` lets anyone grant unlimited token allowances, enabling theft of any holder's balance - (File: evm/src/utils/HyperFungibleTokenImpl.sol)

### Summary
`HyperFungibleTokenImpl.superApprove(address owner, address spender)` is a `public` function with no access control that calls `_approve(owner, spender, type(uint256).max)`, setting an unlimited ERC20 allowance from any arbitrary `owner` to any arbitrary `spender`, without the owner's consent or signature. [1](#0-0) 

### Finding Description
`HyperFungibleTokenImpl` is a production contract in `evm/src/utils/` used as a mintable/burnable ERC20 gated by `AccessControlEnumerable` (`MINTER_ROLE`, `BURNER_ROLE`, `DEFAULT_ADMIN_ROLE`) for its `mint`/`burn`/role-management functions. [2](#0-1) 

However, `superApprove` bypasses this access model entirely. It is declared `public` with no modifier, and directly invokes the internal `_approve` hook to set `type(uint256).max` allowance from the `owner` argument to the `spender` argument — both fully attacker-controlled, and neither requiring `msg.sender == owner` nor any role check:
```solidity
function superApprove(address owner, address spender) public {
    _approve(owner, spender, type(uint256).max);
}
``` [3](#0-2) 

This contract is not a test-only artifact isolated from production paths: it lives under `evm/src/utils/` and is directly imported and deployed by `TokenFaucet.sol`, which is itself deployable and callable by any unprivileged user via `drip(address token)`: [4](#0-3) 

It is also imported and extended by `FeeToken.sol` (which mints an initial supply to `tx.origin`) and referenced in the deployment script `evm/script/DeployIsmp.s.sol`, indicating it is wired into deployed fee-token infrastructure for the ISMP host rather than confined to an isolated mock used only by tests. [5](#0-4) 

Any address holding a balance of a token deployed from `HyperFungibleTokenImpl` (or `FeeToken`) — e.g., users who received tokens via `TokenFaucet.drip` or hold the ISMP host's fee token — can have their entire balance drained by any attacker: the attacker calls `superApprove(victim, attacker)`, then `transferFrom(victim, attacker, victimBalance)`. This is directly analogous to the reported `burnRebalancer` issue: a state-mutating, fund-affecting ERC20 function (there `burn`, here `_approve`) is exposed publicly with no caller restriction, when it should be restricted to the token owner or omitted from any non-test/production contract entirely.

### Impact Explanation
This is a direct theft-of-funds primitive: any unprivileged actor can drain the full balance of any holder of an `HyperFungibleTokenImpl`/`FeeToken` instance by self-granting unlimited allowance and then calling `transferFrom`. Given this token is wired into the fee-token/faucet deployment path used by the ISMP host and dispatch fee mechanisms, exploitation could result in loss of user funds and disruption of the fee-token economy backing message dispatch — satisfying the "concrete theft ... of funds" bar for validity.

### Likelihood Explanation
Trivial and cheap to execute: a single unprivileged transaction (`superApprove`) followed by a standard `transferFrom` call is sufficient. No proof, consensus state, or relayer/keeper cooperation is required — any address with knowledge of a victim's balance can act unilaterally.

### Recommendation
Remove `superApprove` from `HyperFungibleTokenImpl.sol`, or if a test helper is genuinely needed, move it out of `evm/src/utils/` into a test-only mock contract that is never inherited by anything reachable from production/faucet deployments (`FeeToken.sol`, `TokenFaucet.sol`, `DeployIsmp.s.sol`). If retained in a production-adjacent contract, gate it behind `onlyRole(DEFAULT_ADMIN_ROLE)` or restrict to `msg.sender == owner` (standard `approve` semantics).

### Proof of Concept
1. Deploy or locate any `HyperFungibleTokenImpl`/`FeeToken` instance where `victim` holds a balance (e.g., via `TokenFaucet.drip`). [6](#0-5) 
2. Attacker calls `token.superApprove(victim, attacker)` — no restriction stops this call. [3](#0-2) 
3. Attacker calls `token.transferFrom(victim, attacker, token.balanceOf(victim))`, draining the victim's entire balance using the standard inherited ERC20 `transferFrom`, backed by the unlimited allowance set in step 2.

contract HyperFungibleTokenImpl is ERC20, AccessControlEnumerable {
    bytes32 public constant MINTER_ROLE = keccak256("MINTER ROLE");
    bytes32 public constant BURNER_ROLE = keccak256("BURNER ROLE");

    /// @notice Custom error thrown when a non-gateway address attempts to mint or burn
    error OnlyGateway();

    /**
     * @notice Initializes the token with a name, symbol, and admin
     * @param admin The address that will have DEFAULT_ADMIN_ROLE to grant/revoke roles
     * @param name The name of the token
     * @param symbol The symbol of the token
     */
    constructor(address admin, string memory name, string memory symbol) ERC20(name, symbol) {
        require(admin != address(0), "Admin cannot be zero address");
        _grantRole(DEFAULT_ADMIN_ROLE, admin);
    }

    /**
     * @notice Returns the admin address (for compatibility with gateway() interface)
     * @dev Returns the address with DEFAULT_ADMIN_ROLE
     * @return The address of the admin
     */
    function gateway() public view returns (address) {
        // Return the first admin (there should typically be only one)
        // This is primarily for interface compatibility
        if (getRoleMemberCount(DEFAULT_ADMIN_ROLE) > 0) {
            return getRoleMember(DEFAULT_ADMIN_ROLE, 0);
        }
        return address(0);
    }

    /**
     * @notice Mints tokens to the specified account
     * @dev Can be called by any address with MINTER_ROLE
     * @param to The address that will receive the minted tokens
     * @param amount The amount of tokens to mint
     */
    function mint(address to, uint256 amount) external onlyRole(MINTER_ROLE) {
        _mint(to, amount);
    }

    /**
     * @notice Burns tokens from the specified account
     * @dev Can be called by any address with BURNER_ROLE
     * @param from The address from which tokens will be burned
     * @param amount The amount of tokens to burn
     */
    function burn(address from, uint256 amount) external onlyRole(BURNER_ROLE) {
        _burn(from, amount);
    }

    mapping(address => uint256) private consumers;

    // @dev Will only drip tokens, once per day
    function drip(address token) public {
        uint256 lastDrip = consumers[msg.sender];
        uint256 delay = block.timestamp - lastDrip;

        if (delay < 1 days) {
            revert("Can only request tokens once daily");
        }

        consumers[msg.sender] = block.timestamp;
