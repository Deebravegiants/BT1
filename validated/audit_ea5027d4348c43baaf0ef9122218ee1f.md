### Title
Webhook `shop-domain` and `topic` headers are trusted by the handler but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and handed to the handler as trusted `WebhookMetadata`. This breaks the intended binding `hmac == HMAC(secret, body || shop || topic)`, mirroring the report's root cause: an identity-relevant field (`amountToken1PendingLPWithdrawal`) that is used in a security-relevant calculation without being kept consistent/bound to the authoritative state that was actually verified.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by comparing the caller's `hmac` against `HMAC(secret, to_signable_string)`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body bytes: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers, which are not part of the signed content at all: [3](#0-2) 

`Registry.process` validates the HMAC over the body, then passes these unauthenticated header values straight into the handler: [4](#0-3) 

The equality the gem should enforce is: *bytes verified by HMAC == bytes the handler acts on for tenant/topic identity* (`hmac == HMAC(secret, body ‖ shop ‖ topic)`). Instead, it enforces only `hmac == HMAC(secret, body)`, while `shop` and `topic` — the fields the handler uses to decide *which merchant* and *which event* it is processing — are parsed from headers that are verified by nothing.

Because the app's `client_secret` (used to compute webhook HMACs) is the same for every shop that installs the app, any store owner can install the app on their own (even free/dev) store, capture one legitimately-signed webhook delivery (raw body + `X-Shopify-Hmac-Sha256`), and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting arbitrary `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` header values. `HmacValidator.validate` will still return `true`, because only the body is checked, and `Registry.process` will invoke the handler with attacker-chosen `shop` and `topic` in `WebhookMetadata`, alongside body content the developer believes is authenticated as coming from that shop/topic.

### Impact Explanation
This lets an unprivileged internet user who has installed the app once forge webhook events attributed to an arbitrary shop domain and/or topic, without ever needing the merchant's access token or `client_secret` leakage. Host applications that key tenant-specific effects (order/customer records, redact flows, entitlement updates) off `WebhookMetadata#shop` or `#topic`, trusting that the gem's HMAC check bound those fields, will process data under a false tenant identity — a cross-tenant access/injection vector, matching the Critical "cross-tenant access" category in scope.

### Likelihood Explanation
Requires only: (1) installing the target app on any shop (no special privilege — this is exactly the normal, unprivileged flow of any Shopify developer/merchant), (2) capturing one webhook delivery's raw body and HMAC header, and (3) replaying it with modified `shop-domain`/`topic` headers to the app's public webhook endpoint. No secret material, no elevated account, and no interaction with legitimate merchants is needed.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the signed payload used for HMAC verification, or independently authenticate/cross-check these header values (e.g., verify `shop-domain` against the session/shop that requested the delivery) before trusting them in `WebhookMetadata`. At minimum, document prominently that `shop` and `topic` on `Webhooks::Request` are unauthenticated and must not be used for tenant-identifying decisions without additional verification.

### Proof of Concept
1. Attacker installs the victim app on their own shop `attacker.myshopify.com` and registers webhook topic `orders/create`.
2. Shopify delivers a webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H = Base64(HMAC-SHA256(client_secret, B))`, plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker resends the exact same `B` and `H` to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(client_secret, B)` — unchanged, since `to_signable_string` is only `@raw_body` — and returns `true`: [5](#0-4) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed_body, ...)`, and the handler performs tenant-scoped side effects believing this data was authenticated for `victim-shop`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
