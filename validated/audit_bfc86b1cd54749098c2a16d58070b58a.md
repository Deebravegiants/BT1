### Title
Webhook tenant identity (`shop`, `topic`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies webhook authenticity by validating an HMAC that covers only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's handler as trusted, authenticated metadata are read straight from HTTP headers that are never included in the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string using the app's `api_secret_key`: [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof the whole request "did indeed come from Shopify" (per the docs) and then builds `WebhookMetadata` directly from unauthenticated headers, including `shop`: [3](#0-2) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are excluded from the signable string: [4](#0-3) 

The library's own documentation reinforces the false assumption that `process` fully authenticates the request, and instructs handler authors to trust `data.shop` for tenant-scoped work (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) [6](#0-5) 

The identity binding that should hold is: `hmac(signed_bytes, api_secret_key) == received_hmac` AND `signed_bytes ⊇ {shop, topic, webhook_id}`. In this implementation the equality only holds for `signed_bytes = raw_body`; the `shop` field that downstream handler code uses to select/scope per-tenant behavior is disjoint from the signed bytes.

### Impact Explanation
A user who has legitimately installed the app on their own store (Shop A) receives a genuine webhook delivery — a `(raw_body, hmac)` pair that is valid because Shopify signed it with the app's real secret. Since the HMAC never binds `shop`/`topic`/`webhook_id`, that same user can resend the identical `raw_body`/`hmac` pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header value referencing another tenant (Shop B). `Registry.process` will still validate successfully (HMAC only checks `raw_body`) and will hand the handler a `WebhookMetadata` claiming the payload belongs to Shop B, even though the data actually originated from Shop A. Any host application logic that uses `data.shop` to select a tenant-scoped session/database record (exactly as the gem's own documented example does) will process/store Shop A's payload under Shop B's identity — a cross-tenant data-integrity/isolation break attributable to this gem's `process`/`Request` API contract, not the host app misusing an undocumented feature.

### Likelihood Explanation
Exploitation requires no privileged credential, access token, or `client_secret` — only the ability to install the app on an attacker-controlled shop (an ordinary, unprivileged action available to any Shopify merchant) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint (which is, by design, unauthenticated aside from the HMAC). This is directly reachable through the gem's documented `Registry.process` / `Webhooks::Request` API, using only headers and a legitimately-received, previously-valid `(body, hmac)` pair.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values (or otherwise cryptographically bind them) in the value that is HMAC-verified, or explicitly document in `Registry.process`/`Webhooks::Request` that only body integrity is guaranteed and that `shop`/`topic` are unauthenticated, requiring callers to independently confirm `data.shop` corresponds to a shop with an active app installation before acting on the payload.

### Proof of Concept
1. Attacker installs the app on `shop-a.myshopify.com` and receives a real webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid signature over `B` with the app's real secret), `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker replays the exact same `B` and `H` to the app's webhook endpoint, only changing the header to `x-shopify-shop-domain: shop-b.myshopify.com` (a victim tenant).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "shop-b.myshopify.com", "x-shopify-hmac-sha256" => H, ...})` is constructed.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `Digest.hexencode(...)` against `to_signable_string` (`B`), which is unchanged.
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "shop-b.myshopify.com", body: JSON.parse(B), ...)` — the app now believes Shop A's payload belongs to Shop B.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
