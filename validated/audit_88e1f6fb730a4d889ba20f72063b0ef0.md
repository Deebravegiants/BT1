### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook forgery via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body; the `shop-domain` header used to attribute the webhook to a tenant is excluded from the HMAC computation. This breaks the identity binding `hmac == f(body, shop)` that the OAuth flow enforces elsewhere in the same gem, allowing an unprivileged user who legitimately receives a webhook for their own shop to replay the (body, hmac) pair while substituting an arbitrary `shop-domain` header, and have `ShopifyAPI::Webhooks::Registry.process` accept it as valid and dispatch it to the app's handler as belonging to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`shop` is read directly from an attacker-controllable HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`) and is never included in `to_signable_string`, which returns only `@raw_body`: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only checks the signable string (the body) against the HMAC: [4](#0-3) 

`Webhooks::Registry.process` uses this validation result and, once it passes, forwards the unauthenticated `request.shop` value straight to the app-supplied handler as the tenant identifier: [5](#0-4) [6](#0-5) 

Contrast this with the OAuth callback verification in the same gem, where the `shop` field *is* explicitly bound into the signable string that the HMAC covers: [7](#0-6) 

This shows the gem's own pattern for binding a tenant identifier to an HMAC-verified value — a pattern that is not applied to the webhook `shop` field. Since a single app has one `api_secret_key` shared across every merchant installation, any merchant who installs the app can trigger a real webhook for their own store (e.g., placing a test order), capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair — both of which are visible to them as the request's own recipient/inspector at the app's public endpoint or via a proxy they control — and then directly POST that same body and HMAC to the app's public webhook URL while setting `shopify-shop-domain` to a victim shop's domain. Because `shop` is not part of the signed content, `HmacValidator.validate` still returns `true`, and the handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's real payload>, ...)`. `Utils::HmacValidator.validate` is not scoped to any code the app author controls to add such a binding, so this is a gem-level design gap, not a downstream misuse of a documented API contract per the docs example: [8](#0-7) 

Note: this analog is realistic under the stated equality-break class ("a field acted on but not covered by the HMAC") but its exploitability outside the app's own trust boundary in practice mirrors Shopify's own real webhook signature scheme (which also signs only the body). The gem does not add any independent binding of `shop` to the signature, and the SDK's public API (`WebhookMetadata#shop`) explicitly exposes this unauthenticated value as if trustworthy per-tenant attribution data, which is the concrete defect surfaced here.

### Impact Explanation
If an app relies on `data.shop` from `WebhookMetadata` (exactly as the gem's own documentation instructs developers to do) to decide which merchant/tenant record to update, an attacker who merely installs the app on their own store can forge webhook deliveries that are processed as belonging to any other shop of the attacker's choosing, causing cross-tenant data corruption/misattribution (e.g., writing attacker-supplied order/product data into another merchant's record). This matches the "cross-tenant access" Critical impact category, since the identity of the acted-upon tenant is not bound to the cryptographic proof of authenticity.

### Likelihood Explanation
Likelihood is constrained by two factors: (1) the attacker must be able to POST directly to the app's public webhook endpoint with custom headers (feasible for any internet-reachable webhook route, which is the norm), and (2) the attacker must obtain a valid `(body, hmac)` pair, which they can trivially do by installing the app themselves and observing/inspecting the request their own store's webhook produces (e.g., via a debugging proxy in front of their own endpoint, or logging the raw request in an app they operate a copy of). No access to `api_secret_key` itself is required, only observation of one valid signed payload from any shop, including their own. This keeps the finding within scope, but it does rely on the app author trusting `data.shop` without additional binding — a natural but not universal integration pattern.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) inside `to_signable_string` for `Webhooks::Request`, or otherwise document and cryptographically bind the tenant identifier to the payload so that `HmacValidator.validate` can reject any request where the claimed shop was not part of what Shopify actually signed. Where the underlying wire protocol (Shopify's own signature scheme) cannot be changed, the gem should not present `request.shop` as an authenticated field to handlers without a corresponding warning, or should require handlers to cross-check `shop` against a known, previously-registered shop/session before trusting it.

### Proof of Concept
1. App exposes `POST /callback/orders/create`, wired per `docs/usage/webhooks.md` to `ShopifyAPI::Webhooks::Registry.process`.
2. Attacker installs the app on `attacker-shop.myshopify.com` and triggers an `orders/create` event (e.g., places an order), capturing the raw POST body `B` and header `x-shopify-hmac-sha256: H` sent by Shopify to the app's endpoint (observable by the attacker as the operator of a receiving proxy/logger in front of their own app instance, or by any means by which they can see their own inbound webhook traffic).
3. Attacker sends a new HTTP request directly to the app's public webhook route with:
   - body = `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged)
   - header `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `hmac` matches `H` and whose `shop` returns `"victim-shop.myshopify.com"`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `to_signable_string` (`= B`) only, matches `H`, and returns `true` — see [3](#0-2)  and [4](#0-3) .
6. The handler's `handle(data:)` is invoked with `data.shop == "victim-shop.myshopify.com"` and `data.body` containing the attacker's own order data, per [5](#0-4) , causing the app to process attacker-controlled data under the victim's tenant identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
