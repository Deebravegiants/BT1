### Title
Withdrawal status/hash misreported for batched same-asset withdrawals due to assetId-only matching - (File: packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts / packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` and the underlying `waitForWithdrawalCompletion()` helper both resolve which on-chain withdrawal record corresponds to a given `WithdrawalIdentifier` by matching **only on `assetId`** (via `near_token_id`), completely ignoring the withdrawal's `index` (the SDK's own disambiguator for multiple withdrawals emitted from the same NEAR transaction). When a single NEAR transaction contains more than one PoA-bridge withdrawal of the *same* asset (a supported pattern, since `WithdrawalParams` batches and `createWithdrawalIdentifier` explicitly carry an `index` field for this purpose), every `describeWithdrawal` call for that transaction returns the same matched record — the first one the POA API finds — regardless of which index was actually requested.

### Finding Description
`findMatchingWithdrawal` in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` is explicitly documented as matching only by asset: [1](#0-0) 

This same pattern is used in `PoaBridge.describeWithdrawal()`, which calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` and returns the matched withdrawal's `status`/`transfer_tx_hash` directly as the SDK-reported outcome for the requested `index`: [2](#0-1) 

The `Bridge` interface's `describeWithdrawal` contract is keyed by `WithdrawalIdentifier`, which includes an explicit `index` to disambiguate multiple withdrawals from one `tx`: [3](#0-2) 

The equality this breaks: "the withdrawal record returned equals the on-chain outcome of the specific withdrawal identified by `(tx.hash, index)`." Instead it returns "any on-chain withdrawal record whose token matches `assetId`," which is not unique when a transaction contains two or more withdrawals of the same token (e.g., two withdrawals of `nep141:usdt....omft.near` to two different destination addresses/amounts within one signed intents transaction). In that scenario, `describeWithdrawal({index: 1, ...})` can return the `status`/`transfer_tx_hash` that actually belongs to withdrawal `index: 0` (or vice versa), because the lookup never consults `index`, `destinationAddress`, or `amount` to disambiguate.

### Impact Explanation
An integrator polling withdrawal status per `index` to decide when to credit/settle a user, or to display/confirm the destination transaction hash, can be told that a *different* withdrawal (different destination, potentially different amount) has completed. Concretely:
- Two same-asset withdrawals to two different destination addresses in one tx: once either one completes, both indices report `{status:"completed", txHash: <the-one-that-completed>}`, letting an integrator believe the second withdrawal (to a different address) is also done — a status/hash misreport that can lead to premature/duplicate credit or a fund confirmation tied to the wrong destination, with no way to detect the mismatch from the SDK's return value alone.
- This matches the "High" impact category: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This requires no malicious relayer/bridge/RPC behavior — it is triggered by ordinary use of the SDK's documented batch-withdrawal capability (`WithdrawalParams[]`, multiple `mt_withdraw`/`ft_withdraw` intents in a single signed transaction) when two withdrawals share the same `assetId`. The code comment in `waitForWithdrawalCompletion.ts` (lines 138-142) confirms this is a known, unaddressed gap rather than a hypothetical edge case, and the `index` field exists specifically to solve this disambiguation problem but is not used in the actual matching logic.

### Recommendation
Disambiguate `findMatchingWithdrawal` (both in `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` and `intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`) using more than `assetId`: incorporate `destinationAddress`/`amount` and/or stable ordering by `index` against the sorted POA API results (as the code comment itself proposes), and fail closed (throw/pending) rather than silently returning an ambiguous match when multiple same-asset withdrawals are outstanding for the same `tx.hash`.

### Proof of Concept
1. Build and sign a single intents transaction containing two `ft_withdraw` (PoA bridge) intents for the same `assetId` (e.g., `nep141:usdt.omft.near`) but different `destinationAddress` values — supported via the SDK's batched `createWithdrawalIntents`/multi-withdrawal flow.
2. Submit the transaction; obtain `tx.hash`.
3. Call `bridge.createWithdrawalIdentifier({ withdrawalParams: paramsA, index: 0, tx })` and `..., index: 1, tx` for the second withdrawal.
4. Once the POA relayer completes withdrawal #0 (destination A) but withdrawal #1 (destination B) is still pending, call `describeWithdrawal` for `index: 1`.
5. Observe: `findMatchingWithdrawal` finds the withdrawals list entry matching `nep141:usdt.omft.near` (withdrawal #0, already completed) and returns `{status: "completed", txHash: <A's tx hash>}` for the `index: 1` request, even though withdrawal #1 (to destination B) has not happened on-chain. An integrator relying on this to release funds/credit for withdrawal #1 will be misled by a status that does not reflect withdrawal #1's real on-chain outcome.

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
