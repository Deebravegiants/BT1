Based on the code review, the claim is technically accurate about the code structure but there's an important mitigating factor: `authorizeRequest` in `http_trigger_handler.go` is called before `setupCallback`, which enforces a separate uniqueness check on `requestID` (the jsonrpc request `id`), returning `jsonrpc.ErrConflict` if a request with the same ID is already in-flight [1](#0-0) . However, this check happens *after* `Authorize` succeeds for both racing requests, and it keys off the request's `id` field, not the JWT `jti` — so it doesn't actually prevent the described race on the JWT replay cache itself, since both requests can still pass `Authorize` concurrently in the way the claim describes before either creates a callback entry. The core claim — that `isReplay` and `recordUsage` are non-atomic, separated by unrelated authorized-key lookup logic within `Authorize` — is confirmed exactly as described in the code.

Audit Report

## Title
JWT Replay Check-Then-Act Race Allows Duplicate HTTP Trigger Requests to Bypass Replay Protection - (`core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go`)

## Summary
`WorkflowMetadataHandler.Authorize` calls `h.jwtCache.isReplay(claims.ID)` [2](#0-1)  and only calls `h.jwtCache.recordUsage(claims.ID)` at the end of the function, after authorized-key lookups [3](#0-2) . Because the two cache operations acquire the mutex independently rather than as a single atomic check-and-set, two concurrent calls to `Authorize` with the same JWT can both pass the replay check before either records usage.

## Finding Description
`jwtReplayCache.isReplay` takes an `RLock` and returns whether the `jti` exists, releasing the lock immediately [4](#0-3) . `jwtReplayCache.recordUsage` takes a separate `Lock` to insert the entry [5](#0-4) . Between these two calls in `Authorize`, unrelated authorized-key map lookups occur [6](#0-5) . This is a textbook TOCTOU: if two goroutines call `Authorize` with the identical signed JWT at nearly the same time, both can observe `isReplay` == false before either calls `recordUsage`, so both pass. This contrasts with the atomic pattern correctly implemented in `RequestReplayGuard.CheckAndRecord`, which holds a single lock across both the existence check and the insert [7](#0-6) .

The only additional safeguard in the pipeline is a per-`requestID` (jsonrpc `id`, not `jti`) uniqueness check in `setupCallback`, which runs after `Authorize` succeeds [1](#0-0) . That check does not close the race window in `Authorize` itself — it only prevents two *identical requestIDs* from both being scheduled for callback delivery, and does not stop the JWT itself from being treated as valid twice inside `Authorize`, nor does it prevent duplicate `sendWithRetries` fan-out if a caller uses two different top-level `requestID`s (jsonrpc `id`) with the same JWT/`jti`, since `requestID` and `jti` are independent fields controlled separately by the request/JWT payload.

## Impact Explanation
This is a genuine race condition in the replay-protection logic that could, in principle, allow a single signed JWT to authorize a workflow execution more than once if two requests with the same JWT (and different or matching top-level `id`s) are submitted concurrently to the same gateway node. However, this requires the caller to already possess a validly signed JWT for a specific single-use trigger and to intentionally or accidentally deliver it concurrently. The actual downstream impact (duplicate execution) is speculative and contingent on: (a) the client sending the same JWT twice concurrently rather than sequentially, (b) the `requestID` uniqueness check in `setupCallback` not otherwise deduplicating the callback, and (c) the downstream workflow lacking its own idempotency guarantees. No concrete fund-movement or authentication-bypass scenario was demonstrated beyond the theoretical race.

## Likelihood Explanation
Exploitability requires only a valid signed JWT for one's own workflow trigger request (which the calling party already possesses by construction, since it signs its own JWTs), plus the ability to fire two nearly-simultaneous requests. No privilege escalation or unauthorized signer capability is required — an authorized workflow signer could duplicate their own single-use token. This is a narrow race window that would require repeated attempts for reliable exploitation, and its downstream security impact is bounded by the `requestID` conflict check and whatever idempotency exists in the workflow DON itself.

## Recommendation
Replace the separate `isReplay`/`recordUsage` calls with a single atomic `jwtReplayCache.CheckAndRecord(jti)` method that acquires the write lock once, checks for existence, and inserts before releasing — following the pattern already used in `RequestReplayGuard.CheckAndRecord` — and call it immediately after JWT signature verification in `Authorize`, before any authorized-key lookups.

## Proof of Concept
1. Sign one valid JWT-bound HTTP trigger request using `utils.CreateRequestJWT` + `SignedString`, per the pattern in `createTestJWTToken` in `http_trigger_handler_test.go`.
2. Launch two goroutines that both call `handler.Authorize(workflowID, tokenString, req)` concurrently with the same `jti`.
3. Observe that under race conditions both calls can return success (no `"JWT token has already been used"` error), unlike the existing sequential test `TestWorkflowMetadataHandler_Authorize`'s "JWT replay protection" subtest [8](#0-7) , which only exercises the strictly sequential case and does not cover concurrent replay.
