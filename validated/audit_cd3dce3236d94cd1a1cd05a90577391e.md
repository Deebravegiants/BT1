### Title
NFT operator can front-run revocation with a surviving per-token approval and seize the lending account - (File: `contracts/position-nft/src/contract.rs`)

### Summary
`PositionNft` exposes the stock OpenZeppelin NFT approval interface, where an address approved for all of an owner’s tokens can itself call `approve` for an individual token. A malicious operator can therefore create a second approval for an accomplice immediately before the owner revokes `approve_for_all`. Revoking the operator does not remove the separately stored token approval, so the accomplice can still `transfer_from` the position NFT, taking ownership of the entire lending account.

### Finding Description
The contract exports the stock `NonFungibleToken` implementation through `impl NonFungibleToken for PositionNft`. [1](#0-0) 

Its approval model has two independent grants:

- `approve_for_all(owner, operator, live_until_ledger)` creates `ApprovalForAll(owner, operator)`.
- `approve(approver, approved, token_id, live_until_ledger)` creates `Approval(token_id)`; `approver` may be either the owner or that owner’s operator. [2](#0-1) [3](#0-2) 

A token ID is also the controller `account_id`; moving the NFT moves the associated collateral and debt. [4](#0-3)  The controller resolves account authority from the current NFT owner rather than a stale stored owner. [5](#0-4) 

The revocation path only updates the operator grant:

```text
approve_for_all(owner=Alice, operator=Bob, live_until_ledger=0)
```

It has no reason or mechanism to inspect `Approval(token_id)`, because that storage entry belongs to the token rather than to the `(Alice, Bob)` operator pair. A token approval created by Bob therefore survives Bob’s operator revocation. The tests confirm that a revoked operator can no longer use `transfer_from`, but do not test or remove a token approval previously created by that operator. [6](#0-5) 

### Impact Explanation
This can cause theft of user funds.

After Eve takes the NFT, Eve or Bob—as the new owner—can call controller account functions such as `withdraw` and `borrow`. The NFT carries the account’s collateral and borrowing capacity, and the documentation explicitly treats NFT approval as handing over the whole account. [7](#0-6) [8](#0-7) 

The attacker can extract withdrawable collateral and borrow up to the account’s risk limits. Once the NFT is transferred to the attacker, the former owner has no remaining owner authority over that account.

### Likelihood Explanation
The attack requires the victim to have granted `approve_for_all` to a malicious or compromised operator. Such a grant is intentionally broad, but users may reasonably treat `approve_for_all(..., 0)` as a complete revocation. The operator can create the backup token approval at any time before revocation, including immediately after receiving the original grant or after observing an attempted revocation.

The resulting window is not merely theoretical: a single surviving `Approval(token_id)` is enough to transfer the NFT permanently. The owner can attempt an atomic defense that both revokes the operator and overwrites every existing token approval, but there is no dedicated revocation entrypoint that makes this safe behavior explicit or easy to discover.

### Recommendation
Prevent operators from originating per-token approvals. Override or replace the inherited `approve` implementation so `approver` must equal `Base::owner_of(token_id)`, rather than merely being the owner or an operator.

If operator-originated approvals are required, bind each token approval to the operator grant that created it and invalidate it when that operator grant is revoked. Because `Approval(token_id)` and `ApprovalForAll(owner, operator)` are separate storage keys, this would require recording the approval creator or grant epoch in the token-approval entry.

Until the code is changed, document that revoking an operator is not sufficient by itself: the owner must also clear or overwrite any existing `Approval(token_id)` in the same atomic transaction, or move the NFT to a safe address before the backup approval is used.

### Proof of Concept
Assume:

- Alice owns controller account `account_id`.
- `account_id == token_id`.
- Bob is an operator approved through `approve_for_all`.
- Eve is another attacker-controlled address.

```rust
let live_until = env.ledger().sequence() + 1000;

// 1. Alice grants Bob operator authority over all of her position NFTs.
nft.approve_for_all(&alice, &bob, &live_until);
assert!(nft.is_approved_for_all(&alice, &bob));

// 2. Before Alice's revocation executes, Bob uses his operator status to
//    create a separate token-level approval for Eve.
nft.approve(&bob, &eve, &token_id, &live_until);
assert_eq!(nft.get_approved(&token_id), Some(eve.clone()));

// 3. Alice revokes only the operator grant.
nft.approve_for_all(&alice, &bob, &0);
assert!(!nft.is_approved_for_all(&alice, &bob));

// 4. The independently stored token approval survives Bob's revocation.
assert_eq!(nft.get_approved(&token_id), Some(eve.clone()));

// 5. Eve transfers the position NFT to Bob or to herself.
nft.transfer_from(&eve, &alice, &bob, &token_id);
assert_eq!(nft.owner_of(&token_id), bob);

// 6. Bob is now the account owner and can use the controller's owner-gated
//    account paths, e.g.:
controller.withdraw(&bob, &account_id, &withdrawals, &Some(bob.clone()));
```

The critical behavior is that step 3 revokes `ApprovalForAll(alice, bob)` but does not clear `Approval(token_id)` created in step 2. Step 5 converts that surviving approval into permanent ownership of the lending account.
