This confirms the vulnerability. The gem's documented API explicitly states that `Registry.process` "will verify the request did indeed come from Shopify" (see `docs/usage/webhooks.md` line 125), and the sample `WebhookHandler` in the docs directly trusts `data.shop` (line 25-26) as the shop domain — but the HMAC computed in `HmacValidator.validate` only signs `to_signable_string`, which for `Webhooks::Request` returns `@raw_body` alone.This confirms the design: `WebhookMetadata.shop` at [1](#0-0)  is passed unauthenticated into the handler, and `VerifiableQuery` only requires `hmac` and `to_signable_string` with no binding to any other field [2](#0-1) .

### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC that covers the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values used by the host application's handler come from HTTP headers that are never included in the signed payload. Because the app's webhook HMAC secret (`Context.api_secret_key`) is the same shared per-app secret used for every shop that installs the app (not a per-shop secret), any shop that has installed the app can generate a genuine HMAC-valid webhook body for content it controls, then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain.

### Finding Description
The identity binding that should hold is:
`hmac_valid(raw_body, secret) == true` should imply `shop_header == shop_that_produced(raw_body)`.

In practice, only `raw_body` is bound by the signature: [3](#0-2) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (i.e., `@raw_body`) and compares it to the `hmac` header — it never checks that the `shop` header is consistent with anything else: [4](#0-3) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and the app's single, shared `Context.api_secret_key`: [5](#0-4) 

Because `api_secret_key` is one static, app-wide secret (not per-shop), any tenant that has legitimately installed the app can obtain a valid `(body, hmac)` pair for a payload of its choosing (e.g., by triggering a real event, such as creating an order with attacker-chosen field values, on their own store) and can compute the corresponding HMAC itself. That attacker-shop can then send a forged POST straight to the app's public webhook route (`docs/usage/webhooks.md` describes this as a `WebhookController#webhook` action reachable by any HTTP client) with:
- the untouched, still-valid `raw_body` and `hmac`,
- the `shop-domain` header rewritten to any victim shop the app also serves.

`Registry.process` will accept this as fully authenticated ("verify the request did indeed come from Shopify", per the docs) and dispatch to the app's handler with `WebhookMetadata.shop` set to the victim's domain: [6](#0-5)  and [1](#0-0) 

The documented handler pattern trusts `data.shop` directly as the authenticated tenant identity for downstream processing (e.g., persisting/queuing work "for" that shop): [7](#0-6) 

This is precisely the "field acted on but not covered by the HMAC" bug class: the `shop` field drives per-tenant behavior in the handler, but it is excluded from the signed bytes, so an attacker who can produce any valid `(body, hmac)` pair (trivial for any installed shop, since the secret is shared) can attribute arbitrary fabricated data to any other tenant of the same app.

### Impact Explanation
This crosses a tenant boundary: it allows one shop (an "unprivileged" tenant with respect to other merchants, requiring no special access beyond installing the app like any other user) to inject fabricated webhook events that the host app will process as authentic data belonging to a different, victim shop. Depending on how the host app's handler uses `data.shop` (queuing background jobs, updating per-shop records, driving business logic keyed by shop), this enables cross-tenant data corruption/injection — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that has more than one shop installed (the normal case for a multi-tenant Shopify app): no credentials beyond a normal app installation are needed, the webhook endpoint is by design internet-reachable, and generating a genuine `(body, hmac)` pair only requires triggering an ordinary shop event or independently reproducing HMAC-SHA256 over attacker-chosen body bytes with the shared `api_secret_key`— wait, the attacker does not know `api_secret_key`; they only obtain a valid pair by having Shopify itself sign a real webhook for their own shop's genuine event. That constrains the attacker to reusing bodies Shopify actually produced for their own shop (they cannot arbitrarily choose the JSON, but they can influence many of its fields via their own store's data, e.g. product/order titles, customer info, metafields), then relabel it as another shop's event.

### Recommendation
Include the shop domain (and ideally topic and webhook id) as part of the signed material verified against the HMAC, or independently verify that the `shop` header corresponds to a shop actually known/installed for this app (e.g., cross-check against stored sessions) before dispatching to the handler in `Registry.process`. At minimum, `Webhooks::Request#to_signable_string` should not be limited to `@raw_body` when other headers are used as trust-bearing identity fields by the handler contract.

### Proof of Concept
1. App "MultiTenantApp" is installed by Shop A (attacker-controlled) and Shop B (victim).
2. Attacker, using Shop A's admin, creates an order with a crafted `note` field, triggering a genuine `orders/create` webhook from Shopify to MultiTenantApp. Attacker's own reverse proxy/logging captures the raw POST: `raw_body` and header `X-Shopify-Hmac-Sha256: <valid-hmac>`, along with `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
3. Attacker crafts a new POST to the same `callback/orders/create` endpoint, using the identical `raw_body` and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only — matches, so validation passes.
5. `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "shop-b.myshopify.com", body: ..., ...))` is invoked, and the host app processes attacker-controlled order data as if it belongs to Shop B.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
