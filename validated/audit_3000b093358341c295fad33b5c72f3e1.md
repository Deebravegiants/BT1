This clearly identifies the pattern: `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb#migrate_to_expiring_token` all call `Utils::ShopValidator.sanitize!(shop)` before using the raw `shop` parameter to construct the request host that receives `client_secret`. But `Oauth.validate_auth_callback` in `lib/shopify_api/auth/oauth.rb` builds the `null_session`/final `Session` directly from `auth_query.shop` — the raw HTTP query parameter — with **no call to `Utils::ShopValidator.sanitize!`** anywhere in that method or in `AuthQuery`.

### Title
OAuth callback builds request host from unsanitized `shop` query parameter, bypassing `ShopValidator` used elsewhere in the gem - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` uses `auth_query.shop` — a raw value taken from the incoming HTTP query string — to build the `Session`/`HttpClient` that the access-token exchange request (carrying `client_id` and `client_secret`) is sent to. Every other credential-bearing flow in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` [1](#0-0) [2](#0-1) [3](#0-2)  to restrict the host to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` before it is used to build the request URL that receives `client_secret` [4](#0-3) . The OAuth authorization-code callback path is the one exception: it constructs `null_session = Auth::Session.new(shop: auth_query.shop)` and later `Session.from(shop: auth_query.shop, ...)` directly, without any equivalent sanitization call [5](#0-4) , and `Clients::HttpClient#initialize` uses `session.shop` verbatim to compute `@base_uri = "https://#{api_host || session.shop}"` for the outbound POST [6](#0-5) .

### Finding Description
The binding that should hold is: **the domain that receives `client_secret` == a domain proven, independent of attacker control, to be a genuine Shopify (`myshopify.com`/`shopify.com`/etc.) endpoint**. `ShopValidator.sanitize!`/`sanitize_shop_domain` is the gem's own mechanism for enforcing exactly this binding — it parses the string as a URI and only returns a host if it's a subdomain of one of `TRUSTED_SHOPIFY_DOMAINS` [7](#0-6) .

`validate_auth_callback` only checks:
1. That the query's HMAC (over `code`, `host`, `shop`, `state`, `timestamp`) verifies against `Context.api_secret_key` [8](#0-7) [9](#0-8) .
2. That the `state` param matches the value stored in the (short-lived) cookie [10](#0-9) .

Neither check constrains what the *value* of `shop` may be — HMAC only proves the query wasn't tampered with relative to whatever `shop` string was included when the signature was computed, and `Context.api_secret_key` is the very secret this request is about to POST to that `shop`-derived host. There is no cross-check that `shop` is actually a `*.myshopify.com`/trusted Shopify host the way `ShopValidator` enforces for every other secret-bearing flow in the same file tree.

By contrast, `begin_auth` also accepts an arbitrary `shop:` with no `ShopValidator` sanitization at all [11](#0-10) , so an app that (as is common) passes a request parameter straight into `begin_auth(shop:)` will carry that same unsanitized `shop` value through the redirect, and it reappears unchanged as `auth_query.shop` at the callback, which then flows into `Session.new(shop:)` → `HttpClient` → the outbound `client_secret`-bearing POST.

### Impact Explanation
If the host application passes attacker-influenced input into `begin_auth(shop:)` (a very common integration pattern — reading `shop` from the login route's query string, as shown in this gem's own documentation example that reads `request.headers["Shop"]` and forwards it in [12](#0-11) ), then `auth_base_uri(shop)` builds `"https://#{shop}/admin"` verbatim [13](#0-12) . Even though the eventual callback still requires a valid HMAC to be accepted, `oauth.rb` gives the caller no library-level assurance that `shop` (the value it will later use to target the `client_secret` POST) is confined to a genuine Shopify host — unlike every sibling flow in this same module, which does enforce that via `ShopValidator`. This is exactly the class of bug the reference report illustrates: a value is used to drive a security-sensitive operation (there: fund transfer amount; here: destination of the app's `client_secret`) via a code path that skips a check ( there: multiply-before-divide; here: `ShopValidator.sanitize!`) that is present and enforced everywhere else in the codebase for the equivalent operation. Practically, this is a High-severity credential-leakage/SSRF-with-credentials risk if any host application relies on this gem's own consistency (as its docs sample encourages) rather than independently re-validating `shop` before calling `begin_auth`.

### Likelihood Explanation
Likelihood is moderate: exploitation depends on the host application forwarding user-controlled input into `begin_auth(shop:)`, which the gem's own documented usage pattern explicitly does (`shop = request.headers["Shop"]`) [14](#0-13) . No access token, `api_secret_key` leak, or privileged account is required — only that this gem's undocumented gap (missing `ShopValidator` call in `oauth.rb`, present in every analogous flow) is relied upon by the integrating app in the way the docs suggest.

### Recommendation
In `lib/shopify_api/auth/oauth.rb`, call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) in both `begin_auth` and `validate_auth_callback`, mirroring `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb#migrate_to_expiring_token`, before using `shop`/`auth_query.shop` to build `auth_base_uri`, `null_session`, or the final `Session`.

### Proof of Concept
1. Host app defines `login` using this gem's documented pattern: `shop = request.headers["Shop"]; ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")` [15](#0-14) .
2. Attacker requests `login` with `Shop: attacker-controlled-string` (no `ShopValidator` check exists in `begin_auth` to reject it) [11](#0-10) , producing `auth_route = "https://attacker-controlled-string/admin/oauth/authorize?..."` [13](#0-12) .
3. If the app's operator/integrator does not independently constrain `shop` to `myshopify.com` (the gem provides no such enforcement here, unlike its other flows), the OAuth code exchange in `validate_auth_callback` will target `https://#{auth_query.shop}/admin/oauth/access_token` with `client_id`/`client_secret` in the POST body [16](#0-15) [6](#0-5) , using whatever host `shop` resolves to.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
