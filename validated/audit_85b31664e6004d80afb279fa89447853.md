### Title
DepositOnChainUtxos double-entry token aliasing lets an attacker mint 2x shielded UTXO value for a single real transfer - (File: contracts/Hinkal.sol / contracts/external-actions/DepositOnChainUtxosExternalAction.sol)

### Summary
`Hinkal.transact` verifies solvency per token index by comparing `balanceOf()` snapshots taken *once for the entire `erc20TokenAddresses` array* before and after the external action, and matching each index's delta to the UTXOs minted for that exact address. Neither the circuit's `distinctErc20AddressChecks` nor any Solidity check verifies that two different `erc20TokenAddresses[i]` entries correspond to *independent* underlying balances. An attacker who deploys a malicious token where two distinct addresses (`A`, `B`) both report the *same* underlying balance (a shared-storage/alias pair) can list `[A, B]` in one `DepositOnChainUtxosExternalAction` call, perform a single real transfer through `A`, and have the check for `B` pass "for free" because `B.balanceOf(hinkal)` mirrors `A`'s post-transfer balance.

### Finding Description
The invariant the code intends to enforce, per token index `i`, is:
```
balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]
```
at `contracts/Hinkal.sol:137-146`, where `balanceDif[i] = newBalances[i] - oldBalances[i]` and `oldBalances`/`newBalances` come from `getBalancesForArray(circomData.erc20TokenAddresses)` (`contracts/Hinkal.sol:78-90`, implemented in `contracts/Transferer.sol:169-176` via `getERC20OrETHBalance` → `IERC20(token).balanceOf(address(this))`).

This check implicitly assumes each `erc20TokenAddresses[i]` maps to an *independent* real balance. The only anti-duplication check is the circuit's `distinctErc20AddressChecks` (`circuits/MainEVMCircuit.circom:171-182`), which only enforces `erc20TokenAddresses[i] != erc20TokenAddresses[j]` as raw field-element (address) inequality — it cannot and does not reason about whether two *different* addresses share the same underlying storage/balance semantics.

Exploit path:
1. Attacker deploys a malicious "double-entry" token with two distinct addresses `A` and `B` that both read/write a single shared balance for a given holder (e.g., two thin proxy/facade contracts delegating to one shared storage contract, or a contract deployed twice via CREATE2 exposing the same mapping). `A` and `B` satisfy `A != B` (passes the circuit's distinctness check) but `A.balanceOf(hinkal)` and `B.balanceOf(hinkal)` always return the same number.
2. Attacker calls `Hinkal.transact` with `externalActionData.externalActionId` pointing at `DepositOnChainUtxosExternalAction`, `erc20TokenAddresses = [A, B]`, `deltaAmounts = [0, 0]` (required by `DepositOnChainUtxosExternalAction.sol:50-53`), and `externalActionMetadata` decoding to `utxoAmounts = [[X], [X]]` (mint one on-chain UTXO of amount `X` tagged `A`, and one of amount `X` tagged `B`).
3. Inside `DepositOnChainUtxosExternalAction.runAction` (`contracts/external-actions/DepositOnChainUtxosExternalAction.sol:49-83`), for index 0 (`A`) it calls `transferERC20TokenFrom(A, userAddress, msg.sender, X)`, performing one real transfer of `X` tokens which increments the *shared* underlying balance held by Hinkal by `X`. For index 1 (`B`), the attacker's `B.transferFrom` is crafted to be a no-op/self-canceling call that returns success (satisfies `safeTransferFrom` in `Transferer.sol:74-81`) without moving any additional real value, because `B` and `A` alias the same storage — a "transfer" through `B` isn't needed to change the shared balance since it already changed via `A`.
4. Back in `Hinkal.transact`, `oldBalances = [0, 0]`, `newBalances = [X, X]` (both aliases read the same shared balance) since both were snapshotted once each for the whole array (`Hinkal.sol:78-90`). For `i=0` (`A`): `balanceDif = X`, `utxoAmount(A) = X` → check passes. For `i=1` (`B`): `balanceDif = X` (same aliased read), `utxoAmount(B) = X` (the second minted UTXO) → check *also* passes.
5. Result: only `X` real tokens ever entered the vault, but `2X` worth of shielded on-chain UTXOs were minted (`onChainCommitments` created for both, inserted via `insertCommitments` at `Hinkal.sol:161-166`). The attacker can later spend both UTXOs through normal shielded withdrawals, draining `X` more than was ever deposited.

None of the existing guards catch this:
- `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` (`HinkalHelper.sol`) only validate array lengths and that `amountChanges[i]==0` / `inputNullifiers[i]==0` when `onChainCreation[i]` is true — they never inspect whether two token addresses are economically distinct.
- `verifyProof` and the circuit's `distinctErc20AddressChecks` only check raw address inequality, not balance independence; on-chain UTXO amounts (`utxoAmounts` in `externalActionMetadata`) are entirely outside the circuit's constraint system (the circuit's `inTotal + amountChanges[i] === outTotal` only binds off-chain output commitments, not the arbitrary on-chain UTXO amounts chosen by `DepositOnChainUtxosExternalAction`).
- `rootHashExists`/`m_index`/`roots` (`MerkleBase.sol:53-64`, `Merkle.sol:20-35`) only validate that the Merkle root is a legitimate historical root; with a single prior leaf, `roots[MINIMUM_INDEX]` equals that one leaf directly (per `insert`), which is a trivially satisfiable precondition for this pure-deposit transaction (no real input UTXOs are consumed, so `ForceEqualIfEnabled` with `enabled <== inAmounts[i][j] == 0` is disabled) — it does not constrain balance solvency at all.
- `insertNullifiers`/nullifier checks are irrelevant since `onChainCreation` inputs require zero input nullifiers.

### Impact Explanation
The attacker mints shielded on-chain UTXOs backed by less real collateral than credited, directly matching "minting shielded value without backing (protocol insolvency)" — Critical severity. Each execution nets the attacker `X` in stolen/uncollateralized shielded value (the size of the second, unbacked UTXO), and the attack is fully repeatable for arbitrary `X` (bounded only by available liquidity later drained through legitimate shielded withdrawals) and repeatable across transactions/tokens.

### Likelihood Explanation
Preconditions: attacker needs (a) to deploy a custom token contract exhibiting the shared-balance/alias property across two distinct addresses (fully within attacker capability, as stated in scope — "attacker controls... the deployed token"), and (b) a valid Merkle root to pass `rootHashExists`, trivially available even with a nearly-empty tree since deposit-only transactions disable the root-equality constraint for zero-amount inputs. No privileged role, no relay, and no other user's key material is required. This is a self-contained, deterministic exploit requiring only the attacker's own funds and a custom token deployment.

### Recommendation
Do not rely solely on per-index `balanceOf` deltas snapshotted once for the whole array. Instead:
- Enforce that each real token transfer inside `DepositOnChainUtxosExternalAction` (and other external actions) is verified with a per-call, per-token balance check immediately surrounding that specific transfer (before/after each `transferERC20TokenFrom`), rather than aggregating balance snapshots for the entire token array before and after all transfers.
- Alternatively/additionally, require and verify (e.g., via `EXTCODEHASH`/registry allow-listing of vetted ERC20 implementations, or a canonical-token registry) that `erc20TokenAddresses` entries are canonical, non-aliased token contracts, and reject unknown/arbitrary tokens for on-chain UTXO creation paths.
- Track a running "expected total balance moved so far" independent of `balanceOf`, driven by amounts actually acknowledged as transferred per specific token contract instance, rather than trusting `balanceOf` reads that can be shared across addresses.

### Proof of Concept
Foundry test plan:
1. Deploy `SharedBalanceToken` pair: contracts `A` and `B` that both delegate `balanceOf`/`transferFrom` reads/writes to one shared `mapping(address=>uint256)` (e.g., both are thin wrappers around a single `Vault` storage contract), such that `A.balanceOf(x) == B.balanceOf(x)` always, and `B.transferFrom` can be made to succeed without changing the shared balance beyond what `A`'s transfer already caused.
2. Deploy `Hinkal`, `HinkalHelper`, `DepositOnChainUtxosExternalAction`, register it as an external action and allowed recipient.
3. Fund attacker EOA with `X` real tokens (mint on the shared vault so `A.balanceOf(attacker) == B.balanceOf(attacker) == X`); approve both `A` and `B` for the external action contract.
4. Craft `CircomData` with `erc20TokenAddresses = [A, B]`, `onChainCreation = [true, true]`, `amountChanges = [0, 0]`, `externalActionData.externalActionMetadata = abi.encode([[X],[X]])`, valid proof/root for a deposit-only transaction (no consumed inputs), `slippageValues = [0, 0]`.
5. Call `Hinkal.transact(...)`.
6. Assertions:
   - Real vault balance delta (shared underlying storage) increased by exactly `X` (`sharedVaultBalance_after - sharedVaultBalance_before == X`).
   - Sum of minted on-chain UTXO amounts credited to attacker (`utxoSet` amounts tagged `A` + tagged `B`) equals `2X`.
   - Assert `2X > X` (credited shielded value exceeds real value received) — this is the broken invariant `net tokens entering Hinkal == sum(amountChanges) + sum(on-chain UTXO amounts minted)` (LHS = `X`, RHS = `0 + 2X`).
   - Confirm transaction does not revert despite the mismatch, proving the `balanceDif == ... + utxoAmount` check is satisfied per-index despite global insolvency.
