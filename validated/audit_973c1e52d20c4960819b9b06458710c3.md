### Title
Missing `address(0)` check on `Order.output.beneficiary` / `Order.user` lets a misconfigured order permanently burn escrowed and filled funds - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`'s fill and withdrawal paths derive the token recipient directly from a user-supplied `bytes32` field (`order.output.beneficiary` for fills, `order.user`/`WithdrawalRequest.beneficiary` for refunds and redemptions) without ever checking that the decoded address is non-zero, mirroring the exact bug class of the referenced `TimeLockPool` report (missing `address(0)` check on a caller-supplied receiver).

### Finding Description
In `IntrinsicIntents._fillSameChain` and `ExtrinsicIntents._fillCrossChain`, the beneficiary address is taken straight from the order the user placed: [1](#0-0) [2](#0-1) 

Both then transfer the solver's output tokens (ERC20 or native) directly to this address with no zero check: [3](#0-2) 

Similarly, the shared escrow-release routine `_withdraw` — used for cross-chain `RedeemEscrow`/`RefundEscrow` settlement and for same-chain cancel/partial-fill releases — decodes the beneficiary from `WithdrawalRequest.beneficiary` (itself populated from `order.user` or `msg.sender` at fill time) and transfers escrowed input tokens or accumulated fees to it without validating it is non-zero: [4](#0-3) 

`_cancelSameChain` builds the refund `WithdrawalRequest` using `order.user` as the beneficiary with no validation either: [5](#0-4) 

None of `placeOrder`, `fillOrder`, or `_withdraw` enforce that the decoded `beneficiary`/`user` address is non-zero anywhere in the reviewed code path. The analogous `HyperFungibleToken.onAccept`/`_toAddr` mint path has the same gap (mints to a caller-chosen `to` address with only a length check, not a zero check): [6](#0-5) 

### Impact Explanation
If a user places an order with `output.beneficiary` (or, via a client bug/UI error, `order.user`) set to `bytes32(0)`, every downstream transfer that is supposed to pay them — the solver's output tokens on fill, the escrow release/refund on the source chain, and any accumulated relayer/transaction fees — is sent to `address(0)` and permanently destroyed. This is unrecoverable fund loss reachable by a single `placeOrder` + `fillOrder` transaction pair from an ordinary, unprivileged user/solver, matching the "concrete... permanent freezing of funds" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: this requires a user (or an integrating wallet/SDK) to pass a zero value for the beneficiary/user field, which is an operator/integration mistake rather than an attacker action, but no contract-level guard prevents it, and the loss is total and irreversible once it happens — consistent with the medium severity of the referenced analog.

### Recommendation
Add explicit `address(0)` checks:
- In `placeOrder`, revert if `order.user == bytes32(0)` or `order.output.beneficiary == bytes32(0)`.
- In `fillOrder`/`_fillSameChain`/`_fillCrossChain`, revert if the decoded `beneficiary` is `address(0)`.
- In `_withdraw`, revert if the decoded `beneficiary` is `address(0)` before any transfer, as a defense-in-depth backstop against malformed cross-chain `WithdrawalRequest` payloads.
- Apply the same `address(0)` guard to `HyperFungibleToken`/`HyperFungibleTokenUpgradeable`'s `_toAddr`-derived mint recipients in `onAccept`/`onPostRequestTimeout`.

### Proof of Concept
1. User calls `placeOrder(order, ...)` with `order.output.beneficiary = bytes32(0)` (e.g., due to a client-side encoding bug that leaves the field unset) and escrows input tokens.
2. A solver calls `fillOrder(order, options)`; `_fillSameChain`/`_fillCrossChain` computes `beneficiary = address(uint160(uint256(order.output.beneficiary))) == address(0)` and sends the required output tokens/ETH to `address(0)` via `IERC20.safeTransferFrom(..., beneficiary, ...)` or `beneficiary.call{value: ...}("")`.
3. Output funds are irrecoverably burned; if the solver is not the malicious party here, they still lose the ability to have delivered value to a real counterparty, and any refund/cancel path that also resolves to `order.user == address(0)` similarly burns the escrowed input tokens in `_withdraw`.
