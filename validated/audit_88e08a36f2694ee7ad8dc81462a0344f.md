### Title
Fee-on-Transfer Tokens Break Escrow Accounting in `WrappedHyperFungibleToken.send()`, Causing Unbacked Cross-Chain Mint/Insolvency - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` pulls `params.amount` of the underlying ERC20 via `safeTransferFrom` but never verifies how much was actually received before encoding that same `params.amount` into the cross-chain `Message` that is dispatched. For any fee-on-transfer (or deflationary) underlying token, the contract locks less than it broadcasts, so the destination side unlocks/mints the full pre-fee amount — draining the escrow relative to what is actually backed.

### Finding Description
In `send()`, the underlying token is locked with a blind `safeTransferFrom`: [1](#0-0) 

The same unverified `params.amount` is then embedded directly into the dispatched `Message.amount` used to build the ISMP request: [2](#0-1) 

Unlike `IntentGatewayV2.placeOrder`, which explicitly snapshots balances before/after every token pull and mutates the order to the *actually received* amount specifically to handle fee-on-transfer tokens (see the balance-diff pattern and dedicated `FeeOnTransferToken` test suite): [3](#0-2) [4](#0-3) 

`WrappedHyperFungibleToken` has no such balance-diff protection anywhere in `send()`, `onAccept()`, or `onPostRequestTimeout()`. On `onAccept()` at the destination, the peer contract transfers out `message.amount` (the full, pre-fee amount) to the beneficiary: [5](#0-4) 

If the destination is a plain `HyperFungibleToken` (burn/mint model), it will `_mint` the full `message.amount`, which is strictly more than what was actually escrowed on the source chain — an unbacked mint. If the destination is another `WrappedHyperFungibleToken` instance and the message later times out, `onPostRequestTimeout()` also attempts to refund the full, unreduced `message.amount`: [6](#0-5) 

Because the actual locked balance is smaller than the amount referenced by every message, this discrepancy accumulates with every `send()` call for a fee-on-transfer underlying. Eventually the contract's escrowed balance is insufficient to satisfy legitimate unlock/refund obligations from prior or subsequent messages, resulting in a stuck contract state (some `safeTransfer` calls will revert once the shortfall exceeds available balance) — freezing funds for the affected users who can no longer redeem/timeout their locked tokens.

### Impact Explanation
This is directly reachable by any unprivileged user who calls `send()` with a fee-on-transfer/deflationary ERC20 configured as the `_underlying` token. Impact is either:
- Unbacked minting on the destination chain (destination mints/unlocks more than what was actually escrowed on the source), or
- Permanent freezing of funds once the escrow shortfall makes later `onAccept`/`onPostRequestTimeout` transfers revert due to insufficient balance, since ISMP delivery for those paths would then fail with no remediation path in this contract.

Both align with High severity: unbacked mint and permanent freezing of funds are explicitly in-scope impact categories.

### Likelihood Explanation
Likelihood depends on the owner configuring a fee-on-transfer or deflationary token as `_underlying` via `configure()`. This is a normal, foreseeable configuration for a generic token-wrapping bridge (the codebase's own comments and the sibling `IntentGatewayV2` module treat fee-on-transfer tokens as an expected, supported case and specifically test for them). Given `WrappedHyperFungibleToken` is meant to wrap "existing ERC20 tokens" generically, and no validation prevents deploying it against such tokens, likelihood is Medium-High for any deployment targeting non-standard ERC20s.

### Recommendation
In `send()`, measure the actual balance delta before/after `safeTransferFrom` (as already done in `IntentGatewayV2.placeOrder`) and use that actual received amount both for escrow accounting and for the `Message.amount` encoded in the dispatched request, rather than trusting the caller-supplied `params.amount`.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` and configures `_underlying` to a token that charges e.g. a 1% fee on transfer (same pattern as the `FeeOnTransferToken` test helper already present in the repo test suite).
2. User calls `send({ amount: 1000e18, ... })`. `safeTransferFrom(msg.sender, address(this), 1000e18)` results in the contract actually receiving `990e18` (fee burned/redirected), but `_buildDispatchPost` still encodes `amount: 1000e18` in the `Message` body.
3. On the destination chain, `HyperFungibleToken.onAccept()` (or the peer `WrappedHyperFungibleToken.onAccept()`) executes `_mint(beneficiary, 1000e18)` / `safeTransfer(beneficiary, 1000e18)` — 10e18 more than was actually locked.
4. Repeating this pattern drains the real backing ratio; eventually a subsequent legitimate `onAccept` or `onPostRequestTimeout` call on the source `WrappedHyperFungibleToken` reverts due to insufficient underlying balance, freezing that user's funds. [7](#0-6)

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
