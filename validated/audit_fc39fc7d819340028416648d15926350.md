### Title
Deposit attached to a failed `DeterministicStateInitAction` is silently lost (never credited or refunded) - ([File: runtime/runtime/src/deterministic_account_id.rs])

### Summary
When `action_deterministic_state_init` invokes `deploy_deterministic_account`, a failure inside `use_global_contract` (e.g. `GlobalContractDoesNotExist` because the referenced `GlobalContractIdentifier::AccountId` was never published or was deleted) causes an early return via the `if result.result.is_err() { return Ok(()); }` guard at line 53-55, before any of the deposit-handling logic (`check_storage_stake` / `deposit_refund` / `Receipt::new_balance_refund`) executes. The `action.deposit` value carried by the failed action is never added to the account balance and never refunded to the sender, meaning it is dropped from the state entirely.

### Finding Description
The relevant flow in `action_deterministic_state_init` (`runtime/runtime/src/deterministic_account_id.rs:15-94`) is:

1. If the account doesn't exist, a bare `0` balance account is created and inserted into `maybe_account` [1](#0-0) .
2. If the account has no contract yet, `deploy_deterministic_account` is called, which in turn calls `use_global_contract` [2](#0-1) .
3. `use_global_contract` checks `state_update.contains_key(&key, ...)` for the `GlobalContractCode` trie key derived from the attacker-chosen `GlobalContractIdentifier::AccountId`; if it's absent it sets `result.result = Err(GlobalContractDoesNotExist)` and returns *before* touching `account.storage_usage()` or `account.contract()` [3](#0-2) .
4. Back in `action_deterministic_state_init`, the check `if result.result.is_err() { return Ok(()); }` (line 53-55) short-circuits, skipping the entire deposit-accounting block that would otherwise call `check_storage_stake`, add missing balance via `account.set_amount(...)`, or push a `Receipt::new_balance_refund(...)` for the unused portion [4](#0-3) .

The `action.deposit` field is a value carried by the `DeterministicStateInitAction` itself (distinct from any separate `Transfer` used to pre-fund the account, per the NEP-616 doc description of the field: "a field to include a balance specifically to cover storage… anything above the required amount to cover storage requirements is refunded") [5](#0-4) . Unlike `Transfer`, whose deposit is credited to the account unconditionally as part of executing the action, `DeterministicStateInitAction`'s deposit is only ever applied to the account balance inside the `deposit_refund`/`check_storage_stake` block that lies past the early-return guard. No code path in this file (or, as far as could be found in this investigation, elsewhere in `runtime/runtime/src/lib.rs`'s general receipt-processing loop) credits this deposit to any account or emits a refund receipt when `deploy_deterministic_account` fails. As a result, the deposit is neither added to `account.amount()` nor refunded to the sender nor recorded in `tokens_burnt` — it is unaccounted for, which is a token-conservation invariant violation if confirmed to have no other safety net.

I was not able to fully verify (within the available iterations) whether some other generic per-receipt mechanism outside this file catches and refunds unused action deposits on any action failure across the whole codebase; this file itself contains no such fallback for the `GlobalContractDoesNotExist` early-return path, which is the concrete gap identified.

The related claim in the prompt about "send-side per-byte/per-entry fee overcharging vs. free repeated probing" is not a separate bug: NEAR's prepaid-gas model always charges send-side fees upfront regardless of whether the action ultimately succeeds (the same is true for any failed `FunctionCall` or `DeployContract`), so that part of the question does not describe a protocol flaw distinct from normal fee prepayment semantics.

### Impact Explanation
If the deposit-loss is not caught elsewhere, this is a fund-loss bug: any deposit an attacker (or an innocent user) attaches to a `DeterministicStateInitAction` referencing a currently-nonexistent `GlobalContractIdentifier::AccountId` is burned from the account's effective balance without appearing in `tokens_burnt`, violating total-supply conservation (an "Accounting/state consistency" class bug per NEAR's bounty categories, potentially fund loss). Note this is a *loss* to the depositor rather than a discount/inflation for the attacker, so its primary bounty relevance is "balance/supply accounting violation," not "free execution."

### Likelihood Explanation
Trivially reachable by any unprivileged account: submit a `DeterministicStateInitAction` with `state_init.code() = GlobalContractIdentifier::AccountId(some_never_published_or_deleted_account)` and a non-zero `action.deposit`. No special privileges, no need to control the global-contract registry beyond simply not deploying (or having deleted) the referenced global contract. Fully repeatable each time with a fresh deterministic account id (varying `data`/`code`).

### Recommendation
In `action_deterministic_state_init` (`runtime/runtime/src/deterministic_account_id.rs`), before the early `return Ok(())` when `result.result.is_err()`, always push a `Receipt::new_balance_refund(receipt.balance_refund_receiver(), action.deposit)` (or equivalent) so that the deposit is unconditionally either credited/refunded or explicitly recorded, matching the pattern already used in the success path. Add an invariant check/test asserting the sum of `tokens_burnt` + refunded amounts across all outcomes of a `DeterministicStateInitAction` (success or failure) equals the originally attached deposit.

### Proof of Concept
Integration test (extend `test-loop-tests/src/tests/deterministic_account_id.rs`):
1. Do NOT deploy any global contract (or deploy then delete it if deletion is supported).
2. Construct a `DeterministicStateInitAction` with `state_init.code() = GlobalContractIdentifier::AccountId(nonexistent_id)`, a non-empty `data` map, and `action.deposit = N` (N > 0).
3. Submit the transaction from a funded account; observe the outcome status is `ActionErrorKind::GlobalContractDoesNotExist`.
4. Assert:
   - `account_state.storage_usage` unchanged (expected to already hold — sanity check).
   - `account_state.amount` for the deterministic account did **not** increase by `N`.
   - No refund receipt for `N` was generated to `balance_refund_receiver()`.
   - `receipt_execution_outcome.outcome.tokens_burnt` does not account for `N` either.
   - Compute total balance before/after (sender balance + all account balances + tokens_burnt across the chain) and show it decreased by `N`, violating conservation.
