### Title
Unswept leftover swap-input dust in `ExternalActionSwap`/`LifiExternalAction` can be stolen by a later swap via unlimited router allowance - (File: `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`LifiExternalAction.callRouter()` grants the LI.FI router an **unlimited** ERC-20 allowance and then forwards a fully off-chain-crafted, unvalidated calldata blob to it. Just like the Juicebox `JBXBuybackDelegate` bug (where a partially-filled Uniswap swap leaves unused ETH permanently stuck in the delegate because the callback only forwards exactly what the pool consumed), a partially-filled or under-specified router swap in Hinkal leaves unspent `inputToken` dust sitting in the `ExternalActionSwap` contract. Unlike the Juicebox contract, however, this dust is not simply frozen — because the router keeps an **infinite approval** over the contract's whole balance, any *subsequent* prover can craft router calldata that pulls the previous depositor's leftover dust together with their own funds, and claim the resulting extra output entirely as their own UTXO.

### Finding Description
In `swap()` (`contracts/external-actions/swaps/ExternalActionSwap.sol:40-102`), `inputAmount` is derived only from the caller's own `deltaAmounts[0]` and handed to `callRouter()`: [1](#0-0) 

`LifiExternalAction.callRouter()` then unconditionally grants unlimited allowance and executes the caller-supplied `externalActionMetadata` against the router: [2](#0-1) 

`swappedAmount` is computed purely from the **output**-token balance delta (`getERC20OrETHBalance(outputToken) - balanceBefore`); there is no check that the router consumed exactly `inputAmount` of the **input** token. If a router call only partially fills the requested trade (low liquidity / manipulated pool / attacker-crafted `externalActionMetadata` with a smaller `amountIn` than what Hinkal transferred), the unconsumed `inputToken` remains in the `ExternalActionSwap`/`LifiExternalAction` contract balance — it is never returned to the depositor and never recorded as any UTXO.

Because `approveUnlimited(inputToken, router)` is called on every swap (infinite allowance, not scoped to `inputAmount`), the router retains a standing unlimited allowance over the *entire* contract balance of that token, not just the amount belonging to the current transaction. A later transaction (any prover, including an attacker) using the same `inputToken` can supply `externalActionMetadata` whose embedded `amountIn` parameter requests more than the `inputAmount` Hinkal transferred for that call — the router will happily pull the extra amount from the contract's pre-existing (dust) balance via the unlimited allowance. The resulting `swappedAmount` (and hence `amountToSendToHinkal` and the new UTXO minted for the attacker) is inflated by value that was never contributed by the attacker and was never accounted for in any prior balance equation: [3](#0-2) 

Hinkal's own top-level balance equation in `transact()` only checks that Hinkal's own balance delta equals the externally-provided `amountChanges[i]`/UTXO sum for that transaction — it has no visibility into, or check against, dust sitting inside the external action contract: [4](#0-3) 

So the leftover value of an earlier depositor (never wrapped into any UTXO, hence unrecoverable by them) can be silently appropriated by a later caller's UTXO, without breaking any of the on-chain equality checks that Hinkal enforces.

### Impact Explanation
This is theft of shielded/in-flight user funds: value belonging to one user (the unspent portion of their swap input, analogous to the locked ETH in the Juicebox report) is captured by a different user's UTXO, meeting the Critical bar ("direct theft of shielded or in-flight user funds ... minting shielded value without backing"). The value minted into the attacker's UTXO is not backed by their own contributed balance-equation delta.

### Likelihood Explanation
Requires (1) some transaction leaving unswept input-token dust in `ExternalActionSwap`/`LifiExternalAction` (plausible given `externalActionMetadata` is off-chain router calldata subject to slippage/partial-fill/low-liquidity, exactly the class of trigger in the cited report), and (2) a subsequent caller supplying router calldata that requests more than their own `inputAmount`. Both conditions are within reach of any unprivileged prover/relayer since `externalActionMetadata` and `deltaAmounts` are attacker-controlled inputs to `runAction`, and the router allowance is unconditionally unlimited and never revoked or scoped per-transaction.

### Recommendation
- Scope the router approval to exactly `inputAmount` per call instead of `approveUnlimited`, and reset/reduce allowance after the swap.
- Track and enforce that the router consumes exactly (or at most) `inputAmount` of `inputToken` (compare input-token balance before/after, not just output-token balance), reverting or refunding any unconsumed dust to the depositor's UTXO instead of leaving it as a shared, unaccounted contract balance.
- Never let a caller's `externalActionMetadata` reference the contract's pre-existing token balance implicitly through infinite allowances.

### Proof of Concept
1. Prover A calls `transact()` with `externalActionId` for LI.FI swap, `erc20TokenAddresses[0] = TokenX`, contributing `amountIn_A`. The off-chain-built `externalActionMetadata` targets a low-liquidity route that only partially fills, so the router only pulls `amountIn_A - dust` of `TokenX` (using the unlimited allowance granted in `approveUnlimited`), leaving `dust` of `TokenX` sitting in `LifiExternalAction`'s balance. `swappedAmount` is measured only via output-token delta, so this passes the swap function's own accounting and Hinkal's top-level balance check for A's transaction.
2. Prover B (attacker) calls `transact()` for the same swap action with `erc20TokenAddresses[0] = TokenX`, contributing only `amountIn_B` via `deltaAmounts[0]`, but crafts `externalActionMetadata` whose embedded `amountIn` parameter equals `amountIn_B + dust`. Since `LifiExternalAction` already holds an unlimited allowance for the router over its `TokenX` balance (from step 1's `approveUnlimited` call), and the contract's actual `TokenX` balance is `amountIn_B + dust` (B's own transfer plus A's leftover dust), the router successfully pulls the full `amountIn_B + dust`.
3. `swappedAmount` is computed from the output-token balance delta, which now reflects a swap of `amountIn_B + dust`, larger than what B contributed. `amountToSendToHinkal` and the resulting UTXO minted for B in `ExternalActionSwap.swap()` (`contracts/external-actions/swaps/ExternalActionSwap.sol:93-101`) are inflated by the value of A's stranded dust, while Hinkal's own balance-equation check for B's transaction (`contracts/Hinkal.sol:134-146`) passes because it only compares Hinkal's own balance delta to B's declared `amountChanges`/UTXO — it never sees or restricts what happened inside the external action contract.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
