### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity solely from the unauthenticated `shopify-shop-domain` HTTP header, while the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies is computed only over the raw request body. This breaks the intended binding: `shop authenticated == shop used as the tenant identity`. An attacker who can obtain any one valid `(body, hmac)` pair signed with the app's secret can replay it to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header, and the request will still pass HMAC validation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is part of `@headers`, not `@raw_body`: [2](#0-1) 

`Registry.process` validates the webhook using `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (body only) and compares against `verifiable_query.hmac`. It performs no validation of the `shop`, `topic`, `webhook_id`, or `api_version` headers before invoking the handler with `request.shop`: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirms the signature is computed only from `verifiable_query.to_signable_string`, i.e. the body: [4](#0-3) 

Contrast this with the OAuth callback's `AuthQuery`, where `shop` **is** included inside `to_signable_string` and therefore is covered by the HMAC: [5](#0-4) 

Because the webhook `shop` header sits outside the signed material, any party who can produce (or capture) one valid `(raw_body, hmac)` pair — for example, by installing the app on their own store and receiving a legitimate webhook for that store — can resend that exact body/hmac pair to the app's public webhook endpoint with the `shopify-shop-domain` header changed to a different, victim shop. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` object whose `shop` field is the attacker-chosen value while `body`/`topic`/`webhook_id` come from the original signed payload: [6](#0-5) 

Any host application that uses `data.shop` as the tenant/session key to look up store-specific state (which is exactly the documented/expected usage per `docs/usage/webhooks.md` and the `shopify_app` reference pattern) will process the forged event as if it belongs to the victim shop, since the gem itself provides no cross-check between the signed body and the claimed shop.

### Impact Explanation
This crosses a tenant boundary: an attacker who legitimately controls one shop (e.g., a free/dev store where they install the target app) can cause the app to attribute webhook data/events to an arbitrary victim `shop-domain` of their choosing, because the identity field (`shop`) used to key the tenant lookup is never covered by the cryptographic proof (HMAC) the gem relies on for authentication. This matches the "Critical - cross-tenant access" impact bucket, since it defeats the tenant isolation the HMAC check is supposed to provide.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that: (1) accepts webhooks from multiple shops, and (2) allows an attacker to install the app on a shop they control (common for public apps in the Shopify App Store, or free dev-store signups) — this only requires the attacker to be an "unprivileged internet user," no leaked secret, TLS interception, or privileged account is needed. The attacker never needs `api_secret_key`; they only need to observe/replay one webhook body+HMAC that Shopify itself validly signed for their own store.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the material that is HMAC-verified, or independently authenticate the `shop` header against session/tenant records before trusting it downstream. At minimum, `Request#to_signable_string` should incorporate the shop domain so `HmacValidator.validate` binds the verified signature to the claimed tenant, closing the gap between "hmac authenticated" and "shop used as session/tenant key."

### Proof of Concept
1. Attacker signs up for a free trial/dev store `attacker.myshopify.com` and installs the target app so it subscribes to webhooks.
2. Shopify sends a legitimate webhook to the app's callback endpoint: body `B`, headers include `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `api_secret_key`) and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this `(B, H)` pair (they own the store; no TLS interception needed — e.g., they can trigger and observe it via their own dev tooling, or simply reuse a webhook they legitimately caused).
4. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `B` only and compares to `H` — validation succeeds because `H` was indeed the valid signature of `B`.
6. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: B, ...)`, causing the host app to associate the attacker-controlled body/event with the victim shop's tenant record. [3](#0-2) [7](#0-6)

            result

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
