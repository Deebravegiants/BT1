## Finding

### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the signable content for HMAC verification from the raw request body only, while the shop-identifying header (`x-shopify-shop-domain`), topic, and webhook id are taken verbatim from unauthenticated HTTP headers and forwarded to the application's webhook handler as if they were verified. Because the HMAC binds only the body bytes and not the tenant identifier, a party in possession of one legitimately-signed webhook body/HMAC pair for their own shop can replay it with a different `shop-domain` header and have the host application process it under another tenant's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over that signable string: [2](#0-1) 

`Registry.process` accepts the request once the body HMAC validates, and then dispatches to the handler using `request.shop`, `request.topic`, and `request.webhook_id` — all read straight from headers with no cryptographic binding to the body that was actually verified: [3](#0-2) 

and those header accessors are plain pass-throughs with no validation: [4](#0-3) 

The identity binding that should hold is:
`shop_attributed_to_handler == shop_that_the_signature_actually_authenticates`

Because the signature authenticates only the body bytes, the equality never actually holds — `shop` is fully attacker/network-controlled independent of the signature check. Since Shopify webhook HMACs are computed with the app-wide `api_secret_key` (shared across every shop that installs the app, not a per-shop secret), any merchant who installs the app receives real, validly-signed webhook deliveries for their own shop. That merchant can capture one such `(raw_body, hmac)` pair and re-POST it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop that also uses the app. `Utils::HmacValidator.validate` will still succeed (it only checks the body/HMAC pair), and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the victim's domain and attacker-controlled `body`.

### Impact Explanation
This breaks the cross-tenant boundary that `shop` is supposed to enforce: the webhook handler is a merchant-provided callback that uses `WebhookMetadata#shop` to determine which tenant's data to update, delete, or otherwise act on (e.g., `app/uninstalled`, `shop/redact`, order/customer webhooks). An attacker who is a legitimate (even free-tier) install of the app can forge webhook deliveries attributed to any other shop that has installed the same app, without needing the app's `client_secret`, an access token, or any privileged credential — only the ability to install the app once and observe one webhook. This is a cross-tenant confusion vulnerability (Critical, per the rubric's "cross-tenant access" category), since the shop-scoping guarantee the gem is meant to provide (`HmacValidator.validate` + `request.shop`) is not actually enforced together.

### Likelihood Explanation
Likelihood is high for any app that (a) allows self-serve/public installation (so an attacker can become a legitimate merchant on the same app) and (b) has webhook handlers that trust `WebhookMetadata#shop` for tenant-scoped side effects, which is the standard integration pattern documented for this gem (`Registry.add_registration` + `handler.handle(data: WebhookMetadata...)`). No secret material is required beyond a normal shop install; the attacker only needs to capture one real webhook body+signature pair for their own shop and replay it with a modified header.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content that is HMAC-verified, or otherwise cryptographically bind them to the verified body (e.g., verify shop/topic against Shopify via a secondary authenticated lookup) before constructing `WebhookMetadata` in `Registry.process`. At minimum, document prominently that `request.shop`/`topic`/`webhook_id` are NOT authenticated by `Utils::HmacValidator.validate` and must not be trusted for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (a fully self-service, unprivileged action).
2. Shopify sends the attacker a legitimate webhook, e.g.:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body B, computed by Shopify with the app's api_secret_key>
   x-shopify-shop-domain: attacker.myshopify.com
   Body: B
   ```
3. Attacker captures `(B, valid HMAC)` and replays it to the same endpoint with the header changed:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: B   (unchanged)
   ```
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb#L26-L31`) succeeds because it only checks `B` against the HMAC.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb#L188-L200`) invokes the merchant's handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the application to process attacker-controlled webhook content as if it originated from the victim tenant.
