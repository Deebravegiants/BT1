### Title
Webhook `shop` attribution is not covered by the HMAC, allowing cross-tenant shop spoofing on replayed webhook payloads - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value that is handed to the app's handler is read from an HTTP header that is never included in the signed content. This breaks the intended binding `HMAC(shared_secret, raw_body) == valid ⇒ shop == request.shop`; in reality the HMAC only proves `raw_body` integrity, not which shop the payload belongs to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e. the body only) and secure-compares it to the `hmac` header: [2](#0-1) 

`Registry.process` uses this same HMAC check to authorize the request, then constructs `WebhookMetadata` (which is passed to the app's handler as the trusted shop identity) using `request.shop`, a plain header value (`shopify-shop-domain` / `x-shopify-shop-domain`) that was never part of the signed bytes: [3](#0-2) [4](#0-3) 

By contrast, the equivalent OAuth callback flow (`AuthQuery`) deliberately includes `shop` inside `to_signable_string`, so the shop identity there *is* cryptographically bound to the HMAC: [5](#0-4) 

This is the same bug class as the external report: an unchecked computation trusts an input whose range/authenticity was never validated against the guard that is supposed to protect it — here, `request.shop` is trusted for tenant attribution despite being outside the scope of the HMAC that is supposed to authenticate the whole request.

Because the app's API secret (`Context.api_secret_key`) is shared across every shop that installs the app, any tenant who receives a legitimate webhook for their own shop can capture the exact `raw_body` + valid `hmac` pair and resend it to the app's webhook endpoint with a modified `shopify-shop-domain` (or `x-shopify-shop-domain`) header pointing at a different shop. `Utils::HmacValidator.validate` will still return `true` (it only checks `raw_body` against the secret), so `Registry.process` will accept the request and pass `WebhookMetadata.new(shop: <attacker-chosen shop>, body: <victim's original payload>, ...)` to the app's handler.

### Impact Explanation
If the consuming application uses `WebhookMetadata#shop` (as documented/intended) to determine which tenant's records to create/update/delete from the webhook `body`, an attacker can inject or misattribute another shop's webhook data into an arbitrary target shop's tenant space — a cross-tenant data-integrity/confusion issue. This matches the "Critical - cross-tenant access" impact category, since the gem's own authentication primitive (`HmacValidator`) is what silently permits the shop field to be forged without failing validation.

### Likelihood Explanation
Exploitability requires only: (1) being (or having briefly installed) the app on any one shop to legitimately receive one authentic webhook with a valid HMAC, and (2) the ability to POST an HTTP request to the app's public webhook endpoint with modified headers — both are unprivileged-internet-user actions requiring no access token, no `api_secret_key`, and no interception of TLS. The library provides no built-in binding between the HMAC and the shop-domain header, so any host application that follows the documented usage (`Registry.process`) inherits this gap without any misuse on its part.

### Recommendation
Include the shop-identifying data inside the HMAC-signed content, or otherwise cryptographically bind `shop` to the payload before trusting it, e.g.:
- Compute the webhook HMAC over `shop-domain + raw_body` (or a canonical string containing both), analogous to what `AuthQuery#to_signable_string` already does for OAuth callbacks, and update `Webhooks::Request#to_signable_string` accordingly, or
- Have `Registry.process` refuse to trust `request.shop` unless the app has independently verified that shop is one that actually installed the app (e.g., cross-checked against stored sessions) rather than deriving the WebhookMetadata shop solely from an unauthenticated header value.

### Proof of Concept
1. App receives a genuine Shopify webhook for `victim-shop.myshopify.com`:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of raw_body using api_secret_key>
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: {"id": 123, "sensitive": "data"}
   ```
2. Attacker (who can observe this webhook, e.g. via their own installed app instance or a shared logging/proxy layer they control) captures `raw_body` and the exact `X-Shopify-Hmac-Sha256` value.
3. Attacker resends the identical body and HMAC to the app's webhook endpoint but swaps the domain header:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <same HMAC as step 1, still valid>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id": 123, "sensitive": "data"}
   ```
4. `Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. `Registry.process` proceeds and invokes the app's handler with `WebhookMetadata.new(shop: "attacker-shop.myshopify.com", body: <victim's data>, ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the victim's order data to be processed under the attacker's shop identity.

Note: I could not find a per-shop webhook secret or any additional binding mechanism elsewhere in `lib/shopify_api/**` (searches for HMAC/session/shop-binding code turned up only the files cited above), so this gap appears to be root-caused entirely in `Webhooks::Request`/`HmacValidator`/`Registry` as shown.
