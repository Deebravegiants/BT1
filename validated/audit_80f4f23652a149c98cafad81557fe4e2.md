### Title
Webhook `shop` identity is derived from an HMAC-unsigned header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only [1](#0-0) , while the `shop` identity used downstream is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in that signed string [2](#0-1) . `Registry.process` verifies only that the body's HMAC matches, then passes the unauthenticated `request.shop` straight to the app's webhook handler as trusted tenant identity [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop field verified by HMAC == shop field delivered to the handler`. Here it does not — `to_signable_string` only returns `@raw_body` [1](#0-0) , so `HmacValidator.validate` only proves that the *body* bytes were signed with the app's `client_secret`; it proves nothing about which shop header accompanied them [4](#0-3) .

Because a webhook `client_secret` is per-app (shared across every shop that installs the app), any merchant who installs the app receives real, validly-signed webhooks for their own shop. An attacker-merchant can capture one such legitimate `(raw_body, hmac)` pair, then replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Request#initialize` only checks that the required header *names* are present, not that their values are bound to the signature [5](#0-4) . `HmacValidator.validate` still passes because the body is unchanged, and `Registry.process` forwards `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` to the handler with the attacker-chosen shop [6](#0-5) .

### Impact Explanation
Any app built on this gem that trusts `WebhookMetadata#shop` to select which merchant's session/access token/database row a webhook payload applies to (the intended and documented usage pattern) can be tricked into applying attacker-controlled webhook body content to a different, victim tenant's records. This is a cross-tenant integrity/confidentiality violation: the attacker's own (or fabricated) order/customer/app data gets attributed and processed under the victim shop's identity, potentially triggering shop-scoped side effects (e.g., data updates, downstream Admin API calls using the victim's stored access token) without any interaction from the victim.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the app on their own store (a normal, unprivileged merchant action) to obtain one legitimately signed webhook, and then send an HTTP POST to the app's public webhook endpoint with a forged shop-domain header. No access token, `client_secret`, or victim interaction is needed — only observation of one's own legitimate webhook traffic, which is trivial.

### Recommendation
Bind the shop (and ideally topic/api-version) into the signed material, or otherwise authenticate the header value against the signature rather than trusting it verbatim. At minimum, `Registry.process`/`Request` should require the caller to supply the shop domain from a source that Shopify's HMAC actually covers, or the gem should document explicitly that `request.shop` is unauthenticated and must never be used as the sole tenant selector.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets it receive a legitimate webhook, e.g. `orders/create`, capturing `raw_body` and header `x-shopify-hmac-sha256: <hmac>` (both valid, since `HmacValidator.validate_signature` only signs `raw_body` with the shared `client_secret` [4](#0-3) ).
2. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Request#initialize` accepts the request (all required headers present) [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which returns `true` because the body/hmac pair is unchanged [7](#0-6) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled `body`, and processes it as if it legitimately originated from the victim shop [6](#0-5) .
