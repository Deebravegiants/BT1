### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by checking only the HMAC over the raw request body, but the `shop` identifier that is subsequently handed to the app's `WebhookHandler` is read from an unauthenticated HTTP header. This breaks the identity binding `HMAC-verified bytes == data acted upon`, analogous to the `WstEth` report's pattern of "a value used for a critical decision is not the value that was actually verified."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e. the raw body) and compares it to the `hmac` header: [2](#0-1) 

`Registry.process` gates on this HMAC check, then immediately builds a `WebhookMetadata` object using `request.shop`, which is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header — a field that was never part of the signed bytes: [3](#0-2) [4](#0-3) 

The equality that should hold is:
`shop authenticated by HMAC == shop used to build WebhookMetadata.shop`

In this implementation that equality does not hold: the HMAC only authenticates `(body, api_secret_key)`. The `shop`, `topic`, `webhook_id`, and `api_version` fields are all taken from headers with zero cryptographic binding to the signature, exactly like the `WstEth` bug where `ethPerDerivative` returned a value that didn't reflect what was actually verified/exchanged.

Since the app's `api_secret_key` is shared across every shop that installs the app, this is not merely a "trust the sender" problem — it is a genuine tenant-confusion vector for any multi-tenant Shopify app. A user who legitimately installs the app on their own shop will receive genuine webhooks from Shopify for their shop, each with a valid HMAC over that specific body and their own `shop-domain` header. Because the HMAC computation is body-only, that same `(body, hmac)` pair remains valid if the `shop-domain` header is swapped for an arbitrary different shop domain string before resending it to the app's webhook endpoint. The `WebhookHandler#handle` implementation receives a `WebhookMetadata` whose `.shop` is attacker-controlled while `HmacValidator.validate` still returns `true`.

### Impact Explanation
This matches the Critical bucket: cross-tenant access. A host application that uses `WebhookMetadata.shop` (the officially provided, gem-validated field) to decide which merchant's session/data/state to update — the documented and expected usage pattern — can be made to apply a webhook payload under the identity of a shop the attacker does not own, since the gem never binds the shop header to the cryptographic proof. This is not "the host app ignoring documented behavior"; the gem's own `Registry.process` performs the authentication step and hands out `request.shop` as if it were authenticated data, with no signal to the caller that `shop` is unauthenticated relative to the HMAC check that was just performed.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must possess at least one genuine, validly-signed webhook body for the same `api_secret_key` (e.g., by owning/operating any shop that has installed the target app). No access to `api_secret_key`, access tokens, or other privileged secrets is required — only a legitimately obtained webhook delivery for their own tenant, which is available to any unprivileged merchant/developer who installs the app. This satisfies the "unprivileged internet user" analog boundary from the rules.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed material that `to_signable_string` returns, or otherwise cryptographically bind the shop identity to the payload before it is exposed via `WebhookMetadata`. At minimum, document explicitly that `WebhookMetadata.shop` is unauthenticated header data and must be independently reconciled by the host application (e.g., cross-checked against a known/installed shop list) before being trusted for tenant-scoped operations.

### Proof of Concept
```ruby
# Attacker owns/operates "attacker-shop.myshopify.com", which has installed the target app.
# Shopify delivers a genuine, validly-signed webhook to the app's endpoint:
body = '{"id":123,"note":"legit payload for attacker-shop"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_secret, body)

headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com", # legitimately theirs
}

# Attacker resends the exact same body+hmac, only swapping the shop-domain header:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

# HMAC validation still passes because it never covered shop-domain:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# The handler receives data.shop == "victim-shop.myshopify.com"
ShopifyAPI::Webhooks::Registry.process(request)
```
`HmacValidator.validate` at [5](#0-4)  returns `true` for the forged request because it never inspects `request.shop`, yet `Registry.process` passes `request.shop` (now `"victim-shop.myshopify.com"`) straight into `WebhookMetadata` at [6](#0-5) , which the app's `WebhookHandler#handle` will treat as authenticated tenant identity per [7](#0-6) .
