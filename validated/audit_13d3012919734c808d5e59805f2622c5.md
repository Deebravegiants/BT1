### Title
`begin_auth` builds the OAuth `authorize` redirect from an unsanitized `shop` value, allowing userinfo-style host confusion (open redirect) - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` interpolates the caller-supplied `shop` string directly into `auth_base_uri` (`"https://#{shop}/admin"`) with no host validation, whereas the library's own `Utils::ShopValidator.sanitize!` explicitly rejects any shop value containing `@`. This means a `shop` value like `real-shop.myshopify.com@attacker.example.com` produces an authorize URL whose actual host (per URL userinfo semantics) is `attacker.example.com`, redirecting the merchant's browser away from Shopify.

### Finding Description
The broken binding: `host_the_browser_will_connect_to(auth_base_uri(shop))` should equal `host_ShopValidator_would_accept(shop)`. Tracing the code:

- `begin_auth` ( [1](#0-0) ) takes `shop:` as a plain `String` with no call into `Utils::ShopValidator` anywhere in the method.
- `auth_base_uri` ( [2](#0-1) ) does `"https://#{shop}/admin"` unless the shop is a special local dev-server host — no `@` check, no domain allow-list check.
- Contrast with `Utils::ShopValidator#uri_from_shop_domain`, which explicitly guards `return nil if name.include?("@")` ( [3](#0-2) ), and `sanitize!` raises `Errors::InvalidShopError` when validation fails ( [4](#0-3) ).
- Other OAuth-adjacent flows in this same gem do call `ShopValidator.sanitize!` before using `shop` in a request (e.g. `TokenExchange.migrate_to_expiring_token`, [5](#0-4) ), confirming the guard exists in the library and is simply not applied to `begin_auth`.
- The library's own documented usage pattern feeds an unsanitized header value straight into `begin_auth` (`shop = request.headers["Shop"]` → `Oauth.begin_auth(shop: domain, ...)`), with no sanitization step shown, reinforcing that `begin_auth` is trusted (incorrectly) to be safe for raw attacker-controlled input.

Given `shop = "real-shop.myshopify.com@attacker.example.com"`, `auth_route` becomes `"https://real-shop.myshopify.com@attacker.example.com/admin/oauth/authorize?client_id=...&state=...&..."`. Per RFC 3986 / browser URL parsing, everything before `@` is userinfo and is discarded for host resolution — the browser connects to `attacker.example.com`, not `real-shop.myshopify.com`. The `redirect_uri` query parameter itself is built from `ShopifyAPI::Context.host` (the app's own configured host, not attacker-controlled), so the OAuth authorization code, once/if produced, is still delivered back to the legitimate app's callback route rather than to the attacker directly.

None of the existing guards intercept this: `Context.setup?`/`private?` checks are unrelated to shop-host validation, and `HmacValidator`, `state` comparison, and `JwtPayload` checks only apply in `validate_auth_callback`, which runs later and on a different code path — they never see or validate the `shop` string used to build `auth_base_uri`.

### Impact Explanation
What is exposed: the merchant's browser is redirected, from a request the merchant made to the legitimate app, to a fully attacker-chosen host, carrying the app's public `client_id`, requested `scope`, and a one-time `state` nonce in the query string. None of these values are secret credentials (`client_id` is public, `state` only matters when compared server-side against the app's own session cookie at the real callback), and the `redirect_uri` the eventual authorization code would be sent to remains the legitimate app's own domain (from `Context.host`), not attacker-controlled. Consequently, this does not by itself hand the attacker a Shopify access token, refresh token, authorization code, or `client_secret` — the stronger "token/code theft" outcome described in the question requires the attacker to also stand up infrastructure that transparently proxies Shopify's real authorize page (a MITM-style reverse proxy) and depends on the merchant proceeding through that page, which goes beyond a pure code-path bug and shades into phishing/social-engineering territory that is explicitly out of scope for this audit. The concrete, code-level impact that is unambiguously demonstrable is an **open redirect at the OAuth-begin step**, repeatable against any victim shop/app pairing where the host application passes an unsanitized `shop` value into `begin_auth` (as the library's own documentation example does).

### Likelihood Explanation
Attacker cost is low: no credentials, secrets, or privileged access are required — only the ability to get a victim (or the victim's browser, e.g. via a crafted link) to hit the host app's own OAuth-start route with a manipulated `shop` parameter. This is entirely feasible if the host application follows the gem's documented pattern of forwarding a raw shop value from the request into `begin_auth` without independently calling `ShopValidator.sanitize!` first. It is repeatable against any shop/app combination.

### Recommendation
Have `Oauth.begin_auth` validate/normalize `shop` via `Utils::ShopValidator.sanitize!` (as `TokenExchange.migrate_to_expiring_token`, `ClientCredentials`, and `RefreshToken` already do) before constructing `auth_base_uri`, raising `Errors::InvalidShopError` for any shop string containing `@` or otherwise failing the trusted-domain check.

### Proof of Concept
```ruby
# test/auth/oauth_userinfo_test.rb
require "test_helper"

class OauthUserinfoRedirectTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(
      api_key: "test_key",
      api_secret_key: "test_secret",
      host_name: "app.example.com",
      scope: ["read_products"],
      is_private: false,
      is_embedded: false,
      api_version: "unstable",
    )
  end

  def test_begin_auth_does_not_reject_userinfo_shop
    malicious_shop = "real-shop.myshopify.com@attacker.example.com"

    result = ShopifyAPI::Auth::Oauth.begin_auth(shop: malicious_shop, redirect_path: "/cb")

    # Demonstrates the browser-resolved host diverges from the shop the
    # library would otherwise consider trusted.
    parsed_host = URI.parse(result[:auth_route].sub("real-shop.myshopify.com@", "")).host
    assert_equal "attacker.example.com", parsed_host

    # Contrast: ShopValidator, used elsewhere in this gem, rejects the same input.
    assert_raises(ShopifyAPI::Errors::InvalidShopError) do
      ShopifyAPI::Utils::ShopValidator.sanitize!(malicious_shop)
    end
  end
end
```
Both assertions pass against current code, proving `begin_auth` produces a redirect URL without raising `InvalidShopError`, while `ShopValidator.sanitize!` correctly rejects the identical input elsewhere in the same gem.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
