### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header values are not covered by HMAC, allowing cross-tenant identity forgery on replayed webhook bodies - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes the HMAC purely over that signable string [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` values are pulled straight from HTTP headers with no cryptographic binding to the body or to each other [2](#0-1) . `Registry.process` accepts the request once the body HMAC checks out, then passes `request.shop` unchanged into the handler as the tenant identity [3](#0-2) .

### Finding Description
The equality the gem is implicitly claiming to guarantee is: `hmac_signed_content == (shop, topic, webhook_id, api_version, body)`. In reality it is only: `hmac_signed_content == body`. Because `api_secret_key` is a single app-wide secret shared across every shop that installs the app (not shop-specific), any unprivileged merchant who installs the app on their own store can trigger a legitimate webhook (e.g. `orders/create`) and capture a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's own secret. That attacker-controlled shop then replays the exact same body and HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain. Because none of those headers factor into the HMAC computation, `HmacValidator.validate` still passes, and `Registry.process` hands the handler a `WebhookMetadata` claiming the body originated from the victim shop [5](#0-4) .

### Impact Explanation
Any host application that uses `data.shop` from the `WebhookMetadata` to key per-tenant data (order records, inventory, customer records, redaction requests, etc.) can be made to process attacker-supplied body content under a different, victim shop's identity — a cross-tenant write/read primitive with no privileged access required beyond installing the app on any shop.

### Likelihood Explanation
Requires only: (1) the ability to install the app on an attacker-controlled shop (or otherwise trigger any legitimate webhook for it) to obtain a valid `(body, hmac)` pair, and (2) sending an HTTP request to the app's public webhook endpoint with forged headers. No access to `api_secret_key`, tokens, or victim credentials is needed.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the signable content used for HMAC verification (or otherwise cryptographically tie them to the signed body), so that replaying a valid body/HMAC pair with substituted headers is rejected.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; trigger `orders/create` to receive a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`).
2. Replay `POST /webhooks` with the same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `HmacValidator.validate` succeeds because it only checks `B` against `H` [6](#0-5) ; `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` [5](#0-4) , causing the host app to attribute attacker-controlled data to the victim tenant.
