### Title
Webhook `shop` (and `topic`) header is trusted for tenant attribution while only the raw body is HMAC-verified - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as the raw request body only, while the `shop` (and `topic`) values used to attribute and dispatch the webhook are read straight from unauthenticated HTTP headers. `Registry.process` verifies the HMAC and then unconditionally forwards the header-derived `shop` to the handler, so the "shop the payload is attributed to" is never covered by the same signature that authenticates the payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` and `topic` are pulled from HTTP headers that are not part of that signed string: [2](#0-1) 

`Registry.process` validates the HMAC over the body and, once it passes, builds the dispatched metadata directly from the request's header-derived `shop`, `topic`, `api_version`, and `webhook_id` — none of which participated in the HMAC computation: [3](#0-2) 

The identity binding that should hold is:
`HMAC_valid(body) == true` should imply `shop_header == shop_that_actually_produced_and_signed_this_body`.

In this implementation that equality is never checked. The `HmacValidator` only proves that whoever produced `raw_body` knew the app's `api_secret_key`/`old_api_secret_key` (i.e., that it is a genuine webhook from *some* installed shop of this app): [4](#0-3) 

It does not prove which shop that body belongs to, because `shop` is never mixed into the signed bytes.

### Impact Explanation
In any multi-tenant app (the typical deployment model this gem targets), the host application relies on `WebhookMetadata#shop` (built from `request.shop`) to decide which tenant's session/record the webhook payload should be applied to (e.g., look up shop-specific settings, update shop-scoped data, etc.). Because the HMAC never covers the `shop` header, a party who has installed the app on their own store (an ordinary, otherwise-unprivileged user of the app, not requiring `api_secret_key`) can capture one of their own genuine webhook deliveries — a valid `(raw_body, hmac)` pair, which is legitimate and passes validation regardless of the `shop-domain` header value — and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a different shop's domain. `Registry.process` will validate the HMAC (it only checks the body/secret), then dispatch the payload attributed to the victim shop. This yields cross-tenant data confusion/injection: the attacker's own data is written into or triggers actions for a different, unrelated tenant, without ever needing that tenant's or the app's `api_secret_key`.

### Likelihood Explanation
Exploitation requires only:
1. Being an installed customer of the target app (any shop can install a public app and receive real webhooks for their own store), and
2. The ability to POST to the app's publicly-reachable webhook endpoint with attacker-controlled headers (webhook endpoints are ordinary public HTTP endpoints, headers are fully attacker-controlled when replaying outside of Shopify's original delivery).

No credentials beyond normal app installation are needed, and the HMAC check passes unmodified because it never inspects the `shop` header. This makes the attack straightforward for any user with a shop already using the target app.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the HMAC-signed content, or otherwise cryptographically bind the header-derived shop identity to the verified body (e.g., verify webhook shop domain against a value embedded in/derived from the signed payload, or require the host application to cross-check `request.shop` against an expected/allow-listed shop before dispatch). At minimum, document/enforce that `Registry.process` must not be trusted to authenticate the `shop` attribution and that callers must independently verify shop identity before using webhook payload data in a tenant-scoped way.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a real webhook event (e.g., `orders/create`), causing Shopify to POST a legitimate `(raw_body, x-shopify-hmac-sha256, x-shopify-shop-domain: attacker-shop.myshopify.com)` to the app's webhook endpoint.
2. Attacker intercepts/records this `raw_body` and its valid `hmac` value (both are visible to the store owner receiving their own webhook, e.g. via app logs, browser devtools on ngrok tunnels used in development, or by controlling their own receiving infrastructure during setup).
3. Attacker sends a new POST request to the same webhook endpoint with the exact same `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` compute/verify HMAC solely from `raw_body`: [5](#0-4) 
   validation succeeds because it is the identical body/HMAC pair originally produced by Shopify.
5. `Registry.process` passes the HMAC check and dispatches `WebhookMetadata.new(shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"`, even though the body content actually originated from and describes `attacker-shop.myshopify.com`'s data: [6](#0-5) 
6. The host application's webhook handler processes the attacker's payload as if it belongs to `victim-shop`, achieving cross-tenant data injection/confusion.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
