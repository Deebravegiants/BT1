### Title
Emporium `runAction` skips all balance and signature checks when `tokenNumber=0`, allowing theft of protocol-held funds - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Finding Description
The claimed equality is: **AUTHORITY** — every `stack.ops[]` executed against Emporium's balance must be authorised either by (a) an EIP-712 signature from `stack.signerAddress`, or (b) a ZK proof binding `amountChanges`/nullifiers to the attacker's own deposited funds, enforced by the post-loop balance check in `runAction`.

`verifyWallet` skips the signature check entirely when `stack.signerAddress == address(0)` [1](#0-0) . In that mode, the only remaining guard is the post-execution balance-diff loop in `runAction`, which iterates `circomData.erc20TokenAddresses` and reverts with `BalanceChangeShouldBePositive` unless `balanceChange >= 0` after accounting for `deltaAmountChanges` [2](#0-1) .

`CircomDataBuilder.formInputForCircom` has a dedicated branch that produces a minimal public-input vector (`emporiumMessage`, `timeStamp`, `calldataHash` only — no `rootHashHinkal`, no nullifiers, no `amountChanges`) whenever `circomData.erc20TokenAddresses.length == 0` for the Emporium action [3](#0-2) . `Hinkal.transact` uses `dimensions.tokenNumber` (fully attacker-supplied calldata) both to select the verifier via `buildVerifierId` and to size all the token-indexed loops [4](#0-3) . When `tokenNumber=0`:

- `dimensionsCheck` only requires all the per-token arrays to have length 0, which is self-consistent and trivially satisfiable [5](#0-4) .
- The ZK proof carries **no nullifier, no root-hash, no amount constraint** at all (the `MainEVMCircuit` per-token loop that enforces `inTotal + amountChanges === outTotal`, nullifier validity and root-hash equality simply doesn't execute for `tokenCount=0`) [6](#0-5) . `rootHashExists` in `Hinkal.transact` still requires a valid historical root, but that root is not cryptographically tied to anything in this proof, so any historical root/index works.
- In `Hinkal._externalTransact`, `deltaAmountChanges` is sized to `erc20TokenAddresses.length` (0), so no deposit transfer into Emporium occurs before `runAction` is invoked [7](#0-6) .
- In `EmporiumUpgradeable.runAction`, `circomData.erc20TokenAddresses` is empty, so the balance-before/after diff loop that would normally catch a stolen balance never executes (zero iterations) [8](#0-7) .

Combined with `signerAddress = address(0)` skipping the signature check, `stack.ops` (fully attacker-crafted `externalActionMetadata`) execute unconditionally as `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium` [9](#0-8) . Nothing prevents `op.value`/`op.callData` from draining Emporium's own held ETH or calling an ERC20's `transfer`/`approve` where Emporium is the caller — no check ties any of this to the attacker's own deposit, and no post-check verifies Emporium's balance wasn't reduced, because the entire balance-verification loop is scoped to a zero-length array.

The attacker's exact call: submit `Hinkal.transact` with `dimensions.tokenNumber = nullifierAmount = outputAmount = 0`, `circomData.erc20TokenAddresses = []`, `circomData.externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and `externalActionMetadata` decoding to an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: <target>, value: <Emporium's balance>, callData: <drain call>}]}`, alongside a trivially-generated proof for the minimal 3-input circuit and any valid historical root/index.

### Impact Explanation
Any ETH or ERC20 tokens sitting in the Emporium contract's own balance (e.g., in-flight funds momentarily held between a deposit step and a subsequent stateful wallet op, dust from partial fills, or leftover fee balances via the contract's `receive()` function) can be moved to an attacker-chosen `endpoint`/recipient with zero signature and zero balance verification. This is unauthorised movement of protocol/in-flight user funds with no on-chain constraint tying the moved value to anything the attacker owns, matching Critical/High impact ("theft of shielded or in-flight user funds" / "executing calls or moving assets... a prover never authorised"). The exploit is repeatable every time Emporium holds a nonzero balance.

### Likelihood Explanation
Preconditions: (1) a verifier must be registered in `verifierMap` for `buildVerifierId(tokenNumber=0, nullifierAmount=0, outputAmount=0, EMPORIUM_ACTION_ID)` — the dedicated `formInputEmporiumMin` code path in `CircomDataBuilder` strongly indicates this minimal-proof flow is an intentionally supported feature, not dead code, so such a verifier is expected to be deployed for the Emporium action; (2) Emporium must hold a nonzero balance at attack time, which is a normal transient state of the contract's own design (it accepts ETH via `receive()` and holds deposited/withdrawn balances mid-flow). The attacker's cost is a single locally-generated proof for a near-trivial circuit plus gas — no deposit, no signature, and no privileged role are required, exactly matching the "unprivileged attacker" threat model.

### Recommendation
- Do not allow `tokenNumber == 0` (or any configuration bypassing the balance-verification loop) to be combined with `stack.signerAddress == address(0)` in `EmporiumUpgradeable.runAction`/`verifyWallet` — require a valid EIP-712 signature whenever the token-diff loop cannot itself bound the operations.
- Alternatively, make the Emporium balance-check independent of `circomData.erc20TokenAddresses.length` by tracking and asserting `address(this).balance` and all touched-token balances unconditionally (not scoped to a caller-controlled array that can be emptied).
- Ensure the minimal-input circuit path (`formInputEmporiumMin`) is only reachable when `stack.signerAddress != address(0)` is enforced on-chain, i.e., reject `tokenNumber == 0` unless a valid wallet signature is present.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register `EmporiumUpgradeable` as `externalActionMap[HINKAL_EMPORIUM_ACTION_ID]` and as an allowed recipient.
2. Fund `EmporiumUpgradeable` with, e.g., 10 ETH (simulating in-flight/leftover balance via its `receive()`).
3. Register (or use existing) a verifier for `buildVerifierId(0,0,0,HINKAL_EMPORIUM_ACTION_ID)`; locally generate a proof for the minimal 3-signal circuit with attacker-chosen `emporiumMessage`, `timeStamp`, `calldataHash`.
4. Build `EmporiumStack{signerAddress: address(0), ops: [{endpoint: address(maliciousReceiver), invokeWallet: false, value: 10 ether, callData: ""}]}`, encode as `externalActionMetadata`.
5. Call `Hinkal.transact(a,b,c, dimensions{tokenNumber:0,...}, circomData{erc20TokenAddresses: [], externalActionData: {...}, rootHashHinkal: <any valid root>, ...})`.
6. Assert: transaction succeeds (no revert), `EmporiumUpgradeable`'s ETH balance is now 0, `maliciousReceiver` balance increased by 10 ETH — i.e., LHS (funds moved) ≠ RHS (attacker's own authorised/deposited amount, which is 0), proving the equality is broken.
