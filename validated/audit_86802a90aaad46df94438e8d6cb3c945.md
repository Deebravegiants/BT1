### Title
NFT `Owner` entry TTL desync makes live accounts unreadable — withdrawals and liquidations fail with `AccountNotFound` while positions remain - (File: contracts/controller/src/storage/account.rs)

### Summary
The controller resolves account ownership by reading the position-NFT `Owner(token_id)` persistent entry on every account load. That entry is only lifted to the 120-day user window at mint and via the explicit `renew`/`renew_account` path, while the OZ `owner_of` read used by the controller only bumps it to a ~30-day window. Controller-side account entries (`AccountMeta`, position maps) are renewed to the full user window on every read. The result is a window where the NFT `Owner` entry has archived but the account's metadata and positions are still live: `try_account_owner` fails the lookup (a missing/null read), `get_account` collapses to `AccountNotFound`, and every entrypoint that loads the account — including `withdraw` and permissionless `liquidate`/`clean_bad_debt` — reverts until the archived entry is manually restored.

### Finding Description
The external report's bug class is a null/missing-value dereference (a pointer assumed non-null is dereferenced unconditionally). The analog in this codebase is the ownership dereference in `get_account`:

- `try_get_account` requires both `try_get_account_meta` and `try_account_owner`; a `None` from either aborts the whole account load (`contracts/controller/src/storage/account.rs:153-161`).
- `try_account_owner` returns `None` when `nft_try_owner_of_call` fails — which includes the `Owner(token_id)` persistent entry being archived, since an archived persistent read traps rather than returning a value (`account.rs:35-38`).
- Controller account entries get full user-window renewal on reads: `get_user`/`renew_user_key` renew `AccountMeta`, `SupplyPositions`, `BorrowPositions`, `Delegates` to `TTL_BUMP_USER` (`account.rs:259-272`, header comment "successful reads renew user TTL").
- The NFT side does not get the same treatment on reads. `extend_user_persistent_ttl` lifts `Owner`/`Balance` to `TTL_BUMP_USER` only inside `mint` and `renew`, and the code documents that "OZ `owner_of` extends `Owner` to only 30 days" while account renewal targets "the same 120-day window as the account entries" — and `renew_user_account` explicitly "does not renew the NFT" (`contracts/position-nft/src/contract.rs:30-46, 97-115`; `account.rs:258`).
- `renew(token_id)` cannot self-heal an archived entry either: it calls `Base::owner_of` first precisely because `extend_ttl` on a missing key traps, and `owner_of` itself traps on the archived entry before any extension happens (`contract.rs:109-115`).

Reachable path (all permissionless or owner-level, no privileged role): any caller invoking `Controller::withdraw`, `liquidate`, `clean_bad_debt`, `repay`, `borrow`, `update_account_threshold`, `flash_position`, or the strategy entrypoints against an account whose `Owner` entry is archived hits `get_account`/`get_account_borrow_only` → `account_owner` → `AccountNotFound` and reverts.

### Impact Explanation
Two qualifying impacts:

1. **Temporary freezing of user funds.** During the desync window (NFT `Owner` archived while `AccountMeta`/`SupplyPositions` still live), the account owner cannot `withdraw`, `repay`, `swap_collateral`, or `repay_debt_with_collateral` — every path loads the account via `get_account`. Funds stay frozen until someone restores the archived persistent entry with `restore_footprint`, which is a separate operator action outside the contract ABI.
2. **Blocked liquidations → insolvency risk.** `process_liquidation` calls `storage::get_account` (confirmed by `tests/test-harness/tests/controller/position_nft_ttl_and_ownership_reads.rs:281-307`, where burning the `Owner` leg makes a plain partial liquidation fail with `ACCOUNT_NOT_FOUND`). A borrower can hold an undercollateralized position that liquidators cannot touch during the archived window; the same applies to `clean_bad_debt`/`socialize_bad_debt`. Delayed liquidation on a deteriorating position converts directly into protocol bad debt borne by suppliers.

The failure is a direct analog of the CVE: an ownership record is assumed present (non-null), the dereference path offers no in-band recovery, and the consequence is denial of service on the affected object — here with real funds at stake rather than a local crash.

### Likelihood Explanation
No privileged action is required. TTL drift arises from ordinary usage: each account interaction bumps `AccountMeta` and the position maps to the full user window but only bumps the NFT `Owner` entry to the shorter OZ 30-day window via `owner_of`. An account that goes ~30+ days without an explicit `renew`/`renew_account` call but whose controller entries were touched more recently lands in the desync state. Any third party's subsequent read of the account reverts, so the condition is self-sustaining once entered: nothing on the read path can fix it, and `renew` itself traps on the archived entry. A motivated borrower can arrange this deliberately by keeping the NFT entry cold while maintaining recent controller-side entries, then waiting for adverse price movement to make the unliquidatable window profitable.

### Recommendation
Make the ownership dereference symmetric with account-entry TTL handling:

- Have the controller renew the NFT `Owner` entry (e.g., call `PositionNft::renew` or an equivalent `extend_ttl`) inside `renew_user_account` or inside `try_account_owner` whenever the lookup succeeds, so the owner record shares the 120-day user window with `AccountMeta`.
- In `PositionNft::renew`, attempt `extend_ttl`/`restore` semantics rather than unconditionally calling `owner_of` first, or document that archived entries require `restore_footprint` and expose that path.
- Alternatively, treat an unreadable `Owner` entry distinctly from a nonexistent account in `try_get_account` so reads that don't strictly need the owner (e.g., liquidation planning) can proceed.

### Proof of Concept
Sketch (mirroring `tests/test-harness/tests/controller/position_nft_ttl_and_ownership_reads.rs:285-308`):

```rust
let mut t = LendingTest::new().standard_two_asset().build();
t.supply(ALICE, "USDC", 10_000.0);
t.borrow(ALICE, "ETH", 3.0);
let id = t.account_id(ALICE);

// Keep account entries warm (renewed to TTL_BUMP_USER) while the NFT
// Owner(token_id) entry only receives the ~30-day OZ bump via owner_of.
// Advance ledger time past the 30-day owner window but inside the
// 120-day account window (e.g., env.ledger().set_sequence_number / timestamp jump).
// The persistent Owner entry is now archived; AccountMeta/SupplyPositions are live.

t.set_price("USDC", usd_cents(50));
assert!(t.account_exists(id));          // controller state still live
let res = t.try_liquidate(LIQUIDATOR, ALICE, "ETH", 1.0);
assert_contract_error(res, errors::ACCOUNT_NOT_FOUND);   // liquidation reverts

// Owner's own exit fails identically:
let w = vec![&t.env, (hub_asset(usdc), 0i128)];
// t.ctrl_client().withdraw(&alice, &id, &w, &None)  -> panics AccountNotFound
```

Key uncertainty I could not fully verify within the read scope: the exact TTL constants (`TTL_BUMP_USER`, `TTL_THRESHOLD_USER`, and the OZ `owner_of` internal window) and whether `renew_account`/`update_account_threshold` is invoked automatically on reads in a way that already lifts the `Owner` entry. If the NFT `Owner` entry is in fact renewed to the same window on every account read, the desync window closes and this reduces to a no-finding. Verification requires `common::constants` TTL values and the `nft_try_owner_of_call` wrapper in `contracts/controller/src/external/position_nft.rs`.
