Confirmed: the `HmacValidator` for webhooks signs only `to_signable_string` (the raw body), while `shop` comes from a separate header never included in that signable string.### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The Caviar `Factory.create` bug class is: an attacker-controllable field (`_salt`) determines a security-sensitive outcome (pool address / ownership) while the binding that should tie that field to the legitimate actor (the deployer's identity) is missing. The direct analog in this gem is `ShopifyAPI::Webhooks::Request`: the HMAC signature that `Registry.process` uses to decide "this webhook is authentic" is computed **only over the raw body**, while the `shop` identity attribute handed to the app's webhook handler is read from a header that is **never part of the signed bytes**. The equality that should hold — `hmac == HMAC(secret, body ++ shop)` — is actually only `hmac == HMAC(secret, body)`, so `shop` can be substituted freely without invalidating the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are read from separate, unauthenticated headers, independent of the signed string: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies the `to_signable_string` output (the body) against the received `hmac`: [3](#0-2) 

`Webhooks::Registry.process` treats a passing HMAC check as authorization to dispatch the request — including the unauthenticated `shop` value — straight to the app's handler: [4](#0-3) 

Because `hmac` binds only the body bytes, any (body, hmac) pair that was legitimately produced by Shopify for **one** shop remains a **valid** HMAC pair when replayed with a different `shopify-shop-domain` / `x-shopify-shop-domain` header value. `Registry.process` will accept it and hand the forged `shop` string to the host application's handler as if it were verified, since `process` is the gem's documented trust boundary ("validate then dispatch") — the host app is not expected to independently re-derive tenant identity once `Utils::HmacValidator.validate(request)` has passed.

### Impact Explanation
An unprivileged actor who legitimately installs the target app on their own store (a normal, unprivileged tenant) receives genuine (body, hmac) pairs for their own webhook events, signed with the app's real `client_secret`/`api_secret_key`. That attacker can replay the identical raw body and HMAC to the app's webhook endpoint while altering only the `shop-domain` header to name a victim shop. `Registry.process` will accept the request as authentic and dispatch `WebhookMetadata` with the attacker-chosen `shop` value to the handler, since `shop` was never part of the equality the HMAC verifies. Any host logic that trusts `data.shop` from a successfully-verified webhook (the documented, intended usage of this API) to select/act on a merchant's records is exposed to cross-tenant data confusion/attribution — e.g., an app could apply a webhook meant for the attacker's own store (e.g., `customers/redact`, `shop/redact`, order/product change data) against a different, victim tenant's records, or misattribute state changes across tenants.

### Likelihood Explanation
Exploitation requires no secrets, tokens, or privileged access — only the ability to (a) install the target app on any shop (a normal, low-privilege action any merchant can perform) and (b) capture and replay one of that shop's own inbound webhook HTTP requests with one header changed. No cryptographic material needs to be forged; the legitimate HMAC is reused verbatim. This is straightforward to automate and repeat for any topic the app subscribes to.

### Recommendation
Bind the tenant identity into the signed material used for webhook verification, mirroring the fix applied to the analog `Factory.create` issue (combine `_salt` with `msg.sender`). Concretely, in `ShopifyAPI::Webhooks::Request#to_signable_string`, include the `shop` (and ideally `topic`/`webhook_id`) header values alongside the raw body before validation, e.g.:

```ruby
sig { override.returns(String) }
def to_signable_string
  "#{shop}\n#{topic}\n#{@raw_body}"
end
```

and adjust `HmacValidator`/webhook verification accordingly (this requires a corresponding server-side signing change or, at minimum, clear documentation warning that `shop` is not authenticated by the HMAC so host apps must independently corroborate tenant identity, e.g. by checking that the shop has a stored, matching offline session, before trusting `WebhookMetadata#shop`).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g. `orders/create`).
2. Attacker triggers the event on their own shop and captures the raw HTTP request Shopify sends to the app's webhook endpoint, including headers `X-Shopify-Hmac-Sha256: <hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and the raw JSON body.
3. Attacker replays the exact same body and `X-Shopify-Hmac-Sha256` value to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. Server-side, `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — unaffected by the header change — and succeeds: [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the event actually originated from and describes `attacker-shop.myshopify.com`'s data.
