Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only that HMAC and then trusts `request.shop` for tenant attribution passed to the handler [3](#0-2) .

### Title
Webhook shop identity is not covered by HMAC verification, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw body only, but derives the `shop` (tenant) attribution from an HTTP header that is not included in the signed content. `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated `shop` value and passes it straight to the app's webhook handler.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it to the `hmac` value [4](#0-3) . For webhook requests, `to_signable_string` is defined to be exactly `@raw_body` [1](#0-0) . The `shop` accessor, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [5](#0-4) , which plays no part in the HMAC computation at all.

`Registry.process` only checks `Utils::HmacValidator.validate(request)` — i.e., that the body bytes match a signature computed with the app's `client_secret` — and then immediately builds `WebhookMetadata` using `request.shop` (the unverified header) as the tenant identity handed to the app's handler [3](#0-2) .

This breaks the intended binding: `shop-authenticated-by-HMAC == shop-used-for-tenant-attribution`. In reality, `bytes-verified (raw_body) != bytes/fields-used-for-identity (shop header)`.

An unprivileged internet user who has ever received one legitimate webhook from Shopify (e.g., because they have their own store with the app installed, or from any publicly triggerable webhook with predictable/reusable body content) has in hand a `(raw_body, hmac)` pair that is valid for the app's `client_secret` without ever needing to know that secret. Because the `shop-domain` header is not part of the signed content, that same `(raw_body, hmac)` pair remains valid no matter what value is placed in the `shop-domain` header. The attacker can therefore POST directly to the app's public webhook endpoint with the original valid body/HMAC but an arbitrary victim `shop-domain` (and arbitrary `topic`/`webhook-id`/`api-version` headers, which are equally unverified), causing the app to process attacker-supplied/replayed data as though it originated from a different, victim tenant.

### Impact Explanation
This is a cross-tenant identity confusion: data that Shopify never actually sent for the victim shop gets attributed to that shop by the app via the gem's own webhook processing API. Depending on how the host application acts on `WebhookMetadata#shop` (e.g., updating shop-scoped records, triggering `shop/redact`-style flows, or invalidating/toggling state keyed by shop), this can lead to state corruption or actions being taken against another merchant's tenant, without the attacker ever possessing that merchant's credentials. This matches the in-scope "cross-tenant access" impact category, since the gem's own webhook verification API is the root cause, not host misuse.

### Likelihood Explanation
Any unprivileged internet user can reach a public webhook HTTP endpoint (that's the endpoint's purpose). The only prerequisite is a single valid `(raw_body, hmac)` pair for the target app's `client_secret`, which is naturally obtainable by an attacker who installs/uses the app on their own store and captures a real webhook delivery, or by resending a previously observed webhook body they intercepted. No access token, `client_secret`, or privileged account is required — only the ability to record and replay a legitimately-signed body against arbitrary header values.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed content (or otherwise cryptographically bind them to the signature), rather than signing only `raw_body`. At minimum, `Registry.process` should validate `request.shop` against the session/shop the webhook is expected for, rather than trusting the header unconditionally.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook delivery with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-for-raw_body>`, and some `raw_body`.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint reusing the exact same `raw_body` and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC [6](#0-5) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` [7](#0-6) , causing the app to process forged data as belonging to `victim-shop.myshopify.com`.
