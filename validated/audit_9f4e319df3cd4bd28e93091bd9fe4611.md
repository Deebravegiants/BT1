### Title
Unrestricted arbitrary call in `EmporiumUpgradeable.runAction` lets any unprivileged prover drain tokens held by the shared Emporium contract outside the checked balance equation - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` decodes an `EmporiumStack` from the fully caller-controlled `circomData.externalActionData.externalActionMetadata` and, whenever `stack.signerAddress == address(0)` ("Stateless Interaction"), executes `op.endpoint.call{value: op.value}(op.callData)` for an attacker-chosen endpoint/value/callData with no signature check at all. The only post-call safety check reconciles balances solely for tokens listed in the same caller-supplied `circomData.erc20TokenAddresses` array, so any asset moved by the arbitrary call that is not in that array is invisible to the accounting equation.

### Finding Description
`runAction` is reachable by any unprivileged EOA through `Hinkal.transact` → `Hinkal._externalTransact` → `IExternalActionV2(externalAddress).runAction(...)`, where `externalAddress` is the registered Emporium contract, a single persistent contract shared by all users of the protocol: [1](#0-0) 

Inside Emporium, the "Stateless Interaction" branch performs the arbitrary call without any signature/authorization check when `stack.signerAddress == address(0)`: [2](#0-1) 

`verifyWallet` only enforces a signature check when `stack.signerAddress != address(0)`; for the stateless case it simply marks the message used and returns, imposing no constraint on `op.endpoint`/`op.callData`/`op.value`: [3](#0-2) 

The only solvency check after the call iterates exclusively over `circomData.erc20TokenAddresses`, an array that is also chosen by the same caller/prover: [4](#0-3) 

Although `circomData.externalActionData` (including `externalActionMetadata`) is bound into `calldataHash` and checked in `HinkalHelper.performHinkalChecks`, that only proves the caller chose this exact metadata - it does nothing to constrain which tokens the metadata's arbitrary call can touch relative to the declared `erc20TokenAddresses`: [5](#0-4) [6](#0-5) 

Emporium is a single, shared, long-lived contract (registered once via `registerExternalAction`) reused across all users' swap/emporium transactions, and the code explicitly anticipates it holding a residual balance across calls (comment: "the only case when balanceChange can be < 0, when there were some funds on emporium before the call"): [7](#0-6) 

Such residual balances accumulate naturally: relay fees (`payRelayFees`), rounding dust from `ExternalActionSwap.swap`'s `swappedAmount - totalFee`, or leftover output tokens routed through LI.FI: [8](#0-7) 

An attacker submits a self-crafted `transact()` call with `externalActionId` pointing to Emporium, `erc20TokenAddresses` containing only a harmless token/amount, and `externalActionMetadata` decoding to an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation` whose `endpoint` is a different ERC20 token held by Emporium (e.g. accumulated relay-fee token) and `callData = transfer(attacker, balance)`. The call selector filter only blocks `callHinkalWallet`/`doSendToRelay` on `IHinkalWallet`, so an ERC20 `transfer` call passes unimpeded: [9](#0-8) 

Because the drained token is absent from `circomData.erc20TokenAddresses`, the balance-diff loop never observes the loss, `balanceChange` for the declared tokens remains non-negative, and the function returns successfully — breaking the equation that "change in Emporium's ERC20/ETH balance across the call must equal what the balance-checked tokens/UTXOs account for."

### Impact Explanation
This allows any unprivileged EOA (their own prover, no signer/relay/admin key needed) to steal ERC20 tokens or ETH sitting in the shared Emporium contract that belong to the protocol or other users (accumulated relay fees, swap dust, leftover balances) — value movement that is never reflected in the Hinkal balance equation or reflected as a UTXO. This meets the High severity bar of "theft ... of protocol/relay fees" and, depending on how much residual balance accumulates in the shared contract at attack time, can escalate toward direct theft of user funds.

### Likelihood Explanation
Likelihood is high: no privileged role is required, the attacker is their own prover/signer for the transaction, and the vulnerable path (`signerAddress == address(0)`, arbitrary `op.endpoint`/`op.callData`) is a normal, intended usage mode of `runAction`, not an edge case requiring compromise of any key.

### Recommendation
- Require every token/ETH address touched by `EmporiumOperation.endpoint`/decoded from `op.callData` to be included and balance-checked in `circomData.erc20TokenAddresses`, or alternatively snapshot and reconcile Emporium's balance for the destination/token implied by each `op` (not just the declared array) before returning.
- Consider disallowing the stateless, unsigned "Case 2" arbitrary-call path entirely, or restrict its target/callData surface (e.g. an allow-list of endpoints/selectors) so it cannot invoke arbitrary ERC20 `transfer`/`transferFrom`/other value-moving functions on tokens outside the declared set.
- Ensure Emporium never retains cross-transaction balances (sweep dust/fees immediately) so that even an unconstrained call has nothing valuable to move.

### Proof of Concept
1. Wait until Emporium (shared contract) holds a non-trivial balance of some ERC20 token `X` (e.g., accumulated relay fees from unrelated swaps, or rounding dust from `ExternalActionSwap.swap`).
2. As any unprivileged user, call `Hinkal.transact` with a self-generated valid proof where:
   - `circomData.externalActionData.externalActionId` = Emporium's registered id, `externalAddress` = Emporium.
   - `circomData.erc20TokenAddresses` = `[Y]` for some unrelated token `Y` with zero/benign `amountChanges`.
   - `circomData.externalActionData.externalActionMetadata` = `abi.encode(EmporiumStack{ signerAddress: address(0), ops: [EmporiumOperation{ endpoint: X, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, X.balanceOf(emporium))) }], maxFee: 0, deadline: 0 })`.
3. `runAction` executes `X.transfer(attacker, balance)` from Emporium via the stateless branch (no signature required), passing the post-call check because token `X` is never in `circomData.erc20TokenAddresses`.
4. Attacker now holds Emporium's entire balance of token `X`, while the shielded balance/UTXO accounting for the transaction remains internally consistent and shows no loss.
