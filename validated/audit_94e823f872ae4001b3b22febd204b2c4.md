There is no refund-of-excess-`msg.value` logic on this path (unlike `placeOrder`, which explicitly refunds unspent native tokens at the end via `_sendValue(msg.sender, msgValue)`, and `fillOrder`'s same-chain path, which also refunds unspent `msgValue`). ### Title
`IntentGatewayV2.cancelOrder` same-chain path is payable but never refunds `msg.value`, permanently trapping user-sent ETH - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`cancelOrder` is marked `public payable` to support the cross-chain source-cancel route, which needs native ETH to pay for dispatching a `DispatchGet` request through the host. However, the same-chain cancellation branch (`_cancelSameChain`) performs no dispatch and consumes no `msg.value`, yet the function accepts arbitrary ETH from the caller without validating or refunding it.

### Finding Description
`cancelOrder` at [1](#0-0)  is declared `payable` and branches into three paths based on `isSameChain`/`currentChain`. Only the `_cancelFromSource` cross-chain path actually spends `msg.value` (to dispatch a GET request for the storage proof, mirrored in `IntrinsicIntents`/`ExtrinsicIntents`). The same-chain path calls `_cancelSameChain`, shown in `IntrinsicIntents.sol` at [2](#0-1) , which only reads escrow balances and calls `_withdraw` to send the escrowed input tokens back to `order.user` — it never reads or forwards `msg.value`.

Contrast this with `placeOrder`, which explicitly tracks `msgValue` and refunds any unspent amount at line [3](#0-2) , and `fillOrder`'s same-chain path in `IntrinsicIntents.sol`, which similarly refunds unspent native tokens to the solver at the end of the fill loop [4](#0-3) . `cancelOrder`'s same-chain branch has no equivalent refund, so any ETH sent alongside a same-chain cancel call (e.g., a caller who reuses a `msg.value`-populated transaction template meant for cross-chain cancels, or a wallet UI that always attaches a relayer-fee estimate) is retained by the `IntentGatewayV2` contract indefinitely with no accounting variable tracking it and no path to reclaim it (the contract's `receive()` function at [5](#0-4)  also accepts arbitrary ETH but that's a distinct, intentional entry point for escrow/sweep flows).

### Impact Explanation
This is a direct freezing-of-funds bug reachable by any unprivileged user submitting a single transaction (`cancelOrder` on a same-chain order with non-zero `msg.value`). The ETH becomes permanently stuck in the `IntentGatewayV2` contract — it isn't tracked in any per-order escrow accounting (`_orders` mapping keys on token address, and `address(0)` for native ETH is only credited via `placeOrder`), and there's no admin/governance sweep for arbitrary un-escrowed ETH sent through this specific call path outside of `SweepDust`, which requires Hyperbridge-originated dispatch tied to real dust from fills, not stray user-sent cancel-call value. This matches the analog bug class (payable withdraw/cancel function on one branch that shouldn't accept value, causing stuck funds) and rises to Medium severity, as it is concrete permanent value loss for the caller.

### Likelihood Explanation
Likelihood depends on user/integrator behavior: if SDKs or front-ends always populate `msg.value` with the same estimated relayer fee regardless of whether the specific order is same-chain or cross-chain (a plausible integration pattern given `cancelOrder` has one unified signature and only branches internally on `order.source`/`order.destination`), this triggers routinely for same-chain cancellations. A user calling the contract directly with leftover ETH from a template also triggers it. The lack of any input validation (e.g., no `require(msg.value == 0)` guard) on the same-chain branch means the bug is trivially reachable, though it requires an affirmative (if easy) mistake by the caller rather than depending on adversarial exploitation of another party's funds.

### Recommendation
Reject non-zero `msg.value` on the same-chain cancel path (e.g., `if (isSameChain && msg.value > 0) revert UnexpectedValue();`) or, to preserve UX, refund any unspent `msg.value` at the end of the same-chain branch the same way `placeOrder` and the same-chain fill path already do, ensuring no ETH sent by the caller can be silently absorbed by the contract.

### Proof of Concept
1. User places a same-chain order via `placeOrder`, escrowing input tokens (e.g., ERC-20, no ETH).
2. Before the order is filled, the user calls `cancelOrder(order, options)` with `msg.value = 1 ether` (either by mistake, reusing a fee-estimate template used for cross-chain cancels, or via a front-end that doesn't branch on same-chain vs cross-chain for calldata construction).
3. `cancelOrder` at [6](#0-5)  detects `isSameChain == true`, validates `currentChain == orderSource`, and calls `_cancelSameChain(order, commitment)`.
4. `_cancelSameChain` in [2](#0-1)  refunds the escrowed ERC-20 input tokens to `order.user` via `_withdraw`, but never inspects or forwards the 1 ETH sent with the transaction.
5. The transaction succeeds; the user's ERC-20 tokens are refunded, but the 1 ETH remains in the `IntentGatewayV2` contract's balance with no order, escrow entry, or governance path referencing it — it is permanently unrecoverable by that user.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable nonReentrant {
        bytes32 commitment = keccak256(abi.encode(order));

        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        // Emitted here, once, rather than from each of the three routes below. Every check those
        // routes make — Unauthorized, NotExpired, UnknownOrder — reverts, and a revert discards
        // logs, so an early emit can never announce a cancellation that did not happen. Emitting
        // before the branch also keeps `EscrowRefunded` the last log on the same-chain route, where
        // the refund is processed in this same transaction. Three emit sites cost bytecode this
        // contract does not have: it sits within ~100 bytes of the EIP-170 limit.
        emit OrderCancelled({commitment: commitment, canceller: msg.sender});

        if (isSameChain) {
            // Checked here rather than inside `_cancelSameChain`, which used to re-read `host()`,
            // re-query the host's state machine id and re-hash `order.source` to reach the same
            // answer this function already has. Same check, one external call fewer.
            if (currentChain != orderSource) revert WrongChain();
            _cancelSameChain(order, commitment);
        } else if (currentChain == orderSource) {
            _cancelFromSource(order, options, commitment);
        } else if (currentChain == orderDest) {
            _cancelFromDest(order, options, commitment);
        } else {
            revert WrongChain();
        }
    }

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
