## Title
Webhook shop identity (`shop-domain`) and topic are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used downstream by `ShopifyAPI::Webhooks::Registry.process` are taken from unauthenticated HTTP headers that are never part of the signed material. Because the same `api_secret_key` is shared by every shop that installs the app, any merchant who legitimately receives a signed webhook can replay that exact body/HMAC pair to the app's webhook endpoint while attaching an arbitrary `shop-domain` header, causing the handler to process the payload under a different, victim tenant's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` verifies the HMAC exclusively against `verifiable_query.to_signable_string` (i.e., the raw body) and the app's `api_secret_key`: [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read straight from HTTP headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` only checks the HMAC validity, then trusts `request.shop` and `request.topic` to build `WebhookMetadata` passed straight to the app's handler: [4](#0-3) 

The equality that should hold is: `shop that produced/authorized the signed body == shop the handler is told the payload belongs to`. Because the HMAC secret (`api_secret_key`) is identical for every shop that has the app installed, and the header carrying the shop identity is excluded from the signed bytes, this equality is not enforced — the shop the handler acts on is attacker-controlled while the bytes that were actually verified (the body) can come from any shop's own genuine webhook.

### Impact Explanation
An attacker who operates their own store with the app installed will legitimately receive real, validly-signed webhooks (body + `X-Shopify-Hmac-SHA256`) for their own shop. They can replay that exact body and HMAC to the app's public webhook endpoint while substituting `shop-domain` (and optionally `topic`/`webhook-id`) headers naming a victim shop. `HmacValidator.validate` will accept the request because it only checks the body bytes against the shared secret; `Registry.process` then invokes the registered handler with `shop: <victim-shop>` and the attacker's body content. Any app logic that uses `WebhookMetadata#shop` to select which merchant's records to update, trigger side effects for, or write data on behalf of, will act on the victim tenant using attacker-supplied content — a cross-tenant data integrity/spoofing issue.

### Likelihood Explanation
High. The attacker only needs the app installed on any shop they control (a low bar) and knowledge of the app's public webhook receiving endpoint (not secret). No access token, `client_secret`, or privileged account is required — only a legitimate, unprivileged HMAC that Shopify itself delivers to the attacker for their own shop's events.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material verified against the header-derived HMAC, or independently verify that the `shop-domain` header matches a shop known to have installed the app for the specific webhook subscription (e.g., cross-check against a stored per-shop webhook registration/session, and/or validate the request originates from Shopify's documented source IP ranges as an additional binding). At minimum, document that consuming applications must not treat `WebhookMetadata#shop` as authenticated unless it is corroborated by a persisted session/store record for that shop before use.

### Proof of Concept
1. App developer installs their own test shop A with the app; app registers a handler for topic `orders/create`.
2. Shop A generates a genuine webhook: raw body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker captures this request (they control shop A) and resends it to the app's webhook endpoint, changing only `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `HmacValidator.validate` succeeds because it only checks `B` against the shared secret: [5](#0-4) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and performs its action against the victim tenant using attacker-controlled data.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
