### Title
Missing zero-address validation on `_underlying`/`_dispatcher` in `WrappedHyperFungibleTokenUpgradeable.configure()` allows unbacked cross-chain mints - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol])

### Summary
`WrappedHyperFungibleTokenUpgradeable` splits configuration between `initialize()` (which only wires `Ownable`/`Pausable`/`ERC165`) and a separate `configure()` call that the owner must make afterwards to set `_host`, `_dispatcher`, and `_underlying` [1](#0-0) . Unlike `_host`, which is guarded by a one-time zero-check, `_underlying` and `_dispatcher` are unconditionally overwritten on every `configure()` call with no validation that the new value is non-zero [2](#0-1) . This mirrors the original report's root cause: critical state used to gate fund-moving logic is left uninitialized/unvalidated outside the constructor, and ordinary (non-malicious) admin operation can leave the contract in that dangerous state while it remains reachable by unprivileged callers.

### Finding Description
`send()` locks tokens via `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` before dispatching a cross-chain message that instructs the destination chain to credit `params.amount` of value to the recipient [3](#0-2) . OpenZeppelin's `SafeERC20._callOptionalReturn` (used internally by `safeTransferFrom`) treats a call that succeeds with empty return data as a successful transfer. A low-level call to an address with no contract code (e.g. `address(0)`) always succeeds trivially with empty return data, so if `_underlying == address(0)` at the time `send()` is invoked, `safeTransferFrom` silently "succeeds" without any tokens ever leaving `msg.sender`.

Because `_host` and `_underlying` are set together in the *first* `configure()` call, but only `_host` is protected from being reset, any later `configure()` call that passes `options.underlying == address(0)` (an operational/config-script mistake, not necessarily malicious intent, exactly as the original report envisions for `cardPartnerAddress`/`allowanceSignatureTimespan`) leaves `_host` correctly wired while `_underlying` silently becomes the zero address. From that point on, `send()` is fully reachable by any unprivileged user, and the fake "lock" bypasses `safeTransferFrom` while the real dispatch to a properly configured `_host` still succeeds, producing a legitimate ISMP message that will mint/unlock real value on the destination chain with no backing collateral on the source chain.

### Impact Explanation
This is an unbacked-mint / permanent-fund-forgery vector: an attacker (or any regular user) can call `send()` any number of times, paying nothing in `_underlying` tokens (since the transfer silently no-ops), while the destination-chain `onAccept()` unlocks/mints the full `message.amount` of the wrapped asset to an attacker-controlled `beneficiary` [4](#0-3) . This directly drains the underlying token reserves backing the wrapper on the destination chain, satisfying the "unbacked mint" / "concrete theft" criteria.

### Likelihood Explanation
The trigger condition (`_underlying == address(0)`) requires an operational error in an ordinary, non-malicious `configure()` call, since the function has zero validation on `options.underlying`/`options.dispatcher` even though it protects `options.host` on the very same call. Given `configure()` is meant to be re-callable for legitimate reconfiguration (e.g., rotating `_dispatcher`), any integration or governance script that omits or mis-serializes the `underlying` field when doing so reaches this state without any attacker action. Once reached, exploitation by an unprivileged user is a single `send()` transaction with no further preconditions.

### Recommendation
- Guard `_underlying` (and `_dispatcher`) in `configure()` against zero values, e.g. `if (options.underlying == address(0)) revert InvalidAddress(...)`.
- Consider making `_underlying` one-shot (like `_host`) since it is a foundational invariant of the wrapper, not a rotatable parameter.
- Add a runtime invariant check in `send()`/`onAccept()` that reverts if `_underlying == address(0)` before performing any transfer or dispatch.

### Proof of Concept
1. Deploy `WrappedHyperFungibleTokenUpgradeable` proxy, call `initialize(owner)` — `_host`, `_underlying`, `_dispatcher` remain `address(0)` [1](#0-0) .
2. Owner calls `configure({host: HOST, dispatcher: DISPATCHER, underlying: TOKEN, isWeth: false})` to correctly wire the contract on first setup, setting `_host = HOST` permanently.
3. Owner (via a later maintenance/rotation script) calls `configure({host: HOST, dispatcher: NEW_DISPATCHER, underlying: address(0), isWeth: false})` intending only to rotate the dispatcher — `_host` stays `HOST` (guarded), but `_underlying` is overwritten to `address(0)` with no revert [2](#0-1) .
4. Any user calls `send({dest: X, to: attacker, amount: LARGE_AMOUNT, timeout: 0, relayerFee: 0, data: ""})`. `IERC20(address(0)).safeTransferFrom(...)` succeeds silently (no tokens actually pulled), and `IDispatcher(HOST).dispatch(...)` succeeds since `_host` is valid, emitting a legitimate ISMP `Sent` commitment.
5. On the destination chain, the delivered message triggers `onAccept()`, transferring `LARGE_AMOUNT` of the real underlying token to `attacker` with zero collateral ever locked on the source chain [5](#0-4) .

        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
        }

        DispatchPost memory request = _buildDispatchPost(params);
        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,

        });

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(request.body, (HyperFungibleTokenUpgradeable.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({from: message.from, to: beneficiary, source: string(request.source), amount: message.amount});
    }
