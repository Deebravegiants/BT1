### Title
Sybil multi-account farming of the BEEFY uncle-proof reward curve drains the treasury — ([File: modules/pallets/beefy-consensus-proofs/src/lib.rs])

### Summary
`pallet-beefy-consensus-proofs::submit_proof` pays out a decreasing-curve reward (100% / 50% / 30% / 20% / 10% / 5%) to up to `MaxUncleProvers + 1` provers per finality target, intended to compensate genuinely independent provers for redundancy. The pallet's only anti-Sybil control is *per-account* deduplication and proof-to-signer binding — nothing prevents a single operator from controlling multiple accounts and submitting one SP1 proof per account for the same finality target, sweeping every uncle slot and extracting up to 215% of the base reward from the treasury for work that a single participant performed, exactly analogous to the UEarnPool exploit where an attacker created many self-controlled contracts to farm a tiered team/level reward meant for distinct participants.

### Finding Description
`submit_proof` is a permissionless, signed, unprivileged extrinsic (no staking or whitelisting): [1](#0-0) 

The uncle path (`settle_uncle_proof`) dedups only on the `account` value committed as the SP1 proof's nonce, which the pallet requires to equal the extrinsic signer: [2](#0-1) 

This "prover-bound" mechanism only prevents *stealing* someone else's proof from the mempool; it does not — and cannot — prevent a single operator from generating multiple independently-nonced SP1 proofs of the same underlying finality justification bound to Sybil-controlled accounts they themselves created, at no cost beyond compute: [3](#0-2) 

Each such proof is accepted as an "independent" uncle and paid at a decreasing curve fraction of `ProofReward`, transferred straight from the treasury: [4](#0-3) 

The docs explicitly acknowledge the permissionless, unstaked design and describe the uncle mechanism as rewarding "independent" provers for redundancy, but "independent" is enforced only by account identity, which is free and unlimited to fabricate: [5](#0-4) 

This mirrors the UEarnPool bug class precisely: the external exploit created 22 self-controlled contracts to satisfy a cumulative team/level threshold and collect a tiered reward meant to reward distinct, independent participants. Here, a single prover operator creates N accounts and produces N valid proofs for the same target to fill every position on the decreasing-curve, capturing rewards meant to compensate distinct, independent liveness/redundancy contributions.

### Impact Explanation
Each successful exploitation round pays out up to 215% of `ProofReward` (100% + 50% + 30% + 20% + 10% + 5%, per the mainnet curve) from `TreasuryPalletId` to a single operator's Sybil accounts, instead of the ~100-115% intended when only one or two genuinely independent provers participate. Because this can be repeated at every finality target/messaging proof (which occur continuously as new consensus updates land), it constitutes a sustained, unbounded treasury drain — a direct, permanent loss of protocol-owned funds meant to fund legitimate prover incentives, satisfying "concrete theft ... of funds."

### Likelihood Explanation
Likelihood is high: `submit_proof` is fully permissionless (no staking, no whitelist), account creation on a Substrate chain is free, and running multiple SP1 proving pipelines against the same relay-chain finality data under different committed nonces requires only additional GPU compute time that any operator running one prover already possesses. No collusion with other parties, no governance/admin/privileged access, and no additional cryptographic barrier is required beyond what a rational, profit-motivated single operator already controls.

### Recommendation
Tie uncle eligibility to a scarce, unforgeable resource rather than free account identity — e.g., require a minimum stake/bond per rewarded account (so Sybil accounts cost capital), or reduce/cap the aggregate uncle payout per finality target to a fixed multiple of the base reward regardless of how many distinct accounts submit, or require some external identity/collateral binding (e.g., a registered prover key with reputation history) before an account is eligible for uncle-position rewards. At minimum, monitor for accounts submitting proofs in tight clusters relative to `latest_beefy_height`/`blockNumber` from the same originating infrastructure and cap total per-window payout per underlying justification.

### Proof of Concept
1. Generate a set of `MaxUncleProvers + 1` fresh Substrate accounts (`A0..A5`), funded with only enough balance to pay the (refunded-on-success) tx fee.
2. For the same BEEFY finality target / parachain height, run the SP1 prover pipeline `MaxUncleProvers + 1` times, each time committing a different account (`A0..A5`) as the proof's public-value nonce, producing `MaxUncleProvers + 1` independently-valid SP1 proofs for the identical underlying justification.
3. Submit the first proof from `A0` via `submit_proof` — it lands as the first proof (position 0), advances state, and pays 100% of `ProofReward` to `A0`, per `pay_position_reward(&submitter, 0)`.
4. Submit the remaining proofs from `A1..A5` in sequence — each is routed to `settle_uncle_proof`, passes the per-account dedup check (each account appears only once in `AcceptedProvers`), verifies successfully against the same `ProofContext` snapshot, and pays 50%, 30%, 20%, 10%, 5% of `ProofReward` respectively to `A1..A5`.
5. Sweep all six accounts' rewards to a single beneficiary. Total extracted: 215% of `ProofReward` from the treasury for a single operator's proving work, repeatable at every subsequent finality target indefinitely.

//! Each SP1 proof commits a prover-chosen nonce into its public values, and the pallet

		/// Apply the curve at `position` to [`ProofReward`], transfer from the treasury,
		/// and mint reputation 1:1.
		fn pay_position_reward(
			submitter: &T::AccountId,
			position: u32,
		) -> Result<BalanceOf<T>, Error<T>> {
			let zero = BalanceOf::<T>::default();
			let base = ProofReward::<T>::get();
			if base == zero {
				return Ok(zero);
			}

			let reward = Self::position_reward(base, position);
			if reward == zero {
				return Ok(zero);
			}

			let treasury: T::AccountId =
				<T as Config>::TreasuryPalletId::get().into_account_truncating();
			<T as Config>::Currency::transfer(&treasury, submitter, reward, Preservation::Preserve)
				.map_err(|e| {
					log::warn!(
						target: "ismp",
						"[beefy-consensus-proofs] treasury reward transfer failed: {e:?}",
					);
					Error::<T>::RewardTransferFailed
				})?;

			if let Err(e) = T::ReputationAsset::mint_into(submitter, reward) {
				log::warn!(
					target: "ismp",
					"[beefy-consensus-proofs] reputation mint failed: {e:?}",
				);
			}

			Ok(reward)
		}

```text
### Uncle Proofs

To reward redundancy and keep proving live, Hyperbridge rewards more than just the single fastest prover. The **first** prover to land a valid proof for a given finality target advances the chain's state and earns the **full** reward. Additional **independent** provers that generate their own valid proof for the **same** target are accepted as **uncles** and paid on a *decreasing reward curve*, up to a governance-configured limit (`MaxUncleProvers`).

The curve (set via `set_reward_curve`) pays each position a fraction of the base reward. The current curve is **100% / 50% / 30% / 20% / 10% / 5%** — the first prover receives the full reward (100%), and the next five uncles receive 50%, 30%, 20%, 10%, and 5% respectively. Uncle rewards apply to SP1 proofs only.

### Prover-Bound Proofs

Each SP1 proof commits a nonce into its public values, and the runtime requires that nonce to equal the extrinsic signer. This binds a proof to the prover that produced it:

- A proof **cannot be stolen** — copying the proof bytes from the mempool and submitting them under a different account is rejected, because the committed account no longer matches the signer.
- Reward **deduplication is per-account** — an account is rewarded at most once per finality target, so a single prover cannot mint many byte-distinct variants of one proof (e.g. via Groth16 re-randomization) to sweep multiple uncle slots.
```
