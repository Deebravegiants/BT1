## Analysis

The reported behavior is real: `new_multi_key_from_single_keys` in `aptos-move/framework/aptos-stdlib/sources/cryptography/multi_key.move` only validates `num_keys > 0` and `num_keys <= MAX_NUMBER_OF_PUBLIC_KEYS <= signatures_required`-relationship, but never rejects `signatures_required == 0`. [1](#0-0) 

The same gap exists in `deserialize_multi_key`, used by `new_public_key_from_bytes`, so a `MultiKey{signatures_required: 0}` can also be built directly from raw bytes without going through the constructor at all. [2](#0-1) 

This is inconsistent with every other layer of the codebase that implements the same "k-of-n" invariant, all of which explicitly reject `k == 0`:

- Legacy `MultiEd25519PublicKey`/`PrivateKey` constructor: [3](#0-2) 
- Rust `MultiKey::new` used to build `MultiKeyAuthenticator`: [4](#0-3) 
- API input validation for `MultiKeySignature`: [5](#0-4) 
- API input validation for legacy `MultiEd25519Signature`: [6](#0-5) 

Critically, the actual native downstream check that turns a `MultiKey` into "how many real signatures are required" is a `>=` comparison, not a strict positivity check: [7](#0-6) 

If `signatures_required == 0`, `self.signatures.len() >= 0` is trivially true even for an **empty** signature set, and `verify()` then iterates zero authenticators and returns `Ok(())` — i.e., zero cryptographic signatures are needed to authenticate. [8](#0-7) 

## Where this stops being a full end‑to‑end custody bypass

I traced usages of `new_multi_key_from_single_keys`: it is called from `aptos-move/framework/aptos-framework/sources/account/account.move` and `aptos-move/framework/aptos-framework/sources/keyless_account.move`, both 2–4 call sites, but I was not able to confirm within the available tool budget whether either of those call sites (a) is reachable from an **unprivileged, no-signature entrypoint** that lets an attacker rotate an *existing, already-funded* custody account's authentication key to a zero-threshold `MultiKey`, or (b) requires the current account owner's own signature (pre-existing authority) to authorize the rotation. Aptos's key-rotation flow normally requires the current key holder to co-sign the rotation transaction, which would mean this bug only lets someone corrupt a key config they *already control* (self-inflicted), not seize an arbitrary victim's account outright. Verifying the exact reachability of these two call sites, and whether `MultiKeyAuthenticator` bytes built at the native/Rust layer bypass `MultiKey::new` during BCS deserialization of a raw transaction (they do, since it's a plain `#[derive(Deserialize)]` struct), would require deeper tracing than is possible here.

## Verdict

The finding is valid as a genuine, unprivileged-reachable **invariant violation** (input validation gap), because:
1. The Move constructor and deserializer accept `signatures_required = 0` while every equivalent Rust/API validator in the same codebase treats this as an invalid, custody-breaking configuration.
2. The native signature-verification code path (`MultiKeyAuthenticator::to_single_key_authenticators`/`verify`) trivially accepts an **empty signature set** once `signatures_required == 0`, meaning any account whose authentication key is derived from such a `MultiKey` becomes authenticatable with **zero valid signatures** by anyone.

### Title
Missing `signatures_required > 0` check in `new_multi_key_from_single_keys`/`deserialize_multi_key` allows constructing a zero-threshold `MultiKey` that native verification treats as requiring no signatures at all - (File: aptos-move/framework/aptos-stdlib/sources/cryptography/multi_key.move)

### Summary
`new_multi_key_from_single_keys` (and `deserialize_multi_key`) never enforce `signatures_required > 0`, unlike the analogous Rust (`MultiKey::new`, `MultiEd25519PublicKey::new`) and API (`MultiKeySignature::verify`, `MultiEd25519Signature::verify`) validators, which all explicitly reject a zero threshold.

### Finding Description
`new_multi_key_from_single_keys` only checks `num_keys > 0`, `num_keys <= MAX_NUMBER_OF_PUBLIC_KEYS`, and `signatures_required <= num_keys`, but not `signatures_required > 0`. [9](#0-8) 
`deserialize_multi_key` similarly builds a `MultiKey` straight from BCS bytes with no validation at all. [10](#0-9) 
Once a `MultiKey{signatures_required: 0}` becomes the live authentication key of any account (multisig-controlled resource account, object owner, etc.), the native verification code that checks `self.signatures.len() >= self.public_keys.signatures_required() as usize` is satisfied by an empty signature list, so `verify()` succeeds having performed zero actual cryptographic checks. [11](#0-10) 

### Impact Explanation
If a zero-threshold `MultiKey` is ever accepted as a live authentication key (e.g., through a rotation path that relies on this Move-level function as its safety check), the corresponding account can be fully authenticated and controlled by anyone submitting a `MultiKeyAuthenticator` with an empty signature/bitmap — a complete custody bypass (transfer, withdraw, upgrade, or freeze authority) for that account.

### Likelihood Explanation
Moderate-to-uncertain in isolation: exploiting this against a pre-existing, already-funded custody account additionally requires that account's authentication key to actually be rotated/derived to a zero-threshold `MultiKey` through a path that relies on this validator as its only gate. I could not confirm within available tooling whether `account.move`'s or `keyless_account.move`'s call sites expose this to an attacker without pre-existing signing authority over the target account, so likelihood of a fully unprivileged end-to-end account takeover (vs. a self-inflicted misconfiguration trap) is unverified.

### Recommendation
Add `assert!(signatures_required > 0, error::invalid_argument(E_INVALID_MULTI_KEY_SIGNATURES_REQUIRED_ZERO))` to both `new_multi_key_from_single_keys` and `deserialize_multi_key`, mirroring the checks already present in `MultiKey::new` (authenticator.rs), `MultiEd25519PublicKey::new`, and the API's `MultiKeySignature::verify`/`MultiEd25519Signature::verify`. Also verify/close the `>= 0` threshold-trivially-satisfied path in `MultiKeyAuthenticator::to_single_key_authenticators` as defense in depth.
