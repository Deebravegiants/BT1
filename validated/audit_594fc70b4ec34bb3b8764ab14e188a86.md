### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on an otherwise-valid webhook (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature only over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by `Registry.process` to build `WebhookMetadata` are taken from unauthenticated HTTP headers. This breaks the equality "shop the HMAC vouches for == shop the handler acts on," enabling a cross-tenant replay: any body+HMAC pair that is valid for one shop's webhook can be resent with a different `shop-domain` header and will still pass validation, causing the handler to process/attribute the payload to an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` / `validate_signature` verify the HMAC exclusively against that signable string (`verifiable_query.to_signable_string`) using `Context.api_secret_key`: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the body or to each other: [3](#0-2) 

`Registry.process` only checks the HMAC before trusting `request.shop` (and the other header-derived fields) to construct `WebhookMetadata`, which is handed to the app's handler as the authoritative tenant identity for that payload: [4](#0-3) 

Because the signature never covers the `shop-domain` header, the equality the app relies on — `authenticated_shop == acted_on_shop` — does not hold. Any request whose `raw_body` + `hmac` pair is valid for the shared `api_secret_key` (e.g., a genuine webhook delivery for the attacker's own installed shop, which they can capture since they control their own store and can trigger arbitrary webhook events) can be replayed with the `shop-domain` (and `topic`/`webhook_id`) header swapped to a victim shop. `Utils::HmacValidator.validate` still returns `true` because it only checks the body bytes, so `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This crosses a tenant boundary: an unprivileged actor who merely operates their own shop (or otherwise obtains one valid webhook body/HMAC pair) can make the app attribute/act on that payload as though it originated from a different, victim shop. Any handler logic that uses `data.shop` to select which shop's session/data to read or mutate is subject to cross-tenant data confusion — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitability only requires: (1) the ability to receive one legitimate webhook (trivial — install the app on any shop, even a free/dev store, and trigger any subscribed event), and (2) the ability to POST an HTTP request to the app's public webhook endpoint with modified headers, which is exactly what the endpoint is designed to accept from the internet. No access token, `client_secret`, or privileged account is needed, and the HMAC check itself passes unmodified.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable material verified by the HMAC check, or otherwise cryptographically/authoritatively bind the header-derived `shop` to the specific webhook delivery (e.g., cross-check against Shopify by looking the webhook id/shop pair up via the Admin API, or reject processing unless the shop domain matches an expected/registered value) before constructing `WebhookMetadata` and invoking the handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`), capturing the genuine delivery: raw JSON body `B` and header `x-shopify-hmac-sha256: H` (valid, computed by Shopify with the app's shared `api_secret_key`).
2. Attacker POSTs to the app's webhook endpoint with body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and adjusts `x-shopify-topic`/`x-shopify-webhook-id` as desired.
3. `ShopifyAPI::Utils::HmacValidator.validate` (called from `Registry.process`) only hashes `B`, so it returns `true`. [5](#0-4) 
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)` and invokes the handler, which now believes the (attacker-supplied) event/data belongs to `victim-shop.myshopify.com`.
