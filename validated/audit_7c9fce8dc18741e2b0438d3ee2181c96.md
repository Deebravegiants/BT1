### Title
Webhook `shop` (tenant identifier) is not covered by the HMAC signature, allowing shop-domain spoofing on an otherwise validly-signed webhook - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — none of the HTTP headers (including `shop-domain`) are part of the signed material. Yet the `shop` value taken straight from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header is what gets forwarded to the host application's handler as the tenant identifier in `WebhookMetadata`.

### Finding Description
The verification chain is:
- `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-22`) calls `validate_signature`, which computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac`. [1](#0-0) 
- For `Webhooks::Request`, `to_signable_string` returns `@raw_body` exclusively. [2](#0-1) 
- `shop` is read directly from the `shop-domain` header, which is not part of the signed bytes. [3](#0-2) 
- `Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the tenant-scoped `WebhookMetadata` handed to the app's handler. [4](#0-3) 
- `WebhookMetadata.shop` is a plain `String` field with no further binding to the HMAC or to any Shopify-verified value. [5](#0-4) 

This breaks the identity binding `shop_authenticated == shop_used_for_tenant_scoping`. The gem authenticates only the *body bytes*, not the `(body, shop)` pair, yet exposes `shop` as if it were an authenticated attribute of the request. Any unprivileged actor who can obtain one valid `(body, hmac)` pair from Shopify — trivially, by installing the app on their own shop and receiving a legitimate webhook — can replay that exact body/HMAC combination while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` will still pass because it never inspects the header, and the host application's handler will receive `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker-controlled shop can cause the library to (falsely) assert to the host application's webhook handler that data belongs to a different, victim shop, while the app's own authentication (HMAC) mechanism reports success. Any host logic that trusts `WebhookMetadata#shop` for per-tenant side effects (e.g., updating shop-scoped state, looking up sessions/tokens by `shop`, dispatching tenant-specific business logic) can be tricked into acting on attacker-supplied `shop` values with attacker-supplied `body` content that was never actually sent by Shopify for that shop. This matches the "Critical - cross-tenant access" category because the confusion of tenant identity is the direct, provable consequence of the gem's own signature-computation design (`to_signable_string` excluding `shop`).

### Likelihood Explanation
High. No credentials, tokens, or privileged access are required — only the ability to install the app on any shop (which is the normal, unprivileged installation flow) to capture one legitimate `(body, hmac)` pair, and the ability to POST directly to the app's webhook endpoint with a forged `shop-domain` header while keeping the intercepted body and HMAC unchanged.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the signable string used for HMAC verification, or otherwise cryptographically bind them to the verified payload before exposing `WebhookMetadata#shop` to host application handlers. At minimum, document prominently that `WebhookMetadata#shop` is not itself HMAC-authenticated and must be independently cross-checked by the host application against a known/expected shop before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a legitimate webhook: body `B`, headers include `x-shopify-shop-domain: attacker.myshopify.com` and `x-shopify-hmac-sha256: H` (a valid HMAC of `B` under the app's `api_secret_key`).
2. Attacker resends the same request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`B` only) and compares against `H` — validation succeeds because `shop-domain` is not part of the signed data. [6](#0-5) 
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body_of_B, ...)`, i.e., attacker-controlled content falsely attributed to the victim shop. [7](#0-6)
