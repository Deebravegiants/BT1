### Title
Permissionless pool initialization with attacker-chosen low reserves enables first-depositor share dilution via direct token donation - ([File: program/src/processor.rs])

### Summary
The reported bug class ("initial liquidity is too low, enabling price/ratio manipulation of an unbacked pool") maps onto Raydium's `Initialize2` + `Deposit` flow. `Initialize2` lets any unprivileged caller create a pool and freely choose `init_pc_amount`/`init_coin_amount` (only bounded by `InitLpAmountTooLess`, i.e. `sqrt(pc*coin) > 10^lp_decimals`), and `Deposit` computes a depositor's minted LP share from the *live* vault token balances rather than any internally-tracked, donation-resistant reserve value.

### Finding Description
`process_initialize2` accepts attacker-supplied `init_pc_amount`/`init_coin_amount` with no minimum beyond the tiny anti-zero check, so an attacker can create a pool with a very small amount of both tokens: [1](#0-0) . The resulting LP token supply (`amm.lp_amount`) can therefore be made extremely small right after creation.

Subsequently, `process_deposit` computes the pool's current reserves directly from the coin/pc vault SPL token account balances (`amm_coin_vault.amount`, `amm_pc_vault.amount`) via `calc_total_without_take_pnl_no_orderbook`, not from any deposit-tracked invariant: [2](#0-1) . The LP tokens to mint for a new depositor are then computed as `deduct_amount / total_without_pnl * amm.lp_amount`, floor-rounded: [3](#0-2) [4](#0-3) .

Because the vault balance (`total_coin_without_take_pnl`/`total_pc_without_take_pnl`) is read directly from the token account rather than from a value that only changes through `Deposit`/`Withdraw`/swap accounting, any plain SPL token transfer directly into `amm_coin_vault`/`amm_pc_vault` inflates the ratio without minting corresponding LP tokens. Combined with the fact that a pool can be created with `amm.lp_amount` as low as just above `10^lp_decimals` (i.e. attacker holds virtually all outstanding LP supply), the attacker can:
1. Call `Initialize2` with the minimum passing `init_pc_amount`/`init_coin_amount`, becoming (near) sole LP holder.
2. Directly transfer a large amount of coin/pc tokens into the pool's vaults (an ordinary SPL `Transfer`, not a program instruction) to massively inflate `total_coin_without_take_pnl`/`total_pc_without_take_pnl` relative to `amm.lp_amount`.
3. When a victim's subsequent `Deposit` executes, `mint_lp_amount = deduct_amount * amm.lp_amount / total_without_pnl` rounds down (potentially to 0, which the code only guards with `mint_lp_amount == 0` reverting the whole deposit, but for slightly-above-zero results the victim receives disproportionately few LP tokens for a large deposit) while the transferred tokens are absorbed into the vaults that the attacker's (near-total) LP supply is entitled to.
4. Attacker then calls `Withdraw`, which computes payout the same way — `token_input=withdraw.amount, token_total=amm.lp_amount` against the (now-inflated) vault-derived `total_coin_without_take_pnl`/`total_pc_without_take_pnl` — capturing the donated funds via `exchange_pool_to_token`: [5](#0-4) .

This is the same fundamental "unbacked/skewed initial liquidity enables ratio manipulation" primitive as the referenced report, but concretely reachable in this AMM through permissionless `Initialize2` combined with a plain token transfer to the vault and `Deposit`/`Withdraw`, i.e. a classic first-depositor/donation attack on the pool's exchange-rate math.

### Impact Explanation
A depositor who trusts the displayed/expected reserve ratio can have most of their deposited tokens absorbed into the pool with little to no corresponding LP minted, and the attacker (holding the bulk of `amm.lp_amount`) can subsequently withdraw a share of the pool that includes the victim's donated/deposited tokens. This is a direct theft-of-user-funds vector on any newly created, low-liquidity pool, which is exactly the scenario the referenced report calls out as high risk for newly bootstrapped/thin pools.

### Likelihood Explanation
Pool creation (`Initialize2`) is fully permissionless and the only enforced floor is `sqrt(pc*coin) > 10^lp_decimals`, which is trivially satisfiable with tiny (e.g. a few units above `10^decimals`) amounts, so an attacker can cheaply set up a nearly-monopolized LP position. Front-running/timing a victim's first meaningful `Deposit` into a freshly created, low-liquidity pool on a public mempool-less-but-still-observable Solana network is realistic, particularly for pools created for new tokens where the creator amounts are attacker-controlled or attacker-created.

### Recommendation
- Enforce a meaningfully larger, protocol-defined minimum initial liquidity (not just `> 10^decimals`) for `Initialize2`, and/or permanently lock a fixed minimum LP amount to a burn address as Uniswap V2 does, sized so that donation-based ratio manipulation is not profitable relative to gas/rent costs.
- Do not derive `total_pc_without_take_pnl`/`total_coin_without_take_pnl` purely from raw SPL vault balances for deposit/withdraw share calculations; track deposits/withdrawals internally (or reconcile any excess vault balance beyond tracked deposits as protocol-owned, not distributable via the naive ratio) so unsolicited donations cannot skew a depositor's minted-share calculation.
- Consider requiring `Deposit` to revert (rather than mint a very small non-zero share) whenever the computed `mint_lp_amount` is disproportionately small relative to the value deposited, or add a minimum-shares-out slippage parameter tied to expected pool share rather than only `other_amount_min` token amounts.

### Proof of Concept
1. Attacker calls `Initialize2` for a fresh mint pair with `init_coin_amount`/`init_pc_amount` chosen just large enough to pass `InitLpAmountTooLess` (`sqrt(pc*coin) > 10^lp_decimals`), receiving nearly all of `amm.lp_amount` — see check at [1](#0-0) .
2. Attacker performs a plain `spl_token::instruction::transfer` of a large amount of coin (or pc) tokens directly to `amm.coin_vault` (no Raydium instruction required, ordinary SPL CPI), inflating `amm_coin_vault.amount` far beyond what `amm.lp_amount` represents.
3. Victim calls `Deposit` expecting a proportional share; `total_coin_without_take_pnl` is read from the inflated vault balance at [6](#0-5) , so `mint_lp_amount` computed at [3](#0-2)  is disproportionately small relative to the tokens the victim transfers into the vault.
4. Attacker calls `Withdraw` with their LP tokens; payout is computed from the same inflated vault-derived totals at [5](#0-4) , letting the attacker redeem a share that includes the victim's contributed tokens.

Note: I was not able to execute this against a running validator/test harness in this environment, so the exact numeric magnitude of extractable value (dependent on `lp_decimals`, fee/pnl-taking via `calc_take_pnl`, and rounding) is derived from static code review rather than a live PoC run.

    pub fn exchange_token_to_pool(
        &self,
        pool_total_amount: u64,
        round_direction: RoundDirection,
    ) -> Option<u64> {
        Some(if round_direction == RoundDirection::Floor {
            U128::from(pool_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_div(self.token_total.into())
                .unwrap()
                .as_u64()
        } else {
            U128::from(pool_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_ceil_div(self.token_total.into())
                .unwrap()
                .as_u64()
        })
    }
