### Title
Webhook shop identity spoofing via HMAC that only covers the request body, not the `shop-domain` header - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request **body**. The `shop` identity that is handed to the application's webhook handler is read from the `X-Shopify-Shop-Domain` header, which is **not** part of the signed material. Any party who can produce one HMAC-valid webhook payload for the shared app secret (e.g., a merchant who has installed the app on their own store and thus legitimately receives real, correctly-signed webhooks) can replay that same body+HMAC pair while substituting an arbitrary `shop-domain` header, causing the handler to process attacker-supplied data under another tenant's shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the (unsigned) header: [2](#0-1) 

`Registry.process` validates the HMAC against `Utils::HmacValidator.validate`, which in turn calls `validate_signature`/`compute_signature` over `verifiable_query.to_signable_string` (i.e. the body only) using the app's `api_secret_key`: [3](#0-2) 

After the HMAC check passes, `request.shop` (the unsigned header value) is forwarded verbatim into `WebhookMetadata` and delivered to the app's handler as the trusted tenant identity: [4](#0-3) 

The identity binding that should hold is:
`hmac_signed_bytes == bytes_that_determine_which_shop_the_data_is_attributed_to`

Here that equality fails: `hmac_signed_bytes = raw_body` while `shop_attributed_to = headers["shop-domain"]`. Because the webhook endpoint is a public, unauthenticated-by-network HTTP endpoint (the HMAC is the *only* authentication mechanism this gem enforces), and because the same `api_secret_key` is shared across every shop that has installed a given (multi-tenant/public) app, any shop that has legitimately installed the app can capture one of its own genuine webhook deliveries (valid body + valid HMAC for that body) and replay it against the endpoint with the `X-Shopify-Shop-Domain` header changed to point at a different, victim shop. The HMAC still validates (it only checks the body), and the handler receives `WebhookMetadata#shop` set to the victim's shop domain while the `body` is attacker-controlled content from the attacker's own store.

### Impact Explanation
This breaks the tenant/shop identity boundary: the application's webhook handler will process attacker-chosen data believing it originates from a different merchant's shop. Depending on how the host application keys off `WebhookMetadata#shop` (e.g., looking up that shop's session/access token, updating shop-scoped records, triggering shop-scoped side effects), this enables cross-tenant data injection/corruption using only the identity of the victim shop, without ever needing that shop's credentials — a cross-tenant access vulnerability.

### Likelihood Explanation
Any entity that can install the app on a shop they control (a normal, low-privilege path for public/multi-tenant Shopify apps) automatically receives real webhooks with valid HMACs signed by the shared `api_secret_key`. No special privilege beyond "having installed the app on some shop" is required to obtain a valid (body, HMAC) pair; only the header needs to be forged in the replay, which is trivial for any HTTP client posting directly to the webhook endpoint.

### Recommendation
Bind the shop identity into the authenticated material, or otherwise validate it out-of-band:
- Prefer verifying that the `X-Shopify-Shop-Domain` header corresponds to a shop with a known, stored HMAC/webhook secret or app installation record before trusting it, rather than trusting the header purely because the body-only HMAC validated.
- Where possible, include the shop domain (and topic) in the signable string, or require the host application to cross-check `request.shop` against its own session/shop registry before acting on webhook data, and document this requirement clearly for consumers of `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs a public multi-tenant app on `attacker.myshopify.com`; app is configured with a single shared `api_secret_key`.
2. Attacker triggers/receives a legitimate webhook delivery, e.g. `orders/create`, and captures `raw_body` and the resulting `X-Shopify-Hmac-Sha256` value (both are attacker-controlled/observable since it's their own shop).
3. Attacker POSTs the exact same `raw_body` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` instead of their own domain.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — passes, since the body wasn't changed: [4](#0-3) 
5. The handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and `body` containing attacker-controlled content, causing the app to attribute/process attacker data under the victim shop's identity.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
