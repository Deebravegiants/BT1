### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` (and `topic`/`webhook_id`) values that the host application relies on to determine *which merchant* the webhook belongs to are taken from HTTP headers that are never included in the signed material. Because the HMAC secret (`Context.api_secret_key`) is the same for every shop that has installed the app, anyone who has legitimately received one authentic webhook (e.g., by installing the app on their own store) possesses a `(body, hmac)` pair that remains "valid" forever, and can replay it while swapping the `shop-domain` header to any other tenant, causing the app to treat attacker-controlled data as authentic data from a different, victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC of `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to return only the raw HTTP body — none of the identifying headers are part of the signed string: [2](#0-1) 

The `shop`, `topic`, and `webhook_id` accessors are parsed straight from attacker-controllable HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`), with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., the body) and then forwards the *unauthenticated* `request.shop` value straight into `WebhookMetadata`, which is what the app's own `WebhookHandler#handle` implementation consumes as the tenant identity for the webhook: [4](#0-3) [5](#0-4) 

This breaks the intended identity binding: `hmac verified over body` ≠ `shop trusted by handler`. The equality that should hold — "the shop the handler believes sent this payload" == "the shop cryptographically proven to have sent this payload" — does not, because the header carrying the shop identity sits entirely outside the HMAC's coverage. Since `Context.api_secret_key` is a single, app-wide secret shared across *all* installing shops (not a per-shop secret), a valid `(body, hmac)` pair obtained from one shop's genuine webhook is a valid pair for the shared secret regardless of which shop header accompanies it.

### Impact Explanation
An attacker who installs the target app on their own store (an ordinary, unprivileged action) will receive genuine webhooks with valid `(body, hmac)` pairs signed with the app's `client_secret`. The attacker can then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `Registry.process` will accept the request (the HMAC over the unmodified body is still valid) and hand the handler a `WebhookMetadata` claiming to be from the victim shop. Any host application that uses `data.shop` to look up per-tenant state, apply the payload to the victim's records, or route the event will process attacker-supplied content under another tenant's identity — a cross-tenant data-integrity/isolation break consistent with the "Critical: cross-tenant access" impact category, since the shop-scoping boundary that the gem is expected to enforce via HMAC validation is not actually bound to the shop claim it hands to the handler.

### Likelihood Explanation
Likelihood is high for any attacker capable of installing the app on a store they control (a normal, unprivileged flow for public/embedded Shopify apps), since that is sufficient to harvest a valid `(body, hmac)` pair without needing the `client_secret` itself. No access token, session, or privileged credential is required — only observation of one legitimate webhook delivery.

### Recommendation
Bind the shop (and topic/webhook id) into the value that is actually verified, e.g. include the `shopify-shop-domain` (and other Shopify-supplied identifying headers) in the signable string used for HMAC computation, or otherwise cryptographically bind the `shop` claim to the signature before exposing it to `WebhookHandler#handle`. Short term, callers of `Registry.process` should be documented to independently corroborate `data.shop` against a shop known to have a valid webhook registration/session before trusting it; long term, the library itself should refuse to expose an unauthenticated `shop` value as part of `WebhookMetadata`.

### Proof of Concept
1. Attacker creates development store `attacker.myshopify.com` and installs the target Shopify app (uses the app's single, shared `client_secret`).
2. App sends attacker a genuine webhook, e.g. `orders/create`, with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`. Attacker captures `(B, H)`.
3. Attacker crafts a new HTTP POST to the app's webhook endpoint with the identical body `B` and header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `shopify-topic`/`shopify-webhook-id`, since those are unauthenticated too).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because it only checks `HMAC-SHA256(client_secret, B) == H`, both of which are unchanged and valid: [4](#0-3) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and, following normal app patterns, applies `B`'s data to `victim-shop`'s tenant record — a forged cross-tenant webhook accepted as authentic.
