### Title
Webhook shop-tenant identity spoofing via unsigned `shop-domain` header — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by HMAC-verifying only the raw request body, but the `shop` value handed to the application's webhook handler is read from an HTTP header that is never covered by that HMAC. This breaks the identity binding `shop authenticated == shop used as tenant key`, allowing anyone who can produce one valid (body, HMAC) pair — trivially obtainable by installing the app on their own store — to relabel that payload as belonging to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` only signs `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop` value returned by `Request#shop`, however, is pulled directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed payload: [3](#0-2) 

`Utils::HmacValidator.validate` computes and compares HMAC over `verifiable_query.to_signable_string` — i.e. body only — using `Context.api_secret_key`, the app's single client secret shared across every shop that has installed the app: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identifier passed into the application's handler: [5](#0-4) 

Because the same `api_secret_key` signs webhook bodies for every shop that installed the app, a valid `(raw_body, hmac)` pair obtained from one shop's own webhook traffic remains cryptographically valid no matter what shop-domain header accompanies it. The equality the gem implicitly assumes is:

`shop authenticated by HMAC == shop delivered to handler.handle(shop: request.shop, ...)`

but in fact HMAC only proves "signed with this app's secret", not "this specific shop sent it." An unprivileged user who has legitimately installed the app on their own store (`shop-A.myshopify.com`) receives real webhook deliveries with valid HMACs computed over their own event bodies. They can then submit that same `(raw_body, hmac)` to the app's webhook endpoint while substituting `x-shopify-shop-domain: victim-shop.myshopify.com`. `Utils::HmacValidator.validate` still returns `true` (it never inspects the shop header), and `Registry.process` calls the app's handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: attacker's own body, ...)`.

Any host application that uses `WebhookMetadata#shop` as the tenant/session key to look up or write per-shop data (a standard, gem-recommended pattern) will process the attacker's forged event under the victim shop's identity — a cross-tenant data confusion/injection primitive driven entirely by an unauthenticated header value.

### Impact Explanation
This is a cross-tenant boundary break: an attacker with no more than their own paid/free app install can forge webhook events attributed to any other merchant using the same app, because the shop identity is never bound to the cryptographic proof of authenticity. Depending on how the host app consumes `WebhookMetadata#shop` (e.g., updating orders, inventory, or triggering redacts/uninstalls keyed by shop), this can lead to cross-tenant data corruption or spoofed lifecycle events for shops the attacker does not control, meeting the "cross-tenant access" bar for Critical severity.

### Likelihood Explanation
Likelihood is high for any attacker who can install the target app on a shop they control (a normal, unprivileged action for any Shopify merchant/developer) and can send arbitrary HTTP requests to the app's public webhook endpoint (which by design must accept unauthenticated internet traffic from "Shopify"). No secret, token, or privileged access is required — only capturing one legitimate `(body, hmac)` pair from their own install and replaying it with a modified header.

### Recommendation
Bind the shop identity cryptographically to the verified payload rather than trusting the unsigned header:
- Include the `shop-domain` (and ideally `webhook-id`/`topic`) header values in the HMAC-signable string, or
- Cross-check `request.shop` against a shop identifier embedded in the verified JSON body (when the topic's payload includes one) before dispatching to the handler, and
- Document clearly in `Webhooks::Request`/`Registry` that the shop header is not currently authenticated, so host apps do not use it as a sole tenant key without additional verification (e.g., confirming an active session/install exists for that shop before trusting the payload).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers/receives any webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-SHA256` header value `H` (valid because `H = HMAC(secret, B)`).
2. Attacker sends a new POST request directly to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - Header `X-Shopify-Hmac-SHA256: H` (unchanged)
   - Header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - Header `X-Shopify-Topic`, `X-Shopify-Webhook-Id` as desired
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present).
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes HMAC over `B` using the shared `api_secret_key`. [6](#0-5) 
5. The registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, so the host application processes attacker-controlled data under the victim's tenant identity.
