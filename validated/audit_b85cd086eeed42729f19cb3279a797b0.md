Audit Report

## Title
Gateway CORS wildcard allowlist bypass via missing subdomain boundary check - ([File: core/services/gateway/network/httpserver.go])

## Summary
`httpServer.isAllowedOrigin` implements wildcard CORS matching (`*.example.com`) by stripping the `*.` prefix and testing `strings.HasSuffix(originHost, allowedHost)` with no requirement that the matched suffix be preceded by a `.` boundary. As a result, an attacker-controlled `Origin` such as `evilexample.com` incorrectly satisfies an allowlist entry configured as `*.example.com`, even though it is not a genuine subdomain.

## Finding Description
`handleRequest` reads the client-supplied `Origin` header directly and passes it unvalidated (other than URL parsing) to `isAllowedOrigin`: [1](#0-0) . Inside `isAllowedOrigin`, after exact-match fails, the wildcard branch strips `*.` and performs a bare suffix check: [2](#0-1) . Since `strings.HasSuffix` has no boundary awareness, `originHost = "evilexample.com"` passes `strings.HasSuffix(originHost, "example.com")` for an allowlist entry `*.example.com`, despite not being a subdomain. No other check (scheme/port comparisons at lines 172-179) mitigates this, since those only filter scheme/port, not the host structure.

## Impact Explanation
When the check passes, the server reflects the attacker-supplied `Origin` into `Access-Control-Allow-Origin` and sets permissive `Access-Control-Allow-Methods`/`Access-Control-Allow-Headers`: [3](#0-2) . This allows a page hosted on an attacker-controlled domain that merely shares a suffix with (rather than being a true subdomain of) the operator's allowlisted domain to perform authorized-looking cross-origin browser requests against the gateway's user-facing API — a concrete CORS/allowlist-bypass matching the in-scope "allowlist bypass" / "cross-user response corruption" impact category.

## Likelihood Explanation
Exploitation only requires that an operator has configured a wildcard CORS entry (`*.example.com`), a supported and documented configuration, and that a victim's browser sends a request with an `Origin` header controlled by the attacker (e.g., by visiting an attacker-registered domain like `evilexample.com` or `attacker-example.com`). No credentials, roles, or node/operator privileges are needed to trigger the mismatch — it is exercised on every incoming request's `Origin` header via a fully client-controlled input.

## Recommendation
Require a subdomain boundary when doing wildcard suffix matching, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    base := allowedHost[2:]
    if originHost == base || strings.HasSuffix(originHost, "."+base) {
        return true
    }
}
```

## Proof of Concept
1. Configure the gateway with `CORSEnabled: true` and `CORSAllowedOrigins: []string{"*.example.com"}`.
2. Send an HTTP request to the gateway's configured path with header `Origin: https://evilexample.com`.
3. Observe `isAllowedOrigin` returns `true` (since `strings.HasSuffix("evilexample.com", "example.com")` is `true`), and the response contains `Access-Control-Allow-Origin: https://evilexample.com`, despite `evilexample.com` not being a subdomain of `example.com`.

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}
