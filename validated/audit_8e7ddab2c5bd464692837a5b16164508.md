Audit Report

## Title
CORS wildcard-origin allowlist bypass via unanchored suffix match - ([File: core/services/gateway/network/httpserver.go])

## Summary
`isAllowedOrigin` in `core/services/gateway/network/httpserver.go` matches wildcard `CORSAllowedOrigins` entries (e.g. `*.remix.com`) using an unanchored `strings.HasSuffix` check with no subdomain boundary enforcement. This allows any origin hostname that merely ends with the allowed suffix string — e.g. `evilremix.com` matching an intended `*.remix.com` allowlist — to be treated as an allowed CORS origin.

## Finding Description
The wildcard branch of `isAllowedOrigin` strips the `*.` prefix from the configured allowed host and then checks `strings.HasSuffix(originHost, allowedHost)` with no verification that the character preceding the matched suffix is a literal `.` boundary: [1](#0-0) 

Since `allowedHost` after stripping `*.` becomes the bare domain string (e.g. `remix.com`), `strings.HasSuffix("evilremix.com", "remix.com")` returns `true` even though `evilremix.com` is not a subdomain of `remix.com`. This is invoked directly from `handleRequest`, the entry point for every request to the gateway HTTP server, which sets `Access-Control-Allow-Origin` to the raw reflected `Origin` header value whenever `isAllowedOrigin` returns true: [2](#0-1) 

The existing test suite (`core/services/gateway/network/httpserver_test.go`) exercises basic wildcard-match and non-match cases but does not cover the sibling-suffix bypass scenario (e.g. `evilremix.com` vs. `*.remix.com`), so this defect is not caught by current tests: [3](#0-2) [4](#0-3) 

`CORSAllowedOrigins`/wildcard entries are a documented, supported configuration option (used with values such as `https://remix.ethereum.org` in test fixtures and sample configs), so triggering the wildcard code path does not require any unusual or invalid operator behavior — it is the intended, supported feature whose matching logic is broken.

## Impact Explanation
This is a genuine allowlist bypass (matching the in-scope "allowlist bypass" impact category): an attacker who registers a domain sharing the suffix of a configured wildcard pattern (e.g. `evilremix.com` for `*.remix.com`) can have their origin reflected into `Access-Control-Allow-Origin`, enabling cross-origin browser reads of gateway responses from a page hosted on that attacker domain. The practical severity is limited because `Access-Control-Allow-Credentials` is never set by this handler, which restricts the browser's ability to send/read credentialed (cookie-based) requests cross-origin; exploitation for authenticated flows would require the attacker to already possess the Bearer token used in the `Authorization` header, which a same-origin browser storage/JS boundary would normally prevent an unrelated evil domain from obtaining. Nonetheless, the root cause — an unanchored suffix check instead of a proper subdomain boundary check — is a real logic flaw in the allowlist enforcement, independent of any operator misconfiguration.

## Likelihood Explanation
Exploitation requires only that the operator has enabled `CORSEnabled` and configured at least one wildcard entry in `CORSAllowedOrigins` (a supported, documented configuration pattern demonstrated in the codebase's own test suite and sample configs), and that an attacker registers a low-cost domain sharing the suffix string. No special credentials, roles, or host access are needed to trigger the flawed comparison itself; the attacker only needs to make a request with a crafted `Origin` header, or get a browser to do so, to observe the bypass.

## Recommendation
Anchor the wildcard suffix check on a subdomain boundary, e.g. compare against the suffix including a leading dot (`.remix.com`) or verify that the character immediately preceding the matched suffix in `originHost` is `.`, and also allow the bare domain (`remix.com`) as an explicit exact match if desired. Add regression tests for sibling-suffix domains such as `evilremix.com`, `notremix.com`, and `evil-remix.com` against a `*.remix.com` allow entry to ensure they are rejected while `foo.remix.com` continues to match.

## Proof of Concept
1. Configure `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.remix.com"]` on the gateway HTTP server.
2. Send an HTTP request with header `Origin: https://evilremix.com`.
3. Observe that `isAllowedOrigin` returns `true` because `strings.HasSuffix("evilremix.com", "remix.com")` is `true`, and the response includes `Access-Control-Allow-Origin: https://evilremix.com`, `Access-Control-Allow-Methods: GET, POST, OPTIONS`, and `Access-Control-Allow-Headers: Content-Type`, per `handleRequest`.
4. Add a Go unit test analogous to `TestHTTPServer_HandleRequest_CORSEnabled_FromNotAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, but asserting that an origin like `https://evilremix.com` against allowed origin `https://*.remix.com` is currently (incorrectly) accepted, demonstrating the bypass.

```go
func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}
```
