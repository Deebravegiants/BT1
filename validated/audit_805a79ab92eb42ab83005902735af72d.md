### Title
Unbounded/Infinite Loop in `AncestryChain::ancestry` via Attacker-Crafted Cyclic Headers, Executed Before Signature Verification - ([File: modules/consensus/grandpa/primitives/src/justification.rs])

### Summary
`AncestryChain::ancestry` walks a parent-hash chain from `block` back to `base` using a `BTreeMap<Hash, Header>` built entirely from attacker-supplied `unknown_headers` in a submitted GRANDPA consensus proof. The loop has no iteration bound and no cycle detection: it only terminates when `current_hash == base` or a hash is missing from the map. Because the `unknown_headers` are unauthenticated raw structs at this point (their `parent_hash` field is just attacker-chosen bytes, not derived from cryptographic linkage that is checked before this call), an attacker can submit two or more headers whose `parent_hash` fields form a cycle that never reaches `base`, causing the loop to run forever.

### Finding Description
`AncestryChain::ancestry` in `modules/consensus/grandpa/primitives/src/justification.rs`: [1](#0-0) 
walks `current_hash` back through `self.ancestry` (a map keyed by `header.hash()`) following each header's `parent_hash()`, pushing to `route` until `current_hash == base`. There is no bound on the number of iterations and no protection against a cycle: if header A's `parent_hash` equals `hash(B)` and header B's `parent_hash` equals `hash(A)`, and `base` is never one of `hash(A)`/`hash(B)`, the `while current_hash != base` loop never terminates.

Critically, `verify_grandpa_finality_proof` in `modules/consensus/grandpa/verifier/src/lib.rs` calls this ancestry walk **before** the GRANDPA justification signatures are checked: [2](#0-1) 
Specifically, `headers.ancestry(base.hash(), consensus_state.latest_hash)` (line 84) and `headers.ancestry(from, target.hash())` (line 88) both execute using only `finality_proof.unknown_headers` — a raw, attacker-supplied `Vec<H>` with no cryptographic validation of the parent-hash linkage — prior to `justification.verify(...)` at line 91-93. This means an attacker relaying a consensus message does not need any valid GRANDPA signature or authority-set membership to trigger the loop; they only need to construct two or more headers whose declared `parent_hash` fields point to each other, submitted as `unknown_headers` in a `ConsensusMessage`.

This verifier function is reached from the untrusted, unsigned consensus-message-delivery path (`verify_consensus` in `modules/ismp/clients/grandpa/src/consensus.rs`, itself invoked by `pallet-ismp`'s message-handling flow for consensus updates), which any relayer can submit.

### Impact Explanation
Since the Rust `while` loop is unbounded native code executed inside the runtime's `verify_consensus` call — not something metered per-iteration by the pre-declared/benchmarked extrinsic weight — a single malicious consensus message can hang block execution indefinitely. This halts the collator/validator processing that extrinsic, exactly analogous to the referenced Tomcat CWE-835 infinite-loop DoS: an attacker-controlled proof with cyclic/invalid data causes the loop's exit condition to become unreachable, denying availability. This blocks the GRANDPA consensus-update route used to admit new state-machine heights, preventing any further ISMP messages from that source chain from being delivered — "a route unable to deliver messages," which the validation criteria explicitly call out as acceptable impact.

### Likelihood Explanation
High. The attack requires no privileged role, no valid authority signatures, and no prior state — only the ability to submit a `ConsensusMessage` with `unknown_headers` and a syntactically well-formed (but otherwise garbage) justification field, since the vulnerable ancestry walks occur before justification/signature verification. Constructing two headers with mutually-referencing `parent_hash` fields is a trivial encoding operation.

### Recommendation
Bound the ancestry walk with an explicit iteration cap (e.g., `unknown_headers.len() + 1`) or track visited hashes in a `BTreeSet` and abort with an error the moment a hash is revisited before reaching `base`. Additionally, consider validating that `unknown_headers` form an actual injective, acyclic parent-hash chain (e.g., verifying strictly-decreasing block numbers along the walk) before running any ancestry traversal, and/or move authentication (signature/justification checks) ahead of any traversal over unauthenticated header data.

### Proof of Concept
1. Attacker crafts header `H1` with an arbitrary `parent_hash = hash(H2)` and header `H2` with `parent_hash = hash(H1)` (both otherwise well-formed `SubstrateHeader`/`DefaultHeader` values encodable via SCALE).
2. Attacker builds a `FinalityProof { block: hash(H1), unknown_headers: vec![H1, H2, ...], justification: <any SCALE-decodable GrandpaJustification bytes> }` and wraps it in a `ConsensusMessage` targeting the GRANDPA consensus client's `consensus_state_id`.
3. Submits this as an unsigned/relayed consensus message through the normal relayer path into `pallet-ismp`.
4. `verify_consensus` → `verify_grandpa_finality_proof` builds `AncestryChain::new(&finality_proof.unknown_headers)` and calls `headers.ancestry(from, target.hash())` (line 88 of `modules/consensus/grandpa/verifier/src/lib.rs`), which enters `while current_hash != base` in `justification.rs` and loops forever between `hash(H1)` and `hash(H2)`, since `base` (`from`, the trusted `consensus_state.latest_hash`) is never reached — well before the justification signature is ever checked.

Note: I was unable to directly inspect the SCALE `Decode` bound-checking behavior for `Vec<H>` in `FinalityProof::unknown_headers` (whether Substrate's decoder imposes any implicit size cap based on remaining input bytes) — this does not affect the core finding, since a cycle needs only two headers, well within any such bound.

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
