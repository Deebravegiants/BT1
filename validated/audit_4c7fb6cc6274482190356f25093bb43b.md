### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` are trusted from unauthenticated headers while the HMAC only covers the raw body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC of the raw request body, then unconditionally trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` HTTP headers to build the `WebhookMetadata` passed to the app's handler. None of those header values are covered by the HMAC signature, so their authenticity is never verified.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the HMAC over `verifiable_query.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to the signed body: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately constructs `WebhookMetadata` from these unauthenticated header fields, dispatching them to the app's handler as trusted, verified data: [3](#0-2) 

The identity binding that should hold is: `shop header == shop that produced/authorized the signed body`. In this implementation that equality is never checked — only `hmac(raw_body) == expected` is checked, while `shop`, `topic`, `webhook_id`, `api_version` are parsed but never verified. This is exactly the "bytes verified vs. bytes parsed" / "field acted on but not covered by the HMAC" bug class from the reference report (there, the redemption check verified `BUIDL` balance but acted on a different, unverified quantity; here, the HMAC verifies the body but the code acts on unverified header fields).

The gem's own documentation confirms it advertises full authenticity: "This will verify the request did indeed come from Shopify and then call the specified handler," with no caveat that `shop`/`topic`/`webhook_id`/`api_version` are unauthenticated: [4](#0-3) 

### Impact Explanation
Any party that can obtain one genuine, HMAC-signed webhook body for their own shop (any merchant can trivially generate legitimate webhooks for their own store by taking normal store actions) can replay that exact body while substituting the `shop-domain` header to any victim shop domain the app is installed on. Because the HMAC only signs the body, the swapped header passes `HmacValidator.validate` unchanged, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim's shop. In a multi-tenant app that uses `data.shop` to select which tenant's session/database/queue to act on (as shown in the gem's own documented usage example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), this allows an attacker-controlled payload to be attributed to and processed under a victim shop's identity — a cross-tenant data injection primitive. The `topic`, `webhook_id`, and `api_version` are similarly forgeable, allowing the same signed body to be reinterpreted under an arbitrary topic (e.g., replaying a "products/update" body as "app/uninstalled" or other sensitive topics) and to defeat webhook-id-based deduplication.

### Likelihood Explanation
Any user with access to the app (a merchant with the app installed, or anyone able to capture/replay one legitimate webhook HTTP request) can perform this without any credentials, tokens, or privileged access — satisfying the "unprivileged internet user" and "no host-app misuse required" bars, since the vulnerable trust decision (act on unauthenticated headers as verified after only checking the body's HMAC) is made entirely inside this gem's `Registry.process`/`Webhooks::Request`, not by host-app misuse of a documented safe API.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signable payload (or otherwise cryptographically bind them to the body, e.g., include them as part of the canonical string that is signed/verified), so that `HmacValidator.validate` fails if any of these header fields are altered independently of the body. At minimum, document and enforce that `shop`, `topic`, `webhook_id`, and `api_version` must not be treated as verified/tenant-authoritative unless bound to the signature.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the genuine HTTP request, including its valid `X-Shopify-Hmac-Sha256` header (computed by Shopify over the JSON body using the app's real secret).
2. Attacker resends the identical raw body and HMAC header to the app's webhook endpoint, but changes the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com` (and optionally the topic/webhook-id headers).
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged headers unmodified: [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` — it still matches, since the body was untouched: [6](#0-5) 
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built using the forged `shop`/`topic` values and passed to the app handler as though Shopify verified it came from `victim-shop.myshopify.com`: [3](#0-2)

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
