### Title
Webhook `shop-domain` header is not authenticated by the HMAC, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , and `Utils::HmacValidator.validate` computes/verifies the HMAC against that signable string only [2](#0-1) . The `shop` attribute, however, is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header [3](#0-2) , and `Registry.process` forwards this same unauthenticated value as `shop:` into the `WebhookMetadata` passed to the app's handler after only checking the HMAC of the body [4](#0-3) . This mirrors the reported bug class: a field ("shop") is acted upon (used as the tenant identifier for the webhook) while not being covered by the integrity check (HMAC only covers the body).

### Finding Description
The identity binding the gem is supposed to enforce is:
`shop used to attribute/process the webhook == shop that Shopify actually generated the signed payload for`.

In practice this binding does not hold, because:
- The HMAC secret (`Context.api_secret_key`) is a single **per-app** secret shared across every shop that installs the app — it is not shop-specific [5](#0-4) .
- The signature only binds the raw body bytes, never the `shop-domain` header [1](#0-0) .
- `Registry.process` validates the HMAC, then immediately trusts `request.shop` (from the header) as the tenant identity handed to the app's `handler.handle` [4](#0-3) .

Because any shop that has installed the app is a legitimate, unprivileged sender of real Shopify webhooks (any merchant can install a public app or run their own dev store), an attacker who controls Shop A can capture a genuine, correctly HMAC-signed webhook request generated by Shopify for Shop A, then replay it to the app's webhook endpoint with the `shop-domain` header rewritten to Shop B's domain (a victim tenant). The HMAC check still passes, because it only verifies the body was signed by the app's secret — which is true, since Shopify really did sign it (for Shop A). The registry then calls the handler with `shop: "shop-b.myshopify.com"` even though the payload actually originated from, and describes, Shop A.

The documentation itself instructs applications to use `data.shop` directly as the tenant key (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), so this is the gem's own documented, intended usage of the field — not a case where the host app is ignoring documented guidance.

### Impact Explanation
This breaks the identity binding "shop attributed to a webhook == shop that produced it," letting an unprivileged attacker (any shop owner who installed the app) inject webhook events attributed to a victim shop of their choosing. If the host application uses `data.shop` to look up the victim's session/access token (as shown in the gem's own docs and companion `shopify_app` reference patterns) to enrich the webhook, sync data, or update stores keyed by shop domain, an attacker can trigger unauthorized cross-tenant writes/reads or corrupt another merchant's data with attacker-supplied body content, an authentication/tenant-isolation bypass class of vulnerability (cross-tenant access) at the boundary this gem is responsible for authenticating.

### Likelihood Explanation
Exploitation only requires the attacker to control one shop (trivial — a free Shopify developer store), capture one legitimately signed webhook, and resend it with a modified header to the app's public webhook endpoint. No secrets, tokens, or privileged access are required — only the HMAC secret already known to be shared per-app, not per-shop, is at play, and the gem does not incorporate `shop` (or any per-tenant value) into the signed payload.

### Recommendation
Cover the `shop` (and ideally `topic`/`webhook_id`) fields in the HMAC-signable string, or independently verify that the `shop-domain` header corresponds to the shop actually associated with the app's HMAC-secret-derived context/session before trusting `request.shop` downstream. At minimum, `Registry.process`/`Request` should not treat the `shop-domain` header as authenticated data equivalent to information protected by the HMAC.

### Proof of Concept
1. App is installed by attacker's own shop, `attacker-shop.myshopify.com`, and by victim shop `victim-shop.myshopify.com`.
2. Shopify sends the attacker a legitimately signed webhook for `orders/create`:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body computed with shared api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id": 1, "note": "attacker-controlled content"}
   ```
3. Attacker replays this exact body/HMAC to the same endpoint but sets:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Request#hmac` and `Utils::HmacValidator.validate` only check the body against `Context.api_secret_key` [1](#0-0) [6](#0-5)  — the check passes since the body/signature pair is genuinely valid.
5. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` with `shop == "victim-shop.myshopify.com"` [7](#0-6) , causing the host application (following the gem's documented pattern) to process attacker-controlled webhook content as if it originated from the victim shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
