I found a concrete analog. The bug-class ("a field acted on but not covered by the HMAC") maps directly onto how `ShopifyAPI::Webhooks::Request` and `Registry.process` handle inbound webhooks.

Key facts:
- `Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signs the body but not the `shop`, `topic`, `webhook_id`, or `api_version` values, which are all read straight from HTTP headers. [1](#0-0) 
- `Registry.process` validates only that HMAC-over-body, then trusts `request.shop`/`request.topic` unconditionally when dispatching to the handler. [2](#0-1) 
- The signing secret (`Context.api_secret_key`) is the app's single client secret, shared across every shop/tenant that installs the app — it is not shop-specific. [3](#0-2) 

Because the signature is computed over the body only, with a secret shared by all tenants, a signed `(body, hmac)` pair captured from one shop's own legitimate webhook delivery remains valid when replayed with the `shop-domain` (and `topic`/`webhook-id`) headers swapped to point at a different shop. `Registry.process` has no way to detect this since it never binds `shop`/`topic` into the signature check.

### Title
Webhook shop/topic identity not bound to HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`Webhooks::Request#to_signable_string` returns only the raw body, so `Utils::HmacValidator.validate` verifies solely that the body was signed with the app's `api_secret_key`. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values used by `Registry.process` and forwarded to the app's handler via `WebhookMetadata` are taken from unauthenticated headers that are not part of the signed payload.

### Finding Description
`HmacValidator.validate(request)` recomputes an HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac-sha256` header. For `Webhooks::Request`, `to_signable_string` is defined as just `@raw_body`. [4](#0-3) 
The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from headers with no cryptographic binding to the body or the HMAC. [5](#0-4) 

`Registry.process` only asserts `Utils::HmacValidator.validate(request)`, then immediately uses `request.topic`, `request.shop`, and `request.webhook_id` to look up the handler and construct `WebhookMetadata` passed to application code: [2](#0-1) 

Because the HMAC key is the single, app-wide `api_secret_key`/`old_api_secret_key` (not per-shop), any genuinely signed `(raw_body, hmac)` pair — for instance one legitimately delivered to a merchant's own store, which that merchant can freely observe since it is their own inbound traffic — remains cryptographically valid no matter what `shop-domain`/`topic`/`webhook-id` headers accompany it. The equality the code implicitly assumes is:

`hmac_valid(raw_body) == (shop_header identifies the tenant that produced raw_body)`

but this equality does not hold: `hmac_valid(raw_body)` only proves "signed by this app's secret," not "signed for shop X." An unprivileged user who operates their own shop installation of the app can capture one legitimately-signed webhook body and replay it directly to the app's shared webhook endpoint with the `shop-domain` header rewritten to a victim shop, and/or the `topic` header rewritten to a different, more sensitive topic sharing a compatible body shape. `Registry.process` will accept it as authentic and hand it to the host application's handler tagged as coming from the victim shop.

### Impact Explanation
This crosses the multi-tenant boundary the gem is supposed to help enforce: data that the host application believes originated from and is scoped to shop B can actually be attacker-supplied content authored by the operator of shop A. Any app that uses `WebhookMetadata#shop` to attribute writes, side effects, or authorization decisions per-tenant (a normal usage pattern, since that field exists specifically for that purpose) can have its per-tenant isolation subverted — i.e., cross-tenant access/injection, which maps to the Critical impact bucket in scope.

### Likelihood Explanation
Likelihood is Low-Medium: it requires the attacker to control a real shop installation of the target app (to legitimately obtain one signed body/hmac pair) and to be able to POST directly to the app's public webhook endpoint with custom headers (which any internet user can do, since Shopify webhook endpoints are plain HTTP(S) endpoints with no additional caller authentication beyond the HMAC this gem checks). No secret, token, or privileged access is needed beyond being any app-installing merchant.

### Recommendation
Bind the tenant/topic identity into the verified payload instead of trusting unauthenticated headers. Concretely, change `Webhooks::Request#to_signable_string` (or add a secondary check in `Registry.process`) to incorporate `shop`, `topic`, and `webhook_id` into what is verified — e.g., require the handler-visible `shop`/`topic` to be cross-checked against values embedded in `raw_body` where Shopify includes them, or reject processing when the header-derived shop is not one the caller expects to receive webhooks for. At minimum, document clearly that `WebhookMetadata#shop`/`#topic` are not covered by the HMAC guarantee so host apps do not rely on them for tenant-scoping decisions without independent verification (e.g., checking that the shop is a known, currently-installed shop in their own session store).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers/observes a webhook to their own controlled receiver (or captures the request en route to the real app endpoint, which they are entitled to do since it's their own traffic).
2. Attacker records the raw POST body and the `X-Shopify-Hmac-Sha256` header value from that legitimate delivery.
3. Attacker sends a new HTTP POST to the app's public webhook endpoint with the same raw body and HMAC header, but with `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `Utils::HmacValidator.validate` succeeds because it only checks the body against the app-wide secret. [6](#0-5) 
5. `Registry.process` dispatches to the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ...)`, and the host application processes attacker-authored data as if it came from the victim shop. [7](#0-6)
