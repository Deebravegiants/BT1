### Title
Webhook shop identity is not covered by HMAC, allowing cross-tenant shop-domain spoofing on a validated webhook body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw JSON body, while the `shop` (and `topic`/`webhook_id`) values used by the application's webhook handler are read from HTTP headers that are never included in the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#shop` is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, entirely independent of the signable string: [1](#0-0) [2](#0-1) 

`Registry.process` validates only that the HMAC matches the body, then hands the (unauthenticated) `request.shop` straight to the app's handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever checks `verifiable_query.to_signable_string` against the secret — for webhooks that string never contains the shop domain header: [4](#0-3) 

The binding the gem is implicitly asserting to callers is: `shop delivered to handler == shop that produced this signed body`. Because the shop header falls outside the HMAC's coverage, that equality does not hold — the gem authenticates the bytes of the body, but hands the caller a shop value that was never part of what was verified.

### Impact Explanation
A merchant who owns/controls their own shop (an "unprivileged" tenant relative to other merchants of the same app) legitimately receives real webhook deliveries from Shopify for their own shop — genuine body + valid HMAC signed with the app's shared `api_secret_key`. Because the shop-domain header is not part of the signed content, that same valid `(body, hmac)` pair can be replayed to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to name a different, victim shop. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` forwards `request.shop` (now the victim's domain) to the handler as `WebhookMetadata#shop`. Any host application that trusts `data.shop` from the handler to key off session/tenant data (a documented, expected usage of this gem) will process attacker-supplied webhook content under a different tenant's identity — a cross-tenant data-integrity break driven purely by this gem's verification boundary.

### Likelihood Explanation
Exploitation requires: (1) the attacker be a legitimate merchant of the app (so they can trigger and capture a real, validly-signed webhook body for an event they control, e.g. by editing their own store to trigger `products/update`, etc.), and (2) the ability to replay an HTTP POST to the app's public webhook endpoint with a modified header — both are within reach of an "unprivileged" (non-admin, non-credentialed-beyond-being-a-merchant) actor and require no access to `api_secret_key` or any token. The main mitigating factor is that the attacker only controls whichever body content Shopify would send for their own store's events, limiting what payload can be forged for the victim shop, but the tenant/shop binding itself is broken regardless of payload content.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the HMAC-covered signable string for webhook requests, or otherwise independently verify the shop header against a value bound to the signature (e.g., derive/attach shop identity to the payload before signing verification, consistent with how `AuthQuery#to_signable_string` includes `shop` in its OAuth HMAC computation).

### Proof of Concept
1. As a legitimate merchant, install the app and trigger any subscribed webhook topic (e.g. `products/update`) on your own shop `attacker-shop.myshopify.com`; capture the raw POST body and the `x-shopify-hmac-sha256` header sent by Shopify (both are valid/verifiable, since they were genuinely produced by Shopify with the app's secret).
2. Replay that exact captured body and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the (unchanged) HMAC. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from and describes `attacker-shop.myshopify.com`, demonstrating the broken shop-identity binding.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
