### Title
Attacker-inflated vault balances can overflow `U128` multiplication in `calc_take_pnl`, causing swaps/deposits to panic and permanently freezing the pool - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`calc_take_pnl` (called from `process_deposit` and swap paths) multiplies two `U128`-wrapped values derived directly from live SPL token vault balances via `.checked_mul(...).unwrap()`. An unprivileged actor can inflate these vault balances via a direct SPL-token transfer to the `amm_pc_vault`/`amm_coin_vault` accounts, pushing the product of `pool_pc_amount * pool_coin_amount` toward/over `U128::MAX`, causing an `unwrap()` panic that aborts every subsequent deposit/swap that reaches this code path — the same "large-transfer-triggers-overflow-revert" bug class described in the external report for `BondTokenManager`.

### Finding Description
In `calc_take_pnl`, `total_pc_without_take_pnl` and `total_coin_without_take_pnl` are derived from the AMM's actual coin/pc vault SPL balances (`amm_pc_vault.amount`, `amm_coin_vault.amount`), only reduced by `need_take_pnl_pc`/`need_take_pnl_coin`: [1](#0-0) 

These are then converted to `U128` and multiplied without any bound check other than `.unwrap()`: [2](#0-1) 

Both `pool_pc_amount` and `pool_coin_amount` are `U128` values populated from `u64` vault balances, so each can approach `u64::MAX` (~1.8×10^19). `U128::checked_mul` panics via `.unwrap()` if the product exceeds `U128::MAX` (2^128 − 1); two operands each close to `2^64` produce a product close to `2^128`, which overflows. Since SPL token vaults are ordinary token accounts, anyone can call the SPL token program to transfer tokens directly into `amm.coin_vault` or `amm.pc_vault` without any privileged signer — this directly increases `amm_coin_vault.amount`/`amm_pc_vault.amount` read in `process_deposit` (and, through the shared `calc_total_without_take_pnl_no_orderbook` helper, in the swap handlers) with no need to go through swap/deposit instruction logic at all. [3](#0-2) 

This is functionally identical to the reported bug class: an attacker controls a value that feeds into an unchecked/`unwrap`-guarded multiplication, and by transferring a large amount of tokens can force that multiplication to overflow and revert (panic) legitimate calls made by other, benign users.

### Impact Explanation
If reachable, this permanently denies deposits (and any swap path invoking `calc_take_pnl`) for the affected pool, since any transaction that hits the multiplication after the attacker's balance-inflating transfer will panic and abort. This blocks legitimate LPs and swappers from interacting with the pool, a form of freezing of user/LP funds functionality (inability to deposit/exit through the affected instruction) without requiring any privileged access — satisfying the "permanent freezing of user or LP funds" impact bar.

### Likelihood Explanation
Likelihood is **low-to-uncertain** in practice: reaching an overflow requires both `total_pc_without_take_pnl` and `total_coin_without_take_pnl` to simultaneously approach `u64::MAX` (~1.8×10^19 raw units each), which for most real tokens (even with 6-9 decimals) is an enormous, likely economically infeasible amount of tokens to acquire and transfer for both sides of the pool. Additionally, I was not able to fully verify within the available tool budget whether `calc_take_pnl` is actually reachable from the currently-active swap instructions (`process_swap_base_in`/`process_swap_base_out`) versus only from the legacy/orderbook-integrated `process_deposit` path — the swap handlers I inspected (`process_swap_base_in`, `process_swap_base_in_v2`) call `calc_total_without_take_pnl_no_orderbook` but I did not confirm a subsequent call into `calc_take_pnl` within those specific functions before hitting the tool-call limit. This should be verified against the full function bodies before treating this as confirmed-exploitable rather than a theoretical analog.

### Recommendation
Replace `.unwrap()` on `pool_pc_amount.checked_mul(pool_coin_amount)` (and the analogous `calc_pc_amount.checked_mul(calc_coin_amount)`) with a graceful error return (e.g., propagate `AmmError::CalcPnlError` or a new overflow-specific error) instead of panicking, and/or use a wider integer type (`U256`, as already used elsewhere in `math.rs` for `calc_x_power`) for this particular product to avoid overflow entirely given the realistic range of vault balances.

### Proof of Concept
1. Attacker identifies a live Raydium pool with `amm.coin_vault` and `amm.pc_vault` SPL token accounts.
2. Attacker acquires and transfers (via standard `spl_token::transfer`, no program-specific authorization needed) enough coin and pc tokens directly into both vaults so that `amm_coin_vault.amount` and `amm_pc_vault.amount` (as read by `Self::unpack_token_account`) approach `u64::MAX`.
3. Any subsequent call to `process_deposit` computes `total_pc_without_take_pnl`/`total_coin_without_take_pnl` from these inflated balances via `calc_total_without_take_pnl_no_orderbook`, then calls `Self::calc_take_pnl`.
4. Inside `calc_take_pnl`, `pool_pc_amount.checked_mul(pool_coin_amount).unwrap()` panics because the product exceeds `U128::MAX`, aborting the transaction and any future transaction that follows the same path, effectively freezing deposits for the pool. [4](#0-3)

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
