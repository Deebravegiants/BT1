### Title
Stale `Account.owner` grants the previous holder full spending authority after a position-NFT transfer — (File: contracts/controller/src/account.rs)

### Summary

The position NFT (`contracts/position-nft/src/contract.rs`) is a stock OpenZeppelin enumerable token: `transfer`/`approve` move `owner_of` with no callback into the controller. The controller, however, records the owner once in `Account.owner` at mint time (`account.rs` L64–65) and never updates it. The spending-authority check used by `borrow`, `withdraw`, `multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `flash_position` and `migrate_from_blend` — `require_owner_or_delegate` / `is_owner_or_delegate` (`account.rs` L115–140) — compares `caller` against that **stored** `account.owner`, not the live NFT `owner_of`. After an in-scope `position-nft::transfer`, the seller retains full authority over the account and can drain it. This is the on-chain analog of the Jenkins Google Login bug: an authentication decision made against a client-controllable / stale attribute (the minted-in owner field) instead of the authoritative source (actual NFT ownership, which `require_account_owner` at L143–148 does read via `storage::account_owner`).

### Finding Description

- `create_account` sets `account.owner = owner` once and stores it (`account.rs` L64–70); no code path ever rewrites `owner` — the struct is only mutated through its position maps.
- `process_borrow` (`positions/debt.rs` L40–45) and every strategy/withdraw flow authenticate via `require_owner_or_delegate(env, account_id, caller, &account.owner)`, which returns `true` when `caller == owner` (`account.rs` L121) — the stored, pre-transfer address.
- `resolve_seize_receiver` in liquidation (`positions/liquidation/mod.rs` L179–180) uses the same stored-owner check for `SeizeMode::Credit` receivers, so the ex-owner can also capture seizure credits.
- The NFT side is the stock OZ implementation (`contract.rs` L131–133, `NonFungibleToken`/`Enumerable`): a plain `transfer` requires only the token owner's auth and emits no hook to sync controller state.
- Conversely `require_account_owner` (`account.rs` L143–148) checks the live NFT owner, so delegate management and `renew_account` split away from spending authority — confirming the two notions of "owner" are inconsistent by construction.

### Impact Explanation

Theft of user funds / permanent loss of control. After buying or receiving a position NFT, the victim holds the token but not the account: the previous `account.owner` can `borrow` up to the LTV limit to itself (`to` parameter pays any external address, `debt.rs` L45–47) and `withdraw` the collateral, leaving the new owner a hollow NFT burdened with debt. Even absent malice, the new owner cannot move the position — spending authority is permanently bound to the seller, so funds are frozen for the legitimate holder. The two account notions also split: the NFT owner manages delegates while the stale owner spends, so neither party alone has the full expected authority surface.

### Likelihood Explanation

Fully reachable by an unprivileged address: `position-nft` `transfer`/`approve`+`transfer_from` are explicitly in scope, and any secondary-market sale, OTC deal, or wallet migration triggers it. No governance action, oracle movement, or timing race is required — the divergence exists the moment `Base::update` moves the token. The attacker (seller) then calls `controller::borrow`/`withdraw` with `caller = self`, which passes `require_auth` legitimately since they are still `account.owner` in storage.

### Recommendation

Make spending authority derive from the same source as `require_account_owner`: call `storage::account_owner(env, account_id)` (NFT `owner_of`) inside `require_owner_or_delegate` instead of the cached `account.owner`, or resync `account.owner` (and invalidate stored delegates, which are keyed by the old owner per `account.rs` L126 and `set_account_delegate` L261–263) on every position flow. If the cached field is kept for gas reasons, it must be treated as informational only and refreshed from the NFT before any auth decision; delegate lists keyed to a stale owner must be cleared on transfer.

### Proof of Concept

1. Alice calls `controller::supply(caller=Alice, account_id=0, spoke_id=1, assets=[(XLM_key, 10_000e7)])`; controller mints NFT id `N` to Alice and stores `Account { owner: Alice, … }`.
2. Alice calls `position-nft::transfer(from=Alice, to=Mallory_victim_Bob, token_id=N)` — stock OZ path succeeds; controller is never invoked, `Account.owner` remains `Alice`.
3. Alice calls `controller::withdraw(caller=Alice, account_id=N, withdrawals=[(XLM_key, 0)], to=Some(Alice))`. `require_authorized_caller` → `Alice.require_auth()` succeeds; `require_owner_or_delegate` sees `caller == account.owner` (stored) and returns early. The collateral is paid to Alice.
4. Bob's `owner_of(N)` reads Bob, but `controller::withdraw(caller=Bob, …)` reverts `NotAuthorized` — Bob owns a token whose collateral was already extracted by the previous holder. The same sequence works via `borrow` to encumber the account with debt payable to Alice before the NFT sale.
