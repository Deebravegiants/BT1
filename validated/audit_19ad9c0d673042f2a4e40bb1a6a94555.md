## Answer

The claim is valid. This is a real critical vulnerability, though the actual exploitable code lives in `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol` (CASE 2 branch) together with `contracts/Transferer.sol`'s `getBalancesForArray`, rather than in `contracts/types/ITransactHook.sol` (which is just the `afterTransact`/`preTransact` interface and has no bearing on this bug) [1](#0-0) .

### Title
Unprivileged CASE 2 op can drain any ERC1155/ERC721 balance parked at Emporium because `msg.sender` for the raw call is Emporium itself - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 "stateless" branch executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract, so `msg.sender` inside that call is always `address(Emporium)`, not the caller's wallet [2](#0-1) . Because Emporium also implements `onERC1155BatchReceived`/`onERC721Received` unconditionally via `Transferer` [3](#0-2) , and only ERC20/ETH balances are tracked by `getBalancesForArray` [4](#0-3) , any ERC1155/ERC721 tokens that land on Emporium's own address (e.g. from an earlier victim CASE 2 op that mints/transfers such tokens to `msg.sender`) are both untracked by the balance equation and freely extractable by any subsequent unprivileged caller, since `safeBatchTransferFrom(Emporium, attacker, ids, amounts, "")` only requires `msg.sender == from`, which trivially holds because Emporium itself places the call.

### Finding Description
The invariant the protocol implicitly relies on is: *any asset that ends up parked at Emporium after a user's op belongs to that user and can only be moved out under that user's own subsequent authorized op.* This is broken because Emporium has no per-user ledger for anything outside `circomData.erc20TokenAddresses` (ERC20/ETH only).

Code path:
1. Victim's `transact()` selects `externalActionId` routing to `EmporiumUpgradeable.runAction`, with a CASE 2 (`invokeWallet=false`) op whose `endpoint`/`callData` causes an ERC1155 contract to credit token balances to `msg.sender`. Since the low-level call `op.endpoint.call{value: op.value}(op.callData)` at [5](#0-4)  is executed by the Emporium contract itself, any such "recipient = msg.sender" semantics resolve to `address(Emporium)`. Emporium accepts the incoming batch via the inherited stateless `onERC1155BatchReceived` [6](#0-5) .
2. `runAction`'s before/after balance diffing and the resulting `balanceDif`/UTXO equation in `Hinkal.transact` only iterate over `circomData.erc20TokenAddresses`, calling `getERC20OrETHBalance` for each [4](#0-3) , [7](#0-6) . ERC1155/ERC721 balances are never included, so the deposited semi-fungible tokens leave zero trace in `deltaAmountChanges`, `balanceDif`, or `utxoAmount` - they are simply an orphaned raw token balance sitting at `address(Emporium)`.
3. Any unprivileged attacker later submits their own `transact()` with a CASE 2 op: `endpoint = <ERC1155 token>`, `callData = abi.encodeCall(IERC1155.safeBatchTransferFrom, (Emporium, attacker, ids, amounts, ""))`. Because Emporium itself performs `op.endpoint.call(...)`, `msg.sender` observed inside the ERC1155 contract equals `address(Emporium)`, which equals `from`. The standard ERC1155 authorization check `require(from == _msgSender() || isApprovedForAll(from, _msgSender()))` passes with no approval needed. `EmporiumUpgradeable.verifyWallet` and the wallet-selector guard only block `callHinkalWallet`/`doSendToRelay` selectors [8](#0-7) ; nothing restricts the `endpoint`/`callData` chosen for CASE 2 to only affect ERC20/ETH.
4. `onlyAllowedRecipient` only checks that `msg.sender` (the top-level `Hinkal` contract) is whitelisted to call `runAction` [9](#0-8)  - it does not restrict what arbitrary attacker-supplied `op.endpoint`/`op.callData` can do once inside `runAction`.

No proof/circuit constraint, nullifier check, `dimensionsCheck`, or balance-equation check in `HinkalHelper.performHinkalChecks` (only referenced in `contracts/HinkalHelper.sol` and `contracts/Hinkal.sol`) constrains non-ERC20/ETH asset movement performed via CASE 2 raw calls, because the circuit and balance equation are scoped strictly to `circomData.erc20TokenAddresses`.

### Impact Explanation
Any ERC1155 (or ERC721, same mechanism) tokens that ever land on Emporium's address - from a victim's CASE 2 op, a misconfigured protocol call, or dust left after a partial fill - can be stolen in full by any unprivileged party with zero footprint in the shielded-balance accounting. This is direct theft of a victim's assets that were never wrapped into a UTXO/commitment and is repeatable for every future occurrence of such tokens landing at Emporium. This matches the Critical category: direct theft of shielded/in-flight user funds and moving assets a wallet owner never authorized.

### Likelihood Explanation
Preconditions: Emporium must hold nonzero ERC1155 (or ERC721) balance for specific token IDs (achievable whenever any CASE 2 `op` results in tokens being minted/transferred to `msg.sender`, which resolves to Emporium). No special tree state, nullifier, or root is required. Attacker cost is a single ordinary `transact()` call with a self-crafted proof over their own UTXOs (needed only to pass `performHinkalChecks`/gas-fee mechanics), plus knowledge of the token IDs/amounts sitting at Emporium (observable on-chain). This is fully feasible for any EOA and repeatable each time the precondition recurs.

### Recommendation
- Do not allow arbitrary CASE 2 `op.callData` to be executed with Emporium itself as `msg.sender` against attacker-chosen `endpoint` contracts without restricting the ultimate recipient/`from` semantics, or
- Explicitly track and account for non-ERC20 (ERC721/ERC1155) balances touched by CASE 2 ops in the balance-diff equation and mandatorily sweep/UTXO-wrap them at the end of `runAction` (mirroring the ERC20/ETH `handleOut` sweep), so no asset can be left owned by Emporium after a transaction, or
- Restrict CASE 2 `op.endpoint` calls to a per-transaction allow-list bound to the `circomData` token set proven in the circuit, rejecting calls to token contracts not declared in `erc20TokenAddresses`/an equivalent declared-asset list.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, and a mock ERC1155 contract whose `mintBatch(to, ids, amounts)` is callable permissionlessly.
2. Victim executes `transact()` with a CASE 2 `EmporiumOperation` where `endpoint = mockERC1155`, `callData = abi.encodeCall(mockERC1155.mintBatch, (address(emporium), ids, amounts))` (simulating a real protocol crediting `msg.sender`). Assert `mockERC1155.balanceOfBatch([emporium,...], ids) == amounts` after the tx, and assert none of `deltaAmountChanges`, resulting `utxoSet`, or emitted `NewCommitment` events reference these ids/amounts.
3. Attacker (unrelated EOA, no approval from Emporium) executes their own `transact()` with a CASE 2 op: `endpoint = mockERC1155`, `callData = abi.encodeCall(mockERC1155.safeBatchTransferFrom, (address(emporium), attacker, ids, amounts, ""))`.
4. Assert the call succeeds without revert (no `ERC1155: caller is not owner nor approved`), `mockERC1155.balanceOfBatch([attacker,...], ids) == amounts`, `mockERC1155.balanceOfBatch([emporium,...], ids) == 0`, and that the attacker's own `deltaAmountChanges`/`utxoAmount`/`balanceDif` for their transaction show no entry corresponding to this ERC1155 transfer (equality `balanceDif == amountChanges[i] + utxoAmount` in `Hinkal.transact` is satisfied trivially for the unrelated ERC20 tokens listed by the attacker, while the stolen ERC1155 value is completely absent from both sides of the equation).
