Based on my research, the strongest custody-grade analog is a permissionless "migration" function in `coin.move` that can silently overwrite a fungible-asset store's `frozen` state using stale data from a legacy resource — the same bug class as the Lens report (a permissionless batch-migration call that can restore/alter a custody control state — there, `follow`; here, `frozen`).

### Title
Permissionless `migrate_coin_store_to_fungible_store` can unfreeze a victim's primary Fungible Store using stale `CoinStore.frozen` state - (File: `aptos-move/framework/aptos-framework/sources/coin.move`)

### Summary
`coin::migrate_coin_store_to_fungible_store` is a `public entry fun` callable by **any account**, for **any list of target accounts**, with no ownership or authorization check on the target addresses. It calls `maybe_convert_to_fungible_store` for each address, which — if a legacy `CoinStore<CoinType>` exists with a non-zero balance — synchronizes the primary `FungibleStore`'s `frozen` flag to match the legacy `CoinStore.frozen` flag whenever the two differ, via `fungible_asset::set_frozen_flag_internal`. [1](#0-0) [2](#0-1) 

### Finding Description
`maybe_convert_to_fungible_store` moves the `CoinStore<CoinType>` out of storage and, when the coin has value, deposits it into the (possibly newly created) primary fungible store, then unconditionally reconciles frozen status:

```
if (frozen != fungible_asset::is_frozen(store)) {
    fungible_asset::set_frozen_flag_internal(store, frozen)
}
``` [3](#0-2) 

The `frozen` value used here comes from the **legacy `CoinStore` resource**, not from any currently-authorized freeze reference (`TransferRef`/`BurnRef`/`MintRef`). The FA-level freeze authority (e.g. a compliance/security freeze applied directly to the primary store via `fungible_asset::set_frozen_flag` / `primary_fungible_store::set_frozen_flag` through a `TransferRef`) has no relationship enforced with the old `CoinStore.frozen` bit. If an account still holds an un-frozen legacy `CoinStore` with a positive balance (frozen=false) while its primary `FungibleStore` for the paired FA is independently frozen (frozen=true, e.g. by the asset's freeze authority for compliance/security reasons), then **any unprivileged third party** can call `coin::migrate_coin_store_to_fungible_store` on that address and cause the primary store's `frozen` flag to be overwritten to `false`, silently reversing the freeze.

This exactly mirrors the reported bug class: a permissionless "migrate" entry point (`batchMigrateFollows` there, `migrate_coin_store_to_fungible_store` here) that does not respect a blocking/authority state (`isBlocked` there, FA-level `frozen`/freeze authority here) and thereby restores a capability (follow / transfer) that the authorized controller had disabled.

### Impact Explanation
If exploitable, this allows an unprivileged caller to defeat the freeze control on a fungible asset store (custody control tied to live assets), restoring transfer capability to an account that a freeze authority (compliance, security incident response, regulated stablecoin issuer, etc.) intentionally froze. This directly maps to "Unauthorized takeover of... freeze control... tied to live assets" in the Custody Impact Gate. Because `migrate_coin_store_to_fungible_store` takes a `vector<address>` and is a public entry function with zero authorization, the corrupted control field is `FungibleStore.frozen` at the target's primary store address, and the actor triggering it need not be the account owner or the freeze authority.

### Likelihood Explanation
Exploitability depends on a precondition I could not fully confirm from the index in the time available: that an account can simultaneously hold (a) a legacy, non-frozen `CoinStore<CoinType>` with a positive balance, and (b) a frozen primary `FungibleStore` for the paired FA metadata — i.e., that the freeze authority's `set_frozen_flag`/`TransferRef` path and the legacy `CoinStore.frozen` path can diverge in practice for a given account/CoinType pairing. I was unable to retrieve the full implementation of `coin::freeze_coin_store`/`unfreeze_coin_store` and how `FreezeCapability<CoinType>` interacts with paired-FA freezing before running out of tool budget, so I cannot certify that divergence is reachable on mainnet-relevant coins (e.g., whether all freeze operations for paired coins are funneled through a single code path that keeps both flags in lockstep). This is the key unresolved link in the chain.

### Recommendation
- Do not let `maybe_convert_to_fungible_store` silently overwrite the FA store's frozen flag from the legacy `CoinStore.frozen` value. At minimum, only allow the transition from unfrozen→frozen automatically (never automatically unfreeze), or require the caller to hold the relevant `FreezeCapability`/`TransferRef` to change frozen state.
- Audit `coin::freeze_coin_store`/`unfreeze_coin_store` and any FA-level freeze paths for the same `CoinType` to confirm whether `CoinStore.frozen` and `FungibleStore.frozen` can actually diverge for a live, paired coin; if they can, this is a live custody-freeze bypass.

### Proof of Concept
Not fully constructable from the index alone; would require: (1) a `CoinType` paired with a Fungible Asset via `coin::create_pairing`, (2) freezing the primary fungible store for a specific holder directly via the FA-level `TransferRef`/`set_frozen_flag` path while that holder's legacy `CoinStore<CoinType>` remains unfrozen with `coin.value > 0`, then (3) any third party calling `coin::migrate_coin_store_to_fungible_store<CoinType>(vector[victim])` and observing `fungible_asset::is_frozen(primary_store)` flip from `true` to `false`. Because step (2)'s reachability was not fully verified against `freeze_coin_store`'s implementation, this should be validated with a full Devin session that has direct repository/test access before treating this as confirmed.

*Given the unresolved precondition noted in Likelihood Explanation, this should be treated as a candidate requiring further verification rather than a fully confirmed vulnerability.*

    fun maybe_convert_to_fungible_store<CoinType>(
        account: address
    ) acquires CoinStore, CoinConversionMap, CoinInfo {
        if (exists<CoinStore<CoinType>>(account)) {
            let CoinStore<CoinType> { coin, frozen, deposit_events, withdraw_events } =
                move_from<CoinStore<CoinType>>(account);
            if (is_coin_initialized<CoinType>() && coin.value > 0) {
                let metadata = ensure_paired_metadata<CoinType>();
                let store =
                    primary_fungible_store::ensure_primary_store_exists(
                        account, metadata
                    );

                event::emit(
                    CoinStoreDeletion {
                        coin_type: type_info::type_name<CoinType>(),
                        event_handle_creation_address: guid::creator_address(
                            event::guid(&deposit_events)
                        ),
                        deleted_deposit_event_handle_creation_number: guid::creation_num(
                            event::guid(&deposit_events)
                        ),
                        deleted_withdraw_event_handle_creation_number: guid::creation_num(
                            event::guid(&withdraw_events)
                        )
                    }
                );

                if (coin.value == 0) {
                    destroy_zero(coin);
                } else {
                    fungible_asset::unchecked_deposit_with_no_events(
                        store.object_address(),
                        coin_to_fungible_asset(coin)
                    );
                };

                // Note:
                // It is possible the primary fungible store may already exist before this function call.
                // In this case, if the account owns a frozen CoinStore and an unfrozen primary fungible store, this
                // function would convert and deposit the rest coin into the primary store and freeze it to make the
                // `frozen` semantic as consistent as possible.
                if (frozen != fungible_asset::is_frozen(store)) {
                    fungible_asset::set_frozen_flag_internal(store, frozen);
                }
            } else {
                destroy_zero(coin);
            };
            event::destroy_handle(deposit_events);
            event::destroy_handle(withdraw_events);
        };
    }
