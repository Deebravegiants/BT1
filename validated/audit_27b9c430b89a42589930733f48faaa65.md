## Title
Webhook `shop`/`topic`/`webhook_id` identity spoofing — HMAC only signs the raw body, not the shop header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are all read verbatim from unauthenticated HTTP headers. `ShopifyAPI::Utils::HmacValidator.validate` (invoked by `Registry.process`) only proves that the body bytes were signed with the app's secret — it never binds the `shop-domain` header to that signature. An attacker who can obtain any single valid `(raw_body, hmac)` pair (trivially available by installing the target app on an attacker-owned/dev store and letting it deliver one legitimate webhook) can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value. The request still passes `HmacValidator.validate`, and `Registry.process` hands the handler a `WebhookMetadata` whose `shop` field is the attacker-chosen, unauthenticated value.

### Finding Description
The identity binding that should hold is: `shop used by the handler == shop actually authenticated by the HMAC`. In this gem that equality does not hold.

- `Registry#process` validates the request purely on body content: [1](#0-0) [2](#0-1) 

- `Request#to_signable_string` only returns `@raw_body`, never the headers: [3](#0-2) 

- `Request#shop`, `#topic`, `#webhook_id`, `#api_version` are read straight from attacker-controlled HTTP headers with no cross-check against the signed body: [4](#0-3) 

- `HmacValidator.validate` computes/compares the signature only over `verifiable_query.to_signable_string` (i.e. the body), so it never touches `shop`: [5](#0-4) 

- The (unauthenticated) `shop` header value is then handed to the app's webhook handler as if it were trusted, alongside the (authenticated) body: [6](#0-5) 

Because `shop` is never part of the HMAC input, "HMAC valid" only proves "this exact body byte-string was signed by the app's secret at some point" — it says nothing about which shop the request is claiming to be from. Any party in possession of one legitimate `(body, hmac)` pair (obtainable without any privileged credential — just install the app on any store, including a free/dev store the attacker controls) can forge the shop attribution for that payload.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): a webhook handler that uses `WebhookMetadata#shop` to select which tenant's records to update/create (a very common and gem-endorsed pattern, since `Registry.process` explicitly supplies `shop` to the handler as an authenticated field) can be made to apply attacker-supplied webhook body content under a victim shop's identity. This matches the "cross-tenant access" Critical impact category, since it lets an unprivileged internet user cause the app to process data as though it originated from a shop the attacker does not own, purely by manipulating a header that is outside the cryptographic envelope.

### Likelihood Explanation
Exploitation requires no leaked secrets, no access token, and no privileged account: an attacker only needs (a) the ability to send an HTTP request to the app's public webhook endpoint, and (b) one valid `(body, hmac)` sample, which is freely obtainable by installing the app on an attacker-controlled development/trial store and capturing any webhook delivery the app itself triggers. The header can then be freely rewritten before replay since it is never re-validated against the signature.

### Recommendation
Bind `shop` (and ideally `topic`) into the signed material, or otherwise verify it independently against the current active session/shop the app already has on file for that `webhook_id`/topic combination, before trusting it in `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must be revalidated by the consuming application before being used for tenant-scoped operations, rather than presenting it as a first-class field returned from HMAC-validated `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own (free/dev) store `attacker.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the exact `raw_body` and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker replays that exact body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the HMAC — this passes because the body/HMAC pair is genuinely valid. [7](#0-6) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's own order data>, ...)` and, if it uses `shop` to pick the tenant record to update, corrupts/impersonates data belonging to `victim-shop.myshopify.com`. [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
