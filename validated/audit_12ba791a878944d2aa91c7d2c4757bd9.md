### Title
Webhook `shop` (and `topic`) identity is trusted from unauthenticated headers while the HMAC signature only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable material solely from the raw HTTP body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to dispatch the webhook to a handler are read directly from HTTP headers that are never included in the HMAC computation. This breaks the intended binding `HMAC(secret, signed_bytes) == shop_used_for_dispatch`, mirroring the report's bug class of "verifying one field while acting on another, unbound field."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are parsed straight from headers, with no cryptographic linkage to the body or its HMAC: [2](#0-1) 

`Registry.process` validates only the body's HMAC, then dispatches to the handler using the unauthenticated header-derived `shop`: [3](#0-2) 

`HmacValidator.validate` confirms only that `verifiable_query.to_signable_string` (i.e., the raw body) matches the signature — it says nothing about which shop, topic, or webhook_id header accompanied that body: [4](#0-3) 

The equality that should hold is: `bytes verified by HMAC == bytes the app trusts as the tenant identity (shop)`. Here, the bytes verified are `@raw_body` only, while the bytes the app trusts for tenant routing (`request.shop`) are unauthenticated header bytes — the binding is broken.

### Impact Explanation
Any unprivileged internet user who is a legitimate merchant on their own shop (and can therefore receive a genuinely Shopify-signed webhook delivery to their own registered endpoint) can capture one valid `(raw_body, hmac)` pair, then resend a raw POST to the app's webhook endpoint with the same body/HMAC but with the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header swapped to a victim shop. Because `Utils::HmacValidator.validate` only checks the body, the request is accepted as valid, and `Registry.process` calls `handler.handle` with `shop: request.shop` set to the victim's domain paired with attacker-controlled body content. If the consuming app trusts this `shop` field to select which tenant's local records to update (the documented purpose of the `shop` field in `WebhookMetadata`), this enables cross-tenant data confusion/injection without ever needing the app's `client_secret`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Requires only that the attacker operate their own shop with the target app installed (an "unprivileged internet user" relative to other merchants) so they can capture a legitimate webhook delivery, then craft a raw HTTP request replaying the body/HMAC with a modified `shop-domain` header. No secrets, tokens, or elevated access are needed — only the webhook endpoint's public URL and one intercepted delivery.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the body (e.g., verify the shop against a value obtained independently of the header, such as looking up the registered app/shop pairing rather than trusting the header verbatim). At minimum, document clearly that `request.shop`/`request.topic` are not covered by the HMAC and must not be trusted for tenant routing without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the raw POST body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed with the app's secret.
2. Attacker sends a new POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Request.new` parses headers successfully (all required headers present) — see the header-presence check: [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only re-hashes `@raw_body` (unchanged) — see `to_signable_string`.
5. The handler is invoked as `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...))`, so the app processes attacker-controlled body content as if it originated from `victim-shop.myshopify.com`.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end
