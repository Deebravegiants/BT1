### Title
Multi-wavelength extension binds IR eye-camera frames to `target_left_eye` without eye-side revalidation, allowing wrong-eye imagery to be stored as identification data - ([File: src/plans/biometric_capture/multi_wavelength.rs])

### Summary
`multi_wavelength.rs::perform_multi_wavelength` disables `ir_net` before switching the IR LED wavelength and capturing extra 940nm/740nm frames, then labels whichever frame arrives next purely by the static `target_left_eye` value captured at the start of the extension, with no re-validation of which eye is actually in frame. This is different from the normal capture path in `biometric_capture/mod.rs`, which explicitly validates `estimate.perceived_side` against `target_left_eye` before accepting a frame.

### Finding Description
In `State::ExtraWavelength` ( [1](#0-0) ), `target_left_eye` is fixed once when `perform_multi_wavelength` starts, from `self.biometric_capture.target_left_eye` ( [2](#0-1) ).

`handle_ir_eye_camera` for this state assigns every incoming IR frame directly to a slot (`left_940nm`/`left_740nm`/`right_940nm`/`right_740nm`) chosen solely by this fixed flag - there is no per-frame check of frame content or eye identity: [3](#0-2) .

Crucially, `handle_ir_net` for `ExtraWavelength` is a no-op (`Ok(BrokerFlow::Continue)`), and `ir_net` itself is disabled for the whole extension ( [4](#0-3)  and [5](#0-4) ). This is the exact `perceived_side` cross-check that the normal biometric-capture path performs and relies on for eye-binding integrity: [6](#0-5) .

Unlike the other extensions (`mirror_sweep.rs`, `focus_sweep.rs`, `overcapture.rs`), `multi_wavelength.rs` does **not** call `orb.disable_mirror()` or `orb.disable_eye_tracker()` - only `eye_pid_controller` and `ir_auto_focus` are disabled ( [5](#0-4) ). The eye tracker keeps steering the mirror based on RGB-camera-derived eye coordinates, but only over a `400ms` (`AUTO_EXPOSURE_WAIT_TIME`) settle window per wavelength switch ( [7](#0-6) ). If the signup subject physically repositions during this window (e.g., between the 940nm and 740nm captures, or during the wait after `set_ir_wavelength`), a frame captured under a still-transitioning mirror aim/exposure can depict the other eye or off-target imagery, yet gets unconditionally written into the slot for the eye that was originally targeted, since no `ir_net` perceived-side check exists in this code path to catch the mismatch.

The mislabeled frame is merged into the final `Capture` ( [8](#0-7) ), stored/encrypted via `save_identification_images_impl` ( [9](#0-8) ), and included in `IdentificationImages` referenced by the debug report / signup upload ( [10](#0-9) ).

### Impact Explanation
This produces a wrong-identity/eye-binding violation confined to the auxiliary 940nm/740nm identification images used by the `MultiWavelength` signup extension (activated via `qr_scan::user::SignupMode::MultiWavelength`, [11](#0-10) ). These auxiliary wavelength frames (used for additional per-side anti-spoof/texture analysis, per the module doc [12](#0-11) ) can end up mismatched to the labeled eye side without any software-side detection, since the only eye-binding check (`ir_net` perceived-side) that exists elsewhere in the codebase is deliberately skipped here. The primary 850nm identification image and its iris signature remain protected by the standard `handle_ir_net` perceived-side check in the normal capture path, limiting the blast radius to the auxiliary wavelength images and any downstream analysis (e.g. liveness/spoof heuristics) that assumes same-eye consistency across wavelengths for a given signup.

### Likelihood Explanation
Exploitability requires only the signup subject's own physical movement, precisely timed within a ~400ms window between an IR LED wavelength switch and frame capture during the `MultiWavelength` signup extension - no privileged access, tampering, or social engineering needed. This is fully under the control of an unprivileged signup participant. Reliability depends on precise timing of eye/head movement relative to LED and camera pipeline latency, which is a nontrivial but plausible timing attack for a motivated participant, especially given the fixed and generous 400ms auto-exposure wait window.

### Recommendation
Re-enable `ir_net` (or an equivalent lightweight eye-side classifier) during the `ExtraWavelength` state and validate `perceived_side` against the stored `target_left_eye` before assigning a frame to a slot, mirroring the check already performed in `biometric_capture/mod.rs::handle_ir_net`. Alternatively, disable `mirror`/`eye_tracker` during the multi-wavelength window (as done in `mirror_sweep.rs`/`focus_sweep.rs`/`overcapture.rs`) and/or discard frames captured within a debounce interval after `set_ir_wavelength` until eye-side identity has been reconfirmed.

### Proof of Concept

Simulate two `port::Output<camera::ir::Sensor>` frames delivered to `handle_ir_eye_camera`: first tag frame content/metadata as "left eye" content, second (arriving within the 400ms window, simulating late mirror settle) tag as "right eye" content (e.g., via a fake `camera::ir::Frame` carrying a marker or via mocking `ir_net::EstimateOutput::perceived_side = Some(1)` if fed through `ir_net`).
3. Assert that today, `self.left_940nm` is overwritten with the "right eye" frame with no rejection or error (`slot = Some(output.value)` unconditionally) - demonstrating the missing validation.
4. Expected fix behavior: the second frame should be rejected/skipped (i.e., `left_940nm` should retain the first, correctly-sided frame, or capture should be flagged) once a `perceived_side` check analogous to `biometric_capture/mod.rs` lines 226-234 is added to the `ExtraWavelength` handling path.
