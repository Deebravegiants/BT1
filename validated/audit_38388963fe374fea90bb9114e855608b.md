### Title
Token exchange accepts non-admin session tokens (missing `iss`/audience-context binding) - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` trusts the `dest` claim of *any* validly-signed Shopify session token to determine which shop receives the app's `client_id`/`client_secret` and to be upgraded into a full online/offline **admin** access token. It never checks that the token was actually issued as an *admin* session token (`iss` ending in `/admin`), even though `ShopifyAPI::Auth::JwtPayload` already computes that fact internally via the private `admin_session_token?` method and uses it elsewhere (to gate `shopify_user_id`).

### Finding Description
`JwtPayload#initialize` decodes and signature-verifies the JWT and only checks `aud == Context.api_key` [1](#0-0) . It exposes `shop` (derived from `dest`) publicly, but the context-binding check `admin_session_token?` (`iss.end_with?("/admin")`) is private and only used to compute `shopify_user_id` [2](#0-1) [3](#0-2) .

`TokenExchange.exchange_token` takes the raw `dest_shop = jwt_payload.shop` and immediately uses it to build the OAuth token-exchange request, sending the app's `client_secret` and requesting an **admin** access token (online or offline) for that shop, without ever checking `jwt_payload` came from an admin session context: [4](#0-3) .

Session tokens issued by App Bridge for non-admin execution contexts (e.g. Checkout UI Extensions or Customer Account UI Extensions) are signed with the same shared secret and pass the exact same signature/`aud` checks — this is demonstrated by the library's own test fixture for a "checkout UI extension" JWT payload, whose `iss` is `https://.../checkouts` rather than `.../admin` [5](#0-4) . Nothing in `exchange_token` distinguishes such a token from a true admin session token before using it to mint a full admin access token — the equality that should be enforced, `token.iss context == "/admin"`, is never checked, so the binding "token issued for admin surface" ⇔ "token usable to exchange for admin API access" is broken.

### Impact Explanation
If an app is loaded across multiple embedded surfaces (main admin app, checkout UI extension, customer account UI extension) and any code path in the app forwards a non-admin-context session token to `TokenExchange.exchange_token` (directly, or because a compromised/malicious extension component posts its session token to the app's token-exchange endpoint instead of/along with the intended admin token), the gem will silently accept it, extract the `shop` from its `dest` claim, and exchange it for a genuine online/offline **admin** access token — an elevation from an extension-scoped token to full merchant admin API access. This matches the "scope or expiry check bypass" High-impact category: a token that should only assert identity in a restricted, non-admin context is treated as equivalent to an admin session token, and the library performs no check to prevent that escalation.

### Likelihood Explanation
Exploitation requires that the host application (or an attacker-influenced input into the host application, e.g. a script running inside a Checkout/Customer-Account UI extension iframe under the attacker's control, or extension code compromised via supply-chain/XSS) supplies a non-admin session token to the `exchange_token` API. The gem provides no primitive to reject such tokens and no documentation flags this distinction as the caller's responsibility to check (the `admin_session_token?` helper that would allow this is `private`), so any caller relying on the gem's validation to be complete is unprotected. Likelihood is Medium: it depends on app architecture forwarding tokens from multiple surfaces, but the gem's own test suite for `JwtPayload` demonstrates that non-admin ("checkouts") tokens are a normal, expected artifact the library already anticipates receiving.

### Recommendation
In `TokenExchange.exchange_token`, after constructing `jwt_payload`, explicitly assert the token was issued for the admin surface (e.g. expose and check a public `admin_session_token?`/`iss` validation, raising `Errors::InvalidJwtTokenError` if the `iss` does not correspond to `"https://#{dest_shop}/admin"`) before using `dest_shop` to request an access token from Shopify.

### Proof of Concept
1. App is embedded and exposes both the main admin UI and a Checkout UI Extension for the same `client_id`.
2. Checkout UI Extension surface receives a valid App Bridge session token whose `iss` is `https://{shop}/checkouts` (per the JWT structure demonstrated in `test/auth/jwt_payload_test.rb` lines 23-32), not `/admin`.
3. This token is sent (via a compromised/attacker-controlled extension script, or by a backend bug that forwards whatever session token it receives) to the app's token-exchange endpoint, which calls:
   ```ruby
   ShopifyAPI::Auth::TokenExchange.exchange_token(
     session_token: checkout_extension_token,
     requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
   )
   ```
4. `JwtPayload.new` succeeds (signature + `aud` valid); `exchange_token` proceeds, uses `dest_shop`, and returns a full offline admin `Session` with `access_token` for that shop — despite the original token never having been an admin-context session token [4](#0-3) .
