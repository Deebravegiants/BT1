Confirmed: `process_withdraw` directly checks `min_coin_amount` and `min_pc_amount` against the actual computed output amounts [1](#0-0) , giving withdrawals a genuine output-slippage guarantee. `process_deposit` has no equivalent guarantee on the LP tokens actually minted.

### Title
Missing minimum-LP-out check in `process_deposit` allows sandwich attacks to reduce minted LP for a fixed deposit amount - (File: `program/src/processor.rs`)

### Summary
`process_deposit` lets a depositor fix one side of the deposit (`max_coin_amount` when `base_side == 0`, or `max_pc_amount` when `base_side == 1`) and only bounds the *other* token amount via `max_coin_amount`/`max_pc_amount` and an optional `other_amount_min` [2](#0-1) . The number of LP tokens minted, `mint_lp_amount`, is computed from the fixed side divided by the pool's *current* reserve, scaled by the current LP supply [3](#0-2) [4](#0-3) . There is no check that `mint_lp_amount` meets any user-specified minimum, so an attacker who shifts the pool's reserve ratio immediately before the victim's deposit executes can cause the victim to receive materially fewer LP tokens for the same fixed input, without necessarily tripping the `other_amount_min`/`max_*_amount` bounds (and `other_amount_min` is optional and can be `None` entirely) [5](#0-4) .

### Finding Description
For `base_side == 0` (fixed coin amount):
- `deduct_coin_amount = deposit.max_coin_amount` (fixed, chosen by the user ahead of time).
- `deduct_pc_amount` is derived from the *current* reserve ratio via `exchange_coin_to_pc` [6](#0-5) .
- `mint_lp_amount = deduct_coin_amount / total_coin_without_take_pnl * amm.lp_amount` (via `InvariantPool::exchange_token_to_pool`) [3](#0-2) .

Because `deduct_coin_amount` is fixed but `total_coin_without_take_pnl` (the coin reserve) is read live at execution time, `mint_lp_amount` is inversely proportional to whatever the coin reserve happens to be when the deposit instruction actually executes. An attacker can submit a swap instruction immediately before the victim's `Deposit` instruction (same block/bundle, or simply front-running in the mempool/leader schedule) that increases `total_coin_without_take_pnl` by swapping the coin token into the pool. This:
- Decreases the required `deduct_pc_amount` (since coin got relatively more abundant), which can easily stay within `[other_amount_min, max_pc_amount]` — especially since `other_amount_min` is `Option<u64>` and can be omitted, or set loosely.
- Simultaneously and independently decreases `mint_lp_amount` for the same fixed `deduct_coin_amount`, because the denominator `total_coin_without_take_pnl` used in the pool-share calculation has grown.

This is structurally the same root cause as the referenced Velocimeter Sherlock finding: a fixed deposit amount is matched against spot (manipulable) reserves to compute the paired amount and the resulting share/LP output, and the protocol only guards the paired-token amount's bounds, not the actual minted LP output. The `Deposit` instruction is reachable by any unprivileged caller with attacker-chosen accounts/data, and the pool reserves can be freely moved by any of the four public swap instructions (`SwapBaseIn`, `SwapBaseOut`, `SwapBaseInV2`, `SwapBaseOutV2`) beforehand, all without any privileged signer.

By contrast, `process_withdraw` explicitly checks the computed `coin_amount`/`pc_amount` outputs against `min_coin_amount`/`min_pc_amount` [1](#0-0) , showing the withdraw path has proper output-side slippage protection while the deposit path lacks the analogous protection on `mint_lp_amount`.

### Impact Explanation
A depositor can be sandwiched so that they receive substantially fewer LP tokens than the pool's current price/ratio should entitle them to, while still transferring their full intended token amounts into the pool. This is a direct loss of value for LPs interacting with the pool, and is exploitable purely by an unprivileged actor issuing a swap transaction ahead of the victim's deposit — no privileged role, leaked key, or off-chain component is required. This qualifies as a Medium/High severity value-extraction bug against LP depositors.

### Likelihood Explanation
Exploitability only requires ordering control over transactions relative to the victim's deposit (a classic sandwich pattern achievable by any searcher/attacker who can submit a swap transaction that lands right before the victim's `Deposit` instruction), and does not require any special permissions, account ownership, or protocol misconfiguration. Any pool with reasonable trading activity and a depositor who does not set very tight `other_amount_min`/`max_pc_amount` bounds (or does not set `other_amount_min` at all, since it's optional) is at risk.

### Recommendation
Add an explicit, mandatory minimum-LP-out parameter to `DepositInstruction` (e.g. `min_lp_amount`) and enforce it in `process_deposit` against the computed `mint_lp_amount`, mirroring the `min_coin_amount`/`min_pc_amount` checks already present in `process_withdraw`. Alternatively/additionally, make `other_amount_min` mandatory rather than `Option<u64>` so deposits cannot be submitted with zero slippage protection.
