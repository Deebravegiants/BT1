## Analysis

The reported bug class (M-09) is a "checked value not enforced consistently" pattern — a loop increments its guard variable only inside a conditional branch, causing state used later to diverge from state that was validated. The closest analog in this gem's in-scope code is a similar "verified vs. used" mismatch in webhook processing: the **HMAC signature only covers the raw request body**, while the **`shop` identifier acted upon by the handler is taken from an unauthenticated HTTP header** and is never itself covered by the signature. [1](#0-0) [2](#0-1) [3](#0-2) 

`Request#hmac` decodes the `shopify-hmac-sha256` (or `x-shopify-hmac-sha256`) header, and `Request#to_signable_string` returns only `@raw_body`. `Registry.process` validates this HMAC via `Utils::HmacValidator.validate(request)` [4](#0-3)  and, once validated, immediately trusts `request.shop` — which is read straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header [5](#0-4)  — passing it into `WebhookMetadata` for the app's handler.

`HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it against the header-supplied signature [6](#0-5) . Since `to_signable_string` for `Webhooks::Request` is only the raw body, the equality the gem actually proves is:

`HMAC(secret, body) == signature`

but the equality the gem *implies* is proven (by packaging `shop` alongside the "validated" request and handing it to the app) is:

`shop_header == shop_that_produced_this_body`

These are not the same thing. Anyone who has received one legitimate webhook delivery (e.g. by installing the app on their own test store) possesses a `(body, hmac)` pair that is valid forever for that body under the app's secret. They can then replay that exact body to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` (it never inspects the shop header), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop domain, alongside the replayed (legitimate) body content.

This breaks the intended binding "the `shop` field handed to the handler is the shop that actually sent this data" and can enable cross-tenant confusion in any host application that relies on `WebhookMetadata#shop`/`Request#shop` (as returned by this gem's own public API) to select which tenant's data/session to act on — exactly the kind of unprivileged, credential-free identity-binding break called out in the prompt (field acted upon but not covered by the HMAC).

### Title
Webhook `shop` field is not covered by the HMAC, allowing cross-tenant shop-domain spoofing via body replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw webhook body [2](#0-1) , while `Request#shop` is read verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header [5](#0-4) , a value that is never included in the signed payload. `Utils::HmacValidator.validate` only checks the body-derived signature [7](#0-6) . `Webhooks::Registry.process` treats a validated HMAC as authorization to trust the entire request, including the header-sourced `shop`, and forwards it to the app's handler via `WebhookMetadata` [3](#0-2) .

### Impact Explanation
An unprivileged internet user who has obtained one legitimate `(body, hmac)` pair (e.g. from a webhook fired by their own store's installation of the app) can replay the identical body to the app's webhook endpoint while setting an arbitrary `shopify-shop-domain` header. The HMAC check still passes because it never examines that header. The app's handler receives `WebhookMetadata#shop` claiming to be a different (victim) merchant, while acting on attacker-supplied/replayed body data — a cross-tenant identity binding break exposed directly through this gem's own webhook-processing API.

### Likelihood Explanation
Requires only the ability to receive one webhook for any shop that has (or that the attacker sets up to have) the app installed, plus the ability to send an arbitrary HTTP request with attacker-chosen headers to the app's public webhook URL — no access token, secret, or privileged account is needed.

### Recommendation
Bind the trusted shop identity into the signed material, or otherwise cryptographically tie the `shop` header to the signature — e.g., include the shop domain (and/or webhook id) in `to_signable_string`, or require host applications to cross-check `request.shop` against the shop that is expected to have triggered that specific `webhook_id`/topic before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Install the target app on an attacker-controlled development store to receive one legitimate webhook delivery; capture the raw body and the `x-shopify-hmac-sha256` header value.
2. Replay an HTTP POST to the app's webhook endpoint using the exact captured body and HMAC header, but set `x-shopify-shop-domain` to a victim shop's domain.
3. `Utils::HmacValidator.validate` returns `true` because it only verifies `HMAC(secret, body)`; `Registry.process` invokes the handler with `WebhookMetadata#shop` set to the victim domain, demonstrating the shop field is unauthenticated relative to the signature that gates processing.
