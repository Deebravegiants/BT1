Confirmed root cause: in `Processor::process_swap_base_out`, `Calculator::swap_token_amount_base_out` is invoked with attacker-supplied `swap.amount_out` **before** the corresponding `amount_out >= total_*_without_take_pnl` sufficiency check is performed.

### Title
Unchecked-subtraction panic in `SwapBaseOut`/`SwapBaseOutV2` lets an attacker-supplied `amount_out` abort the pool transaction (transaction-level DoS) - (File: program/src/math.rs)

### Summary
`process_swap_base_out` (and `process_swap_base_out_v2`) calls `Calculator::swap_token_amount_base_out(swap.amount_out, total_pc_without_take_pnl, total_coin_without_take_pnl, swap_direction)` at [1](#0-0)  before the `if swap.amount_out >= total_pc_without_take_pnl { return Err(InsufficientFunds) }` / `total_coin_without_take_pnl` guard, which only runs later at [2](#0-1) . Inside `swap_token_amount_base_out`, the denominator is computed as `total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` (or `total_coin_without_take_pnl.checked_sub(amount_out).unwrap()` for the reverse direction) at [3](#0-2) .

### Finding Description
`SwapInstructionBaseOut.amount_out` is a fully attacker-controlled `u64` from instruction data, unpacked at [4](#0-3) . Any unprivileged user can call `SwapBaseOut` (or `SwapBaseOutV2`) with `amount_out` set equal to or larger than the pool's current `total_pc_without_take_pnl` (or `total_coin_without_take_pnl`). Because the arithmetic in `swap_token_amount_base_out` runs before the sufficiency check that would otherwise reject such a request with a clean `AmmError::InsufficientFunds`, `checked_sub(amount_out)` returns `None` and the subsequent `.unwrap()` panics. On Solana this manifests as the transaction failing with a program panic instead of a graceful `ProgramError`, and — more importantly — it demonstrates that the ordering of the check is wrong: the "safety net" (`InsufficientFunds`) exists but is unreachable for the exact values that need it, since the panic fires first. This matches the CVE's bug class: a routine, attacker-reachable input value causes an out-of-bounds/precondition-violating internal computation that hits an assert (here, Rust's arithmetic `unwrap`/overflow-panic), producing a DoS rather than a controlled error path.

### Impact Explanation
Every call is a single transaction from an unprivileged swapper with fully attacker-chosen instruction data (`amount_out`), reachable through the public `SwapBaseOut`/`SwapBaseOutV2` instructions with no signer other than the caller. While the failing transaction itself simply aborts (no funds move, since token transfers happen after the panic point), this is exactly the analog to the referenced CVE class: a malformed/edge-case but syntactically valid request from an unprivileged party crashes internal accounting logic via an unchecked precondition instead of returning a typed error. It is a code-quality/robustness defect that removes the intended `InsufficientFunds` guard's effectiveness for this instruction and could compound with other logic (e.g., off-chain simulators, downstream integrators, or bots that rely on the program returning a normal `ProgramError` instead of panicking) though it does not, by itself, cause fund loss or pool insolvency.

### Likelihood Explanation
High likelihood of being triggered accidentally (e.g., a slightly-stale client quoting `amount_out` close to the vault balance, or a compounding effect from another swap in the same slot) and trivially triggerable intentionally by any user submitting `amount_out >= total_pc_without_take_pnl` (or the coin equivalent).

### Recommendation
Move the `swap.amount_out >= total_pc_without_take_pnl` / `total_coin_without_take_pnl` sufficiency checks (currently at [2](#0-1) ) to before the call to `Calculator::swap_token_amount_base_out` at [1](#0-0) , for both `process_swap_base_out` and `process_swap_base_out_v2`. Additionally, replace the `.unwrap()` calls in `swap_token_amount_base_out` at [3](#0-2)  with `.ok_or(AmmError::CalculationExRateFailure)?`-style error propagation so that any future caller ordering mistake degrades to a typed error instead of a panic.

### Proof of Concept
1. Create/observe a Raydium AMM pool with `total_pc_without_take_pnl = P` (derivable from public vault balances and `amm.state_data.need_take_pnl_pc`).
2. Submit a `SwapBaseOut` instruction (tag `11`) with `amount_out = P` (or any value `>= P`) and an arbitrary `max_amount_in`, using the caller's own token accounts as `user_source`/`user_destination` (direction `Coin2PC`).
3. `Processor::process_swap_base_out` reaches `Calculator::swap_token_amount_base_out(P, P, total_coin_without_take_pnl, Coin2PC)`, computing `denominator = P.checked_sub(P) = 0` — wait, note `checked_sub` returns `Some(0)` for equal values, so the true trigger is `amount_out > P` (strict), which yields `None` and panics `.unwrap()` on `None`, aborting the transaction with a Rust panic instead of the intended `AmmError::InsufficientFunds`.

**Note on confidence**: I verified the code path via the index up to line 2265 of `processor.rs` and lines 327-368 of `math.rs`, confirming the ordering issue precisely. I was not able to execute the program to confirm the exact runtime error surfaced (panic vs. Solana's built-in arithmetic-overflow trap under `overflow-checks`), so the precise error message/log format is unconfirmed; a Devin session with build/test tooling would be needed to reproduce this end-to-end on a local validator.
