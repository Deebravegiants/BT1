### Title
Fee-token transfer with no balance check reverts an already-successful `onGetResponse` delivery, permanently blocking GET-response delivery - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(GetResponse, address relayer)` executes the destination module's `onGetResponse` callback and, only *after* that call succeeds, pays the relayer its accumulated fee with an unchecked `IERC20(feeToken()).safeTransfer(relayer, fee)`. There is no check that the host's `feeToken()` balance actually covers `fee` before making the transfer. If it does not, `safeTransfer` reverts, which unwinds the entire transaction — including the module callback that had already executed and mutated state (e.g. releasing escrow in `IntentGateway`/`IntentsBase._withdraw`). This is the same bug class as the reference Y2K `Carousel.withdraw()` finding: a second, unrelated token transfer with no balance validation blocks an otherwise valid state transition.

### Finding Description
`dispatchIncoming` for GET responses is:
```solidity
function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
    bytes32 commitment = response.request.hash();
    _responseReceipts[commitment] = ResponseReceipt({relayer: relayer, responseCommitment: response.hash()});

    (bool success,) = _bytesToAddress(response.request.from)
        .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

    if (!success) {
        delete _responseReceipts[commitment];
        return;
    }

    uint256 fee = _requestCommitments[commitment].fee;
    if (fee != 0) {
        IERC20(feeToken()).safeTransfer(relayer, fee);
    }
    emit GetRequestHandled({commitment: commitment, relayer: relayer});
}
``` [1](#0-0) 

The analogous `dispatchTimeOut` handlers for POST and GET timeouts have the identical pattern: execute the app callback, and only after success unconditionally `safeTransfer` the refunded fee to `meta.sender` with no balance check. [2](#0-1) [3](#0-2) 

Unlike the successful `dispatchIncoming(PostRequest)` path, which returns early on a failed app callback but does not itself perform any post-callback token transfer, these three functions place a `safeTransfer` *after* a successful (already state-mutating) external call, with no `balanceOf(address(this)) >= fee` guard. If `feeToken()`'s balance held by the host is less than `fee` at that moment, `safeTransfer` reverts, and the whole `dispatchIncoming`/`dispatchTimeOut` call reverts, discarding the state changes performed by the destination app's callback (e.g. `IntentsBase._withdraw` releasing escrow, or `onGetResponse` refunding an `IntentGateway` order per `evm/src/apps/intentsv2/ExtrinsicIntents.sol:360` and `evm/src/apps/intentsv2/IntentsBase.sol:451-485`).

While fee accounting is intended to be 1:1 (fee collected on `dispatch()`/`fundRequest()` and paid out once on delivery), the host's `feeToken()` balance is a single shared pool across every outstanding request/response, not segregated per-commitment. Any transient discrepancy between the pooled feeToken balance and the sum of outstanding fee obligations (e.g. from ordering/timing of concurrent GET dispatches, `fundRequest` top-ups on already-delivered/expired commitments treated as "donations", or a benign accounting edge case) is sufficient to make this specific relayer's fee payment revert — and because it's on the tail of a state-mutating call, that failure blocks delivery entirely rather than merely skipping the fee.

### Impact Explanation
This falls squarely under "a route unable to deliver messages": once a `feeToken()` balance shortfall (even transient, or specific to one destination module reverting on second call) makes the trailing `safeTransfer` fail, the relayer cannot ever successfully submit that GET response or timeout (a resubmission produces the exact same commitment and the exact same fee obligation), permanently stalling delivery of that message and, transitively, whatever cross-chain settlement action (e.g., escrow refund/release in `IntentGateway`) the message was carrying. This is a freezing-of-funds vector: escrowed assets tied to that specific request can become permanently unrecoverable if delivery can never complete.

### Likelihood Explanation
Reachable by any relayer submitting a legitimately proven GET response or timeout through `HandlerV2` — no privileged role required. The precondition (feeToken balance on `EvmHost` insufficient for the specific fee owed at delivery time) is plausible under concurrent fee accounting/rounding, and once triggered it is deterministic and permanent for that commitment, since replays hash to the same commitment/fee and hit the same shortfall.

### Recommendation
Before performing the relayer/refund `feeToken` transfer in `dispatchIncoming(GetResponse,...)`, `dispatchTimeOut(GetRequestTimeout,...)`, and `dispatchTimeOut(PostRequestTimeout,...)`, check `IERC20(feeToken()).balanceOf(address(this)) >= fee` (or `meta.fee`). If insufficient, skip the transfer (mirroring the "let it be retried"/"treated as a shortfall" pattern) or record the underpayment for later claim, rather than letting an unguarded `safeTransfer` revert the entire delivery and roll back the already-executed application callback. At minimum, perform the fee transfer *before* the state-mutating app callback, or move it into a separate call so a shortfall cannot undo delivery.

### Proof of Concept
1. A relayer submits a valid GET response for commitment `C` with `fee = F` recorded in `_requestCommitments[C]`.
2. `EvmHost.dispatchIncoming(GetResponse, relayer)` calls `onGetResponse` on the destination module (e.g., `IntentsBase._withdraw` inside `ExtrinsicIntents.onGetResponse`), which successfully executes and would release escrowed funds to the user/solver.
3. Immediately after, the function attempts `IERC20(feeToken()).safeTransfer(relayer, F)`. If the host's actual `feeToken()` balance is below `F` at this moment (e.g., due to a concurrent fee-accounting discrepancy), this call reverts.
4. Because Solidity reverts undo the entire external call including the state changes made inside `onGetResponse`, the whole `dispatchIncoming` transaction reverts: the escrow release never happens, and the relayer receives nothing.
5. Any retry of the same delivery recomputes the same `commitment`/`fee` and hits the identical shortfall, so the message can never be delivered until governance intervenes to top up `feeToken()` balance — a permanent stall of that specific cross-chain settlement.
