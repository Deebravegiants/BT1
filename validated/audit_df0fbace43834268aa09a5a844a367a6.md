### Title
Withdrawal completion matched only by assetId, misreporting status/tx hash when multiple withdrawals of the same token exist in one call - ([File: packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts])

### Summary

### Finding Description
`findMatchingWithdrawal` selects a withdrawal record from the POA bridge API response using `Array.prototype.find`, matching purely on `assetId` (derived from `near_token_id`), and returns the *first* match: [1](#0-0) 

This is the same bug class as the reported `getSpentUnbondingTx` issue: a function that is supposed to identify *the* corresponding on-chain event for a given off-chain intent instead returns the first item matching a coarse criterion, silently dropping/misassigning the rest when several items share that criterion. Here, if a user withdraws the same token more than once (e.g., two withdrawal intents for the same `near_token_id` are in flight concurrently, or a batch operation initiates two withdrawals of the same asset), `waitForWithdrawalCompletion` for the *second* call has no way to distinguish which of the two "matching" entries in `result.withdrawals` corresponds to its own `txHash` — it will match on the first entry in API response order that has the same `assetId`, regardless of which `withdrawal_hash`/near tx actually produced it.

The code comment itself acknowledges the limitation is known but frames it as unsupported/POA-API-limited rather than as a concrete exploit path: [2](#0-1) 

The same first-match pattern (`findMatchingWithdrawal`) is reused in `describeWithdrawal`: [3](#0-2) 

### Impact Explanation
If this mismatch occurs, `waitForWithdrawalCompletion`/`describeWithdrawal` can report the `destinationTxHash`/`chain` of a *different* withdrawal than the one the caller is actually waiting on. An integrator polling for a specific `txHash`'s completion could be told it completed (with a `transfer_tx_hash` belonging to another withdrawal), potentially causing it to credit or reconcile the wrong transaction, or to consider its own withdrawal complete before it actually settles.

### Likelihood Explanation
This requires the accompanying documentation/comment's own admission — the API is not designed to disambiguate multiple withdrawals of the same asset, and the SDK does not add its own disambiguation (e.g., by amount, nonce, or destination address) despite that being explicitly suggested in the comment as a future improvement. However, this is presented in the code as a known, documented limitation rather than something the report's author claims to have exploited, and I could not fully trace, within the available tool budget, a concrete caller path in `packages/intents-sdk/src/sdk.ts` that issues two same-asset withdrawals concurrently and then relies on `waitForWithdrawalCompletion` to correctly disambiguate them (the relevant `sdk.ts` usage was not retrievable in the remaining iterations).

### Recommendation
Extend `findMatchingWithdrawal` and `WithdrawalCriteria` to disambiguate by more than `assetId` alone — e.g., match by amount and/or destination address, or by sorting both the API results and pending withdrawal params by amount (as already suggested in the existing code comment) to avoid returning a withdrawal record that doesn't correspond to the caller's specific transaction when multiple same-asset withdrawals are in flight.

### Proof of Concept
Not independently verified against a live caller path due to tool-call limits; the code path itself is shown above and its documented limitation supports the analog, but I could not confirm within this session whether `packages/intents-sdk/src/sdk.ts` ever invokes `waitForWithdrawalCompletion` twice concurrently for the same `assetId` in a way that would trigger the misreport in practice.

function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}
