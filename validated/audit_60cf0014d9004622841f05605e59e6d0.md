### Title
Freezing the host blocks cross-chain order cancellation/refund, trapping user escrow - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch()` is gated by the `notFrozen` modifier, which reverts with `FrozenHost` whenever the admin sets `FrozenStatus.Outgoing` or `FrozenStatus.All` [1](#0-0) [2](#0-1) . The Intent Gateway's cross-chain cancellation paths (`_cancelFromSource` and `_cancelFromDest`), which are the *only* way a user recovers escrowed funds for a cross-chain order, route through this same `dispatch()` call, exactly like order placement does.

### Finding Description
`_cancelFromDest` marks the order as filled locally and then calls `_post`, which dispatches a `RefundEscrow` message via `IDispatcher(hostAddr).dispatch{value: msg.value}(request)` (or `dispatchWithFeeToken`) [3](#0-2) . The analogous Tron implementation shows the same pattern explicitly for both the source-side GET dispatch and the destination-side RefundEscrow POST dispatch [4](#0-3) .

Both of these dispatch calls hit `EvmHost.dispatch()`, which is `notFrozen`-gated and reverts once the admin sets `FrozenStatus.Outgoing` or `FrozenStatus.All` — the emergency circuit-breaker for the whole host [5](#0-4) . There is no distinction in this check between a message that would create new risk exposure (placing a new order, filling an order) and a message whose sole purpose is to return already-escrowed user funds (cancel/refund). Just like the referenced Superposition finding, where `update_position` checked `enabled` regardless of whether liquidity was being added or removed, here `dispatch()` checks `notFrozen` regardless of whether the message is a new order or a withdrawal/refund of already-locked funds.

Same-chain cancellation (`_cancelSameChain`) is unaffected because it never calls `dispatch()` [6](#0-5) , but any cross-chain order — which is the primary intended use case of the Intent Gateway — has no path to recover escrowed input tokens while the host is frozen for outgoing messages.

### Impact Explanation
If an admin freezes the host (e.g., in response to a security incident, which is exactly the scenario this mechanism exists for) with `FrozenStatus.Outgoing` or `FrozenStatus.All`, any user with a pending cross-chain order cannot cancel it to reclaim their escrowed tokens: both `_cancelFromSource` (GET dispatch) and `_cancelFromDest` (RefundEscrow POST dispatch) revert with `FrozenHost`. This is precisely the scenario a freeze is meant to protect against — user funds becoming stuck or at risk — yet the freeze itself is what prevents the recovery. Funds remain locked in escrow for the duration of the freeze, which could be extended arbitrarily by the admin, constituting a temporary-to-permanent freezing of user funds depending on freeze duration and whether the deadline/expiry windows lapse while frozen.

### Likelihood Explanation
Freezing the host is an expected admin operational lever (used during incidents/upgrades), and any user with an outstanding cross-chain order at that time is automatically affected — no special conditions or attacker action are required, only the coincidence of an active order and an admin-initiated freeze. Given that freezes are the intended emergency response mechanism, this is a realistic and directly reachable condition, not a contrived edge case.

### Recommendation
Distinguish, in `EvmHost.dispatch()` or at the call sites in the Intent Gateway, between dispatches that create new exposure (place/fill order) and dispatches whose sole effect is refunding/cancelling escrow already held. Either exempt withdrawal/refund-only dispatches from the `notFrozen` check, or add a dedicated non-dispatch recovery path (e.g., a delayed self-service withdrawal after a freeze exceeds some threshold) so users can always retrieve escrowed funds regardless of host freeze state.

### Proof of Concept
1. User places a cross-chain order via `placeOrder`, escrowing input tokens on the source chain.
2. Before the order is filled, the admin calls `setFrozenState(FrozenStatus.Outgoing)` on the source `EvmHost` (or `All`) — as demonstrated in `testCannotDispatchWithFrozenHost` [7](#0-6) .
3. User calls `cancelOrder()`; on a cross-chain order this routes to `_cancelFromSource` or `_cancelFromDest`, both of which call `IDispatcher(hostAddr).dispatch(...)` [3](#0-2) .
4. `EvmHost.dispatch` reverts with `FrozenHost` [2](#0-1) , leaving the user's escrowed tokens locked in the gateway with no available recovery path until the admin unfreezes the host.

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value

    function _cancelSameChain(Order calldata order, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        uint256 inputsLen = order.inputs.length;
        TokenInfo[] memory remainingTokens = new TokenInfo[](inputsLen);
        bool hasEscrow = false;
        for (uint256 i; i < inputsLen;) {
            address token = address(uint160(uint256(order.inputs[i].token)));
            uint256 escrowed = _orders[commitment][token];
            if (escrowed > 0) hasEscrow = true;
            remainingTokens[i] = TokenInfo({token: order.inputs[i].token, amount: escrowed});
            unchecked {
                ++i;
            }
        }
        if (!hasEscrow) revert UnknownOrder();

        WithdrawalRequest memory body =
            WithdrawalRequest({commitment: commitment, tokens: remainingTokens, beneficiary: order.user});

        _withdraw(body, true, true);
    }
