### Title
Webhook `shop`/`topic` identity fields are not covered by HMAC verification, allowing cross‑tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's handler, but the HMAC check only authenticates the raw request body. The `shop` (and `topic`) values that the handler treats as the trusted tenant identifier come from HTTP headers that are never included in the signed bytes, so an attacker who possesses one valid `(body, hmac)` pair can replay it while swapping the shop-domain header to any value and the signature will still validate.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` and compares it to the supplied `hmac`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw request body: [2](#0-1) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are read from separate, unauthenticated HTTP headers via `shopify_header`: [3](#0-2) 

`Registry.process` performs the HMAC check and then unconditionally forwards `request.shop` (an unsigned header) to the app's handler as the tenant identity, alongside the (signed) body: [4](#0-3) 

This is the exact binding gap called out in the report's bug class: a field that is acted upon (`shop`, used by the handler to route/attribute data to a tenant) is not covered by the integrity check (`hmac`, computed over body only). The documentation reinforces that callers are meant to trust this "verified" request end‑to‑end: [5](#0-4) 

### Impact Explanation
An attacker who can obtain any single valid `(raw_body, x-shopify-hmac-sha256)` pair — trivially available to them since they can register a webhook to their own endpoint for their own Shopify store using the same app — can replay that exact body with the `x-shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` will report the request as valid because the signature never covered the shop header, and `Registry.process` will call the merchant's webhook handler with `WebhookMetadata(shop: <victim-shop>, body: <attacker-controlled but for their own shop>)`. Any host application that uses `data.shop` from the gem as a trusted per-tenant key (as the gem's own documentation and example handler instruct) will attribute attacker-controlled webhook content to a different tenant, enabling cross-tenant data injection/corruption within the merchant's app — a Critical-impact cross-tenant boundary violation, achieved without any credentials.

### Likelihood Explanation
Any internet user who can install the same third-party app on their own Shopify development/free store (a trivial, unprivileged action) can generate a validly-signed webhook body/HMAC pair for a chosen topic, then replay it against the target app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` header. No secrets, tokens, or elevated privileges are required — only network access to the app's public webhook callback path, which is a documented, always-listening endpoint.

### Recommendation
Bind the tenant-identifying and routing fields into the signed payload verification, mirroring how `AuthQuery` includes `shop`/`host` in its `to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb`). Concretely, in `lib/shopify_api/webhooks/request.rb`, include `shop`, `topic`, and `webhook_id` (or otherwise cryptographically bind them, e.g., via a webhook_id uniqueness/replay check tied to the verified body plus enforcing that repeated `webhook_id`s cannot be replayed with a different shop) before `Registry.process` passes them to the handler, and document that `data.shop` is only as trustworthy as this binding.

### Proof of Concept
1. Attacker installs the target app on their own Shopify store `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify sends a legitimately-signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the app's `client_secret`), and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the identical `B`/`H` to the same app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against `H`. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the app handler with `WebhookMetadata(shop: "victim.myshopify.com", body: <attacker's own order data>)`, causing the host app to process attacker-controlled data under the victim shop's tenant context.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
