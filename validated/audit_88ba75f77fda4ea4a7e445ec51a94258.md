### No vulnerability found for this question.

**Reasoning:**

The claimed broken equality is `computeIntentHash(multiPayload) == intent_hash` (from `publishIntent`), allegedly caused by a malformed-length nonce silently producing a divergent hash.

Tracing the path: `computeSignedNep413Hash` [1](#0-0)  converts `payload.nonce` via `Array.from(base64.decode(payload.nonce))` and feeds it into `hashNEP413Message`, whose Borsh schema declares `nonce` as a **fixed-size** `BorshSchema.Array(BorshSchema.u8, 32)` [2](#0-1) . Crucially, this exact same conversion and serialization function is used both when the payload is **originally signed** (`IntentSignerNEP413.signRaw`, `Array.from(base64.decode(input.payload.nonce))`) [3](#0-2)  and when the hash is **recomputed later** for local tracking via `computeIntentHash`. There is no separate/divergent code path — both sides of the claimed equality rely on the identical fixed-32-byte Borsh schema.

If `payload.nonce` decodes to a non-32-byte array, the fixed-size Borsh array serialization in the schema will fail consistently at both signing time and verification time (the same schema/function is reused), so no *valid* signature could ever be produced over a malformed-length nonce in the first place using this SDK's own signing flow. In normal operation, nonces are generated by `VersionedNonceBuilder.encodeNonce`, which always emits exactly 32 bytes (4-byte magic prefix + 1-byte version + 27-byte salted-nonce body) and validates its inputs strictly [4](#0-3) .

For an externally-supplied (counterparty) `MultiPayload` with a genuinely malformed nonce, NEP-413 itself specifies a fixed 32-byte nonce, and the on-chain `intents.near` contract's Borsh deserialization of the NEP-413 payload uses the same fixed `[u8; 32]` type — a malformed nonce would fail Borsh deserialization/signature verification on-chain as well, never producing a settled `intent_hash` to compare against. Both sides fail together rather than silently diverging into mismatched-but-valid hashes, so the equality is never broken in a way that produces the described "settled with a different hash" scenario. The described failure mode (a thrown error from `Array.from`/Borsh serialization on malformed input) is an input-validation/exception case, not a hash-mismatch/duplicate-resend vulnerability, and denial-of-service style failures are explicitly out of scope per the rules.

export async function computeSignedNep413Hash(
	signed: Extract<MultiPayload, { standard: "nep413" }>,
): Promise<Uint8Array> {
	// For NEP-413, we need to reconstruct the original message that was hashed
	const payload = signed.payload;

	return hashNEP413Message({
		message: payload.message,
		recipient: payload.recipient,
		nonce: Array.from(base64.decode(payload.nonce)),
		callback_url: payload.callbackUrl,
	});
}

	export function encodeNonce(
		salt: Salt,
		deadline: Date,
		randomBytes: Uint8Array<ArrayBufferLike> = crypto.getRandomValues(
			new Uint8Array(RANDOM_BYTES_LENGTH),
		),
	): string {
		if (salt.length !== 4) {
			throw new Error(`Invalid salt length: ${salt.length}, expected 4`);
		}
		if (randomBytes.length !== RANDOM_BYTES_LENGTH) {
			throw new Error(
				`Invalid randomBytes length: ${randomBytes.length}, expected ${RANDOM_BYTES_LENGTH}`,
			);
		}

		const deadlineBigInt = BigInt(deadline.getTime()) * 1_000_000n;

		// Manual serialization of SaltedNonce
		// salt (4) + deadline (8) + nonce (15) = 27 bytes
		const borshBytes = new Uint8Array(27);

		// Salt
		borshBytes.set(salt, 0);

		// Deadline (u64 little endian)
		const view = new DataView(
			borshBytes.buffer,
			borshBytes.byteOffset,
			borshBytes.byteLength,
		);
		view.setBigUint64(4, deadlineBigInt, true);

		// Random bytes
		borshBytes.set(randomBytes, 12);

		// Serializing in full format: MAGIC_PREFIX (4) | VERSION (1) | NONCE_BYTES (27)
		const result = new Uint8Array(4 + 1 + borshBytes.length);
		result.set(VERSIONED_MAGIC_PREFIX, 0);
		result.set([LATEST_VERSION], 4);
		result.set(borshBytes, 5);

		return base64.encode(result);
	}
