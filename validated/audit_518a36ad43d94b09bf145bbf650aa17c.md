### Title
`MigrateController` and `UpdateGovDelay` resolve to the `Standard` delay tier despite being higher-risk than `Sensitive` operations - (File: contracts/governance/src/op.rs)

### Summary
The governance timelock classifies each `AdminOperation` into a `DelayTier` (`Standard`, `Sensitive`, `Recovery`) that determines how many ledgers must pass before a scheduled operation is executable. Two of the most consequential operations — `MigrateController`, which calls the controller's `migrate` entrypoint, and `UpdateGovDelay`, which rewrites the timelock's own minimum delay — are resolved at `DelayTier::Standard` (`op.rs:370-372`, `op.rs:135-143`), while clearly less dangerous operations such as `SetPositionManager`, `ForceSocializeBadDebt`, `GrantGovRole`, `RevokeGovRole`, and every code upgrade are `Sensitive` (`op.rs:337-388`, `op.rs:407-411`, `op.rs:144-179`).

### Finding Description
`operation_delay` gives `Standard` the raw configured `min_delay`, while `Sensitive` enforces `max(min_delay, TIMELOCK_SENSITIVE_MIN_DELAY_LEDGERS)` (`contracts/governance/src/timelock/mod.rs:42-49`). The Sensitive floor exists precisely to guarantee a review window for dangerous state changes even when the configured minimum is low.

Yet `resolve_op` maps:

- `AdminOperation::MigrateController(version)` → `controller_operation(env, "migrate", ...)` → `DelayTier::Standard` (`op.rs:370-372`). Controller migration is the XOXNO equivalent of the report's `MigrateKernel`/`ChangeExecutor` class: it can rewrite or move the controller's state/authority and is more dangerous than upgrades that are already `Sensitive`.
- `AdminOperation::UpdateGovDelay(new_delay)` → `self_operation(env, "update_delay", ..., DelayTier::Standard)` (`op.rs:135-143`). `validate_delay_update` only enforces `new_delay >= current && <= MAX` (`timelock/mod.rs:59-67`), so while the value cannot decrease immediately, the operation that controls the entire security parameter of the timelock itself gets less review time than e.g. `SetPositionManager`.

Once scheduled, `execute`/`execute_self` are permissionless — `executor: None` performs no auth or role check (`timelock/mod.rs:75-82`), so any unprivileged address drives the operation the moment the (too-short) Standard delay elapses.

### Impact Explanation
Operations capable of migrating the lending controller or altering the governance delay parameter receive a shorter mandatory review/cancellation window than the protocol's own threat model assigns to lesser operations (the threat model documents Sensitive = `max(minimum, 12)` as the intended floor for risky ops, `docs/explanation/threat-model.md:38-47`). On a deployment where `min_delay` is below the Sensitive floor, a `MigrateController` or `UpdateGovDelay` operation becomes `Ready` sooner than guardians/cancellers expect, shrinking the window to detect and veto a malicious or erroneous proposal. A bad migration can permanently freeze or seize control of all controller-held accounting and pool authority.

### Likelihood Explanation
Proposing `MigrateController`/`UpdateGovDelay` requires the owner as proposer (`docs/reference/endpoints.md:215`), so the trigger is privileged at the proposal step; however the misclassification is a defense-in-depth failure identical in class to the report: the delay tier is the only mitigation, execution is permissionless, and the mis-tiering silently defeats the Sensitive floor whenever `min_delay < TIMELOCK_SENSITIVE_MIN_DELAY_LEDGERS`.

### Recommendation
In `resolve_op` (`contracts/governance/src/op.rs`), route `AdminOperation::MigrateController` through `sensitive_controller_operation` and `AdminOperation::UpdateGovDelay` through `self_operation(..., DelayTier::Sensitive)`, so operations that can migrate the controller or mutate the timelock's own delay always wait at least the Sensitive floor.

### Proof of Concept
```rust
// contracts/governance conceptual check
let proposed_at = env.ledger().sequence();

// On an instance with min_delay < SENSITIVE_FLOOR:
let id_migrate = gov.propose(
    &admin,
    &AdminOperation::MigrateController(2u32),
    &salt,
);
// BUG: ready after bare min_delay instead of SENSITIVE_FLOOR
assert_eq!(
    gov.get_operation_ledger(&id_migrate),
    proposed_at + LOW_MIN_DELAY          // Standard tier
    // expected: proposed_at + SENSITIVE_FLOOR
);

let id_delay = gov.propose(
    &admin,
    &AdminOperation::UpdateGovDelay(new_delay),
    &salt2,
);
// BUG: same — Standard tier despite controlling the timelock itself
assert_eq!(
    gov.get_operation_ledger(&id_delay),
    proposed_at + LOW_MIN_DELAY
);

// Meanwhile, less dangerous ops are Sensitive:
let id_mgr = gov.propose(&admin, &AdminOperation::SetPositionManager(m, true), &salt3);
assert_eq!(gov.get_operation_ledger(&id_mgr), proposed_at + SENSITIVE_FLOOR);
```

Root cause lines: `op.rs:370-372` (`MigrateController` → `controller_operation`, Standard), `op.rs:135-143` (`UpdateGovDelay` → Standard), `op.rs:62-78` (Standard vs Sensitive builders), `timelock/mod.rs:42-49` (tier-to-delay mapping).
