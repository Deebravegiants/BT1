### Title
Webhook HMAC signature does not bind the `shop-domain` header, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so `Utils::HmacValidator.validate` proves nothing about which shop the webhook belongs to. `Registry.process` nonetheless trusts the unauthenticated `shop-domain` header when dispatching to the app's handler, letting anyone who already possesses one valid `(body, hmac)` pair for their own shop replay it under a different, victim shop's domain.

### Finding Description
The verification chain for an incoming webhook is:
1. `Registry.process` calls `Utils::HmacValidator.validate(request)` and raises `InvalidWebhookError` if it returns `false`. [1](#0-0) 
2. `HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` with the app's `api_secret_key` and compares it to the presented `hmac`. [2](#0-1) 
3. For webhooks, `to_signable_string` is defined as just the raw HTTP body — it does **not** include `shop`, `topic`, or `webhook_id`, all of which come from separate, unsigned HTTP headers. [3](#0-2) 
4. After the HMAC check passes, `Registry.process` builds `WebhookMetadata` directly from these unauthenticated header values, including `shop: request.shop`, and hands it to the app's registered handler. [1](#0-0) 

The identity binding that should hold is:
`hmac_valid(body, hmac) == true` ⟹ `provenance(shop_header) == Shopify-for-that-shop`

What the code actually proves is only:
`hmac_valid(body, hmac) == true` ⟹ `provenance(body) == holder-of-client_secret`

Because `shop` (and `topic`/`webhook_id`) are fields *acted on* (passed straight into the handler and used by apps to key per-tenant data, per the documented `WebhookMetadata` contract) but are *not covered by the HMAC*, an attacker can freely choose the `shop` header value while keeping a body/hmac pair that will still validate.

### Impact Explanation
This breaks the shop/tenant identity binding of the webhook system: a request whose HMAC verifies as "genuinely signed by Shopify with this app's secret" can be attributed to an arbitrary shop of the attacker's choosing. Any host application that follows the documented pattern (using `data.shop` from `WebhookMetadata` to look up/update per-merchant records, as shown in the library's own webhook documentation) can be made to write or act on data under a shop it was never contacted about — a cross-tenant impact.

### Likelihood Explanation
No access token, `api_secret_key`, or privileged account is required. An attacker only needs to be a normal, unprivileged user of the app: install the app (or trigger any webhook-eligible event) on their own store to receive one legitimately signed `(body, hmac)` pair addressed to their own shop domain, then POST that identical body/hmac directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header with the victim shop's domain. Because the signature check only looks at the body, the forged request passes `HmacValidator.validate` unchanged, making this reliably exploitable and not dependent on any host misconfiguration or misuse of the documented API — `Registry.process`, used exactly as documented, is what performs the unsafe binding.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) in the value that is HMAC-verified, or otherwise cryptographically bind them to the body before trusting `request.shop`. Where Shopify's webhook signing scheme genuinely only signs the body, `Utils::HmacValidator`/`Webhooks::Request`/`Registry.process` should document and/or enforce that host applications cross-check `request.shop` against a known, previously-authenticated shop record (e.g., an existing session for that shop) before acting on the payload, rather than implicitly treating a passed HMAC check as proof that the `shop` header is trustworthy.

### Proof of Concept
1. Install the target app (as any user) on `attacker-shop.myshopify.com`; trigger a subscribed webhook topic (e.g., `orders/create`) so Shopify delivers a webhook to the app's public callback URL with headers:
   `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>`, plus the raw JSON body.
2. Capture that exact `raw_body` and `X-Shopify-Hmac-Sha256` value (attacker fully controls/observes their own deliveries).
3. Send a new HTTP POST directly to the same app webhook endpoint, reusing the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but replace the header with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes the HMAC over `to_signable_string` (the body only) — since the body is unchanged, verification succeeds. [4](#0-3) 
5. `Registry.process` proceeds to call the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker-chosen body, even though the request never came from Shopify or from that shop. [1](#0-0)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
