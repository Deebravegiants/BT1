Audit Report

## Title
CORS wildcard-origin allowlist bypass via unanchored suffix match - (File: core/services/gateway/network/httpserver.go)

## Summary
The Gateway HTTP server's `isAllowedOrigin` function validates wildcard CORS origin entries (e.g. `*.remix.com`) using an unanchored `strings.HasSuffix(originHost, allowedHost)` check instead of enforcing a subdomain boundary. This allows any attacker-controlled hostname that merely ends with the configured suffix string (e.g. `evilremix.com`) — not just legitimate subdomains — to be treated as an allowed CORS origin.

## Finding Description
In `isAllowedOrigin`, for wildcard entries the `*.` prefix is stripped from `allowedHost` and then matched against `originHost` purely via `strings.HasSuffix`, with no check that the preceding character is a dot or that `originHost` equals `allowedHost`: [1](#0-0) 
Given an allowlist entry `*.remix.com`, `allowedHost` becomes `remix.com`, and `strings.HasSuffix("evilremix.com", "remix.com")` evaluates to `true`, even though `evilremix.com` shares only a string suffix and is not a subdomain of `remix.com`. The scheme and port are also checked, but neither constrains the host boundary problem. [2](#0-1) 
The result is reflected verbatim into the response header in `handleRequest` when `CORSEnabled` is true: [3](#0-2) 
`handleRequest` is the handler wired directly to the configured `Path` mux entry, reachable by unprivileged HTTP clients, and forwards the raw body and any bearer token to `ProcessRequest`: [4](#0-3) 
There is no other origin-validation layer between the raw `Origin` header and this suffix check, so the flaw is exploitable exactly as described.

## Impact Explanation
When an operator enables CORS with a wildcard allowlist entry (a supported, documented configuration pattern), an attacker who registers/controls a domain that string-suffix-matches the configured suffix (e.g. `evilremix.com` against `*.remix.com`) can host a page that issues cross-origin `fetch`/XHR requests to the Gateway. The Gateway will reflect `Access-Control-Allow-Origin: https://evilremix.com`, letting the attacker's page read JSON-RPC response bodies from the Gateway that were intended to be restricted to the legitimate `*.remix.com` origin family. This is a cross-origin response confusion / allowlist bypass in the CORS trust decision itself.

## Likelihood Explanation
Exploitation requires only that the operator has configured `CORSEnabled = true` with a wildcard entry in `CORSAllowedOrigins`, which is a normal, supported, documented configuration (not a misconfiguration outside intended use — wildcard subdomain matching is an intentional feature). Given that, any external, unprivileged attacker can register a domain sharing the target suffix and exploit the bug with a simple cross-origin browser request; no credentials, node access, or privileged role are required.

## Recommendation
Anchor the wildcard host comparison to a proper subdomain boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
Add unit tests for non-subdomain suffix collisions such as `evilremix.com`, `notremix.com`, and `xremix.com` against `*.remix.com` to prevent regression.

## Proof of Concept
1. Configure the Gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.remix.com"]`.
2. From a browser on attacker-controlled `https://evilremix.com`, send `fetch("https://<gateway-host>/<configured Path>", { headers: { Origin: "https://evilremix.com" } })`.
3. Observe that the Gateway responds with `Access-Control-Allow-Origin: https://evilremix.com` because `isAllowedOrigin` computes `allowedHost = "remix.com"` and `strings.HasSuffix("evilremix.com", "remix.com")` returns `true`, allowing the attacker page's script to read the cross-origin response. A Go unit test calling `isAllowedOrigin("https://evilremix.com")` with `CORSAllowedOrigins: []string{"https://*.remix.com"}` and asserting it returns `false` (currently returns `true`) demonstrates the bug directly.

func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}

func (s *httpServer) handleRequest(w http.ResponseWriter, r *http.Request) {
	if s.config.CORSEnabled {
		origin := r.Header.Get("Origin")
		if s.isAllowedOrigin(origin) {
			w.Header().Set("Access-Control-Allow-Origin", origin)
			w.Header().Set("Access-Control-Allow-Methods", "GET, POST, OPTIONS")
			w.Header().Set("Access-Control-Allow-Headers", "Content-Type")
		}

		// handle preflight requests
		if r.Method == http.MethodOptions {
			w.WriteHeader(http.StatusNoContent)
			return
		}
	}
