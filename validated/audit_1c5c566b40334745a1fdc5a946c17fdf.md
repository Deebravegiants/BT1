### Title
Webhook shop identity spoofing via unauthenticated header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `X-Shopify-Shop-Domain` HTTP header, but this header is never included in the HMAC signature verification. Any caller with network access to a webhook endpoint that uses this gem can send a request with a valid-looking body/HMAC pair captured from one tenant, paired with an arbitrary `shop-domain` header, and the library will report a different shop than the one whose secret actually signed the payload.

### Finding Description
The HMAC verification for webhooks is delegated to `Utils::HmacValidator.validate`, which computes the signature over `to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` method, used by host applications to route/attribute the incoming webhook to a specific merchant/session, is derived purely from the `shopify-shop-domain` header without any cryptographic binding to the signed body [2](#0-1) .

This breaks the identity binding: `shop-header-claimed == shop-that-signed-the-body`. An attacker who can capture or predict a validly-signed webhook body (e.g., a webhook the merchant's own store legitimately receives, or a request replayed from a shop they control, since the body/HMAC pair for a given topic can be content they influence, e.g. via a metaobject/webhook payload they trigger from their own shop) can resend the exact same `raw_body`+`hmac` pair while substituting an arbitrary value in the `shopify-shop-domain` header. `HmacValidator.validate` only checks that `hmac` matches `HMAC(api_secret_key, raw_body)` [3](#0-2)  — it never checks that the claimed `shop` matches anything cryptographically. Because `api_secret_key` is shared across all shops installing the same app, an attacker's own shop can produce a validly-HMAC'd body, and then that same body can be replayed with a forged `shop-domain` header claiming to be a victim shop.

The host application typically trusts `request.shop` to select which merchant's session/data to update as a result of the (validated) webhook — this is the documented contract of the gem. Since the gem asserts the request is "valid" via `verified?`/HMAC check while returning an unauthenticated `shop`, downstream code that does `session = lookup_session(request.shop)` after `request.verified?` is misled into cross-tenant data application.

### Impact Explanation
This qualifies as cross-tenant access: a request cryptographically valid for shop A's payload can be attributed to shop B purely by forging an HTTP header, since the shop identifier is never part of the signed bytes. Any host application that relies on this gem's `Webhooks::Request#shop` after `Utils::HmacValidator.validate` succeeds (the gem's own documented verification path) can be tricked into processing/crediting a webhook under the wrong merchant.

### Likelihood Explanation
Exploitability requires the attacker to obtain one validly-signed `raw_body` for the shared `api_secret_key` (trivial if the attacker has installed the app on their own shop and can trigger topics with attacker-controlled body content, e.g. product/webhook update payloads), and network access to the app's webhook endpoint — both are available to an unprivileged internet user / app-installing attacker without needing the `client_secret` itself.

### Recommendation
Bind the `shop` claim cryptographically to the signed payload: either include the shop domain in the bytes covered by `to_signable_string`, or require host applications to derive the shop exclusively from the verified request body (most Shopify webhook payloads already embed shop/domain-scoped data), and document that the header-derived `shop` in `Webhooks::Request` must not be trusted for tenant identification absent additional verification (e.g., comparing to a known, pre-registered shop associated with the specific webhook subscription id).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook topic whose payload body they control (e.g., updates a resource so its JSON body content is attacker-influenced).
2. Attacker captures the resulting `raw_body` and the corresponding `X-Shopify-Hmac-Sha256` header — both valid under the shared `api_secret_key`.
3. Attacker replays this exact `raw_body` + `hmac` pair to the app's webhook endpoint, but sets the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(api_secret_key, raw_body)` [4](#0-3) .
5. `request.shop` returns `"victim-shop.myshopify.com"` [2](#0-1) , and the host application processes the (attacker-controlled) payload as if it belonged to the victim shop.
