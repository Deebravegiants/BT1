Audit Report

## Title
Fee-on-transfer / non-standard ERC20 tokens break custody accounting in `ERC20Transactor` - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

## Summary
`ERC20Transactor::withdraw_asset_with_surplus` and `ERC20Transactor::deposit_asset_with_surplus` move ERC20 tokens by invoking `IERC20::transfer()` and only check the boolean success return, then unconditionally credit/release the requested `amount` (not any measured balance delta) into/out of the XCM `AssetsInHolding` register via `Erc20Credit(amount)`. [1](#0-0) [2](#0-1)  Because the ERC20 matcher (`ERC20Matcher`) accepts any `AccountKey20` location with no allow-list, an unprivileged user can deploy a fee-on-transfer/deflationary ERC20 and exploit the desync between real custody balance and XCM-recognized holding amount.

## Finding Description
In `withdraw_asset_with_surplus`, the transactor transfers `amount` from `who` to the checking account and, if the call doesn't revert and the ABI-decoded return is `true`, credits `Erc20Credit(amount)` — the requested amount, not any observed balance change — into the returned `AssetsInHolding`. [3](#0-2) 

Symmetrically, `deposit_asset_with_surplus` transfers `amount` from the checking account to the beneficiary and treats the deposit as fully successful as soon as the call returns `Ok(true)`, again without verifying the beneficiary's actual balance increase. [4](#0-3) 

Neither function calls `balanceOf` before/after the transfer to measure the real amount moved; both rely solely on the boolean success flag combined with the pre-computed `amount` parameter. For a standard-compliant ERC20 that's accurate, but for a fee-on-transfer, deflationary, or rebasing token, the amount actually received by the checking account (on withdraw) or by the beneficiary (on deposit) can be strictly less than `amount`, while the XCM holding bookkeeping still reflects the full `amount`.

The `Erc20Credit` imbalance type used to represent this holding performs no runtime-level balance enforcement — the comment on the type explicitly states balance constraints are meant to be enforced by the ERC20 contract itself, not the runtime. [5](#0-4)  This design assumption is violated by non-standard tokens, and the code path provides no mitigation.

The matching contract address is not registered or allow-listed — `ERC20Matcher` matches any `AccountKey20` location via `IsLocalAccountKey20`. [6](#0-5)  This confirms the transactor is reachable for any deployed contract address without governance gating, and it is wired into the live `AssetTransactors` tuple used by Asset Hub Westend's XCM executor. [7](#0-6) 

## Impact Explanation
Since any account can deploy an arbitrary ERC20/`pallet-revive` contract with fee-on-transfer, deflationary, or rebasing semantics and immediately have it recognized by `ERC20Transactor` with zero registration, an attacker can construct an XCM program (`WithdrawAsset` followed by further instructions consuming the holding, e.g. `DepositAsset`/`BuyExecution`) where the executor's in-memory `AssetsInHolding` is credited with more than what is actually held in escrow by `TransfersCheckingAccount`. This is a genuine accounting desync between the ERC20 contract's real balance movement and the XCM executor's bookkeeping, allowing extraction of XCM-recognized value beyond the true custodied balance.

## Likelihood Explanation
Deploying a custom ERC20 contract and referencing it as an `AccountKey20` asset id in an XCM program is achievable by any unprivileged account, requires no special permission or asset registration, and fee-on-transfer/deflationary/rebasing token patterns are trivial and well-known ERC20 variants. The exploit path is fully within the reach of a normal external user through `pallet_xcm::execute`/`transfer_assets`.

## Recommendation
In both `withdraw_asset_with_surplus` and `deposit_asset_with_surplus`, measure the actual balance delta of the checking account/beneficiary via `balanceOf` calls before and after the `transfer`, and use that measured delta (not the requested `amount`) when constructing/releasing the `Erc20Credit`. Alternatively, restrict `ERC20Matcher` to an allow-list of vetted, standards-compliant, non-fee-on-transfer, non-rebasing ERC20 contracts.

## Proof of Concept
1. Deploy an ERC20 contract via `pallet-revive` whose `transfer` implementation withholds/burns a percentage of `value` on every call (fee-on-transfer) while remaining otherwise ABI-compliant and returning `true`.
2. From an unprivileged account, submit an XCM program (via `pallet_xcm::execute` or `transfer_assets`) referencing asset id `Location(0, [AccountKey20{ key: <contract_address> }])` with `amount = 1000`, containing `WithdrawAsset` followed by an instruction that consumes the resulting holding.
3. Observe that `withdraw_asset_with_surplus` (`erc20_transactor.rs:166-203`) only moves the fee-reduced amount into `TransfersCheckingAccount`'s real ERC20 balance, but credits `Erc20Credit(1000)` (the full requested amount) into `AssetsInHolding`.
4. The downstream instruction consuming the holding treats it as fully-custodied value equal to the requested `amount`, though the real escrowed balance is smaller — demonstrating the accounting desync.
