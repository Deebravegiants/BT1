## Finding: Confirmed

The equality that should hold is: for each `WithdrawalIdentifier` `i` with `withdrawalParams.assetId === X`, `describeWithdrawal` should return the status/`txHash` of the withdrawal record whose `data.address`/`data.amount` correspond to `withdrawalParams` at index `i`. Tracing the code shows this equality breaks when a batch contains two withdrawals of `nep141:btc.omft.near`.

`describeWithdrawal` calls `getWithdrawalStatusWithRetry`, which queries the POA API keyed only by `args.tx.hash` (the shared NEAR intent tx) [1](#0-0) . Both withdrawal identifiers for the two BTC legs therefore receive the identical `withdrawals` array back. The result is then narrowed with `findMatchingWithdrawal`, which matches purely by `nep141:<near_token_id> === assetId` via `Array.prototype.find`, with no use of `index`, `destinationAddress`, or `amount` [2](#0-1) . The docstring explicitly acknowledges this: "multiple withdrawals of the same token in a single transaction are not supported" [3](#0-2) .

Because `.find()` always returns the *first* array element matching the assetId, both `describeWithdrawal` calls (one for each `WithdrawalIdentifier`/index) resolve to the exact same withdrawal record and therefore the same `status`/`txHash`, regardless of which destination address each `WithdrawalIdentifier` actually corresponds to [4](#0-3) . This is reachable through `IntentsSDK.waitForWithdrawalCompletion` → `createWithdrawalCompletionPromises` → `watchWithdrawal`, where each batch item gets its own `WithdrawalIdentifier` with a distinct `index` but the same `assetId` [5](#0-4) [6](#0-5) . The same unguarded pattern exists in the sibling `internal-utils` helper `findMatchingWithdrawal` used by `waitForWithdrawalCompletion` [7](#0-6) .

No other guard (no `destinationAddress`/`amount` cross-check, no sorting by amount as the comment suggests as a future fix) currently prevents this divergence. There is an existing regression test confirming matching is done "by assetId, not by index" for *different* chains, but there is no test covering two same-assetId withdrawals in one batch [8](#0-7) .

### Title
Same-token double withdrawal in one batch causes `describeWithdrawal` to report the wrong destination's status/txHash - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
When a NEAR intent contains two withdrawals of the same token (e.g. `nep141:btc.omft.near`) to two different destination addresses, `PoaBridge.describeWithdrawal`'s helper `findMatchingWithdrawal` matches purely on `assetId` via `Array.prototype.find`, so both `WithdrawalIdentifier`s (index 0 and index 1) resolve to the same first-matching withdrawal record. This causes the SDK to report identical `status`/`txHash` for both legs, misattributing one destination's completion (and `txHash`) to the other.

### Finding Description
`describeWithdrawal` fetches all withdrawals for the shared NEAR tx hash and narrows to a single entry using `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` [4](#0-3) . `findMatchingWithdrawal` matches solely by `nep141:<near_token_id> === assetId`, ignoring `destinationAddress` and `amount`, and the docstring explicitly states this doesn't support multiple same-token withdrawals in one tx [2](#0-1) . When a batch has two BTC withdrawals (different destination addresses/amounts) in one intent, both calls to `describeWithdrawal` (once per `WithdrawalIdentifier`, distinguished only by `index`, which is unused in matching) return the **same** underlying record — whichever appears first in the API's unsorted list. Consequently, the caller of `IntentsSDK.waitForWithdrawalCompletion` receives the same `txHash` for both entries in the returned array, misreporting the status/hash of one destination as if it belonged to the other.

### Impact Explanation
The misreported value is the `txHash`/`status` returned per `WithdrawalIdentifier` to the integrator via `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` [9](#0-8) . An integrator relying on per-index results to credit or reconcile a payout could see the wrong destination reported as "completed" with a specific `txHash`, potentially crediting a payment to the wrong account, or crediting the same underlying transfer twice for two logically distinct withdrawal legs. This matches the High severity category "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
This is trivially reproducible by any user/integrator constructing a batch intent with two withdrawals of the same PoA token (e.g. two `nep141:btc.omft.near` legs to different addresses) — no special privileges are required, since batch composition is fully attacker/integrator controlled. It is deterministic and repeatable every time the POA bridge's withdrawal list for that tx hash contains ≥2 entries for the same token, since `.find()` always yields the same (first) match for every caller regardless of index.

### Recommendation
Extend `findMatchingWithdrawal` to disambiguate same-`assetId` withdrawals by also matching `data.address` (destination) and `data.amount`, or — as the code comment suggests — sort both the API response and the local withdrawal params by amount (since fees are equal for same-token withdrawals) and use position-based pairing to preserve correct index-to-record correspondence. Apply the same fix in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`'s `findMatchingWithdrawal`.

### Proof of Concept
Vitest plan (mocking only `poaBridge.httpClient.getWithdrawalStatus`):
1. Mock `getWithdrawalStatus` to return two `COMPLETED` withdrawals, both `near_token_id: "btc.omft.near"`, one with `address: "addrA"`, `transfer_tx_hash: "hashA"`, the other `address: "addrB"`, `transfer_tx_hash: "hashB"`.
2. Call `bridge.describeWithdrawal` twice: once with `withdrawalParams.destinationAddress = "addrA"` (index 0), once with `destinationAddress = "addrB"` (index 1), both `assetId: "nep141:btc.omft.near"`.
3. Assert (equality under test): `result0.txHash === "hashA"` AND `result1.txHash === "hashB"` (each identifier resolves to its own destination's hash).
4. Current behavior: both calls return `txHash: "hashA"` (the first array entry), demonstrating the two results are identical and thus one is wrong — proving the equality is broken.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
