### Title
Missing Re-Initialization Guard in `LockupContract::new()` Allows Unauthorized Takeover of Locked Funds - (File: `lockup/src/lib.rs`)

### Summary
The analog of the Rocket Pool `RocketMinipoolBase.initialise()` bug exists in `lockup/src/lib.rs`. Every other production contract in this repository (`staking-pool`, `staking-pool-factory`, `whitelist`, `multisig`, `lockup-factory`) guards its `#[init]` constructor with `assert!(!env::state_exists(), "Already initialized")` (or an equivalent message), which prevents the initializer from being called again once the contract state has been created. The `LockupContract::new()` function in `lockup/src/lib.rs` is missing this exact check, meaning an already-deployed and initialized lockup contract can have its `new()` re-invoked by anyone, completely overwriting `owner_account_id`, `lockup_information`, `vesting_information`, and other critical state.

### Finding Description
`LockupContract::new()` is marked `#[init]` and is a normal public contract method reachable via a NEAR function call, exactly like every other constructor examined in this codebase: [1](#0-0) 

Compare this to the analogous constructors elsewhere in the repo, all of which include a state-exists guard to reject re-initialization: [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

`LockupContract::new()` has no such check. NEAR's `#[near_bindgen]` macro does not restrict `#[init]` methods to be called only once by default — the `assert!(!env::state_exists(), ...)` pattern used throughout the rest of this codebase is the actual enforcement mechanism, and it is the recommended fix explicitly called out in the analog report ("check ... to ensure that the storageState is Undefined"). Its absence in `lockup/src/lib.rs` is the direct root cause analog to `RocketMinipoolBase.initialise()` lacking a `StorageState.Undefined` check.

Because `new()` sets `owner_account_id` directly from caller-supplied input and recomputes `lockup_information.lockup_amount` from `env::account_balance()` at call time: [7](#0-6) 

an unprivileged attacker can call `new()` a second time on any already-deployed, funded lockup contract, setting `owner_account_id` to their own account and resetting `vesting_information`/`lockup_information` fields (e.g., clearing termination status, resetting lockup timestamps, or enabling transfers depending on supplied `transfers_information`). Once `owner_account_id` is overwritten, the attacker becomes the privileged owner of the contract and can invoke owner-only withdrawal/transfer methods to drain the locked NEAR balance.

### Impact Explanation
This maps to the "Critical" impact category: unauthorized transfer/withdrawal of locked NEAR through a public-call state-transition bypass, reachable by an unprivileged user re-invoking a public `#[init]` entrypoint that lacks a re-initialization guard present everywhere else in the codebase.

### Likelihood Explanation
The entrypoint is fully public and requires no privileged role, key, or special access — any account can issue a function call to `new()` on a deployed lockup contract account. The only precondition is that the lockup account's `new` method has not been made otherwise unreachable, and the pattern is directly comparable to (and less encumbered than) the peer constructors in this same repo, all of which recognized this exact class of risk and added the guard. This is a straightforward, deterministic exploit for anyone who can send a transaction to the contract's `new` function.

### Recommendation
Add the same guard used in the other contracts to `LockupContract::new()`:
```rust
#[init]
pub fn new(...) -> Self {
    assert!(!env::state_exists(), "The contract is already initialized");
    ...
}
```
This aligns `lockup/src/lib.rs` with `staking-pool/src/lib.rs`, `staking-pool-factory/src/lib.rs`, `whitelist/src/lib.rs`, `multisig/src/lib.rs`, and `lockup-factory/src/lib.rs`, all of which already contain this protection.

### Proof of Concept
1. A lockup contract is deployed and initialized normally via `LockupContract::new(owner_account_id: victim, ...)`, funded with locked NEAR.
2. An attacker (any unprivileged account) sends a function call `new(owner_account_id: attacker, lockup_duration: 0, lockup_timestamp: None, transfers_information: TransfersEnabled{...}, vesting_schedule: None, release_duration: None, staking_pool_whitelist_account_id: ..., foundation_account_id: None)` directly to the deployed lockup contract account.
3. Because there is no `assert!(!env::state_exists(), ...)` check (unlike in every sibling contract), the call succeeds and overwrites `owner_account_id` to the attacker's account and resets `lockup_information`/`vesting_information` based on attacker-supplied parameters.
4. The attacker, now recognized as `owner_account_id`, calls the owner-only transfer/withdrawal methods in `lockup/src/owner.rs` to move the contract's NEAR balance to an account they control.
