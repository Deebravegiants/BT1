### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then passes the unauthenticated `shop-domain` header straight to the app's handler as the tenant identifier. Since the HMAC signature never covers the shop, code, or any header, an attacker who owns a legitimate (even free/dev) shop can capture a genuine, validly-signed webhook delivered to their own endpoint and replay it with a forged `shop-domain` header, making the host application process it as if it originated from a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

None of the identity-carrying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) are included in the signed string. `Registry.process` validates only that computed signature against the body: [2](#0-1) 

and then forwards `request.shop` — read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header — to the handler as the tenant identifier: [3](#0-2) 

The gem's own `HmacValidator.validate` only checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [4](#0-3) 

so for webhooks it verifies **body vs signature** but never **shop vs signature**. This breaks the identity binding `shop_authenticated == shop_used_by_handler`: the value the gem asserts is authentic (the body/HMAC pair) is disjoint from the value the host application is documented to trust as the tenant (`data.shop`). The gem's own documentation instructs developers to trust `data.shop` as "The shop domain of the webhook" and states that `process` "will verify the request did indeed come from Shopify," implying the whole request (including shop) is authenticated — which it is not: [5](#0-4) [6](#0-5) 

Unlike the OAuth callback path, where `AuthQuery#to_signable_string` explicitly folds `shop` into the signed payload so the shop cannot be swapped without invalidating the HMAC: [7](#0-6) 

the webhook path has no equivalent binding. There is also no call to `ShopValidator` anywhere in `Registry.process`/`Request`, so the shop value is neither cryptographically bound nor sanity-checked.

### Impact Explanation
Any unprivileged internet user who can install (or run a free/dev instance of) the app on their own shop can receive genuine Shopify webhooks signed with the app's real secret. They can then replay that exact signed body to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for an arbitrary victim shop domain. Because the HMAC only signs the body, the forged request still validates, and the host application — following the gem's documented contract exactly — will process attacker-controlled webhook data (e.g., `orders/create`, `customers/update`, etc.) as belonging to the victim tenant. This is a cross-tenant data-injection primitive reachable without any credentials, access tokens, or privileged account, satisfying the Critical "cross-tenant access" impact bar.

### Likelihood Explanation
High. The attack requires no secrets: the attacker only needs their own (free) shop to legitimately receive one valid webhook delivery, then modify one HTTP header and replay it to the target app's public callback URL. No `api_secret_key`, access token, or social engineering is needed, and it exploits the gem's documented `Registry.process`/`Request` API exactly as intended by app developers.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) into the HMAC-signed material, or otherwise cryptographically/contextually assert that the shop asserted in the header matches the shop the app expects for that webhook subscription (e.g., compare against the shop associated with the specific `webhook_id` on record) before handing `WebhookMetadata` to the handler. At minimum, update `VerifiableQuery`/`HmacValidator` usage for webhooks so `to_signable_string` incorporates the shop domain, mirroring how `AuthQuery` binds `shop` into its signable string.

### Proof of Concept
1. Attacker creates their own (development) shop `attacker-shop.myshopify.com` and installs the target app, subscribing it to a webhook topic (e.g. `customers/update`).
2. Shopify delivers a legitimately signed webhook to the app's endpoint:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: attacker-controlled JSON (attacker fully controls their own shop's data, e.g. customer email/name fields).
3. Attacker captures this raw request and replays it to the same endpoint, changing only the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - Body and `x-shopify-hmac-sha256` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC: [2](#0-1) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, and the host app processes/stores this as authentic data for the victim tenant.
