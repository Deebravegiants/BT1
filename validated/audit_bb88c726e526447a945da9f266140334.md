## Title
Webhook Shop/Topic Header Spoofing — HMAC only covers the request body, not the tenant-identifying headers - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop`, `topic`, `webhook_id`, and `api_version` fields used by `Registry.process` to route and attribute the webhook are taken from unauthenticated HTTP headers. An unprivileged attacker who obtains one valid `(body, hmac)` pair for the app (e.g., from a webhook delivered to a shop they themselves control, since the app's `client_secret`/webhook secret is shared across every shop that installs the app) can replay that body with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header pointing at a victim shop. `HmacValidator.validate` will still pass because it only re-computes the signature over the body, so the app will process attacker-supplied data as if it originated from — and belongs to — the victim tenant.

### Finding Description
`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, and for webhooks that method returns only the raw HTTP body: [1](#0-0) [2](#0-1) 

Meanwhile, `shop`, `topic`, `webhook_id`, and `api_version` are all read straight off request headers with no cryptographic binding to the body or to the HMAC signature: [3](#0-2) 

`Registry.process` uses these unauthenticated header values both to select the handler (`request.topic`) and to construct the `WebhookMetadata` passed to app code, including `shop: request.shop`: [4](#0-3) 

The identity binding the app relies on is effectively:
`hmac_valid(body) == true` ⇒ `(shop_header, topic_header, body)` all trustworthy

But what is actually proven is only:
`hmac_valid(body) == true` ⇒ `body` was signed once by the shared app secret

Since the webhook secret (the app's `client_secret`/`api_secret_key`) is identical for every shop that installs the app, any shop owner — an unprivileged internet user with respect to other tenants — can capture a legitimately-signed `(body, hmac)` pair from their own webhook deliveries and replay it to the same endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain (and/or the topic header changed). The signature check in `HmacValidator.validate` neither observes nor cares about this change, so `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim shop while the body content is attacker-controlled.

### Impact Explanation
This breaks the tenant boundary the webhook handler mechanism is meant to enforce: host applications built on this gem's webhook processing (`Registry.process`) key their business logic off `WebhookMetadata#shop`, trusting that a passing HMAC check means the header-derived `shop`/`topic` are authentic. An attacker can make the app believe arbitrary attacker-chosen webhook data belongs to a different, victim tenant (cross-tenant data injection/confusion), and can also relabel the `topic` to route a captured body into an unrelated handler. This matches the Critical "cross-tenant access" impact category since it lets one tenant's traffic be attributed to another tenant purely through unauthenticated header spoofing.

### Likelihood Explanation
Any developer/merchant who installs the app on their own shop can legitimately receive HMAC-valid webhook payloads for that shop (no leaked secret or privileged access needed — this is normal app usage). Replaying that exact body with modified headers to the app's public webhook endpoint requires nothing beyond basic HTTP tooling, so the likelihood is high wherever the host app relies on `request.shop`/`request.topic` from this gem without independently re-verifying header authenticity.

### Recommendation
Bind the tenant-identifying and routing fields into the signed payload rather than trusting bare headers:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise cryptographically bind them to the body before computing/verifying the HMAC), so any header tampering invalidates the signature.
- Alternatively/additionally, document and enforce that host apps must cross-check `request.shop` against an already-known, previously-registered shop for that webhook registration/topic combination rather than trusting the header value outright.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; attacker triggers/receives a normal webhook delivery, capturing the raw body `B` and the valid header `x-shopify-hmac-sha256: H` (computed by Shopify using the app's shared secret over `B`).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `B` — validation succeeds: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host app to process attacker-controlled data under the victim shop's identity.
