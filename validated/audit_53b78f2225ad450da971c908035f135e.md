### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, and `webhook_id` used to route and attribute the webhook are taken from unauthenticated HTTP headers. `Registry.process` validates only that the body's HMAC is correct, then trusts the header-derived `shop` value when building `WebhookMetadata` passed to the app's handler. This breaks the intended binding: `bytes verified` (the raw body) ≠ `bytes parsed for tenant identity` (the shop header).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, and `webhook_id` are read straight from HTTP headers with no cryptographic tie to the body/signature: [2](#0-1) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)`, which validates `request.hmac` against `request.to_signable_string` (i.e., only the body): [3](#0-2) [4](#0-3) 

Since `Context.api_secret_key` is a single per-app secret (identical for every shop that installs the app), any shop that installs the app can generate a body+HMAC pair that is valid for **any** other shop, simply by changing the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header while replaying the same raw body and HMAC. `HmacValidator.validate` has no way to detect this because it never inspects the shop header. The resulting `request.shop` (attacker-controlled) is then handed to the app's `WebhookHandler#handle` via `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, and the app is expected to use `shop` to identify which merchant's data the event/body applies to.

This differs from the OAuth callback path, where `AuthQuery#to_signable_string` explicitly includes `shop` (along with `code`, `host`, `state`, `timestamp`) inside the signed content, so the shop cannot be swapped without invalidating the signature: [5](#0-4) 

For webhooks, no equivalent binding exists.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged attacker who is themselves a legitimate merchant with the target app installed (a normal, unprivileged capability, not requiring `api_secret_key`, an access token, or any special privilege) can capture a valid `{raw_body, hmac}` pair from their own store's webhook deliveries and replay it against the app's webhook endpoint with a forged shop-domain header claiming to be a different merchant. Because this gem's own `Registry.process`/`HmacValidator` accepts the request as authentic and reports the forged `shop`, any host application that follows this gem's documented webhook-processing API (`Registry.process` → `WebhookHandler#handle` with `WebhookMetadata#shop`) will act on data attributed to the wrong tenant. This matches the "cross-tenant access" Critical impact category, since the gem's own verification primitive fails to bind the party-identifying field to the cryptographic proof.

### Likelihood Explanation
Likelihood is moderate-to-high for apps with any publicly installable component: the only prerequisite is that the attacker can install the target app on a shop they control (a normal, low-privilege action) and capture one webhook delivery, which many apps' webhook payloads (e.g., `app/uninstalled`, `shop/redact`) make trivial to obtain and replay. No secrets, tokens, or elevated access are required — only observation of one's own webhook traffic and the ability to send arbitrary HTTP requests to the app's public webhook endpoint.

### Recommendation
Include the shop-identifying and topic-identifying headers in the HMAC-signed content, or otherwise cryptographically bind them (e.g., verify the shop domain against Shopify's webhook payload contents where available, or require the signature to cover a canonicalized header+body representation). At minimum, `Utils::HmacValidator` should validate that the `shop`, `topic`, and `webhook_id` used in `WebhookMetadata` are consistent with values covered by the signature, not solely trust unauthenticated headers.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (legitimate action).
2. Shopify sends a webhook to the app with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <hmac>`, and body `B`. The attacker records `(B, hmac)`.
3. Attacker sends a new POST to the same webhook endpoint with the same body `B` and the same `hmac`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` parses headers, exposing `shop == "victim-shop.myshopify.com"`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (= `B` only) using `Context.api_secret_key` and finds it matches — validation succeeds. [6](#0-5) 
6. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and processes/attributes the (attacker-supplied) body content as if it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
