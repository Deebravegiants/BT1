**Rationale:**

The described attack requires an attacker-supplied `MoveType::Struct` type argument to cause `try_into_vm_value_struct`'s `WithTypes` branch to interpret one resource's raw bytes as if they belonged to a different, unrelated struct type (type confusion via matching byte layout). This does not hold up against the actual code path:

1. `try_into_vm_value_struct` operates on a `MoveStructLayout::WithTypes { type_, fields }` layout that is not attacker-suppliable arbitrary data — it is derived by `view_fully_decorated_ty_layout(type_tag)` from the real on-chain module's declared struct definition, resolved via the VM's type/module resolver [1](#0-0) . The `struct_tag` embedded in that layout always corresponds to the actual struct being resolved for the given `TypeTag`, not something an attacker can freely substitute to alias two unrelated structs. The function's only use of `struct_tag` here is to special-case UTF-8 `string::String` formatting, and it then walks the declared `field_layouts` — which come from the real module definition — to build a `MoveValue::Struct` from user-supplied JSON, not from raw resource bytes [2](#0-1) .

2. This whole path is used to convert a JSON `Value` (submitted in `ViewRequest.arguments`) into VM call arguments for invoking a view function — it is not the path used for interpreting a resource's stored bytes under an attacker-chosen type. Reading a resource's bytes under a type happens via `view_value`/`try_into_move_value`, which is driven by the resource's actual stored type tag in global storage, or via `move-resource-viewer`'s `resolve_struct_tag`, which resolves the *real* module definition for the given `StructTag`, again not an attacker-aliasable mapping [3](#0-2) .

3. `convert_view_function` does allow `type_arguments` to be freely chosen by the caller and passed through as `ty_args: Vec<TypeTag>` for a generic view function [4](#0-3) , and Aptos's Move VM/global storage indexes resources strictly by full `StructTag` (address + module + name + type args) equality — there is no mechanism by which supplying a different-but-layout-compatible struct as a generic parameter causes the VM to reinterpret an unrelated resource's bytes under the wrong `struct_tag`. Any actual read of global storage (`borrow_global<T>`) is type-checked by the Move bytecode verifier/VM at the byte-code level against the real declared type, independent of this API-layer JSON-to-MoveValue conversion.

The premise conflates a JSON-argument-encoding helper (`try_into_vm_value_struct`) with actual global-storage resource-type resolution, and no evidence shows a case where a `struct_tag` embedded in a `WithTypes` layout can be attacker-substituted to alias an unrelated resource's field layout. Without a concrete demonstration that the VM's storage/type system (not just this JSON encoder) can be tricked into reading FA metadata bytes under a mismatched type, this does not cross a real custody boundary.
