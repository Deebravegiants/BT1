### Title
Attacker can permanently prevent a spoke asset from being removed by supplying 1 unit - (File: contracts/controller/src/config/asset.rs)

### Summary
`remove_asset_from_spoke` requires per-spoke scaled usage (`supplied_scaled_ray` and `borrowed_scaled_ray`) to be exactly zero before delisting an asset. Any unprivileged account can keep `supplied_scaled_ray > 0` forever by supplying a single token unit into that spoke and never withdrawing, causing every removal attempt to revert with `SpokeAssetInUse`. This is the same bug class as the Rio `removeAsset` grief (1-wei donation to the deposit pool), mapped onto XOXNO Lending's hub/spoke listing book.

### Finding Description
The spoke-asset removal path is:

```rust
// contracts/controller/src/config/asset.rs:189-201
pub(crate) fn remove_asset_from_spoke(env: &Env, hub_asset: HubAssetKey, spoke_id: u32) {
    assert_with_error!(
        env,
        storage::get_spoke_asset(env, spoke_id, &hub_asset).is_some(),
        SpokeError::AssetNotInSpoke
    );
    let usage = storage::get_spoke_usage(env, spoke_id, &hub_asset).unwrap_or_default();
    assert_with_error!(
        env,
        usage.supplied_scaled_ray == 0 && usage.borrowed_scaled_ray == 0,
        SpokeError::SpokeAssetInUse
    );
    storage::remove_spoke_asset(env, spoke_id, &hub_asset);
    ...
}
```

`supplied_scaled_ray` / `borrowed_scaled_ray` are aggregate scaled-share counters incremented by the permissionless `supply`/`borrow` flows and decremented only when users exit. Unlike the Rio case (a raw token balance the attacker must donate), here the attacker uses the normal `supply` entrypoint: a 1-unit supply mints positive scaled supply shares for the attacker's own account and pushes `usage.supplied_scaled_ray` above zero. There is no minimum supply floor that would round a dust deposit to zero shares — INV-ACCT-05 requires positive supply to mint shares, so the dust position is real usage. The attacker can additionally repay/re-supply at will, so even if governance waits for existing suppliers to exit, the attacker can re-open usage in the same block range as the removal attempt (or simply never withdraw, making the block permanent rather than race-dependent). Since `remove_asset_from_spoke` is itself a governance/admin operation executed through the controller's owner path, a single unprivileged address cheaply vetoes it.

### Impact Explanation
An asset is typically removed from a spoke when its risk parameters or market quality deteriorate — exactly when the protocol most needs the operation. The attacker permanently (or for as long as they maintain dust usage) prevents delisting, keeping the degraded asset's market active for that spoke. The cost is one token unit, which remains withdrawable, so griefing is essentially free. This mirrors the accepted Medium severity of the Rio analog: an administrative safety operation is neutralized by dust. Note the residual limitation: removal is blocked, but withdrawal/liquidation of user funds is unaffected; the impact is the blocked governance action itself plus continued exposure of the listing.

### Likelihood Explanation
Requires only a standard `supply` call on the target `(spoke_id, hub_asset)` with the minimum mintable amount. No privileged role, no capital lockup beyond dust, no timing dependence if the attacker simply holds the position. Any user anticipating or reacting to a delisting can execute it.

### Recommendation
Do not gate removal on zero aggregate usage, or gate it only on `borrowed_scaled_ray == 0` while force-migrating/reclassifying residual supply (e.g., automatically moving leftover supply into a deprecated/non-listable state, or allowing removal that internally pauses the asset and sweeps dust to revenue). At minimum, ignore usage below a dust threshold so a single unit cannot veto the operation.

### Proof of Concept
1. Governance schedules/executes `remove_asset_from_spoke(hub_asset, spoke_id)` for a deteriorating asset.
2. Attacker calls `supply(caller, account_id, spoke_id, [{ asset: hub_asset, amount: 1 }])` beforehand (or simply already holds a dust supply position).
3. `get_spoke_usage` returns `supplied_scaled_ray > 0`; removal reverts with `SpokeError::SpokeAssetInUse` at `asset.rs:197-201`.
4. The attacker repeats step 2 whenever needed, or never withdraws, making the delisting permanently unreachable at a cost of 1 token unit.

### INV-ACCT-05 — Positive position settlement requires shares

Positive supply and borrow amounts must mint shares. Positive net repayments
and gross withdrawals must burn shares; positive same-asset net settlement
must burn both supply and debt shares. Zero-share results revert at these
boundaries.

Cash credits and fees have separate rules: recapitalization mints no shares,
and protocol-reward conversion can floor to zero revenue shares.
