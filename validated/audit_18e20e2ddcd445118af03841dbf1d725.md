### Title
Unbounded ancestry-chain walk in GRANDPA justification verification can hang block execution on a crafted, permissionless consensus message - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
`AncestryChain::ancestry` walks a caller-supplied set of headers backwards via `parent_hash` pointers until it reaches a target hash, with no bound on the number of hops and no protection against cycles among the supplied headers. This function is reachable from the fully permissionless `pallet_ismp::handle_unsigned` extrinsic via the GRANDPA consensus client, so an attacker can submit a `Message::Consensus` payload whose `unknown_headers` contain a `parent_hash` cycle, causing the walk to loop forever during transaction/block execution.

### Finding Description
`GrandpaConsensusClient::verify_consensus` (`modules/ismp/clients/grandpa/src/consensus.rs`) decodes an attacker-supplied `ConsensusMessage` from the unsigned extrinsic body and calls `verify_grandpa_finality_proof`, which builds an `AncestryChain` directly from `finality_proof.unknown_headers` — a `Vec<H>` fully controlled by whoever submits the message: [1](#0-0) 

`AncestryChain::new` indexes these headers by their own hash into a `BTreeMap`, with no validation that they form a real, acyclic chain rooted anywhere in particular: [2](#0-1) 

`AncestryChain::ancestry` then walks backward from `block` toward `base` purely by following `parent_hash` lookups in that attacker-populated map: [3](#0-2) 

Nothing about the headers' `parent_hash` fields is cryptographically bound to their neighbors beyond what the attacker chooses to encode (headers just need to SCALE-decode as valid `Header` values; their `parent_hash` field can point anywhere, including back into the same submitted header set). If the submitter includes header `A` with `parent_hash = hash(B)` and header `B` with `parent_hash = hash(A)`, and seeds the walk starting from a header in that cycle (e.g. as `target` — the maximum-numbered header in `unknown_headers` — while `base`/`from` is the trusted `consensus_state.latest_hash`, which the cycle never reaches), the `while current_hash != base` loop never terminates: every lookup in `self.ancestry.get(&current_hash)` succeeds (the map always contains the cyclic entries), so the loop never hits the `None` branch that would return `Err(NotDescendent)`, and it never equals `base`.

The same unbounded-walk pattern is also used inside `GrandpaJustification::verify_with_voter_set` for `votes_ancestries`: [4](#0-3) 

This is invoked unconditionally via the permissionless `handle_unsigned` extrinsic: [5](#0-4) 

and again during `validate_unsigned`, meaning even transaction-pool validation (before the transaction is even included in a block) executes this same unbounded walk: [6](#0-5) 

### Impact Explanation
Substrate's `#[pallet::weight]` is a declared/benchmarked estimate, not an enforced instruction budget checked during execution — if the extrinsic's logic loops without returning, execution does not get preempted at the declared weight. An infinite loop inside `handle_unsigned`/`validate_unsigned` therefore hangs the thread importing/validating that block (and every node's transaction pool that tries to validate the same unsigned extrinsic), which halts block production and consensus progress for the chain — a "route unable to deliver messages" condition per the validation rubric, and considerably worse: it can stall the chain itself, not merely one route. This matches the CVE-2024-21008 bug class (crafted input causing the query/verification engine to hang) but is reachable by any unprivileged relayer submitting a single unsigned extrinsic, rather than requiring high database privileges.

### Likelihood Explanation
Exploitation requires only constructing a `Message::Consensus` payload for the GRANDPA consensus client with a `FinalityProof.unknown_headers` list containing a `parent_hash` cycle among headers whose SCALE-decoding is otherwise valid, and satisfying the earlier structural checks in `verify_grandpa_finality_proof` (`target.hash() == finality_proof.block`, a justification whose `commit.target_hash` matches, etc.) up to the point the `ancestry` walk is invoked. No signatures over individual `unknown_headers` are required — only the GRANDPA justification itself is signature-checked, and that check occurs after (or independently of) the vulnerable ancestry walk in some code paths (`verify_with_voter_set`'s own ancestry walk over `votes_ancestries` runs per-precommit before the full validation completes). This is submittable by any unprivileged relayer via the unsigned `handle_unsigned` call.

### Recommendation
Bound `AncestryChain::ancestry` with a visited-set / max-hop check so that revisiting a hash (indicating a cycle) or exceeding `unknown_headers.len()` iterations returns an error instead of looping. Apply the same bound to the ancestry walk inside `GrandpaJustification::verify_with_voter_set`. Consider also validating that `unknown_headers` forms a single connected, acyclic parent chain before any ancestry walk begins.

### Proof of Concept
Not runnable within this review's scope (no code execution / repository checkout available here), but the exploit sketch is:
1. Craft two syntactically valid `Header` values `A` and `B` (arbitrary `number`, `extrinsics_root`, `state_root`, `digest`) with `A.parent_hash = B.hash()` and `B.parent_hash = A.hash()`.
2. Include `A` and `B` (plus enough headers to satisfy `target`/`base` selection so the walk starts inside the `{A, B}` cycle) in `FinalityProof.unknown_headers`.
3. Attach a `GrandpaJustification` whose `commit.target_hash` equals the chosen `target` header's hash, satisfying earlier checks.
4. Submit this as `Message::Consensus(...)` via `pallet_ismp::handle_unsigned`; both `validate_unsigned` and on-chain execution will call `AncestryChain::ancestry`, which loops indefinitely on the `A ↔ B` cycle, hanging the node.

Given the significant hardening already present elsewhere in this codebase against very similar issues (e.g., the explicitly patched BEEFY `leaf_indices[0]` panic and GRANDPA's own `RelayHeaderNotInUnknownHeaders` typed-error fix), I was not able to fully verify from static reading alone whether some downstream/upstream check independently rejects cyclic or duplicate-hash header sets before the ancestry walk runs; a Devin session with the ability to build and run the `grandpa-verifier` crate's test harness would be needed to confirm the loop is actually unreachable-proof, i.e. to conclusively prove/disprove exploitability with a concrete test case.

impl<H: HeaderT> AncestryChain<H> {
	/// Initialize the ancestry chain given a set of relay chain headers.
	pub fn new(ancestry: &[H]) -> AncestryChain<H> {
		let ancestry: BTreeMap<_, _> = ancestry.iter().cloned().map(|h: H| (h.hash(), h)).collect();

		AncestryChain { ancestry }
	}

	/// Fetch a header from the ancestry chain, given it's hash. Returns [`None`] if it doesn't
	/// exist.
	pub fn header(&self, hash: &H::Hash) -> Option<&H> {
		self.ancestry.get(hash)
	}
}

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
}
