### Title
Webhook HMAC validation only covers the request body, allowing the `shop-domain` header to be spoofed to any tenant - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature that `Utils::HmacValidator` checks never covers the `X-Shopify-Shop-Domain` header. `Registry.process` trusts `request.shop` (parsed straight from that unauthenticated header) as the tenant identity once the body HMAC checks out, letting any holder of a validly-signed body (e.g. one generated for their own store) relabel it as belonging to an arbitrary other shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns `@raw_body` only, while `shop` is read independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value derived from the same header set: [3](#0-2) 

`Registry.process` gates entirely on that body-only HMAC, then forwards `request.shop` — the unauthenticated header value — as the tenant identity to the app's handler: [4](#0-3) 

The broken binding is: `hmac == HMAC(secret, shop ‖ body)` is what the check *should* enforce, but the gem actually enforces only `hmac == HMAC(secret, body)`, i.e. `shop` is never bound to the signature at all. This is structurally the same class of defect as the reported `MultiSig_V2` bug: an invariant that is supposed to tie two pieces of state together (`_numConfirmationsRequired <= _whiteWallet.length`, here `shop == the domain the signature actually authenticates`) is enforced at one call path but silently loses coverage through another path (`DeregisterWhiteWallet` there; the header-vs-body split here).

### Impact Explanation
Any actor who can obtain one genuinely-signed webhook body/HMAC pair from the app (trivially available to any merchant who installs the app on their own store and triggers a webhook such as `orders/create`) can replay that exact body+hmac to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different, victim shop that also uses the app. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` object claiming the data belongs to the victim shop, causing the host application to attribute attacker-controlled webhook content to another tenant — a cross-tenant data-integrity/confusion issue in a system that is supposed to isolate merchants from one another.

### Likelihood Explanation
Likelihood is high for anyone who is a legitimate (even trial) installer of the target app: they can generate their own validly-signed webhook payloads on demand and only need to modify one header value, no cryptographic secret is required.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) in the signed material that `to_signable_string` returns, or have `Registry.process` independently verify that `request.shop` matches a shop value bound into the signature (e.g. include it as part of the HMAC computation as Shopify's official webhook verification recommends), so the tenant identity cannot be swapped without invalidating the signature.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic and capture the raw POST body plus the `X-Shopify-Hmac-Sha256` header Shopify sends.
2. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (via `Request#to_signable_string`) validates successfully because only the body is signed. `Registry.process` invokes the handler with `shop: "victim.myshopify.com"`, causing the host app to process/store attacker data as if it came from the victim tenant.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
