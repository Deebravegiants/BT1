### Title
User-centric signup path bypasses backend duplicate/fraud verification, allowing local-only signup success determination - (File: `src/plans/mod.rs`)

### Summary
When a QR-code's `user_centric_signup` flag is set, `MasterPlan::do_signup` never calls the backend signup submission/poll cycle (`signup_post`/`signup_poll`) that performs the backend's authoritative duplicate-signup and fraud checks. Instead it marks the signup as `Success` purely from a locally computed `SignupReason`, mirroring the Carapace bug where a single-transaction check (`canBuyProtection`) was applied without any cumulative/state-tracked verification, letting repeated authorization events succeed without the central uniqueness gate ever running.

### Finding Description
`MasterPlan::do_signup` branches on `user_centric_signup` (sourced from backend-signed `UserData` attached to the user QR-code) and `orb.config.ignore_user_centric_signups` (default `false`): [1](#0-0) 

For the `user_centric_signup` branch, `success` is derived only from `signup_reason == SignupReason::Normal`, which is itself computed purely from local pipeline results and orb-side fraud detection: [2](#0-1) 

For the non-user-centric branch, `enroll_user::Plan::run` is invoked, which POSTs the signup to the backend and polls for completion. The comments in that function explicitly enumerate that backend-side duplicate/fraud detection is the authoritative check that this call path exercises: [3](#0-2) 

`SignupReason::Fraud` in the local computation is explicitly documented as distinct from (and weaker than) the backend's own fraud/duplicate checks: [4](#0-3) 

This is structurally the same class of bug as the Carapace `canBuyProtection` finding: a single-shot, locally-scoped check is treated as sufficient authorization, while the system's actual cumulative/state-tracked verification (here, the backend's duplicate/inflight/fraud check performed via `signup_post`/`signup_poll`) is skipped for an entire code path (`user_centric_signup == true`).

### Impact Explanation
Because the backend round-trip is skipped entirely for user-centric signups, the backend never gets the opportunity to reject a repeat, duplicate, or fraud-flagged submission for the same identity/session the way it would for orb-centric signups. `do_signup`/`report_signup_reason` will report `signup_successful()` and the UI will show a completed signup based solely on local pipeline output, with no cross-check against backend-tracked signup state (analogous to the missing "total protection subscribed" tracking in the reported bug).

### Likelihood Explanation
`ignore_user_centric_signups` defaults to `false`: [5](#0-4) 

so any signup where the backend-supplied `UserData.user_centric_signup` is `true` will take this code path by default, making the bypass reachable in the normal signup flow rather than a rare configuration edge case.

### Recommendation
Do not treat local `signup_reason` alone as sufficient for reporting signup success in the `user_centric_signup` path. Require some backend-confirmed state (equivalent to the `signup_post`/`signup_poll` round trip, or an explicit backend acknowledgment tied to the `signup_id`) before marking `enroll_user::Status::Success`/`debug_report.signup_successful()`, so backend-side duplicate/fraud tracking is always consulted regardless of signup mode.

### Proof of Concept
1. Present a user QR-code whose backend-signed `UserData` sets `user_centric_signup = true` (this is the officially supported "app does its own enrollment" mode).
2. Complete biometric capture; the local pipeline succeeds and orb-side fraud detection (`detect_fraud`) does not flag anything (`SignupReason::Normal`).
3. `do_signup` takes the branch at `src/plans/mod.rs:639-656`, sets `enroll_user::Status::Success`, and never calls `enroll_user::Plan::run` (i.e., never calls `signup_post`/`signup_poll`).
4. Repeat the same flow multiple times (e.g., with the same or colluding biometric data) — each run independently computes its own local `SignupReason::Normal` and is reported as a successful signup, since the backend's duplicate/inflight/fraud check (the only place such cross-session state is tracked, per the comments in `enroll_user.rs:162-168`) is never invoked for this path.
