### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let `msg.value` be counted twice in `Hinkal.transact`, minting unbacked shielded ETH - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` iterates over `circomData.erc20TokenAddresses` and, for every index where the token equals `address(0)`, unconditionally re-adds the full `msg.value` to that index's `balanceDif`. There is no check anywhere in `dimensionsCheck`, `checkOnchainCreation`, or `performHinkalChecks` that requires the entries of `erc20TokenAddresses` to be unique, so an attacker can list `address(0)` (or any token) more than once and have the same real balance delta credited independently to each duplicated index.

### Finding Description
The invariant the contract intends to enforce per token slot `i` is:
`balanceDif[i] == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount[i]`,
where for ETH, `balanceDif[i] = newBalances[i] + msg.value - oldBalances[i]` [1](#0-0) 
and the closing check [2](#0-1) .

`oldBalances`/`newBalances` are obtained via `getBalancesForArray(circomData.erc20TokenAddresses)` before and after `_internalTransact`/`_externalTransact` [3](#0-2) .
If `address(0)` appears twice in `erc20TokenAddresses`, both indices read the identical real `address(this).balance` before and after, so `newBalances[i]-oldBalances[i]` is identical for both. On top of that identical real delta, the loop separately re-adds the *entire* `msg.value` for each occurrence (line 101-104), rather than distributing/consuming it once across the array. There is no uniqueness constraint on `erc20TokenAddresses` in `dimensionsCheck` (only length checks) nor in `checkOnchainCreation` (only bounds `amountChanges`/`inputNullifiers` when `onChainCreation` is true) [4](#0-3) [5](#0-4) .

Because the ZK circuit (out of scope for direct inspection here, but architecturally) treats each array index as an independent "token slot" with its own nullifiers/commitments and its own public `amountChanges[i]`, nothing forces `erc20TokenAddresses[i]` to be distinct across `i`. This lets the attacker's proof legitimately satisfy two independent slot constraints (`inTotal[i] + amountChanges[i] === outTotal[i]`) for two indices that both claim to be backed by the same ETH.

Exploit call: `Hinkal.transact` with `dimensions.tokenNumber = 2`, `circomData.erc20TokenAddresses = [address(0), address(0)]`, `msg.value = X`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, both slots' `inputNullifiers` empty/zero and matching `outCommitments` created by a locally generated valid proof for two independent deposit slots of size X each. In the loop:
- i=0: `balanceDif = 0(real ETH change) + X - 0 == X` → matches `amountChanges[0]=X` ✓
- i=1: `balanceDif = 0(real ETH change) + X - 0 == X` (same `msg.value` re-added) → matches `amountChanges[1]=X` ✓

Only `X` ETH was ever sent, but the accounting logic validates `2·X` worth of new shielded value (two output commitment sets each worth `X`). `insertCommitments` then persists both output sets as valid leaves in the tree, minting `X` extra unbacked shielded ETH per duplicated slot.

Existing guards do not prevent this: `performHinkalChecks`/`dimensionsCheck` only check array *lengths* match `dimensions.tokenNumber`, never element uniqueness; `verifyProof` only checks the SNARK is internally consistent (each slot's own `in+delta=out`), not that ETH backing is claimed once; the slippage/balance `require` at line 111-114 and the balance-equation `require` at 137-146 are satisfied independently per index because the same real balance value and the same `msg.value` term are simply re-read/re-added for each duplicate index.

Note: `prooflessDeposit`'s helper `_calcTokenChangesForProoflessDeposit` deduplicates `erc20Addresses` by summing amounts into `uniqueTokens` before transferring [6](#0-5) , so the specific double-count in the question's literal wording (via `prooflessDeposit`) does not apply there. The real, exploitable instance of this bug is in `Hinkal.transact`'s per-token loop.

### Impact Explanation
An attacker can mint shielded UTXOs worth up to `(k-1)·X` extra unbacked value for any token duplicated `k` times in `erc20TokenAddresses` while only depositing `X` real value once (trivially with `address(0)`/ETH, and also possible with any ERC20 token since the same real balance is read for each duplicate index). This is direct creation of shielded value without on-chain backing, i.e., protocol insolvency — matching the "Critical: minting shielded value without backing" category. It is fully repeatable per transaction with no privileged role required, only the ability to build a valid Circom proof for two independent token slots pointing at the same token address.

### Likelihood Explanation
Preconditions are minimal: attacker needs to (1) deposit any nonzero ETH/ERC20 amount, (2) construct `circomData` with a duplicated entry in `erc20TokenAddresses` across two (or more) of the `dimensions.tokenNumber` slots, and (3) generate a valid Groth16 proof locally for a circuit with `tokenNumber ≥ 2` where two slots reference the same token — entirely within the attacker's own control (their own UTXOs/nullifiers, arbitrary encrypted outputs). No relay, oracle, or third-party interaction is required, and it can be repeated indefinitely to continually mint unbacked shielded balance.

### Recommendation
Enforce uniqueness of `circomData.erc20TokenAddresses` in `dimensionsCheck` (or a dedicated check called from `performHinkalChecks`), rejecting any transaction whose token array contains a repeated address. Additionally, restructure the `address(0)` balance formula in `Hinkal.transact` so `msg.value` is accounted for exactly once across the whole array (e.g., track a single `ethAccountedFor` accumulator that is asserted to equal `msg.value` in total, rather than adding the full `msg.value` per matching index).

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and verifier mocks/real verifier compiled from a 2-token-slot circuit instance.
2. Craft `CircomData` with `dimensions.tokenNumber = 2`, `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [X, X]`, `onChainCreation = [false, false]`, valid empty/zero nullifiers for both slots (fresh deposit), and two independently valid sets of `outCommitments`/`encryptedOutputs` generated locally via snarkjs for a proof satisfying `inTotal[i] + amountChanges[i] === outTotal[i]` for `i=0,1`.
3. Call `hinkal.transact{value: X}(a, b, c, dimensions, circomData)`.
4. Assert equality-before: real ETH sent by attacker = `X`; assert equality-claimed-by-contract: sum of validated `amountChanges` across slots = `2X`.
5. Assert transaction succeeds (does not revert on the balance-equation `require` at contracts/Hinkal.sol:137-146) despite `2X` claimed value vs `X` actual value received (`address(this).balance` increased by only `X`).
6. Assert two sets of on-/off-chain commitments worth `X` each were inserted via `insertCommitments`, i.e., total shielded value created (`2X`) exceeds `address(this).balance` delta (`X`), proving unbacked minting.

        address[] calldata erc20Addresses,
        uint256[] calldata amounts
    )
        private
        pure
        returns (TokenWithAmount[] memory uniqueTokens, uint256 uniqueCount)
    {
        uniqueTokens = new TokenWithAmount[](erc20Addresses.length);

        for (uint256 i = 0; i < erc20Addresses.length; i++) {
            bool found = false;
            for (uint256 j = 0; j < uniqueCount; j++) {
                if (uniqueTokens[j].erc20Address == erc20Addresses[i]) {
                    uniqueTokens[j].amount += amounts[i];
                    found = true;
                    break;
                }
            }
            if (!found) {
                uniqueTokens[uniqueCount] = TokenWithAmount({
                    erc20Address: erc20Addresses[i],
                    amount: amounts[i]
                });
                uniqueCount++;
            }
        }
    }
