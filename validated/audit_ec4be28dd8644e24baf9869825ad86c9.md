### Title
Integer overflow panic when decoding untrusted Pharos validator storage values before proof verification - (File: `modules/consensus/pharos/verifier/src/state_proof.rs`)

### Summary
The BSC/GStreamer-class bug — a decoder trusting attacker-supplied length/size fields from a crafted blob before validating the blob, causing an invalid-memory-read crash — has a direct analog in Hyperbridge's Pharos consensus verifier. `bls_data_slots_from_header` derives a string length from a fully attacker-controlled storage value and performs unchecked arithmetic on it *before* that storage value has been proven authentic against any trusted state root.

### Finding Description
`verify_validator_set_proof` [1](#0-0)  first calls `compute_all_storage_keys` on the caller-supplied `proof.storage_values` to derive expected storage keys, and only *afterwards* calls `verify_all_storage_proofs` to check those values against `state_root`. This ordering means `storage_values` are parsed and used for size/length calculations while still completely untrusted.

`header_val` can be any `U256` up to `U256::MAX` (bounded only by `decode_u256_from_storage`'s 32-byte length check [4](#0-3) ). If the low bit is set, `str_len = length.low_u64() as usize` truncates to the low 64 bits of a much larger value, so `str_len` can be forced arbitrarily close to `u64::MAX`/`usize::MAX`. The subsequent `str_len + 31` is unchecked addition and overflows.

This mirrors the FLIC/GStreamer bug class: a size/length field is read straight out of an untrusted, not-yet-authenticated data blob and fed into arithmetic/indexing without validating it is consistent with the actual data, producing a crash on crafted input rather than a controlled rejection.

### Impact Explanation
If the runtime is built with arithmetic-overflow checks enabled (the common Substrate/Polkadot production default), this overflow panics the runtime thread processing the extrinsic/proof, aborting execution of the consensus-update call — a denial of service against the Pharos consensus client triggered by a single relayed proof, before any cryptographic or state-root check has run. If overflow checks are disabled, the value wraps to an attacker-chosen small number, silently corrupting the derived `slots_needed`/storage-key computation, which can desynchronize the keys checked in `verify_all_storage_proofs` from what a legitimate validator set would produce — a route toward smuggling an unvalidated/incorrect validator set past verification.

### Likelihood Explanation
Reachable by any unprivileged relayer submitting a Pharos consensus proof: `ValidatorSetProof.storage_values` is attacker-supplied and is size-parsed by `compute_all_storage_keys`/`bls_data_slots_from_header` before `verify_all_storage_proofs` authenticates it against `state_root`. No signature, staking, or prior valid proof is required to reach the vulnerable arithmetic — only a well-formed extrinsic carrying a crafted 32-byte "header" slot value.

### Recommendation
Validate storage-value-derived lengths before doing arithmetic on them (e.g., bound-check `str_len` against a sane maximum, such as `MAX_VALIDATORS`-scale limits already used elsewhere in this file), and use checked/saturating arithmetic (`checked_add`, `saturating_add`) instead of raw `+` when computing `slots_needed`. More fundamentally, defer any size-driven parsing of `storage_values` until after `verify_all_storage_proofs` has authenticated the values against `state_root`, consistent with how the codebase's other consensus verifiers were hardened (`InvalidMerkleBranch`/length checks added in `sync-committee/verifier/src/lib.rs`, `MAX_PROOF_DEPTH` in `pharos/primitives/src/spv.rs`).

### Proof of Concept
1. Craft a `ValidatorSetProof` where `storage_values[1]` (the validator count) is a small valid count (e.g., `1`), satisfying the `MAX_VALIDATORS` bound.
2. Set the corresponding BLS-header storage value (`storage_values[idx]` at the position `compute_all_storage_keys` expects the header) to a 32-byte big-endian value that is odd (long-string flag set) and whose low 64 bits are close to `u64::MAX`, e.g. `header_val = 2^64 - 1` padded to 32 bytes with an odd low byte.
3. Submit this as the consensus proof for the Pharos client's `verify_consensus` [5](#0-4)  path (or directly to `verify_validator_set_proof`).
4. `bls_data_slots_from_header` computes `str_len` near `u64::MAX`, and `str_len + 31` overflows before any state-root proof check has executed, panicking (or wrapping and corrupting subsequent key derivation, depending on build profile) — before `verify_all_storage_proofs` ever runs.

Note: I could not confirm from the indexed files whether the workspace enables `overflow-checks = true` in its release profile (no `Cargo.toml` overflow-checks setting was found in the indexed content), which determines whether this manifests as a hard panic (DoS) versus a wrapping-arithmetic logic bug. pub fn verify_validator_set_proof<H: Keccak256 + Send + Sync>(
	state_root: H256,
	proof: &ValidatorSetProof,
	epoch: u64,
) -> Result<ValidatorSet, Error> {
	let layout = StakingContractLayout::default();

	// Recompute expected storage keys from the storage values
	let keys = compute_all_storage_keys::<H>(&proof.storage_values, &layout)?;

	// Verify each storage value against its per-key proof path.
	// Pharos uses a flat trie — storage proofs verify directly against state_root.
	verify_all_storage_proofs(&keys, &proof.storage_values, &proof.storage_proof, &state_root)?;

	// Decode the verified storage values into a ValidatorSet
	let decoded_set = decode_validator_set_from_storage::<H>(&proof.storage_values, epoch)?;

	validate_validator_set(&decoded_set)?;

	Ok(decoded_set)
}

pub fn bls_data_slots_from_header(header_value: &[u8]) -> Result<usize, Error> {
	let header_val = decode_u256_from_storage(header_value)?;
	let header_bytes = header_val.to_big_endian();
	let lowest_byte = header_bytes[31];

	if lowest_byte & 1 == 0 {
		// Short string - data is in the header itself
		Ok(0)
	} else {
		// Long string - header = length * 2 + 1
		let length = (header_val - 1) / 2;
		let str_len = length.low_u64() as usize;
		Ok((str_len + 31) / 32)
	}
}

pub fn decode_u256_from_storage(value: &[u8]) -> Result<U256, Error> {
	if value.is_empty() {
		return Ok(U256::zero());
	}

	if value.len() <= 32 {
		let mut padded = [0u8; 32];
		padded[32 - value.len()..].copy_from_slice(value);
		Ok(U256::from_big_endian(&padded))
	} else {
		Err(Error::StorageValueTooLarge)
	}
}
