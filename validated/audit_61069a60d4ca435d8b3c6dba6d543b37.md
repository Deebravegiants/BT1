Confirmed: `WebhookMetadata` is constructed directly from unauthenticated header fields — `shop`, `topic`, `webhook_id`, `api_version` — while `HmacValidator.validate` only checks the raw body via `Request#to_signable_string`.### Title
Webhook `shop`, `topic`, `webhook_id`, `api_version` headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values to build `WebhookMetadata` that is handed to the host app's handler. None of those header fields are part of the signed payload, so they carry no cryptographic binding to the shop that actually produced the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (the body) and compares it to the `hmac` header: [2](#0-1) [3](#0-2) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers with no signature coverage: [4](#0-3) 

`Registry.process` validates the HMAC and then immediately trusts these unauthenticated fields to build `WebhookMetadata`, which is passed straight to the host app's handler: [5](#0-4) [6](#0-5) 

The identity binding that is broken is:

`shop claimed in the `shopify-shop-domain` header` **≠** `shop that actually holds the secret which produced the HMAC over the body`.

The gem treats these as equal (it never checks them against each other), but nothing enforces that equality. The `api_secret_key` used to sign webhooks is the app's `client_secret`, shared across *every* merchant that installs the app — it is not per-shop. This is analogous to the H-7 report's root cause: a value acted upon by downstream logic (there, the RA amount used for `unsafeIssueToLv`; here, the `shop`/`topic`/`webhook_id` fields consumed by `WebhookMetadata`) is not actually covered by the same accounting/authentication mechanism (there, `lockFrom`; here, the HMAC) that the code assumes protects it.

### Impact Explanation
Any unprivileged internet user can install the target Shopify app on their own store (a fully legitimate, self-controlled tenant) and thereby receive genuine webhooks signed with the app's shared `api_secret_key`. Because the HMAC only covers the body, that attacker can capture a real, validly-signed webhook (body + hmac header) from their own shop and replay it to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and optionally `topic`/`webhook-id`) with a victim shop's domain. `HmacValidator.validate` still succeeds because the body/HMAC pair is genuinely valid, and `Registry.process` forwards `WebhookMetadata` with the attacker-chosen `shop` value to the app's handler as if Shopify had confirmed the request originated from that shop. Any host application logic that keys tenant-scoped actions (data writes, session/cache invalidation, uninstall/GDPR-redaction handling, order/customer record updates, etc.) off `WebhookMetadata#shop` can be made to act against a shop the attacker does not control — a cross-tenant integrity/confidentiality violation triggered purely by an unprivileged party with any real (even free/dev) shop.

### Likelihood Explanation
High. Registering a development/trial Shopify store and installing a target app is trivial and requires no privileged access to the app's `client_secret` or the victim's data — only that the attacker's own shop is a legitimate install of the same app (a normal, unprivileged capability for any public app). Capturing your own webhook bytes/HMAC is also trivial (you receive them on your own endpoint). No credential leakage or infrastructure compromise is needed.

### Recommendation
Bind the shop identity to the signed material instead of trusting raw headers:
- Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed payload construction (`to_signable_string`), or
- Require host applications (and enforce within the gem) to cross-check `request.shop` against the shop associated with the session/registration that the webhook was registered for, rejecting mismatches, and
- Document/verify that `WebhookMetadata` fields other than `body` must not be treated as authenticated unless additionally cross-validated by the caller.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`; app's webhook endpoint is public.
2. Attacker triggers any registered webhook topic (e.g. `orders/create`) on their own shop, capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — this HMAC is valid because it's signed with the same shared `api_secret_key` used for all installs of the app.
3. Attacker resends this exact `raw_body` + `hmac` header to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in [2](#0-1)  only checks the body against the HMAC and returns `true`.
5. `Registry.process` in [5](#0-4)  builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and invokes the host app's handler, which will act on data intended for `attacker-shop` under the victim shop's identity — a cross-tenant identity spoof achievable by any unprivileged app installer.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
