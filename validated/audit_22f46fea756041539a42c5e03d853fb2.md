Audit Report

## Title
Persistent Secret Token Disclosure via External Initiator List/Read API - ([File: core/web/presenters/external_initiators.go])

## Summary
The `GET /v2/external_initiators` endpoint returns the plaintext `OutgoingToken` secret for every registered External Initiator on every read, to any authenticated node user — including the lowest-privileged `view` role — not just the initiator's creator and not just once at creation time. This mirrors CWE-200: a list/read API meant to expose only non-sensitive metadata instead re-discloses a live outbound-authentication credential on every call.

## Finding Description
When an External Initiator is created, the node generates an `OutgoingToken`/`OutgoingSecret` pair (used by the node to authenticate itself to the initiator's webhook) alongside an incoming `AccessKey`/hashed `Secret` pair (used to authenticate calls from the EI to the node): [3](#0-2) 

The incoming secret is properly protected — never persisted in plaintext and only returned once via `ExternalInitiatorAuthentication` at creation: [4](#0-3) 

However, `OutgoingToken` is persisted in plaintext in the DB and embedded directly in `ExternalInitiatorResource`, the presenter used for the list endpoint: [5](#0-4) 

The controller's `Index` handler loads and serializes *all* External Initiators through this presenter on every call: [6](#0-5) 

Critically, this route is registered with no role-gating wrapper at all, unlike the `Create`/`Destroy` routes which require `auth.RequiresEditRole`: [7](#0-6) 

This is confirmed by the RBAC route map used in the project's own tests, which explicitly documents `GET /v2/external_initiators` as accessible to `view`-role users (`viewOnlyAllowed: true`): [2](#0-1) 

The test suite further confirms `OutgoingToken` appears in the plain `Index` response for pre-existing initiators, i.e., disclosed on every subsequent read, not solely at creation: [8](#0-7) 

The same pattern is present for `BridgeType.OutgoingToken`, exposed via `GET /v2/bridge_types` under the identical `viewOnlyAllowed: true` rule: [9](#0-8) 

## Impact Explanation
`OutgoingToken` is a bearer-style secret the node presents to the External Initiator's own service when triggering it. Because the `Index` route carries no role check, any node user session (including `UserRoleView`, the lowest tier granted for read-only dashboards) can enumerate this secret for every configured initiator/bridge, not merely ones they created. This breaks the node's own internal privilege-tiering assumption (`view` < `run` < `edit` < `admin`) by letting the lowest-privileged authenticated role read a live outbound credential intended to be edit/admin-scoped, enabling impersonation of the node's calls to third-party EI/bridge endpoints — a concrete CWE-200 secret exfiltration with a request-impersonation follow-on impact.

## Likelihood Explanation
Exploitation requires only a valid session/API token for any node user, at any role level, since the route is unauthenticated with respect to role checks (only session/token authentication is required). This is a single GET request with no further preconditions, fully reproducible via `TestExternalInitiatorsController_Index`-style calls or a live `GET /v2/external_initiators` against a node with a `view`-role user, making it trivially and repeatably exploitable by any lower-privileged internal node user.

## Recommendation
- Exclude `OutgoingToken` (and `BridgeType.OutgoingToken`) from `ExternalInitiatorResource`/bridge list-read presenters; return it only once, at creation, matching how `Secret`/`AccessKey` are already handled via `ExternalInitiatorAuthentication`.
- Gate `GET /v2/external_initiators` and `GET /v2/bridge_types` with at minimum `auth.RequiresEditRole` (or a dedicated masked-field presenter) so that `view`/`run`-role users cannot retrieve live outgoing secrets.
- If later verification of the outgoing token is required, store/expose a hash or masked value instead of the raw secret.

## Proof of Concept
1. Create an admin user and an External Initiator via `POST /v2/external_initiators` (records an `OutgoingToken`).
2. Create a second node user with role `view` (`UserRoleView`).
3. As the `view`-role user, call `GET /v2/external_initiators`.
4. Observe the JSON response includes `outgoingToken` for the initiator created by the admin user, confirming disclosure to a lower-privileged, non-creator user on every read — matching the assertions in `TestExternalInitiatorsController_Index` (`core/web/external_initiators_controller_test.go:104-109`) combined with the `viewOnlyAllowed: true` RBAC rule for this route in `core/web/auth/auth_test.go:224`.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}
