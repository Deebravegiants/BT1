Confirmed: `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers and are never included in the HMAC-signed material [2](#0-1) . `Registry.process` validates only the body's HMAC and then trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler [3](#0-2) .

### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not covered by the HMAC, allowing shop-spoofed webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating `HmacValidator.validate(request)`, which HMACs `request.to_signable_string` — the raw request body only. The `shop` field that is handed to the app's `WebhookHandler` as the tenant identifier is read from the `x-shopify-shop-domain`/`shopify-shop-domain` header and is completely outside the HMAC's coverage.

### Finding Description
`Request#to_signable_string` is defined as:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header value using `OpenSSL.secure_compare` [4](#0-3) . This proves only that the body bytes are unmodified and were signed with the app's shared secret — it says nothing about which shop, topic, or webhook-id the signer intended.

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled straight from attacker-visible HTTP headers with no cryptographic binding to the HMAC:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [5](#0-4) 

`Registry.process` uses these unauthenticated header values directly to route and label the payload delivered to the host application's handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

This breaks the binding **HMAC(shared_secret, signed_bytes) proves origin == the `shop`/`topic` values the app acts on**. In practice, the `hmac`, `shop`, and `body` should form a single authenticated tuple; here, only `body` is bound to the signature — `shop` (and `topic`, `webhook_id`) can be freely substituted by anyone who can reach the webhook endpoint and who possesses *any* validly-signed body for the shared `api_secret_key`.

An unprivileged internet user who legitimately installs the app on their own (e.g. free development) store will receive genuine webhooks with a valid HMAC signed with the app's shared `api_secret_key` (the same secret is used for every shop using the app, since there is no per-shop signing key here — only `Context.api_secret_key`/`old_api_secret_key`) [6](#0-5) . That attacker can capture one such validly-signed request and replay it to the app's webhook endpoint while swapping only the `x-shopify-shop-domain` header to a victim shop's domain. `Registry.process` will still pass `Utils::HmacValidator.validate`, because the body (the only signed material) is unchanged, and will hand the handler a `WebhookMetadata` claiming the payload is for the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker who is authenticated only as their own low-privilege tenant can make the host application process a webhook payload as if it originated from a different, victim shop. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., looking up the victim's stored session/access token to act on the victim's store, or triggering shop-scoped side effects such as data deletion for GDPR `shop/redact`), this can lead to cross-tenant access or actions being taken against a shop the attacker never had access to — matching the Critical "cross-tenant access" impact category, since the gem provides no mechanism at all to verify that the `shop` header matches the shop the signed body was actually issued for.

### Likelihood Explanation
Likelihood is realistic but not trivial: the attacker needs (a) the ability to install the target app on a shop they control (common for public apps) or otherwise obtain one validly HMAC-signed webhook body, and (b) knowledge of/interest in a specific victim shop domain and the ability to reach the app's public webhook endpoint. Because HTTP headers are fully attacker-controlled on any request reaching the endpoint, and the gem does nothing to bind `shop` to the signature, exploitation requires no secret material beyond a single legitimately obtained signed body.

### Recommendation
Include the shop domain (and ideally the topic and webhook-id) in the HMAC-signed material, or otherwise cryptographically bind them (e.g., verify the header `shop` against a value embedded in/derived from the signed body, or maintain a per-shop webhook signing context). At minimum, `Registry.process`/`WebhookMetadata` should not treat `request.shop` as trustworthy input for authorization-sensitive decisions unless it has been verified against records already associated with the signed payload (e.g., cross-check against a topic/shop pair fetched via a trusted API call), and documentation should make clear that `request.shop` is unauthenticated header data.

### Proof of Concept
1. Attacker signs up for a free Shopify development store `attacker.myshopify.com` and installs the target app so the app registers webhooks for it.
2. Shopify (or the attacker directly, since the endpoint is public) sends a legitimate webhook to the app's webhook route with headers:
   ```
   x-shopify-topic: customers/data_request
   x-shopify-hmac-sha256: <valid signature over raw body B>
   x-shopify-shop-domain: attacker.myshopify.com
   ```
3. Attacker replays the exact same raw body `B` and `x-shopify-hmac-sha256` value, but changes only:
   ```
   x-shopify-shop-domain: victim.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `to_signable_string` (`@raw_body`, unchanged) against the HMAC [8](#0-7) .
5. `handler.handle` is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's body>, ...)`, and the host application processes the payload as if it were a genuine event from the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
