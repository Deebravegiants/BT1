### Title
Excess native-token payment on `EvmHost.dispatch()` is stranded because Uniswap V2 refunds the leftover ETH to the Host contract instead of the user - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` accept native token payment and internally perform an exact-output Uniswap V2 swap (`swapETHForExactTokens`) to acquire the fee token, exactly mirroring the reported bug class: a price/value-dependent conversion executed on-chain with no slippage protection and no accounting for the fact that the AMM price used to size the required input can move between the moment the caller estimated the cost (via `quote()`) and the moment the transaction executes.

### Finding Description
Any unprivileged caller can dispatch a POST/GET request and pay in native token: [1](#0-0) 

The frontend/SDK computes the `msg.value` to send off-chain by calling `HyperApp.quote()`, which itself explicitly warns it is "vulnerable to sandwich attacks" and must only be used off-chain: [2](#0-1) [3](#0-2) 

Because `swapETHForExactTokens` is called with `to = address(this)` (the `EvmHost` contract) rather than the original caller, any ETH sent in excess of the amount actually required to buy `post.fee`/`get.fee` units of the fee token at execution-time price is refunded by the Uniswap V2 router back to `address(this)` — i.e., to the `EvmHost` contract itself, not to `_msgSender()` who paid it. The deadline parameter is also `block.timestamp`, which provides no real protection since it is always satisfied at execution time (any block will pass this check), so it offers no defense against delayed/backrun execution — the trade always executes at whatever spot price exists in that block.

Consequently:
- If the pool price is more favorable at execution than at quote time, the surplus ETH the user sent (to cover conservative slippage buffers, as the SDK explicitly does by padding quotes — see `OrderCanceller.quoteCancelFromSource`, which pads native value by 1% specifically because "pool reserves drift between quote and execution") is silently swallowed by the Host contract rather than returned to the user.
- If the pool price moves unfavorably (e.g., via front-running/sandwiching the `dispatch` call, a known MEV risk that the router-based fee model is inherently exposed to), the swap can revert, causing a denial of service for the request, or in edge cases, the same in-block price manipulation could be leveraged by third parties to force the transaction to consume nearly all of `msg.value` while only guaranteeing the exact `fee` output, wasting most of the value provided.

This is confirmed by the SDK's own defensive padding logic acknowledging the drift issue exists in production usage: [4](#0-3) 

No `IHost`/`EvmHost` interface exposes a way for a user to reclaim ETH refunded to the Host, and there is no visible sweep/withdraw-native path for users in the reviewed portion of `EvmHost.sol`.

### Impact Explanation
Funds (native ETH) sent by ordinary users dispatching cross-chain messages (a core, permissionless, frequently-used entry point reachable from any relayed/dispatched request) can be permanently lost/stranded in the `EvmHost` contract whenever the actual AMM execution price differs favorably from the quoted price used to size `msg.value`, since the leftover ETH is refunded to the contract rather than the caller. This is a direct, unprivileged loss-of-funds vector reachable from a single transaction (any `dispatch()` call paying in native token), matching the "permanent freezing/loss of funds due to lack of slippage protection" bug class validated in the report. Severity is Medium: it does not lead to protocol insolvency or forged messages, but it causes concrete, permanent user fund loss on every native-token dispatch where the quoted amount conservatively overshoots the execution-time requirement (which the SDK itself does by design, e.g. its 1%/101% padding).

### Likelihood Explanation
High likelihood of occurrence in normal operation: the SDK/documentation explicitly instruct users to over-provide `msg.value` relative to the `quote()` estimate because of expected slippage/pool drift (seen in `OrderCanceller.quoteCancelFromSource` padding by 1%, and in the docs' explicit warning about sandwich-attack exposure of `quote()`). Every such over-provision that isn't consumed by the swap becomes stuck. This does not require a malicious actor — it happens under ordinary market movement between quote-time and dispatch-time — though a malicious searcher could also amplify losses by manipulating the pool price to widen the discrepancy.

### Recommendation
- In `EvmHost.dispatch(DispatchPost)` / `dispatch(DispatchGet)` / `fundRequest`, change the Uniswap `to` parameter of `swapETHForExactTokens` from `address(this)` to `_msgSender()` (or the designated payer) so any refunded ETH goes back to the original caller instead of being retained by the Host.
- Replace `deadline: block.timestamp` with a caller-supplied deadline parameter to provide genuine transaction-staleness protection.
- Consider allowing callers to pass an explicit `maxNativeIn`/slippage-bound parameter validated against the swap's actual `amounts[0]`, and emit/return the leftover amount explicitly rather than relying on implicit router refund semantics.
- Add a sweep/rescue function (owner or per-payer) to recover any ETH inadvertently stranded in `EvmHost` from historical refunds.

### Proof of Concept
1. Caller calls `HyperApp.quote(DispatchPost)` off-chain, which reads current Uniswap V2 reserves via `getAmountsIn(post.fee, [WETH, feeToken])` and returns e.g. `1.00 ETH` needed to buy `post.fee` fee-tokens.
2. Caller pads this by a buffer (as the SDK itself does, e.g. 1–5%) and sends `msg.value = 1.05 ETH` to `EvmHost.dispatch(post)`.
3. Between the quote and the transaction's execution, the pool reserves shift favorably (natural price movement or unrelated trades), so only `0.98 ETH` is now required to buy the same `post.fee` fee-tokens.
4. `EvmHost.dispatch` executes:
```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```
5. Uniswap V2 router consumes `0.98 ETH` and refunds `0.07 ETH` — but refunds it to `address(this)` (the `EvmHost` contract), not to the caller.
6. The caller has permanently lost `0.07 ETH` with no code path to reclaim it; `EvmHost` accumulates ETH that does not belong to protocol revenue and (per the reviewed contract) has no visible corresponding user-facing withdrawal mechanism. [1](#0-0)
