### Title
Unbounded `handle_unsigned` message batch with fixed static weight enables unsigned, fee-free block-computation DoS - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet_ismp::Pallet::handle_unsigned` accepts an unbounded `Vec<Message>` (and each `Message` variant in turn carries an unbounded `Vec<Request>`/`Vec<PostRequest>`/`Vec<GetRequest>`), yet is annotated with a fixed, size-independent weight (`Weight::from_parts(300_000_000, 0)`). Because the call is dispatched as an **unsigned, fee-free extrinsic** (`ensure_none(origin)`), any unprivileged party can submit a single transaction whose actual execution cost (proof verification, membership/non-membership checks, `dedup_requests`, module callback dispatch) is arbitrarily larger than the weight the runtime accounts for it, letting one transaction consume disproportionate block computation without paying for it. This is a direct structural analog of BIT-gitlab-2020-13315/CVE-2020-13315, where an endpoint failed to bound the amount of work a single unauthenticated request could request, enabling denial of service.

### Finding Description
`handle_unsigned` is declared: [1](#0-0) 

with the weight function: [2](#0-1) 

`messages: Vec<Message>` has no `#[pallet::call]`-enforced maximum length, and `Message::Request`, `Message::Response`, and `Message::Timeout` variants each wrap their own unbounded `Vec<...>` of requests. `Pallet::execute` iterates over every message and, for each, calls `handle_incoming_message`, which for `Request`/`Response`/`Timeout` messages runs `dedup_requests` (a linear scan building a `BTreeSet`), per-request validity checks, one MMR/state membership or non-membership proof verification per batch, and one `router.module_for_id`/`on_accept`/`on_response`/`on_timeout` callback dispatch per request: [3](#0-2) [4](#0-3) 

The `validate_unsigned` hook for this call *also* fully executes `Self::execute(messages.clone())` during transaction-pool validation, before the transaction is even included in a block: [5](#0-4) 

So the unbounded-computation cost is paid twice per submission — once during pool validation, once at block execution — while the runtime's `CheckWeight` extension only ever sees the fixed `300_000_000` weight declared on the call, regardless of how many messages or requests are actually packed inside. This mirrors the GitLab bug class: an unauthenticated caller can request an arbitrarily large amount of "work" (there, activity results; here, ISMP messages/requests/proof-verifications) with no server-side cap, and the system's cost-accounting (there, pagination limits; here, declared transaction weight) does not scale with the actual work performed.

### Impact Explanation
Any unprivileged actor can submit (for free, since this is an unsigned extrinsic with `Pays::No`-style accounting via `FeeHandler`) a `handle_unsigned` call carrying a very large `Vec<Message>`, each with a large inner `Vec<PostRequest>`/`Vec<GetRequest>`, forged/garbage but well-formed enough to reach the proof-verification/dedup stage before failing. Since the pallet's weight is fixed at 300M regardless of actual size, `CheckWeight` will not reject such a transaction for exceeding declared weight, but its real execution time (hashing, dedup, proof verification, router dispatch attempts) can be made to dominate block-authoring time — validated once in the pool and again at block execution. This can stall block production or exhaust collator/validator resources, a denial-of-service against the entire chain's liveness — impacting the message dispatcher/relayer path that every application and relayer on Hyperbridge depends on.

### Likelihood Explanation
High reachability: `handle_unsigned` is explicitly permissionless and unsigned (`ensure_none(origin)`), documented as "allows users execute ISMP datagrams for free... Use with caution." No `BoundedVec` or explicit length cap exists on `messages`, `RequestMessage::requests`, `ResponseMessage::requests`, or `TimeoutMessage::{Post,Get}.requests`. An attacker needs no privileges, no fee balance beyond gossip/transaction submission costs (there are none since it is unsigned), and no valid final state — the batch only needs to survive far enough into validation (e.g., past `dedup_requests` and initial per-request checks) to burn CPU before any proof check fails.

### Recommendation
- Enforce an explicit maximum on `messages.len()` in `handle_unsigned` and on the inner `Vec<Request>`/`Vec<PostRequest>`/`Vec<GetRequest>` fields of each `Message` variant (e.g., via `BoundedVec` with a runtime-configured `MaxMessagesPerBatch` / `MaxRequestsPerMessage`), rejecting oversized batches in `pre_dispatch`/`validate_unsigned` before any handler executes.
- Make the declared weight in `#[pallet::weight(weight())]` scale with the actual size of `messages` (and nested request vectors), so `CheckWeight` can reject batches whose declared cost would exceed the block weight limit, instead of using a single static constant.
- Consider skipping full `Self::execute` inside `validate_unsigned` (or bounding it separately) to avoid doubling the unbounded-cost exposure between pool validation and block execution.

### Proof of Concept
1. Construct a `handle_unsigned` extrinsic carrying `messages = vec![Message::Request(RequestMessage { requests: <N very large well-formed but bogus PostRequests>, proof, signer }); M]` for large `N`/`M`, using distinct (non-duplicate) request payloads so `dedup_requests` does not short-circuit early.
2. Submit it as an unsigned transaction (`ensure_none` origin) to a Hyperbridge node's transaction pool.
3. Observe that `validate_unsigned` executes `Self::execute(messages.clone())`, running `dedup_requests` and per-request checks over the full unbounded batch before any error is returned, and that the declared weight for the call remains the fixed `Weight::from_parts(300_000_000, 0)` irrespective of `N`/`M`.
4. Repeat with concurrently gossiped variants (to bypass mempool same-tag dedup) to multiply the aggregate unaccounted computation imposed on every node validating and re-validating the pool, and on the collator executing the block.
