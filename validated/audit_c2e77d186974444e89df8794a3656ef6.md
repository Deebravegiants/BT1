### Title
Unbounded attacker-controlled scrypt cost parameters allow DoS during backup decryption - ([File: libraries/secure-container/src/index.js])

### Summary
The `decrypt()` function in `libraries/secure-container/src/index.js` validates a SHA-256 checksum before decoding metadata and running `scrypt`, but that checksum is computed by the attacker themselves over data they fully control, so it provides no tamper protection. An attacker who crafts an `encryptedData` buffer (e.g., via imported backup/QR/deeplink) can set `metadata.scrypt.n/r/p` to arbitrarily large `UInt32BE` values, causing `stretchPassphrase`/`scrypt` to run with attacker-chosen cost parameters before the passphrase/AES-GCM auth tag is ever verified.

### Finding Description
`decrypt()` calls `conFile.decode(encryptedData)`, then computes `checksum = sha256(metadata || blobLen || blob)` and compares it to `fileObj.checksum` [1](#0-0) . This checksum is not an HMAC or signature bound to any secret possessed only by the legitimate creator — `computeChecksum` is a plain `sha256` over publicly-derivable bytes [2](#0-1) . Since the attacker supplies the entire raw `encryptedData` buffer (including `metadata` and `blob`), they can compute a matching checksum for any content they choose, including a `metadata.scrypt` section with `n`, `r`, `p` set to the max `UInt32BE` value (4294967295), because these fields are plain `UInt32BE` values in the varstruct schema with no bounds validation [3](#0-2) .

After the checksum "passes" (trivially, since attacker computed it), `conMetadata.decode` parses the attacker-controlled `n/r/p` with no validation [4](#0-3) , and `decryptBlobKey` forwards `metadata.scrypt` directly into `boxDecrypt` [5](#0-4) . `boxDecrypt` merges these attacker params with defaults and calls `stretchPassphrase`, which invokes `scrypt(passphrase, salt, { N: n, r, p, dkLen: 32 }, 'buffer')` with no caps on `N`/`r`/`p` [6](#0-5) [7](#0-6) . Only after this potentially very expensive/OOM-triggering scrypt call completes does execution proceed to AES-GCM decryption where a wrong passphrase or corrupted data would actually be detected via the auth tag. There is no explicit rejection of oversized cost parameters anywhere in this reachable path.

### Impact Explanation
An attacker-crafted backup/import file can force the victim's device to run `scrypt` with cost parameters chosen to consume excessive CPU time and/or memory (scrypt memory usage scales with `N * r`), well before password validation occurs. This can hang or crash the wallet-unlock/import flow, constituting a denial-of-service against wallet availability triggered purely by importing an untrusted file — matching the "denial of wallet unlock/availability via malicious backup import" impact category. This does not expose secrets or bypass authentication; it is a resource-exhaustion/availability issue.

### Likelihood Explanation
This is highly feasible and repeatable: the only precondition is that the victim imports/decrypts an attacker-supplied `encryptedData` buffer (a normal use case for backups/QR/deeplink imports). No knowledge of any secret is required because the checksum is self-computable by the attacker; the file format contains no separate anti-tamper mechanism (like an HMAC keyed by a value not under attacker control, or bounded/allow-listed scrypt parameters) to prevent this. Every decrypt attempt with a malicious file will trigger the oversized `scrypt` call deterministically.

### Recommendation
Enforce strict upper bounds (and reasonable lower bounds) on `metadata.scrypt.n`, `r`, and `p` immediately after `conMetadata.decode`, before calling `decryptBlobKey`/`stretchPassphrase` — reject any values outside an allow-listed range (e.g., matching `createScryptParams` defaults or a small fixed set of supported presets). Additionally, consider deriving the checksum/authentication from a mechanism that isn't fully attacker-computable for the parts of metadata that affect resource cost, or explicitly document/enforce that `scrypt` parameters are fixed by the application layer and not taken from untrusted input.

### Proof of Concept
Unit/fuzz test plan for `libraries/secure-container/src/__tests__/`:
1. Build a valid container via `encrypt()` normally to obtain a template `encryptedData`.
2. Decode it with `conFile.decode`, then `conMetadata.decode` its metadata; mutate `metadata.scrypt.n` (and/or `r`, `p`) to `0xFFFFFFFF`.
3. Re-serialize metadata via `conMetadata.serialize`, recompute `checksum = conFile.computeChecksum(mdBuf, blob)` (attacker can do this without the passphrase), and rebuild `fileObj`/`encryptedData` via `conFile.encode`.
4. Call `decrypt(encryptedData, anyPassphrase)` with a timeout (e.g., `Promise.race` with a few-second timeout) and assert that the call either exceeds the timeout/consumes excessive memory (demonstrating the DoS), or — after a fix — that `decrypt()` throws an explicit "invalid scrypt parameters" error quickly instead of invoking `scrypt` with attacker-chosen `n/r/p`.

export async function decrypt(encryptedData, passphrase) {
  const fileObj = conFile.decode(encryptedData)

  const checksum = await conFile.computeChecksum(fileObj.metadata, fileObj.blob)
  if (!fileObj.checksum.equals(checksum))
    throw new Error('seco checksum does not match; data may be corrupted')

  const metadata = conMetadata.decode(fileObj.metadata)
  const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)
