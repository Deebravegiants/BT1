### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating only the raw request body against the HMAC, but then hands the caller's `shop` header — which is never included in that signature — to the app's handler as the authoritative tenant identifier. This breaks the intended identity binding `HMAC-verified bytes == data acted upon`.

### Finding Description
The report's bug class is "using a value that was not actually bound by the security check that was supposedly performed." The Ruby analog here is in the webhook-processing path:

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, however, is read straight from an attacker-suppliable HTTP header (`shopify-shop-domain` / `x-shopify-shop-domain`) and is never part of the signed material: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string` (the body) and compares it to the `hmac` header: [4](#0-3) 

`Registry.process` uses this HMAC check as the sole gate, then immediately trusts `request.shop` as the tenant identity passed to the handler: [5](#0-4) 

**The equality that is supposed to hold but doesn't:**
`bytes verified by HMAC` (raw body only) `== bytes the handler treats as authoritative for tenant attribution` (raw body **and** the `shop` header).

Because Shopify computes the webhook HMAC only over the raw JSON body (this is documented, standard Shopify behavior, faithfully mirrored by this gem), any entity capable of obtaining one validly-signed webhook body+HMAC pair for **any** shop (trivially available to an attacker who owns a development store or a store where they installed the app) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` will still return `true`, because it only checks the body, and `Registry.process` will call the app's handler with `WebhookMetadata` carrying the attacker-chosen `shop` value: [6](#0-5) 

Nothing in this gem cross-checks the `shop` header against the shop that the HMAC/secret actually authenticates, nor against a known/registered shop for the given `webhook_id`/topic.

### Impact Explanation
Any application built on this gem that keys tenant-scoped logic off `WebhookMetadata#shop` (e.g., "look up merchant record for this shop and apply the webhook payload", "deactivate/redact records for this shop", "sync order/customer data for this shop") can be made to attribute attacker-controlled, cryptographically "verified" data to a victim tenant it never came from. This is a cross-tenant confusion vulnerability: the app is led to believe the payload legitimately originates from `victim-shop.myshopify.com` when it was actually replayed by an unrelated attacker-controlled shop. Depending on what the handler does with `shop`, this can range from data corruption/injection into another tenant's records to triggering mandatory-compliance actions (e.g., a forged `customers/redact` or `shop/redact` webhook) against a shop the attacker doesn't control — all without ever needing the app's `api_secret_key`, an access token, or any privileged credential.

### Likelihood Explanation
Likelihood is high for any unprivileged internet user who can install the target app on their own (even free/dev) store: they can trigger a real webhook for their own shop, capture the valid raw body + `X-Shopify-Hmac-Sha256` value, and replay it to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No IP allow-listing, mTLS, or additional per-shop binding is enforced anywhere in this gem's webhook path (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`) — the HMAC check is the only defense, and it does not cover the `shop` field.

### Recommendation
Bind the `shop` (and ideally `webhook_id`/`topic`) into the value that is HMAC-verified, or otherwise independently verify that the `X-Shopify-Shop-Domain` header corresponds to a shop for which the app holds a session/registration before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant attribution without an out-of-band check (e.g., matching against a known/installed shop list) — or change `Request#to_signable_string` / `Registry.process` so the shop header participates in the trust decision.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store, `attacker.myshopify.com`.
2. Attacker triggers any webhook (e.g. `orders/create`) and captures the raw POST body `B` and the valid `X-Shopify-Hmac-Sha256: H` header sent by Shopify (computed by Shopify using the app's real secret over `B`).
3. Attacker sends a new HTTP request to the app's webhook endpoint with:
   - Body: the exact same `B`
   - Headers: `X-Shopify-Hmac-Sha256: H` (unchanged, still valid because it signs only `B`), `X-Shopify-Topic: orders/create`, `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` (`B`) and matches `H` — validation passes.
5. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the application to act as if `victim-shop.myshopify.com` sent this data, even though it originated entirely from the attacker's own store.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
