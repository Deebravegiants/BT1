### Title
Webhook Shop-Domain Header Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw JSON body of an incoming webhook via HMAC, while the `shop` (and `topic`/`api_version`/`webhook_id`) values used to route and attribute the webhook are taken from unauthenticated HTTP headers. Because Shopify signs webhooks with the app's single shared `client_secret` (identical for every shop that installs the app), a party who can obtain one validly-signed webhook (e.g., by installing the app on their own store) can replay that exact body with a forged `shop-domain` header pointing at a different (victim) shop, and the HMAC check will still pass — the equality `bytes_verified_by_hmac == bytes_acted_on` is broken specifically for the `shop` field.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` reads the `hmac-sha256` header: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled from separate, unsigned headers: [2](#0-1) 

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (the body) and compares it against the `hmac` header, never incorporating `shop`, `topic`, or any other header: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, and then forwards the unauthenticated `request.shop` value straight into the handler as the tenant identity, alongside the (signed) body: [4](#0-3) 

The equality the library implicitly claims to enforce is:
`hmac_signed_bytes == bytes_the_handler_trusts_for(shop, topic, webhook_id, api_version)`

In reality only the body is in `hmac_signed_bytes`; `shop`, `topic`, `webhook_id`, and `api_version` are outside it. Since the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is the same across every shop that has installed the app, any legitimate installer can capture one genuinely-signed webhook and retransmit its exact bytes with a different `shop-domain` (and/or `topic`/`webhook_id`) header value. `Registry.process` will still validate it as authentic and hand the handler a `WebhookMetadata` claiming it came from the attacker-chosen shop.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` to key merchant data (the standard integration pattern shown in the gem's own docs and tests, e.g. `data.shop`) can be made to attribute forged/replayed webhook content to an arbitrary victim shop domain chosen by the attacker. This is a cross-tenant data-integrity/confusion issue: an unprivileged user who is a legitimate installer of the app on their own store can produce data that the app associates with a different merchant's shop record purely by relabeling the `shop-domain` header on a replayed, still-HMAC-valid payload. This satisfies the "cross-tenant access" impact category, since tenant attribution (shop identity) is not cryptographically bound to the authenticated bytes.

### Likelihood Explanation
Exploitation only requires installing the target app on any shop (including the attacker's own free/dev store) to obtain one genuinely HMAC-signed webhook delivery, then replaying that exact body to the app's webhook endpoint with a modified `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header. No access to the app's `client_secret`, no token theft, and no privileged account are required — only the ability to receive one legitimate webhook as any installer, which is the normal, expected, unprivileged use of the library.

### Recommendation
Bind the shop (and ideally topic/webhook-id) identity into the value verified by the HMAC, or otherwise enforce an out-of-band binding: e.g., require the caller to independently verify `request.shop` against a known/authorized shop for the delivery URL or session context before trusting it, or have `Registry.process` cross-check the `shop-domain` header against a shop value embedded in the (signed) request body/topic-specific payload where Shopify includes one. At minimum, document prominently that `request.shop` is unauthenticated and must not be used as a sole tenant key without additional verification, and consider validating it against records already known to belong to that specific webhook subscription (e.g., matched by `webhook_id` from a lookup in your own storage), rather than trusting the header value emitted directly into `WebhookMetadata`.

### Proof of Concept
1. Install the vulnerable app on an attacker-controlled store `attacker.myshopify.com` and trigger any webhook (e.g. `orders/create`) so Shopify sends a valid, HMAC-signed POST to the app's webhook endpoint.
2. Attacker captures the raw body and the `x-shopify-hmac-sha256` value from that request (both delivered to a listener under the attacker's control).
3. Attacker resends an identical POST to the app's webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. In `Webhooks::Registry.process`, `Utils::HmacValidator.validate(request)` at [5](#0-4) 
passes because it only checks the (unchanged) body against the (unchanged) HMAC.
5. The handler receives `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` and, following the pattern documented in the gem's own usage examples, records/acts on the replayed body as if it genuinely originated from `victim.myshopify.com`, even though the victim never sent it.
