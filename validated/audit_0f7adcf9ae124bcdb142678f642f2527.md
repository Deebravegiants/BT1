### Title
Reentrancy in Tron `IntentGatewayV2` due to missing `ReentrancyGuard` protection - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The canonical EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol`) was previously vulnerable to a reentrancy attack in its order-fill logic where an attacker-controlled `beneficiary` receiving native ETH output could re-enter `fillOrder` before `_filled[commitment]` was set, allowing theft of escrowed fees/inputs. This was fixed by adopting a checks-effects-interactions pattern (`_filled[commitment] = msg.sender` set at the top of `_fillSameChain`/`_fillCrossChain`) and by inheriting `ReentrancyGuardTransient` with `nonReentrant` on both `placeOrder` and `fillOrder`, as documented and regression-tested in `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
The Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, declares its inheritance as `contract IntentGatewayV2 is HyperApp, EIP712` — it does **not** inherit `ReentrancyGuard`/`ReentrancyGuardTransient` at all, unlike the EVM version. [5](#0-4) 

Additionally, `placeOrder` in the Tron contract is declared `public payable` with no `nonReentrant` modifier, in contrast to the EVM version's `placeOrder(...) public payable nonReentrant`. [6](#0-5) [2](#0-1) 

`placeOrder` also performs native-token transfers to an external `dispatcher` address (`dispatcher.call{value: amount}("")`) mid-function, before all escrow bookkeeping (`_orders[commitment][token] += ...`) and the final `OrderPlaced` event are completed, giving an external contract (the `CallDispatcher`, or any contract it forwards control to) an opportunity to re-enter during predispatch execution. [7](#0-6) 

This mirrors the audit report's bug class: an external call (analogous to `_safeMint`'s `onERC721Received` callback) occurring before critical accounting is finalized, with no reentrancy guard present to stop a re-entrant call. I was unable to fully read the `fillOrder`/`_fillSameChain`/`_fillCrossChain` equivalent logic in this file within the available tool budget to confirm whether the CEI fix (`_filled[commitment] = msg.sender` set first) was also ported to Tron, but the complete absence of the `ReentrancyGuard` inheritance and of any `nonReentrant` modifier anywhere in this file (confirmed via search) means even if CEI ordering was copied, any code path that was missed or diverges during the port has no defense-in-depth backstop. [8](#0-7) 

### Impact Explanation
If the fill/withdraw logic in the Tron contract has the same interactions-before-effects flaw the EVM version had before its fix (which the missing guard cannot catch), a malicious solver-selected beneficiary contract could re-enter mid-fill and drain escrowed input tokens or fees intended for legitimate solvers/protocol — a direct theft of user/protocol funds analogous to the EVM `testReentrancy_FeeTheft` / `testReentrancy_EscrowTheft_MultiOutput` scenarios. [9](#0-8) 

### Likelihood Explanation
Reachable directly by any unprivileged actor placing/filling an order and controlling the `beneficiary`/`predispatch` calldata target — no special privileges required, matching the "single submitted transaction" reachability bar. Likelihood depends on whether the `_filled`-style guard was correctly ported alongside removing `ReentrancyGuard`; since I could not confirm the fill function body, this should be treated as unverified but high-priority to check given the missing guard.

### Recommendation
Add `ReentrancyGuardTransient` (or equivalent) inheritance and `nonReentrant` modifiers to `placeOrder`, `fillOrder`, `cancelOrder`, and `withdraw` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to match the hardening already applied to `evm/src/apps/IntentGatewayV2.sol`, and audit the fill/withdraw functions for the same CEI ordering fix (mark `_filled[commitment]` before any external value transfer).

### Proof of Concept
Not independently constructed — I could not read the Tron contract's `fillOrder`/`_fillSameChain` implementation within the available tool budget to build a concrete reentrant call sequence. The EVM version's pre-fix exploit (documented in `IntrinsicIntentsReentrancyTest.sol`) is the template: a `receive()` callback on the beneficiary re-enters `fillOrder`/`placeOrder` during the native-token transfer before escrow/`_filled` state is finalized. [10](#0-9) 

**Uncertainty**: I was unable to view the full `fillOrder`/`_fillSameChain`/`withdraw` bodies of `evm/tron/contracts/apps/IntentGatewayV2.sol` due to tool-call limits, so I cannot confirm with certainty whether the CEI fix was independently applied there despite the missing `ReentrancyGuard`. Given the codebase index's size limits, a full manual review of this file (recommended via a Devin session) would be needed to conclusively confirm or rule out an exploitable reentrancy path.
