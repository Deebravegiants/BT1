### Title
`accrue()` embeds a treasury fee-mint inside a `try!` that can permanently brick all vault operations - (File: mainnet/contracts/vault/v0-vault-stx.clar and equivalent v0-vault-* files)

### Summary
Every state-changing vault entrypoint (deposit, redeem, borrow, repay, flashloan) begins with `(u (try! (accrue)))`. `accrue()` computes a protocol reserve fee and mints it to `.dao-treasury`, wrapping that mint in `try!` and also computing a division whose denominator can reach zero/underflow. Just like the Canto `PostTxProcessing` hook mixing an unrelated CSR side-effect into every EVM transaction, `accrue()` mixes an unrelated treasury bookkeeping step into every user-facing operation, so a failure in that side path reverts (or permanently blocks) transactions that have nothing to do with the treasury mint.

### Finding Description
`accrue()` is defined identically across `mainnet/contracts/vault/v0-vault-*.clar` files: [1](#0-0) 

The critical computation is:
```
(reserve-inc (mul-div-down debt-delta (var-get fee-reserve) BPS))
(treasury-lp (if (> reserve-inc u0) (mul-div-down reserve-inc (total-supply) (- (total-assets-preview) reserve-inc)) u0))
...
(if (> treasury-lp u0) (try! (ft-mint? zft treasury-lp .dao-treasury)) false)
```
The denominator `(- (total-assets-preview) reserve-inc)` underflows or hits zero whenever the accrued reserve share (`reserve-inc`) reaches or exceeds `total-assets-preview` (e.g., when the vault's live asset base is very small relative to outstanding scaled debt, such as after most liquidity has been withdrawn while debt is still accruing interest). In Clarity, both uint underflow and integer division by zero cause the transaction to abort. Because `accrue()` is invoked via `try!` as the very first step of `deposit`, `redeem`/`withdraw`, `borrow`, `repay`, and `flashloan` in every vault contract: [2](#0-1) 

...a single failing accrual computation blocks *all* subsequent vault activity, not just the treasury fee-mint that triggered it. Since `next-index`/`next-liquidity-index` are monotonically increasing with elapsed time, once `debt-delta`'s reserve share catches up to (or exceeds) the shrinking `total-assets-preview`, the condition does not self-heal — every future call that must call `accrue()` first will keep hitting the same underflow/division-by-zero and abort, with no external caller able to change `principal-scaled`, `index`, or `assets` because every entrypoint requires `accrue()` to succeed first.

### Impact Explanation
This is directly analogous to the referenced bug class: an unrelated internal bookkeeping operation (treasury reserve minting) is entangled with the success of core, unrelated user operations (deposits, withdrawals, borrows, repayments), because it's `try!`-wrapped inside a function that gates all of them. Where the CSR report describes a *temporary* revert-per-tx, here the vulnerable path can become a *permanent* denial-of-service on the entire vault: once the arithmetic condition is hit, no user can deposit, withdraw, borrow, or repay again, since `accrue()` will always be executed and always abort. This maps to "permanent freezing of funds" (Critical) for all depositors and borrowers in that vault.

### Likelihood Explanation
Likelihood depends on how easily `total-assets-preview` can shrink close to `reserve-inc` relative to outstanding debt-delta — e.g., large withdrawals draining the vault's underlying balance while a sizable scaled-principal debt continues to accrue index growth. I was not able to retrieve the exact `mul-div-down`/`total-assets-preview` implementations before the tool budget ran out, so I cannot fully confirm the precise numeric conditions or whether any guard exists elsewhere to prevent `total-assets-preview` from falling below `reserve-inc`. This should be validated against the full `total-assets-preview`, `next-index`, and `mul-div-down` definitions in a follow-up session (e.g., via a live Devin session with full file access) before treating this as fully confirmed.

### Recommendation
Do not gate core lending/vault operations on the success of the treasury reserve-fee mint or its underlying division. Compute `treasury-lp` defensively (e.g., clamp the denominator, skip the mint gracefully with a log/no-op if the computation would underflow/divide-by-zero) rather than embedding it in a `try!` that aborts the entire calling transaction, mirroring the recommended fix for `PostTxProcessing`: log/skip on failure and continue rather than reverting unrelated operations.

### Proof of Concept
Conceptual sequence (cannot be fully validated without `mul-div-down`/`total-assets-preview` source):
1. Vault has active scaled debt (`principal-scaled > 0`) while most underlying liquidity has been withdrawn, so `total-assets-preview` is small.
2. Time passes; `next-index` increases `debt-delta`, and `reserve-inc = mul-div-down(debt-delta, fee-reserve, BPS)` grows to equal/exceed `total-assets-preview`.
3. Any user calls `deposit`, `redeem`, `borrow`, or `repay`; each internally calls `(try! (accrue))`. [2](#0-1) 
4. Inside `accrue()`, `(- (total-assets-preview) reserve-inc)` underflows/hits zero, aborting the transaction. [3](#0-2) 
5. Because `index`/`lindex`/`assets` state is never updated (the abort discards all state changes), the same condition recurs on every subsequent call, permanently freezing the vault.
