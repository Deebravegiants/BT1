### Title
Webhook `shop`/`topic` identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are never part of the HMAC-signed material. `Registry.process` validates the HMAC and then trusts these unsigned headers as the tenant identity passed to the app's `WebhookHandler`, breaking the binding `HMAC-verified bytes == identity acted upon`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` for HMAC validation, but its signable string is only the raw body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from HTTP headers, which are completely outside the signed content: [2](#0-1) 

`Registry.process` validates the HMAC of the `Request` object and, once it passes, unconditionally trusts `request.topic` and `request.shop` to build the `WebhookMetadata` handed to the app's handler — the value used to identify which tenant/shop the event belongs to: [3](#0-2) 

`WebhookMetadata.shop` is a plain, unauthenticated field the host application is expected to use to look up the tenant/session the event pertains to: [4](#0-3) 

Because a single `client_secret` (`Context.api_secret_key`) is shared across every shop that installs the app, `OpenSSL::HMAC` computed over the body is identical no matter which shop the event genuinely came from — the signature never binds to shop or topic: [5](#0-4) 

The identity binding that should hold is:
`hmac-verified request == (body, shop, topic)`

but the actual code only enforces:
`hmac-verified request == (body)`

leaving `shop` and `topic` as attacker-controlled headers once a valid `(body, hmac)` pair is obtained.

### Impact Explanation
Any unprivileged internet user can install the app on their own (free/dev) store and receive a genuine, correctly signed webhook from Shopify for an event they trigger themselves (e.g., `orders/create`). Because the HMAC only covers the JSON body, the attacker can replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers with an arbitrary victim shop domain / topic. `Registry.process` will validate successfully (`HmacValidator.validate` only checks the body-derived signature) and dispatch the forged event as if it belonged to the victim shop, via `WebhookMetadata#shop`. Any host-application logic keyed off `data.shop` (billing state changes, order/customer record creation, GDPR redaction triggers such as `customers/redact`, `shop/redact`, feature flags, notifications, etc.) can be manipulated for a tenant the attacker does not control — a cross-tenant integrity/impersonation issue.

### Likelihood Explanation
High feasibility: obtaining a legitimately signed body+HMAC pair requires only installing the app on a store the attacker controls (no special privileges, no leaked secrets, no TLS interception). Crafting the HTTP request with modified headers is trivial once the app's public webhook endpoint is known (webhook endpoints are, by design, unauthenticated HTTP endpoints reachable from the internet).

### Recommendation
Bind the security-relevant identity fields into the signed material, or independently authenticate them:
- Change `to_signable_string` (or add a companion check) so the HMAC covers `shop`, `topic`, and `webhook_id` in addition to the body, rejecting any request whose header values were altered post-signing; or
- Have `Registry.process` cross-check `request.shop` against the set of shops the app has legitimately installed/expects for that specific delivery, rather than trusting the header verbatim; and
- Document to gem consumers that `WebhookMetadata.shop`/`topic` must not be treated as cryptographically authenticated on their own — only the raw body is HMAC-protected.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (no special access required).
2. Attacker triggers a webhook event (e.g., creates an order), causing Shopify to POST a JSON body `B` to the app's webhook endpoint with header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(client_secret, B)` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker resends the exact same body `B` and header `X-Shopify-Hmac-Sha256: H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `request.to_signable_string` (`= B`) — validation succeeds because `H` still matches `B` signed with the shared `client_secret`: [6](#0-5) 
5. The app's registered handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, body: B, ...)`, causing the host application to act on data as if it came from `victim-shop.myshopify.com`, despite the attacker never having access to that shop or its credentials.
