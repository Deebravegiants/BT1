### Title
Missing sane bounds on solver liquidity weights lets a single bidder dictate the published phantom-order price - ([File: sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts])

### Summary
`aggregatePhantomBids` prices every phantom-intent leg with a liquidity-weighted median where each solver's "weight" is an unbounded, self-controlled on-chain token balance read live via `eth_call`. There is no cap, normalization, or minimum-diversity check on that weight, so a single solver who transiently holds the majority of a leg's output-token inventory sets the leg's published `medianPrice` to its own quote verbatim, exactly the "no sane bounds on weight" bug class from the report (there the weight was an admin-set `uint256`; here it is a solver-set effective weight derived from a balance the solver fully controls).

### Finding Description
The weighting function is a direct analog of `veTokenMinter.veAssetWeights`: an unbounded numeric input multiplies/divides into a payout-relevant quantity with no min/max sanity check.

`weightedMedian` picks one bidder's exact price once its cumulative weight crosses half of `totalWeight` — it is a *selection*, not a blend: [1](#0-0) 

The weight fed into it is simply the solver's live ERC-20 + vault + Uniswap V4 position balance for that leg's output token, read at snapshot time with no bound relative to the leg's total depth, no time-weighting, and no per-solver cap: [2](#0-1) 

The project's own documentation confirms the consequence explicitly: *"a solver holding over half the leg's weight sets the published price verbatim, and the result can never be a value nobody quoted."* [3](#0-2) 

That verbatim price is then written straight into the pool's published rate, which `updateLiquidityPools` derives per-leg and per-direction from the median with no additional bounding against a reference price: [4](#0-3) 

Downstream, this indexed rate is exactly what the SDK uses to compute a user's quoted `amountOut` for real intents: [5](#0-4) 

Just as the original report's admin could set `veAssetWeights` to `0` or `type(uint256).max` and skew `Booster.rewardClaimed`'s payout ratio with no guardrail, an unprivileged phantom-order solver can inflate its own effective weight (e.g., by parking capital in the leg's output token immediately before a bid window closes, or by declaring a large Uniswap V4 position it happens to control) to unilaterally dictate the leg's `medianPrice` with no bound checking that the weight is not disproportionate to the rest of the market's declared liquidity.

### Impact Explanation
A single solver that dominates a leg's weight can move `PoolChainLiquidity`/`LiquidityPool` `sellRate`/`buyRate` away from the true market rate. Users constructing intents via `quoteIntent`/`queryBuyAndSellRates` compute their expected `amountOut` from this manipulated rate; a solver skewing the rate in its own favor can extract value when it later fills the resulting intent at the (mispriced) rate the user was quoted, causing the counterparty to receive less value than a fair market rate would provide. This is a loss-of-funds/mispriced-trade impact analogous to the "excessive inflation/deflation" impact in the original report, reachable purely by submitting bids as an ordinary, permissionless intent solver — no admin or governance action required.

### Likelihood Explanation
Any address that can bid as a phantom-order solver and hold (even transiently) the output token or a declared Uniswap V4 position on the destination chain can influence the weight computation; the balance read is a plain `eth_call` at snapshot time with no historical averaging or diversity requirement, so temporarily concentrating capital in a thin leg is a realistic, low-cost attack, particularly on legs where liquidity is naturally sparse (a "leg where no bidder holds the output token is absent from the result" already shows liquidity can be very thin for some legs).

### Recommendation
Bound a single solver's influence on `weightedMedian`, e.g., cap any one bidder's weight at some fraction (e.g., 25–33%) of `totalWeight` before computing the cumulative threshold, require a minimum number of distinct bidders/weight diversity before publishing a rate for a leg, and/or cross-check the resulting `medianPrice` against an external reference price (oracle or prior published rate) with a maximum deviation bound before writing it to `LiquidityPool`.

### Proof of Concept
1. A solver monitoring phantom bid windows identifies a leg with thin liquidity (few or no other bidders holding the output token).
2. Immediately before the bid window closes, the solver acquires/parks output-token balance (or declares a Uniswap V4 position) on the destination chain sufficient to exceed 50% of the leg's aggregate weight, then submits a bid quoting a price favorable to itself, per `runAggregation`'s weight computation: [2](#0-1) 
3. `weightedMedian` selects this solver's exact quoted price as the leg's `medianPrice` because its cumulative weight crosses `totalWeight / 2` first: [6](#0-5) 
4. `updateLiquidityPools` writes this skewed price into the pool's published `sellRate`/`buyRate`: [4](#0-3) 
5. A subsequent user quoting/filling an intent against this pool receives an `amountOut` computed from the manipulated rate, to the manipulating solver's benefit.

// Liquidity-weighted median of solver quotes. Each quote's influence is proportional to `weight` —
// the solver's total balance for the output token across native + vault venues — so a solver that
// can actually deliver size moves the price more than one quoting on thin liquidity. Returns the
// lower weighted median: the smallest price whose cumulative weight reaches half of the total.
// Zero-weight quotes contribute nothing.
//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}
