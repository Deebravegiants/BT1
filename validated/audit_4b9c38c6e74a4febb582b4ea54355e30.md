### Title
`Config::download()` can flip `ignore_user_centric_signups` mid-signup, causing a race that skips backend enrollment verification for an in-flight signup - (File: src/plans/mod.rs, src/brokers/observer.rs, src/config.rs)

### Summary
The external report's bug class is: a critical, globally-scoped configuration value can be changed *while an in-flight operation depends on it staying stable*, and different phases of that operation observe different values of the same "logical" config, producing an inconsistent/unsafe outcome (funds stuck, in `PaymentSettler`). The orb-core analog is the shared `Arc<Mutex<Config>>` object, which is wholesale-replaced by a background task every `CONFIG_UPDATE_INTERVAL` (10s) regardless of whether a signup is currently in progress, and the signup pipeline reads individual config fields from that mutex at different, non-atomic points in time rather than taking one consistent snapshot for the whole signup lifecycle.

### Finding Description
`DefaultPlan::config_update` in the observer broker downloads a fresh `Config` from the backend and unconditionally replaces the entire shared config object at a fixed interval, with no check on whether a signup is currently active: [1](#0-0) 

The polling loop that drives this call is gated only on network availability, not on `signup_flag`: [2](#0-1) 

`Config::download_and_store` similarly performs an atomic swap of the whole struct: [3](#0-2) 

Inside `MasterPlan::do_signup`, most config values used throughout a signup are captured once, at the very top, into local variables (`self_serve`, `pcp_v3`, relay timeouts, `operator_qr_expiration_time`): [4](#0-3) 

However, `ignore_user_centric_signups` is *not* captured in that initial snapshot. It is instead read fresh from the live, possibly-already-mutated `Config` at the very end of the signup, after biometric capture, the ML pipeline, fraud detection, and PCP upload have all completed (which can take many seconds — well beyond the 10s config poll interval): [5](#0-4) 

The `user_centric_signup` boolean itself originates from data supplied by the *unprivileged* signing-up user's mobile app QR payload (`orb_qr_link::UserData::user_centric_signup`), fetched via `backend::user_status::request`: [6](#0-5) 

The branch at line 639 decides whether the orb performs actual backend enrollment verification (`self.enroll_user(...)`, which calls `signup_post`/`signup_poll` and can return `SignupVerificationNotSuccessful`/`ServerError`) or whether it *skips* that backend round-trip entirely and just trusts the locally-computed `signup_reason` as the outcome: [7](#0-6) 

Because `ignore_user_centric_signups` is read live rather than from the signup's initial config snapshot, a background config download that completes mid-signup (which is entirely normal, unauthenticated-by-signup-state behavior — it runs every 10 seconds independent of `signup_flag`) can flip the branch taken for a signup whose QR code already declared `user_centric_signup = true`. If the config toggles from `ignore_user_centric_signups = true` (force backend verification) to `false` partway through a lengthy capture/pipeline, the signup that started under a "must verify against backend" policy silently finishes under a "trust the client-declared flag" policy — bypassing the backend's duplicate/fraud check (`signup_post`/`signup_poll`) for that specific signup even though the deployment's config, at signup submission time, mandated it.

This mirrors the `PaymentSettler::setStablecoin` pattern exactly: a shared, globally mutable configuration value is changed with no regard to in-flight state, and different phases of one already-open transaction/session observe inconsistent versions of that value, producing a result the system's design invariants do not intend.

### Impact Explanation
If this race lands unfavorably, a signup is completed and its `enrollment_status` marked `Success` based purely on on-device fraud/liveness signals (`signup_reason == SignupReason::Normal`) without the backend-side verification step that would otherwise run (duplicate iris check, backend fraud detection, etc.). This is a concrete "fraud/liveness bypass" style impact: a signup that the operator's currently-mandated policy (`ignore_user_centric_signups = true`) requires to be centrally verified is instead accepted client-side, purely because the global config object was swapped underneath the in-flight signup. This can lead to unauthorized/misattributed identity enrollment being accepted (analogous to funds/claims being mishandled in the smart-contract report).

### Likelihood Explanation
Likelihood is Low-to-Medium: it requires (a) the backend to actually flip `ignore_user_centric_signups` (or the app's `user_centric_signup` value semantics) between two consecutive 10-second config polls, and (b) a signup to be in-flight (capture + biometric pipeline can easily take well over 10 seconds) at exactly the moment the swap lands. This is a background/legitimate operation (periodic config refresh), not a malicious peer/operator action, so it does not fall under a rejected category — it is a genuine timing/config-consistency bug reachable purely by normal operational config changes colliding with in-progress signups.

### Recommendation
Capture `ignore_user_centric_signups` (and any other flag used to decide enrollment/verification policy) into the same initial `Config` snapshot destructured at the top of `do_signup` (lines 497-506), so the entire signup lifecycle consistently uses the policy that was in effect when the signup started, rather than re-reading the live, concurrently-mutable `Arc<Mutex<Config>>` at a later decision point. More generally, `DefaultPlan::config_update` should avoid replacing config fields that affect signup-verification policy while `signup_flag` is set, or the signup pipeline should snapshot the *entire* `Config` once at `do_signup` entry and use only that snapshot for the duration of the signup.

### Proof of Concept
Not directly executable without live backend/config-server access, but the race is reproducible logically:
1. Start with backend config `ignore_user_centric_signups = true`.
2. User's QR payload sets `user_centric_signup = true` (backend `authenticated_app_data`).
3. Orb begins `do_signup`; biometric capture + ML pipeline run for >10s.
4. Meanwhile, `DefaultPlan::config_update` (triggered every `CONFIG_UPDATE_INTERVAL`) downloads a new config where `ignore_user_centric_signups = false`, and swaps it into `orb.config` via `*config.lock().await = new_config` — unconditional on `signup_flag`.
5. `do_signup` reaches line 639, reads the now-mutated `orb.config.lock().await.ignore_user_centric_signups == false`, takes the `user_centric_signup && !ignore_user_centric_signups` branch, and marks the signup `Success`/`Error` purely from `signup_reason`, skipping the backend `enroll_user` verification call entirely — even though the policy in effect when the signup began required backend verification.

        if self.before_config_update()? {

                Some(None) => return Ok(()),
                Some(Some(result)) => result??,

            let ui = observer.ui.clone();

                    *config.lock().await = new_config;
                    config.lock().await.propagate_to_ui(ui.as_ref());
                }
                Ok(())
            }));
        }
        Ok(())
    }
