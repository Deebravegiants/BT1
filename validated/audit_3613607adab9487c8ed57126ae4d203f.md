## Title
Webhook HMAC only covers the raw request body, not the `shop-domain` or `topic` headers, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC exclusively over the raw JSON body via `to_signable_string`, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to route and attribute the webhook are read directly from unauthenticated HTTP headers that are never included in the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are parsed straight from HTTP headers with no cross-check against the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the *body* was produced with the app's `api_secret_key`) and then unconditionally trusts `request.shop` and `request.topic` — values that live outside the signed scope — to build `WebhookMetadata` and dispatch to the matching handler: [3](#0-2) 

This is the same class of bug as the H-8 report: an identity-binding field (`shop`) is *acted on* (used to attribute/route the webhook to a tenant) but is *not covered* by the HMAC that is supposed to authenticate the request. The equality that should hold — `shop authenticated by HMAC == shop stored/used as the tenant key` — is broken because the HMAC only authenticates the body bytes, not the header bytes.

Because Shopify apps use a single, app-wide `api_secret_key` shared across every installed shop (not a per-shop secret), any merchant who has the app installed on their own store legitimately receives webhooks with valid `hmac-sha256` signatures over bodies whose content they substantially influence (e.g. by editing product/order fields that appear in the payload). Since the header values are unsigned, that same valid `(body, hmac)` pair can be replayed with an arbitrary `shopify-shop-domain` and/or `shopify-topic` header, and `Registry.process` will still accept it as authentic — attributing the webhook, and any handler side effects (data writes, cache updates, entitlement changes, etc.) keyed by `WebhookMetadata#shop`, to a victim shop chosen by the attacker.

### Impact Explanation
This breaks the tenant boundary that the webhook signature is supposed to enforce: a request that only proves "this body was HMAC'd with the app's secret" is treated as proof of "this event came from shop X." An attacker with no more than legitimate access to their own installation can craft `(shop, topic, body)` combinations that a host application built on this gem will process as if they originated from a different, victim tenant, i.e., cross-tenant access rooted in this gem's own request-parsing/authentication logic.

### Likelihood Explanation
Any app built with this gem's webhook handling is affected. Exploitation only requires the attacker to control (or have installed) one instance of the app, obtain a legitimately-signed webhook for their own shop, and replay it against the webhook endpoint with modified `shopify-shop-domain`/`shopify-topic` headers — no access to `api_secret_key`, tokens, or victim credentials is needed.

### Recommendation
Include the `shop-domain`, `topic`, and `webhook_id` header values in the HMAC-signed content (or otherwise cryptographically bind them to the signed body) so that `Utils::HmacValidator.validate` cannot succeed unless the headers used for routing/attribution match what was actually signed by Shopify.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker-shop.myshopify.com` and triggers a webhook event with a body they can influence, receiving a legitimate request with headers:
   - `shopify-hmac-sha256: <valid hmac over raw_body>`
   - `shopify-shop-domain: attacker-shop.myshopify.com`
   - `shopify-topic: orders/create`
2. Attacker resends the exact same `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but changes:
   - `shopify-shop-domain: victim-shop.myshopify.com`
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` [4](#0-3)  — validation succeeds because the body is unchanged.
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` [5](#0-4) , causing the host application to process attacker-controlled webhook data under the victim shop's tenant identity.
