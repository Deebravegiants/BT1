## Title
Unauthenticated `address` field in `state-coprocessor::handle_unsigned` lets anyone front-run a relayer's proof and steal the reputation mint - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
CVE-2018-11783 is a class of bug where a value that is supposed to be derived only from a verified/authenticated source (the client certificate) is instead accepted straight from unauthenticated caller input and then trusted downstream. The same pattern exists in `pallet-state-coprocessor`: the `GetRequestsWithProof.address` field, which is used to attribute delivery credit and mint a reputation asset, is taken verbatim from the unsigned extrinsic payload with no cryptographic binding to whoever actually assembled the state proofs.

### Finding Description
`GetRequestsWithProof` carries a plain `address: Vec<u8>` field documented as "Address that should be credited with fees" [1](#0-0) . It is submitted through `handle_unsigned`, which only checks `ensure_none(origin)` — i.e. it is a free, unsigned extrinsic callable by anyone [2](#0-1) .

Inside `handle_get_requests`, the entire pipeline (source membership proof, destination state proof) is cryptographically verified, but the `address` used to credit the work is never checked against anything: it is copied straight into `mint_into(&relayer, amount)` for the `ReputationAsset` and into the `GetRequestHandled` event's `relayer` field [3](#0-2) .

This is inconsistent with the sibling pallet `pallet-messaging-incentives`, which mints the same reputation asset but only after cryptographically recovering the relayer's account from the sr25519 signature on the message: "Recovers the relayer's account from the sr25519 signature on the message's `signer` field" [4](#0-3) . `GetRequestsWithProof` has no equivalent `signer`/signature field to authenticate `address` — the value is a raw, attacker-controlled byte string.

Because the extrinsic is unsigned and reachable by anyone, an attacker can observe a legitimate relayer's `GetRequestsWithProof` submission in the mempool (the state/response proofs are public), rebuild an identical transaction with only the `address` field swapped to their own account, and submit it first (or via any front-running technique), before the original relayer's transaction lands. `dedup_requests` and the `response_receipt` duplicate check only prevent the *same request* from being answered twice — they do not protect the *identity credited* for answering it first.

### Impact Explanation
The reputation asset is explicitly non-transferable/soulbound and is the basis for Collator selection eligibility: "The Reputation Asset ... mirrors your `$BRIDGE` earnings at a 1:1 ratio" and directly determines who is eligible to become a Collator [5](#0-4) , enforced by `ReputationCallFilter`, which blocks all transfers of this asset id [6](#0-5) . An attacker who can front-run and steal this credit performs an unbacked/misattributed mint of a governance-relevant asset without doing the underlying relaying work, at the expense of the legitimate relayer who paid the real off-chain proof-fetching cost. This directly undermines the meritocratic Collator-selection mechanism and constitutes an unauthorized state-changing action (minting to an arbitrary attacker-chosen address) reachable by any unprivileged actor.

### Likelihood Explanation
The attack requires no privileged role: any address can submit `handle_unsigned` for `StateCoprocessor`, since it is free and unsigned. Front-running an unsigned, fee-less, publicly visible mempool transaction by resubmitting it with one field changed is a low-cost, well-understood MEV pattern, and the reward is deterministic and continuous (every batch of Get responses that would otherwise mint reputation).

### Recommendation
Bind `address` to an authenticated identity the same way `pallet-messaging-incentives` does: add a `signer`/signature field to `GetRequestsWithProof`, verify the signature over the message contents (or over the request commitments) on-chain, and derive the credited account from the recovered signer rather than trusting the raw `address` bytes supplied in the call.

### Proof of Concept
1. Relayer A builds a valid `GetRequestsWithProof` (real source/response proofs) with `address = A`, and submits `StateCoprocessor::handle_unsigned` as an unsigned extrinsic.
2. Attacker B observes this pending transaction in the mempool, copies `requests`, `source`, and `response` verbatim, replaces `address` with `B`, and submits its own unsigned `handle_unsigned` extrinsic with higher priority/earlier inclusion.
3. B's transaction executes first: `dedup_requests`/`response_receipt` checks pass (nothing has been recorded yet), the proofs verify (they're the same valid proofs A built), and `ReputationAsset::mint_into(&B, amount)` mints the reputation reward to B [7](#0-6) .
4. A's original transaction now fails at the `response_receipt`/duplicate-response check, so A gets nothing despite doing the real off-chain work of assembling the proofs.

/// Reputation tokens are soulbound — credited via the incentive pallets
/// and consumed only by `pallet-collator-manager`'s per-session reset.
/// The holder must not be able to send them anywhere, so this filter
/// rejects every dispatched `Assets` call that could move balance out
/// of a holder's account when the target asset is the reputation asset.
/// Programmatic `fungible::Mutate` (mint / burn from runtime pallets)
/// bypasses dispatch and is therefore unaffected.
pub struct ReputationCallFilter;
impl frame_support::traits::Contains<RuntimeCall> for ReputationCallFilter {
	fn contains(call: &RuntimeCall) -> bool {
		let rep = ReputationAssetId::get();
		match call {
			RuntimeCall::Assets(
				pallet_assets::Call::transfer { id, .. } |
				pallet_assets::Call::transfer_keep_alive { id, .. } |
				pallet_assets::Call::transfer_all { id, .. } |
				pallet_assets::Call::approve_transfer { id, .. } |
				pallet_assets::Call::transfer_approved { id, .. },
			) => *id != rep,
			_ => true,
		}
	}
}
