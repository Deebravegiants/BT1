### Title
Webhook `topic`, `shop-domain`, and `webhook-id` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then forwards `topic`, `shop`, `webhook_id`, and `api_version` — all read directly from unauthenticated HTTP headers — into the trusted `WebhookMetadata` object passed to the app's handler. None of these header values are included in the HMAC-signed content, so they can be freely rewritten by anyone able to produce a body/HMAC pair that this app's single, shop-agnostic `api_secret_key` will validate.

### Finding Description
`Utils::HmacValidator.validate` computes/compares an HMAC over `verifiable_query.to_signable_string`. For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The identity fields used downstream — `topic`, `shop`, `webhook_id`, `api_version` — are parsed straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)` (i.e., HMAC-of-body check) before trusting these header-derived fields and handing them to the merchant's handler as authenticated `WebhookMetadata`: [3](#0-2) [4](#0-3) 

The identity equality that should hold is:
`shop-domain header == shop that authored the signed body`
and
`topic header == topic that authored the signed body`

But the code only proves `hmac == HMAC(raw_body, api_secret_key)`. It never proves `hmac` (or any other value) binds `shop`/`topic`/`webhook_id` to that specific body. Because `api_secret_key` is the app's single client secret shared across **every** shop that has installed the app (it is not shop-specific — see `Context.api_secret_key` usage in `HmacValidator.validate`), any unprivileged user who can install the app on their own store (a normal, unprivileged action) receives real Shopify webhook deliveries with bodies/HMACs computed under that same secret. They can then take a body they legitimately received (or trigger a webhook with an attacker-influenced body, e.g. renaming a product/customer field that appears verbatim in the payload) together with its valid HMAC, and replay it to the app's webhook endpoint with the headers changed to name a different `shop-domain` and a different (already-registered) `topic`/`webhook_id`. The HMAC check still passes because only the body bytes are checked, not the headers.

### Impact Explanation
This breaks the tenant isolation the library is expected to provide: the app's webhook handlers receive `WebhookMetadata#shop` and `#topic` that the library implicitly presents as authenticated, but they are attacker-controlled. An app relying on `data.shop`/`data.topic` (as the library's own documented and tested handler contract does) to decide which merchant record to update, revoke, or act upon can be tricked into acting on a victim shop's identifier using attacker-supplied/attacker-influenced body content — e.g., forging an `app/uninstalled` event for a victim shop (causing session/token deletion for that shop), or a mandatory GDPR topic (`customers/redact`, `shop/redact`) for a shop the attacker doesn't own. This is a cross-tenant access/integrity issue stemming purely from this gem's own webhook verification code, not from host-app misuse of a documented contract.

### Likelihood Explanation
Likelihood is constrained by: (1) the attacker must be able to obtain at least one valid `(body, hmac)` pair signed under the app's `api_secret_key`, which is realistically achievable by simply installing the target app on the attacker's own store and receiving a legitimate webhook (an unprivileged action requiring no leaked credentials), and (2) the victim's `shop` value and desired `topic` must be guessable/known and already registered in `Registry`. No `api_secret_key`, access token, or privileged account is required — only ordinary use of the app as any merchant. This keeps it within an unprivileged-internet-user threat model, though the practical value of the forged webhook depends on how much of the payload the attacker can influence and how the specific app's handler uses `shop`/`topic`.

### Recommendation
Bind the identity fields to the signature instead of trusting raw headers:
- Change `Webhooks::Request#to_signable_string` (or `HmacValidator`) to include `shop`, `topic`, and `webhook_id` in the signed material, or verify these header values against an independent authenticated source (e.g., cross-check `shop` against the set of shops with an active, previously-established session/installation) before constructing `WebhookMetadata`.
- At minimum, document and enforce that `Registry.process` must be called only after the caller has independently confirmed the `shop-domain` header corresponds to a known, currently-installed shop, and reject requests where it does not.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, granting it access as any ordinary merchant would.
2. Attacker triggers a webhook whose body content they can influence (e.g., updates a product title to a value that will appear in the JSON body) for a topic the app has registered, and captures the real inbound request: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker replays a forged HTTP request to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: app/uninstalled` (or any other topic registered via `Registry.add_registration`)
   - `X-Shopify-Webhook-Id: <arbitrary>`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it equals `H` — validation passes because only `B` (unchanged) is signed: [3](#0-2) 
5. The registered handler for `app/uninstalled` is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", body: <attacker's body>, ...)`, causing the app to act on the victim shop's identity based on an attacker-forged request.

*Note: I was unable to further verify how any specific downstream app typically implements handler logic (that is outside this gem), so real-world impact severity depends on the handler's use of `shop`/`topic`; the vulnerability described is confined to and fully reproducible within this gem's own `Webhooks::Request`/`Webhooks::Registry` code.*
