### Title
Directly-transferred LT donated to the curve `Pair` is permanently frozen — never returned to the sender and never recycled as protocol collateral or LP - ([File: packages/contracts/src/Pair.sol], [File: packages/contracts/src/Router.sol], [File: packages/contracts/src/Bonding.sol])

### Summary
Any unprivileged address can send LT directly to a token's curve `Pair` via a plain ERC20 `transfer`. This "donation" is intentionally excluded from graduation accounting and, by the protocol's own design notes, becomes permanently unreachable once the token graduates — no path exists to return it to the sender, recycle it as protocol collateral, or route it into the LP. This mirrors the Rocket Pool report's bug class: value provided to the contract is neither refunded nor fed back into the system, and is simply stranded.

### Finding Description
`Router.graduate` drains only the exact real LT raised by the curve (`amount = storedAssetReserve - virtualLtReserve`), explicitly excluding donated LT: [1](#0-0) . The protocol's own comment states plainly that once `Bonding`'s lifecycle passes `Curve`, `graduate` is unreachable, so any LT sitting in the pair beyond `ltFromPair` is permanently stuck: "Donated LT remains in the curve pair, reachable only via `Pair.transferAsset` which is gated by `Router`'s `BONDING_ROLE`... the leftover is unreachable" [2](#0-1) .

`Pair.transferAsset` is the only extraction path and is gated `onlyRouter` [3](#0-2) , and `Router` only exposes it via `sell` (requires burning curve tokens, not applicable to a pure donor with no tokens) and `graduate` (only callable pre-graduation, from `Bonding._prepareGraduationLiquidity`). This is confirmed by the invariant test suite itself, which asserts the donated LT balance remains in the pair forever after graduation: `assertEq(IPair(pairAddr).assetBalance(), donation, "donated LT must remain locked in the curve pair")` [4](#0-3) .

This is architecturally identical to the reported issue: a value transfer into the protocol (ETH challenge cost in the Rocket Pool case, LT donation here) that is deliberately excluded from the normal settlement/recycling flow and left permanently in the contract with zero return path — not returned to the party who sent it, and not swept into any recoverable pool (LP, `FeeVault`, or protocol treasury).

### Impact Explanation
Any LT sent to a `Pair` after the curve is near/at graduation, or any donation timed just before another buyer triggers graduation, is permanently frozen with no recovery mechanism anywhere in the codebase — not by the sender, not by the protocol owner, and not by any keeper. Unlike `FeeVault.sweepDonations()`, which exists specifically to recover donated USDC to `feeTo` [5](#0-4) , or `Bonding._sweepLTToOwner`, which recovers rebalance-residue LT during graduation seeding [6](#0-5) , there is no equivalent sweep for LT donated directly to a `Pair`. This is a permanent freeze of funds for any address that mistakenly or deliberately sends LT to a `Pair` contract, and it scales with the value donated (the test suite exercises donations up to `graduationThresholdUsd() * 5` with no upper bound) [7](#0-6) .

### Likelihood Explanation
High reachability: `Pair` addresses are publicly discoverable (`Bonding.getTokenInfo(tokenAddress).pair`), and sending ERC20 tokens to a known address requires no special privilege or protocol interaction — it's a bare `IERC20.transfer`. The team's own fuzz tests exercise this exact action across a wide range of donation sizes and curve-staging percentages [8](#0-7) , confirming the path is easily triggered, whether by user error (mistaking the `Pair` for a deposit address) or by an attacker choosing to grief a specific token's donor.

### Recommendation
Add a permissionless sweep analogous to `FeeVault.sweepDonations()`: after graduation (or at any point pre-graduation, gated appropriately), allow anyone to call a function that computes `Pair.assetBalance() - storedAssetReserve` (the unaccounted donation) and routes it somewhere recoverable — e.g., to the protocol owner as unbacked collateral, or back to the LP via `Bonding`. This closes the same class of "provided value is neither refunded nor recycled" gap the external report flagged, without altering the intentional non-triggering-of-graduation behavior for donations.

### Proof of Concept
1. Attacker/donor calls `IERC20(lt).transfer(pairAddr, donationAmount)` directly on a live curve's `Pair`, as exercised by `test_inv_donation_zeroGapPreserved` [9](#0-8) .
2. The curve later graduates via a normal `Zap.buy` crossing the threshold, triggering `Bonding._enterGraduating` → `_prepareGraduationLiquidity` → `Router.graduate(token, ltFromPair)`, which drains only the accounted-for LT, leaving the donation behind [10](#0-9) .
3. `finalizeGraduation` seeds the LP and flips `lifecycle` to `Graduated`, permanently retiring the only reachable code path (`Router.graduate`) that could ever move funds out of the `Pair` [11](#0-10) .
4. `IPair(pairAddr).assetBalance()` permanently equals the donated amount with no function in `Pair`, `Router`, `Bonding`, `Zap`, or `FeeVault` capable of moving it anywhere — confirmed directly by the test assertion `"donated LT must remain locked in the curve pair"` [12](#0-11) .

    /// @notice Transfer exactly `amount` of LT out of the pair to the caller.
    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }

    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }

    /// @dev Send LT held by this contract above `keep` to the owner,
    ///      emitting `LTRescued`. Called at the end of
    ///      `finalizeGraduation` with `keep = protectedLT` (any escrow
    ///      that doesn't belong to this graduation), so only THIS
    ///      graduation's rebalance residue lands on the owner. No-op on
    ///      the empty-pair fast path (nothing to sweep).
    function _sweepLTToOwner(
        address lt,
        uint256 keep
    ) internal {
        uint256 bal = IERC20(lt).balanceOf(address(this));
        if (bal <= keep) return;
        uint256 amount = bal - keep;
        address recipient = owner();
        IERC20(lt).safeTransfer(recipient, amount);
        emit LTRescued(lt, recipient, amount);
    }

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;
