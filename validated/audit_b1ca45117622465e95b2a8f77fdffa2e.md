### Title
Webhook shop-domain identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-verifiable signable string solely from the raw request body [1](#0-0) , while the `shop` (tenant identity) used by `Registry.process` to route data to the app's handler is taken from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header [2](#0-1) . The `shop` header is never included in the bytes that are HMAC-verified, breaking the identity binding `authenticated_bytes == acted_on_shop`.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field [3](#0-2) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is derived from the `hmac-sha256` header [4](#0-3) . Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from headers with no cryptographic binding to the body or the HMAC at all [5](#0-4) .

`Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., only the body) and then dispatches to the handler using `request.shop`, `request.topic`, etc., taken directly from the unauthenticated headers: [6](#0-5) .

Because the HMAC only proves "this body was produced by Shopify with the app's secret," and not "for shop X" or "for topic Y," any entity that possesses one genuine (body, hmac) pair — e.g., a merchant on their own store, who can trivially capture the raw POST body and `X-Shopify-Hmac-Sha256` value that Shopify sends to their own app's webhook endpoint for their own store's events — can replay that exact (body, hmac) pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (and arbitrary `X-Shopify-Topic`/`X-Shopify-Webhook-Id` headers). The HMAC check still passes because it only re-verifies the untouched body bytes, and the forged `shop` header flows straight into `WebhookMetadata` and the app's business logic as if it were an authenticated fact about the request's tenant.

### Impact Explanation
This breaks the identity binding "the shop whose HMAC is verified" == "the shop the app trusts and stores/acts on," a cross-tenant identity confusion. An app relying on this library's webhook plumbing to determine which merchant a payload belongs to (as the documented `WebhookMetadata#shop` field is intended to be used for) can be tricked into processing data under an incorrect tenant identity supplied entirely by an unprivileged webhook-capable actor (any merchant with the app installed). Depending on how the host app uses `data.shop`, this can enable cross-tenant data writes/reads, mandatory-topic abuse (`shop/redact`, `customers/redact`, `customers/data_request` are handled through this same unauthenticated `shop` field), or state corruption attributed to a victim shop — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The attacker needs no special privileges beyond being a merchant/user who can trigger a webhook-eligible action on their own store (or otherwise capture one legitimate webhook body+HMAC pair, e.g. via their own app installation) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint (which is, by design, internet-reachable and unauthenticated apart from this HMAC check). No TLS interception, leaked secrets, or privileged access is required — only reuse/replay of one legitimate signed payload with a modified `shop-domain` header. This is straightforward and repeatable.

### Recommendation
Bind the shop (and other routing-critical headers such as topic and webhook id) into the HMAC-verified signable string, or otherwise cryptographically authenticate the shop-domain header, e.g. include the concatenation of `shop-domain + topic + raw_body` in `to_signable_string`, or require the host app to independently validate that the shop in the header corresponds to an installed, known session before trusting `WebhookMetadata#shop`. At minimum, document prominently that `shop`, `topic`, and `webhook_id` are NOT covered by the HMAC and must not be trusted as authenticated tenant identifiers by consuming applications.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and triggers a webhook-eligible event (e.g. `orders/create`), capturing the raw POST body and the genuine `X-Shopify-Hmac-Sha256` header value that Shopify sends to the app's public webhook endpoint.
2. Attacker replays this exact same raw body and `X-Shopify-Hmac-Sha256` value directly to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present) [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, raw_body)` against the unchanged raw body [8](#0-7) .
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is `"victim-shop.myshopify.com"` — a value the attacker fully controls and that was never covered by the HMAC [9](#0-8) .

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
