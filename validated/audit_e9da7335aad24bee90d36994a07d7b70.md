### Title
Source-Identity Check Bypass for `RequestState` Messages Allows Cross-Session Signup-State Disclosure - ([File: orb-relay-client/src/client.rs])

### Summary
`PollerAgent::main_loop` in the Orb-Relay client is the trust boundary that filters inbound relay messages by verifying `src.id == self.config.dst_id` before accepting them into the message buffer. This check is completely skipped for any payload that matches `self_serve::app::v1::RequestState`, causing the client to unconditionally replay its last outbound message (`self.last_message`) to whoever sent the `RequestState` payload, without verifying that the sender is the legitimate paired entity for the session.

### Finding Description
In `main_loop`, incoming `RelayConnectResponse::Payload` messages are handled with this precedence: [1](#0-0) 

The `RequestState::matches(&payload)` branch is evaluated first and, if true, immediately triggers `sender_tx.send(self.last_message.clone())` — **before** the `src.id != self.config.dst_id` identity check that governs every other message type is ever reached. The identity check exists precisely because, per the developer's own TODO comment, the relay stream multiplexes messages from different sources and the client currently has no per-message subscription filter other than this manual `src.id` comparison: [2](#0-1) 

This is structurally analogous to the reported bug class: a privileged action (`self.last_message` replay, which represents the last state the orb — or app — pushed, e.g. `SignupEnded`, `CaptureStarted`, `CaptureTriggerTimeout`, `AgeVerificationRequiredFromOperator`, `AnnounceOrbId`) is executed on the basis of the *message's declared type/shape* rather than a verified caller identity, exactly like `distributeRewardToRelayers` trusting a crafted cross-message merely because it arrived through the gateway path. Here, any entity able to inject a payload matching `RequestState` into the multiplexed relay stream — regardless of whether it is the actual paired app/orb for that `dst_id` — bypasses the sole client-side authorization check (`src.id != self.config.dst_id`) and receives the replay.

### Impact Explanation
Successful exploitation discloses the most recent self-serve signup-flow state message to an unauthorized party sharing the multiplexed relay connection, rather than only to the intended paired orb/app. Depending on which message was last sent, this can leak signup lifecycle/state information (e.g., `SignupEnded{success, failure_feedback}`, `AgeVerificationRequiredFromOperator`) to a recipient that never should have received it — a cross-signup state bleed / unauthorized information disclosure via the self-serve orb-relay channel.

### Likelihood Explanation
Exploitation requires only the ability to send a `self_serve::app::v1::RequestState`-shaped payload on a relay connection whose stream is multiplexed with the victim orb/app pair — no special privilege beyond normal app-side relay access is needed, matching an "unprivileged user" precondition. The developer's own TODO acknowledges multiplexing of messages from different sources on the same stream, which is the exact condition the `src.id` check was added to mitigate, and that mitigation is bypassed for this one message type.

### Recommendation
Move the `src.id != self.config.dst_id` (or an equivalent authenticated-session) check ahead of, and apply it uniformly to, the `RequestState` handling branch so that `self.last_message` is only replayed to the verified paired entity for the session, never based solely on payload type.

### Proof of Concept
1. Establish (or otherwise gain access to) a multiplexed relay stream that also carries traffic for a target orb/app session pair.
2. Send a `RelayPayload` whose `payload` decodes as `self_serve::app::v1::W::RequestState` (via `self_serve::app::v1::RequestState::matches`), with any `src` — it need not equal `self.config.dst_id`.
3. Because the `RequestState::matches` branch is checked before the `src.id` comparison, the client immediately calls `sender_tx.send(self.last_message.clone())`, replaying the last message that was sent on that connection (e.g., signup state) back into the stream, observable/receivable by the attacker instead of being restricted to the legitimate paired entity.
