The core vulnerability class here—optional/bypassable minimum-output slippage protection on liquidity removal—has a direct analog in `raydium-amm`'s `Withdraw` instruction.

### Title
Optional/omittable slippage protection in `process_withdraw` allows sandwich attacks with zero minimum-output enforcement - (File: `program/src/processor.rs`, `program/src/instruction.rs`)

### Summary
The `Withdraw` instruction's slippage parameters (`min_coin_amount`, `min_pc_amount`) are `Option<u64>` fields that are only unpacked and enforced when the instruction data explicitly includes both trailing 8-byte values. If a caller submits a `Withdraw` instruction with the shorter (legacy) payload — only the `amount` field, omitting the two minimum fields — the program silently skips the slippage check entirely, exactly mirroring the reported Curve issue where `_min_amount` is effectively set to `0`.

### Finding Description
`WithdrawInstruction::unpack` only populates `min_coin_amount`/`min_pc_amount` if the remaining instruction data is at least 16 bytes; otherwise both are set to `None`: [1](#0-0) 

In `process_withdraw`, the resulting `coin_amount`/`pc_amount` (computed from the current pool reserves via `InvariantPool::exchange_pool_to_token`) are compared against the minimums only when **both** options are `Some`: [2](#0-1) 

If either or both are `None` (i.e., the withdraw instruction is built without appending the min-amount fields), no slippage check is performed at all, and the withdrawal proceeds using whatever `coin_amount`/`pc_amount` the pool state yields at execution time — a value that can be freely manipulated by an attacker via a swap immediately before the withdrawal.

### Impact Explanation
A malicious actor can sandwich a `Withdraw` transaction that lacks slippage parameters: front-run with a large `SwapBaseIn`/`SwapBaseOut` to skew the coin/pc reserve ratio, let the victim's withdrawal execute against the skewed reserves (extracting a disproportionately small share of one asset and large share of the other, or generally less value than expected), then back-run to restore the price and capture the difference. This causes direct loss of user funds during liquidity removal — the same "Loss of Funds" impact described in the source report for `remove_liquidity_one_coin`.

### Likelihood Explanation
`Withdraw` is a fully permissionless, frequently-used instruction reachable from a single transaction with attacker-chosen accounts and swap sizing. The vulnerability is triggered whenever a wallet/integrator/client constructs the shorter withdraw payload (omitting min amounts), which the on-chain program explicitly supports as a valid, unpacked instruction variant — it is not an edge case requiring privileged access, just a specific but valid transaction encoding.

### Recommendation
Make `min_coin_amount` and `min_pc_amount` mandatory (non-optional) fields in `WithdrawInstruction`, or enforce the slippage check whenever *either* field is provided (rather than requiring both to be `Some` before checking), and reject withdrawals lacking these guarantees, ensuring every liquidity-removal path is protected against reserve manipulation between transaction submission and execution.

### Proof of Concept
1. Attacker observes a pending `Withdraw` instruction in the mempool/leader schedule that was built with only the 8-byte `amount` field (no min-amount suffix), resulting in `min_coin_amount = None`, `min_pc_amount = None` per `AmmInstruction::unpack` (`program/src/instruction.rs:372-386`).
2. Attacker submits a `SwapBaseIn`/`SwapBaseOut` transaction immediately before the victim's withdrawal to shift `amm_coin_vault`/`amm_pc_vault` balances.
3. Victim's `process_withdraw` executes: since `withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()` is `false`, the `ExceededSlippage` check at `program/src/processor.rs:1780-1786` is bypassed, and the victim's LP tokens are burned for `coin_amount`/`pc_amount` computed off the manipulated reserves.
4. Attacker submits a reverse swap to restore price, pocketing the value taken from the victim's withdrawal.
