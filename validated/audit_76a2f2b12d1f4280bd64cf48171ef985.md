## Finding: Missing Upper-Bound Timestamp Validation in Gateway Legacy User Message Handler

The reported VTVL bug class — a caller-supplied timestamp that is validated only in one direction (missing a bound requiring it be consistent with "now") — has a direct analog in the chainlink gateway's legacy WebAPI trigger message handling path.

### Title
Missing future-timestamp bound in `handleLegacyUserMessage` staleness check allows caller-controlled bypass of message freshness validation - (File: `core/services/gateway/handlers/capabilities/handler.go`)

### Summary
`HandleLegacyUserMessage` validates a caller-supplied `payload.Timestamp` only against a lower bound (rejecting messages that are too old), but never validates an upper bound (rejecting messages whose timestamp is in the future). This mirrors the VTVL finding: a caller-controlled timestamp field is checked in only one temporal direction, letting an unprivileged/untrusted party manipulate the field to defeat the intended validity-window control entirely.

### Finding Description
In `HandleLegacyUserMessage`, the only staleness check performed is: [1](#0-0) 

```go
if uint(time.Now().Unix())-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) {
    h.lggr.Errorw("stale message")
    ...
}
```

This only rejects messages where `payload.Timestamp` is *too far in the past*. There is no corresponding check that `payload.Timestamp` is not *in the future* (i.e., no `payload.Timestamp > time.Now().Unix()` rejection). A caller supplying an arbitrarily large (future) `Timestamp` value in the trigger payload will always satisfy `now - MaxAllowedMessageAgeSec > timestamp` as false, permanently bypassing the "stale message" gate — the exact same one-directional-check gap the VTVL report flagged for `_startTimestamp`/`_endTimestamp` (checked for being unreasonable in one direction but not validated against `block.timestamp`/`now` on the other side).

This handler is reachable from an unprivileged path: it processes `web_api_trigger` / `web_api_target` / `compute_action` / `workflow_syncer` legacy `api.Message` payloads forwarded through the Gateway's public-facing connector, which is the internet-facing gateway envelope path explicitly in scope (message envelopes/handlers/caches).

### Impact Explanation
The `MaxAllowedMessageAgeSec` staleness gate exists specifically to bound the validity window of externally-supplied trigger/target messages. Bypassing it via a future timestamp undermines whatever downstream assumptions rely on message freshness (e.g., correlating with `CallbackMaxAgeSec`/`pruneCallbacks` cache eviction logic that uses wall-clock `createdAt`, not the attacker-controlled payload timestamp). While the direct blast radius is limited because a separate, wall-clock-based `savedCallbacks` prune mechanism independently ages out entries, the staleness check itself provides no actual protection against messages with manipulated future timestamps — an attacker-controlled field is trusted for time-based validation with only half the necessary bound, which is a data-integrity/validation-logic flaw of the same class as the VTVL finding.

### Likelihood Explanation
Any client able to submit a legacy Gateway `api.Message` (the payload's `Timestamp` field is fully attacker-controlled, unsigned by any timestamp-integrity mechanism beyond the message signature) can trivially set an arbitrarily-future value. No special privilege is required beyond normal message submission.

### Recommendation
Add a symmetric upper-bound check alongside the existing staleness check in `HandleLegacyUserMessage`:
```go
now := uint(time.Now().Unix())
if now-h.config.MaxAllowedMessageAgeSec > uint(payload.Timestamp) || uint(payload.Timestamp) > now+someToleranceSec {
    // reject stale or future-dated message
}
```

### Proof of Concept
1. Attacker crafts a `web_api_trigger` payload with `Timestamp` set to a value far in the future (e.g., `time.Now().Unix() + 10_000_000`).
2. `HandleLegacyUserMessage` evaluates `now - MaxAllowedMessageAgeSec > payload.Timestamp`, which is false regardless of how stale the request logically is meant to be treated, because the future timestamp always satisfies "not stale."
3. The staleness gate is bypassed unconditionally for any future timestamp value, demonstrating the missing upper-bound check. [2](#0-1)
