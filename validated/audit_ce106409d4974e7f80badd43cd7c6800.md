This confirms the vulnerability. The webhook HMAC signature covers only the raw request body (`to_signable_string` returns `@raw_body`) — it never includes the `shop-domain` header — while `Registry.process` trusts `request.shop` (read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header) to attribute the webhook payload to a tenant.

### Title
Webhook Shop Attribution Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only [1](#0-0) , while the `shop` value used to route/attribute the webhook is read from an unsigned header [2](#0-1) . `Webhooks::Registry.process` validates the HMAC and then hands `request.shop` straight to the handler without any cross-check that this shop actually matches what was signed [3](#0-2) .

### Finding Description
The Shopify webhook HMAC is computed over the raw JSON body using the app's shared `api_secret_key` [4](#0-3) . Since a single app's `api_secret_key` is shared across every shop that installs that app, any merchant who installs the app receives their own legitimately-signed webhooks. Because the HMAC only covers `@raw_body` and never the `shopify-shop-domain` header [5](#0-4) , a malicious merchant (an "unprivileged" but legitimately-installed app user) can take a webhook body+HMAC pair legitimately delivered to their own shop and replay it to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a different, victim shop domain. `Utils::HmacValidator.validate` will report the signature as valid, because it only recomputes/compares the signature against the body [6](#0-5) , and `Registry.process` will then dispatch to the handler using the attacker-supplied `shop` value [3](#0-2) .

This breaks the identity binding: `shop authenticated by HMAC` ≠ `shop trusted by the handler`. The library asserts only "was this body signed by *some* installed shop of this app," not "was this body signed *for the shop named in this request*."

### Impact Explanation
Any downstream handler that uses `WebhookMetadata#shop` to key data (e.g., updating per-shop records, marking a shop's subscription/billing/GDPR status, storing per-tenant configuration) can be tricked into applying data intended for the attacker's own shop against an arbitrary victim shop, or vice versa. This is a cross-tenant data-integrity/confidentiality break driven entirely by an attacker who only needs to be an app-installing merchant themselves — no access token, secret, or privileged account required beyond their own legitimate install.

### Likelihood Explanation
Likelihood is high for any app that installs and uses this library's webhook processing as documented: an attacker only needs to install the target app on their own store (a normal, unprivileged action), capture one webhook delivery, and replay it with a modified `shop-domain` header value.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically verify that the shop in `shopify-shop-domain` matches the shop the payload was actually delivered for (e.g., compare it against the shop stored for the currently active session/tenant context, or include the shop in the HMAC-signed payload) before dispatching to the handler in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, so the app's shared `api_secret_key` is used to sign genuine webhooks delivered to them.
2. Shopify delivers a legitimate webhook to the app with headers `x-shopify-topic`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker.myshopify.com`, and some JSON body.
3. Attacker replays the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only validates the body [7](#0-6) .
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)` [8](#0-7) , causing the app to process attacker-controlled data as if it originated from the victim shop.
