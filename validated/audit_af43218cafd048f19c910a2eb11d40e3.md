## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant misattribution of webhook payloads - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Registry.process` validates authenticates the webhook body but not the `shop` (from the `X-Shopify-Shop-Domain` header) that the gem hands to the app's `WebhookHandler`. This breaks the intended identity binding `hmac_signed_bytes == bytes_the_handler_trusts_as_tenant_identity`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
and `shop` is read straight from an HTTP header with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (body-only) — it never validates `request.shop`. It then forwards the *unauthenticated* `shop` value straight into `WebhookMetadata`, which is passed to the app's handler as the tenant identifier: [3](#0-2) [4](#0-3) 

`Utils::HmacValidator.validate_signature` recomputes the HMAC only over `verifiable_query.to_signable_string`, i.e. only over the raw body, and compares it to the received signature — it says nothing about the headers: [5](#0-4) 

Contrast this with `Auth::Oauth::AuthQuery#to_signable_string`, which explicitly includes `shop` in the signed string for the OAuth callback: [6](#0-5) 
The webhook path has no analogous coverage of `shop`, so `hmac_valid(body) == true` does not imply `shop_header == shop_that_produced_body`.

### Impact Explanation
Any actor who can obtain one genuine, HMAC-signed webhook for the target app (e.g., by installing the app on their own store, or intercepting/replaying a webhook delivery they were legitimately sent) can resend that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. Because `HmacValidator` never checks the shop header, `Registry.process` will accept the request as valid and dispatch it to the handler tagged with the attacker-chosen `shop`. Any host application that relies on `WebhookMetadata#shop` (as the docs instruct: `WebhookMetadata` is the only tenant identifier the gem surfaces to handlers) to select the tenant's DB record, credentials, or session risks acting on/for the wrong tenant — a cross-tenant data integrity issue. This matches the "field acted on but not covered by the HMAC" identity-binding class called out in the task rules.

### Likelihood Explanation
Medium: exploitation requires the attacker to possess at least one valid signed webhook body (trivially obtainable for any public app the attacker can install on their own store), and it requires the host application to trust `WebhookMetadata#shop` without independently confirming the sender (which is exactly the documented usage pattern of this gem, since `shop` is the only identity field the library exposes from a validated webhook).

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header value in the string that `Utils::HmacValidator` verifies for webhooks, or otherwise cryptographically bind the header data to the signed payload before constructing `WebhookMetadata`, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed string.

### Proof of Concept
1. Install the target app on an attacker-controlled store `attacker.myshopify.com`; trigger any subscribed webhook topic to receive a legitimately signed request with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`).
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H...})` is constructed; `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)`, which still equals `H`, so validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` and calls `handler.handle(data: ...)`, causing the host app to process attacker-supplied data under the victim shop's identity.
