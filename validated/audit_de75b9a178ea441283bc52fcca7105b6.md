### Title
Fully attacker-controlled `timeStamp` and `stealthAddressStructure` in `EmporiumUpgradeable.handleOut` allow commitment collision that permanently freezes a victim's UTXO - (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`handleOut` mints an out-UTXO whose commitment preimage is `(balanceChange, erc20TokenAddress, stealthAddressStructure, circomData.timeStamp)`, all of which except `balanceChange`'s magnitude are taken verbatim from calldata rather than derived from `block.timestamp` or fresh entropy. Because the on-chain nullifier is `Poseidon(commitment, signature)` with no dependency on the leaf's tree index, an attacker who reproduces a victim's exact `(amount, token, stealthAddressStructure, timeStamp)` quadruple from a public `NewCommitment` event can mint a second leaf with an identical commitment, and therefore an identical future nullifier, to the victim's original leaf.

### Finding Description
The broken equality: for two distinct tree leaves L1 (victim's genuine UTXO) and L2 (attacker-minted UTXO), `commitment(L1) == commitment(L2)` should never hold unless it is the same UTXO, yet it can be forced to hold here.

- `handleOut` builds the out-UTXO directly from calldata:
`UTXO(uint256(balanceChange), circomData.erc20TokenAddresses[i], circomData.stealthAddressStructure, circomData.timeStamp)` [1](#0-0) 
- The commitment itself is computed in-circuit as `Poseidon(amount, erc20TokenAddress, publicKey, timeStamp)` [2](#0-1) , i.e. exactly the four fields `handleOut` stamps onto the UTXO, with `timeStamp` never constrained to `block.timestamp` anywhere in `handleOut` or `runAction`.
- The nullifier is `Poseidon(commitment, signature)` [3](#0-2) , and depends only on the commitment value and the owner's signature over it — not on the leaf's index or Merkle path. So if two leaves share the same commitment and are both signed by the same owning key (the victim's, since `stealthAddressStructure`/`publicKey` is copied from the victim's public event data), both leaves resolve to the identical nullifier value.
- `performHinkalChecks` in `HinkalHelper.sol` validates dimensions, calldata hash integrity, relay whitelisting and on-chain creation flags, but never checks that `circomData.timeStamp` equals `block.timestamp` nor that the resulting commitment is unique in the tree [4](#0-3) . `dimensionsCheck` and `checkOnchainCreation` only check array lengths/zero-nullifier invariants for onChainCreation flows, not Emporium `handleOut` outputs, since Emporium outputs are minted directly as UTXOs bypassing the standard onChainCreation gate.

Attacker call sequence: attacker calls `transact()` → `EmporiumUpgradeable.runAction` with a whitelisted `externalActionId`, `op.endpoint` set to an attacker-controlled contract engineered so that `balancesAfter[i] - balancesBefore[i]` equals the victim's previously observed `amount`, and `circomData.timeStamp` / `circomData.stealthAddressStructure` copied verbatim from the victim's public `NewCommitment` event for that token/amount. `handleOut` then mints a second leaf whose commitment is bit-for-bit identical to the victim's original leaf and inserts it at a new tree index.

### Impact Explanation
Once the victim spends either of the two colliding leaves, the shared nullifier is marked used; any subsequent attempt to spend the other, distinct tree leaf (which still legitimately backs real, previously-deposited victim funds) will be rejected by the double-spend check, permanently freezing those funds with no possible recovery path — a Critical-severity permanent freeze of victim funds, triggered entirely by an unprivileged attacker-controlled Emporium call requiring no victim cooperation and no privileged role. This is repeatable against any victim leaf whose full `(amount, token, stealthAddressStructure, timeStamp)` quadruple is exposed via the public `NewCommitment` event log, which is the normal, unavoidable on-chain visibility of every commitment.

### Likelihood Explanation
Preconditions are modest for a determined but unprivileged attacker: (1) access to any already-whitelisted Emporium `externalActionId` (a normal, non-privileged integration point since any user can invoke `runAction` via `onlyAllowedRecipient`/relay flow), (2) ability to deploy a `op.endpoint` contract that yields the exact target `balanceChange` (fully attacker-controlled, e.g. a contract that simply transfers the exact recorded amount back), and (3) copying a victim's fully public `(amount, token, stealthAddressStructure, timeStamp)` values from chain history. No victim key material, no relay privilege, and no owner/admin role is required. Cost is a single transaction; the exploit is deterministic and repeatable against any past `NewCommitment` for any victim.

### Recommendation
Do not let `handleOut` (or any Emporium output path) use a fully caller-supplied `timeStamp`; bind it to `block.timestamp` (or a strictly monotonically increasing, contract-tracked nonce/leaf-index) so identical `(amount, token, stealthAddressStructure)` tuples cannot reproduce a prior commitment. Additionally, incorporate the leaf's tree index (or an equivalent per-insertion nonce) into the nullifier derivation so that even accidental or intentional commitment collisions cannot collapse to the same nullifier, and/or enforce commitment uniqueness at insertion time (revert if the commitment already exists in the tree).

### Proof of Concept
Hardhat fork test plan:
1. Victim deposits/creates a UTXO through the normal flow, producing leaf L1 with commitment `C = Poseidon(amount, token, pubKey, ts)`; capture `(amount, token, stealthAddressStructure, timeStamp)` from the emitted `NewCommitment` event.
2. Attacker deploys a minimal `endpoint` contract that, when called via `EmporiumUpgradeable.runAction`, causes `balancesAfter[i]-balancesBefore[i] == amount` for the same `token`.
3. Attacker calls `transact()` → `runAction` with `circomData.timeStamp = ts` and `circomData.stealthAddressStructure` copied from step 1, producing leaf L2 with commitment `C2`.
4. Assert `C2 == C` (both sides of the equality using locally computed `Poseidon(amount, token, pubKey, ts)` off-chain, matching `OriginalCommitmentCalculator`).
5. Using the victim's `nullifyingPrivateKey` to sign `C` (deterministically, as the circuit does), compute `N1 = Poseidon(C, sig)` for L1 and `N2 = Poseidon(C2, sig)` for L2; assert `N1 == N2`.
6. Simulate spending L1 via `transact()` with a valid proof; assert `insertNullifiers` marks `N1` used.
7. Attempt to spend L2 with a valid proof for the same nullifier; assert the transaction reverts due to nullifier-already-used, demonstrating permanent freeze of L2's backing funds.
