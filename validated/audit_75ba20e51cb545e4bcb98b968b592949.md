Confirmed: on the EVM side, `_buildDispatchPost` sets `Message.from = abi.encodePacked(msg.sender)` — the actual caller's address, not attacker-choosable independent of the caller [1](#0-0) . So `message.from` is bound to the real EVM caller of `send()`. When the pallet's `on_accept` falls back to the unsigned branch, it derives `origin` from `message.from` via `T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[...]))` [2](#0-1) . Any EVM address, including ones with no known private key on the destination chain (since it's just `H160 -> AccountId32` derivation, not a proof of possession), can dispatch a `RuntimeCall` there. This is not a signature bypass of a legitimate holder's key — it's dispatching a call **as an arbitrary EVM-derived substrate account** whenever `substrate_data.signature` is `None`, gated only by `BaseCallFilter`.

## Assessment

This is a legitimate finding worth flagging, though it's more precisely an **authorization/origin-binding defect** than a classic Java-deserialization RCE analog. The bug-class overlap with GHSA-mm57-9j6q-rxm2 (untrusted, insufficiently-validated data driving execution) maps onto `SubstrateCalldata::runtime_call` being SCALE-decoded from cross-chain message bytes and then `dispatch`ed with an origin that — in the no-signature branch — is derived straight from attacker-controlled cross-chain data without any cryptographic proof of key ownership.

### Title
Unauthenticated `RuntimeCall` dispatch as any EVM-derived account via HFT calldata's no-signature path - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` decodes an ABI `Message.data` field into `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }`. If `signature` is `None`, the pallet dispatches `runtime_call` with `RawOrigin::Signed(origin)` where `origin` is derived purely from `message.from` — the EVM sender address that any account can present as itself when calling `HyperFungibleToken.send()` on the source chain [3](#0-2) . No signature, nonce-replay proof, or key-ownership check gates this branch: it only checks `BaseCallFilter`.

### Finding Description
On the EVM side, `HyperFungibleToken._buildDispatchPost` sets `message.from = abi.encodePacked(msg.sender)` and `message.data = params.data` (fully caller-controlled) [1](#0-0) . Any address — an EOA or contract on the EVM chain — can call `send()` and supply arbitrary `data`.

On delivery, `pallet-hyper-fungible-token::on_accept` decodes this `data` into `SubstrateCalldata` and, when `signature` is `None`, computes:
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
} else { ... }
```
then dispatches `runtime_call.dispatch(RawOrigin::Signed(origin.clone()))` [4](#0-3) . `EvmToSubstrate::convert` is a deterministic, keyless mapping (zero-pad the 20-byte address into 32 bytes) [5](#0-4) , so the resulting substrate `AccountId` is fully predictable from an EVM address that the attacker chose merely by calling `send()` from that address — no signature over the call is required in this branch. Only `BaseCallFilter` stands between an attacker and dispatching **any** allowed `RuntimeCall** as that derived account, e.g. `Balances::transfer_all` moving funds already held by that mapped account (funds the mapped account received from *any* prior bridged transfer to that same EVM address, or funds sitting there through independent EVM<->substrate derivation used elsewhere in the runtime), pallet calls that assume `ensure_signed` implies genuine authorization, staking/voting calls, etc.

### Impact Explanation
Any account whose substrate identity is only reachable via the same `EvmToSubstrate` address-derivation (which is used pervasively for this pallet's `beneficiary` and possibly elsewhere in the runtime for EVM-linked accounts) can have arbitrary filtered `RuntimeCall`s executed as it, without ever signing anything, merely by an attacker calling `send()` from that EVM address with a 0-value/no-op token transfer and calldata that is a `SubstrateCalldata{ signature: None, runtime_call: <malicious call> }`. This is an authorization bypass enabling unauthorized dispatch — the impact scales with whatever `RuntimeCall`s `BaseCallFilter` allows (fund movement, governance votes, staking operations bound to that derived account, etc.), i.e., concrete theft or unauthorized app action within the blast radius of the pallet.

### Likelihood Explanation
High: the path is reachable by any address on any registered source EVM chain calling the public, unprivileged `HyperFungibleToken.send()`/`WrappedHyperFungibleToken.send()` function with `params.data` set to the exploit calldata, and delivered by any relayer through the normal ISMP flow — no admin, governance, or privileged role is needed.

### Recommendation
Require a valid signature (the existing `Ed25519`/`Sr25519`/`Ecdsa` branches) for **every** `SubstrateCalldata` execution, and remove or tightly scope the no-signature fallback so an "unsigned" calldata can, at most, act as the token beneficiary for benign follow-up actions the beneficiary already implicitly authorized by receiving funds — never as an arbitrary dispatch origin derived from attacker-supplied `message.from`. If the no-signature convenience path must remain, bind it to an origin that has no side effects outside the beneficiary's own newly-minted balance (e.g., disallow `RuntimeCall`s that touch state unrelated to the token just received), or drop it entirely and always require a signature to dispatch a `RuntimeCall`.

### Proof of Concept
1. Attacker (any EVM account `E`) calls `HyperFungibleToken.send()` on the source chain with `params.data = abi.encode(Call[])` shaped so the destination pallet decodes it as `SubstrateCalldata { signature: None, runtime_call: <SCALE-encoded RuntimeCall::Balances::transfer_all { dest: attacker_substrate_account, keep_alive: false } > }`, and any minimal `amount`/`to`.
2. A relayer delivers the message; `pallet-hyper-fungible-token::on_accept` runs, mints/transfers the bridged amount to `beneficiary`, then decodes `SubstrateCalldata`, sees `signature == None`, and computes `origin = EvmToSubstrate::convert(H160::from(E))` [2](#0-1) .
3. `runtime_call.dispatch(RawOrigin::Signed(origin))` executes `Balances::transfer_all` (or any other `BaseCallFilter`-allowed call) as the account mapped from `E`, moving out any balance that account holds on the destination chain — funds the real controller of `E`'s EVM key never authorized this specific substrate-side action for [6](#0-5) .
