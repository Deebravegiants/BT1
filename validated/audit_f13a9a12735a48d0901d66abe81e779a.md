### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` authenticates the *body bytes* but never binds that authentication to the `shop-domain` header that the library subsequently trusts as the webhook's tenant identity. This is the same class of bug as the Symbiotic report: a value that is *acted on* (the epoch duration / here, the shop) is decoupled from the value that is actually *verified* (the vault's stored duration / here, the HMAC-signed bytes), breaking an identity binding that downstream logic silently assumes holds.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`to_signable_string` returns `@raw_body` exclusively — the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are never mixed into the HMAC-verified string. `HmacValidator.validate` then simply recomputes `HMAC(secret, raw_body)` and compares it to the received signature: [3](#0-2) 

`Registry.process` treats a passing HMAC check as authorization to hand `request.shop` to the app's handler as trusted tenant metadata: [4](#0-3) 

Because Shopify signs webhooks with the **app's single shared `api_secret_key`** (not a per-shop key — see `HmacValidator.validate` using `Context.api_secret_key`/`Context.old_api_secret_key` only, no shop-scoping), any `(raw_body, hmac)` pair that is valid for one installed shop of the app is also a valid `(raw_body, hmac)` pair for *any other shop* of the same app, because the secret is identical and the shop is not part of the signed content. The binding that should hold is:

`shop_the_handler_trusts == shop_that_actually_produced_this_signed_body`

but the code only proves:

`hmac_computed_over(raw_body) == received_hmac`

which says nothing about which shop sent it.

### Impact Explanation
An attacker who can trigger at least one legitimate webhook delivery for the app (e.g., by installing the app on their own store — an ordinary, unprivileged action requiring no secrets) obtains a valid `(raw_body, hmac)` pair signed with the app's shared secret. They can then send this exact `raw_body` + `hmac` to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-controlled body>, ...)`. Any host application that uses `data.shop` to look up the victim's session/access token and applies `data.body` against that shop's data (a normal, documented usage pattern) processes attacker-controlled content under a different tenant's identity — a cross-tenant data-integrity/isolation break carrying no requirement for `api_secret_key` theft, TLS interception, or privileged access.

### Likelihood Explanation
Likelihood is meaningful but not maximal: the attacker needs only to be an app user (any store owner who installs the target app) to obtain one legitimate webhook capture, and needs the target app to trust `WebhookMetadata#shop`/`#body` together for tenant-scoped side effects (a very common pattern, e.g. `orders/create`, `app/uninstalled`, `customers/data_request`). No secret material, no cryptographic break, and no interaction with the victim is required — only a passive capture of one's own webhook traffic and a replay with a modified header.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is HMAC-verified, or at minimum expose/require verification that ties body provenance to header claims before constructing `WebhookMetadata`. Concretely:
- Include `shop-domain` (and `topic`) in `Request#to_signable_string`, or
- Require host apps to additionally validate that the shop in the webhook belongs to a shop that has a stored, previously-issued session/access token for this exact app installation before trusting `data.shop`, and document this requirement prominently since the library currently implies HMAC success is sufficient to trust `data.shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, capturing one webhook delivery: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid since `H = HMAC(app_secret, B)`).
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body = B`, same `x-shopify-hmac-sha256 = H`, but `x-shopify-shop-domain = victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes `HMAC(app_secret, B)` — matches `H`, since the shop header plays no part in `to_signable_string`. Validation in `lib/shopify_api/webhooks/registry.rb` line 190 passes.
4. `Registry.process` calls the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to act on attacker-supplied content as if it originated from `victim-shop.myshopify.com`.
