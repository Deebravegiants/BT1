Based on my analysis, this confirms the vulnerability. The `Request#to_signable_string` in `lib/shopify_api/webhooks/request.rb` returns only `@raw_body`, meaning the HMAC signature covers *only* the JSON body bytes, while `shop`, `topic`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers and passed straight into `WebhookMetadata` as trusted identity data consumed by the host app's handler.

### Title
Webhook Shop/Topic Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only [1](#0-0) , while the `shop`, `topic`, `webhook_id`, and `api_version` fields are read directly from unauthenticated HTTP headers [2](#0-1)  and passed unmodified into `WebhookMetadata`, which apps use as the trusted tenant identifier [3](#0-2) [4](#0-3) .

### Finding Description
`Registry.process` validates authenticity solely via `Utils::HmacValidator.validate(request)` [5](#0-4) , which calls `verifiable_query.to_signable_string` to obtain the bytes to verify against the `hmac` header [6](#0-5) . For `Request`, `to_signable_string` returns `@raw_body` exclusively [1](#0-0) . The `shop` accessor, however, is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` header, a value the HMAC computation never touches [7](#0-6) . After validation succeeds, `Registry.process` forwards `request.shop` straight into `WebhookMetadata.shop`, which is the field host applications rely on to select the tenant/session to act on [3](#0-2) .

This breaks the intended identity binding: `bytes_verified_by_hmac == raw_body` but `bytes_acted_on_as_tenant_identity == shop_header`, and `shop_header ⊄ bytes_verified_by_hmac`. Because Shopify's shared webhook secret (`api_secret_key`) is common to the whole app across all its installing shops (not shop-specific), a payload that is validly signed for one installed shop (e.g., the attacker's own store, which they fully control and can trigger arbitrary webhook-eligible events in) remains validly signed if replayed with the `shop`/`topic`/`webhook_id` headers rewritten to reference a different, victim shop. `Utils::HmacValidator.validate` will still return `true`, since it only recomputes the digest over `@raw_body` [8](#0-7) , and the forged headers pass straight through to the handler unauthenticated. This is a direct instance of "a field acted on but not covered by the HMAC."

### Impact Explanation
This is a cross-tenant confusion vulnerability at the library level: the API contract promises HMAC-authenticated webhook metadata (`WebhookMetadata#shop`) to the consuming application, but the `shop` field carried in that authenticated-looking struct is not actually bound to the signature. Any application that uses `data.shop` from `WebhookHandler#handle` to select which merchant's session/data to update (the documented, expected usage pattern) is exposed to cross-tenant data corruption/injection driven entirely by an attacker who is merely an installed, unprivileged merchant of the app — no leaked secret or privileged account is required, satisfying the "cross-tenant access" Critical impact bucket.

### Likelihood Explanation
Exploitability is high for any attacker who can install the target app on their own store (a normal, unprivileged action for any Shopify merchant/dev-store operator). They can trigger a real, validly-signed webhook delivery for their own shop, capture the raw body + hmac, then replay the request to the app's webhook endpoint with the `shopify-shop-domain` (and/or `shopify-webhook-id`/`shopify-topic`) header value swapped to the victim shop's domain. No cryptographic secret needs to be known or brute-forced because the signature check never inspects the header being spoofed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signable string used for HMAC verification, or otherwise require the caller to supply/verify the expected shop out-of-band and compare it explicitly against a value bound to the payload (e.g., an authenticated shop identifier embedded in the JSON body by Shopify, if available) rather than trusting the raw header. At minimum, document that `WebhookMetadata#shop` is not cryptographically authenticated and must not be used as the sole tenant selector without additional verification (e.g., cross-checking against a known/registered shop for that specific webhook subscription/session).

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" with the app installed.
# Shopify sends a legitimate, correctly-signed webhook for that shop:
raw_body = '{"id":123,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Attacker captures this request, then replays it to the app's webhook
# endpoint with the shop-domain header rewritten to the victim's shop:
forged_headers = {
  "shopify-topic"        => "orders/create",
  "shopify-hmac-sha256"  => Base64.encode64(hmac), # unchanged, still valid!
  "shopify-shop-domain"  => "victim-shop.myshopify.com", # forged, not covered by hmac
  "shopify-webhook-id"   => "forged-id",
  "shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HmacValidator.validate only checks raw_body against the secret - it has no
# knowledge of / binding to the shop header, so this still succeeds:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process then hands off attacker-controlled tenant identity to the
# host app's handler as if it were authenticated for "victim-shop.myshopify.com":
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```
