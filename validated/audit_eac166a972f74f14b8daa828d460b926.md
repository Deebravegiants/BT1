### Title
Webhook `shop-domain` (and topic/api-version/webhook-id) headers are trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values used by the host application to identify the tenant and route the webhook are read straight from unauthenticated HTTP headers that are never included in the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against `verifiable_query.to_signable_string`, i.e. the body bytes: [2](#0-1) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` are all pulled from headers that are never hashed: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately hands the header-derived `request.shop` (along with `topic`/`webhook_id`/`api_version`) to the application's webhook handler as trusted tenant metadata: [4](#0-3) 

The binding the code implicitly assumes is:

`bytes verified by HMAC == bytes/fields acted upon by the handler`

but in reality:

`bytes verified by HMAC (raw_body only) != fields acted upon (raw_body + shop-domain + topic + webhook-id + api-version headers)`

Because the shop-domain header sits entirely outside the signed material, anyone who possesses one valid `(body, hmac)` pair — for example, the operator of their own Shopify store, who legitimately receives correctly-signed webhooks for their own shop — can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header value. `HmacValidator.validate` still succeeds because it never looks at the header, and `Registry.process` forwards the attacker-chosen `shop` value to the handler as if it were authentic.

### Impact Explanation
Any downstream logic that uses `WebhookMetadata#shop` as a tenant/session key (the documented and expected usage pattern for this gem, per `docs/usage/webhooks.md`) can be tricked into attributing a validly-signed payload to a different shop than the one that actually sent it. Since the shop is the primary tenant boundary in a multi-tenant Shopify app, this allows cross-tenant data injection: a payload signed for shop A's data can be relabeled and processed under shop B's identity, bypassing the tenant isolation the HMAC check is meant to guarantee.

### Likelihood Explanation
The attacker only needs one legitimately-signed webhook body/HMAC pair, which any merchant using the app (or anyone able to trigger a webhook-firing event on any store, even their own) already possesses — no `api_secret_key`, access token, or TLS interception is required. They then resend the same body/HMAC with a forged `shop-domain` header to the app's webhook endpoint.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, and ideally `topic`/`webhook-id`) in the signed material, or otherwise bind them cryptographically to the signature (e.g., HMAC over `header-values || raw_body` instead of `raw_body` alone), so that `to_signable_string` covers every field that `Registry.process` and downstream handlers rely on for tenant identity.

### Proof of Concept
1. Attacker operates (or briefly gains visibility into) their own store, "attacker-shop.myshopify.com", and receives a legitimate webhook for it: body `B`, header `shopify-shop-domain: attacker-shop.myshopify.com`, header `shopify-hmac-sha256: H` where `H = HMAC(secret, B)`.
2. Attacker POSTs to the victim app's webhook endpoint with the same body `B` and same signature header `H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H})` is constructed; `to_signable_string` returns `B` unchanged.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` and compares to `H` — it matches, since the shop header was never part of the signed input: [5](#0-4) 
5. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...))`, and the host application processes body `B` as if it genuinely originated from `victim-shop.myshopify.com`.
