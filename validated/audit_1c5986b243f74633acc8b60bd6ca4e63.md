### Title
`findMatchingWithdrawal` matches by `assetId` only, misreporting status/txHash across same-token withdrawals in a batch - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` resolves the status of a specific `WithdrawalIdentifier` by fetching all withdrawals for the shared NEAR transaction hash and then picking the one whose `near_token_id` matches the requested `assetId`, ignoring destination address, amount, and the identifier's own `index`. When a single NEAR intents transaction contains two or more withdrawals of the same POA token to different destinations, both `WithdrawalIdentifier`s resolve to the exact same matched entry, so one of them reports the wrong `status`/`txHash`.

### Finding Description
The broken equality is: for a given `WithdrawalIdentifier` (`landingChain`, `index`, `withdrawalParams` incl. `destinationAddress`/`amount`, `tx`), the returned `WithdrawalStatus` should describe *that* withdrawal, not some other withdrawal from the same NEAR transaction. Instead, `describeWithdrawal` calls `getWithdrawalStatusWithRetry(args)` which queries `poaBridge.httpClient.getWithdrawalStatus({ withdrawal_hash: args.tx.hash })` — keyed only by the shared NEAR transaction hash, returning **all** withdrawals contained in that batch transaction:
<cite repo="Alyssadaypin/sdk-monorepo--010" path="packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts" start="313&#8203;" end="343" />

It then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does an `Array.prototype.find` keyed solely on `` `nep141:${w.data.near_token_id}` === assetId ``: [1](#0-0) 

The function's own doc comment admits the defect: *"multiple withdrawals of the same token in a single transaction are not supported"* — yet nothing in `supports()`, `validateWithdrawal()`, or `createWithdrawalIdentifiers` in `withdrawal-watcher.ts` rejects or disambiguates such a batch. `createWithdrawalIdentifiers` assigns a per-bridge `index` [2](#0-1)  but that `index` is never used by `findMatchingWithdrawal` to disambiguate — it's dead for this purpose. `createWithdrawalIdentifier` in `poa-bridge.ts` simply carries the params/index through without using them for matching [3](#0-2) .

Exploit flow: an integrator (or any caller) submits a NEAR intents transaction that batches two withdrawal intents for `nep141:gnosis-0xe91d153e0b41518a2ce8dd3d7944fa863463a97d.omft.near` to two different destination addresses/amounts within the same `tx.hash`. Both resulting `WithdrawalIdentifier`s are watched via `watchWithdrawal` → `bridge.describeWithdrawal` [4](#0-3) . Once the POA indexer reports one of the two withdrawals as `COMPLETED` (with `transfer_tx_hash` possibly `null` if not yet propagated) and the other as still `PENDING`, `.find()` returns the **first array entry matching the token id** for *both* identifier lookups — because the API response list is unsorted and keyed only by token, both watch calls converge on the same matched entry. One of the two payouts is then reported with the other payout's status/txHash.

Existing guards do not catch this: `supports()` and `validateWithdrawal()` validate token/address format per-withdrawal but never check for duplicate `assetId` within a batch; `matchesRequest`/`FeeExceedsAmountError`/nonce checks operate on intent construction, not on post-hoc status resolution; nothing in `poa-bridge.ts` or `withdrawal-watcher.ts` rejects `supports()` calls for batches containing repeated `assetId`.

### Impact Explanation
An integrator that relies on `IntentsSDK.waitForWithdrawalCompletion`/`watchWithdrawal` per `WithdrawalIdentifier` to learn when to credit or reconcile a payout can be told `status: "completed"` with a `txHash` belonging to the *other* destination's transfer, while the truly-completed payout for its own destination is reported as still pending (or vice-versa). This is a status/hash misreport that can cause an integrator to credit or refund the wrong side twice — matching the "High" impact category (status or hash misreport making an integrator credit or refund twice).

### Likelihood Explanation
Requires only: (1) a NEAR intents transaction batching ≥2 withdrawal intents for the same POA `assetId` to different destinations/amounts, and (2) an integrator/consumer that watches each resulting `WithdrawalIdentifier` independently (the documented usage pattern via `waitForWithdrawalCompletion`). No privileged access is needed — a normal user (or an integrator building batches on behalf of multiple end customers withdrawing the same token) can trigger this at zero extra cost, and it is repeatable on every batch containing a same-token duplicate. The comment in `findMatchingWithdrawal` confirms the SDK authors are aware the case is unhandled, yet no guard prevents forming/watching such batches.

### Recommendation
Reject (in `supports()`/`validateWithdrawal()`) or explicitly disambiguate batches containing multiple withdrawals with the same `assetId` in a single NEAR transaction. If POA's API cannot disambiguate by destination/amount, either throw a clear "unsupported: duplicate token withdrawals in one transaction" error at intent-construction time, or implement the sort-by-amount pairing strategy the comment suggests (sort both the API response and the local `withdrawalParams` for that token by amount, since fees are equal for the same token) and match by that stable relative order plus destination address rather than a bare `.find()` on token id alone.

2. Create two `WithdrawalIdentifier`s via `bridge.createWithdrawalIdentifier` with the same `assetId` and `tx.hash`, but distinct `destinationAddress`/`amount` corresponding to each mocked entry.
3. Call `bridge.describeWithdrawal` for both identifiers.
4. Instead, both calls will return the same `{ status: "completed", txHash: "hash-A" }` (or whichever entry `.find()` returns first), proving both identifiers resolve to the array's first same-`assetId` match regardless of which destination/amount they actually represent.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
