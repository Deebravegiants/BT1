### Title
Unrestricted `initialize()` in `EmporiumUpgradeable` allows front-running to seize contract ownership - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.initialize()` is a `public` function guarded only by OpenZeppelin's `initializer` modifier, which merely prevents double-initialization — it enforces no check that the caller is a trusted deployer/admin address.

### Finding Description
The implementation contract's constructor calls `_disableInitializers()` [1](#0-0) , which only protects the logic/implementation contract from being initialized directly. When `EmporiumUpgradeable` is deployed behind a proxy, the proxy's storage starts uninitialized, and `initialize()` remains callable by anyone until the legitimate deployer's transaction lands:

```solidity
function initialize(
    IHinkalHelper _hinkalHelper,
    address[] memory _allowedRecipients,
    address _owner
) public initializer {
    __EIP712_init("Emporium", "1.0.0");
    __ExternalActionBase_init(_allowedRecipients);
    EmporiumStorageVars storage $ = _getEmporiumStorage();
    $._hinkalHelper = _hinkalHelper;
    _transferOwnership(_owner);
}
``` [2](#0-1) 

There is no `onlyOwner`, `onlyRole`, or deployer-address check on `initialize`. Because proxy deployment and the `initialize` call are two separate transactions (deploy-then-initialize is the standard upgradeable pattern, and no atomic factory in this repo performs both together for Emporium, unlike `HinkalFactory.deployHinkal` which does grant/transfer ownership atomically in one function), an unprivileged attacker can observe the proxy deployment in the mempool and front-run the legitimate `initialize` call with their own `_owner` and `_allowedRecipients` arguments.

Once initialized by the attacker, they become the contract `owner` (via `Ownable2StepUpgradeable`) and control:
- `setAllowedRecipients(address[])` — `onlyOwner`, which grants arbitrary addresses `_isAllowedRecipient[...] = true` [3](#0-2) , thereby satisfying `onlyAllowedRecipient` on `runAction` for any attacker-controlled contract [4](#0-3) .
- `setHinkalHelper(IHinkalHelper)` — `onlyOwner`, redirecting the trusted Hinkal helper reference used by the Emporium logic [5](#0-4) .

`runAction` executes arbitrary `op.endpoint.call{value: op.value}(op.callData)` for any caller satisfying `onlyAllowedRecipient` [6](#0-5) . Since the attacker controls `_isAllowedRecipient`, they can register their own address/contract as an allowed recipient and then invoke `runAction` directly (bypassing Hinkal's shielded-pool accounting entirely), moving out any tokens/ETH that legitimately or accidentally reside on the Emporium proxy — an asset movement never authorised by the true Hinkal admin, wallet owner, or prover.

### Impact Explanation
This breaks the trust assumption that only the legitimate Hinkal deployer configures the Emporium's owner and allowed recipients. An attacker-controlled owner can whitelist itself as an allowed recipient and directly call `runAction` to move any funds held by the Emporium proxy to itself — executing calls/asset movement never authorised by a wallet owner or prover, and permanently compromising the contract's configuration (owner is `Ownable2Step`, so recovery requires a second attacker-controlled step, i.e., practically irrecoverable without a full redeploy). This matches the High/Critical impact class: unauthorised asset movement and permanent loss of legitimate control over the Emporium instance.

### Likelihood Explanation
Any unprivileged EOA can monitor for proxy deployment transactions targeting `EmporiumUpgradeable` and front-run the intended `initialize()` call with their own parameters, since `initialize()` has no caller restriction beyond the one-time `initializer` guard. This requires no special privileges, only mempool visibility and gas to outbid the legitimate init transaction — the same bug class documented in the external report for Solana `initialize` instructions, directly analogous here in the EVM upgradeable-initializer pattern.

### Recommendation
Restrict `EmporiumUpgradeable.initialize()` so it can only be called by a trusted, known deployer address (e.g., verify `msg.sender` against a fixed deployer/factory address, or perform proxy deployment and initialization atomically in the same transaction via a factory contract, analogous to how `HinkalFactory.deployHinkal` atomically deploys and transfers ownership in one call). Alternatively, use a deterministic deploy+initialize helper that reverts if `msg.sender` is not the designated deployer.

### Proof of Concept
1. Deployer submits a transaction deploying an `ERC1967Proxy` (or equivalent) pointing at the `EmporiumUpgradeable` implementation, intending to follow up with `initialize(hinkalHelper, allowedRecipients, ownerAddress)`.
2. Attacker observes the proxy deployment transaction in the mempool, and before the deployer's `initialize` transaction is mined, submits their own transaction calling `initialize(attackerHinkalHelper, [attackerContract], attackerAddress)` on the same proxy with higher gas.
3. The attacker's transaction is mined first; `initializer` modifier only prevents a second call, so the attacker's call succeeds, making `attackerAddress` the `owner` and `attackerContract` an allowed recipient.
4. The legitimate deployer's `initialize` call now reverts (already initialized).
5. Attacker calls `runAction` from `attackerContract` (now passing `onlyAllowedRecipient`), executing arbitrary `op.endpoint.call` to drain any funds sent to/held by the Emporium proxy, and can further call `setHinkalHelper`/`setAllowedRecipients` to escalate.
