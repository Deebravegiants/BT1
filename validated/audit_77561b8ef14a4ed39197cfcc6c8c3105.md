### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop-domain` header — the value used by the application to attribute the webhook to a specific merchant — is never included in what gets signed or verified. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands the *unverified* `shop` value straight to the app's handler, so the field the host application uses to bind the event to a tenant is not the field the HMAC actually protects.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it to the `hmac` value: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be exactly the raw request body — nothing else: [2](#0-1) 

The `shop` accessor, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is **not** part of the signed payload: [3](#0-2) 

`Registry.process` only checks the HMAC of the body before dispatching, then forwards the header-derived `shop` (and `topic`) to the handler as trusted metadata: [4](#0-3) 

The identity binding that should hold is:
`HMAC_valid(body, shop) == true` implies `shop` is authentic for that body.

In reality the gem only proves `HMAC_valid(body) == true`; `shop` is parsed independently of the signature. Since a single app-wide `client_secret`/`api_secret_key` is used to validate webhooks from *every* installed shop (this is inherent to the Shopify webhook HMAC scheme, not per-shop), any merchant who has installed the app can:

1. Trigger a legitimate webhook from their own shop (e.g. create an order), producing a body + valid HMAC signed with the app's shared secret.
2. Replay that exact body/HMAC pair to the app's webhook endpoint, but with the `shop-domain` header rewritten to a victim shop that also has the app installed.
3. `HmacValidator.validate` still returns `true` because it never looked at the header, and `Registry.process` calls the handler with `shop: <victim shop>` attached to attacker-controlled body content.

This is the same bug class as the reported `emergencyExit`/`launch` mutual-exclusion failure — a security-relevant field (`totalCommittedFGEN`/tenant-binding) is *acted upon* by downstream logic without being covered by the check that is supposed to guarantee its integrity (the exit accounting vs. the HMAC-verified shop identity).

### Impact Explanation
This crosses a tenant boundary: an unprivileged installer of the app (any merchant, no special access needed) can forge webhook events "from" a different merchant's shop, causing the host application to act on falsified data attributed to a shop it never actually came from (e.g. spoofed `orders/create`, `app/uninstalled`, or GDPR `customers/data_request` events). Depending on how the host app uses `WebhookMetadata#shop`, this can lead to cross-tenant data corruption, unauthorized uninstall/cleanup flows, or processing of forged compliance requests against a victim store — matching the "cross-tenant access" Critical-tier impact category.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on their own shop (a normal, unprivileged action any Shopify merchant can take) and to capture/replay one legitimate webhook body while modifying the `shop-domain` header — no access to `api_secret_key` or any victim credentials is needed since the HMAC never covers the header.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values in the signable string used for HMAC verification, or independently re-verify that the `shop-domain` header matches a shop actually associated with the app/session before dispatching to handlers, so the verified bytes and the bytes acted upon are the same.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and trigger any webhook (e.g. create an order) to capture a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared secret.
2. Send a POST to the app's webhook endpoint reusing that exact `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. Observe that `ShopifyAPI::Webhooks::Registry.process` (via `Utils::HmacValidator.validate`) accepts the request and invokes the handler with `shop: "victim-shop.myshopify.com"`, even though `victim-shop` never sent this event.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
