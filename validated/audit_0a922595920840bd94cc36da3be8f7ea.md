### Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` headers are not covered by the HMAC, enabling cross-tenant webhook forgery via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `ShopifyAPI::Webhooks::Registry.process` uses `Utils::HmacValidator.validate` to authenticate the request based solely on that raw body. The `shop`, `topic`, `webhook_id`, and `api_version` values, which are read directly from HTTP headers, are never included in the HMAC computation, so they are unauthenticated. Any unprivileged internet user who obtains one genuine `(raw_body, hmac)` pair (e.g. an app's own webhook consumer logs, a shared proxy, or a merchant replaying it) can resubmit that exact body/HMAC pair to the app's webhook endpoint with a **different** `shop-domain`, `topic`, `webhook-id`, or `api-version` header and have it pass validation.

Because the app's `api_secret_key` is shared across every shop that installs the app (it is the app's `client_secret`, not a per-shop secret), and because the HMAC is computed only over the body, the binding that should hold is:

`hmac == HMAC(secret, body)` **and implicitly** `shop_header == the shop that actually generated body`

but the code only verifies the first half. The second half — that the `shop-domain` (and `topic`/`webhook_id`) header actually corresponds to the signed body — is never checked. An attacker who has captured one legitimate `(body, hmac)` pair for shop A can replay it with `x-shopify-shop-domain: shop-b.myshopify.com` (or any other shop with the app installed) and the app will process it as an authentic webhook for shop B, since `HmacValidator.validate` only recomputes the HMAC over `@raw_body` and never checks that the accompanying `shop`, `topic`, `webhook_id`, or `api_version` are the ones that were actually signed.

This is directly analogous to the reported bug class: a field ("shop"/"topic"/"webhook_id") is acted upon by the consuming code but is not covered by the authentication mechanism (HMAC) that is supposed to guarantee the message's integrity/origin, letting an unprivileged caller "take away" the trust granted by a valid signature meant for different data.

### Impact Explanation
If the host application's webhook handler makes any per-shop or per-topic decisions using `WebhookMetadata#shop`, `#topic`, `#webhook_id`, or `#api_version` (which is the documented and expected use, see `docs/usage/webhooks.md`), an attacker can cause data destined for shop A to be attributed to shop B, or cause a topic-specific handler to run with a mismatched topic/body combination. This is a cross-tenant integrity violation: the app cannot trust that the shop identity attached to a webhook event actually matches the shop that produced the signed payload.

### Likelihood Explanation
Exploitation requires the attacker to have observed at least one legitimate `(raw_body, hmac)` pair — for example via a compromised or curious party with visibility into webhook traffic, logs, or a shared test/staging environment, or a merchant who received a real webhook and simply changes the `shop-domain` header when replaying it against the app's webhook endpoint. No knowledge of `api_secret_key` is required, matching the "unprivileged internet user" threat model, since the header fields are not bound into the signature at all.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used by `HmacValidator`, or otherwise verify that the shop/topic asserted in the headers is consistent with metadata bound into the HMAC. At minimum, document that `Registry.process` does not authenticate `shop`/`topic`/`webhook_id`/`api_version` and that host applications must independently validate these values (e.g., against their own session/shop registry) before trusting them for tenant-specific actions.

### Proof of Concept
1. App has two shops installed: `shop-a.myshopify.com` and `shop-b.myshopify.com`, both use the same `api_secret_key`.
2. Attacker captures a legitimate webhook delivery for `shop-a.myshopify.com`: `raw_body = '{"id":1}'`, `x-shopify-hmac-sha256 = <valid HMAC of body>`.
3. Attacker POSTs to the app's webhook endpoint with the same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `raw_body` only and succeeds, per `lib/shopify_api/webhooks/request.rb` `to_signable_string`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) calls the handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)`, even though the body was never actually produced for shop B.
