## Title
Unchecked empty-body indexing in `onAccept` causes permanent, unrecoverable message-delivery failure - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
CVE-2019-6445 is a NULL-pointer dereference in NTPsec's `ctl_getitem`, where an authenticated but low-privilege remote message triggers a crash because the parser indexes into a data structure without checking that it actually contains an item. The analogous pattern in Hyperbridge is `ExtrinsicIntents.onAccept()`, which reads `incoming.request.body[0]` before validating that `body` is non-empty. Since `body` is fully attacker-controlled cross-chain request payload, any account on any connected source chain can dispatch a `PostRequest` with an empty `body` targeting this contract, causing the callback to always revert.

### Finding Description
`onAccept` is the `IIsmpModule` callback invoked by the Hyperbridge `HandlerV2`/host when delivering a `PostRequest` to this application [1](#0-0) . It decodes the message `kind` by reading the first byte of `incoming.request.body`:
```solidity
function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
    _checkRelayer(incoming.relayer);
    RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
``` [2](#0-1) 

There is no length check on `incoming.request.body` before this index access, and the sender/source authentication (`_authenticate`) only runs *after* the `kind` is decoded, for the `RedeemEscrow`/`RefundEscrow` branches [3](#0-2) . `body` is the arbitrary payload of a cross-chain `PostRequest` that any account on the *source* state machine can create via `IDispatcher.dispatch`, and any permissionless relayer can then deliver by supplying a valid state proof through the host's message-handling path. A request with `to` set to this contract's address and `body = ""` (empty bytes) will always cause `body[0]` to revert with an out-of-bounds panic, since Solidity's `calldata` byte-array indexing traps when the index is `>= length`.

This differs from the already-hardened classes of bugs found elsewhere in the repo (SCALE/RLP/SSZ decoders and MMR/GRANDPA/sync-committee verifiers, all of which now explicitly guard length/index bounds before slicing untrusted proof bytes, e.g. `modules/consensus/pharos/primitives/src/spv.rs`, `modules/trees/ethereum/src/node_codec.rs`, `modules/consensus/beefy/verifier/src/lib.rs`) — those were previously patched for the exact `ctl_getitem`-style class of bug. `ExtrinsicIntents.onAccept` has the same unguarded-index pattern but on the EVM application layer, reachable straight from a permissionless cross-chain dispatch + relay.

### Impact Explanation
Because the malformed `PostRequest` is a normal ISMP message (committed on the source chain and delivered with a valid membership proof), the destination host will process it as any other request. Once the module callback (`onAccept`) reverts, the delivery attempt fails. Since the `body` bytes are fixed at dispatch time on the source chain (the request commitment is derived from the request contents, including `body`), the payload can never be corrected — every future delivery attempt for that exact request will revert identically until the request times out. This is a "route unable to deliver messages" condition for that specific request, and any solver/relayer batching that includes it risks reverting the whole batch transaction (depending on whether `HandlerV2` executes each request atomically or batches multiple requests in one transaction — batching behavior in `HandlerV2.sol` was not fully confirmed within available context, so the blast radius beyond the single malformed request could not be fully verified here).

### Likelihood Explanation
High: constructing an empty-body `PostRequest` targeting `ExtrinsicIntents` requires only a normal, permissionless `dispatch()` call from any account on a connected source chain, with no special privileges, no gateway registration, and no signature/authentication bypass needed. The only prerequisite is knowing the target contract address, which is public.

### Recommendation
Validate `incoming.request.body.length > 0` (and, ideally, that it is long enough for the specific `RequestKind` payload) at the top of `onAccept` before indexing `body[0]`, reverting with a clear, catchable error (e.g., `InvalidInput()`) rather than relying on Solidity's implicit out-of-bounds panic. Additionally, consider running `_authenticate`/source checks before any decoding of attacker-controlled `body` content, consistent with the "validate before parse" pattern already applied to the SCALE/RLP/SSZ decoders elsewhere in the codebase.

### Proof of Concept
1. On any connected source chain, call `IDispatcher(sourceHost).dispatch(DispatchPost({ dest: <destChain>, to: abi.encodePacked(<ExtrinsicIntentsAddress>), body: "", timeout: 0, fee: 0, payer: msg.sender }))`.
2. Wait for the request commitment to be included and finalized.
3. Any relayer submits the state proof to the destination `IsmpHost`/`HandlerV2`, which calls `IIsmpModule(ExtrinsicIntentsAddress).onAccept(incoming)` with `incoming.request.body == ""`.
4. Execution reverts inside `onAccept` at `RequestKind(uint8(incoming.request.body[0]))` due to out-of-bounds array access — the request can never be successfully delivered, regardless of how many times relayers retry, until it times out.
