### Title
Webhook `shop`, `topic`, `webhook-id`, and `api-version` headers are trusted but not covered by the HMAC signature, allowing cross-tenant webhook forgery via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable content solely from the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and process the webhook are taken from unauthenticated HTTP headers that are never included in the signed bytes. This is the same bug class as the reported `calcDestinationId` issue: an identity/context binding is derived from data that a hash/signature does not actually cover, so the verified bytes and the acted-upon bytes diverge.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies a request by recomputing an HMAC over `verifiable_query.to_signable_string` and comparing it against `verifiable_query.hmac`: [1](#0-0) 

For webhooks, `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` reads the `hmac-sha256` header: [2](#0-1) 

However, `shop`, `topic`, `webhook_id`, and `api_version` are all read from separate HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) that are **not part of the signed bytes**: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then builds `WebhookMetadata` directly from these unsigned headers, handing it to the app's `handler.handle`: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `bytes verified by HMAC == bytes the handler treats as the source of truth for shop/topic/webhook_id`. Instead, only the body is verified, while `shop`, `topic`, `webhook_id`, and `api_version` — the very fields the host application uses to decide *which tenant and which action* to apply the payload to — are unauthenticated header values with no cryptographic binding to the signed body.

Because many legitimate webhook payloads are small/predictable (e.g., an empty `{}` body, as used in this repo's own tests for `shop/redact`), an attacker who is an unprivileged internet user that installs the app on their own store receives valid, correctly-signed webhook deliveries for their own shop. They can capture one such delivery (valid `hmac-sha256` header + raw body) and replay it to the app's public webhook endpoint while swapping the `shopify-shop-domain` header to a victim shop and/or the `shopify-topic`/`shopify-webhook-id` headers to a different, more sensitive topic (e.g. a mandatory compliance topic like `shop/redact` or `customers/data_request`, both registered as `MANDATORY_TOPICS` in this gem) or to an app-specific privileged topic. The HMAC check still passes because it never examined those headers, and `Registry.process` will happily route this forged event, with an attacker-chosen `shop` field in `WebhookMetadata`, into the host application's handler.

### Impact Explanation
This breaks the tenant/authentication boundary the HMAC is meant to enforce: an unprivileged attacker with their own install can generate a request that is accepted as "verified" for a different shop and/or a different (chosen) topic than the one the body was actually captured for. If the host app trusts `WebhookMetadata#shop`/`#topic` (as the library's own documentation and `WebhookHandler` interface encourage), this enables cross-tenant data corruption, spoofed compliance actions, or triggering shop-scoped side effects for a victim store the attacker does not control — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only: (1) the app's webhook endpoint URL (typically not secret — apps expose a fixed callback path), and (2) the attacker installing the app on their own shop to legitimately receive at least one signed webhook with a predictable/reusable body (e.g., empty-body events such as `app/uninstalled` or mandatory redact topics are common). No access to `api_secret_key` or any merchant's access token is needed — the attacker only reuses a signature they were legitimately given for their own tenant. This is a realistic, low-effort replay, not merely theoretical.

### Recommendation
Bind the identity fields into the signed content, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the request that was verified:
- If Shopify's HMAC scheme cannot be changed (it is fixed by the platform to sign the body only), the library should not treat header-derived `shop`/`topic`/`webhook_id` as verified/trusted output of `Registry.process`; at minimum, document loudly that these fields are unauthenticated and require out-of-band correlation (e.g., cross-checking `shop` against the session/shop the app expects, or deduplicating by `webhook_id` against Shopify's Admin API) before being used for any tenant-scoped action.
- Where feasible, have `to_signable_string` incorporate the raw header values used for routing (or reject requests whose header-derived shop doesn't match session state the app already has for that installation).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook (e.g., `shop/redact` with an empty JSON body `{}`), including a valid `X-Shopify-Hmac-Sha256` header computed by Shopify over that body with the app's secret.
2. Attacker replays this exact HTTP body to the app's public webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: shop/redact` (or another topic sharing/matching an empty-body signature the attacker has captured)
   - `X-Shopify-Webhook-Id: <attacker-chosen>`
   - `X-Shopify-Hmac-Sha256: <the still-valid signature from step 1>`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` (`{}`), matching the replayed signature — validation succeeds: [6](#0-5) 
4. `WebhookMetadata` is built with `shop: "victim-shop.myshopify.com"` and the attacker-chosen `topic`/`webhook_id`, and passed to the app's handler, which treats it as an authentic event for the victim shop.

          received_signature = verifiable_query.hmac
