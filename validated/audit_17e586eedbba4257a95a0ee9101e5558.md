Interesting: `callback_gas = ADDRESS_CHECK_CALLBACK_GAS.saturating_add(action.gas())` and `NEP_141_STORAGE_BALANCE_CALLBACK_GAS.saturating_add(action.gas())` do scale the callback's gas budget with the user-supplied action's gas, which somewhat mitigates simple out-of-gas griefing for those two paths, but `rlp_execute_callback` itself and the final `.then(ext.rlp_execute_callback(caller_deposit))` chained after `action_to_promise(...)` calls always use the fixed `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) regardless of the size/complexity of `caller_deposit` refund logic or the action-derived data being processed — but that logic is simple, so the out-of-gas griefing hypothesis on this specific path is weaker than initially suspected and I could not fully confirm an exploitable trigger within the remaining tool budget.

### Title
Permanent lockout of `WalletContract` when the `has_in_flight_tx` reentrancy-guard reset fails to commit - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
`WalletContract` (the ETH-implicit-account emulation contract) uses a boolean flag, `has_in_flight_tx`, as a manual mutex/reentrancy guard to ensure only one relayer transaction is "in flight" at a time. [1](#0-0) 
`rlp_execute` sets the flag to `true` and rejects any new call while it is `true`. [2](#0-1) 
The flag is only cleared inside the async callbacks (`address_check_callback`, `nep_141_storage_balance_callback`, `rlp_execute_callback`, `ban_relayer`) that NEAR schedules as separate receipts via `.then(...)`. [3](#0-2) [4](#0-3) 

### Finding Description
This mirrors the Renzo bug's structural shape: a "lock"-style guard is set on entry and is supposed to be released by a call that is itself part of the very execution flow the lock is protecting. In Renzo, `nonReentrant` on `receive()` blocked the legitimate reentrant callback from `completeQueuedWithdrawal`, permanently trapping ETH. In `WalletContract`, `has_in_flight_tx` is cleared as the very first statement of each callback function, but NEAR's runtime semantics dictate that **all state writes for a receipt are rolled back if that receipt's execution fails** (documented explicitly: "When a receipt fails, its state changes are rolled back using `TrieUpdate`"). [5](#0-4) 
This means if the callback function call fails for *any* reason after being invoked — e.g. it runs out of the gas statically budgeted for it, or panics while parsing/handling the passed-through `action`/`caller_deposit` — the `self.has_in_flight_tx = false;` write is discarded along with the rest of the callback's state changes, while the earlier `self.has_in_flight_tx = true;` write (committed in the prior, separate receipt) remains persisted. [6](#0-5) 
Because `rlp_execute` unconditionally short-circuits whenever `has_in_flight_tx == true`, [7](#0-6) 
once this happens the account is permanently locked: no future `rlp_execute` call can ever succeed again, since there is no other code path that can clear the flag from outside a callback.

The most concrete gas-margin risk is in the `ERC20Transfer` and `EOABaseTokenTransfer` (address-check) paths, where the callback gas is computed as a fixed constant plus the user-derived `action.gas()`: [8](#0-7) [9](#0-8) 
Any static-gas constant that under-provisions the actual worst-case execution cost of its associated callback (e.g. due to large `args`/`caller_deposit` payloads, host-function costs for constructing nested promises, or unaccounted for wasm compilation/branching costs) can push a specific, otherwise valid, relayed transaction into an out-of-gas failure inside the callback, permanently freezing the `has_in_flight_tx` guard in the `true` state.

### Impact Explanation
If the callback that is supposed to reset `has_in_flight_tx` fails to commit its state change, the affected NEAR account's `WalletContract` becomes permanently unusable — every subsequent `rlp_execute` call (i.e., every future Ethereum-style transaction routed through this account) is rejected forever, since the check at the top of `rlp_execute` cannot be bypassed by any other method. [2](#0-1) 
This is a permanent denial of service for the account: any ETH-implicit account whose owner cannot get relayers to submit new transactions is functionally bricked, mirroring the "permanently stuck" impact class described in the reference report (funds and functionality become irretrievable without a contract upgrade).

### Likelihood Explanation
I was only able to confirm the structural precondition (the guard-reset-in-callback pattern that is rolled back on receipt failure) from the code and the documented runtime rollback semantics; I could **not** conclusively verify, within the remaining investigation budget, a concrete transaction shape that reliably drives one of the callbacks into an out-of-gas or panic condition despite the `action.gas()`-scaled budgets on two of the three callback paths. The `rlp_execute_callback` path itself always uses the fixed `RLP_EXECUTE_CALLBACK_GAS` (5 Tgas) regardless of upstream promise complexity, which is the most plausible under-provisioned path, but I did not trace every possible caller_deposit/action combination that reaches it. This should be treated as a plausible-but-unconfirmed likelihood pending deeper gas-cost analysis of each callback's worst case.

### Recommendation
- Do not rely on a callback that can itself fail to reset a persistent lock flag; instead clear/set the guard using a pattern that is robust to callback failure, e.g. track "in-flight" state via a separate promise/receipt that is guaranteed to run regardless of the primary callback's success (a dedicated cleanup step), or use `Promise::then` combined with a fixed/guaranteed final gas-bounded callback with minimal logic solely responsible for clearing the flag.
- Audit and add a safety margin to all static gas constants (`RLP_EXECUTE_CALLBACK_GAS`, `ADDRESS_CHECK_CALLBACK_GAS`, `NEP_141_STORAGE_BALANCE_CALLBACK_GAS`) against the actual worst-case execution cost of their respective callback bodies, including nested promise construction costs.
- Add a recovery mechanism (e.g., an owner-only or timeout-based "force reset" method) so that if `has_in_flight_tx` is ever left stuck `true` due to an unexpected callback failure, the account is not permanently bricked.

### Proof of Concept
Not independently reproduced. The reasoning is based on: (1) the documented NEAR runtime invariant that a failed receipt's state changes (including `self.has_in_flight_tx = false`) are rolled back, [5](#0-4) 
(2) the guard being set in one receipt and cleared only inside subsequent, separately-executed callback receipts, [6](#0-5) 
and (3) `rlp_execute`'s unconditional rejection while the flag is `true` with no alternate reset path. [7](#0-6) 
A full PoC would require constructing a specific RLP transaction/action whose downstream callback execution provably exceeds its statically allocated gas (or otherwise panics), which I was unable to confirm concretely given tool-call limits.
