### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` treats the `shop-domain` header as a trusted tenant identifier and forwards it to the app's webhook handler, but `Utils::HmacValidator` never authenticates that field — it only verifies the raw request body. This is the same class of bug as the reported Solana issue: a value that is *used* to determine which "account" (here, which shop/tenant) an operation applies to is never *bound* by the cryptographic proof (HMAC ≈ PDA derivation) meant to guarantee its authenticity.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via: [1](#0-0) 

which calls `Utils::HmacValidator.validate`, computing/comparing the HMAC over `request.to_signable_string`: [2](#0-1) 

`Webhooks::Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

But `Webhooks::Request#shop` (and `topic`, `webhook_id`, `api_version`) are read straight from unauthenticated HTTP headers and passed to the app's handler as trusted identity metadata: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop header == shop cryptographically proven by HMAC`. In reality the HMAC only proves `body == body signed by Shopify`; it says nothing about which shop the body belongs to. Compare this to `Auth::Oauth::AuthQuery`, where `shop` **is** included in `to_signable_string` and thus is bound by the HMAC: [6](#0-5) 

For webhooks, no equivalent binding exists — `shop-domain` sits completely outside the signed data.

### Impact Explanation
Any actor who can obtain one genuine, HMAC-signed webhook body/signature pair from Shopify for *any* shop (trivial: they can install the app for free on their own development/partner store and capture the webhook Shopify sends to the app's registered endpoint) can replay that exact `raw_body` + `hmac-sha256` header combination to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value. `Utils::HmacValidator.validate` will still return `true` (it never looks at the shop header), and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the attacker-chosen shop. Any host application that trusts this `shop` value to scope tenant data (e.g., "delete this shop's data", "update this shop's config") can be tricked into performing that action against a different, victim tenant — a cross-tenant impact.

### Likelihood Explanation
Reaching this requires only the ability to send arbitrary HTTP requests to the app's public webhook endpoint (no credentials, tokens, or privileged access needed) plus possession of one legitimately-issued webhook body/HMAC pair, which any developer/attacker with a free trial or partner store can obtain by installing the target app once. This is squarely an "unprivileged internet user" scenario as scoped by the rules, and it exploits a real omission in this gem's own signed-data construction.

### Recommendation
Include the shop identifier (and ideally topic/webhook-id) in the value that is HMAC-verified, or otherwise cryptographically bind the `shop-domain` header to the signature before trusting it. Practically:
- Modify `Webhooks::Request#to_signable_string` (or add a companion check in `Registry.process`) to also verify that the `shop-domain` header corresponds to a shop the app actually expects/has a stored session for, rather than passing it through unauthenticated.
- At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and host apps must independently verify it against known/installed shops before using it to scope any data operation.
- Apply the same "field acted upon vs. field covered by signature" review across other `VerifiableQuery` implementers to ensure every value later trusted downstream is part of the signed payload.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled development store `attacker-shop.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g., `orders/create`) and capture the raw POST Shopify sends to the app's webhook endpoint, including headers `x-shopify-hmac-sha256: <HMAC>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, and the raw body `B`.
3. Replay the exact same request to the same endpoint, but replace the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only (see `to_signable_string`) and matches the replayed `hmac-sha256`, so `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed(B) ...)`.
5. Any handler logic keyed off `data.shop` (e.g., writing/deleting per-tenant records) now operates on `victim-shop` using attacker-supplied body content, despite the HMAC only ever having authenticated `attacker-shop`'s data.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
