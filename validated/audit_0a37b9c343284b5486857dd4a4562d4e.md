### Title
Emporium `signerAddress == 0` bypasses all signature and balance accounting, letting anyone steal tokens held by Emporium via the min-circuit path - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `CircomDataBuilder.formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` and constrains nothing about UTXOs, tokens, or balances. Combined with `EmporiumUpgradeable.verifyWallet` skipping signature verification entirely when `stack.signerAddress == address(0)`, and `runAction`'s balance-accounting loop iterating the attacker-chosen empty `erc20TokenAddresses` array, an unprivileged attacker can execute an arbitrary unsigned `EmporiumOperation` (e.g. `ERC20.transfer(attacker, amount)`) from Emporium's identity with zero accounting anywhere in the call stack.

### Finding Description
The broken equality: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`** (and in Hinkal's own `oldBalances`/`newBalances` loop). This is violated because the accounting arrays are sized by `circomData.erc20TokenAddresses`, which the attacker fully controls and can set to `[]`.

Path:
1. `Hinkal.transact` → `hinkalHelper.performHinkalChecks` → `CircomDataBuilder.formInputForCircom` (`contracts/CircomDataBuilder.sol:134-148`). If `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`, it calls `formInputEmporiumMin` (`contracts/CircomDataBuilder.sol:150-161`), which only produces 3 public signals: `emporiumMessage`, `timeStamp`, `calldataHash`. This maps to `MainEVMCircuitMin` (`circuits/MainEVMCircuitMin.circom:6-18`), whose only constraint is `message === Poseidon(messageSeed)` — it does **not** constrain `rootHashHinkal`, nullifiers, `amountChanges`, or ownership of any UTXO. `calldataHash` integrity is checked separately on-chain (`HinkalHelper.performHinkalChecks`, `contracts/HinkalHelper.sol:221-225`), so this proof is trivially generatable by anyone who picks a `messageSeed`.
2. `dimensionsCheck` (`contracts/HinkalHelper.sol:64-150`) forces `dimensions.tokenNumber == erc20TokenAddresses.length == 0`, which forces `amountChanges`, `inputNullifiers`, `outCommitments`, `onChainCreation`, `slippageValues` to all be empty too.
3. `rootHashExists` (`contracts/MerkleBase.sol:53-64`) only needs *some* valid stored root/index; with exactly one prior leaf inserted, `roots[MINIMUM_INDEX]` already equals that leaf, so any prior deposit (even the attacker's own trivial one) satisfies this trivially — no real ownership of value is required since `amountChanges`/nullifiers are empty anyway.
4. `Hinkal._externalTransact` (`contracts/Hinkal.sol:234-261`) checks only that `externalActionMap[externalActionId] == externalAddress` (public, permissionless to satisfy — attacker just points at the deployed Emporium address). Since `erc20TokenAddresses.length == 0`, `deltaAmountChanges` is `[]`, so no pre-funding transfer happens.
5. `EmporiumUpgradeable.runAction` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`) decodes the attacker-supplied `EmporiumStack` from `externalActionMetadata`. `balancesBefore`/`balancesAfter` are computed over the empty `erc20TokenAddresses` array (lines 85-87, 122-124), so the accounting loop at lines 132-151 never executes — nothing is checked.
6. `verifyWallet` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:302-349`): when `stack.signerAddress == address(0)`, it marks the message used and **returns immediately without any signature check** (lines 314-316).
7. In the ops loop (lines 91-118), since `stack.signerAddress == address(0)`, the "Stateful Interaction" branch (`op.invokeWallet && stack.signerAddress != address(0)`) is always false, so every op falls into the "Stateless Interaction" branch: `op.endpoint.call{value: op.value}(op.callData)` executed **with `msg.sender == Emporium`**. The only restriction is blocking the `callHinkalWallet`/`doSendToRelay` selectors; arbitrary calls to any other contract (e.g. an ERC20 token Emporium holds) are unrestricted.

Exploit: attacker crafts `EmporiumStack{ signerAddress: address(0), ops: [{endpoint: TOKEN, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, amount)}], maxFee: 0, deadline: far future }`, sets `feeStructure.flatFee = 0` (to avoid the `"Gas Token in Emporium is not found"` revert in `payRelayFees`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:247-251`), sets `erc20TokenAddresses = []`, generates a trivial min-circuit proof, and calls `Hinkal.transact`. The call executes `TOKEN.transfer(attacker, amount)` from Emporium's own balance, uncontested by any check anywhere in the call chain.

Existing guards fail because: `performHinkalChecks`/`dimensionsCheck` only enforce internal array-length consistency, not that `erc20TokenAddresses` is non-empty when Emporium executes ops; `rootHashExists` doesn't tie to any spent value since nullifiers are empty; `verifyProof` accepts the min proof since it only constrains `message`; `verifyWallet`'s signature check is explicitly skipped for `signerAddress == 0`; and the balance-diff invariant in `EmporiumUpgradeable.runAction` and in `Hinkal.transact` (lines 97-147) is keyed off the same attacker-controlled empty array, so it can never observe the stolen token.

### Impact Explanation
Any funds sitting on the Emporium contract's own balance (accumulated from prior deposits, partial fills, dust, relay fees in transit, or ETH from `op.value`) can be transferred to an arbitrary attacker-controlled address with a single, cheap, unauthenticated call. This is direct theft of funds held by the protocol's Emporium module — Critical severity, matching "direct theft of shielded or in-flight user funds" / "executing calls or moving assets... never authorised." It is fully repeatable for as long as Emporium holds any balance.

### Likelihood Explanation
Preconditions are minimal: the attacker needs (a) the publicly known Emporium proxy address registered in `externalActionMap`, (b) any single prior leaf in the tree to obtain a valid root (trivially satisfiable, including by the attacker's own harmless deposit), (c) the ability to generate a Groth16 proof for `MainEVMCircuitMin`, which requires no secret UTXO data — just picking `messageSeed`. No privileged role, no victim signature, and no non-empty `deltaAmountChanges` are required. Cost is limited to gas and one throwaway deposit to seed a root. This is a low-cost, highly feasible, repeatable attack whenever Emporium holds a non-zero token/ETH balance.

### Recommendation
Do not let `runAction` execute unsigned, arbitrary external calls when `signerAddress == address(0)`; require a valid signature (or a stricter allow-list of endpoints/selectors) regardless of `erc20TokenAddresses.length`. Additionally, decouple accounting from the attacker-supplied `erc20TokenAddresses` array — e.g., require `erc20TokenAddresses.length > 0` whenever `stack.ops.length > 0`, or independently snapshot/verify Emporium's full balance sheet (or at minimum every token touched by `op.callData`) before and after executing ops, rather than trusting the caller-chosen token list.

### Proof of Concept
Foundry test plan:
1. Deploy Hinkal, HinkalHelper, Merkle, EmporiumUpgradeable (register it via `registerExternalAction(HINKAL_EMPORIUM_ACTION_ID, emporiumAddress)` as admin — a one-time protocol setup step, not attacker-privileged).
2. Fund Emporium with `TOKEN.transfer(emporium, 1000e18)` to simulate residual/held balance.
3. Insert one leaf into the tree (any prior legitimate deposit) so `roots[MINIMUM_INDEX]` is valid; record `rootHashHinkal`/`rootHashHinkalIndex`.
4. As `attacker` (no special role), build `CircomData` with: `erc20TokenAddresses = []`, `amountChanges = []`, `inputNullifiers = []`, `outCommitments = []`, `onChainCreation = []`, `slippageValues = []`, `feeStructure.flatFee = 0`, `externalActionData = {externalAddress: emporium, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{signerAddress: address(0), ops: [{endpoint: TOKEN, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, 1000e18)}], maxFee: 0, deadline: type(uint256).max})}`, valid `calldataHash` via `getHashedCalldata`, `emporiumMessage = Poseidon(messageSeed)` for an attacker-chosen `messageSeed`.
5. Generate a Groth16 proof for `MainEVMCircuitMin` using `messageSeed`, `timeStamp`, `calldataHash`.
6. Call `Hinkal.transact(a, b, c, dimensions{tokenNumber:0, nullifierAmount:0, outputAmount:0}, circomData)` from `attacker`.
7. Assert: `TOKEN.balanceOf(attacker)` increases by `1000e18` and `TOKEN.balanceOf(emporium)` decreases by `1000e18`, while `oldBalances == newBalances` (both empty arrays) in `Hinkal.transact` and `balancesBefore == balancesAfter` (both empty arrays) in `EmporiumUpgradeable.runAction` — i.e., the equality "assets moved == assets accounted" is violated (nonzero token delta vs. zero accounted delta), and the transaction does not revert.
