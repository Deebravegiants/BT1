## Title
Webhook Tenant/Topic Confusion via Header Fields Not Covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's webhook handler, but the HMAC signature it validates only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — all taken from unauthenticated HTTP headers — are handed to the handler as the trusted tenant/topic identity without being bound to the HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` by exposing: [1](#0-0) [2](#0-1) 

`hmac` reads the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header, and `to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` accessors read separate, independent headers that are never mixed into `to_signable_string`: [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` header using `OpenSSL.secure_compare`: [4](#0-3) 

`Registry.process` treats a passing HMAC check as authenticating the whole request, then forwards the unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` header values straight to the app's handler: [5](#0-4) 

The documented contract for this API explicitly states the intent is full request authentication: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook" (`docs/usage/webhooks.md`, "Process a Webhook" section). In practice, only the body bytes are bound to the HMAC — `shop`, `topic`, `webhook_id`, and `api_version` are **verified-vs-parsed** mismatches: they are parsed from headers but never verified as part of the signed content.

**Broken identity binding (as an equality):**
`hmac_header == HMAC(secret, raw_body)` is checked, but the code (and downstream handlers) treats this as if `hmac_header == HMAC(secret, raw_body ‖ shop ‖ topic ‖ webhook_id ‖ api_version)`. The `shop` value used as the tenant key for handler dispatch is never part of the signed material.

### Impact Explanation
Any party that can obtain one legitimate webhook delivery with a valid HMAC (e.g., an app's own merchant/tenant receiving genuine webhooks for their own shop, or anyone who otherwise captures one valid `(body, hmac)` pair for the configured `client_secret`) can replay that exact body+HMAC to the app's webhook endpoint while freely substituting the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, and `x-shopify-api-version` headers. `HmacValidator.validate` still passes (it only checks the body), and `Registry.process` will dispatch the handler with `shop:` set to an arbitrary tenant string and `topic:`/`api_version` set to any registered value, causing the host application to process attacker-chosen webhook metadata under a spoofed tenant identity — a cross-tenant identity confusion at the webhook-processing boundary that this gem's own documentation claims is prevented by HMAC verification.

### Likelihood Explanation
Exploitation only requires possession of one genuine `(raw_body, hmac)` pair signed with the app's `client_secret` — obtainable by any merchant/tenant who has installed the app and received a single real webhook — and the ability to send an HTTP POST to the app's public webhook endpoint with modified headers. No access token, session, or `api_secret_key` leak is required beyond what a normal, unprivileged installed-tenant already legitimately receives.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` header values in the signable string used for HMAC validation (or otherwise cryptographically bind them, e.g. by deriving them only from data that Shopify signs), so that `Utils::HmacValidator.validate` fails if any of these fields are altered. At minimum, update `Webhooks::Request#to_signable_string` to incorporate these fields, and update `docs/usage/webhooks.md` to accurately describe what is and isn't covered by the HMAC check if header binding is not added.

### Proof of Concept
1. Attacker's own shop, `attacker.myshopify.com`, has the app installed and receives a legitimate webhook: body `{"id":1}`, headers include `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker resends the identical body and `hmac` header to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`/`x-shopify-api-version` to any registered value).
3. `ShopifyAPI::Webhooks::Request.new` parses the new headers; `Utils::HmacValidator.validate` recomputes `HMAC(secret, raw_body)`, which is unchanged and still matches — validation passes.
4. `Registry.process` looks up the handler for the (possibly attacker-chosen) topic and invokes it with `WebhookMetadata.new(shop: "victim.myshopify.com", topic: ..., body: {"id"=>1}, ...)`, i.e., the handler executes believing this data pertains to `victim.myshopify.com`. [5](#0-4) [6](#0-5)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
