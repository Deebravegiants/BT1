### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via `Utils::HmacValidator.validate(request)`, which validates the HMAC over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — it does not include the `shop-domain`, `topic`, `webhook-id`, or `api-version` header values. Those fields are read directly, unauthenticated, from HTTP headers and passed straight into `WebhookMetadata` given to the app's handler.

### Finding Description
The identity binding broken is: `shop` value cryptographically bound by the HMAC == `shop` value the app's webhook handler acts upon.

`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it (via `OpenSSL.secure_compare`) to the `hmac` header value [5](#0-4) . For webhook requests, `to_signable_string` is defined as just the raw JSON body [6](#0-5) , while `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from the `x-shopify-*`/`shopify-*` headers with no cryptographic tie to the HMAC [7](#0-6) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with `request.shop` as the trusted tenant identifier [4](#0-3) . Because the body is often small, generic, or reusable JSON (e.g., mandatory compliance topics, or repeated field sets across topics/shops), an attacker who has observed or received one legitimate `(body, hmac)` pair issued by Shopify for any shop (including their own store, or one they can subscribe to) can replay that exact body+hmac to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The HMAC still validates because it never covered the shop field, so the app's handler receives `WebhookMetadata` attributing that body to a shop the attacker chose, not the shop the signature actually vouches for.

### Impact Explanation
This breaks the tenant-identity binding the HMAC is supposed to provide: apps rely on `request.shop` (passed through as `WebhookMetadata#shop`) to determine which merchant's data the webhook payload applies to, e.g., to look up/update per-shop records, trigger redaction, or index by shop. Forging the shop field lets an unprivileged attacker cause the app to process/attribute webhook data under a different tenant's identity — a cross-tenant integrity issue reachable without any credentials, satisfying the High-severity "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one legitimate `(raw_body, hmac)` pair for the app's secret (trivially available if the attacker owns any shop/dev store that installs the app and receives webhooks, since mandatory topics like `shop/redact` are required for every app) and then replay it directly to the app's public webhook receiver endpoint with a modified shop header. Webhook endpoints are typically internet-reachable with no other authentication, so this is straightforward for anyone who can install the app on a shop they control.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable string bound by the HMAC, or independently verify that `request.shop` matches an expected/authorized shop before dispatching to handlers — e.g., have `Webhooks::Request#to_signable_string` incorporate `shop`/`topic` alongside the body, or have `Registry.process` cross-check the shop domain against the session/shop the app expects for that webhook subscription.

### Proof of Concept
1. App receives a legitimate webhook for `shop-a.myshopify.com` with body `{}` and a valid `x-shopify-hmac-sha256` computed over `{}`.
2. Attacker controls `shop-a` (or otherwise captured this valid body+hmac pair) and replays the identical raw body and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks the HMAC against `@raw_body`, which is unchanged [3](#0-2) .
4. `Registry.process` dispatches to the handler with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)`, even though Shopify never signed anything on behalf of `shop-b` [8](#0-7) .
