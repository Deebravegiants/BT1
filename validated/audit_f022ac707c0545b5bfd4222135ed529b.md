### Title
Webhook `shop`, `topic`, and `webhook_id` Are Not Covered by the HMAC, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook `Request` as fully authenticated once `Utils::HmacValidator.validate(request)` returns `true`, then hands `request.shop`, `request.topic`, and `request.webhook_id` straight to the app's handler as trusted tenant-identifying data. However, the HMAC signature only covers the raw request body — none of those header-derived fields are bound to the signature. Any party who can obtain one validly-signed `(body, hmac)` pair for the app (trivial for any merchant who has installed the app, since the `api_secret_key` used to sign webhooks is shared across all shops of the app, not per-shop) can replay that exact body/hmac pair while forging the `shop-domain`, `topic`, and `webhook-id` headers to any value they choose, and the gem will still report the request as valid.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated headers: [2](#0-1) 

`Registry.process` gates on the HMAC check and then forwards these unauthenticated fields to the app's handler as the identity of the event: [3](#0-2) 

`HmacValidator.validate` computes the signature purely over `verifiable_query.to_signable_string` (the body) and compares it to the received `hmac`: [4](#0-3) 

Because `api_secret_key` is the app's single shared secret across every shop that has installed the app (not a per-shop secret), any merchant using the app can legitimately trigger a webhook for their own store and obtain a valid `(raw_body, hmac)` pair. That pair remains valid under `HmacValidator.validate` no matter what `shop-domain`, `topic`, or `webhook-id` headers are sent alongside it, because those fields are never part of the signed content.

**Binding that should hold:** `request.shop == shop_that_generated(raw_body, hmac)`.
**Binding that actually holds:** `HmacValidator.validate(request) == true` regardless of `request.shop`, so the equality above is not enforced by the gem — it silently degrades to "the body plus *some* header set (attacker-chosen) is accepted."

### Impact Explanation
An attacker who is a legitimate merchant of the target app (i.e., has zero elevated privileges over other tenants, and does not need the app's `client_secret`/access tokens for other shops) can craft a POST to the app's webhook endpoint using a body+HMAC pair they legitimately received for their own shop, but with the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers rewritten to point at a different shop. `Registry.process` will validate the HMAC successfully and invoke the app's handler with `WebhookMetadata` claiming the event belongs to the victim shop. If the host app uses `data.shop` (as documented/intended) to select which tenant's record to update, this crosses the tenant boundary — e.g. spoofing `app/uninstalled`, `shop/update`, or `customers/data_request` for another merchant, corrupting or deleting that merchant's data within the app.

### Likelihood Explanation
Exploitation only requires: (1) being any merchant with the app installed (unprivileged relative to other tenants — no `api_secret_key`, access token, or credential theft required), (2) triggering one action in their own store to receive a legitimately-signed webhook body, and (3) POSTing that captured body with forged headers to the app's public webhook endpoint. No cryptographic material needs to be recovered or brute-forced, since the signature check never covers the fields being forged.

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the signable content that `HmacValidator` verifies, or otherwise separately authenticate `request.shop`/`request.topic` (e.g., require the caller to cross-check them against the session/shop the handler is being invoked for) before trusting them in `Registry.process`. At minimum, document clearly that `HmacValidator.validate` only attests to body integrity and that `request.shop`/`request.topic` are NOT authenticated by it, so host applications don't mistakenly treat `WebhookMetadata#shop` as a verified tenant identifier.

### Proof of Concept
1. As Merchant A (any shop with the app installed), perform an action that triggers a subscribed webhook (e.g., `orders/create`). Capture the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` that Shopify sent to the app's endpoint.
2. Send a new POST request to the same app webhook endpoint with:
   - Body: unchanged `B`
   - `X-Shopify-Hmac-Sha256`: unchanged `H`
   - `X-Shopify-Shop-Domain`: rewritten to `victim-shop.myshopify.com`
   - `X-Shopify-Topic`: optionally changed to another registered topic
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes HMAC over `B`.
4. `Registry.process(request)` dispatches to the registered handler with `WebhookMetadata.new(topic: forged_topic, shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, and the host app acts on data attributed to a shop that never sent it.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
