### Title
Permissionless `CallDispatcher.dispatch()` lets anyone steal tokens left stranded in the shared dispatcher after `HyperFungibleToken`/`IntentGatewayV2` calldata execution - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, persistently deployed, shared contract used by every `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2` deployment on a chain to execute user-supplied `Call[]` arrays against tokens that are temporarily routed through it. Its `dispatch()` entrypoint has no access control at all, and `HyperFungibleToken.onAccept` — unlike `IntentGatewayV2`, which sweeps residual balances back to itself after dispatch — never reclaims leftover tokens from the dispatcher. Any token minted to the `CallDispatcher` (by design, when a sender sets `to = CallDispatcher` for calldata execution) that is not fully consumed by the attached calls stays in the dispatcher indefinitely, and because `dispatch()` is callable by anyone, an attacker can immediately drain it.

### Finding Description
`CallDispatcher.dispatch()` executes an arbitrary attacker-supplied `Call[]` with no `msg.sender` restriction: [1](#0-0) 

`HyperFungibleToken.onAccept` mints bridged tokens directly to the `beneficiary` address specified in the cross-chain message, then, if calldata is attached, forwards it unconditionally to the shared `_dispatcher`: [2](#0-1) 

Per the documented usage pattern, users set `to` to the `CallDispatcher` address so that the attached `Call[]` (e.g. approve + swap) can spend the minted tokens: [3](#0-2) 

Unlike `IntentGatewayV2`, which explicitly sweeps every enumerated output/input token balance out of the dispatcher after execution via `_execute`/transfer-back `Call[]`s: [4](#0-3) 

`HyperFungibleToken.onAccept` performs no such sweep. Any amount not fully consumed by the attached calls — due to slippage, partial fills, an intermediate hop token not accounted for by the sender's `Call[]`, or a sender who simply supplies calldata that under-spends the minted amount — remains sitting in the shared `CallDispatcher` contract's ERC20/ETH balance. The same class of gap exists for the `IntentGatewayV2` predispatch/postdispatch paths for any token not explicitly enumerated in `order.inputs`/`order.output.assets` (e.g., unlisted intermediate swap-path tokens), since the sweep only iterates over the enumerated asset lists.

Because `CallDispatcher` is one shared, long-lived contract address used by every app instance on the chain (listed permanently on the contract-addresses pages) and `dispatch()` has zero access control, any unrelated third party can call `CallDispatcher.dispatch()` directly with a `Call[]` such as `{to: strandedToken, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)}` and take any tokens left behind by any other user's bridge transfer or order fill.

This mirrors the referenced report's root cause exactly: a shared, multi-tenant contract that can be left holding user funds through a legitimate calldata-execution feature, combined with an unrestricted "anyone can call this to move funds out" entrypoint (`MagnetarAction.Permit`/`OFT` there, `CallDispatcher.dispatch()` here) — the combination converts an intended composability feature into outright fund theft.

### Impact Explanation
Any tokens/native ETH stranded in the shared `CallDispatcher` — from a bridged `HyperFungibleToken`/`WrappedHyperFungibleToken` transfer whose attached calldata under-spends the minted amount, or from an intermediate token produced during an `IntentGatewayV2` predispatch/postdispatch swap that isn't part of the enumerated input/output asset list — can be permanently and unconditionally taken by any attacker monitoring the dispatcher's balance. This is concrete theft of user/protocol funds routed through the composability feature of Hyperbridge's token bridge and intents system, reachable from a single relayed cross-chain message or a single order fill, with no privileged role required by the attacker.

### Likelihood Explanation
The likelihood is Medium: the composability feature (bridge-and-call, swap-then-escrow) explicitly requires routing tokens through the shared `CallDispatcher`, and any calldata that does not perfectly and exhaustively drain every token type it could touch (slippage, multi-hop intermediates, reverted/partial third-party call behavior, user error) leaves a balance behind. Given `CallDispatcher` is a single persistent address monitored by MEV/搜索 bots and reused across all apps on a chain, any residual balance is trivial and cheap to detect and sweep by an attacker calling `dispatch()` themselves.

### Recommendation
- Add an access-control check to `CallDispatcher.dispatch()` (e.g., an allowlist of authorized callers/apps, or make `CallDispatcher` instances ephemeral/per-call rather than a shared singleton) so that arbitrary third parties cannot invoke it to move out tokens they did not deposit.
- In `HyperFungibleToken.onAccept` (and `WrappedHyperFungibleToken`'s equivalent), sweep any residual token/ETH balance left in the dispatcher back to the intended beneficiary after executing the attached calldata, mirroring the sweep-and-`DustCollected` pattern already implemented in `IntentGatewayV2`/`IntentsBase._execute`.
- For `IntentGatewayV2`, extend the sweep in `_execute`/predispatch handling to cover any token balance present in the dispatcher after execution, not just tokens explicitly enumerated in `order.inputs`/`order.output.assets`.

### Proof of Concept
1. A user bridges `HyperFungibleToken` cross-chain with `to = CALL_DISPATCHER` and attaches calldata that performs a swap with a non-zero `minAmountOut` slack (or that only partially spends the minted amount).
2. `HyperFungibleToken.onAccept` mints the full amount to `CallDispatcher`, then calls `ICallDispatcher(_dispatcher).dispatch(message.data)`, which executes only the user's supplied calls; any unspent token amount remains on `CallDispatcher`'s balance since no sweep-back occurs. [5](#0-4) 
3. An attacker, watching the shared `CallDispatcher` address's token balances, calls `CallDispatcher.dispatch(abi.encode([Call({to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedBalance)})]))` directly — this succeeds because `dispatch()` performs no caller authorization. [1](#0-0) 
4. The attacker receives the stranded tokens that belonged to the original bridging user/order, with no way for the victim to recover them.

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }

        if (order.output.call.length == 0) return;

        address dispatcher = _params.dispatcher;
        ICallDispatcher(dispatcher).dispatch(order.output.call);

        Call[] memory sweepCalls = new Call[](outputsLen);
        uint256 sweepCount = 0;

        for (uint256 i; i < outputsLen;) {
            address token = address(uint160(uint256(order.output.assets[i].token)));

            if (token == address(0)) {
                uint256 balance = dispatcher.balance;
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({to: address(this), value: balance, data: ""});
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            } else {
                uint256 balance = IERC20(token).balanceOf(dispatcher);
                if (balance > 0) {
                    sweepCalls[sweepCount] = Call({
                        to: token,
                        value: 0,
                        data: abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)
                    });
                    sweepCount++;
                    emit DustCollected(token, balance);
                }
            }

            unchecked {
                ++i;
            }
        }

        if (sweepCount > 0) {

                    ++i;
                }
            }
            ICallDispatcher(dispatcher).dispatch(abi.encode(finalCalls));
        }
