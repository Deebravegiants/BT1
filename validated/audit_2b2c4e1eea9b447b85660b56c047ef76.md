### Title
Router's constant-product AMM math rounds trade outputs in favor of the trader instead of the protocol on both the uncapped buy path and every sell - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy`'s uncapped branch and `Router._computeSell` both derive the trader's payout as `originalReserve - floor(k / newReserve)`. Because Solidity integer division always rounds toward zero (floor), `floor(k / newReserve) <= exact(k / newReserve)`, so the amount handed to the trader (`tokensOut` on buy, `assetOut` on sell) is always rounded *up* relative to the true constant-product value. This is the same rounding-direction defect as the M-3 report: a division that should be rounded in the protocol's favor is instead rounded in the user's favor, and the bonding-curve pair pays out marginally more than the invariant allows on every trade.

### Finding Description
`Router._computeSell` computes:
```solidity
uint256 newReserveToken = reserveToken + amountIn;
assetOut = reserveAsset - (k / newReserveToken);
``` [1](#0-0) 

`k / newReserveToken` is a floor division, so the computed `newReserveAsset` is `<=` the true (irrational) constant-product value. Subtracting a smaller-than-true `newReserveAsset` from `reserveAsset` yields an `assetOut` that is `>=` the exact value — i.e., the seller is overpaid by up to 1 wei of LT per sell, at the pair's expense.

The same pattern exists in the uncapped branch of `Router._computeBuy`:
```solidity
uint256 newReserveAsset = reserveAsset + amountInUsed;
tokensOut = reserveToken - (k / newReserveAsset);
``` [2](#0-1) 

Here `k / newReserveAsset` floors, so `tokensOut` is rounded up — the buyer receives up to 1 wei more of the launched token than the constant-product invariant dictates, again at the curve's expense.

Notably, the protocol's own code comments show the developers *are* aware that rounding must favor the protocol elsewhere in the same function — the overflow-cap branch explicitly rounds `amountInUsed` (the amount charged to the buyer) up ("rounded up so the curve never under-charges") [3](#0-2) . But the ordinary uncapped buy path, and the entire sell path, still use the naive floor-division-then-subtract pattern that rounds the *payout* up instead of down, which is exactly the inverted-rounding-direction bug class described in M-3.

`Pair.swap`'s K-invariant check does not close this gap — it only tolerates a `+1` slack per reserve (`(newTokenReserve + 1) * (newAssetReserve + 1) < k`) [4](#0-3) , and per-swap output rounding is bounded by the same amount, so the check simply accommodates the leak rather than preventing it.

### Impact Explanation
Every buy and sell through `Bonding.buy`/`Bonding.sell` (reachable by any address via `Zap.buy`/`Zap.sell`) pays the trader up to 1 wei more than the exact constant-product amount. This is a systemic, protocol-wide rounding bias against the pair's reserves rather than a one-off dust event: it applies to every single trade on every bonding curve for the life of the protocol, and is compounded by the fact that both legs of a round-trip (buy then sell) each round in the trader's favor, so a buy-then-sell loop leaks reserve value on both legs. At scale (many trades or many tokens), this constitutes a continual value drain from curve reserves that ultimately belong to the protocol/creator/LP path (drained reserves reduce what is later drained into the graduation LP via `Router.graduate`/`_prepareGraduationLiquidity`).

### Likelihood Explanation
High likelihood of occurrence (fires on literally every trade, no special conditions needed) though the per-trade magnitude is small (sub-wei to low-wei). Any unprivileged trader can trigger it via ordinary `Zap.buy`/`Zap.sell` calls, and a motivated actor can automate round-trips to accumulate the leak over many transactions at negligible additional cost since the leaked amount does not depend on trade size, only on a fixed 1-wei-class rounding error per call.

### Recommendation
Round the trader-facing output down (in the protocol's favor) rather than relying on the subtraction of a floor-divided intermediate. Concretely, compute the new reserve with ceiling division so the subtraction yields a floored (not ceiled) output:
```solidity
// buy (uncapped branch)
uint256 newReserveAsset = reserveAsset + amountInUsed;
uint256 newReserveToken = (k + newReserveAsset - 1) / newReserveAsset; // ceil
tokensOut = reserveToken - newReserveToken;

// sell
uint256 newReserveToken2 = reserveToken + amountIn;
uint256 newReserveAsset2 = (k + newReserveToken2 - 1) / newReserveToken2; // ceil
assetOut = reserveAsset - newReserveAsset2;
```
This mirrors the ceil-rounding already used correctly for `amountInUsed` in the overflow-cap branch, ensuring the pair never pays out more than the constant-product invariant allows.

### Proof of Concept
1. Launch a token via `Zap.createToken`, establishing a `Pair` with `k = tokenReserve * assetReserve` fixed at mint.
2. Call `Zap.buy` with an `amountIn` chosen such that `k / (reserveAsset + amountInUsed)` truncates a non-zero remainder (trivial to arrange, since this holds for almost all inputs) — the buyer receives `tokensOut = reserveToken - floor(k/newReserveAsset)`, which is provably `>=` the exact solution `reserveToken - k/newReserveAsset`.
3. Immediately call `Zap.sell` with the tokens just received — `Router._computeSell` again rounds `assetOut` up via the same floor-then-subtract pattern.
4. Compare `assetOut` (LT received back) against the LT originally spent (`amountInUsed`) net of fees: the tester can observe the residual reserve drift is consistently biased in the trader's favor across repeated round-trips (verifiable with a fuzz/differential test computing the exact rational constant-product value alongside the on-chain integer result and asserting `onchain_result <= exact_result` fails, i.e. the on-chain result is strictly greater).

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
