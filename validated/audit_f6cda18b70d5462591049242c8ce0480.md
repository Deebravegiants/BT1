## Title
`SimplexPaymaster` prices gas fees via Chainlink oracles with no L2 sequencer-uptime check, allowing stale prices during a sequencer outage to be treated as fresh - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` is deployed across multiple L2 chains (Base, Optimism, Arbitrum, BSC per the Chainlink feed configuration) and converts every sponsored `UserOperation`'s gas cost into an ERC-20 token amount using two Chainlink `AggregatorV3Interface` feeds (native/USD and token/USD). The staleness check it performs (`block.timestamp - updatedAt > maxOracleAge`) only protects against an oracle that itself stops updating; it does nothing to detect an L2 sequencer outage, during which a Chainlink feed's `updatedAt` can remain "fresh" by wall-clock time while the on-chain price is stale relative to the true off-chain market, exactly the class of bug described in the reference Sherlock report for `PriceTierVesting.sol`.

### Finding Description
`_getOraclePrice` is the sole gate on price data used for every sponsored `UserOperation`: [1](#0-0) 

It reads `latestRoundData()` and only rejects non-positive answers or answers older than `maxOracleAge`. There is no `AggregatorV2V3Interface` "sequencer uptime feed" check (e.g. Chainlink's `0xBCF...` L2 sequencer feeds for Arbitrum/Optimism/Base), and no grace period after a sequencer restart. This price feeds directly into `_tokenPrice`, which every sponsored `UserOperation` relies on to compute how many ERC-20 tokens to pull from the sender: [2](#0-1) 

`_tokenPrice` is invoked from `_fetchDetails` (called during `_validatePaymasterUserOp`, i.e. on every sponsored transaction submitted by any unprivileged user/bundler) and from `swapAndDeposit`: [3](#0-2) [4](#0-3) 

The contract's own header explicitly acknowledges the deployment targets are L2s with fast-updating heartbeats ("BSC stablecoins ~27s, Base/Ethereum stablecoins up to 24h"), confirming this contract runs on sequencer-dependent chains where the missing check is directly reachable: [5](#0-4) 

### Impact Explanation
If the L2 sequencer for a deployment chain (Base, Optimism, Arbitrum) goes down, Chainlink's L2 price feed can continue reporting a stale `updatedAt` timestamp that still falls within `maxOracleAge`, so `_getOraclePrice` treats it as valid. Any unprivileged user who submits a `UserOperation` during this window has their gas fee (charged in ERC-20 tokens) priced against stale native/USD or token/USD values. If the stale price undervalues the native asset relative to its real (pre-outage) price, users pay fewer tokens than the actual gas cost, directly draining value from the paymaster's treasury/surplus; the inverse case overcharges users. Given the contract is explicitly built to run unattended (no privileged key path for per-transaction pricing), this is a direct funds-drain vector against the paymaster during any sequencer disruption on the affected L2s.

### Likelihood Explanation
L2 sequencer downtimes are a recurring, documented occurrence on Arbitrum, Optimism, and Base, and the exploit requires no special privileges — any address whose `UserOperation` is sponsored by `SimplexPaymaster` during the outage automatically transacts against the mispriced feed. No governance action, malicious relayer, or malicious admin is required to trigger the condition; it is a natural, well-known chain-infrastructure event.

### Recommendation
Add a Chainlink sequencer-uptime feed check (per chain) to `_getOraclePrice`/`_tokenPrice`, following Chainlink's documented pattern: revert if `answer == 1` (sequencer down), and enforce a grace period after `startedAt` before trusting the feed again post-restart, mirroring the recommendation in the referenced report.

### Proof of Concept
1. Deploy `SimplexPaymaster` on an L2 (e.g. Base) with `maxOracleAge` set to the chain's normal heartbeat (e.g. 24h for a stablecoin feed).
2. Simulate a sequencer outage where the underlying Chainlink feed's `updatedAt` was refreshed just before the outage began, so `block.timestamp - updatedAt <= maxOracleAge` throughout the outage.
3. During the outage, the real off-chain native/USD price moves significantly, but the feed value is stuck.
4. Submit a `UserOperation` with `paymasterData` for a registered token; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` returns the stale price without reverting, since no sequencer check exists.
5. The token amount charged to the sender diverges from the true gas cost, allowing systematic underpayment (theft from the paymaster's held funds) for the duration of the outage. [6](#0-5)

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
