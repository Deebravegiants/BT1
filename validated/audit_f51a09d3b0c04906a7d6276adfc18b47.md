## Analog Found

### Title
Pausing a HyperFungibleToken/WrappedHyperFungibleToken blocks the only refund path for timed-out cross-chain transfers - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol])

### Summary
`WrappedHyperFungibleToken(Upgradeable)` and `HyperFungibleToken(Upgradeable)` gate `onPostRequestTimeout()` — the sole mechanism that returns a user's locked/burned principal after a cross-chain `send()` fails to be delivered — behind the `whenNotPaused` modifier. This mirrors the reported Balancer bug: a legitimate protection mechanism (pause) on a critical path unintentionally blocks the very recovery/refund action a user needs to reclaim funds already committed to an in-flight, irreversible operation.

### Finding Description
`send()` locks the user's ERC-20 (or wraps native ETH) and dispatches a POST request cross-chain, whose escrow is only released back to the user in one of two ways: successful delivery (which is out of the user's control, dependent on relayers and destination chain liveness) or `onPostRequestTimeout()`, called by `EvmHost.dispatchTimeOut` once the message has timed out: [1](#0-0) 

Both `onAccept()` and `onPostRequestTimeout()` on these token apps are marked `whenNotPaused`: [2](#0-1) [3](#0-2) [4](#0-3) 

The host's timeout dispatcher makes a low-level `.call` into the app's `onPostRequestTimeout`; if that call reverts (as it will while `paused()` is true), the commitment is simply re-stored for a future retry — it does not fail permanently at the protocol level: [5](#0-4) 

The documentation confirms `onPostRequestTimeout` "Can be called multiple times until it succeeds" and is expected to be idempotent: [6](#0-5) 

The bug-class match to the Balancer report is precise: in both cases, an emergency/administrative pause on a dependency that is *supposed to be orthogonal to refunds* silently blocks the one function that lets a user recover already-committed principal for an action whose outcome is otherwise irreversible (the source-chain assets are already locked/burned; only `onAccept` on the destination or `onPostRequestTimeout` on the source can release them).

### Impact Explanation
While the pause is active, users whose `send()` transactions have timed out (e.g., due to relayer inactivity, destination chain congestion, or a state-machine liveness fault — exactly the scenarios the ISMP timeout mechanism exists to handle per `docs/content/protocol/ismp/timeouts.mdx`) cannot reclaim their locked/burned tokens. Because pausing is frequently triggered *in response to* an active incident (e.g., a suspected exploit or bridge malfunction), this is precisely the window during which timeouts are most likely to occur and users most need to recover funds — yet the pause blocks the recovery path itself. If the pause persists (extended incident response, abandoned contract, or governance delay), user funds remain frozen in escrow indefinitely, with no alternative recovery path defined in the contract.

### Likelihood Explanation
This triggers under a realistic combination of ordinary operational events: (1) a cross-chain `send()` is dispatched, (2) it times out due to non-malicious relayer/liveness issues, and (3) the token contract is paused at the same time (for any legitimate operational reason, not requiring a malicious actor). No attacker action is needed — an unprivileged user's routine use of `send()` combined with normal pause operations for incident response is sufficient to reach this state.

### Recommendation
Do not gate `onPostRequestTimeout()` (and ideally `onAccept()`'s finalize/refund paths) with `whenNotPaused`. Pause should only block the initiation of *new* value-locking actions (`send()`), never the finalization of already-committed cross-chain operations. If pausing must also affect these callbacks for safety reasons, provide an explicit, separately-gated emergency-recovery function that lets users withdraw escrowed principal for timed-out requests independent of the pause flag.

### Proof of Concept
1. Alice calls `send()` on `WrappedHyperFungibleTokenUpgradeable`, locking 1000 USDC and dispatching a POST request with a 1-hour timeout.
2. The relayer network fails to deliver the message before the timeout elapses (liveness/congestion — no malicious actor required).
3. Before Alice can submit the timeout proof, the contract owner pauses the token (e.g., in response to an unrelated incident) via the inherited `Pausable.pause()`.
4. A relayer or Alice submits `handlePostRequestTimeouts()` on `EvmHost`, which calls `dispatchTimeOut()`, which low-level `.call`s `onPostRequestTimeout()`.
5. The call reverts due to `whenNotPaused`; `EvmHost.dispatchTimeOut` re-stores the commitment (per `evm/src/core/EvmHost.sol` lines 885-906) and no refund occurs.
6. Alice's 1000 USDC remains locked in the contract with no way to reclaim it until the contract is unpaused — a decision entirely outside her control.

    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(incoming.request.body, (HyperFungibleTokenUpgradeable.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }

    function dispatchTimeOut(
        PostRequestTimeout memory timeout,
        FeeMetadata memory meta,
        bytes32 commitment
    ) external restrict(_hostParams.handler) {
        // replay protection
        delete _requestCommitments[commitment];
        (bool success,) = _bytesToAddress(timeout.request.from)
            .call(abi.encodeWithSelector(IApp.onPostRequestTimeout.selector, timeout));

        if (!success) {
            // so that it can be retried
            _requestCommitments[commitment] = meta;
            return;
        }

        if (meta.fee != 0) {
            // refund relayer fee
            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);
        }
        emit PostRequestTimeoutHandled({commitment: commitment, dest: string(timeout.request.dest)});
    }
