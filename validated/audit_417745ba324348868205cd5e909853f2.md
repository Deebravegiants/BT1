### Title
Webhook `shop-domain` Header Is Not Covered by the HMAC, Allowing Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for a webhook exclusively from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, while the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only ever covers the raw request body. This breaks the binding `shop_authenticated_by_hmac == shop_used_for_tenant_routing`, since no such binding exists in the code.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` values are all pulled straight from HTTP headers with no cryptographic relationship to the signature: [2](#0-1) 

`HmacValidator.validate` verifies the signature strictly against `verifiable_query.to_signable_string` (the body) using `Context.api_secret_key`: [3](#0-2) 

`Registry.process` only checks this body-only HMAC before dispatching the handler with `shop: request.shop`, taken directly from the unauthenticated header: [4](#0-3) 

Because the `client_secret`/`api_secret_key` is shared across every shop that installs a given app, any unprivileged internet user who controls a legitimate installation of the target app (e.g., their own development/test store) can capture one genuine `(raw_body, hmac)` pair that Shopify sent them. They can then replay that exact body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header with an arbitrary victim shop domain. `HmacValidator.validate` will still pass, because the shop value was never part of the signed content, and the registry will invoke the app's handler believing the event originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an attacker with a legitimate (but unrelated) installation can inject webhook events that the host application will attribute to any other merchant's shop domain. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to key per-tenant storage, trigger data deletion for `shop/redact` or `customers/redact` topics, or gate `app/uninstalled` cleanup), this enables cross-tenant data corruption or spoofed lifecycle events for shops the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Requires only: (1) the attacker legitimately installs the target app on any shop they control (trivial, no special privilege), (2) capture one real webhook delivery (trivial, any topic works, e.g. `app/uninstalled`), (3) replay it against the app's public webhook endpoint with a modified `shop-domain` header. No access token, `api_secret_key`, or credential theft is required — only observation of traffic the attacker themselves legitimately receives. This is a low-effort, no-privilege attack limited only by the app author's specific use of `shop` in their handler logic.

### Recommendation
Bind the `shop` (and ideally `topic`) values into the signed content verified against the HMAC, or otherwise cryptographically bind the header-derived shop to the request before trusting it for tenant routing — e.g., include the shop domain in the signable string, or cross-validate the header shop against a shop-specific webhook secret / registered shop list rather than relying purely on the shared app secret over the body alone.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers/receives a legitimate webhook, e.g. `app/uninstalled`, capturing:
   - `raw_body = "{}"` (or any real payload)
   - `x-shopify-hmac-sha256 = <valid HMAC over raw_body computed by Shopify with the app's shared secret>`
3. Attacker sends a forged HTTP request to the app's webhook receiver:
   ```
   POST /webhooks
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <captured valid hmac>
   x-shopify-shop-domain: victim-shop.myshopify.com
   Body: {}   (same raw_body used to compute the captured hmac)
   ```
4. `Utils::HmacValidator.validate` recomputes the HMAC over the body only, matches, and returns `true` (per `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` proceeds to call the app's handler with `shop: "victim-shop.myshopify.com"` (per `lib/shopify_api/webhooks/registry.rb:198-199`), even though Shopify never sent this event for that shop.
