### Title
Predictable, unsigned `offline_#{shop}` session cookie value enables cross-tenant session fixation - (File: `lib/shopify_api/auth/session.rb`, `lib/shopify_api/auth/oauth.rb`, `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded (and embedded-without-JWT-fallback) apps, this gem generates the browser session-cookie value as the deterministic, unsigned string `"offline_#{shop}"` (or `"#{shop}_#{user_id}"` for online sessions), and later retrieves the "current session id" by reading that cookie value back verbatim with no cryptographic verification. This breaks the identity binding `cookie value == authenticated session id`: the value that ends up authorizing API calls is derived entirely from unauthenticated, attacker-suppliable bytes plus a publicly-guessable shop domain.

### Finding Description
`ShopifyAPI::Auth::Session.from` builds the session `id` deterministically from the `shop` string alone for offline sessions: [1](#0-0) 

`Oauth.validate_auth_callback` then places this predictable `session.id` directly into the `SessionCookie#value` with no signature, MAC, or any binding to the browser/user that completed OAuth: [2](#0-1) 

`SessionCookie` itself is a plain value struct with no integrity protection: [3](#0-2) 

On the read side, `SessionUtils.current_session_id` / `cookie_session_id` return the raw cookie value verbatim as the trusted "current session id," performing zero verification that the bytes originated from a real, previously-completed OAuth flow: [4](#0-3) [5](#0-4) 

This is the analog of the `liquidateFrom` bug class: just as `liquidateFrom` let an unprivileged caller set an arbitrary `from` account and bypass the checks that normally bind an action to its rightful owner, here an unprivileged party can set an arbitrary `shopify_app_session` cookie value and bypass the checks that should bind a "current session id" to a real, previously-authenticated session. The equality that should hold — `session_id_returned_by_gem == session_id_of_a_session_that_actually_completed_HMAC-verified_OAuth` — does not hold, because the gem's own `cookie_session_id` performs no verification step at all; it trusts whatever bytes are in the cookie.

Because the offline session id is simply `"offline_" + shop` and myshopify.com shop domains are public/enumerable (visible in storefronts, sitemaps, app listings, etc.), any unauthenticated internet user can construct this string for a victim shop without needing any secret. If a host application follows the gem's own documented pattern (`docs/getting_started.md`, `docs/usage/oauth.md`) of using `current_session_id` as the storage lookup key, an attacker's forged cookie causes the gem to hand back the victim shop's session id, and the host app's `SessionRepository.retrieve_session_for_shop`-style lookup returns the victim's real access token/session for use in subsequent Admin API calls made through `ShopifyAPI::Clients` on the attacker's behalf.

### Impact Explanation
This is a session fixation / cross-tenant impersonation vector: an unauthenticated attacker can obtain the app's use of a legitimate merchant's access token by supplying a forged, unsigned cookie value that the gem itself creates via a predictable, non-random ID scheme and returns without verification. This crosses the tenant boundary the library exists to protect (shop A's session used on behalf of shop A only), fitting the "cross-tenant access" / "credential leakage" high/critical impact category.

### Likelihood Explanation
Likelihood is tempered by real-world constraints: exploitation requires the host application to (a) be non-embedded (or embedded and falling back to cookie auth), and (b) implement session storage keyed directly by `session.id` as shown in the gem's own documentation and the referenced `shopify_app` reference implementation — i.e., the gem's documented API is followed as intended, not misused. The `offline_#{shop}` value requires no secret to construct, only knowledge of the target's `myshopify.com` domain, which is generally public. This makes the primitive readily reachable, but the full exploit chain also depends on how the specific host stores/serves that cookie (e.g., whether `httponly`/`secure` flags on the attacker's own browser block them from setting it cross-origin, and whether the app actually keys its store by this exact value).

### Recommendation
- Do not derive session identifiers solely from public/predictable values (`shop`, `user_id`); if a cookie must carry the session id, sign it (e.g., HMAC with `api_secret_key`) or make the cookie itself an opaque, cryptographically random token as it already is for `Session#id` default (`SecureRandom.uuid`) — remove the deterministic `id: "offline_#{shop}"` / `"#{shop}_#{user_id}"` override in `Session.from` and prefer the random default, or MAC-sign whatever value is placed in the cookie.
- In `SessionUtils.cookie_session_id`, verify the cookie's integrity (e.g., HMAC verification) before returning it as a trusted session id, mirroring the pattern already used for OAuth callbacks (`Utils::HmacValidator`).
- Document explicitly that cookie values must never be used as direct, unauthenticated database lookup keys without a signature check.

### Proof of Concept
1. Attacker learns (publicly) that the target app is installed on `victim-shop.myshopify.com`.
2. Attacker sends a request to any endpoint of the host app that calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, with `cookies["shopify_app_session"] = "offline_victim-shop.myshopify.com"`.
3. `cookie_session_id` returns `"offline_victim-shop.myshopify.com"` unmodified (`lib/shopify_api/utils/session_utils.rb:68-71`).
4. Following the gem's documented pattern, the host app looks up its session store by this id (as shown in `docs/getting_started.md` / `BREAKING_CHANGES_FOR_V16.md` reference implementation) and retrieves the real `access_token` for `victim-shop.myshopify.com`.
5. Host app performs Shopify Admin API calls using that access token on behalf of the attacker's request, exfiltrating/modifying the victim's store data.

# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Auth
    module Oauth
      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
    end
