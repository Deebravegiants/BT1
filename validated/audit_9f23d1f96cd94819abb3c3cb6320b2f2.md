### Title
Overfill protection is dead-code by design — `maxOverfillBps`/`maxConsecutiveClamps` never actually bound solver payout, giving a false sense of loss protection - (File: `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
This is analogous to the reported `isSafeMode`/`highDivergence` bug: a safety threshold that is documented and configured as an active protection mechanism, but whose triggering condition never actually changes program behavior — it only logs, leaving the protected code path fully exposed. In Hyperbridge's `FXFiller` (the intent-solver strategy that fills orders dispatched through the Hyperbridge intents/order-fill path), the `overfillProtection` config (`maxOverfillBps`, `maxConsecutiveClamps`) is documented and exposed to filler operators as "Bounds per-leg loss when internal pricing is wrong (bug, stale cache, manipulated venue)" and "halt after `maxConsecutiveClamps` consecutive clamped orders," but the clamp itself is deliberately disabled in code, and the halt counter is permanently fed a hardcoded `false`.

### Finding Description
In `resolveOutputsForOrder` (fx.ts), the overfill ceiling is computed and compared, but the result is only used for a warning log, not for clamping the actual payout: [1](#0-0) 

`policyMaxOutput` is assigned directly from `rawPolicyMaxOutput` (the unclamped curve-computed value) rather than `min(rawPolicyMaxOutput, overfillCeiling)`, and the code comment explicitly states: "Overfill detection is warn-only: the clamp is DISABLED, so the filler fills the full computed amount even when it exceeds (1 + maxOverfillBps) × user-requested." This mirrors the `RiskEngine.isSafeMode()` situation: the threshold comparison exists and looks like an enforced safety gate, but the branch that would act on a breach (clamping/halting) never fires against the value actually paid out.

Compounding this, `recordOrderOutcome` — the function that increments `consecutiveClamps` toward `maxConsecutiveClamps` and halts the filler — is documented to react "Only venue-priced legs feed this counter... a streak of those is the signal that a live market source has gone off... and the filler should stop": [2](#0-1) 

But per the project's own decision log, this call site is now permanently invoked with `clamped = false`, since the clamp was removed, so `maxConsecutiveClamps` can never be reached and `this.halted` never becomes `true` via this path: [3](#0-2) 

Meanwhile the CLI wizard, TOML docs, and README-style config comments still actively instruct operators to configure `maxOverfillBps`/`maxConsecutiveClamps` as if they bound risk: [4](#0-3) [5](#0-4) [6](#0-5) 

### Impact Explanation
The overfill/halt mechanism exists specifically to bound loss "when internal pricing is wrong (bug, stale cache, manipulated venue)" — i.e., it is the intent solver's last line of defense against paying out far more than intended per fill, and against continuing to fill (and lose funds) once a systemic pricing fault is detected. Because the clamp never executes and the halt counter never increments, a pricing bug, stale cache, or a manipulated Uniswap V4 venue quote (the exact threat model named in the code's own comments and the `checkPriceGuard`/`referenceRate` price-guard machinery) can cause the filler to repeatedly overpay on every subsequent order with no automatic circuit breaker, unboundedly draining the solver's escrowed/vault funds across an entire market-making session rather than being capped at a single 5%-over-quote loss and a 3-order halt as documented. Operators who rely on the advertised `overfillProtection` config as their stated risk bound are exposed to materially larger, uncapped losses than the documentation and CLI wizard represent — a direct parallel to the `highDivergence` finding where a safety check that "looks" enforced never actually constrains the dangerous state.

### Likelihood Explanation
This is not a probabilistic bug — it is code that always executes this way for every order once `maxOverfillBps`/`overfillProtection` is configured; the disabling is deterministic and permanent for as long as the current implementation stands, exactly like the `highDivergence` check being unconditionally unreachable. It is triggered any time (a) pricing input is wrong, e.g., via a stale cache, an internal pricing bug, or a manipulated/thin Uniswap V4 pool the `checkPriceGuard` band doesn't reject, and (b) the resulting curve/pool-derived quantity happens to exceed the user-requested amount by more than the configured ceiling — a realistic scenario for a market-making solver executing continuously against live venue prices.

### Recommendation
Either (a) re-enable an actual output clamp — `policyMaxOutput = min(rawPolicyMaxOutput, overfillCeiling)` — when overfill protection is configured and accept the documented trade-off (escrow proportionality vs. quoted price), or (b) if overfilling must remain unconditional as a deliberate business decision, remove/rename the `overfillProtection` config, CLI wizard step, and documentation so operators are not led to believe a loss bound and halt mechanism are active. At minimum, `recordOrderOutcome` should be wired to the real overfill-ceiling breach (not a hardcoded `false`) so `maxConsecutiveClamps` can still serve as a systemic-pricing-fault circuit breaker even if the per-order clamp itself is intentionally disabled.

### Proof of Concept
1. Configure a filler with `[simplex.overfillProtection] maxOverfillBps = 500, maxConsecutiveClamps = 3` and a Uniswap V4 venue-priced pair.
2. Feed a manipulated/thin pool quote that still passes `checkPriceGuard`'s `maxDeviationBps` band but yields a `rawPolicyMaxOutput` more than 5% above `output.amount` for several consecutive orders (as in the existing `fx.price-guard.test.ts` and `fx.curve-payout.test.ts` suites, which already assert the payout equals the unclamped curve amount, not the capped one — see `sdk/packages/simplex/docs/ai/changelog/2026-08-20-regression-test-fills-pay-the-curve-amount.md`).
3. Observe: `resolveOutputsForOrder` logs "Overfill ceiling exceeded — clamp disabled, filling unclamped amount" on each order but pays the full `rawPolicyMaxOutput` every time ( [1](#0-0) ), and `this.halted` never becomes `true` regardless of how many consecutive orders exceed the ceiling, since `recordOrderOutcome(false, ...)` is invoked unconditionally.

	/**
	 * Update consecutive-clamp counter after a successful order evaluation.
	 * Only venue-priced legs feed this counter (see clamp site) — a streak of those
	 * is the signal that a live market source has gone off (stale pool, manipulated
	 * venue) and the filler should stop until an operator investigates. Offline
	 * price-curve clamps warn but never reach here.
	 */
	private recordOrderOutcome(clamped: boolean, orderId: string | undefined) {
		if (clamped) {
			this.consecutiveClamps += 1
			if (this.consecutiveClamps >= this.maxConsecutiveClamps) {
				this.halted = true
				this.logger.error(
					{ orderId, consecutiveClamps: this.consecutiveClamps, maxConsecutiveClamps: this.maxConsecutiveClamps },
					"FXFiller HALTED — venue-priced overfill clamp triggered consecutively; restart required after investigation",
				)
			}
		} else {
			this.consecutiveClamps = 0
		}
	}
