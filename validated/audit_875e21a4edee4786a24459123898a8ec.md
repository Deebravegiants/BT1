### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which validates the HMAC over `request.to_signable_string`. For `Webhooks::Request`, `to_signable_string` returns only the raw request body [1](#0-0) . The `shop` (tenant identity), `topic`, and `webhook_id` are all pulled directly from unauthenticated HTTP headers and are never included in the signed bytes [2](#0-1) . `Registry.process` then hands `request.shop` straight to the handler as the tenant identifier after only checking the HMAC [3](#0-2) .

### Finding Description
This is the same class of bug as the report's identity-binding break: an "action" field (`shop`) is used to make a tenant-scoped decision, but the binding proof (HMAC) does not cover that field. Concretely:

- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received `hmac` [4](#0-3) .
- For webhooks, `to_signable_string` == `@raw_body` only [1](#0-0) .
- `shop` is read from the `shop-domain` header, which is not part of that signed string [5](#0-4) .
- `Registry.process` trusts `request.shop` for tenant attribution as soon as `HmacValidator.validate` returns true [3](#0-2) .

Equality that should hold but doesn't: `shop_bound_by_hmac == shop_used_for_tenant_dispatch`. In reality, `shop_bound_by_hmac` is undefined (empty set — the signature covers zero identity fields), while `shop_used_for_tenant_dispatch` is taken verbatim from an attacker-controllable header.

Because the app's `client_secret` (and thus the HMAC key) is shared across every shop that installs the app, any unprivileged party who operates their own shop instance receives genuine Shopify webhooks with a valid `raw_body`/`hmac` pair for their own tenant. That valid `(raw_body, hmac)` pair can be replayed to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the shop header), and `Registry.process` dispatches the handler with `shop: request.shop` set to the victim's domain, `WebhookMetadata.new(... shop: request.shop ...)` [6](#0-5) .

### Impact Explanation
Any app-supplied webhook handler that trusts `WebhookMetadata#shop` to select which tenant's stored session/access token to use, or to key persisted data, can be made to act on/against a shop the attacker does not own — a cross-tenant access primitive triggered purely by header substitution on an otherwise legitimately-signed payload. This meets the Critical bar of "cross-tenant access."

### Likelihood Explanation
Requires only: (1) the attacker controls one unprivileged shop with the vulnerable app installed (any merchant can do this for a public app), so they receive at least one real `(raw_body, hmac)` pair for their own shop; (2) the app's webhook endpoint is reachable from the internet, which is required for Shopify delivery in the first place. No access token, `client_secret`, or privileged account is needed — only header manipulation of a replayed, previously-valid body.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that is actually HMAC-verified, or independently authenticate the shop domain against a known/expected value before dispatch (e.g. compare `request.shop` to the shop associated with the stored offline session used to fetch context, and/or include a nonce/timestamp check to prevent replay). At minimum, document and encourage host apps to cross-check `request.shop` against an already-trusted tenant record rather than trusting the header as authenticated identity.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a real webhook: raw body `B` with header `x-shopify-hmac-sha256: H` (valid, computed by Shopify with the app's `client_secret`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the identical request to the app's webhook endpoint, keeping body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`, so any tenant-scoped logic executes as if the (attacker-supplied) body genuinely originated from `victim.myshopify.com`.
