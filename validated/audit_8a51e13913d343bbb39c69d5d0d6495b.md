### Title
Webhook `shop` (and `topic`/`webhook-id`) attribution is not covered by the HMAC, allowing shop-spoofing via header manipulation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `WebhookMetadata` struct whose `shop` (and `topic`, `webhook_id`) fields are taken directly from unauthenticated HTTP headers. The binding `shop-that-produced-the-HMAC == shop-attributed-to-the-webhook` is never enforced.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines the signable content as the raw body only: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors, by contrast, are read straight from HTTP headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)` — which, per `HmacValidator`/`VerifiableQuery`, checks the HMAC exclusively against `to_signable_string` (the raw body) — and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to construct the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

`WebhookMetadata.shop` is the only tenant identifier handed to the app's `WebhookHandler#handle`: [5](#0-4) 

Because the app's webhook client secret is shared across every shop that installs the app, any user who installs the app on their own store (e.g. a free development store) receives genuine webhook deliveries with a valid `hmac-sha256` computed over a body they fully control/observe. That attacker can then replay the exact same `raw_body` + `hmac` pair directly to the app's public webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`/`shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` will still pass, because the header values it substitutes are never part of `to_signable_string`. `Registry.process` will then deliver a `WebhookMetadata` claiming the victim shop as the origin, with an attacker-chosen `body`, `topic`, and `webhook_id`, to the host application's handler.

This breaks the binding equality: **shop that authenticated (via the HMAC-bound body) ≠ shop attributed to the event in `WebhookMetadata.shop`**.

### Impact Explanation
If a host application's webhook handler uses `WebhookMetadata.shop` to look up or mutate per-tenant state (session lookup, order/customer records, mandatory redact webhooks such as `shop/redact`, `customers/redact`, `customers/data_request`), an attacker can forge events attributed to a victim shop's tenant using only their own legitimately obtained (but replayed with modified headers) webhook payload — this is a cross-tenant access primitive, since it lets one merchant inject fabricated webhook data into another merchant's tenant context within the host app, without ever needing the victim's credentials or access token.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on an attacker-controlled shop to receive a genuine signed webhook, and (2) the ability to send an arbitrary HTTP POST to the app's public webhook receiver endpoint with attacker-chosen headers — both are available to any unprivileged internet user/merchant, no leaked secrets or privileged access required.

### Recommendation
Bind the `shop` (and `topic`/`webhook_id`) values into the HMAC-verified signable content, or independently authenticate the shop domain (e.g., verify it against a known/registered shop list bound to the delivery, not merely trust the header) before constructing `WebhookMetadata` in `Registry.process`. At minimum, document/enforce that `to_signable_string` must include all fields the handler will treat as trusted identity, not just the body.

### Proof of Concept
1. Install the target Shopify app on an attacker-owned shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) to capture a real request with headers `shopify-hmac-sha256: <valid-hmac>`, `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: orders/create`, and raw body `B`.
2. Replay the exact same body `B` and `shopify-hmac-sha256` value to the app's webhook endpoint, but set `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC against `request.to_signable_string` (`= B`) — validation succeeds.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", topic: "orders/create", body: <attacker-controlled>, ...)`, i.e., a forged event falsely attributed to the victim tenant.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
