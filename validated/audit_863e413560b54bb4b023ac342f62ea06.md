### Title
Permanent market freeze from index-growth overflow before borrow-index cap - ([File: common/src/rates/simulate.rs])

### Summary
A sufficiently large borrowed position can make `scaled_to_original()` overflow during interest accrual before `update_borrow_index()` can clamp the borrow index to `MAX_BORROW_INDEX_RAY`. Because every pool mutation calls `global_sync()` before processing, the first accrual that reaches this product bound permanently panics the market: borrowers cannot repay, suppliers cannot withdraw, and liquidations cannot proceed.

### Finding Description
`accrue_step()` first converts stored scaled debt into RAY value using `borrowed.mul(env, borrow_index)`, then calculates the interest factor, and only afterward calls `update_borrow_index()` [1](#0-0) . `scaled_to_original()` is a non-saturating `Ray` multiplication [2](#0-1) . Although `update_borrow_index()` caps a successfully calculated index at `MAX_BORROW_INDEX_RAY`, that cap is reached too late to prevent `borrowed * borrow_index` from overflowing [3](#0-2) .

Every `PoolAction` leg validates and loads the market through `synced_market()`, which invokes `global_sync()` before repayment, withdrawal, borrowing, settlement, or seizure accounting [4](#0-3) . `global_sync()` writes the new timestamp only after all accrual chunks complete [5](#0-4) . Therefore a panic in the first value conversion aborts the call without advancing `last_timestamp`; retrying the same or any other mutation reaches the same overflow again.

The repository’s own production-path test establishes the condition and consequences: a large 18-decimal market at sustained high utilization overflows inside `scaled_to_original()` while `borrow_index < MAX_BORROW_INDEX_RAY`, after which both withdrawal and repayment fail with `MathOverflow` [6](#0-5) . The test comments explicitly state that every verb accrues first and that no repay, withdraw, or liquidation remains possible [7](#0-6) .

### Impact Explanation
This causes permanent freezing of all supplier funds and outstanding collateral recovery in the affected `(hub_id, asset)` market. Once the stored scaled debt and index cross the representable product bound:

- `withdraw` cannot burn supply shares or return supplier funds;
- `repay` cannot burn debt or restore liquidity;
- `liquidate` cannot seize collateral or repay bad positions;
- `clean_bad_debt`, `recapitalize`, `claim_revenue`, and later `update_indexes` calls also load the same accrual path;
- borrowers’ collateral remains locked because the debt market cannot be accrued or settled.

This is a market-wide liveness failure, not merely a transaction-level denial of service. The stored timestamp does not advance on failure, so no caller can skip the overflowing interval.

### Likelihood Explanation
The trigger requires a large absolute debt book and enough high-rate accrual for `borrowed_scaled_ray * borrow_index` to exceed `i128::MAX`. An unprivileged address can create the required state with the public controller paths:

1. `supply(caller, account_id, spoke_id, supplies)` for the debt-market asset.
2. `supply(caller, account_id, spoke_id, supplies)` for collateral.
3. `borrow(caller, account_id, borrows, to)` to establish very high utilization.
4. `update_indexes(hub_assets)` after sufficient accrual.

No privileged operation is needed for the state transition itself; interest accrues autonomously from ledger time. The practical likelihood is constrained by token liquidity, market caps, collateral requirements, and the amount of accrual needed, so this is a Medium-severity permanent-freeze condition rather than an immediately reachable theft.

### Recommendation
Bound the debt value before applying index growth. In `accrue_step()` or `update_borrow_index()`:

- compute the largest `borrow_index` representable for the current `borrowed` scaled amount;
- clamp `new_borrow_index` to `min(MAX_BORROW_INDEX_RAY, i128::MAX-compatible product bound)`;
- ensure utilization, supplier rewards, and supply-index distribution use the same clamped value;
- preserve monotonicity and emit or record that the value-bound clamp was reached.

Alternatively, store and accrue on representations that cannot overflow, such as bounded normalized totals or wider `I256` intermediates with explicit saturation. Add regression coverage proving that `update_indexes`, `repay`, `withdraw`, and `liquidate` remain callable after the index reaches either bound.

### Proof of Concept
The existing test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates the path:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

let failure = loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
        break e;
    }
};

assert_contract_error(Err::<(), _>(failure), errors::MATH_OVERFLOW);
assert!(book(&t, "BIG18").borrow_index < MAX_BORROW_INDEX_RAY);
assert_contract_error(
    t.try_withdraw_raw(BOB, "BIG18", 1),
    errors::MATH_OVERFLOW
);
assert_contract_error(
    t.try_repay(ALICE, "BIG18", 1.0),
    errors::MATH_OVERFLOW
);
```

The call sequence is reachable through public `controller::supply`, `controller::borrow`, and `controller::update_indexes`; the pool enforces owner-only mutation internally, with the controller acting as that owner [8](#0-7) . The failure occurs below the configured index cap because the unbounded market-value conversion runs before the cap can engage [9](#0-8) .

    if !cache.needs_accrual() {
        return;

        remaining = remaining.saturating_sub(chunk);
