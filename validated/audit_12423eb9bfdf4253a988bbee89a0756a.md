## Finding

### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor read directly from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body, never the headers. Any party capable of obtaining one validly-signed webhook body (e.g. by installing the app on a shop they control) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `Registry.process` accepts the request as valid and hands the forged shop identity to the host application's handler as if it were authenticated.

### Finding Description
The library's HMAC check is: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`. That validator recomputes the HMAC only over `verifiable_query.to_signable_string`: [2](#0-1) 

For webhooks, `to_signable_string` is defined as the raw body only: [3](#0-2) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated headers: [4](#0-3) 

So the binding the code implicitly assumes — `shop authenticated == shop delivered to handler` — does not hold: the HMAC only proves "this body was produced with the app's secret for *some* delivery," not "this body belongs to *this* shop." After `HmacValidator.validate` succeeds, `Registry.process` forwards the header-derived, unauthenticated `shop` value straight into the handler's `WebhookMetadata`: [5](#0-4) 

An attacker who has (or creates) their own shop installation of the app receives a webhook whose HMAC is computed only over that body. They can capture that valid body+HMAC pair and re-POST it to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop. `Registry.process` will validate successfully (the HMAC still matches the unchanged body) and dispatch the handler with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own store.

### Impact Explanation
If the host application trusts the `shop` value returned by this library to select which tenant's data/session the webhook payload applies to (a common pattern, since the library markets `Registry.process` as the trusted entry point after HMAC validation), an attacker can inject fabricated event data attributed to an arbitrary victim shop. This is a cross-tenant identity confusion: data controlled by an unprivileged attacker (their own shop's webhook body) is processed under another tenant's identity, without the attacker ever needing the app's `client_secret`, an access token, or any privileged credential.

### Likelihood Explanation
Requires only: (1) ability to install the target app on a shop the attacker controls (unprivileged, self-service), and (2) ability to construct/replay an HTTP request with attacker-chosen headers but a legitimate captured body+HMAC pair to the app's webhook endpoint — no secret material is needed. This is a realistic path for any public/listed app.

### Recommendation
Extend the webhook signable string (or introduce a separate binding check) to cover the shop-domain header, or explicitly document/require that consuming applications must not treat the `shop` value from `Webhooks::Request`/`WebhookMetadata` as authenticated beyond mere delivery-by-Shopify, and instead cross-check it against a shop the app has an active, previously-established session/subscription for before acting on it.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and trigger a webhook (e.g. `orders/create`) so Shopify delivers a POST with a valid `X-Shopify-Hmac-Sha256` computed over the JSON body.
2. Capture the raw body and HMAC header from that delivery (e.g. via a proxy the attacker controls, or Partner Dashboard webhook delivery logs).
3. Re-send the identical body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain: attacker-shop.myshopify.com` with `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which passes because it only checks the unchanged body against the HMAC; the handler executes with `shop: "victim-shop.myshopify.com"`. [6](#0-5) [7](#0-6)
