### Title
XRP withdrawal to unfunded XRPL account bypasses destination-tag/deposit-auth checks - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
In `PoaBridge.validateWithdrawal`, the XRPL destination-tag and deposit-auth checks are performed only inside a `try` block that first calls `xrpl.httpClient.getAccountInfo`. For an XRP withdrawal (`isXrp === true`) to an address not yet activated on the ledger, this call throws `XrplAccountNotFundedError`, which is swallowed by the `catch`, causing `validateWithdrawal` to resolve successfully without ever evaluating `requireDestinationTag`/`depositAuthEnabled`.

### Finding Description
The broken equality: the (chain, address, memo) tuple that will be enforced once the XRPL account is funded and potentially has `requireDestinationTag`/`depositAuth` flags set, is assumed to equal the "no destination-tag/deposit-auth requirement" state used at signing/validation time — but this equality is never actually checked because the code path that would check it is skipped entirely.

Code path: [1](#0-0)  shows that when `assetInfo.blockchain === Chains.XRPL`, the code calls `xrpl.httpClient.getAccountInfo(args.destinationAddress, xrplConfig)` and only inside that same `try` reads `accountInfo.account_flags.requireDestinationTag` and `accountInfo.account_flags.depositAuth` to throw `XrplDestinationTagRequiredError`/`XrplDepositAuthEnabledError`. If `getAccountInfo` throws before those reads (i.e., the account does not yet exist on ledger, producing `XrplAccountNotFundedError`), the `catch` block explicitly suppresses the error whenever `isXrp && error instanceof xrpl.httpClient.XrplAccountNotFundedError`, letting `validateWithdrawal` resolve normally.

Attacker input: a real, currently-unfunded classic XRPL address as `destinationAddress`, `destinationMemo` omitted, `assetId` = native XRP (`xrp.omft.near`, so `isXrp === true`). No malicious behavior is required — this is simply a normal user-supplied address that happens to be unfunded at the time of the call but could later be activated with `requireDestinationTag` enabled (a very common XRPL exchange-deposit configuration).

Why existing guards don't help: `validateAddress`/`compareAddresses` only check address format and token-address collisions [2](#0-1) , not on-ledger flags. There is no re-validation of the destination tag requirement at any later point (e.g., at broadcast time when the account is actually funded), so the omission at `validateWithdrawal` time is never corrected. `XrplAccountNotFundedError` is defined in `packages/internal-utils/src/xrpl/xrplHttpClient/errors.ts` purely to represent "account not on ledger yet" and carries no information about the eventual flag state.

### Impact Explanation
An XRP withdrawal destined for an address that later becomes funded and requires a destination tag (common for exchange deposit addresses) will be executed with no tag attached because the check was skipped, not because the destination genuinely had no tag requirement. Since XRPL destination-tag requirements are commonly used by custodial exchanges to route deposits to specific sub-accounts, a payment landing without the required tag typically gets stuck / unable to be credited by the receiving custodian until manual support intervention — this matches the "High" impact category of "a withdrawal stuck until manual intervention."

### Likelihood Explanation
Preconditions: the destination must be a real XRPL classic address that is currently unfunded (so `getAccountInfo` throws not-funded) but will later require a destination tag once activated — a state fully within reach of any ordinary user who copies a deposit address before it happens to be indexed as funded, or an address on a chain with slow ledger propagation. The asset must be native XRP (`isXrp === true`); for non-XRP tokens issued on XRPL, the suppression does not apply and the error would propagate. This requires no privilege beyond calling the SDK's public withdrawal-validation flow with attacker/user-controlled `assetId`/`destinationAddress`/`destinationMemo`, and is repeatable on every call where the account is not yet funded at query time.

### Recommendation
Do not treat "account not funded" as equivalent to "no destination-tag/deposit-auth requirement." Either: (1) require a `destinationMemo` for any not-yet-funded XRPL destination when it cannot be verified, surfacing a clear error/warning to the caller instead of silently succeeding, or (2) re-validate the destination tag/deposit-auth requirement closer to broadcast time when the account may have since been funded, and fail closed rather than open when account state cannot be determined.

### Proof of Concept
```ts
// poa-bridge.test.ts (vitest) - mock only HTTP layer
import { xrpl } from "@src/internal-utils"; // or actual import path for xrpl.httpClient

it("does NOT validate destination tag requirement for unfunded XRP destination", async () => {
  vi.spyOn(xrpl.httpClient, "getAccountInfo").mockRejectedValueOnce(
    new xrpl.httpClient.XrplAccountNotFundedError("rSomeUnfundedClassicAddress")
  );

  const bridge = new PoaBridge(/* ...config with XRPL RPC url... */);

  // isXrp === true, destinationMemo omitted
  await expect(
    bridge.validateWithdrawal({
      assetId: "xrp.omft.near",
      destinationAddress: "rSomeUnfundedClassicAddress",
      destinationMemo: undefined,
      amount: 1000000n,
      // ...other required args
    })
  ).resolves.not.toThrow();

  // Assert equality broken: requireDestinationTag/depositAuthEnabled were never read
  // because getAccountInfo threw before those lines executed — no
  // XrplDestinationTagRequiredError / XrplDepositAuthEnabledError was possible to raise,
  // regardless of what the account's flags would be once funded.
});
```
This demonstrates that `validateWithdrawal` resolves without throwing despite no `destinationMemo`, proving the destination-tag/deposit-auth check at [3](#0-2)  is never executed for unfunded XRP destinations.
