### Title
Webhook `shop` (tenant identity) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop` (tenant identifier) is read directly from an unauthenticated header. Because a single app-wide `client_secret` (`Context.api_secret_key`) is used to sign webhooks for *every* shop that installs the app, a valid `(body, hmac)` pair captured from one tenant's webhook can be replayed against the same endpoint with a different `shop-domain` header, and `HmacValidator.validate` will still pass — binding attacker-controlled body content to an arbitrary victim shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from a header with no cryptographic binding to the HMAC at all: [2](#0-1) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)`, i.e. only the body, and then forwards `request.shop` (the unauthenticated header value) to the handler as the tenant identity for the event: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the signature purely from `to_signable_string` (the body) and `Context.api_secret_key`: [4](#0-3) 

Because `Context.api_secret_key` is one secret shared by the app across *all* merchant shops (it is not per-shop), a `(raw_body, hmac)` pair that is valid for shop A's webhook is also a cryptographically valid pair for the same content regardless of which `shop-domain` header accompanies it. The binding that should hold is:
`hmac_verified_bytes == identity_bytes_used_by_the_handler`
but here `hmac_verified_bytes = raw_body` while `identity_bytes_used_by_handler = header["shop-domain"]` — two disjoint pieces of data. This is the direct analog of the Merkle-tree bug: the code verifies one structural element (the body via HMAC) but trusts an adjacent, unverified element (the shop header) to determine the "leaf"/tenant identity that the verified payload gets attributed to.

### Impact Explanation
This breaks the tenant boundary (cross-tenant access), a Critical-impact category per this exercise's rules. An attacker who controls one shop with the app installed (an unprivileged action any merchant can perform) can capture a legitimate `(body, hmac)` pair from their own webhook deliveries, then replay it directly to the app's public webhook endpoint with a forged `shopify-shop-domain`/`x-shopify-shop-domain` header pointing at a victim shop. `Registry.process` will accept it as authentic (HMAC still matches the body) and dispatch it to the handler tagged with the victim's shop identity. Any host application logic that trusts `WebhookMetadata#shop` to select the tenant's data store, revoke access, process GDPR/customer-data requests, update orders, etc., will apply attacker-controlled webhook content under the victim's tenant.

### Likelihood Explanation
The webhook HTTP endpoint is by design internet-reachable and unauthenticated aside from the HMAC header, so no credentials, tokens, or privileged access are required — only that the attacker be a shop owner who has installed the app once (a normal, unprivileged interaction), which is exactly the "unprivileged internet user" threat model in scope.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically tie the shop header to the verified body (e.g., include it in the signable string, or independently confirm the shop against a value obtained through an authenticated channel such as a previously stored, verified session/access-token record) before using `request.shop` to route or key any tenant-scoped operation.

### Proof of Concept
1. Install the app on attacker-owned `attacker-shop.myshopify.com`; trigger any webhook event (e.g. `orders/create`) and capture the raw POST body `B` and its `x-shopify-hmac-sha256` header value `H` sent by Shopify (signed with the app's single `client_secret`).
2. Send a new POST request directly to the app's webhook endpoint with:
   - body = `B` (unchanged)
   - header `x-shopify-hmac-sha256` = `H` (unchanged)
   - header `x-shopify-shop-domain` = `victim-shop.myshopify.com` (attacker-supplied)
3. `ShopifyAPI::Webhooks::Request.new` builds a request object where `hmac` and `to_signable_string` (`B`) are unchanged, so `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) returns `true`.
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...))`, so the host app processes attacker-controlled body `B` as if it were an authentic event for `victim-shop.myshopify.com`.
