### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the identity of the shop a webhook belongs to from the `x-shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` values are all taken from unauthenticated headers and passed straight into the `WebhookMetadata` struct that handlers act on, without any of them being bound to the signature [2](#0-1) .

### Finding Description
`Registry.process` accepts a `Request`, validates it with `Utils::HmacValidator.validate(request)`, and — if that passes — calls the handler with a `WebhookMetadata` built from `request.shop`, `request.topic`, `request.parsed_body`, etc. [3](#0-2) . The HMAC validator computes `HMAC-SHA256(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` value from the query [4](#0-3) . For webhooks, `to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is read from the `hmac-sha256` header [5](#0-4) .

This breaks the intended identity binding: `signed(body) == valid` should imply `shop-domain header == the shop that actually produced this signed body`, but the gem only proves `signed(body) == valid`; the `shop-domain` header is never part of what's signed. Concretely, the equality the gem should enforce is `HMAC(secret, body || shop)` but it only checks `HMAC(secret, body)`.

Since the HMAC secret (`client_secret`) is identical for every shop that installs a given app, a legitimate installer of the app (an unprivileged actor with respect to *other* merchants using the same app) can capture one of their own genuinely-signed webhook deliveries (body + valid `hmac-sha256` header) and resubmit it to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a different, victim shop's domain. `Utils::HmacValidator.validate` will still return `true` because it only checks the body signature, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop [6](#0-5) . Any host application that uses `data.shop` to look up a session/tenant and apply the webhook body to that tenant's local records (the exact pattern documented in `docs/usage/webhooks.md`) would apply the attacker's shop data under the victim's identity — a cross-tenant data-integrity/impersonation issue.

### Impact Explanation
This matches the "Critical: cross-tenant access" category — an app-installing attacker can make the webhook-processing pipeline attribute their own webhook payload to a different, victim shop merely by relabeling one header, because the field the application trusts for tenant identity (`shop`) is disjoint from the field that is cryptographically verified (the body). This is a direct instance of the "field acted on but not covered by HMAC" analog called out in the scope.

### Likelihood Explanation
Requires only that the attacker be a legitimate app installer for some shop (unprivileged relative to other tenants of the same app) capable of capturing their own webhook deliveries and replaying an HTTP POST with a modified header — no access to `api_secret_key`, access tokens, or victim credentials is needed.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header value in the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the signed payload, e.g. change `to_signable_string` to something like `"#{shop}\n#{@raw_body}"` and update validation/documentation accordingly, or require host apps to independently verify that `data.shop` corresponds to a shop session, matching the tenant that installed the app before trusting the header value in `lib/shopify_api/webhooks/request.rb`.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com`; attacker controls that shop and can trigger any webhook topic (e.g. `orders/create`) they've subscribed to.
2. Shopify sends the app a legitimately signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` using the app's `client_secret`), and `x-shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker replays this exact request to the app's webhook endpoint, but rewrites the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` [7](#0-6) , which recomputes HMAC over `B` only and matches `H`, so validation passes.
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)` [6](#0-5) , causing the host app to process attacker-controlled data under the victim shop's tenant context.
