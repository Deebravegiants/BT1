This confirms the claim exactly as described. The code review shows:

1. `NewRouter` creates the `api` base group with only rate limiting and session-cookie middleware — no authentication requirement.
2. `loopRoutes(app, api)` is called directly on this unauthenticated group, registering `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, and `/plugins/:name/debug/pprof/symbol` with zero auth middleware.
3. In contrast, `metricRoutes(authv2)` (the standard Go pprof endpoints) is only invoked inside the `authv2` group, which requires `auth.Authenticate(..., AuthenticateByToken, AuthenticateBySession)`.
4. The plugin pprof handlers (`pluginPPROFHandler`, `pluginPPROFPOSTSymbolHandler`, `pluginMetricHandler`) perform no authentication or role checks — they only validate that the requested plugin name exists in the registry, then proxy the request to the internal LOOP-plugin process and return the raw response body.

This is a genuine, concrete, code-verifiable authentication-bypass/inconsistency issue reachable by any unauthenticated network client with no privilege prerequisites, matching the in-scope impact category of authentication bypass on the node API. It is not excluded by SECURITY.md (which excludes things like DDoS-only, non-sensitive info disclosure, missing headers, etc. — this is a real unauthenticated data-exposure/DoS-adjacent issue via a functioning code path, not a theoretical or configuration-only issue).

Audit Report

## Title
Unauthenticated pprof/metrics debug endpoints reachable via `loopRoutes`, bypassing the authentication constraints applied to the equivalent `/v2/debug/pprof` endpoints - (File: `core/web/router.go`)

## Summary
`NewRouter` mounts `loopRoutes` (which exposes `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, and `/plugins/:name/debug/pprof/symbol`) directly on the unauthenticated base `api` router group, while the equivalent built-in pprof endpoints exposed via `metricRoutes` are only reachable through the authenticated `authv2` group. This allows any unauthenticated network client to enumerate LOOP plugins and pull their runtime metrics and full pprof profiling data without credentials.

## Finding Description
`NewRouter` builds the base `api` group with only rate-limiting and session-cookie middleware attached (no authentication requirement) at [1](#0-0) , then calls `loopRoutes(app, api)` on this unauthenticated group alongside other route groups at [2](#0-1) . `loopRoutes` registers the discovery, plugin-metrics, plugin-pprof, and plugin-pprof-symbol endpoints with no auth middleware applied to the router group or the routes themselves: [3](#0-2) .

By contrast, the standard Go pprof endpoints registered by `metricRoutes` are only ever invoked from inside the `authv2` group, which requires `auth.Authenticate(..., AuthenticateByToken, AuthenticateBySession)`: [4](#0-3)  and [5](#0-4) . A repository-wide search confirms `metricRoutes` is only called this once, inside the authenticated group.

The plugin pprof/metrics handlers themselves perform no ownership, role, or authentication checks anywhere in their call chain — they only verify the plugin name exists in the registry, then proxy the request to the internal plugin process and stream back the raw response body: [6](#0-5)  (pprof handler), [7](#0-6)  (pprof symbol POST handler), and [8](#0-7)  (plugin metrics handler). The `pprofURLVals` helper also forwards attacker-controlled `debug`, `gc`, and `seconds` query parameters unauthenticated to the internal plugin: [9](#0-8) .

This demonstrates a genuine "alternate path" authorization bypass: the same resource class (pprof/profiling and metrics data) is protected via one route (`/v2/debug/pprof/*`) but unprotected via another (`/plugins/:name/debug/pprof/*`, `/plugins/:name/metrics`) because the auth middleware was attached at the route-group level for the "expected" path rather than uniformly enforced for the resource class itself.

## Impact Explanation
An unauthenticated client reachable to the node's HTTP listener can enumerate registered LOOP plugins via `/discovery`, retrieve their internal Prometheus metrics via `/plugins/:name/metrics`, and pull heap/goroutine/CPU-profile/trace data via `/plugins/:name/debug/pprof/*` — all without any session cookie, API token, or credentials. This exposes internal runtime state and memory-derived data of node capability plugins, and the attacker-controlled `seconds` parameter for CPU profiling can also be used to hold open proxied requests to internal plugin processes. This maps to an in-scope "node API authentication bypass" impact category, since a resource explicitly gated behind authentication on one path is exposed without authentication on another path serving the same underlying data.

## Likelihood Explanation
High for any node deployment where this HTTP listener is network-reachable (the same listener serving the authenticated `/v2` API and UI), since exploitation requires no credentials and the plugin name needed for the metrics/pprof routes is itself discoverable via the equally unauthenticated `/discovery` endpoint. This is trivially and repeatably triggerable by any unprivileged network client with a single unauthenticated HTTP request.

## Recommendation
Apply the same authentication middleware used for `authv2`/`metricRoutes` (`auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)`, plus appropriate role checks) to the routes registered in `loopRoutes`, or move `loopRoutes` registration inside the authenticated `authv2` group, so plugin metrics and pprof-forwarding endpoints are gated identically to the built-in `/v2/debug/pprof` endpoints.

## Proof of Concept
1. Start a chainlink node with at least one LOOP plugin registered.
2. Without any session cookie or API token: `curl http://<node>:<port>/discovery` — returns plugin names/ports unauthenticated (see `discoveryHandler` at `core/web/loop_registry.go:53-81`).
3. Using a discovered plugin name: `curl http://<node>:<port>/plugins/<name>/debug/pprof/heap?debug=1` — `pluginPPROFHandler` (`core/web/loop_registry.go:150-166`) forwards the request to the plugin's internal pprof endpoint and returns the profile data with no auth check performed at `core/web/router.go:234` or anywhere in the handler chain.
4. Compare with `curl http://<node>:<port>/v2/debug/pprof/heap` without credentials, which is rejected by the `auth.Authenticate` middleware attached at `core/web/router.go:245-248,445-446`, confirming the inconsistency.

func pprofURLVals(gc *gin.Context) (urlVals url.Values, timeout time.Duration) {
	urlVals = make(url.Values)

		urlVals.Set("debug", db)
	}
	if gc, ok := gc.GetQuery("gc"); ok {
		urlVals.Set("gc", gc)
	}
	timeout = PPROFOverheadSeconds * time.Second
	if sec, ok := gc.GetQuery("seconds"); ok {
		urlVals.Set("seconds", sec)
		if i, err := strconv.Atoi(sec); err == nil {
			timeout = time.Duration(i+PPROFOverheadSeconds) * time.Second
		}
	}
	return urlVals, timeout
}
