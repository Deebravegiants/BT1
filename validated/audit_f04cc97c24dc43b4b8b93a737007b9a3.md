## Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by validating an HMAC that is computed **only over the raw request body**, while the `shop` identifier that the host application uses to bind the webhook to a specific merchant/tenant is taken from an **unsigned HTTP header**. An attacker who can obtain one legitimately-signed webhook (trivial: install the app on their own development/test store) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header. The HMAC check still passes because it never covers the header, so the gem hands the host application a `WebhookMetadata` object asserting the attacker-chosen `shop`, together with attacker-controlled body content, as if it were verified as coming from that shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` derives both the authenticated payload and the tenant identity from the same HTTP message, but they are bound by two entirely disjoint fields: [1](#0-0) 

`hmac` is derived from the `hmac-sha256`/`x-shopify-hmac-sha256` header, and `shop` is derived independently from the `shop-domain`/`x-shopify-shop-domain` header. Critically, the value that actually gets signed/verified is only the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e. the raw body, and never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` checks only that HMAC, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The identity binding that should hold is: `shop == shop authenticated by the HMAC`. In reality, the HMAC only authenticates `raw_body == raw_body signed with api_secret_key`; it says nothing about which shop that body belongs to. The gem's own documentation reinforces the false assumption that the whole request — including `data.shop` — is verified: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook," and lists `shop` as one of the trustworthy fields on `data`. [5](#0-4) [6](#0-5) 

Because any external actor can install the target app on a shop they control and thereby obtain a validly-signed webhook body/HMAC pair for arbitrary topics (e.g., `orders/create`, `app/uninstalled`, `customers/data_request`), they can replay that exact `(raw_body, hmac)` pair against the app's public webhook endpoint while forging the `shop-domain` header to name a victim shop. `Utils::HmacValidator.validate` still returns `true` (the body/signature pair is genuinely valid), so `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim's domain and `body` fully attacker-controlled.

### Impact Explanation
Any application that follows this gem's documented contract — trusting `data.shop` from a webhook that "passed HMAC verification" to select which tenant's records to create/update/delete — can be made to apply attacker-supplied data under a victim shop's identity. This is a cross-tenant integrity/confidentiality break reachable by an unprivileged internet user (anyone who can self-install the target Shopify app) and satisfies the Critical "cross-tenant access" bar, since it lets an attacker inject fabricated events (including mandatory compliance topics like `customers/redact`, `shop/redact`) attributed to a shop they do not control.

### Likelihood Explanation
Likelihood is high: obtaining a legitimately signed webhook only requires installing the app once on an attacker-controlled development store (a normal, unprivileged action), and forging an HTTP header on a replayed POST request requires no cryptographic material and no access to `api_secret_key`. No credential, TLS interception, or social engineering is needed.

### Recommendation
Bind the header-derived identity fields into the signed material, or otherwise cross-check them, before trusting them downstream:
- Include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (or a canonical form containing them) so `HmacValidator.validate` authenticates the full tuple, not just the body; or
- At minimum, document clearly (and enforce in `Registry.process`) that `data.shop` is unauthenticated header data and must be cross-validated by the host app against a known/installed shop list before being used for tenant-scoped writes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, triggering a real webhook, e.g. `orders/create`, to the app's registered endpoint. Attacker captures the raw POST: `raw_body = B`, `x-shopify-hmac-sha256 = H` (valid HMAC of `B` under the app's `api_secret_key`), `x-shopify-shop-domain = attacker-shop.myshopify.com`.
2. Attacker resends the identical request to the same endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H` unchanged, but sets `x-shopify-shop-domain = victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` parses successfully; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only (per `to_signable_string`) and it matches `H`, so validation passes.
4. `Registry.process` proceeds to build `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` and invokes the registered handler, which (per the gem's documented usage pattern) processes/persists data under `victim-shop.myshopify.com` even though that shop never sent this webhook.
