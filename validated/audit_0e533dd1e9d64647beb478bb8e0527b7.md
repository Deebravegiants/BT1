**Analysis:**

`Code::from_arced_verified` is a private-crate-level constructor that simply wraps an already-provided `Arc<V>` into the `Verified` variant [1](#0-0) . Its only production callers are:

1. `AptosCodeStorageAdapter::into_verified_module_code_iter`, which re-wraps `Arc<Module>` values that were already drained out of the `UnsyncModuleStorage`'s own verified-module cache (i.e., code that already went through `visit_dependencies_and_verify` / `build_verified_module_with_linking_checks`) — it does not accept attacker-supplied `Arc<V>` from any external, unprivileged source [2](#0-1) .
2. `ModuleCode::from_verified`/`ModuleCode::from_arced_verified` calls inside `insert_verified_module`, which are only reachable from `visit_dependencies_and_verify` after the runtime environment has actually run `build_locally_verified_module` and `build_verified_module_with_linking_checks` on the bytecode [3](#0-2) .
3. Test-only helper code in `resource_tests.rs` and `combinatorial_tests`, which is not part of the production custody path at all [4](#0-3) .

There is no unprivileged transaction, entry function, API, or bytecode input in the reviewed repository that can directly call `Code::from_arced_verified` (or `ModuleCode::from_arced_verified`) with an out-of-band, attacker-fabricated `Arc<V>` that bypasses `runtime_environment.build_verified_module_with_linking_checks`. The function is an internal Rust-level API invariant (the caller is trusted to only pass in `Arc<V>` values that came from the verifier), not an externally reachable custody gate. Since no unprivileged entrypoint (transaction, package publish, view function, authenticator, API, or proof input) can construct or inject a foreign `Arc<V>` into this constructor, the described path does not cross a real custody boundary as required by the review's decision standard.
