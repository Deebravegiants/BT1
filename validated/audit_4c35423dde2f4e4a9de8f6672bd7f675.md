Based on my analysis, I found a valid analog matching the report's bug class.

### Title
Webhook HMAC only covers the request body, allowing the `shop-domain` identity header to be forged/replayed across tenants - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by checking the HMAC of the raw body, then trusts the `shop-domain` header — which is never part of the HMAC-signed material — as the identity used to dispatch business logic. This is exactly the class of bug in the report: "a field acted on but not covered by the HMAC." A party who has legitimately received one authentic webhook (e.g., for their own shop) can replay that exact signed body to the app's webhook endpoint while substituting the `shop-domain` header, and the gem will accept it as authentic and dispatch it as if it originated from an arbitrary victim shop.

### Finding Description
The equality the code is *supposed* to enforce is:
`shop asserted in the request == shop cryptographically bound by the HMAC`

In `HmacValidator.validate`, the signature is computed only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, and `webhook_id` are pulled straight from HTTP headers, which are entirely outside the HMAC: [3](#0-2) 

`Registry.process` then validates only the HMAC (i.e., only proves the body wasn't tampered with) and immediately trusts `request.shop` as the tenant identity handed to the app's handler: [4](#0-3) 

Because the `api_secret_key` used to compute the HMAC is a single app-wide secret (not per-shop), and the signature check never binds the signature to the `shop-domain` header, the gem's own `process` method cannot distinguish "body X really came from shop A" from "body X was replayed by anyone who once legitimately saw it, now claiming to be shop B." The header-vs-signed-bytes gap is inside the gem's own code path (`Request#initialize`/`shop` and `Registry.process`), not a misuse of a documented external API by the host app.

### Impact Explanation
This breaks the tenant isolation boundary the gem is expected to provide via `Registry.process`/`WebhookMetadata`: an unprivileged actor with access to only one legitimately delivered webhook body (e.g., their own installed shop's `orders/create` or `app/uninstalled` payload) can cause the app to execute the handler logic as if it were issued by a different, victim shop by simply changing the `x-shopify-shop-domain` header on a direct POST to the app's webhook endpoint. Any handler that keys persistence, cache invalidation, uninstall/redaction processing, or entitlement changes off `WebhookMetadata#shop` will act on the wrong tenant's data — a cross-tenant access condition (Critical per the scope's impact list).

### Likelihood Explanation
Likelihood is high for any app exposing a webhook endpoint built on this gem: the attacker needs no secrets, only (a) the ability to POST directly to the app's public webhook URL, and (b) one authentic prior webhook body they were legitimately shown (trivial for `MANDATORY_TOPICS` such as `customers/data_request`/`shop/redact`, which every installed merchant receives, or for any topic on their own shop). No `api_secret_key`, access token, or privileged account is required.

### Recommendation
Include the asserted `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind the identity header to the signature so `Registry.process` can reject a body/header combination that wasn't jointly signed by Shopify. At minimum, document and/or enforce that the `shop` passed to handlers must be independently confirmed (e.g., against a known/registered shop for that specific webhook subscription) rather than trusted purely from the header.

### Proof of Concept
1. Install the app on Shop A; the app's webhook endpoint receives a legitimate `customers/data_request` webhook with a valid `x-shopify-hmac-sha256` header computed over the JSON body using the app's `api_secret_key`, and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (who operates Shop A, or otherwise obtains this one webhook delivery) captures the raw body and its valid HMAC header.
3. Attacker crafts a new HTTP POST directly to the app's public webhook endpoint, reusing the identical raw body and `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (victim shop).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC — see [5](#0-4) .
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"shop-b.myshopify.com"`, causing the app to process/execute redaction, uninstall, or business logic attributed to Shop B — a cross-tenant action the attacker does not control or own — see [6](#0-5) .

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
