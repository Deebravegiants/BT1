### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant identity (`shop`) that gets handed to the app's webhook handler purely from the `X-Shopify-Shop-Domain` header, but the HMAC signature that `Registry.process` verifies is computed only over the raw request body. The `shop` field is never bound into the signed material, so it can be swapped without invalidating the signature.

### Finding Description
`Registry.process` verifies the request's authenticity with: [1](#0-0) 

The HMAC check calls into `Utils::HmacValidator.validate`, which recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the value returned by `request.hmac`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw HTTP body — it never includes `shop`, `topic`, `api_version`, or `webhook_id`: [3](#0-2)  

Meanwhile, `shop` is read straight from the `shopify-shop-domain` (or `x-shopify-shop-domain`) header with no cross-check against the signed body or any allow-list of installed shops: [4](#0-3) 

`Registry.process` then forwards that unauthenticated `shop` value directly into `WebhookMetadata`, which is the only identity information the host application's handler receives to decide which merchant record to act on: [1](#0-0) 

The identity binding that should hold is:
```
hmac_signed_bytes == bytes_that_determine_which_shop_is_acted_on
```
Here, `hmac_signed_bytes = raw_body` while `bytes_that_determine_which_shop_is_acted_on = header["shop-domain"]`. These are disjoint, so the equality never actually holds — the header can be freely altered independent of the signed payload.

Because every shop that installs a given app shares the same `api_secret_key`, an attacker who controls one install of the app (e.g., their own free/dev store) can legitimately trigger a webhook from Shopify to obtain a body + valid HMAC pair signed with that shared secret, then replay the same body/HMAC to the app's webhook endpoint while substituting an arbitrary `shop-domain` header value for a different merchant. `Utils::HmacValidator.validate` will still return `true` because the signature never covered the shop field, and `Registry.process` will invoke the handler believing the event belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce: an unprivileged user with any legitimate install of the app can produce webhook deliveries that the library accepts as authentic for a shop they do not control, unlocking cross-tenant access/data corruption in any host application that trusts `WebhookMetadata#shop` from a verified `Registry.process` call (which is the documented usage pattern for this gem).

### Likelihood Explanation
Exploitation only requires the ability to install the target app on any store (including a free development store) to obtain one legitimately-signed webhook body/HMAC pair, and the ability to send an HTTP POST with a forged `shop-domain` header to the app's public webhook endpoint. No access to the app's `client_secret`, an access token, or any other privileged credential is required.

### Recommendation
Include the identity-carrying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable material, or independently re-derive/validate `request.shop` against a value that is itself authenticated (e.g., compare it to a per-shop secret, or require the host app to validate `shop` against its own installed-shops table before trusting `WebhookMetadata`), and document this requirement prominently since `Registry.process`'s success return currently implies full authenticity of every field in `WebhookMetadata`.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled Store A; capture a legitimate webhook delivery (raw body `B` + `X-Shopify-Hmac-Sha256` header `H`, valid for the app's shared `api_secret_key`).
2. Send a POST to the app's webhook endpoint with the same body `B` and header `H`, but replace `X-Shopify-Shop-Domain` with victim Store B's domain.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), `Utils::HmacValidator.validate` returns `true` because `to_signable_string` only checks `B` against `H`, and `Registry.process` invokes the handler with `WebhookMetadata(shop: "storeB.myshopify.com", ...)`, causing the host app to act on Store B's data using an event that Shopify never sent for Store B.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
