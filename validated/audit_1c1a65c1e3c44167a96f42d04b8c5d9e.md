### Title
Untrusted body byte cast directly to a Solidity `enum` in `IApp.onAccept` implementations causes a low-level `Panic` revert instead of a graceful reject, permanently bricking message delivery - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
CVE-2018-17204 is a "use enum/command value before its validity has been established" bug class: OvS's OF1.5 decoder used a group-mod `type`/`command` field to select decoding logic before the whole message had been range-checked, hitting `OVS_NOT_REACHED` (an assertion failure) on crafted input. The analogous pattern in this codebase is any place that casts an attacker-controlled byte straight into a Solidity `enum` via `EnumType(uint8(...))`. Solidity's explicit enum conversion performs a bounds check at the EVM level and, for a value outside the enum's declared range, throws a **`Panic(0x21)`** ("invalid enum value") — a low-level, unrecoverable revert, not a normal `require`/custom-error rejection. Several `IApp.onAccept` implementations that receive permissionlessly-relayed, remotely-crafted request bodies perform exactly this unchecked cast before any length/range validation.

### Finding Description
`EvmHost.dispatchIncoming` delivers every accepted `PostRequest` to the destination app via a raw low-level `call` and treats any failure (including a `Panic`) identically to a normal application-level rejection: it deletes the request receipt and returns without reverting the batch, explicitly to keep the message "retryable" [1](#0-0) .

Multiple `IApp` implementations decode the first body byte directly into an `enum` before any length check on the body or validation of the discriminant range:
- `ExtrinsicIntents.onAccept`: `RequestKind kind = RequestKind(uint8(incoming.request.body[0]));` [2](#0-1) 
- `IntentGatewayV2.onAccept` (Tron variant): same pattern [3](#0-2) 
- `SimplexPaymaster.onAccept`: same pattern [4](#0-3) 

The request `body` originates entirely from whatever the source-chain sender encoded; a `PostRequest`'s `to` field only needs to match the destination app's address for `dispatchIncoming` to reach it — there is no upfront validation of `body.length` or of the discriminant range before the explicit enum cast. If `body` is empty, `body[0]` on a `bytes calldata`/`memory` performs an out-of-bounds array access — itself a `Panic(0x32)`. If `body[0]` holds a value greater than the highest declared enum member, the explicit conversion reverts with `Panic(0x21)`. Both are Solidity's built-in equivalent of `OVS_NOT_REACHED`: the low-level EVM aborts execution via `INVALID`/panic rather than a normal error path, exactly mirroring the CVE's core defect of using a not-yet-validated type/command discriminant before checking it is in range.

Because `EvmHost.dispatchIncoming` deletes the receipt on *any* failed low-level call and treats the request as retryable [5](#0-4) , and because the request's `body` bytes are fixed inputs to the immutable, MMR-committed request commitment, a crafted request with an out-of-range or empty body can never be redelivered successfully by anyone — it will panic every single time it is retried, since the panic is a deterministic function of the (unchangeable) request bytes.

### Impact Explanation
This produces a permanent denial-of-service on a specific cross-chain message: the request can never be delivered to its destination app, regardless of how many times a relayer retries `handlePostRequests`, because Solidity's enum-cast bounds check will re-panic identically every time on the same immutable request body. Per the report's Validate criteria, this constitutes "a route unable to deliver messages." If the crafted message also happens to represent a legitimate user action (e.g., an escrow redemption `RequestKind.RedeemEscrow` malformed only in an unrelated way, or a governance action queued with a corrupted discriminant), any escrowed funds or state transition contingent on that specific request's delivery become permanently unreachable, since the request can never be re-encoded (its commitment is fixed by the MMR proof already accepted on the source chain).

This is a Medium-severity, permanent-message-undeliverable condition matching the CVE's "reachable via crafted decode-time input, hits an unrecoverable low-level failure instead of a controlled rejection" bug class; it does not by itself corrupt consensus or state and requires the crafted request to already be committed/proven, which is why it is bounded to Medium rather than High.

### Likelihood Explanation
Any account able to dispatch a `PostRequest` on a source chain toward one of these gateway contracts as `to` (an ordinary, unprivileged cross-chain dispatch, not requiring any special role) can set `body[0]` to any value including one exceeding the enum's declared range, or dispatch an empty body. Delivery is fully permissionless (`handlePostRequests` may be called by anyone once the MMR proof is valid), so triggering the panic requires no privileged access — only a normal user-level cross-chain message dispatch from any connected chain.

### Recommendation
Before casting the first body byte to `RequestKind` (or any similar discriminant enum), explicitly validate: (1) `body.length > 0`, and (2) the raw `uint8` value is `<= uint8(type(RequestKind).max)`, returning a normal custom error (e.g., `revert InvalidRequestKind(uint8)`) instead of relying on Solidity's implicit enum-cast bounds check. Apply this to `ExtrinsicIntents.onAccept`, `IntentGatewayV2.onAccept` (Tron), and `SimplexPaymaster.onAccept`, mirroring the explicit bounds check already used in `ConsensusRouter.sol`'s `ProofType` decode [6](#0-5) , which correctly checks the range before constructing the enum and thus avoids the panic path entirely. Consider also having `EvmHost.dispatchIncoming`/the relevant `IApp` catch low-level panics distinctly (or make truly malformed messages catchable/timeoutable) so a permanently-unparseable request does not remain stuck as "pending" forever.

### Proof of Concept
1. On a source chain, dispatch a `PostRequest` with `to = <ExtrinsicIntents address>` and `body = ""` (empty) or `body = hex"ff" ++ arbitrary` where `0xff` exceeds `RequestKind`'s highest discriminant.
2. Once Hyperbridge finalizes/proves the request, any relayer calls `HandlerV2.handlePostRequests` with a valid MMR membership proof; this succeeds and calls `host.dispatchIncoming(request, relayer)`.
3. `EvmHost.dispatchIncoming` low-level calls `ExtrinsicIntents.onAccept(...)`; execution reaches `RequestKind kind = RequestKind(uint8(incoming.request.body[0]));` and panics (`Panic(0x21)` for out-of-range, `Panic(0x32)` for empty body).
4. The low-level `call` returns `success = false`; `dispatchIncoming` deletes the request receipt and returns without reverting the batch [7](#0-6) .
5. Any later attempt by any relayer to re-deliver the same (immutable) request repeats steps 3–4 identically — the message can never be successfully delivered.

        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
