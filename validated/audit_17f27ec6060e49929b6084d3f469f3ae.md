The premise mischaracterizes how `update_transaction_on_abort` and the underlying `MVHashMap` actually separate concerns between the flat map (`data()`) and the group map (`group_data()`).

**Why this isn't a real bug:**

1. **The FA store balance (the actual custody-relevant value) is a *tagged* entry inside the resource group, not a "flat-key" entry.** When a transaction writes to a resource-group-held FA store, that write flows through `resource_group_write_set()` and becomes part of `group_ops`, which is written to `versioned_cache.group_data()` (not `data()`). Non-group resource writes go through `resource_write_set()` into `data()`. These are disjoint categories, not two "map representations of the same underlying resource." [1](#0-0) 

2. **On abort, `update_transaction_on_abort` marks estimates in exactly the right places for each category**: non-group resource keys via `versioned_cache.data().mark_estimate` from `modified_resource_keys` (which explicitly excludes group keys), and the tagged group entries via `versioned_cache.group_data().mark_estimate` from `for_each_resource_group_key_and_tags`. This is precisely the path that covers a resource-group-held FA store balance. [2](#0-1) 

3. **The one thing that is *not* marked as estimate is the group's metadata entry in `data()`** (the `group_metadata_op`, e.g. the group's own `StateValueMetadata`/existence marker) — and this is an explicit, documented design decision, not an oversight: the code comment states that after a transaction changes group metadata, a write to that path is guaranteed to trigger suffix re-validation, so a stale metadata read will always be caught by validation rather than relying on the estimate/wait mechanism. [3](#0-2) [4](#0-3) 

4. **Delayed field ids (the mechanism used for FA store balances/aggregators) are tracked and marked estimate independently**, in `versioned_cache.delayed_fields()`, and are validated separately at commit time rather than relying on the data()/group_data() estimate marking at all — this is called out directly in `validate()`. [5](#0-4) [6](#0-5) 

So the scenario described — a dependent transaction re-reading a "stale, non-estimated" FA store balance due to inconsistent estimate marking between `data()` and `group_data()` — doesn't correspond to an actual code path: the FA store's tagged value in the group is correctly marked as an estimate via `group_data().mark_estimate`, and the only entry that skips marking (`data()` group metadata) is guaranteed to trigger suffix re-validation on the next write, and delayed-field correctness is enforced by a separate commit-time validation mechanism. No unprivileged-input path exists here that changes custody of APT, fungible assets, or objects.

pub(crate) fn update_transaction_on_abort<T, E>(
    txn_idx: TxnIndex,
    last_input_output: &TxnLastInputOutput<T, E::Output>,
    versioned_cache: &MVHashMap<T::Key, T::Tag, ValueWithLayout<T::Value>, DelayedFieldID>,
) where
    T: Transaction,
    E: ExecutorTask<Txn = T>,
{
    counters::SPECULATIVE_ABORT_COUNT.inc();

    // Any logs from the aborted execution should be cleared and not reported.
    clear_speculative_txn_logs(txn_idx as usize);

    // Not valid and successfully aborted, mark the latest write/delta sets as estimates.
    if let Some(keys) = last_input_output.modified_resource_keys(txn_idx) {
        for k in keys {
            versioned_cache.data().mark_estimate(&k, txn_idx);
        }
    }

    // Group metadata lives in same versioned cache as data / resources.
    // We are not marking metadata change as estimate, but after a transaction execution
    // changes metadata, suffix validation is guaranteed to be triggered. Estimation affecting
    // execution behavior is left to size, which uses a heuristic approach.
    last_input_output
        .for_each_resource_group_key_and_tags(txn_idx, |key, tags| {
            versioned_cache
                .group_data()
                .mark_estimate(key, txn_idx, tags);
            Ok(())
        })
        .expect("Passed closure always returns Ok");

    if let Some(keys) = last_input_output.delayed_field_keys(txn_idx) {
        for k in keys {
            versioned_cache.delayed_fields().mark_estimate(&k, txn_idx);
        }
    }
}
