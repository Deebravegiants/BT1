Audit Report

## Title
Bridge `OutgoingToken` credential is stored in plaintext and exposed to any authenticated `view`-role user via REST and GraphQL bridge read endpoints - ([File: core/bridges/bridge_type.go])

## Summary
Chainlink's bridge subsystem generates an `OutgoingToken` used by the node to authenticate to external adapter services, but unlike `IncomingToken` (hashed at rest, only returned once at creation), the `OutgoingToken` is stored unhashed in the `bridge_types.outgoing_token` column and is unconditionally returned by both REST (`GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`) and GraphQL (`bridges`, `bridge`) read endpoints. These endpoints require only the lowest `view` role, meaning any authenticated node-UI user can read the plaintext credential for every configured bridge.

## Finding Description
`NewBridgeType` generates `incomingToken`, `outgoingToken`, and `salt`, hashes only the incoming token (`incomingTokenHash(incomingToken, salt)`), and stores `outgoingToken` as plaintext in `BridgeType.OutgoingToken` (`db:"outgoing_token"`, a plain `text` column) [8](#0-7) [9](#0-8) .

This plaintext value is unconditionally serialized in `BridgeResource.OutgoingToken` (json tag `"outgoingToken"`, no `omitempty`), in contrast to `IncomingToken`, which is tagged `omitempty` and only populated at creation time [6](#0-5) . The REST controller's `Index` and `Show` handlers build this presenter directly from stored `BridgeType` records for every list/show request [10](#0-9) . The router wires `GET /v2/bridge_types` and `GET /v2/bridge_types/:BridgeName` with only base session/token authentication and no role-restricting middleware, while the mutating routes (`POST`, `PATCH`, `DELETE`) are wrapped in `auth.RequiresEditRole` [2](#0-1) . This is confirmed by the RBAC route table used in `auth_test.go`, which explicitly marks both GET routes as `viewOnlyAllowed: true` [1](#0-0) , and by the `TestRBAC_Routemap_ViewOnly` test asserting non-`Unauthorized`/`Forbidden` responses for such routes under a `view`-role user [11](#0-10) .

The same pattern exists in GraphQL: the `Bridge`/`Bridges` resolvers call only `authenticateUser`, which merely checks for a valid session and grants "inherently... 'view' access" without any role check [3](#0-2) [4](#0-3) , unlike other mutation-oriented resolvers that use `authenticateUserCanEdit`/`authenticateUserCanRun`/`authenticateUserIsAdmin`. The `bridge.graphql` schema exposes `outgoingToken: String!` on the `Bridge` type with no redaction [7](#0-6) .

## Impact Explanation
The `OutgoingToken` is a live authentication credential used by the node to call external bridge adapters. Its unconditional exposure to `view`-role users — the lowest privilege tier, which by design cannot create/edit/delete bridges, jobs, or keys — allows those low-privilege users to extract a credential usable to impersonate the node when calling the configured external adapter, exceeding their intended access scope. This maps to the "key/secret exfiltration" impact class for Chainlink node API authorization, since it's a broken authorization boundary between `view` and `admin`/`edit` roles rather than a network-layer or host-level issue.

## Likelihood Explanation
Exploitation requires only a valid low-privilege (`view`-role) session on the node's Operator UI/API — no privilege escalation, misconfiguration, or special bypass is needed. A single `GET /v2/bridge_types` or `GET /v2/bridge_types/:BridgeName` request (or the GraphQL `bridges`/`bridge` query) as a `view` user returns the plaintext token, repeatable for every configured bridge, on default configuration and default RBAC wiring as confirmed by the existing test suite.

## Recommendation
- Redact `OutgoingToken` from list/show responses to `view`-role sessions; return it only to `edit`/`admin` roles, or only once at creation time analogous to `IncomingToken`.
- Consider hashing/encrypting `OutgoingToken` at rest and having the runner fetch/decrypt it via a secure internal path only when executing bridge calls, rather than storing and serving it as plaintext.
- Add `omitempty`/role-gating to the `OutgoingToken` field in `BridgeResource` and the GraphQL `Bridge` type, mirroring `IncomingToken`'s handling.

## Proof of Concept
1. As an admin, create a bridge via `POST /v2/bridge_types`; note the returned `outgoingToken`.
2. Create a second user with role `view` (`sessions.UserRoleView`).
3. Authenticate as the `view` user and call `GET /v2/bridge_types/:BridgeName` (or execute the GraphQL query `{ bridge(id: "<name>") { ... on Bridge { outgoingToken } } }`).
4. Observe the response contains the identical plaintext `outgoingToken`, despite the `view` role having no create/edit/delete rights on bridges — reproducible directly against `core/web/auth/auth_test.go`'s `TestRBAC_Routemap_ViewOnly` test harness by adding an assertion on the response body's `outgoingToken` field for the `/v2/bridge_types/MOCK` route case.
