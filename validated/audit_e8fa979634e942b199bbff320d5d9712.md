### Title
Webhook HMAC only covers the raw body — `shop`/`topic`/`webhook_id` headers are unauthenticated, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its `to_signable_string` from the raw request body only, while the `shop`, `topic`, and `webhook_id` values used for tenant attribution and handler dispatch are read directly from HTTP headers that are never included in the HMAC computation. Any actor who can obtain one valid `(body, hmac)` pair delivered to their own shop can replay it against the shared webhook endpoint with a forged `X-Shopify-Shop-Domain` header, and `ShopifyAPI::Webhooks::Registry.process` will accept it as authentic and dispatch it as if it originated from an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are pulled straight from headers that are entirely outside the signed data: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC over exactly that signable string (the body) and nothing else: [3](#0-2) 

`Registry.process` trusts `request.shop` for tenant attribution once the body HMAC passes, and dispatches the handler with that unauthenticated shop value: [4](#0-3) 

The identity binding that should hold is:
`shop used for tenant attribution == shop that produced the HMAC-signed bytes`

But the actual binding enforced by the code is only:
`bytes verified by HMAC == raw_body`

Because `shop` (and `topic`/`webhook_id`) are never part of the signed payload, the equality above does not hold. Any unprivileged actor who installs the app on their own shop (Shop A) is legitimately delivered a valid `(raw_body, hmac)` pair by Shopify for their own webhook. That same `(raw_body, hmac)` pair remains cryptographically valid forever (no timestamp/nonce binds it to a single delivery in this gem's verification path) and is independent of the `shop-domain` header. The attacker can replay that exact body+hmac to the app's shared webhook endpoint while substituting `X-Shopify-Shop-Domain: shop-b.myshopify.com` (or any other tenant's domain). `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` forwards `shop: request.shop` (now "shop-b.myshopify.com") to the host application's handler — cross-tenant data injection/attribution with no credential, secret, or victim interaction required.

### Impact Explanation
This is a cross-tenant access / data-integrity break as defined by the Critical impact criteria: an attacker who is merely another tenant of the same app (an ordinary, unprivileged merchant) can cause webhook payloads to be processed and attributed under an arbitrary victim shop's identity, without knowing `api_secret_key`, without any access token, and without compromising the victim. Depending on how the host application's webhook handlers use `WebhookMetadata#shop` (e.g., to look up/store per-shop records, trigger per-shop side effects, or make credentialed API calls scoped "as" that shop), this can lead to cross-tenant data corruption or unauthorized actions performed in another merchant's context.

### Likelihood Explanation
Likelihood is high for any app using this gem's `Webhooks::Registry`/`Webhooks::Request` as documented: the attacker only needs to be a legitimate (even free/trial) merchant of the app to legitimately receive one valid signed webhook, then replay it with a modified shop header to the same public webhook endpoint. No secret material, token, or social engineering is required — only observation of one's own legitimately-delivered webhook traffic.

### Recommendation
Bind the tenant-identifying fields into the signed material, or otherwise cryptographically verify that the declared `shop` matches the shop the webhook was actually issued for:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-signable string (mirroring the `AuthQuery` pattern where every field asserted by the caller is part of `to_signable_string`), or
- Require callers to pass the expected shop (from their own authenticated session/registration state) and assert equality against the header value before dispatching the handler, or
- Bind each webhook delivery to a single-use identifier verified against Shopify (e.g., cross-check `webhook_id`/timestamp freshness against previously seen values) so that a captured `(body, hmac)` cannot be replayed under a different tenant identity.

### Proof of Concept
1. Attacker registers the target app on their own store `shop-a.myshopify.com` and receives a legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`), per `Request#to_signable_string`/`hmac`.
2. Attacker replays the exact same `B`/`H` pair to the app's shared webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com` (and optionally a different `X-Shopify-Topic`/`Webhook-Id` if desired).
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and finds it equal to `H` — validation passes, since the shop header was never part of the signed input.
4. `Registry.process` then invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "shop-victim.myshopify.com", body: parsed(B), ...)`, causing the app to process/attribute webhook data as though it came from `shop-victim.myshopify.com`, despite the payload actually being replayed from the attacker's own shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
