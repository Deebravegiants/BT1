### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop` value that is handed to the app's `WebhookHandler` is read straight from the `x-shopify-shop-domain` HTTP header, which is never included in the signed payload [2](#0-1) . This breaks the identity binding `hmac == HMAC(body_and_shop)` down to `hmac == HMAC(body)`, so the "shop" the gem reports to the app is an unauthenticated field, exactly analogous to the audited Witch.sol bug where a value used by the system (`to`/`auctioneer`) was not part of any binding/validation check.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body` [3](#0-2) [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` fields are all read from HTTP headers via `shopify_header`, none of which factor into the signed string [5](#0-4) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identifier passed to the app's handler:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

Because a single app has one `api_secret_key` shared across **every** merchant/shop that installs it, any unprivileged user who installs the app on their own store can:
1. Trigger a real webhook event on their own store (e.g. `orders/create`), receiving a request with a valid `x-shopify-hmac-sha256` computed over the body using the app's shared secret.
2. Capture that `(raw_body, hmac)` pair.
3. Replay the same body/HMAC to the app's webhook endpoint, but substitute `x-shopify-shop-domain` (and/or `x-shopify-topic`) with a victim shop's domain.

`Utils::HmacValidator.validate` still returns `true` because the HMAC only ever covered the body, and `Registry.process` forwards the attacker-chosen `shop` value straight to the app's `WebhookHandler` as if it were authenticated. The library's own documentation confirms this trust: `Registry.process`'s doc comment states it "will verify the request did indeed come from Shopify" [6](#0-5) , and the documented `data.shop` field is presented to consuming apps as trustworthy shop metadata [7](#0-6) , with no caveat that `shop` is unauthenticated and must be independently re-validated against a known/looked-up session before use.

### Impact Explanation
This is a cross-tenant identity-confusion vector: an app that (as documented) keys its data model or session lookups off `data.shop` from the webhook handler can be made to attribute/apply another merchant's webhook processing under an attacker-controlled shop domain, or conversely inject fabricated events falsely labeled as coming from a victim shop. Depending on what the host app does with `data.shop` (e.g., look up the shop's access token/session, write to shop-scoped state, trigger GDPR data actions since `MANDATORY_TOPICS` includes `shop/redact`, `customers/redact`, `customers/data_request` — see `lib/shopify_api/webhooks/registry.rb`), this can cause cross-tenant data corruption or spoofed mandatory-compliance actions attributed to the wrong shop. This falls under "cross-tenant access" impact.

### Likelihood Explanation
Requires only that an attacker can install the target app on a store they control (a normal, unprivileged OAuth install available to any merchant/developer) and can send arbitrary HTTP requests to the app's publicly reachable webhook endpoint — no access token, `api_secret_key`, or privileged account is needed. The HMAC secret used to sign the attacker's own genuine webhook is the same secret shared by the app across all its installations, so the captured `(body, hmac)` pair remains valid regardless of which `shop-domain` header is sent.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material that is validated, or otherwise cryptographically bind the header values to the request before trusting them: e.g., extend `VerifiableQuery`/`to_signable_string` (or add a parallel check) so `Registry.process` verifies the `shop-domain` header against the shop that is expected/registered for the corresponding topic/session, rather than passing the raw header value straight through to `WebhookHandler`. At minimum, document explicitly that `WebhookMetadata#shop` is not covered by the HMAC and must be cross-checked by the consuming app against a known, previously-authenticated shop/session before being trusted for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (normal, unprivileged install flow) and registers for a webhook topic (e.g., `orders/create`).
2. Attacker triggers the webhook (e.g., creates an order in their own store), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends — this HMAC is computed with the app's `api_secret_key`, over the body only.
3. Attacker resends the identical body and HMAC header directly to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only and matches — validation succeeds [8](#0-7) .
5. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is invoked with `shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop [9](#0-8) .
