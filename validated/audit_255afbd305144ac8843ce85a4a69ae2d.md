### Title
Permanent Denial of Service of a launched token's bonding curve via `assetReserve` underflow in `canGraduate` — ([File: packages/contracts/src/Bonding.sol])

### Summary
`canGraduate` derives `realLtRaised` by subtracting the immutable launch-time virtual LT reserve from the pair's **stored** `assetReserve`. This subtraction is unchecked and reverts with a Solidity Panic if `assetReserve` is ever lower than the launch-time virtual reserve. Because `Bonding.sell` calls `canGraduate` unconditionally before every sell, and `Bonding.buy`'s `_executeBuy` calls it at the end of every buy, any state that drives `assetReserve` below the virtual floor permanently DoSes **all** future buys and sells on that token's curve — an analog of the "crafted statements causing DoS" pattern from CVE-2024-57637, mapped onto alt.fun's own bonding-curve accounting instead of SQL.

### Finding Description
- `_launchTimeVirtualLtReserve` recovers the launch-time virtual LT reserve as `Pair.k() / Token.TOTAL_SUPPLY()`, a fixed value baked in at `Pair.mint` [3](#0-2) .
- `canGraduate` reads the pair's live stored `assetReserve` and does `assetReserve - _launchTimeVirtualLtReserve(...)` with no bounds check [4](#0-3) .
- `Pair.swap`'s K-invariant check contains a `+1` rounding slack on both sides: `(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` [5](#0-4) . This slack, combined with `Router._computeSell`'s floor division (`assetOut = reserveAsset - (k / newReserveToken)`) [6](#0-5) , means each buy/sell round trip can leak up to 1 wei of the pair's effective `k` in the seller's favor, monotonically shrinking the pair's realized K relative to the theoretical launch K. Repeated buy→sell round trips (via `Zap.buy`/`Zap.sell`, fully reachable by an unprivileged trader) drive `assetReserve` down by small increments each cycle.
- Once enough round trips have executed, `assetReserve` can fall to exactly the launch-time virtual reserve or below it (e.g., a trader who bought with the mandatory seed and repeatedly buys/sells dust amounts). At that point, *any* subsequent call to `canGraduate` — which happens on every single `Bonding.sell` (explicit pre-check) and at the tail of every `Bonding.buy`/`_executeBuy` — underflows and reverts with an undecodable Panic, since `assetReserve - virtualLtReserve` goes negative in `uint256` arithmetic.
- Because there is no `try/catch` around this computation and no guard clamping the subtraction, this failure is unconditional and unrecoverable from within the curve: every future `Zap.buy` and `Zap.sell` on that token will revert until (if ever) an outside actor pushes `assetReserve` back above the virtual floor — which cannot happen from inside the curve because both buy and sell revert. The curve becomes permanently frozen, precisely the DoS class described by the external report (crafted operations that make normal statements — here, ordinary buy/sell "SQL-like" curve operations — hang/crash the engine).
- Test comments in the repo (`test/Zap.t.sol` around `_stageDonationAttack`) reference a related, already-patched underflow in `previewLtUntilGraduation`'s supply leg from a token-donation attack, showing this exact underflow class (stored reserves minus a derived virtual constant) has previously bitten this codebase and that not all instances were closed off — `canGraduate`'s own subtraction at line 692 remains unguarded.

### Impact Explanation
If reachable, this permanently freezes trading (both buy and sell) for the affected token's bonding curve: traders cannot exit their position via `Zap.sell` (permanent freezing of trader funds sitting in the LT/curve), the creator cannot see the token graduate (frozen creator upside), and the only path out — `Bonding.buy`'s ultimate `canGraduate` call — is equally bricked. This meets the "permanent freezing of trader … funds" bar under Medium/High severity.

### Likelihood Explanation
The requirement is a series of unprivileged buy/sell round trips via `Zap.buy`/`Zap.sell` sized to exploit the `+1` rounding slack in `Pair.swap` and the floor division in `Router._computeSell`/`_computeBuy`. Whether the accumulated rounding loss per round trip is consistently nonzero (not just occasionally) and how many iterations are required to close the gap between `assetReserve` and the virtual floor could not be fully confirmed analytically in this pass — it depends on the exact floor/ceil interactions across `_computeBuy`'s cap branch and `_computeSell`, and on whether `Zap`'s own fee-skimming and LT-mint floor rounding interfreres with the exact wei-level state needed. I was not able to fully simulate the numeric trajectory of `assetReserve` across many round trips to confirm the underflow is reachable in practice without running the test suite/fuzzer.

### Recommendation
Guard the subtraction in `canGraduate` (and any other call site deriving `realLtRaised` the same way) with a saturating computation, e.g. `assetReserve > virtualLtReserve ? assetReserve - virtualLtReserve : 0`, mirroring the saturating-subtract pattern already used elsewhere in the codebase (e.g., `_ltSwapInventory` in `Bonding.sol`) [7](#0-6) . Add an invariant test asserting `assetReserve >= launchTimeVirtualLtReserve` holds after arbitrarily long buy/sell round-trip sequences, and re-run `test/GraduationInvariants.t.sol` after the fix.

### Proof of Concept
Not fully constructable without executing the Foundry test suite to confirm the exact wei-level trajectory of `assetReserve` under repeated `Zap.buy`/`Zap.sell` round trips; a Devin session with terminal access would be needed to fuzz `_computeBuy`/`_computeSell`/`Pair.swap` round trips against `canGraduate`'s subtraction to empirically confirm or rule out the underflow being reachable from a purely unprivileged trader's perspective.

    function canGraduate(
        address token_
    ) public view returns (bool) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return false;
        if (info.lifecycle != Lifecycle.Curve) return false;

        address pair = info.pair;
        if (IPair(pair).tokenBalance() == 0) return true;

        (, uint256 assetReserve) = IPair(pair).getReserves();
        uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
        uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
        return valueUsd >= $.graduationThresholdUsd;
    }
