This confirms the vulnerability: `ShopifyAPI::Webhooks::Request#shop` at [1](#0-0)  reads the tenant identifier from the `shopify-shop-domain` header, but the HMAC signature only covers the raw request body via `to_signable_string` at [2](#0-1) . `Registry.process` validates the HMAC and then forwards `request.shop` unchanged into `WebhookMetadata` for the app's handler [3](#0-2) , and the documented handler contract explicitly trusts `data.shop` as "The shop domain of the webhook" to key per-tenant work [4](#0-3) .

### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant shop spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload solely from the raw body (`to_signable_string` returns `@raw_body`), while the `shop` attribute used downstream for tenant attribution is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never included in the signed bytes. `Registry.process` validates the HMAC against the body only, then unconditionally passes the header-derived `shop` value to the host application's webhook handler.

### Finding Description
The identity binding that should hold is: `shop attributed to a webhook == shop authenticated by the HMAC signature`. In this gem that equality is broken:

- `hmac` is computed from the `shopify-hmac-sha256` header [5](#0-4) .
- `to_signable_string`, the only data actually verified by `HmacValidator`, returns just `@raw_body` [2](#0-1) .
- `shop` is parsed independently from the `shop-domain` header, outside the signed content [1](#0-0) .
- `Registry.process` verifies `Utils::HmacValidator.validate(request)` (body-only) and then hands `request.shop`, unauthenticated, straight to the app's handler as tenant identity via `WebhookMetadata` [3](#0-2) .

Because the `shop-domain` header is not part of the HMAC-signed bytes, any party capable of producing one valid `(body, hmac)` pair for their own shop (which is trivial — an attacker's own store legitimately triggers webhooks with a correctly-signed body for that attacker's own shop) can subsequently submit a request with that identical valid `body`/`hmac` pair but an arbitrary `shopify-shop-domain` header value naming a different, victim shop. `HmacValidator.validate` will still pass because it only recomputes and compares against `raw_body` [6](#0-5) . The handler then receives `data.shop` claiming to be the victim shop, while the actual signed content (and the shop that produced the valid signature) is the attacker's own shop.

### Impact Explanation
The gem's own documentation instructs integrators to trust `data.shop` as "The shop domain of the webhook" for keying per-tenant background jobs and data processing (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [7](#0-6) . Mandatory compliance topics such as `shop/redact`, `customers/redact`, and `customers/data_request` are processed through this same unauthenticated `shop` field [8](#0-7) . An attacker who owns any shop can forge the `shop` attribution on an otherwise validly-HMAC'd webhook to point at a victim shop, causing the app to perform actions (data deletion/redaction, job scheduling, cache/record updates) against the wrong tenant — a cross-tenant integrity violation stemming directly from the gem's identity-binding gap.

### Likelihood Explanation
Exploitation requires only the ability to send one HTTP request to the app's webhook endpoint with a header value the attacker controls; no access token, `client_secret`, or privileged credential is needed. Any developer/merchant with their own Shopify store can obtain a validly-signed body/HMAC pair via normal webhook delivery to their own endpoint, then replay it with a substituted `shop-domain` header against the same endpoint (which is typically shared across all installs of the app).

### Recommendation
Include the shop domain (and ideally other identifying headers) inside the HMAC-signable content, or otherwise cryptographically bind the claimed `shop` value to the signature, e.g. compute the signable string over `raw_body + shop-domain header` rather than `raw_body` alone in `to_signable_string` at [2](#0-1) . At minimum, document that host applications must not treat `WebhookMetadata#shop` as authenticated unless it is cross-checked against a shop the app has an active session/install for.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and configures a webhook subscription (e.g. `orders/create`).
2. Shopify delivers a webhook to the app with body `B`, header `shopify-shop-domain: attacker.myshopify.com`, and a valid `shopify-hmac-sha256` computed over `B` with the app's shared secret — the attacker observes/captures this exact `(B, hmac)` pair (e.g. via their own logging middleware, since it's their own traffic).
3. Attacker sends a new HTTP request to the same app webhook endpoint with the identical body `B` and identical `hmac` header, but sets `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts it; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against `hmac` — this passes since `B`/`hmac` are unchanged [9](#0-8) .
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` [10](#0-9) , and the host application performs shop-scoped processing (e.g., data update/redaction/job enqueue) attributed to the victim shop despite the request never actually being authenticated for that shop.
