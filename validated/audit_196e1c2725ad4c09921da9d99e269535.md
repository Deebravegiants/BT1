### Title
Webhook `topic` and `shop-domain` are trusted for routing/tenant-attribution but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `Registry.process` uses the unsigned `topic` and `shop` header values to select the handler and to build the `WebhookMetadata` that is handed to the app's business logic. The identity binding "bytes verified == bytes acted on" is broken: the HMAC proves only that the *body* bytes were produced with the app's secret, not that the accompanying `shop-domain`/`topic` headers belong to that body.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` accessor of the same object [1](#0-0) . For `Webhooks::Request`, `to_signable_string` is defined as `@raw_body` only [2](#0-1) , while `topic`, `shop`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the body [3](#0-2) .

`Registry.process` then trusts these unsigned headers: it uses `request.topic` to look up which registered `handler` executes, and passes `request.shop` straight into `WebhookMetadata`, which is the tenant identifier the host application's handler code will act on [4](#0-3) .

Because Shopify signs all webhooks for an app with the same shared `client_secret` regardless of which shop/topic triggered them, and only the body is signed, a single legitimate `(raw_body, hmac)` pair captured from *any* shop (including one the attacker owns) remains a **valid signature** for that raw body no matter what `shopify-shop-domain` or `shopify-topic` header values are attached to it. The equality the gem should enforce is:

```
HMAC(shared_secret, signed_bytes) == received_hmac  AND  signed_bytes ⊇ {shop, topic}
```

but the actual implementation only enforces:

```
HMAC(shared_secret, raw_body) == received_hmac
```

with `shop` and `topic` entirely outside `signed_bytes`.

### Impact Explanation
An attacker who can trigger a webhook for their own store (a routine, unprivileged action — e.g. create/update a resource on their own dev/trial shop that is installed with the target app) obtains a genuinely-signed `(raw_body, hmac)` pair from Shopify. Because the signature never covers `shop-domain` or `topic`, the attacker can replay that exact request to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop and/or the `shopify-topic` header for a different registered topic. `HmacValidator.validate` still returns `true`, `Registry.process` still dispatches it to the corresponding handler, and the handler receives a `WebhookMetadata` claiming the event came from the victim shop [5](#0-4) . Any host application that uses `data.shop` to look up the shop's stored session/access token and act on it (the documented pattern in this gem's own webhook usage guidance) will now perform actions against — or attribute state changes to — a shop the attacker does not own, which is a cross-tenant identity-binding break.

### Likelihood Explanation
Requires only an unprivileged party who can install the target app on a shop they control (or otherwise cause one legitimate webhook delivery) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-chosen headers — no access token, `client_secret`, or privileged account is needed. The gem performs no defense against this by design (`to_signable_string` for webhooks is hard-coded to the body only), so any application relying solely on this gem's `HmacValidator`/`Registry.process` for tenant attribution is affected.

### Recommendation
Bind `shop`, `topic` (and ideally `webhook_id`/`api_version`) into the signature verification, not just the raw body — e.g., verify the HMAC against `raw_body` as Shopify computes it (unchanged, since Shopify itself only signs the body) but additionally require applications to cross-check `shop`/`topic` against session state they already trust, or expose a combined verification that rejects unexpected shop/topic pairs for a given body hash cached from previous deliveries. At minimum, the docs and `WebhookMetadata` consumers should be explicitly warned that `shop` and `topic` are unauthenticated header values and must not be used as the sole tenant/session lookup key without an independent binding (e.g., matching against an actively registered webhook_id/shop pairing recorded at registration time).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook (e.g. `products/update`), capturing the real request Shopify sends: `raw_body`, header `shopify-hmac-sha256: <hmac>`, `shopify-topic: products/update`, `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical `raw_body` and `shopify-hmac-sha256` value to the app's webhook endpoint, but changes `shopify-shop-domain` to `victim-shop.myshopify.com`.
3. `Webhooks::Request.new` parses the forged headers [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and succeeds [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.new(topic: "products/update", shop: "victim-shop.myshopify.com", ...)` [5](#0-4) , and any host logic keyed on `data.shop` operates against the victim tenant despite the payload never having been produced for that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
