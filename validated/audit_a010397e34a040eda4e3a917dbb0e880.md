### Title
Webhook shop/topic identity is trusted from unauthenticated headers while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify," but the HMAC computed by `HmacValidator` only authenticates the raw JSON body. The `shop`, `topic`, `webhook_id`, and `api_version` fields that the registry uses to route the event and populate `WebhookMetadata` (which the host application uses to identify the tenant) are taken verbatim from HTTP headers that are never included in the signed data. Any actor who can produce one authentic `(body, hmac)` pair signed with the app's `client_secret` — which is shared across every shop that installs the app — can replay that exact pair while forging the `shop-domain`/`topic` headers to make the app process the event as if it belonged to a different shop or topic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the HMAC purely over that signable string (the body) and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof the *entire request*, including `topic` and `shop`, is authentic, and immediately hands those header-derived values to the handler: [3](#0-2) 

But `topic`, `shop`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding to the body that was actually signed: [4](#0-3) 

The documentation reinforces the false guarantee: "This will verify the request did indeed come from Shopify and then call the specified handler for that webhook." [5](#0-4) 

This is the same class of bug as the reference report: the equality the code actually enforces is `hmac_verified(body) == true`, but the code and its documentation act as though `shop_verified == shop_used` and `topic_verified == topic_used` also hold. Since the app's `client_secret` is identical for every shop that installs the app, any tenant that can trigger one authentic webhook for their own store (e.g. by creating an order or updating a product on a store they legitimately installed the app on — an ordinary, unprivileged action) obtains a `(body, hmac)` pair that will pass `HmacValidator.validate` regardless of which `shop-domain`/`topic` headers accompany it. That tenant can then replay the identical body+hmac to the app's public webhook endpoint with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header naming a victim shop, and `Registry.process` will dispatch it to the handler with `WebhookMetadata#shop` set to the victim's domain.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee to the host application: `data.shop`/`data.topic` in `WebhookMetadata` are presented as authenticated, but they are fully attacker-controlled once any one genuine webhook signature has been observed. A host application that keys any per-tenant state, background job, or side effect off `data.shop` (as the gem's own documentation examples show — `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to attribute attacker-supplied webhook content to an arbitrary victim shop. This is a cross-tenant confusion/spoofing primitive rooted entirely in this gem's verification logic, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
High for an attacker who is simply a merchant installer of the app (an ordinary, unprivileged relationship with respect to the app's own security model, requiring no access token, no `client_secret`, and no privileged account): they only need to capture one legitimate webhook delivery to their own store (trivially triggered by performing an action that fires a registered topic) and then replay it against the app's internet-reachable webhook endpoint with modified, unsigned headers.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signable material, or otherwise cryptographically bind them to the payload before dispatch, so that `HmacValidator.validate` fails whenever any of these fields have been altered from what Shopify actually sent for that specific body. At minimum, document clearly that `HmacValidator`/`Registry.process` only authenticates the body and that host applications must independently verify `shop` against their own list of installed/known shops before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. Attacker installs the target app on their own (attacker-controlled) Shopify store and registers for a webhook topic, e.g. `orders/create`.
2. Attacker performs an action on their store that triggers the webhook, capturing the genuine `raw_body` and the `x-shopify-hmac-sha256` value Shopify computed with the shared `client_secret`.
3. Attacker resends this exact `raw_body`/`hmac` pair to the app's public webhook endpoint, but replaces:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: <any registered topic>` (optionally different from the original)
4. `HmacValidator.validate` recomputes the HMAC over `raw_body` only, which still matches, so `Registry.process` calls the handler with `WebhookMetadata.new(topic: "<forged>", shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`.
5. The host application processes attacker-controlled webhook content as if it originated from `victim-shop.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
