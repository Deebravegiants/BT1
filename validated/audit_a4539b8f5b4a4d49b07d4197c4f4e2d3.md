### Title
Arbitrary stateless call in `EmporiumUpgradeable.runAction` allows draining any ERC20 balance held by the Emporium contract, unaccounted for in the balance equation - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` executes arbitrary attacker-supplied `op.endpoint.call{value: op.value}(op.callData)` for every "Case 2: Stateless" `EmporiumOperation` (when `invokeWallet` is false or `signerAddress == address(0)`), with the call executed *as* the `EmporiumUpgradeable` contract itself. The only balance accounting performed afterward is limited to the tokens the caller explicitly lists in `circomData.erc20TokenAddresses` [1](#0-0) . Any ERC20 token not included in that self-declared array is never balance-checked, so a caller can insert an operation whose `endpoint` is an arbitrary ERC20 token contract and whose `callData` is `transfer(attacker, amount)`, draining that token from `EmporiumUpgradeable` without it ever appearing in the balance equation.

### Finding Description
The Case-2 branch performs an unrestricted low-level call: [2](#0-1) 

The only restriction is a selector check preventing spoofing of `callHinkalWallet`/`doSendToRelay`; `op.endpoint` and the rest of `op.callData` are fully attacker-controlled. Because `stack.signerAddress` can be `address(0)`, this path requires no EIP-712 signature at all (`verifyWallet` returns immediately for `signerAddress == address(0)`) [3](#0-2) . The only remaining gate is `onlyAllowedRecipient`, which merely requires `msg.sender == Hinkal.sol` (i.e. that the call was routed through the normal `transact()` entrypoint) [4](#0-3) , not that the operation is safe or scoped to declared tokens.

The post-call accounting only iterates `circomData.erc20TokenAddresses`, a caller-chosen public array, comparing balances before/after and forwarding any positive delta to the caller via `handleOut`/`transferERC20TokenOrETH` [5](#0-4)  and [6](#0-5) . If a token is deliberately *omitted* from `circomData.erc20TokenAddresses`, any balance change to it caused during the `ops` loop is completely invisible to the protocol's balance equation — this is exactly the "value moved by an external action but not counted in the balance equation" class from the Aura analog (there, the minted `AURA` token was omitted from `tokensIn`; here, an attacker deliberately omits the target token from their own public input array).

`EmporiumStorage` confirms there is no on-chain per-user ledger of who owns what balance inside the contract — it only tracks `usedMessages` [7](#0-6) . Ownership of tokens sitting in `EmporiumUpgradeable` between transactions (which is explicitly anticipated — "tokens deposited into Emporium are not charged", implying deposits can persist across calls, [8](#0-7) ) is tracked nowhere on-chain; it is purely the contract's raw ERC20 balance. Any other user going through `Hinkal.transact()` with their own valid proof can craft an `EmporiumOperation` that calls `token.transfer(attacker, balance)` directly on any ERC20 the Emporium contract holds, and as long as that token address is absent from their own `erc20TokenAddresses`, the theft is never checked against the balance equation and the transaction succeeds.

### Impact Explanation
This breaks the equality the Emporium's balance-diff loop is supposed to enforce: "on-chain balance change of an accounted token == amount claimed as UTXO". By simply not declaring the target token as one of the accounted tokens, an attacker moves assets out of the shared `EmporiumUpgradeable` contract with zero on-chain accounting or slippage/UTXO constraint applied. Since the contract is a shared vault with no internal per-depositor ledger, this is direct theft of any ERC20 tokens temporarily or persistently held by `EmporiumUpgradeable` on behalf of other users (deposits pending multi-step composition, dust from swaps, unclaimed reward-like tokens from arbitrary `op.endpoint` calls, etc.) — Critical severity theft of protocol/user funds and an unauthorized asset movement never authorized by the token owner's proof or signature.

### Likelihood Explanation
High. No signature is required (`signerAddress = address(0)` skips `verifyWallet`'s EIP-712 check entirely), the only precondition is that the attacker can produce a valid ZK proof for their *own* commitments/nullifiers (trivial, since it doesn't constrain the token being stolen), and route the call through `Hinkal.transact()` targeting the Emporium external action, which is the intended/allowed way to invoke `EmporiumUpgradeable.runAction`. The only work needed is to omit the target token from `circomData.erc20TokenAddresses` and craft `op.callData` as a standard ERC20 `transfer`/`transferFrom`/`approve` call.

### Recommendation
- Restrict Case-2 stateless operations to a whitelist of allowed endpoints/selectors (e.g., only known DeFi routers/protocol contracts), rather than allowing arbitrary `endpoint.call(callData)`.
- Alternatively/additionally, enforce that any token balance change caused by `ops` execution — for *all* tokens touched, not only those declared in `circomData.erc20TokenAddresses` — is reconciled against the balance equation (e.g., by requiring the full set of touched tokens as part of `calldataHash`/the public inputs, or by disallowing raw token-contract calls as `op.endpoint`).
- Never allow `signerAddress == address(0)` stateless operations to invoke arbitrary calldata against arbitrary contracts holding pooled user funds without some form of authorization tied to token ownership.

### Proof of Concept
1. Assume `EmporiumUpgradeable` currently holds `X` amount of `TOKEN` belonging to another user (deposited via a prior legitimate multi-step operation, or accrued as a side-effect of some other user's `ops` call).
2. Attacker builds a valid Hinkal ZK proof for their own (possibly empty/zero-value) UTXOs, targeting the Emporium external action, with:
   - `circomData.erc20TokenAddresses` = `[]` or some unrelated token (deliberately excluding `TOKEN`).
   - `EmporiumStack.signerAddress = address(0)` (no signature check).
   - `EmporiumStack.ops = [{ endpoint: TOKEN, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, X) }]`.
3. Attacker calls `Hinkal.transact(...)`. The proof and root-hash checks pass (they only constrain the attacker's own shielded balances), `hinkalHelper.performSideEffects` runs, and `EmporiumUpgradeable.runAction` executes `TOKEN.transfer(attacker, X)` as `msg.sender = EmporiumUpgradeable` [2](#0-1) .
4. The post-loop balance check only iterates `circomData.erc20TokenAddresses` (empty/unrelated), so the `TOKEN` outflow is never checked [5](#0-4) .
5. Transaction succeeds; attacker has stolen `X` amount of `TOKEN` from `EmporiumUpgradeable` with no reduction to their own shielded balance and no revert.
