### Title
Unchecked ERC20 return value in `IntentGatewayV2` (Tron) `withdraw`/`SweepDust` allows escrow to be wiped without tokens ever reaching the beneficiary - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2` pays out escrowed order tokens, transaction fees, and swept dust using a raw low-level `.call` to the token's `transfer` function and only checks that the call itself did not revert (`success`), never decoding/validating the returned boolean. Non-compliant ERC20/TRC20 tokens that return `false` on failure instead of reverting (a very common pattern on Tron, mirroring USDT-style tokens) will make this check pass even though no tokens were moved, while the internal escrow accounting is unconditionally decremented/deleted.

### Finding Description
In `withdraw()`, which is invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` request kinds (reachable by any relayer that delivers a valid cross-chain ISMP message), and in the `SweepDust` handling branch of `onAccept()`, token payouts use: [1](#0-0) [2](#0-1) [3](#0-2) 

In all three spots, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` is checked only via `success` (i.e., "call did not revert"), never via `abi.decode(data, (bool))`. This differs from the file's own `SafeERC20`/`safeTransferFrom` usage elsewhere in the same contract (e.g. `placeOrder`) and from the canonical EVM `IntentGatewayV2` (non-Tron) which consistently uses `SafeERC20`: [4](#0-3) 

Regardless of whether the token transfer actually succeeded, `withdraw()` unconditionally decrements `_orders[body.commitment][token]` and deletes the fee escrow entry: [5](#0-4) 

If the payout token returns `false` on failed transfer (e.g., insufficient balance held by the gateway due to a rounding/dust edge case, a paused/blacklisted token, or any TRC20 implementing the historically common "return false instead of revert" semantics), the low-level `call` still returns `success = true` (the call executed without reverting), so the `if (!success) revert TransferFailed();` guard never fires. The function proceeds to zero out the escrow record and mark `_filled[body.commitment] = beneficiary`, permanently closing out the order as fulfilled even though the beneficiary received nothing.

### Impact Explanation
This produces a permanent freezing/loss of user or solver funds:
- The intended recipient (user on refund, or solver on fill redemption) never receives their tokens.
- The escrow accounting (`_orders[commitment][token]`) is wiped, and `_filled[commitment]` is set, so the withdrawal cannot be retried or re-triggered — the funds become permanently stuck in the `IntentGatewayV2` contract with no code path to recover them for the rightful owner.
- The same pattern affects `SweepDust`, meaning protocol-owned dust can also be silently "swept" without actually moving tokens, corrupting internal accounting versus actual token balances.

This matches the required impact bar: concrete permanent freezing of funds reachable via a normal relayed cross-chain message (RedeemEscrow/RefundEscrow/SweepDust), which any relayer can trigger by delivering a valid proof once the source-chain order state permits it.

### Likelihood Explanation
Likelihood is elevated specifically because this is the **Tron** variant of the contract. TRC20 tokens on Tron very commonly follow the non-reverting, boolean-return convention (mirroring Ethereum's USDT), so encountering a token whose `transfer` returns `false` instead of reverting on failure is a realistic, not merely theoretical, scenario for this deployment target. Any listed intent-gateway token with this behavior — combined with any condition causing a transfer shortfall (e.g., fee-on-transfer tokens as already handled elsewhere in this same file, blacklisting, pausing, or balance discrepancies from the predispatch/dispatcher flow) — triggers the bug on the very next legitimate withdrawal.

### Recommendation
Use OpenZeppelin's `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;` and elsewhere in the same contract for `safeTransferFrom`) instead of the raw low-level `.call` + `success`-only check, for all three payout sites in `withdraw()` and the `SweepDust` branch of `onAccept()`:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```
This decodes and validates the return data when present, and still handles tokens with no return value correctly, closing the gap where `success == true` but the transfer logically failed.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron) with a TRC20 test token whose `transfer` implementation returns `false` on failure rather than reverting (representative of common Tron token behavior), e.g. by making its balance insufficient at payout time.
2. A user places a cross-chain order with this token as input; escrow is recorded in `_orders[commitment][token]`.
3. Before redemption, drain/reduce the gateway's balance of that token below `amount` (e.g., via an admin action or a bug in the predispatch/dispatcher accounting path already present in the file, or a paused/blacklist state on the token for the beneficiary).
4. A relayer delivers a valid `RedeemEscrow` proof; `onAccept` → `withdraw()` is called.
5. `token.call(...)` executes and returns `(true, encodedFalse)` because the token's `transfer` returns `false` on insufficient balance instead of reverting; the `success` bool from the low-level call is `true`, so the `revert TransferFailed()` guard is skipped.
6. `_orders[body.commitment][token] -= amount` succeeds (no revert since it's unconditional after the check), `_filled[body.commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — yet the beneficiary's token balance never increased.
7. The order is now permanently marked filled/refunded in `_orders`/`_filled`, with no further code path to pay the beneficiary; funds are stuck in the gateway contract.
