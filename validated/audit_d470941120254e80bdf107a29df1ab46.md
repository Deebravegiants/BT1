## Title
`webhook-id` header spoofing on a validly-signed body bypasses cross-tenant dedup — (File: lib/shopify_api/webhooks/request.rb)

## Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `webhook_id` is read exclusively from the `x-shopify-webhook-id` / `shopify-webhook-id` header, never mixed into the signed bytes. Because `Utils::HmacValidator.validate` only checks the HMAC over the raw body, any request whose body/HMAC pair is genuine (from *any* shop, including an attacker's own dev shop) will pass validation regardless of what `webhook-id` (and `shop-domain`, `topic`) headers are attached, so `Registry.process` hands the handler a `WebhookMetadata` whose `webhook_id` (and `shop`) fields are fully attacker-controlled.

## Finding Description
The binding the host app relies on is: `webhook_id inside signed bytes == webhook_id acted upon by the handler`. Tracing the code shows this is false:

- `to_signable_string` returns `@raw_body` only: [1](#0-0) 
- `webhook_id` is read purely from the header, with no cross-check against the body: [2](#0-1) 
- `shop` and `topic` suffer the identical issue — also header-only, also excluded from the signed string: [3](#0-2) 
- `HmacValidator.validate` computes the HMAC solely over `to_signable_string` (i.e. the raw body) and compares against the `hmac` header: [4](#0-3) 
- `Registry.process` validates the HMAC, then builds `WebhookMetadata` directly from the unauthenticated header-derived accessors (`request.shop`, `request.webhook_id`) and hands it to the host app's handler: [5](#0-4) 
- `WebhookMetadata.webhook_id` and `.shop` are plain `String` fields with no provenance/verification attached: [6](#0-5) 
- The docs explicitly instruct host apps to use `webhook_id` for dedup and `shop` to identify the tenant, reinforcing that this is the documented/expected trust boundary: [7](#0-6) 

Attack flow: the attacker installs the app on their own development shop and receives a real webhook delivery — a genuine `(raw_body, hmac)` pair signed with the app's shared `client_secret` (the same secret is used for HMAC verification across all shops installing the app; it authenticates the *app*, not the *shop*). The attacker then POSTs that exact same `raw_body`/`hmac` to the app's public webhook endpoint again, but swaps the `x-shopify-webhook-id` header to a value they've observed or guessed as belonging to a victim shop's prior delivery, and/or swaps `x-shopify-shop-domain` to the victim's domain. Since `to_signable_string` never includes any header, the HMAC still validates. `Registry.process` passes, and the handler receives a `WebhookMetadata` object whose `shop` and `webhook_id` are exactly whatever the attacker put in the headers, carrying the attacker's own (real but unrelated) body content. A host app that performs cross-tenant dedup keyed by `webhook_id` (+ `shop`) will treat this forged delivery as a legitimate retry/duplicate for the victim tenant, confusing or overwriting victim-associated state with attacker-supplied data.

No existing guard prevents this: `HmacValidator.validate` only authenticates the body bytes, not the header metadata; there is no `ShopValidator.sanitize!`/session cross-check performed inside `Request`/`Registry` at all; Sorbet's `String` typing on `WebhookMetadata` fields provides no authenticity guarantee, only a type guarantee.

## Impact Explanation
This breaks the trust boundary for **all** header-derived webhook metadata (`shop`, `topic`, `webhook_id`, `api_version`) simultaneously — not just `webhook_id`. A host app that uses `shop` from `WebhookMetadata` to select which tenant's data to update, or `webhook_id` to dedupe/gate reprocessing, can be made to act on attacker-controlled tenant identifiers while the payload content is real, HMAC-valid data from the attacker's own shop. This is cross-tenant confusion: an unprivileged attacker can repeatedly, and against arbitrary chosen victim shop domains/webhook IDs, inject events that a host app will bind to a different tenant. This matches the Critical "cross-tenant access" category.

## Likelihood Explanation
Preconditions are minimal and entirely within the stated attacker capability: create a free/dev shop, install the app, register any webhook topic, and receive one genuine delivery to obtain a valid `(raw_body, hmac)` pair. No `client_secret`, access token, or other credential is needed. The victim's `webhook_id` value would need to be known/guessed by the attacker for the dedup-bypass scenario specifically to have a targeted, exploitable effect (webhook IDs are Shopify-format GUIDs, not secret, and may be observable via app logs, GraphQL `webhookSubscriptions` responses, or side channels depending on host app), but the underlying primitive — being able to set `shop`/`webhook_id`/`topic` to arbitrary attacker-chosen values on a validly-HMAC'd request — requires no guessing at all and is trivially repeatable against any endpoint using this gem as documented.

## Recommendation
Bind webhook-critical metadata into the signed content, or otherwise authenticate it independently of raw headers:
- Modify `Request#to_signable_string` (or add an additional check in `Utils::HmacValidator`/`Registry.process`) so that `shop`, `topic`, and `webhook_id` are cryptographically bound to the HMAC-verified payload rather than being read solely from unauthenticated request headers.
- Alternatively, since Shopify's real webhook body payloads typically carry shop-identifying context, cross-validate the header-derived `shop` against a shop identifier embedded in `parsed_body` (or against the shop stored for the corresponding `webhook_id` if previously seen) before constructing `WebhookMetadata`.
- At minimum, document prominently that `WebhookMetadata#shop` and `#webhook_id` are **not** authenticated by the HMAC and must not be used by host apps for tenant selection or dedup without additional verification — though a code-level fix binding these values into the signature is the correct remediation, not a documentation workaround.

## Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_webhook_id_and_shop_are_not_bound_to_hmac_signed_body
  raw_body = '{"id":1,"note":"hello"}'
  secret = "secret"
  ShopifyAPI::Context.setup(api_key: "key", api_secret_key: secret, ...)

  hmac = Base64.encode64(
    OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)
  )

  attacker_headers = {
    "shopify-hmac-sha256" => hmac,
    "shopify-topic" => "orders/create",
    "shopify-shop-domain" => "attacker-shop.myshopify.com",
    "shopify-webhook-id" => "attacker-chosen-id-1",
  }

  victim_headers = attacker_headers.merge(
    "shopify-shop-domain" => "victim-shop.myshopify.com",
    "shopify-webhook-id" => "victim-webhook-id-99", # attacker-guessed/observed victim id
  )

  request_a = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: attacker_headers)
  request_b = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: victim_headers)

  captured = []
  handler = Class.new do
    extend ShopifyAPI::Webhooks::WebhookHandler
    define_singleton_method(:handle) { |data:| captured << data }
  end
  ShopifyAPI::Webhooks::Registry.add_registration(topic: "orders/create", delivery_method: :http,
    handler: handler, path: "cb")

  # binding claimed: webhook_id inside signed bytes == webhook_id acted on
  assert(ShopifyAPI::Utils::HmacValidator.validate(request_a))
  assert(ShopifyAPI::Utils::HmacValidator.validate(request_b)) # same HMAC validity, different webhook_id/shop

  ShopifyAPI::Webhooks::Registry.process(request_a)
  ShopifyAPI::Webhooks::Registry.process(request_b)

  assert_equal("attacker-chosen-id-1", captured[0].webhook_id)
  assert_equal("victim-webhook-id-99", captured[1].webhook_id) # forged, host app dedup keys would collide with victim's real ID
  assert_equal("victim-shop.myshopify.com", captured[1].shop)  # forged tenant binding
end
```
This demonstrates both `Request` objects — identical `raw_body`/HMAC, different `webhook-id`/`shop` headers — pass `Registry.process`, and the attacker fully controls `WebhookMetadata#webhook_id` and `#shop` despite a valid signature, confirming the binding does not hold.
