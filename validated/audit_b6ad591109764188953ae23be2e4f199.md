### Title
`EvmHost.updateHostParamsInternal()` allows the challenge period to be reduced with no recalculation of already-stored, still-pending state commitments - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.updateHostParamsInternal()` validates several `HostParams` fields when governance (or, on `TestnetHost`, the admin) updates them — it enforces a floor on `unStakingPeriod`, blocks changing `feeToken` while a balance is held, and requires `hostManager`/`handler`/`consensusClient` to implement the right interfaces — but it applies **no validation at all to `challengePeriod`**. Any already-stored state commitments that were accepted under the old (longer) challenge period are silently re-evaluated against the new, shorter one the moment the update lands, because `HandlerV2` only ever compares `block.timestamp - stateMachineCommitmentUpdateTime` against the host's *current* `challengePeriod()`, never the period that was in force when the commitment was stored.

### Finding Description
`updateHostParamsInternal` is the single place that writes all `HostParams`, including `challengePeriod`: [1](#0-0) 

Compare the checks it performs for `unStakingPeriod` and `feeToken` against the complete absence of any check for `challengePeriod`: [2](#0-1) 

There is no `InvalidChallengePeriod`-style guard, and no logic that inspects outstanding `_stateCommitments`/`_stateCommitmentsUpdateTime` entries before allowing the change — unlike the Token.sol report where `setReservedUntilTokenId()` changes a load-bearing parameter without recalculating the founders' vesting allocation ids that were computed against the old value.

Every consumer of the challenge period reads it live from the host at call time and compares it to the *current* `challengePeriod()`, not the value that applied when the commitment was written: [3](#0-2) [4](#0-3) 

Meanwhile, fishermen invalidate a bad/fraudulent state commitment by deleting it (via the handler, `deleteStateMachineCommitmentInternal`) — this is the veto mechanism the challenge period exists to give time for: [5](#0-4) 

Because `updateHostParamsInternal` performs no recalculation or protection for state commitments already in flight, a governance-issued `SetHostParam` message (delivered through `HostManager.onAccept`, reachable by the authorized relayer over the normal cross-chain governance path) that lowers `challengePeriod` retroactively shrinks the safety window for every commitment stored before the update: [6](#0-5) 

### Impact Explanation
If `challengePeriod` is reduced (e.g. from several days down to a much smaller value, or even to a value smaller than the time already elapsed since a pending commitment's `stateMachineCommitmentUpdateTime`), any state commitment that was stored just before the update — and that a fisherman had not yet had the chance to veto under the old, longer window — instantly becomes usable. A relayer can immediately call `handlePostRequests`/`handleGetResponses`/`handlePostRequestTimeouts`/`handleGetRequestTimeouts` against that commitment, since these only check the challenge period currently configured on the host, not the one that applied when the commitment was recorded. This lets a state commitment produced from a compromised or short-range-forked consensus proof be used to deliver forged/unverified messages before fishermen can react, resulting in unauthorized app actions or forged message delivery — the exact class of impact called out as acceptable (forged message delivery / unsound state commitment).

### Likelihood Explanation
The trigger is a normal, expected operational action (a `SetHostParam` governance update lowering `challengePeriod`, e.g. as part of routine parameter tuning) delivered through the existing, non-malicious `HostManager`/`updateHostParams` path — not an admin/governance compromise. The root cause is purely the missing recalculation/validation logic in `updateHostParamsInternal`, mirroring the reported bug class exactly: a legitimate parameter change silently invalidates the safety assumptions baked into already-existing dependent state (pending state commitments / their fraud-proof window), and the downstream handler has no way to detect the mismatch.

### Recommendation
When `challengePeriod` is decreased, either (a) apply the new value only to state commitments stored after the update (retain the old period for already-stored heights until they've cleared it), or (b) require that no state commitment is currently within its still-open old challenge window before allowing the decrease, similar to the existing `CannotChangeFeeToken`/`CannotDecreaseRestriction`-style guards already used for other parameters in the same function.

### Proof of Concept
1. Host is configured with `challengePeriod = 7 days`.
2. A consensus proof stores a new state commitment at height H at time T (`storeStateMachineCommitment`), starting its 7-day fisherman-veto window.
3. Before fishermen can veto (say at T+1 hour), governance delivers a `SetHostParam` request via `HostManager.onAccept` → `EvmHost.updateHostParams` → `updateHostParamsInternal`, setting `challengePeriod = 1 hour`. No check prevents this since only `unStakingPeriod` and `feeToken` are validated.
4. Immediately after, `HandlerV2.handlePostRequests` computes `delay = block.timestamp - stateMachineCommitmentUpdateTime(H) = 1 hour`, which now satisfies `challengePeriod = 1 hour`, so the check `challengePeriod > delay` passes even though fishermen only had 1 hour instead of the promised 7 days to veto a potentially fraudulent commitment at height H.
5. A relayer submits a forged/unverified request proven against commitment H and it is accepted and dispatched to the destination module before the originally-promised challenge window elapsed.

    function updateHostParamsInternal(HostParams memory params) internal {
        // check the params to prevent the host from getting bricked.
        if (
            params.hostManager == address(0) || address(params.hostManager).code.length == 0
                || !IERC165(params.hostManager).supportsInterface(type(IApp).interfaceId)
        ) {
            // otherwise cannot process new cross-chain governance requests
            revert InvalidHostManager();
        }

        if (
            params.handler == address(0) || address(params.handler).code.length == 0
                || !IERC165(params.handler).supportsInterface(type(IHandlerV2).interfaceId)
        ) {
            // otherwise cannot process new datagrams
            revert InvalidHandler();
        }

        if (
            params.consensusClient == address(0) || address(params.consensusClient).code.length == 0
                || !IERC165(params.consensusClient).supportsInterface(type(IConsensusV2).interfaceId)
        ) {
            // otherwise cannot process new consensus datagrams
            revert InvalidConsensusClient();
        }

        // otherwise cannot process new cross-chain governance requests
        if (keccak256(params.hyperbridge) == keccak256(bytes(""))) revert InvalidHyperbridgeId();

        // otherwise cannot process new datagrams
        uint256 stateMachinesLen = params.stateMachines.length;
        if (stateMachinesLen == 0) revert InvalidStateMachinesLength();

        // otherwise cannot process new datagrams
        if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();

        address oldFeeToken = feeToken();
        if (oldFeeToken != address(0) && oldFeeToken != params.feeToken) {
            uint256 balance = IERC20(oldFeeToken).balanceOf(address(this));
            if (balance != 0) revert CannotChangeFeeToken();

        // and don't want to store a temp variable for the old params
