### Title
Webhook shop/topic identity spoofing via unsigned headers — cross-tenant webhook processing (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` verifies the HMAC exclusively against that body. The `shop`, `topic`, and `webhook_id` values used by `Registry.process` to route and identify the tenant come straight from unauthenticated HTTP headers, so they are never bound to the HMAC signature.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop`, `topic`, `webhook_id` are read directly from headers with no cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only recompute and compare the HMAC over `verifiable_query.to_signable_string` (i.e., the body), never over the shop/topic headers: [3](#0-2) 

`Registry.process` checks only this body-only HMAC, then immediately trusts `request.shop`/`request.topic` to dispatch to a handler and build `WebhookMetadata`: [4](#0-3) 

The equality the gem is implicitly relying on is:
`valid_hmac(body) == true` implies `shop_header == shop_that_generated_this_body`

but the actual guarantee provided is only `valid_hmac(body) == true` implies `body was signed by api_secret_key at some point`, with no guarantee that `shop_header` (or `topic`) match what was originally signed. Any bytes labelled as the `shop-domain`/`topic` headers are parsed and handed to the app's handler without being verified.

### Impact Explanation
This breaks the tenant-identity binding for webhook processing. An unprivileged internet user who can obtain any single valid `(raw_body, hmac)` pair from the app (e.g., by installing the target app on their own shop, since Shopify sends real webhooks with a valid HMAC to any shop with the app installed) can replay that exact body + HMAC to the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` and/or `X-Shopify-Topic` headers to arbitrary values. Because `HmacValidator.validate` never inspects those headers, the forged request passes validation, and `Registry.process` will invoke the registered handler with `WebhookMetadata` claiming the payload belongs to a different shop/topic than what actually generated it. Any host application that uses `WebhookMetadata#shop` to select which merchant's records to update (the intended and documented usage) can be tricked into writing data belonging to one tenant into a different tenant's stored record — a cross-tenant data integrity/confidentiality violation.

### Likelihood Explanation
Likelihood is non-trivial but not trivial: it requires the attacker to obtain at least one genuine `(body, hmac)` pair for the target app, which is achievable by any user able to install the app on a shop they control (a normal, unprivileged install), then replaying it with modified headers to the same publicly reachable webhook endpoint. No access to `api_secret_key`, tokens, or the app's infrastructure is required.

### Recommendation
Include the shop domain and topic in the signed material that `to_signable_string` returns (or otherwise independently verify that the `X-Shopify-Shop-Domain` header matches an expected/known-installed shop before dispatch), so the HMAC binds the full identity context, not just the body bytes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers/receives any real webhook (e.g. `app/uninstalled`), capturing the exact raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (valid because Shopify computed it with the app's real `api_secret_key`).
2. Attacker replays a POST to the app's webhook endpoint with:
   - body = `B`
   - `X-Shopify-Hmac-Sha256` = `H` (unchanged, still valid since it's HMAC over `B` only)
   - `X-Shopify-Shop-Domain` = `victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic` = original or another registered topic
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb#L12-31` passes because it only checks `HMAC(B, secret) == H`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb#L188-200` dispatches the handler with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"`, even though `B` was never actually generated for that shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
