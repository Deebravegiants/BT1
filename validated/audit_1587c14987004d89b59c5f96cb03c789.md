## Title
Webhook Shop/Topic Identity Headers Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, while the `shop`, `topic`, and `webhook_id` values used to identify and dispatch the event are read from unauthenticated HTTP headers that are never part of the signed bytes.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` value extracted from the request [1](#0-0) .

For webhooks, `Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `Request#shop`, `Request#topic`, and `Request#webhook_id` are all pulled from HTTP headers, which are completely outside the HMAC-signed content: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then unconditionally trusts these header-derived identity fields to dispatch the handler and populate `WebhookMetadata`: [4](#0-3) 

The broken identity binding, stated as an equality that should hold but does not:
`bytes_covered_by_HMAC (raw_body)` == `identity_used_for_dispatch (headers: shop-domain, topic, webhook-id)`

Because the app's `api_secret_key` is a single shared secret used for **every** shop that installs the app (not a per-shop secret), any unprivileged user who installs the app on their own store — a legitimate, no-privilege action — can trigger any topic and capture a fully valid `(raw_body, hmac)` pair for their own webhook. That pair remains valid HMAC-wise no matter what `shop-domain`/`topic`/`webhook-id` headers are sent alongside it, since those headers are never part of `to_signable_string`.

### Impact Explanation
An attacker (any user who can self-install/uninstall the app to obtain one valid `(body, hmac)` sample) can replay that body+HMAC directly to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with an arbitrary victim shop domain, and/or substituting `X-Shopify-Topic`/`X-Shopify-Webhook-Id`. `Utils::HmacValidator.validate(request)` still returns `true` because only the body bytes are checked. The app's registered `WebhookHandler` then receives `WebhookMetadata` claiming the event belongs to the victim shop, causing the handler to process data under the wrong tenant's identity — a cross-tenant integrity violation (e.g. an app that stores/mutates per-shop state keyed off `data.shop` from the webhook could have arbitrary victim-shop records manipulated using attacker-controlled body content).

### Likelihood Explanation
Requires only: (1) ability to self-install the target app to obtain one legitimate signed webhook body (trivial, no privilege needed beyond being any merchant/dev store owner), and (2) sending a raw HTTP POST directly to the app's public webhook endpoint with modified headers, which any internet client can do since Shopify webhook endpoints are public HTTP(S) endpoints. This does not require the victim's access token, `client_secret`, or any credential leak.

### Recommendation
Bind the identity headers into the signed payload verification — e.g., include `shop`, `topic`, and `webhook_id` in the value used for `to_signable_string`, or otherwise cryptographically bind header values to the request before trusting them for dispatch, matching the same pattern already used for `Oauth::AuthQuery#to_signable_string`, which does include all identity fields (`code`, `host`, `shop`, `state`, `timestamp`) in the signed string [5](#0-4) .

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev/test store (`attacker.myshopify.com`) — no special privilege required.
2. Attacker triggers any registered webhook topic (e.g. `orders/create`) on their own store and captures the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify — this HMAC is valid because it is computed with the app's single shared `api_secret_key`.
3. Attacker sends that exact `(raw_body, hmac)` pair directly to the app's public webhook endpoint, but replaces `X-Shopify-Shop-Domain` with `victim.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `Utils::HmacValidator.validate(request)` in `Registry.process` passes because it only verifies `@raw_body` against the HMAC [6](#0-5) .
5. The registered handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`, where `shop` is `"victim.myshopify.com"` even though the payload actually originated from the attacker's own store — spoofing a cross-tenant webhook event.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
