Confirmed: `Registry.process` in `lib/shopify_api/webhooks/registry.rb:189-200` only checks `Utils::HmacValidator.validate(request)` (which HMACs only `@raw_body`, see `Request#to_signable_string`), then blindly forwards `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` — all unauthenticated header values — into `WebhookMetadata` passed to the app's handler.

### Title
Webhook shop/topic identity spoofing via HMAC that only covers the body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The gem's webhook signature verification only binds the HMAC to the raw request body, while the shop domain, topic, webhook id, and API version are taken from unauthenticated headers and handed directly to the app's webhook handler as trusted tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate_signature` computes and compares the HMAC solely over that signable string [2](#0-1) . Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from HTTP headers (`x-shopify-shop-domain`, `x-shopify-topic`, etc.) with no cryptographic binding to the HMAC at all [3](#0-2) . `Registry.process` validates only the HMAC and then constructs `WebhookMetadata` directly from these unauthenticated header fields before invoking the app's handler [4](#0-3) .

The broken identity binding, stated as an equality that should hold but doesn't:
`HMAC-covered-bytes(raw_body) == identity-bytes(shop, topic, webhook_id, api_version)` — the gem verifies the former but the handler trusts the latter as if it were verified.

### Impact Explanation
Any entity that can obtain one legitimately-signed webhook body+HMAC pair (e.g., an attacker who installs the app on their own shop and captures a webhook Shopify sends them) can replay that exact body/HMAC pair to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop's domain (and/or the topic/webhook-id headers). Because the HMAC check only covers the body bytes, the forged request still validates successfully, and the handler receives `WebhookMetadata` claiming it belongs to the victim shop. If the host application uses `data.shop` from `WebhookMetadata` to key per-tenant storage, trigger data deletion/redaction (e.g. `shop/redact`, `customers/redact`), or otherwise act on tenant-scoped state, this becomes a cross-tenant data integrity/confidentiality issue attributable to a boundary this gem is responsible for enforcing.

### Likelihood Explanation
Exploitation requires the attacker to have captured at least one valid signed webhook body (achievable simply by installing the target app on an attacker-controlled shop, which is normal unprivileged access), then replaying it with modified headers — no access to `api_secret_key` or any merchant token is required. This is a realistic and quite low-effort attack path.

### Recommendation
Include the security-relevant headers (at minimum `shop`, `topic`, and ideally `webhook_id`/`api_version`) in the HMAC-signed payload, or otherwise cryptographically bind them to the verified body before constructing `WebhookMetadata`, similar to how OAuth's `AuthQuery#to_signable_string` binds `shop`/`host`/`code`/`state` into the signed string [5](#0-4) .

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, triggering a real webhook (e.g. `orders/create`) with a valid `x-shopify-hmac-sha256` for a given raw body.
2. Attacker captures the raw body and HMAC header from that legitimate request.
3. Attacker crafts a new POST to the app's webhook endpoint with the identical raw body and HMAC header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over the raw body — validation passes [6](#0-5) .
5. The handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though the body content actually originated from the attacker's own shop [7](#0-6) .
