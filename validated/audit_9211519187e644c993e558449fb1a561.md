### Title
Missing allowlist/rate-limit enforcement lets any unauthenticated gateway client trigger workflow execution on every DON node - ([File: core/services/gateway/handlers/capabilities/handler.go])

### Summary
`HandleLegacyUserMessage` in the WebAPI capabilities gateway handler processes `web_api_trigger` messages from external, unauthenticated HTTP clients and forwards them verbatim to every node in the DON, with an explicit `// TODO: apply allowlist and rate-limiting here` marking the missing check before the request is dispatched. [1](#0-0) 

### Finding Description
The external report describes a pattern where a component blindly forwards attacker/actor-controlled data to an external call/target without an allowlist/authorization check that was intended to gate it (`manageSwapTarget`/`rebalanceAll` performing `params.swapTarget.call(params.swapData)` without restricting payload/target against user-approved funds). The same bug class - "downstream dispatch of unvalidated, caller-controlled data due to a missing gating check" - is present in the gateway's WebAPI capabilities handler.

`HandleLegacyUserMessage` validates message structure (payload decode, timestamp/staleness, method name) but explicitly skips the allowlist and rate-limiting step that is called out as still-needed in the code comment:
```go
// TODO: apply allowlist and rate-limiting here
if msg.Body.Method != MethodWebAPITrigger {
    ...
}
``` [2](#0-1) 

After this check, the handler converts the raw message into a signed request and unconditionally fans it out to every DON member:
```go
for _, member := range h.donConfig.Members {
    err = errors.Join(err, don.SendToNode(ctx, member.Address, req))
}
``` [3](#0-2) 

This `HandleLegacyUserMessage` entry point is the one invoked for arbitrary "user requests" arriving at the gateway (per the `Handler` interface docstring: "Each user request is processed by a separate goroutine, which: 1. calls HandleUserMessage"). [4](#0-3)  There is no caller/tenant allowlist check comparable to the Vault capability's `Authorizer`/`allowListBasedAuth` mechanism (which explicitly checks the workflow-registry allowlist before authorizing any request) before this trigger payload is forwarded to nodes. [5](#0-4) 

### Impact Explanation
Because any unauthenticated external caller of the gateway's WebAPI trigger endpoint can have their payload dispatched to every DON node without an allowlist check, this permits unauthorized triggering of workflow executions on the DON at will - the internet-facing gateway is the analog to the "manager" role in the original report: it is a trusted-but-lower-privilege forwarding component that can be abused to move/execute value-bearing DON operations (workflow runs, downstream external HTTP calls via `MethodWebAPITarget`) using caller-supplied data that has not been validated against any per-caller allowlist. This matches "unauthorized job run" impact class.

### Likelihood Explanation
The vulnerable code path is directly reachable from any external, unauthenticated client hitting the gateway's user-message endpoint with a `web_api_trigger` payload - no attacker privilege beyond "network client to the gateway" is required, and the missing check is explicitly flagged by the maintainers' own TODO comment, indicating this is a known, currently-unmitigated gap rather than a defense-in-depth nuance.

### Recommendation
Implement the allowlist/rate-limiting check called out in the TODO before forwarding `web_api_trigger` (and other `HandleLegacyUserMessage`-routed) requests to DON nodes - e.g., validate the requesting caller/workflow-owner against a registry-backed allowlist (as already done for the Vault capability's `AllowListBasedAuth`) and apply per-caller rate limiting, rejecting the request before any `don.SendToNode` fan-out occurs.

### Proof of Concept
1. An unauthenticated client sends an HTTP request to the gateway targeting the WebAPI capabilities handler with `msg.Body.Method = "web_api_trigger"` and a well-formed `webapicap.TriggerRequestPayload` (valid, non-stale `Timestamp`).
2. `HandleLegacyUserMessage` passes payload decoding, staleness check, and method-name check - all before the "apply allowlist" TODO, none of which validate the caller's identity/allowlist status. [6](#0-5) 
3. The handler forwards the resulting request unconditionally to every `donConfig.Members` node via `don.SendToNode`, triggering workflow execution on the DON without any allowlist authorization of the caller. [3](#0-2) 

Note: I was unable to fully trace the outer HTTP-facing entry point that constructs `*api.Message` and invokes `HandleLegacyUserMessage` from raw external client requests (the code index did not surface the gateway's HTTP listener/route file), so I cannot confirm whether any authentication middleware exists further upstream that might partially mitigate this. This should be verified in a full checkout of the repository.

// AuthorizeRequest authorizes a request using AllowListBasedAuth.
// It does NOT check if the request method is allowed.
func (r *allowListBasedAuth) AuthorizeRequest(ctx context.Context, req jsonrpc.Request[json.RawMessage]) (*AuthResult, error) {
	r.lggr.Debugw("AllowListBasedAuth authorizing request", "method", req.Method, "requestID", req.ID)
	requestDigest, err := req.Digest()
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to create digest", "method", req.Method, "requestID", req.ID, "error", err)
		return nil, err
	}
	requestDigestBytes, err := hex.DecodeString(requestDigest)
	if err != nil {
		r.lggr.Debugw("AllowListBasedAuth failed to decode digest", "method", req.Method, "requestID", req.ID, "requestDigest", requestDigest, "error", err)
		return nil, err
	}
	requestDigestBytes32 := [32]byte(requestDigestBytes)
	if r.workflowRegistrySyncer == nil {
		r.lggr.Errorw("AllowListBasedAuth workflowRegistrySyncer is nil", "method", req.Method, "requestID", req.ID)
		return nil, errors.New("internal error: workflowRegistrySyncer is nil")
	}
	allowlistedRequest, allowedRequestsStrs, err := r.findAllowlistedItemWithRetry(ctx, req, requestDigest, requestDigestBytes32)
	if err != nil {
		return nil, err
	}
	if allowlistedRequest == nil {
		r.lggr.Debugw("AllowListBasedAuth request digest not allowlisted",
			"method", req.Method,
			"requestID", req.ID,
			"digestHexStr", requestDigest,
			"allowedRequestsStrs", allowedRequestsStrs)
		return nil, errors.New("request not allowlisted")
	}
