### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's handler are read directly from unauthenticated HTTP headers and are never included in the signed payload, so an attacker who can obtain one genuinely signed webhook (e.g., by installing the app on their own store) can replay it with a forged `shop-domain` header to impersonate any other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from request headers, none of which are part of the signable string: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (which validates `hmac` against `to_signable_string`, i.e. the body) before dispatching to the handler with the unauthenticated `shop` header value: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the HMAC purely from `verifiable_query.to_signable_string` and the app's `api_secret_key` — no shop or topic binding is included: [4](#0-3) 

The identity binding that is broken is:
`hmac-authenticated bytes (raw body only)` ≠ `shop identity acted upon (request.shop header, unauthenticated)`

Since Shopify signs webhooks with the app's single `client_secret` for **every** installed shop, and the signature covers only the JSON body (not the shop domain), any two webhooks with the same body content and same app secret will produce the same valid HMAC regardless of which shop actually triggered the event. An unprivileged attacker can:
1. Install the target app on their own (attacker-controlled) development/free store — a normal, unprivileged action.
2. Trigger a webhook for a topic the app subscribes to (e.g., `orders/create`, `app/uninstalled`, GDPR webhooks), with an attacker-chosen JSON body (order contents, customer info, etc. are attacker-controlled since it's the attacker's own store).
3. Capture the resulting legitimately-signed HTTP request (valid `hmac-sha256` header for that body, produced by Shopify with the app's real `client_secret`).
4. Replay that exact body/HMAC to the app's public webhook endpoint, but with the `shopify-shop-domain` header rewritten to the victim shop's domain.

`ShopifyAPI::Utils::HmacValidator.validate` will still return `true` because it never inspects the `shop` header, so `Registry.process` invokes the app's `WebhookHandler#handle` with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled>, ...)`: [5](#0-4) 

The documented handler pattern trusts `data.shop` as the tenant identifier for downstream processing/storage: [6](#0-5) 

### Impact Explanation
This breaks the app's tenant boundary: any handler logic keyed on `data.shop` (e.g. writing order/customer data, triggering per-shop side effects, processing `app/uninstalled` or GDPR compliance webhooks) can be fed attacker-controlled content while being attributed to any victim shop the attacker names, since Shopify never binds the `shop-domain` header into the cryptographic signature. This is a cross-tenant confusion vulnerability enabled purely by the gem's `Request`/`HmacValidator` design, which validates authenticity of the body but not of the claimed originating shop.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on any store they control (a normal, unprivileged onboarding flow for most public apps) and that the app's webhook endpoint is reachable on the internet (a documented requirement of this gem's webhook processing flow). No access token, `client_secret`, or privileged account is needed — only observation/capture of one's own legitimately delivered webhook and a header rewrite on replay.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the authenticated data used for trust decisions. At minimum, `ShopifyAPI::Webhooks::Request#to_signable_string` should not be the sole trust anchor for `shop`; the gem should document/enforce that `shop` must be cross-checked against a shop the app has an active session/installation for (not just header trust), or Shopify's registered signature scheme should be extended to bind the shop domain. Consumers of `WebhookMetadata.shop` should be warned in `docs/usage/webhooks.md` that the shop value is not itself HMAC-protected and must be validated against known installed shops before being used as a tenant key.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and enables an `orders/create` webhook.
2. Shopify sends: `POST /callback/orders/create` with body `{"id":1,"note":"pwn"}` and header `shopify-hmac-sha256: <valid HMAC for that body>` and `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical body and `hmac-sha256` header to the same endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request whose `hmac` still matches (body unchanged); `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` because it only checks the body signature.
5. `ShopifyAPI::Webhooks::Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"id"=>1,"note"=>"pwn"}, ...)`, and the app processes attacker-controlled data as if it legitimately originated from `victim-shop.myshopify.com`.
