### Title
RAY value-ceiling overflow during accrual permanently freezes a whale-scale market - (File: common/src/rates/index.rs)

### Summary
Analog of the CVE-2019-10164 class (attacker-controlled value overflows a bounded buffer and crashes the system): an unprivileged address can drive a market's scaled debt/supply large enough that `scaled * index` exceeds `i128::MAX` inside interest accrual. Because every pool verb calls `global_sync` first, the resulting `MathOverflow` panic bricks the market — no supply, withdraw, borrow, repay, liquidation, or bad-debt cleanup can ever execute again, permanently freezing all supplier funds.

### Finding Description
`global_sync` runs unconditionally at the head of every mutating pool entrypoint and calls `accrue_chunk` → `accrue_step`, which computes `borrowed.mul(env, new_borrow_index)` and `supplied.mul(env, old_index)` in `calculate_supplier_rewards` and `update_supply_index` [1](#0-0) [2](#0-1) . These operands are RAY-scaled: `scaled` is `debt_base_units * 10^(27-d)` and `index` is ~`1e27+`. Their product overflows `i128` when the underlying position reaches roughly `i128::MAX / index` in RAY terms — about `1e11`-scale whole tokens for an 18-decimal asset — long before `update_borrow_index`'s `MAX_BORROW_INDEX_RAY` cap can clamp growth [3](#0-2) .

The integration test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` proves the cliff: with a billion-token supply and 98% borrowed on the XLM rate curve, accrual eventually panics with `MathOverflow`, `borrow_index < MAX_BORROW_INDEX_RAY` at the moment of failure, and subsequent `try_withdraw_raw`/`try_repay` also panic since they accrue first [4](#0-3) . There is no accrual-free escape hatch: `withdraw`, `repay`, `seize_positions`/`clean_bad_debt`, `recapitalize`, and `claim_revenue` all route through `Cache::load` + `global_sync` [5](#0-4) , and `calculate_scaled_supply`/`calculate_scaled_borrow` panic on overflow rather than saturating [6](#0-5) .

Reachability for a single unprivileged address: `supply` then `borrow` at high utilization requires only the token balance and a supply cap at or near `max_cap_for_decimals` — caps are governance parameters, and `require_cap_within_asset_domain` permits caps up to the asset-domain maximum, so the precondition is capital, not privilege. Direct token transfers to the pool cannot bypass the check since `cash` is accounting-internal.

### Impact Explanation
Permanent freezing of funds. Once `scaled * index` crosses `i128::MAX`, every entrypoint that touches the market reverts in `global_sync` before any state change, forever. All suppliers' deposits, all borrowers' collateral backing (via HF evaluation elsewhere), and unclaimed revenue in that `(hub, token)` book are irrecoverable; liquidations also fail, so underwater positions cannot be unwound, converting the freeze into eventual insolvency for the pool's other books if the market is cross-collateralized.

### Likelihood Explanation
Medium. Requires a whale-scale position (≈10^11+ whole tokens of an 18-decimal asset, or proportionally more for fewer decimals) sustained near maximum utilization for an extended accrual period on a steep rate curve. The caps must permit the position size, which is a configuration-dependent precondition. It is not triggerable on demand by a small account, but nothing in code prevents a funded attacker from constructing it, and the freeze is irreversible once reached.

### Recommendation
- Clamp before multiplying: in `accrue_step`, cap `borrowed`/`supplied` scaled values or pre-clamp `new_borrow_index` to `min(index, i128::MAX / scaled)` so the cap engages before the product overflows.
- Make `update_borrow_index` compute the cap check via division (`old_index > MAX / factor`) instead of post-multiplication, and apply the same saturating treatment to `calculate_supplier_rewards`/`update_supply_index` (e.g. `mul_div_floor_saturating` on the value path).
- Add a governance-independent safety bound on per-market scaled supply (e.g. reject `supply`/`borrow`/`multiply` when `supplied * MAX_SUPPLY_INDEX_RAY` would exceed `i128::MAX`), so the cliff is unreachable regardless of cap configuration.

### Proof of Concept
See `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`: supply `BILLION * 10^18` of `BIG18`, borrow 98% of it against `COL` collateral, then advance time until `try_update_indexes_for(&["BIG18"])` returns `MathOverflow` — with `borrow_index` still below `MAX_BORROW_INDEX_RAY`. Afterward both `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", 1.0)` panic with `MathOverflow`, demonstrating the market is permanently frozen.

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
```
