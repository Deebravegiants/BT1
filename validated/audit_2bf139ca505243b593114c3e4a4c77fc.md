### Title
Webhook `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are trusted for dispatch but are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC validated by `Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` covers exclusively the request body bytes. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which are read unauthenticated from `@headers` and forwarded directly into the merchant-facing `WebhookMetadata` used by the app's handler — are never part of the signed content.

### Finding Description
`Request#hmac` extracts the signature from the `x-shopify-hmac-sha256`/`shopify-hmac-sha256` header, and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Registry.process` validates only this HMAC (over the body) and then dispatches the handler using `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`, all of which are pulled straight from unauthenticated headers: [2](#0-1) 

The identity binding that should hold is:
`shop-domain header used for handler dispatch == shop-domain bytes covered by the HMAC`

but in this gem the equality is:
`shop-domain header used for handler dispatch != any byte covered by the HMAC` (HMAC only covers `@raw_body`)

Because the app's `client_secret` (`api_secret_key`) is shared across every shop that has installed the app, any unprivileged user who has installed the app on their own store can legitimately receive a webhook with a valid `(raw_body, hmac)` pair signed with that shared secret. That same `(raw_body, hmac)` pair remains cryptographically valid regardless of which `shop-domain`/`topic`/`webhook-id` headers accompany it, since those headers are excluded from `to_signable_string`. The attacker can therefore resend the exact body/HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `topic`/`webhook-id`) with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only recomputes the HMAC over the (unchanged) body: [3](#0-2) 

The app's webhook handler then executes attacker-supplied body content under the impersonated victim shop's identity (`WebhookMetadata#shop`), since nothing in the library ties the authenticated bytes to the shop the handler believes it received.

### Impact Explanation
This crosses a tenant boundary: an attacker with only their own (unprivileged) shop installation can cause the app to process fabricated/replayed webhook data attributed to a victim merchant it has no relationship with, satisfying the "cross-tenant access" criterion. Depending on how the host app's webhook handlers act on `shop`/`topic` (e.g. updating per-shop state, billing records, order data, or uninstall/GDPR flows keyed by `shop-domain`), this can lead to cross-tenant data corruption or unauthorized state changes for a shop the attacker does not control.

### Likelihood Explanation
Webhook endpoints are, by design, public internet-facing endpoints that must accept unauthenticated POSTs from "Shopify," so the only trust boundary is the HMAC. Obtaining one valid `(raw_body, hmac)` pair requires nothing more than installing the app on any shop (a normal, unprivileged action) and observing a webhook that is delivered to that shop — which is trivial and expected app-usage behavior, not a privileged operation.

### Recommendation
Bind the shop/topic identity into the signed content check, or otherwise cryptographically tie the accepted headers to the request: e.g., after validating the body HMAC, additionally verify that the `shop-domain` header matches an app-known/authorized shop for the current session/webhook subscription, or extend the signable string to include the identifying headers (matching what Shopify actually signs, if Shopify's HMAC scheme allows it) so header tampering invalidates the signature. At minimum, document that `request.shop`/`request.topic` are unauthenticated and must be independently verified against the app's own installation records (e.g. an existing offline session for that shop) before being trusted by handler logic.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` (unprivileged, self-service).
2. Shopify sends a legitimate webhook to the app's endpoint: `raw_body = "{...attacker-controlled fields...}"`, headers include `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker captures this exact `(raw_body, H)` pair.
4. Attacker sends a new HTTP request directly to the app's public webhook URL with the same `raw_body` and `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only (per `to_signable_string`) — it matches `H`, so validation passes.
6. `handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: parsed_body, ...))` is invoked, and the app processes attacker-controlled body content as if it were an authentic webhook from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
