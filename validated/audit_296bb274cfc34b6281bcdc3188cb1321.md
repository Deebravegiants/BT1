### Title
Missing Chainlink L2 sequencer-uptime check in `SimplexPaymaster` allows gas mispricing / paymaster fund drain during sequencer downtime - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice()` validates only that a Chainlink answer is positive and not older than `maxOracleAge`, but never checks whether the L2 sequencer is up (or has just come back up), even though the paymaster is explicitly designed to be deployed on L2s such as Base, Optimism and Arbitrum.

### Finding Description
`_getOraclePrice` is the sole gate on Chainlink data used to price gas: [1](#0-0) 

It only reverts on a non-positive answer or on `block.timestamp - updatedAt > maxOracleAge`. There is no call to an L2 sequencer-uptime feed (`0xBCF85224fc0756B9Fa45aA7892530B47e10b6433`-style feeds) and no post-restart grace period, unlike the pattern Chainlink recommends for L2 deployments (the exact class of bug in the referenced report).

The paymaster's own documentation and configuration confirm L2 deployment: `Params.nativeOracle` comment lists "BNB/USD on BSC, ETH/USD on Ethereum, etc." and staleness bounds vary "BSC stablecoins ~27s, Base/Ethereum stablecoins up to 24h": [2](#0-1) 

The SDK's Chainlink feed registry independently confirms Base, Optimism and Arbitrum mainnet/testnet deployments consume these same aggregator addresses: [3](#0-2) 

`_getOraclePrice` is invoked from `_tokenPrice`, which is used both in the validation-time pricing path (`_fetchDetails`) that determines how many ERC-20 tokens a UserOp sender pays for gas, and in the treasury-only `swapAndDeposit` fee-recycling path: [4](#0-3) [5](#0-4) 

A repo-wide search confirms there is no sequencer-uptime handling anywhere in the codebase (`grep` for "sequencer" only matches unrelated Arbitrum/OP-stack consensus-client code, not the paymaster oracle path).

When an Arbitrum/OP-stack sequencer goes down and later resumes, Chainlink price feeds on that L2 can continue to report a stale `answer`/`updatedAt` pair that still satisfies `block.timestamp - updatedAt <= maxOracleAge` (because L2 timestamps themselves stall or catch up in a burst), even though the true off-chain market price has since moved substantially. Absent a sequencer check, `_getOraclePrice` will accept this out-of-date price as valid.

### Impact Explanation
Because `_tokenPrice` derives `tokenPrice` directly from `nativeUsd`/`tokenUsd` without any sequencer-liveness gating, any unprivileged UserOp submitter (a "bandwidth purchaser" paying gas through the paymaster) can submit operations during a sequencer-down/recovery window and be charged based on a stale exchange rate. If the native asset has appreciated relative to the stable token while the sequencer was down, the sender pays fewer tokens than the true gas cost, draining native ETH the paymaster deposited at the `EntryPoint` (funded by the treasury) for under-value ERC-20 tokens. This is a direct, repeatable value-extraction/fund-drain vector against a Hyperbridge-governed paymaster contract, reachable from a single unprivileged UserOp.

### Likelihood Explanation
Likelihood depends on an L2 sequencer downtime/recovery event, which is not attacker-controlled but does occur periodically on Optimism/Arbitrum/Base. Once such a window opens, exploitation requires no privilege — any address can submit a UserOp with paymasterData referencing a registered token, so likelihood of exploitation conditional on a sequencer event is high, and the paymaster explicitly targets these L2 chains.

### Recommendation
Add an L2 sequencer-uptime feed check (per Chainlink's documented pattern) to `_getOraclePrice`, reverting or forcing a grace-period delay when `answer == 1` (sequencer down) or when less than a configured grace period (e.g. 1 hour) has elapsed since the sequencer's `startedAt` came back up, mirroring the existing `StaleOraclePrice`/`InvalidOraclePrice` guards already present in `SimplexPaymaster.sol`.

### Proof of Concept
1. Deploy `SimplexPaymaster` on an OP-stack/Arbitrum L2 with a registered stablecoin and `nativeOracle`.
2. Simulate sequencer downtime by having the mocked native/token Chainlink aggregators (as in `MockOracle` from `evm/tests/foundry/SimplexPaymasterTest.t.sol`) keep `updatedAt` within `maxOracleAge` while `answer` no longer reflects the true off-chain price (i.e., the sequencer resumed but the feed hasn't caught up, or caught up with a burst update that stays within the staleness window).
3. Submit a UserOp with `paymasterData` mode `0x00`/`0x02` referencing that token; `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` accepts the stale-but-"fresh-enough" price and computes `tokenPrice` favorable to the sender.
4. The `_postOp` charges the sender fewer ERC-20 tokens than the true gas cost, while the paymaster's native `EntryPoint` deposit is debited at the real cost, draining paymaster-held native funds over repeated UserOps during the window.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
