### Title
Webhook `shop` (and `topic`/`api-version`) headers are trusted for tenant routing but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the shop identity (`shop-domain` header) used for tenant routing in `ShopifyAPI::Webhooks::Registry.process` is read from an unsigned HTTP header. This breaks the intended binding `HMAC(secret, signed_bytes) == HMAC(secret, bytes_that_determine_the_tenant)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `#topic`, `#api_version`, `#webhook_id`) are read straight from HTTP headers, which are never included in the signed material: [2](#0-1) 

`HmacValidator.validate` only ever authenticates `verifiable_query.to_signable_string` (i.e., the body) against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` verifies the HMAC and then unconditionally trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the host application's handler, which uses it as the tenant identifier for that webhook payload: [4](#0-3) 

Because `shop-domain` is not part of the signed bytes, the equality the code implicitly relies on — `shop header the app trusts == shop that produced/authorized this HMAC` — does not hold. Anyone who can obtain one genuine `(raw_body, hmac)` pair signed with the app's secret (e.g., by installing the app on their own store and capturing a real webhook delivery to their own endpoint, or via any endpoint that echoes back a signed body) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will hand the attacker-chosen body to the handler tagged with an attacker-chosen `shop`, i.e. a different merchant's tenant identity.

### Impact Explanation
This is a cross-tenant confusion vector: a multi-tenant host application built on this gem processes webhook data using `WebhookMetadata#shop` as the tenant key without any cryptographic guarantee that the body was actually generated for that shop. An attacker who owns any single shop that has this app installed can forge webhook deliveries that the app attributes to a shop of the attacker's choosing, potentially causing state (orders, inventory, GDPR/compliance triggers, uninstall flows, etc.) to be written into or acted upon on behalf of a victim tenant. This satisfies the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Requires only an unprivileged internet user who can install the app on any store to obtain one genuine `(body, hmac)` pair (something the gem's own webhook docs/design expect every merchant to be able to generate for themselves), plus the ability to POST directly to the app's public webhook endpoint with custom headers — no access token, `api_secret_key`, or privileged account required.

### Recommendation
Bind the tenant-identifying header(s) into the signed material, e.g. compute/verify the HMAC over `shop-domain` + `topic` + body (as Shopify's own webhook verification guidance recommends double-checking `shop` against the authenticated session/registration), or otherwise cross-check `request.shop` against an independently known, already-authenticated shop before dispatching to handlers in `Registry.process`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a genuine webhook delivery, i.e. `raw_body` and its `shopify-hmac-sha256` header (correctly HMAC'd with the app's real `api_secret_key`).
2. Replay this same `raw_body` + `shopify-hmac-sha256` to the app's public webhook endpoint, but set `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` builds the request object; `Utils::HmacValidator.validate` succeeds because it only checks the (unchanged) body against the (unchanged, still-valid) HMAC (`lib/shopify_api/utils/hmac_validator.rb:12-31`).
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...))` (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the host application to act on `victim.myshopify.com`'s tenant context with attacker-supplied body content.

        def validate(verifiable_query)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
