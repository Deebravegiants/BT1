### Title
Anyone can permanently invalidate another user's signed Emporium operation via `cancelEmporiumMessage` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`cancelEmporiumMessage()` is intended to let the original signer of an `EmporiumOperation` burn their own `emporiumMessage` nonce before it is executed [1](#0-0) . However, the function only checks that the caller can produce a valid EIP-712 signature over the cancel struct that recovers to `msg.sender` — it never checks that `msg.sender` (or the recovered address) matches the `signerAddress` that actually authorized the corresponding `EmporiumOperation`. Because any address can trivially self-sign a message with its own key, any unprivileged EOA can call this function with an arbitrary `emporiumMessage` value belonging to someone else and mark it used, permanently blocking that legitimate signed operation from ever executing.

### Finding Description
The check is: [2](#0-1) 

```
function cancelEmporiumMessage(uint256 emporiumMessage, uint8 v, bytes32 r, bytes32 s) external {
    ...
    bytes32 hashedMessage = _hashTypedDataV4(
        keccak256(abi.encode(EMPORIUM_CANCEL_TYPEHASH, emporiumMessage))
    );
    (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(hashedMessage, v, r, s);
    bool verified = err == ECDSA.RecoverError.NoError && recoveredAddress == msg.sender;
    if (!verified) revert InvalidSignature();
    $.usedMessages[emporiumMessage] = true;
}
```

`recoveredAddress == msg.sender` is not a meaningful authorization check: `msg.sender` can generate a fresh signature over `keccak256(EMPORIUM_CANCEL_TYPEHASH, emporiumMessage)` for *any* `emporiumMessage` value using their own private key, and `ecrecover` will always return `msg.sender` for that self-produced signature. There is no binding to the actual `stack.signerAddress` that signed the original `EmporiumOperation` in `verifyWallet()` [3](#0-2) . Consequently, the "signature verification" degenerates into a no-op access-control gate — exactly analogous to the referenced report where a critical state-changing function lacked real access control (there, anyone could call `updateBaseRate`; here, anyone can "authenticate" as though they were any signer for any `emporiumMessage`).

Once `usedMessages[emporiumMessage]` is set to `true` by the attacker, the real operation can never execute, because `verifyWallet()` unconditionally reverts on a used message: [4](#0-3) 

### Impact Explanation
This breaks the intended invariant that "no one else can cancel [a message] for them" (per the function's own doc comment) [5](#0-4) . An attacker who learns (or guesses/front-runs) a pending `emporiumMessage` nonce used by a legitimate user's signed off-chain `EmporiumOperation` can permanently freeze that operation before it is ever relayed/executed on-chain — this is a permanent freezing of the user's intended fund movement/relay execution, since the nonce can never be reused. This qualifies as High severity impact: permanent freezing of a wallet owner's authorised operation, unauthorised interference with an action the signer never consented to be cancelled.

### Likelihood Explanation
Likelihood depends on the attacker being able to observe `emporiumMessage` values ahead of execution (e.g., via mempool monitoring of the relay's `transact` calldata, or via off-chain infrastructure leaks), similarly to how block-delta-based griefing windows are exploited in the referenced report. Given Hinkal's meta-transaction/relay architecture (calldata visible before finality), an attacker monitoring pending transactions can front-run the legitimate relayer submission with their own `cancelEmporiumMessage` call using a self-signed signature, at negligible cost (one cheap tx, no special privilege required).

### Recommendation
Bind the cancellation authorization to the actual original signer, not to an arbitrary self-signed wrapper:
- Require the caller/recovered signer to equal the `signerAddress` stored/derivable for that specific `emporiumMessage` (e.g., store the intended signer alongside the message when first observed, or require the cancel call to include the full `EmporiumOperation`/stack data and re-derive `stack.signerAddress`, then check `recoveredAddress == stack.signerAddress`).
- Alternatively, require `EMPORIUM_CANCEL_TYPEHASH` to be signed by the same key used in the original `EMPORIUM_SIGNATURE_TYPEHASH`, and verify against that specific signer address passed as an explicit parameter, rather than trusting `msg.sender`.

### Proof of Concept
1. Alice signs an `EmporiumOperation` set off-chain with nonce `emporiumMessage = M` and submits it (or a relayer holds it pending) intending to call `verifyWallet` via `runAction`.
2. Attacker Bob (no relation to Alice, no special role) observes `M` in the pending calldata.
3. Bob computes `hashedMessage = _hashTypedDataV4(keccak256(abi.encode(EMPORIUM_CANCEL_TYPEHASH, M)))` and signs it with his own private key, producing `(v, r, s)` such that `ecrecover(hashedMessage, v, r, s) == Bob`.
4. Bob calls `cancelEmporiumMessage(M, v, r, s)`. The check `recoveredAddress == msg.sender` passes because `msg.sender == Bob == recoveredAddress`.
5. `usedMessages[M] = true` is now set.
6. When Alice's transaction is later submitted, `verifyWallet` reverts with `UsedMessage()`, permanently blocking Alice's authorized operation. [6](#0-5)
