### Title
BEEFY consensus verifier counts duplicate authority votes toward the 2/3+1 supermajority threshold, allowing a minority relay-chain authority set (or a single compromised relayer resubmitting the same authority's signature multiple times) to forge state-machine commitment updates - ([File: evm/src/consensus/EcdsaBeefy.sol], [File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
The BEEFY consensus verifiers (both the Solidity `EcdsaBeefy` contract used by EVM `HandlerV2`/`IHost`, and the Rust `verify_mmr_update_proof` used by `ismp-beefy` on Substrate) compute the supermajority threshold purely from the *length* of the submitted vote/signature array (`sigLen` / `signatures_length`), without ever checking that the `authorityIndex` values inside that array are unique. This is analogous to the reported `DataMarket.submitBatchAttestation` bug, where a single validator's vote could be counted more than once toward finalizing a batch because there was no per-voter dedup guard.

### Finding Description
In `evm/src/consensus/EcdsaBeefy.sol::verifyMmrUpdateProof`: [1](#0-0) 
`sigLen` is taken directly from `relayProof.signedCommitment.votes.length` and fed straight into `checkParticipationThreshold(sigLen, authoritySet.len)` before any signatures are recovered or leaves are built. Each `Vote` in the array is independently ECDSA-recovered and turned into a `MerkleMultiProof.Leaf{index: vote.authorityIndex, hash: keccak256(authority)}` — there is no `require`/loop that rejects a repeated `authorityIndex` (or repeated signature) among the `votes` entries before counting it toward `sigLen`.

The Rust equivalent has the same shape: [2](#0-1) 
`signatures_length` (`mmr.signed_commitment.signatures.len()`) is checked against `check_participation_threshold` with no uniqueness constraint on `sig.index`, and the loop that follows (lines 146-162) builds `authority_leaves`/`authority_indices` from every signature entry, again without deduplication.

This is the exact bug class from the report: the count used to decide "have we reached quorum" is derived from raw submission count rather than the count of *distinct* validators/authorities. Contrast this with the sibling Pharos verifier in the same codebase, which *does* have this exact guard: [3](#0-2) 
`verify_validator_membership` explicitly deduplicates participant keys and returns `Error::DuplicateParticipant` if any repeat — proving the codebase is aware of this bug class and has patched it in one consensus client but not in the BEEFY (EVM ECDSA and Substrate) client.

Whether a duplicated `(authorityIndex, signature)` pair can additionally slip through `MerkleMultiProof.VerifyProof` depends on the external `solidity-merkle-trees`/`rs_merkle` library's handling of repeated leaf indices, which is vendored outside this repo and could not be inspected here. If that library tolerates (or is not defensively hardened against) duplicate index entries in the leaf set — e.g., treats each duplicate as an independent valid inclusion of the same already-verified leaf — the threshold check is bypassable with fewer than 2/3+1 *distinct* authorities. This uncertainty is the main gap in fully proving exploitability end-to-end from the code available in this repo.

### Impact Explanation
BEEFY is the trust root for `EvmHost`/`HandlerV2` state-machine commitment updates (via `IConsensusV2.verify`) and for the Substrate `ismp-beefy` client. If quorum can be satisfied by resubmitting fewer distinct authorities' signatures multiple times, an attacker (a relayer submitting the consensus proof — an unprivileged, permissionless role reachable by anyone) could push a forged/unsound `StateCommitment` or a forged authority-set rotation into `EvmHost`/pallet-ismp, from which all downstream message delivery, state proofs, and token bridge mint/burn decisions are derived. This maps directly to "unsound state commitment" / "forged message delivery" impact categories.

### Likelihood Explanation
Likelihood depends entirely on whether the underlying merkle multi-proof implementation actually accepts duplicate leaf/index entries as valid inclusion proofs for the same original commitment (this repo doesn't vendor `solidity-merkle-trees`, so it can't be conclusively verified here). If the library naturally rejects duplicate indices (most multi-proof algorithms assume a strictly increasing/unique index set and would produce a mismatched root when an index is repeated), this specific vector is not exploitable as described, and the missing explicit check is a defense-in-depth gap rather than an immediately exploitable bug. Given this significant uncertainty in the exploit chain (unlike the original `DataMarket` report, which had a concrete, self-contained PoC), confidence here is lower than the reference report.

### Recommendation
Add an explicit uniqueness check on the submitted authority indices before counting them toward `sigLen`/`signatures_length`, mirroring the `verify_validator_membership` pattern already used in `modules/consensus/pharos/verifier/src/lib.rs`:
- In `EcdsaBeefy.sol::verifyMmrUpdateProof`, before computing `sigLen`/before calling `checkParticipationThreshold`, dedupe `vote.authorityIndex` (e.g., via a bitmap/seen-set) and revert on any repeat.
- In `modules/consensus/beefy/verifier/src/lib.rs::verify_mmr_update_proof`, add an equivalent `BTreeSet`-based dedup check over `sig.index` before computing `signatures_length` and before threshold verification, returning a new `Error::DuplicateParticipant`-style variant on failure.

### Proof of Concept
A fully concrete PoC could not be constructed with certainty because the exploitability hinges on the external `solidity-merkle-trees`/`rs_merkle` multi-proof verifier's behavior with duplicate leaf indices, which is not vendored in this repository and could not be inspected. Conceptually the attack shape is:
1. Attacker (any permissionless relayer) collects signatures from `k < 2/3*N + 1` distinct BEEFY authorities.
2. Attacker duplicates one or more `(authorityIndex, signature)` pairs in `RelayChainProof.signedCommitment.votes` so `votes.length >= 2/3*N + 1`.
3. `checkParticipationThreshold(sigLen, authoritySet.len)` passes on the inflated count.
4. If `MerkleMultiProof.VerifyProof` does not itself reject repeated indices in the leaf set, the forged proof is accepted, and an attacker-chosen `StateCommitment`/authority-set rotation is stored via `HandlerV2`/`EvmHost`.

This should be validated by a Devin session with access to the vendored `solidity-merkle-trees` and `rs_merkle` crate sources to confirm step 4's feasibility, and by writing a Foundry test against `evm/tests/foundry/Beefy.sol` that submits a `RelayChainProof` with a duplicated `Vote` entry.

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
