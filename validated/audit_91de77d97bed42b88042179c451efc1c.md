### Title
Deposit/Withdraw/Swap instructions transfer a caller-specified amount without verifying vaults actually received it, allowing fee-on-transfer (Token-2022) tokens to cause LP over-minting and pool insolvency - (File: `program/src/processor.rs`, `program/src/invokers.rs`)

### Summary
`process_deposit`, `process_withdraw`, `process_swap_base_in`/`process_swap_base_out` (and their V2 variants) compute `deduct_coin_amount`/`deduct_pc_amount`/`swap_amount_out`/etc. from pool-state math and then issue an SPL-token `Transfer` for that exact requested amount, unconditionally assuming the destination account's balance increases by the full amount transferred. There is no balance-before/balance-after check on the receiving vault or destination token account.

### Finding Description
In `process_deposit`, the amount of `STAKING`-style vault deposit is computed (`deduct_coin_amount`, `deduct_pc_amount`) and the corresponding LP amount to mint (`mint_lp_amount`) is derived purely from these requested amounts and current vault balances *before* the transfer occurs: [1](#0-0) 
The program then transfers `deduct_coin_amount`/`deduct_pc_amount` via `Invokers::token_transfer`, and immediately mints `mint_lp_amount` LP tokens to the depositor, without re-reading the vault's actual received balance: [2](#0-1) 

The same fixed-amount-transfer assumption appears in withdraw: [3](#0-2) 

and in all four swap paths (`SwapBaseIn`, `SwapBaseOut`, and their V2 variants), where `swap.amount_in`/`swap_in_after_add_fee` is transferred into the vault and `swap_amount_out`/`swap.amount_out` is immediately transferred out based on pre-transfer pool-balance math: [4](#0-3) [5](#0-4) 

The underlying primitive is `Invokers::token_transfer`, which just issues `spl_token::instruction::transfer` for the exact `deposit_amount` and returns success without inspecting resulting balances: [6](#0-5) 

If the mint used for `coin`/`pc` is a fee-on-transfer token (e.g., an SPL Token-2022 mint with the `TransferFee` extension, or any deflationary token compatible with the classic `spl_token::instruction::transfer` interface at the account-data level the program checks), the vault will receive strictly less than the amount the program assumes. Because `mint_lp_amount` (deposit) or `swap_amount_out` (swap) is computed from the *intended* transfer amount rather than the *actual* balance delta, the pool state becomes decoupled from real vault holdings: LP tokens get minted against value the pool never actually received, and swap outputs are calculated as if the pool received the full `amount_in`, when it actually received less. Over repeated deposit/swap cycles this depletes real backing per LP token and can drain the pool for later LPs/swappers.

### Impact Explanation
This breaks solvency invariants central to the AMM: LP token supply becomes decoupled from real vault backing, allowing a depositor to receive full-value LP tokens while the pool coffers hold less than expected (effectively diluting/robbing other LPs), and swappers using such a mint would receive quoted `amount_out` computed against a pool that never actually absorbed the full `amount_in`, corrupting the constant-product invariant (`InvariantToken`/`InvariantPool`) that both deposit-ratio and swap-price math depend on. This is reachable by any ordinary user with a single transaction (`Deposit`/`SwapBaseIn`/`SwapBaseOut`) supplying attacker-chosen token accounts backed by a fee-on-transfer mint, and results in unbacked LP minting / insolvent pool accounting affecting all pool participants — matching the "Medium/High, concrete theft or insolvent accounting" bar.

### Likelihood Explanation
Likelihood depends entirely on whether a pool can be created/paired with a fee-on-transfer mint (e.g., Token-2022 with `TransferFeeConfig`). The scope's `invokers.rs` token CPIs use the plain `spl_token::instruction::transfer` (not `transfer_checked`), and I was unable to fully confirm within the available index whether `process_initialize2`/deposit/swap explicitly reject non-classic-`spl_token` mints/token-program IDs (i.e., whether Token-2022 fee-bearing mints are excluded at pool-creation time). If such an explicit program-id/mint check exists and strictly enforces classic SPL Token (no transfer-fee extension possible), the practical likelihood is low; if it does not, any coin/pc mint chosen at pool creation with a transfer fee makes this trivially and repeatedly exploitable. Given the uncertainty, this should be treated as a real risk to validate against the actual `Initialize2`/mint validation logic.

### Recommendation
Read and record the destination (vault or receiving user token account) balance immediately before and after each `Invokers::token_transfer`/`token_transfer_with_authority` call, and use the *actual* received/sent delta (not the requested `amount`) for all downstream `mint_lp_amount`, `swap_amount_out`, and pnl/target-orders accounting. Alternatively/additionally, explicitly reject any coin/pc/lp mint whose token program is not the canonical `spl_token` program with no transfer-fee-like extensions (i.e., disallow Token-2022 mints with `TransferFeeConfig`), and document this restriction, mirroring the referenced report's "will not support deflationary tokens" mitigation stance.

### Proof of Concept
1. Attacker creates (or uses) an AMM pool where the `coin` mint is a fee-on-transfer SPL Token-2022 mint with e.g. a 5% transfer fee, paired with a normal `pc` mint.
2. Attacker calls `Deposit` with `max_coin_amount = 100_000`. `process_deposit` computes `deduct_coin_amount = 100_000` and a proportional `mint_lp_amount` based on the pool's current `total_coin_without_take_pnl` (pre-transfer) at [7](#0-6) .
3. `Invokers::token_transfer` moves `100_000` coin tokens from the user, but due to the 5% fee only `95_000` actually lands in `amm_coin_vault_info` at [8](#0-7) .
4. The program still mints the full `mint_lp_amount` computed against the assumed `100_000` deposit at [9](#0-8) , over-crediting the depositor's LP share relative to what the pool actually holds.
5. Repeating this (or performing a swap where `amount_in` is taxed on the way in but `amount_out` is paid out in full per the pre-transfer quote) progressively drains real backing from the pool, at the expense of other LPs/swappers who later redeem/trade against the now-insolvent vault balances.

    pub fn token_transfer<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        owner: AccountInfo<'a>,
        deposit_amount: u64,

        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            owner.key,
            &[],
            deposit_amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, owner, token_program],
            &[],
        )
    }
