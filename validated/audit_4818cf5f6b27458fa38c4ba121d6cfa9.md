### Title
Anyone can drain stranded ETH/token balances from the shared `CallDispatcher` contract via its unrestricted `dispatch()` function - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch()` is a fully `external`, permissionless function with no caller restriction (no `onlyOwner`, `onlyGateway`, or similar modifier). It accepts an arbitrary `Call[]` array and executes each call using the contract's own held ETH balance (`call.value`) and arbitrary `call.data`/`call.to`. Because the same `CallDispatcher` instance is shared across `IntentGatewayV2`/`IntentsBase` order flows (referenced via `_params.dispatcher`) and can end up holding native ETH or ERC20 balances that are not fully swept back by the gateway's bookkeeping, anyone can call `dispatch()` directly to sweep out whatever balance currently sits in the contract to an address of their choosing — exactly analogous to the reported `D3Proxy.refundETH()` issue where an unrestricted withdrawal function drains a shared contract's balance.

### Finding Description
`CallDispatcher.dispatch()` is defined with no access control at all: [1](#0-0) 

It loops over caller-supplied `Call` structs and executes `to.call{value: call.value}(call.data)`, forwarding the contract's own balance as dictated purely by attacker input, the only check being that `to` has code (`extcodesize(to) != 0`). There is no restriction limiting the caller to `IntentGatewayV2`/`IntentsBase` or to any privileged relayer/admin.

The contract is designed to *temporarily* hold funds during order execution: predispatch assets are transferred to it before being executed and swept back, and postdispatch output calldata is executed on it in `_execute()`: [2](#0-1) 

Critically, the postdispatch sweep in `_execute()` only iterates over `outputsLen` — i.e., only the token addresses explicitly listed in `order.output.assets` — and re-invokes `dispatch()` a second time to sweep those balances back to the gateway: [3](#0-2) 

Any native ETH or ERC20 token produced by `order.output.call` execution that is **not** one of the tokens listed in `order.output.assets` (e.g., an intermediate swap hop token, reward token, dust from a DEX router, or a gas/ETH refund not matching any listed output asset) is left stranded in the `CallDispatcher` — the sweep logic has no way to discover or recover it. Because `dispatch()` has no access control, that stranded balance (and any other balance that lands on the contract via its `receive()` function) is then freely withdrawable by any third party who calls `CallDispatcher.dispatch()` directly with a `Call` transferring the balance to an address they control.

### Impact Explanation
Any ETH or ERC20 tokens left behind in the shared, permissionless `CallDispatcher` — whether from imperfect output-asset accounting in `_execute()`, unswept predispatch dust, or accidental direct transfers to the contract's `receive()` — can be permanently stolen by any unprivileged address, since `dispatch()` places no restriction on the caller and fully controls the destination and value of outgoing calls funded by the contract's balance. This is a direct loss-of-funds vector reachable from a single unprivileged transaction, matching the reported bug class (unrestricted withdrawal function on a shared periphery contract).

### Likelihood Explanation
The `CallDispatcher` is a shared, reusable infrastructure contract referenced by multiple order-processing paths (predispatch and postdispatch execution in both `IntentGatewayV2.sol` and `intentsv2/IntentsBase.sol`). Any deployment where postdispatch calldata produces a token/asset outside the declared `order.output.assets` list, or where any ETH/token transfer to the dispatcher isn't fully consumed within the same call, creates an immediately and permanently exploitable balance — requiring no privileged access, no timing race, and no cooperation from the gateway or its users; an attacker simply monitors the `CallDispatcher`'s balance and calls `dispatch()`.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by an authorized/registered gateway address (e.g., an `onlyAuthorizedCaller` modifier configured at deployment or via an allow-list), and additionally have `_execute()` sweep the *entire* remaining native and token balance for any asset touched by the postdispatch call (not just the ones enumerated in `order.output.assets`) before returning control, so no residual balance is ever left on the shared dispatcher.

### Proof of Concept
1. A solver fills a cross-chain order whose `order.output.call` swaps through an intermediate token or DEX route that leaves a small amount of an unlisted token (or ETH) on the `CallDispatcher` after execution — this is not swept back because `_execute()` in `evm/src/apps/intentsv2/IntentsBase.sol:504-533` only sweeps addresses present in `order.output.assets`.
2. An attacker observes the `CallDispatcher`'s balance (ETH or the stranded ERC20) and, in a follow-up transaction, calls `CallDispatcher.dispatch(abi.encode(calls))` directly — bypassing `IntentGatewayV2`/`IntentsBase` entirely — with `calls = [Call({to: attackerContract, value: strandedBalance, data: ""})]` (or an ERC20 `transfer` call to itself for token dust).
3. Since `dispatch()` in `evm/src/utils/CallDispatcher.sol:44-62` has no access control, the call succeeds and the stranded funds are transferred to the attacker, permanently removing them from the protocol/legitimate beneficiaries.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

                revert NotContract(to);
            }

        }
