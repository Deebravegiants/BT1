## Analysis

The reported bug class is: a value-bearing account/parameter (Mango's `RootBank`) that participates in a financial calculation is never checked against the trusted source of truth, so a party can substitute a different account between two calls of the same flow and pocket the difference. The strongest analog in this repo is in Hinkal's Emporium wallet-authorization mechanism, where the wallet owner's EIP-712 signature caps a fee amount (`maxFee`) but never binds which **token** that fee is denominated in. [1](#0-0) 

`EMPORIUM_SIGNATURE_TYPEHASH` only commits to `emporiumMessage`, the hash of `stack.ops`, `stack.maxFee`, and `stack.deadline` [2](#0-1) . `verifyWallet` enforces only `circomData.feeStructure.flatFee <= stack.maxFee` [3](#0-2) , but `circomData.feeStructure.feeToken` (the ERC20 the fee is actually paid in) is not part of the signed struct at all. `payRelayFees` then uses that unconstrained `feeToken` to pull `flatFee` units directly out of the user's on-chain wallet via `doSendToRelay`: [4](#0-3) 

### Title
Emporium wallet fee signature does not bind `feeToken`, allowing relay-controlled token substitution to drain wallet funds - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
The Emporium EIP-712 wallet authorization signs a numeric `maxFee` cap but never signs the ERC20 token that fee is paid in. A relay/prover can present a `feeStructure.feeToken` different from what the wallet owner intended while keeping the numeric `flatFee` under the signed `maxFee`, causing `doSendToRelay` to pull that amount of a more valuable/lower-decimal token from the user's wallet — funds the signer never actually authorized to be moved.

### Finding Description
`verifyWallet` recovers the signer from a struct that includes only `emporiumMessage`, `_hashEmporiumOps(stack.ops)`, `stack.maxFee`, `stack.deadline` [5](#0-4) . It checks `circomData.feeStructure.flatFee > stack.maxFee` but performs no check on `circomData.feeStructure.feeToken` [3](#0-2) . `feeStructure` (including `feeToken`) is supplied as part of `CircomData`, which is assembled by whoever submits the `transact()` call (the relay), and `payRelayFees` uses it directly to select which token to withdraw from the signer's wallet: [6](#0-5) , calling `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)` [4](#0-3) .

This breaks the equality the wallet owner intended when signing: "at most `maxFee` value of the agreed fee token may leave my wallet." Since token identity is not part of the signed data, `maxFee` numeric units can be reinterpreted against any ERC20 (different decimals/market value), so the same signed number authorizes wildly different economic amounts depending on which `feeToken` the relay chooses — exactly analogous to the Mango issue where an unconstrained `RootBank` (account/asset identity) let an attacker apply one exchange rate on deposit and a different, mismatched one on withdrawal for outsized profit.

### Impact Explanation
This lets a relay execute an unauthorized asset movement out of a user's Hinkal wallet beyond what the wallet owner signed for, i.e., theft of value the signer never approved. This matches "High - theft ... of protocol/relay fees ... executing calls or moving assets a wallet owner or prover never authorised."

### Likelihood Explanation
Exploitability depends only on the entity assembling `CircomData.feeStructure` for a given `transact()` call (typically the relay) choosing an unexpected `feeToken` while keeping the numeric `flatFee` ≤ the signed `maxFee`. No admin/owner key is needed; only a standard whitelisted relay role, which the threat model treats as semi-trusted but not authorized to move arbitrary wallet value.

### Recommendation
Include `feeStructure.feeToken` (and ideally the full `feeStructure`) inside `EMPORIUM_SIGNATURE_TYPEHASH` so the signer explicitly commits to which token can be pulled, not just a bare numeric cap.

### Proof of Concept
1. Wallet owner signs an `EmporiumStack` with `maxFee = 100` expecting fees to be paid in USDC (6 decimals ⇒ $100).
2. Relay submits `transact()` with the same signed `stack` but sets `circomData.feeStructure.feeToken` to a token the wallet holds with fewer decimals / higher unit value (e.g., WBTC), and `flatFee = 100` (same raw units, satisfying `flatFee <= maxFee`).
3. `verifyWallet` passes because it never checks `feeToken`.
4. `payRelayFees` → `sendToRelayFromWallet` → `doSendToRelay` withdraws 100 units of WBTC from the wallet to the relay — vastly more value than the $100 the signer intended to authorize.

Note: I was unable to inspect `IHinkalWallet.doSendToRelay`'s implementation in the index (not returned by search), so the exact wallet-side enforcement (if any) of token/amount limits could not be fully verified; if the wallet implementation independently checks fee token/amount, this reduces the practical severity. A Devin session with full repo access should confirm the wallet implementation before treating this as fully confirmed.

    function _hashEmporiumOps(
        EmporiumOperation[] memory ops
    ) private pure returns (bytes32) {
        bytes32[] memory opHashes = new bytes32[](ops.length);
        for (uint256 i = 0; i < ops.length; i++) {
            opHashes[i] = keccak256(
                abi.encode(
                    EMPORIUM_OPERATION_TYPEHASH,
                    ops[i].endpoint,
                    ops[i].invokeWallet,
                    ops[i].value,
                    keccak256(ops[i].callData)
                )
            );
        }
        return keccak256(abi.encodePacked(opHashes));
    }

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
