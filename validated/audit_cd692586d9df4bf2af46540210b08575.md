### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing on replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` attribute that is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but `Registry.process` only validates the HMAC over the raw request body, never over the shop header. The `shop` value is then trusted and forwarded, unauthenticated, into `WebhookMetadata` for the host app's webhook handler.

### Finding Description
`Utils::HmacValidator.validate` is applied to the incoming `Request` object in `Registry.process`: [1](#0-0) 

The HMAC check calls `verifiable_query.to_signable_string`, and for a webhook `Request`, that method returns only `@raw_body` — nothing else: [2](#0-1) 

Meanwhile, `shop` is read straight from an HTTP header that is never mixed into the signed material: [3](#0-2) 

After HMAC validation succeeds, `Registry.process` builds `WebhookMetadata` using `request.shop` as the authenticated tenant identifier and hands it to the app's handler: [4](#0-3) 

`WebhookMetadata#shop` is a plain `String` field with no further validation, and the documented `WebhookHandler#handle` contract treats it as a trusted attribute of the verified webhook: [5](#0-4) 

This breaks the identity binding `shop (validated) == shop (bound by HMAC)`. The body's cryptographic integrity is guaranteed, but the `shop` header that the app uses to route data per-tenant is not covered by that same guarantee. Because Shopify apps use one `api_secret_key` shared across every shop that has installed the app, anyone who has legitimately received one valid webhook (raw_body + hmac pair) for their own store — which requires no special privilege beyond installing the app — holds a `(raw_body, hmac)` pair that stays valid for the same secret. That request can be replayed to the app's webhook endpoint with the `shop-domain` header rewritten to a different, victim shop domain, and `Utils::HmacValidator.validate` still returns `true` because it only checks `raw_body` against the secret, never `shop`.

### Impact Explanation
This is a cross-tenant identity-binding failure: an unprivileged user (an ordinary merchant with the app installed on their own store) can produce a request that the library will certify as "verified" for an arbitrary other shop, since `shop` is not bound by the HMAC that the gem uses as its sole authenticity check. Any host application that relies on `WebhookMetadata#shop` (the value this gem hands back after "verifying" the webhook) to attribute incoming data/state changes to a tenant will process attacker-chosen data under a victim shop's identity — a cross-tenant access primitive, matching the Critical impact bucket ("cross-tenant access").

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own shop has the target app installed (a normal, unprivileged action), so they legitimately receive at least one valid `(raw_body, hmac)` pair, and (2) they can send an HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header — both of which are within reach of any ordinary internet user/merchant and require no `api_secret_key`, no leaked credentials, and no TLS interception. This makes the likelihood high wherever a host app trusts `WebhookMetadata#shop` as gem-verified for authorization/routing decisions, which is exactly the field's documented purpose.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the HMAC-signable material for webhook requests, or otherwise cryptographically bind the shop domain to the verified payload before constructing `WebhookMetadata`, so `Utils::HmacValidator.validate` fails whenever the shop header does not match the shop the body was actually signed for.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook `POST` with `x-shopify-hmac-sha256: H` for body `B`, valid under the shared `api_secret_key`.
2. Attacker replays the same raw body `B` and the same signature `H` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (`B` only) — it matches `H`, so validation passes [6](#0-5) .
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` and passed to the app's handler as a verified webhook for that shop [4](#0-3) , even though Shopify never sent this data for `victim-shop`.
