### Title
Stranded/refunded token balances in `EmporiumUpgradeable` can be drained by any unprivileged caller via unrestricted stateless `ops` calls - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` executes attacker-supplied `EmporiumOperation[]` calls (`op.endpoint.call{value: op.value}(op.callData)`) with the action contract's own identity and balances whenever `stack.signerAddress == address(0)` (the "stateless" path). Neither this call nor the surrounding accounting in `runAction`/`Hinkal.transact` constrains `ops` to only touch tokens listed in `circomData.erc20TokenAddresses`. Any ERC20 balance sitting in the Emporium contract that is *not* included in that array (e.g. dust left behind by a router refund from a prior transaction) can be transferred straight to an attacker-chosen address via a crafted op, with zero effect on any of the invariants the protocol checks.

### Finding Description
The claimed equality is: *tokens leaving the action in a tx == `-deltaAmountChanges` Hinkal sent it that tx (plus what's returned as tracked UTXOs)*. This is enforced only for tokens present in `circomData.erc20TokenAddresses`:

- In `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` and the `balanceChange < 0` revert are computed strictly over `circomData.erc20TokenAddresses` [1](#0-0) .
- In `Hinkal.transact`, the top-level `balanceDif == amountChanges[i] + utxoAmount` check that reconciles Hinkal's own balance against the returned `utxoSet` also iterates only over `circomData.erc20TokenAddresses` [2](#0-1) .
- `circomData.erc20TokenAddresses` (and thus which tokens are "in scope") is entirely attacker-chosen, since the attacker crafts their own `CircomData` and generates their own valid proof for their own UTXOs.
- The `ops` array itself is decoded from attacker-controlled `externalActionMetadata` and, in the stateless branch, is executed with no restriction beyond blocking `callHinkalWallet`/`doSendToRelay` selectors: `(success, err) = op.endpoint.call{value: op.value}(op.callData);` [3](#0-2) .
- `verifyWallet` only checks/marks `emporiumMessage` as unused; when `stack.signerAddress == address(0)` it returns immediately without validating the ops at all [4](#0-3) .

Exploit flow: if the Emporium contract holds a stray balance of `tokenA` (e.g. left over from a previous swap where a router refunded unused input back to the action instead of it being swept, since only tokens in that earlier tx's `erc20TokenAddresses` were accounted for), an attacker submits `Hinkal.transact` with:
- `circomData.erc20TokenAddresses` that **excludes** `tokenA` entirely (only including whatever tokens are needed for their own trivial/self-funded operation, or an empty array).
- `externalActionData.externalActionAddress` = Emporium, `externalActionMetadata` decoding to an `EmporiumStack` with `signerAddress = address(0)` and `ops = [{ endpoint: tokenA, invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedAmount) }]`.
- A self-generated valid proof (the attacker fully controls their own nullifiers/commitments, e.g. a zero-value operation), satisfying `verifyProof`/`rootHashExists`.

`runAction` executes the loop, the op calls `tokenA.transfer(attacker, strandedAmount)` directly from the Emporium contract's own balance/identity, sending the stray tokens straight to the attacker's EOA. Since `tokenA` is absent from `circomData.erc20TokenAddresses`, none of `balanceChange < 0` (in `EmporiumUpgradeable`), `balanceDif == amountChanges[i] + utxoAmount` (in `Hinkal.sol`), or the returned `utxoSet` (which is empty for `tokenA`, matching the question's "empty UTXO set" premise) ever observe or constrain this transfer. The attacker's own listed tokens reconcile normally, so the whole transaction passes every existing check.

### Impact Explanation
This is direct theft of protocol/in-flight/parked user or protocol funds by an unprivileged attacker (Critical). Any dust, router refund, accidental transfer, or otherwise "stranded" balance held by the Emporium action contract can be swept by literally the next caller, with no relation to their own deposit/withdrawal accounting. The attack is repeatable indefinitely as new residual balances accumulate.

### Likelihood Explanation
Preconditions are simply (a) any nonzero token balance sitting in `EmporiumUpgradeable` that is not part of the current transaction's `erc20TokenAddresses`, which is a realistic byproduct of router refunds/partial fills in existing swap ops, and (b) the ability to submit a self-authored valid Hinkal proof, which any depositor already has by design. No privileged role, signature, or victim cooperation is required, and cost is just gas plus a trivial self-funded UTXO operation.

### Recommendation
Bind `ops` execution to the declared token scope: either (1) require that every token balance touched/changed by `ops` be included in `circomData.erc20TokenAddresses` and re-check *all* ERC20 balances the action could plausibly hold (not just the listed ones) before/after `runAction`, or (2) restrict the stateless `ops` path so `op.endpoint`/`op.callData` cannot directly target ERC20 token contracts held by the action (e.g. via an allowlist of router/DEX endpoints, disallowing direct calls to `circomData.erc20TokenAddresses`-adjacent token contracts with transfer-like selectors), or (3) sweep and force-account for the full balance of the entire token universe the action can hold at the end of every `runAction`, not just the caller-chosen subset.

### Proof of Concept
Foundry plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, a mock ERC20 `TokenA`, and register Emporium as an external action / allowed recipient.
2. Seed the residual: directly `TokenA.mint(address(emporium), strandedAmount)` to simulate a router-refund/stranded balance.
3. As `attacker` (unprivileged EOA), construct a `CircomData` with `erc20TokenAddresses` that excludes `TokenA`, a self-generated valid proof for a benign/zero UTXO operation, `externalActionData` pointing at Emporium, and `externalActionMetadata` encoding an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: address(TokenA), invokeWallet: false, value: 0, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, strandedAmount)}]}`.
4. Call `Hinkal.transact(...)`.
5. Assert: `TokenA.balanceOf(attacker) == strandedAmount` and `TokenA.balanceOf(address(emporium)) == 0` after the call, while the returned `utxoSet` for `TokenA` is empty/absent and `-deltaAmountChanges` Hinkal sent for `TokenA` in that tx was `0` — demonstrating tokens left the action without appearing on either side of the claimed equality.
