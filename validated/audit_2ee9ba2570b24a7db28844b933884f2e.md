### Title
Unchecked ERC20 return value in `IntentGatewayV2.withdraw()` can zero escrow while leaving tokens undelivered - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.withdraw()` releases escrowed order funds using a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and only checks that the call did not revert (`success`), never decoding/validating the returned boolean. Any ERC20 token that signals transfer failure by returning `false` instead of reverting will pass this check while the beneficiary receives nothing, yet the function unconditionally decrements the escrow accounting by the full `amount` — exactly the failure mode described in the reference report: state is updated as if the full withdrawal succeeded, while the actual transfer moved less (here, zero) value, permanently locking the user's/solver's funds.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 691-730) iterates the withdrawal request's token list and, for ERC20 tokens, does: [1](#0-0) 

```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();

_orders[body.commitment][token] -= amount;
```

This mirrors the `AssetManager.withdraw()` pattern from the report: the function assumes the transfer moved the full requested `amount` and unconditionally mutates escrow state (`_orders[...] -= amount`) to reflect that, without verifying the actual amount delivered to the beneficiary. Unlike `success` from a low-level `.call`, which only tells you the callee did not revert, ERC20 tokens that are non-compliant (return `false` on failure rather than reverting, e.g. legacy tokens like some deployments of USDT/BNB-style tokens, or any custom token with pausable/blacklist logic returning `false`) will make `success == true` while `transfer()` performed no value movement. The escrow entry `_orders[body.commitment][token]` is nonetheless zeroed/decremented, and `_filled[body.commitment]` is set, permanently marking the order as filled/refunded.

Contrast this with the sibling EVM contract `evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw()`, which correctly uses `IERC20(token).safeTransfer(beneficiary, amount)` (OpenZeppelin's `SafeERC20`, which does decode and require the boolean return value), and the main-chain `evm/src/apps/IntentGatewayV2.sol`, which likewise uses `IERC20.safeTransferFrom`/`safeTransfer` throughout. The Tron fork instead consistently uses raw `token.call(...)` for every token movement (16 occurrences repo-wide in this file), deliberately avoiding `SafeERC20`, presumably for TRON/TVM ABI compatibility reasons — but this removes the return-value validation that protects against the exact partial/failed-transfer class flagged in the reference report.

### Impact Explanation
Once `withdraw()` executes against a non-standard token that returns `false` instead of reverting:
- The escrowed balance for that `(commitment, token)` pair is decremented/zeroed even though the beneficiary received nothing.
- `_filled[body.commitment]` is set, so the order is marked filled and cannot be retried through the normal fill/refund/cancel/timeout paths (`UnknownOrder()` would trigger on any later attempt since `_orders[...] == 0`).
- The result is permanent freezing of the escrowed order funds — funds remain in the contract's balance for that token, but no accounting path can ever release them to the intended beneficiary again. This matches the report's "High" impact: user funds locked indefinitely due to state being updated as though a full transfer succeeded.

### Likelihood Explanation
This path is reachable by any user/solver whose order or fill uses an ERC20 token that does not strictly follow the ERC20 standard's revert-on-failure convention (only relevant standard behavior is "return `false`" — plenty of real tokens, especially ones deployed for TRON-style ecosystems, follow the "return false, don't revert" pattern that this contract is specifically written for by using raw `.call()` everywhere instead of `SafeERC20`). Since `withdraw()` is invoked from `onGetResponse` (timeout/refund GET response callback) as well as from standard fill/cancel flows, any unprivileged party dispatching a fill, cancel, or refund of an order denominated in such a token triggers the vulnerable code without special privileges.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` (and the analogous transfer/transferFrom call sites in this file) with `SafeERC20.safeTransfer`/`safeTransferFrom`, which decodes and requires the return value to be `true` (or absent, per the standard's edge case), consistent with the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol` and the main-chain `evm/src/apps/IntentGatewayV2.sol`. If raw `.call` must be retained for TVM compatibility reasons, explicitly decode the returned data and require it to be either empty or ABI-decode to `true` before mutating any escrow/order state.

### Proof of Concept
1. Deploy a token whose `transfer()` implementation returns `false` (without reverting) when, e.g., the recipient is blacklisted or the transfer otherwise fails (a standard "non-reverting failure" ERC20 pattern).
2. Create and fill/escrow an order in `IntentGatewayV2` (tron) denominated in this token, so `_orders[commitment][token] == amount`.
3. Trigger a path that ends up calling `withdraw(body, isRefund)` for this order/token (e.g., a timeout refund via `onGetResponse`, or the standard withdrawal flow) while the beneficiary is blacklisted/unable to receive the token.
4. `token.call(...)` returns `success == true` (call didn't revert) with return data `abi.encode(false)`, which is never checked.
5. `_orders[body.commitment][token]` is decremented to zero and `_filled[body.commitment]` is set, while the beneficiary's token balance is unchanged.
6. The escrowed tokens remain stuck in the `IntentGatewayV2` contract with no code path left to release them to the beneficiary — confirming permanent freezing of funds. [2](#0-1)

```text
    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
```
