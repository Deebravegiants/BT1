### Title
Unchecked ERC20 `transfer` Return Value in `withdraw()` and `SweepDust` Enables Silent Transfer Failures and Permanent Escrow Freezing - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` settles escrow withdrawals and dust sweeps using a raw low-level `.call()` to the token's `transfer()` selector, checking only that the call did not revert — it never inspects the ABI-encoded boolean return value. Non-compliant or Tron/TRC20-style tokens that return `false` on failure (instead of reverting) will be treated as a successful transfer, while the contract permanently decrements/clears the internal escrow accounting as if funds were delivered.

### Finding Description
In `withdraw()`, escrowed tokens are released to the beneficiary via:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

and for accumulated transaction fees:
```solidity
(bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
if (!success) revert TransferFailed();
``` [2](#0-1) 

The same unchecked pattern is used for `SweepDust` requests dispatched from Hyperbridge governance:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [3](#0-2) 

This `success` boolean only reflects whether the external call itself reverted — it does not decode or validate the returned `bool` from the token's `transfer()` function. Per the ERC20/TRC20 standard, many token implementations (and in particular non-standard tokens deployed on Tron, where TRC20 semantics diverge in edge cases) return `false` on failure rather than reverting. Such a token would make `success == true` even though no tokens moved, so the `if (!success) revert TransferFailed();` guard never triggers.

Critically, this is a **regression from the pattern used elsewhere in the same codebase**: the file itself declares `using SafeERC20 for IERC20;` and correctly uses `safeTransferFrom` when pulling funds into escrow in `placeOrder()`, e.g.:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
``` [4](#0-3) 

and the EVM sibling implementation (`IntentsBase.sol`) uses `safeTransfer` for the outbound leg:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
``` [5](#0-4) 

Only the Tron contract's outbound withdrawal/sweep path bypasses `SafeERC20` and substitutes a manual, incomplete check.

### Impact Explanation
`withdraw()` is reachable from a single relayed cross-chain message: `onAccept` dispatches to it for `RedeemEscrow`/`RefundEscrow` request kinds after authenticating the source as a known peer `IntentGateway` instance [6](#0-5) , and `onGetResponse` calls it directly for order-cancellation refunds [7](#0-6) . In both flows, once `withdraw()` executes, `_orders[body.commitment][token] -= amount;` unconditionally decrements escrow bookkeeping regardless of whether the token transfer actually delivered value. If the underlying token returns `false` on failure, the beneficiary receives nothing, yet the protocol's internal accounting marks the order filled/refunded and the escrow slot exhausted — the tokens become permanently unrecoverable (locked in the contract with no accounting path left to reclaim them). This satisfies "permanent freezing of funds" for the affected token's escrow.

### Likelihood Explanation
Exploitation requires an order to use an input/output token whose `transfer()` implementation returns `false` instead of reverting on failure (e.g., insufficient balance edge cases in custom TRC20 tokens, or tokens with unusual accounting hooks). Given Tron's TRC20 ecosystem has more implementation variance than mainstream EVM ERC20s, and that the IntentGateway is permissionless regarding which tokens users may escrow via `placeOrder`, an attacker (or even an honest user interacting with a non-standard token) can trigger this path without any privileged access — it only requires a normal order fill/cancel/redeem flow to complete against such a token.

### Recommendation
Replace the raw `.call` + boolean-only check pattern in `withdraw()` (both the token loop and the fee transfer) and in the `SweepDust` handler with `SafeERC20.safeTransfer`, consistent with the rest of the codebase (`IntentsBase.sol` and the `safeTransferFrom` calls already used in this same file):
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```
This ensures both call-revert and return-data-false conditions correctly abort the transaction and preserve escrow accounting integrity.

### Proof of Concept
1. Deploy a mock TRC20/ERC20 token whose `transfer()` function returns `false` when, e.g., `amount > balanceOf(address(this))` or another custom condition, instead of reverting.
2. Place an order on `IntentGatewayV2` (Tron) using this token as an input, escrowing funds via `placeOrder()`.
3. Have a solver fill the order on the destination chain, causing a `RedeemEscrow` message to be relayed back and processed by `onAccept` → `withdraw()`.
4. Craft/trigger the token state so `transfer(beneficiary, amount)` returns `false` (without reverting) during `withdraw()`.
5. Observe: `success` is `true` (the external call did not revert), so `if (!success) revert TransferFailed();` does not fire; `_orders[commitment][token] -= amount` executes, permanently clearing the escrow slot, while `beneficiary` never received the tokens — funds are now frozen in the contract with no remaining accounting path to recover them.
