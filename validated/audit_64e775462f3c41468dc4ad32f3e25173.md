### Title
Webhook shop-domain spoofing via HMAC that only binds the raw body, not the shop header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` (tenant identity) is read from a separate, unauthenticated header. `ShopifyAPI::Webhooks::Registry.process` validates only the body HMAC and then trusts `request.shop` as the tenant the webhook belongs to, allowing an attacker who can obtain any one validly-signed body/HMAC pair (e.g. by installing the app on their own shop) to relabel it as belonging to an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed material: [2](#0-1) 

`HmacValidator.validate` verifies `HMAC(secret, to_signable_string)` against the `hmac` header/claim: [3](#0-2) 

`Registry.process` checks only this body-bound HMAC, then immediately forwards `request.shop` — the unauthenticated header — to the host application's handler as the authoritative tenant identity: [4](#0-3) 

The equality that should hold is:
`shop bound by HMAC == shop acted upon by the handler`

but the actual invariant is:
`shop bound by HMAC (none) != shop delivered to handler (attacker-controlled header)`

Because the signature only covers `raw_body`, any request with a body/HMAC pair that is valid for *any* shop is equally valid for *every* shop — the `shop` field can be swapped freely without invalidating the signature.

### Impact Explanation
An unprivileged internet user who can install the target app on a shop they control (a normal, unprivileged flow — free/dev shops are trivially available) will receive genuine, correctly-signed webhook deliveries for topics whose body content they can substantially influence (e.g. `orders/create`, `products/update`, or fixed-schema mandatory topics like `customers/redact`/`shop/redact`). By capturing one such valid `(raw_body, hmac)` pair and replaying it to the app's webhook endpoint with the `shop-domain` header changed to a victim's public, well-known myshopify domain, the request passes `HmacValidator.validate` unchanged, and the host application's `WebhookHandler.handle` receives a `WebhookMetadata` claiming the event originated from the victim shop. This is a cross-tenant identity confusion: the app acts on attacker-chosen event data while believing it belongs to another merchant's tenant — matching the "cross-tenant access" impact category, since any tenant-scoped side effect the handler performs (data writes, redaction triggers, uninstall handling, sync jobs) is now attributable to, and executed against, a shop the attacker does not control.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the attacker to have their own legitimate shop/app install to harvest a valid signed webhook, and knowledge of a target's shop domain (public information). No credentials, secrets, or privileged access are needed — only the gem's own documented `Registry.process` flow, which is exactly what host apps are told to call.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the signed/verified material for webhook requests, or independently verify that the `shop` header value corresponds to a shop the app has a legitimate active session/install for before passing it to the handler. At minimum, `Registry.process` should cross-check `request.shop` against an app-side registry of installed shops rather than trusting the header unconditionally once the body HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and creates an order (or triggers any subscribed webhook topic), causing Shopify to POST a legitimately-signed webhook to the app's endpoint:
   - Headers: `X-Shopify-Hmac-Sha256: <H>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, body `B`.
2. Attacker captures `(B, H)`.
3. Attacker resends the same body `B` and the same `X-Shopify-Hmac-Sha256: <H>` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` — unaffected by the header change — and succeeds: [5](#0-4) 
5. The host app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, and performs tenant-scoped processing believing it is legitimate data from the victim.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
