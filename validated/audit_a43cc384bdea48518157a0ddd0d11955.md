## Finding

### Title
Checks-Effects-Interactions violation in `IntentGatewayV2.withdraw` enables reentrant double-release of escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment target of the Intent Gateway performs the external token/native transfer to the beneficiary *before* decrementing the escrow accounting for that order/token pair, and it carries no reentrancy guard. This is the exact bug class from the referenced report: an external call is made to an address the protocol does not control (the beneficiary, or a malicious/hook-bearing token) before the balance/state that gates further withdrawals is updated.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is the internal function invoked from `onAccept()` (for `RedeemEscrow`/`RefundEscrow` requests) and `onGetResponse()` (for cancel-from-source refunds): [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <-- effect happens AFTER the external call
        unchecked { ++i; }
    }
    ...
```

The validation check (`_orders[body.commitment][token] == 0`) and the escrow decrement (`_orders[body.commitment][token] -= amount`) bracket a raw low-level external call (`beneficiary.call{value: amount}("")` for native transfers, or `token.call(...)` for ERC-20 transfers) with no return-data/allowance validation and no `nonReentrant` modifier. This is a direct Checks-Effects-Interactions violation: control is handed to an address the protocol does not trust (the beneficiary for native transfers, or the token contract itself for ERC-20 transfers, which can implement transfer hooks) while `_orders[commitment][token]` still reflects the pre-withdrawal balance.

Contrast this with the corrected implementation shipped for the primary EVM target, which performs the escrow decrement *before* the external transfer: [2](#0-1) 

and which is additionally protected with `nonReentrant`: [3](#0-2) 
(6 `nonReentrant` occurrences found in that file, none in the Tron variant)

The Tron variant has neither protection, so the withdrawal path exactly reproduces the vulnerable pattern described in the report: state that gates repeated withdrawal (`_orders[commitment][token]`) is only updated *after* control has been handed to an untrusted address.

### Impact Explanation
If a native-ETH beneficiary is (or becomes) a contract with a `receive()`/`fallback()` that re-enters the delivery path, or if an ERC-20 token used as an order asset implements a pre/post-transfer hook (ERC-777-style, or any token deliberately deployed/whitelisted for use in orders), the untrusted callee gains control before `_orders[commitment][token]` is decremented. Any nested invocation of `withdraw()` for the same `commitment`/`token` pair that lands before the outer call's decrement executes will still observe the stale (undecremented) escrow balance and pass the `UnknownOrder` guard, releasing the same escrowed funds again. This directly enables theft of escrowed user/protocol funds and insolvency of the escrow accounting — a concrete loss-of-funds outcome.

### Likelihood Explanation
`withdraw()` is reachable from the standard, unprivileged intent lifecycle: any user can place an order with an arbitrary ERC-20 `token` address and designate themselves (or a solver they collude with) as `beneficiary` of a `RedeemEscrow`/`RefundEscrow`/cancellation flow, so the attacker fully controls both the receiving address and (for ERC-20 legs) the token implementation and its transfer-hook behavior. The only external precondition is that `onAccept`/`onGetResponse` execution be nested (e.g., the host/relayer processing path re-entered from within the token/native transfer) — a precondition the code makes no attempt to prevent, unlike the sibling EVM contract which explicitly guards against it with `nonReentrant` and CEI ordering. The presence of a hardened, CEI-compliant version elsewhere in the same repository indicates the team is aware of and actively mitigates this exact class of bug for the primary EVM deployment, but the mitigation was not carried over to this contract.

### Recommendation
Apply the same fix already used in `evm/src/apps/intentsv2/IntentsBase.sol` and `evm/src/apps/IntentGatewayV2.sol`:
1. Reorder `withdraw()` so `_orders[body.commitment][token] -= amount` (and the `TRANSACTION_FEES` deletion) execute *before* any external call.
2. Add a `nonReentrant` guard to `withdraw()`/`onAccept()`/`onGetResponse()`.
3. Replace raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` with OpenZeppelin's `SafeERC20.safeTransfer`, which also correctly validates non-standard return values.

### Proof of Concept
1. Attacker places an order using a malicious ERC-20 (or acts as `beneficiary` for a native-ETH leg) and becomes the `beneficiary` of a subsequent `RedeemEscrow`/`RefundEscrow`/cancel-refund `WithdrawalRequest` for commitment `C`.
2. When `withdraw(body, ...)` executes for `C`/`token`, the check `_orders[C][token] == 0` passes and `token.call(transfer(...))` (or `beneficiary.call{value: amount}("")`) transfers `amount` to the attacker-controlled address/token, handing it control before `_orders[C][token] -= amount` runs.
3. From that callback, the attacker triggers a nested call path that reaches `onAccept`/`onGetResponse` again for the same `commitment`/`token` (e.g., via a queued/duplicate message processed in the same relayed transaction).
4. The nested `withdraw()` call re-reads the still-undecremented `_orders[C][token]`, passes `UnknownOrder` check again, and transfers `amount` a second time before either decrement executes — draining the escrow for that order beyond its legitimate balance.
