## Analysis Result

### Title
Log Injection via Unsanitized Email in LDAP Login Success Message - (File: core/sessions/ldapauth/ldap.go)

### Summary
The `ldapAuthenticator.CreateSession` function logs the raw, attacker-controlled `sr.Email` value at `Info` level without any sanitization, allowing an unauthenticated client to inject terminal control/escape sequences (or newline-based log forging content) into the node's log stream — the same bug class as CVE-2017-10784 (WEBrick logging unsanitized Basic-Auth username).

### Finding Description
The `/sessions` HTTP endpoint accepts a JSON body that is bound directly into a `sessions.SessionRequest{Email, Password}` struct with no sanitization at the transport layer. [1](#0-0) 
That struct is passed straight through to the authentication provider's `CreateSession`, which — for the LDAP driver — logs `sr.Email` verbatim on the success path: [2](#0-1) 
and also on intermediate/failure branches: [3](#0-2) 

Notably, the sibling `oidcauth` driver's `CreateSession` explicitly strips `\n` and `\r` from the email before logging it, showing that the project is aware of and has previously mitigated this exact class of issue in one authenticator but not in the LDAP one: [4](#0-3) 

Because the LDAP path performs `ldap.EscapeFilter` (LDAP-filter escaping only, not log/terminal escaping) on the email used for the bind DN, but logs the *original, unescaped* `sr.Email` at line 435, no protection against ANSI/terminal escape sequence injection exists on this path. [5](#0-4) 

The codebase does have a generic sanitizer, `remote.SanitizeLogString`, used elsewhere for exactly this purpose (stripping/escaping unprintable characters before logging), but it is not applied here. [6](#0-5) 

### Impact Explanation
An unauthenticated actor submitting a login attempt (successful, e.g. via fallback local-admin credentials, or partially successful reaching the "user login, but error querying groups" branch) can embed ANSI/VT100 terminal escape sequences or CR/LF sequences into the `email` field. When an operator views raw node logs in a vulnerable terminal emulator (e.g., via `tail`, `less`, `cat`, or an SSH session), this can result in cursor manipulation, hidden/spoofed log content (log forging to mislead incident response), or, on legacy/vulnerable terminal emulators, execution of terminal-injected commands — mirroring the exact impact class of CVE-2017-10784.

### Likelihood Explanation
Reachability requires only an unauthenticated HTTP POST to the login endpoint with a crafted `email` field; no privileges are needed to reach the logging sink. The bug is only exploitable for impact (beyond log forging) when an administrator inspects logs in an escape-sequence-vulnerable terminal, which somewhat limits severity relative to the original WEBrick CVE, but the underlying root cause (unsanitized user-controlled string written to Info logs) is identical.

### Recommendation
Sanitize `sr.Email` (and any other externally-controlled string) before it is passed to any logger call in `core/sessions/ldapauth/ldap.go`, consistent with the mitigation already present in `core/sessions/oidcauth/oidc.go` (strip `\n`/`\r`), or better, reuse the existing `remote.SanitizeLogString`-style helper across all authenticators (`ldapauth`, `oidcauth`, `localauth`) to strip/escape all non-printable and ANSI escape characters prior to logging.

### Proof of Concept
1. Configure the node with the LDAP authenticator enabled.
2. Send an unauthenticated request:
```
POST /sessions HTTP/1.1
Content-Type: application/json

{"email": "attacker\u001b[31mFAKE ADMIN LOGIN\u001b[0m@example.com", "password": "whatever"}
```
3. If local-admin fallback succeeds (or even on an intermediate failure branch), the server logs:
```
l.lggr.Infof("Successful LDAP login request for user %s - %s", sr.Email, foundUser.Role)
```
embedding the raw escape sequence into the Info log line at `core/sessions/ldapauth/ldap.go:435`, which will render/execute in a vulnerable terminal when an operator tails the node's logs.

```go
func (oi *oidcAuthenticator) CreateSession(ctx context.Context, sr clsessions.SessionRequest) (string, error) {
	foundUser, err := oi.localLoginFallback(ctx, sr)
	if err != nil {
		return "", err
	}

	sanitizedEmail := strings.ReplaceAll(sr.Email, "\n", "")
	sanitizedEmail = strings.ReplaceAll(sanitizedEmail, "\r", "")
	oi.lggr.Infof("Successful local admin login request for user %s - %s", sanitizedEmail, foundUser.Role)
```
