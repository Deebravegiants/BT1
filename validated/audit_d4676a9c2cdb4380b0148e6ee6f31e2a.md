### Title
Webhook shop-domain header used for tenant identification is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature verified by `Utils::HmacValidator` only proves the integrity of the body, not of the `shop`, `topic`, `webhook_id`, or `api_version` values that are taken directly from unauthenticated HTTP headers. `Webhooks::Registry.process` uses `request.shop` (the unauthenticated header) to build the `WebhookMetadata` passed to the app's handler, so any caller who can produce one valid `(body, hmac)` pair can reuse it with an arbitrary `shop-domain` header and have the payload attributed to a different, victim shop.

### Finding Description
The identity binding that should hold is:
`shop value authenticated by HMAC == shop value acted upon by the handler`

In practice:
- `HmacValidator.validate` computes/verifies the signature over `verifiable_query.to_signable_string` only. [1](#0-0) 
- For webhooks, `to_signable_string` returns just `@raw_body`, deliberately excluding the shop/topic/webhook-id headers from the signed content. [2](#0-1) 
- `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from the raw (attacker-controllable, non-signed) HTTP headers. [3](#0-2) 
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., that the body's signature is valid for *some* shop using the app's shared `api_secret_key`), then immediately trusts `request.shop` and `request.topic` to build `WebhookMetadata` handed to the app's handler. [4](#0-3) 

Because the app's `api_secret_key` is shared across *every* shop that installs the app (it is not shop-specific), any merchant who installs the app receives genuine, correctly-signed webhook deliveries for their own store. That merchant can capture one legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair from their own store and replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. Since the HMAC never covered the shop header, `HmacValidator.validate` still returns `true`, and `Registry.process` will invoke the app's handler with `shop: <victim-shop>` and the attacker-chosen body — i.e., the low-privilege attacker (a legitimate but unprivileged installer of the app on their own store) can inject data attributed to a shop they do not control.

This is the same bug class as the referenced report: a value that is *acted upon* (here, the shop used for tenant attribution) is not the same value that was *cryptographically verified* (here, only the raw body bytes), letting an attacker use one shop's legitimately-signed material to claim a different shop's identity.

### Impact Explanation
This allows cross-tenant data injection: a webhook payload can be delivered to the app's handler tagged with an arbitrary victim `shop` domain, letting an attacker forge webhook events (e.g., `app/uninstalled`, `orders/create`, `customers/data_request`) as if they originated from a shop they don't own. Depending on how the host app's registered handler keys storage/side effects off `WebhookMetadata#shop`, this can corrupt or leak another tenant's data — a cross-tenant access impact.

### Likelihood Explanation
Medium-High. The only requirement is that the attacker install the app on a store they control (or otherwise obtain one legitimately-signed webhook body/HMAC pair for any topic), then replay that pair to the app's public webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key`, access tokens, or any other credential is required, and the gem's own `Registry.process`/`HmacValidator` logic performs no check binding the header-derived `shop` to the signed content.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signable content for webhooks, or otherwise cryptographically bind the `shop-domain` header value before trusting it in `Webhooks::Request#to_signable_string`/`Registry.process`. At minimum, document that host applications must independently verify `request.shop` corresponds to a shop that actually has this specific `webhook_id`/subscription registered, since the gem's `HmacValidator` does not protect header-derived identity fields.

### Proof of Concept
1. Attacker installs the app on their own store `attacker-shop.myshopify.com` and receives a genuine webhook delivery, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`, and `api_secret_key` is shared across all installs of the app).
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: headers))`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [5](#0-4) , and `Registry.process` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` with `shop == "victim-shop.myshopify.com"` [6](#0-5) , even though the body content actually came from the attacker's own shop.
