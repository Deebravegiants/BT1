### Title
Webhook `shop` and `topic` fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never included in the HMAC computation. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then dispatches the handler using the unauthenticated `request.shop` and `request.topic` values, breaking the identity binding `hmac_signed_bytes == bytes_acted_on`.

### Finding Description
`Request#to_signable_string` is defined as:
```ruby
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

but `shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from headers with no signature coverage:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `@raw_body`) and then trusts these unsigned header values to route and identify the tenant:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, so it never validates that `shop` or `topic` match what was actually signed by Shopify:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [4](#0-3) 

**Identity binding broken:** the gem verifies `HMAC(raw_body)` but *acts on* `(shop, topic, api_version, webhook_id)`, none of which are part of the signed payload — i.e. `bytes_verified != fields_acted_on`.

### Impact Explanation
Because `shop` and `topic` are not bound to the signature, an attacker who controls a shop that has the app installed can:
1. Trigger a legitimate webhook delivery to the app's public webhook endpoint for their own shop, capturing a valid `(raw_body, hmac)` pair (this only requires having the app installed on a shop they control — no `api_secret_key`, access token, or victim credentials needed).
2. Replay that exact `raw_body`/`hmac` pair to the same endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic` header) with a victim shop's domain (or a different registered topic).
3. Because `HmacValidator.validate` only checks `raw_body` against `hmac`, the forged request passes validation, and `Registry.process` calls the handler with `WebhookMetadata` claiming the payload originated from the victim shop/topic.

This is a cross-tenant identity confusion: the app-level webhook handler (which many apps use to identify the shop for authorization or data attribution, per `docs/usage/webhooks.md`) ends up trusting attacker-controlled `shop`/`topic` values that were never authenticated by Shopify's HMAC, letting one tenant impersonate another to the receiving app's business logic.

### Likelihood Explanation
Medium-High: the attacker needs the app installed on any shop they control (trivial for public apps, and even attainable via a dev-store) to obtain one valid `(body, hmac)` pair, and the webhook endpoint is by design a public, unauthenticated HTTP endpoint. No secret material is required — only observation of headers that this gem never protects.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the HMAC-signed payload (or otherwise cryptographically bind them to the request) instead of trusting raw headers, e.g. compute the signature over a canonical string that includes these header values along with the body, and reject requests where the recomputed signature does not match.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; a webhook (e.g. `orders/create`) fires, delivering:
   - headers: `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - body: `{"id": 1}`
2. Attacker replays the exact same body and `x-shopify-hmac-sha256` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the HMAC successfully (it only checks the unmodified body) and invokes the handler with `shop: "victim-shop.myshopify.com"`, even though Shopify never sent this webhook for that shop.
