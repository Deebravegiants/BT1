### Title
Fee-on-transfer / deflationary underlying tokens allow value to leak from `WrappedHyperFungibleToken`, letting bridged transfers redeem more than was ever locked - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` (and its upgradeable twin `WrappedHyperFungibleTokenUpgradeable.send()`) locks the underlying ERC-20 via `safeTransferFrom(msg.sender, address(this), params.amount)` but then encodes the cross-chain `Message.amount` as the caller-specified `params.amount`, never the amount actually received by the contract. If `_underlying` is a fee-on-transfer/deflationary token, the contract locks strictly less than `params.amount`, yet the destination-chain peer unlocks the full nominal `params.amount` to the beneficiary via `onAccept`. This is the exact same "nominal amount vs. actual amount received" mismatch flagged in the referenced Allo `_fundPool`/`increasePoolAmount` report, just reachable here through a single, unprivileged `send()` call from any user.

### Finding Description
`send()` computes the amount to lock and the amount to bridge from the same untrusted parameter without ever measuring the contract's actual token balance delta: [1](#0-0) 

- If `_isWeth` is false, `IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount)` is called, but no balance-before/balance-after check is performed to determine how much was actually received.
- `_buildDispatchPost` immediately encodes `params.amount` (the nominal, pre-fee amount) into the cross-chain `Message`: [2](#0-1) 

- On the destination chain, `onAccept` unconditionally releases the full nominal `message.amount` to the beneficiary from the destination contract's own underlying reserve: [3](#0-2) 

The identical pattern exists in the upgradeable variant: [4](#0-3) 

Notably, this codebase already recognizes and fixes this exact bug class elsewhere: `IntentGatewayV2.placeOrder` explicitly snapshots balances before/after `safeTransferFrom` and mutates `order.inputs[i].amount` to the actually-received amount before computing the commitment/escrow, specifically to handle fee-on-transfer tokens: [5](#0-4) 

`WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` never received this fix — they still trust `params.amount` as both the amount locked and the amount to bridge.

### Impact Explanation
Each `send()` call with a deflationary underlying token locks `params.amount - fee` but instructs the peer contract to release the full `params.amount`. Over repeated sends, the aggregate amount promised/unlocked cross-chain exceeds the aggregate amount actually locked, progressively depleting the counterparty contract's underlying reserve relative to its true backing. This is a permanent, protocol-level value leak: later legitimate `onAccept` unlocks can fail once the reserve is exhausted (funds frozen for those users), while earlier redeemers effectively extract more value than was ever escrowed. No privileged role is required — a single user's transaction with any fee-on-transfer underlying triggers the discrepancy immediately, satisfying "concrete theft or permanent freezing of funds" from a single submitted transaction.

### Likelihood Explanation
Likelihood is high wherever token owners configure `_underlying` to any token with transfer fees/rebasing behavior (a common ERC-20 category), since `configure()` places no restriction preventing such tokens from being wrapped. Any unprivileged holder of such a token can call `send()` directly — no special conditions, races, or governance actions are needed to trigger the mismatch.

### Recommendation
Measure the contract's actual balance delta after `safeTransferFrom` (and after the WETH-deposit path) and use that measured amount — not `params.amount` — when building the dispatched `Message.amount`, mirroring the balance-diff pattern already used in `IntentGatewayV2.placeOrder`. Reject or fee-normalize sends where the received amount differs from the requested amount if that policy is preferred, but the encoded cross-chain amount must never exceed what was actually locked.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` set to a fee-on-transfer token that deducts 1% on every transfer (as demonstrated by the `FeeOnTransferToken` test helper already present in the repo's test suite, e.g. `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` lines 2690-2735).
2. Alice approves the wrapper for `1000e18` and calls `send({ amount: 1000e18, dest: chainB, to: alice, ... })`.
3. `safeTransferFrom` actually delivers only `990e18` to the wrapper (`balanceOf(wrapper)` increases by `990e18`), but `_buildDispatchPost` encodes `Message.amount = 1000e18`.
4. On chain B, `onAccept` calls `IERC20(_underlying).safeTransfer(alice, 1000e18)` from chain B's reserve — 10e18 more than was ever backed by Alice's deposit on chain A.
5. Repeating this drains chain B's reserve faster than chain A's lock grows, until a subsequent legitimate `onAccept` reverts due to insufficient balance (funds frozen) while early users have already extracted the surplus.

    function _buildDispatchPost(HyperFungibleToken.SendParams calldata params) internal view returns (DispatchPost memory) {
        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

        return DispatchPost({
            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.

                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
