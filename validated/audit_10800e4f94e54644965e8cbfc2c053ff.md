### Title
Attacker-crafted hostile pre-seed ratio can overflow `Math.mulDiv` in `_noFeeSwapInput`, permanently bricking `finalizeGraduation` and freezing curve-raised LT and the 250M `LP_RESERVE` tokens - (File: `packages/contracts/src/Bonding.sol`)

### Summary
CVE-2024-28568 is a buffer-overflow DoS triggered when a parser processes attacker-supplied data (a crafted TIFF/IPTC profile) without validating that intermediate values stay in bounds. The analogous bug class on alt.fun is an unbounded arithmetic computation over attacker-influenced values during the permissionless graduation-LP-seeding path: `Bonding._noFeeSwapInput` multiplies attacker-controlled HyperSwap V2 pair reserves by protocol-derived ratio terms and feeds them into `Math.mulDiv`, which reverts if the mathematically exact result does not fit in `uint256`. A hostile mint-pre-seed sized to trip that overflow makes `finalizeGraduation` revert unconditionally and permanently, since the hostile reserve ratio is already baked into the HyperSwap pair and cannot be un-set by any other call.

### Finding Description
`finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput`: [1](#0-0)

`reserveIn`/`reserveOut` are the live HyperSwap V2 pair reserves, read as `uint112` from the pair the attacker fully controls via a "Regime 3" hostile mint pre-seed (permissionless `factory.createPair` + `transfer` + `pair.mint`), documented in `_seedUniswapV2Direct`'s own natspec: [2](#0-1) 

`targetN`/`targetD` are `ltFromPair`/`tokensForLP` (or the inverse), cached at phase 1 in `_prepareGraduationLiquidity`: [3](#0-2) 

The code's own comment on `_noFeeSwapInput` concedes the danger: the intermediate product must "fit in uint256" and "Constructed adversarial inputs that violate this would revert rather than silently truncate" — treating that revert as an acceptable failure mode: [4](#0-3) 

The problem is that `finalizeGraduation` has no fallback once `_pairRebalance`/`_noFeeSwapInput` reverts: `_seedRebalancing`'s only two return paths for the "pool imbalanced" branches are the rebalance-then-deposit path or, when `_pairRebalance` returns `false` (i.e. `_noFeeSwapInput` returns `0`), a fallback to `_seedDirectMint`. But a *revert* (as opposed to a `false` return) inside `_noFeeSwapInput`/`Math.mulDiv` is not caught anywhere — it propagates straight up through `_pairRebalance`, `_seedRebalancing`, `_seedUniswapV2Direct`, and `finalizeGraduation`, reverting the whole call: [5](#0-4) [6](#0-5) 

`finalizeGraduation` is the *only* function that can move a token's `Lifecycle` out of `Graduating`: [7](#0-6) 

and once in `Graduating`, both `buy` and `sell` are frozen (`TokenIsGraduating`), and `triggerGraduation` also rejects re-entry: [8](#0-7) 

The attacker sets `reserveIn`/`reserveOut` via their own pre-seed of the fresh HyperSwap pair (bounded practically by their capital and by the token's fixed `1e27`-wei total supply on the TOKEN side, but effectively unbounded on the LT side up to the pair's native `uint112` cap). `targetN`/`targetD` are curve-derived and, per the code's own "zero-gap LP seeding" design, `tokensForLP` legitimately can be pushed arbitrarily small relative to `ltFromPair` for tokens that graduate via the USD trigger after very little real curve trading (e.g. a rate spike right after a small seed buy triggers `canGraduate` with `ltFromPair` sizeable but `tokensForLP` tiny, since `tokensForLP = ltFromPair * tokenReserve / assetReserve`). A small `targetD` combined with a large attacker-supplied `reserveIn * reserveOut` (which alone comfortably fits `uint256`, since each factor is capped by `uint112`) is exactly the shape that pushes `Math.mulDiv`'s exact numerator/denominator quotient past `2^256`, forcing the revert documented by OpenZeppelin's `Math.mulDiv` ("the result must fit in a uint256").

This directly contradicts the module's stated invariant that "a hostile pre-seed of any shape cannot DoS `finalizeGraduation`" (see the natspec on `_seedUniswapV2Direct`), which is the exact property `Router._computeBuy`'s overflow cap and the `DIRECT_MINT_PRESEED_BPS` dust-band exist to preserve, but which the arithmetic in `_noFeeSwapInput` does not actually enforce for pre-seeds large enough to reach the rebalance branch.

### Impact Explanation
A permanently reverting `finalizeGraduation` strands the token in `Lifecycle.Graduating` forever:
- The curve-raised LT already drained into `Bonding` via `Router.graduate(token, ltFromPair)` in phase 1 (`_prepareGraduationLiquidity`) is permanently locked in the contract with no withdrawal path.
- The 250M `LP_RESERVE` tokens minus `lpBurned` remain stuck, unsellable and un-mintable to any LP.
- All curve traders and the token creator permanently lose access to their funds/tokens on that token, since `buy`/`sell` stay frozen (`TokenIsGraduating`) and there is no admin or permissionless override that bypasses `_seedUniswapV2Direct`.

This matches the required impact class: permanent freezing of trader/creator/LP funds via a one-shot, unrecoverable revert triggered by attacker-supplied data — the direct analog of a DoS caused by unbounded input processing (CVE-2024-28568's buffer-overflow class).

### Likelihood Explanation
Medium. The attack requires the attacker to:
1. Front-run `finalizeGraduation` between phase 1 (`_enterGraduating`) and phase 2 by creating the HyperSwap V2 pair and minting a self-funded LP position at a crafted reserve ratio (permissionless, already an anticipated attack surface per `AGENTS.md`'s "HyperSwap Pre-Seed Defense" section).
2. Size that pre-seed so that, combined with the specific `(tokensForLP, ltFromPair)` cached for that token, the `Math.mulDiv` numerator/denominator computation in `_noFeeSwapInput` exceeds `uint256`.

This is a specific, crafted condition rather than a universally-triggered bug, but it is fully reachable by any unprivileged wallet with modest capital, is not caught or defended against anywhere in the call chain, and directly contradicts the code's own claimed brick-resistance guarantee.

### Recommendation
- Wrap the `Math.mulDiv` call (and the whole `_noFeeSwapInput`/`_pairRebalance` computation) in a way that a would-be overflow degrades to the existing "skip swap, fall back to `_seedDirectMint`" path instead of reverting the whole `finalizeGraduation` call — e.g., pre-check whether `reserveIn * reserveOut` scaled by `targetN` can safely be divided by `targetD` before calling `mulDiv`, and treat an out-of-range case identically to the `s == 0` / `expectedOut == 0` degenerate cases already handled in `_pairRebalance`.
- Alternatively, clamp `reserveIn`/`reserveOut` (or the swap-input search space) to a value that provably keeps `Math.mulDiv`'s inputs within safe bounds given the known caps on `tokensForLP` (`≤ LP_RESERVE`) and `ltFromPair` (bounded by the `ExchangeRateTooLow` launch-time cap), so the "constructed adversarial input" case the current comment accepts as a revert is instead handled as a graceful fallback.
- Add a regression test that seeds a HyperSwap pair with reserves and a token pair whose `(tokensForLP, ltFromPair)` combination is deliberately chosen to drive `_noFeeSwapInput`'s `Math.mulDiv` argument past `uint256`, and assert `finalizeGraduation` still succeeds (mirroring the existing `test_brick_resistance_frontRun_dust_seed` but for the overflow edge instead of the dust edge).

### Proof of Concept
1. Launch a token whose paired LT has a very low `exchangeRate()` close to the `ExchangeRateTooLow` boundary, so `virtualLtReserve` (and hence the LT-denominated scale of `assetReserve`) is large.
2. Drive the curve to the USD graduation trigger via a single sizeable buy right after a tiny amount of real trading, so that at `_enterGraduating` time `ltFromPair` (real LT raised) is sizeable while `tokensForLP = ltFromPair * tokenReserve / assetReserve` rounds to a very small value (`targetD` in the "pool TOKEN-rich" rebalance branch).
3. Before `finalizeGraduation` is called, front-run: call `IUniswapV2Factory.createPair(token, lt)`, `transfer` a large amount of `lt` and `token` to the new pair (bounded by the token's fixed `1e27`-wei total supply on one side, and by attacker LT holdings on the other, up to comfortably reach the required product), and call `pair.mint(attacker)` to set hostile `(r0, r1)` reserves.
4. Call `finalizeGraduation(token)`. Trace execution into `_seedRebalancing` → `_pairRebalance` → `_noFeeSwapInput`, where `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` computes a numerator/denominator quotient exceeding `type(uint256).max`, reverting the entire transaction.
5. Confirm the token is permanently stuck: `bonding.isGraduating(token)` remains `true` forever, `buy`/`sell` revert with `TokenIsGraduating`, and repeated calls to `finalizeGraduation` always revert identically because the hostile pair reserves and the cached `pendingGraduation` values never change.

    function _pairRebalance(
        RebalanceParams memory p
    ) internal returns (bool) {
        uint256 s = _noFeeSwapInput(p.reserveIn, p.reserveOut, p.targetN, p.targetD, p.maxSwap);
        if (s == 0) return false;

        // Quote from the pair so the output tracks its live fee; a value
        // derived from a stale fee rate would trip the pair's K-check.
        uint256 expectedOut = IUniswapV2Pair(p.pair).getAmountOut(s, p.tokenIn);
        if (expectedOut == 0) return false;

        IERC20(p.tokenIn).safeTransfer(p.pair, s);
        (uint256 amount0Out, uint256 amount1Out) = p.tokenInIs0 ? (uint256(0), expectedOut) : (expectedOut, uint256(0));
        IUniswapV2Pair(p.pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
        return true;
    }

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
