### Title
Direct LT donations to a bonding-curve `Pair` are permanently and irrecoverably frozen — ([File: packages/contracts/src/Router.sol], [File: packages/contracts/src/Bonding.sol])

### Summary
The external report's bug class is an accounting scheme where a subset of funds (slashed tokens) is silently excluded from the "delegated" bucket used to drive the unlock logic, so that excluded portion — and everything gated behind it — can never be released. Alt.fun has a structurally identical pattern: `Bonding._prepareGraduationLiquidity` computes the LT to drain from a curve `Pair` as `ltFromPair = assetReserve - virtualLtReserve`, where `assetReserve` is the **stored** reserve tracked by `Pair.swap`, not the pair's live token balance [1](#0-0) . Any LT sent to the `Pair` via a plain ERC20 `transfer` (a donation) never touches `_pool.assetReserve`, so it is excluded from `ltFromPair` and is never drained by `Router.graduate` [2](#0-1) . `Pair.transferAsset`, the only function capable of moving the asset token out of the `Pair`, is `onlyRouter`, and `Router` only exposes it through `sell()` and `graduate()`, both gated by `BONDING_ROLE` [3](#0-2) . Once a token's lifecycle passes `Curve`, `Bonding.sell` unconditionally reverts (`TokenNotTrading`), and `Bonding` calls `Router.graduate` exactly once, for exactly `ltFromPair` [4](#0-3) . The donated LT balance is consequently unreachable by any on-chain path, for the token's entire lifetime — a permanent freeze, exactly analogous to the referenced report's "slashed funds never counted as delegated, so the rest can never unlock."

### Finding Description
`Pair.assetBalance()` reads the live ERC20 balance, but graduation logic and the K-invariant bookkeeping both use `_pool.assetReserve`, mutated only by `Pair.swap` (called from `Router.buy`/`Router.sell`) and `Pair.mint` (called once, at launch) [5](#0-4) . A plain `IERC20(lt).transfer(pairAddress, amount)` increases the real balance without touching `_pool.assetReserve`. This is confirmed and treated as intentional donation-resistance in the protocol's own documentation: "Direct LT donations to the pair don't count toward the USD threshold and don't enter the LP — they stay in the curve pair under the trust assumption that `BONDING_ROLE` is only ever held by `Bonding`" [6](#0-5) .

The natspec on `Router.graduate` explicitly documents the resulting lock as a *design trust assumption*, not a guaranteed recoverable state: "the leftover is unreachable as long as (a) `BONDING_ROLE` is not granted to any other address, and (b) future `Bonding` upgrades preserve the lifecycle gate" [7](#0-6) . Under the currently deployed contract set, that "unreachable" state is not merely a corner case — it is the *only* outcome: there is no owner rescue, no skim, no post-graduation sweep for the curve `Pair`'s asset side (unlike the HyperSwap V2 pair path, which has `_sweepLTToOwner`/`LTRescued` for its own residue) [8](#0-7) . Once `finalizeGraduation` completes, the token's `Lifecycle` is `Graduated`, `Bonding.buy`/`sell` on the curve are permanently closed, and `Router.graduate` has already been consumed for that token — so the donated LT is permanently stranded in the curve `Pair` contract with zero code paths capable of moving it.

### Impact Explanation
Any unprivileged trader can freeze their own LT (or grief another address's donated LT — the exclusion applies to any sender) by transferring it directly into a launched token's bonding-curve `Pair` address instead of routing it through `Zap.buy`. This satisfies the "permanent freezing of trader ... funds" bar via a fully unprivileged, single-transaction ERC20 transfer — no special role, no upgrade, no off-chain component required. This is explicitly one of the permitted analog paths ("direct ERC20 transfers of a launched Token or an LT ... into Pair").

### Likelihood Explanation
The action requires only a standard `IERC20.transfer` call to a publicly known, permissionless `Pair` address — reachable by any wallet, at any point in the curve's life (pre- or post-graduation trigger). This can happen accidentally (fat-fingered transfer/wrong-address send, common with ERC20s) or deliberately (grief/DoS of one's own or another depositor's funds); the protocol's own docs already acknowledge the resulting state is a hard, accepted trust assumption rather than a recoverable one.

### Recommendation
Add a recovery path analogous to `_sweepLTToOwner`/`LTRescued` for the curve `Pair`'s stranded asset-side donations — e.g., allow `Bonding` (via a new `Router` function gated the same way as `graduate`) to sweep `assetBalance() - assetReserve` to a rescue address either during `_prepareGraduationLiquidity` or as a standalone permissionless post-graduation function, mirroring the token-side `unsoldBurned` handling that already exists for donated launched tokens. At minimum, document this as a known, permanent, and irrecoverable loss risk surfaced prominently in the UI before any direct-transfer interaction with a `Pair` address.

### Proof of Concept
1. `creator` launches a token via `Bonding.launch`, producing `tokenAddr` and its curve `pairAddr` (per `docs/contracts-scope.md` graduation flow).
2. Any address (attacker or well-meaning-but-mistaken user) calls `IERC20(lt).transfer(pairAddr, X)` directly, bypassing `Zap`/`Bonding` entirely — a plain ERC20 transfer requires no allowlisting.
3. Normal curve trading proceeds via `Zap.buy`/`Zap.sell`; `Pair.swap` only ever mutates `_pool.assetReserve` by the amounts passed through `Router.buy`/`Router.sell`, never touching the donated `X`.
4. Graduation triggers: `Bonding._enterGraduating` → `_prepareGraduationLiquidity` computes `ltFromPair = assetReserve - virtualLtReserve` from **stored** reserve, so `X` is excluded; `Router.graduate(token, ltFromPair)` drains only the non-donated amount [1](#0-0) .
5. `finalizeGraduation` completes; `info.lifecycle` becomes `Graduated`; `pendingGraduation[token]` is deleted [9](#0-8) .
6. `Bonding.sell` now always reverts with `TokenNotTrading` for this token, and `Router.graduate` will never be invoked again for it (it's a one-time call inside `_enterGraduating`, and `_enterGraduating` is only reachable from `Curve` lifecycle). `X` LT is now permanently stuck at `pairAddr`, verifiable via `IPair(pairAddr).assetBalance() > 0` post-graduation with no function in `Pair`, `Router`, or `Bonding` capable of moving it out.

    /// @notice Transfer exactly `amount` of LT out of the pair to the caller.
    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }
