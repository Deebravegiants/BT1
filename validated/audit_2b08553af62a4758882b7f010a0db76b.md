### Title
Webhook `shop` identity is trusted from an unauthenticated header while the HMAC only signs the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used by downstream webhook handlers from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header via `shop`, while the HMAC signature that authenticates the request is computed exclusively over `@raw_body` via `to_signable_string`: [1](#0-0) [2](#0-1) 

`Registry.process` validates only that the body's HMAC matches, then dispatches the handler using the unauthenticated `shop` value: [3](#0-2) 

`HmacValidator.validate` computes and compares the signature strictly against `verifiable_query.to_signable_string`, which for `Request` is `@raw_body` alone — the `shop`, `topic`, `api-version`, and `webhook-id` headers are never part of the signed material: [4](#0-3) 

The identity binding that the gem implicitly presents to consuming applications is: **HMAC-valid webhook body ⇒ this body genuinely originated for the shop named in `WebhookMetadata#shop`**. In reality the binding only proves: **HMAC-valid webhook body ⇒ this body was signed by our `client_secret` for *some* webhook**, with `shop` being attacker-controllable header data carried alongside it. `WebhookMetadata` propagates this unauthenticated field directly to the handler: [5](#0-4) 

### Impact Explanation
Any party who can capture one legitimately HMAC-signed webhook body (e.g., by installing the target app on a store they control and receiving a webhook for a topic with attacker-influenceable/static body content, such as `shop/redact`, `customers/redact`, or any webhook whose JSON body doesn't embed the shop domain) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header for a *different*, victim tenant. Since `Utils::HmacValidator.validate` never verifies the header against the signed payload, the request passes validation, and the handler receives `WebhookMetadata` claiming to be for the victim shop. Any host application that keys per-tenant state, session lookups, or data-redaction/deletion actions off `WebhookMetadata#shop` (the officially exposed, "trusted" field of this gem's webhook API) can be tricked into applying attacker-supplied data to, or performing destructive actions against, a shop the attacker does not control — a cross-tenant access/integrity violation stemming directly from this gem's failure to bind the authenticated body to the claimed shop.

### Likelihood Explanation
Exploitation requires no secrets: an attacker needs only (a) their own webhook body/HMAC pair from any shop they control (trivial to obtain by installing any Shopify app that registers webhooks, or via their own test app), and (b) the ability to send an HTTP request with a spoofed `x-shopify-shop-domain` header to the target app's public webhook endpoint. The gem itself performs no additional binding, so the trust decision is delegated entirely — and silently — to the `shop` header despite it looking authenticated because `HmacValidator.validate` returns `true`.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) fields into the HMAC-signed material, or otherwise cryptographically tie them to the body, e.g., by including them in `to_signable_string`, or by requiring host applications to cross-check `shop` against a value derived from an already-authenticated source (such as an existing session record keyed by webhook_id) before trusting `WebhookMetadata#shop`. At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be used as a sole tenant-identity source.

### Proof of Concept
1. Attacker creates/owns `attacker-shop.myshopify.com`, installs the target app, and captures a legitimate webhook delivery for a topic whose body content is static or attacker-influenceable (e.g. `app/uninstalled`, `shop/redact`), including its `x-shopify-hmac-sha256` header value `H` computed by Shopify over body `B` using the app's real `client_secret`.
2. Attacker sends a POST to the victim app's webhook endpoint with:
   - Body: `B` (unchanged, so `Digest.hexencode(Base64.decode64(H))` still matches)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (spoofed)
   - Header `x-shopify-topic`, `x-shopify-hmac-sha256: H` (unchanged from capture)
3. `ShopifyAPI::Webhooks::Request.new` builds the request object from these headers/body.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (`B`), matching `H`.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and any host logic that trusts `data.shop` (e.g., "delete all customer data for this shop", "invalidate this shop's session") now acts on the victim tenant using attacker-triggered, body-content controlled by the attacker's own shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
