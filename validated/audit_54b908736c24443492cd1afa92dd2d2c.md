### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` binds its HMAC only to the raw request body, never to the `shop-domain` header, yet `Registry.process` forwards that unauthenticated header straight to the app's webhook handler as the tenant identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop` is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic tie to the signed material: [2](#0-1) 

`HmacValidator.validate` (and `validate_signature`) only ever computes/compares the HMAC over `verifiable_query.to_signable_string`, i.e. the body — the `shop` field plays no role in the equality check: [3](#0-2) 

`Registry.process` validates that HMAC and then, once it passes, hands `request.shop` directly to the registered handler as the tenant/shop for that event, with no separate check that this shop is the one that actually produced the signed body: [4](#0-3) 
`WebhookMetadata.shop` is a plain, unauthenticated `String` field consumed by the host app's `WebhookHandler#handle`: [5](#0-4) 

The broken identity binding, expressed as an equality that the gem fails to enforce:
`shop_bound_by_HMAC (∅, not in to_signable_string) != shop_delivered_to_handler (request.shop, from header)`

Because the app's `api_secret_key` is shared across every shop that installs the app, any merchant who installs the app on their own store can obtain a genuinely-signed webhook (valid `hmac-sha256` for a body they control, since orders/products/customers on their own store are attacker-created data). They can then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header (e.g., a victim shop). `HmacValidator.validate` still succeeds because the shop header was never part of the signed string, and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: <victim's domain>, body: <attacker-controlled body>, ...)`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee to the host application: webhook consumers (per Shopify's own documented contract, and as implicitly expected by every `WebhookHandler` implementation) treat a successfully-HMAC-validated request as authentic proof that both the body and the shop identity came from Shopify for that specific shop. Since `shop` is unauthenticated, an unprivileged attacker who is merely a legitimate installer of the app on their own store can forge webhook deliveries attributed to any other shop that has the app installed, causing the host app to process attacker-controlled data (e.g., order/customer/product payloads) under a victim shop's identity — data corruption, spoofed business events, or state corruption keyed by `shop`. This matches the "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) the attacker's own legitimate app installation to obtain one genuinely-signed webhook body/HMAC pair, and (2) the ability to POST directly to the app's public webhook endpoint with modified headers (webhook endpoints are internet-reachable by design, and Shopify itself does not IP-allowlist webhook delivery for apps to rely on). No access token, `api_secret_key`, or privileged account is needed — only ordinary merchant/app-installer capability. This is fully reachable through the gem's documented API (`Registry.process`) exactly as intended, not a misuse of undocumented behavior.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header value inside the HMAC-signed material, or otherwise cryptographically bind the shop claim to the signature — e.g., compute the signature over a canonical string that concatenates body + shop domain, matching it against a per-request expectation, or require callers to supply the expected shop and compare it post-validation. At minimum, document prominently that `request.shop`/`WebhookMetadata.shop` is unauthenticated and must not be trusted for tenant identification without an out-of-band check (e.g., cross-referencing against the shop's stored, previously-established session/installation record) before using it as a lookup key.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com`, triggering a legitimate webhook delivery for topic `orders/create` with body `B` and Shopify-computed `x-shopify-hmac-sha256: H` (valid against the app's shared `api_secret_key`).
2. Attacker captures `(B, H)` from the delivery to their own webhook endpoint (or via a network capture on their own infrastructure).
3. Attacker POSTs directly to the app's webhook endpoint with:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim.myshopify.com` (swapped)
   - body: `B` (unchanged)
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only re-hashes `B`: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` and processes attacker-controlled data as if it originated from the victim shop.
