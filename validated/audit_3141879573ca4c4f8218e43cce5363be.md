### Title
Fee-on-transfer tokens break escrow accounting in Tron `IntentGatewayV2::placeOrder` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` computes the escrow amount credited to `_orders[commitment][token]` from the user-specified nominal `order.inputs[i].amount` (minus protocol fee) *before* performing the token transfer, and in the non-predispatch branch never validates that the amount actually received matches what is credited. With a fee-on-transfer token, this credits more into escrow than the contract actually holds.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `placeOrder()` first computes `reducedInputs` (protocol-fee-adjusted escrow amounts) and the order `commitment` directly from `order.inputs[i].amount` [1](#0-0) . It then performs the actual token pull in the non-predispatch branch:

```
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            if (msgValue < order.inputs[i].amount) revert InsufficientNativeToken();
            msgValue -= order.inputs[i].amount;
        } else {
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;
        ...
``` [2](#0-1) 

There is no `balanceOf` before/after check here, so `reducedInputs[i].amount` (derived from the nominal `order.inputs[i].amount`) is credited to escrow regardless of what the gateway actually received. If `token` is a fee-on-transfer ERC-20, `safeTransferFrom` delivers less than `order.inputs[i].amount` to the gateway, yet the full nominal (fee-adjusted-for-protocol-fee-only) amount is still recorded as escrowed liability.

This is the exact bug class described in the external report (Gitcoin Allo `_fundPool` crediting the pre-fee amount instead of the actually-received amount). Notably, the sibling production contract `evm/src/apps/IntentGatewayV2.sol` was explicitly hardened against this: it measures `balanceOf` before/after every transfer and mutates `order.inputs[i].amount` to the actual received amount before computing the commitment and crediting escrow [3](#0-2) , and this behavior is covered by dedicated fee-on-transfer tests [4](#0-3) . The Tron fork (`evm/tron/contracts/apps/IntentGatewayV2.sol`) does not carry this fix in its non-predispatch code path, and even in its predispatch path only checks for excess dust assuming `balance >= requiredAmount` [5](#0-4) , still without adjusting the credited escrow amount to what the gateway itself actually receives after the final leg of the transfer.

### Impact Explanation
Any unprivileged user placing an order with a fee-on-transfer ERC-20 as input on the Tron deployment causes the gateway's internal escrow ledger (`_orders[commitment][token]`) to overstate the true on-chain token balance held by the contract. Because escrow balances for the same token are pooled contract-wide (not order-isolated custody), this creates a system-wide insolvency: the sum of all `_orders[...][token]` liabilities can exceed the actual `IERC20(token).balanceOf(gateway)`. Depending on withdrawal ordering, this either permanently strands funds for later orders paid in the same token (freezing) or allows a filler/solver to be paid out from another user's genuinely-deposited balance, effectively transferring/losing funds for other order placers. This satisfies the "concrete theft or permanent freezing of funds" criterion.

### Likelihood Explanation
Reachable by any single `placeOrder` transaction from an unprivileged user; no special privileges are required, and it triggers on ordinary use of a deflationary/fee-on-transfer ERC-20 as an order input token, a token category common enough (analogous to `USDT`-style fee tokens) that operators cannot simply assume it won't appear given the gateway is a general-purpose token intent settlement layer.

### Recommendation
Mirror the fix already applied in `evm/src/apps/IntentGatewayV2.sol`: measure `IERC20(token).balanceOf(address(this))` immediately before and after each `safeTransferFrom` call (and after the final leg of the predispatch sweep), mutate `order.inputs[i].amount` to the actually-received delta, and only then compute `protocolFee`, `reducedInputs`, the `commitment`, and the escrow credit in `_orders[commitment][token]`. Apply the same balance-delta measurement in the predispatch branch's final transfer-back-to-gateway step rather than assuming the swept `balance` equals what the gateway will actually hold.

### Proof of Concept
1. Deploy a fee-on-transfer ERC-20 (e.g., 1% fee, similar to the `FeeOnTransferToken` used in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`) and mint balance to a user.
2. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: FOT, amount: 1000e18}` via the non-predispatch path (no `predispatch.call`/`predispatch.assets`).
3. `safeTransferFrom` delivers only `990e18` to the gateway (1% fee burned/redirected), but `_orders[commitment][FOT] += reducedInputs[0].amount` credits the full `1000e18` (minus only the protocol fee, if any) — i.e., escrow ledger says `~1000e18` while gateway actually holds `990e18`.
4. Repeating this or combining with genuine full-balance tokens from other orders in the same `FOT` token demonstrates that total `_orders[...][FOT]` liabilities exceed `IERC20(FOT).balanceOf(gateway)`, so a later legitimate order's `fillOrder`/`redeemEscrow`/cancellation payout in `FOT` can fail (funds frozen) or be paid from another user's escrowed balance (funds effectively misappropriated).

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
