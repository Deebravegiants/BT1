### Title
Live config updates to `operator_qr_expiration_time` desynchronize operator-QR validity checks across the signup flow - (File: src/plans/mod.rs)

### Summary
The Symbiotic report describes a class of bug where a duration parameter (epoch duration) can be changed at runtime in one place (`EpochManager`) while multiple dependent components (vault, slashers) keep using stale copies of that duration when validating timestamps, causing security checks to pass or fail incorrectly. orb-core has a structurally identical pattern: `operator_qr_expiration_time` is a live, backend-mutable `Config` field [1](#0-0)  that gates how long an operator's QR-code authorization remains valid, but it is independently re-read from the shared `Arc<Mutex<Config>>` at multiple, temporally-separated points of the same signup session instead of being captured once and used consistently.

### Finding Description
`operator_qr_expiration_time` is downloaded from the backend and can change at any time via the periodic config refresh mechanism (`Config::download_and_store`) that is fetched during orb startup and can be re-triggered later [2](#0-1) . The value is stored in a shared `Arc<Mutex<Config>>` (`orb.config`) that is read independently at several distinct points during a single signup lifecycle:

- When first deciding whether a previously scanned operator QR is still fresh, in `scan_initial_qr_codes` [3](#0-2) , which is itself invoked from `MasterPlan::run` after re-reading the config at loop start [4](#0-3) .
- Later, when deciding whether to reuse the same `OperatorData` for scanning the user QR code, in `scan_remaining_qr_codes` [5](#0-4) , called from `do_signup` after re-reading the config again [6](#0-5) .
- Also in `idle_scan_user_qr_code`, which computes a remaining timeout as `operator_qr_expiration_time.saturating_sub(operator_data.timestamp.elapsed())` using a freshly passed-in value [7](#0-6) .

Because each of these call sites locks `orb.config` and reads `operator_qr_expiration_time` independently rather than deriving all checks from a single value captured once for the whole `OperatorData` lifetime, a backend-driven config change between these reads changes the effective validity window mid-session for an already-captured `operator_data.timestamp`. This is the same root-cause shape as the reported bug: a duration used to validate elapsed time against a stored timestamp is not held constant for the object whose age it is meant to bound, so raising or lowering it after the timestamp was recorded changes the validity retroactively.

### Impact Explanation
If the backend increases `operator_qr_expiration_time` while an operator QR has already been captured (and thus `operator_data.timestamp` set) under the old, shorter policy, later checks in `scan_remaining_qr_codes`/`idle_scan_user_qr_code` will treat the stale operator authorization as still valid for longer than the policy in force at capture time intended. This effectively extends operator supervision/authorization beyond the audited window, letting subsequent unattended user QR scans and biometric captures proceed under a previously-issued operator authorization that should have expired sooner — a signup-authorization desync analogous to the vault/slasher epoch-duration desync where a changed duration retroactively alters the validity of already-recorded state. Conversely, a decrease can cause an in-progress, legitimately-scanned operator authorization to be treated as expired earlier than the operator/user expects, unexpectedly interrupting or forcing re-authorization mid-flow.

### Likelihood Explanation
This requires only a backend-driven config change (the orb regularly re-fetches config; the field is fully backend-controlled and has no local pinning/versioning), no attacker-controlled input or malicious peer is needed, matching the "unprivileged-user" self-serve signup-authorization flow in scope. The condition triggers automatically whenever the backend adjusts this operator-QR timing knob while any orb has an in-flight signup, which given periodic config refresh is a realistic operational occurrence rather than a rare edge case.

### Recommendation
Capture `operator_qr_expiration_time` once at the moment `OperatorData` is created and store it alongside the timestamp (e.g., inside `OperatorData`), then use that captured value consistently for all subsequent staleness checks (`scan_initial_qr_codes`, `scan_remaining_qr_codes`, `idle_scan_user_qr_code`) instead of re-reading the live, potentially-changed config value on each check.

### Proof of Concept
1. Orb captures an operator QR, creating `OperatorData { timestamp: t0, .. }`, with `operator_qr_expiration_time = D1` read from config at that time [8](#0-7) .
2. Backend config refresh updates `operator_qr_expiration_time` to `D2 > D1` before the user proceeds to `scan_remaining_qr_codes`/user QR scan.
3. `do_signup` re-reads config and now uses `D2` when checking `operator_data.timestamp.elapsed() < operator_qr_expiration_time` [6](#0-5) [9](#0-8) , allowing the operator authorization captured under the old, shorter policy to be accepted well past the point it should have expired under the policy in effect when it was recorded.
