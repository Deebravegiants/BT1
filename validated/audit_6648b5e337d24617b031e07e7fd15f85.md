### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body. The `shop` value that identifies which tenant the webhook belongs to is read from an HTTP header that is never included in the signed material. Because the identity-binding equality `hmac_signed_bytes == (body, shop)` is never enforced — it is only `hmac_signed_bytes == body` — an attacker who can obtain one validly-signed webhook (trivially, by triggering a webhook on their own store, which they legitimately control) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header. The library will treat the forged shop value as authentic and pass it to the host application's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is `hmac` + `to_signable_string`. For webhooks, `to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, however, is read straight from a header that is completely independent of the signed content: [2](#0-1) 

`Registry.process` performs exactly one authenticity check — `Utils::HmacValidator.validate(request)` — before dispatching to the registered handler with `shop: request.shop` taken directly from the request: [3](#0-2) 

`HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` (i.e., only the body) and compares it to the received signature: [4](#0-3) 

Because the `shop-domain` header is outside the HMAC's coverage, the equality the code implicitly relies on — "the shop that receives this webhook data == the shop Shopify actually generated it for" — is never verified. Any bytes with a valid `(body, hmac)` pair can be paired with any attacker-chosen `shop-domain` header and will still pass `HmacValidator.validate`.

### Impact Explanation
An attacker who operates their own store (a normal, unprivileged install of the merchant's app — no special credentials, access tokens, or `client_secret` required) can:
1. Trigger any webhook topic on their own shop (e.g., `orders/create`), capturing the genuine `raw_body` and `x-shopify-hmac-sha256` value Shopify sends to the app's endpoint.
2. Resend that exact body and HMAC header to the same endpoint, but with `x-shopify-shop-domain` changed to a victim shop's domain.
3. `HmacValidator.validate` still succeeds (it never looked at the shop header), and `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled/replayed body>, ...)`.

Any host application that uses `data.shop` from the webhook metadata to key session lookups, local database writes, or downstream Admin API calls (a normal and expected usage pattern this gem's own docs and tests demonstrate) will act on/for the wrong tenant using attacker-supplied body content, i.e., cross-tenant access/data injection.

### Likelihood Explanation
Likelihood is high: no secret, token, or privileged access is needed — only a standard app install on an attacker-controlled shop (which any unprivileged internet user can obtain by installing a public Shopify app) and the ability to POST to the app's public webhook endpoint. Capturing a valid body/HMAC pair from one's own store is trivial and repeatable for any topic.

### Recommendation
Bind the shop identity into the signed material verified by this gem, e.g., have `HmacValidator`/`Webhooks::Request` also require that the `shop-domain` header value is consistent with an out-of-band trusted source, or extend `to_signable_string`/validation to incorporate the shop domain (and other Shopify-provided headers relied upon by handlers) so a valid signature cannot be replayed against a different tenant identifier.

### Proof of Concept
```
# Attacker's own shop receives a legitimate webhook:
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC over body, computed with the app's secret>
x-shopify-shop-domain: attacker-shop.myshopify.com
x-shopify-webhook-id: ...
<raw_body>

# Attacker replays identical body + HMAC, only changing the shop header:
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <same HMAC as above>
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: ...
<same raw_body>
```
`ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) will accept this second request — `HmacValidator.validate` passes because it only checks the body — and will call the registered handler with `shop: "victim-shop.myshopify.com"`, letting the attacker attribute arbitrary webhook payload content to a tenant they do not control.
