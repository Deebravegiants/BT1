### Title
Excess native token sent to `IntentGatewayV2.placeOrder` is permanently trapped instead of refunded - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`placeOrder()` is a `payable` function that accepts `msg.value` to cover native-token order inputs, predispatch assets, and solver fees, but it never validates that the supplied `msg.value` exactly matches what is consumed, nor does it refund any unconsumed remainder to the caller. Any ETH sent beyond what the order actually requires is silently absorbed into the contract's balance with no mechanism to return it to the depositor — the same root cause as the reported Gitcoin `RoundImplementation.vote()` issue: a payable entry point that mixes native-token and ERC20 accounting without a `msg.value`/required-amount reconciliation or refund step.

### Finding Description
`placeOrder(Order memory order, bytes32 graffiti)` is `external payable` and tracks a local `msgValue` variable that is decremented as native-token (`token == address(0)`) inputs and predispatch assets are consumed: [1](#0-0) [2](#0-1) 

In the non-predispatch branch, for every native input the code only checks `msgValue < order.inputs[i].amount` and decrements `msgValue`; it never asserts that the final `msgValue == 0` after all inputs (and fees) are processed: [3](#0-2) 

When `order.fees > 0`, the leftover `msgValue` (whatever amount is left after inputs) is fed wholesale into `swapETHForExactTokens{value: msgValue}(order.fees, ...)`. Uniswap's router refunds any ETH not consumed by the swap back to its immediate caller — which is the `IntentGatewayV2` contract itself, not the original user — so any overpayment beyond `order.fees` lands in the gateway's own balance rather than the user's wallet: [4](#0-3) 

The contract does define a `receive()` function specifically to accept such native-token deposits/refunds: [5](#0-4) 

but no code path in `placeOrder` (or elsewhere reachable by an ordinary user) forwards unconsumed `msg.value` back to `msg.sender`. Once absorbed, the excess ETH is indistinguishable from other escrowed order funds and is not tied to any order commitment, so the depositing user has no way to reclaim it — exactly the "no check for `_amount` and `msg.value`" defect described in the reported issue, just relocated from `RoundImplementation.vote()` to `IntentGatewayV2.placeOrder()`.

### Impact Explanation
Any user who overestimates the native-token amount required for an order (e.g., due to gas/slippage buffers, wallet UI rounding, or simply fat-fingering `msg.value`) permanently loses the difference — it becomes indistinguishable protocol-owned ETH with no attribution to the depositor and no user-facing withdrawal path. Because `placeOrder` is a core, frequently-used, unprivileged entry point (any address can call it with arbitrary `msg.value`), this can recur on every order and accumulate stuck value in the gateway over time. This matches the "permanent freezing of funds" bar for a Medium finding.

### Likelihood Explanation
High likelihood of occurrence: this requires no attacker, no special preconditions, and no malicious actor — it triggers on ordinary user error when constructing `msg.value` for `placeOrder`, which is a normal, frequently invoked, single-transaction, unprivileged code path.

### Recommendation
- After all native-token consumption (inputs, predispatch assets, and fee swap) in `placeOrder`, require that the remaining `msgValue == 0`, or explicitly refund any residual `msgValue` to `msg.sender` via a low-level call.
- Apply the same reconciliation to the `evm/tron/contracts/apps/IntentGatewayV2.sol` variant, which has the identical pattern.
- Consider adding a similar exact-refund check to `EvmHost.dispatch`/`fundRequest`, which also perform `swapETHForExactTokens{value: msg.value}` without confirming that the router refund is forwarded to the original caller rather than being retained by the host contract.

### Proof of Concept
1. User calls `placeOrder(order, graffiti)` with one native-token input of `0.5 ETH` and `order.fees = 0`, but sends `msg.value = 1 ETH`.
2. In the non-predispatch branch, `msgValue` starts at `1 ETH`, is checked (`1 ETH >= 0.5 ETH`), and decremented to `0.5 ETH`; `order.fees == 0` so the fee branch is skipped. [3](#0-2) 
3. The function completes successfully, emitting `OrderPlaced`, with no revert and no refund of the remaining `0.5 ETH`.
4. The extra `0.5 ETH` remains in the `IntentGatewayV2` contract balance (accepted via `receive()`), permanently inaccessible to the depositing user through any documented user-facing function.
