### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop/tenant spoofing on an otherwise validly-signed webhook - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `Registry.process` validates is computed only over the raw request body, never over the shop-domain header. This breaks the identity binding: `hmac_valid? == true` should imply "this exact (shop, topic, body) tuple was produced by Shopify for this shop," but it only proves "this exact body was produced by Shopify for *some* shop."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read directly and unauthenticated from a header: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (the body only) and compares it against the received `hmac-sha256` header — it never incorporates `shop`, `topic`, `webhook_id`, or `api_version`: [3](#0-2) 

`Webhooks::Registry.process` only checks this body-only HMAC before dispatching to the handler with `request.shop` as the tenant identifier: [4](#0-3) 

Since a webhook body for one topic type is frequently structurally identical or replayable across different shops (e.g., `orders/create` bodies with the same shape), and the signature never binds the header-supplied `shop` to the signed bytes, an attacker who can obtain any single validly-signed webhook body (for example, by installing the app on their own development/test store and receiving genuine webhooks from Shopify for their own shop) can resend that exact body to the app's webhook endpoint while substituting an arbitrary value in the `shop-domain` header. `HmacValidator.validate` still succeeds because the signed content (`@raw_body`) is unchanged, and `Registry.process` then hands the handler a `WebhookMetadata` claiming the data belongs to the attacker-chosen shop. This is the same class of bug as the reported Timelock issue: a field that is acted upon by the trust decision (here, the shop/tenant identity) is not covered by the integrity/authentication check that gates that decision.

### Impact Explanation
This breaks the identity binding `authenticated_shop == acted_upon_shop`. Any handler that trusts `WebhookMetadata#shop` to select which merchant's data/session to update (the intended and documented use, per `docs/usage/webhooks.md`) can be made to process attacker-supplied (replayed) data under a different shop's identity, resulting in cross-tenant data confusion/cross-tenant access — one merchant's webhook event can be attributed to another merchant's tenant record purely because the shop-domain header is unauthenticated relative to the HMAC.

### Likelihood Explanation
Requires the attacker to first obtain one genuinely-signed webhook body, which is achievable without any privileged credentials (e.g., an unprivileged user can install the app on their own dev/test store to receive real Shopify-signed webhooks for their own shop), then replay that body with a forged `shop-domain` header to the same publicly reachable webhook endpoint. No knowledge of `api_secret_key` is needed because the signature over the (unmodified) body remains valid.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop`) in the signable content verified for webhooks, or independently authenticate/whitelist the shop domain against the app's known/installed shops before dispatching to a handler, rather than trusting the raw header value once only the body-HMAC has passed.

### Proof of Concept
1. Install the target app on shop `attacker-shop.myshopify.com` (achievable by any unprivileged internet user via normal app installation).
2. Trigger a webhook event (e.g., `orders/create`) and capture the genuine request Shopify sends, including its valid `x-shopify-hmac-sha256` header and raw body.
3. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) succeeds because it only checks the unmodified body.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
