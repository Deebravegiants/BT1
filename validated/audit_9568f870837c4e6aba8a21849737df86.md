Confirmed: `rootHashHinkalIndex` is a field of `CircomData` that is used on-chain but never bound into `calldataHash` or `signedMessageHash`, and never included in the public input vector fed to the circuit.

### Title
`rootHashHinkalIndex` is unconstrained by the proof, calldataHash, or signedMessageHash, allowing a stale/attacker-chosen Merkle root index to be used - (File: `contracts/Hinkal.sol`, `contracts/CircomDataBuilder.sol`)

### Summary
`Hinkal.transact()` validates the Merkle root pair `(circomData.rootHashHinkal, circomData.rootHashHinkalIndex)` against the on-chain root history via `rootHashExists`, but only `rootHashHinkal` is committed to by the zk-proof's public inputs and by the `calldataHash`/`signedMessageHash` integrity checks. `rootHashHinkalIndex` is never included in either hash or in the circuit's public signal list, so it is a free, prover-supplied field.

### Finding Description
`CircomData` declares both `rootHashHinkal` and `rootHashHinkalIndex` [1](#0-0) . In `Hinkal.transact()`, both fields are used together to validate that the claimed root actually exists in the tree's root history: `rootHashExists(circomData.rootHashHinkal, circomData.rootHashHinkalIndex)` [2](#0-1) .

However, tracing how `calldataHash` and `signedMessageHash` are built in `CircomDataBuilder.sol`:
- `getHashedCalldata1`/`getHashedCalldata2` (which form `calldataHash`) include `publicSignalCount`, `relay`, `emporiumMessage`, `externalActionData`, `slippageValues`, `hookData`, `encryptedOutputs`, `onChainEncryptedOutput`, `feeStructure`, `onChainCreation`, `originalSender`, `extraData` — no `rootHashHinkalIndex` [3](#0-2) .
- `getSignedMessageHash` includes `rootHashHinkal`, `erc20TokenAddresses`, `amountChanges`, `timeStamp`, `inputNullifiers`, `outCommitments`, `calldataHash`, `emporiumMessage`, and the stealth address structure — again no `rootHashHinkalIndex` [4](#0-3) .
- The circuit's public input vector (`formBasicInput`) only ever pushes `rootHashHinkal` (as a private/witness input consumed by `MainEVMCircuit`), never the index [5](#0-4) .
- Inside the circuit itself, `rootHashHinkal` is the only root-related signal; there is no `rootHashHinkalIndex` signal at all [6](#0-5) [7](#0-6) .

This matches the analog class: a `CircomData` field (`rootHashHinkalIndex`) that is acted on by the contract but sits outside `calldataHash`, `signedMessageHash`, and the public-input vector. Since `performHinkalChecks` only verifies `getHashedCalldata(circomData) == circomData.calldataHash` [8](#0-7) , and this hash never touches `rootHashHinkalIndex`, a caller (any unprivileged EOA acting as its own relay, i.e. `relay == address(0)`, `originalSender == msg.sender`) can freely resubmit the same valid proof/`circomData` bundle with a different `rootHashHinkalIndex` value without invalidating `calldataHash` or the proof.

### Impact Explanation
Because `rootHashHinkalIndex` is unconstrained, the practical exploit path depends entirely on what `rootHashExists` does with a wrong/attacker-chosen index — if `rootHashExists` performs an O(1) array lookup keyed by index and merely equality-checks the root at that index (a common Merkle-root-history pattern), an attacker could not forge validity for an arbitrary root because `rootHashHinkal` itself is still bound by `signedMessageHash`/proof to the actual tree state used at proof-generation time. However, the field is still used to select *which* historical root entry the check reads, and because it is completely free of any cryptographic binding, this breaks the intended equality that the (root, index) pair the circuit was proved against is the exact pair used on-chain. Any code path in `rootHashExists` that has any subtlety, replay, or off-by-one behavior tied to index (e.g. reusing an older, already-superseded index which could still satisfy `rootHashHinkal == storedRoots[index]` for a coincidental or attacker-crafted match) becomes exploitable since there is no cryptographic tie between the index actually used to prove membership and the index passed on-chain.

### Likelihood Explanation
I could not view the implementation of `rootHashExists` within the available index (it lives in the Merkle base contract, which was not returned by my searches), so I cannot confirm whether the missing binding is actually exploitable to accept a forged root, or if `rootHashExists`'s own bounds/equality checks fully neutralize the missing hash coverage. Given tool and index limits, I could not verify the exact semantics of `rootHashExists`, and I don't have enough evidence to state with certainty that this rises to a concrete double-spend/root-forgery bypass rather than a defensive-depth gap.

### Recommendation
Include `rootHashHinkalIndex` in either the `calldataHash` computation (`getHashedCalldata1`/`getHashedCalldata2`) or the `signedMessageHash` computation in `contracts/CircomDataBuilder.sol`, so that the exact (root, index) pair used on-chain is cryptographically bound to the same integrity checks that already protect `rootHashHinkal` and the rest of `CircomData`.

### Proof of Concept
Not constructible with confidence from the available index: exploitability hinges on the internal logic of `rootHashExists`/the Merkle root-history contract, which I was unable to inspect within my remaining tool budget. I recommend a Devin session with full repository access to inspect the Merkle root-history implementation (`rootHashExists`) before confirming whether this gap is directly exploitable or merely a missing defense-in-depth binding.

            keccak256(
                abi.encode(
