## Title
Webhook HMAC only signs the request body, allowing shop-domain and topic header spoofing (cross-tenant webhook confusion) - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery#to_signable_string` by returning only the raw HTTP body [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC only over that signable string [2](#0-1) . This means the `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which are read straight from the (attacker-controllable) HTTP headers [3](#0-2)  and forwarded unchanged into the `WebhookMetadata` passed to the app's handler [4](#0-3)  — are never bound to the HMAC-verified body. Any request whose body+HMAC pair is valid for the app's secret will be accepted by `Registry.process` regardless of which shop-domain or topic headers are attached to it.

### Finding Description
`Registry.process` performs exactly one authentication check before dispatching to the app's handler:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
``` [4](#0-3) 

`HmacValidator.validate` verifies the received `hmac` header against an HMAC computed over `verifiable_query.to_signable_string` [5](#0-4) , and for a webhook `Request`, `to_signable_string` is simply the raw body:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are read directly from HTTP headers with no cryptographic binding to the body or the HMAC:
```ruby
def topic
  T.cast(shopify_header("topic"), String)
end
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [6](#0-5) 

The equality being violated is:

`shop/topic claimed in the unauthenticated HTTP headers` ≠ `shop/topic that Shopify actually generated the HMAC-signed body for`

Because only the body is authenticated, a party who legitimately installs the target app on any shop they control (a normal, unprivileged action available to any internet user — no credentials, access tokens, or `api_secret_key` needed) will receive real webhook deliveries containing a valid `(body, hmac)` pair signed with the app's real secret for their own shop. That pair can then be POSTed directly to the app's public webhook endpoint with the `shop-domain`/`topic` headers rewritten to any value the attacker chooses. `HmacValidator.validate` still returns `true` (the body/HMAC pair is legitimately valid), so `Registry.process` proceeds to build `WebhookMetadata` carrying the attacker-chosen `shop` and `topic` and calls the app's handler with it [7](#0-6) .

### Impact Explanation
Applications built on this gem are expected to use `WebhookMetadata#shop` to key their persisted per-tenant state (this is the gem's documented intended use — see how `Session.from`/`SessionUtils` key sessions by shop domain [8](#0-7) , establishing `shop` as the tenant identity key throughout the library). Because the webhook `shop`/`topic` fields are never bound to the signed body, a low-privileged attacker who legitimately installs the app on their own store can forge webhook deliveries that appear to originate from a different shop (cross-tenant confusion) or a different topic than the one the payload was actually signed for (e.g. replaying a benign event's signed body while claiming it is a privileged mandatory topic such as `shop/redact` or `app/uninstalled`). This can trigger destructive or trust-sensitive handler logic (data deletion, deauthorization, mandatory-compliance actions) attributed to a victim shop that never sent the event — a cross-tenant integrity/authentication violation.

### Likelihood Explanation
Exploitation requires only the ability to (1) install the app on a shop the attacker controls (freely available to any internet user via a Shopify dev/trial store) to obtain one valid `(body, hmac)` pair, and (2) send an arbitrary HTTP POST to the app's public webhook endpoint with modified headers. No `api_secret_key`, access token, or privileged account is required, and the app's webhook endpoint is by design a public, unauthenticated HTTP endpoint. Likelihood is therefore high for any application relying on `ShopifyAPI::Webhooks::Registry.process` to authenticate the shop/topic of an inbound webhook.

### Recommendation
Bind the security-relevant header values into the HMAC-signed material (or otherwise cryptographically bind `shop`, `topic`, and `webhook_id` to the verified body), for example by having `VerifiableQuery#to_signable_string` for webhooks include the shop domain and topic alongside the raw body, or by having `Registry.process` cross-check the delivered `shop`/`topic` against a value independently confirmed for that specific webhook subscription (e.g., verifying the webhook was actually registered for that topic/shop combination) rather than trusting the header values outright once the body's HMAC checks out.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` (no special privilege required).
2. Shopify sends a real webhook to the app, e.g. `orders/create` for `attacker-shop.myshopify.com`, with a body `B` and a valid `X-Shopify-Hmac-Sha256` header `H` computed by Shopify over `B` using the app's secret.
3. Attacker captures `(B, H)` and re-sends a POST to the same app endpoint, keeping body `B` and header `H` unchanged, but replacing:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: shop/redact` (or any other topic the attacker wants to trigger)
4. `ShopifyAPI::Webhooks::Request.new` accepts these headers as-is [9](#0-8) ; `HmacValidator.validate` succeeds because it only checks `B` against `H` [2](#0-1) .
5. `Registry.process` dispatches the app's `shop/redact` handler with `shop: "victim-shop.myshopify.com"`, even though `victim-shop` never triggered this event and the attacker never had access to `victim-shop`'s credentials.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
