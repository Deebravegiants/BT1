## Title
HOT Bridge API fallback reports withdrawal as "completed" without checking `verified_withdraw` flag - ([File: packages/intents-sdk/src/bridges/hot-bridge/hot-bridge.ts])

### Summary
`HotBridge.fetchWithdrawalHashFromApi` parses the HOT withdrawal API response with a schema that includes a `verified_withdraw` boolean per withdrawal, but the function never reads or checks this field before returning the destination hash. As a result, `describeWithdrawal` can report `status: "completed"` for a withdrawal whose destination transfer has not actually been verified by HOT, breaking the equality between the reported status and the real on-chain/verified outcome.

### Finding Description
`HotApiWithdrawalSchema` explicitly parses a `verified_withdraw: v.boolean()` field for each withdrawal entry: [1](#0-0) 

However, `fetchWithdrawalHashFromApi` only matches the withdrawal by `nonce` and immediately returns `withdrawal.hash` if present and valid hex — it never inspects `verified_withdraw`: [2](#0-1) 

This fallback path is reached in two places in `describeWithdrawal`:
1. When the bridge indexer throws for EVM/Stellar chains, the code falls back to the HOT API and returns `"completed"` with whatever hash the API returns, regardless of verification state.
2. For non-EVM/non-Stellar/non-TON chains, when the contract view returns `null`/pending, the same unchecked API fallback is used to declare the withdrawal `"completed"`. [3](#0-2) [4](#0-3) 

This breaks the equality the SDK's own type contract promises: `WithdrawalStatus` documents that `"completed"` status should mean the withdrawal genuinely finished, following an AWS-style "describe" API contract: [5](#0-4) 

But the implementation reports `"completed"` purely based on presence of a `hash` field for the matching nonce, not on `verified_withdraw === true`. If HOT's API surfaces a hash for a transaction that hasn't been confirmed/verified as landed on the destination chain (e.g., it's pending finality, reorged, or flagged during verification), the SDK will still tell callers the withdrawal is `"completed"` with a specific `txHash`.

### Impact Explanation
`describeWithdrawal`'s `"completed"` result is consumed by `watchWithdrawal`, which resolves the withdrawal promise with `{ hash: status.txHash }` as soon as `status === "completed"`: [6](#0-5) 

Integrators built on top of this SDK typically treat promise resolution as the signal to credit/release funds or mark an off-chain ledger entry as final. If the underlying HOT transfer is not actually `verified_withdraw`, an integrator can credit a user based on a hash that HOT itself has not confirmed as a completed, verified transfer — a status/hash misreport that can cause an integrator to credit funds prematurely or twice if the transfer is later found invalid or is re-processed. This matches the "status or hash misreport making an integrator credit or refund twice" impact category (High).

### Likelihood Explanation
This code path is reached whenever the bridge indexer errors out (a routine transient condition, given the code already anticipates and handles indexer failures) or when HOT's contract view method has not yet reflected settlement — both are unprivileged, naturally occurring conditions requiring no attacker action beyond normal use of the withdrawal flow, making this reachable in normal production operation rather than a contrived edge case.

### Recommendation
In `fetchWithdrawalHashFromApi`, only treat a withdrawal as resolvable if `withdrawal.verified_withdraw === true`; otherwise treat it as still pending (return `null`) so `describeWithdrawal` continues polling instead of reporting `"completed"`.

### Proof of Concept
1. HOT API returns for a given `near_trx`/`nonce`: `{ hash: "0xabc...", nonce: "1", verified_withdraw: false, chain_id: 56 }`.
2. Bridge indexer request fails or times out for an EVM withdrawal (or contract view returns `null` for another chain).
3. `describeWithdrawal` calls `fetchWithdrawalHashFromApi`, which finds the withdrawal by nonce, sees `hash` is a non-empty valid hex string, and returns it — ignoring `verified_withdraw: false`.
4. `describeWithdrawal` returns `{ status: "completed", txHash: "0xabc..." }`.
5. `watchWithdrawal` resolves with `{ hash: "0xabc..." }`, and any integrator polling/awaiting this promise treats the withdrawal as finalized, even though HOT has not verified the transfer. [7](#0-6)

	private async fetchWithdrawalHashFromApi(
		nearTxHash: string,
		nonce: bigint,
		logger?: ILogger,
	): Promise<string | null> {
		try {
			const response = await withTimeout(
				() =>
					this.hotSdk.api.requestApi(
						`/api/v1/evm/bridge_withdrawal_hash?near_trx=${nearTxHash}`,
						{ method: "GET" },
					),
				{ timeout: HotBridge.API_FALLBACK_TIMEOUT_MS },
			);
			const data: unknown = await response.json();

			const parseResult = v.safeParse(HotApiWithdrawalResponseSchema, data);
			if (!parseResult.success) {
				logger?.debug("HOT API response parse failed", {
					issues: parseResult.issues,
				});
				return null;
			}

			const withdrawal = parseResult.output.withdrawals.find(
				(w) => w.nonce === nonce.toString(),
			);

			if (withdrawal?.hash) {
				const hash = withdrawal.hash.replace(/^0x/, "");
				if (isHex(hash)) {
					logger?.info("HOT withdrawal hash found via API fallback", {
						nearTxHash,
						nonce: nonce.toString(),
					});
					return hash;
				}
			}
			return null;
		} catch (error) {
			logger?.debug("HOT API fallback failed", { error, nearTxHash });
			return null;
		}
