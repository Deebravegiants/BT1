### Title
Storage-deposit cache key collision in `DirectBridge` allows fee-estimation cross-contamination between unrelated (token, account) pairs - (File: `packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts`)

### Summary
`DirectBridge.getCachedStorageDepositValue` derives its LRU cache key by naively concatenating `contractId` and `accountId` with no separator, exactly the same "unsafe packing" root cause described in the EmissaryLib report (fields overlapping/losing their boundary during derivation). Because both NEAR identifiers share the same charset (lowercase letters, digits, `.`, `-`, `_`), two different `(contractId, accountId)` pairs can serialize to the identical cache key, letting a cached "storage already sufficient" result computed for one pair be served for a completely different pair.

### Finding Description
`getCachedStorageDepositValue` builds its cache key like this: [1](#0-0) 

Both `contractId` (the NEP-141 token account) and `accountId` (the withdrawal `destinationAddress`) are plain NEAR account IDs, and NEAR account ID grammar has no character that is disallowed inside the identifier but reserved for use as a boundary marker. That means a string such as `usdc.nearbo.near` can be split two different ways — `contractId="usdc.nearbo"`, `accountId=".near"`-style ambiguity, or more realistically `contractId="usdc.near"`, `accountId="bob.near"` versus `contractId="usdc.nearbob"`, `accountId=".near"` — producing the exact same concatenated cache key `"usdc.nearbob.near"` for two semantically distinct (token, destination) pairs. The cache is only populated when `result[1] >= result[0]` (i.e., when the account already holds sufficient storage for that specific token), and that "sufficient" verdict is what gets reused for the colliding pair.

The only guard on the cache write is `if (result[1] >= result[0])`, meaning a "sufficient" (fee = 0) result gets memoized whenever some prior valid pair happened to collide with the string of a different, unrelated pair. [2](#0-1) 

This cached tuple is then consumed directly by `estimateWithdrawalFee` to decide whether a `storageDepositFee` is owed: [3](#0-2) 

If a `DirectBridge` instance is reused across withdrawal requests for multiple sponsors/users (the normal server-side usage pattern for the `IntentsSDK`), a collision lets a stale "sufficient storage" verdict computed for one caller leak into the fee computation for a different caller's `(token, destinationAddress)` pair.

### Impact Explanation
When the collision causes `estimateWithdrawalFee` to wrongly report `storageDepositFee: 0n` for an account/token pair that in reality has insufficient NEP-141 storage registered, `createWithdrawIntentPrimitive` will build the `ft_withdraw` intent without the storage deposit it actually needs. The resulting on-chain transaction will fail (NEAR NEP-141 contracts panic on transfers to unregistered accounts), leaving the withdrawal stuck and requiring manual intervention/resubmission — this matches the "withdrawal stuck until manual intervention" High-impact category. It also causes an integrator to under-report the true cost of a withdrawal (a status/estimate that does not match the on-chain requirement), analogous to the misreport class called out in the rules.

### Likelihood Explanation
Exploitability depends on an attacker being able to name/choose an account (or interacting with a legitimately named token) whose concatenation with a target token/account boundary collides with an already-cached entry, and on the `DirectBridge`/cache instance being shared across multiple callers' requests (as is typical for a backend service embedding the SDK). This is a real, deterministic string-boundary collision (not a hash collision), so once a colliding pair of valid NEAR account IDs exists and the "donor" pair has been cached, the collision is 100% reproducible for the "victim" pair — unlike the original Solidity bug this doesn't affect *every* request, but it is a genuine, provable break of the intended key uniqueness with no attacker requiring privileged access.

### Recommendation
Use an unambiguous, delimited (or length-prefixed) cache key, e.g. `` `${contractId.length}:${contractId}:${accountId}` `` or a tuple-based `Map`/`WeakMap` keyed by `[contractId, accountId]`, so that no two distinct pairs can ever serialize to the same key.

	private async getCachedStorageDepositValue(
		contractId: string,
		accountId: string,
	): Promise<[MinStorageBalance, StorageDepositBalance]> {
		const key = `${contractId}${accountId}`;
		const cached = this.storageDepositCache.get(key);
		if (cached !== undefined) {
			return cached;
		}

		const result = await Promise.all([
			getNearNep141MinStorageBalance({
				contractId: contractId,
				nearProvider: this.nearProvider,
			}),
			getNearNep141StorageBalance({
				contractId: contractId,
				accountId: accountId,
				nearProvider: this.nearProvider,
			}),
		]);

		if (result[1] >= result[0]) {
			this.storageDepositCache.set(key, result);
		}

		return result;
