### Title
Webhook shop-tenant identity not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`) identity used by the handler is taken from an HTTP header that is never included in the signed content. Because a single app secret (`api_secret_key`) is shared across every shop that installs the app, anyone who installs the app on their own (attacker-controlled) shop can legitimately receive a validly-signed webhook, then replay that same `(body, hmac)` pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. The signature check still passes, but the handler executes business logic attributing the event to the victim tenant.

### Finding Description
`Utils::HmacValidator.validate` checks the request's HMAC against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw HTTP body, and `Request#shop` is derived purely from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) [3](#0-2) 

`Registry.process` only verifies the HMAC and then hands `request.shop` straight to the handler as the tenant identity, with no independent check that the shop header matches the actual signer/originator of the body: [4](#0-3) 

The equality this design is supposed to preserve is:
`shop that produced/authorized this HMAC-signed payload == shop attributed to the event by the handler`

Because `shop` is transmitted out-of-band in an unsigned header, that equality is never actually checked — only `hmac(body, api_secret_key) == received_hmac` is checked, and `api_secret_key` is identical for every shop that has installed the app. Any user can install the target app on a store they themselves control (a free Shopify dev/partner store), trigger a webhook topic (e.g. `app/uninstalled`, `orders/create`, `customers/data_request`), capture the genuine `(raw_body, x-shopify-hmac-sha256)` pair Shopify sends for their own store, and then POST that identical pair to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` will accept it because the body and HMAC are unchanged and were legitimately signed with the shared secret, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` equal to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant/shop identity binding without needing any leaked credential, access token, or `api_secret_key`. Depending on what the hosting application does with `WebhookMetadata#shop` (the documented and expected use, e.g. looking up the shop's session/access token, deleting/creating per-shop records, processing `app/uninstalled` to revoke a shop's data, or `customers/data_request`/`shop/redact`), this can let one merchant forge events attributed to another merchant's shop — a cross-tenant access/integrity issue. This matches the Critical "cross-tenant access" impact category, since the identity boundary between tenants (shops) is exactly what the HMAC check is meant to enforce for webhook authenticity, and here the trust decision (accept as authentic) is decoupled from the value the handler actually consumes for tenant scoping.

### Likelihood Explanation
Likelihood is meaningfully non-trivial: no privileged access, no stolen secret, and no TLS interception is required — only (a) the ability to install/interact with the target app as any user on any shop (freely obtainable via a Shopify partner/dev store) to receive a genuinely signed webhook, and (b) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with a modified header, both of which are within an ordinary "unprivileged internet user" capability. The main variable is whether the specific host application's handler logic actually trusts `data.shop` for anything sensitive (which is the documented intended usage of the field), and whether the webhook route is reachable without additional binding to the installer's own shop.

### Recommendation
Bind the tenant identity into the authenticated material instead of trusting an unsigned header:
- Include `shop` (and `topic`) in the value that is HMAC-verified (or independently verify that the `shop` header corresponds to a shop with an active session/installation before dispatching to the handler), so that `hmac`-verified authenticity and the `shop` used for tenant scoping cannot diverge.
- At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values and must not be trusted for authorization decisions without cross-checking against a known, previously-established session for that shop.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (free/dev store), which causes the app to register webhooks (e.g., `app/uninstalled`).
2. Shopify sends the app a real webhook for `attacker-shop.myshopify.com`:
   - Headers: `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid HMAC of body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - Body: `{}` (or whatever payload Shopify sends for that topic)
3. Attacker captures this `(raw_body, hmac)` pair (e.g., via their own reverse proxy/logging in front of their receiving endpoint, or by running their own instance of the target app).
4. Attacker POSTs to the target app's public webhook endpoint with the same body and HMAC, but replaces the shop header:
   ```
   POST /webhooks
   x-shopify-topic: app/uninstalled
   x-shopify-hmac-sha256: <same valid HMAC>
   x-shopify-shop-domain: victim-shop.myshopify.com

   {}
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`{}`) using the shared `api_secret_key` and finds it matches — validation succeeds. [5](#0-4) 
6. The registered handler is invoked with `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)`, causing the host application to act (e.g., revoke/delete data, invalidate sessions) as if `victim-shop.myshopify.com` sent the event, even though it did not.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
