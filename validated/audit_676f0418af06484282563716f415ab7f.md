## Title
Webhook shop-domain identity spoofing due to HMAC covering only the request body, not the `shop`/`topic`/`webhook_id` headers - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers, but its `to_signable_string` (used by `Utils::HmacValidator.validate`) signs only the raw request body. This breaks the identity binding `HMAC-verified bytes == data attributed to the shop`, because the `x-shopify-shop-domain` (or `shopify-shop-domain`) header is never covered by the signature check.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` and compares it to the received signature with `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately hands the *unauthenticated* `request.shop`/`topic`/`webhook_id` fields to the app's handler as trusted metadata: [4](#0-3) 

The equality that should hold is: `shop attributed to the event == shop cryptographically bound by the HMAC`. In fact, the HMAC only proves `body == HMAC⁻¹(signature, api_secret_key)`; it says nothing about which shop the header claims the body came from. Since the app's `api_secret_key` is the same for every installed shop, any attacker who controls (or has installed the app on) shop A can capture a legitimately signed webhook (valid body + valid HMAC), then replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to shop B. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: "shop-B", ...)`, `topic`, and `webhook_id` all attacker-controlled, backed only by a signature that proves the body came from *some* installation of the app, not from shop B.

### Impact Explanation
Any application built on this gem that trusts `data.shop`/`data.topic`/`data.webhook_id` from a "verified" webhook (which is the documented, intended usage pattern shown in `docs/usage/webhooks.md`) can be made to process attacker-forged events under an arbitrary victim shop's identity — e.g., triggering shop-B business logic (order creation handlers, uninstall/GDPR handlers, metafield updates) or duplicate-detection bypass (forged `webhook_id`), while only needing HMAC material from shop A's own legitimately delivered webhook. This is cross-tenant event injection/spoofing, since the shop attribution used to key per-tenant logic is not covered by the authentication mechanism the app is told to rely on.

### Likelihood Explanation
The webhook endpoint is unauthenticated and internet-reachable by design (Shopify pushes to it). The only requirement is that the attacker be able to capture one legitimately-signed webhook delivered to the same app (e.g., by installing the app on their own test shop, which is available to any developer), then replay the exact same body/HMAC with a modified shop header to the app's public callback route. No access to `api_secret_key` or any credential is required, satisfying the unprivileged-internet-user threat model.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable payload (or otherwise cryptographically bind them, e.g., HMAC over `headers + body`) so `HmacValidator.validate` fails if any of those fields are altered after signing. At minimum, document/require that consuming applications independently verify `data.shop` against a known installed-shop record before trusting the corresponding session/access token, rather than trusting the header value on its own as an identity claim.

### Proof of Concept
1. Install the app on attacker-controlled `shop-a.myshopify.com`; capture a real webhook delivery (raw body `B`, header `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-a.myshopify.com`).
2. Replay to the app's webhook endpoint:
   ```
   POST /webhooks/orders_create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H          # unchanged, still valid for body B
   x-shopify-shop-domain: shop-victim.myshopify.com   # forged
   x-shopify-webhook-id: <any-value>

   B
   ```
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `B` against `H`.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the app's handler with `WebhookMetadata.new(shop: "shop-victim.myshopify.com", topic: "orders/create", body: parsed(B), webhook_id: forged)`, and the host application processes it as a genuine event for `shop-victim`.
