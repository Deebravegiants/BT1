### Title
Unvalidated swap-route contracts can steal caller wallet tokens - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` accept opaque route bytes and execute them through the configured router without validating the contracts encoded in that route. [1](#0-0)  A malicious route can invoke an attacker-controlled contract that requests a token transfer from the caller; Soroban records it beneath the caller’s signed authorization tree and executes it if that tree is signed. [2](#0-1) 

### Finding Description
`process_swap_collateral` authenticates the caller and account owner or delegate, then passes the caller-provided `swap` payload into `withdraw_and_swap_from_supply`. [3](#0-2)  `swap_tokens` checks only that the payload is nonempty, authorizes the exact protocol input transfer to the router, and invokes `execute_strategy` with the uninspected bytes. [1](#0-0)  The swap payload’s `assets` registry contains caller-selected pool and token addresses, and each swap hop builds a `SwapHop` directly from those addresses before dispatching it. [4](#0-3)  There is no protocol-level venue allowlist or check that a payload-selected contract is a genuine pool rather than arbitrary attacker code. [5](#0-4) 

### Impact Explanation
An attacker-controlled route contract can request `token.transfer(victim, attacker, amount)` for any token held by the victim, including assets unrelated to the lending market. [6](#0-5)  Simulation attaches that transfer as a child of the victim’s `swap_collateral` authorization, and signing the simulated tree causes the host to execute the theft while the strategy still receives a valid output and completes. [7](#0-6)  This is theft of user funds because the loss extends beyond the authorized swap input to arbitrary wallet balances. [8](#0-7) 

### Likelihood Explanation
Exploitation requires the victim to submit a malicious route and sign the authorization tree produced by simulation, so it is not unilateral. [9](#0-8)  However, the route is an opaque XDR blob to the controller, and the protocol does not bound which contracts the route may call; a malicious frontend, quoter, or counterparty can therefore supply a poisoned route that otherwise produces a fair-looking swap. [1](#0-0)  The repository’s threat model confirms that an honest simulation records the extra transfer under the caller’s authorization and that it executes if signed. [2](#0-1) 

### Recommendation
Replace opaque caller-controlled route contracts with a structured route whose pool and token addresses are validated against approved venue contracts before invocation. [10](#0-9)  Alternatively, make the router reject any payload-selected venue that is not on an explicit protocol-maintained allowlist and fail the transaction if route execution requests authorization outside the expected input-transfer scope. [11](#0-10) 

### Proof of Concept
1. Deploy a router-compatible executor that performs a fair `USDC -> ETH` output transfer but also invokes a payload-selected `hop_pool`. [12](#0-11) 
2. Deploy `RogueHopPool` with a stored plan containing the victim address, an unrelated wallet-token address, the attacker recipient, and the victim’s full wallet balance. [13](#0-12) 
3. Construct route bytes naming that rogue contract as the hop pool and submit `swap_collateral(Alice, account_id, USDC, 5_000 USDC, ETH, route)`. [14](#0-13) 
4. During simulation, the rogue contract requests `wallet_token.transfer(Alice, attacker, WALLET_BALANCE)`, which appears as a child invocation beneath Alice’s `swap_collateral` authorization. [15](#0-14) 
5. Signing that recorded tree executes the route successfully, credits Alice with the expected ETH collateral, and transfers the entire unrelated wallet-token balance to the attacker. [8](#0-7)
