### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then unconditionally trusts the `shop` value taken from the unauthenticated `X-Shopify-Shop-Domain`/`shopify-shop-domain` header and forwards it to the app's webhook handler as the identity of the originating shop. Because the HMAC never covers the shop-domain field, an attacker who can obtain one valid `(body, hmac)` pair for their own shop (by simply installing the app on a shop they control) can replay that pair while swapping in an arbitrary victim shop domain, and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor simply reads the unauthenticated header value with no cryptographic binding to it: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the HMAC strictly over `verifiable_query.to_signable_string` (i.e., the raw body only): [3](#0-2) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then constructs `WebhookMetadata` using `request.shop` (the unauthenticated header) and dispatches it to the app's handler: [4](#0-3) 

Shopify computes webhook HMACs using the app's single, per-app `client_secret` (the gem's `Context.api_secret_key`), the same secret shared across every shop that installs the app — it is not a per-shop secret. This is the exact analog of the reported bug class: a field that is acted upon (`shop`) is not covered by the value that is cryptographically verified (the HMAC over the body only). The binding that should hold is:

`shop authenticated by HMAC == shop trusted/forwarded to handler`

but the gem only proves `body authenticated by HMAC`, and separately, unconditionally trusts `shop` from a header with no signature coverage.

### Impact Explanation
Because the same `api_secret_key` signs webhooks for every shop that installs the app, an unprivileged internet user can:
1. Install the app on a shop they control (or otherwise legitimately receive one real webhook, e.g., via a free/dev store).
2. Capture the resulting HTTP request: raw body + valid `X-Shopify-Hmac-Sha256` header.
3. Replay that exact body/HMAC pair to the app's webhook endpoint, but with the `X-Shopify-Shop-Domain` header changed to an arbitrary victim shop's domain.
4. `Utils::HmacValidator.validate` still succeeds (it only checks the body), so `Registry.process` dispatches the forged webhook to the handler with `WebhookMetadata#shop` set to the victim's domain.

If the host application's webhook handler uses `data.shop` to select which merchant's session/data to update (the intended and documented use, per `WebhookMetadata`), the attacker can inject data attributed to a shop they do not control — a cross-tenant data-integrity/confidentiality violation depending on what the handler does with the (attacker-chosen topic/body, victim-shop) pair.

### Likelihood Explanation
Exploitability only requires the ability to install the app on any shop (including a free development store) to obtain one valid signed webhook, plus the ability to send arbitrary HTTP requests to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — this is exactly an "unprivileged internet user" scenario. The only constraint is that the attacker must reuse a body/topic they already legitimately received (they cannot forge arbitrary new content without the secret), but the shop identity attached to that content is fully attacker-controlled.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise independently authenticate the shop domain, e.g.:
- Look up the target shop's session/access-token record and confirm the app is actually installed there before trusting `request.shop`, rather than trusting the header value directly, and/or
- Have `Registry.process` cross-check `request.shop` against a shop known to have this exact webhook `topic`/subscription registered (via the GraphQL webhook subscription list) before dispatching, and/or
- At minimum, document prominently that `WebhookMetadata#shop` is not cryptographically authenticated and must not be trusted as a tenant identifier without additional verification by the host application.

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop and captures a real webhook request Shopify sends:
raw_body = '{"id":1,"note":"hi"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com", # original, legitimate
}

# 2. Attacker replays the SAME body + SAME hmac, but swaps the shop-domain header:
forged_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HMAC validation still passes because it only checks raw_body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches to the handler with shop == "victim-shop.myshopify.com"
ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", ...))
```
The handler receives forged data falsely attributed to `victim-shop.myshopify.com`, despite that shop never having sent this webhook.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
