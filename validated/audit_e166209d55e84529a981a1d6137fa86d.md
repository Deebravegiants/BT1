## Analysis: PnL take-profit accounting can permanently freeze a pool (analog to HoneyFactory single-bad-state DoS)

### Title
Persisted `need_take_pnl_pc`/`need_take_pnl_coin` state can exceed live vault balances and permanently brick swap/deposit/withdraw for a pool - ([File: program/src/math.rs])

### Summary
The external report describes a single piece of persistent "bad" state (a bad-collateral flag) that is checked unconditionally on every call to a core user-facing function, causing that function to revert forever once the bad state is set, with no way to clear it via the normal user flow. Raydium AMM has a structurally identical hazard: `Calculator::calc_total_without_take_pnl_no_orderbook` [1](#0-0)  is invoked unconditionally as the very first pool-balance computation in every core unprivileged instruction — `process_deposit`, `process_withdraw`, `process_withdrawpnl`, `process_swap_base_in`, `process_swap_base_in_v2`, `process_swap_base_out`, and `process_swap_base_out_v2` — and it does a `checked_sub` of the persisted `AmmInfo.state_data.need_take_pnl_pc` / `need_take_pnl_coin` fields from the *live* vault token balances.

### Finding Description
`calc_total_without_take_pnl_no_orderbook` computes:
```
total_pc_without_take_pnl = pc_amount.checked_sub(need_take_pnl_pc).ok_or(CheckedSubOverflow)?;
total_coin_without_take_pnl = coin_amount.checked_sub(need_take_pnl_coin).ok_or(CheckedSubOverflow)?;
``` [1](#0-0) 

`need_take_pnl_pc`/`need_take_pnl_coin` are persistent fields of `AmmInfo.state_data` [2](#0-1)  that only grow via `calc_take_pnl`, called from `process_deposit`, `process_withdraw`, and `process_withdrawpnl` [3](#0-2) [4](#0-3) . `calc_take_pnl` itself relies on chained fixed-point rescaling through `normalize_decimal_v2`/`restore_decimal`, which truncate on `checked_div` (floor rounding) at every step [5](#0-4) . Because these functions are called repeatedly across the pool's life (every deposit/withdraw increments `need_take_pnl_pc/coin` while decrementing a locally-scoped `total_*_without_take_pnl` value, not the true vault balance recomputed independently each time), any systematic rounding bias accumulates directly into `need_take_pnl_pc`/`need_take_pnl_coin` over many operations without ever being re-validated against the *actual* on-chain vault balance until the next call to `calc_total_without_take_pnl_no_orderbook`.

Once `need_take_pnl_pc` or `need_take_pnl_coin` exceeds the real vault balance for any reason, `calc_total_without_take_pnl_no_orderbook` returns `Err(AmmError::CheckedSubOverflow)` and that failure propagates immediately in every one of `process_deposit`, `process_withdraw`, `process_swap_base_in(_v2)`, and `process_swap_base_out(_v2)` — the entire pool becomes unusable for all unprivileged swappers and liquidity providers, exactly analogous to how HoneyFactory's per-asset loop check on `AssetIsBadCollateral` blocks *all* future `mint` calls once one asset enters a bad state.

Critically, the "escape hatch" — `process_withdrawpnl`, which is the only instruction that resets `need_take_pnl_pc`/`need_take_pnl_coin` to zero — also begins by calling `calc_total_without_take_pnl_no_orderbook` [6](#0-5) . So if the persisted PnL-owed value ever exceeds the vault's real balance, even the privileged recovery path (`withdrawpnl`) reverts with the same `CheckedSubOverflow` error, leaving the pool permanently bricked with no code path to reset the corrupted state — a stronger, unrecoverable version of the HoneyFactory issue.

### Impact Explanation
If triggered, this permanently freezes: user swaps (`SwapBaseIn`/`SwapBaseOut`/`SwapBaseInV2`/`SwapBaseOutV2`), liquidity deposits (`Deposit`), and liquidity withdrawals (`Withdraw`) for the affected pool, and the LP tokens already minted become unredeemable through the normal withdraw path — a permanent freeze of user/LP funds. This matches the "permanent freezing of user or LP funds" impact bar in the validation rubric.

### Likelihood Explanation
I was not able to fully verify, within the scope of this analysis, that a purely unprivileged sequence of deposits/swaps/withdraws (with no admin action) can push `need_take_pnl_pc`/`need_take_pnl_coin` strictly above the live vault balance given the rounding directions actually used (`restore_decimal`/`normalize_decimal_v2` truncate via `checked_div`, and `calc_take_pnl` only increments `need_take_pnl_*` by an amount it also subtracts from the same in-function running total, which is a self-consistent invariant under exact arithmetic). Establishing concrete triggering conditions (e.g., a sequence of decimal-mismatched-mint deposits/withdraws whose repeated floor-rounding cumulatively biases `need_take_pnl_pc/coin` upward relative to the real vault balance) would require deeper numeric analysis or a fuzzing harness that I do not have tool access to run here. This is the main source of uncertainty in this finding — the code structure clearly reproduces the "single persistent bad-state check gates every core function, with no recovery path" bug class, but I could not conclusively construct or confirm a concrete unprivileged transaction sequence that produces the divergence, given available tools.

### Recommendation
- Make `process_withdrawpnl` resilient to `CheckedSubOverflow` by clamping `need_take_pnl_pc`/`need_take_pnl_coin` to the actual vault balances (as is already done defensively at [7](#0-6) ) rather than relying on the same unconditional `checked_sub` used by the swap/deposit/withdraw hot path, so PnL can always be reconciled and cleared even in a corrupted-state scenario.
- Recompute `need_take_pnl_pc`/`need_take_pnl_coin` independent of accumulated rounding in `calc_take_pnl`, or periodically re-derive them directly from vault balances instead of only incrementing them across calls.
- Add saturating/clamped subtraction (`saturating_sub`, as already used elsewhere in `math.rs`, e.g. `get_max_buy_size_at_price`/`get_max_sell_size_at_price` [8](#0-7) ) in `calc_total_without_take_pnl_no_orderbook` instead of a hard error, so a transient rounding drift cannot permanently gate every downstream instruction.

### Proof of Concept
Not conclusively constructed — see Likelihood Explanation. A full PoC would require simulating many repeated `Deposit`/`Withdraw` cycles with mismatched `coin_decimals`/`pc_decimals` (forcing `normalize_decimal_v2`/`restore_decimal` truncation on each round-trip) to demonstrate that `need_take_pnl_pc` or `need_take_pnl_coin` can exceed the live vault balance purely through unprivileged transactions, then showing that the subsequent `Swap`/`Deposit`/`Withdraw`/`WithdrawPnl` calls all revert with `AmmError::CheckedSubOverflow`.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }

    pub fn get_max_buy_size_at_price(price: u64, x: u128, y: u128, amm: &AmmInfo) -> u64 {
        // max_size = x / (1.0025 * price) - y
        let price_with_fee = U128::from(price)
            .checked_mul(U128::from(
                amm.fees.trade_fee_denominator + amm.fees.trade_fee_numerator,
            ))
            .unwrap()
            .checked_div(U128::from(amm.fees.trade_fee_denominator))
            .unwrap();
        let mut max_size = U128::from(x)
            .checked_mul(amm.sys_decimal_value.into())
            .unwrap()
            .checked_div(price_with_fee)
            .unwrap();
        max_size = max_size.saturating_sub(y.into());
        Self::to_u64(max_size.as_u128()).unwrap()
    }

    pub fn get_max_sell_size_at_price(price: u64, x: u128, y: u128, amm: &AmmInfo) -> u64 {
        // let max_size = y - x / (p / 1.0025)
        let price_with_fee = U128::from(price)
            .checked_mul(amm.fees.trade_fee_denominator.into())
            .unwrap()
            .checked_div(U128::from(
                amm.fees.trade_fee_denominator + amm.fees.trade_fee_numerator,
            ))
            .unwrap();

            .checked_mul(amm.sys_decimal_value.into())
            .unwrap()
            .checked_div(price_with_fee.into())
            .unwrap();

        let max_size = U128::from(y).saturating_sub(second_part);
        Self::to_u64(max_size.as_u128()).unwrap()
    }
