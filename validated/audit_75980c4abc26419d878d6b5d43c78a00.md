### Title
Silent `u64` truncation via unchecked `U128::as_u64()` in swap math bypasses balance/slippage checks - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
The AMM's fixed-point math uses a custom `U128`/`U256` type built with `uint::construct_uint!` [1](#0-0) . Every conversion of an intermediate 128-bit swap/LP calculation back to `u64` in the hot swap and deposit/withdraw paths is done with the unchecked `.as_u64()` method rather than the checked `Calculator::to_u64()` helper that already exists in the same file [2](#0-1) . Like `g_byte_array_new_take()` in the referenced glibc CVE, which truncates a length modulo 2**32 instead of failing, the `uint` crate's `as_u64()` silently drops the high bits of a `U128` value that exceeds `u64::MAX` when compiled without debug assertions (the normal Solana BPF release build), instead of erroring.

### Finding Description
`process_swap_base_out` / `process_swap_base_out_v2` compute the amount the trader must actually pay entirely in `U128` and only truncate to `u64` at the very last step before the slippage/balance checks: [3](#0-2) 

`swap_token_amount_base_out` computes `amount_in = total_X * amount_out / (total_Y - amount_out)` entirely in `U128` [4](#0-3) . Because `total_coin`/`total_pc` and `amount_out` are each bounded only by `u64::MAX`, their product can be as large as ~2^128, which still fits inside `U128` without triggering `checked_mul().unwrap()`. When the caller picks `amount_out` very close to the opposing side's reserve, the `checked_sub` denominator becomes very small (as small as `1`), so the resulting `amount_in` (further multiplied by `swap_fee_denominator/(swap_fee_denominator - swap_fee_numerator)`) can comfortably exceed `u64::MAX`.

That oversized `U128` value is then narrowed with `.as_u64()`: [5](#0-4) 

Unlike `Calculator::to_u64()`, which uses `try_into()` and returns `AmmError::ConversionFailure` on overflow [6](#0-5) , `U128::as_u64()` (from `uint::construct_uint!`) truncates modulo 2^64 in release builds (its overflow guard is a `debug_assert!`, which is compiled out without `debug-assertions=true`). The truncated `swap_in_after_add_fee` value is then used for both the funds check and the slippage check that gate the actual token transfer: [7](#0-6) 

Because the truncated value can be arbitrarily small relative to the true amount owed, both `user_source.amount < swap_in_after_add_fee` and `swap.max_amount_in < swap_in_after_add_fee` can pass trivially, and the program transfers only the truncated (tiny) `swap_in_after_add_fee` from the user while paying out the full attacker-chosen `swap.amount_out` from the vault.

The same unchecked `.as_u64()` pattern is used throughout `InvariantToken`/`InvariantPool` (deposit/withdraw math) [8](#0-7)  and in `process_swap_base_in`/`process_deposit`/`process_withdraw`, so the same truncation-bypass class threatens deposit LP minting and withdrawal accounting as well.

### Impact Explanation
An attacker who can push `amount_out` close enough to the opposing reserve (achievable once pool reserves and the chosen `amount_out` make `total_X * amount_out` exceed `u64::MAX` after division by a small denominator and fee scaling) pays a wrapped, near-zero `swap_in_after_add_fee` while draining `swap.amount_out` of the other token from the vault. This is concrete theft/drain of pool funds and insolvent pool accounting — the checked value used to gate the transfer no longer reflects the real amount transferred, a High severity impact.

### Likelihood Explanation
The path is reachable directly from a single submitted transaction via the public `SwapBaseOut`/`SwapBaseOutV2` instructions with fully attacker-chosen `amount_out`/`max_amount_in` and account bindings already validated normally (vault/authority checks pass) [9](#0-8) . The only precondition is that the pool's reserves and the attacker's chosen `amount_out` combination push the U128 intermediate above `u64::MAX`, which is purely a function of numbers the attacker controls together with existing pool state (no privileged signer, no off-chain component, no reliance on non-default builds).

### Recommendation
Replace every unchecked `.as_u64()` call in `program/src/math.rs` (`InvariantToken`, `InvariantPool`) and `program/src/processor.rs` (`process_swap_base_in`, `process_swap_base_out`, `process_swap_base_out_v2`, and equivalents) with the existing checked `Calculator::to_u64()` (or an explicit `u64::try_from` with error propagation), so that any value that would truncate is rejected with `AmmError::ConversionFailure` instead of silently wrapping.

### Proof of Concept
1. Attacker observes/engineers a pool state where `total_coin_without_take_pnl` and `total_pc_without_take_pnl` are large enough that `total_coin * amount_out` exceeds `u64::MAX` once `amount_out` is chosen near `total_pc_without_take_pnl` (denominator `total_pc - amount_out` = small, e.g. `1`).
2. Attacker submits `SwapBaseOut`/`SwapBaseOutV2` with `amount_out` set to `total_pc_without_take_pnl - 1` and `max_amount_in` set to a small value.
3. Inside `swap_token_amount_base_out`, `amount_in = total_coin * amount_out / 1` is computed in `U128` and can exceed `u64::MAX`; after further scaling by the fee ratio, `swap_in_after_add_fee = (...).as_u64()` truncates modulo 2^64 to a small number [3](#0-2) .
4. Checks `user_source.amount < swap_in_after_add_fee` and `swap.max_amount_in < swap_in_after_add_fee` pass because the truncated value is small [10](#0-9) .
5. The program transfers only the truncated (tiny) `swap_in_after_add_fee` from the attacker but sends the full, near-total-reserve `swap.amount_out` from the vault to the attacker's destination account [11](#0-10) , draining the pool.

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
