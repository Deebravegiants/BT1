### Title
`Webhooks::Request#shop` returns an unauthenticated header value that `Registry.process` trusts as the tenant identity - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#shop` reads the `shopify-shop-domain` / `x-shopify-shop-domain` header, but `to_signable_string` returns only `@raw_body`, so the shop-domain header (along with `topic`, `webhook_id`, `api_version`) is never part of the HMAC-signed content. `Registry.process` validates the HMAC and then unconditionally forwards `request.shop` to the webhook handler as the authenticated tenant, so an attacker who possesses any single valid `(body, hmac)` pair can replay it with an arbitrary `shop-domain` header and have it accepted as coming from any shop.

### Finding Description
The invariant that should hold is: `shop == value_inside(to_signable_string)`, i.e. every field the app treats as authenticated must be covered by the signature checked in `HmacValidator.validate`. Tracing the code:

- `Webhooks::Request#shop` reads `shopify_header("shop-domain")`, i.e. `@headers["shopify-shop-domain"] || @headers["x-shopify-shop-domain"]`. [1](#0-0) 
- `to_signable_string` — the only content ever handed to `HmacValidator` — is `@raw_body`, with no headers mixed in. [2](#0-1) 
- `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received `hmac` header via `OpenSSL.secure_compare`. Only the body is covered; no header participates in the digest at all. [3](#0-2) 
- `Registry.process` calls `Utils::HmacValidator.validate(request)` (validating only the body) and then, on success, builds `WebhookMetadata` directly from `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` and dispatches it to the app's handler. [4](#0-3) 

Because `shop` sits entirely outside `to_signable_string`, the “duplicate header / `||` preference / lenient `Base64.decode64`” mechanism described in the question is not actually required to break the binding — it is already broken unconditionally. An attacker who owns their own development shop can receive one legitimately-signed webhook (body `B`, hmac `H`), then POST `B` with header `H` again to the same public endpoint but with `x-shopify-shop-domain` (or `shopify-shop-domain`) rewritten to any victim shop's domain. `HmacValidator.validate` still passes because `H` matches `HMAC(secret, B)` regardless of headers, and `Registry.process` will call the handler with `WebhookMetadata.shop` set to the attacker-chosen value. No existing guard (`ShopValidator.sanitize!`, `Context.setup?`, Sorbet typing) intervenes, since none of them are invoked in this path — `ShopValidator` is used elsewhere (OAuth), not in `Webhooks::Registry.process`.

### Impact Explanation
This is a Critical authentication-bypass class finding: a value (`shop`) that the app is documented to trust as “the shop domain of the webhook” (see `docs/usage/webhooks.md`) is fully attacker-controlled and never covered by the signature. Any app that uses `data.shop` from `WebhookHandler#handle` to select which tenant's data to update (a common and Shopify-recommended pattern) can be made to apply another shop's webhook body to an attacker-chosen `shop` value, or vice versa — replay the attacker's own signed payload under a victim shop's identity. This is repeatable against arbitrary victim shop domains from a single captured valid signature, with no need to guess secrets or intercept traffic; it is a genuine cross-tenant confusion / forged-request-accepted-as-authentic bug.

### Likelihood Explanation
Preconditions are minimal and fully within the described attacker capability set: the attacker only needs to run their own development shop, register a webhook, and capture one legitimately-signed `(body, hmac)` pair — something explicitly permitted by the threat model. From there the replay with a modified `shop-domain` header is a single crafted HTTP POST to the app's public webhook endpoint. No secret, token, or privileged access is required, making this highly feasible and cheap to execute repeatedly.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the value that is cryptographically bound to the HMAC check, or otherwise stop treating header-derived `shop` as authenticated. Concretely: change `Webhooks::Request#to_signable_string` (or add a secondary check in `Registry.process`) so that the shop domain is verified against a source of truth (e.g., the shop's stored webhook registration/session) instead of being taken verbatim from an unsigned header, since Shopify's `X-Shopify-Hmac-SHA256` by design only signs the raw body.

### Proof of Concept
```ruby
# test/webhooks/registry_test.rb (new test)
def test_shop_domain_can_be_forged_by_replaying_a_valid_body_hmac_pair
  ShopifyAPI::Context.setup(api_secret_key: "secret", ...)

  body = '{"id":1}'
  hmac = Base64.strict_encode64(
    OpenSSL::HMAC.digest("sha256", "secret", body)
  )

  received_shop = nil
  handler = Class.new do
    extend ShopifyAPI::Webhooks::WebhookHandler
    define_singleton_method(:handle) { |data:| received_shop = data.shop }
  end
  ShopifyAPI::Webhooks::Registry.add_registration(
    topic: "orders/create", delivery_method: :http, path: "cb", handler: handler
  )

  request = ShopifyAPI::Webhooks::Request.new(
    raw_body: body,
    headers: {
      "x-shopify-topic" => "orders/create",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen, unsigned
      "x-shopify-webhook-id" => "1",
      "x-shopify-api-version" => "2023-01",
    },
  )

  ShopifyAPI::Webhooks::Registry.process(request) # HMAC validation passes
  assert_equal "victim-shop.myshopify.com", received_shop
  # Assertion demonstrates: shop != any value inside to_signable_string (== raw_body),
  # yet Registry.process accepted it as authenticated.
end
```
