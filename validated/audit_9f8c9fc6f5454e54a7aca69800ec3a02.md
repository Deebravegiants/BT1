### Title
Shared per-app bandwidth allowance can be drained by a single unprivileged sender, causing permanent denial-of-service for all other users of that app - (File: `modules/pallets/bandwidth/src/lib.rs`)

### Summary
`pallet-bandwidth`'s `BandwidthGate::try_consume` enforces a rate-limit-style byte budget keyed by `(request.source, request.from)`, analogous to the PSM's `TimeBasedRateLimiter` in the referenced report. Because `request.from` is the *sending contract's* address rather than the end-user's, any shared/multi-tenant dispatcher contract (e.g. a bridge token, gateway, or other `IDispatcher` consumer used by many independent callers) shares one bandwidth pool across all of its users. A single unprivileged caller can submit one oversized message through that shared contract to exhaust the entire pool in one transaction, denying every other user of that contract until governance manually re-tops-up the allowance — with no automatic time-based reset as PSM has.

### Finding Description
`BandwidthGate::try_consume` is invoked from the router in `on_accept` for every non-purchase inbound request: [1](#0-0) 

The gate call passes `request.source` and `request.from` as the keying tuple, and `bytes = ismp::abi::encode_post_request(&request).len()` — a size that is entirely attacker/caller controlled through the message body (`data`/payload fields accepted by sending apps).

The gate itself atomically drains a shared FIFO of subscriptions for that `(source, from)` key: [2](#0-1) 

`Allowance` storage is keyed by `(app_chain, AppKey)` where `AppKey` is derived from the sending contract's address, not the individual end-user: [3](#0-2) 

Any contract that dispatches ISMP messages on behalf of multiple independent end-users (a bridge/token gateway such as `BridgeToken.sol` built on `HyperFungibleToken`, or any generic `IApp` shared by many callers) has all of its outbound traffic billed against one bandwidth pool, since the pool is keyed by the *sender contract's* address: [4](#0-3) 

There is no per-caller sub-limit and no automatic time-based reset comparable to `resetMintDuration`/`resetRedeemDuration` in the referenced PSM report — once a pool is drained, it stays at zero (`GateError::NoAllowance` / `GateError::Insufficient`) until a new purchase message is dispatched and delivered through the full purchase flow (source-chain tx → relay → pallet credit): [5](#0-4) 

This mirrors the report's bug class precisely: a shared, exhaustible rate-limit resource that any single unprivileged sender can max out in one transaction, locking out every other legitimate user of that route — except here recovery additionally requires a manual/administered top-up rather than a bounded time window, making the freeze open-ended rather than merely "until the window resets."

### Impact Explanation
Any application built on Hyperbridge that multiplexes many independent end-users through one dispatching contract (bridge tokens, gateways, relayer-fee/reward contracts, etc.) is exposed: a single malicious user can construct one maximally-sized outbound message (e.g. by stuffing the `data`/payload field of a `send`/transfer call) to consume the entire prepaid `(source, app)` byte allowance in a single transaction. Because the drain is atomic and irreversible outside of a new purchase, this denies message delivery for every other legitimate user of that shared app on that source chain — a route unable to deliver messages, which the validation rules explicitly recognize as qualifying impact. Recovery requires governance/operator action (a new cross-chain purchase, relayed and credited), not merely waiting out a window, so the outage duration is operator-dependent rather than bounded.

### Likelihood Explanation
The attack requires only a single unprivileged, permissionless transaction from any account with access to the shared dispatching contract — no special privileges, no governance access, and no contention with other actors beyond needing the target `(source, app)` allowance to be non-empty. The cost to the attacker is bounded by whatever fee/gas the sending call costs plus (if applicable) the ISMP message fee for their own submission; unlike PSM's redemption fee deterrent, there is no economic disincentive baked into the bandwidth gate itself. Any app with meaningful adoption (i.e., more than one end-user sharing a `BandwidthManager`-purchased allowance) is a viable target, making likelihood Medium-to-High for apps built this way.

### Recommendation
- **Short term**: Document clearly that `(source, app)` bandwidth allowances are shared across all callers who dispatch through the same `from` address, and require/encourage app developers to enforce their own per-caller sub-limits (e.g., a max message size per end-user call, or per-user micro-quotas) before relying on the shared pool. Consider adding an optional per-request byte cap enforced at the gate (reject any single message whose size exceeds some fraction of the current allowance) so one call cannot exhaust the pool outright.
- **Long term**: Consider allowing `pallet-bandwidth` to track sub-allocations or rate-limit bursts within a `(source, app)` bucket (e.g., a max-bytes-per-block or max-bytes-per-message cap on top of the aggregate budget), so no single transaction can zero out the entire subscription list. Provide off-chain monitoring/alerting on `BandwidthConsumed` events for anomalous single-message consumption, and an expedited emergency top-up/`force_credit` path for governance to restore service quickly when this occurs.

### Proof of Concept
1. Governance registers a `BandwidthManager` for chain `C` and an app address `A` (e.g., a shared `BridgeToken`/gateway contract used by many end-users) purchases a tier, crediting `Allowance::<T>::get(C, A)` with `N` bytes.
2. Any unprivileged user `U` (not the app operator) calls the shared contract's send/transfer entrypoint with an arbitrarily large `data`/payload argument, producing an ISMP `PostRequest` whose ABI-encoded size (`ismp::abi::encode_post_request(&request).len()`) is close to `N` bytes.
3. `ProxyModule::on_accept` calls `BandwidthGate::try_consume(&request.source, &request.from, bytes)` — see [1](#0-0) . Since `request.from == A`, this drains the shared `(C, A)` allowance to (near) zero in `pallet_bandwidth::Pallet::try_consume` — see [2](#0-1) .
4. Every subsequent message from any other end-user routed through the same contract `A` on chain `C` now hits `GateError::NoAllowance` or `GateError::Insufficient` and is rejected, until the app operator dispatches and gets delivered a new purchase message crediting the pool again.

```rust
impl<T: Config> BandwidthGate for Pallet<T> {
	fn try_consume(
		source: &ismp::host::StateMachine,
		app: &[u8],
		bytes: u32,
	) -> Result<(), GateError> {
		let key = AppKey::truncate_from(app.to_vec());
		if Allowlist::<T>::contains_key(source, &key) {
			return Ok(());
		}

		let need: u128 = bytes.into();
		let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();

		let total = pallet::Allowance::<T>::mutate(source, &key, |list| {
			// Sweep expired in-place. Order-preserving.
			list.retain(|s| s.expires_at > now);

			if list.is_empty() {
				return Err(GateError::NoAllowance);
			}

			let total: u128 = list.iter().map(|s| s.remaining_bytes).sum();
			if total < need {
				return Err(GateError::Insufficient { remaining: total, required: need });
			}

			// Drain from the front in insertion order. Once a sub is
			// fully consumed, pop it and continue with the next.
			// `get_mut` defends against a malformed list that satisfies
			// the `total >= need` precheck but is structurally empty;
			// we'd otherwise panic via `list[0]`.
			let mut left = need;
			while left > 0 {
				let Some(head) = list.get_mut(0) else {
					return Err(GateError::NoAllowance);
				};
				let take = head.remaining_bytes.min(left);
				head.remaining_bytes = head.remaining_bytes.saturating_sub(take);
				left = left.saturating_sub(take);
				if head.remaining_bytes == 0 {
					list.remove(0);
				}
			}

			Ok(total)
		})?;

		Self::deposit_event(Event::BandwidthConsumed {
			source: *source,
			app: key,
			bytes: need,
			remaining: total - need,
		});
		Ok(())
	}
```

```text
## The Gate

Every non-purchase POST request from a registered source chain runs through `BandwidthGate::try_consume(source, app, bytes)`:

1. If the app is on the **allowlist** for that source, return `Ok` without touching the ledger.
2. Sweep expired subscriptions in place.
3. If no live subscriptions remain → `GateError::NoAllowance`.
4. Sum `remaining_bytes` across live entries. If the sum is short → `GateError::Insufficient { remaining, required }`. **No mutation happens in this case** — the caller can retry after a top-up.
5. Otherwise drain from the head until the requested bytes are satisfied. Pop entries that hit zero. Emit `BandwidthConsumed` with the post-deduct remaining.

The "no mutation on insufficient" property is load-bearing: it means a top-up race is safe — if a message arrives between when an app notices it's short and when the top-up lands, the message stays rejectable rather than half-consuming the subscription.
```
