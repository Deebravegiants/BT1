### Title
Missing sender (`from`) verification in `ExtrinsicIntents.onAccept` governance actions — chain-level authorization instead of module-level - ([File: evm/src/apps/intentsv2/ExtrinsicIntents.sol])

### Summary
`ExtrinsicIntents.onAccept` gates its privileged actions (`NewDeployment`, `UpdateParams`, `SweepDust`, `Execute`) only by checking that the incoming request's **source state machine** equals Hyperbridge [1](#0-0) , but never checks `incoming.request.from` — the specific pallet/account on the Hyperbridge chain that dispatched the message. This is the same authorization-scope class of bug as CVE-2023-40315: a check exists, but it authorizes an entire coarse-grained principal (the whole Hyperbridge state machine) rather than the specific privileged actor (the governance pallet) that is supposed to be the only one allowed to perform the action, letting a lower-privileged sender on that chain reach admin-only functionality.

### Finding Description
`ExtrinsicIntents.onAccept` distinguishes user-facing actions from governance actions:

- `RedeemEscrow`/`RefundEscrow` are authenticated with `_authenticate`, which checks `request.from` against the registered gateway instance for `request.source` [2](#0-1) .
- `NewDeployment`, `UpdateParams`, `SweepDust`, and `Execute` are instead gated only by:
```solidity
if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
``` [3](#0-2) 

This check only proves the message came from the Hyperbridge **chain**, not from any specific privileged pallet/account on that chain. There is no equivalent of `_authenticate`/`_instance` comparison against `incoming.request.from` for these branches. `Execute` in particular performs an unrestricted delegatecall into the current implementation with attacker-supplied calldata, and that calldata can reach `setRelayer` and `upgradeToAndCall` because those functions are `onlyHost`, and inside `Execute` the caller context is still the host (`msg.sender` unchanged through delegatecall) [4](#0-3) [5](#0-4) .

On the Hyperbridge (Polkadot) side, dispatching an arbitrary POST request with attacker-influenced `from`/`to`/`body` to any EVM destination is a documented capability of `IsmpDispatcher::dispatch_request`, reachable from a plain signed extrinsic in at least one shipped pallet pattern: `pallet_ismp_demo::dispatch_to_evm` requires only `ensure_signed(origin)` and lets the caller choose the destination module (`params.module`) and dispatch an arbitrary body [6](#0-5) . The analogous `dispatch_to_evm` example in the pallet-ismp docs is likewise `ensure_signed` [7](#0-6) . If any production pallet on the Hyperbridge parachain exposes a similarly permissioned (non-`AdminOrigin`/non-governance) dispatch primitive that lets a caller choose an arbitrary destination `to` and craft the `body`, that caller can address a message to a deployed `ExtrinsicIntents`/`IntentGatewayV2` instance with `RequestKind.Execute` and arbitrary delegatecall payload, since `onAccept` never verifies which pallet on Hyperbridge actually originated the message.

This mirrors the OpenNMS bug class exactly: the code performs a role/identity check, but at the wrong granularity, so a caller who legitimately holds a lesser capability (dispatching *any* generic cross-chain message from Hyperbridge) can trigger functionality reserved for a higher-privileged actor (the intents-gateway's governance pallet), i.e., privilege escalation to "ROLE_ADMIN" equivalent for that specific gateway deployment.

### Impact Explanation
If a permissionless or under-restricted dispatcher reachable on Hyperbridge exists (as `pallet_ismp_demo` demonstrates is architecturally possible), an attacker could:
- Force `Execute` → arbitrary `delegatecall`, including `upgradeToAndCall` to a malicious implementation (full contract takeover) or `setRelayer` to an attacker-controlled relayer (subsequent forged deliveries of `RedeemEscrow`/`RefundEscrow` bypassing `_checkRelayer`) [8](#0-7) .
- Trigger `SweepDust`, draining accumulated protocol dust to an attacker beneficiary.
- Trigger `NewDeployment`/`UpdateParams` to corrupt the gateway's registered instance mapping, which is later trusted by `_authenticate` for `RedeemEscrow`/`RefundEscrow`, potentially enabling theft of escrowed intent funds.

This is a concrete route to theft of escrowed funds and unauthorized app action / contract takeover, matching the required impact bar.

### Likelihood Explanation
Confirmed: the `onAccept` authorization gap itself (missing `from` check on governance-only `RequestKind`s) is present in the code as read [3](#0-2) .
Unconfirmed / uncertain: whether the production Hyperbridge runtime exposes a signed-origin (non-governance) extrinsic that can dispatch an arbitrary-`to`, arbitrary-`body` POST request to an EVM destination outside of the `pallet-ismp-demo` testing pallet. I was unable to locate, within the tool budget, the specific production pallet (e.g. `pallet_intents_coprocessor`) call that actually dispatches these governance-tagged `RequestKind`s to `ExtrinsicIntents`, nor confirm its origin is `EnsureRoot`/`GovernanceOrigin` in all code paths versus a generic dispatch primitive. If the only pallets that dispatch `NewDeployment`/`UpdateParams`/`SweepDust`/`Execute` bodies are themselves root/governance-gated, the coarse `source`-only check, while still an architectural weakness (defense-in-depth gap), would not be exploitable end-to-end without a companion vulnerability. Given this uncertainty, likelihood is assessed as Medium pending confirmation of a permissionless dispatch path into this destination module.

### Recommendation
Add an explicit `from` check for the governance-only branches in `ExtrinsicIntents.onAccept`, analogous to `_authenticate`, verifying `incoming.request.from` equals a specifically configured governance module id (not just that `request.source` is the Hyperbridge chain), e.g.:
```solidity
if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())
    || address(bytes20(incoming.request.from)) != _governanceModule) revert Unauthorized();
```
Separately, audit every pallet on the Hyperbridge parachain that can call `IsmpDispatcher::dispatch_request` toward EVM destinations to ensure none of them allow a caller-supplied `from`/`to`/arbitrary `body` combination under a merely-`ensure_signed` origin when the destination could be a governance-sensitive module (the `pallet_ismp_demo::dispatch_to_evm` pattern should never be mirrored in a production pallet without an `AdminOrigin`/governance gate).

### Proof of Concept
1. Attacker (or any account) invokes a Hyperbridge-side dispatcher capable of sending an arbitrary IsmpDispatcher POST (structurally identical to `pallet_ismp_demo::dispatch_to_evm`, requiring only `ensure_signed`) [6](#0-5) , addressing `to` = the target `ExtrinsicIntents` proxy address, with `body = bytes.concat(bytes1(uint8(RequestKind.Execute)), abi.encodeCall(setRelayer, (attacker)))`.
2. The relayer delivers this through `HandlerV2`/`EvmHost.dispatchIncoming`, calling `ExtrinsicIntents.onAccept` with `incoming.relayer` set to any account (gate is open pre-arming, or attacker is the authorised relayer) [9](#0-8) .
3. `onAccept` checks only `incoming.request.source == hyperbridge` — true, since the message did originate from the Hyperbridge chain — and proceeds to `RequestKind.Execute`, delegatecalling `setRelayer(attacker)` with the host as `msg.sender`, satisfying `onlyHost` [5](#0-4) [10](#0-9) .
4. Attacker is now the sole authorised relayer for all future `RedeemEscrow`/`RefundEscrow` deliveries, enabling forged escrow releases, or repeats the process with `upgradeToAndCall` for full takeover.
