## Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook forgery via replay — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives its HMAC-signable content solely from the raw HTTP body [1](#0-0) , while the tenant-identifying `shop` field (and `topic`/`webhook_id`) is read from an HTTP header that is never included in the signed payload [2](#0-1) . `Webhooks::Registry.process` validates only that raw-body HMAC and then unconditionally trusts `request.shop` as the authoritative tenant for the webhook handler [3](#0-2) . This breaks the identity binding `hmac_signed_payload == (body, shop)`; in reality it only equals `(body)`.

### Finding Description
For OAuth callbacks, the analogous `AuthQuery#to_signable_string` correctly includes `shop` inside the HMAC-covered string [4](#0-3) , so the shop cannot be swapped without invalidating the signature. Webhook requests do not follow this pattern: `to_signable_string` returns only `@raw_body`, and `shop`, `topic`, and `webhook_id` are pulled straight from headers with no cryptographic binding to the signed body [5](#0-4) .

`Utils::HmacValidator.validate` performs a byte-for-byte HMAC check against `verifiable_query.to_signable_string` [6](#0-5) , so any `(raw_body, hmac)` pair that was legitimately generated by Shopify for one shop remains valid forever, regardless of which `shop-domain` header accompanies it. `Registry.process` uses exactly this check and then forwards `request.shop` unchecked to the registered handler as the tenant identity [3](#0-2) .

Because the app's `api_secret_key` is shared across all shops/tenants using the app, any merchant who installs the app (a free/trial Shopify store is enough) legitimately receives real `(raw_body, hmac)` pairs signed by Shopify. That merchant can then replay the exact same body+HMAC to the app's public webhook endpoint while substituting a victim shop's domain in the `shopify-shop-domain` header. The HMAC check still passes (it never looked at the header), and the handler processes attacker-controlled webhook content under the victim tenant's identity.

### Impact Explanation
This is a cross-tenant identity confusion: the gem lets an unprivileged party (any app installer) inject webhook data that the host application will attribute to a different shop/tenant, because the `shop` claim is verified independently of, rather than as part of, the cryptographic proof. Per the given impact categories, this is Critical (cross-tenant access) since it lets one tenant's actions be misattributed to another tenant purely through this gem's HMAC/tenant-binding logic.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on any Shopify store (no privileged account, secret, or token needed), (2) capturing one legitimate webhook delivery (raw body + `x-shopify-hmac-sha256` header), and (3) POSTing that exact body/HMAC to the app's webhook endpoint with a different `shopify-shop-domain` header. No knowledge of `api_secret_key` is needed because the attacker reuses a signature Shopify already computed for them. This is straightforward and repeatable (no timestamp/nonce is included in the webhook signable string to bound replay), unlike the OAuth flow.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values inside `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the shop-domain header to the signed body before `Registry.process` uses it as the tenant identity — mirroring what `Auth::Oauth::AuthQuery` already does by including `shop` in its signable string.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g., updates a product), receiving a legitimate request with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the shared `api_secret_key`).
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `H` against `B` [7](#0-6) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` [8](#0-7) , causing the host app to process attacker-controlled webhook content as if it originated from `victim-shop.myshopify.com`.
