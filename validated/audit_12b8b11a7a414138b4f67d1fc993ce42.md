### Title
Excess native-token dust from Uniswap swap is permanently stranded in `EvmHost` instead of being refunded to the dispatcher - ([File: evm/src/core/EvmHost.sol])

### Summary
When a user pays Hyperbridge dispatch/funding fees with native token (ETH), `EvmHost` forwards the *entire* `msg.value` to `swapETHForExactTokens` on the configured Uniswap V2-compatible router. Any leftover ETH from that swap (the difference between `msg.value` and the amount actually needed to buy `post.fee`/`get.fee`/`amount` of `feeToken`) is refunded by the router to `msg.sender` of the swap call — which is `EvmHost` itself, not the original caller who supplied the native token. `EvmHost` has no logic to forward this dust back to the user, and no admin/user-facing withdrawal path for it, so it becomes permanently stuck native token in the contract, analogous to the Allo `_createPool()` baseFee issue.

### Finding Description
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all follow the same pattern: if `msg.value > 0`, the full `msg.value` is passed to the router's `swapETHForExactTokens`, requesting an *exact* output amount (`post.fee`, `get.fee`, or `amount`): [1](#0-0) [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` (both the canonical Uniswap V2 router and the project's own wrapper implementations) only consumes as much ETH as needed to produce the exact output, and refunds the unused portion of `msg.value` to `msg.sender` — i.e., the account that invoked the router, which in this call chain is `EvmHost`, not the original transaction sender. This is explicit in the project's own `UniV3UniswapV2Wrapper`: [4](#0-3) 

The canonical `UniswapV2Router02.swapETHForExactTokens` behaves identically (`safeTransferETH(msg.sender, msg.value - amounts[0])`), and `msg.sender` there is likewise `EvmHost`.

`EvmHost` never reads or propagates this refund. It does not track or forward the returned dust to `post.payer`/`get.payer`/`_msgSender()`, and no `receive()`/withdrawal function exists in the reviewed sections to let anyone later recover this ETH. Because callers are explicitly told (in docs) to estimate fees off-chain via `quote()` (which is itself only approximate and vulnerable to slippage/sandwiching), any positive slippage or overestimation results in leftover ETH being silently absorbed by the contract with no recovery mechanism for the user: [5](#0-4) 

This mirrors the reported Allo `_createPool()` bug class: user overpays native token relative to the exact fee required, the excess is not returned to the payer, and it becomes permanently stuck in the contract.

### Impact Explanation
Any user who dispatches a POST/GET request or calls `fundRequest` with native token will lose the difference between the `msg.value` they sent and the exact ETH consumed by the swap, whenever that difference is nonzero (which is the common case — off-chain quotes are estimates, and the docs explicitly warn about sandwich-attack-induced slippage). This is a direct, permanent loss of user funds with no recovery path, affecting every native-token payer across `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`. Given native-token payment is advertised as the primary "user-facing" convenience path, this can affect a large volume of transactions and is rated High severity — permanent freezing/loss of user funds in a core message-dispatch path reachable by any unprivileged caller.

### Likelihood Explanation
Likelihood is high: this triggers on essentially every native-token dispatch where the actual swap cost differs even slightly from `msg.value`, which is the expected, documented behavior since users are told to add slippage buffers on top of `quote()` estimates and quoting is admittedly imprecise (subject to slippage/MEV). No malicious actor is even required — normal usage guarantees dust accumulation over time.

### Recommendation
After calling `swapETHForExactTokens`, capture the returned `amounts[0]` (ETH actually spent) and refund `msg.value - amounts[0]` back to `_msgSender()` (or the designated `payer`) instead of allowing the router to send the dust back to `EvmHost`. Apply this fix uniformly to `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` in `evm/src/core/EvmHost.sol`. Alternatively, add a mechanism where `EvmHost` immediately forwards any native token balance increase from the swap call back to the original caller within the same transaction.

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost{fee: F, ...})` with `msg.value = V` where `V` is intentionally (or due to slippage estimation error) greater than the ETH actually required to purchase `F` fee tokens.
2. `EvmHost` calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: V}(F, path, address(this), block.timestamp)`.
3. The router spends `amounts[0] < V` ETH and refunds `V - amounts[0]` to `msg.sender`, which is `EvmHost`'s own address (see `swapETHForExactTokens` refund logic at [4](#0-3) , mirroring the canonical Uniswap V2 router's behavior).
4. `EvmHost.dispatch` proceeds to emit the `PostRequestEvent` and return the commitment without ever inspecting or refunding `V - amounts[0]` — see the full function body at [6](#0-5) .
5. The dust ETH now sits in `EvmHost`'s balance permanently; the user has no function to reclaim it.

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

        // adjust the timeout
        uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
        PostRequest memory request = PostRequest({
            source: host(),
            dest: post.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            to: post.to,
            timeoutTimestamp: timeoutTimestamp,
            body: post.body
        });

        // make the commitment
        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});
        emit PostRequestEvent({
            source: string(request.source),
            dest: string(request.dest),
            from: _msgSender(),
            to: abi.encodePacked(request.to),
            nonce: request.nonce,
            timeoutTimestamp: request.timeoutTimestamp,
            body: request.body,
            fee: post.fee
        });
    }
