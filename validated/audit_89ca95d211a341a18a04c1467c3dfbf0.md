Audit Report

## Title
Silent, unrecoverable loss of on-demand orders during `MigrateV3ToV4` when the on-demand `OrderQueue` is user-filled to capacity - (File: polkadot/runtime/parachains/src/scheduler/migration.rs)

## Summary
`UncheckedMigrateToV4::on_runtime_upgrade` re-inserts surviving V3 `Assignment::Pool` claim-queue entries into the on-demand pallet via `on_demand::Pallet::<T>::push_back_order`, which silently drops the order on failure. Because `push_back_order` only bounds itself against the hard-coded `ON_DEMAND_MAX_QUEUE_MAX_SIZE` capacity of the underlying `BoundedVec`, rather than the governance-configured `on_demand_queue_max_size` enforced on normal user order placement, a chain whose configured limit is close to the hard cap can have already-paid orders permanently and silently dropped during the migration if the queue was filled by users beforehand.

## Finding Description
`push_back_order` calls `order_status.queue.try_push(now, para_id)` against a `BoundedVec<EnqueuedOrder<N>, ConstU32<ON_DEMAND_MAX_QUEUE_MAX_SIZE>>`, and on failure only emits a `debug`-level log with no error propagation, retry, or accounting correction: [1](#0-0) 

The user-facing `do_place_order` path (reached via signed extrinsics `place_order_with_credits`/`place_order_allow_death`) enforces admission against the runtime-configured `config.scheduler_params.on_demand_queue_max_size`, not the hard cap: [2](#0-1) 

`configuration.rs`'s consistency check only requires `on_demand_queue_max_size <= ON_DEMAND_MAX_QUEUE_MAX_SIZE`, permitting but not requiring headroom: [3](#0-2) 

During the V3→V4 migration, every surviving `Assignment::Pool` entry is pushed back via `push_back_order` with no capacity reservation and no fallback on failure — bulk assignments are intentionally dropped, but pool (paid) assignments are only "intended" to be preserved, not guaranteed: [4](#0-3) 

This confirms the reported root cause: the admission check in `do_place_order` that protects normal users from over-filling the queue is bypassed entirely by the migration's call path, which is bounded only by the wider hard-coded constant. If a chain's configured `on_demand_queue_max_size` is set near `ON_DEMAND_MAX_QUEUE_MAX_SIZE`, an attacker filling the queue via normal paid extrinsics leaves little slack for the migration to safely re-insert surviving pool entries, and any that don't fit are dropped with only a debug log.

## Impact Explanation
Pool assignments that fail `push_back_order` during the upgrade are permanently lost from on-demand scheduling: the affected `ParaId`s vanish from `peek_order_queue`, are never rescheduled, and there is no event, error, or recoverable state — only a debug log line. Since the funds/credits for these orders were already deducted in `do_place_order` prior to queueing, affected parachains lose paid-for core assignments with no refund path, causing concrete (though bounded and non-repeatable per upgrade) financial/service loss.

## Likelihood Explanation
This is a real but conditional bug: it requires (1) an unprivileged, funded attacker to fill the on-demand queue via `place_order_with_credits`/`place_order_allow_death`, which is trivial and repeatable, and (2) the chain's governance-configured `on_demand_queue_max_size` to be close enough to `ON_DEMAND_MAX_QUEUE_MAX_SIZE` that migration pushbacks (bounded by `num_cores * lookahead`) have no spare capacity. The migration itself runs exactly once per chain (at the V3→V4 storage-version transition), so the attack window is narrow and governance-dependent, but the code contains no defensive check, capacity reservation, or retry mechanism to guarantee lossless preservation regardless of concurrent queue occupancy, which is a genuine gap in the migration's stated invariant ("This ensures user-paid orders are not lost").

## Recommendation
In `UncheckedMigrateToV4::on_runtime_upgrade` (`polkadot/runtime/parachains/src/scheduler/migration.rs`), reserve capacity for in-flight pool assignments ahead of the migration (e.g., temporarily cap or pause new order admission before migrating, or check remaining `OrderQueue` capacity against the number of pool assignments to migrate and evict/compact as needed), and/or collect failed `push_back_order` results into a bounded auxiliary storage item for post-upgrade draining, emitting a countable event instead of only a debug log. Additionally, consider requiring `on_demand_queue_max_size` to maintain a safety margin below `ON_DEMAND_MAX_QUEUE_MAX_SIZE` in the configuration consistency check.

## Proof of Concept
1. Set `configuration::ActiveConfig::<Test>::mutate` so `scheduler_params.on_demand_queue_max_size == ON_DEMAND_MAX_QUEUE_MAX_SIZE` and `num_cores = 1`.
2. Fill `on_demand::pallet::OrderStatus::<Test>` to capacity via repeated `place_order_allow_death` calls from a funded signed account until `Error::QueueFull` is returned.
3. Seed `v3::ClaimQueue::<Test>::put` with an `Assignment::Pool { para_id: ParaId::from(9999), .. }` entry.
4. Set `StorageVersion::new(3)` and invoke `UncheckedMigrateToV4::<Test>::on_runtime_upgrade()`.
5. Assert `on_demand::Pallet::<Test>::peek_order_queue()` does not contain `ParaId::from(9999)` and it is never scheduled via `pop_assignment_for_cores`, confirming silent, permanent loss of the paid order.

		});
