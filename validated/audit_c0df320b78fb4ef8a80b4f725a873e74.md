Confirmed identity binding break: `ShopifyAPI::Webhooks::Request#shop` is read from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header [1](#0-0) , while the HMAC signature that `Registry.process` validates via `Utils::HmacValidator.validate(request)` is computed only over `to_signable_string`, which returns the raw request body and nothing else [2](#0-1) . The `shop` value is then trusted and forwarded to the app's webhook handler as tenant identity in `WebhookMetadata` without any re-verification [3](#0-2) [4](#0-3) .

### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is completely outside the scope of the HMAC signature Shopify computes and the gem verifies. Only the raw body is signed/verified, so an attacker who can trigger (or replay) one legitimately-HMAC-signed webhook payload for their own store can relabel it as coming from any other shop, and the app's handler will process it under the wrong tenant's identity.

### Finding Description
The gem's webhook trust model is: verify HMAC over the request, then trust the request's exposed attributes. `Utils::HmacValidator.validate` computes/compares the signature strictly against `verifiable_query.to_signable_string`: [5](#0-4) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop` (the tenant identity used downstream) is read from a header, not from the signed body: [1](#0-0) 

`Registry.process` validates the HMAC of the request as a whole, then unconditionally trusts `request.shop` to build `WebhookMetadata` handed to the app-defined handler: [3](#0-2) 

This breaks the intended identity binding: **shop claimed via header == shop covered by HMAC**. In reality, the HMAC only authenticates "this body was produced by someone holding `api_secret_key`" — it says nothing about which shop the header claims to be from. Any attacker who can get one valid signed body (e.g., by triggering a real webhook for their own, legitimately-installed shop, or capturing one in transit to their own server) can resend that exact body with an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header. `HmacValidator.validate` still returns true because the signature check never looks at the header, and the handler receives `WebhookMetadata#shop` set to the attacker-chosen value.

### Impact Explanation
This is a cross-tenant identity/authentication boundary break inside the gem: the shop identity that the handler receives as authenticated (having "passed HMAC verification") is in fact unauthenticated attacker-controlled input. Downstream apps commonly key session/data lookups by `data.shop` (as shown in the gem's own documented usage pattern), so a forged shop label lets an attacker inject data attributed to a victim shop or trigger shop-scoped side effects (e.g., job processing, cache/database writes, deduplication keyed by shop) under a tenant they do not control — a cross-tenant access condition.

### Likelihood Explanation
Requires the attacker to possess at least one validly-signed webhook body, which is achievable via their own app installation/shop (any developer/merchant that installs the app receives real, validly-HMAC-signed webhooks) or interception of an in-flight webhook delivery. No access to `api_secret_key` is needed. The header value is a plain HTTP header, trivially rewritable when replaying the captured/self-generated request to the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/api-version/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind the resolved `shop` to the same authenticated bytes as the body, so `Utils::HmacValidator.validate` cannot pass for a request whose header-derived `shop` differs from the shop that produced the signed payload. At minimum, document that `request.shop`/`WebhookMetadata#shop` is unauthenticated and must not be used as the sole tenant key without additional server-side verification (e.g., cross-checking against a known list of shop domains associated with a stored webhook subscription/id).

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger a subscribed webhook topic (e.g., `orders/create`) so Shopify delivers a request with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's real `api_secret_key`.
2. Capture the raw body and the valid HMAC value from that request.
3. Replay the exact same raw body and HMAC to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-computes the HMAC over `request.to_signable_string` (`@raw_body`), never inspecting the shop header: [6](#0-5) [7](#0-6) 
5. The app's handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and processes the attacker's payload as if it originated from the victim shop.
