### Title
Webhook `shop` (and `topic`/`webhook-id`/`api-version`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body [5](#0-4) . The `shop` identity that the gem hands to the app's webhook handler, however, comes from the `shopify-shop-domain` HTTP header, which is never part of the signed bytes [4](#0-3) [1](#0-0) . This breaks the equality the gem is implicitly promising the host application: `hmac_is_valid(body) == shop_header_is_authentic`. In fact, only the body's authenticity is proven; the shop header's authenticity is not.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it (constant-time) to the `hmac` field [6](#0-5) . For `Webhooks::Request`, `to_signable_string` is simply `@raw_body` [1](#0-0) ; none of the HTTP headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) participate in the signature. `Registry.process` nonetheless trusts `request.shop` (and `request.topic`, etc.) as authenticated tenant/topic context and forwards it directly into `WebhookMetadata` passed to the app's handler [3](#0-2) .

Because the same `client_secret` is used to sign webhooks for every shop that has installed the app, a merchant who has legitimately installed the app (an unprivileged actor with respect to *other* tenants) receives genuine `(raw_body, hmac)` pairs for their own shop. That merchant can replay the exact same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `x-shopify-topic`) with a different shop's domain. `Utils::HmacValidator.validate` still returns `true` because the body is unchanged, and `Registry.process` will invoke the handler with `shop: request.shop` set to the victim shop, even though the body content came from the attacker's own installation event.

### Impact Explanation
This is a cross-tenant identity binding failure inside the gem's own webhook-processing code: the field the host application acts on (`shop`) is not covered by the verification mechanism (`HMAC over raw_body`) that is supposed to authenticate the request. Any app that uses `request.shop` from `WebhookMetadata` to select which tenant's session/data to write to (a documented, expected usage per `docs/usage/webhooks.md`) can be tricked into attributing/processing another merchant's webhook data under the attacker-chosen shop domain — i.e., cross-tenant access/data confusion, satisfying the Critical "cross-tenant access" category.

### Likelihood Explanation
Moderate-to-high: exploitation only requires being a normal (even unprivileged) installed merchant of the target app who can capture one legitimate webhook delivery (trivial, since apps receive webhooks routinely) and replay it with a modified header, which is a simple unauthenticated HTTP request — no access token, `client_secret`, or privileged account is needed.

### Recommendation
Bind the identifying headers into the signed content that `HmacValidator` checks for webhooks — e.g., by including `shop`, `topic`, and `webhook_id` in `to_signable_string` (or, at minimum, requiring callers to independently verify that the resolved `shop` corresponds to a session/store the app expects for that specific webhook subscription) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. App has processed a legitimate webhook for `shop-a.myshopify.com`: attacker (who controls shop-a) records `raw_body` and the `x-shopify-hmac-sha256` header from a webhook Shopify sent to the app.
2. Attacker POSTs the same `raw_body` to the app's webhook endpoint but sets `x-shopify-shop-domain: shop-b.myshopify.com` (a shop they do not control) while keeping the original valid `x-shopify-hmac-sha256`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers (no cross-check between `shop-domain` and `hmac`) [7](#0-6) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` (`raw_body`) is unchanged [5](#0-4) .
5. The handler is invoked with `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)`, causing the app to process attacker-controlled data as if it originated from `shop-b`.
