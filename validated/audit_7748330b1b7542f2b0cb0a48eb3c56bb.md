### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC exclusively over that body. The `shop-domain` header, which is later trusted and forwarded verbatim to the app's webhook handler as the tenant identifier, is never part of the signed material. An attacker who can obtain one legitimately-signed webhook body (e.g., by installing the app on their own store and triggering any webhook) can replay that exact body with a forged `x-shopify-shop-domain` header pointing at a victim shop, and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC to `@raw_body` only: [1](#0-0) 

`shop` is read from an unauthenticated header and is not included in the signable string: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature strictly against `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` only calls `HmacValidator.validate(request)` and then unconditionally trusts `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The equality being broken is: **shop header used by the handler == shop bound by the HMAC signature**. The gem only guarantees `raw_body == HMAC-verified(raw_body)`; it never establishes `shop-domain header == HMAC-verified(shop-domain)`. This is directly analogous to the GMX report pattern of "a field acted on but not covered by the [signature/slippage] check" — here, `shop` is acted on (passed to the handler as the source-of-truth tenant identifier) but is not bound by the cryptographic check that is supposed to authenticate the whole request.

### Impact Explanation
Any unprivileged actor who can get the target app installed on a shop they control (a normal, permitted, self-service action — installing an app on your own store/dev store requires no special privilege) can capture one legitimately HMAC-signed webhook payload for a topic of their choosing. They can then replay that identical body to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because the header isn't part of the signed content, and `Registry.process` calls the app's handler with `shop: <victim-shop>` and attacker-controlled body content. Any app logic that trusts `data.shop` to key writes, background jobs, or cross-tenant identifiers (as the gem's own documentation examples show: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be tricked into attributing forged/attacker-chosen data to a shop the attacker does not control — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation requires no secrets, no access token, and no knowledge of `api_secret_key` — only a body+signature pair that Shopify legitimately delivered to the attacker's own installed instance of the app, plus knowledge of the victim's `myshopify.com` domain (public information). Replaying an HTTP request with one modified header is trivial.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is cryptographically verified, or independently authenticate `request.shop` against the shop associated with the specific webhook subscription (e.g., verify the shop is one your app has installed/registered a webhook for, and correlate the `webhook-id` to the shop that owns the corresponding subscription) before trusting it. At minimum, document prominently that `shop` in `WebhookMetadata` is not authenticated by the HMAC and must be independently validated by the host application against known installed shops before being used for any tenant-sensitive operation.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers for `orders/create`.
2. Attacker places an order, receiving a legitimate webhook POST with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
3. Attacker resends the exact same request to the app's webhook endpoint, only replacing the header `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`. The `x-shopify-hmac-sha256: H` header is left unchanged.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a request whose `to_signable_string` is still `B`.
5. `ShopifyAPI::Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(secret, B) == H` and returns `true`.
6. `ShopifyAPI::Webhooks::Registry.process(request)` invokes the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed_body_of_B, ...)`, causing the app to process attacker-supplied order data as if it belonged to `victim.myshopify.com`.
