## Title
Missing shop-domain validation in `Oauth.begin_auth` allows the OAuth authorization redirect to be sent to an attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorization URL directly from the caller-supplied `shop` string with no validation that it is a genuine Shopify domain, unlike every other credential-issuing entry point in the gem.

### Finding Description
`begin_auth` takes an arbitrary `shop:` string and passes it straight into `auth_base_uri(shop)`, which simply interpolates it into `"https://#{shop}/admin"`: [1](#0-0) [2](#0-1) 

No call to `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) is made. That validator exists specifically to prevent exactly this class of bug — accepting an "attacker-controlled domain" as the shop — and is applied everywhere else a `shop` string is turned into a request host: [3](#0-2) [4](#0-3) [5](#0-4) 

The `ShopValidator` module and its test suite explicitly document the threat this closes: [6](#0-5) [7](#0-6) 

The binding that should hold is: `host(auth_route)` (the domain that receives the app's `client_id`, requested `scope`, `redirect_uri`, and the freshly generated OAuth `state` nonce) must equal a `ShopValidator`-trusted Shopify domain. In `begin_auth`, `host(auth_route) == shop` unconditionally, with `shop` fully attacker/caller-controlled — the equality is never checked. Apps commonly forward a request parameter (e.g. a `shop` query param or header, as shown in the gem's own docs) straight into `begin_auth`, so an attacker can supply e.g. `attacker.example` as the shop and cause the app to redirect the merchant's browser to `https://attacker.example/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=...&state=...`, along with a `state` cookie set for that flow.

### Impact Explanation
This is a forced-OAuth/host-confusion vector: the app's `client_id`, requested access `scope`, and the fixed `redirect_uri` are sent to a host of the attacker's choosing rather than to Shopify, and a legitimate OAuth `state` nonce/cookie is issued for that attacker-directed flow. This matches the "session fixation or forced OAuth completion" High-impact category — the victim can be induced to complete part of the OAuth ceremony against a domain the attacker controls, enabling phishing of the merchant or manipulation of the flow the app believes it initiated.

### Likelihood Explanation
Any host application that plumbs user- or request-supplied shop input into `begin_auth` without its own separate validation is affected; the gem's own documentation shows exactly this pattern (`shop = request.headers["Shop"]` passed directly to `begin_auth`). Because the gem provides no built-in check here — unlike its sibling flows — this is easy to trigger for any unprivileged caller who can influence the `shop` value reaching `begin_auth`.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (as done in `client_credentials.rb`, `refresh_token.rb`, and `token_exchange.rb`) at the top of `Oauth.begin_auth` before constructing `auth_base_uri`, so only trusted Shopify domains can be targeted by the generated `auth_route`.

### Proof of Concept
1. Host app exposes a login endpoint that calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")`, mirroring the documented usage pattern.
2. Attacker sends `shop=attacker.example` (or links the victim to the app's login route with that value).
3. `begin_auth` returns `auth_route = "https://attacker.example/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=https://app-host/auth/callback&state=<nonce>"` and a `SessionCookie` bound to that nonce.
4. The app 307-redirects the merchant's browser to `attacker.example`, leaking the app's `client_id`/scope/redirect target to that host and completing the "begin" half of OAuth against an attacker-controlled domain.

```ruby
        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
```

```ruby
        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
```
