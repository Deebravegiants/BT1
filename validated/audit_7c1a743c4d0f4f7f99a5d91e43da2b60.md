### Title
Timelock-elapsed bypass allows already-pending malicious multisig transactions to execute instantly once a timelock is (re)activated - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The `MultisigAccountTimeLock` feature (`aptos-move/framework/aptos-framework/sources/multisig_account.move`) is meant to force a delay between a multisig transaction gathering enough approvals and its execution, giving owners a reaction window to reject a malicious proposal. The elapsed-time check is computed from the transaction's original `creation_time_secs`, not from when the timelock was actually activated. This is the same bug-class as the Notional oracle-rate report: a defensive time window is measured against a clock that an attacker (or circumstance) can make stale, letting the "protection" already appear expired the instant it is turned on.

### Finding Description
`MultisigTransaction.creation_time_secs` is set once, when a transaction is proposed [1](#0-0) . The gate that is supposed to enforce the timelock is `can_execute_with_timelock`: [2](#0-1) 

It computes `elapsed = now_seconds() - pending_transaction.creation_time_secs` and allows execution once `elapsed >= timelock`. This value is compared against whatever `timelock_period` is configured **at the time of execution**, not at the time the transaction was created. `upsert_timelock`/`upsert_timelock_internal` can add or change the timelock config at any point via the normal owner-quorum flow [3](#0-2) .

The module's own doc comment on `upsert_timelock` acknowledges this design gap, but only analyzes the case where a timelock is being *updated* (i.e., a prior timelock already existed), calling the resulting window "bounded by the previous timelock period" and calling it acceptable [4](#0-3) . It does not address the case where **no timelock existed previously** (the common "we just realized we need a timelock" emergency-response scenario): a pending transaction can be created and sit in the queue indefinitely (there is no expiry on pending transactions; `MAX_PENDING_TRANSACTIONS` only caps count, not age — see `available_transaction_queue_capacity` [5](#0-4) ). If owners then activate a timelock via `upsert_timelock` to slow down execution of a suspicious pending transaction, `elapsed` for that already-old transaction can already exceed the newly-configured `timelock_period` (max 14 days, min 1 hour, per `MIN_TIMELOCK_PERIOD`/`MAX_TIMELOCK_PERIOD` [6](#0-5) ), so the defense provides **zero** actual delay for that transaction — it is immediately executable the moment quorum is reached, defeating the entire purpose of the just-added safeguard.

Because `add_owners`, `remove_owners`, `update_signatures_required`, and even auth-key rotation/signer-capability revocation are all executed through this same multisig transaction flow, this stale-clock bypass directly threatens custody: a pending transaction that (for example) swaps in an attacker-controlled owner, lowers `num_signatures_required`, or transfers the resource account's `signer_cap` can be finalized the instant the last approval lands, with the timelock the honest owners just enabled offering no real protection.

### Impact Explanation
This breaks the intended custody-protection invariant of the multisig timelock: "any transaction, once it obtains quorum, must wait `timelock_period` before execution unless override_threshold is met." A resource-account/multisig-account-controlled asset (APT, fungible assets, capabilities) can be moved or ownership-changed with no real timelock delay, precisely in the scenario where the timelock was added specifically to buy reaction time against a suspected malicious proposal. This is high impact because it can lead to irreversible custody loss (owner-list takeover, signer-capability transfer, auth-key rotation) despite an active, correctly-configured timelock.

### Likelihood Explanation
Requires that (a) the multisig timelock feature is enabled (`features::is_multisig_timelock_enabled()`), (b) a transaction has been pending long enough (or the timelock is being added for the first time on an existing old pending transaction) that `now() - creation_time_secs` already exceeds the newly-configured `timelock_period`, and (c) the transaction reaches quorum after the timelock is enabled. This is a realistic "emergency response" scenario — owners react to a suspicious pending proposal by trying to add a timelock — so likelihood is moderate to high, similar to the medium risk the Notional judge assigned given the alignment of conditions required.

### Recommendation
Do not derive the timelock deadline solely from `creation_time_secs` compared to the timelock configuration active at execution time. Instead, record the timelock parameters (or an explicit `unlock_time_secs`) that applied to the queue at the moment of activation, and for any transaction already pending when a timelock is introduced/updated, require the full `timelock_period` measured from the activation time (or from whichever is later, `creation_time_secs + timelock_period` or `timelock_activation_time_secs + timelock_period`), rather than allowing already-elapsed wall-clock time predating the timelock's existence to count toward satisfying it.

### Proof of Concept
1. Multisig account M has `num_signatures_required = 3`, no timelock configured, 5 owners.
2. Owner A creates a malicious transaction (e.g., `swap_owner` to add a colluding address) at `t0`. Two owners approve; quorum of 3 not yet reached.
3. Time passes — 20 days (`t0 + 1,728,000s`), well beyond `MAX_TIMELOCK_PERIOD` (14 days = 1,209,600s).
4. Honest owners notice the risk and, via a separate quorum vote, call `upsert_timelock(M, timelock_period = 1_209_600 /*14 days*/, override_threshold = none)` to slow down any future execution.
5. Immediately afterward, the third malicious/colluding approval arrives for the original pending transaction (sequence number unchanged, `creation_time_secs = t0`).
6. `can_execute_with_timelock` computes `elapsed = now() - t0 ≈ 1,728,000s`, which is `>= timelock_period (1,209,600s)`, so it returns `true` — the transaction executes instantly, with the newly-added timelock providing no delay at all, exactly as the code comment predicts but does not prevent for the "first-time activation" case [2](#0-1) .

**Note on verification**: I was not able to fully trace whether any additional VM-level or governance-level safeguard resets `creation_time_secs` on config changes elsewhere in the codebase (the file is 3215 lines and only the first ~1120 lines plus targeted greps were reviewed within the available iterations); a Devin session with full file access should confirm there is no such reset before treating this as final.

    /// Return true if the transaction with given transaction id can be executed immediately, or it has to wait
    /// for the timelock to expire.
    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }

    entry fun upsert_timelock(multisig_account: &signer, timelock_period: u64, override_threshold: Option<u64>) {
        assert!(
            features::is_multisig_timelock_enabled(),
            error::unavailable(ETIMELOCK_NOT_ENABLED)
        );
        upsert_timelock_internal(multisig_account, timelock_period, override_threshold);
    }

    /// Shared validation + publish logic for timelock configuration. Used by `upsert_timelock` and
    /// by the creation-time variants (`create_with_owners_and_timelock`, ...) so the invariant that
    /// `MultisigAccountTimeLock` is only ever published through a single validated path is preserved.
    fun upsert_timelock_internal(
        multisig_account: &signer,
        timelock_period: u64,
        override_threshold: Option<u64>,
    ) {
        let multisig_address = address_of(multisig_account);
        assert_multisig_account_exists(multisig_address);

        assert!(
            timelock_period >= MIN_TIMELOCK_PERIOD && timelock_period <= MAX_TIMELOCK_PERIOD,
            error::invalid_argument(EINVALID_TIMELOCK_DURATION)
        );

        let multisig_account_resource = &MultisigAccount[multisig_address];
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() > multisig_account_resource.num_signatures_required,
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() <= multisig_account_resource.owners.length(),
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );

        if (exists<MultisigAccountTimeLock>(multisig_address)) {
            let multisig_account_resource = &mut MultisigAccountTimeLock[multisig_address];
            multisig_account_resource.timelock_period = timelock_period;
            multisig_account_resource.override_threshold = override_threshold;
        } else {
            move_to(multisig_account, MultisigAccountTimeLock::V1 {
                timelock_period,
                override_threshold,
            });
        }

        emit(TimelockUpdated {
            multisig_account: multisig_address,
            timelock_period,
            override_threshold,
        });
    }
