### Title
Per-route withdrawal index in `createWithdrawalIdentifiers` ignores `signedIntents.before`/`.after`, causing `OmniBridge.describeWithdrawal` to report the wrong transfer's (status, txHash) - (File: `packages/intents-sdk/src/core/withdrawal-watcher.ts`, `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`)

### Summary
`createWithdrawalIdentifiers` assigns each `WithdrawalIdentifier.index` purely by counting entries in the integrator-supplied `withdrawalParams` array per bridge route, with no knowledge of any Omni Bridge withdrawals embedded in pre-signed `signedIntents.before`/`.after` payloads that get published atomically in the same NEAR transaction. `OmniBridge.describeWithdrawal` then uses that index to select an item from `omniBridgeAPI.getTransfer({transactionHash})`, which reflects the *actual* on-chain order of all Omni Bridge transfers triggered in that transaction — including ones from `before`/`after`. If an attacker-supplied `before` payload contains an Omni Bridge withdrawal, the true transfer order shifts and the integrator's own withdrawal is described using another transfer's status/hash.

### Finding Description
The broken equality is:

`WithdrawalIdentifier.index` (as assigned in `createWithdrawalIdentifiers`, packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107) `==` position of the integrator's withdrawal among Omni-Bridge transfer events actually recorded on-chain for `intentTx.hash` (as consumed by `getTransfer({transactionHash})[args.index]` in `omni-bridge.ts:694-698`).

`signedIntents` is an attacker-controllable field per the rules ("a counterparty whose strings an integrator forwards into the SDK ... signedIntents"), composed via `composeMultiPayloads` (`intent-executer.ts:190-214`) as `[before…, newPayload, after…]`, and published together with `publishIntents` → `execute_intents(signed: MultiPayload[])` in a single NEAR transaction (`contract-types/artifacts/defuse_contract_abi.json:906-921`, `intent-relayer-public.ts:44-71`). `waitForSettlement` returns one `intentTx.hash` for that whole transaction (`intent-relayer-public.ts:73-92`).

`createWithdrawalIdentifiers` only iterates `args.withdrawalParams` (the integrator's own array), computing `currentIndex` per `bridge.route` without any visibility into what `before`/`after` MultiPayloads contain [1](#0-0) . If an attacker's `before` payload independently performs an Omni Bridge `ft_withdraw`, that transfer appears first in the actual transaction and is the first entry the indexer returns for `getTransfer({transactionHash})`, but the integrator's own withdrawal is still assigned `index: 0` by the SDK. `describeWithdrawal` then returns the attacker's transfer's status/hash for the integrator's withdrawal [2](#0-1) .

Existing guards do not catch this: `validateWithdrawal`, `supports()`, `compareAddresses`, and the intents contract's own signature/nonce checks all validate the *content* of each individually signed intent, but none of them verify that the position of a bridge withdraw intent inside the composed, atomically-published payload sequence matches the index the SDK later uses to query bridge status. This is purely an SDK-side bookkeeping gap.

### Impact Explanation
An integrator polling `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` for their own withdrawal can receive `{status: "completed", txHash: <someone else's tx hash>}` while their own withdrawal is still pending, stuck, or was refunded. If the integrator credits the user or clears an internal ledger entry based on that (status, txHash) pair, they can be tricked into crediting a withdrawal that never actually landed — matching the "High: status or hash misreport making an integrator credit or refund twice" category. The attack is repeatable per batch where the integrator accepts attacker-supplied `signedIntents`.

### Likelihood Explanation
Requires the integrator to accept externally-supplied `signedIntents.before`/`.after` (an explicitly documented, attacker-reachable feature per the rules) and to route the integrator's own withdrawal through OmniBridge (or any bridge whose `describeWithdrawal` indexes into a shared per-transaction transfer list). The attacker only needs a valid, previously-signed MultiPayload of their own performing an Omni Bridge withdrawal — no privileged access required, and the technique is reusable on every batch the integrator processes this way.

### Recommendation
Compute `WithdrawalIdentifier.index` from the true position of each withdraw intent within the fully composed payload sequence (including `before`/`after`), not from the integrator's own `withdrawalParams` array alone — e.g., by having `createWithdrawalIdentifiers`/`signAndSendWithdrawalIntent` propagate the actual global offset (`beforeCount` plus position within the caller's intents) into the identifier, or by having `describeWithdrawal` match transfers by a stable per-intent correlation ID (e.g., derived from the specific intent's hash/nonce) rather than positional array indexing into `getTransfer()`.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const transfer = (
			await this.omniBridgeAPI.getTransfer({
				transactionHash: args.tx.hash,
			})
		)[args.index];

		if (transfer == null || transfer.recipient == null) {
			return { status: "pending" };
		}

		const destinationChain = getChain(transfer.recipient as OmniAddress);
		let txHash = null;
		if (
			isEvmChain(destinationChain) ||
			destinationChain === ChainKind.Sol ||
			destinationChain === ChainKind.Fogo ||
			destinationChain === ChainKind.Strk ||
			destinationChain === ChainKind.Aptos
		) {
			txHash = transfer.finalised?.transaction_hash;
		} else if (isUtxoChain(destinationChain)) {
			// pending_sign_id is not the finalised tx hash. In rare cases, the hash may
			// change if the BTC transfer fails to be submitted. We return fast hash for FE and
			// wait for final one (transfer.finalised?.transaction_hash) for BE.
			txHash =
				typeof window !== "undefined"
					? transfer.utxo_meta?.pending_sign_id
					: transfer.finalised?.transaction_hash;
		} else {
			return { status: "completed", txHash: null };
		}

		if (!txHash) {
			return { status: "pending" };
		}

		return { status: "completed", txHash };
	}
