### Title
Withdrawal status matched only by `assetId`, causing cross-withdrawal status/hash misreport in batched POA Bridge withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain outcome of a specific withdrawal by looking up the POA Bridge's withdrawal list and matching purely on `assetId`, discarding the `index`, destination address and amount that uniquely identify which withdrawal in a batch the caller is asking about. When a caller issues multiple withdrawals of the *same* asset in one signed intent (a normal, supported flow via `signAndSendWithdrawalIntent`'s batch support), the status/tx-hash reported for withdrawal N can actually belong to a different withdrawal of the same asset.

### Finding Description
`describeWithdrawal` explicitly matches "by assetId instead of index" because the POA API response list is unsorted: [1](#0-0) 

The `WithdrawalIdentifier` type carries an `index` field specifically meant to distinguish multiple withdrawals within the same NEAR transaction: [2](#0-1) 

The SDK explicitly supports batching multiple withdrawals into a single signed intent transaction, tracking each by index: [3](#0-2) 

The repo's own test suite documents the matching logic operates solely on `assetId`, not `index`: [4](#0-3) 

In that test, correctness only holds because the two withdrawals had *different* `assetId`s (eth vs btc). Nothing in `findMatchingWithdrawal`'s contract (as invoked from `describeWithdrawal`, taking only `response.withdrawals` and `args.withdrawalParams.assetId`) disambiguates two withdrawals sharing the same `assetId` but different destination addresses/amounts — e.g. a batch withdrawing BTC to two different addresses in one transaction. Both entries in the unsorted POA response satisfy the same match predicate, so whichever one `Array.find`-style logic returns first is used for every index of that asset in the batch. The `withdrawal-watcher.ts` polling loop then treats whatever status/hash comes back as the ground truth for that specific `WithdrawalIdentifier`: [5](#0-4) 

This breaks the equality "status/hash reported == the on-chain outcome of *this* withdrawal." An integrator polling per-index status for a batch of same-asset withdrawals can be told withdrawal #0 is `completed` with a `transfer_tx_hash` that actually belongs to withdrawal #1 (or vice versa), while the real #0 is still pending or failed.

### Impact Explanation
If an integrator uses the reported `completed` status + `txHash` to release goods, mark an off-chain ledger as settled, or trigger a secondary payout, a same-asset batch withdrawal misreport can cause the integrator to credit/settle the wrong (or non-existent) transfer — matching the rule's High-impact class "a status or hash misreport making an integrator credit or refund twice." The actual destination funds are still delivered correctly on-chain (POA bridge itself is unaffected), but the SDK-reported status for a given index is not proven to correspond to that index's own outcome.

### Likelihood Explanation
Requires an integrator to batch two or more withdrawals of the identical `assetId` (e.g., two BTC withdrawals to different recipients) within one signed intent and to rely on per-index `describeWithdrawal`/`watchWithdrawal` results — a scenario directly supported and exercised by the SDK's own batch withdrawal API, not an unusual or malicious usage pattern.

### Recommendation
Disambiguate matches in `findMatchingWithdrawal` (and its counterpart in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) using additional identifying fields returned by the POA API for each withdrawal record — destination address, amount, and/or a per-withdrawal sequence/nonce — rather than `assetId` alone, so each `WithdrawalIdentifier.index` maps deterministically to its own POA withdrawal record.

### Proof of Concept
1. Call `sdk.signAndSendWithdrawalIntent` with `withdrawalParams` array containing two BTC withdrawals (same `assetId: "nep141:btc.omft.near"`) to two different destination addresses/amounts, batched in one NEAR tx.
2. The POA relayer processes both, returning an unsorted `withdrawals` list containing two `nep141:btc.omft.near` entries with different `transfer_tx_hash`/status.
3. Call `bridge.describeWithdrawal` for index 0 and index 1 (or let `watchWithdrawal` poll both). Because `findMatchingWithdrawal` filters only on `assetId`, both indices can resolve to the same withdrawal record — as demonstrated by the analogous test at `poa-bridge.test.ts:1054-1111`, which relies on *different* assetIds to get correct matching, showing there is no protection when assetIds are identical.

I could not view the exact body of `findMatchingWithdrawal` (its definition line wasn't retrieved before the tool budget ran out), so the precise matching predicate (e.g., whether it uses `Array.find` returning the first match, or `Array.filter` with different resolution) is not fully confirmed — this should be verified directly in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` before treating this as fully conclusive.
