`ShopifyAPI::Auth::Oauth.begin_auth` builds the OAuth authorize redirect from an unsanitized `shop` parameter - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`Oauth.begin_auth` interpolates the caller-supplied `shop:` argument directly into `auth_base_uri(shop)`, producing `"https://#{shop}/admin"` without ever calling `Utils::ShopValidator.sanitize!`. Every other OAuth-adjacent flow in the gem (`token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`) validates the shop through `ShopValidator.sanitize!`, but `begin_auth` does not, breaking the intended invariant that the OAuth redirect target is always a trusted Shopify domain.

### Finding Description
Binding claimed: `auth_route host == ShopValidator.sanitize!(shop)` (i.e., the redirect target must always be a value accepted by `Utils::ShopValidator`).

Tracing `begin_auth` in [1](#0-0) , the `shop` parameter is only Sorbet-typed as `String` — there is no call to `Utils::ShopValidator.sanitize!` anywhere in the method. It is passed straight to the private `auth_base_uri` helper: [2](#0-1) 

which returns `"https://#{shop}/admin"` unless the dev-server branch is taken. This string becomes the host of `auth_route` returned to the caller, which host apps redirect the merchant's browser to. By contrast, `ShopValidator.sanitize!` — defined in [3](#0-2)  — is used to validate shop input in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, showing that the gem's own design intent is to sanitize any shop value before it is trusted, but `begin_auth` omits this step.

Attacker request: a host app built "as documented" typically passes the raw `shop` query parameter from the install/login request straight into `begin_auth(shop: params[:shop], ...)`. An attacker requests `/login?shop=attacker.example` (or any other host); `begin_auth` returns `auth_route = "https://attacker.example/admin/oauth/authorize?client_id=...&scope=...&redirect_uri=...&state=..."`. If the host app redirects the merchant's browser to `auth_route` (the documented usage), the merchant is sent to `attacker.example` instead of a `*.myshopify.com` domain, along with the real `client_id`, `scope`, and `redirect_uri` in the query string. `Context.setup?` and `Context.private?` checks in `begin_auth` do not validate the shop value at all, and no HMAC/state validation applies at this stage (state/HMAC only guard the *callback*, not the *outgoing* redirect target), so nothing else in the code path prevents this divergence.

### Impact Explanation
An attacker-controlled `auth_route` host means the merchant's browser is redirected to a server chosen by the attacker, carrying the app's real `client_id`, requested `scope`, and `redirect_uri`. This is textbook forced-redirect/SSRF-adjacent (open redirect from the app's login flow) and matches the "High - SSRF driving an authenticated request to an unintended host / forced OAuth completion" category: the attacker can present a convincing fake Shopify authorize page at their own host and, if the merchant is tricked into entering credentials there or is chained with a real Shopify authorize flow, harvest the OAuth `code` before it is ever handed to the legitimate app. This is repeatable against any merchant who reaches the affected app's install endpoint with an attacker-supplied `shop` value, since the flaw is in the gem's `auth_base_uri` construction and not tied to any single shop.

### Likelihood Explanation
Requires only that the host app pass an unsanitized `shop` value into `begin_auth`, which is the pattern the question states many host apps follow (raw `shop` query param from the install request) and is consistent with the fact that the gem itself provides no sanitization inside `begin_auth`. No credentials, secrets, or privileged access are needed — the attacker only needs to control the `shop` query parameter of a request to the app's own login/install route, which is by definition attacker-controlled input. This is a very low-cost, easily repeatable attack against any deployment that mirrors the documented `begin_auth` usage without adding its own sanitization layer.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop, myshopify_domain: ...)` at the top of `begin_auth` (mirroring `token_exchange.rb`/`client_credentials.rb`/`refresh_token.rb`) and use the sanitized/returned host in `auth_base_uri`, raising `Errors::InvalidShopError` for any value that isn't a trusted Shopify domain.
