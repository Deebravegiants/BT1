## Analysis

Looking at `Router.buy()` and `Pair.swap()`, the same root-cause pattern from the Sherlock finding — crediting internal accounting by a *stated* transfer amount instead of the *actually received* balance — is present in alt.fun's curve AMM for its reserve asset (the BounceTech LT). [1](#0-0) 

`Router.buy()` computes `amountInUsed` from the K-invariant, pulls that exact amount from the trader into the `Pair` via `safeTransferFrom`, and then unconditionally tells `Pair.swap()` that `amountInUsed` of asset came in: [2](#0-1) 

`Pair.swap()` blindly adds the passed-in `assetIn` to `_pool.assetReserve` — it never re-checks `IERC20(assetToken).balanceOf(address(this))`: [3](#0-2) 

The asset side of every pair is the external BounceTech LT — not alt.fun's own `Token.sol` (which is a plain OZ `ERC20Upgradeable` with no fee hooks, confirmed at `Token.sol:18-44`). alt.fun explicitly documents this LT as an untrusted external reserve asset read via `exchangeRate`/`baseToLtAmount`/`ltToBaseAmount`/`minTransactionSize`, and separately calls out that BounceTech can change LT behavior (e.g., de-registering an LT, pausing `mint`) without alt.fun's control — the codebase already treats the LT's transfer semantics as something it must defensively handle, not something it can assume. [4](#0-3) 

If the LT ever skims any amount on a plain `transferFrom` (a fee-on-transfer path distinct from its documented mint/redemption fees, which only fire inside `mint`/`redeem`, not on `transfer`), `Pair._pool.assetReserve` becomes permanently inflated relative to the Pair's real LT balance (`Pair.assetBalance()`), because `swap()` never reconciles against `balanceOf`. There is no invariant anywhere in `Pair.sol`, `Router.sol`, or the invariant test suite (`test/GraduationInvariants.t.sol`) that ties `assetReserve` back to the real balance — the K-check `(newTokenReserve+1)*(newAssetReserve+1) < _pool.k` operates purely on the stored counters.

## Impact

Once `assetReserve` overstates the real LT balance held by the `Pair`:
- `Router._computeSell` computes `assetOut` from the (now-inflated) stored `reserveAsset`, so a seller near the tail of the curve can be quoted/owed more real LT than the `Pair` actually holds.
- `Pair.transferAsset` (called from `Router.sell`) performs a real `safeTransfer`, which reverts if the Pair's actual LT balance is insufficient — permanently freezing that seller's ability to exit via the curve, since every subsequent sell attempt against the same stale-inflated reserve keeps reverting.
- The graduation drain (`Router.graduate`, called from `Bonding._prepareGraduationLiquidity`) also computes `ltFromPair = reserve1 - virtualLtReserve` off the stored reserve and attempts a real `transferAsset` for that amount — an under-collateralized pair can make the threshold-crossing buy's inline phase-1 graduation revert, trapping the token's curve state.

This is the same class of bug as the referenced Sherlock finding: an amount that should be measured by balance delta is instead trusted at face value, only here it's the internal AMM reserve accounting (`Pair.swap`) rather than a share-mint step, and the "deflationary" asset is alt.fun's own configurable external reserve token (the LT) rather than a generic ERC20.

## Caveat

This analog's severity is conditional on whether the specific BounceTech LT contracts (or any that alt.fun's permissionless `Bonding.launch` accepts via `ltExists`) ever apply a fee on plain ERC20 `transfer`/`transferFrom` outside of `mint`/`redeem`. The provided interface (`IBounceLeveragedToken`) and documentation only describe fees on `mint`/`redeem`, not on raw transfers, so I could not confirm from this repo's context whether any real/accepted LT actually behaves this way — the vulnerability is a structural gap (missing balance reconciliation in `Pair.swap`) that would only be exploitable if such an LT exists or is later onboarded. [5](#0-4)

## HyperSwap Pre-Seed Defense (Read This Before Touching `_seedUniswapV2Direct`)

The whole sub-system inside `_seedUniswapV2Direct` exists to defuse one specific attack class. It's the most subtle code in the package. Read this before touching any of the helpers (`_seedRebalancing`, `_pairRebalance`, `_routerDepositAndDispose`, `_noFeeSwapInput`).

### The exploit

A vanilla UniswapV2 pair is deployable by anyone: `factory.createPair(token, lt)` is permissionless, and after creation anyone can call `pair.mint(to)` against pre-transferred tokens. So between phase 1 (`_enterGraduating` flips lifecycle to `Graduating` and caches `tokensForLP / ltFromPair`) and phase 2 (`finalizeGraduation` mints LP via `pair.mint(lpLock)`), an attacker can:

1. Front-run by calling `factory.createPair(token, lt)` themselves
2. `transfer(pair, smallToken)` and `transfer(pair, smallLT)` at any ratio they choose
3. Call `pair.mint(attacker)` — they now own LP at a hostile reserve ratio

When our `pair.mint(lpLock)` runs in phase 2 against this non-empty pair, V2's mint formula picks up the existing reserves:

```
liquidity = min(amount0 · totalSupply / reserve0, amount1 · totalSupply / reserve1)
```

The `min(...)` arm whose denominator is bigger relative to its numerator wins, and the OTHER arm's "excess" deposit is donated pro-rata to existing LP holders — i.e. to the attacker. Two harms:

- **Wrong opening price.** Post-mint reserves are `(R_attacker + T_a, R_attacker + T_b)`, so the LP opens at `(R_a + T_a) / (R_b + T_b)`, NOT at the curve close `T_a / T_b`. A `$15` LT pre-seed at 50% off curve close opens the pool ~454 bps off.
- **LP capture.** The wasted-side excess goes to the attacker's LP claim. A `1 wei + 1 LT` pre-seed (~`$1` attack budget) captures ~34 bps of LP.
