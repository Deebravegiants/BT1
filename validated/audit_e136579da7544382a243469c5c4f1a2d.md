### Title
Webhook shop domain is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates a webhook by validating the HMAC over the raw body only, but the `shop` field passed to the handler is read from an unauthenticated header. Because the HMAC secret (`Context.api_secret_key`) is shared across every shop that installs the app, any entity able to obtain one valid `(body, hmac)` pair (e.g. a merchant who has the app installed on their own store) can replay that pair while substituting the `x-shopify-shop-domain` header for a victim shop, and the library will process the webhook as if it belonged to the victim tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed payload: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC over that same body-only string and then forwards the unauthenticated `request.shop` value straight to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` only ever hash the `to_signable_string` value (the body) against `Context.api_secret_key`: [4](#0-3) 

Because `api_secret_key` is a single per-app secret shared by all installing shops (not a per-shop secret), the HMAC only proves "this body was produced with this app's secret" — it proves nothing about which shop the request is for. The identity binding that should hold is:

`shop asserted to the handler == shop the HMAC-authenticated payload actually originated from`

but the code only enforces:

`shop asserted to the handler == value of an arbitrary, unauthenticated header`

This is the binding failure equality broken here.

### Impact Explanation
This allows a low-privileged actor — any merchant who has installed the app on their own store, and therefore legitimately receives one authentic `(body, hmac)` webhook pair — to relay a POST to the app's webhook endpoint with the same body/HMAC but an arbitrary `x-shopify-shop-domain` header naming a different, victim shop. The host application's webhook handler (built on `WebhookMetadata#shop`) will process/act on this event as if it came from the victim shop. Depending on what the handler does (e.g. updating stored order/customer/app data keyed by shop, or triggering data mutations scoped to "the shop of the event"), this results in cross-tenant data corruption or cross-tenant action — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate to high for any app that installs on multiple merchants: obtaining one valid webhook is trivial (install the app on your own dev/test store and capture any webhook delivery), and forging the header swap requires only a normal HTTP client capable of setting the `x-shopify-shop-domain` header — no cryptographic secret is needed since that header is unauthenticated.

### Recommendation
Bind the shop identity into the authenticated material: include the shop domain (and topic/webhook id) in `to_signable_string`, or independently verify that the header-provided shop actually matches the shop the app expects for this app installation/session before invoking the handler, rather than trusting the header verbatim just because the HMAC (which only certifies the body) validates.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com`. Capture one legitimate webhook delivery: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the app's shared secret), and header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Resend an HTTP POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but with `x-shopify-shop-domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` — it succeeds (line references above).
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the app to treat the attacker-controlled payload as originating from `victim.myshopify.com`.

          received_signature = verifiable_query.hmac
