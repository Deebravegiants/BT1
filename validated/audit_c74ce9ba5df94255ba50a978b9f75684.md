### Title
Balance-based crediting of `predispatch` sweeps in `placeOrder` lets a caller claim any token balance sitting on the shared `dispatcher` as their own escrowed input - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` executes a caller-supplied `order.predispatch.call` through a single, protocol-wide `dispatcher` contract (`_params.dispatcher`), and then credits the order's escrow with whatever the **entire** `balanceOf(dispatcher)` happens to be at that moment, rather than the amount actually produced by the caller's own predispatch assets/call. This is the same root-cause class as the PLTD incident: crediting an operation from an absolute, externally-influenceable balance snapshot instead of tracking a verified delta belonging to the caller.

### Finding Description
In `placeOrder`, when `order.predispatch.call.length > 0`, the caller's declared predispatch assets are pushed to the shared `dispatcher`: [1](#0-0) 

`dispatcher` is not a fresh, per-order contract — it is a single address stored in `_params.dispatcher` and reused by every `placeOrder`/`fillOrder` call across the protocol's lifetime (confirmed by `Params.dispatcher` in `_params` and by tests such as `IntentGatewayV2Test.sol` referring to the singleton `dispatcher`/`CallDispatcher`). After the arbitrary, caller-controlled call is dispatched via `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)`, the gateway does not measure the amount that predispatch call actually produced. Instead, it reads the dispatcher's **total** current balance for each declared input token and sweeps all of it: [2](#0-1) 

The swept amount is then treated as the caller's own received input and used to set `order.inputs[i].amount`, which is exactly what is used to compute the commitment hash, escrow (`_orders[commitment][token]`), and — through the fee-reduction step — the amount a solver is later paid to redeem via `fillOrder`: [3](#0-2) [4](#0-3) 

Because `balanceOf(dispatcher)` is read as an absolute value rather than a `balanceAfter - balanceBefore` delta scoped to the caller's own deposited assets, any value that lands on the dispatcher's address for a given token — whether from residual dust of a prior, unrelated transaction, or from funds pulled in by the attacker's own arbitrary `order.predispatch.call` (which runs *as* the dispatcher and can move tokens the dispatcher is authorized to move, e.g. lingering allowances from other flows that route through the same dispatcher) — gets folded entirely into the current caller's escrow credit. This is structurally identical to the PLTD exploit pattern: the victim contract trusted a spot balance of a shared/pooled address as proof of "funds I received," and that balance can be inflated or manipulated by an unprivileged party through the very same code path that reads it.

### Impact Explanation
An attacker who can transiently inflate the dispatcher's balance for a given token (via a prior partial-sweep leftover, or via calls executed as the dispatcher itself) can have that entire balance attributed to their own order as escrowed input, then have a solver fill the order and receive matching output — i.e., value that never actually came from the attacker is paid out to them by a solver, or diverted from the intended dust-collection/treasury path. This is unbacked crediting of escrow, a form of unauthorized value creation from a message-dispatcher/token-bridge-adjacent, unprivileged, single-transaction entry point (`placeOrder`), squarely in the "concrete theft" / "unbacked mint" impact category.

### Likelihood Explanation
`placeOrder` is a fully public, unprivileged, single-transaction entry point, and the attacker fully controls `order.predispatch.call` and `order.predispatch.assets`. The only precondition is that the shared `dispatcher` contract be holding (even transiently) more of a token than what the attacker's declared predispatch assets caused it to receive — plausible via ordinary dust/slippage from other predispatch/fill flows that route through the same dispatcher, or via calls the attacker directs the dispatcher to make on its own behalf. This makes the class Medium likelihood: it does not require privileged access, but does require some non-zero balance to be present on the dispatcher at the time of exploitation.

### Recommendation
Do not credit `order.inputs[i].amount` from the dispatcher's absolute `balanceOf`. Snapshot the dispatcher's balance **before** transferring the caller's own predispatch assets to it, and credit only `balanceAfter(dispatcher) - balanceBeforeCallerDeposit(dispatcher)` scoped strictly to what the current call's `predispatch.assets` deposited, mirroring the delta-based pattern already correctly used elsewhere in the same function (e.g. lines 320-322 for the non-predispatch path). Additionally, ensure the dispatcher never retains cross-transaction residual balances (fully sweep to zero at the end of every operation, or make the dispatcher single-use/ephemeral per order) so no caller can piggyback on another party's leftover balance.

### Proof of Concept
1. Some interaction (a prior `placeOrder`/`fillOrder` predispatch, or dust from slippage) leaves `T` tokens sitting at `dispatcher`.
2. Attacker calls `placeOrder` with `predispatch.assets` containing a negligible amount of `T`-token (or another token the dispatcher already holds) and a no-op `predispatch.call`.
3. In the sweep phase, `balance = IERC20(T).balanceOf(dispatcher)` reads the full pre-existing balance (attacker's negligible deposit + residual funds), and the entire amount is transferred to the gateway and credited as `order.inputs[i].amount`. [5](#0-4) 
4. A solver, observing the (fee-reduced) commitment, fills the order and pays out the corresponding output, effectively paying the attacker for value the attacker never actually deposited.
