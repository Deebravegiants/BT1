### Title
Webhook shop-domain header is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` from independent HTTP headers, but the object's `to_signable_string` — the value actually checked against the HMAC — is only the raw request body. `Registry.process` validates the HMAC and then trusts `request.shop` to attribute the payload to a tenant, without that field ever participating in the signature.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

All the other identifying fields — `shop`, `topic`, `webhook_id`, `api_version` — come straight from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) [3](#0-2) 

`Registry.process` validates only `Utils::HmacValidator.validate(request)`, i.e., only that `hmac == HMAC(secret, raw_body)`, and then immediately hands `request.shop` (an unauthenticated header) to the handler as the tenant identity for the payload: [4](#0-3) 

`HmacValidator.validate`/`validate_signature` compute the digest solely over `verifiable_query.to_signable_string`, so for webhooks that string is the raw body — `shop` never enters the computation: [5](#0-4) 

The binding the gem implicitly relies on is:
`shop header used to attribute payload == shop that produced/signed the body`

but the actual check only proves:
`hmac == HMAC(secret, raw_body)`

with the `shop` (and `topic`/`webhook_id`) headers completely outside that equality. Anyone who can obtain one genuine `(raw_body, hmac)` pair for their own shop (trivial — any merchant installing the app receives real webhooks for their own store) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` / `x-shopify-shop-domain` header value. `HmacValidator.validate` still returns `true` (the body and HMAC are unchanged and genuinely valid), and `Registry.process` calls the handler with `WebhookMetadata.new(topic: ..., shop: <attacker-chosen shop>, body: ..., ...)`, misattributing attacker-controlled/attacker-owned webhook content to a victim tenant.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: an unprivileged actor who legitimately installed the app on their own store can forge webhook events that the host application will process as if they came from a different, victim shop. Depending on how the host app's webhook handler uses `data.shop` (e.g., to load the merchant's session/access token, to write data into that merchant's records, or to trigger tenant-scoped side effects), this enables cross-tenant data pollution / cross-tenant action execution using only a legitimately-issued signature for a different (attacker-owned) payload. This matches the "Critical — cross-tenant access" bucket, since the confused-deputy path lets one tenant's traffic be attributed to another tenant purely through unauthenticated header substitution.

### Likelihood Explanation
Likelihood is realistic for any unprivileged internet user with their own installation: obtaining a valid `(raw_body, hmac)` pair requires nothing more than installing the app on any store (a merchant can always self-install a public/dev app) and capturing one webhook delivery. Replaying it to the app's public webhook endpoint with a modified `shop` header is a standard HTTP replay, requiring no knowledge of `api_secret_key`. The only mitigating factor is that impact is bounded by what the specific host application does with `data.shop`; the gem itself provides no protection and documents/exposes `shop` as trustworthy webhook metadata once `HmacValidator.validate` passes.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signed/verified material for webhook requests, or otherwise cryptographically bind them to the payload before exposing `WebhookMetadata#shop` to handlers. At minimum, `Registry.process` should not treat `request.shop` as trusted merchant identity unless it can be verified — e.g., by cross-checking it against a shop value looked up independently (such as a previously stored session for the webhook's `webhook_id`) rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g., `orders/create`), capturing the raw request body `B` and its header `shopify-hmac-sha256: H` (valid, since `H == HMAC(secret, B)`).
2. Attacker replays the exact same request to the app's webhook endpoint, but changes only the `shopify-shop-domain` header to `victim-shop.myshopify.com`, keeping body `B` and HMAC `H` untouched.
3. `Registry.process` runs `Utils::HmacValidator.validate(request)` — this recomputes `HMAC(secret, B)` and compares to `H`; it matches, since the body is unchanged: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)`, so the host application processes attacker-controlled content under the victim shop's identity.

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
