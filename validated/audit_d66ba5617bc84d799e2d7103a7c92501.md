This confirms the vulnerability pattern. The webhook `Request#to_signable_string` (used as the HMAC input) returns only `@raw_body`, while `shop`, `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers and used by `Registry.process` to dispatch tenant-scoped data to the handler.### Title
Webhook shop/topic identity is trusted from unauthenticated headers while the HMAC only covers the request body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying `Utils::HmacValidator.validate(request)`, but that validator only signs `request.to_signable_string`, which is defined as the raw HTTP body. The `shop`, `topic`, and `webhook_id` values that determine *which tenant* and *which handler* the payload is dispatched to are read directly from unauthenticated HTTP headers and are never part of the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates the request using only `Utils::HmacValidator.validate(request)`, which internally calls `verifiable_query.to_signable_string` (i.e., the raw body) as the signed content, and once that passes it dispatches `request.topic` and `request.shop` — taken from headers — straight to the application-supplied handler as trusted tenant metadata: [3](#0-2) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [4](#0-3) 

This is the same bug class as the report's Chainlink finding: a downstream consumer trusts a value (`updateAt`/`minAnswer`/`maxAnswer` there; `shop`/`topic` header here) that was never actually validated by the check that is supposed to guarantee authenticity (the price-staleness bound there; the HMAC there here). The identity binding that should hold is:

`hmac_verified_bytes == bytes_that_determine_tenant_and_handler`

but in this gem: `hmac_verified_bytes = raw_body`, while `bytes_that_determine_tenant_and_handler = headers(shop, topic, webhook_id)`. These are disjoint, so the binding is broken.

### Impact Explanation
Because the shop identity and topic are not covered by the HMAC, any request whose raw body happens to produce a valid signature for the app's secret (i.e., any body Shopify has legitimately signed and sent to this endpoint, for any topic/shop, since Shopify uses the same `api_secret_key` for all webhook deliveries to a given app across all its installed shops) can be replayed with the `shop-domain` header swapped to a different shop, or the `topic` header swapped to a different topic, without invalidating the HMAC. If a merchant application relies on `WebhookMetadata#shop` to select the tenant's data store/session or relies on `topic` to decide how to interpret `body`, an attacker who can capture or resend one legitimately-signed webhook (e.g., via replay through any network path that reaches the endpoint, or a malicious middle party who has visibility into one shop's webhook deliveries) can cause cross-tenant data to be written or read under a different shop's identity, or cause a handler to misinterpret a payload for an unintended topic. This crosses a tenant boundary using only the gem's own webhook validation logic, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Webhook endpoints are internet-reachable by design (Shopify posts to them over the public internet), so an unprivileged actor who can observe or replay any single valid webhook delivery for the app (from any shop) has everything needed: a body + hmac pair that remains valid regardless of the `shop-domain`/`topic` headers sent alongside it. No access token, `client_secret`, or privileged account is required — only capturing or reusing a previously delivered, validly-signed webhook body, which is a realistic condition for apps that also log raw request bodies, proxy webhooks through shared infrastructure, or where the same generic body could plausibly apply to multiple shops/topics.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, and ideally `webhook_id`) in the signed content used for HMAC verification, or otherwise cryptographically bind them (e.g., derive/validate `shop` and `topic` from a signed envelope rather than trusting raw headers independently of the HMAC). At minimum, document and enforce that `WebhookMetadata#shop`/`#topic` must not be treated as authenticated unless the consuming application independently re-validates that the webhook was registered for that specific shop/topic combination (e.g., cross-check against the registrations database) before acting on it.

### Proof of Concept
1. Attacker captures a legitimately Shopify-signed webhook POST to the app's endpoint (e.g., from Shop A, topic `carts/update`, body `{}`), including its valid `x-shopify-hmac-sha256` header computed by Shopify over the raw body.
2. Attacker resends the identical raw body and `hmac` header to the same endpoint, but with `x-shopify-shop-domain` changed to Shop B and/or `x-shopify-topic` changed to a different mandatory/registered topic.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers successfully (only presence of headers is checked, not their correctness) — see `lib/shopify_api/webhooks/request.rb` lines 45-63.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) and finds it matches, since the body and hmac are unchanged — see `lib/shopify_api/webhooks/registry.rb` line 190 and `lib/shopify_api/utils/hmac_validator.rb` lines 26-31.
5. The handler registered for the forged topic is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` carrying the attacker-chosen `shop`/`topic`, even though neither was verified — see `lib/shopify_api/webhooks/registry.rb` lines 198-199.
