### Title
Unbounded per-order bid entries in `pallet-intents-coprocessor` allow storage/iteration spam analogous to Factory.sol's unbounded pair arrays - ([File: modules/pallets/intents-coprocessor/src/lib.rs])

### Summary
The Sherlock finding describes `Factory.sol`'s Collateral-Debt pair arrays that anyone can append to (by creating coolers with any msg.sender), causing unbounded growth that DOSes any on-chain contract iterating over them. The closest analog in Hyperbridge is `pallet-intents-coprocessor`'s `Bids` storage, a `StorageDoubleMap<commitment, filler_account, deposit>` that any signed account can insert into via the permissionless `place_bid` extrinsic [1](#0-0) , with no cap on the number of distinct fillers per commitment.

### Finding Description
`place_bid` lets any `ensure_signed` origin insert a new `(commitment, filler)` entry into `Bids` for an arbitrary order commitment, paying only a configurable `StorageDepositFee` [2](#0-1) . Unlike the `phantom` order path — which enforces "one bid per filler" and a bid window — regular (non-phantom) orders have no such restriction visible in this code path, so an attacker can generate many distinct accounts and place many bids against the same commitment for the cost of the deposit (which is reserved, not burned, and can be reclaimed via `retract_bid`).

The one place that reads back the full bid set is `intents_getBidsForOrder`, but that RPC caps the on-chain scan at `MAX_ON_CHAIN_BIDS = 30` [3](#0-2) , which limits (but does not eliminate) the read-side blast radius — an attacker filling the first 30 keys under a commitment with junk bids can crowd out legitimate solver bids from ever being surfaced by the RPC (since `storage_keys` iteration order is not amount- or time-ranked, it is lexicographic on `blake2_128(filler) ++ filler`). Off-chain, the solver-side SDK (`BidManager.sortBids`/`selectAndExecuteBest`) iterates over whatever the RPC/indexer returns without an independent bound [4](#0-3) , so a flood of bids can also degrade solver-side selection latency.

I was not able to fully verify within the available tool budget whether there is any additional on-chain (pallet or EVM) code path that iterates the full, unbounded `Bids` map for a commitment (e.g., for governance cleanup, weight-critical logic, or on-chain winner selection) — the pallet's `#[pallet::call]` block was only partially inspected. If such a path exists, this would directly meet the "unbounded array iterated on-chain" bug class from the report; if no such path exists, the confirmed impact is limited to the bounded RPC read (already mitigated to 30 entries) and off-chain solver tooling, not an on-chain iteration DOS.

### Impact Explanation
Confirmed impact: spam bids on a commitment can occupy the fixed 30-slot window that `intents_getBidsForOrder` scans, hiding legitimate solver bids from being fetched (griefing order fulfillment / degrading price discovery for that order), and can burden off-chain solver bid-selection loops. This is a griefing/DOS on the intents bid-discovery path, not a direct fund-theft vector, and the storage-deposit cost imposes some economic friction (though it is refundable via `retract_bid`, making repeat spam cheap in aggregate gas cost only).

Unconfirmed/potential impact: if any additional on-chain logic (not located in this pass) iterates the full unbounded bid set per commitment, that would elevate this to a genuine on-chain gas-DOS matching the reported bug class more precisely.

### Likelihood Explanation
Any signed account can call `place_bid` for any commitment at any time; the only cost is the reservable `StorageDepositFee`, which is refunded on `retract_bid`. Multiple fillers bidding on the same order is explicitly a supported and tested scenario [5](#0-4) , meaning the write path imposes no per-order cap and is trivially reachable by an unprivileged relayer/solver-imitating attacker generating many accounts.

### Recommendation
- Bound the number of bids storable per commitment (e.g., a `BoundedVec`/counter enforcing `MAX_BIDS_PER_ORDER`), rejecting or evicting the lowest-value bid once the cap is reached, mirroring the eviction pattern already used in `pallet-bandwidth`'s `SubscriptionList` [6](#0-5) .
- Alternatively/additionally, raise `StorageDepositFee` enough to make wide-account spam economically unattractive, and/or apply the phantom-order-style "one bid per filler, bounded window" restriction to all orders, not just phantom ones.
- If any on-chain (non-RPC) code path iterates `Bids` per commitment unbounded, that path must be identified and bounded before this can be ruled out as a genuine on-chain DOS vector — this needs further investigation beyond what was verified here.

### Proof of Concept
1. Attacker generates N distinct `AccountId`s, each funded with enough balance to cover `StorageDepositFee` (reservable, refundable).
2. For a target order `commitment`, submit `place_bid(commitment, junk_user_op)` from each of the N accounts — none of the phantom-order restrictions (`PhantomOrderBidWindowClosed`, `DuplicatePhantomBid`) apply to a regular order, so this succeeds N times [7](#0-6) .
3. `intents_getBidsForOrder` scans on-chain storage keys under the commitment prefix and takes the first 30 in key order [8](#0-7) ; if the attacker's N ≥ 30 junk entries sort ahead of the genuine solver's bid (by `blake2_128(filler)` ordering), the genuine bid is never returned to fillers/solvers querying the order, stalling fulfillment.
4. Attacker calls `retract_bid` on each junk entry afterward to reclaim the deposit, making the griefing essentially free apart from transaction fees.

		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::place_bid())]
		pub fn place_bid(
			origin: OriginFor<T>,
			commitment: H256,
			user_op: BoundedVec<u8, ConstU32<1_048_576>>,
		) -> DispatchResult {
			let filler = ensure_signed(origin)?;

			// Validate user_op is not empty
			ensure!(!user_op.is_empty(), Error::<T>::InvalidUserOp);

			// Phantom orders have stricter rules: one bid per filler, no updates, and only
			// within the configured acceptance window after the order was registered. Every
			// chain's active order is checked, not just the most recently generated one.
			if let Some(active) = CurrentPhantomOrder::<T>::get() {
				if let Some((_, info)) = active.iter().find(|(c, _)| *c == commitment) {
					let window: BlockNumberFor<T> = Self::phantom_bid_window().into();
					ensure!(
						frame_system::Pallet::<T>::block_number() <= info.created_at_block + window,
						Error::<T>::PhantomOrderBidWindowClosed
					);
					ensure!(
						!Bids::<T>::contains_key(&commitment, &filler),
						Error::<T>::DuplicatePhantomBid
					);
				}
			}

			// If a bid already exists, unreserve the old deposit first
			if let Some(old_deposit) = Bids::<T>::get(&commitment, &filler) {
				<T as Config>::Currency::unreserve(&filler, old_deposit);
			}

			let deposit = Self::storage_deposit_fee();

			// Reserve the new deposit
			<T as Config>::Currency::reserve(&filler, deposit)
				.map_err(|_| Error::<T>::InsufficientBalance)?;

			// Store the bid in offchain storage
			let bid = Bid { filler: filler.clone(), user_op: user_op.to_vec() };
			let offchain_key = Self::offchain_bid_key(&commitment, &filler);
			offchain_index::set(&offchain_key, &bid.encode());

			// Store deposit amount in onchain storage for discoverability and accurate refunds
			Bids::<T>::insert(&commitment, &filler, deposit);

			Self::deposit_event(Event::BidPlaced { filler, commitment, deposit });

			Ok(())
		}

#[test]
fn multiple_fillers_can_bid_on_same_order() {
	new_test_ext().execute_with(|| {
		let filler1 = AccountId32::new([1; 32]);
		let filler2 = AccountId32::new([2; 32]);
		let commitment = H256::random();
		let user_op = BoundedVec::try_from(vec![1u8, 2u8, 3u8]).unwrap();

		// Both fillers place bids
		assert_ok!(Intents::place_bid(
			RuntimeOrigin::signed(filler1.clone()),
			commitment,
			user_op.clone()
		));

		assert_ok!(Intents::place_bid(RuntimeOrigin::signed(filler2.clone()), commitment, user_op));

		// Verify both bids exist
		assert!(Bids::<Test>::contains_key(&commitment, &filler1));
		assert!(Bids::<Test>::contains_key(&commitment, &filler2));
	});
}
