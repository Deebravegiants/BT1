### Title
Webhook HMAC only signs the raw body, not the `shop`/`topic` headers, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
Analogous to the `safeApprove()` bug class (a value is trusted for an action while the field that actually identifies *who* the action applies to is left outside the verified/covered data), Shopify's webhook verification in this gem authenticates only the JSON body bytes, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to dispatch and attribute the webhook are taken from unauthenticated HTTP headers that are never included in the HMAC computation.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`, and the `hmac` accessor is read from the `hmac-sha256` header. Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e. the body) and compares it to the received `hmac`: [3](#0-2) 

`Webhooks::Registry.process` only calls this HMAC check, then immediately trusts the unauthenticated `request.topic` and `request.shop` to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity-binding equality that should hold is:
`hmac(secret, signable_string)` should authenticate `(shop, topic, webhook_id, body)` as a unit → but in fact it only authenticates `body`. `shop` and `topic` are accepted as-is from headers with no cryptographic binding to the signature that was verified.

### Impact Explanation
`Context.api_secret_key` is shared by **all** shops that install a given app (it's the app's client secret, not per-shop). Any merchant who installs the app (an "unprivileged" actor with respect to other tenants of the same app) legitimately receives real Shopify webhooks for their own shop, each with a valid `X-Shopify-Hmac-Sha256` for the exact body bytes. Because the header fields are outside the signed content, that merchant can replay the same (body, hmac) pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) to name a different, victim shop. `HmacValidator.validate` still succeeds (it only checks the body against the shared secret), and `Registry.process` dispatches the handler with `WebhookMetadata.shop` set to the attacker-chosen victim domain. Any app that follows the documented usage of keying per-tenant state off `WebhookMetadata#shop` (the intended, documented use of this API) will process/store attacker-controlled body content under another tenant's identity — a cross-tenant integrity/confusion issue, which meets the "cross-tenant access" Critical bar in the rubric.

### Likelihood Explanation
Exploitation only requires the attacker to be able to install the target app on their own shop (a normal, low-privilege action for any Shopify merchant/developer for public apps), capture one legitimate webhook delivery, and replay it with a modified `shop`/`topic` header value — no access to `api_secret_key`, tokens, or the app's infrastructure is needed. This is a realistic and repeatable attack path.

### Recommendation
Include the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable content used for HMAC verification (or otherwise cryptographically bind them, e.g. by having the HMAC cover a canonicalized string of `shop|topic|webhook_id|body`), so that the verified signature actually authenticates the full tuple that `Registry.process` and the handler act upon, not just the JSON body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` (normal app install, no elevated privilege required).
2. Attacker triggers a webhook (e.g. `orders/create`) and captures the raw POST: headers including `X-Shopify-Hmac-Sha256: <H>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: orders/create`, and body `B`.
3. Attacker resends the exact same body `B` and `X-Shopify-Hmac-Sha256: <H>` to the app's webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Utils::HmacValidator.validate` recomputes the HMAC over `@raw_body` only (`to_signable_string`), which still matches `<H>` because the body was not altered.
5. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: JSON.parse(B), ...))`, causing the app to process attacker-supplied order data as belonging to `victim.myshopify.com`.
