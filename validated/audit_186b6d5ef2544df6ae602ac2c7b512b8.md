### Title
Webhook Cross-Tenant Impersonation via Unsigned `shop-domain` Header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` extracts the tenant-identifying `shop`, `topic`, `webhook_id`, and `api_version` fields from raw HTTP headers, but `Utils::HmacValidator` only verifies the HMAC-SHA256 signature over the raw request body — never over these header values. This breaks the identity binding: `signed_bytes == asserted_shop` does not hold.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from unauthenticated headers with no cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` computes and compares the signature only against `verifiable_query.to_signable_string` (the body): [3](#0-2) 

`Registry.process` gates handling solely on this body-only HMAC check, then trusts `request.shop`/`request.topic`/`request.webhook_id` verbatim when building the data passed to the app's handler: [4](#0-3) 

Because `Context.api_secret_key` is a single secret shared by the app across **all** of its installed shops (it is the app's client secret, not a per-shop secret), any merchant who has legitimately installed the app can capture one authentic `(raw_body, hmac)` pair from their own real webhook deliveries. That HMAC will validate successfully for that body regardless of which shop's header values accompany it, since the headers are never part of the signed content. The attacker can then replay that exact body/HMAC pair to the app's public webhook endpoint while forging the `shop-domain` (and `topic`/`webhook-id`) headers to claim the payload belongs to a different, victim shop.

### Impact Explanation
This is a cross-tenant identity spoofing primitive: the library asserts a validated webhook came from `request.shop`, but that value is never covered by the signature that was actually checked. A downstream app that uses `request.shop` (as surfaced via `WebhookMetadata`) to route, authorize, or persist data per-tenant can be made to attribute attacker-controlled payload/topic combinations to an arbitrary victim shop, since the only thing cryptographically guaranteed is "this body came from *some* installation of this app," not "this body came from *this* shop." This matches the Critical/High criteria for cross-tenant access carried through the gem's own trusted verification path.

### Likelihood Explanation
Exploitability requires only an ordinary, unprivileged installation of the target app (any merchant can install most public/embedded apps) plus the ability to capture one's own legitimate webhook HTTP traffic and replay an HTTP request to the app's public webhook endpoint with modified headers — no access to `api_secret_key`, no TLS interception, and no privileged account is required.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signable content used for HMAC verification, or otherwise cryptographically bind `request.shop` to the verified body (e.g., verify the resolved session/shop separately via a trusted store lookup rather than trusting the header). At minimum, document that `request.shop` is unauthenticated and must not be used for tenant-scoping decisions without independent verification against a known/registered shop.

### Proof of Concept
1. Attacker installs the target Shopify app as "attacker-shop.myshopify.com" (legitimate, unprivileged installation).
2. Attacker registers a webhook and captures a real delivery: raw body `B` and header `x-shopify-hmac-sha256: H`, where `H` is valid HMAC over `B` using the app's shared `api_secret_key`.
3. Attacker sends a forged POST to the app's webhook endpoint with the same body `B` and hmac header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` — this passes. [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-chosen body/topic, despite the payload never having been signed for that shop. [6](#0-5)
