### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header not covered by HMAC — (`File: lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by verifying the HMAC over the raw request body. The `shop` identity that is handed to the app's webhook handler, however, is read from the `x-shopify-shop-domain` HTTP header, which is never included in the HMAC-signed material. An attacker can therefore take any legitimately-signed webhook payload (e.g., one delivered to their own shop) and re-submit it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop, and the gem will report it as valid and attribute it to the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`. Its `to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `shop` (along with `topic`, `api_version`, `webhook_id`) is pulled straight from HTTP headers, which are not part of the signed string at all: [2](#0-1) 

`Registry.process` verifies the HMAC (over the body only) and then unconditionally trusts `request.shop` when building the object handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes/compares the signature only against `verifiable_query.to_signable_string` (the body), never the headers: [4](#0-3) 

The gem's own documented usage pattern reinforces trusting this unauthenticated field as the shop identity for downstream business logic (e.g. enqueuing per-shop jobs): [5](#0-4) 

**Broken identity binding (as an equality):**
`shop` used by the handler == bytes covered by the HMAC should hold, but in reality:
`request.shop` (from unauthenticated header) ≠ any value verified by `HmacValidator.validate(request)` (which only covers `raw_body`).

Because `client_secret` (used to compute the HMAC) is shared across every shop that has installed the app, any shop owner running the app can legitimately receive a validly-HMAC'd webhook body for their own shop, then replay that exact body to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header (or `shopify-shop-domain`) for a different (victim) shop's domain. The HMAC still validates (it never covered the header), and `Registry.process` calls the handler with `data.shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant/shop identity boundary the gem is supposed to enforce for webhook authenticity: an unprivileged attacker who has installed the app on their own shop can forge webhook deliveries that the app will process as if they came from an arbitrary victim shop. Any host application that follows the gem's documented pattern of trusting `data.shop` to route data, invalidate caches, apply mandatory-compliance actions (e.g. `shop/redact`, `customers/redact`, `customers/data_request`), or otherwise key work per-tenant is exposed to cross-tenant data confusion/manipulation using only a shop the attacker legitimately owns — no access token or secret leakage required.

### Likelihood Explanation
High. Only requires installing the app on an attacker-controlled shop (something available to any unprivileged internet user through Shopify's normal app installation flow) to obtain one validly-signed webhook body/HMAC pair, then a single crafted HTTP POST to the app's own public webhook endpoint with a forged `shop-domain` header. No secrets, tokens, or elevated privileges are needed, and it works in one request.

### Recommendation
Bind the shop identity to the signed material. At minimum, `Webhooks::Request#to_signable_string` (or a new signed field set) should incorporate `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) so that `HmacValidator.validate` fails if any of these headers are altered, or the gem should require/verify shop domain against an expected value passed in by the caller (e.g., session lookup) rather than trusting the header blindly.

### Proof of Concept
```ruby
require "shopify_api"

ShopifyAPI::Context.setup(
  api_key: "key",
  api_secret_key: "shared_client_secret",
  host: "https://example-app.com",
  scope: "read_orders",
  is_embedded: true,
  api_version: "2025-07",
)

raw_body = '{"id":123,"note":"hi"}'

# Attacker legitimately owns "attacker-shop.myshopify.com" and receives a real webhook
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the same body+hmac but forges the shop-domain header to a victim shop
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker does NOT own this shop
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2025-07",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HMAC validation succeeds because it never covered shop-domain
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...))
# The app now believes this webhook, and the order data in it, belongs to "victim-shop.myshopify.com".
```
