### Title
Cross-chain token amounts smaller than `10^(erc_decimals - local_decimals)` are silently rounded to zero on delivery, permanently freezing the escrowed/burned funds - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
The `hyper-fungible-token` pallet's `convert_to_balance` helper truncates (via integer division) an incoming ERC-20 `U256` amount down to the pallet's local balance precision. When the EVM-side token has more decimals than the local asset (a very common configuration, e.g. an 18-decimal ERC-20 token paired with a 6-decimal Substrate asset), any transferred amount below one local unit is converted to `0` and silently accepted — while the corresponding value was already burned or escrowed on the source chain. This is the same "divide before checking scale" rounding-to-zero pattern flagged in the referenced Ajna report, but here it results in real loss of bridged funds rather than a revert.

### Finding Description
`convert_to_balance` performs pure integer division with no minimum-amount check and no rejection path for a zero result: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
```

Per the pallet README, this is exactly the function used on the receiving side of a cross-chain transfer: `on_accept` maps the source EVM contract to the local asset, "scales the amount using `Precisions`, then mints (non-native) or releases from escrow (native) to the beneficiary." [2](#0-1) 

If `erc_decimals - local_decimals = d > 0` (e.g. 18 vs 6, `d = 12`), any transferred ERC-20 `value < 10^d` divides to `0`. The pallet then proceeds to mint/release `0` to the beneficiary — a valid, non-erroring outcome — even though on the EVM side the equivalent value was already burned or moved into escrow via the symmetric `send()` path, which uses the inverse scaling function `convert_to_erc20` with no floor/minimum check either: [3](#0-2) 

This is reachable by any unprivileged user: anyone can call the paired EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract to send an arbitrarily small amount, which is escrowed/burned on that side and dispatched as an ISMP `Send` message; once relayed, `on_accept` on the pallet side scales it down to `0` and finalizes the message with no error, no revert, and no event indicating a lossy delivery.

### Impact Explanation
Funds transferred cross-chain in amounts below the decimal-scaling threshold are permanently lost: the source-side value is burned/escrowed with no way to reclaim it (the message is delivered successfully, so no timeout/refund path fires), and the destination side credits the beneficiary nothing. This is a permanent freezing/loss-of-funds bug in the token bridge's mint/burn accounting, matching the "Medium" severity class of the referenced report — small-value transfers of any token pair with a decimals mismatch (which is the norm, not the exception, across EVM chains) are silently destroyed rather than reverted or refunded.

### Likelihood Explanation
High for any token pair where the EVM-side asset has more decimals than the paired Substrate asset — a routine configuration (e.g., 18-decimal wrapped assets paired against 6- or 8-decimal parachain assets). Any user (or an automated relayer forwarding a legitimate low-value message) can trigger this with a single `send()`/transfer call; no privileged role or special conditions are required.

### Recommendation
Reject (rather than silently truncate) amounts that scale to zero: `convert_to_balance` should return an error (and the corresponding `send()`/`on_accept` flow should revert/refuse) whenever the computed local balance is `0` for a non-zero input `value`. Alternatively, enforce a minimum transferable amount of `10^(erc_decimals - local_decimals)` at the point of dispatch (`send()`), symmetric to the check already needed on delivery, so that funds are never burned/escrowed on one side without a matching non-zero credit on the other.

### Proof of Concept
1. Register a token pair where the EVM-side contract declares `erc_decimals = 18` and the local pallet asset has `local_decimals = 6` (a difference `d = 12`), as configured via `Precisions`.
2. A user calls `send()` (or the EVM `HyperFungibleToken` equivalent) with an amount `value = 10^11` (i.e., 0.1 of the smallest scaling unit, less than `10^12`). The source side burns/escrows this amount.
3. The ISMP message carrying `value = 10^11` is relayed and delivered; `on_accept` calls `convert_to_balance(value, 18, 6)`, computing `10^11 / 10^12 = 0` (integer division truncates to zero).
4. The pallet mints/releases `0` to the beneficiary and the message is marked delivered successfully — no revert, no timeout, no refund.
5. Net result: the user's `10^11`-unit worth of value is permanently destroyed with nothing credited on the destination chain.

## ISMP module behaviour

- `on_accept` — receives `Send` messages from the paired EVM contract. Maps

- `on_timeout` — refunds the original sender's balance from escrow or by
  re-minting. Emits `TokenRefunded`.
- `on_response` — unused; this pallet uses post-only messaging.
