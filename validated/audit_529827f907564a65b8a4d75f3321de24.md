### Title
`deleteStateMachineCommitmentInternal` resets `latestStateMachineHeight` to a hardcoded `1` instead of the true previous height, unlike the equivalent Substrate logic - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.deleteStateMachineCommitmentInternal` clears a vetoed state machine commitment and, when the vetoed height happens to be the current "latest" height, resets `_latestStateMachineHeight[id]` to the hardcoded constant `1` rather than restoring the actual previously-accepted height [1](#0-0) . This is the same bug class as the reported issue: a piece of "clear/reset" logic that assumes a fixed baseline (index `0`/height `1`) is always the correct rollback point instead of tracking/reverse-engineering the actual prior valid state.

### Finding Description
In `EvmHost.sol`, `deleteStateMachineCommitmentInternal` is the fisherman-veto path that removes a state commitment and its update timestamp:

```solidity
function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
    StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
    // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
    if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
        _latestStateMachineHeight[height.stateMachineId] = 1;
    }
    ...
}
``` [1](#0-0) 

Compare this to the Substrate `pallet-ismp` implementation of the identical operation, which explicitly tracks the real prior height via a dedicated `PreviousStateMachineHeight` storage item and restores that value rather than an arbitrary constant:

```rust
if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
    if latest == height.height {
        // Reset back to the initial height to allow for honest updates
        let prev_height =
            PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
                Error::Custom("Previous state machine height should exist".to_string())
            })?;
        LatestStateMachineHeight::<T>::insert(height.id, prev_height);
    }
}
``` [2](#0-1) 

The EVM implementation of `EvmHost` has no equivalent `_previousStateMachineHeight` tracking at all — it simply hardcodes `1` as the "safe" rollback point, exactly mirroring the `updateFounders()` flaw of assuming index `0`/the first slot is always the correct baseline for a reverse/reset operation instead of computing or storing the real prior value.

### Impact Explanation
After any height is vetoed via `deleteStateMachineCommitment` (fisherman path, callable through the handler) while it is the current latest height, `_latestStateMachineHeight[id]` collapses to `1` regardless of how far the state machine has actually progressed (which in production will be far beyond height `1`). Any code path in `EvmHost`/`HandlerV2` that gates acceptance of new state-machine updates on comparison against `_latestStateMachineHeight` (e.g. requiring a new height to exceed the tracked latest height) is thereby put into an incorrect state: it will treat height `1` as the trusted baseline instead of the real last good height, potentially re-opening a wide range of already-superseded heights for submission and breaking the intended monotonic-height invariant used to accept/prove state commitments. This directly undermines the state proof/consensus verification path that unauthorized apps, token bridge mints, and message delivery all rely on for correctness.

### Likelihood Explanation
The veto path is a normal, expected part of the fisherman/dispute-resolution mechanism (`deleteStateMachineCommitment` is restricted to the handler, i.e., it's part of the intended operational flow, not an attacker-only exploit), so this incorrect reset triggers under a legitimate, foreseeable condition: vetoing the current latest height. Because the constant `1` is used unconditionally with no fallback to real prior state, this will misbehave every single time the vetoed height is the latest, not just in edge cases — this closely parallels how the original Nounsbuilder bug always misbehaved after the *first* founders update.

### Recommendation
Track the actual previous state machine height (analogous to Substrate's `PreviousStateMachineHeight`) whenever `storeStateMachineCommitment` is called, and use that tracked value to restore `_latestStateMachineHeight` in `deleteStateMachineCommitmentInternal`, instead of hardcoding `1`.

### Proof of Concept
