## Missing Arbitrum Sequencer-Uptime Check in `SimplexPaymaster` Oracle Pricing - (`evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-4337 gas payments using Chainlink `AggregatorV3Interface.latestRoundData()` for both the native asset and the paid token, checking only for a non-positive answer and staleness against `maxOracleAge`. It never consults an L2 Sequencer Uptime Feed, so on Arbitrum (or any Chainlink-supported L2 whose sequencer can go offline) a sequencer outage lets stale, frozen prices continue to be accepted as valid until `maxOracleAge` (configurable up to 7 days) elapses.

### Finding Description
`_getOraclePrice` is the sole gate on oracle freshness/validity: [1](#0-0) 

It is called from `_tokenPrice` (used to price every gas-paying `UserOperation`) and from `swapAndDeposit` (used to bound the minimum swap output during fee recycling): [2](#0-1) [3](#0-2) 

Unlike Chainlink's own recommendation for L2 deployments (consulting a Sequencer Uptime Feed and enforcing a grace period after it recovers), this contract has no such check anywhere — a repo-wide search for sequencer-uptime patterns (`isSequencerActive`, `SequencerUptimeFeed`, `GracePeriod`) returns nothing. The contract's doc comments and deployment tooling show it is intended to be deployed across multiple chains including those with a centralized sequencer, with `maxOracleAge` set per-chain (e.g., a long window for infrequent-heartbeat feeds): [4](#0-3) [5](#0-4) 

Because `updatedAt` only reflects the last time the feed was pushed on-chain, a sequencer outage freezes both `nativeOracle` and each token's oracle at their last reported prices. As long as the outage (plus any subsequent catch-up) stays within `maxOracleAge`, `_getOraclePrice` returns the stale answer as if it were current, with no revert and no grace-period delay after the sequencer resumes.

### Impact Explanation
An unprivileged `UserOperation` sender interacts with this paymaster permissionlessly (mode 0x00/0x02 paymasterData, no allowlist on `fetchDetails`/pricing). During a sequencer outage where the true native/token exchange rate has moved (e.g., a market crash or spike), the sender can submit gas-payment operations priced off the stale, frozen Chainlink answer instead of the real rate. Because `_tokenPrice` directly determines how many ERC-20 tokens are pulled from the sender to cover the paymaster's real (native) gas outlay, a sender can systematically underpay tokens relative to the native gas actually spent by the paymaster, draining the paymaster's EntryPoint deposit over repeated operations — a direct theft-of-funds vector against the paymaster's treasury. The same stale price also feeds `swapAndDeposit`'s `amountOutMin` computation, letting `swapExactTokensForETH` be forced through at an unfavorable, stale-derived floor during the same outage window, extractable via sandwiching by the treasury-adjacent caller path once the DEX price reflects reality.

### Likelihood Explanation
Sequencer outages on Arbitrum (and other centralized-sequencer L2s this paymaster targets) have occurred historically and are a known, recurring operational risk explicitly called out by Chainlink's own oracle integration guidance. The `maxOracleAge` bound is deliberately generous (up to 7 days, and set to ~24h+ buffers for some stablecoin feeds per the deployment script comments), meaning realistic outage durations fall well inside the window where stale prices are silently accepted. No privileged action or malicious insider is required — any UserOp sender can exploit the mispricing window as soon as it opens.

### Recommendation
Integrate the Chainlink L2 Sequencer Uptime Feed for every chain where one exists: before accepting an oracle answer in `_getOraclePrice` (and thus in `_tokenPrice`/`swapAndDeposit`), check `sequencerUptimeFeed.latestRoundData()`, revert if the sequencer is reported down, and enforce a grace period (e.g., Chainlink's recommended pattern) after it comes back up before trusting price data again.

### Proof of Concept
1. Deploy `SimplexPaymaster` on Arbitrum with `nativeOracle`/token oracles pointed at real Chainlink ETH/USD and TOKEN/USD feeds, `maxOracleAge` set to a multi-hour/day window as in the deployment script defaults.
2. Arbitrum sequencer goes offline; Chainlink feeds stop updating but remain within `maxOracleAge`.
3. While the sequencer is down (or during the following grace period once it resumes, per Chainlink's guidance), the true native/token exchange rate diverges materially from the last on-chain answer (e.g., ETH price drops sharply off-chain/on other venues).
4. An attacker submits `UserOperations` through the paymaster (mode 0x00/0x02) that get priced via `_tokenPrice`, paying tokens computed from the stale, favorable exchange rate while the paymaster's actual native gas outlay reflects the real, now-higher relative cost of ETH.
5. Repeating this drains the paymaster's EntryPoint-deposited native balance faster than the token markup can replenish it, since `_getOraclePrice` never rejects the stale answer — there is no sequencer-uptime or grace-period check anywhere in `SimplexPaymaster.sol`.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
