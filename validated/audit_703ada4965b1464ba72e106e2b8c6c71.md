### Title
Missing shop-domain validation in `TokenExchange.exchange_token` allows `client_secret` exfiltration via crafted `dest` claim - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds an `Auth::Session` and an HTTP client directly from the JWT `dest` claim (`jwt_payload.shop`), and never validates that the resulting host is a trusted Shopify domain, unlike the sibling method `migrate_to_expiring_token`, which explicitly calls `Utils::ShopValidator.sanitize!` for this exact purpose.

### Finding Description
In `exchange_token`, the shop used for the outbound request is derived purely from the token's `dest` claim: `dest_shop = jwt_payload.shop` [1](#0-0) . `JwtPayload#shop` simply strips `"https://"` from the raw `dest` string with no domain-format check: `@dest.gsub("https://", "")` [2](#0-1) . This `dest_shop` is used to build a `Session` and then an `HttpClient`, whose `base_uri` is `"https://#{api_host || session.shop}"` — i.e., the value from the token directly becomes the request host that receives the app's `client_id`/`client_secret` in the POST body [3](#0-2) [4](#0-3) .

Compare this to `migrate_to_expiring_token`, in the same module, which sanitizes the shop before use: `validated_shop = Utils::ShopValidator.sanitize!(shop)` [5](#0-4) . `ShopValidator.sanitize!` enforces that the host belongs to one of a fixed set of trusted Shopify domains (`myshopify.com`, `myshopify.io`, `shopify.com`, `spin.dev`, `shop.dev`) [6](#0-5) . `exchange_token` has no equivalent check.

The binding that should hold is: `shop used to route the client_secret == a Shopify-trusted admin domain`. In `exchange_token` this becomes: `shop used to route the client_secret == whatever string appears in the JWT dest claim`, which is a weaker binding since the `dest` claim's format is not independently verified as a legitimate Shopify domain.

Because JWT decoding restricts the algorithm to `HS256` and requires `aud == Context.api_key` [7](#0-6) , a fully-valid signature still requires knowledge of `Context.api_secret_key`. Given the rules of this analysis exclude analogs that require possession of the `api_secret_key`, an external, credential-less attacker cannot forge a token with a malicious `dest` to exploit this path directly through JWT forgery. The unverified issue is a genuine authenticity/binding gap (mirroring the reported oracle-authenticity bug class: a value is trusted for routing security-sensitive material without independent verification of its legitimacy), but I could not establish, purely from `lib/shopify_api/**`, a way for an unprivileged attacker to supply a malicious `dest`/`session_token` without already controlling a signed token or the app secret.

### Impact Explanation
If reachable, an attacker-controlled `dest` claim would let this method exfiltrate the app's `client_secret` to an attacker-controlled host — matching the "SSRF with the app's credentials" / credential-leak impact bucket. However, the realistic exploit path depends on the host application accepting a `session_token` from an untrusted source without itself validating the `dest`/issuer host — which falls under "host application ignoring documented API" and is explicitly out of scope, or on possession of the api_secret_key (also out of scope).

### Likelihood Explanation
Low-to-unproven for an unprivileged internet user, given the JWT signature requirement. This is best characterized as a **defense-in-depth gap** relative to `migrate_to_expiring_token`'s stricter handling of the same class of input, rather than a demonstrated remote exploit reachable without secret material.

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` in `exchange_token` before constructing the `Session`/`HttpClient`, consistent with `migrate_to_expiring_token`, so that even a technically-signed but malformed/unexpected `dest` value cannot route the client secret to a non-Shopify host.

### Proof of Concept
Not constructible within scope: exploitation requires either the app's `api_secret_key` (to sign a JWT with a malicious `dest`) or a host application that forwards an externally-supplied, unsigned/unverified `session_token` into `exchange_token` — both are excluded by the stated rules. No standalone PoC exists purely within `lib/shopify_api/**`.
