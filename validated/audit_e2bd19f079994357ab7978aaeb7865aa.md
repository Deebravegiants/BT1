### Title
Tron `IntentGatewayV2.onAccept` is missing the relayer-authentication gate present in the EVM `ExtrinsicIntents` implementation, reopening the forged-handler delivery route - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The mainline EVM intents contract, `ExtrinsicIntents.sol`, gates every delivery through `_checkRelayer(incoming.relayer)` before it reads the request body, closing a route where a forged/compromised host handler can report an arbitrary relayer address and get accepted by the app. `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `onAccept` does not perform this check at all, leaving the Tron deployment in the pre-fix state that the EVM codebase's own changelog explicitly identifies as exploitable.

### Finding Description
In `evm/src/apps/intentsv2/ExtrinsicIntents.sol`, `onAccept`/`onGetResponse` call `_checkRelayer(incoming.relayer)` immediately, before the first body byte is even read as a `RequestKind`: [1](#0-0) [2](#0-1) 

This gate exists specifically to defend against a scenario documented in the repo's own decision log: a forged consensus proof can deliver a `SetHostParam` governance message that swaps the host's trusted `handler` for a malicious one which reports whatever relayer address it likes on every `dispatchIncoming` call. Without a per-app relayer check, that forged handler can make an app believe a message came from the authorised relayer when it did not: [3](#0-2) 

The Tron variant, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the same `RequestKind`-dispatch pattern (`RedeemEscrow`, `RefundEscrow`, `NewDeployment`, `UpdateParams`, `SweepDust`) but its `onAccept` never checks `incoming.relayer` against any authorised value before decoding and acting on the body: [4](#0-3) 

The only checks performed are `onlyHost` (the caller is the host) and, for governance-only actions, that `request.source` equals Hyperbridge's own state machine ID. Neither of these depends on which relayer address the host reports for the delivery. `authenticate()` (used for `RedeemEscrow`/`RefundEscrow`) checks the module sender, not the relayer, so it provides no protection against the forged-handler scenario either.

### Impact Explanation
If a forged consensus proof (or any other route that can install a malicious `handler` on the host, e.g. through the `HostManager`/`SetHostParam` chain described in the flow doc) is combined with this gateway, the malicious handler can report an attacker-controlled address as `relayer` on `dispatchIncoming`. Because `IntentGatewayV2.onAccept` performs no relayer check, any downstream logic in this codebase that trusts `incoming.relayer` as an authorisation signal (the same signal `ExtrinsicIntents._checkRelayer` exists to protect) is bypassed on the Tron deployment, reopening the exact "forged handler swap" attack the EVM fix closed. This can lead to unauthorized execution of escrow redeem/refund/withdrawal flows and governance-only actions (`NewDeployment`, `UpdateParams`, `SweepDust`) being processed under a spoofed relayer identity, directly risking theft or misdirection of escrowed funds.

### Likelihood Explanation
This requires the attacker to first achieve a forged/compromised handler (a non-trivial precondition shared with the EVM attack this mirrors), but once that precondition holds, exploitation against the Tron gateway is trivial and mirrors a scenario the project has already treated as a real, high-severity threat worth a dedicated fix and regression test (`testForgedHandlerSwapIsRefused`) on the EVM side.

### Recommendation
Port the `_relayer` / `_checkRelayer` gate (and its `setRelayer`/`migrate` arming logic) from `evm/src/apps/intentsv2/ExtrinsicIntents.sol` into `evm/tron/contracts/apps/IntentGatewayV2.sol`, calling it at the top of `onAccept` and `onGetResponse` before any body decoding, so the Tron deployment receives the same defense-in-depth against a forged handler that the EVM `ExtrinsicIntents` implementation already has.

### Proof of Concept
1. Assume an attacker can forge a consensus proof sufficient to deliver a `SetHostParam` request that swaps the Tron host's `handler` to a malicious contract implementing `IHandlerV2`'s interface (analogous to `MaliciousHandler` in `evm/tests/foundry/HostManagerTest.sol`).
2. The malicious handler calls `host.dispatchIncoming(request, attackerChosenRelayer)` for a crafted `PostRequest` with `body[0] = RequestKind.RedeemEscrow` (or another kind) and a `source`/`from` designed to pass `authenticate()`/the Hyperbridge-source check.
3. `IntentGatewayV2.onAccept` executes with `incoming.relayer == attackerChosenRelayer` — there is no equivalent of `_checkRelayer` to revert this, unlike `ExtrinsicIntents.onAccept`, so the withdrawal/governance action proceeds using the attacker-controlled relayer identity.

# 2026-09-03 — `HostManager` deliveries are gated too, and that does not touch permissionless relaying

Chosen: `HostManager.onAccept` refuses any relayer but the one the host admin set, zero included.

The app gates check an address the host reports, and the host takes it from its handler. The
handler is a host parameter that a `SetHostParam` governance message can replace, and until now
any relayer could deliver that message once its consensus proof verified. Under a forged consensus
an attacker would swap in a handler that reports the whitelisted relayer on every message, and the
app gates would pass. Gating the HostManager closes that route.

It does not weaken the open-relayer model because the HostManager never carries user traffic. Its
first check already rejects anything not sourced from Hyperbridge, so the only messages it ever
sees are Polytope's own `Withdraw` and `SetHostParam`. Third-party relayers keep delivering every
ordinary message to every ordinary app exactly as before.

    /**
     * @notice Executes an incoming post request.
     * @dev This function is called when an incoming post request is accepted.
     * It is only accessible by the host.
     * @param incoming The incoming post request data.
     */
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            authenticate(incoming.request);
