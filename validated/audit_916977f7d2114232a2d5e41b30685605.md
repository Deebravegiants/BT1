### Title
No cross-check between iris frames and self-custody face frame allows identity mismatch within a single signup - (File: src/plans/biometric_capture/mod.rs)

### Summary
`Plan::poll_extra` and `into_capture` only check that `left_ir`, `right_ir`, and `self_custody_candidate_rgb` are each individually present, never that they were captured from the same continuous physical presentation. Because `self_custody_candidate_rgb` is updated opportunistically across the *entire* capture session (both eye objectives) whenever a higher-scoring valid face frame arrives, an attacker who swaps identity between the two eye-scan objectives can bind a face capture of one person to iris captures of another person.

### Finding Description
`self_custody_candidate_rgb` is populated in `handle_face_identifier` [1](#0-0)  which runs concurrently with iris capture across both objectives (there is no `target_left_eye`/objective-index gating comparable to `handle_ir_net`'s left/right slot selection). It keeps whichever RGB frame scored highest for face validity, regardless of which objective (left-eye or right-eye) is currently active, and regardless of whether the iris frames captured before/after it belong to the same person.

The completion check in `poll_extra` only verifies presence, not identity consistency: [2](#0-1) 

`into_capture` similarly just requires all fields to be `Some`, with no cross-field identity comparison: [3](#0-2) 

There is no invocation of a "same-person" or face-vs-iris identity-matching check anywhere in this file, and `is_success`/`failure_feedback` also only check for presence of each component: [4](#0-3) 

Because `left_ir`/`right_ir` slots are captured independently per-objective (based on `target_left_eye`) with no re-validation that the left-eye captor and right-eye captor are the same person either, an attacker with an accomplice (or automated frame replay) could: present identity A during objective 1 (left eye) → high-scoring face frame for A stored in `self_custody_candidate_rgb` and `left_ir`/`left_rgb` stored for A → swap to identity B during objective 2 (right eye) → `right_ir`/`right_rgb` stored for B → `poll_extra` sees all fields populated and breaks, `into_capture` packages a `Capture` combining A's face/left-iris and B's right-iris.

I could not find, within `src/plans/biometric_capture/mod.rs`, `src/plans/biometric_pipeline/mod.rs`, or `src/plans/personal_custody_package.rs`, any subsequent same-person/identity cross-check between `face_self_custody_candidate` and the two `EyeCapture` iris frames before signing/uploading — the `face_identifier::Model` output only validates that the RGB frame contains *a* valid face for self-custody purposes (`IsValidImage`/`is_valid`), not that it matches the iris identity. This part of the analysis is based on available indexed content; downstream backend-side verification (if any exists off-device) could not be confirmed from the available code.

### Impact Explanation
If confirmed end-to-end, this would allow an iris code to be cryptographically/biometrically bound to a self-custody face image of a *different* person within the same signup package, undermining the self-custody identity-binding guarantee (the face image is meant to let the iris-code owner later re-authenticate/recover using their own face). This matches a "wrong identity binding" / biometric integrity bounty class, since the resulting `Capture` output would be internally inconsistent about whose iris and whose face are bound together.

### Likelihood Explanation
Exploitation requires an unprivileged attacker (or attacker+accomplice) able to control what is presented to the cameras during their own signup session — a precondition consistent with the audit's threat model (no operator/root access, no hardware tampering). It requires precise timing to swap presented identity between the two eye-scan objectives while keeping frames flowing (e.g., swapping seats/mirrors mid-scan or replaying frames), which is a real physical/logistical hurdle but plausible for a determined attacker with an accomplice, especially since there is no continuity/liveness cross-check between objectives in this code path. However, I was unable to confirm from the indexed code whether other layers (e.g., a distinct fraud-detection/liveness pipeline elsewhere in the codebase, or backend-side verification not visible in the index) already mitigate this — this is a limitation of the available search results, not a confirmed absence of mitigation.

### Recommendation
Add an explicit identity-consistency check before completing biometric capture: e.g., run a same-person/face-embedding comparison between the `self_custody_candidate_rgb` frame and a face embedding derived from (or associated with) the IR/RGB eye captures, and reject/reset the capture if they don't match. Alternatively, gate `self_custody_candidate_rgb` acquisition to a single fixed point in the sequence (e.g., only during the last objective, immediately following successful iris capture of both eyes, with a continuity/liveness check spanning the full capture window) rather than allowing it to be updated opportunistically across the whole session.

### Proof of Concept
Integration test plan for `src/plans/biometric_capture/mod.rs`:
1. Construct a `Plan` via `Plan::new`, feed synthetic `ir_net`/`rgb_net` outputs tagged with "identity A" markers for the first (left-eye) objective, causing `left_ir`/`left_rgb` and a high-scoring `self_custody_candidate_rgb` for A to be set via `handle_ir_net`/`handle_rgb_net`/`handle_face_identifier`.
2. Advance to the second (right-eye) objective and feed synthetic outputs tagged "identity B", causing `right_ir`/`right_rgb` for B to be set.
3. Call `poll_extra` and assert it currently returns `BrokerFlow::Break` (demonstrating the bypass) despite `self_custody_candidate_rgb` (A) and `right_ir`/`right_rgb` (B) originating from different identity markers.
4. Call `into_capture` and assert the resulting `Capture.face_self_custody_candidate` (A) and `Capture.eye_right`/`eye_left` (mixed A/B) are inconsistent — expected behavior after fix: `poll_extra`/`into_capture` should reject or reset the capture when identity markers mismatch between objectives.
