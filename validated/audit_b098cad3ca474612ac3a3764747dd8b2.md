This confirms the root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), while `shop`, `topic`, and `webhook_id` are all read from HTTP headers (`shopify_header`, `lib/shopify_api/webhooks/request.rb:20-33`) that are excluded from the HMAC computation. `HmacValidator.validate` only checks `verifiable_query.to_signable_string` (`lib/shopify_api/utils/hmac_validator.rb:27-31`), so it never authenticates the `shop-domain` header. Yet `Registry.process` passes this unauthenticated `request.shop` straight into `WebhookMetadata` (`lib/shopify_api/webhooks/registry.rb:189-199`, `lib/shopify_api/webhooks/webhook_handler.rb:6-12`), which is the value host apps use to identify which merchant/tenant the event belongs to.

### Title
Webhook `shop-domain` header is trusted for tenant identity but excluded from HMAC verification, enabling cross-tenant webhook forgery via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the host application a `WebhookMetadata` struct whose `shop` field is taken from the unauthenticated `shop-domain` header. Because the signature never covers this header, an attacker who can obtain any validly-signed webhook body/HMAC pair (e.g., from their own shop's own webhook deliveries) can resend that same body+HMAC with a forged `shop-domain` (and `topic`/`webhook-id`) header pointing at a different tenant. The app's webhook handler receives a `WebhookMetadata` that passes HMAC verification while attributing the event to an arbitrary shop, breaking the equality that should hold: `authenticated(shop_that_signed_the_payload) == shop_the_handler_believes_sent_it`.

### Finding Description
`Registry.process` gates all trust in a webhook on a single check: [1](#0-0) 

The HMAC check calls `Utils::HmacValidator.validate(request)`, which computes and compares the signature strictly against `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only the raw JSON body, never any header: [3](#0-2) 

Meanwhile `shop`, `topic`, and `webhook_id` are all read out of HTTP headers via `shopify_header`, none of which participate in the signable string: [4](#0-3) [5](#0-4) 

After the HMAC check passes, `Registry.process` unconditionally forwards `request.shop` into `WebhookMetadata`, the object the host application's `WebhookHandler#handle` trusts as the authenticated tenant identity for the event: [6](#0-5) [7](#0-6) 

This is exactly the "field acted on but not covered by the HMAC" pattern: the gem verifies *that the body byte-string was signed by the app's secret*, but the application-level identity binding (`shop`) is never part of what's verified. Any attacker who can obtain a single legitimately-signed webhook body+HMAC (trivially available to any merchant who installs the app on their own store and captures Shopify's own webhook delivery to their own endpoint) can replay that exact body/HMAC pair to the same public endpoint while substituting a different `shop-domain` header. `HmacValidator.validate` will still return `true` (the body and secret are unchanged), but `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop instead of the attacker's own shop.

### Impact Explanation
This crosses a tenant boundary: a webhook payload cryptographically proven only to originate from the app's secret key is relabeled, via an unauthenticated header, as belonging to an arbitrary other merchant. Host applications that key persistence, entitlement changes, or side effects (e.g., `APP_UNINSTALLED`, `SHOP_UPDATE`, `CUSTOMERS_DATA_REQUEST`, billing/subscription webhooks) off `data.shop` — which is the gem's documented and intended usage — will apply the attacker-chosen shop's state transition to the victim tenant. This matches the "cross-tenant access" High/Critical-impact category: an unprivileged internet user can, without ever seeing the app's `client_secret`, cause a webhook event to be misattributed to a store they do not own or operate.

### Likelihood Explanation
Exploitability requires only: (1) the attacker be able to install the target app on a shop they control (or otherwise obtain one valid signed webhook delivery, which Shopify sends automatically), and (2) the app's webhook endpoint be reachable from the internet, which is a deployment requirement for receiving Shopify webhooks at all. No secret material, TLS interception, or privileged access is needed — only replaying an HTTP POST with a modified header, which is well within "unprivileged internet user" capability.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the HMAC-verified surface, or otherwise independently authenticate them, before constructing `WebhookMetadata`. Concretely, extend `Webhooks::Request#to_signable_string` (or add a separate verification step in `Registry.process`) to incorporate the `shop-domain` header into the signed material actually validated by `HmacValidator`, so that a replay with a substituted header fails HMAC verification. At minimum, document prominently that `data.shop` is not covered by the HMAC and must not be trusted as tenant identity without an additional binding (e.g., cross-checking against a shop already known from an existing session/install record).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook (e.g. `orders/create`) to the app's public webhook endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, and some JSON `raw_body`.
2. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value (it is delivered to their own server/logs, so no interception of Shopify-attacker traffic is needed).
3. Attacker crafts a new HTTP POST to the same webhook endpoint, reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only (`lib/shopify_api/webhooks/request.rb:36-38`), which matches, so `Registry.process` proceeds.
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`) and invokes the app's handler with it, even though the payload was never actually signed in association with `victim-shop.myshopify.com`.
