## Title
First LP (pool creator) can inflate their share via `Initialize2`'s coarse LP-minting and then dilute later depositors through a direct-transfer donation, stealing value via `process_deposit`'s floor-rounded share math - (File: `program/src/processor.rs`, `program/src/math.rs`)

### Summary
`process_initialize2` mints LP tokens to the pool creator as `sqrt(init_pc_amount * init_coin_amount) - 10^lp_decimals`, with no floor beyond "> 0". A creator can choose amounts that just clear this threshold to receive as little as `1` LP token for the whole pool. Because `process_deposit` prices new deposits against the *live* vault token balances (which anyone can inflate via a plain SPL token transfer) using floor-rounded division, the creator can donate extra tokens to the vaults after minting only 1 LP token, then capture a disproportionate share of the next depositor's contribution — mirroring the "first depositor share-price manipulation" bug class from the referenced report.

### Finding Description
`process_initialize2` computes the initial liquidity purely from the sqrt of the deposited amounts and subtracts a fixed `10^lp_decimals` "burn", but the *number of LP tokens actually minted to the creator* (`user_lp_amount`) can be as small as `1`: [1](#0-0) 

This is set directly into `amm.lp_amount` and the vaults hold exactly `init_coin_amount`/`init_pc_amount`: [2](#0-1) [3](#0-2) 

The coin/pc vaults created here are ordinary SPL Token accounts owned by the AMM authority PDA; standard SPL semantics allow *anyone* to `transfer` tokens **into** them without any authority check on the destination, so their balance can be inflated at any time independent of `amm.lp_amount`.

When a later depositor calls `Deposit`, the pool's live vault balances (not the recorded `lp_amount`-consistent state) are read directly: [4](#0-3) 

and the number of new LP tokens minted is computed with **floor** rounding against the current `amm.lp_amount` and the (inflatable) `total_coin_without_take_pnl` / `total_pc_without_take_pnl`: [5](#0-4) [6](#0-5) 

There is no re-derivation of "fair" reserves from `lp_amount`, and no minimum-deposit or price-manipulation resistance — the only backstop is that `mint_lp_amount == 0` reverts the whole deposit (preventing a *complete* zero-mint griefing, but not a *diluting* deposit where `mint_lp_amount >= 1`): [7](#0-6) 

Because `amm.lp_amount` can be as low as `1`, the granularity of ownership is extremely coarse: any deposit that is not an exact integer multiple of `total_coin_without_take_pnl / lp_amount` will be floor-rounded down, and the "lost" fractional value is captured entirely by existing LP holders (i.e., the pool creator).

### Impact Explanation
An attacker who creates the pool can:
1. Call `Initialize2` with `init_coin_amount`/`init_pc_amount` chosen so `sqrt(init_pc_amount*init_coin_amount)` is only slightly larger than `10^lp_decimals`, minting themselves just `1` LP token while depositing a modest amount of real capital.
2. Directly transfer (donate) additional coin/pc tokens into `amm_coin_vault`/`amm_pc_vault` via the SPL Token program (not through the AMM program at all), inflating the pool's real balances while `amm.lp_amount` remains `1`.
3. Wait for (or front-run) the first real depositor's `Deposit` call. Because the deposit's `mint_lp_amount` is floor-divided against the inflated vault balance and the attacker's tiny `lp_amount`, the depositor's LP allocation rounds far down relative to the true value they contributed, and the surplus accrues to the attacker's single LP token.

This is a direct value transfer (theft) from the victim depositor to the attacker, i.e., concrete theft of user funds, matching the report's impact class.

### Likelihood Explanation
Pool creation via `Initialize2` is permissionless and reachable from a single transaction with attacker-chosen accounts/amounts; donating tokens into a public vault ATA is a standard, unrestricted SPL transfer requiring no special privilege. The only cost to the attacker is the capital locked in the donation (which they still own via their LP share) and normal deposit fees/slippage from real users, making the attack economically viable for freshly created, low-liquidity pools — precisely the scenario the underlying report describes for ERC-4626 vaults.

### Recommendation
- Enforce a fixed, sizable minimum LP-token mint amount for `Initialize2` (in LP token units, not raw asset value), analogous to Uniswap V2's `MINIMUM_LIQUIDITY` lock, so the first minted supply can never be as small as `1`.
- Alternatively/additionally, base share-issuance math for `Deposit` on internally tracked reserves updated only through program instructions (mint/burn/swap), rather than trusting `spl_token::Account::amount` read directly from the vaults, to remove the donation attack surface entirely.
- Consider rounding deposit share calculations in favor of the pool (ceiling for `deduct_*`, already done) but also enforce a minimum deposit size relative to current `lp_amount` to prevent low-liquidity-denomination griefing/theft.

### Proof of Concept
1. Attacker calls `Initialize2` with `init_coin_amount = init_pc_amount = 1_000_001` (6-decimal mints) → `liquidity = 1_000_001`, `user_lp_amount = 1_000_001 - 1_000_000 = 1` (`program/src/processor.rs` lines 908-918). Attacker now owns 100% of `amm.lp_amount = 1`, vault balances are `1_000_001` coin / `1_000_001` pc.
2. Attacker performs a plain SPL `transfer` of `10_000_000` coin and `10_000_000` pc tokens directly to `amm_coin_vault`/`amm_pc_vault` (no AMM instruction involved). Vault balances become `11_000_001` each; `amm.lp_amount` is unchanged at `1`.
3. Victim calls `Deposit` with `base_side = 0`, `max_coin_amount = 16_500_000` (attempting to deposit ~1.5x current pool value). `total_coin_without_take_pnl = 11_000_001` (`program/src/math.rs` lines 238-250); `mint_lp_amount = floor(1 * 16_500_000 / 11_000_001) = 1` (`program/src/processor.rs` lines 1243-1250, `program/src/math.rs` lines 457-477).
4. After the deposit, `amm.lp_amount = 2`, and total vault holdings ≈ `27_500_001`. The victim owns `1/2` of the pool (~`13_750_000`) despite contributing `16_500_000`+matching pc — a loss of roughly `2.75M` tokens per side that accrues entirely to the attacker's single LP token.

    pub fn exchange_token_to_pool(
        &self,
        pool_total_amount: u64,
        round_direction: RoundDirection,
    ) -> Option<u64> {
        Some(if round_direction == RoundDirection::Floor {
            U128::from(pool_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_div(self.token_total.into())
                .unwrap()
                .as_u64()
        } else {
            U128::from(pool_total_amount)
                .checked_mul(self.token_input.into())
                .unwrap()
                .checked_ceil_div(self.token_total.into())
                .unwrap()
                .as_u64()
        })
    }
