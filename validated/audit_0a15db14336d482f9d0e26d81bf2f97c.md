### Title
SSRF/credential leakage in `Oauth.begin_auth` and `Oauth.validate_auth_callback` via unvalidated `shop` parameter - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::ClientCredentials.client_credentials` and `ShopifyAPI::Auth::RefreshToken.refresh_access_token` both call `Utils::ShopValidator.sanitize!(shop)` before using the caller-supplied `shop` string to build the request host that will receive the app's `client_secret`. `ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback`, which implement the exact same "send `client_id`/`client_secret` to `https://#{shop}/admin/oauth/...`" pattern, never call `ShopValidator` on `shop`/`auth_query.shop`.

### Finding Description
The binding that should hold across every OAuth entry point in this library is: `shop domain used to build the outbound request host == a value proven to be a genuine `*.myshopify.com`/trusted Shopify domain`.

- `Utils::ShopValidator.sanitize!` [1](#0-0)  is the mechanism this gem provides to enforce that binding, and it is used consistently in `ClientCredentials.client_credentials` [2](#0-1)  and `RefreshToken.refresh_access_token` [3](#0-2)  before the `shop` value is used to construct `Auth::Session` and issue the request carrying `client_secret`.
- `Oauth.begin_auth`, however, takes the raw `shop:` argument and feeds it straight into `auth_base_uri(shop)` → `"https://#{shop}/admin"` with no `ShopValidator` call anywhere in the method [4](#0-3) [5](#0-4) .
- `Oauth.validate_auth_callback` likewise takes `auth_query.shop` and passes it directly to `Auth::Session.new(shop: auth_query.shop)`, which becomes the host of the `Clients::HttpClient` that POSTs `client_id`/`client_secret`/`code` to `https://#{shop}/admin/oauth/access_token` [6](#0-5) . There is no `ShopValidator.sanitize!` call in this path either. The only check performed is `Utils::HmacValidator.validate(auth_query)` [7](#0-6) , and `HmacValidator` requires `Context.api_secret_key` to forge, so a party without the secret cannot pass this check with an attacker-chosen `shop` — this path is not exploitable by an unprivileged internet user without the app's secret.
- `begin_auth`, by contrast, has no HMAC gate at all: it is the entry point of the flow, invoked by the host app typically with a `shop` value taken straight from an unauthenticated request (e.g. `request.headers["Shop"]` as literally shown in this gem's own documentation example) [8](#0-7) . If the host app forwards that unauthenticated input to `begin_auth` (which the documented example directly encourages), an attacker controls the `shop` string used to build the `auth_route` redirect target `https://#{shop}/admin/oauth/authorize?...&client_id=...`. Because `client_id` (and the app's own `redirect_uri`) is placed in the query string sent to that attacker-controlled host, this both (a) redirects the merchant's browser to an attacker-controlled origin, leaking the app's `client_id` and full OAuth authorize request to that origin, and (b) can be used to construct a forced-OAuth-completion / open-redirect flow, since the resulting redirect target is never checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

The gem itself demonstrates the sanitize-before-use pattern in three of four OAuth-adjacent flows (`ClientCredentials`, `RefreshToken`, and implicitly via `TokenExchange` deriving `shop` only from a verified JWT `dest` claim [9](#0-8) ), making the omission in `begin_auth`/`validate_auth_callback` an inconsistency rather than an intentional design choice deferred to the host app.

### Impact Explanation
This maps to "High - session fixation or forced OAuth completion" and partially to SSRF-adjacent credential exposure: the app's `client_id` (and, in a crafted redirect chain, potentially session state) is sent to a domain fully chosen by an unauthenticated party, and the merchant's browser is redirected off-platform as part of what looks like a legitimate install flow.

### Likelihood Explanation
Likelihood depends on whether the host application passes an unauthenticated `shop` parameter straight to `begin_auth`, which is exactly what this gem's own documentation example does (`shop = request.headers["Shop"]`). Given the library performs `ShopValidator.sanitize!` in every other analogous flow, a reasonable integrator relying on the gem to enforce the trusted-domain invariant consistently would not add their own validation here, making this a realistic and moderate-likelihood gap.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` (or `sanitize_shop_domain`) at the top of `Oauth.begin_auth` before constructing `auth_base_uri`, and validate `auth_query.shop` with the same helper in `Oauth.validate_auth_callback` before constructing the `Auth::Session`/`HttpClient`, mirroring the pattern already used in `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`.

### Proof of Concept
1. Host app exposes a login route that does `shop = params[:shop]; ShopifyAPI::Auth::Oauth.begin_auth(shop: shop, redirect_path: "/auth/callback")` (as shown in this gem's own `docs/usage/oauth.md` example using `request.headers["Shop"]`).
2. Attacker requests that route with `shop=attacker-controlled.example`.
3. `auth_base_uri("attacker-controlled.example")` returns `"https://attacker-controlled.example/admin"` [10](#0-9) , and `begin_auth` returns `auth_route: "https://attacker-controlled.example/admin/oauth/authorize?client_id=...&redirect_uri=...&state=..."`.
4. The victim's browser is redirected to the attacker's host with the app's `client_id` and `redirect_uri` in the query string — no `ShopValidator` check ever runs, unlike in `ClientCredentials`/`RefreshToken`.

          params(
            shop: String,
            redirect_path: String,
            is_online: T.nilable(T::Boolean),

          ).returns(T::Hash[Symbol, T.any(String, SessionCookie)])

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end

class ShopifyAuthController < ApplicationController
  def login
    shop = request.headers["Shop"]

    # Builds the authorization URL route to redirect the user to
    auth_response = ShopifyAPI::Auth::Oauth.begin_auth(shop: domain, redirect_path: "/auth/callback")

    # Store the authorization cookie
    cookies[auth_response[:cookie].name] = {
      expires: auth_response[:cookie].expires,
      secure: true,
      http_only: true,
      value: auth_response[:cookie].value
    }

    # Redirect the user to "auth_response[:auth_route]" to allow user to grant the app permission
    # This will lead the user to the Shopify Authorization page
    head 307
    response.set_header("Location", auth_response[:auth_route])
  end
