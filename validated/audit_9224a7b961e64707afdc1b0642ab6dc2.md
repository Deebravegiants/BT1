### Title
Webhook shop-tenant identity not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value that is handed to the app's `WebhookHandler` (and used by the host app to select/scope the tenant a webhook applies to) is read from the `X-Shopify-Shop-Domain` header, which is never included in the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header and is not part of that signable content: [2](#0-1) 

`Registry.process` validates only the HMAC (`Utils::HmacValidator.validate(request)` → computes HMAC over `to_signable_string`, i.e., body only) and then passes `request.shop` straight into `WebhookMetadata`, which is delivered to the app-defined handler as the tenant identifier: [3](#0-2) 

The identity binding broken is: `hmac == HMAC(body)` proves only that *some* request body was produced by a holder of the app's `client_secret` (i.e. genuinely came from Shopify for *some* shop using this app) — it does **not** prove `shop_header == shop_that_generated(body, hmac)`. The documentation explicitly instructs developers to trust `data.shop` from `WebhookMetadata` as the tenant identity for routing/processing: [4](#0-3) [5](#0-4) 

Because `hmac-sha256` is computed over the body only, any two webhooks that happen to share byte-identical `raw_body` content will produce the same valid HMAC signature regardless of which shop the header claims to be from. An attacker who is able to obtain one valid `(raw_body, hmac)` pair for a webhook they legitimately triggered on any shop installed with the app (e.g. by installing the app as a test/free merchant, or observing a `customers/redact`/mandatory topic payload, or any webhook whose body content is attacker-influenceable/predictable) can replay that exact body+hmac to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `Request#initialize` only checks for the presence of the header, not its correlation to the signed body: [6](#0-5) 

### Impact Explanation
This breaks the tenant (shop) identity binding: `shop_header == shop_that_produced(hmac, body)` is never checked, only `hmac == HMAC(body, client_secret)` is checked. This can result in cross-tenant data confusion — an app's webhook handler processing data intended/attributed to shop B while believing it belongs to shop A, corrupting per-tenant state, triggering unauthorized actions scoped to the spoofed shop, or bypassing per-shop authorization checks that rely on `data.shop`. This matches the Critical "cross-tenant access" category, since the gem itself provides no protection against a shop-identity mismatch and actively hands the unverified shop value to the app as trusted tenant metadata.

### Likelihood Explanation
Exploitability depends on an attacker being able to obtain a valid `(raw_body, hmac)` pair for content whose shop-domain header they want to spoof, and being able to send arbitrary POST requests with custom headers directly to the app's public webhook endpoint (both realistic for an unprivileged internet user/merchant, since webhook endpoints are public HTTP endpoints and merchants can trigger and often observe their own webhook deliveries, e.g., via mandatory-compliance topics or through predictable/attacker-controlled body content). No possession of `client_secret`, access tokens, or TLS interception is required — only a body+hmac pair legitimately produced by Shopify for the attacker's own shop.

### Recommendation
Bind the shop identity into the verified content: either (a) have `Request#to_signable_string` include the shop-domain header (and other identifying headers such as `topic`/`webhook_id`) in the HMAC-covered payload used for verification, or (b) after HMAC validation, cross-check `request.shop` against the shop associated with the session/installation the webhook is expected to be about (e.g., verify it matches a known, previously-installed store) before dispatching to the handler. At minimum, document prominently that `data.shop` is not itself authenticated and must be independently validated by the host application before being trusted as a tenant identifier.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`, or otherwise obtain a legitimate webhook delivery `(raw_body, hmac)` pair sent by Shopify to the app (e.g., via a triggerable/predictable-body topic).
2. Capture the raw POST body and the `X-Shopify-Hmac-Sha256` header value from that delivery.
3. Send a new POST request directly to the app's registered webhook URL, keeping the same raw body and `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` succeeds because it only checks `HMAC(raw_body)`; the handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` paired with attacker-controlled body content, as shown in: [3](#0-2)

        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
