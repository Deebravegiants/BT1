### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is read separately and never included in the signed material. `Registry.process` validates the HMAC over the body alone and then trusts the unauthenticated `shop` header to attribute the payload to a tenant when invoking the app's webhook handler.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` with: [1](#0-0) 
`shop` is pulled straight from a header and is *not* part of `to_signable_string`, so it is excluded from the HMAC computation performed in `HmacValidator.validate`: [2](#0-1) 
`Registry.process` only checks that the HMAC (computed over the body) is valid, then forwards the caller-supplied `request.shop` value verbatim to the app's handler as the tenant identity for the webhook: [3](#0-2) 

Because the same `client_secret`/`api_secret_key` is used to sign webhooks for *every* shop that has installed the app (it is not shop-specific), any body+HMAC pair that is valid for one shop is also a syntactically valid HMAC when replayed with the same body but a different `shop-domain` header — the signature never covered `shop` in the first place. This breaks the identity binding `HMAC-verified request == the shop attributed to that request`.

### Impact Explanation
An attacker who is a legitimate but unprivileged installer of the app on their own store (Shop A) receives (or can trigger) genuine webhook deliveries containing valid `(body, hmac)` pairs signed with the app's shared secret. By POSTing that same body/HMAC pair directly to the app's public webhook endpoint while substituting the `shop-domain` header with a victim's shop (Shop B), the request still passes `HmacValidator.validate`, and the handler receives `WebhookMetadata` with `shop: "shop-b.myshopify.com"` even though the payload was never sent by/for Shop B. Any app logic that uses `data.shop` to look up sessions, apply data, or make authorization decisions for that tenant can be tricked into acting on forged data attributed to a different merchant — a cross-tenant access primitive as defined by the impact criteria (Critical).

### Likelihood Explanation
Exploitation requires only: (1) being able to install the target app on any shop (the normal, unprivileged onboarding flow for a public app), and (2) the ability to send an HTTP POST with attacker-controlled headers directly to the app's public webhook route (no access token, no `api_secret_key`, no TLS interception needed). This is reachable entirely through the gem's own webhook-verification API surface as documented and used by host apps.

### Recommendation
Include the shop-domain header (and ideally the topic/api-version/webhook-id) inside `to_signable_string`, or otherwise bind `request.shop` cryptographically to the verified payload, e.g.:
```ruby
def to_signable_string
  "#{shop}:#{@raw_body}"
end
```
so that tampering with the `shop-domain` header invalidates the HMAC, restoring the binding between the verified bytes and the shop identity acted upon.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, receives/triggers a legitimate webhook and captures its raw body `B` and its valid `x-shopify-hmac-sha256` value `H` (both computed with the app's shared secret, not shop-specific).
2. Attacker sends a forged POST directly to the app's webhook endpoint:
```
POST /webhooks HTTP/1.1
x-shopify-topic: orders/create
x-shopify-hmac-sha256: H
x-shopify-shop-domain: victim-shop.myshopify.com

B
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`== B`) and matches `H` — validation succeeds [4](#0-3) .
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` [5](#0-4) , causing the app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
