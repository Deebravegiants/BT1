Confirmed: `RequestMessage.requests: Vec<PostRequest>` and the top-level `handle_unsigned(messages: Vec<Message>)` are both unbounded, and `handle_unsigned` is dispatched as `ensure_none` (fully permissionless, fee-less) with a **static** declared weight.### Title
`pallet-ismp::handle_unsigned` charges a static declared weight regardless of actual batch size, letting a fee-less unsigned extrinsic exhaust block-execution time — Allocation of Resources Without Limits or Throttling - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`Call::handle_unsigned` accepts an unbounded `Vec<Message>` where each `Message::Request`/`Message::Response` itself carries an unbounded `Vec<PostRequest>`/`Vec<GetRequest>`. The extrinsic is dispatched with `ensure_none(origin)` (fully permissionless, fee-less — "This allows users execute ISMP datagrams for free") [1](#0-0) , yet its declared weight is a fixed constant, `Weight::from_parts(300_000_000, 0)`, independent of how many messages or nested requests the batch contains [2](#0-1) .

### Finding Description
`RequestMessage.requests: Vec<PostRequest>` and `ResponseMessage.requests: Vec<GetRequest>` have no bound (`BoundedVec` or explicit cap) [3](#0-2) , and the outer `handle_unsigned(messages: Vec<Message>)` call likewise takes an unbounded `Vec<Message>` [4](#0-3) .

`validate_unsigned` for this pallet does not merely check validity cheaply — it actually **executes** the entire batch (`Self::execute(messages.clone())`) during transaction-pool validation, before the extrinsic is even included in a block [5](#0-4) . `execute()` iterates every message and calls `handle_incoming_message` for each, which in turn iterates every request in the batch, verifies membership/non-membership proofs, hashes each request, and dispatches to `IsmpModule::on_accept`/`on_response` [6](#0-5) [7](#0-6) .

Because the call is unsigned (no nonce, no fee, `ensure_none`), and the declared `#[pallet::weight(weight())]` used for block-inclusion accounting is the static constant above rather than something scaled by `messages.len()` or the aggregate request/key count, an attacker can submit a single valid extrinsic containing an extremely large batch (thousands of `PostRequest`/`GetRequest`/`GetRequest.keys` entries, each requiring proof verification, hashing, and dispatch) whose actual computational cost vastly exceeds the 300M declared weight units used by the runtime's weight-to-block-time accounting. This breaks the invariant that "declared weight ≈ real execution time" that keeps block authoring within its slot budget, and — since the same call is *executed* during `validate_unsigned` on every full node that receives the gossiped transaction, for free — enables network-wide CPU amplification even before block inclusion.

The batch size is bounded only indirectly by `RuntimeBlockLength` (e.g. 5 MB, up to 85% for the extrinsic on solochains per the docs) [8](#0-7) , which limits encoded bytes but not the number of independent proof-verification/hashing/dispatch operations that fit inside that byte budget when many small requests are packed together, especially GET requests whose `keys: Vec<Vec<u8>>` field is itself unbounded.

### Impact Explanation
This is a High-severity resource-exhaustion vector directly analogous to CVE-2022-21822 (unauthenticated actor causing unbounded resource allocation, leading to system unavailability):
- Any unprivileged party can submit crafted `handle_unsigned` batches (as long as the requests carry a currently-valid membership/non-membership proof against an already-finalized state commitment — which relayers regularly produce) that are cheap to construct but expensive to re-verify per request.
- Every node executes the full batch during `validate_unsigned` for free before block inclusion, and the fixed declared weight understates the real cost used for block-time budgeting once such a batch is included, risking block-production stalls/timeouts (denial of service against the ISMP-hosting chain, i.e. Hyperbridge itself or any connected chain running pallet-ismp).
- This directly reaches the message-dispatch path that this class of finding is scoped to: `pallet-ismp handle_unsigned` and its request/response handlers.

### Likelihood Explanation
Medium-to-High. No privileged role is required — `ensure_none` accepts any unsigned submission with a valid proof. Constructing a batch with many entries under a single valid multi-proof is a normal relayer operation scaled up; the attacker only needs to build/replay a legitimately provable batch of maximal size, not forge anything cryptographically. The main mitigating factors are the encoded-extrinsic byte cap (`RuntimeBlockLength`) and mempool longevity/dedup (`provides` tag), which reduce but do not eliminate the amplification, since the byte cap still allows many thousands of small `GetRequest`/`PostRequest` entries per transaction.

### Recommendation
- Scale the declared weight of `handle_unsigned` (and the `state-coprocessor` pallet's analogous `handle_unsigned`) with the actual number of `Message`s and nested requests/keys in the batch (e.g., `WeightInfo::handle_unsigned(messages.len(), total_requests, total_keys)`), rather than a fixed constant.
- Introduce explicit `BoundedVec` caps (configurable `Config::MaxMessagesPerBatch`, `Config::MaxRequestsPerMessage`, `Config::MaxKeysPerGetRequest`) enforced at both SCALE-decode time and in `validate_unsigned`/`execute`, rejecting oversized batches early instead of relying solely on block-length limits.
- Consider charging (or throttling) unsigned batches based on measured proof-verification cost rather than treating all `handle_unsigned` calls as uniformly "free."

### Proof of Concept
1. Construct a `RequestMessage` (or `ResponseMessage`) whose `requests` vector contains the maximum number of `PostRequest`/`GetRequest` entries that fit within `RuntimeBlockLength`'s extrinsic-length allowance, each carrying a distinct nonce but referencing commitments provable under one legitimate multi-proof against a known finalized `StateCommitment`.
2. Wrap it as `Message::Request(...)`/`Message::Response(...)` inside `Call::handle_unsigned { messages: vec![...] }` and submit it as an unsigned extrinsic (as done in the test harness pattern) [9](#0-8) .
3. Observe that `validate_unsigned` fully executes `Self::execute(messages.clone())` [5](#0-4)  — verifying every proof, hashing every request, and invoking `on_accept`/`on_response` for each — while the pallet declares only the fixed `Weight::from_parts(300_000_000, 0)` [2](#0-1)  for block-inclusion accounting, regardless of `messages.len()` or the number of nested requests, demonstrating the mismatch between declared and actual resource consumption.

Note: I could not fully verify from the indexed code whether a global cap on `messages.len()` or per-message request count exists anywhere else in the runtime configuration (e.g., in `Config` bounds not surfaced by the index) — if such a cap exists and is enforced pre-execution, it would reduce the severity of this finding. I recommend confirming this via a full repository checkout (Devin session) before treating the finding as final, since the index may not surface every configuration constant.

	let state = host.state_machine_commitment(msg.proof.height)?;
	let commitments = msg
		.requests
		.iter()
		.map(|post| hash_request::<H>(&Request::Post(post.clone())))
		.collect();
	state_machine.verify_membership(host, commitments, state, &msg.proof)?;

	let mut total_weights = Weight::zero();
	let result = msg
		.requests
		.into_iter()
		.map(|request| {
			let wrapped_req = Request::Post(request.clone());
			let mut lambda = || {
				let cb = router.module_for_id(request.to.clone())?;
				// Re-check the receipt right before dispatch. The up-front pass above
				// runs before any callback executes; a prior request's on_accept in
				// this same batch could have stored a receipt for this request
				// (directly or by re-entering the handler), and we must not invoke
				// on_accept a second time.
				if host.request_receipt(&wrapped_req).is_some() {
					Err(Error::DuplicateRequest { meta: wrapped_req.clone().into() })?
				}
				// Store request receipt to prevent reentrancy attack
				let signer = host.store_request_receipt(&wrapped_req, &msg.signer)?;
				let res = cb.on_accept(request.clone()).map(|weight| {
					total_weights.saturating_accrue(weight);

					let commitment = hash_request::<H>(&wrapped_req);
					Event::PostRequestHandled(RequestResponseHandled {
						commitment,
						relayer: signer,
					})
				});
				// Delete receipt if module callback failed so it can be timed out
				if res.is_err() {
					host.delete_request_receipt(&wrapped_req)?;
				}
				Ok(res)
			};

			let res = lambda().and_then(|res| res);
			res
		})
		.collect::<Vec<_>>();
