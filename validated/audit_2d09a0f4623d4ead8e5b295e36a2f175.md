### Title
Cross-tenant webhook spoofing via `shop-domain` header not covered by HMAC signature — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header as the tenant identity passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is derived from the `hmac-sha256` header [1](#0-0) . `HmacValidator.validate` computes the signature over `to_signable_string` (i.e., only the body) using `Context.api_secret_key` [2](#0-1) . `Registry.process` gates on this HMAC check and then immediately builds `WebhookMetadata` from `request.shop` (taken straight from the `shop-domain` header) without any additional verification that this shop matches the shop the signed body actually belongs to [3](#0-2) . `request.shop` is read verbatim from the `shopify-shop-domain`/`x-shopify-shop-domain` header [4](#0-3) .

This is the same class of bug as the referenced report: the field the application acts on (`shop`, used as the tenant identity/session key downstream, as shown in the docs' `WebhookHandler` example that dispatches jobs keyed by `data.shop`) is not the field the equality check (HMAC) actually covers [5](#0-4) . The binding that should hold is:
`shop_used_by_handler == shop_the_signature_actually_authenticates`
but the HMAC only authenticates `body`, never `shop`, so this equality is not enforced by the gem.

Because `api_secret_key` is a single per-app value shared across every shop that installs the app (not a per-shop secret), any legitimate installer of the app receives valid `(body, hmac)` pairs from Shopify for their own shop's webhooks. Since the header carrying `shop-domain` is outside the signed payload, an attacker who has installed the app on their own (attacker-controlled) shop can capture one authentic webhook delivery and replay the exact same signed body to the app's public webhook endpoint while substituting a different `shop-domain` header value. `Registry.process` will accept it as valid (the HMAC check passes because the body/signature pair is genuinely Shopify-signed) and will hand the handler a `WebhookMetadata` claiming to be from a different shop.

### Impact Explanation
This breaks the shop-authenticated vs. shop-used-as-tenant-key binding and enables cross-tenant confusion: an unprivileged app installer can cause the app to process attacker-supplied webhook content under an arbitrary victim shop's identity, without needing the app's `client_secret`, an access token, or any privileged credential — they only need their own legitimate, low-privilege app installation. Depending on how the host application uses `data.shop` (e.g., to look up/associate the wrong merchant's session or trigger shop-scoped side effects), this can lead to cross-tenant data confusion or actions being attributed to/executed against the wrong tenant, matching the "High: cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation requires only a standard, unprivileged app installation (any merchant can install a public/embedded app) plus the ability to send an arbitrary HTTP request with attacker-chosen headers and a captured valid body/HMAC pair to the app's publicly reachable webhook route — no secrets, tokens, or elevated access are required. It does depend on the host application actually trusting `data.shop` for something tenant-sensitive rather than independently re-validating it, which the gem's own documentation encourages (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`).

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed payload, or otherwise require the host application to independently verify that `shop` corresponds to a shop with an active, known session/installation before trusting it as a tenant key. At minimum, document prominently that `shop`, `topic`, and `webhook_id` are not covered by the HMAC verification and must not be trusted as an authenticated tenant identifier without additional cross-checking against a known/installed shop.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers for a webhook topic.
2. Shopify delivers a genuine webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(B, api_secret_key)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers fine (all required headers present) [6](#0-5) ; `Utils::HmacValidator.validate(request)` returns `true` because it only checks the body against the hmac, which is unchanged [2](#0-1) .
5. `Registry.process` proceeds and invokes the app's handler with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)` [3](#0-2) , causing the app to act as if the (attacker-controlled) payload `B` originated from the victim shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
