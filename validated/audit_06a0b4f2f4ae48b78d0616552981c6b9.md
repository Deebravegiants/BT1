Audit Report

## Title
Staking after pool expiry can permanently brick a pool via arithmetic underflow in `reward_per_token` - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards`'s `stake` extrinsic performs no check that the pool has not already expired, and `update_pool_rewards` always stamps `last_update_block` with the true current block instead of clamping it to `expiry_block`. Combined with `reward_per_token`'s zero-stake fast path, this lets `last_update_block` end up set to a value greater than `expiry_block` while `total_tokens_staked == 0`; any subsequent stake into that pool causes `total_tokens_staked` to become non-zero, and every following `reward_per_token` computation then does `expiry_block.ensure_sub(last_update_block)` with `last_update_block > expiry_block`, causing a checked-arithmetic underflow error that permanently reverts `stake`, `unstake`, and `harvest_rewards` for that pool.

## Finding Description
`stake` has no expiry check: [1](#0-0) . By contrast, `unstake` and `harvest_rewards` only restrict *who* can act once the pool is expired (`now > pool_info.expiry_block || caller == staker`), but do not prevent action after expiry itself: [2](#0-1) [3](#0-2) .

`reward_per_token` takes a fast path returning the stored value unchanged when `total_tokens_staked` is zero, and otherwise computes `last_block_reward_applicable(expiry_block).ensure_sub(last_update_block)`: [4](#0-3) . `last_block_reward_applicable` clamps "now" to `expiry_block` once expired: [5](#0-4) . But `update_pool_rewards` always writes the real, unclamped current block into `last_update_block`: [6](#0-5) .

Tracing an exploitable sequence: if a pool's last staker fully unstakes after `expiry_block` (a normal, permissionless action per the `unstake` guard), `reward_per_token` at that call computes correctly (using the still-valid, pre-expiry `last_update_block`), but `update_pool_rewards` then sets `last_update_block` to the current (post-expiry) block while `total_tokens_staked` becomes `0`. At this point the pool is in the exact "poisoned" state the report describes: `total_tokens_staked == 0` and `last_update_block > expiry_block`. Any later `stake` call (unrestricted by any expiry check) succeeds via the zero-stake fast path, leaving `total_tokens_staked > 0` again while `last_update_block` remains `> expiry_block`. From that point, every future call to `reward_per_token` (triggered by `stake`, `unstake`, or `harvest_rewards`) takes the non-zero branch and computes `expiry_block.ensure_sub(last_update_block)`, which underflows because `last_update_block > expiry_block`, and `ensure_sub` (checked subtraction) returns `Err`, causing the whole extrinsic to fail.

This confirms the finding's core mechanism, and additionally shows the precondition (`last_update_block > expiry_block` with `total_tokens_staked == 0`) is reachable purely through normal, permissionless post-expiry `unstake` activity — not only through a pool that was "never staked."

Once poisoned, `cleanup_pool`'s guard requires the stakers list to be empty (`PoolStakers::iter_key_prefix(pool_id).next().is_none()`), which can never become true because `unstake` on the poisoned staker will always fail with the underflow error: [7](#0-6) .

## Impact Explanation
This is a real, unprivileged, permanent denial-of-service against a core pallet flow: once poisoned, the pool's reward-asset balance held at `pool_info.account` and its `PoolCost` storage deposit become permanently unrecoverable, since `cleanup_pool` can never pass its non-empty-stakers guard and the poisoned staker's own funds are also frozen forever (since `unstake` always reverts). This matches the claim's "funds locked forever" impact and is caused entirely by SDK pallet logic, not any external or node-level behavior.

## Likelihood Explanation
The trigger requires no privilege: any account can call `stake` on a pool that is past its `expiry_block` with `total_tokens_staked == 0` — a state reachable either by nobody ever staking, or (as shown above) by the normal, permissionless post-expiry `unstake` path draining the last staker. No race condition, governance action, or unrealistic assumption is needed; it is a low-cost, repeatable griefing vector against any pool nearing/at expiry with zero current stake.

## Recommendation
- Reject `stake` when `now >= pool_info.expiry_block`, mirroring the intent already partially present in `unstake`/`harvest_rewards`.
- Clamp `last_update_block` to `min(now, expiry_block)` in `update_pool_rewards`, so `reward_per_token`'s subtraction can never underflow regardless of call ordering.
- Consider allowing `cleanup_pool` (or an admin-only sweep) to force-remove residual zero-reward stakers after expiry so a poisoned state cannot permanently block fund recovery.

## Proof of Concept
1. Admin creates a pool with `expiry_block = E`. A staker deposits before `E`, then fully unstakes at block `C3 > E` (permitted since `unstake` only restricts caller identity, not timing) — this sets `pool_info.last_update_block = C3 > E` while `total_tokens_staked = 0`.
2. At block `C4 >= C3`, an attacker calls `stake(pool_id, 1)`. `reward_per_token` takes the zero-stake fast path (no error), and `update_pool_rewards` sets `last_update_block = C4` (still `> E`), while `total_tokens_staked` becomes `1`.
3. At block `C5 >= C4`, any call touching this pool (e.g., `unstake(pool_id, 1, Some(attacker))`, permissionless since `now > E`) invokes `reward_per_token`, which now takes the non-zero branch: `last_block_reward_applicable(E) = E`, then `E.ensure_sub(C4)` underflows because `C4 > E`, returning `Err`, and the extrinsic fails.
4. All subsequent `stake`/`unstake`/`harvest_rewards` calls on this pool fail identically, and `cleanup_pool`'s `ensure!(stakers.is_none(), ...)` guard can never pass, permanently locking the pool's reward-asset balance and `PoolCost` deposit.

This can be verified with a unit test in `substrate/frame/asset-rewards/src/tests.rs` that advances the mock block number past a created pool's expiry, drains all stakers via `unstake`, then calls `stake` again and asserts that a subsequent `unstake` or `harvest_rewards` call returns an arithmetic underflow `DispatchError`.

		#[pallet::call_index(8)]
		pub fn cleanup_pool(origin: OriginFor<T>, pool_id: PoolId) -> DispatchResult {
			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;
			ensure!(pool_info.admin == who, BadOrigin);

			let stakers = PoolStakers::<T>::iter_key_prefix(pool_id).next();
			ensure!(stakers.is_none(), Error::<T>::NonEmptyPool);

			let pool_balance = T::Assets::reducible_balance(
				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,
				Fortitude::Polite,
			);
			T::Assets::transfer(
				pool_info.reward_asset_id,
				&pool_info.account,
				&pool_info.admin,
				pool_balance,
				Preservation::Expendable,
			)?;

			if let Some((who, cost)) = PoolCost::<T>::take(pool_id) {
				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
		}

		/// Derives the current reward per token for this pool.
		pub(super) fn reward_per_token(
			pool_info: &PoolInfoFor<T>,
		) -> Result<T::Balance, DispatchError> {
			if pool_info.total_tokens_staked.is_zero() {
				return Ok(pool_info.reward_per_token_stored);
			}

			let rewardable_blocks_elapsed: u32 =
				match Self::last_block_reward_applicable(pool_info.expiry_block)
					.ensure_sub(pool_info.last_update_block)?
					.try_into()
				{
					Ok(b) => b,
					Err(_) => return Err(Error::<T>::BlockNumberConversionError.into()),
				};

			Ok(pool_info.reward_per_token_stored.ensure_add(
				pool_info
					.reward_rate_per_block
					.ensure_mul(rewardable_blocks_elapsed.into())?
					.ensure_mul(PRECISION_SCALING_FACTOR.into())?
					.ensure_div(pool_info.total_tokens_staked)?,
			)?)
		}
