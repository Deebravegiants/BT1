### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity is trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity solely via an HMAC computed over the raw request body, then dispatches the handler using the shop identity taken from an HTTP header that is never included in that HMAC computation. This breaks the intended binding "the shop credited with a webhook event == the shop that actually generated the signed bytes."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are pulled directly from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC (bytes verified) and then immediately trusts `request.shop` (bytes parsed) to build the metadata handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the body) against the `hmac` field — it has no knowledge of, and cannot bind, the `shop-domain` header: [4](#0-3) 

Equality that should hold: `shop_credited_to_event == shop_that_produced_the_signed_bytes`. Because the HMAC only covers `raw_body`, an attacker who possesses *any* validly-signed `(raw_body, hmac)` pair for the app's shared `client_secret` (trivially obtainable by installing the app, even for a short time, on a shop the attacker controls, and capturing one webhook delivery) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. The HMAC check still passes (body untouched), but `WebhookMetadata#shop` — and thus everything the host app's webhook handler does keyed on "shop" (writing state, triggering actions, invalidating data, crediting orders, etc.) — is now attributed to a victim shop the attacker never had access to. This is a cross-tenant identity-binding break, directly analogous to the report's "field acted on but not covered by the HMAC" bug class.

### Impact Explanation
This lets an unprivileged attacker (a merchant who merely installed the app on their own store, or anyone who intercepts/replays a delivered webhook) forge webhook events that are processed by the app under an arbitrary, attacker-chosen shop identity. Because host applications built on this library are expected to key persistent state/actions off `WebhookMetadata#shop`, this enables cross-tenant data corruption or cross-tenant actions — matching the Critical "cross-tenant access" impact category, since the shop-scoping guarantee the gem is supposed to provide via HMAC verification is violated.

### Likelihood Explanation
Exploitation only requires: (1) obtaining one legitimately-signed webhook body+HMAC pair, which is trivial for an app that supports self-serve installs (attacker installs on their own store and triggers any webhook topic), and (2) replaying it to the target app's public webhook endpoint with a modified `x-shopify-shop-domain`/`shopify-shop-domain` header. No access to `api_secret_key`, tokens, or any privileged account is needed beyond an ordinary, self-service app install.

### Recommendation
Bind the `shop` (and ideally `topic`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop identity to the signed payload before trusting it in `Registry.process`. At minimum, cross-check the header-provided `shop` against a shop already known/authorized for this app (e.g., an existing offline session) before invoking the handler, rather than trusting the raw header value once the body's HMAC checks out.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw POST body `B` and the `x-shopify-hmac-sha256` header `H` sent by Shopify (valid because it's signed with the app's shared `client_secret`).
2. Attacker sends a forged request to the app's webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H          # unchanged
   x-shopify-shop-domain: victim-shop.myshopify.com   # forged
   x-shopify-webhook-id: <any>
   Body: B                          # unchanged
   ```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only checks `B` against `H`. [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the host app to process/act on data as if it originated from `victim-shop.myshopify.com`, even though it never sent this webhook.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
