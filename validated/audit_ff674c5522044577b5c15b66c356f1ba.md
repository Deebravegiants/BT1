### Title
Unregistered destination/source chains fall back to `address(this)` in `IntentGatewayV2.instance()`, letting an attacker forge escrow withdrawals — (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.instance()` returns `address(this)` whenever a `stateMachineId` has no registered peer in `_instances` [1](#0-0) . This "default identity" is then relied upon by `authenticate()`, the only gate protecting `RedeemEscrow`/`RefundEscrow` delivery in `onAccept` [2](#0-1) [3](#0-2) . This is structurally the same class of bug as CVE-2019-7304: an owner/peer identity check that silently degrades to a permissive default when the real identity was never configured, letting an unprivileged actor impersonate the expected principal.

### Finding Description
`authenticate()` is the sole check that a `RedeemEscrow`/`RefundEscrow` `onAccept` call really originates from a known instance of `IntentGatewayV2` on the claimed source chain:
```solidity
function authenticate(PostRequest calldata request) internal view {
    if (request.from.length != 20) revert InvalidInput();
    address module = address(bytes20(request.from));
    if (instance(request.source) != module) revert Unauthorized();
}
``` [2](#0-1) 

`instance()` is defined as:
```solidity
function instance(bytes calldata stateMachineId) public view returns (address) {
    address gateway = _instances[keccak256(stateMachineId)];
    return gateway == address(0) ? address(this) : gateway;
}
``` [1](#0-0) 

For any `request.source` state machine that has *not* been explicitly registered via `NewDeployment` (governed by Hyperbridge, per `onAccept`'s later branch [4](#0-3) ), `instance()` returns `address(this)` — the deploying chain's own gateway address — instead of reverting or requiring an explicit peer. Consequently, `authenticate()` accepts *any* message whose `request.from` equals `address(this)` (this contract's own address), regardless of what chain it claims to be from, as long as ISMP's proof machinery accepts a `request.source` for some state machine Hyperbridge has a consensus client for.

Since `IntentGatewayV2` is intended to be deployed at the same address across many EVM chains via CREATE2 (as referenced throughout the SDK and LZ-endpoint docs' "assumes same contract address on all chains" pattern), an attacker who deploys a malicious/self-controlled contract at that identical address on any EVM-compatible chain that Hyperbridge already has (or will have) a working consensus client for — but where the operator has not yet called `NewDeployment` to register that chain in `_instances` — can dispatch a forged `RedeemEscrow` or `RefundEscrow` `PostRequest` from that chain. The forged message's `from` field trivially satisfies `address(bytes20(request.from)) == address(this)` because the attacker deployed exactly at that address.

Once `authenticate()` passes, `onAccept` decodes an attacker-controlled `WithdrawalRequest{commitment, tokens, beneficiary}` and calls `withdraw()`, which pays out real escrowed order funds for that `commitment` to the attacker-chosen `beneficiary` [5](#0-4) [6](#0-5) . The only remaining backstop is that `_orders[commitment][token]` must be non-zero for the targeted commitment (i.e., a real order with that exact commitment hash must have been escrowed) — but any legitimate cross-chain order whose `order.source`/`order.destination` matches the unregistered chain qualifies, and an attacker who also controls the fake chain can drive both legs of the order lifecycle.

### Impact Explanation
This allows theft/misdirection of escrowed order funds: an attacker satisfying the CREATE2 same-address assumption on an unregistered-but-consensus-known chain can forge `RefundEscrow`/`RedeemEscrow` deliveries and redirect `withdraw()` payouts to an arbitrary `beneficiary`, draining escrowed `_orders[commitment][token]` balances that belong to real users' cross-chain intents. This is a concrete theft-of-funds path reachable by a single forged/relayed ISMP message from an unprivileged actor, matching the required severity bar (Medium/High/Critical, concrete theft or forged message delivery).

### Likelihood Explanation
Exploitability depends on: (1) Hyperbridge already running (or later running) a consensus client for some EVM state machine that the IntentGateway governance has not yet called `NewDeployment` for, and (2) the attacker being able to deploy a contract at the exact `address(this)` value via CREATE2 on that chain (straightforward on a fresh/newly-supported chain). Given IntentGatewayV2 deployments explicitly rely on identical cross-chain addressing as a design assumption, and new chains are periodically onboarded to Hyperbridge before every app's peer registry is updated, this is a realistic operational window rather than a purely theoretical one.

### Recommendation
`instance()` should not silently fall back to `address(this)` for use in `authenticate()`'s security check. Either:
- Revert (e.g., `revert UnknownSource()`) when `_instances[keccak256(stateMachineId)] == address(0)` inside `authenticate()`, requiring an explicit, governance-registered peer before any inbound escrow action is trusted; or
- Split `instance()` into two functions: a permissive lookup used only for constructing GET-request storage keys (where a same-address default may be intentional), and a strict lookup used by `authenticate()` that never defaults to `address(this)`.

### Proof of Concept
1. Hyperbridge onboards consensus support for `Evm(X)` (a new chain) but `IntentGatewayV2` governance has not yet called `NewDeployment` for `Evm(X)`, so `_instances[keccak256(Evm(X))] == address(0)`.
2. Attacker deploys a contract via CREATE2 on `Evm(X)` at the exact same address as the destination chain's `IntentGatewayV2`.
3. Attacker's contract dispatches (or the attacker gets a relayer to deliver) a forged `PostRequest` with `source = Evm(X)`, `from = <this address>`, `body = [RedeemEscrow|RefundEscrow] ++ abi.encode(WithdrawalRequest{commitment: <target order commitment>, tokens: ..., beneficiary: <attacker>})`.
4. On delivery, `onAccept` → `authenticate()` computes `instance(Evm(X)) == address(this)` (default) and `module == address(this)` (attacker's CREATE2 address), so the check passes despite `Evm(X)` never being registered.
5. `withdraw()` pays out the escrowed `_orders[commitment][token]` to the attacker's `beneficiary`.

Note: I could not fully verify from the index whether an additional filter exists elsewhere (e.g., a consensus-client allowlist restricting which `StateMachine`s can produce valid proofs at all) that might narrow which "unregistered" chains are actually reachable; a Devin session with full repo access would be needed to confirm the exact scope of currently-configured consensus clients versus registered `_instances` peers across deployed environments.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
