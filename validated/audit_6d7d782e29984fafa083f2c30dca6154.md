## Title
Webhook HMAC Verifies Only the Raw Body, Allowing Cross-Tenant Shop/Topic Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
The C4 report's root cause is a rounding calculation that is applied to some parties (`votingPower`) but not others (`splitRecipient`), breaking the invariant that the parts must equal the whole. The analogous bug class here is "a field acted on but not covered by the HMAC": in `ShopifyAPI::Webhooks::Request`, the HMAC computed by Shopify only signs the raw JSON body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the library extracts and hands to the merchant's webhook handler come straight from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0)  and `Utils::HmacValidator.validate` computes/compares the HMAC solely against that signable string [2](#0-1) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read directly out of request headers with no cryptographic binding to the signed payload [3](#0-2) .

`Webhooks::Registry.process` validates the HMAC and then immediately trusts these unauthenticated fields to build the metadata passed to the handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [4](#0-3) .

Because Shopify signs webhooks with the app's single `api_secret_key` (shared across every shop that installs the app, not per-shop), the digest `HMAC(client_secret, raw_body)` is identical no matter which shop the payload was actually sent for. An attacker who legitimately installs the app on their own shop will receive genuinely-signed webhooks for their shop. They can replay that exact `raw_body` + `hmac` header pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, so `Registry.process` invokes the handler believing the event legitimately belongs to the victim shop.

The equality this breaks: **shop-domain claimed in `WebhookMetadata` == shop-domain the HMAC actually authenticates**. The library asserts they're equal by passing `request.shop` straight through, but the HMAC never binds `shop` at all.

### Impact Explanation
Any host application that uses `request.shop` from webhook processing to look up or mutate per-tenant state (the documented pattern, since `WebhookMetadata#shop` is the library's officially exposed tenant identifier) can be tricked into applying attacker-supplied webhook data to a different, victim merchant's session/records. This is a cross-tenant identity confusion introduced entirely within this gem's `Webhooks::Request`/`Registry` code, independent of any host-application misuse — the library documents and returns `shop` as a validated/trusted field once `HmacValidator.validate` passes, but it does not actually authenticate that field.

### Likelihood Explanation
Any user who can install the app on their own shop (the normal, unprivileged Shopify merchant flow) automatically receives correctly-HMAC'd webhook traffic they fully control the timing and content of (e.g., trigger `orders/create` by placing an order). Replaying that captured request with a modified `shop-domain` header requires no secret material and no elevated privilege — only a generic HTTP client.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified, or independently verify that the `shop-domain` header matches the shop associated with the target `Session`/webhook registration before invoking the handler, rather than trusting header values that sit outside the signed payload.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed with the app's single `client_secret`.
2. Attacker POSTs to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid because it only signs `B`), but `x-shopify-shop-domain: victim.myshopify.com` and/or a different `x-shopify-topic`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `to_signable_string` (`@raw_body`) [1](#0-0) .
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ...)` [5](#0-4) , causing the host app to process attacker-controlled data as if it originated from the victim shop.
