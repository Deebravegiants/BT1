### Title
BEEFY Consensus Forgery via Duplicate Authority Votes — No Signer Uniqueness Check Before Supermajority Threshold - ([File: evm/src/consensus/EcdsaBeefy.sol])

### Summary
`EcdsaBeefy.verifyMmrUpdateProof` (and its Rust counterpart in `modules/consensus/beefy/verifier/src/lib.rs::verify_mmr_update_proof`) counts the raw length of the submitted `votes`/`signatures` array and compares it against the 2/3+1 supermajority threshold, but never verifies that the votes come from *distinct* authorities. This mirrors the `bigclaim()` bug class: a threshold check on array length with no uniqueness enforcement on the underlying signers.

### Finding Description
`checkParticipationThreshold(sigLen, authoritySet.len)` at [1](#0-0)  only checks `sigLen >= (2*total)/3 + 1`, where `sigLen = relayProof.signedCommitment.votes.length` [2](#0-1) . The loop that follows recovers a signer address for every entry in `votes` and builds a `MerkleMultiProof.Leaf[]` array keyed by the attacker-supplied `vote.authorityIndex`: [3](#0-2) 

There is no check anywhere in this function (or in `checkParticipationThreshold`) that the `authorityIndex` values are unique, or that the recovered `authority` addresses are distinct. A single valid BEEFY signature from one honest authority can be repeated in the `votes` array under multiple (or the same) `authorityIndex` entries, artificially inflating `sigLen` past the supermajority threshold while representing only one real signer's participation.

The identical pattern exists in the Rust verifier used by the off-chain/relaychain light client: `signatures_length = mmr.signed_commitment.signatures.len()` is checked via `check_participation_threshold` [4](#0-3) , and then `authority_indices`/`authority_leaves` are built directly from the (potentially duplicated) signature list without deduplication before being passed to the merkle multi-proof verifier [5](#0-4) .

This is the exact bug class from the report: a "multi-signature" gate (`bigclaim()`'s `signers[]` length check / BEEFY's `sigLen` supermajority check) is satisfied by counting array entries instead of counting **unique** signers, so one signer can pass a threshold meant to require independent participants.

For comparison, other consensus verifiers in this same codebase correctly guard against this: `pharos` explicitly deduplicates participant keys with a `BTreeSet` before applying its stake threshold [6](#0-5) , and `tendermint` explicitly rejects validator sets with duplicate addresses [7](#0-6) . `EcdsaBeefy.sol` and the BEEFY Rust verifier have no equivalent check.

### Impact Explanation
BEEFY consensus verification is the trust root for `EvmHost`/state-machine updates bridging the Polkadot relay chain to EVM chains. If a single (or small minority of) compromised/malicious relay-chain authority can submit a valid ECDSA signature over a commitment, a relayer can replicate that one signature across enough `votes` entries (with distinct or even colliding `authorityIndex` values, depending on how `MerkleMultiProof.VerifyProof` treats duplicate indices) to pass the 2/3+1 threshold check without an actual supermajority of the authority set agreeing. This would let an attacker forge a fraudulent MMR root / parachain header update, leading to unsound state commitments being accepted by `EvmHost`, which downstream can be used to forge cross-chain message delivery, mint unbacked tokens via the token bridge, or otherwise falsify finalized state — a critical unsound state commitment / forged-message-delivery scenario per the Hyperbridge threat model.

### Likelihood Explanation
Exploitation requires only a normal, unprivileged relayer submitting a consensus proof through the public `verify` entrypoint of `EcdsaBeefy` — no special privileges required. The only prerequisite is obtaining one valid signature over the commitment from any authority in the current/next authority set (which is a much lower bar than an actual 2/3+1 supermajority collusion). Whether the exploit fully succeeds ultimately depends on whether `MerkleMultiProof.VerifyProof`/`rs_merkle`'s multi-proof verification would accept an `authorities`/`authority_leaves` array containing duplicate indices/leaves and still return `valid == true` for a proof only real for unique indices — this needs to be confirmed against the actual `solidity-merkle-trees` and `rs_merkle` implementations, but the missing uniqueness check at the `EcdsaBeefy`/BEEFY-verifier layer is a clear root-cause gap independent of that library detail.

### Recommendation
Before or while building `authorities`/`authority_leaves`, explicitly enforce that all `vote.authorityIndex` values (and/or all recovered `authority` addresses) in the votes array are unique — e.g., using a bitmap/set keyed by `authorityIndex`, rejecting the proof if a duplicate is found — in both `EcdsaBeefy.verifyMmrUpdateProof` and `beefy::verifier::verify_mmr_update_proof`, mirroring the deduplication already done in `pharos`'s `verify_validator_membership`.

### Proof of Concept
1. Obtain one authority's valid ECDSA signature `sig` over `commitmentHash` (e.g. from a leaked/compromised single validator key, or a validator that signs a proof intended for a different, legitimate purpose).
2. Construct `relayProof.signedCommitment.votes` as an array of length `>= (2*total)/3 + 1`, where every entry reuses `sig` but is assigned an `authorityIndex` value that is a legitimate index in `authoritySet` (this may need distinct indices if `MerkleMultiProof.VerifyProof` requires unique k-indices, but each `authorities[i]` leaf hash is simply `keccak256(authority)` from the *same* recovered signer, so if the multi-proof library does not tie a specific index to a specific pre-known leaf-address mapping beyond the merkle path, distinct indices referencing the *same* signer are not prevented by this contract).
3. Call `EcdsaBeefy.verify(previousState, proof)`. `checkParticipationThreshold` passes because `sigLen` meets the array-length threshold, despite only one authority actually signing.
4. If the merkle multi-proof step also passes (library-dependent — needs confirmation), a fraudulent MMR/parachain state update is accepted as consensus-verified.

fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}

/// Rejects a validator set that reuses the same address twice. Each address is a
/// hash of its public key, so a duplicate signals a set that was not built honestly.
fn ensure_unique_addresses(
	validators: &[cometbft::validator::Info],
) -> Result<(), VerificationError> {
	let unique = validators.iter().map(|v| v.address).collect::<BTreeSet<_>>();
	if unique.len() != validators.len() {
		return Err(VerificationError::ValidatorSetError(
			"duplicate validator address in set".to_string(),
		));
	}
	Ok(())
}
