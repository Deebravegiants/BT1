### Title
Relayer fees accrued to a contract address can never be withdrawn — `withdraw()` and the beneficiary redirect require an EOA-style signature - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
`pallet-ismp-relayer` credits delivery fees to whatever address is proven as the delivering relayer in `RequestReceipts[commitment]` on the destination chain, which for EVM chains is the raw `msg.sender` that called `HandlerV2.handlePostRequests`/`handleGetResponses` [1](#0-0) . The only way to move those accumulated fees out of `Fees::<T>` is `Pallet::withdraw`, which unconditionally requires a `Signature` (EVM secp256k1 / sr25519 / ed25519) that ECDSA/Schnorr-recovers to exactly the credited address [2](#0-1) . A relayer that delivers messages from a smart-contract address (a common operational pattern — automation bots, gas-sponsoring relays, multisigs) has no private key and can never produce such a signature, so its accrued fees become permanently unclaimable. The only alternate path, the beneficiary redirect baked into `accumulate()`, has the identical restriction: it still requires a signature that recovers to `delivery_address` before fees can be routed to any other beneficiary [3](#0-2) .

### Finding Description
`Pallet::withdraw` derives the claimant `address` strictly from the supplied `Signature` variant and then checks the signature actually recovers to that same address before reading `Fees::<T>::get(dest_chain, address)`:
```rust
let address = match &withdrawal_data.signature {
    Signature::Evm { address, .. } => address.clone(),
    Signature::Sr25519 { public_key, .. } => public_key.clone(),
    Signature::Ed25519 { public_key, .. } => public_key.clone(),
};
...
Signature::Evm { address, .. } => {
    let eth_address = withdrawal_data.signature.verify(&msg, None)...;
    if &eth_address != address { Err(Error::<T>::InvalidPublicKey)? }
},
``` [4](#0-3) 

There is no origin/permission check that gates who may submit this call (`withdraw` extrinsic is `ensure_none`, i.e. unsigned, spam-protected only via `validate_unsigned`) [5](#0-4)  — meaning anyone can submit the extrinsic, but only if they can produce a valid raw ECDSA/sr25519/ed25519 signature over the withdrawal message from the *exact* keypair that corresponds to the address credited with fees.

The credited address is not chosen by the relayer at claim time; it is whatever `decode_receipt_relayer` extracts from the delivery receipt on the destination chain — for EVM, `Address::decode` of the raw receipt bytes, which is populated from the actual `msg.sender` (or `_msgSender()`) that delivered the request through `HandlerV2` [6](#0-5) , [1](#0-0) . Nothing prevents a smart-contract wallet, relayer-bot contract, batching/automation contract, or multisig from calling `HandlerV2.handlePostRequests` directly as `msg.sender` — this is in fact a normal way to run relayer infrastructure with gas sponsorship, batching, or access-control logic. Once fees accrue to that contract address in `Fees::<T>`, both exits are blocked:
- `withdraw()` demands a signature recoverable to that address — impossible for a contract, which has no private key.
- The `beneficiary_details` redirect inside `accumulate()` requires the same signature-over-`delivery_address` check before it will route fees to a different beneficiary [3](#0-2) .

This mirrors the reported bug class exactly: a token/fee balance is attributed to an address by a mechanism the address's owner does not control (proof of delivery, not a deliberate opt-in), and the only claim path is restricted to a form of self-authorization (`msg.sender`/signature) that a contract account structurally cannot satisfy, and there is no third-party or delegated claim path.

### Impact Explanation
Any relayer operator that delivers ISMP messages through a smart-contract address (a legitimate, common operational choice for automation, gas abstraction, or access control) permanently loses every fee earned through that contract address. The funds remain forever locked in the `Fees::<T>` storage map and in the treasury/host-manager escrow backing them on the destination chain — they can never be accumulated to a different, signable address and never withdrawn, constituting a permanent freezing of funds for the affected relayer.

### Likelihood Explanation
Medium-to-High: nothing in the protocol prevents or warns against delivering as a contract; `EvmHost.dispatchIncoming` and `HandlerV2` record whatever `_msgSender()` submitted the transaction with no EOA-only restriction [7](#0-6) . Relaying via a smart contract wallet or bot contract is a realistic and even encouraged pattern (batching multiple deliveries, gas sponsorship, permissioned relay sets), so this is likely to be hit in practice rather than a purely theoretical edge case.

### Recommendation
Support contract-owned relayer addresses in the withdrawal/redirect paths, e.g. by allowing an ERC-1271-style contract signature verification for EVM delivery addresses, or by allowing the currently-recorded delivery address itself (via a proof that it is a contract, or via a permissionless call gated only by `msg.sender == delivery_address` when the withdrawal is submitted directly through the EVM host/manager) to redirect/claim its own accrued fees without requiring an ECDSA private-key signature.

### Proof of Concept
1. Operate a relayer using a smart-contract wallet `C` (e.g., a Gnosis Safe or a custom automation contract) as the caller of `HandlerV2.handlePostRequests` on an EVM destination chain, so `EvmHost.dispatchIncoming` records `C` as the delivering relayer in `RequestReceipts[commitment]`.
2. Submit a `WithdrawalProof` to `accumulate_fees` proving delivery by `C`; `decode_receipt_relayer` extracts `C`'s address from the receipt and `Fees::<T>[dest_chain][C]` is credited with the fee [8](#0-7) .
3. Attempt to call `withdraw` (or the `beneficiary_details` redirect in a later `accumulate` call) with any `Signature` variant. Because `C` is a contract with no private key, no valid ECDSA/sr25519/ed25519 signature can ever recover to `C`'s address, so `Error::<T>::InvalidPublicKey`/`InvalidSignature` is unavoidable for every attempt [9](#0-8) .
4. `Fees::<T>[dest_chain][C]` remains non-zero indefinitely — the fee is permanently unclaimable.

			Signature::Evm { address, .. } => address.clone(),
			Signature::Sr25519 { public_key, .. } => public_key.clone(),
			Signature::Ed25519 { public_key, .. } => public_key.clone(),
		};

		let nonce = Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain);
		let msg = message(nonce, withdrawal_data.dest_chain, withdrawal_data.beneficiary.clone());

		match &withdrawal_data.signature {
			Signature::Evm { address, .. } => {
				let eth_address = withdrawal_data
					.signature
					.verify(&msg, None)

	pub fn decode_receipt_relayer(state_id: StateMachine, raw: &[u8]) -> Result<Vec<u8>, Error<T>> {
		match state_id {
			s if crate::is_pharos(&s) =>
				if raw.len() == 32 {
					Ok(Address::from_slice(&raw[12..]).0.to_vec())
				} else {
					Err(Error::<T>::ProofValidationError)
				},

				use alloy_rlp::Decodable;

					.map_err(|_| Error::<T>::ProofValidationError)?
					.0
					.to_vec())
			},
