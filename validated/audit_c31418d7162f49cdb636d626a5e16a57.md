### Title
Uncounted native-ETH drain via `EmporiumOperation.value` bypassing `erc20TokenAddresses` balance accounting - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` measures the balance-conservation invariant only over the tokens the caller lists in `circomData.erc20TokenAddresses`, via `getBalancesForArray` [1](#0-0) . Because `circomData.erc20TokenAddresses` is attacker-supplied input to `transact`, an attacker can simply omit the native-ETH placeholder `address(0)` from that array while still crafting an `EmporiumOperation` with a nonzero `value` field that gets sent via a raw stateless call [2](#0-1) .

### Finding Description
**Equality claimed broken:** VALUE_CONSERVATION — for every unit of value that leaves the Emporium proxy's balance during `runAction`, there must be a corresponding negative entry accounted for in `balanceChange`/`deltaAmountChanges` for that same token (here, native ETH, `address(0)`).

**Code path:**
1. `balancesBefore = getBalancesForArray(circomData.erc20TokenAddresses)` — balances are only fetched for the tokens in the caller-supplied array [1](#0-0) . `getERC20OrETHBalance` special-cases `address(0)` to read `address(this).balance` [3](#0-2) , but this is only invoked if `address(0)` is actually present in the array.
2. The op loop executes `op.endpoint.call{value: op.value}(op.callData)` in the "Case 2: Stateless Interaction" branch for `invokeWallet == false` [2](#0-1) . This directly spends the Emporium proxy's own ETH balance (which can hold ETH accumulated from other users' prior deposits via `receive() external payable {}` at line 369) toward `op.endpoint`, fully attacker-controlled since `stack` is decoded from `circomData.externalActionData.externalActionMetadata`, itself attacker-supplied calldata.
3. After the loop, `balancesAfter = getBalancesForArray(circomData.erc20TokenAddresses)` is computed over the *same* attacker-chosen array — if `address(0)` was excluded, the ETH drain is invisible to both `balancesBefore` and `balancesAfter`.
4. The reconciliation loop at lines 132–151 only iterates `i < circomData.erc20TokenAddresses.length`, so any token/ETH not listed is never checked against `deltaAmountChanges` or subjected to the `balanceChange < 0` revert guard.

**Root cause:** The balance-conservation check trusts an attacker-controlled list of tokens (`circomData.erc20TokenAddresses`) to be the complete set of assets touched by the operation, but the `op.value` field of `EmporiumOperation` is not cross-checked against that list — the circuit-side `deltaAmountChanges`/`amountChanges` and the on-chain `erc20TokenAddresses` array can simply omit ETH while `op.value` still moves it.

**Why existing guards don't catch this:**
- `verifyWallet` only validates the EIP-712 signature over `stack.ops` if `stack.signerAddress != address(0)`; but the attacker can set `signerAddress == address(0)` to skip the whole signature-check branch and short-circuit at line 314-316, meaning **no signer authorization is required at all** for the stateless (`invokeWallet == false`) `.call{value: op.value}` path. This means any attacker calling through `transact` can define `ops` with `op.value` freely — there's no signature binding required when `signerAddress == address(0)`.
- `onlyAllowedRecipient` only checks that `msg.sender` is `Hinkal` (or another allowed relay contract), not that the *content* of `circomData`/`stack` is honest — this doesn't protect against a malicious `erc20TokenAddresses` array.
- The `balanceChange < 0` revert (line 142-144) is a real check, but it is a no-op for any token absent from `erc20TokenAddresses` — ETH is simply never examined if omitted.

**Attacker's exact call:** Through `Hinkal.transact`, targeting Emporium as the external action, with `circomData.erc20TokenAddresses` = `[someOtherERC20]` (excluding `address(0)`), and `externalActionMetadata` decoding to an `EmporiumStack` with `signerAddress = address(0)` and `ops = [{endpoint: attackerEOA, invokeWallet: false, value: V, callData: ""}]`. On execution, `attackerEOA.call{value: V}("")` drains `V` wei from Emporium's ETH balance to the attacker, while none of `balancesBefore`, `balancesAfter`, or `deltaAmountChanges` register any ETH movement.

### Impact Explanation
This is direct theft of shielded/pooled ETH belonging to other users that has accumulated in the `EmporiumUpgradeable` proxy's balance (e.g., from ETH-denominated deposits or leftover balances of prior operations, given the unconditional `receive() external payable {}`). The stolen value is fully uncounted by the value-conservation equation, meeting the Critical bar ("direct theft of shielded or in-flight user funds ... a leaf spent twice or stranded, or a field acted on that the proof never constrained"). It is repeatable for as long as the Emporium proxy holds any ETH balance, and the attacker's cost is only gas plus proof generation for a self-authored `transact` call.

### Likelihood Explanation
Preconditions:
- The Emporium proxy must hold a nonzero ETH balance (plausible whenever any user routes ETH through Emporium, since deposits/leftover proceeds accumulate there via `receive()`).
- Attacker needs no special role — only the ability to call `transact` as an ordinary user (satisfying `onlyAllowedRecipient` simply requires being routed via the registered Hinkal→Emporium path), and to craft their own `CircomData`/`EmporiumStack`/proof for their own UTXOs.
- No signature is required for the vulnerable path since `signerAddress == address(0)` bypasses `verifyWallet`'s EIP-712 check entirely.

This is easily reachable and repeatable — feasibility is high, cost is low (gas + one legitimate proof for the attacker's own inputs).

### Recommendation
Enforce that any `EmporiumOperation.value` moved via the stateless `.call{value: ...}` path is only sourced from funds the caller is entitled to (e.g., require `address(0)` to always be present in `circomData.erc20TokenAddresses` whenever any `op.value > 0` across `stack.ops`, or sum all `op.value` fields and require that sum be reflected as a mandatory negative `deltaAmountChanges` entry against `address(0)` before permitting any nonzero `op.value`). Alternatively, disallow nonzero `op.value` entirely in the stateless call branch, or require the reconciliation loop to always include `address(0)` in the balance-diff check regardless of what the caller supplies in `erc20TokenAddresses`.

### Proof of Concept
Foundry test plan:
1. Deploy `EmporiumUpgradeable` behind a proxy, initialize with a `Hinkal`-style allowed recipient and a mock `IHinkalHelper`.
2. Fund the Emporium proxy with ETH by simulating a benign prior deposit/operation that leaves ETH on the contract (or send ETH directly via `receive()` to simulate accumulated balance from another user).
3. As `attacker`, construct `CircomData` with `erc20TokenAddresses = [someUnrelatedERC20]` (excluding `address(0)`), and `externalActionData.externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)`, `ops = [{endpoint: attackerEOA, invokeWallet: false, value: V, callData: ""}]`, `deltaAmountChanges` sized to `erc20TokenAddresses.length` with all zero/no ETH entry.
4. Call `runAction` (via the allowed-recipient path) and assert:
   - `attackerEOA.balance` increases by `V`.
   - `EmporiumUpgradeable`'s ETH balance decreases by `V`.
   - The returned `utxoSet`/`deltaAmountChanges` sum to zero net change for ETH (no negative entry corresponding to `V`), demonstrating `tokens leaving != counted amount`.
5. Show the transaction does not revert (no `BalanceChangeShouldBePositive` triggered) because ETH was never part of the checked array.
