### Title
Accrued debt-value overflow permanently freezes a high-balance market - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
Interest accrual multiplies the market’s total scaled debt by the newly computed borrow index before enforcing the index ceiling. Once `borrowed * new_borrow_index` exceeds `i128::MAX`, `Ray::mul` traps with `MathOverflow` instead of first clamping the index or bounding the market value. Because every pool mutation and the permissionless `update_indexes` path synchronizes the market before doing anything else, crossing this boundary permanently prevents repayment, withdrawal, liquidation, bad-debt cleanup, flash loans, and recapitalization for that market.

### Finding Description
`update_indexes` is callable by any authorized user and forwards the requested `HubAssetKey` list to the pool [1](#0-0) . Pool accrual loads each market and invokes `global_sync` [2](#0-1) , while all ordinary pool mutations use the same synchronization wrapper before acting [3](#0-2) .

During each accrual chunk, `calculate_supplier_rewards` computes both the old and new total debt values using `borrowed.mul(index)` [4](#0-3) . `scaled_to_original` has the same unchecked logical shape: a scaled amount is multiplied by an index and is expected to fit the fixed-point domain [5](#0-4) . Although `update_borrow_index` caps the index itself at `1e36`, the resulting scaled debt-value multiplication is performed afterward without a corresponding market-value cap [6](#0-5) ; the configured index ceiling is `1e36` raw RAY [7](#0-6) .

The repository has a direct regression demonstrating this boundary. A billion-token, 18-decimal market supplied at 98% utilization eventually causes `update_indexes` to fail with `MathOverflow`; the same overflow then makes both `withdraw` and `repay` fail [8](#0-7) .

### Impact Explanation
This is a permanent freeze of user funds at market scope. Once the state is crossed, no interest-bearing operation can complete because the accrual runs before the operation and panics on the overflowing debt valuation. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot retire debt, and recapitalization cannot restore the market. The regression explicitly confirms that withdrawal and repayment hit the same `MathOverflow` after the accrual cliff [9](#0-8) .

### Likelihood Explanation
No privileged call is required to trigger the panic once market size and debt growth are sufficient. A whale can create the condition through ordinary `supply`, `borrow`, and later `update_indexes` calls, provided the configured caps and admitted market liquidity permit the large position. The repository’s regression uses a billion-token market and 98% utilization; it reports that the value ceiling is reached before the nominal borrow-index ceiling engages [8](#0-7) .

The required balance is extreme, so likelihood is bounded by listed-token supply, configured caps, collateral availability, and sustained high utilization. Nevertheless, the vulnerable path is deterministic: ordinary users cannot create arbitrary parameters, but they can create the arithmetic state under a permissive configured cap, and any subsequent unprivileged `update_indexes` call permanently activates the freeze.

### Recommendation
Enforce a representable market-value bound before calculating accrued debt and supplier rewards. In particular:

- bound `borrowed` and `supplied` scaled totals against the maximum index before admitting new exposure;
- compute `new_borrow_index` first, clamp it, and calculate the resulting debt using checked or saturating arithmetic;
- return a recoverable market-specific error or clamp accrual at the largest index for which `borrowed * index` remains representable;
- apply the same rule to simulated accrual so views cannot diverge from state-changing calls;
- add regression coverage for values just below, exactly at, and above the representable debt-value boundary.

### Proof of Concept
The existing regression provides the concrete sequence:

```rust
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);
```

It then advances time and repeatedly calls `update_indexes` until the call fails with `MathOverflow`; afterward, both withdrawal and repayment also fail with `MathOverflow` [10](#0-9) .

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
