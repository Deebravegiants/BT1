### Title
Webhook shop-domain and topic headers are trusted but not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers and hands them directly to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers with no cryptographic binding at all [2](#0-1) . `Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which computes the signature over `to_signable_string` (i.e. the body only) and compares it against the `hmac-sha256` header [3](#0-2) [4](#0-3) . After that check passes, the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` are forwarded verbatim to the app's `WebhookMetadata` and handler [5](#0-4) .

Critically, the webhook HMAC secret is the app's single `api_secret_key` (`Context.api_secret_key`), which is shared across *every* shop that has installed the app — it is not a per-shop secret [6](#0-5) . This breaks the intended binding: `shop == the tenant whose webhook body produced this signature`. In reality the verified equality is only `hmac == HMAC(api_secret_key, raw_body)`; the `shop` header is never included in that computation.

Consequently, any unprivileged party who controls a shop with the app installed (an "unprivileged internet user" in the sense of the analog rules, since installing a free/dev app requires no special privilege) can trigger a real webhook for their own store, capture the resulting `(raw_body, hmac)` pair (which is valid because it's genuinely signed with the shared app secret), and replay that exact body to the app's webhook endpoint while substituting the `shop-domain` header (and/or `topic`/`webhook_id`) for a victim shop's domain. Since `to_signable_string` never covers those headers, `HmacValidator.validate` still returns true, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain [7](#0-6) .

Because apps are documented to use `data.shop` as the tenant key for attributing webhook data to a merchant (e.g. enqueuing background jobs keyed by `shop_domain`) [8](#0-7) [9](#0-8) , this gem's own validated boundary lets an attacker forge webhook payload attribution across tenants, i.e. `data.shop` for the accepted, HMAC-"verified" request can be an arbitrary victim domain unrelated to the actual signer of the payload.

### Impact Explanation
This is a cross-tenant data confusion / cross-tenant access vulnerability directly attributable to this gem's own webhook verification logic: it validates only the body's authenticity but not the identity of the shop the request claims to originate from, even though it exposes and the docs recommend using `shop` as the tenant identifier. An attacker who is a legitimate (even free-tier) merchant of the app can make the app's webhook handler process/store attacker-controlled webhook bodies under a victim merchant's shop domain, which can pollute or manipulate per-tenant state, trigger unintended actions against a victim's tenant record, or leak information depending on how the host app uses `data.shop`.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on any shop (something any developer/merchant can do without special privilege), (2) triggering one real webhook event to obtain a validly-signed `(body, hmac)` pair, and (3) resending the HTTP request to the app's webhook endpoint with a modified `shop-domain` (and optionally `topic`/`webhook_id`) header. No access token, `client_secret`, or victim credentials are needed — only the shared app-level `api_secret_key`-derived signature, which is not scoped per shop. This is straightforward to reproduce and does not depend on the host application ignoring documented behavior; it is inherent to how `Utils::HmacValidator` and `Webhooks::Request` are implemented in this gem.

### Recommendation
Bind the identity fields into the signed payload used for verification rather than trusting raw headers. At minimum, `Webhooks::Request#to_signable_string` (or `HmacValidator.validate`) should incorporate `shop`, `topic`, and `webhook_id` alongside the raw body so that the HMAC check fails if any of these headers are altered after Shopify signs the request. Alternatively/additionally, cross-check the incoming `shop` header against known shop sessions/subscriptions the app itself registered for that specific webhook_id before invoking the handler, rather than passing the header value through unauthenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a real event (e.g. updates a product) that the app is registered to receive as a webhook.
2. Shopify sends the app: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: products/update`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`, plus the JSON `raw_body`.
3. Attacker replays this exact request to the app's webhook endpoint but changes only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com` (and/or `x-shopify-webhook-id`/`x-shopify-topic`), leaving `raw_body` and `x-shopify-hmac-sha256` untouched.
4. `Utils::HmacValidator.validate` recomputes the HMAC solely from `raw_body` [1](#0-0)  and it still matches, so `Registry.process` proceeds and invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [10](#0-9) , even though the payload's content was never generated for or by that victim shop.
