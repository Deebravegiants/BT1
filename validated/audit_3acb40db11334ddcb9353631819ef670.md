### Title
Fee-quote ratio guard permits solver to overcharge withdrawal fee by up to 49.9% - ([File: packages/intents-sdk/src/lib/estimate-fee.ts])

### Summary
In the exact-in fallback branch of `getFeeQuote()`, the only sanity check on the solver's returned `amount_out` is an upper bound of `1500n` (1.5x) relative to the requested `feeAmount`, with a lower bound of `feeAmount` itself. Any `amount_out` strictly between `feeAmount` and `1.5 * feeAmount` is silently accepted and becomes the fee actually charged to the user, even though the comment states the expected buffer is only ~1.2x.

### Finding Description
`getFeeQuote()` first attempts an exact-out quote (`exact_amount_out: feeAmount`). If the solver relay throws a `QuoteError` (e.g., no route can guarantee that exact output), the code falls back to an exact-in quote, sending `exact_amount_in` computed as roughly `feeAmount * 1.2` (scaled by asset prices/decimals) [1](#0-0) .

The solver then replies with its own `amount_out` for that `exact_amount_in`. The code validates this response only with two loose bounds:
```
const actualRatio = (BigInt(quote.amount_out) * RATIO_SCALE) / feeAmount;
if (actualRatio > 1500n) { ... throw err; }
if (BigInt(quote.amount_out) < feeAmount) { ... throw err; }
return quote;
``` [2](#0-1) 

The equality that should hold — "the fee actually charged ≈ the true cost `feeAmount` of the bridge/relayer fee, plus a small, bounded buffer" — is violated because the accepted range is `[feeAmount, 1.5 * feeAmount)`, not tightly bound around the intended ~1.2x buffer mentioned in the comment on line 44 ("ExactIn fallback with 1.2x multiplier") and line 139 ("should be around 1.2x due to our buffer"). A solver answering the exact-in quote can legally return `amount_out = 1499n` for `feeAmount = 1000n` (a 49.9% markup) and the function returns this `quote` object unmodified as the accepted fee quote — no further check compares the actual multiplier against the intended 1.2x target or rejects amounts between 1.2x and 1.5x.

This `quote.amount_out` is subsequently used as the material fee amount deducted from the user's withdrawal (flows into `FeeEstimation.amount`, checked only for being *less than* the withdrawal amount via `FeeExceedsAmountError` [3](#0-2) , not for being reasonably close to the true fee cost). None of `FeeExceedsAmountError`, `getUnderlyingFee`, or the intents contract's signature/nonce checks constrain the *magnitude* of the fee itself — they only ensure the fee doesn't exceed the withdrawal amount and that underlying fee objects are populated.

### Impact Explanation
The fee amount accepted from a permissionless solver can be inflated by up to 49.9% beyond the actual required `feeAmount` without triggering any rejection, resulting in the user's withdrawal intent being constructed with an inflated fee that is debited from their balance. This matches the "fee overcharge or a solver overpaid" High-severity category. It is repeatable on every withdrawal that triggers the exact-in fallback path (i.e., whenever the solver relay cannot satisfy an exact-out quote), giving a colluding/malicious solver a systematic way to extract excess value across many withdrawals.

### Likelihood Explanation
Preconditions: the exact-out quote request must fail with a `QuoteError` (a realistic, solver-controlled or route-dependent condition — not attacker-privileged, since any solver can simply refuse/fail exact-out quoting to force the exact-in fallback), and the same or a colluding solver must be the one answering the exact-in quote. The attacker (a permissionless solver) controls the `amount_out` it returns for a given `exact_amount_in`, so achieving a value inside `[1.2x, 1.5x)` of `feeAmount` requires no special access — it is a normal quote response. This is entirely feasible and repeatable at no cost to the solver beyond normal quote-serving.

### Recommendation
Tighten the fallback ratio check to reject any `amount_out` meaningfully above the intended buffer (e.g., 1.2x plus a small fixed tolerance, such as 1.25x–1.3x) instead of 1.5x, and/or re-derive the maximum acceptable fee independently from `feePriceScaled`/`tokenPriceScaled` computed on line 105–108 rather than trusting the solver's `amount_out` up to a wide multiplier.

### Proof of Concept
```ts
// vitest, mocking only solverRelay.getQuote and tokens()
it("accepts a solver quote up to 1.499x the true feeAmount in exact-in fallback", async () => {
  const feeAmount = 1000n;

  vi.spyOn(solverRelay, "getQuote")
    .mockRejectedValueOnce(new QuoteError(/* ... */)) // force exact-out failure
    .mockResolvedValueOnce({ amount_out: "1499", /* ...other quote fields */ });

  vi.spyOn(tokensModule, "tokens").mockResolvedValue({
    items: [
      { defuse_asset_id: feeAssetId, price: 1, decimals: 6 },
      { defuse_asset_id: tokenAssetId, price: 1, decimals: 6 },
    ],
  });

  const quote = await getFeeQuote({
    feeAmount,
    feeAssetId,
    tokenAssetId,
    envConfig,
  });

  // Broken equality: accepted quote.amount_out should equal feeAmount (the true required fee),
  // but the SDK accepts a value 49.9% above it without rejection.
  expect(BigInt(quote.amount_out)).toBe(1499n); // accepted, not rejected
  expect(BigInt(quote.amount_out)).not.toBe(feeAmount); // divergence from true fee
});
```
