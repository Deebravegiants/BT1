## Title
Webhook HMAC signature does not bind the `shop` (or `topic`/`webhook-id`) header, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` authenticates the *payload bytes* but never binds the `shop` header (or `topic`/`webhook-id`) that the same request object exposes to the app's handler. Because the identity of the tenant (`shop`) is read straight from an unauthenticated header while only the body is HMAC‑checked, an attacker who can obtain one genuinely signed webhook (e.g., by triggering an event on their own, legitimately-installed shop) can replay that exact `raw_body`/`hmac` pair while substituting the `x-shopify-shop-domain` (and/or `topic`/`webhook-id`) header for a victim shop. `Registry.process` accepts it because it only re-validates the body signature, then hands the forged `shop` value straight to the app's handler.

### Finding Description
`Request#hmac`/`to_signable_string` compute/verify signature material from `@raw_body` alone: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read from headers that are never mixed into `to_signable_string`, i.e. never covered by the HMAC: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against a signature computed from `to_signable_string`, i.e. body-only for webhooks: [3](#0-2) 

`Registry.process` uses exactly this check to gate processing, then forwards the unauthenticated `request.shop` (and `topic`, `webhook_id`, `api_version`) directly into `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The equality the library implicitly promises to the host application is:

`shop that produced/authorized this webhook == request.shop consumed by the handler`

But the HMAC only proves:

`hmac == HMAC_SHA256(client_secret, raw_body)`

with no cryptographic tie between `raw_body` and the claimed `shop`/`topic`/`webhook_id`. Any party capable of obtaining one validly-signed `(raw_body, hmac)` pair (trivially available to any merchant who installs the app, since Shopify sends real webhooks with valid signatures to that merchant's own events) can pair that same body/signature with a forged `shop-domain` header pointing at a different, victim tenant. `Registry.process` will accept it as authentic and pass the wrong `shop` on to the handler, breaking the tenant binding for the app relying on this gem's webhook verification.

### Impact Explanation
This crosses a tenant boundary: an attacker with access to only their own (unprivileged) shop installation can cause the library to hand the application code data tagged with an arbitrary victim shop's identity while carrying a validly-verified signature. Applications that trust `WebhookMetadata#shop` (as the library's own tests demonstrate is the expected usage pattern) after `Registry.process` succeeds may update, delete, or act on data keyed by that spoofed shop, or create/refresh sessions under the wrong tenant — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app that: (1) has more than one shop able to trigger the same webhook topic/body byte-for-byte or with content the attacker controls (many webhook topics carry attacker-influenced content, e.g. `app/uninstalled`, `carts/*`, order edits with attacker-supplied fields on the attacker's own store), and (2) exposes its webhook endpoint publicly (required by Shopify's webhook delivery model). No access token, `client_secret`, or privileged account is needed — only the ability to install the app on one's own store and intercept/replay one's own legitimately delivered webhook with a modified `shop-domain` header.

### Recommendation
- Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or independently validate that the claimed `shop` header actually corresponds to a shop with an active installation/session known to the app before trusting `WebhookMetadata#shop`.
- Alternatively, have `HmacValidator`/`Request` treat the header set as part of `to_signable_string`, or expose an API that lets host apps assert the expected shop out-of-band (e.g., compare against the URL path parameter used to route the webhook) rather than trusting the header value alone.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`), causing Shopify to POST a validly HMAC-signed webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid>`, body `B`.
2. Attacker captures `(B, valid_hmac)` and replays it directly to the app's public webhook endpoint, but rewrites the header to `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully; `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(secret, B) == valid_hmac` — passes. [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and body `B`, even though `B` and the signature never originated from `victim-shop`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
