### Title
Webhook HMAC signature does not bind the `shop-domain` header, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shopify-shop-domain` (and `topic`/`webhook-id`) headers from the HMAC-covered bytes. `Utils::HmacValidator.validate` therefore only proves that *some* request body was signed by the app's `client_secret` — it proves nothing about which shop the body belongs to. `Webhooks::Registry.process` nonetheless forwards the unauthenticated `request.shop` value straight to the handler as the tenant identifier.

### Finding Description
`Request#hmac` is read from the `hmac-sha256` header and `Request#to_signable_string` returns `@raw_body` only: [1](#0-0) [2](#0-1) 

`Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the supplied HMAC: [3](#0-2) 

Because `to_signable_string` only returns the body, the `shop` field is never part of the signed bytes. `Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

This is the exact bug class described in the analog prompt — "bytes verified" (the body) diverge from "the field acted on" (the `shop` header used as the tenant key by the handler). It is also directly analogous to the smart-contract report's theme of an identity/count binding enforced in one code path (`AuthQuery#to_signable_string`, which does include `shop` in its signed string: [5](#0-4) ) but *not* enforced consistently in the sibling `VerifiableQuery` implementation used for webhooks.

Since every shop that installs the same app shares one `client_secret`, any merchant (an "unprivileged internet user" relative to other tenants of the same app) who legitimately receives one authentic `(body, hmac)` pair from Shopify for their own shop can replay that exact body/HMAC to the app's webhook endpoint while substituting a different `shopify-shop-domain` header value belonging to a victim shop. `HmacValidator.validate` still succeeds (the secret and body are unchanged), and `Registry.process` passes the forged `shop` value straight to the app's `WebhookHandler#handle`, causing the application to process/attribute the payload as belonging to the victim tenant — a cross-tenant confusion inside this gem's own trust boundary (`shop_verified == shop_acted_on` is broken).

### Impact Explanation
This breaks the shop/tenant identity binding without needing the `client_secret` or any credential of the victim shop, matching the "cross-tenant access" bucket (Critical) — a request authenticated as belonging to shop A is processed as if it came from shop B.

### Likelihood Explanation
Requires the attacker to already hold one valid Shopify-issued webhook `(body, hmac)` pair, which any merchant with a legitimate install of the target app can obtain from their own webhook deliveries (no secret leakage or privileged access needed) and then replay with a modified header against the app's shared webhook endpoint — this is a realistic replay scenario for a multi-tenant Shopify app.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the string that is HMAC-verified in `Request#to_signable_string`, or otherwise cryptographically bind the shop identity to the signed payload, so `HmacValidator.validate` cannot succeed for a `(body, hmac)` pair replayed under a different shop header.

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` and `shop-b.myshopify.com`, both sharing the same `client_secret`.
2. Shopify sends a legitimate webhook to the app for `shop-a.myshopify.com`: headers include `shopify-hmac-sha256: <valid HMAC of body B>` and `shopify-shop-domain: shop-a.myshopify.com`.
3. Attacker (a user with access to shop-a's webhook logs/proxy) captures `body B` and its `hmac`.
4. Attacker POSTs the same `body B` and `hmac` to the app's webhook endpoint but sets `shopify-shop-domain: shop-b.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `body B` — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
6. The handler receives `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)` and processes shop-a's data as shop-b's, per `lib/shopify_api/webhooks/registry.rb:188-200`.

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
