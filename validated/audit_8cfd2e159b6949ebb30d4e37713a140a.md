### Title
Webhook `shop-domain`/`topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed unchanged to the webhook handler. Any party that can obtain one genuine `(body, hmac)` pair signed with the app's shared `client_secret` (e.g., by installing the app on their own store) can replay that body/HMAC pair while forging the `shop-domain` and `topic` headers, causing the app to process attacker-controlled webhook content under a victim shop's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` only checks that `to_signable_string` (i.e., the raw body) was signed with the app's `api_secret_key`; it never touches `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC (body only) and then trusts the header-derived `shop`/`topic`/`webhook_id`/`api_version` to build the metadata handed to the app's webhook handler: [4](#0-3) 

The identity binding that should hold is:
`shop_that_receives_the_side_effect == shop_that_the_webhook_body/HMAC_was_actually_issued_for`

Because the HMAC only proves "this body was signed with our app's shared secret," not "this body was signed for shop X, topic Y," the equality above does not hold. `api_secret_key` is shared by every shop that installs the app, so any merchant who installs the app (an ordinary, unprivileged action) receives their own genuine `(body, hmac)` pairs from Shopify. That merchant can capture such a pair and resubmit it to the app's webhook endpoint with a modified `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header pointing at a different, victim shop. `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` dispatches the handler with `WebhookMetadata.shop` set to the forged victim shop.

### Impact Explanation
This breaks the tenant boundary the whole webhook mechanism is supposed to enforce: the app's business logic (order sync, inventory decrement, `app/uninstalled` cleanup, GDPR `shop/redact`, `customers/data_request`, etc.) keys off `WebhookMetadata#shop` believing it to be authenticated, when it is actually attacker-controlled. An attacker-merchant can, for example, replay their own `products/create` or `orders/create` payload tagged with a victim's shop domain to corrupt or inject data attributed to that victim, or replay a captured payload against a forged `app/uninstalled`/`shop/redact` topic to trigger destructive cleanup logic for a shop they don't own. This is cross-tenant access/data corruption achieved without any access token, credential theft, or privileged position — only requiring the attacker to be a normal app installer, which satisfies the "unprivileged internet user" bar.

### Likelihood Explanation
Likelihood is high: obtaining a genuine `(body, hmac)` pair only requires installing the target app on an attacker-controlled shop (a normal, unauthenticated-relative-to-victim action any merchant can take), and the header spoofing itself requires no cryptography — the `shop-domain`/`topic` headers are plain HTTP headers with zero validation against the signed payload. The only barrier is guessing/knowing a valid target shop domain, which is often public information (`*.myshopify.com` storefront URLs are frequently public).

### Recommendation
Include the identity-defining fields in the signed material, or otherwise cryptographically bind them:
- Extend `to_signable_string` (or add a second check inside `HmacValidator`/`Registry.process`) to incorporate `shop`, `topic`, and `webhook_id` alongside the raw body before computing/verifying the HMAC, OR
- Independently verify the `shop-domain` header against a value already trusted for the current request context (e.g., cross-check with a shop-scoped API call, or require callers to pass the expected shop explicitly and assert equality against `request.shop` before invoking the handler).
- At minimum, document prominently that `shop`/`topic`/`webhook_id` are NOT authenticated by `HmacValidator.validate`, and that consuming applications must not trust them as tenant-identifying values without additional verification (e.g., confirming the shop is an existing, currently-installed tenant and that the webhook was actually registered for that topic/shop combination via the Admin API).

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop: attacker-shop.myshopify.com
#    Shopify legitimately sends a webhook to the app's endpoint, e.g.:
#      X-Shopify-Topic: products/create
#      X-Shopify-Hmac-Sha256: <valid HMAC of body, signed with shared client_secret>
#      X-Shopify-Shop-Domain: attacker-shop.myshopify.com
#      body: '{"id":1,"title":"evil"}'

# 2. Attacker captures the body + hmac header exactly as sent, then replays it,
#    only changing the shop-domain (and/or topic) header:
headers = {
  "x-shopify-topic" => "app/uninstalled",              # forged topic
  "x-shopify-hmac-sha256" => captured_hmac_header,      # unchanged - still valid, since only body is signed
  "x-shopify-shop-domain" => "victim-shop.myshopify.com" # forged shop
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: headers)

# 3. HmacValidator.validate(request) returns true (body signature matches),
#    even though shop/topic were never actually issued by Shopify for victim-shop.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...))
# The app's uninstall-cleanup logic now runs against victim-shop's tenant data,
# triggered entirely by an unprivileged attacker who merely installed the app themselves.

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
      def shopify_header(name)
        @headers["shopify-#{name}"] || @headers["x-shopify-#{name}"]
      end
    end
  end
end

module ShopifyAPI
  module Utils
    module HmacValidator
      extend T::Sig

      class << self
        extend T::Sig

        sig { params(verifiable_query: VerifiableQuery).returns(T::Boolean) }
        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
      end
    end
  end
end
