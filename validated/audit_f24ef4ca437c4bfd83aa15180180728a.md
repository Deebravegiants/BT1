### Title
Untyped, non-domain-separated signature in `pallet-hyper-fungible-token` calldata execution enables cross-chain replay of privileged `RuntimeCall` dispatch — (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`pallet-hyper-fungible-token`'s `on_accept` handler lets an attacker-controlled cross-chain message carry a `SubstrateCalldata{signature, runtime_call}` payload that, once verified, dispatches an arbitrary `RuntimeCall` as the beneficiary's own account. The signed payload is `(nonce, runtime_call)` — no chain identifier, genesis hash, pallet/module id, or any other domain separator is included, so the exact vulnerability class from the referenced report ("untyped data signing" enabling cross-chain/cross-application signature reuse) applies directly here.

### Finding Description
In `modules/pallets/hyper-fungible-token/src/module.rs`, `on_accept` optionally executes calldata attached to an inbound token transfer: [1](#0-0) 

The signed message for all three supported signature schemes (Ed25519, Sr25519, ECDSA) is built the same way: [2](#0-1) 

```rust
let payload = (nonce, substrate_data.runtime_call.clone()).encode();
let msg = sp_io::hashing::keccak_256(&payload);
```

This is exactly the "untyped application data is directly hashed and signed" pattern from the report: the payload has no domain separator binding it to:
1. **A specific chain/pallet instance** — no chain id, genesis hash, or `PALLET_ID` is folded into the hash, unlike `pallet-relayer`'s analogous signed messages, which explicitly include the `state_machine` (see `modules/pallets/relayer/src/withdrawal.rs` and `accumulate.rs`) specifically to prevent this class of bug (its own tests, `test_accumulate_fees_rejects_replay_from_other_chain`, exist precisely to guard against this).
2. **The application/protocol context** — the payload looks like a generic `(u64, Vec<u8>)` tuple; nothing tells a signer or their wallet that this authorizes an arbitrary runtime call dispatch through the HFT bridge, making it trivial to obtain via blind-signing/phishing under an unrelated pretext (report's attack #4).

`SubstrateCalldata` is defined with only these two fields: [3](#0-2) 

The `nonce` used is `frame_system::Pallet::<T>::account_nonce(beneficiary)` — a per-account, per-chain system nonce that is commonly `0` for any account that has not yet transacted on that particular chain: [4](#0-3) 

Critically, the inbound message that carries this signed payload is attacker-triggerable: `on_accept` only requires that the ISMP `from`/`source` pair matches a registered peer contract (`ContractToAsset`), which is the standard, permissionless paired token contract on the source chain — anyone can call that contract's `send()` with an arbitrary `data` field (containing any `SubstrateCalldata`) and an arbitrary beneficiary address: [5](#0-4) 

Because `pallet-hyper-fungible-token` is meant to be deployed identically across many parachains (as documented), and because the signed payload binds to nothing but `(nonce, runtime_call)`, a signature a user produces intending to authorize a call on one HFT deployment/chain can be replayed by an attacker into an inbound message targeted at a different chain (or a different, freshly-onboarded account with the same nonce), causing the identical `RuntimeCall` to be dispatched there with the beneficiary as origin.

### Impact Explanation
If the recovered/verified signer matches the declared beneficiary, the pallet dispatches `runtime_call` as `RawOrigin::Signed(beneficiary)`, filtered only by `BaseCallFilter`: [6](#0-5) 

This is unauthorized app/account action: an attacker who obtains (via replay, phishing, or reuse from an unrelated application using the same trivial `(nonce, bytes)` signing convention) a user's signature over some call can force that exact call to be dispatched as that user's origin on a different chain/instance than the user intended, whenever the nonce lines up (most reliably nonce `0`, i.e. against fresh accounts) — e.g. dispatching `Balances::transfer`, staking, or governance calls the victim never authorized on that chain. This can lead to direct theft of funds or unauthorized privileged actions, matching the required "unauthorized app action" / "concrete theft" impact bar.

### Likelihood Explanation
The attack requires an attacker to already possess a valid signature over `(nonce, runtime_call)` from the victim — obtainable either by intercepting/replaying a legitimately-produced signature meant for one chain and resubmitting it (via the permissionless source-contract `send()`) into a message aimed at a different chain/account with a matching nonce, or by phishing the victim into producing such a signature under an unrelated pretext, since the payload carries no readable domain context. Given HFT is explicitly designed for multi-chain, identical-pallet deployment and the nonce space is small/predictable (0 for fresh accounts), this is a realistic, low-cost griefing/theft vector reachable from a single crafted cross-chain send — no privileged role needed.

### Recommendation
Bind the signed payload to a proper domain separator before hashing, analogous to how `pallet-relayer` includes `state_machine` in its signed messages: include at minimum the destination `StateMachine`/chain id (or genesis hash), the pallet's `PALLET_ID`, and a type/context tag (e.g. `b"HFT-CALLDATA"`), e.g. `(b"HFT-CALLDATA", dest_state_machine, PALLET_ID, nonce, runtime_call).encode()`. Ideally, follow an EIP-712/SCALE-equivalent typed-data convention so wallets can render what is being authorized, preventing both cross-chain replay and blind-signing phishing.

### Proof of Concept
1. Victim has account `A` with nonce `0` on parachain `P1` (running `pallet-hyper-fungible-token`) and also owns/derives the same keypair for account `A` on parachain `P2` (also running the same pallet, also at nonce `0`, e.g. freshly onboarded to the Hyperbridge HFT deployment).
2. Victim legitimately signs `(nonce=0, runtime_call=X)` for some intended action on `P1` and this signature circulates (leaked off-chain, phished under an unrelated cover story, or observed on-chain in a prior `SubstrateCalldata`).
3. Attacker calls `send()` on the paired `HyperFungibleToken`/`WrappedHyperFungibleToken` EVM contract targeting `P2`, setting `to = A` and `data = SubstrateCalldata { signature: <victim's signature>, runtime_call: X }` (any dust amount/fee suffices).
4. On `P2`, `on_accept` recomputes `keccak256((0u64, X).encode())`, verifies it against the victim's public key/address, succeeds (because the payload never referenced `P1` or `P2`), and dispatches `X` as `RawOrigin::Signed(A)` on `P2` — an action the victim never authorized on that chain.

		// If 32 bytes: use directly. If 20 bytes: left-pad with zeros.
