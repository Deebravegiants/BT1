### Title
Non-embedded session cookie value is an unsigned, guessable session ID (`offline_#{shop}`), enabling cross-tenant session hijacking - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
This gem's OAuth callback flow builds the `shopify_app_session` cookie's value directly from `Session#id`, which for offline sessions is the fully predictable string `"offline_#{shop}"` and for online sessions is `"#{shop}_#{associated_user.id}"`. This value carries no cryptographic binding (no HMAC, no signature) to the actual authenticated shop — it is later read verbatim by `SessionUtils.cookie_session_id` and used as the lookup key for retrieving the stored `Session` (which contains the shop's `access_token`). Because `shop` is public information and the ID format is deterministic and documented, an attacker can set this cookie to another tenant's session ID and have the host application's session-storage lookup hand back that tenant's session.

### Finding Description
In the authorization-code-grant callback, `ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the session and cookie as: [1](#0-0) 

For non-embedded apps, `cookie.value` is set to `session.id`. `Session.from` derives that ID deterministically and without any secret: [2](#0-1) 

This cookie value is later read back verbatim (no signature check, no HMAC) as the "current session id" that the host app is expected to use to retrieve the stored session: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`cookie bytes handed to the browser == a value that only the legitimately-authenticated shop/user could have produced or observed`

Instead the binding that actually holds is:
`cookie bytes accepted by cookie_session_id == any string of the form "offline_{myshopify_domain}" or "{myshopify_domain}_{user_id}", none of which require any secret or prior authentication to construct`

Since `myshopify_domain` values are public (every shop's domain is guessable/enumerable, and merchants can trivially learn their own or find others'), and for the online case `associated_user.id` is often a small sequential/discoverable integer, an attacker who has ever installed the app (or otherwise interacts with the app's callback/session endpoints) can set `shopify_app_session=offline_othershop.myshopify.com` on their own request and have the host app's `SessionRepository.retrieve_session(id)` (the pattern this gem's own docs prescribe, see `docs/usage/oauth.md`) return the victim shop's `Session`, including its `access_token`.

This is exactly analogous to the reported bug class: two code paths are supposed to agree on what constitutes a validated identity token, but one path (`cookie_session_id`) trusts raw, unauthenticated bytes as if they were an already-verified session identifier, while the sibling path (`session_id_from_shopify_id_token`) only accepts an identifier derived from a properly HMAC/JWT-verified source (`Auth::JwtPayload`, which is signed with `Context.api_secret_key`).

### Impact Explanation
If exploited, this allows cross-tenant access: an attacker forges/guesses another merchant's deterministic session ID and, via the host application's documented session-retrieval pattern, obtains that merchant's stored `Session` object including its `access_token`, enabling API calls as that merchant/shop. This matches the Critical impact category (cross-tenant access / theft of a merchant access token via the exposed identity primitive this gem hands to consuming applications).

### Likelihood Explanation
Likelihood is high for the offline case: the session ID is simply `"offline_" + myshopify_domain`, and `myshopify_domain` is not a secret — it is the shop's own public storefront domain. No secret key, token, or privileged access is needed to construct a valid-looking session ID; only the ability to set/send a cookie header to the app is required, which is available to any unprivileged actor interacting with the app's non-embedded flow.

### Recommendation
Do not use raw, attacker-suppliable identifiers (shop domain, user id) as the sole session lookup key exposed via an unsigned cookie. Either sign/HMAC the cookie value (bind it to `Context.api_secret_key` the same way `HmacValidator`/`JwtPayload` do for other identity primitives) and verify that signature in `cookie_session_id`, or store only an unguessable, randomly-generated token (e.g. `SecureRandom.uuid`, which `Session#id` already supports as a default) as the cookie value instead of the deterministic `shop`/`user_id`-derived ID, and keep the deterministic ID solely as an internal storage key not exposed to the browser.

### Proof of Concept
1. App is installed for `victim-shop.myshopify.com`; OAuth completes and, per `Oauth.validate_auth_callback`, the app (non-embedded) sets cookie `shopify_app_session=offline_victim-shop.myshopify.com` in the victim admin's browser and persists the corresponding `Session` (with `access_token`) via `SessionRepository.store_session`.
2. Attacker, who separately uses the same app (or simply knows the target's public `myshopify.com` domain), sends a request to the host app with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`.
3. Host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)` → `cookie_session_id(cookies)` → returns `"offline_victim-shop.myshopify.com"` unchanged (no verification performed by the gem). [5](#0-4) 
4. Host app looks up `SessionRepository.retrieve_session("offline_victim-shop.myshopify.com")` and obtains the victim shop's `Session`, including `access_token`, allowing the attacker to make authenticated Admin API calls against `victim-shop.myshopify.com`.
