## Title
Webhook HMAC signature covers only the raw body — `shop`, `topic`, `webhook-id`, and `api-version` headers are unauthenticated and can be forged for cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` authenticates nothing but the byte content of the payload. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers that are never included in the signed data, yet `Registry.process` trusts `request.shop` and `request.topic` to route the payload and identify the tenant.

### Finding Description
`Request#hmac` is derived from the `hmac-sha256` header, and the value it is checked against is computed by `HmacValidator.compute_signature(verifiable_query.to_signable_string, secret)`: [1](#0-0) 

`to_signable_string` returns only `@raw_body`; it does not fold in `shop`, `topic`, `webhook_id`, or `api_version`, all of which are read from separate, independently attacker-controllable headers: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only ever hash `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` then trusts `request.topic` (to select the handler) and `request.shop` (passed straight into `WebhookMetadata`, which apps use to identify the tenant the event belongs to) — despite neither being covered by the HMAC that was just validated: [4](#0-3) 

**Equality that should hold but doesn't:** `shop signed over by HMAC == shop used to route/attribute the webhook`. In this gem, the HMAC only binds `raw_body`, so `hmac_covers(shop) == false` while `Registry.process` still does `handler.handle(shop: request.shop, ...)`.

Any party who can obtain one genuinely-signed `(raw_body, hmac)` pair from Shopify for the app's real `api_secret_key` — trivially achievable by any unprivileged user who installs the app on their own store and lets Shopify deliver a real webhook to the app's public endpoint — can resend that exact `raw_body`/`hmac` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and/or `x-shopify-topic`) header. `HmacValidator.validate` still succeeds because it only re-hashes the unmodified body, and `Registry.process` then dispatches the handler believing the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: an app that uses `WebhookMetadata#shop` to look up per-shop state, credentials, or to perform writes (e.g. processing `app/uninstalled`, `shop/update`, or order/customer topics keyed off `shop`) can be made to act on/for an arbitrary shop identifier supplied by an unrelated, unprivileged attacker. This is a cross-tenant access vector as defined in scope (Critical impact bucket), since the shop attribution used for routing/business logic is never authenticated.

### Likelihood Explanation
Any user can become a real, low-privilege Shopify merchant/dev-store owner and install the target app, which causes Shopify to deliver a validly-HMAC'd webhook with a body they control (their own store's data) to the app's already-public webhook endpoint. They then only need to replay that exact `(body, hmac)` with a spoofed `shop-domain` (and optionally `topic`) header — no secret, token, or elevated privilege is required. This is a mechanical, low-effort attack once instructions are known.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed payload (or otherwise cryptographically bind them to the body) before verifying the HMAC, e.g. by canonicalizing a string of `topic + shop + webhook_id + api_version + raw_body` in `to_signable_string`, or — since Shopify's actual HMAC is computed over the raw body only — treat `request.shop`/`request.topic` as untrusted and require applications to independently verify the shop against a known/installed shop record before acting on webhook data, and document this gap clearly to consumers of `Webhooks::Registry`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`; Shopify delivers a legitimate webhook (e.g. `carts/update`) to the app's public endpoint with headers `x-shopify-hmac-sha256: <valid-hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: carts/update`, and some JSON body `B`.
2. Attacker captures `(B, valid-hmac)`.
3. Attacker sends a new POST to the same webhook endpoint with body `B` unchanged, `x-shopify-hmac-sha256: <valid-hmac>` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `HmacValidator.validate` recomputes HMAC over `@raw_body` only and it matches, so `Registry.process` proceeds and calls the registered handler with `WebhookMetadata.new(topic: "carts/update", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, even though this event never occurred for `victim-shop.myshopify.com`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
