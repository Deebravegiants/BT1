### Title
Unbounded gas forwarded to attacker-controlled destination app in `EvmHost.dispatchIncoming` enables gas-griefing of relayers - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming` forwards essentially all available gas to an arbitrary destination contract via a low-level `.call()` when delivering a POST request, with no caller-configurable or protocol-enforced gas cap. Because `EvmHost.dispatch` is fully permissionless and does not validate that `post.to` is a legitimate `IApp` implementation, any address can craft a POST request destined for a malicious contract that deliberately burns gas in `onAccept`. This directly mirrors the reported `RFTLib`/`tokenRequestCB` gas-griefing pattern: an untrusted callee is invoked with unbounded gas by a party (here, the relayer) who bears the cost.

### Finding Description
`EvmHost.dispatch(DispatchPost memory post)` lets `_msgSender()` set `post.to` to any address and `post.dest` to any state machine, with no allow-list or interface check on the destination [1](#0-0) . Once finalized on Hyperbridge, any permissionless relayer submits the proof via `HandlerV2.handlePostRequests`, which iterates every request leaf in the batch and calls `host.dispatchIncoming(leaf.request, _msgSender())` for each [2](#0-1) .

`EvmHost.dispatchIncoming` then executes:
```solidity
(bool success,) = address(destination)
    .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
``` [3](#0-2) 

This `.call()` has no explicit gas stipend, so by EVM semantics it forwards up to 63/64 of all gas remaining in the relayer's transaction. Since `destination` is attacker-chosen and unvalidated, an attacker deploys a malicious contract whose `onAccept` (or fallback, since `extcodesize` only checks for *any* code, not `IApp` conformance) consumes an amount of gas far exceeding what the relayer's off-chain gas estimation predicted. The relayer's tx.rs tooling estimates gas per-message via `estimate_gas()` calls before submission [4](#0-3) , but this estimate can be manipulated on-chain by the attacker's contract behaving differently at simulation time versus execution time (e.g., gas-dependent branching, or simply consuming gas proportional to whatever is forwarded via a bounded-but-large loop keyed off `gasleft()`).

Because `HandlerV2.handlePostRequests` processes a whole batch of leaves in one relayer transaction under a single externally-supplied gas limit, one malicious request destined for a gas-guzzling contract can exhaust the gas budget for the entire batch, causing the surrounding transaction to run out of gas and revert before the loop completes — even though other legitimate, honestly-behaving requests were bundled in the same delivery transaction. The relayer pays for all gas consumed in the failed transaction, and since delivery failed, the requests remain undelivered and can be resubmitted, letting the attacker force repeated relayer griefing at will (the malicious request can always be resubmitted alongside new batches, or targeted alone, at negligible attacker cost relative to relayer loss).

### Impact Explanation
Impact is Medium: relayers are the entities that pay gas to deliver messages and are the ones directly harmed — they lose gas fees on reverted or gas-heavy deliveries and can be repeatedly forced to retry, degrading the reliability of the message-delivery route (a "route unable to deliver messages" condition for batches containing the malicious request). This does not directly enable theft of user funds but can be leveraged to stall delivery of arbitrary bundled requests and drain relayer profitability, which threatens the liveness/economic viability of Hyperbridge's core relaying function.

### Likelihood Explanation
Likelihood is Medium: dispatching a POST request to an arbitrary destination is fully permissionless and requires no special privilege beyond paying the (attacker-controlled) relayer fee/dispatch fee, and any EOA can deploy a gas-guzzling contract as the destination. The only cost to the attacker is the fee paid to dispatch the request (which they control and can set low or zero if self-relaying is possible, or via griefing a third-party relayer who has already committed to deliver).

### Recommendation
Introduce an explicit, bounded gas stipend for the `IApp.onAccept` callback invoked in `EvmHost.dispatchIncoming` (and the analogous `onGetResponse`/`onGetTimeout`/`onPostRequestTimeout` calls), e.g. `destination.call{gas: GAS_CAP}(...)`, with `GAS_CAP` either a protocol-wide constant or a per-request value supplied and paid for by the dispatcher at `dispatch()` time (mirroring relayer-fee economics), so a relayer's worst-case cost per request is bounded and known in advance. Additionally, consider capping the number of leaves processed per `handlePostRequests` batch or allowing partial-batch continuation so a single malicious request cannot compromise the delivery of an entire batch of unrelated legitimate requests.

### Proof of Concept
1. Attacker deploys `MaliciousApp` with:
```solidity
contract MaliciousApp {
    function onAccept(IncomingPostRequest calldata) external {
        while (gasleft() > 1000) { /* spin */ }
    }
}
```
2. Attacker calls `EvmHost.dispatch(DispatchPost{ to: abi.encodePacked(address(maliciousApp)), dest: <destChain>, body: "", fee: 0, payer: attacker, timeout: 0 })` on the source chain — no validation prevents this [1](#0-0) .
3. A relayer, having estimated gas for a batch that bundles this request together with several legitimate ones, submits `HandlerV2.handlePostRequests` with the estimated gas limit.
4. During execution, `dispatchIncoming` forwards nearly all remaining gas to `MaliciousApp.onAccept`, which spins until it exhausts the forwarded gas [5](#0-4) .
5. The remaining gas budget for the rest of the loop in `handlePostRequests` is insufficient to process the remaining leaves, causing the whole transaction to run out of gas and revert, so none of the batched (including legitimate) requests are delivered, and the relayer's gas fee for the failed transaction is lost [2](#0-1) .

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
