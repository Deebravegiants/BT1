### Title
Webhook shop-domain identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to application webhook handlers purely from an HTTP header, while the HMAC signature that is supposed to authenticate the whole webhook request only covers the raw request body. Any actor who can obtain one valid `(body, hmac)` pair for a shop they control can replay that exact body/HMAC pair while substituting the `shop-domain` header for a different, victim shop, and the signature check will still pass — breaking the equality "shop the HMAC vouches for == shop the handler acts on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (as well as `topic`, `api_version`, `webhook_id`) is read straight from headers and is never part of the signable string: [2](#0-1) 

`HmacValidator.validate` only ever verifies the signature against `verifiable_query.to_signable_string`, i.e. the raw body — it has no knowledge of, and does not incorporate, the `shop` header: [3](#0-2) 

`Registry.process` trusts this unauthenticated `shop` field once the HMAC check passes and forwards it directly into the application's webhook handler as the tenant identity: [4](#0-3) 

Formally, the gem's authentication guarantee should be:
`HMAC-verified(shop) == handler-acted-on(shop)`

But the actual binding is:
`HMAC-verified(raw_body) ; handler-acted-on(shop_header)` — two disjoint values, with only the first being cryptographically checked.

An attacker who legitimately controls (or can trivially provision) a Shopify development/trial shop of their own will receive genuine Shopify-signed webhook deliveries for that shop — valid `raw_body` + valid `x-shopify-hmac-sha256` pairs signed with the target app's own `api_secret_key` (the app's secret is never exposed to the attacker; they merely observe Shopify's own valid delivery to their own shop). They can replay that exact `(body, hmac)` pair to the target application's webhook endpoint while rewriting `x-shopify-shop-domain` to any victim shop domain string of their choosing. `HmacValidator.validate` will still return `true` since it only checks the body, and `Registry.process` will pass the attacker-chosen `shop` value on to the handler as if Shopify itself asserted it.

### Impact Explanation
This allows cross-tenant confusion: webhook payloads that were only ever signed and delivered for the attacker's own shop can be injected into the application under an arbitrary victim shop identity. Depending on how the host application's webhook handler uses `data.shop` (e.g., to look up/update tenant-scoped records, credentials, or billing state keyed by shop domain), this can lead to cross-tenant data corruption or unauthorized cross-tenant writes — matching the "cross-tenant access" Critical impact category, since the shop-tenant boundary that the HMAC is meant to enforce is not actually enforced for the `shop` field consumed by handlers.

### Likelihood Explanation
Likelihood is high for any unprivileged internet user: no access token, `api_secret_key`, or privileged account is required. The attacker only needs a shop of their own (trivially obtainable, e.g. a free Shopify development store) that has the target app installed, so they can capture a real `(raw_body, hmac)` pair from a genuine Shopify webhook delivery, then replay it to the app's public webhook endpoint with a forged `shop-domain` header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable string, or independently verify that the `shop` header value is consistent with a value bound to the signature (e.g., have applications additionally verify the `shop` against their own known-installed-shops list before trusting `WebhookMetadata#shop`). At minimum, document that `request.shop` is unauthenticated by the HMAC check and must not be trusted as a tenant boundary without additional verification by the host application.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the target app installed.
# Shopify delivers a genuine, correctly-signed webhook to the attacker's endpoint:
raw_body = '{"id":123,"note":"legit order for attacker shop"}'
valid_hmac_from_shopify = "<captured x-shopify-hmac-sha256 value from real delivery>"

# Attacker replays the exact same body+hmac, but swaps the shop header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_from_shopify, # unchanged, still valid because it only signs raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged tenant identity
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HmacValidator.validate(request) => true, because it only checks raw_body against the HMAC.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", ...))
# The host app now processes attacker-controlled data under the victim shop's identity.
```

        def validate(verifiable_query)

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
