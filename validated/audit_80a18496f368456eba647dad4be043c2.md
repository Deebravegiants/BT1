### Title
Relayer fee is paid unconditionally from `NearWalletContract` even when the underlying emulated transfer fails - (File: `runtime/near-wallet-contract/implementation/wallet-contract/src/lib.rs`)

### Summary
In the NEAR ETH-wallet-contract implementation, `inner_rlp_execute` pays out the relayer `fee` for `EOABaseTokenTransfer`/`ERC20Transfer` transactions via an independent `Promise` created before the actual transfer action, rather than being contingent on that action's success. This mirrors the Taiko `Bridge.processMessage()` bug class: an unprivileged caller (the relayer) collects a fee/reward that is supposed to compensate for successfully delivering a call, even when that call fails.

### Finding Description
`inner_rlp_execute` parses a signed Ethereum-style transaction into a NEAR action. For `EOABaseTokenTransfer`/`ERC20Transfer` kinds carrying a non-zero `fee`, the code immediately creates a standalone promise batch that transfers `fee` to the relayer (`context.predecessor_account_id`): [1](#0-0) 

This fee promise is unconditional — it does not depend on (is not `.then()`-chained after) the actual action promise, which is constructed separately later in the same function and only resolves/fails in `rlp_execute_callback`: [2](#0-1) 

If the underlying transfer/call fails, `rlp_execute_callback` only refunds the `caller_deposit` (the attached NEAR deposit passed by the predecessor for the inner call) — the `fee` that was already sent to the relayer is not returned: [3](#0-2) 

The only precondition for the fee payment is that `parse_rlp_tx_to_action` succeeds (valid signature/nonce/formatting), not that the resulting action itself executes successfully: [4](#0-3) 

This is structurally identical to the Taiko `Bridge.processMessage()` issue: the caller (relayer) is rewarded for merely invoking the entry point, independent of whether the invoked cross-account call actually succeeds.

### Impact Explanation
Any account can act as a relayer for a signed `SignedDelegateAction`-like RLP payload and call `rlp_execute` on the target `WalletContract`. A malicious or opportunistic relayer can select and submit only transactions it knows (or can check in advance, e.g. via a view call on token balance) will fail the inner `ERC20Transfer`/`EOABaseTokenTransfer` action (e.g., insufficient token balance, non-existent/unregistered receiver in a way that still causes downstream failure, or destination contract logic reverting), while still collecting the full `fee` from the wallet-contract account's own NEAR balance. This drains value from the wallet-contract owner's account without the promised service (the transfer) being rendered, and removes the economic incentive for relayers to actually complete transfers correctly — they are paid the same whether or not the action succeeds.

### Likelihood Explanation
The wallet-contract design explicitly documents that relayers can be arbitrary and untrusted ("This allows any relayer to safely serve base token transfers from any wallet without additional on-boarding"), and its own comments acknowledge the risk ("Users should always verify the fee before signing a base token transfer. Relayers should also verify the fee..."). This shows the unconditional-fee behavior is a recognized trade-off similar to Taiko's own confirmed-but-accepted response to [M-14] ("I don't think paying fees only when `_invokeMessageCall` returns true is a good idea..."). Any account can act as relayer and check in advance (via a view call) whether the emulated transfer will fail, making exploitation straightforward and low-cost, since only gas is spent submitting a transaction that is already known to fail the inner action while the fee payout still executes unconditionally.

### Recommendation
Chain the fee-transfer promise after the success of the inner action (e.g., append it as part of the `.then()` continuation, conditioned on `PromiseResult::Successful` in `rlp_execute_callback`), rather than firing it independently at parse time. Alternatively, hold the fee in escrow and release it to the relayer only from within `rlp_execute_callback` upon confirmed success of the emulated transfer, mirroring the recommendation from the referenced report.

### Proof of Concept
1. Deploy a `WalletContract` for address `A` funded with NEAR and holding some fungible token `T` with a low balance.
2. `A` signs an RLP-encoded `ERC20Transfer` (or `EOABaseTokenTransfer`) transaction for token `T`, receiver `B`, with `fee = X` payable to whichever relayer submits it, but with a transfer `amount` exceeding `A`'s actual `T` balance (or crafted so `ft_transfer` will fail/panic).
3. A malicious relayer `R` observes/knows (e.g., via a view call to `T.ft_balance_of(A)`) that the transfer will fail, then calls `WalletContract::rlp_execute(target=T, tx_bytes_b64=...)` as predecessor `R`.
4. Inside `inner_rlp_execute`, the code path at [5](#0-4)  immediately schedules `promise_batch_action_transfer(fee)` to `R`, independent of the subsequent `ft_transfer` promise.
5. The subsequent `ft_transfer` call (chained via `nep_141_storage_balance_callback`/`action_to_promise`) fails; `rlp_execute_callback`'s `PromiseResult::Failed` branch only refunds `caller_deposit`, not `fee`.
6. `R` receives `fee` in full even though `A`'s intended transfer never completed, at `A`'s expense.
