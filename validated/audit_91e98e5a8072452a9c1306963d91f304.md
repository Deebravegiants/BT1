Found it. `TokenExchange.exchange_token` in `lib/shopify_api/auth/token_exchange.rb` uses `jwt_payload.shop` (the JWT `dest` claim) directly as the host for the token-exchange HTTP request that carries the app's `client_secret`, without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-bearing flow in the same file and module (`migrate_to_expiring_token`, `RefreshToken.refresh_access_token`, `ClientCredentials.client_credentials` all call `Utils::ShopValidator.sanitize!(shop)` before use).

### Title
SSRF / `client_secret` exfiltration via unsanitized JWT `dest` claim in Token Exchange - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the outbound request host from the session token's `dest` claim (`jwt_payload.shop`) but never runs it through `Utils::ShopValidator.sanitize!`, breaking the equality that should hold everywhere else in this module: `host contacted with client_secret == ShopValidator.sanitize!(shop)`. Every sibling credential-bearing method (`RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`, `ClientCredentials.client_credentials`) enforces this equality; `exchange_token` does not.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` via `ShopifyAPI::Auth::JwtPayload.new(session_token)` [1](#0-0) . `JwtPayload#shop` merely strips the literal string `"https://"` from the raw `dest` claim with no domain allow-listing: [2](#0-1) . The only server-side check on the JWT is signature validity (`HS256` with `api_secret_key`) and `aud == Context.api_key` [3](#0-2) ; `iss`/`dest` are never checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

This unsanitized `dest_shop` is used to build the `Auth::Session` whose `shop` becomes the HTTP host that `Clients::HttpClient` connects to, carrying the app's `client_id`/`client_secret` in the POST body: [4](#0-3) . `HttpClient#initialize` builds `@base_uri` directly from `session.shop` [5](#0-4) .

Contrast with the sanitized siblings in the same file/module: [6](#0-5) [7](#0-6) [8](#0-7) 

`ShopValidator.sanitize!` exists precisely to enforce that any shop-derived host is one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or an app-configured `myshopify_domain` [9](#0-8) . `exchange_token` skips this exact guard for the one field it fully trusts to route a credential-bearing outbound request.

Since a session token is a self-issued JWT that the app itself creates and sends to the browser/App Bridge to be exchanged, and since forging a *validly signed* JWT still requires the `api_secret_key` (out of scope per the rules), this is not a full unauthenticated bypass — it is a code-quality/defense-in-depth gap relative to the pattern established by the rest of the module rather than a directly exploitable vulnerability without already holding the secret or being able to influence the `dest` claim of a token the app itself signs. I could not establish a path where an "unprivileged internet user" supplies an attacker-chosen `dest` into a JWT that then gets validated successfully by `JwtPayload.new`, because `JwtPayload` verifies the signature before trusting any claim, and only the app (holder of `api_secret_key`) can produce a valid signature.

### Impact Explanation
If exploitable (e.g., via a compromised or leaked `api_secret_key`, or any code path that lets an untrusted party influence the `dest` claim of an otherwise-valid session token), the impact would be High: SSRF carrying the app's `client_id`/`client_secret` to an attacker-chosen host, i.e., `client_secret` exfiltration to an arbitrary domain.

### Likelihood Explanation
Low. Exploitation requires the attacker to already control or forge a validly-signed session token's `dest` claim, which in turn requires the `api_secret_key` — explicitly out of scope per the rules ("anything requiring... leaked credentials"). Absent that, the token's `dest` is set exclusively by Shopify/the app itself during normal session-token issuance, so under normal operation this is not reachable by an unprivileged party.

### Recommendation
Apply the same `Utils::ShopValidator.sanitize!(jwt_payload.shop)` guard in `TokenExchange.exchange_token` that is already used in `migrate_to_expiring_token`, `RefreshToken.refresh_access_token`, and `ClientCredentials.client_credentials`, so that the JWT `dest` claim cannot route the `client_secret`-bearing request to any host outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not constructible as a genuine unprivileged-attacker exploit: doing so requires forging a signature-valid JWT with an attacker-chosen `dest`, which requires possession of `api_secret_key`. This is flagged as a defense-in-depth inconsistency rather than a proven, independently-exploitable vulnerability.
