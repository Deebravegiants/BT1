## Title
Webhook shop-domain header is not covered by the HMAC, allowing cross-tenant webhook spoofing — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw request body only, while the shop identity used downstream by the webhook handler comes from a separate, unsigned HTTP header. Any party who can obtain one valid `(raw_body, hmac)` pair for a webhook delivered to the app (e.g. by installing the app on their own store) can replay that exact body to the app's shared webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for an arbitrary victim shop. `Utils::HmacValidator` will still validate successfully because it only checks the body bytes against the secret, and `Registry.process` will hand the (attacker-controlled) shop value to the app's handler as if it were authenticated.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
It returns only `@raw_body`. Meanwhile, `Request#shop` is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely independent of the signed content: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC exclusively against `to_signable_string` (the body): [3](#0-2) 

`Registry.process` then trusts `request.shop` as the tenant identity, passing it straight into the handler without any additional binding check to the signed payload: [4](#0-3) 

This breaks the intended identity binding: **shop-domain-in-signed-payload == shop-domain-acted-on**. The HMAC only proves "this body byte-sequence was produced with knowledge of `client_secret`" — it says nothing about which shop the body belongs to, because `shop` is never part of `to_signable_string`. Anyone able to source one legitimate `(body, hmac)` pair (trivially available to any merchant who installs the app on their own store, since Shopify delivers a correctly-signed webhook to the app's endpoint for that install) can resend that same body/hmac pair with a different `shop-domain` header value, and the gem will treat it as an authenticated webhook for the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding bypass: a value (`shop`) that the handler relies on to determine which merchant's data/session a webhook belongs to is not covered by the cryptographic proof that gates processing. A multi-tenant app built on this gem (typical usage pattern shown in `docs/usage/webhooks.md` and `WebhookMetadata`) will process attacker-controlled webhook bodies under an arbitrary victim shop identity, enabling cross-tenant data confusion/injection into another merchant's records — this matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Any unprivileged internet user can become a legitimate installer of a Shopify app targeting this gem (e.g. via a free developer/test store), which is enough to receive one real, validly-signed webhook body for a topic the app subscribes to. Replaying that exact body to the shared webhook endpoint with a forged `shop-domain` header requires no secret material, no access token, and no TLS interception — only a standard HTTP POST to the app's public webhook route.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind the shop value to the verified body before it is handed to `WebhookHandler#handle`. At minimum, `Registry.process` should independently confirm that `request.shop` corresponds to a shop with an active, known session/installation before trusting it as the tenant key, rather than treating an unauthenticated header as ground truth alongside an HMAC that never covers it.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a subscribed webhook topic (e.g. `orders/create`) so Shopify POSTs a legitimately signed webhook to the app's public endpoint, giving the attacker a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair.
2. Replay that exact `raw_body` and `X-Shopify-Hmac-Sha256` value to the same endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate` succeeds (it only checks the unmodified body against the secret via `to_signable_string`), and `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", ...))`, so the app processes attacker-supplied data under `victim.myshopify.com`'s identity.
