Confirmed: `message.from` on the EVM side is always set to `msg.sender` [1](#0-0) , so an attacker cannot forge an arbitrary `from` value from a legitimate `send()` call on that contract. But the pallet's `on_accept` derives the dispatch origin from `message.from` without any signature check whenever `substrate_data.signature` is `None`, and this `from` is fully attacker-chosen 20/32 raw bytes embedded in the ABI-encoded `Message.from` field, decoded independently of `message.to`/beneficiary [2](#0-1) . The critical question is whether `Message.from` is actually constrained to `msg.sender` on every possible source chain contract that could be registered against this pallet via `ContractToAsset`, or whether an EVM message router that is not the canonical `HyperFungibleTokenUpgradeable` contract (e.g. a different/compromised implementation, or a chain where the registered "source" is not validated to only be that trusted contract) could submit an ISMP POST with an arbitrary `from`.

### Title
Unauthenticated runtime-call dispatch via unsigned cross-chain calldata in `pallet-hyper-fungible-token` - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` decodes an ABI-encoded `Message` from an incoming ISMP POST request and, if `message.data` is non-empty, SCALE-decodes it into `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` [3](#0-2) . It then decodes `runtime_call` into `T::RuntimeCall` and dispatches it with `RawOrigin::Signed(origin)` [4](#0-3) . When `substrate_data.signature` is `None`, `origin` is derived directly from the untrusted `message.from` bytes carried in the cross-chain payload, with **no cryptographic proof that the dispatcher actually controls that account** [2](#0-1) .

### Finding Description
This is the closest reachable analog to the AgentScope "deserialize untrusted bytes into an object that is then executed with elevated privilege" bug class: instead of `dill.loads` executing arbitrary Python, this pallet SCALE-`Decode`s an arbitrary `T::RuntimeCall` from cross-chain message bytes and unconditionally `.dispatch()`s it as a chosen account's signed origin. The only gate applied is `BaseCallFilter::contains(&runtime_call)` [5](#0-4)  — a filter, not an authentication check.

Authentication of the *origin* is supposed to come from the `Option<Vec<u8>> signature` in `SubstrateCalldata`. But that field is `Option` and, when `None`, the code falls back to deriving `origin` from `message.from`/`message.to` bytes without any signature verification at all — it simply converts whatever 20/32 raw bytes were included in the message into an `AccountId` and dispatches as that account. The only real guard is that the ISMP `source`/`from` (contract address) of the POST request must match a registered `ContractToAsset` mapping [6](#0-5) , which authenticates *which EVM contract* sent the message, not what `message.from`/`beneficiary` values are inside the ABI-encoded body. On the reference EVM contract, `Message.from` is hard-pinned to `msg.sender` [1](#0-0) , which prevents forging `from` through that specific contract's `send()`. However, the pallet's security model as written does not itself enforce this — it trusts whatever `from`/`to` bytes arrive in the body and treats an *unsigned* call as authorized for that origin. Any alternate, buggy, or attacker-influenced sender-side implementation registered in `ContractToAsset` (or any bridged non-EVM source with `source.is_evm() == false`, which takes the `to_bytes`/`from_bytes` directly with no `msg.sender` binding at all) would let an attacker dispatch arbitrary filtered runtime calls as an arbitrary account, with zero cryptographic proof of authorization.

### Impact Explanation
If reachable, this allows unauthorized dispatch of `T::RuntimeCall`s as any account for which an attacker can select `message.from`/`to`, since `beneficiary` is exactly the decoded `to` bytes and origin defaults to it. Combined with `BaseCallFilter` typically permitting most transfer/asset extrinsics, an attacker could drain assets or invoke privileged pallet calls in the name of any account whose raw bytes they can construct, without any signature — a direct theft-of-funds / unauthorized-app-action primitive, i.e., Critical impact per the report's CWE-502-style "deserialize and act on untrusted data" class.

### Likelihood Explanation
Likelihood depends entirely on whether every contract/module that can be registered under `ContractToAsset::<T>` for a given `(source, from)` pair enforces `Message.from == msg.sender`. The audited reference contract does enforce this [7](#0-6) , which substantially mitigates exploitability for that specific deployed contract. I was unable to verify all other implementations (`HyperFungibleToken.sol`, `WrappedHyperFungibleToken(Upgradeable).sol`) or any non-EVM (substrate-source) senders within the available index to confirm they apply the same binding, and the pallet code itself provides no independent enforcement — the authorization boundary lives entirely in sender-side contracts that this pallet has no way to guarantee are correctly implemented for every registered source.

### Recommendation
Require a valid `signature` in `SubstrateCalldata` (or otherwise cryptographically bind `message.from` to the calldata) for *every* dispatched runtime call, rather than allowing an unsigned fallback path that trusts `message.from`/`to` bytes as an implicit authorization. At minimum, do not derive a dispatch origin from unauthenticated cross-chain payload bytes; require the pallet itself to enforce the `from == msg.sender`-equivalent invariant rather than relying on trust in external, potentially-mutable sender contracts.

### Proof of Concept
Not constructible with full certainty from the indexed code alone, since the reference EVM contract does pin `from` to `msg.sender`. Conceptually: register (or compromise) any source contract/module against `ContractToAsset` that does not bind `Message.from` to the true caller, then submit a POST request whose `Message.data` decodes to `SubstrateCalldata { signature: None, runtime_call: <SCALE-encoded privileged call> }` with `to` set to a victim account — `on_accept` will dispatch the call as `RawOrigin::Signed(victim)` with no proof of authorization [8](#0-7) .
