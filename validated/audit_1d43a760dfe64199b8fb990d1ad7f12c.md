The `Registry.process` method validates HMAC over the raw body only, but hands `request.shop` (an unauthenticated header) to the handler as the tenant identifier.Confirmed: `WebhookMetadata.shop` is passed directly from the unauthenticated `shop-domain` header into the handler, while the HMAC only covers `@raw_body`.### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` (tenant identifier) is read from an unauthenticated HTTP header. `Registry.process` validates only the body's HMAC and then hands the unauthenticated `shop` value straight to the app's `WebhookHandler`. Any party who can obtain one genuine, HMAC-signed webhook body (e.g. from their own store) can replay it to the app's webhook endpoint with the `shop-domain` header swapped to a victim shop, and the signature will still validate — breaking the binding between "shop whose secret signed this payload" and "shop the payload is attributed to."

### Finding Description
The HMAC validation flow is:
- `Utils::HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to `verifiable_query.hmac`. [1](#0-0) 
- For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body` — it does **not** include `shop`, `topic`, `webhook_id`, or `api_version`. [2](#0-1) 
- `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, with no cryptographic binding to the body or the HMAC. [3](#0-2) 
- `Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., body HMAC), then immediately constructs `WebhookMetadata` using `request.shop` and dispatches it to the app's handler. [4](#0-3) 
- `WebhookMetadata.shop` is a plain `String` field, so the handler receives a “shop” that carries no HMAC guarantee at all. [5](#0-4) 

This mirrors the analog class requested: **a field acted on (`shop`, used as the tenant key by the handler) but not covered by the HMAC** (which only covers `@raw_body`). The gem verifies the *bytes of the body*, not the *bytes that determine which tenant the payload is attributed to* — exactly the "bytes verified versus bytes parsed/acted on" mismatch pattern from the rounding-bug analog (a check on one quantity, an action based on a different, unguarded quantity).

Unlike the OAuth `AuthQuery`, whose `to_signable_string` explicitly includes `shop` inside the signed parameters (so shop tampering invalidates the HMAC) [6](#0-5) , the webhook `Request` deliberately excludes `shop` from what is signed. This asymmetry within the same gem confirms the webhook path is the outlier that breaks the identity binding.

### Impact Explanation
Because `shop` is not part of the signed material, an attacker who operates their own Shopify store receives genuine, correctly HMAC-signed webhook deliveries for their own shop. They can capture the raw body + valid HMAC from their own legitimate webhook and replay it to the target app's public webhook endpoint with the `shop-domain` header rewritten to a victim merchant's domain. `HmacValidator.validate` still returns `true` (it only checks the body against the secret), so `Registry.process` will invoke the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload was never produced for that shop. Any app logic that trusts `data.shop` for tenant-scoped writes, entitlement checks, or triggering privileged actions (e.g., creating orders/fulfillments, updating billing state, or de-provisioning data) can be manipulated cross-tenant — this is a cross-tenant access boundary break using this gem's own verification primitive as the enabling mechanism.

### Likelihood Explanation
The prerequisite — owning/operating one Shopify store and receiving one webhook from it — is trivial and requires no credentials belonging to the target app or victim merchant. The webhook HTTP endpoint is, by design, internet-reachable and unauthenticated apart from HMAC. Replaying a captured body with a modified header requires no cryptographic material besides the attacker's own webhook payload, so the attack is straightforward to mount by any unprivileged internet user who signs up for a Shopify dev/trial store.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) as part of the HMAC-signed message, or otherwise cryptographically bind the header-derived tenant identifier to the verified payload before it is passed to `WebhookHandler#handle`. At minimum, `Webhooks::Request#to_signable_string` should not diverge from `AuthQuery#to_signable_string`'s pattern of including the shop in what gets verified, and `Registry.process` should re-validate that the `shop` header used for dispatch is consistent with data actually covered by the HMAC (e.g., derive/verify shop identity from a value that is part of the signed body, not solely from an independently-supplied header).

### Proof of Concept
1. Attacker registers their own store, `attacker-shop.myshopify.com`, and installs the target app so genuine webhooks are delivered to the app's public webhook endpoint.
2. Attacker triggers a webhook event (e.g., `orders/create`) and captures the full raw POST: headers (`x-shopify-hmac-sha256`, `x-shopify-topic`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-webhook-id`, `x-shopify-api-version`) and the raw JSON body.
3. Attacker resends this exact request to the same app endpoint, changing only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`, keeping the raw body and `x-shopify-hmac-sha256` unchanged.
4. In the gem: `Webhooks::Request.new(raw_body:, headers:)` parses this into a `Request` whose `hmac` and `to_signable_string` (`@raw_body`) are unchanged from step 2, so `Utils::HmacValidator.validate(request)` returns `true`. [7](#0-6) 
5. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...))`, causing the app to process attacker-controlled order/customer data as if it belonged to the victim shop. [4](#0-3)
