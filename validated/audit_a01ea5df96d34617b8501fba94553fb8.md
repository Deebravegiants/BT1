### Title
Unbounded gateway HTTP response cache allows workflow-triggered memory exhaustion - ([File: core/services/gateway/handlers/capabilities/v2/response_cache.go])

### Summary
The gateway's `responseCache` used by the HTTP Capability Handler stores every cacheable outbound HTTP response in an in-memory map keyed by a hash of the request, with no upper bound on the number of entries. The only mitigation is a periodic, TTL-based `DeleteExpired` sweep, which is the same architectural flaw as the zeroconf `DNSCache` bug: unbounded insertion combined with a cleanup pass that cannot keep up with a sustained flood of unique keys.

### Finding Description
`responseCache` is a plain `map[string]*cachedResponse` protected by a `sync.RWMutex`, with entries added in `Set` and inside the singleflight callback in `Fetch`: [1](#0-0) [2](#0-1) 

Cache keys are `req.Hash()`, computed from method, URL, headers, body, and workflow owner (per the module's own documentation): [3](#0-2) 

There is no `maxCacheSize`/capacity check anywhere in `response_cache.go`. Entries are only ever removed by `DeleteExpired`, which is invoked on a periodic interval (`CleanUpPeriodMs`, default 10 minutes): [4](#0-3) [5](#0-4) 

This is a direct architectural analog to the zeroconf `DNSCache._async_add` bug: unbounded insertion into a map, protected only by a periodic TTL sweep that can't outpace an insertion flood, with no per-entry or total-entry cap.

Contrast this with the sibling cache in the same package tree, `core/services/gateway/handlers/common/requestcache.go`, which enforces a hard `maxCacheSize` and rejects new entries once full: [6](#0-5) 
This shows the codebase already has the correct mitigation pattern elsewhere, but it was not applied to `response_cache.go`.

Reachability: outbound HTTP action requests are generated by DON nodes executing a workflow's own logic (URL, headers, body, and `CacheSettings.Store`) on behalf of a workflow owner — an unprivileged, non-operator actor who merely deploys/authors a CRE workflow. `makeOutgoingRequest` unconditionally calls `responseCache.Set` (or `Fetch` with `storeOnFetch=true`) for every distinct outbound request whenever `CacheSettings.Store` is true, with no cap on how many distinct cache keys a single workflow owner (or many owners) can generate: [7](#0-6) 

### Impact Explanation
A workflow author (or a small set of colluding/careless workflow owners — no operator or node-compromise privilege required) can cause the gateway process to accumulate an unbounded number of cached HTTP responses by issuing HTTP actions with `CacheSettings.Store=true` and varying request parameters (URL query strings, headers, body) fast enough that cleanup (bounded to once per `CleanUpPeriodMs`, default 10 minutes) cannot keep the map size in check. This grows heap memory linearly with request volume and eventually leads to OOM of the gateway process, which is shared infrastructure serving the whole DON — denial of service for all workflows routed through that gateway, matching the CWE-400/CWE-770 classification of the referenced advisory.

### Likelihood Explanation
Likely, since it requires only the ability to submit HTTP action capability requests as a workflow owner — a standard, unprivileged capability of any onboarded CRE user — with no rate limit on the number of *distinct* cache keys (only global/per-node/per-owner request-rate limiters exist, which throttle request rate but not accumulated unique cache-entry count over time).

### Recommendation
Add a hard cap (`maxEntries`) to `responseCache`, evicting the oldest/least-recently-used entry (or rejecting the `Set`) once the cap is reached, following the same pattern already used in `core/services/gateway/handlers/common/requestcache.go` (`maxCacheSize`). Alternatively, switch to a bounded LRU cache implementation and/or reduce `CleanUpPeriodMs` to shrink the exposure window, but a hard entry cap is the primary fix since TTL-only cleanup does not bound peak memory under flood.

### Proof of Concept
1. Onboard/author a workflow that issues HTTP action requests with `CacheSettings.Store = true` and a monotonically varying query parameter or header value on each invocation (e.g., `?nonce=<uuid>`).
2. Trigger the workflow repeatedly (or run many parallel workflow executions) so that `makeOutgoingRequest` → `responseCache.Set` inserts a new, unique-hash entry into `gatewayHandler.responseCache.cache` for each request: [8](#0-7) 
3. Sustain this faster than the 10-minute default `DeleteExpired` sweep can reclaim entries; the `cache` map grows unbounded, consuming increasing gateway memory until the process is OOM-killed or GC pauses degrade unrelated gateway traffic.

func (rc *responseCache) Set(req gateway.OutboundHTTPRequest, response gateway.OutboundHTTPResponse) {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	if isCacheableStatusCode(response.StatusCode) && rc.isExpiredOrNotCached(req) {
		rc.cache[req.Hash()] = &cachedResponse{
			response: response,
			storedAt: time.Now(),
		}
	}
}

func (rc *responseCache) DeleteExpired(ctx context.Context) int {
	rc.cacheMu.Lock()
	defer rc.cacheMu.Unlock()
	now := time.Now()
	var expiredCount int
	for key, cachedResp := range rc.cache {
		if now.After(cachedResp.storedAt.Add(rc.ttl)) {
			delete(rc.cache, key)
			expiredCount++
		}
	}
	rc.lggr.Debugw("Removed expired cached HTTP responses", "count", expiredCount, "remaining", len(rc.cache))
	rc.metrics.IncrementCacheCleanUpCount(ctx, int64(expiredCount), rc.lggr)
	rc.metrics.RecordCacheSize(ctx, int64(len(rc.cache)), rc.lggr)
	return expiredCount
}

type requestCache[T any] struct {
	cache        map[globalID]*pendingRequest[T]
	maxCacheSize uint32
	timeout      time.Duration
	mu           sync.Mutex
}

type globalID struct {
	sender string
	id     string
}

type pendingRequest[T any] struct {
	handlers.Callback
	responseData *T
	timeoutTimer *time.Timer
	mu           sync.Mutex
}

func NewRequestCache[T any](timeout time.Duration, maxCacheSize uint32) RequestCache[T] {
	return &requestCache[T]{cache: make(map[globalID]*pendingRequest[T]), timeout: timeout, maxCacheSize: maxCacheSize}
}

func (c *requestCache[T]) NewRequest(lggr logger.Logger, request *api.Message, callback handlers.Callback, responseData *T) error {
	if request == nil {
		return errors.New("request is nil")
	}
	if responseData == nil {
		return errors.New("responseData is nil")
	}
	key := globalID{request.Body.Sender, request.Body.MessageID}
	c.mu.Lock()
	defer c.mu.Unlock()
	_, ok := c.cache[key]
	if ok {
		return errors.New("request already exists")
	}
	if len(c.cache) >= int(c.maxCacheSize) {
		return errors.New("request cache is full")
	}
