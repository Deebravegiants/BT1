### Title
Unchecked division-by-zero panic in AMM swap/pnl math causes transaction abort and pool-wide denial of service - (File: `program/src/math.rs`, `program/src/processor.rs`)

### Summary
CVE-2018-12108 describes a crash (`SIGFPE`) caused by an unvalidated arithmetic path in Dropbox Lepton's `validateAndCompress`, where attacker-influenced input reaches a division/modulo operation without a zero-denominator check. The analogous bug class — reachable, attacker-influenced divisions guarded only by `.unwrap()` rather than validated non-zero denominators — is present throughout the AMM's core swap and pnl-accounting math, reachable directly from the four public swap instructions and from `Deposit`/`Withdraw`.

### Finding Description
`Calculator::swap_token_amount_base_in` divides by a pool-reserve-derived denominator with a bare `.unwrap()` and no prior zero check: [1](#0-0) 

Both swap directions compute `denominator` from live pool reserves (`total_coin_without_take_pnl` / `total_pc_without_take_pnl`) plus `amount_in`, then immediately call `.checked_div(denominator).unwrap()`. In `process_swap_base_in`, the check that `swap.amount_in != 0` happens *after* this division is executed: [2](#0-1) 

`total_coin_without_take_pnl`/`total_pc_without_take_pnl` are derived by subtracting `amm.state_data.need_take_pnl_pc/coin` from the live vault balances: [3](#0-2) 

If either of these reserve values reaches zero (e.g., a vault whose entire balance is already earmarked as `need_take_pnl_*`, or a nearly-drained side of the pool) and `swap.amount_in == 0` is supplied by an attacker, `denominator` becomes `0`, and `checked_div(0).unwrap()` panics — an unhandled arithmetic exception directly analogous to the CVE's SIGFPE-on-malformed-input pattern. The same denominator-from-reserves-with-`.unwrap()` pattern recurs in `swap_token_amount_base_out`: [4](#0-3) 

A second, more consistently reachable instance is `Processor::calc_take_pnl`, invoked from `Deposit`, `Withdraw`, and `WithdrawPnl` — all instructions callable by any user (LP or pool creator) with attacker-influenced timing/state: [5](#0-4) 

Here `y2 = x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` divides by `x1` (the normalized `total_pc_without_take_pnl`) with no zero-guard. `x1`/`y1` come from the same subtraction-based reserve calculation shown above, so any pool state where the pc (or coin) side of the reserve nets to zero — a state not explicitly forbidden anywhere in `Deposit`/`Withdraw`/`WithdrawPnl` — turns every subsequent call into a guaranteed panic.

### Impact Explanation
A panic inside an on-chain Solana program causes the transaction to abort, but more importantly, once the pool's on-chain state reaches the zero-reserve condition (whether through legitimate fee accrual to `need_take_pnl_*`, edge-case withdrawals, or repeated small-amount interactions), **every future call to `Deposit`, `Withdraw`, `WithdrawPnl`, or either swap instruction against that pool will unconditionally panic**, because the divisor is recomputed from the same persistent, poisoned state each time. This permanently freezes all LP and swapper funds locked in the vaults — no instruction path exists to reset `need_take_pnl_pc/coin` or the reserve state once it triggers the panic. This satisfies the "permanent freezing of user or LP funds" bar without requiring any privileged signer, malicious validator, or off-chain component.

### Likelihood Explanation
The `amount_in == 0` swap path is trivially reachable by any unprivileged swapper in a single transaction with attacker-chosen instruction data (`swap.amount_in = 0`), since the zero-amount validation in `process_swap_base_in` occurs strictly after the vulnerable division. The zero-reserve precondition (`total_pc_without_take_pnl == 0` or `total_coin_without_take_pnl == 0`) is state-dependent and I could not fully confirm from the available code whether normal fee/pnl accrual alone can naturally drive a reserve to exactly zero versus requiring an already-degenerate pool (e.g., one created with extreme decimal/fee parameters or already near-drained). This is the main uncertainty in the analysis — a full confirmation would require tracing all `need_take_pnl_pc/coin` accrual paths and initialization bounds across `Initialize2`/`SetParams`, which I was not able to fully audit within available context.

### Recommendation
Replace bare `.unwrap()` calls on `checked_div` in `Calculator::swap_token_amount_base_in`, `swap_token_amount_base_out`, and `Processor::calc_take_pnl` with explicit zero-denominator checks that return `AmmError::CheckedDivOverflow` (already defined) instead of panicking, and move the `swap.amount_in == 0` / `swap.amount_out == 0` validation in `process_swap_base_in`/`process_swap_base_out` to occur *before* any division is performed on reserve-derived denominators.

### Proof of Concept
1. Identify or drive a pool into a state where `total_coin_without_take_pnl` (or `total_pc_without_take_pnl`) computed by `Calculator::calc_total_without_take_pnl_no_orderbook` equals `0` (vault balance fully consumed by `amm.state_data.need_take_pnl_coin`/`pc`).
2. Submit a `SwapBaseIn` instruction with `amount_in = 0` and a valid `swap_direction` matching the zero-reserve side.
3. `swap_in_after_deduct_fee` evaluates to `0`; `Calculator::swap_token_amount_base_in` computes `denominator = total_coin_without_take_pnl.checked_add(0) = 0`, then `checked_div(0).unwrap()` panics, aborting the transaction.
4. Because the pool state persists, the same panic recurs on every future swap/deposit/withdraw attempt against that pool, permanently denying access to pooled funds.

        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }
