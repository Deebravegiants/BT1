### Title
Biometric Self-Custody Face Frame Selection Uses Highest-Score-Wins Logic Without Binding to the Actual Iris-Scanned Identity, Enabling Cross-Person Face Misattribution in a Signup - (File: src/plans/biometric_capture/mod.rs)

### Summary
The reported Anchor Governance bug is a class of "checkpoint vs. later-mutated state" flaw: a decision is locked in at one point in time (the poll snapshot), but the value actually used to compute influence is continually mutated afterward by unprivileged actors, letting late actions disproportionately/incorrectly dominate the final outcome. The orb-core `biometric_capture::Plan::handle_face_identifier` handler exhibits the same structural weakness: the face image that becomes the authoritative "self-custody" identity record for a signup is not fixed at any checkpoint tied to the iris capture, but is continuously overwritten by whichever RGB frame achieves the highest validity score at any point during the multi-second, two-eye capture window — with no check that it belongs to the same person whose iris was actually scanned.

### Finding Description
In `src/plans/biometric_capture/mod.rs`, `handle_face_identifier` maintains `self.self_custody_candidate_rgb` and replaces it any time a new frame's score exceeds the previous best: [1](#0-0) 

This "highest score wins" comparison spans the *entire* capture session — both the left-eye and right-eye objectives — as shown by the `Plan` struct holding a single `self_custody_candidate_rgb` slot that is not reset per-objective, and by `into_capture()` simply taking whatever frame is stored at the end: [2](#0-1) 

The only "checkpoint" establishing who should be enrolled is the one-time `detect_face` call at the very start of `biometric_capture`, before iris scanning begins: [3](#0-2) 

After that single check, nothing re-verifies that later RGB frames used to update `self_custody_candidate_rgb` (or the iris/IR frames themselves) belong to the same physical person. The resulting face frame is passed straight into the pipeline and ultimately encrypted and uploaded as the user's `face_identifier_bundle` / self-custody thumbnail and embeddings, bound to the `signup_id` and to the iris data captured in the same session: [4](#0-3) [5](#0-4) 

Because the "winning" frame is selected purely by a floating validity/quality score with no temporal binding to the iris-capture identity, and no identity-consistency check across all admitted frames, a second person who briefly enters/dominates the camera view late in the ~two-eye capture window (e.g. leaning in with better lighting/angle) can have their face score higher and become the frame that gets encrypted and uploaded as the signup's face identity — even though the iris codes in the same package belong to a different individual.

### Impact Explanation
This is directly analogous to the governance "snapshot vs. late stake" issue: the authoritative decision (which face representation is bound to the signup) is not fixed at the point that should define it (iris-identity capture start) but is instead continuously mutated by whichever un-vetted input arrives with a favorable score later in the same window. The concrete impact is a **cross-signup biometric data / misattribution issue**: a bystander's or second, unprivileged participant's raw face image and face embeddings can be captured, encrypted, and uploaded as part of another person's signup package without that second person's consent or knowledge, and the enrolled user's personal custody package can end up containing face biometric data that does not correspond to their own iris codes.

### Likelihood Explanation
No privileged access is required — any person physically present during a normal, unprivileged signup flow (e.g., a bystander leaning into frame near the end of the roughly multi-second two-eye capture routine) can trigger the override, since `handle_face_identifier` accepts and can promote any RGB frame that passes `IsValidImage` with a higher score, regardless of source or timing relative to the iris capture.

### Recommendation
Bind the self-custody face selection to the same identity checkpoint used for the iris capture: e.g., freeze/lock the candidate as soon as the last iris objective for both eyes is captured (rather than allowing continuous override across the whole session), and/or add a face-identity consistency check (e.g. face embedding similarity) between all admitted frames within a single capture session before allowing an override, rejecting frames whose embedding diverges materially from the previously accepted candidate/detected face.

### Proof of Concept
1. Start a signup; `detect_face` passes for User A, and both eyes begin being scanned.
2. During the capture window (before the last objective completes), User B leans into the camera's field of view momentarily with better lighting/angle than User A had, producing an `IsValidImage` output with a higher `score` than the currently stored candidate.
3. `handle_face_identifier` (src/plans/biometric_capture/mod.rs:301-317) overwrites `self.self_custody_candidate_rgb` with User B's frame because `output.score > highest`, with no check that this frame corresponds to the same identity as User A's already-captured iris frames.
4. The capture completes with User A's iris codes but User B's face frame in `Capture.face_self_custody_candidate`.
5. This frame flows into `biometric_pipeline` and `build_pcp`, and is encrypted/uploaded as part of User A's `signup_id` personal custody package (`src/plans/mod.rs:1668-1691`, `src/plans/personal_custody_package.rs:299-306`), resulting in User B's face biometric data being disclosed and misattributed to User A's signup.
