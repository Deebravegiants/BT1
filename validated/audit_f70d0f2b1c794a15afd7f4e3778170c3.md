## Title
`WrappedHyperFungibleToken.send()` locks `params.amount` but dispatches the pre-fee amount for fee-on-transfer underlying tokens - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` pulls the underlying ERC20 via `safeTransferFrom` without measuring the actual amount received, yet dispatches a cross-chain message that commits to the full `params.amount`. If the underlying token charges a transfer fee, the wrapper receives less than `params.amount`, but the peer wrapper on the destination chain unlocks the full, unadjusted `message.amount` to the beneficiary, creating a shortfall in the locked-collateral pool.

### Finding Description

There is no balance-before/balance-after check, so `params.amount` is trusted as the actual amount locked, even though for a fee-on-transfer token the wrapper's balance only increases by `params.amount - fee`. This unadjusted `params.amount` is then embedded in the dispatched message body: [2](#0-1) 

On the destination chain's peer `WrappedHyperFungibleToken`, `onAccept` unlocks the full `message.amount` to the beneficiary without any cross-check against what is actually backed by locked collateral: [3](#0-2) 

The same unguarded pattern is duplicated in `WrappedHyperFungibleTokenUpgradeable.sol`'s `send()`/`onAccept()`.

This is the exact bug class described in the external report: a token-transferring entry point doesn't account for fee-on-transfer deductions, so downstream accounting (here, the amount unlocked cross-chain) diverges from the true collateral actually held. Notably, the sibling app `evm/src/apps/IntentGatewayV2.sol` already defends against this by snapshotting `balanceOf` before/after `safeTransferFrom` and mutating `order.inputs[i].amount` to the actually-received value (see `evm/src/apps/IntentGatewayV2.sol:319-323` and the dedicated foundry tests `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`), confirming the codebase is aware of this class of issue but the fix was not applied to `WrappedHyperFungibleToken`.

### Impact Explanation
Each `WrappedHyperFungibleToken` deployment acts as a bidirectional lock/unlock pool for its underlying token on that chain: inbound `send()` calls lock collateral, and `onAccept()` calls (triggered by transfers originating from the peer chain) unlock collateral from that same pool. If the underlying is a fee-on-transfer token, every `send()` under-collateralizes the pool relative to the amount promised in the cross-chain message. As payments accumulate, the pool balance will fall short of the aggregate amounts other users are entitled to unlock, leading to reverting/failed unlocks for legitimate recipients (frozen funds) once the pool is drained, exactly mirroring the Alice/Bob scenario in the original report. This is unauthorized value creation from the perspective of the destination chain (unlocking more than is actually escrowed) and a freezing-of-funds risk for later recipients.

### Likelihood Explanation
This requires only that the token owner configures `WrappedHyperFungibleToken.configure()` with a fee-on-transfer ERC20 as `_underlying` — a normal, permissionless configuration choice for any project wrapping such a token (deflationary/tax tokens are common in the wild). Any unprivileged user calling `send()` triggers the shortfall; no special privileges, timing, or race conditions are needed.

### Recommendation
Mirror the fix already used in `IntentGatewayV2.placeOrder`: measure the wrapper's `balanceOf` before and after `safeTransferFrom`, and use the actual received delta (not `params.amount`) both for the locked collateral and for the amount embedded in the dispatched message body. Apply the same fix in `WrappedHyperFungibleTokenUpgradeable.sol`.

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` = a fee-on-transfer token (e.g., 10% fee) on chain A and its peer wrapper on chain B.
2. Alice calls `send({ amount: 1000, to: Bob, dest: chainB, ... })`. `safeTransferFrom` moves 1000 nominal but the wrapper's balance only increases by 900 (chain A pool now short by 100).
3. `_buildDispatchPost` still encodes `amount: 1000` in the ISMP message.
4. On chain B, `onAccept` unlocks 1000 tokens to Bob from chain B's pool — 100 more than chain A ever actually collateralized for this transfer.
5. Repeating this accumulates an unbacked deficit; eventually a legitimate unlock call on either side reverts due to insufficient balance, freezing funds for the affected recipient. [4](#0-3)

        bytes memory dest = _supportedChains[params.dest];
        if (dest.length == 0) revert UnsupportedChain();

        bytes memory body = abi.encode(HyperFungibleToken.Message({
            from: abi.encodePacked(msg.sender),
            to: params.to,
            amount: params.amount,
            data: params.data
        }));

            dest: params.dest,
            to: dest,
            body: body,
            timeout: params.timeout,
            fee: params.relayerFee,
            payer: msg.sender
        });

    function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
        }

        DispatchPost memory request = _buildDispatchPost(params);
        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }

    /**
     * @notice Handles incoming cross-chain token transfer messages
     * @dev Called by the ISMP host when a POST request is received. Verifies the source
     * address matches the configured contract for that chain, then transfers the underlying
     * ERC20 to the recipient. If calldata is present, executes it via the CallDispatcher.
     * @param incoming The incoming POST request containing the token transfer message
     */
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
