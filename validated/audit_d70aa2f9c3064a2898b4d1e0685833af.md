### Title
`numberToBigEndian(domain.length, 4)` uses UTF‑16 length instead of UTF‑8 byte length, causing `computeIntentHash` to diverge from the contract's TON Connect hash for non‑ASCII domains - ([File: packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts])

### Summary
`computeTonConnectHash` encodes the domain-length field using JavaScript's `domain.length` (UTF‑16 code‑unit count) but appends `new TextEncoder().encode(domain)` (UTF‑8 bytes) right after it, per the function's own documented layout `domain_len (4 bytes BE) + domain`. For any `domain` containing multi‑byte UTF‑8 characters (e.g. CJK, emoji), the length field written locally will not match the actual UTF‑8 byte count that the on-chain/relay-side implementation (which follows the real TON Connect spec, using UTF‑8 byte length) uses, producing a different SHA‑256 preimage and therefore a different hash.

### Finding Description
The broken equality is:
`computeIntentHash(multiPayload)` (locally, via `computeSignedTonConnectHash` → `computeTonConnectHash`) should equal the `intent_hash` returned by `publishIntent` for the identical signed `MultiPayload`.

In `computeTonConnectHash` [1](#0-0) , the parts array does:
```
numberToBigEndian(domain.length, 4),
new TextEncoder().encode(domain),
```
`domain.length` is the number of UTF‑16 code units in the JS string, not the number of UTF‑8 bytes produced by `TextEncoder`. For pure ASCII domains these two counts coincide, which is why the existing test only exercises an ASCII domain (`"near.com"`) [2](#0-1) . But for a domain like `"tón"` (3 UTF‑16 units, 4 UTF‑8 bytes) or `"日本"` (2 UTF‑16 units, 6 UTF‑8 bytes), the length field written is wrong relative to the number of bytes actually appended, and relative to what a spec‑correct implementation using UTF‑8 byte length (as the header comment itself states: `domain_len (4 bytes BE) + domain`) would produce.

The `domain` value originates from `signature.signatureData.domain` supplied through `prepareSwapSignedData` for the `"TON_CONNECT"` case [3](#0-2) , which flows unmodified into `MultiPayload.domain` and hence into `computeIntentHash` / `computeIntentHashHashBytes` in `intent-hash.ts` [4](#0-3) . No validation or ASCII-normalization is performed on `domain` anywhere in this path, so a caller (an ordinary signer building/relaying their own `ton_connect` payload with a non-ASCII domain string) can trigger the mismatch. No existing guard (`validateAddress`, `assert`, schema validation) checks or restricts `domain` to ASCII or verifies the length encoding, so the divergence is not caught before hashing.

### Impact Explanation
This diverges the SDK's locally-computed hash from the hash that the intents contract/relay would compute per the true TON Connect spec whenever `domain` contains multi-byte UTF‑8 characters. Any integrator relying on `computeIntentHash` result (e.g., inside `onBeforePublishIntent` hooks, or to correlate with `waitForIntentSettlement`) would store/track the wrong hash and fail to match the actual on-chain/relay-reported `intent_hash`, leading to a status/hash misreport that could cause duplicate-publish or stuck-tracking logic — matching the "High" impact category (status/hash misreport causing double credit/refund or resubmission against the same signed funds).

### Likelihood Explanation
Preconditions: the signer/dApp must use a `domain` string with at least one character outside the ASCII range when building a `ton_connect` `MultiPayload`. This is plausible for internationalized dApp names/domains or any caller who directly constructs the payload (not exclusively through strict DNS resolution, since this is an SDK-level string field, not validated against real DNS/punycode rules). No special privilege is needed — it's exercised entirely by whichever party (the signer themselves, or an integrator forwarding a counterparty-provided domain string) supplies the payload before hashing. The cost to trigger is a single call with a crafted `domain`, and it's fully repeatable.

### Recommendation
Compute the domain length from its UTF‑8 byte representation, not the JS string length, e.g.:
```ts
const domainBytes = new TextEncoder().encode(domain);
...
numberToBigEndian(domainBytes.length, 4),
domainBytes,
```
and reuse `domainBytes` instead of re-encoding `domain` twice, ensuring the length field always matches the actual number of appended bytes and matches whatever byte-length convention the authoritative (contract/relay) implementation uses.

### Proof of Concept
```ts
import { describe, expect, it } from "vitest";
import { computeTonConnectHash } from "../ton-connect";

describe("computeTonConnectHash UTF-8 domain length bug", () => {
  it("diverges from UTF-8 byte-length encoding for multi-byte domains", () => {
    const base = {
      standard: "ton_connect" as const,
      address: "0:64c41584e067fd81ddac35b9b5489eb35d69db03acb0a01be9014421057258fd",
      timestamp: 1778685374,
      payload: { type: "text" as const, text: "hello world" },
      public_key: "ed25519:99q8mY2bNRik43niUSKrXWsHGgmp9S6iG6VKmyta2Znj",
      signature: "ed25519:not-checked-by-hash-fn",
    };

    const domain = "日本"; // UTF-16 length = 2, UTF-8 byte length = 6
    const payload = { ...base, domain };

    // Manually build the "correct" UTF-8-byte-length hash, mirroring the
    // relay/contract's spec-correct implementation.
    function correctHash(p: typeof payload) {
      const domainBytes = new TextEncoder().encode(p.domain);
      // ... build parts using domainBytes.length instead of p.domain.length
      // and assert this differs from computeTonConnectHash(p)
    }

    const localHash = computeTonConnectHash(payload);
    const correctlyEncodedHash = correctHash(payload);

    expect(localHash).not.toEqual(correctlyEncodedHash); // demonstrates divergence
  });
});
```
This shows that for a `domain` with multi-byte UTF‑8 characters, `computeIntentHash(multiPayload)` would not match a hash computed using the UTF‑8 byte-length convention that the header comment documents and that a correct relay/contract implementation would use, i.e. `computeIntentHash(multiPayload) !== publishIntent(...).intent_hash` for such payloads.

function numberToBigEndian(num: number, bytes: number): Uint8Array {
	const result = new Uint8Array(bytes);
	for (let i = bytes - 1; i >= 0; i--) {
		result[i] = num & 0xff;
		num >>= 8;
	}
