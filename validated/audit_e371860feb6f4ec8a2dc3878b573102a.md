### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `Utils::HmacValidator.validate` in `Registry.process` only proves that the raw body was signed with the app's shared `api_secret_key` [2](#0-1) . The `shop` value read from the `x-shopify-shop-domain`/`shopify-shop-domain` header [3](#0-2)  is never included in the signed content, yet it is trusted and forwarded directly into `WebhookMetadata` for tenant-scoped processing [4](#0-3) .

### Finding Description
The binding that should hold is: `shop asserted in the header == shop that the HMAC-signed body actually originated from`. Because `api_secret_key` is a single app-wide secret shared across every shop that has installed the app (it is not shop-specific), any merchant who installs the app on their own store is a valid "signer" for the HMAC — they can trivially obtain genuine `(raw_body, hmac)` pairs for their own shop by simply receiving a real webhook. Since the header carrying the shop identity (`x-shopify-shop-domain`) is parsed by `Request#shop` [3](#0-2)  but is completely absent from `to_signable_string` [1](#0-0) , an attacker (an unprivileged internet user who merely installed the app on their own dev/test store, which is normal, unprivileged access to any public Shopify app) can:

1. Register/receive a legitimate webhook for their own shop and capture the valid `raw_body` + `x-shopify-hmac-sha256` value.
2. Replay that exact HTTP request to the app's webhook endpoint, but with the `x-shopify-shop-domain` header rewritten to a victim shop's domain.
3. `Utils::HmacValidator.validate` in `Registry.process` still passes, because it only recomputes the HMAC over `raw_body` [5](#0-4) , and `Registry.process` then dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` to the app's handler using the forged shop value [4](#0-3) .

The application-level handler, trusting that `shop` was authenticated by the gem's HMAC check, will process/store the attacker's own webhook body as if it belongs to the victim tenant, crossing the tenant boundary the gem is expected to enforce for webhook processing.

### Impact Explanation
This breaks tenant isolation: an attacker can make the app record/act on data under an arbitrary victim shop identifier, despite only having their own shop's install and a valid signature for their own payload. Depending on how the consuming application keys its per-shop data on `WebhookMetadata#shop` (which is the gem's documented, intended usage pattern per `docs/usage/webhooks.md`), this can lead to cross-tenant data corruption/injection — classified as **Critical – cross-tenant access** per the rubric, since the only "credential" needed (the app's `api_secret_key`) is not shop-scoped and the attacker never needs to see it; they only need a genuine payload from their own tenant.

### Likelihood Explanation
Likelihood is high for any app that has more than one shop connected (any public/multi-tenant app). Obtaining a self-shop webhook is normal usage (install the app on a free dev shop, trigger an order/product event). Forging the header and replaying via a raw HTTP client (curl) requires no special access, no leaked secrets, and no privileged account — it exactly matches the "unprivileged internet user" threat model in scope.

### Recommendation
Do not trust `x-shopify-shop-domain` as an authenticated tenant identifier from the webhook payload alone. Either:
- Bind the shop value into the material that is verified against the app-level record (e.g., cross-check `request.shop` against the shop that owns the currently-active webhook subscription/registration id via a server-side lookup) before calling the handler, or
- If Shopify's API supported it, include the shop in the signed content; since it does not, `Registry.process`/consuming apps must independently verify that `request.shop` is a shop with an active install/session for this app before trusting `WebhookMetadata#shop`, rather than treating a passing `HmacValidator.validate` as proof of the shop's identity.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker-shop.myshopify.com`; trigger any subscribed topic (e.g., `orders/create`) to receive a genuine webhook POST with headers `x-shopify-hmac-sha256: <valid>` and `x-shopify-shop-domain: attacker-shop.myshopify.com` and some `raw_body`.
2. Replay the identical request to the app's webhook endpoint, changing only the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-hmac-sha256: <same valid value from step 1>
   (same raw_body)
   ```
3. `Utils::HmacValidator.validate(request)` returns `true` (it only checks `raw_body` against the secret) [6](#0-5) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` [4](#0-3) , so the application processes attacker-controlled data under the victim tenant's identity.
