ERC721/ERC1155 tokens are entirely outside this accounting model.### Title
Any NFT held by Emporium after a CASE 2 op can be stolen by any unrelated attacker via a second, independent CASE 2 op - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
Emporium's CASE 2 "stateless" branch of `runAction` executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract, so `msg.sender` for that call is always the shared Emporium address, not any per-user identity. Because Hinkal's on-chain accounting (`Hinkal.sol` `_externalTransact`, `EmporiumUpgradeable.runAction` balance-diff/`handleOut`) only tracks fungible balances listed in `circomData.erc20TokenAddresses`, an ERC721/ERC1155 token sent to Emporium (e.g. minted to `address(this)` == Emporium by a victim's CASE 2 op, accepted unconditionally by `Transferer.onERC721Received`/`onERC1155Received`) is never converted into a UTXO or bound to the depositor's nullifier/proof. Any unrelated attacker can then submit their own independent `transact` with a CASE 2 op calling `IERC721(nft).transferFrom(emporium, attacker, tokenId)`, which Emporium executes as `msg.sender`, moving the NFT out with zero relation to the original depositor.

### Finding Description
Broken equality: `authorized_mover(tokenId)` should equal `account_that_produced_the_original_proof_owning_tokenId`, but in practice `authorized_mover == any address able to get Emporium to execute a CASE 2 call`, i.e. anyone.

Trace:
- `Hinkal.transact` → `_externalTransact` (contracts/Hinkal.sol lines 234-261) computes `deltaAmountChanges` and calls `IExternalActionV2(externalAddress).runAction(circomData, deltaAmountChanges)`. This loop and the accounting only iterate over `circomData.erc20TokenAddresses` — ERC721/1155 token IDs are never part of `amountChanges`, `balanceDif`, or `utxoAmount` checks in `Hinkal.sol` lines 82-130.
- `EmporiumUpgradeable.runAction` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol lines 76-150) branches on `op.invokeWallet`:
  - CASE 1 (stateful): routed through `IHinkalWallet(stack.signerAddress).callHinkalWallet`, gated by `onlyEmporium` on the per-user `HinkalWallet` and an EIP-712 signature recovered to `stack.signerAddress` (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol lines 302-349, contracts/external-actions/emporium/HinkalWallet.sol lines 21-34). This ties the call to a specific signer.
  - CASE 2 (stateless): `(success, err) = op.endpoint.call{value: op.value}(op.callData)` (line 112). The only restriction is blocking the `callHinkalWallet`/`doSendToRelay` selectors (lines 104-110) to stop CASE 2 ops from puppeteering another user's `HinkalWallet`. There is no check that ties the call, or its target/tokenId, to the specific prover who deposited an asset at Emporium.
- Only fungible balances are reconciled after CASE 2/CASE1 execution (`balancesBefore`/`balancesAfter` loop over `circomData.erc20TokenAddresses`, lines 85-150) and converted to `UTXO`s via `handleOut`. An ERC721/1155 received by Emporium (accepted via `Transferer.onERC721Received`/`onERC1155Received`, contracts/Transferer.sol lines 19-36, which unconditionally return the selector for any token/data/operator) is completely outside this reconciliation — no UTXO is minted for it, no nullifier or commitment binds it to the depositor.
- Because Emporium is a shared singleton contract (not a per-user wallet like `HinkalWallet`), any subsequent, wholly independent `transact` from any attacker — using the attacker's own valid proof/nullifiers over the attacker's own UTXOs — can include a CASE 2 op targeting `nft.transferFrom(emporium, attacker, tokenId)`. Emporium, as `msg.sender`/owner-or-approved of that NFT, executes the transfer successfully, since ERC721 `transferFrom` only checks that the caller is the token owner or approved — a check satisfied by Emporium regardless of who originally caused it to hold that token.
- `performHinkalChecks`, `verifyProof`, `rootHashExists`, and `insertNullifiers` all validate the attacker's own proof/nullifiers correctly for the attacker's own transaction; none of these checks constrain the target address, selector, or arguments encoded in `circomData.externalActionData.externalActionMetadata` for a CASE 2 op against a third party's asset, since `externalActionMetadata` is opaque to the circuit apart from its hash (`calldataHash`) being signed by the attacker over their own submission.

### Impact Explanation
Direct theft of a specific NFT (or ERC1155 balance) that ended up custodied at the Emporium contract as a side effect of a victim's stateless op, executed by any unprivileged attacker with no relation to the victim's nullifier or UTXO set. This is repeatable for every NFT/ERC1155 token type Emporium ever holds via CASE 2 interactions, and costs the attacker only their own proof-generation/gas cost. This matches the Critical category: direct theft of user funds/assets held in-flight at a Hinkal-controlled contract, with no proof/nullifier binding preventing the divergence.

### Likelihood Explanation
Preconditions: a victim (or the victim's tooling) must execute a CASE 2 Emporium op whose external call results in an NFT/ERC1155 token being sent to `address(this)` (Emporium), e.g. minting or purchasing an NFT through a marketplace/mint contract in stateless mode. Given that `Transferer.onERC721Received`/`onERC1155Received` are unconditional acceptors, any such token transfer succeeds and the asset lingers at Emporium with no accounting. The attacker only needs: (1) knowledge (on-chain, observable) that Emporium holds a specific `tokenId`, (2) their own funds to generate a valid, unrelated proof for their own `transact`, and (3) to craft a CASE 2 `EmporiumOperation` calling `transferFrom(emporium, attacker, tokenId)`. No privileged role, no relayer collusion, and no interaction with the victim's keys or nullifiers are required. This is fully attacker-controlled and repeatable for every stray token Emporium ends up holding.

### Recommendation
Do not allow arbitrary CASE 2 targets/calldata to move assets out of the shared Emporium address; either (a) forbid NFT/ERC1155 flows through CASE 2 entirely and force any op that can result in NFT receipt to run through the signer-bound `HinkalWallet` (CASE 1) instead of Emporium itself, or (b) extend the accounting model to track ERC721/ERC1155 balances/ownership per depositor (e.g. require an explicit token-id allowlist per `circomData` and verify before/after ownership matches the expected recipient bound to the prover's stealth address), or (c) have `Transferer.onERC721Received`/`onERC1155Received` reject transfers unless the mint/transfer is expected/whitelisted for the current `transact` call, preventing arbitrary tokens from resting at Emporium unaccounted for.
