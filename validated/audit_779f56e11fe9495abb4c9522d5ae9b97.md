### Title
BEEFY consensus proof verification loops over the entire signature set, permanently DoS-ing the light client once validator count grows large enough - (File: evm/src/consensus/EcdsaBeefy.sol)

### Summary
The ECDSA BEEFY consensus client verifies a relay chain finality proof by recovering a signer address and building a merkle-multiproof leaf for **every signature** in the submitted commitment, with the total required count driven by the (unbounded, governance-controlled) authority set size. This is structurally the same class of bug as TRST-H-5: gas cost of a core dispatch/verification path grows linearly with the size of a set that is expected to keep growing, and once that set is large enough the call can no longer fit in a block, permanently DOS-ing the function.

### Finding Description
`verifyMmrUpdateProof` in `EcdsaBeefy.sol` requires a 2/3+1 supermajority of `sigLen = relayProof.signedCommitment.votes.length` signatures and then, for every one of them, performs an `ECDSA.recover` and constructs a merkle-multiproof leaf in a `for` loop: [1](#0-0) 

`checkParticipationThreshold(sigLen, authoritySet.len)` ties the number of signatures that must be supplied (and thus verified) to `authoritySet.len`, the size of the relay chain's current/next validator set. There is no cap on `authoritySet.len` in this contract — it is only bounded by whatever the relay chain's own governance allows, and BEEFY/GRANDPA validator sets are designed to grow with the security budget of the chain over time.

The identical unbounded-loop pattern exists in the Rust consensus-client counterpart used by parachains, which performs one `secp256k1_recover` + `keccak256` per signature: [2](#0-1) 

The project's own documentation acknowledges that ECDSA verification cost "increases linearly with the number of validators" and describes zkBEEFY (a SNARK-based verifier) as the intended long-term fix, precisely because this cost is unbounded: [3](#0-2) 

However, `EcdsaBeefy.sol` remains a live, selectable `IConsensusV2` implementation. Whichever state machine registers this client for its BEEFY state stays permanently exposed: once the relay chain's authority set grows past the point where a 2/3+1-signature proof's `ecrecover` + merkle-proof-construction loop fits inside the EVM's per-block gas limit, `verify()` can never succeed again for that chain. This blocks all future consensus updates for that route, and by extension permanently freezes every state commitment, request/response delivery, and fund-affecting message that depends on that state machine's consensus client — a full route-level denial of service that no relayer, however honest, can work around, mirroring the way `_vote()` in the referenced report could be permanently bricked by unbounded veSatin enumeration.

### Impact Explanation
If a state machine configures `EcdsaBeefy` as its consensus client and its authority set grows large enough that the required signature count's verification (ecrecover + merkle leaf assembly, per signature) exceeds the block gas limit, `verify()` on that client permanently reverts. This makes it impossible to advance the trusted consensus state for that chain, which halts membership/non-membership proof verification for all pending and future ISMP requests/responses routed through it — freezing in-flight funds (fees, token transfers, intents) and preventing new messages from ever being delivered on that route. This is a High severity, protocol-wide route DoS once triggered, matching the impact class the mitigation section calls out ("a route unable to deliver messages").

### Likelihood Explanation
Triggering this requires no attacker action beyond ordinary chain operation — the validator set naturally grows through relay-chain governance over the life of the protocol, and the trigger condition (gas-cost of the loop exceeding block gas limit) is deterministic once the authority set crosses a fixed size threshold. Because this is entirely usage/growth-driven rather than requiring any malicious input, and the docs already flag the underlying cost as a known concern for large validator sets, the likelihood over the protocol's lifetime is realistic, though it depends on validator-set growth trends of the specific relay chain being bridged.

### Recommendation
Cap the maximum authority set size that `EcdsaBeefy` will accept per commitment (rejecting proofs from oversized sets, or requiring migration to a constant-cost verifier such as the already-designed `SP1Beefy`/zkBEEFY client before the authority set can grow past a safe bound), and/or make signature-count verification cost bounded independent of authority-set growth (e.g., BLS aggregation once available, or enforced use of the zk verifier for chains whose validator counts exceed a governance-configured ceiling).

### Proof of Concept
1. A relay chain using `EcdsaBeefy` as its Hyperbridge consensus client grows its validator/authority set to a size `N` such that `2/3*N + 1` ECDSA `ecrecover` calls plus the corresponding `MerkleMultiProof.Leaf` construction loop in `verifyMmrUpdateProof` (evm/src/consensus/EcdsaBeefy.sol:144-163) costs more gas than the chain's block gas limit.
2. Any relayer submits a validly-signed BEEFY commitment for the next finalized height; `verify()` is called via the host's consensus-update path.
3. The transaction reverts out-of-gas regardless of gas limit supplied, because it cannot fit in a block.
4. No future consensus update for this state machine can ever succeed, permanently freezing all message delivery, fee accumulation, and fund movement tied to that route.

## zkBEEFY

While BLS precompiles are not yet available on popular EVM chains, we unfortunately have to use ECDSA signatures to prove BEEFY finality. Although ECDSA signatures are cheap to verify, the number of signatures creates high verification cost and prevents frequent posting of consensus proofs for faster finality. This is because ECDSA signatures do not support aggregation, and the verification cost increases linearly with the number of validators.

A workaround for would be to leverage a SNARK circuit to perform the verification of these signatures alongside their membership proofs in the `keyset_commitment`. This effectively to amortizes the cost of verification, making it constant no matter how large the validator set grows. For this, we leverage the [barretenberg](https://github.com/AztecProtocol/barretenberg) framework by the aztec team, which is able to prove the verification of secp256k1 signatures in less than 2s. This ensures fast proving times for generating the zkBEEFY cosnensus proof.
