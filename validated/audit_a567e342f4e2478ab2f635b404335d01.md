### Title
Attacker-controlled EVM/TRON revert-reason strings are printed unsanitized to the relayer operator's terminal, enabling ANSI/terminal escape-sequence injection - (File: tesseract/messaging/evm/src/provider.rs)

### Summary
The bug class from CVE-2025-55754 (Tomcat printing unescaped ANSI sequences from attacker-influenced log messages to an administrator's console) maps directly onto Hyperbridge's Tesseract relayer: revert-reason bytes originating from an arbitrary destination module contract are decoded to UTF‑8 and written straight into `log::error!`/`tracing` output, which lands on the relayer operator's terminal (or terminal-emulating log viewer such as `docker logs`) without stripping control/escape sequences.

### Finding Description
Any account can dispatch an ISMP POST request whose destination `to` field is an arbitrary contract address on the destination chain (`modules/pallets/ismp/src/dispatcher.rs:128-145`, `docs/content/developers/polkadot/dispatching.mdx:34-77`). An attacker can deploy a malicious "module" contract at that address whose fallback/`onAccept` handler deliberately reverts with a crafted `Error(string)` payload containing ANSI/VT100 escape sequences (e.g. cursor movement, terminal title changes, or OSC 52 clipboard-write sequences — the same primitive used in the Tomcat advisory).

When the Tesseract EVM relayer verifies delivery via `debug_traceCall`/`debug_traceTransaction` (`tesseract/messaging/evm/src/provider.rs`, `CheckTraceForEventParams`), it reads `call_frame.revert_reason` (and per-frame `frame.error`) straight from the trace and logs it verbatim: [1](#0-0) [2](#0-1) 

The TRON relayer has the same pattern: `decode_revert_message` takes the hex-encoded `resMessage`/`result` field from a `TransactionInfo`, hex-decodes it, and does a raw `String::from_utf8` decode with no sanitization before logging it via `log::error!`: [3](#0-2) [4](#0-3) 

Both `tesseract-relayer`'s and the messaging relayer's logging is initialized with `tracing_subscriber::fmt()`, which writes formatted, non-JSON records straight to a terminal-attached stdout/stderr — exactly the kind of "console" the Tomcat advisory describes (interactive terminals interpret escape sequences; ANSI is not stripped anywhere in this pipeline): [5](#0-4) 

None of these code paths sanitize, escape, or strip control characters from the decoded string before it reaches the formatter/writer.

### Impact Explanation
This does not directly move funds, but it gives any unprivileged actor who can dispatch an ISMP request (i.e., essentially anyone with gas) a channel to inject arbitrary terminal escape sequences into the operational output an infrastructure operator watches (interactive SSH sessions, `docker logs -f tesseract`, tmux/screen panes, terminal emulators supporting OSC 52 clipboard write, etc.). As in the referenced CVE, this can be used to overwrite the visible prompt, hide/alter subsequent log lines, or place attacker-chosen text into the operator's clipboard in hopes the operator pastes and runs it — a social-engineering vector against relayer operators who run privileged commands (key management, `withdraw`, config edits) directly from that same terminal. Given relayer operators typically hold hot keys used for on-chain fee withdrawal and message submission, tricking them into running an injected command is a credible path to key/fund compromise, satisfying the "unauthorized app action" bar even though the injection itself is not a protocol-level fund primitive.

### Likelihood Explanation
Likelihood is Medium: triggering the log line only requires deploying a cheap malicious contract as an ISMP destination module and getting any message routed to it (an attacker fully controls this, no relayer cooperation needed), and the revert-reason contents are entirely attacker-chosen ABI-encoded bytes decoded straight into the log message. The main mitigating factors are that (a) it requires the operator to be actively watching an interactive terminal that renders ANSI sequences (not all `docker logs` consumers do), and (b) it's a social-engineering primitive rather than a fully automated exploit, unlike the direct fund-loss paths this program otherwise scores highest.

### Recommendation
Sanitize/strip ANSI escape and other control sequences (or hex-escape non-printable bytes) from any UTF‑8-decoded external data — particularly EVM `revert_reason`/`frame.error` in `tesseract/messaging/evm/src/provider.rs` and the TRON `decode_revert_message` result in `tesseract/messaging/tron/src/tx.rs` — before passing it to `log::error!`/`tracing`. A shared helper (e.g. filtering to a printable-ASCII/whitelist charset or using a crate like `strip-ansi-escapes`) should wrap all revert-reason and other externally-sourced string fields before they are interpolated into log macros anywhere in the Tesseract relayer crates.

### Proof of Concept
1. Deploy a malicious "module" contract on an EVM destination chain whose fallback reverts with `revert("\x1b]52;c;<base64-clipboard-payload>\x07Fake status: OK")` (an OSC 52 clipboard-write sequence followed by benign-looking text).
2. Dispatch any ISMP POST request from a source chain/pallet with `to` set to this contract's address (e.g. via `pallet-ismp`'s `dispatch_request`, `modules/pallets/ismp/src/dispatcher.rs:92-151`, or `HyperFungibleToken::send`, `modules/pallets/hyper-fungible-token/src/lib.rs:241-315`, with `call_data`/`recipient` steering execution into the attacker contract).
3. Once the relayer submits the delivery transaction and it reverts inside the callback, `check_trace_for_event` in `tesseract/messaging/evm/src/provider.rs:797-804` extracts `call_frame.revert_reason` and logs it verbatim via `log::error!`.
4. An operator watching the relayer's `tracing_subscriber::fmt()` terminal output (`tesseract/messaging/relayer/src/logging.rs:19-25`) has the escape sequence rendered by their terminal, silently overwriting their clipboard/prompt with attacker-controlled content.

/// Try to decode a human-readable revert reason from a failed transaction.
fn decode_revert_message(info: &TransactionInfo) -> String {
	log::trace!(target: crate::LOG_TARGET, "decode_revert_message for tx {}", info.id);
	log::trace!(target: crate::LOG_TARGET, "res_message: {:?}", info.res_message);
	log::trace!(target: crate::LOG_TARGET, "result: {:?}", info.result);

	let decoded = info
		.res_message
		.as_deref()
		.and_then(|hex_msg| {
			log::trace!(target: crate::LOG_TARGET, "Attempting to decode hex res_message: {}", hex_msg);
			hex::decode(hex_msg).ok()
		})
		.and_then(|bytes| {
			log::trace!(target: crate::LOG_TARGET, "Attempting UTF-8 decode of {} bytes", bytes.len());
			String::from_utf8(bytes).ok()
		})
		.unwrap_or_else(|| {
			let fallback = info.result.clone().unwrap_or_else(|| "unknown error".into());
			log::trace!(target: crate::LOG_TARGET, "Using fallback revert message: {}", fallback);
			fallback
		});

	log::trace!(target: crate::LOG_TARGET, "Decoded revert message: {}", decoded);
	decoded
}
