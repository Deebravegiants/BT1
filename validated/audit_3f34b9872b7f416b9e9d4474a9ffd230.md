### Title
Unsigned `circomData.relay`/`feeStructure` lets an executor redirect and inflate wallet-signed Emporium fees - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
The EIP-712 message a `HinkalWallet` owner signs for an Emporium action (`EMPORIUM_SIGNATURE_TYPEHASH`) binds only `emporiumMessage`, the ops hash, `maxFee`, and `deadline` — it never binds `circomData.relay`, `circomData.feeStructure.feeToken`, or `circomData.feeStructure.variableRate`. Any unprivileged party who obtains a validly-signed `EmporiumStack` (the intended executor/relay for that stack) can replay it inside a self-crafted `Hinkal.transact` call with an arbitrary `circomData.relay` and `feeStructure`, causing `HinkalWallet.doSendToRelay` to push a `flatFee`-sized payment, denominated in whatever token the attacker chooses and paid to whatever address the attacker chooses, directly out of the signer's wallet.

### Finding Description
The claimed equality is: *(fee token, fee amount, fee recipient) actually paid from the signer's wallet == (fee token, fee amount, fee recipient) the owner's EIP-712 signature authorised*. Tracing the code shows this equality is not enforced.

`verifyWallet` recomputes and checks the signature over exactly:
```
EMPORIUM_SIGNATURE_TYPEHASH(emporiumMessage, hash(ops), maxFee, deadline)
``` [3](#0-2) 
and the *only* fee-related guard is `circomData.feeStructure.flatFee > stack.maxFee → revert FeeExceedsSignedMax()` — a bare numeric comparison with no token identity check [4](#0-3) . `circomData.relay` and `circomData.feeStructure` are never included in the hashed message and are never validated against the wallet owner's intent anywhere else in `verifyWallet`.

In `runAction`, after the signed `ops` are executed, `payRelayFees` is called with the caller-supplied `circomData` [5](#0-4) . For the signed-wallet case (`signerAddress != address(0)`), `relayFee = flatFee` — the raw numeric value bound only by `maxFee`, with no constraint on which `erc20TokenAddress` it is denominated in, since `isFeeToken` is simply `erc20TokenAddress == feeStructure.feeToken` for whatever `feeStructure` the caller supplied [6](#0-5) . The payment is then dispatched via `payRelay` → `sendToRelayFromWallet` → `IHinkalWallet(signerAddress).doSendToRelay(relay, relayFee, feeToken)` [7](#0-6) .

`HinkalWallet.doSendToRelay` is gated only by `onlyEmporium`, i.e. it fully trusts whatever `relay`, `amount`, and `erc20TokenAddress` the Emporium contract passes, and transfers that amount directly out of the wallet's own balance [1](#0-0) . Since `circomData` (including `relay` and `feeStructure`) is supplied by whoever calls `Hinkal.transact`/`_externalTransact` and is only constrained by that caller's own ZK proof (via `calldataHash`/`getHashedCalldata`, which commits `circomData.relay` and `circomData.feeStructure` as public inputs of the *caller's* proof, not the wallet-owner's signature) [8](#0-7) , the circuit constrains internal consistency of the prover's own transaction but does nothing to bind these fields to what the wallet owner signed off-chain.

Consequently, an attacker who is handed (or intercepts) a validly-signed `EmporiumStack` for execution can submit it themselves with:
- `circomData.relay` = attacker's own address (instead of the intended relay), and
- `circomData.feeStructure.feeToken` = any token present in `erc20TokenAddresses` with a negative `deltaAmountChanges` entry, potentially far more valuable per-unit than the token the signer expected `maxFee` to be denominated in, while keeping `flatFee <= maxFee` numerically.

This causes `doSendToRelay` to pull `flatFee` units of an attacker-chosen token, to an attacker-chosen address, straight from the signer's `HinkalWallet` balance — value and destination the owner's EIP-712 signature never specified.

### Impact Explanation
This is theft of wallet-owner funds disguised as a "relay fee": the attacker (as the executor of a legitimately signed stack) redirects the fee payment to themselves and/or inflates its real-world value by choosing the fee-denominating token, while the owner only authorized a numeric cap with an implicit (unenforced) token assumption. This matches "executing calls or moving assets a wallet owner or prover never authorised" (High) since it moves the wallet owner's actual token balance to a destination and under fee terms never signed. It is repeatable for every signed `EmporiumStack` the attacker is asked to execute, and scales with how many tokens the wallet holds that satisfy the fee-token substitution.

### Likelihood Explanation
Preconditions: attacker must be the entity that actually submits the `transact` call carrying a validly-signed `EmporiumStack` (i.e., acting as executor/relay for that stack) — a normal, expected role in this flow since Emporium is designed for third-party execution of signed wallet operations. No privileged role, whitelisted relay status, or victim keys are required; the attacker crafts their own proof and their own `circomData.relay`/`feeStructure`. The wallet must simply hold a balance of some token distinct from what the signer assumed `maxFee` was denominated in, or the attacker needs only to set `relay` to their own address to steal the intended (but now redirected) fee outright — a trivial precondition.

### Recommendation
Include `circomData.relay`, `feeStructure.feeToken`, and `feeStructure.variableRate` (or a hash of the full `FeeStructure`) inside the EIP-712 `EMPORIUM_SIGNATURE_TYPEHASH` that the wallet owner signs, so `verifyWallet` cryptographically binds the actual fee token, rate, and relay recipient the owner intended — not just a bare numeric `maxFee` ceiling.

### Proof of Concept
Foundry test plan:
1. Deploy `HinkalWallet` for `signer`, fund it with `TokenA` (expected fee token) and `TokenB` (expensive token).
2. `signer` EIP-712 signs an `EmporiumStack` with `ops` performing some benign action, `maxFee = 1e6` (intended: 1 unit of `TokenA`, 6 decimals), `deadline` in future.
3. Attacker submits `Hinkal.transact` with a self-generated proof/`circomData` where `erc20TokenAddresses` includes `TokenB` with negative `deltaAmountChanges`, `feeStructure.feeToken = TokenB`, `feeStructure.flatFee = 1e6`, `circomData.relay = attacker`.
4. Assert: `verifyWallet` does not revert (`flatFee (1e6) <= maxFee (1e6)` passes).
5. Assert: `TokenB.balanceOf(signerWallet)` decreases by `1e6` and `TokenB.balanceOf(attacker)` increases by `1e6`, even though `signer` never signed any `TokenB`/`attacker` relay terms — i.e. `(fee token, fee amount, fee recipient) paid ≠ (fee token, fee amount, fee recipient) signed`.

        EmporiumStorageVars storage $ = _getEmporiumStorage();

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;

        bytes32 hashedMessage = _hashTypedDataV4(

                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,

                    stack.maxFee,
                    stack.deadline
                )

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s

            recoveredAddress == stack.signerAddress;
