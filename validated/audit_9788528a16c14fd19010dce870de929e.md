### Title
Fee-on-transfer tokens allow depositors to mint unbacked LP tokens, diluting/draining existing LPs - (File: program/src/processor.rs)

### Summary
`process_deposit` (and analogously `process_swap_base_in/out`) compute the amount of pool tokens to mint (or output tokens to pay) using the *nominal* transfer amount requested (`deduct_coin_amount` / `deduct_pc_amount` / `swap.amount_in`), then call `Invokers::token_transfer` with that same nominal amount. Neither the deposit nor swap path re-reads the vault's post-transfer balance to confirm how much was actually received. For a token that charges a transfer fee (fee-on-transfer / deflationary token), the amount that actually lands in the AMM vault is strictly less than the nominal amount used in the LP-minting and swap-output math, so LP tokens are minted (and swap outputs paid) against value that was never actually deposited into the vault.

### Finding Description
In `process_deposit`, the pool's current reserves are read once from the live vault balances via `Self::unpack_token_account` and `Calculator::calc_total_without_take_pnl_no_orderbook` [1](#0-0) . From these reserves, `deduct_coin_amount`/`deduct_pc_amount` are derived, and `mint_lp_amount` is computed purely from the nominal `deduct_coin_amount` (or `deduct_pc_amount`) via `InvariantPool::exchange_token_to_pool` [2](#0-1) . The code then transfers exactly `deduct_coin_amount`/`deduct_pc_amount` from the user to the vaults and mints `mint_lp_amount` LP tokens unconditionally: [3](#0-2) .

`Invokers::token_transfer` simply issues an SPL `Transfer` instruction for the specified `deposit_amount`/`amount`; it performs no post-transfer balance check and has no way to know or account for a transfer fee deducted by the token's own mint/program logic [4](#0-3) . If the coin or pc mint charges a transfer fee, the vault receives `deduct_amount - fee`, but `mint_lp_amount` was computed as if the full `deduct_amount` was contributed. The minted LP supply therefore overstates the depositor's real contribution relative to the other reserve (or relative to existing LP holders), silently diluting/underbacking the pool.

The same root cause exists in swap: `swap_amount_out` is computed from `swap.amount_in` (the nominal amount) and the reserves via `Calculator::swap_token_amount_base_in`, then exactly `swap.amount_in` is transferred into the vault while `swap_amount_out` is paid out from the other vault based on that assumption [5](#0-4) [6](#0-5) . If the input token has a transfer fee, the coin/pc vault receiving the input gets less than `swap.amount_in`, but the constant-product output was computed assuming full crediting, causing the pool to pay out more value than it actually took in for that trade.

Because `process_initialize2`/`process_deposit`/swap all use plain `Invokers::token_transfer` (no `sync_native`-style balance re-read, no `transfer_checked` fee validation), this reserve/LP-share math implicitly assumes the transferred token is a standard non-fee SPL token.

### Impact Explanation
Each deposit made with a fee-on-transfer coin or pc mint mints LP tokens backed by less value than assumed, diluting all pre-existing LPs' claim on the pool (unbacked LP minting). Repeated deposit/withdraw cycles by the same actor can be used to extract more value on withdrawal than was actually contributed, at the expense of other liquidity providers. Similarly, each swap involving a fee-on-transfer input token causes the pool to pay out swap proceeds calculated against an input amount larger than what was actually credited to the vault, bleeding value from LPs to traders on every trade. Over repeated trades/deposits this constitutes an ongoing, permanent loss of LP funds — a Medium severity issue, consistent with the "unbacked LP minting / insolvent pool accounting" impact category.

### Likelihood Explanation
This is reachable by any pool creator or LP through the ordinary `Deposit`/`SwapBaseIn`/`SwapBaseInV2` instructions with attacker-chosen (or simply commonly-used) SPL token mints; no privileged signer or special build is required — the only precondition is that the pool's coin or pc mint is a fee-on-transfer/deflationary SPL token, which is common in the wild. There are no additional protections (`transfer_checked`, `sync_native`-style balance re-check) that would prevent this.

### Recommendation
Read the vault's token balance immediately before and after each `Invokers::token_transfer` call in `process_deposit`, `process_swap_base_in(_v2)`, and `process_swap_base_out(_v2)`, and use the *actual* delta (post-balance − pre-balance) rather than the nominal instruction amount when computing `mint_lp_amount` and swap outputs. Alternatively, explicitly reject mints that are fee-on-transfer at pool `Initialize2` time (e.g., by verifying that a transfer of a known amount lands unchanged in the vault), and document/enforce that only standard, non-fee SPL tokens are supported.

### Proof of Concept
1. Create a pool via `Initialize2` where the coin mint is a fee-on-transfer SPL token (e.g., 5% fee on transfer) and pc mint is a normal token.
2. Attacker A deposits via `Deposit` with `base_side = 0`, `max_coin_amount = 1,000,000`. `deduct_coin_amount = 1,000,000` is used to compute `mint_lp_amount` per `program/src/processor.rs:1244-1250`, but the vault only receives `950,000` after the 5% fee is deducted in the SPL transfer at `program/src/processor.rs:1327-1333`. `mint_lp_amount` is minted at `program/src/processor.rs:1341-1349` as if the full `1,000,000` had been contributed.
3. Attacker A immediately withdraws with `Withdraw`, receiving a share of the *combined* real coin reserves (in this case, effectively over-withdrawing relative to their real contribution and diluting other LPs), because `process_withdraw` computes `coin_amount`/`pc_amount` purely from `withdraw.amount / amm.lp_amount * total_coin_without_take_pnl` (using real vault balances) per `program/src/processor.rs:1751-1761`, without ever knowing that A's `mint_lp_amount` was over-issued relative to A's true deposit.
4. Repeating deposit/withdraw cycles allows Attacker A to progressively extract value contributed by other LPs, or simply degrades the backing ratio of LP tokens for all holders.
