### Title
Fee-on-transfer tokens cause `WrappedHyperFungibleToken.send()` to under-lock collateral while dispatching the full nominal amount, enabling unbacked minting/unlocking on the destination chain - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` pulls the underlying ERC20 via a plain `safeTransferFrom` and then dispatches a cross-chain `Message` containing the caller-supplied `params.amount` — with no check of the actual tokens received by the contract. If the underlying token charges a transfer fee (fee-on-transfer / deflationary token), the contract locks less than `params.amount`, yet the destination chain's `HyperFungibleToken`/`WrappedHyperFungibleToken` instance will mint or unlock the full `params.amount` to the beneficiary when the message is delivered via `onAccept`.

### Finding Description
In `send()`:
```
sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:266-290
``` [1](#0-0) 

the non-WETH path does:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
``` [2](#0-1) 

There is no `balanceOf` before/after check, unlike the pattern already applied elsewhere in this same codebase for `IntentGatewayV2.placeOrder()`, which explicitly mutates `order.inputs[i].amount` to the actual balance delta received to defend against fee-on-transfer tokens:
```solidity
uint256 balBefore = IERC20(token).balanceOf(address(this));
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
``` [3](#0-2) 

That same audited defense (confirmed by dedicated fee-on-transfer unit tests such as `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`) is absent in `WrappedHyperFungibleToken.send()`. The `_buildDispatchPost` call immediately after the transfer still encodes the caller-supplied `params.amount`, not the actual amount locked:
```solidity
bytes memory body = abi.encode(HyperFungibleToken.Message({
    from: abi.encodePacked(msg.sender),
    to: params.to,
    amount: params.amount,
    data: params.data
}));
``` [4](#0-3) 

When this message is delivered on the destination chain, `onAccept` releases/mints exactly `message.amount` to the beneficiary — the full, un-discounted amount — without any check that the amount was actually backed by tokens locked on the source side:
```solidity
IERC20(_underlying).safeTransfer(beneficiary, message.amount);
``` [5](#0-4) 

Because `WrappedHyperFungibleToken` is the lock/unlock (custody) side of the bridge pair for any underlying ERC20 the deployer configures, a fee-on-transfer underlying breaks 1:1 backing: every `send()` call locks `amount * (1-fee)` but the destination side unlocks/mints the full `amount`, progressively draining the collateral pool held by `WrappedHyperFungibleToken` until it can no longer honor later unlocks/refunds (insolvency / permanent freezing of funds for later users) — or, for deployments where the destination side mints (`HyperFungibleToken`), this becomes literal unbacked minting.

### Impact Explanation
This is reachable by any unprivileged user in a single `send()` transaction targeting a `WrappedHyperFungibleToken` deployment configured with a fee-on-transfer (or otherwise deflationary) underlying token. Repeated exploitation drains the locked-collateral pool relative to the total amount unlockable on the destination chain, leading to insolvency of the bridge pair and inability for legitimate users' later cross-chain transfers/refunds/timeouts to be honored — a concrete freezing-of-funds condition, and for mint-side deployments an unbacked-mint condition. This matches the accepted impact classes (unbacked mint / permanent freezing of funds).

### Likelihood Explanation
Likelihood depends entirely on whether a deployer configures `WrappedHyperFungibleToken._underlying` to a fee-on-transfer token. Given the codebase's own test suite treats fee-on-transfer tokens as an explicitly supported/anticipated case in `IntentGatewayV2` (with dedicated tests), it is reasonable to expect FOT-token underlyings to be used with `HyperFungibleToken`/`WrappedHyperFungibleToken` as well, and the docs make no restriction against wrapping such tokens. No privileged action or governance error is required — only a normal `send()` call by any user.

### Recommendation
Apply the same balance-delta pattern used in `IntentGatewayV2.placeOrder()` to `WrappedHyperFungibleToken.send()`: measure `balanceOf(address(this))` before and after `safeTransferFrom`, use the actual delta as the amount encoded in the dispatched `Message`, and reject deposits where the received amount does not match the intended one, or explicitly compute and dispatch the discounted amount so destination-side release/mint always matches locked collateral.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` with `_underlying` set to a fee-on-transfer ERC20 (e.g., 1% fee per transfer), non-WETH mode.
2. User calls `send({dest, to: recipient, amount: 1000e18, timeout, relayerFee, data: ""})` after approving `1000e18`.
3. `safeTransferFrom` moves `1000e18` requested, but due to the 1% fee the contract's balance only increases by `990e18`.
4. The dispatched `Message.amount` is still `1000e18` (the caller-supplied value), not the `990e18` actually locked.
5. On the destination chain, `onAccept` unlocks/mints `1000e18` to `recipient` — 10e18 more than was actually collateralized on the source chain.
6. Repeating this drains the wrapper's real collateral relative to its outstanding unlock/mint obligations, eventually causing later legitimate unlocks (or timeout refunds) to fail due to insufficient underlying balance.

    function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
        }

        DispatchPost memory request = _buildDispatchPost(params);
        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }
