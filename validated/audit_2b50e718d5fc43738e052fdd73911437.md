This confirms the finding. For OAuth, `AuthQuery#to_signable_string` includes `shop` in the HMAC-signed payload [1](#0-0) , so the shop identity used by `validate_auth_callback` is cryptographically bound to the signature. But for webhooks, `Request#to_signable_string` returns only `@raw_body`, and `shop`, `topic`, and `webhook_id` are all pulled from separate, unsigned HTTP headers [2](#0-1) . `Registry.process` passes that unverified `request.shop` straight into `WebhookMetadata`, which is the only tenant-identifying field handed to the consuming app's handler [3](#0-2) [4](#0-3) .

### Title
Webhook shop identity not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, then trusts the `shop` (and `topic`/`webhook_id`) values taken from separate, unsigned HTTP headers when constructing the `WebhookMetadata` passed to the app's handler. Because the shop identity is not bound to the signature, a party who can obtain one validly-signed webhook delivery (e.g., by installing the app on their own store) can replay that request while swapping the `X-Shopify-Shop-Domain` header to a victim shop, causing the app to process attacker-controlled webhook content under another tenant's identity.

### Finding Description
`Utils::HmacValidator.validate` computes the signature from `verifiable_query.to_signable_string` and compares it to the `hmac` field [5](#0-4) . For `Webhooks::Request`, `to_signable_string` returns `@raw_body` exclusively [6](#0-5) , while `shop`, `topic`, `api_version`, and `webhook_id` are read from HTTP headers that play no part in the HMAC computation [7](#0-6) . `Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` [3](#0-2) . The equality this breaks: the identity binding "shop that authorized/signed this payload == shop attributed to the processed webhook" does not hold, because the signature proves only "signed with this app's `api_secret_key`" (shared across all shops that install the app), not "signed for this specific shop." This contrasts with the OAuth callback flow, where `AuthQuery#to_signable_string` explicitly includes `shop` in the signed string [1](#0-0) , correctly binding shop identity to the signature there.

### Impact Explanation
Any store owner who installs the app can capture a legitimately HMAC-signed webhook body from their own shop, then resend it to the app's webhook endpoint with the `shopify-shop-domain`/`x-shopify-shop-domain` header changed to a victim shop's domain. Since `HmacValidator` never inspects headers, the forged request passes validation and the handler receives `WebhookMetadata` attributing attacker-controlled `topic`/`body` to the victim shop — a cross-tenant data/identity confusion at the library's trust boundary, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Exploitation requires only that the attacker have (or obtain) their own valid app installation to harvest one genuine signed webhook and standard ability to POST to the app's public webhook endpoint with custom headers — no leaked secrets or privileged access needed, making this readily reachable by any unprivileged merchant/attacker of the app.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed material, or otherwise cryptographically bind the header-derived shop to the verified body (e.g., verify the shop against a per-shop secret/session lookup) before constructing `WebhookMetadata`, so the identity handed to the app's handler is provably tied to the HMAC that was validated.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture a genuine webhook POST (e.g., `orders/create`) including its valid `X-Shopify-Hmac-Sha256` header (computed over the raw body with the shared `api_secret_key`).
2. Replay the exact same request to the app's webhook endpoint, keeping the body and HMAC header unchanged, but replacing `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (untouched) body against the (untouched) HMAC and succeeds [8](#0-7) .
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)`, processing attacker data as if it originated from the victim shop.
