### Title
`coin::migrate_coin_store_to_fungible_store` lets anyone unfreeze a compliance-frozen `FungibleStore` by re-syncing it to a stale legacy `CoinStore.frozen` bit - (File: `aptos-move/framework/aptos-framework/sources/coin.move`)

### Summary
`coin::maybe_convert_to_fungible_store` (invoked by the permissionless entry functions `migrate_to_fungible_store` and, critically, `migrate_coin_store_to_fungible_store`) unconditionally overwrites a primary `FungibleStore`'s `frozen` flag with the value of the legacy `CoinStore.frozen` field whenever the two disagree. Because `migrate_coin_store_to_fungible_store` takes a caller-supplied `vector<address>` with **no signer/ownership check at all**, any unprivileged account can force this "consistency" sync on any victim account, silently clearing an admin-set freeze on the victim's `FungibleStore` (e.g. a stablecoin denylist freeze applied via `TransferRef`).

### Finding Description
The relevant code: [1](#0-0) 

```
if (frozen != fungible_asset::is_frozen(store)) {
    fungible_asset::set_frozen_flag_internal(store, frozen)
}
```

`frozen` here is taken directly from the destructured legacy `CoinStore<CoinType>` resource being migrated, not from any privileged capability. `set_frozen_flag_internal` is a `friend`-only function that normally can only be invoked by a `TransferRef` holder (the asset admin) via `fungible_asset::set_frozen_flag`: [2](#0-1) 

`coin.move`'s migration path bypasses that authority model entirely: it treats the old `CoinStore.frozen` bit as the source of truth and force-writes it onto the `FungibleStore`, in either direction (freeze *or* unfreeze).

The entry points that trigger this: [3](#0-2) 

`migrate_to_fungible_store` requires the account's own signer, but `migrate_coin_store_to_fungible_store` accepts an arbitrary `vector<address>` and has **no signer parameter whatsoever** — it can be called by anyone against any set of target accounts.

Attack path:
1. A stablecoin/compliance issuer freezes a denylisted account's `FungibleStore` using `TransferRef::set_frozen_flag` (FA-native freeze API), while the account's legacy `CoinStore<CoinType>.frozen` remains `false` (its default, since it was never frozen through the old `coin::freeze_coin_store` path).
2. As long as that account still holds a non-zero balance in the legacy `CoinStore<CoinType>` (e.g., dust left before full FA migration, or received via a still-supported legacy coin deposit path), the condition `is_coin_initialized<CoinType>() && coin.value > 0` is satisfied.
3. Anyone (the frozen account itself, or any third party) calls `coin::migrate_coin_store_to_fungible_store<CoinType>(vector[victim_addr])`.
4. `maybe_convert_to_fungible_store` compares `frozen` (`false`, from `CoinStore`) against `fungible_asset::is_frozen(store)` (`true`, admin-set), finds a mismatch, and calls `fungible_asset::set_frozen_flag_internal(store, false)` — unfreezing the compliance-frozen store.
5. The victim's `FungibleStore` is now unfrozen and transferable, defeating the freeze/denylist control the asset issuer relied on.

### Impact Explanation
This breaks the custody invariant that only the `TransferRef` holder (the fungible-asset admin/compliance authority) controls a store's frozen state. A permissionless migration utility can silently strip freeze/denylist protection from any account's `FungibleStore`, enabling a sanctioned or compliance-frozen holder to resume transfers of live custodial value (stablecoins, regulated assets) without any privileged action. Because `migrate_coin_store_to_fungible_store` takes no signer, this is exploitable by any third party against any account, not merely the account owner — a full unauthorized takeover of freeze control for the affected store.

### Likelihood Explanation
Requires: (a) a `CoinType` that has been paired with a `Metadata`/`FungibleStore` (common for coins undergoing the Coin→FA migration, including APT and third-party coins using `ensure_paired_metadata`), (b) the target holding a residual non-zero `CoinStore<CoinType>` balance, and (c) the asset's freeze authority having frozen the `FungibleStore` side rather than (or in addition to) the legacy `CoinStore`. Given the framework is actively migrating all coins to the FA model and encourages FA-native freeze/denylist tooling (see `dispatchable_fungible_asset`/`managed_fungible_asset` freeze patterns), this precondition is realistic for any coin still carrying legacy `CoinStore` balances during the migration window. The call itself has no gas/permission barrier.

### Recommendation
`maybe_convert_to_fungible_store` should never downgrade a `FungibleStore`'s frozen state that is more restrictive than the legacy `CoinStore`. At minimum:
- Only propagate `frozen = true` from `CoinStore` to `FungibleStore` (freeze can be tightened, never loosened) during migration, or
- Skip the frozen-flag sync entirely once the `FungibleStore` already exists and let the FA-side authority manage its own frozen state independently, or
- Require that only the asset's `TransferRef` holder can alter frozen semantics during migration (i.e., never touch `frozen` unless the `FungibleStore` did not previously exist).

### Proof of Concept
1. Admin creates `CoinType` with paired FA metadata; issues coins to `victim` via legacy `coin::deposit`, leaving `CoinStore<CoinType>{frozen: false, coin.value = N>0}` at `victim`.
2. Admin (compliance) freezes `victim`'s `FungibleStore` using `TransferRef::set_frozen_flag(true)` (fungible_asset.move L1035-1052).
3. Attacker (any account) submits `coin::migrate_coin_store_to_fungible_store<CoinType>(vector[victim])` (coin.move L732-738).
4. `maybe_convert_to_fungible_store` executes; `frozen` read from `CoinStore` is `false`; compares to `fungible_asset::is_frozen(store) == true`; calls `set_frozen_flag_internal(store, false)`.
5. `victim`'s `FungibleStore.frozen` is now `false`; the account can freely transfer/withdraw the FA balance despite the compliance freeze remaining logically "in force" from the issuer's perspective.

Note: I was unable to fully trace whether a currently-deployed production `CoinType` (e.g. APT) actually exposes a path for users to retain a non-zero legacy `CoinStore` after FA pairing under default protocol configuration — this depends on feature-flag state and migration policy not fully visible in the indexed code, so exploit preconditions should be independently verified against the live migration feature flags before treating this as immediately mainnet-exploitable.

    fun maybe_convert_to_fungible_store<CoinType>(
        account: address
    ) acquires CoinStore, CoinConversionMap, CoinInfo {
        if (exists<CoinStore<CoinType>>(account)) {
            let CoinStore<CoinType> { coin, frozen, deposit_events, withdraw_events } =
                move_from<CoinStore<CoinType>>(account);
            if (is_coin_initialized<CoinType>() && coin.value > 0) {
                let metadata = ensure_paired_metadata<CoinType>();
                let store =
                    primary_fungible_store::ensure_primary_store_exists(
                        account, metadata
                    );

                event::emit(
                    CoinStoreDeletion {
                        coin_type: type_info::type_name<CoinType>(),
                        event_handle_creation_address: guid::creator_address(
                            event::guid(&deposit_events)
                        ),
                        deleted_deposit_event_handle_creation_number: guid::creation_num(
                            event::guid(&deposit_events)
                        ),
                        deleted_withdraw_event_handle_creation_number: guid::creation_num(
                            event::guid(&withdraw_events)
                        )
                    }
                );

                if (coin.value == 0) {
                    destroy_zero(coin);
                } else {
                    fungible_asset::unchecked_deposit_with_no_events(
                        store.object_address(),
                        coin_to_fungible_asset(coin)
                    );
                };

                // Note:
                // It is possible the primary fungible store may already exist before this function call.
                // In this case, if the account owns a frozen CoinStore and an unfrozen primary fungible store, this
                // function would convert and deposit the rest coin into the primary store and freeze it to make the
                // `frozen` semantic as consistent as possible.
                if (frozen != fungible_asset::is_frozen(store)) {
                    fungible_asset::set_frozen_flag_internal(store, frozen);
                }
            } else {
                destroy_zero(coin);
            };
            event::destroy_handle(deposit_events);
            event::destroy_handle(withdraw_events);
        };
    }

    /// Enable/disable a store's ability to do direct transfers of the fungible asset.
    public fun set_frozen_flag<T: key>(
        self: &TransferRef, store: Object<T>, frozen: bool
    ) acquires FungibleStore {
        assert!(
            self.metadata == store_metadata(store),
            error::invalid_argument(ETRANSFER_REF_AND_STORE_MISMATCH)
        );
        set_frozen_flag_internal(store, frozen)
    }

    public(friend) fun set_frozen_flag_internal<T: key>(
        store: Object<T>, frozen: bool
    ) acquires FungibleStore {
        let store_addr = store.object_address();
        borrow_global_mut<FungibleStore>(store_addr).frozen = frozen;

        event::emit(Frozen { store: store_addr, frozen });
    }
