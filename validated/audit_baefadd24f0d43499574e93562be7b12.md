### Title
Webhook HMAC Validation Does Not Cover `shop-domain`, `topic`, or `webhook-id` Headers, Allowing Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body when validating a webhook's HMAC, while the `shop-domain`, `topic`, `api-version`, and `webhook-id` values — all taken from unauthenticated HTTP headers — are handed to the app's webhook handler as trusted tenant/routing identity. This breaks the equality `shop authenticated by HMAC == shop acted on by the handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to those header values: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, i.e. only the body: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC and then dispatches directly using the unauthenticated `request.shop` / `request.topic` header values as the trusted tenant/topic identity handed to the host application's handler: [4](#0-3) 

Because the signature only covers the JSON body bytes, any actor who can obtain one validly-signed webhook body+HMAC pair (trivially available to anyone who installs the app on their own store and receives any webhook for it) can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a different (victim) shop. `HmacValidator.validate` will still report success because it never inspects the headers, and `Registry.process` will call the handler with `data.shop` set to the attacker-chosen victim shop domain alongside the attacker's own (validly-signed) body content.

### Impact Explanation
This breaks a tenant-identity binding: the HMAC is meant to prove "this payload came from Shopify for shop X," but shop X is never actually part of what's signed. Host applications built on this gem's documented webhook API (`Webhooks::Registry.process`, `WebhookMetadata#shop`) reasonably treat `data.shop` as an authenticated tenant identifier once `HmacValidator.validate` passes. An attacker controlling any single tenant (their own shop with the app installed) can inject arbitrary attacker-chosen body content attributed to any other merchant's shop, corrupting per-tenant data or state in the host application — a cross-tenant access/confusion vulnerability.

### Likelihood Explanation
Likelihood is high: obtaining a validly-signed webhook body/HMAC pair requires nothing more than installing the target app on any Shopify development store (something any internet user can do for a public app) and capturing one webhook delivery. No access to `api_secret_key`, access tokens, or any privileged account for the victim shop is required — only the ability to change the `shop-domain` (and `topic`/`webhook-id`) HTTP headers on a replayed POST to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed payload used for HMAC verification (e.g., concatenate them with the body in a canonical, delimiter-safe form before hashing), or otherwise cryptographically bind the header-derived identity fields to the signature so that `HmacValidator.validate` fails if any of them are altered independently of the body.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the raw JSON body `B` and the corresponding `x-shopify-hmac-sha256` header `H` (valid, computed over `B` with the app's real secret).
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only recomputes HMAC over `B`, matching `H`.
4. `Registry.process(request)` invokes the app's registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: attacker_chosen_topic, body: parsed(B), ...)`, causing the host application to process attacker-controlled data under the victim shop's tenant identity.
