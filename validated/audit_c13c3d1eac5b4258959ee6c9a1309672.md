### Title
Permanent freeze of escrowed intent funds via unconditional `revert UnknownOrder()` in `IntentsBase._withdraw()` when per-token escrow is already zero - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw()`, the shared release path for both cross-chain `RedeemEscrow`/`RefundEscrow` deliveries (via `ExtrinsicIntents.onAccept`) and cross-chain cancel GET responses (via `ExtrinsicIntents.onGetResponse`), unconditionally reverts with `UnknownOrder()` whenever the per-token escrow balance for an order's commitment is zero for a non-zero requested amount. This mirrors the Notional M-25 pattern: a `price()`/settlement-critical function that assumes a per-asset value can never legitimately be zero, and reverts deterministically instead of degrading gracefully — permanently freezing the affected funds since the same commitment/token pair will always retry into the same revert.

### Finding Description
`_withdraw()` loops over the withdrawal request's token list and, for every token with a non-zero requested `amount`, requires `_orders[commitment][token] != 0`: [1](#0-0) 

```
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
_orders[body.commitment][token] = escrowed - amount;
```

This assumes the invariant "escrow for (commitment, token) is always non-zero right before this specific withdraw runs" holds at all times. It does not:

- `_cancelFromSource` (source-chain cancel) independently checks, per input token, `_orders[commitment][token] == 0 → revert UnknownOrder()` before dispatching the GET request: [2](#0-1) 
  This check only runs at dispatch time. If, between dispatch and delivery of the `onGetResponse`, any other finalizing path (a `RedeemEscrow`/`RefundEscrow` delivered by Hyperbridge, or the destination-chain `_cancelFromDest` message racing in) has already withdrawn/zeroed one of the tokens' escrow (fully or exactly), the later `_withdraw()` call triggered by `onGetResponse` will hit `escrowed == 0` for that token and revert with `UnknownOrder()`.
- Because ordering across independently-dispatched cross-chain messages (a GET for cancellation vs. a POST from a fill/refund on the other chain) is not serialized by the protocol, a race between a cancel-from-source flow and a fill/refund flow is possible, since both can be in flight for the same commitment once the deadline passes (`_cancelFromDest` is callable by anyone after expiry, independent of a source-side cancel already having been triggered).
- `onAccept`/`onGetResponse` deliveries are wrapped in `EvmHost.dispatchIncoming` as a low-level `.call()`; on revert only the request receipt is deleted "so it can be retried" — [3](#0-2)  — meaning the message is retried with the exact same calldata. Since the revert condition (`_orders[commitment][token] == 0`) is a deterministic function of on-chain state that a duplicate delivery of the same body cannot change, retrying can never succeed: the specific commitment's escrow becomes permanently unredeemable, exactly analogous to `getWithdrawRequestValue()`'s `require(hasRequest)` bricking the position.

### Impact Explanation
Once triggered, the escrowed input tokens for the affected order commitment become permanently stuck: they can never be released to the solver, refunded to the user, or swept by governance (there is no privileged path that bypasses `_withdraw`'s per-token check). This is a permanent freezing-of-funds condition reachable from ordinary user/solver actions (`placeOrder`, `fillOrder`/cross-chain fill, `cancelOrder` on either side) with no admin or protocol-level malicious actor required — satisfying "concrete... permanent freezing of funds."

### Likelihood Explanation
Requires a race between the two independent cross-chain finalization paths for the same commitment (a source-initiated cancel's GET-response settlement vs. a destination-initiated fill/refund's POST settlement), both of which are user/solver-triggerable and both eventually settle asynchronously through Hyperbridge with no on-chain serialization/lock between them for a given commitment beyond `_filled`. This is a narrower window than the original Sherlock finding's "any zero-balance token" trigger, and I could not fully verify from static reading alone whether `_filled` or other order-lifecycle guards (e.g., the destination-side `_filled[commitment]` set in `_withdraw` before the token loop, or same-chain `_filled` checks not shown here) fully close this race for every input token in every code path, since some entry points (`fillOrder`, `cancelOrder` dispatch wrappers, `_filled` checks gating `_cancelFromDest`/redemption) were not read in full. This should be treated as Medium confidence pending confirmation of whether `_filled` guards prevent both a redeem and a cancel-refund from ever reaching `_withdraw` for the same commitment.

### Recommendation
In `_withdraw()`, do not revert the entire withdrawal batch when a specific token's escrow is already zero for a non-zero requested amount if the order has already been finalized through a valid alternate path (check `_filled[body.commitment] != address(0)` first and treat this call as a no-op/idempotent skip rather than reverting), or gate all finalizing paths (`RedeemEscrow`, `RefundEscrow`, and the cancellation GET response) behind a single `_filled` check performed atomically at the top of `_withdraw`, ensuring only the first-to-arrive finalization is allowed to touch escrow and every subsequent one is treated as already-settled rather than reverting into a permanently retryable failure.

### Proof of Concept
Not independently constructed; the analog is derived from static code reading of `_withdraw`, `_cancelFromSource`, `_cancelFromDest`, and `EvmHost.dispatchIncoming`'s retry-on-revert semantics. A concrete PoC would need to demonstrate concurrent in-flight `RedeemEscrow`/`RefundEscrow` and cancel-GET-response messages for the same commitment landing in an order that leaves one token's `_orders[commitment][token]` at zero before the second message is processed — this exact sequencing was not verified end-to-end within the available exploration budget.
