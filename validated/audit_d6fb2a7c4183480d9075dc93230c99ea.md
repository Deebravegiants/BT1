Audit Report

## Title
Long-lived LDAP API tokens and sessions remain valid after upstream user revocation when `UpstreamSyncInterval` is left at its default disabled value - (File: core/sessions/ldapauth/sync.go)

## Summary
The LDAP authentication provider caches user sessions and API tokens in local tables (`ldap_sessions`, `ldap_user_api_tokens`) and the only mechanism that revalidates that cache against the upstream directory — `LDAPServerStateSyncer.Work` — is scheduled solely by `UpstreamSyncInterval`, which defaults to `'0s'`. With this default, `Work` runs exactly once at node startup and never again, and neither `AuthorizedUserWithSession` nor `FindUserByAPIToken` triggers it on a per-request basis, despite the package doc claiming otherwise. [1](#0-0) [2](#0-1) 

## Finding Description
`LDAPServerStateSyncer.Start` only launches the recurring `run()` goroutine (ticker-driven `Work` calls) when `UpstreamSyncInterval` is non-zero; otherwise it calls `Work` a single time at startup. [1](#0-0) 

`AuthorizedUserWithSession` and `FindUserByAPIToken` in `core/sessions/ldapauth/ldap.go` both validate purely against a locally-cached row using a time-based `created_at + duration >= now()` check, with no call into `LDAPServerStateSyncer.Work` or any other live upstream check. [3](#0-2) [4](#0-3) 

I confirmed the login (`SessionsController.Create`) and logout (`SessionsController.Destroy`) HTTP handlers only call `sc.App.WakeSessionReaper()` — which wakes the generic `sessionReaper` (used by `localauth`/`oidcauth`) — not the LDAP-specific `LDAPServerStateSyncer.Work`. [5](#0-4) 
This directly contradicts both the package-level doc comment in `ldap.go` ("This sync happens for every auth endpoint hit...") and the `UpstreamSyncInterval` config doc ("This check is already performed during login/logout actions...") — neither of these documented behaviors is actually wired up in code for LDAP; `WakeSessionReaper` and `LDAPServerStateSyncer` are separate, unconnected components. [6](#0-5) [2](#0-1) 

With `UserAPITokenDuration` defaulting to `240h0m0s` (10 days), a token issued to a user is treated as valid purely on local timestamp comparison for up to 10 days after issuance, irrespective of upstream directory state, when `UpstreamSyncInterval` is left at its default `0s`. [7](#0-6) 

## Impact Explanation
If an operator removes/deactivates an LDAP user upstream while leaving `UpstreamSyncInterval` at its documented default (`0s`), that user's previously-issued session cookie or API token continues to authenticate successfully via `AuthorizedUserWithSession`/`FindUserByAPIToken` for up to `SessionTimeout`/`UserAPITokenDuration` respectively, since only a local-clock check gates validity and no automatic re-sync against the authoritative LDAP source occurs after startup. This grants continued unauthorized API/GUI access at the user's last-synced role (potentially Admin) to a party who should have lost access — an in-scope "node API authentication/role bypass"-class impact.

## Likelihood Explanation
The attack requires no sophistication beyond possessing a still-unexpired, previously-valid LDAP session or API token issued before revocation — a realistic offboarding/access-revocation scenario. The likelihood is entirely contingent on the operator's configuration: it manifests precisely when `UpstreamSyncInterval` is left at its shipped default value of `'0s'`, i.e., it is a default-configuration gap rather than something requiring privileged or unusual attacker action to trigger.

## Recommendation
- Trigger `LDAPServerStateSyncer.Work` (rate-limited) synchronously from `AuthorizedUserWithSession` and `FindUserByAPIToken`, or from the HTTP middleware/session-reaper wake path, so the documented "sync on every auth endpoint hit" behavior is actually implemented.
- Change semantics so `UpstreamSyncInterval = 0` means "sync on every auth check" rather than "only sync once at startup," or emit a prominent startup warning that upstream revocation will not propagate without a node restart while `UpstreamSyncInterval` is disabled.
- Consider lowering the default `UserAPITokenDuration` and clearly documenting the operational risk of leaving `UpstreamSyncInterval` at `0s`.

## Proof of Concept
1. Run a chainlink node with `WebServer.AuthenticationMethod = 'ldap'`, `WebServer.LDAP.UpstreamSyncInterval = '0s'` (default), `UserApiTokenEnabled = true`, `UserAPITokenDuration = '240h0m0s'` (default).
2. Log in as `alice` via `POST /sessions`, which calls `ldapAuthenticator.CreateSession`, inserting a row into `ldap_sessions`; issue an API token stored in `ldap_user_api_tokens`.
3. Have an LDAP administrator remove `alice` from her role group upstream (simulating offboarding).
4. Because `UpstreamSyncInterval` is `0s`, `LDAPServerStateSyncer.run()` never starts, and no other code path invokes `Work` again; `SessionsController.Create`/`Destroy` only call `WakeSessionReaper`, which does not touch `LDAPServerStateSyncer`.
5. `alice` continues calling the node API with her API token; `FindUserByAPIToken` returns her cached role successfully as long as `created_at + UserAPITokenDuration >= now()`, up to 10 days after revocation, with no restart or manual admin action able to detect the discrepancy in real time.

func (l *LDAPServerStateSyncer) Start(ctx context.Context) error {
	// If enabled, start a background task that calls the Sync/Work function on an
	// interval without needing an auth event to trigger it
	// Use IsInstant to check 0 value to omit functionality.
	if !l.config.UpstreamSyncInterval().IsInstant() {
		l.lggr.Info("LDAP Config UpstreamSyncInterval is non-zero, sync functionality will be called on a timer, respecting the UpstreamSyncRateLimit value")
		go l.run()
	} else {
		// Ensure upstream server state is synced on startup manually if interval check not set
		l.Work(ctx)
	}
	return nil
}

// FindUserByAPIToken retrieves a possible stored user and role from the ldap_user_api_tokens table store
func (l *ldapAuthenticator) FindUserByAPIToken(ctx context.Context, apiToken string) (sessions.User, error) {
	if !l.config.UserApiTokenEnabled() {
		return sessions.User{}, errors.New("API token is not enabled ")
	}

	// Query the ldap user API token table for given token, user role and email are cached so
	// no further upstream LDAP query is performed, sessions and tokens are synced against the upstream server
	// via the UpstreamSyncInterval config and reaper.go sync implementation
	var foundUserToken struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	err := l.ds.GetContext(ctx, &foundUserToken,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_user_api_tokens WHERE token_key = $1",
		apiToken, l.config.UserAPITokenDuration().Duration(),
	)
	if err != nil {
		return sessions.User{}, err
	}

func (l *ldapAuthenticator) AuthorizedUserWithSession(ctx context.Context, sessionID string) (sessions.User, error) {
	if len(sessionID) == 0 {
		return sessions.User{}, errors.New("session ID cannot be empty")
	}
	// Query the ldap_sessions table for given session ID, user role and email are cached so
	// no further upstream LDAP query is performed
	var foundSession struct {
		UserEmail string
		UserRole  sessions.UserRole
		Valid     bool
	}
	if err := l.ds.GetContext(ctx, &foundSession,
		"SELECT user_email, user_role, created_at + $2 >= now() as valid FROM ldap_sessions WHERE id = $1",
		sessionID, l.config.SessionTimeout().Duration(),
	); err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

func (sc *SessionsController) Create(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()
	sc.App.GetLogger().Debugf("TRACE: Starting Session Creation")

	session := sessions.Default(c)
	var sr clsessions.SessionRequest
	if err := c.ShouldBindJSON(&sr); err != nil {
		jsonAPIError(c, http.StatusBadRequest, fmt.Errorf("error binding json %w", err))
		return
	}

	// Does this user have 2FA enabled?
	userWebAuthnTokens, err := sc.App.AuthenticationProvider().GetUserWebAuthn(ctx, sr.Email)
	if err != nil {
		sc.App.GetLogger().Errorf("Error loading user WebAuthn data: %s", err)
		jsonAPIError(c, http.StatusInternalServerError, errors.New("internal Server Error"))
		return
	}

	// If the user has registered MFA tokens, then populate our session store and context
	// required for successful WebAuthn authentication
	if len(userWebAuthnTokens) > 0 {
		sr.SessionStore = sc.sessions
		sr.WebAuthnConfig = sc.App.GetWebAuthnConfiguration()
	}

	sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
	if err != nil {
		jsonAPIError(c, http.StatusUnauthorized, err)
		return
	}

	if err := saveSessionID(session, sid); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, errors.Join(errors.New("unable to save session id"), err))
		return
	}

	jsonAPIResponse(c, Session{Authenticated: true}, "session")
}

// Destroy removes the specified session ID from the database.
func (sc *SessionsController) Destroy(c *gin.Context) {
	defer sc.App.WakeSessionReaper()
	ctx := c.Request.Context()

	session := sessions.Default(c)
	defer session.Clear()
	sessionID, ok := session.Get(auth.SessionIDKey).(string)
	if !ok {
		jsonAPIResponse(c, Session{Authenticated: false}, "session")
		return
	}
	if err := sc.App.AuthenticationProvider().DeleteUserSession(ctx, sessionID); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	sc.App.GetAuditLogger().Audit(audit.AuthSessionDeleted, map[string]any{"sessionID": sessionID})
	jsonAPIResponse(c, Session{Authenticated: false}, "session")
