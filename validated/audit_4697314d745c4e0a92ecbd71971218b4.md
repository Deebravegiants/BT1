### Title
Hardcoded single-fee-tier Uniswap V3 pool used to price `EvmHost` fee-token swaps causes mispriced/DoS'd request dispatch - (File: `evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol`)

### Summary
`EvmHost.dispatch()`, `dispatch(DispatchGet)`, and `fundRequest()` swap a submitter's native token into the protocol `feeToken` via `IUniswapV2Router02(uniswapV2).swapETHForExactTokens(...)`, where `uniswapV2` on many deployments is configured to point at `UniV3UniswapV2Wrapper`, a V2-router-compatible shim over Uniswap V3 [1](#0-0) [2](#0-1) . This wrapper hardcodes a single Uniswap V3 fee tier (`maxFee`, set once at deploy time) and uses it for every swap and every quote, regardless of the actual `(WETH, feeToken)` pair being priced [3](#0-2) .

### Finding Description
`UniV3UniswapV2Wrapper.Params.maxFee` is a single `uint24` fee tier chosen once at deployment and stored in `_params` [4](#0-3) . Every function that this wrapper exposes with the `IUniswapV2Router02`-compatible interface — `swapETHForExactTokens`, `swapExactTokensForETH`, `getAmountsIn`, `getAmountsOut` — passes this same hardcoded `_params.maxFee` into the underlying `IV3SwapRouter`/`IQuoterV2` calls as the pool `fee`, exactly mirroring the root cause described in the Real Wagmi report (hardcoded `500` fee used both to execute the swap and to compute `amountOut` for slippage checks) [5](#0-4) [6](#0-5) [7](#0-6) .

This wrapper is wired directly into the message-dispatch path that every unprivileged sender of a cross-chain request/message uses. `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` each call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, [WETH, feeToken], address(this), block.timestamp)` whenever a caller pays with native token [1](#0-0) [8](#0-7) . `HyperApp.quote(...)`, used by any app/user to estimate the native amount to send, also calls `getAmountsIn` on this same wrapper/router with the same fixed fee tier logic [9](#0-8) . The wrapper is registered in host config as `UNISWAP_V2`, i.e. it *is* `IHost.uniswapV2Router()` for the chain [10](#0-9) .

Because `maxFee` is fixed at deploy time and not selected per-pair or by best liquidity (unlike the SDK's own `getBestV3Pool`/`COMMON_FEE_TIERS` best-liquidity search used elsewhere in the codebase for swap quoting [11](#0-10) ), any WETH/feeToken pair that does not have deep liquidity in that specific fee tier will be quoted/executed against a thin or nonexistent pool. This is the same failure mode Sherlock rated High in Real Wagmi: not every pair has liquidity concentrated in the hardcoded tier, and the tier is not chosen for volume/TVL.

### Impact Explanation
- If the hardcoded fee-tier pool for `(WETH, feeToken)` on a given deployment has low liquidity relative to mainnet's canonical 0.05%/0.3% pools (e.g. secondary/L2 deployments), `swapETHForExactTokens` in `dispatch()`/`fundRequest()` executes against that thin pool, paying far more in slippage than a correctly-routed swap would, and `amountInMaximum = msg.value` provides no real protection since the caller pre-funds based on `getAmountsIn` computed from the *same* mispriced pool (garbage-in, garbage-out) [1](#0-0) [9](#0-8) .
- If the hardcoded fee-tier pool for that pair does not exist at all, every native-token dispatch/fundRequest call on that chain reverts, permanently freezing the ability to pay relayer fees in native token for that route (a denial of the message-delivery/fee-funding path) — consistent with the "route unable to deliver messages" acceptance criterion.
- Because this affects the fee-payment leg of `dispatch()`/`fundRequest()`, which every unprivileged message sender relies on to fund relayer delivery, mispricing here directly translates into either overpaying protocol/relayer fees (funds loss to the submitter) or requests never being fundable/dispatchable via native token on that chain.

### Likelihood Explanation
Likelihood is deployment-dependent but realistic: the wrapper is an actively maintained, deployed artifact (`DeployUniV3Wrapper.s.sol`, referenced by `ConfiguredWrapperForkTest.t.sol`) intended specifically for chains where a native Uniswap V2 router/pool doesn't exist for the desired feeToken pair, i.e. exactly the "secondary chain" scenario called out in the original report [12](#0-11) . Any chain configured with a `maxFee` that isn't the deepest tier for its WETH/feeToken pair — or where liquidity migrates to a different tier over time — is silently exposed, and there's no per-call or on-chain mechanism to select/verify the tier; it is a single governance-set constant with no fallback across tiers.

### Recommendation
Do not hardcode a single V3 fee tier in `UniV3UniswapV2Wrapper`. Instead:
- Select the fee tier dynamically per call by querying the `V3_FACTORY`/`IQuoterV2` across the standard tier set (100/500/3000/10000) and picking the tier with the deepest liquidity for the pair, mirroring the SDK's existing `getBestV3Pool`/`COMMON_FEE_TIERS` pattern already used elsewhere in this codebase [11](#0-10) .
- Alternatively, accept the fee (or full V3 path) as an explicit parameter to `swapETHForExactTokens`/`swapExactTokensForETH`/`getAmountsIn`/`getAmountsOut`, or store fee tiers keyed by token pair rather than a single global `maxFee`.
- Add monitoring/fork tests (extending `ConfiguredWrapperForkTest.t.sol`) that assert the configured tier is in fact the deepest-liquidity tier for the pair on each supported chain, and alert if liquidity migrates away from the configured tier.

### Proof of Concept
1. Deploy `UniV3UniswapV2Wrapper` on a chain where the WETH/feeToken pair's liquidity is concentrated in the 0.3% (3000) tier, but the deployer configures `MAX_FEE = 500` (or vice versa) via `DeployUniV3Wrapper.s.sol` [13](#0-12) .
2. Register this wrapper as `IHost.uniswapV2Router()`/`uniswapV2` in `EvmHost`'s `HostParams` [14](#0-13) .
3. Any user calls `EvmHost.dispatch(DispatchPost)` with `msg.value` set to pay in native token; `EvmHost` calls `swapETHForExactTokens` on the wrapper using the hardcoded `500` fee [1](#0-0) [5](#0-4) .
4. Because the deep-liquidity pool is actually at the 3000 tier, the swap either reverts (pool at 500 has zero/near-zero liquidity → dispatch permanently fails for native-token payers) or executes at a materially worse price than the true market rate (user overpays for the same `post.fee` amount of feeToken), while `HyperApp.quote()` — used to pre-estimate the required native amount — reports the same mispriced/failing value since it queries the identical hardcoded-fee wrapper [9](#0-8) .

	private async getBestV3Pool(
		client: PublicClient,
		token0: HexString,
		token1: HexString,
		evmChainID: string,
	): Promise<{ poolAddress: HexString; fee: number }> {
		const factoryAddress = this.chainConfigService.getUniswapV3FactoryAddress(evmChainID)

		let mostLiquidPool = ADDRESS_ZERO
		let bestFee = 0
		let deepestLiquidity = 0n

		for (const fee of COMMON_FEE_TIERS) {
			try {
				const poolAddress = (await client.readContract({
					address: factoryAddress,
					abi: [
						parseAbiItem(
							"function getPool(address tokenA, address tokenB, uint24 fee) view returns (address pool)",
						),
					],
					functionName: "getPool",
					args: [token0, token1, fee],
				})) as HexString

				if (poolAddress !== ADDRESS_ZERO) {
					const liquidity = await client.readContract({
						address: poolAddress,
						abi: [parseAbiItem("function liquidity() view returns (uint128)")],
						functionName: "liquidity",
					})

					if (liquidity > deepestLiquidity) {
						deepestLiquidity = liquidity
						mostLiquidPool = poolAddress
						bestFee = fee
					}
				}
			} catch {
				console.warn(`Failed to get V3 pool for fee ${fee}:`)
				continue
			}
		}

		if (mostLiquidPool === ADDRESS_ZERO) {
			throw new Error(`No V3 pools found for tokens ${token0} and ${token1}`)
		}

		return { poolAddress: mostLiquidPool, fee: bestFee }
