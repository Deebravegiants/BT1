### Title
Predictable, unsigned session identifier is stored in a plaintext cookie and returned verbatim by `cookie_session_id`, letting the cookie value alone select and load another shop's session — (`lib/shopify_api/utils/session_utils.rb`, `lib/shopify_api/auth/session.rb`, `lib/shopify_api/auth/oauth.rb`)

### Summary
For non-embedded apps, `SessionUtils.cookie_session_id` returns `cookies['shopify_app_session']` verbatim with no cryptographic verification of who set it. That cookie's value is, by this gem's own design, the deterministic, non-secret session `id` (`"offline_#{shop}"` for offline sessions, `"#{shop}_#{associated_user.id}"` for online sessions) produced in `Session.from` and placed into the cookie unsigned by `Oauth.validate_auth_callback`. Because the identifier carries no secret entropy and is not bound to the browser/cookie jar that completed OAuth, an attacker who can guess/know a victim shop's domain can present that exact string as their own cookie and have the host app's keyed session storage (the pattern the gem's own docs demonstrate) hand back the victim's session/access token.

### Finding Description
The broken binding: `cookie_session_id(cookies) == session_owner(cookies[SESSION_COOKIE_NAME])` is assumed by every caller, but the code only guarantees `cookie_session_id(cookies) == cookies[SESSION_COOKIE_NAME]` — nothing ties the string to the party who legitimately received it.

Trace:
1. `Oauth.validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:96-113`) builds the `Session` via `Session.from`, then for non-embedded apps sets `SessionCookie.new(value: session.id, ...)` — the cookie's value is exactly `session.id`.
2. `Session.from` (`lib/shopify_api/auth/session.rb:107-117`) computes `id = "offline_#{shop}"` for offline tokens or `id = "#{shop}_#{associated_user.id}"` for online tokens — fully deterministic from public/guessable inputs (shop domain, user id), no randomness, no HMAC, no signature.
3. `SessionCookie` (`lib/shopify_api/auth/oauth/session_cookie.rb`) is a plain `T::Struct` with no signing; the docs (`docs/usage/oauth.md:188-193,254-259`) and `BREAKING_CHANGES_FOR_V16.md:41-45` instruct storing/looking up sessions with `cookies[name] = { value: ... }` and `redis.get("session:#{session_id}")` — a bare keyed lookup.
4. On every later request, `SessionUtils.current_session_id` (`lib/shopify_api/utils/session_utils.rb:19-37`) for a non-embedded app only checks the cookie is present, then calls `cookie_session_id(cookies)` (`lib/shopify_api/utils/session_utils.rb:68-71`), which is `cookies[SESSION_COOKIE_NAME]` — returned unconditionally, with **no** HMAC check, no `state` comparison, no JWT `aud`/`iss` check, and the `online` argument is not even consulted in this branch.

None of the invariant's cited guards (`covers?`, `expired?`, `state` comparison, proxy gate) sit on this path: `HmacValidator`/`state` are only used inside `validate_auth_callback` during the one-time OAuth exchange, not on subsequent cookie-based lookups; `JwtPayload`'s `aud` check only applies to the embedded/JWT branch; `Context.embedded?`/`private?` only pick the code path, they don't validate cookie authenticity.

Attacker's exact request: send an HTTP request to the target app with header `Cookie: shopify_app_session=offline_victim-shop.myshopify.com` (or the guessable online form `victim-shop.myshopify.com_<user_id>`). `current_session_id` returns that string unmodified as the "session id" the host app then uses to fetch a `Session` record (per the gem's own documented storage pattern), yielding the victim's access token.

### Impact Explanation
If the host app implements session storage as documented by this gem (key lookup by `session.id`), any attacker who knows or can enumerate a target shop's `.myshopify.com` domain (public, guessable, or simply their own store name pattern) can retrieve that shop's offline access token, or a staff user's online access token if the numeric user id is known/guessable — cross-tenant credential theft, Critical severity, fully repeatable against arbitrary victim shops with no rate limit beyond guessing the shop domain.

### Likelihood Explanation
Requires: the app is configured `is_embedded: false` (cookie-only auth path) and its session storage keys sessions by the raw `session.id` string with no additional server-side binding (a natural reading/implementation of this gem's own documented examples). Attacker cost is a single crafted HTTP request with a forged cookie header — no secrets, no valid prior session, no signed values needed since the gem never signs or randomizes this identifier for offline sessions.

### Recommendation
Do not use a deterministic, guessable string (`offline_#{shop}`, `#{shop}_#{user_id}`) as the value placed directly into a plaintext browser cookie for non-embedded apps. Either (a) sign/encrypt the `SessionCookie` value (e.g., HMAC it with `api_secret_key` and verify server-side in `cookie_session_id`) so an attacker cannot fabricate a valid cookie for an arbitrary shop, or (b) make the cookie value an unguessable random token that is only usable as an indirection key, never the literal shop-derived `session.id`, and document that host apps must never key storage lookups directly off client-supplied values without such a signature.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb
def test_cookie_session_id_returns_forged_deterministic_value_unverified
  ShopifyAPI::Context.stubs(:embedded?).returns(false)
  forged_offline_id = "offline_victim-shop.myshopify.com" # guessable per Session.from
  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_offline_id }

  returned = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)

  # Demonstrates zero integrity check: the exact victim-shaped id is echoed back verbatim,
  # with no HMAC/state/JWT verification anywhere on this path.
  assert_equal(forged_offline_id, returned)
end
```
This matches the existing test `test_non_embedded_app_current_session_id_returns_id_from_cookie` (`test/utils/session_utils_test.rb:80-89`), confirming any client-controlled cookie value — including one matching another shop's deterministic `Session.from` id format — is accepted verbatim as the session identity key. # typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Auth
    module Oauth
      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
    end
  end
end
