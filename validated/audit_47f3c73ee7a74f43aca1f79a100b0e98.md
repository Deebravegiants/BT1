## Finding

### Title
Fee-on-Transfer / deflationary underlying tokens cause insolvency and permanent fund freezing in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable` - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`, `sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol`)

### Summary
`WrappedHyperFungibleToken.send()` (and its upgradeable twin) locks the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then encodes the caller-supplied `params.amount` — not the actual amount received — into the cross-chain `Message` that is dispatched to mint/unlock tokens on the destination chain. Unlike `IntentGatewayV2.placeOrder`, which was hardened to measure actual received balances for fee-on-transfer (FOT) tokens (see `evm/src/apps/IntentGatewayV2.sol`), the wrapped bridge contracts never verify the amount actually locked.

### Finding Description
In `send()`:
```solidity
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
...
bytes memory body = abi.encode(HyperFungibleToken.Message({
    from: abi.encodePacked(msg.sender),
    to: params.to,
    amount: params.amount,   // <-- unchecked, assumed == amount received
    data: params.data
}));
``` [1](#0-0) [2](#0-1) 

If `_underlying` is a fee-on-transfer/deflationary token, the contract receives strictly less than `params.amount`, yet the dispatched ISMP message still commits to `params.amount`. On the destination chain, `onAccept()` unlocks/transfers exactly `message.amount` of the underlying to the beneficiary:
```solidity
IERC20(_underlying).safeTransfer(beneficiary, message.amount);
``` [3](#0-2) 

Because the module addresses are peers of each other and mirror-locked liquidity is shared implicitly through the ISMP message accounting, every `send()` call with an FOT underlying creates a shortfall between what is actually escrowed on the source chain and what is promised/unlocked on the destination side. This directly parallels the reported `VaultLogic.sol` bug class: assuming `balanceOf` deltas equal the nominal transfer amount when moving tokens is unsafe for FOT tokens — except here there isn't even a `require` that would revert the transaction; the mismatch is silently baked into the cross-chain commitment and propagated to the peer contract, which will emit excess claimable balance.

### Impact Explanation
Each such transfer causes the destination-side wrapper contract to owe (mint/unlock) more of the underlying than was actually locked/escrowed on the source side. Over repeated transfers this produces an unbacked entitlement: some users will successfully unlock funds while later users cannot, because the wrapper's real underlying balance runs out before all committed `message.amount` values are honored — a permanent freezing-of-funds condition for the users left unable to redeem, and effectively an insolvency/drain vector for the shared token-bridge float. This satisfies the "unbacked mint" / "permanent freezing of funds" impact bar for a token bridge mint/burn path.

### Likelihood Explanation
Likelihood depends on the wrapper being configured with a fee-on-transfer/deflationary underlying ERC20 token (`configure()` sets `_underlying` to an arbitrary owner-chosen ERC20). Given the wrapper is explicitly designed to wrap "existing ERC20 tokens" generically, and the codebase already anticipated and fixed the exact same class of bug in `IntentGatewayV2` (see the `FeeOnTransferToken` tests in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`), it demonstrates the protocol intends to support such tokens elsewhere but failed to apply the same fix to `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`. Any single `send()` call by an unprivileged user with an FOT underlying reaches this path.

### Recommendation
Measure the actual balance delta after `safeTransferFrom` in `send()`, and use that measured amount (not `params.amount`) both for the locked accounting and for the `Message.amount` field encoded into the dispatched request, mirroring the fix already applied in `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol` lines 313-328):
```solidity
uint256 balBefore = IERC20(_underlying).balanceOf(address(this));
IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
uint256 received = IERC20(_underlying).balanceOf(address(this)) - balBefore;
// use `received` in place of params.amount for Message.amount
```

### Proof of Concept
1. Owner configures `WrappedHyperFungibleToken` with `_underlying` set to a token that charges e.g. a 2% fee on every `transfer`/`transferFrom`.
2. Alice calls `send({amount: 1000, ...})`. The contract's actual underlying balance increases by only 980, but the dispatched `Message.amount` is `1000`.
3. On the destination peer, `onAccept` unlocks 1000 of the underlying to Alice's designated recipient — 20 more than was actually escrowed on the source chain.
4. Repeating this (or reversing direction) drains the shared underlying float faster than it is replenished; eventually a legitimate holder's `onAccept`/timeout refund call reverts due to insufficient balance in the wrapper contract, permanently freezing their funds.

```text
    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
