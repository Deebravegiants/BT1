### Title
Webhook `shop`/`topic` headers are not covered by the HMAC signature, allowing cross-tenant webhook data injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying the HMAC of the raw request body. The `shop`, `topic`, `webhook_id` and `api_version` values that the gem extracts from HTTP headers and hands to the app's handler are never included in the signed payload. Because the app's `client_secret` (and therefore the HMAC) is identical across every shop that has the app installed, anyone who can obtain one validly-signed webhook body (e.g. by installing the app on their own store) can replay that exact body to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and/or topic) header to point at a different, victim tenant. The HMAC check still passes, and the handler receives attacker-controlled `shop`/`topic` attribution for genuinely-signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates only the body HMAC before dispatching the (attacker-influenceable) `shop`/`topic` fields to the registered handler: [3](#0-2) 

`HmacValidator.validate` performs a straightforward constant-time comparison of `HMAC(secret, raw_body)`: [4](#0-3) 

The identity binding that is broken is:
`HMAC(client_secret, raw_body)` is treated as proof of `(shop, topic, raw_body)` together, when it is actually only proof of `raw_body` alone — i.e. `verified(raw_body) ⇏ verified(shop) ∧ verified(topic)`.

Since a single app `client_secret` is shared across every shop that installs the app, any unprivileged internet user can:
1. Install the target app on their own (attacker-controlled) development/trial store — this yields a genuinely, validly-HMAC-signed webhook delivery from Shopify for a body they control/observe (e.g., `orders/create` with an empty or attacker-authored payload).
2. Capture that raw body and its `X-Shopify-Hmac-Sha256` header.
3. Send that exact body + HMAC directly to the app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` header (and optionally the topic header) rewritten to the victim shop's domain.
4. `Registry.process` validates the HMAC against the (unmodified, genuinely signed) body successfully, and calls the handler with `shop: <victim-shop>`, `topic: <chosen-topic>`, `body: <attacker-controlled data>`.

The app's handler — which trusts `WebhookMetadata#shop`/`#topic` as authenticated tenant context — will process attacker-supplied data as if it originated from the victim shop, since nothing in the gem ties the header-derived shop/topic to the signed payload.

### Impact Explanation
This is a cross-tenant boundary break: an attacker with only their own (legitimately installed) shop can inject arbitrary event data attributed to any other shop that uses the same app, without possessing that shop's credentials. Depending on the handler logic (e.g., order/fulfillment/inventory sync, billing events, GDPR events), this can corrupt another merchant's data, trigger unauthorized side effects keyed off webhook topic/shop, or be used to desynchronize/poison per-tenant state — satisfying the "cross-tenant access" Critical impact bucket, since the tenant (shop) attribution boundary is entirely unauthenticated.

### Likelihood Explanation
Likelihood is high for any attacker who can freely obtain an app installation on a store they control (development stores, free trials, or any merchant account) and can send arbitrary HTTP requests to the app's public webhook endpoint. No access token, `client_secret`, or privileged account for the *victim* shop is required — only a normal, self-service install for the attacker's own shop plus header manipulation on a replayed request.

### Recommendation
Bind `shop`, `topic`, and any other header value the handler relies on into the signed material, or otherwise cryptographically tie them to the payload before trusting them:
- Include the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` header values in `to_signable_string` (or otherwise incorporate them into the HMAC computation) so the signature covers the full authenticated context, not just the body.
- Alternatively/additionally, require host applications to look up the shop from a known, pre-registered set of installed shops (server-side) before trusting the header value, and document this expectation clearly in `Webhooks::Registry`/`Request`.
- Consider signing webhook requests per-shop (unique secret material per shop) rather than relying solely on the single app-wide `client_secret`, eliminating cross-tenant replay entirely.

### Proof of Concept
```ruby
# Attacker installs the target app on their own shop "attacker-shop.myshopify.com"
# and receives a legitimate webhook delivery:
raw_body = '{"id":1,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)
# (hmac is valid because it's signed with the shared app client_secret)

# Attacker replays the SAME body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC check passes (Utils::HmacValidator.validate only checks raw_body),
#    handler.handle is invoked with shop: "victim-shop.myshopify.com",
#    even though Shopify never sent this webhook for that shop.
```
