### Title
Webhook `shop`/`topic` identity not covered by HMAC allows cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, but the `shop` (and `topic`) identity that the handler subsequently trusts and acts on is taken from unauthenticated HTTP headers that are never included in the signed material. This breaks the intended binding: `hmac_covers(bytes) == identity_acted_on(bytes)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

The `shop` accessor, however, is read directly from the `shop-domain` header, which is not part of the signed string: [2](#0-1) 

`Registry.process` validates only the HMAC of `request` (i.e., the body) and then immediately trusts `request.shop`/`request.topic` to build the metadata passed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms this: it only ever signs/compares `verifiable_query.to_signable_string`, i.e., the body, using the app's single, shop-independent `api_secret_key`: [4](#0-3) 

Because the same `api_secret_key` is used to validate webhooks for every shop that installs the app, and the `shop-domain` header is not cryptographically bound to the body, any party who can obtain one legitimately-signed `(raw_body, hmac)` pair (e.g., a merchant using the app who receives real webhook deliveries for their own store) can replay that exact body/HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (or `shopify-shop-domain`) header value. `HmacValidator.validate` will still succeed because it never inspects the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from a different (victim) shop.

### Impact Explanation
This breaks the shop-identity binding this gem is expected to provide to host applications: the handler receives `shop: request.shop` believing it has been authenticated together with the body, when in fact it has not. A host application that uses `WebhookMetadata#shop` to select which tenant's data/access token to update (a documented, expected usage pattern) can be tricked into writing/reading data under, or acting with credentials of, a shop the attacker does not own — i.e., cross-tenant access, which the rules classify as Critical impact. This is analogous to the reported bug class: an operation binds trust to bytes that were verified (the HMAC-body), but then acts on a separate field (`shop`) that was never covered by that verification.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one valid `(raw_body, hmac)` pair signed with the app's secret. Any merchant who installs the app and has webhooks configured legitimately receives such pairs for their own store, so a malicious/compromised merchant of a multi-tenant app is a realistic, unprivileged-relative-to-other-tenants attacker. No possession of the app's `client_secret`/`api_secret_key` itself is required — only receipt of a normal webhook delivery, which any installing merchant obtains.

### Recommendation
Bind the shop/topic identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the HMAC-validated payload before trusting it:
- Include `shop`, `topic`, and `webhook-id` in `to_signable_string` (this requires Shopify to sign over these fields), or
- Require the host application to independently verify that `request.shop` matches an expected/allow-listed shop for the delivery (e.g., cross-check against the shop that owns the webhook subscription id) before acting on the payload, and document this requirement clearly in `ShopifyAPI::Webhooks::Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Attacker triggers or waits for a real webhook delivery, capturing the raw body `B` and the valid `X-Shopify-Hmac-Sha256: H` header (computed by Shopify using the app's shared `api_secret_key` over `B`).
3. Attacker POSTs `B` with header `H` to the app's webhook endpoint again, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` succeeds because it only checks `B` against `H` [5](#0-4) .
5. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the host application to process attacker-controlled data as if it belonged to the victim shop.
