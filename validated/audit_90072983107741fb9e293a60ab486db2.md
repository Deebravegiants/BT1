### Title
Fraud/liveness enforcement is fully disabled, allowing any signup to be enrolled as "Normal" without fraud detection - (File: `src/plans/mod.rs`)

### Summary
The Elfi report describes a function (`batchUpdateAccountToken`) that lets any caller directly force privileged internal state (account balance) to attacker-chosen values, bypassing the actual verification/deposit flow that is supposed to gate that state. The closest analog in `orb-core` is `MasterPlan::detect_fraud`, which is supposed to gate whether a signup is classified as `SignupReason::Fraud` before enrollment/PCP upload, but the function body has been stubbed to unconditionally return `Ok(false)` — i.e. the state that should only be reachable after genuine fraud/liveness verification is now reachable unconditionally, for every signup, with no check performed at all.

### Finding Description
`detect_fraud` is invoked from `do_signup` to gate the `signup_reason` used to decide whether a signup should be enrolled or rejected as fraudulent: [1](#0-0) 

The implementation of `detect_fraud` itself contains no verification logic at all — it is hard-stubbed to always return `false` (not fraud), regardless of the biometric pipeline output: [2](#0-1) 

This means `signup_reason` can only ever become `SignupReason::Fraud` if `pipeline` construction itself fails; the dedicated fraud-detection control that is supposed to inspect the completed biometric pipeline result and flag duplicate/fraudulent enrollment attempts never executes. The downstream logic treats every biometric-pipeline-succeeding signup as `SignupReason::Normal`, which then drives both PCP construction/upload and enrollment status: [3](#0-2) 

In effect, an unprivileged individual going through the normal signup flow (no special access, keys, or hardware bypass needed) is treated by the pipeline exactly as if the dedicated fraud-detection subsystem had run and cleared them — even though that subsystem performs zero checks. This directly parallels the reported bug class: a critical state transition (here, "is this signup fraudulent," analogous to "is this balance authorized") is granted without executing the verification logic that is supposed to gate it.

### Impact Explanation
Fraud detection is a named, distinct security control in the signup pipeline (separate from face/iris capture and enrollment), intended to catch fraudulent/duplicate signup attempts before a Personal Custody Package is built and uploaded and before `enroll_user` is invoked. With this control permanently disabled, any signup that produces a biometric pipeline result is unconditionally classified `SignupReason::Normal`, bypassing the intended fraud/liveness gate before enrollment. This matches the "fraud/liveness bypass" impact category explicitly accepted by the validation rules — it does not require any privileged access, secret keys, or physical/hardware tampering, since it happens on the standard, unprivileged signup path for every user.

### Likelihood Explanation
This is not a rare edge case — it is the unconditional, default behavior of the shipped code path for every single signup that reaches the fraud-detection phase (i.e., every signup where the biometric pipeline succeeds). No attacker action, timing, or special input is required to trigger it; it is a root-cause, always-on bypass rather than a probabilistic or hard-to-reach condition.

### Recommendation
Restore or re-implement the fraud-detection logic in `detect_fraud` (or explicitly gate the stubbed-out behavior behind a clearly documented, non-default "FOSS build" flag that cannot silently ship as the production default). At minimum, `detect_fraud` should not unconditionally return `false`; the code should either invoke the actual fraud-check pipeline (as referenced by `fraud_check::Report` and `debug_report.fraud_check_report`) or fail closed (treat unknown/undetectable fraud status as fraud) rather than fail open.

### Proof of Concept
Not directly exploitable via crafted attacker input — this is a code-path analysis rather than an attacker-supplied trigger:
1. Any user performs a normal signup through the standard flow (QR scan, biometric capture) with no special privileges.
2. `do_signup` reaches the fraud-detection phase and calls `self.detect_fraud(...)` per `src/plans/mod.rs:563-564`.
3. `detect_fraud`'s body (`src/plans/mod.rs:1390-1406`) performs no computation and returns `Ok(false)` unconditionally whenever `pipeline` is `Some`.
4. `signup_reason` becomes `SignupReason::Normal` for any signup whose biometric pipeline succeeded, per `src/plans/mod.rs:565-571`, regardless of whether the signup would have been flagged fraudulent by an actual fraud-detection check.
5. The signup proceeds to PCP construction/upload and enrollment as `Normal`, per `src/plans/mod.rs:639-661`, with the fraud gate never having executed any real check.
