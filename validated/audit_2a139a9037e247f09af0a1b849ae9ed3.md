## Analysis

The Pyth bug class here is: **treating a signed magnitude difference as if it always points in one direction**, silently collapsing the other direction to a no-op scale, which corrupts amounts by orders of magnitude when precision moves the "wrong way."

The `hyper-fungible-token` pallet's decimal-conversion helpers reproduce exactly this bug class, and they sit directly on the unprivileged token-bridge mint/refund path. [1](#0-0) 

`convert_to_balance` and `convert_to_erc20` both compute the decimals delta with `erc_decimals.saturating_sub(local_decimals)` and always apply the resulting exponent in a single fixed direction (divide for `convert_to_balance`, multiply for `convert_to_erc20`). `saturating_sub` clamps to `0` whenever `local_decimals > erc_decimals` (for `convert_to_balance`) or `local_decimals > erc_decimals` (for `convert_to_erc20`, same clamp condition), silently treating that case as "no scaling needed" instead of scaling in the opposite direction. This is the same class of error as unconditionally multiplying by `10**|expo|` regardless of the sign of `expo` in the Pyth report.

`convert_to_balance` is invoked in `on_accept`, the handler for an inbound cross-chain token message from *any* registered remote ERC20 contract, using the `erc_decimals` value stored per-`(local_asset_id, source)` pair in `Precisions` and the live local asset decimals: [2](#0-1) 

and it drives `NativeCurrency::transfer` / `Assets::mint_into` for the beneficiary: [3](#0-2) 

The same function and the same collapse also apply on the timeout/refund path: [4](#0-3) 

If the local asset's decimals exceed the registered remote ERC20's `erc_decimals` (a legitimate and plausible configuration — e.g. a local 18-decimal asset bridged to a 6-decimal remote ERC20), `erc_decimals.saturating_sub(local_decimals)` is `0`, so `convert_to_balance` divides by `10**0 = 1`, i.e. it does **not** upscale the raw ERC20 value to local precision at all. This mints/transfers an amount that is `10**(local_decimals - erc_decimals)` times **smaller** than the amount the sender actually locked/burned on the source chain — a silent underpayment to every legitimate depositor for that asset pair. Conversely, on the outbound side `convert_to_erc20` (used when initiating a transfer to the remote chain) would fail to downscale in the mirror case, over/under crediting the destination in the same broken way, since it has the identical `saturating_sub` collapse.

This is not merely a rounding/precision nit: it's a magnitude-order asymmetric conversion bug reachable by any unprivileged user who bridges a token pair configured with `local_decimals > erc_decimals`, matching the reported bug class (Pyth's `expo` sign mistreatment) and creating protocol malfunction/fund-accounting corruption on an ISMP token-bridge mint/refund path — squarely in scope.

### Title
Decimal-scaling direction is silently dropped by `saturating_sub` in `convert_to_balance`/`convert_to_erc20`, corrupting bridged token amounts by orders of magnitude - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` and `convert_to_erc20` in the `hyper-fungible-token` pallet compute the ERC20 ↔ local decimals delta using `erc_decimals.saturating_sub(local_decimals)` and always apply that exponent in one fixed direction (divide-only, multiply-only respectively). When the subtraction underflows (i.e., decimals differ in the opposite direction from what the function assumes), `saturating_sub` returns `0`, causing the function to silently skip scaling instead of scaling the other way.

### Finding Description
`convert_to_balance` is meant to convert an inbound ERC20 `U256` amount (at `erc_decimals` precision) into the local balance representation (`local_decimals` precision) by dividing by `10^(erc_decimals - local_decimals)` when `erc_decimals > local_decimals`. However, when `local_decimals > erc_decimals` (i.e. the local asset uses more decimal places than the registered remote ERC20), the correct operation is to multiply by `10^(local_decimals - erc_decimals)`. Because the code uses `saturating_sub`, this negative difference clamps to `0`, and the function divides by `10^0 = 1`, effectively performing no scaling at all instead of the required upscale. [5](#0-4) 

The symmetric bug exists in `convert_to_erc20`, which multiplies by `10^(erc_decimals.saturating_sub(local_decimals))` when converting a local balance to ERC20 units — it should divide when `local_decimals > erc_decimals`, but instead performs no scaling. [6](#0-5) 

`convert_to_balance` is called directly in the ISMP `on_accept` handler (processing any inbound cross-chain token message from a registered remote ERC20 contract) and in `on_timeout` (refund path), both of which then mint or transfer the resulting `amount` to a beneficiary without any additional bounds check on plausibility. [7](#0-6) 

### Impact Explanation
For any token pair configured with `local_decimals > erc_decimals`, every inbound transfer/mint via `on_accept` (and every refund via `on_timeout`) credits the beneficiary `10^(local_decimals - erc_decimals)` times less than the value actually locked/sent on the source chain. This is a direct funds-loss bug for depositors and a broken accounting invariant for the bridge, matching the reported bug's core defect: an asymmetric, sign-unaware decimal exponent application that corrupts value by orders of magnitude. The reverse configuration corrupts `convert_to_erc20`'s output analogously on the outbound path, over/under-crediting the destination.

### Likelihood Explanation
This triggers deterministically for any token registered with `Precisions` such that `local_decimals > erc_decimals` (a plausible cross-chain configuration, since local pallet-managed assets can be minted with more decimals than the registered remote ERC20's `decimals()`), and it does not require attacker privilege — merely a normal user bridging that token pair after the mismatched decimals configuration is set up by governance/registration.

### Recommendation
Replace the one-directional `saturating_sub` scaling with an explicit signed comparison of `erc_decimals` and `local_decimals`, applying multiplication or division depending on which is larger, symmetrically in both `convert_to_balance` and `convert_to_erc20` (mirroring how `VWAPOracle._normalizeAmount` in `evm/src/utils/VWAPOracle.sol` correctly branches on `_decimals < 18` vs `> 18`).

### Proof of Concept
1. Register a local asset `X` with `local_decimals = 18` and a remote ERC20 contract `E` with `erc_decimals = 6` in `Precisions::<T>`.
2. A user locks `1_000_000` units (1 token at 6 decimals) of `E` on the EVM side and dispatches a bridge message with `message.amount = 1_000_000`.
3. On `on_accept`, `convert_to_balance(U256::from(1_000_000), erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so it returns `1_000_000` divided by `10^0 = 1`, i.e. `1_000_000` raw units — which at 18 local decimals is `0.000000000001` tokens instead of the correct `1_000_000 * 10^12 = 1e18` raw units (1 whole token). The beneficiary receives a mint that is `10^12` times smaller than the value locked on the source chain.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
