### Title
Webhook `shop` (tenant identifier) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` (and `topic`) are taken from unauthenticated HTTP headers that are never part of the signed material. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only and then blindly trusts `request.shop` as the tenant identifier passed to the app's webhook handler.

### Finding Description
The HMAC validation in `Utils::HmacValidator.validate` verifies `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [1](#0-0) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop` (and `topic`, `webhook_id`, `api_version`) are read straight from attacker-visible/settable HTTP headers, with no cryptographic binding to the body or the HMAC: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then forwards `request.shop` directly to the handler as the tenant-identifying field: [4](#0-3) 

This breaks the intended identity binding: `shop_header == shop_that_produced_the_signed_body`. In fact any `(raw_body, hmac)` pair that is valid for one shop remains valid (HMAC still matches) if the `x-shopify-shop-domain` (or `shopify-shop-domain`) header is swapped for a different shop domain, because that header is not part of the signed content.

### Impact Explanation
Any party capable of receiving a legitimately-signed webhook for their own store (e.g., an app developer/merchant who installed the app on their own shop — an "unprivileged" party relative to other tenants) can capture a valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to point at a victim shop. Because `Registry.process` only checks the HMAC of the body, this forged request passes validation and the handler executes with `WebhookMetadata#shop` set to the victim's domain. If the consuming application uses `data.shop` to look up/authorize the tenant record to mutate (a common and encouraged pattern, per the gem's own webhook docs), this results in cross-tenant data corruption/access — falsely attributing (and acting on) webhook data under another merchant's identity. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any host application that trusts `WebhookMetadata#shop` (or `Request#shop`) as an authenticated tenant identifier without independently re-verifying it against the shop associated with the specific registered webhook subscription — which is exactly the intended usage documented for this gem's webhook registry (`docs/usage/webhooks.md`). No secret material is required by the attacker beyond a legitimately delivered webhook to their own shop.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the HMAC-signed material verified by `HmacValidator`, or, at minimum, have `Registry.process` cross-check `request.shop` against the webhook subscription/session that was registered for the given `webhook_id`/topic before invoking the handler, rather than trusting the header value implicitly.

### Proof of Concept
1. App developer installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook: body `{}` with header `x-shopify-shop-domain: attacker-shop.myshopify.com` and a valid `x-shopify-hmac-sha256` computed over that body (see `lib/shopify_api/webhooks/request.rb` and `hmac_validator.rb`).
2. Attacker replays the exact same raw body and HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body/hmac pair.
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now returns `"victim-shop.myshopify.com"`, causing the app to process/act on data as if it came from the victim tenant.
