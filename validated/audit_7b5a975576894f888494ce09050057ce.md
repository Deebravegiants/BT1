### Title
`update_token`'s `remove_chains` deletes `ContractToAsset`/`Precisions` needed by `on_timeout`, permanently freezing in-flight escrowed/burned funds - (File: modules/pallets/hyper-fungible-token/src/lib.rs, modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`pallet-hyper-fungible-token`'s `update_token` extrinsic allows the `CreateOrigin` to remove a chain's configuration (`TokenContracts`, `ContractToAsset`, `Precisions`) for an asset while ISMP `send()` requests dispatched to that chain are still in flight (not yet delivered or timed out). When such a request later times out, `on_timeout` cannot find the asset because the `ContractToAsset` mapping it relies on has been deleted, causing the refund to fail permanently. This mirrors the Renzo `RestakeManager.removeCollateralToken()` bug class: a legitimate, non-malicious configuration change performed while user-initiated obligations are still pending breaks the protocol's ability to make users whole, resulting in permanently frozen or lost funds.

### Finding Description
A user calls `send()` on `pallet-hyper-fungible-token`, which either escrows the native asset in `Self::pallet_account()` or burns a non-native asset from the sender, then dispatches an ISMP `DispatchPost` to the destination chain's token contract: [1](#0-0) 

The dispatched message carries `to = token_contract` for that `(asset, destination)` pair as looked up at send time: [2](#0-1) 

If the request is not delivered before its timeout, `on_timeout` is invoked with the *original* `to`/`dest` recorded in the request body, and it re-derives the local asset via `ContractToAsset::<T>::get(dest, &to)`: [3](#0-2) 

However, `update_token`'s `remove_chains` path deletes exactly this mapping (`ContractToAsset`), along with `TokenContracts` and `Precisions`, for the given `(chain, asset)` pair: [4](#0-3) 

If `update_token` is called with that chain in `remove_chains` at any point between a user's `send()` and the eventual timeout of that request (a normal operational action, e.g. migrating a contract address or deprecating a chain — not requiring any malicious intent), the subsequent `on_timeout` lookup `ContractToAsset::<T>::get(dest, &to)` returns `None` and the call reverts with `UnknownContractOnTimeout`: [5](#0-4) 

Because this refund path can never succeed once the mapping is gone (there is no way to reconstruct the removed contract-to-asset link after the fact, and `pallet-ismp`'s `on_timeout` dispatch is not retried through an alternate path), the escrowed native tokens remain stuck in `pallet_account()` forever, and for non-native (burn/mint) assets the tokens that were already burned from the sender at `send()` time are never re-minted back — a real economic loss with no corresponding balance to redeem it.

This is the direct analog of the Renzo report: an admin action (removing a collateral token / removing a chain's token config) that is legitimate under normal operating assumptions becomes unsafe specifically because user-initiated obligations (pending withdrawals / in-flight cross-chain sends) can still reference the removed configuration, and the protocol has no guard requiring those obligations to be cleared first.

### Impact Explanation
- For native assets: funds transferred to `pallet_account()` in `send()` become permanently unrecoverable once `on_timeout` cannot resolve the asset — a direct freezing of user funds with no recovery mechanism.
- For non-native (bridged) assets: `send()` unconditionally burns the sender's tokens via `Assets::burn_from` before the message is dispatched; if the corresponding `on_timeout` refund (which would `mint_into` the tokens back) fails due to the removed mapping, the user's tokens are burned with no compensating mint — a permanent, protocol-level loss of value for that user.
- There is no code path that recovers from this state: `update_token`'s `add_chains` re-inserts fresh mappings but does not distinguish "re-adding a chain that has pending in-flight requests" from a clean addition, so even re-registering the chain does not automatically fix already-in-flight requests whose refund attempt already failed and reverted (and a reverted `on_timeout` dispatch generally cannot be indefinitely retried by relayers/pallet-ismp for a request that has already timed out and been consumed).

This satisfies "permanent freezing of funds" from the validation criteria.

### Likelihood Explanation
Likelihood is significant in ordinary operation, not just adversarial scenarios: chains get deprecated, token contracts get migrated/redeployed, and `update_token` is the pallet's documented mechanism for handling exactly this ("Add or remove chains from an existing token's configuration"). Any window between an in-flight `send()` and its ISMP timeout (which can be tens of minutes to hours per `params.timeout`) is enough for an unrelated, routine `update_token(remove_chains=[chain])` call to strand that specific in-flight request's refund. No coordination or malice by `CreateOrigin` is required — a single call performed for a legitimate reason breaks the invariant for any concurrently in-flight message to that chain for that asset.

### Recommendation
- Before allowing a chain to be removed via `update_token`'s `remove_chains`, require that there are no undelivered/untimed-out requests outstanding for that `(asset, chain)` pair (e.g., track an in-flight counter incremented in `send()` and decremented in `on_accept`/`on_timeout`, and `ensure!(count == 0)` in `update_token`).
- Alternatively, retain the old `ContractToAsset` (and `Precisions`) entry in a secondary "retired" storage map indexed by `(chain, contract_bytes)` when it's removed from the active `TokenContracts`/`ContractToAsset` maps, and have `on_timeout` fall back to this retired map so in-flight refunds can still resolve the correct asset and decimals even after the chain configuration has been updated/removed.
- Document and enforce a mandatory draining/cool-down period before removing a chain, matching Renzo's own remediation of checking outstanding balances/claims before removal.

### Proof of Concept
1. `CreateOrigin` registers asset `X` (non-native) for `StateMachine::Evm(1)` via `register_token`, setting `TokenContracts(Evm(1), X) = addr`, `ContractToAsset(Evm(1), addr) = X`, `Precisions(X, Evm(1)) = 18`.
2. User Alice calls `send({asset_id: X, destination: Evm(1), amount: 100, timeout: T, ...})`. Her 100 `X` tokens are burned via `Assets::burn_from` in `lib.rs::send` (lines 277-286), and an ISMP `DispatchPost` with `to = addr` is dispatched with a commitment recorded by `pallet-ismp`.
3. Before the request is delivered or times out, `CreateOrigin` calls `update_token({asset_id: X, remove_chains: [Evm(1)], add_chains: []})` — e.g., because the team is migrating `X`'s contract to a new address on Ethereum. This executes `lib.rs` lines 423-430, deleting `ContractToAsset(Evm(1), addr)`, `TokenContracts(Evm(1), X)`, and `Precisions(X, Evm(1))`.
4. The relayer/network fails to deliver Alice's request before timeout `T` (a normal, expected occurrence in cross-chain messaging). `pallet-ismp` invokes `Pallet::<T>::on_timeout` with the original `Request::Post{ to: addr, dest: Evm(1), body, .. }`.
5. In `module.rs::on_timeout`, `ContractToAsset::<T>::get(Evm(1), addr)` now returns `None` (line 236), so the call returns `Err(HftError::UnknownContractOnTimeout)` (line 237) instead of re-minting Alice's 100 `X` tokens.
6. Alice's 100 `X` were burned in step 2 and are never restored — a permanent loss of her funds caused solely by a routine `update_token` call that had nothing to do with her specific transaction.

				// Refund the original sender
				let from_bytes = message.from.as_ref();

					sender_bytes.copy_from_slice(from_bytes);
				} else if from_bytes.len() == 20 {
