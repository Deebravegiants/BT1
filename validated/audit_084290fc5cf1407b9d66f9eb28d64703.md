### Title
Signup authorization reuses stale operator QR/location verification based on a local expiration timer instead of re-validating with the backend - (File: src/plans/mod.rs)

### Summary
The Sherlock report describes a pattern where a protocol substitutes a **local staleness check** for an actual **re-verification against the source of truth** before making an authorization decision (mint/redeem). Orb-core's signup flow contains the same anti-pattern: operator QR-code authorization (`verify_operator_qr_code`) and its associated `location_data` are cached in `OperatorData`, and are reused across the idle loop and across multiple subsequent signups purely based on `operator_data.timestamp.elapsed() < operator_qr_expiration_time` (default 23 hours), rather than re-querying the backend for the operator's current authorization/location status before each signup decision.

### Finding Description
`OperatorData` stores a `qr_code`, `location_data`, and a capture `timestamp`: [1](#0-0) 

In `MasterPlan::run`, `scan_initial_qr_codes` only re-scans/re-verifies the operator QR code with the backend if the cached timestamp has exceeded `operator_qr_expiration_time`; otherwise the previously verified `operator_data` (and its `location_data`) is carried forward unchanged into the next signup iteration: [2](#0-1) 

`scan_remaining_qr_codes` repeats the same pattern: if `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, the cached, previously-backend-verified `operator_data` is reused directly for the *current* signup's authorization/location context without calling `verify_operator_qr_code` again: [3](#0-2) 

The only path that actually calls the backend to re-verify operator authorization and refresh `location_data` is the `_ =>` fallback branch, which is skipped entirely while the cached data is "not stale enough": [4](#0-3) 

This cached `location_data` is not merely cosmetic — it is fed directly into the backend user-status/authorization request that decides whether a *user* QR code (and thus the signup) is `valid`, via `user_qr_validation_use_only_operator_location`, which defaults to `true`: [5](#0-4) [6](#0-5) [7](#0-6) 

The default expiration window is very large — 23 hours: [8](#0-7) 

This exactly mirrors the audited bug class: instead of invoking the actual "update" (`verify_operator_qr_code` → fresh backend call), the code relies solely on a local elapsed-time threshold to decide whether previously-fetched authorization state is still "fresh enough" to drive a security-relevant decision (signup authorization / operator location attribution) for an unrelated, later signup event.

### Impact Explanation
Because the operator's authorization/location state can be reused for up to 23 hours across many independent, unrelated signups, any change in ground truth on the backend side during that window (e.g., operator's session location changes, or a backend-side re-evaluation of eligibility tied to the reported operator location) is not reflected until the local timer expires — the orb makes real signup-authorization decisions using this stale cached location context in the interim. This is directly analogous to `LibUbiquityPool` making mint/redeem eligibility decisions off a stale TWAP because the "update" call was skipped in favor of a time-based staleness check: the underlying source-of-truth call is bypassed, and a security-relevant decision (which signups are authorized/attributed to which operator/location) is made against out-of-date backend state. Multiple unrelated signups performed in the same window can be authorized/attributed using location data from a single, earlier verification — a cross-signup state bleed of authorization context.

### Likelihood Explanation
This path is hit on every normal (non-self-serve) orb operation cycle when the operator QR/location cache has not yet expired (which is nearly always the case given the 23-hour default), so the condition triggers routinely rather than requiring rare or adversarial timing — matching the Sherlock finding's own conclusion that curve-metapool staleness triggers "nearly all the time" for low-traffic pools. No special privileges are needed to be affected; every user going through signup within the caching window is subject to the reused (potentially outdated) operator/location authorization context.

### Recommendation
Re-verify operator authorization/location with the backend (call the `verify_operator_qr_code` equivalent) immediately before using `location_data` in the user-status/authorization decision for each individual signup, rather than gating the refresh purely on a local elapsed-time threshold. If a caching window is kept for UX reasons, treat it strictly as a UX/latency optimization and not as a substitute for confirming backend-authoritative state at the moment an authorization-relevant decision (e.g., `user_qr_validation_use_only_operator_location`) is made.

### Proof of Concept
1. Operator scans/validates their QR code; backend returns `location_data` (e.g., location A) which is cached in `OperatorData` with `timestamp = now`.
2. Within the `operator_qr_expiration_time` window (default 23h), the operator's real location/authorization context on the backend changes (e.g., moves, or is revoked/adjusted server-side).
3. A new, unrelated user begins a signup; `scan_remaining_qr_codes`/`scan_initial_qr_codes` observes `operator_data.timestamp.elapsed() < operator_qr_expiration_time` and skips calling `verify_operator_qr_code` again [3](#0-2) .
4. The stale, cached `location_data` from step 1 is passed into `verify_user_qr_code` → `backend::user_status::request`, influencing the authorization decision for this new, unrelated signup [6](#0-5) .
5. The signup proceeds/is denied based on outdated operator/location context instead of the backend's current state — the same failure mode as making mint/redeem decisions off a stale TWAP.

    async fn scan_initial_qr_codes(
        &mut self,
        orb: &mut Orb,
        qr_codes: &mut QrCodes,
        self_serve: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<()> {
        if self_serve
            && qr_codes
                .operator_timestamp()
                .map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)
        {
            loop {
                let qr_capture_start = Instant::now();
                let operator_qr_code =
                    self.scan_operator_qr_code(orb, None).await?.expect("to never timeout");
                let Some(operator_qr_code) =
                    self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                else {
                    continue;
                };
                let Some((_, operator_location_data)) =
                    self.verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start).await?
                else {
                    continue;
                };
                *qr_codes = QrCodes::Operator {
                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }

#[cfg(not(feature = "skip-user-qr-validation"))]
async fn do_request(
    qr_code: &qr_scan::user::Data,
    operator_data: &OperatorData,
    use_full_operator_qr: bool,
    use_only_operator_location: bool,
) -> Result<Response> {
    let request = if use_only_operator_location {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id,))
            .query(&[
                ("lat", operator_data.location_data.session_coordinates.latitude),
                ("lon", operator_data.location_data.session_coordinates.longitude),
            ])
    } else if use_full_operator_qr {
        super::client()?
            .get(format!("{}/api/v2/session/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
            .query(&[("operator_id", &operator_data.qr_code.user_id)])
    } else {
        super::client()?
            .get(format!("{}/api/v1/user/{}/status", *SIGNUP_BACKEND_URL, qr_code.user_id))
    }
    .basic_auth(&*ORB_ID, Some(get_orb_token()?));
