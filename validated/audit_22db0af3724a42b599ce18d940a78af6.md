### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted as the tenant identity but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then hands the caller-supplied (and unauthenticated) `shop-domain`, `topic`, `webhook-id` and `api-version` HTTP headers straight into the merchant-facing handler as if they had been verified. This is the same class of bug as the KUMA finding: the code checks one identity (the bytes that produced a valid signature) but acts on a different, unverified identity (the shop the data is attributed to).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

and `shop`, `topic`, `webhook_id`, `api_version` are all read directly from HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (i.e. the raw body for webhooks) and compares it with `secure_compare`: [3](#0-2) 

`Registry.process` then raises only if the HMAC (of the body) is invalid, and otherwise forwards the **unauthenticated** `request.shop`, `request.topic`, `request.webhook_id`, `request.api_version` to the app-supplied handler: [4](#0-3) 

The binding that should hold is:
`shop_the_HMAC_was_computed_for == shop_the_handler_is_told_the_data_belongs_to`

In this code, the left side does not exist at all — the HMAC only proves "this body was produced by someone possessing `api_secret_key`" — it says nothing about which shop the body is for. The right side (`request.shop`, taken from the `x-shopify-shop-domain`/`shopify-shop-domain` header) is attacker-controllable, exactly like the KUMA bug where `approve()` checked `msg.sender`/`to` but not the actual token owner.

### Impact Explanation
Any entity that can install the app on **their own** store (a normal, unprivileged action — e.g. registering a free/dev install) receives genuine webhook deliveries for their own shop, complete with a valid `x-shopify-hmac-sha256` computed with the app's shared `api_secret_key`. Because the signature covers only the body, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and `topic`/`webhook-id`) with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the headers), and `Registry.process` calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` attributing the attacker's own webhook body to the victim tenant.

Any host application that follows the gem's documented pattern — using `data.shop` from the webhook handler to look up the tenant's session/store record and apply the event (e.g., update inventory, mark orders paid, redact/delete customer data for `customers/redact`) — will act on forged, cross-tenant data. This satisfies the "cross-tenant access" criterion: an attacker with no credentials for the victim shop can inject fabricated webhook events attributed to that shop.

### Likelihood Explanation
Likelihood is high for any app that installs on more than one shop (which is the norm for public apps): the attacker only needs their own (attacker-controlled) install to obtain a validly-signed body/HMAC pair, and needs no access to `api_secret_key`, tokens, or the victim shop at all — they only spoof headers, which are never covered by the signature. The mandatory `customers/redact`, `customers/data_request`, `shop/redact` topics make the impact concrete: an attacker can forge a `shop/redact` or `customers/redact` event for a victim shop.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the authenticated payload rather than trusting headers outright:
- Extend `to_signable_string` (or add a second verification step) so the `shop-domain` header is included in the HMAC input, matching what Shopify actually signs, or
- Independently verify the `shop-domain` header against a known/registered shop for the given `access_token`/session before dispatching to the handler, and
- Validate `topic` against the registration key rather than trusting the header value for dispatch decisions when the topic drives sensitive data actions.

### Proof of Concept
1. Install the target app on an attacker-controlled shop (`attacker-shop.myshopify.com`); this is a normal, unprivileged action available to anyone.
2. Shopify sends the attacker a genuine webhook, e.g. `customers/redact` for `attacker-shop.myshopify.com`, with header `x-shopify-hmac-sha256: <valid HMAC over raw_body>`.
3. Attacker replays the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally alters `x-shopify-topic`/`x-shopify-webhook-id`).
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks the raw body.
5. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` (lines 188-200) invokes the app's handler with `shop: "victim-shop.myshopify.com"`, causing the host app to act on forged data attributed to a shop the attacker never had access to.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
