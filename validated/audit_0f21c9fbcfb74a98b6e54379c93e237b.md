This confirms the pattern. `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token` all call `Utils::ShopValidator.sanitize!(shop)` before building a session and sending the request (which includes `client_secret: Context.api_secret_key` in the POST body) to `https://#{session.shop}/admin/oauth/access_token` via `HttpClient`, whose base URI is built directly as `"https://#{api_host || session.shop}"` [1](#0-0) . `TokenExchange.exchange_token`, however, derives `dest_shop` straight from the JWT's `dest` claim without ever passing it through `ShopValidator.sanitize!` [2](#0-1) , and `JwtPayload` itself never validates that `dest`/`iss` is a trusted Shopify domain — it only checks `aud == Context.api_key` [3](#0-2) .

### Title
Missing shop-domain sanitization in `TokenExchange.exchange_token` sends `client_secret` to an unsanitized host derived from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` builds the token-exchange request host directly from the session token's `dest` claim without passing it through `Utils::ShopValidator.sanitize!`, unlike the sibling methods `client_credentials`, `refresh_access_token`, and `migrate_to_expiring_token`, which all sanitize `shop` before use.

### Finding Description
`exchange_token` decodes the session token via `JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop` [4](#0-3) . `JwtPayload#shop` is simply `@dest.gsub("https://", "")` with no domain allow-list check [5](#0-4) , and the constructor only enforces `aud == Context.api_key`, never validating that `iss`/`dest` belongs to a trusted `*.myshopify.com`/`myshopify.io`/`shopify.com` domain [6](#0-5) . `dest_shop` is then used unmodified to build `shop_session`, which `HttpClient` turns directly into the request host (`"https://#{api_host || session.shop}"`) for the POST that carries `client_id` and `client_secret: ShopifyAPI::Context.api_secret_key` [7](#0-6) [1](#0-0) .

By contrast, `client_credentials`, `refresh_access_token`, and `migrate_to_expiring_token` all call `validated_shop = Utils::ShopValidator.sanitize!(shop)` before constructing the session, which raises `Errors::InvalidShopError` unless the host matches `TRUSTED_SHOPIFY_DOMAINS` [8](#0-7) [9](#0-8) [10](#0-9) [11](#0-10) . This shows the maintainers intentionally treat "shop host that receives the `client_secret`" as a value that must be bound to a trusted domain — but that binding is missing specifically on the `exchange_token` path.

The binding that should hold is: `host receiving client_secret == trusted Shopify domain`. For every other credential-issuing method this is enforced by `ShopValidator.sanitize!`; for `exchange_token` it degrades to `host receiving client_secret == whatever string is in the JWT dest claim`, with no allow-list check.

### Impact Explanation
If it is possible for `dest` to be attacker-influenced (e.g., by a compromised/rogue extension context, a non-Admin token issuer, or via the `JWT_LEEWAY`-based cross-secret fallback in `JwtPayload#initialize` combined with `old_api_secret_key` rotation misuse), the app's `client_secret` and `client_id` would be POSTed to an attacker-controlled host, resulting in `client_secret` exfiltration — a Critical-severity outcome per the stated impact categories (theft of the app's `client_secret`). Even short of full forgery, this is a clear violation of the "host validated versus host that receives the client_secret" defensive pattern that the rest of the module enforces, and it is inconsistent/latent risk that should be fixed defensively regardless of whether a concrete forgery path exists today.

### Likelihood Explanation
Exploitability is bounded by the fact the JWT signature is verified against `Context.api_secret_key` (or `old_api_secret_key`) before `dest` is trusted [12](#0-11) , so an external attacker without knowledge of the API secret cannot forge a token with an arbitrary `dest`. I could not find, within the in-scope library code, a path that lets an unprivileged internet user supply an unsigned or wrongly-scoped `dest` value that reaches `exchange_token` — the missing `ShopValidator.sanitize!` call is a defense-in-depth omission/inconsistency rather than a proven, directly reachable exploit for an unauthenticated attacker. I was not able to fully verify whether any other in-scope code path (e.g., a JWT signed under a rotated `old_api_secret_key` with a different trust boundary, or any host-application misuse the gem's docs implicitly allow) could inject an untrusted `dest` before reaching `exchange_token`.

### Recommendation
Add `dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)` in `TokenExchange.exchange_token` immediately after extracting `dest_shop`, mirroring `client_credentials`, `refresh_access_token`, and `migrate_to_expiring_token`, so the host that receives `client_id`/`client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not independently reproducible with unprivileged-attacker-only access in the current codebase, because the JWT signature check (`aud`/HMAC via `Context.api_secret_key`) blocks forgery of the `dest` claim without knowledge of the API secret. The finding is presented as a code-consistency / defense-in-depth gap: `exchange_token` is the only credential-issuing method in `lib/shopify_api/auth/**` that skips `ShopValidator.sanitize!` on the shop value used to build the request host that receives `client_secret`.
