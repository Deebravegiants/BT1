### Title
Webhook `shop` tenant identifier is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the body's HMAC and then dispatches to the handler using `request.shop` taken straight from the header, with no cross-check that the header matches the body's actual tenant [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`shop used for tenant dispatch (request.shop, from X-Shopify-Shop-Domain header) == shop that produced/authorized the signed bytes (raw_body, covered by hmac)`

`HmacValidator.validate` only recomputes the signature over `verifiable_query.to_signable_string`, i.e. the raw body [4](#0-3) . The `shop-domain` header is never mixed into the signed string, so its authenticity is not established — the HMAC only proves "this body was produced with the app's `client_secret`," not "this body/shop pairing was produced together."

Because `Registry.process` trusts `request.shop` directly for building `WebhookMetadata` passed to the app's handler [5](#0-4) , an attacker who can obtain one validly-signed webhook body (e.g., from their own dev/trial store on which the target app is installed) can replay that exact `raw_body` + `hmac-sha256` pair while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still pass because it never inspects the header, and the handler will process the payload as belonging to the attacker-chosen shop.

This is the same class of bug as the referenced report: a value that drives sensitive logic (`feesUpdatedAt`/tenant-shop) is decoupled from the value actually protected by the cryptographic/state check (fee amount at collection time / HMAC-signed body).

### Impact Explanation
This enables cross-tenant confusion: a handler that keys per-shop side effects (data storage, redaction, entitlement checks, webhook-id dedup) off `WebhookMetadata#shop` can be made to attribute one shop's legitimately-signed webhook body to a different, victim shop identifier, without possessing the app's `client_secret` for the victim shop. This satisfies the "cross-tenant access" criterion for a Critical-impact finding, since it lets an unprivileged actor who merely has access to their own store's webhook traffic move data/actions across tenant boundaries in code that trusts this gem's `shop` accessor.

### Likelihood Explanation
Requires only: (1) installing the target app on any shop the attacker controls (mandatory topics like `customers/redact`, `customers/data_request`, `shop/redact` are always fired to installed apps), (2) capturing one legitimate webhook delivery (body + `hmac-sha256` header) for that shop, and (3) resending it to the app's webhook endpoint with a different `shopify-shop-domain` header value. No secret material, TLS interception, or privileged account is needed — this is fully reachable by any unprivileged internet user who can install a free/dev shop.

### Recommendation
Bind `shop` (and ideally `topic`) into the signed material checked by `HmacValidator`, or have `Registry.process` independently verify that the shop domain in the header is consistent with data embedded in `parsed_body` (Shopify webhook payloads typically include the shop's own id/domain in the body for many topics) before constructing `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop` is not integrity-protected by the HMAC and must not be trusted alone for tenant-scoped authorization decisions.

### Proof of Concept
1. Install the target app (using this gem) on attacker-owned shop `attacker.myshopify.com`; Shopify delivers a legitimately signed webhook, e.g.:
   ```
   POST /webhooks
   X-Shopify-Topic: customers/data_request
   X-Shopify-Hmac-Sha256: <valid-for-body>
   X-Shopify-Shop-Domain: attacker.myshopify.com
   Body: {"shop_id": ..., "customer": {...}}
   ```
2. Attacker captures the exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
3. Attacker resends the identical body/HMAC to the same endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` [6](#0-5)  still returns `true` because only the body bytes are checked.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ...)` [5](#0-4)  and invokes the app's handler as if the (attacker-controlled) payload legitimately originated from `victim.myshopify.com`.
