### Title
Webhook shop identity not bound to HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC-signable string from the raw request body only, while the `shop` (tenant identity), `topic`, and `webhook_id` are all taken from unauthenticated HTTP headers. `Registry.process` validates only the body-derived HMAC and then dispatches the handler using the header-derived `shop`, so the tenant binding the app relies on to process the webhook is never covered by the signature check.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read straight from headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately dispatches the handler using `request.shop`, trusting it as the authenticated tenant identity: [3](#0-2) 

`HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against the received HMAC — for webhooks that string is the body alone: [4](#0-3) 

This breaks the identity binding `authenticated_bytes == (body, shop)`; in reality it only enforces `authenticated_bytes == body`. Contrast this with the OAuth callback flow, where `shop` (along with `host`, `code`, `state`, `timestamp`) is explicitly included in the signable string and therefore is bound by the HMAC: [5](#0-4) 

Because the webhook `shop` header is excluded from the signed bytes, any two webhook deliveries with identical bodies (e.g. two shops updating a product with the same field values, or an attacker replaying a captured payload) produce identical valid HMACs regardless of which shop header is attached.

### Impact Explanation
An unprivileged actor who legitimately installs the app on their own store (no special privileges beyond a normal merchant account) can trigger a real webhook delivery to the app and capture a body + valid HMAC pair. Because the HMAC never covers `shop`, that exact body/HMAC pair can be resubmitted to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a different (victim) shop. `HmacValidator.validate` will still pass, and `Registry.process` will hand the handler a `WebhookMetadata` whose `shop` field claims to be the victim tenant. If the host application uses that `shop` value to look up the victim's stored session/access token or to perform tenant-scoped side effects (the intended and documented use of `WebhookMetadata#shop`), this results in cross-tenant confusion — actions or data attributed to the wrong merchant.

### Likelihood Explanation
Moderate-to-high: no access token, `client_secret`, or privileged account is required — only the ability to make the app process a normal webhook for a shop the attacker controls, which is standard, unprivileged app usage. The header-vs-body decoupling is deterministic and always exploitable once any body/HMAC pair is known; no timing or race condition is needed.

### Recommendation
Include the tenant-identifying header value (`shop`) — and ideally `topic`/`webhook_id` — in the HMAC-signable material for webhooks, or otherwise cryptographically bind the shop domain to the payload before it is trusted downstream. At minimum, document (and enforce in `Registry.process`) that `request.shop` must be cross-checked by the host application against the shop associated with the session/token used to register that webhook, rather than treated as an authenticated value on its own.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; attacker triggers an event (e.g. `products/update`) causing Shopify to deliver a webhook with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker resubmits the same body `B` and same header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)`, which still equals `H` (body untouched) — validation passes.
4. `Registry.process` dispatches the handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`; the app processes/attributes the event as belonging to `victim-shop.myshopify.com` even though it never sent this webhook, achieving cross-tenant confusion using only the attacker's own legitimate app installation.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
