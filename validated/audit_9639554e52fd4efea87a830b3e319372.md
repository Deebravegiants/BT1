### Title
Reentrant Drain via State Update After External Call in Tron `IntentGatewayV2.withdraw` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of the Intent Gateway's escrow-release routine, `withdraw()`, sends native BNB/TRX or ERC-20 tokens to the beneficiary and only decrements the corresponding `_orders[commitment][token]` escrow balance *after* the external transfer completes, for every token processed in the loop. This is the exact "pay-then-account" pattern described in the external GG-2 report, and unlike the primary EVM implementation, this Tron contract has no `nonReentrant`/lock protection.

### Finding Description
In `withdraw()`, for each token in the withdrawal body, the escrow amount is checked, an external transfer is executed, and only afterward is the escrow balance reduced: [1](#0-0) 

Compare this to the corrected pattern in the main EVM `IntentsBase._withdraw`, where the escrow is decremented **before** the transfer (checks-effects-interactions): [2](#0-1) 

The main EVM `IntentGatewayV2.fillOrder` is also explicitly hardened with a `nonReentrant` modifier and the `_filled[commitment] = msg.sender` guard set at the very top of `_fillSameChain`/`_fillCrossChain` before any external call, and this fix is validated by a dedicated regression suite (`IntrinsicIntentsReentrancyTest.sol`): [3](#0-2) [4](#0-3) 

No equivalent `nonReentrant`/`ReentrancyGuard` usage exists anywhere under `evm/tron/`, confirmed by searching the Tron contracts directory. The Tron `withdraw()` sets `_filled[body.commitment] = beneficiary` at the top (line 693), which blocks a second full finalization of the *same* commitment, but it does not protect the per-token escrow bookkeeping inside the loop itself: if the beneficiary is a malicious contract that receives the native-token transfer at `beneficiary.call{value: amount}("")` (line 703), its fallback executes before `_orders[body.commitment][token] -= amount` runs for that token (line 710) and before subsequent tokens in the same loop are processed. Any externally reachable function that reads `_orders[commitment][token]` to compute a payout (e.g., cancellation/refund style logic sharing the same mapping) can be re-entered mid-loop and observe stale, not-yet-decremented escrow balances, enabling a double-payout of the same escrowed funds.

### Impact Explanation
A malicious beneficiary contract that is the target of a same-commitment, multi-token (or native + fee-token) `withdraw()` can, via its `receive()`/fallback hook, drain escrowed input tokens or fee-token balances beyond what was actually reserved for that order, directly stealing funds from the Intent Gateway's escrow pool.

### Likelihood Explanation
The withdrawal path is reachable by any solver/user acting as, or colluding with, a malicious `beneficiary` contract address in a normal order fill/cancel flow — no privileged role is required, satisfying the "unprivileged... token bridger/intent solver" reachability bar. The precondition is simply that the beneficiary is a contract address, which is fully attacker-controlled.

### Recommendation
Apply the same fix already shipped in `evm/src/apps/intentsv2/IntentsBase.sol` to the Tron contract: decrement `_orders[body.commitment][token]` (and the `TRANSACTION_FEES` bucket) **before** performing the external `.call`/token transfer, and add a `nonReentrant` guard (or an equivalent lock modifier) to any externally reachable entry point that can trigger `withdraw()` or read/write the same `_orders` mapping.

### Proof of Concept
1. Attacker deploys a `Malicious` contract as the `beneficiary` of an order with at least two escrowed tokens: native TRX/BNB and an ERC-20 (or fee token).
2. The order settlement flow calls `withdraw()`; the loop reaches the native-token entry first: `beneficiary.call{value: amount}("")` fires before `_orders[commitment][address(0)] -= amount` executes. [5](#0-4) 
3. `Malicious.receive()` re-enters an externally callable function that reads `_orders[commitment][erc20Token]` (still un-decremented) to compute a refund/cancel amount and triggers a second payout of the same ERC-20 escrow.
4. The outer `withdraw()` call resumes, decrements and pays out the ERC-20 leg again as originally intended — resulting in the ERC-20 escrow being paid out twice for one order.
