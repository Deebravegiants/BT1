Audit Report

## Title
Unauthenticated LOOP plugin discovery, metrics, and pprof/profiling endpoints on the primary web server - ([File: core/web/router.go])

## Summary
`NewRouter` registers `loopRoutes(app, api)` on the same `api` group as the rest of the public API, applying only rate-limiting and session-cookie middleware — no `auth.Authenticate` wrapper — while `loopRoutes` itself binds `/discovery`, `/plugins/:name/metrics`, `/plugins/:name/debug/pprof/*profile`, and `/plugins/:name/debug/pprof/symbol` with zero auth checks. <cite repo="AYontt/chainlink--015" path="core/web/router.go" start="77-91" /> <cite repo="AYontt/chainlink--015" path="core/web/router.go" start="230-236" /> This is inconsistent with the codebase's own convention that debug/profiling endpoints require authentication, as shown by `debugRoutes` (`/debug/vars`) requiring session auth, and `metricRoutes` (`/v2/debug/pprof/*`) being deliberately nested inside the authenticated `authv2` group.

## Finding Description
In `NewRouter`, the `api` group is built with only `rateLimiter` and `sessions.Sessions` middleware, and `loopRoutes(app, api)` is called directly on it: <cite repo="AYontt/chainlink--015" path="core/web/router.go" start="77-91" />. Inside `loopRoutes`, four handlers are registered with no auth middleware applied at all: <cite repo="AYontt/chainlink--015" path="core/web/router.go" start="230-236" />.

Contrast this with `debugRoutes`, which wraps `/debug/vars` in `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession)` <cite repo="AYontt/chainlink--015" path="core/web/router.go" start="180-183" />, and `metricRoutes`, which is only ever invoked inside the `authv2` group protected by token/session auth: <cite repo="AYontt/chainlink--015" path="core/web/router.go" start="438-447" />, <cite repo="AYontt/chainlink--015" path="core/web/router.go" start="245-249" />.

The handler implementations confirm the exposed surface:
- `discoveryHandler` enumerates all registered LOOP plugins, revealing internal hostnames and Prometheus ports for the node and each plugin. <cite repo="AYontt/chainlink--015" path="core/web/loop_registry.go" start="52-65" />
- `pluginMetricHandler` proxies to `http://<loopHostName>:<PrometheusPort>/metrics` for any plugin name supplied in the URL, with no credential check. <cite repo="AYontt/chainlink--015" path="core/web/loop_registry.go" start="96-127" />
- `pluginPPROFHandler` and `pluginPPROFPOSTSymbolHandler` proxy arbitrary `net/http/pprof` profile requests (including attacker-controlled `debug`, `gc`, and `seconds` query parameters, with `seconds` directly controlling request timeout duration) to the plugin's internal debug port. <cite repo="AYontt/chainlink--015" path="core/web/loop_registry.go" start="130-188" />

The `NewLoopRegistryServer` constructor sets `exposedPromPort` to the node's own `WebServer().HTTPPort()` <cite repo="AYontt/chainlink--015" path="core/web/loop_registry.go" start="39-50" />, confirming these routes live on the same externally-reachable primary web server port as the rest of the authenticated API — not a separate internal-only listener.

The existing test suite (`loop_registry_test.go`) exercises `/discovery` and `/plugins/mockLoopImpl/metrics` using a plain unauthenticated `app.NewHTTPClient(nil)` client and asserts `200 OK`, confirming this is the intended (if flawed) behavior, not a test artifact of a separately-secured route.

I was unable to verify from the available tooling whether this specific issue has previously been triaged, fixed, or acknowledged upstream (e.g., via a later PR moving these routes into an authenticated group, or documentation stating these endpoints are intentionally exposed for external Prometheus scraping and are expected to be protected at the network/deployment layer rather than in-app). The repository only shows a single "Initial commit" in its history for both `router.go` and `loop_registry.go`, so no fix history is visible here.

## Impact Explanation
An unauthenticated network-reachable attacker (no credentials, no session, no API token) can:
- Enumerate internal LOOP plugin topology/ports via `/discovery`, aiding reconnaissance.
- Repeatedly scrape internal plugin `/metrics` without authentication (information disclosure).
- Trigger CPU/heap/goroutine/trace profiling via `/plugins/:name/debug/pprof/*` with attacker-controlled `seconds`, potentially causing resource exhaustion on plugin processes and exposing runtime memory/stack data.

This is a genuine inconsistency with the codebase's stated security model: the functionally identical `/v2/debug/pprof` routes are explicitly gated behind authentication, while the LOOP-plugin equivalent is not. This maps to Chainlink's in-scope "node API authentication bypass" impact category, though the disclosed information (internal hostnames/ports, plugin metrics, profiling data) is lower severity than credential/key theft or fund movement, and DoS-only impacts are typically discounted per bounty program norms (SECURITY.md excludes "Impacts that only require DDoS").

## Likelihood Explanation
High reachability: these routes are unconditionally registered on the primary API group whenever LOOP plugins are configured (which is a default/common configuration for OCR2 nodes), require no special setup to reach, and are demonstrably invoked successfully by an unauthenticated HTTP client in the existing test suite (`loop_registry_test.go`).

## Recommendation
Wrap the routes registered by `loopRoutes` in an authenticated group (e.g., reuse `auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession)` as done for `authv2`/`metricRoutes`), or bind the LOOP discovery/metrics/pprof endpoints to a separate internal-only listener not exposed on the primary externally-facing web server port.

## Proof of Concept
```
# No credentials required
curl http://<node-host>:<webserver-port>/discovery
curl http://<node-host>:<webserver-port>/plugins/<pluginName>/metrics
curl "http://<node-host>:<webserver-port>/plugins/<pluginName>/debug/pprof/profile?seconds=60"
```
This matches the pattern already verified in `core/web/loop_registry_test.go` (lines 99-140), where an unauthenticated `client := app.NewHTTPClient(nil)` successfully retrieves `200 OK` from `/discovery` and `/plugins/mockLoopImpl/metrics`.
