### Title
Excess native-token payment during `dispatch`/`fundRequest` is refunded to `EvmHost` instead of the caller, permanently locking user funds - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all let users pay the relayer fee in native token by calling Uniswap's `swapETHForExactTokens` with the entire `msg.value`. Any unused ETH from that swap is refunded by the Uniswap router to its immediate caller — `EvmHost` itself — not to the original transaction sender, and `EvmHost` has no mechanism to forward or let users reclaim that stray ETH.

### Finding Description
In `dispatch(DispatchPost)`, when a user pays in native token, the contract swaps exactly `post.fee` worth of fee token out of `msg.value`: [1](#0-0) 

The same pattern repeats in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

`IUniswapV2Router02.swapETHForExactTokens(amountOut, path, to, deadline)` computes the exact ETH input required (`amounts[0]`) via `getAmountsIn`, performs the swap for `to = address(this)` (the fee token recipient), and refunds `msg.value - amounts[0]` — but that refund goes to the **caller of the router**, which is `EvmHost`, not the end user who sent the original transaction to `EvmHost`. `EvmHost` has no `receive()`/refund logic to forward that leftover ETH back to `_msgSender()`, and no public withdrawal path exposed to the original payer to recover it.

This is structurally identical to the reported `Multicall.click()` bug: the caller sends `msg.value` computed from an off-chain/estimated price, the actual amount consumed can be less than what was sent (here, due to slippage/estimation buffer rather than a mutable `entryFee`), and the difference is stranded in the contract with no return path to the user. The SDK's own fee-estimation code applies a deliberate 2x buffer under the assumption the excess will be refunded to the user by the router (see comment in `HyperbridgeLzEndpoint.quote`: "Excess native is refunded by the uniswap router"), which is incorrect for this call pattern since `EvmHost`, not the user, is the router's `msg.sender`. [4](#0-3) 

### Impact Explanation
Any unprivileged user who dispatches a POST/GET request or funds a pending request with native token and sends `msg.value` even slightly above the exact amount needed to cover `post.fee`/`get.fee`/`amount` (which is expected and encouraged by SDK tooling that applies buffers to absorb slippage) permanently loses the difference. The ETH is not burned but becomes native balance of `EvmHost` with no user-facing recovery mechanism, constituting a permanent freezing/loss of user funds. This is systemic — it affects every native-token dispatch across all EVM deployments of `EvmHost`, not a one-off edge case.

### Likelihood Explanation
High. Native-token payment is a first-class, documented payment method for `dispatch`/`fundRequest` and is actively used by integrators (e.g., `HyperbridgeLzEndpoint.send`, `HyperFungibleToken.send`, `IntentGatewayV2`). Because Uniswap V2 exact-output swaps require the caller to send `msg.value` at least equal to (and typically more than, due to slippage/estimation buffers) the exact required input, triggering the excess-refund-to-wrong-address path happens on essentially every native-token dispatch, not just an adversarial edge case.

### Recommendation
After calling `swapETHForExactTokens`, check the router's return value (`amounts[0]`, the actual ETH consumed) and forward the leftover `msg.value - amounts[0]` back to `_msgSender()` via a low-level call, or use `swapETHForExactTokens`'s refund with an explicit sweep in `EvmHost` that returns unspent native balance to the caller within the same transaction. Alternatively, require and enforce `msg.value == quoted amount` and revert on mismatch, consistent with the recommendation in the referenced report.

### Proof of Concept
1. User estimates the native ETH needed for a `dispatch(DispatchPost)` call with `post.fee = 100` fee-token units, adding a buffer (as recommended by SDK docs / `HyperbridgeLzEndpoint.quote`, which applies a 2x safety margin) and sends `msg.value = 2X` where `X` is the exact ETH needed. [1](#0-0) 
2. `EvmHost.dispatch` calls `swapETHForExactTokens{value: 2X}(100, path, address(this), deadline)`.
3. The router only needs `X` ETH to produce `100` fee tokens; it refunds `2X - X = X` ETH — but to `msg.sender` of the swap call, which is `EvmHost`, not the original user.
4. The request is dispatched successfully, but the user's leftover `X` ETH is now stuck as `EvmHost`'s native balance with no code path returning it to the user. [2](#0-1)
