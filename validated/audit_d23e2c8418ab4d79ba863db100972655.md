## Title
Webhook Shop Identity Not Bound by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (tenant identity) is read from an unauthenticated HTTP header. `Registry.process` validates the HMAC and then unconditionally trusts the header-derived `shop` value when dispatching to the app's handler, so the body integrity check and the tenant identity are not bound together.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the signed material: [2](#0-1) 

`Registry.process` validates only the HMAC of the request (i.e., the body), then immediately builds and dispatches `WebhookMetadata` using `request.shop` as the trusted tenant identifier for the handler: [3](#0-2) 

Because `HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` (the raw body) against the computed signature: [4](#0-3) 

...the binding the library implicitly asserts — `hmac_valid(body) == true` implies `shop == the tenant that produced this body` — does not hold. The two are independently controllable: `raw_body + hmac` come from one channel (Shopify's genuine signed delivery to *some* shop that has the app installed) while `shop` comes from an entirely different, unauthenticated header field on the same HTTP request.

### Impact Explanation
Any shop that has installed the app (an "unprivileged" tenant relative to other tenants of the same app) receives genuinely Shopify-signed webhook deliveries (`raw_body` + valid `hmac`) for its own store. Since the `shop` header is not part of the signed payload, that same `raw_body`/`hmac` pair remains valid when replayed to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to name a different (victim) shop. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` together with data that actually originated from the attacker's own store. Any host application that uses `data.shop` (as documented/intended by this gem) to key session lookups, per-tenant data storage, or trigger tenant-scoped actions will attribute attacker-controlled webhook content to another merchant's tenant — a cross-tenant data/identity confusion.

### Likelihood Explanation
Exploitation requires no privileged access: an attacker only needs a normal (e.g., free trial/dev) installation of the target app so that Shopify delivers real signed webhooks to them, which they can then replay with a forged shop header. This is a low-effort, low-privilege attack path reachable purely by using the app's own documented webhook flow.

### Recommendation
Bind the `shop` identity into the value that is authenticated. Either include the shop domain in the HMAC-signable string used by `Request#to_signable_string`/`HmacValidator`, or have `Registry.process`/the host-facing API cross-check `request.shop` against an independently established, authenticated source of truth (e.g., the shop associated with the specific webhook subscription/session) rather than trusting the header value outright after only validating the body's HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`), receiving a genuine Shopify delivery: headers include `x-shopify-hmac-sha256: <valid_hmac_of_body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, with some `raw_body`.
2. Attacker replays this exact `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into `shop = "victim-shop.myshopify.com"`, `hmac` from the header, and `to_signable_string = raw_body` (unchanged).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` and matches — validation succeeds.
5. The handler is invoked via `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...))`, causing the host app to process attacker-supplied data as if it belonged to `victim-shop`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
