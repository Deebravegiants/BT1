### Title
Webhook `shop-domain` Header Is Not Covered by HMAC Signature, Allowing Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` (and `topic`, `webhook_id`, `api_version`) attributes exclusively from unauthenticated HTTP headers, while `to_signable_string` — the value used to validate the webhook's HMAC — is defined as only the raw request body. This breaks the identity binding that `Registry.process` implicitly relies on: "the HMAC was computed by Shopify for *this* webhook" is treated as equivalent to "the HMAC was computed by Shopify for *this shop*," when in fact the shop identity is never part of the signed material.

### Finding Description
The webhook signature-validation flow is: [1](#0-0) 

`Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` using the shared `Context.api_secret_key`: [2](#0-1) 

But `to_signable_string` for a webhook `Request` is only the raw body — it does **not** include the `shop`, `topic`, `webhook-id`, or `api-version` headers: [3](#0-2) 

Once `Utils::HmacValidator.validate` returns `true`, `Registry.process` trusts `request.shop` (sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` header) and hands it to the app's handler as an authenticated fact: [1](#0-0) 

Because `Context.api_secret_key` is a single value shared across *every* shop that has installed the app (it is the app's `client_secret`, not a per-shop secret), any HMAC(body, secret) pair that is valid for one merchant's webhook is also numerically valid for the identical body sent with a different `shop-domain` header. The equality the code implicitly assumes is:

`shop header value == shop that Shopify computed the HMAC for`

but the actual guarantee provided by the HMAC check is only:

`raw body bytes == bytes Shopify signed with the app's shared secret`

These are not equivalent, since the shop identity is outside the signed payload.

### Impact Explanation
An unprivileged internet user who operates their own shop with the app installed can capture one legitimately delivered webhook (body + valid `hmac-sha256` header) for their own store, then replay the exact same HTTP request to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still returns `true` (it never looks at the header), so `Registry.process` invokes the registered `WebhookHandler` with `WebhookMetadata` claiming the payload belongs to the victim shop. Any host application that uses `request.shop` from this gem to look up tenant-scoped credentials/session or to write tenant-scoped data (the intended and documented use, per `docs/usage/webhooks.md`) can be tricked into cross-tenant data corruption/injection — e.g., attacker-controlled body content (product data, customer data, order data, `shop/redact` payloads, etc.) gets attributed to and processed against a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category, since the tenant boundary (shop) is exactly what is being bypassed.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate (even trial) merchant of the target app so they can observe one real webhook delivery containing a valid HMAC for arbitrary body content they influence (e.g., by editing their own store's products/customers/orders to control the JSON body), then resend it with a forged shop header at will. No access to `api_secret_key`, access tokens, or any privileged account for the *victim* shop is required — only the ability to install the app once as any shop. This is a low-effort, repeatable attack.

### Recommendation
Bind the shop (and ideally topic/webhook-id) identity into the authenticated material, or otherwise cryptographically tie the header claims to the signed body — for example, include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or validate `request.shop` against a value obtained through a channel that is bound to the specific installation (e.g., verifying the shop is a shop your app has installed and cross-checking against session storage keyed by an out-of-band-verified shop), rather than trusting the raw header once only the body's HMAC has been checked. At minimum, documentation should make explicit that `request.shop` is unauthenticated and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook (e.g., `products/create`) by creating a product on the attacker shop; capture the raw POST body `B` and the resulting `X-Shopify-Hmac-Sha256: H` header sent to the app's webhook endpoint. `H` is valid because `HMAC(api_secret_key, B) == H` — proven by: [4](#0-3) 
3. Replay the exact same request to the app's webhook endpoint, keeping body `B` and header `H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(api_secret_key, B)`, which still equals `H`, so validation succeeds: [5](#0-4) 
5. `Registry.process` dispatches to the handler with `shop: "victim.myshopify.com"`, `body:` attacker-controlled `B`, despite the request never having been produced by Shopify for that shop: [6](#0-5)
