## Analysis

The Hyperbridge IntentGatewayV2 stack (`IntentsBase.sol` → `ExtrinsicIntents.sol` → `IntentGatewayV2.sol`) is a live, UUPS-upgradeable proxy holding escrowed intent funds and relayer authorization state, but unlike `SimplexPaymaster.sol` (which does reserve `uint256[48] private __gap;` [1](#0-0)  ), none of `IntentsBase`, `ExtrinsicIntents`, or `HyperApp` reserve any storage gap.

`IntentsBase` declares all of the gateway's critical escrow/authorization storage directly, in strict declaration order, with no gap reserved anywhere in the layout: [2](#0-1) 

`ExtrinsicIntents` (an intermediate abstract contract in the inheritance chain between `IntentsBase` and `IntentGatewayV2`, also inheriting `HyperApp`) adds no storage itself, and `HyperApp` likewise declares no state and no gap: [3](#0-2) [4](#0-3) 

The gateway is a genuine UUPS proxy upgraded via a governance-relayed `Execute`/`upgradeToAndCall` request delivered through `onAccept`, confirmed live on mainnet: [5](#0-4) [6](#0-5) 

The team's own decision log shows explicit, manual, error-prone storage-slot bookkeeping instead of a reserved gap — e.g. `_paused` was "appended last to preserve existing storage slots" and `_relayer` was appended "after `_paused`" specifically because inserting a field into the `Params` struct would "push every mapping behind it and corrupt escrow on the live proxy": [7](#0-6) [8](#0-7) 

This is precisely the bug class in the report: without a `__gap`, any future variable inserted anywhere in `IntentsBase`/`ExtrinsicIntents` other than at the very physical end (a mistake an AI-assisted commit or a rushed governance-approved implementation could easily make, given the team is already relying on manual "append last" discipline rather than tooling) silently shifts the slots of `_orders` (escrowed funds), `_instances` (peer authentication), `_partialFills`, `_destinationProtocolFees`, and `_relayer` (the relayer authorization gate) on the live proxy. `_orders`/`_relayer` corruption can permanently freeze escrowed funds or misauthorize `onAccept` deliveries.

### Title
Missing storage `__gap` in `IntentsBase`/`ExtrinsicIntents` risks storage-slot collision on future `IntentGatewayV2` upgrades - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentGatewayV2`'s upgradeable storage base, `IntentsBase` (and the intermediate `ExtrinsicIntents`/`HyperApp`), reserves no `__gap` storage buffer, unlike the project's own `SimplexPaymaster`, which does. All escrow accounting (`_orders`, `_filled`, `_partialFills`), peer routing (`_instances`), fee configuration (`_destinationProtocolFees`), and the relayer authorization gate (`_relayer`) are declared without any reserved slack, relying entirely on developer discipline to append future fields at the exact tail of the contract.

### Finding Description
`IntentGatewayV2` is deployed behind an ERC1967/UUPS proxy and upgraded exclusively through a Hyperbridge-governance-relayed `Execute` request that delegatecalls `upgradeToAndCall`, confirmed live on Ethereum mainnet and other chains. Its storage-holding base, `IntentsBase`, lays out nine state variables in fixed slot order with no reserved gap at the end. The intermediate abstract contracts `ExtrinsicIntents` and `HyperApp` in the inheritance chain (`IntentGatewayV2 is IntentsBase, HyperApp` via `ExtrinsicIntents`) likewise declare no gap. Contrast this with `SimplexPaymaster`, a comparable upgradeable governance-controlled contract in the same repo, which explicitly reserves `uint256[48] private __gap` for exactly this purpose. The team's own AI decision logs confirm they are aware storage layout is fragile — they manually reasoned about exactly where `_paused` and `_relayer` needed to be appended to avoid corrupting the live escrow layout — but chose ad-hoc manual placement discipline over a structural safety margin. Any future implementation that adds a state variable anywhere in `IntentsBase`/`ExtrinsicIntents` except at the literal last declared slot (e.g., inserted mid-file, added to `ExtrinsicIntents` instead of at the tail of `IntentsBase`, or added by an automated/AI-assisted change without full awareness of the exact live slot layout) shifts every subsequent variable's storage slot on the already-deployed proxy.

### Impact Explanation
A slot shift on the live proxy corrupts `_orders` (per-order escrowed token balances), `_partialFills`, `_destinationProtocolFees`, and `_relayer` simultaneously. Corrupting `_orders` can permanently freeze or misdirect escrowed user/solver funds (values silently reinterpreted as different token amounts or wrong keys). Corrupting `_relayer` can either lock out the legitimate relayer (permanently freezing all pending cross-chain settlements, since only the authorized relayer's deliveries are accepted) or, in the worst case, leave the gate reading as unset/zero-address, reopening `onAccept` to any relayer and enabling unauthorized escrow releases. This is a governance-triggered but non-malicious failure mode — exactly the "Alice adds a variable and the contract breaks" scenario from the original report — with concrete fund-freezing/fund-misdirection impact on a live, fund-holding proxy.

### Likelihood Explanation
The team is already actively evolving this contract's storage layout under manual discipline (as shown by the `_paused`/`_relayer` decision logs) rather than a structural `__gap`, and the codebase shows heavy AI-assisted/automated commit activity (per the `docs/ai/decisions` changelog pattern), which increases the chance a future storage-adding change is placed incorrectly relative to the live deployed layout. There is no compiler-enforced or `__gap`-based safety net to catch such a mistake before it reaches a governance-approved upgrade of the live mainnet proxy holding escrowed funds.

### Recommendation
- **Short term:** Add `uint256[50] private __gap;` (sized to project's convention, matching `SimplexPaymaster`) at the end of `IntentsBase`, and equivalent gaps at the end of `ExtrinsicIntents` and `HyperApp` if they are ever expected to gain storage, so future variables can be added without manual slot-shift analysis.
- **Long term:** Adopt a storage-layout CI check (e.g. `forge inspect storage` diffing against the previous deployed implementation, similar to what `modules/ismp/state-machines/evm/src/presets.rs` already does manually for `EvmHost`) that fails the build if any inherited base contract's storage layout changes incompatibly ahead of an upgrade.

### Proof of Concept
1. Deploy `IntentGatewayV2` as a UUPS proxy (as done in `testAtomicInitialization`) and place/escrow an order so `_orders[commitment][token] = amount`.
2. Author a new implementation, `IntentGatewayV2Vulnerable`, identical to `IntentGatewayV2` except with one new state variable inserted into `IntentsBase` (e.g., a new `mapping(address => bool) public frozenTokens;`) placed before `_destinationProtocolFees`/`_paused`/`_relayer` rather than strictly appended at the tail — a plausible mistake absent a `__gap` marker.
3. Deliver an `Execute`/`upgradeToAndCall` request through the host from the authorized relayer, as in `testOnAcceptUpgradeContractPreservesState`.
4. Read `_relayer` and `_orders[commitment][token]` post-upgrade: they now resolve to whatever raw bytes occupy the shifted slot, demonstrating that authorization/escrow state is silently corrupted, without any code path detecting or preventing the collision.

# 2026-09-03 — The relayer is a separate storage variable, not a `Params` field

Chosen: `address _relayer` appended after `_paused` in `IntentsBase`, set through its own
`setRelayer` call.

`Params` occupies slots 4 to 8 and `_orders` starts at slot 9. Adding a field to the struct would
push every mapping behind it and corrupt escrow on the live proxy. Reusing `UpdateParams` was
therefore never available, quite apart from it being a Hyperbridge-relayed message: the whole point
is to hold even if Hyperbridge's consensus is compromised, so the setter must not depend on it.

Alternative rejected — a new `RequestKind` for governance to set the relayer. It needs the
`intents-coprocessor` pallet mirrored, and it is still a cross-chain message. Governance can already
rotate the relayer through `UpgradeContract` migration calldata when it wants to; the owner path
covers the case where it cannot.
