### Title
Gas key `FunctionCallPermission.allowance` is silently unenforced, allowing a restricted gas key to spend beyond its declared limit - (File: runtime/runtime/src/verifier.rs)

### Summary
`AccessKeyPermission::GasKeyFunctionCall(GasKeyInfo, FunctionCallPermission)` bundles a `GasKeyInfo.balance` (the prepaid pot) together with a `FunctionCallPermission` that also carries an optional `allowance: Option<Balance>` field [1](#0-0) . The `allowance` field is documented and actively enforced for plain `FunctionCall` keys, being checked and decremented via `check_and_compute_new_allowance` [2](#0-1)  inside the regular verification path [3](#0-2) . However, the gas-key verification path, `verify_and_charge_gas_key_tx_ephemeral`, never calls `check_and_compute_new_allowance`; it only calls `verify_function_call_permission` (which checks receiver_id/method_names/zero-deposit) and otherwise gates spending solely on `GasKeyInfo.balance` [4](#0-3) . This mirrors the reported bug class: two parallel accounting mechanisms exist for the same conceptual limit (allowance vs. balance), and one code path (gas-key) updates/enforces only one of them while leaving the other field inert, exactly as `increaseAllowance`/`decreaseAllowance` silently diverged from the custom `allowances` mapping in the ERC20 report.

### Finding Description
`AccessKey::gas_key_function_call` lets a caller construct a `GasKeyFunctionCall` key carrying both a `GasKeyInfo.balance` and a `FunctionCallPermission.allowance` [5](#0-4) . This is directly reachable by any account holder via the `AddKey` action and via the host function `promise_batch_action_add_key_with_function_call` / the gas-key equivalent used in `test_gas_key_add_function_call_host_function`, where a caller passes an explicit `allowance` value [6](#0-5) . The host-function docs state that only a literal `0` value maps to `None` (unlimited); any positive value becomes `Some(allowance)` [7](#0-6) , so a non-zero, finite allowance is a legitimate, reachable configuration for a `GasKeyFunctionCall` key.

For a regular `FunctionCall` key, this `allowance` is the sole balance-limiting mechanism, checked and decremented in lockstep with the transaction cost via `check_and_compute_new_allowance` [8](#0-7) , called from `verify_and_charge_tx_ephemeral` [3](#0-2) .

For a `GasKeyFunctionCall` key, execution instead goes through `verify_and_charge_gas_key_tx_ephemeral`. That function validates gas cost only against `GasKeyInfo.balance` [9](#0-8) , and separately validates `FunctionCallPermission` constraints (receiver, methods, zero deposit) via `verify_function_call_permission` [4](#0-3) . At no point in this function, nor in `AccessKeyUpdate::GasKey`'s application logic [10](#0-9) , is `check_and_compute_new_allowance` invoked or the `FunctionCallPermission.allowance` field read, checked, or decremented. The field is preserved verbatim in state and continues to be reported unchanged through the view API (`AccessKeyPermissionView::GasKeyFunctionCall { allowance, .. }` in `core/primitives/src/views.rs`) [11](#0-10) , giving the illusion that a spending cap is in effect and being tracked, when in reality the only enforced limit is the (typically much larger) `GasKeyInfo.balance`.

### Impact Explanation
A caller (or a service issuing gas keys to third parties, e.g. a relayer or wallet provider) that creates a `GasKeyFunctionCall` key with a *small* `allowance` intended to cap what that key can spend, while funding the key's `GasKeyInfo.balance` with a *larger* prepaid pot (for later top-ups or because the same balance is meant to be portioned by allowance), will find that the allowance restriction is never enforced. The key can spend up to the full `GasKeyInfo.balance`, not the intended `allowance`, resulting in unauthorized/unbounded balance drawdown relative to the declared, on-chain-visible restriction. This is an authorization-bypass in the access-key permission model, reachable from ordinary transactions with no validator or network-layer privilege required.

### Likelihood Explanation
High reachability: any account can create a `GasKeyFunctionCall` key with `AddKeyAction` or via the `promise_batch_action_add_key_with_function_call`-style host function, set a non-zero `allowance`, fund the key's `GasKeyInfo.balance` beyond that allowance, and then submit ordinary gas-key transactions (via `nonce_index`) to spend past the declared allowance up to the full balance. No special conditions, races, or validator behavior are needed — it's a straightforward mismatch between a documented/visible restriction field and the actual enforcement code path.

### Recommendation
Either enforce `FunctionCallPermission.allowance` in `verify_and_charge_gas_key_tx_ephemeral` (checking and decrementing it in lockstep with `GasKeyInfo.balance`, analogous to `check_and_compute_new_allowance` in the regular path), or explicitly disallow/ignore-and-reject a `Some` allowance when constructing a `GasKeyFunctionCall` permission (forcing it to `None`) so the field cannot mislead callers into believing it is an enforced spending cap. Add coverage asserting that a `GasKeyFunctionCall` key with a finite allowance smaller than its `GasKeyInfo.balance` cannot spend beyond the allowance.

### Proof of Concept
1. Account `alice` calls `AddKey` (or the equivalent host function) to add a `GasKeyFunctionCall` key with `FunctionCallPermission { allowance: Some(1 NEAR), receiver_id: "bob.near", method_names: [] }` and `GasKeyInfo { balance: 0, num_nonces: N }` [5](#0-4) .
2. `alice` calls `TransferToGasKeyAction` to deposit e.g. 100 NEAR into the key's `GasKeyInfo.balance` via `action_transfer_to_gas_key` [12](#0-11) .
3. Using this gas key (with `TransactionNonce::GasKeyNonce`), submit repeated `FunctionCall` transactions to `bob.near` totaling well over 1 NEAR in gas costs. Each transaction is verified only via `verify_and_charge_gas_key_tx_ephemeral`, which checks against `GasKeyInfo.balance` (100 NEAR) and never against the declared `allowance` (1 NEAR) [13](#0-12) .
4. Observe that transactions continue to succeed past the 1 NEAR allowance threshold, and that `view_access_key_query` still reports the unchanged `allowance: Some(1 NEAR)` even as spending exceeds it — confirming the declared restriction is never enforced or updated.

fn check_and_compute_new_allowance(
    access_key: &AccessKey,
    account_id: &AccountId,
    public_key: &PublicKey,
    total_cost: Balance,
) -> Result<Option<Balance>, InvalidTxError> {
    let Some(fc) = access_key.permission.function_call_permission() else {
        return Ok(None);
    };
    let Some(allowance) = fc.allowance else {
        return Ok(None);
    };
    let new_allowance = allowance.checked_sub(total_cost).ok_or_else(|| {
        InvalidTxError::InvalidAccessKeyError(InvalidAccessKeyError::NotEnoughAllowance {
            account_id: account_id.clone(),
            public_key: public_key.clone().into(),
            allowance,
            cost: total_cost,
        })
    })?;
    Ok(Some(new_allowance))
}

/// Describes how to update the access key after a verified transaction.
#[derive(Debug, Clone, PartialEq)]
pub enum AccessKeyUpdate {
    /// Regular tx: set access_key.nonce, update allowance if specified.
    Regular { nonce: Nonce, new_allowance: Option<Balance> },
    /// Gas key tx: set gas_key_info.balance and persist external nonce.
    GasKey { new_balance: Balance, nonce_index: NonceIndex, nonce: Nonce },
}

impl VerificationResult {
    /// Apply the state changes described by this result to the given account and access key.
    pub fn apply(&self, account: &mut Account, access_key: &mut AccessKey) {
        account.set_amount(self.new_account_amount);
        match &self.access_key_update {
            AccessKeyUpdate::Regular { nonce, new_allowance } => {
                access_key.nonce = *nonce;
                if let Some(a) = new_allowance {
                    access_key.permission.function_call_permission_mut().unwrap().allowance =
                        Some(*a);
                }
            }
            AccessKeyUpdate::GasKey { new_balance, .. } => {
                access_key.gas_key_info_mut().unwrap().balance = *new_balance;
            }
        }
    }

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
