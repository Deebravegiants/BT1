### Title
Webhook shop/topic identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers that are excluded from that signature [2](#0-1) . `Registry.process` validates only the body HMAC and then dispatches to the handler using the unverified header-derived `shop` value [3](#0-2) .

### Finding Description
The binding that should hold is: `shop attributed to the webhook == shop whose secret produced the HMAC over the delivered content`. Instead, the gem only proves `HMAC(raw_body, api_secret_key) == received_hmac` via `Utils::HmacValidator.validate(request)` [4](#0-3) ; it never proves that the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers were produced or endorsed by Shopify for that specific body. `Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop`/`#topic`/`#webhook_id` simply read whichever `shopify-*` or `x-shopify-*` header is present [2](#0-1) [5](#0-4) . Because the same `api_secret_key` is shared across all shops that installed the app (multi-tenant apps use one shared app secret with per-shop sessions), any body+HMAC pair legitimately produced for one tenant remains a valid HMAC pair regardless of which `shop-domain`/`topic`/`webhook-id` header accompanies it. `WebhookMetadata` is then built directly from these unverified header values and handed to the app's handler [6](#0-5) , so the handler is told to attribute the (attacker-observed, HMAC-valid) body to whatever `shop-domain`/`webhook-id`/`topic` the request carries.

### Impact Explanation
An unprivileged user who legitimately installs the app on their own shop (obtaining genuine webhook deliveries and their valid HMACs for their own shop's data) can replay those exact bytes while substituting the `x-shopify-shop-domain` header for a victim shop. `Utils::HmacValidator.validate` still returns true because it never inspects the shop header [7](#0-6) , so `Registry.process` will call the app's handler claiming the payload belongs to the victim shop [3](#0-2) . Any app that uses `WebhookMetadata#shop` to select which tenant's records to create/update/delete (a documented, expected usage pattern for this metadata) can have attacker-controlled data written into or associated with another merchant's tenant — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Exploitation only requires the ability to send an arbitrary HTTP request to the app's webhook endpoint (an unprivileged internet capability) plus one genuine webhook delivery from the attacker's own store, which any developer/merchant can obtain simply by installing the app. No access token, `client_secret`, or privileged credential is needed. The `shop`/`topic`/`webhook_id` accessors are a documented part of this gem's public webhook API surface used to build `WebhookMetadata`, so apps following the library's own contract are affected.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed payload used for verification (or otherwise cryptographically bind them to the raw body before trusting them), and document that `WebhookMetadata#shop` must not be trusted as tenant-authoritative unless it is corroborated by the session/shop the app itself associates with the delivery.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture a legitimate webhook delivery: `raw_body`, `x-shopify-hmac-sha256`, `x-shopify-topic`, `x-shopify-webhook-id`.
2. Resend the identical `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but replace the header `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(raw_body, api_secret_key)` and matches the unchanged `hmac` header — validation passes [4](#0-3) .
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)` [6](#0-5)  and processes attacker-supplied data under the victim shop's identity.
