### Title
Webhook shop-domain (and topic/api-version/webhook-id) headers are trusted for tenant identification but are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field from an HTTP header, but the HMAC signature that `ShopifyAPI::Webhooks::Registry.process` validates only covers the raw request body. Any party that can obtain one genuine, validly-signed webhook body/HMAC pair for the shared app secret (e.g. a merchant who has legitimately installed the public app and receives webhooks to their own endpoint) can replay that exact body+HMAC while swapping the `x-shopify-shop-domain` header to point at a different tenant. `Registry.process` will still accept the request as authentic and hand the attacker-chosen `shop` value to the app's webhook handler as if it came from Shopify.

### Finding Description
`Utils::VerifiableQuery#to_signable_string` is the only material that gets HMAC-verified via `Utils::HmacValidator.validate`: [1](#0-0) 

```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from attacker-controllable HTTP headers with no binding to the signed content: [2](#0-1) 

`Registry.process` validates the HMAC (which, again, only covers the body) and then forwards `request.shop` (an unauthenticated header) directly to the merchant's webhook handler as the trusted tenant identifier: [3](#0-2) 

Because the app's `api_secret_key` used to compute/verify the HMAC is shared across every shop that installs the app (it is not per-shop), a valid `(raw_body, hmac)` pair generated for tenant A's install is equally "valid" when replayed with tenant B's `shop-domain` header — the signature check in `Utils::HmacValidator.validate_signature` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) only recomputes the HMAC over `raw_body` and never incorporates `shop`, so it cannot detect the substitution.

This exactly matches the report's bug class: **a field (`shop`) that is acted on by the application logic but is not covered by the identity-binding HMAC**, breaking the equality that should hold between "the shop the signature was computed for" and "the shop the handler is told the event belongs to."

### Impact Explanation
This crosses a tenant boundary: an unprivileged party who can obtain any one authentic webhook delivery for the shared app (by legitimately installing the public app to their own store and capturing what their own server receives, or intercepting a delivery to their own endpoint) can forge deliveries that the app processes as if they originated from an arbitrary other merchant's shop, without ever needing the app's `client_secret`/`api_secret_key`. Depending on the host application's webhook handlers (e.g. `app/uninstalled`, `orders/*`, `customers/data_request`, `shop/redact`), this can lead to cross-tenant state corruption, unauthorized data deletion/redaction, or triggering privileged actions against a victim shop's session/data — i.e. cross-tenant access via a spoofed identity binding.

### Likelihood Explanation
Any entity able to install (or otherwise legitimately receive webhooks from) the target app can produce one authentic `(body, hmac)` pair for the shared secret, then trivially replay it with a different `shop-domain` header — no cryptographic secret, TLS interception, or privileged credential is required. Likelihood is moderate-to-high for any app that relies on `Registry.process`'s `data.shop` value for tenant-sensitive logic.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed material, or otherwise cross-check the header-derived `shop` against an independently-verified identity (e.g. validate that the shop corresponds to a session/install the app already trusts) before acting on it. At minimum, document that `request.shop` is unauthenticated and must not be used as the sole tenant key, or extend `to_signable_string`/the HMAC computation to include the header fields that `Registry.process` currently treats as trusted.

### Proof of Concept
1. Malicious merchant `evil-shop.myshopify.com` installs the target public app and receives a real webhook, e.g. `orders/create`, with a valid `x-shopify-hmac-sha256` computed by Shopify over the JSON body using the app's shared `api_secret_key`.
2. Attacker captures the exact `raw_body` and `x-shopify-hmac-sha256` value.
3. Attacker re-sends this exact body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate`, which succeeds because it only checks `@raw_body` against the HMAC (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host application to process attacker-controlled data as belonging to the victim shop.
