### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-spoofed webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) for a webhook exclusively from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies is computed only over the raw request body. Because the shop-identifying field is never part of the signed material, an attacker who can influence or replay the headers of an otherwise HMAC-valid webhook request can rebind that request to an arbitrary shop, and the registered webhook handler will process it as if it genuinely originated from that other tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shop-domain` header, completely independent of the signed body: [2](#0-1) 

`HmacValidator.validate` verifies `verifiable_query.hmac` against `HMAC(secret, verifiable_query.to_signable_string)`, i.e. against the body only: [3](#0-2) 

`Registry.process` trusts this validation and then dispatches to the handler using `request.shop` as the tenant identity, without any additional check that the shop matches what was actually signed: [4](#0-3) 

The binding that should hold is:

`shop used to authorize/attribute the webhook (request.shop) == shop bound inside the HMAC-covered bytes (to_signable_string)`

but the actual implementation gives:

`to_signable_string == @raw_body` (shop-domain excluded)
`request.shop == header["shop-domain"]` (fully attacker/transport controllable, unauthenticated by the HMAC)

Since every shop installed on the same app shares the same `api_secret_key`/`client_secret` used to compute the HMAC, an attacker who controls (or can install) one shop on the app can obtain a body + HMAC pair that is valid for the shared secret, then present that same body/HMAC pair together with a different `shop-domain` header value. `HmacValidator.validate` will still pass because it never looks at the header, and `Registry.process` will hand the payload to the handler tagged with the attacker-chosen `shop`, `topic`, `webhook_id`, and `api_version` metadata (`WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`), none of which are covered by the signature.

This is the same class of defect as the reference report: a field that is *acted upon* (the tenant/shop binding) is not *covered* by the integrity check (the HMAC), so verified bytes and used bytes diverge.

### Impact Explanation
This breaks the shop/tenant identity binding that host applications rely on to route webhook side effects (e.g., updating per-shop billing/subscription state, cancelling app installations, processing `shop/redact` GDPR requests, etc.) to the correct merchant record. A forged `shop` value on an otherwise-authentic (secret-signed) webhook can cause the host application to apply another merchant's webhook event to the wrong tenant's data — a cross-tenant data-integrity/access issue. This matches the Critical "cross-tenant access" impact category since the shop context, not just the body, is what applications use to decide which merchant record to mutate.

### Likelihood Explanation
Exploitation requires the attacker to be able to supply/modify the `shop-domain` header independently of the body while keeping a body+HMAC pair valid for the shared app secret — which is achievable by any developer/attacker who can install the target app on their own store (a normal unprivileged action) and control how the resulting authentic webhook is relayed to the processing endpoint (many integrations proxy raw body + headers, or headers can be manipulated in a replay). No access token, `api_secret_key`, or victim credentials are required — only knowledge of your own shop's genuine webhook deliveries for the shared app.

### Recommendation
Include the shop domain (and ideally `topic`/`api-version`) inside the HMAC-covered signable string, e.g. by having `Request#to_signable_string` return a canonical concatenation of `shop-domain` + `topic` + `raw_body`, and update the validator/tests accordingly. Alternatively, require host applications to independently re-verify `request.shop` against session/tenant records before trusting it, and document this as a security-relevant deviation from what the HMAC guarantees.

### Proof of Concept
```ruby
secret = ShopifyAPI::Context.api_secret_key
body = '{"id":1}'
hmac = Base64.encode64(OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, body))

# Genuine headers as delivered by Shopify for the attacker's OWN shop
genuine_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => hmac,
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}

# Attacker swaps only the shop-domain header before forwarding to the app's webhook endpoint
forged_headers = genuine_headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")

request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: forged_headers)

ShopifyAPI::Utils::HmacValidator.validate(request) # => true, HMAC still validates
request.shop                                        # => "victim-shop.myshopify.com"

ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle is invoked with data.shop == "victim-shop.myshopify.com",
# even though the HMAC never authenticated that shop value.
```

          received_signature = verifiable_query.hmac
