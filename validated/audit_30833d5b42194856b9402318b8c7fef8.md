### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header not covered by HMAC verification enables cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read from unauthenticated HTTP headers. `Registry.process` validates the HMAC against the body only and then trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler, without any binding between the verified bytes and the identity fields used downstream.

### Finding Description
`HmacValidator.validate` computes and compares the HMAC using `verifiable_query.to_signable_string`, which for a webhook `Request` is defined as `@raw_body` only: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors read directly from HTTP headers (`shopify-shop-domain`/`x-shopify-shop-domain`, etc.), which are not part of the signed payload at all: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` and `request.topic` to construct the metadata dispatched to the registered handler: [3](#0-2) 

This breaks the intended identity binding: `verified_bytes (raw_body signed by HMAC) == identity_fields_acted_on (shop, topic, webhook_id headers)`. In reality, only the body is verified; the shop/topic/webhook_id headers are accepted unauthenticated. Any party who can produce one valid `(raw_body, hmac)` pair for a topic — e.g., by installing the target app on their own store and receiving a legitimate webhook from Shopify with the topic/body/HMAC they need — can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. The HMAC check still passes (it only checks the body against the secret), and the handler receives a `WebhookMetadata` whose `shop` field is fully attacker-controlled.

### Impact Explanation
Any host application built on this gem that uses `WebhookMetadata#shop` to identify which tenant/session a webhook event pertains to (the standard use case documented for the webhook `Registry`) can be made to attribute attacker-supplied data to an arbitrary victim shop, or trigger shop-scoped side effects (e.g., mandatory `shop/redact`, `customers/redact`, `customers/data_request` handling, or app-specific data mutation) under a spoofed shop identity. This is a cross-tenant identity confusion vulnerability reachable by any unprivileged actor who can obtain one legitimate webhook delivery (trivially achievable by installing the app on their own development store), satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High. No secret material beyond what Shopify normally sends any app installer is required. An attacker only needs:
1. To install the target Shopify app on a store they control (an ordinary, unprivileged action), and
2. To capture one legitimate webhook delivery (raw body + `X-Shopify-Hmac-Sha256` header) that Shopify sends them for that installation.
They can then replay this exact body/HMAC pair to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header. No brute forcing, no access to `api_secret_key`, and no privileged account is needed.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed materials used for verification, or otherwise cryptographically/authoritatively confirm the shop header against a value obtained from a source not controlled by the requester (e.g., cross-check the shop domain against the app's own installed-shop/session store keyed by the topic+webhook id, or include these fields in an application-level signed envelope rather than trusting raw headers). At minimum, document/enforce that consumers of `WebhookMetadata#shop` must not treat it as authenticated unless it has been independently corroborated against a known install record for that shop.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal, permitted install).
2. Shopify delivers a legitimate webhook to the app's endpoint for `attacker-shop.myshopify.com`, e.g. body `{"id":123}` with headers:
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of the body>`
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
3. Attacker captures this exact `(body, hmac)` pair (they legitimately received it) and resends it directly to the app's webhook HTTP endpoint, but replaces the header:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `@raw_body` only — this still matches the captured HMAC, since the shop header was never part of the signed content [1](#0-0) .
5. `Registry.process` passes validation and invokes the app's handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: {"id":123}, ...)` [3](#0-2) , causing the host application to process attacker-controlled data under the victim shop's identity.
