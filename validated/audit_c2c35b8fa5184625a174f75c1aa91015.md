### Title
Webhook shop-domain header not covered by HMAC, enabling cross-tenant webhook data injection - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header, while `Utils::HmacValidator` only verifies the raw request body against the `hmac-sha256` header. The `shop` field is never included in the signed payload, so the HMAC check does not bind the tenant claim to the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `HmacValidator.validate`/`validate_signature` compute the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compare it to the `hmac` accessor, which itself is also derived only from the `hmac-sha256` header decoded against the same raw body: [2](#0-1) [3](#0-2) .

The `shop` attribute, however, is read directly and unauthenticated from the `shopify-shop-domain` header: [4](#0-3) . `Registry.process` only checks the HMAC of the body, then immediately forwards `request.shop` (alongside the verified body) to the app's handler as the tenant identity for the event: [5](#0-4) .

The broken identity binding, expressed as an equality that the gem fails to enforce:
`HMAC(raw_body, client_secret) == received_hmac` is verified, but `shop_header == shop_that_was_actually_signed` is never checked — the gem implicitly (and incorrectly) treats "body HMAC valid" as if it also authenticates the `shop` header, when in fact `shop` is completely outside the signed material.

Because Shopify apps share a single `client_secret` across every installed shop, any webhook payload that a merchant legitimately receives for their own shop carries a valid HMAC for that raw body under the app's secret. That HMAC remains valid for the exact same bytes regardless of which `shop` header accompanies the request. A malicious merchant (an unprivileged internet user with respect to any other tenant of the app) can therefore capture a legitimately-signed webhook delivered to their own shop, and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the (unchanged) body bytes against the (unchanged) signature, and `Registry.process` passes the forged `shop` straight to the handler as `WebhookMetadata#shop`, which is what host applications use to scope the incoming event to a tenant record, session, or access token: [6](#0-5) .

### Impact Explanation
This breaks the tenant boundary the HMAC check is meant to enforce for webhook processing. An attacker who controls one shop's install of an app can inject data that is falsely attributed to another merchant's shop into any handler that trusts `WebhookMetadata#shop` (e.g., to update per-shop state, sync inventory/orders, or take actions using that shop's stored access token). This is a cross-tenant access issue, matching the "Critical – cross-tenant access" impact category, since it lets an unprivileged actor with only their own tenant's credentials cause the application to process attacker-influenced events under a different tenant's identity.

### Likelihood Explanation
Exploitation only requires the attacker to operate their own installed instance of the app (a legitimate, unprivileged capability every merchant has) and to be able to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-controlled headers — both trivially available to any internet user who has installed the app once. No access token, `api_secret_key`, or privileged access is needed; the attacker only reuses HMAC values Shopify itself already computed and delivered to them.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) values into the HMAC-covered signable string, or otherwise cryptographically tie the claimed shop to the specific webhook delivery (e.g., verify against a per-shop webhook secret, or cross-check the claimed shop against an independent, already-authenticated relationship such as the shop associated with the specific `webhook-id` via the Admin API) before trusting `request.shop` in `Registry.process`. At minimum, document that the `shop` header is unauthenticated and must not be used by host apps as a trusted tenant identifier without further verification.

### Proof of Concept
1. App has two shops installed: `attacker.myshopify.com` (attacker-controlled) and `victim.myshopify.com`.
2. Shopify sends a legitimate webhook to the app for `attacker.myshopify.com`:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of BODY under shared client_secret>
   x-shopify-shop-domain: attacker.myshopify.com
   BODY
   ```
3. Attacker replays the same request to the app's webhook endpoint, changing only the shop header:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <same valid HMAC, unchanged since BODY is unchanged>
   x-shopify-shop-domain: victim.myshopify.com
   BODY   (unchanged bytes)
   ```
4. `Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb:12-31) returns `true` because it only checks `BODY` against the HMAC.
5. `Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: BODY, ...)`, causing the host application to process attacker-supplied data as if it originated from the victim's shop.
