### Title
Object-form `walletAccount` bypasses account lookup/consent in `MessageSigner`, letting `HardwareMessageSigner.signMessage` derive keys and target a hardware device for an attacker-chosen account - ([File: features/message-signer/src/module/hardware-signer.ts])

### Summary
`MessageSigner#normalizeWalletAccount` in `message-signer.ts` only resolves and validates the `walletAccount` parameter against the `walletAccountsAtom` when it is passed as a `string`; when a plain object is passed, it is returned unchanged with no existence or ownership check. This unvalidated object then flows straight into `HardwareMessageSigner.signMessage`, which uses its `index`/`id`/`seedId` fields to build the derivation path and call `requireDeviceFor`, binding signing to whatever account the caller specified rather than the account actually registered/connected.

### Finding Description
In `message-signer.ts`, `#normalizeWalletAccount` performs the "known account" check only for the string branch: [1](#0-0) 
For any non-string input, the object is trusted verbatim and passed to `#getMessageSigner` and then to the selected signer: [2](#0-1) 

`HardwareMessageSigner.signMessage` (`hardware-signer.ts`) performs no independent verification that the `walletAccount` it receives corresponds to a real/registered/authorized account. It only asserts the object shape (`typeof walletAccount === 'object'`), then uses `walletAccount.index`, `walletAccount.compatibilityMode`, and `walletAccount.toString()` to derive the key identifier and finally calls `this.#hardwareWallets.requireDeviceFor(walletAccount)` with the caller-supplied object directly: [3](#0-2) [4](#0-3) 

`HardwareWallets.requireDeviceFor` in turn uses the passed-in `walletAccount` for subsequent `signTransaction`/`signMessage` calls without re-validating it against the wallet's known accounts: [5](#0-4) 

Because the only "known-account" gate (`walletAccountsAtom` lookup) is skipped for object input, an attacker able to invoke `signMessage({ walletAccount: forgedObject, ... })` directly determines which account's key is used, independent of any origin/consent binding that may exist elsewhere (e.g., in `@exodus/connected-origins`, which tracks per-origin connected accounts but is not consulted anywhere in this call path).

### Impact Explanation
If reachable with attacker-controlled input, this allows cross-account signing: an origin that is only authorized/connected for one wallet account can construct a `WalletAccount`-shaped object referencing a different account (via `index`, `id`, `seedId`) and have the hardware wallet sign a message under that other account's key, producing a valid signature disclosure/authorization for an account the origin was never granted consent for. This maps to a wrong-account/authorization-bypass signing impact.

### Likelihood Explanation
Exploitability is entirely contingent on whether an unprivileged dapp/RPC caller can actually invoke `exodus.messageSigner.signMessage` with a raw object rather than a string. The `messageSignerApi` (`features/message-signer/src/api/index.ts`) forwards `SignMessageParams` (typed as `WalletAccount | string`) verbatim to the module, and the module is registered as `public: true`, so nothing in this feature module itself restricts the input to strings or enforces origin/consent binding: [6](#0-5) [7](#0-6) 
I could not find, within indexed code, a dapp-facing RPC/provider bridge (e.g. Solana/Ethereum/Bitcoin provider handlers) that forwards an attacker-supplied raw `walletAccount` object into this API from an untrusted origin — the provider docs describe dapp-facing `signMessage` taking only `address`/`message` strings, suggesting the wallet-side origin/consent resolution normally happens before this module is invoked. Whether some other RPC surface exposes the object form directly to untrusted origins is not confirmed by available index coverage.

### Recommendation
Make `#normalizeWalletAccount` always resolve and verify the account against `walletAccountsAtom` (and against the origin's connected/consented account, if applicable) regardless of whether the input is a string or an object — e.g., by looking up `walletAccount.toString()` in the atom and asserting the resolved instance matches the object's fields (or simply always re-fetching the canonical instance by key) before it is passed to any signer, instead of trusting caller-supplied objects verbatim.

### Proof of Concept
Integration test plan for `features/message-signer/src/module/__tests__/index.test.ts`:
1. Seed `walletAccountsAtom` with a legitimate `ledger` `WalletAccount` (`index: 0, id: 'legit-id'`) representing the origin's actual connected/consented account.
2. Call `messageSigner.signMessage({ baseAssetName, message, walletAccount: { index: 1, id: 'other-account-id', source: LEDGER_SRC, isHardware: true, toString: () => 'ledger_1', compatibilityMode: undefined } })` — a plain object shaped like a different account, never stored in `walletAccountsAtom`.
3. Assert that `hardwareMessageSigner.signMessage` (and downstream `hardwareWallets.requireDeviceFor`) is invoked with `index: 1`/`id: 'other-account-id'` rather than throwing an "account not found" error or being rejected for not matching the origin's connected account — demonstrating that no lookup/consent check occurred for the object-form input, unlike the string-form path in the existing `assert(instance, ...)` check.
