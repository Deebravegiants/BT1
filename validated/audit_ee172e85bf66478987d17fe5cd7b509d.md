### Title
Webhook shop-tenant identity spoofing — HMAC signs only the raw body, not the `shop`, `topic`, or `webhook_id` headers used for tenant dispatch - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` field purely from an HTTP header, while `to_signable_string` (the value HMAC-verified by `Utils::HmacValidator`) returns only the raw request body. This breaks the binding: `hmac-verified bytes == tenant identity acted upon`. An attacker who obtains any one genuine, validly-signed webhook payload (trivially available by installing the target app on their own store) can replay it to the victim app's webhook endpoint while swapping the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) headers, and `Registry.process` will accept it as authentic for the spoofed shop.

### Finding Description
`Registry.process` gates all further processing on a single check: [1](#0-0) 

That check calls `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`: [2](#0-1) 

`Request#to_signable_string` returns `@raw_body` only: [3](#0-2) 

But `shop`, `topic`, `webhook_id`, and `api_version` — the fields the host app is told it can trust for tenant dispatch — are all pulled straight from unauthenticated headers: [4](#0-3) 

These unauthenticated fields are then handed directly to the app's webhook handler as the trusted tenant identity: [5](#0-4) 

The gem's own documentation asserts that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole request — including the shop attribution — is authenticated: [6](#0-5) 

In reality, only the byte-for-byte body is authenticated. Since the app's client secret (used to sign webhooks) is shared across every shop that installs the app, any unprivileged internet user can install the target app on their own store, capture a legitimate webhook (valid HMAC over that body), and then replay the identical body to the app's webhook URL with the `shopify-shop-domain` header rewritten to a victim shop's domain (and `shopify-webhook-id`/`shopify-topic` changed to fit the desired handler). `Utils::HmacValidator.validate` will still pass because it only checks the body bytes, and the handler will run with `data.shop` set to the attacker-chosen victim domain — this is a cross-tenant identity break using no credential belonging to the victim and no leaked `api_secret_key`.

### Impact Explanation
This satisfies the Critical bar of "cross-tenant access": an attacker with no access to the victim's credentials, session, or `api_secret_key` can cause the app to process attacker-controlled webhook data attributed to an arbitrary victim shop. Depending on the handler's trust in `data.shop` (e.g., using it to look up/act on that shop's stored session, trigger `shop/redact`/`customers/redact` GDPR flows, invalidate installs, or update per-shop state), this can lead to data corruption, forced uninstall/redaction actions, or state confusion across tenants — entirely through the documented, supported `Registry.process` / `Webhooks::Request` API surface of this gem.

### Likelihood Explanation
High for any app author who follows the gem's documented pattern of trusting `data.shop` from `WebhookMetadata` as the tenant identity (as the official docs and example handler do), since the gem itself provides no protection: the tenant-identifying headers are never included in the signed payload, and the gem exposes no independent shop verification step in `Registry.process`. Obtaining a valid signed body is trivial for anyone who can install the app on their own store (many apps auto-approve installs).

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or otherwise require the host app to independently verify `request.shop` against a known/installed shop list before dispatch), and update `Utils::HmacValidator`/`Webhooks::Request#to_signable_string` so verification covers the full identity of the webhook, not just the body bytes. At minimum, correct the documentation so it no longer implies `Registry.process` authenticates the shop, and require/encourage callers to cross-check `data.shop` against their own session store before acting.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development store `attacker-shop.myshopify.com`, receiving genuine webhooks (e.g. `orders/create`) signed with the app's shared `client_secret`.
2. Attacker captures one such webhook: raw body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker sends `B` unmodified to the victim app's webhook endpoint, but with headers changed to:
   - `shopify-hmac-sha256: H` (unchanged, still valid because body is unchanged)
   - `shopify-shop-domain: victim-shop.myshopify.com`
   - `shopify-topic`/`shopify-webhook-id` set as desired
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only hashes `@raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. The handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, `lib/shopify_api/webhooks/registry.rb:198-199`, even though the payload `B` was entirely attacker-authored content from the attacker's own store, achieving cross-tenant impersonation.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
