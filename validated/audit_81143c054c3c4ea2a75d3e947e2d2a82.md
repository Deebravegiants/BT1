### Title
No vulnerability - CSR Create path unconditionally zeroes Status, so admission plugin's Update-only Handler is not bypassable - (File: pkg/registry/certificates/certificates/strategy.go)

### Summary
The `csrStrategy.PrepareForCreate` function in `pkg/registry/certificates/certificates/strategy.go` unconditionally resets `csr.Status` to an empty `CertificateSigningRequestStatus{}` (with an empty `Conditions` slice) on every Create request, regardless of what the client submits in the request body. This means an attacker cannot smuggle a pre-populated `Status.Certificate` or `Status.Conditions=[Approved]` through a single Create call, so the premise of the question — that the signer-authorization admission plugin (registered with `admission.NewHandler(admission.Update)` only) could be bypassed via Create — does not hold.

### Finding Description
The relevant code is: [1](#0-0) 

`PrepareForCreate` is invoked by the generic registry `Store` before `Validate`/persist on every Create request for `certificatesigningrequests`, and it explicitly clears `csr.Status` and resets `csr.Status.Conditions` to an empty slice at lines 98-100, overriding whatever the client submitted in the POST body. This is independent of and precedes any admission plugin logic — it runs in the storage strategy layer (`genericregistry.Store.CreateStrategy`), which is wired in `pkg/registry/certificates/certificates/storage/storage.go` (`CreateStrategy: csrregistry.Strategy`). Because of this, a Create request carrying `Status.Certificate` and `Status.Conditions=[Approved]` in the body is persisted with an empty status — there is no way to create a CSR object with pre-populated status via a single Create call. The only paths that can set `Status.Certificate` or `Status.Conditions` are the `/status` and `/approval` subresources, which use `Update` verb and dedicated strategies (`csrStatusStrategy`, `csrApprovalStrategy`), both of which are properly covered by the plugin's `admission.NewHandler(admission.Update)` registration.

This behavior is also explicitly covered by an existing regression test: [2](#0-1) 

The "pre-approved status" test case directly asserts that a CSR object created with a pre-populated `Approved` condition is stripped down to an empty status after `PrepareForCreate` runs.

### Impact Explanation
No exploitable impact. The claimed bypass path — creating a CSR with an attacker-controlled `Status` via a single Create call — is already prevented at the storage-strategy layer before the object is ever persisted, and the strategy has a dedicated existing unit test asserting this invariant. There is no cross-tenant read/write, privilege escalation, or identity forgery achievable via this path.

### Likelihood Explanation
Not applicable — the precondition assumed by the question (that a Create call can embed and persist a non-empty `Status`) is false in the current code, as demonstrated by `PrepareForCreate` and its regression test.

### Recommendation
No change needed for this specific concern. As the question itself suggests, if `PrepareForCreate` is ever modified to stop zeroing `Status` unconditionally, the existing `TestStrategyCreate` "pre-approved status" case would catch the regression, and at that point the admission plugin's Handler would need to be extended to also cover `admission.Create`.

### Proof of Concept
Existing test `TestStrategyCreate` in `pkg/registry/certificates/certificates/strategy_test.go` (case `"pre-approved status"`, lines 105-117) already serves as this proof: it constructs a CSR with `Status.Conditions=[{Type: CertificateApproved}]` set before calling `Strategy.PrepareForCreate`, and asserts the resulting object's `Status` is reset to `{Conditions: []certapi.CertificateSigningRequestCondition{}}` — i.e., empty, with the Approved condition and any `Certificate` bytes stripped. No further PoC is required to confirm the claimed bypass is not exploitable.

// PrepareForCreate clears fields that are not allowed to be set by end users
// on creation.
func (csrStrategy) PrepareForCreate(ctx context.Context, obj runtime.Object) {
	csr := obj.(*certificates.CertificateSigningRequest)

	// Clear any user-specified info
	csr.Spec.Username = ""
	csr.Spec.UID = ""
	csr.Spec.Groups = nil
	csr.Spec.Extra = nil
	// Inject user.Info from request context
	if user, ok := genericapirequest.UserFrom(ctx); ok {
		csr.Spec.Username = user.GetName()
		csr.Spec.UID = user.GetUID()
		csr.Spec.Groups = user.GetGroups()
		if extra := user.GetExtra(); len(extra) > 0 {
			csr.Spec.Extra = map[string]certificates.ExtraValue{}
			for k, v := range extra {
				csr.Spec.Extra[k] = v
			}
		}
	}

	// Be explicit that users cannot create pre-approved certificate requests.
	csr.Status = certificates.CertificateSigningRequestStatus{}
	csr.Status.Conditions = []certificates.CertificateSigningRequestCondition{}
}
