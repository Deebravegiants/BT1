Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the authenticity of an incoming webhook by HMAC-signing only the raw request body, while the shop identity that is handed to the app's webhook handler is read straight from an unauthenticated HTTP header. Because the HMAC never covers the `shop` value, any tenant that can obtain one validly-signed webhook body (from their own installation of the app) can replay it with a forged `shop-domain` header to make the app process the event as if it belonged to a different merchant.

### Finding Description
`Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string` and compares it to the `hmac` value with `OpenSSL.secure_compare`: [1](#0-0) 

For webhook requests, `to_signable_string` is defined as just the raw body, and `shop` is read from the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header, which is never part of the signable string: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then forwards the unauthenticated `request.shop` header value directly into `WebhookMetadata` that is delivered to the app's handler as the tenant identifier: [3](#0-2) 

`WebhookMetadata#shop` is a plain, unauthenticated `String` field consumed by application code implementing `WebhookHandler#handle`: [4](#0-3) 

The identity binding that should hold is: `shop header value == shop bound inside the HMAC-signed bytes`. In this gem it is instead: `shop header value` is trusted independently of the signature, while the signature only proves `raw_body` integrity. Since a single app-wide `client_secret` is shared across every merchant that installs the app, any merchant (an "unprivileged internet user" from the perspective of other tenants) can:
1. Install the app on their own shop and trigger a webhook event, obtaining a request with a genuinely valid `hmac-sha256` signature over some `raw_body`.
2. Replay that exact `raw_body`/`hmac` pair to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. `Utils::HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` calls the handler with `WebhookMetadata.shop` set to the victim's domain.

### Impact Explanation
This breaks the tenant/shop identity boundary the gem is expected to enforce for webhook delivery: an attacker who is merely a legitimate tenant of the app (not privileged, no access token or `client_secret` needed) can make the app's webhook handling logic act as though an event originated from a different merchant's shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to select the merchant's stored session/access token, update per-shop state, or trigger `app/uninstalled`-style cleanup), this enables cross-tenant access/data corruption — the Critical-impact category defined in scope.

### Likelihood Explanation
Likelihood is high for any app that relies on `ShopifyAPI::Webhooks::Registry.process`/`WebhookMetadata#shop` as the trusted tenant identifier, which is the gem's documented and only supported way of consuming webhook shop identity. No credentials beyond installing the app as an ordinary merchant are required, and the forged request is a simple header substitution replay of an otherwise-legitimate, validly-signed payload.

### Recommendation
Include the shop domain in the HMAC-signed material for webhook requests (e.g., sign a canonical string combining `topic`, `shop`, `webhook_id`, and `raw_body`, or require the consuming application to cross-check the header shop against an independently verified/registered shop before trusting `WebhookMetadata#shop`). At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be used as a tenant selector without additional verification (e.g., checking it matches a shop for which the app has an active, previously-established session/webhook registration).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `X-Shopify-Hmac-Sha256: <valid-signature-for-body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, and `Utils::HmacValidator.validate(request)` returns `true` because `to_signable_string` only checks `raw_body` (unchanged).
4. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to process/act on data attributed to `victim-shop.myshopify.com` even though the request never actually came from Shopify on behalf of that shop.
