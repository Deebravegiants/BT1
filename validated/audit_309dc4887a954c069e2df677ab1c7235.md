### Title
Tokens transferred directly to the pool or controller are permanently locked — no unbooked-custody recovery path exists - (File: contracts/pool/src/lib.rs)

### Summary
The pool accounts for liquidity through a `cash` book that is credited only by measured receipts inside `supply`, `repay`, and `recapitalize`. A plain SAC `token.transfer` to the pool address raises real custody without raising any market's book, and no entrypoint — unprivileged or owner — ever pays out the difference. The same applies to tokens sent directly to the controller, whose refund paths sweep only positive callback deltas of refund-listed tokens, never prior balances. Directly transferred tokens are stranded permanently.

### Finding Description
In the referenced Incentivizer bug, the underlying asset could not be rescued. Here the pool is the analog: every inbound flow measures the delta of its *own* transfer, not the standing balance. `markets::recapitalize` prefunds the pool and credits only `payments::transfer_amount_measured` for that call's transfer (`contracts/controller/src/markets.rs:153-163`), so a donation sitting in custody from an earlier transaction is never attributed to anyone. The architecture doc states this explicitly: "Supply, repayment, and recapitalization credit the tokens actually received; direct donations do not automatically increase booked cash" (`docs/reference/architecture.md:57-61`), and the threat model notes "Direct donations do not rewrite those books" even though hubs share one physical pool balance (`docs/explanation/threat-model.md:129-131`). The test `pool_all_money_paths_preserve_books_and_shared_token_custody` pins that a 7-unit donation belongs to no market's cash book (`tests/test-harness/tests/pool_money_flow_audit.rs:86-96`). Withdrawals, borrows, and liquidation payouts are all bounded by the `cash` book (`Cache::require_reserves` reads the book, not the balance), so the surplus above total booked cash can never leave through any legitimate flow. The pool has no `skim`/`rescue`/`sweep` function — all mutators are `#[only_owner]` and none pays out unbooked custody. The controller likewise has no sweep: threat-model line 172-173 confirms "Neither category sweeps prior balances."

### Impact Explanation
Permanent freezing of user funds. A user who mistakenly transfers a pool asset (or any token) directly to the pool or controller address instead of calling `supply`/`repay`/`recapitalize` receives no shares, no debt credit, and no shortfall credit — and the tokens are locked forever. This is a realistic and recurring mistake pattern (the original audit classifies it medium). The stranded funds are not recoverable by governance either, since no owner entrypoint pays out unbooked balance.

### Likelihood Explanation
Likelihood is moderate-to-high by human error: users routinely send tokens to a known contract address rather than invoking the deposit entrypoint. The path is trivially reachable by any unprivileged address via a plain `token.transfer` to the pool or controller — exactly the listed in-scope vector "direct token transfers to the pool or controller." Note this does not enable theft by a third party: measured-delta crediting means another caller cannot claim the donation in a later transaction, so the loss is strictly the sender's.

### Recommendation
Add an owner- or governance-gated rescue that can pay out `token.balance(pool) - Σ market cash` per token (i.e., only custody exceeding all booked obligations across every hub sharing the physical balance), mirroring the swap-aggregator's `sweep_balance` pattern which transfers only `balance - reserved_fee_balance` (`contracts/swap-aggregator/src/lib.rs:188-202`). For the controller, add an equivalent sweep of any non-reserved token balance. Alternatively, document the address and actively warn integrators that direct transfers are unrecoverable.

### Proof of Concept
1. Deploy controller + pool, create a market for `USDC`, have Alice supply 1,000 USDC via `Controller::supply` (books: `cash = 1,000`).
2. Bob calls `token::Client::transfer(bob, pool, 500)` directly — a plain SAC transfer, not through the controller.
3. Observe `token.balance(pool) = 1,500` while every hub's `cash` still sums to 1,000 (per `pool_money_flow_audit.rs:86-96`, the donation "belongs to no market's cash book").
4. Bob has no entrypoint to recover the 500 USDC: `supply`/`repay`/`recapitalize` measure only the delta of their own transfer; `withdraw`/`borrow` are bounded by `cash`; no `sweep`/`rescue` exists on the pool.
5. The 500 USDC is permanently stranded — it merely inflates custody above book for the life of the contract.

One caveat: I confirmed no `rescue`/`skim`/`sweep` function exists in `contracts/pool` and `contracts/controller` via search, and the threat-model docs corroborate the absence ("no entrypoint to claim or forward"; "no recovery path for arbitrary stranded assets"), but I did not exhaustively read every pool entrypoint signature in `contracts/pool/src/lib.rs`.
