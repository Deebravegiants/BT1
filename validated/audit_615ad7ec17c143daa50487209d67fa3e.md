### Title
DeleteAccount with a non-existent, non-implicit `beneficiary_id` can panic the runtime (chain-halting DoS) - ([File: runtime/runtime/src/actions.rs] / [File: runtime/runtime/src/lib.rs])

### Summary
Analogous to the reported issue (a user-controlled fee/beneficiary recipient that is only syntax-checked, not existence-checked, causing unintended fund handling), NEAR's `DeleteAccount` action lets any caller specify an arbitrary `beneficiary_id` that is only validated as a *syntactically well-formed* `AccountId`, never checked for actually existing or being of a type the refund-processing code can handle. When the beneficiary account does not exist and is not an implicit/deterministic account type, processing the resulting balance-refund receipt reaches an unconditional `panic!("must be implicit")`.

### Finding Description
`validate_delete_action` only calls `validate_action_account_id`, which validates format via `AccountId::validate`, and never checks that the account exists or is of an implicit type: [1](#0-0) 

When a `DeleteAccount` action executes and the deleted account has a positive balance, `action_delete_account` unconditionally creates a balance-refund receipt addressed to `beneficiary_id`, with no check that this account exists: [2](#0-1) 

That refund receipt is later applied through `action_transfer_or_implicit_account_creation`. If the target account does not exist (`account.as_mut()` returns `None`), the code path is: [3](#0-2) 

For a refund (`is_refund == true`), the `debug_assert!(!is_refund)` documents that this branch is not supposed to be reached by refunds at all, yet execution proceeds into `action_implicit_account_creation_transfer`, which explicitly panics for any `AccountType::NamedAccount`: [4](#0-3) 

The comment at the panic site states this is believed "unreachable" because `check_account_existence` supposedly rejects non-implicit, non-existent receivers before this function is invoked — but that existence check is designed for *user-submitted* `Transfer` actions during validation, not for internally generated system refund receipts such as `Receipt::new_balance_refund`, which are created directly by `action_delete_account` from an attacker-chosen `beneficiary_id` and dispatched without re-validating existence.

### Impact Explanation
If reachable (i.e., if refund receipts indeed bypass `check_account_existence`), a single unprivileged `DeleteAccount` transaction with a crafted `beneficiary_id` (any syntactically valid but non-existent, non-implicit account name, e.g. `"doesnotexist.near"`) causes a runtime panic while applying the chunk. This is a chain-halting/node-crash class bug — every validator applying that receipt would panic, producing a network-wide stall, which is far more severe than the fund-burning scenario in the original report.

### Likelihood Explanation
Likelihood is Medium-to-High if the refund path indeed skips `check_account_existence`: the trigger is a single, cheap, unprivileged transaction (`DeleteAccount` with a self-chosen `beneficiary_id`) requiring no special permissions, validator status, or victim cooperation — only that the deleted account holds a nonzero balance.

### Recommendation
- Validate that `beneficiary_id` in `DeleteAccountAction` either already exists as an account, or is of an implicit/deterministic account type that the refund-creation code can construct, at action-validation time (`validate_delete_action`), rejecting otherwise with a normal `ActionError` instead of deferring to receipt-processing time.
- Alternatively/additionally, make `action_transfer_or_implicit_account_creation` handle the `Named && !exists` case gracefully for refunds (burn the amount into `tokens_burnt`, matching the "burn to zero" precedent from the report, and emit a graceful `ActionError`) instead of calling into `action_implicit_account_creation_transfer`, which should remain a genuine `unreachable!()` only for validated call sites.

### Proof of Concept
This could not be fully verified end-to-end within the available exploration (in particular, whether `check_account_existence` is actually skipped for `Receipt::new_balance_refund` receipts, and whether `debug_assert!` builds are used in production validators). This should be confirmed by:
1. Constructing a `DeleteAccount` transaction on an account with `amount() > 0` and `beneficiary_id = "nonexistent-non-implicit.near"` (a syntactically valid, unused, non-implicit account name).
2. Tracing whether the generated `Receipt::new_balance_refund` bypasses `check_account_existence` before reaching `action_transfer_or_implicit_account_creation` in `runtime/runtime/src/lib.rs`.
3. Confirming whether execution reaches the `panic!("must be implicit")` in `action_implicit_account_creation_transfer` (`runtime/runtime/src/actions.rs:270`) in a release build (assert compiled out or not).
