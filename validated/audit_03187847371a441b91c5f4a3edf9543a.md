## Title
Unchecked ERC20 `transfer()` return value in `IntentGatewayV2.withdraw()` lets escrow accounting mark orders filled/refunded while tokens are never actually delivered - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of the Intent Gateway (`evm/tron/contracts/apps/IntentGatewayV2.sol`) releases escrowed tokens with a raw, unchecked low-level `.call()` to the ERC20's `transfer` selector instead of using `SafeERC20`. This is exactly the bug class in the report: `success` from `.call(...)` only reflects whether the call reverted, not whether the token contract's `transfer()` actually returned `true`. A token that returns `false` on failure instead of reverting will be treated as a successful transfer, while the contract permanently marks the order as filled/refunded and decrements escrow, with no tokens ever moving to the beneficiary.

### Finding Description
`withdraw()` releases escrow to a beneficiary using: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}
``` [2](#0-1) 

`success` here is only `true`/`false` based on whether the external call itself reverted (out-of-gas, revert, etc.) — it does **not** decode the `bytes` return data to check the boolean value the ERC20 standard requires `transfer()` to return. Non-compliant or legacy ERC20 tokens (and tokens that intentionally return `false` on failure, e.g. blacklist/pause conditions, insufficient balance in some implementations) will make this call return `success = true` with an encoded `false`, which is silently accepted.

Once accepted, the function proceeds to:
```solidity
_orders[body.commitment][token] -= amount;
...
emit EscrowReleased(...) / emit EscrowRefunded(...)
```
and for `RedeemEscrow`/`RefundEscrow` calls, also sets `_filled[body.commitment] = beneficiary;` — permanently finalizing the order as complete even though the beneficiary received nothing.

The same unchecked pattern also appears in the fee payout inside `withdraw()`: [3](#0-2) 

and in the governance `SweepDust` handler: [4](#0-3) 

By contrast, the canonical EVM implementation (`evm/src/apps/intentsv2/IntentsBase.sol`) uses `SafeERC20.safeTransfer`, which reverts on both a hard revert and a `false` return value: [5](#0-4) 

The Tron contract does not use `SafeERC20` for any of its outgoing token movements, reintroducing exactly the unchecked-return-value class described in the report.

`withdraw()` is reached via `onAccept` for cross-chain `RedeemEscrow`/`RefundEscrow` messages (delivered by any relayer once a Hyperbridge proof is submitted) and via `onGetResponse` for the source-chain cancel path — both are triggered by ordinary, unprivileged user/solver actions (placing an order, filling it, or cancelling it), not by governance or an admin: [6](#0-5) [7](#0-6) 

### Impact Explanation
Any order whose input/output token is a non-standard ERC20 that returns `false` (rather than reverting) on transfer failure allows the following losses:
- A solver/beneficiary can be denied their escrowed payout: the gateway believes the transfer succeeded (marks `_filled`, emits `EscrowReleased`/`EscrowRefunded`, decrements internal accounting) while the beneficiary receives zero tokens — a permanent, unrecoverable loss of the user's or solver's principal, since the order is now finalized and cannot be retried.
- This breaks the fundamental escrow-release invariant of the Intent Gateway (payment and settlement should be atomic), causing silent fund loss classified High per the reference report's Case 2 (payer/beneficiary ends up without funds although the contract's state says the exchange completed).

### Likelihood Explanation
Reaching this path requires only: (1) an order whose escrowed token contract returns `false` on a failed `transfer()` instead of reverting (a real-world token behavior, common among older/non-compliant ERC20s and TRC20/TRON-native tokens — plausible given this file targets the Tron EVM specifically), and (2) a legitimate relayed `RedeemEscrow`/`RefundEscrow`/GET-response delivery, which is a normal part of the protocol's cross-chain settlement and cancel flows, not a privileged action. No special permissions or governance access are needed.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` / `IERC20(...).transfer(...)` calls in `evm/tron/contracts/apps/IntentGatewayV2.sol` (in `withdraw()`, the fee payout, and `SweepDust` handling) with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, consistent with the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`. This ensures both revert-on-failure and `false`-return-on-failure tokens are correctly treated as failed transfers before escrow state is mutated or the order is finalized.

### Proof of Concept
1. Deploy an ERC20-like token whose `transfer()` returns `false` (no revert) when the caller's balance is insufficient or the recipient is disallowed — this is legal per the ERC20 standard and exists in real-world tokens.
2. Place a cross-chain order on the Tron `IntentGatewayV2` using this token as an input, and have a solver fill it on the destination chain (or let the deadline pass to trigger a refund/cancel).
3. Arrange for the outgoing `transfer()` inside `withdraw()` to fail silently (e.g. beneficiary is blacklisted by the token, or gateway's tracked balance for the token diverges from the token's own internal balance for any reason).
4. `withdraw()` proceeds past `if (!success) revert TransferFailed();` because the call itself did not revert, decrements `_orders[commitment][token]`, sets `_filled[commitment]`, and emits `EscrowReleased`/`EscrowRefunded` — even though the beneficiary's on-chain token balance did not increase. The beneficiary has permanently lost the escrowed funds with no path to retry, while the contract's own bookkeeping shows the order as successfully settled.
