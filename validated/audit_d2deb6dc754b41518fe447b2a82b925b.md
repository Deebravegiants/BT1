### Title
Predispatch escrow sweep in `IntentGatewayV2.placeOrder` trusts a raw `IERC20.transfer` call routed through `CallDispatcher` without checking the ERC-20 boolean return value, permanently corrupting escrow accounting - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
In the predispatch branch of `placeOrder`, the gateway sweeps tokens back from the `CallDispatcher` to itself using a raw, low-level encoded `IERC20.transfer` call rather than `SafeERC20.safeTransfer`. `CallDispatcher.dispatch` only checks that the low-level `.call` did not revert (`success`), never decoding/validating the ERC-20 boolean return value. For any token that signals failure by returning `false` instead of reverting, the sweep can silently fail while `_orders[commitment][token]` is still credited with the full `reducedInputs[i].amount`, permanently desynchronizing the escrow ledger from the gateway's real token balance for that order.

### Finding Description
In `placeOrder`, when an order carries predispatch calldata, funds are first moved to `_params.dispatcher` and a user-supplied call is executed there. Afterward, the gateway builds a `Call[]` to sweep the resulting balances back to itself, encoding a raw ERC-20 transfer instead of using `SafeERC20`: [1](#0-0) 

This is dispatched via `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))`, and `CallDispatcher.dispatch` only checks that the low-level call itself did not revert: [2](#0-1) 

For a standard-but-non-reverting ERC-20 (i.e., one that returns `false` on a failed `transfer` rather than reverting), `to.call(...)` succeeds (`success == true`) even though no tokens moved. Immediately after building this call, `placeOrder` unconditionally increments the escrow bookkeeping regardless of what actually happened on-chain: [3](#0-2) 

The same unchecked pattern (`abi.encodeWithSelector(IERC20.transfer.selector, ...)` dispatched through `ICallDispatcher`) is duplicated in the Tron and SDK copies of the contract: [4](#0-3) 

By contrast, every other collateral-moving path in the same contracts correctly uses `SafeERC20.safeTransferFrom`/`safeTransfer` (e.g. the non-predispatch input path, and `_withdraw`), showing the missing check is an inconsistency rather than an intentional design: [5](#0-4) 

This is the exact bug class from the external report: a code path that transfers the escrow/collateral token without going through `safeTransfer`/checking the boolean return value, allowing a non-reverting-failure ERC-20 to desynchronize internal accounting from actual token custody.

### Impact Explanation
Once `_orders[commitment][token]` is credited above the gateway's real balance for that token/commitment, any later attempt to settle that order (fill + `_withdraw`, or cancel + `_withdraw`) will call `IERC20.safeTransfer(beneficiary, amount)` for the phantom amount, which reverts because the gateway does not actually hold the tokens: [6](#0-5) 

Because `_withdraw` iterates over all tokens of the order atomically, this single corrupted token entry makes the *entire* order (including any other legitimately escrowed input tokens in the same order) permanently unfillable and uncancellable — a durable freeze of the honestly escrowed assets in that order and a denial-of-service on order settlement, reachable by any unprivileged user (order placer) via a single `placeOrder` transaction using predispatch calldata with a compatible token. No privileged role is required.

### Likelihood Explanation
This is trivially triggerable by any user who submits an order with `predispatch.call.length > 0` referencing a token whose `transfer` can return `false` on failure (a common ERC-20 pattern, and a token governance/allowlist may not always exclude such tokens, or a user-controlled predispatch call could leave the dispatcher's balance manipulated such that the transfer condition results in `false`). The vulnerability requires no attacker privilege beyond calling the public `placeOrder` entrypoint, matching the "unprivileged message dispatcher/token bridger" reachability bar.

### Recommendation
Replace the raw `abi.encodeWithSelector(IERC20.transfer.selector, ...)` construction in the predispatch sweep with `SafeERC20.safeTransfer`/`safeTransferFrom` semantics, or have `CallDispatcher`/`placeOrder` explicitly decode and validate the boolean return value of `transfer` calls routed through it before crediting `_orders[commitment][token]`. Apply the fix consistently across `evm/src/apps/IntentGatewayV2.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`, and `sdk/packages/core/contracts/apps/IntentGatewayV2.sol`. Add unit tests using a "return-false-on-failure" mock ERC-20 to cover the predispatch sweep path.

### Proof of Concept
1. Deploy a token `T` whose `transfer` returns `false` (instead of reverting) whenever a configurable failure condition is met (e.g. attacker sets `failNextTransfer = true`).
2. Attacker calls `IntentGatewayV2.placeOrder` with `order.predispatch.assets = [T, amount]` and a benign no-op `predispatch.call`, and `order.inputs` referencing the same token `T`.
3. Set `T.failNextTransfer = true` right before/inside the predispatch call so that the sweep-back `transfer(address(this), balance)` from the dispatcher returns `false` without reverting.
4. `CallDispatcher.dispatch` sees `success == true` (the call didn't revert) and returns normally.
5. `placeOrder` still executes `_orders[commitment][token] += reducedInputs[i].amount`, even though the gateway's actual `T` balance did not increase.
6. Any subsequent `fillOrder`/`cancelOrder` → `_withdraw` call for this commitment reverts on `IERC20(T).safeTransfer(beneficiary, amount)` due to insufficient real balance, permanently freezing the order and any other legitimately escrowed tokens within it.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
