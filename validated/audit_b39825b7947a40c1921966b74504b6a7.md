### Title
Webhook shop-domain/topic headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `Registry.process` validates the HMAC over the body only and then trusts the header-derived `shop`/`topic` values to route and label the payload to app-level handlers, breaking the intended binding `HMAC-signed bytes == bytes acted on`.

### Finding Description
`Utils::HmacValidator.validate` verifies the signature by calling `verifiable_query.to_signable_string`, which for webhooks is implemented as: [1](#0-0) 
Only `@raw_body` is signed. However, `shop`, `topic`, `webhook_id`, and `api_version` are all taken directly from HTTP headers, with zero cryptographic binding to the HMAC: [2](#0-1) [3](#0-2) 

`Registry.process` validates HMAC over the body, then immediately trusts these unauthenticated header fields to select the handler and to populate the metadata object handed to the app's business logic: [4](#0-3) 

Since a valid HMAC only proves the body bytes were signed by Shopify with the app's `client_secret` — it says nothing about which shop or topic that body was signed for — an attacker who legitimately receives real webhook deliveries for their own shop (any merchant who installs the app is, from the app's perspective, an "unprivileged" external actor relative to other tenants) can capture a body+HMAC pair from one webhook delivery and resend it to the app's webhook endpoint with a different `shopify-shop-domain` (and/or `shopify-topic`) header. `Utils::HmacValidator.validate` will still return `true` because it never looks at those headers, and `Registry.process` will build a `WebhookMetadata` claiming a different shop authored/received the event, then hand it to the app's handler.

This is the exact bug class named in scope: "a field acted on but not covered by the HMAC" — here `shop` (and `topic`/`webhook_id`) is acted upon (used to route, label, and attribute the event) but is not part of the signed bytes.

### Impact Explanation
This is a Critical-tier cross-tenant issue per the given impact taxonomy: an attacker who controls one legitimate shop installation can forge webhook events that the host application will process as if they came from an arbitrary other shop domain of the attacker's choosing (since `shop` is attacker-controlled header, not signature-bound). Any host application that uses `WebhookMetadata#shop` (as intended and documented) to key session lookups, data writes, or GDPR-style redaction flows will act on the wrong tenant, resulting in cross-tenant data corruption/injection without ever needing the app's `api_secret_key` or any privileged credential — only a legitimately-received webhook body/HMAC pair from the attacker's own shop.

### Likelihood Explanation
High likelihood: any merchant that installs the target app naturally receives real webhook deliveries with valid HMACs for their own shop. Replaying that body with a modified `shopify-shop-domain` header (a standard HTTP header, fully attacker-controlled in a raw request) is trivial and requires no cryptographic material beyond what the attacker already legitimately possesses from their own installation.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop` and `topic`) in the signed payload used for HMAC verification — e.g., by having `to_signable_string` canonically bind the header values together with the body, or by independently validating that `request.shop` matches a shop for which the app has an active installation/session before dispatching to a handler. At minimum, document and enforce that host applications must independently verify `WebhookMetadata#shop` against a known active session before trusting it, since the gem alone cannot currently guarantee this binding.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a real webhook (e.g., `orders/create`), capturing the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify over `B` using the app's `client_secret`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and the same header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally a different `X-Shopify-Topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers into `shop`/`topic` without any check against the HMAC.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and compares to `H` — validation succeeds because `B` is unchanged.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: JSON.parse(B), ...)` and invokes the app's handler, which now processes attacker-supplied data as if it were an authentic event from `victim.myshopify.com`. [4](#0-3) [5](#0-4)

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

      private

      sig { params(name: String).returns(T.untyped) }
