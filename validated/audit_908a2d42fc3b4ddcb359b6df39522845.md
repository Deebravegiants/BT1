### Title
Sign-extension bug in `numberToBigEndian` corrupts `ton_connect` timestamp encoding, causing `computeIntentHash` to diverge from the on-chain intent hash for timestamps ≥ 2^31 - (File: packages/intents-sdk/src/intents/intent-hashes/ton-connect.ts)

### Summary
`numberToBigEndian` uses JavaScript's bitwise `>>=` operator, which coerces its operand to a signed 32-bit integer (`ToInt32`) before shifting. For the 8-byte `timestamp` field in `computeTonConnectHash`, any timestamp ≥ 2^31 (a perfectly valid future Unix time, e.g. post year-2038) causes the low 32 bits to be treated as negative, so the arithmetic right shift sign-extends with `0xFF` instead of `0x00` into the high-order 4 bytes. This produces a hash input that diverges from the TON Connect spec's canonical unsigned 8-byte big-endian encoding, breaking the equality between the SDK's locally computed `computeIntentHash(multiPayload)` and the true `intent_hash` returned by `publishIntent`/tracked by the relay.

### Finding Description
The broken equality is:
`computeIntentHash(multiPayload)` (local, via `computeSignedTonConnectHash` → `computeTonConnectHash`) `==` `intent_hash` produced/verified by the network for that same `multiPayload`.

Root cause, in `numberToBigEndian`: [1](#0-0) 
`num >>= 8` operates on the ToInt32-coerced value. For `num = Number(timestamp)` where `timestamp >= 2**31`, the low-32-bit pattern's top bit is set, so `ToInt32` yields a negative number; the subsequent arithmetic shifts sign-extend with `1`s, filling the high 4 of the 8 output bytes with `0xFF` rather than `0x00`.

This is invoked directly in the hash-construction pipeline: [2](#0-1) 

`computeTonConnectHash` is reached from `computeIntentHash`, which is used both as the hook payload for integrators (`onBeforePublishIntent`) and, in the intended usage pattern, to derive the value passed to `waitForIntentSettlement`'s `intentHash` polling parameter: [3](#0-2) [4](#0-3) [5](#0-4) 

Attacker's exact input: any `ton_connect` `MultiPayload` where `timestamp` (part of the data the wallet signs) is set to a value ≥ `2**31` (e.g. `2**31 + 100`, a legitimate future int64 Unix timestamp — the JSON Schema for this field only checks type, with no freshness/range constraint): [6](#0-5) 

Since the `timestamp` is chosen by whoever constructs the payload before signing (the user's own wallet, or a counterparty whose payload an integrator forwards through the SDK), this value is fully attacker-controlled and requires no privileged access — no existing guard in this repo (`validate.ts`/JSON schema) restricts it to "now."

Exploit flow: attacker (or their own wallet client) signs a `ton_connect` payload with `timestamp >= 2**31`. The integrator calls `computeIntentHash` locally (e.g. via the `onBeforePublishIntent` hook) to persist a tracking key, and/or uses it to poll `waitForIntentSettlement`. Because `numberToBigEndian` sign-extends, the SDK's locally-computed hash differs from the real hash the network computes/tracks for the same signed bytes (any correctly-implemented big-endian u64 encoder, as used by TON Connect verifiers and the intents infrastructure, does not have this JS-specific ToInt32 truncation defect). The integrator's persisted ticket/hash no longer matches, so polling by that hash never observes settlement.

### Impact Explanation
The mismatch causes a hash misreport: the integrator's locally derived `intentHash` — used for persistence/deduplication and for `waitForIntentSettlement` polling — does not correspond to the actual settled intent hash on-chain. The integrator can conclude the intent was never submitted/settled and re-issue a new signed intent against the same funds, this is repeatable on every `ton_connect` payload where the signer sets `timestamp >= 2**31`. This matches the High severity category of "a status or hash misreport making an integrator credit or refund twice" / causing loss of tracking leading to duplicate signed intents.

### Likelihood Explanation
Preconditions: usage of the `ton_connect` standard and an integrator relying on the SDK's `computeIntentHash`/`onBeforePublishIntent` hook value (as documented) to track/poll intent settlement. Attacker cost is a single wallet-side choice of `timestamp` value (fully free, no on-chain cost, no special privilege) at signing time. Feasibility is high since nothing in the repo's schema or hash-computation code rejects or clamps out-of-range/future timestamps; the bug triggers deterministically for any `timestamp >= 2**31`.

### Recommendation
Fix `numberToBigEndian` to avoid JS 32-bit signed bitwise coercion, e.g. use `BigInt` arithmetic (`num & 0xffn`, `num >>= 8n`) or unsigned shifts (`>>> `) applied to properly split 32-bit halves, ensuring correct unsigned big-endian encoding for values up to 2^63-1 (or at least up to 2^32-1) matching the TON Connect wire format exactly.

function numberToBigEndian(num: number, bytes: number): Uint8Array {
	const result = new Uint8Array(bytes);
	for (let i = bytes - 1; i >= 0; i--) {
		result[i] = num & 0xff;
		num >>= 8;
	}
	return result;
}
