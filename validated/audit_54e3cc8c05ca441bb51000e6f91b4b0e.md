### Title
Permissionless accrual checkpointing lets a supplier divert protocol revenue - (File: contracts/pool/src/interest.rs)

### Summary
An unprivileged user can manipulate the frequency of market accrual through `Controller::update_indexes`, causing per-checkpoint rounding to suppress protocol revenue shares and leave more value claimable by suppliers. An attacker who controls a dominant supply position can checkpoint the market every ledger and later withdraw the diverted yield.

### Finding Description
`Controller::update_indexes` is explicitly permissionless and only requires the caller's own authorization. [1](#0-0)  The controller forwards the caller-selected asset list to the pool's `update_indexes` entrypoint. [2](#0-1) 

For each asset, `ops::market::accrue` loads the market, calls `interest::global_sync`, commits the state, and emits the updated snapshot. [3](#0-2)  `Cache::load` stamps the current ledger time, while `elapsed_ms` and `mark_accrued` make each successful call the next accrual boundary. [4](#0-3) [5](#0-4) 

`global_sync` runs `accrue_step` for each elapsed chunk and immediately mints the returned `revenue_shares` into protocol revenue. [6](#0-5) [7](#0-6)  The in-repo cadence harness identifies the resulting failure mode directly: frequent accrual can floor the protocol fee before the reserve factor applies, and because `update_indexes` is permissionless, the attacker chooses the cadence. [8](#0-7) 

The attacker benefits by owning supply shares while repeatedly advancing the accrual boundary; revenue shares are minted inside total supply, so reducing the revenue-share allocation leaves the corresponding value claimable through the attacker’s supply position. [9](#0-8) [10](#0-9) 

### Impact Explanation
This is theft of unclaimed protocol yield: value that should have accumulated as protocol revenue remains attributable to suppliers instead. The protocol's claimable revenue is later burned and paid only to the configured accumulator, so suppressing `revenue_shares` permanently reduces the amount the accumulator can receive. [11](#0-10)  On a market with sustained debt and a dominant attacker-controlled supply share, repeating the checkpoint every ledger can systematically divert reserve-factor yield.

### Likelihood Explanation
The attacker needs no privileged role, leaked key, governance approval, oracle manipulation, or victim interaction. They only need a funded supply position and can submit `update_indexes(caller, vec![hub_asset])` at their chosen cadence. [12](#0-11) [1](#0-0)  The cost is transaction fees for repeated accrual calls, while the benefit scales with the attacker's share of supply and the market's accrued interest.

### Recommendation
Make interest/revenue splitting invariant to checkpoint cadence. Track reserve-fee entitlement cumulatively at full `RAY` precision and round it only when revenue is claimed, or carry a persistent unrounded revenue remainder so fractional fees are not discarded at every `update_indexes` boundary. Protocol-fee rounding should favor revenue, for example by ceiling the fee-share calculation or accruing the reserve-factor entitlement before user-visible checkpoint rounding. The cadence harness should additionally assert that frequent accrual cannot reduce `revenue_claim` relative to a single accrual over the same elapsed interval.

### Proof of Concept
1. Create or select an active `(hub_id, asset)` market with borrowed liquidity and a positive reserve factor.
2. The attacker calls `Controller::supply(caller, 0, spoke_id, [(hub_asset, amount)])`, obtaining most or all of the market's supply shares.
3. Before a normal mutating call forces a large accrual, the attacker repeatedly calls `Controller::update_indexes(caller, [hub_asset])` once per ledger.
4. Each call loads `last_timestamp`, accrues only through the current ledger time, and stores that checkpoint as the next boundary.
5. The small per-checkpoint protocol-fee allocation is rounded down or eliminated, while interest remains reflected in supply claims.
6. The attacker withdraws their supply position and receives value that would have been minted as protocol revenue under the less frequent accrual cadence.
7. A later `claim_revenue` call transfers less to the accumulator, demonstrating loss of unclaimed protocol yield rather than merely moving revenue between honest suppliers.

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
```
