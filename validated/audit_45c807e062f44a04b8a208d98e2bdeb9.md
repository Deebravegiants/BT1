### Title
Webhook `shop` Identity Attributed Without HMAC Binding, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC digest only over the raw request body [1](#0-0) , while the `shop` identity that is later handed to the application handler is read directly and unauthenticated from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [2](#0-1) . `Registry.process` only validates the body HMAC and then forwards the untrusted `shop` header straight to the handler as the tenant identity [3](#0-2) . This breaks the binding `HMAC-verified bytes == tenant identity acted upon`: the bytes that are cryptographically verified (the body) are disjoint from the field (`shop`) that the documentation explicitly promises is verified as coming from Shopify.

### Finding Description
The webhook signature verification path is:
1. `HmacValidator.validate(request)` computes an HMAC over `request.to_signable_string`, which is defined as `@raw_body` only [1](#0-0)  and [4](#0-3) .
2. `Registry.process` raises `InvalidWebhookError` only if that body HMAC check fails, otherwise it immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and calls the handler [3](#0-2) .
3. `request.shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the HMAC-verified body [2](#0-1) .

The gem's own documentation states this call "will verify the request did indeed come from Shopify and then call the specified handler for that webhook" [5](#0-4)  and instructs host apps to treat `data.shop` as the authenticated shop domain of the webhook [6](#0-5) . In reality, only the body bytes are authenticated; the `shop` value that host applications are told to trust for tenant attribution is not covered by that authentication at all.

Any internet-reachable actor who can obtain one valid `(raw_body, hmac-sha256)` pair for the target app's client secret — trivially available to any merchant who installs the app on their own store and receives a single legitimate webhook — can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` header with any other merchant's `myshopify.com` domain. The HMAC still validates (it never inspected the header), and `Registry.process` dispatches the payload to the handler labeled as belonging to the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding failure: an unprivileged app installer (one legitimate tenant) can cause the library to attribute arbitrary attacker-supplied webhook data to a different tenant (`shop`) of their choosing, because the field used for tenant attribution is disjoint from the field cryptographically verified. Applications built on the documented contract ("process...will verify the request did indeed come from Shopify") will process this as a trusted event for the victim's store (e.g., enqueue "order created," "app uninstalled," or "shop update" work keyed by `data.shop`), which is exactly the cross-tenant access category called for by the rules.

### Likelihood Explanation
Reachability requires no secrets: the webhook endpoint is a normal public HTTP route exposed by the host app, and any user of the app (a legitimate installer) naturally receives real `(body, hmac)` pairs through ordinary use. Replaying the body with a different `shop-domain` header is a simple HTTP-level manipulation available to any unprivileged internet client, making this a low-effort, credential-free attack once one real webhook has been observed.

### Recommendation
Bind the `shop` (and ideally `topic`, `api_version`, `webhook_id`) values into the signed/verified content, or otherwise cryptographically tie the header-derived shop identity to the HMAC-covered body (e.g., include the shop domain in `to_signable_string`, or require the host app to cross-check `request.shop` against a shop already known to be associated with the specific `webhook_id`/subscription before trusting it). At minimum, update the documentation to clearly state that only the body is authenticated and that the `shop` header must not be treated as verified/trusted tenant identity without additional application-level checks.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers for a webhook topic (e.g. `orders/create`).
2. Shopify delivers a legitimate webhook to the app's public callback URL with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
4. Attacker replays an HTTP POST directly to the same public webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` accepts the request; `HmacValidator.validate` succeeds because it only checks `raw_body` [1](#0-0) ; `Registry.process` calls the app handler with `shop: "victim.myshopify.com"` [7](#0-6) , causing the host application to process attacker-controlled data as if it originated from the victim's store.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

        end
