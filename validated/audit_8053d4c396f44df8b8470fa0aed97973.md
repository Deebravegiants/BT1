### Title
Webhook shop/topic/metadata identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. All of the routing/identity metadata that the gem hands to the host application's webhook handler — `shop`, `topic`, `webhook_id`, `api_version` — comes from unauthenticated HTTP headers that are never part of the signed payload. Any party who possesses one valid `(raw_body, hmac)` pair signed with the app's shared secret (trivially obtainable by installing the app on their own store and receiving a real webhook) can replay that exact body/HMAC pair while substituting an arbitrary `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header. The signature will still validate, and the gem will hand the forged shop identity to the host app's handler as if it were authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 

`to_signable_string` returns only `@raw_body`. The `shop`, `topic`, `api_version`, and `webhook_id` accessors read directly from HTTP headers and are excluded from the signed string: [2](#0-1) 

`Registry.process` validates the HMAC against the request (i.e., against `raw_body` only), then immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to build the `WebhookMetadata` handed to the app-defined handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, which for a webhook is exactly `raw_body`: [4](#0-3) 

The identity binding the gem *should* enforce is: `shop header value == shop that the HMAC secures`. In reality the HMAC secures only the bytes of the body; the `shop` (and `topic`/`webhook_id`) header is a completely independent, unauthenticated value. Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-tenant), anyone who can get one legitimate webhook delivered to themselves (e.g., by installing the app on their own development/trial store) obtains a `(body, hmac)` pair that is valid for *any* shop header value — the signature computation never looks at the header at all. Replaying that pair with `X-Shopify-Shop-Domain` set to a victim shop causes `Registry.process` to invoke the host application's handler with a `WebhookMetadata` claiming to originate from the victim shop, while the actual signed content and event were never generated by Shopify for that shop.

This is the direct structural analogue of the reported GitLab bug: an access/identity claim (`shop`) is carried and acted upon without being bound to the value that was actually verified (the HMAC-covered `raw_body`), letting one tenant's legitimately-signed material be reattributed to another tenant.

### Impact Explanation
This breaks the shop/tenant boundary that host applications rely on to route webhook events (order updates, GDPR redaction requests, uninstall/app-scope changes, etc.) to the correct merchant's data. Per the documented usage pattern, apps key their persistence/business logic off `data.shop`: [5](#0-4) 

An attacker who installs the app on their own store can forge webhook deliveries "as" any other shop known to use the app, causing cross-tenant data confusion (e.g., injecting fake `orders/create`/`shop/redact` events attributed to a victim shop, or corrupting per-shop state keyed by the spoofed `shop` value). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only: (1) the ability to send an HTTP request to the app's public webhook endpoint (no credentials needed), and (2) a single legitimately-signed `(raw_body, hmac)` pair, which any unprivileged party can obtain by installing the target app on their own free/trial store and receiving one real webhook. No access token, `client_secret`, or privileged account is required — this is well within reach of an ordinary internet user.

### Recommendation
Bind the shop/topic identity to the HMAC-verified material instead of trusting unauthenticated headers:
- Extend `to_signable_string` (or add a separate verification step) that incorporates the `shop`, `topic`, and `webhook_id` header values into the signed content actually verifiable against Shopify's HMAC scheme, or
- Cross-check the header-derived `shop` against an independently trusted source (e.g., require the caller to supply the expected shop/session and compare it before dispatching to the handler), and
- Document/enforce that host applications must not trust `data.shop` from `WebhookMetadata` as an authentication signal without additional verification, or have the gem perform that verification itself before invoking the handler.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled store `attacker-shop.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g., `orders/create`) so Shopify delivers a real webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` header computed over the raw JSON body using the app's shared `api_secret_key`.
3. Capture the exact `raw_body` and `X-Shopify-Hmac-Sha256` value from that delivery.
4. Replay an HTTP POST to the same webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (it only checks `raw_body`), and `Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though Shopify never generated this event for that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
