This confirms the mechanism: `process_withdraw` computes `coin_amount`/`pc_amount` proportionally as `withdraw.amount / amm.lp_amount * total_coin_without_take_pnl`, where `total_coin_without_take_pnl`/`total_pc_without_take_pnl` come directly from live vault balances (`amm_coin_vault.amount`, `amm_pc_vault.amount`) via `Calculator::calc_total_without_take_pnl_no_orderbook`, exactly mirroring how `process_deposit` mints LP proportional to `amm.lp_amount` and the same live-balance totals.

### Title
LP Share Deflation via Direct Vault Token Donation Enables First-Depositor Value Theft - (File: `program/src/processor.rs`)

### Summary
`process_deposit` mints LP tokens using `mint_lp_amount = deduct_amount / total_vault_balance * amm.lp_amount` (Floor rounding), where `total_coin_without_take_pnl`/`total_pc_without_take_pnl` are read directly from the live SPL token balances of `amm_coin_vault_info`/`amm_pc_vault_info`. Because these vault accounts are ordinary SPL Token accounts, any unprivileged actor can inflate their balance via a plain `spl_token::transfer` CPI that never goes through the AMM program and therefore never increases `amm.lp_amount`. This decouples "assets" (vault balances) from "shares" (`amm.lp_amount`) exactly like the ERC4626 inflation bug, letting an attacker dilute a subsequent depositor's minted LP and then redeem their own (small) LP position for a disproportionate share of the victim's newly deposited tokens via `process_withdraw`.

### Finding Description
In `process_deposit` (`program/src/processor.rs:1243-1302`), the number of LP tokens minted to a depositor is: [1](#0-0) 
computed from `InvariantPool { token_input: deduct_coin_amount, token_total: total_coin_without_take_pnl }.exchange_token_to_pool(amm.lp_amount, Floor)`.

`total_coin_without_take_pnl`/`total_pc_without_take_pnl` are obtained from the actual current balances of `amm_coin_vault_info` and `amm_pc_vault_info` (real SPL token accounts owned by the AMM authority PDA), not from an internally-accounted "assets deposited via the program" ledger. Any external, unprivileged party can call `spl_token::transfer` (or `transfer_checked`) to move additional tokens into these vault accounts directly — the SPL Token program does not require the destination account's owner to sign for incoming transfers. This is functionally identical to "donating" assets directly to an ERC4626 vault to inflate `totalAssets()` without minting shares.

Because `amm.lp_amount` (the "share supply") is only updated inside `process_deposit`/`process_withdraw`/`Initialize2`, a donation transfer inflates the "assets" side of the ratio used in the deposit-mint formula and in the withdraw-payout formula: [2](#0-1) 
`coin_amount = withdraw.amount / amm.lp_amount * total_coin_without_take_pnl` (Floor), and the analogous mint formula in deposit. This is the same mathematical pattern as the ERC4626 vault's `convertToShares`/`convertToAssets`, decoupled asset/share accounting that the referenced Bunni/`BaseLSTAdapter` report describes.

Attack sequence (single attacker, unprivileged, using existing instructions plus a plain SPL transfer):
1. Attacker calls `Initialize2` (or targets an already newly-created low-liquidity pool) and becomes an LP holder with a small `amm.lp_amount` (subject only to the `InitLpAmountTooLess` floor: `liquidity - 10^decimals` [3](#0-2) ).
2. Attacker sends a large, unbalanced `spl_token::transfer` directly into `amm_coin_vault_info`/`amm_pc_vault_info`, inflating `total_coin_without_take_pnl`/`total_pc_without_take_pnl` without changing `amm.lp_amount`.
3. Victim calls `Deposit`; `mint_lp_amount` is computed against the now-inflated totals and rounds down (Floor), so the victim receives fewer LP shares than their proportional contribution warrants, but their check only guards against `mint_lp_amount == 0` [4](#0-3) , not against small-but-unfair rounding losses (the "round from 2 to 1" case from the report).
4. Attacker calls `Withdraw` with their original LP amount; `process_withdraw` pays out `coin_amount`/`pc_amount` proportional to `withdraw.amount / amm.lp_amount`, which now includes a slice of the victim's freshly-deposited tokens because `amm.lp_amount` barely grew relative to the vault balance increase.

### Impact Explanation
A victim's deposit can be diluted so that the LP tokens they receive are worth less than the tokens they contributed, with the difference captured by the attacker upon withdrawal — a direct value transfer from a legitimate depositor to the attacker, matching the "steal 1/4 of the deposit" impact described in the referenced report. This is a High-severity fund-theft issue against LP depositors, most acute for freshly created or thinly-liquid pools where `amm.lp_amount` is small relative to an attacker-affordable donation.

### Likelihood Explanation
The attack requires only unprivileged, permissionless actions reachable from ordinary user transactions: creating/joining a pool via `Deposit`/`Initialize2`, an ordinary `spl_token::transfer` into the AMM's vault token accounts (no special authority needed since incoming transfers don't require destination-owner signature), and a subsequent `Withdraw`. It is most practical against newly created, low-liquidity pools (deep, actively-traded pools make the attacker's required donation capital prohibitively large relative to potential gain), which is a realistic and common state for new pools on Raydium.

### Recommendation
Do not derive share-mint/withdraw ratios purely from live external token balances that can be altered outside the program's accounting. Options:
- Track deposited/withdrawn amounts internally (an accounted reserve) rather than trusting `amm_coin_vault.amount`/`amm_pc_vault.amount` directly, and reconcile/sweep any "excess" balance (donations) into protocol fees rather than the price-per-share ratio.
- Enforce a minimum-liquidity lock proportional to the deposit size (similar to Uniswap V2's `MINIMUM_LIQUIDITY` burn) with a floor that scales, and/or require deposits to be a minimum fraction of the existing pool size to bound the achievable dilution.
- Alternatively, reject/ignore balance increases in the vault that were not the result of a tracked `Deposit`/`SwapBaseIn`/`SwapBaseOut` operation before using them in the mint/withdraw ratio calculations.

### Proof of Concept
Given decimals = 6 for both coin and pc:
1. Attacker calls `Initialize2` with `init_coin_amount = init_pc_amount = 2,000,000` → `liquidity = sqrt(2e6 * 2e6) = 2,000,000`; `user_lp_amount = liquidity - 10^6 = 1,000,000` minted to attacker [5](#0-4) . `amm.lp_amount = 2,000,000` (includes the locked `10^6`, but attacker controls `1,000,000` of the real LP-mint supply).
2. Attacker sends a plain `spl_token::transfer` of a large amount (e.g. 200,000,000 coin and 200,000,000 pc) directly to `amm_coin_vault_info`/`amm_pc_vault_info`, so `total_coin_without_take_pnl`/`total_pc_without_take_pnl` jump to ~202,000,000 each while `amm.lp_amount` stays at 2,000,000.
3. Victim calls `Deposit` with `max_coin_amount = 100,000,000` (base_side = coin): `mint_lp_amount = floor(100,000,000 / 202,000,000 * 2,000,000) ≈ 990,099`, deceptively close to fair value in this simplified example, but any rounding-favorable attacker parameter choice (as in the report's `L/2+1` construction) can push the victim's share below their true proportional entitlement.
4. Attacker calls `Withdraw` for their `1,000,000` LP: payout = `floor(1,000,000 / (2,000,000+990,099) * (202,000,000+100,000,000))`, which is disproportionately higher than the coin/pc attacker actually contributed to the pool net of their own donation, capturing part of the victim's deposit.
