### Title
Webhook `shop`/`topic` metadata is not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `ShopifyAPI::Webhooks::Registry.process` and handed to app handlers via `WebhookMetadata` come from HTTP headers that are never part of the HMAC-signed material.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
i.e. it returns `@raw_body` only. The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all derived from separate, unsigned headers: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC exclusively over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` accepts any request whose body-only HMAC validates, then unconditionally trusts the request's `shop`/`topic`/`webhook_id`/`api_version` header values to build `WebhookMetadata`, which is passed to the app's handler: [4](#0-3) [5](#0-4) 

This breaks the intended identity binding: `HMAC-authenticated bytes == raw_body` but `shop attributed to the event (used by the handler for tenant-scoped effects) == unauthenticated header value`. Because the signature does not cover `shop-domain`/`topic`/`webhook-id`, any two values are interchangeable as long as the body and its HMAC stay paired. An attacker who legitimately receives one genuinely signed webhook (e.g., by installing the app on their own store and capturing a callback with a body they control, such as an `app/uninstalled` or `carts/update` payload where the body content is attacker-influenced or irrelevant) can replay the same `raw_body` + `x-shopify-hmac-sha256` pair while substituting a different `x-shopify-shop-domain` header for a victim shop and/or a different `x-shopify-topic`. The HMAC check still passes because it only re-hashes the untouched body, but the handler now executes under the attacker-chosen `shop` and `topic` metadata.

### Impact Explanation
This is a scope/identity-binding bypass reachable by any unprivileged internet user who can send a POST to the app's webhook endpoint and who has captured one validly signed webhook body (from their own tenant or a public/low-sensitivity topic). It allows forging the `shop` attribution and/or `topic` of an otherwise validly-signed webhook, letting an attacker trigger a handler's tenant-scoped logic (e.g. uninstall cleanup, GDPR redaction, subscription state changes) against an arbitrary victim shop domain, or re-route a payload to a different registered topic's handler — a cross-tenant confusion consistent with the "High/Critical" bar (cross-tenant access) called out in scope.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to first obtain one genuinely-signed webhook (trivial if they install the target app on their own development store, since Shopify will send them real signed webhooks), after which replay against arbitrary `shop`/`topic` header values costs nothing extra. No `api_secret_key`, access token, or credential theft is required — only observation of one legitimate webhook delivery to any shop the attacker controls.

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable material, or otherwise bind them cryptographically to the signed body (e.g., compute the HMAC over `"#{shop}|#{topic}|#{webhook_id}|#{raw_body}"`) rather than the raw body alone, so a valid signature can only ever be replayed for the exact shop/topic/webhook combination Shopify originally sent.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook for topic `carts/update`.
2. Shopify delivers a webhook to the app with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: carts/update`, and a valid `x-shopify-hmac-sha256` computed over the JSON body.
3. Attacker captures this full request (headers + raw body).
4. Attacker resends the identical raw body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different registered `x-shopify-topic`).
5. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC only over `to_signable_string` (`@raw_body`), which is unchanged, so validation succeeds: [6](#0-5) .
6. `Registry.process` builds `WebhookMetadata` using `request.shop` = `"victim-shop.myshopify.com"` and dispatches it to the app's handler, which now performs its logic under the attacker-chosen shop identity rather than the shop that actually sent the (only genuinely authenticated) body.
