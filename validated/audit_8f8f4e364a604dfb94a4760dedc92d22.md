### Title
Unbounded router allowance + fully attacker-controlled swap calldata lets any caller drain stranded/refunded token balance out of `LifiExternalAction` as their own output UTXO - ([File: contracts/external-actions/swaps/ExternalActionSwap.sol])

### Summary
`ExternalActionSwap.swap` computes `swappedAmount` purely as the ERC20/ETH balance delta measured across an arbitrary, attacker-supplied `externalActionMetadata` call to the router, while `approveUnlimited` leaves a standing max allowance from the action contract to the router. Because the Solidity code never verifies that the amount actually pulled/swapped by the router-call equals `inputAmount` (`-deltaAmounts[0]`), any balance already sitting in the action contract (e.g. router refunds of unspent input, rounding dust from a prior swap) can be folded into the current caller's `swappedAmount` and paid out entirely to that caller's own stealth-address UTXO.

### Finding Description
The invariant that should hold is: *tokens leaving the action contract in a transaction == `-deltaAmountChanges` that Hinkal transferred into the action for that same transaction.* In `swap`: [1](#0-0) 

`inputAmount` is derived from `deltaAmounts[0]` (the proof-committed amount Hinkal moved into the action, see `Hinkal._externalTransact`): [2](#0-1) 

but `inputAmount` is only passed into `callRouter` as an informational parameter — `LifiExternalAction.callRouter` never uses it to bound the actual swap: [3](#0-2) 

`approveUnlimited` grants the router `type(uint256).max` allowance over the action's ERC20 balance, persisting across transactions: [4](#0-3) 

The router call is made with `externalActionMetadata`, which the rules state the attacker fully controls; nothing constrains the encoded "fromAmount" inside that calldata to equal `inputAmount`. `swappedAmount` is then computed purely as `balanceAfter - balanceBefore` of `outputToken`, measured right before/after the router call: [5](#0-4) 

That whole `swappedAmount` (minus fees) is forwarded to `msg.sender` (Hinkal) and packaged as a single output UTXO owned by the attacker's `stealthAddressStructure`: [6](#0-5) 

If the action contract holds any pre-existing `inputToken` balance not accounted for by the current transaction's committed `deltaAmounts[0]` — for example dust/refunds the router leaves behind from a prior swap (a documented pattern for aggregators that quote a max "fromAmount" but only consume what the actual route needs, refunding the remainder to the caller, i.e. the action contract) — the attacker can craft `externalActionMetadata` that instructs the router to pull/swap that entire stranded balance (using the standing unlimited allowance) rather than just their own committed `inputAmount`. The resulting inflated `swappedAmount` is credited entirely to the attacker as their own output UTXO.

None of Hinkal's own guards catch this: the balance-diff/slippage checks in `Hinkal.transact` only compare Hinkal's *own* balance change against `circomData.amountChanges` and the returned `utxoSet`, and since the UTXO amount is derived directly from whatever the action decides to send back, the equation is self-consistent by construction — it validates internal accounting, not that the swap output is proportionate to the committed input: [7](#0-6) 

The slippage check (`balanceDif >= slippageValues[i]`) only enforces a floor, so it cannot block *excess* output. `verifyProof`, `rootHashExists`, `onlyAllowedRecipient`, and `nonReentrant` all pass normally since the attacker is a legitimate unprivileged caller with a valid proof for their own (small) committed amount — none of them constrain what happens inside `callRouter`.

### Impact Explanation
An attacker can claim value from the action contract's balance that was never part of their proof-committed `deltaAmountChanges`, receiving it as a legitimate shielded output UTXO under their own stealth address. This is direct theft of in-flight/stranded protocol/user funds parked in the external action, matching the Critical category ("direct theft of shielded or in-flight user funds"). The attack is repeatable any time residual balance accumulates in the action contract (e.g. after every swap that leaves router-refunded dust), letting a single attacker or bot systematically front-run and vacuum any stranded balance before it can be reclaimed by its rightful owner or admin sweep.

### Likelihood Explanation
Preconditions: (1) some ERC20/ETH balance must be sitting in the `LifiExternalAction` contract that is not part of the current transaction's committed input — plausible in practice through aggregator input-refund behavior baked into LI.FI-style routing (not "user mistake," but a designed protocol refund pattern that this contract does not sweep or account for); (2) the attacker must be able to construct router calldata that consumes more than their own committed `inputAmount` — feasible since `externalActionMetadata` is raw, unchecked calldata forwarded verbatim to `router.call`. The attacker's cost is a normal `Hinkal.transact` call with a valid proof for a trivial input amount; there is no privileged role or race condition needed beyond calling before anyone else claims the dust, and the standing `approveUnlimited` allowance makes the residual perpetually available to whoever swaps next.

### Recommendation
Bind the actual amount pulled/swapped by the router to the proof-committed `inputAmount`: either (a) have `callRouter`/the router-calldata builder assert the encoded "fromAmount" equals `inputAmount` (e.g. via post-call balance checks specifically on `inputToken`, requiring `balanceBefore(inputToken) - balanceAfter(inputToken) == inputAmount`), or (b) transfer exactly `inputAmount` of `inputToken` into a fresh/ isolated context (or pull via `transferFrom` with an exact, single-use approval rather than `approveUnlimited`) so the router can never consume more than what this transaction is authorized to move. Additionally, sweep/reconcile any stranded balance through an owner-only or explicitly accounted mechanism rather than leaving it silently claimable via arbitrary swap calldata.

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction` with a mock router that (a) on first call takes `X` of `inputToken` via `transferFrom` but only converts `X - refund` to `outputToken`, sending the `refund` amount of `inputToken` back to the caller (simulating a real aggregator's partial-fill refund) — this leaves `refund` stranded in the action contract, and confirm via `IERC20(inputToken).balanceOf(action)` that `refund > 0` after tx 1.
2. As a second, unrelated attacker, call `Hinkal.transact` with a valid proof committing a tiny `deltaAmounts[0]` (e.g. `1`), but supply `externalActionMetadata` for the mock router that swaps `1 + refund` of `inputToken` (using the standing `approveUnlimited` allowance) into `outputToken`.
3. Assert: `swappedAmount` returned by `callRouter` > what a swap of only `1` unit would produce, and the attacker's resulting UTXO (`utxoSet[0].amount`) reflects the `refund` amount as well.
4. Assert the broken equality: tokens leaving the action in tx 2 (`swappedAmount`-equivalent value) != `-deltaAmountChanges[0]` (`1`) that Hinkal sent it in tx 2, proving the attacker captured `refund` that was never part of their committed input.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
