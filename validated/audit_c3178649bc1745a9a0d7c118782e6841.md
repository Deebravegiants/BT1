### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing tenant-spoofing replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC over that signable string alone and then passes the header-derived `shop` value straight to the app's handler, breaking the intended binding `hmac_verified_bytes == data_the_handler_trusts_as_the_tenant_identifier`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
and only ever returns `@raw_body`. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes `HMAC-SHA256(api_secret_key, request.to_signable_string)` and constant-time-compares it to the `hmac` header: [2](#0-1) 
Because the signable string is just the body, the `shop`, `topic`, `webhook_id`, and `api_version` headers are never part of what is signed: [3](#0-2) 
Yet `Registry.process` uses `request.shop` (an unverified header) to build the `WebhookMetadata` passed to the app's handler: [4](#0-3) 
The gem's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole request — including the shop it claims to be from — is authenticated: [5](#0-4) 
and explicitly instructs handlers to key work off `data.shop`: [6](#0-5) 

This is a direct analog to the Qubit Finance bug class: the "resourceID"/token-contract binding in the Bridge was not covered by the same validation that gated the deposit, so an attacker could substitute an unvalidated value (`address(0)`) that was accepted anyway. Here the `shop` value that the handler trusts as the tenant key is never covered by the cryptographic check (`hmac`) that gates whether the request is processed at all.

**Break of binding:** `verified_bytes(raw_body)` ≠ `bytes_used_as_tenant_identifier(shop header)`.

### Impact Explanation
Any unprivileged internet user who has legitimately installed the app on their own store receives real webhooks with a valid `hmac` computed over the body of that webhook. Because the header set (`shop-domain`, `topic`, `webhook-id`) is not part of the signed content, the attacker can resend that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header (e.g., a victim's shop, or a shop the attacker never installed on). The HMAC check still passes because it only validates the unchanged body bytes. `Registry.process` then invokes the app's handler with `WebhookMetadata` whose `shop` field is fully attacker-controlled, despite the API's documentation assuring integrators the request has been "verified" to come from Shopify. Downstream this enables cross-tenant data injection/corruption in any app that uses `data.shop` (as the docs instruct) to key per-merchant storage or business logic, without any additional access to credentials, tokens, or privileged accounts.

### Likelihood Explanation
No secrets, tokens or elevated privileges are required — only network access to the app's public webhook route and the ability to install the app once (a normal, unprivileged action) to obtain one valid `(body, hmac)` pair to replay with forged headers. The vulnerable code path (`Registry.process` → `HmacValidator.validate` → handler invocation with header-derived `shop`) is on the default, documented integration flow shown in `docs/usage/webhooks.md`.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signed material (or otherwise cryptographically bind them to the body) in `Request#to_signable_string`, so any header tampering invalidates the signature. At minimum, `Registry.process` should independently verify that the `shop` claimed in headers matches a shop known to be associated with the specific `webhook_id`/subscription before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify delivers a legitimate webhook to the attacker's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
3. Attacker replays `POST /callback/orders/create` to the target app with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `webhook-id`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(secret, B)` — matches `H`, so validation passes.
5. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...))` is invoked, causing the app to process attacker-supplied data as if it belonged to `victim-shop.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
