### Title
User enumeration via distinct error messages on `/sessions` login endpoint - (File: core/sessions/localauth/orm.go)

### Summary
The Chainlink node's `/sessions` login endpoint returns different, verbatim error strings depending on whether the submitted email exists in the `users` table (`"Invalid email"`) or exists but with a wrong password (`"Invalid password"`). These errors are propagated unmodified into the JSON response body sent to an unauthenticated caller, allowing an attacker to enumerate valid node-operator/admin accounts — directly analogous to the Shopware `CHECKOUT__CUSTOMER_NOT_FOUND` vs `CHECKOUT__CUSTOMER_AUTH_BAD_CREDENTIALS` discrepancy (CVE-2026-31888, CWE-204).

### Finding Description
`orm.CreateSession` (the local authentication provider) first looks up the user by email, then performs distinct checks and returns distinct error values: [1](#0-0) 

```go
func (o *orm) CreateSession(ctx context.Context, sr sessions.SessionRequest) (string, error) {
	user, err := o.FindUser(ctx, sr.Email)
	if err != nil {
		return "", err
	}
	...
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		o.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid email")
	}

	if !utils.CheckPasswordHash(sr.Password, string(user.HashedPassword)) {
		o.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return "", pkgerrors.New("Invalid password")
	}
	...
}
```
When `FindUser` fails (email not registered), the underlying SQL "no rows" error (from `findUser`) is returned as-is; when the email *is* found but the password is wrong, the distinct string `"Invalid password"` is returned. The same email/password distinction pattern also exists in the LDAP and OIDC local-fallback authenticators: [2](#0-1) [3](#0-2) 

The HTTP handler for `/sessions` passes this error straight through to the client with no normalization: [4](#0-3) 

```go
sid, err := sc.App.AuthenticationProvider().CreateSession(ctx, sr)
if err != nil {
	jsonAPIError(c, http.StatusUnauthorized, err)
	return
}
```

`jsonAPIError` serializes `err.Error()` verbatim into the JSON API response body sent to the client: [5](#0-4) 

```go
func jsonAPIError(c *gin.Context, statusCode int, err error) {
	_ = c.Error(err).SetType(gin.ErrorTypePublic)
	var jsonErr *models.JSONAPIErrors
	if errors.As(err, &jsonErr) {
		c.JSON(statusCode, jsonErr)
		return
	}
	c.JSON(statusCode, models.NewJSONAPIErrorsWith(err.Error()))
}
```

The `/sessions` endpoint is reachable without authentication, gated only by a generic IP-based rate limiter, not per-account enumeration protection: [6](#0-5) 

The existing test suite even documents the two distinct outcome types by name (`"incorrect pwd"` vs `"incorrect email"`), confirming the behavior is intentional/observable rather than an artifact: [7](#0-6) 

Additionally, before password verification even occurs, the endpoint performs a WebAuthn (MFA) lookup keyed on the submitted email and can surface an internal-server error path distinguishable from the invalid-credentials path: [8](#0-7) 

### Impact Explanation
An unauthenticated network attacker can send crafted `POST /sessions` requests with candidate email addresses and a throwaway password, then distinguish `"Invalid email"` from `"Invalid password"` in the JSON response to determine which emails correspond to valid Chainlink node operator/admin accounts. Since Chainlink node UI/API accounts often correspond to node operators or team members with `admin`/`edit` privileges over a production node (job management, bridges, keys, EI configuration), enumerating valid accounts materially aids targeted credential-stuffing or phishing against a high-value node-operator surface. This matches CWE-204 Observable Response Discrepancy and is a direct structural analog of the reported Shopware Store API issue: two authentication code paths that were supposed to be indistinguishable are not.

### Likelihood Explanation
High likelihood of exploitability: the `/sessions` endpoint is intentionally unauthenticated (it's the login endpoint itself), requires no special network position, and the distinguishing behavior is deterministic and directly present in the HTTP response body (not a timing side channel). The only mitigating control is a generic IP+time rate limiter (`rl.UnauthenticatedPeriod()/rl.Unauthenticated()`), which — as in the original report — only throttles bulk requests, not single-probe enumeration, and is bypassable via IP rotation.

### Recommendation
Normalize both the "email not found" and "wrong password" code paths in `orm.CreateSession` (and the LDAP/OIDC local-fallback equivalents) to return a single generic error (e.g., `"invalid credentials"`), matching the pattern already used elsewhere for constant-time comparisons. Ensure `jsonAPIError` for `/sessions` failures never differentiates based on account existence, and consider unifying the WebAuthn pre-check so its failure/success paths don't leak account existence either.

### Proof of Concept
1. Unauthenticated attacker sends:
   `POST /sessions {"email":"knownuser@node.com","password":"wrongpw"}` → response body contains `"Invalid password"`.
2. Attacker sends:
   `POST /sessions {"email":"randomguess@node.com","password":"wrongpw"}` → response body contains `"Invalid email"` (or the underlying "no rows" SQL error string).
3. By comparing the two distinct error strings across many candidate emails, the attacker builds a list of confirmed, valid Chainlink node accounts without needing correct credentials, as reflected directly by `core/sessions/localauth/orm.go:156` vs `:161` and surfaced unmodified through `core/web/helpers.go:28`.

func (l *ldapAuthenticator) localLoginFallback(ctx context.Context, sr sessions.SessionRequest) (sessions.User, error) {
	var user sessions.User
	sql := "SELECT * FROM users WHERE lower(email) = lower($1)"
	err := l.ds.GetContext(ctx, &user, sql, sr.Email)
	if err != nil {
		return user, err
	}
	if !constantTimeEmailCompare(strings.ToLower(sr.Email), strings.ToLower(user.Email)) {
		l.auditLogger.Audit(audit.AuthLoginFailedEmail, map[string]any{"email": sr.Email})

		l.auditLogger.Audit(audit.AuthLoginFailedPassword, map[string]any{"email": sr.Email})
		return user, errors.New("invalid password")
	}

	return user, nil

func sessionRoutes(app chainlink.Application, r *gin.RouterGroup) {
	config := app.GetConfig()
	rl := config.WebServer().RateLimit()
	unauth := r.Group("/", rateLimiter(
		rl.UnauthenticatedPeriod(),
		rl.Unauthenticated(),
	))
	sc := NewSessionsController(app)
	unauth.POST("/sessions", sc.Create)
	auth := r.Group("/", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateBySession))
	auth.DELETE("/sessions", sc.Destroy)
}
