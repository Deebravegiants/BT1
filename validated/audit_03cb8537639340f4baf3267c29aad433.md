### Title
Unrevoked `approveUnlimited` router allowance lets an attacker steal residual token balance stuck in `LifiExternalAction`, minted as a fresh on-chain UTXO - (File: contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`LifiExternalAction.callRouter` grants the LI.FI router an unlimited, never-revoked ERC20 allowance over its own balance via `approveUnlimited`, and only measures `outputToken` balance before/after the router call to compute `swappedAmount`. Because `externalActionMetadata` is fully attacker-controlled calldata forwarded verbatim to the router, and Hinkal never checks the action contract's internal token flows for the *input* token (only its own balance), an attacker can make the router pull more `inputToken` out of `LifiExternalAction` than the `inputAmount`/`deltaAmountChanges` Hinkal transferred for that transaction, and have the resulting inflated `swappedAmount` legitimately minted into a brand-new on-chain UTXO.

### Finding Description
Equality that must hold: *tokens actually consumed from `LifiExternalAction`'s `inputToken` balance for a given call == `-deltaAmounts[0]` (the `inputAmount` Hinkal transferred to the action for that specific `circomData`)*. This is broken.

Path: `Hinkal.transact` → `_externalTransact` (transfers `-deltaAmountChanges[i]` of `inputToken` to the action, [1](#0-0) ) → `ExternalActionSwap.runAction` (gated only by `onlyAllowedRecipient`, i.e. any transaction routed through the registered Hinkal contract, [2](#0-1) ) → `swap` → `LifiExternalAction.callRouter`:

```
approveUnlimited(inputToken, router);
(bool success, ) = router.call(externalActionMetadata);
...
swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
``` [3](#0-2) 

`approveUnlimited` only re-approves if the current allowance is below `type(uint256).max/2`; it is never reduced back to the actually-used amount and persists across all future transactions of all users routed through this shared, stateful action contract. [4](#0-3) 

Root cause / exploit flow:
1. In a first transaction (attacker's own, or any prior legitimate swap), Hinkal transfers `inputAmount` of `inputToken` to `LifiExternalAction`, which then sets an unlimited allowance for the router and calls `router.call(externalActionMetadata)`. The attacker fully controls `externalActionMetadata` (it is a raw field of `circomData.externalActionData`, and only the `circomData.externalActionData.externalAddress`/`externalActionId` pair is checked in `Hinkal._externalTransact`, not the semantic contents of the metadata bytes). By choosing metadata that causes the router to pull less than the full `inputAmount` (e.g., a route that only spends part of the approved balance), residual `inputToken` dust is left sitting in `LifiExternalAction`'s balance while the router retains its unlimited allowance over it.
2. In a later transaction (any attacker, using their own UTXOs/proof), the attacker again routes a swap through `LifiExternalAction` with the same `inputToken`, declaring a small `deltaAmounts[0]` (small `inputAmount`). Hinkal transfers only that small amount to the action. Inside `callRouter`, the attacker's `externalActionMetadata` instructs the router to pull an amount from `LifiExternalAction` far larger than the freshly transferred `inputAmount` — up to the entire stuck balance — using the already-standing unlimited allowance (the router's own `transferFrom` pulls from `msg.sender` = `LifiExternalAction`, which is exactly the caller of `router.call`, so no third-party authorization is needed).
3. The router performs a real swap consuming this inflated input amount, so `swappedAmount = outputToken.balanceAfter - balanceBefore` is correspondingly inflated — it is a real, correctly-measured `outputToken` delta, so `LifiExternalAction`'s local accounting is “consistent”, but it never checked that the *input* side matched what Hinkal actually authorized for this transaction.
4. `ExternalActionSwap.swap` returns a UTXO with `amount = amountToSendToHinkal` computed from this inflated `swappedAmount` [5](#0-4) .
5. Back in `Hinkal.transact`, the only cross-check is `balanceDif == (onChainCreation? 0 : amountChanges[i]) + utxoAmount` [6](#0-5) . `balanceDif` for `outputToken` is Hinkal's own balance increase, which by construction exactly equals `amountToSendToHinkal` (the very same value used to build `utxoAmount`), so this check is tautological — it validates internal self-consistency of the return values, not that the swap only consumed the `inputAmount` Hinkal actually sent. The output UTXO commitment is created fresh on-chain via `createOnchainCommitment` from this inflated amount, with no circuit-level constraint tying it back to the burned input nullifier amount (swap outputs are inherently variable and not pre-committed in the SNARK, by design).

None of `performHinkalChecks`, `verifyProof`, `rootHashExists`, or the balance/slippage `require`s catch this, because they all operate on Hinkal's own balance deltas (which stay self-consistent) or on values the attacker fully controls (their own declared `slippageValues`, `amountChanges`), never on `LifiExternalAction`'s internal input-token balance/allowance state across transactions.

### Impact Explanation
An attacker can convert dust/residual `inputToken` balance stranded inside the shared `LifiExternalAction` contract — which may originate from other users' prior swaps that under-consumed their approved/transferred input — into a legitimately-minted shielded UTXO for themselves, without burning a matching amount of their own shielded balance. This is a theft of funds routed through the shared action contract by other users/the protocol, realized as extra shielded value minted to the attacker, repeatable every time residual balance/allowance accumulates. This matches "Critical – direct theft of shielded or in-flight user funds" / "minting shielded value without backing."

### Likelihood Explanation
Preconditions: (1) at least one prior swap through `LifiExternalAction` for a given `inputToken` that leaves the router with a standing allowance and leaves any non-zero token balance in the contract (achievable by the attacker themselves in a first transaction, or naturally occurring from any other user's partial-fill route), and (2) the LI.FI router exposes a function reachable via attacker-supplied calldata that pulls tokens from `msg.sender` (the router's normal swap entrypoints do exactly this). Both are fully within the attacker's control (their own txs, their own proofs, their own crafted `externalActionMetadata`); no privileged role is required. Cost is only gas plus normal swap fees; the attack is repeatable indefinitely as dust/allowance keeps being available.

### Recommendation
- In `LifiExternalAction.callRouter`, snapshot and check the `inputToken` balance of the action contract before and after the router call, and require that the amount actually consumed does not exceed `inputAmount` (revert otherwise), rather than only checking `outputToken`.
- Replace `approveUnlimited` with an exact, per-call approval equal to `inputAmount`, reset to 0 after the call (or use `forceApprove`/reset pattern), so no allowance persists between transactions.
- Sweep/disallow any leftover token balance in the action contract after each call (e.g., revert if `inputToken` balance after the call is greater than 0, or return leftover dust to Hinkal/the depositor instead of leaving it stranded).

### Proof of Concept
Foundry fork test plan:
1. Deploy `LifiExternalAction` with a mock router that supports: (a) a `swap(tokenIn, amountIn, tokenOut, amountOutMin)` style function pulling `amountIn` of `tokenIn` from `msg.sender` via `transferFrom` and sending `tokenOut` back, and (b) accepts arbitrary `amountIn` independent of any Hinkal-declared amount.
2. Tx1: Through `Hinkal.transact` with a valid proof, swap `inputToken`→`outputToken` with `deltaAmounts[0] = -1000`, but craft `externalActionMetadata` so the mock router only pulls `amountIn = 1` from `LifiExternalAction`, leaving `999` `inputToken` stuck in the contract while `router` retains `type(uint256).max` allowance over it.
3. Tx2 (attacker, unrelated UTXOs): call `Hinkal.transact` again for the same `inputToken`/`outputToken` pair with `deltaAmounts[0] = -1`, but craft `externalActionMetadata` so the mock router calls `transferFrom(LifiExternalAction, router, 1000)` (the full remaining balance) instead of just `1`, then swaps the full `1000` for `outputToken`.
4. Assert: `swappedAmount` returned by `callRouter` (and the resulting UTXO's `amount`) is computed from `1000` input tokens even though Hinkal only authorized/sent `-deltaAmounts[0] = 1` for this transaction — i.e., assert `actualInputConsumedByRouter (1000) != -deltaAmounts[0] (1)`, while `Hinkal.transact` still succeeds (all `require`s pass) and a new on-chain UTXO commitment for the inflated `outputToken` amount is inserted into the tree.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
