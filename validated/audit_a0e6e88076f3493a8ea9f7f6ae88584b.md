### Title
Webhook `shop` identifier is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature over the raw request body only, while the `shop-domain` header — which the gem hands to the app's webhook handler as the authoritative tenant identifier — is never included in the signed bytes. Any party that can obtain one genuine `(raw_body, hmac)` pair for the app (e.g. by installing the app on their own store and capturing a webhook Shopify sends them) can replay that same body/HMAC pair to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop. `Utils::HmacValidator` will validate successfully because the signature check never looks at the shop header, and the app's handler will process the payload as if it belonged to the victim tenant.

### Finding Description
The equality that should hold is: *bytes verified by the HMAC == bytes the app trusts for tenant identity*. In this gem, that equality is broken:

`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Webhooks::Request#shop` is read directly from an unauthenticated HTTP header: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the signature over `to_signable_string` (the body) and compares it to the `hmac` header — it never binds `shop`, `topic`, or `webhook_id` into the signed material: [3](#0-2) 

`Webhooks::Registry.process` accepts the request once the HMAC check passes and forwards `request.shop` straight into `WebhookMetadata`, which is what the app's handler will use to route/attribute the webhook to a merchant: [4](#0-3) [5](#0-4) 

The gem's own documentation instructs app authors to treat `data.shop` as the trusted shop domain of the webhook, reinforcing that this is the gem's documented API contract, not a misuse by the host app: [6](#0-5) 

Because the `api_secret_key` is a single, app-wide secret shared across every shop that installs the app (it is not per-shop), a valid `(body, hmac)` pair generated for shop A's webhook is cryptographically indistinguishable from a valid pair for shop B's webhook — only the (unsigned) `shop-domain` header differs. This directly parallels the report's root cause: a value used to make security/tenant decisions (`effectiveSupply()`/price) is derived from state that isn't bound by the check that's supposed to protect it (escrowed shares not burned); here, the value used to make a tenant decision (`shop`) isn't bound by the check that's supposed to protect it (the HMAC).

### Impact Explanation
This breaks the shop-authenticated-via-HMAC vs. shop-used-for-tenant-routing binding, allowing cross-tenant confusion: any user who can install the app on their own store (an "unprivileged internet user" from the app's perspective — no special privileges, access tokens, or `api_secret_key` needed) can capture a legitimately-signed webhook body and replay it with a forged shop header to make the host app process/attribute data under a different, victim tenant's identity. This matches the "cross-tenant access" Critical-impact category in scope.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app once on an attacker-controlled store to receive one genuine webhook, and (2) POSTing that same body/HMAC to the app's public webhook endpoint with a modified `X-Shopify-Shop-Domain` header. No secrets, tokens, or privileged access are required beyond normal app installation, which is available to any Shopify merchant/user. This is a low-effort, repeatable attack against any app relying solely on this gem's `Webhooks::Registry.process`/`Request` for both authenticity and tenant identification, exactly as documented.

### Recommendation
Bind the tenant-identifying fields into the signed material actually verified, or add an independent authenticity check for `shop`: e.g., require the receiving app to verify `request.shop` against a known/installed-shop list before trusting it, and/or extend `to_signable_string`/`HmacValidator` to incorporate `shop`, `topic`, and `webhook_id` (mirroring how `Oauth::AuthQuery#to_signable_string` already includes `shop` in its signed params) so a spoofed header invalidates the signature.

### Proof of Concept
1. Install the target Shopify app on attacker-owned store `attacker.myshopify.com`.
2. Trigger any subscribed webhook (e.g. `orders/create`) and capture the raw POST: `raw_body` and the `X-Shopify-Hmac-Sha256` header.
3. Replay the exact same `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and succeeds (per `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` (per `lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to act on/attribute attacker-controlled data as belonging to the victim shop.
