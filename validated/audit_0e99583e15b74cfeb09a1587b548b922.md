### Title
Webhook `shop`/`topic` identity not bound to HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook exclusively by validating the HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken from unauthenticated HTTP headers. Because the HMAC never binds those header fields, any party able to produce one validly-signed webhook body (i.e., any merchant who has the app installed) can replay that body to the app's public webhook endpoint while forging the `shop-domain` header to impersonate a different, victim tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute and compare the HMAC solely against that signable string (the body), never against `shop`, `topic`, or `webhook_id`: [2](#0-1) 

`Registry.process` treats a passing HMAC check as authorization to trust the request's headers wholesale, and immediately builds `WebhookMetadata` from `request.shop`, `request.topic`, and `request.webhook_id` — all of which come straight from attacker-controlled HTTP headers, not from the signed payload: [3](#0-2) [4](#0-3) 

The binding that is broken can be stated as an equality that the gem fails to enforce:
`shop_that_signed(body) == shop_claimed_in(shop-domain header)`

Since a single `api_secret_key` is shared by every shop that has the app installed, any merchant with the app installed can trigger a real webhook on their own store, capture the (correctly) signed body + HMAC, and then send that exact body/HMAC pair directly to the app's public webhook endpoint with a forged `shopify-shop-domain` header naming a different, victim shop (and optionally a different `shopify-topic`/`shopify-webhook-id`). `Utils::HmacValidator.validate` in `Registry.process` still passes because the signature only ever covered the body, and the handler is invoked believing the data originated from the victim tenant.

### Impact Explanation
This breaks the tenant isolation the HMAC check is supposed to provide: the handler processes attacker-supplied JSON body content while `WebhookMetadata#shop` falsely identifies it as belonging to another merchant's store. Depending on how the host application's webhook handlers key off `data.shop` (e.g., to look up/update per-shop records, credentials, or trigger shop-scoped side effects), this enables cross-tenant data injection/corruption using another tenant's identity — a High-severity cross-tenant access issue, since the confusion is driven entirely by an identity claim that the gem itself fails to cryptographically bind to the signed material.

### Likelihood Explanation
Requires only that the attacker have the app installed on any shop they control (a normal, unprivileged action for any merchant who can install a public/custom app) and be able to send an arbitrary HTTP POST to the app's public webhook URL — no access token, API secret, or privileged account is needed. The gem's own `HmacValidator`/`Registry.process` implementation is the root cause: it validates the wrong scope of data (body-only) versus what it trusts (headers).

### Recommendation
Bind the identity fields to the authenticated computation instead of trusting raw headers post-hoc:
- Include `shop-domain` (and ideally `topic`/`webhook-id`) in the HMAC-covered signable string, matching what Shopify's outbound webhook signature actually protects, or
- Require the host application (and this gem's `Request`) to cross-check the `shop-domain` header against a shop the app actually knows/expects (e.g. compare to the session used to register that specific webhook) before dispatching, rejecting mismatches.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any webhook topic (e.g. `orders/create`) on that shop; capture the raw JSON body and the `X-Shopify-Hmac-Sha256` value Shopify sends — this HMAC is valid because it is computed with the shared `api_secret_key`.
3. Send a direct POST to the app's public webhook endpoint reusing that exact body and HMAC header, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com` (and optionally any `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the body (`request.to_signable_string`), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the app to process attacker-controlled data under the victim shop's identity.
