## Finding

### Title
Secondary `FungibleStore` objects are transferable at the object layer, letting holders bypass `frozen`/dispatch-hook custody controls and silently burn value with no supply accounting - (File: `aptos-move/framework/aptos-framework/sources/fungible_asset.move`)

### Summary
The external GNTDeposit report reduces to one invariant: *a holder must not be able to move value to an unrecoverable/uncontrolled destination through a path that bypasses the protocol's burn/transfer authorization and accounting*. In Aptos, `fungible_asset::create_store` creates a `FungibleStore` object without disabling `allow_ungated_transfer`, unlike `primary_fungible_store::create_primary_store`, which explicitly calls `disable_ungated_transfer` "as deterministic stores shouldn't be transferrable" [1](#0-0) . Because a secondary `FungibleStore` is itself an `Object`, any owner can call `object::transfer`/`object::transfer_call` on the store object directly, moving the entire underlying balance to any address without going through `fungible_asset::withdraw`/`deposit` at all.

### Finding Description
`fungible_asset::create_store` only disables transfer of the store when the FA type itself is globally marked `Untransferable`; otherwise the store inherits the default `allow_ungated_transfer = true` from `object::create_object`: [2](#0-1) 

This is confirmed by the framework's own unit test: transferring a normal (non-`Untransferable`) store via `object::transfer` succeeds — only the `set_untransferable` case is expected to fail: [3](#0-2) 

`object::transfer_raw` / `transfer_call` only check `allow_ungated_transfer` and ownership chains — they never touch `FungibleStore.frozen`, never call `withdraw_sanity_check`/`deposit_sanity_check`, and never invoke `DispatchFunctionStore` withdraw/deposit hooks: [4](#0-3) 

Compare this to the intended withdraw/deposit path, which enforces `frozen` and dispatch hooks (used by real deployed patterns such as `usdk.move`'s denylist and `FACoin.move`'s pause check): [5](#0-4) [6](#0-5) 

Because the object-transfer path bypasses all of this:
- A frozen or denylisted store's balance can still be moved out by transferring the *store object itself* to another address the attacker controls, defeating `set_frozen_flag`/denylist compliance controls entirely.
- The store (with its balance) can be transferred directly to `object::BURN_ADDRESS` (`0xfff...fff`) via `transfer_raw`/`transfer_call` instead of via the sanctioned `object::burn` (which only tombstones and preserves recoverability). A direct `transfer` to `BURN_ADDRESS` creates **no `TombStone`**: [7](#0-6) [8](#0-7) 

Since `unburn` requires an existing `TombStone`, this destination is permanently unrecoverable — but the `Supply`/`ConcurrentSupply` global counters are **never decreased**, because no `BurnRef.burn`/`decrease_supply` call ever executes. The `Withdraw`/`Deposit`/`Burn` events also never fire, exactly mirroring the GNTDeposit pattern of value disappearing from circulation without the corresponding `Burn` accounting event.

### Impact Explanation
Any unprivileged holder of a non-primary `FungibleStore` (a normal, widely-used pattern for isolating balances outside of `primary_fungible_store`, e.g. `fungible_asset::create_store` used directly by dApps/user-owned objects) can:
1. Bypass `frozen` state and dispatch-based compliance hooks (denylist/pause) to move funds out from under an issuer's freeze/denylist control.
2. Permanently and irrecoverably move balances to `BURN_ADDRESS` without triggering `BurnRef`/`decrease_supply`, corrupting the relationship between `Supply.current` and actually-circulating/accessible balance — a supply/custody accounting corruption identical in spirit to the GNTDeposit issue.

This is a genuine custody-invariant violation (accounting corruption + freeze/compliance bypass + irrecoverable value loss) affecting any fungible asset whose issuer relies on `frozen`/dispatch hooks for compliance and that permits (directly or indirectly) users to hold balances in non-primary stores.

### Likelihood Explanation
Likelihood is Medium: it requires the FA/dApp design to expose secondary `FungibleStore` objects that end users directly own (rather than exclusively using `primary_fungible_store`, which is hardened against this). This is a real and common pattern (any contract calling `fungible_asset::create_store` for user-facing balances, vaults, or per-purpose stores) rather than a purely theoretical corner case, and requires no special privilege — just ordinary `object::transfer_call` from the store owner.

### Recommendation
`fungible_asset::create_store` should disable ungated transfer on every `FungibleStore` object by default (mirroring `primary_fungible_store::create_primary_store`'s `disable_ungated_transfer` call), regardless of whether the underlying metadata is marked `Untransferable`. Store movement should only be possible through the sanctioned withdraw/deposit (and dispatch-hook-aware) APIs, or explicitly via `TransferRef`, never via raw object ownership transfer of the store itself.

### Proof of Concept
1. Issuer creates FA `X` with `set_frozen_flag`/dispatch-hook based denylist controls (e.g., like `usdk.move`).
2. User creates a personal object and calls `fungible_asset::create_store(&constructor_ref, X)`, then deposits funds into it (e.g. via `fungible_asset::deposit`), holding balance in this secondary store instead of a primary store.
3. Issuer freezes/denylists the user's store via `TransferRef`.
4. User calls `object::transfer_call(user_signer, store_address, attacker_or_burn_address)` — this succeeds (per `test_untransferable`, only `Untransferable`-marked FAs block this), moving the entire frozen balance out, bypassing `frozen`/denylist enforcement.
5. Alternatively, user calls `object::transfer_call(user_signer, store_address, object::BURN_ADDRESS)` directly (not via `object::burn`) — balance becomes permanently inaccessible with **no `TombStone`**, **no `Burn` event**, and **`Supply.current` unchanged**, reproducing the GNTDeposit-style supply/circulation accounting mismatch.     /// Allow an object to hold a store for fungible assets.
    /// Applications can use this to create multiple stores for isolating fungible assets for different purposes.
    public fun create_store<T: key>(
        constructor_ref: &ConstructorRef, metadata: Object<T>
    ): Object<FungibleStore> {
        let store_obj = &constructor_ref.generate_signer();
        move_to(
            store_obj,
            FungibleStore { metadata: metadata.convert(), balance: 0, frozen: false }
        );

        if (is_untransferable(metadata)) {
            constructor_ref.set_untransferable();
        };

        if (default_to_concurrent_fungible_balance()) {
            move_to(
                store_obj,
                ConcurrentFungibleBalance {
                    balance: aggregator_v2::create_unbounded_aggregator()
                }
            );
        };

        constructor_ref.object_from_constructor_ref<FungibleStore>()
    }

    public fun transfer_raw(
        owner: &signer,
        object: address,
        to: address,
    ) {
        let owner_address = signer::address_of(owner);
        verify_ungated_and_descendant(owner_address, object);
        transfer_raw_inner(object, to);
    }

    inline fun transfer_raw_inner(object: address, to: address) {
        let object_core = borrow_global_mut<ObjectCore>(object);
        if (object_core.owner != to) {
            event::emit(
                Transfer {
                    object,
                    from: object_core.owner,
                    to,
                },
            );
            object_core.owner = to;
        };
    }

    /// Transfer the given object to another object. See `transfer` for more information.
    public entry fun transfer_to_object<O: key, T: key>(
        owner: &signer,
        object: Object<O>,
        to: Object<T>,
    ) {
        transfer(owner, object, to.inner)
    }

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

    /// Add a TombStone to the object.  The object will then be interpreted as hidden via indexers.
    /// This only works for objects directly owned and for simplicity does not apply to indirectly owned objects.
    /// Original owners can reclaim burnt objects any time in the future by calling unburn.
    /// Please use the test only [`object::burn_object_with_transfer`] for testing with previously burned objects.
    public entry fun burn<T: key>(owner: &signer, object: Object<T>) {
        let original_owner = signer::address_of(owner);
        assert!(is_owner(object, original_owner), error::permission_denied(ENOT_OBJECT_OWNER));
        let object_addr = object.inner;
        assert!(!exists<TombStone>(object_addr), EOBJECT_ALREADY_BURNT);
        move_to(&create_signer(object_addr), TombStone { original_owner });
    }

    /// Allow origin owners to reclaim any objects they previous burnt.
    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
