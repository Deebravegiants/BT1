### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `ShopifyAPI::Webhooks::Registry.process` trusts the unauthenticated `shop-domain` header (exposed via `Request#shop`) to identify which merchant/tenant a webhook belongs to. Since the app's `api_secret_key` is a single, app-wide secret shared across every shop that installs the app, any user who installs the app on their own store can capture a validly-HMAC-signed webhook and replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop, defeating the HMAC's purpose as a tenant-binding mechanism.

### Finding Description
The vulnerability pattern mirrors the reported bug class: a value that is *acted upon* by the code (here, `shop`, used as the tenant identifier passed to the handler) is not covered by the cryptographic check that is supposed to authenticate the request (the HMAC).

- `Webhooks::Request#hmac` decodes the `hmac-sha256` header, and `#to_signable_string` returns `@raw_body` only [3](#0-2) .
- `Webhooks::Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from attacker-controllable HTTP headers, with no relationship to the signed body [4](#0-3) .
- `Utils::HmacValidator.validate` only compares an HMAC computed over `to_signable_string` (i.e., the raw body) against the received HMAC, using the app's single `Context.api_secret_key` [5](#0-4) .
- `Registry.process` gates on that same HMAC validation, then unconditionally builds `WebhookMetadata` using `request.shop` (the header value) as the tenant identifier passed to the app's handler [2](#0-1) .

The binding that is broken is: `authenticated_tenant (bound by HMAC over signed content)` should equal `shop used to scope handler data (WebhookMetadata#shop)`. In this implementation, `signed_content = raw_body` while `used_tenant_identifier = header["shop-domain"]`, and these are never checked against each other. Because the HMAC secret (`api_secret_key`) is identical for every shop that installs a given app (it's the app's secret, not a per-shop secret), an attacker with a normal, unprivileged Shopify store can install the target app and receive legitimate webhooks signed with that same secret. The attacker then re-POSTs the captured `raw_body` (unmodified, so the HMAC still validates) to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` forwards the attacker-chosen `shop` value straight to the host app's handler as if it were an authenticated fact about the victim shop.

### Impact Explanation
This is a cross-tenant data confusion primitive at the gem level: the gem hands the host application a `shop` value in `WebhookMetadata` that it implicitly presents as HMAC-authenticated (because `Registry.process` only proceeds after `HmacValidator.validate` succeeds), when in fact that field was never covered by the signature. Any host app that uses `data.shop` from `handler.handle` to key writes/reads (e.g., "store `data.body` under shop `data.shop`") can have attacker-controlled shop-scoped data corrupted, or fed with fabricated events attributed to a shop the attacker doesn't own — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Reaching this requires only: (1) installing the target app onto an attacker-owned, unprivileged store — a normal, no-privilege action available to anyone on Shopify — to obtain one legitimate HMAC-signed webhook body/signature pair, and (2) POSTing that raw body and signature to the app's public webhook callback URL with a forged `shop-domain` header. No access token, `client_secret`, or `api_secret_key` disclosure is needed; the attacker only reuses a signature they legitimately received for their own shop's traffic.

### Recommendation
Bind the tenant identity into the signed content, or otherwise independently verify `shop` against a value that is authenticated. Options:
- Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in `to_signable_string`, matching them against the value returned by `#shop` before trusting it downstream.
- Alternatively, require host apps to cross-check `request.shop` against a known, previously-registered/installed shop record before acting on `WebhookMetadata#shop`, and document this requirement clearly since the current API implies the shop field is authenticated once HMAC validation passes.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a normal, no-privilege operation).
2. Attacker triggers a webhook event (e.g., `orders/create`) on their own store, receiving a POST to the app's webhook endpoint with headers `x-shopify-hmac-sha256: <hmac>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and some `raw_body`.
3. Attacker resends the exact same `raw_body` and `x-shopify-hmac-sha256` value to the same webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only [6](#0-5)  — it still matches, since the header change didn't alter `to_signable_string`.
5. `Registry.process` calls the host app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [7](#0-6) , even though the payload actually originated from the attacker's own shop.
