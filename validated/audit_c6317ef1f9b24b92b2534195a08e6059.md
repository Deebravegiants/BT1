This confirms the vulnerability. The `Registry.process` method binds `request.shop`, `request.topic`, and `request.webhook_id` — none of which are covered by the HMAC — into `WebhookMetadata`, which is handed to the app's handler as trusted, authenticated data.

### Title
Webhook shop/topic identity spoofing via unauthenticated headers — HMAC only covers request body, not the `X-Shopify-Shop-Domain`/topic/webhook-id headers used for tenant identification - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively over that signable string [2](#0-1) . However, `Registry.process` extracts the tenant identity (`request.shop`), the `topic`, and the `webhook_id` directly from HTTP headers that are never included in the HMAC computation, and forwards them as trusted fields to the app's webhook handler [3](#0-2) . This breaks the identity binding: `hmac_verified(body) == true` does not imply `shop_header == shop_that_actually_sent_this_body`.

### Finding Description
The `Request` object is built from the raw body and headers [4](#0-3) . Its `shop`, `topic`, `webhook_id`, and `api_version` accessors all read from headers [5](#0-4) , while `hmac` and `to_signable_string` are the only fields covered by the cryptographic check, and `to_signable_string` is just `@raw_body` [6](#0-5) .

`Registry.process` performs:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [3](#0-2) 

The HMAC check only proves the body bytes were signed by someone possessing `Context.api_secret_key` (i.e., Shopify, for *some* legitimate webhook delivery to *some* shop running this app). It proves nothing about which shop the `x-shopify-shop-domain`/`shopify-shop-domain` header claims. Since any shop can install a publicly-installable app and receive genuinely-signed webhooks for itself, an attacker who owns/controls Shop A (unprivileged, no special credentials needed — just installing the app on their own store) can capture one authentic `(raw_body, hmac)` pair from a webhook Shopify sends them, then replay that identical `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with Shop B's domain (a public, guessable/known value — merchant `.myshopify.com` domains are not secret). `HmacValidator.validate` still returns `true` because it only re-hashes `raw_body`; `Registry.process` then calls the handler with `shop: "shop-b.myshopify.com"` even though the body content and signature originated entirely from Shop A's install.

This is the direct analog of the ERC20 `approve`/`transferFrom` race: the value that is *acted upon* (`shop`, used by the app to bind data/actions to a tenant) is not the value that was *authenticated* (the raw body bytes only). Before: `hmac_valid == (shop_header == originating_shop)`. After attacker's replay: `hmac_valid == true` while `shop_header != originating_shop` — the binding `shop_header == shop_that_signed_body` is broken.

### Impact Explanation
Any app built on this gem that trusts `WebhookMetadata#shop` (or `#topic`/`#webhook_id`) after `Registry.process` succeeds — which is the documented, expected usage pattern since HMAC validation is the library's only stated integrity guarantee — can be made to process attacker-supplied webhook bodies under an arbitrary victim shop's identity. Depending on the handler's logic (e.g., `app/uninstalled`, `shop/update`, billing-related topics, GDPR `customers/redact`), this enables cross-tenant data corruption, spoofed uninstall/redaction events against a victim shop, or state confusion between tenants — all without needing the app's `client_secret`, an access token, or any privileged credential, satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on an attacker-controlled shop (a normal, unprivileged action for any public app), (2) capturing one legitimate webhook delivery (raw body + `X-Shopify-Hmac-Sha256` header), and (3) replaying it to the app's webhook endpoint with a modified shop-domain header. No secret material, brute force, or timing race is needed — this is a deterministic forgery, not a probabilistic one, making likelihood high wherever the host app relies on `WebhookMetadata#shop` for authorization/tenant binding after this gem's `Registry.process` returns successfully.

### Recommendation
Include the tenant-identifying headers (at minimum `shop`, and ideally `topic`/`webhook-id`) in the HMAC-signed payload used by `HmacValidator`, or otherwise cryptographically bind them to the signature — e.g., verify HMAC over `"#{shop}|#{topic}|#{raw_body}"` instead of `raw_body` alone — so that a signature validated for one shop's payload cannot be replayed with a different shop's identity attached. At minimum, document explicitly that `Request#shop`/`#topic`/`#webhook_id` are unauthenticated headers not covered by HMAC verification, so host applications know they must independently correlate the shop header against a shop they already have an active session/install record for before trusting webhook content.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop "attacker.myshopify.com"
#    and receives a legitimate webhook (e.g. app/uninstalled), capturing:
raw_body = '{"id":123}'
hmac_b64 = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# 2. Attacker replays the SAME body/hmac to the app's webhook endpoint,
#    but swaps the shop-domain header to a victim shop's public domain:
headers = {
  "x-shopify-topic" => "app/uninstalled",
  "x-shopify-hmac-sha256" => hmac_b64,       # still valid — body unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # attacker-controlled, not signed
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true (only raw_body is checked)

ShopifyAPI::Webhooks::Registry.process(request)
# Handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", ...)
# even though the payload/signature came entirely from the attacker's own shop.
```
