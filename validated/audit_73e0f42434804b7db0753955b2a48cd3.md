Based on the analysis, I've found a valid structural analog to the Algorand vault bug: a cryptographic signature that authenticates only a subset of the fields relevant to a signup request, leaving other security-relevant fields ("distributorId"/operator attribution and `region`) outside the signed digest and thus tamperable without invalidating the signature — mirroring the missing `RekeyTo` check pattern (validating *some* fields of a transaction/request while omitting others that materially affect outcome/attribution).

### Title
Secure-Element Signup Signature Omits Operator/Distributor Attribution Field, Allowing Misattributed Signup Credit - (File: `src/plans/enroll_user.rs`)

### Summary
The signup request built in `signup_post::request` sends a `distributorId` field (`operator_qr_code.user_id`) alongside a secure-element-generated `signature`, but the signature itself is computed by `make_signature` over only `ORB_ID`, the user's `user_id`, and the iris code/mask data — it never includes the operator/distributor identifier. Because the field that determines which operator/distributor is credited for the signup is not covered by the cryptographic proof, it can be altered in transit or by any code path preceding the network call without invalidating the signature, analogous to the vault contract validating some transaction fields (asset amount, receiver) while omitting `RekeyTo`, which let an attacker mutate an unchecked but security-relevant field.

### Finding Description
`make_signature` in `src/plans/enroll_user.rs` hashes and signs a narrow set of fields: [1](#0-0) 

This signature is then transmitted together with, but not binding, the `distributorId` and `region` fields in the multipart form built by `signup_post::request`: [2](#0-1) 

The `operator_qr_code` (whose `user_id` becomes `distributorId`) is captured earlier in the signup flow and passed down through `enroll_user::Plan`: [3](#0-2) 

Just as the vault's burn validation checked `AssetAmount`, `AssetReceiver`, and `XferAsset` but never verified `RekeyTo` — a field that, left unchecked, let the vault owner redirect control of the account after the checked transaction executed — the signup signature validates the iris biometric payload and `ORB_ID`/`user_id` but never binds `distributorId`/`region`. Any component between biometric-pipeline signing and the HTTP POST (or a compromised/modified build of this exact code path) can substitute a different operator's QR code identifier into the outgoing request while the cryptographically-signed portion (iris data + user id) remains valid and unchanged.

### Impact Explanation
If the backend relies on the presence of a valid secure-element signature as an indicator that the entire signup request (including operator attribution) originated legitimately from the orb hardware, an attacker who can influence the `operator_qr_code` value used at the `signup_post::request` call site (e.g., a modified/rooted orb build, or a defect elsewhere in the pipeline) can misattribute a real, biometrically-verified signup to an operator/distributor who did not actually process it. This is a concrete misattributed-signup impact: the biometric proof is real and valid, but the party credited for it is not authenticated by the signature.

### Likelihood Explanation
Exploitation requires control over the orb-core process between pipeline signing and network submission (not a remote network attacker against TLS), similar to how the vault bug required the vault owner — an already-authorized party — to perform an additional unchecked action (`RekeyTo`). This keeps the difficulty in the same "low-but-real" tier as the original finding: no cryptographic break is needed, only exploitation of an unchecked field.

### Recommendation
Include `operator_qr_code.user_id` (and other request fields intended to be tamper-evident, e.g., `region`) inside the SHA-256 digest signed in `make_signature`, and have the backend verify the signature against the full set of security-relevant fields it receives, not just the iris codes and `user_id`.

### Proof of Concept
1. Orb completes a legitimate biometric capture and pipeline for `user_qr_code` U.
2. `make_signature(&U, &pipeline)` computes a signature over `ORB_ID || U.user_id || iris data`.
3. Before/while `signup_post::request` is invoked, the `operator_qr_code` argument value is swapped from operator A's QR data to operator B's QR data (the signature argument is unaffected since it never included operator data).
4. The resulting multipart request has `distributorId = B`, `signature = <valid signature for U's iris data>`; backend has no way to detect that operator B did not actually run this signup, since the signature does not cover `distributorId`. [1](#0-0) [4](#0-3)

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
