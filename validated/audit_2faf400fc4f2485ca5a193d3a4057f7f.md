### Title
Incorrect decimal scaling via `saturating_sub` in `pallet-hyper-fungible-token` causes unbacked over-minting when a token's EVM decimals are lower than its local decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s cross-chain amount conversion helpers, `convert_to_balance` and `convert_to_erc20`, compute the decimal scaling factor using `erc_decimals.saturating_sub(local_decimals)` (and vice versa). This clamps to zero — i.e. applies **no scaling at all** — whenever the ERC20-side decimals are lower than the local asset's decimals, silently propagating a raw amount from one decimal precision to another as if they were equal. This is the same bug class as the reported PerpDepository issue: code assumes a decimal precision that does not hold, and mints/credits the wrong amount of tokens.

### Finding Description
The two conversion helpers are: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256, erc_decimals: u8, local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value / U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))).to_string();
	dec_str.parse::<B>()
}
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions only handle the case `erc_decimals >= local_decimals` correctly. When `erc_decimals < local_decimals` (a normal, legitimate configuration — e.g. a locally-registered asset with 18 decimals whose remote ERC20 representation uses 6 decimals, similar to how USDC is 6 decimals while many substrate assets are configured at 18), `saturating_sub` returns 0, so the exponent is `10^0 = 1` and **no scaling is applied in either direction**.

This is used directly on the unprivileged, user-reachable `send` extrinsic: [2](#0-1) 

```rust
let amount: u128 = params.amount.into();
let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);

let token_message = Message {
    from: sender.to_vec().into(),
    to: params.recipient.to_vec().into(),
    amount: alloy_primitives::U256::from_be_bytes(erc20_amount.to_big_endian()),
    ...
};
```

`erc_decimals` here is a value that governance previously registered as the correct destination-chain decimals via `register_token`/`update_asset_precision` — it is not attacker-controlled, and using a token with fewer EVM decimals than local decimals is a completely legitimate registration (documented explicitly in the docs: *"e.g. 10-decimal DOT on Polkadot vs 18-decimal DOT on Ethereum"* — the reverse relationship, local > remote, is equally plausible for any USDC-like token). The bug is a pure arithmetic defect in the helper, not a misconfiguration.

The wrongly-computed `erc20_amount` (which equals the raw local-decimal amount, unscaled) is placed into `Message.amount` and dispatched via ISMP `DispatchPost` to the destination `HyperFungibleToken` contract. That contract mints the raw value verbatim with no decimal adjustment of its own: [3](#0-2) 

```solidity
_mint(beneficiary, message.amount);
```

So if `local_decimals = 18` and `erc_decimals = 6`, a user sending `1000 * 10^18` raw units (1000 tokens) causes `message.amount = 1000 * 10^18` to be minted on the EVM side instead of the correct `1000 * 10^6`, an over-mint by a factor of `10^12` — unbacked tokens are created on the destination chain relative to what was locked/burned on the source chain.

The same flaw exists symmetrically in `convert_to_balance`, used in `on_accept`/`on_timeout` on the Substrate side: [4](#0-3) 

meaning inbound EVM→Substrate transfers where `erc_decimals < local_decimals` would credit the beneficiary an unscaled (too-small, by the same 10^N factor) local balance, permanently freezing/losing the difference relative to what was burned/escrowed on the EVM side.

### Impact Explanation
This directly matches the "unbacked mint" / "permanent freezing of funds" criteria: depending on transfer direction, either
1. `send()` (Substrate → EVM) results in unbacked over-minting on the destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract (inflation of that token's supply, draining any pooled liquidity or backing), or
2. an inbound `on_accept`/`on_timeout` (EVM → Substrate) credits the beneficiary far less than what was locked/burned upstream, permanently freezing the difference in the corresponding escrow/burn accounting.

Both are High severity: they compromise the 1:1 backing invariant that HyperFungibleToken/WrappedHyperFungibleToken depend on for security.

### Likelihood Explanation
Triggering the bug requires no special privilege beyond a single `send()` call by any signed account, once a token is registered (by governance/`CreateOrigin`, as normal, non-malicious operation) with EVM decimals lower than its local decimals — a realistic and common configuration for tokens like USDC (6 decimals) bridged from higher-decimal substrate assets. No malicious admin, governance, or collator action is needed; only a standard/legitimate precision configuration plus a normal user transfer.

### Recommendation
Replace `saturating_sub` with signed decimal-difference handling that scales in both directions, e.g.:
```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and the mirrored fix for `convert_to_balance`. Add test coverage for the `erc_decimals < local_decimals` case (currently untested — existing tests only exercise `erc_decimals(18) > local_decimals(10/12)`).

### Proof of Concept
1. Governance registers asset `X` locally with 18 decimals (`pallet-assets` `decimals() = 18`) and registers its EVM counterpart contract with `Precisions::<T>::insert(X, dest_chain, 6)` (a 6-decimal ERC20/HyperFungibleToken deployment, e.g. USDC-style).
2. A user calls `send(SendParams { asset_id: X, amount: 1000 * 10^18, destination: dest_chain, ... })`.
3. In `send()`: `erc_decimals = 6`, `decimals = 18`, `erc20_amount = convert_to_erc20(1000 * 10^18, 6, 18)` → exponent `= 6u8.saturating_sub(18) = 0` → `erc20_amount = 1000 * 10^18` (unchanged, should have been `1000 * 10^6`).
4. `Message.amount = 1000 * 10^18` is ABI-encoded and dispatched via ISMP `DispatchPost` to the destination `HyperFungibleToken` contract.
5. On delivery, `HyperFungibleToken.onAccept` calls `_mint(beneficiary, 1000 * 10^18)`, minting `10^12` times more tokens than the `1000` units of asset `X` (with true 6-decimal precision) that were actually locked/burned on the source chain — an unbacked mint of the bridged representation.
