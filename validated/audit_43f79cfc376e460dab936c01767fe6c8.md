### Title
Withdraw discards the post-withdraw solvency check result, allowing payout without valid collateral status - (File: contracts/controller/src/positions/supply.rs)

### Summary
The Aimeos advisory class is "product delivered without verifying payment succeeded". In XOXNO Lending the analogous shape is `process_withdraw`: it pays tokens out of the pool first and then *calls* the post-withdraw solvency enforcement but explicitly discards its return value with `let _ =`, so a failed solvency outcome does not revert the payout.

### Finding Description
In `process_withdraw` (contracts/controller/src/positions/supply.rs:140-168), the flow is:

```rust
let paid = settle_withdraw(env, &mut account, &recipient, &aggregated, &mut cache);
let _ = enforce_post_pool_solvency(env, &mut cache, &mut account);
```

`settle_withdraw` has already executed `apply_withdraw_batch`, which transfers underlying tokens from the pool to `recipient` (an arbitrary `to` address controlled by the caller, only required to not be pool/controller per `require_external_recipient`). The solvency guard `enforce_post_pool_solvency` is invoked *after* the transfer and its result is bound to `_` and never inspected. The `let _ =` idiom is only meaningful if the function returns a value (e.g. `Result`/`bool`); if it simply panicked on failure the binding would be redundant. Discarding the result means that whatever status the enforcement computes — including an account left below the required collateralization/health threshold — cannot affect the outcome: the tokens are already out and the transaction commits via `finalize_position_flow`.

This is the direct analog of "digital download delivered without checking that payment succeeded": value (pool cash) is released before/without honoring the success status of the mandatory post-condition check.

### Impact Explanation
An unprivileged owner/delegate can call `withdraw(account_id, withdrawals, to)` withdrawing supply that is needed to back open borrows. If `enforce_post_pool_solvency` returning a failure status is ignored, the caller extracts collateral that should have been blocked, leaving the account undercollateralized. That is theft of pool funds / protocol insolvency: the bad debt left behind must later be absorbed via `clean_bad_debt` supply-index write-downs at other suppliers' expense.

### Likelihood Explanation
Reachable by any account owner or delegate through the public `withdraw` entrypoint with chosen amounts and recipient. It requires only that `enforce_post_pool_solvency` signals failure via its return value rather than by panicking — which is precisely what the `let _ =` pattern implies (panics need no result binding). No privileged role, oracle manipulation, or exotic path is required.

### Recommendation
Propagate the result: change `let _ = enforce_post_pool_solvency(...)` to `enforce_post_pool_solvency(...)?` / unwrap-and-panic so a failed solvency check reverts the transaction before `finalize_position_flow` commits, or restructure so solvency is enforced prior to the token transfer.

### Proof of Concept
1. Supply collateral, borrow near the account's max LTV.
2. Call `withdraw` requesting enough collateral to push the health factor below 1, with `to` = attacker's external address.
3. `settle_withdraw` transfers the tokens out; `enforce_post_pool_solvency` computes a failing status that is discarded via `let _ =`; the transaction commits.
4. Account is left undercollateralized; attacker keeps the withdrawn collateral, leaving bad debt for suppliers.

Caveat: this conclusion depends on `enforce_post_pool_solvency` returning its verdict rather than panicking internally; I was unable to read its body in `positions/debt.rs` within the available iterations to confirm. If it panics on failure and returns `()`, the `let _ =` is harmless style and no vulnerability exists.
