### Title
Webhook shop/topic attribution is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before invoking the app's handler, but the HMAC it validates only covers the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values — which are extracted from unauthenticated HTTP headers and handed to the app's handler as trusted identifiers — are never included in the signed payload. This breaks the identity binding `hmac_signed_bytes == bytes_the_handler_trusts_as_shop_identity`, exactly the class of bug described in the external report (a value used by downstream logic that isn't covered by the authentication check).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC purely over that `to_signable_string` value: [2](#0-1) 

`Registry.process` treats a passing HMAC check as proof of the whole request's integrity, then constructs `WebhookMetadata` straight from unauthenticated headers (`request.shop`, `request.topic`, `request.webhook_id`, `request.api_version`) and hands it to the app's handler: [3](#0-2) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read from `shopify-*` / `x-shopify-*` HTTP headers, none of which participate in `to_signable_string`: [4](#0-3) 

The gem's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole envelope (including shop attribution) is authenticated: [5](#0-4) 

In reality only the body bytes are authenticated. Because a single app's `api_secret_key` is shared across every merchant that installs the app, any attacker who is themselves a legitimate merchant of the app (or who otherwise obtains one valid `(body, hmac)` pair from a real webhook delivery) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers with arbitrary attacker-chosen values. `HmacValidator.validate` will still pass (it only checks the body), and `Registry.process` will call the handler with `data.shop` set to the attacker-chosen value, `data.topic` to whatever handler is desired, while `data.body` contains content the attacker fully controls the shape of (their own store's real webhook payload).

This is the same bug class as the reported issue: a value trusted and acted upon by downstream logic (the proposal's "staked" tally / here the webhook's shop identity) is not actually covered by the binding check (HMAC) that is supposed to make the value trustworthy.

### Impact Explanation
An app that keys any per-tenant state off `data.shop` (nearly universal — e.g., "look up this shop's local DB record and update it based on the webhook body") can be made to write or act on data attributed to a victim shop using a payload/topic controlled by the attacker's own shop. This is a cross-tenant integrity/confusion issue: the attacker cannot forge content for a topic they've never received (they still need a legitimately-received valid `(body, hmac)` for some topic), but they can freely relabel the `shop`, `topic`, and `webhook_id` of that valid pair, causing the host application to process attacker-supplied webhook content under another tenant's identity. This crosses the tenant-isolation boundary the gem is relied upon to enforce for webhook processing.

### Likelihood Explanation
Exploitation requires the attacker to have legitimately installed the target app on at least one shop (to receive a genuinely HMAC-valid webhook), which is trivial for any public app since anyone can install it on their own development/test store. The webhook endpoint is by design internet-reachable and unauthenticated aside from the HMAC check, so replaying a captured request with modified headers is straightforward (no secret material needed).

### Recommendation
Bind the identity/routing fields into the signed payload verification, e.g., by requiring the caller to supply the expected `shop` (and ideally `topic`/`webhook_id`) out-of-band (matched against the currently active session or a registration-time expectation) and rejecting the request if the header-derived value doesn't match, rather than trusting header values by construction after a body-only HMAC check. At minimum, update `Registry.process`/`Request` so the shop domain is cross-checked against a known/authorized value before being handed to the handler, and correct the documentation so integrators know they must not treat `data.shop` as authenticated purely because `process` succeeded.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets Shopify deliver a real webhook, e.g. `orders/create`, capturing the raw body `B` and the valid header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` with the app's shared `client_secret`).
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with:
   - body: `B` (unchanged, so HMAC still validates)
   - `x-shopify-hmac-sha256: H` (unchanged, valid)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (spoofed)
   - `x-shopify-topic: orders/create` (unchanged, or spoofed to another registered topic if desired)
3. `ShopifyAPI::Webhooks::Registry.process` runs `Utils::HmacValidator.validate(request)`, which only checks `H` against `B`, and passes.
4. The handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"` and `body == B` (attacker-controlled content from their own store), causing the host application to process attacker-supplied data as if it belonged to `victim-shop.myshopify.com`.
