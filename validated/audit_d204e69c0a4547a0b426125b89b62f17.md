### Title
Unbounded RSA key size in CertificateSigningRequest allows CPU-exhaustion DoS during signature verification - (File: pkg/apis/certificates/validation/validation.go)

### Summary
The legacy/stable `CertificateSigningRequest` API (`certificates.k8s.io`) accepts an arbitrary PKCS#10 CSR blob in `spec.request` and validates it by decoding the PEM/DER and calling `csr.CheckSignature()`, with no restriction on the size of the embedded public key. This mirrors the CVE-2023-39533 bug class exactly: an attacker-supplied oversized RSA key forces the receiving process to spend disproportionate CPU time performing signature verification.

### Finding Description
`validateCertificateSigningRequest` calls `validateCSR(csr)`, which parses `csr.Spec.Request` via `certificates.ParseCSR` and then calls `csr.CheckSignature()` (Go's `x509.CertificateRequest.CheckSignature`, which internally performs RSA signature verification using the key embedded in the CSR itself): [1](#0-0) [2](#0-1) 

Unlike the newer `PodCertificateRequest` API, which explicitly bounds RSA keys to 3072 or 4096 bits before doing any signature verification: [3](#0-2) [4](#0-3) 

...the `CertificateSigningRequest` validation path has no analogous key-size check. `validateCertificateSigningRequest` only checks usages, signer name, expiration seconds, and conditions, and unconditionally calls `validateCSR` regardless of the modulus size of any RSA key embedded in the CSR: [5](#0-4) 

This validation runs on every `CertificateSigningRequest` create request handled by kube-apiserver, i.e., on the hot path of an ordinary authenticated user's API request (any principal with RBAC permission to `create certificatesigningrequests`, which is broadly granted by default via roles such as `system:node-bootstrapper` and various `system:certificates.k8s.io:*` roles, and often by cluster operators to additional groups for cert rotation workflows).

### Impact Explanation
An authenticated principal with `create` permission on `certificatesigningrequests` can submit a CSR embedding an extremely large RSA public key (e.g., tens of thousands of bits, which is a tiny DER payload of only a few KB — well under etcd/object size limits). Each time kube-apiserver validates that object (on create, and again on any update path that revalidates the CSR, e.g. `ValidateCertificateSigningRequestUpdate`), it performs RSA signature verification against that oversized key. Because RSA verification cost scales superlinearly with modulus size, a handful of concurrently submitted CSRs with sufficiently large keys can consume disproportionate CPU on kube-apiserver, degrading availability for all API consumers — the same "resource exhaustion via large RSA keys" primitive described in the go-libp2p advisory (CVE-2023-39533).

### Likelihood Explanation
Moderate-to-high: the `certificatesigningrequests` resource is reachable by many principals in typical clusters (kubelet bootstrap tokens, CI/CD service accounts doing cert rotation, or any RBAC binding granting create on this resource), and crafting a CSR with an oversized RSA key requires no special privilege beyond that create permission — no admission webhook or built-in kube-apiserver check currently bounds the key size.

### Recommendation
Add an explicit RSA (and other asymmetric key) modulus/size bound check in `validateCSR`/`validateCertificateSigningRequest` before calling `csr.CheckSignature()`, consistent with the bound already enforced for `PodCertificateRequest` (`pub.Size()*8` checked against an allowed set such as 2048–4096 bits), and reject CSRs whose embedded public key exceeds the bound with a `field.Invalid` error prior to performing any expensive cryptographic verification.

### Proof of Concept
1. As a principal holding `create` permission on `certificatesigningrequests` (e.g., a bound `system:node-bootstrapper`-equivalent role), generate an RSA private key with a very large modulus (e.g., 32768 or 65536 bits).
2. Build a PKCS#10 CSR using that key (self-signed, no special validation needed on subject/SANs) and base64/PEM-encode it into `spec.request`.
3. Submit repeated/concurrent `CertificateSigningRequest` create calls with this payload; kube-apiserver will invoke `validateCSR` → `csr.CheckSignature()` on each request, consuming excessive CPU per validation and degrading kube-apiserver responsiveness under modest request volume.

Note: I was not able to independently execute this PoC or measure actual CPU cost in this environment (no code execution available in ask-only mode); the finding is based on static analysis of the validation code path and direct comparison to the already-mitigated `PodCertificateRequest` path in the same file.

// validateCSR validates the signature and formatting of a base64-wrapped,
// PEM-encoded PKCS#10 certificate signing request. If this is invalid, we must
// not accept the CSR for further processing.
func validateCSR(obj *certificates.CertificateSigningRequest) error {
	csr, err := certificates.ParseCSR(obj.Spec.Request)
	if err != nil {
		return err
	}
	// check that the signature is valid
	return csr.CheckSignature()
}

func validateCertificateSigningRequest(csr *certificates.CertificateSigningRequest, opts certificateValidationOptions) field.ErrorList {
	isNamespaced := false
	allErrs := apivalidation.ValidateObjectMeta(&csr.ObjectMeta, isNamespaced, ValidateCertificateRequestName, field.NewPath("metadata"))

	specPath := field.NewPath("spec")
	err := validateCSR(csr)
	if err != nil {
		allErrs = append(allErrs, field.Invalid(specPath.Child("request"), csr.Spec.Request, fmt.Sprintf("%v", err)))
	}
	if len(csr.Spec.Usages) == 0 {
		allErrs = append(allErrs, field.Required(specPath.Child("usages"), ""))
	}
	if !opts.allowUnknownUsages {
		for i, usage := range csr.Spec.Usages {
			if !allValidUsages.Has(string(usage)) {
				allErrs = append(allErrs, field.NotSupported(specPath.Child("usages").Index(i), usage, allValidUsages.List()))
			}
		}
	}
	if !opts.allowDuplicateUsages {
		seen := make(map[certificates.KeyUsage]bool, len(csr.Spec.Usages))
		for i, usage := range csr.Spec.Usages {
			if seen[usage] {
				allErrs = append(allErrs, field.Duplicate(specPath.Child("usages").Index(i), usage))
			}
			seen[usage] = true
		}
	}
	if !opts.allowLegacySignerName && csr.Spec.SignerName == certificates.LegacyUnknownSignerName {
		allErrs = append(allErrs, field.Invalid(specPath.Child("signerName"), csr.Spec.SignerName, "the legacy signerName is not allowed via this API version"))
	} else {
		allErrs = append(allErrs, apivalidation.ValidateSignerName(specPath.Child("signerName"), csr.Spec.SignerName)...)
	}
	if csr.Spec.ExpirationSeconds != nil && *csr.Spec.ExpirationSeconds < 600 {
		allErrs = append(allErrs, field.Invalid(specPath.Child("expirationSeconds"), *csr.Spec.ExpirationSeconds, "may not specify a duration less than 600 seconds (10 minutes)"))
	}
	allErrs = append(allErrs, validateConditions(field.NewPath("status", "conditions"), csr, opts)...)

	if !opts.allowArbitraryCertificate {
		if err := validateCertificate(csr.Status.Certificate); err != nil {
			allErrs = append(allErrs, field.Invalid(field.NewPath("status", "certificate"), "<certificate data>", err.Error()))
		}
	}

	return allErrs
}
