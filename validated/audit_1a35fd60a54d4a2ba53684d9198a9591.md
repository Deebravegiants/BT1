### Title
Webhook shop/topic identity is not bound to the HMAC, allowing forged shop attribution on replayed webhook bodies - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw JSON body against the `X-Shopify-Hmac-Sha256` header. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers used to build `WebhookMetadata` handed to the app's handler are never part of the signed material.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` [4](#0-3) . For webhooks, `to_signable_string` is defined as just `@raw_body` [1](#0-0) . The `shop` accessor used downstream is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header [5](#0-4) , which is not fed into the HMAC at all.

`Registry.process` raises only if the body-HMAC fails, then immediately trusts `request.shop` and `request.topic` (sourced purely from headers) to select the registered handler and build the `WebhookMetadata` struct passed to the app: [3](#0-2) .

The identity binding this breaks, expressed as an equality that should hold but doesn't:
`shop_bound_by_HMAC == shop_used_by_handler`

Before request: an attacker holding one legitimately-Shopify-signed webhook delivery for their own shop has `(raw_body, hmac)` that are cryptographically valid, and `shop-domain = attacker-shop.myshopify.com` in the header (unsigned).
After the attacker's replay with a modified `shop-domain` header but the same `raw_body`/`hmac`: `HmacValidator.validate` still returns `true` (because it only checks `raw_body` against `hmac`), yet `request.shop` now returns an arbitrary attacker-chosen shop domain, e.g. `victim-shop.myshopify.com`. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` for content that was never actually generated for that shop.

### Impact Explanation
If a host application uses `data.shop` from the webhook handler to scope tenant data operations (a documented, expected usage pattern shown in this gem's own docs, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [6](#0-5) , an attacker who can obtain one genuinely-signed webhook body (e.g. from their own installed/trial shop) can relabel it to any victim shop domain and have the host process it as if it originated from the victim tenant. Depending on the topic (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, order/customer webhooks), this is a cross-tenant data-integrity/confusion vector — the gem itself provides no protection binding the claimed shop identity to the cryptographic proof, despite documenting `shop` as a trusted field of the verified payload.

### Likelihood Explanation
This requires the attacker to possess at least one validly-signed webhook body/HMAC pair for some shop under the same app (e.g. by installing the app on a shop they control, which is a realistic "unprivileged internet user" position relative to a multi-tenant app), then send a raw HTTP POST with edited headers to the app's own webhook endpoint. No access token, `client_secret`, or privileged account is required — everything needed (raw_body + hmac) is delivered to them legitimately over the wire.

### Recommendation
Include the `shop-domain` (and ideally `topic`) header values in the HMAC-signed material, or otherwise cryptographically bind the shop identity to the payload (e.g., look up the expected shop for a webhook subscription server-side, rather than trusting the header at face value) before constructing `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate `orders/create` webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = H` (valid HMAC of `B` with the app's `client_secret`), header `x-shopify-shop-domain = attacker-shop.myshopify.com`.
2. Attacker POSTs to the app's webhook endpoint with the same `raw_body = B` and `x-shopify-hmac-sha256 = H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H` [7](#0-6) .
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is built with `shop = "victim-shop.myshopify.com"` and passed to the app's handler [8](#0-7) , causing the app to process attacker-controlled data as belonging to the victim tenant.
