This confirms the vulnerability. The `HmacValidator.validate` only signs `request.to_signable_string`, which for `ShopifyAPI::Webhooks::Request` returns just `@raw_body` [1](#0-0) . The `shop` value used downstream comes from the `shopify-shop-domain` header, read independently of the HMAC computation [2](#0-1) . `Registry.process` validates the HMAC over the body only, then passes `request.shop` (the unauthenticated header) straight into the tenant-identifying `WebhookMetadata` handed to the app's handler [3](#0-2) .

### Title
Webhook `shop` domain is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body [4](#0-3) . The `shop` identifier that the gem hands to the host application's webhook handler, however, is read straight from the `x-shopify-shop-domain` HTTP header and is never included in the signed payload [2](#0-1) [1](#0-0) . This breaks the intended identity binding: `hmac_verified_bytes == raw_body` while the tenant-identifying field consumed by the app (`shop`) is a separate, unauthenticated header value.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it against the `hmac` field [5](#0-4) . For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) , so the signature proves only that the *body bytes* were produced with the shop's secret — it says nothing about which shop domain header accompanied that body. `Registry.process` then builds `WebhookMetadata` using `request.shop`, taken from the header, and passes it to the app's registered handler as the tenant identifier [6](#0-5) .

Because Shopify signs each webhook per-shop using that shop's own `client_secret` (or the app's shared secret in the case of multiple stores sharing an app config), and because the signature never binds the `shop-domain` header, a party who can legitimately receive webhook deliveries for one shop (e.g., an attacker who installs the app on their own store, a low-privilege actor with access to their own store's outgoing webhook traffic, or anyone who can intercept/replay an HTTP request reaching the app's public webhook endpoint) can take a validly-signed request and swap in a different `x-shopify-shop-domain` header value. The HMAC check in `Registry.process` still passes because it only re-hashes `@raw_body`, and the app's handler receives an attacker-chosen `shop` value alongside data actually authenticated only for the original body.

This is exactly the "field acted on but not covered by the HMAC" analog: the equality the gem is supposed to enforce is `authenticated_shop == shop_used_by_handler`, but the actual behavior enforces only `authenticated_bytes(raw_body) == raw_body`, leaving `shop_used_by_handler` completely outside the cryptographic binding.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (returned by `Registry.process`) as a tenant/session key — for example to look up which merchant's `Session`/access token to act on, or to decide which store's data a webhook payload applies to — can be tricked into associating one shop's signed webhook body with another shop's identity. Combined with a body that is otherwise attacker-influenceable within the sending shop's control (e.g. `orders/create`, `customers/data_request`, or app-defined webhook topics with attacker-controllable field values from the sender's own shop), this allows cross-tenant confusion: data intended for or originating from Shop A's webhook is processed by the host app as if it belonged to Shop B. This matches the Critical "cross-tenant access" impact bucket, since the trust boundary between tenants is broken purely through the gem's own webhook verification logic.

### Likelihood Explanation
Exploitation requires only the ability to deliver an HTTP POST to the app's public webhook endpoint with a valid HMAC for *some* shop (trivially obtainable by installing the app on an attacker-controlled development/trial store and capturing its own legitimately-signed webhook deliveries) and then modifying the `shop-domain` header before replaying it. No access token, `client_secret`, or privileged account is needed beyond operating an ordinary (even free/trial) shop that can install the app — squarely within the "unprivileged internet user" threat model.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) as part of the signed material verified against the HMAC, or otherwise cryptographically bind the header value to the signature before it is exposed to the application (e.g., re-verify that `x-shopify-shop-domain` matches an expected/allow-listed shop associated with the session that originally registered the webhook, rather than trusting the header verbatim). At minimum, document that host applications must independently verify `WebhookMetadata#shop` against their own known-shop registry rather than treating it as authenticated by `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com` and trigger any webhook topic the app subscribes to, capturing the raw HTTP request Shopify sends, including its `x-shopify-hmac-sha256` header (valid for `attacker.myshopify.com`'s body).
2. Replay that exact request to the app's public webhook endpoint, but replace the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`@raw_body` only) [1](#0-0)  — unaffected by the header change — so validation succeeds.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"` [6](#0-5)  and passed to the app's handler, which processes attacker-supplied body content under the victim shop's identity.
