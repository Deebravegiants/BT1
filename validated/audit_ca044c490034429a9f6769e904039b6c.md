### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook replay/spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the HMAC computed by Shopify signs only that raw body as well. The `shop-domain`, `topic`, and `webhook-id` headers — which `ShopifyAPI::Webhooks::Registry.process` uses to identify the tenant and dispatch the payload to the handler — are never part of the signed data. This breaks the identity binding `authenticated bytes == bytes acted upon`: the HMAC authenticates the body only, but the gem trusts the (unauthenticated) `shop` header as the tenant identifier and the `topic`/`webhook_id` headers to route/dedupe the event.

### Finding Description
`Webhooks::Request` extracts the shop, topic, and webhook id purely from HTTP headers: [1](#0-0) 

Note that `to_signable_string` (used for HMAC verification) returns only `@raw_body` — none of the identity-bearing headers (`shop`, `topic`, `webhook_id`, `api_version`) are included in the signed string.

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string`: [2](#0-1) 

`Webhooks::Registry.process` validates only this body-only HMAC, and then unconditionally trusts the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` object passed to the app's handler: [3](#0-2) 

Since a given app's webhooks share one `api_secret_key` across every installed shop, any merchant that installs the app on their own store can trigger a legitimately-signed webhook delivery for a chosen topic and body (they control resource creation/timing, and many topics allow attacker-influenced body content such as `metafields` values or custom resource titles). Because the HMAC signs only the body, that same `(raw_body, hmac)` pair remains valid when replayed to the app's webhook endpoint with a different `x-shopify-shop-domain` (or `x-shopify-topic` / `x-shopify-webhook-id`) header — the signature check still passes because those headers were never part of the signed content. The app's handler (as documented) trusts `data.shop` to identify which tenant's data the webhook is about: [4](#0-3) 

This lets an attacker (an unprivileged internet user who merely has access to their own shop's webhook deliveries) forge webhooks appearing to originate from a victim shop, or relabel one topic's payload as another topic, entirely from outside the trust boundary the HMAC is supposed to establish.

### Impact Explanation
This is a Critical-class cross-tenant issue: it lets an attacker impersonate another merchant's webhook traffic to the host application, bypassing the tenant-identity guarantee that the HMAC signature is meant to provide. Depending on how the host app consumes `data.shop`/`data.topic` (e.g., to update per-shop billing state, mark app-uninstall/GDPR redaction, or trigger shop-scoped side effects), this enables cross-tenant data corruption or spoofed lifecycle events without any credential theft — only knowledge of the app's public webhook endpoint and control of one's own shop's webhook stream.

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation requires only an app installation the attacker already controls (no secrets, tokens, or privileged access needed) and the ability to capture one raw webhook body/HMAC pair emitted for their own shop, then replay it with modified headers to the app's public webhook callback URL. No cryptographic material needs to be known to the attacker.

### Recommendation
Bind the tenant/topic identity to the HMAC verification: include `shop`, `topic`, and `webhook_id` (in addition to the raw body) in the string that `Webhooks::Request#to_signable_string` produces for HMAC purposes, or otherwise cryptographically bind these header values before they're trusted for dispatch. At minimum, document/require host apps to independently verify `data.shop` against a known/installed-shop list rather than trusting it as authenticated.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com`, receiving legitimate webhook deliveries signed with the app's shared `api_secret_key`.
2. Attacker captures a delivered webhook's raw body and its `X-Shopify-Hmac-Sha256` value (valid per `HmacValidator.validate`, since it signs only the body — see `lib/shopify_api/utils/hmac_validator.rb`).
3. Attacker replays a POST to the app's webhook endpoint with the same raw body and HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) validates the HMAC successfully (it only checks the body) and calls the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", topic: <attacker-chosen>, ...)`, causing the host app to act on forged tenant/topic data.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
