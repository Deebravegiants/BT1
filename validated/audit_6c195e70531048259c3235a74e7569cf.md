### Title
Unvalidated swap routes can hide unauthorized wallet transfers in the caller's authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller swap strategies accept an opaque `swap` payload and forward it to the configured router without constraining the contracts reachable through the route. A malicious venue contract invoked by that route can request an unrelated token transfer from the caller. Soroban simulation records that transfer as a child of the caller's strategy authorization, so signing the simulated tree authorizes theft of wallet assets unrelated to the lending swap. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_collateral` accepts caller-supplied `swap` bytes, authenticates only that the caller owns or delegates the account, and validates the source and destination markets. It does not decode or constrain the route itself. [3](#0-2) [4](#0-3) 

`swap_tokens` authorizes only the controller's exact input-token transfer to the configured router, then calls `execute_strategy` with the opaque payload. The subsequent checks measure only the controller's input balance, output balance, overspending, and positive output. They do not detect an unrelated transfer from the caller performed by a contract reached through the route. [5](#0-4) 

The repository's threat model states that route payloads can name arbitrary pool and token addresses and that third-party code can execute below the caller's authorization. It further states that such code can add a wallet-token transfer to the caller's simulated authorization tree and that neither route minimums nor final risk checks bound that loss. [6](#0-5) 

### Impact Explanation
A malicious route can steal arbitrary spendable wallet assets from a user who signs the poisoned authorization tree. The stolen asset does not need to be the swap input, collateral asset, debt asset, or a protocol-listed token. [7](#0-6) 

The protocol-level checks still pass because the route can return a fair swap output and leave the lending position healthy. The loss therefore bypasses the controller's measured-output and solvency checks and is bounded by the victim's wallet balances rather than the routed amount. [8](#0-7) [6](#0-5) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue and distribute the crafted route through a quoting interface, phishing flow, compromised route source, or manipulated swap request. Exploitation requires the victim to sign the expanded authorization tree, so it has the user-interaction characteristics and medium severity of the reference bug class. [9](#0-8) [10](#0-9) 

### Recommendation
Use a structured route format and enforce an allowlist of approved venue contracts or pool deployments before execution. Reject routes containing arbitrary contract addresses, and make the router capable of executing only calls that cannot introduce caller-scoped authorization requirements beyond the declared input transfer. Clients should additionally reject any authorization tree containing unexpected child invocations.

At a minimum, the controller and router interface should make the allowed authorization tree explicit: one controller input transfer for controller strategies and one sender input transfer for direct router swaps. Any venue requiring additional caller authorization should fail closed.

### Proof of Concept
The included scenario uses a router reachable by `execute_strategy` that decodes a route and invokes the route-supplied `hop_pool`; the malicious pool then calls `wallet_token.transfer(victim, attacker, amount)`. [11](#0-10) [12](#0-11) 

When Alice invokes `swap_collateral` with that route, simulation records the unrelated wallet-token transfer beneath her `swap_collateral` authorization. The transfer executes once that tree is signed, reducing Alice's unrelated wallet balance to zero and crediting the attacker while the strategy still receives its expected output. [2](#0-1)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
