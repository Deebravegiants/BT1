### Title
OAuth token-exchange request host is built from an unvalidated `shop` value, allowing `client_secret` exfiltration to an attacker-controlled host - (File: lib/shopify_api/auth/oauth.rb, lib/shopify_api/clients/http_client.rb)

### Summary
`Oauth.validate_auth_callback` builds a `null_session` from `auth_query.shop` and passes it to `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")` to POST the app's `client_id`/`client_secret`/authorization `code` to exchange for an access token. [1](#0-0) 
`HttpClient#initialize` derives the request's destination host directly from `session.shop` with no domain trust check performed inside the client itself. [2](#0-1) 

### Finding Description
The gem does provide a domain allow-list, `Utils::ShopValidator`/`TRUSTED_SHOPIFY_DOMAINS`, meant to bind the `shop` value to a legitimate Shopify domain before it's used for anything sensitive. [3](#0-2) 
However, `Auth::Oauth.validate_auth_callback` never calls `ShopValidator.sanitize!`/`sanitize_shop_domain` on `auth_query.shop` before using it to construct the `null_session` that determines the token-exchange request's target host. [4](#0-3) 
The HMAC check (`Utils::HmacValidator.validate(auth_query)`) only proves the query bytes were signed by *a* holder of `api_secret_key` (i.e., Shopify) for the *exact* `shop`/`code`/`state`/`host`/`timestamp` tuple presented — it does not independently constrain `shop` to be a `*.myshopify.com` (or other trusted) domain. The equality that should hold is:
`request_destination_host == trusted_shopify_domain(shop)`,
but what is actually enforced is only:
`hmac(shop, code, host, state, timestamp) == valid_signature`.
Because Shopify's own OAuth redirect always supplies a legitimate `shop`, this is not exploitable through the normal flow. But this is a library-level gap: `HttpClient`, the low-level primitive reused for the access-token exchange, trusts `session.shop` as a raw hostname with no defensive validation, and `validate_auth_callback` does not call `ShopValidator` at all in this path (compare with the webhook `Request#shop`, which is also unvalidated by `ShopValidator` before being handed off in `WebhookMetadata`). [5](#0-4) 

### Impact Explanation
If any code path can influence `auth_query.shop` (or more generally, any `Session#shop` fed into `HttpClient`) without going through `ShopValidator`, an attacker-controlled hostname would receive the POST containing `client_id`, `client_secret`, and the authorization `code` — a Critical-severity theft of the app's `client_secret` and authorization code (usable for full account/tenant impersonation). This matches the report's "host validated versus the host that receives the access token / client_secret" identity-binding pattern.

### Likelihood Explanation
Exploitability strictly depends on whether the host application (or a future library code path) passes `shop` into `Session`/`HttpClient` without first running it through `ShopValidator.sanitize!`. In the current `validate_auth_callback` flow, `shop` originates from the OAuth callback query which is itself HMAC-signed by Shopify, so under normal operation the value is trustworthy at the point it reaches `HttpClient`. I could not find, within the in-scope `lib/shopify_api/**` code (excluding generated REST resources), any reachable path where an unprivileged internet user can supply an arbitrary `shop` string that reaches `HttpClient` without HMAC/JWT verification already binding it to a real Shopify-issued value. The gap is therefore a defense-in-depth omission at the `HttpClient`/`validate_auth_callback` layer rather than a demonstrated end-to-end bypass reachable purely from unauthenticated attacker input.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` before constructing `null_session` in `Oauth.validate_auth_callback`, and consider adding the same validation inside `HttpClient#initialize` (or `Auth::Session`) as a defense-in-depth measure so that any future caller cannot construct a request host from an unvalidated `shop` string.

### Proof of Concept
Could not be constructed as a concrete unauthenticated exploit: every reachable entry point into `HttpClient` with `session.shop` in this repo (`Oauth.validate_auth_callback`, `TokenExchange.exchange_token`) obtains `shop` only from HMAC-verified (`AuthQuery`) or JWT-verified (`JwtPayload#dest`, checked against `Context.api_key` as `aud`) data, both of which are cryptographically bound to Shopify. No proof-of-concept payload demonstrates an actual host-confusion bypass with today's code; this is reported as a structural/defense-in-depth gap rather than a proven Critical/High finding.
