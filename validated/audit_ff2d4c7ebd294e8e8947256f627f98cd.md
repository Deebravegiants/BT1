### Title
Webhook `shop-domain` (and `topic`/`webhook_id`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never included in the HMAC computation. `Utils::HmacValidator.validate` therefore only proves that the *body* was signed by Shopify with the app's secret — it proves nothing about which shop, topic, or webhook the signature was originally issued for. `Registry.process` then trusts the unverified `request.shop` value and hands it straight to the app's handler as the tenant identifier.

### Finding Description
The identity binding that should hold is: `shop header == shop the HMAC was actually issued for`. Instead, the gem only checks `HMAC(raw_body, secret) == received_hmac`: [1](#0-0) [2](#0-1) 

```ruby
sig { override.returns(String) }
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

`to_signable_string` is what gets hashed: [3](#0-2) 

```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
```

Since only `@raw_body` is signed, the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are entirely outside the cryptographic proof. `Registry.process` still uses the unverified `request.shop` as the tenant identity passed to the app's handler: [4](#0-3) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

Because a single app-level secret is shared across every shop that installs the app, any tenant of the app — including a low-privilege attacker who installs the app on their own store and thus legitimately receives correctly-signed webhooks addressed to their own shop — can capture one of their own `(raw_body, hmac)` pairs and resend it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop. `HmacValidator.validate` will still succeed because the signed bytes (`raw_body`) are untouched; only the unsigned header changed. The library then reports this attacker-controlled payload to the host application as if it were genuinely sent for the victim's shop.

### Impact Explanation
This breaks the equality `shop authenticated by the HMAC == shop the payload is attributed to`, which is exactly the identity-binding failure category called out in the rules (shop authenticated vs. shop used downstream; field acted on but not covered by HMAC). Any application that uses `WebhookMetadata#shop` (as documented/intended) to select the tenant/session context for processing the webhook body is exposed to cross-tenant data injection — an attacker can make the app process attacker-chosen payload content under a victim shop's identity, since the gem hands the host application data it fraudulently labels as "verified."

### Likelihood Explanation
Requires only: (1) the attacker be a normal, unprivileged user who can install the target app on their own (even free/dev) store — a standard, low-barrier action — and (2) the ability to send an HTTP POST to the app's public webhook endpoint with modified headers, which is trivial. No access token, `client_secret`, or privileged account is required; the attacker never needs to compute or know the actual signing secret.

### Recommendation
Include the identity fields that the application relies on (at minimum `shop-domain`, and ideally `topic`/`webhook_id`) in the signed payload used for HMAC verification, or independently bind/verify the `shop-domain` header against an out-of-band trusted source (e.g., cross-check against the registration's expected shop for that endpoint/session) before passing it to the handler as trusted `WebhookMetadata`. Document clearly that `WebhookMetadata#shop` is derived from an unauthenticated header and must not be used alone as a tenant boundary unless it is bound into the signature.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g. `orders/create`).
2. Shopify sends the app a legitimately signed webhook:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC(raw_body, api_secret_key)>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id": 1, "note": "<attacker controlled content>"}
   ```
3. Attacker captures this exact `(raw_body, X-Shopify-Hmac-Sha256)` pair (it was addressed to their own server/app instance, so this is trivially observable).
4. Attacker replays the identical body and HMAC header to the app's webhook endpoint, only changing:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes HMAC over `@raw_body` only — identical to step 2 — so validation passes.
6. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's original body>, ...)`, causing the app to process attacker-controlled data under the victim's tenant identity.
