### Title
Webhook shop identity (`X-Shopify-Shop-Domain`) is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Utils::HmacValidator.validate` verifies the HMAC solely against that raw body. The `shop` value that is handed to the app's webhook handler, however, is read directly from the unauthenticated `X-Shopify-Shop-Domain` HTTP header. No binding exists between the HMAC-verified body and the shop identity attached to it, breaking the equality `hmac_verified(body) == shop_claimed_in_header`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. `Registry.process` gates handler execution purely on this body-only HMAC check: [2](#0-1) 
and constructs the `WebhookMetadata` passed to the app's handler using `request.shop`, which is read straight from headers with no cross-check against the HMAC-covered data: [3](#0-2) [4](#0-3) 

Because `shop` is excluded from `to_signable_string`, any HTTP client that possesses one valid `(raw_body, hmac)` pair for a given app (e.g., a genuine webhook payload delivered for their *own* store, which a merchant/attacker can freely trigger by, for example, creating an order in their own store to which the app is installed) can resend that exact `raw_body` + `hmac` to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `HmacValidator.validate` will still succeed because it only checks the body signature: [5](#0-4) 
and the handler will receive `WebhookMetadata` claiming the forged/victim shop domain, as documented for host-app consumers: [6](#0-5) 

This is the identity-binding gap explicitly called out in the analog rules ("a shop authenticated versus the shop stored as a session key" / "a field acted on but not covered by the HMAC"): the gem's own webhook `shop` field is acted upon by host applications (as shown in the gem's documented usage pattern, e.g. `perform_later(topic:, shop_domain: data.shop, ...)`) but is never verified against the HMAC-signed material.

### Impact Explanation
An attacker who legitimately installs the target app on their own shop (a normal unprivileged merchant, not requiring `api_secret_key`, access tokens, or any credential leak) can generate a genuinely-signed webhook body for their own tenant, then replay it to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header pointing at a victim tenant. Because the gem only validates the raw body's HMAC and blindly passes the header-derived `shop` through to the host application's handler, the host application will process/store data under the wrong tenant identity — a cross-tenant data-integrity/confidentiality violation (e.g. victim's order/customer records overwritten with attacker-controlled content, or attacker data attributed to a victim shop). This matches the "cross-tenant access" High/Critical impact category since it crosses a tenant boundary using only the gem's own verification logic.

### Likelihood Explanation
Likelihood is High: any app developer who installs the app on their own store can trivially trigger a real webhook delivery (e.g., create an order), capture the resulting `(raw_body, hmac)` pair, and replay it against the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` header — no secrets, tokens, or privileged access are required beyond normal, self-service Shopify merchant capabilities.

### Recommendation
Bind the shop identity into the HMAC-verified material, or otherwise cryptographically/contextually verify that the `shop-domain` header corresponds to the same request Shopify actually signed. Concretely:
- Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in `Request#to_signable_string`, matching them against a signature computed the same way Shopify computes it, OR
- Require callers to independently verify that the resolved `shop` exists in their own registered/installed-shop store before trusting `WebhookMetadata#shop`, and document this requirement prominently, OR
- Have `Registry.process` reject requests where the shop cannot be corroborated by other server-side state (e.g., an active session/install record for that shop) before invoking the handler.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has the app installed there.
# Step 1: Attacker triggers a legitimate webhook (e.g., orders/create) for their own shop.
# Shopify delivers, e.g.:
#   headers: {
#     "X-Shopify-Topic" => "orders/create",
#     "X-Shopify-Hmac-Sha256" => "<valid HMAC of raw_body>",
#     "X-Shopify-Shop-Domain" => "attacker-shop.myshopify.com",
#     ...
#   }
#   raw_body: '{"id":1,"note":"forged content"}'

# Step 2: Attacker replays the exact same raw_body + valid hmac to the app's
# public webhook endpoint, but swaps the shop-domain header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_valid_hmac,   # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_raw_body, headers: headers)

# Step 3: Registry.process passes HMAC validation (body-only check) and invokes
# the handler with WebhookMetadata claiming shop: "victim-shop.myshopify.com".
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {...}, ...))
```
This succeeds because `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) only checks `raw_body` via `to_signable_string`, never the `shop` header.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
