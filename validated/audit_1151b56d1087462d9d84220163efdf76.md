### Title
Webhook `shop-domain` (and `topic`/`webhook_id`) header is trusted for tenant routing without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body [1](#0-0) , while the tenant-identifying `shop` field (and `topic`, `webhook_id`, `api_version`) is read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates only the HMAC and then forwards the header-derived `shop` (and `topic`) straight to the host app's handler as trusted tenant metadata [3](#0-2) . The equality the library implicitly promises but does not enforce is: `shop_bound_by_hmac == shop_delivered_to_handler`. Because the two are never bound together, an attacker who can obtain any single valid `(raw_body, hmac)` pair for the app's secret (e.g., by installing the app on their own store and receiving a legitimate webhook from it) can replay that exact body/HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a victim shop. `HmacValidator.validate` will still pass, since it only re-derives the signature from `@raw_body` [4](#0-3) , and the handler will process attacker-controlled body content attributed to the victim shop.

### Finding Description
`WebhookHandler` implementations receive a `WebhookMetadata` struct built from `request.topic`, `request.shop`, `request.parsed_body`, etc. [5](#0-4) . `Registry.process` gates this only on `Utils::HmacValidator.validate(request)` [6](#0-5) , which in turn calls `verifiable_query.to_signable_string` — for `Request` this is exactly `@raw_body`, nothing else [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors pull straight from `@headers` with no cryptographic tie to the signed content [7](#0-6) .

This is the same bug class flagged in the external report: a value acted upon by downstream logic (there, `_totalStake`; here, `shop`/`topic`) is not covered by the integrity check that gates the whole operation (there, the post-call balance check; here, the HMAC). The check answers "is this body authentic for *some* webhook this secret produced" rather than "is this body authentic *for this specific shop and topic*."

### Impact Explanation
This crosses a tenant boundary: it is a **cross-tenant access** issue. An unprivileged internet user who is also a legitimate (even free-tier) merchant of the app can capture one authentic webhook delivery from their own shop, then forge deliveries to the app's public webhook endpoint that impersonate any other shop by only changing headers, since the body's HMAC never bound the shop. Depending on the host app's handler logic, this can inject attacker-controlled order/product/customer data into another merchant's records, trigger destructive actions (e.g., uninstall/GDPR handlers) against a victim shop, or pollute per-shop caches/queues keyed by the spoofed `shop` value — all without ever needing the victim's access token or the app's `client_secret`.

### Likelihood Explanation
Likelihood is moderate: the attacker needs (a) their own legitimate install of the target app to harvest one valid `(body, hmac)` pair, and (b) the webhook endpoint to be reachable from the internet (true by design, since Shopify itself delivers webhooks over the public internet, and the gem provides no IP allowlisting). No secrets, TLS interception, or privileged access are required — only the ability to send an HTTP POST with attacker-chosen headers and a previously-observed valid body/HMAC pair.

### Recommendation
Bind the tenant-identifying fields into the signed content rather than trusting headers verbatim: include `shop`, `topic`, and `webhook_id` in `to_signable_string` (mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`, `state`, `code`, etc. into its signature [8](#0-7) ), or at minimum document/enforce that host applications must independently authenticate `shop` against their own installed-shop registry before trusting `WebhookMetadata#shop`/`#topic` for any tenant-scoped action.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled store `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g. `orders/create`) on that store; capture the raw POST body `B` and the `x-shopify-hmac-sha256` header value `H` — a valid pair because `HmacValidator` only signs `B` [1](#0-0) .
3. Send a new POST to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim.myshopify.com` and, if desired, a different `x-shopify-topic`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate`, which recomputes the signature over `B` only and succeeds [9](#0-8) .
5. The registered `WebhookHandler#handle` is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body_of_B, ...)` [10](#0-9) , causing the host application to act on attacker-supplied data under the victim shop's identity.
