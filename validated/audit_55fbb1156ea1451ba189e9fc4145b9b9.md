### Title
Webhook shop/topic/webhook-id identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature over the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed straight through to the registered handler. This is the same class of bug as the reported Vault issue: a field that is acted upon (`shop`) is not covered by the identity-binding check (`hmac`), so the two can be made to disagree.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from headers, which are never mixed into the signable string: [2](#0-1) 

`Registry.process` validates the HMAC over the request (i.e., over `raw_body` only) and, once that passes, dispatches the handler using the *unverified* header-derived `shop`, `topic`, `webhook_id`, and `api_version`: [3](#0-2) 

`HmacValidator.validate` confirms this: it only ever checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e., against whatever `to_signable_string` returns — for webhooks, that's the body, never the shop header: [4](#0-3) 

The identity binding that should hold is: `shop-header == shop-that-produced(hmac, body)`. Because `shop` is outside the signed content, that equality is never actually checked — any `(body, hmac)` pair valid for the app's `client_secret` can be replayed with an arbitrary `shop-domain` header and will still pass `HmacValidator.validate`.

### Impact Explanation
An unprivileged actor who can obtain one valid `(raw_body, hmac)` pair for the target app (e.g., by installing the app on their own store and capturing a webhook Shopify sends them, since HMAC is computed with the app's shared `client_secret` across all installs) can replay that exact payload to the app's webhook endpoint while substituting the `shop-domain`/`topic`/`webhook-id` headers for a different, victim shop. `Registry.process` will accept it (HMAC only checks the body) and hand the handler a `WebhookMetadata` claiming to be from the victim shop, causing the app to act on/store attacker-controlled data under another tenant's identity — a cross-tenant integrity/confidentiality violation depending on how the host app keys its data by `data.shop`.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even free) installer of the target app on their own shop — no access token, `client_secret`, or privileged account is needed, satisfying the "unprivileged internet user" bar. Capturing your own shop's webhook body/HMAC and replaying it with a modified `shop-domain` header is straightforward HTTP tampering.

### Recommendation
Do not let handler-visible identity fields (`shop`, `topic`, `webhook_id`, `api_version`) be sourced purely from headers that are outside the signed content. At minimum, cross-check the header-derived `shop` against the session/shop the request was routed to (e.g., verify it matches the shop associated with the resolved app installation/session before dispatch), or document explicitly that `WebhookMetadata#shop` is unauthenticated and must be revalidated by the host application before use.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed with the app's `client_secret`), plus `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays `B`/`H` unchanged but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `topic`/`webhook-id`).
4. `ShopifyAPI::Webhooks::Request.new` accepts it (only presence of headers is checked), `HmacValidator.validate` passes because it only checks `raw_body` against `H`, and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to process attacker data as if it originated from the victim shop.

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
