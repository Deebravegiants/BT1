### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute used for tenant identification purely from the unauthenticated `X-Shopify-Shop-Domain` HTTP header, while the HMAC signature that `Registry.process` validates only covers the raw request body. Any party able to obtain one valid `(body, hmac)` pair for the app's shared `client_secret` (e.g., an attacker who has installed the app on their own shop) can replay that body/HMAC pair while substituting an arbitrary `shop-domain` header, and the handler will process the webhook as if it originated from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop` is read straight from the header, with no cryptographic tie to the signed payload: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` — i.e., it verifies that the HMAC matches the body using the app's `client_secret` (or `old_api_secret_key`) — and then immediately forwards `request.shop` (and `request.topic`, `request.parsed_body`) to the registered handler without any further binding check: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the signature purely from `verifiable_query.to_signable_string` (the body) and the shared secret — the `shop` header plays no role in this computation: [4](#0-3) 

Because Shopify uses the same app-level `client_secret` to sign webhooks for *every* shop that has the app installed, an attacker who legitimately installs the app on their own shop (an unprivileged action requiring no special credential) can capture a real `(raw_body, X-Shopify-Hmac-Sha256)` pair generated for their own shop, then POST it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to any other shop domain of their choosing. The HMAC check still passes (only the body is verified), so `Registry.process` will invoke the app's webhook handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop.

This breaks the identity binding: the equality that should hold is `shop authenticated by HMAC == shop acted upon by the handler`, but here `shop acted upon by handler` is taken from a header that the HMAC computation never covers, so the two are never actually forced to match.

### Impact Explanation
This is a cross-tenant confusion primitive: the app's webhook-handling logic (order updates, GDPR/compliance events, data deletion, inventory changes, etc., depending on what topics the integrating app registers) can be triggered with forged data attributed to a shop the attacker does not control and never authenticated as. Depending on what the host application does with `WebhookMetadata#shop` (e.g., looking up a stored session/access token for that shop and performing actions, or writing/deleting records keyed by that shop id), this can enable injection of bogus data into, or unauthorized state changes for, an arbitrary tenant — satisfying the "cross-tenant access" criticality bucket, since an attacker with no relationship to the victim shop can cause the app to process events as belonging to it.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that (a) allows self-service installs (most public apps do) and (b) trusts `WebhookMetadata#shop` for tenant-scoped side effects without independently re-validating that the shop is the one actually engaged in the specific business event. The prerequisite — installing the app on an attacker-controlled shop — is available to any unprivileged internet user with a Shopify partner/dev account, which is free and requires no special access. Exploitation only requires resending an HTTP request with a rewritten header, a trivial capability once one legitimate webhook payload+signature has been observed.

### Recommendation
Bind the shop identity to the signed payload rather than trusting an unauthenticated header:
- Where the webhook topic's JSON body includes shop-identifying data, cross-check it against the header value before dispatching to the handler, and reject on mismatch.
- More robustly, have `Registry.process` (or a documented integration pattern) require the host application to verify that `request.shop` corresponds to a shop with an active, stored session/installation before performing any tenant-scoped effects, rather than relying on the header value.
- Consider including the shop domain within the HMAC-signed material (or otherwise cryptographically binding it), if/when this is possible within Shopify's webhook signing scheme, and document explicitly that `request.shop` is unauthenticated and must be independently corroborated by the integrating application.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, obtaining a legitimately signed webhook delivery for some subscribed topic, e.g.:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: `{"id": 123, ...}`
2. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but rewrites the header:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC: [5](#0-4) 
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)`, i.e., attacker-controlled data attributed to a shop the attacker never authenticated as.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
