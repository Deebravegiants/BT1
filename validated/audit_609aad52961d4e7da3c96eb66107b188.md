### Title
Webhook `shop` (and other identifying headers) are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) used by application webhook handlers from an HTTP header that is never included in the HMAC signature computation. The HMAC only covers the raw request body, so any attacker who can obtain one valid `(body, hmac)` pair for their own shop can freely relabel it as coming from any other shop by changing the `shop-domain`/`x-shopify-shop-domain` header, without invalidating the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the request solely via `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` and therefore only checks the body bytes against the secret key. It never independently confirms that the `shop` value is authentic: [2](#0-1) 

The `shop` accessor is read straight from an attacker-controlled header: [3](#0-2) 

This breaks the intended identity binding:
`shop_verified_by_hmac == shop_delivered_to_handler`

Before the attacker's request: for a legitimate Shopify-originated webhook, `shop-domain` header and HMAC-signed body both originate from Shopify for the same shop, so the two values are always consistent.

After the attacker's request sequence: an attacker who owns/controls a shop that has the app installed can capture one legitimate `(raw_body, hmac)` pair delivered to their own tenant's webhook endpoint (e.g., by installing the app on their own store and receiving a real webhook, or via any endpoint the app exposes that echoes/logs webhook deliveries). They then POST that same `raw_body` and `hmac` to the app's webhook endpoint, but substitute the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds because the signature only covers `raw_body`, which is unchanged. `Registry.process` then invokes the handler with `WebhookMetadata.shop` set to the victim shop, while the body content is fully attacker-controlled (from their own shop's webhook): [4](#0-3) 

This is a direct analog of the bug class in the reference report: a field (`shop`) that is acted upon by privileged application logic is not bound by the cryptographic check (HMAC) that is supposed to authenticate the whole request.

### Impact Explanation
This allows cross-tenant data/event injection: an attacker can make the host application believe events (`orders/create`, `app/uninstalled`, `customers/data_request`, etc.) originated from a shop they do not control, with body content of their choosing (subject to being a previously-observed valid payload for their own shop). Depending on how the host app's webhook handlers use `WebhookMetadata.shop` (e.g., writing state, revoking access, updating billing, deleting merchant data), this can lead to unauthorized cross-tenant state changes attributed to a victim shop — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires the attacker to have or create at least one shop with the app installed (any developer/free plan can do this) and to observe one raw HMAC/body pair from a real webhook delivery to that shop, both of which are trivial for any unprivileged Shopify merchant/developer. No secret key, access token, or privileged account is needed — only reuse of a self-obtained payload with a swapped header.

### Recommendation
Bind the shop identity into the authenticated bytes: include the `shop-domain` (and other trust-relevant headers like `topic`, `webhook-id`, `api-version`) inside the HMAC-signable string, or otherwise cryptographically verify the header value out-of-band before trusting it (e.g., cross-check `shop` against an installed/active session store keyed by the shop that the app already trusts, rather than the raw header alone).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook delivery (e.g., updates an order) and captures the raw request: `raw_body`, and header `x-shopify-hmac-sha256`.
3. Attacker crafts a new HTTP POST to the app's webhook endpoint using the captured `raw_body` and `x-shopify-hmac-sha256` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `shop` returns `"victim-shop.myshopify.com"` [3](#0-2) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches the (unchanged) signature, so validation passes [5](#0-4) .
6. The registered handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the event actually originated from the attacker's own shop [4](#0-3) .
