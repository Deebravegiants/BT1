### Title
Solver fills at a same-block-manipulable Uniswap V4 spot price with no worst-case bound - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`)

### Summary
The FX/Simplex intent-solver strategy prices venue-funded pairs directly off a Uniswap V4 pool's instantaneous spot price (`sqrtPriceX96`-derived `token0Price`/`token1Price`) with no TWAP, no price-impact/depth modeling, and no per-fill slippage bound. The only safeguard, `checkPriceGuard`, merely checks that the spot quote is within a static basis-point band of an operator-configured reference price — exactly analogous to the reported Perennial bug where liquidation only checked the current oracle price and not a worst-case price movement. An attacker who can move the pool price within that allowed band in the same block (e.g., via a flash-loan-funded swap) can force the solver to quote and pay out at a manipulated rate, extracting solver funds/inventory, and the historical loss-bounding overfill clamp for exactly this scenario has been intentionally disabled.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` reads the pool's current price for the highest-liquidity qualifying position and returns it unadjusted as `priceUsd`: [1](#0-0) 

`computeDirectPoolPriceUsd` returns the raw pool mid derived from `sqrtPriceX96` with no fee-tier or size/impact adjustment: [4](#0-3) 

`FXFiller.resolveLegRates`/`checkPriceGuard` in the solver consumes this live venue price and only checks that it is within `maxDeviationBps` of a static, operator-set `referencePrice` — it never checks execution cost, depth, or worst-case slippage: [2](#0-1) 

The project's own documentation confirms this gap explicitly: "`checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost. A venue-priced pair that has to swap through its own pool to source inventory pays a fee tier it never quoted against." [5](#0-4) 

Compounding this, the per-leg loss bound that historically protected the solver from a manipulated venue price has been deliberately disabled — overfill beyond the ceiling is now only logged, not clamped: [3](#0-2) 

This is the same root-cause pattern as the referenced Perennial finding: a critical financial decision (liquidation threshold there; solver fill price/payout here) is derived solely from a single current on-chain price read, checked only against a static/instantaneous bound, with no consideration of the worst-case price an attacker can engineer within the same transaction or block.

### Impact Explanation
An attacker (any unprivileged actor who can submit an order and simultaneously move the referenced Uniswap V4 pool, e.g. via a same-block/flash-loan swap) can push the pool's spot price to the edge of the `maxDeviationBps` band around the static reference — a legitimate-looking, in-band manipulation — and have the solver's `computeLegPolicyOutput`/funding-withdrawal path pay out inventory (LP-position tokens) at that manipulated rate. Because the overfill clamp is disabled and there is no execution-cost or TWAP check, the solver can be made to overpay per-unit and drain value from its Uniswap V4 positions, i.e., concrete theft/loss of solver funds. This qualifies as a High-severity, reachable path since it is triggered purely by submitting an order plus a public DEX swap — no privileged access required.

### Likelihood Explanation
Uniswap V4 pools are permissionlessly swappable, and moving a pool's spot price within a modest bps band (whatever `maxDeviationBps` is configured to) is inexpensive, especially for lower-liquidity "exotic" pairs the config explicitly targets (cNGN, ZARP, etc.). Any solver operator running the `UniswapV4FundingPlanner` path with `priceGuard` configured loosely (or default, unguarded) is exposed on every fill sourced from that venue. The disabled overfill clamp is a further amplifier the code comments themselves flag as a removed protection.

### Recommendation
- Replace or supplement the spot-price read with a time-weighted average price (TWAP) over multiple blocks, or require multiple independent price sources (e.g., a corroborating oracle) before sourcing from a Uniswap V4 position.
- Bound the trade by expected price impact/execution cost of the actual withdrawal size rather than only comparing against a static reference band.
- Re-enable (or replace) the overfill clamp so that a bad or manipulated quote cannot cause the solver to overpay beyond a strict, enforced ceiling rather than only emitting a warning.
- Consider tightening `maxDeviationBps` and combining it with liquidity-depth checks so a thin pool cannot be manipulated within the allowed band cheaply.

### Proof of Concept
1. Configure/observe a solver running `FXFiller` with a venue-priced pair backed by a Uniswap V4 position (`[vault.uniswapV4]`), with `priceGuard.maxDeviationBps` set to a typical value (e.g., 200 bps per the docs example) [6](#0-5) .
2. In the same block as submitting an intent order that this solver would fill from that position, execute a large swap against the underlying Uniswap V4 pool to move its spot price to the edge of the allowed deviation band (still passing `checkPriceGuard`).
3. The solver calls `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd`, which reads the manipulated spot price [1](#0-0) .
4. `checkPriceGuard` passes because the manipulated price is within `maxDeviationBps` of the static reference [7](#0-6) .
5. `computeLegPolicyOutput`/the funding withdrawal plans and executes a liquidity removal priced at the manipulated rate, and any resulting overfill beyond the configured ceiling is only logged, not blocked [3](#0-2) , letting the attacker extract value from the solver's position at the manipulated price before it reverts to normal.

	async getExoticTokenPrice(chain: string, exoticToken: string): Promise<Decimal | null> {
		const state = this.stateByChain.get(chain)
		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
