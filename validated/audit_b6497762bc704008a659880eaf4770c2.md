### Title
Unauthenticated Session Cookie Value Enables Cross-Tenant Session Hijacking via Predictable Session IDs - ([File: lib/shopify_api/utils/session_utils.rb])

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` and its helper `cookie_session_id` return the raw, unverified value of the `shopify_app_session` cookie as the identifier used to look up a merchant's stored `Session` (including its `access_token`). Because this cookie is a plain, unsigned string set via ordinary `cookies[...] = { value: ... }` (per the gem's own documented usage), and because the value the gem itself writes into that cookie is a fully predictable string (`"offline_#{shop}"` or `"#{shop}_#{user_id}"`), any unauthenticated client can forge the cookie to claim any shop's session id, breaking the binding between "session id used to fetch stored credentials" and "shop the requester is actually authenticated as."

### Finding Description
When completing OAuth, `ShopifyAPI::Auth::Oauth.validate_auth_callback` builds a session cookie whose value is exactly `session.id`: [1](#0-0) 

`session.id` is deterministic and derived only from public/guessable values — the shop's domain and (for online tokens) the associated user id: [2](#0-1) 

The `SessionCookie` struct carries only `name`, `value`, `expires` — there is no signature, MAC, or any binding to the actual authenticated requester: [3](#0-2) 

The gem's own documentation instructs host apps to store this cookie with a plain (non-signed) cookie jar (`cookies[name] = { value:, secure:, http_only: }`), and to use `SessionRepository.store_session`/`retrieve` keyed by this id: [4](#0-3) 

Later, when the host app wants to identify "the current session" for a request, it calls `SessionUtils.current_session_id`, which — for non-embedded apps, or as a fallback for embedded apps without a JWT — simply returns whatever byte string is in the `shopify_app_session` cookie, with zero validation that it corresponds to the requester's actual shop: [5](#0-4) [6](#0-5) 

The equality that should hold is:
`session_id_used_to_fetch_credentials == session_id_of_the_shop_the_requester_actually_completed_OAuth_as`

Instead, the gem enforces only:
`session_id_used_to_fetch_credentials == raw_cookie_bytes_supplied_by_the_client`

Since the cookie is unsigned and its value format (`offline_<shop>.myshopify.com` or `<shop>.myshopify.com_<user_id>`) is documented/predictable, and shop domains are typically public knowledge (they appear in storefront URLs, app listings, etc.), any unauthenticated internet client can set `Cookie: shopify_app_session=offline_victim-shop.myshopify.com` on a request to the host app. If the host app follows the gem's documented pattern (`SessionRepository.retrieve(session_id)` then makes API calls with that `Session`), the attacker causes the app to load and act with the victim shop's real, stored `access_token` — a cross-tenant credential-confusion attack requiring no secret, token, or prior authentication.

### Impact Explanation
This breaks tenant isolation: an unauthenticated party can cause the host application to operate under another merchant's OAuth session/access token merely by supplying a guessable cookie value. This maps to Critical impact — cross-tenant access / theft-equivalent use of another merchant's access token — because the gem provides no integrity protection on the value it tells developers to persist as the tenant-identifying session key.

### Likelihood Explanation
Likelihood is high for non-embedded apps (and as a fallback path for embedded apps lacking a bearer token): the session id format is fixed and documented by the gem itself (`offline_#{shop}` / `#{shop}_#{user_id}`), shop domains are commonly public, and no authentication step is required to send an arbitrary `Cookie` header. The only friction is guessing/knowing the target shop's `.myshopify.com` domain and (for online sessions) a numeric user id, both of which are frequently discoverable.

### Recommendation
Do not use an unsigned, predictable string as the trust anchor for session lookup. Either:
- Sign/MAC the `SessionCookie` value (e.g., HMAC it with the app's `client_secret`, similar to `Utils::HmacValidator`) and verify the MAC in `SessionUtils.cookie_session_id` before trusting it, or
- Require the cookie value to be an unguessable random token that is looked up server-side (indirection), never the raw predictable session id, or
- Clearly document that host applications MUST use a cryptographically signed/encrypted cookie jar (e.g., Rails `cookies.signed`/`cookies.encrypted`) for `shopify_app_session`, and add a runtime check/warning when this isn't the case.

### Proof of Concept
1. Victim shop `victim-shop.myshopify.com` has installed the app and completed offline OAuth; the app's `SessionRepository` stores `Session(id: "offline_victim-shop.myshopify.com", access_token: "shpat_xxx", ...)`, following the documented flow in `docs/usage/oauth.md`.
2. Attacker (no account, no prior interaction) sends a request to any host-app endpoint that resolves the current session via `ShopifyAPI::Utils::SessionUtils.current_session_id`, with header:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
3. `current_session_id` → `cookie_session_id(cookies)` returns `"offline_victim-shop.myshopify.com"` unchanged: [6](#0-5) 
4. The host app calls `SessionRepository.retrieve("offline_victim-shop.myshopify.com")`, obtains the victim's real `Session` (with `access_token`), and performs API actions/renders data on the attacker's behalf using the victim's credentials — a cross-tenant compromise achieved with no secret or prior authentication.

```ruby
# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Auth
    module Oauth
      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
```
