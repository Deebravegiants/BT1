### Title
`ir_face_save_fps_override` and `thermal_save_fps_override` are never reset to `None` after mirror sweep, causing permanent excessive raw biometric persistence beyond the sweep - ([File: src/plans/biometric_capture/mirror_sweep.rs])

### Finding Description
In `Plan::perform_mirror_sweep`, all three save-fps overrides are set to `Some(f32::INFINITY)` before starting the sweep: [1](#0-0) 

After `orb.run(self).await?` returns (whether the sweep completes normally by exhausting `frame_counter` or is aborted early via the `self.timeout` `Fuse` firing in `poll_extra`, both of which resolve as `Ok(BrokerFlow::Break)` and thus a normal `Ok(())` return from `orb.run`), the cleanup code only resets `orb.ir_eye_save_fps_override`: [2](#0-1) 

There is no line resetting `orb.ir_face_save_fps_override` or `orb.thermal_save_fps_override` back to `None` anywhere in this function, nor anywhere else in the file (only 4 matches for these fields in the file: the two `Some(f32::INFINITY)` assignments for `ir_face`/`thermal`, the `ir_eye` assignment, and the single `ir_eye` reset). This is not conditional on the timeout/early-abort path specifically — it happens on **every** invocation of `perform_mirror_sweep`, including the normal, non-aborted completion path, because the reset for those two fields simply does not exist in the code.

Since `Orb` (and its `ir_face_save_fps_override`/`thermal_save_fps_override` fields) is the broker instance used across the device's operation, once a mirror sweep runs once, these two overrides remain stuck at `Some(f32::INFINITY)` for the rest of that signup and for all subsequent signups performed on that Orb unit until process restart, because nothing else in the codebase clears them.

### Impact Explanation
This causes `image_notary` (gated via the `*_save_fps_override` mechanism) to persist every captured raw IR-face and thermal frame at maximum/unbounded rate for the remainder of the current signup and for all future signups on the same device, exceeding the intended per-frame-rate persistence policy. This is a genuine cross-signup state bleed: an attacker triggering the mirror sweep extension during their own signup (via QR-supplied `signup_extension_config` parameters that select the extension) permanently degrades the raw-image retention policy for every subsequent, unrelated user's signup on that Orb, not just their own.

### Likelihood Explanation
Deterministic and unconditional — the bug fires on every single execution of `perform_mirror_sweep` regardless of timeout/abort, since the reset code for `ir_face_save_fps_override`/`thermal_save_fps_override` simply does not exist. No special attacker timing or race condition is required; any signup that exercises the mirror sweep extension once (attacker-selectable via QR extension config parameter parsed in `SweepConfiguration::new`) permanently taints the override state for the device.

### Recommendation
In `Plan::perform_mirror_sweep`, add the missing resets alongside the existing `orb.ir_eye_save_fps_override = None;` line:
```rust
orb.ir_eye_save_fps_override = None;
orb.ir_face_save_fps_override = None;
orb.thermal_save_fps_override = None;
```
Additionally, guard against early-return via `?` (e.g., if `orb.run(self).await?` or any MCU send prior to this point errors) by wrapping the sweep body in a scope/guard (e.g. RAII guard or explicit `let result = ...; reset overrides; result?;`) so the overrides are always cleared even on error propagation, not just on the `Ok` path currently reached at line 246.

### Proof of Concept
Integration test plan:
1. Construct an `Orb` broker test harness with a `mirror_sweep::Plan` wrapping a `biometric_capture::Plan`.
2. Call `perform_mirror_sweep` and let it run to normal completion (send exactly `SWEEP_FRAMES` IR-eye camera frames so `frame_counter` reaches 0 without the timeout firing).
3. Assert after return: `orb.ir_eye_save_fps_override == None` (passes), but `orb.ir_face_save_fps_override == Some(f32::INFINITY)` and `orb.thermal_save_fps_override == Some(f32::INFINITY)` (both incorrectly remain set — demonstrating the bug is present even without any forced early abort).
4. Repeat with the timeout `Fuse` firing mid-loop (send fewer than `SWEEP_FRAMES` frames and let `time::sleep` elapse) — confirm the same result: `ir_eye_save_fps_override` reset, `ir_face_save_fps_override`/`thermal_save_fps_override` still stuck at infinity.
5. Call `perform_mirror_sweep` a second time (simulating a subsequent, unrelated signup reusing the same `Orb`) and confirm `ir_face_save_fps_override`/`thermal_save_fps_override` were already `Some(f32::INFINITY)` before this second call even started, proving state bleed across signup sessions.
