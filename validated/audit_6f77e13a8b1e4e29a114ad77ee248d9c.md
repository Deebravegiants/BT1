### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the raw request body via HMAC, then hands the caller's own, unauthenticated `shop-domain` header straight to the app's handler as the tenant identifier. The `shop` value used to attribute a webhook to a merchant is never itself covered by the signature check, breaking the identity binding `hmac(request) == hmac(shop ∧ body)`.

### Finding Description
`Registry.process` does: [1](#0-0) 

It raises unless `Utils::HmacValidator.validate(request)` succeeds, then immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and forwards it to the app's handler.

The HMAC check itself only ever covers the raw body, never the `shop` header: [2](#0-1) 

`hmac` is computed from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body`. `shop` is read from a completely separate, unsigned header (`shop-domain`) via `shopify_header`: [3](#0-2) [4](#0-3) 

`Utils::HmacValidator.validate` confirms this: it only ever calls `verifiable_query.to_signable_string`, i.e. the body, never the shop header: [5](#0-4) 

The library's own docs instruct consumers to trust `data.shop` as "the shop domain of the webhook" and use it directly to key business logic (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), i.e. this gem's documented contract explicitly encourages the app to use `request.shop` as the tenant-identity key for the webhook payload, even though this gem never binds that field into the signature it verifies.

Because the HMAC only signs the body, any bytes that arrive with a body/HMAC pair that is valid for *some* shop (e.g. an app installed on the attacker's own store, or any HMAC-signed webhook the attacker legitimately received) remain valid if the `x-shopify-shop-domain` / `shopify-shop-domain` header is swapped to name a different (victim) shop — the signature check in `hmac_validator.rb` cannot detect the change because that header was never part of the signed material to begin with.

### Impact Explanation
This breaks the equality `verified_shop == acted_upon_shop`: the gem verifies "this body was HMAC-signed with our `api_secret_key`" but acts on "this body belongs to `request.shop`" without ever proving the two are the same tenant. An attacker who can obtain any valid `(body, hmac)` pair for their own installation (trivial — they own that shop) can present it to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop. `Registry.process` accepts it, and the handler executes attacker-controlled webhook data (`data.body`) under the victim's tenant identity (`data.shop`), leading to cross-tenant data injection into whatever store/session/queue the app keys off `data.shop` (e.g. writing attacker-controlled "order" data into the victim's records, or triggering shop-scoped side effects using the victim's session/access token that the app looks up by `data.shop`). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
No credentials, TLS interception, or privileged access are required — any user who can install the app on their own store (or otherwise obtain one legitimately-signed webhook body+HMAC) can replay it to the app's public webhook callback URL with a forged `shop-domain` header. The only "difficulty" is knowing/guessing the app's webhook URL, which is typically documented/predictable (`path` configured at registration, e.g. `callback/orders/create`).

### Recommendation
Bind the shop domain into the identity check before it is used, e.g.:
- Include the `shop-domain` header (and ideally `topic`/`webhook-id`) in the HMAC-signable material used by `VerifiableQuery#to_signable_string`, or
- Independently validate that `request.shop` corresponds to a shop for which this app currently holds a session/webhook registration (cross-check against the app's own persisted list of subscribed shops) before invoking the handler, and reject/flag mismatches.

At minimum, document prominently that `data.shop` is not authenticated by the HMAC check and must not be trusted as a tenant key without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target app on their own development store `attacker.myshopify.com` and registers for `orders/create`.
2. Shopify legitimately delivers a webhook to the app's callback URL for that topic; attacker captures the exact `raw_body` and the `x-shopify-hmac-sha256` value Shopify sent (both are visible to the attacker as the shop owner, e.g. via request logging on their own receiving endpoint, or by using ngrok/a debug endpoint).
3. Attacker crafts a new HTTP POST to the same app callback URL, reusing the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only and it matches (per `lib/shopify_api/utils/hmac_validator.rb:12-31` and `lib/shopify_api/webhooks/request.rb:10-38`), so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) proceeds.
5. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body, and performs shop-scoped work (e.g. `perform_later(shop_domain: data.shop, webhook: data.body)` per the gem's own documented usage) attributing attacker-controlled data to the victim's tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
