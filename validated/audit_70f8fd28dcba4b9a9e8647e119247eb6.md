### Title
Webhook shop-domain header is trusted for tenant identity but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The gem's webhook HMAC check verifies only the raw request body against the app's shared `client_secret`, while the `shop` (tenant identifier) that gets handed to the application's webhook handler is read from an unauthenticated HTTP header. This breaks the intended binding: `hmac_valid(body) == authenticated(shop)`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic tie to that body: [1](#0-0) [2](#0-1) 

`Registry.process` validates the HMAC of the body only, then immediately forwards the header-derived `shop` to the handler without any additional check: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e., the body) using the app's `Context.api_secret_key`, which is the same secret for every shop that has the app installed: [4](#0-3) 

Because the same `client_secret` is used to sign webhooks for every tenant of a multi-tenant app, a valid `(body, hmac)` pair generated by triggering a real webhook from one shop remains a cryptographically valid pair no matter what value is placed in the `shop-domain` header. The equality that should hold — "the shop asserted to the handler equals the shop the signature was computed for" — does not hold, because the shop is never part of the signed input.

### Impact Explanation
An unprivileged internet user who can install the app on their own (free/dev) shop can capture a legitimate webhook body + HMAC pair sent to their own endpoint, then replay a forged HTTP POST to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to any other installed shop's domain. The HMAC check still passes (it never examined the header), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen value: [5](#0-4) 

Any handler logic that uses `data.shop` to look up a session, scope a database write, or trigger tenant-specific side effects can be made to act on/for a shop the attacker does not control — a cross-tenant data-integrity/confidentiality issue.

### Likelihood Explanation
Medium-to-High: no privileged credentials are required — only the ability to install the app on one's own shop (which is normally open to any merchant) to obtain a valid signed body, plus the ability to send an arbitrary HTTP request to the app's public webhook endpoint with modified headers. This mirrors the analog pattern of "field acted on but not covered by the HMAC," directly matching the report's bug class (transfer acting on a destination not bound to the balance check) applied here to the shop identity not being bound to the signature.

### Recommendation
Include the shop domain (and/or webhook id / topic) as part of the signed material, or otherwise cryptographically bind the header value to the verified payload before it is trusted as a tenant identifier — e.g., verify the `shop` against session/install records looked up via the webhook id, or require applications to cross-check `data.shop` against known installed shops rather than trusting the header value implicitly.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (self-service, no privilege needed).
2. Attacker triggers any subscribed webhook event (e.g. updates a product), Shopify sends `POST /webhook` with body `B` and header `x-shopify-hmac-sha256: H` (computed as `HMAC-SHA256(client_secret, B)`), and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the exact same body `B` and header `H` to the app's webhook endpoint but replaces `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` and `client_secret` — it never inspects `shop`.
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, letting the attacker's forged payload masquerade as an event from `victim.myshopify.com`.
