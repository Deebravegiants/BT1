This confirms the vulnerability. The `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, and `webhook_id` are all read straight from HTTP headers that are never included in the HMAC-covered signable string [2](#0-1) . `Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)` and then trusts `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` passed to the host app's handler [3](#0-2) .

### Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted but not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop`, `topic`, and `webhook_id` fields that are handed to the application's webhook handler come from unauthenticated HTTP headers.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively [1](#0-0) . `Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header using `OpenSSL.secure_compare` [4](#0-3) . This proves the body's integrity/authenticity, but nothing else. Meanwhile `Request#shop`, `#topic`, and `#webhook_id` read the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers directly, with no cryptographic binding to the HMAC at all [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e., the body) and then constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, ..., webhook_id: request.webhook_id)` which is passed straight into the app-supplied handler [3](#0-2) .

This breaks the intended identity binding: `HMAC-verified fields == fields the handler acts on`. In reality, `HMAC-verified fields = {raw_body}` while `fields the handler acts on = {raw_body, shop, topic, webhook_id}`.

Because a legitimate Shopify webhook delivery for a merchant who has installed the app produces a genuine, correctly-signed body+HMAC pair for that merchant's own shop, and because HTTP headers of any inbound request to an app's webhook endpoint are entirely attacker-controllable (the endpoint is a public internet-facing route with no other authentication), any actor able to send an HTTP request to the app's webhook endpoint can take a validly-signed `(raw_body, hmac)` pair (e.g., captured from webhook traffic to their own installed test shop, or from the Shopify webhook logs UI which is accessible to that shop's own staff) and replay it with an arbitrary `shop-domain` header naming a *different* merchant/tenant. The gem's `Registry.process` will accept it as valid (body HMAC still matches) and hand the handler a `WebhookMetadata` claiming to be from the victim shop, while the body content actually belongs to the attacker's own shop.

### Impact Explanation
This is a cross-tenant identity-confusion vector: the host application's webhook handler makes tenant-scoped decisions (e.g., which shop's records to update, delete, or overwrite; which shop's data-erasure/GDPR request to act on for `shop/redact`, `customers/redact`, `customers/data_request` mandatory topics) based on `WebhookMetadata#shop`, which this gem cannot guarantee corresponds to the actual origin of the signed payload. An attacker can cause the app to associate their own (attacker-controlled) webhook body/content with a victim merchant's `shop` domain, leading to cross-tenant data injection/corruption inside the merchant's app instance — satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs a genuinely-signed `(raw_body, hmac)` pair, which requires access to at least one real webhook delivery (obtainable by installing the app on the attacker's own store/dev shop, which any developer can do) plus the ability to send crafted HTTP requests with arbitrary headers to the app's public webhook endpoint (this endpoint is unauthenticated by design, per Shopify's webhook architecture, and the gem performs no header-binding check). No merchant credentials, `api_secret_key`, or access tokens are required.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable representation (or otherwise cryptographically bind them, e.g. by including them in an AAD/signed envelope) so that spoofed headers invalidate the signature, mirroring how `Auth::Oauth::AuthQuery` binds `shop`, `state`, `code`, etc. into its `to_signable_string` for OAuth HMAC verification.

### Proof of Concept
1. Attacker installs the app on their own dev shop `attacker.myshopify.com` and receives a legitimate webhook delivery: body `raw_body`, header `shopify-hmac-sha256: <valid_hmac_for_raw_body>`, `shopify-shop-domain: attacker.myshopify.com`, `shopify-topic: customers/redact`.
2. Attacker resends this exact request to the app's webhook endpoint, only changing the header `shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` builds a `Webhooks::Request`, calls `Utils::HmacValidator.validate(request)` [5](#0-4) ; since `to_signable_string` only reflects `raw_body`, the HMAC still matches and validation passes.
4. The handler is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim.myshopify.com", body: request.parsed_body, ...)` [6](#0-5) , causing the app to process attacker-controlled data as if it originated from, and applies to, the victim shop.
