## Finding

### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The gem's webhook verification only proves that the **request body** was signed with the app's shared secret; the `shop-domain` header that the library uses to attribute the event to a tenant is never included in the signed material. An attacker who can obtain one genuinely Shopify-signed webhook payload (e.g., by installing the app on their own store, which is normal unprivileged access) can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and `ShopifyAPI::Webhooks::Registry.process` will accept it and dispatch it to the app's handler as if it originated from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor, in contrast, is read straight from an unauthenticated header and is never mixed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC, then immediately trusts `request.shop` to build the event metadata passed to the app's handler: [4](#0-3) 

Because the app's webhook secret (`Context.api_secret_key`, i.e. the app's `client_secret`) is shared across **every** shop that installs the app, "the request body was validly HMAC-signed" only proves *some* installation of the app produced it — it says nothing about *which* shop. The binding that should hold is:
`shop authenticated by HMAC == shop acted upon by the handler`
but the code only guarantees `body authenticated by HMAC`, while `shop` is parsed from an out-of-band header and trusted unconditionally.

### Impact Explanation
Any unprivileged actor who runs a shop with the app installed receives real, validly-signed webhooks for their own shop (this is normal, unprivileged use of the product). By capturing one such payload+HMAC and resending it to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop, the HMAC check in `Registry.process` still passes (it never inspected `shop`), and `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` hands the attacker-chosen `shop` value straight to the app's business logic. Depending on what the host application does with webhook data keyed by `shop` (e.g. update order/inventory/customer records, fulfil GDPR/uninstall actions, sync state), this lets one tenant inject data or trigger actions attributed to another tenant — a cross-tenant access impact.

### Likelihood Explanation
The only requirement is that the attacker has legitimate access to one shop with the app installed (installing an app is not privileged access to the app's `client_secret` or another merchant's data) and can capture a webhook payload sent to their own endpoint plus resend an HTTP request with a modified header — both trivial for a technical, unprivileged attacker. No secret, token, or credential belonging to the victim or the app developer is needed.

### Recommendation
Include the identifying header(s) (`shop-domain`, `webhook-id`, `topic`, `api-version`) in the signable string used for HMAC verification, or otherwise cryptographically bind the shop to the signed payload, so that a signature computed for one shop's payload cannot be replayed for another shop merely by editing the header.

### Proof of Concept
1. App installs on Attacker's own shop `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, body: `{"id":123,...}`.
2. Attacker captures this request (e.g. from their own server logs, since it was sent to their own app instance/endpoint).
3. Attacker resends the identical body and identical `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (the raw body only) — this still matches, since the body wasn't altered.
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: {...}, ...)`, causing the app to process attacker-controlled data as though it came from `victim-shop.myshopify.com`.
