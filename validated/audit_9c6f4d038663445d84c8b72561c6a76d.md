## Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-verifying the raw request body, then trusts the unauthenticated `shopify-shop-domain` (or `x-shopify-shop-domain`) header as the tenant identity dispatched to the app's handler. Because the header is never included in the signed material, any holder of one valid `(raw_body, hmac)` pair — obtainable from webhooks delivered to their own store, since all shops on an app share the same `api_secret_key` — can replay that pair to the app's public webhook endpoint with an arbitrary `shop-domain` header and have the handler process/attribute the data as coming from a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` (and `topic`, `api_version`, `webhook_id`) values are read directly from HTTP headers and are never part of the signed string: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (i.e., the body only) and compares it to the `hmac-sha256` header: [3](#0-2) [4](#0-3) 

Once the HMAC check passes, `request.shop` is forwarded, unchecked, into the `WebhookMetadata` object handed to the app's registered handler (`Registry.process`, line 198), which per the gem's own documentation is expected to identify which merchant/tenant the payload belongs to: [5](#0-4) 

The identity binding that should hold is: `shop authenticated by HMAC == shop the payload is attributed to`. Because the HMAC only binds `raw_body`, this equality does not hold — the `shop-domain` header can be swapped freely without invalidating the signature.

### Impact Explanation
All Shopify apps share the webhook signing secret (`api_secret_key`/`client_secret`) across every installed shop; there is no per-shop HMAC key. Consequently, any merchant who has installed the app (an "unprivileged" party from the perspective of other tenants) can capture one legitimate `(raw_body, hmac)` pair delivered to their own store (e.g., by pointing their webhook callback at a URL they control, or intercepting traffic to their own endpoint) and replay it to the target app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain, along with an arbitrary `x-shopify-topic`/`x-shopify-webhook-id`. The app's handler — following the gem's documented `data.shop` contract — will process and act on this attacker-supplied payload as if it originated from and pertains to the victim shop. Depending on how the host app uses `data.shop` (e.g., looking up the victim's stored session/access token to enrich or act on the "webhook" data, writing to the victim's records, or triggering business logic scoped to the victim), this results in cross-tenant data injection/confusion using the app's own trusted webhook channel — a cross-tenant access impact achieved with no credentials beyond running the app on one's own store.

### Likelihood Explanation
The webhook receiving endpoint is a plain public HTTP endpoint by design (Shopify's webhook delivery model), so no network position or credential theft is required — only becoming an app user on any shop to obtain one valid signed payload. Constructing the replay request (same body/HMAC, altered `shop-domain` header) requires only a basic HTTP client.

### Recommendation
Include the tenant-identifying headers (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signed material, or otherwise cryptographically bind them to the verified body (e.g., verify `shop` against a per-shop stored value keyed by the already-authenticated body content, or require the host app to independently confirm the resulting `data.shop` matches a known/expected session before trusting it). At minimum, update `Utils::VerifiableQuery`/`Webhooks::Request#to_signable_string` so that all fields the application logic keys off of are part of the signed string, consistent with how OAuth's `AuthQuery#to_signable_string` binds `shop` into its signature.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers/receives a webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header `H` (valid since `H = HMAC-SHA256(api_secret_key, B)`).
2. Attacker sends a new POST to the app's webhook endpoint with:
   - Body: `B` (unchanged)
   - `X-Shopify-Hmac-Sha256: H` (unchanged)
   - `X-Shopify-Shop-Domain: victim.myshopify.com` (changed)
   - `X-Shopify-Topic`, `X-Shopify-Webhook-Id` set arbitrarily.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes.
4. `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed(B), ...)` is passed to the app's handler, which processes attacker-controlled data as if it belongs to `victim.myshopify.com`. [6](#0-5)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
