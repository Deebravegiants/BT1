### Title
Routed strategy puts third-party code beneath the caller's `require_auth`, letting a crafted swap route transfer the caller's unrelated wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller's swap-based strategies (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `flash_position`, `migrate_from_blend`) forward a fully attacker/user-supplied `StrategySwap` payload to the configured router. The router keeps no allowlist of the pool or token addresses the payload names, so arbitrary on-chain code executes on the call stack below the caller's `require_auth` entry. That code can invoke `token.transfer(caller, attacker, amount)` on any token the caller holds; in recording mode it is attached as a child of the caller's `swap_collateral` auth entry, and if the caller signs the simulated tree it executes. This is the exact confused-deputy shape of CVE-2024-9870: a trusted contract is induced to make calls to attacker-chosen endpoints under the victim's authority.

### Finding Description
In `contracts/controller/src/strategies/swap.rs:13-55`, `swap_tokens` takes the user-supplied `swap: &StrategySwap`, authorizes only one exact input transfer to the router (`authorize_transfer_as_current`, line 34), then calls `router.execute_strategy(&controller, &amount_in, swap)` (line 37). Nothing in the controller inspects which pool/token addresses the route names.

The threat model itself confirms the exposure: "The router calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization. A token transfer that such code makes from the caller is recorded ... as a child of the caller's authorization entry, and it executes if the caller signs that tree. The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it." (`docs/explanation/threat-model.md:154-165`).

The harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates end-to-end that a route through an attacker-deployed "pool" records `token.transfer(alice, attacker, WALLET_BALANCE)` under Alice's `swap_collateral` entry and, when the signed tree includes that child, drains her wallet of an unrelated token (lines 194-269).

### Impact Explanation
Theft of user funds beyond the routed amount. The controller's measured-delta checks (`RouterOverspend`, `NoSwapOutput`) only bound the controller's own token flows; a transfer of the caller's arbitrary wallet token inside the signed auth tree is invisible to those guards. Every swap-bearing controller entrypoint is a reachable trigger for a single unprivileged attacker who crafts the route and gets the victim to sign a simulated auth tree — a realistic flow since wallets sign exactly what `simulateTransaction` returns.

### Likelihood Explanation
Medium. Exploitation requires the victim to sign a poisoned authorization tree, which happens naturally when a malicious dapp/quote provider supplies the route and the wallet displays the simulation-derived auth. The attack needs no privileged role, no leaked key, and no router compromise — only the documented absence of a venue allowlist combined with user-controlled route bytes.

### Recommendation
Enforce a venue/pool allowlist on the controller or router side (reject routes naming unvetted pool or token addresses), or have the controller wrap the router call so the caller's auth entry cannot carry unrelated child transfers. Clients should refuse to sign auth trees whose `swap_*`/`multiply`/`flash_position` root contains children other than the single expected `token_in.transfer`.

### Proof of Concept
`tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:
1. `UnlistedPoolRouter::execute_strategy` (lines 39-47) invokes `env.invoke_contract(&route.hop_pool, "swap")` — arbitrary code under the caller's auth.
2. `RogueHopPool::swap` (lines 62-71) calls `token.transfer(victim, attacker, amount)` on an unlisted wallet token.
3. The recording-mode test (lines 194-227) asserts the stolen transfer is recorded as a child of Alice's `swap_collateral` entry and her wallet is drained.
4. The enforcing-mode test (lines 229-269) shows the same transfer succeeds whenever the signed tree contains it.
