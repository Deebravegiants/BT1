### Title
Flash-loan-funded hostile HyperSwap pre-seed lets an attacker capture graduation LP value / open the pool off the curve-close price - ([File: packages/contracts/src/Bonding.sol])

### Summary
The Lava incident is a "flash loan attack" bug class: an attacker uses a single-transaction, uncollateralized capital swing to distort a protocol's price/liquidity assumptions and extract value. Alt.fun's closest reachable analog is the **permissionless two-phase graduation**'s HyperSwap V2 LP-seeding logic in `Bonding.sol`, which explicitly documents that it must defend against an attacker who pre-seeds (mints LP into) the HyperSwap TOKEN/LT pair with a hostile ratio between `_enterGraduating` (phase 1) and `finalizeGraduation` (phase 2) [1](#0-0) . Because anyone can call `finalizeGraduation` and the pair can be pre-created/pre-seeded by anyone before that call, an attacker can flash-borrow LT and/or Token liquidity to fund an oversized hostile mint that overwhelms the protocol's own bounded rebalance budget.

### Finding Description
Graduation is split into two permissionless transactions: `_enterGraduating` (phase 1, fired inline on a threshold-crossing buy or via `triggerGraduation`) computes and caches `tokensForLP`/`ltFromPair` at the last curve price [2](#0-1) , and `finalizeGraduation` (phase 2, permissionless) later seeds the HyperSwap V2 pair using those cached values [3](#0-2) .

Between these two transactions the token sits in `Lifecycle.Graduating` with no LP yet minted. An unrelated wallet can create the HyperSwap pair (`_ensureUniswapV2Pair` is called from inside `finalizeGraduation`, but the V2 factory itself is open — anyone can call `factory.createPair` directly) and mint LP into it at an attacker-chosen ratio, backed by a flash loan of LT and/or the launched Token (both of which are freely transferable ERC20s obtainable by buying on the still-open curve before phase 1 fires, or by flash-borrowing the LT itself).

`_seedRebalancing` handles this "mint pre-seed" regime by rebalancing the pool toward the cached curve-close ratio via a **direct `pair.swap`** whose input is capped at `_swapBudget(...)`, i.e. 99% of `Bonding`'s own inventory of the relevant side (`tokensForLP` / `ltFromPair`, which are themselves capped at the curve's own raised size) [4](#0-3) . That budget is fixed by protocol-side funds only — it does not scale with the size of the attacker's pre-seed. If the attacker's flash-loaned pre-seed reserves are large enough to exceed `DIRECT_MINT_PRESEED_BPS` on at least one side but still dwarf the protocol's rebalance budget, `_noFeeSwapInput`'s capped swap (`s > maxSwap ? maxSwap : s`) cannot fully correct the ratio [5](#0-4) . `_routerDepositAndDispose` then deposits the protocol's remaining balanced subset via `addLiquidity(min0=1, min1=1)` at whatever post-swap ratio resulted [6](#0-5) . Since the swap could not move the ratio all the way to the curve-close price, the LP is minted off-price relative to the attacker's dominant pre-existing position, letting the attacker's own LP (funded by the flash loan, then withdrawn in the same or a follow-up transaction) capture a disproportionate share of the deposited value, or letting the pool open away from the true curve-close price to the attacker's advantage.

Critically, the project's own documentation states this exact scenario's dedicated regression coverage has been removed: *"The dedicated end-to-end hostile-pre-seed integration suite (`test/HostilePreSeed.t.sol`) was removed for runtime reasons after deployment — the wrong-opening-price / LP-capture scenarios, attacker-no-profit, leftover recovery, and concurrent-graduation isolation properties are no longer enforced by automated tests."* [7](#0-6) . This confirms the "attacker-no-profit" and "wrong-opening-price" invariants for this exact code path are currently unverified in CI, even though the mitigation code (`_seedRebalancing`/`_pairRebalance`/`_swapBudget`) exists.

### Impact Explanation
If the flash-loaned pre-seed size can be chosen to exceed the fixed rebalance budget on one side while remaining below the deposit-blocking cap, the attacker's own LP position captures a portion of the protocol-funded `tokensForLP`/`ltFromPair` deposit, and/or the graduated pool opens at a ratio detectably worse than the curve's true close price. This is a direct value transfer from the protocol's (creator/trader-funded) graduation liquidity to the attacker — LP seeded away from the curve close price, matching the accepted impact class for this analog.

### Likelihood Explanation
Medium. The attack requires: (1) monitoring for `TokenGraduating` events (phase 1 firing), (2) front-running `finalizeGraduation` with a large hostile mint into the HyperSwap pair, sized to exceed the fixed `_swapBudget` cap on at least one side, and (3) enough capital to fund that pre-seed — trivially obtainable via a flash loan of LT on HyperEVM, since LT is a freely transferable, externally mintable/redeemable ERC20 [8](#0-7) . `finalizeGraduation` is explicitly permissionless and keeper-driven with only a ~60s window in the happy path, but the pre-seed transaction (`pair.mint`) can be submitted by the attacker as soon as `TokenGraduating` fires, ahead of the keeper's `finalizeGraduation` call, giving a real front-running window. The removal of the dedicated end-to-end test suite for exactly this scenario increases the likelihood that the mitigation's edge cases (budget sizing vs. realistic graduation amounts) have regressed undetected.

### Recommendation
- Restore or rewrite `test/HostilePreSeed.t.sol`-equivalent coverage asserting an explicit "attacker-no-profit" bound and a maximum LP-open-price deviation, sized against realistic worst-case `tokensForLP`/`ltFromPair` values.
- Consider making `_swapBudget`/`maxSwap` scale defensively with the *attacker's* pre-seed size (e.g., abort/queue graduation rather than deposit at a still-off-ratio price when the swap cannot fully correct the pool), or add a maximum-deviation guard on the post-swap ratio before calling `_routerDepositAndDispose`.
- Consider having `finalizeGraduation` create the HyperSwap pair itself atomically inside phase 1 (or otherwise close the front-runnable window between phase 1 and phase 2) rather than relying on a keeper's ~60s SLA as the primary defense.

### Proof of Concept
1. Attacker (or colluding trader) drives a token's bonding curve to the graduation threshold, firing `_enterGraduating` (phase 1) and emitting `TokenGraduating` with cached `tokensForLP`/`ltFromPair` [9](#0-8) .
2. Before the keeper's `finalizeGraduation` call lands, attacker flash-borrows a large amount of LT, calls the HyperSwap V2 factory to create the TOKEN/LT pair (or uses an existing empty one), and calls `pair.mint(attacker)` after transferring a hostile-ratio amount of Token + flash-loaned LT directly to the pair — sized so that at least one side's reserve exceeds `DIRECT_MINT_PRESEED_BPS` of `tokensForLP`/`ltFromPair` (routing into the `_seedRebalancing` branch) but is large relative to `_swapBudget(...)` (99% of `Bonding`'s own inventory) [10](#0-9) .
3. `finalizeGraduation` executes: `_pairRebalance` swaps only up to the capped budget and cannot fully correct the ratio; `_routerDepositAndDispose` deposits the protocol's residual balanced subset at the resulting off-target ratio, minting LP to `LPLock` that is diluted/mispriced relative to the attacker's dominant pre-existing LP position [6](#0-5) .
4. Attacker withdraws their LP (or immediately arbitrages the mispriced pool against the true curve-close price), extracting value and repaying the flash loan within the same transaction bundle.

```text
    function finalizeGraduation(
        address tokenAddress
    ) external nonReentrant {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[tokenAddress];
        if (info.lifecycle != Lifecycle.Graduating) revert NotGraduating();

        address lt = info.ltAddress;
        PendingGraduation memory p = $.pendingGraduation[tokenAddress];

        // Anything in this contract beyond `p.ltFromPair` belongs to a
        // concurrent graduation on the same LT (Phase 1 transferred it
        // via `Router.graduate`) or to stray dust. Either way it is
        // off-limits to this graduation's deposit and sweep — see
        // `_routerDepositAndDispose` and `_sweepLTToOwner`.
        // Saturating subtract: a balance below `p.ltFromPair` shouldn't
        // be reachable in normal operation, but we keep finalize from
        // bricking on a Panic if any future code path or non-canonical
        // LT briefly violates the invariant.
        uint256 ltBalance = IERC20(lt).balanceOf(address(this));
        uint256 protectedLT = ltBalance > p.ltFromPair ? ltBalance - p.ltFromPair : 0;

        address lpPair = _ensureUniswapV2Pair(tokenAddress, lt);
        uint256 liquidity = _seedUniswapV2Direct(tokenAddress, lt, lpPair, p.tokensForLP, p.ltFromPair, protectedLT);

        _sweepLTToOwner(lt, protectedLT);

        info.lifecycle = Lifecycle.Graduated;
        $.graduatedPair[tokenAddress] = lpPair;
        delete $.pendingGraduation[tokenAddress];

        LPLock($.lpLock).recordLock(tokenAddress, lpPair, liquidity);

        emit TokenGraduated(tokenAddress, lpPair, liquidity, p.tokensForLP, p.lpBurned, p.unsoldBurned);
    }
```

```text
    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
```

```markdown
- **Virtual token reserve.** At launch, `Pair.reserve0 = totalSupply (1B)` while only `curveSupply = 75%` (750M) of real tokens are transferred to the pair. The other 250M (`LP_RESERVE`) sit in `Bonding` for graduation. This extends the curve beyond the sellable supply, which is what makes dynamic LP seeding work cleanly.
- **Dual trigger.** Phase 1 fires on whichever hits first: `(storedAssetReserve - virtualLtReserve) × exchangeRate ≥ $9K` (USD, for LT pumps) or `IPair.tokenBalance() == 0` (supply, for flat/bear markets). The USD trigger reads STORED reserves so direct LT donations to the pair don't count toward the threshold; the launch-time `virtualLtReserve` is recovered on-the-fly as `Pair.k() / Token.TOTAL_SUPPLY()` (K is set once at mint and never modified by `Pair.swap`). The supply trigger reads live `tokenBalance()`, which is donation-resistant in the opposite direction: token donations only INCREASE the balance and can never satisfy `== 0`, and any donated tokens are unconditionally burned by `_prepareGraduationLiquidity`.
- **Zero-gap LP seeding.** `_prepareGraduationLiquidity` computes `ltFromPair = storedAssetReserve - virtualLtReserve` (the real LT raised by the curve, donation-immune; `virtualLtReserve` is derived from `Pair.k() / Token.TOTAL_SUPPLY()`) and `tokensForLP = ltFromPair × storedTokenReserve / storedAssetReserve` at end-of-phase-1, caching the result. Phase 2 uses the cached value verbatim, so the curve→LP price match is invariant under the tx split. Donated LT stays in the curve pair under the trust assumption that `BONDING_ROLE` is only ever held by `Bonding` and `Bonding` won't call `Router.graduate` again post-graduation.
```
