Confirmed: `Registry.process` validates the HMAC over the request via `Utils::HmacValidator.validate(request)`, but `Request#to_signable_string` returns only `@raw_body`, and `Request#shop` is read separately from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in the signed content.

### Title
Webhook shop-domain header spoofing due to HMAC coverage excluding tenant-identifying header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating an HMAC that covers only the raw request body, while the `shop` value used downstream to attribute the webhook to a specific merchant is read from the `x-shopify-shop-domain` header, which is not part of the signed content. Because a Shopify app's webhook HMAC secret (`Context.api_secret_key`, i.e. the app's `client_secret`) is shared across every shop that installs the app, a valid signature over a given body is valid regardless of which shop the header claims to be from.

### Finding Description
`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it against the `hmac` value [1](#0-0) . For webhooks, `Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `Request#hmac` is parsed from the `hmac-sha256` header [3](#0-2) . Separately, `Request#shop` is read straight from the `shop-domain` header with no cryptographic binding to the signed body [4](#0-3) .

`Registry.process` validates the HMAC and, if it passes, immediately trusts `request.shop` to build `WebhookMetadata` that is handed to the app's registered handler as the tenant identity for that event [5](#0-4) .

The identity binding broken here is: `hmac_valid(body, secret) == true` is treated as equivalent to `shop_header == originating_shop`, but the HMAC secret is the app's single `client_secret`, identical for all shops that installed the app — it is not shop-specific. Consequently:
- `hmac(body, secret)` covers only `body`
- `shop` is read from an unsigned header
- `hmac_valid` says nothing about which shop the header names

Any party who can obtain one validly-signed `(body, hmac)` pair for the app — for example by installing the app on their own shop and receiving a genuine webhook, or observing one via a shared/multi-tenant deployment — can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will dispatch the handler with the attacker-chosen `shop`, causing the host application to process (and potentially persist/act on) data as if it originated from a victim shop.

### Impact Explanation
This crosses the tenant boundary the HMAC check is meant to enforce: it lets an attacker (any developer/merchant who can install or has installed the app) forge which shop a webhook event is attributed to, despite a "valid" HMAC. Since host applications commonly key their session/data lookups by `WebhookMetadata#shop` [6](#0-5) , this can lead to cross-tenant data confusion/access — e.g. an attacker triggering handler logic (order sync, inventory update, uninstall/GDPR-style webhook, etc.) tagged as belonging to a victim shop's session, without ever holding that victim's credentials.

### Likelihood Explanation
The attacker only needs one genuine, unmodified `(raw_body, hmac)` pair from the app (trivially obtainable by installing the target app on any shop they control, or from any prior legitimately received webhook) and the ability to POST to the app's public webhook endpoint with a modified `shop-domain` header — no access token, secret, or victim credential is required. This is fully reachable by an unprivileged internet-facing attacker who has ever interacted with the app.

### Recommendation
Bind the tenant identity into the signed content, or otherwise independently authenticate the `shop` value:
- Prefer verifying via GraphQL Admin API / re-fetching shop context using an access token already on file for that `shop`, rather than trusting the header outright, or
- Where feasible, require the host application to cross-check `request.shop` against a shop it has an active, previously-established session/install record for (already-known shop), and reject unknown/mismatched shops before dispatching to handlers.
- Document prominently in `lib/shopify_api/webhooks/registry.rb` / `request.rb` that `shop` is unauthenticated header data and must not be trusted for authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (or otherwise obtains any one legitimate webhook delivery for the app).
2. Attacker captures the raw POST body and the `x-shopify-hmac-sha256` header from a genuine webhook delivery — this HMAC is valid because it's computed with the app's single shared `client_secret`, not a per-shop secret.
3. Attacker replays the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the secret [2](#0-1) .
5. `Registry.process` proceeds and calls the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , even though the payload never originated from that shop.
