## Title
Fee-on-transfer/deflationary ERC20 inputs are escrowed at nominal (not actual received) amount in the Tron `IntentGatewayV2.placeOrder`, causing escrow insolvency that drains/denies legitimate solver reward redemption - (`evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder()` credits the internal escrow accounting (`_orders[commitment][token]`) with the user-declared, fee-reduced input amount without ever verifying that the contract actually received that amount of tokens. Any user can place an order using a fee-on-transfer/deflationary ERC20 as an input token; the contract will record more tokens as "escrowed" than it actually holds, creating a shortfall that lets an order's beneficiary later drain tokens belonging to other, honestly-funded orders of the same token — directly analogous to the external report's "malicious intent creator drains/denies solver rewards via arbitrary reward token behavior."

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, the non-predispatch escrow branch of `placeOrder` performs: [1](#0-0) 

```
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {

        } else {

        }
        // Store reduced amount (after protocol fees) in escrow
        _orders[commitment][token] += reducedInputs[i].amount;

```

The escrow ledger `_orders[commitment][token]` is credited with `reducedInputs[i].amount` (the *declared* amount minus protocol fee) regardless of how many tokens `safeTransferFrom` actually moved into the contract. For a fee-on-transfer/deflationary token, the contract receives strictly less than `order.inputs[i].amount`, yet the ledger records the full nominal (fee-reduced) amount as if it were received.

This is the exact same class of gap identified in the external report (unchecked reliance on nominal transferred amounts for atypical ERC20 tokens), but manifests through fee-on-transfer semantics rather than a non-reverting `transferFrom`. Notably, the main EVM contract in this same repository already fixes this exact issue by measuring the actual balance delta: [2](#0-1) 

```
} else {
    for (uint256 i; i < inputsLen;) {
        if (order.inputs[i].amount == 0) revert InvalidInput();
        address token = address(uint160(uint256(order.inputs[i].token)));
        if (token == address(0)) {
            ...
        } else {
            uint256 balBefore = IERC20(token).balanceOf(address(this));
            IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
            order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore;
        }
        ...
    }
}
```

The Tron contract's predispatch branch also performs an actual balance check against the dispatcher (`balance = IERC20(token).balanceOf(dispatcher); if (balance < requiredAmount) revert InvalidInput();`), showing the codebase is aware of this hazard class elsewhere, but the direct (non-predispatch) escrow path in the Tron contract omits it. [3](#0-2) 

Because all escrow balances for a given token are drawn from the single shared ERC20 balance held by the contract (`_orders[commitment][token]` is only a bookkeeping mapping, not a real per-order token reserve), any single order that under-collects tokens due to a fee-on-transfer effect creates a debt against the pool. On redemption, `withdraw()` transfers the *recorded* (overstated) amount: [4](#0-3) 

If the first beneficiary to redeem for that token happens to draw down the shared balance, a subsequent legitimate order's solver attempting to redeem the same token can find the contract's actual balance insufficient, causing the low-level `token.call(...)` transfer to fail and revert with `TransferFailed()` — denying that solver their rightful escrowed reward, or in a race, allowing an earlier beneficiary to consume tokens funded by a different, honest order.

### Impact Explanation
High — this allows escrow insolvency for any fee-on-transfer/deflationary ERC20 input token on the Tron gateway, causing solver reward redemption to permanently fail (denial) or be effectively "stolen" from another order sharing the same token pool, matching the "drain/deny solver rewards" impact class from the reference report. Funds already escrowed by honest users become undercollateralized relative to the liabilities recorded in `_orders`.

### Likelihood Explanation
Medium — requires only that an intent creator use (or attackers deploy/select) a fee-on-transfer/deflationary token as an input, which is entirely permitted since `placeOrder` performs no token whitelisting or type-of-token validation, and is directly reachable by any unprivileged user submitting an order transaction.

### Recommendation
Apply the same actual-balance-delta accounting used in `evm/src/apps/IntentGatewayV2.sol` (measure `balanceOf(address(this))` before and after `safeTransferFrom`, and credit `_orders[commitment][token]` with the actual received/reduced amount) to the Tron contract's non-predispatch escrow branch in `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Deploy/select a fee-on-transfer ERC20 token `T` (transfers deliver `amount - fee` to the recipient).
2. User A places a legitimate order via `placeOrder` with `T` as input, `amount = 1000`; contract actually receives `990` `T`, but `_orders[commitmentA][T]` is credited `1000` (minus protocol fee).
3. User B (malicious or simply another normal fee-on-transfer user) places a second order with `T`, again under-delivering tokens to the contract while the ledger records the full nominal amount.
4. Once order A is filled and its `RedeemEscrow`/`withdraw()` is processed first, the beneficiary receives the full recorded `_orders[commitmentA][T]` amount — drawing from the shared, now-undercollateralized `T` balance.
5. When order B's solver later attempts `withdraw()`, the contract's actual `T` balance is insufficient to cover `_orders[commitmentB][T]`, and the low-level transfer fails, reverting with `TransferFailed()` — permanently denying B's solver their reward.
