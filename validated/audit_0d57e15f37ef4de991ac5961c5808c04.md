## Analysis

The `DepositManagerV1.refundDeposit` bug class -- "amount is computed dynamically at execution time based on then-current state, and the operation is irreversible with no minimum-output protection guaranteed" -- has an analog in the `process_withdraw` handler of the Raydium AMM program.

### Title
Withdraw slippage protection is optional and silently skipped, exposing LP withdrawers to value extraction from pool-ratio manipulation - (File: `program/src/processor.rs`)

### Summary
`WithdrawInstruction.min_coin_amount` / `min_pc_amount` are `Option<u64>` fields, and the slippage check in `process_withdraw` is only executed `if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()`. Unlike the swap instructions, where `minimum_amount_out` / `max_amount_in` are mandatory, non-optional fields, a `Withdraw` instruction can be submitted (and is a valid encoding accepted by `AmmInstruction::unpack`) with no minimum-output protection at all.

### Finding Description
`coin_amount` and `pc_amount` paid out to the withdrawing user are computed at execution time from the pool's current vault balances and the PnL-adjusted totals: [1](#0-0) 

The only guard against this dynamically computed, execution-time-dependent value is: [2](#0-1) 

Because both `min_coin_amount` and `min_pc_amount` must be `Some` for the check to run at all, any transaction encoded with `WithdrawInstruction { amount, min_coin_amount: None, min_pc_amount: None }` bypasses slippage protection entirely, as confirmed by the unpack logic that defaults both to `None` together: [3](#0-2) 

The user's LP tokens are burned and the (possibly reduced) `coin_amount`/`pc_amount` transferred out atomically and irreversibly in the same instruction: [4](#0-3) 

Contrast this with the swap instructions, where the equivalent protections are mandatory struct fields rather than optional ones: [5](#0-4) 

This mirrors the reported bug class exactly: an amount is derived from mutable, attacker-influenceable on-chain state at the moment of execution (here, `amm_coin_vault.amount`/`amm_pc_vault.amount` and the PnL/take calculation via `calc_take_pnl`, which any preceding swap in the same block/slot can shift), the payout can silently come in lower than the depositor's true share, and the action (LP burn + fund transfer) is final with no way to "retry" or recover the difference — just as `refunded[_depositId] = true` permanently forecloses a second attempt in the original report.

### Impact Explanation
A user submitting a `Withdraw` instruction without setting `min_coin_amount`/`min_pc_amount` (which the on-chain program permits and does not enforce as mandatory) has zero protection against the pool's coin/pc ratio being moved against them between transaction construction and execution — e.g., by a swap that lands immediately before the withdrawal in the same or an adjacent slot. The withdrawer's LP tokens are burned for a `coin_amount`/`pc_amount` that can be significantly less than the value they held immediately prior, and this loss is realized and finalized in a single atomic instruction with no recourse. This is a direct loss of LP-holder funds.

### Likelihood Explanation
Likelihood is Medium: exploitation requires only a permissionless swap transaction ordered adjacent to the victim's withdrawal (any address can call `SwapBaseIn`/`SwapBaseOut`), and the vulnerable path is reached whenever a withdrawer (or any wallet/integration built on top of the program) omits the optional min amounts — which the protocol itself does not require, unlike for swaps.

### Recommendation
Make `min_coin_amount` and `min_pc_amount` mandatory (non-`Option`) fields on `WithdrawInstruction`, consistent with how `minimum_amount_out`/`max_amount_in` are mandatory on the swap instructions, so that every withdrawal is required to carry slippage protection rather than making it an easily-omitted opt-in.

### Proof of Concept
1. Victim submits `Withdraw { amount: X, min_coin_amount: None, min_pc_amount: None }` (a validly encoded instruction per `AmmInstruction::unpack`, `program/src/instruction.rs:372-386`).
2. Attacker observes the pending transaction and submits a large `SwapBaseIn`/`SwapBaseOut` that shifts `amm_coin_vault.amount`/`amm_pc_vault.amount` just before the victim's transaction lands.
3. `process_withdraw` computes `coin_amount`/`pc_amount` from the now-skewed vault balances (`program/src/processor.rs:1719-1761`); because both min fields are `None`, the check at `program/src/processor.rs:1779-1786` is skipped entirely.
4. The victim's LP tokens are burned and the reduced `coin_amount`/`pc_amount` transferred out (`program/src/processor.rs:1787-1812`), permanently realizing the loss with no possibility to retry or recover the shortfall.
