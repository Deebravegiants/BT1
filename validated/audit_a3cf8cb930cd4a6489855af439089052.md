### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values that are subsequently trusted and handed to the app's webhook handler are read from HTTP headers that are **not** covered by that HMAC. Any actor who can obtain one validly-signed webhook body/HMAC pair from Shopify (e.g., by installing the app on their own store) can replay that same body+HMAC to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to name a different (victim) shop, and the signature check will still pass.

### Finding Description
`Registry.process` performs authentication like this: [1](#0-0) 

The HMAC is validated via `Utils::HmacValidator.validate(request)`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For a webhook `Request`, `to_signable_string` returns **only the raw body**: [3](#0-2) 

Meanwhile, `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from HTTP headers and are never included in the signed material: [4](#0-3) 

After the (body-only) HMAC check passes, `Registry.process` immediately trusts `request.shop` as the tenant identity and forwards it, unauthenticated, to the app's handler: [5](#0-4) 

This is exactly the identity-binding break called out in the rules: **a field (`shop`) that is acted upon (used as the tenant key passed to `WebhookMetadata`/the handler) but is not covered by the HMAC** that is supposed to authenticate the request. The equality that should hold is:

`bytes verified by HMAC == bytes that determine the trusted shop identity`

but in this code:

`bytes verified by HMAC (raw_body only) != bytes that determine shop identity (X-Shopify-Shop-Domain header, unauthenticated)`

### Impact Explanation
Because the API secret (`Context.api_secret_key`) used to sign webhooks is shared across every shop that has the app installed, any shop that installs the app can capture one legitimately Shopify-signed webhook (body + `X-Shopify-Hmac-Sha256`). That attacker-controlled shop can then replay the identical body/HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and, if desired, `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header value to point at a victim shop. `Registry.process` will accept it as authentic (HMAC still validates, since only the body is signed) and hand `WebhookMetadata` down to the app's handler labeled with the victim's shop domain. Any app logic that uses this `shop` value to look up sessions, update per-tenant records, trigger billing actions, or store data keyed by shop enables cross-tenant data corruption or disclosure — an authentication/tenant-isolation bypass for the webhook channel.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on any Shopify store (something any internet user with a Shopify account can do, at no special privilege), (2) triggering one webhook event and capturing its raw body and `X-Shopify-Hmac-Sha256` header, and (3) resending that exact body with a forged shop header to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is required — only the ability to be a normal (self-service) merchant of the target app, which matches the "unprivileged internet user" threat model. This is straightforward to script and does not depend on race conditions or unusual timing.

### Recommendation
Bind the shop (and ideally topic/webhook id) identity into the signed material, or otherwise independently authenticate it:
- Include the `shop-domain` (and other trusted header fields the app relies on) in `to_signable_string`/the HMAC computation, matching what Shopify actually signs, or
- Cross-check that the `shop-domain` header corresponds to a shop with a valid, previously-established session/webhook registration for that specific webhook id/topic before trusting it, rather than trusting the header value unconditionally once the body-only HMAC passes.

```diff
// lib/shopify_api/webhooks/request.rb
       sig { override.returns(String) }
       def to_signable_string
-        @raw_body
+        # bind headers that are trusted downstream (e.g., shop) into the signable material,
+        # or validate `shop` against known Shopify domain patterns / an out-of-band trust source
+        @raw_body
       end
```
(Exact remediation depends on what signal Shopify actually signs; at minimum, apps built on this gem should be warned in-code/doc that `shop` from `WebhookMetadata` is not cryptographically bound to the HMAC and must not be trusted as the sole tenant key.)

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the target app installed.
# Step 1: capture a real webhook fired by Shopify for the attacker's own shop.
raw_body = '{"id": 1, "note": "legit order for attacker shop"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Step 2: replay the identical body + hmac, but forge the shop-domain header to the victim.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- forged, not covered by HMAC
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Step 3: this passes HMAC validation because it only checks raw_body, and the handler
# now believes this event legitimately came from "victim-shop.myshopify.com".
ShopifyAPI::Webhooks::Registry.process(request)
```
`Registry.process` does not raise `Errors::InvalidWebhookError`; the handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` despite the event actually having originated for `attacker-shop.myshopify.com`. [1](#0-0)
