### Title
Sustained high-utilization accrual overflows the i128 RAY value ceiling and permanently freezes a market — no repay, withdraw, or liquidation can execute - (File: common/src/math/fp_core.rs)

### Summary
The MySQL CVE's bug class is a hang/crash that permanently disables a component. The direct analog in XOXNO Lending is reachable by any unprivileged supplier/borrower pair: once a market's scaled RAY principal is large enough, interest accrual inside `scaled_to_original` overflows `i128` and panics with `MathOverflow`. Because every state-changing verb accrues the market first, the entire market freezes — supplies cannot be withdrawn, debts cannot be repaid or liquidated — even though the `MAX_BORROW_INDEX_RAY` cap was intended to bound index growth. The test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates that the index cap never engages before the value overflow.

### Finding Description
`Cache::calculate_utilization` and every accrual path convert scaled RAY shares back to asset value via `scaled_to_original(&env, scaled, index)` in `contracts/pool/src/cache/scale.rs` (lines 23-24). That helper multiplies the scaled share amount (already in 1e27 RAY units) by the index (also ~1e27), dividing by RAY — an `x * y / d` computed by `mul_div_half_up`/`try_mul_div_half_up` in `common/src/math/fp_core.rs:122-143`. The widened `I256` path is exact, but the final `.to_i128()` returns `None` when the quotient exceeds `i128::MAX`, and `mul_div_half_up` panics with `GenericError::MathOverflow` (lines 108-118, 300-303).

A billion whole tokens at 18 decimals is `1e36` raw ray; `i128::MAX` is only ~170× that. On a steep utilization curve, a few years of accrual push `scaled * index / RAY` past `i128::MAX` while `borrow_index` is still below `MAX_BORROW_INDEX_RAY`, so the index cap — the mechanism designed to stop exactly this runaway — is never reached (test lines 315-360). Every market verb (`supply`, `withdraw`, `borrow`, `repay`, `liquidate`, `clean_bad_debt`, flash paths, `update_indexes`) loads the `Cache` and accrues before touching state, so all of them revert on the same panic.

An unprivileged attacker can set this up alone: `supply` a large amount into a low-decimals-cap-listed market, `borrow` near maximum against collateral in a second market (driving utilization to the steep rate segment), then simply wait — or keep the position healthy enough that no one can profitably intervene — until accrual crosses the cliff. `update_indexes` is permissionless and the cliff is time-driven, so the attacker can also trigger it by calling `update_indexes` once time has elapsed.

### Impact Explanation
Permanent freezing of funds and protocol insolvency for the affected market: all supplier principal is locked (withdraw reverts), all debt is unrepayable and unliquidatable (repay/liquidate revert), and the bad-debt `clean_bad_debt` path also accrues first. The harness test confirms `try_withdraw_raw` and `try_repay` both fail with `MATH_OVERFLOW` after the cliff (lines 354-356). This matches the "permanent freezing of funds" acceptance criterion exactly.

### Likelihood Explanation
Medium likelihood, high cost to trigger. It requires a whale-scale deposit (~10^9 tokens at 18 decimals, or proportionally less at lower caps if the listing's `max_cap_for_decimals` permits it) and sustained near-max utilization for years on a steep curve — precisely what the documented threat-model row "Tamper.6 / numeric limits" flags as an unresolved residual: "Finite RAY value capacity can be exhausted before the index ceiling" (`docs/explanation/threat-model.md:319-324`). No privileged action, oracle manipulation, or external dependency is needed; the attacker needs only capital and patience, and the test proves the cliff is reached well before the 40-year bound.

### Recommendation
Bound the RAY value, not just the index: enforce market supply/borrow caps so that `scaled_ray * worst-case index` stays below `i128::MAX` for the listing's maximum horizon, or clamp accrual at `MAX_BORROW_INDEX_RAY` *before* `scaled_to_original` can overflow (e.g., saturate the stored index and skip further multiplication once capped). Alternatively, make `scaled_to_original` saturate rather than panic on the accrual path so exits remain possible, and recompute `max_cap_for_decimals` against the steep-segment rate curve for every listed market.

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-360
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);          // unprivileged supply
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);             // 98% utilization

loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// -> MATH_OVERFLOW while borrow_index < MAX_BORROW_INDEX_RAY
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```
