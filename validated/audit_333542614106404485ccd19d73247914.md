Webhook `shop` (tenant identity) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` fields from raw, unauthenticated HTTP headers, while `Utils::HmacValidator` only verifies the request's raw body against the app's shared `api_secret_key`. Because the signature never binds the `shop-domain` header to the signed body, an unprivileged app user who installs the app on their own store can capture a validly-signed webhook body and replay it with a forged `shop-domain` header claiming to be a different (victim) merchant, and `ShopifyAPI::Webhooks::Registry.process` will accept it and hand the forged tenant identity to the host app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from HTTP headers, which are never included in the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (i.e. the body) and compares it with the `hmac` header value, using the app-level `Context.api_secret_key` (the same secret for every shop that has installed the app, not a per-shop credential): [3](#0-2) 

`Registry.process` calls this validator, and once it passes, forwards `request.shop` — taken straight from the unauthenticated header — into `WebhookMetadata`, which is the sole tenant-identifying field given to the host application's handler: [4](#0-3) [5](#0-4) 

The broken identity binding, stated as an equality that must hold but doesn't:
`shop that produced/authorized the signed body == shop asserted in the "shop-domain" header trusted by Registry.process`

Since the HMAC secret (`api_secret_key`) is shared across every shop using the app (it is the app's client secret, not a per-installation secret), any merchant who installs the app on their own store is a legitimate holder of validly-signed webhook payloads for that secret. Such an unprivileged, self-installing attacker can:
1. Trigger/observe a real webhook delivery to their own endpoint (valid body + valid `x-shopify-hmac-sha256`, computed with the same shared `api_secret_key`).
2. Replay the identical `raw_body` and `hmac` header value to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` passes `request.shop == victim-shop.myshopify.com` to the host app's handler as if Shopify itself had sent that webhook for the victim shop.

This lets an attacker inject events/data attributed to another merchant's tenant into the host application, which is a cross-tenant identity/authentication boundary crossing entirely enabled by this gem's webhook-processing code — the host app never has a chance to detect the forgery because the library asserts `request.shop` as trustworthy immediately after successful HMAC validation.

### Impact Explanation
This breaks tenant isolation: any app-installing user can impersonate a different Shopify merchant to the app's webhook pipeline, causing the host app to process attacker-controlled data (order/product/customer payloads, etc.) as if it originated from the victim's store. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to select data scoping, to look up per-shop settings, to write to per-shop records), this can lead to cross-tenant data corruption, unauthorized writes into another merchant's records, or triggering shop-scoped business logic against the wrong tenant — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High. No privileged credentials, TLS interception, or social engineering are required — only the ability to install the app on one's own store (a normal, unprivileged action available to any merchant) and to send an HTTP request with a crafted header to the app's public webhook endpoint. The attacker fully controls both the header value and can reuse any body/HMAC pair they legitimately received.

### Recommendation
Bind the tenant identity into the authenticated material. Concretely:
- Include the `shop-domain` (and ideally `topic`, `webhook_id`, `api_version`) header values in `to_signable_string`, or otherwise cryptographically bind them to the signed payload, so that a mismatch between the signed shop and the asserted shop causes `HmacValidator.validate` to fail.
- Alternatively/additionally, require the caller of `Registry.process` to supply the expected shop (e.g., from an authenticated session or the app's own installation record) and assert equality with `request.shop` before invoking the handler, rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` (a normal installation flow, no special privilege needed).
2. Shopify sends a legitimate webhook to the app's endpoint:
   - Body: `{"id":123, ...}`
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid signature of body with shared api_secret_key>`, `x-shopify-topic: orders/create`
3. Attacker intercepts/logs this request (they own the endpoint receiving it) and replays it to the same endpoint but changes only the header:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - Body and `x-shopify-hmac-sha256` are left unchanged.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged headers; `Utils::HmacValidator.validate(request)` succeeds because it only recomputes the HMAC over `raw_body`, which is unchanged. [6](#0-5) 
5. `Registry.process(request)` calls the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: {...}, ...)`, and the host application processes attacker-controlled data as though it came from `victim-shop.myshopify.com`. [7](#0-6)
