Confirmed: `ShopifyAPI::Webhooks::Request#shop` (`lib/shopify_api/webhooks/request.rb:20-23`) reads the `shop-domain` header directly, while `to_signable_string` (used for HMAC verification) returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`). `Registry.process` validates the HMAC over the body only (`lib/shopify_api/webhooks/registry.rb:190`) and then forwards the unauthenticated `request.shop` header value straight into `WebhookMetadata` (`lib/shopify_api/webhooks/registry.rb:198-199`), which is documented as the trusted tenant identifier (`docs/usage/webhooks.md:13-14`, `WebhookMetadata` at `lib/shopify_api/webhooks/webhook_handler.rb:6-12`).

### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Finding Description
Shopify signs a webhook's HMAC over the raw request body only. `ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the signature only against that signable string [2](#0-1) . However, `Request#shop` is read straight from the `shop-domain` header, which is never included in the signed bytes [3](#0-2) .

`Registry.process` treats a valid body HMAC as proof of the entire request's authenticity, then forwards the unauthenticated `request.shop` value into `WebhookMetadata` handed to the app's handler as the tenant identifier: [4](#0-3) . This binds "HMAC verified" to "body integrity" but the app-level identity binding actually required is "shop the data belongs to == shop reported to the handler" — and that equality is never checked.

Because every shop that installs the app shares the same `api_secret_key` (single global app secret, `Context.api_secret_key` in `lib/shopify_api/utils/hmac_validator.rb:16`), any merchant who installs the app can legitimately receive a real webhook for their own shop, complete with a valid `hmac-sha256` header for that specific body. That attacker-merchant can then resend the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `shop-domain` header (and optionally `webhook-id`/`topic`, which are also unauthenticated per `Request#topic`/`Request#webhook_id`, lines 15-18 and 30-33) to name a victim shop. `Utils::HmacValidator.validate(request)` still returns `true` because it only checks the raw body [5](#0-4) , so the forged request is accepted and dispatched to the handler as if it were genuine data belonging to the victim's shop.

### Impact Explanation
This breaks the tenant boundary the gem's documented webhook API relies on: `data.shop` in `WebhookMetadata` is documented as "The shop domain of the webhook" and is the field host apps are expected to use to attribute/store incoming webhook data per-tenant [6](#0-5) . An attacker who merely installs the app on their own shop (unprivileged w.r.t. other tenants, no access token or `client_secret` needed) can inject attacker-controlled webhook bodies that the app processes under a victim shop's identity — a cross-tenant data injection using only the gem's documented processing flow, since the gem itself supplies the unauthenticated `shop` value as if it were verified.

### Likelihood Explanation
Requires only: (1) installing the app on an attacker-controlled shop (any developer/merchant can do this, no elevated privileges), and (2) capturing one legitimate webhook (its raw body + `hmac-sha256` header) delivered to that shop's endpoint, then replaying it with a modified `shop-domain` header. No knowledge of `api_secret_key`, access tokens, or other shops' credentials is required.

### Recommendation
Bind the shop domain (and other trust-sensitive headers such as `webhook-id`/`topic`) into the HMAC-verified material, or otherwise cryptographically tie the reported `shop` value to the specific delivery, e.g. by validating it out-of-band against Shopify (registered webhook endpoints/shop lookup) before trusting it, rather than deriving `to_signable_string` from body bytes alone while separately trusting an unauthenticated header for tenant attribution.

### Proof of Concept
1. Install the app on attacker's own shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g. `orders/create`) so Shopify delivers a real webhook with a valid `x-shopify-hmac-sha256` computed over the raw body using the app's shared `api_secret_key`.
2. Capture the raw request: `raw_body` and `x-shopify-hmac-sha256` header value.
3. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — it succeeds (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/webhooks/request.rb:36-38`).
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's body>, ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) and processes/stores attacker data as belonging to the victim shop.
