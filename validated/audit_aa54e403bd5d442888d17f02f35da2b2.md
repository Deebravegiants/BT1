### Title
Webhook shop-domain, topic, and webhook_id headers are not covered by HMAC verification, allowing tenant/topic spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop`, `topic`, and `webhook_id` values taken directly from HTTP headers that are never included in the signed data. The identity binding "verified sender == header-derived tenant/topic" does not hold, letting an unprivileged sender who possesses one valid `(raw_body, hmac)` pair replay it with arbitrary `shop-domain`/`topic`/`webhook-id` headers and still pass verification.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers, independently of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string`, i.e., the body: [3](#0-2) 

`Registry.process` gates entirely on that body-only HMAC check, then trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived, unsigned) to route and label the event to the handler: [4](#0-3) 

The equality broken is: **bytes verified (raw body via HMAC) != bytes acted on (shop/topic/webhook_id headers used for tenant attribution and dispatch)**. Any party capable of sending arbitrary HTTP requests to the app's public webhook endpoint (an unprivileged network attacker) can take a `(raw_body, hmac)` pair that is valid for the app's secret — for instance one legitimately generated by Shopify for the attacker's own store — and re-POST it with a different `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because it only checks the body/secret relationship, and `Registry.process` will invoke the handler with `data.shop` set to the attacker-chosen victim shop domain while `data.body` is fully attacker-controlled content originally signed for the attacker's own store.

### Impact Explanation
This breaks the tenant identity binding used by every app handler (`WebhookMetadata#shop`) to decide which merchant's data the event belongs to. An attacker can cause the app to process attacker-controlled webhook payloads under a spoofed victim shop identity — a cross-tenant confusion analogous to the pool's `_tokens` amounts being trusted without their sum being properly bound to `msg.value` in the reported Solidity issue. Similarly here, the "amount" analog (shop/topic identity) is acted upon by the handler without being bound to the value that was actually verified (the body/HMAC pair).

### Likelihood Explanation
Webhook endpoints are unauthenticated-by-design public HTTP endpoints (any caller can POST to them; that's exactly how Shopify itself delivers webhooks), so no privileged access or secret key is needed by the attacker — they only need one legitimately-signed `(body, hmac)` pair, which is trivial for an attacker to obtain since they can install the app on their own store and observe the webhook Shopify sends them.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the signed/verified string, or independently verify that the `shop-domain` header matches an expected/registered shop for the app before dispatching to the handler. At minimum, document that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for tenant isolation without additional verification by the host application.

### Proof of Concept
```ruby
# Attacker installs the app on their own store "attacker.myshopify.com" and
# receives (or crafts within their own store's control) a legitimately
# signed webhook body + HMAC from Shopify for topic "orders/create".

raw_body = '{"id":1,"note":"malicious content"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the same (raw_body, hmac) but swaps the shop-domain header
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: spoofed_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate passes (body/secret match); handler.handle is invoked
#    with data.shop == "victim-shop.myshopify.com" even though the payload
#    was never signed for that shop.
```
