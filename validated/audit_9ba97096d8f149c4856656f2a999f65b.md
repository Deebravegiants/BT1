Webhook `shop-domain` (and `topic`/`webhook_id`) header is trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by HMAC-verifying the raw request body, but the tenant-identifying `shop` value (and `topic`/`webhook_id`) that the handler acts on are read from unauthenticated HTTP headers that are never part of the signed bytes. An attacker who can produce (or replay) any valid `(raw_body, hmac)` pair for the app's secret can freely substitute the `shop-domain`, `topic`, and `webhook-id` headers, causing the handler to process the payload under an attacker-chosen shop identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are all derived independently from headers, none of which feed into the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` calls this validator, then immediately builds `WebhookMetadata` from the request's unauthenticated `shop`, `topic`, `webhook_id`, and `api_version` accessors and dispatches it to the app's handler: [4](#0-3) 

The equality the gem implicitly claims to enforce is: *the shop bound to the HMAC-signed bytes == the shop passed to the handler*. In reality: `hmac == HMAC(raw_body)` says nothing about `shop`, `topic`, or `webhook_id`, since those are read from `@headers["x-shopify-shop-domain"]` etc., completely outside the signed payload: [5](#0-4) 

Because the JSON body for many webhook topics is legitimately identical or attacker-influenced across shops (e.g., a shop can trigger `orders/create` webhooks with a body content it partly controls, or two different apps/installations can observe the same signed body for events with generic payloads), and because `hmac-sha256` is computed with the app's own `client_secret` (shared across all shops that installed the app), any request bearing a body+HMAC pair the attacker has legitimately observed for their own shop can be replayed with the `x-shopify-shop-domain` header swapped to point at a victim shop. `HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop.

### Impact Explanation
This breaks the identity binding host applications rely on: they use `data.shop` from `WebhookMetadata` (per the gem's own documented usage) to select which merchant/tenant record to update, exactly as shown in the gem's docs (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [6](#0-5) 

Since the gem provides no cryptographic assurance that `shop` corresponds to the entity that produced the signed body, an attacker controlling one installation of the app can forge webhook deliveries that appear to originate from a different shop, leading to cross-tenant data corruption/access in any host application that trusts `data.shop` for authorization or record lookup (as the gem's docs instruct). This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to have valid app credentials for at least one shop installation (to obtain a legitimately-signed body/HMAC pair) and to be able to submit HTTP requests with attacker-controlled headers directly to the app's webhook endpoint (bypassing/spoofing Shopify's delivery, which is possible since nothing in this gem binds the request to Shopify's infrastructure beyond the HMAC over the body). This is a realistic capability for an unprivileged internet user who has installed the app on their own store and can then send crafted HTTP requests to the merchant's public webhook callback URL.

### Recommendation
Include the identity-binding fields (`shop`, `topic`, and ideally `webhook_id`) in the HMAC-signed payload verification, e.g., by validating a canonical string built from headers + body (similar to how `AuthQuery#to_signable_string` binds `shop`/`host`/`state` into the OAuth HMAC), or by requiring the host application to independently corroborate `shop` against a known session/installation before trusting `data.shop`. At minimum, document prominently that `data.shop` is unauthenticated header data and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook for topic `orders/create` with body `{}` (or any body they can trigger), together with its valid `x-shopify-hmac-sha256` header computed from the app's shared `client_secret`.
2. Attacker replays this exact `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers without validating any cross-consistency between `shop` and `hmac`: [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes HMAC over `raw_body`: [7](#0-6) 
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-forged `shop` header and dispatches to the app's handler as if it were a genuine event from `victim-shop.myshopify.com`: [8](#0-7)
