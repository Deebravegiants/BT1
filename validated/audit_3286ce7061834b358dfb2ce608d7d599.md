### Title
`ConnectedOrigins#getConnectedAccounts` ignores the stored `walletAccount` scope and discloses addresses for every enabled wallet account - ([File: features/connected-origins/module/connections.js])

### Summary
`ConnectedOrigins.add()` persists a per-connection `walletAccount` field intended to scope which wallet account a trusted origin may access [1](#0-0) . However, `getConnectedAccounts` never reads or filters on `value.walletAccount`; it only checks `isTrusted` and filters by asset name, then returns addresses for *all* wallet accounts present in `connectedAccountsAtom`, which is populated from `enabledWalletAccountsAtom` for every enabled account [2](#0-1) .

### Finding Description
- `add({ origin, walletAccount, trusted, ... })` stores `walletAccount` as an attribute on the connection entry, implying per-origin wallet-account scoping is a supported concept [3](#0-2) .
- `#getAccounts(assetNames)` builds the account cache by iterating **every** entry of `enabledWalletAccountsAtom.get()`, with no per-origin/account filtering — this is expected since it's a shared cache for all origins [4](#0-3) .
- The actual authorization boundary should be enforced in `getConnectedAccounts`, but that method only checks `isTrusted({ origin })` and computes `assetNames` from `value.connectedAssetName`/`value.assetNames`. It then loops over `Object.keys(accounts)` (i.e., every enabled wallet account name in the shared `connectedAccountsAtom`) and returns all of them, only re-ordering so the active wallet account comes first [2](#0-1) . The `value.walletAccount` field set during `add()` is never consulted here.
- The existing test `returns connected accounts with active wallet account first` demonstrates this behavior concretely: an origin connected via `add()` (with no explicit account restriction in that test) still gets back both `exodus_0` and `exodus_1` addresses [5](#0-4) . Since `getConnectedAccounts` has no code path that special-cases a `walletAccount`-scoped connection, calling `add({ origin, walletAccount: 'exodus_1', trusted: true })` and then `getConnectedAccounts({ origin })` produces the identical result — addresses for `exodus_0`, `exodus_1`, and any other enabled account are all returned, not just `exodus_1`.
- No other guard exists between the dapp-facing API (`features/connected-origins/api/index.js`, which directly re-exports `connectedOrigins.getConnectedAccounts`) and this implementation [6](#0-5) .

### Impact Explanation
An origin that a user explicitly consented to trust for a single wallet account can enumerate receive addresses for all other enabled wallet accounts belonging to the same user, including accounts the user never intended to expose to that dapp. This is a wrong-account-scope / cross-account address disclosure — a privacy and unauthorized-account-access issue (not a key/fund compromise), matching a "wrong-account access" / information-disclosure bounty category.

### Likelihood Explanation
Highly feasible: requires only (1) multiple wallet accounts enabled (an ordinary user configuration) and (2) a single `connectedOrigins.add()` call scoping trust to one account — both are normal, unprivileged flows reachable by any dapp using the standard connect API. No auth bypass, key leakage, or special preconditions beyond ordinary multi-account usage are needed, and the behavior is deterministic/repeatable on every `getConnectedAccounts` call.

### Recommendation
In `getConnectedAccounts`, filter the account cache by the connection's stored `value.walletAccount` when present, e.g. only include `accounts[value.walletAccount]` (plus, if desired, the active wallet account only when it matches the stored scope), instead of iterating over `Object.keys(accounts)` unconditionally. If `walletAccount` is undefined (legacy/unscoped connections), document and gate that fallback behavior explicitly rather than treating it as "all accounts" by default.

### Proof of Concept
Integration test in `features/connected-origins/module/__tests__/connections.test.js`:
1. Enable two wallet accounts (`exodus_0`, `exodus_1`) as in existing `beforeEach`.
2. Call `connectedOrigins.add({ origin: 'exodus.com', connectedAssetName: 'solana', walletAccount: 'exodus_1', trusted: true })`.
3. Call `const accounts = await connectedOrigins.getConnectedAccounts({ origin: 'exodus.com' })`.
4. Assert `accounts` contains only `{ name: 'exodus_1', addresses: {...} }` and does NOT contain an entry for `exodus_0`.
5. Current code fails this assertion, returning both `exodus_0` and `exodus_1` entries, demonstrating the leak.

  getConnectedAccounts = async ({ origin }) => {
    const isTrusted = await this.isTrusted({ origin })
    if (!isTrusted) return []

    const value = await this.#getOrigin({ origin })
    const assetNames = [value.connectedAssetName, ...(value.assetNames ?? [])].filter(
      (name, index, ary) => Boolean(name) && ary.indexOf(name) === index
    )

    const activeWalletAccount = await this.#activeWalletAccountAtom.get()
    const accounts = await this.#connectedAccountsAtom.get()

    const connectedAccounts = []
    for (const name of Object.keys(accounts)) {
      if (name === activeWalletAccount) continue
      connectedAccounts.push({ name, addresses: pick(accounts[name].addresses, assetNames) })
    }

    connectedAccounts.unshift({
      name: activeWalletAccount,
      addresses: pick(accounts[activeWalletAccount].addresses, assetNames),
    })

    return connectedAccounts
  }
