### Title
No Rate-Limiting or Lockout on PIN Verification Allows Unlimited Brute-Force of `auth.isCorrectPin` - (File: features/auth-mobile/module/auth.js)

### Summary
The external report describes a security checkpoint (Vercel WAF) that fails to escalate blocking beyond a single browser profile/session, letting an attacker trivially reset the "challenge" state and keep attacking. The closest reachable analog in this codebase is the mobile PIN authentication module `@exodus/auth-mobile`, whose `isCorrectPin` check has **no attempt counter, delay, or lockout at all** — a weaker version of the same bug class (a security checkpoint gate with no effective escalation/throttling against repeated verification attempts).

### Finding Description
`Auth#isCorrectPin` simply compares the input against the stored PIN secret with no state tracking of failed attempts: [1](#0-0) 

There is no companion mechanism anywhere in the module (`setPin`, `removePin`, `clear`, `#mergeIntoAtom`) that records failed attempts, throttles retries, or locks the wallet after N wrong guesses: [2](#0-1) [3](#0-2) 

A repo-wide search for `attempts`, `lockout`, `maxAttempts`, and `failedAttempts` found no matches anywhere in the `auth-mobile` feature (or any other auth-related module), confirming that attempt-limiting logic simply does not exist in this codebase — it is entirely left to whatever UI layer calls `isCorrectPin`. This mirrors the WAF report's root cause: the "checkpoint" (PIN gate) is not backed by any server/attempt-tracking mechanism, and any layer that resets or bypasses the caller-side state (app restart, in-memory UI counter reset, or a UI variant that doesn't implement its own throttling) fully defeats the checkpoint — just as clearing cookies/using a new profile defeats the Vercel checkpoint.

The `auth` module is registered as `public: true`, exposing `isCorrectPin` directly on the SDK's public surface (`exodus.auth.isCorrectPin`) for any UI/consumer code to call without restriction: [4](#0-3) 

### Impact Explanation
Because the module itself enforces no lockout, the security of the PIN gate depends entirely on whichever UI happens to wrap it. If any consuming app (or a future/alternate UI, a compromised renderer, or an automated script driving the app) calls `exodus.auth.isCorrectPin` directly and repeatedly, it can brute-force a 6-digit numeric PIN (only 1,000,000 combinations, validated via `InvalidPasscodeLengthError` requiring exactly length 6) with no throttling, exactly as the WAF bypass allowed unrestricted repeated attempts once profile state was reset. Since `shouldAuthenticate` — and by extension access to sensitive wallet operations — is gated purely on this boolean PIN check, successful brute force here effectively acts as an auth bypass to unlock protectworthy resources (e.g. seed/mnemonic access, as noted in the module's own docs: "indicator for the UI to restrict access to protectworthy resources such as the mnemonic phrase").

### Likelihood Explanation
The precondition is local/device access to a running SDK instance with a PIN set and biometric auth not relied upon exclusively (i.e., an attacker with physical/local access to the unlocked app process or a script able to invoke the public SDK API), which is a realistic unprivileged-attacker scenario for mobile wallets (e.g., stolen/unlocked device, or a malicious co-located app/script able to call into the SDK). No network or privileged credentials are required, and the vulnerability is unconditional since the module never implements throttling regardless of caller.

### Recommendation
Implement attempt tracking and progressive lockout directly inside the `Auth` module (not left to the UI layer), e.g.:
- Persist a failed-attempt counter in the keystore alongside `AUTH_KEYSTORE_PIN_KEY`.
- Increment on each wrong `isCorrectPin` call, reset only on success.
- Apply exponential backoff / temporary lockout after N consecutive failures, and require full wipe/reset (or biometric-only re-auth) after a hard threshold, mirroring the report's recommended "progressive challenge escalation."

### Proof of Concept
```js
// Any caller with access to the public SDK surface can brute-force the PIN
// with zero throttling, since isCorrectPin has no attempt tracking:
for (let i = 0; i <= 999999; i++) {
  const guess = String(i).padStart(6, '0')
  const ok = await exodus.auth.isCorrectPin(guess)
  if (ok) {
    console.log('PIN found:', guess)
    break
  }
  // no delay, no lockout, no error after any number of failures
}
```
This is directly reachable because `isCorrectPin` in `features/auth-mobile/module/auth.js:128-131` performs a bare secret comparison with no rate limiting, and no other part of the module or its tests implement such controls.

  #mergeIntoAtom = async (params) => {
    await this.#authAtom.set((current) => {
      const data = {
        ...current,
        ...params,
      }

      const { hasBioAuth, biometry, hasPin, hasDeviceAuth } = data

      data.hasBioAuth = hasBioAuth && !!biometry
      data.shouldAuthenticate = hasDeviceAuth || hasBioAuth || hasPin

      if (isEqual(current, data)) return current

      this.#logger.info('Updated auth data', data)
      return data
    })
  }
