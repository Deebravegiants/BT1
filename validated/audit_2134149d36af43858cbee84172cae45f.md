### Title
Fungible-asset freeze bypass via dual CoinStore/FungibleStore custody paths - ([File: aptos-move/framework/aptos-framework/sources/coin.move])

### Summary
The external bug is fundamentally about **decoupled authority over the same custodied value**: updating a reference (which contract is "live") does not retroactively revoke the ability of the stale path to keep moving funds, so two paths can custody the same asset in parallel. The Aptos-native analog is the coexistence of the legacy `coin::CoinStore<CoinType>` and the AIP-typed `fungible_asset::FungibleStore` for the *same* coin/FA identity. Freeze state is tracked as two **independent** `frozen` booleans on two different resources, and only the migration helper reconciles them — normal operation does not.

### Finding Description
`coin.move` maintains a `CoinConversionMap` pairing every `CoinType` with an FA `Metadata` object [1](#0-0) . A holder's total balance is the **sum** of the legacy `CoinStore<CoinType>.coin.value` and the FA primary store balance [2](#0-1) , meaning both representations are simultaneously valid, spendable custody records for the same economic value.

Each representation has its **own, separate** `frozen` flag: `CoinStore<CoinType>.frozen` (legacy) and `FungibleStore.frozen` (`fungible_asset.move`, gated by `TransferRef`/`set_frozen_flag`) [3](#0-2) . The only place the framework itself acknowledges and reconciles this split is inside the one-time migration helper `maybe_convert_to_fungible_store`, which explicitly notes the inconsistent-frozen-state scenario and patches it up *only during migration*: [4](#0-3) 

Outside of that migration path, nothing keeps the two `frozen` fields synchronized. `primary_fungible_store`/`dispatchable_fungible_asset` withdraw/deposit/transfer paths check only `FungibleStore.frozen` [5](#0-4) , while legacy `Coin<CoinType>` operations check only `CoinStore.frozen`. A user can independently create/hold value in the FA form (e.g. via `coin_to_fungible_asset` + `primary_fungible_store::deposit`, or by simply receiving an FA transfer to their primary store) without ever touching their `CoinStore`. If an issuer with `FreezeCapability<CoinType>` freezes the account intending to halt all of that account's holdings of `CoinType`, but the freeze primitive only mutates `CoinStore<CoinType>.frozen`, the account's FA-form balance of the *same* paired asset remains unfrozen and fully transferable through `primary_fungible_store::transfer`/`dispatchable_fungible_asset::transfer`.

### Impact Explanation
This breaks the intended custody invariant that "freezing an account's holdings of an asset blocks all of that holder's value in that asset," analogous to the zAuction scenario where an old/decoupled path kept accepting value after the reference was supposedly updated. For freeze-gated fungible assets (denylist/compliance-controlled stablecoins, sanctioned-address controls, etc. — see `stablecoin/usdk.move`'s freeze/denylist pattern), an account holding both representations could evade a freeze intended to halt all transfers, moving out the FA-form balance while appearing "frozen" via the legacy `CoinStore` flag. This is a custody/authority-enforcement gap on live mainnet assets (APT and any migrated Coin<T>).

### Likelihood Explanation
Medium: it requires (a) the asset to have a paired Coin/FA representation (true for `AptosCoin` and any legacy `CoinType` with `create_pairing`/migration enabled), and (b) the holder to have value split across both stores, which happens naturally today because migration is voluntary (`migrate_to_fungible_store`) and FA deposits/mints can independently populate the primary store while a `CoinStore` still exists. No special privilege is needed by the holder to exploit the desync — only the freeze issuer needs the normal `FreezeCapability`, and the gap is that their freeze action doesn't propagate across both custody records.

### Recommendation
Make `CoinStore.frozen` and the paired `FungibleStore.frozen` a single, authoritative flag (or have freeze/unfreeze operations on one automatically propagate to the other, the way `maybe_convert_to_fungible_store` already does during migration), so that freezing an account for `CoinType` is guaranteed to also freeze its paired-FA holdings, and vice versa.

### Proof of Concept
1. Issuer has `FreezeCapability<CoinType>` and a paired FA exists (`coin::create_pairing<CoinType>` already invoked).
2. Victim account holds `Coin<CoinType>` in `CoinStore<CoinType>` (frozen target) **and** independently obtains FA-form balance of the same paired metadata (e.g., someone deposits FA directly to the victim's primary store via `primary_fungible_store::deposit`, or the victim calls `coin::coin_to_fungible_asset` + `primary_fungible_store::deposit` themselves before being frozen).
3. Issuer calls `coin::freeze(...)`/equivalent using `FreezeCapability<CoinType>`, setting `CoinStore<CoinType>.frozen = true` for the victim.
4. Victim calls `primary_fungible_store::transfer<Metadata>(victim, paired_metadata, attacker_addr, amount)` — this only checks `FungibleStore.frozen` (still `false`), so the transfer succeeds despite the account being "frozen" from the issuer's point of view.

Note: I was not able to view the exact body of `coin::freeze_coin_store`/`unfreeze_coin_store` in this session (only located via grep matches) to confirm it does not itself synchronize the paired FA store's frozen flag outside the migration helper; this should be verified directly in `aptos-move/framework/aptos-framework/sources/coin.move` before treating this as fully confirmed.

        store: Object<T>, frozen: bool
