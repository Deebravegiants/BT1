### Title
Same-token batch withdrawals on PoaBridge collapse to a single tracked record, causing status/hash misreport — (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain withdrawal record for a given `WithdrawalIdentifier` by matching **only on `assetId`** (`nep141:<near_token_id>`), ignoring the identifier's `index`, `destinationAddress` and `amount`. When a caller batches two withdrawals of the same token to two different addresses through `IntentsSDK.processWithdrawal` / `createWithdrawalCompletionPromises`, both local trackers query the POA bridge with the same NEAR intent tx hash and both get matched to the **first** API record for that token — regardless of which withdrawal it actually belongs to.

### Finding Description
The invariant the question asks to validate is: the `(amount, fee, destinationAddress)` that was signed for withdrawal `i` must be the same tuple that gets *confirmed* for withdrawal `i` at watch time. This holds correctly through signing (fee/amount pairing is strictly positional via `zip` in `signAndSendWithdrawalIntent`, [1](#0-0) , which throws an `AssertionError` on length mismatch), but it breaks at the **watch/report** step.

- `createWithdrawalIdentifiers` assigns a per-bridge `index` to each withdrawal and builds one `WithdrawalIdentifier` per entry, all sharing the same `intentTx` (the single NEAR transaction hash for the whole batch): [2](#0-1) .
- `PoaBridge.createWithdrawalIdentifier` stores that `index` in the identifier but never uses it for matching: [3](#0-2) .
- `describeWithdrawal` fetches the withdrawal list for the shared `tx.hash` and calls `findMatchingWithdrawal`, which matches purely by `assetId`: [4](#0-3)  and [5](#0-4) . The code comment explicitly acknowledges this: "multiple withdrawals of the same token in a single transaction are not supported."

Exploit flow: an unprivileged caller submits `withdrawalParams = [{assetId: T, destinationAddress: X, amount: A}, {assetId: T, destinationAddress: Y, amount: B}]` in one `processWithdrawal`/batch call. `createWithdrawalIntents` correctly signs two distinct `ft_withdraw` intents with correct `amount + fee` per destination — that part is sound (verified in `createWithdrawalIntents`, [6](#0-5) ). But at Step 4 (`waitForWithdrawalCompletion` / `watchWithdrawal`, [7](#0-6) ), both `describeWithdrawal({assetId: T, index: 0, tx})` and `describeWithdrawal({assetId: T, index: 1, tx})` query the same `tx.hash` and both resolve to whichever record `.find()` returns first for token `T`. If that first record is `X`'s completed record with `txHash = H_X`, both promises resolve as "completed" with `txHash = H_X`, even though `Y`'s actual withdrawal may still be pending, failed, or completed with a different hash.

No existing guard prevents this: `supports()`, `validateWithdrawal`, `compareAddresses`, and `FeeExceedsAmountError` all operate per-withdrawal on signing/estimation, not on watch-time identity; nothing rejects a batch containing duplicate `assetId` entries.

### Impact Explanation
The party affected is the integrator/caller polling `destinationTx` for a batch. It can misreport a wrong `txHash`/status for one of the withdrawals in a same-token batch — the exact "status or hash misreport making an integrator credit or refund twice" category (High). No funds are misrouted on-chain (each `ft_withdraw` intent still carries the correct destination and amount), but the SDK's own completion reporting for that withdrawal is unreliable, which can lead an integrator to prematurely credit/release funds tied to the misreported withdrawal, or fail to notice a still-pending/failed withdrawal. This is repeatable on every batch containing ≥2 same-token entries.

### Likelihood Explanation
Preconditions are trivial and require no special access: any caller of the public `processWithdrawal`/`createWithdrawalCompletionPromises` API can construct a batch with two (or more) withdrawals sharing the same `assetId` but different destinations/amounts on the PoA bridge route. No cost beyond normal withdrawal fees; fully repeatable and deterministic given the POA API's response ordering.

### Recommendation
Fix `findMatchingWithdrawal` (and `describeWithdrawal`) in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` to disambiguate matches within the same tx/token by more than `assetId` — e.g., match by `(near_token_id, destination address/memo, amount)` or, if the POA bridge API exposes ordering/indexing, use it via `WithdrawalIdentifier.index`. Until fixed, explicitly reject (throw) batches with duplicate `assetId` values destined to different addresses at `createWithdrawalIdentifiers` time so the caller cannot silently rely on broken tracking.

### Proof of Concept
Vitest plan (mock only HTTP):

2. Build two `WithdrawalIdentifier`s (`index: 0` for X, `index: 1` for Y) via `createWithdrawalIdentifiers` with the same `intentTx`.
3. Call `bridge.describeWithdrawal` for both identifiers.

export async function watchWithdrawal(args: {
	bridge: Bridge;
	wid: WithdrawalIdentifier;
	signal?: AbortSignal;
	logger?: ILogger;
}): Promise<TxInfo | TxNoInfo> {
	const stats = getWithdrawalStatsForChain({
		chain: args.wid.landingChain,
		bridgeRoute: args.bridge.route,
	});
	let consecutiveErrors = 0;

	try {
		return await poll(
			async () => {
				try {
					const status = await args.bridge.describeWithdrawal({
						...args.wid,
						logger: args.logger,
					});

					consecutiveErrors = 0;

					if (status.status === "completed") {
						return status.txHash != null
							? { hash: status.txHash }
							: { hash: null };
					}

					if (status.status === "failed") {
						throw new WithdrawalFailedError(status.reason);
					}

					return POLL_PENDING;
				} catch (err: unknown) {
					if (err instanceof WithdrawalFailedError) {
						throw err;
					}

					consecutiveErrors++;
					if (consecutiveErrors >= MAX_CONSECUTIVE_ERRORS) {
						throw new WithdrawalWatchError(err);
					}

					args.logger?.warn(
						`Transient error (${consecutiveErrors}/${MAX_CONSECUTIVE_ERRORS}): ${err}`,
					);
					return POLL_PENDING;
				}
			},
			{ stats, signal: args.signal },
		);
	} catch (err: unknown) {
		if (err instanceof PollTimeoutError) {
			throw new WithdrawalWatchError(err);
		}
		throw err;
	}
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
