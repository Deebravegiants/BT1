## Analysis

`ShopifyAPI::Webhooks::Registry.process` validates a webhook purely by checking the HMAC over the **raw request body**, and separately trusts the `shop-domain` header for tenant dispatch — but the HMAC signature never covers that header. [1](#0-0) 

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end
...
def to_signable_string
  @raw_body
end
```

`to_signable_string` only returns `@raw_body`; `shop`, `topic`, `webhook-id`, and `api-version` are all read straight from unauthenticated HTTP headers and are never part of the signed material. [2](#0-1) 

`Registry.process` validates only that HMAC, then dispatches the handler using the unauthenticated `request.shop` value: [3](#0-2) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Utils::HmacValidator.validate` authenticates a webhook using only the raw JSON body as signable material (`Request#to_signable_string` returns `@raw_body`). The `shop`, `topic`, `webhook-id`, and `api-version` values that `Registry.process` passes on to the app's handler (`WebhookMetadata`) come from HTTP headers that are entirely outside the HMAC's coverage.

### Finding Description
Because all Shopify apps' webhook HMACs are computed with the same `api_secret_key` regardless of which installed shop triggered the event, any merchant who has the app installed on their own store (an unprivileged internet user with no special access to the app's credentials) can obtain a body+HMAC pair that is valid under the shared secret — simply by owning a shop where they can generate a webhook (e.g. by making an order, or via a "customers/redact"/GDPR-style webhook whose body they can partly influence). They can then replay that exact `raw_body` + `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` still succeeds because it only checks the untouched body, and `Registry.process` forwards the attacker-chosen `shop` value straight to the handler as trusted tenant context.

This is exactly the "field acted on but not covered by the HMAC" identity-binding break called out in scope: the equality the code implicitly assumes — `shop header == shop that produced this signed body` — does not hold, because the signature binds only to the body.

### Impact Explanation
This breaks the tenant boundary the webhook system is supposed to enforce. Any handler that keys destructive or sensitive actions off `WebhookMetadata#shop` (e.g. mandatory `customers/redact`, `shop/redact`, or `app/uninstalled` handlers that revoke sessions or delete stored merchant data for that shop) can be triggered for a victim shop the attacker does not own, using only a webhook the attacker legitimately received for their own shop. This is cross-tenant access/action without ever needing the app's `api_secret_key`, an access token, or the victim's credentials.

### Likelihood Explanation
Any developer/merchant with the app installed on a store they control can obtain a validly-signed webhook body/HMAC pair through normal use of their own shop, then replay it with a forged `shop-domain` header via a simple HTTP client. No special access, secrets, or social engineering is required — only knowledge of the app's public webhook endpoint (which is typically discoverable/documented).

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signable material that `Utils::HmacValidator` verifies, or otherwise independently correlate `request.shop` against a known/registered/expected shop (e.g., validating it belongs to a shop with an active session for this app) before dispatching to handlers. At minimum, document to consumers that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook topic the app subscribes to, capturing the raw request body and the `X-Shopify-Hmac-Sha256` header Shopify sent to the app's endpoint.
2. Attacker sends a new HTTP POST to the same webhook endpoint with:
   - Body: identical to the captured raw body.
   - `X-Shopify-Hmac-Sha256`: identical to the captured header.
   - `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (arbitrary victim domain).
   - `X-Shopify-Topic`: same topic as captured.
3. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13-31`) succeeds because it only compares HMAC over `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), which is unchanged.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-200`) invokes the registered handler with `shop: "victim-shop.myshopify.com"`, letting the attacker trigger tenant-scoped webhook logic for a shop they do not control.
