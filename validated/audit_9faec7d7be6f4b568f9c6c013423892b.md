The gem's webhook signature check only binds the **HTTP body**, not the metadata headers it later trusts. `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes the HMAC exclusively over that signable string [2](#0-1) . Yet `Request#shop`, `#topic`, and `#webhook_id` are read straight from unauthenticated headers [3](#0-2) , and `Registry.process` forwards that unverified `shop` value directly into the handler as the tenant identifier after only checking the body HMAC [4](#0-3) .

### Title
Webhook shop/topic identity not bound to HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic for a given shop once `Utils::HmacValidator.validate(request)` succeeds. However the HMAC is computed only over `raw_body`; the `shop-domain`, `topic`, and `webhook-id` HTTP headers that identify *which tenant* the payload belongs to are never part of the signed bytes.

### Finding Description
`Request#to_signable_string` returns `@raw_body` alone [1](#0-0) . `HmacValidator.validate_signature` recomputes the HMAC over that same signable string and compares it to the `hmac-sha256` header [2](#0-1) . Meanwhile `Request#shop`, `#topic`, and `#webhook_id` come from separate headers that are never mixed into the signed string [5](#0-4) .

`Registry.process` checks only the HMAC and then trusts `request.shop`/`request.topic` to build `WebhookMetadata` passed to the app's handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

Because the app's `api_secret_key` is shared across every shop installed on the app, any merchant who installs the app and legitimately receives one authentic webhook (valid `raw_body` + `hmac-sha256` pair for their own store) possesses a byte string whose HMAC verifies successfully regardless of the `shop-domain` header value sent alongside it. That merchant can replay the exact same `raw_body`/`hmac-sha256` pair to the app's public webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. `HmacValidator.validate` will accept it (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

This breaks the identity binding: **the shop authenticated by the HMAC ≠ the shop the gem hands to the application as the payload owner.**

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to select which merchant's stored offline access token/session to act on (a common, expected pattern per the docs' own example), an attacker-controlled shop can inject attacker-chosen body content that gets processed under a victim shop's identity — leading to cross-tenant data corruption or actions taken using the victim's access token. This matches the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Requires only that the attacker be an unprivileged, legitimately-installed merchant of the app (no special credentials, no access to `api_secret_key` or victim's token) — well within the unprivileged-internet-user threat model. The only prerequisite is that the app installs on more than one shop and shares one `api_secret_key`, which is the default multi-tenant Shopify app model.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values in the HMAC-signed string, or otherwise cryptographically bind them to the body before trusting them (e.g., mirror how `AuthQuery#to_signable_string` includes `shop` in its signed payload [6](#0-5) ). At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers for a webhook topic (e.g., `orders/create`).
2. Shopify sends a legitimate webhook to the app: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this exact `(B, hmac)` pair (they control their own shop/network path to their app instance, or their own storefront events, so they can reliably produce a chosen `B`).
4. Attacker sends a new HTTP request directly to the app's public webhook endpoint with the same `raw_body = B` and same `x-shopify-hmac-sha256` header, but `x-shopify-shop-domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` returns `true` (body/HMAC match) [7](#0-6) ; `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` and attacker-controlled `body` [8](#0-7) .
6. Any handler logic keyed off `data.shop` (e.g., look up victim's stored session/access token and act on `data.body`) now operates on victim data using attacker-supplied content.
