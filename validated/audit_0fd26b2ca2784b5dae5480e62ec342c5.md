### Title
Webhook shop-domain header not covered by HMAC allows cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop-domain` header — which the registry trusts as the tenant identity for the webhook — is never included in the signed payload. An attacker who can obtain any single valid `(body, hmac)` pair (e.g. by triggering a webhook delivery to their own, legitimately-installed shop) can replay that exact body/HMAC combination to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header value, causing the receiving application to process the payload as if it originated from a different (victim) tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from an attacker-influenced header without any cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against `to_signable_string` (the raw body), never incorporating `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then forwards `request.shop` — the unauthenticated header — directly to the app's webhook handler as the tenant identity for the event: [4](#0-3) 

The identity binding that should hold is:
`HMAC-verified bytes == bytes the handler attributes to a specific tenant`

But in this implementation:
`HMAC-verified bytes (raw_body only) != tenant-identifying bytes (shop-domain header)`

Because the `shop` header sits outside the signed scope, any party who can obtain one genuine `(raw_body, hmac)` pair — trivially available to an attacker who owns their own shop with the app installed and triggers an event whose body they control (e.g. an order they create) — can resend that exact body and signature to the app's webhook receiver with the `shop-domain` header rewritten to point at a different shop. The signature still validates because it never covered the shop field, and `Registry.process` dispatches the payload to the handler under the spoofed tenant identity.

### Impact Explanation
This breaks tenant isolation for any host application relying on `request.shop` (or the `shop` field of `WebhookMetadata`) to scope data written or side effects triggered by webhook processing, e.g. writing order/product data or triggering business logic keyed by shop. An attacker with only unprivileged access to their own shop installation can cause the app to process attacker-supplied data under another merchant's tenant identity — cross-tenant data injection/corruption without needing the app's `client_secret`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Likelihood is high for any app that has at least one publicly reachable webhook endpoint (the standard integration pattern for this gem) and that trusts `WebhookMetadata#shop` for tenant scoping without independent verification. The prerequisite — legitimately installing the app on an attacker-controlled shop and triggering an event with attacker-chosen body content — is available to any unprivileged internet user who can sign up for the host application.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header bytes in the signed payload used for HMAC verification, or independently verify that the `shop` claimed by the webhook matches a shop the application actually expects/has an active session for, rather than trusting an unsigned header value for tenant attribution.

### Proof of Concept
1. Install the vulnerable app on attacker-owned shop `attacker.myshopify.com`.
2. Trigger a webhook event (e.g., create an order) so Shopify delivers a webhook with headers:
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-hmac-sha256: <valid HMAC of raw_body>`
   - raw body containing attacker-controlled content.
3. Capture the raw body and the valid HMAC value from this genuine delivery.
4. Re-POST the same raw body and HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` in [5](#0-4) 
succeeds because it only checks the raw body, and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"`, causing the app to attribute attacker-controlled webhook content to the victim tenant.
