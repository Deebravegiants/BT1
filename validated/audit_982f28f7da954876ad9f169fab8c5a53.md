Confirmed: three separate entry points in `EvmHost.sol` — `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` — all pass `block.timestamp` as the Uniswap V2 `swapETHForExactTokens` deadline, which is the exact "current timestamp as deadline" pattern the report flags as unsafe.

### Title
Unsafe use of `block.timestamp` as swap deadline in `EvmHost.dispatch`/`fundRequest` enables MEV/sandwich exploitation of native-token fee swaps - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` each allow any unprivileged caller to pay the ISMP relayer fee in native ETH, which the host swaps for `feeToken()` via `IUniswapV2Router02.swapETHForExactTokens`. In all three functions the `deadline` argument passed to the router is `block.timestamp` — the timestamp at the moment the transaction is *mined*, not a caller-supplied bound. This mirrors the reported anti-pattern: `deadline: block.timestamp` makes the router's deadline check `block.timestamp <= block.timestamp`, which is always true regardless of how long the transaction sits in the mempool before being included.

### Finding Description [1](#0-0) [2](#0-1) [3](#0-2) 

Each of these three functions is reachable directly by any account submitting a transaction to `dispatch()` or `fundRequest()` with `msg.value > 0`. When native ETH is supplied, the host performs:

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
```

Because the `deadline` parameter evaluates to `block.timestamp` at *execution* time rather than at *submission* time, the Uniswap V2 router's `require(deadline >= block.timestamp)` check is satisfied trivially no matter when the transaction is actually included in a block — the transaction can be held by a searcher/builder or simply left pending in a volatile-fee-market mempool for an extended period without ever failing the deadline check. This is functionally identical to providing no deadline protection at all, which is precisely the anti-pattern the external report identifies in `VeloDeployFactory._mint`'s `deadline: block.timestamp`.

### Impact Explanation
`swapETHForExactTokens` fixes the *output* amount (`post.fee`/`amount`) and lets the *input* (`msg.value`) float up to whatever ETH is supplied, refunding any unspent ETH would normally happen but here it does not — the code sends the full `msg.value` into the swap with no unused-ETH refund path, and more importantly the price at which that swap executes is whatever the pool state is at inclusion time, not at submission time. A held transaction can be delayed until the pool price moves unfavorably (or be sandwiched around) so the caller's ETH buys the fixed `feeToken` output at a much worse rate, or a builder can reorder it alongside other trades to extract value from the swap — this is a direct fund-loss vector for whoever pays the relayer fee in native token, executed inside a core, highly-privileged infrastructure contract (`EvmHost`) that every dispatched request and fee top-up passes through.

### Likelihood Explanation
Any user who dispatches a POST/GET request or calls `fundRequest` with native ETH exercises this path — it requires no special permissions, only that `msg.value > 0`, which is an explicitly documented, normal usage mode (`@notice Payment for the request can be made with either the native token or the feeToken`). MEV searchers actively monitor mempools for router calls with weak deadlines, making exploitation practical whenever gas markets are congested or a transaction is delayed for any reason.

### Recommendation
Add a `deadline` parameter to `DispatchPost`, `DispatchGet`, and `fundRequest`'s calldata (or otherwise let the caller supply it) and forward that caller-chosen value to `swapETHForExactTokens` instead of `block.timestamp`, so the deadline reflects the caller's tolerance for inclusion delay rather than always being satisfied by construction. Additionally consider refunding unused `msg.value` when the actual swap input is less than the amount forwarded.

### Proof of Concept
1. Attacker/searcher observes a pending `dispatch(DispatchPost)` (or `fundRequest`) transaction in the mempool that supplies ETH to swap for a fixed amount of `feeToken` via `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)`.
2. The searcher delays inclusion (e.g., via private order flow, or simply waits for a period of network congestion) or sandwiches the pending swap by moving the WETH/feeToken pool price unfavorably immediately before the victim's swap executes.
3. Because the deadline is computed as `block.timestamp` at execution time, the router's deadline check always passes — the swap executes regardless of the delay or the adverse price movement.
4. The victim's transaction consumes more ETH than intended for the same fixed `post.fee` output amount, resulting in a direct loss of value with no way for the original caller to have bounded the acceptable execution window.
