### Title
Fee-on-transfer tokens cause escrow over-crediting in Tron `IntentGatewayV2.placeOrder()` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` credits the order escrow mapping `_orders[commitment][token]` using the user-requested `order.inputs[i].amount` (minus protocol fee) instead of the amount actually received by the gateway via `safeTransferFrom`. For any ERC20 with a non-zero transfer fee, the gateway will hold less balance than what is recorded as escrowed, exactly mirroring the Sherlock M-11 root cause where `claims[recipientId][token] += amount` assumed the full donated `amount` reached the vault.

### Finding Description
In the non-predispatch branch of `placeOrder`, the contract does:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
// Store reduced amount (after protocol fees) in escrow
_orders[commitment][token] += reducedInputs[i].amount;
``` [1](#0-0) 

`reducedInputs[i].amount` is derived purely from `order.inputs[i].amount` reduced by the protocol fee bps, computed earlier without ever checking the gateway's actual token balance before/after the transfer: [2](#0-1) 

If `token` charges a transfer fee (fee-on-transfer / rebasing / deflationary token), `safeTransferFrom` delivers strictly less than `order.inputs[i].amount` to the gateway, yet the escrow ledger (`_orders[commitment][token]`) is incremented by the full requested (fee-adjusted-for-protocol-fee-only) amount. This is the exact faulty assumption identified in Sherlock M-11: the contract assumes `transferFrom` amount == amount received, and credits an internal accounting mapping accordingly without measuring actual balance delta.

Note the same predispatch branch has the identical bug: it credits `_orders[commitment][token] += reducedInputs[i].amount` based on the "required" balance sweep, and although it computes `dust = balance - requiredAmount` for the sweep from the dispatcher, it never adjusts for shortfall if `balance < requiredAmount` was already reverted — but the fee-on-transfer haircut from `msg.sender` to the dispatcher (`IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)`) is not accounted for either. [3](#0-2) 

This is notably a regression relative to the main EVM `IntentGatewayV2.sol`, which was hardened against exactly this class of bug: it snapshots balances before/after the transfer and sets `order.inputs[i].amount` to the actual received delta before computing the commitment and escrow. [4](#0-3) [5](#0-4) 

The fee-on-transfer regression tests that exist for the main gateway (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`, `testPlaceOrder_FeeOnTransferToken_Predispatch`) confirm the intended fix pattern and its absence in the Tron port. [6](#0-5) 

### Impact Explanation
Any unprivileged user can call `placeOrder` on the Tron `IntentGateway` with a fee-on-transfer ERC20 as an input asset. This over-credits the escrow ledger for that commitment beyond the gateway's actual token balance. When a solver later fills the order and the fill/cancel/settlement logic pays out based on the escrow ledger value rather than the actual balance, the gateway becomes insolvent for that token — subsequent legitimate claims against the shared token balance can fail or be underpaid, and depending on the withdrawal accounting, an attacker could potentially drain balances belonging to other orders' escrow of the same token. At minimum this causes permanent inability to fully honor recorded escrow claims (freezing/loss of funds for other order participants), satisfying the "concrete theft or permanent freezing of funds" bar. This is a Medium-severity issue, consistent with the original Sherlock M-11 classification.

### Likelihood Explanation
Likelihood is contingent on whether the deployed/whitelisted input tokens for the Tron IntentGateway ever include a fee-on-transfer, rebasing, or deflationary ERC20. Given that the underlying protocol pattern (Hyperbridge intents) is designed to be permissionless w.r.t. input token selection (as seen from the main EVM gateway explicitly supporting arbitrary ERC20 inputs and being hardened against exactly this), and this hardening was demonstrably applied to `evm/src/apps/IntentGatewayV2.sol` but not carried over to the Tron fork, this is a straightforward, single-transaction-triggerable bug once a fee-on-transfer token is used as an order input.

### Recommendation
Apply the same fix used in `evm/src/apps/IntentGatewayV2.sol` to `evm/tron/contracts/apps/IntentGatewayV2.sol`: snapshot the gateway's (or dispatcher's) token balance before calling `safeTransferFrom`, compute the actual received amount as the balance delta, and use that measured amount (rather than the requested `order.inputs[i].amount`) as the basis for `reducedInputs[i].amount` and the escrow credit `_orders[commitment][token]`, for both the direct-transfer and predispatch code paths.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee) and whitelist it as an intent input token on the Tron `IntentGatewayV2`.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`, `protocolFeeBps = 0`.
3. `IERC20(FOT).safeTransferFrom(msg.sender, address(this), 1000e18)` executes; due to the 1% fee, the gateway's actual FOT balance increases by only 990e18.
4. `reducedInputs[0].amount` is computed as `1000e18` (no protocol fee to subtract), and `_orders[commitment][FOT] += 1000e18` is recorded. [1](#0-0) 
5. The gateway now records escrow of 1000e18 FOT for this order while only holding 990e18 FOT — a 10e18 shortfall that either blocks correct settlement of this order or is siphoned from other orders' escrowed FOT balance, mirroring the exact fault pattern from Sherlock M-11.

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
