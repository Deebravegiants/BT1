### Title
Unverified `amount` in `pool.repay`/`recapitalize` lets any caller refund tokens that were never paid, draining pool custody - (File: contracts/pool/src/ops/repay.rs)

### Summary
`ops::repay::apply` computes an `overpayment` refund purely from the caller-declared `PoolAction.amount` and pays it out of the pool's real token balance via `cache.transfer_out(payer, overpayment)`, with no verification that any tokens were actually transferred in. When the position's outstanding debt is zero (or smaller than the declared amount), `resolve_repay` treats the entire declared amount as excess and refunds it out of existing supplier custody. The same pattern exists in `ops::recapitalize::apply` (excess over the shortfall). This is the direct analog of CVE-2022-47943: a large attacker-controlled length (`amount`) consumed at a zero offset (zero actual inbound transfer), because the code trusts a declared inbound quantity instead of measuring it.

### Finding Description
In `contracts/pool/src/ops/repay.rs`, `accounting` resolves `(burned, overpayment) = cache.resolve_repay(amount, position)` where `amount` comes straight from `action.amount`. `resolve_repay` (common/src/rates/scaling.rs:171-191) returns `overpayment = amount - current_debt_ceil` whenever `amount >= current_debt_ceil`. For a market with no debt, `current_debt_ceil == 0`, so `overpayment == amount` and `net_repay == 0`; the `RepayRoundsToZeroShares` assert passes on its `net_repay == 0` disjunct. `apply` then executes `outcome.cache.transfer_out(payer, outcome.overpayment)`, moving real custody to the payer. The module comment states the trust assumption: "The controller transfers the repay amount into the pool before this call" — the pool leg itself never measures the inbound balance delta, unlike the controller-side `payments::transfer_amount_measured` used in `settle_repay` (contracts/controller/src/positions/debt.rs:144-151).

The codebase's own test documents the primitive: `test_unfunded_repay_overpayment_refund_also_pays_out_of_custody` (contracts/pool/tests/flows.rs:3589-3611) calls `client().repay(&payer, &t.ract(0, custody_before))` on a market with `borrowed == 0`, transfers nothing in, and observes the entire declared `custody_before` refunded to `payer` out of real custody with the book untouched. The same test file documents the identical gap for `ops::recapitalize::apply` (excess over the shortfall is refunded without debiting `cash` or passing `require_reserves`).

The precondition for exploitability is that the pool's `repay`/`recapitalize` entrypoints are reachable by an unprivileged address (they take a `payer`/`Address` argument and the test harness invokes them directly). If the pool gates these on the controller address, the bug is still live through `controller.repay`/`recapitalize` only if the controller ever routes an unmeasured or partially-measured amount — the controller does measure transfers, so the primary exposure is direct pool calls. Note: even if `payer.require_auth` is enforced, the attacker is the payer and can authorize the call.

### Impact Explanation
Theft of user funds: a single call `repay(payer = attacker, actions = [PoolAction{scaled_amount: 0, amount: <pool token balance>, hub_asset}])` on any market with `borrowed == 0` (or declaring `amount = debt_ceil + balance` on an active market) transfers supplier custody to the attacker with zero tokens deposited. Repeating per market drains all unborrowed cash. Where debt exists, the excess portion `amount - debt_ceil` is still paid out unbacked, so only `debt_ceil` needs to be funded to extract the whole balance.

### Likelihood Explanation
High: the exploit requires no position, no collateral, no price movement, and no privileged role. Any funded market is a target; markets with zero outstanding debt (freshly listed or fully repaid) are drained with a single call and zero capital. The only uncertainty is whether the pool contract restricts `repay`/`recapitalize` callers to the controller; the test-suite evidence (`flows.rs` calling `client().repay` directly with a generated payer) indicates they are externally callable.

### Recommendation
Measure the inbound transfer inside the pool instead of trusting `action.amount`: snapshot `token.balance(pool)` before and after a pull from `payer` (as `payments::transfer_amount_measured` does on the controller side), and use the measured delta for `resolve_repay` and the refund computation. Alternatively, restrict `repay`/`recapitalize` to the controller contract address via a stored authorized-caller check, since the controller already performs the measured transfer before invoking the pool.

pub fn resolve_repay(
    env: &Env,
    amount: i128,
    pos_scaled: Ray,
    borrow_index: Ray,
    decimals: u32,
) -> (Ray, i128) {
    let current_debt_ceil = unscale_borrow_ceil(env, pos_scaled, borrow_index, decimals);
    if amount >= current_debt_ceil {
        (
            pos_scaled,
            amount
                .checked_sub(current_debt_ceil)
                .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow)),
        )
    } else {
        (
            calculate_scaled_borrow_floor(env, amount, decimals, borrow_index),
            0,
        )
    }

fn test_unfunded_repay_overpayment_refund_also_pays_out_of_custody() {

    let token = token::Client::new(&t.env, &t.asset);
    let payer = Address::generate(&t.env);

    let custody_before = token.balance(&t.pool);
    let before = t.state_snapshot();
    assert_eq!(
        before.cash, custody_before,
        "fixture guard: book and custody must start in sync"
    );
    assert_eq!(before.borrowed, 0, "fixture must carry no debt");

    // Nothing transferred in, no debt to retire: the whole amount is "excess".
    let credited = t
        .client()
        .repay(&payer, &t.ract(0, custody_before))
        .get_unchecked(0)
        .actual_amount;
    assert_eq!(credited, 0, "no debt was retired, so nothing is credited");
    assert_unfunded_refund_drained_custody(&t, &payer, custody_before, &before);
}
