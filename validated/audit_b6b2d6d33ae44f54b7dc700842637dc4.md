### Title
Shared mutable `intentSigner` field on `IntentsSDK` allows a concurrent request to sign with the wrong signer - (File: `packages/intents-sdk/src/sdk.ts`)

### Summary
`IntentsSDK` stores the active signer as a single mutable instance field (`this.intentSigner`) that is set via `setIntentSigner()` and read later by call sites such as `signAndSendIntent()` and `invalidateNonces()` through the `args.signer ?? this.intentSigner` fallback pattern. If a single `IntentsSDK` instance is reused to serve multiple logical users/requests concurrently (a common pattern for a long-lived SDK object, e.g. on a server), a `setIntentSigner()` call for user B racing with an in-flight signing call for user A can cause user A's intent to be built and signed with user B's signer, exactly mirroring the SurrealDB advisory's TOCTOU pattern: a per-request identity temporarily lives in shared mutable state instead of being bound to the request/call.

### Finding Description
`IntentsSDK` declares `intentSigner` as a `protected` instance property, initialized from the constructor and mutated by `setIntentSigner()`: [1](#0-0) [2](#0-1) [3](#0-2) 

Consumers that don't pass an explicit `signer` argument fall back to this shared field at the moment they execute, not at the moment the caller intended to use it. This exact "read-shared-mutable-identity-at-execution-time" pattern is visible in `invalidateNonces()`: [4](#0-3) 

The unit tests for `signAndSendIntent()` confirm the same fallback semantics are used there: calling `setIntentSigner()` changes which signer is used by a subsequently issued (but asynchronously executing) `signAndSendIntent()` call: [5](#0-4) 

Because `signAndSendIntent()`/`invalidateNonces()` are `async` and perform awaited work (salt fetching, RPC calls, publishing) before actually invoking `intentSigner.signIntent(...)`, there is a window between "start of the call" and "signer actually used" during which another concurrent caller on the same `IntentsSDK` instance can call `setIntentSigner()` and overwrite the shared field. The equality that breaks is: *the signer that signs the payload* is no longer guaranteed to be *the signer the caller who initiated that specific call intended to use* — an analog of the advisory's "the session that executes the request is not the session the caller authenticated as."

### Impact Explanation
If an integrator builds a multi-tenant service around a single, long-lived `IntentsSDK` instance and uses the convenience `setIntentSigner()` API (rather than always passing `signer` explicitly into every call), two concurrent user requests can race: User A's `signAndSendIntent`/`invalidateNonces` call, still awaiting internal async work, can end up signing/publishing with User B's signer (or vice versa). This is a signature bound to the wrong signer, which per the rules maps to a High-severity outcome (funds moved/signed under another identity's key, or a nonce invalidation performed under the wrong signer, potentially invalidating another user's valid nonce or producing an intent attributed to the wrong account).

### Likelihood Explanation
Exploitability depends entirely on integration pattern: if every caller always supplies `args.signer` explicitly (bypassing the shared fallback), this is not reachable. But the SDK's own public API explicitly promotes the stateful pattern (`sdk.setIntentSigner(signer)` then call methods without `signer`), as shown in the README and tests, making misuse likely in exactly the kind of shared/long-lived server-side SDK instance that a backend integrator would set up. This requires no privileged access — only the ability to trigger two concurrent SDK calls against the same shared instance, similar to the advisory's unauthenticated concurrent HTTP requests.

### Recommendation
- Make `signer` a required, per-call argument on `signAndSendIntent`, `invalidateNonces`, and any other method that ultimately signs, rather than allowing an implicit fallback to shared mutable instance state.
- Deprecate/remove `setIntentSigner()` as a means of changing behavior of in-flight or future calls on a shared instance; or clearly document that `IntentsSDK` instances with a "default signer" set via `setIntentSigner()` must never be shared across concurrent, multi-user request contexts.
- Alternatively, snapshot `this.intentSigner` into a local constant at the very start of each public method (before any `await`), and thread that local value through the rest of the call, instead of re-reading `this.intentSigner` implicitly at the point of use only via the parameter default.

### Proof of Concept
1. Instantiate one `IntentsSDK` on a server, without any signer set (or with a default signer for tenant A only used as identity marker).
2. Concurrently handle two HTTP requests: Request A calls `sdk.setIntentSigner(signerA)` then `await sdk.signAndSendIntent({ intents: intentsForA })` (not awaiting the setter, just sequential calls as the "convenience" pattern suggests).
3. Immediately after A's `setIntentSigner` but before A's `signAndSendIntent` reaches the point where it reads `this.intentSigner` (e.g. during the awaited salt-fetch step), Request B calls `sdk.setIntentSigner(signerB)`.
4. Because `signAndSendIntent` reads the shared `this.intentSigner` field lazily at execution time (per the same pattern shown in `invalidateNonces`, `packages/intents-sdk/src/sdk.ts:280-281`), Request A's intent ends up signed using `signerB`, producing a payload attributed to/signed by the wrong account for A's intended transfer.
