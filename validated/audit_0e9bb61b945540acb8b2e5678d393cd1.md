### Title
Webhook `shop` Field Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` claims to "verify the request did indeed come from Shopify" before dispatching webhook data to the host app's handler, but the HMAC signature only covers the raw request body. The `shop` attribute — which the gem documents as a verified, trustworthy field of `WebhookMetadata` — is read directly from an HTTP header that is completely outside the signed payload. An attacker who can produce (or replay/capture) any validly-signed webhook body can freely substitute the shop-domain header to impersonate a different merchant, causing the host app to process webhook data under the wrong tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor, however, is derived independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header via `shopify_header`: [2](#0-1) , which is not part of the signable string at all.

`Registry.process` validates only this body-based HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string` and compares it to the `hmac` field — it never incorporates the `shop` header: [4](#0-3) .

The gem's own documentation instructs developers to trust `data.shop` as "The shop domain of the webhook" coming out of a request that was already verified to "indeed come from Shopify": [5](#0-4) [6](#0-5) . This is the same class of bug as the reported `EigenLSTRestaking.invoke()` issue: a privileged/trusted-looking operation (`shop`-scoped webhook dispatch) is not actually bound to the identity check (`HMAC`) that is supposed to authorize it — the equality that should hold, `hmac_verified_bytes == bytes_that_determine_the_tenant`, does not, because `hmac_verified_bytes == raw_body` while `bytes_that_determine_the_tenant == shop_domain_header`.

Because Shopify signs webhooks for all shops on an app installation with the **same** `api_secret_key`, any shop that has installed the app can generate a genuinely-signed webhook body (e.g., by triggering `orders/create` on their own store) and then replay that exact body to the app's webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. The HMAC still validates (it only checks the body), but `WebhookMetadata#shop` now reports the victim's domain to the handler.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: a webhook that genuinely originated from shop A can be relabeled and delivered to the host application as if it came from shop B. Any host logic keyed off `data.shop` (looking up per-shop access tokens/sessions, writing/deleting per-shop records, invoking APIs on behalf of "the shop", scoping data mutation) can be misattributed to a different tenant, i.e. a **cross-tenant access** condition — Critical per the report's own classification.

### Likelihood Explanation
Exploitation requires only that the attacker's own shop (or any shop) has the target app installed so they can generate at least one validly-signed webhook payload, plus the ability to POST arbitrary headers to the app's public webhook endpoint — both are available to an ordinary unprivileged merchant/internet actor, with no access token, `client_secret`, or privileged credential required.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values into the HMAC-covered signable string, or otherwise cryptographically tie the header-derived identity to the verified body before constructing `WebhookMetadata`. At minimum, `Registry.process` should refuse to trust `request.shop` unless it is independently corroborated (e.g., cross-checked against a known/expected shop for the webhook subscription) rather than treating an unauthenticated header as verified output.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` (attacker is a legitimate but unprivileged merchant).
2. Attacker triggers a real webhook, e.g. `orders/create`, and captures the raw body + valid `shopify-hmac-sha256` value Shopify sent to the app's endpoint.
3. Attacker (or anyone who can reach the app's public webhook endpoint) resends the exact same body and HMAC header, but with `shopify-shop-domain: victim-shop.myshopify.com`.
4. `HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb) succeeds because it only checks the untouched raw body.
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)` (lib/shopify_api/webhooks/registry.rb lines 198-199) and calls the host handler, which processes the attacker's data as if it belonged to `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
