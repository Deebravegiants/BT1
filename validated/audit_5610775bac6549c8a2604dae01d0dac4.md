### Title
Webhook shop-domain identity spoofing via HMAC scope mismatch (header not covered by signature) - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  while `shop` is read from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [2](#0-1) . `Registry.process` validates HMAC over the body only via `Utils::HmacValidator.validate(request)`, then dispatches to the handler passing `shop: request.shop` taken straight from that unverified header [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop header == shop cryptographically bound by HMAC`. In reality `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares against `verifiable_query.hmac` [4](#0-3) , and for webhooks `to_signable_string` is exclusively the raw JSON body [1](#0-0) . None of `shop`, `topic`, `webhook_id`, or `api_version` headers are part of the signed material — only the body bytes are verified, but the `shop` field is the one acted on by the handler (`WebhookMetadata.new(... shop: request.shop ...)`) [5](#0-4) .

This is directly analogous to the reported `BlackGovernor` bug class: an on-chain calculation (quorum) is evaluated against a metric (`smNFTBalance`) that is not the metric actually gating the action (active voting power), causing a mismatch between the check and the acted-upon value. Here, the field that gates tenant identity (`shop`) is disjoint from the field actually covered by the cryptographic check (`raw_body`).

Because the HMAC never binds `shop` to the body, any entity capable of delivering an HTTP POST to the app's webhook endpoint with a *previously valid* `(body, hmac)` pair — e.g., a legitimate webhook the attacker's own shop received (since a merchant naturally receives/controls webhooks destined for their own installed app, or can capture one via a debugging proxy on their own tenant) — can replay that exact `(body, hmac)` while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still returns `true` because the signed material (`raw_body`) is unchanged; `Registry.process` then hands the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
Applications built on this gem (following the documented pattern in `docs/usage/webhooks.md`) use `WebhookMetadata#shop` to determine which tenant's data to upsert/act on. Since the gem provides no protection against shop-header spoofing under a replayed-but-validly-signed body, a malicious merchant can inject data attributed to another shop into that shop's tenant records — a cross-tenant data-integrity/confusion issue. This satisfies the "cross-tenant access" impact category in scope.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to possess at least one legitimately signed `(raw_body, hmac)` pair, which any merchant with the app installed can obtain from their own genuine webhook deliveries (no `client_secret` needed) and requires no privileged access. The only additional step is re-POSTing the captured bytes to the app's public webhook endpoint with a modified `shop-domain` header, which is native to how this gem's `Request`/`Registry` API is documented and used.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material, or verify the header against a value derivable from the payload/registration. Since Shopify's actual HMAC scheme only ever signs the body, the gem should not treat `request.shop` as authenticated; at minimum, `WebhookMetadata` and the docs should explicitly warn that `shop` is unauthenticated and must be cross-checked by the host application against a known, previously-registered shop for that specific webhook subscription (e.g. by correlating `webhook_id` with the shop that registered it), rather than trusted implicitly.

### Proof of Concept
1. App registers webhook handling and exposes a public endpoint that calls `ShopifyAPI::Webhooks::Registry.process(request)`.
2. Attacker (merchant of `attacker.myshopify.com`, app installed) triggers a benign event (e.g., `orders/create`) and captures the raw POST: body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker re-sends `POST` to the app's webhook endpoint with the same body `B` and header `H`, but sets `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim.myshopify.com", "shopify-hmac-sha256" => H})` is constructed.
5. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` → validation passes.
6. `handler.handle(data: WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...))` is invoked — the host application now processes attacker-controlled data under `victim.myshopify.com`'s tenant identity.
