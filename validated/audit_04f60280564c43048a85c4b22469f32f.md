Confirmed: the `shop` field delivered to app handlers via `WebhookMetadata` is taken from an HTTP header that is never covered by the HMAC. This matches the report's bug class ("a field acted on but not covered by the HMAC") and is directly reachable in this gem's own code.

### Title
Webhook `shop`/`topic`/`webhook_id` identity headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` only verifies the HMAC over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that the app's `WebhookHandler` receives and trusts are all read from unauthenticated HTTP headers.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Registry.process` validates the webhook solely against that signable string via `Utils::HmacValidator.validate(request)` [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` fields, however, are read directly from HTTP headers with no cryptographic binding to the HMAC at all [3](#0-2) . After the HMAC check passes, these unauthenticated header values are packaged into `WebhookMetadata` and handed to the app's `WebhookHandler#handle` as if they were verified [4](#0-3) [5](#0-4) .

The equality that should hold but does not: `HMAC-covered-bytes == identity-bytes-trusted-by-handler`. In reality, `HMAC-covered-bytes = raw_body` while `identity-bytes-trusted-by-handler = headers(shop-domain, topic, webhook-id, api-version)`, which are disjoint from what the signature protects.

A legitimate valid `(body, hmac)` pair — for example one produced by installing the app on the attacker's own shop and triggering a webhook whose body content the attacker can influence or predict (e.g. a resource they create themselves) — can be replayed to the app's public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop domain and/or the `x-shopify-topic`/`x-shopify-webhook-id` headers rewritten. Because `Registry.process` never checks that the signed body is consistent with the claimed shop/topic, the HMAC check still passes, and the handler receives `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the library hands the app-level handler an authenticated-looking `shop` value that is, in fact, attacker-controlled and disconnected from the actual HMAC verification. Any app whose webhook handler uses `data.shop` to look up records, apply mutations, or route to per-tenant logic (the documented/expected usage pattern) can be made to act on/for the wrong tenant using a signature that was never issued for that tenant's data. This matches the "cross-tenant access" Critical impact category, since the trust boundary between tenants collapses at the point the library reports webhook identity to the app.

### Likelihood Explanation
Exploitation requires an internet-reachable webhook endpoint (this is the app's normal, documented setup) and a valid `(body, hmac)` pair, which any developer/attacker can freely obtain by installing the app on their own shop and receiving genuine webhooks for it — no privileged credentials, `api_secret_key`, or access token is required. The header rewrite is a standard HTTP replay/tamper with a raw HTTP client, well within reach of an unprivileged internet user.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signed payload verification (e.g., by having `to_signable_string` bind them, or by independently confirming the topic/shop against the caller's registered webhook subscription/session before invoking the handler), so an attacker cannot decouple the identity headers from the signed body.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`) so Shopify sends it a legitimately HMAC-signed request with body `B` and header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures this raw `(B, hmac)` pair.
3. Attacker POSTs the same body `B` and `hmac` to the app's public webhook endpoint, but rewrites `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `OpenSSL::HMAC.hexdigest(secret, B)` against the supplied hmac — this succeeds since `B` and `hmac` are a genuine matched pair [2](#0-1) .
5. The app's `WebhookHandler#handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the app processes/persists data as belonging to `victim-shop.myshopify.com` [6](#0-5) .
