### Title
Spending authority stays bound to the stale stored `Account.owner` after the position NFT changes hands - (File: contracts/controller/src/account.rs)

### Summary
The controller keeps two notions of account ownership: the live position-NFT holder (`storage::account_owner`) and the `owner` field persisted inside the `Account` struct at creation. All spending verbs (`borrow`, `withdraw`, `multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`) authorize via `require_owner_or_delegate(env, account_id, caller, &account.owner)`, which compares the caller against the stored field — not the live NFT owner. Because `PositionNft` uses the stock OpenZeppelin `transfer`/`approve`/`transfer_from` with no controller hook, nothing rewrites `Account.owner` on transfer. The previous holder therefore retains full spending authority over an account it no longer owns, and the new holder is locked out of owner-only flows.

### Finding Description
- `create_account_with` writes `Account { owner, .. }` once at mint time; there is no code path that mutates `account.owner` afterward (`contracts/controller/src/account.rs:64-71`).
- `load_or_create_account` passes `&account.owner` (the stored field) into `require_owner_or_delegate` for `Migrate` and `Multiply` guards, and the same stored-owner comparison `caller == owner` in `is_owner_or_delegate` gates every spending verb (`account.rs:99-127`). This is the analog of the CakePHP issue: an authorization artifact bound to one context (the original depositor) is still accepted for a different context (the account after its NFT was transferred), because the check validates against a stale binding instead of the current authority.
- `require_account_owner`, by contrast, re-reads `storage::account_owner` (live NFT owner) and is only used for `renew_account`/`add_delegate`/`remove_delegate` (`account.rs:143-148,249-250`), proving the codebase treats the NFT owner as authoritative but fails to apply that binding to spending verbs.
- `PositionNft` implements stock `NonFungibleToken`/`NonFungibleEnumerable` with only `token_uri` overridden; `transfer`, `approve`, and `transfer_from` execute with no controller callback, so a transfer can never resync `Account.owner` (`contracts/position-nft/src/contract.rs:131-173`).
- Delegations are keyed under the stored owner (`storage::add_delegate(env, account_id, caller, delegate)` stores under `caller`; `get_delegates(env, account_id, owner)` looks up under `account.owner`), so after a transfer the old owner's delegate list remains effective while grants made by the new owner are stored under a key that `is_owner_or_delegate` never reads (`account.rs:124-127,260-264`).

### Impact Explanation
Theft of user funds. After a legitimate transfer or sale of the position NFT, the prior owner (or any manager they delegated) can still pass `caller == account.owner` and invoke `borrow`/`withdraw` to pull the account's collateral and draw new debt against it, while the NFT's current holder — who paid for the position — cannot authorize the same verbs and is limited to the permissionless surface. A buyer of a collateralized position can be drained in the same transaction sequence as the NFT handoff.

### Likelihood Explanation
Reachable by any unprivileged address that has ever owned a lending account: `transfer` on the position NFT is permissionless for the token holder, and `withdraw`/`borrow` require only `caller.require_auth()` plus the stale `account.owner` match. No privileged state, timing race, or oracle dependency is needed; the precondition is simply that an account NFT changed hands after its first funding, which is the NFT's designed purpose.

### Recommendation
In `is_owner_or_delegate`/`require_owner_or_delegate`, resolve the live owner via `storage::account_owner(env, account_id)` instead of trusting `Account.owner` (or resync `account.owner` from the NFT owner on every `get_account` load). Store delegate sets keyed by `account_id` alone, not by `(account_id, owner)`, so a change of NFT ownership naturally invalidates prior grants, and have `add_delegate`/`remove_delegate` write under the live owner.

### Proof of Concept
1. Alice calls `supply` with `account_id = 0`; the controller mints position NFT `N` to Alice and stores `Account.owner = Alice`.
2. Alice optionally calls `add_delegate(M)`, then calls `position_nft.transfer(Alice, Bob, N)` (stock OZ entrypoint; no controller hook fires, `Account.owner` remains `Alice`).
3. Bob now owns the account per `owner_of(N)`, but `require_account_owner` and `is_owner_or_delegate` disagree: Alice (or delegate `M`) calls `withdraw(N, collateral)` — `caller.require_auth()` succeeds and `caller == account.owner` still holds — moving Bob's collateral out to Alice. Alice can equally call `borrow` to max out the account's LTV before Bob can react.
4. Bob's own `withdraw`/`borrow`/`add_delegate` calls revert with `NotAuthorized`/`AccountNotInMarket`, since `account.owner` was never updated.

Note on confidence: I was unable to read `contracts/controller/src/storage/account.rs` (index iteration limit) to confirm whether `get_account` resyncs `Account.owner` from the live NFT owner on load. If `get_account` performs that resync, this finding does not hold; the asymmetry between `require_owner_or_delegate` (stored field) and `require_account_owner` (live NFT read), plus the absence of any `account.owner` write path after creation, indicates it does not.
