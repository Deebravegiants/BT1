## Title
Webhook `shop` and `topic` fields are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop-domain` and `topic` headers — which are used by `ShopifyAPI::Webhooks::Registry.process` to route the event and to identify which merchant it belongs to — are read directly from unauthenticated HTTP headers and never included in the signed payload. Any party capable of obtaining one genuinely-signed `(body, hmac)` pair from Shopify (e.g., by installing the host app on their own shop) can replay that pair against the app's webhook endpoint while freely rewriting the `shop-domain` and `topic` headers, causing the handler to process attacker-chosen webhook data under an arbitrary victim shop and topic.

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

Note that `to_signable_string` returns only `@raw_body`:
```ruby
def to_signable_string
  @raw_body
end
```
while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers via `shopify_header`, none of which are part of the signed string.

`HmacValidator.validate` only checks that `hmac == HMAC(secret, to_signable_string)`, i.e. it authenticates the *body bytes* but not the headers: [2](#0-1) 

`Registry.process` then uses the unauthenticated `request.topic` to select a handler and the unauthenticated `request.shop` to identify the merchant, passing both straight into the handler: [3](#0-2) 

The identity binding that should hold is: `shop that the HMAC authenticates == shop the handler is told the data came from`. Because `shop` (and `topic`) are excluded from `to_signable_string`, this equality does not hold — the HMAC only proves "some payload signed by this app's shared secret", not "this payload came from shop X for topic Y". This is the same class of bug as the reported WETHGateway issue: a value that is acted upon (`shop`, `topic`) is not covered by the integrity check that is otherwise relied upon to establish trust (the HMAC).

Since Shopify apps sign webhooks with a single secret (`Context.api_secret_key`) shared across all merchant installations of the app, an unprivileged user who installs the target app on their own (attacker-controlled) shop will receive genuinely HMAC-signed webhook deliveries. They can capture one such `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop, and/or a forged `X-Shopify-Topic` header selecting any registered handler. `Registry.process` will accept it as valid (the HMAC still checks out against the unmodified body) and invoke the handler believing the event originates from the victim shop/topic.

### Impact Explanation
This breaks the tenant boundary between shops using the same app: a handler that keys off `WebhookMetadata#shop` (e.g., to look up that shop's session/access token, update per-shop billing state, trigger `app/uninstalled` cleanup, or process GDPR data-request/erasure flows) can be made to act on behalf of an arbitrary victim shop using attacker-supplied data. This is a cross-tenant access primitive stemming purely from a gap in this gem's own webhook verification logic, not from any host application misuse.

### Likelihood Explanation
Any user can become an "attacker" simply by installing the target app on a shop/dev store they control (a standard, unprivileged action), which is enough to obtain a validly-signed `(body, hmac)` pair. No access token, `client_secret`, or privileged account is required — only the ability to receive one webhook and to send an arbitrary POST request to the app's public webhook endpoint with modified headers.

### Recommendation
Include `shop`, `topic`, and any other header fields the application relies on for identity/routing in the HMAC-signed material (or otherwise cryptographically bind them to the body/HMAC), so that the signature authenticates the full tuple `(shop, topic, body)` rather than the body alone.

### Proof of Concept
1. Attacker registers/installs the target Shopify app on a shop they control and subscribes to a webhook topic the app handles (e.g. `app/uninstalled`).
2. Shopify delivers a webhook to the app's endpoint with a genuine `X-Shopify-Hmac-Sha256` header computed over the raw JSON body using the app's shared secret. Attacker captures `raw_body` and `hmac`.
3. Attacker resends an HTTP POST to the same webhook endpoint with:
   - Body: the captured `raw_body` (unchanged, so the HMAC still validates)
   - `X-Shopify-Hmac-Sha256`: the captured `hmac` (unchanged)
   - `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com` (forged)
   - `X-Shopify-Topic`: any topic registered with a handler in this app (forged)
4. `Utils::HmacValidator.validate(request)` in [4](#0-3) 
succeeds because it only checks the body bytes; `Registry.process` dispatches to the handler for the forged topic with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled data as if it belonged to the victim shop.
