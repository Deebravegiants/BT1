## Analysis

The NUMA incident is a classic price-manipulation drain: an attacker distorts a price source used by a contract to compute swap outputs, then extracts value against the distorted price. The closest analog reachable by an unprivileged actor (an intent/order placer) in this codebase is Hyperbridge's **Simplex** solver, specifically its Uniswap V4 pool-based venue pricing used to fill `IntentGatewayV2` orders.

### Title
Unbounded, execution-cost-blind Uniswap V4 pool pricing lets an attacker manipulate the spot price to drain Simplex solver liquidity on `IntentGatewayV2` fills - (File: `sdk/packages/simplex/src/funding/uniswapV4/UniswapV4FundingPlanner.ts`, `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
When a Simplex-configured pair has no static bid/ask curve, its price is read directly from the current tick (spot price) of a Uniswap V4 pool via `computeDirectPoolPriceUsd` [1](#0-0) , and that raw mid price is applied linearly to the entire order size with no slippage/impact term or fee-tier adjustment, as documented in the flow notes [2](#0-1) . The only defense is `checkPriceGuard`, which rejects a quote only if it deviates from a **static** `referencePrice` by more than `maxDeviationBps` [3](#0-2) . An attacker can move the pool price by up to `maxDeviationBps` (an operator-configured static tolerance, e.g. 200 bps in the documented example) via an ordinary swap and stay inside the guard, then place an `IntentGatewayV2` order that Simplex fills at that manipulated rate, systematically extracting the solver's escrowed inventory — the same "manipulate price, then extract value" pattern as the NUMA incident.

### Finding Description
1. A Simplex operator can configure a "venue-priced" pair with no curves, sourcing price entirely from a Uniswap V4 position: `[vault.uniswapV4]` [4](#0-3) .
2. `getVenueUsdPrice` → `UniswapV4FundingPlanner.getExoticTokenPrice` picks the most-liquid position and calls `computeDirectPoolPriceUsd`, which returns `sdkPool.token0Price`/`token1Price` — the pool's current spot price, derived from `sqrtPriceX96` — with **no size or impact term** [5](#0-4) .
3. `resolveLegRates` uses this venue price for *any* order size in that pair up to the pair's cap, applying it linearly through `computeLegPolicyOutput` [6](#0-5) .
4. The only sanity check, `checkPriceGuard`, compares the live quote to a fixed `referencePrice` within `maxDeviationBps` [7](#0-6) . This bound is static and configured once by the operator; it does not measure execution cost, price impact of the attacker's own manipulating swap, or how "fresh"/thin the pool is beyond a fixed percentage band.
5. Because the guard only rejects fills once the pool deviates by more than the configured band, an attacker can move the pool price by *just under* that band (e.g., swap to push the price 1.9% away when the guard is 2%) with a single transaction, place (or have a colluding/self bid win) an `IntentGatewayV2` order sized at the operator's `maxOrderSize`, get it filled by Simplex at the skewed price, and then reverse the manipulating swap (or simply exit) — realizing the spread between the true and manipulated price as profit paid out of solver inventory.
6. This is structurally the same bug class as NUMA: a single, un-time-weighted, execution-cost-blind price read used directly to price value transfers, with a static tolerance band that a single manipulator can operate inside of.

### Impact Explanation
A successful attack drains the Simplex solver's escrowed/pooled inventory (its Uniswap V4 LP position and/or vault stablecoins) each time a venue-priced pair is filled against a manipulated pool. Because `maxOrderSize` bounds a single order but not the number of orders an attacker can place across the deviation window, and the guard's band directly determines how much manipulation is "legal" per fill, this is a **theft-of-funds** vulnerability against solver capital, reachable by any unprivileged party who can (a) swap in the referenced Uniswap V4 pool and (b) place an `IntentGatewayV2` order — both permissionless actions. Given a low-liquidity or thinly-traded exotic-asset pool (the exact profile Simplex's cNGN/ZARP-style pairs target), moving price within a 1–2% band is inexpensive relative to the extractable spread on a `$5,000`+ order (the documented `maxOrderSize` example), yielding a loss profile analogous in scale to the $530K NUMA incident when repeated or scaled to larger caps.

### Likelihood Explanation
Medium-to-High. Exploitation requires: a venue-priced pair configured (no curves, Uniswap V4-only pricing — an explicitly supported first-class configuration, not an edge case) [8](#0-7) ; a pool with tractable liquidity relative to the attacker's capital; and a price guard band wide enough to allow profitable manipulation (which the operator sets, and the docs' own example of 200 bps is not a negligible tolerance). No privileged role, governance action, or protocol bug is needed — only ordinary DEX swaps and ordinary order placement, both permissionless paths explicitly in scope.

### Recommendation
- Replace or augment the raw spot-price read with a manipulation-resistant price feed (TWAP over multiple blocks, or a Chainlink/other independent oracle) before pricing venue-based fills.
- Incorporate the order's own size/impact into the quoted rate (apply the pool's fee tier and a price-impact model, not the pure `token0Price`/`token1Price` mid) rather than extending the mid linearly across the whole order.
- Make `checkPriceGuard` sensitive to short-term price velocity (e.g., reject if the pool price moved materially within the last N blocks) rather than only a static reference/band, and consider bounding cumulative fills against a single pool within a rolling window.
- Consider requiring price confirmation across multiple blocks/pools before crediting a venue price for orders above a risk-scaled threshold.

### Proof of Concept
1. Operator configures a venue-priced pair (e.g., USDC/CNGN) with `[vault.uniswapV4]` position on Base and a `referencePrice`/`maxDeviationBps` guard of 200 bps, per the documented config [9](#0-8) .
2. Attacker executes a swap against the same Uniswap V4 pool (the pool paired with USDC/USDT per the code's `usdc`/`usdt` check [10](#0-9) ) sufficient to move the spot price ~1.9% (just inside the 2% guard).
3. Attacker immediately places an `IntentGatewayV2` order at `maxOrderSize` for the same pair; `checkPriceGuard` passes because the deviation is under the configured bps [11](#0-10) .
4. Simplex's `resolveLegRates`/`computeLegPolicyOutput` prices the fill at the skewed spot rate and the solver's `UniswapV4FundingPlanner` withdraws liquidity to fund it at that rate [6](#0-5) .
5. Attacker reverses the manipulating swap, pocketing the difference between the true pre-manipulation price and the skewed fill price, funded from solver inventory.

**Note on confidence:** I was unable to complete verification of `computeLegPolicyOutput`, `sizeOrder`, and the exact `maxOrderSize` enforcement path (`cappedByPair`) due to running out of tool iterations before reading those specific files in full — the excerpts I did retrieve (`fx.ts` lines 390-479, 1339-1481, and the flow doc) are consistent with the described bug, but I could not directly inspect the size-capping code that determines the maximum single-order profit ceiling. A Devin session with full file access should confirm exact bounds before treating the dollar-impact estimate as precise.

		if (!state || !state.isHydrated()) return null

		try {
			await state.refresh()
		} catch (err) {
			this.logger.error({ err, chain }, "Failed to refresh state for price query")
			return null
		}

		const tokenLower = exoticToken.toLowerCase()
		let bestPrice: Decimal | null = null
		let bestLiquidity = 0n

		for (const pos of state.allPositions()) {
			if (pos.currency0.toLowerCase() !== tokenLower && pos.currency1.toLowerCase() !== tokenLower) continue
			const sdkPool = state.getSdkPool(pos.tokenId)
			if (!sdkPool) continue

			const result = this.computeDirectPoolPriceUsd(pos, sdkPool, chain)
			if (result && result.exoticToken.toLowerCase() === tokenLower) {
				const poolLiquidity = state.getPoolLiquidity(pos.tokenId)
				if (poolLiquidity > bestLiquidity) {
					bestPrice = result.priceUsd
					bestLiquidity = poolLiquidity
				}
			}
		}

		if (bestPrice) {
			this.logger.debug({ chain, token: tokenLower, priceUsd: bestPrice.toString() }, "Exotic token price computed")
		}
		return bestPrice
	}

	private computeDirectPoolPriceUsd(
		pos: HydratedV4Position,
		sdkPool: V4Pool,
		chain: string,
	): { exoticToken: string; priceUsd: Decimal } | null {
		const usdc = this.configService.getUsdcAsset(chain).toLowerCase()
		const usdt = this.configService.getUsdtAsset(chain).toLowerCase()
		const c0 = pos.currency0.toLowerCase()
		const c1 = pos.currency1.toLowerCase()

		if (c0 === usdc || c0 === usdt) {
			// currency0 is stable → exotic is currency1
			// token1Price = "token0 per token1" = USD per exotic
			return {
				exoticToken: c1,
				priceUsd: new Decimal(sdkPool.token1Price.toFixed(18)),
			}
		}

		if (c1 === usdc || c1 === usdt) {
			// currency1 is stable → exotic is currency0
			// token0Price = "token1 per token0" = USD per exotic
			return {
				exoticToken: c0,
				priceUsd: new Decimal(sdkPool.token0Price.toFixed(18)),
			}
		}

		return null
	}

	/**
	 * Validates a live venue quote against the static reference price for the chain.
	 * Returns true (pass) when no guard is configured, or no reference exists for the
	 * chain. Returns false when the quote (token1 per USD) deviates from the reference
	 * by more than `maxDeviationBps`, in which case the order must not be filled.
	 */
	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}

```text
## Pool-Based Pricing

When **`[vault.uniswapV4]`** lists at least one position, cross-asset pairs without curves derive bid/ask prices from **Uniswap V4 pool state** (current tick). The pool acts as the price oracle instead of a static curve. Note this yields a **single** price used in both directions — a venue-priced pair has no bid/ask spread of its own, so its margin comes from `order.fees` alone.

With Uniswap V4 positions configured, you can **omit** `bidPriceCurve` and `askPriceCurve` on the pair. Pool pricing requires the pair's `token0` to be a USD stablecoin, and same-token pairs always need their curve. The optional **`spreadBps`** field (basis points) sets the slippage tolerance for on-chain LP redemptions; defaults to `50` (0.50%).

Uniswap V4 venue pricing uses pools that pair the exotic token with **USDC or USDT** (addresses from your chain config). When multiple positions exist for the same exotic token on a chain, the most-liquid qualifying pool's price is used.

```toml lineNumbers
[assets.CNGN]
"EVM-8453" = "0x46C85152bFe9f96829aA94755D9f915F9B10EF5F"

[[pairs]]
token0 = "USDC"
token1 = "CNGN"
maxOrderSize = "5000"       # no curves — priced from the pool

[vault.uniswapV4]
spreadBps = 50  # 0.5% slippage tolerance on LP redemptions

    { chain = "EVM-8453", tokenId = "2087350" },
]
```

<Callout type="info">
Startup validation requires a pricing source per pair: **either** bid/ask price curves, **or** at least one `[vault.uniswapV4]` position. A pair with neither fails validation.
</Callout>
```
