## Title
Runtime panic on empty BEEFY commitment payload in `pallet-beefy-consensus-proofs::submit_proof` (naive/ECDSA proof path) - (File: `evm/rust/src/conversions.rs`)

## Summary
`pallet_beefy_consensus_proofs::Pallet::verify_and_apply` ABI-decodes an attacker-supplied byte string into `ismp_abi::ecdsa_beefy::BeefyConsensusProof` and immediately converts it with `.into()` into the SCALE `ConsensusMessage` type used by `ismp-beefy`. That conversion chain unconditionally assumes the BEEFY `Commitment.payload` array has at least one entry and panics (`.expect(...)`) if it is empty. Because Solidity ABI encoding allows a dynamic array to be legitimately zero-length, an unprivileged, signed account can submit a syntactically valid but semantically empty proof through the public `submit_proof` extrinsic and trigger a Rust panic deep inside on-chain execution, before any cryptographic/consensus validation happens.

## Finding Description
`verify_and_apply` decodes the naive proof type as follows: [1](#0-0) 

The `abi_decode_params` call only enforces ABI shape — it does not, and cannot, enforce that the nested `Commitment.payload` dynamic array is non-empty. The resulting `abi_proof.into()` call routes through:

`From<BeefyConsensusProof> for ConsensusMessage` → `value.relay.into()`: [2](#0-1) 

`From<RelayChainProof> for MmrProof` → `value.signedCommitment.commitment.into()`: [3](#0-2) 

`From<Commitment> for SpCommitment`, which unwraps the first payload entry unconditionally: [4](#0-3) 

If `value.payload` is empty, `iter.next()` returns `None` and `.expect("commitment has at least one payload entry")` panics. This executes inside the pallet's dispatchable call (`submit_proof`), which the pallet documentation and tests confirm is reachable by any *signed* (non-privileged) origin — only unsigned origins are rejected: [5](#0-4) 

This is functionally the same bug class as CVE-2018-7419: a message-derived structure (BEEFY `Commitment.payload`, analogous to the NBAP DCH ID list) is consumed without verifying it was actually populated, and the missing-initialization/empty-collection case is reached directly from untrusted, attacker-controlled wire data.

## Impact Explanation
A panic raised while executing a dispatchable inside a Substrate runtime aborts the transaction execution unpredictably at the Wasm/host boundary; because every validating/full node re-executes the same extrinsic when importing or validating the block, this is not merely a single-node crash but a deterministic panic reproduced by all nodes processing that block — an availability failure of the messaging/consensus-update pipeline (`pallet-beefy-consensus-proofs` is the entry point for BEEFY-based consensus updates that gate all cross-chain message delivery on Hyperbridge). This maps to "a route unable to deliver messages": while the panic is being resolved/investigated, or if it destabilizes block production/import, no BEEFY consensus updates or gated ISMP messages can be delivered through this path.

## Likelihood Explanation
High. The trigger requires only:
- A signed account (any account, no special permission) able to submit an extrinsic,
- A proof byte string with `proof_type = PROOF_TYPE_NAIVE` and a validly ABI-encoded `BeefyConsensusProof` whose `relay.signedCommitment.commitment.payload` array has zero elements.

No signature, MMR, or authority-set validity checks are needed to reach the panic point — it occurs during type conversion prior to any cryptographic verification.

## Recommendation
Replace the `.expect("commitment has at least one payload entry")` in `From<Commitment> for SpCommitment` (and the sibling `.expect(...)` calls in the same file, e.g. `mmr leaf index out of bounds`, `block number out of bounds`, `authority index out of bounds`, `validator set id out of bounds`) with fallible conversions (`TryFrom`) that propagate a typed error back through `BeefyConsensusProof`/`Sp1BeefyProof` conversions. `pallet_beefy_consensus_proofs::verify_and_apply` should surface this as `Error::<T>::AbiDecodeFailed` (or a new `Error::<T>::InvalidCommitmentPayload`) instead of allowing an unchecked panic to occur inside dispatchable execution.

## Proof of Concept
1. Construct an ABI-encoded `ecdsa_beefy::BeefyConsensusProof` where `relay.signedCommitment.commitment.payload` is an empty array (valid ABI encoding of a zero-length dynamic array — no special tooling needed beyond standard `abi_encode_params`).
2. Prefix the bytes with `PROOF_TYPE_NAIVE` (per `types::PROOF_TYPE_NAIVE`) as `verify_and_apply` expects.
3. Submit this as `proof` via `pallet_beefy_consensus_proofs::Pallet::submit_proof` from any signed test account (see the signed-extrinsic pattern in `parachain/simtests/src/pallet_beefy_consensus_proofs.rs`).
4. Observe that the call panics with `"commitment has at least one payload entry"` inside `From<Commitment> for SpCommitment` (`evm/rust/src/conversions.rs:340`) rather than returning `Error::<T>::AbiDecodeFailed`/`Error::<T>::VerificationFailed`.

Note: I could not directly confirm within the index whether `ismp_abi::ecdsa_beefy::BeefyConsensusProof` (used by the pallet) and `crate::ecdsa_beefy::Beefy::BeefyConsensusProof` (used in `evm/rust/src/conversions.rs`) resolve to the identical generated type via crate re-export — the module wiring for `ismp-abi` was not fully visible in the indexed content. This should be verified against the full crate source (e.g. via a Devin session with full repo access) to confirm the exact re-export path, though the type names, field shapes, and the `.into()` call sites strongly indicate they are the same generated `alloy_sol_macro` type.
