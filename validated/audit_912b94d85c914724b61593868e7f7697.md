### Title
Cache-key collision in confidential relay dedup cache due to unescaped delimiter join - (File: core/capabilities/confidentialrelay/response_cache.go)

### Summary
The confidential relay handler deduplicates in-flight capability-exec and secrets-get requests using a cache key built by joining request-identity fields with `"/"` as a delimiter, without escaping or length-prefixing the individual field values. If any of the joined fields (`WorkflowID`, `ExecutionID`, `ReferenceID`, `CapabilityID`, or `CallbackID`) can contain the `"/"` character, two logically distinct requests can be crafted to produce an identical cache key, causing the pending-request cache to conflate them and deliver one execution's response/result to a waiter belonging to a different execution. This is the same bug class as CVE-2026-33729 (OpenFGA GHSA-h6c8-cww8-35hf): an ambiguous/collidable cache key allows the cache to return a result computed for a different logical request.

### Finding Description
`capExecKey` and `secretsKey` build cache keys via `strings.Join([]string{...}, "/")`: [1](#0-0) 

The comment explicitly states the design rationale is that "the fields are required non-empty by Validate, so a plain join is stable and debuggable" — this only guarantees non-emptiness, not that the fields are free of the join delimiter `"/"`. Because `strings.Join` with a single-character delimiter and no escaping is not an injective encoding of a tuple of strings, two different tuples `(WorkflowID, ExecutionID, ReferenceID, CapabilityID)` can serialize to the identical joined string whenever a field boundary can be shifted by embedding a `"/"` inside one field and removing it from an adjacent one (e.g., `WorkflowID="A/B", ExecutionID="C"` vs. `WorkflowID="A", ExecutionID="B/C"` produce the same joined key). The same applies to `secretsKey`.

This key is then used as the identity for the in-flight de-duplication cache: [2](#0-1) 

`checkOrCreatePendingRequest` treats any second caller presenting the same string key as a duplicate of an already in-flight request and has it wait for, then receive, the *original* caller's result rather than executing its own request: [3](#0-2) 

If the colliding tuple belongs to a different workflow/execution/owner, the second (colliding) caller receives the signed relay result — or, in the `secretsKey` path, the "get-secrets" outcome — that was computed for someone else's request, i.e., a cross-execution/cross-workflow response confusion analogous in effect to the OpenFGA cached-authorization-key collision.

### Impact Explanation
If exploitable, this allows a request originating from one workflow/execution to receive the confidential-relay output (potentially including secrets fetched via the `secretsKey`/`SecretsRequestParams` path) that was actually computed for a different, unrelated execution — a cross-tenant/cross-workflow data disclosure and result-substitution issue. This maps to the "cross-user response confusion" / "key/secret disclosure" categories called out as acceptable impact classes.

### Likelihood Explanation
Exploitability hinges entirely on whether an unprivileged/semi-trusted workflow node can control the exact byte content of `WorkflowID`, `ExecutionID`, `ReferenceID`, or `CapabilityID` (or `CallbackID`) enough to insert a `"/"` character and shift field boundaries to match another in-flight request's key — this repo snapshot did not let me inspect the `Validate()` implementation in `confidentialrelaytypes` (chainlink-common) or the exact call sites in `execution_handlers.go`/`handler.go` that populate these fields from node-supplied input, so I could not confirm whether workflow/execution identifiers are restricted to a safe charset (e.g., UUIDs) that would make this impractical, or whether they are more loosely validated strings from workflow metadata. Given the docstring only claims "non-empty," and there is no visible sanitization against the delimiter, this should be treated as a real but not fully confirmed risk given the indexing limits on this codebase — a Devin session with full repository access would be needed to inspect `Validate()` and the upstream producers of these IDs to determine exact exploitability.

### Recommendation
Replace the delimiter-joined key with a collision-resistant encoding, e.g., hash each field independently (or length-prefix each field) before joining, such as `sha256(len(WorkflowID)||WorkflowID||len(ExecutionID)||ExecutionID||...)`, so that no two distinct tuples can produce the same key regardless of field content. Alternatively, validate that `WorkflowID`, `ExecutionID`, `ReferenceID`, and `CapabilityID` cannot contain the `"/"` character (or any reserved delimiter) before constructing the key, and enforce this in `Validate()`.

### Proof of Concept
Conceptual (unconfirmed against the actual `Validate()` restrictions):
1. Attacker-controlled workflow A submits a capability-exec request with `WorkflowID="victim/execA", ExecutionID="ref1", ReferenceID="cap1", CapabilityID="x"`.
2. Victim workflow B (or attacker crafting the second request) submits `WorkflowID="victim", ExecutionID="execA/ref1", ReferenceID="cap1", CapabilityID="x"`.
3. Both produce `capExecKey` = `"call-capability/victim/execA/ref1/cap1/x"`.
4. `checkOrCreatePendingRequest` treats the second request as a duplicate of the first and, on completion, delivers the first request's signed relay result to the second caller via `waitForPendingRequest`, even though they are logically distinct executions. [4](#0-3) [2](#0-1)

// capExecKey is the deterministic cache key for a capability-exec request,
// built from its logical identity: the (workflow, execution, step, capability)
// tuple the relay-DON signature binds to. Avoids hashing: the fields are
// required non-empty by Validate, so a plain join is stable and debuggable.
func capExecKey(p confidentialrelaytypes.CapabilityRequestParams) string {
	return strings.Join([]string{capabilityCallDomain, p.WorkflowID, p.ExecutionID, p.ReferenceID, p.CapabilityID}, "/")
}

// secretsKey is the deterministic cache key for a secrets-get request, built
// from its logical identity: workflow, execution, callback id.
func secretsKey(p confidentialrelaytypes.SecretsRequestParams) string {
	return strings.Join([]string{secretsGetDomain, p.WorkflowID, p.ExecutionID, strconv.Itoa(int(p.CallbackID))}, "/")
}

func (h *Handler) checkOrCreatePendingRequest(key string) (*pendingRequest, error) {
	mine := &pendingRequest{done: make(chan struct{})}
	if h.pendingRequests.Add(key, mine, cache.DefaultExpiration) == nil {
		h.lggr.Debugw("registered pending relay request, executing", "key", key)
		return nil, nil
	}
	if existing, ok := h.pendingRequests.Get(key); ok {
		if p, ok := existing.(*pendingRequest); ok {
			h.lggr.Debugw("relay request already in flight, waiting for its result", "key", key)
			return p, nil
		}
	}
	h.lggr.Errorw("pending request cache holds an entry of unexpected type", "key", key)
	return nil, fmt.Errorf("pending set holds an invalid entry for key %q", key)
}

func (h *Handler) completePendingRequest(key string, signed any) {
	if v, ok := h.pendingRequests.Get(key); ok {
		if pr, ok := v.(*pendingRequest); ok {
			pr.signed = signed
			close(pr.done)
		}
	}
	h.pendingRequests.Delete(key)
}

// failPendingRequest publishes the owner's failure to any waiters and clears
// the entry. err is the error the owner is answering with — a relayError, so
// it carries that answer's JSON-RPC code — which lets waiters report the real
// cause (vault failure, missing execution handler, ...) rather than a vague
// error of their own.
func (h *Handler) failPendingRequest(key string, err error) {
	h.lggr.Debugw("publishing pending relay request failure", "key", key, "err", err)
	if v, ok := h.pendingRequests.Get(key); ok {
		if pr, ok := v.(*pendingRequest); ok {
			pr.err = err
			close(pr.done)
		}
	}
	h.pendingRequests.Delete(key)
}

// waitForPendingRequest blocks until the owner publishes its outcome — a
// signed result, or the error it failed with — or until ctx is done. ok is
// false only on the caller's own deadline; the gateway has already timed that
// request out by then. The owner writes the fields before closing done, so
// observing the close is enough to read them.
func waitForPendingRequest(ctx context.Context, pr *pendingRequest) (signed any, ok bool, err error) {
	select {
	case <-pr.done:
		return pr.signed, true, pr.err
	case <-ctx.Done():
		return nil, false, nil
	}
}
