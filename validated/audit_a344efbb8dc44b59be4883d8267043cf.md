### Title
Webhook `shop` tenant identifier is not covered by the HMAC signature, enabling cross-tenant impersonation via header substitution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC computed over the raw request body, but the `shop` field that downstream handlers use to attribute the webhook to a tenant is read from an HTTP header that is never included in the signed bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor, however, is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is parsed independently of the signature computation: [2](#0-1) .

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)` and then immediately hands `request.shop` to the registered handler as the tenant identifier, with no additional binding check between the verified body and the unverified header: [3](#0-2) .

`HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (i.e., the raw body) using `Context.api_secret_key`, a single secret shared across all shops connected to the app: [4](#0-3) .

**Binding that should hold:** `shop_header == shop_that_produced(raw_body, hmac)`.
**Binding actually enforced:** `hmac == HMAC(raw_body, client_secret)`, with `shop_header` entirely unconstrained.

Because the app's `client_secret` — and therefore the HMAC — is identical for every shop installation of the app, a webhook payload and its valid `hmac-sha256` header captured from tenant A's traffic remains cryptographically valid if replayed with the `shop-domain` header swapped to tenant B. The gem performs no cross-check that the body content (e.g., embedded resource/shop identifiers) matches the claimed `shop` header, so `WebhookMetadata.new(... shop: request.shop ...)` passed to the handler can misattribute an authentic, HMAC-valid payload to an arbitrary shop of the attacker's choosing.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (as returned by this gem) to select which tenant's data/session/state to update will act on attacker-chosen tenant data while believing the payload is authenticated — this is a cross-tenant access primitive: an attacker who can capture (or replay) one legitimate signed webhook body can cause the app to process it as if it belonged to a different shop, since the only verification (`HmacValidator.validate`) does not bind the header-derived `shop` to the signed bytes.

### Likelihood Explanation
Exploitation requires capturing or replaying a single valid `raw_body` + `hmac-sha256` pair (e.g., via a webhook subscription the attacker's own shop can receive) and re-delivering it to the app's webhook endpoint with a forged `shop-domain` header — this does not require the `client_secret`, an access token, or any privileged account, only network delivery to the app's public webhook endpoint, which is unprivileged-internet-reachable by design. Likelihood is bounded by whether the host app's webhook endpoint is reachable without additional network-layer protections (e.g., IP allow-listing of Shopify's servers), which this gem does not enforce or document as mandatory.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`) values into the signed material, or otherwise cryptographically tie the header-derived tenant identifier to the verified body — for example, require the host application (and this gem's `Registry.process`) to cross-validate `request.shop` against a shop identifier embedded in `parsed_body`, or extend `to_signable_string` to canonically include the shop-domain header before computing/verifying the HMAC.

### Proof of Concept
1. Attacker's own shop `attacker.myshopify.com` receives a legitimately signed webhook: raw body `B`, header `X-Shopify-Hmac-Sha256: H = HMAC(client_secret, B)`, header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays the exact same `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com", hmac-sha256: H...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and finds it equal to `H` — validation passes [5](#0-4) .
4. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with `shop == "victim.myshopify.com"` even though the payload actually originated from and pertains to `attacker.myshopify.com` [6](#0-5) .
