### Title
Emporium CASE 2 stateless calls share a single msg.sender identity, letting any user hijack a victim's on-chain order/escrow refund - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 branch executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract, so every stateless op from every Hinkal user is executed with the same `msg.sender == Emporium`. If a victim uses this path to create state on an external contract that is keyed by caller address (e.g. `createLimitOrder`, `maker = msg.sender`), any other user's later CASE 2 op that triggers a refund to that same shared address will have the refunded balance attributed to whoever's transaction happened to trigger it, via the balance-diff + `handleOut` mechanism.

### Finding Description
Equality claimed broken: `UTXO.owner_stealth_address == victim_stealth_address_that_locked_the_funds`. Actual result: `UTXO.owner_stealth_address == attacker_stealth_address`.

- Victim's `transact()` → `_externalTransact` → `EmporiumUpgradeable.runAction`, CASE 2 branch, calls the router with `msg.sender == Emporium` [1](#0-0) . The router records `maker = Emporium`, not any per-user identifier, because Hinkal's architecture has no per-victim identity in this call path (unlike CASE 1, which explicitly routes through the user's own `IHinkalWallet(stack.signerAddress)` precisely to preserve stateful caller identity) [2](#0-1) .
- Attacker's own, later, unrelated `transact()` call also routes a CASE 2 op through Emporium (`cancelOrder(orderId)`), again with `msg.sender == Emporium`, which the router authorizes since it's checking `msg.sender == maker == Emporium` and refunds the locked tokens back to `msg.sender == Emporium`.
- Inside the *attacker's* call to `runAction`, `balancesAfter - balancesBefore` now includes the victim's refunded tokens [3](#0-2) . `handleOut` mints a UTXO for that balance increase directly to `circomData.stealthAddressStructure`, which is the *attacker's own* stealth address taken from the attacker's own `CircomData` [4](#0-3) .
- Back in `Hinkal.transact`, the balance-conservation check only verifies that the token balance change *at the Hinkal contract level* equals `amountChanges[i] + utxoAmount` [5](#0-4) . Since the attacker fully controls both `amountChanges[i]` and the out-UTXO amount in their own proof/CircomData, this equation is trivially self-consistent — it enforces nothing about *whose* funds originated the balance increase, only that the attacker's declared numbers match the observed diff.
- Existing guards (`dimensionsCheck`, `checkOnchainCreation`, `performHinkalChecks`) only check array-length consistency, calldata-hash integrity, relay validity, and that on-chain-creation UTXOs have zero `amountChanges`/nullifiers [6](#0-5) . None of them tie an output UTXO or a balance increase back to the specific prior depositor who caused an external protocol to hold that balance; there is no linkage between the victim's original locked funds and any spend authorization the attacker must produce (no requirement that the attacker present nullifiers proving ownership of a UTXO corresponding to that value).

Root cause: Emporium's CASE 2 "Stateless Interaction" path is architected to be a **shared identity** for many unrelated users' calls; the protocol's only defense against misattribution is a same-transaction balance diff, which cannot distinguish "funds I already owned" from "funds some external protocol happened to release to Emporium's shared address during my call because a previous, unrelated user parked value there."

### Impact Explanation
Any victim who uses CASE 2 (rather than CASE 1's dedicated per-user `IHinkalWallet`) to interact with an external contract that ties state/authorization to caller address (limit order books, escrows, staking positions with withdraw-to-caller semantics, etc.) has their locked value exposed to theft by any other unrelated Hinkal user, at zero cost beyond gas, and repeatable for every victim who makes this mistake. This is direct theft of a victim's escrowed/locked value by an unrelated party, and constitutes minting a UTXO not backed by any input the attacker legitimately owns — matching the Critical category (direct theft of shielded/in-flight user funds, minting value without backing).

### Likelihood Explanation
Preconditions: (1) a victim's CASE 2 op creates persistent, caller-keyed state on an external contract (a normal, common pattern for order books/escrows — not itself a "defect" of the external protocol, but incompatible with Emporium's shared-identity model); (2) that external state remains uncollected/uncancelled by the time an attacker acts. No privileged role, no relayer compromise, and no bug in the external router is required — this is a consequence of the CASE 2 code path in this repo always using `msg.sender == Emporium` for arbitrary users. The attack is fully within reach of an unprivileged EOA who can craft their own `CircomData`/`EmporiumStack` and generate a valid proof for their own (even zero-value) inputs.

### Recommendation
Do not allow CASE 2 ("stateless") calls to be used for operations that create externally-persisted, caller-keyed state at the Emporium address. Concretely: either (a) restrict CASE 2 target calldata to a vetted allow-list of genuinely atomic/stateless operations (e.g., swaps that settle entirely within the call), or (b) require any stateful operation (order creation/cancellation, deposits with delayed withdrawal) to go exclusively through CASE 1's per-user `IHinkalWallet`, and reject CASE 2 selectors that are known to create maker/owner-keyed external state. Additionally, consider adding a Emporium-level accounting ledger that attributes any pre-existing balance held by Emporium to the depositing transaction/stealth-address rather than relying purely on a same-transaction balance diff.

### Proof of Concept
Foundry test plan:
1. Deploy a mock limit-order router with `createLimitOrder(...)` recording `orders[id].maker = msg.sender` and locking `amountIn` from `msg.sender`, and `cancelOrder(id)` requiring `msg.sender == orders[id].maker`, refunding `amountIn` to `msg.sender`.
2. Victim calls `Hinkal.transact` with `externalActionData.externalActionId = EMPORIUM_ID`, `EmporiumStack.ops[0] = {invokeWallet:false, endpoint: router, callData: createLimitOrder(...)}` (CASE 2), depositing `amountIn` of tokenX into Emporium via negative `amountChanges`. Assert router state shows `orders[id].maker == address(emporium)`.
3. Attacker (unrelated address, own stealth key) calls `Hinkal.transact` with their own `CircomData`/proof, `EmporiumStack.ops[0] = {invokeWallet:false, endpoint: router, callData: cancelOrder(id)}` (CASE 2), `amountChanges` for tokenX = 0, and an out-UTXO in `outCommitments` for tokenX equal to `amountIn`.
4. Assert the call succeeds, `handleOut` mints `UTXO.amount == amountIn` to the attacker's `stealthAddressStructure`, and the victim never receives any UTXO/refund for the locked `amountIn` — i.e. `attacker_UTXO.amount == victim_locked_amount` while `victim_stealth_address` received nothing, proving the equality break described above.

    function handleOut(
        int256 balanceChange,
        CircomData calldata circomData,
        uint256 i
    ) internal returns (UTXO memory outUtxo) {
        // total change can be less than zero if there was some balance before the call -> that's why we have <=
        if (balanceChange <= 0) {
            return outUtxo;
        }

        transferERC20TokenOrETH(
            circomData.erc20TokenAddresses[i],
            msg.sender,
            uint256(balanceChange)
        );

        outUtxo = UTXO(
            uint256(balanceChange),
            circomData.erc20TokenAddresses[i],
            circomData.stealthAddressStructure,
            circomData.timeStamp
        );
    }
