### Title
Non-embedded session ID trusted directly from an unauthenticated cookie value - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` derives the session identifier that a host application uses to look up a merchant's stored `Session` (and therefore the access token bound to a shop) directly from the raw browser cookie value, with no cryptographic verification that the cookie was actually issued by this gem's OAuth flow for that shop.

### Finding Description
For non-embedded apps (and as a fallback for embedded apps without a session token), `current_session_id` requires only that `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` be present, then returns that value verbatim via `cookie_session_id`: [1](#0-0) [2](#0-1) 

Compare this to the embedded/JWT path, where the session id is computed only after the token has been cryptographically verified against `Context.api_secret_key` and its `aud`/expiry claims checked in `JwtPayload`: [3](#0-2) 

The non-embedded cookie path has no equivalent binding. The identity check being broken is:
`shop authenticated by OAuth == shop key used to fetch the session from storage`

On the write side, `Oauth.validate_auth_callback` does set the cookie value to the real, HMAC-verified `session.id` after a successful OAuth callback, and that `id` follows a predictable, deterministic format (`"offline_#{shop}"` for offline sessions, `"#{shop}_#{associated_user.id}"` for online sessions): [4](#0-3) 

But on the read side (`current_session_id` / `cookie_session_id`), nothing re-verifies that the value came from that flow or is unmodified — it is simply pulled out of the cookie hash and handed back as the session key. Because the format `offline_{shop-domain}` is fully deterministic and publicly guessable (shop domains are public), any party able to set or overwrite that specific cookie name for the app's origin can supply an arbitrary value such as `offline_victim-shop.myshopify.com`, and this gem will return that string as the "current session id" with no signature, MAC, or expiry check performed by the library itself.

### Impact Explanation
If the host application follows the gem's documented pattern of using the value returned by `current_session_id` as the lookup key into its own session/token store (as shown in the gem's own OAuth usage documentation), an attacker who can influence this specific cookie's value can cause the returned identifier to resolve to a different shop's stored access token — a cross-tenant session/token disclosure. This maps to the report's "identity binding not enforced" theme (fee params not bound to on-chain checks) applied here as "session id not bound to any signature/HMAC" — a direct match to the explicitly allowed analog class "a session id derived from unauthenticated bytes."

### Likelihood Explanation
Exploitation of this specific weakness inside the gem requires that the attacker be able to set or overwrite the named cookie for the app's origin (e.g., via a cookie-injection vector, subdomain cookie scoping, or lack of `__Host-`/signing protections in the surrounding web framework). The gem itself performs no independent verification, so the residual risk is entirely deferred to hygiene outside this library's own code; likelihood as a self-contained bug in this gem is therefore moderate-to-low, but the gap (no HMAC/signature check on the returned session id) is real and verifiable purely from `lib/shopify_api/utils/session_utils.rb`.

### Recommendation
Do not treat the raw cookie value as a trusted session key. Instead:
- Sign/HMAC the cookie value (e.g., with `Context.api_secret_key`) when it is set in `Oauth.validate_auth_callback`, and verify that signature in `SessionUtils.cookie_session_id` before returning it.
- Alternatively, avoid embedding the deterministic `shop`/`offline_{shop}` string directly in a client-readable, unsigned cookie; use an opaque, unguessable token instead and map it server-side to the actual session id.

### Proof of Concept
1. A legitimate merchant `victim-shop.myshopify.com` completes OAuth; the gem sets a cookie `shopify_session_id = offline_victim-shop.myshopify.com` per `Oauth.validate_auth_callback` → `Session.from`. [5](#0-4) 
2. An attacker who can set/overwrite this same-named cookie in their own browser session against the app (e.g., via a cookie-injection bug in the surrounding framework, or lack of cookie signing) sets `shopify_session_id = offline_victim-shop.myshopify.com` manually — this value is entirely predictable since shop domains are public.
3. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` without any verification: [1](#0-0) 
4. The host application looks up its stored session/access token using this id and returns `victim-shop`'s access token to the attacker's request context — a cross-tenant session identity confusion rooted in the fact that this gem's `current_session_id`/`cookie_session_id` never binds the returned identifier to any signature over the original OAuth-issued cookie.

              session_id_from_shopify_id_token(id_token: id_token, online: online)

          end
        end

        sig { params(shop: String, access_token_response: Oauth::AccessTokenResponse).returns(Session) }
        def from(shop:, access_token_response:)
          is_online = access_token_response.online_token?

          if is_online
            associated_user = T.must(access_token_response.associated_user)
            associated_user_scope = access_token_response.associated_user_scope
            id = "#{shop}_#{associated_user.id}"
          else
            id = "offline_#{shop}"
          end

          if access_token_response.expires_in
            expires = Time.now + access_token_response.expires_in.to_i
          end

          if access_token_response.refresh_token_expires_in
            refresh_token_expires = Time.now + access_token_response.refresh_token_expires_in.to_i
          end

          new(
            id: id,
            shop: shop,
            access_token: access_token_response.access_token,
            scope: access_token_response.scope,
            is_online: is_online,
            associated_user_scope: associated_user_scope,
            associated_user: associated_user,
            expires: expires,
            shopify_session_id: access_token_response.session,
            refresh_token: access_token_response.refresh_token,
            refresh_token_expires: refresh_token_expires,
          )
        end
