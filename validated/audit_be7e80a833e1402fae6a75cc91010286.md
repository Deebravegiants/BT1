Confirmed: the docs explicitly claim `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and `data.shop` is documented as "The shop domain of the webhook" that handlers are meant to trust [2](#0-1) , but the actual HMAC only covers `@raw_body`.

### Title
Webhook `shop-domain`, `topic`, `webhook_id`, and `api_version` Headers Are Not Covered by the HMAC, Allowing Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers. `ShopifyAPI::Utils::HmacValidator.validate` only checks that the body's HMAC matches, so any attacker who can obtain one genuinely-signed `(raw_body, hmac)` pair (trivially, by installing the app on their own store and registering any webhook topic) can replay that same body+hmac to the app's webhook endpoint while forging a different `shop-domain`, `topic`, or `webhook_id` header. `Registry.process` will treat this as a legitimately verified webhook for the victim shop.

### Finding Description
`Registry.process` gates all webhook handling on a single check:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
``` [3](#0-2) 

`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [4](#0-3) 

For webhook requests, `to_signable_string` is defined as just the raw body:
```ruby
def to_signable_string
  @raw_body
end
```
while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from attacker-controllable HTTP headers with no cryptographic binding to the body or the HMAC:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [5](#0-4) 

The identity equality that should hold is: `shop asserted by the HMAC-signed bytes == shop acted upon by the handler`. In reality, only the body is authenticated; `shop` (and `topic`/`webhook_id`) are taken from headers that are never included in `to_signable_string`, so this equality does not hold. This matches the report's bug class of "a field acted on but not covered by the HMAC."

Because Shopify signs webhooks per-app (using the app's single `client_secret`) rather than per-shop, any store owner who installs the app — an ordinary, unprivileged action requiring no special access — receives genuinely HMAC-signed webhook deliveries for their own store. The attacker can capture one such `(raw_body, hmac)` pair (e.g., from a webhook topic whose body content they don't care about, or from a store they fully control) and replay it to the app's public webhook endpoint with the `shop-domain` header rewritten to the victim's `myshopify.com` domain, and/or the `topic`/`webhook_id` headers rewritten to any topic registered by the app. `Utils::HmacValidator.validate` still succeeds because it only checks the (unmodified) body against the (unmodified) hmac; `Registry.process` then dispatches to the handler with:
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [6](#0-5) 

The host application's handler receives `shop: request.shop` believing it has been authenticated by the gem (the docs explicitly say `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0)  and describe `data.shop` as trustworthy metadata [2](#0-1) ), when in fact the shop identity is entirely attacker-controlled.

### Impact Explanation
This is a cross-tenant confusion vulnerability. Any host application that keys its webhook business logic off `data.shop` (as the gem's own documentation instructs) can be made to process an attacker-chosen payload while believing it originated from an arbitrary victim shop the attacker does not control — e.g., triggering data deletion/GDPR flows, cache invalidation, order/product state changes, or other side effects scoped to the victim's tenant, using content the attacker fully controls (their own genuinely-signed body). This satisfies the Critical "cross-tenant access" impact bar since it breaks the shop-identity boundary the gem is documented to enforce.

### Likelihood Explanation
Likelihood is high: obtaining a valid `(raw_body, hmac)` pair requires nothing more than installing the target app on any store (a normal, unprivileged onboarding flow) and registering any webhook topic; from there, forging the `shop-domain`/`topic`/`webhook_id` headers on a replayed HTTP request to the app's public webhook endpoint is trivial and requires no credentials, tokens, or knowledge of `api_secret_key`.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the HMAC-signed material (`to_signable_string`), or otherwise cryptographically bind these header-derived fields to the verified body (e.g., require the host app to cross-check `request.shop` against a shop known to have installed the app / registered that specific webhook, rather than trusting the header value implicitly once `HmacValidator.validate` passes).

### Proof of Concept
1. Attacker installs the target Shopify app on a store they control (`attacker-shop.myshopify.com`) and registers a webhook for any topic the app subscribes to.
2. Shopify delivers a genuine webhook to the app's registered endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker replays an HTTP POST to the same app endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed by the app and passed to `Registry.process`.
5. `Utils::HmacValidator.validate(request)` returns `true` because it only recomputes the HMAC over `B`, which is unchanged.
6. `Registry.process` invokes the app's handler with `data.shop == "victim-shop.myshopify.com"`, even though the request never originated from or was authorized by that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
