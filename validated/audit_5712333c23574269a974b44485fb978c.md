## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook request by HMAC-validating only the raw request body, then hands the `shop` value straight from an HTTP header — which is never part of the signed bytes — to the app's handler as the authoritative tenant identifier. This breaks the identity binding `verified_bytes == acted_on_bytes`: the HMAC-verified data is `raw_body` alone, while the data the handler treats as "the shop this event happened for" is the unauthenticated `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header.

### Finding Description
`ShopifyAPI::Webhooks::Request` extracts `shop` purely from a header: [1](#0-0) 

and the HMAC comparison is only ever computed over `@raw_body`: [2](#0-1) 

`Utils::HmacValidator.validate` simply signs `to_signable_string` (the raw body) with `Context.api_secret_key` and compares it to the `hmac-sha256` header — it never mixes in `shop`, `topic`, or `webhook-id`: [3](#0-2) 

`Registry.process` treats a passing HMAC check as sufficient authentication for the entire request, then forwards the unauthenticated `shop` header to the handler as trusted metadata: [4](#0-3) 

Because the signed payload (`raw_body`) and the value the handler acts on (`shop` header) are disjoint, any attacker who has legitimately received one authentic webhook body+HMAC pair (e.g. by installing the app on their own shop, a low-privilege, unauthenticated-relative-to-other-tenants action) can replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting a different `shop-domain` header. `Utils::HmacValidator.validate` will still pass, because it only checks the body bytes, and `Registry.process` will call the app's handler with `WebhookMetadata.new(shop: <attacker-chosen shop>, ...)`. Any host application that uses this `shop` field to look up a session/access token and perform tenant-scoped side effects (the documented and expected usage per `docs/usage/webhooks.md`) will act on behalf of the wrong shop.

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled `shop` value, disjoint from the HMAC-verified bytes, is delivered to app logic as if it were an authenticated Shopify claim. Per the rules, cross-tenant access qualifies as Critical impact — an attacker can cause the app to process/act on data intended for a different merchant's shop by supplying a header value the library never authenticates.

### Likelihood Explanation
Requires the attacker to possess one valid (body, hmac) pair, which they trivially obtain by installing the target app on a shop they control (or any shop that will send it a webhook), then replaying that exact body/HMAC to the endpoint with a forged `shop-domain` header. This needs no access to `api_secret_key` and no privileged account — a very low bar consistent with an "unprivileged internet user" threat model.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (or otherwise cryptographically bind them), or require the caller to independently corroborate the `shop` header against a previously known/registered relationship before trusting it in `WebhookMetadata`. At minimum, document prominently that `request.shop` is unauthenticated and must not be used to select tenant-scoped resources without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering a legitimate webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with the app's real `api_secret_key`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same request to the app's webhook route, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` while keeping body `B` and header `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new` builds a request object where `hmac` returns the value from `H` and `shop` returns `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only, which still matches `H`, so validation passes — see `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` — see `lib/shopify_api/webhooks/registry.rb:188-200` — causing the host app to act as though the event originated from `victim-shop`.
