### Title
Anti-snipe launch delay measured in blocks collapses to near-zero on HyperEVM's variable block-time dispatch - (File: `packages/contracts/src/Bonding.sol`)

### Summary
`Bonding.LAUNCH_TRADING_DELAY_BLOCKS = 3` is a fixed block-count constant that is supposed to give a launching creator a short, snipe-free window before public buys are allowed on a freshly launched curve. This mirrors the reported oracle bug class: a duration expressed in blocks rather than `block.timestamp`, deployed on a chain whose block production is not a fixed 12s (or any fixed) interval.

### Finding Description
`Bonding.launch()` records `$.launchBlock[tokenAddr] = uint64(block.number)` [1](#0-0)  and gates every subsequent public `buy()` for `LAUNCH_TRADING_DELAY_BLOCKS = 3` blocks, opening trading only at `launchBlock + LAUNCH_TRADING_DELAY_BLOCKS + 1` [2](#0-1) . The natspec explicitly frames this as the protocol's "first-block-sniper mitigation," intended to give the creator's seed buy (which bypasses the gate via a transient-storage flag) a head start before any other address can buy in [2](#0-1) .

The project's own deployment documentation shows the target chain, HyperEVM, does not have a fixed block time at all — it has a "dual block dispatch" mode: small blocks (~2M gas, ~1s) and big blocks (~30M gas, ~60s), and this mode is a **per-wallet, persistent setting** toggled via an off-chain Hyperliquid L1 action (`evmUserModify`), not a network-wide parameter [3](#0-2) . The toggle script itself documents this: `usingBigBlocks` per address, ~1s vs ~60s confirmation cadence, controllable at will [4](#0-3) .

This is precisely the analog of the external report's root cause: a "6 hours" duration hard-coded as "1800 blocks" under a 12s-block assumption breaks the moment the underlying chain's block cadence differs from that assumption. Here, "a few seconds of front-run protection" is hard-coded as "3 blocks," but on HyperEVM the attacker (a sniper wallet, fully unprivileged) can unilaterally toggle itself into "small blocks" mode (~1s per block, the default) to make the 3-block window collapse to ~3 seconds of real time — trivially raceable by a bot watching the mempool/indexer for `TokenLaunched` — while the creator/deployer wallet may be sitting in a different block-cadence mode. There is no `block.timestamp`-based floor anywhere in the gate; it is pure `block.number` arithmetic [5](#0-4) .

### Impact Explanation
The anti-snipe delay is the system's only stated defense against a sniper front-running the creator's seed buy at launch (the docs literally call it "the system's first-block-sniper mitigation" combined with `MIN_SEED_USDC`) [2](#0-1) . If the effective real-time window shrinks from an intended multi-second/multi-block buffer to near-instant, a sniper can land in the very next block after the creator's seed lands, buying up the cheap early curve supply before organic buyers can react — extracting value that the anti-snipe delay was designed to deny them and degrading the fairness of every new token launch. This is a griefing/value-extraction vector against creators and early legitimate buyers on every `Zap.createToken` call, reachable by any unprivileged wallet with no special access.

### Likelihood Explanation
High reachability: the only actions needed are (1) an attacker's own wallet self-toggling to small-block mode (already the network default, requiring no privileged action, per the documented `toggle-big-blocks.mjs` script) and (2) submitting `Zap.buy` immediately after observing `TokenLaunched`/the creator's seed buy. No permissioned role, no upgrade, no oracle manipulation is required — only the natural, chain-specific block cadence documented by the project itself.

### Recommendation
Replace the `block.number`-based `launchBlock` / `LAUNCH_TRADING_DELAY_BLOCKS` gate with a `block.timestamp`-based delay (e.g., record `launchTimestamp` and require `block.timestamp >= launchTimestamp + LAUNCH_TRADING_DELAY_SECONDS`), matching the EVM-portable pattern recommended in the referenced report. This removes the dependence on HyperEVM's variable, wallet-toggleable block cadence and gives a consistent real-time anti-snipe buffer regardless of which block-dispatch mode any given wallet is using.

### Proof of Concept
1. Creator calls `Zap.createToken(...)` → `Bonding.launch()` records `launchBlock = block.number` and the seed buy consumes the transient bypass in the same tx [5](#0-4) .
2. An unprivileged attacker wallet ensures it is operating in HyperEVM's default "small blocks" mode (~1s/block) — the documented default, no `evmUserModify` action needed [4](#0-3) .
3. Attacker watches for the `TokenLaunched`/`Trade` event and submits `Zap.buy(tokenAddr, usdcAmount, 0, address(0))` as soon as `block.number >= launchBlock + LAUNCH_TRADING_DELAY_BLOCKS + 1` — which, at ~1s/block, is only ~4 seconds after launch instead of the many-block buffer the constant's comments imply is meant to deter sniping.
4. Attacker's buy lands at the still-near-launch curve price, ahead of legitimate buyers who react on normal human/UI timescales, defeating the intended anti-snipe protection purely because the delay is denominated in blocks rather than seconds.
