### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` value that identifies which tenant the webhook belongs to is read from an HTTP header that is never included in the HMAC computation. Because the HMAC secret (`Context.api_secret_key`) is per-app, not per-shop, this breaks the binding between "the shop the signature proves the webhook came from" and "the shop the handler is told the webhook came from."

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic binding to the signed body: [2](#0-1) 

`HmacValidator.validate` computes and compares the signature only against `verifiable_query.to_signable_string` (i.e., the body), never the shop header: [3](#0-2) 

`Registry.process` trusts this unverified `shop` field and forwards it straight into the handler's `WebhookMetadata`: [4](#0-3) 

The equality that should hold is: `shop cryptographically proven by HMAC == shop delivered to the handler`. Because the HMAC only covers the body and the secret (`Context.api_secret_key`) is shared across every shop that installs the app (it is not a per-shop key), any bytes that produce a valid HMAC for one shop produce an identical valid HMAC regardless of which `shop-domain` header accompanies them. An attacker who can obtain one genuine `(raw_body, hmac)` pair for the app (e.g., by installing the app on their own store and capturing a webhook Shopify sends them) can replay that exact body/HMAC pair while substituting an arbitrary `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event is for the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged user, using only a self-owned shop's legitimately signed webhook, can make the app process a webhook attributed to a different merchant's shop. Any application logic that uses `data.shop` to look up sessions, tokens, or trigger tenant-scoped side effects (order fulfillment, inventory sync, deleting data, sending notifications, etc., which is exactly what the `Handler#handle` API is designed for) can be tricked into acting as if the event came from the victim shop — cross-tenant access using only a resource the attacker legitimately controls (their own shop's webhook traffic).

### Likelihood Explanation
The attacker requirement is low: no access token, no `client_secret`, no privileged account, no TLS interception — only the ability to install the app on any shop (including a free/dev shop) and capture one webhook delivery, which Shopify sends automatically. The forged request is a straightforward HTTP replay/header substitution against the app's public webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the signed payload validated against the HMAC, or otherwise cryptographically bind the `shop-domain` header to the specific shop's registration/session before trusting it (e.g., verify the shop is a known, sanitized `ShopifyAPI::Utils::ShopValidator`-approved domain that actually has an active session/webhook registration, and reject shop/body combinations that don't match what was registered for that specific shop). At minimum, document/require host apps to independently verify `data.shop` against a known installed-shop list before granting all data access.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) to receive a genuine webhook delivery with a valid `x-shopify-hmac-sha256` header computed over the raw body using the app's shared `client_secret`.
2. Capture the raw body and the `x-shopify-hmac-sha256` value from that delivery.
3. Send a new HTTP POST to the app's webhook endpoint with the identical raw body and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic` to the desired topic.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` returns `true` (body unchanged), and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act on data intended for the victim shop.
