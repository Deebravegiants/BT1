### Title
Webhook `shop-domain` and `topic` identity fields are unauthenticated (excluded from HMAC binding), enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract is `hmac` + `to_signable_string`. For webhook requests, `to_signable_string` returns only the raw HTTP body: [1](#0-0) 

but the class also exposes `topic` and `shop`, both read directly from unauthenticated HTTP headers (`x-shopify-topic` / `shopify-topic`, `x-shopify-shop-domain` / `shopify-shop-domain`): [2](#0-1) 

`Utils::HmacValidator.validate` only ever computes and compares the HMAC over `to_signable_string`: [3](#0-2) 

`Webhooks::Registry.process` validates the HMAC, then immediately trusts `request.topic` and `request.shop` — fields that were never covered by that HMAC — to select the handler and construct the tenant-identifying `WebhookMetadata` passed to application code: [4](#0-3) [5](#0-4) 

The broken identity binding, stated as an equality that should hold but does not:
`shop authenticated by HMAC` ≠ `shop stored/used as tenant key in WebhookMetadata`.

Because the webhook HMAC secret is the app's `client_secret` (`Context.api_secret_key`), which is identical for every shop that has the app installed, a valid `(raw_body, hmac)` pair is **not shop-specific**. The same pair is cryptographically valid for the same raw body no matter which shop declares it via the `shop-domain` header, and no matter what `topic` header is attached.

### Impact Explanation
This breaks the multi-tenant identity boundary the gem is expected to provide to its host application: `Registry.process` hands `handler.handle` a `WebhookMetadata.shop` value that is fully attacker-controlled while only the raw body bytes are cryptographically verified. An attacker who controls (or has installed the app on) shop A can legitimately receive a genuine webhook with a valid `(body, hmac)` pair for shop A, then resend that exact pair to the app's webhook endpoint with the `shop-domain` header rewritten to shop B (a different tenant) and/or the `topic` header changed. `HmacValidator.validate` will pass because it never inspected either header, and the host app's handler will process attacker-supplied body content under a spoofed tenant identity (`data.shop == "shop-b.myshopify.com"`) and/or under a spoofed topic (e.g. redirecting body meant for one topic into a `customers/redact` or `shop/redact` handler). This is a cross-tenant identity confusion vulnerability rooted entirely in this gem's `Webhooks::Request`/`Registry` implementation, not a host-application misuse of documented API — the gem's own `to_signable_string` implementation is what excludes these identity fields from the signature.

### Likelihood Explanation
Any actor who can install the app on at least one shop (a normal, unprivileged action available to any Shopify merchant/developer for public or custom apps) can capture a genuine `(raw_body, hmac)` pair from their own tenant's webhook deliveries and replay it toward the app's public webhook endpoint with forged `shop-domain`/`topic` headers. No access to the app's `client_secret`, no TLS interception, and no privileged account is required — only the ability to trigger and observe one webhook for a shop the attacker controls.

### Recommendation
Include the identity-binding headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the signable string used for HMAC computation and verification, or otherwise cryptographically bind them to the body (e.g., verify `shop` against the session/store the app expects for that endpoint rather than trusting the header value alone). At minimum, `Webhooks::Registry.process` should not treat `request.shop`/`request.topic` as trusted merely because `HmacValidator.validate` returned true when those fields were excluded from the signed payload.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers any webhook subscribed by the app (e.g. `orders/create`), capturing the raw request: body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC_SHA256(client_secret, B)`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and same `hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com` (a different tenant using the same app) and, optionally, a different `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers into `shop`/`topic` without any cryptographic check on them (`lib/shopify_api/webhooks/request.rb:20-23`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes `HMAC_SHA256(client_secret, B)` and compares to `H` — it matches, because the signature never depended on the `shop`/`topic` headers (`lib/shopify_api/webhooks/registry.rb:190`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. The registered handler for the (possibly attacker-chosen) topic is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: <attacker's parsed body>, ...)` — the application now processes attacker-supplied data believing it originated from `victim.myshopify.com`.
