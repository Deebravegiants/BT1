### Title
Permanent Freezing of Escrowed Funds via Blacklist/Reverting Token Transfer to a Fixed Beneficiary in IntentGatewayV2 Withdraw/Cancel - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw()` releases escrowed order funds by calling `IERC20(token).safeTransfer(beneficiary, amount)` directly to an address that is fixed at order-placement time (`order.user` for refunds, `order.output.beneficiary` for fills) and never validated for transferability. This mirrors the reported bug class: a withdraw/cancel path unconditionally pushes tokens to a recipient address without checking whether that recipient can actually receive the token, so a non-receivable recipient (e.g. blacklisted by a compliance-gated ERC-20 such as USDC/USDT, or simply an address a malicious/careless input made unable to receive tokens) permanently locks the escrow.

### Finding Description
`_withdraw` is the single settlement primitive used by both the cancellation and fill-redemption cross-chain paths: [1](#0-0) 

It is invoked from two unprivileged, message-driven entry points that a relayer (an untrusted, permissionless actor) triggers by delivering a Hyperbridge message:

- `onAccept` for `RedeemEscrow`/`RefundEscrow` cross-chain deliveries: [2](#0-1) 

- `onGetResponse` for source-side cancellation, after Hyperbridge proves the order was never filled on the destination: [3](#0-2) 

The beneficiary in both flows is taken verbatim from the order — `order.user` for cancellations, and `order.output.beneficiary`/`msg.sender` embedded at fill time for redemptions — and is never checked against `is_account_registered`-style validation, nor is the transfer wrapped in a way that isolates a single bad token/recipient interaction from the rest of the batch. If any one `TokenInfo` entry in `body.tokens` targets an ERC-20 whose `transfer`/`transferFrom` reverts for that specific beneficiary (e.g., a USDC/USDT-style blacklist, a paused token, or any non-standard ERC-20 with recipient-side restrictions), the `safeTransfer` call reverts, which reverts the entire `_withdraw` loop — and therefore the entire `onAccept`/`onGetResponse` message handling.

Because `onAccept`/`onGetResponse` is the terminal ISMP delivery for that message, a relayer can keep resubmitting the same proof/message and it will deterministically revert every time (the beneficiary and token list are baked into the message body/commitment and cannot be altered post hoc). There is no fallback, no per-token isolation (e.g., try/catch to skip a failing token while releasing the others), and no mechanism to redirect the beneficiary. All input tokens escrowed under that commitment — not just the incompatible one — remain locked in `_orders[commitment][token]` forever, since `_filled[commitment]` is never set (the `finalize` branch that sets it runs only after the loop completes without reverting).

### Impact Explanation
This causes permanent freezing of user/protocol funds: once an order's beneficiary is incompatible with even one of its escrowed input tokens, neither the cancel-from-source, cancel-from-destination, nor the solver's fill-redemption path can ever complete, because they all funnel through the same reverting `_withdraw`. The affected escrow (potentially multiple tokens in the same order) is stuck permanently with no governance or user recovery path exposed in this contract. This qualifies as Medium/High severity per the DoS/fund-freezing class in the analog report, reachable by any user who places an order with a beneficiary/token combination that a compliance-gated token can later blacklist, or by an attacker crafting/spoofing similar conditions for griefing.

### Likelihood Explanation
Likelihood is realistic: many top ERC-20 tokens (USDC, USDT, and various stablecoins) implement recipient blacklisting that can be applied after order placement but before settlement, and the Intent Gateway explicitly supports arbitrary ERC-20 tokens in `TokenInfo.token`. A user's own beneficiary address could become blacklisted between order placement and cancellation/fill, or a malicious order creator/solver could deliberately target a beneficiary/token pair known to revert, griefing their own escrow or another party's expected redemption to force a permanent lock (denial of settlement) — no elevated privileges are required beyond normal permissionless calls to `placeOrder`/`cancelOrder`/`fillOrder`.

### Recommendation
Isolate each token transfer in `_withdraw` (and in `_sweepDust`) with a low-level call/try-catch so a single failing transfer does not block release of the other escrowed tokens, and/or add a recovery mechanism (e.g., an escrow-to-alternate-address sweep gated by governance, or a pull-based claim pattern) so funds are not irrecoverably stuck when a beneficiary cannot receive a particular token. At minimum, consider validating at order-placement time (or before dispatching refund/redeem messages) that the beneficiary can receive the escrowed tokens, analogous to `coin::is_account_registered` in the original report.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2.placeOrder` with `order.user` = address `B`, escrowing input token `X` (a USDC-like token with a blacklist) and token `Y`.
2. Token `X` later blacklists address `B` (a normal, expected operational event for compliance-gated stablecoins, or triggered adversarially against a target).
3. User (or anyone after the deadline) calls `cancelOrder` from the destination chain; `_cancelFromDest` dispatches a `RefundEscrow` message to the source chain: [4](#0-3) 
4. The relayer delivers this to the source chain's `onAccept`, which calls `_withdraw(body, true, true)`: [1](#0-0) 
5. The loop reaches token `X`, calls `IERC20(X).safeTransfer(B, amount)`, which reverts because `B` is blacklisted. The whole `onAccept` transaction reverts.
6. Every retry by any relayer reverts identically since `commitment`, `beneficiary`, and `tokens` are fixed in the signed/committed message body — both token `X` and token `Y`'s escrow are now permanently unrecoverable.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }

    function _cancelFromDest(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.deadline >= _blockNumber()) {
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();
        }

        _filled[commitment] = address(uint160(uint256(order.user)));

        _post(
            order, _body(RequestKind.RefundEscrow, commitment, order.inputs, order.user), options.relayerFee, msg.value
        );
    }
