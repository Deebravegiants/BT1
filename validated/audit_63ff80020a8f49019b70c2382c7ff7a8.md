Audit Report

## Title
Colliding `RemoteLockedFungibles` keys after XCM-version migration strand a locked-fungible record forever, making its remote-lock bookkeeping unreachable via `request_unlock` - ([File: polkadot/xcm/pallet-xcm/src/migration.rs])

## Summary
`migrate_data_to_xcm_version`'s key-migration step for `RemoteLockedFungibles` skips the swap of `old_key` -> `new_key` (only logging an error and `continue`ing) whenever a record already exists at the computed `new_key`, permanently leaving the old-keyed record un-migrated and orphaned. Because `note_unlockable` always writes new records keyed by the pallet's current `XCM_VERSION`, and `prepare_reduce_unlockable` always looks up records using the current `XCM_VERSION`, a legitimately-created old-keyed record that collides with a newer record at migration time can never again be reached by the standard `RequestUnlock` flow.

## Finding Description
`RemoteLockedFungibles` entries are created only by `Pallet::<T>::note_unlockable`, which computes the storage key as `(XCM_VERSION, account, id)` using the crate's currently compiled `XCM_VERSION` constant. [1](#0-0) 

This function is reachable by an unprivileged signed user via the `LockAsset`/`NoteUnlockable` XCM instructions processed in the executor. [2](#0-1) 

The `migrate_data_to_xcm_version` routine (in `polkadot/xcm/pallet-xcm/src/migration.rs`) performs a two-step migration of `RemoteLockedFungibles`: first migrating record *data* (owner/locker versions), then migrating storage *keys*. In the key-migration loop, before swapping `old_key` to `new_key`, it checks whether `new_key` is already populated; if so, it logs an error and `continue`s without migrating, leaving `old_key`'s record in place, unmigrated: [3](#0-2) 

`prepare_reduce_unlockable`, which is invoked from the `RequestUnlock` XCM instruction (also reachable via a signed extrinsic), computes its lookup key strictly using the *current* `XCM_VERSION`, never the stale/old key: [4](#0-3) 

Consequently, if an account has two `RemoteLockedFungibles` entries — one created under an older `XCM_VERSION` epoch and one under a newer epoch — that normalize to the same `(latest_version, account, asset_id)` key after a runtime bump, the migration's collision-avoidance logic silently strands the older entry at its old key forever, with no merge or reconciliation, and no future migration attempt can recover it (it will hit the same "already exists" check on every subsequent run). Since `prepare_reduce_unlockable` can never construct anything but the current-version key, the account permanently loses standard on-chain access to the stranded record's `amount`/`consumers` bookkeeping.

I confirmed this code matches the described behavior exactly in the current repository state: the collision check and `continue` in `migration.rs` lines 340-350, and the current-version-only key derivation in both `note_unlockable` (line 3784) and `prepare_reduce_unlockable` (line 3812), are present verbatim as described in the claim.

## Impact Explanation
The stranded `RemoteLockedFungibleRecord.amount` represents bookkeeping required to authorize unlocking funds locked on a remote chain via `UnlockAsset`. Losing addressability of this record via the standard `RequestUnlock`/`prepare_reduce_unlockable` path means the owner can no longer issue a valid on-chain proof to unlock the corresponding remote lock through this mechanism, effectively freezing that specific remotely-locked balance from this chain's perspective. This is a real, in-scope "funds unlockable/frozen" type impact, not a cosmetic or informational bug — the existing test suite (`migrate_data_to_xcm_version_works`) exercises this exact code path and confirms the "skip" behavior is a deliberate but unremediated fallback ("let's just skip for now ... could be potentially caused with missing this migration before (manual clean-up?)"), which the code comment itself acknowledges as an unresolved edge case.

## Likelihood Explanation
Triggering the strand requires: (1) an account creating a `RemoteLockedFungibles` entry for a given remote asset under one `XCM_VERSION` epoch, (2) a runtime upgrade bumping `XCM_VERSION` (a privileged/governance event, but a normal and recurring part of the chain's lifecycle), (3) the same account creating another lock for the same normalized asset id under the new epoch (both are ordinary unprivileged `lock_asset` actions), and (4) the version-migration routine running and hitting the collision. None of these steps require attacker privilege, mocked state, or direct storage writes — they are all reachable via ordinary signed extrinsics and normal chain-upgrade cadence. The precise "same asset id normalizes identically" and "two epochs of locking" conditions do narrow the practical frequency, but they are far from implausible for a long-lived account that routinely locks/unlocks the same bridged/remote asset across chain upgrades.

## Recommendation
On key collision in the `RemoteLockedFungibles` key-migration step, do not silently skip and orphan the old record. Instead, merge the old record into the existing new-key record — validating that `locker`/`owner` match and combining `amount` (e.g., `max` or `saturating_add`, consistent with the merge logic already present in `note_unlockable`) and `consumers` — or fail the runtime upgrade/migration explicitly so operators are forced to reconcile manually rather than silently losing bookkeeping. At minimum, emit a persistent, actionable on-chain event/alert (not just a log) so affected accounts can be identified and remediated.

## Proof of Concept
1. In `polkadot/xcm/pallet-xcm/src/tests/mod.rs`, extend `migrate_data_to_xcm_version_works`:
   - Insert `key_old = (previous_version, account, asset_id.into_version(previous_version))` with a nonzero `amount`/`consumers`.
   - Insert `key_new = (latest_version, account, asset_id)` for the same account/asset with a different `amount`/`consumers`, simulating a second lock created after a version bump.
2. Call `Pallet::<Test>::migrate_data_to_xcm_version(&mut Weight::zero(), latest_version)`.
3. Assert `RemoteLockedFungibles::<Test>::get(&key_old)` is still `Some(..)` (unmigrated) and `RemoteLockedFungibles::<Test>::get(&key_new)` is unchanged — confirming the collision `continue` path.
4. Call `Pallet::<Test>::prepare_reduce_unlockable(locker, asset, owner)` (the function invoked by `RequestUnlock`) and show it only ever resolves `key_new`, proving `key_old`'s locked amount/consumers are permanently unreachable through the standard unlock path, even though real funds were locked remotely against that record.

		locker: Location,
		asset: Asset,
		mut owner: Location,
	) -> Result<(), xcm_executor::traits::LockError> {
		use xcm_executor::traits::LockError::*;
		ensure!(T::TrustedLockers::contains(&locker, &asset), NotTrusted);
		let amount = match asset.fun {
			Fungible(a) => a,
			NonFungible(_) => return Err(Unimplemented),
		};
		owner.remove_network_id();
		let account = T::SovereignAccountOf::convert_location(&owner).ok_or(BadOwner)?;
		let locker = locker.into();
		let owner = owner.into();
		let id: VersionedAssetId = asset.id.into();
		let key = (XCM_VERSION, account, id);
		let mut record =
			RemoteLockedFungibleRecord { amount, owner, locker, consumers: BoundedVec::default() };
		if let Some(old) = RemoteLockedFungibles::<T>::get(&key) {
			// Make sure that the new record wouldn't clobber any old data.
			ensure!(old.locker == record.locker && old.owner == record.owner, WouldClobber);
			record.consumers = old.consumers;
			record.amount = record.amount.max(old.amount);
		}
		RemoteLockedFungibles::<T>::insert(&key, record);
		Ok(())
	}

	fn prepare_reduce_unlockable(
		locker: Location,
		asset: Asset,
		mut owner: Location,
	) -> Result<Self::ReduceTicket, xcm_executor::traits::LockError> {
		use xcm_executor::traits::LockError::*;
		let amount = match asset.fun {
			Fungible(a) => a,
			NonFungible(_) => return Err(Unimplemented),
		};
		owner.remove_network_id();
		let sovereign_account = T::SovereignAccountOf::convert_location(&owner).ok_or(BadOwner)?;
		let locker = locker.into();
		let owner = owner.into();
		let id: VersionedAssetId = asset.id.into();
		let key = (XCM_VERSION, sovereign_account, id);

		let record = RemoteLockedFungibles::<T>::get(&key).ok_or(NotLocked)?;
		// Make sure that the record contains what we expect and there's enough to unlock.
		ensure!(locker == record.locker && owner == record.owner, WouldClobber);
		ensure!(record.amount >= amount, NotEnoughLocked);
		ensure!(
			record.amount_held().map_or(true, |h| record.amount.saturating_sub(amount) >= h),
			InUse
		);
		Ok(ReduceTicket { key, amount, locker, owner })
	}
