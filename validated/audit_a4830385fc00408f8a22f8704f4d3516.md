Confirmed: `oldBalances`/`newBalances` in `Hinkal.sol::transact` are the **Hinkal contract's own** ERC20/ETH balances, checked before/after `_externalTransact`, per token index, against `amountChanges[i] + utxoAmount`. [1](#0-0) [2](#0-1) 

### Title
Unbounded input consumption in LI.FI swap via unlimited router approval lets a caller sweep pre-existing/residual token balances of `ExternalActionSwap` into their own output UTXO - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`, `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`ExternalActionSwap.swap` never verifies that the LI.FI router actually consumed exactly `inputAmount` of `inputToken`; it only measures the *output* token's balance delta across the router call. Combined with `LifiExternalAction.callRouter`'s `approveUnlimited(inputToken, router)`, the attacker fully controls the router calldata (`externalActionMetadata`) and can direct the router to pull more `inputToken` than they declared (`deltaAmounts[0]`), including any pre-existing/stranded balance of that token sitting in the shared `ExternalActionSwap` contract, and have the resulting extra output attributed entirely to their own claimed output UTXO.

### Finding Description
The invariant that should hold is: *tokens leaving the action contract in a given tx == `-deltaAmountChanges` Hinkal sent to it that tx (plus whatever it received back from the router for that same declared input)*. In `swap()`:

```
address inputToken = circomData.erc20TokenAddresses[0];
uint256 inputAmount = uint256(-deltaAmounts[0]);
...
uint256 swappedAmount = callRouter(inputToken, inputAmount, outputToken, circomData.externalActionData.externalActionMetadata);
``` [3](#0-2) 

`inputAmount` is passed to `callRouter` but is **never actually enforced on-chain** — `callRouter` doesn't use it to bound the router call; it is passed only for informational/interface purposes:

```
function callRouter(...) internal override returns (uint256 swappedAmount) {
    uint256 balanceBefore = getERC20OrETHBalance(outputToken);
    ...
    approveUnlimited(inputToken, router);
    (bool success, ) = router.call(externalActionMetadata);
    ...
    swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
}
``` [4](#0-3) 

Because `router.call(externalActionMetadata)` forwards **attacker-crafted calldata**, and `approveUnlimited` grants the router an unlimited allowance over the contract's entire `inputToken` balance (not just `inputAmount`), the attacker can encode a router call that pulls the whole `inputToken` balance held by `ExternalActionSwap` — including any residual balance left over from prior transactions (partial fills/dust from LI.FI, or funds stranded from a transaction using >2 tokens in `circomData.erc20TokenAddresses`, since `swap()` only ever touches index 0 and 1 and ignores any other index whose negative delta Hinkal already pushed into this contract per `_externalTransact`'s loop) [5](#0-4) . The entire swap output of that inflated input amount is measured as `swappedAmount`, flows through unchanged into `amountToSendToHinkal`, and is transferred to `msg.sender` (Hinkal) and recorded as the attacker's own output UTXO:

```
utxoSet[0] = UTXO({ amount: amountToSendToHinkal, ... });
``` [6](#0-5) 

`performHinkalChecks`/`dimensionsCheck` only validate array-length consistency and calldata-hash integrity [7](#0-6) ; they never validate `circomData.erc20TokenAddresses.length == 2` for a swap action, so a caller can supply a 3rd (or more) token with a negative `amountChanges[i]`, having Hinkal push that value into `ExternalActionSwap` where `swap()` silently drops it (never builds a UTXO for it, never uses it). Hinkal's own balance-diff check at the caller's own tx (`balanceDif == amountChanges[i] + utxoAmount`, `utxoAmount` computed by summing `utxoSet` entries matching that token) still holds for the depositor's own tx because Hinkal's own balance dropped by exactly that pushed amount and no UTXO is claimed for it — so the check passes even though the money is now stuck/available inside `ExternalActionSwap`, unaccounted at the action-contract level. [2](#0-1) 

That residual balance (from stranding, dust, or partial-fill refunds from the LI.FI router) then sits in the shared `ExternalActionSwap`/`LifiExternalAction` contract instance used by *all* Hinkal users. A subsequent unprivileged attacker observes this balance via a view call, then submits their own `Hinkal.transact` swap with a tiny declared `deltaAmounts[0]` but crafts `externalActionMetadata` so the router consumes the full available `inputToken` balance (stranded value + attacker's own small deposit). The excess conversion is captured entirely in `swappedAmount`, and the attacker generates a valid ZK proof for a UTXO whose amount they can compute in advance from the observed on-chain balance, matching `amountChanges[1]` to `amountToSendToHinkal`. None of `verifyProof`, `rootHashExists`, `insertNullifiers`, or the balance/slippage checks constrain what the router actually consumed versus what was declared — the circuit only constrains `inTotal + amountChanges[i] === outTotal` for the caller's own nullifiers/commitments, it has no visibility into the router call or the action contract's internal balance bookkeeping.

### Impact Explanation
An unprivileged attacker can convert stranded/residual token balances sitting in the shared `ExternalActionSwap` contract (arising from a prior transaction's dropped >2-token deltas, or from LI.FI partial-fill/positive-slippage dust) into their own shielded output UTXO, at the expense of whichever user's funds were stranded there — this is direct theft of in-flight/shielded user funds and matches the Critical impact category. The theft is repeatable any time a residual balance accumulates in the shared action contract, and the attacker's cost is only their own small declared `deltaAmounts[0]` burn plus gas.

### Likelihood Explanation
Preconditions: (1) some residual `inputToken` balance must exist in `ExternalActionSwap`/`LifiExternalAction` (achievable by the attacker themselves in a first transaction using a 3rd token with a negative delta that `swap()` ignores, or by waiting for LI.FI dust/refunds), and (2) the attacker must be able to craft `externalActionMetadata` that the router accepts to pull more than the officially declared `inputAmount` — LI.FI router calldata format generally allows specifying arbitrary `fromAmount` up to allowance, which is straightforward for an attacker who fully controls this field. Both preconditions are attacker-achievable with no privileged role required, and the attack is self-contained within two ordinary `Hinkal.transact` calls.

### Recommendation
In `ExternalActionSwap.swap`, explicitly require `circomData.erc20TokenAddresses.length == 2` for swap actions, and in `LifiExternalAction.callRouter`, measure and enforce that the router consumed exactly `inputAmount` of `inputToken` (`balanceBefore - balanceAfter == inputAmount`), reverting otherwise. Replace `approveUnlimited` with an approval scoped exactly to `inputAmount` per call (reset to zero afterward), so the router can never pull more than the declared amount regardless of attacker-controlled calldata.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `LifiExternalAction` with a mock LI.FI router that performs a simple deterministic token swap based on calldata-specified `fromAmount`.
2. Tx A (stranding): attacker calls `Hinkal.transact` with `circomData.erc20TokenAddresses = [tokenA, tokenB, tokenC]`, `deltaAmounts = [-X, +swapOut, -Y]` (`Y>0` for tokenC), routed through the swap external action. Assert after Tx A that `tokenC.balanceOf(LifiExternalAction) == Y` (stranded, no UTXO created for it) while Hinkal's own balance-diff check still passed.
3. Tx B (theft): a second attacker (or same) calls `Hinkal.transact` with `erc20TokenAddresses = [tokenC, tokenD]`, declares `deltaAmounts[0] = -1` (only burning 1 unit of tokenC from their own shielded balance), but crafts `externalActionMetadata` for the mock router to pull `Y+1` of tokenC (using the unlimited approval) and swap it all to tokenD.
4. Assert: `swappedAmount` returned by `callRouter` corresponds to swapping `Y+1`, not `1`; the attacker's new UTXO amount (`amountToSendToHinkal`) reflects the stolen `Y` worth of tokenC's swap value; and `tokenC.balanceOf(LifiExternalAction)` drops to 0, i.e., the equality "tokens leaving the action == `-deltaAmountChanges` Hinkal sent it that tx" is broken (`Y+1` left vs `1` sent).

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
