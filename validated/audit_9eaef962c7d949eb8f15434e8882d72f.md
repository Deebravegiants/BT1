### Title
Accumulated rounding drift from `Pair.swap`'s `+1` K-slack and `Router._computeSell`'s floor division can push a curve's stored `assetReserve` below the recovered `virtualLtReserve`, causing an unguarded underflow that permanently freezes the token's trading and graduation - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate` and `Bonding._prepareGraduationLiquidity` both compute the curve's real LT raised as a bare subtraction, `assetReserve - _launchTimeVirtualLtReserve(...)`, with no floor-at-zero guard, under the documented assumption that stored `assetReserve` can never fall below the launch-time virtual LT seed. [1](#0-0) [2](#0-1)  That assumption is not actually enforced on-chain: `Pair.swap`'s K-invariant check tolerates a `+1`/`+1` slack on both reserves, and `Router._computeSell` floors `k / newTokenReserve` when deriving `assetOut`, both of which let a sell extract marginally more LT than the exact continuous curve would allow. [3](#0-2) [4](#0-3)  Over enough small sells this rounding dust can accumulate until stored `assetReserve` dips at or below the recovered `virtualLtReserve` (`Pair.k() / TOTAL_SUPPLY()`), at which point the subtraction underflows and every subsequent call to `canGraduate` — which fires unconditionally at the end of every `Bonding.buy` — reverts, permanently bricking the token. This is analogous to CVE-2019-19624's root cause: an implicit ordering invariant (`coarsest_scale >= finest_scale`, here `assetReserve >= virtualLtReserve`) that silently breaks for small/edge-case magnitudes and is trusted without a bounds check, corrupting downstream arithmetic.

### Finding Description
`_launchTimeVirtualLtReserve` derives the launch-time virtual LT seed purely from the immutable `k` constant: `Pair.k() / Token.TOTAL_SUPPLY()`. [5](#0-4)  Both `canGraduate`'s USD leg and `_prepareGraduationLiquidity`'s `ltFromPair` computation subtract this value directly from the pair's live stored `assetReserve`, with no `>=` check or saturating-subtract guard:

```
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
``` [6](#0-5) 

```
ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
``` [2](#0-1) 

This code relies on the invariant "`assetReserve` can never fall below the launch-time virtual LT seed" holding exactly, unlike the parallel token-side invariant (`tokenBalance() < tokenReserve()`), which the test suite explicitly fuzzes and documents as load-bearing (`test_inv_virtualReserveAlwaysExceedsRealBalance`). [7](#0-6)  No equivalent invariant test exists for the asset side.

The invariant is not actually strict, because two rounding sources both bias sells in the trader's favor:

1. `Router._computeSell` computes `assetOut = reserveAsset - (k / newTokenReserve)`. Integer division floors `k / newTokenReserve`, which makes the subtracted term smaller than the true continuous value, so `assetOut` is rounded *up* relative to the exact curve — the pool pays out marginally more LT than the constant-product curve strictly allows. [4](#0-3) 
2. `Pair.swap`'s K check is `(newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k` reverts, i.e. it accepts any post-swap state where `newTokenReserve*newAssetReserve >= k - newTokenReserve - newAssetReserve - 1`. This bakes in an additional epsilon of tolerance beyond the exact invariant, on top of (1). [3](#0-2) 

Both slack sources are applied on every single sell. An unprivileged trader can submit a long sequence of minimal-size sells (`Zap.sell` → `Bonding.sell` → `Router.sell` → `Pair.swap`) that each round in their favor by the smallest possible unit, and repeat this until the cumulative drift pulls stored `assetReserve` down to (or below) `virtualLtReserve`. Once that boundary is crossed, `assetReserve - _launchTimeVirtualLtReserve(...)` underflows and reverts with a `Panic(0x11)`.

Because `canGraduate()` is called unconditionally at the end of every `Bonding.buy` (per the documented flow, "`Bonding.canGraduate()` is checked at the end of every buy inside `_executeBuy`"), this underflow does not only block graduation — it reverts **every** subsequent buy on that token, since the buy path cannot complete without evaluating `canGraduate`. [8](#0-7)  If `Zap.sell`'s graduatable pre-check similarly calls `canGraduate` before allowing a sell to proceed (per the documented sell flow's "if the curve token is already graduatable...the sell triggers graduation instead"), sells on the same token become unreachable too, since the check itself reverts rather than returning `false`.

### Impact Explanation
Once triggered, the token is bricked in `Lifecycle.Curve` with no recovery path:
- All buys revert (the `canGraduate()` call inside `_executeBuy` panics before any trade can complete).
- Sells that need the graduatable pre-check panic identically.
- The token can never reach `_enterGraduating`/`finalizeGraduation`, so the 250M `LP_RESERVE` tokens held in `Bonding` and all real LT raised in the `Pair` are permanently locked with no rescue function.
- Traders holding the launched token lose all ability to exit via the curve (and the token never reaches the HyperSwap pool either, so there is no post-graduation exit path).

This is a permanent freezing of trader, creator, and protocol funds tied to that token — no privileged action, upgrade, or off-chain intervention can undo an on-chain underflow condition once the stored reserves have drifted past the boundary.

### Likelihood Explanation
The rounding drift per sell is extremely small (fractions of a wei-equivalent per trade, bounded by `Pair.swap`'s `+1`/`+1` slack and the floor-division residual in `_computeSell`), so this is not a single-transaction exploit — it requires repeated small sells to accumulate. However, any unprivileged wallet can submit an arbitrary number of minimal `Zap.sell` calls at negligible gas cost per iteration, and the drift is strictly one-directional (always in the seller's favor), so it is monotonic and guaranteed to eventually cross the boundary given enough iterations, particularly on curves with small virtual LT reserves (low-cap tokens paired against low-value LTs), which is analogous to the "small images" edge case in the original CVE where the assumed ordering invariant broke down specifically at small scale.

### Recommendation
- Guard both subtractions with a saturating pattern (mirroring the existing `_sweepLTToOwner` style: `bal > keep ? bal - keep : 0`) so `realLtRaised`/`ltFromPair` clamp to zero instead of underflowing when `assetReserve <= virtualLtReserve`.
- Tighten `Pair.swap`'s K-invariant check to remove or bound the `+1`/`+1` slack, and/or round `Router._computeSell`'s output down (ceil the subtracted term) so LT payouts never exceed what the exact constant-product curve allows.
- Add a fuzz/invariant test analogous to `test_inv_virtualReserveAlwaysExceedsRealBalance` that asserts `assetReserve >= virtualLtReserve` holds after arbitrarily long sequences of minimal buys/sells.

### Proof of Concept
1. Launch a token via `Zap.createToken` with a modest seed, establishing `Pair.k()` and thus `virtualLtReserve = k / TOTAL_SUPPLY`.
2. From an unprivileged wallet, repeatedly call `Zap.sell(token, dustAmount, 0)` with the smallest tradeable token amount, each time letting `Router._computeSell`'s floored division and `Pair.swap`'s `+1` slack shave a small excess of LT out of the pair beyond the exact curve.
3. Continue the loop; each iteration strictly decreases stored `assetReserve` relative to the invariant `assetReserve >= virtualLtReserve` by the rounding residual.
4. Once cumulative drift causes `assetReserve <= virtualLtReserve`, call `Bonding.canGraduate(token)` (directly, or via any `Zap.buy`/`Zap.sell` that reaches it) — the subtraction at `Bonding.sol:692`/`Bonding.sol:1084` underflows and reverts, and this now happens on every future call, permanently freezing the token's trading and graduation.

Note: the exact number of iterations needed to cross the boundary depends on the curve's reserve magnitudes and could not be empirically measured without running the Foundry test suite; this would need to be confirmed with a fuzz/PoC test in `packages/contracts/test` to quantify the iteration count for realistic seed sizes.

        BondingStorage storage $ = _s();

    }

    function swap(
        uint256 tokenIn,
        uint256 tokenOut,
        uint256 assetIn,
        uint256 assetOut
    ) external onlyRouter returns (bool) {
        uint256 newTokenReserve = (_pool.tokenReserve + tokenIn) - tokenOut;
        uint256 newAssetReserve = (_pool.assetReserve + assetIn) - assetOut;
        if ((newTokenReserve + 1) * (newAssetReserve + 1) < _pool.k) revert KInvariantViolated();

        _pool.tokenReserve = newTokenReserve;
        _pool.assetReserve = newAssetReserve;
        emit Swap(tokenIn, tokenOut, assetIn, assetOut);
        return true;
    }

        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 assetOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        uint256 newReserveToken = reserveToken + amountIn;
