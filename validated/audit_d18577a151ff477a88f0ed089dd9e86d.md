This confirms the vulnerability pattern: the webhook `hmac` signature only covers `to_signable_string`, which returns `@raw_body` alone, while `shop` (the `shopify-shop-domain`/`x-shopify-shop-domain` header) is never included in the signed bytes.This confirms the exact identity-binding break: the app's documented webhook flow explicitly passes `data.shop` to the handler as the authoritative tenant identifier [1](#0-0) , and the handler is told it can trust `data.shop` for routing/dispatch decisions (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [2](#0-1) , yet the HMAC that `Registry.process` validates only signs `@raw_body` and never the `shop-domain` header.

### Title
Webhook HMAC does not cover the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop` is read directly from an unauthenticated HTTP header. `Registry.process` validates the HMAC against the body alone and then forwards the header-derived `shop` value to the app's webhook handler as the trusted tenant identifier.

### Finding Description
`Request#hmac` decodes the `x-shopify-hmac-sha256` header and `Request#to_signable_string` returns `@raw_body` verbatim [3](#0-2) . `Utils::HmacValidator.validate` recomputes the HMAC-SHA256 exclusively over `verifiable_query.to_signable_string` (i.e. the body) using `Context.api_secret_key`, and compares it to the received signature with `OpenSSL.secure_compare` [4](#0-3) . `Registry.process` gates on that same HMAC check and then builds `WebhookMetadata` using `request.shop`, which is pulled straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no relation to the signed bytes [5](#0-4) [6](#0-5) .

The identity binding broken is: `HMAC(raw_body, api_secret_key) == received_signature` is treated by callers as if it also proved `shop == request.shop`, but the two are independent — `shop` is never an input to the HMAC. Because a single app-level `api_secret_key` is shared across every merchant/shop that installs the app, any bytes that produce a valid signature for shop A's webhook (e.g. captured from a legitimate delivery, or from the attacker's own store when the attacker is a merchant installing the app) remain validly signed when replayed with the `shop-domain` header rewritten to shop B. `Registry.process` will accept the request and dispatch `data.shop = "shop-B"` with `data.body` unchanged to the handler [7](#0-6) .

The gem's own documentation instructs host apps to treat `data.shop` as the authoritative shop for the webhook and to key downstream work off it, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [2](#0-1) , so this is not merely "the host app should have validated it further" — the gem's own API surface (`WebhookMetadata#shop`, produced by `Registry.process`) is what carries the unauthenticated value forward as if it were authenticated.

### Impact Explanation
This breaks tenant isolation for any app that stores or acts on webhook data keyed by `data.shop` (e.g. persisting order/customer data, revoking access, updating per-shop settings) — exactly the cross-tenant access category. An attacker who is a legitimate merchant of the app (or who otherwise obtains one validly-signed body/signature pair, since bodies for many topics are deterministic or attacker-triggerable, e.g. `orders/create` on the attacker's own shop) can replay that exact `(body, hmac)` pair against the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header naming a victim shop. The app processes it as legitimate data for the victim tenant.

### Likelihood Explanation
Likelihood is bounded by needing at least one valid `(body, hmac)` pair, which is trivial to obtain: any shop that installs the app can trigger real webhooks for itself (e.g. by creating an order) and capture the resulting signed body/HMAC, since `api_secret_key` is shared across all installs of the app. From there, forging the `shop-domain` header requires no cryptographic material — it is a plain, unauthenticated request header.

### Recommendation
Include the shop domain (and ideally topic and webhook id) in the bytes covered by the HMAC verification, or otherwise cryptographically bind `shop` to the signature before trusting it — e.g. verify the header value against a shop derived independently and securely (such as an already-established session/access-token record) rather than trusting the unauthenticated header as the tenant key for dispatch.

### Proof of Concept
1. App merchant "attacker-shop.myshopify.com" installs the target app and triggers a real webhook (e.g. `orders/create`). Capture the raw body `B` and the resulting `x-shopify-hmac-sha256` header `H` — both are valid because Shopify signs `HMAC(api_secret_key, B) == H`.
2. Send a new HTTP request to the app's webhook endpoint with:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: H` (unchanged)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - body: `B` (unchanged)
3. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)`, which still equals `H`, so validation succeeds [8](#0-7) .
4. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body `B`, even though `victim-shop` never sent this webhook [7](#0-6) .
