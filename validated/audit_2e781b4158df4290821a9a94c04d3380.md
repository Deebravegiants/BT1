Audit Report

## Title
`StackLimitReached` is permanently dropped by `service_page_item` while treated as transient by `do_execute_overweight_inner` - (File: substrate/frame/message-queue/src/lib.rs)

## Summary
`process_message_payload` maps an XCM executor `ProcessMessageError::StackLimitReached` into `MessageExecutionStatus::StackLimitReached` and only emits a `ProcessingFailed` event [1](#0-0) . In the normal servicing path, `service_page_item` classifies this status alongside `Processed` and `Unprocessable { permanent: true }` as `is_processed = true`, permanently removing the message from the page [2](#0-1) , whereas `do_execute_overweight_inner` treats the identical status as `TemporarilyUnprocessable`, refusing to finalize it [3](#0-2) .

## Finding Description
The normal servicing path `service_queue` → `service_page` → `service_page_item` → `process_message_payload` → `T::MessageProcessor::process_message` runs automatically (e.g., during `on_initialize`) for all UMP/DMP/XCMP messages. When the XCM executor exceeds its recursion limit, `process_message_payload`'s match arm `Err(error @ StackLimitReached)` fires, deposits only a `ProcessingFailed` event, and returns `MessageExecutionStatus::StackLimitReached` [1](#0-0) . Back in `service_page_item`, this status is folded into the `is_processed = true` branch together with `Processed` and `Unprocessable { permanent: true }`, and `page.skip_first(is_processed)` marks the message done, decrementing `message_count`/`size` permanently [2](#0-1) . No `OverweightEnqueued` event is fired for this branch — that event is only deposited for the `Overweight` branch [4](#0-3) , so the message is never registered for retry via `execute_overweight`.

In contrast, `do_execute_overweight_inner` maps the same `StackLimitReached` variant to `Err(Error::<T>::TemporarilyUnprocessable)`, explicitly refusing to finalize/remove the message [3](#0-2) . This confirms the exact inconsistency claimed: the identical `MessageExecutionStatus::StackLimitReached` variant is treated as permanent in one code path and transient in the other. All cited line numbers and code content match the current repository state.

## Impact Explanation
Since `service_page_item` runs first during normal, automatic queue servicing (before any operator or user could invoke `execute_overweight` on the not-yet-processed message), any XCM message that triggers `StackLimitReached` is permanently dropped from the queue the very first time it is serviced. This is a genuine logic bug in the message-queue pallet: the message (and any transfers/instructions nested within it) is lost with no retry mechanism and no `OverweightEnqueued` audit trail, only a `ProcessingFailed` event. This matches a "message permanently stuck/lost" impact class rather than direct fund theft or duplication.

## Likelihood Explanation
Constructing a deeply nested XCM program (e.g., recursive `SetAppendix`/`ExecuteWithOrigin`) that exceeds the executor's fixed recursion limit is achievable by any unprivileged actor able to route a message through UMP/DMP/XCMP to `MessageQueue`. No governance or special origin is needed, and the behavior is deterministic and repeatable: every normal servicing pass will silently drop such a message via `service_page_item`'s current classification, since normal servicing runs before any manual overweight-execution attempt could occur.

## Recommendation
Make `service_page_item`'s classification of `MessageExecutionStatus::StackLimitReached` consistent with `do_execute_overweight_inner` — treat it as non-permanent/retryable (e.g., return `ItemExecutionStatus::Bailed`/`NoProgress`, or explicitly enqueue it into the overweight book with an `OverweightEnqueued`-style event) instead of folding it into `is_processed = true`. Ensure both call sites use the same permanence/retry classification for every `MessageExecutionStatus` variant.

## Proof of Concept
1. In `substrate/frame/message-queue/src/tests.rs`, using the existing recording message processor mock, configure it to return `Err(ProcessMessageError::StackLimitReached)` for a specific payload.
2. Enqueue one message with that payload and call `MessageQueue::service_queues(Weight::MAX)`.
3. Assert the message is removed from the page/book (`book_state.message_count == 0`), no `OverweightEnqueued` event was emitted, and only `Event::ProcessingFailed` appears — demonstrating permanent silent drop.
4. In a separate scenario, before servicing, call `execute_overweight` on the same not-yet-serviced message and assert it returns `Err(Error::<T>::TemporarilyUnprocessable)` — demonstrating the same status is treated as transient there.
5. The divergence between step 3 (permanent loss via normal servicing) and step 4 (transient/retryable via `do_execute_overweight_inner`) proves the inconsistency; a fix should make both paths agree.
