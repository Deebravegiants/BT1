### Title
Webhook shop-domain header is unauthenticated and not bound by the HMAC, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#hmac` is verified against `to_signable_string`, which returns only `@raw_body` [1](#0-0)  The `shop` accessor used to identify the tenant for the handler is read directly from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header [2](#0-1)  `Registry.process` validates the HMAC and then calls the handler with `shop: request.shop` taken straight from that header, with no cross-check that the HMAC-covered body actually belongs to that shop [3](#0-2) 

### Finding Description
The identity binding that should hold is: `shop value trusted by the handler == shop that the HMAC-signed bytes were generated for`. In this gem that equality is never enforced, because the HMAC signature only covers `@raw_body` [1](#0-0) , while `topic`, `shop`, `api_version`, and `webhook_id` are all read from plain, unsigned headers [4](#0-3) .

`HmacValidator.validate` only ever calls `verifiable_query.to_signable_string`, so for a `Webhooks::Request` it validates body-authenticity but nothing about which shop the body came from [5](#0-4) . `Registry.process` accepts any request whose body HMAC validates and unconditionally forwards `request.shop` (the raw header) to the app's handler as the shop identity for that payload [3](#0-2) .

Because Shopify signs webhooks for *all* shops that install a given app using the same app-level `api_secret_key` (the app's client secret, not a per-shop secret), any unprivileged internet user who installs the app on their own store can capture a genuinely-signed webhook body for their own shop, and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header. The HMAC computed over the (unchanged) body will still validate, since the header is not part of the signable string, yet `WebhookMetadata.shop` will now report the attacker-chosen shop domain [6](#0-5) .

The gem's own documentation confirms `process` is expected to be the sole authenticity check ("This will verify the request did indeed come from Shopify") before dispatching to the handler with `data.shop` as the trusted identity [7](#0-6) , so this is not merely a host-application misuse of an undocumented API — the gem itself hands the handler an unauthenticated tenant identifier under the guise of a "verified" webhook.

### Impact Explanation
Any application built on top of this gem that uses `data.shop` from a processed webhook to select which tenant's records to create/update/delete (the documented and expected usage pattern shown in `docs/usage/webhooks.md`) can be made to attribute or apply a webhook payload to a different, victim shop than the one that actually triggered it. This is a cross-tenant data-integrity/confusion vulnerability reachable by any internet user who can install the app on a shop they control (a normal, unprivileged action) and replay signed traffic with a forged shop header — satisfying the "cross-tenant access" criterion for Critical impact.

### Likelihood Explanation
High. No credentials, access tokens, or `client_secret` are needed. The attacker only needs to install the target app on a shop they control (an unprivileged, public action), capture one legitimate webhook (HMAC + body), and replay it to the app's public webhook endpoint with the `shop-domain` header altered. `Registry.process` performs no additional check binding shop to body.

### Recommendation
When constructing `WebhookMetadata`, do not trust the `shop-domain` header as-is for cross-tenant decisions unless the application independently verifies it (e.g., cross-checking against the shop associated with the webhook by an authenticated GraphQL lookup, or including shop in the HMAC-signed material). At minimum, the gem should document prominently that `data.shop` from `Registry.process` is not itself authenticated by the HMAC and must be corroborated against a known/installed-shop list before being used for any write, tenant-scoping, or authorization decision.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`), capturing the raw body `B` and the corresponding `X-Shopify-Hmac-Sha256` header `H` (`HMAC_SHA256(api_secret_key, B) == H`).
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), and header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` decodes `H`; `Utils::HmacValidator.validate` recomputes HMAC over `to_signable_string` (`= B`) and it matches, so validation succeeds [1](#0-0) .
4. `Registry.process` calls the app handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: <attacker's own order data> ...)` [8](#0-7) , causing the app to process attacker-controlled data as if it belonged to the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
