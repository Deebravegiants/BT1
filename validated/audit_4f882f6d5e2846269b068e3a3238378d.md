### Title
Untrusted swap-route pool code can steal unrelated caller wallet tokens - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The controller accepts an opaque `swap` payload in `swap_collateral` and forwards it to the configured router after authorizing only the intended input-token transfer. [1](#0-0) [2](#0-1)  The route can name an arbitrary pool address, which is invoked without a venue-address allowlist; malicious pool code can request a transfer from the caller’s wallet, causing transaction simulation to place that transfer under the caller’s authorization tree. [3](#0-2) [4](#0-3)  If the caller signs the simulation-generated tree without noticing the added child invocation, the malicious pool can drain unrelated wallet tokens while still returning a valid swap output. [5](#0-4) 

### Finding Description
`swap_collateral` passes caller-supplied `swap` bytes through `swap_tokens_or_passthrough`, which invokes `SwapAggregatorClient::execute_strategy` on the configured router. [6](#0-5) [7](#0-6)  Although the controller authorizes only `token_in.transfer(controller, router, amount_in)`, it does not constrain which contracts the router subsequently invokes. [8](#0-7) 

The router decodes a swap instruction’s `pool`, `token_in`, and `token_out` directly from the payload’s `assets` registry. [9](#0-8)  The program validates opcode and registry indices, but not whether `pool` is a known or trusted deployment. [10](#0-9)  For example, the Phoenix adapter invokes `swap` on the payload-selected pool. [11](#0-10) 

A malicious pool can therefore run arbitrary contract code during the strategy and issue a token transfer whose `from` address is the lending caller rather than the router. [12](#0-11)  The project’s test demonstrates that simulation records such a transfer as a child of the caller’s `swap_collateral` authorization and that signing that generated tree allows the theft. [5](#0-4) 

### Impact Explanation
The attacker can steal any unrelated token held by the caller, bounded by the token amount requested by the malicious contract and the caller’s signed authorization tree. [13](#0-12)  This exceeds the routed collateral because neither the controller’s exact input authorization nor the router’s measured-output checks constrain a nested transfer naming the caller as `from`. [14](#0-13) [15](#0-14) 

### Likelihood Explanation
Exploitation requires the victim to submit an attacker-supplied route and sign an authorization tree containing the extra transfer. [16](#0-15)  That precondition reduces likelihood, but opaque packed route bytes and simulation-generated auth trees make the added invocation easy to miss unless the client explicitly rejects unexpected children. [17](#0-16) [18](#0-17) 

### Recommendation
Do not permit arbitrary pool addresses in production routes. [19](#0-18)  The router or controller boundary should validate each hop against a governed venue/pool registry, and clients should refuse to sign any `swap_collateral`, `multiply`, `swap_debt`, or `repay_debt_with_collateral` authorization containing children beyond the expected exact input-transfer path. [7](#0-6) [18](#0-17) 

### Proof of Concept
1. Alice supplies USDC and owns an unrelated `wallet_token` balance. [20](#0-19) 
2. The attacker deploys a pool-compatible contract whose `swap` function calls `wallet_token.transfer(Alice, attacker, balance)` and also produces enough `token_out` to satisfy the router’s measured-output checks. [21](#0-20) [22](#0-21) 
3. The attacker gives Alice a valid packed `StrategyPayload` whose `assets` entry selects that contract as the hop pool. [23](#0-22) [24](#0-23) 
4. Alice calls `swap_collateral(Alice, account_id, USDC, amount, ETH, route)`. [25](#0-24) 
5. Simulation records the malicious wallet transfer under Alice’s `swap_collateral` authorization. [26](#0-25) 
6. If Alice signs that generated tree, the transaction swaps successfully and transfers the unrelated wallet-token balance to the attacker. [27](#0-26)

```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.

//! A strategy is a linear program over an address registry and an amount
//! registry. Every instruction is a fixed 5-byte record holding one opcode, one
//! amount selector, and three `u8` registry indices, so a hop costs 5 bytes on
//! the wire instead of a full XDR struct.
//!
//! ```text
//! header (10 bytes)
//!   [0]      version, must be VERSION
//!   [1]      token_in   -> assets[..]
//!   [2]      token_out  -> assets[..]
//!   [3]      min_out    -> amounts[..]
//!   [4..8]   referral id, u32 big-endian (0 = none)
//!   [8]      op_count
//!   [9]      weight_count
//! instructions (5 * op_count bytes)
//!   [0]      opcode      -> Opcode
//!   [1]      mode        -> Mode
//!   [2]      idx_a       pool
//!   [3]      idx_b       token_in  | lp share token
//!   [4]      idx_c       token_out | amounts index
//! weights (3 * weight_count bytes)
//!   u24 big-endian parts-per-million, each in 1..=PPM_DENOMINATOR
```
