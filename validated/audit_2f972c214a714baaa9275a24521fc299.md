### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request **body**. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values are taken directly from unauthenticated HTTP headers and are never included in the signed content, so any request whose body+HMAC pair is valid will be accepted regardless of which shop the headers claim it came from.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read straight from HTTP headers, none of which are part of the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC only over `verifiable_query.to_signable_string` (i.e. the body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` performs this HMAC check and then immediately trusts `request.shop` (an unauthenticated header) to build the `WebhookMetadata` that is handed to the app's webhook handler: [4](#0-3) 

This breaks the identity binding: `shop == shop-domain header`, when only `shop == shop encoded inside the HMAC-signed payload` should be trusted. Because the header is not covered by the signature, the binding "the shop that produced this authenticated payload" and "the shop the gem reports to the handler" are not equal.

### Impact Explanation
An attacker who legitimately installs the target app on their own store (an ordinary, unprivileged action available to any merchant/developer) can obtain a genuine `body` + `hmac-sha256` pair signed with the app's real `api_secret_key` for their own shop's webhook delivery. Because the signature never covers the `shop-domain` header, the attacker can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` (and `topic`/`webhook_id`) header. `Registry.process` will still pass HMAC validation and will invoke the handler with `WebhookMetadata` claiming the payload came from the victim shop. If the host application uses `data.shop` to look up sessions, apply mutations, or otherwise make tenant-scoped decisions (which is exactly what the shop field is documented for), this results in cross-tenant data confusion/write attribution — a Critical-severity cross-tenant boundary violation, directly analogous to the "fake `LPToken.sol` instance" pattern of trusting an unverified identity field to perform privileged tenant-scoped actions.

### Likelihood Explanation
The prerequisite is only that the attacker be able to install the app (or otherwise obtain one valid HMAC-signed webhook body for any shop, including their own) and be able to POST arbitrary headers to the app's public webhook endpoint — both are unprivileged, internet-reachable actions requiring no access token, `client_secret`, or leaked credential. The only gem-level defense (`Utils::HmacValidator.validate`) never inspects the header fields, so the attack surface is fully exposed by design of `Webhooks::Request`/`Webhooks::Registry`.

### Recommendation
Include the `shop-domain`, `topic`, `webhook-id`, and `api-version` values in the HMAC-signed payload (or otherwise cryptographically bind them to the body), and have `Registry.process` reject requests where these header values are not verified as part of the signature. At minimum, document that `data.shop` from `WebhookMetadata` is unauthenticated and must not be used by host applications as a sole tenant-scoping key.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook, capturing the raw body `B` and the valid `x-shopify-hmac-sha256` header `H` that Shopify computed with the app's real `api_secret_key`.
2. Attacker sends a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com` and any desired `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers; `Utils::HmacValidator.validate` succeeds because it only re-computes the HMAC over `B` [5](#0-4) 
4. `Registry.process` calls the registered handler with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"`, even though the payload never originated from that shop [6](#0-5)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
