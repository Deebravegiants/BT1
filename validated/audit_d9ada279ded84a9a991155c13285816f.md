### Title
CASE 2 stateless `EmporiumOperation` executes arbitrary calls as `address(Emporium)`, letting any unrelated user drain NFTs/LP shares left owned by the Emporium after another user's action - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` only accounts for balance changes of the ERC20/ETH addresses listed in `circomData.erc20TokenAddresses`; any non‑ERC20 asset (ERC721/ERC1155/vault share/LP position) minted to `address(Emporium)` by a CASE 2 stateless op is left permanently owned by the shared `Emporium` contract with no on-chain link to the depositor. Because CASE 2 only blacklists the `callHinkalWallet`/`doSendToRelay` selectors and otherwise permits `op.endpoint.call{value: op.value}(op.callData)` to any address with any calldata, an unrelated attacker can submit their own valid `transact()` whose `EmporiumStack` calls `asset.transferFrom(address(Emporium), attacker, tokenId)`, which succeeds trivially since `msg.sender == address(Emporium)` is the asset's owner.

### Finding Description
The broken equality: `asset_owner(tokenId)` should always equal `victim_identity` (the depositor's stealth wallet) for any asset created by the victim's proof/action, but instead `asset_owner(tokenId)` becomes `address(Emporium)` after the victim's tx and can be moved to any `attacker` by a completely independent tx.

Code path:
- `runAction` decodes `EmporiumStack` from `circomData.externalActionData.externalActionMetadata`, entirely attacker/user controlled content bound only by their own proof: [1](#0-0) 
- CASE 2 (`invokeWallet == false` or `signerAddress == address(0)`) performs a raw low-level call from the Emporium contract itself, only rejecting the two wallet-management selectors: [2](#0-1) 
- Post-call accounting (`balancesBefore`/`balancesAfter`) is computed exclusively over `circomData.erc20TokenAddresses`, an array the caller themselves supplies, and there is no equivalent tracking for ERC721/ERC1155/vault shares: [3](#0-2) 
- `Transferer`/`TransfererBase` grant Emporium unconditional `onERC721Received`/`onERC1155Received` acceptance, so any NFT/LP-mint call in CASE 2 completes silently: [4](#0-3) 
- `onlyAllowedRecipient` only restricts `msg.sender` to the fixed allowed caller (Hinkal/HinkalHelper contract), not to any specific end-user, so *any* holder of a valid ZK proof for their own UTXOs can invoke `runAction` with an arbitrary `EmporiumStack`: [5](#0-4) 

Exploit flow: victim's `transact()` runs a CASE 2 op that mints/deposits into a vault or NFT contract, leaving `tokenId`/shares owned by `address(Emporium)`. Attacker, in an unrelated `transact()` with their own valid proof, crafts a CASE 2 op calling `asset.transferFrom(address(Emporium), attackerAddress, tokenId)`; since `Emporium` is the on-chain owner, the call succeeds with no additional authorization, and no code path checks whether `op.endpoint`/`op.callData` pertains to the caller's own previously created position.

### Impact Explanation
Direct, permanent theft of a shielded/in-flight user's asset (NFT, LP position, vault share) by any unrelated, unprivileged party who can submit their own `transact()`. This matches the Critical category: theft of a shielded/in-flight user's asset, executed via a call the victim's proof never authorized on that specific asset's ownership going forward.

### Likelihood Explanation
Feasible for any protocol integration where a CASE 2 op interacts with a contract returning a non-ERC20 receipt (NFT vault wrapper, LP position NFT, ERC1155 share token, etc.) — a realistic pattern for DeFi/vault integrations Emporium is designed to support. Attacker cost is only their own transaction plus proof generation for their own UTXOs (no special role required); the attack is repeatable against every future victim action that leaves such an asset temporarily/permanently held by Emporium, and the attacker only needs to observe pending/mined victim transactions to react.

### Recommendation
Restrict CASE 2 `op.endpoint.call` targets/effects so external calls cannot move assets that do not belong to the initiating action, e.g.: require `invokeWallet == true` (route through the per-user `HinkalWallet`) for any interaction that can result in non-fungible/receipt-token custody, track and reconcile ERC721/ERC1155/vault-share balances the same way ERC20 balances are reconciled and force them to leave Emporium within the same transaction, or maintain a global "Emporium never custodies a persistent balance across transactions" invariant enforced by asserting all touched balances (fungible and non-fungible) return to pre-call levels (minus what is paid out to `msg.sender`) before `runAction` returns.

### Proof of Concept
Foundry test:
1. Deploy a mock ERC721 "vault" with `mint(address to, uint256 tokenId)` and standard `transferFrom`.
2. Victim calls `Hinkal.transact()` with a valid proof and `EmporiumStack` containing one CASE 2 op: `vault.mint(address(Emporium), tokenId)`. Assert `vault.ownerOf(tokenId) == address(Emporium)`.
3. Attacker (unrelated EOA, own UTXOs/proof) calls `Hinkal.transact()` with `EmporiumStack` containing one CASE 2 op: `vault.transferFrom(address(Emporium), attacker, tokenId)`.
4. Assert the call succeeds and `vault.ownerOf(tokenId) == attacker`, proving `asset_owner(tokenId)` transitioned from `address(Emporium)` to `attacker` without ever equaling `victim_identity`, and without any check in `runAction`/`onlyAllowedRecipient`/`verifyWallet` preventing it.
