### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` verifies the HMAC and then forwards `request.shop` unchanged to the app's `WebhookHandler`, so the tenant identity used by application logic is never bound to the value that was cryptographically verified.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding to the HMAC at all [3](#0-2) .

`Registry.process` verifies the HMAC and then immediately builds a `WebhookMetadata` object using `request.shop`, handing it to the registered handler as the tenant identity for that webhook: [4](#0-3) . `WebhookMetadata` carries `shop` as the field applications use to select which merchant's data/session to act on [5](#0-4) .

This breaks the identity binding: `shop_covered_by_hmac (∅) != shop_used_for_tenant_routing (request.shop, from header)`. Contrast this with `Auth::Oauth::AuthQuery`, where `shop` **is** explicitly included inside `to_signable_string` and thus is bound to the HMAC [6](#0-5) . The webhook `Request` class has no equivalent binding for `shop`.

Since the client secret used to sign webhooks is the app's single, shared secret (not a per-shop secret), any merchant who has installed the app can legitimately trigger real, correctly-signed webhooks for their own shop by taking ordinary actions in their own store. Because the header carrying `shop-domain` is not part of the signed payload, that same merchant can capture one of their own genuinely-signed webhook deliveries and resend it to the app's webhook endpoint after swapping only the `shopify-shop-domain` header value to a victim shop's domain. `HmacValidator.validate` will still succeed (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an unprivileged app user (a legitimate but malicious merchant with the app installed) can make the host application process webhook events under an arbitrary victim shop's identity. Depending on how the host app's handlers use `data.shop` (e.g., `app/uninstalled` to purge tokens, `shop/redact` / `customers/redact` for GDPR deletion, order/inventory update handlers keyed by shop), this can be leveraged to delete or corrupt another merchant's data, or interfere with their app session/access-token lifecycle — a cross-tenant boundary violation, which the scope rules classify as Critical.

### Likelihood Explanation
Likelihood is realistic for any actor with a normal, non-privileged merchant account that has the app installed: they can generate real signed webhook traffic for their own shop at will (e.g. by creating an order) and replay it with a modified `shop-domain` header, since HTTP headers are fully attacker-controlled and are not covered by the signature. No access token, `client_secret`, or privileged access to any other tenant is required.

### Recommendation
Bind `shop` (and ideally `topic`/`api_version`) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived shop domain to the verified payload before it is handed to the handler. Concretely, change `Request#to_signable_string` to include the shop domain (and other trust-sensitive headers) rather than only `@raw_body`, mirroring the approach already used in `Auth::Oauth::AuthQuery#to_signable_string`. At minimum, document/require host apps to cross-check `request.shop` against the shop associated with the corresponding stored access token/session rather than trusting the header value on its own.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers a webhook for a topic the app relies on (e.g. `app/uninstalled`, `orders/create`).
2. Attacker performs an action that causes Shopify to send a legitimately HMAC-signed webhook to the app's endpoint, capturing the raw body `B` and the valid `X-Shopify-Hmac-Sha256` header `H` (computed by Shopify over `B` with the app's shared secret).
3. Attacker resends the identical `(B, H)` pair to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `H` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the host application to act on the victim's tenant context using attacker-supplied data.
