Audit Report

## Title
Unrelated `T::Currency::transfer` inside `pallet-nfts::do_claim_swap` pays/receives funds based on the *live* owner of the offered item, allowing an attacker to force any account (including an `pallet-asset-conversion` pool sovereign account) to unknowingly pay or receive a currency transfer - ([File: substrate/frame/nfts/src/features/atomic_swap.rs])

## Finding Description
`do_create_swap` records a `PendingSwap` keyed on the offered `(collection, item)` but never locks the item's transferability, nor stores the identity of the item's owner at creation time [1](#0-0) . `do_claim_swap` later fetches `receive_item.owner` live from `Item::<T,I>::get(...)` at claim time and unconditionally executes `T::Currency::transfer` between `receive_item.owner` and `send_item.owner` based on `price.direction`, with no check that `receive_item.owner` is still the account that created the swap [2](#0-1) . NFT ownership transfer via `do_transfer` never requires the destination account's consent — it unconditionally overwrites `Item.owner` and `Account` storage [3](#0-2) .

Combining these facts: after `A1` creates a swap offering an item with `price.direction == Send` (meaning the offered item's *current owner* pays the price on claim, as shown by the `claim_swap_should_work` test where the swap creator pays when direction is `Send`) [4](#0-3) , `A1` can freely transfer the offered NFT to *any* other account (no consent required), and that account becomes obligated to pay the price at claim time — because `do_claim_swap` re-resolves the owner live rather than validating it against the original swap creator.

The report specifically targets a `pallet-asset-conversion` pool's sovereign account as the victim. Such accounts are confirmed to be plain, keyless `AccountId`s deterministically derived via `AccountIdConverter`/`PoolLocator` from a `PalletId` and asset pair [5](#0-4) , and asset-hub runtimes do configure `pallet_nfts::Config::Currency = Balances` [6](#0-5)  while `pallet_asset_conversion`'s native asset is also `Balances`/`TokenLocation` in those same runtimes, with `PalletFeatures::all_enabled()` enabling the `Swaps` feature [7](#0-6) . This confirms the necessary preconditions (shared currency, Swaps feature enabled) exist in real, deployed runtime configurations.

Existing checks are insufficient: `do_claim_swap` validates `send_item.owner == caller`, `swap.desired_collection`/`witness_price` match, and the deadline, but never re-validates that `receive_item.owner` is the original swap creator [8](#0-7) .

## Impact Explanation
The transfer moves real, unbacked `T::Currency` funds out of (or forces unwanted funds into) whichever account happens to hold the offered NFT at claim time, without that account's consent or awareness of the swap. When the victim account is a `pallet-asset-conversion` pool sovereign account, this can drain the pool's native-currency reserves down to the existential deposit, desynchronizing actual balance from LP-token-implied entitlements. This is a concrete fund-drain vector with realistic in-scope impact — not merely a theoretical concern — because `do_claim_swap` unconditionally executes `T::Currency::transfer` based on live-storage ownership rather than an owner fixed/validated at swap-creation time.

## Likelihood Explanation
The exploit requires only unprivileged, signed accounts: an attacker mints/owns an NFT, calls `create_swap` with `price.direction = Send`, transfers the offered NFT to the target victim account (a normal, permissionless NFT transfer, since `do_transfer` requires no destination consent), then claims the swap from a second account they control. No governance, leaked keys, or privileged origin is required, and the pool sovereign account address is publicly computable off-chain. The only preconditions are that the runtime enables the `Swaps` pallet feature and uses a currency shared with a target victim (e.g., an asset-conversion pool) — both of which are true in the asset-hub-rococo/westend runtimes examined. This is repeatable against any account (not just pool accounts) that can be forced to "own" an NFT and has a `KeepAlive`-respecting free balance to drain.

## Recommendation
- In `do_claim_swap`, verify that `receive_item.owner` still matches the account that created the swap (e.g., store the creator's `AccountId` in `PendingSwap` at creation time and compare it against `receive_item.owner` at claim time), rejecting the claim (or the currency leg of it) if ownership of the offered item changed since the swap was created.
- Alternatively, lock/freeze the offered item's transferability while a `PendingSwap` exists for it, similar to how `ItemPriceOf`/other locking mechanisms work elsewhere in the pallet, preventing the underlying ownership-substitution attack entirely.
- More generally, avoid triggering `T::Currency::transfer` against an account resolved from mutable, consent-free ownership state without re-validating that the account is the one that actually agreed to the price term of the swap.

## Proof of Concept
1. In a test runtime with `pallet_nfts` (Swaps feature enabled) and `pallet_asset_conversion` sharing `Balances` as the native currency, set up a pool and add liquidity, recording the pool's sovereign account address via `PoolLocator::address`.
2. Attacker (`A1`) mints an NFT and calls `Nfts::create_swap` offering that NFT, with `price = Some({amount: X, direction: Send})`.
3. `A1` calls `Nfts::transfer` to send the offered NFT to the pool's sovereign account (no consent required, confirmed by `do_transfer` in `transfer.rs`).
4. A second attacker-controlled account (`A2`) mints/owns the desired item and calls `Nfts::claim_swap`, naming the offered item as `receive_item`.
5. Assert: `T::Currency::transfer` executes from the pool account to `A2` for amount `X`, confirmed by the code path in `do_claim_swap` (lines 193-208) and the existing `claim_swap_should_work` unit test pattern demonstrating that the item owner pays/receives currency based on `price.direction` [9](#0-8) .

	pub fn do_transfer(
		collection: T::CollectionId,
		item: T::ItemId,
		dest: T::AccountId,
		with_details: impl FnOnce(
			&CollectionDetailsFor<T, I>,
			&mut ItemDetailsFor<T, I>,
		) -> DispatchResult,
	) -> DispatchResult {
		// Retrieve collection details.
		let collection_details =
			Collection::<T, I>::get(&collection).ok_or(Error::<T, I>::UnknownCollection)?;

		// Ensure the item is not locked.
		ensure!(!T::Locker::is_locked(collection, item), Error::<T, I>::ItemLocked);

		// Ensure the item is not transfer disabled on the system level attribute.
		ensure!(
			!Self::has_system_attribute(&collection, &item, PalletAttributes::TransferDisabled)?,
			Error::<T, I>::ItemLocked
		);

		// Retrieve collection config and check if items are transferable.
		let collection_config = Self::get_collection_config(&collection)?;
		ensure!(
			collection_config.is_setting_enabled(CollectionSetting::TransferableItems),
			Error::<T, I>::ItemsNonTransferable
		);

		// Retrieve item config and check if the item is transferable.
		let item_config = Self::get_item_config(&collection, &item)?;
		ensure!(
			item_config.is_setting_enabled(ItemSetting::Transferable),
			Error::<T, I>::ItemLocked
		);

		// Retrieve the item details.
		let mut details =
			Item::<T, I>::get(&collection, &item).ok_or(Error::<T, I>::UnknownItem)?;

		// Perform the transfer with custom details using the provided closure.
		with_details(&collection_details, &mut details)?;

		// Update account ownership information.
		Account::<T, I>::remove((&details.owner, &collection, &item));
		Account::<T, I>::insert((&dest, &collection, &item), ());
		let origin = details.owner;
		details.owner = dest;

		// The approved accounts have to be reset to `None`, because otherwise pre-approve attack
		// would be possible, where the owner can approve their second account before making the
		// transaction and then claiming the item back.
		details.approvals.clear();

		// Update item details.
		Item::<T, I>::insert(&collection, &item, &details);
		ItemPriceOf::<T, I>::remove(&collection, &item);
		PendingSwapOf::<T, I>::remove(&collection, &item);

		// Emit `Transferred` event.
		Self::deposit_event(Event::Transferred {
			collection,
			item,
			from: origin,
			to: details.owner,
		});
		Ok(())
	}
