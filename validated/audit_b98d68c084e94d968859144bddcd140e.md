### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, while the `shop`, `topic`, and `webhook_id` values consumed by `ShopifyAPI::Webhooks::Registry.process` are read directly from unauthenticated HTTP headers. Any party who can obtain one validly-HMAC'd webhook body (e.g., a merchant receiving legitimate webhooks for their own installed shop) can replay that exact body/HMAC pair while substituting an arbitrary `shopify-shop-domain` header, causing the host application to process the payload as though it originated from a different (victim) shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`HmacValidator.validate` only checks that the *body* matches the signature computed with the app's secret — it has no knowledge of, and does not check, the `shop` header at all: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (none of which are HMAC-covered) to route and label the payload delivered to the app's registered handler: [4](#0-3) 

The equality that is supposed to hold is: *the shop that Shopify signed this webhook for == the shop the application acts on*. Because the HMAC signs only the body, this binding is broken — `hmac(body, secret)` is valid regardless of the `shop-domain` header value.

### Impact Explanation
This breaks the tenant-isolation guarantee the library's own HMAC check is meant to provide. A user who has installed the app on their own shop (an unprivileged install, no `api_secret_key` or access token needed) receives legitimate webhooks whose HMAC is computed only over the body. That user can capture one such body+HMAC pair and resend it with the `shopify-shop-domain` header changed to any other shop the attacker chooses. `Registry.process` will accept it as valid (since `HmacValidator.validate` never inspects `shop`) and dispatch it to the app's handler labeled with the attacker-chosen victim shop via `WebhookMetadata.new(shop: request.shop, ...)`. Any handler logic that trusts `data.shop` to select which merchant's data to update/delete/notify (a common and expected usage pattern, e.g. mandatory `shop/redact`, `customers/redact` compliance webhooks) can be tricked into acting on the wrong tenant — i.e., cross-tenant data corruption/exposure, satisfying the "Critical — cross-tenant access" bar.

### Likelihood Explanation
Moderate-to-high. The only prerequisite is the ability to receive one real webhook from Shopify for an app the attacker has installed on their own (unprivileged) shop, or bodies that are attacker-influenced/predictable in content (e.g., compliance webhooks whose bodies are largely fixed shape). No secrets, tokens, or elevated access are required — only the ability to intercept/replay their own webhook HTTP requests to the app's public webhook endpoint with a modified header.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed payload verification, e.g., by including these header values in `to_signable_string` (matching Shopify's actual signing scheme if it covers them) or, at minimum, have `Registry.process`/`HmacValidator` re-derive/cross-check the shop domain against an independently trusted source (such as an existing session record for that shop) before dispatching to handlers. Document clearly that consumers must not trust `WebhookMetadata#shop` without additional verification, or change the library to enforce it internally.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and receives a legitimate webhook (e.g., `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker resends the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only verifies `HMAC(secret, B) == H` — the `shop-domain` header is never part of the signed string: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`, causing the app to process attacker-supplied data as if it came from the victim shop.

          received_signature = verifiable_query.hmac
