## Finding

Aptos's object soft-burn/reclaim mechanism (`object.move`) is the closest custody analog to the reported bug pattern: a state comparison is made against a value that is not kept in sync with the object's *current* ownership history, letting a party bypass an intended one-way state transition (burn → permanent) the same way the Astaria borrower could bypass accrued interest by exploiting a check that ignored intervening state changes.

### Title
Stale `TombStone.original_owner` survives ordinary object transfers, allowing a former owner to reclaim an object away from `BURN_ADDRESS` after it has been legitimately re-owned and burned by someone else - (File: aptos-move/framework/aptos-framework/sources/object.move)

### Summary
`object::burn` creates a `TombStone { original_owner }` record under the object without changing its `ObjectCore.owner`. This record is only cleared by `transfer_with_ref` (used for `LinearTransferRef`-gated transfers), but **not** by the ordinary `transfer`, `transfer_raw`, or `transfer_to_object` entry points. As a result, once any account has ever called `burn` on an object, its address is permanently "reserved" in that object's tombstone even after the object legitimately changes hands one or more times. If any later owner sends the object to the well-known `BURN_ADDRESS`, the original (now unrelated) burner can call `unburn` and reclaim full ownership, overriding the current/legitimate custody chain.

### Finding Description
- `burn` sets a tombstone but does not change ownership: [1](#0-0) 
- `TombStone` struct only stores the `original_owner`, with no linkage/versioning tied to the ownership chain: [2](#0-1) 
- Ordinary transfers (`transfer`, `transfer_raw`, `transfer_to_object`) go through `transfer_raw_inner`, which updates `owner` but never touches/clears `TombStone`: [3](#0-2) 
- Only `transfer_with_ref` explicitly clears a stale tombstone, with a comment acknowledging exactly this risk ("Undo soft burn if present as we don't want the original owner to be able to reclaim by calling unburn later"), but this safeguard is absent from the ordinary transfer paths: [4](#0-3) 
- `unburn`'s "old functionality" branch reclaims the object from `BURN_ADDRESS` back to whatever `original_owner` is stored in the (possibly stale) `TombStone`, verifying only that the caller matches that stored value — not that the caller was the party who actually sent the object to `BURN_ADDRESS`: [5](#0-4) 

Exploit chain:
1. Attacker `A` owns object `O` and calls `burn(A, O)`. This only writes `TombStone{original_owner: A}`; `A` keeps ownership (soft burn).
2. `A` sells/transfers `O` to `B` via a normal `transfer`/`transfer_raw` call. `TombStone{original_owner: A}` is never cleared by this path.
3. `B`, unaware of the stale tombstone, later decides to permanently destroy/lock `O` by transferring it to the conventional `BURN_ADDRESS` (`0xff...ff`) using the ordinary `transfer` entry function.
4. `A` calls `unburn(A, O)`. Since `object_core.owner == BURN_ADDRESS`, the code takes the reclaim branch, matches `original_owner_addr == A`, and calls `transfer_raw_inner(object_addr, A)` — silently returning full ownership of `O` to `A`, even though `A` had no ownership or authorization at the time `B` burned it.

### Impact Explanation
This breaks the fundamental custody invariant that transferring an object to `BURN_ADDRESS` permanently removes it from circulation. A stale, unprivileged former owner can unilaterally reassign ownership of a token/code object away from the burn address back to themselves, corrupting the object's ownership field to the wrong (unauthorized) holder. For any token-object or asset-holding object (NFTs, in-object value, code objects with attached resources), this is a high-severity custody violation matching "Unauthorized ... owner reassignment of ... token objects, or other object-held value" and "Object creation, transfer, burn ... must preserve the intended controller."

### Likelihood Explanation
The exploit requires no privileged role — only that the attacker was ever a past owner of the object who called `burn` at some point in the object's history, and that a later owner subsequently transfers the object to `BURN_ADDRESS`. Since `burn`/`unburn`/`transfer` are all public entry functions with no cross-checks preventing this sequence, and objects routinely change hands (marketplaces, transfers, resales), this is a realistically triggerable sequence rather than a purely theoretical one.

### Recommendation
Clear any existing `TombStone` on an object whenever its ownership changes through **any** transfer path (`transfer_raw_inner`), not just `transfer_with_ref`. Alternatively, tie `TombStone.original_owner` validity to the specific owner that performed the `BURN_ADDRESS` transfer (e.g., record the owner-at-burn-time on the transfer to `BURN_ADDRESS` itself, rather than trusting a value that can predate multiple subsequent, unrelated ownership changes).

### Proof of Concept
Move pseudocode illustrating the sequence (based on existing test patterns such as `test_burn_and_unburn_old`):
```
// A owns O
object::burn(&A_signer, O);                  // TombStone{original_owner: A}, A still owner

// A sells/transfers O to B normally — TombStone NOT cleared
object::transfer(&A_signer, O, B_addr);

// B, the legitimate new owner, burns O by sending to BURN_ADDRESS
object::transfer(&B_signer, O, BURN_ADDRESS);

// A reclaims O from BURN_ADDRESS despite not owning/authorizing anything since step 1
object::unburn(&A_signer, O);
assert!(object::owner(O) == A_addr, 0); // A now owns O again, stolen from B's intended burn
``` [6](#0-5)

    public fun transfer_with_ref(self: LinearTransferRef, to: address) {
        assert!(!exists<Untransferable>(self.self), error::permission_denied(EOBJECT_NOT_TRANSFERRABLE));

        // Undo soft burn if present as we don't want the original owner to be able to reclaim by calling unburn later.
        if (exists<TombStone>(self.self)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(self.self);

        );

            Transfer {
                object: self.self,
                from: object.owner,
                to,
            },
        );
        object.owner = to;
    }

    /// allow_ungated_transfer is set true. Note, that this allows the owner of a nested object to
    /// transfer that object, so long as allow_ungated_transfer is enabled at each stage in the
    /// hierarchy.
    public fun transfer_raw(
        owner: &signer,
        object: address,
        to: address,
    ) {
        let owner_address = signer::address_of(owner);
        verify_ungated_and_descendant(owner_address, object);
        transfer_raw_inner(object, to);
    }

    inline fun transfer_raw_inner(object: address, to: address) {
        let object_core = borrow_global_mut<ObjectCore>(object);
        if (object_core.owner != to) {
            event::emit(
                Transfer {
                    object,
                    from: object_core.owner,
                    to,
                },
            );
            object_core.owner = to;
        };
    }

    /// Allow origin owners to reclaim any objects they previous burnt.
    public entry fun unburn<T: key>(
        original_owner: &signer,
        object: Object<T>,
    ) {
        let object_addr = object.inner;
        assert!(exists<TombStone>(object_addr), error::invalid_argument(EOBJECT_NOT_BURNT));

        // The new owner of the object can always unburn it, but if it's the burn address, we go to the old functionality
        let object_core = borrow_global<ObjectCore>(object_addr);
        if (object_core.owner == signer::address_of(original_owner)) {
            let TombStone { original_owner: _ } = move_from<TombStone>(object_addr);
        } else if (object_core.owner == BURN_ADDRESS) {
            // The old functionality
            let TombStone { original_owner: original_owner_addr } = move_from<TombStone>(object_addr);
            assert!(
                original_owner_addr == signer::address_of(original_owner),
                error::permission_denied(ENOT_OBJECT_OWNER)
            );
            transfer_raw_inner(object_addr, original_owner_addr);
        } else {
            abort error::permission_denied(ENOT_OBJECT_OWNER);
        };
    }
