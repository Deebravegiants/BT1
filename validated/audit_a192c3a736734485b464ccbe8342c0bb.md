This confirms the asymmetry: in `AuthQuery` (OAuth callback), `shop` is included in `to_signable_string` and thus covered by the HMAC verification (`lib/shopify_api/auth/oauth/auth_query.rb:34-43`), but in `Webhooks::Request`, `to_signable_string` returns only `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), excluding the `shop-domain`, `topic`, and `webhook-id` headers entirely from the HMAC computation.### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity solely via `Utils::HmacValidator.validate`, which HMACs only the raw request body. The `shop` (and `topic`/`webhook_id`) values, which are trusted and forwarded to the app's handler as authenticated tenant identity, are taken from HTTP headers that are never part of the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the signature: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string`, i.e. only the body, and compares it via `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` only checks this body HMAC, then immediately trusts `request.shop` as the tenant identity passed into `WebhookMetadata`, which the handler uses to attribute the webhook to a shop (e.g., to look up per-shop data/sessions): [4](#0-3) [5](#0-4) 

This is an inconsistency within the gem itself: the OAuth `AuthQuery` path deliberately includes `shop` inside the HMAC-signed string, correctly binding shop identity to the signature: [6](#0-5) 

But the webhook path does not apply the same binding, breaking the equality that should hold: `shop asserted in WebhookMetadata.shop == shop cryptographically bound in the verified HMAC signature`. In practice, since the app's `client_secret` (and thus the HMAC key) is shared across every shop that installs the app, any tenant that can trigger a legitimately-signed webhook for their own store (by installing the app, since installation is unprivileged for public apps) obtains a `(raw_body, hmac)` pair that is valid under the shared secret regardless of which `shop-domain` header accompanies it. That attacker can then replay the same body/HMAC to the app's webhook endpoint with an arbitrary `x-shopify-shop-domain` header value naming a victim shop. `HmacValidator.validate` will accept it (it never examined the shop header), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body came from the victim shop.

### Impact Explanation
This breaks the shop-identity binding the library implies it provides once a webhook passes signature verification ("this will verify the request did indeed come from Shopify" per the gem's own documentation). Host applications built on the documented API reasonably treat `data.shop` from a processed webhook as authenticated. If the host application uses `data.shop` to select the shop-scoped session/access-token, update shop records, or trigger per-shop side effects, this vulnerability enables cross-tenant data confusion/injection — an attacker-controlled shop can inject data attributed to a victim shop.

### Likelihood Explanation
Any user can create a Shopify development/partner store and install a public app to receive a legitimately-signed webhook containing attacker-chosen body content (e.g., product/order fields the attacker controls in their own store). No access token, `client_secret`, or privileged account is required — only normal use of the app as an unprivileged installer/tenant. The `shop` header can then be freely rewritten in a replayed request because it is outside the signed data.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`) header values in the HMAC-signable content in `ShopifyAPI::Webhooks::Request#to_signable_string`, or otherwise cryptographically bind the shop domain to the verified payload before constructing `WebhookMetadata`, mirroring the approach already used in `ShopifyAPI::Auth::Oauth::AuthQuery`.

### Proof of Concept
1. Attacker installs the target public app on their own controlled store (`attacker-shop.myshopify.com`), an unprivileged action.
2. App sends a legitimate webhook to attacker's endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker crafts `B` to contain arbitrary/malicious field values (fully controlled by the attacker as owner of that shop's data).
4. Attacker replays the exact same body `B` and HMAC header to the same app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; since `to_signable_string` only returns the raw body (`lib/shopify_api/webhooks/request.rb:36-38`), the check passes.
6. `WebhookMetadata.shop` is set to `"victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), and the handler processes attacker-controlled data as authenticated data for the victim shop.
