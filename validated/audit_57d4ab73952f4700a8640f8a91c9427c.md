### Title
Gas Griefing via Return-Bomb in `EvmHost` Incoming-Message Dispatch — Unbounded `call()` Return Data Copy Enables Relayer DoS - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatchIncoming` (and the timeout counterparts) forward ISMP messages to arbitrary destination modules using a raw, gas-unbounded `.call()` whose return data is unconditionally copied into memory by the EVM/Solidity call ABI, even though only the `success` boolean is consumed. An attacker who controls (or deploys) the destination `to` address can make `onAccept`/`onGetResponse`/`onPostRequestTimeout`/`onGetTimeout` return an enormous blob, forcing the relayer's `handlePostRequests`/`handleGetResponses`/timeout-handling transaction to pay for the return-data copy and associated quadratic memory expansion. This is the same "return bomb" class described in the OmniPortal report, and it lands on Hyperbridge's message-delivery path.

### Finding Description
`EvmHost.dispatchIncoming(PostRequest,...)` performs:
```solidity
(bool success,) = address(destination)
    .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
``` [1](#0-0) 

No `gas:` stipend is set, so the callee receives essentially all remaining gas, and although only `success` is bound (`,` discards the bytes), Solidity's low-level `call()` returns `(bool, bytes memory)` and the generated code performs the `RETURNDATACOPY` into freshly allocated memory as part of constructing that return tuple regardless of whether the caller uses the second element. This is exactly the mechanism the referenced OmniPortal report calls out: discarding the return value in the Solidity source does not prevent the return data from being loaded into memory.

The same unguarded pattern recurs at every incoming-message dispatch point in the host:
- `dispatchIncoming(GetResponse,...)` calling `onGetResponse` [2](#0-1) 
- `dispatchTimeOut(GetRequestTimeout,...)` calling `onGetTimeout` [3](#0-2) 
- `dispatchTimeOut(PostRequestTimeout,...)` calling `onPostRequestTimeout` [4](#0-3) 

These are invoked in a loop from `HandlerV2.handlePostRequests` / `handleGetResponses`, which iterate over every leaf in the relayer-submitted batch and call `host.dispatchIncoming(...)` for each without any gas budgeting per leaf or bound on the target's return-data size: [5](#0-4) [6](#0-5) 

Crucially, the destination `to` of a `PostRequest` is fully attacker-controlled: any application (including one an attacker deploys) can dispatch a request whose `to` field points at an arbitrary contract on the destination chain, and that contract's `onAccept` will be invoked by any relayer who later submits proof of the request. There is no `extcodesize`-based short-circuit that also checks return-data size, and no `excessivelySafeCall()`-style bound exists anywhere in this call chain.

### Impact Explanation
A relayer submitting `handlePostRequests`/`handleGetResponses` for a batch that includes even one malicious leaf can have their entire batch's gas consumption blown up by the return-bomb, since the loop processes multiple leaves in one transaction and the malicious call sits inline in that loop. This can:
- Force relayers to either drastically over-provision gas (making relaying uneconomical/unprofitable), or have their delivery transactions revert out-of-gas, stalling delivery of every other (legitimate) request bundled in the same proof/batch.
- On destination chains with lower block gas limits, a large enough return bomb can make an entire XStream/route practically undeliverable, matching the "route unable to deliver messages" impact class, since MMR multiproof verification plus a return-bomb-inflated `onAccept` call can exceed the block gas limit.

This is a Medium/High-severity gas-griefing / relay-DoS issue: it does not directly steal funds, but it can degrade or deny message delivery liveness for the affected route, and it is reachable by any unprivileged party who can dispatch a `PostRequest`/`GetResponse` targeting an attacker-controlled destination contract.

### Likelihood Explanation
The precondition is trivial: dispatching a `PostRequest` from any source-chain module to an attacker-deployed destination contract requires no special privilege — this is the exact same interface used by ordinary cross-chain applications. Any user who can submit a dispatch (or a malicious/compromised app owner) can trigger this, and it does not require compromising the relayer, host, or consensus layer.

### Recommendation
Bound the destination call's return data using an "excessively safe call" pattern (as recommended in the original OmniPortal advisory), e.g., forwarding a fixed gas stipend and truncating/ignoring the return data using inline assembly that limits `RETURNDATACOPY` size (or performs the call without copying returndata into memory at all, relying only on the success flag). Apply this to all four dispatch points: `dispatchIncoming(PostRequest,...)`, `dispatchIncoming(GetResponse,...)`, `dispatchTimeOut(PostRequestTimeout,...)`, and `dispatchTimeOut(GetRequestTimeout,...)` in `evm/src/core/EvmHost.sol`.

### Proof of Concept
1. Deploy `MaliciousModule` on the destination chain implementing `onAccept(IncomingPostRequest calldata)` (and/or `onGetResponse`/`onPostRequestTimeout`) that returns a several-hundred-KB `bytes` blob (e.g. via an explicit large `return` or by consuming most gas in a loop before returning a huge buffer).
2. From any source-chain application, dispatch a `PostRequest` with `to = address(MaliciousModule)` and a body that will pass `MaliciousModule`'s own checks (or none at all, since `onAccept` executes regardless of body content unless it reverts).
3. Once finalized, a relayer submits `HandlerV2.handlePostRequests` bundling this request with other unrelated legitimate requests in the same MMR proof.
4. Observe that `EvmHost.dispatchIncoming`'s `address(destination).call(...)` copies the full return blob into memory, consuming gas disproportionate to the relayer's expectation (following the same gas-scaling curve as in the original OmniPortal report's table), causing the whole batch transaction to revert out-of-gas or become unprofitable for the relayer to submit, thereby stalling delivery of the co-batched legitimate requests.
