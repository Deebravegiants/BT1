### Title
Unguarded division in AMM invariant math can panic (division-by-zero) and halt Deposit when one side of the pool balance is depleted to zero - (File: `program/src/math.rs`)

### Summary
Analogous to TFLite `GatherNd`'s division-by-zero when an empty `params` tensor makes `params_shape.Dims(.)` zero, Raydium AMM's `InvariantToken::exchange_coin_to_pc` / `exchange_pc_to_coin` and `InvariantPool::exchange_token_to_pool` / `exchange_pool_to_token` perform `checked_div(self.token_coin/self.token_pc/self.token_total)` followed by an unconditional `.unwrap()`, with no upstream check that the divisor is non‑zero. If `total_coin_without_take_pnl` or `total_pc_without_take_pnl` is zero when `process_deposit` builds the `InvariantToken`, the ensuing division panics, aborting the transaction (and, depending on caller composition, can be used to reliably fail deposits against a degenerate pool state).

### Finding Description
`InvariantToken` (used only by `process_deposit`) divides by its own operand fields without a zero guard: [1](#0-0) 

These are invoked in `process_deposit` with `token_coin = total_coin_without_take_pnl` and `token_pc = total_pc_without_take_pnl`, derived directly from `calc_total_without_take_pnl_no_orderbook(amm_pc_vault.amount, amm_coin_vault.amount, &amm)`: [2](#0-1) 

Depending on `deposit.base_side`, the code calls either `exchange_coin_to_pc` (divides by `total_coin_without_take_pnl`) or `exchange_pc_to_coin` (divides by `total_pc_without_take_pnl`): [3](#0-2) 

The only guard present before this is `if amm.lp_amount == 0 { return Err(AmmError::NotAllowZeroLP) }` — this checks `lp_amount`, **not** `total_coin_without_take_pnl` or `total_pc_without_take_pnl`. `calc_total_without_take_pnl_no_orderbook` simply subtracts `need_take_pnl_pc`/`need_take_pnl_coin` from the raw vault balances with `checked_sub`, which can legitimately yield `0` (not just error out) if the vault balance exactly equals the accrued but unclaimed pnl on that side: [4](#0-3) 

The identical unguarded-division pattern also exists in `InvariantPool::exchange_pool_to_token` / `exchange_token_to_pool` (divides by `self.token_total`), used in `Deposit`/`Withdraw`/test code: [5](#0-4) 

For `Withdraw`, `token_total` is `amm.lp_amount`, which is explicitly checked non‑zero before use (`withdraw.amount >= amm.lp_amount` rejects `lp_amount == 0`) — that call site is safe: [6](#0-5) 

But for `Deposit`, the analogous `InvariantPool` calls use `token_total = total_coin_without_take_pnl` / `total_pc_without_take_pnl`, which are **not** checked for zero anywhere before use: [7](#0-6) 

### Impact Explanation
If `total_coin_without_take_pnl` or `total_pc_without_take_pnl` reaches exactly `0` while `amm.lp_amount != 0` (i.e., unclaimed pnl on one side exactly consumes that side's vault balance), any subsequent `Deposit` transaction on that pool will hit `checked_div(0)` → `None` → `.unwrap()` panics. A Rust panic inside a Solana BPF program aborts the transaction non‑gracefully (rather than returning a typed `ProgramError`), which can be used to permanently deny deposits (denial of service) against that specific pool state until `withdrawpnl` is called by the privileged `pnl_owner` to rebalance `need_take_pnl_*`. This is a liveness/availability impact on LP deposits, not a direct fund-theft primitive, but it matches the External Report's classification of a division-by-zero defect reachable through attacker-influenced state without requiring any privileged action to trigger the crash.

### Likelihood Explanation
Reaching `total_coin_without_take_pnl == 0` (or the pc equivalent) exactly requires the accumulated `need_take_pnl_coin`/`need_take_pnl_pc` to precisely equal the vault's raw token balance on that side. Swaps are guarded (`swap_amount_out >= total_*_without_take_pnl` is rejected) so a single swap transaction cannot drive the value to exactly zero, and `calc_take_pnl`'s internal invariant check (`pool_pc*pool_coin >= calc_pnl_x*calc_pnl_y`) makes reaching precisely 0 via normal pnl accrual unlikely but not proven impossible given u128/U256 rounding across many operations. I could not construct or confirm a concrete single-transaction path that forces this exact zero state from genuinely permissionless swap/deposit/withdraw calls alone; it appears to require a specific sequence of state accrual over multiple transactions rather than one attacker-controlled call. This lowers confidence that it is reachable purely "from a single submitted transaction with attacker-chosen accounts and data," as required by the validation criteria.

### Recommendation
Add explicit zero-checks before invoking `InvariantToken`/`InvariantPool` division helpers (returning `AmmError::CalculationExRateFailure` or similar) whenever `total_coin_without_take_pnl`, `total_pc_without_take_pnl`, or `token_total` could be zero, mirroring the existing `lp_amount == 0` guard. Convert the internal `checked_div(...).unwrap()` calls in `math.rs` to propagate `None` via `?`/`ok_or` instead of panicking, so a degenerate state returns a normal program error rather than aborting via panic.

### Proof of Concept
A concrete, single-transaction proof of concept could not be constructed with confidence: doing so requires driving `total_coin_without_take_pnl` (or `total_pc_without_take_pnl`) to exactly `0` while `amm.lp_amount != 0`, which — based on the guards found in swaps and the invariant check in `calc_take_pnl` — appears to require multi-transaction state accrual (accumulating `need_take_pnl_coin`/`need_take_pnl_pc` via `calc_take_pnl` across several deposit/withdraw calls) rather than a single attacker-chosen call. Conceptually: (1) create a pool via `Initialize2`; (2) perform swaps/deposits/withdraws over multiple transactions to accrue `need_take_pnl_coin` until it approaches `amm_coin_vault.amount`; (3) submit a final `Deposit` with `base_side = 0` (base coin) once `total_coin_without_take_pnl == 0`, which calls `InvariantToken::exchange_coin_to_pc`, hits `checked_div(0)`, and panics. This path is not verified end-to-end against the guards in `calc_take_pnl`/swap instructions, so it should be treated as an unconfirmed hypothesis requiring further dynamic testing (e.g., a Devin session running the program against a local validator) rather than a proven exploit.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
