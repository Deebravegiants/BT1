### Title
Webhook shop-domain header is trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` validates authenticity using `Utils::HmacValidator.validate(request)`, which computes the HMAC only over `to_signable_string`, i.e. the raw HTTP body. The `shop` attribute, however, is read from the `X-Shopify-Shop-Domain` HTTP header and is never included in the signed bytes. `Registry.process` uses this unauthenticated `shop` value directly when dispatching to the app's `WebhookHandler`, so the tenant identity that the app trusts is disconnected from the bytes that were actually HMAC-verified.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

Meanwhile `shop` is parsed from a separate header that carries no cryptographic binding to the signed body: [2](#0-1) 

`Registry#process` validates the HMAC over the body and then trusts `request.shop` for building the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The identity binding that should hold is:
`shop attributed to the webhook == shop cryptographically bound to the HMAC-verified bytes`

In this implementation that equality does not hold: the HMAC verifies "bytes parsed" (the raw body) while the `shop` field consumed by the handler comes from "bytes not covered" (the `X-Shopify-Shop-Domain` header). This is the same class of bug as the reported analog — an identity field is acted upon (used to attribute the event to a tenant/shop) without being covered by the authenticity check that is supposed to bind it.

### Impact Explanation
Any entity capable of installing the app on their own store (an unprivileged actor with respect to any other merchant) receives genuine webhooks for their own shop with a valid HMAC over the body. Because the shop-domain header is not part of the signed bytes, that same valid `(body, hmac)` pair remains valid if replayed with a different `X-Shopify-Shop-Domain` header. An app that keys any per-tenant behavior (e.g., record lookups, session/access-token selection, GDPR/data-redaction actions, billing, or multi-tenant data writes) off `WebhookMetadata#shop` as delivered by this gem can be made to process attacker-supplied body content while attributing it to an arbitrary victim shop, producing cross-tenant data confusion. This matches the "cross-tenant access" class of Critical impact defined in scope.

### Likelihood Explanation
Exploitability depends entirely on whether the calling application uses `WebhookMetadata#shop` as a trusted per-tenant key when handling webhook payloads — which is the intended and documented usage of this API (`Registry.process` and `WebhookHandler#handle` are the gem's own dispatch mechanism, not something outside its documented API). No access token, `api_secret_key`, or privileged access is required from the attacker; they only need the ability to trigger a legitimate webhook for a shop they control (trivial, via installing the app or performing an action that triggers a webhook) and the ability to replay/forge the HTTP request that reaches the app's webhook endpoint with a modified header.

### Recommendation
Bind the shop identity to the HMAC-verified bytes rather than trusting an unsigned header:
- Include the shop domain in the signable string used for HMAC verification, or
- Independently authenticate/derive the shop from data that Shopify itself signs (e.g., cross-check the header value against a shop association already known/authorized for a matching, previously-established session before dispatch), or
- At minimum, document prominently that `WebhookMetadata#shop` is not part of the HMAC-verified payload and must not be used as a trust boundary without additional verification by the host application.

### Proof of Concept
1. Install the (victim) app on `attacker-shop.myshopify.com`; trigger any webhook topic the app handles. Capture the resulting HTTP request: raw body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid, computed by Shopify over `B` with the app's `client_secret`).
2. Replay this exact request to the app's webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com` (leave `B` and `H` untouched).
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` is constructed;
`Utils::HmacValidator.validate(request)` calls `to_signable_string`, which returns `B` — the HMAC check passes because it never inspected the shop header. [4](#0-3) 
4. `Registry.process` proceeds to call `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` with `shop == "victim-shop.myshopify.com"` and `body == B` (attacker-controlled content from their own shop), demonstrating that the app-level handler receives attacker-influenced data falsely attributed to the victim tenant. [5](#0-4)
