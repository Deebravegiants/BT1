### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing on webhook delivery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop` attribute (from the `X-Shopify-Shop-Domain` header) is read separately and is never included in the signed bytes. `Webhooks::Registry.process` trusts `request.shop` to identify the tenant for the handler without that value being covered by the HMAC check.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively [1](#0-0) , while `Request#shop` is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header [2](#0-1) . `HmacValidator.validate` verifies the HMAC strictly against `to_signable_string` (the body) using the app's `api_secret_key` [3](#0-2) . `Registry.process` calls `Utils::HmacValidator.validate(request)` and then, once the HMAC on the body is confirmed, immediately forwards `request.shop` as the tenant identifier to the handler: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

This breaks the identity binding `authenticated_bytes == acted_upon_shop`: the HMAC authenticates only the JSON body bytes, not the shop header, so `request.shop` (an attacker-controlled HTTP header) is treated as trustworthy tenant data even though it was never part of the signed material.

Because the `api_secret_key` used to compute/verify the HMAC is a single app-level secret shared across every shop that installs the app (not shop-specific), any party who can trigger a legitimate webhook for their own shop (e.g., by installing the app on a shop they control and performing an action that fires a webhook with an attacker-chosen body, such as a custom order note or product title) obtains a validly-signed `(body, hmac)` pair. They can then replay that exact body with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop. `HmacValidator.validate` will still pass, since it only checks the body bytes against the secret, and `Registry.process` will hand the handler a `WebhookMetadata` object claiming `shop: <victim-shop>` with attacker-controlled `body`.

### Impact Explanation
This is a cross-tenant identity confusion: the webhook processing pipeline in this gem allows an attacker to make webhook data appear to originate from a different (victim) shop than the one that actually produced it, while passing HMAC validation. Any host application that uses `request.shop` from `WebhookMetadata` (as documented/intended usage of this gem) to look up per-shop sessions, access tokens, or to gate multi-tenant business logic will process attacker-controlled data under the wrong tenant's identity — a cross-tenant access condition, which is listed as a Critical impact category.

### Likelihood Explanation
Requires only an app installation on a shop the attacker controls (no special credentials, no `api_secret_key`, no access token) plus the ability to trigger any webhook whose body content is attacker-influenced, then a single forged HTTP request replaying that body under the target's shop domain header. No merchant misbehavior or privileged access is needed — this is exploitable by any unprivileged party able to install the app once, which keeps likelihood moderate-to-high.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signable string, or otherwise cryptographically bind the `shop-domain` header to the verified body (e.g., verify the header value against the shop associated with the specific webhook subscription/id via ID lookup with Shopify, or require verification of `shop` as part of `to_signable_string`). At minimum, document that `request.shop` is unauthenticated and must not be trusted for tenant identification without an independent verification step.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and obtains a legitimately signed webhook whose body is attacker-influenced (e.g. an order webhook containing a note field they control), computing `hmac = HMAC-SHA256(api_secret_key, raw_body)`.
2. Attacker sends a forged HTTP POST to the app's webhook endpoint with:
   - `X-Shopify-Hmac-Sha256`: the valid hmac captured in step 1
   - `X-Shopify-Shop-Domain`: `victim-shop.myshopify.com`
   - Body: the same `raw_body` from step 1
3. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate(request)`, which passes because it only checks the body bytes [5](#0-4) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, despite the data having never come from that shop [6](#0-5) .
