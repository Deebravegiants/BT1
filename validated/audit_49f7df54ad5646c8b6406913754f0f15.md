This confirms the finding: `docs/usage/webhooks.md:125` states the library "will verify the request did indeed come from Shopify" as the security guarantee of `Registry.process`, and the handler receives `data.shop` (line 14 of the doc) as an authenticated field — the documented contract implies `shop` is trustworthy since it's part of the verified webhook data. But the implementation only signs the raw body.

### Title
Webhook Shop-Domain Header Spoofing via HMAC Scope Bypass Enables Cross-Tenant Webhook Injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely via `Utils::HmacValidator.validate(request)`, which computes and checks the HMAC over `request.to_signable_string`. For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body` [1](#0-0) . Once the HMAC check on the body passes, `Registry.process` dispatches to the handler using `request.shop`, which is read verbatim from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [2](#0-1)  and passed straight into `WebhookMetadata` [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop attributed to the webhook event == shop that the HMAC-verified body actually originated from`. In this gem, the HMAC only covers the raw JSON body; the `shop-domain` header (along with `topic`, `webhook-id`, `api-version`) is excluded from the signature computation entirely, since `to_signable_string` returns just `@raw_body` [1](#0-0) . `Utils::HmacValidator.validate_signature` recomputes an HMAC-SHA256 over that signable string with `Context.api_secret_key` and compares it via `OpenSSL.secure_compare` against the header-derived digest [4](#0-3) . A valid signature therefore only proves the body bytes are authentic — it says nothing about which shop the header claims sent it.

`Registry.process` treats a passing HMAC check as sufficient authorization to act on the header-derived `shop`:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [3](#0-2) 

An unprivileged internet user who can obtain any single legitimately-signed webhook body/HMAC pair for a topic (trivially done by installing the app on their own shop and receiving one real webhook) can replay that exact `raw_body` + `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value. `Utils::HmacValidator.validate` will still return `true` because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the attacker-chosen shop, with the topic/webhook_id also attacker-controlled and unverified.

### Impact Explanation
The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" [5](#0-4)  and describes `data.shop` as simply "The shop domain of the webhook" [6](#0-5)  without any caveat that this field is unauthenticated — implying host applications are meant to trust it as part of the verified payload. Applications following this documented contract (e.g., using `data.shop` to look up which tenant's session/record to update, as shown in the very doc example: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [7](#0-6) ) can be tricked into applying webhook body content to the wrong tenant — a cross-tenant data confusion driven entirely by an unauthenticated header.

### Likelihood Explanation
Exploitation requires no privileged credentials, no `api_secret_key`, and no access token: only one legitimately-signed body/HMAC pair for *any* shop (attacker's own test shop works) plus the ability to send an arbitrary HTTP request to the target app's public webhook endpoint with a forged shop-domain header. This is realistically achievable by any developer who has installed the app once.

### Recommendation
Include the shop domain (and ideally topic/webhook_id) in the signed material verified against Shopify, or independently verify `request.shop` against a known/registered shop before dispatch (e.g., cross-check against the shop associated with the webhook_id via a registration lookup), rather than trusting the unauthenticated header once only the body HMAC has passed.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; capture one real incoming webhook request: raw body `B` and header `X-Shopify-Hmac-Sha256: H` (both valid, `H = HMAC-SHA256(api_secret_key, B)`).
2. Replay to the app's public webhook endpoint:
```
POST /webhooks
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: H
X-Shopify-Shop-Domain: victim-shop.myshopify.com
X-Shopify-Webhook-Id: <attacker-chosen>

<B>
```
3. `Utils::HmacValidator.validate` succeeds (only `B` is checked). `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, even though the body never originated from `victim-shop`.
