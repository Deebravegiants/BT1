Found: `LPLock.recordLock` explicitly requires `amount == 0 → revert ZeroAmount` [1](#0-0) . This is the one hard revert on the phase-2 finalize path that cannot be "swallowed" by the brick-resistance layering the way `pair.swap`/`getAmountOut`-round-to-zero paths are guarded in `_pairRebalance`/`_seedRebalancing`.

`finalizeGraduation` calls `_seedUniswapV2Direct`, which returns `liquidity`, and unconditionally passes it into `LPLock(lpLock).recordLock(tokenAddress, lpPair, liquidity)` [2](#0-1) . The natspec on `_swapBudget` itself documents the exact failure mode: an extreme hostile pre-seed can drive `_pairRebalance`'s swap to consume 100% of one side, `_routerDepositAndDispose` then skips `addLiquidity` entirely (`remToken == 0` or `remLT == 0`), and `liquidity` comes back `0` [3](#0-2) . The 99%-budget reservation is stated to prevent this "in practice," but it is a heuristic cap, not a proof — it only guarantees non-zero legs when `s_unconstrained` is "orders of magnitude below `maxSwap`" for "any realistic pre-seed," explicitly conceding it can still bind for "catastrophic pre-seeds beyond our budget capacity" [4](#0-3) .

If that zero-liquidity edge case is reached, `recordLock` reverts with `ZeroAmount`, and since `LPLock.recordLock`'s one-shot `lockedAt` guard means `finalizeGraduation` cannot be retried past this point without reverting on the same zero-liquidity computation again (the pre-seed state and cached `tokensForLP`/`ltFromPair` don't change), the token is permanently stuck in `Lifecycle.Graduating` — trading frozen, curve-raised LT and the 250M LP-reserve tokens parked on `Bonding` unreachable, exactly the persistent-DoS/fund-freeze class the CVE-2023-37016 analog calls for.

However, I was not able to fully verify within available tool calls whether the attacker can actually construct a pre-seed cheaply enough (front-run `factory.createPair` + `pair.mint`) to drive `_swapBudget`'s 99% margin to bind exactly at the boundary that zeroes out `remToken`/`remLT`, given the `_seedRebalancing` "below-band" direct-mint fallback (`DIRECT_MINT_PRESEED_BPS` check) also intercepts many extreme-skew shapes before reaching `_pairRebalance` [5](#0-4) . Confirming exact numeric feasibility (reserve/target ratios, uint112 pair caps, and whether the direct-mint fallback's band closes off every path that could zero a leg) would need computing concrete numbers or fuzzing, which requires running the actual Solidity math rather than static reading — beyond what I could do with read-only inspection here.

### Title
Zero-liquidity graduation finalize permanently bricks a token when an extreme hostile LP pre-seed saturates the `_swapBudget` reservation - (File: packages/contracts/src/Bonding.sol, packages/contracts/src/LPLock.sol)

### Summary
`Bonding.finalizeGraduation`'s hostile-pre-seed defense caps the rebalance swap at 99% of available inventory via `_swapBudget`, explicitly acknowledging (in its own natspec) that a sufficiently extreme pre-seed can still consume 100% of one side of the deposit, causing `_routerDepositAndDispose` to skip `addLiquidity` and return `liquidity == 0`. `LPLock.recordLock` unconditionally reverts on `amount == 0`, and its one-shot `lockedAt` guard means the same zero-liquidity computation recurs on every retry, permanently trapping the token in `Lifecycle.Graduating`.

### Finding Description
`finalizeGraduation` drains and seeds the graduation LP via `_seedUniswapV2Direct` → `_seedRebalancing` → `_pairRebalance`/`_routerDepositAndDispose`, then unconditionally calls `LPLock.recordLock(tokenAddress, lpPair, liquidity)` with whatever `liquidity` came back [2](#0-1) . `_swapBudget` reserves only 1% of the swap-side inventory to guarantee both legs of the subsequent `addLiquidity` are non-zero, but its own natspec documents that this guarantee holds only "for any realistic pre-seed" and concedes the cap can be "beyond our budget capacity" for a catastrophic pre-seed, in which case `remToken == 0` or `remLT == 0`, `addLiquidity` is skipped, and `liquidity` returns `0` [3](#0-2) . `LPLock.recordLock` reverts with `ZeroAmount` on that input and marks the finalize as permanently failing once `lockedAt` would otherwise be set (it never is, so retries hit the same zero-liquidity path deterministically since the cached `pendingGraduation` values and existing hostile-pre-seed pair state don't change between calls) [1](#0-0) .

### Impact Explanation
A token stuck in `Lifecycle.Graduating` can never trade again: `buy`/`sell` both revert with `TokenIsGraduating` while graduating [6](#0-5) , and `finalizeGraduation` deterministically reverts forever, so all curve-raised LT (`ltFromPair`, drained into `Bonding` by `Router.graduate` during phase 1) and the 250M LP-reserve tokens sitting on `Bonding` are permanently frozen with no owner rescue path. This is a permanent freeze of trader/creator funds.

### Likelihood Explanation
Reaching the extreme pre-seed ratio needed to saturate the 99% budget requires a well-resourced, deliberate front-run (`factory.createPair` + self-funded `pair.mint` at a specific hostile ratio) between phase 1 and phase 2, which the protocol's own `AGENTS.md`/inline natspec treats as a real, anticipated attack class (it is the entire reason `_seedUniswapV2Direct`'s three-regime defense exists) rather than a purely theoretical corner case.

### Recommendation
Add an explicit guard in `_routerDepositAndDispose`/`_seedRebalancing` that detects the zero-liquidity outcome before calling `recordLock`, and fall back to the same `_seedDirectMint` overpower path used for dust pre-seeds (transfer both cached amounts and mint directly) so `finalizeGraduation` never produces a zero `liquidity` value that would hard-revert against `LPLock`'s `ZeroAmount` check.

### Proof of Concept
Not independently reproduced with a fuzz/unit test in this pass; the failure mode is derived directly from the code's own documented boundary condition (`_swapBudget`'s natspec) and `LPLock.recordLock`'s `ZeroAmount`/one-shot-lock guards. Confirming the exact numeric pre-seed ratio (bounded by `uint112` V2 reserves and the `DIRECT_MINT_PRESEED_BPS` fallback band in `_seedRebalancing`) that reaches this path would require running the Solidity math (e.g., via `test/NoFeeSwapInput.t.sol`'s harness or a new fuzz test) rather than static review.

    function recordLock(
        address token,
        address lpPair,
        uint256 amount
    ) external {
        LPLockStorage storage $ = _s();
        if (!$.isLocker[msg.sender]) revert NotAuthorized();
        if (lpPair == address(0)) revert ZeroAddress();
        if (amount == 0) revert ZeroAmount();
        // `lockedAt` is the one-shot sentinel: it is always set to a non-zero
        // timestamp on the first lock, so the guard holds for any `amount`.
        if ($.locks[token].lockedAt != 0) revert AlreadyLocked();
        if (IERC20(lpPair).balanceOf(address(this)) < amount) revert InsufficientLPBalance();
        $.locks[token] = LockInfo({lpPair: lpPair, amount: amount, lockedAt: block.timestamp});
        emit LPLocked(token, lpPair, amount);
    }

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }
