### Title
Predictable, unauthenticated session cookie value is trusted as the cross-tenant session/access-token lookup key - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` resolves the active session purely from the raw bytes of the `shopify_app_session` cookie via `cookie_session_id`, with no signature or binding check performed by the gem. Session ids are generated in a fully predictable format (`"offline_#{shop}"` or `"#{shop}_#{associated_user.id}"`), so any client that can set its own cookie value can cause the host application to resolve and use another merchant's stored `Session` (and therefore its access token), breaking the identity binding between "the cookie the gem issued to shop A" and "the session the host application loads."

### Finding Description
When an app is non-embedded (or embedded without a Shopify ID token present), `current_session_id` falls back to `cookie_session_id`, which simply returns whatever value is stored under `Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME`: [1](#0-0) [2](#0-1) 

This value is never checked against an HMAC, JWT signature, or any other proof that it was issued by Shopify/the gem for the requesting browser — it is trusted as-is to become the lookup key for the merchant's `Session` object (which contains the access token) in the host application's session storage.

The value that gets placed in this cookie is fully deterministic and derivable from public information (the shop's `myshopify.com` domain, which is exposed in URLs, webhooks, and the OAuth flow itself): [3](#0-2) [4](#0-3) 

The gem itself sets this exact predictable id as the cookie value at the end of the OAuth callback for non-embedded apps: [5](#0-4) 

Nothing in `SessionCookie` (a plain `name`/`value`/`expires` struct) cryptographically signs or binds the value to the shop that owns it: [6](#0-5) 

Equality being checked: the gem treats `cookie_bytes_supplied_by_browser == session_id_used_to_fetch_access_token`, when the correct invariant should be `cookie_bytes_cryptographically_bound_to(shop_that_completed_OAuth) == session_id_used_to_fetch_access_token`. Because the id format is public/predictable (`"offline_#{shop}"`), any client — including a merchant who has installed the app on their own store and can freely edit cookies sent by their own browser — can substitute a different shop's id and have the host app resolve a different tenant's session and access token, exactly mirroring the TransmuterBuffer pattern of trusting a reference/pointer without validating that the underlying resource still legitimately belongs to the current authenticated context.

### Impact Explanation
If the host application uses this gem's documented `current_session_id`/`cookie_session_id` flow to key its session store (as shown in `docs/getting_started.md`), an attacker can set the `shopify_app_session` cookie to `offline_<victim-shop>.myshopify.com` (or a guessed `"#{shop}_#{user_id}"` for online tokens) and have the application load and act with another merchant's stored access token — cross-tenant access to Admin API data and possibly write actions performed with the victim's stolen token by proxy.

### Likelihood Explanation
The ids are not secrets: shop domains are public/known, and online-session ids only require guessing a small associated user id. No secret material (`api_secret_key`, access token) is needed by the attacker — only the ability to set a cookie for their own browser session, which is available to any unprivileged internet user (including a legitimately installed but malicious merchant).

### Recommendation
Do not use raw, predictable strings as the sole session cookie value that also functions as the session-store lookup key. Bind the cookie to the actual session cryptographically (e.g., sign/encrypt the cookie payload with `Context.api_secret_key`, or store only an unguessable, random token in the cookie that maps server-side to the session), and verify that signature/binding in `cookie_session_id` before returning it as a trusted session id.

### Proof of Concept
1. Merchant A completes OAuth for shop `shop-a.myshopify.com`; per `Auth::Oauth.validate_auth_callback`, the app sets cookie `shopify_app_session=offline_shop-a.myshopify.com` (non-embedded, offline case).
2. A user of `shop-b.myshopify.com` (attacker, already an authenticated merchant of their own store) simply sets their browser's `shopify_app_session` cookie to `offline_shop-a.myshopify.com`.
3. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_shop-a.myshopify.com"` verbatim from `cookie_session_id` with no verification.
4. The host app looks up and activates shop A's `Session` (containing shop A's access token) and serves shop A's data/actions to the attacker.

      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
