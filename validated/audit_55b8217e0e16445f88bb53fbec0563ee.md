### Title
Any op can drain tokens Emporium approved via a prior (possibly victim's) `permit2`/ERC20 approval, because stateless ops execute with `msg.sender = address(Emporium)` against an unrestricted, attacker-chosen `endpoint`/`callData`, and the balance-diff guard only checks tokens the attacker chooses to list in their own `erc20TokenAddresses` - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable` is a single shared contract used by every Hinkal user; any "stateless" `EmporiumOperation` is executed with `op.endpoint.call{value}(op.callData)` directly from `address(Emporium)`, with no allowlist on `op.endpoint`/`op.callData` beyond blocking the wallet-only selectors. Any ERC20/Permit2 allowance ever granted `from = address(Emporium)` to a spender is therefore a shared, persistent resource keyed only to the Emporium contract's own address, not to any user/stealth-address identity, and any subsequent unrelated `runAction` can invoke that spender to pull the approved tokens out of Emporium to an attacker-chosen recipient. The transaction-level balance/slippage checks in `runAction` and in `Hinkal.sol` only examine tokens present in that specific caller's own `circomData.erc20TokenAddresses` array, so an attacker can simply omit the drained token from their own array and the theft is invisible to those checks.

### Finding Description
Equality that should hold: `spender_of_allowance_created_by(any op executed via address(Emporium)) == that same submitter's subsequent op only`. In reality it holds: `spender_of_allowance_created_by(address(Emporium)) == anyone who can construct a valid runAction`, because the allowance is recorded by the ERC20/Permit2 contract against `owner = address(Emporium)`, an address shared by all users.

Code path:
1. A victim (or attacker themselves in an earlier tx) submits `runAction` with a stateless op: `op.invokeWallet=false` (or `stack.signerAddress==0`), `op.endpoint = permit2` (or the token itself), `op.callData = approve(token, router, MAX, deadline)`. This is executed at [1](#0-0)  via a plain low-level `.call`, so the approval's `owner` is `address(Emporium)`.
2. `verifyWallet` only checks a signature when `stack.signerAddress != address(0)` [2](#0-1) ; for stateless ops with `signerAddress==0` there is no signature/identity binding at all — the only gatekeeping is a valid ZK proof over the submitter's own UTXOs, unrelated to who set the approval.
3. There is no allowlist restricting `op.endpoint`/`op.callData` for stateless ops (confirmed: no `allowedEndpoint`/similar mapping exists anywhere in the repo), so any address and any calldata (other than the two blocked wallet selectors) can be called.
4. An attacker later submits their own `runAction` whose op calls `router.swapExactTokensForTokens(...)` (or any function that internally does `permit2.transferFrom(msg.sender, recipient, amount, token)`); because the router is invoked via `op.endpoint.call(...)` from `EmporiumUpgradeable`, `msg.sender` seen by the router/permit2 is `address(Emporium)`, so the router pulls from the persisted allowance and sends tokens to whatever recipient the attacker encodes (themselves).
5. The only balance protections are: `getBalancesForArray(circomData.erc20TokenAddresses)` before/after in `runAction` [3](#0-2)  and [4](#0-3) , and the `balanceDif == amountChanges[i] + utxoAmount` check in `Hinkal.sol` [5](#0-4) . Both loops iterate only over `circomData.erc20TokenAddresses`, which the attacker constructs for their own transaction. If the attacker simply omits the drained token from their own array, neither check observes or reverts on the drain — the check in `Transferer.sol`'s `getBalancesForArray` [6](#0-5)  never even reads that token's balance.

Why existing guards fail: `performHinkalChecks`, `verifyProof`, `rootHashExists`, `insertNullifiers`, `onlyAllowedRecipient`, `nonReentrant` all constrain the attacker's *own* declared tokens/UTXOs/nullifiers correctly, but none of them constrain arbitrary side effects of `op.endpoint.call` on tokens outside the declared `erc20TokenAddresses` array, and none of them bind a Permit2/ERC20 approval made `from address(Emporium)` to the specific user who created it.

### Impact Explanation
Direct theft of any ERC20 balance that Emporium has ever been made to approve to any spender via a stateless op (Permit2 `approve`/`permit`, or a plain `IERC20.approve` op) — this is Critical severity: direct theft of shielded/in-flight user funds. Any past user's approval effectively becomes a shared, standing allowance that an unrelated attacker can trigger at will as long as the spender still has allowance and Emporium (transiently) holds or receives the token. This is fully repeatable for every token/spender pair ever approved this way, and for every subsequent block until the allowance is consumed or revoked.

### Likelihood Explanation
Preconditions: (1) some op — from a victim, or a bootstrapping/legitimate flow — has previously executed `approve`/`permit2.approve` from `address(Emporium)` to a spender/router with nonzero allowance; (2) that spender contract, when called, moves tokens using `msg.sender` (i.e., `address(Emporium)`) as the payer with an attacker-controllable output/recipient parameter. Attacker cost is just one ordinary `runAction` transaction with a valid ZK proof over their own (unrelated, possibly zero-value) UTXOs — no signature, no privileged role, no special timing required. This is entirely within the unprivileged-EOA threat model: attacker crafts `CircomData`, `externalActionMetadata` (`EmporiumStack`), and chooses which tokens to declare in `erc20TokenAddresses`. The attack is repeatable every time such an allowance exists.

### Recommendation
- Disallow open-ended, standing approvals from `address(Emporium)` in stateless ops entirely, or scope every approval-consuming call to the same atomic transaction that created it (e.g., approve-then-swap-then-revoke within one `runAction`, never leaving a nonzero allowance after the call sequence completes).
- Add an allowlist for `op.endpoint` in stateless (non-wallet) ops, restricting calls to vetted router/permit2 usage patterns, and/or require any op that would move tokens out of Emporium to have its balance impact captured by including that token in `circomData.erc20TokenAddresses` for that same transaction (so the existing balance-diff/slippage checks actually see it).
- Alternatively, force all "stateless" interactions to route through per-user `HinkalWallet` instances (Case 1) so that approvals are scoped to each wallet address rather than to the shared `Emporium` contract, and never permit `signerAddress == address(0)` to make token-approving calls without ownership binding.

### Proof of Concept
Foundry fork test outline:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, and the canonical `Permit2` contract; register a mock `Router` whose `swapExactTokensForTokens(token, amount, recipient)` internally calls `permit2.transferFrom(msg.sender, recipient, amount, token)`.
2. Victim runAction #1: submit a stateless op `{endpoint: permit2, invokeWallet:false, value:0, callData: approve(TOKEN, ROUTER, type(uint160).max, deadline)}` with `signerAddress=0`; assert `permit2.allowance(address(Emporium), ROUTER, TOKEN) == type(uint160).max` after the tx.
3. Fund Emporium with `TOKEN` balance (e.g., via a legitimate earlier deposit UTXO that leaves funds on Emporium, or directly via `deal`).
4. Attacker runAction #2: submit their own unrelated proof/UTXO set with `circomData.erc20TokenAddresses` NOT including `TOKEN`; stateless op `{endpoint: ROUTER, callData: swapExactTokensForTokens(TOKEN, amount, attacker)}`.
5. Assert equality violated: `permit2.transferFrom` moved `amount` of `TOKEN` from Emporium to attacker, `TOKEN.balanceOf(attacker)` increased by `amount`, and no UTXO/nullifier belonging to the attacker or victim reflects this change (`circomData.amountChanges` for `TOKEN` never existed in attacker's tx, and `balanceDif` checks in `Hinkal.sol`/`EmporiumUpgradeable.runAction` never executed for `TOKEN` because it was absent from `erc20TokenAddresses`).
6. Assert victim's own shielded UTXOs are unaffected/uncredited despite the token loss originating from their approval.
