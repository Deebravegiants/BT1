### Title
Webhook shop identity is not bound by the HMAC, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, then unconditionally trusts the `X-Shopify-Shop-Domain` header (exposed as `request.shop`) as the tenant identity for the handler. Because the header is not part of the signed material, an attacker who owns a legitimate installation of the app can capture one genuinely-signed webhook (body + HMAC) and replay it with a different `shop-domain` header value, successfully passing HMAC validation while impersonating an arbitrary victim shop.

### Finding Description
The identity binding that should hold is:

`shop_authenticated_by_HMAC == shop_used_by_handler`

but in this gem it is actually:

`shop_authenticated_by_HMAC (none, HMAC covers body only) != shop_used_by_handler (arbitrary header value)`

`Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, entirely independent of the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC exclusively against `to_signable_string` (the body): [3](#0-2) 

`Registry.process` performs only that HMAC check, then immediately builds `WebhookMetadata` using `request.shop` as the authenticated tenant identity handed to the app's handler, with no cross-check that the header actually matches a shop tied to the signed content: [4](#0-3) 

Since the app's webhook secret (`api_secret_key`) is shared across every shop that installs the app, any unprivileged attacker who installs the app on their own store receives genuinely HMAC-signed webhooks for their own shop. Because the shop header is excluded from the signed payload, the attacker can take that valid `(body, hmac)` pair and resend it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop domain. `HmacValidator.validate` still succeeds (it only checks the body/HMAC pair), so `Registry.process` dispatches the handler believing the event originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker with no access to any victim's credentials can make the gem assert, to the host application, that a webhook event came from a shop the attacker does not control. Any handler logic keyed off `WebhookMetadata#shop` (e.g., looking up per-shop settings, triggering per-shop side effects, invalidating data, or writing state under the victim's shop key) is spoofable by an attacker who merely has their own shop installation of the app — satisfying the "cross-tenant access" criterion without needing the app's `client_secret`, an access token, or any privileged account.

### Likelihood Explanation
Likelihood is high for any unprivileged internet user with a normal, low-privilege installation of the target app: they can trigger a real webhook against their own shop (e.g. via a normal store action), capture the raw body and HMAC header from the delivered request, and replay it to the same webhook endpoint with only the shop-domain header changed. No secret material, token, or elevated privilege is required — only the ability to install the app on a shop they control and observe/replay HTTP traffic to the app's own public webhook endpoint.

### Recommendation
Bind the shop identity into the value that is cryptographically verified, or otherwise cross-check it against server-side state established during OAuth for that shop, before trusting it in `WebhookMetadata`. Concretely: include the `shop-domain` (and `topic`/`webhook-id`) in `to_signable_string`, or validate that the shop asserted by the header matches a shop known to have produced the signed body (e.g., correlate against a nonce/id embedded in the payload, or require the recipient to independently confirm shop identity via a session lookup) before dispatching to the handler in `Registry.process`.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any subscribed webhook topic (e.g. `orders/create`) so Shopify sends a legitimately signed webhook: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Capture `B` and the HMAC header.
4. Resend the exact same `B` and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
5. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:26-31`) succeeds because it only checks `B` against the HMAC; `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches the handler with `shop: "victim.myshopify.com"`, even though the event content actually originated from the attacker's own shop.
