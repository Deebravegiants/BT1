### Title
Webhook `shop` identity is read from an HMAC-unverified header while only the body is signed, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the `shop` value that the SDK hands to the application's webhook handler comes from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header, which is never included in the signed material. This breaks the identity binding `shop_verified_by_hmac == shop_used_by_handler`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` verifies the HMAC over that signable string via `Utils::HmacValidator.validate(request)`, and — once verification succeeds — forwards `request.shop`, taken straight from the header accessor, into the `WebhookMetadata` object passed to the app's handler: [2](#0-1) 

`Request#shop` is a pure header read, with no cryptographic binding to the HMAC: [3](#0-2) [4](#0-3) 

`Utils::HmacValidator.validate` only compares the HMAC of `to_signable_string` (i.e., the raw body) against the received `hmac`, never touching `shop`, `topic`, or `webhook_id`: [5](#0-4) 

Because the shared HMAC secret (`Context.api_secret_key`) is the app's single client secret and is identical for every shop that has installed the app, any tenant that legitimately triggers a webhook delivery to a server they control (e.g., by creating a webhook subscription with a callback address of their choosing via Shopify's Admin API, using their own valid offline access token obtained through the normal, unprivileged OAuth install flow) can capture a `(raw_body, valid_hmac)` pair. Because the `shop-domain` header is not part of the signed bytes, the attacker can replay that exact body and HMAC to the victim app's real webhook endpoint while substituting an arbitrary `shop-domain` header. `Registry.process` will validate the HMAC successfully (it only checks the body) and dispatch the payload to the handler tagged with the attacker-chosen `shop`, i.e., "bytes verified" (body) diverges from "identity used" (header-derived shop) — exactly the class of binding break described in scope.

### Impact Explanation
This allows a verified, unprivileged tenant (any user who can install the app on their own store) to inject attacker-controlled webhook data attributed to another tenant's shop domain into the host application, as long as the host application trusts `WebhookMetadata#shop` (which the SDK explicitly derives from the unauthenticated header and exposes to the handler as the authoritative identity) to select the tenant/session context for processing that payload. This is a cross-tenant data-integrity/identity break enabled purely by this gem's HMAC-validation surface not covering the header it treats as the trust anchor for tenant attribution.

### Likelihood Explanation
Exploitability requires only: (1) installing the target app on an attacker-controlled shop through the ordinary, public OAuth flow, and (2) the ability to register or receive a webhook delivery to a server the attacker controls with a body of their choosing (Shopify allows dynamic callback addresses for Admin API-registered webhook subscriptions independent of this SDK). No secret, privileged account, or interception is required — this fits squarely into the "unprivileged internet user" threat model.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) header values into the HMAC-signable string in `Webhooks::Request#to_signable_string`, or otherwise require the host application to independently authenticate the tenant (e.g., cross-check `request.shop` against a shop known to have a currently registered subscription for that specific `webhook_id`) rather than trusting the header value alone once body-HMAC validation passes.

### Proof of Concept
1. As shop A (attacker, install app normally via OAuth), use the granted access token to call Shopify's Admin GraphQL `webhookSubscriptionCreate` with `callbackUrl` pointing to a server the attacker controls.
2. Trigger an event on shop A (e.g., create an order) so Shopify delivers a webhook to the attacker's server with a legitimate `X-Shopify-Hmac-Sha256` computed over the raw body using the app's real `api_secret_key`.
3. Capture `(raw_body, hmac_header)`.
4. Replay the identical `raw_body` and `hmac_header` to the victim app's actual webhook endpoint, but replace `X-Shopify-Shop-Domain` with shop B's domain.
5. `ShopifyAPI::Webhooks::Registry.process` (via `Utils::HmacValidator.validate`) accepts the request because only the body is verified, and the handler receives `WebhookMetadata` with `shop == "shop-B.myshopify.com"` despite the payload originating from shop A.
