### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator.validate` checks is computed only over the raw request body, not the headers. This breaks the intended binding `authenticated_shop == shop_used_by_handler`, letting anyone who possesses one valid `(raw_body, hmac)` pair replay it to the app's webhook endpoint with an arbitrary `shop-domain` header value and have it accepted as authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
`hmac` reads the `hmac-sha256` header and `shop` reads the `shop-domain` header separately, while [2](#0-1) 
`to_signable_string` returns only `@raw_body` — the `shop-domain` header value is never part of the signed content.

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` (the raw body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` trusts this validation and then constructs the `WebhookMetadata` handed to the app's handler directly from `request.shop`, i.e. the unauthenticated header: [4](#0-3) 

Because the signature only binds `raw_body` to the app's secret, and `shop` is read from a header that is completely outside that signed content, the equality the code implicitly assumes — `hmac_valid_for(shop, body) == hmac_valid_for(body)` — does not hold. Anyone able to obtain one genuine `(raw_body, hmac)` pair (e.g., by installing the app on their own store and triggering a webhook for a topic that has no shop-specific secret content in the body, or that has a body identical/predictable across shops) can resend that exact body+hmac to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` will still return `true` because it never inspected the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity-binding break: the shop identity attached to webhook data is not part of the cryptographically authenticated content. A host application that uses `WebhookMetadata#shop` to select which tenant's session/data store to update (the exact pattern the gem's own docs and tests encourage, e.g. `assert_equal(@shop, data.shop)`) can be tricked into applying a legitimately-signed payload to the wrong shop's record, which is a cross-tenant access vector per the rules (Critical impact category).

### Likelihood Explanation
Exploitation requires the attacker to obtain one authentic `(raw_body, hmac)` pair. This is achievable without any Shopify-side credentials or privileged access to the target: an attacker can install the app on a store they control (many mandatory topics such as `shop/redact`, `customers/redact`, `customers/data_request` are sent automatically and to some extent have attacker-influenced/predictable bodies), capture the resulting HMAC-signed webhook, and replay it with a forged `shop-domain` header against the app's public webhook endpoint. No `api_secret_key`, access token, or victim credential is required — only the ability to sign up as any merchant/developer, which is standard, low-privilege access to the Shopify platform, not a "privileged account" in the sense excluded by the rules.

### Recommendation
Bind the shop identity into the signed content instead of trusting a separate header. Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value inside `to_signable_string`, or otherwise compute/verify the HMAC over the full set of Shopify-controlled identifying headers plus body, so an attacker cannot swap the shop after the fact while keeping a valid signature. At minimum, document prominently that `shop` must be treated as validated only in conjunction with an out-of-band mapping from webhook subscription id to shop, and never trusted as an authenticated field on its own.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers (or waits for) a webhook whose body content is attacker-controlled or shop-agnostic (e.g. a mandatory `customers/data_request` webhook, or any topic whose JSON body doesn't itself embed the shop domain).
2. Shopify sends the webhook to the app's registered endpoint with headers `X-Shopify-Hmac-Sha256: <hmac>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, and the raw JSON body.
3. Attacker replays the identical HTTP request to the same endpoint but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`, leaving `raw_body` and `X-Shopify-Hmac-Sha256` untouched.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` only and matches — validation succeeds.
5. `Registry.process` invokes the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, even though Shopify never sent this webhook for `victim-shop`.
