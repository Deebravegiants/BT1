### Title
Webhook `shop` identity is taken from an unauthenticated HTTP header, not the HMAC-signed payload, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity solely against `@raw_body` via HMAC, while the `shop` (and `topic`, `api_version`, `webhook_id`) values that are handed to the app's webhook handler are read straight from HTTP headers that are never included in the signed material. This breaks the identity binding `hmac_signed_bytes == bytes_that_determine_shop_identity`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook exclusively with: [1](#0-0) 

`Utils::HmacValidator.validate` in turn calls `to_signable_string`, which for `Webhooks::Request` is defined as only the raw body: [2](#0-1) 

However, the `shop` value that is subsequently passed to the merchant's webhook handler as the tenant identifier is read from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is not part of the signed string at all: [3](#0-2) 

That unauthenticated `shop` value flows directly into `WebhookMetadata`, which is the struct the app's handler code uses to know which tenant the event belongs to: [4](#0-3) [5](#0-4) 

The equality that should hold is: `bytes verified by HMAC == bytes used to establish the shop identity acted on`. Here, `hmac(raw_body)` is checked, but `shop` is sourced from a header outside that HMAC scope. Because the HMAC in Shopify's webhook scheme is computed only over the request body (this is Shopify's documented format, not something this gem controls), an app instance that owns one authenticated shop (e.g., a malicious merchant who installed the app on their own store) can capture one of their own legitimately-signed webhook deliveries (valid `raw_body` + valid `hmac-sha256`) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header altered to any other shop domain the app services. `HmacValidator.validate` still returns `true` because it only checks the untouched body/hmac pair, and `Registry.process` will happily hand the handler a `WebhookMetadata` claiming the event is for the victim shop.

### Impact Explanation
This is a cross-tenant identity spoofing primitive: an app's webhook handler will act on attacker-supplied `shop`, `topic`, `webhook_id`, and `api_version` values believing they are authenticated by Shopify, since HMAC validation succeeded. Any app whose handler logic branches on `shop` (e.g., to update per-tenant state, mark a shop as uninstalled via `app/uninstalled`, gate feature flags, or write to tenant-scoped storage) can be tricked into applying another shop's state transition using data an attacker fully controls the "shop" association for. This matches the "cross-tenant access" criterion.

### Likelihood Explanation
Requires only that the attacker control at least one legitimate shop install of the target app (or otherwise obtain one valid signed webhook payload/HMAC pair for any topic present on the target app) and be able to POST arbitrary headers to the app's public webhook endpoint — both are standard unprivileged-internet-user capabilities once an app is public on the Shopify App Store. No access to `api_secret_key`, tokens, or Shopify infrastructure is required, since the header is never bound by the signature at all.

### Recommendation
Do not trust the `x-shopify-shop-domain` (or any other Shopify header) as an identity source unless it is cryptographically bound to the payload. Concrete options:
- Include the shop domain (and topic/webhook id) in the HMAC-signable string, i.e., extend `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to combine `raw_body` with the header values that are later trusted, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop`, `host`, `code`, etc. before HMAC verification (`lib/shopify_api/auth/oauth/auth_query.rb`).
- Alternatively, document/require host applications to cross-check the header `shop` against a shop-scoped webhook secret or registered shop list before trusting it, and add a runtime check in `Registry.process` rejecting shops not previously known/authorized to the app.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and legitimately receives a real webhook delivery for topic `orders/create` with headers:
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-hmac-sha256: <valid hmac of raw_body>`
   - `x-shopify-topic: orders/create`
   - body: `{"id":123, ...}` (attacker's own data, freely shaped by attacker as their own store's order)
2. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint but changes the header to:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this normally (`lib/shopify_api/webhooks/request.rb:45-63`), `Utils::HmacValidator.validate(request)` succeeds because it only hashes `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`), and `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`) — the app now processes attacker-controlled data under the victim shop's identity.
