### Title
Cross-function signed-message replay in `pallet-ismp-relayer` lets an attacker front-run a relayer's fee redirect/withdrawal authorization - (File: `modules/pallets/relayer/src/accumulate.rs`, `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
The Lido incident stemmed from a whitelisted operator being able to exploit an under-scoped verification path to redirect funds intended for someone else. `pallet-ismp-relayer` has an analogous scoping failure: two independent, fund-moving entry points — `Pallet::withdraw` (in `withdrawal.rs`) and the beneficiary-redirect branch of `Pallet::accumulate` (in `accumulate.rs`) — build their signed authorization message with the *exact same byte encoding* and validate it against the *same* `Nonce` counter, with no domain separator distinguishing which function the signature was meant for.

### Finding Description
`withdrawal.rs::message()` computes:
```rust
sp_io::hashing::keccak_256(&(nonce, dest_chain, beneficiary).encode())
``` [1](#0-0) 

`accumulate.rs::beneficiary_message()` computes:
```rust
sp_io::hashing::keccak_256(&(nonce, state_machine, beneficiary).encode())
``` [2](#0-1) 

Both take a `(u64, StateMachine, beneficiary-bytes)` tuple and SCALE-encode it identically, so for the same `(nonce, chain, beneficiary)` triple the two functions hash to the *same 32 bytes* — a signature valid for one is a valid signature for the other. Both functions also draw from the same `Nonce` storage map keyed by `(address, state_machine)`:

- `withdraw()` reads/increments `Nonce::<T>::get(address.clone(), withdrawal_data.dest_chain)` [3](#0-2)  and [4](#0-3) 
- `accumulate()` reads/increments `Nonce::<T>::get(&delivery_address, state_machine)` for the beneficiary redirect [5](#0-4) 

There is no tag/prefix in either payload identifying "this signature authorizes a `withdraw` call" versus "this signature authorizes an `accumulate` beneficiary redirect." Both `withdraw` and `accumulate` are dispatched as **unsigned extrinsics** (per the module docs, `withdraw`'s extrinsic "is unsigned and will not require any native tokens for execution fees" [6](#0-5) ), meaning a relayer's signed payload is broadcast in plaintext through the public transaction pool before inclusion. Any unprivileged party observing that pool can extract the `(signature, nonce, beneficiary)` tuple and resubmit it to the *other* function ahead of the relayer's own transaction.

Because the nonce is shared, whichever call lands first consumes it; the honest relayer's follow-up call recomputes the message with the now-advanced nonce and its signature no longer matches, so the second call fails outright — the relayer's original intended state transition (either the redirect in `accumulate` or the withdrawal in `withdraw`) is silently dropped/reverted rather than applied as intended, while the front-run call **executes the wrong operation with the attacker's chosen timing and batch pairing**. In `withdraw`'s case this triggers an immediate cross-chain POST dispatch instructing `HostManager`/`HYPERBRIDGE_MODULE_ID` to disburse `available_amount` [7](#0-6)  — an unauthorized-timing trigger of a real fund-moving message, using a signature the relayer never intended for that call.

### Impact Explanation
This is a genuine "unauthorized app action" / message-authorization-forging class bug reachable by any unprivileged observer of the transaction pool (an unprivileged relayer/dispatcher path, matching the allowed threat surface). While the *beneficiary* named in the replayed signature is still the one the relayer chose (limiting straightforward third-party theft), the vulnerability lets an outsider:
- Force a mismatched `(commitments, beneficiary)` pairing between `accumulate`'s freshly-proven fee batch and `withdraw`'s already-accumulated balance, causing relayer fee credits/withdrawals to be dispatched at attacker-chosen moments rather than under the relayer's control.
- Cause the relayer's genuine, intended call to revert due to nonce mismatch, effectively freezing/griefing that specific fee-crediting operation until the relayer re-signs — a denial-of-service on relayer fee accounting that can be repeated indefinitely by monitoring the mempool.
- Because `accumulate`'s failure path returns an `Err` before any `RequestCommitments` are marked `claimed` [8](#0-7) , a griefed accumulate attempt costs the relayer wasted proof-submission effort and delays fee accrual, which for the built-in delivery-race incentive model is a direct value impact on relayers' fee accounting — matching the medium-severity, no-direct-loss but fund-flow-integrity nature of the Lido report.

### Likelihood Explanation
Both `withdraw` and `accumulate` are unsigned extrinsics whose payloads (including the relayer's signature) are visible in the public transaction pool before inclusion, so front-running requires no privileged access — only mempool monitoring, which is standard for any relayer/MEV-style actor. The only additional requirement to redirect `accumulate`'s larger fee batches is possessing a valid `WithdrawalProof` for other undelivered commitments from the same relayer, which is also publicly derivable from chain state (state proofs are, by design, "freely provided by connected chains" per the relayer documentation). This makes exploitation feasible for any party racing transactions against relayers, which is a routine, low-cost activity.

### Recommendation
Add a distinct domain separator (e.g., a leading discriminant byte/string like `b"WITHDRAW"` vs `b"ACCUMULATE-BENEFICIARY"`) to the encoded tuple in both `message()` (`modules/pallets/relayer/src/withdrawal.rs`) and `beneficiary_message()` (`modules/pallets/relayer/src/accumulate.rs`) before hashing, so a signature produced for one function can never verify against the other, even when nonce, chain, and beneficiary values coincide. Consider also using independent nonce counters (or a single counter with the domain tag folded into the nonce derivation) so that consuming a nonce in one function cannot invalidate an unrelated in-flight signature intended for the other.

### Proof of Concept
1. Relayer R accrues fees for delivering messages to chain `C` and wants to redirect them to beneficiary `B` via `accumulate`'s beneficiary-redirect path. It builds and signs `beneficiary_message(nonce=N, C, B)` and submits an unsigned `accumulate(withdrawal_proof)` extrinsic containing `(B, sig)` in `beneficiary_details`.
2. Attacker A observes this extrinsic in the pool, extracts `(sig, N, C, B)`, and constructs a `WithdrawalInputData { signature: sig, dest_chain: C, beneficiary: Some(B) }` for `Pallet::withdraw`, since `withdrawal.rs::message(N, C, Some(B))` hashes identically to `accumulate.rs::beneficiary_message(N, C, B)` [1](#0-0) [2](#0-1) .
3. A submits `withdraw` first with a higher priority/fee; it passes signature verification (`eth_address == address` / sr25519/ed25519 checks) [9](#0-8) , consumes nonce `N`, and immediately dispatches a POST request moving `available_amount` (R's currently accumulated `Fees[C][R]`) to `B` [7](#0-6) .
4. R's original `accumulate` extrinsic then executes against nonce `N+1`; its stored signature no longer matches the recomputed `beneficiary_message(N+1, C, B)`, so `Error::<T>::InvalidSignature`/`InvalidPublicKey` is returned and the entire `accumulate` call (including marking commitments `claimed`) fails [10](#0-9) , silently discarding R's intended fee-batch crediting and forcing a re-proof.

This chain is reproducible purely from public mempool data and existing pallet logic; I was not able to run it end-to-end in this environment, but the message-hash equivalence and shared `Nonce` storage are directly confirmed from the cited source.
