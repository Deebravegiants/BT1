### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates only the JSON body of an incoming webhook via HMAC, but attributes the event to a shop taken from an unauthenticated HTTP header. The `shop` value handed to app handlers is therefore not bound to the cryptographic proof that "the request did indeed come from Shopify" for that shop, breaking the identity binding `authenticated_body == authenticated_shop`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`hmac` and `shop` are both read from independent HTTP headers with no cryptographic linkage between them: [2](#0-1) 

`Utils::HmacValidator.validate` computes/compares the signature only over `to_signable_string` (i.e., the raw body), never incorporating `shop`: [3](#0-2) 

`Registry.process` validates that HMAC and then forwards `request.shop` straight into `WebhookMetadata` for the handler, treating it as trusted tenant-identifying data: [4](#0-3) 

The gem's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify," implying the whole payload including shop attribution is authenticated: [5](#0-4) 

In reality, the HMAC only proves that whoever holds the app's `client_secret` produced this exact body — it says nothing about which shop the body is "for." Since the `x-shopify-shop-domain` / `shopify-shop-domain` header is excluded from the signed content, any holder of one valid `(body, hmac)` pair can replay it with an arbitrary `shop` header value and the signature will still validate.

This is the same bug class as the referenced report: a field that downstream logic treats as authoritative (`token()`/`shop`) is read from a location/channel that the integrity check does not actually cover (`calldataload` offset / HMAC signable string), so the two "should be equal but aren't" — here, `verified_body == verified_shop` does not hold; only `verified_body` holds.

### Impact Explanation
An unprivileged internet user who can install the target app on any shop (e.g., a free/dev store, which requires no privileged credentials) will legitimately receive genuine Shopify webhooks — each with a valid HMAC computed over the body using the app's `client_secret`, which the attacker never needs to know or steal. By capturing one such `(raw_body, hmac)` pair and replaying it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop, the attacker forces the app's webhook handler to process attacker-supplied event data under the identity of a different, unrelated merchant. Because handlers commonly key persistence, billing, or business logic by `data.shop` (as shown in the gem's own documented usage example), this enables cross-tenant data injection/confusion — matching the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Likelihood is High for any app that (a) allows self-serve installs (dev stores, trial shops — trivial for any internet user to obtain) and (b) uses `data.shop` from `WebhookMetadata` to key business logic, which is exactly the pattern the gem's documentation recommends. No secret, token, or privileged account is required — only the ability to install the app once on an attacker-controlled shop to harvest one valid signed webhook body.

### Recommendation
Bind the shop identity into the authenticated content, e.g., include the `shop-domain` (and ideally `topic`, `webhook-id`) header value in the HMAC signable string (matching Shopify's actual signing scope), or independently verify that the shop asserted in the header matches a shop with an active, previously-established session/registration before dispatching to handlers. At minimum, document clearly that `Registry.process` does not authenticate the `shop` field, so integrators do not treat it as trusted.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` (any free/dev store).
2. Trigger any subscribed event (e.g., `orders/create`) and capture the legitimate webhook POST: raw body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's secret).
3. Replay the request to the same app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `H` against `B`: [6](#0-5) 
5. `Registry.process` invokes the handler with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"` even though the body actually originated from `attacker-shop.myshopify.com`, demonstrating forged cross-tenant attribution.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
