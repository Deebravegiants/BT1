### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header not covered by HMAC allows shop-identity spoofing in `ShopifyAPI::Webhooks::Request` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers [2](#0-1) . `Registry.process` only validates the HMAC over the body and then forwards `request.shop` unmodified to the app's handler as the trusted shop identity [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`HMAC-verified bytes == bytes the app treats as the authenticated tenant (shop)`

Here that equality is broken: `HmacValidator.validate` calls `verifiable_query.to_signable_string`, which for a webhook `Request` is literally `@raw_body` only [1](#0-0) . The `shop-domain`, `topic`, `webhook-id`, and `api-version` values come from HTTP headers that are never mixed into the signed string [4](#0-3) . `Utils::HmacValidator.validate` computes and compares the HMAC purely against this body-only string [5](#0-4) .

`Registry.process` treats a passing HMAC check as proof the entire request (including headers) is authentic, and hands `request.shop` directly to the registered handler as `WebhookMetadata#shop` — the field the docs explicitly tell integrators to use to attribute the webhook to a shop/tenant [3](#0-2) [6](#0-5) .

Since only the body is HMAC-covered, any HTTP request with a body that legitimately came from Shopify (with a valid, previously-captured or self-generated HMAC over that exact body) can be replayed to the app's webhook endpoint with an arbitrary, attacker-chosen `x-shopify-shop-domain` header. The HMAC check still passes because it never examined the header, so `Registry.process` will call the app's handler claiming the payload belongs to whatever shop the attacker put in the header [7](#0-6) .

This matches the "field acted on but not covered by the HMAC" pattern: the `shop` field is acted upon (used as the tenant identifier passed to the app) but is not part of the cryptographically verified data.

### Impact Explanation
An unprivileged internet user who can obtain any single genuinely-signed webhook body/HMAC pair for a given topic (e.g., by installing a free/dev app on their own store and receiving a legitimate webhook with a predictable/empty/re-usable body, such as `app/uninstalled`, `shop/redact`, or any topic with an empty or attacker-controlled body) can replay that request to a target app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for any other merchant's domain. Because `HmacValidator` never binds the header to the signature, the forged request is accepted as authentic and routed to the handler as if it came from the victim shop. Depending on how the host application acts on `data.shop` (e.g., triggering `shop/redact`/GDPR flows, marking an app as uninstalled, updating billing/session state, or writing merchant-scoped data), this can produce cross-tenant data corruption, false uninstall/redact triggers, or tenant impersonation for a completely different merchant — a cross-tenant identity confusion enabled directly by this gem's webhook verification logic.

### Likelihood Explanation
Webhook HTTP endpoints are public by design (Shopify must be able to POST to them from the internet), so no privileged access, TLS interception, or secret material is required. The attacker only needs one legitimate signed payload for a topic whose body is static, predictable, or attacker-influenced (many mandatory/compliance topics and several resource topics have small/fixed or attacker-obtainable bodies), then can freely vary the `shop-domain` header on replay. The library provides no header-binding, no timestamp/replay protection tied to the header set, and no warning in the docs that `shop` is unauthenticated relative to the HMAC.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the request (e.g., concatenate them with the body before computing/verifying the digest in `to_signable_string`), so that any header tampering invalidates the signature. At minimum, `shop` must be covered, since it is the field the whole webhook processing pipeline trusts for tenant attribution.

### Proof of Concept
1. Attacker installs the target app (or a similar app using this gem) on their own store and triggers a webhook with a static/empty/attacker-influenced body (e.g., `{}` for many topics, or a topic whose payload they control), capturing the raw `raw_body` and the `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker sends a forged HTTP POST to the target app's public webhook endpoint with:
   - the exact same `raw_body` (so the HMAC computed by `HmacValidator.validate` over `to_signable_string` == `@raw_body` still matches),
   - the original valid `x-shopify-hmac-sha256` value,
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (arbitrary, attacker-chosen),
   - `x-shopify-topic` set to the topic registered by the app.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `@raw_body` against the HMAC [8](#0-7) [9](#0-8) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(..., shop: request.shop, ...)` where `request.shop == "victim-shop.myshopify.com"`, even though that value was never authenticated [10](#0-9) .
