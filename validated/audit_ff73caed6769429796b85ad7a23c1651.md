## Analog Found

### Title
Permissionless `Initialize2` pool creation can be front-run to set an attacker-controlled initial price ratio - ([File: program/src/processor.rs])

### Summary
`process_initialize2` allows any signer to create the AMM pool for a given Serum/OpenBook `market` account, supplying arbitrary `init_pc_amount`/`init_coin_amount` values that fix the pool's *initial* price and initial LP token distribution. The AMM, vault, and target-orders accounts are all deterministically derived only from the `market` pubkey, so an attacker who observes a pending `Initialize2` transaction in the mempool can front-run it with the same market/mint accounts but self-chosen amounts and become the pool's first (and price-setting) liquidity provider.

### Finding Description
`AmmInstruction::Initialize2` has no caller restriction (it is meant to be permissionless, similar to a "public initializer") and takes `init_pc_amount`/`init_coin_amount` directly from instruction data supplied by whoever submits the transaction: [1](#0-0) 

In `process_initialize2`, the AMM/target-orders/vault/lp-mint accounts are derived solely from the `market_info.key` via `get_associated_address_and_bump_seed`, and creation is only rejected if these accounts are *already* owned by something other than the system program: [2](#0-1) [3](#0-2) 

There is no check that `init_pc_amount`/`init_coin_amount` reflect a fair market price (no comparison against the market order book, no config-supplied bounds, no minimum/maximum ratio). The only guard is that the resulting geometric-mean liquidity must exceed `10^lp_decimals`: [4](#0-3) 

The caller (`user_wallet_info`, required only to be a signer) is credited with the resulting `user_lp_amount` and effectively sets `amm.status`/initial reserves for the pool: [5](#0-4) 

Because the AMM address depends only on the `market` pubkey (not on the caller or on the initial amounts), an attacker monitoring the mempool for a legitimate creator's `Initialize2` transaction (same `market`/mint pair) can submit their own `Initialize2` with the same accounts but a heavily skewed `init_coin_amount`/`init_pc_amount` ratio and a higher priority fee, landing first. Once the attacker's transaction executes, the AMM/vault/target-orders accounts are no longer system-owned, so the legitimate creator's subsequent transaction fails with `AmmError::RepeatCreateAmm`: [6](#0-5) [7](#0-6) 

The attacker is now the pool's initial LP holder at a price ratio of their choosing, with no protocol-level check that it matches the real market price.

### Impact Explanation
The attacker can set an arbitrarily mispriced pool (e.g., 1 unit of an expensive token against a large amount of a cheap token) while satisfying only the minimal liquidity floor. Subsequent swappers or depositors who interact with the pool assuming a fair price (matching the intended creator's amounts) suffer immediate loss: swaps execute at the attacker's chosen ratio, and any `Deposit` must conform to that skewed ratio, letting the attacker profit as sole/majority initial LP through subsequent trading/arbitrage against the mispriced vault. This is a direct extraction of value from the legitimate market participants and results in an initial-state insolvency/mispricing of the pool relative to its intended launch parameters — satisfying "concrete theft ... of user or LP funds" via price manipulation.

### Likelihood Explanation
Any user can construct and submit an `Initialize2` transaction for a public `market`/mint pair once they observe a pending creation transaction, since the required accounts (`market`, mints, fee destination, config) are all public and derivable, and only a signer wallet with sufficient SOL/tokens for the fee/minimum liquidity is needed. This requires no privileged role, no off-chain assumptions, and is directly reachable from a single submitted transaction with attacker-chosen `init_pc_amount`/`init_coin_amount`, matching the exploitability pattern described in the reference report (front-runnable initializer with attacker-chosen values).

### Recommendation
Bind the initial price to a verifiable reference (e.g., require the initial ratio to be within a bound derived from the OpenBook/Serum market's best bid/ask, or require the pool creator to pre-commit the AMM account and initial ratio in a separate transaction/PDA seeded by the creator's pubkey so it cannot be hijacked), and/or allow the intended creator to specify a minimum acceptable LP amount/price bound so a front-run with different amounts fails instead of silently succeeding with attacker-chosen values.

### Proof of Concept
1. Legitimate user builds and broadcasts an `Initialize2` transaction for `market M`, `coin mint A`, `pc mint B`, with `init_coin_amount` and `init_pc_amount` reflecting the fair market price.
2. Attacker observes the pending transaction (mempool/gossip), and submits their own `Initialize2` for the same `market M`/mint pair but with a skewed `init_coin_amount`/`init_pc_amount` (satisfying only the `liquidity > 10^lp_decimals` check in `process_initialize2`, lines 908-917 above), using a higher priority fee to land first.
3. Attacker's transaction succeeds: `generate_amm_associated_account`/`generate_amm_associated_spl_token` create the AMM/vault accounts (lines 307-317, 378-382 above) at the market-derived address, mint `user_lp_amount` LP tokens to the attacker, and set `amm.status`.
4. The legitimate user's transaction now fails with `AmmError::RepeatCreateAmm` since the accounts are no longer system-owned.
5. The pool is live with the attacker as majority/sole LP at an arbitrary price ratio; the attacker can immediately swap or wait for the (uninformed) legitimate user/other traders to interact with the pool at the wrong price, extracting value.
