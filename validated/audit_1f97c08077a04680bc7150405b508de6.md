### Title
Griefing via unauthorized gas-key balance inflation blocks `DeleteKey`/`DeleteAccount` — hardcoded burn-threshold check on an attacker-fundable balance ([File: runtime/runtime/src/access_keys.rs], [File: runtime/runtime/src/actions.rs])

### Summary
The `UniswapHandler.addLiquidity` bug class is: a contract action makes a hard, unconditional assumption about a balance value (and checks it against a fixed threshold), while that balance can be topped up by an unprivileged, unrelated third party — letting an attacker push the value past the hardcoded bound and cause the legitimate operation to revert. The nearcore analog is `GasKeyInfo::MAX_BALANCE_TO_BURN`: gas-key deletion and account deletion both hard-fail if a gas key's `balance` exceeds this fixed constant, and that balance can be topped up via `TransferToGasKeyAction`, a deposit-style action with no apparent requirement that the caller be the account owner.

### Finding Description
`delete_gas_key` refuses to delete a gas key whose `balance` exceeds `GasKeyInfo::MAX_BALANCE_TO_BURN`, returning `ActionErrorKind::GasKeyBalanceTooHigh` instead of completing the deletion: [1](#0-0) 

The same hardcoded threshold is applied at account-deletion time against the *sum* of all gas-key balances on the account: [2](#0-1) 

Crucially, the balance being checked is attacker-fundable: `action_transfer_to_gas_key` adds `action.deposit` to an existing gas key's balance purely by public key, with no check that the caller (`predecessor_id`/signer) is the account that owns the key: [3](#0-2) 

This mirrors the reported bug class exactly: a fixed percentage/threshold check (`95%` balance ratio in the Uniswap report vs. `MAX_BALANCE_TO_BURN` here) is evaluated against a balance an outside party can manipulate by simply sending funds, and the manipulation causes the intended operation (`addLiquidity` there, `DeleteKey`/`DeleteAccount` here) to permanently revert.

### Impact Explanation
If `TransferToGasKeyAction` can indeed target a gas key on an account the caller does not control (this action is a deposit-style action analogous to `Transfer`, and the function itself performs no ownership check), an attacker can:
1. Send a `TransferToGasKeyAction` depositing an amount just over `MAX_BALANCE_TO_BURN` into a victim's gas key.
2. This permanently blocks the victim from deleting that specific key via `DeleteKey` (`GasKeyBalanceTooHigh`).
3. Because `action_delete_account` sums *all* gas-key balances on the account and applies the same threshold (`runtime/runtime/src/actions.rs:354-363`), the same attack against any single gas key can permanently block account deletion for the whole account — a denial-of-service on account lifecycle operations, analogous to the griefing-via-revert described in the report.

### Likelihood Explanation
The action is reachable from a normal signed transaction/receipt (no validator or node-level privilege required), and the cost to the attacker is just the yoctoNEAR/NEAR amount deposited (which is burnt on deletion, but bounded — an attacker only needs to exceed `MAX_BALANCE_TO_BURN` by 1 yoctoNEAR to trigger the block). This makes the griefing cheap and repeatable against any account that exposes a gas key public key (gas keys are, by design, meant to be fundable by third-party relayers, which is what makes this reachable).

### Recommendation
- Verify/enforce that `TransferToGasKeyAction` cannot be used to grief unrelated accounts: either require an explicit "topped-up-by-owner-consent" model, or decouple the DoS by not hard-failing deletion when funded balance exceeds the burn cap — e.g., refund/burn any excess above `MAX_BALANCE_TO_BURN` instead of rejecting the whole `DeleteKey`/`DeleteAccount` action.
- At minimum, cap how much an external `TransferToGasKeyAction` can add in a single call, or allow `DeleteKey`/`DeleteAccount` to proceed by burning the balance in excess of `MAX_BALANCE_TO_BURN` (or refunding it to a beneficiary) rather than failing outright.

### Proof of Concept
1. Account `V` has a gas key `pk_gk` with balance `0`.
2. Attacker `A` submits a transaction/receipt containing `Action::TransferToGasKey(TransferToGasKeyAction { public_key: pk_gk, deposit: MAX_BALANCE_TO_BURN + 1 })` targeting `V`'s account — accepted by `action_transfer_to_gas_key` with no ownership check (`runtime/runtime/src/access_keys.rs:257-288`).
3. `V` later submits `DeleteKey(pk_gk)`: `delete_gas_key` now returns `GasKeyBalanceTooHigh` and the key can never be deleted (`runtime/runtime/src/access_keys.rs:103-111`).
4. `V` attempts `DeleteAccount`: `compute_gas_key_balance_sum` includes the inflated balance, exceeding `MAX_BALANCE_TO_BURN`, and `action_delete_account` fails with `GasKeyBalanceTooHigh`, permanently blocking account deletion (`runtime/runtime/src/actions.rs:354-363`).

Note: I was unable to fully trace `action_validation.rs`'s permission rules for `TransferToGasKeyAction` within the available tool budget to conclusively confirm it is entirely permissionless against an arbitrary receiver account (as opposed to being restricted the way `AddKey`/`DeleteKey`/`Stake` typically are to `receiver_id == signer_id`). This is the one open verification point for confirming full exploitability; the threshold-vs-attacker-fundable-balance root cause itself is confirmed in code.

pub(crate) fn action_transfer_to_gas_key(
    state_update: &mut TrieUpdate,
    result: &mut ActionResult,
    account_id: &AccountId,
    action: &TransferToGasKeyAction,
) -> Result<(), RuntimeError> {
    let Some(mut access_key) = get_access_key(state_update, account_id, &action.public_key)? else {
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };
    let Some(gas_key_info) = access_key.gas_key_info_mut() else {
        // Key exists but is not a gas key
        result.result = Err(ActionErrorKind::GasKeyDoesNotExist {
            account_id: account_id.clone(),
            public_key: Box::new(action.public_key.clone()),
        }
        .into());
        return Ok(());
    };

    gas_key_info.balance = gas_key_info.balance.checked_add(action.deposit).ok_or_else(|| {
        RuntimeError::StorageError(StorageError::StorageInconsistentState(
            "gas key balance integer overflow".to_string(),
        ))
    })?;
    set_access_key(state_update, account_id.clone(), action.public_key.clone(), &access_key);
    Ok(())
}
