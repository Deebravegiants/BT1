Missing L2 Sequencer Uptime Check in `SimplexPaymaster._getOraclePrice()` Enables Stale/Manipulated Gas Pricing During Sequencer Downtime - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using Chainlink `latestRoundData()` feeds and checks only price positivity and staleness against `maxOracleAge`, exactly the pattern flagged in the external report's `calculateArbAmount()`. Unlike the reference report's target, this contract is confirmed deployed on Arbitrum and Base (`docs/content/developers/evm/simplex/configuration.mdx:81`), both of which run a centralized sequencer whose outage can freeze/replay stale Chainlink answers on L2 without ever tripping the staleness check, since `updatedAt` on L2 aggregators reflects L1 forwarding time, not sequencer health.

### Finding Description
`_getOraclePrice()` fetches `latestRoundData()` from `nativeOracle` and each token's `tokenOracle`, validating only: [1](#0-0) 

It never queries an L2 sequencer-uptime feed (e.g., Chainlink's `0xFdB631F5EE196F0ed6FAa767959853A9F217697` on Arbitrum) to confirm the sequencer has been up for a grace period before trusting the price. This mirrors the exact root cause in the external report: an L2-deployed contract consuming `latestRoundData()` without a sequencer-liveness gate.

Because `_tokenPrice()` — called from the unprivileged, permissionless `_fetchDetails()`/`_prefund()` path that any UserOperation sender reaches — derives the gas-payment exchange rate purely from these two oracle reads: [2](#0-1) 

any submitter of a UserOperation using mode `0x00`/`0x02` paymasterData reaches this pricing logic directly: [3](#0-2) 

If the Arbitrum/Base sequencer goes down and later resumes, Chainlink price feeds on that L2 can report an outdated/incorrect `answer` while `updatedAt` still lags within `maxOracleAge` (up to 24h for Base/Ethereum stables, per the contract's own comment), so the price passes both checks despite the sequencer having been unavailable.

### Impact Explanation
An outdated exchange rate lets a UserOperation sender pay dramatically less (or more) stablecoin than the true gas cost — a favorable stale price effectively lets an attacker drain the paymaster's ERC-20/native reserves relative to actual gas spent, or lets the paymaster overcharge users, both of which are direct fund-safety issues for a contract explicitly built to hold and disburse value (deposit, stake, markup surplus) with "no privileged key" recovery. This matches Medium severity per the original report given it depends on an external sequencer-downtime precondition, but the blast radius here is broader because `SimplexPaymaster` is live across five chains including two sequencer-based L2s (Arbitrum, Base), not a single internal reward calculation.

### Likelihood Explanation
Likelihood is Medium: it requires an actual Arbitrum or Base sequencer outage/recovery window, an event that has occurred historically on these networks. During that narrow window, any unprivileged UserOp sender (not the treasury or governance) can trigger `_fetchDetails`/`_prefund` and get priced off the stale rate — no special privileges or governance approval needed to exploit it, only submitting a normal paymaster-sponsored UserOperation.

### Recommendation
Add an L2 sequencer-uptime-feed check (per Chainlink's documented pattern) inside `_getOraclePrice()` for each L2 deployment, reverting if the sequencer is down or the grace period since it came back up has not elapsed, mirroring the fix approach in the referenced report.

### Proof of Concept
1. Arbitrum/Base sequencer stalls; Chainlink `updatedAt` for `nativeOracle`/`tokenOracle` freezes at the last pre-outage value.
2. Market price moves materially away from the frozen `answer` during the outage.
3. Once the sequencer resumes (or even mid-outage if `answer` is still within `maxOracleAge`), any user submits a UserOperation with `paymasterData` mode `0x00`/`0x02` referencing a registered token.
4. `_fetchDetails` → `_tokenPrice` → `_getOraclePrice` accepts the stale, non-representative price because `block.timestamp - updatedAt <= maxOracleAge` and `answer > 0`, with no sequencer check performed anywhere in the file (confirmed via full-file search for `sequencer`/`Sequencer`/`Arbitrum` in `SimplexPaymaster.sol`, which returned no matches).
5. The UserOperation is sponsored/charged at the stale rate, allowing the sender to pay less token value than the true gas cost consumed, at the paymaster's expense.

```text
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);
```

```text
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
