### Title
Webhook `shop-domain` identity is trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary

### Finding Description
`ShopifyAPI::Webhooks::Request` derives the tenant identity used for webhook processing (`shop`) directly from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header [1](#0-0) , while the HMAC signature that `Registry.process` relies on to authenticate the request is computed only over the raw request body: [2](#0-1) 
`Registry.process` validates only this body-derived signature, then immediately trusts `request.shop` as the tenant key passed to the handler: [3](#0-2) 
`Utils::HmacValidator.validate` confirms `HMAC(secret, to_signable_string)`, i.e. `HMAC(secret, raw_body)` only — the `shop`, `topic`, and `webhook-id` headers are never part of the signed material: [4](#0-3) 

This breaks the identity binding: `shop authenticated by HMAC` ≠ `shop used as the tenant/session key by the handler`. The `client_secret`/`api_secret_key` used to sign webhooks is the app's single, shop-independent secret (the same secret Shopify uses for every shop that has the app installed), so *any* shop that has genuinely installed the app can obtain a validly-HMAC-signed webhook body for data it controls (e.g. by placing an order, updating a product, etc. in its own store, triggering Shopify to deliver a real, correctly-signed webhook to the app's endpoint). Because the `shop-domain` header is not part of the signed payload, that same `raw_body` + `hmac-sha256` pair can be replayed to the app's public webhook endpoint with an arbitrary `shop-domain` header value pointing at a victim shop. `Utils::HmacValidator.validate` still returns `true` (the body and signature are untouched), and `Registry.process` hands the handler a `WebhookMetadata` claiming the attacker-controlled body belongs to the victim shop [5](#0-4) .

### Impact Explanation
This is a cross-tenant access primitive: an attacker with a normal, unprivileged app installation on their own store can forge webhook deliveries that the host application will process as if they belong to a different, victim shop, since the library exposes no mechanism binding the authenticated bytes to the claimed shop. Any host application that uses `request.shop` (as documented/intended) to select per-tenant credentials, look up per-shop records, or update per-shop state is exposed to writing attacker-supplied data into, or acting under the identity of, an arbitrary shop merely by guessing/knowing its domain — no access token or `client_secret` value needs to be known or leaked by the attacker.

### Likelihood Explanation
Reaching this requires only: (1) an app installed on any store (a routine, unprivileged action available to anyone who can install a public/dev app), (2) capturing one genuinely delivered webhook (raw body + `hmac-sha256` header) for that store, and (3) POSTing it to the app's public webhook endpoint with a modified `shop-domain` header. No secret material, session, or elevated privilege is required beyond normal app installation, and the vulnerable code path (`Webhooks::Request#shop`, `Registry.process`) is exactly the one this gem instructs implementers to rely on for identifying which shop a webhook belongs to.

### Recommendation
Do not derive the trusted tenant identity solely from the `shop-domain` header. Either:
- Include the shop domain in the HMAC-signed material used for verification (matching it against the value returned from `AccountOwnerActor`/session storage), or
- Require host applications to independently verify that `request.shop` corresponds to a shop with an active, previously-persisted session/access token for this app before processing the payload, and clearly document that `Webhooks::Request#shop` is unauthenticated header data, not a value covered by the HMAC in `to_signable_string`.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker-shop.myshopify.com` (normal, unprivileged installation).
2. Trigger any subscribed webhook topic (e.g. `products/update`) by modifying a resource in `attacker-shop.myshopify.com`. Shopify delivers a webhook to the app's endpoint with a body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)` — this signature is valid because `Utils::HmacValidator.validate` only checks `HMAC(secret, raw_body)`: [6](#0-5) 
3. Capture this exact request (raw body `B` and `hmac-sha256` header untouched).
4. Replay the identical body/HMAC to the same app endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Webhooks::Request.new` parses `shop` from this attacker-supplied header [7](#0-6) ; `Registry.process` validates the (unchanged) HMAC successfully and dispatches `WebhookMetadata.new(topic:, shop: request.shop, body: request.parsed_body, ...)` to the app's handler with `shop = "victim-shop.myshopify.com"` [8](#0-7) , causing attacker-controlled data to be processed under the victim shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
