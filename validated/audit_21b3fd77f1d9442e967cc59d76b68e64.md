### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while `Registry.process` dispatches to the app's webhook handler using the `shop` value read straight from the unauthenticated `shop-domain` (or `x-shopify-shop-domain`) header. Because the app's webhook signing secret (`Context.api_secret_key`) is shared across every shop that has installed the app, any merchant who has installed the app can capture a genuinely-signed `(raw_body, hmac)` pair from their own store's webhooks and replay it to the app's webhook endpoint with a forged `shop-domain` header, causing the handler to process attacker-controlled data under a victim shop's identity.

### Finding Description
`Utils::HmacValidator.validate` verifies the signature by computing `HMAC(secret, verifiable_query.to_signable_string)` and comparing it to the received HMAC: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from HTTP headers and are never part of the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.shop` (and the other header-derived fields) to build the `WebhookMetadata` passed into the app's handler: [4](#0-3) 

This breaks the intended binding `authenticated_shop == handler_dispatch_shop`. In practice the equality that should hold is:
`HMAC-covered content == identity used for tenant dispatch`

but here:
`HMAC-covered content (raw_body only) != identity used for tenant dispatch (shop header)`

Since the webhook secret is the app-level `client_secret` (identical for all shops using the app, not a per-shop secret), any shop that has legitimately installed the app can:
1. Trigger a webhook to be delivered to the app for their own store (e.g. by creating an order, updating a product, etc.), receiving a valid `(raw_body, hmac)` pair signed with the app's shared secret.
2. Replay that exact `raw_body`/`hmac` to the app's webhook endpoint, but substitute the `shop-domain` (or `x-shopify-shop-domain`) header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds (it only checks `raw_body` against `hmac`), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

Any host application that uses `request.shop`/`data.shop` (as the sample handler in this gem's own test suite does) as the tenant key to look up a session, update records, or authorize an action for "the shop the webhook is about" is fully exposed to this spoofing, because the gem provides no mechanism binding the header-derived shop to the signed payload.

### Impact Explanation
This crosses a tenant boundary: an attacker who is a legitimate (but malicious) installer of the app can make the app process a webhook body as if it belonged to an arbitrary victim merchant, because the only cryptographically-verified artifact (the raw body) carries no shop binding, while the value used for tenant dispatch is taken from an unauthenticated header. Any app logic keyed off `data.shop` (session lookup, order/product mutation, inventory sync, etc.) can be tricked into acting on/for the wrong tenant — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any app author following the gem's documented pattern of trusting `WebhookMetadata#shop` (as shown in the gem's own tests, e.g. `test/webhooks/registry_test.rb`) as the tenant/session key, since:
- No special credentials beyond a normal app install are required (the attacker only needs to be a shop merchant who installed the target app).
- Crafting the replay only requires capturing one legitimate webhook and forging one HTTP header; no cryptographic secret needs to be recovered.

### Recommendation
Bind the shop identity into the value that is actually HMAC-verified, e.g. include the `shop-domain` header (and other dispatch-relevant fields) in `Request#to_signable_string`, or otherwise require host apps to verify that `request.shop` corresponds to a session/shop context established independently of the header before trusting it for tenant dispatch. At minimum, document prominently that `Request#shop`/`WebhookMetadata#shop` is unauthenticated header data and must not be used as a sole tenant-binding key.

### Proof of Concept
1. App with client secret `S` is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`.
2. Attacker triggers any webhook on their own shop, capturing the raw POST body `B` and its valid header `X-Shopify-Hmac-Sha256: HMAC(S, B)`.
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and same HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(S, B)`: [5](#0-4) 
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though the body content actually originated from the attacker's own shop.
