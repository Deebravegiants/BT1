This confirms the trust model: the docs explicitly promise that `Registry.process` "will verify the request did indeed come from Shopify" and hand the app `data.shop` to attribute the webhook to a tenant. That promise is broken because the shop identity is never bound to the signature.

### Title
Webhook `shop` domain is trusted from an unauthenticated header while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC over the raw request body only, then trusts the `shop` value taken straight from the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to attribute the event to a tenant, without that header ever being part of the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and `Request#shop` returns an unsigned header value: [1](#0-0) [2](#0-1) [3](#0-2) 

`Registry.process` validates only this body-bound HMAC and then forwards the unsigned `request.shop` straight to the app's handler: [4](#0-3) 

The equality the code implicitly (and incorrectly) assumes is:
`shop that produced/authorized this signed body == shop header value read from the request`

But the HMAC key (`Context.api_secret_key` / `old_api_secret_key`) is the app's single `client_secret`, shared across every merchant/tenant that has installed the app — it is not shop-specific: [5](#0-4) 

Because the signature covers only `@raw_body` and never the shop header, any raw body + HMAC pair that is valid for tenant A's webhook delivery remains a perfectly valid signature when replayed with the `x-shopify-shop-domain` header rewritten to tenant B. `HmacValidator.validate` will pass, and `Registry.process` calls the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `shop` is "tenant B", even though the signed body content actually originated from tenant A's event: [6](#0-5) 

The gem's own documentation tells integrators that `process` "will verify the request did indeed come from Shopify" and that `data.shop` is "the shop domain of the webhook," encouraging host apps to key persistence/business logic off `data.shop` without additional verification, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`. This is precisely the "field acted on but not covered by the HMAC" binding failure: the field used for tenant attribution (`shop`) is disjoint from the field cryptographically verified (`raw_body`).

### Impact Explanation
An attacker who legitimately installs the app on their own store (a normal, unprivileged action available to any merchant/internet user, requiring no leaked secrets or privileged access) will receive genuine webhook deliveries from Shopify that are HMAC-signed with the app's `client_secret`. Because that HMAC never binds the shop domain, the attacker can replay the exact same raw body + `hmac-sha256` value to the app's public webhook endpoint while substituting `x-shopify-shop-domain` with a victim tenant's domain. `Registry.process` will accept it as authentic and dispatch it to the app's handler labeled as an event from the victim shop, letting the attacker inject attacker-controlled webhook content (order/product/customer payloads, etc.) into another tenant's data pipeline. This is a cross-tenant integrity/isolation break within a multi-tenant app built on this gem, satisfying the Critical "cross-tenant access" bar defined for this analysis, since the only thing standing between "my own webhook data" and "the victim's tenant scope" is an unauthenticated header value.

### Likelihood Explanation
Likelihood is high for any app that follows the gem's documented pattern of trusting `data.shop`: the only prerequisite is that the attacker be a legitimate app installer for some shop (freely available to any internet user through normal app installation/OAuth), and have the ability to POST directly to the app's public webhook route with custom headers — both trivial with a normal HTTP client. No access token, `api_secret_key`, or privileged credentials are required; the attacker only needs one real, validly-signed webhook delivery from their own tenant to replay.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is HMAC-verified, or otherwise re-derive/verify shop identity independent of client-supplied headers:
- Include `shop-domain` (and `topic`) in `Request#to_signable_string` so `HmacValidator.validate` fails if these headers are altered relative to what Shopify actually signed, or
- Cross-check `request.shop` against a shop already known/authorized for the specific `webhook_id`/subscription before invoking the handler, rather than trusting the header verbatim.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) so Shopify sends a real request to the app's webhook endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-raw-body>`, and some `raw_body`.
2. Capture that exact `raw_body` and `x-shopify-hmac-sha256` value.
3. Send a new POST to the same app webhook endpoint with identical `raw_body` and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` (it only checked `@raw_body`), and `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches the handler with `shop: "victim.myshopify.com"` and the attacker-supplied body content, as if Shopify had sent this event for the victim's tenant.
