### Title
Stale delegate grant re-arms when the position NFT returns to the original grantor — (File: contracts/controller/src/storage/account.rs)

### Summary
A `DelegateGrant` is keyed by `account_id` and validated by comparing its stored `granted_by` to the *current* NFT owner, rather than being deleted on ownership change. A grant therefore becomes dormant on transfer but is never wiped, and it silently re-activates if the position NFT ever returns to the address that created it. This is the on-chain analog of CVE-2018-1062's incompletely-wiped storage block being reallocated: the controller's `Delegates(account_id)` slot retains authorization residue that surfaces only when the "block" (the account) is reallocated back to a previous holder.

### Finding Description
The controller stores per-account delegate grants under `ControllerKey::Delegates(account_id)`. Each `DelegateGrant` carries the `granted_by` address, and `get_delegates` filters on `granted_by == current_owner` instead of clearing the entry at transfer time. The project documents this behavior: the stale grant "stays in storage and re-arms if the token returns to `granted_by`," and an intermediate owner can only purge it by calling `remove_delegate` per delegate (max 16 entries) — grants they may not know exist, since `get_delegates` returns an empty list while they are dormant. [1](#0-0) [2](#0-1) 

The regression test `remove_delegate_purges_stale_grant_preventing_resurrection` proves the resurrection primitive explicitly: Alice's grant on `Delegates(account_id)` survives her transfer to Bob in persistent storage, and would grant the delegate full account powers again "when the NFT returns to its original owner." [3](#0-2) 

Delegates are not read-only: owner-or-active-delegate authorization covers `borrow`, `withdraw`, and every account strategy verb (`multiply`, `flash_position`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`). A resurrected delegate can borrow against the account's collateral and withdraw to itself. [4](#0-3) 

Attack path (all unprivileged):

1. Alice owns account `N` and previously granted delegate `D` (e.g., a keeper/manager contract).
2. Alice transfers/sells the position NFT to Bob. The grant goes dormant but is not erased.
3. Bob never calls `remove_delegate` — he cannot see dormant grants via `get_delegates`, and nothing forces him to.
4. Alice reacquires the NFT (buys it back, wins it in a settlement, receives it in a liquidation `Credit` flow involving the same account id path, or Bob simply transfers it back).
5. `D`'s grant is live again without any fresh authorization from Alice. `D` calls `borrow(account_id = N, to = D)` / `withdraw` and drains LTV-available value.

### Impact Explanation
Theft of user funds: the resurrected delegate can withdraw collateral or mint debt payable to itself up to the account's solvency limits, transferring value out of a position whose current owner never re-consented to the delegation. The loss is bounded only by the account's collateral and LTV headroom. Because account ids are NFT token ids and are never reused, the residue is pinned to a durable, tradeable asset — the "sensitive data" left in the un-wiped slot is spending authority. [5](#0-4) 

### Likelihood Explanation
Requires an account that once had a delegate to change hands and later return to the grantor — plausible for marketplace sales, OTC position transfers, and unwind-and-rebuy flows, all permitted by permissionless `transfer`/`transfer_from`. No price condition, timing race, or privileged action is needed; the dormant grant persists indefinitely in persistent storage and `renew_user_account` keeps renewing the `Delegates` key alongside the account's other entries, so it does not even expire with the account TTL. [6](#0-5)  The only mitigation is that an intermediate holder voluntarily purges invisible grants, which the protocol neither requires nor surfaces.

### Recommendation
Wipe the grant list at the authorization boundary instead of filtering on `granted_by`: either (a) stamp grants with an owner-change epoch/nonce captured at transfer detection and reject grants whose epoch is stale, or (b) store grants keyed under the owner address rather than the account id so they cannot re-bind. At minimum, have `get_delegates`/`is_delegate` treat a grant as valid only when it was created under the *current continuous* ownership (e.g., store a mint/transfer counter), so a round-trip transfer cannot resurrect it. Document the residual risk until fixed: a reacquiring owner should call `remove_delegate` for every historical grantee.

### Proof of Concept
Conceptual trace against `contracts/controller/src/storage/account.rs`:

1. `add_delegate(alice, N, D)` → `Delegates(N) = [DelegateGrant{ granted_by: alice, delegate: D }]`.
2. `position_nft.transfer(alice → bob, N)`. `Delegates(N)` is untouched (`transfer` is a stock OZ call; the controller is not notified). `get_delegates(N, bob)` returns `[]` because `granted_by != bob`.
3. `position_nft.transfer(bob → alice, N)`. Now `granted_by == owner` again; `get_delegates(N, alice)` returns `[D]` and `require_authorized_caller(env, D)` for owner-or-delegate verbs succeeds.
4. `D` calls `borrow(caller = D, account_id = N, borrows = [(debt_asset, X)], to = Some(D))` — authorized as active delegate — and `withdraw(...)` to move collateral out.

The existing unit test at `contracts/controller/tests/storage/account.rs:177-225` already demonstrates steps 1–3 (grant survives transfer and would re-arm); step 4 follows because delegate status gates `borrow`/`withdraw`/strategy verbs.

```rust
/// The new owner's `remove_delegate` deletes a previous owner's grant and returns `false`.
/// The grant stays deleted when the NFT returns to the previous owner.
#[test]
fn remove_delegate_purges_stale_grant_preventing_resurrection() {
    let env = Env::default();
    env.mock_all_auths();
    let admin = Address::generate(&env);
    let contract_id = env.register(Controller, (admin,));
    let nft = setup_position_nft(&env, &contract_id);

    let alice = Address::generate(&env);
    let bob = Address::generate(&env);
    let delegate = Address::generate(&env);
    let account_id = u64::from(position_nft::PositionNftClient::new(&env, &nft).mint(&alice));

    env.as_contract(&contract_id, || {
        assert!(add_delegate(&env, account_id, &alice, &delegate));
        assert_eq!(get_delegates(&env, account_id, &alice).len(), 1);
    });

    position_nft::PositionNftClient::new(&env, &nft).transfer(
        &alice,
        &bob,
        &u32::try_from(account_id).unwrap(),
    );

    env.as_contract(&contract_id, || {
        assert!(!remove_delegate(&env, account_id, &bob, &delegate));
        assert!(
            !env.storage()
                .persistent()
                .has(&ControllerKey::Delegates(account_id)),
            "stale grant must be purged from storage, not merely read as empty"
        );
    });

    position_nft::PositionNftClient::new(&env, &nft).transfer(
        &bob,
        &alice,
        &u32::try_from(account_id).unwrap(),
    );

    env.as_contract(&contract_id, || {
        assert_eq!(
            get_delegates(&env, account_id, &alice).len(),
            0,
            "the purged grant must not resurrect when the NFT returns to its original owner"
        );
    });
```

```rust
/// Deletes metadata, both position maps, and delegates. Does not burn the NFT.
pub(crate) fn remove_account_entry(env: &Env, account_id: u64) {
    let persistent = env.storage().persistent();
    persistent.remove(&ControllerKey::AccountMeta(account_id));
    persistent.remove(&ControllerKey::SupplyPositions(account_id));
    persistent.remove(&ControllerKey::BorrowPositions(account_id));
    persistent.remove(&ControllerKey::Delegates(account_id));
}
```

```rust
/// Renews user TTL for each existing account entry; does not renew the NFT.
pub(crate) fn renew_user_account(env: &Env, account_id: u64) {
    let persistent = env.storage().persistent();
    let keys = [
        ControllerKey::AccountMeta(account_id),
        ControllerKey::SupplyPositions(account_id),
        ControllerKey::BorrowPositions(account_id),
        ControllerKey::Delegates(account_id),
    ];
    for key in &keys {
        if persistent.has(key) {
            renew_user_key(env, key);
        }
    }
}
```
