## Title
`IsmpCallFilter` denylist only inspects `Message::Consensus`, letting `Message::FraudProof` reach the BEEFY consensus client and permanently freeze the bridge without the protocol's SP1 gate - (File: `parachain/runtimes/gargantua/src/lib.rs`, `parachain/runtimes/nexus/src/lib.rs`)

### Summary
`IsmpCallFilter::contains` is the `BaseCallFilter` that is supposed to keep `pallet_ismp::Call::handle_unsigned` from ever touching the BEEFY consensus client directly, forcing all BEEFY state advances through `pallet-beefy-consensus-proofs`, which requires SP1 zkVM verification. The filter, however, only pattern-matches `Message::Consensus(...)` when scanning a submitted batch: [1](#0-0) [2](#0-1) 

```rust
match message {
    Message::Consensus(consensus) =>
        host.consensus_client_id(consensus.consensus_state_id) == Some(ismp_beefy::BEEFY_CONSENSUS_ID),
    _ => false,
}
```

`ismp::messaging::Message` has five variants, and `Message::FraudProof(FraudProofMessage)` carries the exact same `consensus_state_id` field that a `Consensus` message does [3](#0-2) , but it is caught only by the filter's `_ => false` catch-all. Any batch containing solely `FraudProof`/`Request`/`Response`/`Timeout` messages is unconditionally allowed through the filter, even when it targets the BEEFY `consensus_state_id`. This is structurally identical to picklescan's incomplete denylist (`pty.spawn` omitted from a hand-maintained "dangerous" list): the filter denylists one variant that can touch BEEFY's `consensus_state_id` but not the sibling variant with the same field.

### Finding Description
`pallet-ismp::handle_unsigned` is a permissionless entry point reachable by any unprivileged relayer/fisherman via an unsigned extrinsic, dispatching straight into `handle_incoming_message`: [4](#0-3) 

```rust
match message {
    Message::Consensus(consensus_message) => consensus::update_client(host, consensus_message),
    Message::FraudProof(fraud_proof) => consensus::freeze_client(host, fraud_proof),
    ...
}
```

`freeze_client` calls `consensus_client.verify_fraud_proof(...)` for the BEEFY client and, if it returns `Ok`, unconditionally calls `host.freeze_consensus_client(...)`, permanently freezing the client [5](#0-4) . Per the docs, "Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized" — this is a hard, permanent halt of all requests/responses on that route.

The runtime comment explicitly states the design intent of `IsmpCallFilter`: BEEFY must only advance through `pallet-beefy-consensus-proofs`'s SP1-gated path, and "allowing raw updates through `handle_unsigned` would bypass that requirement entirely" [6](#0-5) . The filter enforces this only for `Message::Consensus`. `Message::FraudProof` bypasses the filter and reaches `BeefyConsensusClient::verify_fraud_proof` directly, with no SP1 check: [7](#0-6) . This routine only checks that `proof_1`/`proof_2` are two decodable BEEFY MMR proofs with the same block number and different commitments, both independently valid against the trusted state — a much weaker bar than the SP1 circuit gating `Message::Consensus`, and it is reachable via `handle_unsigned` without going through `pallet-beefy-consensus-proofs` at all.

The base call filter's own regression test suite explicitly documents the intended scope as "blocks `Ismp::handle_unsigned` when the batch carries a BEEFY consensus update," and every assertion in it only ever constructs `Message::Consensus` batches — no case exercises `Message::FraudProof` against the BEEFY state id, so the gap in test coverage mirrors the gap in the filter itself [8](#0-7) .

### Impact Explanation
An attacker who can produce two conflicting-but-independently-valid BEEFY MMR proofs for the same block height (this is exactly the "fraud proof" mechanism, intentionally permissionless for legitimate fishermen use) can submit them as a `Message::FraudProof` batch via `handle_unsigned`. `IsmpCallFilter` allows the call to dispatch (it isn't a `Message::Consensus` variant), `ensure_none` passes (unsigned dispatch is exactly what `handle_unsigned`/`ValidateUnsigned` supports), and `freeze_client` permanently freezes the BEEFY consensus client. Once frozen, the client "can no longer process new consensus messages as well as new requests & responses," and cannot be unfrozen without governance re-initializing a brand-new consensus client — a permanent denial-of-service that halts the entire BEEFY-secured bridge route (Ethereum/Polkadot messaging on gargantua/nexus), matching the "route unable to deliver messages" criterion.

### Likelihood Explanation
This is reachable directly from a single unsigned extrinsic by any unprivileged party — no admin, governance, or privileged role is required, consistent with the "fisherman" permission model intentionally being permissionless. The only requirement is producing two valid-but-conflicting BEEFY consensus proofs at the same block height, which is the entire premise fraud proofs are designed to support (they aren't supposed to require insider access, only genuine byzantine evidence — but the bug is that the *filter* doesn't gate this path the way it gates the `Consensus` update path, so the SP1 hardening intentionally added for BEEFY updates does not extend to BEEFY freezes).

### Recommendation
Extend `IsmpCallFilter::contains` in both `parachain/runtimes/gargantua/src/lib.rs` and `parachain/runtimes/nexus/src/lib.rs` to also inspect `Message::FraudProof(fraud_proof)` and compare `fraud_proof.consensus_state_id` against the BEEFY consensus client id, rejecting it the same way `Message::Consensus` is rejected — or otherwise route BEEFY fraud proofs exclusively through `pallet-beefy-consensus-proofs` (mirroring how consensus updates were hardened), so `handle_unsigned` can never touch the BEEFY client's state through any `Message` variant.

### Proof of Concept
1. Construct two valid BEEFY MMR proofs (`proof_1`, `proof_2`) for the same block number with different commitments, satisfying `BeefyConsensusClient::verify_fraud_proof`'s checks (decodable, same `block_number`, differing commitment bytes, and each independently passes `verify_consensus::<SubstrateCrypto>`).
2. Build `Message::FraudProof(FraudProofMessage { proof_1, proof_2, consensus_state_id: ismp_beefy::BEEFY_CONSENSUS_ID, signer: vec![] })`.
3. Submit `Ismp::handle_unsigned(vec![message])` as an unsigned extrinsic.
4. `IsmpCallFilter::contains` evaluates the single message: it is not `Message::Consensus`, so the closure returns `false` for it; `!messages.iter().any(...)` is `true`, so the filter allows the call.
5. `ensure_none(origin)` passes since the extrinsic is unsigned.
6. `Self::execute` → `handle_incoming_message` → `consensus::freeze_client` → `BeefyConsensusClient::verify_fraud_proof` succeeds → `host.freeze_consensus_client(BEEFY_CONSENSUS_ID)` permanently freezes the BEEFY client, halting all further BEEFY-secured message delivery.

```rust
pub struct IsmpCallFilter;
impl frame_support::traits::Contains<RuntimeCall> for IsmpCallFilter {
```

```rust
/// Freeze a consensus client by providing a valid fraud proof.
pub fn freeze_client<H>(host: &H, msg: FraudProofMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host
		.consensus_client_id(msg.consensus_state_id)
		.ok_or_else(|| Error::Custom("Unknown Consensus State Id".to_string()))?;

	host.is_consensus_client_frozen(msg.consensus_state_id)?;

	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;

	consensus_client.verify_fraud_proof(host, trusted_state, msg.proof_1, msg.proof_2)?;

	host.freeze_consensus_client(msg.consensus_state_id)?;

	host.store_consensus_update_time(msg.consensus_state_id, host.timestamp())?;

	Ok(MessageResult::FrozenClient(msg.consensus_state_id))
}
```

```rust
	fn verify_fraud_proof(
		&self,
		_host: &dyn IsmpHost,
		trusted_consensus_state: Vec<u8>,
		proof_1: Vec<u8>,
		proof_2: Vec<u8>,
	) -> Result<(), Error> {
		let consensus_state: ConsensusState =
			codec::Decode::decode(&mut &trusted_consensus_state[..])
				.map_err(|e| BeefyError::DecodeConsensusState(format!("{e:?}")))?;

		let first_proof: MmrProof = codec::Decode::decode(&mut &proof_1[..])
			.map_err(|e| BeefyError::DecodeMmrProof(format!("{e:?}")))?;

		let second_proof: MmrProof = codec::Decode::decode(&mut &proof_2[..])
			.map_err(|e| BeefyError::DecodeMmrProof(format!("{e:?}")))?;

		let first_commitment = &first_proof.signed_commitment.commitment;
		let second_commitment = &second_proof.signed_commitment.commitment;

		if first_commitment.block_number != second_commitment.block_number {
			return Err(BeefyError::FraudProofsDifferentBlock.into());
		}

		if first_commitment.encode() == second_commitment.encode() {
			return Err(BeefyError::FraudProofsIdenticalCommitments.into());
		}

		let empty_parachain_proof =
			ParachainProof { parachains: vec![], proof: vec![], total_leaves: 0 };

		verify_consensus::<SubstrateCrypto>(
			consensus_state.clone(),
			ConsensusMessage { mmr: first_proof, parachain: empty_parachain_proof.clone() },
		)
		.map_err(|e| BeefyError::FraudProofVerificationFailed(format!("first: {e:?}")))?;

		verify_consensus::<SubstrateCrypto>(
			consensus_state,
			ConsensusMessage { mmr: second_proof, parachain: empty_parachain_proof },
		)
		.map_err(|e| BeefyError::FraudProofVerificationFailed(format!("second: {e:?}")))?;

		Ok(())
	}
```
