## Title
IntentGatewayV2 (Tron) `placeOrder` credits escrow with the requested amount instead of the actually-received balance, allowing fee-on-transfer/deflationary tokens to permanently insolvent the escrow pool - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` in the Tron deployment does not implement a token allow-list, so any ERC-20 address can be used as an order input, including fee-on-transfer or rebasing tokens. In the non-predispatch escrow path, the contract calls `safeTransferFrom` for the requested `amount` and then unconditionally credits the internal escrow ledger `_orders[commitment][token]` with `reducedInputs[i].amount`, which is derived from the *requested* amount rather than the amount the gateway actually received. This is the same bug class as the reported `_safeRewardTransfer` finding: without balance-before/after verification, deflationary transfers cause on-chain accounting to diverge from real custodied funds.

### Finding Description
In `placeOrder`'s "no predispatch" branch: [1](#0-0) 

the code does:
```solidity
IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount);
...
_orders[commitment][token] += reducedInputs[i].amount;
```
No `balanceOf(address(this))` snapshot is taken before/after the transfer, so if `token` charges a transfer fee or rebases downward, the gateway receives less than `order.inputs[i].amount`, yet the escrow ledger is incremented as if the full amount arrived.

This directly contrasts with the sibling EVM implementation, which was already patched to avoid exactly this issue by measuring the balance delta: [2](#0-1) 

Later, when the escrow is redeemed/refunded, `withdraw` pays out the full ledgered `amount` from the shared token balance pool: [3](#0-2) 

Because `_orders[commitment][token]` for every order placed with a deflationary token is inflated relative to the actual tokens custodied, the aggregate ledgered escrow across all commitments for that token exceeds `IERC20(token).balanceOf(address(this))`. The protocol has no token whitelist, so nothing prevents this — matching the referenced report's premise ("the system does not currently have a white-listing feature for tokens").

### Impact Explanation
Once the aggregate escrow ledger for a token exceeds the gateway's real token balance, later legitimate `withdraw` calls (via `RedeemEscrow` or `RefundEscrow` settlement) for that token will revert on insufficient balance, permanently freezing those users' escrowed funds. Because token balances are pooled per-contract rather than per-order, this insolvency can also spill over to unrelated orders sharing the same token, letting earlier claimants effectively drain value that should have covered later depositors — a fund-freezing/insolvency condition reachable by any unprivileged user simply by placing an order with a fee-on-transfer token as input.

### Likelihood Explanation
Any user can call `placeOrder` with an arbitrary ERC-20 token address, since there is no token whitelist in `IntentGatewayV2`. Fee-on-transfer/deflationary tokens are common and require no special privileges or complex setup — a single `placeOrder` transaction with such a token triggers the divergence between ledgered and actual escrow.

### Recommendation
Mirror the fix already applied in `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before and after `safeTransferFrom` in the non-predispatch branch of `placeOrder`, and credit `_orders[commitment][token]` (and `order.inputs[i].amount`/`reducedInputs[i].amount` derivations) based on the actual received delta rather than the requested amount.

### Proof of Concept
1. Deploy or use an existing fee-on-transfer ERC-20 token `T` (e.g., burns 5% on every transfer).
2. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs[0] = {token: T, amount: 1000}` and no predispatch calls.
3. `safeTransferFrom(msg.sender, address(this), 1000)` results in the gateway actually receiving only 950 `T` tokens, but `_orders[commitment][T] += reducedInputs[0].amount` (based on 1000, minus any protocol fee) is credited as if the full amount arrived.
4. Repeat with multiple orders/users using token `T`; the sum of all `_orders[*][T]` values grows faster than the gateway's real `T` balance.
5. When a later order's `withdraw` is triggered (via fill/redeem or cancel/refund), the `token.call(transfer, ...)` for `T` reverts due to insufficient balance, permanently freezing that user's escrowed funds (or, if it succeeds, pulls balance that rightfully belongs to another commitment's escrow).
