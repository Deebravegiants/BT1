### Title
Session-token context confusion allows non-Admin (customer-facing) tokens to be exchanged for full merchant Admin API access — (`lib/shopify_api/auth/token_exchange.rb`, `lib/shopify_api/auth/jwt_payload.rb`)

### Summary
`ShopifyAPI::Auth::JwtPayload` validates a Shopify session token's signature and its `aud` (app API key) and expiry claims, but never binds the token to the *context/issuer* that minted it (Admin embedded app vs. Checkout UI Extension vs. Customer Account UI Extension — all of which sign session tokens with the same shared `api_secret_key`/`aud`). `TokenExchange.exchange_token` then blindly trusts `jwt_payload.shop` (the `dest` claim) and performs a server-to-server OAuth token exchange, optionally requesting an `OFFLINE_ACCESS_TOKEN` — the highest-privilege, app-level (not per-customer) merchant access token — for whatever shop the token names, without checking that the token actually came from a privileged Admin session.

### Finding Description
`JwtPayload#initialize` only enforces: [1](#0-0) 
i.e. `aud == Context.api_key`, plus standard JWT exp/nbf/signature checks via the shared `api_secret_key`. It never restricts or checks `iss`/`dest` format to ensure the token was minted for the privileged Admin embedding context. The only place `iss` is examined is the private helper `admin_session_token?`, and it is used solely to gate `shopify_user_id`, not to gate token-exchange eligibility: [2](#0-1) [3](#0-2) 

The test fixtures confirm that this same `api_secret_key` is used to sign session tokens for fundamentally different, non-Admin surfaces (e.g. Checkout UI Extensions), which have `iss` ending in `/checkouts` rather than `/admin`: [4](#0-3) 

`TokenExchange.exchange_token` takes any session token that satisfies `JwtPayload`'s checks — i.e., any token signed with the app's shared secret and matching `aud`, regardless of `iss`/context — extracts the shop from `dest`, and uses it directly to request an access token, including the app-level `OFFLINE_ACCESS_TOKEN` grant that is not scoped to an individual customer: [5](#0-4) 

The identity binding that should hold is:
`token.intended_context (Admin-privileged) == token.actual_context (whatever surface issued it)`

Because `JwtPayload`/`TokenExchange` never check this, a token minted by a low-privilege, customer-facing surface (Checkout UI Extension / Customer Account UI Extension, which any storefront visitor can obtain via that extension's JS session-token API) satisfies exactly the same validation path as a token minted by the privileged Admin embed, and can be "replayed" into a merchant-level token exchange. This is the direct analog of the reported bug class: one shared signing key is used across multiple distinct "signers"/contexts, and the verifier fails to rehash/bind the signature to the specific context it was intended for, enabling a signature (session token) legitimate in one context to be reused in another, more privileged one.

### Impact Explanation
If a host application built on this gem exposes a token-exchange endpoint that accepts a `session_token` from a customer-facing surface (as the gem's own `TokenExchange.exchange_token` is documented and designed to be called with "the" session token, with no guidance to reject non-Admin issuers), any anonymous shopper who can load a Checkout UI Extension or Customer Account UI Extension for the target shop can obtain a validly-signed session token and use it to mint an **offline, app-level Admin access token** for that shop via this library — i.e., authentication/privilege-boundary bypass and theft of a merchant access token by an unauthenticated storefront visitor. This meets the Critical bar: theft of a merchant access token via a scope/context check that answers permissively.

### Likelihood Explanation
Exploitation requires no secrets, no privileged account, and no network interception: an ordinary customer visiting checkout or the customer-account portal of any shop that has the app installed can retrieve a genuinely Shopify-signed session token for that low-privilege surface and submit it to the app's token-exchange call path. The library itself performs no `iss`/context check to prevent this, so the likelihood of a host app (relying on this gem's advertised `aud`-based validation as "the" security check) being vulnerable is high.

### Recommendation
In `JwtPayload`, validate and expose the token's issuing context (`iss`) explicitly (not just as a side helper for `shopify_user_id`), and have `TokenExchange.exchange_token` reject session tokens whose `iss` does not correspond to an Admin-embedded session before performing any grant, especially before requesting `OFFLINE_ACCESS_TOKEN`. More generally, apply a defensive binding similar to ERC-7739's approach referenced in the report: incorporate the expected context/audience into what is checked before trusting a signature (token) for a privileged operation, rather than relying solely on a shared secret/`aud` match that is common to multiple, differently-privileged issuers.

### Proof of Concept
1. App `MyApp` is installed on `victim-shop.myshopify.com` and uses a Checkout UI Extension (or Customer Account UI Extension), both of which sign session tokens with `MyApp`'s `client_secret`/`api_key` as `aud`, and `iss` ending in `/checkouts` (not `/admin`).
2. Any unauthenticated shopper opens checkout on `victim-shop.myshopify.com`, and via the extension's JS session-token API obtains a valid, Shopify-signed `session_token` (`iss` = `.../checkouts`, `aud` = `MyApp`'s api key, `dest` = `victim-shop.myshopify.com`).
3. The shopper POSTs this `session_token` to `MyApp`'s backend endpoint that calls:
```ruby
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: session_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
```
4. `JwtPayload.new(session_token)` succeeds (signature valid, `aud` matches, not expired) — see [6](#0-5) .
5. `exchange_token` proceeds to request an `OFFLINE_ACCESS_TOKEN` for `victim-shop.myshopify.com` from Shopify's OAuth endpoint using `MyApp`'s `client_secret`, returning a full merchant-level offline access token to the caller — see [7](#0-6) .
6. The unauthenticated shopper (via the app's endpoint) now effectively causes issuance of a merchant Admin API access token, despite having supplied only a customer-facing checkout session token.
