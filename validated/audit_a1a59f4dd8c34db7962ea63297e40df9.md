## Analog Found

### Title
Emporium wallet-signature verification uses raw ECDSA and never checks EIP-1271, permanently bricking all wallet-authorized operations - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.verifyWallet()` authenticates `EmporiumStack.signerAddress` purely via `ECDSA.tryRecover`, exactly the EIP-712/ECDSA-only pattern flagged as broken in the external report. In this repo `signerAddress` is not an arbitrary EOA — it is used directly as the address of a `HinkalWallet` smart-contract instance (`IHinkalWallet(stack.signerAddress).callHinkalWallet(...)`), and `HinkalWallet` itself already implements the EIP-1271 `isValidSignature()` recovery precisely so it can "sign" on its own behalf. `verifyWallet()` never calls it, so contract-wallet-authorized flows can never pass verification.

### Finding Description
`EmporiumStack` carries `v, r, s, signerAddress` [1](#0-0) . In `runAction`, whenever an operation is a "Stateful Interaction" (`op.invokeWallet && stack.signerAddress != address(0)`), `stack.signerAddress` is cast directly to `IHinkalWallet` and its `callHinkalWallet`/`doSendToRelay` are invoked [2](#0-1) . That is, `signerAddress` is by design the address of a `HinkalWallet` smart contract that holds the ERC20/ETH balance being operated on, not an EOA.

`HinkalWallet` gates both of those state-changing functions with `onlyEmporium`, and correctly implements EIP-1271's `isValidSignature()` so that it can authorize a signature "on its own behalf" via `ECDSA.tryRecover(hash, signature)` compared against `address(this)` [3](#0-2) .

However, the actual authorization check performed before any wallet-mediated call, `verifyWallet()`, never calls `IERC1271(stack.signerAddress).isValidSignature(...)`. It only does raw `ECDSA.tryRecover` on the EIP-712 typed hash and requires `recoveredAddress == stack.signerAddress`: [4](#0-3) 

Since `stack.signerAddress` is a contract address (a `HinkalWallet` instance) with no associated secp256k1 private key, `ECDSA.tryRecover` can never return that address as the recovered signer for any real signature (only via an astronomically improbable hash/address collision). Consequently, `verified` is always `false` and `verifyWallet` always reverts with `InvalidSignature()` whenever `signerAddress != address(0)` — i.e., every time the protocol intends to authenticate a wallet-mediated operation.

This breaks the intended equality "signature recovered == wallet contract that is being authorized to act," and does so unconditionally, not just for edge-case wallets — the `HinkalWallet` contract itself is never an EOA, so this path is unreachable by design for its only real caller pattern. The `isValidSignature` function that was clearly written to solve exactly this (dead code, never invoked anywhere else in the codebase) confirms the intended fix was omitted from the enforcement point.

### Impact Explanation
Any ERC20/ETH balance sitting on a `HinkalWallet` contract that is meant to be moved via a signer-authorized stateful operation (`callHinkalWallet`) or via `doSendToRelay`/`sendToRelayFromWallet` fee payment can never be released, because the only entry point that can call these `onlyEmporium`-gated functions (`EmporiumUpgradeable.runAction` → `verifyWallet`) will always revert for a non-zero `signerAddress`. There is no alternate authorized path to move funds out of the wallet. This permanently freezes user funds routed through the contract-wallet / stateful-Emporium flow, matching the Critical/High "permanent freezing of user funds" impact class.

### Likelihood Explanation
This triggers deterministically, every single time, for any use of the intended contract-wallet-signed feature (`invokeWallet` stateful operations or non-zero `signerAddress` relay fee payment) — there is no special attacker action required, only normal use of the documented feature. Likelihood is effectively 100% for any user of this code path.

### Recommendation
In `verifyWallet()`, when `stack.signerAddress` is a contract, dispatch to `IERC1271(stack.signerAddress).isValidSignature(hashedMessage, signature)` and compare against `IERC1271.isValidSignature.selector`, falling back to `ECDSA.tryRecover` only for EOA signers (e.g., using `SignatureChecker.isValidSignatureNow` from OpenZeppelin, which already implements this dual-path check safely).

### Proof of Concept
1. Deploy `HinkalWallet` for a user (its address has no private key).
2. User funds the wallet, then attempts an Emporium `runAction` with `EmporiumStack.signerAddress = <HinkalWallet address>` and `op.invokeWallet = true`, along with any `(v,r,s)`.
3. `verifyWallet()` computes `hashedMessage` and calls `ECDSA.tryRecover(hashedMessage, v, r, s)`; no matter what valid EIP-1271 signature bytes are supplied for the wallet (e.g., a signature that would pass `HinkalWallet.isValidSignature`), the raw ECDSA recovery can never yield the wallet's own contract address as `recoveredAddress`.
4. `verified` is `false`, `verifyWallet` reverts with `InvalidSignature()`, `runAction` reverts, and the wallet's funds remain stuck with no alternative unlock path (`callHinkalWallet`/`doSendToRelay` are `onlyEmporium`).

    // EIP-1271: https://eips.ethereum.org/EIPS/eip-1271
    function isValidSignature(
        bytes32 _hash,
        bytes memory _signature
    ) external view returns (bytes4) {
        (address addr, ECDSA.RecoverError err) = ECDSA.tryRecover(
            _hash,
            _signature
        );

        bool verified = err == ECDSA.RecoverError.NoError &&
            addr == address(this);

        return bytes4(verified ? 0x1626ba7e : 0xffffffff);
    }
