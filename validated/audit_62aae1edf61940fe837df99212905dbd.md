**Analysis:** The premise doesn't hold up against the actual code.

`EpochChangeProof::verify` in [1](#0-0)  chains verification strictly: for each `ledger_info_with_sigs` in the proof, it calls `verifier_ref.verify(...)`, then reassigns `verifier_ref` to that ledger info's `next_epoch_state()` before processing the next entry [2](#0-1) .

The concrete `Verifier` implementation, `EpochState::verify`, enforces `self.epoch == ledger_info.ledger_info().epoch()` [3](#0-2) . Since `verifier_ref` is replaced each iteration with the *next* epoch's state (epoch N+1) taken from the previous entry's `next_epoch_state()`, a crafted proof containing epoch N twice in a row would fail this equality check on the second occurrence — the verifier now expects epoch N+1, not N. This is exactly what the existing unit test `verify_epoch_change_proof` checks under "Test non contiguous proof will fail" and "Test non increasing proof will fail" [4](#0-3) . So `verify` already rejects non-strictly-increasing/duplicate-epoch sequences by construction; it doesn't need a special duplicate-detection check because the chained epoch-equality assertion enforces it implicitly.

Additionally, `EpochChangeProof`/`Verifier` in `types/src/epoch_change.rs` is part of the consensus/state-sync light-client trust-chain verification used to advance a node's or client's trusted validator set — it has no connection to Fungible Asset dispatchable hooks, metadata ownership, or code-object ownership in the Move framework. There is no code path where a consumer "naively takes the last matching entry" of an `EpochChangeProof` to select an FA dispatch hook address; these are unrelated subsystems. The scenario described doesn't correspond to any real custody boundary crossed by unprivileged input in this codebase.

    pub fn verify(&self, verifier: &dyn Verifier) -> Result<&LedgerInfoWithSignatures> {
        ensure!(
            !self.ledger_info_with_sigs.is_empty(),
            "The EpochChangeProof is empty"
        );
        ensure!(
            !verifier
                .is_ledger_info_stale(self.ledger_info_with_sigs.last().unwrap().ledger_info()),
            "The EpochChangeProof is stale as our verifier is already ahead \
             of the entire EpochChangeProof"
        );
        let mut verifier_ref = verifier;

        for ledger_info_with_sigs in self
            .ledger_info_with_sigs
            .iter()
            // Skip any stale ledger infos in the proof prefix. Note that with
            // the assertion above, we are guaranteed there is at least one
            // non-stale ledger info in the proof.
            //
            // It's useful to skip these stale ledger infos to better allow for
            // concurrent client requests.
            //
            // For example, suppose the following:
            //
            // 1. My current trusted state is at epoch 5.
            // 2. I make two concurrent requests to two validators A and B, who
            //    live at epochs 9 and 11 respectively.
            //
            // If A's response returns first, I will ratchet my trusted state
            // to epoch 9. When B's response returns, I will still be able to
            // ratchet forward to 11 even though B's EpochChangeProof
            // includes a bunch of stale ledger infos (for epochs 5, 6, 7, 8).
            //
            // Of course, if B's response returns first, we will reject A's
            // response as it's completely stale.
            .skip_while(|&ledger_info_with_sigs| {
                verifier.is_ledger_info_stale(ledger_info_with_sigs.ledger_info())
            })
        {
            // Try to verify each (epoch -> epoch + 1) jump in the EpochChangeProof.
            verifier_ref.verify(ledger_info_with_sigs)?;
            // While the original verification could've been via waypoints,
            // all the next epoch changes are verified using the (already
            // trusted) validator sets.
            verifier_ref = ledger_info_with_sigs
                .ledger_info()
                .next_epoch_state()
                .ok_or_else(|| format_err!("LedgerInfo doesn't carry a ValidatorSet"))?;
        }

        Ok(self.ledger_info_with_sigs.last().unwrap())
    }
