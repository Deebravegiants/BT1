## Analog Vulnerability Found

The OpenQ bug — an unprivileged depositor spamming a hard-capped array with low-value entries to push out a high-value entry the intended party needs — has a direct analog in `pallet-bandwidth`'s FIFO subscription list.

### Title
Unbounded, permissionless `purchase()` lets anyone evict a victim app's paid bandwidth subscriptions via the 1024-slot FIFO cap - ([File: modules/pallets/bandwidth/src/lib.rs])

### Summary
`BandwidthManager.purchase()` on any EVM source chain lets **any caller** credit a bandwidth subscription to an arbitrary `(chain, app)` pair — the `app` parameter is caller-supplied and unchecked against `msg.sender`. On the pallet side, `Allowance<T>` stores subscriptions per `(app_chain, app)` in a `BoundedVec` capped at `MAX_SUBSCRIPTIONS = 1024`. Once the list is full, every further push evicts the single oldest entry via `list.remove(0)`, regardless of its remaining value.

### Finding Description
`purchase()` in `evm/src/apps/BandwidthManager.sol` takes an arbitrary `app` and `chain` argument and dispatches a credit message with no ownership check: [1](#0-0) 

The pallet's inbound handler appends the new subscription via `push_subscription`, which evicts the oldest entry once the per-`(app_chain, app)` list reaches the 1024 cap: [2](#0-1) 

`Allowance` is keyed purely by `(app_chain, app)`, not by payer, so any account can push into any app's queue: [3](#0-2) 

Because eviction always removes index 0 (oldest, FIFO) irrespective of its `remaining_bytes`, an attacker can target a victim app that just purchased a large, long-duration, high-value tier (e.g. the $1000/8MB plan) and flood the same `(app_chain, app)` bucket with 1024 minimum-cost, minimum-`months` purchases of the cheapest tier. This pushes the victim's legitimate subscription out of the list entirely — even though it may have most of its paid-for bytes still unconsumed — while costing the attacker only `1024 × cheapest_tier_price`. This is structurally identical to the OpenQ bug: an unprivileged party fills a hard-capped slot list with low-value entries, forcing out (rather than blocking, in this case) the value the legitimate party paid for.

### Impact Explanation
The victim app permanently loses the unused byte allowance it paid real fee-token money for — `SubscriptionEvicted { lost_bytes }` fires and the bytes are gone; there is no way to reclaim them. Because `purchase()` accepts any `app`/`chain` pair and the pallet does not gate pushes by the original payer, this is a permanent, on-chain loss of protocol-purchased value inflicted by an unprivileged third party — a concrete freezing/loss of funds, matching the report's bug class (max out a bounded structure with low-value entries to force out a legitimate high-value entry).

### Likelihood Explanation
`purchase()` is fully permissionless and cheap to call repeatedly (one ERC-20 transfer + one ISMP dispatch per call); the attacker only needs to know the target `app` address and `app_chain`, both of which are public (any deployed app's identity). Cost scales with the cheapest configured tier price × 1024, which the documentation itself notes is normally "years of headroom" only under *good-faith* usage — it provides no defense against a targeted, adversarial flood. No special privileges, timing, or race conditions are required.

### Recommendation
Do not let an unprivileged, unrelated caller mutate another app's subscription queue. Options:
- Restrict `purchase()`'s effective `app` to require some proof of ownership/authorization on the destination chain, or
- Change eviction policy so a push from a payer who isn't the app's registered owner cannot evict subscriptions it didn't fund (e.g., segregate by payer, or refuse to evict entries with significant remaining value/unexpired duration in favor of reverting/queueing), or
- Increase `MAX_SUBSCRIPTIONS` substantially and/or rate-limit pushes per `(app_chain, app)` per block to raise attacker cost, and emit an alarm/require governance intervention rather than silent eviction of high-value entries.

### Proof of Concept
1. Victim app buys the largest tier (`TierFour`, 8MB/$1000) via `BandwidthManager.purchase()` on its source chain, crediting a subscription onto `Allowance[app_chain][app]`.
2. Attacker, from any account/chain with a registered `BandwidthManager`, calls `purchase(app = victim_app, tier = cheapest_configured_tier, months = 1, chain = app_chain)` 1024 times (or enough times to reach the cap, accounting for whatever else is already queued).
3. Each call appends to the same `Allowance[app_chain][victim_app]` `BoundedVec` per `push_subscription`; once the list hits `MAX_SUBSCRIPTIONS = 1024`, `list.remove(0)` evicts the oldest entry — eventually the victim's high-value subscription — emitting `SubscriptionEvicted { lost_bytes }` for whatever bytes remained unconsumed.
4. Victim app's paid-for bandwidth is permanently gone; the attacker paid only `1024 × cheapest_tier_price` to destroy up to `1 × most_expensive_tier_price` worth of the victim's allowance. [4](#0-3)

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

/// The 1024-sub cap evicts the oldest entry. force_credit reuses the
/// same push path as purchase, so this also covers the purchase cap.
#[test]
fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.
		for i in 0..cap {
			Bandwidth::force_credit(
				RuntimeOrigin::root(),
				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().remaining_bytes, 1, "oldest is index 1");

		// One more push: evicts the oldest, appends the new one.
		Bandwidth::force_credit(
			RuntimeOrigin::root(),
			ForceCreditParams {
				app_chain: APP_CHAIN,
				app: app_key(),
				tier: TIER1,
				bytes: cap + 1,
				duration_secs: MONTH_SECS,
			},
		)
		.unwrap();

		assert_eq!(sub_count(APP_CHAIN), cap as usize, "still capped");
		assert_eq!(
			sub_at(APP_CHAIN, 0).unwrap().remaining_bytes,
			2,
			"former second-oldest is now front",
		);
		assert_eq!(
			sub_at(APP_CHAIN, (cap - 1) as usize).unwrap().remaining_bytes,
			cap + 1,
			"new sub is at the back",
		);
	});
}
