Audit Report

## Title
NULL pointer dereference in Vault node-side `PublicKeyGet` handler due to missing params nil-check - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` routes `vaulttypes.MethodPublicKeyGet` directly to `handlePublicKeyGet` [1](#0-0) , bypassing `GatewayVaultRequestProcessor.ProcessRequest`, the component that validates `req.Params != nil` for every other Vault method [2](#0-1) . `handlePublicKeyGet` unmarshals `*req.Params` unconditionally [3](#0-2) , so a request with `Params == nil` panics on the nil-pointer dereference.

## Finding Description
The dispatch switch in `HandleGatewayMessage` sends `MethodPublicKeyGet` straight to `h.handlePublicKeyGet(ctx, gatewayID, req)`, unlike `MethodSecretsCreate`/`Update`/`Delete`/`List`, which go through `h.requestProcessor.ProcessRequest` first [4](#0-3) . Each of those four processor methods explicitly checks `if req.Params == nil { return ... }` before touching `*req.Params` [5](#0-4) [6](#0-5) . `processRequest`'s method switch has no case for `MethodPublicKeyGet`, confirming it was never meant to flow through this gate [7](#0-6) . `handlePublicKeyGet` itself has no such guard, calling `json.Unmarshal(*req.Params, r)` directly, which dereferences a nil `*json.RawMessage` and panics if `Params` is nil [3](#0-2) .

Critically, I traced the full path from an unprivileged external client through the gateway to confirm reachability, and the claim holds up:

1. The gateway's public-facing handler (`core/services/gateway/handlers/vault/handler.go`) explicitly special-cases `MethodPublicKeyGet` in `HandleJSONRPCUserMessage`, stating "Public key requests don't require authorization" and skipping `requestProcessor.ProcessRequest` entirely for this method [8](#0-7) .
2. When the public key is not cached, it builds an `activeRequest` from the *original user-supplied* `req` (whatever `Params` the client sent, including nil) and calls `handlePublicKeyGet` → `fanOutToVaultNodes`, which forwards `&ar.req` — the unmodified original request — to every node via `h.don.SendToNode` [9](#0-8) .
3. On the node side, `connector.go`'s `readLoop` unmarshals the wire JSON-RPC message and calls the registered handler (`GatewayHandler.HandleGatewayMessage`) directly, with no `recover()` wrapping and no params validation [10](#0-9) . I confirmed there is no `recover()` anywhere in `core/services/gateway/**` production code that would contain this panic.

So a client-supplied `vault_publicKeyGet` request with omitted/null `params` reaches the node's `handlePublicKeyGet` completely unvalidated, and panics.

## Impact Explanation
This is an unauthenticated, unprivileged denial-of-service: any client able to reach the gateway's Vault JSON-RPC endpoint can crash the goroutine handling gateway traffic on every node in the DON simultaneously (since the gateway fans the request out to all `donConfig.Members`), by sending a single malformed `vault_publicKeyGet` request with no `params`. This matches an in-scope DoS impact class and is a genuine, concrete, reproducible bug — not the theoretical/unverified scenario described in the original report. The report's own uncertainty ("this forwarding path ... was not fully verified") is resolved: the forwarding path does propagate unvalidated `Params` to nodes.

## Likelihood Explanation
High. No credentials, authorization, or special role are required — the gateway explicitly bypasses authorization for `PublicKeyGet` by design. The trigger is a single, trivially crafted JSON-RPC request (`{"jsonrpc":"2.0","id":"1","method":"vault_publicKeyGet"}` with no or null `params`) sent to the gateway's vault endpoint, which is then broadcast to all nodes in the DON, causing a repeatable, DON-wide crash of the gateway-connector read loop on each node.

## Recommendation
Add an explicit `if req.Params == nil` guard in `handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go`, returning a `UserMessageParseError` response, matching the pattern used by the other four Vault node-side processor methods. Additionally, consider adding a `recover()` in `connector.go`'s message-handling loop as defense-in-depth against any other current or future unguarded handler panics, and audit the gateway-side `handler.go` public-key path to ensure it validates the wire request shape before fanning out to nodes.

## Proof of Concept
1. Configure a local Gateway + node DON with the Vault capability enabled.
2. POST a JSON-RPC request to the gateway's Vault HTTP endpoint:
```json
{"jsonrpc":"2.0","id":"1","method":"vault_publicKeyGet"}
```
(omit `params`, or send `"params": null`), before the gateway has a cached public key (`cachedPublicKeyGetResponse == nil`).
3. Observe: gateway's `HandleJSONRPCUserMessage` skips `ProcessRequest` for `MethodPublicKeyGet`, calls `fanOutToVaultNodes`, forwarding the original request (nil `Params`) to each node via `SendToNode`.
4. On the node, `connector.go`'s `readLoop` calls `GatewayHandler.HandleGatewayMessage` → `handlePublicKeyGet` → `json.Unmarshal(*req.Params, r)` panics with a nil-pointer dereference, crashing the read-loop goroutine (and, absent a `recover()`, likely the process depending on how the goroutine is supervised).
5. A Go unit test invoking `GatewayHandler.HandleGatewayMessage` (or directly `handlePublicKeyGet`) with `req.Params = nil` reproduces the panic deterministically.
