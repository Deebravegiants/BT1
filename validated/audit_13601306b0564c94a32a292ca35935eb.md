The external report's root cause is a mutable counter (`totalSupply()`) being trusted as ground truth for accounting when it can be independently mutated (via burn) outside the code path that assumes it stays consistent. There is a structurally analogous pattern in this AMM: `amm.lp_amount` is a manually-maintained "shadow" counter of LP supply that is used as the denominator for all pro-rata pool math, but it is never reconciled with the actual SPL LP mint's `supply`, which any LP holder can independently decrease by calling `spl_token::instruction::burn` directly (bypassing the `Withdraw` instruction entirely, since burning only requires the token-account owner's signature, not the AMM program).

### Title
Divergence between `amm.lp_amount` and the real LP mint supply permanently misprices deposits/withdrawals, freezing pool funds - (File: program/src/processor.rs)

### Summary
`AmmInfo.lp_amount` is used everywhere as the "total LP supply" denominator for both `Deposit` and `Withdraw` pro‑rata math, instead of reading the SPL LP mint's actual `supply`. Any LP holder can burn their own LP tokens directly via the SPL Token program (no permission from the AMM is required, and the LP mint has no freeze authority), which decreases the mint's real `supply` without decreasing `amm.lp_amount`. This causes `amm.lp_amount` to drift permanently above the true circulating LP supply.

### Finding Description
`process_deposit` and `process_withdraw` both size the user's coin/pc share strictly from `amm.lp_amount`, a field maintained only by the program itself (incremented in deposit, decremented in withdraw): [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

Withdraw only ever bounds `withdraw.amount` against `lp_mint.supply` and `amm.lp_amount`, it never checks that the two are equal or reconciles them: [5](#0-4) 

At init, both values start equal (`amm.lp_amount` mirrors the freshly minted LP supply): [6](#0-5) 

Because the LP mint's `freeze_authority` is required to be `None` and only `mint_authority` (the AMM PDA) gates minting — not burning — any LP token holder can call `spl_token::instruction::burn` on their own LP token account, outside of `Withdraw`, at any time. This is exactly analogous to the reported bug class: a value assumed to only move through one controlled code path (`totalSupply()` / `amm.lp_amount`) is actually externally mutable (`burn` by any NFT/token holder), and the program keeps trusting its stale/incorrect internal copy for critical accounting.

### Impact Explanation
Once `amm.lp_amount` > actual `lp_mint.supply` (achieved by any single LP holder directly burning some of their own LP tokens instead of calling `Withdraw`), every subsequent `Deposit` and `Withdraw` uses an inflated denominator:
- New depositors receive fewer LP tokens than their contribution is worth (`exchange_token_to_pool` uses the inflated `amm.lp_amount`), permanently diluting them relative to true pool value.
- All withdrawers, including the original burner's remaining balance and all pre-existing/future LP holders, receive proportionally less coin/pc than their real share of the pool (`exchange_pool_to_token` also divides by the inflated `amm.lp_amount`).

The result is that a portion of the pool's coin/pc reserves becomes permanently unclaimable by any LP holder — a real loss/freezing of LP funds, and the pool's internal accounting becomes insolvent relative to its true backing ratio (the pool always retains a residual balance nobody can withdraw, growing with each direct burn).

### Likelihood Explanation
This requires no privileged access: any unprivileged LP holder who owns an LP token account can independently invoke the SPL Token `Burn` instruction on their own tokens at any time — this is standard, always-available functionality for any SPL token holder and cannot be blocked by the AMM program. It only takes one such burn transaction to permanently desynchronize `amm.lp_amount` from `lp_mint.supply`, after which the mispricing affects every subsequent `Deposit`/`Withdraw` call from any user.

### Recommendation
Do not maintain a separate manually-tracked `lp_amount` counter as the source of truth for pro-rata math. Read the LP mint's `supply` field directly (as already unpacked via `Self::unpack_mint(&amm_lp_mint_info, ...)`) at the time of each `Deposit`/`Withdraw`, and use that value as the denominator for `InvariantPool` calculations, ensuring `amm.lp_amount` (if kept for informational purposes) is validated against `lp_mint.supply` before being trusted in any calculation, or removed in favor of the authoritative on-chain mint state.

### Proof of Concept
1. Pool is initialized; `amm.lp_amount` == `lp_mint.supply` == S (both track the initial minted liquidity).
2. Any LP holder Alice (owns an ATA holding LP tokens) issues a standalone transaction calling `spl_token::instruction::burn` on her own LP token account for amount `B`, signed only by herself — this does not touch the Raydium AMM program at all.
3. Now `lp_mint.supply == S - B`, but `amm.lp_amount` is still `S` (unchanged, since only `process_withdraw` decrements it).
4. Any user then calls `Withdraw` with `amount == W`: `coin_amount`/`pc_amount` are computed via `InvariantPool{ token_input: W, token_total: amm.lp_amount == S }` against `total_coin_without_take_pnl`/`total_pc_without_take_pnl` — i.e., divided by `S` instead of the true `S - B`, understating the payout for every withdrawer from that point on, permanently trapping the difference in the vaults.
