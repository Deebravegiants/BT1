### Title
Beneficiary-redirect signature in `pallet-ismp-relayer::accumulate_fees` omits the commitment set and fee amount, letting anyone pair a captured signature with an unintended withdrawal batch - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`accumulate_fees` is an **unsigned, permissionless** extrinsic (`ensure_none(origin)` in `claim_outbound_request_delivery_reward`'s sibling call, `Call::accumulate_fees`) that lets anyone submit a `WithdrawalProof` on behalf of a relayer to redirect that relayer's accrued fees to a chosen `beneficiary_address`. The redirect is authorized by a relayer-signed message, but that message only binds `(nonce, state_machine, beneficiary)` — it never binds *which* request commitments or *how much* fee is being redirected. Anyone who observes a relayer's beneficiary-redirect signature (public unsigned-extrinsic mempool, or a previously included/failed transaction) can resubmit it packaged with a different, self-chosen `WithdrawalProof.commitments` set, causing an amount and commitment set the signer never authorized to be swept to the named beneficiary and the relayer's own nonce to be consumed.

### Finding Description
`Pallet::accumulate` (`modules/pallets/relayer/src/accumulate.rs:48-170`) verifies a `WithdrawalProof` (arbitrary, attacker-suppliable `commitments: Vec<H256>`, source/dest state proofs) and computes `(delivery_address, total_fee)` purely from the state proofs [1](#0-0) .

If the caller wants the fee sent somewhere other than `delivery_address`, they attach `beneficiary_details: Option<(beneficiary_address, signature)>`. The signature is checked against:

```rust
let msg = beneficiary_message(nonce, state_machine, &beneficiary_address);
``` [2](#0-1) 

and
```rust
pub fn beneficiary_message(nonce: u64, state_machine: StateMachine, beneficiary: &[u8]) -> [u8; 32] {
	sp_io::hashing::keccak_256(&(nonce, state_machine, beneficiary).encode())
}
``` [3](#0-2) 

This signed payload covers only the per-`(delivery_address, state_machine)` `nonce`, the `state_machine`, and the `beneficiary` — it does **not** cover `withdrawal_proof.commitments` or the resulting `total_fee`. Those two values are instead supplied unsigned by whoever submits the extrinsic and are only constrained by "must be real, unclaimed commitments this relayer actually delivered" (proven by the accompanying state proofs), not by anything the relayer signed. Since `accumulate_fees` is dispatched via `ensure_none` and validated in `validate_unsigned`, no authentication of the submitter is required at all [4](#0-3) .

Consequence: a relayer signs a beneficiary redirect intending to move a specific, small batch of accrued fees (say, fees from commitments A, B) to `beneficiary`. That signature is bound only to `(nonce, state_machine, beneficiary)`. Anyone who sees this signature (the unsigned extrinsic sits in the public transaction pool before inclusion, exactly the "mempool front-running" attack path in the source report) can submit their own `accumulate_fees` call reusing the identical signature but substituting a different `commitments` vector — e.g. every currently unclaimed commitment delivered by that same relayer on that `state_machine` — as long as it is submitted before the relayer's own transaction (same nonce, so only one can land). The pallet has no way to detect this: it verifies only that the signature matches `(nonce, state_machine, beneficiary)`, then trusts the submitter's `commitments`/`total_fee` for the redirect and increments the nonce, permanently invalidating the relayer's original narrower authorization [5](#0-4) .

### Impact Explanation
This is the direct analog of the referenced bug class: a signature that authenticates *who* (beneficiary, on which chain, with which nonce) but not *what* (which fees, how much), letting an unprivileged party couple a legitimate signature with malicious/arbitrary batch parameters. Concretely:
- An attacker can front-run a relayer's intended small beneficiary redirect and instead sweep the relayer's *entire currently claimable fee balance* on that state machine to the signed beneficiary, forcing an unintended, larger-than-authorized transfer.
- Because the nonce is burned by whichever `commitments` set lands first, the relayer's actually-intended transaction becomes permanently invalid (nonce mismatch), a denial-of-service on the relayer's fee-redirection workflow — mirroring the "user forced into unintended parameters / DoS" impact called out in the source report.
- This does not enable outright theft to a third party (the beneficiary is still whatever the relayer signed), but it does let an unprivileged submitter dictate the amount and commitment set redirected under someone else's signature, which is an unauthorized state mutation of accrued-fee accounting driven by unsigned parameters — a Medium-severity issue in fee/reward accounting reachable from a single submitted extrinsic.

### Likelihood Explanation
`accumulate_fees` extrinsics are unsigned and sit in the public transaction pool prior to inclusion, exactly like the ERC-4337 mempool scenario in the source report; any observer can extract `(beneficiary_address, signature)` from a pending/broadcast call and resubmit it with a rebuilt `WithdrawalProof` (still requiring valid, verifiable state proofs of real deliveries by that relayer, which are also public/derivable) ahead of the original. No special privilege, insider access, or governance/validator compromise is needed — only visibility into pending or historical unsigned extrinsics and the ability to construct a state proof, both routinely available to any relayer/node operator.

### Recommendation
Include the authorized scope of the redirect in the signed payload — e.g. bind `beneficiary_message` to a commitment set (or its hash) and/or an explicit maximum amount, not just `(nonce, state_machine, beneficiary)`:
```rust
sp_io::hashing::keccak_256(&(nonce, state_machine, beneficiary, commitments_hash, max_amount).encode())
```
and verify that the actually-computed `total_fee`/`commitments` match what was signed before applying the redirect.

### Proof of Concept
1. Relayer `R` accrues fees from delivering commitments `{A, B}` on `state_machine = S`. `R` wants to redirect only these to `beneficiary = X`, so it signs `beneficiary_message(nonce=n, S, X)` and submits `accumulate_fees(WithdrawalProof{ commitments: [A, B], ..., beneficiary_details: Some((X, sig)) })` as an unsigned extrinsic.
2. While this extrinsic is pending in the pool (unsigned extrinsics broadcast publicly before inclusion), an observer `M` extracts `(X, sig)`.
3. `M` independently builds a valid `WithdrawalProof` proving `R` also delivered unclaimed commitments `{C, D, E, ...}` (all real, provable, unclaimed deliveries by `R` on `S`), and submits `accumulate_fees(WithdrawalProof{ commitments: [C, D, E, ...], ..., beneficiary_details: Some((X, sig)) })` using the same captured `sig`.
4. Because `beneficiary_message` only commits to `(n, S, X)`, `M`'s call passes signature verification identically to `R`'s intended call. Whichever lands first consumes nonce `n`; if `M`'s lands first, `R`'s full `{C, D, E, ...}` batch (potentially far larger than `{A, B}`) is redirected to `X`, and `R`'s own original `{A, B}` transaction now fails with a stale nonce.
