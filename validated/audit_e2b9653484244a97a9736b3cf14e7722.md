### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant impersonation - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` for a webhook exclusively from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the bytes that `Utils::HmacValidator` verifies. Only the raw request body is HMAC-authenticated. Any party who can obtain one valid `(body, hmac)` pair signed with the app's `api_secret_key` — which is trivially available to anyone who installs the (public) app on their own store — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and `ShopifyAPI::Webhooks::Registry.process` will accept it as an authentic webhook for the victim shop.

### Finding Description
The binding that should hold is:
`shop asserted to the handler == shop that the api_secret_key–holder actually intended to authenticate`

`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the signed body: [2](#0-1) 

`Utils::HmacValidator.validate` / `validate_signature` computes the HMAC only over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header — it never incorporates `shop`, `topic`, or `webhook_id`: [3](#0-2) 

`Webhooks::Registry.process` gates entirely on this body-only HMAC check, then forwards the unauthenticated `request.shop` straight to the app's handler as the tenant identifier: [4](#0-3) 

Crucially, `api_secret_key` is a single app-level secret shared across every shop that installs the app — it is not per-tenant. So a signature computed with that secret for a body sent to Shop A's webhook is byte-for-byte identical to what would be computed for the same body "belonging" to Shop B; the signature carries no shop identity at all. The `shop` value is 100% attacker-controlled header data once a valid `(body, hmac)` pair is obtained.

### Impact Explanation
This breaks the tenant boundary the library is supposed to enforce: `request.shop` is treated by `Registry.process` (and consequently by any `WebhookHandler` built on this gem, via `WebhookMetadata.shop`) as an authenticated identity even though it is unauthenticated header data. An attacker can:
1. Install the (public) target app on their own, attacker-controlled store — an ordinary, unprivileged action requiring no special access.
2. Trigger a webhook delivery to capture a valid `(raw_body, X-Shopify-Hmac-Sha256)` pair signed with the app's shared `api_secret_key`.
3. Replay that exact body/HMAC to the app's webhook endpoint while changing the `X-Shopify-Shop-Domain` header to a victim shop's domain.
4. `Utils::HmacValidator.validate` still returns `true` (the body/HMAC pair is valid), and `Registry.process` invokes the handler with `shop: <victim shop>`.

Any downstream logic that uses the webhook's `shop` value to look up records, scope data, or make decisions per-tenant (which is the entire purpose of exposing `shop` on `WebhookMetadata`) can be tricked into acting on/for the victim shop — a cross-tenant access primitive, satisfying the Critical impact bar (cross-tenant access) defined in scope.

### Likelihood Explanation
High. No credentials, access tokens, or the app's `client_secret` need to be stolen. The only prerequisite is the ability to install a copy of the target (typically public) app on any store — a routine, unprivileged action — and the ability to send arbitrary HTTP requests to the app's public webhook endpoint. Both are available to any unprivileged internet user targeting a public embedded Shopify app built on this gem.

### Recommendation
Do not derive the trusted `shop` identity for a webhook from an unauthenticated header. Options:
- Fold `shop`, `topic`, and `webhook_id` into the HMAC-signed material (not possible unilaterally since Shopify controls what it signs), or
- More practically: require app code to cross-check `request.shop` against a shop that is independently known to have that specific webhook registered/expected (e.g., correlate with `webhook_id` returned from `Registry.register`), and document clearly that `Webhooks::Request#shop` is NOT cryptographically authenticated by `HmacValidator.validate` — only the body is.
- At minimum, update documentation/API so `shop` is not presented alongside “verified” webhook data without a loud warning that it is unauthenticated header input, and provide a supported mechanism (e.g., an allow-list check against previously registered shops) inside `Registry.process` before dispatching to handlers.

### Proof of Concept
```ruby
# Attacker installs the target app on their own shop "attacker-shop.myshopify.com"
# and captures a real webhook delivery:
raw_body = '{"id":123,"note":"legit order"}'
valid_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
)

# Attacker now replays the SAME body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to the victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,        # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/HMAC unchanged),
#    handler is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
```
This demonstrates that `Registry.process` accepts an attacker-chosen `shop` value as long as the attacker can supply *any* valid `(body, hmac)` pair for the app — which they can trivially obtain by installing the app themselves.
