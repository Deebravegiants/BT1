### Title
Missing minimum-liquidity guard before `pair.mint` in graduation seeding can permanently brick `finalizeGraduation` — ([File: packages/contracts/src/Bonding.sol])

### Summary
The Wormhole fix guards a heartbeat-processing code path against a `nil` value (`gk *ecdsa.PublicKey`) that the code implicitly assumed was always non-null, which would otherwise crash the node when dereferenced. The analogous root cause in alt.fun is that `Bonding._prepareGraduationLiquidity` / `_seedDirectMint` compute `tokensForLP` and `ltFromPair` and pass them straight into `IUniswapV2Pair.mint` with no floor check ensuring the product is large enough for a V2 pair's mandatory `MINIMUM_LIQUIDITY` burn on first mint. If that assumption is ever violated, the external HyperSwap V2 pair's `mint` reverts on arithmetic underflow, and — because `finalizeGraduation`'s inputs are cached once in phase 1 and recomputed byte-identically on every retry — the token is permanently stuck in `Lifecycle.Graduating` with its curve-raised LT and the 250M `LP_RESERVE` tokens parked in `Bonding` forever.

### Finding Description
`_prepareGraduationLiquidity` computes the LP-bound amounts with no lower bound other than the trivial `assetReserve == 0 ? 0 : ...` guard: [1](#0-0) 

These values (`tokensForLP`, `ltFromPair`) are cached verbatim in `pendingGraduation` at phase 1 and consumed unmodified by phase 2: [2](#0-1) 

In the (overwhelmingly common, ~99% per the code's own comment) empty-pair regime, `_seedDirectMint` transfers exactly `(tokensForLP, ltFromPair)` to the pair and calls `pair.mint(lpLock)` directly, with no check that the pair's own first-mint invariant (`liquidity = sqrt(amount0*amount1) - MINIMUM_LIQUIDITY`, standard UniswapV2) can succeed: [3](#0-2) 

Nowhere in `_prepareGraduationLiquidity`, `_enterGraduating`, `canGraduate`, or `_seedDirectMint` is there a floor ensuring `sqrt(tokensForLP * ltFromPair) > MINIMUM_LIQUIDITY` (1000 wei on a standard V2 pair). The code elsewhere is careful to defend `finalizeGraduation` against *attacker*-induced zero-liquidity outcomes — see the `_swapBudget` 99%-reservation comment explicitly reasoning about `liquidity == 0` bricking `LPLock.recordLock`: [4](#0-3) 

But that defense only covers the *rebalance* regime (regime 3, hostile mint pre-seed) via `_pairRebalance`'s budget cap; it does nothing to bound the *magnitude* of `tokensForLP`/`ltFromPair` themselves in the direct-mint regime that every honest graduation takes. If a token launches against a low-value LT / low `graduationThresholdUsd` combination such that the real LT raised by the curve (`ltFromPair`) and its paired `tokensForLP` are individually non-zero but their product's square root falls at or below `MINIMUM_LIQUIDITY`, `pair.mint` underflows and reverts on every call, including every future retry, because `_prepareGraduationLiquidity`'s cached values never change once frozen in `Lifecycle.Graduating`.

This is the same bug class as the external report: code that dereferences/consumes a value (`gk`, or here `tokensForLP`/`ltFromPair`) under the unstated assumption that it will never be degenerate, causing a hard crash/revert deep in a critical path instead of a graceful, checked failure.

### Impact Explanation
If `finalizeGraduation` reverts unconditionally for a token, that token is permanently frozen in `Lifecycle.Graduating`:
- All curve-raised LT already drained via `Router.graduate` in phase 1 sits unrecoverable inside `Bonding` (no owner-rescue path is documented for LT parked mid-graduation).
- The 250M `LP_RESERVE` tokens (`Token.TOTAL_SUPPLY() * 25%`) held by `Bonding` for this token are permanently unusable.
- Trading is frozen (`Lifecycle.Graduating` blocks `Bonding.buy`/`sell`), so holders can never exit and the creator can never claim further fees tied to the token's post-graduation venue.

This is a permanent freeze of trader, creator, and protocol funds tied to that token — squarely a High-severity outcome under the validation rubric.

### Likelihood Explanation
This requires a specific launch configuration (a low-value reserve LT and/or a low `graduationThresholdUsd` relative to `LP_RESERVE`/token decimals) that yields `ltFromPair` and/or `tokensForLP` small enough that `sqrt(tokensForLP * ltFromPair) ≤ MINIMUM_LIQUIDITY`. Given `graduationThresholdUsd` and LT parameters are protocol-configured (not attacker-controlled) this is more of a configuration/edge-case risk than an attacker-triggerable one on a well-tuned deployment, but it is directly reachable by any unprivileged trader simply pushing a token through the normal buy flow that crosses either graduation trigger — no privileged action is needed to *trigger* the revert, only specific (plausible) protocol parameters to make the amounts fall below the V2 floor.

### Recommendation
Add an explicit floor check in `_prepareGraduationLiquidity` (or immediately before `pair.mint` in `_seedDirectMint`) verifying `Math.sqrt(tokensForLP * ltFromPair) > MINIMUM_LIQUIDITY` before allowing `_enterGraduating`/`finalizeGraduation` to proceed with the direct-mint path, and fail closed with a named error (rather than relying on the pair's own underflow) or make graduation configuration (`graduationThresholdUsd` vs. `LP_RESERVE`/decimals) provably bounded away from this floor at deploy time.

### Proof of Concept
Not independently reproduced against live `MockHyperswapPair`/HyperSwap V2 bytecode within this review; the finding is derived from static analysis of `_prepareGraduationLiquidity` (packages/contracts/src/Bonding.sol:1073-1096) and `_seedDirectMint` (packages/contracts/src/Bonding.sol:1245-1259) showing no lower-bound check on `tokensForLP`/`ltFromPair` before they are consumed by `IUniswapV2Pair.mint`, contrasted with the codebase's own acknowledged concern about `liquidity == 0` bricking `LPLock.recordLock` (packages/contracts/src/Bonding.sol:1356-1378) which is handled only for the rebalance-regime path, not the direct-mint majority path. A concrete underflow trigger would require constructing a launch with a `graduationThresholdUsd`/LT-exchangeRate/token-decimals combination driving `ltFromPair`/`tokensForLP` below the V2 `MINIMUM_LIQUIDITY` floor and asserting `finalizeGraduation` reverts irrecoverably — recommend a Devin session with full repo/test access to confirm exact numeric parameters (`graduationThresholdUsd`, `LP_RESERVE`, `MockHyperswapPair.MINIMUM_LIQUIDITY`) reproduce the revert.

        // `_routerDepositAndDispose` and `_sweepLTToOwner`.

        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair
    ) internal returns (uint256 liquidity) {
        IERC20(tokenAddress).safeTransfer(pair, tokensForLP);
        IERC20(lt).safeTransfer(pair, ltFromPair);

    /// @dev Cap the rebalance swap at 99% of the available side's budget,
    ///      so the subsequent `addLiquidity` always has a non-zero amount
    ///      of BOTH sides to deposit. Without this, an extreme hostile
    ///      pre-seed (massively imbalanced reserves) drives the
    ///      unconstrained `_noFeeSwapInput` past our per-side budget,
    ///      `_pairRebalance` clamps to the full budget, and the swap
    ///      consumes 100% of one side. `_routerDepositAndDispose` then
    ///      skips `addLiquidity` (`remToken == 0` or `remLT == 0`),
    ///      `finalizeGraduation` returns `liquidity = 0`, and
    ///      `LPLock.recordLock(...)` records a zero-sized lock — the
    ///      attacker's pre-existing LP becomes 100% of the pool. Reserving
    ///      1% guarantees the deposit leg always lands AND mints non-zero
    ///      LP at the post-swap ratio. The 1% comes off the swap, not the
    ///      deposit — for any realistic pre-seed `s_unconstrained` is
    ///      orders of magnitude below `maxSwap`, so the cap doesn't bind
    ///      and behaviour is unchanged. It only kicks in for catastrophic
    ///      pre-seeds beyond our budget capacity, where the alternative
    ///      is bricking.
    function _swapBudget(
        uint256 budget
    ) internal pure returns (uint256) {
        return (budget * 99) / 100;
    }
