### Title
Front-runnable pool-account PDAs allow permanent freezing of `Initialize2` pool creation for a targeted market - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives all of a pool's core accounts (AMM state account, LP mint, coin/pc vaults, target orders) as PDAs seeded only by `program_id` and the raw `market_info.key` — a value the code itself documents as "Just a seed for AMM account. Can be any account." Because there is no check binding `market_info` to a real OpenBook/Serum market or to the supplied `coin_mint`/`pc_mint`, an attacker can call `Initialize2` first, using any two throw-away SPL mints, but supplying the pubkey of a market that a legitimate project intends to use. This permanently claims (assigns ownership away from the System Program) the deterministic PDAs tied to that market pubkey, causing all future legitimate `Initialize2` calls for that same market to revert with `AmmError::RepeatCreateAmm`.

### Finding Description
`get_associated_address_and_bump_seed` derives the LP mint, coin vault, pc vault, target-orders, and AMM account addresses solely from `program_id.to_bytes()`, `market_address.to_bytes()`, and a fixed `associated_seed` constant (`LP_MINT_ASSOCIATED_SEED`, `COIN_VAULT_ASSOCIATED_SEED`, `PC_VAULT_ASSOCIATED_SEED`, `TARGET_ASSOCIATED_SEED`, `AMM_ASSOCIATED_SEED`): [1](#0-0) 

Inside `generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint`/`generate_amm_associated_account`, if the derived account is not currently owned by the System Program, the call fails with `AmmError::RepeatCreateAmm` instead of proceeding: [2](#0-1) [3](#0-2) 

Critically, `process_initialize2` explicitly treats `market_info` as an arbitrary seed value with no ownership or content validation: [4](#0-3) [5](#0-4) 

Only `coin_mint != pc_mint` is checked, and the mints are unpacked as valid SPL mints, but nothing ties `market_info` to those mints or to a real order book: [6](#0-5) [7](#0-6) 

Because the vault/mint/target-orders/AMM PDAs depend only on `market_info.key` (not on the mints), an attacker who knows (or predicts) the pubkey of a market that a project intends to launch a pool for can call `Initialize2` first with `market_info = <target market>` and arbitrary cheap/self-created mints and minimal `init_coin_amount`/`init_pc_amount`. This succeeds and permanently assigns those five PDAs to the AMM program (owner != System Program), exactly analogous to the referenced `Registry.register` front-running bug where an attacker pre-registers a deterministic address to force all subsequent legitimate calls to revert.

### Impact Explanation
Once the attacker's junk pool occupies the PDAs derived from a given market pubkey, no legitimate `Initialize2` call using that market can ever succeed — every attempt hits the `owner == system_program_account.key` check and returns `AmmError::RepeatCreateAmm` for the LP mint / vaults / target-orders / AMM account (`generate_amm_associated_spl_token`, `generate_amm_associated_spl_mint`, `generate_amm_associated_account`). This permanently freezes the ability to create a standard Raydium AMM pool for that market — a denial-of-service on the pool-creation factory functionality with no possible remediation (the PDAs cannot be reassigned or reset), analogous in effect and root cause to the reported `SafeGuardFactory` freezing issue.

### Likelihood Explanation
The attack requires only: creating two throw-away SPL mints, paying trivial rent for the five accounts, and submitting a single `Initialize2` transaction naming the target market's pubkey — no special privileges, no market ownership, and no large capital (minimal `init_coin_amount`/`init_pc_amount`, e.g. `1`). Any market pubkey that is publicly known ahead of a planned pool launch (which is common, since market creation and pool creation are typically separate, sequential, publicly observable transactions) is directly griefable by any unprivileged actor submitting a single transaction.

### Recommendation
Bind `market_info` to genuine market data instead of treating it as an arbitrary seed: validate that `market_info` is owned by the expected market program and that its stored base/quote mints match `amm_coin_mint_info`/`amm_pc_mint_info` before using it to derive the associated PDAs. Alternatively, derive the PDAs from a combination that includes the mints (or an explicit, checked market identity) so that squatting one market/mint pair cannot block others, and/or require that `market_info` be a genuine, uninitialized-for-AMM-use market account verified via its own program-owned state.

### Proof of Concept
1. Attacker observes (or predicts) that market `M` will be used to create the "real" Raydium pool for tokens `X`/`Y`.
2. Attacker creates two fresh SPL mints `A` and `B` (or even reuses arbitrary existing mints, as long as `A != B`), mints trivial LP/init amounts to themselves.
3. Attacker calls `Initialize2` with `market_info = M`, `amm_coin_mint = A`, `amm_pc_mint = B`, `init_coin_amount = 1`, `init_pc_amount = 1`, and account addresses for `amm_lp_mint`, `amm_coin_vault`, `amm_pc_vault`, `amm_target_orders`, `amm` correctly derived via `get_associated_address_and_bump_seed(program_id, M, <seed>, program_id)`.
4. `process_initialize2` succeeds: `generate_amm_associated_spl_token`/`_mint`/`_account` create and assign ownership of these PDAs to the AMM program (`program/src/processor.rs:317-382`, `675-835`).
5. The legitimate team later calls `Initialize2` with `market_info = M` and their real mints `X`/`Y`; the same PDAs are derived (seeds only depend on `M`), but they are already owned by the AMM program, so every associated-account creation call returns `AmmError::RepeatCreateAmm`, permanently blocking pool creation for market `M`.
