### Title
Webhook `shop` (and topic/webhook_id/api_version) fields are trusted but not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authenticated for a given shop as soon as `Utils::HmacValidator.validate(request)` succeeds. However, the HMAC is computed only over the raw request body, not over the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. An attacker who can obtain one valid `(body, hmac)` pair for a webhook delivered to their own installation of the app can replay that exact body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop, and the request still passes validation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes and compares the HMAC solely against `verifiable_query.to_signable_string`: [2](#0-1) 

`Registry.process` gates only on this HMAC check, then constructs `WebhookMetadata` directly from unauthenticated headers, including `request.shop`, `request.topic`, and `request.webhook_id`, none of which are covered by the signature: [3](#0-2) 

The `shop`, `topic`, and `webhook_id` accessors simply read the corresponding HTTP headers with no cryptographic binding to the signed body: [4](#0-3) 

The equality that should hold is: `shop_bound_by_hmac == shop_delivered_to_handler`. In this implementation, `shop_bound_by_hmac` is undefined (HMAC only binds `raw_body`), while `shop_delivered_to_handler = request.shop` (an arbitrary, attacker-controllable header). The documented API explicitly instructs consuming apps to trust `data.shop` as "The shop domain of the webhook": [5](#0-4)  — so this is the gem's own documented contract, not a misuse by the host app.

### Impact Explanation
This breaks the shop-identity binding that host applications rely on to know which tenant's data is contained in the webhook body. An attacker who operates their own installation of the app (an "unprivileged" merchant with respect to other tenants) can capture a legitimate `(raw_body, hmac)` pair delivered to their own endpoint, then POST it directly to the app's webhook controller with a forged `x-shopify-shop-domain` header pointing at a victim shop. `HmacValidator.validate` still returns `true` since only the body is checked, and `Registry.process` will invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain while `body` contains the attacker's own data. Any host application that uses `data.shop` to select which tenant's records to create/update (the documented usage pattern) will attribute attacker-controlled data to another merchant — a cross-tenant data injection/corruption, which maps to the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires the attacker to have at least one legitimate webhook delivery to an app installation they control (trivial for any developer/merchant who installs the app on their own store) and the ability to send arbitrary HTTP requests to the app's public webhook endpoint (no privileged credentials needed). No secret material is required since the HMAC/body pair is reused unmodified. Likelihood is Medium: it requires the app owner to have a multi-tenant webhook handler that trusts `data.shop`, but the gem's own documentation encourages exactly that usage.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is authenticated, or independently verify that the `shop-domain` header corresponds to a shop with a currently valid/known session or app installation before dispatching to the handler, rather than trusting a header that sits outside the HMAC-signed payload. At minimum, document prominently that `data.shop` is unauthenticated and must be independently cross-checked by the consuming application before being used to select tenant-scoped resources.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) that is delivered to the app's endpoint with a body `B` and a valid `x-shopify-hmac-sha256` header `H` (computed by Shopify using the app's `client_secret` over `B`).
2. Attacker captures `B` and `H` (e.g., via their own server logs, since it was delivered to their own endpoint).
3. Attacker sends a new HTTP POST directly to the app's public webhook URL with:
   - body: `B` (unchanged)
   - header `x-shopify-hmac-sha256`: `H` (unchanged)
   - header `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - header `x-shopify-topic`: unchanged/any registered topic
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` parses successfully (all required headers present) [6](#0-5) .
5. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it validates `H` against `B` only, ignoring the shop header [7](#0-6) .
6. The registered handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: <attacker's parsed body>, ...)`, causing the host app to process attacker-controlled data under the victim's tenant identity.

```ruby
      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
```
