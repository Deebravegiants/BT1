### Title
Storage-Deposit Cache Key Collision Enables Cross-Account Storage-Check Poisoning, Causing Withdrawals to Stuck On-Chain - ([File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts])

### Summary
`DirectBridge` caches the NEP-141 storage-deposit sufficiency check per `(contractId, accountId)` pair using an unseparated string concatenation as the cache key: `` `${contractId}${accountId}` ``. Because both `contractId` (derived from the caller-supplied `assetId`) and `accountId` (the caller-supplied `destinationAddress`) are attacker-influenceable strings with no fixed length or delimiter, two distinct `(contractId, accountId)` pairs can be crafted to produce an identical concatenated key. This lets a "sufficient storage" result cached for one pair be served — via the shared, long-lived `LRUCache` instance on the bridge object — to a different pair, silently skipping the storage-deposit fee/allocation for a withdrawal whose real destination account actually lacks a registered storage balance on the real token.

This is called from `estimateWithdrawalFee` with the token's `contractId` and the caller-supplied `withdrawalParams.destinationAddress`: [2](#0-1) 

Both inputs are effectively caller-controlled strings of variable length (any supported NEP-141 `contractId`, plus an arbitrary NEAR account name/implicit account for `destinationAddress`). Because the key is `contractId + accountId` with no separator, two different pairs `(A, B)` and `(A', B')` where `A + B === A' + B'` collide to the same cache entry. Since the `storageDepositCache` (`LRUCache`, `ttl: 3600000` = 1 hour) is a field on the `DirectBridge` instance rather than scoped per call, and SDK bridge instances are typically long-lived within a host application/service that serves many independent withdrawal requests, an entry primed by one withdrawal request (real, "sufficient storage" outcome, which is the only outcome cached per line 295-297) can be returned for a later, unrelated request whose real `(contractId, accountId)` pair happens to produce the same concatenated string.

This mirrors the report's root-cause pattern: a predictable/ambiguous identifier used for state lookup (`ng-state` / here, the naive concatenated cache key) allows an unintended entity to be substituted for the genuine one, and the substituted (attacker-influenced) state is then trusted and acted upon without re-validation — i.e., the equality "the storage-sufficiency result returned belongs to the exact `(token, destination account)` pair queried" is broken.

### Impact Explanation
When the collision causes a false "sufficient storage" result to be returned for a withdrawal whose real destination account does **not** actually have a registered/sufficient NEP-141 storage balance on the real target token:
- `estimateWithdrawalFee` returns `storageDepositFee: 0n` and omits `feeAmount`/quote for the storage deposit, even though the real destination truly needs a storage deposit (line 231-241, 259-267).
- `createWithdrawalIntents` then builds the withdrawal intent without a `storageDeposit` allocation, since it is derived directly from the (wrong) fee estimation (`getUnderlyingFee(...,"storageDepositFee")`, line 137-141).
- When this intent executes, the underlying NEP-141 `ft_transfer`/`ft_transfer_call` to the destination account fails on-chain because the account is not storage-registered on that token, leaving the withdrawal in a failed/incomplete state that requires manual intervention to resolve or refund.

This matches the "High" impact bucket: *a withdrawal stuck until manual intervention* caused by a fee/allocation computed from data belonging to the wrong (contractId, accountId) pair rather than the one actually validated.

### Likelihood Explanation
Exploitability depends on: (1) the `DirectBridge` (or SDK) instance being reused/shared across multiple independent withdrawal requests (a common integration pattern for a backend service using this SDK), and (2) an attacker being able to engineer a `contractId`/`accountId` string pair that collides with a real, already-cached "sufficient" entry for a different pair used by another caller/withdrawal. Because `contractId` is restricted to the set of supported NEP-141 token ids and `accountId` must be a valid/existing NEAR account (enforced elsewhere in `validateWithdrawal`), engineering an exact concatenation collision against an *unknown* victim's specific token+destination pair is difficult in the general case, though trivially constructible when the attacker controls (or can predict) both sides of the collision (e.g., re-priming the cache for their own future request using a differently-split but identically-concatenated pair). This lowers likelihood from the base DOM-clobbering scenario (browser-enforced global uniqueness of a predictable ID) to a narrower, but still concretely reachable, path via the unseparated key construction itself, which is unambiguously a bug independent of exploitation difficulty.

### Recommendation
Use a delimiter-safe, unambiguous cache key, e.g. `` `${contractId}\u0000${accountId}` `` or a structured `Map` keyed by a tuple/JSON-encoded pair with fixed field boundaries, so that no two distinct `(contractId, accountId)` inputs can ever produce the same cache key. Apply the same fix to any other bridge caches built via naive string concatenation of multiple caller-influenced fields.

### Proof of Concept
1. Attacker (or an unrelated legitimate flow) triggers `estimateWithdrawalFee` for `(contractId = "usdc.near", destinationAddress = "bob.near")` where `bob.near` genuinely has sufficient storage on `usdc.near`. This primes `storageDepositCache` at key `"usdc.nearbob.near"` with a "sufficient" result (line 295-297).
2. A second withdrawal request is made with `(contractId = "usdc.nearb", destinationAddress = "ob.near")` — a different token/account pair whose concatenation is identical: `"usdc.nearb" + "ob.near" === "usdc.nearbob.near"`.
3. `getCachedStorageDepositValue` computes the same key and returns the cached "sufficient" tuple from step 1 without querying the real storage balance for `("usdc.nearb", "ob.near")`.
4. `estimateWithdrawalFee` reports `storageDepositFee: 0n`; the resulting withdrawal intent omits the needed storage deposit for the real `(contractId, accountId)` pair.
5. On execution, the NEP-141 transfer to `ob.near` on `usdc.nearb` fails due to missing storage registration, leaving the withdrawal stuck pending manual remediation.

	): Promise<[MinStorageBalance, StorageDepositBalance]> {
