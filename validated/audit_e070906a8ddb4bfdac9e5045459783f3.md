### Title
`Webhooks::Registry.process`/`add_registration` dispatch trusts unsigned `shopify-topic` and `shopify-shop-domain` headers, which are outside the HMAC signable string - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`Webhooks::Registry.process` validates only the raw request body against the HMAC, then uses the unsigned `shopify-topic` and `shopify-shop-domain` headers to select the handler and to populate `WebhookMetadata#shop`. Because `Webhooks::Request#to_signable_string` returns only `@raw_body`, an attacker who obtains any genuinely-signed webhook body (e.g., from their own dev shop) can replay it with forged `topic`/`shop` headers and have it processed as if it came from a different topic/shop, since the signature check does not cover those headers.

### Finding Description
The invariant that should hold is: `to_signable_string(request) == every value the handler acts on`. In practice:

- `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) .
- `topic` and `shop` are read straight from the (unsigned) `shopify-topic` / `shopify-shop-domain` headers [2](#0-1) .
- `HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received HMAC — this only proves the body bytes are untampered, it says nothing about the headers [3](#0-2) .
- `Registry.process` uses exactly those unsigned values for authorization-relevant decisions: `@registry[request.topic]&.handler` selects which handler code runs, and `request.shop` is passed straight into `WebhookMetadata#shop` given to the handler [4](#0-3) .

So the two sides of the equality diverge: the signature only binds `raw_body`; the app trusts `topic` and `shop` (headers) as if they were signed. `add_registration` is the mechanism that populates `@registry` keyed by `topic` [5](#0-4) , so `Registry.process`'s topic-based lookup is exactly the dispatch surface described.

Exploit flow: an attacker registers their own app installation on a shop they control, and receives a legitimately HMAC-signed webhook body (signed by Shopify with the real `api_secret_key`) for some topic. The attacker then replays that exact raw body to the target app's webhook endpoint but swaps the `X-Shopify-Topic` and `X-Shopify-Shop-Domain` headers to whatever topic/shop they want. `HmacValidator.validate` still succeeds because it only re-hashes `raw_body`, which the attacker did not alter. `Registry.process` then dispatches to the handler registered for the forged topic and hands it a `WebhookMetadata` whose `shop` field is the attacker-chosen (unsigned) value.

None of the existing guards catch this: `HmacValidator.validate` checks body integrity only [6](#0-5) ; there is no secondary check anywhere in `Registry` or `Request` that the header-derived `topic`/`shop` match anything inside the signed payload; Sorbet typing only enforces types (`String`), not provenance.

### Impact Explanation
This lets an unprivileged attacker with any one validly-signed webhook body (obtainable from their own shop's real webhook traffic) cause the app to invoke an arbitrary registered handler (e.g., `customers/data_request`, `shop/redact`, `app/uninstalled`) with an attacker-chosen `shop` value passed to that handler as though it were authenticated. If a handler uses `WebhookMetadata#shop` to identify the tenant (e.g., to look up/delete a session, purge data, or take an action scoped by shop) without independently re-validating that shop against the signed body content, the attacker can trigger tenant-scoped actions attributed to a shop domain they do not own. This is a cross-tenant/authentication-bypass class issue: the app treats an unsigned value as if it had been authenticated by Shopify.

### Likelihood Explanation
Preconditions: the attacker needs to have obtained at least one genuinely HMAC-signed webhook body (trivial — install their own app on their own dev shop and capture any webhook delivery), and the target app must route business logic on `WebhookMetadata#shop`/`topic` without independent verification (typical usage per the documented handler contract). Attacker cost is minimal (one HTTP replay with modified headers); it is fully repeatable against any handler registered via `add_registration` and against any `shop` string the attacker chooses to set in the unsigned header.

### Recommendation
Include the security-relevant headers (`shopify-topic`, `shopify-shop-domain`, `shopify-webhook-id`, `shopify-api-version`) in the HMAC-signable material, or otherwise cryptographically bind them to the payload before trusting them for dispatch/tenant attribution — e.g., verify `shop`/`topic` against fields already present in the signed JSON body, or require the host app to independently authenticate `shop` against a known/installed shop list before invoking handlers. At minimum, document that `WebhookMetadata#shop` and `#topic` are not covered by the HMAC and must not be trusted as authenticated identifiers without additional verification.

### Proof of Concept
Minitest sketch (WebMock/Mocha, no live shop):
```ruby
# test/webhooks/registry_signature_bypass_test.rb
class RegistrySignatureBypassTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.clear
    @handler_a = mock_handler_for("topic/a")
    @handler_b = mock_handler_for("topic/b")
    ShopifyAPI::Webhooks::Registry.add_registration(topic: "topic/a", delivery_method: :http,
      path: "/wh", handler: @handler_a)
    ShopifyAPI::Webhooks::Registry.add_registration(topic: "topic/b", delivery_method: :http,
      path: "/wh", handler: @handler_b)
  end

  def test_dispatch_follows_unsigned_topic_header_not_signature
    raw_body = '{"id":1}'
    secret = ShopifyAPI::Context.api_secret_key
    hmac = Base64.strict_encode64(OpenSSL::HMAC.digest("sha256", secret, raw_body))

    # Genuinely signed body, but claim topic/b + attacker-chosen shop via headers
    request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: {
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-topic" => "topic/b",
      "x-shopify-shop-domain" => "victim-shop.myshopify.com",
      "x-shopify-api-version" => "2023-01",
      "x-shopify-webhook-id" => "1",
    })

    @handler_b.expects(:handle).with(
      data: has_attributes(shop: "victim-shop.myshopify.com", topic: "topic/b"),
    )
    @handler_a.expects(:handle).never

    ShopifyAPI::Webhooks::Registry.process(request)
    # Assert: signature validity (bound only to raw_body) does not constrain
    # which handler/shop is used -- dispatch follows the unsigned header.
  end
end
```
This demonstrates that `HmacValidator.validate` accepts the request purely because `raw_body` matches, while `topic` and `shop` — both outside `to_signable_string` — fully control dispatch and tenant attribution, confirming the signature-coverage invariant is broken.

          @registry[topic] = case delivery_method

          else
            raise Errors::InvalidWebhookRegistrationError,
              "Unsupported delivery method #{delivery_method}. Allowed values: {:http, :pub_sub, :event_bridge}."
