### Title
Caller-controlled swap routes can execute unintended token transfers under the caller’s authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary

`swap_collateral`, `swap_debt`, and `repay_debt_with_collateral` accept an opaque caller-supplied `swap` payload and pass it to the configured router after authorizing the account owner or delegate. [1](#0-0)  The controller constrains only its own exact input transfer and measured output balances; it does not constrain unrelated calls the router makes while executing the route. [2](#0-1)  A malicious route can therefore place an unrelated `token.transfer(caller, attacker, amount)` beneath the caller’s signed strategy invocation. [3](#0-2) 

### Finding Description

The external report’s bug class is attacker-controlled access to an unintended resource. Here, the `swap: Bytes` argument is an attacker-influenced execution path, while the controller treats router execution as a black box. [4](#0-3)  The strategy first requires caller authorization and verifies ownership or delegation, then withdraws collateral and invokes the swap helper. [3](#0-2)  `swap_tokens` grants the router authority to pull exactly `amount_in` from the controller, but the nested route itself remains opaque. [5](#0-4)  After execution, the controller validates only that its input balance did not increase, spending did not exceed `amount_in`, and some output was received. [6](#0-5)  Those checks do not prevent route code from requesting an additional transfer from the caller’s wallet. [6](#0-5) 

### Impact Explanation

A malicious route can steal unrelated wallet tokens from the account owner when transaction simulation records the hidden child invocation and the owner signs the resulting authorization tree. [7](#0-6)  The loss is not limited to the collateral amount submitted to the strategy because the router’s side effect can name a different token and recipient. [5](#0-4)  The strategy can still satisfy the controller’s measured-input and positive-output checks, allowing the malicious transaction to complete. [6](#0-5) 

### Likelihood Explanation

The victim must invoke an affected strategy using a malicious `swap` payload and sign the authorization tree produced for it. [7](#0-6)  This is plausible when routes are supplied by a quote service, aggregator UI, or copied transaction rather than independently decoded by the signer. [8](#0-7)  Attackers cannot directly drain an arbitrary account without that account’s strategy authorization, so the issue is not an unauthenticated transfer. [9](#0-8) 

### Recommendation

Use a typed, allowlisted route representation rather than opaque execution bytes, or require the router to present a bounded invocation manifest that the controller verifies before execution. [10](#0-9)  Wallets and callers should reject any authorization tree containing calls beyond the expected router input pull and venue interactions. [5](#0-4)  The durable fix is to prevent arbitrary route-selected code from running beneath the caller’s strategy authorization. [8](#0-7) 

### Proof of Concept

1. Alice owns a funded position and calls `swap_collateral(caller=alice, account_id, current=USDC, amount, new=ETH, swap=route)`. [4](#0-3) 
2. `process_swap_collateral` authenticates Alice and confirms she owns or delegates the position. [9](#0-8) 
3. The controller invokes `router.execute_strategy(controller, amount, route)` under the flash guard. [5](#0-4) 
4. Route-selected code calls `unrelated_token.transfer(alice, attacker, alice_balance)` while still returning enough `ETH` to satisfy the controller’s output check. [6](#0-5) 
5. Simulation places that transfer beneath Alice’s `swap_collateral` authorization; if Alice signs the generated tree, the unrelated token transfer and otherwise-valid strategy both execute. [11](#0-10)
