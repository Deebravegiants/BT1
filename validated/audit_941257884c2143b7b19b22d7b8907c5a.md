### Title
Emporium acts as a shared custodial identity for external protocols keyed on `msg.sender`, letting any user unstake/withdraw another victim's locked position - (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes arbitrary `endpoint.call(callData)` in CASE 2 (`stack.signerAddress == 0`) with no binding between the caller who benefits from the resulting `balanceChange` and the party who originally caused funds to enter the target protocol under Emporium's identity. Because a third-party staking contract can only authenticate `msg.sender == Emporium`, and Emporium is a single shared contract used by all Hinkal users, any unprivileged user can submit their own valid Hinkal transaction (with their own ZK proof and own UTXOs) whose CASE 2 op calls `unstake()`/`withdraw()` on a protocol where a *different* victim previously staked via Emporium, and receive the payout as their own new UTXO.

### Finding Description
The claimed broken equality is: `staker (as understood by the external staking contract) == the wallet/stealth address that produced the Hinkal proof for the current transaction`. This equality is never enforced anywhere in the contracts, because:

- `runAction` is gated only by `onlyAllowedRecipient` [1](#0-0) , which restricts the caller to the registered `Hinkal` contract, not to a specific user - any unprivileged attacker can reach it by calling `Hinkal.transact()` with a self-generated proof over their own commitments/nullifiers.
- Inside `runAction`, CASE 2 (`op.invokeWallet==false` or `stack.signerAddress==address(0)`) performs `op.endpoint.call{value: op.value}(op.callData)` directly with no check tying `op.callData` to the identity of whoever supplied the current `circomData`/proof [2](#0-1) .
- `verifyWallet` only replays a signature check when `stack.signerAddress != address(0)`; for CASE 2 it just marks `circomData.emporiumMessage` used and returns, performing no ownership check of the underlying staking position [3](#0-2) .
- `handleOut` sends any positive `balanceChange` for a token to `msg.sender` (the calling `Hinkal` contract) and mints a `UTXO` keyed to `circomData.stealthAddressStructure` — i.e. whichever address crafted the current proof, regardless of who actually staked the tokens originally [4](#0-3) .
- On the `Hinkal.sol` side, the balance/slippage checks (`balanceDif == amountChanges[i] + utxoAmount`) only verify that Hinkal's own token balance change for this single transaction is fully accounted for by on/off-chain UTXOs created in *this* transaction [5](#0-4) . They say nothing about which external state (a third party's staking position) produced the funds; they only ensure self-consistency of the current call, so a valid proof over the attacker's own (possibly zero) `amountChanges` for that token still satisfies the equation while the attacker walks away with the victim's unlocked stake.
- `_externalTransact` merely checks that the registered external action address matches and forwards `deltaAmountChanges` computed from the attacker's own `circomData.amountChanges` [6](#0-5) ; there is no linkage requiring that a withdrawal only be honored for the depositor who created it.

Exploit flow: Victim stakes via Emporium CASE 2 (`endpoint=staking, callData=stake(amount, lockDuration)`), recorded by the staking contract as `staker=Emporium` because the staking contract only tracks `msg.sender`. After `lockDuration`, attacker crafts their own `CircomData`/ZK proof (their own nullifiers/commitments, `amountChanges[tokenIndex]==0` for the staked token, `deltaAmountChanges[tokenIndex] ≥ 0`) with an Emporium `EmporiumStack` op set to CASE 2 `callData=unstake(amount)`, and calls `Hinkal.transact()`. `_externalTransact` invokes `EmporiumUpgradeable.runAction`, which calls `staking.unstake(amount)`; since the staking contract validates only `msg.sender==Emporium`, it releases the victim's tokens to Emporium. `handleOut` then forwards them to `Hinkal` and creates a UTXO owned by the attacker's stealth address, which the attacker can later spend.

### Impact Explanation
This is direct theft of a victim's locked/staked shielded funds once the lock period elapses: any unprivileged party can drain another user's staking position routed through the shared `EmporiumUpgradeable` contract, matching the Critical category ("direct theft of shielded or in-flight user funds"). The attack is repeatable against every staking-style integration that authenticates solely on `msg.sender` and is exposed for the full window after `lockDuration` until the legitimate staker races to withdraw first.

### Likelihood Explanation
Preconditions: a victim must have staked ERC20 into a third-party contract via Emporium CASE 2 with a lock period, and that contract must authorize unstake/withdraw purely by `msg.sender` (a common pattern, e.g. `stake(amount)/unstake(amount)` without a `beneficiary` mapping keyed by the original depositor's own address). No privileged role, victim key, or relay cooperation is required — the attacker only needs to generate their own valid Hinkal proof (fully within an unprivileged user's capability) and knowledge of the target staking contract/lock expiry, both of which are observable on-chain. This is a race but requires no special access, and is directly reachable through `Hinkal.transact()`.

### Recommendation
Bind external CASE 2 stateless calls in Emporium to a per-user "staker" identity rather than the shared Emporium address: either (a) deploy a per-user minimal proxy/sub-account for each Hinkal user's external staking interactions, so that `msg.sender` seen by the staking contract is unique per user, or (b) require CASE 2 ops that later release funds (unstake/withdraw) to carry a signed `EmporiumStack.signerAddress` proof tying the withdrawal back to the specific stealth address/session that performed the original stake, and reject CASE 2 execution for withdrawal-type calldata when `signerAddress==0`.

### Proof of Concept
Foundry test plan:
1. Deploy a mock staking contract that tracks `balances[msg.sender]`, with `stake(amount, lockDuration)` pulling ERC20 from caller and `unstake(amount)` paying back to caller after `lockDuration`, with no other identity tracking.
2. Victim: call `Hinkal.transact()` with a valid proof, `externalActionId=Emporium`, CASE 2 op `endpoint=staking, callData=stake(amount, lockDuration)`, depositing `amount` tokens; assert staking contract records `balances[Emporium] == amount` and victim's UTXO tree reflects the deposit consumed with no output UTXO for that token.
3. Warp `vm.warp(block.timestamp + lockDuration + 1)`.
4. Attacker: generate their own valid proof for a zero-value Hinkal transaction (`amountChanges[tokenIndex]=0`), same Emporium action, CASE 2 op `endpoint=staking, callData=unstake(amount)`, `erc20TokenAddresses` including the staked token, `stealthAddressStructure` pointing to attacker's own address.
5. Assert: `staking.balances(Emporium)` decreases by `amount`; a new UTXO commitment is inserted into the Hinkal tree keyed to the attacker's stealth address with `amount` equal to the victim's original stake; assert `balanceDif == amountChanges[i] + utxoAmount` holds trivially for the attacker's zero-deposit transaction while the victim never regains access to those funds — demonstrating the equality "staker == prover" is false without any check enforcing it.
