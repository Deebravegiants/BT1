### Title
Webhook `shop`, `topic`, and `webhook-id` values are trusted from unauthenticated HTTP headers not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verified by `Utils::HmacValidator.validate` proves the integrity of the JSON payload alone. The `shop`, `topic`, `webhook_id`, and `api_version` values are read from HTTP headers that are never included in the signed bytes, yet `Registry.process` passes them straight into `WebhookMetadata` and the app's handler as if they were authenticated. This breaks the binding: `bytes verified (raw_body) != bytes trusted as shop identity (shopify-shop-domain header)`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the raw body is signable. `Request#shop`, `#topic`, and `#webhook_id` are pulled from headers with no cryptographic tie to that body: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then forwards the header-derived `shop` (and `topic`, `webhook_id`) unchecked to the registered handler: [3](#0-2) 

Because `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:12-31`) only recomputes the HMAC of `verifiable_query.to_signable_string`, which for a webhook is exclusively `@raw_body`, a valid HMAC proves nothing about which shop, topic, or webhook id the payload was destined for. Any attacker who can obtain one genuinely-signed webhook body (e.g., by installing the target app on their own free/dev store and receiving a real webhook call from Shopify) can resend that same body+HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`/`shopify-webhook-id`) for an arbitrary victim shop domain. `Registry.process` will accept it as valid and hand the handler a `WebhookMetadata` claiming to be from the victim shop: [4](#0-3) 

This mirrors the report's bug class exactly: "a field acted on but not covered by the HMAC" — here the acted-upon field is the tenant-identifying `shop` header, verified bytes (`raw_body`) diverge from the bytes actually trusted for tenant attribution (headers).

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (or `#topic`/`#webhook_id`) to key data lookups, cache invalidation, deletion of shop records, or compliance actions (the built-in mandatory topics `shop/redact`, `customers/redact`, `customers/data_request` are exactly this kind of sensitive per-shop action), an attacker can trigger those actions against a shop of their choosing without ever compromising that shop's credentials. This is a cross-tenant identity-binding bypass reachable by any unprivileged internet user who can obtain one legitimately-signed webhook body of their own and replay it with a forged shop header, satisfying the "cross-tenant access" Critical-impact criterion.

### Likelihood Explanation
The gem exposes no API to bind or check the header-derived identity against the signed payload — `to_signable_string` for `Webhooks::Request` unconditionally returns only `@raw_body`, so every app built on this gem's `Registry.process` inherits this gap. Any developer who trusts `WebhookMetadata#shop`/`#topic`/`#webhook_id` for authorization or data-scoping decisions (a documented, expected usage pattern) is exposed. Obtaining a validly signed payload requires only a free Shopify development/partner store installing the target public app — no leaked credentials, TLS interception, or privileged account needed.

### Recommendation
Include the tenant/topic-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the payload (e.g., cross-check `shop` against a shop known to be associated with the delivered `webhook_id` via a server-side lookup) before constructing `WebhookMetadata`, so that a modified header invalidates the signature.

### Proof of Concept
1. Install the target app on an attacker-controlled Shopify development store (`attacker-shop.myshopify.com`) and trigger a webhook event (e.g., `orders/create`) registered via `Registry.add_registration`.
2. Capture the resulting HTTP POST: raw body `B`, header `shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`), and header `shopify-shop-domain: attacker-shop.myshopify.com`.
3. Replay the exact same body `B` and HMAC header `H` to the app's webhook endpoint, but change `shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (it only checks `B` against `H`), `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the app's handler executes app logic believing the event originated from the victim shop.
