### Title
Zero relayer fee combined with native-token payment causes `EvmHost.dispatch()` to revert, permanently DoS-ing self-relayed message dispatch - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` swap native token payment into the fee token via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(post.fee, path, ...)` whenever `msg.value > 0`, regardless of the value of `post.fee`/`get.fee`. The protocol's own documentation explicitly allows `fee` to be `0` ("self-relay"), but standard Uniswap V2 router/library code reverts on `getAmountsIn`/`getAmountIn` when the requested output amount is `0` (`require(amountOut > 0, 'UniswapV2Library: INSUFFICIENT_OUTPUT_AMOUNT')`). Any caller who dispatches with `msg.value > 0` and a `fee` of `0` will have their transaction revert, exactly analogous to the reported `stakeAmount == 0` issue where a downstream external protocol rejects a zero-value call that upstream code allows to occur.

The code branches purely on `msg.value > 0`; it never checks whether `post.fee` (the amount to be swapped for) is non-zero before invoking `swapETHForExactTokens`. The protocol's own documentation states that setting the relayer fee to `0` is an intended, supported flow for self-relaying: [3](#0-2) 

Every unprivileged application built on top of `IDispatcher`/`HyperApp` follows the same pattern of forwarding `msg.value` unconditionally when `msg.value > 0`, independent of the `fee` value it sets, e.g.: [4](#0-3) [5](#0-4) 

In a standard Uniswap V2 router/library, `swapETHForExactTokens(amountOut, path, ...)` calls `UniswapV2Library.getAmountsIn(factory, amountOut, path)`, which iterates backward calling `getAmountIn(amounts[i], reserveIn, reserveOut)`. The canonical `UniswapV2Library.getAmountIn` implementation requires `amountOut > 0` and reverts with `INSUFFICIENT_OUTPUT_AMOUNT` otherwise. Consequently, calling `swapETHForExactTokens(0, ...)` — which is exactly what happens when `post.fee == 0` and `msg.value > 0` — reverts before any swap logic executes, unwinding the whole `dispatch()` call.

This mirrors the reported bug class precisely: an internal code path allows an amount to be `0` in a legitimate scenario (self-relay with fee = 0), but that `0` is then fed into an external, unmodifiable dependency (Uniswap V2) that unconditionally rejects zero amounts, causing an unavoidable revert.

### Impact Explanation
Any application or user attempting to self-relay (setting `fee = 0`, as explicitly endorsed by protocol documentation) while paying via native token (`msg.value > 0`, e.g. because they still want to cover the host's Uniswap-swap based flow, or because their wrapper/app forwards `msg.value` unconditionally as shown above) will have `dispatch()` revert. This breaks the "self-relay" feature entirely for the native-payment path and can permanently block message dispatch for any caller/integration relying on this documented flow, causing a denial of service for a class of legitimate transactions across `HyperFungibleToken.send()`, `IntentGatewayV2`/`ExtrinsicIntents` order cancellation/dispatch paths, `HyperbridgeLzEndpoint.send()`, and any other app built on `IDispatcher.dispatch{value: msg.value}(...)` with a zero fee. Because these are core dispatch entry points reachable by any unprivileged caller/relayer/app in a single transaction, and the failure is deterministic and unconditional (not an edge-case race), this constitutes a Medium severity route-availability/DoS issue: a legitimate message a caller intends to send can never be delivered through this path.

### Likelihood Explanation
Likelihood is high whenever an integrator or user chooses to self-relay (fee = 0) yet also sends `msg.value > 0` — a combination the protocol's own docs describe as valid, and one that is trivial for any app that always forwards `msg.value` when non-zero (as seen in `HyperFungibleToken.send`, `HyperbridgeLzEndpoint.send`, and Intent gateway dispatch helpers) without separately checking whether the computed fee is zero. No special privileges, front-running, or precise conditions are required — it is a straightforward, deterministically reachable condition from a single transaction.

### Recommendation
In `EvmHost.dispatch(DispatchPost)` and `dispatch(DispatchGet)` (and the analogous `fundRequest` if it shares this pattern), only invoke `swapETHForExactTokens` when `post.fee`/`get.fee` (or the funded amount) is non-zero. When `msg.value > 0` but the target fee amount is `0`, either skip the swap and refund/ignore the sent native value, or explicitly revert with a clear error instead of relying on the downstream Uniswap revert. Concretely:
```solidity
if (msg.value > 0 && post.fee > 0) {
    // perform swap as before
} else if (post.fee > 0) {
    IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
}
// if msg.value > 0 && post.fee == 0, refund msg.value to _msgSender() or revert explicitly
```

### Proof of Concept
1. Deploy/observe `EvmHost` with a configured `uniswapV2` router and `feeToken`.
2. From any unprivileged app (e.g., `HyperFungibleToken`), call `send()` with `params.relayerFee = 0` (self-relay) while sending `msg.value = 1 wei` (or any non-zero native amount), i.e. `send{value: 1}(params)`.
3. `send()` forwards to `IDispatcher(_host).dispatch{value: msg.value}(request)` with `request.fee == 0`.
4. Inside `EvmHost.dispatch`, since `msg.value > 0`, it calls `swapETHForExactTokens{value: 1}(0, [WETH, feeToken], address(this), block.timestamp)`.
5. The Uniswap V2 router's underlying `UniswapV2Library.getAmountIn` call reverts with `INSUFFICIENT_OUTPUT_AMOUNT` because `amountOut == 0`, unwinding the entire `dispatch()` call and the outer `send()` transaction.
6. The caller cannot dispatch their message through this path at all, despite following the documented self-relay pattern.
