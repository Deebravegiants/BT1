### Title
Unprivileged solver-bid griefing via mode-blind ERC-7821 execution scan in `SolverAccount._containsFillOrder` - (File: evm/src/apps/intentsv2/SolverAccount.sol)

### Summary
`SolverAccount.validateUserOp()` decides whether a UserOperation is allowed to use the plain 65-byte ECDSA signature path by scanning its calldata with `_containsFillOrder()` for a call into `IntentGatewayV2.fillOrder`. That scanner discards the ERC-7821 `mode` word entirely and unconditionally treats `executionData` as one flat `Execution[]` array, exactly like the busybox/toybox report where an opaque, mode-multiplexed executor could run behavior the approval logic never actually inspected. Because `_erc7821AuthorizedExecutor` explicitly authorizes self-calls in addition to the EntryPoint, the same account can recursively re-enter its own `execute()`, so `fillOrder` can be reached through a nested/self-referential batch that the flat scan never inspects.

### Finding Description
`validateUserOp` branches purely on `op.signature.length`: [1](#0-0) 
For the 65-byte ECDSA branch, the only safety gate against an attacker stripping the `commitment`/`sessionSignature` off a public solver bid and replaying the bare `solverSignature` is `_containsFillOrder`: [2](#0-1) 
This function decodes `callData[4:]` as `(bytes32 mode, bytes executionData)` and then *discards* `mode` (`(, bytes memory executionData) = ...`), unconditionally assuming `executionData` is a single flat `Execution[]` batch. It only flags a call as `fillOrder` when `calls[i].target == INTENT_GATEWAY_V2 && bytes4(calls[i].callData) == FILL_ORDER_SELECTOR` — i.e. only when the gateway is called *directly* at the top level of that one specific encoding.

`ERC7821.execute(bytes32 mode, bytes executionData)`, which this contract implements, defines its call semantics by `mode`, not merely by the `execute` selector — the standard reserves mode values for nested/"batch of batches" execution and try/revert variants. `_containsFillOrder` never checks which mode is being used, so it cannot distinguish "flat batch that directly calls the gateway" from any other mode-defined encoding that ultimately reaches the gateway through an intermediate call. Critically, `_erc7821AuthorizedExecutor` authorizes the account to re-enter its own `execute()`: [3](#0-2) 
so a top-level `Execution` whose `target` is `address(this)` and whose `callData` is itself another `EXECUTE_SELECTOR` call (a different, gateway-calling batch) is a code path the account itself will happily execute, yet its `callData`'s selector is `EXECUTE_SELECTOR`, not `FILL_ORDER_SELECTOR` — so the flat scan's `bytes4(calls[i].callData) == FILL_ORDER_SELECTOR` check misses it entirely.

This is structurally identical to the busybox/toybox class of bug: the exec-approval check (`_containsFillOrder`) is bound to one opaque top-level identifier/shape (`EXECUTE_SELECTOR` + a single, hardcoded flat-array decode) rather than to the actual behavior the multiplexed executor (`ERC7821.execute`, mode-dependent) will run, so a legitimate bid's calldata that reaches `fillOrder` through any nested/self-referential encoding evades the guard while still executing identically at runtime.

### Impact Explanation
The whole purpose of `_containsFillOrder` is stated in its own comment: without it, "anyone could strip the commitment and session signature from a bid and submit the bare operation," consuming the solver's bid nonce and burning the solver's prepaid gas even though the fill itself reverts (no `select()` was staged). Because `callData` and therefore `userOpHash` are unchanged when only the `op.signature` field is truncated to 65 bytes, the previously-valid `solverSignature` (already signed over the plain `userOpHash`) remains valid on the ECDSA path — the *only* thing stopping the griefing attack today is the flat-array scan in `_containsFillOrder`. If a bid's calldata reaches `fillOrder` via any mode/encoding the scan does not recognize (nested batch, self-call re-entry into `execute`), an unprivileged attacker who merely observes the public bid can truncate its signature and resubmit it: `_containsFillOrder` returns `false`, `super.validateUserOp` accepts the bare 65-byte ECDSA signature, the EntryPoint executes the op, `fillOrder` is reached and reverts (no session was staged), but the solver's bid nonce is burned and their prefunded gas (`_payPrefund`/EntryPoint deposit) is consumed — a directly reachable griefing/DoS vector against solvers competing in Hyperbridge's intents auctions, executable by any unprivileged observer of public bid calldata, with no privileged role required.

### Likelihood Explanation
Any address can observe `OrderPlaced`/bid UserOperations broadcast for auction (they are explicitly documented as public), extract the 65-byte `solverSignature` from the 162-byte packed signature, and resubmit the identical `callData`/`userOpHash` with the truncated signature via the ERC-4337 EntryPoint — no special permissions, keys, or governance access are needed. The only precondition is that the bid's calldata be encoded via any ERC-7821 mode/nesting that `_containsFillOrder`'s hardcoded flat-array decode does not model; since `_erc7821AuthorizedExecutor` already authorizes self-call recursion into `execute()`, this is a code path the contract itself supports today, not a hypothetical extension.

### Recommendation
Fail closed instead of best-effort scanning: `_containsFillOrder` should reject (return `SIG_VALIDATION_FAILED`) on the 65-byte ECDSA path whenever `mode` is anything other than the single specific flat-batch encoding it knows how to inspect, and should recursively unwrap/reject any `Execution` whose `target == address(this)` (or whose `callData` selector is itself `EXECUTE_SELECTOR`) rather than only pattern-matching `target == INTENT_GATEWAY_V2`. Equivalently, bind the guard to `mode` explicitly (assert it equals the one supported ERC-7821 mode constant) and revert on any other mode/nested-execution encoding, mirroring the busybox fix's "opaque mutable executor is treated as unsafe by default; fail closed" approach.

### Proof of Concept
1. A solver `S` submits a bid: `op.callData = execute(mode, executionData)` where the top-level `Execution[]` batch contains one entry `{target: address(S) /*self*/, value: 0, data: execute(mode2, executionData2)}`, and `executionData2`'s batch contains `{target: INTENT_GATEWAY_V2, data: fillOrder(...)}`. `op.signature = abi.encodePacked(commitment, solverSignature, sessionSignature)` (162 bytes), where `solverSignature` is `S`'s ECDSA signature over the plain `userOpHash` of this exact `op`.
2. `S` broadcasts this UserOperation publicly for the auction, per the documented bid flow.
3. Attacker `A` (unprivileged, no keys) copies `op.callData` verbatim and sets `op.signature = solverSignature` (65 bytes, sliced from the observed 162-byte signature). `userOpHash` is unchanged since `callData`, sender, and nonce are unchanged, so `solverSignature` still recovers to `S`.
4. `A` submits this modified op to the bundler/EntryPoint. `validateUserOp` takes the `op.signature.length == 65` branch, calls `_containsFillOrder(op.callData)`. The top-level scan sees `calls[0].target == address(S)` (not `INTENT_GATEWAY_V2`) and `bytes4(calls[0].callData) == EXECUTE_SELECTOR` (not `FILL_ORDER_SELECTOR`), so it returns `false`.
5. `super.validateUserOp` accepts the bare ECDSA signature; the EntryPoint executes the op. Execution recurses through the self-call into `execute()` again and reaches `fillOrder`, which reverts because no `select()` was staged in this transaction (transient-storage authorization missing). The `PackedUserOperation`'s bid nonce is nonetheless consumed and `S`'s prefunded gas is burned by the EntryPoint's non-atomic charge for a reverted `execute` phase — reproducing exactly the griefing scenario `_containsFillOrder` was written to prevent.     function validateUserOp(PackedUserOperation calldata op, bytes32 userOpHash, uint256 missingAccountFunds)
        public
        override
        onlyEntryPoint
        returns (uint256)
    {
        if (op.signature.length == ECDSA_SIGNATURE_LENGTH) {
            if (_containsFillOrder(op.callData)) return ERC4337Utils.SIG_VALIDATION_FAILED;
            return super.validateUserOp(op, userOpHash, missingAccountFunds);
        }

        // Expected format: abi.encodePacked(commitment, solverSignature, sessionSignature)
        // commitment: 32 bytes, solverSignature: 65 bytes, sessionSignature: 65 bytes
        if (op.signature.length < INTENT_SELECT_SIGNATURE_LENGTH) return ERC4337Utils.SIG_VALIDATION_FAILED;

        bytes32 commitment = bytes32(op.signature[0:32]);
        bytes calldata solverSignature = op.signature[32:97];
        bytes calldata sessionSignature = op.signature[97:162];

        // Call IntentGatewayV2.select to recover the sessionKey. This also stages the
        // transient-storage selection that fillOrder enforces at execution.
        SelectOptions memory selectOptions =
            SelectOptions({commitment: commitment, solver: address(this), signature: sessionSignature});
        bytes memory selectCalldata = abi.encodeWithSelector(SELECT_SELECTOR, selectOptions);
        (bool success, bytes memory returnData) = INTENT_GATEWAY_V2.call(selectCalldata);

        if (!success || returnData.length < 32) return ERC4337Utils.SIG_VALIDATION_FAILED;

        address sessionKey = abi.decode(returnData, (address));
        uint192 userOpNonce = uint192(uint256(keccak256(abi.encodePacked(commitment, sessionKey))));
        if (uint192(op.nonce >> 64) != userOpNonce) return ERC4337Utils.SIG_VALIDATION_FAILED;
        if (!_rawSignatureValidation(userOpHash, solverSignature)) return ERC4337Utils.SIG_VALIDATION_FAILED;

        // Pay for gas if needed
        _payPrefund(missingAccountFunds);

        return ERC4337Utils.SIG_VALIDATION_SUCCESS;
    }

    /**
     * @notice Scans userOp calldata for a call to IntentGatewayV2.fillOrder
     * @dev The calldata is covered by the solver's signature over the userOpHash, so a
     *      replayed bid cannot be reshaped to hide the call — the scan only needs to
     *      recognize the bid's ERC-7821 execute(mode, executionData) batch. abi.decode
     *      reverts on malformed calldata, rejecting the op during validation just as
     *      execution would.
     * @param callData The userOp calldata to scan
     * @return bool True if the calldata contains a fillOrder call to the IntentGateway
     */
    function _containsFillOrder(bytes calldata callData) private view returns (bool) {
        if (callData.length < 4 || bytes4(callData[0:4]) != EXECUTE_SELECTOR) return false;

        (, bytes memory executionData) = abi.decode(callData[4:], (bytes32, bytes));
        Execution[] memory calls = abi.decode(executionData, (Execution[]));

        for (uint256 i = 0; i < calls.length; i++) {
            bool hasFillOrder = calls[i].target == INTENT_GATEWAY_V2 && bytes4(calls[i].callData) == FILL_ORDER_SELECTOR;
            if (hasFillOrder) return true;
        }
        return false;
    }
