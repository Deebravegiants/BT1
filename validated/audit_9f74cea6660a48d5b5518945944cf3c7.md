### Title
Attacker-controlled `amount_out` in `swap_base_out` can force division-by-zero panic in `swap_token_amount_base_out` - (File: `program/src/math.rs`)

### Summary
`process_swap_base_out` [1](#0-0)  calls `Calculator::swap_token_amount_base_out` with the user-supplied `swap.amount_out` value before any bound check against the pool reserves [2](#0-1) . Inside that function, the reserve minus `amount_out` is used as a division denominator via `checked_ceil_div`, which can become zero.

### Finding Description
`swap_token_amount_base_out` computes `denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap()` (Coin2PC direction) or `denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap()` (PC2Coin direction), then divides by that denominator via `.checked_ceil_div(denominator).unwrap()` [3](#0-2) . `checked_ceil_div` internally calls `self.checked_div(rhs)?`, which returns `None` when `rhs == 0`; the caller then immediately calls `.unwrap()` on that `Option`, causing a panic/revert [4](#0-3) .

Because `process_swap_base_out` never validates `swap.amount_out` against `total_pc_without_take_pnl`/`total_coin_without_take_pnl` before this call, an attacker submitting a swap-base-out transaction with `amount_out` exactly equal to the relevant pool reserve (or greater, which underflows and is caught by `checked_sub` returning `None`→panic via the outer `.unwrap()` on the subtraction itself) will drive the denominator to zero and force a runtime panic in the program.

### Impact Explanation
This is a denial-of-service class issue reachable by any unprivileged swapper via a single transaction with attacker-chosen instruction data (`amount_out`). It does not directly enable theft or fund freezing of already-deposited assets, and the transaction itself simply fails/reverts (Solana programs propagate a panic as a failed transaction, not state corruption), so no funds are moved or lost. This mirrors the reported bug class (division by zero due to insufficiently defensive `>= 0` vs `> 0` checks) but the concrete effect here is a reverted transaction, not persistent value loss.

### Likelihood Explanation
High likelihood of triggerability: `amount_out` is a plain `u64` argument fully controlled by the caller in `SwapInstructionBaseOut`, and the only preconditions are that the AMM is in a swap-permitted status and the user source/destination mint checks pass — both trivially satisfiable by any user holding the relevant token accounts.

### Recommendation
Add an explicit check in `process_swap_base_out` (and the `_v2` variant) requiring `swap.amount_out < total_pc_without_take_pnl` (or `< total_coin_without_take_pnl` depending on direction) before calling `Calculator::swap_token_amount_base_out`, returning an explicit `AmmError` (e.g. `AmmError::InvalidInput` or a new `ExceedPoolReserve` error) instead of allowing the internal `unwrap()` to panic.

### Proof of Concept
1. Attacker calls `process_swap_base_out` with `swap_direction = Coin2PC` and `swap.amount_out = total_pc_without_take_pnl` (the exact current PC reserve, obtainable by reading the AMM's vault balances, which are public accounts).
2. `swap_token_amount_base_out` computes `denominator = total_pc_without_take_pnl.checked_sub(amount_out) = 0`.
3. `total_coin_without_take_pnl.checked_mul(amount_out).unwrap().checked_ceil_div(0)` returns `None` inside `checked_ceil_div` (division by zero), and the outer `.unwrap()` panics, aborting the transaction. [5](#0-4) [6](#0-5)

    pub fn swap_token_amount_base_out(
        amount_out: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_in;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_in = coin * pc / (pc - amount_out) - coin
                // => amount_in = (coin * pc - pc * coin + amount_out * coin) / (pc - amount_out)
                // => amount_in = (amount_out * coin) / (pc - amount_out)
                let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_coin_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)

                // => amount_in = coin * pc / (coin - amount_out) - pc
                // => amount_in = (coin * pc - pc * coin + pc * amount_out) / (coin - amount_out)
                // => amount_in = (pc * amount_out) / (coin - amount_out)
                let denominator = total_coin_without_take_pnl.checked_sub(amount_out).unwrap();
                amount_in = total_pc_without_take_pnl
                    .checked_mul(amount_out)
                    .unwrap()
                    .checked_ceil_div(denominator)
                    .unwrap()
            }
        }
        return amount_in;
    }

impl CheckedCeilDiv for u128 {
    fn checked_ceil_div(&self, rhs: Self) -> Option<Self> {
        let mut quotient = self.checked_div(rhs)?;
        let remainder = self.checked_rem(rhs)?;
        if remainder != 0 {
            quotient = quotient.checked_add(1)?;
        }
        Some(quotient)
    }
}
