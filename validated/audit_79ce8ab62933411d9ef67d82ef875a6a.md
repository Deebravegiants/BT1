### Title
Webhook `shop` field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop` (tenant) identity is read from an HTTP header that is never included in the signed bytes. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then unconditionally forwards `request.shop` to the app's webhook handler as the authoritative shop for that event, without any binding between the verified bytes and the claimed shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Webhooks::Request#shop` is parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is ordinary attacker-controllable HTTP header data, not part of the HMAC input: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC over the body, then reads `request.topic`, `request.shop`, `request.webhook_id`, `request.api_version` — none but `topic`(indirectly, via body content) are part of the signed content — and passes them straight to the registered handler: [2](#0-1) 

Because Shopify signs webhooks with the app's single `client_secret` (the same secret is used for every shop the app is installed on — `HmacValidator` uses the global `Context.api_secret_key`) [5](#0-4) , a genuine webhook delivered to an app for shop A carries a valid HMAC that depends only on the body bytes, not on which shop it was intended for. An attacker who controls or operates shop A (an ordinary, unprivileged merchant/developer who installed the target app) receives real Shopify webhooks for shop A with a correctly computed HMAC. They can replay that exact `raw_body`/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header with victim shop B's domain. `Request#to_signable_string` — and therefore `HmacValidator.validate` — is blind to this substitution because the header is not part of the signed bytes, so the HMAC check still passes. The handler then receives `data.shop == "shop-B.myshopify.com"` bound to attacker-influenced body content, breaking the equality the app is meant to rely on: `verified(shop) == acted_on(shop)`.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` (as the library's own documentation recommends: "shop, String - The shop domain of the webhook") to key per-tenant storage, look up the shop's session/access token, or otherwise scope side effects, can be made to attribute attacker-supplied webhook content to a shop the attacker does not own or operate, since the gem provides no cryptographic binding between the verified bytes and the shop identity. This is a cross-tenant integrity/confusion issue in the credential/tenant boundary this gem is responsible for enforcing during webhook verification.

### Likelihood Explanation
Any user who can install the target app on their own shop (i.e., any unprivileged merchant, which is the normal, expected path to obtaining a validly signed webhook payload) can capture a genuine `raw_body` + `hmac` pair for their own shop and immediately replay it with a forged shop-domain header, since HTTP headers are entirely attacker-controlled on the wire and the gem performs no additional binding.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed content, or otherwise cryptographically bind the claimed shop to the verified payload (e.g., verify the shop is one of a known, pre-registered set of shops with an active session before trusting `request.shop`), rather than validating the HMAC over the raw body alone and independently trusting an unauthenticated header for tenant identity.

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com`; app's webhook endpoint receives a genuine Shopify webhook: body `raw_body`, header `x-shopify-shop-domain: attacker.myshopify.com`, and a valid `x-shopify-hmac-sha256` computed by Shopify using the app's `client_secret` over `raw_body`.
2. Attacker resends this exact `raw_body` and `x-shopify-hmac-sha256` to the app's webhook endpoint but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds a request object where `hmac` and `to_signable_string` are unaffected by the header change.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `to_signable_string` (`raw_body`) against the HMAC.
5. The registered handler is invoked with `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's body>, ...)`, causing the host app to process attacker-controlled webhook content as if it originated from `victim.myshopify.com`.
