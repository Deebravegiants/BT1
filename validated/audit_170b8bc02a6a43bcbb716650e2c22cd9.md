### Title
Webhook `shop` (and topic/api-version/webhook-id) headers are trusted by `Webhooks::Registry.process` without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop`, `topic`, `api-version`, and `webhook-id` values are read straight from unauthenticated HTTP headers and forwarded unchanged to the registered handler. The gem's own `Webhooks::Registry.process` treats HMAC validation as proof that the whole webhook (including its shop attribution) is authentic, but the shop identity is never bound to the signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled from HTTP headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate` verifies only that `to_signable_string` (the body) matches the supplied HMAC using the app's `api_secret_key`: [3](#0-2) 

`Registry.process` uses that body-only validation as its sole authenticity gate, then constructs `WebhookMetadata` directly from the unauthenticated `request.shop` header and hands it to the app's handler: [4](#0-3) 

The binding that should hold is:
`shop_bound_by_hmac(payload) == shop_used_by_handler(payload)`

but in this implementation:
`shop_used_by_handler(payload) = header["x-shopify-shop-domain"]`, which is disjoint from `shop_bound_by_hmac(payload) = ∅` (the HMAC covers no shop field at all).

Because every shop that installs the app shares the same app-level `api_secret_key` (there is no per-shop signing key), any merchant who has installed the app (an unprivileged internet user with respect to other tenants of the same app) can capture one legitimately-signed webhook body sent to their own endpoint and resubmit it to the same endpoint with the `x-shopify-shop-domain` (and `x-shopify-topic`/`x-shopify-webhook-id`) headers rewritten to name a different, victim shop. `Registry.process` will still pass `Utils::HmacValidator.validate`, since only the body is checked, and will invoke the handler with `WebhookMetadata` claiming the victim's shop.

### Impact Explanation
If the host application's webhook handler uses `WebhookMetadata#shop` to select which tenant's data/session/access token to act on (a common and gem-encouraged pattern, since `shop` is provided specifically for that purpose), an attacker-controlled shop can cause writes, deletions, or side effects to be attributed to and executed against a different merchant's data — a cross-tenant access/integrity violation achieved without ever needing the app's `api_secret_key`, an access token, or any privileged credential beyond installing the app on one's own store.

### Likelihood Explanation
Likelihood is high: exploitation requires only installing the app as a normal merchant (no special privilege), capturing one webhook delivery (trivial, since it is delivered to the attacker's own endpoint), and replaying it with modified headers to the same public endpoint. No knowledge of `api_secret_key` or any other secret is needed because the shop identity was never protected by the signature in the first place.

### Recommendation
Bind the shop domain (and topic/webhook id) into the HMAC-verified material, or otherwise cryptographically tie the header claims to the signed body, before constructing `WebhookMetadata`. At minimum, `Registry.process` should cross-check `request.shop` against an independently trusted source (e.g., the session/shop the endpoint is registered for) rather than trusting the header value outright, and `to_signable_string` should not omit fields that downstream code treats as authenticated identity.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; trigger any subscribed webhook topic so Shopify POSTs a signed payload to the app's webhook endpoint:
   - Headers: `x-shopify-hmac-sha256: <valid HMAC of raw body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, body `B`.
2. Capture `B` and the valid `x-shopify-hmac-sha256` value.
3. Replay the exact same body `B` and HMAC header to the same endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds (it only checks `B` against the HMAC, per `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/utils/hmac_validator.rb`), so `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act as if the event came from the victim shop.
