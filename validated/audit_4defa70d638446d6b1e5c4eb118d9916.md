### Title
Webhook shop-domain and topic are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while the `shop`, `topic`, and `webhook_id` values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the body only, then dispatches the handler using the unauthenticated `shop` header value. Any user who can register the app on their own shop can capture one genuine, validly-signed webhook and replay it to the app's public webhook endpoint with a forged `shop-domain` header, causing the receiving app to attribute the attacker's payload to an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `shop`, `topic`, `webhook_id` are pulled straight from headers with no cryptographic binding: [2](#0-1) 

`Registry.process` verifies the HMAC (over the body only) and then immediately trusts the header-derived `shop`, `topic`, and `webhook_id` to build the metadata handed to the app's handler: [3](#0-2) 

The `HmacValidator.validate` call used here signs/verifies exactly the value returned from `to_signable_string`, i.e. only `@raw_body`: [4](#0-3) 

This is the same bug class as the referenced report: a value that is *acted upon* (here, the `shop` identity used to route/persist the webhook payload) is not part of the data actually covered by the integrity check (the HMAC), so the two can be made to diverge. The broken identity binding is:

`shop authenticated by HMAC` (nothing — HMAC covers body only) **≠** `shop used as the tenant key for the webhook handler` (`request.shop`, taken from an arbitrary, attacker-controlled header).

### Impact Explanation
Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any merchant (an unprivileged actor from the app's perspective) can install the app on their own store, trigger a real webhook (e.g., `orders/create`), and thereby obtain one raw body + valid `hmac-sha256` pair signed with the app's real secret. That pair remains valid forever for that exact body, regardless of which `shop-domain`/`topic`/`webhook-id` headers accompany it, because those headers are excluded from the signed content. Replaying the captured `(raw_body, hmac)` to the app's public webhook endpoint with a forged `x-shopify-shop-domain` header naming a different (victim) shop passes `HmacValidator.validate` and is dispatched to the app's handler tagged with the victim's shop. Any app logic that uses `WebhookMetadata#shop` to look up sessions, write data, or attribute the payload to a tenant will act on attacker-supplied data under the victim's identity — a cross-tenant integrity/confidentiality break satisfying the Critical bar in this program ("cross-tenant access").

### Likelihood Explanation
Likelihood is high: obtaining one genuine `(body, hmac)` pair only requires installing the app on an attacker-controlled shop (no privileged credentials, access tokens, or `client_secret` needed), which is a normal, unprivileged interaction with any Shopify app using this gem. The webhook HTTP endpoint is public by design (documented usage pattern in `docs/usage/webhooks.md`), and no other component in the gem cross-checks the header-derived `shop` against anything cryptographically bound to the request.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value returned by `to_signable_string` (or otherwise bind them into the HMAC verification), mirroring how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop`/`host` alongside the other signed fields: [5](#0-4) 
Alternatively, document and enforce that `Registry.process` must re-derive the shop association strictly from Shopify's HMAC computation input (as Shopify's platform actually signs `shop`, `topic`, etc. into the HMAC on the wire) rather than trusting the header values independently of what was signed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers an `orders/create` webhook, capturing the raw POST body `B` and the header `x-shopify-hmac-sha256: H` (a valid signature for `B` computed with the app's real `api_secret_key`, per `HmacValidator.compute_signature`/`validate_signature` in `lib/shopify_api/utils/hmac_validator.rb`).
2. Attacker sends a new POST to the app's webhook route with body `B` (unchanged) and headers:
   - `x-shopify-hmac-sha256: H` (unchanged, still valid because only `B` is signed)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - `x-shopify-topic: orders/create`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` is constructed and passed to `ShopifyAPI::Webhooks::Registry.process`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `H` against `B` (`lib/shopify_api/webhooks/request.rb` lines 35-38, `lib/shopify_api/utils/hmac_validator.rb` lines 12-31).
5. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"` and the attacker's payload `B` (`lib/shopify_api/webhooks/registry.rb` lines 188-200), causing the app to process attacker-controlled data under the victim shop's identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
