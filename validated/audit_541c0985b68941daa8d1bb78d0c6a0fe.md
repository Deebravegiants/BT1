## Finding

### Title
Webhook shop identity is not bound to the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/utils/hmac_validator.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop` identity that is subsequently handed to the host application's handler is taken from the unauthenticated `X-Shopify-Shop-Domain` header, which is never included in the HMAC-signed data.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` decodes the `hmac-sha256` header — the `shop`, `topic`, `webhook-id`, and `api-version` headers are excluded from the signed payload entirely: [1](#0-0) [2](#0-1) [3](#0-2) 

`HmacValidator.validate` verifies the HMAC only against `verifiable_query.to_signable_string`, i.e. only the body bytes: [4](#0-3) 

`Registry.process` uses this validation as the sole authentication gate, then forwards `request.shop` — the unauthenticated header — directly to the host application's handler as the tenant identity: [5](#0-4) 

Because `api_secret_key` is the app's single shared secret (identical across every merchant/shop that installs the app), any unprivileged user who installs the app on their own store receives genuine webhooks signed with that same secret. Such a user can capture a valid `(raw_body, hmac)` pair from their own shop's webhook traffic, then replay it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain. `HmacValidator.validate` will still pass (it only checks the body bytes against the shared secret), and `Registry.process` will dispatch to the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

This breaks the binding: {shop cryptographically authenticated by the HMAC} ≠ {shop acted upon by the handler (`request.shop`)}.

### Impact Explanation
Host applications built on this gem are documented to key their per-tenant session/data lookups off the `shop` field provided in `WebhookMetadata` (as shown in the gem's own webhook usage examples). An attacker who is a legitimate-but-unprivileged installer of a shared app can forge webhook events that the host application will process under an arbitrary victim shop's identity — enabling cross-tenant data confusion/injection (e.g., causing order/product/customer data or app state changes to be attributed to a shop the attacker does not control). This matches the "cross-tenant access" critical-impact category.

### Likelihood Explanation
Exploitation only requires: (1) installing the app once as any ordinary merchant to obtain one valid `(body, hmac)` pair, and (2) sending a crafted HTTP POST to the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` header. No access to `api_secret_key`, tokens, or privileged accounts is required beyond what any regular app installer already has. The likelihood is elevated because this requires no interaction with Shopify's servers at replay time — the attacker directly POSTs to the app's own endpoint.

### Recommendation
Bind the identity headers into the signed payload verification, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the verified body (e.g., include them in the HMAC input, or require the host app to cross-check the delivered `shop` against a `webhook_id` that was independently registered per-shop with Shopify, rejecting webhooks whose `shop` was not the one the corresponding `webhook_id`/subscription was registered for).

### Proof of Concept
1. Install the target Shopify app on attacker-owned shop `attacker-shop.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw POST body and its `X-Shopify-Hmac-Sha256` header value — both are valid because they're signed with the app's single shared `api_secret_key`.
2. Replay the exact same body and HMAC header to the app's webhook endpoint, but set:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <captured value>
   ```
3. `ShopifyAPI::Utils::HmacValidator.validate` in `Registry.process` passes (body/HMAC match), and the handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the body/data actually originated from the attacker's own shop, as shown in `lib/shopify_api/webhooks/registry.rb` lines 188-199 and `lib/shopify_api/webhooks/request.rb` lines 20-38.
