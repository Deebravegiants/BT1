### Title
Missing L2 sequencer uptime check in `SimplexPaymaster._getOraclePrice` allows stale Chainlink prices to be treated as fresh during Optimism/Base/Arbitrum sequencer downtime - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster` prices ERC-20 gas payments using Chainlink `AggregatorV3Interface` feeds and only guards against staleness with a `block.timestamp - updatedAt > maxOracleAge` check. It performs no L2 sequencer-uptime check, even though the contract is explicitly designed to be deployed across multiple chains including OP-stack L2s (its own comments reference "Base/Ethereum stablecoins" heartbeats), where Chainlink recommends checking a sequencer-uptime feed before trusting `latestRoundData()`.

### Finding Description
`_getOraclePrice` is the sole freshness gate for both the `nativeOracle` and each token's `tokenOracle`: [1](#0-0) 

It reverts only when the answer is non-positive or `updatedAt` is older than `maxOracleAge`; there is no call to a Chainlink L2 sequencer-uptime feed (e.g. `0xFdB631F5EE196F0ed6FAa767959853A9F217697D` on Arbitrum, `0x371EAD81c9102C9BF4874A9075FFFf170F2Ee389` on Optimism) and no `GRACE_PERIOD_TIME` check after sequencer restart. `maxOracleAge` is governance-configurable up to `MAX_ORACLE_AGE = 7 days`, and the contract's own docs acknowledge heartbeats vary "up to 24h" on Base: [2](#0-1) 

On an OP-stack chain, when the sequencer goes down, Chainlink feeds stop being updated by L2 keepers; when the sequencer restarts, feeds can catch up with `updatedAt` values that still fall inside `maxOracleAge`, or worse, stale rounds can be replayed/manipulated during the outage window without the paymaster detecting it, since `_getOraclePrice` has no visibility into sequencer health at all — it only compares timestamps.

`_tokenPrice`, which feeds every gas-cost computation (`_tokenPrice`, `getTokenPrice`, `estimateTokenCost`, and the internal `_erc20Cost`-equivalent conversion in `PaymasterERC20`), directly consumes this unguarded price: [3](#0-2) 

### Impact Explanation
Any unprivileged party submitting a `PackedUserOperation` (mode `PERMIT` or `PERMIT2`) through this permissionless paymaster can have their gas cost computed from a manipulated or catch-up-skewed price during/after a sequencer outage, causing the paymaster to under-charge the ERC-20 token relative to actual native gas cost. This directly drains the paymaster's treasury/markup surplus and, at scale, its EntryPoint deposit — a concrete loss of funds reachable from a single submitted UserOperation, matching the "unprivileged message dispatcher" surface (the paymaster's `validatePaymasterUserOp`/`fetchDetails` path is open to any bundler-submitted op).

### Likelihood Explanation
The condition (L2 sequencer downtime followed by recovery) is a known, recurring operational event on Optimism/Arbitrum/Base rollups, and it requires no privileged access — any user can time a permit/permit2-mode UserOperation to land during or immediately after such a window. The contract has no chain-agnostic defense against this, so the likelihood is directly tied to sequencer incident frequency on whichever L2 `SimplexPaymaster` is deployed to.

### Recommendation
Add a Chainlink `L2SequencerUptimeFeed` check to `_getOraclePrice` (or `_tokenPrice`) on L2 deployments: revert if the feed reports the sequencer is down, and enforce a grace period (e.g. Chainlink's recommended pattern) after it comes back up before trusting `latestRoundData()`. Make the sequencer-feed address a governable parameter analogous to `nativeOracle`/`tokenConfigs`, defaulting to disabled on L1 deployments.

### Proof of Concept
1. Deploy `SimplexPaymaster` on an OP-stack chain (e.g. Base) per `evm/script/DeploySimplexPaymaster.s.sol`, with `maxOracleAge` set to the chain's normal heartbeat (e.g. 24h per code comments).
2. Simulate sequencer downtime: the L2's Chainlink price feed stops updating `updatedAt` (or, per Chainlink's documented risk, catches up post-recovery with a value still inside `maxOracleAge`) while the real off-chain USD price of the token/native asset has moved.
3. An attacker submits a `PackedUserOperation` with mode `0x00`/`0x02` referencing a stale-but-"fresh" price via `_executePermit`/permit2 path; `_getOraclePrice` in `evm/src/utils/SimplexPaymaster.sol` (lines 662-668) accepts it because `block.timestamp - updatedAt <= maxOracleAge` and `answer > 0`, with no sequencer check performed anywhere in the file.
4. `_tokenPrice` computes gas cost using the stale rate, letting the attacker pay less ERC-20 than the actual gas cost, extracting value from the paymaster's treasury/deposit over repeated ops during the outage/recovery window.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
