Based on my investigation, I found a direct analog to the report's rounding/binding-mismatch bug class: a field that is **acted upon but not covered by the cryptographic verification**.

### Title
Webhook shop-domain header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [1](#0-0)  which is what `HmacValidator.validate` signs and verifies [2](#0-1) . However, the `shop` value used downstream to tag/route the webhook to a tenant is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed bytes [3](#0-2) .

### Finding Description
`Registry.process` only checks `Utils::HmacValidator.validate(request)` (which verifies the raw body against the shared `client_secret`) before constructing `WebhookMetadata` using `request.shop`, the unauthenticated header value, and dispatching it to the app's handler: [4](#0-3) .

The binding that should hold is:
`shop asserted to the handler == shop cryptographically bound to the signed payload`

But in reality:
`shop asserted to the handler (request.shop, from an unsigned header) != shop covered by the HMAC (only @raw_body)`

Because the HMAC secret (`api_secret_key`/`client_secret`) is the same for every shop that has installed a given app, any entity that can obtain one valid `(raw_body, hmac)` pair from Shopify for *any* shop where the app is installed (e.g., their own store, or a shop where they have collaborator/admin access sufficient to receive a webhook, such as a test/development store) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a different (victim) shop. `HmacValidator.validate` will still pass, because it never inspects the shop header, only the raw body bytes.

The docs even describe `Registry.process` as something that "will verify the request did indeed come from Shopify" [5](#0-4)  and document `data.shop` as "The shop domain of the webhook" [6](#0-5)  - implying to integrators that the `shop` field, like the rest of the payload, has been authenticated by the preceding `Registry.process` call. This is not accurate: only the body bytes are authenticated, the shop attribution is not.

### Impact Explanation
This is a cross-tenant identity-binding break: an app that uses `WebhookMetadata#shop` (as the shipped example handler does: `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [7](#0-6) ) to select the tenant/session/store to act on can be made to apply an attacker-controlled body to a victim shop's tenant context, purely by replaying a signature that was legitimately issued for the attacker's own store. This falls under "cross-tenant access" since the shop identity carried in the trusted, gem-verified webhook data structure can be forged independent of the HMAC.

### Likelihood Explanation
Requires only that the attacker has (or can obtain) any single valid webhook delivery from Shopify for an app instance they control (trivial - install a test/dev app copy, or use any shop with the same app installed), since the client secret and thus the HMAC computation is identical across all shops for a given app. No access to `api_secret_key`, tokens, or the victim's data is required - purely a replay against the public webhook endpoint with a modified header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of `to_signable_string` for webhook requests, or otherwise cryptographically bind the shop attribution to the signed payload, so that the value exposed via `WebhookMetadata#shop` is a verified fact rather than an unauthenticated header echoed back to the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`. Shopify sends a legitimate webhook with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker captures `(B, H)`.
3. Attacker POSTs to the app's webhook endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `HmacValidator.validate` computes `HMAC-SHA256(client_secret, B)` and compares to `H` — passes, because the signable string never included the shop header: [1](#0-0) .
5. `Registry.process` dispatches `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` to the app's handler, which the host app trusts as an authenticated fact about `victim.myshopify.com`: [8](#0-7) .
