### Title
Webhook shop-domain header is not covered by the HMAC, allowing tenant-identity spoofing on otherwise-valid webhook requests - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a request as "verified" solely on the HMAC of the raw body, then hands the handler an unauthenticated `shop` value taken from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header. Because the header is never included in the signed material, the `shop` claim can be altered without invalidating the HMAC, breaking the binding `verified_sender == claimed_shop`.

### Finding Description
`Registry.process` raises `InvalidWebhookError` unless `Utils::HmacValidator.validate(request)` succeeds, and then calls the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`: [1](#0-0) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`, and `shop` is read straight from the (unsigned) header: [3](#0-2) 

So the equality the gem is supposed to guarantee is:
`hmac_valid(raw_body) == true` implies `shop header == the shop that actually generated raw_body`.

That implication does not hold: `shop` is parsed from a header that plays no part in the signature computation, so `verified_body_source != claimed_shop` is a state that is fully reachable while `HmacValidator.validate` still returns `true`. Any party capable of intercepting or replaying an HMAC-valid webhook body (e.g., a merchant who installed the app on their own store and thus legitimately receives correctly-signed webhook deliveries for their own data) can substitute the `shop-domain` header with an arbitrary victim shop domain before the request reaches the host application's webhook endpoint. `Registry.process` will still validate the HMAC (it only covers the body) and will forward `shop: <attacker-chosen victim domain>` to the handler as if it were an authenticated fact.

The library's own documentation reinforces the false trust: it says `Registry.process` "will verify the request did indeed come from Shopify" without qualifying that only the body — not the shop attribution — is verified: [4](#0-3) 

A host application following this documented API exactly (as shown in the docs' own example, constructing `Request` from `raw_post`/headers and calling `process`) has no indication that it must independently re-verify the shop domain; it is invited to treat `WebhookMetadata#shop` as trustworthy once `process` does not raise.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as intended and as documented) to key per-tenant records — e.g., updating a customer's/shop's local billing state, order records, or webhook-driven data sync — an attacker can cause the library to hand back data for shop A tagged as belonging to shop B. This is a cross-tenant identity confusion rooted entirely in this gem's verification logic, since the "verified" boolean it returns does not bind to the shop field it also returns from the same request.

### Likelihood Explanation
Exploitability requires the attacker to control or intercept the transport of an HMAC-valid webhook delivery before it is parsed by the host app (e.g., a merchant installing the app on their own store, who legitimately receives valid webhook deliveries and can modify headers en route to a self-hosted receiving endpoint, or any man-in-the-middle position on an unencrypted/misconfigured relay). No knowledge of `api_secret_key` is needed — the attacker reuses a genuinely-signed body/HMAC pair and only changes the unsigned header.

### Recommendation
Include the shop domain (and other identity-relevant headers such as topic/api-version) in the signed material verified by `HmacValidator`, or otherwise cryptographically bind `Request#shop` to the HMAC-checked body before exposing it via `WebhookMetadata`. At minimum, update `Webhooks::Request#to_signable_string` so the HMAC covers the headers used for identity, and update `docs/usage/webhooks.md` to explicitly clarify what `process` does and does not verify.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and body `B`.
2. The attacker (who controls the delivery path to the app's webhook endpoint, e.g. a proxy or a self-relayed webhook forwarder) rewrites the header to `X-Shopify-Shop-Domain: victim-shop.myshopify.com`, leaving body `B` and the HMAC header unchanged.
3. App calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: modified_headers))`.
4. `HmacValidator.validate` succeeds because it only checks `HMAC(B, api_secret_key)`, per [5](#0-4)  and [6](#0-5) .
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and body data that actually originated from `attacker-shop.myshopify.com`, per [7](#0-6) , causing the host application to attribute attacker-controlled data to the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
