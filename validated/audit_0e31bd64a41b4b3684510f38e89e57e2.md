### Title
Position NFT `transfer` to an address that can never authorize permanently freezes the account and its collateral - (File: contracts/position-nft/src/contract.rs)

### Summary
The position NFT is the sole ownership record for a controller account: the token id **is** the account id and `owner_of` is the account owner (`contract.rs:1-2`). The contract exposes the stock OpenZeppelin `NonFungibleToken` interface (`contract.rs:131-133`), whose `transfer`/`transfer_from` only require `from.require_auth()` — there is no validation that `to` is an address capable of authorizing future operations. Transferring the NFT to an address that can never produce an authorization (a contract address without a `transfer` path, such as the controller or pool contract itself) permanently locks the position, freezing all supplied collateral and debt inside it.

### Finding Description
- `PositionNft` implements `NonFungibleToken` with `ContractType = Enumerable` and adds no transfer restrictions or recipient checks (`contract.rs:132-133`, `contract.rs:172-173`). The only custom entrypoints are controller-gated `mint`, `burn`, and `upgrade`, plus permissionless `renew` (`contract.rs:68-124`).
- Ownership is the only access credential: the comments state "The token owner (`owner_of`) is the account owner" (`contract.rs:2`), and the controller's `burn` exists precisely because "the controller must burn when liquidation empties an account without the owner's signature" (`contract.rs:80-83`) — confirming every user-facing controller entrypoint (withdraw, repay-driven collateral release, etc.) requires the NFT owner's auth.
- On Soroban there is no `address(0)`, but any `Address` is a valid transfer target, including contract addresses. A contract address can only "authorize" if the contract code calls `require_auth` on itself; neither the controller nor the pool exposes a function that lets it transfer out an NFT it owns. The OZ `Base::update` performed by `transfer` simply rewrites `NFTStorageKey::Owner(token_id)` (`contract.rs:30-45`), so the account's collateral is thereafter unreachable.
- This is the direct analog of the reported bug: a share/NFT transfer path with no guard on the recipient, where the recipient can be an address from which the position can never be recovered — shares effectively burned, funds irretrievable.

### Impact Explanation
Permanent freezing of funds. Once the NFT lands on a non-authorizable address, `withdraw`, `borrow`/`repay` collateral flows, liquidation participation, and every owner-gated controller call can never authenticate `owner_of(account_id)`, so all supplied assets in that account are locked forever (the controller's `burn` can only destroy the token, not release collateral). For an account with material collateral this is a total loss.

### Likelihood Explanation
Medium. The path is a single unprivileged `transfer(token_id, to)` call, but the freeze requires the user (or an approved operator) to pick an unusable recipient — contract addresses, or simply an address whose keys are lost. It cannot be triggered against a third-party victim, which caps severity below High; still, the same "send position to a contract" mistake is routine on Stellar where contract and account addresses share one `Address` type and there is no `address(0)` sentinel to warn users.

### Recommendation
Guard the transfer path in `PositionNft` (override `transfer`/`transfer_from` in the `NonFungibleToken` impl) to reject recipients that cannot take ownership — at minimum, reject the controller and pool contract addresses and any `Address` matching known protocol contracts, or alternatively require `to.require_auth()` so the recipient actively accepts the position. Document that NFT transfer transfers the whole account so integrators add their own checks.

### Proof of Concept
```rust
// Attacker/victim: any account owner.
// 1. User supplies collateral; position NFT id = account_id (contract.rs:1-2, mint at :68).
// 2. User (or an approved spender) calls:
position_nft.transfer(&user, &controller_contract_address, account_id);
//    OZ transfer only calls from.require_auth() and rewrites
//    NFTStorageKey::Owner(token_id) (contract.rs:30-45) — succeeds.
// 3. owner_of(account_id) is now the controller contract.
// 4. controller.withdraw(...) requires the new owner's auth; the controller
//    has no entrypoint that calls require_auth() on itself for NFT transfer,
//    so the call always fails. Collateral is frozen permanently.
```
The same applies with `to = pool_contract` or any contract address that lacks a self-authorized NFT `transfer` call.

Caveat: this was verified against `PositionNft`'s own code; the OZ `transfer` body lives in the `stellar_tokens` dependency, not vendored in-repo, so I could not cite its exact lines — the behavior (only `from` auth, no recipient check) is the documented stock implementation referenced by `contract.rs`.
