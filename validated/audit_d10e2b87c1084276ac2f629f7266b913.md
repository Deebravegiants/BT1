## Title
Shop-domain identity spoofing via unauthenticated `X-Shopify-Shop-Domain` header in webhook processing (cross-tenant impersonation) - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, but the `shop` identity that downstream handler code relies on to attribute the webhook to a tenant is read from an HTTP header that is **not included in the signed material**. This breaks the intended binding: `HMAC(secret, raw_body) == received_hmac` should imply `shop == the-shop-that-Shopify-signed-this-for`, but the code only proves the former, not the latter.

### Finding Description
`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string`, which for a webhook `Request` is defined as: [1](#0-0) 

i.e., the signable string is only the raw body (`@raw_body`), never the headers. Meanwhile, `shop` is read straight from an unauthenticated header: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately hands `request.shop` (the unauthenticated header value) to the app's handler as the tenant identifier, alongside the (signed) body: [3](#0-2) 

The equality the code should enforce is:
`hmac_valid(raw_body) ∧ shop_header == shop_bound_to(raw_body, secret)`

but it only checks the first conjunct. The `shop-domain` header is never covered by the signature computation in `to_signable_string`, so any request with a *previously valid* `(raw_body, hmac)` pair remains valid under `HmacValidator.validate` regardless of what value is placed in `x-shopify-shop-domain` / `shopify-shop-domain`.

### Impact Explanation
An app built on this gem that uses `WebhookMetadata#shop` (populated from `request.shop`) to decide which merchant/tenant record to update, look up, or act on — the normal, documented usage pattern — can be tricked into attributing a legitimate webhook body to the wrong shop. A user who has installed the app on their own shop can capture one of their own genuine webhook deliveries (raw body + valid HMAC, which they legitimately receive since they run an endpoint that receives Shopify webhooks for their own installation) and replay the exact same body/HMAC pair to the app's webhook endpoint while substituting a different `shop-domain` header value. Because `HmacValidator.validate` never verifies the shop claim, the replayed request passes validation and is dispatched to the handler as if it originated from the victim shop, corrupting or exfiltrating data attributed to a tenant the attacker does not control — a cross-tenant integrity/confidentiality violation without needing the app's `client_secret`, an access token, or any privileged credential.

### Likelihood Explanation
Low-to-moderate difficulty: the attacker must be an existing user/merchant of the target application (so they receive at least one legitimate webhook to their own installation) but requires no secret material — only a valid captured `(raw_body, hmac)` pair and the ability to send an HTTP request to the app's public webhook endpoint with a forged shop header. No access token, api_secret_key, or TLS interception is required, satisfying the "unprivileged internet user" bar.

### Recommendation
- Include the claimed `shop-domain` (and ideally `topic`, `webhook-id`) in the signed material that `HmacValidator` verifies, or independently validate that `request.shop` matches a shop the app actually has an active session/installation for before processing.
- Short term: in `Registry.process`, cross-check `request.shop` against the app's own installation store before invoking the handler, rather than trusting the header value implicitly once HMAC-over-body passes.
- Document explicitly that `Webhooks::Request#shop` is not authenticated by the HMAC and must be corroborated against known installed shops.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and stands up their own webhook receiver endpoint (as normal integration).
2. Shopify sends a legitimate webhook to the attacker's endpoint: body `B`, header `x-shopify-hmac-sha256: H` (valid for secret S and body `B`), header `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same request to the target app's real webhook processing endpoint but changes only the header: `x-shopify-shop-domain: victim-shop.myshopify.com`, keeping body `B` and hmac `H` unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which recomputes HMAC over `B` only — matches `H` — validation passes (see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`).
5. `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, body: request.parsed_body, ...))` is invoked with `shop = "victim-shop.myshopify.com"` and attacker-controlled body content, causing the app to process attacker data under the victim's tenant identity.
