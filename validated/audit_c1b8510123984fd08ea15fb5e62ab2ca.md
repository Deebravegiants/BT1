## Title
Escrowed intent funds are permanently frozen if a token blacklists the fixed beneficiary — `_withdraw` in `IntentsBase.sol`

### Summary
`IntentsBase._withdraw`, which is invoked by `ExtrinsicIntents.onAccept` (for `RedeemEscrow`/`RefundEscrow`) and `onGetResponse`, pushes escrowed ERC-20 tokens to a beneficiary address that is baked into the original order commitment. If that token contract blacklists the beneficiary (e.g., a USDC/USDT-style blacklist), the transfer permanently reverts, and — unlike an admin-controlled treasury address — there is no way to change the beneficiary for a given commitment, so the escrowed funds are stuck forever.

### Finding Description
`_withdraw` unconditionally calls `safeTransfer(beneficiary, amount)` on escrowed tokens: [1](#0-0) 

The `beneficiary` comes from a `WithdrawalRequest` that is embedded, immutably, in the order:
- For `RedeemEscrow`, the beneficiary is the filler (`msg.sender` of the fill), set at fill time and dispatched cross-chain: [2](#0-1) 
- For `RefundEscrow`, the beneficiary is `order.user`: [3](#0-2) 
- Same-chain cancel-from-source uses the same fixed beneficiary via a `DispatchGet`/`onGetResponse` round trip: [4](#0-3) , [5](#0-4) 

`onAccept` dispatches directly into `_withdraw` with no try/catch: [6](#0-5) 

If `onAccept` reverts, `EvmHost.dispatchIncoming` deletes the receipt and does not revert the whole batch, leaving the message "retryable" — but because the `WithdrawalRequest.beneficiary` is fixed as part of the already-hashed/committed order (it cannot be altered by governance or by the relayer), redelivery hits the exact same reverting `safeTransfer` every time. This is confirmed by the project's own documented delivery semantics: [7](#0-6) 

There is no pull-payment/withdraw-pattern fallback for these paths, unlike the governance-only `SweepDust` (`_sweepDust`) or `EvmHost.withdraw`/`HostManager` paths, where governance can simply re-dispatch a fresh withdrawal to a different beneficiary: [8](#0-7) , [9](#0-8) .

### Impact Explanation
Once a token blacklists the filler (RedeemEscrow) or the original order creator (RefundEscrow/cancel), the corresponding escrowed input tokens can never be released from `IntentGatewayV2`/`IntentsBase`. There is no admin function to redirect or force-withdraw escrow to an alternate address, so the funds are permanently locked — a direct fund-freezing vulnerability reachable by any unprivileged order placer or solver simply by placing/filling/cancelling an order whose relevant address later gets blacklisted by the token issuer (a scenario entirely outside the protocol's control). This satisfies "permanent freezing of funds," matching the Medium severity of the original analog.

### Likelihood Explanation
Any ERC-20 with a blacklist/freeze feature (USDC, USDT, and similar centrally-administered stablecoins) is a realistic input/output token for cross-chain intents. A user or solver being blacklisted post-order-placement (for reasons unrelated to Hyperbridge, e.g., regulatory action) is a foreseeable, externally-triggered event, not attacker-controlled but fully within scope as a reachable, permissionless flow (order placement/fill/cancel are all open to any address).

### Recommendation
Replace the push-based `safeTransfer` in `_withdraw` (and the corresponding fill-time transfers in `_fillCrossChain`) with a pull-payment/claims pattern: on transfer failure, credit an internal claimable balance for the beneficiary instead of reverting, and expose a separate `claim` function (optionally allowing the beneficiary or governance to redirect the claim to an alternate address) so a single blacklisted recipient cannot indefinitely lock the escrowed funds.

### Proof of Concept
1. User places a cross-chain order via `IntentGatewayV2.placeOrder`, escrowing USDC as `order.inputs`.
2. A solver fills the order on the destination chain via `_fillCrossChain`, setting itself (`msg.sender`) as the `RedeemEscrow` beneficiary and dispatching the request back to the source chain: [2](#0-1) .
3. Before the message is relayed/delivered, USDC's issuer blacklists the solver's address.
4. When the relayer delivers the `RedeemEscrow` message, `onAccept` → `_withdraw` calls `IERC20(usdc).safeTransfer(solver, amount)`, which reverts due to the blacklist: [10](#0-9) .
5. `EvmHost.dispatchIncoming` swallows the revert and marks the request undelivered/retryable, but since the beneficiary in the committed `WithdrawalRequest` cannot be changed, every future redelivery attempt fails identically.
6. The escrowed USDC remains locked in the gateway contract indefinitely, with no admin/governance function able to redirect or force-release it to a different address.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
