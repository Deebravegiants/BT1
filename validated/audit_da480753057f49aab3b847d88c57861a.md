### Title
Webhook HMAC only signs the request body while `shop`, `topic`, and `webhook-id` are taken from unauthenticated headers, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are excluded from the signature. `Registry.process` validates only the body HMAC and then trusts these header-derived values when invoking the app's webhook handler, breaking the equality "bytes verified == bytes acted on."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled directly from headers (`x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) that are never part of the HMAC computation: [2](#0-1) 

`Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (the raw body) and compares it against `request.hmac`. It then dispatches the handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [3](#0-2) 

Because Shopify computes the HMAC using the app's single, shared `client_secret` (not a per-shop key), the signature only proves "this body was signed by someone possessing the app secret" — it does not bind the signature to a specific shop or topic. An attacker who legitimately installs the app on their own store (or captures a genuine webhook delivery from any shop, e.g. via a public tunnel/log) obtains a valid `(raw_body, hmac)` pair signed with the app's secret. They can then replay this exact `raw_body`/`hmac` pair to the app's webhook endpoint while freely rewriting the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers to any value, since none of them affect the signature check. `HmacValidator.validate` will still return `true` because it only re-signs `@raw_body`.

This breaks the intended binding: `bytes verified (raw body only) != bytes/metadata acted upon (shop, topic, webhook_id passed to the handler)`.

### Impact Explanation
This allows an unprivileged attacker who has captured or self-generated one authentic `(body, hmac)` pair to have the gem report to the app's handler that a webhook of an **arbitrary topic** arrived for an **arbitrary shop domain** (`WebhookMetadata#shop`), which is a cross-tenant identity spoof. Depending on the handler's trust in `WebhookMetadata#shop`/`#topic` (a reasonable and common assumption, since the gem asserts the request "passed HMAC validation"), this can be leveraged to trigger privileged, shop-scoped actions (e.g., mandatory compliance webhooks like `customers/redact`, `shop/redact`, or business-logic handlers that update/delete data) attributed to a shop the attacker does not control — i.e., cross-tenant access enabled purely through this gem's verification logic.

### Likelihood Explanation
Likelihood is limited by the need for the attacker to first obtain one authentic `(raw_body, hmac)` pair signed by the app's secret. This is trivially achievable by any developer/merchant who can install the target app on their own (even free/dev) store and trigger any webhook — no privileged credentials, access tokens, or `api_secret_key` knowledge are required to obtain this pair. Once captured, forging the shop/topic headers on replay requires only a raw HTTP client.

### Recommendation
Bind the header-derived identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) into the signed payload verification path — e.g., include them in `to_signable_string`, or independently verify that `shop` corresponds to a shop the app has an active installation/session for before dispatching the handler, rather than trusting header values solely because the raw body HMAC matched.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers any webhook (e.g. `orders/create`), capturing the raw POST body `B` and the `X-Shopify-Hmac-Sha256` header value `H` sent by Shopify (valid because signed with the app's shared secret).
2. Attacker sends a new HTTP POST to the app's webhook endpoint with the same body `B` and header `H`, but sets:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic: customers/redact` (or any other registered topic)
   - `x-shopify-webhook-id: <arbitrary>`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only (`to_signable_string` in `lib/shopify_api/webhooks/request.rb`) — validation succeeds because `B`/`H` are still an authentic pair.
4. The registered handler for `customers/redact` is invoked with `WebhookMetadata.new(topic: "customers/redact", shop: "victim-shop.myshopify.com", ...)`, causing the app to perform shop-scoped actions for `victim-shop.myshopify.com` despite the attacker having no relationship with that shop.
