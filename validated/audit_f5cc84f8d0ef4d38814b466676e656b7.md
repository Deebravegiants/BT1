### Title
Webhook HMAC only covers the raw body, not the `shop-domain` header — allows cross-tenant webhook forgery/replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs (and later verifies) only the raw HTTP body via HMAC, while the `shop-domain`, `topic`, and `webhook-id` values used by `Registry.process` to route and attribute the webhook are taken from unauthenticated headers. Because a single app-wide `api_secret_key` is used to validate the HMAC for every shop that has the app installed, an attacker who legitimately receives one valid `(body, hmac)` pair for their own shop can replay it against the app's webhook endpoint with a forged `shop-domain` header naming a victim shop. The HMAC check still passes, and the handler is invoked believing the payload originated from the victim tenant.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `shop`, `topic`, and `webhook_id` — the values actually used downstream — are read straight from caller-supplied headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`HmacValidator.validate` verifies the HMAC using the app's single, shop-independent `api_secret_key` (or `old_api_secret_key`), i.e. the same secret is valid for every shop that installed the app: [3](#0-2) 

`Registry.process` only checks that the HMAC over the body is valid, then dispatches the handler using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id`: [4](#0-3) 

The broken identity binding is:
`HMAC_valid(body, api_secret_key) == true` is treated as proof that `(shop, topic, body)` all originated from Shopify for that specific shop, when in fact `HMAC_valid` only proves `body` was signed with the app's shared secret — it says nothing about which shop or topic the signer intended.

Because `api_secret_key` is identical for all shops using the app (not shop-scoped), any user who can get one legitimate webhook delivered to them (e.g., by installing the app on their own store or free dev store and triggering an event) obtains a `(raw_body, hmac)` pair that remains valid regardless of which `shop-domain` header accompanies it. That user can then POST the same body/HMAC directly to the app's public webhook endpoint with an arbitrary `x-shopify-shop-domain` header claiming to be a different, victim shop.

### Impact Explanation
This breaks the tenant boundary the library is meant to enforce: `Registry.process` will call the app's registered handler with `WebhookMetadata#shop` set to an attacker-chosen victim shop domain, while `body`/`topic` are attacker-influenced (via their own legitimately triggered event). Any host application that trusts `data.shop` from a validated webhook (which is the documented, intended use of this API — see `docs/usage/webhooks.md`) can be made to write/act on data under a victim shop's identity — i.e., cross-tenant data injection/confusion using only the attacker's own legitimate app installation, no access token or leaked credential required.

### Likelihood Explanation
Requires only: (1) attacker installs the app on any shop under their control (or otherwise triggers one authentic webhook delivery to themselves) to obtain a valid `(body, hmac)` pair for a topic of interest, and (2) attacker sends a direct HTTP POST to the app's public webhook endpoint with that body/HMAC and a forged `shop-domain` header. No secrets, tokens, or privileged access are needed beyond normal, unprivileged app installation. This is fully reachable through this gem's own verification logic (`Utils::HmacValidator` + `Webhooks::Request`/`Registry`).

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is HMAC-verified, or otherwise cryptographically tie the claimed `shop-domain` header to the signed body (e.g., include it in `to_signable_string`, or require the host app to independently confirm `shop` against a known/registered shop record before trusting `WebhookMetadata#shop`). At minimum, document prominently that `shop`, `topic`, and `webhook_id` are NOT covered by the HMAC and must not be trusted for tenant attribution without additional verification (e.g., matching against the app's list of installed shops).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and registers/triggers a webhook (e.g., `orders/create`), receiving a legitimate delivery with body `B` and header `x-shopify-hmac-sha256: H = HMAC_SHA256(api_secret_key, B)`.
2. Attacker crafts a raw POST to the app's public webhook endpoint with:
   - body: `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged, still valid since it only signs `B`)
   - header `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
   - header `x-shopify-topic: orders/create`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(api_secret_key, B)` and compares to `H` — validation succeeds because only `B` is signed: [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the event actually pertains to the attacker's own shop — demonstrating that the shop attribution is not authenticated by the HMAC.
