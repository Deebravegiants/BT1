### Title
`RollbackAccounts::data_size()` can exceed the declared `loaded_accounts_data_size_limit` for fee-only `SeparateNonceAndFeePayer` transactions, violating the cost-model upper-bound invariant - ([File: svm/src/account_loader.rs])

### Summary
When a durable-nonce transaction uses a separate fee payer and nonce account (`RollbackAccounts::SeparateNonceAndFeePayer`) and load fails, `load_transaction()` computes the transaction's reported `loaded_accounts_data_size` as `rollback_accounts.data_size()` — the raw sum of the nonce and fee-payer account sizes — instead of the size actually tracked (and capped) against the transaction's requested `loaded_accounts_data_size_limit`. This legacy fallback path is active whenever `define_ltds_fee_only_semantics` is not activated on cluster (it defaults to `false` in `SVMFeatureSet`).

### Finding Description
In `load_transaction()` (`svm/src/account_loader.rs:456-467`), when transaction loading fails, the reported cost-model size for the resulting `FeesOnlyTransaction` is chosen by feature flag: [1](#0-0) 

- If `define_ltds_fee_only_semantics` is true, `loaded_accounts_data_size` is `loaded_transaction_data_size.into()`, which is the value accumulated and hard-capped by `LoadedTransactionDataSize::increase_calculated_data_size` against `requested_loaded_accounts_data_size_limit` (`svm/src/account_loader.rs:488-511`); it can never exceed the declared limit.
- If the feature is *not* active (the default, per `SVMFeatureSet::default()` in `svm-feature-set/src/lib.rs`, where `define_ltds_fee_only_semantics` is not set in `all_enabled` unless the cluster feature has activated), `loaded_accounts_data_size` is instead `tx_details.rollback_accounts.data_size() as u32`, computed by `RollbackAccounts::data_size()`: [2](#0-1) 

This function sums the *actual* on-chain sizes of the nonce and fee-payer accounts for the `SeparateNonceAndFeePayer` variant (two tracked accounts), completely bypassing the `requested_loaded_accounts_data_size_limit` that gated the load.

An unprivileged attacker can craft a durable-nonce transaction with:
- a distinct nonce account and fee payer (`RollbackAccounts::SeparateNonceAndFeePayer`, created via `RollbackAccounts::new` in `svm/src/rollback_accounts.rs:64-100` whenever nonce and fee-payer addresses differ), and
- a `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit` value small enough that it is exceeded very early in `load_transaction_accounts` (e.g., by the fee payer's own size or the address-lookup-table base size — see `svm/src/account_loader.rs:522-597`), causing `TransactionError::MaxLoadedAccountsDataSizeExceeded` before any budget is spent loading the bulk of the transaction's real accounts.

Because the failure happens at/near the very first `increase_calculated_data_size` call, the tracked `loaded_transaction_data_size` used by the *correct* path would be small/limit-capped, but the fallback legacy path instead reports the full nonce+fee-payer account sizes, which — since the attacker controls the tiny declared limit — trivially exceeds it. This breaks the invariant that the cost-model estimate/declared limit upper-bounds the reported/real work for a transaction, since the value fed back into `CostModel::calculate_cost_for_executed_transaction` (`cost-model/src/cost_model.rs:56-77`) for block-cost accounting can now be larger than what the transaction was ever authorized (and fee-budgeted) to consume.

Existing guards do not stop this: the `increase_calculated_data_size` limit check (`svm/src/account_loader.rs:505-508`) only bounds the *accumulated tracked* size used for the `Ok`/successful-load path and is not consulted at all when the fallback branch (`!define_ltds_fee_only_semantics`) computes the reported size for a *failed* load.

### Impact Explanation
This is a cost-model/resource-accounting integrity issue rather than a direct lamport-theft path: the reported `loaded_accounts_data_size` for fee-only (failed-load) durable-nonce transactions with separate fee payer and nonce feeds into `CostModel::calculate_cost_for_executed_transaction` and hence into block-cost tracking (`core/src/banking_stage/consumer.rs:1251-1276`). An attacker can cause the recorded per-transaction "actual" loaded-accounts-data-size cost to exceed the value the transaction declared and was fee-budgeted for, which is a violation of the "cost-model estimate upper-bounds real work" invariant and constitutes materially mis-priced (here, over-reported, but structurally uncontrolled) resource accounting reachable by any unprivileged sender using nonce-as-fee-payer separation. This maps to Agave's "materially underpriced/mispriced execution" / cost-model integrity bounty category, not to a lamport-mint/duplicate/destroy category — there is no evidence in the traced code that lamports are moved, minted, or duplicated by this path.

### Likelihood Explanation
- Preconditions are fully attacker-controlled and require no privileged access: any unprivileged sender can create a durable-nonce transaction with a nonce account distinct from the fee payer, and can freely set an arbitrarily small `loaded_accounts_data_size_limit` via `ComputeBudgetInstruction::set_loaded_accounts_data_size_limit`.
- The bug is only live while `define_ltds_fee_only_semantics` has not been activated cluster-wide; `SVMFeatureSet` shows this is a distinct, separately-gated feature (not automatically true), so its exploitability depends on the current activation status of that feature gate on the live cluster, which cannot be verified from the code alone.
- The exploit is deterministic and repeatable given the precondition; no timing races or leader control are required.

### Recommendation
Remove the legacy fallback branch (`tx_details.rollback_accounts.data_size() as u32`) once `define_ltds_fee_only_semantics` is fully activated on all clusters, or in the interim, cap the fallback value with `.min(tx_details.loaded_accounts_bytes_limit)` so the reported size can never exceed the transaction's declared limit regardless of feature-gate state.

### Proof of Concept
```rust
// svm/src/rollback_accounts.rs (add to existing #[cfg(test)] mod)
use solana_compute_budget_instruction::compute_budget_limits::MAX_LOADED_ACCOUNTS_DATA_SIZE_BYTES;

#[test]
fn test_separate_nonce_and_fee_payer_data_size_can_exceed_declared_limit() {
    // Build a SeparateNonceAndFeePayer with nonzero-sized nonce + fee payer accounts.
    let nonce_address = Pubkey::new_unique();
    let durable_nonce = DurableNonce::from_blockhash(&Hash::new_unique());
    let nonce_account = AccountSharedData::new_data(
        43,
        &NonceVersions::new(NonceState::Initialized(NonceData::new(
            Pubkey::default(),
            durable_nonce,
            42,
        ))),
        &system_program::id(),
    )
    .unwrap();
    let fee_payer_address = Pubkey::new_unique();
    let fee_payer_account = AccountSharedData::new(44, 0, &Pubkey::default());

    let rollback_accounts = RollbackAccounts::SeparateNonceAndFeePayer {
        nonce: (nonce_address, nonce_account.clone()),
        fee_payer: (fee_payer_address, fee_payer_account.clone()),
    };

    // Attacker declares a tiny limit (1 byte), well below real nonce+fee-payer size.
    let declared_limit: u32 = 1;
    let real_size = rollback_accounts.data_size() as u32;

    // Invariant under audit: declared_limit should always dominate real_size
    // when define_ltds_fee_only_semantics is NOT active (legacy fallback path
    // in svm/src/account_loader.rs::load_transaction uses rollback_accounts.data_size()).
    assert!(
        real_size > declared_limit,
        "expected real rollback size ({real_size}) to exceed the declared limit ({declared_limit}), demonstrating the invariant violation"
    );
}
```

Integration-level PoC (conceptually, extending `svm/tests/integration_test.rs::fee_only_loaded_transaction_data_size` for the `false` (legacy) case): construct a `SeparateNonceAndFeePayer` transaction (distinct nonce and fee payer), attach `set_loaded_accounts_data_size_limit(1)`, force a load failure (e.g., `MaxLoadedAccountsDataSizeExceeded`), run with `feature_set.define_ltds_fee_only_semantics = false`, and assert that `output.processing_results[..].loaded_accounts_data_size()` (sourced from `RollbackAccounts::data_size()`) is greater than the declared limit of `1` — demonstrating that, unlike the `true` (SIMD-186) branch which is capped at the limit, the legacy branch's reported size is unbounded by the declared `loaded_accounts_data_size_limit`.

    // Size of accounts tracked for rollback, used internally when calculating the actual
    // loaded transaction data size for the cost model. This function will be removed by
    // the fee-payer data size amendment to SIMD-186.
    pub(crate) fn data_size(&self) -> usize {
        let mut total_size: usize = 0;
        for (_, account) in self.iter() {
            total_size = total_size.saturating_add(account.data().len());
        }
        total_size
    }
