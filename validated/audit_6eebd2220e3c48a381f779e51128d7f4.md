### Title
Webhook shop identity spoofable via `shop-domain` header not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is handed to the app's webhook handler from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature that `Registry.process` validates is computed only over the raw request body, never over the shop header. This breaks the intended binding `hmac-authenticated bytes == bytes acted on`, allowing a party who already possesses one valid `(raw_body, hmac)` pair (e.g., from a webhook legitimately delivered to their own shop) to relabel that payload as belonging to any other shop by simply changing the `shop-domain` header on replay.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates the HMAC using this signable string and, if valid, immediately trusts `request.shop` (parsed straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header) as the tenant identity passed into the handler: [2](#0-1) 

`Request#shop` is read directly from the header with no cross-check against the signed body: [3](#0-2) 

`HmacValidator.validate` only proves that `to_signable_string` (the raw body) was produced with the app's `api_secret_key`; it says nothing about which headers accompanied that body: [4](#0-3) 

The identity binding this code implicitly assumes is:
`shop header used by handler == shop that produced the HMAC-signed body`

That equality is never checked or enforced anywhere in `lib/shopify_api/webhooks/**`. The `shop` value is a field "acted on" (passed to `WebhookMetadata` and used by the host app to select per-tenant data) but not covered by the HMAC — exactly the class of binding break called out in scope.

### Impact Explanation
Any party that operates their own shop with the app installed receives genuine webhook deliveries containing a valid `(raw_body, hmac)` pair signed with the app's shared `client_secret`. Nothing in this gem prevents them from re-POSTing that exact `raw_body` (thus an unchanged, still-valid HMAC) to the app's webhook endpoint while substituting a different value in the `X-Shopify-Shop-Domain` header. `ShopifyAPI::Webhooks::Registry.process` will validate the HMAC successfully (it never inspected the header) and dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen shop domain: [5](#0-4) 

Any host application relying on this gem's parsed `shop` value to select the tenant/session context for processing (a documented and expected usage pattern of this library) can be made to attribute attacker-controlled webhook content to an arbitrary victim shop, i.e. cross-tenant confusion/injection of webhook events using only knowledge available to any shop that has the app installed — no `api_secret_key`, access token, or privileged account is required.

### Likelihood Explanation
Requires only that the attacker's own store has the app installed (a normal, unprivileged, self-service action) so they can capture at least one legitimate `(raw_body, hmac)` webhook pair, then replay it with a modified `shop-domain` header directly to the app's public webhook endpoint. No cryptographic material, secrets, or privileged access is needed; this is reachable purely from the header/body contract of `ShopifyAPI::Webhooks::Request`.

### Recommendation
Include the shop domain (and ideally the topic/webhook-id) in the signed material that `HmacValidator` verifies, or otherwise cryptographically bind the header-derived `shop` to the HMAC-covered body before it is handed to `WebhookMetadata`/handlers — e.g., recompute/verify the HMAC over `shop + topic + raw_body` rather than `raw_body` alone, matching the binding assumed by consumers of `request.shop`.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `client_secret`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker replays the exact same request to the app's webhook endpoint, changing only the header to `X-Shopify-Shop-Domain: victim.myshopify.com`, keeping body `B` and HMAC `H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== `B`) and matches `H` — validation succeeds since the header was never part of the signed content: [6](#0-5) 
4. The handler is invoked with `shop: "victim.myshopify.com"` even though the body `B` never originated from Shopify for that shop: [5](#0-4)
