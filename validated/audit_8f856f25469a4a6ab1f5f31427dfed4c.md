### Title
DoS in `IntentGatewayV2.placeOrder` when fees are paid in native token but no UniswapV2 router/pool is configured/available - (File: evm/src/apps/IntentGatewayV2.sol)

### Summary
`IntentGatewayV2.placeOrder` hardcodes a dependency on `IDispatcher(hostAddr).uniswapV2Router()` to convert leftover native value into the protocol `feeToken` whenever an order sets `order.fees > 0` and the caller supplies native value (`msgValue > 0`). This mirrors the Multipool `getAmountOut` bug: a critical code path unconditionally calls into an external pool/router address that is only assumed—never guaranteed—to exist and to have the required liquidity, causing a hard revert instead of a graceful fallback.

### Finding Description
In `placeOrder`, after escrow accounting, if `order.fees > 0` and the caller has any leftover native value (`msgValue > 0`, e.g. because the order also carries a native-token input), the contract goes down this branch: [1](#0-0) 

```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    if (msgValue > 0) {
        address uniswapV2 = IDispatcher(hostAddr).uniswapV2Router();
        address WETH = IUniswapV2Router02(uniswapV2).WETH();
        address[] memory path = new address[](2);
        path[0] = WETH;
        path[1] = feeToken;
        uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
            order.fees, path, address(this), block.timestamp
        );
        msgValue -= amounts[0];
    } else {
        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    }
    _orders[commitment][TRANSACTION_FEES] = order.fees;
}
```

This code always calls `IUniswapV2Router02(uniswapV2).WETH()` and `swapETHForExactTokens` against whatever address `EvmHost.uniswapV2Router()` currently returns, with no check that:
1. `uniswapV2` is non-zero, or
2. a liquidity pool exists for the `WETH`/`feeToken` pair with sufficient reserves to fill `order.fees`.

If the host's configured UniswapV2 router is `address(0)` (e.g., not deployed/configured on that chain, or intentionally left unset), or if the `WETH`/`feeToken` pair has no pool or insufficient liquidity, `WETH()`/`swapETHForExactTokens` will revert. Because this branch is reached by any ordinary, unprivileged user who calls `placeOrder` with any leftover native value while `order.fees > 0`, every such call permanently reverts — there is no fallback such as reverting to a plain `feeToken` transferFrom or reverting only the fee-conversion portion. This is exactly analogous to the Multipool report: a hardcoded external liquidity dependency, not validated for existence, that DoSes a core dispatcher function (there, `rebalanceAll`; here, `placeOrder`, the entry point for cross-chain intents/order escrow).

### Impact Explanation
Any user who wants to pay the `order.fees` component in native currency (a normal, documented flow for orders that combine a native-token input with dispatch fees) will have their `placeOrder` transaction unconditionally revert if the host's `uniswapV2Router` is unset or the `WETH`/`feeToken` pool lacks liquidity/doesn't exist on that chain. This blocks legitimate order placement entirely for that fee-payment mode on the affected chain, which is a denial-of-service on a core, unprivileged user-facing entry point of the intents system (order placement/escrow). This is not an admin-only misconfiguration risk in the sense of "malicious admin"; it is a reachable liveness failure triggered by ordinary configuration gaps (e.g. rollup/L2 deployments where no canonical UniswapV2 deployment or WETH/feeToken pool exists yet), consistent with the "route unable to deliver messages/complete orders" acceptance criterion.

### Likelihood Explanation
Likelihood is meaningful wherever `IntentGatewayV2` is deployed on a chain that either has not configured `uniswapV2Router` in `EvmHost` or where no liquid `WETH`/`feeToken` (typically DAI) UniswapV2 pool exists (common on newer L2s/appchains at rollout, or any chain where fee token liquidity migrates to V3/V4 only). Any user attempting to place an order with a native-token component and non-zero `order.fees` on such a chain triggers the revert deterministically, with no workaround available inside `placeOrder` itself.

### Recommendation
Do not hardcode a mandatory UniswapV2 conversion path for fee payment:
- Validate `uniswapV2Router != address(0)` before attempting the swap, and if it is zero, fall back to requiring the user to have supplied fees in `feeToken` (revert with a clear, actionable error instead of an opaque low-level revert from the router).
- Consider making fee-payment-in-native an explicit opt-in flag on the order rather than an implicit consequence of "any leftover msgValue," so users can always fall back to paying fees directly in `feeToken` via `safeTransferFrom`.
- Optionally support multiple router/DEX versions (V2/V3/V4) similarly to how the SDK's `swap.ts`/wrapper contracts already do multi-tier/multi-protocol fallback, instead of relying on a single hardcoded router reference from `EvmHost`.

### Proof of Concept
1. Deploy `EvmHost` with `HostParams.uniswapV2 = address(0)` (or point it to a router where no `WETH`/`feeToken` pool exists) — a legitimate configuration on a chain without UniswapV2 liquidity for the fee token.
2. As an ordinary user, call `IntentGatewayV2.placeOrder` with an order that includes a native-token (`address(0)`) input and `order.fees > 0`, sending `msg.value` covering both the native input and the fee amount.
3. Execution reaches the `msgValue > 0` branch and calls `IUniswapV2Router02(address(0)).WETH()`, which reverts (call to non-contract), or `swapETHForExactTokens` reverts due to missing pool/liquidity.
4. The entire `placeOrder` transaction reverts — the user cannot place the order at all through this fee-payment mode, regardless of retries, until governance reconfigures `uniswapV2Router` on `EvmHost` (a separate privileged action outside the user's control). [1](#0-0)
