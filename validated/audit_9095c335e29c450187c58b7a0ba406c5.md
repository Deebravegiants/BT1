Emporium "Min" proof path lets any unprivileged attacker drain Emporium's held assets via unauthenticated `EmporiumStack.ops` when `signerAddress == 0` and `erc20TokenAddresses` is empty - (File: contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` via `MainEVMCircuitMin` and constrains nothing else about the transaction. `EmporiumUpgradeable.runAction` then executes `stack.ops` (an arbitrary, attacker-supplied `EmporiumStack` decoded from `externalActionMetadata`) completely independent of `erc20TokenAddresses.length`, and when `signerAddress == 0` no signature over the ops is required at all. Because the balance-accounting loop (`balancesBefore`/`balancesAfter`) only iterates over the (empty) `erc20TokenAddresses` array, any assets moved by `stack.ops` are never accounted for, checked for slippage, or blocked, letting an attacker instruct Emporium to call `token.transfer(attacker, amount)` directly and drain Emporium's real ERC20/ETH holdings.

### Finding Description
The broken equality is: **assets Emporium's `stack.ops` can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`**. This equality is trivially violated when `circomData.erc20TokenAddresses.length == 0`.

Path:
1. `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [1](#0-0) 
2. `formInputEmporiumMin` only emits 3 public signals: `emporiumMessage`, `timeStamp`, `calldataHash`: [2](#0-1) 
3. The corresponding circuit, `MainEVMCircuitMin`, proves nothing except `message === Poseidon(messageSeed)` — a self-chosen secret with zero linkage to any prior deposit, UTXO, nullifier, or the actual `EmporiumStack` content: [3](#0-2) 
4. `HinkalHelper.performHinkalChecks` only verifies calldata-hash *integrity* (that on-chain `circomData` fields match `circomData.calldataHash`), dimensions, and onchain-creation rules — none of these constrain the semantic content of `externalActionMetadata`/`stack.ops`: [4](#0-3) 
5. `EmporiumUpgradeable.runAction` decodes the attacker-controlled `EmporiumStack` and executes `stack.ops` in a loop that is bounded by `stack.ops.length`, not by `erc20TokenAddresses.length`: [5](#0-4) 
6. `verifyWallet` — the only authorization gate on the ops — returns immediately with **no signature check whatsoever** when `stack.signerAddress == address(0)`, requiring only that the (attacker-chosen) `emporiumMessage` hasn't been used before: [6](#0-5) 
7. With `signerAddress == 0`, every op falls into "CASE 2: Stateless Interaction," which performs a raw `op.endpoint.call{value: op.value}(op.callData)` with `msg.sender == Emporium`. The only restriction is blocking `callHinkalWallet`/`doSendToRelay` selectors — nothing prevents `op.endpoint` being an arbitrary ERC20 token held by Emporium and `op.callData` being `transfer(attacker, amount)`: [7](#0-6) 
8. Both the accounting inside `runAction` (`balancesBefore`/`balancesAfter`, `balanceChange` revert guard) and the outer accounting in `Hinkal.transact` (`oldBalances`/`newBalances`, `balanceDif >= slippageValues[i]`) iterate strictly over `circomData.erc20TokenAddresses`, which is forced to be empty (length 0) to even reach this code path — so neither guard ever executes a single iteration and cannot detect the theft: [8](#0-7) [9](#0-8) 

The root cause is a design decoupling: the "Min" proof path was intended for authorization-only messages where funds movement is governed by `stack.ops` via a signed EIP-712 authorization from `signerAddress`. But when `signerAddress == 0`, that signature check is skipped entirely, and neither the ZK circuit nor any on-chain check binds the `emporiumMessage`/`messageSeed` to a specific, pre-authorized set of `ops`. Combined with the accounting loop being scoped to the (attacker-forced-empty) token array, this gives an unprivileged attacker unauthenticated, unaccounted control of Emporium's identity to call any external contract, including direct ERC20 `transfer` calls draining Emporium's balance.

### Impact Explanation
Any funds held in the `EmporiumUpgradeable` contract's own balance (ERC20 tokens or ETH corresponding to shielded/in-flight user deposits awaiting withdrawal, swap settlement, or other Emporium-mediated operations) can be directly transferred to an attacker-controlled address with a single `Hinkal.transact` call using a self-generated, unlinked Min proof. This matches Critical severity: **direct theft of shielded or in-flight user funds**. The attack is fully repeatable for any token the attacker knows Emporium holds, limited only by needing a fresh (unused) `emporiumMessage` each time — trivially satisfied since the attacker picks it.

### Likelihood Explanation
Preconditions: Emporium must hold a non-zero balance of some asset (an expected, normal operational state given Emporium's purpose of custody during external actions/wallet operations). The attacker needs no privileged role, no valid signature, no knowledge of any other user's secrets — only the ability to generate a trivial ZK proof of `message == Poseidon(messageSeed)` for a self-chosen `messageSeed`, and to encode an `EmporiumStack` with `signerAddress = 0` and an `ops` array whose `callData` calls `transfer` on the target token. This is well within the stated "unprivileged attacker" capabilities (deposit, generate own proofs, craft `CircomData`/`externalActionMetadata`). Cost is a single transaction plus proof generation (cheap for the "Min" circuit, which has almost no constraints).

### Recommendation
- Require `verifyWallet` to always validate `stack.ops` against a cryptographic commitment tied to the `message`/`messageSeed`, even when `signerAddress == 0` (e.g., the ops hash must be a public input constrained by the Min circuit, or `signerAddress == 0` should be disallowed for stateless calls that touch arbitrary `endpoint`/`callData`).
- Do not allow the balance-accounting loop to be bypassed based on `erc20TokenAddresses.length == 0`; either require the Min path to disallow any `op` that is not `invokeWallet` (restrict stateless calls with `signerAddress == 0` to a safe allow-list), or require `erc20TokenAddresses` to include every token touched by `stack.ops` so accounting/slippage checks apply.
- Bind `calldataHash`/`emporiumMessage` inside the SNARK circuit to a commitment of the actual `ops` content, closing the gap where the circuit proves only `Poseidon(messageSeed)` with no relation to the authorized action.
