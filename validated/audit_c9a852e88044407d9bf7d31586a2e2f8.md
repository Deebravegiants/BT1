### Title
Unchecked subtraction in `vesting::total_accumulated_rewards` can permanently brick vesting fund unlock/distribution - (File: aptos-move/framework/aptos-framework/sources/vesting.move)

### Summary
`vesting::total_accumulated_rewards` computes accumulated rewards with an unchecked, un-clamped subtraction chain (`total_active_stake - remaining_grant - commission_amount`). This mirrors the external report's root cause: a NAV/accounting subtraction that reverts on underflow instead of saturating or handling the undercollateralized case, and this same function sits on the only path (`vest` → `unlock_rewards` → `total_accumulated_rewards`) used to ever unlock and later distribute vesting-pool funds held in a resource-account-controlled stake pool.

### Finding Description [1](#0-0) 

```
public fun total_accumulated_rewards(vesting_contract_address: address): u64 acquires VestingContract {
    assert_active_vesting_contract(vesting_contract_address);
    let vesting_contract = borrow_global<VestingContract>(vesting_contract_address);
    let (total_active_stake, _, commission_amount) =
        staking_contract::staking_contract_amounts(vesting_contract_address, vesting_contract.staking.operator);
    total_active_stake - vesting_contract.remaining_grant - commission_amount
}
```

This function subtracts `remaining_grant` and `commission_amount` from `total_active_stake` with no bounds checking, and its own module spec explicitly documents that this can abort: [2](#0-1) 

```
let total_active_stake = active + pending_active;
let accumulated_rewards = total_active_stake - staking_contract.principal;
let commission_amount = accumulated_rewards * staking_contract.commission_percentage / 100;
aborts_if !exists<stake::StakePool>(pool_address);
aborts_if active + pending_active > MAX_U64;
aborts_if total_active_stake < staking_contract.principal;
aborts_if accumulated_rewards * staking_contract.commission_percentage > MAX_U64;
// This two item both contribute to the timeout
aborts_if (vesting_contract.remaining_grant + commission_amount) > total_active_stake;
aborts_if total_active_stake < vesting_contract.remaining_grant;
```

`remaining_grant` is decremented only in `vest()`, but the value it is compared against — `total_active_stake` from the underlying `staking_contract`/`stake` pool — is an external, mutable value that can move independently of `remaining_grant` bookkeeping (e.g. via operator commission changes, or any accounting drift between the vesting module's tracked `remaining_grant` and the live stake pool balance reported by `staking_contract::staking_contract_amounts`). If `total_active_stake < remaining_grant + commission_amount` at any point, this subtraction underflows and aborts.

Critically, this same computation is on the only call path that unlocks vested/reward funds: [3](#0-2) 
```
public entry fun unlock_rewards(contract_address: address) acquires VestingContract {
    let accumulated_rewards = total_accumulated_rewards(contract_address);
    let vesting_contract = borrow_global<VestingContract>(contract_address);
    unlock_stake(vesting_contract, accumulated_rewards);
}
``` [4](#0-3) 
and `vest()` always calls `unlock_rewards()` first before vesting the scheduled grant portion. `distribute()` and `terminate_vesting_contract()` in turn call `vest`/`distribute`, meaning once `total_accumulated_rewards` reverts, the entire custody-recovery path (unlock → vest → distribute → withdraw to beneficiaries) for the vesting contract's stake, held in a resource account, is bricked with no alternate recovery function.

### Impact Explanation
Vesting contracts hold real APT stake in a resource-account-controlled stake pool on behalf of shareholders/beneficiaries. If `total_accumulated_rewards` permanently reverts for a given vesting contract, `unlock_rewards`, `vest`, `distribute`, and `terminate_vesting_contract` all become permanently unusable for that contract, since they all transitively depend on this computation succeeding. This results in a permanent, non-recoverable lock of custody-held value (the vesting contract's stake and unpaid rewards) with no admin/emergency-bypass function shown in the reviewed functions. This matches the "permanent lock or non-recoverable loss of ... resource-account-held value" custody impact.

### Likelihood Explanation
Likelihood is uncertain without being able to fully verify (given ask-only/index constraints) whether the invariant `total_active_stake >= remaining_grant + commission_amount` is always maintained across all state-mutating paths in `staking_contract.move` (e.g., commission rate updates, operator switch, restaking of rewards, or partial withdrawals that could desynchronize `remaining_grant` bookkeeping from the live stake-pool balance). The module's own formal-verification spec explicitly enumerates this underflow as a possible abort condition, indicating the authors were aware it is reachable under some state, but I could not fully trace every caller of `staking_contract::request_commission`/commission-rate-change functions to construct a concrete end-to-end trigger within the available tool budget.

### Recommendation
Guard the subtraction the same way the external report recommends for `Treasury._loadSwapState`: saturate to zero (or a well-defined recoverable state) instead of aborting when the pool is "undercollateralized" relative to `remaining_grant + commission_amount`, e.g.:
```move
let owed = vesting_contract.remaining_grant + commission_amount;
if (total_active_stake <= owed) { 0 } else { total_active_stake - owed }
```
Additionally, provide a recovery/admin path that does not depend on `total_accumulated_rewards` succeeding, so a desynchronized `remaining_grant` cannot permanently block distribution of already-vested/withdrawable funds.

### Proof of Concept
I was unable to construct and verify a concrete, fully-traced trigger (specific sequence of `staking_contract` calls that desynchronizes `remaining_grant` vs. `total_active_stake`) within the tool budget available in this session; this would require deeper tracing through `staking_contract.move`'s commission/principal update paths (`request_commission`, `update_commision_percentage`, `switch_operator`, etc.), which a background Devin agent with full repo/test access should verify directly, e.g. by writing a Move unit test that manipulates `commission_percentage` or triggers a `staking_contract` state change that reduces `total_active_stake` relative to `remaining_grant`, then calls `vest()`/`unlock_rewards()` and observes the abort.

```text
    public entry fun vest(contract_address: address) acquires VestingContract {
        // Unlock all rewards first, if any.
        unlock_rewards(contract_address);

        // Unlock the vested amount. This amount will become withdrawable when the underlying stake pool's lockup
        // expires.
        let vesting_contract = borrow_global_mut<VestingContract>(contract_address);
        // Short-circuit if vesting hasn't started yet.
        if (vesting_contract.vesting_schedule.start_timestamp_secs > timestamp::now_seconds()) {
            return
        };

        // Check if the next vested period has already passed. If not, short-circuit since there's nothing to vest.
        let vesting_schedule = &mut vesting_contract.vesting_schedule;
        let last_vested_period = vesting_schedule.last_vested_period;
        let next_period_to_vest = last_vested_period + 1;
        let last_completed_period =
            (timestamp::now_seconds() - vesting_schedule.start_timestamp_secs) / vesting_schedule.period_duration;
        if (last_completed_period < next_period_to_vest) {
            return
        };

        // Calculate how much has vested, excluding rewards.
        // Index is 0-based while period is 1-based so we need to subtract 1.
        let schedule = &vesting_schedule.schedule;
        let schedule_index = next_period_to_vest - 1;
        let vesting_fraction = if (schedule_index < schedule.length()) {
            schedule[schedule_index]
        } else {
            // Last vesting schedule fraction will repeat until the grant runs out.
            schedule[schedule.length() - 1]
        };
        let total_grant = vesting_contract.grant_pool.total_coins();
        let vested_amount = fixed_point32::multiply_u64(total_grant, vesting_fraction);
        // Cap vested amount by the remaining grant amount so we don't try to distribute more than what's remaining.
        vested_amount = min(vested_amount, vesting_contract.remaining_grant);
        vesting_contract.remaining_grant -= vested_amount;
        vesting_schedule.last_vested_period = next_period_to_vest;
        unlock_stake(vesting_contract, vested_amount);
```
