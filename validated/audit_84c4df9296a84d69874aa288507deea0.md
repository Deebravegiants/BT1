### Title
Webhook `shop` identity is not covered by HMAC verification, allowing tenant spoofing in `Registry.process` - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Registry.process` authenticates a webhook by validating the HMAC over the request body, then hands `request.shop` — a value taken from an unauthenticated HTTP header — to the app's `WebhookHandler`. The `shop` field is never part of the HMAC-signed payload, so the value the app trusts as the tenant identifier is not bound to the signature that proves the request came from Shopify.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop`, however, is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is attacker-controlled input, not authenticated data: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e., the raw body) and the app's secret, and never incorporates `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and, once it passes, immediately builds `WebhookMetadata` using the unauthenticated `request.shop` value, passing it straight to the app's handler as the trusted tenant identifier: [4](#0-3) 

This breaks the intended binding: `HMAC-verified(shop header) == shop used for tenant-scoped processing`. In reality, the equality that holds is only `HMAC-verified(raw_body) == raw_body`, while `shop` is asserted "for free," unchecked by cryptography. An attacker who can produce a request whose body legitimately belongs to a *different* shop's genuine webhook (e.g., by capturing/replaying a webhook payload for shop A, or exploiting any endpoint that forwards raw bodies) can freely rewrite the `X-Shopify-Shop-Domain` header to shop B before delivering it to the app's webhook endpoint. Since the header is not part of the signed content, `HmacValidator.validate` still returns `true` (the body/signature pair for shop A is untouched), yet `WebhookMetadata#shop` reports shop B. Any host application that uses `data.shop` from `WebhookHandler#handle` to select which tenant's records to update (a documented, expected usage pattern of this SDK, since `WebhookMetadata` exists specifically to carry `shop` to the handler) will perform the webhook's mutation against the wrong tenant.

### Impact Explanation
This is a cross-tenant access vector: a request cryptographically proven to originate from Shopify for shop A can be relabeled to target shop B's data path within the host application, because the gem provides no binding between the verified HMAC and the `shop` value it exposes as trustworthy. This matches the Critical impact category of cross-tenant access via a gem-level identity-binding failure — the boundary crossed is the per-shop authentication boundary that `HmacValidator.validate` is supposed to enforce for `Registry.process`.

### Likelihood Explanation
Exploitation requires the attacker to control or replay the raw body/header delivery to the app's webhook endpoint (e.g., a network position, logging/replay proxy, or an environment where an attacker can trigger Shopify to send them a real webhook for a shop they control, then relay that verbatim body to the victim's endpoint with a rewritten shop header). This is a realistic "unprivileged internet user" scenario since no access token, `api_secret_key`, or privileged Shopify account is needed — only the ability to receive one legitimately signed webhook (e.g., for the attacker's own installed app/shop) and resend its body to the target app's endpoint with a different shop header.

### Recommendation
Include `shop` (and other identity-relevant headers such as `topic`, `api_version`) in the value signed and verified by HMAC, or otherwise cryptographically bind the shop domain used to build `WebhookMetadata` to the same signed payload, so `HmacValidator.validate` fails if the shop context differs from what was originally signed. At minimum, document/require that host applications reconcile `WebhookMetadata#shop` against an app-side registry of shops with pending mandatory webhooks/subscriptions rather than trusting it implicitly. Add regression tests asserting that altering the shop header without altering the body invalidates processing.

### Proof of Concept
1. Register a webhook handler in the host app relying on `WebhookMetadata#shop` to select the tenant database record to update, per the documented `Registry.process` flow: [4](#0-3) 
2. Attacker installs the app on their own shop (`attacker-shop.myshopify.com`) and receives a legitimately Shopify-signed webhook (e.g., `orders/create`) with a valid `X-Shopify-Hmac-Sha256` for that raw body.
3. Attacker resends the identical raw body/HMAC pair to the victim app's webhook endpoint, but rewrites the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes HMAC solely over `@raw_body` [1](#0-0)  — it still matches, since body and signature are unchanged.
5. `Registry.process` passes and calls `handler.handle` with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` built from the spoofed header [5](#0-4) , causing the app to apply attacker-controlled webhook data under the victim shop's tenant context.
