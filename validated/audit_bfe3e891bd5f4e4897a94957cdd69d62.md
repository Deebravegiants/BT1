## Title
Webhook shop identity not covered by HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request` computes the value it trusts as webhook tenant identity (`shop`) from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `HmacValidator` checks only covers the raw request body. Any actor who can obtain one valid `(body, hmac)` pair for a webhook topic can replay that pair with an arbitrary `shop-domain` header and have it accepted as authentic, letting them impersonate a different tenant to the app's webhook handler.

## Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from HTTP headers, which are not part of the signed material: [2](#0-1) 

`Registry.process` validates the request using only `Utils::HmacValidator.validate(request)`, i.e., only the body, and then dispatches the handler with the *header-derived, unverified* `request.shop` as the tenant identity: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` recomputes the HMAC purely from `verifiable_query.to_signable_string` (the body) and compares it to the received `hmac`: [4](#0-3) 

The identity binding that should hold is:
`shop used to attribute/process the webhook == shop that Shopify actually signed for`

But because the signature only covers the body, this equality is never enforced — the equality that actually holds is only:
`body verified by HMAC == body received`, independent of `shop`, `topic`, `webhook_id`, `api_version`.

This means any two webhook deliveries that happen to share an identical raw body (e.g., a topic like `app/uninstalled`, `shop/redact`, or any payload with a fixed/predictable JSON shape, or simply a body the attacker's own shop received and captured) are cryptographically indistinguishable regardless of which shop or topic header accompanies them. An attacker who operates their own (attacker-controlled) shop installation of the app can:
1. Trigger a real webhook to their own store and capture the genuine `(raw_body, x-shopify-hmac-sha256)` pair Shopify sends.
2. Replay that exact body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain.
3. `HmacValidator.validate` succeeds (body+HMAC are genuinely valid), and `Registry.process` calls the handler with `WebhookMetadata` claiming `shop: <victim-shop>` for that (attacker-chosen) body.

Since the handler code that most integrating apps write keys tenant-scoped side effects (record updates, session/access revocation logic for `shop/redact` and `app/uninstalled`, GDPR data workflows, cache invalidation, etc.) directly off `WebhookMetadata#shop`, this breaks the tenant boundary the webhook mechanism is supposed to guarantee.

## Impact Explanation
This is a cross-tenant identity confusion: an unprivileged actor (any merchant who can install the app on their own store, or anyone who can otherwise obtain a valid body/HMAC pair for a given topic) can make the library report webhook data as belonging to an arbitrary victim shop. Any host application relying on `WebhookMetadata#shop` — which is the documented and only interface the gem exposes for this purpose — to scope processing to the correct tenant will act on the wrong tenant. This matches the "Critical: cross-tenant access" impact category.

## Likelihood Explanation
The likelihood is bounded by two factors: (1) the attacker needs a webhook endpoint they control reachable with attacker-chosen headers (many hosting setups pass through raw headers to app code unfiltered — the gem's own `Request.new` explicitly supports header normalization from various formats, e.g., `HTTP_X_SHOPIFY_*` from Rack, which are attacker/proxy-influenced in many deployment setups), and (2) a captured valid `(body, hmac)` pair for a topic whose body content is invariant or predictable across shops (mandatory compliance topics like `customers/redact`, `shop/redact`, `customers_data_request`, or webhooks with static/near-empty bodies, are good candidates). This does not require the app's `client_secret`, an access token, or any privileged account — only ordinary use of the app as a merchant/attacker-controlled tenant.

## Recommendation
Bind the identity fields to the signature verification, not just the body. Options:
- Have `Request#to_signable_string` (or a new signable representation) include `shop`, `topic`, and `webhook_id` alongside the body so HMAC validation fails if headers are tampered with independent of the body, OR
- Cross-check the header-derived `shop` against an out-of-band trusted source (e.g., require the caller to pass the expected shop/session, or validate against the shop associated with the session used to register the webhook) before dispatching to handlers.
- At minimum, document loudly that `request.shop` is unauthenticated header data and must never be trusted for tenant scoping without additional verification — and prefer to fail closed rather than silently trusting header content that sits outside the cryptographic envelope.

## Proof of Concept
```ruby
# 1. Attacker triggers (or otherwise obtains) a genuine webhook delivery to their own shop
#    "attacker-shop.myshopify.com" for a topic with a fixed/predictable body, e.g. "{}"
captured_body = "{}"
captured_hmac = "base64-hmac-that-Shopify-actually-sent-for-attacker-shop"

# 2. Attacker replays the exact same body+hmac but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic"       => "shop/redact",
  "x-shopify-hmac-sha256" => captured_hmac,       # still cryptographically valid for the body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # NOT covered by HMAC
  "x-shopify-webhook-id"  => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)

# HmacValidator.validate(request) only checks captured_body vs captured_hmac -> PASSES
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "shop/redact", shop: "victim-shop.myshopify.com", ...))
# The host app's handler now believes this legitimate-looking, HMAC-"verified" redact/uninstall
# event is for "victim-shop.myshopify.com", even though Shopify never sent this event for that shop.
```
