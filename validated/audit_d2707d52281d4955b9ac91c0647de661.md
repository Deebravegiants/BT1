### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted for tenant identity but excluded from the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`Webhooks::Request#to_signable_string` signs only the raw request body, while the shop identity (`shop-domain` header) and other metadata (`topic`, `webhook-id`, `api-version`) are read from unauthenticated HTTP headers and passed straight through to the app's webhook handler. This breaks the binding "the shop the HMAC proves the payload came from" == "the shop the handler is told the payload came from."

### Finding Description
`ShopifyAPI::Webhooks::Request#hmac` is computed by Shopify over the raw body only, and `Utils::HmacValidator.validate` checks that signature against `to_signable_string`, which returns just `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic linkage to the signed body: [2](#0-1) 

`Registry.process` only validates the HMAC (over the body) and then forwards `request.shop`, `request.topic`, and `request.webhook_id`—all header-derived, unsigned fields—to the app's handler as the authoritative tenant identity for the event: [3](#0-2) 

Because the app's `client_secret` (used as the HMAC key) is the same for every shop that installs the app, an attacker who legitimately installs the app on their own store can obtain a genuinely-signed webhook (valid HMAC over a body they fully control, e.g. by creating a product with an attacker-chosen title/body in their own store). They can then replay that exact raw body to the app's webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain (and/or a different `topic`/`webhook-id`). `Utils::HmacValidator.validate` will still pass, because the signature only covers `@raw_body`, which is unchanged. The app's handler then processes attacker-controlled data as if it came from the victim shop.

This exactly matches the reported bug class analog: a field ("shop", the tenant identity) is acted upon by the consuming code but is not covered by the integrity check (HMAC), while a different, signed field (body) is treated as sufficiently verified.

### Impact Explanation
This breaks the equality: `shop_the_HMAC_authenticates == shop_the_handler_trusts`. An attacker can make the host application attribute attacker-controlled webhook data to an arbitrary victim shop's tenant, which is a cross-tenant confusion vulnerability. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up per-shop offline access tokens, update per-shop state, or trigger shop-scoped side effects), this can lead to cross-tenant data corruption or the app taking privileged actions against a shop the attacker does not control, using attacker-authored payloads. This lands in the Critical category (cross-tenant access) per the given impact list.

### Likelihood Explanation
The prerequisite is that the attacker can install the target app on their own shop (a normal, unprivileged action available to any Shopify merchant/developer for a public app) and can trigger any webhook topic the app subscribes to with content they control (e.g. `products/create`). No leaked secrets, TLS interception, or privileged access are required—only the ability to replay an HTTP request with a modified header, which any unprivileged internet user with a dev store can do.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that is authenticated, or independently verify that the `shop-domain` header corresponds to a shop the app has an active session/install for before trusting it. At minimum, `to_signable_string` should not be the sole basis for trusting `shop`; the registry/handler dispatch should cross-check `request.shop` against known installed shops (e.g., via `SessionStorage`) rather than treating the header as authenticated by the body HMAC.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g. `products/create`) with a body they control, e.g. `{"id":1,"title":"PAYLOAD"}`. Shopify signs this body with the app's `client_secret`, producing a valid `X-Shopify-Hmac-Sha256` header.
3. Attacker captures the raw HTTP request (raw body + valid HMAC header) and replays it to the app's webhook endpoint, changing only the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) raw body against the HMAC: [4](#0-3) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, believing the data legitimately originated from the victim shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
