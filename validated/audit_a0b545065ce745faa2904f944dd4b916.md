Audit Report

## Title
Missing role check on Bridge Type `Show` (and `Index`) endpoints discloses external adapter URL to low-privileged users - (File: core/web/router.go)

## Summary
The `/v2/bridge_types/:BridgeName` `GET` route (`BridgeTypesController.Show`) and the `/v2/bridge_types` `GET` route (`Index`) are registered with only base authentication (`auth.Authenticate`, any role) while `Create`, `Update`, and `Destroy` for the same resource require `auth.RequiresEditRole`. Any authenticated user, including one holding only `UserRoleView`, can call `Show` and read the bridge's full configuration, including its `URL` field, which is otherwise treated as edit-restricted data.

## Finding Description
In `core/web/router.go`, the bridge type routes are registered as: [1](#0-0) 
`Index` and `Show` have no role wrapper, whereas `Create`, `Update`, and `Destroy` are wrapped in `auth.RequiresEditRole`. `BridgeTypesController.Show` performs no additional authorization beyond the parent `authv2` group's `auth.Authenticate` middleware (token or session, any role): [2](#0-1) 
`Show` fetches the bridge and serializes it directly via `presenters.NewBridgeResource`: [3](#0-2) 
`BridgeResource` unconditionally includes the `URL` field (`json:"url"`) sourced from `b.URL.String()`, with no redaction for lower roles: [4](#0-3) 
`auth.RequiresEditRole` explicitly rejects `UserRoleView` and `UserRoleRun`, confirming the intended access-control tier that is bypassed for read access: [5](#0-4) 
This is a genuine inconsistency: the write path enforces Edit role for the same resource whose read path (`Index`/`Show`) requires no role beyond generic authentication.

## Impact Explanation
Bridge `URL` values frequently encode operator-managed external adapter endpoints, which may include embedded basic-auth credentials or internal-network hostnames not intended for viewer-level users. A `UserRoleView` authenticated actor can enumerate bridge names via `Index` and retrieve full bridge configuration including `URL` via `Show`, without possessing the Edit role the system otherwise requires to view/manage this data. This is an authorization/confidentiality flaw (CWE-285/CWE-862) — a lower-privileged authenticated user obtaining data intended to require the Edit role.

## Likelihood Explanation
High. Exploitation requires only a valid low-privilege (`View`) session or API token and a single `GET` request; no additional preconditions, host access, or victim interaction are needed.

## Recommendation
Wrap `authv2.GET("/bridge_types", bt.Index)` and `authv2.GET("/bridge_types/:BridgeName", bt.Show)` with `auth.RequiresEditRole` (or another role check consistent with policy) in `core/web/router.go`, matching `Create`/`Update`/`Destroy`. Alternatively, redact `URL` (and other sensitive fields) from `BridgeResource` for viewer-role requests if broader read access to bridge names is intended to remain available.

## Proof of Concept
1. As an Edit/Admin user, create a bridge: `POST /v2/bridge_types` with `{"name":"mybridge","url":"http://internal-adapter.internal/secret-path?key=..."}`.
2. Create a session/API token for a separate user with role `View` only.
3. As the View-role user, call `GET /v2/bridge_types/mybridge` (or `GET /v2/bridge_types`).
4. Observe the response includes the full `url` field from `BridgeResource`, despite the requester lacking Edit role — demonstrating the read-path permission gap relative to the write-path's `auth.RequiresEditRole` enforcement.
