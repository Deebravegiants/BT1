### Title
Unspent swap input tokens are stranded and unlimited router approval lets a later caller steal them - (File: `contracts/external-actions/swaps/LifiExternalAction.sol`, `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`ExternalActionSwap.swap()` never returns or issues a UTXO for any part of the input token that the router does not actually consume, and `LifiExternalAction.callRouter()` grants the router an unlimited, persistent allowance over the contract's entire balance rather than only the amount transferred in for the current call. Because the router calldata (`externalActionData.externalActionMetadata`) is opaque, attacker-supplied bytes that are only hash-committed (not amount-constrained) by the circuit, a user can leave input-token dust stuck in the external action contract, and any later caller can craft calldata that causes the router to pull that stranded balance on top of their own declared amount — minting themselves a larger shielded output UTXO than what their own withdrawal from the shielded pool backs.

### Finding Description
In `swap()`: [1](#0-0) 
`inputAmount` is derived only from `deltaAmounts[0]` (the amount Hinkal debited from the caller's own shielded balance/nullifiers), then handed to `callRouter`. In `LifiExternalAction.callRouter()`: [2](#0-1) 
the router is given an unlimited allowance via `approveUnlimited`: [3](#0-2) 
and then `router.call(externalActionMetadata)` is invoked with fully attacker-chosen calldata. Nothing here (or in `Hinkal.sol`/`HinkalHelper.sol`) verifies that the router actually consumed exactly `inputAmount` of the input token — only `swappedAmount` (the *output* token balance delta) is measured and only `slippageValues[1] != 0` is checked, per: [4](#0-3) 

If the router under-consumes the approved input (e.g. the attacker's own calldata specifies a smaller sell amount than what Hinkal transferred to the contract, or partial-fill semantics of the aggregator leave dust), that leftover input token has no exit path: `swap()` only builds a UTXO for `outputToken`, never for unspent `inputToken`, so it is permanently stranded in the external-action contract's balance. Because the router's allowance is unlimited and persistent, and the swap calldata for *any subsequent call* is arbitrary attacker-chosen bytes bound only by a hash commitment (not by a constraint that its "sell amount" equals the caller's own `inputAmount`), a later caller can construct calldata that instructs the router to pull more of the contract's input-token balance than the amount Hinkal actually transferred them for that call. The resulting inflated `swappedAmount` becomes `amountToSendToHinkal`, which is transferred to Hinkal and turned into a legitimate-looking output UTXO for the attacker: [5](#0-4) 

Hinkal's own balance-equation check in `transact()` cannot catch this, because it only verifies that the output-token balance change equals the reported `utxoAmount` — by construction that always holds, since `utxoAmount` is derived from the same balance delta: [6](#0-5) 
There is no check tying the input side's actual consumption by the router to the caller's declared/proved `deltaAmounts[0]`. This breaks the intended equality "value withdrawn from the shielded pool by the prover == value fed into the external action and swapped for the prover's benefit."

### Impact Explanation
This allows theft of previously-stranded funds (originally another depositor's) and unbacked minting of shielded value: an attacker can receive an output UTXO whose value is not fully backed by their own withdrawal from the shielded pool, at the expense of whichever user's input tokens got stuck in the contract from an earlier partial swap. This qualifies as Critical (minting shielded value without backing / theft of shielded funds) under the stated impact criteria, since the attacker walks away with tokens that were never debited from their own commitment.

### Likelihood Explanation
Exploitation requires (1) some residual input-token balance to exist in the external action contract (achievable either by a prior user's swap that the router under-fills, or trivially by directly donating tokens to the well-known, immutable `LifiExternalAction` contract address — no protocol interaction required), and (2) crafting router calldata that pulls more than the declared `inputAmount`. Both are within reach of any unprivileged EOA that controls `externalActionData.externalActionMetadata`, since that field is opaque calldata forwarded verbatim to an external router and is only bound by a hash, not by an amount constraint.

### Recommendation
- Enforce, on-chain, that the router's actual token consumption for the *current* call equals `inputAmount` (e.g., measure and require `balanceBefore(inputToken) - balanceAfter(inputToken) == inputAmount`, refunding any unspent input back to Hinkal/the caller as a UTXO rather than leaving it in the contract).
- Replace the persistent `approveUnlimited` allowance with a just-in-time approval scoped to exactly `inputAmount` for each call, reset to zero afterward.
- Sweep/refund any residual token balance in the external-action contract at the end of each `runAction` call so no value can accumulate there between transactions.

### Proof of Concept
1. User A calls `transact()` with an external swap where `deltaAmounts[0] = -100` DAI; the router calldata A supplies only actually sells 1 DAI to the router (rest stays approved-but-unspent). `swap()` computes `amountToSendToHinkal` from the tiny output, creates a UTXO for that small amount, and the remaining ~99 DAI sits in `LifiExternalAction`'s balance with no accounting or refund path.
2. Attacker B calls `transact()` with their own legitimate `deltaAmounts[0] = -1` DAI (a tiny withdrawal from B's own shielded balance), but supplies router calldata that instructs the router to sell 100 DAI (pulling the full balance held by the contract, permitted by the pre-existing unlimited approval from step 1) for a much larger output amount.
3. `callRouter` measures `swappedAmount` as the full output-token balance delta (driven by the 100 DAI actually pulled, not B's declared 1 DAI), and `swap()` mints B a UTXO for that inflated amount.
4. Hinkal's balance-equation check passes trivially because it only compares the output-token balance delta to the reported `utxoAmount`, which are definitionally equal — B receives shielded value they never withdrew from their own balance, at User A's expense.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
