### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` allow `msg.value` to be counted once per index, minting unbacked shielded ETH - (File: contracts/Hinkal.sol)

### Summary
`Hinkal.transact` validates the balance change per-token by iterating `circomData.erc20TokenAddresses` and, for every entry equal to `address(0)`, adding the *entire* `msg.value` into `balanceDif` for that index. Because `erc20TokenAddresses` is never checked for uniqueness, an attacker can list `address(0)` at two indices, causing `msg.value` to be credited twice against two independent "balance equals amountChanges/onChainCreation + utxoAmount" checks, letting the same ETH deposit back two separate accounting terms (an `amountChanges` deposit at one index and an `onChainCreation` UTXO mint at the other).

### Finding Description
The invariant that should hold is: **for a given real-world ETH balance delta, `msg.value` should back exactly one accounting term** — either an `amountChanges` entry (internal/external transfer) or a UTXO amount (for `onChainCreation`), but not both simultaneously for the same ETH.

In `contracts/Hinkal.sol::transact`, the balances are snapshotted once via `getBalancesForArray(circomData.erc20TokenAddresses)` before (`oldBalances`) and after (`newBalances`) running the action [1](#0-0) . The verification loop then runs per-index:

```solidity
if (circomData.erc20TokenAddresses[i] == address(0)) {
    balanceDif = int256(newBalances[i]) + int256(msg.value) - int256(oldBalances[i]);
} else {
    balanceDif = int256(newBalances[i]) - int256(oldBalances[i]);
}
...
require(
    balanceDif ==
        (circomData.onChainCreation[i] ? int256(0) : circomData.amountChanges[i]) +
            int256(utxoAmount),
    "Balance Diff Should be equal to sum of onchain and offchain created commitments"
);
``` [2](#0-1) 

Neither `dimensionsCheck` nor `checkOnchainCreation` in `contracts/HinkalHelper.sol` enforce uniqueness of `erc20TokenAddresses` entries; they only check array-length equality across the various `CircomData` fields [3](#0-2)  and per-index onChainCreation constraints (`amountChanges[i]==0`, `inputNullifiers[i]` all zero) [4](#0-3) . `performHinkalChecks` calls both but never rejects duplicate token addresses [5](#0-4) .

Because `oldBalances[i]`/`newBalances[i]` are recomputed from `getERC20OrETHBalance(address(0))` = `address(this).balance` for *every* matching index (`getBalancesForArray` in `contracts/Transferer.sol`, lines 169-176), duplicate `address(0)` entries at indices `i` and `k` yield identical `oldBalances[i]==oldBalances[k]` and `newBalances[i]==newBalances[k]` — i.e., there is only **one** real ETH delta, but the loop adds `msg.value` to `balanceDif` independently at both `i` and `k`. If, for example, index `i` has `onChainCreation[i] == false` with `amountChanges[i] = msg.value` (an ETH deposit into an external action), and index `k` has `onChainCreation[k] == true` with `amountChanges[k] == 0` (forced by `checkOnchainCreation`) and a UTXO of amount `msg.value` returned in `utxoSet` matching `erc20TokenAddresses[k] == address(0)`, then:
- At index `i`: `balanceDif_i = realDelta + msg.value` must equal `amountChanges[i] + utxoAmount_i`. This is satisfied by the normal deposit accounting.
- At index `k`: `balanceDif_k = realDelta + msg.value` (same `realDelta`, same `msg.value`) must equal `0 + utxoAmount_k`. Since the attacker controls the `CircomData`/proof for their own UTXOs, they can set `utxoAmount_k = realDelta + msg.value`, i.e., mint an on-chain UTXO backed by the *same* ETH that already backed the deposit at index `i`.

The single real ETH inflow (`msg.value`) is thus used to satisfy two independent balance equations, letting the attacker mint a shielded/on-chain ETH UTXO that is not backed by any additional ETH sent to the contract — the protocol's aggregate liabilities (UTXO tree value) grow by `utxoAmount_k` while the contract's actual ETH balance only grew by the single `msg.value` already consumed by the other term.

Existing guards do not prevent this: `dimensionsCheck` and `checkOnchainCreation` never assert `erc20TokenAddresses` entries are unique [6](#0-5) ; `verifyProof`/circuit constraints operate on the `amountChanges`/`onChainCreation` values supplied per index and do not know that two indices map to the physically identical `address(0)` balance, so they cannot detect the double use of the same ETH; and the on-chain balance snapshot mechanism (`getBalancesForArray`) is index-based, not address-deduplicated, so it faithfully re-reads the same balance twice rather than erroring.

### Impact Explanation
The attacker mints a shielded/on-chain ETH UTXO without depositing any additional ETH to back it, i.e., value is created in the Hinkal system without a corresponding real ETH inflow. This directly matches "minting shielded value without backing (protocol insolvency)," a Critical-severity issue, since it allows the attacker to later withdraw the unbacked UTXO for real ETH, draining funds belonging to other users. The attack is repeatable per transaction subject to the attacker's ability to construct a valid proof/circuit input for the extra UTXO and (for the external-action path) an external action such as `EmporiumUpgradeable` that returns a `utxoSet` entry for the duplicated index.

### Likelihood Explanation
- The attacker needs no privileges: they craft their own `CircomData` (including `erc20TokenAddresses`, `amountChanges`, `onChainCreation`, `slippageValues`) and their own valid ZK proof, and call `Hinkal.transact` directly.
- The attacker must get an external action (or the internal path) to return/accept a UTXO matching the duplicated `address(0)` index with the desired amount, which requires the ability to control `externalActionMetadata`/action behavior (attacker can use registered actions like the Emporium, whose `runAction` in `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol` iterates over the same `circomData.erc20TokenAddresses` array and independently computes `balanceChange`/`handleOut` per index, so a duplicated `address(0)` index there can likewise produce a second UTXO/payout from the same underlying balance delta).
- Cost is only proof-generation effort and gas; no special role or timing is required, and the exploit is repeatable.

### Recommendation
Enforce uniqueness of `erc20TokenAddresses` entries in `dimensionsCheck` (or a new dedicated check) called from `HinkalHelper.performHinkalChecks`, rejecting any `CircomData` where the same token address (including `address(0)`) appears more than once. Alternatively, restructure the balance-equation loop in `Hinkal.sol::transact` to add `msg.value` to the aggregate ETH delta exactly once (e.g., compute a single global ETH balance check outside the per-token loop) rather than per matching index, and apply the analogous fix to `EmporiumUpgradeable.runAction`'s per-index `balancesBefore`/`balancesAfter` handling.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and a registered `EmporiumUpgradeable` (or a minimal external action) exposing `runAction`.
2. Construct `CircomData` with `erc20TokenAddresses = [address(0), address(0)]`, `onChainCreation = [false, true]`, `amountChanges = [X, 0]`, matching `slippageValues`, and a valid locally-generated proof for a corresponding circuit input that produces one off-chain deposit of `X` (`amountChanges[0]`) and one on-chain UTXO output of amount `Y` at index 1.
3. Craft the external action (or use `EmporiumUpgradeable` with an op that leaves `balanceChange` at index1 equal to `X`) so that `utxoSet` returns a UTXO with `erc20Address == address(0)` and `amount == Y`, where `Y > X` (i.e., `Y` exceeds the real ETH inflow).
4. Call `Hinkal.transact{value: X}(...)`.
5. Assert: (a) the call succeeds (both balance-equation `require`s pass), (b) `address(this).balance` after the call increased by exactly `X` (or less, if any ETH left via relay/fees), while (c) the newly inserted on-chain commitment / minted UTXO records value `Y > X`, demonstrating `mintedShieldedValue (Y) > actualETHDelta (X)` — i.e., the equality `msg.value backing == exactly one accounting term` is violated and unbacked shielded ETH was minted.

    function dimensionsCheck(
        CircomData calldata circomData,
        Dimensions calldata dimensions
    ) internal pure {
        require(
            circomData.erc20TokenAddresses.length == dimensions.tokenNumber,
            "erc20TokenAddresses number should be equal to token number"
        );
        require(
            circomData.amountChanges.length == dimensions.tokenNumber,
            "AmountChanges number should be equal to token number"
        );

        require(
            circomData.onChainCreation.length == dimensions.tokenNumber,
            "onchain creation is equal to tokens count"
        );

        require(
            circomData.slippageValues.length == dimensions.tokenNumber,
            "slippageValues length should be equal to tokens count"
        );

        require(
            circomData.inputNullifiers.length == dimensions.tokenNumber,
            "InputNullifiers number should be equal to token number"
        );

        uint previousNullifierAmount = circomData.inputNullifiers.length > 0
            ? circomData.inputNullifiers[0].length
            : 0;
        for (uint i = 1; i < circomData.inputNullifiers.length; i++) {
            require(
                circomData.inputNullifiers[i].length == previousNullifierAmount,
                "Nullifier amount should be equal"
            );
        }
        require(
            previousNullifierAmount == dimensions.nullifierAmount,
            "Actual and Claimed Nullifier Amount should be equal"
        );

        require(
            circomData.outCommitments.length == dimensions.tokenNumber,
            "OutCommitments number should be equal to token number"
        );

        uint previousCommitmentAmount = circomData.outCommitments.length > 0
            ? circomData.outCommitments[0].length
            : 0;

        for (uint i = 1; i < circomData.outCommitments.length; i++) {
            require(
                circomData.outCommitments[i].length == previousCommitmentAmount,
                "Commitment amount should be equal"
            );
        }
        require(
            previousCommitmentAmount == dimensions.outputAmount,
            "Actual and Claimed Commitment Amount should be equal"
