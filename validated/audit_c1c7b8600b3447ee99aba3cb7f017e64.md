### Title
Webhook shop/topic identity is trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC signature to `@raw_body` only, but `Registry.process` dispatches the webhook handler using `request.shop`, `request.topic`, and `request.webhook_id`, all of which are read directly from HTTP headers that are never covered by the HMAC. This breaks the identity binding `HMAC-verified-bytes == bytes-the-handler-trusts-as-shop/topic`, analogous to the Seaport `errorBuffer` bug where a value that should have been fully validated (all failure modes covered) was instead only partially checked, letting unchecked/mismatched inputs flow through as "valid".

### Finding Description
`lib/shopify_api/webhooks/request.rb`:
```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end

def shop
  T.cast(shopify_header("shop-domain"), String)
end

def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` all come from `shopify_header(...)`, i.e. HTTP request headers supplied by whoever sends the POST to the app's webhook endpoint. None of these values participate in `to_signable_string`, so `HmacValidator.validate_signature` only proves that the sender possesses the shared secret and that `@raw_body` was signed by it — it proves nothing about which shop or topic the request claims to be for. [2](#0-1) 

`Registry.process` then trusts these unauthenticated header values directly:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

**Identity binding broken (as an equality):**
`shop_the_handler_believes_this_is_for` (header `X-Shopify-Shop-Domain`, unauthenticated) ≠ `shop_that_the_HMAC_actually_certifies` (nothing — the HMAC certifies only `@raw_body`).

**Before the attacker's request:** a legitimate webhook from Shopify has `hmac = HMAC(secret, body)` and header `shop-domain = shopA.myshopify.com`, and both are consistent because Shopify itself set both fields for the same event.

**After the attacker's request sequence:** an attacker who operates their own Shopify store (installed the app) receives a genuinely-signed webhook `(body B, hmac = HMAC(secret, B), shop-domain = attackerShop)`. They replay this exact `(body B, hmac)` pair to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with a victim shop's domain / a different topic. `Utils::HmacValidator.validate(request)` still succeeds because it only checks `body` against `hmac`; `request.shop` and `request.topic`, read straight from the attacker-controlled headers, are passed unmodified into `WebhookMetadata` and into the registered handler.

### Impact Explanation
This crosses a tenant boundary: the handler executes host-application logic (e.g., writing order/customer/product data, triggering redaction handling for `shop/redact`, `customers/redact`, `customers/data_request`, or any app-specific business logic keyed off `shop`) believing the event legitimately originates from and pertains to the victim shop, when in fact the payload content was authored by/for the attacker's own store. This is a cross-tenant data-integrity/confusion issue reachable by any internet user who controls a Shopify store and can install the target app (i.e., no `api_secret_key`, no access token, and no privileged account for the *victim* tenant is required — the attacker only needs a legitimately signed message for a tenant they themselves control).

### Likelihood Explanation
Exploitability requires only that the attacker (a) can install the merchant app on a store they control to obtain one genuinely HMAC-signed webhook payload, and (b) can send an arbitrary HTTP POST to the app's public webhook endpoint with forged `X-Shopify-*` headers (trivial with `curl`). No secret material or victim credentials are needed since the exploit is a header-substitution replay of a body the attacker legitimately signed for themselves. The main constraint is that `body` content is fixed by what the attacker's own store's webhook contained, limiting the payload the attacker can inject, but topic/shop confusion alone (e.g., causing the app to process a `customers/redact` or `orders/create` handler under the wrong shop identity) is enough to constitute cross-tenant impact.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed material, or otherwise cryptographically tie the header claims to the payload, before trusting them in `Registry.process`. Concretely, change `Request#to_signable_string` to include a canonical representation of `shop`, `topic`, and `webhook_id` alongside `@raw_body` (mirroring how `Oauth::AuthQuery#to_signable_string` binds all trust-relevant fields, not just a subset), and reject the webhook if the reconstructed signable string doesn't match the received `hmac`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a webhook, e.g. `customers/redact`, to the app's endpoint: headers `X-Shopify-Topic: customers/redact`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over body B>`, with body `B`.
2. Attacker captures `(B, valid HMAC)`.
3. Attacker crafts a new POST to the same webhook endpoint using the same `B` and the same `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and/or a different `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, B)` — unaffected by header changes. [4](#0-3) 
5. `Registry.process` looks up the handler for the attacker-chosen `request.topic` and invokes it with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed_body_of_B, ...)`, causing the app to process attacker-authored data under the victim shop's identity. [5](#0-4)
