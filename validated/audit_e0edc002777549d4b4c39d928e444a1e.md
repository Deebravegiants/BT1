## Title
Webhook `shop` field is trusted by `Webhooks::Registry.process` without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while the tenant-identifying `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is never included in the signed content. `Webhooks::Registry.process` nonetheless treats `request.shop` as an authenticated tenant identifier and hands it straight to the app's webhook handler, creating a binding mismatch between "the bytes the HMAC verifies" and "the shop the handler is told the event belongs to."

### Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) [2](#0-1) 

`shop` is read from an HTTP header that is completely independent of `to_signable_string`: [3](#0-2) 

`HmacValidator.validate` only re-computes and compares the signature over `to_signable_string`, i.e. the raw body — it never incorporates `shop`, `topic`, `webhook_id`, or `api_version`: [4](#0-3) 

`Registry.process` calls `HmacValidator.validate(request)` and, on success, forwards `request.shop` (the unauthenticated header) directly to the handler as the tenant identity of the event: [5](#0-4) 

Because Shopify apps sign all webhooks to a given app with a single, app-level `api_secret_key` (shared across every shop that installs the app, not per-shop), a valid `(raw_body, hmac)` pair is not bound to any particular shop. Anyone who can obtain one genuine, signed webhook payload for the app (e.g. by installing the app on their own development/test store and capturing a real webhook delivery) possesses a body/HMAC pair that passes `HmacValidator.validate` unconditionally, regardless of what `shopify-shop-domain` value they attach when replaying the request to the app's public webhook endpoint.

The identity binding that should hold is:
`shop authenticated by HMAC == shop attributed to the delivered event`

but the actual binding enforced by the code is:
`bytes verified by HMAC (raw_body only) == bytes verified by HMAC`, with `shop` carried along unauthenticated.

### Impact Explanation
An unprivileged internet user with no access token, no `client_secret`, and no privileged account can cause the host application to process a webhook body under an arbitrary victim shop identity of the attacker's choosing, since `Registry.process` accepts the request as valid and passes `WebhookMetadata` (including the attacker-controlled `shop`) to the app's handler. Any host logic that keys per-tenant state, access-control decisions, or side effects off `data.shop` (as intended and documented by this gem) can be tricked into acting as if the event originated from a different, victim shop — a cross-tenant identity confusion rooted entirely in this gem's webhook verification design (`Request#to_signable_string` + `HmacValidator` + `Registry.process`), not in host misuse.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the app on any shop they control (readily available to any internet user with a free/dev Shopify store) to obtain one legitimate `(raw_body, hmac)` pair, and (2) replaying that exact body/HMAC to the app's public webhook URL while swapping the `shopify-shop-domain` header value. No secret material, TLS interception, or social engineering is needed — this is a direct consequence of the signature scope chosen in `Webhooks::Request#to_signable_string`.

### Recommendation
Bind the claimed `shop` (and ideally `topic`/`webhook_id`) into the signed content verified by `HmacValidator`, or otherwise require that `Registry.process` cross-check the delivered `shop` against an independently-established, per-shop webhook registration/subscription record before trusting it as the event's tenant. At minimum, document prominently that `request.shop` is unauthenticated header data and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any webhook subscribed by the app (e.g. `orders/create`), capturing the exact `raw_body` and the `shopify-hmac-sha256` header Shopify sent — both are valid because they were signed with the app's `api_secret_key`.
2. Attacker POSTs to the app's webhook endpoint, keeping `raw_body` and `shopify-hmac-sha256` identical, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Request.new` accepts it (all required headers present); `HmacValidator.validate(request)` succeeds because it only checks `Digest.hexencode(Base64.decode64(hmac_header))` against `HMAC(raw_body, api_secret_key)` — `shop` is irrelevant to this check. [6](#0-5) 
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop == "victim-shop.myshopify.com"` and invokes the handler, even though the underlying event data actually originated from `attacker-shop.myshopify.com`. [7](#0-6)

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
