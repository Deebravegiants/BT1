The key detail confirming the analog: `Bonding` uses `Ownable2StepUpgradeable` for the *protocol owner* (a two-step, error-tolerant transfer), but `transferCreator` — the analogous ownership-of-fee-stream handoff for **creators**, an unprivileged, permissionless role — is a single-step, immediate write with no accept/confirm step and no way to reverse a mistake.### Title
Single-step `transferCreator` permanently misdirects future creator fee revenue on address typo, with no recovery - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.transferCreator` lets a token's creator repoint all future creator-side trading fees to a new address in one unconfirmed, irreversible call, unlike the protocol owner role which uses `Ownable2StepUpgradeable`'s pending/accept pattern precisely to guard against this class of mistake.

### Finding Description
`Bonding.transferCreator` only checks that `newCreator != address(0)` and `newCreator != info.creator`, then immediately overwrites `info.creator` in one transaction: [1](#0-0) 

`info.creator` is the sole attribution key used every time `Zap` accrues fees: `Zap` reads `Bonding.tokenInfo(token).creator` and forwards `creatorAmount` into `FeeVault.accrue(token, creator, ...)`, which credits `creatorBalance[creator]`, a mapping keyed purely by that address: [2](#0-1) [3](#0-2) 

There is no allowlisting, no pending/accept two-step confirmation, and no on-chain sanity check that `newCreator` is an address the caller actually controls — the exact class of gap the external report flags ("no checking… no way to recover the wrong payments"). By contrast, the protocol notably *does* use the safer `Ownable2StepUpgradeable` pattern for its own owner role elsewhere in the same package (confirmed present in `Bonding.sol`'s imports/inheritance), showing the team is aware of and mitigates this exact mistake class for the admin role but not for the creator role, which is reachable by any unprivileged token creator.

Since `FeeVault.creatorBalance` is keyed by address and future accruals are computed at trade time using the live `info.creator`, a fat-fingered or otherwise incorrect `newCreator` argument immediately and permanently redirects every subsequent 0.25% creator-side fee (on every buy and sell of that token, curve and post-graduation, indefinitely) to an address the real creator does not control. Only the *new* (now-wrong) address can call `transferCreator` again — the original creator has no way to reverse the mistake, matching the reported bug class of "no way to recover the wrong payments for users."

### Impact Explanation
This is a direct, permanent loss of future creator fee revenue for the misdirected token. Unlike the cited Gitcoin report where the loss is bounded to a single vote/payment round, here the misdirection is durable: every trade of the token forever after the mistaken call routes its 0.25% creator fee to the wrong address, with `lifetimeCreatorEarned` and pooled `creatorBalance` accruing irretrievably to a party who is not the actual creator. This satisfies the "permanent freezing/loss of creator funds" bar for a Medium finding, since the true creator can never claim these accrued fees and has no recourse.

### Likelihood Explanation
Likelihood is realistic but not high: it requires the token's own creator to submit a malformed/incorrect `newCreator` argument (e.g., copy-paste error, wrong-chain address, wrong case-sensitive checksum handling in a UI/script) with no on-chain safeguard to catch it, similar to the class of "wrong address" mistakes cited in the referenced report. Any single unprivileged creator can trigger this on their own token via a normal, permitted call to `transferCreator` — no special privilege beyond being the current creator is needed.

### Recommendation
Convert `transferCreator` to a two-step pending/accept pattern mirroring `Ownable2StepUpgradeable`: store `newCreator` in a `pendingCreator[token]` slot on the first call, and require the new address to call an `acceptCreator(token)` function to finalize the change. This ensures the address is reachable/controlled before fee attribution is switched, eliminating unrecoverable fat-finger losses while preserving permissionless creator self-service.

### Proof of Concept
1. Creator `C` launches a token via `Zap.createToken`, becoming `Bonding.tokenInfo(token).creator == C`.
2. Trading proceeds normally; `Zap` accrues 0.25%-per-trade creator fees into `FeeVault.creatorBalance[C]`.
3. `C` calls `bonding.transferCreator(token, mistakenAddress)` intending to send it to their own multisig `M` but mistypes/pastes the wrong address (`mistakenAddress != M`), passing only the `!= address(0)` and `!= info.creator` checks: [1](#0-0) 
4. From this block forward, every `Zap.buy`/`Zap.sell` on `token` accrues its 0.25% creator fee into `FeeVault.creatorBalance[mistakenAddress]` instead of `M`, as shown by the accrual flow keyed on `info.creator`: [3](#0-2) 
5. `mistakenAddress`, if it belongs to no one the creator controls (e.g., a burn address, an exchange deposit address, or a non-existent EOA), can never call `FeeVault.claim()` on `C`'s behalf, and `C` has no further call available on `Bonding` to reverse the assignment — all future creator fee revenue for that token is permanently lost.

## Fees & FeeVault

All fees are charged by `Zap` in USDC and forwarded into `FeeVault`. The router holds no fee state — the vault is where balances live and where creators and the protocol claim.

- **Rate:** 0.75% on every buy/sell (curve **and** post-grad), split 0.5% protocol / 0.25% creator.
- **Accrual:** `Zap` transfers the fee USDC to `FeeVault`, then calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)`. Creator attribution comes from `Bonding.tokenInfo(token).creator` (set at launch, updatable via `transferCreator`).
- **Claims:** `FeeVault.claim()` pays the caller their pooled USDC balance across every token they've launched. `FeeVault.claimProtocol()` is permissionless and pays the configured `feeTo` — anyone can trigger the payout, but funds always go to the admin-set address.
- **Lifetime counters:** `lifetimeCreatorEarned(creator)` / `lifetimeProtocolEarned` never decrement on claim, so the UI can render "total earned / claimed / claimable" consistently.
- **Router swapability:** The vault has an owner-controlled depositor allowlist. A new router is whitelisted, the old router removed, and creator balances are untouched during the transition.
- `transferCreator(tokenAddress, newCreator)` (on `Bonding`) — transfers role and future fee attribution.

    function accrue(
        address token,
        address creator,
        uint256 creatorAmount,
        uint256 protocolAmount,
        bool isBuy
    ) external onlyDepositor {
        FeeVaultStorage storage $ = _s();
        if (creatorAmount > 0) {
            if (creator == address(0)) revert ZeroAddress();
            $.creatorBalance[creator] += creatorAmount;
            $.totalAccruedCreator += creatorAmount;
            $.lifetimeCreatorEarned[creator] += creatorAmount;
        }
        if (protocolAmount > 0) {
            $.protocolBalance += protocolAmount;
            $.lifetimeProtocolEarned += protocolAmount;
        }
        if ($.usdc.balanceOf(address(this)) < $.totalAccruedCreator + $.protocolBalance) {
            revert UnderfundedAccrual();
        }
        emit FeeAccrued(token, creator, creatorAmount, protocolAmount, isBuy);
    }
