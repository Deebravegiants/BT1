### Title
Spot-balance weighting of phantom price snapshots allows JIT/flash-loan-style manipulation of published pool rates - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
`aggregatePhantomBids` weights every solver's quote in a phantom order's price snapshot purely by that solver's **instantaneous, unlocked** balance of the leg's output token, read via a single live RPC call (`getBalance`) at aggregation time. There is no time-weighting, holding-period requirement, or "early withdrawal" type penalty analogous to what the Ajna report calls for — the same bug class ("manipulation of a periodically-sampled, capital-weighted metric via transiently-held capital") applies here, except the mechanism is even weaker than an EMA because it takes the raw spot reading with zero smoothing.

### Finding Description
`aggregatePhantomBids` (`sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1479-1497`) computes each bidder's weight as: [1](#0-0) 

`getBalance` is a memoized wrapper around a live RPC read of ERC-20/vault balance (no historical block pinning is enforced for this weighting path, unlike the later-added per-event refresh which explicitly pins to a specific block — see the design note that periodic sweeps intentionally read "at the chain head"): [2](#0-1) 

The weight then feeds `weightedMedian`, which is a **selection**, not a blend — the bidder that holds a majority of the total weight for a leg sets the published price verbatim: [3](#0-2) 

This is confirmed by the SDK's own doc comments and tests: "a solver holding over half the leg's weight sets the published price verbatim": [4](#0-3) [5](#0-4) 

Any account can become a phantom-order "solver" bidder by EIP-7702-delegating an EOA to the chain's `SolverAccount` implementation and signing a `UserOperation` — this is a permissionless, unprivileged path (matching the "intent solver" reachable role): [6](#0-5) 

Because a phantom order is only a **probe** — "a probe commits no capital" — the attacker never has to actually deliver the quoted output; they only need their wallet/vault balance of the output token to be large at the moment the indexer's aggregation runs: [7](#0-6) 

The resulting `medianPrice`/`lowestPrice`/`highestPrice` are persisted into `PhantomOrderPriceSnapshotV2` and then folded into the `LiquidityPool.sellRate`/`buyRate` used by `updateLiquidityPools`, which is a depth-weighted mean over these medians: [8](#0-7) [9](#0-8) 

These pool rates are then consumed by real fillers as the reference curve for pricing genuine cross-chain fills, per the FX filler's own documented flow ("curve sampled at THIS leg's size"): [10](#0-9) 

This is precisely the bug class in the Ajna report: a periodically-sampled, capital-weighted signal (there: EMA of target utilization; here: liquidity-weighted median of phantom quotes) that is manipulable by an actor who only needs to hold capital for the brief window between placing the bid and the aggregation's balance read, with no lock-up, no vesting, and no penalty for immediately moving the funds elsewhere afterward.

### Impact Explanation
An attacker (acting as an unprivileged, permissionlessly self-delegated "solver") can:
1. Acquire a large balance of a leg's output token on the destination chain (via a short-term loan, a large but temporary transfer, or borrowing) shortly before a phantom order's bid window closes.
2. Submit an extreme (favorable-to-attacker) quote for that leg.
3. Because their balance dominates total weight, `weightedMedian` returns their quoted price verbatim as `medianPrice`.
4. This manipulated median propagates into `PhantomOrderPriceSnapshotV2` and the depth-weighted `LiquidityPool.sellRate`/`buyRate`, which downstream real fillers (e.g. FXFiller) use as their pricing curve for actual user fills.
5. Real users filling intents against the corrupted rate receive a worse (or, depending on direction, an attacker-favorable arbitrage) price than the true market rate, and legitimate solvers' liquidity/pricing decisions are skewed. This is a concrete route to loss of funds for users/protocol participants via mispriced fills, satisfying the "unbacked mint / unsound state / forged pricing signal" bar for a Medium-severity finding.

Unlike the Ajna EMA case, there is no smoothing (12h EMA) at all here — a single manipulated bid dominates the metric outright provided the attacker's balance exceeds the combined weight of all other bidders for that leg, which is easy when legitimate solver liquidity for a given token/chain pair is thin (the docs themselves note legs with zero legitimate weight are common and dropped entirely).

### Likelihood Explanation
Medium likelihood. The attack does not require a true same-transaction atomic flash loan (the balance read happens off-chain, asynchronously, after the triggering block is finalized, so same-tx flash-loan repayment would erase the inflated balance before it is observed). It does require the attacker to hold borrowed/temporary capital across at least one block/aggregation window — a materially cheaper and lower-risk operation than a full collateralized loan, but not literally "free" like a single-block flash loan. This is the same "just-in-time liquidity" class of risk the Ajna report highlights, and it is the practical, currently-reachable analog to that report's concern in this codebase, since `IIntentPriceOracle.recordSpread`'s VWAP path (the closer literal analog to Ajna's TU/EMA weighting) has already been disconnected from `fillOrder` per a prior security-audit remediation.

### Recommendation
- Weight phantom-bid quotes by a time-averaged or historically-committed liquidity measure (e.g., an EMA of the solver's balance sampled over multiple blocks/windows, or a minimum holding-period requirement) rather than a single spot RPC read at aggregation time.
- Pin the balance read used for weighting to a block that predates the bid-window open (as is already done for the unrelated per-event liquidity refresh path), so an attacker cannot inflate their balance after committing to a quote.
- Apply a cap on how much weight/share of the total any single solver's balance can contribute to a leg's median, so a single well-funded (even briefly) actor cannot unilaterally set the published price.
- Consider requiring solvers to actually escrow/lock the quoted capital for some minimum duration before their quote counts toward the weighted median, mirroring the withdrawal-penalty style deterrent the original report recommends for Ajna's collateral deposits.

### Proof of Concept
1. Attacker EOA self-delegates via EIP-7702 to the chain's canonical `SolverAccount` implementation (permissionless, standard onboarding for any solver).
2. Shortly before a `PhantomOrderV2`'s bid window is expected to close, attacker acquires a large balance of the leg's output token on the destination chain (loan, large temporary transfer, etc.).
3. Attacker signs and submits a `UserOperation` bid via `intents_getBidsForOrder`'s submission path quoting an extreme output amount for that leg.
4. `PhantomBidWindowExhausted` fires; the indexer calls `aggregatePhantomBids`, which reads the attacker's (currently inflated) balance via `getBalance` at the current chain head and computes `weightedMedian` — dominated by the attacker's weight, it returns the attacker's quoted price as `medianPrice`/`lowestPrice`/`highestPrice`. [11](#0-10) 
5. `updateLiquidityPools` folds this manipulated snapshot into `LiquidityPool.sellRate`/`buyRate`.
6. Attacker returns/unwinds the borrowed balance.
7. Subsequent real fills priced off the corrupted `LiquidityPool` rate settle at the manipulated price, transferring value away from the counterparty (user or protocol) that trusted the published rate.

Note: I was unable to fully verify the exact timing window between bid-window closure and the indexer's RPC read (i.e., precisely how many blocks/seconds an attacker must sustain the inflated balance), since that depends on live indexer/pallet configuration not fully present in the indexed code. This affects only the attack's capital cost/duration, not the underlying design flaw.

export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

# 2026-09-01 — Per-event reads are pinned to the event's block (#1159)

Chosen: the balance and position reads a refresh performs are pinned to the block of the event that triggered
them, via the SDK's `blockTag` parameter, and the read memo is keyed by that block so several events in one block
share one set of reads.

Alternative rejected — read at the chain head, as the periodic sweep does. It is what the first cut did, and it
is not replayable: reindexing an old fill would stamp today's balance onto it. The pool guard (skip a pool whose
last snapshot postdates the event) hid that by making the refresh a no-op during a resync; pinning the reads
makes the guard a cost optimization rather than the only thing standing between a replay and wrong data.

Only the event's own chain is pinned. Block numbers are per chain and a refresh reaches across every chain the
pool is quoted on, so the others stay at the head — the correct reading available for them.
