### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers when constructing the `WebhookMetadata` passed to the app's handler. Because the shop identity is never bound to the signed bytes, a request whose body/HMAC pair is valid for one shop can be replayed with a different `shop-domain` header and will still pass validation, attributing the payload to an arbitrary tenant.

### Finding Description
`Utils::HmacValidator.validate` verifies the HMAC exclusively against `verifiable_query.to_signable_string`, which for webhooks is defined as the raw request body only: [1](#0-0) 

The `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from request headers that are entirely outside the HMAC's signed scope: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the app's handler, with no cross-check that the signed body actually corresponds to that shop: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no relation enforced to the HMAC-covered bytes: [4](#0-3) 

Because `Context.api_secret_key` is a single app-wide secret shared across every shop that installs the app (not a per-shop secret), any merchant who installs the app can capture a legitimately-signed webhook delivered to their own shop (valid body + valid HMAC), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop. `Utils::HmacValidator.validate` only recomputes the HMAC over the body, so it still succeeds, and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim shop as the source. This breaks the identity binding "the shop authenticated (by a valid HMAC computed with the app secret) must equal the shop stored/acted upon (the `shop` field used by the handler to scope data/tenant operations)".

### Impact Explanation
Any app that uses `data.shop` from `WebhookMetadata` to scope database writes, feature toggles, billing state, or other per-tenant side effects (the exact pattern shown in this gem's own documentation and tests) can have its cross-tenant isolation broken: a malicious but valid app-installer can inject attacker-controlled webhook bodies under another merchant's shop identity. This matches the cross-tenant access category since one merchant's authenticated request stream can create/mutate data attributed to a different tenant.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even unprivileged) installer of the target app — no access to `api_secret_key`, access tokens, or the victim's credentials is needed. The attacker simply captures one real webhook delivery to their own shop and replays it with a different `shop-domain` header value, which is trivial given the header is not part of the signed material.

### Recommendation
Bind the shop identity to the signed payload instead of trusting an unauthenticated header. Shopify's actual webhook payloads (JSON body) already include shop-identifying fields; at minimum, `Request#shop` should never be treated as authenticated identity independent of body contents. Alternatively, gate the `Registry.process` flow by cross-validating `request.shop` against the offline session/shop record with a stored per-shop verification token rather than relying on an app-wide secret alone, and document/enforce in `WebhookMetadata` that consumers must not trust `shop` as the sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook to the app: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, and valid `x-shopify-hmac-sha256` computed as `HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures this request and resends it to the app's webhook endpoint, replacing only the `x-shopify-shop-domain` header with `victim-shop.myshopify.com`, keeping body `B` and the HMAC unchanged.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes `HMAC-SHA256(api_secret_key, B)` — this still matches since `B` is unchanged: [5](#0-4)  — validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: B, ...)` and calls the app's handler, which now performs tenant-scoped work attributing attacker-controlled data `B` to `victim-shop.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
