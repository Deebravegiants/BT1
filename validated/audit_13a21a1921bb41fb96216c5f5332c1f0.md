### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](), [File: lib/shopify_api/webhooks/registry.rb]())

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches to the app's handler using `request.shop`, a value read from an HTTP header that is never included in the signed content.

### Finding Description
`Utils::HmacValidator.validate` is invoked on the `Webhooks::Request` object in `registry.rb`: [1](#0-0) 

The HMAC check delegates to `to_signable_string`, which for a webhook request returns only the raw HTTP body — never the shop domain: [2](#0-1) 

Meanwhile, `shop` is parsed directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cross-check against the signed payload: [3](#0-2) 

After the HMAC check passes, `registry.rb` builds the metadata passed to the app-provided handler directly from `request.shop`: [4](#0-3) 

This breaks the intended identity binding: `hmac_valid(body) == true` is treated as equivalent to `shop == genuine_source_shop`, but the equality that is actually verified is only `hmac_valid(body) == true`; `shop` is an independent, unauthenticated field. Any two webhook deliveries carrying the exact same raw JSON body (which is not unusual — Shopify webhook payloads for a given topic/schema often overlap or can be replayed byte-for-byte by the attacker's own store) will produce an identical valid HMAC regardless of which shop domain header is attached, because the app's own `api_secret_key` is a single per-app secret shared across every one of the app's install shops. This is the same root-cause class as the report: a check on one identity (`msg.sender` valid vs. the specific `questID` in the report; here, "HMAC is valid" vs. the specific `shop` it is claimed to belong to) is used as a stand-in for a binding that is never actually enforced.

### Impact Explanation
An attacker who controls a shop that has installed the app (a normal, unprivileged capability for any developer/merchant) can trigger a webhook from their own store, capture the `(raw_body, hmac)` pair — both computed with the app's single shared `api_secret_key` — and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. Because `Registry.process` never re-derives or checks `shop` against anything cryptographic, the forged request passes validation and is dispatched to the handler as if it originated from the victim tenant. If the host application acts on `request.shop` to select which tenant's stored session/access token/data to read or mutate (the intended and documented usage — `WebhookMetadata#shop` is the field apps are expected to use to identify which merchant the event pertains to), this yields cross-tenant access: an attacker-controlled webhook can trigger effects (data writes, resyncs, deletions, notifications) scoped to a different merchant's account without ever compromising that merchant.

### Likelihood Explanation
Medium-to-low but non-trivial: it requires the attacker to already have an app installation of their own (a normal capability, not a privileged one) and to find or construct a body that matches a webhook topic where the payload is fixed, guessable, or attacker-influenced from their own shop (e.g. `app/uninstalled`, `shop/update` with predictable/static fields, or any topic where the attacker fully controls resource content in their own store). It does not require the victim's access token, `client_secret`, or any credential leak — only knowledge of the app's public webhook endpoint and standard webhook mechanics.

### Recommendation
Bind `shop` cryptographically to the payload before trusting it, or, more robustly, cross-validate `request.shop` against a shop already known to the app (e.g. require that a session/install record exists for the exact `shop` value before processing) instead of relying purely on the HMAC-over-body check to imply the header's authenticity. At minimum, document prominently that `request.shop` is unauthenticated and must never be used as the sole tenant selector without an independent server-side lookup tying it to an existing installation record established via a fully-verified OAuth flow.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com`.
2. Attacker triggers a webhook whose body content is static/predictable for a given topic (or crafts store data to produce a chosen JSON body), capturing the resulting `raw_body` and `x-shopify-hmac-sha256` value delivered by Shopify (computed with the app's single `api_secret_key`).
3. Attacker POSTs that same `raw_body` + `hmac` to the app's webhook endpoint, but sets the `x-shopify-shop-domain` header to `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `"victim.myshopify.com"` [3](#0-2) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body-derived signature and returns `true` [5](#0-4) .
5. The handler receives `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim.myshopify.com"` [6](#0-5)  and performs whatever tenant-scoped action the app implements for that shop, even though the request never originated from Shopify on behalf of that shop.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
