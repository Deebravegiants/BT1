Webhook `shop` (tenant identity) header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , while `Registry.process` trusts the `shop` (and `topic`, `webhook_id`, `api_version`) values read straight from unauthenticated HTTP headers and hands them to the host app's handler as the tenant identity [2](#0-1) . The HMAC check in `Registry.process` (`Utils::HmacValidator.validate(request)`) only proves the body was signed with the app's shared `api_secret_key`; it does not bind that signature to the shop the request claims to be from.

### Finding Description
`Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the `hmac` field supplied by the caller [3](#0-2) . For webhooks, `to_signable_string` is defined as just `@raw_body` [1](#0-0) , and `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers with no cryptographic binding to the body or the HMAC at all [4](#0-3) .

Because a single Shopify app uses **one shared `api_secret_key` for every merchant shop** that installs it, this means:
- The identity binding the report describes ("the shop authenticated versus the shop stored/acted upon") is broken: the HMAC authenticates *the app*, not *the specific shop*.
- Any actor who can obtain one valid `(raw_body, hmac)` pair signed by the app's shared secret — e.g. by triggering a real webhook event on a shop they themselves control/install the app on — can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header naming a victim shop.
- `Registry.process` will pass HMAC validation (it only checks the body) and will call the host handler with `WebhookMetadata.new(..., shop: request.shop, body: request.parsed_body, ...)` [5](#0-4) , presenting attacker-controlled/legitimately-signed-but-mismatched data as if it originated from the victim shop.
- The gem's own documentation instructs handlers to key business logic directly off `data.shop` (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [6](#0-5) , so this is the intended, documented usage pattern of the gem's own API — not a case of the host app deviating from the documented interface.

This is the direct analog to the HAL-style bug class: a field (`shop`) that gates tenant-scoped downstream action is not covered by the same authenticity check (`hmac`) that gates the rest of the request, so the "shop verified" side of the equality (`hmac(secret) valid` ⇒ `request is genuinely from request.shop`) does not actually hold.

### Impact Explanation
This meets the "Cross-tenant access" criterion for Critical impact: an attacker who is a legitimate (even free-trial) installer of the app on their own shop can, using only their own store's webhook traffic, forge webhook deliveries that the app attributes to a different, victim merchant shop. Any host application that follows the gem's documented pattern of trusting `data.shop` (e.g. to select which merchant record/session/queue to enqueue work against) can be made to process attacker-supplied webhook bodies under a victim shop's identity, without any of the victim's credentials.

### Likelihood Explanation
Likelihood is high for any app that has more than one installed shop (the normal case for a multi-tenant Shopify app): the attacker needs no special privileges beyond installing the target app on a shop they control (or capturing one of their own past webhook deliveries) and the ability to POST to the app's public webhook callback URL, which is an unauthenticated, internet-reachable endpoint by design.

### Recommendation
Bind the claimed tenant identity into the signature verification, not just the body:
- Include the `shop` (and ideally `topic`/`webhook_id`) header value as part of `to_signable_string` in `ShopifyAPI::Webhooks::Request`, or
- After HMAC validation, cross-check `request.shop` against the shop associated with the session/store that the app expects to be receiving this specific webhook (e.g., validate that a webhook subscription for that exact shop+topic was registered), rejecting the request if it doesn't match.
- At minimum, update `docs/usage/webhooks.md` to warn that `data.shop` is not covered by the HMAC and must be independently verified against known installed shops before being trusted for tenant-scoped side effects.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a shop they control) and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the raw POST: headers (`X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`, ...) and raw body `B`.
2. Attacker resends an identical POST to the same app's webhook endpoint but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`, keeping body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `to_signable_string` returns `B` unchanged [1](#0-0) .
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)`, which still equals `H` (secret is shared across all shops), so validation **passes** [7](#0-6) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [5](#0-4) , causing the host app to act on attacker-controlled webhook content as if it were genuinely delivered for the victim shop.
