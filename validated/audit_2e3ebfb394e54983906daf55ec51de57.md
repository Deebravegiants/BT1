### Title
Cross-function relayer-signature replay via shared `Nonce` map and identical message preimages between `accumulate`'s beneficiary redirect and `withdraw`'s beneficiary withdrawal - (File: modules/pallets/relayer/src/accumulate.rs, modules/pallets/relayer/src/withdrawal.rs)

### Summary
`pallet-ismp-relayer` derives the signed payload for two functionally different operations — accumulating fees to a redirected beneficiary and withdrawing fees to a beneficiary — from an identical preimage structure `(nonce: u64, StateMachine, beneficiary: Vec<u8>/&[u8])`, hashed with the same `keccak_256`, and validated against the same shared `Nonce<T>` storage double-map keyed by `(address, state_machine)`.

### Finding Description
`beneficiary_message` in `accumulate.rs` computes `keccak_256(&(nonce, state_machine, beneficiary).encode())` [3](#0-2) , while `message` in `withdrawal.rs` computes `keccak_256(&(nonce, dest_chain, beneficiary).encode())` when a beneficiary is supplied [4](#0-3) . Both functions read/increment the exact same `Nonce<T>` double map (`address` × `StateMachine`) [5](#0-4) , used identically in `accumulate()` [6](#0-5)  and `withdraw()` [7](#0-6) . Because SCALE-encoding a `Vec<u8>` and a `&[u8]` produce byte-identical output, and the tuple shapes `(u64, StateMachine, bytes)` are structurally identical, a signature a relayer produces for one purpose is byte-for-byte valid for the other purpose at the same nonce. Both `accumulate_fees` and `withdraw_fees` are unsigned (`ensure_none`) extrinsics validated purely through `validate_unsigned`/signature recovery [1](#0-0) , so anyone observing a relayer's broadcast signed payload in the mempool (or in a previously-included, now-failed-due-to-race transaction) can resubmit it into the *other* dispatchable before the relayer's intended transaction lands, since there is no domain separator (e.g., a function-specific tag/prefix) distinguishing "this signature authorizes an `accumulate` beneficiary redirect" from "this signature authorizes a `withdraw`". The only replay defense is the shared monotonic nonce, which does not distinguish intended call-site.

### Impact Explanation
An attacker who observes a relayer-signed `(nonce, chain, beneficiary)` payload intended for `withdraw_fees` can front-run it into `accumulate_fees` (supplying any valid, publicly reconstructible `WithdrawalProof` for that relayer's already-delivered, unclaimed commitments) before the honest transaction is mined. This consumes the nonce, redirects the newly accumulated fee batch to the beneficiary embedded in the captured signature under `accumulate`'s semantics rather than `withdraw`'s, and causes the relayer's own subsequent, intended transaction to fail with a nonce mismatch. The reverse (capturing an `accumulate` beneficiary-redirect signature and replaying it into `withdraw_fees`) similarly lets an attacker force-trigger a fee withdrawal at an unintended point, misdirecting whichever `Fees[state_machine][address]` balance currently exists to the beneficiary and zeroing it, ahead of the relayer's planned redirect. This is an improper-access-control class issue: authorization intended to scope a signature to a specific action (mirroring the phpMyFAQ report's lack of validation binding an update to its intended, safe scope) is not enforced, letting a third party trigger the "wrong" state-mutating function with a signature meant for a different one, causing fund misdirection/DoS on relayer fee accounting.

### Likelihood Explanation
Exploitation requires no privileged access — only mempool observation of an unsigned extrinsic (both calls are `ensure_none`) and knowledge of a relayer's delivered-but-unclaimed commitments, which is public chain state. The attacker needs no relayer private key; they only race a captured, already-signed payload into the other function. This is realistically triggerable by any relayer, token bridger, or other unprivileged actor monitoring the network.

### Recommendation
Add a domain separator/tag distinguishing the `accumulate` beneficiary-redirect message from the `withdraw` beneficiary message (e.g., prefix bytes like `b"ACCUMULATE_BENEFICIARY"` vs `b"WITHDRAW_BENEFICIARY"` in the hashed preimage), and/or use disjoint nonce namespaces (e.g., separate `Nonce` storage maps per purpose) so a signature valid for one call can never satisfy the other's verification.

### Proof of Concept
1. Relayer R (delivery address `A`) signs `msg = keccak256((nonce=N, chain=C, beneficiary=B).encode())` intending to call `withdraw_fees` with `WithdrawalInputData { signature, dest_chain: C, beneficiary: Some(B) }`, and broadcasts it as an unsigned extrinsic.
2. Attacker observes this extrinsic in the mempool, extracts `(signature, B)`, and separately assembles a `WithdrawalProof` proving R's already-delivered, unclaimed request commitments on chain `C` (public state) with `beneficiary_details: Some((B, signature))`.
3. Attacker submits `accumulate_fees(withdrawal_proof)` first. `Nonce::<T>::get(A, C)` still equals `N`, so `beneficiary_message(N, C, B)` matches the captured signature's preimage, `signature.verify` succeeds, and `Fees[C][B] += total_fee` is credited while `Nonce[A][C]` is incremented to `N+1`. [8](#0-7) 
4. R's originally intended `withdraw_fees` transaction, still carrying `nonce=N`, is now rejected on-chain because `Nonce::<T>::get(A, C)` no longer equals `N`, causing the relayer's real withdrawal intent to fail while the attacker's front-run has already redirected the fee accumulation.
