## Title
Duplicate authority-index votes bypass BEEFY supermajority threshold via unmerged signature count - (File: modules/consensus/beefy/verifier/src/lib.rs / evm/src/consensus/EcdsaBeefy.sol)

### Summary
This is not the reported JS-YAML bug class reproduced literally — I found extensive, deliberate mitigations already in place across every reachable batch-processing path (`dedup_requests` in request/response/timeout handlers, `seen_keys` BTreeSet in `verify_state_proof` for EVM state machines, commitment dedup in `pallet-relayer::accumulate`, and duplicate-participant checks in the Pharos BLS verifier's `verify_validator_membership`). These all follow the exact "reject repeats before doing disproportionate work" pattern that the JS-YAML advisory recommends, so the CWE-407 quadratic-merge-alias analog appears already closed everywhere I could check with available context.

However, while tracing this bug class (repeated/duplicate references not deduplicated before being counted or processed) through consensus verification, I found that the BEEFY ECDSA consensus client's supermajority check counts raw signature/vote array length rather than deduplicated authority participation.

### Finding Description
In `verify_mmr_update_proof` (`modules/consensus/beefy/verifier/src/lib.rs:105-187`), the participation threshold is checked against the raw length of the submitted signatures array: [1](#0-0) 

`signatures_length` is `mmr.signed_commitment.signatures.len()` — the count of entries in the relayer-supplied `Vec`, not the count of distinct authorities. The subsequent loop pushes `sig.index` into `authority_indices` and the recovered address hash into `authority_leaves` for every entry without checking for repeats: [2](#0-1) 

The identical shape exists in the Solidity ECDSA BEEFY client used on EVM destination chains: [3](#0-2) 

`sigLen` is `relayProof.signedCommitment.votes.length` (raw array length) and is what `checkParticipationThreshold` is evaluated against, before any authority-index deduplication.

This is structurally the same root cause pattern as the JS-YAML report: a relayer-controlled batch (`votes`/`signatures`) can contain the same reference (one authority's valid signature + its claimed `authorityIndex`) repeated many times, and the code that gates acceptance (`checkParticipationThreshold`/`check_participation_threshold`) treats each repeat as independent weight rather than collapsing duplicates before counting — the same "idempotent operation charged multiple times" defect class described in the advisory, but here the disproportionate effect is on a security threshold rather than CPU time.

### Impact Explanation
Whether this is exploitable to forge consensus acceptance depends entirely on whether the downstream merkle multi-proof verifier (`MerkleProof::verify` from `rs_merkle` in Rust, `MerkleMultiProof.VerifyProof` in Solidity) itself rejects an `indices`/leaves list containing the same index more than once. I was unable to inspect the internals of `rs_merkle::MerkleProof::verify` or `@polytope-labs/solidity-merkle-trees`'s `MerkleMultiProof.VerifyProof` (external dependencies, not indexed in this repo), so I cannot confirm whether duplicate `(index, hash)` leaf pairs are accepted, rejected, or cause a panic/revert in either implementation. If either library silently accepts duplicate leaf indices during multi-proof reconstruction (a documented pitfall of naive Merkle multi-proof implementations, distinct from OpenZeppelin's own historical multi-proof duplicate-leaf issue), an attacker could replay one validator's single valid signature many times to satisfy `checkParticipationThreshold`'s 2/3+1 raw-count check without true supermajority participation — i.e., forge acceptance of a fraudulent BEEFY consensus update, which is the highest-severity Hyperbridge outcome (unsound state commitment / forged message delivery).

### Likelihood Explanation
I could not verify the actual behavior of the external merkle-multiproof verification libraries against duplicate leaf indices, so I cannot assert this is currently exploitable — it may already be safe if those libraries revert or fail proof reconstruction on duplicate indices (which is plausible, since a duplicated k-index would produce an odd/mismatched pairing during multi-proof root recomputation and likely fail the root check in the common case). Given this uncertainty, I am not confident enough in end-to-end exploitability to assert this as a proven, standalone finding equivalent to the reported advisory.

### Recommendation
As defense-in-depth regardless of the external library's behavior, add an explicit duplicate check on `authority_indices` (Rust) / `authorityIndex` per vote (Solidity) before computing/checking the participation threshold and before calling into the merkle multi-proof verifier — mirroring the pattern already used in `modules/consensus/pharos/verifier/src/lib.rs::verify_validator_membership`, which deduplicates `participant_keys` via a `BTreeSet` and returns `Error::DuplicateParticipant` on any repeat. This closes the gap even if the underlying merkle library happens to tolerate duplicate leaf positions.

### Proof of Concept
Not established — verifying whether this is exploitable requires exercising `rs_merkle::MerkleProof::verify` (or `MerkleMultiProof.VerifyProof` in Solidity) with a leaves/indices array containing a repeated `(authorityIndex, hash)` pair against a real authority-set Merkle root, which requires access to those external library sources not present in this indexed codebase. I could not construct or confirm a concrete PoC within the available context.
