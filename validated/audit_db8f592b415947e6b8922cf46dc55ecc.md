### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant shop spoofing on webhook delivery - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop` value taken from the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header — a field that is never included in the HMAC-signed content. This breaks the intended binding `hmac_verified_body == shop_the_app_acts_on`, letting anyone who can produce (or replay) one validly-signed webhook body attribute that payload to an arbitrary victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes the signature over exactly that signable string and compares it against the `hmac-sha256` header: [2](#0-1) 

`Registry.process` uses this same body-only HMAC check to decide whether the request is trustworthy, and then immediately trusts `request.shop`, which is parsed from a separate, unauthenticated header: [3](#0-2) [4](#0-3) 

The equality the code implicitly assumes is:
`shop bound by HMAC == shop the handler is told the data came from`

In reality: `hmac covers raw_body only` != `shop is read from an unsigned header`. Any actor who can obtain one legitimately-signed webhook body (e.g. a webhook for their own shop, since the app's webhook signing key is shared across every shop that installs the app) can resend that same body/HMAC pair to the app's public webhook endpoint with the `shop-domain` header rewritten to name a different, victim shop. `Request#hmac` and `Request#shop` are derived independently from unrelated header/body sources, so `Utils::HmacValidator.validate` still returns `true`, and `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is dispatched to the handler carrying the attacker-chosen `shop` value.

This directly matches the class of bug identified in the analog report: a downstream identity check (`disable`/module-removal ordering in the Solidity report) trusts state that is no longer authoritative by the time it's consulted. Here, the "shop" identity that handlers use to select per-tenant state/storage is consulted from data that was never covered by the authentication mechanism (the HMAC) meant to establish trust in the request.

### Impact Explanation
This is a cross-tenant data confusion vector at the application/gem boundary: the gem hands the host application attacker-controlled body content labeled with a victim's `shop` value while claiming it passed HMAC verification. Any app that uses `WebhookMetadata#shop` (as the docs/tests show is expected — `data.shop` is a first-class field returned to handlers) to select which merchant's records to create/update/delete will act on the victim tenant using attacker-supplied body content, without needing the app's `client_secret`, an access token, or any privileged credential. This satisfies the "cross-tenant access" criterion for Critical impact, since the webhook-processing API is the exact trust boundary meant to isolate shops from one another and it is defeated purely with a replay the attacker can generate from their own legitimately-installed shop.

### Likelihood Explanation
Medium-to-High: exploitation requires only (a) installing the app on any shop the attacker controls (a normal, unprivileged action available to any merchant/developer), (b) capturing one webhook delivery for that shop (trivial, since it's delivered to an endpoint the attacker's app configuration controls), and (c) replaying the same raw body/HMAC pair to the app's public webhook endpoint with a modified shop-domain header. No secret material, TLS interception, or social engineering is needed — this is exactly the "unprivileged internet user" scenario the rules describe.

### Recommendation
Bind the shop identity into the authenticated material before trusting it: include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the HMAC-signed content that `Request#to_signable_string` returns (mirroring the way `Auth::Oauth::AuthQuery#to_signable_string` already binds `shop` into its signable string), or independently verify that `request.shop` matches a shop record already provisioned/authenticated for the app (e.g., a session lookup) before dispatching to `handler.handle`. At minimum, document that `WebhookMetadata#shop` is not authenticated and must not be trusted for tenant selection.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a genuine webhook delivery, e.g. body `{"id":1,"note":"hello"}`, with header `x-shopify-hmac-sha256: <valid-hmac-of-that-body>` and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the identical raw body and identical `x-shopify-hmac-sha256` value to the same app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unchanged) body against the (unchanged) HMAC — validation succeeds: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled body content, even though `victim.myshopify.com` never sent this webhook and the attacker holds no credentials for it.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
