### Title
Excess attached deposit is permanently locked in `AddressRegistrar::register` due to `<` check instead of exact/refund logic - (File: `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs`)

### Summary
The `AddressRegistrar` contract's `register` method is `#[payable]` and only validates that the attached deposit is *at least* the storage cost required to store the new address-to-account mapping. When registration succeeds (the `Entry::Vacant` branch), any amount attached above the exact storage cost is never refunded and is permanently retained by the contract, matching the reported bug class where functions check `msg.value >= required` instead of an exact match or performing a refund of the excess.

### Finding Description
`register` computes `required_deposit` from the number of bytes to store and only panics if `given_deposit < required_deposit`: [1](#0-0) 

If the deposit check passes and the address is new (`Entry::Vacant`), the mapping is stored but there is no logic to compute or refund `given_deposit - required_deposit`: [2](#0-1) 

Notably, the contract already implements the correct refund pattern for the collision case (`Entry::Occupied`), where the *entire* deposit is refunded via a transfer promise because no storage was consumed: [3](#0-2) 

This inconsistency shows the refund mechanism exists in the codebase but was omitted for the successful-registration path, which is the primary and most common code path. Any caller (including the `WalletContract`, which invokes this registrar as part of its Ethereum-transaction emulation flow) that attaches more than the exact `required_deposit` — for example, rounding up gas/deposit estimates, or reusing a fixed constant deposit for calls regardless of the account_id length — will have the excess yoctoNEAR permanently locked in the `AddressRegistrar` account, with no way to reclaim it.

### Impact Explanation
Funds locked in `AddressRegistrar` are unrecoverable by the caller since there's no withdrawal or refund mechanism for the excess. This is a benign-but-real balance loss for any unprivileged account interacting with this contract with an over-provisioned deposit, analogous to the reported "amount sent above fee gets locked" bug class. Severity is limited to whatever excess yoctoNEAR/NEAR a caller over-attaches per call; it does not enable token inflation, unauthorized state changes, or a broader chain-level fault, but constitutes user fund loss caused directly by the contract's flawed validation logic.

### Likelihood Explanation
Any transaction or cross-contract call that attaches a deposit larger than the exact computed storage cost (e.g., due to rounding, safety margins, or reuse of a fixed constant like `NEP_141_STORAGE_DEPOSIT_AMOUNT`-style padding elsewhere in the wallet-contract implementation) will trigger this on the very first (successful) call, i.e., the common/expected case, not just an edge case. No privileged access or special conditions are needed — a normal `FunctionCall` action with `register(account_id)` and `attached_deposit > required_deposit` reliably reproduces this.

### Recommendation
In the `Entry::Vacant` branch of `register`, compute `given_deposit.saturating_sub(required_deposit)` and, if non-zero, issue a `promise_batch_action_transfer` refund to `env::predecessor_account_id()`, mirroring the refund pattern already used in the `Entry::Occupied` branch.

### Proof of Concept
1. Deploy/use the `AddressRegistrar` contract.
2. Call `register(account_id)` with `attached_deposit = required_deposit + X` (X > 0), where `required_deposit = storage_byte_cost * (20 + account_id.len())`.
3. Observe: the call succeeds (`Entry::Vacant` path), the mapping is stored, but no refund receipt is created — `X` yoctoNEAR remains locked in the `AddressRegistrar` contract's balance indefinitely, confirmed by inspecting `runtime/near-wallet-contract/implementation/address-registrar/src/lib.rs:65-72` where no `promise_batch_action_transfer` call exists, unlike the collision branch at lines 80-82.
