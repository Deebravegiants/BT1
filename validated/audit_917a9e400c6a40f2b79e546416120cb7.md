### Title
Webhook HMAC Only Signs the Raw Body, Not the `shop-domain` Header — Shop Identity Is Not Bound to the Signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` cryptographically verifies nothing but the JSON body bytes. The `shop` (from the `shopify-shop-domain`/`x-shopify-shop-domain` header), `topic`, `webhook-id`, and `api-version` are all read straight from unauthenticated HTTP headers and passed on to the app's handler as trusted tenant identity, exactly mirroring the reported bug class: a value used to make a security-relevant decision (which tenant/shop this event belongs to) is not covered by the binding mechanism (the HMAC) that is supposed to prove authenticity.

### Finding Description
`Registry.process` validates a webhook purely via: [1](#0-0) [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`, which HMACs `request.to_signable_string` — the raw body only: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are parsed unauthenticated from headers: [3](#0-2) 

and are handed directly to the app's handler as the tenant identity in `WebhookMetadata`: [4](#0-3) 

The identity binding that should hold is: `HMAC(secret, bytes_verified) == HMAC(secret, bytes_that_determine_shop)`. Here `bytes_verified = raw_body` while `bytes_that_determine_shop = shop-domain header`, which are disjoint. `secret` (the app's `api_secret_key`) is identical across every shop that installed the app, so any webhook the attacker can legitimately trigger for their own installed test/dev shop yields a `(raw_body, hmac)` pair that is valid for that same `secret` regardless of which shop header is attached.

### Impact Explanation
This breaks the shop-authenticated-versus-shop-stored identity binding called out in the rules: the gem verifies bytes (the body) that are disjoint from the bytes actually used to select the tenant (the `shop-domain` header). An attacker who controls an install of the victim's app on their own shop can generate a legitimate `(body, hmac)` pair (e.g., by placing an order, updating a product, etc., in their own store) and then replay that exact HTTP POST to the app's webhook endpoint while substituting the victim shop's domain in the `shopify-shop-domain` header. `HmacValidator.validate` still passes because it only checks the body against the shared `api_secret_key`. The app then executes shop-scoped business logic (e.g., "look up the victim's session/access token by `shop`, and update that shop's local records with attacker-supplied `body` content") believing the event genuinely originated from the victim shop. This is a cross-tenant access/data-injection vector satisfying the Critical impact bar in the rules ("cross-tenant access").

### Likelihood Explanation
Any developer of any app using this gem is exposed by default: they build a `ShopifyAPI::Webhooks::Request` straight from the incoming headers and body exactly as documented, and call `Registry.process`, per the gem's own docs: [5](#0-4) 
No extra opt-in or misuse of the API is required — the exposure is inherent to how `to_signable_string` is implemented in this gem, not to any documented safeguard being skipped by the host app.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed/verified material, or otherwise cryptographically bind them — e.g., compute the HMAC over a canonical string built from `shop-domain + raw_body` rather than `raw_body` alone, or require the app to additionally verify the shop's known registered domain against session/store records before trusting `WebhookMetadata#shop`. At minimum, document prominently that `request.shop` is unauthenticated and must not be used as a sole tenant key.

### Proof of Concept
1. Attacker installs the target app on their own dev shop `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook event (e.g. `orders/create`) on their own shop; Shopify sends:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of RAW_BODY under shared api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: RAW_BODY
   ```
3. Attacker replays this exact request to the app's webhook endpoint, changing only:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Request#to_signable_string` returns the unchanged `RAW_BODY`; `Utils::HmacValidator.validate` recomputes the same HMAC and it matches (per `lib/shopify_api/utils/hmac_validator.rb` lines 26-31, `lib/shopify_api/webhooks/request.rb` lines 35-38).
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: RAW_BODY, ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), causing the app to process attacker-controlled data under the victim's tenant context.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
