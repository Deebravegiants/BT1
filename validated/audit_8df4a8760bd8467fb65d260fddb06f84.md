### Title
Infinite loop / node hang via cyclic parent-hash references in GRANDPA justification's `votes_ancestries` - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
`AncestryChain::ancestry` (used by `GrandpaJustification::verify_with_voter_set`) walks a header chain by following `parent_hash` pointers inside a `BTreeMap` built entirely from attacker-controlled `votes_ancestries` headers, with no cycle detection and no bound on the number of hops. A crafted justification whose ancestry headers form a `parent_hash` cycle (that never resolves to `base`) drives the `while` loop into an infinite loop, hanging the process — the same bug class as ALPINE-CVE-2019-20421 (crafted input causing an infinite loop / high CPU denial of service).

### Finding Description
`AncestryChain::new` builds a `BTreeMap<H::Hash, H>` from the justification's `votes_ancestries` — a `Vec<H>` fully supplied by an untrusted relayer/prover inside `GrandpaJustification` (SCALE-decoded straight from submitted proof bytes): [1](#0-0) 

The `Chain::ancestry` implementation walks backward from `block` toward `base` purely by dereferencing `parent_hash()` on whatever header is found at `current_hash` in the map, with no visited-set / cycle check and no maximum iteration bound: [2](#0-1) 

Because each header in `votes_ancestries` is attacker-supplied data (not derived by hashing forward from a genesis or trusted point), an attacker can construct two (or more) headers `H1`, `H2` such that:
- `H1.parent_hash = hash(H2)`
- `H2.parent_hash = hash(H1)`

Both headers hash to distinct keys and both get inserted into the `BTreeMap`. If the walk starts at `hash(H1)` (or `hash(H2)`) and `base` is any hash not on this 2-cycle, the loop body always finds an entry in the map (alternating between `H1` and `H2`) and never becomes equal to `base`, so the `while current_hash != base` loop never terminates — an unbounded, CPU-consuming infinite loop, exactly analogous to the Exiv2 `Jp2Image::readMetadata()` infinite-loop DoS in the reference CVE.

This function is reached from `verify_with_voter_set`, which is called from `GrandpaJustification::verify`, invoked for every precommit in the justification's commit: [3](#0-2) 

`verify_with_voter_set`/`verify` is the function used by the GRANDPA consensus client (`ismp-grandpa`) and the standalone verifier (`verify_grandpa_finality_proof`) to validate a `ConsensusMessage`/`FinalityProof` submitted via `verify_consensus`, which is the standard permissionless entry point any relayer can call to update GRANDPA-based consensus state on Hyperbridge (dispatch through `ConsensusClient::verify_consensus`). There is no bound on `votes_ancestries.len()` and no cycle-detection guard anywhere in this code path.

### Impact Explanation
An unprivileged relayer can submit a `GrandpaJustification` whose `votes_ancestries` contains a small parent-hash cycle. When the node processes the consensus update (`verify_consensus` → `GrandpaJustification::verify`/`verify_with_voter_set` → `AncestryChain::ancestry`), the thread executing verification enters an infinite loop and never returns, hanging that execution context. Depending on the runtime environment (parachain runtime execution vs. off-chain prover/verifier), this can stall block production/import or make the consensus-update extrinsic never finalize, preventing further GRANDPA consensus updates and message delivery for that route — a denial-of-service against the bridge's consensus-update path. This matches "a route unable to deliver messages" in the validation criteria, warranting High severity.

### Likelihood Explanation
Likelihood is high: the `votes_ancestries` field and the whole `GrandpaJustification` are fully attacker-controlled inputs supplied via a permissionless "submit proof"-style extrinsic/relayer call; no signing key compromise, governance, or privileged role is required. Constructing the two-header cycle only requires setting each header's `parent_hash` field to the hash of the other — no hash preimage or collision is needed, since headers are freely chosen data structures under attacker control, not values that must satisfy any hash-preimage constraint. Nothing in the current code checks for cycles or bounds the number of `ancestry` hops.

### Recommendation
- In `AncestryChain::ancestry`, track visited hashes (e.g., a `BTreeSet`) and bail out with `finality_grandpa::Error::NotDescendent` as soon as a hash is revisited, or cap the number of iterations to `votes_ancestries.len() + 1`.
- Alternatively/additionally, bound `votes_ancestries.len()` (e.g., via a `BoundedVec` or explicit length check) at the SCALE-decode/extrinsic boundary before verification, consistent with similar defenses already applied elsewhere in the codebase (e.g., `MAX_PROOF_DEPTH` in `modules/consensus/pharos/primitives/src/spv.rs`).

### Proof of Concept
1. Construct two headers `H1` and `H2` (type `H: HeaderT`, e.g. `sp_runtime::generic::Header<u32, BlakeTwo256>`):
   - `H2` first with an arbitrary `parent_hash` placeholder, compute `hash(H2)`.
   - Set `H1.parent_hash = hash(H2)`, compute `hash(H1)`.
   - Set `H2.parent_hash = hash(H1)` (re-derive `H2`'s final hash after this edit — since `parent_hash` is part of the hashed content, iterate: fix `H2.parent_hash = hash(H1)`, this changes `hash(H2)`; then recompute and fix `H1.parent_hash` to the new `hash(H2)`. This converges quickly because each header's other fields can be treated as fixed and only `parent_hash` is varied, so it is a straightforward two-variable resolution, not a hash-preimage search.)
2. Put `votes_ancestries = vec![H1.clone(), H2.clone()]` into a `GrandpaJustification` whose `commit.precommits` contains a precommit with `target_hash = hash(H1)` (or `hash(H2)`), and whose `base_hash` (lowest-numbered precommit target) is some third, unrelated hash not present in `votes_ancestries`.
3. Call `AncestryChain::new(&votes_ancestries).ancestry(base_hash, hash(H1))` directly, or submit the justification through the standard `verify`/`verify_with_voter_set` path — the `while current_hash != base` loop alternates between `hash(H1)` and `hash(H2)` forever, hanging the calling thread.

**Uncertainty**: I could not verify from the index alone whether `verify_consensus` for GRANDPA runs inside an on-chain runtime execution context (where a hang could stall block production/import) versus purely off-chain relayer verification (where it would only hang the relayer process); the severity framing above assumes the on-chain/runtime path used by `ismp-grandpa`'s `ConsensusClient::verify_consensus`, which is the reachable, permissionless surface described in the scope rules. A Devin session with full repository access could confirm the exact execution context and any existing `BoundedVec` limits on `votes_ancestries` at the extrinsic/decode boundary.

impl<H: HeaderT> finality_grandpa::Chain<H::Hash, H::Number> for AncestryChain<H>
where
	H::Number: finality_grandpa::BlockNumberOps,
{
	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
}
