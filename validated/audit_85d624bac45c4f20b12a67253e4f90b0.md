### Title
Webhook shop-domain and topic headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values used to dispatch the webhook to a handler are taken from unauthenticated HTTP headers that are never included in the signed content.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` is read from the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

`#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled directly from headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are not part of `to_signable_string`: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e., it verifies the body but never the headers: [4](#0-3) 

`Registry.process` then trusts `request.topic` to select a handler and forwards the unauthenticated `request.shop` value straight into `WebhookMetadata` given to the app's handler: [5](#0-4) 

**Equality that should hold but doesn't:** `shop_bound_by_hmac == shop_used_for_dispatch`. In this code, `shop_bound_by_hmac = ∅` (the HMAC covers only the JSON body) while `shop_used_for_dispatch = request.shop` (an arbitrary, attacker-suppliable header). The same gap applies to `topic`.

**Attack sequence:** An unprivileged attacker can install the target app for free on their own throwaway/development shop (a normal, unauthenticated Shopify onboarding action requiring no secrets) and receive one legitimately-signed webhook delivery — capturing `raw_body` and its valid `hmac-sha256` value for a topic the app has a handler for. The attacker then replays that exact `raw_body`/`hmac` pair to the app's public webhook endpoint, but substitutes the `shopify-shop-domain` header with the victim shop's domain (and/or the `shopify-topic` header to target a different handler). `HmacValidator.validate` still returns `true` because the body/HMAC pair is unchanged and valid. `Registry.process` dispatches the forged request, and the app's handler executes attacker-controlled webhook JSON tagged as belonging to the victim shop.

### Impact Explanation
This breaks the tenant-identity binding that webhook consumers rely on: apps commonly use `WebhookMetadata#shop` to look up/act on per-tenant records (e.g., updating billing state, marking a shop as uninstalled, processing customer data-erasure requests, writing order data) without additional verification, since the gem's own webhook dispatch layer is expected to have authenticated the sender. Because the shop and topic are unauthenticated here, an attacker can inject data/actions attributed to a shop they do not control, achieving cross-tenant data corruption or logic confusion. This maps to the report's "protected/administrative identity binding" bug class where a field acted upon (the shop identity used for dispatch) is not covered by the trust mechanism (HMAC) that is supposed to authenticate the message. Impact is Critical under the given rubric (cross-tenant access via a credential/identity-binding gap in the gem's own dispatch code), not merely a host-application misuse issue, because the vulnerable binding is inside `Webhooks::Request`/`Registry` themselves.

### Likelihood Explanation
Likelihood is moderate-to-high: obtaining one valid `raw_body`/`hmac` sample requires nothing more than installing the target app on any Shopify development store — an action any unprivileged internet user can perform without credentials belonging to the target merchant, `api_secret_key`, or any privileged account. The replay itself is a simple HTTP request with modified headers to the app's public webhook URL.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed content that `HmacValidator` verifies, or independently authenticate `request.shop` against Shopify (e.g., cross-check against the `X-Shopify-Shop-Domain` claim using a source that is cryptographically tied to the HMAC, or require verification that the webhook was actually registered/expected for that specific shop before dispatch). At minimum, document that consumers of `WebhookMetadata#shop` must not trust it without additional shop-specific verification, but the safer fix is to include shop/topic in the HMAC-covered signable string within `Webhooks::Request`.

### Proof of Concept
1. Attacker creates a free Shopify development store and installs the target app, causing the app to register a webhook (e.g., `orders/paid`).
2. Attacker triggers that webhook event on their own store and captures the raw POST body and the `X-Shopify-Hmac-Sha256` header from the delivery (e.g., via a webhook logging proxy they control).
3. Attacker resends the exact same body and `hmac-sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because the body/HMAC pair is untouched: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` resolves to `"victim-shop.myshopify.com"`, taken straight from the attacker-controlled header: [7](#0-6) 
6. The app processes attacker-supplied webhook data as if it originated from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
