### Title
Webhook `shop` identity is trusted downstream but is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a successful `HmacValidator.validate(request)` as proof that the entire webhook request — including the tenant identity (`shop`) — is authentic. In reality the HMAC only signs the raw body; the `shop-domain` header used to build `WebhookMetadata` and dispatched to the app's handler is never part of the signed material, so it can be freely substituted while keeping a valid signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from an independent, unauthenticated header: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against a signature computed over `to_signable_string` (the body), never over `shop`: [3](#0-2) 

`Registry.process` gates on this single boolean and then forwards the *unauthenticated* `request.shop` straight into `WebhookMetadata`, which is handed to the app's business logic as trustworthy tenant identity: [4](#0-3) 

This is exactly the identity-binding gap the report describes: a field (`shop`) that is *acted on* (used to key tenant-scoped data via `WebhookMetadata#shop`) but is *not covered* by the cryptographic check that gates processing (`HmacValidator.validate`). Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, where the equivalent field is explicitly folded into the signed string: [5](#0-4) 

so the gem is inconsistent about which identity fields it actually binds to its own signature checks, and for webhooks it silently omits `shop` while still reporting the request as `valid`.

The equality that should hold but doesn't: `shop_claimed_in_header == shop_bound_by_hmac`. In practice `shop_bound_by_hmac` doesn't exist at all — only `body_bound_by_hmac == body_received` is checked.

### Impact Explanation
Because a single `client_secret` (`Context.api_secret_key`) is shared by an app across *all* its installed shops/tenants, any merchant who has installed the app (an unprivileged actor with respect to other tenants) receives genuinely Shopify-signed webhook bodies for their own shop. That attacker can replay the identical raw body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` (it only re-derives the HMAC from the untouched body), so `Registry.process` proceeds and calls the app's handler with `WebhookMetadata#shop` set to the victim's domain. Any host application that keys per-tenant state off `data.shop` (the pattern this gem's own `WebhookMetadata` encourages) can be made to attribute attacker-controlled webhook data to another merchant — a cross-tenant data integrity/confidentiality break attributable to this gem's verification primitive advertising more assurance than it provides.

### Likelihood Explanation
Requires only: (1) attacker installs the target app on their own shop (standard, unprivileged, no leaked credentials, no `api_secret_key`/access token needed), (2) capture one genuine webhook delivery to their own endpoint, (3) replay it to the same endpoint with an altered shop-domain header. No cryptographic material needs to be forged, since the body content itself isn't modified — only the outside identity header is swapped. This is straightforward and repeatable.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that `HmacValidator` authenticates, or otherwise have `Webhooks::Request`/`Registry.process` treat the `shop-domain` header as untrusted metadata that must be independently corroborated (e.g., against a shop known to have an active session/installation) before being handed to handlers as an authenticated tenant identity. At minimum, document clearly that `HmacValidator.validate` only proves body integrity, not the authenticity of any header field including `shop`, so host applications don't implicitly trust `WebhookMetadata#shop` as verified.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; app's `client_secret` is shared across all installs.
2. Shopify sends a legitimately HMAC-signed webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid hmac of body>`, and some JSON body.
3. Attacker resends the exact same body and HMAC header to the endpoint but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the modified headers/body; `HmacValidator.validate` returns `true` because it only checks the (unchanged) body against the (unchanged) HMAC — see [6](#0-5)  and [1](#0-0) .
5. `Registry.process` proceeds and invokes the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` — see [4](#0-3) , causing the host app to process attacker-supplied data under the victim's tenant identity.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
