### Title
`EvmHost.dispatch`/`fundRequest` do not refund excess native-token swap change to the caller, permanently trapping user funds in the host - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` accept `msg.value` and forward the entire amount into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The standard UniswapV2Router02 implementation refunds any unspent ETH (`msg.value - amounts[0]`) to `msg.sender` of the swap call — which is `EvmHost` itself, not the original caller (`_msgSender()`/`post.payer`). `EvmHost` never forwards that refunded dust back out, so any ETH sent above the exact swap cost is permanently retained by the contract with no path back to the payer.

### Finding Description
In `evm/src/core/EvmHost.sol`:

The same pattern repeats in `dispatch(DispatchGet)` [2](#0-1)  and `fundRequest` [3](#0-2) .

`swapETHForExactTokens` is documented to require *at least* the swap cost and to refund the difference to `msg.sender`. Since `EvmHost` itself calls the router (`msg.sender` from the router's perspective is `EvmHost`), any dust ETH refund lands in `EvmHost`'s own balance — not the app/user who called `dispatch`/`fundRequest`. `EvmHost` does not track or forward this residual balance anywhere; there is no subsequent `_msgSender().call{value: ...}` or equivalent refund logic in these functions (unlike the sibling `IntentGatewayV2`/`IntentsBase` contracts, which explicitly track `msgValue` and call `_sendValue(msg.sender, msgValue)` for any unspent native tokens, e.g. `IntentGatewayV2.sol` lines 394-397 and `IntentsBase.sol`'s `_sendValue`). This is the exact bug class from the external report: functions that check a payment is "at least" a required amount, swap/consume the required amount, but never reimburse the leftover — here permanently trapping caller ETH in the protocol contract instead of returning it, since callers must overestimate `msg.value` to guard against price slippage in `swapETHForExactTokens` (an exact-output swap whose exact input cost is not knowable in advance on-chain).

Because `dispatch`/`fundRequest` are the primary unprivileged entry points every app and end user uses to pay Hyperbridge relayer fees in native token (per the documented "Native Token Payment" flow), this is broadly and repeatedly reachable — any caller who cannot predict the exact swap price precisely (essentially always, since AMM prices move between quote and execution) will lose the difference on every native-token-paid dispatch or `fundRequest` call.

### Impact Explanation
This is a direct loss-of-funds bug for any unprivileged caller (app, relayer, or end user) using the native-token payment path for `dispatch()` or `fundRequest()`. Since `swapETHForExactTokens` is an exact-output swap, callers must send `msg.value` with margin above the expected fee cost to tolerate slippage/quote staleness; that margin is silently retained by `EvmHost` with no recovery mechanism exposed in these functions. Over the aggregate of all Hyperbridge dispatches paid in native token, this results in a continuous, uncapped drain of user funds into the protocol contract, meeting the "concrete theft ... of funds" bar via the message dispatcher's fee-payment path (`EvmHost`, the entry point behind `IDispatcher.dispatch`/`fundRequest` used across the intent gateway, token bridge, and general messaging apps).

### Likelihood Explanation
High likelihood: this triggers on essentially every call to `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest` that pays in native token, since callers cannot know the exact required `amounts[0]` ahead of the on-chain swap execution and must overpay to avoid reverts from price movement between quote-time and execution-time. No malicious actor or special preconditions are required — it happens under normal, honest usage of the documented native-token payment flow.

### Recommendation
After each `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the returned `amounts[0]` (actual ETH spent) and refund `msg.value - amounts[0]` back to `_msgSender()` (or `post.payer`), following the same pattern already used in `IntentGatewayV2`/`IntentsBase` (`_sendValue(msg.sender, msgValue)` for unspent native tokens). Alternatively, account for the returned dust in a `receive()`/sweep mechanism that credits it back to the original caller rather than absorbing it into the host's balance.

### Proof of Concept
1. Caller estimates the fee-token cost of `swapETHForExactTokens(feeAmount, [WETH, feeToken], EvmHost, deadline)` off-chain and, to tolerate slippage, sends `msg.value = estimatedCost * 1.5` when calling `EvmHost.dispatch(post)` (a normal, documented usage pattern since the exact swap input cannot be predicted precisely on-chain).
2. `EvmHost.dispatch` forwards the full `msg.value` to `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` [4](#0-3) .
3. The router spends only `amounts[0] < msg.value` and refunds the remainder `msg.value - amounts[0]` to `msg.sender` of the swap call, which is `EvmHost`'s own address (not the original caller).
4. `EvmHost.dispatch` proceeds to emit `PostRequestEvent` and returns, with no code path returning the refunded ETH to the caller [5](#0-4) .
5. The caller's excess ETH remains permanently stuck in `EvmHost`'s balance; repeating this across many callers accumulates continuous fund loss with no recovery function present in the contract for this specific residual.

    function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                post.fee, path, address(this), block.timestamp
            );
        } else if (post.fee > 0) {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
        }

        // adjust the timeout
        uint64 timeoutTimestamp = post.timeout == 0 ? 0 : uint64(block.timestamp) + uint64(post.timeout);
        PostRequest memory request = PostRequest({
            source: host(),
            dest: post.dest,
            nonce: uint64(_nextNonce()),
            from: abi.encodePacked(_msgSender()),
            to: post.to,
            timeoutTimestamp: timeoutTimestamp,
            body: post.body
        });

        // make the commitment
        commitment = request.hash();
        _requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});
        emit PostRequestEvent({
            source: string(request.source),
            dest: string(request.dest),
            from: _msgSender(),
            to: abi.encodePacked(request.to),
            nonce: request.nonce,
            timeoutTimestamp: request.timeoutTimestamp,
            body: request.body,
            fee: post.fee
        });
    }
