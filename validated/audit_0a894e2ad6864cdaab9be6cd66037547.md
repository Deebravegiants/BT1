### Title
Webhook `shop-domain` header is trusted for tenant identification without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, but the `shop` value used downstream to identify the tenant for the webhook handler is taken from an HTTP header that is not part of the signed content. This breaks the identity binding `shop-header == shop-that-produced-the-signed-body`, allowing a valid (attacker-obtainable) body/HMAC pair to be replayed with a different `shop-domain` header to impersonate another merchant's webhook to the app.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` and defines `to_signable_string` to return only the raw request body: [1](#0-0) 

The `shop` accessor, however, is read straight from an unauthenticated header (`shopify-shop-domain` / `x-shopify-shop-domain`) and is never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC only against this raw body via `Utils::HmacValidator.validate(request)`, and then forwards `request.shop` (the unauthenticated header value) straight to the app's handler as the tenant identifier in `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string` (the raw body), never touching `shop`: [4](#0-3) 

This is the same bug class as the referenced report: an authorization/identity check ("is this webhook really from shop X") is performed on the wrong data — the signature covers the body but not the field (`shop`) that the app relies on to bind the payload to a specific tenant. Any principal capable of producing one legitimately HMAC-signed payload (e.g., an unprivileged merchant who installed the app on their own store and receives real webhooks, or anyone who captures one webhook delivery) can strip/replace the `shopify-shop-domain` header on replay to make the app process the payload as belonging to a different shop, because the header is never authenticated.

### Impact Explanation
This crosses a tenant boundary within the app: the handler receives `WebhookMetadata#shop` claiming to be shop B, backed by a body/HMAC pair that only proves it was signed by the app's `api_secret_key` for *some* request, not that shop B produced it. Depending on what the app does with `data.shop` (e.g. looking up/mutating per-shop records, updating billing/subscription state, disabling/enabling features, triggering data deletion for a shop on `shop/redact` topics, etc.), this enables cross-tenant data corruption or unauthorized actions against a shop the attacker does not control — matching the "cross-tenant access" Critical impact class.

### Likelihood Explanation
Requires the attacker to have obtained at least one validly-signed HMAC/body pair (trivial for any merchant that installed the app, since Shopify sends them real webhooks routinely, or via any means of observing one delivery), then a single unauthenticated header rewrite and replay to the app's webhook endpoint. No access token, `client_secret`, or privileged account is needed — this is exploitable by an ordinary internet-facing actor who can reach the app's webhook route and possesses one legitimate webhook sample. Actual impact is bounded by what the hosting application does with `WebhookMetadata#shop`, which is outside this gem, but the gem itself provides no protection against this header-spoofing/replay pattern.

### Recommendation
Include `shop` (and ideally `topic`, `webhook_id`, `api_version`) in the HMAC-covered signable content, or otherwise cryptographically bind the shop-domain header to the signed body before it is trusted. At minimum, document that `Registry.process`/`Request#shop` is not authenticated by the HMAC and callers must independently verify the shop against a previously established session/installation record before using it as a tenant key.

### Proof of Concept
1. Attacker installs the app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery: raw body `B` with header `x-shopify-hmac-sha256: H` (valid HMAC over `B`) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the exact same body `B` and HMAC `H` to the app's webhook endpoint, but changes the header to `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC solely from `request.to_signable_string` (`B`) — validation succeeds since `B`/`H` are unchanged [5](#0-4) .
4. The registry dispatches the handler with `WebhookMetadata.new(... shop: request.shop ...)`, where `request.shop` now reads `victim.myshopify.com` from the spoofed header [2](#0-1) , causing the app to process attacker-controlled webhook content as if it originated from the victim shop.

          received_signature = verifiable_query.hmac
