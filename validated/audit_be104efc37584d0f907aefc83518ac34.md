### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook re-attribution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body [1](#0-0) . The `Request#to_signable_string` method that feeds this HMAC check returns only `@raw_body`, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers [2](#0-1) . Yet `request.shop`, taken verbatim from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header [3](#0-2) , is the value passed to the app's handler as the tenant identity for the webhook [4](#0-3) , and is documented as "The shop domain of the webhook" for apps to key off of [5](#0-4) .

### Finding Description
The identity binding that should hold is: `shop header used to attribute the event == shop cryptographically bound by the HMAC`. This is broken because the HMAC is computed and verified over `@raw_body` only:

```
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with `request.shop` as the tenant field:
```
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
end
``` [6](#0-5) 

An attacker who controls a shop that is itself a legitimate merchant of the app receives (or can capture) a real, validly-HMAC-signed webhook payload for their own store. Because the signature covers only the body bytes, the attacker can replay that exact body/HMAC pair directly to the app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header (e.g. a victim shop). `HmacValidator.validate` recomputes the signature only from `to_signable_string` (the body), which is unchanged, so validation still succeeds [7](#0-6) . The handler then receives `data.shop` set to the attacker-chosen domain while the body content actually belongs to the attacker's own shop — a field (`shop`) that is acted upon by the app is not bound by the same signature that authenticates the request.

### Impact Explanation
Any app built on this gem that uses `data.shop` from the webhook handler to decide which merchant's session/access token to use, which tenant's records to update, or which tenant's queue/job to enqueue (exactly as shown in the gem's own documented example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [8](#0-7) ) can be made to process attacker-supplied webhook content under a victim shop's identity. This is a cross-tenant identity-confusion vector reachable by any unprivileged Shopify merchant who is themselves a legitimate app installer (no access token, secret, or privileged account is required — only receipt of one's own legitimately delivered webhook).

### Likelihood Explanation
Likelihood is limited by two factors: (1) the attacker must be an installed merchant capable of triggering/receiving at least one webhook for their own shop to obtain a validly-signed body, and (2) the impact depends on the host application actually keying tenant-sensitive logic off `data.shop` without independently cross-checking it (e.g., against the topic-specific registered shop or an internal shop allowlist) — which is exactly what the gem's own documentation shows as the intended usage pattern. Because the vulnerable binding (HMAC over body only, `shop` unauthenticated) lives entirely in this gem's `Request`/`Registry` code and matches the gem's documented handler pattern, this is not merely "host app ignoring documented API" — it is the documented API failing to bind the field it exposes as tenant identity.

### Recommendation
Do not treat `shop-domain` (or `topic`/`webhook-id`) as authenticated data. At minimum, document prominently that `data.shop` is unauthenticated and must be cross-validated by the consuming app against a known/expected shop for that webhook subscription (or against a stored session) before being used for tenant-sensitive operations. Where feasible, `Registry.process` could also enforce that the topic/shop pair matches a topic that was actually registered, reducing (but not eliminating, since Shopify's HMAC scheme is body-only) the risk of silent cross-tenant misattribution.

### Proof of Concept
1. As merchant A (attacker, a legitimate installer of the app), receive a real webhook delivery for topic `orders/create`, capturing the raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` with the app's shared secret).
2. POST directly to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged), `x-shopify-topic: orders/create` (unchanged), but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` builds the request from these headers; `HmacValidator.validate` recomputes the signature only from `@raw_body`, which still matches `H`, so `Registry.process` accepts it [1](#0-0) .
4. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and body content that is actually attacker A's own order data [4](#0-3) , causing any app logic keyed on `data.shop` to misattribute the event to the victim tenant.
