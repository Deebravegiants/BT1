### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` value used for tenant identification purely from an unauthenticated HTTP header, while the HMAC signature that this gem verifies covers only the raw request body. This breaks the intended identity binding `verified_bytes == acted_on_identity`, mirroring the reported bug class: a field acted upon (`shop`) is not covered by the authenticity check (`HMAC`).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Webhooks::Registry.process` validates the webhook exclusively via `Utils::HmacValidator.validate(request)`, which HMACs `to_signable_string` (i.e. the body only) against `Context.api_secret_key`: [2](#0-1) [3](#0-2) 

However, `request.shop` — the value that identifies which merchant/tenant the webhook belongs to — is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never included in the signed string: [4](#0-3) 

After HMAC validation passes, `process` builds `WebhookMetadata` directly from `request.shop` and hands it to the app's registered handler, so the handler trusts this unverified value as the webhook's tenant: [5](#0-4) 

The equality that should hold is: `shop bound by HMAC == shop used by handler`. In reality: `shop bound by HMAC == {} (nothing)` while `shop used by handler == header value` — an attacker-controllable field that is disjoint from the cryptographically verified bytes.

### Impact Explanation
Because the `shop-domain` header is not part of the signed payload, an attacker who possesses one legitimately-signed webhook body+HMAC pair (trivially obtainable by registering their own store's webhook to an endpoint they control, since Shopify signs webhooks per-app with the same `client_secret`, not per-shop) can replay that exact body/HMAC to the target app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `HmacValidator.validate` will still return `true` because it only checks the body, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to a different, victim shop. Any app logic that keys off `WebhookMetadata#shop` (e.g. `app/uninstalled`, `shop/redact`, `customers/redact`, or business logic that looks up a session/tenant record by `shop`) can be tricked into acting on the wrong tenant — a cross-tenant integrity/confusion issue.

### Likelihood Explanation
Exploitation requires no privileged credentials or access to the app's `client_secret` — only the ability to (a) register any Shopify store trigger a webhook to an attacker-controlled receiver to capture one valid `(body, hmac)` pair, and (b) send an HTTP POST to the victim app's public webhook endpoint with forged headers, which is functionality this gem exposes generically (`ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)`). This is a purely unprivileged-internet-user path through the gem's own verification logic.

### Recommendation
Include the shop domain (and other identity-bearing headers such as `webhook-id`/`api-version` if they influence handler behavior) in the signed material, or otherwise cryptographically bind `shop` to the verified payload before constructing `WebhookMetadata`. At minimum, `HmacValidator`/`Request#to_signable_string` should incorporate the shop header the same way Shopify's own HMAC-with-headers verification scheme intends, so `process` cannot be tricked into associating a validly-signed body with an attacker-chosen shop.

### Proof of Concept
1. Attacker registers a webhook (any topic) pointing to an endpoint they control, using their own Shopify store `attacker-shop.myshopify.com`.
2. Shopify delivers the webhook to the attacker's endpoint with headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` to the victim app's real webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` recomputes the HMAC over `raw_body` only and it matches, so `Registry.process` proceeds: [6](#0-5) 
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload was never issued for that shop, allowing tenant-confused processing in the host application.
