### Title
Webhook `shop-domain` header is trusted for tenant routing but not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, never over the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` validates that HMAC and then unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the app's registered handler. This breaks the identity binding "shop authenticated == shop acted on": the gem cryptographically proves the *body* came from Shopify, but never proves *which shop* that body belongs to.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from an attacker-controllable HTTP header, with no cryptographic tie to the body or the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to construct the metadata passed to the app's handler, without re-deriving or cross-checking the shop against anything covered by the signature: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` only ever operate on `verifiable_query.to_signable_string`, i.e. the raw body for webhooks — the shop header never enters the computation: [4](#0-3) 

Because the JSON body for many webhook topics does not redundantly encode the shop domain in a way the app cross-validates, and the gem provides no built-in cross-check, an unprivileged party who legitimately receives webhooks for their **own** shop (e.g., any merchant who installs the app) can capture a raw body + its valid `shopify-hmac-sha256` value from their own webhook deliveries, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting a victim's shop domain in the `shopify-shop-domain` header. `HmacValidator.validate` still passes (it only checks the body against the secret), and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the victim's shop domain instead of the attacker's own shop.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` (as returned by this library) to look up the merchant's session/access token, write data, or trigger merchant-scoped side effects — which is exactly the intended and documented usage pattern of `ShopifyAPI::Webhooks::WebhookHandler` — an attacker can cause the handler to execute logic against a victim shop's stored session/state using data the attacker controls (their own webhook body, replayed under a spoofed tenant identity). This is a cross-tenant confusion vector: the library's own trust boundary (HMAC-validated ⇒ safe to act on `request.shop`) is false, because `shop` is not part of the signed content. This satisfies the Critical "cross-tenant access" impact category, since the vulnerability lives entirely in this gem's `Webhooks::Request`/`Webhooks::Registry` code path and does not require the app to violate documented usage — the gem's documented API (`Registry.process` → handler receives `WebhookMetadata.shop`) is exactly what enables the confusion.

### Likelihood Explanation
Exploitation requires the attacker to possess one valid (body, HMAC) pair, which any merchant installing the app can trivially obtain by triggering a webhook for their own store (e.g., creating an order) and capturing the raw POST. No access to `api_secret_key` or any victim credential is needed — only replay of previously-observed, non-secret wire data with a modified header, which is well within an "unprivileged internet user" threat model. The main mitigating factor is that downstream apps must actually key merchant lookups off the header-provided shop for the impact to materialize, and TLS/network delivery to the endpoint is otherwise ordinary internet traffic to the app's public webhook route.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) as part of the signed material verified by `HmacValidator`, or have `Registry.process` independently verify that the `shop` header matches a shop domain that can be derived from data that *is* covered by the HMAC (e.g., a `shop_id`/`myshopify_domain` field embedded in and validated against the payload where the topic supports it). At minimum, document explicitly and enforce in code that `WebhookMetadata#shop` must never be used as the sole tenant key without an additional application-level correlation (e.g., matching against the `id`/`admin_graphql_api_id` fields already scoped in the payload, or validating against a previously known list of installed shop domains) since it is not authenticated by the HMAC.

### Proof of Concept
```ruby
require "openssl"
require "base64"

secret = "shpss_test_secret" # ShopifyAPI::Context.api_secret_key

# Attacker legitimately receives this webhook for THEIR OWN shop:
raw_body = '{"id":123,"note":"legit order for attacker-shop.myshopify.com"}'
hmac_digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)
valid_hmac_b64 = Base64.encode64(hmac_digest)

# Attacker replays the SAME body + SAME hmac, but swaps the shop header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <-- not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes: HmacValidator only checks raw_body against the secret.
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process will invoke the handler with data.shop == "victim-shop.myshopify.com",
# even though the body/HMAC pair originated from the attacker's own shop delivery.
ShopifyAPI::Webhooks::Registry.process(request)
```
