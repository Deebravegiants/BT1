### Title
Biometric data (personal custody package) uploaded to backend before signup authorization/fraud verdict is finalized - ([File: src/plans/mod.rs])

### Summary
In `do_signup` the orb builds and uploads the user's raw biometric material (iris codes/shares, face embeddings, normalized iris images) to the backend via `build_pcp` and `upload_pcp_tier_0`/tiered uploads *before* the actual enrollment/authorization call (`enroll_user`, which performs `signup_post::request` + `signup_poll::request`) is made and its result is known. The on-device fraud check that runs earlier (`detect_fraud`) is a no-op stub. This mirrors the reported bug class ("external call executed before the state that finalizes/authorizes the operation is settled") — here the external call is the disclosure/persistence of sensitive biometric data to the backend, and the "burn" (i.e., the authoritative enrollment decision) happens only afterward.

### Finding Description
`Plan::do_signup` executes the following order:
1. `detect_fraud` is called, but the implementation is hard-stubbed to always return `false` — "FOSS: WE HAVE DELETED ALL FRAUD CHECKS": [1](#0-0) 
2. `signup_reason` is computed from this meaningless fraud result.
3. `build_pcp` constructs the personal custody package containing the user's actual iris codes/shares, normalized iris images, and face embeddings: [2](#0-1) 
4. The package (tier 0, and tiers 1/2 for pcp_version >= 3) is uploaded to the backend via `upload_pcp_tier_0` / `data_uploader`, which performs the external network call `backend::upload_personal_custody_package::request`: [3](#0-2) [4](#0-3) 
5. Only *after* this biometric data has already been transmitted/persisted does the code call `enroll_user`, which performs the actual authoritative signup creation and polls for the backend's verdict (success / duplicate / fraud / server error): [5](#0-4) [6](#0-5) 

Because the biometric upload (the "external call") is not gated on the outcome of `enroll_user` (the actual authorization/fraud decision, analogous to "burning the shares" before value is released in the original report), a signup that is later determined to be unauthorized, duplicate, or fraudulent by the backend's own signup/poll endpoint still results in the user's raw iris code shares and face embedding data having been fully uploaded and stored beforehand. The local `detect_fraud` gate that nominally runs before the upload provides no actual protection since it always returns `false`.

### Impact Explanation
This ordering allows biometric data disclosure/retention to occur independent of whether the signup is ultimately authorized. Since real fraud/duplicate detection is performed only server-side by `signup_post`/`signup_poll` (invoked in step 5, after the data already left the device), any signup path that reaches `build_pcp`/`upload_pcp_tier_0` will have already leaked/stored the user's iris code shares and face embeddings on the backend regardless of the final enrollment verdict. This is the biometric-upload/retention analog of "funds transferred before shares burned" — data exposure occurs before the operation is authoritatively finalized.

### Likelihood Explanation
This occurs on every normal signup path reaching biometric pipeline completion (not an edge case), since `build_pcp`/upload always run prior to `enroll_user` in `do_signup`. It requires no attacker action beyond running a normal (or intentionally-to-be-rejected) signup attempt, making the likelihood of biometric data reaching backend storage ahead of authorization high.

### Recommendation
Reorder `do_signup` so that the personal custody package build/upload only occurs after `enroll_user` (and the backend's fraud/duplicate verdict from `signup_post`/`signup_poll`) confirms the signup is legitimate and authorized, or ensure any pre-authorization upload is provisional/revocable (e.g., uploaded to a quarantined, orb-scoped store that is only linked/finalized to the user identity after the backend authorization succeeds). At minimum, restore genuine on-device fraud detection in `detect_fraud` before any biometric package leaves the device, rather than the current stub that always returns `false`.

### Proof of Concept
Not independently reproducible from static review alone (requires live backend interaction); the ordering issue is demonstrated structurally: `build_pcp`/`upload_pcp_tier_0` (src/plans/mod.rs:574-636) execute and complete before `enroll_user` (src/plans/mod.rs:647-656) is invoked, and `detect_fraud` (src/plans/mod.rs:1390-1406) — the only pre-upload gate — is a stub always returning `false`, so no signup reaches `build_pcp` after being locally rejected for fraud; all such gating is deferred to the post-upload `enroll_user` call.
