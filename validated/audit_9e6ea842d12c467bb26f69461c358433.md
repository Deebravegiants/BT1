## #Vulnerability found

### Title
Session hijacking via unauthenticated, predictable session cookie value used as session-store lookup key - (File: lib/shopify_api/utils/session_utils.rb)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` returns the raw, unsigned `shopify_app_session` cookie value verbatim as the session-store lookup key for non-embedded apps (and as a fallback for embedded apps). That value is nothing more than a predictable string built by `ShopifyAPI::Auth::Session.from` as `"offline_#{shop}"` or `"#{shop}_#{associated_user.id}"`. Because the cookie carries no cryptographic signature binding it to the browser/session that actually completed OAuth, an unauthenticated attacker who knows (or guesses) a target shop's `myshopify.com` domain can set that cookie value directly in an HTTP request and cause the host application to look up and use that shop's stored offline access token.

### Finding Description
The identity binding the app relies on for authentication should be: `cookie value` == `an unforgeable proof that this browser completed OAuth for the shop`. In this gem, that binding is broken:

- The cookie value is set to `session.id` at the end of OAuth: [1](#0-0) 

- `session.id` is a deterministic, non-secret string derived only from the `shop` and (for online sessions) the numeric user id — no random/secret component beyond what an attacker can enumerate for offline sessions: [2](#0-1) 

- `SessionCookie` is a plain struct holding this string value; nothing signs or MACs it: [3](#0-2) 

- When resolving "the current session," the gem takes whatever is in the cookie and returns it unchanged as the lookup key, for non-embedded apps unconditionally, and for embedded apps whenever no `shopify_id_token` is supplied: [4](#0-3) [5](#0-4) 

The host application is documented to use this returned id to fetch a stored `Session` (containing the shop's real `access_token`) from its session storage and then make authenticated Admin API calls with it. Since `"offline_#{shop}"` is entirely predictable from a publicly-known shop domain, and nothing verifies the cookie was ever issued by this server to this browser for this shop, an attacker who never completed OAuth can simply present `Cookie: shopify_app_session=offline_<victim-shop>.myshopify.com` and have the host app treat them as authenticated for the victim shop.

### Impact Explanation
This is a critical impact: cross-tenant access and effective theft/use of a merchant's offline access token. Any unprivileged internet user who knows a target's `myshopify.com` domain (public information — it's the store's own domain) can forge the session cookie and cause the app to act with that shop's access token, without possessing credentials, without social engineering, and without any privileged access.

### Likelihood Explanation
High likelihood: no secret material, TLS interception, or privileged access is required. Shop domains are public. The session id format (`offline_#{shop}`, `#{shop}_#{user_id}`) is deterministic and documented/inferable from the gem's own source. For non-embedded apps this path is the only one used (`current_session_id`), and for embedded apps it's a documented fallback whenever an id token isn't presented.

### Recommendation
Do not use an unsigned, predictable string as the bearer credential for session lookup. Bind the cookie to server-side state that only the server can produce/verify, e.g.:
- Store an unpredictable, high-entropy random token (like the OAuth `state`/nonce already used) as the cookie value, and use it purely as an opaque pointer to the session that was created server-side, rather than deriving/reconstructing the shop identity from the cookie value.
- Alternatively, HMAC-sign the cookie value (id + expiry) with `api_secret_key` and verify the signature before trusting it as a lookup key, so the identity bound to the cookie cannot be forged without the app's secret.

### Proof of Concept
1. Attacker learns (or guesses) the victim's shop domain, e.g. `victim-shop.myshopify.com` (public knowledge).
2. Attacker sends a request to any authenticated route of the target host app with header:
   `Cookie: shopify_app_session=offline_victim-shop.myshopify.com`
3. Host app (per documented usage) calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which for a non-embedded app (or embedded-without-id-token) returns `cookie_session_id(cookies)` unchanged: [6](#0-5) 
4. Host app looks up `"offline_victim-shop.myshopify.com"` in its session storage, retrieves the victim shop's real `Session` (with `access_token`), and performs Admin API calls on the attacker's behalf using the victim's credentials — with the attacker never having completed OAuth for that shop.
