### Title
Permanent, unbounded freezing of stray LT transferred into `Bonding` — no rescue path exists outside the graduation-earmark sweep - ([File: packages/contracts/src/Bonding.sol])

### Summary
Any unrelated wallet can send the reserve-asset LT directly to `Bonding` via a plain ERC20 `transfer`. `finalizeGraduation`'s `protectedLT` accounting is *designed* to treat any LT balance above the current graduation's `ltFromPair` earmark — whether it's a concurrent graduation's escrow or stray/misdirected dust — as off-limits to both the LP deposit and the post-sweep. There is no other function in `Bonding` that can recover this stray LT: it accumulates, unbounded, call after call, and is never freed, mirroring the CVE's pattern of a resource that is allocated (a balance held by the contract) but never released on the path that should reclaim it.

### Finding Description
`finalizeGraduation` snapshots the "protected" LT balance before doing anything else: [1](#0-0) 

`protectedLT` is defined as *any* balance beyond `p.ltFromPair` for the token being finalized — the code and its own natspec state this covers two cases: another graduation's escrow, **or "stray dust."** `_sweepLTToOwner` is then called with `keep = protectedLT`, and by construction never touches anything below that floor: [2](#0-1) 

The design intent is confirmed explicitly in the contract's own documentation, which states contamination "stays in `Bonding`" by design so it isn't misclassified: [3](#0-2) 

There is no other admin- or permissionless-callable function shown in the graduation code path (`_prepareGraduationLiquidity`, `_seedUniswapV2Direct`, `_seedDirectMint`, `_seedRebalancing`, `_sweepLTToOwner`) that can ever drain LT sitting in `Bonding` below the `protectedLT` floor. Consequently, any LT an unrelated wallet transfers directly to `Bonding` (outside of the `Router.graduate` escrow flow) is permanently walled off from every subsequent `finalizeGraduation` call for every token sharing that LT, for as long as the protocol operates — each stray transfer only adds to a floor that is never reduced. This is structurally identical to the CVE's root cause: a resource that is allocated/held but is never freed on the code path that governs its lifecycle, so repeated occurrences accumulate without bound.

### Impact Explanation
Every LT unit sent directly to `Bonding` (accidental misdirected transfers, or a griefer wishing to permanently lock LT value out of circulation) is frozen forever — it can never reach `LPLock`, the owner, or any trader/creator. Because `protectedLT` is a floor with no decrement mechanism, this is a strictly growing, permanent loss of reserve-asset value with no cap, i.e., real, accumulating freezing of funds inside a production contract with no recovery function.

### Likelihood Explanation
The trigger requires only an ERC20 `transfer` of LT to the `Bonding` contract address — a single unprivileged transaction, reachable at any time, with no dependency on graduation timing, token state, or any other precondition. This is explicitly listed as an in-scope reachable action.

### Recommendation
Add a permissionless or owner-gated rescue function that can sweep LT balances in `Bonding` that are not currently earmarked by *any* live `pendingGraduation[...].ltFromPair` across all tokens paired to that LT (i.e., true orphaned dust, distinguishable from legitimate concurrent-graduation escrow by summing all outstanding earmarks for that LT rather than only the single token being finalized). This mirrors `FeeVault.sweepDonations`, which already provides an equivalent recovery path for a different asset class.

### Proof of Concept
1. Launch token A against LT `L` and let it enter `Lifecycle.Graduating` (phase 1), so `pendingGraduation[A].ltFromPair = X` is escrowed in `Bonding`.
2. Before phase 2 (`finalizeGraduation(A)`) is called, an unrelated wallet calls `L.transfer(address(bonding), D)` for some dust amount `D`.
3. Call `bonding.finalizeGraduation(A)`. `ltBalance = X + D`; `protectedLT = (X + D) - X = D`. `_sweepLTToOwner(lt, D)` computes `bal = D` (post phase-2 consumption of `X`), sees `bal <= keep`, and returns without sweeping anything.
4. `D` remains in `Bonding` indefinitely. Repeat step 2 for any number of unrelated transfers before any future `finalizeGraduation` call on any token sharing `L`; each repetition strictly increases the permanently stuck balance, with no function anywhere in the contract capable of ever moving it out.

```text
    function _sweepLTToOwner(
        address lt,
        uint256 keep
    ) internal {
        uint256 bal = IERC20(lt).balanceOf(address(this));
        if (bal <= keep) return;
        uint256 amount = bal - keep;
        address recipient = owner();
        IERC20(lt).safeTransfer(recipient, amount);
        emit LTRescued(lt, recipient, amount);
    }
```

```markdown
`finalizeGraduation` snapshots `protectedLT = balanceOf(this) - p.ltFromPair` at the top: any LT in `Bonding` beyond this graduation's earmark is either another concurrent graduation's escrow (Phase 1 already moved it in via `Router.graduate`) or stray dust. Both must stay out of THIS graduation's LP and post-sweep.

That snapshot is plumbed through `_seedUniswapV2Direct` → `_seedRebalancing` → `_routerDepositAndDispose`, where the deposit allowance is capped at `balanceOf(this) - protectedLT`. Then a single `_sweepLTToOwner(lt, protectedLT)` at the end of `finalizeGraduation` sends only THIS graduation's rebalance residue to the protocol owner, leaving any concurrent-graduation escrow / stray dust untouched. Honest empty-pair graduations have no residue at the post-sweep so it's a no-op there.

Two scenarios this guards against:

- **Concurrent graduations on the same LT.** Two tokens A and B share an LT and both reach `Lifecycle.Graduating` before either finalizes (the keeper takes ~60s and popular LTs see overlap). Without `protectedLT`, A's finalize would treat the full balance as its own and either sweep B's escrow to the owner (bricking B's later finalize) or — for hostile-pre-seed graduations — deposit it into A's locked LP. With it, A only ever sees `ltFromPair_A` and B is preserved.
- **Cross-token LT residue.** Old residue or a misdirected transfer sitting in `Bonding` would otherwise be visible to `_routerDepositAndDispose`'s `balanceOf(this)` read and could be silently consumed into a future graduation's locked LP. With `protectedLT`, contamination stays in `Bonding` and the deposit only sees this graduation's earmark.

The auto-sweep emits `LTRescued(lt, owner, amount)` for indexer observability. The dedicated regression tests for these edge cases were removed alongside `HostilePreSeed.t.sol`; future changes to `finalizeGraduation` / `_routerDepositAndDispose` / `_sweepLTToOwner` should add targeted coverage if the behaviour is non-obvious from the unit-level tests in `TwoPhaseGraduation.t.sol`.
```
