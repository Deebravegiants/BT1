### Title
Webhook `shop-domain` Header Is Trusted for Tenant Identity but Not Covered by the HMAC Signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is used throughout the webhook pipeline to identify which tenant (shop) a webhook belongs to, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body, never the `shop-domain` header. This breaks the identity binding: `shop header used by handler == shop header covered by HMAC` is false. An attacker who can obtain one valid `(body, hmac)` pair for the app's shared client secret (e.g. by installing the app on their own shop and capturing a genuine, Shopify-signed webhook delivery) can replay that same body/HMAC pair while substituting an arbitrary victim `shop-domain` header, and the gem will accept it as authentic and hand it to the app's handler as if it came from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile, `shop` is read directly from an attacker-controllable header with no cross-check against the signed content: [2](#0-1) 

`Registry.process` validates the HMAC (which, as shown above, is computed only from the body) and then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string` (the body) and the app's shared `api_secret_key`/`old_api_secret_key`: [4](#0-3) 

The gem's own documentation confirms that `data.shop` is treated as an authoritative tenant identifier by consuming applications (e.g. used to enqueue background jobs keyed by `shop_domain`): [5](#0-4) 

Because the app's `client_secret` (and hence the HMAC key) is shared across every shop that installs the app — not shop-specific — any shop owner who has installed the app can capture a legitimately-signed `(body, hmac)` webhook pair delivered to the app's endpoint for their own shop. That pair remains cryptographically valid regardless of which `X-Shopify-Shop-Domain` header accompanies it, since the header is never part of the signed content. Replaying the same body/HMAC with the `shop-domain` header changed to a victim shop passes `HmacValidator.validate` unchanged, and `Registry.process` forwards the forged `shop` value straight to the app's handler.

### Impact Explanation
This is a cross-tenant access vector: an attacker who has (legitimately) installed the app on their own store can cause the app to process attacker-chosen webhook payloads (of any topic they can trigger for their own shop, e.g. `orders/create`, `customers/update`, `app/uninstalled`) while impersonating any other shop that uses the same app. Depending on how the host application consumes `data.shop` (as documented, apps commonly use it directly to select the tenant record to update), this can lead to cross-tenant data corruption or state changes attributed to a victim merchant, which matches the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to be able to install the target app on a shop they control (a low bar — any developer/trial store qualifies as an "unprivileged" actor with respect to other merchants' data) and to capture one genuine webhook delivery (body + HMAC) from their own shop, which is trivial since it is delivered straight to their own app infrastructure or a proxy they control. No access token, `api_secret_key`, or victim-shop credentials are needed — only the ability to replay an HTTP request with a modified header, which the gem does not protect against.

### Recommendation
Include the shop domain (and ideally the topic/webhook-id) in the HMAC-covered `to_signable_string`, or otherwise independently verify that the `shop-domain` header matches a shop the app actually expects/has an active session for before dispatching to the handler. At minimum, document and enforce that consuming applications must not trust `data.shop` unless it is cross-validated against a known installed-shop record independent of this header.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g., updates a product) causing Shopify to POST a signed webhook to the app's endpoint:
   - Headers: `X-Shopify-Topic: products/update`, `X-Shopify-Hmac-Sha256: <valid HMAC over body>`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - Body: `{"id": 123, ...}`
3. Attacker captures this raw body and HMAC value (they control the receiving proxy/logs since it's their own installation).
4. Attacker resends an HTTP request to the same app endpoint with the identical body and `X-Shopify-Hmac-Sha256` value, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks the body signature: [6](#0-5) 
6. `ShopifyAPI::Webhooks::Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"`, causing the app to act as though the payload originated from the victim shop.
