### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body via HMAC, but the `shop` (and `topic`/`webhook_id`) values used to route and process the webhook are taken from unauthenticated HTTP headers that are never included in the signed payload.

### Finding Description
`Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the request: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — it does not include the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers: [3](#0-2) 

Yet those same unauthenticated headers are exactly what `Registry.process` uses to identify the tenant and dispatch the payload to the handler: [1](#0-0) 

This breaks the intended identity binding: the equality that should hold is `shop(header) == shop(bytes covered by HMAC)`, but instead the gem only proves `HMAC(secret, raw_body)` is valid — a property that holds identically for *every* shop that shares the same app's `api_secret_key` (i.e., every merchant that installs the app, since Shopify apps use one `client_secret`/`api_secret_key` for all installations). Any party who can obtain one validly-signed `(raw_body, hmac)` pair from Shopify for their *own* store (trivial: install the app and trigger any webhook, or replay a captured webhook) can resubmit that exact body to the app's webhook endpoint with a forged `shop-domain` header naming a different, victim shop. `HmacValidator.validate` will report success because it never looks at the header, and `Registry.process` will hand `WebhookMetadata.new(topic:, shop: request.shop, ...)` — with `shop` set to the attacker-chosen value — to the app's registered handler.

### Impact Explanation
This is a cross-tenant identity-binding bypass: an unprivileged internet user who controls (or has previously observed) any validly-signed webhook body for the shared `api_secret_key` can make the library assert an arbitrary `shop` value to the host application's webhook handler. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to load that shop's stored session/access token, to write attacker-supplied `body` data against another merchant's records, or to trigger shop-scoped side effects), this enables cross-tenant data corruption or disclosure without ever needing the victim's access token or credentials — satisfying the "cross-tenant access" bar.

### Likelihood Explanation
Any app installed on more than one shop (i.e., any typical public/embedded Shopify app) shares one `api_secret_key` across all its installations. An attacker only needs to install the app on their own shop (or otherwise obtain one legitimately-signed webhook body/HMAC pair) to derive a signature that will validate for a forged `shop-domain` header pointed at any other shop. No secret leak, TLS interception, or privileged account is required — only the ability to install/interact with the app as any ordinary merchant and to POST directly to the app's public webhook endpoint.

### Recommendation
Bind the `shop`/`topic`/`webhook_id` identity to the signed material, not just the raw body:
- Include the relevant Shopify headers (at minimum `shop-domain`) in the signable string used for HMAC verification, or
- After HMAC verification, cross-check `request.shop` against the shop associated with the specific webhook subscription (e.g., by looking up the webhook by `webhook_id`/topic registration rather than trusting the header at face value), and reject if it does not match the expected tenant for that session/handler context.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` (or subscribes to any webhook topic).
2. Shopify sends the attacker a webhook: `raw_body = B`, header `x-shopify-hmac-sha256 = HMAC(secret, B)`, header `x-shopify-shop-domain = attacker.myshopify.com`.
3. Attacker resends the same `raw_body = B` and the same valid `hmac` header to the app's webhook endpoint, but replaces `x-shopify-shop-domain` with `victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds successfully (all required headers present), and `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, B)`, which is unchanged — see `to_signable_string` at [4](#0-3) .
5. `Webhooks::Registry.process` passes `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: JSON.parse(B), ...)` to the app's handler, which now believes the event/body legitimately originated from `victim.myshopify.com` — see [1](#0-0) .
