Confirmed root cause: the HMAC (`Utils::HmacValidator.validate`) validates only `Request#to_signable_string`, which returns the raw request body [1](#0-0) , while `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly and unauthenticated from HTTP headers [2](#0-1) . `Registry.process` validates the HMAC and then dispatches to the handler using `request.shop` as the tenant identifier, without the HMAC covering that field [3](#0-2) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers that are never included in the HMAC signature computation. `Utils::HmacValidator.validate` only checks the signature against `to_signable_string`, which is the raw body. This breaks the identity binding: `shop` (used to dispatch/attribute the webhook to a tenant) ≠ `shop` (covered by the HMAC that authenticates the payload).

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) . `Utils::HmacValidator.validate_signature` computes the HMAC over exactly that signable string and compares it to the `hmac` header value [4](#0-3) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from request headers with no cryptographic binding to the body or the HMAC [2](#0-1) .

`Registry.process` validates the HMAC and, once it passes, trusts `request.shop` (and `request.topic`) to look up the handler and construct `WebhookMetadata`, which is handed to the app's per-tenant handler logic [3](#0-2) .

Because the signature never covers `shop`, any request carrying a body+HMAC pair that is valid for *some* shop (e.g. a webhook the attacker legitimately received for their own store, where the app is installed on an attacker-controlled shop) will still pass `Utils::HmacValidator.validate` even after the `shopify-shop-domain` header is swapped to a victim shop's domain. The equality that should hold — `shop authenticated by HMAC == shop used for tenant dispatch` — does not hold, because the HMAC never authenticates `shop` at all.

### Impact Explanation
An attacker who legitimately receives webhooks for their own store (trivial: install the app on their own shop, trigger any webhook event) can capture a valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) header. `Registry.process` will accept it as authentic and route it to the handler tagged with the attacker-chosen shop, letting the attacker inject fabricated webhook events/data attributed to another tenant — a cross-tenant integrity/confusion issue in how this gem exposes verified webhook data to the host application.

### Likelihood Explanation
Requires only that the attacker be able to obtain one valid `(body, hmac)` pair for any shop where the app is installed (including their own shop, which they control) and be able to send an HTTP request to the app's public webhook endpoint — no access token, `client_secret`, or privileged account is needed, satisfying the "unprivileged internet user" threat model.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signature verification rather than trusting bare headers: either extend `to_signable_string`/`VerifiableQuery` so the HMAC covers a canonical string that includes the shop domain and topic, or require the host application to independently verify that `request.shop` matches an expected/registered shop for the delivery context before dispatch. At minimum, document that `shop` is unauthenticated and must not be used as the sole tenant key without additional verification (e.g., cross-checking against a known/expected shop for that webhook subscription).

### Proof of Concept
```ruby
# 1. Attacker installs the app on their own shop "attacker.myshopify.com"
#    and triggers a webhook (e.g. orders/create), capturing the raw POST:
#    body = '{"id":1,...}'
#    valid_hmac = <value of shopify-hmac-sha256 header Shopify sent>

# 2. Attacker replays the exact same body+hmac to the app's public
#    webhook endpoint, but swaps the shop header:
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => valid_hmac,          # still valid: HMAC only covers raw_body
  "shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)

ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true (HMAC matches raw_body)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create",
#      shop: "victim-shop.myshopify.com", body: parsed_body, ...))
# The host app's handler now believes this payload legitimately originated
# from victim-shop.myshopify.com.
``` [3](#0-2)
