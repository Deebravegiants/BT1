### Title
Webhook `shop` (and `topic`/`webhook-id`) identity is not bound by the HMAC signature, allowing a malicious merchant to spoof a webhook's tenant - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC computed over the raw request body, but the shop identity (`X-Shopify-Shop-Domain` / `shopify-shop-domain` header) delivered to the app's handler is never part of that HMAC. This breaks the intended binding `shop verified by HMAC == shop delivered to handler`, letting an attacker who controls one legitimate, validly-signed webhook body swap in a different shop domain header and have it accepted and dispatched as if it belonged to that other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors are read straight from untrusted request headers, entirely outside the signed material: [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (i.e., the body HMAC) before dispatching to the handler with the header-derived `shop`: [3](#0-2) 

`HmacValidator.validate` computes and compares the signature only over `to_signable_string` (the body), never incorporating the `shop` header: [4](#0-3) 

The gem's own documentation tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" and then hands the handler `data.shop` to key business logic per-tenant (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) [6](#0-5) 

The identity equality that should hold is: `shop that produced/authorized the signed body == shop passed to the handler`. Because the header is not part of the signed content, an attacker who owns (or briefly controls) one shop can capture a legitimately-signed webhook body/HMAC pair generated for their own tenant and re-POST it to the app's webhook endpoint with the `shop-domain` header changed to an arbitrary victim shop. `Registry.process` will still validate (the HMAC only checks the body bytes, which weren't altered) and will invoke the handler believing the event originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary: an attacker-controlled shop can inject fabricated webhook events attributed to a different shop into the host application, without ever obtaining that victim shop's access token or the app's `client_secret`. Depending on how the host app uses `data.shop` (as most integrators are told to, per the documented example), this enables cross-tenant data injection/spoofing — e.g., forging `app/uninstalled`, `shop/redact`, or business-data webhooks (`orders/create`, `customers/update`, etc.) that the receiving application will process as if they came from the victim shop. This matches the "cross-tenant access" High-impact category.

### Likelihood Explanation
Any merchant who installs the app (a low-privilege, non-attacker-favored position relative to other tenants) can trigger a real event on their own store to obtain one valid `(body, hmac)` pair, then trivially replay it with a modified `shop-domain` header via a normal HTTP POST to the public webhook endpoint. No secrets, tokens, or elevated access are required — only knowledge of the app's public webhook URL and the ability to make an HTTP request, which is standard for a webhook receiver.

### Recommendation
Bind the shop (and ideally topic/webhook-id) to the authenticated payload rather than trusting the header value independently of the HMAC. Options include: verifying that the `shop` header matches a shop for which the webhook was actually registered (cross-checked against stored registration state) before dispatching, or otherwise not treating the header-derived `shop` as an authenticated value in documentation/handler contracts without such a check.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and registers for `orders/create` (or any topic).
2. Attacker triggers an order on their own shop, causing Shopify to POST a validly HMAC-signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `B` and `H`, then sends a new POST to the app's webhook endpoint with the same body `B` and HMAC header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` — the shop header is never inspected. [3](#0-2) 
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, and the host app processes the (attacker-controlled) event content as belonging to `victim-shop`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
