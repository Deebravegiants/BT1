### Title
Permissionless `Initialize2` allows front-running/griefing of a market's canonical AMM pool address with attacker-chosen minimal liquidity, permanently blocking the legitimate pool creator - (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives the AMM pool, LP mint, target-orders, and coin/pc vault PDAs solely from the `market_info` account key, with no check that the caller is authorized to create a pool for that specific market. Any unprivileged user can front-run the legitimate pool creator's `Initialize2` transaction for the same market with a minimal/attacker-chosen `init_pc_amount`/`init_coin_amount`, permanently occupying the market's canonical pool address and setting the initial price ratio, since re-initialization is rejected once the account is created.

### Finding Description
The account addresses used by `Initialize2` (AMM info, LP mint, target orders, coin vault, pc vault) are computed via `get_associated_address_and_bump_seed`, which only mixes in `program_id`, `market_account.key`, and a fixed seed suffix [1](#0-0) . The `market_info` account is explicitly documented in the code as "Just a seed for AMM account. Can be any account." [2](#0-1) , meaning it is not validated to be a genuine OpenBook/Serum market controlled by the caller.

`process_initialize2` only checks that `user_wallet_info` is a signer, that the token/system/ATA program IDs match, that the amm authority PDA and config PDA are correct, and that the create-pool-fee destination matches a fixed address [3](#0-2) . There is no check restricting which signer may create a pool for a given market — any wallet can submit `Initialize2` for any `market_info` pubkey.

The associated-account creation helper `generate_amm_associated_account`/`generate_amm_associated_spl_mint`/`generate_amm_associated_spl_token` derives the PDA from the market key and rejects the call only if the account already exists (`AmmError::RepeatCreateAmm`) [4](#0-3) . This means the *first* caller to submit `Initialize2` for a given `market_info` value permanently claims that market's canonical pool address, LP mint, and vaults.

The only floor on liquidity is the `InitLpAmountTooLess` check, requiring `liquidity > 10^lp_decimals` [5](#0-4) , which is a small, attacker-affordable amount (using their own funds) relative to what a legitimate market operator would typically seed.

### Impact Explanation
An attacker can watch the mempool/transaction stream for a legitimate `Initialize2` call (or preemptively target markets they expect will be used), and submit their own `Initialize2` with a tiny/skewed `init_pc_amount`/`init_coin_amount` ratio for the same `market_info` key first. Because the AMM pool, LP mint, target orders, and vault addresses are permanently bound to that market key and `RepeatCreateAmm` prevents any retry, the legitimate operator can never create the intended pool at the expected canonical address for that market. The attacker also controls the initial price ratio and receives the initial LP tokens, potentially setting up further griefing (e.g., extreme price skew) before real liquidity/swap activity arrives. This is a permanent, unrecoverable griefing/denial-of-service of the pool-creation flow for that market, matching the "unrestricted vestFor" pattern: an unauthenticated caller using insignificant/attacker-chosen values to permanently lock a resource meant for another party.

### Likelihood Explanation
High likelihood: `Initialize2` is fully permissionless by design (any signer, any market key), requires only a modest amount of attacker-controlled capital to satisfy the minimum-liquidity check, and pool creation transactions/market keys are typically known or predictable ahead of time (e.g., newly listed OpenBook markets), making front-running straightforward for anyone monitoring the chain.

### Recommendation
Add an authorization mechanism for pool creation tied to a specific market — e.g., require the market's designated creator/authority to co-sign, use a permissioned allowlist/registry keyed by market, or bind pool creation to proof of market ownership (such as requiring the caller to be the market's `event_queue` authority or a value stored in a config account) so that arbitrary unrelated accounts cannot pre-empt a specific market's canonical pool.

### Proof of Concept
1. Observe (or predict) a `market_info` pubkey `M` that a legitimate operator intends to use for `Initialize2`.
2. Before the legitimate operator's transaction lands, attacker submits their own `Initialize2` instruction with the same `market_info = M`, their own `user_wallet_info`, minimal `init_pc_amount`/`init_coin_amount` (just above the `InitLpAmountTooLess` floor) and a skewed price ratio, per `process_initialize2` [6](#0-5) .
3. `generate_amm_associated_account` computes the AMM/LP mint/vault PDAs from `M` and successfully creates them for the attacker since they don't yet exist [7](#0-6) .
4. When the legitimate operator's `Initialize2` transaction for `M` executes afterward, it fails with `AmmError::RepeatCreateAmm` because the same PDAs are already owned/initialized, permanently blocking creation of the intended pool at market `M`'s canonical address.

    fn generate_amm_associated_account<'a, 'b: 'a>(
        program_id: &Pubkey,
        assign_to: &Pubkey,
        market_account: &'a AccountInfo<'b>,
        associated_token_account: &'a AccountInfo<'b>,
        user_wallet_account: &'a AccountInfo<'b>,
        system_program_account: &'a AccountInfo<'b>,
        _rent_sysvar_account: &'a AccountInfo<'b>,
        associated_seed: &[u8],
        data_size: usize,
    ) -> ProgramResult {
        let (associated_token_address, bump_seed) = get_associated_address_and_bump_seed(
            &program_id,
            &market_account.key,
            associated_seed,
            program_id,
        );
        if associated_token_address != *associated_token_account.key {
            msg!("Error: Associated token address does not match seed derivation");
            return Err(AmmError::ExpectedAccount.into());
        }
        if associated_token_account.owner == system_program_account.key {
            let associated_account_signer_seeds: &[&[_]] = &[
                &program_id.to_bytes(),
                &market_account.key.to_bytes(),
                associated_seed,
                &[bump_seed],
            ];
            let rent = Rent::get()?;
            let required_lamports = rent
                .minimum_balance(data_size)
                .max(1)
                .saturating_sub(associated_token_account.lamports());
            if required_lamports > 0 {
                invoke(
                    &system_instruction::transfer(
                        user_wallet_account.key,
                        associated_token_account.key,
                        required_lamports,
                    ),
                    &[
                        user_wallet_account.clone(),
                        associated_token_account.clone(),
                        system_program_account.clone(),
                    ],
                )?;
            }
            invoke_signed(
                &system_instruction::allocate(associated_token_account.key, data_size as u64),
                &[
                    associated_token_account.clone(),
                    system_program_account.clone(),
                ],
                &[&associated_account_signer_seeds],
            )?;
            invoke_signed(
                &system_instruction::assign(associated_token_account.key, assign_to),
                &[
                    associated_token_account.clone(),
                    system_program_account.clone(),
                ],
                &[&associated_account_signer_seeds],
            )?;
        } else {
            associated_token_address.log();
            return Err(AmmError::RepeatCreateAmm.into());
        }
        Ok(())
    }
