Confirmed: the Tron `IntentGatewayV2.sol` has **zero** parameter validation anywhere — no `_validateParams`, no bounds check on `surplusShareBps`, `protocolFeeBps`, or `destinationFeeBps`, unlike the canonical EVM `IntentsBase.sol` which enforces these invariants both at `initialize` and in `_updateParams`.

### Title
Missing bounds validation on governance `UpdateParams` in Tron IntentGatewayV2 permits `destinationFeeBps`/`protocolFeeBps` ≥ 10000, bricking `placeOrder` via arithmetic revert - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The canonical EVM `IntentGatewayV2` validates every governance-supplied `Params`/`DestinationFee` update through `IntentsBase._validateParams` and an explicit `feeBps >= 10_000` check in `_updateParams` before applying it [1](#0-0) . The Tron port of the same contract implements the identical `UpdateParams` request kind in `onAccept` but applies `_params = update.params` and `_destinationProtocolFees[stateMachineId] = feeBps` directly, with no equivalent validation function or bounds check anywhere in the file [2](#0-1) .

### Finding Description
This is the same bug class as the referenced report (M-06 Validations): setter/update functions that accept percentage or basis-point parameters must validate them against their arithmetic domain (e.g., `<= BASE`) or a downstream calculation can divide/subtract into an invalid state. `placeOrder` on Tron computes `protocolFee = (originalAmount * protocolFeeBps) / 10_000` and then `reducedAmount = originalAmount - protocolFee` [3](#0-2) . If `protocolFeeBps` (sourced from `_destinationProtocolFees` or `_params.protocolFeeBps`, both settable via the unvalidated `UpdateParams` path) is set to a value ≥ 10,000 (100%), `protocolFee` exceeds `originalAmount`, and the subsequent subtraction underflows. Since the contract compiles with Solidity ≥0.8's built-in overflow checks, this reverts every `placeOrder` call routed to that destination.

The main EVM `IntentGatewayV2` closes this exact gap by rejecting any `feeBps >= 10_000` before it is written to storage [4](#0-3) ; the Tron variant has no such guard, so the same invariant that protects users on EVM chains is silently absent on Tron.

### Impact Explanation
Once an out-of-range `protocolFeeBps` or `destinationFeeBps` is written (whether by a governance misconfiguration or a bug in the off-chain params encoder — no malicious intent required, only the absence of an on-chain safety net), every subsequent `placeOrder` call from ordinary users targeting that destination chain reverts permanently. This is a route-availability/DOS finding: user funds already escrowed are unaffected, but new orders to the affected destination can never be placed until governance issues another `UpdateParams` message to correct the value — and there is no on-chain mechanism forcing that correction to be valid either, so a second bad update can re-introduce the same failure. This matches the judge's characterization in the reference report: "some of these setters can be used to DOS the protocol... this is a valid medium severity finding."

### Likelihood Explanation
Reachable purely through the normal governance→`onAccept`→`placeOrder` flow that every `UpdateParams` deployment already exercises (see the equivalent, validated flow tested in `IntentGatewayV2Test.sol`'s `testRevert_UpdateParams_DestinationFeeBpsTooHigh`, which only asserts this behavior against the main EVM contract, not Tron) [5](#0-4) . No attacker action is needed beyond a single ordinary `placeOrder` transaction to trigger the revert once a bad value is live; the missing validation is a straightforward code-review gap between the two contract ports.

### Recommendation
Port `IntentsBase._validateParams` (and the `feeBps >= 10_000` guard applied per destination-fee entry in `_updateParams`) into the Tron `IntentGatewayV2.onAccept` `UpdateParams` branch before writing to `_params` and `_destinationProtocolFees`. Additionally validate `host`/`dispatcher` are non-zero contract addresses, matching the EVM implementation, to prevent bricking `host()`-dependent calls.

### Proof of Concept
1. Governance dispatches an `UpdateParams` `PostRequest` to the Tron `IntentGatewayV2` with `destinationFees = [{ chain: "ARBITRUM", destinationFeeBps: 10_000 }]` (or any value ≥ 10,000).
2. `onAccept` decodes and stores it unconditionally: `_destinationProtocolFees[stateMachineId] = feeBps;` [6](#0-5) .
3. A user calls `placeOrder` with `order.destination = "ARBITRUM"`; `protocolFeeBps` resolves to 10,000, so `protocolFee == originalAmount`, and `reducedAmount = originalAmount - protocolFee` (line 364) evaluates to exactly 0 for `feeBps == 10_000`; for any `feeBps > 10_000`, `protocolFee > originalAmount` and the subtraction underflows and reverts under Solidity's checked arithmetic. Either way, every order to that destination is either drained to zero fee-taken or permanently reverted, depending on the exact value — both outcomes are unintended and unrecoverable without a corrective governance message.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }

    /**
     * @dev Updates the gateway's configuration parameters and per-destination protocol fees.
     * Called by Hyperbridge governance to modify fee settings, host address, dispatcher,
     * price oracle, and other operational parameters.
     *
     * Validates all params before applying. Emits ParamsUpdated with the old and new params,
     * then iterates over any destination-specific fee overrides and applies them to
     * `_destinationProtocolFees`.
     *
     * @param update The parameter update containing new params and destination fee overrides.
     */
    function _updateParams(ParamsUpdate memory update) internal {
        _validateParams(update.params);

        emit ParamsUpdated({previous: _params, current: update.params});
        _params = update.params;

        for (uint256 i; i < update.destinationFees.length;) {
            bytes memory chain = update.destinationFees[i].chain;
            uint256 feeBps = update.destinationFees[i].destinationFeeBps;
            if (feeBps >= 10_000) revert InvalidInput();
            _destinationProtocolFees[keccak256(chain)] = feeBps;

            unchecked {
                ++i;
            }
            emit DestinationProtocolFeeUpdated(string(chain), feeBps);
        }
    }
