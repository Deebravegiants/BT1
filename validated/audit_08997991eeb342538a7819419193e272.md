## Analog Found

### Title
Unvalidated `beneficiary_address` in relayer fee redirect permanently locks accumulated fees - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`pallet_ismp_relayer::Pallet::accumulate` (dispatched via the unsigned, permissionless `accumulate_fees` extrinsic) lets a relayer redirect their proven delivery fee to an arbitrary `beneficiary_address: Vec<u8>` by supplying a signature over that address. Unlike every other beneficiary-address code path in the same module family, `accumulate` never validates that this address is a well-formed, signature-derivable address for the relevant destination chain before crediting `Fees::<T>`, so an address that can never be recovered from a real signature permanently strands the fee — the same root cause as the referenced DODORouteProxy finding ("fee sent to an unvalidated address is never regained").

### Finding Description
In `accumulate`, the redirect path takes an attacker/relayer supplied `beneficiary_address` and, after verifying only that the *signature* over it was produced by the legitimate `delivery_address`, credits `Fees::<T>` directly under that raw byte string with no format/length validation: [1](#0-0) 

Contrast this with the two other places in the codebase that handle the same conceptual value (a beneficiary address to later be paid out) — both of which explicitly validate the byte length before it can be persisted/dispatched:
- `withdraw()` in `withdrawal.rs`, which enforces `AccountId32::try_from(&beneficiary_address[..])` for substrate destinations and rejects malformed input via `WithdrawalParams::abi_encode()`: [2](#0-1) 
- The EVM `WithdrawalParams::abi_encode()` helper, which explicitly rejects any `beneficiary_address` that isn't exactly 20 bytes: [3](#0-2) 

`accumulate` has no equivalent check. `Fees::<T>` is a `(StateMachine, Vec<u8>) -> U256` map keyed on the raw bytes supplied at credit time: [4](#0-3) 

To later withdraw, `withdraw()` derives `address` strictly from signature verification — 20 bytes for `Signature::Evm`, or the raw public key bytes for `Signature::Sr25519`/`Signature::Ed25519` — and looks up `Fees::<T>::get(dest_chain, address)`: [5](#0-4) 

If the `beneficiary_address` credited during `accumulate` is not exactly the canonical length/format that a real signature can ever produce (e.g., wrong byte length for an EVM address, or 32 bytes that don't correspond to any private key the caller actually controls), no future call to `withdraw()` can ever produce a matching `address`, and the `Fees::<T>` entry becomes permanently unclaimable.

### Impact Explanation
The accumulated relayer fee (funds already proven-delivered and credited on-chain) becomes permanently locked/lost — no path exists to recover it once `Fees::<T>` is credited to a malformed key, since `withdraw()` can only ever be reached by producing a matching signature-derived address. This is a direct, permanent loss of funds, matching the Medium severity of the referenced report.

### Likelihood Explanation
`accumulate_fees` is an unsigned, permissionless extrinsic — "anyone can submit a WithdrawalProof" per the module's own test comments — and the redirect (`beneficiary_details`) branch is reachable by any relayer simply by signing over whatever bytes they choose as `beneficiary_address`. No cross-validation against the destination `StateMachine`'s expected address format is performed, so a single malformed submission (accidental mis-encoding, wrong length, or copy of a public key without holding the private key) is sufficient to trigger permanent fund loss, with no signature or length safety net analogous to `withdraw()`'s.

### Recommendation
In `accumulate` (`modules/pallets/relayer/src/accumulate.rs`), validate `beneficiary_address` before crediting `Fees::<T>`:
- For EVM destination state machines, require `beneficiary_address.len() == 20`.
- For substrate destination state machines, require `beneficiary_address.len() == 32` (mirroring `AccountId32::try_from`).
- Reject the extrinsic (or fall back to crediting `delivery_address` instead) if the format check fails, matching the safeguards already present in `withdraw()` and `WithdrawalParams::abi_encode()`.

### Proof of Concept
1. A relayer legitimately delivers a message and is entitled to a fee under `delivery_address`.
2. They call `accumulate_fees` with `beneficiary_details = Some((beneficiary_address, signature))` where `signature` correctly proves ownership of `delivery_address`, but `beneficiary_address` is a malformed value — e.g. 32 raw bytes submitted for an EVM destination chain, or a 32-byte value for which the caller does not actually hold the corresponding sr25519/ed25519 private key.
3. `accumulate` performs no length/format check and credits `Fees::<StateMachine, beneficiary_address> += total_fee` per `accumulate.rs:134-137`.
4. No subsequent call to `withdraw()` can ever produce a `Signature`-derived `address` equal to this malformed `beneficiary_address` (EVM ecrecover always yields 20 bytes; substrate signature verification requires the actual private key), so `Fees::<T>::get(dest_chain, beneficiary_address)` remains forever unreachable — the fee is permanently stranded.
