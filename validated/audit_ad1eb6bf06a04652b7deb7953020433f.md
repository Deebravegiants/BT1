I found a concrete, self-contained analog. The external bug's core custody invariant is: *a caller-supplied guard/limit value is computed but the code never actually uses it to enforce/select the correct execution branch, so the intended cap is bypassed*. Searching Aptos-native fungible-asset/DEX flows for the same pattern (a computed bound checked against the wrong variable, or an if-condition that never actually reflects the check it claims to perform) turned up exactly this defect in the example swap router's liquidity-amount calculation.

### Title
`router::optimal_liquidity_amounts` compares the wrong variable, so the upper-bound token cap is never enforced, letting the router withdraw more of a user's token than `amount_2_desired` allows - ([File: aptos-move/move-examples/swap/sources/router.move])

### Summary
`optimal_liquidity_amounts` is supposed to mirror Uniswap-V2-style logic: compute `amount_2_optimal` from `amount_1_desired`, and only use it if it does not exceed the user-specified `amount_2_desired`; otherwise fall back to shrinking `amount_1`. The branch condition instead checks the pre-existing local variable `amount_2` (still equal to `amount_2_desired`) against itself, which is always true, so the shrink-`amount_1` fallback branch is dead code and the upper bound on `amount_2` is never enforced.

### Finding Description [1](#0-0) 

```move

    math128::sqrt(amount_1 * amount_2) - (liquidity_pool::min_liquidity() as u128)
} else if (reserves_1 > 0 && reserves_2 > 0) {

        assert!(amount_2_optimal >= amount_2_min, EINSUFFICIENT_OUTPUT_AMOUNT);

    } else {

        assert!(amount_1 <= amount_1_desired && amount_1 >= amount_1_min, EINSUFFICIENT_OUTPUT_AMOUNT);
    };

```

At line 194, `amount_2` is initialized to `amount_2_desired` and is never mutated before the `if` on line 199. The condition therefore always reduces to `amount_2_desired <= amount_2_desired`, which is trivially `true`. The correct check (per the intended Uniswap-style algorithm, and matching the comparable check on line 204 for the other branch) should be `amount_2_optimal <= amount_2_desired`. Because the wrong variable is compared, the `else` branch (which recomputes and caps `amount_1`, and would assert `amount_1 <= amount_1_desired`) is unreachable, and the code unconditionally sets `amount_2 = amount_2_optimal`, only asserting a *lower* bound (`amount_2_optimal >= amount_2_min`) and never an *upper* bound against `amount_2_desired`.

This value flows directly into an unprivileged custody-affecting withdraw: [2](#0-1) 

```move
let (optimal_amount_1, optimal_amount_2, _) = optimal_liquidity_amounts(
    token_1, token_2, is_stable,
    amount_1_desired, amount_2_desired, amount_1_min, amount_2_min,
);
let optimal_1 = primary_fungible_store::withdraw(lp, token_1, optimal_amount_1);
let optimal_2 = primary_fungible_store::withdraw(lp, token_2, optimal_amount_2);
```

The same computed, uncapped `optimal_amount_2`/`optimal_amount_1` values are also used by `add_liquidity_coin_entry` and `liquidity_pairs.move`'s equivalent flow, so the bug is not isolated to one call site.

### Impact Explanation
`amount_2_desired` is the caller's explicit ceiling on how much of `token_2` they are willing to deposit. Because the comparison never actually evaluates the true cap, when the pool ratio implies `amount_2_optimal > amount_2_desired`, the router still withdraws `amount_2_optimal` (bounded only by `amount_2_min`, a floor) from the caller's primary fungible store via `primary_fungible_store::withdraw`. This directly custodies/moves more of the user's fungible asset balance than the user authorized/expected for the operation, which is a value-extraction/custody-accounting defect: the withdrawn amount can silently exceed the user-specified maximum, draining more funds than intended in a single add-liquidity call — the exact same class of defect as the reported "slippage checked but never applied" bug, just manifesting as a max-input cap instead of a min-output cap.

### Likelihood Explanation
This triggers deterministically whenever the pool's price ratio has drifted (e.g., due to any prior swap or normal price movement) such that `amount_2_optimal` computed from `amount_1_desired` exceeds `amount_2_desired`. No attacker action beyond normal usage is required — any legitimate `add_liquidity_entry`/`add_liquidity_coin_entry` caller can be affected purely by pool-state drift between the time they choose `amount_2_desired` and when the transaction executes.

### Recommendation
Fix the branch condition to compare the actually computed value, not the untouched initializer:
```move
let amount_2_optimal = math128::mul_div(amount_1_desired, reserves_2, reserves_1);
if (amount_2_optimal <= amount_2_desired) {
    assert!(amount_2_optimal >= amount_2_min, EINSUFFICIENT_OUTPUT_AMOUNT);
    amount_2 = amount_2_optimal;
} else {
    amount_1 = math128::mul_div(amount_2_desired, reserves_1, reserves_2);
    assert!(amount_1 <= amount_1_desired && amount_1 >= amount_1_min, EINSUFFICIENT_OUTPUT_AMOUNT);
};
```
This restores the intended dual-sided cap (both `amount_1 <= amount_1_desired` and `amount_2 <= amount_2_desired` are properly enforced depending on which branch executes).

### Proof of Concept
1. Create a pool for `token_1`/`token_2` with reserves such that `reserves_2/reserves_1` ratio is, e.g., `10`.
2. User A calls `add_liquidity_entry` with `amount_1_desired = 100`, `amount_2_desired = 50` (expecting to deposit at most 50 of `token_2`), `amount_2_min = 1`.
3. Inside `optimal_liquidity_amounts`: `amount_2_optimal = mul_div(100, reserves_2, reserves_1) = 1000` (far exceeding `amount_2_desired = 50`).
4. The condition `if (amount_2 <= amount_2_desired)` evaluates `50 <= 50` → `true` (always true regardless of `amount_2_optimal`), so the code sets `amount_2 = amount_2_optimal = 1000` and only checks `1000 >= amount_2_min(1)`, which passes.
5. `add_liquidity_entry` then calls `primary_fungible_store::withdraw(lp, token_2, 1000)`, withdrawing 20x more of `token_2` from the user's store than the user's specified `amount_2_desired = 50`, with no code-level cap preventing it. [3](#0-2)
