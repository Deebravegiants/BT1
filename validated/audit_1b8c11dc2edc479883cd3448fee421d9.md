### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/validates the HMAC over the raw request body only, but the `shop` identifier that the host application uses to attribute the webhook to a tenant is read from an unrelated, unsigned header. Any party that can obtain one validly-signed webhook payload (e.g. by installing the app on their own store) can replay that exact body+HMAC while swapping the `shop-domain` header to a victim shop, and `Registry.process` will accept it as authentic.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `hmac` accessor and the `shop` accessor are both derived from headers, but only `hmac` participates in the signed content; `shop` never does: [2](#0-1) 

`Registry.process` validates the HMAC of the body via `Utils::HmacValidator.validate(request)`, then immediately trusts `request.shop` to build the `WebhookMetadata` passed to the handler, with no independent check that this shop is the one that actually produced the signed body: [3](#0-2) 

`Utils::HmacValidator.validate_signature` confirms the signature is computed only over `verifiable_query.to_signable_string` (the body, for webhooks) using the single, app-wide `Context.api_secret_key` — the same secret is used to sign webhooks for every shop that installs the app, it is not shop-specific: [4](#0-3) 

The broken identity binding, expressed as an equality that should hold but doesn't:
`shop_header_used_by_handler == shop_that_actually_generated_this_signed_body`

Only `hmac(body) == valid_signature` is enforced; `shop` is orthogonal to that check. This is the same bug class as the OrderBook report — a value that downstream code treats as authoritative (there: which orders have already been claimed; here: which tenant a webhook belongs to) is not covered by the check that is supposed to establish trust (there: proper skip logic before `_claim`; here: the HMAC over the payload).

### Impact Explanation
Because the app secret is shared across all shops that install the app (not per-shop), any unprivileged user who can install the app on their own store — a normal, unprivileged action — can generate a legitimately-signed webhook body/HMAC pair for their own shop. They can then send that exact body and HMAC to the app's webhook endpoint while setting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header to a victim shop's domain. `Utils::HmacValidator.validate` will pass (the body's HMAC is still valid against the app secret), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload belongs to the victim shop. Host applications (as documented in this gem's own usage docs) key their tenant data off `WebhookMetadata#shop`, so this results in data being attributed to, or acted upon for, the wrong tenant — a cross-tenant access/injection vulnerability.

### Likelihood Explanation
Likelihood is meaningful: exploitation requires no leaked credentials or `api_secret_key` knowledge — only the ability to install the app on an attacker-controlled store (the normal onboarding flow for any public app) to harvest one valid signed webhook, plus a way to POST directly to the app's public webhook endpoint with custom headers (trivial for any internet client, since the webhook receiver is by definition internet-facing).

### Recommendation
Bind the `shop` value to the signed content, e.g. include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable string, or have `Registry.process` cross-check `request.shop` against a shop that the host app has already established a relationship/session with before dispatching to the handler, rather than trusting the header verbatim once the body's HMAC checks out.

### Proof of Concept
1. Install the target app on an attacker-controlled development shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw request: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's shared secret).
2. Send a new HTTP request to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H`, and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)`, causing the host app to process attacker-supplied data as if it originated from the victim shop.
