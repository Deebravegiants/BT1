### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) headers are trusted for tenant routing without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, but then dispatches the request to the app's handler using `shop`, `topic`, and `webhook_id` values that are read from HTTP headers which are **not** included in the signed content. Any actor who can obtain one legitimately-signed webhook body/HMAC pair (e.g., by installing the app on their own store and receiving a real webhook) can replay that exact body+signature to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to claim it originated from a different merchant, breaking the binding between "bytes verified" (the body) and "identity acted on" (the shop header).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from unauthenticated HTTP headers: [2](#0-1) 

`Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it to the `hmac-sha256` header: [3](#0-2) 

`Registry.process` checks only this body HMAC and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived, unauthenticated) to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

Because the shop identity is never bound into the signed payload, the equality the app relies on — "bytes verified == identity acted on" — does not hold: an attacker can present a byte-identical, validly-signed body while changing only the `shop-domain` header. Apps are documented and expected to use `WebhookMetadata#shop` to route/persist per-tenant data (this is the standard multi-tenant webhook pattern promoted in Shopify app documentation), so this header spoofing directly enables cross-tenant webhook injection.

### Impact Explanation
This is a cross-tenant access vulnerability (Critical per the rubric): an unprivileged actor who operates any shop with the app installed can capture one authentic webhook (body + valid HMAC), then replay it against the app's public webhook endpoint with a forged `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header pointing at a victim shop. Any app logic that keys off `WebhookMetadata#shop` (session lookup, per-tenant data writes, GDPR/redact processing, etc.) will process the attacker's captured payload as if it belongs to the victim tenant, since the gem's own verification never binds the shop header to the signed bytes.

### Likelihood Explanation
Likelihood is high for any internet-reachable webhook endpoint: no secret, token, or elevated privilege is required — only possession of one legitimately-signed webhook (trivially obtainable by installing the app on an attacker-controlled/free development store, which virtually every Shopify app allows) and the ability to send an arbitrary HTTP request with custom headers to the app's public webhook callback URL.

### Recommendation
Bind the shop (and topic/webhook id) into the HMAC-verified content, or otherwise independently authenticate the shop associated with a webhook before trusting it: e.g., include the `shop-domain` header in the signable string, or cross-check the delivered `shop` against a shop known to be associated with the specific `webhook_id`/subscription (looked up via a trusted, previously-recorded mapping) before invoking the handler, rather than trusting the raw header value unconditionally.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a real webhook delivery, e.g. body `{"id":123}` with header `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the exact same body and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and adjust `X-Shopify-Topic`/`X-Shopify-Webhook-Id` if desired).
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers (only checks presence, not shop-header authenticity) and `HmacValidator.validate` succeeds because it only hashes the unmodified raw body: [5](#0-4) 
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, so the app processes attacker-supplied data as belonging to `victim.myshopify.com`.
