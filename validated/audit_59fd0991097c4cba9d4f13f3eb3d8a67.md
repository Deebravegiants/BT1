### Title
Webhook Shop Domain Not Bound to HMAC Signature Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate(request)` succeeds, then hands `request.shop` straight to the app's handler as the verified tenant identity. However the HMAC signature only covers the raw request body — the `shop` (and `topic`/`webhook_id`) values are read from unauthenticated HTTP headers that play no part in the signature computation. This breaks the binding `shop_authenticated == shop_delivered_to_handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from HTTP headers that are never fed into the signature: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, and then immediately trusts `request.shop` to build the `WebhookMetadata` object passed to the app's handler, with no further check that the shop matches the body's actual origin: [3](#0-2) 

`HmacValidator.validate` confirms only that `to_signable_string` (the raw body) was signed by the app's `api_secret_key` — it says nothing about which shop that body belongs to: [4](#0-3) 

Because the shared `api_secret_key` HMAC is per-app (not per-shop), any shop that has installed the app can obtain a genuinely-signed webhook payload for its own store, then resend that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with another tenant's domain. The signature still validates (it only covers the body), yet `Registry.process` reports the spoofed shop to the handler as authenticated: `data.shop` in `WebhookMetadata` is derived purely from the header, not from anything cryptographically tied to that shop.

### Impact Explanation
This lets one tenant (any merchant who installed the app — an unprivileged actor relative to other merchants) forge the appearance that a webhook payload originated from a different shop. Any host application that relies on `ShopifyAPI::Webhooks::Registry.process`'s HMAC validation as proof that `data.shop` is trustworthy (a reasonable assumption, since the library explicitly performs an "Invalid webhook HMAC" check before handing off the metadata) will attribute attacker-controlled webhook data to a victim shop. Depending on how the host app uses `data.shop` (e.g., looking up the victim's stored access token/session, writing data under the victim's tenant record, triggering per-shop business logic), this is a cross-tenant data/identity confusion vulnerability — matching the "Critical: cross-tenant access" impact category.

### Likelihood Explanation
Any shop that has installed the target app can trivially capture one legitimate signed webhook for itself (webhooks are sent automatically once subscribed) and replay it with a modified shop-domain header using an ordinary HTTP client — no access to `api_secret_key`, access tokens, or privileged accounts is required beyond normal app installation, which is the standard "unprivileged internet user" position for this gem's threat model.

### Recommendation
Bind the shop identity into the authenticated bytes. Either include the `X-Shopify-Shop-Domain` (and topic/webhook id) header values as part of `to_signable_string` so they are covered by the HMAC, or independently corroborate `request.shop` against a known/expected shop before trusting it in `WebhookMetadata` (e.g., cross-check against the shop that registered for that specific `webhook_id`/subscription).

### Proof of Concept
1. Merchant A installs the app and lets Shopify deliver a legitimate webhook, e.g. `orders/create`, to the app's callback URL. Capture the raw body and the `X-Shopify-Hmac-Sha256` header — the signature is valid because it's computed over the body with the shared `api_secret_key`.
2. Replay the exact same request to the app's webhook endpoint, keeping body and HMAC header unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` (`lib/shopify_api/utils/hmac_validator.rb:13`), which succeeds because it only checks the raw body.
4. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` (`lib/shopify_api/webhooks/registry.rb:198`) using the attacker-controlled header value `victim-shop.myshopify.com`.
5. The host app's `WebhookHandler#handle` receives `data.shop == "victim-shop.myshopify.com"` with attacker-controlled body content, believing it passed the library's authenticity check.
