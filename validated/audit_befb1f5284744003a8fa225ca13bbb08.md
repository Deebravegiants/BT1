Audit Report

## Title
Unprivileged auction win against a para with a pending `AssignedSlots` temporary slot causes `allocate_temporary_slot_leases` to abort its entire batch via early-return `?`, denying other paras their scheduled temp-slot turn - (File: `polkadot/runtime/common/src/assigned_slots/mod.rs`)

## Summary
`AssignedSlots::assign_temp_parachain_slot` only checks `already_leased` for a bounded window of current + 2 lease periods, leaving future recurring temp-slot periods unguarded against conflicting `slots` auction wins. If an unprivileged account wins an `Auctions`/`Crowdloan` lease overlapping such a future period, `allocate_temporary_slot_leases`'s `for` loop propagates the resulting `LeaseError::AlreadyLeased` via `?` immediately, aborting processing of every other pending para queued later in that batch for the same lease-period boundary.

## Finding Description
`assign_temp_parachain_slot` guards only `current_lease_period` through `current_lease_period + 2*TemporarySlotLeasePeriodLength` [1](#0-0) , leaving later recurring turns (`last_lease + 2*period_count`) unchecked at assignment time. `Auctions::handle_bid` independently only rejects bids overlapping an *existing* `slots::Leases` entry [2](#0-1) , and requires only `ensure_signed` [3](#0-2) , so nothing stops a signed account from winning an auction for a future period that `AssignedSlots` intends to occupy later, since no `Leases` entry exists yet for that lazily-allocated future period.

When that period arrives, `allocate_temporary_slot_leases` iterates the sorted `slots_to_be_upgraded` and, for each para, calls `TemporarySlots::try_mutate(...)` which internally calls `configure_slot_lease` → `T::Leaser::lease_out`; on failure this returns `Err(Error::<T>::CannotUpgrade)` from the closure, and the `?` immediately after `try_mutate(...)?` propagates that error out of `allocate_temporary_slot_leases` as a whole [4](#0-3) . This confirms the claimed root cause: the `for` loop has no per-iteration error isolation, so one para's conflict aborts the entire batch, skipping all subsequently-iterated pending paras and the final `ActiveTemporarySlotCount::<T>::set(...)` update at line 564.

## Impact Explanation
This is a genuine denial-of-service/batch-isolation bug: a single unprivileged auction win against one para can prevent other, unrelated paras from receiving their scheduled temp-slot lease for that lease-period boundary, and can leave `ActiveTemporarySlotCount` stale for that period. The affected para's own `TemporarySlots` entry is unchanged (not corrupted) because `try_mutate` discards mutations on `Err`, so it remains eligible as "pending" and will be retried in subsequent lease periods. The impact is a legitimate correctness/availability issue within `pallet-assigned-slots`, though it is bounded to delaying/denying temp-slot allocation rather than causing fund loss or privilege escalation.

## Likelihood Explanation
The attack is realistically executable: `Auctions::bid` requires only a signed origin and reservable funds, with no special permission tied to the target para's manager status [3](#0-2) . `TemporarySlots` and `TemporarySlotLeasePeriodLength`/`period_begin` values are public on-chain storage, so an attacker can compute the exact future lease-period range to target. The attacker must actually win the auction (via `Crowdloan` or direct funds), which carries a real cost (reserved deposit), making it feasible but not free, and repeatable each time the targeted para re-enters "pending" status.

## Recommendation
In `allocate_temporary_slot_leases`, do not propagate a single para's `configure_slot_lease` failure with `?` out of the whole function. Handle the `try_mutate` result per-iteration (e.g., log a warning and `continue` on error) so failures for one para do not block processing of the remaining `slots_to_be_upgraded` entries, and compute `ActiveTemporarySlotCount` based on leases actually created rather than assuming success. Additionally, consider widening the `already_leased` check in `assign_temp_parachain_slot` to cover the full recurring window, or rejecting `Auctions`/`Crowdloan` bids against paras holding an active `AssignedSlots::TemporarySlots` entry.

## Proof of Concept
1. Register two parathreads `para_a` and `para_b`; call `assign_temp_parachain_slot(Root, para_a, SlotLeasePeriodStart::Next)` and the same for `para_b`, giving both `TemporarySlots` entries with `last_lease: None`.
2. Before the next lease-period boundary, have a signed account win an `Auctions`/`Crowdloan` lease for `para_a` exactly covering `para_a`'s scheduled `period_begin..period_begin+period_count-1` range, populating `slots::Leases` for `para_a` for that range.
3. Advance to the lease-period boundary, triggering `on_initialize` → `manage_lease_period_start` → `allocate_temporary_slot_leases`.
4. Assert `TemporarySlots::<Test>::get(para_a).last_lease` is unchanged (still `None`), and critically that `TemporarySlots::<Test>::get(para_b).last_lease` is also still `None` despite no conflict for `para_b`, demonstrating the batch-abort effect; also check `ActiveTemporarySlotCount::<T>::get()` was not updated for the period.
