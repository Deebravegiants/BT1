## Finding

### Title
`WrappedHyperFungibleToken.send()` does not account for fee-on-transfer tokens, causing locked balance to diverge from the amount promised in cross-chain messages, leading to insolvency/frozen unlocks - (File: `sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol`)

### Summary
`WrappedHyperFungibleToken.send()` (and its upgradeable twin `WrappedHyperFungibleTokenUpgradeable.send()`) locks the underlying ERC20 via `safeTransferFrom` and then dispatches a cross-chain `Message` that encodes `params.amount` as the locked/backing amount. If the underlying token charges a transfer fee (deflationary/fee-on-transfer token), the wrapper actually receives less than `params.amount`, but the message still commits to the full requested amount, exactly mirroring the `Allo.sol` `_fundPool`/`increasePoolAmount` bug where `amountAfterFee` accounting diverges from actual token balance.

### Finding Description
In `send()`:
```solidity

        ...
    } else {
        IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
    }

    DispatchPost memory request = _buildDispatchPost(params);
    ...

``` [1](#0-0) 

`_buildDispatchPost` encodes the message body using `params.amount` verbatim, not the actual amount received by the contract: [2](#0-1) 

There is no before/after balance check to capture the actual amount received, unlike `IntentGatewayV2.sol`, which explicitly snapshots `balanceOf` before and after `safeTransferFrom` and mutates `order.inputs[i].amount` to the real received amount to keep escrow accounting consistent with actual holdings: [3](#0-2) 

Because `WrappedHyperFungibleToken` lacks this correction, if `_underlying` is a fee-on-transfer token, the contract's actual token balance backing all outstanding `send()` calls falls behind the sum of `amount`s promised in dispatched messages. On the destination side, `onAccept` mints/unlocks the full `message.amount` and on the home chain, unlock via `onAccept`/timeout refund also transfers the full `message.amount`: [4](#0-3) [5](#0-4) 

The same pattern exists in the upgradeable variant: [6](#0-5) 

### Impact Explanation
As fee-on-transfer volume accumulates through `send()`, the wrapper's real token balance progressively falls short of the total amount it has "promised" to unlock/mint elsewhere. Since minted/unlocked HFT supply on remote chains is meant to be fully backed by tokens locked here, this creates unbacked liabilities: later `onAccept` unlock calls (for messages routed back to the home chain) or timeout refunds can revert due to insufficient balance, permanently freezing funds for some users — directly analogous to the reported `Allo.sol` issue where `poolAmount` no longer matches actual holdings and later distributions revert.

### Likelihood Explanation
This is reachable by any unprivileged user simply calling `send()` with a wrapped fee-on-transfer ERC20 configured as `_underlying`. No special privileges are required, and the issue triggers deterministically whenever the underlying token charges a transfer fee — a token type explicitly acknowledged and handled elsewhere in the codebase (`IntentGatewayV2.sol`), showing the bug class is real and reachable for tokens deployed as `_underlying` in `WrappedHyperFungibleToken`/`WrappedHyperFungibleTokenUpgradeable`.

### Recommendation
In `send()`, snapshot `IERC20(_underlying).balanceOf(address(this))` before and after `safeTransferFrom`, and use the actual delta as the `amount` encoded into the dispatched `Message`, mirroring the fix pattern already used in `IntentGatewayV2.sol`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken`, configure `_underlying` as a 1% fee-on-transfer ERC20.
2. Call `send({amount: 1000, ...})`. `safeTransferFrom(msg.sender, address(this), 1000)` results in the wrapper receiving only 990 tokens, but the dispatched `Message.amount` is `1000`.
3. On the destination chain, the peer `HyperFungibleToken` mints `1000` tokens to the recipient — fully backed liability is only `990`.
4. If the recipient later bridges back (burn 1000, dispatch unlock for 1000) or an original sender's message times out, `onAccept`/`onPostRequestTimeout` calls `IERC20(_underlying).safeTransfer(beneficiary/refundee, 1000)`, but the wrapper only actually holds `990` (plus whatever other `send()` calls contributed, all similarly short), eventually causing reverts once cumulative shortfall exceeds available balance — freezing the corresponding user funds.

        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
