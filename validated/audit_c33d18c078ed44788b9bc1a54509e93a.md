Found: `TokenExchange.exchange_token` (`lib/shopify_api/auth/token_exchange.rb:29-51`) takes the `dest` claim straight out of the JWT and uses it, unvalidated by `Utils::ShopValidator`, as the host to which the app's `client_id`/`client_secret` are sent — unlike the sibling flows `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, which both call `Utils::ShopValidator.sanitize!(shop)` before building the request host.

### Title
Unsanitized JWT `dest` claim used as OAuth token-exchange request host, unlike sibling credential flows - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`TokenExchange.exchange_token` extracts `dest_shop` from the caller-supplied session token (`JwtPayload#shop`, which is just `dest.gsub("https://", "")`) and uses it directly as the `Session#shop`, which becomes the request host for the `POST /admin/oauth/access_token` call that carries `client_id` and `client_secret` in the body [1](#0-0) . Every other credential-issuing flow in the gem — `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` — passes the shop through `Utils::ShopValidator.sanitize!` before it is used to build the same kind of request, restricting the destination host to Shopify's trusted domain list [2](#0-1) [3](#0-2) [4](#0-3) . `token_exchange.rb` has no equivalent call.

### Finding Description
The binding that should hold is: `host that receives client_secret == a Shopify-trusted domain`. In `client_credentials.rb`/`refresh_token.rb` this equality is enforced via `Utils::ShopValidator.sanitize!(shop)`, which raises `Errors::InvalidShopError` unless the host resolves to one of `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) [5](#0-4) . In `token_exchange.rb` the shop instead comes straight from `JwtPayload#shop`/`dest`, which is taken verbatim from the JWT payload with no domain allow-list check — only the `aud` (api_key) claim is checked [6](#0-5) . Because the JWT is signed by this app's own `api_secret_key`, `dest` cannot be forged by a network attacker, but this app never asserts that `dest` is actually a `*.myshopify.com`/trusted host, unlike its sibling flows. This creates an inconsistent trust boundary within the same gem: two of three OAuth credential paths enforce host allow-listing on the exact value used to construct the request destination, one does not.

### Impact Explanation
If `dest` is not confined to Shopify's own domains, `client_id`/`client_secret` could be sent to a non-Shopify host in the same request that is trusted to hold live merchant credentials, which matches the Critical impact category "theft or exfiltration of ... the app's client_secret" (per rules, if reachable with data influenceable by dest that bypasses the allow-list other flows enforce).

### Likelihood Explanation
Low-to-uncertain: exploitation would require a way to get `dest` set to a non-Shopify value inside a JWT that still verifies against this app's `api_secret_key`. Since the JWT signature check binds `aud` but not `iss`/`dest` to a trusted-domain allow-list, and no HMAC/scope check in this gem constrains `dest` beyond the signature itself, this is theoretically reachable through any caller-supplied `session_token`, but I could not fully verify within this file set whether Shopify or the host app is expected to further constrain `dest` before this gem is invoked (the `iss` claim's `/admin` suffix check exists in `admin_session_token?`, but it's used only for `shopify_user_id`, not for validating `dest`) [7](#0-6) .

### Recommendation
Apply `Utils::ShopValidator.sanitize!(dest_shop)` to the shop derived from the JWT `dest` claim in `token_exchange.rb`, matching the pattern already used in `client_credentials.rb` and `refresh_token.rb`, before it is used to build the `Session` and the `/admin/oauth/access_token` request host.

### Proof of Concept
1. Obtain/construct a session token whose `dest` claim is not a Shopify-trusted domain (e.g. `https://attacker.example`), signed such that it passes `JWT.decode` with the configured `api_secret_key` (this step is the unresolved precondition noted above).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe `dest_shop` = `"attacker.example"` is used unsanitized to build `shop_session` and consequently the request host `https://attacker.example/admin/oauth/access_token`, to which `client_id`/`client_secret` are sent in the body [8](#0-7) , whereas the equivalent call in `client_credentials.rb`/`refresh_token.rb` would raise `Errors::InvalidShopError` for the same input.

        [
          "shopify.com",
          "myshopify.io",

          "shop.dev",

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end

        sig do
          params(
            shop: String,
            myshopify_domain: T.nilable(String),
          ).returns(String)
        end
        def sanitize!(shop, myshopify_domain: nil)
          host = sanitize_shop_domain(shop, myshopify_domain: myshopify_domain)
          if host.nil? || host.empty?
            raise Errors::InvalidShopError,
              "shop must be a trusted Shopify domain (see ShopValidator::TRUSTED_SHOPIFY_DOMAINS), got: #{shop.inspect}"
          end

          host
        end
