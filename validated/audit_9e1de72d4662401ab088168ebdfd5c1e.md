### Title
XRPL `depositAuth` check in `validateWithdrawal` is not re-verified in `createWithdrawalIntents`, allowing a signed withdrawal to be produced for a destination that will reject the deposit — ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.validateWithdrawal` fetches the XRPL destination account's `depositAuth` flag and throws `XrplDepositAuthEnabledError` if it is enabled, but this check only runs inside `validateWithdrawal` [1](#0-0) . `PoaBridge.createWithdrawalIntents`, the method that actually builds the signable intent, performs no XRPL account-flag lookup at all and unconditionally constructs the withdrawal intent from the caller-supplied `destinationAddress` [2](#0-1) . Because these are two independent public methods with no shared state or freshness guarantee, an XRPL account owner (a counterparty relative to the SDK caller) can flip `depositAuth` on after `validateWithdrawal` passes and before `createWithdrawalIntents` is called/signed.

### Finding Description
The equality that should hold is: *"the XRPL account's `depositAuth` state checked by `validateWithdrawal` == the XRPL account's `depositAuth` state at the moment the withdrawal intent produced by `createWithdrawalIntents` is executed on-chain."* 

Tracing the code:
- `validateWithdrawal` calls `xrpl.httpClient.getAccountInfo(args.destinationAddress, xrplConfig)` and throws `XrplDepositAuthEnabledError` only if `accountInfo.account_flags.depositAuth` is true at that instant [3](#0-2) .
- `createWithdrawalIntents` takes `args.withdrawalParams` (including `destinationAddress`) and `args.feeEstimation`, computes `relayerFee`, and directly builds `createWithdrawIntentPrimitive({...args.withdrawalParams, amount, destinationMemo})` — it never calls `validateWithdrawal` or performs any XRPL RPC lookup [2](#0-1) .
- There is no shared token, timestamp, or cached "last validated" state passed between `validateWithdrawal` and `createWithdrawalIntents`; they are independent public methods on `PoaBridge`, so nothing in the class prevents calling `createWithdrawalIntents` for a `destinationAddress` that was never validated, or whose validated state is now stale.

Root cause: the destination chain's acceptance state (`depositAuth`) is checked once, out-of-band from intent construction/signing, with no re-check, no expiry, and no binding between the validation result and the intent that gets signed. Existing guards (`validateAddress`, `compareAddresses`, `MinWithdrawalAmountError`, `assert` on `relayerFee`) address different invariants (address format, token/destination collision, minimum amount, fee sign) and do nothing to bind the depositAuth check to the signed intent.

### Impact Explanation
A signed `ft_withdraw` intent is produced and can be submitted for an XRPL destination that, at submission time, has `depositAuth` enabled. The XRPL ledger will reject the incoming payment. Since the NEAR-side intent has already executed (tokens moved into the withdrawal/intents pool on the NEAR side) while the XRPL leg fails, the funds are stranded and require manual intervention to redirect — this matches the "High: a withdrawal stuck until manual intervention" impact category. The affected party is whoever initiated/is credited for the withdrawal (the SDK caller/integrator's end user), and the party controlling the outcome is the destination account owner (a counterparty), who can repeat this any time they retain control of `depositAuth` on their account.

### Likelihood Explanation
This requires: (1) an XRPL destination account whose owner can toggle `depositAuth`, (2) a caller/integrator flow that calls `validateWithdrawal` and `createWithdrawalIntents` as separate, non-atomic steps (as the two methods are designed), and (3) a timing window between the two calls in which the flag is flipped. The cost to the destination-account owner is trivial (one `AccountSet` transaction on XRPL), but the “attacker” gains nothing tangible except griefing the withdrawal — no funds are redirected to them, no funds are stolen; the outcome is stuck/misdirected funds requiring off-chain remediation. The window size depends entirely on how the integrator sequences these two SDK calls, which is outside this repo's control for the general case, but the repo itself provides no re-validation safety net regardless of window size.

### Recommendation
Re-validate the XRPL `depositAuth` (and `requireDestinationTag`) flags for XRPL destinations inside `createWithdrawalIntents` (or immediately before signing in the withdrawal orchestration in `sdk.ts`), rather than relying solely on the earlier, independent `validateWithdrawal` call. Alternatively, make `createWithdrawalIntents` accept only a previously-returned validation token/timestamp with a short TTL, and reject stale validations.

### Proof of Concept
Vitest test (mock only `xrpl.httpClient.getAccountInfo` over HTTP):
1. Mock `getAccountInfo` to return `account_flags.depositAuth = false` on the first call.
2. Call `bridge.validateWithdrawal({ assetId, amount, destinationAddress: xrplAddress })` and assert it resolves without throwing.
3. Change the mock so the next call to `getAccountInfo` returns `account_flags.depositAuth = true`.
4. Call `bridge.createWithdrawalIntents({ withdrawalParams: { assetId, amount, destinationAddress: xrplAddress, routeConfig }, feeEstimation })` directly (without calling `validateWithdrawal` again).
5. Assert that `createWithdrawalIntents` resolves and returns a signable `IntentPrimitive[]` (i.e., does NOT throw `XrplDepositAuthEnabledError`), proving that the depositAuth state at "validate" time and at "intent construction/sign" time can diverge with no re-check — the equality `depositAuth@validate == depositAuth@sign` is broken and unenforced.
