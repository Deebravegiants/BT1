### Title
Divide-by-zero panic in `swap_token_amount_base_out` reachable via attacker-chosen `amount_out` in `SwapBaseOut` (denial of service) - (File: program/src/math.rs, program/src/processor.rs)

### Summary
`process_swap_base_out` (and its `_v2` variant) computes the required input amount for a base-out swap by calling `Calculator::swap_token_amount_base_out` **before** validating that the caller-supplied `swap.amount_out` is strictly less than the pool's available liquidity for the output token. This ordering allows an unprivileged swapper, in a single transaction with attacker-chosen instruction data, to force a subtraction that yields `0` as a divisor inside the math routine, causing an unwrap panic analogous to the fpAcc divide-by-zero denial-of-service pattern in CVE-2016-3622.

### Finding Description
In `Calculator::swap_token_amount_base_out`, for the `Coin2PC` direction the denominator is computed as: [1](#0-0) 

```
let denominator = total_pc_without_take_pnl.checked_sub(amount_out).unwrap();
amount_in = total_coin_without_take_pnl
    .checked_mul(amount_out)
    .unwrap()
    .checked_ceil_div(denominator)
    .unwrap()
```

The same pattern exists for `PC2Coin`: [2](#0-1) 

`total_pc_without_take_pnl`/`total_coin_without_take_pnl` are the vault balances net of pending PnL, and `amount_out` is taken directly from `SwapInstructionBaseOut.amount_out`, fully attacker-controlled instruction data.

`process_swap_base_out` calls this function immediately after computing the pool totals, and only checks `swap.amount_out >= total_pc_without_take_pnl` (or `total_coin_without_take_pnl` for the other direction) *after* the call: [3](#0-2) 

If an attacker submits `swap.amount_out == total_pc_without_take_pnl` (Coin2PC) or `== total_coin_without_take_pnl` (PC2Coin) exactly, `checked_sub` succeeds (equal values subtract to `0`, not underflow, so it doesn't fail the `Option` check), producing `denominator = 0`. The subsequent `.checked_ceil_div(denominator).unwrap()` then operates on a zero divisor. Whether the underlying `checked_ceil_div`/`checked_div` on the `U128` type returns `None` (causing an `unwrap()` panic) is consistent with standard `checked_div` semantics for zero divisors, and the entire computation chain here relies on `.unwrap()` calls with no explicit divide-by-zero guard, matching the bug class of CVE-2016-3622 (unguarded division causing a crash on attacker-supplied input). The identical unguarded code path exists in `process_swap_base_out_v2`, which repeats the same calculation ordering: [4](#0-3) 

### Impact Explanation
A successful trigger causes the on-chain program to panic during instruction processing, aborting the transaction. Because the vulnerable computation runs before any balance/authority mutation, this does not directly enable fund theft, but it is a reachable, low-cost denial-of-service against the `SwapBaseOut`/`SwapBaseOut2` instructions for any pool where an attacker can construct `amount_out` equal to the exact current net pool balance (a value that is readable from public on-chain vault accounts prior to submitting the transaction, making the precondition attacker-achievable).

### Likelihood Explanation
The vault balances (`total_pc_without_take_pnl`, `total_coin_without_take_pnl`) are computed from public token account amounts and the `AmmInfo.state_data` PnL counters, both readable on-chain immediately before submitting a transaction, so an attacker can construct an `amount_out` value equal to the current total with reasonable reliability (accounting for the possibility that another transaction changes the balance in between, which affects timing but not feasibility, especially in a low-traffic pool or via same-slot conflict).

### Recommendation
Reorder the check so that `swap.amount_out < total_pc_without_take_pnl` (or the coin equivalent) is validated **before** calling `Calculator::swap_token_amount_base_out`, in both `process_swap_base_out` and `process_swap_base_out_v2`. Additionally, harden `swap_token_amount_base_out` itself to return an explicit `AmmError` (e.g., `AmmError::CheckedSubOverflow`/a new zero-divisor error) via `checked_sub` and `checked_ceil_div` failure handling rather than `.unwrap()`, so that any future caller ordering mistake cannot cause a panic instead of a clean instruction failure.

### Proof of Concept
1. Observe a pool's `amm_pc_vault` and `amm_coin_vault` token balances and the `AmmInfo.state_data.need_take_pnl_pc/coin` fields to compute `total_pc_without_take_pnl` exactly.
2. Submit a `SwapBaseOut` (or `SwapBaseOut2`) instruction with `user_source` mint = coin, `user_destination` mint = pc (selecting `Coin2PC` direction), and `swap.amount_out` set exactly equal to the computed `total_pc_without_take_pnl`.
3. `process_swap_base_out` calls `Calculator::swap_token_amount_base_out(swap.amount_out, total_pc_without_take_pnl, total_coin_without_take_pnl, Coin2PC)` at [5](#0-4)  before the `swap.amount_out >= total_pc_without_take_pnl` guard at line 2214, so `denominator = total_pc_without_take_pnl.checked_sub(amount_out) = 0` inside [6](#0-5) , triggering the zero-divisor path in the subsequent `checked_ceil_div` call and aborting the transaction.
