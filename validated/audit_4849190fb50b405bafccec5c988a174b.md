### Title
Webhook HMAC only covers the raw body, allowing shop/topic/webhook-id header spoofing for cross-tenant webhook injection - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, and `webhook_id` are read straight from HTTP headers that are never included in the HMAC computation. `Registry.process` validates only the HMAC-over-body and then unconditionally trusts these unauthenticated header values to build `WebhookMetadata` and dispatch the handler, breaking the binding between "bytes verified" and "fields acted on."

### Finding Description
`Webhooks::Request` includes `Utils::VerifiableQuery` and defines: [1](#0-0) 

```ruby
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled from HTTP headers via `shopify_header`, entirely outside of `to_signable_string`, so they are never part of the signed payload: [3](#0-2) 

`HmacValidator.validate` computes and compares the HMAC only over `to_signable_string` (i.e. `@raw_body`): [4](#0-3) 

`Registry.process` relies solely on this body-only HMAC check, then trusts `request.shop`, `request.topic`, and `request.webhook_id` (all header-derived, unsigned) to dispatch to the handler: [5](#0-4) 

The identity binding broken here is: `shop/topic/webhook_id used by handler` ≠ `bytes covered by HMAC`. Because the app's `client_secret` is used to compute a valid HMAC only over the body, any actor capable of legitimately triggering webhooks (e.g. an attacker who installs the app on their **own** shop, a fully unprivileged action) can obtain a genuinely valid `(raw_body, hmac)` pair. They can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will invoke the registered handler with `WebhookMetadata.new(shop: request.shop, ...)` claiming the attacker-chosen body originated from the victim shop.

### Impact Explanation
This is a cross-tenant boundary crossing: an app that trusts `WebhookMetadata#shop` (as the library's own webhook contract instructs consumers to do) to key data lookups/writes, cache invalidation, or session/store selection can be made to process attacker-controlled webhook body content under an arbitrary victim shop's identity, without any privileged credentials, purely because the shop/topic/webhook-id fields consumed by the handler are not bound to the HMAC that authenticates the payload.

### Likelihood Explanation
Likelihood is high for any app author who installs their own throwaway/development shop (a fully unprivileged, self-service action) to harvest legitimate webhook deliveries, since replaying with modified non-signed headers requires no secret knowledge — the HMAC validation logic in `HmacValidator.validate`/`Request#to_signable_string` structurally omits shop/topic/webhook-id from the signed content.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the raw body) in the signable string used for HMAC verification in `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind those header values to the signature so that tampering with them invalidates the HMAC check performed by `Utils::HmacValidator.validate`.

### Proof of Concept
1. Attacker installs the target app on their own Shopify development shop (`attacker-shop.myshopify.com`) — no privileged access needed.
2. Attacker's shop triggers a real webhook delivery; attacker captures the raw body `B` and its valid `X-Shopify-Hmac-Sha256` header `H` (valid because `H = HMAC(secret, B)` per `HmacValidator.compute_signature`).
3. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally a different `X-Shopify-Topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — passes, since it only checks `B` against `H`.
5. Handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to process attacker-controlled content attributed to the victim shop.
