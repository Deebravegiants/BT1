### Title
Withdraw liquidity check trusts the `cash` book, which `recapitalize` inflates by the refunded (non-custodied) amount — (File: contracts/pool/src/ops/recapitalize.rs / contracts/pool/src/cache/cash.rs)

### Summary
Analogous to the RPL bug — where `require(rplStake >= _amount)` ignored the locked, non-withdrawable subset of the stake — the pool's withdrawal reserve check `require_reserves` compares the requested payout against the bookkeeping `cash` field, which is *not* the pool's spendable balance. `Cache::credit_cash` adds the full offered recapitalization amount to `cash`, while the excess-over-shortfall refund is paid back out of pool custody **without debiting `cash`** (the same "refund without debit" pattern documented for `repay`/`recapitalize`). The result is a `cash` book that counts tokens that have already left (or never arrived) — exactly the "total stake minus locked stake" gap: the withdrawable check admits exits against reserves that do not exist.

### Finding Description
- `gate_and_debit` in `contracts/pool/src/ops/withdraw.rs:111-119` calls `cache.require_reserves(net_transfer)`, which in `contracts/pool/src/cache/cash.rs:15-21` asserts only `self.cash >= amount`. `cash` is a ledger field, not the token balance.
- `contracts/pool/README.md` documents: "`repay` and `recapitalize` refund from pool cash without debiting it, correct only because the controller transferred the full amount in first." When that precondition does not hold (an "unfunded" recapitalize — offered amount exceeding the actual backing shortfall, or the refund path paying out before any real receipt), `credit_cash` records the full offered amount while `transfer_out` sends the excess back to the payer.
- The in-repo regression test `test_unfunded_recapitalize_leaves_the_cash_book_overstating_custody` (`contracts/pool/tests/flows.rs:3408-3483`) demonstrates the reachable end state: after a single `recapitalize` call with `amount` equal to the pool's entire token balance, `token.balance(pool) == 0` while `state.cash >= deposit`. A legitimate supplier's `withdraw` then passes `require_reserves` (the book says the liquidity is there) and fails inside the SAC `transfer` with the token contract's `BalanceError = 10` — not with `InsufficientLiquidity` or `PoolInsolvent`.

So `cash` plays the role of `rplStake`, and the refunded/uncredited portion plays the role of `lockedStake`: the check uses `cash >= amount` instead of `cash - unbacked_credit >= amount`.

### Impact Explanation
Two concrete harms, both reachable by an unprivileged address through the controller's permissionless `recapitalize` entrypoint (or a direct pool call where reachable):

1. **Theft of user funds**: the excess-over-shortfall refund is paid from real pool custody against a credit that was never measured as received, letting the caller extract tokens belonging to suppliers.
2. **Temporary freezing of funds / latent insolvency**: afterward the `cash` book overstates custody, so every subsequent `withdraw` is admitted by the pool's own liquidity gate and reverts only inside the token transfer. Suppliers cannot exit until a genuine recapitalization restores the missing custody. Because `cash` is also what `burn_claimable_revenue` treats as available (`min(cash, floor(revenue_value))` in `cache/shares.rs:54-75`), the phantom cash additionally makes unclaimable revenue appear claimable.

### Likelihood Explanation
`recapitalize` is a permissionless maintenance entrypoint (`fn recapitalize(env, payer, hub_asset, amount)` in the controller ABI); the payer only needs to authorize the advertised transfer. The pool credits the offered amount and refunds the excess from custody rather than measuring the net balance delta (contrast with INV-ACCT-03's measured-receipt rule applied to `supply`/`repay`). Any user can submit it at any time — no governance action, price manipulation, or privileged role is required. The failure mode is deterministic once the refund exceeds the tokens actually received.

### Recommendation
Make the withdrawable-reserves check account for the non-custodied subset, mirroring `require(rplStake - lockedStake >= amount)`:

- In `recapitalize` (and `repay`'s refund path), either measure the pool's token balance delta and credit only the retained amount, or call `debit_cash` for every refunded token so `cash` never counts refunded units.
- Add a reconciliation assertion in `withdraw`/`claim_revenue` paths (`require_reserves` against `min(cash, token.balance(pool))`), or keep the invariant that `cash <= balance` enforced at every refund boundary.

### Proof of Concept
The repository already encodes it: `contracts/pool/tests/flows.rs:3408-3483`:

1. Seed a market where a supplier deposits `D` (`cash == balance == D`).
2. Call `recapitalize(hub_asset, payer, amount = D)` with an unfunded `payer` — the pool refunds the "excess" from custody while `credit_cash` retains the full amount: `balance == 0`, `cash >= D`.
3. Supplier calls `withdraw(receiver, amount = i128::MAX)`: `require_reserves(D)` passes on the inflated book, and the call reverts only inside the SAC `transfer` (`BalanceError = 10`), leaving the supplier's funds frozen and the book still claiming `cash >= D`.
