### Title
Direct calls to `Bonding.buy`/`Bonding.sell` bypass the entire Zap fee layer, permanently starving FeeVault - (File: packages/contracts/src/Bonding.sol, packages/contracts/src/Zap.sol)

### Summary
In the Footium report, `FootiumPlayer` charges an EIP2981 royalty but `FootiumClub` does not, so a user can route the same underlying value (players) through the club to dodge the fee. In alt.fun, the analogous split is between `Zap` (the only place that computes and forwards the 0.75% Alt Fun fee to `FeeVault`) and `Bonding`/`Router` (the underlying AMM that actually executes trades and holds **no fee logic at all** — confirmed by the project's own scope doc, `docs/contracts-scope.md:11` "`Router.sol` | AMM math, buy/sell execution (returns gross amounts; no fee deduction)" and `docs/contracts-scope.md:13`). `Zap._buyOnCurve`/`_sellOnCurve` simply call `bonding_.buy(...)`/`bonding_.sell(...)` [1](#0-0)  as ordinary external calls on `Bonding`, with the fee deducted only inside `Zap._buyInternal`/`_sellInternal` before/after those calls [2](#0-1) [3](#0-2) .

### Finding Description
`Zap` is documented as the sole "fee layer" ("`Zap.sol` | User-facing entry point — USDC in/out, LT abstraction, **fee layer**" [4](#0-3) ), while `Bonding` is explicitly documented as having "no fee logic — moved to the router" [5](#0-4) . All 0.75% fee computation, transfer to `FeeVault`, and `accrue()` calls live exclusively in `Zap._buyInternal`/`_sellInternal`/`_accrueFee` [6](#0-5) . `Bonding.buy`/`Bonding.sell` are the real trade-execution entry points that `Zap` itself calls as plain external functions (`bonding_.buy(ltAmount, tokenAddress, 0, msg.sender)`, `bonding_.sell(tokenAmount, tokenAddress, 0, msg.sender)`) [1](#0-0) . Because the fee exists only in the wrapper (`Zap`) and not in the underlying value-moving contract (`Bonding`/`Router`), this mirrors the FootiumPlayer/FootiumClub pattern: any unprivileged trader who already holds the paired LT (or who mints/acquires LT directly through the BounceTech LT contract, entirely outside `Zap`) can call `Bonding.buy`/`Bonding.sell` directly — approving LT/token to `Bonding`'s underlying `Router` — and execute the exact same curve trade `Zap` would perform, without ever passing through `Zap._buyInternal`/`_sellInternal`, and therefore without any fee ever being computed, transferred, or accrued to `FeeVault`.

### Impact Explanation
Every trade executed by calling `Bonding.buy`/`Bonding.sell` directly (bypassing `Zap`) permanently denies the protocol its 0.5% protocol share and creators their 0.25% share of the 0.75% Alt Fun fee on that trade — an unrecoverable, structural revenue bypass, not a one-off loss. At scale this can zero out `FeeVault` accrual for all traders sophisticated enough to interact with `Bonding`/`Router` directly (any bot or integrator), which is the same class of impact ("bypass fees on player sales by selling club instead") that Sherlock accepted as a valid Medium in the source report.

### Likelihood Explanation
Likelihood is high for any user willing to interact with contracts below the `Zap` abstraction — this requires only holding/minting the paired LT (via BounceTech's own `mint`) and calling `Bonding.buy`/`sell` with standard ERC20 approvals; no privileged role, upgrade, or off-chain component is needed. It is directly analogous to the accepted Footium escalation reasoning: any two-sided entry point into the same underlying value transfer where only one side enforces the fee will be exploited by fee-sensitive/volume traders and bots, exactly as EIP2981-aware marketplaces vs. non-enforcing ones were exploited in the original report.

### Recommendation
Either (a) move fee enforcement down into `Bonding`/`Router` (charge and forward the fee inside `Bonding.buy`/`Bonding.sell` themselves, so no entry point can skip it), or (b) restrict `Bonding.buy`/`Bonding.sell` (and any other value-moving entry point) to be callable only by the allowlisted `Zap` router (e.g., an `onlyZap`/depositor-style access check mirroring `FeeVault`'s `onlyDepositor` pattern), so the fee layer cannot be structurally bypassed by calling the underlying AMM directly.

### Proof of Concept
1. Attacker acquires the LT paired with a launched `Token` directly via BounceTech's `mint()` (outside `Zap`, no fee involved).
2. Attacker calls `Router`/`Bonding`'s public trade path directly — `bonding.buy(ltAmount, tokenAddress, minTokensOut, attacker)` — approving the LT to the curve `Router` first, exactly as `Zap._buyOnCurve` does internally [7](#0-6) .
3. The trade executes on the bonding curve with the full gross amount, since `Bonding`/`Router` compute and return only gross amounts and never call `FeeVault.accrue` (confirmed by scope doc: "no fee deduction" [8](#0-7) ).
4. Attacker repeats for `sell`, redeeming LT for USDC off-chain via BounceTech `redeem()` themselves — completing the entire buy/sell cycle with zero USDC ever routed through `Zap._accrueFee` [6](#0-5) , and `FeeVault.protocolBalance`/`creatorBalance` never incremented for this volume.

    function _buyInternal(
        address tokenAddress,
        uint256 usdcAmount,
        uint256 minTokensOut,
        address referrer
    ) internal returns (uint256 tokensOut) {
        if (usdcAmount == 0) revert InvalidInput();
        if (tokenAddress == address(0)) revert InvalidInput();
        if (usdcAmount < minUsdcAmount()) revert BelowMinAmount();
        Bonding bonding_ = _s().bonding;
        if (bonding_.creatorOf(tokenAddress) == address(0)) revert TokenNotTrading();
        if (bonding_.isGraduating(tokenAddress)) revert TokenIsGraduating();

        uint256 grossSpent;
        uint256 actualFee;
        (tokensOut, grossSpent, actualFee) = _executeBuy(tokenAddress, usdcAmount);

        if (tokensOut < minTokensOut) revert SlippageExceeded();

        if (actualFee > 0) {
            _accrueFee(tokenAddress, bonding_.creatorOf(tokenAddress), actualFee, true);
        }

        // Report the USDC actually spent, not the submitted `usdcAmount`. A
        // graduation-capped buy refunds the unused principal and fee, so the
        // two diverge there; for every other buy they're equal.
        emit Buy(tokenAddress, msg.sender, grossSpent, tokensOut);

        if (referrer != address(0) && referrer != msg.sender) {
            emit Referred(tokenAddress, msg.sender, referrer, grossSpent);
        }

    function _accrueFee(
        address token,
        address creator,
        uint256 feeAmount,
        bool isBuy
    ) internal {
        ZapStorage storage $ = _s();
        uint256 creatorShare = (feeAmount * $.creatorFeeBps) / BPS_DENOM;
        uint256 protocolShare = feeAmount - creatorShare;
        $.usdc.safeTransfer(address($.feeVault), feeAmount);
        $.feeVault.accrue(token, creator, creatorShare, protocolShare, isBuy);
    }

    function _buyOnCurve(
        address tokenAddress,
        address lt,
        uint256 ltAmount
    ) internal returns (uint256 tokensOut, uint256 amountInUsed) {
        Bonding bonding_ = _s().bonding;
        Router curveRouter = bonding_.router();
        IERC20(lt).forceApprove(address(curveRouter), ltAmount);
        // Slippage check happens after the refund path in `_buyInternal`.
        // `msg.sender` here is the user-EOA that called `Zap.buy`; passed
        // through as `trader` for the emitted `Trade` event.
        (tokensOut, amountInUsed) = bonding_.buy(ltAmount, tokenAddress, 0, msg.sender);
        IERC20(lt).forceApprove(address(curveRouter), 0);
    }

    function _sellOnCurve(
        address tokenAddress,
        uint256 tokenAmount
    ) internal returns (uint256 ltReceived) {
        Bonding bonding_ = _s().bonding;
        Router curveRouter = bonding_.router();
        IERC20(tokenAddress).forceApprove(address(curveRouter), tokenAmount);
        ltReceived = bonding_.sell(tokenAmount, tokenAddress, 0, msg.sender);
