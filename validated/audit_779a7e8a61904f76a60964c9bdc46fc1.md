### Title
Permanent market freeze from RAY-value overflow during interest accrual - (File: contracts/pool/src/interest.rs)

### Summary
An unprivileged borrower can create and maintain a sufficiently large, highly utilized debt position until the pool’s next interest-accrual calculation overflows `i128` before the borrow-index ceiling is reached. [1](#0-0)  Because every affected pool mutation synchronizes that market before processing the requested action, the resulting `MathOverflow` permanently blocks withdrawals, repayments, liquidations, and further index updates for the market. [2](#0-1) 

### Finding Description
`Controller::update_indexes` is permissionless after caller authorization and forwards the attacker-selected `assets` to the pool. [3](#0-2)  The controller’s pool call enters `ops::market::accrue`, which loads each requested market into `Cache`, invokes `interest::global_sync`, and commits the resulting state. [4](#0-3) 

The vulnerable accounting state is a RAY-scaled debt book whose token-unit value no longer fits `i128` at the current borrow index. [5](#0-4)  Interest accrual first raises the stored index and then derives the debt’s original-token value through `scaled_to_original`; that multiplication overflows before `MAX_BORROW_INDEX_RAY` can cap the index. [6](#0-5) 

The reachable setup is:

1. An attacker supplies a very large amount of an 18-decimal market through `supply`.
2. The attacker supplies sufficient collateral and calls `borrow` to keep that market at sustained high utilization.
3. The attacker maintains the position while interest accrues.
4. The attacker, or anyone else, calls `update_indexes` with that market’s `HubAssetKey`; accrual panics with `MathOverflow`.
5. Subsequent `withdraw`, `repay`, liquidation, revenue, and market-parameter operations still attempt accrual first and hit the same overflow. [7](#0-6) 

### Impact Explanation
This is permanent freezing of user funds and market availability: suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot operate because the shared accrual step panics before the requested action. [8](#0-7)  The failure is not merely a caller’s oversized input being rejected; valid small withdrawals and repayments fail once the stored market state crosses the RAY-value ceiling. [2](#0-1) 

### Likelihood Explanation
The condition requires an unusually large supplied book, sustained high utilization, and prolonged accrual, so it is not reachable with ordinary balances or a single bounded input. [9](#0-8)  It is nevertheless externally reachable through the normal `supply`, `borrow`, and `update_indexes` interfaces when market caps and token balances permit the required book size, and once reached the failure is deterministic rather than dependent on oracle behavior, token semantics, or a callback. [10](#0-9) [3](#0-2) 

### Recommendation
Bound the debt book’s represented token value, not just its index. In `contracts/pool/src/interest.rs`, check the scaled-debt-to-token-value conversion before multiplication and fail the borrowing or accrual-triggering configuration change before the state reaches the overflow boundary; alternatively make the post-accrual debt representation use a checked, explicitly handled saturation/recovery path. Enforce market supply and borrow caps using a worst-case reserve that accounts for projected index growth, and add an emergency exit path that can burn debt or withdraw cash without recomputing the overflowing total. Regression coverage should assert that a market approaching the boundary rejects new debt while preserving repayments and withdrawals.

```rust
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
```

```rust
/// Accrues interest for each market in `hub_assets` and emits one state event
/// per market.
///
/// Always commits state so same-ledger simulation records the write footprint
/// needed if time advances before transaction inclusion.
pub(crate) fn accrue(env: &Env, hub_assets: Vec<HubAssetKey>) {
    renew_instance(env);

    for hub_asset in hub_assets.iter() {
        let mut cache = Cache::load(env, &hub_asset);
        interest::global_sync(env, &mut cache);
        events::emit_market_state(env, cache.commit());
    }
```
