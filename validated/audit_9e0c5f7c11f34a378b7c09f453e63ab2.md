### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted for tenant routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from only the raw request body, while the `shop`, `topic`, and `webhook_id` values used downstream for tenant identification and handler dispatch are read directly from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` exclusively: `lib/shopify_api/webhooks/request.rb:35-38`. The `shop`, `topic`, and `webhook_id` accessors instead read straight from HTTP headers via `shopify_header`, with no cross-check against the body or the HMAC: [1](#0-0) . `ShopifyAPI::Utils::HmacValidator.validate` only verifies `to_signable_string` (the body) against the `hmac` header using the app's shared `api_secret_key`: [2](#0-1) . `Registry.process` then trusts `request.shop` (and `request.topic`, `request.webhook_id`) after only validating the HMAC over the body, and passes it straight into `WebhookMetadata` for the handler: [3](#0-2) .

The identity binding that should hold is: `HMAC(shared_secret, signed_bytes) == received_hmac` implies `signed_bytes` authentically represents *all* security-relevant fields the app acts on. Here `signed_bytes = raw_body` but the app acts on `shop` (and `topic`/`webhook_id`) taken from headers that are outside `signed_bytes`. Because every shop that installs a Shopify app which processes webhooks shares the same `api_secret_key` for HMAC computation, an attacker who controls one legitimately-installed shop can capture a valid `(raw_body, hmac)` pair produced by Shopify for their own shop's webhook, then replay that same body/hmac pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` forwards the attacker-chosen `shop` value to the handler as if it originated from the victim tenant.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is documented to provide: per `docs/usage/webhooks.md:125`, `Registry.process` is claimed to "verify the request did indeed come from Shopify" before invoking the handler with `data.shop` as the trusted tenant identifier [4](#0-3) . Host applications built on this documented contract (e.g. `shopify_app`-style controllers) reasonably key per-tenant side effects (session/state lookups, uninstall handling, GDPR redaction processing, background job dispatch) off `data.shop`, since the gem asserts that "the request did indeed come from Shopify" once `process` succeeds. An attacker with a valid app installation (unprivileged relative to other merchants) can therefore forge cross-tenant webhook events with an authentic HMAC, causing the app to process attacker-controlled webhook bodies under another shop's identity — a cross-tenant access primitive.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on their own shop (a normal, unprivileged action any Shopify merchant/developer can perform) and observe/replay their own legitimately-delivered webhook HTTP requests, which is trivial (webhooks are plain HTTP POSTs the attacker's own server receives). No access to `api_secret_key`, tokens, or victim credentials is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable material (or otherwise cryptographically bind them to the signed body), or, at minimum, document and enforce that `shop`/`topic`/`webhook_id` are untrusted metadata that host applications must independently reconcile against the verified body/shop-specific session before use. Ideally, `to_signable_string` should incorporate all header fields the library exposes as verified output (`shop`, `topic`, `webhook_id`) so that `HmacValidator.validate` provides an authenticity guarantee over the complete `WebhookMetadata`, not just the body bytes.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the target app,
# so Shopify legitimately sends them a correctly-HMAC'd webhook for their own shop.
captured_body = '{"id": 123, "note": "hello"}'
captured_hmac = "<valid hmac header value Shopify sent for attacker-shop's webhook>"

# Attacker now POSTs the same body+hmac to the app's webhook endpoint,
# but swaps the shop-domain header to the victim shop.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,   # still valid: only body is signed
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (body/hmac match),
#    handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", ...)) is invoked,
#    even though Shopify never sent this event for victim-shop.
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
