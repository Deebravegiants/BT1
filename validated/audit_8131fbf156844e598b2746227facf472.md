### Title
Unbounded, never-reset ERC20 approvals granted from the shared `CallDispatcher` during order `predispatch`/`postdispatch` calldata allow theft of any token balance later routed through it - (File: `evm/src/utils/CallDispatcher.sol`, `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`)

### Summary
`IntentGatewayV2.placeOrder` and `_execute` (via `IntentsBase._execute`) route arbitrary, user-supplied `Call[]` calldata (`order.predispatch.call` / `order.output.call`) through a single shared `CallDispatcher` contract instance [2](#0-1) [3](#0-2) . `CallDispatcher.dispatch()` blindly executes each call in its own context with no restriction on `to` or `data` beyond `to` having code [1](#0-0) . Because this is the same, persistent contract reused across every order (and reused across HFT/WrappedHFT calldata-execution flows per the docs), any user can submit an order whose `predispatch.call` contains `IERC20(token).approve(attacker, type(uint256).max)`. Nothing in the code ever revokes that allowance. Any token balance the dispatcher subsequently and even transiently holds — from unrelated users' orders, dust, or fee-on-transfer surplus — can then be pulled out by the attacker via `transferFrom`, exactly like the Vault/wrapper scenario in the external report.

### Finding Description
`placeOrder`'s predispatch flow transfers the order's declared predispatch assets to `_params.dispatcher`, then calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` with calldata fully controlled by the order's placer [2](#0-1) . The same pattern exists for `order.output.call` in `_execute`, run after a fill [4](#0-3) .

`CallDispatcher.dispatch` performs a raw low-level `.call` to any contract address with any calldata, in the dispatcher's own storage/allowance context (not `delegatecall`) [1](#0-0) . There is no mechanism — neither in `CallDispatcher` nor in the calling gateway/HFT contracts — that revokes ERC20 allowances the dispatcher may have granted during a `dispatch()` call. The project's own documentation acknowledges this exact risk but only as caller guidance, not as an enforced invariant: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution." This is functionally identical to the reported Vault bug: the trusted contract (`CallDispatcher`/Vault) leaves behind an ERC20 approval to an address chosen by an untrusted party, and nothing resets it afterward.

The `dispatcher` address is a single governance-configured value shared by every order placed on the gateway (`_params.dispatcher`), and per the docs the same `CallDispatcher` deployment is also reused by `HyperFungibleToken`/`WrappedHyperFungibleToken` for calldata execution. Because it is one long-lived, stateful contract shared across all unrelated users and even across protocols, an approval planted by one attacker's order persists indefinitely and is not scoped to that attacker's own transaction or funds.

### Impact Explanation
An attacker submits (or fills) an order whose `predispatch.call` or `output.call` contains a single `approve(attacker, type(uint256).max)` call on some ERC20 token, requiring no real swap or side effect — the attacker's own predispatch assets can be a dust amount just to reach the `dispatch()` call. This plants a permanent max allowance from `CallDispatcher` to the attacker for that token. Afterward, any time the dispatcher holds a nonzero balance of that token — e.g. dust from another user's predispatch/postdispatch flow that isn't fully accounted for by `_execute`'s sweep of only `order.output.assets` tokens [5](#0-4) , from other protocols' calldata execution routed through the same shared instance, or from timing/MEV around another order's transfer-in-then-sweep sequence — the attacker calls `transferFrom(dispatcher, attacker, balance)` and drains it. This is a permissionless path to steal funds that never belonged to the attacker's own order, satisfying "concrete theft of funds" for an intents escrow/CallDispatcher primitive reachable by any unprivileged order placer.

### Likelihood Explanation
Likelihood is high: placing an order with a crafted `predispatch.call`/`output.call` is a normal, permissionless, single-transaction user action requiring no special privilege, no governance action, and only trivial gas cost. The dispatcher's role as a shared, long-lived contract across many orders (and potentially multiple apps) means the attacker does not need to control the timing of the victim transaction precisely — the planted approval sits indefinitely waiting for any balance to appear on the dispatcher.

### Recommendation
- Short term: make `CallDispatcher` reset any allowance it grants to zero immediately after each call in the batch (or forbid `approve`-selector calldata targeting arbitrary spenders), and/or check `msg.sender`/scoping so a dispatcher instance cannot be shared statefully across unrelated callers' calldata.
- Long term: deploy an ephemeral/per-call dispatcher (e.g., via `CREATE2` + `SELFDESTRUCT` or a minimal proxy cleared after use) so no allowance state can outlive a single order's execution, and enforce exact-amount approvals on-chain rather than only documenting the expectation.

### Proof of Concept
1. Attacker calls `placeOrder` with `order.predispatch.assets` = a dust amount of `TOKEN`, and `order.predispatch.call` encoding a single `Call{ to: TOKEN, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max) }`.
2. `IntentGatewayV2.placeOrder` transfers the dust `TOKEN` to `_params.dispatcher` and calls `ICallDispatcher(dispatcher).dispatch(order.predispatch.call)` [6](#0-5) , executing the `approve` from the dispatcher's context. `CallDispatcher` now has an unlimited allowance of `TOKEN` to the attacker, persisted in `TOKEN`'s storage — nothing in `dispatch()` or the gateway ever clears it [1](#0-0) .
3. At any later point that `CallDispatcher` holds a nonzero `TOKEN` balance (e.g., another user's `placeOrder`/`fillOrder` with predispatch/postdispatch calldata involving `TOKEN`, before the gateway's sweep-back completes, or dust left unswept because it isn't in `order.output.assets`), the attacker calls `TOKEN.transferFrom(dispatcher, attacker, balance)` directly, stealing funds that belong to an unrelated order/user.
