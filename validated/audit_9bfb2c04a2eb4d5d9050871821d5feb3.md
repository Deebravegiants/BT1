Audit Report

## Title
Authenticated Nil-Pointer Dereference DoS via Missing `params` in Vault `publicKeyGet` Gateway Message - (File: `core/capabilities/vault/gw_handler.go`)

## Summary
The node-side Vault gateway handler's `handlePublicKeyGet` dereferences `req.Params` without a nil check when handling `vaulttypes.MethodPublicKeyGet` requests, unlike every other Vault method which passes through `GatewayVaultRequestProcessor.ProcessRequest`, whose per-method functions explicitly validate `req.Params != nil` before any handler unmarshals it. Since `MethodPublicKeyGet` is intentionally unauthenticated ("Public key requests don't require authorization"), an unprivileged caller can submit a request with a missing/null `params` field, which is forwarded unchanged from the gateway to node(s), causing a nil-pointer dereference panic in `handlePublicKeyGet`.

## Finding Description
In `core/capabilities/vault/gw_handler.go`, `HandleGatewayMessage` routes `MethodSecretsCreate`/`MethodSecretsUpdate`/`MethodSecretsDelete`/`MethodSecretsList` through `h.requestProcessor.ProcessRequest`, whose implementation in `core/capabilities/vault/gateway_vault_request_processor.go` checks `req.Params == nil` for each of these methods (e.g., `processCreateSecretsRequest` at L110-117, `processListSecretIdentifiersRequest` at L226-232) and returns `InvalidVaultParamsError` before any unmarshal occurs.

By contrast, `MethodPublicKeyGet` is dispatched directly to `handlePublicKeyGet` (`gw_handler.go` L207-208), bypassing the request processor entirely. `handlePublicKeyGet` (`gw_handler.go` L364-368) executes `json.Unmarshal(*req.Params, r)` unconditionally — if `req.Params` is `nil` (JSON `params` field omitted or `null`), this dereferences a nil `*json.RawMessage`, causing a runtime panic.

On the gateway side, `handler.HandleJSONRPCUserMessage` (`core/services/gateway/handlers/vault/handler.go` L404-420) special-cases `MethodPublicKeyGet` to skip the `requestProcessor.ProcessRequest` authorization/validation pipeline used for the other methods, and forwards the request onward (via `handlePublicKeyGet`/active-request flow) without validating that `Params` is present. This means the nil-params guard that protects every other Vault method never applies to `publicKeyGet`, confirming the broken security assumption: the code assumes `Params` is always populated by the time it reaches the unmarshal call, but no code path enforces this for this specific method.

I was unable to conclusively determine, within the scope of my investigation, whether the goroutine executing `HandleGatewayMessage` on the node side is wrapped by a top-level `recover()`. I found no `recover()` call within `core/services/gateway/connector/connector.go`, and the single call site of `HandleGatewayMessage` there did not reveal an obvious panic-recovery wrapper. This leaves some uncertainty about whether the panic crashes the whole node process or is merely an unhandled/dropped request in that particular goroutine — but in either case, the code exhibits a lack of input validation that is inconsistent with equivalent handlers.

## Impact Explanation
If unprotected by a recover wrapper, a panic here crashes the node process, since the gateway fans this request out to all DON members, causing an availability impact across the whole Vault DON simultaneously. This matches an authenticated (or here, effectively unauthenticated) low-privilege DoS impact class. Even absent a full process crash, this is a genuine defect: an unvalidated nil-pointer dereference reachable by any caller of the Vault gateway's public, intentionally-unauthenticated `publicKeyGet` endpoint.

## Likelihood Explanation
`publicKeyGet` is explicitly designed to skip authorization (per the code comment in `handler.go` L405-406: "Public key requests don't require authorization"), so any client capable of reaching the gateway's Vault JSON-RPC endpoint can trigger this with a trivially crafted request (`params` omitted or `null`). No special credentials, roles, or preconditions are required.

## Recommendation
Add an explicit nil-params check in `handlePublicKeyGet` (`core/capabilities/vault/gw_handler.go` L364-368) before dereferencing `req.Params`, returning `api.UserMessageParseError`/`api.InvalidParamsError` instead of panicking, e.g. mirroring the `req.Params == nil` guards used in `GatewayVaultRequestProcessor`. Apply the equivalent validation on the gateway side in `core/services/gateway/handlers/vault/handler.go` before forwarding `MethodPublicKeyGet` requests to nodes, so malformed requests are rejected at the edge rather than propagated to every DON member.

## Proof of Concept
1. Send a JSON-RPC request to the gateway's Vault user-facing endpoint with no `params` field (or `"params": null`) and `method: "vault.publicKeyGet"`.
2. `handler.HandleJSONRPCUserMessage` (`core/services/gateway/handlers/vault/handler.go` L404-420) special-cases this method, skipping `requestProcessor.ProcessRequest`, and forwards the request toward the node(s) via the active-request/fan-out path.
3. On each node, `GatewayHandler.HandleGatewayMessage` (`core/capabilities/vault/gw_handler.go` L207-208) dispatches to `handlePublicKeyGet`, which executes `json.Unmarshal(*req.Params, r)` (L366) with `req.Params == nil`, panicking with a nil-pointer dereference.
4. A Go unit test constructing `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` and calling `GatewayHandler.HandleGatewayMessage` directly (as done in `core/capabilities/vault/gw_handler_test.go`) would reproduce the panic deterministically without needing the full gateway/connector stack.
