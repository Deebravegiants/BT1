### Title
Unchecked ERC20 `transfer` return value in Tron `IntentGatewayV2.withdraw()` can leave escrowed input tokens permanently trapped or falsely marked as settled - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` implements escrow release with a raw low-level `.call()` to the token's `transfer` selector and only checks that the call did not revert, not that the token actually returned `true`. This differs from the main EVM `IntentsBase._withdraw`, which uses OpenZeppelin's `SafeERC20.safeTransfer` (this was the reachable Tron analog found; other suspected analogs to the Converter report's "approve wrong token" issue were not found in the reachable EVM paths).

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, both `onAccept`'s `SweepDust` handling and the internal `withdraw()` function release tokens using:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, req.beneficiary, amount));
if (!success) revert TransferFailed();
``` [1](#0-0) 

This pattern checks only that the low-level call did not revert (`success == true`), but never decodes/validates the returned boolean from `transfer()`. Many ERC20/TRC20-style tokens on Tron follow the pattern of returning `false` on failure instead of reverting (non-compliant tokens, or tokens with quirks such as fee-on-transfer, paused states, or blacklists). For such tokens, `success` will be `true` even though no value was actually moved, while the function proceeds to decrement `_orders[body.commitment][token] -= amount` and mark `_filled[body.commitment] = beneficiary`, permanently finalizing the order as settled. This is directly analogous to the reported `Converter.sol` issue: the withdrawal/settlement logic is "not polished" in a way that silently mishandles the underlying asset accounting, leaking or losing value without the accounting layer noticing.

The counterpart EVM/Solidity implementation of the same contract (`IntentsBase._withdraw` used by `evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/*`) correctly uses `SafeERC20.safeTransfer`, which reverts on both call failure and a `false` return value. [2](#0-1) 

### Impact Explanation
Once `_orders[body.commitment][token]` is decremented and `_filled[body.commitment]` is set despite the token transfer silently failing, the escrowed input tokens remain custodied by the `IntentGatewayV2` contract on Tron with no remaining accounting entry pointing to them and no path to re-claim them (the order is already marked filled/refunded). This is a permanent freezing of user/solver funds reachable purely through the normal, unprivileged `RedeemEscrow`/`RefundEscrow` settlement flow that any relayer delivers after a solver fill or user cancellation — no privileged role is required to trigger it, only a token whose `transfer()` can return `false` without reverting.

### Likelihood Explanation
Likelihood depends on whether any input/output token configured for the Tron intent gateway is a non-compliant/edge-case TRC20 token that returns `false` instead of reverting on failure (e.g., due to a paused state, blacklist, or insufficient balance edge case introduced by re-entrant dust sweeps). Given Tron's TRC20 ecosystem includes many non-standard tokens, and given the corresponding Solidity/EVM implementation of the exact same contract already uses `SafeERC20.safeTransfer` (indicating the team is aware such protection is needed), this is a real regression specific to the Tron deployment path, not a purely theoretical edge case.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw()` and `onAccept`'s `SweepDust` branch with `SafeERC20.safeTransfer` (the contract already imports and uses `SafeERC20` elsewhere), so that both call failure and a `false` return value from non-compliant tokens cause a revert before escrow accounting and `_filled` state are mutated.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron) with an input token whose `transfer()` implementation returns `false` (rather than reverting) under some condition (e.g., token is paused, or beneficiary is blacklisted).
2. User places a same-chain or cross-chain order escrowing that token; solver fills it, triggering `RedeemEscrow` dispatch, or the order is cancelled/refunded, triggering `RefundEscrow`.
3. When `onAccept` invokes `withdraw(body, isRefund)`:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [3](#0-2) 
because the token returns `false` without reverting, `success` is `true`, so execution continues: the escrow record is decremented and `_filled[body.commitment]` is set, finalizing the order as settled — even though the beneficiary received nothing and the tokens remain stuck in the gateway contract with no accounting path left to recover them.

        // redeem escrowed tokens
