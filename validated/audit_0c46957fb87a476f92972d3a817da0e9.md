Based on my analysis, I found a concrete analog in the webhook processing path that matches the requested bug pattern: **a field acted on but not covered by the HMAC**.

### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain`, `topic`, and `webhook-id` headers from the value that is HMAC-verified. `Registry.process` validates only that HMAC, then unconditionally trusts `request.shop` (and `request.topic`, `request.webhook_id`) and hands them to the app's registered handler. This breaks the intended identity binding: `hmac_verified(body) == trusted(shop)` does not hold, since `shop` is never part of what's signed.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the raw body bytes are covered. Meanwhile the `shop`, `topic`, and `webhook_id` accessors are pulled straight from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC over `to_signable_string` (the body only) and, if it passes, immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` passed to the app's handler, with no cross-check that these header values correspond to whichever shop's secret actually produced the HMAC: [3](#0-2) 

Because `OpenSSL::HMAC.hexdigest(sha256, api_secret_key, raw_body)` is a function of the body and the single shared `api_secret_key` for the app (not of which shop the body came from), **any two webhook deliveries with identical bodies produce identical valid HMACs**, and the `shop-domain` header can be swapped freely without invalidating the signature.

An unprivileged attacker who installs the target app on their own store (a completely normal, unprivileged action) will receive genuine webhook deliveries with valid HMACs for their own shop. They can then replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with any other (victim) shop domain. `Utils::HmacValidator.validate` will pass because it only checks the body signature, and `Registry.process` will invoke the handler believing the event originates from the victim shop.

### Impact Explanation
This breaks the tenant boundary that server-side apps rely on: the webhook handler is told a webhook event belongs to shop B, when in fact only shop A (the attacker's own store) produced the signed payload. Depending on the topic being spoofed (e.g. `app/uninstalled`, `shop/update`, `customers/data_request`, order/customer topics with attacker-controlled body content forged for their own shop but replayed as another tenant), this can lead to cross-tenant data corruption, forged state transitions on a shop the attacker doesn't control, or triggering privileged app-side logic (e.g. de-provisioning, GDPR data-erasure flows, billing changes) against a victim merchant. This satisfies the "Critical — cross-tenant access" bar.

### Likelihood Explanation
Exploitation requires no secrets, no privileged access, and no interception: the attacker only needs to be able to install the app on any store they control (a normal, permitted action for any merchant) to obtain a valid `(body, hmac)` pair, then send an HTTP POST to the app's public webhook endpoint with a forged `shop-domain` header. This is entirely reachable by an ordinary internet user with no elevated capability.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that's cryptographically verified, or otherwise cross-check the header-derived `shop` against a value that is itself authenticated (e.g., look up the expected secret/tenant context by an authenticated identifier rather than trusting the header). At minimum, `Registry.process` should not treat `request.shop` as trusted merely because the raw body's HMAC validated — the library should document/enforce that `shop-domain` must be independently reconciled with the app's own installation ownership. If Shopify's wire protocol itself doesn't sign the shop header, this gem should not silently propagate that header as an authenticated fact into `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app for their own store `attacker.myshopify.com`, receiving a legitimate webhook, e.g. `POST /webhooks` with body `{"id":1}`, headers `X-Shopify-Hmac-Sha256: <valid_hmac_for_body>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: app/uninstalled`.
2. Attacker resends the identical request to the app's webhook endpoint, keeping body and `X-Shopify-Hmac-Sha256` unchanged, but replacing `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` (called from `Registry.process`, [4](#0-3) ) succeeds because it only hashes `@raw_body`.
4. The app's handler receives `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim.myshopify.com", ...)` and performs its uninstall/cleanup logic against `victim.myshopify.com`'s tenant record, even though `victim.myshopify.com` never sent this webhook or authorized this action.
