### Title
Unbounded `body.tokens` loop with external token calls in `withdraw()` can permanently DoS escrow release and cause loss of user/filler funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`IntentGatewayV2.withdraw()` iterates over `WithdrawalRequest.tokens`, an array whose length is fully attacker/user-controlled at order-placement time via `Order.inputs`, performing an external low-level `.call` for each token to transfer funds out of escrow. Because the loop has no bound and each iteration makes an external call, a sufficiently large `inputs` array (or a modest one combined with future gas-cost increases via EIP-1559/repricing or expensive token `transfer` implementations) can push the aggregate gas cost of `withdraw()` above the block gas limit, making delivery of `RedeemEscrow`/`RefundEscrow` (and the `onGetResponse` refund path) permanently unexecutable for that order.

### Finding Description
`placeOrder()` accepts an `Order` whose `inputs` field is an unbounded `TokenInfo[]` [1](#0-0) . These inputs are escrowed and later become the `tokens` array of the `WithdrawalRequest` that is redeemed via `withdraw()`:

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    ...
    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }
        _orders[body.commitment][token] -= amount;
        unchecked { ++i; }
    }
    ...
}
``` [2](#0-1) 

`withdraw()` is invoked from `onAccept` for both `RedeemEscrow` and `RefundEscrow` requests, i.e. every time hyperbridge delivers a fill/cancel receipt back to the source chain, and again from `onGetResponse` for the GET-based refund path [3](#0-2) [4](#0-3) . Since `placeOrder` places no cap on `order.inputs.length`, any unprivileged order-placer fully controls `body.tokens.length` for the corresponding withdrawal. The equivalent EVM (non-Tron) contract `evm/src/apps/intentsv2/IntentsBase.sol` has the identical unbounded per-token loop pattern in `_withdraw()` [5](#0-4) , so the bug class is shared across both gateway implementations.

This is the same bug class as the referenced `PermissionlessBasicPoolFactory.withdraw()` finding: an unbounded, user-influenced array length combined with a per-element external call inside `withdraw()`, with no offset/batch mechanism to split the work.

### Impact Explanation
If `withdraw()` runs out of gas or exceeds the block gas limit (due to a large `inputs` array, expensive/malicious ERC-20 `transfer` implementations among the escrowed tokens, or future increases in call/storage gas costs relative to when the order was placed), the entire delivery transaction reverts. Since delivery of `RedeemEscrow`/`RefundEscrow` is the only path that releases escrowed funds back to the filler or refunds the user, a permanently-reverting `withdraw()` call means the escrowed tokens for that order become permanently locked in the `IntentGatewayV2` contract — no relayer can ever successfully deliver the message, and there is no batching/retry mechanism to work around it. This is a concrete freezing-of-funds condition reachable from a single order placement (an unprivileged, permissionless action), not a privileged-actor bug.

### Likelihood Explanation
Any user can call `placeOrder()` with an arbitrarily long `inputs` array (bounded only by their own willingness to pay gas/escrow at creation time, and by the source-chain block gas limit for that transaction, which is typically much higher than a single `transfer`-heavy withdrawal loop would need to hit trouble on a congested or gas-repriced destination/source chain). Because `withdraw()`'s gas cost scales linearly with the number of escrowed tokens plus whatever gas each token's `transfer()` implementation consumes, and this cost is evaluated at redemption time — potentially long after order placement, when gas prices/costs may have shifted — the probability of an eventual gas-limit failure grows with the number of orders using multi-token escrows and with time. The condition can also be intentionally triggered by anyone placing an order with a maliciously long `inputs` list purely to lock their own — or, if `inputs` become associated with a counterparty's assets in future design changes, someone else's — funds, or to grief relayers who cannot ever complete delivery.

### Recommendation
Bound the number of escrowed tokens per order at `placeOrder()` time (e.g., enforce `order.inputs.length <= MAX_TOKENS` and a similar cap on `output.assets`), and/or refactor `withdraw()` to support partial/batched redemption (an offset + limit parameter, releasing a subset of tokens per call, similar to the recommendation in the referenced report) so that a large token list can be redeemed across several transactions instead of requiring a single all-or-nothing loop. Additionally, avoid reverting the entire withdrawal transaction on a single failed `token.call()`; consider a pull-based or per-token failure-isolated design so that one broken/expensive token does not lock every other escrowed asset in the same order.

### Proof of Concept
1. Attacker/user calls `placeOrder()` with `order.inputs` containing N `TokenInfo` entries (large N), escrowing N different ERC-20 tokens for a single order — no length check exists in the contract to prevent this [1](#0-0) .
2. A solver fills the order (or it is cancelled/expires); hyperbridge later dispatches a `RedeemEscrow`/`RefundEscrow` `PostRequest` back to the source chain with `WithdrawalRequest.tokens` mirroring the N escrowed tokens.
3. The relayer delivers this request via `onAccept`, which calls `withdraw(body, ...)` [3](#0-2) .
4. `withdraw()`'s `for` loop executes N external `token.call(transfer(...))` invocations in a single transaction [6](#0-5) . For sufficiently large N (or tokens with expensive `transfer` logic), the transaction gas cost exceeds the block gas limit, and the call reverts unconditionally on every retry attempt, permanently freezing the escrowed tokens for that order in the contract.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
