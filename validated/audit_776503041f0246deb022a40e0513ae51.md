### Title
Shopify webhook `shop-domain` and `topic` headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop-domain` and `topic` values that the application logic trusts to attribute and route the webhook event are taken from HTTP headers that are never part of the signed content. This breaks the identity binding `hmac_verified_bytes == bytes_the_app_acts_on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` accessors instead read directly from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC using `HmacValidator.validate(request)`, which only calls `to_signable_string` (i.e. checks the body), and then immediately uses `request.topic` to look up the handler and `request.shop` as tenant identity passed to the handler, without either value being bound by the signature: [3](#0-2) [4](#0-3) 

Since the app's `api_secret_key` is shared across all shops that install the app (it is not shop-specific), any unprivileged user who can install the app on their own store (or otherwise obtain one genuine webhook delivery with a valid body/HMAC pair) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (claiming to be a different merchant) and/or an arbitrary `shopify-topic` header (routing the body to a different handler than the one Shopify actually signed it for). The HMAC check still passes because the header values were never part of what was signed.

### Impact Explanation
This breaks the equality `shop_bound_by_hmac == shop_used_by_handler` (and equivalently for `topic`). An attacker with a single legitimate webhook delivery (trivially obtainable by installing the app on a store they control) can forge webhook events attributed to a victim shop, or divert a signed payload to a handler for a different topic than Shopify intended. Application handlers built on top of this gem (e.g. `shopify_app`) typically use `data.shop` to scope database writes/updates to a tenant, so this enables cross-tenant data confusion/injection without possessing the victim's access token or the app's `client_secret`.

### Likelihood Explanation
Moderate-to-high: exploitation requires only the ability to send arbitrary HTTP requests to the app's public webhook endpoint plus one genuine webhook body/HMAC pair, which any unprivileged user can generate by installing the app on their own shop and capturing the delivered payload. No access token, `api_secret_key`, or privileged account is needed.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the signable content verified by the HMAC, or otherwise cryptographically bind them (e.g., compute the HMAC over a canonical string combining header values and body) instead of computing it over `@raw_body` alone in `Request#to_signable_string`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com`, triggering a real webhook delivery for topic `orders/create` with body `B` and valid header `shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker replays the same body `B` and same HMAC header to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `shopify-topic`).
3. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb:13`) succeeds because it only checks `B` against the HMAC, ignoring the headers.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) dispatches the handler using the attacker-controlled `topic`/`shop` header values, causing the app to process attacker data as if it originated from `victim-shop.myshopify.com`.
