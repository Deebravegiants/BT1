### Title
Webhook `shop` identity is taken from an unauthenticated header while the HMAC only signs the body — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then hands the handler a `WebhookMetadata` object whose `shop` field is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header — a value that is never included in the signed material. An attacker who can obtain any one genuine `(body, hmac)` pair (e.g. by installing the app on their own store and receiving a legitimate webhook) can replay that exact body/HMAC while substituting an arbitrary `shop-domain` header, and the gem will report the forged shop to the handler as authenticated.

### Finding Description
The signable content for a webhook request is defined as the raw body only:

```ruby
# lib/shopify_api/webhooks/request.rb
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

`shop` is read straight from an HTTP header with no cross-check against the signed payload:

```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Registry.process` validates the HMAC and then forwards `request.shop` — the unauthenticated header — directly into the data given to the app's handler:

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [3](#0-2) 

`HmacValidator.validate` in turn only checks `verifiable_query.to_signable_string` (the body) against the secret; it never touches headers: [4](#0-3) 

This breaks the identity binding: **shop value verified by the HMAC (none) ≠ shop value acted upon by the handler (`request.shop`, from an unsigned header)**. Because Shopify's webhook HMAC secret is the app's single `client_secret`, shared across every shop that installs the app, any merchant who has installed the app can capture one genuine `(body, hmac)` pair for their own shop and resend it to the app's webhook endpoint with the `shop-domain` header changed to a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspected the header, and the forged `shop` value is passed to the handler as if authenticated.

This is also the gem's documented usage pattern — the docs instruct handlers to trust `data.shop` directly:

```ruby
def handle(data:)
  puts "Received webhook! topic: #{data.topic} shop: #{data.shop} ..."
  perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
end
``` [5](#0-4) 

so an app built exactly as documented inherits the cross-tenant weakness without deviating from the gem's own recommended API.

### Impact Explanation
An attacker (any user able to install the app on a store they control, or capture one legitimate webhook delivery) can make the gem report an attacker-chosen `shop` for a webhook whose body content and HMAC they replay unmodified. Applications that key per-shop state, jobs, or writes off `WebhookMetadata#shop` (exactly as shown in the gem's own docs) can be made to apply the attacker's webhook body against a different tenant's records — a cross-tenant data integrity issue reachable purely through this gem's webhook-processing code, without needing `api_secret_key`, an access token, or any privileged credential.

### Likelihood Explanation
Likelihood is high: obtaining one legitimate `(body, hmac)` pair only requires installing the app (a normal, unprivileged action any merchant can take), and forging the `shop-domain` header on an HTTP replay is trivial. No cryptographic secret or elevated access is required.

### Recommendation
Bind the shop identity to the authenticated payload instead of trusting a header:
- Include the shop domain (and ideally topic/webhook id) inside the signed material (`to_signable_string`), or
- Have `Registry.process` cross-check `request.shop` against the shop embedded in the parsed body payload (most Shopify webhook payloads include the shop's domain/id), rejecting mismatches, or
- Document and enforce that consuming apps must independently verify `data.shop` against a known/installed-shop store before trusting it for tenant-scoped operations, and update the sample handler in `docs/usage/webhooks.md` to reflect this requirement rather than showing direct, unchecked use of `data.shop`.

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com`; trigger any subscribed webhook topic and capture the resulting HTTP request, including its raw body and `x-shopify-hmac-sha256` header (both legitimately issued by Shopify for the attacker's own shop).
2. Resend that identical request to the app's webhook endpoint, changing only the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates successfully because the signature only covers `@raw_body`, unchanged from step 1.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: <attacker's body>, ...)` and performs tenant-scoped work against the forged shop, per the gem's own documented handler pattern.

          received_signature = verifiable_query.hmac
