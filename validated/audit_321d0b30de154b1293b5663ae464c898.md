### Title
Unsanitized router payload executes attacker-chosen contracts under the caller's authorization tree, enabling wallet theft - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The puppet-facter report is command injection: attacker-supplied input reaching an execution sink without sanitization. The direct analog in XOXNO Lending is the `swap`/`swap_xdr` route payload that every controller strategy (`multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`) forwards verbatim to the swap router, which then invokes whatever `pool` and `token` addresses the payload names. Neither the controller nor the router validates or allowlists those addresses, so arbitrary attacker-deployed code runs inside the transaction — and any `require_auth` it triggers resolves against the victim's signed authorization tree.

### Finding Description
`swap_tokens` decodes nothing and inspects nothing about `swap`: it only authorizes a single `token_in.transfer(controller, router, amount_in)` and calls `router.execute_strategy(&controller, &amount_in, swap)` [1](#0-0) . On the router side, `execute_strategy` decodes the caller-supplied XDR and runs it [2](#0-1) . Hop venue, pool, and token addresses all come from the payload's `assets`/`ops` registries — the router "calls the pool and token addresses its payload names and keeps no allowlist of them, so a route can put third-party code on the call stack below the caller's authorization" [3](#0-2) .

Because Soroban auth is tree-based, a `token.transfer(victim, attacker, x)` issued by the rogue hop pool is recorded by simulation as a child of the victim's `swap_collateral`/`multiply` authorization entry. If the victim signs the simulated tree (the default wallet flow), the transfer executes — draining wallet tokens that were never part of the swap. The protocol's own harness test proves the exact mechanic: `RogueHopPool::swap` calls `token::Client::transfer(&victim, &to, &amount)` and, under the signed poisoned tree, Alice's unrelated wallet balance of 77,770 units moves to the attacker while the swap still pays a fair output and passes all controller risk gates [4](#0-3) [5](#0-4) .

The controller's post-conditions do not bound this: it only checks `actual_spent <= amount_in`, positive measured `token_out` receipt, and final account risk [6](#0-5) . The stolen wallet transfer is invisible to all of them, exactly as the threat model states: "The loss is then the caller's wallet, not the routed amount, and neither the payload minimum nor the final risk gate bounds it" [7](#0-6) .

### Impact Explanation
Theft of user funds. The attacker extracts arbitrary tokens from the victim's wallet up to whatever the victim's signed auth tree permits — bounded only by the victim's balances, not by `amount_in`, the route minimum, or account health. The victim receives a correctly-priced swap output, so nothing on-chain signals the theft.

### Likelihood Explanation
Exploitation requires the victim to sign a route built by the attacker (malicious frontend, compromised quote source, or phishing), and wallets display auth trees poorly enough that simulation-produced trees are routinely signed unexamined — the doc itself prescribes that clients "must decode the route it signs and refuse an authorization tree with any other child," i.e., the contract places the entire defense on the client [8](#0-7) . The injected child is structurally identical to a legitimate hop authorization, so the attack is realistic; severity is tempered by the required victim signature, consistent with a Medium finding.

### Recommendation
Constrain route execution so payload-named code cannot piggyback on the caller's auth:
- Have the router keep an allowlist (or on-chain registry proof, e.g., Aquarius factory lookup) of venue pool contracts and reject payload pool addresses not on it, rather than invoking arbitrary addresses.
- Alternatively/additionally, execute hops with `require_auth_for_args`-scoped router-side authority and have the controller strategies document/enforce that the client's signed tree must contain exactly the expected children — and consider making the controller itself reject any route whose decode references token contracts outside the hub's listed assets.
- At minimum, surface the danger in the client SDK: refuse to produce a signature when simulation returns unexpected sub-invocations.

### Proof of Concept
The repository contains a working PoC at `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`:
1. Alice supplies 10,000 USDC and holds `WALLET_BALANCE` of an unlisted token.
2. The attacker deploys `RogueHopPool` whose `swap()` calls `wallet_token.transfer(alice, attacker, WALLET_BALANCE)` [4](#0-3) .
3. Alice calls `swap_collateral(alice, account_id, USDC, 5_000, ETH, route)` where `route` names the rogue pool. Simulation records the rogue transfer as a child of her `swap_collateral` auth entry [9](#0-8) .
4. Signing the simulated tree executes the theft: `wallet(alice) == 0`, `wallet(attacker) == WALLET_BALANCE`, while Alice still receives the fair ETH output and the position stays healthy [10](#0-9) .

#[test]
fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);
}
