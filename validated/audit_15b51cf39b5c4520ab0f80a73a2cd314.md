### Title
DeleteAccount action performs unmetered/under-metered iteration over all of an account's access keys, gas-key nonces, and contract-data entries, enabling a gas-underpriced or resource-exhausting `DeleteAccount` receipt - (File: `runtime/runtime/src/actions.rs`, `core/store/src/utils/mod.rs`)

### Summary
The `DeleteAccount` action flow mirrors the Uniswap V3 "unbounded loop" bug class: a single, flat-fee action triggers work whose cost scales with attacker-controlled state (the number of access keys/gas-key nonces/contract-data entries on the account), and a large portion of that work is not charged in gas/compute before it runs.

### Finding Description
`action_delete_account` (`runtime/runtime/src/actions.rs:354`) calls `compute_gas_key_balance_sum(state_update, account_id)` [1](#0-0)  before any gas/compute is charged for that scan. `compute_gas_key_balance_sum` (`core/store/src/utils/mod.rs:458-497`) iterates every raw key under the account's access-key trie prefix via `state_update.locked_iter(...)`, parsing each key and, for gas keys, fetching the full `AccessKey` value to sum balances [2](#0-1) . No gas or compute is charged for this pass at all.

Immediately after, `remove_account` (`core/store/src/utils/mod.rs:505-575`) does a second full iteration over the same access-key/gas-key-nonce prefix to build a `keys_to_remove` list, then a third iteration over the account's contract-data prefix to collect data keys to remove [3](#0-2) . Back in `action_delete_account`, only the gas-key-nonce removals are charged compute, via `storage_removes_compute` scaled by `remove_result.gas_key_nonce_count` [4](#0-3) ; the cost of scanning/removing plain access keys and contract-data entries is not reflected in this metering step (contract-data removal is a bulk `state_update.remove` per key with no compute accounted here, and the trie-iteration cost of the two full-account scans is not priced against `DeleteAccount`'s otherwise-flat action fee).

An attacker can cheaply inflate the number of trie entries under their own account: each `AddKey` action only pays a storage-stake deposit proportional to key size, and a single `AddKey` for a gas key can create up to `MAX_NONCES_FOR_GAS_KEY = 1024` nonce entries in one action [5](#0-4) ; there is no cap found on the total number of access keys/gas keys an account may hold beyond the storage-stake balance requirement. `DeployContract`/`FunctionCall` storage writes can similarly grow the contract-data key count arbitrarily (bounded only by the attacker's willingness to pay storage stake, which unlike gas is a refundable deposit, not a spent cost). A single subsequent `DeleteAccount` receipt then forces the runtime to walk all of these entries in `compute_gas_key_balance_sum` and `remove_account` within one receipt's execution, similar to how the Uniswap `swap` loop walks attacker-created tick positions per call.

This differs from the properly-bounded patterns found elsewhere in the same codebase — e.g. `process_delayed_receipts`/`process_incoming_receipts` check `compute_limit`/`trie.check_proof_size_limit_exceed()` on every loop iteration [6](#0-5) , and `view_access_keys` enforces per-page item caps [7](#0-6) . The `DeleteAccount` action's internal iteration has no equivalent per-iteration budget check or upfront cap tied to gas charged.

### Impact Explanation
If the uncharged/under-charged iteration cost is large enough relative to the flat `DeleteAccount` fee and the receipt's prepaid gas, this allows a receipt to consume more wall-clock/CPU/storage-proof-recording work than its gas payment reflects — i.e., free or underpriced execution, which can be used to build receipts that are disproportionately expensive to process relative to gas charged, straining chunk-processing time and potentially affecting the gas/compute-limit-based chunk production guarantees documented for `process_receipts`. This is the same "unbounded loop / underpriced execution" bug class as the Uniswap report, mapped onto this codebase's `DeleteAccount` handling. It requires attacker-owned storage stake to fund the key/data buildup, which bounds — but does not eliminate — the practicality of the attack, since storage stake is a refundable deposit rather than a burned cost.

### Likelihood Explanation
Moderate. Exploitation requires the attacker to (a) fund storage stake for many access keys/gas-key nonces/contract-data entries on an account they control, and (b) submit a `DeleteAccount` action referencing that account. The `MAX_ACCOUNT_DELETION_STORAGE_USAGE = 10_000` bytes cap on `DeleteAccount` (`core/primitives-core/src/account.rs:160`, referenced in the spec) [8](#0-7)  may substantially limit how large the key/data set can grow before deletion is rejected with `DeleteAccountWithLargeState`, which is a mitigating factor I could not fully quantify against the actual per-entry iteration cost without deeper cost-model analysis (e.g., exact bytes-per-access-key vs. this 10,000-byte ceiling, and whether gas-key nonce entries count fully against it).

### Recommendation
- Charge gas/compute for the `compute_gas_key_balance_sum` scan proportional to the number of access keys/gas-key nonces actually iterated, not only for the subsequent nonce removals.
- Charge gas/compute for the contract-data key enumeration/removal pass in `remove_account`, proportional to the number of entries scanned and removed, not just gas-key nonces.
- Consider tightening `MAX_ACCOUNT_DELETION_STORAGE_USAGE` or introducing a separate cap on the number of access keys per account (independent of raw storage-usage bytes) so the `DeleteAccount` iteration cost is bounded by a value calibrated against per-key gas costs, and document this bound explicitly as recommended in the source report's long-term mitigation guidance.

### Proof of Concept
Conceptual (not executed against a live node):
1. Create account `attacker.near` with enough NEAR to cover storage stake.
2. Submit repeated `AddKey` actions adding gas keys with `num_nonces` near `MAX_NONCES_FOR_GAS_KEY` (1024) each, and/or many plain `FullAccess`/`FunctionCall` keys, and contract-data writes via `FunctionCall`, up to the point where `account_storage_usage` (after subtracting contract code, per `actions.rs:343-347`) approaches `MAX_ACCOUNT_DELETION_STORAGE_USAGE`.
3. Submit a `DeleteAccount` action against `attacker.near`.
4. Observe (in a local devnet/test-loop harness) the gas/compute charged for the receipt versus the actual number of trie reads performed in `compute_gas_key_balance_sum` and `remove_account`, to confirm the discrepancy between charged compute and iteration count.

I was not able to fully verify the exact numeric relationship between `MAX_ACCOUNT_DELETION_STORAGE_USAGE` and the achievable number of access-key/gas-key-nonce entries, nor find a hard cap on the total number of access keys per account beyond storage-stake economics, within the available indexed context — a Devin session with full repo/test access would be needed to run the PoC and measure actual gas-vs-work discrepancy.

pub fn compute_gas_key_balance_sum(
    state_update: &TrieUpdate,
    account_id: &AccountId,
) -> Result<Balance, StorageError> {
    let mut total = Balance::ZERO;
    let lock = state_update.trie().lock_for_iter();
    for raw_key in state_update
        .locked_iter(&trie_key_parsers::get_raw_prefix_for_access_keys(account_id), &lock)?
    {
        let raw_key = raw_key?;
        let key_handle = trie_key_parsers::parse_key_handle_from_access_key_key(
            &raw_key, account_id,
        )
        .map_err(|_e| {
            StorageError::StorageInconsistentState(
                "Can't parse key handle from raw key for AccessKey".to_string(),
            )
        })?;
        let nonce_index =
            trie_key_parsers::parse_nonce_index_from_gas_key_key(&raw_key, account_id, &key_handle)
                .map_err(|_e| {
                    StorageError::StorageInconsistentState(
                        "Can't parse nonce index from raw key for AccessKey".to_string(),
                    )
                })?;
        if nonce_index.is_some() {
            continue;
        }
        if let Some(balance) = get_access_key_by_handle(state_update, account_id, &key_handle)?
            .as_ref()
            .and_then(|access_key| access_key.gas_key_info())
            .map(|gas_key_info| gas_key_info.balance)
        {
            total = total.checked_add(balance).ok_or_else(|| {
                StorageError::StorageInconsistentState("gas key balance overflow".to_string())
            })?;
        }
    }
    Ok(total)
}
