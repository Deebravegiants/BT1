Based on the investigation, I found a valid analog that fits the reentrancy bug-class hint ("action executed while state is inconsistent/not fully bound") through an identity-binding gap in the webhook signature verification path.

### Title
Webhook `shop` (and `topic`/`webhook_id`) headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, while the shop-domain header used as the tenant identity key is never part of the signed content. `Utils::HmacValidator` therefore only proves "this body was signed with this app's shared `api_secret_key`" — it says nothing about which shop the body belongs to. Since the app's `api_secret_key` is shared across every shop that installs the app, any merchant/attacker who installs the target app can capture a validly-signed webhook body from their own store and replay it with a spoofed `X-Shopify-Shop-Domain` header for a victim shop.

### Finding Description
`Request#to_signable_string` signs only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id` and `api_version` are all read straight from unauthenticated headers with no binding to the signature: [2](#0-1) 

`HmacValidator.validate` hashes only `verifiable_query.to_signable_string` (the raw body) against the app's `api_secret_key`: [3](#0-2) 

`Registry.process` trusts `request.shop` once the (body-only) HMAC check passes, and forwards it directly to the host application as the tenant identifier: [4](#0-3) 

The equality that should hold is: `shop authenticated by the signature == shop used as the tenant/session key`. Here, the signature authenticates only *the app* (via the shared secret) and *the body bytes*, not the `shop` value — so the two sides diverge: any shop-scoped body legitimately signed for shop A can be presented with a header claiming shop B, and the check in `HmacValidator.validate` still returns `true`.

### Impact Explanation
This is a cross-tenant identity-binding break (Critical per the rules). A merchant that installs the app on their own store (an ordinary, unprivileged action) can obtain a validly HMAC-signed webhook body signed with the app's `api_secret_key`, then replay that exact body to the app's public webhook endpoint while spoofing the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header to name a victim shop. `Registry.process` will accept it as authentic and dispatch `WebhookMetadata.new(shop: <victim shop>, ...)` to the host application's handler, which typically uses `shop` as the key to look up sessions, scope data access, or trigger tenant-specific side effects (e.g., data deletion/redaction webhooks, `app/uninstalled` state changes, inventory/order side effects keyed by shop).

### Likelihood Explanation
High likelihood for any attacker willing to install the target app on a shop they control — no leaked credentials, no `api_secret_key` access, and no privileged account are required, only the ability to (a) install the app normally and receive one legitimately signed webhook, and (b) POST arbitrary bytes/headers to the app's public webhook callback URL.

### Recommendation
Bind the claimed shop (and ideally topic/webhook id) into the signable content used for HMAC verification, or otherwise cryptographically tie the signature to the specific shop claimed in the header (e.g., verify the shop header against Shopify's documented per-request signing scheme, or require host applications to independently confirm the shop is one that actually has this webhook/app installation registered) before trusting `request.shop` as a tenant key in `Registry.process` / `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` (ordinary merchant action) and captures one legitimate webhook: raw body `B` plus its valid `X-Shopify-Hmac-Sha256` header (computed with the app's shared `api_secret_key`).
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `B` and the same valid HMAC header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the spoofed headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because only `@raw_body` (unchanged) is hashed.
4. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the host application to process attacker-influenced data under the victim shop's identity.
