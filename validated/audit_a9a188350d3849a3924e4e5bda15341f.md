### Title
Attacker-manipulated vault balances can force an unguarded `checked_sub().unwrap()` panic in PNL accounting during `Withdraw`/`Deposit`, permanently bricking the pool - (File: `program/src/processor.rs`)

### Summary
The Ella Core advisory (GHSA-6gm8-3g4h-w82m) is a classic "insufficiently guarded arithmetic/state transition on an externally-triggerable message" panic (CWE-476-class DoS). The Raydium AMM has an analogous pattern: the PNL bookkeeping fields `target_orders.calc_pnl_x` / `calc_pnl_y` are updated in `process_deposit` and `process_withdraw` using unchecked `.unwrap()` on `checked_sub`/`checked_add` results derived from live SPL-token vault balances, which any unprivileged actor can perturb by transferring tokens directly into the AMM's coin/pc vault token accounts.

### Finding Description
In `process_deposit`, the pool's normalized totals `x1`/`y1` are computed straight from the vault token account balances via `Calculator::calc_total_without_take_pnl_no_orderbook` [1](#0-0) , then combined with the PNL delta from `Self::calc_take_pnl` [2](#0-1) . After the deposit, the new `calc_pnl_x`/`calc_pnl_y` are recomputed with chained `.unwrap()` calls on `checked_add`/`checked_sub`: [3](#0-2) 

The withdraw path is structurally the same but purely subtractive, which is the more dangerous direction — it subtracts both the amount being withdrawn *and* `delta_x`/`delta_y` from `x1`/`y1` in one unchecked chain: [4](#0-3) 

Because `x1`/`y1` are derived every call directly from `amm_coin_vault.amount` / `amm_pc_vault.amount` [5](#0-4) , and SPL token accounts can receive tokens from *any* signer via a plain `spl_token::transfer` without going through the AMM program at all, an attacker can donate tokens directly to `amm_coin_vault`/`amm_pc_vault` to desynchronize the vault balances from the internal `calc_pnl_x`/`calc_pnl_y` bookkeeping that the AMM believes is consistent. Because `checked_sub` returns `None` on underflow and the code immediately calls `.unwrap()` on the result rather than mapping it to a proper `AmmError`, once the arithmetic invariant is violated, every subsequent `Deposit` or `Withdraw` call against that pool takes the same code path and panics again, since the underlying vault/`target_orders` state producing the invalid subtraction is never corrected.

### Impact Explanation
A panic aborts the transaction, and since `Deposit`/`Withdraw` are core liquidity-provider operations, once the invariant is broken the pool's LPs can no longer deposit or withdraw liquidity through the standard instructions — deposits and withdrawals rely on this exact `calc_pnl_x`/`calc_pnl_y` chain [3](#0-2) [4](#0-3) , causing a persistent denial of service that can amount to a permanent freeze of LP funds in that pool (they can still be withdrawn via `WithdrawPnl`/other privileged paths only by the configured `pnl_owner`, not by ordinary LPs) [6](#0-5) .

### Likelihood Explanation
Reaching this requires (1) sending direct SPL-token transfers to the AMM's vault accounts (unprivileged, single transaction, no special permission needed since vaults are just normal token accounts owned by the AMM authority PDA) and (2) then invoking `Deposit`/`Withdraw` so the mismatched `x1/y1` vs. `calc_pnl_x/calc_pnl_y` values are combined in the unchecked subtraction. I was not able to fully trace `Self::calc_take_pnl`'s internal bounds logic within the available tool budget, so I cannot state with certainty the exact numeric margin needed to trigger underflow, only that the surrounding code performs the final combination with unguarded `.unwrap()` rather than returning a typed `AmmError`, which is the same class of insufficiently-guarded state-transition panic described in the Ella Core advisory.

### Recommendation
Replace the `.unwrap()` calls on `checked_add`/`checked_sub` in the `calc_pnl_x`/`calc_pnl_y` update logic in both `process_deposit` [3](#0-2)  and `process_withdraw` [4](#0-3)  with `.ok_or(AmmError::CalculationExRateFailure)?` (as is already done elsewhere, e.g. `program/src/processor.rs:1255`), and audit `Self::calc_take_pnl` to ensure `delta_x`/`delta_y` can never exceed the pool's current normalized totals even when vault balances are altered by direct external transfers.

### Proof of Concept
Conceptual PoC (cannot be executed without the full node/CPI harness, but the code path is deterministic):
1. Attacker sends an SPL `Transfer` instruction moving tokens directly into `amm_pc_vault` (or `amm_coin_vault`), bypassing the AMM program entirely, to shift `amm_pc_vault.amount` relative to what `target_orders.calc_pnl_x` assumes.
2. Attacker (or anyone) submits a `Withdraw` instruction with a withdrawal amount computed from their LP balance.
3. Inside `process_withdraw`, `x1` is recomputed from the now-inflated/deflated vault balance [5](#0-4) , `delta_x` is derived via `calc_take_pnl`, and the line `x1.checked_sub(normalize(pc_amount)).unwrap().checked_sub(U128::from(delta_x)).unwrap()` [7](#0-6)  underflows, causing `checked_sub` to return `None` and the subsequent `.unwrap()` to panic, aborting the transaction and leaving the pool in a state where subsequent `Deposit`/`Withdraw` calls repeat the same panic.
