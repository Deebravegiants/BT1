### Title
Unchecked ERC20 return value in `IntentGatewayV2.withdraw()`/`SweepDust` allows silent transfer failure and permanent loss of escrowed funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron `IntentGatewayV2` contract settles escrowed order funds and swept dust using raw low-level `.call()` invocations of `IERC20.transfer`, checking only that the external call did not revert (`success`), without decoding and verifying the returned boolean. Non-standard ERC20 tokens that return `false` on a failed transfer instead of reverting will cause the contract to treat the transfer as successful, permanently losing the underlying funds while marking the order as filled/refunded and decrementing escrow accounting.

### Finding Description
`withdraw()` — invoked from `onAccept()` when a `RedeemEscrow`/`RefundEscrow` message is delivered — pays out escrowed tokens and fees using: [1](#0-0) 

and `SweepDust` handling in `onAccept()` uses the identical unchecked pattern: [2](#0-1) 

In both cases the code does `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...)); if (!success) revert TransferFailed();`. This only verifies the low-level call did not revert; it never inspects the ABI-encoded return data. Per the ERC20 standard, a spec-compliant `transfer` returns a boolean indicating success, and non-compliant tokens (e.g. USDT-style tokens, or any token that returns `false` rather than reverting on failure) will cause `success` to be `true` even though the actual token transfer failed.

This directly mirrors the reported bug class ("transfer return value not checked") from the external report, but here it is worse than a naive unchecked `transfer()` call — the code explicitly performs a low-level call and checks a boolean flag, giving a false sense of safety while still not validating the decoded ERC20 return value.

Notably, this contract already imports and uses `SafeERC20`/`safeTransferFrom` elsewhere in the same file (e.g., `placeOrder`), showing the safe pattern is available but was not applied consistently to the withdrawal/sweep paths: [3](#0-2) 

By contrast, the analogous mainline EVM `IntentsBase.sol` withdrawal path uses `IERC20(token).safeTransfer(beneficiary, amount)`, which correctly reverts on both a reverting call and a `false`-returning call: [4](#0-3) 

### Impact Explanation
When a delivered `RedeemEscrow`/`RefundEscrow` message triggers `withdraw()` against a non-compliant ERC20 token whose `transfer` call returns `false` without reverting, the function will:
1. Decrement `_orders[commitment][token]` as if funds were paid out.
2. Mark `_filled[commitment] = beneficiary`.
3. Emit `EscrowReleased`/`EscrowRefunded` events, signaling successful settlement to indexers/solvers/users.

But the tokens are never actually transferred to the beneficiary — they remain stuck in the contract with no accounting path to reclaim them, since escrow state has already been zeroed and the order marked filled. This is a permanent loss of user/solver funds. The same failure mode applies to `SweepDust`, causing swept dust to be permanently trapped instead of delivered.

### Likelihood Explanation
This path is reached whenever a relayer delivers a valid `RedeemEscrow`, `RefundEscrow`, or `SweepDust` ISMP message to `onAccept()` — an action any permissionless relayer performs as part of normal cross-chain intent settlement, requiring no special privilege. The likelihood of triggering the bug is entirely dependent on which ERC20 token is configured for an order's `output`/escrow assets; since deployments explicitly aim to support "any" ERC20 (per the referenced report's on-chain context) including tokens with non-compliant `transfer` semantics, this is a realistic and reachable condition, not a purely theoretical one.

### Recommendation
Replace the raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handling in `onAccept()` with OpenZeppelin's `SafeERC20.safeTransfer()`, consistent with how `safeTransferFrom` is already used elsewhere in this same contract and how `IntentsBase.sol` handles withdrawals on the mainline EVM contract.

### Proof of Concept
1. Deploy an ERC20 token whose `transfer(address,uint256)` returns `false` (instead of reverting) when the transfer cannot be completed (e.g., paused, blacklisted recipient, or insufficient allowance-style internal check) — analogous to real-world tokens like USDT that deviate from strict ERC20 semantics.
2. Place and fill an order using that token as an output/escrow asset via `placeOrder`, so `_orders[commitment][token]` is credited.
3. Have Hyperbridge relay a `RedeemEscrow` (or `RefundEscrow`) message targeting this order, invoking `onAccept()` → `withdraw()`.
4. Inside `withdraw()`, the low-level `token.call(...)` returns `success = true` (call succeeded) but the decoded return data is `false` (transfer failed internally).
5. Since only `success` is checked, `TransferFailed` is not reverted; `_orders[commitment][token]` is decremented, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — yet the beneficiary received zero tokens, permanently losing the escrowed funds.
