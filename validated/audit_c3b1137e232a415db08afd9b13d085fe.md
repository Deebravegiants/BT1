### Title
No storage gap in upgradeable SDK token bridge base contracts intended for inheritance - ([File: sdk/packages/core/contracts/apps/HyperFungibleTokenUpgradeable.sol], [File: sdk/packages/core/contracts/apps/WrappedHyperFungibleTokenUpgradeable.sol])

### Summary
`HyperFungibleTokenUpgradeable` and `WrappedHyperFungibleTokenUpgradeable` are UUPS-upgradeable, `Initializable`-based token-bridge base contracts explicitly designed to be inherited by third-party developers building their own cross-chain tokens, yet neither reserves a storage `__gap`. Elsewhere in the same codebase, `SimplexPaymaster` — a comparable upgradeable, inheritable base contract — does reserve one, showing the pattern is known and intentionally applied elsewhere but omitted here.

### Finding Description
Both contracts declare state variables (`_host`, `_dispatcher`, `_supportedChains`, plus `_underlying`/`_isWeth` in the wrapped variant) directly in the contract body, are built on `Initializable`/OpenZeppelin-Upgradeable mixins, and document themselves as templates meant for inheritance: `HyperFungibleTokenUpgradeable` states "Inherits ERC20Upgradeable ... for derived contracts" and exposes a `virtual`, `onlyInitializing` `__HyperFungibleToken_init` hook precisely for subclassing [1](#0-0) . `WrappedHyperFungibleTokenUpgradeable` follows the identical pattern with `__WrappedHyperFungibleToken_init` [2](#0-1) . Neither file reserves any empty storage slots at the end of its layout, unlike `SimplexPaymaster`, which explicitly reserves `uint256[48] private __gap;` right before its own state to protect future upgrades [3](#0-2) .

Without a gap, if a project inherits `HyperFungibleTokenUpgradeable`/`WrappedHyperFungibleTokenUpgradeable` and appends its own state variables after the parent's, and the parent base contract is later upgraded upstream to add new state (a normal, anticipated upgradability need for a maintained SDK base contract), the parent's new variables will overwrite the child's existing storage slots (or vice versa), corrupting balances, the `_supportedChains` peer registry, `_host`/`_dispatcher` addresses, or `_underlying`/`_isWeth` configuration.

### Impact Explanation
Storage corruption in these fields directly controls burn/mint accounting and peer-chain authorization for the token bridge:
- Corruption of `_supportedChains` could let an attacker's requests be treated as coming from an authorized peer chain (`onAccept` checks `expectedSource` against this mapping) [4](#0-3) , enabling unbacked minting.
- Corruption of `_host`/`_dispatcher` or ERC20 balance slots could freeze funds or break the `send`/`onAccept`/`onPostRequestTimeout` mint-burn-refund invariants for `WrappedHyperFungibleTokenUpgradeable`'s locked underlying tokens [5](#0-4) .

This is consistent with "unbacked mint" / "permanent freezing of funds" impact categories.

### Likelihood Explanation
This is only triggered on a future upstream upgrade of the base contract combined with third-party inheritance and their own upgrade — not exploitable from a single external transaction today. It requires the SDK maintainers to add new storage to the base contract while downstream forks/subclasses exist and are upgraded to the new base implementation. Given these contracts are explicitly published as inheritable templates in `@hyperbridge/core`, this is a foreseeable maintenance/upgrade scenario rather than a purely theoretical one, but it is not directly reachable from an unprivileged single-transaction call today.

### Recommendation
Add a reserved storage gap (e.g., `uint256[50] private __gap;`) at the end of the state variable declarations in both `HyperFungibleTokenUpgradeable` and `WrappedHyperFungibleTokenUpgradeable`, consistent with the pattern already used in `SimplexPaymaster`, to protect any future base-contract storage additions from colliding with subclass storage.

### Proof of Concept
1. Developer `D` deploys `MyToken is HyperFungibleTokenUpgradeable` behind a proxy, appending `uint256 public myTokenFee;` as the first new state variable in `MyToken`.
2. Polytope Labs later ships a new version of `HyperFungibleTokenUpgradeable` that adds `address internal _newFeeCollector;` to support a new feature.
3. `D` upgrades `MyToken`'s implementation to the new base version (a normal, supported upgrade path since the contract is UUPS/`Initializable`).
4. Because no `__gap` exists, `_newFeeCollector` now occupies the storage slot previously used by `myTokenFee` (or vice versa depending on layout), corrupting `D`'s fee accounting or the base contract's new state, potentially leading to loss of collected fees or broken authorization checks depending on how the corrupted slot is used.

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({from: message.from, to: beneficiary, source: string(request.source), amount: message.amount});
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleTokenUpgradeable.Message memory message =
            abi.decode(request.body, (HyperFungibleTokenUpgradeable.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({from: message.from, to: beneficiary, source: string(request.source), amount: message.amount});
    }
