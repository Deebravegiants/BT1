### Title
Unchecked ERC20 return value in `IntentGatewayV2.withdraw()` / `onAccept` (SweepDust) allows escrow funds to be marked as delivered without an actual transfer - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order funds using a raw low-level `.call()` to the token's `transfer` selector instead of `SafeERC20.safeTransfer` (which it imports and aliases via `using SafeERC20 for IERC20;` but does not use for these paths). The code only checks that the low-level call did not revert (`success`), never decoding/validating the boolean return value that ERC20 `transfer` is supposed to produce. This mirrors the `ICErc20.repayBorrow` unchecked-return-value bug class: a call can "succeed" at the EVM level while the underlying operation actually failed and reports failure via its return value, and that failure is silently ignored.

The identical pattern is used again for `SweepDust` in `onAccept`: [3](#0-2) 

In every case, `success` reflects only whether the low-level `.call` did not revert; the ABI-encoded return data (the ERC20 spec's `bool` success flag) is never decoded or checked. Any token whose `transfer` implementation returns `false` on failure instead of reverting — a common pattern for non-standard/older ERC20/TRC20 tokens, and trivially producible by an attacker-supplied malicious token contract used as an order's input/output asset — will cause `success` to be `true` even though no tokens actually moved.

Despite the failed transfer, `withdraw()` unconditionally proceeds to decrement escrow accounting and finalize the order: [4](#0-3) 

marking `_filled[body.commitment] = beneficiary` and emitting `EscrowReleased`/`EscrowRefunded`, permanently closing out the order's accounting even though the beneficiary received nothing.

This differs from the `evm/src/apps/intentsv2/IntentsBase.sol` and non-Tron `evm/src/apps/IntentGatewayV2.sol` implementations, which correctly use `IERC20(token).safeTransfer(beneficiary, amount)` (which reverts on a `false` return via OpenZeppelin's `SafeERC20`): [5](#0-4) 

confirming the Tron contract's deviation to raw, unchecked `.call()` is the root cause.

### Impact Explanation
This function is reachable by anyone whose order is processed through the intent escrow/withdrawal flow — a relayed `RedeemEscrow`/`RefundEscrow` request, a timed-out GET response, or a `SweepDust` admin action delivered cross-chain. Because escrow state (`_orders[...]`) is decremented and the order is marked `_filled` regardless of whether the token transfer actually delivered funds, this can result in:
- Beneficiaries never receiving their tokens while the protocol's on-chain bookkeeping believes the order is settled (permanent loss of the beneficiary's escrowed funds, since the corresponding escrow slot is already zeroed and cannot be redeemed again).
- Any token used in an order (chosen by the order creator when placing the order, or as a protocol fee token) with non-reverting failure semantics silently breaks fund delivery, defeating the escrow guarantee that funds are only released when the transfer actually succeeds.

This is a fund-freezing/loss-of-funds condition satisfying the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
Likelihood is elevated because: (1) Tron/TRC20 tokens are well known for inconsistent `transfer` return-value semantics (some don't return data at all, some return `false` instead of reverting), which is precisely why this contract avoids `SafeERC20.safeTransfer` here in the first place; (2) the token address for order inputs/outputs is attacker/user-influenced data embedded in the `Order`/`WithdrawalRequest` structs, so a malicious actor can deliberately choose or deploy a token that returns `false` on failure to trigger the silent-failure path.

### Recommendation
Decode and check the actual boolean return value (or use `SafeERC20.safeTransfer`/`safeTransferFrom`, which the contract already imports) for every token transfer in `withdraw()` and the `SweepDust` branch of `onAccept`, e.g.:
```solidity
bool ok = success && (data.length == 0 || abi.decode(data, (bool)));
if (!ok) revert TransferFailed();
```
or simply replace the raw `token.call(...)` calls with `IERC20(token).safeTransfer(beneficiary, amount)`.

### Proof of Concept
1. Order creator places an order (or protocol configures a fee token) using a token contract whose `transfer` function returns `false` on failure without reverting (a standard pattern for many legacy/non-compliant ERC20/TRC20 tokens, or a purpose-built malicious token).
2. The order proceeds through fill/redeem, and a `RedeemEscrow` (or `RefundEscrow`/`SweepDust`) request is relayed to `onAccept`, invoking `withdraw()`.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` returns `success = true` (the call itself didn't revert) but the encoded return data is `false`; the code does not check this, so `_orders[body.commitment][token] -= amount` executes and `_filled[body.commitment] = beneficiary` is set, emitting `EscrowReleased`.
4. The beneficiary never actually receives the tokens (transfer's internal logic failed), yet the order is now marked filled/redeemed and the escrow slot is spent — the funds are unrecoverably lost from the beneficiary's perspective while protocol state shows successful settlement.
