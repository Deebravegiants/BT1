### Title
Same-asset batch withdrawals misreport status/txHash via assetId-only matching - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`describeWithdrawal` for the POA bridge resolves the on-chain withdrawal outcome for a given `WithdrawalIdentifier` by calling `findMatchingWithdrawal`, which matches purely on `assetId` (`nep141:${near_token_id}`) with `Array.prototype.find`, ignoring `destinationAddress` and `amount`. When a single intent batch contains two or more withdrawals of the same underlying token, all of them resolve to the first API-returned withdrawal entry for that token, breaking the equality "status reported == on-chain outcome for *this* withdrawal".

### Finding Description
`createWithdrawalIdentifiers` assigns bridge-scoped indexes per withdrawal and, for the POA bridge, each `WithdrawalIdentifier` is later resolved independently through `watchWithdrawal` → `bridge.describeWithdrawal`. Internally, `describeWithdrawal` calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does:
```js
withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId)
```
This lookup has no dependency on `index`, `destinationAddress`, or `amount`. The code's own comment acknowledges: "multiple withdrawals of the same token in a single transaction are not supported." Consequently, if a caller submits a batch (`withdrawalParams: WithdrawalParams[]`) with two entries for the same `assetId` but different `destinationAddress`/`amount` (a completely normal, unprivileged use case — e.g. paying two different BTC addresses in one intent), both `describeWithdrawal` calls converge on the *same* underlying withdrawal object returned by the POA API, since `.find` always returns the first match for a given `assetId` irrespective of which caller/index is asking.

### Impact Explanation
This is a "status or hash misreport" bug that can make an integrator credit or refund twice, satisfying the High severity bar in scope. Concretely:
- Both withdrawals in the batch can be reported `status: "completed"` with the *same* `txHash` even though only one of the two on-chain transfers has actually landed — the SDK falsely confirms delivery of funds to a destination address that has not received anything.
- An integrator that keys off `describeWithdrawal`'s per-index result (as documented in `README.md`'s "Index correspondence: promises[i] corresponds to withdrawalParams[i]") will incorrectly mark the second withdrawal as settled and release/credit downstream funds or close the request as complete, while the real transfer to that address is still pending or has a different tx hash.
- Conversely, if the first (matched) withdrawal fails/is refunded, the second (unrelated) destination's withdrawal is misreported as `failed`/`refunded` even though its real transfer may have succeeded, potentially causing a wrongful refund or double payment attempt.

### Likelihood Explanation
Likelihood is Medium-to-High: no malicious actor or privileged party is required. Any legitimate caller batching multiple withdrawals of the same token (a supported, documented feature per `README.md`'s "Batch Withdrawals" section) to different destinations triggers this deterministically once the POA API returns more than one withdrawal for that asset in the same NEAR transaction.

### Recommendation
Disambiguate matching by including `destinationAddress` (and ideally `amount`) in `findMatchingWithdrawal`, or track/consume matched withdrawals so each API-returned withdrawal is attributed to at most one `WithdrawalIdentifier` (e.g., match-and-remove, or sort both sides by amount as the existing code comment suggests) before falling back to `assetId`-only matching.

### Proof of Concept
1. Submit `processWithdrawal`/`signAndSendWithdrawalIntent` with `withdrawalParams = [{assetId: "nep141:btc.omft.near", destinationAddress: "addrA", amount: 100000n, feeInclusive: false}, {assetId: "nep141:btc.omft.near", destinationAddress: "addrB", amount: 200000n, feeInclusive: false}]`.
2. POA relayer processes and eventually returns `withdrawals: [{status: "COMPLETED", data: {near_token_id: "btc.omft.near", transfer_tx_hash: "0xAAA", address: "addrA", ...}}]` (only the first has settled; the second is still pending on the relayer side).
3. Call `sdk.waitForWithdrawalCompletion` / `createWithdrawalCompletionPromises`, which internally invokes `describeWithdrawal` for both `index: 0` and `index: 1`.
4. Both calls hit `findMatchingWithdrawal(withdrawals, "nep141:btc.omft.near")`, which returns the same single entry for `addrA` regardless of index.
5. Result: index 1 (bound to `addrB`) is reported `{status: "completed", txHash: "0xAAA"}` even though funds for `addrB` never moved — an integrator persisting this result would incorrectly consider the `addrB` withdrawal settled.

 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.

 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,

	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native

	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
