### Title
Webhook `shop` tenant identifier is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the signature strictly against that signable string [2](#0-1) . The `shop` value, read straight from the `X-Shopify-Shop-Domain` header [3](#0-2) , is never included in the HMAC-covered material, yet `Registry.process` passes this unauthenticated header value straight into `WebhookMetadata` as the tenant identifier for the handler [4](#0-3) .

### Finding Description
This is the exact bug class from the external report: a field that is acted upon (`shop`, used as the tenant/session key by the app) is not covered by the integrity check (the HMAC) that is supposed to bind the whole request to an authenticated source. The binding that should hold is:

`HMAC-verified(raw_body) == (shop, topic, body)` used by the handler

but in reality only `HMAC-verified(raw_body) == body`, while `shop` and `topic` ride along unauthenticated in headers.

Any actor capable of triggering a genuine webhook delivery for *any* shop (e.g., a merchant who installs the app on their own low-value/test store, which is an unprivileged action requiring no special access to the victim) can capture one legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair issued by Shopify, then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g., a victim's shop domain). Because `HmacValidator.validate` only checks the body against the HMAC [5](#0-4) , the forged request passes validation with `request.shop` now equal to the victim's domain, and `Registry.process` invokes the app's handler believing the data legitimately belongs to that victim shop [6](#0-5) .

The gem's own documentation instructs developers to trust exactly this unverified value: `data.shop` is documented as "The shop domain of the webhook" [7](#0-6) , and the `process` call is documented as verifying "the request did indeed come from Shopify" [8](#0-7)  — implying the whole request, including the shop identity, is authenticated, which is not the case.

### Impact Explanation
This crosses a tenant boundary: a handler built on top of this gem's documented `data.shop` will perform shop-scoped side effects (writing order/product/customer state, invalidating caches, triggering shop-specific business logic, etc.) keyed off a value that is fully attacker-controlled at the HTTP-header level, as long as the attacker has any one genuine `(body, hmac)` pair (trivially obtainable by installing the app once on their own store or observing one webhook delivery). This meets the "cross-tenant access" criterion for Critical/High severity, since it lets one tenant inject falsely-attributed webhook data into another tenant's processing pipeline.

### Likelihood Explanation
Likelihood is meaningful but requires the attacker to first obtain one valid `(raw_body, hmac)` pair — trivial for anyone able to install the app on any shop, including their own, or for any topic whose body content is attacker-influenceable (e.g. `orders/create` after placing an order in their own store). No access token, `client_secret`, or privileged account for the *target* shop is required, matching the "unprivileged internet user" threat model.

### Recommendation
Bind the `shop` (and ideally `topic`, `api-version`, `webhook-id`) values into the HMAC-covered signable string, or otherwise require the host application to cross-check `request.shop` against an installed/known session before trusting it, and update `to_signable_string` in `lib/shopify_api/webhooks/request.rb` to include these header-derived identity fields rather than only the raw body.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a genuine webhook POST, e.g. for `orders/create`, noting `raw_body` and header `X-Shopify-Hmac-Sha256: <hmac>`.
2. Replay the exact same `raw_body` and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a request object where `hmac` still matches (computed only over `raw_body`) [9](#0-8) .
4. `Utils::HmacValidator.validate(request)` returns `true` [10](#0-9) .
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` [11](#0-10) , and the handler processes attacker-supplied data as belonging to the victim shop.
