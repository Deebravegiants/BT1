## Finding: Webhook `shop` (and `topic`/`webhook_id`) headers are not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates the request body bytes but never binds them to the `shop`, `topic`, or `webhook_id` values that are read straight from HTTP headers. Any party who can obtain one genuinely-signed webhook (e.g. by installing the app on their own shop) can replay that exact body/HMAC pair while substituting a different `x-shopify-shop-domain` header, and the gem's own `Registry.process` will accept it and dispatch it to the app's handler as if it belonged to another tenant.

### Finding Description
`HmacValidator.validate` computes/compares the signature purely over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be only the raw JSON body, while `shop`, `topic`, `api_version`, and `webhook_id` are pulled from headers that are entirely outside the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

This breaks the intended equality `HMAC-authenticated(body) == HMAC-authenticated(shop, body)`: the gem only proves "this body was signed by an entity holding our app's `client_secret`" — which is the *same secret for every shop* that installs the app — but never proves which shop the body actually belongs to. Contrast this with the OAuth callback path, where `AuthQuery#to_signable_string` explicitly includes `shop` in the signed payload: [4](#0-3) 

so the OAuth flow correctly binds shop-to-signature, while the webhook flow does not.

### Impact Explanation
Any unprivileged actor who can install the app on their own (attacker-controlled) shop legitimately receives real webhook deliveries with a valid HMAC computed over the body using the app's shared `client_secret`. Because the `shop` header is unauthenticated, that same attacker can relay/replay the identical `(raw_body, hmac)` pair to the app's public webhook endpoint while forging the `x-shopify-shop-domain` header to name a victim shop. `Registry.process` will pass `HmacValidator.validate` and hand the handler a `WebhookMetadata` claiming the data originated from the victim tenant — leading host applications (which key their local data/state by `data.shop`) to attribute attacker-supplied data to another tenant, i.e. cross-tenant data injection/corruption through the app's own trusted webhook path.

### Likelihood Explanation
Exploitation requires no special access beyond what any developer/merchant can obtain: installing the target app on a shop they control and capturing one webhook delivery, then POSTing a modified request to the app's public webhook URL. No secrets, tokens, or privileged accounts are needed.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the material used to compute/verify the webhook signature, or otherwise cryptographically bind the shop domain to the payload before trusting it (e.g., verify against a shop-specific registered value, or require the shop domain to be embedded in and covered by the signed body per Shopify's webhook verification guidance).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`; app registers a webhook (e.g. `orders/create`).
2. Shopify delivers a real webhook to the app with headers `x-shopify-hmac-sha256: <valid>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and some raw body `B`.
3. Attacker captures `(B, hmac)` and re-sends a POST to the app's webhook endpoint with the same body `B` and same `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com"})` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only checks `B` against `hmac` — see [5](#0-4)  and [6](#0-5) .
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data under the victim tenant's identity.
