## Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unauthenticated headers while the HMAC only covers the raw body, enabling shop-domain spoofing on replayed webhooks - ([File: lib/shopify_api/webhooks/request.rb])

## Summary
`ShopifyAPI::Webhooks::Request` binds `hmac` verification exclusively to `@raw_body`, but the tenant-identifying `shop`, `topic`, and `webhook_id` values are read straight out of caller-supplied HTTP headers with no cryptographic coverage. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then forwards the unauthenticated header values to the app's handler as the trusted tenant context.

## Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are parsed directly from the `headers` hash passed into `initialize`, which is never touched by HMAC validation: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes the signature over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac` header: [4](#0-3) 

`Registry.process` calls this single check and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` that is handed to the app's handler: [5](#0-4) 

The intended identity binding is: `{bytes cryptographically verified by HMAC}` == `{bytes the handler uses to identify which shop/topic/webhook the event belongs to}`. In this implementation that equality is false — only `@raw_body` is verified, while `shop`, `topic`, and `webhook_id` (the actual tenant-routing fields) are unauthenticated header bytes. Any entity capable of sending a POST to the app's webhook endpoint (which is typically a public, unauthenticated route by design, per the gem's own docs) can take one genuine `(raw_body, hmac)` pair — obtainable legitimately from a webhook fired for their own shop/app installation — and replay it with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to a different shop. `HmacValidator.validate` still passes because it never inspects the header, so `Registry.process` calls the handler believing the event is authentically bound to the victim shop.

## Impact Explanation
This breaks the shop-authenticity binding: the handler receives `WebhookMetadata.new(shop: request.shop, ...)` with `shop` sourced from unauthenticated header bytes, even though the HMAC signature makes the request appear cryptographically legitimate. Any downstream logic that keys tenant-scoped writes, cache updates, or session lookups off `WebhookMetadata#shop` can be tricked into acting on behalf of, or writing data attributed to, a shop the attacker does not control — a cross-tenant confusion condition.

## Likelihood Explanation
Likelihood is high given the mechanics required: an attacker only needs one genuine `(raw_body, hmac)` pair, which they can obtain trivially by triggering any webhook event on their own shop/installation of the target app (a normal, unprivileged action any merchant/tester can perform), then POST that captured body/HMAC pair to the app's public webhook endpoint with a forged `shopify-shop-domain` header. No secret key, token, or TLS interception is needed — the header is simply never checked.

## Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed payload before they are used for routing/tenant identification, e.g. by validating that `request.shop` matches an expectation independently established by the caller (such as the shop associated with the session/registration under which the webhook subscription was created), rather than trusting the header value as-is once the body-only HMAC check succeeds.

## Proof of Concept
1. Install/register the target app on an attacker-controlled shop `attacker-shop.myshopify.com` and trigger any subscribed webhook topic (e.g. `orders/create`), capturing the genuine request Shopify sends: `raw_body` and header `shopify-hmac-sha256`.
2. Craft a new HTTP POST to the app's webhook endpoint using the exact same `raw_body` and `shopify-hmac-sha256` value, but set `shopify-shop-domain: victim-shop.myshopify.com` and keep/adjust `shopify-topic` as desired.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed from these values; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC only over `raw_body` — it matches, since the body/HMAC pair is genuine. [6](#0-5) 
4. The registered handler is invoked with `WebhookMetadata` carrying `shop: "victim-shop.myshopify.com"`, even though nothing in the request was ever bound to that shop cryptographically — any app logic keyed on `WebhookMetadata#shop` now processes the attacker's data under the victim's tenant identity.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
