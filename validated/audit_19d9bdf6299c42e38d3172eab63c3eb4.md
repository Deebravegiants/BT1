### Title
Predictable, unsigned session cookie value trusted as an authenticated session ID - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
`SessionUtils.current_session_id` derives the session-lookup key either from a verified JWT or, when no bearer token is present, directly from the raw `shopify_app_session` cookie value with zero integrity checking. Because the session IDs this gem itself generates are fully deterministic strings (`"#{shop}_#{user_id}"` for online, `"offline_#{shop}"` for offline), an attacker who knows a shop's `.myshopify.com` domain and a target user id can construct that exact cookie value and have it trusted as if it came from a legitimate, previously-established browser session.

### Finding Description
The claimed binding is: `cookie_session_id(cookies) == session.id` should only hold for a cookie value that was legitimately issued to the victim's browser and is otherwise unguessable/unforgeable. In the code, that binding is not enforced at all: [1](#0-0) 

When `Context.embedded?` is true and no `shopify_id_token` is supplied, execution falls into the `else` branch, checks only for cookie *presence*, and returns `cookie_session_id(cookies)` — the raw cookie string, with no call to `Auth::JwtPayload.new` and no HMAC/signature check of any kind: [2](#0-1) 

The values this gem itself produces for that ID are deterministic and derivable from public information: [3](#0-2) 

`jwt_session_id(shop, user_id)` = `"#{shop}_#{user_id}"` and `offline_session_id(shop)` = `"offline_#{shop}"`. The shop's `.myshopify.com` domain is not secret, and online-session user ids are small, sequential/enumerable integers. This means the "secret" a legitimate browser holds (the cookie value) is not actually secret at all — it's a computable string — so any unprivileged attacker can construct `Cookie: shopify_app_session=shop-b.myshopify.com_999` for an arbitrary victim shop/user without ever having interacted with that shop.

The `SessionCookie` struct itself is a plain value object with no signing/MAC support: [4](#0-3) 

Nothing in `current_session_id` (embedded or non-embedded branch) verifies that the cookie value was actually issued by the app to that browser — it is used verbatim as the key to fetch the stored `Session` (and its `access_token`) from session storage. Since the ID format is public/derivable, this is not merely "trusting client input for a session lookup" (which is normal when the ID is a high-entropy random token) — it's trusting a *guessable* value, which collapses the security of the entire mechanism for both the embedded fallback and the non-embedded path.

None of the existing guards intervene: `Context.embedded?` only selects which branch runs, it does not gate the cookie branch on any signature; `Auth::JwtPayload`'s `aud`/`dest` checks are bypassed entirely since `JwtPayload.new` is never invoked on this path; `HmacValidator` and `ShopValidator` are unrelated to this code path (they apply to OAuth callbacks/webhooks, not to session lookup).

### Impact Explanation
If session storage returns a full `Session` object (including `access_token`) keyed purely by this attacker-computable string, an unprivileged attacker gains cross-tenant access to another merchant's stored access token/session by simply guessing the shop domain (often public/marketing-known) and a small integer user id — no credentials, no secrets, no interaction with the victim required. This is repeatable against arbitrary shops/users and matches the Critical "cross-tenant access" category.

### Likelihood Explanation
Preconditions: an embedded app using the documented JWT-with-cookie-fallback pattern, and — critically — a session storage backend that returns real session data for any ID that happens to match its keyspace, without also verifying that the requester legitimately holds that specific cookie (e.g., no additional secret component embedded in the cookie value, no server-side binding of cookie to a random nonce). Given the ID format is fully deterministic and gem-produced, feasibility is high and cost to the attacker is trivial (a single crafted HTTP header, no secrets, no privileged access).

### Recommendation
Do not use the deterministic `"#{shop}_#{user_id}"` / `"offline_#{shop}"` strings as the literal cookie value trusted for session lookup. Either (a) store a separate, high-entropy, unguessable session-store key in the cookie (decoupled from the human-readable session id), or (b) sign/MAC the cookie value (e.g., HMAC with `api_secret_key`) and verify the MAC in `cookie_session_id` before trusting it, mirroring the JWT branch's cryptographic verification.

### Proof of Concept
```ruby
# test/utils/session_utils_test.rb (new test)
def test_cookie_fallback_trusts_forged_predictable_session_id_when_embedded
  ShopifyAPI::Context.stubs(:embedded?).returns(true)
  ShopifyAPI::Auth::JwtPayload.expects(:new).never

  forged_cookie_value = "shop-b.myshopify.com_999" # attacker-computed: shop domain is public, 999 is a guessed user id
  cookies = { ShopifyAPI::Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME => forged_cookie_value }

  session_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, true)

  assert_equal forged_cookie_value, session_id
  # demonstrates: no signature/MAC check, no JwtPayload verification,
  # ID accepted verbatim and equal to a value the attacker computed with no secret material
end
```
This confirms the equality `cookie_session_id(cookies) == "shop-b.myshopify.com_999"` holds with `Auth::JwtPayload.new` never invoked, i.e., no cryptographic binding between the returned session id and any proof that the requester is the legitimate holder of shop-b's session.

          if Context.embedded?

              session_id_from_shopify_id_token(id_token: id_token, online: online)

          end
        end
