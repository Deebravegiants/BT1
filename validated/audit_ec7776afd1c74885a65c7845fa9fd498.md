### Title
Unlocked-check race in `addSeed` allows seed import to complete after a concurrent `lock()` - ([File: features/wallet/module/wallet.js])

### Summary
`Wallet#addSeed` checks lock state once via `#assertWalletIsUnlocked()` at entry, then performs several `await`ed operations before writing to storage and the keychain. Because `addSeed` is not concurrency-guarded (unlike `create`/`import`, which use `makeConcurrent`), a concurrently issued `wallet.lock()` can flip `#isLocked` to `true` and call `#keychain.removeAllSeeds()` while `addSeed` is still in-flight, after which `addSeed` resumes and pushes seed data into storage (`#setExtraSeeds`) and re-adds the seed to the keychain via `this.#keychain.addSeed(data.seed)` — completing the seed import despite the wallet being locked.

### Finding Description
`addSeed` in [1](#0-0)  awaits `#assertWalletIsUnlocked()` only at the very start, then performs multiple further `await`s (`mnemonicToSeed`, `getSeedId`, `#primarySeedIdAtom.get()`, `#getExtraSeeds()`, `#setExtraSeeds()`, `#seedMetadataAtom.set()`, `#keychain.addSeed()`) with no re-check of lock state in between.

`lock` is defined as [2](#0-1) , which sets `#isLocked = true` synchronously and calls `this.#keychain.removeAllSeeds()`.

Unlike `create` and `import`, which are wrapped with `makeConcurrent({ concurrency: 1 })` at [3](#0-2) , `addSeed` and `lock` have no concurrency serialization. Calls into the wallet arrive over RPC (`libraries/json-rpc/index.js`), where `_processCallMethod` dispatches each request to the exposed method independently with no per-instance mutex — so an attacker with RPC access to both `wallet.addSeed` and `wallet.lock` can fire them concurrently. If `lock()` executes after `#assertWalletIsUnlocked()` has already resolved `false` but before `addSeed`'s later writes complete, `addSeed` will finish writing `extraSeeds`/metadata to storage and re-insert the seed into the keychain via `#keychain.addSeed(data.seed)`, even though the wallet's `#isLocked` flag (and any UI reflecting it) shows "locked."

### Impact Explanation
This violates the "locked means locked" invariant: seed material import (persisting an extra seed's metadata/encrypted blob and loading it into the live in-memory keychain) can succeed after the wallet has been told to lock and while the UI/API reports a locked state. This is a state/authorization-boundary violation on wallet secret material rather than a pure cosmetic bug — an attacker-controlled dapp/RPC caller can persist and activate seed data outside of the intended locked-wallet trust boundary.

### Likelihood Explanation
Requires only that an unprivileged caller can invoke `wallet.addSeed` and `wallet.lock` via the exposed RPC/API, which is standard reachable surface (`sdks/headless/src/api/index.js` exposes `wallet.addSeed`/`wallet.lock`). No privileged state, keys, or social engineering needed — a straightforward `Promise.all([wallet.addSeed(...), wallet.lock()])` timed to land `lock()`'s synchronous flag flip in the middle of `addSeed`'s async chain is sufficient, and is repeatable since the underlying code has no synchronization primitive preventing it.

### Recommendation
Serialize `addSeed` (and `removeManySeeds`) with the same `makeConcurrent({ concurrency: 1 })` pattern used for `create`/`import`, and additionally re-check `#assertWalletIsUnlocked()` immediately before the final storage/keychain writes (or use a monotonically-incrementing lock "epoch" captured at entry and verified before commit) so that a `lock()` occurring mid-flight aborts the pending `addSeed` instead of allowing it to complete.

### Proof of Concept
Integration test: instantiate `Wallet` with a fake keychain/storage, call `unlock()`, then run `Promise.all([wallet.addSeed({ mnemonic, label, compatibilityMode }), wallet.lock()])` where the fake keychain's `removeAllSeeds` synchronously flips lock state before `addSeed`'s pending `#setExtraSeeds`/`#keychain.addSeed` resolve. Assert that either: (a) `addSeed` throws because the wallet became locked mid-operation, or (b) if it resolves successfully, `wallet.isLocked()` must be `false` at that point — i.e., assert `!(await wallet.isLocked() === true && (await wallet.getExtraSeedIds()).includes(seedId))`, proving no post-lock persistence of seed data occurs. In the current implementation this assertion fails, demonstrating the race.
