### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The `shop-domain` (and `topic`, `webhook-id`, `api-version`) HTTP headers are read directly from unauthenticated request headers and passed straight into `WebhookMetadata`, which app handlers use to identify which tenant/shop the event belongs to. The `shop` field is never included in the signed payload, so the binding `hmac_verified_shop == shop_used_by_handler` does not hold.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256` header: [1](#0-0) 

`Registry.process` validates this HMAC and then immediately trusts the unauthenticated `request.shop` header to build `WebhookMetadata`, which is handed to the app's handler as the tenant identifier: [2](#0-1) 

`shop` is read directly from the `shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the HMAC: [3](#0-2) 

Compare this to `Auth::Oauth::AuthQuery`, where the equivalent `shop` value is explicitly folded into `to_signable_string` and therefore is bound by the HMAC: [4](#0-3) 

No such binding exists for webhooks. `HmacValidator.validate` compares `computed_signature` (over `verifiable_query.to_signable_string`, i.e. only the body) against the received HMAC: [5](#0-4) 

The documented handler contract explicitly relies on `data.shop` as the tenant identifier for subsequent processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), confirming that `shop` is treated as an authenticated, trusted value by consuming applications, when in fact it is not authenticated by this gem at all: [6](#0-5) 

**Root cause / equality that should hold but doesn't**: `hmac_verified(raw_body) == true` should imply `shop_header` is also verified, i.e. `shop_bound_by_hmac == shop_used_by_handler`. In this code, HMAC validation only proves `raw_body` was signed by the app's `client_secret`; it proves nothing about which shop the header claims to be. Any attacker who can obtain one valid `(raw_body, hmac)` pair for their own (attacker-owned/installed) shop — which is trivial since the attacker can install the app on their own store and receive a real, validly-signed webhook — can replay that exact body+signature to the app's webhook endpoint while substituting an arbitrary `shop-domain` header (e.g. a victim shop domain the attacker has merely observed, such as from a public storefront URL). `HmacValidator.validate` still returns `true` because it never inspects the `shop` header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from the victim shop.

### Impact Explanation
This breaks the cross-tenant isolation boundary that the webhook `shop` field is documented and relied upon to provide: consuming applications use `data.shop` to route/attribute incoming order, customer, or product data to the correct merchant record. An attacker (any merchant who can install the app on their own store — an "unprivileged" actor relative to other tenants) can forge events attributed to a different shop, injecting attacker-controlled body content associated with a victim shop's identity. Depending on how the host app uses `data.shop` (e.g., to look up per-shop database records, look up sessions, or trigger per-shop side effects), this enables cross-tenant data confusion/injection — meeting the Critical "cross-tenant access" bar defined in scope.

### Likelihood Explanation
Moderate-to-high: no secrets are required beyond having (or being able to install) the app on any single shop to obtain one legitimate `(body, hmac)` pair; header replacement on an HTTP request is trivial for any actor able to send arbitrary HTTP requests to the app's public webhook endpoint. The `shop`, `topic`, `webhook-id`, and `api-version` headers are all read verbatim from the request with zero cryptographic verification, as shown in `shopify_header`: [7](#0-6) 

### Recommendation
Bind the `shop-domain` header (and ideally `topic`/`webhook-id`) into the signed material verified for webhooks, or otherwise cross-check the header's shop against a value derived from data the gem can independently trust (e.g., require callers to pass an expected shop and assert equality before dispatch). At minimum, `Webhooks::Request#to_signable_string` should not be limited to `@raw_body`; the validation logic in `Registry.process` should not treat the `shop` header as trustworthy input to `WebhookMetadata` without an explicit, cryptographically-verified linkage.

### Proof of Concept
1. Attacker installs the target app on their own controlled Shopify store `attacker.myshopify.com` and triggers a webhook event (e.g., `orders/create`). Shopify sends the app a legitimately HMAC-signed request:
   - Headers: `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over raw_body>`
   - Body: `raw_body` (attacker fully controls the order content on their own store, e.g. crafted note/fields via `fields`/`filter` registration options).
2. Attacker captures this exact `raw_body` and `x-shopify-hmac-sha256` value.
3. Attacker replays the identical `raw_body` and `hmac-sha256` header to the same webhook endpoint but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC — validation passes because the body/HMAC pair is untouched: [2](#0-1) 
5. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled `body`, and processes it as if it were a legitimate event from the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
