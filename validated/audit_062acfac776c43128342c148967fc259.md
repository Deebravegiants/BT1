### Title
Unrefunded excess native token permanently stuck in Tron `IntentGatewayV2.placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron-targeted `IntentGatewayV2.placeOrder` function never refunds leftover `msgValue` to the caller after escrowing inputs and paying `order.fees`, unlike the canonical EVM `IntentGatewayV2.placeOrder` implementation, which explicitly refunds unspent native token at the end of the function.

### Finding Description
In the canonical EVM contract, `placeOrder` tracks a local `msgValue` counter that is decremented as native-token inputs and fees are consumed, and any leftover is sent back to `msg.sender`: [1](#0-0) 

The Tron port (`evm/tron/contracts/apps/IntentGatewayV2.sol`) implements the identical `msgValue` bookkeeping pattern — decrementing it for predispatch native transfers, for native input escrow, and for the fee swap/transfer — but the function ends immediately after the fee-escrow block with no corresponding refund of the remaining `msgValue`: [2](#0-1) 

Concretely: `uint256 msgValue = msg.value;` is declared, used and decremented throughout the function (predispatch native transfer at line 400, native-input escrow at line 457, fee swap at line 474-482), but its final value is discarded — the function goes straight to `emit OrderPlaced(...)` at line 490 without ever calling anything to return the leftover ETH/TRX to `msg.sender`. This is analogous to the reported `isToken0Weth` bug in `ArrakisV2Router.sol`: a value computed for the explicit purpose of returning funds to the caller is silently dropped/never acted upon due to a missing statement in the control flow, rather than being properly consumed.

### Impact Explanation
Any user who calls `placeOrder` with `msg.value` greater than the sum required for predispatch native legs, native input assets, and the native-token fee swap will have the excess permanently locked in the `IntentGatewayV2` contract on Tron. There is no `_sendValue`/refund call and no user-facing mechanism to reclaim this excess — it is not tracked as escrow (`_orders` mapping) tied to any commitment, so `cancelOrder`/`withdraw` paths cannot return it either. This is a direct, unbacked loss of user funds reachable by any unprivileged caller in a single transaction (a submitted `placeOrder` call), matching the "concrete theft or permanent freezing of funds" bar.

### Likelihood Explanation
High. Overpaying `msg.value` is a common and easily-triggered scenario (e.g. SDK/off-chain quote drift, gas-estimation buffers, or a user simply sending a safety margin as demonstrated by the analogous test `testPlaceOrder_RefundsExcessNativeToken` for the EVM contract). Since the Tron variant is otherwise a near-identical copy of the EVM contract (including the `msgValue` decrementing logic), it is very likely to be hit in normal operation whenever this Tron deployment is used with native-token order legs.

### Recommendation
Mirror the EVM contract's behavior: after the fee-escrow block, add a refund of any leftover `msgValue` to `msg.sender` (e.g. `if (msgValue > 0) { (bool sent,) = msg.sender.call{value: msgValue}(""); if (!sent) revert InsufficientNativeToken(); }` or via a shared `_sendValue` helper), consistent with `evm/src/apps/IntentGatewayV2.sol` lines 394-397.

### Proof of Concept
1. User calls `placeOrder{value: X}(order, graffiti)` on the Tron `IntentGatewayV2` where `order.inputs` includes a native-token (`token == address(0)`) leg requiring amount `A < X`, and `order.fees == 0` (or fees paid in fee-token/native but still leaving residual `msgValue`).
2. Inside `placeOrder`: `msgValue = X`; the native input loop decrements `msgValue -= A`, leaving `X - A` unused.
3. Since `order.fees == 0`, the fee-escrow block at lines 471-488 is skipped entirely.
4. Execution proceeds directly to `emit OrderPlaced(...)` at line 490 and returns — the `X - A` excess TRX/native value remains stuck in the contract's balance with no accounting or refund path.
5. Compare against `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` `testPlaceOrder_RefundsExcessNativeToken`, which asserts the EVM contract *does* refund this excess — the Tron contract has no equivalent test coverage or refund logic, confirming the divergence. [3](#0-2)

    /// @notice Excess msg.value beyond native input legs is refunded to the user.
    function testPlaceOrder_RefundsExcessNativeToken() public {
        uint256 inputAmount = 1 ether;
        uint256 overpayment = 0.5 ether;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(0), amount: inputAmount}); // native ETH

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: 1000 * 1e6});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        uint256 userBalBefore = user.balance;

        vm.prank(user);
        intentGateway.placeOrder{value: inputAmount + overpayment}(order, bytes32(0));

        // User should only have spent inputAmount, overpayment refunded
        assertEq(user.balance, userBalBefore - inputAmount, "Overpayment should be refunded");
        assertEq(address(intentGateway).balance, inputAmount, "Gateway should only hold escrowed amount");
    }
