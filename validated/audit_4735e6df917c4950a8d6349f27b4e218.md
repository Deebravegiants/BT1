### Title
Webhook shop/topic identity forgeable because HMAC signs only the request body, not the identifying headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `HmacValidator.validate` verifies the HMAC exclusively against that body. The `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` treats as authoritative for routing and tenant attribution are read straight from unauthenticated HTTP headers that are never included in the signed bytes.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only `@raw_body` is returned. `HmacValidator.validate` computes the HMAC over exactly this signable string and compares it to the `hmac-sha256` header: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all parsed from separate headers that are not part of `to_signable_string`: [3](#0-2) 

`Registry.process` uses the unverified `topic` header to select which handler runs, and forwards the unverified `shop` header to the handler as the tenant identity, while the only thing actually proven by the HMAC is that the raw body bytes were produced by Shopify: [4](#0-3) 

This breaks the binding `verified_bytes == identity_claimed_bytes`. The HMAC proves "this body byte-string came from Shopify (signed with `api_secret_key`)," but the library lets an attacker independently choose which `shop`/`topic` that verified body is attributed to, since those fields are parsed but never verified.

### Impact Explanation
Any unprivileged internet user can install the target app on their own (attacker-controlled) development shop — no special privilege is required to become a merchant and receive real, validly-HMAC-signed webhooks from Shopify for that shop. Once they capture one such genuine `(raw_body, hmac)` pair, they can replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain and/or the `x-shopify-topic` header with a different topic registered by the same app (e.g. `app/uninstalled`, `customers/redact`, `shop/redact`). `HmacValidator.validate` still returns `true` because the signed bytes (the body) are unchanged, but `Registry.process` will route to the handler for the forged topic and pass the forged shop through `WebhookMetadata`. Any host application that relies on `data.shop` from this gem's `WebhookMetadata` to select which tenant's session/data to act on (exactly the pattern this gem exposes and expects, per `test/webhooks/registry_test.rb`'s `test_process` assertions on `data.shop`) will act on the wrong tenant — e.g. deleting or redacting a different shop's data, or triggering the mandatory `app/uninstalled` cleanup logic for a shop that never uninstalled. This is a cross-tenant action triggered purely by header manipulation, meeting the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Exploitation requires no possession of `api_secret_key` or any Shopify-issued credential belonging to the victim: the attacker only needs (a) their own free/dev shop with the app installed to obtain one legitimately-signed webhook body, and (b) the ability to POST that captured body/hmac pair with modified headers directly to the app's public webhook endpoint. Both are available to any unprivileged internet user, and the vulnerable code path (`Registry.process` / `Request#to_signable_string`) is exercised on every webhook delivery, so likelihood is high once discovered.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting them for routing/tenant attribution in `Registry.process`. At minimum, `Request#to_signable_string` should not be the sole basis for header trust — the gem should document/enforce that `shop` and `topic` are only as trustworthy as the raw body's origin, and host apps should be warned not to use these fields as an authorization boundary without additional verification (e.g. cross-checking `shop` against an existing valid session for that shop before performing any destructive/tenant-scoped action).

### Proof of Concept
```ruby
# 1. Attacker installs app on their own shop "attacker-shop.myshopify.com"
#    and receives a genuine, Shopify-signed webhook, e.g. for "orders/create":
raw_body        = '{"id":1,"note":"hi"}'
genuine_hmac_b64 = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)
)

# 2. Attacker replays the exact same body/hmac to the app's webhook endpoint,
#    but swaps the shop-domain and topic headers:
forged_headers = {
  "x-shopify-topic"        => "app/uninstalled",              # different topic than originally signed for
  "x-shopify-hmac-sha256"  => genuine_hmac_b64,                # unchanged - still matches raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com",     # attacker-chosen victim tenant
  "x-shopify-webhook-id"   => "attacker-chosen-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# 3. HMAC validation still passes because only raw_body is checked:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process routes to the "app/uninstalled" handler and reports
#    shop == "victim-shop.myshopify.com" to the handler, even though Shopify
#    never actually sent this event for that shop:
ShopifyAPI::Webhooks::Registry.process(request)
```
