Analysis of the RaspAP code-injection bug class (unauthenticated code execution via a poorly-gated processing function) maps onto Hyperbridge's `CallDispatcher` contract, which executes attacker-suppliable calls with zero caller restriction and is shared across multiple apps.

### Title
Unauthenticated `CallDispatcher.dispatch()` allows any address to drain residual funds left in the shared dispatcher - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch()` has no access control whatsoever — any external account can call it directly with an arbitrary ABI-encoded `Call[]` array, causing the dispatcher to execute calls to attacker-chosen targets with attacker-chosen data and value [1](#0-0) . The `ICallDispatcher` interface itself documents that it is meant to "dispatch untrusted call(s)" [2](#0-1) , but the security model rests entirely on the assumption that nothing of value is ever left sitting in the dispatcher between calls — an assumption the code does not enforce.

### Finding Description
`CallDispatcher` is deployed once and shared as `_params.dispatcher` across `IntentGatewayV2` (predispatch/postdispatch order calldata) and other apps such as `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata execution [3](#0-2) . During `placeOrder`/`fillOrder`, tokens are transferred into the dispatcher, arbitrary calldata is executed against it, and only the tokens explicitly tracked by the calling contract are swept back out:

```solidity
function _execute(Order calldata order, uint256 outputsLen) internal {
    ...
    ICallDispatcher(dispatcher).dispatch(order.output.call);
    // sweep loop only iterates order.output.assets[0..outputsLen)
``` [4](#0-3) 

If the executed calldata causes the dispatcher to receive a token or ETH amount that is *not* part of `order.output.assets` (e.g. a reward token from a DEX swap, a fee refund, or excess native token sent directly via the dispatcher's `receive()` [5](#0-4) ), that balance is never swept and remains permanently held by the shared `CallDispatcher` contract. Because `dispatch()` has no `onlyOwner`/`onlyGateway` guard, **any unprivileged actor can subsequently call `CallDispatcher.dispatch()` directly** with a `Call{to: token, value: 0, data: transfer(attacker, balance)}` and drain that residual balance for themselves, regardless of which app or user originally caused the funds to land there.

The documentation for the token-bridge integration explicitly flags this exact hazard without acknowledging that the fix (exact approvals) does not address the missing access control on `dispatch()` itself: "Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution." [6](#0-5) 

### Impact Explanation
Any value (native token or ERC-20) that ends up sitting in the shared `CallDispatcher` — whether from an incomplete sweep, a swap that returns an untracked reward token, ETH sent directly to the contract, or a partially-failed cross-app flow — is permanently and immediately stealable by any address, since `dispatch()` places no restriction on the caller. This is a direct, unauthenticated path to theft of funds that legitimately belong to users/protocol (dust, refunds, unswept balances), reachable from a single transaction with no special privilege, consistent with concrete theft of funds.

### Likelihood Explanation
The dispatcher is shared infrastructure invoked by every predispatch/postdispatch calldata execution across `IntentGatewayV2` and the HFT token bridge apps, so any deviation between what a calling contract's sweep loop tracks and what the executed calldata actually returns to the dispatcher creates an exploitable window. Given the variety of DeFi calls the dispatcher is designed to execute (Uniswap swaps, lending deposits, arbitrary composable calls), unaccounted-for token receipts (LP dust, referral/reward tokens, rounding remainders, excess native token) are a realistic and recurring occurrence, and the exploit itself (a bare call to `dispatch()`) requires no special conditions once such a balance exists.

### Recommendation
Restrict `CallDispatcher.dispatch()` to an allowlist of authorized callers (the registered gateway/HFT contracts), or redesign the pattern so a fresh, disposable dispatcher/proxy is used per call rather than a shared singleton that can accumulate residual balances. Additionally, ensure calling contracts sweep the dispatcher's *entire* balance of any token that could plausibly be received (not just the tokens explicitly listed in `order.output.assets`), and consider adding a permissionless "sweep to protocol treasury" function so dust cannot be siphoned by an arbitrary caller ahead of the intended beneficiary.

### Proof of Concept
1. A solver fills an order whose `order.output.call` swaps output tokens via a DEX that also pays out a small reward/referral token not listed in `order.output.assets`.
2. `_execute` sweeps only the tracked output tokens back to the gateway; the reward token balance remains on `CallDispatcher` [7](#0-6) .
3. Any third party calls `CallDispatcher.dispatch(abi.encode([Call({to: rewardToken, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance)})]))` directly — this succeeds because `dispatch()` performs no caller check [8](#0-7) , transferring the stranded tokens to the attacker.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires.
