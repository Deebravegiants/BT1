Audit Report

## Title
Value-transferring EVM `CALL`s always classify as `AllowReentry` regardless of stipend gas, defeating the `AllowNext` reentrancy mitigation - ([File: substrate/frame/revive/src/vm/evm/instructions/contract.rs])

## Summary
`run_call` in `substrate/frame/revive/src/vm/evm/instructions/contract.rs` selects reentrancy protection via a tuple `match` on `(value.is_zero(), gas_limit == CALL_STIPEND)`, with the `(false, _)` arm listed first [1](#0-0) . Because Rust evaluates match arms top-down, any call with `value != 0` is unconditionally routed to `ReentrancyProtection::AllowReentry` with `add_stipend = true`, and the `gas_limit == CALL_STIPEND` check is never reached for value-transferring calls - defeating the explicit `AllowNext` mitigation that the code's own doc comment says exists specifically for "calls that transfer value but restrict gas so that the callee only has a stipend gas amount" [2](#0-1) .

## Finding Description
`call<E: Ext>` and the other CALL-family opcode handlers (`delegate_call`, `static_call`) forward into `run_call`, which computes `(add_stipend, reentracy)` from a match that places `(false, _) => (true, ReentrancyProtection::AllowReentry)` before the `(_, true) => (true, ReentrancyProtection::AllowNext)` arm [3](#0-2) [1](#0-0) . Since the first component of the match tuple is `value.is_zero()`, any nonzero `value` short-circuits to `(false, _)` regardless of what `gas_limit` is, so the `AllowNext` arm is dead code for `value != 0`.

Per the accompanying PR documentation, real solc-generated `.transfer(amount)`/`.send(amount)` calls with `value > 0` actually pass `gas_limit = 0` and rely on the EVM's automatic 2300 stipend addition, while the explicit `gas_limit == 2300` pattern is only injected by solc for the `value == 0` corner case (`.transfer(0)`/`.send(0)`) [4](#0-3) . This means the current match arm ordering makes `AllowNext` reachable only for the zero-value corner case (which carries no fund-transfer risk), never for the actual `.transfer()`/`.send()` real-value pattern the mitigation's doc comment explicitly targets [2](#0-1) .

`add_stipend = true` still causes `determine_call_stipend::<T>()` — a nonzero weight derived from `EVMGas(CALL_STIPEND)` plus `DepositEvent` weight — to be added to the callee's frame budget for both the `AllowReentry` and `AllowNext` arms [5](#0-4) . With `AllowReentry` selected instead of `AllowNext`, `Stack::call` never restricts `top_frame_mut().allows_reentry`, so `self.allows_reentry(&dest)` never blocks a reentrant call back into the caller's own frame while it is still active [6](#0-5) .

The doc comment for `AllowNext` explicitly acknowledges that revive's weight/gas scale differs from Ethereum's, so the assumption that "2300 gas is insufficient for a further call" does not automatically hold, and the mitigation was added specifically to enforce this explicitly for stipend-limited transfers [2](#0-1) . Because the match arm ordering bypasses this mitigation for every `value != 0` call, this explicit protection is dead for the exact scenario it was designed to cover.

## Impact Explanation
Contracts written against Solidity's `.transfer()`/`.send()` conventions, which are commonly used specifically because 2300-gas calls are believed to prevent reentrancy, receive no `AllowNext` reentrancy lock in revive's EVM execution path for any nonzero-value call. If revive's weight accounting for the stipend ever provides enough usable weight for the callee to issue a further call (a real risk explicitly called out in the `AllowNext` doc comment given gas-scale differences), a callee could reenter the caller's frame before the caller's own post-call bookkeeping completes, undermining checks-effects-interactions assumptions baked into Solidity contracts relying on stipend-based reentrancy safety.

## Likelihood Explanation
This is reachable by any unprivileged user deploying ordinary EVM contracts and issuing standard `CALL`/`STATICCALL` opcodes with `value != 0` — no special privilege, governance action, or victim mistake beyond writing normal `.transfer()`/`.send()`-style Solidity code is required. The match arm ordering guarantees the `(false, _)` branch is taken for every nonzero-value call, making the bypass deterministic and repeatable, not a narrow edge case.

## Recommendation
Reorder the heuristic so the `gas_limit == CALL_STIPEND` check is evaluated independently of `value.is_zero()`, e.g., check for the stipend gas amount first and apply `AllowNext` whenever `add_stipend` is true, regardless of whether `value` is zero. More broadly, revisit whether `AllowReentry` is ever appropriate when `add_stipend` is true, since revive's stipend maps to real usable weight unlike Ethereum's provably-insufficient 2300 gas.

## Proof of Concept
1. In `substrate/frame/revive/src/vm/evm/instructions/contract.rs`, note that for any call with `value != 0`, the `match (value.is_zero(), gas_limit == CALL_STIPEND)` always hits `(false, _) => (true, ReentrancyProtection::AllowReentry)` at line 196, before the `(_, true)` arm at line 201 can ever be evaluated.
2. Extend the existing `substrate/frame/revive/src/tests/stipends.rs` test suite (which already contains `evm_call_stipend_prevents_transfer_reentrancy`/`evm_call_stipend_prevents_send_reentrancy`) with a unit test that instruments/logs the `reentracy` value chosen by `run_call` for a `value != 0` call with `gas_limit == CALL_STIPEND` (2300), asserting it resolves to `AllowReentry` instead of `AllowNext`.
3. Add a fuzz/integration test sweeping `gas_limit` values with `value = 1` to confirm the reentrancy classification is always `AllowReentry` for nonzero value, contradicting the intended stipend-based protection described in the `AllowNext` doc comment.

fn determine_call_stipend<T: Config>() -> Weight {
	let gas_weight = <EVMGas as Token<T>>::weight(&EVMGas(CALL_STIPEND));
	let event_weight = <RuntimeCosts as Token<T>>::weight(&RuntimeCosts::DepositEvent {
		num_topic: STIPEND_LOG_TOPICS,
		len: STIPEND_LOG_DATA_LEN,
	});
	gas_weight.saturating_add(event_weight)
}
