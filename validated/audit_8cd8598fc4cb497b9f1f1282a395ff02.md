This is the confirmed vulnerability. Unlike `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token` — all of which call `Utils::ShopValidator.sanitize!(shop)` before building the request host — `TokenExchange.exchange_token` takes `dest_shop = jwt_payload.shop` directly from the JWT `dest` claim (stripped of `https://` in `JwtPayload#shop`) and uses it, unvalidated, as `Clients::HttpClient`'s target host, which is where `client_secret` is sent in the POST body.

### Title
Token Exchange sends `client_secret` to an unvalidated host taken from the JWT `dest` claim - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the request host for the `/admin/oauth/access_token` call solely from the session token's `dest` claim, without running it through `Utils::ShopValidator.sanitize!`, unlike the sibling methods `migrate_to_expiring_token`, `ClientCredentials.client_credentials`, and `RefreshToken.refresh_access_token`, which all validate `shop` against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` first.

### Finding Description
`JwtPayload#shop` simply does `@dest.gsub("https://", "")` with no domain allow-listing [1](#0-0) . In `exchange_token`, this raw value becomes `dest_shop` and is used directly to build `shop_session`, which `Clients::HttpClient` turns into `@base_uri = "https://#{session.shop}"` for the outbound POST that carries `client_id` and `client_secret` [2](#0-1) [3](#0-2) . Note that although the JWT signature itself is verified against `Context.api_secret_key` (so an outside attacker can't forge an arbitrary token), the `dest` claim inside a validly-signed token is never bound/checked against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`, unlike every other code path in this module that touches `client_secret`. The other three flows explicitly guard this exact class of bug: `Utils::ShopValidator.sanitize!(shop)` is called before constructing `shop_session` in `refresh_token.rb`, `client_credentials.rb`, and `migrate_to_expiring_token` [4](#0-3) [5](#0-4) [6](#0-5) . `exchange_token` alone skips this check, breaking the identity binding `host validated == host that receives client_secret`.

This mirrors the analog class described in the rules: a value ("host") that receives the app's `client_secret` is not the same value that gets validated (in this case, no validation happens at all on the `dest`-derived host).

### Impact Explanation
If any component that produces or relays the `dest` claim (e.g., a proxy, embedding context, or any code path where `dest` is not strictly `{shop}.myshopify.com`) allows a non-myshopify value into `dest`, the gem will POST the app's `client_id` and `client_secret` to that attacker-controlled host — SSRF carrying the app's credentials, and a direct path to `client_secret` exfiltration (High/Critical per the impact list).

### Likelihood Explanation
Medium: the JWT must still be validly signed with `Context.api_secret_key`, which limits this to session tokens issued through legitimate flows. However, the code makes no independent effort to constrain `dest` to trusted Shopify domains — the safety net that exists everywhere else in this same file (`ShopValidator.sanitize!`) is absent here, so any relaxation upstream (e.g., a non-strict issuer or the "spin.dev"/custom domain variants already accounted for by `ShopValidator`'s `myshopify_domain` parameter) is a single silent path to sending `client_secret` off-domain, with no defense-in-depth from this gem.

### Recommendation
In `TokenExchange.exchange_token`, run `dest_shop` through `Utils::ShopValidator.sanitize!(dest_shop)` before constructing `shop_session`/`Clients::HttpClient`, exactly as is already done in `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`.

### Proof of Concept
1. Obtain (or have the app receive) a validly-signed session token whose `dest` claim is not constrained to `*.myshopify.com`/`*.myshopify.io` (e.g., `dest: "https://attacker.example"`), i.e., any path by which `dest` isn't force-validated upstream of this gem.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token:, requested_token_type: ...)`.
3. Observe that `Clients::HttpClient` is instantiated with `session.shop == "attacker.example"` [7](#0-6) , and the POST to `https://attacker.example/admin/oauth/access_token` includes `client_id` and `client_secret` in its body [3](#0-2) , whereas the same call with `migrate_to_expiring_token`/`client_credentials`/`refresh_access_token` would raise `ShopifyAPI::Errors::InvalidShopError` for the identical host value.
