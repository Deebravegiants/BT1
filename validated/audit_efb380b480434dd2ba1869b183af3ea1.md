### Title
XRPL PoA withdrawal memo is built via unescaped colon-join, letting a `destinationMemo` containing `:` corrupt the destination tag - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts`)

### Summary
`createWithdrawMemo` builds the on-chain memo as `["WITHDRAW_TO", address, xrpMemo].join(":")` with no validation or escaping of colons inside `xrpMemo`. `PoaBridge.validateWithdrawal` only checks that `destinationMemo` is truthy when a destination tag is required, never that it is colon-free (or numeric), so a caller-supplied memo like `"123:456"` produces the ambiguous string `WITHDRAW_TO:rAddr:123:456`, which is indistinguishable from a memo of `"123"` with an extra field, breaking the (address, memo) pair the caller intended to send.

### Finding Description
The equality that must hold is: **the (destinationAddress, destinationMemo) tuple the caller passed into `createWithdrawIntentPrimitive` must equal the (address, tag) tuple the PoA bridge indexer reconstructs from the colon-delimited memo string on-chain.**

- `createWithdrawIntentPrimitive` ( [1](#0-0) ) passes `destinationAddress` and `destinationMemo` straight into `createWithdrawMemo`.
- `createWithdrawMemo` ( [2](#0-1) ) does `memo.push(xrpMemo)` then `memo.join(":")` with zero escaping of `:` inside `xrpMemo`.
- `PoaBridge.validateWithdrawal` ( [3](#0-2) ) only enforces `if (requireDestinationTag && !args.destinationMemo) throw ...` — it never validates the *content* of `destinationMemo` (e.g., that it's digits-only, or free of `:`).
- Nowhere else in the reachable path (`validateAddress`, `compareAddresses`, `supports()`) is the memo's character set constrained.

An attacker (an ordinary user, or a counterparty string forwarded by an integrator) supplies `destinationMemo = "123:456"` for an XRPL withdrawal. The resulting on-chain memo field is `WITHDRAW_TO:rAddr:123:456`. Since the format has no length prefix or escaping, a colon-splitting parser downstream cannot tell whether the intended destination tag was the single value `123:456` or the two-field sequence `123`, `456` — the four-field string is ambiguous versus the expected three-field `WITHDRAW_TO:address:memo` schema.

### Impact Explanation
The memo field carries the XRPL destination tag, which exchanges use to route incoming funds to the correct sub-account inside a shared hot wallet. If the bridge-side indexer's parser resolves the ambiguous colon-joined string to a destination tag different from what the caller intended (e.g., truncating to `123` and dropping `456`, or failing to parse and defaulting to no tag/an incorrect tag), the withdrawn funds land on the correct XRPL address but are tagged incorrectly. Since XRPL destination tags are used by custodians to attribute deposits to specific customer accounts, a wrong tag on a shared/exchange hot wallet address means funds are unrecoverable by the original sender through this SDK — matching the "funds delivered to a wrong address/contract with no recovery" Critical category, since the effective beneficiary attribution is corrupted.

### Likelihood Explanation
Preconditions: withdrawing `nep141:xrp.omft.near` (or other XRP-family asset) to an XRPL address that requires a destination tag, with attacker-supplied `destinationMemo` containing a colon. This requires no privileges — any SDK caller can invoke `createWithdrawIntentPrimitive`/`PoaBridge.createWithdrawalIntents` with an arbitrary `destinationMemo` string, and `validateWithdrawal` does not reject colon-containing memos. This is trivially repeatable per call at zero attacker cost, though the actual definitiveness of harm depends on how the off-chain PoA bridge indexer parses the string (i.e., whether it naively splits on the first two colons or fails safe) — that indexer-side behavior is outside this repo and cannot be confirmed by static analysis here alone.

### Recommendation
In `createWithdrawMemo` / `validateWithdrawal`, reject or escape any `destinationMemo` containing a `:` before constructing the memo string, or validate that for XRPL destination tags, `destinationMemo` matches a strict numeric pattern (`/^\d+$/`) as required by the XRPL destination-tag spec (tags are unsigned 32-bit integers), throwing an explicit error otherwise instead of silently joining.

```ts
import { describe, it, expect } from "vitest";
import { createWithdrawIntentPrimitive } from "./poa-bridge-utils";

describe("createWithdrawIntentPrimitive - XRPL memo ambiguity", () => {
  it("produces an ambiguous memo when destinationMemo contains a colon", () => {
    const intent = createWithdrawIntentPrimitive({
      assetId: "nep141:xrp.omft.near",
      destinationAddress: "rDsbeomae4FXwgQTJp9Rs64Qg9vDiTCdBv",
      destinationMemo: "123:456",
      amount: 1000n,
    });

    // Expected schema: WITHDRAW_TO:<address>:<memo> => 3 fields
    const fields = intent.memo.split(":");
    expect(fields.length).toBeGreaterThan(3); // proves ambiguity: 4 fields instead of 3
    expect(intent.memo).toBe(
      "WITHDRAW_TO:rDsbeomae4FXwgQTJp9Rs64Qg9vDiTCdBv:123:456",
    );
  });
});
```
This test mocks no HTTP (pure function) and demonstrates that the caller's exact `(address, memo)` tuple — `("rDsbeomae4FXwgQTJp9Rs64Qg9vDiTCdBv", "123:456")` — cannot be losslessly reconstructed from `intent.memo` using the documented `:`-delimited schema, since `"123:456"` is indistinguishable from a 2-field remainder `["123","456"]`.

```typescript
function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
```
