### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) fields are trusted for tenant identification without being covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — read from separate, unsigned HTTP headers — are handed to the app's handler as trusted, verified data. This breaks the identity binding that `Registry.process` is documented to guarantee: "verify the request did indeed come from Shopify" is conflated with "the `shop` header can be trusted," when only the body bytes are actually authenticated.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` verifies the HMAC exclusively against that signable string: [2](#0-1) 

Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled straight from HTTP headers that are never included in the signed material: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts these unauthenticated header-derived fields to build `WebhookMetadata`, which is passed to the app's handler as verified data: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` field with no indication to the consumer that it is unauthenticated: [5](#0-4) 

The library's own documentation asserts that `Registry.process` "will verify the request did indeed come from Shopify," and shows `data.shop` being used directly (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`) without any caveat that it is unverified: [6](#0-5) [7](#0-6) 

This is structurally the same class of bug as the reference report: a field that is *acted upon* (here, used for tenant/shop identification and dispatch, analogous to `amountSold` in the Notional report) is not covered by the integrity check that is supposed to bind it to the verified data (analogous to the ETH deposit not matching `trade.limit`). The broken equality is:

`shop used by handler.handle (header-derived) == shop that the HMAC-signed body actually belongs to`

This equality is never checked. Since the webhook HMAC secret (`Context.api_secret_key`) is the app's single client secret shared across *all* merchants who install the app — not a per-shop secret — any shop that has installed the app can capture a validly-signed `(raw_body, hmac)` pair from its own genuine webhook deliveries and replay it against the app's webhook endpoint with a forged `shopify-shop-domain` (and/or `shopify-topic`, `shopify-webhook-id`) header pointing at a different tenant of the same app. `HmacValidator.validate` will pass because it only checks the body bytes, and `Registry.process` will dispatch the payload to the handler tagged with the attacker-chosen `shop`.

### Impact Explanation
This crosses a tenant boundary: an attacker who has legitimate access to their own shop's webhook feed can inject data attributed to another merchant's shop into the host application, because the gem hands the host app a `shop` value it never actually authenticated. Any host application that relies on `WebhookMetadata.shop` (as the documented example does) to route the payload to the correct tenant's records will process/store attacker-controlled data under a different tenant's identity — a cross-tenant data-injection primitive. This matches the "Critical - cross-tenant access" impact category from the rules.

### Likelihood Explanation
Likelihood is moderate-to-high for any app that has at least one hostile or compromised merchant installation: no privileged credentials, TLS interception, or social engineering are required — the attacker only needs to be a normal installed merchant of the target app (an "unprivileged internet user" relative to other tenants) and the ability to send an HTTP POST with custom headers to the app's public webhook endpoint. The vulnerable code path (`Request` + `HmacValidator` + `Registry.process`) is exercised on every webhook delivery and is exactly the code path documented as the intended integration pattern.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., canonicalize headers + body into `to_signable_string`), so that `HmacValidator.validate` fails if any of these fields are altered relative to what Shopify actually sent. At minimum, clearly document that `WebhookMetadata.shop`/`topic`/etc. are derived from unauthenticated headers and that host applications must independently verify `shop` against their own registered-shop list before trusting it for tenant-scoped operations.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on `victim-shop.myshopify.com`, both registered for the `orders/create` topic with the same app (same `client_secret`/`api_secret_key`).
2. Attacker triggers a genuine webhook delivery from Shopify to the app for `attacker-shop.myshopify.com` (e.g., by creating an order), capturing the raw POST body `B` and the valid `X-Shopify-Hmac-Sha256` header `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker replays a POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H, ...})` is constructed: [8](#0-7) 
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B)` against `H`: [9](#0-8) 
6. The handler is invoked with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, so the app processes the attacker's order body under the victim shop's identity — cross-tenant data injection.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
