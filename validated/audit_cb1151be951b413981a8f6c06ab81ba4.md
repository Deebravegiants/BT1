### Title
Wrong decimal scaling in `convert_to_erc20`/`convert_to_balance` allows unbacked cross-chain mint - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token`'s decimal-conversion helpers assume the remote (EVM) chain's decimals are always **greater than or equal to** the local asset's decimals. When that assumption is false — i.e. the local asset has more decimals than the registered EVM token — `saturating_sub` silently clamps the scaling exponent to zero, so no scaling is applied at all. This mirrors the `SecuritizeRedemption.redeem()` bug in the external report: an amount denominated in one token's decimals is used as-is in a context that expects a different decimal denomination, producing amounts that are off by many orders of magnitude.

### Finding Description
`convert_to_erc20` and `convert_to_balance` compute their scaling factor with `erc_decimals.saturating_sub(local_decimals)` / `local_decimals.saturating_sub(erc_decimals)` style logic that only scales in one direction: [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions rely on `saturating_sub`, which returns `0` whenever `local_decimals > erc_decimals`. A `0` exponent means `10^0 = 1`, i.e. **no scaling is applied whatsoever** in that case — the raw numeric value is passed straight through even though the two chains use different decimal precisions.

This is invoked directly from the unprivileged `send` extrinsic: [2](#0-1) 

```rust
let sender: [u8; 32] = who.clone().into();
let amount: u128 = params.amount.into();
let erc20_amount = convert_to_erc20(amount, erc_decimals, decimals);
```

If a token is registered (via `register_token`) with `local_decimals` (e.g. 18, a `pallet-assets` asset or the native currency) greater than the destination chain's registered `erc_decimals` (e.g. 6), then for any user-submitted `send()`:
- The local asset is correctly burned/escrowed for `amount` (in 18-decimal units).
- `convert_to_erc20(amount, 6, 18)` computes `6u8.saturating_sub(18) = 0`, so `erc20_amount = amount * 10^0 = amount` — i.e. the raw 18-decimal-denominated number is placed into the outgoing `Message.amount` field unscaled, instead of being divided by `10^12` to convert to the destination's 6-decimal representation.
- On delivery, the destination `HyperFungibleToken.sol` contract mints exactly `message.amount` (unscaled) to the beneficiary: [3](#0-2) 

```solidity
_mint(beneficiary, message.amount);
...
emit Received({...});
```

The beneficiary is minted `10^12` times more tokens than were escrowed/burned on the source chain — an unbacked mint, directly analogous to the reported bug where a stable-coin amount was computed using the wrong token's decimals, producing a payout `10^12` times too large.

The reverse direction (`on_accept` / `on_timeout` on the substrate side calling `convert_to_balance`) has the symmetric flaw: if `erc_decimals < local_decimals`, no up-scaling occurs when converting an incoming EVM-denominated amount into the local balance, which under-credits recipients relative to what was actually locked on the EVM side (a fund-freezing/loss condition for the substrate-side beneficiary, and a source of accounting mismatch for the escrow backing the bridged supply).

### Impact Explanation
This is a critical unbacked-mint vulnerability reachable by any signed account submitting a single `send()` extrinsic, provided a token is registered (via the privileged `register_token`/`update_token` calls) with local decimals higher than the destination chain's decimals. This is a realistic configuration mistake (e.g. a locally-minted 18-decimal asset bridged to a 6-decimal USDC-style representation on an EVM chain), and once such a token exists, *every* unprivileged user of `send()` can mint arbitrarily inflated balances on the destination chain, or conversely have their `on_accept`/`on_timeout` credit permanently truncated on the substrate side — either theft of protocol-backed value or permanent freezing of a portion of user funds.

### Likelihood Explanation
Likelihood depends on token registration configuration (an admin action), but the vulnerable code path itself requires no special privilege to trigger — a single `send()` call by any user activates the flawed conversion. Since decimal mismatches (6 vs 18, 8 vs 18, etc.) are the normal case for real-world tokens (as acknowledged elsewhere in the codebase, e.g. `BridgeToken.sol`'s explicit 12-vs-18-decimal handling), this is a plausible operational configuration rather than a contrived edge case, and the helper functions provide no validation or revert to prevent it.

### Recommendation
Replace the one-directional `saturating_sub`-based scaling in `convert_to_balance` and `convert_to_erc20` with logic that scales correctly in both directions (multiply when the target has more decimals, divide when it has fewer), matching the pattern already used correctly elsewhere in the codebase (e.g. `VWAPOracle._normalizeAmount`):

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and symmetrically for `convert_to_balance`. Additionally, consider rejecting or explicitly documenting/validating decimal configurations at `register_token`/`update_token` time so silent truncation can never occur.

### Proof of Concept
1. Admin calls `register_token` for asset `X` with `native = false`/`true`, local asset decimals = 18 (e.g. a `pallet-assets` asset or the chain's native currency with `T::Decimals = 18`), and a `ChainConfig` for `StateMachine::Evm(chain)` with `decimals = 6` (matching a 6-decimal ERC20 counterpart).
2. A user calls `send(SendParams { asset_id: X, amount: 1_000_000_000_000_000_000 /* 1 token, 18 decimals */, destination: Evm(chain), ... })`.
3. In `lib.rs::send`, `erc_decimals = 6`, `decimals = 18`; `convert_to_erc20(1e18, 6, 18)` computes `6u8.saturating_sub(18) = 0` ⇒ `erc20_amount = 1e18` (unscaled), instead of the correct `1e18 / 10^12 = 1e6`.
4. The dispatched `Message.amount` therefore encodes `1e18` instead of `1e6`.
5. On the EVM side, once the message is delivered, `HyperFungibleToken.onAccept` calls `_mint(beneficiary, message.amount)` — minting `1e18` raw units of a 6-decimal-denominated token, i.e. `10^12` times the amount that was actually escrowed/burned on the source chain, an unbacked mint of the bridged asset.
