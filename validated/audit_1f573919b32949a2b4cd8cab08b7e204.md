### Title
Stale operator authorization reused across signups without backend re-verification - (File: src/plans/mod.rs)

### Summary
`scan_remaining_qr_codes` and `scan_initial_qr_codes` cache the result of a one-time backend verification of the operator QR-code (`OperatorData`, produced by `verify_operator_qr_code`) and reuse it for any subsequent signup as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, without re-querying the backend. This is structurally the same bug class as the UniV3 oracle issue: a previously-fetched "verified" state is extrapolated forward in time and trusted as still valid, creating a window where a since-revoked/changed authorization is still accepted. [1](#0-0) 

### Finding Description
The signup flow scans an operator QR-code and calls `verify_operator_qr_code`, which performs a backend check (returning `operator_location_data`) before constructing `OperatorData { qr_code, location_data, timestamp: Instant::now() }`. [2](#0-1) 

That `OperatorData` — the artifact representing "the backend confirmed this operator is authorized to run a signup" — is then cached in the `QrCodes` state and, in `scan_remaining_qr_codes`, reused directly for subsequent signups purely based on an elapsed-time check against `operator_qr_expiration_time`, with no re-verification call to the backend:
```
QrCodes::Operator { operator_data }
    if operator_data.timestamp.elapsed() < operator_qr_expiration_time =>
{
    let Some((user_qr_code, user_data, user_qr_code_string)) =
        self.scan_user_qr_code(orb, &operator_data).await?
    ...
``` [3](#0-2) 

The same pattern exists in `scan_initial_qr_codes`, which skips re-scanning/re-verifying the operator entirely if the cached timestamp hasn't expired. [4](#0-3) 

This mirrors the report's root cause precisely: instead of confirming the current state (operator still authorized, location still correct) at the moment it is needed, the code assumes the last known-good verification "still holds" until a fixed time window (`operator_qr_expiration_time`) elapses — exactly like `consult()` assuming the last Uniswap observation is still accurate until a new one arrives. If the operator's authorization is revoked or the operator's account/location is invalidated on the backend during that window (e.g., between two consecutive walk-up signups performed by different operators sharing a session, or after an operator is deactivated for fraud), the orb will keep running signups against the stale, no-longer-valid `OperatorData` for the entire expiration window instead of detecting the change immediately.

### Impact Explanation
`OperatorData` gates the "signup authorization" trust boundary: it is required to proceed to `scan_user_qr_code` and biometric capture. Reusing a stale, backend-unverified authorization for up to `operator_qr_expiration_time` after a single verification means a revoked/deactivated operator (or one whose backend-side authorization state changed) can still push through user signups without the orb detecting it, until the cache naturally expires. This is a misattributed/unauthorized-signup class issue rather than a crash or DoS.

### Likelihood Explanation
The unprivileged-user-facing precondition is limited: it requires that an operator's authorization be revoked or otherwise invalidated at the backend in the middle of the caching window while the physical orb session is left in the `QrCodes::Operator`/`Both` cached state (e.g., due to failed/retried signups or multi-signup sessions), which is a realistic operational scenario for a walk-up kiosk device but is not directly attacker-triggerable by a QR/MECARD payload alone — I could not confirm the exact value or configurability of `operator_qr_expiration_time` (grep matched `src/config.rs` but I was unable to view its content in the remaining budget), so I cannot state how large this window is in practice.

### Recommendation
Re-verify operator authorization with the backend (or at minimum check a lightweight "still authorized" signal) each time cached `OperatorData` is about to be reused for a new signup, rather than trusting elapsed-time alone. If a short cache window is required for UX reasons, keep it minimal and always re-validate before any state-mutating action (starting biometric capture / signup).

### Proof of Concept
Not directly reproducible from static analysis alone: exploitation depends on backend-side operator revocation timing relative to `operator_qr_expiration_time`, which I could not confirm from the available index (this may be a limitation of the codebase index — a full Devin session could inspect `src/config.rs` and `src/backend/config.rs` for the exact value and any backend-side invalidation checks).

    async fn scan_initial_qr_codes(
        &mut self,
        orb: &mut Orb,
        qr_codes: &mut QrCodes,
        self_serve: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<()> {
        if self_serve
            && qr_codes
                .operator_timestamp()
                .map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)
        {
            loop {
                let qr_capture_start = Instant::now();
                let operator_qr_code =
                    self.scan_operator_qr_code(orb, None).await?.expect("to never timeout");
                let Some(operator_qr_code) =
                    self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                else {
                    continue;
                };
                let Some((_, operator_location_data)) =
                    self.verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start).await?
                else {
                    continue;
                };
                *qr_codes = QrCodes::Operator {
                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }
