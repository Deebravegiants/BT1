## Title
Deposit permanently reverts if `total_coin_without_take_pnl` or `total_pc_without_take_pnl` reaches zero due to unchecked division in `InvariantToken` - ([File: program/src/processor.rs], [File: program/src/math.rs])

### Summary
The `process_deposit` path computes an LP-mint quote by dividing by the pool's coin/pc reserves net of pending PnL (`total_coin_without_take_pnl` / `total_pc_without_take_pnl`). If either of these values reaches exactly zero while `amm.lp_amount != 0`, the deposit instruction will panic on division-by-zero, permanently freezing all future deposits into that pool — the same bug class as the reported Carapace `ProtectionPool.convertToSToken` division-by-zero when `totalSTokenUnderlying == 0` but `totalSupply() != 0`.

### Finding Description
`process_deposit` computes `total_pc_without_take_pnl`/`total_coin_without_take_pnl` via `Calculator::calc_total_without_take_pnl_no_orderbook`, which subtracts the amm's `need_take_pnl_pc`/`need_take_pnl_coin` from the live vault balances [1](#0-0) . It then further reduces these totals inside `calc_take_pnl`, based on accumulated price-based PnL since the last checkpoint, again via `checked_sub` [2](#0-1) .

The deposit code only guards against the LP supply being zero (`amm.lp_amount == 0`) [3](#0-2) , but performs no check that `total_coin_without_take_pnl` or `total_pc_without_take_pnl` (used as the constructed `InvariantToken`) is non-zero before dividing by them: [4](#0-3) 

The division itself lives in `InvariantToken::exchange_coin_to_pc` / `exchange_pc_to_coin`, which call `.checked_div(self.token_coin.into()).unwrap()` / `.checked_div(self.token_pc.into()).unwrap()` — if the denominator (`total_coin_without_take_pnl` or `total_pc_without_take_pnl`) is `0`, `checked_div` returns `None` and the subsequent `.unwrap()` panics, aborting the transaction: [5](#0-4) 

This is structurally identical to the referenced Carapace issue: `lp_amount` (analog of `totalSupply()`) is non-zero, but the underlying reserve total (analog of `totalSTokenUnderlying`) can reach zero, causing every subsequent call to the deposit math to divide by zero and revert/panic.

### Impact Explanation
If reached, this permanently bricks the deposit instruction (both `process_deposit` and `process_deposit`/`process_deposit_v2` variants that share this math) for the affected pool — no new liquidity can be added even though LP tokens are still outstanding and swaps may continue to function, which is a Medium-severity availability/DoS impact on LP funds management consistent with the referenced report's classification.

### Likelihood Explanation
Reaching this exact state requires `total_coin_without_take_pnl` or `total_pc_without_take_pnl` to hit precisely zero. Swap instructions guard against fully draining a side (`amount_out >= total_..._without_take_pnl` is rejected) [6](#0-5) , leaving at least 1 unit after a swap. However, the subsequent `calc_take_pnl` invocation performed unconditionally at the start of every deposit/withdraw/swap-pnl-affecting call further subtracts `pc_pnl_amount`/`coin_pnl_amount` from these already-thin reserves [7](#0-6) , and there is no explicit lower-bound check preventing that subtraction from landing exactly on zero. This makes the scenario plausible under adversarial-but-permissionless conditions (thin reserves + accumulated pnl) though it depends on specific numeric alignment, hence Medium likelihood rather than trivially always-reachable.

### Recommendation
Add explicit zero-checks (returning a defined `AmmError`, e.g. `AmmError::CalculationExRateFailure`) immediately after computing `total_pc_without_take_pnl`/`total_coin_without_take_pnl` (and after `calc_take_pnl` mutates them) in `process_deposit`/`process_deposit_v2`, `process_withdraw`, and the swap handlers, rejecting the instruction cleanly instead of allowing the downstream `InvariantToken`/`InvariantPool` division to panic when a denominator is zero. Alternatively, change `InvariantToken::exchange_coin_to_pc`/`exchange_pc_to_coin` and `InvariantPool::exchange_token_to_pool`/`exchange_pool_to_token` to use `checked_div` without `.unwrap()` and propagate `None` as an `AmmError` instead of panicking.

### Proof of Concept
1. Pool is initialized and receives deposits/swaps such that `total_coin_without_take_pnl` (post `calc_total_without_take_pnl_no_orderbook`) is driven very low (e.g., 1) via repeated `SwapBaseIn`/`SwapBaseOut` calls that respect the `amount_out < total_..._without_take_pnl` check [6](#0-5) .
2. A subsequent call into any instruction that invokes `calc_take_pnl` (e.g. another deposit or swap) computes `coin_pnl_amount` based on accumulated price drift since `target_orders.calc_pnl_x/y` checkpoint, and the subtraction `total_coin_without_take_pnl.checked_sub(coin_pnl_amount)` lands exactly on `0` [2](#0-1) .
3. Any subsequent `process_deposit` call constructs `InvariantToken { token_coin: 0, token_pc: total_pc_without_take_pnl }` and calls `exchange_coin_to_pc`, which executes `checked_div(0)` → `None` → `.unwrap()` panics, aborting the transaction [8](#0-7) , permanently blocking deposits into this pool while `amm.lp_amount` remains non-zero.

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
