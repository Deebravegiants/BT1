### Title
Race condition in MemoizedKeychain constructor allows cache clobbering of persisted public key data - ([File: features/keychain/module/memoized-keychain.js])

### Summary
`MemoizedKeychain`'s constructor kicks off an async `storage.get(CACHE_KEY)` load but does not block subsequent calls on its completion. If `exportKey` is invoked before that promise resolves, `#setCachedKey` persists a `#publicKeys` map that only contains the newly exported key, overwriting any pre-existing cached entries for other key IDs/accounts still in storage.

### Finding Description
The constructor initializes `#publicKeys` synchronously to `Object.create(null)` and only later replaces it once `this.#storage.get(CACHE_KEY).then(...)` resolves: [1](#0-0) 

`exportKey` does not await or wait on this load — it directly reads/writes `#publicKeys`: [2](#0-1) 

`#setCachedKey` serializes the current in-memory `#publicKeys` and persists it via `this.#storage.set(CACHE_KEY, ...)`: [3](#0-2) 

If `exportKey` is called synchronously/immediately after `new MemoizedKeychain(...)` (e.g., right after unlock/import re-instantiates the keychain), the microtask queue can allow `#setCachedKey`'s `storage.set` to execute before the constructor's `storage.get(...).then(...)` callback fires. In that scenario `#publicKeys` is still the freshly created empty object, so the persisted payload contains only the single new entry, silently overwriting whatever `CACHE_KEY` previously held (cached public keys for other key IDs/accounts). There is no guard, lock, versioning, or merge-on-write logic to prevent this; `#setCachedKey` unconditionally overwrites the full `CACHE_KEY` entry with whatever `#publicKeys` currently holds in memory.

### Impact Explanation
This is a data-integrity bug rather than a signing/auth bypass: it can silently drop previously cached public-key/xpub entries for other accounts/seeds after a keychain re-instantiation raced by an immediate `exportKey` call. The cached data (`getPublicKeyData` → `{ xpub, publicKey }`) is non-secret material used purely as a performance memoization cache; `exportKey` still falls back to `super.exportKey` and correct crypto derivation when the cache misses. So the primary impact is loss/staleness of memoized data (cache clobbering), not unauthorized signing, secret disclosure, or wrong-account signing — the invariant of underlying key derivation/security is unaffected because a cache miss just re-derives the correct key. This does not rise to wallet compromise, auth bypass, or fund-at-risk impact; at most it causes minor performance degradation (extra key derivation) and forces cache repopulation.

### Likelihood Explanation
The race is real and reproducible: it requires only that `exportKey` be invoked before the constructor's `storage.get` promise resolves, which is plausible when storage access is asynchronous (e.g., disk/IPC-backed) and `exportKey` is called immediately after instantiation. However, exploiting this requires the ability to trigger keychain re-instantiation and an immediate `exportKey` call in the same session, which is within normal wallet-unlock/import flows and not attacker-controlled input in the classic sense (no untrusted external data is injected here) — it is a self-inflicted internal timing issue rather than an attacker-triggerable one from external dapp/RPC input, since the cache values themselves are not secrets and dapp-triggered `exportKey` calls only see already-correct results (from cache or freshly derived).

### Recommendation
Store and await the initial load promise (e.g., `this.#loadPromise = this.#storage.get(CACHE_KEY).then(...)`) and have `#getCachedKey`/`#setCachedKey` await `this.#loadPromise` before reading/writing `#publicKeys`, or merge freshly loaded data into `#publicKeys` instead of replacing it outright, to avoid clobbering entries written before the load resolves.

### Proof of Concept
Unit test: mock `storage.get` to return a deferred promise resolving with `BJSON.stringify({ existingKeyCacheKey: { xpub: 'x', publicKey: 'p' } })`; construct `MemoizedKeychain({ storage })`; immediately call `exportKey(newKeyId)` (mocking `super.exportKey` to resolve quickly) before resolving the deferred `storage.get` promise; then resolve it. Assert that the final `storage.set(CACHE_KEY, ...)` payload (or the last call to `storage.set`) is missing the `existingKeyCacheKey` entry, demonstrating clobbering — while noting this only demonstrates cache-data loss, not a security/authorization bypass, since the cached values are non-secret and correctness of exported keys is unaffected on cache miss.
