### Title
Webhook `shop` and `topic` Identity Fields Are Not Covered by HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity using an HMAC computed only over the raw request body, while the `shop` and `topic` values used to route and attribute the webhook to a tenant are taken from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook via `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` and compares the computed HMAC against the `hmac-sha256` header value: [1](#0-0) [2](#0-1) 

`Request#to_signable_string` returns only `@raw_body`: [3](#0-2) 

But `Request#topic` and `Request#shop` — the values used by `Registry.process` to select the handler and identify the tenant — are read directly from the `x-shopify-topic`/`shopify-topic` and `x-shopify-shop-domain`/`shopify-shop-domain` HTTP headers, which are never included in the HMAC-signed bytes: [4](#0-3) [5](#0-4) 

This breaks the identity binding: `hmac(raw_body) == valid` should imply `(shop, topic, raw_body)` all originated from Shopify for that specific request, but the gem only proves `raw_body` is authentic — `shop` and `topic` are parsed from bytes that were never verified. An entity that can reuse/replay a legitimate `(raw_body, hmac)` pair (e.g., a webhook subscriber endpoint that also proxies to other internal services, a load balancer/CDN layer that allows header injection, or any intermediary/misconfigured routing in front of the app) can attach an arbitrary `shop-domain` and `topic` header to a validly-signed body and have the app process it as if it came from a different shop or represented a different topic, because `HmacValidator.validate` only checks the body bytes. This directly matches the "bytes verified versus bytes parsed" / "field acted on but not covered by the HMAC" identity-binding break: `verified_bytes(raw_body) == acted_upon_bytes(shop, topic)` is false in general, since `shop`/`topic` are excluded from `to_signable_string`.

### Impact Explanation
`Registry.process` passes `request.shop` and `request.topic` straight into `WebhookMetadata` handed to the app's registered `WebhookHandler`, meaning any app that trusts `shop`/`topic` as the tenant/event identity (which is the documented contract of this field) can be made to process an HMAC-valid body under the wrong shop or topic. This is a cross-tenant identity confusion at the field level: the cryptographic proof of authenticity does not cover the very values used for tenant attribution and dispatch.

### Likelihood Explanation
Exploitability depends on an attacker being able to control or replay HTTP headers independently of the signed body reaching the app (e.g., via a reverse proxy/CDN misconfiguration, multi-tenant shared endpoint, or a component that forwards Shopify webhooks with rewritten headers). Given that the header values are entirely outside the cryptographic guarantee provided by this gem, any environment where header integrity isn't otherwise guaranteed downstream of Shopify allows this identity-binding gap to be exploited.

### Recommendation
Include `topic` and `shop-domain` (and ideally `webhook-id`, `api-version`) in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind these header values to the request before using them for tenant/topic routing, so that HMAC validation covers all fields the application acts upon, not just the raw body.

### Proof of Concept
```ruby
require "openssl"
require "base64"
require "digest"

secret = ShopifyAPI::Context.api_secret_key
raw_body = '{"id":1,"note":"legit order for shop-a"}'

# Legitimately computed HMAC over the body only (as Shopify would send for shop-a)
hmac_digest = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), secret, raw_body)
hmac_header = Base64.encode64(hmac_digest).strip

# Attacker/intermediary forwards the same (raw_body, hmac) pair but swaps the
# shop-domain / topic headers - HmacValidator only checks raw_body, so it still passes.
forged_headers = {
  "x-shopify-topic" => "shop/redact",              # different topic than intended
  "x-shopify-hmac-sha256" => hmac_header,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # different shop
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes HMAC validation because it only checks raw_body, despite shop/topic being forged
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

ShopifyAPI::Webhooks::Registry.process(request)
# Handler receives WebhookMetadata with shop: "victim-shop.myshopify.com", topic: "shop/redact"
# even though these were never covered by the HMAC signature.
```
