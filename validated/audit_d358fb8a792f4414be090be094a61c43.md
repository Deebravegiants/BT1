## Title
Cost model's account-data-allocation budget is bypassed by CPI-invoked System Program instructions - ([File: cost-model/src/cost_model.rs])

### Summary
The cost model's per-transaction "allocated accounts data size" calculation only inspects top-level `System Program` instructions in a transaction. Any account allocation performed via a cross-program invocation (CPI) to the System Program (`CreateAccount`, `Allocate`, etc.) from within a custom program is invisible to this calculation, both at the estimation stage and at the post-execution "actual cost" stage. This lets a user split large account-data allocations behind a wrapper program and bypass the per-block account-data-growth throttling that the cost tracker is supposed to enforce, analogous to the GMX report's virtual-inventory bypass where a check is entirely skipped when the relevant condition isn't visible at the checked layer.

### Finding Description
`CostModel::calculate_allocated_accounts_data_size` walks `instructions` and, for each one, calls `calculate_account_data_size_on_instruction`, which only recognizes an allocation if `program_id == &system_program::id()`: [1](#0-0) 

Both the pre-execution estimate (`calculate_cost`, `estimate_cost`) and the **post-execution "actual" cost** (`calculate_cost_for_executed_transaction`) feed this function with `transaction.program_instructions_iter()`: [2](#0-1) [3](#0-2) [4](#0-3) 

`program_instructions_iter()` only yields the transaction's **top-level** instructions/program ids, not instructions invoked via CPI. Consequently, if a user writes a small wrapper program that calls `invoke()`/`invoke_signed()` into the System Program's `CreateAccount`/`Allocate`/`AllocateWithSeed` instructions, the program id seen by the cost model at the top level is the wrapper program, not `system_program::id()`, so `calculate_account_data_size_on_instruction` returns `SystemProgramAccountAllocation::None` and `allocated_accounts_data_size` is computed as `0` for that instruction — even though the transaction really does allocate account data during execution.

This value flows into `TransactionCost.allocated_accounts_data_size`, which is the exact metric used by the cost tracker to enforce the block-wide account-data growth budget: [5](#0-4) [6](#0-5) 

Critically, this is not just an estimation shortcut fixed up after execution: `calculate_cost_for_executed_transaction`, which is supposed to reconcile the estimate with the transaction's *actual* execution results (it does receive `actual_programs_execution_cost` and `actual_loaded_accounts_data_size_bytes` for other cost components), still recomputes `allocated_accounts_data_size` from the same top-level-only `program_instructions_iter()` rather than from any execution-derived delta: [3](#0-2) 

This mirrors the GMX bug precisely: the check ("does this instruction allocate account data") is completely skipped whenever the allocation happens through a path that the checker doesn't inspect (CPI vs. top-level), rather than falling back to a safe/conservative estimate.

### Impact Explanation
The cost tracker's `allocated_data_size` limit (`WouldExceedAccountDataBlockLimit`) exists specifically to bound how much new account data can be created within a single block, protecting the cluster from unbounded accounts-database growth within a block window: [7](#0-6) 

Because this metric is silently zeroed for any CPI-based allocation (both in scheduling estimates and in the "actual" recomputation used when adding processed transactions to the tracker), an attacker can:
1. Deploy a trivial wrapper program that CPIs into the System Program to `CreateAccount`/`Allocate` large account spaces.
2. Submit many such transactions in a single block/leader slot.
3. Have all of them accepted by `would_fit`/`try_add` in the cost tracker as if they allocated `0` bytes of new account data, even though real account data is created/allocated during execution.

This produces materially underpriced execution with respect to the account-data-allocation dimension of the cost model: the enforced per-block account-data-growth budget can be exceeded arbitrarily, without ever tripping `WouldExceedAccountDataBlockLimit`. Since this metric also feeds the `runtime/src/conformance/cost.rs` conformance/cost oracle used to cross-check cost computations, a divergence between a node that treats CPI allocations differently vs. one that doesn't (e.g., future cost-model versions, or SVM implementations with differing treatment) could also become a source of cross-implementation inconsistency, though this report's core, provable claim is the underpricing/bypass of the intended budget.

### Likelihood Explanation
This is trivially reachable by any unprivileged user: it only requires deploying an ordinary BPF program that performs a CPI to the System Program's `CreateAccount`/`Allocate`/`AllocateWithSeed`/`CreateAccountWithSeed` instructions instead of invoking them at the top level of the transaction — a completely ordinary and common pattern (e.g., PDA account creation via `invoke_signed`). No special privileges, validator role, or crafted snapshot is required.

### Recommendation
Compute `allocated_accounts_data_size` (both in the pre-execution estimate and, especially, in `calculate_cost_for_executed_transaction`) from the actual execution-time account data growth (e.g., via `AccountsDeltas`/`accounts_resize_delta`/`accounts_uninitialized_size` already tracked in `TransactionExecutionDetails`) rather than re-deriving it solely from statically-inspected top-level instructions. At minimum, the "actual" cost path should use real post-execution allocation deltas instead of repeating the same static, CPI-blind heuristic used for estimation. [8](#0-7) 

### Proof of Concept
1. Deploy a wrapper BPF program `W` whose instruction handler simply forwards to the System Program via `invoke()`/`invoke_signed()` calling `system_instruction::create_account` (or `allocate`) with a large `space` value (e.g., close to `MAX_PERMITTED_DATA_LENGTH`).
2. Submit a transaction whose only top-level instruction targets program `W` (not `system_program::id()` directly).
3. Observe that `CostModel::calculate_allocated_accounts_data_size` — called from both `calculate_cost` (scheduling estimate) and `calculate_cost_for_executed_transaction` (post-execution "actual" cost) — returns `0` for this transaction because `calculate_account_data_size_on_instruction` only special-cases `program_id == &system_program::id()`; the wrapper program id fails that check and yields `SystemProgramAccountAllocation::None`.
4. Compare against an equivalent transaction that calls `system_instruction::create_account` directly at the top level with the same `space`: `calculate_allocated_accounts_data_size` correctly reports `space` bytes.
5. Repeating step 2 many times within one block allows the cumulative real account-data growth to exceed the cost tracker's `allocated_data_size` limit (`CostTrackerLimits::allocated_data_size`) without ever triggering `CostTrackerError::WouldExceedAccountDataBlockLimit`, demonstrating the bypass of the intended per-block account-data growth budget.

        program_id: &Pubkey,
        instruction: SVMInstruction,
        feature_set: &FeatureSet,
    ) -> SystemProgramAccountAllocation {
        if program_id == &system_program::id() {
            if let Ok(instruction) =
                limited_deserialize(instruction.data, solana_packet::PACKET_DATA_SIZE as u64)
            {
                Self::calculate_account_data_size_on_deserialized_system_instruction(
                    instruction,
                    feature_set,
                )
            } else {
                SystemProgramAccountAllocation::Failed
            }
        } else {
            SystemProgramAccountAllocation::None
        }
    }

    fn would_fit(
        &self,
        tx_cost: &TransactionCost<impl TransactionWithMeta>,
    ) -> Result<(), CostTrackerError> {
        let cost: u64 = tx_cost.sum();

        if self.block_cost().saturating_add(cost) > self.limits.block_cost {
            // check against the total package cost
            return Err(CostTrackerError::WouldExceedBlockMaxLimit);
        }

        // check if the transaction itself is more costly than the account_cost_limit
        if cost > self.limits.account_cost {
            return Err(CostTrackerError::WouldExceedAccountMaxLimit);
        }

        let allocated_accounts_data_size =
            self.allocated_accounts_data_size + Saturating(tx_cost.allocated_accounts_data_size());

        if allocated_accounts_data_size.0 > self.limits.allocated_data_size {
            return Err(CostTrackerError::WouldExceedAccountDataBlockLimit);
