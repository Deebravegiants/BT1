## Finding: Auto-lock passphrase cache can be revived after expiration without re-validating expiry

### Title
Expired cached passphrase can be revived indefinitely via `changeLockTimer`/`restartAutoLockTimer` - (File: `features/application/src/modules/passphrase-cache.ts`)

### Summary
This is a direct analog of the reported "cache that times out can be recovered" bug class. In the external report, `LocalCache#set_expire` reset a key's `expire_at` without first checking whether the key had already logically expired, letting a stale/expired value be resurrected. The same pattern exists in hydra's `PassphraseCache`: its expiry-extension methods (`changeTtl`, `scheduleClear`) only check for the *raw presence* of the cached passphrase in storage, not whether it has already passed its expiry window, allowing an already-expired cached passphrase to be "reactivated" and kept alive indefinitely.

### Finding Description
`PassphraseCache#get` is the only place that actually evaluates expiry (`addedAt + maxTtl` or `inactiveAt + ttl` vs `Date.now()`), and it lazily calls `clear()` only when `get()` happens to be invoked: [1](#0-0) 

However, `changeTtl` and `scheduleClear` do not perform this same expiry check. `scheduleClear` simply reads `PASSPHRASE_KEY` from storage and, if it is merely present (regardless of whether it is already expired), resets `INACTIVE_AT_KEY` to `Date.now()`, restarting the inactivity countdown: [2](#0-1) 

`changeTtl` behaves the same way — it checks `if (passphrase)` against raw storage rather than validating expiry, then updates `TTL_KEY` and triggers `#scheduleClear`, extending the life of a passphrase entry that should already be considered expired: [3](#0-2) 

Both of these methods are reachable through the public `Application` module (`public: true`) via `changeLockTimer` and `restartAutoLockTimer`, which are also exposed through the documented `applicationApi`: [4](#0-3) [5](#0-4) 

On startup, `Application#start` calls `#autoUnlock`, which calls `passphraseCache.get()` and, if it returns a non-expired passphrase, silently unlocks the wallet: [6](#0-5) 

### Impact Explanation
The auto-lock TTL mechanism is a security boundary intended to force re-authentication (re-entry of the passphrase) after a period of inactivity. Because `scheduleClear`/`changeTtl` do not verify actual expiry before refreshing `INACTIVE_AT_KEY`/`TTL_KEY`, a caller with access to the `application.changeLockTimer` / `application.restartAutoLockTimer` surface can keep resetting the inactivity clock on an already-expired cached passphrase, preventing it from ever being cleared by `get()`'s lazy-expiry check and effectively defeating auto-lock. Since `#autoUnlock` uses this cached passphrase to silently unlock the wallet on restart, this could allow the wallet to remain auto-unlockable well past its intended TTL — a direct analog to the "cache that times out can be recovered" issue, applied to an authentication/session boundary rather than off-chain data.

### Likelihood Explanation
Likelihood depends on which contexts can invoke `application.changeLockTimer`/`application.restartAutoLockTimer` — this is exposed as a public application-level API/SDK method (per `sdks/headless`), so its exposure surface (e.g., whether malicious/less-trusted code such as a compromised extension UI process or a bridged RPC caller can reach it) could not be fully confirmed from the indexed code alone. If any component other than the fully-trusted core wallet controller can call these two methods, the bug is directly triggerable without needing any secret.

### Recommendation
In `PassphraseCache#changeTtl` and `PassphraseCache#scheduleClear`, do not treat mere presence of `PASSPHRASE_KEY` in storage as valid — first evaluate the same expiry condition used in `get()` (i.e., check `inactiveAt + ttl` / `addedAt + maxTtl` against `Date.now()`) and short-circuit to `clear()` if already expired, before extending `TTL_KEY`/`INACTIVE_AT_KEY`. Consider factoring the expiry check out of `get()` into a shared private helper (e.g., `#isExpired()`) used by all three methods to avoid this divergence.

### Proof of Concept
1. Unlock the wallet with a passphrase; `PassphraseCache#set` stores `passphrase`, `addedAt`, `ttl`.
2. Let the configured `ttl`/`maxTtl` window elapse so the entry is logically expired, but do not call `passphraseCache.get()` (so `clear()` is never triggered).
3. Call `application.restartAutoLockTimer()` (or `application.changeLockTimer({ ttl })`) — since `scheduleClear`/`changeTtl` only check `if (passphrase)` truthiness in storage, `INACTIVE_AT_KEY` is refreshed to `Date.now()`, silently reviving the expired entry.
4. On next app restart/`start()`, `#autoUnlock` calls `passphraseCache.get()`, which now sees a fresh `inactiveAt` and returns the previously-expired passphrase, auto-unlocking the wallet outside the intended TTL window.

    await this.#autoLockTimerAtom.set(newTtl)
