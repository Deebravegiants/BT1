### Title
Stale `account.owner` used for authorization lets a previous position-NFT owner retain full control after NFT transfer - ([File: contracts/controller/src/account.rs])

### Summary

The Vikunja bug class is an authorization inconsistency: one path enforces a permission check while a sibling path bypasses it, so a low-privilege credential (a read-only link share) can be escalated into full control. In XOXNO Lending, account authority is dual-sourced: `Account.owner` is stored once at account creation, while `storage::account_owner` (the position-NFT owner of record) is consulted only by a few entrypoints. Every value-moving entrypoint — `withdraw`, `borrow`, `multiply`, `swap_debt`, `swap_collateral`, `repay_debt_with_collateral`, `migrate_from_blend`, `flash_position`, liquidation `Credit` receivership — authorizes via `require_owner_or_delegate` against the stored `account.owner`, not the live NFT owner. If a position NFT is transferred without the controller rewriting `account.owner`, the seller keeps owner-equivalent authority over the account forever.

### Finding Description

Accounts are created in `create_account_with`, which mints the NFT to `owner` and persists `Account { owner: owner.clone(), ... }` — the owner is snapshotted at creation time (`contracts/controller/src/account.rs:62-70`). Authorization for all position-mutating flows is `is_owner_or_delegate`, which returns `true` whenever `caller == owner`, where `owner` is the *stored* field (`contracts/controller/src/account.rs:121-127`). `require_owner_or_delegate` panics only when this stale check fails (`contracts/controller/src/account.rs:130-140`).

Meanwhile, the controller does track live NFT ownership: `require_account_owner` compares the caller against `storage::account_owner(env, account_id)` (`contracts/controller/src/account.rs:143-148`), and it is used only for `renew_account`, `add_delegate`, and `remove_delegate` (`contracts/controller/src/account.rs:217-275`). The withdrawal path, by contrast, loads the stored account and checks `require_owner_or_delegate(env, account_id, caller, &account.owner)` (`contracts/controller/src/positions/supply.rs:149-150`); `load_or_create_account` applies the same stored-owner check for `Migrate`/`Multiply` guards (`contracts/controller/src/account.rs:99-110`).

The NFT mint/burn/renew calls exist (`nft_mint_call`, `nft_burn_call`, `nft_renew_call`, `contracts/controller/src/account.rs:12`), but nothing in the account lifecycle writes `account.owner` after creation — there is no owner-resync path analogous to `require_account_owner` for the value-moving entrypoints. If `position-nft` `transfer`/`approve` does not synchronously update `account.owner` in controller storage (no such hook appears in `account.rs`), the stored owner and NFT owner permanently diverge after the first transfer.

### Impact Explanation

- The prior NFT holder retains owner-equivalent authority: they can call `withdraw` to drain all collateral to themselves, `borrow` to pull new debt against the buyer's collateral, or `multiply`/`swap_collateral` to reshape the position — direct theft of the buyer's funds.
- Delegation amplifies it: `storage::get_delegates(env, account_id, owner)` is keyed by the stored owner (`contracts/controller/src/account.rs:126`), so delegates granted by the seller keep authority the buyer cannot revoke (`remove_delegate` requires the *live* NFT owner via `require_account_owner`, and operates on the caller's own delegate list).
- The legitimate buyer of a leveraged position NFT cannot withdraw or manage the position they purchased, while the seller can steal it back — permanent loss/temporary freezing of user funds.

### Likelihood Explanation

Position NFTs are designed to be transferable (`position-nft` `transfer`/`approve` is an in-scope unprivileged surface, and NFTs exist precisely to make accounts transferable/listed). Any secondary-market sale or wallet migration triggers the divergence. Exploitation requires no privileged role, oracle manipulation, or timing — a single `transfer` followed by `withdraw`/`borrow` by the previous owner. Caveat: this finding assumes the NFT `transfer` implementation does not perform a cross-contract owner resync; `contracts/position-nft/src/contract.rs` and `contracts/controller/src/external/position_nft.rs` could not be fully verified within the iteration limit. If such a resync hook exists and is enforced, severity drops to nil.

### Recommendation

Single-source account authority on the live NFT owner:

- In `is_owner_or_delegate`, resolve `storage::account_owner(env, account_id)` (the NFT `owner_of`) instead of trusting `account.owner`, or update `require_owner_or_delegate` call sites to use `require_account_owner`.
- Alternatively, have the position-NFT `transfer` invoke a controller hook that rewrites `Account.owner` and clears the old owner's delegate list (delegates are keyed under the old owner at `account.rs:126` and `account.rs:261`), and restrict `transfer` so the hook cannot be skipped.
- Ensure delegate grants keyed by `owner` are migrated or purged on transfer, since `add_delegate`/`remove_delegate` operate on the caller's list.

### Proof of Concept

1. Alice calls `supply(caller=alice, account_id=0, spoke_id, assets=[(XLM, 1000)])`; `create_account` mints NFT `id=7` to Alice and stores `Account.owner = alice` (`account.rs:62-70`).
2. Alice lists/sells NFT `id=7`; Bob acquires it via `position-nft.transfer`. Controller storage `Account.owner` remains `alice` — no write path exists after creation.
3. Bob supplies more collateral (or the position accrues value). Alice — who no longer holds the NFT — calls `withdraw(caller=alice, account_id=7, withdrawals=[(XLM, 0)], to=Some(alice))`. `process_withdraw` loads the stored account and calls `require_owner_or_delegate(env, 7, alice, &account.owner)` (`supply.rs:149-150`); `caller == account.owner` is true, so the check passes and `settle_withdraw` pays Alice the full balance (`supply.rs:190-198`).
4. Bob, the actual NFT owner, calls `withdraw` himself: `caller == account.owner` fails and he is not in `get_delegates(7, alice)`, so the call panics `NotAuthorized` (`account.rs:136-139`). Alice's earlier `add_delegate` grants also persist beyond Bob's reach.
5. Net effect: the seller of a position NFT reclaims all collateral and can additionally `borrow` against the buyer's position, leaving the buyer with the debt — permission escalation from a stale credential, directly analogous to the leaked share-hash escalation.
