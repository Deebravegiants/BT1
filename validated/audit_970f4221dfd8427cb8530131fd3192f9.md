### Title
Rounding drift in `calc_take_pnl`'s stored `k`-invariant baseline can permanently brick Deposit/Withdraw/WithdrawPnl - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` re-derives a "last observed" pool value (`calc_pc_amount`, `calc_coin_amount`) from the on-chain `TargetOrders.calc_pnl_x` / `calc_pnl_y` baseline by running it back through decimal-normalization math, then requires the *current* pool value to be `>=` that baseline or it hard-fails the whole instruction. Because the baseline is written back through the same lossy fixed-point conversion on every successful call, repeated deposit/withdraw activity can drift the stored baseline upward relative to the true pool reserves by rounding, eventually making the invariant check fail permanently — exactly the "unaccruedSeconds/unstreamed never reaches the expected value because of division precision loss" bug class in the referenced report, but here manifesting as a stuck `>=` comparison instead of a stuck `== 0` comparison.

### Finding Description
On every `Deposit`, `Withdraw`, and `WithdrawPnl` instruction, the processor calls `Calculator::normalize_decimal_v2` to convert current vault balances into the internal `sys_decimal_value` unit (`x1`, `y1`), then calls `Self::calc_take_pnl`: [1](#0-0) 

Inside `calc_take_pnl`, the previously stored baseline is reconstructed via `Calculator::restore_decimal` from `target.calc_pnl_x` / `target.calc_pnl_y`, and the function only proceeds if `pool_pc_amount * pool_coin_amount >= calc_pc_amount * calc_coin_amount`; otherwise it returns `AmmError::CalcPnlError`, aborting the whole instruction: [2](#0-1) [3](#0-2) 

After a successful call, `target_orders.calc_pnl_x` / `calc_pnl_y` are re-written from `x1`/`y1` (the freshly normalized current pool value) minus `delta_x`/`delta_y`, and this round-trips through `normalize_decimal_v2` → `restore_decimal` again on the next call: [4](#0-3) [5](#0-4) 

`normalize_decimal_v2`/`restore_decimal` perform integer multiplication/division scaling between `pc_decimals`/`coin_decimals` and `sys_decimal_value`, which — like the `tdelta * unstreamed / (endStream - lastUpdate)` division in the referenced Locke.sol bug — truncates towards zero and loses fractional units on every round trip. Because this baseline is persisted on-chain in `TargetOrders` and re-derived every call rather than being reset to an authoritative value, repeated legitimate deposit/withdraw traffic (no attacker manipulation required) can accumulate rounding error such that the *restored* baseline product ends up strictly greater than the actual current vault-derived product, tripping the `else` branch unconditionally.

Once that happens, `calc_take_pnl` returns `Err(AmmError::CalcPnlError)` for every future call, because:
- The only way to update/repair `calc_pnl_x`/`calc_pnl_y` is via a *successful* `calc_take_pnl` call inside `process_deposit`, `process_withdraw`, or `process_withdrawpnl`.
- All three of those instructions call `calc_take_pnl` unconditionally (except `Withdraw` while `AmmStatus::WithdrawOnly`), so once the invariant check fails, there is no unprivileged code path left to reset the stale baseline. [6](#0-5) 

### Impact Explanation
This freezes `Deposit`, `Withdraw` (outside `WithdrawOnly` status), and `WithdrawPnl` for the affected pool, permanently locking all LP and PnL-owner funds in the vaults with no unprivileged recovery path — matching the "permanent freezing of user or LP funds" acceptance criterion. It is reachable purely through the normal unprivileged `Deposit`/`Withdraw` instruction paths.

### Likelihood Explanation
Every successful deposit/withdraw call re-derives and re-stores the baseline through a lossy decimal conversion, so the rounding drift is not a one-off theoretical event but an accumulating side effect of ordinary pool usage; the referenced report explicitly notes the underlying class of bug requires no crafted adversarial input; it can surface from ordinary fuzzed/organic sequences of stakes and unstakes.

### Recommendation
Avoid reconstructing the pnl baseline through a full normalize/restore round trip on every call. Either store the baseline already in native token units (avoiding the extra decimal-scaling division), track it exactly (e.g., retain the un-rounded internal `U128`/`U256` values across calls rather than converting to `u64`/back), or replace the strict `>=` invariant with a tolerance-based / floor-based comparison so that dust-level rounding cannot permanently trip `AmmError::CalcPnlError`.

### Proof of Concept
Deterministic reproduction requires simulating the exact fixed-point arithmetic in `Calculator::normalize_decimal_v2`/`restore_decimal` across many `Deposit`→`Withdraw` cycles (as the referenced fuzzing campaign did for `Locke.sol`) to accumulate enough rounding drift that `pool_pc_amount * pool_coin_amount < calc_pc_amount * calc_coin_amount` at `program/src/processor.rs:190`. The existing test `test_calc_pnl_precision` in the same file already demonstrates the precision-sensitive nature of this exact computation path across repeated withdrawals: [7](#0-6) 

Full end-to-end confirmation (constructing the specific sequence of deposit/withdraw amounts that trips the `else` branch) was not completed within this investigation; the root cause and unprivileged reachability are established by direct code inspection above.
