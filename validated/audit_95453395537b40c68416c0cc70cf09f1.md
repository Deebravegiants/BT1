### Title
Cross-chain calldata dispatch in `HftModule::on_accept` checks only the outer `RuntimeCall` against `BaseCallFilter`, letting a filtered dispatchable escape a filter/SafeMode restriction via `Utility::batch` (nested-call filter bypass) - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`IsmpModule::on_accept` in the `hyper-fungible-token` pallet decodes an attacker-supplied `RuntimeCall` from the cross-chain message body and dispatches it after a single, shallow `BaseCallFilter::contains(&runtime_call)` check. Substrate's filter model is only sound if every dispatchable that can nest other calls (`pallet_utility::batch`/`batch_all`, `Proxy::proxy`, `Scheduler::schedule`) re-validates its inner calls, but several of those pallets intentionally use `dispatch_bypass_filter` for inner calls because they assume the top-level `Executive::apply_extrinsic` filter check already gated the whole extrinsic. `on_accept`'s explicit, one-shot check on the *outer* call is exactly this class of shallow sandbox check — analogous to the Groovy sandbox in CVE-2019-1003001, which validated a top-level script construct but could be circumvented via nested/meta-programmed constructs that reached unguarded code paths.

### Finding Description
`on_accept` (`modules/pallets/hyper-fungible-token/src/module.rs:189-200`) decodes the runtime call attached to any incoming cross-chain token transfer: [1](#0-0) 

```
let runtime_call = T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)...
if !<T as frame_system::Config>::BaseCallFilter::contains(&runtime_call) {
    Err(HftError::CallFiltered)?
}
...
runtime_call.dispatch(RawOrigin::Signed(origin.clone()).into())...
```

The comment at line 191-193 states the explicit intent of this check: *"Apply the runtime's base call filter so that cross-chain calls cannot reach dispatchables that the runtime has otherwise filtered out (e.g. during a maintenance mode or a SafeMode period)."* This is the security boundary the pallet author believes protects the runtime during an emergency filter/SafeMode. The origin used to dispatch is derived either from a signature over `(nonce, runtime_call)` or, when unsigned, directly from `message.from`, which the sending contract sets to `msg.sender` (`sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol:239`), so the call is dispatched with the *sender's own* Substrate-mapped account — i.e., an attacker can reach this path with a transaction they fully control, and it is reachable by any unprivileged token bridger with no special permission.

The vulnerability class from CVE-2019-1003001 is a sandbox/permission check that inspects only the surface syntax of an attacker-controlled program and can be bypassed by wrapping the dangerous operation inside a construct the checker does not recurse into. `BaseCallFilter::contains(&runtime_call)` checks only the outer `RuntimeCall` variant. It does not, and structurally cannot, recurse into calls nested inside `pallet_utility::Call::batch`/`batch_all`, `pallet_proxy::Call::proxy`, or `pallet_scheduler::Call::schedule*`, because those pallets internally call the inner call's `dispatch_bypass_filter` (the Substrate-provided escape hatch that deliberately skips `BaseCallFilter`, on the documented assumption that the filter was already enforced once, at the top of the extrinsic, by `frame_executive`). Here there is no such top-of-extrinsic enforcement — the pallet is manufacturing a `RawOrigin::Signed` dispatch deep inside ISMP message handling, so the single `contains()` call at line 194 is the *only* filter gate this path has, and it is exactly the shallow, single-layer check the nested pallets' bypass-filter design assumes will not be relied upon in isolation.

Consequence: if `Utility`, `Proxy`, or `Scheduler` are present in the runtime (as they are, per `parachain/runtimes/gargantua/src/weights/pallet_utility.rs` and `parachain/runtimes/nexus/src/weights/pallet_utility.rs`) and are not themselves filtered (which they normally are not — filtering `Utility::batch` outright would break unrelated user-facing functionality), an attacker can wrap any dispatchable the runtime intends to block — e.g. during a SafeMode/maintenance period referenced in the pallet's own comment — inside `Utility::batch { calls: vec![blocked_call] }`. The outer check at line 194 sees only `Utility::batch`, which passes `contains()`, and `Utility::batch`'s internal execution uses `dispatch_bypass_filter` for `blocked_call`, so the intended block never fires.

### Impact Explanation
This is a sandbox/authorization-bypass vulnerability rated High by analogy to the CVE (unprivileged Overall/Read-level actor gaining code execution the security model intended to block). Concretely: during a declared SafeMode/maintenance window (the exact scenario the pallet's own comment names as the reason for this filter), any unprivileged cross-chain token sender can still get an otherwise-blocked dispatchable executed under their own mapped account by nesting it inside `Utility::batch`. Depending on what the runtime's SafeMode filter is protecting (e.g. asset transfers, governance-adjacent calls, or pallet operations meant to be frozen during an incident), this can let an attacker perform unauthorized app actions the runtime believed were frozen, directly undermining the incident-response control the filter exists to provide. It does not directly mint tokens or forge messages, but it defeats a documented security control on a path reachable by any unprivileged relayed cross-chain message.

### Likelihood Explanation
High: no special privilege is required. Any account holding the bridged token on the source chain can call `send()` with a `data` payload encoding `SubstrateCalldata { runtime_call: Utility::batch([blocked_call]).encode(), signature: None }`, mint/lock a trivial amount of tokens, and have the relayer deliver it — the relayer path is entirely permissionless (`handle_unsigned`/ISMP delivery does not gate on caller identity beyond proof validity). The only preconditions are (a) the runtime includes `pallet_utility` (or `pallet_proxy`/`pallet_scheduler`) and does not filter it, and (b) a SafeMode/maintenance filter is active and blocking some other call the attacker wants to still execute. Both conditions are the normal, expected operating state of a Substrate runtime with these pallets configured.

### Recommendation
- In `on_accept`, do not rely on a single shallow `BaseCallFilter::contains(&runtime_call)` check when the call can wrap arbitrary sub-calls. Either recursively unwrap and check `Utility::batch`/`batch_all`, `Proxy::proxy`, and `Scheduler::schedule*` variants before dispatch, or reject any `RuntimeCall` variant belonging to those wrapper pallets outright from cross-chain calldata execution.
- Prefer dispatching via a mechanism that re-applies the top-level filter recursively (e.g. a wrapper that calls `frame_system::Config::BaseCallFilter::contains` on every level of nesting it discovers, mirroring how `frame_executive` intends the filter to be the sole authority once per extrinsic — but here every cross-chain message *is* effectively its own extrinsic and must get the same guarantee).
- Add a runtime-level test (mirroring `parachain/simtests/src/base_call_filter.rs`) that specifically attempts to smuggle a SafeMode-filtered call through `on_accept`'s calldata path wrapped in `Utility::batch`, and assert it is rejected.

### Proof of Concept
1. Runtime enters SafeMode/maintenance and `IsmpCallFilter`/SafeMode filter blocks dispatchable `X` (e.g. an asset or governance-adjacent call) at the top level.
2. Attacker calls `HyperFungibleToken(destTokenOnEvm).send()`'s peer function (or the equivalent EVM `send()`), setting `data` to an ABI-encoded `SubstrateCalldata` whose `runtime_call` bytes decode to `RuntimeCall::Utility(pallet_utility::Call::batch { calls: vec![X] })`, and `signature = None`.
3. Relayer delivers the ISMP `PostRequest` to the HFT pallet; `on_accept` runs, mints/transfers the bridged token to the beneficiary, then reaches the calldata-execution branch.
4. `BaseCallFilter::contains(&RuntimeCall::Utility(Call::batch{..}))` returns `true` (Utility itself is not filtered) — check at line 194 passes.
5. `runtime_call.dispatch(RawOrigin::Signed(origin))` executes `Utility::batch`, which internally invokes `X.dispatch_bypass_filter(origin)` for the wrapped call, executing `X` despite the active SafeMode filter that was supposed to block it.

Note: I was unable to inspect the exact `BaseCallFilter`/SafeMode implementation body for `gargantua`/`nexus` runtimes (only `type BaseCallFilter = ...` occurrence locations were found, not their full definitions) within the available iterations, so I cannot confirm which specific dispatchables the runtime's SafeMode currently blocks, or whether `pallet_utility`/`pallet_proxy` are additionally excluded from the filter allowlist. This should be verified directly against `parachain/runtimes/gargantua/src/lib.rs` and `parachain/runtimes/nexus/src/lib.rs` before treating the impact as confirmed rather than structural.
