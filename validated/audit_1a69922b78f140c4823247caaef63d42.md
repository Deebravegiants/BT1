### Title
Timeout processing (`handlePostRequestTimeouts` / `handleGetRequestTimeouts`) has no relayer incentive, so timed-out messages will not be processed and escrowed/locked funds remain frozen - (File: `evm/src/core/EvmHost.sol`, `evm/src/core/HandlerV2.sol`)

### Summary
When a POST or GET request times out, the only way to unlock funds held by a `HyperApp` (e.g. burned/locked tokens in `HyperFungibleToken`/`WrappedHyperFungibleToken`/`BridgeToken`, or escrow held by `ExtrinsicIntents`) is for someone to call the permissionless `handlePostRequestTimeouts`/`handleGetRequestTimeouts` functions on `HandlerV2`, supplying a state non-membership proof. This is exactly the kind of costly, permissionless "cleanup" action that off-chain relayer bots perform for a fee — analogous to a liquidator bot in a lending/margin protocol. However, `EvmHost.dispatchTimeOut` always sends the entire relayer fee back to the original `payer`/`meta.sender`, never to `msg.sender`/the relayer that actually generated and submitted the timeout proof. Consequently there is no economic incentive for any relayer to ever submit a timeout message, and rational relayer bots will simply not process timeouts, mirroring the reported liquidation-bot inactivity issue.

### Finding Description
`HandlerV2.handlePostRequestTimeouts` and `handleGetRequestTimeouts` are permissionless entry points that verify a state (non-membership) proof and then call `host.dispatchTimeOut(...)`, passing along `_msgSender()` as the relayer: [1](#0-0) [2](#0-1) 

In `EvmHost.sol`, `dispatchTimeOut` for both POST and GET requests refunds the relayer fee exclusively to `meta.sender` (the original payer), and the `relayer` argument bundled in the timeout struct is only forwarded to the application's callback — it is never used to pay out any portion of the fee to the caller who submitted the proof: [3](#0-2) [4](#0-3) 

The documentation confirms this is the intended (but flawed) design: "GET requests have no relayer fees, so no refunds occur" and for POST timeouts, the fee "refunds the relayer fee to the payer" — with no reward path to the relayer who processed the timeout: [5](#0-4) 

Submitting a timeout message is not free: the caller must construct and submit a full non-membership state trie proof plus pay the L1/L2 gas for verifying it (`PolkadotTrie.VerifyProof`), which is a materially expensive operation — the very reason relayer fees exist for normal delivery. Yet the timeout-processing path pays this cost with zero reward to the caller, unlike normal message delivery (`handlePostRequests`) where the delivering relayer keeps the fee held for that request.

The downstream consequence is severe: application-level fund-recovery logic is gated entirely behind this unrewarded timeout path. For example, `HyperFungibleToken.onPostRequestTimeout` / `WrappedHyperFungibleToken.onPostRequestTimeout` only re-mint/unlock a user's bridged tokens once `onPostRequestTimeout` is invoked by the host, which only happens after a relayer calls `handlePostRequestTimeouts`: [6](#0-5) [7](#0-6) 

Similarly, the Intent Gateway's `_cancelFromSource`/escrow-refund flow and `RedeemEscrow` dispatches rely on Hyperbridge's ISMP request/timeout machinery to eventually settle or refund escrow: [8](#0-7) 

### Impact Explanation
Since the fee-paying relayer role and the timeout-submitting role are decoupled, and the timeout submitter receives no compensation whatsoever (the docs explicitly state GET timeouts pay nothing, and POST timeouts pay the original payer, not the submitter), a profit-driven relayer network — as described in Hyperbridge's own documentation ("Relayers are profit-driven mediators and they will prioritize messages with fees that ensure profitability") — has no reason to ever submit timeout proofs. This causes messages that have timed out to remain permanently unprocessed on the source chain. Because refund/unlock logic for bridged/escrowed user funds (`HyperFungibleToken`, `WrappedHyperFungibleToken`, `BridgeToken`, intents escrow) is gated behind this same unrewarded call, user funds that should be refundable on timeout can become effectively frozen indefinitely absent altruistic or self-relaying actors. This matches the "permanent freezing of funds" / "route unable to deliver messages" impact classes.

### Likelihood Explanation
This triggers under completely ordinary operating conditions — any time a dispatched POST/GET request with a relayer fee is not delivered before its timeout (network congestion, destination-chain issues, insufficient fee, or a reverting `onAccept`/`onPostRequestTimeout` callback that must be retried). No malicious actor is required; it only requires that no altruistic/self-interested party volunteers to pay real gas + proof-generation costs for zero reward, which is the expected rational behavior of a decentralized relayer market described in Hyperbridge's own documentation.

### Recommendation
Split the relayer fee (or a `hostParams`-configured timeout-processing fee) between the payer refund and the address that submits the timeout proof, analogous to how `handlePostRequests`/`dispatchIncoming` rewards the delivering relayer. At minimum, carve out a small fixed/percentage incentive from the escrowed relayer fee (or a protocol-level timeout-processing subsidy) payable to `msg.sender`/`relayer` in `dispatchTimeOut` for both GET and POST paths, so permissionless timeout processing remains economically rational and user funds are not left indefinitely unrecoverable.

### Proof of Concept
1. App `A` dispatches a `DispatchPost` with `fee = F`, `payer = user`, `timeout = T` via `EvmHost.dispatch`.
2. The message is never delivered before `timeoutTimestamp` (e.g., relayer profitability threshold not met, or destination briefly unavailable).
3. Any actor can call `HandlerV2.handlePostRequestTimeouts` with a valid non-membership proof; per `EvmHost.dispatchTimeOut(PostRequestTimeout...)`, `meta.fee` (`F`) is transferred back to `meta.sender` (the original `payer`), and `msg.sender`/relayer who paid gas + constructed the proof receives 0.
4. Because relayers are profit-driven (per Hyperbridge's own fee documentation), no relayer will call step 3, so `onPostRequestTimeout` on the source `HyperApp` (e.g., `HyperFungibleToken`) never runs, and the user's burned/locked tokens are never re-minted/unlocked, remaining stuck until an altruistic party (or the user themselves, if capable of generating the state proof) intervenes.

### dispatchTimeOut(PostRequestTimeout)

Dispatches a timed-out POST request to the source application's `onPostRequestTimeout()` callback. If the callback succeeds, refunds the relayer fee to the payer.

     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Re-mints the burned tokens back to the original sender as a refund.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof

    function onPostRequestTimeout(PostRequestTimeout memory incoming) public virtual override onlyHost whenNotPaused {
        Message memory message = abi.decode(incoming.request.body, (Message));
        address refundee = _toAddr(message.from);
        _mint(refundee, message.amount);
        emit Refunded({to: refundee, amount: message.amount});

    /**
     * @notice Handles timeout of a previously dispatched cross-chain transfer
     * @dev Called by the ISMP host when a sent message times out without being delivered.
     * Attempts to unwrap WETH and refund native tokens.
     * @param incoming The timed-out POST request and the relayer that submitted the timeout proof
     */
    function onPostRequestTimeout(PostRequestTimeout calldata incoming) external override onlyHost whenNotPaused {
        HyperFungibleToken.Message memory message = abi.decode(incoming.request.body, (HyperFungibleToken.Message));
        address refundee = _toAddr(message.from);

        if (_isWeth) {
            // Try a native-ETH push first; if the refundee cannot accept native value
            // (e.g. the caller used the ERC-20 deposit path in `send()` from a
            // non-payable contract), re-wrap the withdrawn ETH and deliver the
            // underlying WETH as an ERC-20 transfer so the timeout still settles and
            // funds are not permanently locked.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = refundee.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(refundee, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(refundee, message.amount);
        }

        emit Refunded({to: refundee, amount: message.amount});
    }
