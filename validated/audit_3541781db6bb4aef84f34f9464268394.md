### Title
Unbounded first-reward payout in `pallet-consensus-incentives` due to zero-defaulted height checkpoints - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary
`calculate_reward` computes relayer rewards as `(latest_height - baseline) * block_cost`, where `baseline` falls back to `previous_commitment_height`, which itself defaults to `0` when no prior height has been recorded for a state machine [1](#0-0) . This mirrors the LpGauge `poolLastUpdate` bug: an unset "last checkpoint" variable defaults to zero, and the very first checkpoint computation multiplies a huge current value (block height here, timestamp there) by the reward rate, letting a single caller collect an outsized reward.

### Finding Description
`calculate_reward` reads:
- `latest_height` via `host.latest_commitment_height(...)`, which itself defaults to `0` via `unwrap_or_default()` when no height has ever been stored [2](#0-1) .
- `previous_height` via `host.previous_commitment_height(...).unwrap_or_default()`, which returns `0` if `PreviousStateMachineHeight` was never populated for that state machine.
- `baseline` from `LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height)` — the first time a state machine is rewarded, this falls straight through to `previous_height` [3](#0-2) .

Governance enables incentives for a state machine at any time by calling `update_cost_per_block`, independent of when consensus updates for that chain began [4](#0-3) . If a state machine has already advanced to a large height (through pre-existing consensus updates delivered before incentives were turned on, or through updates where `PreviousStateMachineHeight` was never populated for that id), then the first relayer to submit any qualifying consensus message after `update_cost_per_block` is set will trigger `process_message` → `calculate_reward`, where `baseline` resolves to `0` (or a stale/absent previous height) while `latest_height` is already large. The reward computed, `blocks_as_balance.saturating_mul(block_cost)`, pays for the entire historical block span in a single message rather than only the incremental advance since incentives began, and is transferred directly from the treasury plus minted as reputation-asset tokens [5](#0-4) .

### Impact Explanation
A relayer can drain the treasury account for an oversized one-time reward and receive a correspondingly inflated reputation-asset mint, by simply being first to deliver a consensus message for a state machine right after (or during) `update_cost_per_block` is configured, when that state machine's already-recorded height is large relative to zero/previous baseline. This is a direct loss of protocol/treasury funds and an unbacked mint of the reputation asset, both concrete impacts.

### Likelihood Explanation
This requires a specific but realistic configuration sequence: `update_cost_per_block` being set for a state machine whose `latest_commitment_height`/`previous_commitment_height` state is already non-trivial (e.g., a chain that had consensus updates flowing before incentives were enabled, or a rollback/edge-case leaving `PreviousStateMachineHeight` unset), consistent with the original report's "Medium" categorization contingent on setup/ordering conditions. Any relayer monitoring `update_cost_per_block` calls could opportunistically front-run the first qualifying `process_message` call.

### Recommendation
When `update_cost_per_block` is called to enable incentives for a state machine that has no `LastRewardedHeight` entry, seed `LastRewardedHeight` with the current `latest_commitment_height` at that time (rather than allowing the first reward calculation to fall back to `0`/a possibly stale `previous_commitment_height`). This ensures rewards only ever cover blocks advanced after incentives were actually turned on.

### Proof of Concept
1. A state machine accumulates consensus updates over time via normal ISMP flow, advancing `LatestStateMachineHeight` to a large value (e.g., height 100000), with `StateMachinesCostPerBlock` unset (no rewards paid yet).
2. Governance calls `update_cost_per_block(state_machine_id, cost_per_block)` to enable incentives [6](#0-5) .
3. A relayer submits any consensus message causing `on_executed` → `process_message` → `calculate_reward` to run for that `state_machine_id`. Since `LastRewardedHeight` has never been set, `baseline` resolves to `previous_commitment_height` (0 or stale), so `blocks = latest_height - baseline ≈ 100000` [3](#0-2) .
4. The relayer is paid `100000 * block_cost` from the treasury in a single call and minted the same amount in reputation asset, despite having only delivered one message covering the incremental advance, not the full historical span.

		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::update_cost_per_block())]

			origin: OriginFor<T>,
			state_machine_id: StateMachineId,
			cost_per_block: <T as pallet_ismp::Config>::Balance,
		) -> DispatchResult {
			T::IncentivesOrigin::ensure_origin(origin)?;

			StateMachinesCostPerBlock::<T>::mutate(state_machine_id.clone(), |maybe_cost| {
				*maybe_cost = Some(cost_per_block);

				state_machine_id,
				cost_per_block,
			});
