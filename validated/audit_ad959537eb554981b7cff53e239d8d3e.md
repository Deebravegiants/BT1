The strongest hydra analog to this bug class is the non-deterministic identifier generation in the hardware-wallet account creation flow, which mirrors the reorg report's root cause: relying on **non-deterministic values to construct a persistent identifier that gates access to a user's assets/keys**.### Title
Non-deterministic `walletId` fallback for Ledger devices causes unstable `WalletAccount` identity, splitting/losing access to synced hardware-wallet keys - ([File: features/hardware-wallets/src/module/hardware-wallets.ts])

### Summary
`Portal`/`VirtualLP`'s use of non-deterministic `create` to derive persistent token/tokenID addresses is analogous, in hydra, to `HardwareWallets.sync()` deriving the persistent `WalletAccount` identifier (`walletId`) from `randomBytes(32)` whenever the connected device does not expose a deterministic `getWalletId()` (true for all Ledger devices today). Because this identifier becomes baked into the `WalletAccount` name/id used to key stored public keys, address caches, and tx history, re-running the "non-deterministic" derivation for the *same physical device* can yield a different persistent identity, splitting or orphaning previously stored keys/addresses — the same class of impact described in the report (loss of access to previously-tied on-chain identifiers due to non-determinism).

### Finding Description
In `sync()`, the wallet computes the account's persistent fingerprint like this: [1](#0-0) 

```
const accountIndex = index ?? this.#walletAccounts.getNextIndex({ source })
// Compute the walletId fingerprint in the currently selected session context.
// ...
// Fallback to randomly generated id, since Ledger doesn't support this..
const walletId = (await device.getWalletId?.()) ?? randomBytes(32).toString('hex')
```

For Trezor, `getWalletId()` is deterministic — it is derived from the device's public key at a fixed path (`TREZOR_WALLET_ID_PATH = "44'/0'/0'"`), hashed with `md5`: [2](#0-1) 

For Ledger, no such method exists in the interfaces (`getWalletId` is optional, per `libraries/hw-common/src/types.ts`), so the code falls back to `randomBytes(32)` — a value with **no relationship to the physical device or its keys**. This `walletId` is then persisted as part of the `WalletAccount`'s identity: [3](#0-2) 

```
const walletAccount = new WalletAccount({
  label: `${label}${accountIndex === 0 ? '' : '_' + accountIndex}`,
  icon: source,
  source,
  model,
  index: accountIndex,
  id: walletId,
  isMultisig: !!isMultisig,
})
const walletAccountName = walletAccount.toString()
await this.#walletAccounts.create(walletAccount)
```

The `WalletAccount` model explicitly documents that `id` is meant to disambiguate accounts of the same index/device (e.g., across BIP39 passphrases): [4](#0-3) 

Because the Ledger `walletId` is regenerated via fresh randomness on every `sync()` call (not derived deterministically from the device/passphrase context as intended), a subsequent sync of the exact same physical Ledger device/account/passphrase produces a *different* `walletId`, and therefore a different `WalletAccount` name (`ledger_${accountIndex}_${walletId}`), as shown in the test fixtures: [5](#0-4) 

This is the direct analog of the reported bug: an identity/address that is supposed to be stable and tied to a specific origin (a physical device/session, in the reorg-bug's case a deployed contract) is instead derived non-deterministically, so re-derivation under the same real-world conditions silently produces a divergent identifier.

### Impact Explanation
Once a new, unrelated `walletId` is generated for what the user believes is "the same Ledger device", `addPublicKeysToWalletAccount` stores newly-synced public keys against the *new* `WalletAccount` name: [6](#0-5) 

The pre-existing `WalletAccount` (with the old random `walletId`), its cached addresses, associated tx history, and label remain under the stale identity. From the user's perspective this can present as: duplicate "Ledger" accounts appearing for the same physical device, address/tx history that appears to vanish from the account the user is actively using, and confusion about which account holds funds — a direct analog to users "losing" tokens/tokenIDs tied to an address that changed due to non-deterministic derivation. This is a wallet-state integrity/availability issue affecting the user's own funds visibility rather than an authentication/signing bypass, so severity is bounded — no attacker-controlled cross-account bleed or unauthorized signing is achieved through this path alone.

### Likelihood Explanation
This triggers under normal usage whenever `getWalletId()` is unavailable (all Ledger devices, per current interfaces) and the user re-syncs/reconnects the device (e.g., after disconnect, app restart, or re-adding the hardware wallet) — a common, non-attacker-driven, unprivileged-user workflow requiring no malicious actor, no reorg, and no adapter-level compromise.

### Recommendation
Derive `walletId` deterministically for devices lacking a native `getWalletId()`, e.g., a keyed hash (HMAC) of a fixed-path public key/xpub retrieved from the device (similar to Trezor's `md5(pubkey @ "44'/0'/0'")` approach), rather than `randomBytes(32)`. This ensures re-syncing the same physical device/passphrase-context always resolves to the same `WalletAccount` identity.

### Proof of Concept
1. Connect a Ledger device and call `hardwareWallets.sync({ accountIndex: 0 })` → `walletId = randomBytes(32)` → `WalletAccount` created as `ledger_0_<randomA>`, public keys stored under it (see test at `features/hardware-wallets/src/module/__tests__/hardware-wallets.test.ts:473-540` for the exact flow: `randomBytes.mockReturnValueOnce(...)` supplies `walletId`, then `create` builds `ledger_${accountIndex}_${id}`).
2. Disconnect/reconnect the same physical device (or restart the app) and call `sync()` again with the same `accountIndex` — because `device.getWalletId` is `undefined` for Ledger, a fresh `randomBytes(32)` value `randomB ≠ randomA` is generated.
3. Calling `create({ syncedKeysId })` again produces a second, distinct `WalletAccount` named `ledger_0_<randomB>`, separate from the original `ledger_0_<randomA>` — the previously-stored public keys, cached addresses, and transaction history under `<randomA>` are now orphaned/inaccessible from the newly active account, reproducing the "loss of access due to changed non-deterministic identifier" bug class from the reference report.

      this.#syncedKeysMap.has(syncedKeysId),
      `no synchronized keys found for id ${syncedKeysId}`
    )

    const { device } = await this.#getSelectedDevice()
    const source = device.descriptor.manufacturer
    const label = source === WalletAccount.LEDGER_SRC ? 'Ledger' : 'Trezor'
    const { accountIndex, model, walletId } = this.#syncedKeysMap.get(syncedKeysId)!

    // Create a new wallet account

      icon: source,
      source,
      model,
      index: accountIndex,
      id: walletId,
      isMultisig: !!isMultisig,
    })
    const walletAccountName = walletAccount.toString()
    await this.#walletAccounts.create(walletAccount)
    await this.#walletAccounts.setActive(walletAccountName)

    await this.addPublicKeysToWalletAccount({ walletAccount, syncedKeysId })

    return walletAccount
  }
