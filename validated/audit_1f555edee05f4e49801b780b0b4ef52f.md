### Title
Under-consumption of `inputAmount` in `LifiExternalAction.callRouter` strands tokens in the shared action contract, which a later unrelated transaction can capture as unbacked swap output - ([File: contracts/external-actions/swaps/LifiExternalAction.sol])

### Summary
`LifiExternalAction.callRouter` grants `router` an unlimited allowance and forwards fully attacker-supplied `externalActionMetadata` calldata without ever checking that the router actually pulled `inputAmount` of `inputToken`. Because the action contract's accounting only tracks the delta of `outputToken` balance (`getERC20OrETHBalance(outputToken) after - before`) and never verifies `inputToken` was fully consumed, any leftover `inputToken` remains stuck in the shared, stateful `LifiExternalAction` contract and its persistent unlimited allowance to `router`, which a later, unrelated Hinkal transaction can pull into its own swap and get credited as its own `swappedAmount`.

### Finding Description
The equality that should hold per transaction is:
`tokens leaving LifiExternalAction to router in this call == -deltaAmountChanges[0]` (the exact `inputAmount` that `Hinkal._externalTransact` sent into the action contract for this call, `contracts/Hinkal.sol:247-256`).

In `swap()` (`contracts/external-actions/swaps/ExternalActionSwap.sol:40-102`), `inputAmount = uint256(-deltaAmounts[0])` is computed but is **never passed into or enforced against** the actual router call in `callRouter` (`contracts/external-actions/swaps/LifiExternalAction.sol:16-36`):

```solidity
approveUnlimited(inputToken, router);
(bool success, ) = router.call(externalActionMetadata);
require(success, "LI.FI swap failed: erc-20 token");
swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
```

`callRouter` measures only the *output*-token delta, and the amount `router` actually pulls of `inputToken` is entirely determined by the attacker-crafted `externalActionMetadata`, decoupled from the `inputAmount` Hinkal transferred. If the crafted calldata causes `router` to pull less than `inputAmount`, the surplus `inputToken` remains in `LifiExternalAction` together with the standing unlimited approval created by `approveUnlimited`.

Because `LifiExternalAction` is a single shared, stateful contract used by every Hinkal user (registered once via `Hinkal.registerExternalAction`), this leftover balance and allowance persist across unrelated transactions. A later caller (the same attacker or a third party) can construct their own `externalActionMetadata` for a swap using the same `inputToken`, instructing `router` to pull both their own genuinely-transferred amount and the stranded dust from the earlier transaction (the unlimited allowance permits this). Since `callRouter`'s `swappedAmount` is derived purely from the resulting increase in `outputToken` balance, this "extra" pulled/converted value is folded into `swappedAmount`, then into `amountToSendToHinkal` (`ExternalActionSwap.sol:91-93`) and finally into the new caller's own UTXO (`ExternalActionSwap.sol:95-101`).

The top-level equality check in `Hinkal.transact` (`contracts/Hinkal.sol:98-146`, `balanceDif == amountChanges[i] + utxoAmount`) does **not** catch this: it only checks that Hinkal's own balance change is internally consistent with the UTXO amount the action contract reports, but it does not verify the *source* of the funds backing that UTXO. If the action contract inflates `swappedAmount` using someone else's stranded tokens, both `balanceDif` and `utxoAmount` scale together and the check passes trivially.

Nothing in `performHinkalChecks`, `verifyProof`, `rootHashExists`, `insertNullifiers`, or the circuit's `inTotal + amountChanges === outTotal` constraint can detect this, because those all validate the depositor's own proof/statement in isolation; none of them constrain what happens to funds once they leave Hinkal into a shared, stateful external-action contract, nor do they enforce that the external action fully consumes the amount handed to it.

### Impact Explanation
A caller (third party or the same depositor across two chained transactions) can be credited a UTXO backed by tokens they never deposited, at the expense of value that a previous, unrelated user sent into `LifiExternalAction` but which the router under-consumed. This is direct theft of another user's in-flight funds via minting an unbacked/over-backed UTXO, matching the **Critical** category (direct theft of in-flight user funds / minting shielded value without full backing). It is repeatable any time the shared action contract accumulates dust of a given token, which any user can trigger deliberately via crafted `externalActionMetadata`.

### Likelihood Explanation
Preconditions are fully within an unpermissioned attacker's control: they can deposit their own funds, choose the `externalActionId` for `LifiExternalAction`, and freely craft `externalActionMetadata` (per the stated attacker model). The only requirement is that the LI.FI/router calldata format allows specifying a swap amount smaller than what was actually approved/transferred (routers generally encode `amountIn` inside their own calldata rather than reading it from `msg.value`/an implicit "whole balance" convention), which is plausible for a generic aggregator call-forwarding design. No privileged role, oracle assumption, or router "bug" beyond ordinary calldata-driven pull semantics is needed — the flaw is that Hinkal-side code never verifies the pulled amount matches `inputAmount`.

### Recommendation
In `callRouter` (and generally in `ExternalActionSwap`), track and enforce the `inputToken` balance delta as well as the output delta: capture `inputToken` balance before the router call and require that the decrease equals exactly `inputAmount` (`require(balanceBeforeInput - getERC20OrETHBalance(inputToken) == inputAmount)`), reverting otherwise. Additionally, avoid `approveUnlimited` in favor of an exact, single-use approval (`approveERC20Token(inputToken, router, inputAmount)`, reset to zero after the call) so that no standing allowance can be exploited by a later, unrelated transaction, and so any residual balance cannot be pulled by future calls' `router.call` regardless of the encoded calldata.

### Proof of Concept
Foundry fork test plan:
1. Deploy `LifiExternalAction` pointed at a controllable stand-in for `router` (or use the real router with crafted calldata that specifies a smaller `amountIn` than approved) that pulls only part of the `inputAmount` transferred to it.
2. Craft `tx1` via `Hinkal.transact` (with a valid proof for attacker's own UTXO) with `externalActionId` = LifiExternalAction, `deltaAmountChanges[0] = -X` (full amount of token A), but `externalActionMetadata` causing router to pull only `X/2`. Assert `IERC20(A).balanceOf(address(LifiExternalAction)) == X/2` after `tx1`.
3. Craft `tx2` from a different EOA with a valid proof for their own smaller UTXO, `inputToken = A`, `deltaAmountChanges[0] = -Y` (their own genuine amount), but with `externalActionMetadata` that instructs the router to pull `Y + X/2` (using the standing unlimited allowance) and swap it all to `outputToken` B.
4. Assert that `amountToSendToHinkal` credited in `tx2`'s resulting UTXO (and the corresponding `utxoAmount` accepted by `Hinkal.transact`'s equality check at `contracts/Hinkal.sol:137-146`) exceeds what `-deltaAmountChanges[0]` (`Y`) alone should have produced, i.e., `swappedAmount(tx2) > f(Y)` while `f(Y + X/2)` matches — proving tx2's depositor was credited value derived from tx1's stranded `X/2`.
