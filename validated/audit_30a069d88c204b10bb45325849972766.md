### Title
Spot Uniswap V4 pool price used unguarded (and unclamped) for order pricing enables manipulated-price fund drain of the Simplex intent solver - (File: `sdk/packages/simplex/src/strategies/fx.ts`)

### Summary
`FXFiller.resolveLegRates` prices curveless (venue-priced) pairs directly off the **current Uniswap V4 pool spot price** (`sqrtPriceX96`/tick) rather than a manipulation-resistant TWAP, exactly the same class of flaw as the referenced `USSDRebalancer.rebalance` bug, which relied on the pool's instantaneous liquidity state instead of a TWAP. The only defense is an *optional*, static-reference deviation guard (`checkPriceGuard`), and the output amount actually paid out (`policyMaxOutput`) has its overfill ceiling explicitly disabled, so a manipulated spot price flows straight through to the amount the solver disburses.

### Finding Description
`UniswapV4FundingPlanner.getExoticTokenPrice` → `computeDirectPoolPriceUsd` reads the pool's live `sqrtPriceX96` from the most-liquid qualifying position and returns it as the USD price with no averaging window: [1](#0-0) [2](#0-1) 

This spot price is consumed by `FXFiller.resolveLegRates` for any curveless pair whose `token0` is a USD stablecoin, and used unchanged as the fill rate (`rate = 1 / venueUsd`): [3](#0-2) 

The only mitigation, `checkPriceGuard`, compares the live quote against a **static, operator-configured reference price** with a fixed `maxDeviationBps`, not a TWAP or execution-cost-aware check — and it is explicitly optional (`referencePrice`/`maxDeviationBps` may both be omitted, "leave the chain unguarded"): [4](#0-3) [5](#0-4) 

Even when the guard is configured, an attacker can move the spot price anywhere inside the allowed deviation band (a "manipulated, stale, or thin pool," per the code's own doc comment) and still pass the check, since the guard only bounds deviation from a fixed number, not from a true time-weighted market price. This is architecturally the same weakness the external report describes: an on-chain AMM's instantaneous state (reserves / tick) is trusted as a price oracle for an automated rebalancing/filling decision that moves real funds, and it can be pushed within one block via a swap.

Compounding this, the amount actually disbursed from this manipulated rate (`policyMaxOutput`, computed in `computeLegPolicyOutput`) is **not capped** — the overfill ceiling is deliberately disabled for all legs, explicitly including venue-priced ones, per the code's own comment: "the clamp is DISABLED... including venue-priced legs (e.g. Uniswap V4). NOTE: this removes the per-leg loss bound that previously protected against a bug / stale cache / manipulated venue price": [6](#0-5) 

The developers' own flow documentation independently confirms the design gap: "`checkPriceGuard` is the only defense on this path, and it checks deviation from a static reference, not execution cost." [7](#0-6) 

### Impact Explanation
An attacker (an unprivileged party who can both swap in the referenced Uniswap V4 pool and submit an intent order the solver evaluates) can push the pool's spot price toward the edge of, or past, whatever guard is configured, then submit an order that `resolveLegRates`/`calculateProfitability` prices at that manipulated rate. Because `state.refresh()` reads pool state on-demand right before pricing and the payout cap is disabled, the solver will compute and pay out `policyMaxOutput` at the manipulated rate with no execution-cost or size-impact adjustment, directly transferring solver funds (the exotic token or the stablecoin, depending on direction) to the attacker at an off-market rate — draining the solver's inventory analogous to how the original report drained the protocol's collateral. This is a fund-loss vulnerability directly reachable by an unprivileged intent submitter/order relayer, matching the "intent solver" actor class in scope.

### Likelihood Explanation
Any Uniswap V4 pool, especially one holding modest liquidity as used for exotic-token positions (the doc explicitly names cNGN-type "exotic" tokens), can be moved with a single swap transaction; the guard band (`maxDeviationBps`) is a known, static, operator-published value the attacker can read from config or infer, so the attack can be tuned to stay inside it while still moving the effective price materially, or executed against unguarded chains where `referencePrice`/`maxDeviationBps` are omitted entirely (an explicitly supported configuration). No special privilege is needed — only the ability to swap in the pool and to submit or trigger evaluation of an order.

### Recommendation
Replace or supplement the instantaneous `sqrtPriceX96`/tick read in `computeDirectPoolPriceUsd` with a TWAP oracle (e.g., Uniswap V4's truncated oracle or an external oracle) for venue pricing, make the price guard mandatory rather than optional for any venue-priced pair, and reinstate a hard cap on `policyMaxOutput` (re-enable the overfill ceiling, particularly for venue-priced legs) so a manipulated or stale quote cannot translate into an unbounded payout regardless of guard configuration.

### Proof of Concept
1. Configure (or find deployed) a Simplex `FXFiller` instance serving a curveless, Uniswap-V4-venue-priced pair (`token0` = USD stable, `token1` = exotic), per `docs/content/developers/evm/simplex/pricing.mdx`, either with no `referencePrice`/`maxDeviationBps` guard, or with a guard whose band the attacker can compute from public config.
2. In the same block (or immediately before order submission), swap a sufficient amount in the exotic/USDC (or USDT) Uniswap V4 pool referenced by the solver's configured position to move `sqrtPriceX96` so that `computeDirectPoolPriceUsd` returns a price favorable to the attacker (understating the exotic token's USD value if the attacker wants to receive exotic tokens cheaply, or overstating it to sell into the solver at an inflated rate) — staying inside `maxDeviationBps` if a guard is configured.
3. Submit (or have relayed) an intent order to the solver's `IntentGateway`/order-filling path that resolves to this pair; `calculateProfitability` → `resolveLegRates` fetches the just-manipulated spot price via `venueUsdPrice`, `checkPriceGuard` passes (band not breached or unguarded), and `computeLegPolicyOutput` computes `policyMaxOutput` at the manipulated rate.
4. Because the overfill ceiling is disabled (`fx.ts` lines 664-701), the solver fills the order at the full manipulated-rate amount, executing the fill transaction (`fillOrder`) and transferring solver funds to the attacker at an off-market price.
5. Reverse the initial pool swap (or let arbitrageurs restore price), realizing the profit extracted from the solver's inventory. Repeating this against the same or multiple venue-priced pairs drains solver funds analogous to the original report's collateral drain.

	private checkPriceGuard(orderId: string | undefined, chain: string, venueToken1PerUsd: Decimal): boolean {
		const guard = this.priceGuard?.get(chain)
		if (!guard || guard.reference.lte(0)) return true

		const deviationBps = venueToken1PerUsd.minus(guard.reference).abs().div(guard.reference).mul(10000)
		if (deviationBps.gt(guard.maxDeviationBps)) {
			this.logger.warn(
				{
					orderId,
					chain,
					venuePrice: venueToken1PerUsd.toString(),
					referencePrice: guard.reference.toString(),
					deviationBps: deviationBps.toFixed(2),
					maxDeviationBps: guard.maxDeviationBps,
				},
				"Rejecting order: Uniswap venue quote outside price-guard band",
			)
			return false
		}
		return true
	}
