### Title
Unchecked ERC20 `transfer()` boolean return value in Tron `IntentGatewayV2.withdraw`/`SweepDust` allows escrow funds to be marked settled without actually being delivered - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` escrows tokens using `safeTransferFrom` (via OpenZeppelin's `SafeERC20`), but when releasing escrowed tokens back out to beneficiaries — in `withdraw()` (fill/refund settlement) and in the `SweepDust` handler inside `onAccept()` — it uses raw low-level `.call()` invocations of `IERC20.transfer` and only checks that the *call itself* did not revert (`success`), never decoding and checking the actual `bool` return value encoded in the return data.

### Finding Description
In `withdraw()`, escrowed token amounts are released like this: [1](#0-0) 

And the `SweepDust` branch of `onAccept()` does the same: [2](#0-1) 

For a standards-compliant ERC20 token whose `transfer()` returns `false` on failure instead of reverting (a legitimate ERC20 behavior explicitly allowed by the spec and used by several real-world tokens), the low-level `.call()` will report `success == true` even though no tokens were actually moved, because the call executed without reverting — it just returned encoded `false` in its return data. The code never inspects that return data, so `if (!success) revert TransferFailed();` never fires, and the function proceeds as though the transfer succeeded.

This is in direct contrast to the deposit side of the same contract, which correctly uses `SafeERC20.safeTransferFrom` (which does check the returned boolean): [3](#0-2) 

The contract already imports and uses `SafeERC20` elsewhere (`using SafeERC20 for IERC20;`), so this asymmetry is a genuine gap rather than an intentional design choice: [4](#0-3) 

`withdraw()` is invoked from `onAccept()`, which is called by the ISMP host upon delivery of a relayed `RedeemEscrow`/`RefundEscrow` POST request — i.e., driven by any relayer submitting a valid proof for a dispatched cross-chain message, not by a privileged actor: [5](#0-4) 

Because `withdraw()` unconditionally decrements `_orders[commitment][token]` and marks `_filled[commitment] = beneficiary` (finalizing the order) regardless of whether the token transfer actually delivered funds: [6](#0-5) 

a silent `transfer()` failure permanently freezes the beneficiary's escrowed funds — the order is marked filled/refunded, the escrow accounting is zeroed out, but the beneficiary never receives the tokens, and there is no remaining code path to reclaim them.

### Impact Explanation
This causes permanent loss/freezing of user funds held in escrow by the IntentGateway on Tron: once `withdraw()` runs, `_orders[commitment][token]` is decremented and `_filled[commitment]` is set, finalizing the order irreversibly, even though the beneficiary received nothing if the token's `transfer()` returned `false` instead of reverting. This qualifies as concrete permanent freezing of escrowed intent funds, reachable purely from the normal relayed-message settlement path (`RedeemEscrow`/`RefundEscrow`) or the `SweepDust` admin/relay path.

### Likelihood Explanation
This requires the escrowed/output token to be one whose `transfer()` returns `false` on failure rather than reverting (a valid, spec-compliant, and not-uncommon ERC20 pattern). Since `IntentGatewayV2` is a generic cross-chain intents gateway intended to support arbitrary ERC20 tokens supplied by users/solvers as `order.inputs`/`order.output.assets`, such tokens are plausible inputs, and the failure could also be triggered deliberately by an attacker-controlled or blocklist/pausable-style token used as the escrowed asset, or by a beneficiary address that a token's transfer logic rejects (e.g., blocklisted recipient) without reverting.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only checks in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer`, consistent with how the deposit side already uses `safeTransferFrom`. `SafeERC20` correctly reverts both when the call reverts and when the call succeeds but returns `false` (or returns no data for non-standard tokens, which it also handles safely).

### Proof of Concept
1. Deploy an ERC20 token whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., a token that checks a blocklist and returns `false` for blocklisted recipients, or a paused-state token that returns `false` while paused).
2. Place a cross-chain order (`placeOrder`) using this token as an input, so it becomes escrowed via `safeTransferFrom` (deposit path works fine).
3. Have the order filled/cancelled on the destination chain, triggering `RedeemEscrow`/`RefundEscrow` dispatch and eventual relay/delivery to `onAccept()` on the Tron gateway.
4. Arrange for the token's `transfer()` call inside `withdraw()` to return `false` (e.g., the beneficiary is blocklisted, or the token is paused at redemption time) without reverting.
5. Observe that `withdraw()` does not revert: `_orders[commitment][token]` is decremented, `_filled[commitment]` is set, and `EscrowReleased`/`EscrowRefunded` is emitted — yet the beneficiary's token balance did not increase, permanently losing access to those escrowed funds.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];

            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
