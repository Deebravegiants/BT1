### Title
Webhook `shop` Domain Is Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by verifying only the raw HTTP body against the `X-Shopify-Hmac-Sha256` header, but the `shop` identity handed to the app's webhook handler is read from the unauthenticated `shop-domain` header. Because a single app's `api_secret_key` is shared across every shop that installs it, an attacker who installs the app on their own (attacker-controlled) shop can capture a validly-signed webhook, then replay the exact body/HMAC pair while substituting an arbitrary victim `shop-domain` header, producing a request that passes verification but is falsely attributed to the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read directly from an unsigned header: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which computes the HMAC solely over `to_signable_string` (i.e. the body), and then unconditionally forwards `request.shop` to the handler as trusted webhook metadata: [3](#0-2) 

`HmacValidator.validate_signature` compares only against the body-derived signable string, with no shop binding: [4](#0-3) 

The identity binding that should hold is:
`shop attributed to the webhook (request.shop, from header)` == `shop cryptographically bound to the signed payload`

but the actual binding enforced is only:
`HMAC(raw_body, api_secret_key)` == `received HMAC`

Since `api_secret_key` is the same value for every shop that installs a given app, any legitimate webhook payload/signature pair obtained from one shop (including an attacker's own shop) remains valid regardless of which `shop-domain` header accompanies it. `Registry.process` never re-derives or checks that the `shop-domain` header corresponds to the shop that actually owns the signed body, so the shop identity is fully attacker-controlled once a single valid (body, HMAC) pair is known.

The library's own documentation states that `Registry.process` will "verify the request did indeed come from Shopify" before invoking the handler, which is a stronger guarantee than what is actually implemented, since the `shop` attribute of the verified `WebhookMetadata` is not itself verified.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an attacker who is merely a legitimate, unprivileged installer of the app on their own store can forge a "verified" webhook event and force the host application to process it as though it originated from an arbitrary victim shop. If the host application uses `WebhookMetadata#shop` to look up sessions, update per-shop state, trigger uninstall/data-erasure flows, or otherwise key any privileged action off of the shop identity from a processed webhook (a natural and expected usage per the library's `Registry.process` documentation), the attacker can manipulate or corrupt another tenant's data/state without ever compromising that tenant's credentials. This satisfies the "cross-tenant access" criterion for Critical severity.

### Likelihood Explanation
Likelihood is high for any app built on this gem that relies on `WebhookMetadata#shop` as an authenticated identity (which the docs actively encourage by describing `process` as verifying that "the request did indeed come from Shopify"). The only prerequisite is the ability to install the target app on an attacker-owned development/trial store — a normal, unprivileged action available to any internet user — after which the attacker can capture one legitimate (body, HMAC) pair and replay it with an arbitrary `shop-domain` header.

### Recommendation
Bind the shop identity into the value that is actually verified, e.g., include `shop`/`topic`/`webhook-id` in the signable string (mirroring the input structure used for `AuthQuery`/`VerifiableQuery`) so that the HMAC covers the full identity of the event, not just the body bytes. Alternatively, require host applications to cross-check `WebhookMetadata#shop` against a shop for which a session already exists (which does not fully close the gap for first-time installs) or document explicitly and prominently that `shop` in `WebhookMetadata` is NOT cryptographically authenticated and must not be trusted without additional out-of-band verification.

### Proof of Concept
1. Attacker creates a free/trial Shopify store `attacker.myshopify.com` and installs the target app, causing Shopify to deliver a legitimate webhook (e.g. `orders/create`) to the app's registered endpoint with a valid `X-Shopify-Hmac-Sha256` header computed over the raw JSON body using the app's shared `api_secret_key`.
2. Attacker captures the raw request body and its `X-Shopify-Hmac-Sha256` value.
3. Attacker sends a new HTTP request to the same webhook endpoint using the identical raw body and `X-Shopify-Hmac-Sha256` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` — the forged request passes verification.
5. The handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` even though the payload was never generated by or for that shop, and any shop-scoped action the handler performs will be executed against the victim's tenant context.
