### Title
Unlimited router allowance in `ExternalActionSwap`/`LifiExternalAction.callRouter` lets a caller drain leftover token balances of the swap contract via unchecked `externalActionMetadata` — ([File: contracts/external-actions/swaps/LifiExternalAction.sol])

### Summary
`LifiExternalAction.callRouter` grants `router` an **unlimited, persistent ERC20 allowance** over the `ExternalActionSwap` contract's balance and then blindly executes attacker/relay-supplied `externalActionMetadata` against `router`, measuring the swap result only as an output-token balance delta. Nothing in `swap()` or `callRouter()` constrains the router call to spend exactly `inputAmount` of `inputToken`; the router can pull any amount up to `type(uint256).max` from `ExternalActionSwap`'s balance. This is the same class of bug as H-10: a caller-influenced parameter (here, the swap `amount`/route encoded in the opaque LI.FI payload, analogous to `tradeType`) is not constrained to the value the protocol accounting assumes was moved, allowing more value to be extracted than was deposited for that trade.

### Finding Description
`ExternalActionSwap.swap()` computes `inputAmount = uint256(-deltaAmounts[0])` [1](#0-0) , which is exactly the amount `Hinkal._externalTransact` transferred into the contract just before invoking `runAction` [2](#0-1) . It then calls `callRouter(inputToken, inputAmount, outputToken, circomData.externalActionData.externalActionMetadata)` [3](#0-2) .

In `LifiExternalAction.callRouter`, for ERC20 input tokens the contract calls `approveUnlimited(inputToken, router)`, which sets the allowance to `type(uint256).max` and only re-approves if the current allowance is below `type(uint256).max/2` (i.e., the max approval persists across calls) [4](#0-3) . It then executes `router.call(externalActionMetadata)` with **no validation that the call only spends `inputAmount`** of `inputToken`, and measures `swappedAmount` purely as the output-token balance delta before/after the call [5](#0-4) .

Because the allowance is unlimited and persistent, and the router call is never checked to only debit `inputAmount` of `inputToken` from `ExternalActionSwap`'s own balance, any residual `inputToken` balance already sitting in the `ExternalActionSwap` contract (e.g., dust left over from a prior partial-fill swap, rounding, or a previous user's aggregator quote that didn't consume 100% of the approved amount) can be pulled in by a *different* user's crafted `externalActionMetadata` that requests a larger sell amount than their own `inputAmount`. The circuit/`Hinkal.sol` balance-diff checks only constrain the **output** side (`balanceDif == amountChanges[i] + utxoAmount`) using whatever `swappedAmount` actually occurred [6](#0-5) ; there is no equality anywhere that ties the *input* side consumed by the router call back to the specific `inputAmount` the attacker deposited for that trade. This breaks the balance equation the report's rule describes: "value moved by Hinkal or an external action but not counted in the balance equation" — the extra input-token value consumed from the contract's leftover balance is never debited against the attacker's own `amountChanges`.

### Impact Explanation
If the `ExternalActionSwap`/`LifiExternalAction` contract accumulates any residual `inputToken` balance (undelivered dust from partial fills, rounding remainders from prior swaps, or funds temporarily in flight), a malicious user can craft `externalActionMetadata` that causes the LI.FI router to pull that residual balance in addition to their own deposited `inputAmount`, receiving proportionally more `outputToken` while only being debited for their own `inputAmount` in `circomData.amountChanges`. This is theft of in-flight/leftover funds that belong to the protocol/other users' unswept trades, at no cost to the attacker — matching the "direct theft of ... in-flight user funds" / "theft ... of protocol fees" criteria.

### Likelihood Explanation
Likelihood depends on residual balances actually existing in the `ExternalActionSwap` contract at the time of the attack (e.g., an aggregator quote that under-fills, leaving unspent `inputToken`, since there is no post-call check that the entire `inputAmount` was consumed). Given that LI.FI/aggregator swaps commonly do not guarantee 100% exact consumption of an approved amount and the contract never sweeps or verifies unspent input balances, dust accumulation over time is plausible, making this a real, not purely theoretical, path — though it is opportunistic rather than always-exploitable on every single transaction.

### Recommendation
- Replace `approveUnlimited` with a bounded approval scoped to exactly `inputAmount` for each call (approve `inputAmount`, and reset/verify the allowance is fully consumed or reset to 0 after the call), instead of a permanent max approval.
- After the router call, assert that `IERC20(inputToken).balanceOf(address(this))` decreased by exactly `inputAmount` (no more, no less), reverting otherwise, so that leftover/dust balances can never be swept into someone else's trade.
- Alternatively, transfer only `inputAmount` of `inputToken` into a per-call context (or sweep/zero any residual balance back to `Hinkal` before granting allowance) so the router can never access more than the amount belonging to the current transaction.

### Proof of Concept
Conceptual/no on-chain PoC executed (index-only investigation); concrete PoC would require:
1. Trigger a swap via `Hinkal.transact` → `LifiExternalAction` where the aggregator quote under-fills, leaving `inputToken` dust in the `LifiExternalAction` contract (or otherwise get dust deposited there, e.g. from a failed/partial prior transaction).
2. As a second, unrelated user, submit a `transact` call with a small legitimate `inputAmount` deposit, but with `externalActionMetadata` crafted (LI.FI allows arbitrary calldata to the router) to sell `inputAmount + dust` of `inputToken` (relying on the persistent unlimited allowance from step 1's `approveUnlimited`).
3. Observe `swappedAmount` (and thus the resulting shielded output UTXO) reflects the larger sell amount, while `circomData.amountChanges[0]` for the attacker only reflects their own smaller `inputAmount` — netting the attacker the value of the dust for free.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
