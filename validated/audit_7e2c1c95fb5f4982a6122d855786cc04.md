### Title
Wallet owner's Emporium signature does not bind `feeStructure.feeToken`, allowing arbitrary-asset fee drain from `HinkalWallet` - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
The `EmporiumUpgradeable.verifyWallet` function requires `stack.signerAddress` (the owner of a `HinkalWallet`) to EIP-712 sign the `EMPORIUM_SIGNATURE_TYPEHASH`, which covers `message`, the hashed `ops` array, `maxFee`, and `deadline`. It does **not** cover `circomData.feeStructure.feeToken` or `circomData.relay`. Because `payRelayFees` allows any `feeToken`/relay-fee amount up to the *unscoped* `maxFee` value to be pulled directly from the signer's `HinkalWallet` via `doSendToRelay`, a transaction submitter (who only needs a valid, unrelated Hinkal ZK proof for their own shielded balance, not the wallet owner's key) can choose which ERC20 asset is debited from the wallet, independent of the signer's intent.

### Finding Description
`EmporiumUpgradeable.runAction` decodes an `EmporiumStack` from `circomData.externalActionData.externalActionMetadata` and calls `verifyWallet(stack, circomData)`: [1](#0-0) 

The EIP-712 typehash that is actually signed by the wallet owner is: [2](#0-1) 

This binds `message`, the hash of `ops` (`endpoint`, `invokeWallet`, `value`, `callData`), `maxFee` and `deadline`. It never includes `feeStructure.feeToken`, `feeStructure.variableRate`, or `circomData.relay`.

After the signed `ops` are executed, `payRelayFees` computes and pays a relay fee **outside** the signed `ops` list: [3](#0-2) 

Critically, when the fee token is not among `circomData.erc20TokenAddresses` being processed in this transaction (`foundToken == false`), the code still charges `feeStructure.flatFee` of `feeStructure.feeToken` — an address chosen entirely by whoever submits `Hinkal.transact()`, not by the wallet owner: [4](#0-3) 

The fee is then pulled directly from the wallet contract's own balance of that arbitrary token via `IHinkalWallet.doSendToRelay`, which only checks `msg.sender == emporium`: [5](#0-4) [6](#0-5) 

The only bound the signer placed is `feeStructure.flatFee <= stack.maxFee`, checked as a raw numeric value: [7](#0-6) 

Since `maxFee` is a plain `uint256` with no token/decimals context, and `feeStructure.feeToken` is not part of the signed digest, `feeStructure.feeToken` and `circomData.relay` are values that are asserted-integrity-checked only against `calldataHash`/`signedMessageHash` computed for the **prover's own shielded-balance EdDSA signature** (`CircomDataBuilder.getHashedCalldata`/`getSignedMessageHash`), not against the wallet owner's ECDSA authorization: [8](#0-7) 

This is a direct structural analog of the reported bug class: an entity whose asset is at stake (the wallet owner/"seller") signs an operation, but a field that materially controls what asset/how much value leaves their custody (`feeToken`) is left outside the signed digest, letting an unrelated party (the "operator"/relay/tx submitter) fill it in unilaterally — a wallet op (asset debit) not authorized by the signer.

### Impact Explanation
This breaks the equality "amount debited from `HinkalWallet` == what `signerAddress` explicitly authorized." An attacker who is any user able to submit a valid `Hinkal.transact()` (using their own unrelated shielded UTXOs, external action id = Emporium) can attach a previously-obtained, otherwise-legitimate signed `EmporiumStack` (message/ops/maxFee/deadline) and freely choose `feeStructure.feeToken` to point at any high-value ERC20 the target `HinkalWallet` holds, draining up to `maxFee` raw units of that asset — regardless of the decimals/value the signer intended when agreeing to `maxFee` for a different, expected fee token. This is theft of user (wallet owner) funds routed through the relay-fee mechanism, i.e., unauthorized asset movement from a wallet never approved for that specific asset by its owner. This satisfies the High/Critical bar: "theft or permanent freezing of protocol/relay fees" / "executing calls or moving assets a wallet owner ... never authorised."

### Likelihood Explanation
Exploitation requires: (1) a previously valid signed `EmporiumStack` (obtainable because signatures are message/ops/maxFee/deadline based and can be replayed by anyone who can observe or receive it off-chain before use, since nothing ties it to a specific relay or fee token), and (2) the attacker's own valid Hinkal ZK proof over their own shielded balance to drive the `Hinkal.transact()` call (permissionless). Both are attacker-controlled/observable, making this practically reachable by any relay operator or user who intercepts/relays a signed Emporium operation, without needing the wallet owner's private key.

### Recommendation
Include `circomData.feeStructure.feeToken`, `circomData.feeStructure.variableRate`, and `circomData.relay` in the `EMPORIUM_SIGNATURE_TYPEHASH` digest that `stack.signerAddress` signs, so the wallet owner explicitly authorizes which asset (and to which relay) any fee can be taken from, in addition to the numeric cap `maxFee`. Alternatively, restrict `feeStructure.feeToken` to be one of `circomData.erc20TokenAddresses` already covered by the transaction's own accounting, removing the unconstrained fallback branch (`!foundToken && feeStructure.flatFee != 0`) that allows fee collection in a token unrelated to the transacted set.

### Proof of Concept
1. Wallet owner (`signerAddress`) signs a legitimate `EmporiumStack` (`ops`, `maxFee = 1000`, `deadline`) intending the relay fee to be paid in USDC (6 decimals), expecting at most ~$1000 worth of exposure.
2. A malicious relay/tx-submitter builds a `Hinkal.transact()` call using their own shielded UTXOs and the Emporium external action, embedding the *same signed* `EmporiumStack` in `externalActionMetadata`, but sets `circomData.feeStructure = { feeToken: <wallet's WBTC or other low-decimal high-value token>, flatFee: 1000, variableRate: 0 }` and an `erc20TokenAddresses` set that does not include that token (so `foundToken` stays `false`).
3. `EmporiumUpgradeable.verifyWallet` recovers `signerAddress` successfully because the signature only covers `message/ops/maxFee/deadline`, all of which are honored as originally signed.
4. `payRelayFees` reaches the `!foundToken && feeStructure.flatFee != 0` branch, calling `payRelay(relay, signerAddress, 1000, <WBTC address>)`, which invokes `IHinkalWallet(signerAddress).doSendToRelay(relay, 1000, WBTC)`, transferring `1000` raw units of WBTC (a materially different and larger value than the USDC the owner intended) out of the wallet to the relay.
5. The wallet owner never signed anything approving WBTC as the fee asset — only the numeric cap `1000`, which was denomination-agnostic in the signature.

    function payRelayFees(
        CircomData calldata circomData,
        address signerAddress,
        int256[] calldata deltaAmountChanges
    ) internal {
        FeeStructure calldata feeStructure = circomData.feeStructure;

        bool foundToken = false;

        for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            // tokens deposited into Emporium are not charged
            if (deltaAmountChanges[i] >= 0) {
                continue;
            }

            address erc20TokenAddress = circomData.erc20TokenAddresses[i];
            bool isFeeToken = erc20TokenAddress == feeStructure.feeToken;

            if (isFeeToken) {
                foundToken = true;
            }

            uint256 relayFee = 0;
            uint256 flatFee = isFeeToken ? feeStructure.flatFee : 0;

            if (signerAddress == address(0)) {
                uint256 sumAbs = uint256(-deltaAmountChanges[i]);

                EmporiumStorageVars storage $ = _getEmporiumStorage();
                relayFee = $._hinkalHelper.calculateRelayFee(
                    sumAbs,
                    flatFee,
                    feeStructure.variableRate
                );
            } else {
                relayFee = flatFee;
            }

            payRelay(
                circomData.relay,
                signerAddress,
                relayFee,
                erc20TokenAddress
            );
        }

        if (!foundToken && feeStructure.flatFee != 0) {
            require(
                signerAddress != address(0),
                "Gas Token in Emporium is not found"
            );

            payRelay(
                circomData.relay,
                signerAddress,
                feeStructure.flatFee,
                feeStructure.feeToken
            );
        }
    }

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
