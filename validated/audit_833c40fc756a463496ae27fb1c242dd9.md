### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated HTTP headers that are never included in the HMAC computation. `Registry.process` accepts any request whose body/HMAC pair validates and then hands the handler the header-derived `shop` value as the trusted tenant identifier. This breaks the identity binding `hmac == HMAC(body, shop, topic, ...)` down to `hmac == HMAC(body)`, letting an attacker replay a legitimately-signed body under a different `shop-domain` header.

### Finding Description
`HmacValidator.validate` computes the signature strictly over `verifiable_query.to_signable_string`, and for webhook requests that method returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` values used downstream are read straight from HTTP headers with zero cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC-over-body, then trusts `request.shop` (and `request.topic`) as the tenant/topic identity for the handler call: [3](#0-2) 

The library's own documentation confirms that `data.shop` is meant to be used by host apps as the authoritative tenant identifier passed to `WebhookHandler#handle`: [4](#0-3) 

**Attack sequence:**
1. Attacker installs the target app on their own (unprivileged) Shopify dev shop `attacker-shop.myshopify.com`. Shopify legitimately delivers a webhook to the app's endpoint with a real, valid `(raw_body, hmac)` pair and headers `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker captures that outgoing request from their own shop (they own the request, no interception of others' traffic is required) — a fully unprivileged action.
3. Attacker resends the exact same `raw_body`/`hmac` pair directly to the app's public webhook endpoint but swaps the header to `shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `webhook-id`).
4. `HmacValidator.validate` recomputes `HMAC(raw_body)`, which is unchanged and still valid — the header spoof is invisible to the check.
5. `Registry.process` dispatches to the handler with `request.shop == "victim-shop.myshopify.com"`, so the app processes attacker-controlled body content as if it originated from the victim tenant.

This is exactly the bug class in the report — a value acted upon (`shop`) is not covered by the integrity check (`HMAC`), enabling identity confusion — applied to the shop-tenant binding instead of the deposit-amount binding.

### Impact Explanation
Any app built on this gem that uses `data.shop` from the webhook handler to key per-tenant state (e.g., updating billing status, order records, GDPR redaction flags, or metafields for "victim-shop") will attribute attacker-supplied webhook bodies to a shop the attacker does not control. This is cross-tenant access/data injection across the multi-tenant boundary that this library is responsible for enforcing at the webhook ingress point.

### Likelihood Explanation
The attacker needs no credentials beyond the ability to install the app on any store they control (a normal, unprivileged action available to any Shopify developer/merchant) and the ability to send an arbitrary HTTP POST to the app's public webhook endpoint (which is inherently internet-reachable and unauthenticated by design). No `client_secret`, access token, or TLS interception is required.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed payload used for verification, or otherwise cryptographically bind them to the HMAC before trusting `request.shop`/`request.topic` in `Registry.process`. At minimum, the gem should provide (and `process` should perform) a check that the shop asserted by the header matches a shop the app has an active registration/session for, rather than trusting the header value outright once body-HMAC validation passes.

### Proof of Concept
```ruby
# 1. Attacker installs app on their own shop and captures a real webhook delivery:
raw_body = '{"id":1,"note":"legit"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# 2. Attacker replays the identical body/hmac pair, only changing the shop header:
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed
  "shopify-webhook-id" => "any-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (HMAC only covers raw_body)
# => handler.handle receives shop: "victim-shop.myshopify.com" despite the request
#    never having been sent by or for that shop.
```
