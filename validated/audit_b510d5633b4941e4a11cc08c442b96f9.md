### Title
Webhook HMAC only covers the request body, letting shop domain (tenant identity) be spoofed via header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string solely from the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from HTTP headers that are never part of the HMAC-signed payload. `Registry.process` trusts these header-derived values (in particular `shop`) to build the `WebhookMetadata` passed to the app's handler, after only checking that the body's HMAC is valid. This lets anyone who can obtain one genuine signed webhook body (e.g., by installing the app on their own shop and having Shopify deliver a real webhook) replay that exact body/HMAC pair to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` header to a victim shop, since the signature never binds to the shop field.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 
`Request#shop` (and `topic`, `api_version`, `webhook_id`) are pulled straight from headers, none of which are covered by `to_signable_string`: [2](#0-1) 
`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity handed to the app's business logic: [3](#0-2) 
`HmacValidator.validate` only compares the digest against `verifiable_query.to_signable_string`, i.e., the body bytes — it has no knowledge of, and does not bind to, the shop header: [4](#0-3) 

The identity binding that should hold is: `shop header value == shop that the HMAC-secret-holder (Shopify) actually intended this body for`. Because the HMAC never covers the shop header, this equality is not enforced by the gem — any request with a body/HMAC pair that is valid for the shared `api_secret_key` will pass validation regardless of which shop header accompanies it.

### Impact Explanation
This crosses the tenant boundary the report's bug class targets (the analog: "a shop authenticated versus the shop stored/acted on" is not the same value). An app built on this gem uses `data.shop` from `WebhookMetadata` to determine which tenant's records to update/delete (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, or any topic with a static/predictable body). An attacker who legitimately installs the app on their own shop receives real, validly-signed webhook deliveries. Because the HMAC is computed over body bytes only (and many topics have static or attacker-influenced body content), the attacker can replay that valid body+HMAC to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header pointing at a victim shop. `Registry.process` will accept it as an authentic event for the victim shop, causing the host app to act on/mutate victim-tenant state (cross-tenant access/confusion) using attacker-supplied context.

### Likelihood Explanation
Requires only that the attacker be able to install the target app on a shop they control (a normal, low-privilege action for any Shopify merchant) and be able to send arbitrary HTTP requests to the app's public webhook endpoint — no access token, `api_secret_key`, or TLS interception needed. Topics with static or minimal bodies (e.g., `app/uninstalled` typically has `{}`) make this straightforward to reproduce.

### Recommendation
Include the shop domain (and ideally topic) in the HMAC-signed material, or otherwise cryptographically bind the shop header to the payload before trusting it, e.g., verify the header shop matches a shop already associated with a previously stored session/access token before acting, and document/enforce that `WebhookMetadata#shop` must not be trusted for authorization decisions without this cross-check.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook with a static/predictable body, e.g., `app/uninstalled` delivered with raw body `{}` and a valid `X-Shopify-Hmac-Sha256` header computed by Shopify using the app's shared `api_secret_key`.
2. Capture the raw body and the `X-Shopify-Hmac-Sha256` value from that legitimate delivery.
3. Replay a forged HTTP POST to the app's webhook endpoint with the same raw body `{}` and the same `X-Shopify-Hmac-Sha256` header, but set `X-Shopify-Shop-Domain: victim.myshopify.com` and `X-Shopify-Topic: app/uninstalled`.
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate` succeeds because it only checks the body bytes against the secret, and `Registry.process` invokes the app's handler with `WebhookMetadata.shop == "victim.myshopify.com"`, causing the host app to perform victim-tenant actions (e.g., uninstall cleanup/data deletion) triggered entirely by the attacker.
