The webhook flow confirms the vulnerability: the gem's own documentation states that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" based on the HMAC — but the HMAC only covers `raw_body`, not the `shop-domain` header, which is exactly the field the handler is told to trust as the tenant identity.

### Title
Webhook shop identity spoofing via HMAC bypass — `shop` header is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, while the shop identity (`shop-domain` header) used by `ShopifyAPI::Webhooks::Registry.process` to construct `WebhookMetadata` is taken from an unauthenticated HTTP header. This breaks the identity binding `HMAC(secret, raw_body) == verified_shop`, since the HMAC never covers the `shop` claim that the handler ultimately trusts.

### Finding Description
`Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which computes `HMAC-SHA256(api_secret_key, request.to_signable_string)` and compares it to the `hmac-sha256` header: [1](#0-0) 

`to_signable_string` is defined to be just the raw body: [2](#0-1) 

Meanwhile, the `shop` value passed into `WebhookMetadata` — the value the app is told represents "the shop domain of the webhook" per the gem's own docs — comes from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is never part of the signed data: [3](#0-2) 

So the equality the gem implicitly claims to enforce is:
`shop_returned_to_handler == shop_that_the_HMAC_authenticated`

but the actual enforced equality is only:
`HMAC(secret, raw_body) == received_hmac`

These are not the same binding. Any party capable of obtaining one validly-signed `(raw_body, hmac)` pair for a webhook belonging to their own shop (e.g., any merchant who installs the app and triggers a webhook for their own store — no `api_secret_key` needed) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a victim shop. `Utils::HmacValidator.validate` still returns `true` because it never inspects the header, and `Registry.process` hands the handler a `WebhookMetadata` claiming the (attacker-chosen) victim shop with the attacker's own body content: [4](#0-3) 

For contrast, the OAuth callback's `AuthQuery#to_signable_string` correctly includes `shop` and `host` inside the signed payload, so that channel does not have this gap: [5](#0-4) 

### Impact Explanation
This is a cross-tenant identity binding failure: the app is misled into attributing attacker-controlled webhook data to a shop the attacker does not own or control, without needing the app's `client_secret`/`api_secret_key`. Depending on how the host application acts on `WebhookMetadata#shop` (as documented, apps are expected to use it directly, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this enables cross-tenant data injection/confusion for any merchant that has installed the app and can generate their own legitimately-signed webhook traffic.

### Likelihood Explanation
Any user who can install the app on their own shop (a standard, unprivileged action) can obtain a validly HMAC-signed webhook body/signature pair for arbitrary content by triggering events on their own store, then replay it against the shared webhook endpoint with a forged `shop-domain` header. No access to the merchant's access token, the app's `client_secret`, or any privileged credential is required — only the ability to intercept/observe one's own webhook deliveries.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) claims into the signed material verified by `HmacValidator`, or otherwise cryptographically tie the header-derived shop to the payload before handing it to `WebhookMetadata`/the handler — e.g., include the `shop-domain` header in `to_signable_string`, or independently verify the shop against a known/registered set of installed shops (with their own per-shop secrets) rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g. `orders/create`), capturing the resulting `raw_body` and the `x-shopify-hmac-sha256` header Shopify sent — both valid and unmodified.
2. Attacker POSTs to the app's webhook endpoint reusing the exact same `raw_body` and `hmac-sha256` header, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully (all required headers present).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, raw_body)` — this still matches, since `to_signable_string` never included the shop header. [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: <attacker's data>, ...)`, and the host app processes attacker-controlled content under the victim's tenant identity.
