## Finding: SignupReason Is Not Part of the Secure-Element-Signed Digest [1](#0-0) 

### Title
Fraud/Failure Signup Reason Is Not Covered by the Secure-Element Iris Signature - (File: `src/plans/enroll_user.rs`)

### Summary
`make_signature()` computes a SHA-256 digest over the orb ID, the user's QR code ID, and the biometric pipeline output (IR-Net version, iris version, and left/right iris code/mask/code-version), then has the Secure Element sign it. [1](#0-0)  This signature is transmitted alongside a separate, unsigned `reason` field (`SignupReason::Normal | Failure | Fraud`) that tells the backend how to classify/process the signup. [2](#0-1)  Exactly like the reported COLLATERAL-token bug — where a critical parameter that determines how a signed payload should be interpreted is left outside the digest — the `SignupReason` here is excluded from what the secure element actually attests to.

### Finding Description
`enroll_user::Plan::run()` computes the signature once via `make_signature(&user_qr_code, &p)` before entering the request/retry loop, then calls `signup_post::request()` passing the signature and the independently-supplied `signup_reason` as separate, uncorrelated parameters. [3](#0-2)  The digest inputs are strictly limited to `ORB_ID`, `user_qr_code.user_id`, and pipeline biometric fields — `SignupReason` (Normal/Failure/Fraud) never enters the hash. [1](#0-0)  `format_pipeline()` confirms the exact set of fields hashed matches only the `CodesV2`/`IrisData` structures sent as the `codes` form field — again, no `reason` binding. [4](#0-3)  The multipart form then sends `signature` and `reason` as independent, unlinked text fields to the backend. [5](#0-4) 

This is structurally identical to the SFA-06 pattern: the signed artifact (Secure-Element signature over iris data) is meant to attest to the authenticity/integrity of a signup submission, but a security-relevant tag traveling alongside it (`SignupReason`, which flags orb-detected fraud attempts) is not bound to that signature. A valid Secure-Element signature computed for one `reason` value remains cryptographically valid and indistinguishable from a signature intended for a different `reason` value, since `reason` never influences the hash.

### Impact Explanation
`SignupReason::Fraud` exists specifically to tag "a fraud attempt at the orb" for backend processing, distinct from backend-side fraud checks. [6](#0-5)  Because the Secure-Element signature does not cover this field, the association between "this iris biometric signature is trustworthy" and "this signup should be flagged as fraud/failure/normal" is not cryptographically enforced. If the `reason` value transmitted to the backend can diverge from the value that was originally intended at signing time (e.g., due to a logic error, a race in the retry loop, or any component between signature computation and HTTP submission), a fraud-flagged capture could be misrepresented to the backend as `Normal`, potentially bypassing orb-side fraud/liveness enforcement that the backend relies on this tag to honor — a legitimate fraud/liveness-bypass impact.

### Likelihood Explanation
The signature is computed once per `Plan::run()` invocation and reused unchanged across up to `RETRIES_COUNT` request attempts, [7](#0-6)  while `signup_reason` is a `Copy` value fixed at plan construction — there is currently no code path that mutates `reason` independently after signing within this file. The likelihood of exploitation therefore depends on future code changes (e.g., a refactor that recomputes/reorders reason assignment after signing, as acknowledged for the original bug in the "significant governance protections" resolution) rather than an immediately exploitable path in the current code as read.

### Recommendation
Include `signup_reason` (and ideally `signup_id`) as inputs to the SHA-256 context in `make_signature()`, so the Secure-Element signature cryptographically binds the biometric payload to the specific reason/signup it was generated for, preventing any future reuse or mismatch between a signed iris payload and an unsigned classification tag.

### Proof of Concept
Not applicable as a runtime PoC — the current control flow does not exhibit an active mismatch between signing time and submission time. The finding is a structural digest-composition gap: `ctx.update()` calls in `make_signature()` never include `signup_reason`, [8](#0-7)  while `signup_post::request()` sends `reason` as a sibling, unauthenticated field to the same endpoint. [9](#0-8)

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
