### Title
Flash-loan repayment pulls via pool-as-spender `transfer_from`, letting any initiator drain a receiver contract's standing token allowance to the pool - ([File: contracts/pool/src/ops/flash.rs](contracts/pool/src/ops/flash.rs))

### Summary
`pool::flash_loan` is permissionless and lets the initiator choose an arbitrary `receiver` contract. Repayment is collected in `collect_repayment` (`contracts/pool/src/ops/flash.rs:166-180`) by checking `asset.allowance(receiver, pool)` and then calling `asset.transfer_from(pool, receiver, pool, total_repayment)` — the spender is the pool contract itself, authorized via invoker-contract auth, so the only thing standing between an attacker and a victim's funds is a stale/steady SAC allowance `receiver → pool`. This is the exact Pearlmit shape: an approval granted to the protocol contract becomes spendable by any caller, because the allowance is keyed to the contract rather than to an authorized spender. Any WASM contract that ever approved the pool (e.g., a flash receiver that grants a generous or non-cleared allowance inside `execute_flash_loan`, analogous to users approving `TapToken` in Pearlmit) can be forced through `flash_loan` and drained.

### Finding Description
In `apply` (`contracts/pool/src/ops/flash.rs:40-71`):

1. `asset.transfer(pool, receiver, amount)` pays principal to the attacker-chosen `receiver`.
2. `invoke_receiver` calls `receiver.execute_flash_loan(initiator, asset, amount, fee, pool, data)` — a cross-contract call any reachable receiver must tolerate.
3. `require_balance` only constrains the *pool's* balance, not the receiver's.
4. `collect_repayment` asserts `asset.allowance(receiver, pool) >= total_repayment` and executes `asset.transfer_from(pool, receiver, pool, total_repayment)`. The `spender.require_auth` inside the token is satisfied by the pool's invoker auth; the receiver's signature is never required — only its standing allowance to the pool.

The auth defect is identical to M-04: the allowance check is evaluated against `pool` (the `msg.sender` of the token call), so whatever any contract approved *to the pool* is pullable by an arbitrary initiator that names that contract as `receiver`.

### Impact Explanation
Guaranteed loss per call is the flash fee: the victim receives `amount` and is debited `amount + fee` from its allowance-backed balance. Repeated calls drain `fee` each time until the allowance or the victim's balance is exhausted. If the victim's `execute_flash_loan` implementation forwards, deposits, or otherwise moves the received principal during the callback (receivers commonly settle or forward funds to `initiator`-derived beneficiaries), the principal leg is not recovered into the victim's balance and the repayment pull then nets the victim the full `total_repayment` — theft of user funds up to the standing allowance. Because `require_wasm_receiver` accepts any WASM contract and `receiver` is a free parameter, no authorization from the victim is ever obtained.

### Likelihood Explanation
Likelihood is gated on the existence of a contract holding (a) tokens and (b) a live allowance to the pool. The pool's own design requires every flash receiver to `approve` the pool inside its callback; any receiver that over-approves or fails to clear the allowance leaves exactly the exposure the Pearlmit report describes. Third-party contracts integrating with the pool may also hold residual approvals. Fee theft alone is repeatable and unbounded over time; full-principal theft additionally needs the victim's callback to disburse the principal, which is receiver-dependent. Medium severity matches the sponsor's own assessment of the source finding.

### Recommendation
Do not rely on a standing `allowance(receiver → pool)` pull. Require the receiver to `transfer` repayment directly inside its callback (measured via `require_balance` against `balance_after_repayment`), or require the receiver contract to authorize the repayment pull itself rather than having the pool spend its own invoker auth against the receiver's allowance. If the allowance pull is retained, bind `receiver` to `initiator` or require `initiator`/`receiver` authorization so an arbitrary caller cannot nominate a victim contract.

### Proof of Concept
Test-style sketch for `contracts/pool/tests/` (harness patterns as in `tests/test-harness/tests/controller/flash_loan_adversarial.rs`):

```rust
// victim is a deployed WASM flash receiver that, in a prior legitimate
// flash loan, approved the pool and left residual allowance:
//   token.approve(receiver=victim, spender=pool, amount=X, expiry=big)
// attacker calls the permissionless entrypoint naming the victim:
let fee = pool_client.flash_loan(
    &hub_asset,
    &attacker,        // initiator — attacker's own auth only
    &victim_contract, // receiver — any WASM contract, no victim auth
    &amount,
    &Bytes::new(&env),
);
// victim's execute_flash_loan runs (no-op or forwards principal),
// then collect_repayment pulls amount + fee via allowance(victim -> pool)
// with the pool as spender — victim loses at least `fee` per call,
// up to `amount + fee` if its callback moved the principal.
assert!(token_client.balance(&victim_contract) < before);
```

Uncertainty I could not fully resolve within available tooling: whether a production-grade receiver exists whose `execute_flash_loan` forwards the principal to `initiator` (which would upgrade the theft from fee-sized to full-allowance-sized), and whether `initiator.require_auth` is enforced in the controller wrapper — either way it binds only the attacker's own identity and does not mitigate the victim-selection flaw.
