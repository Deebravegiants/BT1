### Title
Persistent PCP upload queue `next_id` counter incorrectly resets to 0, causing biometric data package overwrite/loss - (File: `src/agents/data_uploader.rs`)

### Summary
The `Queue::commit` function in the persistent PCP (Personal Custody Package) upload queue resets the `next_id` counter back to `0` whenever `in_progress` reaches zero, without verifying that the on-disk/in-memory queue is actually empty of other still-pending entries. This mirrors the `setReplenishingIndex` bug class: an index/counter is mutated to an unsafe value based on an incomplete condition, and subsequent operations that rely on that counter being unique/monotonic silently clash with existing, unprocessed state, permanently corrupting or losing it.

### Finding Description
`Queue::Persistent` tracks pending personal-custody packages (PCPs, containing the user's biometric data) on disk, identified by monotonically increasing `next_id` values, alongside an `in_progress` counter of currently popped-but-uncommitted items. [1](#0-0) 

In `commit`, once a package is confirmed uploaded and its directory removed, the code checks `if *in_progress == 0 { *next_id = 0; }` and resets the ID counter to zero. This reset happens purely based on the transient state of "no upload currently in flight" — it does **not** check whether `queue` (the `VecDeque<u64>` of already-assigned, still-pending IDs) is empty.

`push` always writes new package data to `path.join(next_id.to_string())`: [2](#0-1) 

If, after a reset, `next_id` collides with an ID that is still present in `queue` (already assigned to an unpopped PCP awaiting upload), the new `push` overwrites that entry's `meta.json`/`data.bin` on disk with the new package's contents, while the queue still holds two references to the same directory. The original biometric package's data is silently destroyed, and the queue becomes internally inconsistent (duplicate IDs), so the original signup's biometric package is never uploaded/backed up while the newer package’s upload is fetched/read twice.

Concretely: push id 0 (queue=[0]) → push id 1 (queue=[0,1]) → pop id 0 (in_progress=1) → commit(0) removes dir "0" and, since `in_progress==0`, resets `next_id=0` **even though id 1 is still sitting unprocessed in `queue`** → a new `push` now reuses id 0 (harmless, since 0 was removed) but the *next* `push` reuses id 1, overwriting the still-pending, uncommitted package's data on disk before it is ever uploaded.

### Impact Explanation
The overwritten package is a Personal Custody Package containing the user's encrypted biometric data (iris/face images) for a completed signup. Once its on-disk files are overwritten by an unrelated, later signup's package, the original biometric package can no longer be correctly reconstructed or uploaded — it is effectively lost, and the corresponding user's biometric enrollment data is not properly backed up/retained as required, while the queue's internal duplicate-ID bookkeeping is also corrupted for the affected tier. This is a concrete data-loss/retention integrity failure directly analogous to "unclaimed tokens frozen forever" from the source report — instead of tokens, it's biometric custody data that becomes unrecoverable.

### Likelihood Explanation
This requires only ordinary operational conditions, not any privileged or malicious actor: multiple signups pushing PCPs to the same tier queue in quick succession, combined with the natural upload/commit cycle completing for one package while another package is still queued. Given this is triggered automatically during normal orb operation (multiple signups happening while an upload is in flight), the state pattern (`in_progress` hitting zero while `queue` remains non-empty) is a normal, expected occurrence rather than an edge case, making it readily reachable.

### Recommendation
Do not reset `next_id` based solely on `in_progress == 0`. Only reset it when the persistent queue is fully empty (`queue.is_empty() && in_progress == 0`), or better, avoid resetting the counter at all and simply let it monotonically increase (matching the mitigation guidance from the judge in the source report to prefer removing/avoiding unsafe resets rather than allowing them under partial conditions).

### Proof of Concept
1. Create a `Queue::Persistent` and `push` two PCPs → assigned ids `0` and `1`, `next_id = 2`.
2. `pop()` id `0` → `in_progress = 1`.
3. `commit(0)` → directory `0` removed, `in_progress` becomes `0`, so `next_id` is reset to `0` per lines 333-336, even though id `1` (unpopped/pending) is still in `queue`.
4. `push` a new PCP → since `next_id == 0`, this is safe (dir `0` was removed) but `next_id` becomes `1`.
5. `push` another PCP → assigned id `1`, which collides with the still-pending, un-uploaded entry from step 1; `fs::write` overwrites `meta.json`/`data.bin` for directory `1`, permanently destroying the original signup's biometric custody package before it was ever uploaded. [3](#0-2)

    async fn push(&mut self, pcp: Pcp) {
        match self {
            Self::Memory { queue } => {
                queue.push_back(pcp);
            }
            Self::Persistent { path, queue, next_id, .. } => {
                let ssd_perform = ssd::perform_async(async {
                    let path = path.join(next_id.to_string());
                    let meta = serde_json::to_string(&pcp)?;
                    fs::create_dir_all(&path).await?;
                    fs::write(path.join("meta.json"), meta).await?;
                    fs::write(path.join("data.bin"), &pcp.data).await?;
                    Ok(())
                });
                match ssd_perform.await {
                    None => {
                        tracing::error!(
                            "Persistent queue is failed during push, switching to memory"
                        );
                        *self = Self::Memory { queue: vec![pcp].into() };
                    }
                    Some(()) => {
                        queue.push_back(*next_id);
                        *next_id = next_id.checked_add(1).expect("shouldn't grow so fast");
                    }
                }
            }
        }
    }

    async fn pop(&mut self) -> Option<(Pcp, u64)> {
        match self {
            Self::Memory { queue } => queue.pop_front().map(|pcp| (pcp, 0)),
            Self::Persistent { path, queue, in_progress, .. } => {
                let id = queue.pop_front()?;
                let ssd_perform = ssd::perform_async(async {
                    let path = path.join(id.to_string());
                    let meta = fs::read_to_string(path.join("meta.json")).await?;
                    let mut pcp = serde_json::from_str::<Pcp>(&meta)?;
                    pcp.data = fs::read(path.join("data.bin")).await?;
                    Ok(pcp)
                });
                match ssd_perform.await {
                    None => {
                        tracing::error!(
                            "Persistent queue is failed during pop, switching to memory"
                        );
                        *self = Self::new_memory();
                        None
                    }
                    Some(pcp) => {
                        *in_progress += 1;
                        Some((pcp, id))
                    }
                }
            }
        }
    }

    async fn commit(&mut self, id: u64) {
        match self {
            Self::Memory { .. } => {}
            Self::Persistent { path, next_id, in_progress, .. } => {
                *in_progress = in_progress.checked_sub(1).expect("shouldn't go negative");
                match ssd::perform_async(fs::remove_dir_all(path.join(id.to_string()))).await {
                    None => {
                        tracing::error!(
                            "Persistent queue is failed during commit, switching to memory"
                        );
                        *self = Self::new_memory();
                    }
                    Some(()) => {
                        if *in_progress == 0 {
                            *next_id = 0;
                        }
                    }
                }
            }
        }
    }
