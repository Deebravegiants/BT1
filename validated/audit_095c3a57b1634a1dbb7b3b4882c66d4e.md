### Title
Emporium min-circuit path (`erc20TokenAddresses.length == 0`) skips all balance/UTXO-backing checks, allowing arbitrary drain of Emporium's held funds - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
When a `transact` call uses the Emporium "min" circuit (`erc20TokenAddresses.length == 0`), `EmporiumUpgradeable.runAction` still executes attacker-supplied `EmporiumOperation`s (arbitrary `endpoint.call{value: op.value}(callData)`), but the balance-accounting loop that computes `balanceChange`/`utxoAmount` and reverts on negative change (`BalanceChangeShouldBePositive`) is `for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)`, which never executes for an empty array. The corresponding top-level check in `Hinkal.transact` (`balanceDif == onChainCreation ? 0 : amountChanges + utxoAmount`) is likewise skipped since it iterates over the same empty `erc20TokenAddresses`. This lets an attacker drain any ETH/ERC20 sitting in the Emporium contract — including funds that back a still-valid on-chain UTXO created by a prior normal-circuit `transact` — without any check ever firing.

### Finding Description
Broken equality: `ETH_backing_unspent_UTXO_at_Emporium(before) == ETH_remaining_at_Emporium(after attacker's min-circuit op)`. This should be enforced by the `balanceChange`/`utxoAmount`/`slippageValues`/`balanceDif` equations in both `EmporiumUpgradeable.runAction` and `Hinkal.transact`, but those equations are structurally guarded by loops bounded by `circomData.erc20TokenAddresses.length`.

Code path:
- `contracts/CircomDataBuilder.sol` `formInputForCircom` routes to `formInputEmporiumMin` whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` [1](#0-0) , and the corresponding circuit `circuits/MainEVMCircuitMin.circom` only constrains `outTimeStamp`, `calldataHash`, and a Poseidon-derived `message` from a private `messageSeed` — no root hash, no nullifiers, no UTXO ownership or token/amount signals whatsoever [2](#0-1) . Any attacker can generate a valid proof for this circuit trivially by choosing their own `messageSeed`.
- `contracts/HinkalHelper.sol` `dimensionsCheck` only requires `erc20TokenAddresses.length == dimensions.tokenNumber` [3](#0-2)  — `tokenNumber == 0` is permitted, so a fully empty token array passes all dimension/onchain-creation checks in `performHinkalChecks`/`checkOnchainCreation` [4](#0-3) .
- In `Hinkal.transact`, the balance-diff/slippage/UTXO-backing enforcement loop iterates `circomData.erc20TokenAddresses.length` times, so with length 0 it does nothing at all [5](#0-4) .
- In `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are computed via `getBalancesForArray(circomData.erc20TokenAddresses)`, which for an empty array returns empty arrays; the loop that computes `balanceChange`, enforces `balanceChange >= 0` (`BalanceChangeShouldBePositive`), and creates the outgoing UTXO via `handleOut` is also bounded by `circomData.erc20TokenAddresses.length` [6](#0-5) . Meanwhile, the operation-execution loop that performs `op.endpoint.call{value: op.value}(op.callData)` runs unconditionally over `stack.ops`, independent of `erc20TokenAddresses` [7](#0-6) .
- `verifyWallet` requires only that `emporiumMessage` hasn't been used before; if `stack.signerAddress == address(0)` it returns immediately without any signature check at all [8](#0-7) .

Exploit flow:
1. Attacker (or a victim, doesn't matter) performs a normal-circuit `transact` with `erc20TokenAddresses = [address(0)]`, `onChainCreation[i] = true`, causing ETH to be held at the Emporium contract backing a valid `outCommitments` leaf inserted into the tree.
2. Attacker then calls `transact` again with `dimensions.tokenNumber = 0`, `circomData.erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` decoding to an `EmporiumStack` with `signerAddress = address(0)` and one `EmporiumOperation{endpoint: attacker, invokeWallet: false, value: <Emporium's ETH balance>, callData: ""}`. The proof is for `MainEVMCircuitMin`, trivially generated.
3. `Hinkal.transact` calls `hinkalHelper.performHinkalChecks` (passes, since `tokenNumber=0`), verifies the min-circuit proof (passes trivially), checks root hash (irrelevant to min-circuit since no nullifiers/roots are actually constrained by the min circuit but `rootHashHinkal` can be any valid root), then calls `_externalTransact` → `EmporiumUpgradeable.runAction`.
4. `runAction` executes `op.endpoint.call{value: op.value}()`, sending all of Emporium's ETH to the attacker. No balance/UTXO check exists for empty `erc20TokenAddresses`, so nothing reverts.
5. Back in `Hinkal.transact`, the top-level balance/slippage/backing loop is also empty, so nothing reverts there either.
6. Result: Emporium's ETH balance is drained; the UTXO commitment from step 1 remains in the tree unspent but the funds backing it are gone. The legitimate holder cannot redeem it.

None of the existing guards (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, `rootHashExists`, the balance/slippage requires, `insertNullifiers`, `onlyAllowedRecipient`, `verifyWallet`, `nonReentrant`) prevent this because they are all either satisfied trivially by the min-circuit's near-empty public input set, or structurally skipped due to loop bounds tied to `erc20TokenAddresses.length == 0`.

### Impact Explanation
This is a Critical finding: it enables direct theft of shielded/in-flight user funds and permanent freezing of the corresponding UTXO. Any unprivileged attacker can drain the entire ETH (and, if `callData` targets an ERC20 `transfer`, arbitrary ERC20 balances) held by the Emporium contract at any point in time — including funds that legitimately back other users' unspent on-chain UTXOs — using a single low-cost `transact` call with a trivially-generated proof. The attack is fully repeatable any time Emporium holds a nonzero balance (e.g., whenever any user performs an on-chain-creation deposit via the normal Emporium circuit path, or leaves residual dust from another Emporium op).

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: Emporium must hold funds (attacker can even self-fund it via their own first-step deposit, or wait for/observe another user's deposit), and the attacker needs to construct a valid `CircomData`/`Dimensions`/`EmporiumStack` with `tokenNumber = 0` and generate a `MainEVMCircuitMin` proof, which requires no privileged knowledge (only a self-chosen `messageSeed`). Cost is a single transaction plus proof generation for a trivial circuit. This is highly feasible and repeatable.

### Recommendation
Do not let `runAction`/`Hinkal.transact` skip balance enforcement when `erc20TokenAddresses.length == 0`. Specifically:
- In `EmporiumUpgradeable.runAction`, independently track the Emporium contract's *total* ETH/native balance (and/or restrict min-circuit ops to only tokens/addresses explicitly whitelisted and zero-value) regardless of `erc20TokenAddresses.length`, and revert if native balance decreases without matching a declared (and checked) outgoing amount.
- Alternatively, disallow `op.value > 0` and disallow calls that could move Emporium-held assets when `erc20TokenAddresses.length == 0` (i.e., truly restrict the "min" path to stateless/zero-value calls that cannot touch Emporium's held balances), or require the min-circuit path to still declare and verify the token(s)/amounts touched by `ops`.
- More fundamentally, tie the min-circuit's public inputs to the actual `EmporiumOperation` set (e.g., hash of `stack.ops` as a public/verified input) so that the circuit that's proven actually constrains what operations are permitted, rather than relying solely on Solidity-side balance loops that are bypassed for empty token arrays.

### Proof of Concept
Foundry fork test outline:
1. Deploy/fork Hinkal + Emporium + HinkalHelper with a whitelisted relay (or `originalSender==sender` path).
2. Step 1 (normal circuit): construct `CircomData` with `dimensions.tokenNumber = 1`, `erc20TokenAddresses = [address(0)]`, `onChainCreation = [true]`, `amountChanges = [0]`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, an `EmporiumStack` op that simply deposits ETH (e.g., a no-op stateless call with `value = X`), send `msg.value = X`. Assert `address(Emporium).balance == X` after, and that `outCommitments[0][0]` is inserted into the tree (`Hinkal.insertCommitments` emits/records the leaf).
3. Step 2 (min circuit): construct `CircomData` with `dimensions.tokenNumber = 0`, `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress: address(0), ops: [EmporiumOperation{endpoint: attacker, invokeWallet: false, value: X, callData: ""}]}`, generate a valid `MainEVMCircuitMin` proof with an arbitrary `messageSeed`. Call `transact` with `msg.value = 0`.
4. Assert both sides of the equality: before step 2, `ETH_backing_unspent_UTXO == X == address(Emporium).balance`; after step 2, `address(Emporium).balance == 0` while the UTXO commitment from step 1 is still present in the tree and unspent (its nullifier not yet inserted) — i.e., `ETH_backing_unspent_UTXO(claimed) = X` but `ETH_remaining_at_Emporium = 0`.
5. Attempt to spend the UTXO from step 1 with a valid normal-circuit withdrawal proof and show `transferERC20TokenOrETH`/`op.endpoint.call` fails or the Emporium's `receive`/withdrawal transfer reverts due to insufficient balance, proving the UTXO is now permanently unredeemable while the attacker holds `X` ETH stolen from Emporium.
