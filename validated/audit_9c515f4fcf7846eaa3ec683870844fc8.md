### Title
Withdraw slippage protection is entirely optional and bypassable, enabling sandwich attacks on LP withdrawals - (File: program/src/processor.rs)

### Summary
The `Withdraw` instruction lets the caller omit `min_coin_amount`/`min_pc_amount` entirely, in which case `process_withdraw` performs **no** minimum-output validation at all, mirroring the reported "lack of validation for minTokenAmounts_" bug class.

### Finding Description
`AmmInstruction::unpack` treats the two minimum-amount fields as optional: they are only parsed if the instruction data is at least 16 bytes longer than the base payload; otherwise both become `None` [3](#0-2) . In `process_withdraw`, `coin_amount`/`pc_amount` are computed from the live vault balances at execution time via `Calculator::calc_total_without_take_pnl_no_orderbook` and the pool-share `InvariantPool` exchange [4](#0-3) , so they are directly influenced by the AMM's spot ratio, which any unprivileged party can move with a swap instruction in the same block. The enforcement of the min amounts is gated behind `withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()` [2](#0-1) : if the transaction simply omits these optional fields (12-account legacy form or a minimal 20-byte payload), the program applies zero minimum-output validation and unconditionally transfers whatever `coin_amount`/`pc_amount` the manipulated ratio yields.

### Impact Explanation
An attacker (MEV searcher) observing a pending withdraw transaction that does not carry `min_coin_amount`/`min_pc_amount` can sandwich it: swap in one direction before the withdrawal to skew the coin/pc ratio, let the victim's withdrawal execute at the skewed ratio (extracting a disproportionately low value in one of the two tokens), then swap back afterward to restore the ratio and capture the difference. Because the check is entirely absent when the fields are `None`, there is no on-chain backstop and the victim's transaction cannot revert regardless of how unfavorable the ratio becomes, resulting in direct fund loss for the withdrawing LP.

### Likelihood Explanation
Any client, wallet, or integrator that builds a `Withdraw` instruction using the legacy/short form (or simply doesn't populate the optional fields) produces an unprotected transaction; this requires no privileged access — only submitting an ordinary swap before/after a publicly visible withdraw transaction, which is a standard, low-cost MEV pattern on Solana.

### Recommendation
Require `min_coin_amount` and `min_pc_amount` unconditionally (reject instructions where they are `None`), or otherwise enforce a protocol-side minimum derived independently of caller input (e.g., a stored oracle price or TWAP-based bound), matching the recommendation in the referenced report.

### Proof of Concept
1. Attacker observes a pending `Withdraw` transaction built without the optional 16-byte suffix (`min_coin_amount`/`min_pc_amount` = `None`), reaching `process_withdraw` via `AmmInstruction::unpack` tag `4` [3](#0-2) .
2. Attacker front-runs with a large `SwapBaseIn`/`SwapBaseOut` to skew `amm_coin_vault.amount`/`amm_pc_vault.amount`.
3. Victim's withdraw executes; `coin_amount`/`pc_amount` are computed off the skewed vault balances [5](#0-4) , and because `min_coin_amount`/`min_pc_amount` are `None`, the `is_some()` guard skips validation entirely and the transfer proceeds [6](#0-5) .
4. Attacker back-runs with an opposing swap to restore the ratio and pocket the extracted value, at the victim's expense.
