### Title
Webhook `shop-domain` header trusted for tenant attribution without HMAC coverage - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are all taken from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` accepts the request once the body-only HMAC validates, then hands the header-derived `shop` value straight to the app's handler as the tenant identifier for that webhook payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` (the body only) and compares it against the received HMAC: [3](#0-2) 

Once that check passes, `process` immediately trusts `request.shop` as the tenant identity and forwards it to the app-supplied handler: [4](#0-3) 

This is the same equality-binding defect described in the external report: a field that is *acted upon* (`shop`, used to attribute the webhook event to a tenant) is not covered by the value that is *cryptographically verified* (the HMAC, which only covers `raw_body`). The binding that should hold — `shop header == shop that produced the signed body` — is never checked; only `computed_signature(body) == received_signature` is checked, and `shop` is orthogonal to that comparison.

Because an app's `api_secret_key` is shared across all shops that install the app (Shopify signs every merchant's webhooks with the same per-app secret, not a per-shop secret), a user who operates their own (attacker-controlled) shop and has installed the target app can receive genuine, validly-signed webhooks for their own shop. Since the signature never covers the `shop-domain` header, that attacker can replay the identical body + HMAC while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `Registry.process` will still validate successfully (the body/HMAC pair is unchanged) and will invoke the handler with `shop: "victim-shop.myshopify.com"`.

### Impact Explanation
Any host application that uses the `shop` value from `WebhookMetadata` (as documented and demonstrated in the test suite, e.g. `data.shop`) to decide which merchant's records to update, delete, or otherwise act upon will process the attacker's payload as if it originated from the victim shop. This is a cross-tenant data-integrity/confusion vulnerability: an app user with no privileges over the victim shop can inject falsified webhook events attributed to that shop (e.g., forged `orders/create`, `app/uninstalled`, or mandatory GDPR-topic payloads), without ever needing the app's `client_secret`, an access token, or any credential belonging to the victim.

### Likelihood Explanation
Exploitation requires only that the attacker be a regular (non-privileged) installer of the target app on their own store — not an admin of, nor holder of any credential for, the victim shop. Capturing a legitimate webhook delivery (body + `X-Shopify-Hmac-Sha256`) for their own shop and replaying it with a modified shop header is straightforward, since this gem performs no comparison between the signed content and the header-derived shop/topic/id values.

### Recommendation
Include `shop`, `topic`, and any other header-derived identity fields consumed by the handler in the value that is HMAC-verified (or otherwise independently verify that the `shop` header corresponds to a shop with an active, previously-established session/installation before dispatching to the handler). At minimum, document and enforce that `WebhookMetadata#shop` must never be trusted as an authentication boundary unless it is cross-checked against a known, installed shop record maintained by the host app.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) with a body they control (order comment/note fields, etc.).
2. Shopify delivers the webhook to the app with a valid `X-Shopify-Hmac-Sha256` computed over that body using the app's shared `api_secret_key`.
3. Attacker captures the raw body and HMAC, then re-sends an HTTP request to the app's webhook endpoint with the same body/HMAC but with the `X-Shopify-Shop-Domain` header changed to `victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — the HMAC still matches the body, so it passes: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, and any host-app logic keyed on `shop` now operates on/attributes data to the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
