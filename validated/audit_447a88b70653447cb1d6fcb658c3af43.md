### Title
Webhook `shop-domain` (and `topic`/`webhook_id`/`api_version`) headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from unauthenticated HTTP headers. `Registry.process` validates the HMAC over the body alone and then hands the *unverified* `shop` header straight to the webhook handler, creating an identity binding break: `verified_bytes(body) != acted_on_identity(shop_header)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all pulled directly from headers with no cryptographic binding to that signed body: [3](#0-2) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, and then trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler: [2](#0-1) 

`HmacValidator.validate_signature` only compares `verifiable_query.to_signable_string` (the raw body) against the received signature — it never touches the `shop` header: [4](#0-3) 

Because the same app-level `api_secret_key` is used to sign webhooks for *every* shop that installs the app, any merchant that installs the app can trigger a real webhook delivery to their own endpoint and obtain a genuinely valid `(raw_body, hmac)` pair for their own shop. That attacker-controlled merchant can then replay the identical body and HMAC to the same app's webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic` header) for a victim shop's domain. `Registry.process` will accept it — the HMAC check passes because it never inspects the header — and the app's handler will process attacker-supplied body content while believing it originates from the victim shop.

### Impact Explanation
This breaks the tenant boundary the whole webhook system exists to enforce: `WebhookMetadata.shop` is the identity the app's own business logic (e.g. per-shop data ingestion, order/customer sync, GDPR/compliance webhooks) relies on to attribute the payload to a tenant. An attacker who is a legitimate but malicious merchant of the app can inject fabricated data into another merchant's per-shop pipeline, or make legitimate events for their own shop appear to belong to a victim shop — a cross-tenant access/data-integrity breach, which the rules classify as Critical impact.

### Likelihood Explanation
Exploitation only requires installing the app as an ordinary merchant (no credential leakage, no TLS interception, no privileged account) and sending a crafted HTTP POST with substituted headers to the app's known public webhook endpoint. This is fully reachable by an unprivileged internet user/merchant using only this gem's own `Registry.process`/`Request` code path.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the signed material verified against the HMAC, or at minimum have `Registry.process`/`Request` cross-check `request.shop` against the shop associated with the session/subscription that the webhook_id belongs to before dispatching to handlers, rather than trusting the raw header value implicitly.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (legitimate merchant install).
2. Attacker triggers a webhook event (e.g. `orders/create`) on their own shop; Shopify sends a POST to the app's webhook endpoint with a genuinely valid `X-Shopify-Hmac-SHA256` computed over the raw body using the app's `api_secret_key`, plus header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this `(raw_body, hmac)` pair (they control the receiving endpoint) and re-POSTs the identical body/hmac to the app's webhook endpoint again, but with header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the body against the hmac — this still passes.
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing attacker-controlled data to be processed as though it belongs to `victim-shop.myshopify.com`.
