### Title
Excess native ETH sent to `EvmHost.dispatch()`/`fundRequest()` for the Uniswap fee swap is never refunded to the caller and is permanently trapped in `EvmHost` - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all forward the caller's full `msg.value` into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` without capturing the returned `amounts` array or refunding unspent ETH to the original caller.

### Finding Description
In each of these functions, when `msg.value > 0`, the code performs: [1](#0-0) [2](#0-1) [3](#0-2) 

The standard `UniswapV2Router02.swapETHForExactTokens` implementation refunds any unspent ETH (`msg.value - amountIn`) directly to its `msg.sender` — which, in this call chain, is `EvmHost` itself (since `EvmHost` is the one calling the router with `{value: msg.value}`), not the original transaction sender who paid the ETH into `EvmHost.dispatch()`/`fundRequest()`. This is confirmed by the local Uniswap wrapper test suite, which explicitly documents that "refund returns to caller" (i.e. to whoever calls the router, not the original upstream caller): [4](#0-3) 

None of the three `EvmHost` functions capture the router's `amounts` return value or forward any leftover ETH back to `_msgSender()`/`post.payer`. The excess ETH therefore accumulates as native balance inside `EvmHost`, and `EvmHost` has no `receive()`/`fallback()` or user-facing withdrawal path for this stray native balance — only `IHostManager.withdraw` (a privileged, ERC20 `feeToken`-oriented governance function) exists for host revenue extraction, not native ETH refunds to individual dispatchers.

Notably, this exact bug class was already identified and fixed elsewhere in the same codebase: `IntentGatewayV2.placeOrder` uses the identical `swapETHForExactTokens` call but explicitly captures `amounts[0]` (ETH actually spent) and refunds the difference back to `msg.sender` via `_sendValue`: [5](#0-4) 
This is validated by a dedicated regression test: [6](#0-5) 

`EvmHost.dispatch`/`fundRequest` lack this same refund logic, making them the analogous unpatched instance of the reported bug class.

### Impact Explanation
Any application contract or EOA that calls `IDispatcher(host).dispatch{value: msg.value}(...)` or `fundRequest{value: msg.value}(...)` with `msg.value` greater than what's needed to acquire `post.fee`/`get.fee`/`amount` worth of fee tokens (which is the expected/documented usage pattern per the SDK/docs — callers estimate fees off-chain and pad for slippage) will have the excess ETH permanently stuck inside `EvmHost`, with no code path to reclaim it for the payer. Given that this is the primary, documented entry point for dispatching POST/GET requests and funding pending requests across the entire Hyperbridge EVM stack (used directly by `HyperApp`, `HyperFungibleToken`, `IntentGatewayV2` (tron variant), `HyperbridgeLzEndpoint`, etc.), this results in a systemic, permanent loss of user funds at protocol scale rather than an isolated integration issue.

### Likelihood Explanation
High. Overpayment is the expected client behavior: fee estimation via Uniswap quotes is inherently approximate due to slippage, and the documentation explicitly instructs users to send native tokens "to cover" fees, with no guidance that exact amounts must be sent. Every dispatch using the native-token payment rail with any margin above the exact swap requirement (which is the common case, since users can't predict the exact swap output precisely) triggers the loss.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, compute `msg.value - amounts[0]`, and refund the difference to `_msgSender()` (or the designated `payer`), mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`.

### Proof of Concept
1. Caller invokes `EvmHost.dispatch{value: 5 ether}(post)` where `post.fee` only requires ~0.01 ETH worth of the fee token via the configured Uniswap pool. [7](#0-6) 
2. `IUniswapV2Router02.swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)` spends only the required amount and refunds the remainder (~4.99 ETH) to its `msg.sender`, which is `EvmHost`.
3. `EvmHost.dispatch` never reads the swap's returned `amounts[0]` and never forwards any ETH back to the caller.
4. The ~4.99 ETH remains as native balance on `EvmHost` indefinitely; there is no `receive()`, no user-facing withdrawal function, and `IHostManager.withdraw`/governance paths target `feeToken` revenue, not stray native ETH refunds — the funds are permanently frozen.
