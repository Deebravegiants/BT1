### Title
Empty-token Min-proof path lets an unprivileged attacker drive `EmporiumUpgradeable.runAction` to make arbitrary, unsigned, unaccounted external calls from Emporium's identity - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`, `contracts/CircomDataBuilder.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, whose circuit (`MainEVMCircuitMin.circom`) constrains only `message == Poseidon(messageSeed)` — a preimage the attacker trivially picks themselves. Combined with an `EmporiumStack.signerAddress == address(0)`, this removes every check that normally authorizes or accounts for Emporium's external calls, letting an unprivileged caller run arbitrary `op.endpoint.call{value: op.value}(op.callData)` from Emporium's own address with no signature and no balance-diff enforcement.

### Finding Description
The broken equality is: *assets Emporium can move via `stack.ops` in a transaction* == *assets accounted for in `balancesBefore`/`balancesAfter` (and in `Hinkal.transact`'s balance-diff loop)*.

- `formInputForCircom` selects `formInputEmporiumMin` whenever `erc20TokenAddresses.length == 0` for the Emporium action id: [1](#0-0) . That function only emits `emporiumMessage`, `timeStamp`, `calldataHash` as public inputs [2](#0-1) .
- The corresponding circuit constrains nothing but `message <== Poseidon(1)([messageSeed])`; `calldataHash`/`outTimeStamp` are declared public but never used in any constraint [3](#0-2) . An attacker can pick any `messageSeed` and compute a matching `emporiumMessage` themselves, so this "proof" carries no real authorization — it is a self-chosen anti-replay tag, not evidence of ownership of shielded funds.
- In `Hinkal.transact`, the balance-diff/UTXO-accounting loop that ties `amountChanges`/`utxoAmount` to real balance changes only iterates over `circomData.erc20TokenAddresses`; with length 0 it does nothing [4](#0-3) .
- Inside `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are computed from the same empty `erc20TokenAddresses` array, so the post-loop accounting (`balanceChange`, `BalanceChangeShouldBePositive`) never executes [5](#0-4) .
- `verifyWallet` — the only place that verifies an EIP-712 signature authorizing `stack.ops` — short-circuits and returns immediately (after only marking `usedMessages[emporiumMessage]`) when `stack.signerAddress == address(0)`, performing **no signature check at all** [6](#0-5) .
- With `signerAddress == 0`, every op falls into the "Stateless Interaction" branch, which performs `op.endpoint.call{value: op.value}(op.callData)` directly with Emporium as `msg.sender`, blocking only the `callHinkalWallet`/`doSendToRelay` selectors [7](#0-6) .

Put together: an attacker calls `Hinkal.transact` with `erc20TokenAddresses = []`, `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, and an `externalActionMetadata` decoding to an `EmporiumStack{signerAddress: address(0), ops: [...attacker-chosen calls...]}`. They generate a trivial proof for the Min circuit (self-chosen `messageSeed`) and satisfy `performHinkalChecks`'s `calldataHash` integrity check (which only ties the hash to their own supplied calldata, not to any external secret) [8](#0-7) . Since no funds are deposited in this same call (`erc20TokenAddresses` is empty so `_calculateDeltaAmount`/negative-delta transfer-in never runs, see `Hinkal.sol` `_externalTransact`) [9](#0-8) , `runAction` executes the attacker's ops purely against whatever balance the Emporium contract already holds (ETH via its `receive()` function, dust, unswept swap remainders, mistaken transfers, etc.) [10](#0-9) , with zero signature check and zero balance accounting to detect or block the outflow.

The premise about "a call into HinkalHelper or a router that trusts Emporium as msg.sender" from the question is not substantiated in the code reviewed — `HinkalHelper`'s privileged entry points are gated by `onlyHinkal`, and I found no evidence any function trusts `msg.sender == Emporium`. That specific sub-claim should be treated as unconfirmed. What is confirmed and independently sufficient for a finding is the unauthenticated, unaccounted arbitrary call capability itself.

### Impact Explanation
Any balance the Emporium contract holds at the time of attack (ETH sent to its `receive()`, ERC20 tokens left over from an incompletely-swept operation, dust from rounding/slippage, or tokens mistakenly sent to it) can be drained by any unprivileged attacker with zero signature and a trivial self-generated proof. This is theft of protocol/relay-held or transiently-held user funds sitting in a shared contract, executed with no on-chain accounting catching the outflow. Repeatable indefinitely (each `emporiumMessage` is single-use via `usedMessages`, but attacker can mint arbitrarily many messages). Severity is Critical/High depending on how much value actually transits or rests in Emporium at attack time; the vulnerable code path itself (unauthenticated calls from Emporium's identity with zero accounting) is a clear violation of the stated invariant.

### Likelihood Explanation
No special preconditions beyond Emporium holding a nonzero balance of some asset, which is plausible given its `receive() external payable {}` and the fact it is a shared, non-per-user contract that can end up holding leftover value between/within transactions (e.g., partially unswept swap outputs, fee remnants, accidental transfers). Attacker cost is a single transaction with a self-generated Groth16 proof for a 1-constraint circuit (trivial to compute) plus arbitrary `EmporiumStack` construction — no wallet key, no relay, no privileged role required.

### Recommendation
Do not allow the "Min" proof path to be combined with `EmporiumStack.signerAddress == address(0)`: enforce that stateless (unsigned) op execution is only reachable when the full circuit's balance/nullifier constraints apply (i.e., `erc20TokenAddresses.length > 0`), or alternatively require a valid EIP-712 signature (`verifyWallet`'s signed branch) unconditionally whenever `erc20TokenAddresses.length == 0`. Additionally, require `msg.sender`/`address(this).balance` invariants: reject `runAction` calls where `erc20TokenAddresses.length == 0` but `stack.ops.length > 0`, since there is nothing to legitimately account for or authorize in that combination.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` per repo test harness; register Emporium as `externalActionMap[HINKAL_EMPORIUM_ACTION_ID]` and as `allowedRecipient`.
2. Send ETH (or an ERC20) directly to the deployed `EmporiumUpgradeable` address to simulate residual/dust balance (`vm.deal(emporium, 1 ether)`).
3. As an attacker EOA with no prior relationship to the funded balance, build `CircomData` with `erc20TokenAddresses = []`, `externalActionData = {externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalAddress: emporium, externalActionMetadata: abi.encode(EmporiumStack{signerAddress: address(0), ops: [{endpoint: attackerContract, invokeWallet: false, value: 1 ether, callData: ""}]})}`.
4. Compute `calldataHash = getHashedCalldata(circomData)` and set `circomData.calldataHash` accordingly; pick `messageSeed`, set `emporiumMessage = Poseidon(messageSeed)`, generate a real Groth16 proof for `MainEVMCircuitMin`.
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker.
6. Assert: `emporium.balance` (or token balance) before == 1 ether, after == 0; `attackerContract.balance` increased by 1 ether — i.e., value left Emporium with no corresponding entry in `balancesBefore`/`balancesAfter` diff logic and no `verifyWallet` signature check performed, confirming the equality "assets moved == assets accounted" is violated.

        CircomData calldata circomData,
        Dimensions calldata dimensions,
        address sender

            (circomData.originalSender == address(0) &&

            CircomDataBuilder.getHashedCalldata(circomData) ==
                circomData.calldataHash,

        );
        relayerIsValid(circomData.relay);
        dimensionsCheck(circomData, dimensions);
        checkOnchainCreation(circomData);

        return
            CircomDataBuilder.formInputForCircom(
                block.chainid,
                hinkalAddress,
                circomData
            );
