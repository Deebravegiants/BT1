### Title
CORS wildcard-origin allowlist bypass via unanchored suffix match - (File: core/services/gateway/network/httpserver.go)

### Summary
The gateway's public HTTP server validates CORS origins against an operator-configured allowlist that supports wildcard entries like `*.example.com`. The wildcard match strips the `*.` prefix and then checks `strings.HasSuffix(originHost, allowedHost)`, without verifying that the character preceding the suffix in the origin is a `.` (domain label boundary). This lets an attacker who registers a domain that merely ends with the allowed suffix as a raw string (e.g. `evilethereum.org` for an allowlist entry `*.ethereum.org`) pass the wildcard check and receive a reflected `Access-Control-Allow-Origin` header, even though it is not actually a subdomain of the intended domain.

### Finding Description
`isAllowedOrigin` performs the wildcard comparison as: [1](#0-0) 

```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if strings.HasSuffix(originHost, allowedHost) {
        return true
    }
}
```

`strings.HasSuffix(originHost, allowedHost)` is a raw string suffix comparison, not a domain-label-aware comparison. For an allowlist entry `*.ethereum.org`, `allowedHost` becomes `ethereum.org`. An origin host such as `evilethereum.org` (no dot separator, entirely attacker-controlled) also ends with the literal string `ethereum.org`, so the check returns `true` even though `evilethereum.org` is not a subdomain of `ethereum.org`. This is the same bug class as the Keycloak wildcard redirect-URI validation flaw (CVE-2026-3872): a wildcard-based allowlist that fails to enforce the proper delimiter/boundary before the allowed suffix, letting any attacker who controls a similarly-suffixed name defeat the allowlist.

This check is invoked directly from `handleRequest`, the top-level entry point for every unauthenticated HTTP request hitting the gateway's public-facing endpoint: [2](#0-1) 

### Impact Explanation
When `CORSEnabled` is true and an operator configures wildcard origins (a documented, supported pattern per the existing test suite, e.g. `https://*.ethereum.org`), an attacker who registers a lookalike domain (`evilethereum.org`, `notethereum.org`, etc.) can have pages on that domain issue cross-origin browser requests to the gateway and receive the response with `Access-Control-Allow-Origin` reflecting their origin. This defeats the Same-Origin Policy protection the allowlist is meant to provide, enabling a malicious webpage to read gateway JSON-RPC responses (e.g. workflow trigger results, capability responses) that a victim's browser would otherwise be prevented from exposing to the attacker's origin, potentially leading to information disclosure or facilitating further request forgery against the gateway on behalf of the victim's browser context.

### Likelihood Explanation
Exploitation requires: (1) an operator enabling CORS with a wildcard allowlist entry (a supported, tested configuration option), and (2) an attacker registering a domain name that shares a suffix with the allowed domain without being an actual subdomain. Domain registration is trivial and cheap, and the vulnerable comparison is deterministic and easy to discover via testing allowed-origin behavior, making this practically exploitable wherever wildcard CORS entries are used.

### Recommendation
Fix the wildcard suffix check to require a proper label boundary, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".ethereum.org" (keep leading dot)
    if originHost == allowedHost[2:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
This ensures `originHost` either equals the base domain or ends with `.` + the base domain, preventing lookalike domains like `evilethereum.org` from matching `*.ethereum.org`.

### Proof of Concept
1. Configure the gateway with `CORSEnabled = true` and `CORSAllowedOrigins = ["https://*.ethereum.org"]`.
2. Register/control a domain `https://evilethereum.org` (no relation to `ethereum.org`).
3. Send a request to the gateway's HTTP endpoint with header `Origin: https://evilethereum.org`.
4. Observe the server responds with `Access-Control-Allow-Origin: https://evilethereum.org`, confirming the wildcard check in `isAllowedOrigin` incorrectly treats `evilethereum.org` as a match for `*.ethereum.org`: [3](#0-2)

func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}
