## Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unsigned headers while only the raw body is HMAC-verified, enabling cross-tenant/topic confusion - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook by computing an HMAC over the *raw body only*, but then dispatches the handler and constructs the tenant-identifying `WebhookMetadata` using the `topic`, `shop`, and `webhook_id` values pulled straight from HTTP headers, none of which are covered by that HMAC. This breaks the identity binding: `HMAC-verified bytes == raw_body` but `WebhookMetadata.shop/topic/webhook_id == unverified header bytes`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are read directly from attacker-controllable HTTP headers with no cryptographic tie to that body: [2](#0-1) 

`Registry.process` validates the HMAC solely against `to_signable_string` (the body), then uses the unsigned `request.topic` to pick which handler runs, and forwards the unsigned `request.shop` / `request.webhook_id` straight into the metadata object passed to that handler: [3](#0-2) 

Because Shopify's HMAC (computed with the app's shared `client_secret`) only binds the JSON body, any request that carries a *body+HMAC pair* previously produced by Shopify for that app (e.g. a webhook event legitimately triggered on the attacker's own installed shop) remains valid even if the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers are swapped for different values. A tenant (merchant) of a multi-tenant app is an untrusted party relative to other tenants, yet can generate arbitrary Shopify-signed bodies on demand by performing actions on their own store (creating orders/customers with attacker-influenced fields, editing shop settings, etc.), then replay that same body+HMAC to the shared webhook endpoint with a forged `shop` header (impersonating another merchant) and/or a forged `topic` header (causing an unrelated handler, e.g. `app/uninstalled` or `shop/update`, to run against a body it never expected). This is the "field acted on but not covered by the HMAC" class of bug: the tenant/session-key binding `verified body == data.shop` does not hold.

### Impact Explanation
This is a cross-tenant integrity/isolation break in a multi-tenant application built on this gem: one merchant's tenant boundary can be crossed by relabeling the `shop` header on an otherwise validly-signed webhook, letting an attacker inject data or trigger business logic attributed to a victim shop. Combined with unsigned `topic`, it also allows handler/type confusion (feeding one topic's body into another topic's handler), which can trigger unintended state transitions (e.g. simulating `app/uninstalled` cleanup or `shop/update` while carrying a different, attacker-chosen body). This matches the Critical "cross-tenant access" impact category the rules define, since the gem is the component responsible for authenticating and attributing webhook events to a tenant.

### Likelihood Explanation
Any developer using the documented `ShopifyAPI::Webhooks::Request` + `Registry.process` flow exactly as shown in this gem's own docs (`raw_body: request.raw_post, headers: request.headers.to_h`) is affected — no misuse of the API is required. The attacker only needs to be a legitimate merchant/tenant of the host app (able to trigger a webhook-eligible action on their own store) and the ability to replay an HTTP POST with modified headers to the app's public webhook endpoint, both of which are within reach of an "unprivileged internet user" relative to other tenants.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed material, or otherwise cryptographically tie header values to the verified payload before using them for dispatch or tenant attribution:
- Include the shop domain and topic in `to_signable_string` (matching what Shopify actually signs, if Shopify includes them) or, at minimum, cross-check the resolved `shop` against the authenticated session/store record before acting.
- Do not use the unsigned `topic` header alone to select the handler that will parse and act on the body; validate that the body's own event indicators are consistent with the claimed topic where possible.

### Proof of Concept
1. Attacker installs the multi-tenant app on their own shop `attacker.myshopify.com` and triggers a webhook-eligible event (e.g. creates a customer with an attacker-chosen `note`/`tags` field), causing Shopify to POST a validly HMAC-signed body to the shared webhook endpoint.
2. Attacker (or a proxy they control, e.g. their own server relaying the same content) resends an HTTP POST with the *same raw body and `X-Shopify-Hmac-Sha256` header* to the identical webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and/or `X-Shopify-Topic: app/uninstalled`.
3. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `raw_body` only and finds it matches, so `Registry.process` proceeds using the forged headers, dispatching to the handler for the forged topic and passing `shop: "victim.myshopify.com"` in `WebhookMetadata`, causing the host app to act as if the victim shop generated this event.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
