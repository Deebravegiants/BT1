Webhook HMAC does not cover the `shop-domain` header, allowing cross-tenant webhook shop-spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, then trusts `request.shop` (read from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` HTTP header) as the tenant identity passed to the app's handler. The HMAC, however, is computed only over the raw request body, so the shop-identifying header is never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the received `hmac` value: [2](#0-1) 

Since `to_signable_string` is only the body, the `shop` value (sourced from the `shop-domain` header) never enters the HMAC computation: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity forwarded to the app's webhook handler: [4](#0-3) 

This is precisely the identity-binding gap called out in the analog task's rule set — "a field acted on but not covered by the HMAC." The equality that should hold is:
`verified(hmac) == (body, shop, topic, webhook_id, api_version)` bound together
but what actually holds is:
`verified(hmac) == (body)` only, while `shop` (and `topic`/`webhook_id`/`api_version`) are parsed unauthenticated from headers and handed to the handler as if bound.

### Impact Explanation
Any unprivileged internet user who legitimately installs the target app on their own store receives real, correctly-signed webhooks for that store (body `B`, valid `hmac = HMAC(secret, B)`). Because the `shop-domain` header is outside the signed scope, that same `(B, hmac)` pair remains "valid" no matter what `shop-domain` header accompanies it. The attacker can replay the exact request to the app's webhook endpoint while substituting an arbitrary victim shop's domain in the `shop-domain` header. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` claiming the body originated from the victim shop. If the host application uses `WebhookMetadata#shop` to scope data writes/reads (which is the documented purpose of this field), this enables cross-tenant data confusion/injection — an app could be tricked into applying a forged payload to a shop's data record set that the attacker does not own, which matches the "cross-tenant access" Critical-impact criteria.

### Likelihood Explanation
The bar to exploit is low: the attacker needs only their own legitimate (even trial/free) installation of the app to obtain a validly-HMAC-signed webhook body/signature pair — no access token, secret key, or privileged account is required. The only work is replaying the HTTP POST to the app's public webhook endpoint with a modified `shop-domain` header.

### Recommendation
Bind the shop (and ideally topic/webhook id/api version) into the signed material actually verified, e.g., by including the `shop-domain` header value in `to_signable_string`, or by cross-checking the webhook's declared shop against an out-of-band trusted list (e.g., the shop associated with the currently active/expected session) before invoking the handler. At minimum, `Utils::HmacValidator` should be extended so `VerifiableQuery` implementations can include a canonical set of headers (matching what Shopify actually signs) in the signable payload for webhook requests, not just the raw body.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; capture one delivered webhook: raw body `B`, header `X-Shopify-Hmac-SHA256: H` (valid because Shopify computed it with the app's real secret), `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Replay the exact HTTP request to the app's webhook endpoint, keeping body `B` and header `X-Shopify-Hmac-SHA256: H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` (`B`) — validation succeeds.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied data as if it came from `victim.myshopify.com`.
