### Title
`OmniBridge.describeWithdrawal` blindly indexes `getTransfer()` array by input order with no recipient match, misreporting status/txHash across withdrawals - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`createWithdrawalIdentifiers` assigns `WithdrawalIdentifier.index` purely by the position of each withdrawal in the caller-supplied `withdrawalParams` array (per bridge route), with no correlation to how the Omni indexer orders transfers for the same NEAR tx. `describeWithdrawal` then does `(await getTransfer({transactionHash}))[args.index]` and reports whatever `recipient`/`finalised.transaction_hash` is at that array position, with no check that `transfer.recipient` matches the withdrawal's own `destinationAddress`.

### Finding Description
The broken equality: for withdrawal `wid` with `wid.index = i` and `wid.withdrawalParams.destinationAddress = D`, the code assumes `getTransfer(txHash)[i].recipient === D`. Nothing enforces this.

- `createWithdrawalIdentifiers` (packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107) assigns `index` strictly by iteration order of the input `withdrawalParams` array, scoped per bridge route (`indexes.get(bridge.route)`).
- `OmniBridge.describeWithdrawal` (packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts:691-731) does `(await this.omniBridgeAPI.getTransfer({transactionHash: args.tx.hash}))[args.index]` and derives `status`/`txHash` from whatever transfer object lands at that array index — it reads `transfer.recipient` only to determine chain-kind branching (EVM vs Sol vs UTXO), never to verify it equals `args.withdrawalParams.destinationAddress`.
- No other guard in the file (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `supports()`) runs in this code path — those only execute during withdrawal creation/validation, not during status polling in `describeWithdrawal`.

Attacker input: submit a single NEAR intents transaction containing two Omni-bridge withdrawal legs to different chains/recipients (e.g., withdrawal A to an Ethereum address, withdrawal B to a Solana address), such that the Omni indexer's `getTransfer` array for that tx hash returns the transfers in a different order than they were passed into `createWithdrawalIdentifiers`. Since the indexer is a separate external system indexing on-chain events, there is no code-level guarantee that its list order matches input order (e.g., it could sort by internal transfer ID, processing/finalization time, or event log order). `watchWithdrawal` for `wid` with `index:0` will then read `getTransfer()[0]`, which may in fact be withdrawal B's transfer object, and report B's `status`/`txHash` as if it belonged to A.

### Impact Explanation
An integrator polling withdrawal A (e.g., destined for the Ethereum recipient) receives the completed status and `txHash` that actually correspond to withdrawal B (destined for the Solana recipient), or vice versa. This is a status/hash misreport that can cause an integrator to credit or reconcile against the wrong on-chain transaction for the wrong chain/recipient, while the sibling withdrawal is reported as still pending indefinitely. This matches the High severity category ("a status or hash misreport making an integrator credit or refund twice" / "a withdrawal stuck until manual intervention") — it is repeatable on any multi-leg Omni-bridge withdrawal batch where indexer ordering diverges from input ordering.

### Likelihood Explanation
Preconditions: a single NEAR tx must contain ≥2 Omni-bridge withdrawal legs (fully within an ordinary user's control — no privilege needed, just constructing a batch withdrawal). The divergence additionally requires the Omni indexer's `getTransfer` response ordering to differ from submission order for at least one pair of legs. This is plausible since nothing in the SDK or the indexer API contract documented here guarantees `getTransfer` returns array-position parity with the order withdrawal intents were created — the field intended for correlation (e.g., a transfer/withdrawal identifier or matching by `recipient`) is not used at all. Attacker cost is a single normal withdrawal transaction with two legs; no special timing or race condition is needed beyond the indexer's own list-ordering behavior.

### Recommendation
In `describeWithdrawal`, do not index into the array positionally. Instead, filter the `getTransfer` result by matching `transfer.recipient` (and ideally `token_id`/`amount`) against `args.withdrawalParams.destinationAddress` (normalized via `compareAddresses`), and only fall back to positional indexing if a unique match cannot be found (with an explicit assertion/log warning about ambiguity). If the indexer API exposes a stable transfer/withdrawal correlation ID at intent-creation time, prefer that over recipient-matching.

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
