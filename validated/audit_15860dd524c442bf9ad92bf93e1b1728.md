### Title
Crafted swap route can execute attacker-controlled code and steal unrelated wallet funds under the caller’s authorization - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` and `swap_debt` accept caller-provided swap-route bytes, authenticate the account owner or delegate, and forward the route to the configured router. [1](#0-0) [2](#0-1)  The controller authorizes only the intended input transfer and measures output, but it does not prevent the route from naming an attacker-controlled pool contract. [3](#0-2)  That pool can perform an additional token transfer from the caller while still returning a valid swap output, causing the enclosing strategy to settle successfully. [4](#0-3) 

### Finding Description
`process_swap_collateral` requires caller authorization and verifies account ownership before executing the route. [5](#0-4)  `swap_tokens` authorizes the router to pull exactly `amount_in`, invokes `execute_strategy` with the opaque `swap` argument, and then only checks controller input spend and output receipt. [6](#0-5) 

The route’s pool address is carried in the caller-controlled address registry and dispatched as a venue hop, with no pool-address allowlist in this execution path. [7](#0-6) [8](#0-7)  The adversarial harness shows that code reached below the caller’s `swap_collateral` authorization can invoke `token.transfer(caller, attacker, amount)`. [9](#0-8)  Simulation records that extra transfer as a child authorization, and enforcement accepts it when the caller signs the generated tree. [10](#0-9) 

The control test confirms that an honest authorization tree rejects the rogue transfer, while signing the route-generated tree authorizes it and empties the unrelated wallet balance. [11](#0-10) 

### Impact Explanation
This is theft of user funds, not merely a bad-price swap: the malicious pool can move assets that were never supplied to the lending account or declared as route input. [12](#0-11)  Because the rogue pool can return sufficient `token_out`, the router’s measured-output check and the controller’s final risk checks can both pass while the unrelated wallet-token transfer remains committed. [13](#0-12) [14](#0-13) 

### Likelihood Explanation
An unprivileged attacker can deploy the malicious venue-compatible contract and supply a crafted `swap` payload, requiring no governance role, leaked key, or protocol privilege. [15](#0-14)  Exploitation does require the victim to submit or sign a transaction whose authorization tree includes the malicious nested transfer, so exploitation depends on a malicious route/provider or an unsafe signing client. [16](#0-15)  The resulting loss can exceed the routed amount because it is bounded by the victim’s spendable wallet balance rather than by `amount_in`. [17](#0-16) 

### Recommendation
Do not expose arbitrary pool contract addresses beneath a user-authorized strategy call. [18](#0-17)  Restrict executable pool addresses to a governance-managed registry or otherwise execute routes through an interface that cannot inherit the caller’s authorization tree. [16](#0-15)  Until a contract-level boundary exists, all route builders and wallets should simulate the call, decode the complete authorization tree, and reject any child invocation other than the exact expected token transfer. [19](#0-18) 

### Proof of Concept
1. The attacker deploys a pool-shaped contract that implements the selected venue call; in addition to consuming the router input and returning `token_out`, it invokes `token.transfer(victim, attacker, victim_balance)` for an unrelated token. [9](#0-8) 
2. The attacker constructs a `StrategyPayload` whose `assets` registry contains that pool and whose hop instruction selects it. [7](#0-6) 
3. The victim invokes `Controller::swap_collateral(caller=victim, account_id=victim_account, current=USDC_key, from_amount=amount, new=ETH_key, swap=crafted_payload)`. [20](#0-19) 
4. The controller withdraws the collateral, grants the router only the declared `amount_in`, and executes the crafted route. [3](#0-2) 
5. The malicious pool transfers the victim’s unrelated wallet tokens and returns enough `token_out` to satisfy the measured-output and final account checks. [13](#0-12) 
6. If the victim signs the authorization tree generated by simulation, the transaction succeeds; the harness records `victim_wallet = 0`, `attacker_wallet = victim_balance`, and the expected strategy output. [10](#0-9)

That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
