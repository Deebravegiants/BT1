### Title
Unbounded `NativeDepositOf` row growth lets an attacker monopolize `ContractInfo::process_deletion_queue_batch`, starving all subsequently queued contracts' cleanup - (File: substrate/frame/revive/src/storage.rs)

### Summary
`process_deletion_queue_batch` processes the deletion queue strictly FIFO, one entry at a time, and only advances to the next queued contract once the current head entry has fully finished both its `NativeDepositOf` drain and child-trie kill for the current call. An attacker can cheaply inflate the number of `NativeDepositOf` rows attributed to one contract (many distinct native-fallback payers), then terminate it, causing that single queue entry to take many blocks to drain and blocking cleanup of every other contract queued behind it.

### Finding Description
`ContractInfo::queue_for_deletion` inserts a `DeletionQueueItem` into a strictly FIFO `DeletionQueueManager` [1](#0-0) . `DeletionQueueManager::next` always returns the entry at `delete_counter` — there is no mechanism to skip ahead to a later, cheaper entry [2](#0-1) .

`process_deletion_queue_batch`'s main loop pulls exactly one entry via `queue.next()`, then for that entry: (1) computes `key_budget_for(remaining, weight_per_native_key)` and clears up to that many `NativeDepositOf` keys via `clear_prefix`; if `result.maybe_cursor.is_some()` (i.e. more rows remain), it `break`s out of the loop entirely; (2) only if phase 1 fully finished does it proceed to kill the child trie, and only removes the entry from the queue once *both* phases finish in the same call [3](#0-2) . Crucially, the `break` on an unfinished entry terminates the whole batch — it does not move on to process the next queued contract with remaining weight.

`NativeDepositOf` rows are created by `PGasDeposit::charge_and_hold` whenever a payer's reducible PGAS balance is insufficient, causing a native-currency fallback charge and a `record_native_deposit(from, to, amount)` call that inserts/updates `NativeDepositOf::<T>::mutate(to, from, ...)` [4](#0-3) [5](#0-4) . There is no cap on the number of distinct `(contract, payer)` rows a single contract can accumulate — only the deposited amount is bounded by the payer's balance, not the row count.

An unprivileged attacker can: (1) instantiate a contract; (2) drive N distinct signed accounts (each holding native balance but insufficient/no PGAS) to each perform a storage-writing call on the contract (e.g. via a fixture like `MultiContributorStorage.growStorage`), each triggering the native fallback in `charge_and_hold` and creating one `NativeDepositOf` row keyed by that payer; (3) terminate the contract so `queue_for_deletion` places it at the tail of the FIFO queue. Because the queue is FIFO and `process_deletion_queue_batch` breaks the entire batch when an entry's native-row drain isn't finished in one pass, this contract's entry sits at the head of the queue for `ceil(N / keys_cleared_per_block)` blocks, during which no other queued contract (however cheap) is even reached, regardless of remaining weight budget after this entry's `break`.

Existing protections do not prevent this: there is no per-block or per-entry cap forcing forward movement to the next queue entry, no limit on the number of distinct payer rows per contract, and `deletion_budget`/`key_budget_for` only bound work *within* the current head entry, not fairness *across* entries.

### Impact Explanation
Any other terminated contract queued after the attacker's inflated entry will have its child-trie and any of its own `NativeDepositOf` rows left undeleted for as long as the head entry takes to drain — proportional to the attacker-chosen N and unbounded in principle (attacker can generate arbitrarily many distinct payer accounts). This is a genuine service-degradation / lazy-deletion-queue-starvation issue: chain storage for unrelated, otherwise-cheap-to-clean contracts remains bloated and un-reclaimed for many blocks, contrary to the intended lazy-but-fair cleanup design described in the module's own comments ("Both the contract's child trie and any `NativeDepositOf` entries it held are drained lazily in `on_idle`").

### Likelihood Explanation
The attack requires no privileged access — only funding N signer accounts with enough native balance to pay small storage deposits and issuing N ordinary signed extrinsics/contract calls plus one terminate call. Feasibility scales with attacker budget (transaction fees + minor deposits per payer); it is fully repeatable and deterministic given the strict-FIFO, no-skip queue design.

### Recommendation
Change `process_deletion_queue_batch`'s loop so that exhausting the weight budget on one entry does not abort the whole batch: continue attempting subsequent queue entries with any leftover weight rather than `break`ing unconditionally, or bound the maximum weight/keys spendable on a single entry per call so remaining weight is guaranteed to be offered to later entries. Additionally, consider capping the number of distinct `NativeDepositOf` payer rows per contract (or batching refunds so termination collapses them) so a single contract cannot accumulate unbounded cleanup cost.

### Proof of Concept
Rust integration test in `substrate/frame/revive`:
1. Instantiate contract `A` and, via `PGasDeposit`-backed config, drive N distinct funded signer accounts (N = 2, 50, 2000) to each perform a storage write that triggers `charge_and_hold`'s native fallback against `A`, producing N `NativeDepositOf::<T>::get(A, payer_i)` rows.
2. Instantiate a second, cheap contract `B` with a small trie and terminate it, queuing it after `A`.
3. Terminate `A`, queuing it before `B` (FIFO order).
4. Repeatedly call `ContractInfo::process_deletion_queue_batch` with a fixed realistic `WeightMeter` limit (e.g. matching one block's on-idle budget) and assert:
   - `B`'s child trie (`child::kill_storage`/`AccountInfoOf` for `B`) is **not** cleared until `NativeDepositOf::iter_prefix(A)` is empty.
   - Count the number of `process_deletion_queue_batch` calls (blocks) required before `B` is drained, and confirm it grows linearly with N, demonstrating unbounded/attacker-controlled starvation of `B`'s cleanup behind `A`'s inflated entry.

			<() as Deposit<T>>::charge_and_hold(reason, src, to, amount)?;
			Self::record_native_deposit(from, to, amount);
		}

	}
