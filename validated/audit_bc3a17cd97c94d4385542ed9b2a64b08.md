## Title
Missing duplicate-vote/authority-index check in ECDSA BEEFY supermajority threshold allows padding participation count without real supermajority - (File: evm/src/consensus/EcdsaBeefy.sol)

### Summary
`EcdsaBeefy.verifyMmrUpdateProof` computes `sigLen = relayProof.signedCommitment.votes.length` and gates consensus updates on `checkParticipationThreshold(sigLen, authoritySet.len)` (2/3+1 of the authority set) *before* confirming that the `authorityIndex` values in `votes` are distinct. [1](#0-0)  The same pattern exists in the pure-Rust verifier used by `ismp-beefy` and the tesseract relayer, `verify_mmr_update_proof`, which counts `mmr.signed_commitment.signatures.len()` for the threshold check with no de-duplication of `sig.index`. [2](#0-1) 

### Finding Description
The BEEFY consensus client is reachable by any relayer submitting a consensus update through `IsmpHost`/`HandlerV2`; it is one of the trust-critical primitives feeding `IntermediateState`s into the bridge (state commitments consumed for message delivery, token bridge mint/burn proofs, etc.), so a forged/weak-quorum BEEFY update is a "forged message delivery / unsound state commitment" class bug per the analog-mapping in this task.

Other consensus clients in this same codebase explicitly defend against exactly this bug class — repeated/duplicated attestors being counted multiple times toward a supermajority threshold:
- Pharos: `verify_validator_membership` explicitly rejects duplicate participant keys before the stake-threshold check. [3](#0-2) 
- Tendermint: `ensure_unique_addresses` explicitly rejects duplicate validator addresses. [4](#0-3) 
- BSC: the vote bitset is explicitly checked so bits beyond `current_validators.len()` cannot inflate the participant count. [5](#0-4) 

In contrast, `EcdsaBeefy.verifyMmrUpdateProof` (Solidity) and `verify_mmr_update_proof` (Rust) never check that the `authorityIndex`/`sig.index` values submitted in the vote list are unique before comparing `sigLen`/`signatures_length` against the 2/3+1 threshold:

```solidity
uint256 sigLen = relayProof.signedCommitment.votes.length;
...
if (!checkParticipationThreshold(sigLen, authoritySet.len)) revert SuperMajorityRequired();
...
for (uint256 i = 0; i < sigLen; i++) {
    Vote memory vote = relayProof.signedCommitment.votes[i];
    address authority = ECDSA.recover(commitmentHash, vote.signature);
    authorities[i] = MerkleMultiProof.Leaf({index: vote.authorityIndex, hash: keccak256(abi.encodePacked(authority))});
}
bool valid = MerkleMultiProof.VerifyProof(authoritySet.root, relayProof.proof, authorities, authoritySet.len);
``` [6](#0-5) 

Since `ECDSA.recover` will happily "verify" the same signature bytes repeated multiple times (the signature is valid for whichever single authority actually produced it), and `authorityIndex` is attacker-supplied per vote entry, a relayer can submit the same `(signature, authorityIndex)` pair (or several colluding-but-still-minority signers' pairs) many times to inflate `sigLen`/`signatures_length` past the 2/3+1 threshold while genuine distinct signer participation stays below quorum. This mirrors CVE-2017-14032's root cause: an unbounded/duplicated set of "intermediate" attestation elements is used to satisfy a counting-based authentication gate, without the gate first collapsing the set to genuinely-distinct authenticators — exactly the invariant that Pharos, Tendermint, and BSC's verifiers already enforce for their own quorum checks in this same codebase.

The remaining question — whether `MerkleMultiProof.VerifyProof` downstream would independently reject duplicate `index` leaves — could not be conclusively confirmed from the indexed codebase (the `solidity-merkle-trees` library source and the `rs_merkle`/pallet-mmr `MerkleProof::verify` internals were not retrievable via search in this session). If that library treats a repeated `(index, hash)` leaf as valid whenever the *first* occurrence's authenticity is provable (i.e. it does not require `authorities.len()` unique indices matching `authoritySet.len` exactly, and instead just recomputes a root from whatever leaves/indices are given), then the threshold-count bypass converts directly into a consensus-authentication bypass: the client would accept a BEEFY commitment signed by fewer than 2/3+1 of the true authority set, letting an attacker forge `IntermediateState` commitments (state roots / overlay roots) that downstream `HandlerV2`/pallet-ismp code trusts for message delivery. This is a case where I could not fully verify the exploitability end-to-end from the available index and flag it explicitly as uncertain — a Devin session with full repository access (including the `solidity-merkle-trees` submodule/dependency and `rs_merkle`) would be needed to confirm whether `VerifyProof`/`MerkleProof::verify` independently rejects duplicate leaf indices before treating the finding as fully proven.

### Impact Explanation
If duplicate-index leaves are not independently rejected by the merkle multiproof verification, this allows a relayer to fabricate a "supermajority" BEEFY commitment using far fewer real validator signatures than required, letting them push arbitrary `nextAuthoritySet`/`latestHeight`/`IntermediateState` (state/overlay roots) into the trusted consensus state. Downstream, `HandlerV2` and pallet-ismp consumers treat these `IntermediateState`s as authenticated state commitments for proof verification (message delivery, GET/POST responses, token bridge mint/burn proofs), so this would constitute forged message delivery / unsound state commitment — High severity if confirmed.

### Likelihood Explanation
Medium-to-Low confidence without confirming the merkle library's duplicate-index handling. The attack requires no special privilege — any account able to call `EcdsaBeefy.verify`/submit an ECDSA BEEFY consensus message can attempt it — but genuinely exploiting it requires the underlying merkle multiproof verifier to accept repeated leaf indices, which was not confirmed in this session.

### Recommendation
In both `EcdsaBeefy.verifyMmrUpdateProof` (Solidity) and `verify_mmr_update_proof` (Rust), before comparing signature/vote count to the supermajority threshold, deduplicate on `authorityIndex`/`sig.index` (and/or on recovered signer address) the same way `verify_validator_membership` (Pharos) and `ensure_unique_addresses` (Tendermint) already do, rejecting the proof if `unique_count != sigLen`.

### Proof of Concept
Not independently reproducible from the indexed code alone — reproducing it requires confirming `MerkleMultiProof.VerifyProof`'s (and `rs_merkle`/pallet-mmr `MerkleProof::verify`'s) behavior on a `Leaf[]` array containing a repeated `(index, hash)` entry. A concrete PoC would submit a `RelayChainProof`/`MmrProof` whose `votes`/`signatures` array repeats one real validator's `(authorityIndex, signature)` pair enough times to clear `checkParticipationThreshold`, while distinct signer count remains below 2/3+1, and observe whether `verify()`/`verify_mmr_update_proof` accepts it.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}

/// Verify that all participating validators are members of the trusted validator set.
fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
