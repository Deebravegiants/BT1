## Title
Webhook `shop` identity is read from an unauthenticated header while the HMAC only covers the request body, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#shop` returns the value of the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header, but the HMAC signature validated by `Registry.process` only covers the raw request body. Any actor who can produce a body/HMAC pair that is valid for the app's shared secret can attach an arbitrary `shop-domain` header, and the gem will pass that spoofed shop identity straight to the host application's webhook handler as authenticated data.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

i.e. the signable string used for HMAC validation is only `@raw_body`. The `shop` accessor, however, is derived independently from a header that is never part of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC over the body and, once that check passes, forwards `request.shop` (the unauthenticated header value) to the registered handler as trusted tenant identity: [3](#0-2) 

This breaks the identity binding `HMAC-signed bytes == bytes acted on`: the HMAC only binds the body, but the `shop` field that host applications use to key their persistence, sessions, or authorization (i.e., "which merchant does this webhook belong to") is taken from a field that is not covered by the signature at all.

Any merchant who has installed the app can trigger a real webhook for their own store (a valid `raw_body` + valid HMAC, since Shopify signs it with the app's shared `client_secret`), intercept the outbound delivery, and resend it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` will still succeed because it only checks `raw_body` against the (unchanged) HMAC: [4](#0-3) 

The app's handler then processes attacker-controlled body content while believing it originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: the gem hands the host application a `WebhookMetadata#shop` value that has no cryptographic binding to the payload it purportedly accompanies. Any consuming app that uses `data.shop` to select which merchant's records/session to mutate (a documented and expected usage pattern for this field) can be made to apply attacker-supplied webhook data to a different tenant than the one that actually sent it — meeting the "cross-tenant access" bar.

### Likelihood Explanation
Any shop that has installed the app already possesses everything needed: it can generate a validly-HMAC-signed body simply by triggering a real event in its own store, and it fully controls headers on the resent request to the app's public webhook URL. No access to the app's `client_secret`, access tokens, or privileged accounts is required — only an ordinary merchant installation.

### Recommendation
Bind the shop identity to the signed payload instead of trusting the unauthenticated header: parse the shop domain out of the (HMAC-verified) body payload where Shopify includes it, or explicitly document/require that consuming code re-verify `shop` against a value obtained through an independently authenticated channel (e.g., a stored per-shop webhook secret, or cross-checking against the shop that installed the webhook subscription) before using it as a tenant key.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any subscribed webhook topic (e.g., `orders/create`), capturing the legitimate raw body `B` and its valid header `x-shopify-hmac-sha256` value `H = HMAC(client_secret, B)`.
2. Attacker resends a request to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(client_secret, B)` and compares it to `H` — this matches because only the body is signed: [5](#0-4) 
4. Validation passes, and `request.shop` returns `"victim-shop.myshopify.com"` from the attacker-controlled header, which is forwarded unchecked to the handler: [6](#0-5) 
5. Any host application logic keyed on `data.shop` now operates against the victim tenant using attacker-supplied body content.
