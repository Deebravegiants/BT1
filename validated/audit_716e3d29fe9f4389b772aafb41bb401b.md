### Title
Webhook shop attribution (`shop-domain`) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then dispatches the handler using the unauthenticated `shop` value, breaking the binding `authenticated(body) == acted-on(shop)`.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are parsed from headers that are never included in the signed material: [2](#0-1) 

`HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (i.e., the body) against `verifiable_query.hmac`: [3](#0-2) 

`Registry.process` performs this body-only HMAC check and then trusts `request.shop` (an unsigned header) to build `WebhookMetadata` and dispatch to the app's handler: [4](#0-3) 

Because the HMAC only proves the body bytes were signed by Shopify with the app's shared secret, and never binds that signature to a specific `shop-domain`, any request carrying a body/HMAC pair that is valid for one shop will also pass validation with the `shop-domain` header rewritten to a different tenant. The library's dispatched `WebhookMetadata.shop` is therefore attacker-controlled independent of which tenant's data was actually signed.

### Impact Explanation
This breaks the identity binding `verified-signer(body) == shop-that-event-is-attributed-to`, which host applications rely on to look up per-tenant sessions/state and to trust the event source. An attacker who controls or has access to one shop's genuine webhook traffic (e.g., their own development/trial store using the same app) can capture a body+HMAC pair valid for that shop and replay it with an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header value. The app's webhook handler—built directly on this gem's `Registry.process`/`WebhookMetadata`—will process the payload as if it originated from the victim's shop, causing cross-tenant data confusion (e.g., attacker-controlled order/product/customer payloads attributed and applied to another merchant's tenant).

### Likelihood Explanation
Any developer using this gem's documented `Registry.process` and `WebhookMetadata.shop` is exposed, since the vulnerability is in the gem's own signature-verification/dispatch logic rather than misuse by the host app. Exploitation only requires network access to the app's public webhook endpoint and one signed body/HMAC pair (obtainable from the attacker's own shop using the same app installation), not the app's `api_secret_key` or any privileged credential.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (or otherwise cryptographically bind them) in the HMAC-signable string of `Webhooks::Request`, or independently verify that the `shop-domain` header matches the shop the caller expects/has a session for, before dispatching to handlers.

### Proof of Concept
1. Register a webhook handler with the app; the app is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`.
2. Trigger a webhook event on `attacker-shop.myshopify.com` (e.g., `orders/create`) so Shopify sends a POST with body `B` and header `x-shopify-hmac-sha256 = HMAC(secret, B)`.
3. Capture the raw HTTP request the app receives.
4. Replay the exact same body `B` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but change `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
5. `HmacValidator.validate` succeeds because it only checks `B` against the HMAC per `Request#to_signable_string` / `HmacValidator.validate_signature`: [5](#0-4) 
6. `Registry.process` dispatches the handler with `shop: request.shop` equal to `victim-shop.myshopify.com`, even though the signed content originated from `attacker-shop.myshopify.com`: [6](#0-5)
