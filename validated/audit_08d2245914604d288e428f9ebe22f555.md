### Title
Webhook `shop-domain` header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature validated in `ShopifyAPI::Webhooks::Registry.process` only signs the raw request body, not the shop header. Because the HMAC secret (`api_secret_key`) is shared by the app across every shop that installs it, any shop that legitimately receives a webhook can capture a valid `(body, hmac)` pair and replay it against the app's webhook endpoint with an arbitrary `shop-domain` header, causing the handler to process attacker-controlled data under a victim shop's identity.

### Finding Description
`Request#hmac`/`#to_signable_string` show that only the raw body bytes are covered by the signature: [1](#0-0) 

`shop` is read straight from an HTTP header with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC and then trusts `request.shop` unconditionally when building the data passed to the handler: [3](#0-2) 

`HmacValidator.validate` confirms the signature only covers `verifiable_query.to_signable_string` (i.e., the body), never the shop header: [4](#0-3) 

Because `api_secret_key` is a single per-app secret shared across all installing shops (not per-shop), `HMAC(secret, body)` is identical no matter which shop it originated from. An unprivileged user who runs their own shop with the app installed can capture a legitimate `(body, hmac)` pair from a webhook delivered to their own store, then POST that same `body`/`hmac` pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still succeed (it never inspects the shop header), and `WebhookMetadata.shop` will be the attacker-supplied victim domain, so the app's webhook handler processes attacker-controlled webhook content believing it came from the victim tenant.

This breaks the identity binding: **shop asserted in the `shop-domain` header == shop cryptographically bound by the HMAC**. The equality does not hold because the HMAC computation excludes the shop field entirely.

### Impact Explanation
This is a cross-tenant integrity issue: an attacker who controls one tenant (their own shop) can forge webhook events that the host application will attribute to a different, victim tenant, since nothing in the signature verification ties the payload to the claimed shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g., looking up per-shop state, writing shop-scoped data, or triggering shop-scoped side effects), this enables cross-tenant data corruption or spoofed events — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any unprivileged user who can install the app on their own store (a normal, unprivileged action): they only need to capture one legitimate webhook (`body` + `X-Shopify-Hmac-Sha256`) delivered to their own shop and then replay it with a modified `shop-domain` header. No access token, `api_secret_key`, or privileged access to Shopify's infrastructure is required.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically verify that the shop header matches the shop encoded in the webhook payload/topic registration before trusting `request.shop`. At minimum, `Registry.process` should not treat `request.shop` as trusted merely because the body's HMAC validated — the shop domain must be part of what is signed and verified.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook: headers include `X-Shopify-Hmac-Sha256: H` and body `B`, where `H = HMAC(api_secret_key, B)`.
2. Attacker sends a POST to the app's webhook endpoint with the same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses `shop` from the (attacker-controlled) `shop-domain` header.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, B) == H` — this passes because `B` and `H` are unchanged from the legitimate delivery.
5. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed(B) ...)`, causing the app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.
