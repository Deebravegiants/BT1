### Title
Webhook `shop` and `topic` identity are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook by validating only the raw request body against the app's `api_secret_key`, then trusts the unauthenticated `shop-domain` and `topic` headers to route and label the payload. This breaks the identity binding `shop asserted in the header == shop actually associated with the HMAC-signed bytes`, letting an unprivileged internet user who can obtain any one valid `(body, hmac)` pair for the app (e.g. by installing the target app on their own free/dev store and capturing a webhook Shopify sends them) replay that body to the app's public webhook endpoint while forging the `shop-domain`/`topic` headers to claim it belongs to a different, victim tenant.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body` — it does not include the `shop`, `topic`, `webhook_id`, or `api_version` headers: [2](#0-1) 

Those same unauthenticated header values are then read directly off attacker-controllable HTTP headers: [3](#0-2) 

`Registry.process` verifies only the HMAC of the body and then forwards `request.shop` and `request.topic` — both unverified — straight into `WebhookMetadata`, which is handed to the host application's handler as the trusted tenant/topic identity: [4](#0-3) [5](#0-4) 

The identity equality that should hold is: `shop the HMAC authenticates == shop the handler acts on`. Because the HMAC only authenticates the raw body bytes, this equality is never enforced — any header value can be substituted after the fact without invalidating the signature check. The library's own documentation instructs developers to trust `data.shop` for tenant-scoped work (e.g. enqueuing a job keyed by `shop_domain: data.shop`): [6](#0-5) 

### Impact Explanation
An attacker who is any ordinary internet user can create a free Shopify development store, install the target app on it, and thereby obtain from Shopify a genuinely-signed `(raw_body, X-Shopify-Hmac-Sha256)` pair computed with the app's real `api_secret_key` — no leaked secret or privileged access is required, since Shopify signs the webhook for them as a normal part of installation. The attacker then POSTs that exact raw body to the app's public webhook endpoint while spoofing `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) to name a victim shop. `Utils::HmacValidator.validate` still returns `true` because it only checks the body bytes, so `Registry.process` invokes the handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload actually originates from the attacker's own store. Any host application that uses `data.shop` to scope tenant data mutations, cache invalidation, session lookups, or billing/inventory updates (the exact pattern shown in this gem's own docs) will attribute attacker-controlled data to a shop the attacker does not own — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
High. No credentials, tokens, or leaked secrets are required — only the ability to install the target app on a store the attacker controls (which for most public/free apps is trivial and unprivileged) and the ability to send arbitrary HTTP requests to the app's public webhook route, which by design must be internet-reachable so Shopify can deliver webhooks to it.

### Recommendation
Extend `Webhooks::Request#to_signable_string` (or add a post-HMAC-verification check in `Registry.process`) so that the `shop`, `topic`, and `webhook_id` identity fields are cryptographically bound to the signature, or at minimum require host applications to independently confirm `request.shop` corresponds to a shop with an active, previously-established session/subscription for that specific `webhook_id`/topic before acting on the payload. Document this binding requirement clearly, and consider validating that the `shop` header matches an expected format and a known installed shop before invoking the handler.

### Proof of Concept
1. Attacker creates a Shopify partner/dev store `attacker-shop.myshopify.com` and installs the target app (normal, unprivileged action).
2. Shopify delivers a legitimate webhook to the app, e.g. for `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `(B, H)` (e.g. from their own server logs, since it was delivered to infrastructure they control).
4. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with:
   - body: `B` (unchanged)
   - header `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since it signs only `B`)
   - header `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged)
   - header `X-Shopify-Topic: orders/create` (unchanged or forged)
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`: [7](#0-6) 
6. The handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` and attacker-controlled `body`, even though the data never came from that shop, achieving cross-tenant spoofing.
