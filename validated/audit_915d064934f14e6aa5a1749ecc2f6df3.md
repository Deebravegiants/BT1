## Title
Unhandled ERC20/TRC20 transfer return-value failures in `IntentGatewayV2.withdraw()` and dust-sweep path permanently lock/misaccount escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` escrows tokens for cross-chain intents and later releases them to a beneficiary via `withdraw()`, and also sweeps residual "dust" tokens via `onPostRequest`'s `SweepDust` branch. Both paths use a raw low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check that the **call itself did not revert** (`success`), never decoding/verifying the ERC20 **return value** of `transfer()`. This is the same bug class as the referenced H02 finding: ERC20-family tokens that return `false` on failure instead of reverting will silently fail the transfer while the contract proceeds as if funds were delivered.

### Finding Description
In `withdraw()`, escrowed token amounts are decremented from `_orders[...]` and the order is marked filled *before or regardless of* whether the underlying token transfer actually succeeded: [1](#0-0) 

The same unchecked-return-value pattern also settles protocol fees: [2](#0-1) 

And in the governance-triggered `SweepDust` handling: [3](#0-2) 

In every one of these, `success` only reflects whether the low-level call reverted — it does not decode the boolean encoded in the returndata that ERC20/TRC20 `transfer()` is supposed to return. Any ERC20-compliant-but-non-reverting token (returns `false` on insufficient balance/blacklist/paused instead of reverting, which is common among older/legacy tokens and some TRC20 tokens on Tron) will pass the `success` check while the beneficiary receives nothing.

Contrast this with the non-Tron `IntentsBase.sol`, which correctly uses `SafeERC20.safeTransfer`, which decodes and enforces the boolean return value: [4](#0-3) 

The Tron contract even imports and `using`s `SafeERC20 for IERC20` (line 56) elsewhere for `safeTransferFrom` on deposit, but deliberately drops down to raw `.call` for these payout paths — an inconsistency that indicates the check was intentionally weakened, not simply omitted by oversight, but the effect is identical to H02: unhandled transfer failures break bridge/escrow synchronization.

### Impact Explanation
Once `withdraw()` runs, `_orders[commitment][token]` is decremented and `_filled[commitment]` is set (or `EscrowReleased`/`EscrowRefunded` emitted) irrespective of whether the beneficiary actually received tokens. If the underlying token transfer silently fails:
- The beneficiary/filler permanently loses the escrowed funds (funds remain stuck in the `IntentGatewayV2` contract with no accounting path left to reclaim them, since `_orders[...]` has already been zeroed/decremented and the order marked filled).
- This constitutes permanent freezing/loss of user or solver funds, matching the accepted "concrete theft or permanent freezing of funds" impact category.

### Likelihood Explanation
This is reachable by any solver/filler calling the withdrawal/redeem flow (`RedeemEscrow`/`RefundEscrow` via `onPostRequest`, or the direct `withdraw` internal call paths) whenever the escrowed/fee token is a non-standard ERC20/TRC20 that returns `false` instead of reverting on failure — a known and common token behavior class (this is exactly the scenario the original H02 report targeted). No privileged role is required; any user selecting such a token for their intent order triggers the vulnerable code path during normal settlement.

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()`, the fee redemption block, and the `SweepDust` handler with `SafeERC20.safeTransfer` (already imported and used elsewhere in the same contract), which decodes and enforces the ERC20 return value and reverts on failure, keeping the escrow accounting synchronized with actual on-chain balances.

### Proof of Concept
1. An order escrows token `T` (a non-reverting ERC20/TRC20 that returns `false` on failed transfers, e.g., due to a pause or blacklist condition applied to the `IntentGatewayV2` contract or beneficiary after escrow).
2. Solver fills the order; `onPostRequest` receives a `RedeemEscrow` request and calls `withdraw(body, false)`.
3. Inside `withdraw()`, `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` is executed. Token `T`'s `transfer()` returns `false` (no revert) because, e.g., the beneficiary is blacklisted or a pause is active.
4. `success` is `true` (the call didn't revert), so the code does not revert; `_orders[body.commitment][token] -= amount` proceeds and `_filled[body.commitment] = beneficiary` is set, emitting `EscrowReleased`.
5. The beneficiary never receives the tokens, and there is no remaining code path to reclaim them — the escrowed `amount` of token `T` is permanently stuck in `IntentGatewayV2`.
