## Title
Webhook `shop`/`topic`/`webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant spoofing via header manipulation - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signable payload from the raw body only, while `shop`, `topic`, `webhook_id` and `api_version` are read straight from HTTP headers and passed unauthenticated to the webhook handler. An unprivileged attacker who can obtain any single legitimately-signed `(raw_body, hmac)` pair for the app (e.g. by installing the app on their own store) can replay that body/HMAC to the app's public webhook endpoint while forging the `shop-domain` (and other) headers to point at a victim tenant, because the equality the gem is supposed to enforce — "the shop the HMAC authenticates == the shop the handler acts on" — is never actually checked.

### Finding Description
`Webhooks::Request#to_signable_string` only returns the raw HTTP body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all derived directly from request headers, none of which participate in the signable string: [2](#0-1) 

`Registry.process` validates only that body-derived HMAC, then immediately trusts the unauthenticated header-derived `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

Because `HmacValidator.validate` calls `to_signable_string`, which is body-only, `Utils::HmacValidator.validate(request)` returning `true` proves only that the body bytes were HMAC'd with `Context.api_secret_key` — it proves nothing about which shop, topic, or webhook that body belongs to: [4](#0-3) 

This exactly matches the reported bug class: a field that is acted upon (`shop`) is not covered by the cryptographic check that is supposed to bind it (`hmac`). The broken equality is:
`shop authenticated by HMAC == shop delivered to WebhookMetadata` — the left side does not exist at all, so the equality can never hold, yet the code proceeds as if it does.

### Impact Explanation
Because the `client_secret`/`api_secret_key` used to sign webhooks is per-app (shared across every merchant that installs the app), any unprivileged user can install the app on their own store and legitimately capture a valid `(body, x-shopify-hmac-sha256)` pair from a real webhook delivery. That pair remains HMAC-valid forever (no nonce/timestamp binding is enforced by this code path) and can be replayed to the app's public webhook endpoint with the `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id` headers rewritten to any value. `Registry.process` will accept it as valid and dispatch it to the handler labeled with the attacker-chosen shop/topic/id, causing cross-tenant data confusion in any handler that trusts `WebhookMetadata#shop` to select the tenant record to update — satisfying the "Critical - cross-tenant access" impact bar.

### Likelihood Explanation
Exploitation requires only: (1) ability to install the target app on any store (unprivileged, standard merchant action) to obtain one valid signed payload, and (2) ability to send arbitrary HTTP requests with custom headers to the app's public webhook endpoint. No `api_secret_key`, access token, or privileged account is required — only observation of one's own legitimate webhook traffic.

### Recommendation
Include the identity-binding headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body before trusting `request.shop`/`request.topic` in `Registry.process`. At minimum, document that `shop`/`topic`/`webhook_id` are unauthenticated and must not be used by host applications for tenant selection without an independent shop-authorization check (e.g. verifying the shop has an active, matching session/access token).

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw POST body and its `X-Shopify-Hmac-Sha256` header — this is a legitimately signed `(body, hmac)` pair.
2. Replay that exact body and HMAC header to the same app's webhook endpoint, but set:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - (optionally) `X-Shopify-Topic`/`X-Shopify-Webhook-Id` to any desired values
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-derives the HMAC from the raw body [5](#0-4)  — validation succeeds because the body/HMAC pair is legitimate.
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the attacker-forged `victim-shop.myshopify.com` value [6](#0-5) , causing any handler logic keyed on shop to act as if the data came from the victim tenant.
