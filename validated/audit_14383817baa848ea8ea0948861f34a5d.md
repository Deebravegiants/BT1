### Title
Premature `_filled` state transition in `_cancelFromDest` can permanently trap escrowed order funds if the `RefundEscrow` message never lands - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`_cancelFromDest` marks an order as settled on the destination chain (`_filled[commitment] = order.user`) *before* the corresponding `RefundEscrow` message is guaranteed to be delivered and processed on the source chain. If that cross-chain message is never successfully delivered/authenticated on the source chain, the order is left in a state from which no recovery path exists: the destination chain has already recorded the order as finished, and the source chain's only alternate cancellation path (`_cancelFromSource`) cross-checks the destination's `_filled` slot and will now see it non-empty, causing it to revert with `Filled()`. The source-chain escrow is then permanently unreachable, exactly analogous to the GoGoPool `recordStakingError()` → `finishFailedMinipoolByMultisig()` sequence that produced a dead-end state from which `withdrawMinipoolFunds()` could never succeed.

### Finding Description
`cancelOrder` routes cross-chain, destination-initiated cancellations to `_cancelFromDest`: [1](#0-0) 

This function performs the state-defining write `_filled[commitment] = address(uint160(uint256(order.user)))` and only afterward dispatches the `RefundEscrow` POST request via `_post(...)`, with `timeout: 0` (no timeout) set inside `_post`: [2](#0-1) 

The destination-side `_filled` write happens unconditionally and is irreversible by design — there is no code path that clears it back to `address(0)`. The only way the escrowed tokens on the *source* chain are ever released is through `onAccept` successfully authenticating and processing the `RefundEscrow` message: [3](#0-2) 

If that message is never delivered (relayer never submits the proof), or `_authenticate`/`_checkRelayer` permanently rejects it (e.g., a relayer rotation via `setRelayer` between dispatch and delivery, or a misconfigured/unregistered deployment on the source side), the withdrawal is never executed and the escrow in `_orders[commitment][token]` on the source chain remains untouched — but frozen.

Crucially, the *other* cancellation route from the source chain, `_cancelFromSource`, is also foreclosed once the destination side has already set `_filled`. That path dispatches a `DispatchGet` to read the destination's `_filled` storage slot for the commitment and expects it to be empty to prove no fill/cancellation occurred: [4](#0-3) 

Because `_cancelFromDest` already wrote a non-zero value into that same `_filled` slot, the GET response will contain a non-empty value, and `onGetResponse` will revert with `Filled()`: [5](#0-4) 

Both `fillOrder` and `cancelOrder` on the destination chain also short-circuit with `revert Filled()` once `_filled[commitment] != address(0)`: [6](#0-5) [7](#0-6) 

So once `_cancelFromDest` executes, every remaining code path that could resolve the order (fill it, cancel it again, or verify it as unfilled) is blocked, and the only surviving path to release the source-chain escrow is a single Hyperbridge `RefundEscrow` message with no timeout and no retry/authentication-failure recovery mechanism. This mirrors the GoGoPool finding precisely: an intermediate/administrative state transition (`recordStakingError` → `finishFailedMinipoolByMultisig`) was allowed to complete without a corresponding valid transition existing for the follow-on action (`withdrawMinipoolFunds`), permanently trapping principal. Here, `_cancelFromDest`'s `_filled` write is the analogous "finish" state that forecloses the only alternate recovery route (`_cancelFromSource`) while depending entirely on a single, untimeoutable cross-chain message for actual fund release.

### Impact Explanation
If the `RefundEscrow` message fails to be delivered or is permanently rejected by `onAccept` (relayer rotated via `setRelayer`, deployment registry mismatch, or the relayer/indexer infrastructure simply never submits/finalizes the proof), the user's escrowed input tokens on the source chain become permanently unrecoverable:
- `fillOrder`/`cancelOrder` on the destination revert with `Filled()`.
- `_cancelFromSource` on the source chain, the only alternate recovery mechanism, is defeated because the destination's `_filled` slot is already non-empty, so `onGetResponse` reverts with `Filled()`.
- There is no timeout-based fallback (`_post` uses `timeout: 0`), so the message can neither be redelivered through a timeout-refund path nor cancelled/retried.

This is a permanent freezing of user funds (the escrowed `order.inputs` and `order.fees`), which is the same class of impact judged Medium/High severity in the original GoGoPool finding.

### Likelihood Explanation
This requires an "unhappy path" for message delivery rather than a malicious actor exploiting business logic directly, similar to how the original finding depended on the multisig/Rialto operator making an admin-level mistake. Here the trigger is any real-world relayer/delivery failure for the specific `RefundEscrow` message (relayer downtime, `setRelayer` rotation mid-flight, misconfigured/missing peer `Deployment` registration, or a permanently rejected `_authenticate` check) — none of which require a malicious actor, only an operational failure or misconfiguration, which is plausible in a live cross-chain messaging system. Given the destination-side state is written unconditionally before delivery is confirmed, likelihood is non-trivial for a protocol that depends on relayer liveness and correct peer configuration across its lifetime.

### Recommendation
Do not commit an irreversible `_filled` state on the destination chain before the corresponding cross-chain refund is durably confirmed. Options:
1. Attach a non-zero `timeout` to the `RefundEscrow` `DispatchPost` and implement a `onPostRequestTimeoutCallback` that reverts the destination-side `_filled` mark (or otherwise unblocks an alternate cancellation/fill path) if the message times out undelivered.
2. Allow `_cancelFromSource`'s `onGetResponse` to distinguish between "filled by a solver" and "cancelled-from-destination-but-refund-pending" states (e.g., by encoding the beneficiary/marker differently), and provide a source-chain recovery path when the destination shows a pending-refund marker rather than a genuine fill.
3. At minimum, add operational safeguards (e.g., a governance-gated emergency withdrawal path) that can restore `_orders[commitment][token]` funds to `order.user` on the source chain if the paired `RefundEscrow` message can be proven un-deliverable.

### Proof of Concept
1. User places a cross-chain order via `placeOrder` on the source chain, escrowing input tokens; `_orders[commitment][token]` is credited.
2. Order expires without being filled. User (or, after expiry, anyone) calls `cancelOrder` on the destination chain, routing to `_cancelFromDest`.
3. `_cancelFromDest` sets `_filled[commitment] = order.user` on the destination chain and dispatches a `RefundEscrow` POST with `timeout: 0` toward the source chain [1](#0-0) .
4. Simulate delivery failure: the relayer is rotated via `setRelayer` before the message is delivered, or the relayer simply never submits the proof to the source-chain host, so `onAccept` is never successfully invoked (or reverts on `_checkRelayer`/`_authenticate`) [3](#0-2) .
5. User attempts `_cancelFromSource` from the source chain to recover the escrow directly. The dispatched `DispatchGet` reads the destination `_filled` slot for the commitment, finds it non-empty (set in step 3), and `onGetResponse` reverts with `Filled()` [5](#0-4) .
6. No other function can release `_orders[commitment][token]` on the source chain — the escrowed input tokens and `order.fees` are permanently stuck.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
