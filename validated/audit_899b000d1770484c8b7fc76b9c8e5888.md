### Title
Webhook HMAC verification covers only the raw body, not the `shop`/`topic` identity fields it authorizes — enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/utils/hmac_validator.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so `Utils::HmacValidator.validate` authenticates nothing but the JSON payload bytes. The `shop`, `topic`, `api_version`, and `webhook_id` fields — which are read straight from attacker-controllable HTTP headers and then handed to the app's webhook handler as trusted tenant-routing identifiers — are never bound by the signature. Because the signing secret (`Context.api_secret_key`) is a single app-wide secret shared across every shop that installs the app, any tenant that has legitimately installed the app can capture a valid `(body, hmac)` pair from their own store and replay it against the public webhook endpoint with the `shop` header rewritten to a victim shop, producing a request that passes `HmacValidator.validate` while being attributed to the wrong tenant.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

Only `@raw_body` is signed. `shop`, `topic`, `webhook_id`, and `api_version` are parsed from headers with no cryptographic tie to the HMAC: [2](#0-1) 

`Registry.process` performs exactly one check — the HMAC over the body — before dispatching the handler with the unauthenticated `shop` value: [3](#0-2) 

`HmacValidator.validate` signs with the single, app-wide `Context.api_secret_key` (falling back to `old_api_secret_key`), which is identical for every shop that has the app installed — there is no per-shop secret: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body ∥ shop ∥ topic)`, i.e. the tenant identity acted upon (`shop`) should be covered by the same signature that authenticates the request. Instead the binding actually enforced is `hmac == HMAC(secret, body)`, with `shop` supplied out-of-band via an unsigned header. This is precisely the "field acted on but not covered by the HMAC" break: any party who can produce a valid `(body, hmac)` pair — which is trivial for a self-installed shop, since the secret is shared app-wide — can attach that pair to an arbitrary `x-shopify-shop-domain` header and have it accepted as if it came from that shop.

The gem's own documentation confirms `shop` is treated as an authenticated, trusted routing key by downstream handler code: [5](#0-4) 

### Impact Explanation
This is a cross-tenant access vulnerability: a malicious merchant who has installed the app on their own store can forge webhook deliveries that the app will process as belonging to any other merchant using the same app (since the shop domain is not part of the signed material and the signing secret is shared across all installs). Depending on the handler's logic (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`), this can lead to injection of fabricated business data into a victim tenant's records, spurious deprovisioning actions, or GDPR-relevant data-request mishandling — all attributed to a shop the attacker does not control. This matches the "Critical – cross-tenant access" impact category.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on an attacker-controlled shop (a normal, permitted action for any Shopify merchant/developer), (2) triggering an event to receive one legitimate `(raw_body, hmac)` pair from the app's own webhook delivery, and (3) POSTing that exact body/HMAC to the app's public webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to the victim's domain. No secrets, tokens, or privileged access to the victim are required, making this highly reachable by any unprivileged internet user who can install the target app.

### Recommendation
Do not trust the `shop` (and ideally `topic`/`webhook_id`) header values purely on the strength of a body-only HMAC. Options:
- Require callers to independently verify that `request.shop` corresponds to a shop with an active, matching webhook registration/session before dispatching to a handler, rather than trusting the header as authoritative.
- If feasible, extend `to_signable_string` to incorporate the header-derived identity fields so the signature binds `shop`/`topic` to the body (note: this requires coordination with Shopify's actual signing scheme on the server side, since Shopify itself signs only the body — so at minimum the library should document that `shop` is *not* authenticated by the HMAC and must be cross-checked against known/registered shops by the caller).
- Add explicit documentation/guardrails in `docs/usage/webhooks.md` warning integrators that `request.shop` is unauthenticated and must be validated against the caller's own tenant registry before use.

### Proof of Concept
```ruby
# Step 1: Attacker installs the target app on their own shop "attacker.myshopify.com"
# and triggers any webhook (e.g. orders/create) to capture a legitimate delivery:
#   raw_body   = '{"id":1,"note":"legit payload from attacker-owned shop"}'
#   hmac_bytes = OpenSSL::HMAC.digest("sha256", Context.api_secret_key, raw_body)  # same secret for ALL shops
#   valid_hmac_b64 = Base64.encode64(hmac_bytes)

# Step 2: Attacker crafts a forged webhook request against the SAME app's public endpoint,
# reusing body + hmac exactly, but swapping the shop-domain header to the victim's shop.
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => valid_hmac_b64,          # unchanged, still valid for raw_body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # spoofed, NOT covered by HMAC
  "x-shopify-webhook-id"   => "forged-id",
  "x-shopify-api-version"  => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Step 3: The gem accepts it, because HmacValidator only checks raw_body:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create",
#                                              shop: "victim-shop.myshopify.com",  # attacker-controlled
#                                              body: JSON.parse(raw_body),
#                                              ...))
```
The app's handler executes believing the payload legitimately originated from `victim-shop.myshopify.com`, even though only the attacker's own body/HMAC pair was reused and the tenant identity was fully attacker-controlled.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
