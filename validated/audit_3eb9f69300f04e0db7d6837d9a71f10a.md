### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, but the HMAC only signs the raw JSON body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values, which are trusted downstream as the identity of the tenant and event, are read from unauthenticated headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns `@raw_body` only [4](#0-3) . `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding to the HMAC [5](#0-4) . `Utils::HmacValidator.validate_signature` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` header via `OpenSSL.secure_compare`, so it never touches those other headers [3](#0-2) . `Registry.process` raises only if the HMAC check fails, then builds `WebhookMetadata` directly from `request.topic`, `request.shop`, `request.webhook_id`, and `request.api_version` and passes it to the registered handler [1](#0-0) .

The identity binding this breaks is: `hmac-verified(body)` should imply `hmac-verified(shop, topic, webhook_id, body)`, but in this gem only the body is bound to the signature — the shop/topic/webhook_id are trusted unauthenticated.

Because any Shopify shop that installs a public app receives genuinely HMAC-signed webhook deliveries (signed with the app's `client_secret`) for its own store, an unprivileged internet user can install the target app on their own store, capture a legitimate `(raw_body, hmac)` pair from a real webhook delivery, and replay that exact body+HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header with a victim shop's domain or a different topic/id. `HmacValidator.validate` still returns `true` because it only checks the (unmodified) body against the HMAC, so `Registry.process` will hand the handler a `WebhookMetadata` claiming to originate from the victim shop / a different topic.

### Impact Explanation
This crosses a tenant boundary: the host application's webhook handler — which typically looks up or writes per-shop records keyed by `data.shop` — is fed a shop identity that was never authenticated by Shopify for that event. This can lead to cross-tenant data confusion/writes (e.g., an attacker's own store's order data being attributed to and merged into a victim shop's records) or forged mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`) being delivered under an arbitrary shop identity, since `Registry.process` does not treat these topics specially with respect to header trust.

### Likelihood Explanation
Exploitation requires only installing the target public app on an attacker-controlled Shopify store (or trial/dev store) to obtain one genuine `(body, hmac)` pair, then a single unauthenticated HTTP POST to the app's webhook endpoint with forged headers — no `api_secret_key`, access token, or privileged access to the victim account is needed.

### Recommendation
Include `shop-domain`, `topic`, `webhook-id`, and `api-version` in the signed/verified material (e.g., verify these header values against the delivery metadata Shopify makes available, or require the host application to independently confirm `shop` is one it has an active session/installation for) before trusting them, rather than relying on `HmacValidator` covering only the raw body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` and registers a webhook for topic `orders/create`.
2. Shopify delivers a legitimate webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `client_secret`), `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same body `B` and HMAC `H` to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` (and/or a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` and passes [6](#0-5) .
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` [7](#0-6) , causing the host app to act on attacker-supplied data as if it belongs to `victim.myshopify.com`.
