### Title
Governance can drain escrowed fee-token balance via `withdraw` and then swap `feeToken`, permanently freezing pending relayer rewards/timeout refunds and blocking their delivery - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.updateHostParams`/`updateHostParamsInternal` allows cross-chain governance (via the `hostManager`) to change the protocol `feeToken`, gated only by a check that the *current on-chain balance* of the old fee token is zero (`CannotChangeFeeTong` check at `evm/src/core/EvmHost.sol:617-621`). This mirrors exactly the `PaymentSettler::setStablecoin` bug class: the check treats "balance == 0" as proof that no obligations remain, but the contract's `withdraw()` function (also gated only by `hostManager`) can freely sweep the *entire* balance of any token — including fees that are escrowed against specific outstanding (undelivered/un-timed-out) requests — with no accounting against those obligations.

### Finding Description
Every outgoing `dispatch(DispatchPost)` pulls `post.fee` of the current `feeToken()` into the host contract and records only the amount (not the token address) in `_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee})` (`evm/src/core/EvmHost.sol:930-948`). That escrowed balance sits in the contract until the request is delivered (rewarding a relayer) or times out (refunding the payer).

`withdraw()` (`evm/src/core/EvmHost.sol:651-660`) is restricted only to `_hostParams.hostManager` and transfers an arbitrary `amount` of an arbitrary `params.token` to a beneficiary with no accounting for how much of that balance is "free" protocol revenue versus fees escrowed for still-pending requests. Governance can therefore legitimately withdraw the entire balance of the current `feeToken`, including money that backs pending commitments.

`updateHostParamsInternal` (`evm/src/core/EvmHost.sol:617-621`) then permits swapping to a new `feeToken` as soon as `IERC20(oldFeeToken).balanceOf(address(this)) == 0` — a condition trivially satisfiable by first calling `withdraw()`, even though outstanding `_requestCommitments`/`FeeMetadata` entries denominated in the old token still exist.

Once the swap occurs, later processing of those still-pending messages pays out in the **new** `feeToken()`, not the token the fee was actually escrowed in:
- `dispatchIncoming(GetResponse, relayer)` rewards the relayer with `IERC20(feeToken()).safeTransfer(relayer, fee)` (`evm/src/core/EvmHost.sol:841-845`).
- `dispatchTimeOut(GetRequestTimeout, ...)` and `dispatchTimeOut(PostRequestTimeout, ...)` refund the original sender with `IERC20(feeToken()).safeTransfer(meta.sender, meta.fee)` (`evm/src/core/EvmHost.sol:872-876`, `evm/src/core/EvmHost.sol:901-905`).

None of these three functions wrap the reward/refund transfer in a try/catch — unlike `dispatchIncoming(PostRequest,...)`, which tolerates a failed downstream call by deleting the receipt and returning. If the contract does not yet hold enough of the *new* `feeToken` (which is likely immediately after a token swap, since only newly-dispatched requests fund it), `safeTransfer` reverts and the entire `dispatchIncoming`/`dispatchTimeOut` call reverts, rolling back the relayer/timeout delivery attempt (including replay-protection state writes for that specific commitment).

### Impact Explanation
This produces the same two-fold impact as the original report:
1. Funds escrowed in the old fee token for outstanding requests are trapped/misappropriated — governance's legitimate `withdraw` sweeps them out under the guise of protocol revenue, and there is no path to reimburse the specific pending commitment in its original token.
2. Relayers and payers are unable to receive their rewards/refunds: any `GetResponse` delivery or `PostRequestTimeout`/`GetRequestTimeout` processing for a request dispatched before the swap will revert until the contract happens to accumulate sufficient balance of the new token, effectively blocking that message route from being delivered. This satisfies the "route unable to deliver messages" impact criterion.

Because this can freeze/misdirect funds and durably block delivery of legitimate ISMP messages, the severity is Medium (High impact, contingent on the low-likelihood but entirely legitimate governance action of migrating the fee token, exactly as flagged in the original report as a realistic operational necessity — e.g., a de-pegging stablecoin).

### Likelihood Explanation
Fee-token migration is an explicitly supported, documented capability (`evm/rust/src/host_params.rs:93-95` even comments "It's important that before changing this parameter, that all funds have been drained from the previous feeToken" — acknowledging the exact scenario but only defending against a naive "any balance" check, not against escrowed-vs-free accounting). Any live host with outstanding, undelivered requests or unprocessed timeouts at the moment of a fee-token rotation will encounter this. Given that fee-token changes are a normal, expected governance operation (analogous to `setStablecoin` in the original report) and pending requests are a routine/permanent state of the protocol (not corner-case), likelihood is non-trivial, though it requires the specific ordering of withdraw-then-swap-then-late-delivery, which is a foreseeable but not everyday occurrence.

### Recommendation
Track escrowed fee-token amounts as a reserved balance (e.g., a running sum of all live `FeeMetadata.fee`) and have `withdraw()` refuse to transfer below that reserved amount for the active `feeToken`. Alternatively, require `updateHostParamsInternal`'s `CannotChangeFeeToken` check to compare balance against total outstanding escrowed fees rather than zero, or store the fee token address per `FeeMetadata` entry so historic commitments are always settled in the token they were originally escrowed in, independent of subsequent `feeToken` rotations. Additionally, wrap the reward/refund transfers in `dispatchIncoming(GetResponse,...)` and both `dispatchTimeOut` overloads in a non-reverting pattern (mirroring the `PostRequest` delivery path) so a payout failure degrades to a retryable state rather than reverting the whole delivery.

### Proof of Concept
Conceptual sequence (mirrors the report's PoC pattern), all through in-scope, unprivileged-reachable paths:
1. Any user dispatches a `PostRequest`/`GetRequest` via `EvmHost.dispatch`, paying `fee` in `feeToken` A; `_requestCommitments[commitment] = FeeMetadata({sender: payer, fee: fee})` is recorded and `fee` of token A now sits in the host (`evm/src/core/EvmHost.sol:930-948`).
2. Before that request is delivered/timed out, cross-chain governance dispatches a `Withdraw` action through `HostManager.onAccept` → `EvmHost.withdraw` (`evm/src/core/EvmHost.sol:651-660`), pulling the full balance of token A (including the escrowed `fee`) to the treasury.
3. Governance dispatches a `SetHostParam` action (`HostManager.onAccept` → `EvmHost.updateHostParams` → `updateHostParamsInternal`, `evm/src/core/EvmHost.sol:573-621`) setting `feeToken = B`. The `CannotChangeFeeToken` check passes because token A's balance is now 0.
4. The relayer later submits the GET response proof (or the request times out) for the request from step 1. `dispatchIncoming(GetResponse,...)` or `dispatchTimeOut(...)` attempts `IERC20(feeToken()).safeTransfer(..., fee)` using token B (`evm/src/core/EvmHost.sol:844`, `874`, `903`). If the host's token-B balance is insufficient, this reverts, and the delivery/timeout for that commitment cannot be finalized — the escrowed token-A fee is unrecoverable by the sender/relayer, and message delivery for that request is blocked.
