### Title
Webhook HMAC only authenticates the request body, not the `shop-domain` header, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers and then handed to the application's webhook handler as trusted identifiers. Any party who can obtain one valid `(raw_body, hmac)` pair for a shop can replay it with a forged `shop-domain` header, and the gem will report the request as HMAC-valid while attributing the payload to an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are parsed directly from the (attacker-controlled on replay) HTTP headers: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which internally HMACs `to_signable_string` (i.e. only the body) with `Context.api_secret_key`, then forwards `request.shop` unmodified to the registered handler as the authoritative tenant identifier: [3](#0-2) [4](#0-3) 

The binding the gem is supposed to enforce is: `shop_the_HMAC_authenticates == shop_the_handler_trusts`. In reality, the HMAC only authenticates `raw_body`, so the equality actually enforced is `hmac(raw_body) == hmac(raw_body)`, and `shop` (along with `topic`/`webhook_id`) is never bound to that signature at all. Because Shopify uses a single `api_secret_key` per app shared across every merchant installation, a valid `(raw_body, hmac)` pair captured from one shop's genuine webhook delivery remains valid forever and for any shop — the signature carries no shop-scoping.

### Impact Explanation
An attacker who operates (or has installed) the app on their own shop receives genuine Shopify-signed webhook deliveries at their endpoint, giving them a valid `raw_body` + `x-shopify-hmac-sha256` pair. By resending that exact body/HMAC pair to the app's public webhook endpoint with the `x-shopify-shop-domain` header changed to a victim merchant's domain, `Utils::HmacValidator.validate` still returns `true` (since the header is not part of the signed content), and `Registry.process` invokes the app's handler with `WebhookMetadata#shop` set to the victim shop. Any host application that uses this `shop` value to select/create/update per-tenant records (the documented and expected use of `WebhookMetadata`) will process the attacker's forged data under the victim's tenant identity — a cross-tenant data-integrity/access violation attributable to this gem's `Registry`/`Request` classes, not to host misuse.

### Likelihood Explanation
Likelihood is realistic: any unprivileged actor able to install the app on any shop (including a shop they control) automatically receives valid signed webhook traffic they can capture, and the app's webhook endpoint is by definition internet-reachable and unauthenticated aside from the HMAC. No possession of `api_secret_key` or any privileged credential is required — the attack only needs one legitimately delivered webhook and the ability to POST to the endpoint with a modified header.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-signable content (or otherwise cryptographically bind them to the signed payload), and validate that the shop the HMAC is computed for actually matches the one in the header before constructing `WebhookMetadata`, rather than trusting the raw header value unconditionally.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any subscribed event, receiving a genuine webhook POST with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the shared `api_secret_key`).
2. Attacker replays the exact same request to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` computes `Utils::HmacValidator.validate(request)` over `request.to_signable_string == B`, which matches `H`, so validation passes.
4. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-supplied data as belonging to `victim-shop.myshopify.com`.
