### Title
Permissionless `force_socialize_bad_debt` bypasses the dust cap and lets any caller seize an insolvent account's residual collateral and write down supplier shares - (File: contracts/controller/src/positions/liquidation/mod.rs)

### Summary
The incident class (attackers draining a wallet without the owner's authorization) maps onto the controller's bad-debt path: `process_force_socialize_bad_debt` is callable by any unprivileged address even though its gate is documented as owner-only. Anyone can trigger full bad-debt socialization on any insolvent account regardless of how much collateral it still holds, burning the owner's remaining collateral and writing down the supply index so all suppliers absorb the loss — losses that a normal liquidation would have partially recovered via liquidator repayments.

### Finding Description
`socialize_bad_debt` defines two admission gates: `DustCapped` (permissionless, collateral at/below dust) and `InsolventOnly` (documented "Owner-only … with no cap on the collateral left behind"). `process_clean_bad_debt` uses `DustCapped`, correctly restricting permissionless cleanup to dust-sized collateral. But `process_force_socialize_bad_debt` implements `InsolventOnly` with **no authorization at all** — its only check is `require_not_flash_loaning`:

```rust
/// Socializes debt exceeding collateral without a dust cap, outside flash loans.
pub(crate) fn process_force_socialize_bad_debt(env: &Env, account_id: u64) {
    validation::require_not_flash_loaning(env);
    socialize_bad_debt(env, account_id, BadDebtGate::InsolventOnly);
}
```

Unlike `process_clean_bad_debt` (which takes a `caller` and calls `caller.require_auth()` at mod.rs:197) and unlike every state-changing path (`require_authorized_caller` in validation.rs:13, `require_owner_or_delegate` in account.rs:130, `require_account_owner` in account.rs:143), this function takes only `account_id` — there is no caller, no `require_auth`, and no owner/delegate check. The "Owner-only" gate documented at lines 206-208 is enforced nowhere. The function is listed in `scripts/permissionless_entrypoints.txt`, confirming it is exposed as a public, unauthenticated entrypoint.

An attacker submits `force_socialize_bad_debt(account_id)` on any account where `total_debt > total_collateral`. `execute_bad_debt_cleanup` then removes the account's collateral and writes down the market's supply index, socializing the entire shortfall across all suppliers.

### Impact Explanation
- **Theft of user funds / protocol insolvency amplification**: an insolvent account holding collateral far above the dust threshold should go through `liquidate`, where a liquidator repays real debt tokens into the pool (`apply_liquidation_repayments` performs measured transfers) before seizing collateral. Force-socialization skips all repayment: suppliers absorb the full `debt` via the supply-index write-down instead of `debt − repaid`, and the account owner's residual collateral is destroyed rather than auctioned with a liquidation bonus. The attacker needs only to front-run the natural liquidation flow — no capital required — to convert a recoverable loss into a permanent protocol write-down.
- The attacker can combine this with their own supply positions timing, or simply grief every insolvent account the moment its health factor crosses 1, denying liquidators the ability to recycle debt and guaranteeing the worst-case outcome for suppliers and the account owner.

### Likelihood Explanation
- Reachable by a single unprivileged address with one call: `controller.force_socialize_bad_debt(account_id)`; no flash loan, no capital, no collusion.
- The precondition (`total_debt > total_collateral`) arises routinely in volatile markets — it is exactly the state liquidators race to capture, so the window is constantly being created.
- The divergence between the documented owner-only gate and the implemented zero-auth gate indicates an authorization oversight, not an intentional ADR (no runbook or comment documents permissionless force-socialize; the runbook in `docs/reference/runbooks/` treats it as an operator action).

### Recommendation
Enforce the documented gate: accept `caller: Address` (or read the account owner from `storage::account_owner`), call `caller.require_auth()`, and require `caller` to be the account owner via `require_account_owner`/`require_owner_or_delegate` before invoking `socialize_bad_debt(env, account_id, BadDebtGate::InsolventOnly)`. Alternatively, if keeper operation is intended, restrict it to a registered position manager and update the comment. Remove it from the permissionless entrypoint set until authorized.

### Proof of Concept
```rust
// Attacker EOA observes account A with total_debt > total_collateral
// but collateral far above the dust threshold (e.g., price just moved).
// Instead of repaying debt via liquidate() — which would inject tokens
// into the pool — the attacker calls:

client.force_socialize_bad_debt(&account_id_of_A);

// process_force_socialize_bad_debt:
//   - require_not_flash_loaning passes (no flash active)
//   - socialize_bad_debt(InsolventOnly): totals.total_debt > totals.total_collateral -> admits
//   - execute_bad_debt_cleanup: A's collateral removed, supply index written down
// Result: suppliers absorb full bad debt; no liquidator repayment ever arrives;
// A's residual collateral is seized without any authorization from A's owner.
```

Caveat: I could not fully read `contracts/controller/src/lib.rs` (entrypoint wrappers) or `bad_debt::execute_bad_debt_cleanup` internals within the available iterations. The finding rests on the zero-auth signature of `process_force_socialize_bad_debt`, its listing in `scripts/permissionless_entrypoints.txt`, and the explicit "Owner-only" documentation of `BadDebtGate::InsolventOnly` at mod.rs:206-208 — all of which support that this path is unintended for unprivileged callers.
