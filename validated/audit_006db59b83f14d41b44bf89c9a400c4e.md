## Finding

### Title
Webhook `shop` domain is trusted for tenant identity but excluded from the HMAC signature - cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC computed **only over the raw request body**, then hands the caller-supplied `shop` header straight through as the tenant identity, without that header ever being covered by the signature.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes the HMAC exclusively over `verifiable_query.to_signable_string` (i.e. the body) and compares it against the `hmac` header: [2](#0-1) 

`Registry.process` gates on that body-only HMAC, then immediately trusts `request.shop` (parsed straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header) as the tenant identifier passed to the handler: [3](#0-2) 

The `shop` header is read with no cross-check against the signed content: [4](#0-3) 

Since Shopify apps share a single `api_secret_key` across every installed shop, this breaks the intended identity binding:

`HMAC(secret, body)` should authenticate `(shop, body)` together, but it only authenticates `body`. Formally: `valid(hmac, body) == true` for **any** `shop` value, because `shop ∉ to_signable_string`.

An attacker who controls one legitimate tenant (installs the app on their own store and thus legitimately receives real, validly-signed webhook payloads for that shop) can:
1. Capture a genuine webhook `(body, hmac)` pair delivered to their own shop.
2. Replay the identical `body`/`hmac` to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim shop's domain.
3. `HmacValidator.validate` still succeeds (it never inspected `shop`), so `Registry.process` calls the handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker-controlled-but-validly-signed-body>, ...)`.

Any host application that uses `WebhookMetadata#shop` to select/update per-tenant data (the documented and expected use, per `docs/usage/webhooks.md` patterns) will process attacker-controlled data under the victim's tenant identity.

### Impact Explanation
This is a cross-tenant identity binding failure: the value used to select the tenant (`shop`) is never included in the value that is cryptographically authenticated (`body`). It allows a malicious but validly-onboarded merchant/app-installer to inject spoofed webhook data attributed to another merchant's shop, i.e., cross-tenant access/data injection into whatever store or workflow the host app keys off `WebhookMetadata#shop`. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any actor able to install the app on their own shop (a normal, low-privilege action for any Shopify merchant) can obtain a validly-HMAC-signed body/hmac pair for arbitrary content they control (by triggering webhook events on their own store, e.g. creating an order/product with attacker-chosen fields), then replay it against the app's public webhook endpoint with a spoofed `shop-domain` header. No secrets, tokens, or privileged access are required beyond ordinary app installation, and the library performs no mitigation.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the authenticated material, or otherwise independently verify that the authenticated body's origin shop matches the `shop` header before it is exposed to the handler — e.g., cross-check `shop` against a known/installed-shop registry the app maintains, rather than trusting the header as-is. At minimum, document that `WebhookMetadata#shop` is not itself covered by the HMAC and must not be trusted for tenant-partitioning decisions without additional verification.

### Proof of Concept
```ruby
# Attacker owns "attacker.myshopify.com" and has genuinely installed the app,
# so they receive real, validly HMAC-signed webhooks for their own shop.
genuine_body = '{"id": 1, "note": "malicious payload"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, genuine_body)

# Attacker replays the SAME body+hmac but swaps the shop-domain header to the victim's shop.
spoofed_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # never covered by the HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: genuine_body, headers: spoofed_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate succeeds (body-only check), handler receives
#    WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker-controlled JSON)
```
