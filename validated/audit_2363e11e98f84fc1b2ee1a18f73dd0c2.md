## Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unauthenticated headers while only the raw body is HMAC-verified, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts a `Webhooks::Request` and validates it solely by HMAC-verifying the raw request body. The `shop`, `topic`, `webhook_id`, and `api_version` values that are then handed to the app's webhook handler as trusted, request-scoped identity fields come straight from HTTP headers that are never included in the signed data. Because every shop that installs a given app shares the same `client_secret`/`api_secret_key`, any merchant who legitimately installs the app can capture a genuinely-signed webhook body and replay it with a different `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header to make the receiving app process it as if it originated from a different, unrelated shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

and `HmacValidator.validate` computes/compares the signature exclusively over that signable string: [2](#0-1) 

`Registry.process` uses this same-body-only HMAC check as the sole authenticity gate, then constructs the metadata passed to the app's handler directly from unauthenticated headers (`request.topic`, `request.shop`, `request.webhook_id`, `request.api_version`): [3](#0-2) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors themselves are simple header readers with no cryptographic binding: [4](#0-3) 

This breaks the identity binding `shop_authenticated == shop_acted_on`: the HMAC only proves "this body byte-string was signed with the app's shared secret at some point," not "this body was signed for this shop/topic." Since the same `api_secret_key` is shared across every shop that installs the app, a legitimate-but-malicious merchant (Shop A) can:
1. Register the app on their own store and receive a genuinely Shopify-signed webhook (valid `hmac-sha256` over some raw body, e.g., an `orders/create` payload).
2. Replay that exact raw body and HMAC value to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header with the domain of a different, unrelated tenant (Shop B), and/or alter the topic header.
3. `HmacValidator.validate` passes because the body/HMAC pair is genuinely valid, and `Registry.process` dispatches the handler with `shop: "shop-b.myshopify.com"` even though the payload was never signed for or generated by Shop B.

This is analogous to the report's "signature doesn't bind to wave/contract-specific context" bug: here the webhook signature doesn't bind to the shop or topic it's claimed to belong to.

### Impact Explanation
This allows cross-tenant confusion: an app that keys any per-shop side effects (data writes, notifications, billing triggers, cache invalidation, session lookups, etc.) off `WebhookMetadata#shop` from `Registry.process` can be made to attribute attacker-controlled payload contents to a victim shop it does not belong to, without the attacker ever needing the app's `api_secret_key`, an access token, or any credential belonging to the victim. This matches the "Critical - cross-tenant access" impact bucket, since it crosses a tenant/shop boundary using only the capability of being any legitimate installer of the app.

### Likelihood Explanation
Any merchant who installs the target app can trivially capture a validly-HMAC'd webhook body sent to their own endpoint (e.g., via a proxy or simply reading their own server logs), then replay it with modified `Shop-Domain`/`Topic` headers to the same publicly reachable webhook endpoint. No secret material, token theft, or privileged access is required beyond ordinary app installation — this is the "unprivileged internet user" class explicitly in scope.

### Recommendation
Include the header fields that the handler treats as authoritative — `shop`, `topic`, `webhook_id`, and `api_version` — as part of the HMAC-signed material (or otherwise bind them cryptographically), analogous to including `address(this)`/context identifiers in the original bug's signature. Since these headers are Shopify-controlled but the signature scheme in this gem does not currently canonicalize them into `to_signable_string`, at minimum the gem should document/enforce that consuming apps must independently trust the `shop`/`topic` values only insofar as they trust the delivery channel per-shop (e.g., correlate against previously registered webhook subscriptions for that specific shop/topic pair) rather than treating a body-only HMAC pass as full authentication of the shop/topic tuple.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop and receives a real webhook,
# e.g. for topic "orders/create":
raw_body = '{"id": 1, "note": "malicious payload"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), shared_api_secret_key, raw_body)

# Attacker replays the same (raw_body, hmac) pair but swaps the shop-domain header
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # <- not the attacker's own shop
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (it only checks raw_body),
#    and the handler is invoked with shop: "victim-shop.myshopify.com",
#    attributing attacker-controlled data to a shop the attacker does not own.
``` [5](#0-4)
