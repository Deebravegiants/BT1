## Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

## Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw webhook body, while `#shop` (the tenant identity used by the handler) is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header. `Registry.process` validates the HMAC over the body only, then passes the header-derived `shop` into the handler untouched, breaking the binding `hmac_signed_bytes == identity_bytes`.

## Finding Description
`Webhooks::Request` implements `Utils::VerifiableQuery` by defining: [1](#0-0) 
which signs only `@raw_body`. The `shop` accessor is derived purely from an HTTP header that is never fed into the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` that is handed to the app's handler: [3](#0-2) 

`WebhookMetadata#shop` is a plain `String` field with no further verification: [4](#0-3) 

Because a single app-level `client_secret` (`Context.api_secret_key`) is shared across every shop that installs the app, `HmacValidator.validate` only proves the body+secret pair is authentic for *some* shop of this app — not which shop: [5](#0-4) 

This is the same class of bug as the report's "field acted on but not covered by the HMAC": the identity binding that should hold is
`hmac_valid(raw_body, secret) == true` implies `shop == the shop that owns raw_body`,
but the code only proves `hmac_valid(raw_body, secret) == true`; `shop` is an independent, attacker-controlled header. A merchant who has legitimately installed the app on their own store (`attacker.myshopify.com`) receives genuine, correctly-signed webhook deliveries from Shopify for their own shop. They can replay that exact `raw_body` (signature is unchanged since it doesn't cover the shop) to the app's webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop (`victim.myshopify.com`). `HmacValidator.validate` still succeeds because it only checks `raw_body`, and `Registry.process` forwards `shop: "victim.myshopify.com"` to the handler.

## Impact Explanation
Any host application that uses `WebhookMetadata#shop` to look up per-tenant sessions/data (the documented and expected usage pattern shown in `docs/usage/webhooks.md`) can be tricked into applying attacker-supplied webhook data (order/customer/app-uninstall events, etc.) to a different, victim tenant's records — a cross-tenant data-integrity/access issue that satisfies the "cross-tenant access" criterion.

## Likelihood Explanation
Any merchant who can install the app on their own shop (a normal, unprivileged action) can capture one legitimately signed webhook body and freely resend it with a different `shop` header — no access token, `client_secret`, or privileged account is required, only the ability to observe traffic to/from their own installed webhook endpoint and replay an HTTP request with a modified header, which is trivial for an unprivileged internet user controlling their own install.

## Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop domain to the signed payload before trusting it, so `HmacValidator.validate` cannot pass for a `raw_body`/`shop` pair that Shopify never actually issued together.

## Proof of Concept
1. App is installed on `attacker.myshopify.com`; attacker receives a genuine webhook POST with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, and some `raw_body`.
2. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `raw_body` — validation passes. [6](#0-5) 
4. The handler receives `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: <attacker's data>, ...)` and, following the documented pattern of looking up the victim's session/store by `shop`, applies attacker-controlled webhook data to the victim tenant.
