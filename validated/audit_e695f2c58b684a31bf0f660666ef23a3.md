### Title
POA Bridge matches withdrawal status by asset only, misreporting completion status/tx hash when a batch contains multiple withdrawals of the same token - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status of a specific `WithdrawalIdentifier` (identified by `index` within a batch) by calling `findMatchingWithdrawal`, which selects the **first** entry in the POA API's `withdrawals` array whose `near_token_id` matches the requested `assetId` [1](#0-0) . The matcher ignores `index`, `destinationAddress`, and `amount` entirely [2](#0-1) .

### Finding Description
The SDK explicitly supports batch withdrawals from a single intent transaction, where `withdrawalParams` is an array and each entry gets a per-bridge sequential `index` via `createWithdrawalIdentifiers` [3](#0-2) . When two or more withdrawals in that batch use the POA bridge and share the same underlying asset (e.g., two BTC withdrawals to different destination addresses/amounts within one intent), each gets its own `WithdrawalIdentifier` with a distinct `index`, but `describeWithdrawal` never uses `index` to disambiguate — it only checks `assetId` via `Array.prototype.find`, which always returns the **first** array element that matches, regardless of which `index` is being queried [4](#0-3) .

This is a known, documented limitation in the code itself: "NOTE: Currently only matches by assetId. This means multiple withdrawals of the same token in a single transaction are not supported" [5](#0-4) . The identical pattern (and identical caveat) exists in `waitForWithdrawalCompletion` in internal-utils [6](#0-5) .

Consequence: if withdrawal A (index 0, destination X, amount 100) and withdrawal B (index 1, destination Y, amount 200), both `nep141:btc.omft.near`, are in the same intent, `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` both resolve to the SAME matched POA record (whichever the API lists first). If A actually failed on-chain (e.g., REFUNDED) while B completed, the caller polling for A's status via `watchWithdrawal`/`createWithdrawalCompletionPromises` will incorrectly receive B's `COMPLETED` status and B's `transfer_tx_hash`, and vice versa for B if A is listed first — the reported status/tx hash for a given `WithdrawalIdentifier` does not correspond to that identifier's actual on-chain outcome. This directly breaks the "status reported must equal the on-chain outcome" equality called out in scope.

### Impact Explanation
This falls into the "status or hash misreport making an integrator credit or refund twice" (High) category: an integrator building on `createWithdrawalCompletionPromises`/`watchWithdrawal` to persist per-withdrawal completion state (as illustrated in the SDK's own RFC docs, e.g. `saveSuccess(index, tx)` keyed by index) [7](#0-6)  would record the wrong `txHash` against the wrong logical withdrawal, or mark a failed withdrawal as completed (masking a stuck/failed transfer) while the truly-completed withdrawal is left unresolved/misattributed. This can cause an integrator to release funds, mark an invoice paid, or refund based on the wrong on-chain event.

### Likelihood Explanation
This does not require a malicious actor — it is triggered purely by legitimate batch-withdrawal usage of the same asset to different destinations within one intent, which the SDK is documented to support (`docs/design/rfc-batch-withdrawal-granular-control.md` gives exactly this batching use case) [8](#0-7) . Any integrator batching two POA-bridge withdrawals of the same token (a realistic pattern, e.g. splitting a large BTC withdrawal into two UTXO-sized transfers, or paying two different BTC recipients in one intent) will hit this ambiguity whenever the two withdrawals settle with different outcomes.

### Recommendation
`findMatchingWithdrawal` should disambiguate by more than `assetId` — e.g., match remaining unclaimed withdrawals by `amount` and `destinationAddress` (and mark consumed entries so repeated calls for different indexes don't return the same record), or wait for the POA API to expose a stable per-withdrawal index/ID that can be threaded through `WithdrawalIdentifier.index`. At minimum, until proper matching is implemented, batch withdrawals of the same asset via POA bridge should be rejected or explicitly documented/guarded against at the SDK boundary (e.g., in `createWithdrawalIdentifiers` or `PoaBridge.supports`) so silent misattribution cannot occur.

### Proof of Concept
1. Submit one NEAR intent with two POA-bridge withdrawals of `nep141:btc.omft.near`: withdrawal #0 to address X for 100000 sats, withdrawal #1 to address Y for 200000 sats.
2. Call `sdk.createWithdrawalCompletionPromises({ withdrawalParams: [wd0, wd1], intentTx })`, which internally assigns `index: 0` and `index: 1` respectively via `createWithdrawalIdentifiers` [3](#0-2) .
3. Suppose the POA relayer's `getWithdrawalStatus` response lists withdrawal #0 (to X) as `REFUNDED` and withdrawal #1 (to Y) as `COMPLETED` with `transfer_tx_hash: "0xY"`, in that array order.
4. `PoaBridge.describeWithdrawal` for **both** `index:0` and `index:1` calls `findMatchingWithdrawal(response.withdrawals, "nep141:btc.omft.near")`, which returns the **first** array element (the `REFUNDED` one to X) for both queries [9](#0-8) .
5. The promise for withdrawal #1 (to Y, actually completed) rejects as `failed`/`REFUNDED` instead of resolving with `0xY`, while the promise for withdrawal #0 (actually refunded) is never distinguished — an integrator persisting per-index results (as shown in the SDK's own recovery example) records the wrong outcome for at least one of the two withdrawals.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

## Problem Statement

The SDK supports batch withdrawals - multiple tokens withdrawn in a single intent. For example: USDC to Solana + BTC refund to Bitcoin.

Current `waitForWithdrawalCompletion` has limitations:

1. **Waits for slowest** - Fast withdrawal (Solana ~2s) blocked by slow withdrawal (Bitcoin ~1hr)
2. **All-or-nothing failure** - If one withdrawal fails, entire function throws
3. **No progress visibility** - Can't know which withdrawals completed until all finish
