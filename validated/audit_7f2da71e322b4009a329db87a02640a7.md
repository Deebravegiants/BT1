### Title
`createWithdrawalIntents` trusts two independent fields of a caller-supplied `FeeEstimation` (`feeEstimation.amount` vs `underlyingFees.PoaBridge.relayerFee`) with no consistency check, letting a mismatched estimate overcharge the withdrawer - (File: `packages/intents-sdk/src/sdk.ts`, `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`IntentsSDK.createWithdrawalIntents` computes the displayed/deducted amount using `feeEstimation.amount`, but `PoaBridge.createWithdrawalIntents` independently re-adds a fee taken from `feeEstimation.underlyingFees.PoaBridge.relayerFee` when building the actual `ft_withdraw` intent amount. Nothing in the code path enforces `feeEstimation.amount === underlyingFees.PoaBridge.relayerFee`, so whenever both fields are not honestly generated from the same estimate, the total amount debited on-chain diverges from `withdrawalParams.amount` plus the displayed `feeEstimation.amount`.

### Finding Description
The claimed equality is:
`sum(debits in produced intents) == withdrawalParams.amount + (feeInclusive ? 0 : feeEstimation.amount)`

Trace:
- `IntentsSDK.createWithdrawalIntents` computes `actualAmount = feeInclusive ? amount - feeEstimation.amount : amount` [1](#0-0)  and forwards `actualAmount` (as `withdrawalParams.amount`) plus the full `feeEstimation` object to `bridge.createWithdrawalIntents` [2](#0-1) .
- `PoaBridge.createWithdrawalIntents` does not reuse `feeEstimation.amount` at all. Instead it extracts `relayerFee` from `feeEstimation.underlyingFees[RouteEnum.PoaBridge].relayerFee` via `getUnderlyingFee` and builds the on-chain withdraw intent with `amount: withdrawalParams.amount + relayerFee` [3](#0-2) .
- `getUnderlyingFee` simply reads whatever value exists at `feeEstimation.underlyingFees[route][feeKey]` with no cross-check against `feeEstimation.amount` [4](#0-3) .

When the SDK generates `feeEstimation` itself via `_estimateWithdrawalFee` → `PoaBridge.estimateWithdrawalFee`, the two fields are always set consistently: `amount: relayerFee` and `underlyingFees: { [PoaBridge]: { relayerFee } }` use the identical `relayerFee` variable [5](#0-4) . In that honest path the invariant holds: `actualAmount + relayerFee == amount` for `feeInclusive` withdrawals.

However, both `IntentsSDK.createWithdrawalIntents` and `IntentsSDK.signAndSendWithdrawalIntent` accept `feeEstimation: FeeEstimation` as a plain caller-supplied argument, not something the SDK derives or re-validates against the bridge's own quote [6](#0-5) [7](#0-6) . No code anywhere re-derives or asserts that `feeEstimation.amount === getUnderlyingFee(feeEstimation, PoaBridge, "relayerFee")`. If a caller (an integrator forwarding a counterparty-supplied fee object, or any code path that constructs `FeeEstimation` from an untrusted source) supplies a `feeEstimation` whose top-level `amount` differs from its `underlyingFees.PoaBridge.relayerFee`, the two independent computations diverge:

`debited = (amount - feeEstimation.amount) + underlyingFees.relayerFee`

This no longer equals `amount` whenever `feeEstimation.amount != underlyingFees.relayerFee`. E.g., `feeEstimation.amount = 100` (small, displayed fee, easily passes `FeeExceedsAmountError` in `_estimateWithdrawalFee`, and irrelevant anyway since `createWithdrawalIntents` has no such guard) but `underlyingFees.PoaBridge.relayerFee = 500,000` results in the withdraw intent debiting `amount + 499,900` more than shown/authorized.

For the specific `amount = 1n` / large-fee framing: if `feeEstimation.amount >= amount`, `actualAmount` underflows to `0n` or negative, which `PoaBridge.validateWithdrawal`'s minimum-amount check (`args.amount < minWithdrawalAmount`) generally catches, since it runs unconditionally in `sdk.ts`'s `createWithdrawalIntents` (no `skipMinAmountValidation` bypass is passed there) [8](#0-7) [9](#0-8) . So the narrow "amount=1n, tiny leftover after fee" variant of this question is largely mitigated by the live minimum-withdrawal-amount check from the PoA bridge API — which is external bridge-API state, out of scope per the rules. The broader, in-scope, code-level defect is the missing consistency check between `feeEstimation.amount` and `underlyingFees.PoaBridge.relayerFee` for larger amounts where the min-amount guard doesn't trigger, which the `FeeExceedsAmountError` guard (present only in `_estimateWithdrawalFee`, not in `createWithdrawalIntents`) also does nothing to prevent.

### Impact Explanation
When `feeEstimation.amount` and `underlyingFees.PoaBridge.relayerFee` diverge, the signed `ft_withdraw` intent debits an amount from the user's intents.near balance that does not match `withdrawalParams.amount` plus the fee they were shown, and the destination chain still only receives `actualAmount` (i.e., `amount - feeEstimation.amount`). The difference is either overcharged from the user or effectively captured by the relayer/bridge beyond the displayed estimate — a fee overcharge matching the "High" impact category (fee estimation calculation error). This affects the user/integrator on every withdrawal call where the supplied `feeEstimation` is inconsistent, and is repeatable per call.

### Likelihood Explanation
This requires the `feeEstimation` object passed to `createWithdrawalIntents`/`signAndSendWithdrawalIntent` to be constructed or forwarded by something other than the SDK's own `estimateWithdrawalFee` call (e.g., an integrator relaying a quote structure from an untrusted party, or a bug in integrator code that recombines fee objects). The SDK's own internally-generated `FeeEstimation` for PoA is always self-consistent, so exploitation depends on the caller supplying a crafted/mismatched object — this is plausible for integrators who accept `feeEstimation` fields from external input (as explicitly called out in the question's "attacker controls ... the `feeEstimation` object itself" scope) rather than always regenerating it via `estimateWithdrawalFee`.

### Recommendation
In `IntentsSDK.createWithdrawalIntents` (and/or in `PoaBridge.createWithdrawalIntents`), assert that `feeEstimation.amount === getUnderlyingFee(feeEstimation, RouteEnum.PoaBridge, "relayerFee")` before using either value, and throw if they diverge. More generally, derive the debit amount from a single source of truth (either always `feeEstimation.amount` or always the route's `underlyingFees` entry, never both independently), and apply the `FeeExceedsAmountError` guard inside `createWithdrawalIntents` itself, not only in `_estimateWithdrawalFee`.

### Proof of Concept
```ts
// vitest, packages/intents-sdk
it("detects debit mismatch when feeEstimation.amount != underlyingFees.PoaBridge.relayerFee", async () => {
  const withdrawalParams = {
    assetId: "nep141:tron-d28a265909efecdcee7c5028585214ea0b96f015.omft.near",
    amount: 1_000_000n,
    feeInclusive: true,
    destinationAddress: "T...", // valid tron address
    routeConfig: { route: RouteEnum.PoaBridge },
  };

  // Crafted/forwarded fee estimation with mismatched fields
  const feeEstimation: FeeEstimation = {
    amount: 100n, // displayed fee
    quote: null,
    underlyingFees: {
      [RouteEnum.PoaBridge]: { relayerFee: 500_000n }, // actual on-chain deduction
    },
  };

  // mock poaBridge.httpClient.getSupportedTokens / validateWithdrawal deps via HTTP mock only
  const intents = await sdk.createWithdrawalIntents({ withdrawalParams, feeEstimation });

  const withdrawIntent = intents[0]; // ft_withdraw
  const debited = BigInt(withdrawIntent.amount);

  const expectedDebit = withdrawalParams.amount; // feeInclusive => no extra debit beyond `amount`
  expect(debited).toBe(expectedDebit); // FAILS: debited = 1,000,000 - 100 + 500,000 = 1,499,900 != 1,000,000
});
```

```typescript
export function getUnderlyingFee<
	R extends keyof UnderlyingFees,
	K extends keyof NonNullable<UnderlyingFees[R]>,
>(
	feeEstimation: FeeEstimation,
	route: R,
	feeKey: K,
): NonNullable<UnderlyingFees[R]>[K] {
	const routeFees = feeEstimation.underlyingFees?.[route];
	if (routeFees === undefined) {
		throw new Error(
			`Missing underlying fees for route "${String(route)}". Fee estimation must populate underlyingFees before creating withdrawal intents.`,
		);
	}
	return (routeFees as NonNullable<UnderlyingFees[R]>)[feeKey];
}
```
