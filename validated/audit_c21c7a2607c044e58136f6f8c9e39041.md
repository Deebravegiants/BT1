### Title
Overpaid native ETH sent to `EvmHost.dispatch`/`fundRequest` is permanently lost instead of refunded to the caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept `msg.value` and forward the *entire* amount to `UniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)` to buy an exact amount of fee tokens. Any unused native ETH is refunded by the real Uniswap V2 router to `msg.sender` of the swap call — which is `EvmHost` itself, not the original transaction sender — and `EvmHost` never forwards that leftover ETH back to the caller. This is the same bug class as the referenced Footium report: a user who sends more ETH than required loses the excess, except here it is trapped inside the protocol's core `EvmHost` contract rather than an academy contract.

### Finding Description
`EvmHost.dispatch(DispatchPost memory post)` performs: [1](#0-0) 

and `EvmHost.dispatch(DispatchGet memory get)` performs the analogous swap: [2](#0-1) 

`fundRequest` (used to top up a pending request's relayer fee) does the same: [3](#0-2) 

In all three functions, `swapETHForExactTokens` is called with `{value: msg.value}` while only `post.fee` / `get.fee` / `amount` worth of the fee token is actually needed. Uniswap V2's canonical `UniswapV2Router02.swapETHForExactTokens` implementation refunds any ETH beyond what was actually spent to `msg.sender` of that call — and because `EvmHost` itself is the caller of the router (not the original EOA/app), the refund lands back in `EvmHost`'s own balance. There is no code path in `EvmHost.dispatch`/`fundRequest` that captures this returned value and forwards it to `_msgSender()`; contrast this with the project's own Uniswap V3/V4 wrapper contracts, which explicitly compute the unspent amount and `.call{value: refund}("")` it back to the caller: [4](#0-3) [5](#0-4) 

Since any application (e.g. `IntentGatewayV2`, `WrappedHyperFungibleToken`, `HyperbridgeLzEndpoint`) or end user calling `IDispatcher.dispatch{value: msg.value}(post)`/`fundRequest` can trivially overestimate the required ETH (fee estimation is inherently approximate given price movement, as documented), any overpayment beyond what the Uniswap swap actually consumes is silently absorbed by `EvmHost` instead of returned to the payer.

### Impact Explanation
Any unprivileged caller dispatching a POST/GET request or funding a pending request with native ETH permanently loses the difference between `msg.value` and the actual swap cost. Because dispatch is the most frequently used entry point in the entire system (every cross-chain message, every `IntentGatewayV2` fee payment via native ETH, every `WrappedHyperFungibleToken`/`HyperFungibleToken` send, LayerZero endpoint messages, etc. can route through this path), the blast radius is broad and repeated — funds accumulate in `EvmHost` without any accounting or user-facing withdrawal mechanism, meeting the "permanent freezing/loss of funds" bar.

### Likelihood Explanation
High. Any caller supplying `msg.value` greater than what the AMM swap actually needs (which is essentially guaranteed unless they compute the exact spot-price-adjusted amount at the exact block) triggers the loss on every call. Slippage/price movement between fee estimation (client-side, per the docs) and execution makes slight overpayment the common case rather than an edge case.

### Recommendation
After calling `swapETHForExactTokens`, use its returned `amounts[0]` (actual ETH spent) to compute `msg.value - amounts[0]` and forward that remainder back to `_msgSender()` via a low-level call (mirroring the pattern already implemented in `UniV3UniswapV2Wrapper.swapETHForExactTokens` and `UniV4UniswapV2Wrapper.swapETHForExactTokens`). Apply this fix consistently in `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest`.

### Proof of Concept
1. App/user calls `IDispatcher(host).dispatch{value: 5 ether}(post)` where `post.fee` only requires 0.001 ether worth of fee tokens (e.g., due to conservative/overestimated client-side fee quoting, as explicitly noted in the SDK docs).
2. `EvmHost.dispatch` forwards the full 5 ETH to `swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)`.
3. The Uniswap V2 router spends only the ETH needed to acquire `post.fee` fee tokens and refunds the remaining ~4.999 ETH to its `msg.sender`, i.e., `EvmHost`.
4. `EvmHost.dispatch` returns without ever inspecting or forwarding this refund; the ~4.999 ETH remains stuck in `EvmHost`'s balance with no accounting entry crediting the original caller, and no function exists to reclaim it.
5. Repeating this for every dispatch/fundRequest call accumulates unrecoverable ETH inside `EvmHost`, permanently lost to callers.
