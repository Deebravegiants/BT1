Confirmed: `Session.new(shop:)` performs no validation on `shop` at all [1](#0-0) , and `HttpClient#initialize` builds the outbound request base URI directly from `session.shop` (`@base_uri = "https://#{api_host || session.shop}"`) whenever `Context.api_host` is not configured [2](#0-1) .

### Title
Token Exchange sends the app's `client_secret` to an unvalidated host derived from the JWT `dest` claim - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the `shop` used to build the outbound OAuth token-exchange request exclusively from the `dest` claim of the caller-supplied session token, without ever passing it through `Utils::ShopValidator.sanitize!` the way every other credential-bearing flow in this library does.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` via `JwtPayload.new(session_token)` and takes `dest_shop = jwt_payload.shop` directly [3](#0-2) . `JwtPayload#shop` merely strips `"https://"` from the raw `dest` claim with no domain allow-list check: `@dest.gsub("https://", "")` [4](#0-3) .

`dest_shop` is then used to build `shop_session = ShopifyAPI::Auth::Session.new(shop: dest_shop)` [5](#0-4) , and that session's `shop` becomes the literal hostname the HTTP client sends the request to: `@base_uri = "https://#{api_host || session.shop}"` [2](#0-1) . The request body sent to that host includes `client_id` and `client_secret` in plaintext [6](#0-5) .

This is the "host validated versus host that receives the `client_secret`" identity binding named in scope. Compare with the two sibling flows in the same file/module that do enforce the binding: `ClientCredentials.client_credentials` calls `Utils::ShopValidator.sanitize!(shop)` before building the session [7](#0-6) , and `TokenExchange.migrate_to_expiring_token` (in the very same module) does the same [8](#0-7) . `exchange_token` is the outlier that skips `ShopValidator` entirely and trusts the JWT `dest` claim's string value as-is.

The security-relevant equality this depends on is: *the JWT signature is valid* ⇒ *`dest` is a genuine `*.myshopify.com`/trusted-domain host*. That equivalence is not enforced in code; it is only true if the HMAC signing key is never known outside Shopify's session-token minting process and no legacy/rotated key is stale. Once `Context.old_api_secret_key` is configured (a supported, documented rotation feature `lib/shopify_api/auth/jwt_payload.rb:26-31`), a token signed with a decommissioned/rotated secret is still accepted, widening the window in which a `dest` value from a stale-key-signed token can drive the outbound request host without any independent domain check.

### Impact Explanation
If an untrusted `dest` value reaches `exchange_token` (e.g., because a leaked/rotated legacy secret is still trusted via `old_api_secret_key`, or a future regression in `JwtPayload`), the gem will POST the app's `client_id`/`client_secret` and the raw `subject_token` to an attacker-influenced host — an SSRF that exfiltrates the app's `client_secret`, matching the "SSRF with the app's credentials" / credential-exfiltration category in scope.

### Likelihood Explanation
Under normal, single-secret operation the JWT signature check makes this hard to exploit directly, since forging `dest` requires knowing `api_secret_key`. However, the missing `ShopValidator.sanitize!` call is a clear, provable code-level asymmetry versus the two sibling flows that do validate — it is a real gap in defense-in-depth for the specific "host receiving the client_secret" binding, elevated by the built-in key-rotation fallback path that widens the trust window without corresponding domain revalidation.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` with `Utils::ShopValidator.sanitize!(dest_shop)` before constructing `shop_session`/`Clients::HttpClient`, mirroring `migrate_to_expiring_token` and `client_credentials`, so the outbound request host (which receives `client_id`/`client_secret`) is always confirmed against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` regardless of which signing key validated the token.

### Proof of Concept
1. Configure the app with `old_api_secret_key` set (documented rotation feature).
2. Obtain (via leak, previous employee, log exposure, etc.) a session token that was signed with the old/rotated secret, whose `dest` claim is `https://attacker-controlled-host.example`.
3. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
4. `JwtPayload.new` accepts the token via the `old_api_secret_key` fallback [9](#0-8) , `dest_shop` becomes `attacker-controlled-host.example` with no `ShopValidator` check, and `HttpClient` POSTs `client_id`/`client_secret` to `https://attacker-controlled-host.example/admin/oauth/access_token`, leaking the app's `client_secret` to the attacker's server.
