### Title
Webhook shop identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC-verifiable signable string that covers **only the raw request body**, while the `shop` (and `topic`/`webhook_id`/`api_version`) identity fields used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook to a merchant are read from unauthenticated HTTP headers. The equality the gem implicitly relies on — "the shop whose secret validated this HMAC" == "the shop this webhook is attributed to" — is broken because the header is never part of the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `webhook_id`, `api_version`) are pulled directly from caller-supplied headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC solely against `to_signable_string` (i.e., the body): [3](#0-2) 

`Registry.process` trusts `request.shop` for downstream attribution once the (body-only) HMAC check passes: [4](#0-3) 

Because the app's `api_secret_key` (used to compute the webhook HMAC) is a single, app-wide secret shared across *every* merchant that installs the app — not a per-shop secret — any actor who can obtain one genuinely-signed `(body, hmac)` pair (e.g., by installing the app on their own store and capturing a real webhook delivery to their own endpoint) can replay that exact body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for an arbitrary victim shop domain. `HmacValidator.validate` will still accept it, since the shop header is never part of the signed content, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim>` with attacker-controlled body content.

This is directly analogous to the pattern called out in scope: "a shop authenticated versus the shop stored as a session key" — here, the shop that produced a valid HMAC (the attacker's own store) is not the shop that the gem reports to the handler (the forged header value).

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` from `ShopifyAPI::Webhooks::Registry.process` to key merchant data, trigger merchant-scoped side effects (e.g., `app/uninstalled`, `shop/redact`, `customers/redact`, order/product sync) will process attacker-supplied data under a victim tenant's identity. This is a cross-tenant data-integrity/confusion issue: the app cannot distinguish "genuine webhook about shop A" from "attacker-replayed body falsely labeled shop B," because the gem's own HMAC validation never binds the shop.

### Likelihood Explanation
Exploitation only requires the attacker to install the target app on any store they control (a normal, unprivileged action available to any Shopify merchant/developer) to obtain one valid `(body, hmac)` pair signed with the app's shared `client_secret`, then replay it with a forged `shop-domain` header to the app's public webhook endpoint. No access to the victim's credentials, access token, or `client_secret` value is required — only knowledge of a validly-signed body, which the attacker can generate themselves via their own installation.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the verified body before it is handed to `Registry.process`/application handlers — e.g., require applications to cross-check `request.shop` against a shop that is independently known to have installed the app (a stored, previously-issued session/access token for that shop), and document this as a mandatory step in `Webhooks::Registry.process`. At minimum, update `Utils::HmacValidator`/`Webhooks::Request#to_signable_string` so the signable payload cannot be replayed across different `shop-domain` header values.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (a normal, permitted action).
2. Shopify delivers a genuine webhook to the app's endpoint with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)` — attacker captures this request.
3. Attacker replays the identical body `B` and HMAC value to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` computes `HMAC(secret, B)` and compares it to the supplied HMAC — it matches, since `B` is unchanged. [5](#0-4) 
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)`, despite `B` having originated from the attacker's own store. [6](#0-5)
