## Title
Webhook `shop` identity field is not covered by the HMAC signature, enabling cross-tenant webhook forgery via signature replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authentic for whatever shop it claims, once `Utils::HmacValidator.validate(request)` succeeds. However the HMAC is computed only over the raw request body, never over the `shop` (or `topic`/`webhook-id`) header. An attacker who legitimately receives one genuinely-signed webhook for their own store can replay that exact `{raw_body, hmac}` pair while substituting an arbitrary `X-Shopify-Shop-Domain` header, and the gem will accept it as an authentic webhook for the victim shop.

### Finding Description
The identity binding that should hold is:
`hmac == HMAC(secret, bytes_that_include_shop)`

but the gem actually implements:
`hmac == HMAC(secret, raw_body)` while `shop` is read unauthenticated from a header.

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is parsed straight from the (attacker-controllable, once a raw request reaches the endpoint) header, entirely independent of the signed bytes: [2](#0-1) 

`Registry.process` validates only the HMAC of the request, then unconditionally trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the metadata handed to the app's handler: [3](#0-2) 

`Utils::HmacValidator.validate` confirms this — it only ever calls `verifiable_query.to_signable_string`, which for `Request` is the raw body, never the shop header: [4](#0-3) 

Because the `api_secret_key` is a single per-app secret shared across *all* shops that install the app (not a per-shop secret), any merchant who installs the app receives a genuinely-signed webhook for their own store. That `{raw_body, hmac}` pair is valid for that body regardless of which shop header accompanies it, since the header is excluded from the signable string. The merchant can therefore resend the same body+hmac to the app's public webhook endpoint with a different `shop-domain` header pointing at a victim shop, and `HmacValidator.validate` will still return `true`.

### Impact Explanation
This breaks the tenant boundary the webhook subsystem is supposed to enforce: `WebhookMetadata#shop` is the field apps use to scope which merchant's data/store the event applies to. An attacker (an ordinary merchant with no special privileges, needing no access token, `api_secret_key`, or leaked credential) can cause the app to process attacker-supplied webhook payloads while impersonating an arbitrary other shop, i.e., cross-tenant data injection. This matches the Critical-impact category of cross-tenant access.

### Likelihood Explanation
The prerequisite is only that the attacker install the app on their own store to receive at least one legitimately-signed webhook (a low bar for any app that installs webhooks on onboarding), then replay it with a modified header to the app's public webhook URL. No secret, token, or elevated access is required beyond normal app installation.

### Recommendation
Include the identity-relevant header fields (`shop-domain` at minimum, ideally `topic` and `webhook-id`) in the signable string used for HMAC verification, or otherwise cryptographically bind the `shop` claim to the signed payload rather than trusting it purely from a header that sits outside the HMAC's protected bytes.

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com` and trigger a webhook topic the app has registered (e.g. `orders/create`). Capture the resulting request: `raw_body` and the `X-Shopify-Hmac-Sha256` header — both are valid together under the app's `api_secret_key`.
2. Replay the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's public webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` [5](#0-4)  — validation passes.
4. `Registry.process` then builds `WebhookMetadata` using the attacker-controlled `shop` value and dispatches it to the app's handler as if it were an authentic event for `victim-shop.myshopify.com` [6](#0-5) , letting the attacker inject data attributed to a tenant they do not own.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
