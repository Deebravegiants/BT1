### Title
Non-compliant ERC20/TRC20 `transfer` return value ignored in `IntentGatewayV2.withdraw`/`SweepDust` permanently freezes escrowed funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed order funds, transaction fees, and swept protocol dust to beneficiaries using a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks that the call itself did not revert. It never decodes/validates the returned boolean, unlike the rest of the codebase which consistently uses `SafeERC20.safeTransfer`/`safeTransferFrom`.

### Finding Description
`withdraw()` is invoked when a `RedeemEscrow` or `RefundEscrow` message is delivered from the source chain via `onAccept` [5](#0-4) . For each escrowed token it performs:
```
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [6](#0-5) 

Per the ERC20/TRC20 standard, a token contract is allowed to signal failure by returning `false` rather than reverting. In that case the low-level `.call` still returns `success == true` (the call executed without reverting), so the `if (!success) revert` guard never fires. The code then unconditionally decrements `_orders[body.commitment][token]` as though the transfer succeeded, even though the beneficiary received nothing. Because the escrow accounting has already been permanently zeroed/reduced, there is no other path to re-claim the tokens that remain stuck in the contract — the same root cause called out in the referenced ACO report for `_transferERC20`/`_transferFromERC20`. The same unchecked pattern is repeated for transaction-fee payout [2](#0-1)  and for governance-triggered dust sweeps [7](#0-6) .

This is reachable by any unprivileged user through the ordinary intents flow: a user calls `placeOrder` escrowing a token that is (or later becomes, e.g. via a pausable/blacklist-capable stablecoin) non-compliant in this way, a solver fills the order, and the resulting cross-chain `RedeemEscrow` delivery silently "succeeds" while leaving the user's/solver's funds permanently trapped in the contract.

### Impact Explanation
Funds escrowed for orders denominated in a non-standard-compliant ERC20/TRC20 token can become permanently frozen: the beneficiary receives no tokens, but the internal escrow ledger is decremented to zero, removing any legitimate way to retry or recover the transfer. This matches the "permanent freezing of funds" acceptance criterion. It is a protocol-level accounting bug reachable purely through normal intent settlement, not a malicious-admin or malicious-relayer scenario.

### Likelihood Explanation
Likelihood is elevated on Tron specifically, since a meaningful share of widely used TRC20 tokens in that ecosystem do not strictly follow the boolean-return convention or can enter blacklist/paused states where `transfer` returns `false` instead of reverting. Any token pair listed by governance that includes such a token turns this into a reliably triggerable freeze on every fill/refund/dust-sweep for that token.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` branch of `onAccept` with `SafeERC20.safeTransfer` (already imported and used elsewhere via `using SafeERC20 for IERC20;` in this same file), so that non-compliant tokens returning `false` cause a revert instead of a silently accepted no-op transfer.

### Proof of Concept
1. Governance registers a TRC20 token `T` for the Tron `IntentGatewayV2` that returns `false` on `transfer` failure (e.g. a paused/blacklist-style token, or simply a minimal mock implementing `transfer` to `return false;` without reverting when a condition is met).
2. A user calls `placeOrder` escrowing `T`; a solver fills it and the `RedeemEscrow` message is relayed and delivered via `onAccept` → `withdraw`.
3. At the moment of delivery, token `T` is configured/blacklists the beneficiary so `transfer` returns `false` without reverting.
4. `withdraw()` sees `success == true` from the low-level `.call`, does not revert, and executes `_orders[body.commitment][token] -= amount;`, zeroing the escrow record even though the beneficiary balance is unchanged.
5. The tokens remain custodied in the `IntentGatewayV2` contract with no remaining escrow entry, and no function permits re-claiming them — the funds are permanently frozen.
