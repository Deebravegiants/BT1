Audit Report

## Title
Unauthenticated LDAP DN injection via login email in LDAP bind construction - (core/sessions/ldapauth/ldap.go)

## Summary
The LDAP authentication provider's `CreateSession` and `TestPassword` (and the internal `FindUser`/bind helper in `CreateSession`) build a raw LDAP bind DN by string-concatenating the attacker-controlled login email, but sanitize that email only with `ldap.EscapeFilter`, which escapes RFC4515 search-filter metacharacters and not RFC4514 DN metacharacters. This allows an unauthenticated caller of `/sessions` to inject additional RDN components into the DN passed to `conn.Bind`, altering the directory object the bind is actually attempted against.

## Finding Description
In `CreateSession`, the request's `sr.Email` is only passed through `ldap.EscapeFilter` and then interpolated directly into a bind DN string: [1](#0-0) . The identical pattern is present in `TestPassword`: [2](#0-1) .

`ldap.EscapeFilter` escapes only `*`, `(`, `)`, `\` and NUL — the RFC4515 filter metacharacters — leaving DN metacharacters such as `,`, `+`, `"`, `<`, `>`, `;`, `=` and leading/trailing spaces untouched. Since `searchBaseDN` is consumed as a literal DN by `conn.Bind`, a login email containing a comma (e.g. `victim,dc=example,dc=com`) restructures the DN tree traversed by the bind, rather than being treated as an opaque attribute value.

By contrast, the properly-scoped filter query in `FindUser` correctly uses `EscapeFilter` in an actual filter context: [3](#0-2) , confirming the bug is a context mismatch specific to the bind-DN construction sites, not the filter-query sites.

The entry point requires no prior authentication — `SessionsController.Create` binds the raw JSON body to `SessionRequest` and forwards it straight to the authentication provider: [4](#0-3) [5](#0-4) . No middleware sanitizes or DN-escapes the email before it reaches `CreateSession`.

## Impact Explanation
This is a real authentication-boundary defect: on a node configured with the LDAP driver, an unauthenticated client fully controls the DN structure used in `conn.Bind`, not merely the leaf attribute value. Depending on the target directory's tree and entries, this can redirect the bind to unintended objects (e.g., objects with weaker/blank credential requirements or anonymous-bind-permitted entries), while `FindUser`'s role lookup is keyed on the same (raw, DN-unescaped) email string — meaning a successful bind against an unintended object can still result in a session being created under the attacker-supplied identity/role mapping. This falls under the node API authentication/role-bypass impact category, since the flaw sits directly in the `/sessions` authentication path (`sessions.AuthenticationProvider` / `ldapauth.CreateSession`/`TestPassword`).

## Likelihood Explanation
Exploitability requires the node to have the LDAP authentication driver enabled (a supported, non-default but legitimate configuration, not a misconfiguration) and depends on the specific LDAP server's directory layout and bind-error behavior. No authentication, prior session, or elevated role is needed to reach the vulnerable code — a single POST to `/sessions` with a crafted `email` value is sufficient to trigger the injected DN construction, making this reliably reproducible for a node operating with LDAP auth enabled.

## Recommendation
- Replace the filter-escaping applied to `escapedEmail` in the DN-construction call sites (`CreateSession` L406-407, `TestPassword` L512-513) with proper RFC4514 DN escaping (e.g., `ldap.EscapeDN` if available in the vendored `go-ldap/v3`, or manual escaping of `,+"\<>;=` and leading/trailing spaces).
- Prefer resolving the user's DN via a properly filter-escaped LDAP *search* and binding with the DN returned by the directory, rather than manually concatenating a DN string from user input.
- Add regression tests asserting that emails containing DN metacharacters are rejected or safely escaped before being passed to `conn.Bind`.

## Proof of Concept
1. Configure a node with `config.LDAP` enabled against a test LDAP directory with a known tree structure.
2. POST to `/sessions`:
   ```json
   {"email": "victim,dc=example,dc=com", "password": "anything"}
   ```
3. Observe `escapedEmail` is unchanged by `ldap.EscapeFilter` (comma is not a filter metacharacter), producing `searchBaseDN = "uid=victim,dc=example,dc=com,ou=users,dc=example,dc=com"` passed to `conn.Bind`, demonstrating attacker control over DN structure rather than the literal supplied email.
4. Repeat against a directory entry known to have anonymous-bind or blank-password semantics to confirm bind success under attacker-chosen DN while `FindUser` assigns a role based on the raw supplied email string.
