## Title
Missing length validation on `message.from` panics `on_accept` for HFT cross-chain transfers with sponsored calldata - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
CVE-2015-8917 is a libarchive crash caused by trusting an attacker-supplied name field to have a fixed shape without validating its length/characters before it is copied into a fixed-size structure, causing a NULL/invalid-memory crash. The same bug class — an unchecked, attacker-influenced variable-length byte field copied into a fixed-size buffer — exists in `pallet-hyper-fungible-token`'s `on_accept` handler, which is reachable by any unprivileged relayer submitting a fee-less `handle_unsigned` extrinsic that carries a valid cross-chain `PostRequest`.

### Finding Description
`Pallet::on_accept` decodes the ABI-encoded `Message` body of a HFT `PostRequest` and, when the message carries optional calldata with no signature, derives the dispatch origin from `message.from` without validating its length: [1](#0-0) 

```
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```

- If `source.is_evm()` is true and `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows (`usize` subtraction), which either panics directly under overflow checks or produces a huge index that panics on slice indexing.
- If `source.is_evm()` is false and `from_bytes.len() != 32`, `copy_from_slice` panics on a length mismatch (Rust `copy_from_slice` requires the source and destination slices to have identical length).

This is the exact bug class already recognized and fixed twice elsewhere in this codebase: `StateMachine::from_str`'s `copy_from_slice` panic on non-4-byte ids (fixed with an explicit length check, see the regression comment) and `as_utf8_string`'s deserializer (fixed after it "crashed the production node"): [2](#0-1) [3](#0-2) 

Critically, the sibling code path in the same file, `on_timeout`, handles the identical `message.from` field correctly by explicitly checking the length and returning `HftError::InvalidSenderLength` for anything else: [4](#0-3) 

The `on_accept` sponsorship-authorization branch was not given the same guard, so it is the one path in this module that still trusts the field's length unconditionally.

### Impact Explanation
`on_accept` executes during ISMP message delivery (`pallet_ismp::Pallet::execute`), which is invoked from the unsigned, fee-less `Call::handle_unsigned` extrinsic: [5](#0-4) 

Any relayer or unprivileged caller who can produce a valid consensus/state proof for a dispatched request can trigger `on_accept`. A panic inside pallet dispatch during block execution is a denial-of-service against message delivery for the affected HFT deployment (and, depending on how the runtime handles panics during block execution versus in the transaction pool, potentially against block production/finalization on the destination chain) — this falls squarely under "a route unable to deliver messages."

### Likelihood Explanation
Reachability depends on whether the registered, legitimate `HyperFungibleToken` source contract can be made to emit a `message.from` of a length other than 20 (EVM) or 32 (Substrate) bytes while attaching non-empty, unsigned calldata (`substrate_data.signature == None`). This requires confirming the Solidity encoding logic in `HyperFungibleToken.sol` for `from`, which was not fully verified within the scope of this analysis — flagged as a genuine gap. Given the codebase's own explicit history of this exact panic pattern being found and fixed in two prior instances, and the presence of an already-hardened sibling function (`on_timeout`) processing the same field, this looks like an overlooked case that deserves the same fix rather than a false positive; however, the precise inbound calldata paths the contract permits must be re-checked to fully confirm attacker control end-to-end.

### Recommendation
Mirror the guard already applied in `on_timeout`: validate `from_bytes.len()` is exactly 20 (for EVM source, after any left-pad/strip decision) or exactly 32 (for non-EVM source) before calling `H160::from_slice`/`copy_from_slice`, and return `HftError::InvalidSenderLength` (or an analogous error) otherwise, so `on_accept` fails gracefully instead of panicking.

### Proof of Concept
1. Register a legitimate `HyperFungibleToken` EVM contract via `ContractToAsset` for `(source, contract_address)`.
2. From the EVM source chain, dispatch a `PostRequest` whose ABI-encoded `Message.from` is not exactly 20 bytes (if achievable via the contract's public interface) and whose `Message.data` decodes to `SubstrateCalldata { signature: None, runtime_call: <any allowed call> }`.
3. Obtain a valid consensus/state proof for that request (standard relayer flow) and submit `Ismp::handle_unsigned` with the corresponding `RequestMessage`.
4. When `Pallet::on_accept` runs and hits `let mut account = [0u8; 32]; account.copy_from_slice(from_bytes);` (or the EVM underflow branch) with a mismatched length, execution panics, denying delivery of this and potentially other messages processed in the same block.

	/// The string must be exactly 4 bytes long (bytes, not chars — a 4-char string of
	/// multi-byte codepoints is rejected). Anything else is a deserialization error; this
	/// runs on untrusted RPC input, so it must never panic.
	pub fn deserialize<'de, D, T>(deserializer: D) -> Result<T, D::Error>
	where
		D: serde::Deserializer<'de>,
		T: From<[u8; 4]>,
	{
		let s = <String>::deserialize(deserializer)?;

		// `s.len()` is the utf-8 byte length, which is what the `[u8; 4]` needs to match.

		Ok(bytes.into())
	}
