### Title
Webhook Shop/Topic Attribution Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the `shop-domain` (and `topic`) HTTP headers—values that are never included in the signed payload—to attribute the webhook to a tenant. Any caller who can produce one valid `(body, hmac)` pair for the shared `api_secret_key` (e.g., a legitimate merchant using the multi-tenant app, who receives real webhooks for their own store) can replay that exact body to the app's shared webhook endpoint while substituting an arbitrary `shop-domain` header, causing the host application to process attacker-controlled data under a different tenant's identity.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares the HMAC only against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns just the raw HTTP body: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from unauthenticated HTTP headers with no cryptographic binding to the HMAC or to the body: [3](#0-2) 

`Registry.process` only checks the body HMAC, then immediately hands the unauthenticated `request.shop` and `request.topic` values to the app's handler as trusted tenant identifiers: [4](#0-3) 

This breaks the intended identity binding: **`hmac` verifies `body`**, but the host application actually keys tenant-scoped behavior off **`shop` (and `topic`)**, i.e. the field acted upon (`shop`) is not the field covered by the HMAC (`body` only). Because every shop installed on a given app shares the same `api_secret_key`, any tenant of the multi-tenant app can generate a body+HMAC pair that is valid for the shared secret (by triggering a real webhook for their own store, or by computing it if the shop is a low-trust/self-serve app install), then POST that same body to the shared webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop. `HmacValidator.validate` will accept it since the body/HMAC pair is genuinely valid for the shared secret, and `Registry.process` will dispatch the payload to the handler labeled as belonging to the victim shop.

### Impact Explanation
This is a cross-tenant data integrity issue: an attacker who is any tenant of the shared app can cause the app to process fabricated webhook events attributed to another merchant's shop domain. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up a `Session`, write to that shop's records, or trigger shop-scoped side effects), this can lead to cross-tenant data corruption/injection, satisfying the "cross-tenant access" Critical impact category, since the gem provides no facility for host apps to detect this forgery and documents `request.shop` as if it were an authenticated value once `HmacValidator.validate` passes.

### Likelihood Explanation
Likelihood is realistic in any multi-tenant embedded app built on this gem (the standard use case): any existing/self-serve installer of the app can legitimately generate valid `(body, hmac)` pairs for the shared `api_secret_key` via their own store's real webhook traffic, then simply replay the body to the shared endpoint with a different `shop-domain` header value—no access token, no `api_secret_key` leakage, and no privileged account required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signable string/verification step, or otherwise cross-check the header-provided `shop` against an independently trusted source (e.g., require the caller to additionally supply/verify shop identity via a registered webhook subscription lookup) before dispatching to handlers. At minimum, document that `request.shop`/`request.topic` are NOT authenticated by the HMAC and must not be trusted for tenant attribution without additional verification (e.g., matching against the shop that had this exact topic/webhook_id registered).

### Proof of Concept
1. App is a multi-tenant Shopify app; tenant A (`attacker.myshopify.com`) has it installed and receives a real, validly-signed webhook, e.g.:
```
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: <valid HMAC of body B computed with the shared api_secret_key>
X-Shopify-Shop-Domain: attacker.myshopify.com
Body: B (attacker can shape B by creating/editing their own order, since it's their own store)
```
2. Attacker replays the exact same body `B` and HMAC to the app's shared webhook endpoint, but changes the header:
```
X-Shopify-Shop-Domain: victim.myshopify.com
```
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), and `Utils::HmacValidator.validate` returns `true` because it only checks `B` against the HMAC: [5](#0-4) 
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: <parsed B>, ...)`, causing the host app to process attacker-controlled data attributed to `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
