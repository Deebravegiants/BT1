### Title
Webhook shop-domain (tenant) header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `shop-domain` header to identify which tenant/shop the webhook event belongs to. Since the HMAC signable string only ever covers the body, any party who can obtain one genuine, validly-signed webhook body/HMAC pair (trivially available to any merchant/developer who installs the app themselves) can replay that same body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header, causing the app to process the event as if it originated from a different, victim shop.

### Finding Description
`Registry.process` performs exactly one authentication check before dispatching a webhook to the handler: [1](#0-0) 

```
sig { params(request: Request).void }
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

The `Utils::HmacValidator.validate` call computes the signature over `request.to_signable_string`, which `ShopifyAPI::Webhooks::Request` defines as the raw body only: [2](#0-1) 

```
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
```

Meanwhile, `topic` and `shop` — used to route and identify the tenant for the webhook — are read directly from HTTP headers that are never included in the signable string: [3](#0-2) 

```
sig { returns(String) }
def topic
  T.cast(shopify_header("topic"), String)
end

sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```

The `HmacValidator` only proves that the *body* bytes were signed with the app's shared `api_secret_key`; it makes no assertion about the `shop-domain` header: [4](#0-3) 

Because `api_secret_key` is the same secret for every shop that installs a given (public) app, an unprivileged attacker who installs the app on their own store will legitimately receive Shopify-generated webhooks — bodies with valid HMACs computed under that same shared secret. The attacker can then replay that exact body+HMAC pair to the app's webhook endpoint, overriding only the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to name a victim shop. `HmacValidator.validate` still succeeds (it never inspected the header), so `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain: [5](#0-4) 

This breaks the intended identity binding: `verified_sender == body_signed_with_shared_secret` is conflated with `event_belongs_to == shop_header`, when in fact the header is attacker-controlled and outside the HMAC's coverage.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to select which merchant's records to create, update, delete, or otherwise act on (a standard and expected usage pattern per the gem's own `WebhookHandler` interface) can be tricked into performing cross-tenant actions: attacker-supplied event data attributed to, and acted upon on behalf of, a shop the attacker does not control. This is a cross-tenant access vulnerability — the app's own trust boundary between shops is defeated using only a HMAC pair obtainable via a legitimate, unprivileged installation of the app.

### Likelihood Explanation
Exploitation requires no secrets, tokens, or privileged access — only that the attacker (or anyone) can install the target app on a shop they control (the normal, unprivileged path for any Shopify merchant/developer) and can send a crafted HTTP request with modified headers to the app's public webhook endpoint. No interaction with Shopify's own infrastructure integrity is needed; the vulnerability is purely in this gem's verification/dispatch logic (`Registry.process`, `Request#to_signable_string`).

### Recommendation
Bind the tenant identity to the same integrity check as the body: either include `shop-domain` (and `topic`) in the HMAC-covered signable string used by `Request#to_signable_string`, or cross-validate the header-derived `shop` against a shop already known/associated with the delivered `webhook_id`/subscription (e.g., verify against a stored subscription-to-shop mapping) before dispatching to the handler. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for tenant selection without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com` (normal app installation, no special privilege).
2. Shopify delivers a genuine webhook to the app, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this request and replays it directly to the app's webhook endpoint, keeping body `B` and header `H` identical, but changing only `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and compares it to `H` — this succeeds because the body is unmodified.
5. `Registry.process` dispatches to the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, even though the event body actually pertains to the attacker's own shop.
6. Any handler logic keyed on `data.shop` now performs its side effects (e.g., creating/updating local records, triggering merchant-facing actions) under the identity of `victim-shop.myshopify.com`.
