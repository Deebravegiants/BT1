## Title
Webhook shop identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook solely by validating the HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`) values that the handler ultimately trusts come from HTTP headers that are **not** included in the signed content. Because the HMAC secret (`Context.api_secret_key`) is the app's single `client_secret` shared across every merchant that installs the app, any merchant with a legitimate installation can capture one of their own genuinely-signed webhook deliveries and replay it against the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a victim shop. The signature still validates because it never covered the shop header, so the app's handler processes attacker-controlled data under a different tenant's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are read straight from headers and are never part of the signed string: [2](#0-1) 

`Registry.process` only calls `Utils::HmacValidator.validate(request)`, which internally calls `validate_signature` against `to_signable_string` (body only), then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) [4](#0-3) 

The documented usage explicitly tells integrators that `Registry.process` "will verify the request did indeed come from Shopify" and shows a handler trusting `data.shop` directly (e.g. to route `perform_later(shop_domain: data.shop, ...)`): [5](#0-4) [6](#0-5) 

The identity binding the library is supposed to guarantee is: `shop reported to the handler == shop that produced the HMAC-signed payload`. In reality the equality only holds for: `body verified by HMAC == body bytes received`; the `shop` header is entirely unauthenticated. Since `Context.api_secret_key` is the one shared secret for the whole app (identical for every installing merchant), any merchant is capable of generating a validly-signed `(body, hmac)` pair for their own store, then resending that exact body/hmac pair to the app's webhook endpoint with a forged `x-shopify-shop-domain` (or `shopify-shop-domain`) header naming a different, victim shop. `HmacValidator.validate` will pass (it never looks at the shop header), and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the victim's domain while the body content is attacker-controlled.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce ("verify the request did indeed come from Shopify" for a specific shop). A malicious but otherwise unprivileged merchant of a multi-tenant app can make the host application believe arbitrary attacker-chosen data (e.g. `orders/create`, `app/uninstalled`, `shop/redact`, `customers/data_request` payloads) originated from a different merchant's shop. Depending on how the host app's handler uses `data.shop` (commonly to look up/act on that shop's stored session or trigger tenant-scoped side effects, exactly as shown in the gem's own docs example), this enables cross-tenant data corruption, spoofed mandatory-compliance webhooks, or triggering shop-scoped background jobs against a victim tenant — a cross-tenant access impact.

### Likelihood Explanation
Exploitation only requires being a normal (unprivileged) installer of the target public/multi-tenant app — no access to `api_secret_key`, no privileged account, and no interception of TLS is needed. The attacker simply needs one legitimately delivered webhook (from their own store) to capture a valid `(raw_body, hmac)` pair, then replays it directly to the app's public webhook endpoint with a modified shop header. This is a standard HTTP request forgery, well within reach of any internet user with a shop on the platform.

### Recommendation
Include the shop (and ideally topic/webhook-id) in the value that is cryptographically verified, or otherwise bind the verified body to the specific claimed shop before constructing `WebhookMetadata`. If Shopify's real HMAC scheme genuinely only signs the body, the gem should not present the header-derived `shop` as a value the host app can trust for authorization decisions without cross-checking it against a shop the app has an active, correctly-scoped session/subscription for that specific webhook id/topic.

### Proof of Concept
1. Merchant "attacker.myshopify.com" installs the target app and lets it deliver a webhook, e.g. `orders/create`, to the app's `/webhooks` endpoint. Attacker captures the raw POST body and the `x-shopify-hmac-sha256` header — both valid, because Shopify computed the HMAC with the app's shared `client_secret`.
2. Attacker resends the identical raw body and HMAC header to the same endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com` instead of their own domain.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and finds it matches — validation succeeds.
4. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` and invokes the host app's handler, which (per the documented pattern) trusts `data.shop` as the authenticated tenant identity, even though the payload actually came from and was intended to represent `attacker.myshopify.com`.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
