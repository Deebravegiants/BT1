This is the critical finding: `HttpClient#initialize` builds `@base_uri = "https://#{api_host || session.shop}"` and then sends `client_secret` in the POST body to that host [1](#0-0) . In `ShopifyAPI::Auth::TokenExchange.exchange_token`, the `shop` used to build that session (and therefore the destination host that receives `client_id`/`client_secret`) is taken directly from the **unverified `dest` claim of the JWT payload**, with no call to `ShopValidator.sanitize!` [2](#0-1) . Compare this to the sibling methods `ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token`, which both explicitly call `Utils::ShopValidator.sanitize!(shop)` before constructing the session that determines the request host [3](#0-2) [4](#0-3) .

`JwtPayload#shop` only strips a literal `"https://"` prefix and returns `@dest` as-is; there is no check that `dest`'s host is a trusted `myshopify.com`/`myshopify.io`/`spin.dev` domain [5](#0-4) . The only checks performed during JWT construction are signature validity (via `Context.api_secret_key`) and `aud == Context.api_key` [6](#0-5) [7](#0-6) .

### Title
Unvalidated `dest` claim used as request host in `TokenExchange.exchange_token` leaks `client_secret` to attacker-controlled host - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`TokenExchange.exchange_token` derives the request host (and thus the destination of the POST that carries `client_id`/`client_secret`) directly from the JWT `dest` claim without running it through `ShopValidator.sanitize!`, unlike the other OAuth-adjacent flows in this gem.

### Finding Description
The binding this code is supposed to enforce is: `host that receives the app's client_secret == a trusted Shopify domain`. In `exchange_token`, `dest_shop = jwt_payload.shop` is taken straight from the JWT's `dest` claim and passed into `ShopifyAPI::Auth::Session.new(shop: dest_shop)` [8](#0-7) . `HttpClient` then builds its base URI from `session.shop` (`@base_uri = "https://#{api_host || session.shop}"`) and sends the POST body — which includes `client_id` and `client_secret` — to that URI [1](#0-0) .

`JwtPayload` only verifies the JWT's HMAC signature and that `aud == Context.api_key`; it performs no allowlist check on `iss`/`dest` against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` [9](#0-8) . Since the token is signed with the shared `api_secret_key`, a legitimate holder of a session token for their own (attacker-controlled) tenant can present a token whose `dest` value is anything the signer places there. Even more directly, an attacker who does not control a signed token at all is not the primary threat here — the real gap is architectural: this gem, unlike its own `ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token` siblings, omits the `ShopValidator.sanitize!` call that is the gem's documented mechanism for keeping the request host bound to a trusted Shopify domain [10](#0-9) [11](#0-10) .

### Impact Explanation
If the `dest` claim can carry a value that is not constrained to a Shopify-owned domain, the gem will send the app's `client_id`/`client_secret` and `subject_token` to that host — an SSRF-with-credentials outcome. This matches the High-impact category "SSRF with the app's credentials".

### Likelihood Explanation
This requires review of what governs the `dest` claim in Shopify-issued session tokens. In this analysis I was unable to fully verify, purely from the gem's code, whether Shopify enforces domain restrictions on `dest` server-side before it ever reaches this gem — the gem itself provides no such control. The asymmetry with `client_credentials.rb` and `migrate_to_expiring_token` (which do sanitize) suggests the gem's own authors intended `ShopValidator.sanitize!` to be applied to all shop-derived request hosts, and its absence in `exchange_token` is an internal inconsistency rather than a deliberate, safe design choice.

### Recommendation
Apply `ShopifyAPI::Utils::ShopValidator.sanitize!(dest_shop)` to the shop value derived from `jwt_payload.shop` in `TokenExchange.exchange_token` before constructing `shop_session`, mirroring the pattern already used in `ClientCredentials.client_credentials` and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
Not independently reproducible from the gem alone without confirming how Shopify's token issuer constrains the `dest` claim; the finding is based on static code-path analysis: `exchange_token` (lib/shopify_api/auth/token_exchange.rb:39-51) → `HttpClient#initialize` (lib/shopify_api/clients/http_client.rb:16-19) → POST body containing `client_secret` sent to `session.shop`. No `ShopValidator` call sits on this path, in contrast to the two sibling methods that do call it.
