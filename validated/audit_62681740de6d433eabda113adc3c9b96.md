### Title
Unconstrained `calldataHash` public signal in `MainEVMCircuit` allows a relay to rewrite fee/hook/external-action parameters after proof generation - (File: `circuits/MainEVMCircuit.circom`)

### Summary
`MainEVMCircuit` declares `calldataHash` as a public circuit signal, and the on-chain flow treats that signal as the sole binding mechanism for a large group of `CircomData` fields (`feeStructure`, `relay`, `externalActionData`, `hookData`, `onChainCreation`, `originalSender`, `extraData`, `slippageValues`, `encryptedOutputs`, `onChainEncryptedOutput`, `publicSignalCount`) that are hashed into it. However, inside the circuit body the `calldataHash` signal is never consumed by any constraint (`<==`/`===`) — it is only listed in the header comment and declared as `signal input calldataHash;` [1](#0-0) [2](#0-1) . The remainder of the circuit (signature check, nullifier/commitment checks, Merkle proof check, sum checks) never references `calldataHash` [3](#0-2) . A public signal that appears with zero coefficient in every R1CS constraint gets a zero verification-key element for the Groth16 "IC" term, so any value can be substituted for it at verification time without invalidating the proof — exactly the "missing commitment" (frozen-heart-style) issue the external report describes, except here the parameter is nominally *inside* the public-input vector but functionally *not bound* by the proof.

### Finding Description
On-chain, `CircomDataBuilder.getHashedCalldata` hashes `feeStructure`, `relay`, `externalActionData`, `hookData`, `onChainCreation`, `originalSender`, `extraData`, `slippageValues`, `encryptedOutputs`, `onChainEncryptedOutput`, and `publicSignalCount` into `calldataHash` [4](#0-3) . `HinkalHelper.performHinkalChecks` only verifies that this hash is *self-consistent* with the rest of the supplied `circomData` (`getHashedCalldata(circomData) == circomData.calldataHash`), then feeds `circomData.calldataHash` into the public-input vector passed to the SNARK verifier via `formBasicInput` [5](#0-4) [6](#0-5) .

The only thing that is supposed to bind these fee/hook/external-action fields to the user's *original intent* (i.e., to the specific proof the user generated) is the fact that `calldataHash` is a public input to the SNARK. But since the circuit never constrains `calldataHash` against anything, the SNARK proof itself carries zero information about it. A relay/attacker that already possesses a valid `(a,b,c)` proof for one `circomData` payload can:
1. Freely change any of the `calldataHash`-only-protected fields (e.g., `feeStructure.flatFee`/`variableRate`, `relay`, `hookData.preHookContract`/`postHookContract`, `externalActionData.externalAddress`/`externalActionMetadata`).
2. Recompute a matching `calldataHash` locally (a plain `keccak256`, not a ZK-protected value) so the `require` in `performHinkalChecks` passes.
3. Resubmit the *same* proof `(a,b,c)` together with the new `circomData` to `Hinkal.transact`. Because `calldataHash`'s verification-key contribution is the identity element (zero coefficient everywhere in the circuit), `verifyProof` still succeeds [7](#0-6) .

`Hinkal.transact` then executes `_internalTransact`/`_externalTransact` and the hook calls using the *tampered* fields — none of which were actually authorized by the user's proof: relay fee extraction uses `circomData.feeStructure`/`circomData.relay` [8](#0-7) , and pre/post hooks and external actions are invoked with `circomData.hookData`/`circomData.externalActionData` [9](#0-8) [10](#0-9) .

This breaks the intended equality "the funds/actions authorized by the prover == the funds/actions executed on-chain," because a party that never held the user's spending key can rewrite fee, relay, hook, and external-action routing after the proof was generated, while reusing the same valid ZK proof.

### Impact Explanation
This is Critical: it allows a malicious relay (an unprivileged EOA with respect to the user's shielded funds) to redirect or inflate `feeStructure` to siphon more of the withdrawn/swapped amount than the user authorized, to point `hookData.preHookContract`/`postHookContract` at attacker-controlled contracts that execute with the user's UTXO context, or to swap `externalActionData.externalAddress`/`externalActionMetadata` to route funds through a different external action than the one the user proved and signed for. This is theft of shielded/in-flight user funds and unauthorized asset movement executed via calls the prover never authorized.

### Likelihood Explanation
Likelihood is high for any relay-submitted transaction, since a relay is by construction an untrusted party that receives the completed proof and calldata from the user and is the one who calls `transact`. No admin/owner/relayer-trust assumption beyond "the relay is not fully honest" is required — this is exactly the threat model Hinkal's relay design is supposed to defend against via `calldataHash`/proof binding.

### Recommendation
Add an explicit constraint inside `MainEVMCircuit` (and any other circuit exposing `calldataHash`) that binds `calldataHash` to a value derived from the actual fee/hook/external-action/relay fields inside the circuit (e.g., recompute the same hash construction in-circuit, or split those fields into individually-constrained public signals), so the Groth16 verification key element for `calldataHash` is non-trivial and the proof cannot be reused with an alternate value. As a general hardening measure, audit every public signal declared in the circuits under `circuits/**` to confirm each one is referenced by at least one constraint, since an unused public signal is unconstrained and effectively a "free parameter" for the prover/relay, mirroring the exact Fiat-Shamir "missing commitment" defect described in the reference report.

### Proof of Concept
1. User builds a legitimate transaction: `circomData` with `feeStructure = {feeToken: T, flatFee: 0, variableRate: 50}` and a fair `hookData`/`externalActionData`. The wallet computes `calldataHash = getHashedCalldata(circomData)` and generates a valid Groth16 proof `(a,b,c)` for `MainEVMCircuit`, where `calldataHash` is passed as one of the public signals but is not referenced by any constraint (confirmed by inspection of `circuits/MainEVMCircuit.circom` lines 1-180 — no use of `calldataHash` outside its declaration).
2. User sends `(a,b,c, dimensions, circomData)` to a relay for submission.
3. Relay mutates `circomData.feeStructure.variableRate` to `10000` (100%) and/or swaps `hookData.postHookContract` to an attacker contract, recomputes `calldataHash' = getHashedCalldata(mutated circomData)` locally (pure keccak, no ZK needed), and calls `Hinkal.transact(a, b, c, dimensions, mutatedCircomData)`.
4. `performHinkalChecks` accepts because `getHashedCalldata(mutatedCircomData) == mutatedCircomData.calldataHash` by construction.
5. `verifyProof(a, b, c, inputForCircom, ...)` still returns true because the `calldataHash` slot's verification-key element is the identity (zero coefficient in every R1CS row), so the changed value has zero effect on the Groth16 pairing check.
6. `_internalTransact`/hook execution now runs with the attacker-controlled `feeStructure`/`hookData`, extracting the user's entire withdrawal as "relay fee" or routing funds through a malicious hook — funds the user never authorized to move that way.

    function _internalTransact(CircomData calldata circomData) private {
        bool hasPaidToRelay = false;
        for (uint64 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 deltaAmountChange = _calculateDeltaAmount(circomData, i);

            if (deltaAmountChange > 0) {
                require(
                    circomData.externalActionData.externalAddress == msg.sender,
                    "Deposit should come from the sender"
                );
                transferERC20TokenFromOrCheckETH(
                    circomData.erc20TokenAddresses[i],
                    circomData.externalActionData.externalAddress,
                    address(this),
                    uint256(circomData.amountChanges[i])
                );
            } else {
                uint256 sumAbs = uint256(-deltaAmountChange);
                uint256 relayFee = 0;
                if (circomData.relay != address(0)) {
                    uint256 flatFee = circomData.feeStructure.feeToken ==
                        circomData.erc20TokenAddresses[i]
                        ? circomData.feeStructure.flatFee
                        : 0;

                    require(
                        sumAbs >= flatFee,
                        "Relay Fee is over withdraw amount"
                    );

                    uint256 recipientAmount = ((10000 -
                        circomData.feeStructure.variableRate) *
                        (sumAbs - flatFee)) / 10000;

                    relayFee = sumAbs - recipientAmount;

                    if (relayFee > 0) {
                        transferERC20TokenOrETH(
                            circomData.erc20TokenAddresses[i],
                            circomData.relay,
                            relayFee
                        );
                    }
                    hasPaidToRelay = true;
                }
                if (sumAbs - relayFee > 0) {
                    transferERC20TokenOrETH(
                        circomData.erc20TokenAddresses[i],
                        circomData.externalActionData.externalAddress,
                        sumAbs - relayFee
                    );
                }
            }
        }
        require(
            circomData.relay == address(0) || hasPaidToRelay,
            "relay not paid"
        );
    }
