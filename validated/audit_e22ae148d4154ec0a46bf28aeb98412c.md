This confirms the root cause: the `VerifiableQuery` interface requires only `hmac` and `to_signable_string`, and `ShopifyAPI::Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb` line 36-38) returns only `@raw_body`. The `shop`, `topic`, `webhook_id`, and `api_version` fields are all read straight from HTTP headers (`shopify_header`) but are never included in the signable string, so `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb` line 26-31) never binds them to the signature. `Registry.process` (`lib/shopify_api/webhooks/registry.rb` line 188-199) trusts `request.shop` and passes it directly into `WebhookMetadata`, which the host app's handler uses to attribute the webhook to a tenant.

### Title
Webhook shop-domain spoofing via HMAC that only covers the body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are taken from unauthenticated HTTP headers. `HmacValidator.validate` only proves the body's integrity/authenticity against the app's `client_secret`; it says nothing about which shop the request claims to be from.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only [1](#0-0) , and `Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic binding [2](#0-1) . `HmacValidator.validate_signature` verifies `computed_signature` (over `to_signable_string`) against the received HMAC using the app-wide `Context.api_secret_key` — the same secret is used for every shop the app is installed on, not a per-shop secret [3](#0-2) . `Registry.process` accepts any request that passes this HMAC check and forwards `request.shop` unchanged into `WebhookMetadata`, which the host app's handler uses to key data per tenant [4](#0-3) .

The equality this breaks: `shop_authenticated_by_hmac == shop_used_by_handler` does not hold — the HMAC authenticates only `(secret, raw_body)`; it never authenticates `(secret, raw_body, shop)`.

### Impact Explanation
Because the webhook secret is the app's `client_secret`, not a per-merchant secret, a malicious merchant who has installed the app can capture a validly-signed webhook body+HMAC pair (sent to their own store) and replay it against the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim merchant's domain. `HmacValidator.validate` will still return `true` since it only checks the body, and `Registry.process` will hand the forged `shop` value to the handler, causing the host application to attribute attacker-controlled webhook data to another tenant — a cross-tenant data-integrity/confusion issue.

### Likelihood Explanation
Requires the attacker to control at least one shop that has installed the app (a legitimate merchant/attacker with no special privileges over other tenants), and requires the host application to trust `WebhookMetadata#shop`/`request.shop` for tenant attribution without independent verification (e.g., checking that the shop is one the app is actually registered/installed for). This is a realistic scenario for typical `shopify_app`-style integrations that key data storage by the webhook's `shop` field.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signable content, or independently verify that `request.shop` corresponds to a shop with an active, stored installation/session before processing the webhook payload, rather than trusting the header value once the body-only HMAC passes.

### Proof of Concept
1. Install the app on `attacker.myshopify.com`; trigger any webhook topic so Shopify sends a request with a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's `client_secret`.
2. Capture `raw_body` and the `hmac-sha256` header from that request.
3. Replay a new HTTP request to the app's webhook endpoint with the identical `raw_body` and `hmac-sha256`, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged `shop` header [2](#0-1) ; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `raw_body` against the shared `client_secret` [5](#0-4) ; `Registry.process` dispatches the handler with `shop: request.shop == "victim.myshopify.com"` [6](#0-5) , even though the payload actually originated from the attacker's own shop.
