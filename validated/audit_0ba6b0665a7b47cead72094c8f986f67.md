### Title
Single global `challengePeriod` in `EvmHost.sol` applied uniformly to all counterparty state machines, unlike per-chain periods supported on the Substrate side - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.sol` stores a single, global `challengePeriod` value inside `HostParams` and exposes it via `challengePeriod()`. This one value is used to gate finality of *every* counterparty state machine whose commitments this host accepts, even though `_hostParams.stateMachines` can list many chains with materially different consensus/finality security assumptions (e.g. fast, low-validator-set EVM chains vs. slower, more Byzantine-resilient chains). This is architecturally identical to the reported MultiFlowPump bug class: a single hardcoded parameter (there, `LOG_MAX_INCREASE`/`LOG_MAX_DECREASE`; here, `challengePeriod`) is reused indiscriminately across heterogeneous entities (there, tokens with different volatility; here, state machines with different consensus security) that should each have their own risk-calibrated parameter.

### Finding Description
`HostParams.challengePeriod` is declared as a single `uint256` field, set once via `setHostParams`/`updateHostParams`, and read back via `challengePeriod()`: [1](#0-0) [2](#0-1) 

It is written unconditionally for the whole host in `updateHostParams` regardless of which state machines are configured: [3](#0-2) 

`HandlerV2.sol` then uses this single global value to gate finality/veto windows for *every* incoming timeout/proof for *any* state machine, comparing it only against the elapsed delay since the specific commitment's update time — it never varies by `message.height.stateMachineId`: [4](#0-3) [5](#0-4) 

By contrast, the Substrate/pallet-ismp side of the protocol explicitly models challenge periods per state machine via a `BTreeMap<StateMachine, u64>`, both when creating a consensus client and when updating it: [6](#0-5) [7](#0-6) [8](#0-7) 

This confirms the protocol's own design intent is per-counterparty-chain challenge periods, but the EVM host implementation collapses this into one universal constant for all counterparties supported by a given `EvmHost` deployment, exactly mirroring the reported bug class of "one-size-fits-all cap used for multiple heterogeneous assets."

### Impact Explanation
Because a single `EvmHost` can be configured to accept state commitments from multiple distinct state machines (`_hostParams.stateMachines` is an array), one global `challengePeriod`:
- Either sets the window too short for chains with weaker/slower finality guarantees or larger validator-set/fork risk, letting a forged or reorged state commitment's requests/timeouts/responses be processed by `HandlerV2.handlePostRequestTimeouts`/`handleGetRequestTimeouts` before the chain's real safety margin has passed — enabling forged message delivery or unsound timeout execution and consequent fund loss/griefing, or
- Sets the window too long for chains with fast, robust finality, unnecessarily delaying legitimate request delivery/timeouts, degrading bridge liveness/UX without any security benefit.

Either direction directly maps to the reportable categories: forged message delivery / unsound state commitment handling (too-short case) or a route effectively unable to deliver messages in a timely, correct manner (too-long case).

### Likelihood Explanation
This is reachable by any relayer submitting a `PostRequestTimeoutMessage`/`GetTimeoutMessage` (or any handler path gated by `challengePeriod`) for any of the multiple state machines an operator configures on one `EvmHost`. No privileged action is required beyond normal governance configuration of `stateMachines` (a routine, expected multi-chain deployment) — the vulnerability is inherent to the data model, not to any single malicious actor, and triggers as soon as more than one counterparty chain with differing security assumptions is added to the same host.

### Recommendation
Change `HostParams.challengePeriod` (and the corresponding `IHost.challengePeriod()`) from a single global `uint256` to a per-state-machine mapping (e.g. `mapping(uint256 stateMachineId => uint256 challengePeriod)`), analogous to the `BTreeMap<StateMachine, u64>` already used on the Substrate side. Update `HandlerV2.sol`'s timeout/proof handlers to look up the challenge period keyed by `message.height.stateMachineId` rather than calling the parameterless `host.challengePeriod()`, and update `updateHostParams`/governance messages to allow setting/updating periods per state machine.

### Proof of Concept
1. Operator configures one `EvmHost` with `stateMachines = [ChainA, ChainB]` where `ChainA` has fast finality/low reorg risk and `ChainB` has materially weaker finality guarantees, and sets a single `challengePeriod` sized for `ChainA`.
2. A relayer submits a state commitment update for `ChainB` that is later invalidated by a reorg/fork on `ChainB` (something the shorter, `ChainA`-sized challenge period does not protect against).
3. Before `ChainB`'s true safety margin elapses, `HandlerV2.handlePostRequestTimeouts` (or the post/response handlers) accept proofs against that commitment because `block.timestamp - host.stateMachineCommitmentUpdateTime(message.height) > host.challengePeriod()` is already satisfied using the too-short global value: [9](#0-8) 
4. This lets a relayer force through timeouts/requests based on a state commitment that is not actually final on `ChainB`, i.e. forged message delivery / unsound state commitment usage, while the same global value forces unnecessary delay for `ChainA` traffic.

        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();
