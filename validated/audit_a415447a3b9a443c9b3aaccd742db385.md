### Title
Webhook `shop` and `topic` headers are not covered by the HMAC, allowing tenant/topic spoofing via body replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, but `Registry.process` uses `request.shop` and `request.topic` — both pulled from unauthenticated headers — to route the webhook and identify the tenant. An unprivileged internet user who obtains one legitimately-signed webhook body/HMAC pair (trivially available by installing the target app on their own development store) can replay that exact body to the app's public webhook endpoint while forging the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers to any value, since those headers are never part of the signed payload.

### Finding Description
`HmacValidator.validate` verifies the request only against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body — none of the Shopify-supplied headers are included in the signable string: [2](#0-1) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from unauthenticated headers: [3](#0-2) 

`Registry.process` uses `request.topic` to select the handler and passes `request.shop` straight through to the handler as the tenant identifier, after only checking the HMAC of the body: [4](#0-3) 

The binding this breaks, expressed as an equality that should hold but does not:
`HMAC-verified bytes (raw body)` ⟺ `bytes acted on for tenant/topic routing (shop-domain header, topic header)`.

Because the header values are excluded from the signed content, any party who can produce (or capture) one valid `(raw_body, hmac)` pair — e.g., by installing the app on their own store and receiving a legitimate webhook — can resend that same body to the app's public webhook endpoint with a different `X-Shopify-Shop-Domain` header. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the data to the app's handler tagged with the attacker-chosen `shop`, `topic`, `webhook_id`, and `api_version`.

### Impact Explanation
This is a cross-tenant identity-binding violation: the app, following this gem's documented API (`WebhookMetadata#shop`), will process/persist data as belonging to whatever shop domain the attacker puts in the header, even though the signed payload was never actually generated for that shop. Depending on how the host application uses `WebhookMetadata.shop` (e.g., to look up a merchant record, key session storage, or trigger side effects scoped by shop), this enables injecting attacker-controlled webhook payloads into another merchant's tenant context — a cross-tenant access primitive. It also allows spoofing `topic` to invoke a different handler than the one the payload was actually signed for.

### Likelihood Explanation
Likelihood is high for any embedded app that exposes a single public webhook endpoint (the standard pattern documented for this gem). The attacker only needs: (1) their own store install to receive one legitimately HMAC-signed webhook body of a type they want to spoof, and (2) the ability to POST directly to the app's public webhook URL with custom headers — both of which are available to any unprivileged internet user/merchant, with no access to `api_secret_key`, access tokens, or any privileged credential.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, and ideally `webhook-id`/`api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the signed body, in `ShopifyAPI::Webhooks::Request#to_signable_string`. At minimum, `Registry.process` should not trust `request.shop`/`request.topic` for tenant/handler routing decisions unless they are covered by the verified signature.

### Proof of Concept
1. Install the target app on an attacker-owned store `attacker-shop.myshopify.com`. Trigger a webhook (e.g., `orders/create`) and capture the raw request body and the `X-Shopify-Hmac-Sha256` header Shopify sent — this pair is valid per `HmacValidator.validate` since it only checks the body: [5](#0-4) 
2. Replay a POST to the app's public webhook endpoint with the exact same body and `X-Shopify-Hmac-Sha256` value, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and, if desired, a different `X-Shopify-Topic`).
3. `Registry.process` passes HMAC validation (body unchanged) and invokes the registered handler with `shop: "victim-shop.myshopify.com"`: [6](#0-5) 
4. The host application processes/stores the attacker's payload as if it originated from `victim-shop`, achieving cross-tenant data injection without ever needing the app's `api_secret_key` or any merchant credentials.
