### Title
Consensus relayer rewards computed with the current `cost_per_block` over the entire unpaid backlog span, letting a relayer capture inflated (or under-collect fair) rewards around a rate change - (File: `modules/pallets/consensus-incentives/src/impls.rs`)

### Summary

### Finding Description
`pallet_consensus_incentives` pays relayers for delivering `ConsensusMessage`s based on how many blocks of consensus progress they proved, using a single governance-configured rate, `StateMachinesCostPerBlock`. The reward span is tracked with a "watermark," `LastRewardedHeight`, and is settled lazily: the reward for the *entire* unpaid span since the watermark is only computed and paid the next time some relayer submits a message for that state machine. [1](#0-0) 

The rate can be changed at any time via `update_cost_per_block`, and this call performs **no checkpoint**: it does not first pay out (or realize) the reward owed for the un-rewarded span accrued under the old rate before switching to the new one. [2](#0-1) 

When a relayer's `ConsensusMessage` is later processed, `calculate_reward` reads whatever `cost_per_block` is stored *at that moment* and multiplies it by `latest_height - baseline`, where `baseline` is the old watermark, i.e., the *entire* backlog since the last payout is priced at the current rate regardless of what the rate was during most of that span: [3](#0-2) 

This is structurally identical to the Backd `M-04` bug: `Minter`/`InflationManager` changed a pool's weight (`ammPoolWeight`) without calling `poolCheckpoint` on all affected pools first, so the next checkpoint distributed tokens as if the new weight had applied for the whole un-checkpointed period. Here, `update_cost_per_block` changes the reward rate without settling (checkpointing) the pending, un-rewarded block span first, so the next `on_executed` call applies the new rate retroactively to the whole backlog.

### Impact Explanation
Because the reward computation is fully retroactive over the unpaid span, and *any* relayer can trigger settlement simply by delivering the next consensus proof (`on_executed` → `process_message`), a relayer can profit from governance rate changes by controlling timing:
- If governance raises `cost_per_block`, a relayer that has withheld/delayed submitting a proof for a state machine with a large unpaid backlog (e.g. because delivery had been rare or the relayer intentionally waited) collects the entire backlog at the new, higher rate instead of the rate that was actually in force for most of that period, draining more BRIDGE from `TreasuryAccount` than governance intended. [4](#0-3) 
- Conversely, if governance lowers the rate, the relayer who accrued a large backlog at the old (higher) rate is shortchanged the moment someone submits the next proof, since the whole span is now priced at the lower rate — a value loss for whichever relayer would otherwise have been rewarded.

Since the reward source is the shared `TreasuryAccount`, and a relayer also mints an equal-value reputation asset from the inflated payout, this results in unbacked over-distribution of the treasury's funds (or the reputation asset) — the same class of loss/leak the Backd report is about, just triggered by relayer message timing instead of a Backd `poolCheckpoint` call. [5](#0-4) 

### Likelihood Explanation
`update_cost_per_block` is `IncentivesOrigin`-gated (governance), but exploiting the miscalculation requires no privilege at all: any relayer can decide when to submit a `ConsensusMessage`, and delivering consensus updates for chains with sparse traffic (long gaps between proofs) is a normal, unprivileged, expected relayer action. Anyone monitoring a pending governance proposal to change `cost_per_block` for a state machine with an accumulated unpaid backlog can withhold a ready proof until after the rate change lands, then submit it to capture the inflated retroactive reward. This mirrors the judge's reasoning in the referenced Backd report that "any individual could ... front-run/back-run" the rate change — making it a Medium/High-severity, realistically exploitable timing issue rather than a purely theoretical one.

### Recommendation
Checkpoint (settle) the reward owed for the pending span at the *current* rate before applying a new `cost_per_block`, e.g. inside `update_cost_per_block`/`remove_incentives`, advance `LastRewardedHeight` to the current `latest_commitment_height` (recording any accrued-but-unclaimed reward, or paying it out to a neutral/no-op destination) so a subsequent relayer message can only be rewarded for blocks that occur strictly after the rate change. Alternatively, store the rate that was active at each block span (or timestamp the rate change) so `calculate_reward` can prorate the backlog across the old and new rates instead of applying a single rate to the whole unpaid span.

### Proof of Concept
1. Governance sets `StateMachinesCostPerBlock[X] = 1` via `update_cost_per_block`. `LastRewardedHeight[X]` is `None`/stale, e.g. last paid at height 1000, and the chain's `latest_commitment_height` for `X` has since advanced to 2000 with no relayer having submitted a settling proof in between (no traffic/no incentive at the old low rate). [6](#0-5) 
2. A relayer observes the pending backlog and, seeing governance about to raise the rate to 100, waits.
3. Governance calls `update_cost_per_block(X, 100)` — no checkpoint occurs, `LastRewardedHeight` is untouched.
4. The relayer immediately submits (or has ready) a `ConsensusMessage` proving state at height 2000+; `on_executed`/`process_message`/`calculate_reward` computes `reward = (2000 - 1000) * 100 = 100,000` instead of the fair value if segmented (`1000` at old rate), transferring the inflated amount from `TreasuryAccount` and minting an equally inflated reputation asset. [7](#0-6)

	#[pallet::call]
	impl<T: Config> Pallet<T> {
		/// Update cost per block for a state machine
		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::update_cost_per_block())]
		pub fn update_cost_per_block(
			origin: OriginFor<T>,
			state_machine_id: StateMachineId,
			cost_per_block: <T as pallet_ismp::Config>::Balance,
		) -> DispatchResult {
			T::IncentivesOrigin::ensure_origin(origin)?;

			StateMachinesCostPerBlock::<T>::mutate(state_machine_id.clone(), |maybe_cost| {
				*maybe_cost = Some(cost_per_block);
			});

			Self::deposit_event(Event::<T>::StateMachineCostPerBlockUpdated {
				state_machine_id,
				cost_per_block,
			});

			Ok(())
		}

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}
