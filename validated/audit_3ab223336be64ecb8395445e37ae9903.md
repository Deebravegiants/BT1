Audit Report

## Title
Reward Tokens Permanently Lost When Pool Has Zero Staked Tokens - (File: `substrate/frame/asset-rewards/src/lib.rs`)

## Summary
`pallet-asset-rewards` ports the Synthetix `StakingRewards.sol` reward algorithm, and its `reward_per_token` function inherits the same zero-total-stake accounting gap: while `pool_info.total_tokens_staked == 0`, the function returns the stale `reward_per_token_stored` without accruing rewards for elapsed blocks, yet `reward_rate_per_block` continues to run against the fixed `expiry_block` deadline. Any block range during which the pool has zero stakers permanently consumes part of the reward budget without crediting it to any staker.

## Finding Description
`reward_per_token` short-circuits and returns `pool_info.reward_per_token_stored` unchanged whenever `total_tokens_staked.is_zero()`, skipping the accrual computation entirely [7](#0-6) . Whenever `update_pool_rewards` is subsequently called (from `stake`, `unstake`, or `harvest_rewards` via `update_pool_and_staker_rewards`), it unconditionally sets `new_pool_info.last_update_block = current_block_number()` [2](#0-1) , which silently "fast-forwards" through the zero-stake window without ever crediting the elapsed blocks to `reward_per_token_stored`. The reward computation is capped only by `last_block_reward_applicable`, which bounds by the fixed `expiry_block` and is never paused or extended by zero-participation periods [3](#0-2) . The only recovery mechanism, `cleanup_pool`, requires the pool to have zero stakers and returns the entire reducible balance to the admin, but does not distinguish or reconcile which portion of that balance corresponds to already-elapsed zero-stake dead time versus genuinely unclaimed rewards [6](#0-5) .

## Impact Explanation
Reward-asset tokens deposited into a pool (via `deposit_reward_tokens` or direct transfer) become permanently unaccounted-for whenever the pool experiences any period with `total_tokens_staked == 0`. This is a direct fund-accounting defect affecting the pool admin/creator, who funded the pool expecting `reward_rate_per_block * duration` to be distributable, but actual claimable rewards fall short by exactly the reward accrued during zero-stake windows. This matches an in-scope Substrate pallet implementation impact (incorrect reward accounting / fund loss within a FRAME pallet).

## Likelihood Explanation
The precondition — a period of zero stake — is trivially and routinely reachable by any unprivileged user: `stake` and `unstake` are both gated only by `ensure_signed` with no special origin required [8](#0-7) [9](#0-8) . A newly created pool with nobody staking immediately, or the last remaining staker fully unstaking, both drive `total_tokens_staked` to zero, which is a normal and expected occurrence rather than an edge case requiring privileged action.

## Recommendation
Track reward accrual so zero-stake block ranges do not silently consume the reward budget — for example, by tracking a separate "last non-zero-stake update block," skipping (not merely capping) accrual during zero-stake spans, dynamically extending `expiry_block` by the length of zero-stake spans, or allowing precise reclamation of only the unaccrued portion corresponding to zero-participation windows rather than requiring full pool teardown via `cleanup_pool`.

## Proof of Concept
1. Admin calls `create_pool` with `reward_rate_per_block = R` and `expiry_block = E`, and funds the pool via `deposit_reward_tokens`.
2. No account calls `stake` for `N` blocks, so `total_tokens_staked` remains `0`; `reward_per_token` returns the unchanged `reward_per_token_stored` [7](#0-6)  each time it is invoked in this window.
3. Alice calls `stake(pool_id, amount)`, which invokes `update_pool_and_staker_rewards` → `reward_per_token` → `update_pool_rewards`, jumping `last_update_block` straight to the current block without having accrued reward for the `N` zero-stake blocks [10](#0-9) .
4. Once the pool reaches `expiry_block`, sum the total rewards claimable by all stakers via `harvest_rewards`; this total is less than `R * (E - creation_block)` by exactly `R * N`, and that `R * N` worth of reward tokens sit in the pool account unattributed to any staker, recoverable only if the admin later fully drains stakers and calls `cleanup_pool` [6](#0-5) .

			let who = ensure_signed(origin)?;

			let pool_info = Pools::<T>::get(pool_id).ok_or(Error::<T>::NonExistentPool)?;

				pool_info.reward_asset_id.clone(),
				&pool_info.account,
				Preservation::Expendable,

				pool_info.reward_asset_id,
				&pool_info.account,

				Preservation::Expendable,

				T::Consideration::drop(cost, &who)?;
			}

			Pools::<T>::remove(pool_id);

			Self::deposit_event(Event::PoolCleanedUp { pool_id });

			Ok(())
