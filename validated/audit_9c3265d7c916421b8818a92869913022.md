### Title
Webhook `shop` Identity Not Bound to HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature that `Utils::HmacValidator` verifies covers exclusively the body bytes. The `shop` value used by `ShopifyAPI::Webhooks::Registry.process` and handed to every app's `WebhookHandler` as the tenant identifier is read straight from the unauthenticated `shopify-shop-domain` header and is never included in the signed data. `hmac_valid(raw_body)` can be `true` while `shop_header != shop_the_body_actually_belongs_to`, breaking the intended binding between "verified sender" and "shop the webhook is attributed to."

### Finding Description
`Request#shop` is derived purely from a header: [1](#0-0) 

The signable string used for HMAC verification is only the raw body, not the shop header: [2](#0-1) 

`HmacValidator.validate` computes/compares the signature strictly against `to_signable_string`, i.e. the body alone: [3](#0-2) 

`Registry.process` accepts the request once the (body-only) HMAC check passes, then forwards the **unauthenticated** `request.shop` value straight into `WebhookMetadata`, which is the sole tenant identifier the app-level handler receives: [4](#0-3) [5](#0-4) 

The gem's own documentation instructs integrators to trust `data.shop` as the shop-scoping key for downstream business logic (e.g., enqueuing per-shop jobs): [6](#0-5) 

Because `shop` is not part of the signed payload, the identity binding the gem is supposed to enforce — *"the shop this webhook is attributed to" == "the shop Shopify actually signed this payload for"* — does not hold. Any request whose body produces a valid HMAC (using the app's real secret, e.g. a genuine webhook a merchant legitimately receives for their own shop) will pass `HmacValidator.validate` regardless of what `shop-domain` header value accompanies it. An attacker who operates their own shop (an "unprivileged" tenant relative to other merchants using the same app) can capture a real webhook delivered to their own endpoint, then replay the identical body/HMAC pair to the app's webhook endpoint while substituting a different shop's domain in the `shopify-shop-domain` header (or `x-shopify-shop-domain`). This is trivial for topics whose payload doesn't inherently encode the shop (e.g., `app/uninstalled`, `shop/update` variants, or any topic whose JSON body is shop-agnostic or attacker-influenced, such as content the attacker themselves created in their own store and that gets echoed into a webhook body, e.g. product/order webhooks where the attacker fully controls the body content in their own shop).

### Impact Explanation
This breaks the shop/tenant identity boundary the gem is meant to enforce for webhook consumers. Since `WebhookMetadata#shop` is the only tenant key surfaced to the app, and the docs explicitly tell developers to key per-shop side effects (job enqueue, per-shop record updates, session/token lookups, uninstall/data-deletion handling) off of it, a forged `shop` value lets an attacker who controls one tenant (their own shop) inject webhook events attributed to a victim shop of their choosing. Depending on how the host app uses `data.shop` (very commonly to look up the stored per-shop access token/session, update per-shop state, or process `app/uninstalled` cleanup), this can result in cross-tenant data corruption, spoofed uninstall/reinstall processing, or webhook-driven actions executed against a shop the attacker does not own. This matches the "cross-tenant access" class of impact.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP POST to the app's public webhook endpoint (no credentials, no `api_secret_key`, no access token) plus a legitimate, attacker-owned shop that installs the app to legitimately receive at least one real, validly-signed webhook whose body the attacker controls or that is shop-agnostic. Both are attainable by an ordinary unprivileged internet user/merchant, making this practically reachable, not merely theoretical.

### Recommendation
Bind the `shop` identity into the signed material, or independently authenticate it, before it is trusted:
- Include the `shop-domain` header (and ideally `topic`/`webhook-id`) in `Request#to_signable_string`, matching them against a value Shopify actually signs, or
- Cross-validate `request.shop` against a shop value embedded in the verified body (where the topic guarantees one), or
- At minimum, document/require host apps to independently confirm `data.shop` corresponds to a shop with a currently valid, previously-established session/webhook registration before using it to key any tenant-scoped side effect, and provide a gem-level helper to perform that check.

### Proof of Concept
1. App developer follows `docs/usage/webhooks.md` and implements a handler that keys per-shop side effects off `data.shop`, per the documented example:
```ruby
def handle(data:)
  perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
end
```
2. Attacker registers their own shop `attacker.myshopify.com` with the target app and receives a legitimate webhook (valid `hmac-sha256`, body `B`) for a topic whose body content the attacker fully controls or is shop-agnostic (e.g. a custom product/page they created).
3. Attacker replays the exact same raw body `B` and `hmac-sha256` header to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes the HMAC over `B` only (`Request#to_signable_string`), which matches, so `Registry.process` proceeds:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
```
5. The handler receives `data.shop == "victim-shop.myshopify.com"` despite the payload never having been signed for that shop, and performs shop-scoped side effects under the wrong tenant.
