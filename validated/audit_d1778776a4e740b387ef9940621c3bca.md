### Title
Session-state feedback loop causes SignupEnded (or last outgoing message) to be re-delivered as if newly occurring - (File: `orb-relay-client/src/client.rs`)

### Summary
The reported Frax bug is a "feedback loop" class of defect: a payable/receive path re-consumes a value that the same contract already accounted for, because the code that emits a value back to a peer does not distinguish "already-finalized/committed state" from "a fresh event." `orb-relay-client`'s `PollerAgent` exhibits the same structural pattern: on receipt of `RequestState`, it unconditionally re-sends `self.last_message` — the last *outgoing* application message, which can be a terminal/one-shot signup event such as `SignupEnded` — back onto the wire, and separately, `replay_pending_messages` re-sends every buffered pending message on reconnect. Neither path checks whether the message was already delivered/consumed, so a stateful, one-time event can be redelivered and reprocessed by the peer as if it were new.

### Finding Description
`PollerAgent::main_loop` stores every outgoing payload as `self.last_message` [1](#0-0) . When the peer sends `self_serve::app::v1::RequestState`, the agent responds by unconditionally re-transmitting `self.last_message.clone()` regardless of what that message semantically represents: [2](#0-1) .

Because `last_message` is simply "whatever was sent most recently" — which can be a one-shot, terminal signup lifecycle event like `SignupEnded { success, failure_feedback }` (confirmed by the manual test harness that sends `SignupEnded` right after `AnnounceOrbId`, [3](#0-2) ) — any `RequestState` message received after a signup has concluded causes the orb to blindly re-emit the terminal `SignupEnded` state to the app. There is no notion of "this event has already been consumed/committed" the way `moveWithheldETH`'s ETH transfer has no notion of "this value has already been credited as frxETH."

A second, related path is `replay_pending_messages`, invoked both automatically on every reconnect (`main_loop` line 412) and explicitly via `Command::ReplayPendingMessages` [4](#0-3) , and driven by the public `graceful_shutdown`/`replay_pending_messages` API [5](#0-4) . This walks the whole `pending_messages` map and resends every entry to the wire without any idempotency/consumption check on the receiving side (`handle_message` only queues onto a bounded ring buffer with no dedup by `seq`) [6](#0-5) . If an ack was actually received by the relay/backend but the local ack channel was dropped/timed out (explicitly acknowledged as a known race in the code comment "receiver dropped ... need to increase the timeout"), the message is retried and can be processed twice downstream, mirroring the ETH-sent-back-and-reprocessed pattern from the report.

### Impact Explanation
Signup completion (`SignupEnded`) and orb identification (`AnnounceOrbId`) are directly tied to the self-serve signup state machine used by the companion app to determine whether a signup succeeded/failed and to bind an app session to a physical orb. A duplicated or misattributed `SignupEnded`/`AnnounceOrbId` delivery — triggered purely by benign app-side `RequestState` polling or by a relay reconnect replay — can cause the app to believe a *new* signup event occurred (e.g. re-displaying "signup succeeded" for a session that already concluded, or re-binding orb/session identity), producing state confusion analogous to "double accounting" of a single real-world event. This is a state-integrity/session-binding issue rather than a funds-loss issue, but it maps onto the same "feedback re-processed as new" root cause the external report flags as Medium severity.

### Likelihood Explanation
`RequestState` and reconnects are ordinary, frequent occurrences in the self-serve flow (the app can legitimately request state at any time, and network reconnects are commonplace on Orb/companion-app WiFi/BLE links), so the redelivery path is reachable without any privileged action — it requires only normal, unprivileged app-side interaction with the relay channel. The likelihood of triggering redelivery is high; the question is only whether the receiving side's business logic is robust to duplicate terminal events (which is not verifiable from this code alone, since app-side handling of `SignupEnded` is outside `orb-core`).

### Recommendation
- Do not treat `RequestState` as "resend arbitrary last outgoing message." Maintain an explicit `current_state` distinct from `last_message` that represents only replayable session/connection-state (e.g. `NoState`, "connected/idle"), and exclude one-shot lifecycle events like `SignupEnded` from being replayed via `RequestState`.
- Add per-message idempotency: tag stateful/terminal events with a monotonically increasing signup/session identifier and have receivers ignore duplicates of an already-consumed terminal event, instead of relying on transport-level dedup.
- In `replay_pending_messages`, only replay messages that are confirmed un-acked by the server (not just locally un-acked), or make redelivery a no-op for already-fully-delivered payloads once the relay server confirms receipt independent of local ack channel state.

### Proof of Concept
1. Orb completes a signup and sends `self_serve::orb::v1::SignupEnded { success: true, .. }` to the app via `Client::send` (as in `after_signup`, [7](#0-6) ); `PollerAgent.last_message` is now set to this payload.
2. Some time later (new signup session or idle state), the app sends `self_serve::app::v1::RequestState {}` — a message with no privilege requirement.
3. `PollerAgent::main_loop`'s `RequestState` branch fires and resends `last_message` (the previous `SignupEnded`) to the app [8](#0-7) .
4. The app, expecting a fresh session/connection state, instead receives a stale terminal `SignupEnded` and may act on it as if a new signup just concluded — a re-processing of already-finalized state, structurally identical to the reported bug class of "state sent back and reprocessed as new."

        &self,
        payload: RelayPayload,
        message_buffer: &Arc<Mutex<VecDeque<RelayPayload>>>,
    ) -> Result<()> {
        let mut buffer = message_buffer.lock().await;
        if buffer.len() >= self.config.max_buffer_size {
            // Remove the oldest message to maintain the buffer size
            let msg: Vec<RelayPayload> = buffer.drain(0..1).collect();
            tracing::warn!("Buffer is full, removing oldest message: {msg:?}");
        }
        buffer.push_back(payload);
        Ok(())
    }
