### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are trusted but not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw HTTP body, while the shop, topic, and webhook-id identifiers used by `Registry.process` to route and tag incoming webhook data are read directly from unauthenticated request headers. This breaks the binding `hmac == HMAC(shop, topic, webhook_id, body)` that a webhook consumer implicitly relies on, allowing any header value to be substituted after a valid signature has been produced for a *different* combination of shop/topic/body.

### Finding Description
`Registry.process` accepts a webhook once `Utils::HmacValidator.validate(request)` succeeds: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute the expected signature purely from `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — the `shop`, `topic`, and `webhook_id` accessors are populated straight from HTTP headers and never enter the signed bytes: [3](#0-2) 

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` **is** part of `to_signable_string` and therefore cryptographically bound to the signature: [4](#0-3) 

Once HMAC validation passes, `Registry.process` forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` straight into `WebhookMetadata`, which is the tenant/topic identity the host application's handler acts on: [5](#0-4) 

This is the same class of bug as the referenced report: a field that is acted upon (there, the timelock target; here, the shop/topic identity used for tenant routing) is not covered by the integrity check (there, `_timelockMint`'s unconditional overwrite; here, the HMAC that only signs the body). The equality that should hold — `verified(shop, topic, webhook_id, body) == acted_on(shop, topic, webhook_id, body)` — instead only verifies `body`, letting an attacker vary `shop`/`topic`/`webhook_id` freely while keeping a signature that is genuinely valid for that `body`.

### Impact Explanation
An unprivileged internet user who legitimately installs the app on their own store receives real, correctly-signed webhooks from Shopify for their own shop. Because the signature never binds `shop-domain`/`topic`/`webhook-id`, they can replay that same signed body to the app's webhook endpoint with a forged `shopify-shop-domain` header naming a victim shop (and/or a different `topic`/`webhook-id`). `Registry.process` will accept it as valid (`HmacValidator.validate` only checks the body) and dispatch it to the handler tagged as belonging to the victim tenant. Any host application that uses `WebhookMetadata#shop` to look up the target merchant's session/access token, or that stores/mutates per-shop state keyed by that value, is exposed to cross-tenant data injection/corruption — meeting the Impact bar of cross-tenant access.

### Likelihood Explanation
Moderate-to-high: exploitation requires no secrets beyond having a working app installation on any shop (which is exactly the "unprivileged internet user with an app install" threat model), plus the ability to send a forged HTTP request to the app's public webhook endpoint with modified headers and a captured, still-valid body/HMAC pair. No access to `api_secret_key`, tokens, or the target shop is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signed content used for verification (or otherwise cryptographically bind them, e.g. re-derive/verify them independently against the shop's own registered webhook configuration) rather than trusting header values that fall entirely outside `to_signable_string`. At minimum, document and enforce that `WebhookMetadata#shop` must never be trusted as an authenticated tenant identifier unless it is cross-checked against an out-of-band trusted source (e.g., a shop the app has an active session for) before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a real webhook, e.g. body `{"id":1}` with header `shopify-shop-domain: attacker.myshopify.com` and a valid `shopify-hmac-sha256` computed over that body only.
2. Attacker replays the identical body/HMAC to the app's webhook endpoint but changes the header to `shopify-shop-domain: victim.myshopify.com` (and optionally a different `shopify-topic`/`shopify-webhook-id`).
3. `Webhooks::Request.new` parses the forged headers; `HmacValidator.validate` in `Registry.process` succeeds because `to_signable_string` (`lib/shopify_api/webhooks/request.rb:36-38`) only covers `@raw_body`, which is unchanged.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) dispatches `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", ...)` to the handler, which the host application treats as an authentic event for `victim.myshopify.com`.
