### Title
Webhook shop-domain header is trusted for handler dispatch but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body, while the `shop` (and `topic`) values used to dispatch the webhook to handler code are read from unauthenticated HTTP headers. This breaks the identity binding `authenticated_bytes == acted_upon_identity`: the bytes verified by the HMAC are `raw_body`, but the shop identity acted upon by `Registry.process` and forwarded to the app's handler is `headers["x-shopify-shop-domain"]`, which carries no cryptographic binding to that signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `Request#shop` is pulled straight from an unauthenticated header: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e., the body only) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

Because the shop header sits outside the signed payload, any entity able to obtain one validly-signed webhook body/HMAC pair (trivially available to any merchant who installs the app on their own store and receives a real webhook) can replay the exact `raw_body` + `hmac` bytes to the app's webhook endpoint while substituting `x-shopify-shop-domain` with a different, victim merchant's domain. `HmacValidator.validate` still succeeds because it only checks the body signature, and the handler receives `WebhookMetadata#shop` pointing at the victim shop.

### Impact Explanation
Because the gem's `WebhookMetadata#shop` value is presented to host application handler code as the verified merchant identity for the webhook (it is populated only after `Utils::HmacValidator.validate` succeeds), an application built against this documented API has no signal from the gem indicating that `shop` is unauthenticated relative to that signature. An attacker who has legitimately received a signed webhook for their own store can replay it against another merchant's tenant context, causing the host application to attribute attacker-controlled webhook data (order/customer/inventory events, etc.) to a different shop's tenant. This crosses a tenant boundary using only credentials the attacker already legitimately possesses (their own shop's webhook deliveries), matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is limited by the precondition that the attacker must already be a legitimate merchant/app installer receiving real webhook deliveries (to obtain a valid raw_body+hmac pair), and by the fact that many host applications additionally cross-check the shop domain against their own session store before trusting it — a mitigation entirely outside this gem. Within the gem's own guarantees, however, nothing prevents the replay, and the `Registry`/`WebhookMetadata` API surface implies `shop` is trustworthy once `process` succeeds.

### Recommendation
Include the shop domain (and ideally topic) in the HMAC-signed material, or explicitly document that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host application against a known/installed shop record before being used for tenant-scoped operations. Alternatively, have `HmacValidator`/`Request` bind the header-derived `shop` value into the signable string so a body signed for shop A cannot be replayed under shop B's header.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and receives a real webhook delivery: body `B`, headers including `x-shopify-hmac-sha256: H` (valid for `B` with the app's secret) and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker sends a new HTTP request to the app's webhook endpoint with the identical body `B` and identical `H`, but with `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and it matches `H`, so validation passes (see `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/registry.rb:190`).
4. `Registry.process` builds `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed(B), ...)` and invokes the app's handler, which now believes this attacker-controlled payload originated from `victim.myshopify.com`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
