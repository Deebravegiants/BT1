### Title
Unbounded chunked-accrual loop in `global_sync` permanently freezes a dormant market - (File: contracts/pool/src/interest.rs)

### Summary
`global_sync` accrues interest in a `while` loop that iterates once per `MAX_COMPOUND_DELTA_MS` of elapsed time since `last_timestamp`. The iteration count is `elapsed_ms / MAX_COMPOUND_DELTA_MS` and grows without bound as time passes. Once a market goes untouched long enough that the chunk count exceeds the Soroban CPU/memory budget, every entrypoint that synchronizes the market traps on budget exhaustion — and since `elapsed_ms` only ever increases, the market can never recover. This is the CWE-835 (excessive-resource-consumption loop) analog mapped onto the pool's millisecond-chunked accrual.

### Finding Description
`global_sync` is called from the pool's operation dispatch (supply/withdraw/borrow/repay and `update_indexes`) whenever `cache.needs_accrual()` is true. Its loop body reads `cache.elapsed_ms()` once, then iterates `remaining / MAX_COMPOUND_DELTA_MS` times, each iteration invoking `accrue_chunk` → `accrue_step` (fixed-point exponentiation/rate math in `common/src/rates/compound.rs`) plus three cache writes (`set_borrow_index`, `set_supply_index`, `accrue_revenue`), which read and write contract storage. [1](#0-0) 

Two properties make this a one-way door:

1. **Monotonic elapsed time**: `elapsed_ms = current_timestamp - last_timestamp`. A failed accrual reverts, so `last_timestamp` is never advanced; the next call faces a strictly larger `remaining`. There is no admin or governance escape hatch that sets the index directly or jumps `last_timestamp` without running the loop.
2. **No partial progress**: the loop is all-or-nothing within one transaction — `cache.mark_accrued()` only runs after the loop completes. A caller cannot chip away at the backlog in multiple transactions.

The codebase itself acknowledges the boundary: `certora/pool/spec/README.md` explicitly lists "Unbounded multi-year accrual" as out of scope for the proofs, and `docs/explanation/threat-model.md` notes "bounded chunks do not make cadence neutral" — i.e., the chunk bound limits per-step numeric error, not iteration count. [2](#0-1) [3](#0-2) 

### Impact Explanation
Permanent freezing of user funds in any market that goes dormant past the budget-execution threshold. All suppliers' underlying tokens remain custodied by the pool contract but `withdraw` can never execute because `global_sync` runs before position settlement and always exceeds the budget. The same applies to `repay`/`liquidate` legs touching that market, so borrowers' collateral in other markets can also become effectively unseizable (a liquidation that repays a leg in the frozen market aborts). Impact severity: permanent freeze of all funds in the affected market — qualifying under the accepted-impact list.

### Likelihood Explanation
- Reachable by an unprivileged address: any caller invoking `update_indexes` (or `supply`, `withdraw`, `repay`) on the dormant market hits the loop. No attacker setup is required — the condition is created by ordinary market dormancy (a low-utilization listed market with no ops for an extended period), and an attacker can also deliberately pick the most stale market and be the one to trigger/confirm the freeze.
- I could not read the concrete value of `MAX_COMPOUND_DELTA_MS` (`common/src/rates/mod.rs` re-exports it from the rate engine); the feasibility gap depends on it and on per-chunk `accrue_step` cost. If the chunk is small (e.g., minutes/hours to keep fixed-point compounding accurate), the dormancy window needed to blow the ~Soroban CPU budget is correspondingly short. This is the main uncertainty in sizing severity; conservatively rated Medium, upgrading to High if the budget-overflow dormancy window is on the order of weeks.
- This is not a "fail-closed DoS" reject: the caller's own transaction failing is not the issue — the state itself becomes permanently unexecutable for everyone, including all other users' funds.

### Recommendation
- Cap total accrual work per call: if `elapsed_ms` exceeds a bound (e.g., `N * MAX_COMPOUND_DELTA_MS` chosen so `N` chunks provably fit the budget), accrue `N` chunks, advance `last_timestamp` by `N * MAX_COMPOUND_DELTA_MS`, commit, and return — letting successive calls make progress instead of reverting.
- Alternatively/additionally, treat over-length gaps as a single capped step (e.g., clamp the effective delta or use the linear rate without compounding beyond the safe domain), documenting the interest-rate approximation for extreme dormancy.
- Ensure at least one permissionless entrypoint (`update_indexes`) can always make bounded progress so no market state is unreachable.

### Proof of Concept
1. Governance lists market M (or use any existing market). No operations touch M; `last_timestamp` stays at listing time.
2. Wait until `elapsed_ms / MAX_COMPOUND_DELTA_MS` exceeds the number of `accrue_chunk` iterations fitting the transaction budget (function of the chunk constant — see Likelihood caveat).
3. Any unprivileged caller invokes `pool.update_indexes(hub_asset_M)` (or `supply`/`withdraw`/`repay` on M).
4. `global_sync` enters the `while` loop, exhausts CPU budget partway, transaction reverts; `last_timestamp` unchanged.
5. Repeat: every subsequent call has a strictly larger `remaining`, so the market is permanently frozen — suppliers cannot withdraw, and liquidation legs touching M abort.

Approximate sketch:

```rust
// after dormancy > threshold:
let res = pool_client.try_update_indexes(&hub_asset(market));
assert!(res.is_err()); // budget exhausted inside global_sync

// last_timestamp never advanced -> gap only grows
let state = pool_client.get_sync_data(&hub_asset(market)).state;
assert_eq!(state.last_timestamp, listing_time_ms);

// supplier withdrawal path reverts the same way
let res = pool_client.try_withdraw(&supplier, &hub_asset(market), &amount, &supplier);
assert!(res.is_err());
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```
