This confirms the vulnerability. `Registry.process` calls `Utils::HmacValidator.validate(request)` which only signs `request.to_signable_string` — i.e., `@raw_body` [1](#0-0) . The `shop` (and `topic`, `webhook_id`, `api_version`) accessors read straight from unauthenticated HTTP headers [2](#0-1) , and `Registry.process` forwards that unauthenticated `request.shop` directly into `WebhookMetadata` passed to the app's handler [3](#0-2) .

### Title
Webhook `shop` (tenant) identifier is not covered by the HMAC signature, allowing cross-tenant webhook body replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string solely from the raw JSON body, while `shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers that are never included in the signed payload. `Registry.process` trusts `request.shop` unconditionally to identify the tenant for the webhook handler, breaking the equality `shop authenticated-by-HMAC == shop delivered-to-handler`.

### Finding Description
`HmacValidator.validate` verifies the HMAC over `verifiable_query.to_signable_string` [4](#0-3) . For webhook requests, `to_signable_string` returns only `@raw_body` [1](#0-0) . The `shop` value, however, is taken from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed bytes at all [2](#0-1) .

`Registry.process` validates the HMAC and then, without any additional binding check, builds `WebhookMetadata` using `request.shop` as the tenant identifier handed to the app's handler [3](#0-2) :
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
```
Because the gem's own `HmacValidator.validate(request)` check "passes" as long as the body bytes match a signature produced with the shared `api_secret_key`, and that secret is identical for every shop/tenant of the app (it is the app's client secret, not a per-shop secret), any actor who can obtain one genuine `(raw_body, hmac)` pair — e.g., by installing the app on their own shop and capturing a webhook it legitimately receives — can resend that exact body and signature to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because it never looked at the header, and `Registry.process` will hand the attacker-chosen `shop` value, together with the captured body, to the app's handler as if it were an authentic webhook for that victim shop.

This breaks the identity binding the report's rule set is describing: "a field acted on [`shop`] but not covered by the HMAC."

### Impact Explanation
This enables cross-tenant data injection: a host application built on this gem's documented webhook API (`ShopifyAPI::Webhooks::Registry.process`) will process attacker-controlled webhook bodies under an arbitrary victim shop's identity. Depending on how the host app uses the `shop`/body pair (e.g., updating orders, customer data, or GDPR redaction records keyed by `shop`), this can lead to cross-tenant data corruption or unauthorized actions attributed to a victim's shop — matching the "cross-tenant access" High/Critical impact category.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the target app on a shop they control (a normal, low-privilege step available to any merchant/developer) to legitimately receive one genuine webhook, and the ability to send arbitrary HTTP requests to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or TLS interception is required, since the shared secret is only used to validate body bytes that the attacker replays verbatim.

### Recommendation
Include the `shop` domain (and ideally `topic`, `webhook_id`, `api_version`) in the HMAC-signable string for webhook requests, or otherwise cryptographically bind the header-derived `shop` to the signed body before handing it to the handler. At minimum, the library should document/enforce that host apps must independently verify that `request.shop` corresponds to a shop for which they have an active installation/session before trusting `WebhookMetadata#shop`, and `to_signable_string` in `lib/shopify_api/webhooks/request.rb` should be updated so replay across tenants is not possible with only body+signature.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), legitimately receiving a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared `api_secret_key`.
2. Attacker sends a POST request to the app's webhook endpoint with:
   - `x-shopify-hmac-sha256`: the captured, still-valid signature
   - body: the captured, unmodified raw body
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (or any other tenant string)
   - `x-shopify-topic`: unchanged
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (headers present) [5](#0-4) .
4. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only and matches, since the body/signature pair is untouched [6](#0-5) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, despite this webhook never having originated from Shopify for that shop [7](#0-6) .
