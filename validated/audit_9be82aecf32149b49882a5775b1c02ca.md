### Title
Unbounded per-block stake-reward partition size defeats the partitioned-rewards DoS mitigation - (File: runtime/src/bank/partitioned_epoch_rewards/mod.rs)

### Summary
Agave's partitioned epoch-rewards distribution was explicitly designed to fix the exact bug class described in the Y2K `rolloverQueue` report: instead of paying out rewards to every stake account in a single slot (an unbounded, attacker-inflatable loop), rewards are chunked into `num_partitions` blocks and only `partitioned_rewards_stake_account_stores_per_block()` accounts are meant to be processed per block. However, the block-count computation in `Bank::get_reward_distribution_num_blocks` clamps the number of partitions to at most 10% of the epoch's slots, independent of how large the stake-account population becomes. Once the number of reward-eligible stake accounts exceeds `stake_account_stores_per_block * (slots_per_epoch / 10)`, the *per-block* partition size necessarily grows past the intended cap, re-introducing an unbounded-work-per-block situation analogous to the `rolloverQueue` growing without bound in the original report.

### Finding Description
The reward-partitioning mitigation lives in `runtime/src/bank/partitioned_epoch_rewards/mod.rs`: [1](#0-0) 

```rust
pub(super) fn get_reward_distribution_num_blocks(
    &self,
    rewards: &PartitionedStakeRewards,
) -> u64 {
    let total_stake_accounts = rewards.num_rewards();
    if self.epoch_schedule.warmup && self.epoch < self.first_normal_epoch() {
        1
    } else {
        const MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH: u64 = 10;
        let num_chunks = total_stake_accounts
            .div_ceil(self.partitioned_rewards_stake_account_stores_per_block() as usize)
            as u64;

        // Limit the reward credit interval to 10% of the total number of slots in a epoch
        num_chunks.clamp(
            1,
            (self.epoch_schedule.slots_per_epoch / MAX_FACTOR_OF_REWARD_BLOCKS_IN_EPOCH).max(1),
        )
    }
}
```

`num_chunks` is the number of blocks *needed* to keep each block's share at or below the baseline (`MAX_PARTITIONED_REWARDS_PER_BLOCK` = 4096, per `accounts-db/src/partitioned_rewards.rs`), but the final `.clamp(...)` silently overrides that need once `num_chunks` exceeds 10% of the epoch's slots. The number of partitions returned is then used directly to build `partition_indices` (one `Vec<usize>` per block) in `begin_partitioned_rewards` / `distribute_partitioned_epoch_rewards`: [2](#0-1) [3](#0-2) 

Each block then unconditionally processes the entire set of indices assigned to its partition in `store_stake_accounts_in_partition`, with no secondary cap on the number of accounts stored within a single block: [4](#0-3) 

So, if the total number of reward-eligible stake accounts grows past `stake_account_stores_per_block * (slots_per_epoch / 10)`, the number of partitions stays capped at `slots_per_epoch / 10`, and each partition's `indices.len()` grows proportionally larger than the intended per-block baseline — meaning a single validator, in a single slot, must run `store_stake_accounts_in_partition` (which loads/mutates a stake account, calls `build_updated_stake_reward`, and eventually `store_accounts`) for far more accounts than the design's stated 4096-per-block target. This is structurally the same defect as the reported `rolloverQueue`: a size limit intended to bound per-round work is nullified once the underlying collection (here, the count of stake accounts) is inflated beyond the designer's assumed scale, and the "queue" is still processed to completion in bounded wall-clock slots regardless of size.

### Impact Explanation
If reached, this would force whichever validator is leader during the affected reward-distribution slot(s) to perform vastly larger-than-budgeted account loads/stores and possibly to overshoot per-slot time/compute expectations, risking slow block production, missed slots, or in the worst case a bank/replay stall while all cluster nodes replay the same oversized partition deterministically (this is consensus code, not leader-only work — every replaying validator must process the same partition). Because the partition sizing directly drives `store_stake_accounts_in_partition`'s workload and this runs in `distribute_partitioned_epoch_rewards` during normal bank freeze/commit, an oversized partition affects the whole cluster's block-processing time for that slot, which is a liveness/DoS-class impact rather than an isolated leader inconvenience.

### Likelihood Explanation
Exploitability is gated by the same economic friction the Sherlock reviewers debated for the original bug (`3xHarry`'s rebuttal about `minDeposit` cost): each additional stake account requires funding a real, rent-exempt `StakeStateV2` account. Whether this fully prevents the attack depends on:
- whether protocol-level minimum-delegation requirements (referenced by feature flags such as `minimum_delegation`-related entries in `feature-set/src/lib.rs`, which I was not able to fully inspect before running out of iterations) block low-value/zero-effective-stake accounts from being reward-eligible and thus counted in `rewards.num_rewards()`, and
- the current mainnet-scale ratio of stake accounts to `slots_per_epoch / 10` headroom, which I could not fully quantify from the indexed code.

I could not confirm within the available searches whether this clamp has already been recognized/tracked as an accepted design trade-off (similar to the sponsor's "acknowledged" stance in the original Y2K report) or whether an additional per-block hard cap exists elsewhere that I did not locate. This should be treated as a plausible but not fully confirmed liveness risk; further investigation (e.g., a Devin session with full repository access) would be needed to check for any additional bound on `indices.len()` per partition and to confirm the effective minimum-stake economic cost of adding reward-eligible stake accounts at scale.

### Recommendation
Add a hard per-partition/per-block cap on the number of stake accounts processed in `store_stake_accounts_in_partition` (e.g., bound `indices.len()` to `partitioned_rewards_stake_account_stores_per_block()` regardless of the `slots_per_epoch / 10` block-count clamp), and instead let the number of *epochs*/*extra distribution intervals* grow, or explicitly document and monitor the stake-account-count threshold at which the 10%-of-epoch clamp begins to violate the per-block budget, so that per-block work stays bounded independent of total stake-account population growth.
