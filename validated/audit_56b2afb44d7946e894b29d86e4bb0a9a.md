### Title
PodGroup/CompositePodGroup `spec.PriorityClassName` and `spec.Priority` can be escalated on Update without re-validation - ([File: plugin/pkg/admission/priority/admission.go])

### Summary
`Plugin.Admit` only invokes `admitPodGroup`/`admitCompositePodGroup` (which call `establishPriority` → `resolvePriorityClass`) when `operation == admission.Create`; for `admission.Update` it falls through to `return nil` at lines 114-123. The corresponding validation functions `ValidatePodGroupUpdate` and `ValidateCompositePodGroupUpdate` in `pkg/apis/scheduling/validation/validation.go` only call `apivalidation.ValidateObjectMetaUpdate` and never check whether `spec.PriorityClassName`/`spec.Priority` changed. As a result, a namespaced user who is authorized to `update` their own PodGroup/CompositePodGroup can freely rewrite `spec.PriorityClassName` (e.g. to `system-cluster-critical`) and `spec.Priority` post-creation with no admission or validation check ever confirming the priority class exists, is permitted, or matches the referenced class's value.

### Finding Description
`Plugin.Admit` dispatches on resource and operation: [1](#0-0) 
For `podGroupResource` and `compositePodGroupResource`, only `admission.Create` triggers `admitPodGroup`/`admitCompositePodGroup`; any `admission.Update` request returns `nil` immediately, skipping `establishPriority`/`resolvePriorityClass` entirely — unlike `podResource`, which explicitly handles both `Create` and `Update` (lines 109-113) and includes update-specific logic in `admitPod` (lines 157-173) to preserve/prevent priority tampering.

The declarative/imperative validation layer does not compensate for this gap: [2](#0-1) [3](#0-2) 
Both `ValidatePodGroupUpdate` and `ValidateCompositePodGroupUpdate` validate only `ObjectMeta`, with no immutability check on `spec.PriorityClassName` or `spec.Priority` (contrast with `ValidatePriorityClassUpdate`, which explicitly makes `Value` and `PreemptionPolicy` immutable on `PriorityClass` objects at lines 64-74).

Attack flow: an attacker with namespace-scoped `update` RBAC on `podgroups`/`compositepodgroups` (a resource they are expected to be able to manage for their own workloads) creates a PodGroup with a low/no priority class, then issues an `Update` request directly setting `spec.PriorityClassName: "system-cluster-critical"` and `spec.Priority` to the corresponding high integer value. Neither `Admit` (skipped for Update) nor `Validate`/`ValidatePodGroupUpdate` (only checks ObjectMeta) rejects or normalizes this change, so the escalated priority reference and value persist in the object unchecked.

### Impact Explanation
This is a persisted invalid/protected field bypass: an unprivileged, namespace-scoped user can assign a system-reserved priority class (normally gated to system components) and an arbitrary priority integer to their own PodGroup/CompositePodGroup after creation, without any admission-time verification that the class exists, is permitted, or that the priority integer matches the class's actual value. Depending on how downstream schedulers/consumers of PodGroup/CompositePodGroup priority act on `spec.Priority`/`spec.PriorityClassName` (e.g., for preemption or scheduling gang priority decisions), this enables priority/preemption escalation for workloads that should not receive system-critical treatment — a control-plane admission bypass matching the "admission bypass leading to privilege/priority escalation" bounty class.

### Likelihood Explanation
Minimal RBAC needed: only `update` verb on `podgroups`/`compositepodgroups` in the attacker's own namespace, which is a realistic and commonly granted permission for anyone allowed to manage their own scheduling objects. The attack requires two ordinary API calls (Create, then Update) and no special timing, race conditions, or elevated access — fully repeatable and gated only by the `GenericWorkload`/`CompositePodGroup` feature gates being enabled (which are enablement, not security, controls).

### Recommendation
Update `Plugin.Admit` in `plugin/pkg/admission/priority/admission.go` to also invoke `admitPodGroup`/`admitCompositePodGroup` (or an update-specific variant) on `admission.Update`, re-resolving/validating `spec.PriorityClassName` against the current old object similarly to how `admitPod` handles updates. Additionally, update `ValidatePodGroupUpdate` and `ValidateCompositePodGroupUpdate` in `pkg/apis/scheduling/validation/validation.go` to enforce immutability of `spec.PriorityClassName` and `spec.Priority` after creation (mirroring `ValidatePriorityClassUpdate`'s immutability checks), unless a controlled, re-validated migration path is explicitly desired.

### Proof of Concept
Integration test plan (extends `plugin/pkg/admission/priority/admission_test.go`):
1. Enable `GenericWorkload` feature gate; register a low-priority `PriorityClass` (`low-priority`, value 0) and the system class `system-cluster-critical` (value 2000000000) in the fake lister/client.
2. Call `Admit` with `operation=Create` for a `PodGroup` object with `spec.PriorityClassName="low-priority"`; assert it succeeds and `spec.Priority` is set to 0.
3. Construct an `Update` `admission.Attributes` for the same PodGroup, with `GetOldObject()` = the created object (`PriorityClassName="low-priority"`) and `GetObject()` = a copy with `spec.PriorityClassName="system-cluster-critical"` and `spec.Priority` set to 2000000000.
4. Call `Admit` and assert it returns `nil` (no error), and that `admitPodGroup`/`establishPriority`/`resolvePriorityClass` were never invoked (e.g., via a spy/mocked lister call-count assertion).
5. Separately call `ValidatePodGroupUpdate(newPodGroup, oldPodGroup)` and assert it returns an empty `field.ErrorList`, confirming the changed `spec.PriorityClassName`/`spec.Priority` pass validation unchecked — demonstrating the escalated priority class reference persists without ever being re-resolved or authorized.
