## Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the webhook HMAC over the raw body only, while the `shop` (and `topic`) values used downstream to attribute the webhook to a tenant are taken verbatim from unauthenticated HTTP headers. `Registry.process` trusts this unbound `shop` value when dispatching to the app's handler, so the identity binding "HMAC-verified bytes == shop the data is attributed to" does not hold.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC header: [3](#0-2) 

`Registry.process` accepts any request whose body HMAC validates, then hands the handler `request.shop` as the tenant identity for the webhook, without any check that this shop value is the one Shopify actually associated with that payload: [4](#0-3) 

Because the app's `client_secret`/`api_secret_key` is a single value shared across every shop that has the app installed (it is not per-shop), any user who can get one legitimate webhook delivered to them (e.g., by installing the app on their own store and triggering an event) obtains a `(raw_body, hmac)` pair that is valid under the app's shared secret. That pair can be replayed to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop's domain. The signature check still passes because the header is never part of the signed content, so the handler executes with `WebhookMetadata#shop` claiming to be the victim tenant while the body's HMAC only proves "some shop of this app produced this body," not "this specific shop produced this body."

This is the same class of defect as the audited report: a value that downstream logic treats as authenticated/trustworthy (there, the rounded tick used for price; here, the `shop` used as tenant identity) is derived from data that is not actually covered by the integrity check (there, `pool.observe()` rounding; here, the HMAC over `raw_body` alone), so the "verified" state and the "acted-upon" state diverge — `shop_authenticated_by(hmac) != shop_used_by(handler)`.

### Impact Explanation
An app built on this gem trusts `WebhookMetadata#shop` (or `Request#shop`) to route webhook payloads to the correct tenant's session/data (e.g., updating orders/products for "that shop"). A cross-tenant write/update triggered by a spoofed `shop` value would let one merchant's traffic corrupt or overwrite another merchant's data inside the host app, meeting the Critical bar for cross-tenant access.

### Likelihood Explanation
Requires only that the attacker be a legitimate (unprivileged) install of the same public app to obtain one valid `(body, hmac)` pair, then a single unauthenticated POST to the app's webhook endpoint with a forged shop header — no access token, `api_secret_key`, or privileged account needed.

### Recommendation
Bind the `shop` (and `topic`/`webhook_id`) to the verified content, e.g. include the `x-shopify-shop-domain` header value as part of the signed string checked in `HmacValidator`, or have `Registry.process` cross-check `request.shop` against an expected/registered shop list before invoking the handler.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker resends this exact body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks the body against the shared `api_secret_key` (`lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `Registry.process` invokes the handler with `shop: request.shop == "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the app to process attacker-controlled data under the victim shop's identity.
