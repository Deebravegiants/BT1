## Title
Missing system:masters restriction for kubelet-client CSR signer allows identity forgery via CertificateSubjectRestriction bypass - (File: plugin/pkg/admission/certificates/subjectrestriction/admission.go)

## Summary
The `CertificateSubjectRestriction` admission plugin's `Validate` function only blocks `system:masters` organization for CSRs whose `signerName` equals `certificatesv1.KubeAPIServerClientSignerName` (`kubernetes.io/kube-apiserver-client`), leaving `KubeAPIServerClientKubeletSignerName` (`kubernetes.io/kube-apiserver-client-kubelet`) and `KubeletServingSignerName` completely unchecked for this dangerous organization value.

## Finding Description
`Plugin.Validate` at [1](#0-0)  exits early unless `csr.Spec.SignerName != certificatesv1.KubeAPIServerClientSignerName`, meaning any CSR submitted with `signerName: kubernetes.io/kube-apiserver-client-kubelet` (or the kubelet-serving signer) bypasses the `system:masters` organization check entirely, even though the PEM-embedded `Organization` field can still be set to `system:masters`.

However, tracing the full pipeline shows this alone is not sufficient for exploitation by an unprivileged attacker:
- The auto-approver (`sarapprove.go`) only auto-approves CSRs for the `KubeAPIServerClientKubeletSignerName` signer when `isNodeClientCert`/`isSelfNodeClientCert` recognize the CSR (i.e., `capihelper.IsKubeletClientCSR` requires a specific `system:node:<name>` CommonName pattern and `system:nodes` group, not `system:masters`), and only after a `SubjectAccessReview` for the `certificatesigningrequests/nodeclient` or `/selfnodeclient` subresource succeeds — permissions an unprivileged attacker does not hold by default [2](#0-1) .
- Manual approval via the `certificatesigningrequests/approval` subresource is separately gated by the `CertificateApproval` admission plugin, which requires the approver to be authorized via `IsAuthorizedForSignerName(..., "approve", csr.Spec.SignerName)` for that specific signer name [3](#0-2) . An unprivileged attacker does not have this RBAC grant by default.
- Signing is likewise gated: `CSRSigningController.handle` only signs approved CSRs matching the controller's configured `signerName`, and for `KubeAPIServerClientKubeletSignerName` it calls `isKubeletClient` → `capihelper.ValidateKubeletClientCSR`, which independently validates the request's subject/usages for the kubelet-client pattern before signing [4](#0-3) .

So while the admission-plugin totality gap is real (the code comment and check are indeed narrowly scoped to one signer name, confirming an incomplete/inconsistent validation design), turning it into an actual `system:masters` identity forgery requires the attacker to also obtain CSR **approval** — which is independently gated by RBAC checked against the specific `signerName` in the `CertificateApproval` plugin, and obtaining that approval permission is equivalent to already having significant control-plane trust that is out of scope for an "ordinary user with only `create` on CSRs" as stated in the preconditions.

## Impact Explanation
If an attacker additionally held (or could obtain) approval rights for the `kubernetes.io/kube-apiserver-client-kubelet` signer, the missing organization check would allow a signed client certificate embedding `O=system:masters`, which is a full cluster-admin impersonation/privilege-escalation primitive. This matches the "CSR identity forgery" / privilege escalation impact class described in the question. However, with only the stated precondition (RBAC `create` on `certificatesigningrequests`), the attack chain stops at the approval stage because the `CertificateApproval` admission plugin enforces a distinct, signer-name-scoped authorization check that the attacker does not satisfy.

## Likelihood Explanation
Low, given the stated attacker capability (CSR `create` only). The gap in `subjectrestriction/admission.go` is real and reduces defense-in-depth (relying solely on approval-time authorization rather than also rejecting dangerous subject content at CSR-creation time for all client-auth signers), but it does not by itself grant privilege escalation to an unprivileged, minimally-privileged attacker because a second independent control (signer-scoped approval authorization) still blocks the forged CSR from ever being approved and signed.

## Recommendation
Broaden the `subjectrestriction` admission check to cover all signer names that produce client-authentication certificates (at minimum `KubeAPIServerClientSignerName` and `KubeAPIServerClientKubeletSignerName`), rather than special-casing a single signer name, so the `system:masters` restriction is consistently enforced as defense-in-depth regardless of the approval-path RBAC configuration.

## Proof of Concept
Table-driven test in `plugin/pkg/admission/certificates/subjectrestriction/admission_test.go` style: construct CSR objects with `Organization=["system:masters"]` for each built-in signer (`KubeAPIServerClientSignerName`, `KubeAPIServerClientKubeletSignerName`, `KubeletServingSignerName`), call `Plugin.Validate`, and assert it returns `admission.NewForbidden` for all client-auth signers. Currently only `KubeAPIServerClientSignerName` is rejected; the other cases return `nil`, demonstrating the inconsistency — but note a full integration PoC to demonstrate actual privilege escalation would additionally need to show approval succeeding under only `create`-CSR RBAC, which the current `CertificateApproval` admission plugin (`plugin/pkg/admission/certificates/approval/admission.go`) prevents.

		return false
	}

		return false
	}

}
