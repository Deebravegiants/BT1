### Title
Permissionless `coin::migrate_to_fungible_store` can silently clear a compliance-issuer freeze on a user's primary fungible store - ([File: aptos-move/framework/aptos-framework/sources/coin.move])

### Summary
The external report's root custody invariant is: *"balance/authority queries used in a withdrawal/state-transition path must reflect the actual custody state of the asset, or the operation must not silently override the correct state."* In Aptos, the analogous flow is the legacy `Coin<CoinType>` → `FungibleAsset` migration path. `coin::maybe_convert_to_fungible_store` reconciles the `frozen` flag between the legacy `CoinStore<CoinType>` and the new primary fungible store (PFS) by unconditionally overwriting the PFS's frozen bit with the `CoinStore`'s frozen bit whenever they differ, with no check on which side is the authoritative/most-recent freeze decision. [1](#0-0) 

### Finding Description
`migrate_to_fungible_store` is a self-service, permissionless entry function callable by any account holder on their own address: [2](#0-1) 

It delegates to `maybe_convert_to_fungible_store`, which moves the legacy `CoinStore<CoinType>` balance into the account's primary fungible store and then reconciles the frozen flag: [3](#0-2) 

The comment in the code even acknowledges the ambiguity: *"It is possible the primary fungible store may already exist before this function call. In this case, if the account owns a frozen CoinStore and an unfrozen primary fungible store, this function would convert and deposit the rest coin into the primary store and freeze it..."* — but the reconciliation logic is symmetric: `if (frozen != fungible_asset::is_frozen(store)) { fungible_asset::set_frozen_flag_internal(store, frozen) }`. This means the reverse case is equally possible: if the account's `CoinStore<CoinType>` is unfrozen (the common/default case for most legacy coin holders, since `CoinStore` freeze requires the coin issuer to have called `freeze_coin_store` with a `FreezeCapability`) but the PFS for the paired FA has been frozen independently by an FA-side `TransferRef` (e.g., a stablecoin issuer's compliance/denylist freeze, as implemented in `stablecoin::usdk` via `Management.transfer_ref`), then calling `migrate_to_fungible_store` self-authorizes an **unfreeze** of the PFS.

The two freeze authorities — `CoinType`'s `FreezeCapability` (legacy coin side) and the FA metadata's `TransferRef` (fungible-asset side) — are independent custody controls, but `maybe_convert_to_fungible_store` treats the legacy side's frozen bit as authoritative and force-syncs it onto the FA side without any check for which control is more recent, more restrictive, or which authority actually owns freeze semantics for that account. Because the migration is invoked by the target account itself (an unprivileged, self-interested party), this converts a purely local self-service operation into a vector for silently clearing an issuer-imposed freeze/denylist control.

### Impact Explanation
This breaks the custody invariant that "freeze state controls asset movement and must only be settable by the privileged issuer/TransferRef holder." A sanctioned or frozen account holding both a (never-frozen) legacy `CoinStore<CoinType>` and a frozen PFS for the paired FA can call the permissionless `migrate_to_fungible_store` entry function to reset `is_frozen` on their PFS to `false`, restoring their ability to transfer/withdraw funds that the issuer intended to lock. This is an unauthorized freeze-control bypass on custody-grade fungible-asset value, matching the "Unauthorized takeover of ... freeze control ... tied to live assets" impact category.

### Likelihood Explanation
The precondition requires: (1) a `CoinType` that has been paired to an FA via `coin::create_pairing`/`ensure_paired_metadata` (common for any coin migrated to the FA standard, including third-party stablecoins that still register `CoinStore`), (2) the FA side supporting freeze (any `TransferRef`-based freeze, as used by managed-stablecoin patterns like `usdk.move`), and (3) the target address's `CoinStore` being unfrozen while its PFS is frozen — a state reachable simply by the account never having interacted with the legacy freeze mechanism (default) while being freshly denylisted on the FA side. All of this is achievable by an ordinary account signer calling a public entry function with no special privileges, making this straightforward to trigger once an issuer relies on FA-side freezing for compliance while `CoinStore` for that type still exists on-chain.

### Recommendation
Do not blindly overwrite the PFS frozen flag from the `CoinStore` frozen flag in `maybe_convert_to_fungible_store`. Options: (a) only propagate `frozen = true` from `CoinStore` to PFS (never unfreeze via migration), (b) require an explicit privileged call (e.g., gated by the same `FreezeCapability`/`TransferRef` authority) to reconcile frozen state instead of doing it implicitly inside a user-triggered migration, or (c) reject/no-op the migration if a freeze-state conflict is detected and surface it to the issuer for manual reconciliation.

### Proof of Concept
1. Issuer defines `CoinType` with `FreezeCapability` and calls `coin::create_pairing<CoinType>` to create the paired FA with `TransferRef`-based freeze support (as in `stablecoin::usdk`).
2. User `A` holds `CoinStore<CoinType>` (never frozen) with balance `X`.
3. Issuer detects suspicious activity and freezes `A`'s primary fungible store directly via `TransferRef` (FA-side freeze), independent of the legacy `CoinStore`.
4. `A` calls `coin::migrate_to_fungible_store<CoinType>(&A)`.
5. Inside `maybe_convert_to_fungible_store`, `frozen` (from `CoinStore`) is `false`, `fungible_asset::is_frozen(store)` is `true` → mismatch triggers `fungible_asset::set_frozen_flag_internal(store, false)`, unfreezing `A`'s PFS.
6. `A` can now transfer/withdraw the previously frozen FA balance, defeating the issuer's freeze control.

Note: I was not able to fully trace `fungible_asset::set_frozen_flag_internal`'s exact visibility/guard conditions or confirm whether any additional framework-level check (outside `coin.move`) prevents this specific scenario in the current build, due to the final iteration limit cutting off further reads. This should be independently verified by reading `set_frozen_flag_internal` in `fungible_asset.move` and any friend/visibility restrictions before treating this as confirmed-exploitable in production.

    fun maybe_convert_to_fungible_store<CoinType>(
        account: address
    ) acquires CoinStore, CoinConversionMap, CoinInfo {
        if (exists<CoinStore<CoinType>>(account)) {
            let CoinStore<CoinType> { coin, frozen, deposit_events, withdraw_events } =
                move_from<CoinStore<CoinType>>(account);
            if (is_coin_initialized<CoinType>() && coin.value > 0) {
                let metadata = ensure_paired_metadata<CoinType>();
                let store =
                    primary_fungible_store::ensure_primary_store_exists(
                        account, metadata
                    );

                event::emit(
                    CoinStoreDeletion {
                        coin_type: type_info::type_name<CoinType>(),
                        event_handle_creation_address: guid::creator_address(
                            event::guid(&deposit_events)
                        ),
                        deleted_deposit_event_handle_creation_number: guid::creation_num(
                            event::guid(&deposit_events)
                        ),
                        deleted_withdraw_event_handle_creation_number: guid::creation_num(
                            event::guid(&withdraw_events)
                        )
                    }
                );

                if (coin.value == 0) {
                    destroy_zero(coin);
                } else {
                    fungible_asset::unchecked_deposit_with_no_events(
                        store.object_address(),
                        coin_to_fungible_asset(coin)
                    );
                };

                // Note:
                // It is possible the primary fungible store may already exist before this function call.
                // In this case, if the account owns a frozen CoinStore and an unfrozen primary fungible store, this
                // function would convert and deposit the rest coin into the primary store and freeze it to make the
                // `frozen` semantic as consistent as possible.
                if (frozen != fungible_asset::is_frozen(store)) {
                    fungible_asset::set_frozen_flag_internal(store, frozen);
                }
