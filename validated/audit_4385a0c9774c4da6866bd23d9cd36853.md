### Title
Stateless Emporium op can drain any victim's stale/infinite ERC20 allowance to Emporium into attacker's shielded balance - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s stateless branch (`invokeWallet == false`) executes `op.endpoint.call(op.callData)` with completely attacker-chosen `callData`, the only restriction being a selector blacklist for `callHinkalWallet`/`doSendToRelay`. Nothing ties the `from` argument of an ERC20 `transferFrom` inside that `callData` to the account that produced the enclosing zk-proof, so an attacker can encode `victimToken.transferFrom(victim, Emporium, amount)` using any allowance `victim` left outstanding to the Emporium address, and have the resulting Emporium balance increase credited to the attacker's own shielded output.

### Finding Description
The broken equality is **authority**: `allowance(victim, Emporium)` was granted by `victim` to permit *victim's own* transactions, not to authorize spending by whoever happens to submit a Hinkal proof. Nothing in the code enforces `from == circomData.originalSender` (or any account controlled by the prover) for tokens pulled inside a stateless op.

Path: `Hinkal.transact` → `_externalTransact` (`contracts/Hinkal.sol:234-261`) computes `deltaAmountChanges[i] = _calculateDeltaAmount(...)`. If the attacker sets this to `0` (not a declared shielded-pool deposit) rather than negative, the `if (deltaAmountChanges[i] < 0)` branch is skipped, so Hinkal sends nothing to Emporium out of its own held funds — the entire token movement has to come from the op itself.

`IExternalActionV2.runAction` is then invoked on `EmporiumUpgradeable` (`contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:76-160`). For a stateless op (`op.invokeWallet == false`), it just does `op.endpoint.call{value: op.value}(op.callData)` (line 112) with no check on the call's target or arguments beyond blocking two specific selectors. The attacker sets `op.endpoint = victimToken` and `op.callData = victimToken.transferFrom(victim, Emporium, amount)`. Since `victim` previously approved `Emporium` (e.g., via a common unlimited-approval UX pattern for a legitimate earlier Emporium deposit, and OpenZeppelin's `_spendAllowance` never decrements an allowance that equals `type(uint256).max`), the call succeeds and Emporium's on-chain balance of `victimToken` rises by `amount`, with `msg.sender` for that `transferFrom` being `Emporium` (satisfying the allowance check) regardless of who initiated the outer transaction.

Back in `runAction`, `balanceChange = balancesAfter[i] - balancesBefore[i] = amount`; since `deltaAmountChanges[i] == 0` (not `< 0`), no adjustment is applied (`EmporiumUpgradeable.sol:132-144`). `handleOut` (`EmporiumUpgradeable.sol:162-184`) sees `balanceChange > 0`, transfers `amount` to `msg.sender` (Hinkal itself), and mints a `UTXO(amount, victimToken, circomData.stealthAddressStructure, ...)` keyed to the **attacker's own** `stealthAddressStructure` (attacker fully controls this field of `circomData`).

Back in `Hinkal.transact` (`contracts/Hinkal.sol:97-146`): `balanceDif` (Hinkal's own balance delta for that token) `== amount` (received from Emporium via `handleOut`). The check `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount` becomes `amount == 0 + amount` — it holds, because the attacker declared `amountChanges[i] = 0` for this token index and let the whole `amount` arrive as an on-chain-created UTXO instead. (Setting `amountChanges[i] = amount` as literally suggested in the question would make the RHS `2*amount`, failing the check — the exploitable variant requires `amountChanges[i] = 0`, with the stolen value flowing entirely through the `utxoAmount` term.)

None of `performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyWallet` (only relevant when `stack.signerAddress != address(0)`, and even then only signs over the attacker's own chosen `callData`, not third-party authority), or the circuit's `inTotal + amountChanges === outTotal` constraint restrict the *content* of a stateless op's `callData` or check that any tokens it moves originate from an account the proof's owner actually controls. The `calldataHash`/`getHashedCalldata` machinery only prevents a relay from tampering with the attacker's already-malicious payload; it provides no authorization semantics.

### Impact Explanation
Critical — direct theft of a third party's ERC20 tokens, converted into a shielded UTXO under the attacker's own key with no on-chain trace pointing to attacker's own funds ever moving. This is repeatable against every unrevoked/unlimited allowance any user has ever granted to any Emporium proxy instance, for the full amount of that allowance, in a single transaction per victim/token pair, at only the attacker's own gas + proof-generation cost.

### Likelihood Explanation
Requires a pre-existing `allowance(victim, Emporium) > 0`. This is a realistic residue given the widespread "approve once for `type(uint256).max`" UX pattern used by front-ends to avoid repeated approval transactions for the Emporium's on-chain-deposit flavor of stateless ops (where legitimate `transferFrom(depositor, Emporium, amount)` calls are expected). Any victim who used this pattern for even one legitimate Emporium deposit remains exposed indefinitely, since standard OpenZeppelin ERC20 semantics never decrement a `type(uint256).max` allowance. The attacker needs no privileges — only their own valid proof over their own (possibly zero-value) UTXOs, and knowledge of `victim`'s outstanding allowance (observable on-chain). ### Recommendation
For stateless Emporium ops (`invokeWallet == false`), require that any ERC20 `transferFrom`/`transfer` call target within `op.callData` uses `from == circomData.originalSender` (or, more generally, restrict stateless ops so they can never encode arbitrary third-party `transferFrom` calls at all — deposits into Emporium should route through a mechanism that binds the pulled funds' source address to the account whose signature/EIP-712 message backs the proof, analogous to how `verifyWallet`/`callHinkalWallet` binds stateful ops to `signerAddress`). At minimum, decode and validate the first 32 bytes after the `transferFrom`/`transferFromTo`-family selectors in `op.callData` against `circomData.originalSender` before executing, or disallow the ERC20 `transferFrom` selector entirely from the stateless path and require token sourcing to happen exclusively via Hinkal's own held balance (`deltaAmountChanges[i] < 0` branch) or via the signed, wallet-mediated stateful path.

### Proof of Concept
Hardhat fork test:
1. Deploy `Hinkal`, `EmporiumUpgradeable`, and a standard ERC20 (`VictimToken`).
2. `victim` calls `VictimToken.approve(Emporium, type(uint256).max)` and performs one legitimate Emporium stateless deposit of `depositAmount` (simulating normal front-end unlimited-approval UX); assert `VictimToken.allowance(victim, Emporium) == type(uint256).max` afterward (OZ semantics never decrement max allowance).
3. `attacker` (unprivileged, no relationship to `victim`) generates their own valid zk-proof for `Hinkal.transact` with `circomData.externalActionData.externalActionId` pointing at Emporium, `circomData.amountChanges[tokenIdx] = 0`, `circomData.erc20TokenAddresses = [VictimToken]`, `circomData.stealthAddressStructure` = attacker's own stealth keys, and `EmporiumStack.ops[0] = { endpoint: VictimToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transferFrom, (victim, Emporium, amount)) }`.
4. Call `Hinkal.transact(...)` as attacker.
5. Assert: `VictimToken.balanceOf(victim)` decreased by `amount`; no `transferFrom` call ever had `attacker` as the `from` or `msg.sender` of the ERC20 call; a new shielded note of `amount` `VictimToken` was created under attacker's stealth address (verify via emitted `NewCommitment`/`onChainCommitments` decrypted with attacker's key); confirm `balanceDif == amountChanges[tokenIdx] + utxoAmount` (i.e., `amount == 0 + amount`) is exactly the equality that let the theft pass unnoticed by existing checks.
