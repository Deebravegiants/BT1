Based on the investigation, the closest reachable analog to the LiFi `LIFuelFacet` "no limits on funds sent, funds can get stuck due to insufficient liquidity on the receiving side" bug class is the lock/unlock cross-chain transfer path in `WrappedHyperFungibleToken.sol`, which is directly reachable by any unprivileged user calling `send()`.

### Title
Unbounded `WrappedHyperFungibleToken.send()` amount can exceed destination-chain locked liquidity, stranding cross-chain transfers - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken` is a lock/unlock bridge: each per-chain deployment independently escrows its own balance of the underlying ERC20 (or wrapped native token). `send()` places no upper bound on `params.amount`, so a user can dispatch a transfer for an amount larger than what is actually held/lockable as `_underlying` balance on the destination chain's deployment, causing the destination `onAccept()` to revert on `safeTransfer`/`WETH.withdraw` due to insufficient balance.

### Finding Description
`send()` takes `params.amount` from the caller and unconditionally locks it (`IERC20(_underlying).safeTransferFrom(...)` or `IWETH(_underlying).deposit{value: params.amount}()`), then dispatches an ISMP POST with that amount embedded in the message body: [1](#0-0) 

There is no check that the destination chain's deployment of the wrapper actually holds `message.amount` of the underlying token to unlock. On the receiving side, `onAccept()` unconditionally attempts to hand out that exact amount: [2](#0-1) 

Because each chain's `WrappedHyperFungibleToken` deployment is its own escrow — "no shared custody pool," per the contract's own docstring — the amount lockable/unlockable on one leg of the route is bounded by how much liquidity happens to be locked on the *other* leg at that moment, which the sender has no way to know or the contract to enforce. There is no `maxAmount`, no liquidity check against `IERC20(_underlying).balanceOf(address(this))` on dispatch, and no backend/limits layer analogous to LiFi's off-chain limit enforcement is referenced anywhere in this contract.

### Impact Explanation
When `message.amount` exceeds the destination contract's underlying balance, `onAccept()` reverts. The ISMP host records the request as undeliverable; relayers cannot successfully execute it until either (a) more liquidity happens to be locked on that chain via other users' `send()` calls, or (b) the request times out and `onPostRequestTimeout()` refunds the original sender. In the interim the sender's tokens are locked and unusable, and if no relayer/liquidity ever materializes before timeout processing, the funds remain non-executable indefinitely — a route that is unable to deliver messages, mirroring the LiFi finding's "funds getting stuck due to insufficient liquidity on the receiving side."

### Likelihood Explanation
Any user can trigger this simply by calling `send()` with an amount larger than what has been organically locked on the destination chain — no coordination or privileged access required. This is especially likely for a freshly deployed wrapper pair or an asymmetric/low-volume route where locked balances on the two sides diverge.

### Recommendation
Enforce an amount limit in `send()`, e.g. cap `params.amount` to the destination chain's currently known/expected liquidity, or require the destination-side balance to be checked/reserved before dispatch (similar to how `HyperFungibleToken`'s mint/burn variant is fully backed 1:1 and does not have this exposure). At minimum, expose a configurable per-chain `maxAmount` that the owner can tune per destination's actual locked liquidity, analogous to LiFi's backend-side limits for `LIFuelFacet`.

### Proof of Concept
1. Deploy `WrappedHyperFungibleToken` on chain A and chain B, `configure()`d and `addChain()`-registered as peers.
2. On chain B, no user has yet called `send()` toward chain A, so chain B's `_underlying` balance is `0`.
3. A user on chain A calls `send()` with `params.amount = 1000e18`, locking `1000e18` of the underlying token on chain A and dispatching the POST request.
4. A relayer delivers the request to chain B; `onAccept()` calls `IERC20(_underlying).safeTransfer(beneficiary, 1000e18)`, which reverts because chain B's deployment holds `0` of that token.
5. The request is undeliverable until enough locked liquidity accumulates on chain B or the request times out and the sender is refunded on chain A — the sender's funds are stuck for the duration, with no protocol-enforced limit having prevented the attempt.

    function send(HyperFungibleToken.SendParams calldata params) external payable whenNotPaused {
        uint256 msgValue = msg.value;
        if (_isWeth && msgValue >= params.amount) {
            msgValue = msgValue - params.amount;
            IWETH(_underlying).deposit{value: params.amount}();
        } else {
            IERC20(_underlying).safeTransferFrom(msg.sender, address(this), params.amount);
        }

        DispatchPost memory request = _buildDispatchPost(params);
        bytes32 commitment;
        if (msgValue > 0) {
            commitment = IDispatcher(_host).dispatch{value: msgValue}(request);
        } else {
            commitment = dispatchWithFeeToken(request);
        }

        emit Sent({
            from: msg.sender,
            to: params.to,
            dest: string(params.dest),
            amount: params.amount,
            commitment: commitment
        });
    }

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        HyperFungibleToken.Message memory message = abi.decode(request.body, (HyperFungibleToken.Message));
        address beneficiary = _toAddr(message.to);

        if (_isWeth) {
            // Try a native-ETH push first (cheap for EOAs and payable contracts);
            // if the recipient cannot accept native value (no `receive()` / `fallback()
            // payable`), re-wrap the withdrawn ETH and deliver the underlying WETH as
            // an ERC-20 transfer instead. This mirrors the deposit-side flexibility of
            // `send()` (which accepts WETH from non-payable callers via `safeTransferFrom`)
            // so the refund path doesn't permanently lock funds for the same caller class.
            IWETH(_underlying).withdraw(message.amount);
            (bool sent,) = beneficiary.call{value: message.amount}("");
            if (!sent) {
                IWETH(_underlying).deposit{value: message.amount}();
                IERC20(_underlying).safeTransfer(beneficiary, message.amount);
            }
        } else {
            IERC20(_underlying).safeTransfer(beneficiary, message.amount);
        }
