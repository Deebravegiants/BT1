This confirms the finding: `docs/usage/webhooks.md` explicitly documents `data.shop` as the trusted "shop domain of the webhook" that apps use to route/attribute the webhook (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), yet this value is never covered by the HMAC signature — only `@raw_body` is.

### Title
Webhook shop-domain spoofing via HMAC scope gap allows cross-tenant webhook injection - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop` (tenant identifier) is read from an unauthenticated header. `ShopifyAPI::Webhooks::Registry.process` validates only the body's HMAC and then forwards the untrusted `shop` value straight to the host application's webhook handler as authoritative tenant context.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC (`Utils::HmacValidator.validate(request)`, which in turn calls `verifiable_query.to_signable_string` — i.e. only the body bytes) and then constructs `WebhookMetadata` using the unauthenticated `request.shop`: [3](#0-2) 

`HmacValidator.validate_signature` confirms the signature is computed only over `verifiable_query.to_signable_string`: [4](#0-3) 

The gem's own documentation instructs app developers to treat `data.shop` as the trusted tenant identifier for dispatching/attributing webhook work (e.g. `shop_domain: data.shop`), reinforcing that this field is expected to be authenticated: [5](#0-4) 

Because Shopify apps use a single `client_secret` (`api_secret_key`) shared across **all** installing shops (not a per-shop secret), any merchant who has legitimately installed the app on their own store can generate a validly-HMAC-signed webhook body for content they control (e.g., an order/product with attacker-chosen field values), intercept that request, and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. The equality the design should enforce is:
`HMAC-authenticated principal (bytes actually signed) == shop used as the tenant/session key for handler dispatch`
This equality is broken because the HMAC only binds the raw body, never the `shop` header that downstream code (per the documented usage pattern) uses as the tenant/session key.

### Impact Explanation
This is a cross-tenant boundary crossing: the attacker (an unprivileged, arbitrary internet user who merely installs the free/dev version of the target app) can make the host application believe events with attacker-chosen JSON content originated from a shop they do not own/control, without possessing that shop's credentials or the app's `client_secret`. Depending on how the host app's handler uses `data.shop` (commonly to key session lookups, enqueue background jobs scoped to that shop, or write attacker-controlled body data into per-shop records), this enables cross-tenant data injection/corruption using only the shared, non-secret `shop` header — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
High likelihood: becoming an "unprivileged" attacker only requires installing the public app once (a normal, permission-less action for any Shopify user for public/dev apps), after which producing a validly-signed body/HMAC pair for attacker-chosen content is trivial (it's simply a normal webhook their own shop legitimately receives). Spoofing the `shop` header on replay requires no secret knowledge, since it is never covered by the signature.

### Recommendation
Include the shop domain (and other identity-relevant headers such as topic/api-version) inside the HMAC-signable content, or otherwise cryptographically bind the header-provided `shop` to the verified payload before it is handed to the handler as `WebhookMetadata#shop`. At minimum, document/require that hosts cross-check `data.shop` against an independently known set of installed shops before using it as a trust boundary — but the gem itself should not present an unauthenticated header as verified tenant context after only validating a body HMAC.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook event (e.g., `orders/create`) with an attacker-chosen note/body field; capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify computed with the app's shared `client_secret`.
3. Replay the exact same raw body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because only `@raw_body` is verified.
5. `WebhookMetadata.new(topic:, shop: request.shop, ...)` is built with `shop == "victim.myshopify.com"`, and the host handler processes attacker-controlled data attributed to the victim shop.
