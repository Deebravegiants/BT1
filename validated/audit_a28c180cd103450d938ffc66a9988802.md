### Title
Webhook `shop` used for tenant identification is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is read directly from the `x-shopify-shop-domain` header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. Any caller (including the gem's own `Webhooks::Registry.process`) that trusts `request.shop`/`WebhookMetadata#shop` to identify which tenant a webhook belongs to is relying on a value that is completely unauthenticated with respect to the cryptographic check that is actually performed.

### Finding Description
`lib/shopify_api/webhooks/request.rb` defines: [1](#0-0) 

```ruby
def hmac
  Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
end
...
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```

and: [2](#0-1) 

```ruby
def to_signable_string
  @raw_body
end
```

The signable string used for HMAC validation is **only** the raw HTTP body. The `Utils::HmacValidator.validate_signature` method computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., `@raw_body`) and compares it to the `hmac` header: [3](#0-2) 

The `shop-domain` header is never part of the bytes that are HMAC-verified. `Webhooks::Registry.process` nonetheless treats `request.shop` as trustworthy tenant identity and forwards it straight to the handler: [4](#0-3) 

```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
```

**Identity binding broken:** the equality that should hold is `hmac_verified_bytes == (body, shop)` but the gem only enforces `hmac_verified_bytes == body`. The `shop` value used by the handler for per-tenant routing/authorization is disjoint from what the signature actually covers.

**Concrete attack path (unprivileged internet user with only their own shop/app install — no victim credentials needed):**
1. Attacker installs the target app on their own Shopify store (`attacker-shop.myshopify.com`) — a routine, unprivileged action any merchant can perform.
2. Attacker triggers/receives a legitimate webhook from Shopify to the app's public webhook endpoint. This request has a valid `x-shopify-hmac-sha256` computed by Shopify over the raw body, and headers `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker replays this exact request to the app's webhook endpoint, but rewrites only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`. Since the HMAC is computed exclusively over `@raw_body` (unchanged), `Utils::HmacValidator.validate` still returns `true`.
4. `Webhooks::Registry.process` accepts the tampered request as valid and calls the handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the payload/HMAC was never associated with that shop by Shopify.
5. Any app that uses `WebhookMetadata#shop` (the documented, exposed accessor for this exact purpose) to select which tenant's records to create/update/delete now attributes attacker-controlled data to a different tenant — a cross-tenant data injection/spoofing condition.

### Impact Explanation
This breaks the tenant boundary that the webhook signature is supposed to guarantee: HMAC validation succeeds while the shop attribute handed to application code is forgeable independently of the signed payload. This matches the "Critical – cross-tenant access" impact category, since an attacker with only their own (attacker-owned) shop can cause the library to report webhook data as belonging to an arbitrary victim shop.

### Likelihood Explanation
High likelihood: no secret material is required, only the ability to send an HTTP request to the app's public webhook endpoint with attacker-chosen headers (trivial for any internet client, since webhook endpoints are ordinary HTTP routes). The `Registry.process`/`Request` API is the gem's officially documented mechanism for exposing `shop` to handlers, so any app author following the gem's own webhook documentation is exposed.

### Recommendation
Include the `shop-domain` (and other Shopify-controlled headers used for identity/routing, e.g. `webhook-id`, `api-version`, `topic`) in the HMAC-signed content, or otherwise cryptographically bind them to the payload before exposing them via `WebhookMetadata`. At minimum, document prominently that `shop` on `WebhookMetadata` is unauthenticated and must be cross-checked by the caller against a known/installed shop list before being trusted for tenant routing.

### Proof of Concept
```ruby
raw_body = '{"id":1}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)

# Legitimate webhook headers for attacker's own shop
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Attacker swaps only the shop-domain header, body/hmac untouched
tampered_headers = headers.merge("x-shopify-shop-domain" => "victim-shop.myshopify.com")
tampered_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: tampered_headers)
ShopifyAPI::Utils::HmacValidator.validate(tampered_request) # => true (still passes!)
tampered_request.shop # => "victim-shop.myshopify.com", accepted by Registry.process
```
