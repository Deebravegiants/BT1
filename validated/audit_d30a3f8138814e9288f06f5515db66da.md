Confirmed root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` and `topic` are read from separate, unauthenticated headers [2](#0-1) . `HmacValidator.validate_signature` only recomputes the HMAC over `to_signable_string`, i.e., the body, and compares it to the `hmac-sha256` header [3](#0-2) . `Registry.process` trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` passed to the app's handler after only validating the HMAC over the body [4](#0-3) . This matches the report's bug class exactly: "a field acted on but not covered by the HMAC."

### Title
Webhook `shop` (and `topic`) attribution is not covered by the HMAC, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its verifiable HMAC signature over the raw body only, never the `shop-domain` or `topic` headers. `ShopifyAPI::Webhooks::Registry.process` validates that HMAC and then unconditionally trusts `request.shop`/`request.topic` to construct the `WebhookMetadata` delivered to the app's handler. Because the `client_secret`/`api_secret_key` used to sign webhooks is shared across every shop that installs the same app (it is per-app, not per-shop), any merchant who installs the app can capture a validly-signed `(raw_body, hmac)` pair for their own shop and later replay that exact body+HMAC to the app's webhook endpoint while claiming (via a spoofed `shopify-shop-domain` header) that it originates from a different, victim shop. The signature still validates because `shop` is not part of the signed content, so the handler processes attacker-controlled body content under the wrong shop's identity.

### Finding Description
The identity binding that should hold is:
`hmac == HMAC(secret, raw_body || shop || topic)` and the shop the handler acts on == the shop the signature was computed for.

Instead the gem only enforces:
`hmac == HMAC(secret, raw_body)` [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are parsed straight from HTTP headers with no cryptographic binding to the signature: [5](#0-4) 

`Registry.process` validates only the HMAC, then blindly trusts these header-derived fields: [4](#0-3) 

Because every shop that installs a given Shopify app shares the same app-level `client_secret` (this is inherent to the OAuth app model, not shop-specific), a legitimate but unprivileged merchant installing the app can:
1. Trigger a webhook for their own shop with attacker-chosen body content (e.g., by creating/updating a resource with attacker-controlled fields, if the topic's payload includes user-controlled data), capturing the resulting valid `(raw_body, X-Shopify-Hmac-Sha256)` pair Shopify sends to the app's endpoint.
2. Replay that exact `raw_body` + `hmac` header to the same endpoint, but substitute the `X-Shopify-Shop-Domain` header with a different, victim shop's domain.
3. `HmacValidator.validate` still returns `true`, because the signature only ever covered `raw_body` [6](#0-5) .
4. `Registry.process` calls the app's handler with `shop: request.shop` set to the spoofed victim domain [7](#0-6) .

This is a direct analog of the `RIPEMD160` bug class described in the report: a value (`start`/`shop`) that is used downstream (dictionary finalization / tenant attribution) is not the value that was actually verified/initialized (the squashed dict / the HMAC-signed content), breaking the intended equality invariant.

### Impact Explanation
This breaks tenant isolation (cross-tenant access): the app's webhook handler, and any downstream storage or job enqueued from it (per the gem's own documented handler pattern, which passes `data.shop` straight to app logic/persistence) [8](#0-7) , will process and persist attacker-influenced webhook content under a victim shop's identity. Depending on the host app's use of `data.shop` (e.g., looking up/creating shop records, updating shop-scoped data), this can corrupt or pollute another tenant's data store using content the attacker fully controls, without needing the `api_secret_key`, an access token, or any privileged access — only a normal app installation on the attacker's own shop.

### Likelihood Explanation
Likelihood is Medium: exploitation requires the attacker to install the target app on their own shop (a normal, unprivileged action any merchant can take), obtain one valid Shopify-delivered webhook body/HMAC pair for their shop, and replay it directly to the app's public webhook endpoint with a modified shop header. No secrets, tokens, or TLS interception are required — only observing/controlling the HTTP request the gem's own `Registry.process` API accepts.

### Recommendation
Include `shop` (and ideally `topic`) in the signed/verified content, or otherwise cryptographically bind the shop attribution to the verified payload before trusting it — e.g., have `Request#to_signable_string` incorporate the shop-domain and topic headers, or require `Registry.process` to independently confirm that the shop header value belongs to a shop with an active, matching webhook registration/session before invoking the handler with that shop value.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`, subscribe to a webhook topic whose payload includes attacker-controllable data (e.g., `products/update` with a custom `title`).
2. Capture the resulting POST request to the app's webhook endpoint, including the `X-Shopify-Hmac-Sha256` header and raw JSON body.
3. Resend the exact same body and `X-Shopify-Hmac-Sha256` header to the same endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. Observe that `ShopifyAPI::Utils::HmacValidator.validate` still returns `true` (per `lib/shopify_api/utils/hmac_validator.rb` lines 12-22, only `raw_body` is checked), and `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and the attacker's `body`, confirming the app's handler is executed for a shop it did not receive a genuine webhook from.
