### Title
Webhook `shop` identity is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop` identity that is subsequently handed to the app's handler is taken from the unauthenticated `x-shopify-shop-domain` HTTP header, which is never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . The `shop` accessor is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding to the body: [2](#0-1) .

`Registry.process` validates the request using `Utils::HmacValidator.validate(request)`, which only verifies `request.to_signable_string` (i.e., the raw body) against the computed HMAC: [3](#0-2)  and [4](#0-3) . After this check passes, `request.shop` (from the unverified header) is placed directly into `WebhookMetadata` and handed to the app's `handler.handle`: [5](#0-4) . `WebhookMetadata#shop` is a plain `String` field with no further validation: [6](#0-5) .

The broken identity binding, stated as an equality that the gem fails to enforce:
`shop_header_used_for_tenant_identification == shop_bytes_covered_by_hmac` — this does not hold, because the HMAC only covers the raw body, never the `shop-domain` header.

### Impact Explanation
Because the app's `client_secret` is shared across all shops that install the app, any developer/merchant who installs the app on their own store (a completely unprivileged action available to any internet user through the normal app-install flow) can trigger a legitimate webhook delivery for their own shop and observe a request with a valid HMAC for a body they control (e.g. `products/update`, `orders/create`, etc., where they control much of the body content). Because the HMAC signs only the body and is independent of any header, the attacker can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` header value naming a victim shop. `Utils::HmacValidator.validate` will report the signature as valid (it never inspects the header), and `Registry.process` will forward `WebhookMetadata` claiming the (attacker-chosen) body originated from the victim shop. Any host application that uses `data.shop` from `WebhookMetadata` to select tenant-scoped state (e.g., "update this shop's product record", "look up this shop's session/settings") will act on forged, cross-tenant data — satisfying the "cross-tenant access" impact criterion, since data intended for one tenant can be attributed to and injected into another tenant's context purely by header manipulation, without ever needing that victim's access token.

### Likelihood Explanation
Likelihood is moderate to high: exploitation only requires (1) that the app is installed on a webhook-registered shop at all (any store, including a free/dev store an attacker controls), (2) capturing one legitimate webhook delivery (trivial via a proxy on the attacker's own endpoint or by using the same app credentials against a webhook-testing endpoint), and (3) resending the captured request with a modified shop-domain header to the target app's public webhook URL. No secret material, access token, or victim credentials are needed — only knowledge that the app's webhook endpoint identifies tenants by the value the gem exposes in `WebhookMetadata#shop`, which is standard integration practice per the gem's own documented `WebhookHandler` contract.

### Recommendation
Bind the shop identity to the verified payload before trusting it: either include the shop domain in the HMAC-covered signable string (not possible without changing Shopify's webhook contract), or require host applications/gem internals to cross-check `request.shop` against an independently known/authorized shop (e.g., a registered shop list, or the shop embedded inside the JSON body when available) before constructing `WebhookMetadata`. At minimum, the gem's documentation and `WebhookMetadata` should make explicit that `shop` is unauthenticated header data and must not be used as the sole tenant-selection key by consuming applications, and ideally the library should provide a stricter verification path that fails closed when the header-derived shop cannot be corroborated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own (attacker-controlled) shop `attacker-shop.myshopify.com`, receiving legitimate webhook deliveries signed with the app's real `api_secret_key`.
2. Attacker triggers a webhook event with a body they control, e.g. `products/update` with `raw_body = '{"id": 1, "title": "PWNED"}'`, and captures the resulting valid headers:
   ```
   x-shopify-topic: products/update
   x-shopify-hmac-sha256: <valid HMAC of raw_body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   ```
3. Attacker resends the identical body and HMAC to the app's public webhook endpoint, but rewrites the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `Utils::HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb) recomputes the HMAC over `raw_body` only and finds it matches — validation passes.
5. `Registry.process` builds `WebhookMetadata.new(topic: "products/update", shop: "victim-shop.myshopify.com", body: {...}, ...)` and invokes the app's handler, which now processes attacker-supplied data as if it belonged to `victim-shop.myshopify.com`.
