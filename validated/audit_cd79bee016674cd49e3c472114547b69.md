### Title
Excess native-token fee sent to `EvmHost.dispatch`/`fundRequest` is refunded to `EvmHost` itself instead of the caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept native token payment and swap it for the fee token via a Uniswap V2-compatible router using `swapETHForExactTokens`. This mirrors the reported analog: the router refunds any unspent ETH to whichever address called the swap function, and here that caller is `EvmHost` itself, not the end user (`_msgSender()`) who supplied the `msg.value`.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

In each case, `EvmHost` calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` directly. Both the standard Uniswap V2 Router02 implementation and the project's own wrapper (`UniV3UniswapV2Wrapper.swapETHForExactTokens`) refund any unspent ETH to `msg.sender` of that call — which, from the router's perspective, is `EvmHost`, since `EvmHost` is the direct caller: [4](#0-3) 

Consequently, if a user (or an app such as `IntentGatewayV2`/`HyperbridgeLzEndpoint` acting on a user's behalf) sends more native token than the swap actually costs, the surplus lands on `EvmHost`'s own balance rather than being returned to `_msgSender()`, the account that funded the call. This is functionally identical to the reported "excess fee refunded to the contract instead of the user" bug class.

By contrast, other parts of the same codebase correctly handle this exact scenario by explicitly forwarding leftover `msg.value` back to `msg.sender` after a native-fee swap, e.g. `IntentGatewayV2.placeOrder`: [5](#0-4) 

`EvmHost.dispatch`/`fundRequest` have no equivalent refund step after the swap.

### Impact Explanation
Any overpayment of native token when calling `dispatch()` or `fundRequest()` on `EvmHost` is permanently misdirected to the host contract's own balance instead of back to the payer. I was unable to confirm within the available context whether `EvmHost` exposes any privileged sweep/withdraw function for stray native balance; if none exists (or if it is not slated for arbitrary ETH recovery to the original payer), the surplus is permanently locked/lost to the depositor, constituting a fund-loss issue for any unprivileged caller (a user calling `dispatch` directly, or indirectly through `IntentGatewayV2`'s cross-chain dispatch path, `HyperbridgeLzEndpoint`, or `HyperFungibleTokenUpgradeable.send`) who overestimates the required native fee — a routine occurrence since callers must estimate `msg.value` in advance of an on-chain AMM swap whose actual cost can fluctuate with slippage.

### Likelihood Explanation
This path is reachable by any unprivileged caller who calls `IDispatcher(host).dispatch{value: msg.value}(...)` or `fundRequest{value: msg.value}(...)`, which is the standard way described in the Hyperbridge SDK/docs for dispatching a POST/GET request funded with native token. Overpayment is likely in practice because exact swap output amounts are not deterministic ahead of time (AMM price movement, slippage), and every example/documentation path shown (`post-requests.mdx`) uses `msg.value` funding.

### Recommendation
After calling `swapETHForExactTokens` in `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, capture the actual `amounts[0]` (ETH spent) returned by the swap and refund the difference `msg.value - amounts[0]` to `_msgSender()`, mirroring the pattern already used in `IntentGatewayV2.placeOrder`.

### Proof of Concept
1. Caller invokes `IDispatcher(evmHost).dispatch{value: 5 ether}(post)` where `post.fee` only requires a fraction of an ETH to acquire via the Uniswap V2 swap.
2. Inside `dispatch`, `EvmHost` calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)`.
3. The router (or `UniV3UniswapV2Wrapper`) spends only a small fraction of the 5 ETH and refunds the remainder to `msg.sender` of the swap call, which is `EvmHost`'s own address — not the original caller.
4. The original caller's transaction succeeds, but the unused ETH now sits in `EvmHost`'s balance instead of being returned; the caller has permanently overpaid with no path to recover the difference through `dispatch`/`fundRequest`.
