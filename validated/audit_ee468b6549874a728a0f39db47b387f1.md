### Title
Webhook `shop` identity is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/registry.rb], [File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, then unconditionally trusts the unauthenticated `shop-domain` header to attribute the payload to a tenant. Because the HMAC only covers the body bytes and never the shop identity, the equality that should hold — `shop_bound_by_hmac == shop_used_for_tenant_attribution` — is violated: the shop used for attribution is never bound by the signature at all.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC over exactly that signable string (i.e., the body only) and compares it to the `hmac-sha256` header: [2](#0-1) 

`Registry.process` gates on that body-only HMAC check, then immediately reads `request.shop` from the unauthenticated `shop-domain` header and hands it to the handler as the tenant identifier, with no cross-check that this shop is bound to the verified body: [3](#0-2) 

`Request#shop` is read directly off the header with no validation against `ShopValidator` or against anything covered by the signature: [4](#0-3) 

The HMAC secret (`api_secret_key`/`client_secret`) is per-app, not per-shop — every shop that has the app installed produces webhook bodies signed with the same app secret. Therefore, a valid `(body, hmac)` pair generated from a webhook delivered for one shop is cryptographically indistinguishable from the same body claimed to originate from any other shop. Since `shop` is not part of `to_signable_string`, swapping the `shop-domain` header while keeping the same body/HMAC pair still passes `HmacValidator.validate`, exactly mirroring the reported bug class: an action (`setNumRows`) performed against the wrong identity (`oracleId` instead of `gcOracleId`) because the field used for identity attribution was never the field actually verified.

### Impact Explanation
An unprivileged internet user who controls (or has observed) any legitimately-signed webhook body for the target app — for example by installing the same public app on their own development/test store and capturing a webhook event whose body content they influence (e.g. a `products/update` payload containing attacker-chosen title/description text) — can resend that exact body and HMAC to the app's public webhook endpoint while substituting an arbitrary victim `shop-domain` header. `Registry.process` will pass HMAC validation and dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen victim shop, causing the receiving application to process attacker-controlled data as if it originated from the victim tenant. This is a cross-tenant identity confusion crossing a tenant boundary using only publicly reachable endpoints and no credentials belonging to the victim, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any consumer of this gem's `Webhooks::Registry.process`/`Request` API for its intended purpose (verifying and routing inbound webhooks) is affected, since the shop/tenant field is never included in the signed material at the library level and no compensating check exists in `process`. An attacker only needs to be a legitimate (even free/trial) installer of the target public app to obtain one valid `(body, hmac)` pair they can reuse against any other shop's identity, which is a low bar and does not require the app's `client_secret`, an access token, or any victim credentials.

### Recommendation
Do not treat the `shop-domain` header as authenticated tenant identity based solely on body-HMAC validation. Either:
- Cross-check the `shop-domain` header against the shop stored in the app's own persisted session/install record for that webhook subscription before routing, or
- Extend `to_signable_string` composition (or add an explicit post-validation check in `Registry.process`) to bind the claimed `shop` value before it is passed to `WebhookMetadata`, rejecting requests where the shop cannot be corroborated against known-installed shops.

### Proof of Concept
1. Install the target public app (built on this gem) on an attacker-controlled development store `attacker-shop.myshopify.com`.
2. Trigger a webhook event with attacker-controlled body content, e.g. update a product title to arbitrary text, causing Shopify to deliver a `products/update` webhook with headers `x-shopify-hmac-sha256: <H>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and body `B`.
3. Capture `(B, H)` — valid under `Utils::HmacValidator.validate` because `H = HMAC(api_secret_key, B)` and does not depend on the shop header.
4. Replay a POST to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) passes HMAC validation (only `B` is checked) and calls the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to apply attacker-controlled data under the victim shop's identity.

          received_signature = verifiable_query.hmac
