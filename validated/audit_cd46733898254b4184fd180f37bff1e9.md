### Title
Stale `account.owner` lets the previous NFT holder keep acting on a transferred position - (File: contracts/controller/src/account.rs)

### Summary
The bug class in CVE-2025-7106 is an access check that is satisfied by the wrong/weak credential. The analog here: the controller stores the owner `Address` inside the `Account` struct at mint time and never re-syncs it when the position NFT changes hands. Mutating entrypoints that authenticate via `require_owner_or_delegate` compare the caller to this stale field — not to the live NFT owner — so after selling or transferring the NFT, the original owner (and any delegates they previously registered) retains full authority over the position now owned by the buyer. [1](#0-0) [2](#0-1) 

### Finding Description
`create_account` writes `owner` into `Account` once, at mint. [3](#0-2)  There is no code path anywhere in `contracts/` that mutates `account.owner` afterwards — no transfer hook, no `update_owner`, and the position-NFT contract has no callback into the controller (`nft_renew_call`, `nft_burn_call`, `nft_try_owner_of_call` are the only outbound NFT calls). [4](#0-3) 

Authorization then splits into two inconsistent primitives:

- `require_account_owner` reads live NFT ownership via `storage::account_owner` and is used by `renew_account` and `set_account_delegate`. [5](#0-4) [6](#0-5) 
- `is_owner_or_delegate` / `require_owner_or_delegate` trust the *stale* `account.owner` field and also accept any delegate registered under it via `storage::get_delegates(env, account_id, owner)`. [2](#0-1) 

`require_owner_or_delegate` gates `load_or_create_account` under the `Migrate` and `Multiply` guards — i.e., the unprivileged `migrate_from_blend` and `multiply` entrypoints — and `account.owner` is also consulted in `positions/supply.rs`, `positions/debt.rs`, and the swap strategies (`swap_collateral`, `swap_debt`, `repay_debt_with_collateral`). [7](#0-6) 

Because `caller.require_auth()` authenticates the *caller* (a real, signing address) and the contract then compares it against the stale owner field, host auth passes cleanly — the failure is purely in the contract's logical owner check, exactly the same shape as the LibreChat "one of several permissions suffices" bug: the wrong credential is treated as sufficient.

### Impact Explanation
After transferring the position NFT to a buyer, the seller (or a manager-delegate they registered before the sale — `set_account_delegate` stores delegates keyed under the stale owner) can still drive `multiply`, `migrate_from_blend`, and the swap-strategy entrypoints against the account. That lets them lever up debt against collateral they no longer own, force collateral/debt swaps on adversarial routes, or migrate positions — degrading the buyer's health factor to the brink of liquidation and extracting value through the strategy outputs. Depending on which entrypoints (e.g., `withdraw`/`borrow` paths in `positions/supply.rs`/`debt.rs`) resolve through `owner_or_delegate` rather than `require_account_owner` — which I could not fully verify within the iteration budget — the impact extends to direct theft of the buyer's collateral. In the worst verified case this is theft of user funds and forced bad debt on the buyer's account.

### Likelihood Explanation
Fully unprivileged and deterministic: the attacker needs only to (1) own an account with collateral, (2) call `position-nft transfer` (explicitly in scope), and (3) sign any owner-or-delegate-gated controller call. No timing, oracle, or liquidity precondition is required — the stale field is permanent for the life of the account. The only mitigating factor is whether the fund-moving paths (`withdraw`, `borrow`) use the live-owner check; if they do, the attack is constrained to position manipulation via strategies, which still supports value extraction and forced liquidation.

### Recommendation
- Treat the NFT as the single source of truth: replace every `account.owner` comparison with `storage::account_owner(env, account_id)` inside `is_owner_or_delegate`, so `require_owner_or_delegate` checks live ownership exactly like `require_account_owner` does.
- Key the delegate list by `account_id` only (or by live owner), so a transfer invalidates prior grants — currently a delegate registered under the seller remains valid because the map key `owner` never changes.
- Alternatively, remove `owner` from `Account` entirely to make stale-credential checks unrepresentable, mirroring the fix pattern of the CVE (check the right permission set, not a convenient subset).

### Proof of Concept
1. Alice calls `supply` → `load_or_create_account` mints account NFT `id` with `account.owner = alice`.
2. (Optional persistence amplifier) Alice calls `add_delegate(alice, id, manager)` while she owns the NFT.
3. Alice transfers NFT `id` to Bob via the position-NFT `transfer` entrypoint. `account.owner` is unchanged — nothing updates it.
4. Bob verifies ownership (`owner_of` returns Bob); Alice no longer has any legitimate claim.
5. Alice calls `multiply(caller=alice, account_id=id, ...)`: `require_authorized_caller` passes (Alice signs), `load_or_create_account` hits `AccountGuard::Multiply` → `require_owner_or_delegate` → `caller == account.owner` (Alice) → authorized. She can lever the account into insolvency; the registered manager-delegate can do the same on any delegate-gated path.
6. If `withdraw`/`borrow` resolve through the same stale check, step 5 becomes a direct drain of Bob's collateral — a straight theft-of-funds exploit.

Key uncertain step: I confirmed `require_owner_or_delegate` gates `Migrate` and `Multiply` and that `account.owner` is referenced in `positions/supply.rs`/`debt.rs`, but did not verify which concrete entrypoints there use it versus `require_account_owner`. The core defect — a permanently stale owner credential accepted by production auth paths — is confirmed.

pub(crate) fn is_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) -> bool {
    if caller == owner {
        return true;
    }
    let active_manager =
        storage::get_position_manager(env, caller).is_some_and(|config| config.is_active);
    active_manager && storage::get_delegates(env, account_id, owner).contains(caller)
}

/// Requires the owner or a registered, active manager delegated by that owner.
pub(crate) fn require_owner_or_delegate(
    env: &Env,
    account_id: u64,
    caller: &Address,
    owner: &Address,
) {
    if is_owner_or_delegate(env, account_id, caller, owner) {
        return;
    }
    panic_with_error!(env, GenericError::NotAuthorized);
}

/// Mints a position NFT and widens its sequential `u32` ID to a `u64` account ID.
pub(crate) fn nft_mint_call(env: &Env, nft: &Address, to: &Address) -> u64 {
    u64::from(PositionNftClient::new(env, nft).mint(to))
}

/// Burns the NFT; IDs outside the mintable `u32` domain fail with `AccountNotFound`.
pub(crate) fn nft_burn_call(env: &Env, nft: &Address, account_id: u64) {
    let token_id = u32::try_from(account_id)
        .unwrap_or_else(|_| panic_with_error!(env, GenericError::AccountNotFound));
    PositionNftClient::new(env, nft).burn(&token_id);
}

/// Returns current NFT ownership. Out-of-range IDs, missing tokens, and failed
/// lookups return `None`, so ownership checks fail closed.
pub(crate) fn nft_try_owner_of_call(env: &Env, nft: &Address, account_id: u64) -> Option<Address> {
    let token_id = u32::try_from(account_id).ok()?;
    match PositionNftClient::new(env, nft).try_owner_of(&token_id) {
        Ok(Ok(owner)) => Some(owner),
        _ => None,
    }
}

/// Renews the NFT `Owner` and owner `Balance` entries to the protocol user TTL window.
/// IDs outside the mintable `u32` domain fail with `AccountNotFound`.
pub(crate) fn nft_renew_call(env: &Env, nft: &Address, account_id: u64) {
    let token_id = u32::try_from(account_id)
        .unwrap_or_else(|_| panic_with_error!(env, GenericError::AccountNotFound));
    PositionNftClient::new(env, nft).renew(&token_id);
}

/// Upgrades NFT Wasm through the controller's owner-gated admin path.
pub(crate) fn nft_upgrade_call(env: &Env, nft: &Address, new_wasm_hash: &BytesN<32>) {
    PositionNftClient::new(env, nft).upgrade(new_wasm_hash);
}
