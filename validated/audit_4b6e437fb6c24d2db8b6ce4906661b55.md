### Title
Webhook `shop` tenant identifier is not bound to the HMAC signature, enabling cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (tenant) identifier is read from an unsigned HTTP header. `Webhooks::Registry.process` validates the HMAC and then hands `request.shop` straight to the application's webhook handler as the trusted tenant identifier, without ever checking that the `shop` value is actually bound to the signed payload.

### Finding Description
The identity binding that should hold is:
`shop_the_HMAC_was_computed_for == shop_the_handler_is_told_the_payload_belongs_to`

In `Request#to_signable_string`, only the raw body is signed: [1](#0-0) 

The `shop` accessor, however, comes from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is completely outside the signed material: [2](#0-1) 

`Webhooks::Registry.process` verifies only the HMAC of the body, then forwards `request.shop` (and `request.topic`, `request.webhook_id`) to the handler as if they were cryptographically part of the same authenticated message: [3](#0-2) 

Because a single app `client_secret` is shared across every shop that installs the app, any body+HMAC pair that is valid for one shop is *also* a valid HMAC for that same body sent under a different shop's header — the signature check in `Utils::HmacValidator.validate` only compares the HMAC digest against the body, never against `shop`: [4](#0-3) 

This is the same bug class as the reference report: an object (there, the applied-vote; here, the webhook payload) is accepted and attributed to an identity (there, the voting node `sign.owner`; here, the `shop` header) that is never checked against the value the signature actually protects.

### Impact Explanation
An attacker who legitimately installs the target app on their own shop (an unprivileged action requiring no special credentials, tokens, or access to `api_secret_key`) receives genuine webhooks for their own shop, each with a valid HMAC over the body. Because that HMAC only covers the body — never the `shop` header — the attacker can replay the same body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` object claiming the payload is `victim-shop.myshopify.com`'s data. If the host application uses `data.shop` (as the docs/tests show is the expected pattern) to look up or write per-tenant records, this leads to cross-tenant data confusion/injection — one merchant's webhook data being attributed to and processed against another merchant's tenant record. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likely, for any app that (a) installs on multiple shops sharing one `client_secret` (the normal Shopify app model) and (b) trusts `WebhookMetadata#shop` for tenant routing without independently cross-checking it — which is exactly the pattern shown in this gem's own tests and docs (`handler.handle` receiving `data.shop` and being expected to key off it). No secrets, tokens, or privileged access are required; only the ability to install the app on an attacker-owned shop, which is the normal unprivileged flow for any Shopify merchant.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signable material, or otherwise cryptographically bind them to the payload before they reach `WebhookMetadata`. At minimum, `Webhooks::Registry.process` should require the caller to supply the expected/allow-listed shop domain(s) for the app's installed shops and reject requests where `request.shop` does not match a shop the app actually has an active installation/session for, rather than trusting the unauthenticated header value directly.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; capture a genuine webhook delivery, e.g. body `{}` for topic `orders/create`, with its real `x-shopify-hmac-sha256` value computed from the app's shared `client_secret`.
2. Replay the exact same HTTP request to the app's webhook endpoint, changing only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged header set (only checks header *presence*, not binding): [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only re-computes the HMAC of `@raw_body` — identical to step 1 — and never inspects `shop`: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop == "victim-shop.myshopify.com"` even though the payload originated from `attacker.myshopify.com`, demonstrating the broken binding.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
