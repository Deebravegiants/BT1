Audit Report

## Title
Unprotected spot-price AMM swap in `SwapFirstAssetTrader::refund_weight` enables sandwich extraction on XCM fee refunds - (File: `cumulus/primitives/utility/src/lib.rs`)

## Summary
`SwapFirstAssetTrader::refund_weight`, used by Asset Hub (Rococo/Westend) and Penpal to refund unused XCM execution fees paid in a non-native, pool-tradeable asset, calls `SwapCredit::swap_exact_tokens_for_tokens(vec![Target::get(), refund_swap_asset], refund, None)` with `amount_out_min = None`. This omits any slippage/minimum-output protection on a swap executed against a live, permissionless `pallet-asset-conversion` pool at spot price, making the refund sandwichable.

## Finding Description
`buy_weight` swaps the user's asset for exactly the fee amount via `swap_tokens_for_exact_tokens`, which is bounded by construction (exact output amount is fixed). `refund_weight`, however, swaps the unused portion of `total_fee` back into the asset the user originally paid with via the unbounded variant `swap_exact_tokens_for_tokens`, explicitly passing `None` for the minimum output: [1](#0-0) 

The underlying pallet logic `do_swap_exact_credit_tokens_for_tokens` in `pallet-asset-conversion` only enforces a minimum-output check when `amount_out_min` is `Some(_)`: [2](#0-1) 

With `None`, this check is skipped entirely, and the swap accepts whatever `get_amount_out` (the standard constant-product spot-price formula) yields from the pool's current reserves at execution time: [3](#0-2) 

`SwapFirstAssetTrader` is configured as part of the production `Trader` tuple on Asset Hub Rococo, Asset Hub Westend, Penpal, and the staking-async parachain runtime, so this code path executes on real chains whenever a user pays XCM fees in a non-native pool asset and the actual weight consumed is less than the weight purchased (the normal case for most XCM messages).

## Impact Explanation
Because the refund swap has no minimum-output bound, an attacker who can influence or predict the relevant asset/native pool's reserves at the time the refund executes can skew the price against the refund direction beforehand, let the swap settle at the manipulated spot price, and reverse the trade afterward to capture the price-impact spread — a standard sandwich pattern. The affected value is bounded by the fee-refund amount (a fraction of the purchased weight fee) and by pool depth, so this is a bounded-value MEV/griefing vector on refunds rather than an unbounded fund-drain, but it is a genuine broken invariant: the refund swap lacks the slippage protection that the corresponding buy-side swap has.

## Likelihood Explanation
The attack is fully permissionless: any user can create a shallow `(Target, X)` pool for an asset `X` and pay XCM fees in `X`, directly controlling the pool depth and thus the price impact achievable against the unprotected refund swap. The manipulated price and resulting attacker profit are deterministically computable in advance from the constant-product formula, and executing the sandwich requires only ordinary, unprivileged AMM trades around the block that processes the refund-triggering XCM message — no elevated privilege, governance action, or victim mistake is required.

## Recommendation
Supply a real `amount_out_min` in `refund_weight` (e.g., derived from a quoted price at `buy_weight` time with a bounded slippage tolerance) instead of `None`, mirroring the implicit bound already present in `buy_weight`'s `swap_tokens_for_exact_tokens` call. Alternatively, avoid a live-pool swap for refunds altogether (e.g., only refund in the `Target` asset, or skip the swap below a configurable threshold) to eliminate the sandwichable code path.

## Proof of Concept
1. Attacker permissionlessly creates a `pallet-asset-conversion` pool for `(Target, X)` with minimal liquidity (bounded only by `MintMinLiquidity`).
2. Attacker sends (or triggers) an XCM message that pays execution fees in `X`, causing `SwapFirstAssetTrader::buy_weight` to run followed by `refund_weight` for the unused weight.
3. Around the block processing this message, the attacker trades against the `(Target, X)` pool to skew the spot price unfavorably for the refund; since `swap_exact_tokens_for_tokens(..., None)` performs no minimum-output check, the refund executes regardless of price.
4. Attacker reverses the trade after the refund settles, capturing the price-impact spread as profit. A unit test in `cumulus/primitives/utility/src/tests/swap_first.rs` mocking a `SwapCredit` implementation that returns an unfavorable-but-nonzero amount for `swap_exact_tokens_for_tokens` when called with `amount_out_min = None` would directly demonstrate that `refund_weight` accepts arbitrarily bad swap outcomes.

		pub fn get_amount_out(
			fee: Permill,
			amount_in: &T::Balance,
			reserve_in: &T::Balance,
			reserve_out: &T::Balance,
		) -> Result<T::Balance, Error<T>> {
			let amount_in = T::HigherPrecisionBalance::from(*amount_in);
			let reserve_in = T::HigherPrecisionBalance::from(*reserve_in);
			let reserve_out = T::HigherPrecisionBalance::from(*reserve_out);

			if reserve_in.is_zero() || reserve_out.is_zero() {
				return Err(Error::<T>::ZeroLiquidity);
			}

			let fee_complement = fee.left_from_one().deconstruct();
			let amount_in_with_fee = amount_in
				.checked_mul(&T::HigherPrecisionBalance::from(fee_complement))
				.ok_or(Error::<T>::Overflow)?;

			let numerator =
				amount_in_with_fee.checked_mul(&reserve_out).ok_or(Error::<T>::Overflow)?;

			let denominator = reserve_in
				.checked_mul(&T::HigherPrecisionBalance::from(Permill::ACCURACY))
				.ok_or(Error::<T>::Overflow)?
				.checked_add(&amount_in_with_fee)
				.ok_or(Error::<T>::Overflow)?;

			let result = numerator.checked_div(&denominator).ok_or(Error::<T>::Overflow)?;

			result.try_into().map_err(|_| Error::<T>::Overflow)
		}
