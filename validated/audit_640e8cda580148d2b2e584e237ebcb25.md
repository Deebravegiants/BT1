### Title
Unbounded router calldata lets an attacker sweep stranded/residual ERC20 balance in `ExternalActionSwap`/`LifiExternalAction` and mint it as their own private output UTXO - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`, `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`LifiExternalAction.callRouter` grants the LI.FI router an unlimited, persistent ERC20 approval and then executes fully attacker-controlled `externalActionMetadata` calldata without ever checking that the router only pulled `inputAmount`. `ExternalActionSwap.swap` measures `swappedAmount` purely as the output-token balance delta of the action contract, so any pre-existing/residual token balance in the action (e.g. left behind by a prior partial-fill router refund, or simply donated via a raw ERC20 transfer) can be consumed by the router call and its resulting output is fully credited to the caller's chosen output UTXO, with no on-chain check tying the output size to the caller's declared `-deltaAmountChanges` for that transaction.

### Finding Description
The invariant that should hold is: *tokens leaving the action in a tx == `-deltaAmountChanges` Hinkal sent it that tx*. This is broken because:

1. In `ExternalActionSwap.swap`, `inputAmount` is computed from `-deltaAmounts[0]` [1](#0-0) , but this value is only used by `callRouter` for the native-ETH branch. For ERC-20 inputs, `LifiExternalAction.callRouter` ignores `inputAmount` entirely and instead grants the router an unlimited approval before executing attacker-supplied calldata verbatim: [2](#0-1) 
2. `swappedAmount` is derived solely from the output-token balance delta measured before/after the router call: [3](#0-2)  There is no corresponding check that the input-token balance of the action decreased by exactly `inputAmount` - the router can pull any amount its calldata specifies (up to the unlimited allowance), including tokens already sitting in the contract from a prior transaction's leftover/refund.
3. The whole computed `amountToSendToHinkal` is transferred out and wrapped into a new UTXO addressed to whatever `stealthAddressStructure` the caller supplied: [4](#0-3) 
4. `Hinkal.transact`'s balance-diff check does not independently validate this either - it only checks that the balance change *at Hinkal* equals `amountChanges[i] + utxoAmount`, where `utxoAmount` is simply the self-reported UTXO amount from the very same action call: [5](#0-4)  Since the action always transfers exactly `amountToSendToHinkal` and reports the same value as `utxoAmount`, this check is a tautology regardless of how large `swappedAmount` actually is - it never ties the output size back to the caller's true committed input.
5. The circuit constraint `inTotal + amountChanges === outTotal` only constrains the ZK-declared numbers the attacker supplies in their own proof; it has no visibility into what the router actually executed on-chain, so it cannot catch this.

**Exploit flow:** A residual ERC20/ETH balance accumulates in the `LifiExternalAction` contract (e.g. a LI.FI partial-fill refund leaves unspent input tokens after a prior swap, since neither `swap()` nor `callRouter()` sweeps or accounts for leftover input balance). Because the router already holds unlimited approval on that token from the earlier call, any subsequent caller submits a new `Hinkal.transact` with a minimal declared `-deltaAmounts[0]` (their own real spend can be tiny) but crafts `externalActionMetadata` so the router pulls the tiny deposit **plus** the stranded residual balance and executes the swap. `swappedAmount` reflects the full (inflated) trade, and the entire proceeds are sent to the attacker's own chosen output UTXO/stealth address, with none of Hinkal's or the circuit's checks detecting the mismatch.

### Impact Explanation
The attacker steals value that was never accounted for by their own `-deltaAmountChanges` - either protocol-stranded dust or another user's leftover deposit from an earlier partial-fill refund - and mints it into their own private UTXO. This is direct theft of in-flight/parked user or protocol funds via the swap external action, matching the Critical category. It is repeatable every time residual balance builds up in the action contract, and an attacker can even manufacture the precondition by chaining two of their own transactions in one block (first leaving a refund/residual, then sweeping it), or simply donating tokens via a raw `transfer` before triggering a swap that ignores the true committed input.

### Likelihood Explanation
Preconditions are easy to reach: the `LifiExternalAction`/router approval is unlimited and persists across calls [6](#0-5) ; LI.FI/aggregator swaps commonly leave unswept residual balances on partial fills; and `externalActionMetadata` is entirely attacker-controlled calldata passed straight to the router [7](#0-6) . No privileged role is required - only the ability to submit a normal `transact` call with a valid proof for the attacker's own (possibly minimal) UTXO input.

### Recommendation
- In `LifiExternalAction.callRouter`, verify that the actual amount pulled from the contract's input-token balance equals `inputAmount` (measure balance before/after on the input side too, not just the output side), and revert if it diverges.
- Replace `approveUnlimited` with a per-call approval scoped exactly to `inputAmount`, reset to zero after the call.
- Sweep/refund any unspent input-token balance back to the depositor (or to Hinkal for re-crediting) at the end of `swap`, rather than leaving it stranded in the action contract.

### Proof of Concept
Foundry plan:
1. Deploy `Hinkal`, `HinkalHelper`, and `LifiExternalAction` with a mock router that supports a "partial fill" mode: on call, it pulls only part of the approved input and swaps it, leaving the rest as ERC20 balance in the action contract (simulating a refund).
2. Tx A: legitimate user calls `Hinkal.transact` with a real proof, `deltaAmounts[0] = -1000e6` USDC; mock router partial-fills, consuming 600e6 and leaving 400e6 USDC stranded in `LifiExternalAction`.
3. Tx B (attacker, same block): calls `Hinkal.transact` with `deltaAmounts[0] = -1` (their own real, tiny spend) but crafts `externalActionMetadata` for the mock router to pull 401e6 USDC (1 wei from new approval headroom + the 400e6 stranded balance) and swap it fully.
4. Assert: `swappedAmount`/`utxoSet[0].amount` in Tx B corresponds to swapping ~401e6 USDC, i.e. `amountToSendToHinkal(TxB) > -deltaAmounts[0](TxB)`-equivalent output, proving output leaving the action in Tx B is backed only by 1 unit of attacker-declared input, not the ~400e6 actually swapped.
5. Assert Hinkal's balance-diff check in Tx B still passes trivially (`balanceDif == amountChanges[1] + utxoAmount`), confirming existing guards did not catch the discrepancy.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
