### Title
Webhook `shop` (tenant identity) field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and exposes an HMAC that is verified against `Utils::HmacValidator`, but the signable string used for that HMAC is the raw request body only. The `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` fields are read directly from unauthenticated HTTP headers and are never included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` passes `request.shop` straight into the handler as the tenant identifier, so the field a host app relies on to bind a webhook to a specific merchant is not bound by the HMAC that supposedly authenticates the request.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are all pulled directly from headers with no cryptographic binding: [2](#0-1) 

`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and only checks that signature against the body-derived signable string — it never touches `shop`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` (an unauthenticated header value) as the tenant identifier to the app's handler: [4](#0-3) 

The documented contract explicitly tells integrators that `Registry.process` "will verify the request did indeed come from Shopify," and that the handler receives `shop` as "the shop domain of the webhook" to be used to route/attribute the payload: [5](#0-4) [6](#0-5) 

This is exactly the reported bug class: a field that is acted upon (`shop`, used as the tenant key by the handler) is not covered by the HMAC that is supposed to authenticate the whole record. The equality that should hold is:

`shop_bound_by_hmac == shop_used_by_handler`

but in this gem, `shop_bound_by_hmac` is undefined (empty set — the HMAC binds nothing but the raw body), while `shop_used_by_handler = request.shop` (attacker-controlled header). The `api_secret_key` used to compute/verify webhook HMACs is per-app, shared across every shop that has the app installed — it is not shop-specific. Because of that, any merchant/shop that has the app installed can capture one of their own genuine webhook deliveries (valid `hmac-sha256` header + raw body), and since the signature is computed only from the body (with the app's single shared secret), that exact `(body, hmac)` pair remains valid regardless of which `shop-domain` header is sent alongside it. An attacker who controls a shop with the app installed can replay that same body/HMAC pair while substituting an arbitrary `shop-domain` header value, and `Registry.process` will accept it as authentic and dispatch it to the handler under the attacker-chosen `shop`.

### Impact Explanation
This crosses a tenant boundary using only unprivileged capabilities: any merchant that installs the app can obtain one valid `(raw_body, hmac)` pair from a webhook Shopify delivers to their own store, then resend that pair with an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header. `Registry.process` will pass the HMAC check (since it only checks the body) and hand the handler a `WebhookMetadata` claiming the payload belongs to a victim shop of the attacker's choosing. Any host application that trusts `data.shop` from this gem to select which tenant's database/records to update (the documented, intended usage pattern) will process attacker-supplied data under a victim shop's identity — i.e., cross-tenant data injection/impersonation via a spoofed webhook. This matches the "cross-tenant access" Critical impact category since it lets one tenant forge events attributed to another tenant purely by manipulating an unauthenticated header.

### Likelihood Explanation
Likelihood is realistic but bounded: it requires the attacker to be a legitimate app user (able to install the app on at least one shop) in order to obtain a valid `(body, hmac)` pair, and it requires the host application to trust `data.shop` as the sole tenant-selection key without any additional out-of-band verification (e.g., checking that the shop is one for which a webhook of that topic/id was actually expected). This is the intended and documented usage pattern shown in `docs/usage/webhooks.md`, so most integrations following the gem's own documentation are exposed.

### Recommendation
Include the tenant-identifying and other trust-relevant fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed payload used for verification, or otherwise cryptographically bind them to the signature verification step (e.g., verify HMAC over a canonical string that concatenates these header values with the body, matching how Shopify signs, if Shopify's signature genuinely only ever covers the body then the gem should not present `HmacValidator.validate` as validating the whole `Request` object — instead it should force integrators to independently and explicitly verify shop ownership/webhook_id uniqueness before trusting `shop`). At minimum, update documentation to make clear that `shop` is unauthenticated and must be cross-checked by the host app against a known/expected shop and webhook subscription before being trusted.

### Proof of Concept
1. App merchant A installs the app; Shopify delivers a real webhook to A's endpoint with body `B` and header `x-shopify-hmac-sha256: H` (valid, since `H = HMAC(app_secret, B)`), and `x-shopify-shop-domain: a.myshopify.com`.
2. Attacker (merchant A) captures `(B, H)`.
3. Attacker resends `raw_body: B`, headers `{ "x-shopify-hmac-sha256" => H, "x-shopify-shop-domain" => "victim.myshopify.com", "x-shopify-topic" => <same topic> }` to the app's webhook endpoint.
4. `ShopifyAPI::Webhooks::Request.new` builds successfully (all required headers present), `Utils::HmacValidator.validate` passes because `to_signable_string` only returns `B`: [1](#0-0) 
5. `Registry.process` dispatches the handler with `shop: "victim.myshopify.com"`: [4](#0-3) 
6. Any host app that stores/updates data keyed by `data.shop` now applies attacker-controlled webhook content to the victim shop's tenant space.

          received_signature = verifiable_query.hmac
