### Title
Arbitrum/Optimism consensus clients accept an attacker-chosen, arbitrarily old L1 state snapshot as the trust root for L2 finality — a "ghost state" replay analogous to CVE-2022-30698 - (File: `modules/ismp/clients/ismp-arbitrum/src/lib.rs`, `modules/ismp/clients/ismp-optimism/src/lib.rs`)

### Summary
CVE-2022-30698 describes Unbound repeatedly refreshing its cache from *child*-supplied delegation data without re-checking that data against the *current* state held by the parent, letting a revoked/rogue domain stay resolvable indefinitely. In Hyperbridge's L2 consensus clients (Arbitrum, Optimism), the L2 finality proof is verified against an L1 state root selected by an attacker-controlled `l1_height` field inside the untrusted `consensus_proof`, with no requirement that this height be the latest, recent, or monotonically increasing relative to any previously used L1 height. This lets a relayer perpetually "refresh" the L2 consensus state using a stale/superseded L1 snapshot instead of the chain's current view, similar to how the DNS resolver kept trusting stale child delegation data.

### Finding Description
`update_client` in `modules/ismp/core/src/handlers/consensus.rs:29-49` invokes `ConsensusClient::verify_consensus(host, consensus_state_id, trusted_state, msg.consensus_proof)` for any submitted `ConsensusMessage` — reachable by any account able to submit an ISMP consensus extrinsic/message (an unprivileged relayer), the same permission level implied by the "single relayed proof" reachability criteria.

In `ArbitrumConsensusClient::verify_consensus` (`modules/ismp/clients/ismp-arbitrum/src/lib.rs:102-125`):
```rust
let ArbitrumUpdate { l1_height, proof } = ArbitrumUpdate::decode(&mut &consensus_proof[..])...
...
let l1_state_machine_height = StateMachineHeight { id: consensus_state.l1_state_machine_id, height: l1_height };
let l1_state_commitment = host.state_machine_commitment(l1_state_machine_height)?;
let state_root = l1_state_commitment.state_root;
```
`l1_height` comes directly from the caller-supplied, unauthenticated `consensus_proof` blob — it is never checked against `consensus_state.finalized_height`, the L1 client's latest height, or any monotonic ordering constraint. The identical pattern exists in `OptimismConsensusClient::verify_consensus` (`modules/ismp/clients/ismp-optimism/src/lib.rs:160-176`).

Once an `l1_height` is chosen, `host.state_machine_commitment(...)` simply fetches whatever L1 state root Hyperbridge has stored for that height (`modules/pallets/ismp/src/lib.rs` bounded commitment map, evicted only after a cap of `MAX_STATE_MACHINE_COMMITMENTS` is exceeded — `insert_bounded_state_commitment`, lines 747-770). Until eviction occurs, arbitrarily old, already-superseded L1 snapshots remain queryable and acceptable as the verification root.

Contrast with the BSC client (`modules/ismp/clients/bsc/src/lib.rs:88-93`), which explicitly enforces `consensus_state.finalized_height >= bsc_client_update.source_header.number.low_u64()` to reject going backwards or replaying stale headers. No equivalent staleness/monotonicity guard exists for the Arbitrum/Optimism `l1_height` selection or for the resulting `consensus_state.finalized_height` update (`ismp-arbitrum/src/lib.rs:174,214`, `ismp-optimism/src/lib.rs:210,254`), which is unconditionally overwritten with whatever `state.height.height` the proof produced — without a check that it exceeds the previous `finalized_height`.

Practically, this means a relayer can:
1. Capture an L1 state snapshot at height *H* where a rollup contract still shows a not-yet-invalidated assertion/output claim (e.g., before a fraud-proof/challenge resolves it on L1, or before the sequencer inbox is later reorganized/corrected).
2. Submit a `ConsensusMessage` referencing `l1_height = H` together with a valid Merkle/storage proof rooted at that old L1 state root.
3. Have Hyperbridge accept and store the resulting (stale) L2 `StateCommitment` as the current/finalized L2 state — even though the live L1 chain has since superseded or invalidated that assertion — because nothing forces `l1_height`/`finalized_height` to be recent or monotonically advancing.

This is the direct analog of the "ghost domain" pattern: a downstream (child/L2) commitment is kept perpetually "resolvable"/valid by continually re-deriving it from historic, no-longer-authoritative parent (L1) data, instead of the parent's current state.

### Impact Explanation
If exploited, this allows forged or stale L2 state commitments to be accepted by Hyperbridge as canonical, which downstream is used by `HandlerV2.sol` (`evm/src/core/HandlerV2.sol`) and pallet-ismp handlers to verify state/non-membership proofs for cross-chain messages, token bridge mint/burn, and intents. Accepting a stale/invalidated L2 state root as authoritative could let an attacker forge message delivery or unsound state commitments for the L2 chain, directly matching the "unsound state commitment / forged message delivery" impact class.

### Likelihood Explanation
Exploitability depends on (a) the eviction window (`MAX_STATE_MACHINE_COMMITMENTS`) still holding a stale/exploitable L1 height, and (b) the attacker being able to produce a valid proof against that stale L1 root pointing at rollup state that has since been invalidated/superseded on L1 (e.g., a since-resolved-fraudulent Arbitrum assertion, or an Optimism output/dispute-game outcome later overturned). This requires specific timing but is reachable purely via a single permissionless consensus-update submission — no privileged role is needed.

### Recommendation
Enforce that `l1_height` (and the derived `consensus_state.finalized_height`) is monotonically non-decreasing relative to the consensus state's previously recorded L1/L2 heights, mirroring the staleness check already present in the BSC client (`modules/ismp/clients/bsc/src/lib.rs:88-93`). Additionally, consider requiring `l1_height` to be within a bounded recency window of the L1 client's current latest height, and re-validate that referenced rollup assertions/output roots have not since been challenged/removed before accepting them as the L2 finality root.

### Proof of Concept
Conceptual (proof construction against real Arbitrum/Optimism contracts is required for full PoC, not derivable purely from the indexed code):
1. Relayer observes L1 height `H` where the target rollup contract shows assertion/output claim `C` as valid (not yet finalized-invalid).
2. Relayer waits for Hyperbridge's L1 light client to advance past `H`, and for `C` to later be successfully challenged/overturned on L1.
3. Relayer submits `ConsensusMessage` with `ArbitrumUpdate{ l1_height: H, proof: <valid Merkle proof of C against L1 state at H> }` (or the Optimism equivalent).
4. `ArbitrumConsensusClient::verify_consensus` (`modules/ismp/clients/ismp-arbitrum/src/lib.rs:124-125,174`) fetches the stale L1 commitment at `H`, verifies the proof successfully (it's cryptographically valid against that old root), and overwrites `consensus_state.finalized_height` / stores the corresponding (now-stale) L2 `StateCommitment` as current — with no check rejecting the outdated `H`. pub fn update_client<H>(host: &H, msg: ConsensusMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host.consensus_client_id(msg.consensus_state_id).ok_or(
		Error::ConsensusStateIdNotRecognized { consensus_state_id: msg.consensus_state_id },
	)?;
	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;
	host.is_consensus_client_frozen(msg.consensus_state_id)?;
	host.is_expired(msg.consensus_state_id)?;

	let (new_state, intermediate_states) = consensus_client.verify_consensus(
		host,
		msg.consensus_state_id,
		trusted_state,
		msg.consensus_proof,
	)?;
	host.store_consensus_state(msg.consensus_state_id, new_state)?;
	let timestamp = host.timestamp();
	host.store_consensus_update_time(msg.consensus_state_id, timestamp)?;

		/// Insert a state commitment into the bounded map. ISMP does not allow
		/// duplicate state updates so we don't have an overwrite path.
		///
		/// Appends the height to the per-chain [`StateCommitmentQueue`] and, once
		/// the chain's cap is exceeded, evicts oldest-first from the queue head.
		/// Evictions are limited to [`MAX_COMMITMENT_EVICTIONS_PER_INSERT`] per
		/// call so a lowered cap drains over many insertions rather than in one.
		pub fn insert_bounded_state_commitment(
			height: StateMachineHeight,
			commitment: StateCommitment,
		) {
			let cap = Self::state_machine_commitment_cap(height.id).max(1) as u64;
			let mut state = CommitmentQueueStates::<T>::get(height.id);

			StateCommitmentQueue::<T>::insert(height.id, state.tail, height.height);
			state.tail += 1;

			let excess = (state.tail - state.head)
				.saturating_sub(cap)
				.min(MAX_COMMITMENT_EVICTIONS_PER_INSERT as u64);
			for _ in 0..excess {
				if let Some(old) = StateCommitmentQueue::<T>::take(height.id, state.head) {
					BoundedStateCommitments::<T>::remove(height.id, old);
					BoundedStateMachineUpdateTime::<T>::remove(height.id, old);
				}
				state.head += 1;
			}

			CommitmentQueueStates::<T>::insert(height.id, state);
			BoundedStateCommitments::<T>::insert(height.id, height.height, commitment);
		}
