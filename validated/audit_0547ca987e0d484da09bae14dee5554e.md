### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor that is used by consuming apps to identify which merchant a webhook belongs to, but this value is read directly from the `X-Shopify-Shop-Domain` HTTP header and is **not** included in the bytes that are HMAC-verified. An attacker who controls one legitimate, validly-signed webhook delivery (e.g. from their own installed shop) can swap the `shop-domain` header for a different shop while keeping the same body/HMAC, and the signature check still passes.

### Finding Description
`Request#to_signable_string` (the value verified by `Utils::HmacValidator.validate`/`OpenSSL.secure_compare`) is defined as: [1](#0-0) 

It returns only `@raw_body`. Meanwhile, the tenant-identifying field used by consuming applications to route/process the webhook, `shop`, is derived straight from an HTTP header that is entirely outside the signed payload: [2](#0-1) 

The `hmac` getter used for comparison also only reads the `hmac-sha256` header, decoded and re-hex-encoded, and is checked against `to_signable_string` (body only): [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop` (the tenant the app will act on behalf of) == `shop` covered by the verified HMAC bytes. Here, `shop` is parsed from an unauthenticated header while the HMAC only authenticates the body, so the equality is broken: an attacker can present `(body, hmac)` that were legitimately signed for shop A, but pair them with a `X-Shopify-Shop-Domain: shop-b.myshopify.com` header. `HmacValidator.validate` still returns `true` because it never inspects the header, and `request.shop` now returns `shop-b.myshopify.com`.

This mirrors the reported bug class of "a field acted on but not covered by the HMAC": in the original AI Arena report, the identity/ownership boundary (`fighterOwner`/`tokenId`) drifted out of sync with the value actually protected by state checks; here, the identity boundary (`shop`) drifts out of sync with the bytes actually protected by the cryptographic signature.

### Impact Explanation
Any app built on this gem that uses `ShopifyAPI::Webhooks::Request#shop` to decide which merchant/tenant record to update, delete, or act upon (a standard and expected usage pattern for multi-tenant Shopify apps processing webhooks) is exposed to cross-tenant data corruption or spoofed events: an attacker who is a legitimate installed merchant of the app (an "unprivileged internet user" relative to other tenants) can capture one of their own genuine webhook deliveries and replay it against the app's webhook endpoint with the `shop-domain` header rewritten to target a different, arbitrary shop that also uses the app. Because signature validation never touches that header, the forged event is accepted as authentic for the victim shop. This is a tenant-identity/authentication-boundary violation — the shop the request claims to represent is not the shop whose secret produced the signature — and requires no possession of `api_secret_key`, no TLS interception, and no privileged account; only a normal merchant's own valid webhook traffic is needed.

### Likelihood Explanation
Likelihood is high for any app that follows the documented usage of this class (using `request.shop` to key data) because the vulnerable code path is exercised on every webhook the gem helps validate; the header can be freely set on any HTTP replay by the attacker's own server, and Shopify's webhook delivery/HMAC design intentionally signs only the body — this library does not compensate by also binding the shop header into the signed bytes or independently cross-checking it.

### Recommendation
Bind the `shop` (and ideally `topic`, `api-version`, `webhook-id`) headers into the value that is HMAC-verified, or require callers to separately validate that `shop` matches an expected/registered shop for the given `webhook_id`/topic before trusting it. At minimum, `to_signable_string` should not silently exclude header-derived identity fields that downstream code (as documented) is expected to trust for tenant routing.

### Proof of Concept
```ruby
require "shopify_api"

ShopifyAPI::Context.setup(
  api_key: "key",
  api_secret_key: "secret",
  api_version: "2024-01",
  is_embedded: true,
  is_private: false
)

raw_body = '{"id":1,"note":"hello"}'
valid_hmac = Base64.strict_encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", raw_body)
)

# Legitimate webhook, genuinely delivered for "attacker-shop.myshopify.com"
legit_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac,
  "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
  "x-shopify-api-version" => "2024-01",
  "x-shopify-webhook-id" => "abc"
}

# Attacker replays the SAME body/hmac but swaps only the shop-domain header
forged_headers = legit_headers.merge(
  "x-shopify-shop-domain" => "victim-shop.myshopify.com"
)

req = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

ShopifyAPI::Utils::HmacValidator.validate(req) # => true (HMAC only covers raw_body)
req.shop # => "victim-shop.myshopify.com"  -- spoofed tenant, HMAC still valid
```
The app's webhook consumer, trusting `HmacValidator.validate(req) == true` and using `req.shop` to select the tenant to act on, will process this forged request as if it legitimately originated from `victim-shop.myshopify.com`.
