### Title
Webhook Shop Identity Spoofing via HMAC Signature Not Covering the `shop-domain` Header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` to identify and dispatch the webhook come from separate, unsigned HTTP headers. This breaks the identity binding `HMAC-verified bytes == data acted upon`, allowing a party who legitimately receives one valid signed webhook (e.g. for their own shop) to relabel it as belonging to a different shop and have the host application's webhook handler process it under the wrong tenant.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are not part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` and compares it against `hmac`, so it only ever authenticates the body bytes, never the header values: [3](#0-2) 

`Registry.process` trusts `request.shop` (and `topic`/`webhook_id`) straight out of the unauthenticated headers to build the `WebhookMetadata` passed to the app's handler, once the (body-only) HMAC check passes: [4](#0-3) 

The equality that should hold is: `shop value covered by HMAC == shop value the handler acts on`. In reality: `HMAC covers raw_body only`, while `handler acts on request.shop`, which is read from `X-Shopify-Shop-Domain` / `shopify-shop-domain`, a field entirely outside the signed scope. Consequently, any request with a body+HMAC pair that was validly generated by Shopify for one shop remains HMAC-valid if the shop-domain (or topic/webhook_id) headers are swapped for a different value, since none of those headers are inputs to the signature.

### Impact Explanation
This is a cross-tenant identity confusion vector: an attacker who is themselves a merchant with the app installed will legitimately receive genuine, correctly-HMAC-signed webhook deliveries for their own shop. By replaying that exact body+HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header (and/or `topic`/`webhook_id`) with a victim shop's identifier, the request still passes `HmacValidator.validate` (which never inspects those headers), and `Registry.process` will hand the host app's webhook handler a `WebhookMetadata` claiming the body originated from the victim shop. Any app logic that trusts `WebhookMetadata#shop` to select the tenant's data/session to act on (a common and encouraged pattern) can be made to apply attacker-controlled body content under another merchant's identity — a cross-tenant access condition.

### Likelihood Explanation
Likelihood is constrained: it requires the attacker to possess at least one genuine signed webhook of their own (trivial — any app-installing merchant receives these) and requires the host application's handler to key tenant-specific behavior off `WebhookMetadata#shop`/`topic`/`webhook_id` without independently re-validating them — a pattern the library's own API surface (`WebhookMetadata`) implicitly encourages since those fields are exposed as if they were part of the verified payload.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for HMAC verification (or otherwise cryptographically bind them to the body), so that `Utils::HmacValidator.validate` fails if any of those header values are altered relative to what Shopify originally signed for that specific delivery.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook delivery with headers:
   - `x-shopify-topic: orders/create`
   - `x-shopify-hmac-sha256: <valid HMAC over body>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - body: `{"id": 1, "note": "..."}`
2. Attacker resends the identical body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `request.to_signable_string` (the unchanged raw body) — validation succeeds. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: ..., ...)`, so any app logic keyed on `data.shop` operates as though this attacker-supplied body genuinely originated from `victim-shop.myshopify.com`.

          received_signature = verifiable_query.hmac
