## Finding

### Title
Webhook shop/topic identity spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then blindly trusts the `shop`, `topic`, `webhook_id`, and `api_version` values taken from HTTP headers — none of which are covered by that HMAC — to build the `WebhookMetadata` handed to the host application's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers with no cryptographic binding to the body or to each other: [2](#0-1) 

`Registry.process` validates the HMAC (which only proves the body bytes were signed by the app's shared `api_secret_key` at some point) and then immediately trusts the header-derived `request.shop`/`request.topic`/`request.webhook_id` to construct the metadata passed to the application handler: [3](#0-2) 

The identity binding this breaks is: `shop authenticated (via HMAC of the payload) == shop attributed to that payload by the handler`. In fact, the HMAC only proves "some body was produced using this app's `api_secret_key`" — it says nothing about which shop, topic, or webhook id that body belongs to. Because `api_secret_key` is shared across *every* shop that installs the app (it is not shop-specific), any merchant who has legitimately installed the app can capture a real `(raw_body, hmac)` pair delivered to their own webhook endpoint (e.g., by configuring their own delivery URL, or via a compromised/curious middlebox on their own store) and then replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a *different* victim shop. `Utils::HmacValidator.validate` will still pass because it only checks the body: [4](#0-3) 

### Impact Explanation
This allows cross-tenant data injection/spoofing: an unprivileged merchant who has installed the app (not the app owner, and without access to `api_secret_key`, access tokens, or any privileged credential) can cause the host application to process fabricated webhook events "as if" they originated from an arbitrary other shop using the same app, since the shop identifier consumed by the handler is never bound to the authenticated bytes. This crosses a tenant boundary using only a legitimately-obtained signed payload from the attacker's own store, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any shop that installs the app can trivially obtain a valid `(body, hmac)` pair for topics of its choosing by triggering real events on its own store (orders, products, etc.) and capturing the webhook delivery to its own controlled endpoint. Replaying that pair against the app's public webhook endpoint with a forged `shop`/`topic` header requires no secret material and no special access — it is directly reachable by any actor who can install the app on a store they control, which is a low bar.

### Recommendation
Bind the shop/topic/webhook identity to the authenticated bytes: include `shop`, `topic`, and `webhook_id` in the HMAC-signed material (or otherwise cryptographically bind them, e.g. by verifying the shop domain against a previously known, session-derived, per-shop secret rather than an unauthenticated header), so that a signed body from shop A cannot be attributed to shop B by simply changing request headers.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and configures/observes a webhook delivery for topic `customers/create`, capturing the raw POST body and its `X-Shopify-Hmac-Sha256` header (both legitimately produced by Shopify with the app's shared `api_secret_key`).
2. Attacker sends this exact `(raw_body, hmac)` pair to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `raw_body` only and it matches, so `Registry.process` proceeds.
4. The application handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker-supplied body, even though that data never came from `victim.myshopify.com`, resulting in cross-tenant data injection/spoofing.
