### Title
Webhook shop identity spoofing via unauthenticated `X-Shopify-Shop-Domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identifier (`shop`) from the `X-Shopify-Shop-Domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `Webhooks::Registry.process` validates only covers the raw request body, not this header. This breaks the identity binding between "the bytes Shopify actually signed" and "the shop identity the app acts on," allowing a holder of one legitimately-signed webhook payload (e.g., from their own store) to replay it while claiming it belongs to a different shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `shop` is read straight from an attacker-controllable header with no cross-check against the signed payload: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which calls `compute_signature(verifiable_query.to_signable_string, secret)` — i.e. it HMACs only the raw body — and then, once that check passes, forwards `request.shop` (the unauthenticated header) straight to the handler as the tenant identity: [3](#0-2) [4](#0-3) 

The equality the code assumes is:
`shop used to authorize/process the event == shop covered by the verified HMAC`

but the actual binding is:
`shop used to process the event = X-Shopify-Shop-Domain header (unauthenticated) ≠ shop bound by HMAC(secret, raw_body)`

Because the shop identifier is never part of the signed material, any request that reuses a validly-signed body (raw bytes + genuine HMAC digest) will pass `HmacValidator.validate` regardless of which shop-domain header accompanies it. A merchant/attacker who operates their own shop can trigger webhooks against their own store (getting Shopify to sign an arbitrary/attacker-influenced payload, e.g. product or customer webhooks with attacker-supplied data), capture the `X-Shopify-Hmac-Sha256` header and raw body, and replay that exact body with a forged `X-Shopify-Shop-Domain` header pointing at a victim shop. `Webhooks::Registry.process` will accept it as valid and dispatch it to the handler tagged with the victim's shop: [5](#0-4) 

Host applications typically use `WebhookMetadata#shop` to select which merchant's session/data store to update, so this allows cross-tenant data injection/spoofing without possessing the app's `client_secret` or any victim credentials — only a legitimately signed webhook from any shop is required.

### Impact Explanation
This is a cross-tenant identity binding failure: the field the application trusts to identify *which* shop an event belongs to (`shop`, from the header) is disjoint from the field actually authenticated by HMAC (the raw body). This enables an attacker to make the host application believe an event originated from a shop it did not, corrupting per-tenant data/state in any app that relies on `WebhookMetadata.shop` for authorization or routing without further validation — a cross-tenant access impact.

### Likelihood Explanation
Medium-to-High: any user who can install the app on a shop they control (or otherwise obtain one authentic webhook body+signature pair, which Shopify sends automatically on standard store events) can perform this replay against the same app's webhook endpoint for any other shop, requiring no secrets, tokens or privileged access.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the signed/verified material, or otherwise cryptographically bind the header values to the payload before trusting them — e.g., verify that `X-Shopify-Shop-Domain` matches a shop associated with the specific `webhook_id`/subscription via a server-side lookup, or require the caller to additionally prove shop identity out-of-band (mutual TLS, per-shop webhook secrets, or including shop in the HMAC-signable string) rather than trusting the raw header once the body-only HMAC passes.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and receives a real webhook from Shopify:
raw_body = '{"id": 1, "note": "hello"}'
real_hmac = <captured from Shopify's genuine X-Shopify-Hmac-Sha256 header for attacker's own shop>

# Attacker replays the identical, validly-signed body against the app's webhook
# endpoint but swaps the shop-domain header to the victim:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac,       # still valid: HMAC only covers raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (body/HMAC unchanged),
#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
#    is invoked, spoofing the event as belonging to the victim shop.
