### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook exclusively by verifying an HMAC over the raw request body, but the `shop` (and `topic`/`webhook_id`) values that are handed to the application's webhook handler are read directly from unauthenticated HTTP headers that are never included in the signed payload. This breaks the identity binding `shop_authenticated == shop_delivered_to_handler`, letting anyone who can obtain one validly-signed webhook body (e.g., from their own connected shop) relabel it as coming from an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` (`lib/shopify_api/utils/verifiable_query.rb`) with: [1](#0-0) 
`hmac` is derived from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers with no cryptographic relationship to the body or the signature: [3](#0-2) 

`Registry.process` validates only the body's HMAC, then forwards the header-derived `shop` to the handler untouched: [4](#0-3) 
`Utils::HmacValidator.validate` recomputes the HMAC purely from `to_signable_string` (the raw body) and compares it to the header-derived signature — it never binds `shop` into the signed value: [5](#0-4) 

Because the signature covers only the body bytes, and `shop-domain` is a separate, unsigned header, the equality the gem implicitly relies on — "the HMAC-verified bytes correspond to the shop attributed to this webhook" — does not hold. Any attacker who possesses one legitimately-signed webhook body (trivial to obtain: install the target app on their own shop and receive one real webhook) can resend that exact body with the `X-Shopify-Shop-Domain` header (and, independently, `X-Shopify-Topic`) changed to any value they choose. `Utils::HmacValidator.validate` will still return `true` because it only checks the body against the secret, and `Registry.process` will dispatch the payload to the handler tagged with the attacker-chosen `shop`.

### Impact Explanation
This is a cross-tenant identity spoofing primitive: the host application's webhook handler receives data it believes originated from shop `S_victim`, when it actually originated from an event on the attacker's own shop `S_attacker`, replayed with a forged header. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up the merchant's stored access token, to trigger uninstall/data-deletion flows, to attribute customer/order data, or to select which tenant's session/cache entry to mutate), this can lead to cross-tenant data corruption or to actions being taken against a merchant who never sent the webhook — satisfying the "cross-tenant access" Critical impact criterion, since the identity binding between authenticated bytes and the tenant identifier is broken entirely within this gem's own webhook-processing code.

### Likelihood Explanation
Low-to-Medium. It requires the attacker to obtain at least one validly HMAC-signed webhook body, which is straightforward if the attacker is themselves able to install the app on their own store (a normal unprivileged action for most public apps) and capture one of their own real webhook deliveries. No access token, `client_secret`, or privileged account is required — only network access to POST a crafted HTTP request to the app's public webhook endpoint with a substituted `shop-domain` header.

### Recommendation
Bind the tenant identity into the authenticated material instead of trusting an unsigned header:
- Extend `VerifiableQuery#to_signable_string` for `Webhooks::Request` (or otherwise fold `shop`, `topic`, and `webhook_id` into the HMAC computation) so that any change to these header values invalidates the signature.
- Alternatively/additionally, cross-check the header-derived `shop` against the shop embedded in the JSON body where Shopify includes it for the relevant topic, rejecting mismatches.
- Document clearly (and enforce in code) that `WebhookMetadata#shop` must not be trusted for tenant lookup unless it has been independently verified against signed content.

### Proof of Concept
1. Attacker installs the target app on their own development/test shop `attacker-shop.myshopify.com` and configures a webhook subscription (e.g., `orders/create`).
2. Attacker triggers the webhook and captures the raw POST body `B` and its valid `X-Shopify-Hmac-Sha256` header value `H` (computed by Shopify over `B` with the app's real secret).
3. Attacker resends an HTTP POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only, matches `H`, and returns `true`.
5. `Registry.process(request)` proceeds and invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host application to process `attacker-shop`'s event data as if it belonged to `victim-shop`. [6](#0-5) [7](#0-6)
