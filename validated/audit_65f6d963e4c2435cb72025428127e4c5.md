## Title
Fee-token swaps via `swapETHForExactTokens` have no independent price bound, letting the router-quoted price be sandwiched up to the caller's full `msg.value` — ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.placeOrder()` and three `EvmHost` entry points (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) convert a caller-supplied native-token payment into the protocol fee token via UniswapV2's `swapETHForExactTokens`. This is the same bug class as the external report: the swap's price protection is not an independently chosen minimum/maximum, but is implicitly whatever `msg.value` happens to be. Any unprivileged caller who submits one of these transactions with native value can be sandwiched, and the attacker extracts the difference between the fair price and the price the victim implicitly accepted by sending extra ETH as buffer (which the SDK/docs explicitly recommend doing).

### Finding Description
`placeOrder()` swaps native ETH for the fee token like this: [1](#0-0) 

```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    if (msgValue > 0) {
        address uniswapV2 = IDispatcher(hostAddr).uniswapV2Router();
        address WETH = IUniswapV2Router02(uniswapV2).WETH();
        address[] memory path = new address[](2);
        path[0] = WETH;
        path[1] = feeToken;
        uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
            order.fees, path, address(this), block.timestamp
        );
        msgValue -= amounts[0];
    } else {
        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    }
    _orders[commitment][TRANSACTION_FEES] = order.fees;
}
```

`swapETHForExactTokens(amountOut, path, to, deadline)` uses `msg.value` as the implicit `amountInMax` — the router will happily spend up to the entirety of `msgValue` to obtain the exact `order.fees` output, reverting only if the price is so bad that even the full `msg.value` cannot buy `order.fees`. There is no caller-supplied cap between "exact quoted price" and "all of msg.value" — the equivalent of the sandwich report's "minimum output can be set to zero," here it's "maximum input can effectively be set to the caller's whole native balance."

The exact same pattern exists in `EvmHost`: [2](#0-1) [3](#0-2) [4](#0-3) 

All four call sites are reachable by any unprivileged account submitting a single transaction that pays the dispatch/order/fund-request fee in native token, matching the required Hyperbridge entry-point classes (`EvmHost` dispatch and Intent Gateway escrow).

Because the SDK explicitly instructs callers to send a buffer above the quoted `nativeValue` ("unused native is refunded"), and the test suite itself demonstrates sending `5 ether` for a fee that costs a tiny fraction of that: [5](#0-4) 

a searcher watching the mempool can front-run the swap (buying WETH→feeToken to move the price against the pending swap), let the victim's `swapETHForExactTokens` execute at the worsened price (consuming far more of the buffer than the fair price would require), and back-run to restore the pool and capture the difference. The victim/protocol loses native token value with no on-chain check that the executed price was close to the market price — the deadline parameter (`block.timestamp`) provides no price protection at all, only staleness protection.

### Impact Explanation
Each affected call moves real value (native ETH sent by the order placer, the relayer/dispatcher, or the fee funder) through an AMM swap that has no independent slippage bound tighter than "the entire amount the caller sent." An attacker can extract this difference as MEV profit on every `placeOrder`, `dispatch`, or `fundRequest` call paid in native token, directly transferring value from ordinary Hyperbridge users to the attacker. This is concrete value extraction, matching the External Report's Medium-risk classification for the analogous `VoltBurn.buyNSendToVoltTreasury()` sandwich issue.

### Likelihood Explanation
Any of these functions can be invoked permissionlessly by anyone paying fees in native token — this is normal, expected usage documented in the SDK guides, not an edge case. Sandwich bots systematically watch mempools for AMM interactions with weak/no slippage protection, so exploitation likelihood is high whenever native-token fee payment with buffer is used, which the SDK actively recommends.

### Recommendation
Add an explicit, caller-supplied `amountInMax` (independent of `msg.value`) for these fee swaps and pass it to `swapETHForExactTokens`, refunding any `msg.value` above that bound before/instead of relying on the router's implicit cap. Alternatively, expose a `maxNativeAmount`/slippage parameter in `Order`/`DispatchPost`/`DispatchGet`/`fundRequest` calls that the caller sets based on their own quote, and validate it on-chain, mirroring the recommendation given for `VoltBurn`.

### Proof of Concept
1. Attacker monitors mempool for a `placeOrder` call carrying `msg.value` well above the current WETH→feeToken quote (as SDK-recommended buffering, e.g., the `5 ether` buffer in `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`).
2. Attacker front-runs with a large WETH→feeToken swap on the same UniswapV2 pool used by `IDispatcher(hostAddr).uniswapV2Router()`, moving the price so that buying `order.fees` feeToken now costs much more WETH.
3. Victim's `placeOrder` executes `swapETHForExactTokens{value: msgValue}(order.fees, ...)`, which now consumes a far larger portion of `msgValue` to obtain the exact `order.fees` output (still succeeds as long as `msgValue` covers the inflated price).
4. Attacker back-runs, selling feeToken back to WETH, netting the price difference — extracted from the victim's `msgValue` — as profit, while the victim's refunded surplus (`msgValue -= amounts[0]`) is correspondingly smaller. [1](#0-0) [2](#0-1)
