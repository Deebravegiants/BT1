### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the `x-shopify-hmac-sha256` signature verifies the body bytes alone. The `shop-domain` header — which is exposed via `Request#shop` and forwarded into `WebhookMetadata#shop` for every registered handler — is never included in the signed content. An attacker who can obtain one valid `(body, hmac)` pair for the app (e.g. as the merchant of their own shop that has the app installed) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `HmacValidator.validate` will report success, and the handler will process the payload as if it originated from the victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` and compares it against the received HMAC: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

But `shop` is read from a separate, unsigned header and exposed as trusted tenant data: [3](#0-2) 

`Registry.process` validates only the HMAC, then hands `request.shop` straight into `WebhookMetadata`, which is the value app code uses to key per-tenant sessions/state: [4](#0-3) [5](#0-4) 

This is precisely the "field acted on but not covered by the HMAC" identity-binding break: the equality the gem should guarantee is `shop_bound_by_hmac == shop_used_by_handler`, but in reality `shop_covered_by_hmac = ∅` while `shop_used_by_handler = header("shop-domain")`. Contrast this with the OAuth flow, where the analogous field *is* correctly bound into the signed content — `Auth::Oauth::AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameter set: [6](#0-5) 

That the OAuth path deliberately binds `shop` into the signature, while the webhook path does not, confirms the omission is a real inconsistency in the gem's own identity-binding guarantees rather than an inherent limitation of HMAC webhooks.

### Impact Explanation
Because `api_secret_key` is shared across all shops that have installed a given app, any merchant using the app (a legitimate but unprivileged "internet user" from the app's perspective) can capture one authentic `(body, hmac)` pair delivered to their own endpoint. They can then replay that same body/HMAC to the app's webhook endpoint with a forged `shop-domain` header pointing at a different, victim shop that also uses the app. Since `HmacValidator.validate` never inspects the shop header, the forged request passes validation and `WebhookMetadata#shop` reports the attacker-chosen shop. Any host application that uses `data.shop` to look up a session, write per-tenant records, or gate business logic (the intended and documented use of this field) will act on attacker-controlled data under the guise of a valid signature, producing cross-tenant data injection into another merchant's records.

### Likelihood Explanation
Exploitation only requires the attacker to run the app on their own shop and be able to send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — no access token, `client_secret`, or privileged access is needed. The bug is deterministic: the shop header is categorically excluded from `to_signable_string`, not merely mis-validated in an edge case.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`api-version`/`webhook-id`) header value in `Request#to_signable_string`, or otherwise cryptographically bind the shop identity to the HMAC-covered content, so that `HmacValidator.validate` fails whenever the `shop-domain` header does not match the value the signature was computed over.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and on victim `victim-shop.myshopify.com`.
2. Shopify sends the attacker a legitimate webhook: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, valid `x-shopify-hmac-sha256: H` computed as `HMAC(api_secret_key, B)` (per `to_signable_string`).
3. Attacker replays the same request to the app's webhook endpoint, keeping body `B` and HMAC `H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` — still equal to `H` — so validation succeeds.
5. The registered handler receives `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and processes/stores data under the victim's tenant identity despite the payload never having been sent by Shopify for that shop.
