## Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values that are handed to the app's webhook handler as the trusted identity of the sending merchant come from HTTP headers that are **not** included in the HMAC-signed payload. Since the signing secret (`api_secret_key`, the app's `client_secret`) is shared by every shop that has installed the app, any shop that legitimately receives one authentic webhook can replay that exact `(raw_body, hmac)` pair while swapping the `X-Shopify-Shop-Domain` header, and the library will report the event as coming from an arbitrary victim shop.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature purely from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only the raw body — none of the Shopify-supplied headers are part of the signed material: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are read directly from HTTP headers that are outside the HMAC's coverage: [3](#0-2) 

`Registry.process` validates only the HMAC and then forwards these unauthenticated header values straight to the app's handler as `WebhookMetadata`, treating `request.shop` as the verified identity of the originating merchant: [4](#0-3) 

The documentation explicitly states that `Registry.process` "will verify the request did indeed come from Shopify," implying the gem is responsible for authenticating both the sender *and* the identity fields it hands to the handler: [5](#0-4) 

**Binding that should hold but doesn't (as an equality):** `hmac_signed_bytes` should equal `bytes_that_determine(shop, topic, webhook_id, api_version)`. In reality: `hmac_signed_bytes == raw_body` only, while `shop == header["x-shopify-shop-domain"]`, entirely disjoint from the signed material. Because the HMAC secret is the app's single `api_secret_key` shared across *all* shops that installed the app (not a per-shop secret), a valid `(raw_body, hmac)` pair obtained from one shop's genuine webhook remains valid when replayed with a different shop-domain header. This breaks the identity binding `authenticated_sender == shop_the_handler_believes_it_is`.

### Impact Explanation
This enables cross-tenant confusion/spoofing between shops that share the same app installation: a malicious merchant (an unprivileged actor with respect to other tenants of the same app) who legitimately receives one authentic webhook can replay it, substituting an arbitrary victim shop's domain in the `X-Shopify-Shop-Domain` header. `Registry.process` still validates because the HMAC only checks body integrity, and the app's webhook handler executes business logic (order/product creation events, job enqueuing, database updates, etc.) believing the event genuinely originated from the victim shop. Depending on the host app's handler logic, this can lead to cross-tenant data corruption, unauthorized state changes, or being tricked into acting on behalf of another merchant — this falls under cross-tenant access.

### Likelihood Explanation
Any party that can install (or has installed) the target app on their own shop qualifies as attacker-capable: they can capture one legitimate webhook `(raw_body, hmac)` from Shopify for a topic of interest and then replay it directly to the app's public webhook endpoint with a forged `shop-domain` header, no access to `api_secret_key` or any privileged credential required. The library performs no additional binding check between the HMAC-authenticated bytes and the shop/topic metadata it extracts and forwards to handlers.

### Recommendation
Bind the shop domain (and ideally topic/webhook_id/api_version) into the HMAC-verified material, or independently verify that `request.shop` corresponds to a shop that both installed the app and is expected to receive that specific `webhook_id`/topic combination (e.g., cross-check against the app's own record of registered shops before invoking the handler), rather than trusting header-derived values purely because the body's HMAC checked out.

### Proof of Concept
1. Shop A installs the app and legitimately receives a webhook: `raw_body = B`, headers include `X-Shopify-Hmac-Sha256: H`, `X-Shopify-Shop-Domain: shop-a.myshopify.com`, where `H = HMAC_SHA256(api_secret_key, B)`.
2. Shop A (attacker) resends an HTTP request to the app's public webhook endpoint with the same `raw_body = B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: shop-victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(api_secret_key, B)` and matches `H` — validation succeeds because `to_signable_string` only depends on `B`: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "shop-victim.myshopify.com" ...)`, and the host app processes the event as if it genuinely came from `shop-victim`, despite `shop-victim` never having sent or authorized this webhook.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
