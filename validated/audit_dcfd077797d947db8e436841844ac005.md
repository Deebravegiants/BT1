## Finding

### Title
Unchecked ERC20 return value in escrow withdrawal and dust sweep allows silent transfer failure and escrow desync - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` move ERC20 tokens using a raw low-level `.call` with `IERC20.transfer.selector`, checking only that the external call itself did not revert (`success`), while never decoding/validating the returned boolean. [1](#0-0) [2](#0-1) 

### Finding Description
For any ERC20 token that signals a failed transfer by returning `false` rather than reverting (a fully standard-compliant behavior explicitly allowed by EIP-20, and used by real deployed tokens), a low-level `.call` to `transfer(...)` still returns `success = true` because the call itself did not revert — only the ABI-encoded return data (`false`) indicates the failure. This code path never inspects that return data:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [3](#0-2) 

This same unchecked pattern is repeated for fee redemption and for `SweepDust`: [4](#0-3) [5](#0-4) 

Notably, the rest of the codebase (the canonical EVM `IntentGatewayV2`/`IntentsBase` and the token-bridge apps) consistently uses OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which decodes and requires the return value to be `true` for tokens that do return data: [6](#0-5) [7](#0-6)  The Tron-targeted fork of the contract deviates from this pattern in exactly the way the external report warns against — reintroducing the "missing/ignored return value" bug class.

`withdraw()` is reached via `onAccept()` when Hyperbridge delivers a `RedeemEscrow` or `RefundEscrow` message after an order fill/cancellation — a path any user's filled/cancelled intent order will traverse: [8](#0-7)  Because `_orders[commitment][token]` accounting is decremented unconditionally regardless of whether the transfer truly succeeded, and the function only reverts if the low-level call itself reverts, a token that returns `false` on failure lets the function proceed as if the beneficiary was paid.

### Impact Explanation
If the escrowed/fee token used for an order returns `false` instead of reverting on a failed transfer (e.g., due to insufficient contract balance from rounding/dust accounting drift, blacklisting, paused states, or any other condition some real ERC20 implementations use `return false` for), `withdraw()` will still: (1) mark the order as filled/refunded (`_filled[commitment] = beneficiary`), (2) decrement the escrow balance, and (3) emit `EscrowReleased`/`EscrowRefunded` — all while the beneficiary receives nothing. The escrowed tokens become stuck/unaccounted for (permanent loss of funds for the beneficiary, since the order is now marked finalized and cannot be retried), and the protocol's internal escrow bookkeeping desyncs from actual token balances. The `SweepDust` and fee-redemption branches have the analogous effect for protocol-owned funds.

### Likelihood Explanation
This requires only that a token used within the Tron `IntentGatewayV2` deployment be one that returns `false` (rather than reverting) on transfer failure — a legitimate, standards-compliant behavior seen in real-world ERC20/TRC20 tokens — combined with an ordinary condition that causes that particular transfer to fail (e.g., contract-level balance/rounding edge cases from the fee/dust arithmetic elsewhere in the contract, or token-side restrictions). No special privileges are needed to reach `onAccept → withdraw`; it fires as part of the normal cross-chain settlement flow for any intent order routed through this Tron gateway.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` + `success`-only check in `withdraw()` and the `SweepDust`/fee-redemption paths of `evm/tron/contracts/apps/IntentGatewayV2.sol` with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring the already-correct pattern used in `IntentsBase._withdraw` and `_sweepDust` on the canonical EVM contract. This ensures both call failure and a `false` return value cause a revert instead of being treated as success.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with an ERC20/TRC20 token whose `transfer` implementation returns `false` on failure instead of reverting (standard-compliant behavior).
2. Create and fill an order using that token as input; escrow accounting records `_orders[commitment][token] = amount`.
3. Cause the contract's actual token balance to fall short of `amount` at redemption time (e.g., via a fee/dust rounding path elsewhere in the contract, or a token-side restriction on the specific beneficiary), such that the token's `transfer()` call returns `false` rather than reverting.
4. `withdraw()` receives `success = true` from the low-level `.call` (call itself doesn't revert), skips the `revert TransferFailed()` check, decrements `_orders[commitment][token]`, sets `_filled[commitment] = beneficiary`, and emits `EscrowReleased`.
5. The beneficiary receives zero tokens, the order is permanently marked filled, and the escrowed funds are unaccounted for — resulting in a hard loss for the beneficiary.
