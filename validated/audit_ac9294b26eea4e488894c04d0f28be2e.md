### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and the HMAC check in `Registry.process` validates that body against the `hmac-sha256` header [1](#0-0) . All other identifying fields taken from the request — `shop`, `topic`, `webhook_id`, `api_version` — are read straight from unauthenticated HTTP headers [2](#0-1)  and are handed to the app's handler unchanged after only the body HMAC is checked [3](#0-2) .

### Finding Description
The identity binding that should hold is: `shop header == shop cryptographically bound to the signed payload`. Instead, the gem only proves `HMAC(secret, raw_body) == received_hmac`; it never proves that `shop-domain` (or `topic`/`webhook-id`) was the value Shopify associated with that specific signed body.

- `to_signable_string` for the OAuth `AuthQuery` deliberately includes `shop` in the signed string [4](#0-3) , showing the gem's own pattern for correctly binding identity fields to the HMAC.
- The webhook `Request`, by contrast, signs only `@raw_body` and leaves `shop`, `topic`, `webhook_id`, `api_version` completely outside the signature [5](#0-4) .
- `Registry.process` validates the HMAC and then immediately trusts these unauthenticated header-derived values to build the `WebhookMetadata` struct delivered to the app's handler: `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id)` [3](#0-2) .

Because only the body bytes are bound to the secret, any (body, HMAC) pair that was legitimately generated for one tenant (e.g. by installing the target app on an attacker-controlled shop and receiving a real webhook with a body the attacker can predict/replay, such as `shop/redact` or a repeatable event) can be replayed to the same public webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop. The signature still validates (it only checks the body), but the handler is told the event belongs to the victim shop. Any host application that uses `WebhookMetadata#shop` to look up the merchant's stored session/access token, gate multi-tenant data, or key idempotency/state processes cross-tenant confusion, since the gem provides no cryptographic proof that `shop` corresponds to the signed body.

### Impact Explanation
This breaks the tenant/shop identity binding for the webhook receipt path with no privileged credential required — an unprivileged actor who can install the app on any shop (or otherwise obtain one valid signed body/HMAC pair) can spoof the shop identity attached to that payload to any other shop. Downstream, apps commonly use the `shop` from webhook metadata to fetch or act on a specific merchant's stored access token/session, so this qualifies as cross-tenant access under the classifications in scope.

### Likelihood Explanation
Moderate: the attacker needs one legitimately signed `(body, hmac)` pair, obtainable by simply installing the target app on their own store (or from any store whose webhook body content is guessable/reusable, e.g. mandatory GDPR topics with static/predictable bodies). No secret, access token, or privileged access is required — just a normal HTTP request to the public webhook endpoint with a forged `x-shopify-shop-domain` header.

### Recommendation
Bind the identity-relevant headers into the signed payload before verifying HMAC: include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (as is already done for `AuthQuery`), or otherwise cryptographically bind the shop domain to the HMAC verification step rather than trusting it as a bare header after only the body is checked.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`; capture a real webhook delivery for a topic with a stable/predictable body (e.g. `shop/redact`), noting `raw_body` and the valid `x-shopify-hmac-sha256` value Shopify computed for it.
2. Replay that exact `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` and `x-shopify-topic`/`x-shopify-webhook-id` to whatever is desired.
3. `Registry.process` computes `HMAC(secret, raw_body)` — it matches, because the body is unchanged — and then calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)` [6](#0-5) , even though Shopify never associated that body with `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
