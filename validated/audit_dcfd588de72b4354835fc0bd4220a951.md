### Title
Cross-user order hijack via shared Emporium identity in CASE 2 stateless ops - (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 branch executes arbitrary `op.endpoint.call(op.callData)` directly from the Emporium proxy address itself, so every Hinkal user who routes a stateless op through Emporium is seen by the external protocol as the *same* `msg.sender`. Any unprivileged attacker can therefore call back into that external protocol (e.g. `cancelOrder(victimOrderId)`) using their own `runAction` invocation, and any refund the protocol sends to that shared `maker`/caller identity is swept into the attacker's own shielded output within the same call.

### Finding Description
Broken equality: the protocol being called (order book) authorizes based on `refund_recipient == maker == msg.sender`, and Hinkal's `AUTHORITY` model assumes `refund_recipient` corresponds to the stealth address of the user whose proof originally created that position. In practice, `refund_recipient` collapses to `address(EmporiumUpgradeable)` for *every* Hinkal user, because CASE 2 makes the external call directly from the Emporium contract: [1](#0-0) 

Since Emporium is a single shared, upgradeable proxy used by all users (not a per-user contract), a victim placing a limit order via CASE 2 registers `maker == emporium` on the external order book — an identity indistinguishable from any other Hinkal user's CASE 2 calls. `verifyWallet` only checks/marks `usedMessages[circomData.emporiumMessage]` and, when `stack.signerAddress == address(0)` (i.e., no CASE 1 wallet is used), returns immediately without validating the op contents against any prior state or victim-specific binding: [2](#0-1) 

Nothing in `circomData` or the circuit constrains `op.callData`/`op.endpoint` to reference only positions the caller itself created — the attacker's own valid proof for their own UTXOs is sufficient to authorize *any* CASE 2 call content, including `cancelOrder(victimOrderId)`.

Attacker call: `runAction` with `ops=[{endpoint: limitOrderBook, invokeWallet:false, value:0, callData: cancelOrder(victimOrderId)}]`. The order book sees `msg.sender == emporium == maker`, refunds the collateral to `address(this)` (Emporium). Back in `runAction`, `balancesAfter - balancesBefore` reflects this refund, and `handleOut` unconditionally forwards any positive balance change to the caller and mints a UTXO tied to whatever `circomData.stealthAddressStructure` the *attacker* supplied for this transaction: [3](#0-2) 

None of `performHinkalChecks`, `rootHashExists`, nullifier insertion, or the circuit's `inTotal+amountChanges==outTotal` constraint address this: they only prove the attacker legitimately owns and spends their *own* input UTXOs and correctly nets their *own* `amountChanges` — they say nothing about who is entitled to a balance increase discovered on the shared Emporium contract mid-call. The only place ownership of "whose funds these are" is decided is `handleOut`, which blindly attributes any residual balance increase to the current caller's stealth address.

By contrast, CASE 1 (stateful) uses per-user `HinkalWallet` contracts (`onlyEmporium` gated, deployed with a distinct address per `signerAddress`) precisely to give each user a distinguishable on-chain identity for stateful external protocol interactions: [4](#0-3) 

CASE 2 has no equivalent isolation, so any external protocol that persists per-caller state (open orders, deposits, positions) tied to `msg.sender` is exploitable cross-user through Emporium.

### Impact Explanation
An attacker can steal any victim's escrowed/refundable funds held by a third-party protocol that was reached via Emporium CASE 2 and that authorizes state-changing calls (cancel/withdraw/claim) by `msg.sender`. The refund lands on the shared Emporium contract and is swept directly into the attacker's own shielded UTXO in the same transaction — direct theft of another user's in-flight funds, matching the Critical category ("direct theft of shielded or in-flight user funds"). The attack is repeatable against every victim who used a msg.sender-authorizing external protocol via CASE 2, and against every open position of that kind, at negligible attacker cost (just their own valid proof).

### Likelihood Explanation
Preconditions are realistic and controlled entirely by the attacker: any external protocol whose stateful/refund logic keys off `msg.sender` (a common pattern for order books, vaults, staking, or claim contracts) integrated via Emporium's unrestricted `op.endpoint.call` in CASE 2. The attacker needs only their own funds/UTXOs to generate a valid proof for their own `runAction` call — no victim cooperation, no privileged role, no race condition beyond simply calling before the victim does (or anytime the position remains open). This is fully within the stated unprivileged attacker capabilities and requires no special timing beyond the order/position being open.

### Recommendation
Do not allow CASE 2 stateless ops to call external protocols whose authorization model is `msg.sender`-based for anything beyond one-shot, self-contained calls (e.g., swaps that complete atomically with no persisted per-caller state). Concretely: either (a) force any op that establishes persistent externally-tracked ownership (place/cancel/withdraw-style calls) through CASE 1 via a per-user `HinkalWallet` instance so `msg.sender` is user-specific, or (b) maintain an Emporium-side registry binding `(endpoint, external order/position id)` to the specific proof/nullifier or stealth address that created it, and enforce that binding before allowing cancel/refund-style calldata in CASE 2. Additionally, `handleOut`'s blanket "any balance increase during the call goes to the current caller" logic should not be trusted as a global truth for shared-identity external calls.

### Proof of Concept
Hardhat test plan:
1. Deploy a mock order book with `placeOrder(token, amount)` (pulls `amount` from `msg.sender`, sets `maker = msg.sender`) and `cancelOrder(orderId)` (`require(msg.sender == orders[orderId].maker)`, refunds `amount` to `msg.sender`).
2. Deploy `EmporiumUpgradeable`, register it in `HinkalFactory`/`Hinkal.sol` as an allowed external action, and whitelist the mock order book as an arbitrary endpoint (no allowlist restriction needed since `op.endpoint` is unrestricted).
3. Victim: deposit tokens into Hinkal, generate a valid proof and CASE 2 `runAction` call with `ops=[{endpoint: orderBook, invokeWallet:false, value:0, callData: placeOrder(token, victimAmount)}]`. Assert `orderBook.orders[orderId].maker == address(emporiumProxy)`.
4. Attacker: deposit their own (unrelated, possibly tiny) funds into Hinkal, generate their own valid proof, and call `runAction` with `ops=[{endpoint: orderBook, invokeWallet:false, value:0, callData: cancelOrder(victimOrderId)}]`.
5. Assert: `token.balanceOf(emporiumProxy)` reflects the refund transiently, and after `handleOut` runs, the resulting UTXO/on-chain transfer sends `victimAmount` to the **attacker's** `stealthAddressStructure`/address, not the victim's — i.e., assert final recipient of the swept refund is the attacker, and the victim's order funds never return to the victim. This confirms `refund_recipient == attacker != stealth address that authorized the original order`.
