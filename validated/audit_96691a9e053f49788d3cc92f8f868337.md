### Title
Webhook shop/topic identity spoofing via unauthenticated headers not covered by HMAC — cross-tenant webhook data confusion - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the app's webhook handler entirely from HTTP headers, while `Utils::HmacValidator` only verifies the raw request **body** against the `X-Shopify-Hmac-Sha256` header. The identity fields that the handler trusts to determine *which tenant* a webhook belongs to are never included in the signed content, so the equality the gem should enforce — "the shop the HMAC was computed for" == "the shop the handler is told the data belongs to" — does not hold.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from attacker-controllable headers, independent of the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (body only) — it never binds `hmac` to `shop`, `topic`, or `webhook_id` — and then constructs `WebhookMetadata` directly from the unauthenticated header values: [3](#0-2) 

Because `VerifiableQuery#to_signable_string` for this class covers only the body, and `HmacValidator.validate_signature` does a secure comparison against that body-only signable string: [4](#0-3) 

...an HTTP request with a **valid, previously-observed `(body, hmac)` pair** but a **different `shopify-shop-domain` / `shopify-topic` / `shopify-webhook-id` header** will still pass `HmacValidator.validate`. The handler then receives `WebhookMetadata` claiming the body belongs to whatever shop/topic the attacker put in the headers, even though that shop never triggered or authorized this event. This breaks the intended binding: *"HMAC-validated request" should imply "the `shop` field it reports is the shop the app's secret authenticated for this exact payload."* Instead, only the body bytes are authenticated; the tenant-identifying headers are parsed but never verified.

This is the same bug class as the referenced Erigon issue in spirit: a value that downstream logic *trusts as authoritative* (there: a result on an unbuffered channel; here: the `shop`/`topic` identity of a webhook) is not actually coupled to the mechanism meant to guarantee its integrity (there: nothing reads it; here: the HMAC doesn't cover it).

### Impact Explanation
An unprivileged internet user who can obtain (or capture) any single valid `(raw_body, hmac)` pair for the target app's webhook endpoint — for example by installing the app on their own low-privilege shop and receiving one legitimate webhook delivery — can replay that exact body/HMAC to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for a different, victim shop. Because `Registry.process` never checks that the signed body content is consistent with the claimed shop, the app's own webhook handler will process/store/act on that data as if it originated from the victim tenant. Depending on the handler implementation (which is out of scope here, but is exactly what this gem's documented API is meant to feed reliably), this yields cross-tenant data confusion/injection — data attributed to the wrong merchant record.

### Likelihood Explanation
Moderate: an attacker needs one legitimately-signed body+HMAC pair, which is trivially obtainable by installing the app on any shop (even a free/trial one) and triggering a webhook (e.g., `app/uninstalled`) themselves — no `api_secret_key`, access token, or TLS interception is required. The header substitution and replay require only unauthenticated HTTP access to the app's public webhook endpoint.

### Recommendation
Bind the tenant/topic identity into the signed material actually verified, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the HMAC-covered body before trusting them in `WebhookMetadata`. At minimum, document/require host apps to independently confirm the reporting shop is one with an active session/installation before acting on webhook data, and consider incorporating the header values into `to_signable_string` (matching Shopify's actual webhook verification contract) so `HmacValidator.validate` fails if headers are altered relative to the signed delivery.

### Proof of Concept
1. Install the target app on shop `attacker.myshopify.com`; capture a legitimate webhook delivery, e.g. headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: app/uninstalled`, `x-shopify-hmac-sha256: <valid-hmac>`, and raw body `B`.
2. Replay the request to the same public webhook endpoint, keeping body `B` and the valid `<valid-hmac>` header unchanged, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `<valid-hmac>` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "app/uninstalled", body: parsed_body, ...)` (`lib/shopify_api/webhooks/registry.rb:188-199`), causing the app to process attacker-controlled data under the victim shop's identity.
