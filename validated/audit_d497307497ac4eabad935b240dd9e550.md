### Title
Webhook `shop`, `topic`, `webhook-id`, and `api-version` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw HTTP body, so the HMAC verification performed by `Utils::HmacValidator.validate` only binds the signature to the body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated headers and passed on to application webhook handlers without being covered by the signature.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` as plain header reads: [1](#0-0) 

But `to_signable_string`, which is what gets HMAC-verified, only returns `@raw_body`: [2](#0-1) 

`Webhooks::Registry.process` verifies the HMAC over that signable string only, then dispatches the handler using the unauthenticated `shop` and `topic` header values: [3](#0-2) 

The binding that should hold is: `hmac == HMAC(secret, body || shop || topic || webhook_id || api_version)`. Instead the gem only enforces `hmac == HMAC(secret, body)`, i.e. `shop`/`topic`/`webhook_id`/`api_version` are "fields acted on but not covered by the HMAC."

Since a webhook body plus its valid HMAC digest is identical no matter which shop or topic header accompanies it, anyone capable of delivering an HTTP request to the app's webhook endpoint (which is normally public, since Shopify webhook receivers do not require additional auth per Shopify's own docs) can take a body+HMAC pair legitimately produced for one shop/topic and resubmit it with a different `shop-domain`/`topic` header. The signature will still validate, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event came from an arbitrary shop/topic of the attacker's choosing.

### Impact Explanation
Handlers built on top of this gem trust `WebhookMetadata#shop` (and `#topic`) as the identity of the tenant the event is about, since that's the only assertion the library makes about which shop the payload belongs to. Because `shop` isn't part of the signed payload, an attacker who obtains one valid signed webhook (e.g., a webhook sent to their own store, or one delivered to a shared/multi-tenant endpoint) can replay it while spoofing the `shop-domain` header to point at a different, unrelated tenant. This causes the application to process/apply the payload as if it belongs to a different merchant — i.e., cross-tenant confusion in the identity used downstream (session lookup, data updates, etc.), matching the "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one legitimately-signed webhook body/HMAC pair (for example, from their own shop's webhooks, which any merchant installing the app can trivially obtain) and the ability to POST to the app's public webhook endpoint with modified headers — both of which are available to an unprivileged internet user/merchant without needing the app's `client_secret` or an access token.

### Recommendation
Include the `shop-domain`, `topic`, `webhook-id`, and `api-version` header values in the signable string used for HMAC verification (or otherwise cryptographically bind them to the signed body), so that spoofing any of these fields invalidates the signature. Shopify's own webhook signature is computed over the raw body only by design, so the safer fix is to have `Registry.process`/handlers additionally check that the shop in the payload body matches the `shop-domain` header rather than trusting the header alone as an identity.

### Proof of Concept
1. Merchant A installs the app; app receives a legitimate webhook: `body = {...}`, `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`.
2. Attacker captures/replays this exact `body` + `x-shopify-hmac-sha256` value but changes `x-shopify-shop-domain` to `shop-b.myshopify.com` (a different, unrelated store) and POSTs it to the app's webhook endpoint.
3. `Utils::HmacValidator.validate` succeeds because it only checks `body` against the HMAC (`to_signable_string` returns `@raw_body`) — see [2](#0-1) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: "shop-b.myshopify.com", body: ..., ...)`, so the app processes attacker-controlled data as if it originated from shop B.
