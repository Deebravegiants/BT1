## Title
Webhook `shop`, `topic`, and `webhook_id` are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request **body only**, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` to route and attribute the webhook are taken from unauthenticated HTTP headers. Any party who can obtain one genuinely signed webhook body/HMAC pair (e.g., by installing the app on their own shop) can replay that exact body and HMAC to the app's webhook endpoint while freely rewriting the `shop-domain`, `topic`, and `webhook-id` headers, causing the library to treat forged, attacker-controlled tenant/topic metadata as authenticated.

### Finding Description
`Request#to_signable_string` only returns the raw body: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers, none of which participate in the HMAC computation: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC via `HmacValidator.validate(request)`, and then dispatches to the handler using the unauthenticated `request.shop` and `request.topic` values: [3](#0-2) 

`HmacValidator.validate` in turn calls `verifiable_query.to_signable_string`, which for a webhook request is exactly the raw body — the shop/topic/id headers are never part of the signed material: [4](#0-3) 

**Identity binding broken (as an equality):**
`shop_header_used_for_tenant_routing == shop_covered_by_hmac` should hold, but instead `shop_header_used_for_tenant_routing != anything_in_the_signed_bytes` — the header is never part of `to_signable_string`, so it is not bound to the signature at all.

**Attack scenario:** An unprivileged internet user who has installed the app on their own store (a normal, unprivileged app install — not requiring `api_secret_key`, an access token, or any privileged credential) legitimately receives webhooks with valid `x-shopify-hmac-sha256` values computed over real bodies by Shopify. Because the signature covers only the body, the attacker can:
1. Capture one valid `(body, hmac)` pair from their own shop's webhook delivery.
2. POST that same body/hmac to the app's public webhook endpoint, but substitute the `x-shopify-shop-domain` header with a victim merchant's domain, and/or substitute `x-shopify-topic` with a different topic (e.g., `app/uninstalled`, `customers/data_request`, `shop/redact`).
3. `Registry.process` verifies the (still valid) body HMAC, sees no inconsistency, and invokes the handler with the attacker-chosen `shop` and `topic` in `WebhookMetadata`, causing the host application to attribute/store/act on data as if it came from a different, unrelated tenant.

This directly matches the reported bug class: a value ("shop"/"topic"/"webhook_id") acted upon by the application is not covered by the same authentication check (HMAC) that is used to establish trust, letting an attacker manufacture a valid signature/identity mismatch.

### Impact Explanation
**High — cross-tenant access.** The webhook `shop` value is the tenant key most host apps use to look up/store/act on merchant data (as documented and demonstrated in `WebhookMetadata.new(... shop: request.shop ...)`). Because it is unauthenticated, an attacker can make the library deliver forged, cross-tenant-attributed webhook events to the host application's handlers, using a genuinely-signed body they only needed to obtain once from their own store. Depending on the handler's semantics (e.g., GDPR/compliance topics, uninstall handling, order/customer sync), this can corrupt or leak another merchant's data or trigger tenant-scoped side effects under a forged shop identity.

### Likelihood Explanation
**Medium.** The attacker needs only an app install on their own store (no special credentials, no `api_secret_key`) to harvest one valid `(body, hmac)` sample, then can freely POST to the app's public webhook endpoint with arbitrary headers. No secret material or privileged access is required.

### Recommendation
Include the security-relevant header values (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material — e.g., use Shopify's documented webhook verification which signs the raw body but should be paired with matching the signed body to an already-registered `(shop, topic)` pair, or bind these header values into `to_signable_string` so any tampering invalidates the HMAC. At minimum, cross-check that the `shop-domain` header corresponds to a shop with an active app installation/session before processing, rather than trusting it purely from the header.

### Proof of Concept
```ruby
# Attacker installs app on their own shop "attacker.myshopify.com" and receives
# a legitimate webhook delivery for topic "orders/create":
raw_body = '{"id": 1, "note": "legit order"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)

# Attacker now replays the SAME body/hmac to the app's public webhook endpoint,
# but swaps the shop-domain and topic headers to target a victim shop / different topic:
forged_headers = {
  "x-shopify-topic" => "app/uninstalled",              # attacker-chosen, unsigned
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac), # still valid! (body unchanged)
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-chosen, unsigned
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HMAC validation passes (it only checks raw_body),
#    handler is invoked with shop: "victim-shop.myshopify.com", topic: "app/uninstalled"
```
