## Analog Found

### Title
Rotating a destination's `fee_token` via `pallet-ismp-host-executive::update_host_params` can permanently burn/misdenominate relayers' already-accrued fees in `pallet-ismp-relayer::withdraw` - (File: `modules/pallets/relayer/src/withdrawal.rs`)

### Summary
This mirrors the DeXe report's bug class: a privileged, cross-chain governance action rotates a stored "current contract address" config value, and a *separate* reward-accounting module keeps reading that config live at claim time instead of snapshotting it when the reward was earned. Here, `pallet-ismp-relayer` accrues relayer fees denominated in whatever `fee_token` was live on the destination `EvmHost` at delivery time, but `withdraw()` re-reads the *current* `fee_token`/`host_manager` from `pallet-ismp-host-executive::HostParams` only at withdrawal time, and unconditionally zeroes the `Fees` balance once the withdrawal message is dispatched — regardless of whether that dispatch is ever honored on the destination in the correct token.

### Finding Description
`pallet-ismp-relayer::accumulate` credits `Fees::<T>` with a `U256` amount for a relayer, on a given `dest_chain`, based on fee metadata proven from the source chain's `RequestCommitments` [1](#0-0) . This amount is denominated in whatever `feeToken` the `EvmHost` on `dest_chain` was configured with when the request/delivery occurred — the balance itself carries no token identity, only a raw numeric amount.

When the relayer later calls `withdraw()`, the pallet fetches the **current** `HostParams` for `dest_chain` from `pallet-ismp-host-executive` and builds the on-chain payout instruction from whatever token/manager address is stored *now*: [2](#0-1) 

Governance can rotate that stored `fee_token` (and/or `host_manager`) at any time via `pallet-ismp-host-executive::update_host_params`, which writes the new params into `HostParams<T>` immediately and only *afterwards* asynchronously dispatches the corresponding `updateHostParams` message to the destination `EvmHost`: [3](#0-2) 

`EvmHost.updateHostParamsInternal` does guard against changing `feeToken` while the **host contract's own on-chain balance** of the old token is nonzero (`CannotChangeFeeToken`) [4](#0-3) , but that check is local to the EVM contract's token balance — it has no knowledge of, and does not check, outstanding `pallet-ismp-relayer::Fees` entries recorded on the Hyperbridge parachain for relayers who have not yet withdrawn. The parachain-side `update_host_params` call performs no cross-check against pending relayer fees for that state machine at all.

Once `fee_token` has been rotated (a scenario the contract's balance-based guard does not prevent whenever the old-token balance happens to be zero, e.g. after a prior sweep/withdraw of protocol revenue, even while relayer fee balances are still outstanding), any relayer whose `Fees` entry was accrued in the old token but who withdraws afterward gets a `WithdrawalParams` payload built with the new `fee_token` address and the old numeric `amount`: [5](#0-4) 

Critically, immediately after dispatching this request, the pallet unconditionally zeroes the relayer's `Fees` entry, with no confirmation that the destination-chain payout ever succeeds, let alone succeeds in the correct token: [6](#0-5) 

The destination `HostManager.onAccept` for the `Withdraw` action simply calls `IHostManager(host).withdraw(withdrawParams)`, which does an ERC20 `safeTransfer` of `params.token` (the new token) for `params.amount` — either reverting (since the numeric amount is now nonsensical for the new token, or the host has no such balance) so the payout is retryable-but-effectively-stuck at the correct amount forever, or in principle succeeding in a token the relayer never actually earned: [7](#0-6) [8](#0-7) 

### Impact Explanation
Relayer fee accounting (`Fees<T>`) is zeroed as soon as the withdrawal request is dispatched, not when it is confirmed delivered. Combined with the fact that `withdraw()` reads the *live* `fee_token`/`host_manager` rather than the value in effect when the fee was accrued, a `fee_token` rotation performed by governance between accrual and withdrawal permanently and silently denies relayers their already-earned, provably-accrued fees: the `Fees` balance is destroyed on the source-of-truth chain (Hyperbridge) while the destination-chain payout either fails or pays out the wrong asset. This is a direct loss of protocol-owed relayer compensation with no recovery path, matching the reported bug class (config rotation silently voiding pending, already-earned reward claims tracked by a separate accounting module).

### Likelihood Explanation
This requires no attacker: any legitimate governance-approved `fee_token` rotation on a chain that still has outstanding, unwithdrawn relayer fees triggers the issue for every relayer who has not withdrawn beforehand. Because relayers can "withdraw at any time" and often batch withdrawals, and because the EVM-side guard only checks the contract's *current* token balance (not the parachain's separate `Fees` ledger), it is entirely plausible for governance to perform a routine fee-token migration while relayer balances are still outstanding, especially since the two checks (EVM balance vs. parachain `Fees` map) are maintained independently with no communication between them.

### Recommendation
- Snapshot the `fee_token`/`host_manager` used at fee-accrual time per `Fees` entry (or per state-machine "epoch" incremented on each `fee_token` rotation), and use that snapshot when constructing the withdrawal payload, rather than re-reading the live `HostParams`.
- Do not zero `Fees::<T>` until the destination confirms the payout succeeded (or use a two-phase commit: mark pending, only clear on confirmed delivery/settlement, and allow retry/refund on failure).
- Have `pallet-ismp-host-executive::update_host_params` refuse (or require draining) a `fee_token` change for a state machine that still has nonzero aggregate `pallet-ismp-relayer::Fees` balances outstanding for that destination, mirroring the intent of `EvmHost`'s `CannotChangeFeeToken` guard but scoped to the actual off-chain-tracked liability rather than just the contract's on-chain token balance.

### Proof of Concept
1. Relayer `R` delivers messages to destination chain `D` and accumulates `Fees::<T>::get(D, R) = 1000` (denominated in `fee_token = TokenA`), via `accumulate()` [9](#0-8) .
2. `TokenA` balance on the `EvmHost` for `D` happens to be zero at this moment (e.g., protocol revenue already swept via `withdraw` governance call), so governance calls `pallet-ismp-host-executive::update_host_params(D, { fee_token: TokenB, ... })`; the `EvmHost.CannotChangeFeeToken` guard passes since `IERC20(TokenA).balanceOf(host) == 0`, and Hyperbridge's `HostParams<T>` for `D` is updated to `TokenB` immediately [10](#0-9) .
3. Relayer `R` calls `withdraw()` for `D`; the pallet reads the now-current `params.fee_token = TokenB` and constructs `WithdrawalParams{ beneficiary_address: R, amount: 1000, token: TokenB }`, dispatches it, and immediately zeroes `Fees::<T>::get(D, R)` [11](#0-10) .
4. On delivery, `HostManager.onAccept` calls `EvmHost.withdraw({ token: TokenB, amount: 1000, beneficiary: R })`; the host has no relationship between `TokenB` and `R`'s actual 1000-unit `TokenA` earning — the transfer either reverts (fee permanently stuck, since `Fees<T>` is already zero and cannot be re-claimed) or pays `R` 1000 units of the wrong token, while `R`'s legitimate `TokenA`-denominated earnings are gone.

		pub fn update_host_params(
			origin: OriginFor<T>,
			state_machine: StateMachine,
			update: HostParamUpdate,
		) -> DispatchResult {
			T::HostExecutiveOrigin::ensure_origin(origin)?;

			let params = HostParams::<T>::get(&state_machine)
				.ok_or_else(|| Error::<T>::UnknownStateMachine)?;

			let (HostParam::EvmHostParam(mut inner), HostParamUpdate::EvmHostParam(update)) =
				(params.clone(), update);
			// The destination host only accepts `updateHostParams` from the manager it currently
			// knows, so a manager rotation must be delivered through the outgoing manager.
			let current_manager = inner.host_manager;
			inner.update(update);

			let body = inner.abi_encode_with_variant().map_err(|_| Error::<T>::DispatchFailed)?;

			let post = DispatchPost {
				dest: state_machine,
				from: PALLET_ID.to_bytes(),
				to: current_manager.0.to_vec(),
				timeout: 0,
				body,
			};

			let updated = HostParam::EvmHostParam(inner);

			let dispatcher = <T as Config>::IsmpHost::default();
			dispatcher
				.dispatch_request(
					DispatchRequest::Post(post),
					FeeMetadata { payer: [0u8; 32].into(), fee: Default::default() },
				)
				.map_err(|_| Error::<T>::DispatchFailed)?;

			HostParams::<T>::insert(state_machine, updated.clone());

			Self::deposit_event(Event::<T>::HostParamsUpdated {
				state_machine,
				old: params,
				new: updated,
			});

			Ok(())
		}
