Audit Report

## Title
Node crash via nil pointer dereference in vault `GetPublicKey` gateway handler when `params` is null - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go` unmarshals `*req.Params` without checking for nil, unlike the sibling secret handlers (Create/Update/Delete/List) which are gated by explicit `req.Params == nil` checks in `GatewayVaultRequestProcessor`. Since `MethodPublicKeyGet` requires no authorization and is unconditionally reachable from the gateway-side handler, an unprivileged client can trigger a nil-pointer-dereference panic on the node by sending a `vault_getPublicKey` request with `params` omitted or `null`.

## Finding Description
On the node side, `HandleGatewayMessage` dispatches `vaulttypes.MethodPublicKeyGet` directly to `h.handlePublicKeyGet` without any nil-params validation: [1](#0-0) 

`handlePublicKeyGet` then dereferences `*req.Params` immediately: [2](#0-1) 

By contrast, all other secret-management request paths call `h.requestProcessor.ProcessRequest`, whose per-method handlers explicitly guard against nil params before ever calling `json.Unmarshal`: [3](#0-2) 

On the gateway side, `HandleJSONRPCUserMessage` routes `MethodPublicKeyGet` to a special-cased, unauthenticated fast path (cache check → forward to nodes) that never validates or reads `req.Params` at all, so a caller-supplied `null`/omitted `params` is forwarded to nodes unmodified: [4](#0-3) 

On the node's connector, incoming messages are dispatched to the handler directly in a read-loop goroutine with no `recover()`: [5](#0-4) 

This confirms the claim's described code path precisely: the nil-check pattern used everywhere else (`gateway_vault_request_processor.go`) is absent for `MethodPublicKeyGet`, and no other validation layer (gateway-side or node-side) intercepts a null/omitted `params` before the unguarded `json.Unmarshal(*req.Params, r)` dereference.

## Impact Explanation
A panic inside the unrecovered `readLoop` goroutine of `gatewayConnector` (`core/services/gateway/connector/connector.go`) crashes that goroutine; since Go panics propagate up the call stack and are not caught anywhere in this connector code, an unrecovered panic here will terminate the node process (or at minimum permanently kill Vault gateway-message processing for that node), consistent with an availability-only impact (no confidentiality/integrity compromise). This maps to a legitimate in-scope availability/DoS impact on node infrastructure reachable via the Gateway's public-facing Vault endpoint, since `MethodPublicKeyGet` bypasses the authorization pipeline entirely.

## Likelihood Explanation
High. Any unauthenticated/unprivileged client able to reach the Gateway's vault endpoint can send a single JSON-RPC request for `vault_getPublicKey` with `params` omitted or `null`. This method requires no credentials or prior authorized state, and the gateway-side handler forwards it to nodes without any validation of `params`.

## Recommendation
Add an explicit `if req.Params == nil` check at the top of `handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go`, returning an `api.UserMessageParseError`/`InvalidVaultParamsError` response instead of unmarshaling a nil pointer — mirroring the pattern in `processCreateSecretsRequest` and friends. Consider adding a shared nil-params guard used uniformly across all dispatch branches (including `MethodPublicKeyGet`) to prevent recurrence, and add a `recover()` in the connector's `readLoop`/`HandleGatewayMessage` invocation as defense-in-depth against any handler bug causing full node crash.

## Proof of Concept
1. As an unauthenticated client, send to the Gateway's Vault endpoint a JSON-RPC request:
```json
{"jsonrpc":"2.0","id":"poc-1","method":"vault_getPublicKey"}
```
(`params` omitted, or explicitly `"params": null`).
2. Gateway-side `handler.HandleJSONRPCUserMessage` (`core/services/gateway/handlers/vault/handler.go:404-420`) forwards this request unchanged to DON nodes (cache miss path) via `fanOutToVaultNodes`.
3. Node-side `gatewayConnector.readLoop` receives the message and calls `GatewayHandler.HandleGatewayMessage`, which routes to `handlePublicKeyGet` (`core/capabilities/vault/gw_handler.go:207-208, 364-368`).
4. `json.Unmarshal(*req.Params, r)` dereferences a nil `*json.RawMessage`, panicking; since no `recover()` exists in `readLoop`, the panic propagates and crashes the node process.
5. A Go unit test invoking `GatewayHandler.HandleGatewayMessage` (or `handlePublicKeyGet` directly) with a `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` would reproduce the panic deterministically.
