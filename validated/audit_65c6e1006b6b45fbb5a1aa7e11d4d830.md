### Title
Webhook HMAC signs only the raw body, allowing `shop-domain`/`topic` header spoofing and cross-tenant webhook impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery#to_signable_string` by returning only the raw request body, while `topic`, `shop`, `webhook_id`, and `api_version` are all read from unauthenticated HTTP headers. `Registry.process` validates only the body-derived HMAC and then dispatches the handler using the unauthenticated `shop` (and `topic`) values, so the tenant binding is never actually verified.

### Finding Description
The Sequence bug binds a static signature to a specific caller, but the code checks the wrong entity (`msg.sender` inside a re-entered call context) instead of the value the signature was actually meant to protect — breaking the equality `verified_caller == acting_caller`.

The analogous binding here is `verified_bytes == acted_upon_shop`. `Utils::HmacValidator.validate` computes and compares the HMAC strictly over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body, and `shop`/`topic`/`webhook_id`/`api_version` are pulled straight from caller-supplied headers with no cryptographic linkage to the body or the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC (body-only) and then immediately trusts `request.shop` and `request.topic` to route and label the payload for the handler: [3](#0-2) 

Because the signature never covers `shop-domain`, an attacker who has legitimately received one valid `(raw_body, hmac)` pair for a webhook delivered to their *own* shop (e.g., a merchant that installed the app, or anyone who can observe a real webhook payload) can resend that identical body and HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` (and/or `shopify-topic`) header. The HMAC check in `HmacValidator.validate` still succeeds — it only checked the body — and `Registry.process` will hand the (attacker-chosen) `shop` value straight to the app's webhook handler as if Shopify itself certified that the payload belongs to that shop.

### Impact Explanation
This breaks the tenant boundary the HMAC is supposed to enforce: the handler receives `WebhookMetadata` claiming a `shop`/`topic` that was never cryptographically verified. An app whose webhook handler acts on `data.shop` (e.g., to look up per-shop settings, update per-shop database records, or trigger per-shop side effects) can be tricked into applying attacker-controlled webhook data under a different tenant's identity — i.e., cross-tenant data corruption/spoofing. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
The likelihood depends on the attacker being able to obtain at least one legitimate `(raw_body, hmac)` pair — which is trivial for any app installer/merchant since they naturally receive their own webhooks with valid signatures over predictable/observable bodies (e.g., `{}` bodies, or bodies whose content the attacker fully controls by triggering the event in their own shop). No possession of `api_secret_key` is required; only replay of an already-valid signed payload with a forged header is needed. This is a deterministic, repeatable bypass whenever an app's webhook handler branches or persists data keyed by `data.shop`/`data.topic` without an independent, out-of-band tenant check.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind them to the body before trusting them in `Registry.process`. At minimum, document that consuming applications must independently authenticate `data.shop` (e.g., cross-reference against a shop-specific webhook registration/secret or session store) rather than treating the header value as verified by `HmacValidator.validate`.

### Proof of Concept
```ruby
# Attacker owns/installs the app on "attacker-shop.myshopify.com" and receives
# a real webhook with body "{}" and a valid HMAC computed with the app's secret.
real_body = "{}"
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, real_body)

# Attacker replays the same body/HMAC but claims a different victim shop.
spoofed_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(real_hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "shopify-webhook-id" => "attacker-controlled-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: real_body, headers: spoofed_headers)

# Passes because Utils::HmacValidator.validate only checks `raw_body`, not headers.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
```
