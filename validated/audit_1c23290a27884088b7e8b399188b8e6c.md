### Title
Webhook shop/topic identity not bound to HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated once `Utils::HmacValidator.validate(request)` succeeds, then forwards `request.shop`, `request.topic`, and `request.webhook_id` to the host app's handler as if they were verified. In reality, the HMAC signature only covers the raw JSON body; the tenant-identifying fields are read from unsigned HTTP headers and are never part of the signed payload.

### Finding Description
`Webhooks::Request` implements `VerifiableQuery` with: [1](#0-0) 

`to_signable_string` returns only `@raw_body`: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from attacker-adjustable headers, none of which feed into the signed string: [3](#0-2) 

`HmacValidator.validate` only proves the `raw_body` bytes were signed with `Context.api_secret_key`; it says nothing about which shop or topic produced them, because `to_signable_string` never includes them: [4](#0-3) 

`Registry.process` gates entirely on this single HMAC check and then hands `request.shop` (the unsigned header) to the application handler as trusted identity data: [5](#0-4) 

The binding that should hold is:
`shop authenticated by HmacValidator.validate(request)` == `shop delivered to WebhookMetadata / the handler`

but the equality never actually holds — the first side authenticates only `@raw_body`, while the second side is `shopify_header("shop-domain")`, a value outside the signed string. This is the same root cause pattern as the referenced report: a check ("is this HMAC valid?") is satisfied while a *different*, unguarded field (here, the shop/topic headers instead of the ZeroEx trade balance) drives the security-relevant business logic.

### Impact Explanation
Any request whose `raw_body` carries a valid HMAC for the configured `api_secret_key` will be accepted regardless of the `shop-domain`, `topic`, or `webhook-id` headers attached to it. A party capable of obtaining one legitimately-signed `(raw_body, hmac)` pair (e.g., from a webhook delivered to their own installed shop) can resubmit it to the same endpoint with a different `shop-domain` header value. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` record claiming the payload originated from an arbitrary shop, letting the host application persist or act on that data under the wrong tenant — a cross-tenant identity confusion inside data this gem is supposed to have "verified."

### Likelihood Explanation
Exploitation needs at least one previously-obtained valid `(raw_body, hmac)` pair for the configured secret; the gem itself performs no additional binding once one is available, so the difficulty is entirely in acquiring a first sample, not in defeating any further protection in this library.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed string `to_signable_string` builds, or otherwise cryptographically bind them to the payload before `Registry.process` forwards them to handlers, so that `HmacValidator.validate` actually authenticates the shop/topic it exposes downstream.

### Proof of Concept
1. Obtain any single valid webhook delivery `(raw_body, X-Shopify-Hmac-Sha256)` pair produced for the app's `api_secret_key` (e.g., a legitimately delivered webhook to shop A).
2. Re-POST the same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with shop B's domain (and optionally swap `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `raw_body` — validation succeeds.
4. The handler receives `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` with `shop` set to shop B, even though the signed body actually originated from shop A, demonstrating the shop identity is unauthenticated relative to the HMAC check that gated processing.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
