### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop identity used downstream (`request.shop`) comes from the `x-shopify-shop-domain` / `shopify-shop-domain` header, which is never included in the HMAC-signed data. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC against the body only, then passes the unauthenticated `request.shop` value straight to the app's webhook handler. This breaks the binding `shop authenticated == shop delivered to handler`.

### Finding Description
`Registry.process` verifies webhook authenticity via: [1](#0-0) 

The HMAC check delegates to `Utils::HmacValidator.validate`, which computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Request`, `to_signable_string` is defined to return only `@raw_body`: [3](#0-2) 

But the `shop` attribute that is handed to the app's `WebhookHandler` (and used to attribute the webhook to a tenant) is read straight from the `shop-domain` header, which is completely outside the HMAC's coverage: [4](#0-3) [5](#0-4) 

So the equality that should hold — `shop bound by HMAC == shop delivered to handler` — does not: the HMAC only authenticates the body bytes, not the shop header. Any request whose body+HMAC pair is valid for *some* shop will pass validation regardless of what shop-domain header accompanies it.

### Impact Explanation
An attacker who is an ordinary, unprivileged merchant can install the target app on their own shop and receive genuine webhook deliveries with valid HMACs for their own shop's data (this requires no secret and no elevated access — it's standard app usage). They can then replay that exact `raw_body` + `hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header value. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` forwards `WebhookMetadata.new(... shop: request.shop ...)` to the handler with the attacker-chosen shop. Any handler logic that keys data storage, redaction, or business actions off `data.shop` will operate against the wrong tenant's record set, using attacker-controlled body content — i.e., cross-tenant data confusion/corruption. For mandatory topics like `shop/redact` or `customers/data_request`, this could trigger deletion/redaction actions attributed to an arbitrary victim shop.

### Likelihood Explanation
High/plausible: requires only normal, unprivileged app installation to obtain one valid signed webhook, then a trivial header substitution when replaying the HTTP request to the app's own webhook endpoint. No access to `api_secret_key`, tokens, or the target shop is needed.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the signed material, or otherwise cryptographically bind the shop value to the HMAC before it is trusted — e.g., verify that the shop the handler receives matches a shop value that was itself covered by the HMAC, rather than deriving `shop` purely from an unauthenticated header (`lib/shopify_api/webhooks/request.rb`, `to_signable_string`/`shop`).

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; capture a genuine webhook delivery: raw body `B`, header `x-shopify-hmac-sha256: H` (valid for `B`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Resend the same request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but replace `x-shopify-shop-domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`= B`) and succeeds, since the shop header was never part of the signed string.
4. The app's registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the app to process attacker-supplied content as though it originated from `victim.myshopify.com`.
