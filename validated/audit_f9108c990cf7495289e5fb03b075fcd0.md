## Title
Webhook shop identity spoofing — HMAC signature does not cover the `shop-domain`/`topic`/`webhook_id` headers used to dispatch webhook payloads - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` so that `Registry.process` can validate the webhook HMAC before invoking the app's handler. However, the signable string used for HMAC verification is only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values that are trusted and forwarded to the handler come from unauthenticated HTTP headers that are never covered by that signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic binding to the body/HMAC: [2](#0-1) 

`Registry.process` validates only the HMAC over the raw body, then unconditionally trusts `request.shop`/`request.topic`/etc. to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

The binding this breaks, expressed as an equality that should hold but doesn't:

`shop authenticated by HMAC == shop delivered to handler as request.shop`

The HMAC only proves "the body was produced by a holder of the app's `client_secret` (i.e., Shopify)", it says nothing about which shop the header claims to be from. A merchant who has installed the app (an unprivileged, legitimately-scoped actor with respect to their own store, but unprivileged with respect to every other tenant) receives real, validly-signed webhook deliveries from Shopify for their own shop. Because they control the raw HTTP request reaching the app's public webhook endpoint, they can capture one such delivery (body + valid `x-shopify-hmac-sha256`) and re-POST it with the `x-shopify-shop-domain` header (and/or `x-shopify-topic`, `x-shopify-webhook-id`) rewritten to name a different shop. `Utils::HmacValidator.validate(request)` still passes, because it only re-computes/compares against `@raw_body`: [4](#0-3) 

`Registry.process` then calls the app's handler with `WebhookMetadata.shop` set to the attacker-controlled value, even though the HMAC never authenticated that field.

### Impact Explanation
Applications built on this gem (this is the documented, intended usage pattern per `docs/usage/webhooks.md`) key their persistence/session and business-logic lookups off `WebhookMetadata#shop` (e.g., "find shop record by domain, then update or delete data, revoke access, mark uninstalled, etc."). Because the shop identity is not covered by the signature, a merchant who legitimately receives their own signed webhook can forge the shop-domain header and cause the host app to act on webhook payloads (uninstall notifications, order/customer data, GDPR data-request/erasure topics, etc.) attributed to an arbitrary victim shop — a cross-tenant identity confusion delivered through the app's own authenticated ingestion path. This satisfies the "cross-tenant access" Critical-impact category, since the app is misled about which tenant a webhook body belongs to despite a "verified" HMAC.

### Likelihood Explanation
Exploitation requires no secrets: the attacker only needs (a) their own app installation to receive one legitimately signed webhook, and (b) the ability to POST arbitrary HTTP requests to the app's public webhook URL (which is by design internet-reachable, since Shopify itself must reach it). No `client_secret`, access token, or privileged access is required — only capturing/replaying one's own valid webhook delivery with a modified header, which is trivial for any merchant using the app.

### Recommendation
Bind the identity fields to the signed payload instead of trusting bare headers:
- Include `shop`, `topic`, and `webhook_id` in the value that is HMAC-verified (e.g., by having the app-level validation also assert that the `shop` header value equals the shop the app expects for that webhook subscription/session, not solely rely on the raw body HMAC), or
- At minimum, document/enforce that consumers of `Registry.process`/`WebhookMetadata` must independently authenticate `shop` against their own session/shop store (e.g., confirm the shop is a known, currently-installed tenant) before trusting it for any state-changing operation, rather than treating a passing `HmacValidator.validate` as proof of the header-derived `shop`.
- Consider having `Request#to_signable_string` incorporate the shop/topic headers so that any header tampering invalidates the HMAC.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) that Shopify signs and delivers to the app's webhook endpoint with headers:
   - `x-shopify-hmac-sha256: <valid HMAC over raw body>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
2. Attacker captures this raw HTTP request (body + `x-shopify-hmac-sha256` unchanged).
3. Attacker re-sends the identical body/HMAC to the same webhook endpoint but with:
   - `x-shopify-shop-domain: victim.myshopify.com`
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` — validation succeeds because the body/HMAC pair is unchanged:
   ` [5](#0-4) `
5. `Registry.process` dispatches to the app's handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, even though the body was actually generated for `attacker.myshopify.com`:
   ` [6](#0-5) `
6. Any host application logic keyed on `metadata.shop` (session lookup, uninstall handling, data deletion) now executes attacker-controlled data under the victim shop's identity — a cross-tenant confusion the "verified" HMAC was supposed to prevent.

          received_signature = verifiable_query.hmac
