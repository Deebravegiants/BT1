This confirms the finding: `AuthQuery#to_signable_string` (used in OAuth callback validation) explicitly includes the `shop` field in the signed string [1](#0-0) , but `Webhooks::Request#to_signable_string` only returns the raw HTTP body, excluding the `x-shopify-shop-domain` header entirely from the HMAC computation [2](#0-1) . The `shop` accessor is read straight from that unauthenticated header [3](#0-2)  and is passed downstream to the app's webhook handler after only the body-HMAC check succeeds [4](#0-3) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body [2](#0-1) , and `Utils::HmacValidator.validate` computes/compares the HMAC solely over that string [5](#0-4) . The `shop` value, read from the `x-shopify-shop-domain`/`shopify-shop-domain` header [3](#0-2) , is never part of the HMAC-signed material, yet `Registry.process` trusts it and forwards it to the app's handler as the tenant identifier once the body-only HMAC passes [4](#0-3) .

### Finding Description
The intended identity binding is: `HMAC-verified webhook payload == (shop, body)` — i.e., a valid signature should attest to both which shop the event is about and what the event contains. Instead the binding actually enforced is `HMAC-verified payload == body only`; `shop` is accepted from an unauthenticated header. This is the same bug class as the referenced report: a field that is acted upon (here, `shop`, used as the tenant key passed to `WebhookMetadata` and ultimately to the host app's persistence/business logic) is not covered by the cryptographic check that is supposed to authenticate the request.

Contrast this with `Auth::Oauth::AuthQuery`, where `shop` is explicitly included inside `to_signable_string` and thus is bound by the HMAC [1](#0-0) . No equivalent binding exists for `Webhooks::Request`.

Any entity capable of receiving one legitimately signed webhook for a shop it controls (e.g., any merchant who installs the app on their own store — an unprivileged action, not requiring `api_secret_key` or any privileged credential) obtains a `(body, valid HMAC)` pair. Because the HMAC never covers the shop header, that same `(body, HMAC)` pair remains valid when replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` will still return `true` [6](#0-5) , and `Registry.process` will hand the handler a `WebhookMetadata` claiming the victim shop, causing the app to process/store attacker-controlled data under the victim's tenant identity.

### Impact Explanation
This breaks cross-tenant isolation, one of the impact categories explicitly in scope. Depending on how a host application implements its webhook handler (a documented, expected usage pattern of this gem, since the gem is what supplies `shop` as the trusted tenant key), an attacker could inject fabricated data (e.g., fake `orders/create`, `app/uninstalled`, or GDPR-style webhooks) attributed to a shop they do not own, without ever needing that shop's credentials.

### Likelihood Explanation
Likelihood is high for any app that relies on this gem's `Webhooks::Request`/`Registry` for webhook shop attribution as documented, since:
- No secret key, access token, or privileged access is required — only that the attacker be able to install the app on a shop they control and capture one legitimate webhook.
- The header swap is trivial (a single HTTP header value), and the vulnerable code path (`Registry.process` → `HmacValidator.validate` → `request.shop`) is the gem's standard, documented webhook flow.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) as part of the HMAC-verified signable material for webhooks, or otherwise cryptographically bind `shop` to the signature (mirroring what `AuthQuery#to_signable_string` already does for OAuth). At minimum, document prominently that `request.shop` is unauthenticated and must be cross-checked by the host application against an independently known shop identity before being trusted as a tenant key.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers an event (e.g., updates a product) so Shopify sends a legitimately signed webhook: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker replays the exact same request to the app's webhook endpoint but changes only `x-shopify-shop-domain` to `victim-shop.myshopify.com`, keeping body `B` and header `H` unchanged.
3. `ShopifyAPI::Webhooks::Request#hmac` reads `H` unchanged; `to_signable_string` still returns `B` unchanged [7](#0-6) .
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` with the app's secret and it matches `H`, so validation passes [5](#0-4) .
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: parsed_body(B) ...)` [8](#0-7) , causing the host app to act on attacker-controlled data as if it originated from the victim shop.
