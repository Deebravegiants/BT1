### Title
Position NFT transfers can permanently lock lending accounts at incapable contracts - ([File: contracts/position-nft/src/contract.rs](contracts/position-nft/src/contract.rs))

### Summary
The position NFT exports the stock `transfer`/`transfer_from` interface without validating that `to` can later authorize or move the token. [1](#0-0)  Because `account_id == token_id`, transferring the NFT transfers control of the entire lending account, including its collateral and debt. [2](#0-1) 

### Finding Description
`transfer` requires authorization from `from`, while `transfer_from` requires authorization from an owner, approved spender, or operator; neither path checks whether `to` is an account capable of subsequently controlling the position. [3](#0-2)  The controller does not retain a separate owner: it resolves account ownership through `owner_of(token_id)` for each operation. [4](#0-3) 

Consequently, an owner or approved operator can move a position NFT to an arbitrary Soroban contract that has no method capable of invoking the NFT contract. The NFT's `Owner` entry then names that contract, so owner-gated controller calls such as `withdraw` can no longer be authorized by the previous owner. [5](#0-4) 

### Impact Explanation
This can permanently freeze all collateral represented by the lending account: the previous owner loses authority immediately, while an incapable recipient cannot transfer the NFT onward or authorize controller operations. [6](#0-5)  The collateral remains protocol-backed but unreachable unless the recipient contract already has—or is later upgraded to have—a suitable control path. [7](#0-6) 

### Likelihood Explanation
Any unprivileged NFT holder can invoke `position_nft.transfer(from, to, token_id)`, and any approved spender can invoke `transfer_from(spender, from, to, token_id)`. [8](#0-7)  Smart wallets, vaults, marketplaces, or integration contracts that are not explicitly designed to control XOXNO position NFTs are plausible recipients, making accidental or malicious freezing feasible. [9](#0-8) 

### Recommendation
Add a checked-transfer mechanism that proves the recipient can control the position, such as a receiver-acceptance callback or explicit recipient authorization, before assigning ownership to a contract. At minimum, reject contract recipients in `transfer`/`transfer_from` unless the recipient implements a documented position-control interface. [1](#0-0) 

### Proof of Concept
```rust
// contracts/position-nft/src/test.rs
#[contract]
pub struct InertReceiver;

#[contractimpl]
impl InertReceiver {}

#[test]
fn position_nft_can_be_locked_at_an_incapable_contract() {
    let env = Env::default();
    env.mock_all_auths();
    let (_controller, nft) = setup(&env);
    let alice = Address::generate(&env);
    let token_id = nft.mint(&alice);

    let receiver = env.register(InertReceiver, ());

    nft.transfer(&alice, &receiver, &token_id);
    assert_eq!(nft.owner_of(&token_id), receiver);

    // No account signer can satisfy `from.require_auth()` for `receiver`, and
    // InertReceiver exports no call that can authorize moving the NFT onward.
    assert!(nft.try_transfer(&receiver, &alice, &token_id).is_err());
}
```

Before this sequence, `controller.supply(caller = alice, account_id = 0, ...)` can create a collateralized account and mint the corresponding NFT to Alice. After the NFT transfer, Alice's owner-gated `controller.withdraw(caller = alice, account_id = token_id, ...)` is rejected because the controller reads the inert contract as the current owner. [5](#0-4)
