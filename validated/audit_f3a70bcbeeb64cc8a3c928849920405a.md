### Title
Overwriting an `IntentGatewayV2` peer instance via `NewDeployment` permanently locks escrow for orders in-flight to the old peer - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`/`ExtrinsicIntents` authenticates every cross-chain `RedeemEscrow`/`RefundEscrow` delivery and every cross-chain cancel dispatch against a single mutable mapping, `_instances[keccak256(chain)]`, set by `_addDeployment`. Governance (Hyperbridge) can call this again for the same `chain` at any time to point it at a new gateway address, with no check for outstanding escrow tied to the previous instance. This mirrors the `Staking.removeAuthorizedGame()` pattern: a privileged re-registration/removal action can strand funds that were escrowed under the old authorization, with no way to release them.

### Finding Description
`_instances` maps `keccak256(stateMachineId)` to the trusted peer gateway address on that chain, and is written unconditionally by `_addDeployment`: [1](#0-0) 

This value is used both to dispatch new cross-chain messages (`instance(order.source/destination)` as the `to`/expected sender) and to authenticate every incoming `RedeemEscrow`/`RefundEscrow` post request in `onAccept`, via `_authenticate`, before releasing escrow: [2](#0-1) 

There is no accounting of "in-flight" cross-chain orders per destination/source instance, and no check preventing `_addDeployment` from being invoked again for a `chain` that already has an existing registered gateway with pending escrowed orders (i.e., orders placed and dispatched while the old instance address was authoritative, but not yet redeemed/refunded). Once the mapping is repointed to a new address:
- Any `RedeemEscrow`/`RefundEscrow` message that the old peer gateway later dispatches referencing the previous instance will fail `_authenticate`'s check against the now-updated `_instances` entry (since authentication is keyed by the current stored address, not the address that was live at order-placement time).
- The escrow for those orders (`_orders[commitment][token]`) has no other path to be released: `withdraw()`/`_withdraw()` are only reachable through `onAccept` (source-authenticated) or the cancel-from-source GET-response flow, both of which route through the same `_instances` lookup / authentication that is now broken.

This is structurally identical to the `Staking.removeAuthorizedGame()` bug: a privileged, unrestricted re-registration action (`NewDeployment`/`_addDeployment`) can silently invalidate the trust anchor that in-flight escrow depends on, with no bookkeeping of "locked liquidity per instance" to gate the change.

### Impact Explanation
Impact is Medium: user funds escrowed in `IntentGatewayV2`/`ExtrinsicIntents` for orders that are mid-flight (dispatched, not yet filled/cancelled) at the moment governance re-registers a chain's gateway instance become permanently unredeemable and unrefundable, since the authenticating address for their `RedeemEscrow`/`RefundEscrow`/cancel-response messages no longer matches the instance mapping. This is a freezing-of-funds condition reachable purely from a normal user's order/escrow flow combined with a routine governance action (chain re-registration), not a compromise.

### Likelihood Explanation
Likelihood is Medium: `NewDeployment` (re-registering/rotating a gateway peer for a state machine) is a plausible, expected governance operation for redeploying or migrating a destination gateway, and nothing in the code prevents calling it while orders referencing the old instance are outstanding. Any order placed shortly before such a rotation and still awaiting cross-chain settlement is affected.

### Recommendation
Track outstanding cross-chain escrow (or in-flight order commitments) per destination/source instance address, and either (a) refuse to overwrite `_instances[keccak256(chain)]` while there is escrow still tied to the previous instance for that chain, or (b) retain the previous instance address as a still-valid authenticator for any pre-existing in-flight orders until they settle, so a governance rotation cannot strand escrowed funds.

### Proof of Concept
Conceptual PoC (not executed):
1. User places a cross-chain order with `source = chainA`, `destination = chainB`; `_orders[commitment][token]` escrow is created on `chainA`, and `_instances[keccak256(chainB)] = gatewayB_old` is the currently registered peer.
2. Before the order is filled, cancelled, or settled, Hyperbridge governance dispatches a `NewDeployment` request for `chainB` pointing to `gatewayB_new` (e.g., a redeploy/migration), calling `_addDeployment` on the gateway on `chainA`, which overwrites `_instances[keccak256(chainB)] = gatewayB_new`.
3. The solver fills the order on `chainB` (against `gatewayB_old`, the contract the order was actually placed against) and dispatches `RedeemEscrow` back to `chainA`.
4. On `chainA`, `onAccept`/`_authenticate` checks the incoming request's `from` against the current `instance(order.destination)`, which is now `gatewayB_new`, not `gatewayB_old` — authentication fails and the escrow release reverts.
5. The escrowed tokens for that commitment remain locked in the `chainA` gateway indefinitely, with no remaining code path to release them, since both `RedeemEscrow` and the source-cancel GET-response flow depend on the same now-stale `_instances` entry. [3](#0-2)
