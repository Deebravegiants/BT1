## Analysis

The bug-class from the report (unchecked/uncovered data used for a security-relevant computation) maps to a genuine identity-binding gap in this gem's webhook verification path.

### The binding that's supposed to hold
`HMAC-valid(raw_body) ⟹ shop == request.shop`

In practice the gem only proves the first half. `ShopifyAPI::Utils::HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string`, and for webhooks that method returns only the raw HTTP body: [1](#0-0) 

The `shop-domain` header, however, is never included in the signable string, and is never independently verified: [2](#0-1) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC over the body only, then trusts `request.shop` (and `request.topic`) unconditionally when dispatching to the handler: [3](#0-2) 

And the HMAC computation itself: [4](#0-3) 

### Why this is exploitable
Any body content that gets a valid, secret-derived HMAC (e.g. `{}` combined with the app's `api_secret_key`, or any legitimate webhook payload the attacker's own shop installation triggers and observes) remains valid for **any** `shop-domain` header value, because that header is not part of the signed bytes. An attacker who controls a shop that has installed the target app (an unprivileged, legitimately-onboarded merchant/attacker) can capture one genuine, correctly-HMAC'd webhook request sent to the app's public webhook endpoint, then replay it with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a victim shop's domain, while keeping the same raw body and therefore the same valid HMAC. The webhook `Registry` will accept the HMAC as valid and dispatch to the app's handler with `WebhookMetadata#shop` set to the attacker-chosen value: [5](#0-4) 

Downstream app logic that uses `data.shop` to key session/tenant lookups (the documented and expected usage pattern for webhook handlers) will act on data under the wrong tenant identity, i.e., a cross-tenant data-injection primitive achieved purely by an unprivileged actor controlling only their own shop's webhook traffic.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` header. `Utils::HmacValidator.validate` and `Webhooks::Registry.process` therefore only prove the body's integrity, not which shop it originated from, yet the same `request.shop` value is trusted and forwarded to app handlers as the authoritative tenant identifier.

### Finding Description
The intended invariant is that a webhook accepted as HMAC-valid genuinely originates from the shop named in its `shop-domain` header — i.e., `hmac_valid ⟹ shop_header == originating_shop`. Because the signed bytes are `raw_body` alone [6](#0-5) , the `shop-domain` header can be freely substituted by anyone who can produce one valid `(body, hmac)` pair for the app's secret — which any shop that installs the app can legitimately obtain by triggering its own webhooks. `Registry.process` performs no additional check binding `request.shop` to the HMAC or to any registered installation record [3](#0-2) , so the forged shop value flows directly into `WebhookMetadata`, which app code uses as the tenant key.

### Impact Explanation
This crosses a tenant boundary using only a valid signature obtained through legitimate self-installation, satisfying the "cross-tenant access" Critical-impact category: an attacker can make the app process/store attacker-controlled webhook payloads under a victim shop's identity.

### Likelihood Explanation
Requires only that the attacker operates (or installs the app on) one shop to legitimately receive/observe one valid `(body, hmac)` pair, then replays it against the app's public webhook endpoint with a rewritten `shop-domain` header — no access to the app's `client_secret` or any victim credential is needed.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header bytes in the signed string, or independently cross-check that the HMAC-covered payload's origin matches the claimed `shop-domain` header (e.g., by also verifying the shop against a known/registered installation) before dispatching to handlers.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and triggers a webhook with a known, reproducible body (e.g., an empty JSON body `{}` for a topic where that's valid), capturing the resulting `x-shopify-hmac-sha256` value — which is valid for `HMAC(api_secret_key, "{}")`.
2. Attacker sends a forged HTTP request directly to the app's public webhook endpoint with headers:
   - `x-shopify-topic: <same topic>`
   - `x-shopify-hmac-sha256: <captured valid HMAC>`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - body: `{}`
3. `Utils::HmacValidator.validate` succeeds because it only checks the body [7](#0-6) .
4. `Registry.process` dispatches to the handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , causing the app to act as though the event came from the victim tenant.
