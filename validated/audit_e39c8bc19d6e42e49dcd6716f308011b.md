### Title
Webhook `shop` domain is trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` (and `topic`) values used to route and label the webhook are taken from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then trusts `request.shop` to attribute the delivered payload to a tenant, without that binding ever being covered by the signature.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. Meanwhile `shop` is read straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header with no cryptographic binding to the signed content: [2](#0-1) 

`HmacValidator.validate` only checks that `hmac == HMAC(secret, to_signable_string)`, i.e. it verifies the equality `HMAC(secret, raw_body) == received_hmac` — it never verifies any equality involving `shop`: [3](#0-2) 

`Registry.process` uses this validated-but-shop-blind request to dispatch to the app's handler, passing the unauthenticated `request.shop` straight into the metadata the app's business logic acts on: [4](#0-3) 

Because the webhook signing secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every merchant that has installed the app rather than being per-shop, any body that produces a valid HMAC for one tenant produces the same valid HMAC regardless of which `shop` header accompanies it. The gem's own binding is therefore: `HMAC(secret, raw_body)` is verified, but the tenant identity (`shop`) that the app subsequently trusts is parsed from bytes that were never part of that equality.

### Impact Explanation
Any unprivileged actor who is a merchant of the app (and therefore legitimately receives real, validly-signed webhook deliveries for their own store) can capture a body/HMAC pair and replay it to the app's webhook endpoint with a different `x-shopify-shop-domain` header. `Registry.process` will still accept it as authentic (the HMAC still matches the body) and will hand the handler a `WebhookMetadata` claiming the payload originated from an arbitrary victim shop: [5](#0-4) 
Depending on how the host app keys its per-tenant state off `WebhookMetadata#shop`, this enables cross-tenant data confusion/injection under another merchant's identity — a break of the shop-to-signature binding that the gem is supposed to enforce.

### Likelihood Explanation
Moderate: exploitation requires being (or having been) a legitimate installer of the target app to obtain a validly HMAC-signed body/signature pair, then simply relaying it with a modified shop header. No secret leakage, TLS interception, or privileged access is required — only ordinary use of the app as a merchant plus the ability to send arbitrary HTTP requests to the app's public webhook endpoint.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signable content the HMAC is computed over, or otherwise cryptographically bind the shop domain to the signature (e.g., verify the shop against the session/shop the app expects for that specific webhook subscription) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. App merchant A installs the app; Shopify delivers a webhook to the app with body `B`, headers `{x-shopify-shop-domain: "shop-a.myshopify.com", x-shopify-hmac-sha256: HMAC(secret, B)}`.
2. Attacker (merchant A) captures this valid request.
3. Attacker resends the same body `B` and same HMAC header, but sets `x-shopify-shop-domain: "shop-b.myshopify.com"` (a different tenant).
4. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B)`; `Registry.process` dispatches the handler with `shop: "shop-b.myshopify.com"`, even though the payload never actually came from shop B's tenant. [4](#0-3)
