### Title
Stranded token balance in `LifiExternalAction` can be exfiltrated by any later caller via unconstrained `callRouter`/`swappedAmount` accounting - (File: `contracts/external-actions/swaps/LifiExternalAction.sol`, `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`LifiExternalAction.callRouter` grants the router a persistent unlimited allowance via `approveUnlimited(inputToken, router)` and never asserts that the router consumed exactly `inputAmount` of `inputToken`. `ExternalActionSwap.swap` computes `swappedAmount` purely from the `outputToken` balance delta, so any residual `inputToken` left in `LifiExternalAction` from a prior partial-fill swap can be pulled by the router in a later, unrelated `transact()` call and converted to `outputToken` credited entirely to that later caller.

### Finding Description
The broken equality is: *tokens the router is permitted to pull from `LifiExternalAction` during a given `swap()` call* should equal *`inputAmount = uint256(-deltaAmounts[0])`, the amount Hinkal.sol just transferred to `LifiExternalAction` for that specific `transact()`*. Neither `swap()` nor `callRouter()` enforce this.

Path: `Hinkal.transact()` → `_externalTransact` (`contracts/Hinkal.sol:244-256`) transfers `-deltaAmountChanges[0]` of `inputToken` to `LifiExternalAction`, then calls `IExternalActionV2.runAction` → `ExternalActionSwap.swap` (`contracts/external-actions/swaps/ExternalActionSwap.sol:40-102`) → `LifiExternalAction.callRouter` (`contracts/external-actions/swaps/LifiExternalAction.sol:16-36`).

`callRouter` does:
```solidity
approveUnlimited(inputToken, router);
(bool success, ) = router.call(externalActionMetadata);
...
swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
``` [1](#0-0) 
`approveUnlimited` leaves a max allowance in place across calls if one already exists [2](#0-1) . `externalActionMetadata` is fully attacker-supplied calldata forwarded verbatim to `router.call`; nothing in `swap()`/`callRouter()` checks that the router consumed only `inputAmount` of `inputToken`, nor that `LifiExternalAction`'s `inputToken` balance returns to its pre-call value. `swappedAmount` is derived solely from the `outputToken` balance delta.

If a prior `transact()` left residual `inputToken` sitting in `LifiExternalAction` (e.g., the router only partially filled the swap and the leftover input was never reclaimed), that residual, combined with the still-standing unlimited allowance, is available to be pulled by *any* subsequent `transact()` that routes through `LifiExternalAction`. An attacker generates their own valid proof/UTXO with a small declared `inputAmount` (even 1 wei) but crafts `externalActionMetadata` that instructs the router to pull the entire current `inputToken` balance of `LifiExternalAction` (new funds + stranded residue) and swap it all to `outputToken`. `swappedAmount` then reflects the inflated output, and `ExternalActionSwap.swap` mints the attacker a UTXO for `amountToSendToHinkal = swappedAmount - totalFee` (`contracts/external-actions/swaps/ExternalActionSwap.sol:91-101`), transferring that full amount to `msg.sender` (Hinkal.sol), which then satisfies Hinkal.sol's own per-transaction `balanceDif == amountChanges[i] + utxoAmount` check trivially — because Hinkal.sol's own balance bookkeeping is self-consistent for its own transfer to/from `LifiExternalAction`, it has no visibility into `LifiExternalAction`'s internal residual balance [3](#0-2) . The circuit's `calldataHash` only commits to the metadata bytes for integrity; it does not constrain their numeric meaning against `inputAmount`/`outputToken` amounts [4](#0-3) . `onlyAllowedRecipient` only restricts `msg.sender` of `runAction` to Hinkal.sol itself [5](#0-4) , it does not restrict what the crafted metadata can instruct the router to pull.

### Impact Explanation
An unprivileged attacker steals ERC-20 value that legitimately belongs to whoever's prior swap left the residual balance stranded in `LifiExternalAction` (the protocol or another depositor whose partial-fill swap under-delivered output and left them without a UTXO for the unconverted portion). This is a direct theft of another user's/protocol's funds mediated entirely through the exploit path in this repo's code, matching the Critical category (theft of in-flight/stranded user funds via a path never authorized by the original depositor's proof).

### Likelihood Explanation
Requires: (1) `LifiExternalAction` registered in `Hinkal.externalActionMap`, (2) a prior swap through it that leaves nonzero residual `inputToken` balance (plausible whenever the LI.FI router performs a partial fill or leaves dust, a realistic router behavior), (3) attacker holds any valid UTXO/proof for that `inputToken` to enter `_externalTransact`, and (4) ability to craft arbitrary calldata for the router accepted as `externalActionMetadata`. All of these are attacker-controllable or externally plausible; no privileged role is needed, and the attack is repeatable each time a residual balance accumulates.

### Recommendation
In `ExternalActionSwap.swap`/`LifiExternalAction.callRouter`, snapshot `inputToken` balance of the action contract before and after the router call and assert the decrease equals exactly `inputAmount` (revert on over/under consumption). Avoid persistent unlimited approvals to the router; approve exactly `inputAmount` per call instead of `approveUnlimited`, and reset any leftover allowance/balance to zero (sweep residual `inputToken` back to Hinkal or fail the transaction) so no value can carry over and be attributed to an unrelated later caller.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and `LifiExternalAction` with a mock router `R` and register `LifiExternalAction` in `externalActionMap`.
2. User A deposits `inputToken` and performs a `transact()` swap where `R`'s calldata intentionally consumes only part of the transferred `inputToken` (partial fill), leaving `inputToken.balanceOf(LifiExternalAction) > 0` after tx1; assert this stranded balance directly.
3. Assert Hinkal.sol's own `balanceDif == amountChanges[i] + utxoAmount` holds for tx1 (showing Hinkal's accounting is blind to the stranded amount).
4. Attacker B deposits a trivial `inputToken` UTXO and calls `transact()` with `externalActionId` = LifiExternalAction id, `deltaAmounts[0]` = -1 wei, but crafts `externalActionMetadata` so `R` pulls `inputToken.balanceOf(LifiExternalAction)` (new 1 wei + tx1's stranded residue) and returns proportional `outputToken`.
5. Assert `LifiExternalAction`'s `inputToken` balance drops to 0 (stolen) while B's minted UTXO amount for `outputToken` exceeds what corresponds to B's declared 1 wei input — i.e., assert `swappedAmount pulled from LifiExternalAction != -deltaAmounts[0] declared in tx2`, proving the equality violation and fund theft from A's residual balance.
