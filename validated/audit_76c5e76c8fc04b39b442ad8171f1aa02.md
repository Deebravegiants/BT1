### Title
Missing `deadline` protection on native-token fee swaps in `EvmHost` — `deadline: block.timestamp` disables Uniswap MEV protection - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all allow an unprivileged caller to pay protocol fees in native token. When `msg.value > 0`, each of these functions performs an on-chain swap via `IUniswapV2Router02.swapETHForExactTokens`, passing `block.timestamp` as the `deadline` argument instead of a caller-supplied, meaningfully-bounded deadline. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
This is the same anti-pattern described in the external report: passing `block.timestamp` as a Uniswap swap `deadline` is a no-op deadline check, because `block.timestamp` is evaluated at the moment of transaction *execution*, not at submission time. This means a transaction can sit in the mempool indefinitely — regardless of how much time or how many blocks pass — and Uniswap's deadline check will always pass, since the value being compared against `block.timestamp` *is* `block.timestamp` at inclusion time.

In all three EvmHost functions, the swap is `swapETHForExactTokens(fee, path, address(this), block.timestamp)`: an *exact-output* swap where `msg.value` is the implicit `amountInMax`. Because there is no genuine time bound, a pending `dispatch()`/`fundRequest()` transaction can be held by a searcher/validator and included at an opportune moment after manipulating the WETH/feeToken pool price (a classic sandwich), forcing the swap to consume close to the full `msg.value` to acquire the fixed `fee`/`amount` output. The caller has no way to cap slippage other than the total ETH they send, and no way to bound how long their quote should remain valid — exactly the MEV/stale-execution risk the source report flags.

This differs from `IntentGatewayV2` and the `UniV3UniswapV2Wrapper`/`UniV4UniswapV2Wrapper` contracts, which correctly accept a caller-supplied `deadline` parameter for their swaps (see `swapETHForExactTokens(uint256 amountOut, address[] calldata path, address recipient, uint256 deadline)` in `evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol`), confirming the codebase is aware of proper deadline handling elsewhere but omitted it in `EvmHost`. [4](#0-3) 

### Impact Explanation
Any unprivileged user submitting a POST/GET dispatch or funding a request with native ETH (`EvmHost.dispatch`, `EvmHost.fundRequest`) is exposed to MEV extraction of the excess ETH sent for the fee swap, because the deadline offers no protection against delayed/opportunistic inclusion. This is directly reachable by any external caller of `EvmHost`'s message-dispatch entrypoints — a core, unprivileged path (message dispatcher paying via native token) — and results in concrete value loss (theft of the price difference) to a searcher/validator rather than the protocol or the intended fee recipient. It does not brick message delivery (an ETH-based dispatch is a convenience path; feeToken-based dispatch remains available), but for users who rely on the ETH-swap convenience path, it is a real fund-theft vector via MEV sandwiching, matching the severity class of the original report.

### Likelihood Explanation
Any transaction paying with native ETH through `dispatch()` or `fundRequest()` is trivially observable in the public mempool, and Uniswap V2 pools are commonly monitored/sandwiched by MEV bots. Since the deadline check is inert, an attacker does not even need to race a tight time window — they can wait for optimal pool conditions before including the swap, making this an easily and reliably exploitable pattern once the ETH-based fee-payment path is used.

### Recommendation
Add a `_deadline` parameter to `DispatchPost`/`DispatchGet` (or to `dispatch`/`fundRequest` directly), validated by the caller, and pass it through to `swapETHForExactTokens` instead of `block.timestamp`, mirroring the fix already applied to the `UniV3UniswapV2Wrapper`/`UniV4UniswapV2Wrapper` contracts in this repo.

### Proof of Concept
1. A user calls `EvmHost.dispatch(DispatchPost)` (or `dispatch(DispatchGet)`/`fundRequest`) with `msg.value > 0` to pay the protocol fee in ETH, targeting a specific `post.fee` amount of `feeToken`.
2. A searcher observes the pending transaction in the mempool.
3. Because `deadline` is `block.timestamp` (always "now" at execution), the searcher can hold/delay inclusion and, right before it lands, move the WETH/feeToken Uniswap V2 pool price against the user (front-run), then restore it after (back-run).
4. `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` executes at the manipulated price, consuming close to all of `msg.value` in ETH to buy the fixed `post.fee` output — the difference between fair price and worst price is extracted by the searcher.
5. The user's dispatch still succeeds (so this is not solely a DoS), but they overpay for the fee swap, resulting in a real loss of ETH value to MEV extraction that could have been prevented by a genuine, short-lived deadline.
