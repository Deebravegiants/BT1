### Title
Unbounded router call lets attacker sweep stranded/residual token balance out of `ExternalActionSwap` as their own output UTXO - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol` / `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`LifiExternalAction.callRouter` measures `swappedAmount` purely as the balance delta of `outputToken` around an arbitrary, attacker-controlled `router.call(externalActionMetadata)`, and never checks how much `inputToken` the router actually pulled versus the declared `inputAmount`. Combined with the `approveUnlimited(inputToken, router)` allowance left standing from any prior call, any balance of `inputToken` sitting in the shared action contract (dust, slippage residue, LI.FI refunds, or tokens sent by any other transaction/user) can be pulled by the router under attacker-supplied calldata and swapped, and the resulting output is credited 100% to the attacker's own new UTXO.

### Finding Description
Broken equality: *tokens leaving the action contract as a newly minted output UTXO in transaction T == -deltaAmountChanges[0] that Hinkal transferred into the action for T* (input pulled from attacker's shielded balance).

Code path:
- `ExternalActionSwap.swap` computes `inputAmount = uint256(-deltaAmounts[0])` [1](#0-0)  and passes it to `callRouter`, but `inputAmount` is only used to compute the declared/expected pull — it is never enforced against what the router actually consumes.
- `LifiExternalAction.callRouter` grants a persistent unlimited approval and then forwards fully attacker-controlled calldata to the router: [2](#0-1) . The router decides how much `inputToken` to pull (the `amountIn` is embedded inside `externalActionMetadata`, which the attacker crafts entirely off-chain per the threat model), and it can pull up to the entire `inputToken` balance held by the action contract because `approveUnlimited` was already set (from this or any prior call).
- `swappedAmount` is derived solely from `getERC20OrETHBalance(outputToken)` before/after the call [3](#0-2) , so it faithfully reflects whatever came in — including value sourced from tokens that were not part of this transaction's declared `-deltaAmounts[0]`.
- Back in `swap`, the entire `swappedAmount` (minus fees) is sent to `msg.sender` (the Hinkal helper) and wrapped into a brand-new `UTXO` addressed to the caller's `stealthAddressStructure` [4](#0-3) , with no check tying `amountToSendToHinkal` back to any circuit-committed expected-output value.

Root cause: the contract has no invariant of the form "input token balance decreased by exactly `inputAmount`" around the router call, and `approveUnlimited` never gets revoked/reset to the exact needed amount. Since `LifiExternalAction`/`ExternalActionSwap` is a shared, singleton contract used across all users' swaps, any inputToken balance stranded there from a previous transaction (partial fill leftovers, LI.FI cross-chain refund arriving later to `msg.sender=this`, rounding dust, or an unrelated direct transfer) remains spendable by the router under the standing unlimited allowance. The attacker's exploit call declares a trivial `deltaAmounts[0]` (minimal cost to their own shielded balance) but crafts `externalActionMetadata` whose embedded `amountIn` is the full stranded balance, causing the router to swap far more value than the attacker paid in, all of which lands in the attacker's own freshly-minted output UTXO.

Existing guards do not catch this: `performHinkalChecks`, `verifyProof`, `rootHashExists`, and the circuit's `inTotal + amountChanges === outTotal` constrain the *input* leg (the shielded UTXO being spent must match `-deltaAmounts[0]`), but nothing constrains the *output* leg produced by `swap()` to be bounded by that same declared delta — by design, swap output is variable (market price dependent), which is exactly the gap this exploit hides inside.

### Impact Explanation
Direct theft of value that is not the attacker's: any residual/stranded ERC-20 balance sitting in the shared `LifiExternalAction`/`ExternalActionSwap` contract (dust, slippage residue, delayed LI.FI refunds meant for a different user, or a previous incomplete swap's leftover) can be swept by any unprivileged attacker into their own private-pool UTXO for the cost of a near-zero declared input. This is repeatable every time residual balance accumulates in the contract, and it matches the "Critical - direct theft of shielded or in-flight user funds" category since the funds captured belong to the protocol/other users, not the attacker.

### Likelihood Explanation
Preconditions: (1) `approveUnlimited` has been set on `inputToken`→`router` by any prior call (this is the expected/normal state of the contract after its first swap, since it is never revoked), and (2) some non-zero balance of `inputToken` exists in the action contract beyond what the current transaction's declared `inputAmount` would justify (achievable via LI.FI partial fills/refunds, rounding, or even the attacker priming it themselves in a prior transaction using otherwise-unrecoverable dust). Attacker cost is minimal (one transaction, their own trivial declared input, and off-chain construction of router calldata that specifies a larger `amountIn`, which is standard LI.FI/DEX calldata attackers can freely build since `externalActionMetadata` is fully attacker-supplied). This is repeatable across any block where such residual balance exists, and batching/ordering (as raised in the question) lets an attacker specifically front-run the sweep before the rightful owner's follow-up transaction can reclaim it.

### Recommendation
Enforce a strict input-conservation check in `callRouter`/`swap`: record the `inputToken` balance immediately before invoking the router and require that the balance decreased by exactly `inputAmount` (no more, no less) after the call, reverting otherwise. Additionally, replace `approveUnlimited` with a per-call approval scoped exactly to `inputAmount` and reset it to zero after the call, so the router can never pull more than the current transaction authorized regardless of what calldata is supplied. Consider also sweeping/disallowing any output-token balance surplus not attributable to the current call's before/after snapshot from being attributed to the caller's UTXO.

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction` with a mock router and mock ERC-20 tokens (`tokenIn`, `tokenOut`).
2. Simulate "prior Emporium op residual": directly `tokenIn.mint(address(lifiAction), RESIDUAL)` to represent stranded/refunded balance, and have the mock router record that `approve(router, type(uint256).max)` was already granted from a prior legitimate call (call `swap` once normally first so `approveUnlimited` is set).
3. Attacker calls `runAction` (via a caller registered as `isAllowedRecipient`, simulating the Hinkal helper relaying attacker's proof) with `deltaAmounts[0] = -1` (trivial declared input) and `externalActionMetadata` crafted to instruct the mock router to `transferFrom(lifiAction, router, RESIDUAL + 1)` of `tokenIn` and mint/transfer back a proportional `tokenOut` amount.
4. Assert: `swappedAmount` (and thus `utxoSet[0].amount`) reflects the full `RESIDUAL + 1` worth of output, not just the amount corresponding to the declared `deltaAmounts[0] = 1`.
5. Assert the broken equality: tokens leaving the action (`swappedAmount` credited to attacker's UTXO) `!=` `-deltaAmountChanges[0]` (1) that Hinkal charged the attacker for that transaction, demonstrating attacker captured `RESIDUAL` worth of value that did not belong to them.

```text
    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
```
