### Title
Webhook `shop` (tenant) identity is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, and `ShopifyAPI::Webhooks::Registry.process` accepts `request.shop` unauthenticated when dispatching the payload to the app's registered handler. The tenant-identifying header `x-shopify-shop-domain` (as well as `topic`, `webhook-id`, `api-version`) is never part of the HMAC-signed content, so an attacker can replay a body+HMAC pair that Shopify genuinely signed for the attacker's own shop while substituting an arbitrary `shop-domain` header, causing the gem to hand the handler data claiming to originate from a victim shop.

### Finding Description
`HmacValidator.validate` computes the signature strictly from `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body, excluding every header: [2](#0-1) 

`Registry.process` verifies only this body HMAC, then immediately trusts `request.shop` (parsed straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

The identity binding that should hold is: *`shop` used to attribute webhook data == shop that Shopify authenticated when generating the HMAC*. Because the HMAC only proves "this body was produced using the app's shared `client_secret`" and says nothing about which shop it came from, this equality does not hold. Since a single app's `client_secret` is shared across every merchant that installs the app, any merchant who installs the app can legitimately receive a genuine `(raw_body, hmac)` pair for their own shop, then resend that exact pair to the app's webhook endpoint with a forged `x-shopify-shop-domain` (and/or `topic`) header pointing at a different tenant. `HmacValidator.validate` will pass because the body/HMAC combination is valid, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce before invoking application webhook handlers: the `shop` field an app relies on to route/attribute webhook data (e.g., to look up the correct merchant record, session, or resource) is attacker-controlled while the accompanying body/HMAC merely proves possession of a validly-signed payload from *some* installed shop. This matches the report's identity-binding failure class exactly (a field acted on — `shop`/`topic`/`webhook_id` — but not covered by the HMAC), and it can be leveraged for cross-tenant data confusion/access in any app whose webhook handler trusts `WebhookMetadata#shop` without independent verification (which the library gives it no means to do, since the shop is never authenticated inside `ShopifyAPI::Webhooks::Registry`/`Request`).

### Likelihood Explanation
Any actor who can install the target app on their own shop (i.e., an ordinary unprivileged merchant/internet user relative to other tenants) automatically receives genuinely-signed webhooks for that shop and can immediately replay them with a modified `shop-domain` header against the same public webhook endpoint — no access token, `client_secret`, or privileged access to the victim's data is required.

### Recommendation
Include the tenant-identifying and dispatch-relevant fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content, or otherwise cryptographically bind them to the signed body before `Registry.process` uses `request.shop`/`request.topic` to build `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and that host applications must independently verify the shop is one they have on record before trusting the payload.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com`.
2. Shopify sends the attacker's app endpoint a webhook with `X-Shopify-Shop-Domain: attacker.myshopify.com`, a JSON body `B`, and `X-Shopify-Hmac-Sha256: HMAC(client_secret, B)`.
3. Attacker captures `B` and the HMAC value (trivial — it's their own inbox/log; no secret needed).
4. Attacker POSTs the identical body `B` and HMAC to the same webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` compute over `B` only [4](#0-3) ; `Utils::HmacValidator.validate` returns `true` [5](#0-4) .
6. `Registry.process` raises no error and calls the handler with `shop: "victim.myshopify.com"` [6](#0-5) , causing the application to process attacker-supplied, attacker-topic-chosen data as if it belongs to the victim tenant.
