## Analysis

The reported bug class — an externally callable function that grants no access control while allowing an attacker to route/approve/transfer funds through arbitrary attacker-supplied calldata — has a direct, concrete analog in `CallDispatcher.dispatch()`.

### Title
Unrestricted `CallDispatcher.dispatch()` allows anyone to drain any residual native/ERC20 balance held by the shared dispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, shared, permissionless-by-design singleton contract used by `HyperFungibleToken(Upgradeable)`, `WrappedHyperFungibleToken(Upgradeable)`, and `IntentGatewayV2`/`IntentsBase` to execute arbitrary attacker/user-supplied `Call[]` batches on behalf of these apps. Its public `dispatch(bytes memory encoded)` entrypoint has no caller restriction whatsoever — exactly the same access-control gap as `D3Callee()` in the referenced report — and it will execute `to.call{value: call.value}(call.data)` for any `to`/`value`/`data` triple supplied by the caller.

### Finding Description
`CallDispatcher.dispatch` is declared `external` with no modifier, no `onlyHost`/`onlyGateway` check, and no `msg.sender` validation of any kind: [1](#0-0) 

Compare this to the intended usage pattern, where `HyperFungibleTokenUpgradeable.onAccept` and `IntentsBase._execute` invoke the *same* dispatcher instance with app-controlled calldata as part of a single atomic transaction: [2](#0-1) [3](#0-2) 

Because `dispatch()` itself performs no authentication, an attacker can call it directly, at any time, independent of these intended flows, supplying their own `Call[]` array. The only condition needed for impact is that the shared `CallDispatcher` instance is holding any balance (native or ERC20) at the moment of the attacker's call. Several realistic ways such a balance can exist:

1. **Direct/mistaken transfers.** `CallDispatcher` implements an unguarded `receive() external payable {}` [4](#0-3)  so anyone can send native ETH to it; ERC20 tokens can likewise be sent to its address by mistake (a common occurrence for any well-known, reused "utility" contract address).
2. **Incomplete sweep coverage.** `IntentsBase._execute` only sweeps tokens enumerated in `order.output.assets` after running `order.output.call` [5](#0-4) . If the postdispatch calldata routes through an intermediate token not listed in `order.output.assets` (e.g., a multi-hop swap through WETH before reaching the final output token), any residual balance of that intermediate token is left on the dispatcher permanently — the protocol's own sweep logic never reaches it, but an unrestricted `dispatch()` call can immediately drain it to any address.
3. Because `CallDispatcher` is a **single shared instance** reused across `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2` deployments, dust or accidental deposits accumulated from *any* app/user become drainable by *anyone*, not just the depositor.

This is structurally identical to the `D3MMLiquidationRouter.D3Callee()` flaw: a public entrypoint that performs `approve`/arbitrary `call`/`transfer` on behalf of the contract with zero access control, letting any caller redirect funds sitting in (or transiently passing through) the contract to themselves.

### Impact Explanation
Any native ETH or ERC20 tokens that end up resident in the shared `CallDispatcher` — whether from accidental transfers, or from postdispatch swap paths that touch tokens outside `order.output.assets` — can be permanently stolen by any unprivileged address, with no relationship to the order, token, or dispatch that produced the balance. This is a direct loss-of-funds vector reachable from a single unauthenticated transaction, satisfying the "concrete theft" bar.

### Likelihood Explanation
Likelihood is dependent on the dispatcher actually holding a balance at some point outside of the fully atomic mint/execute/sweep sequences (e.g., swap paths with intermediate tokens not enumerated in `order.output.assets`, or accidental direct transfers to the well-known dispatcher address). Given `CallDispatcher` is meant to be reused across many orders/token transfers over the contract's lifetime, and its address is public/discoverable, an attacker (or automated MEV bot) simply needs to watch the dispatcher's balances and front-run/back-run with a `dispatch()` call sweeping any non-zero token/ETH balance to themselves.

### Recommendation
Restrict `CallDispatcher.dispatch()` to only be callable by an authorized/registered caller set (e.g., the specific gateway/token instances that are expected to use it), or make each app deploy/own its own dispatcher instance rather than sharing one globally-callable contract. Additionally, ensure `IntentsBase._execute`'s sweep logic accounts for *all* token balances the dispatcher could plausibly hold after arbitrary `order.output.call` execution, not only the tokens enumerated in `order.output.assets`.

### Proof of Concept
1. Some flow (either a mistaken direct transfer, or an `IntentGatewayV2` postdispatch swap that routes through an intermediate token not present in `order.output.assets`, e.g. USDC → WETH → DAI) leaves a non-zero WETH balance on the shared `CallDispatcher` contract.
2. An attacker observes this balance (it is a public, reusable contract, so its balance is trivially observable on-chain).
3. Attacker calls `CallDispatcher.dispatch(abi.encode(calls))` directly, with `calls = [Call({to: WETH, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, wethBalance)})]`.
4. Because `dispatch()` has no `msg.sender` check [6](#0-5) , the call succeeds and the WETH is transferred to the attacker, with no relation to any order, token, or user that originally caused the balance to accrue.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
