### Title
Webhook `shop` field is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, but `to_signable_string` (used by `Utils::HmacValidator.validate`) only signs the raw request body. `Registry.process` trusts the HMAC as proof of authenticity for the whole request, then hands `request.shop` straight to the app's `WebhookHandler` as an authenticated tenant identifier.

### Finding Description
The binding that should hold is: `hmac_signed_bytes == bytes_the_app_trusts_for_tenant_identity`. In this gem that equality is broken:

- `Request#hmac` decodes the `hmac-sha256` header [1](#0-0) .
- `Request#to_signable_string` returns only `@raw_body` [2](#0-1) .
- `Request#shop` is read straight from the `shop-domain` header, entirely outside the signed content [3](#0-2) .
- `Registry.process` checks only `Utils::HmacValidator.validate(request)` (which validates `raw_body` against the secret) and then forwards `request.shop` as the tenant identity to the handler via `WebhookMetadata` [4](#0-3) .
- `WebhookMetadata.shop` is a plain `String` field consumed by the app's `WebhookHandler#handle` implementation with no additional verification performed by this gem [5](#0-4) .

Because a single app-wide `client_secret` is used to compute the HMAC for webhooks sent to every shop that has the app installed (this is documented/tested behaviour — the HMAC is computed only from body+secret, e.g. in `test/utils/hmac_validator_test.rb`), any merchant who installs the app can legitimately receive a validly-HMAC'd webhook for their own shop. Since the header carrying `shop-domain` is not part of the signed bytes, that attacker-controlled shop can replay the exact same body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `Utils::HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid), and `Registry.process` passes the attacker-chosen `shop` value on to the handler as if it were verified.

### Impact Explanation
This breaks the tenant/shop identity binding this gem is responsible for enforcing before forwarding "authenticated" webhook data to application code. An app that keys its per-tenant records or triggers per-tenant side effects (e.g. deleting/updating data, granting entitlements, provisioning resources) using `WebhookMetadata#shop` — which is exactly how this field is designed to be consumed — can be made to apply attacker-supplied webhook payloads to a victim shop's data. This is a cross-tenant access issue: an unprivileged actor (their own installed instance of the app) can spoof webhook data attributed to another merchant's shop, without leaking or needing the app's `client_secret`.

### Likelihood Explanation
Reachable by anyone who can install (or is already a merchant using) the target app, with no special access: they need only their own genuine webhook (or any legitimately HMAC-signed payload their shop can trigger) and control over the HTTP headers of the replayed request, which any unprivileged internet client can set. The gem provides no mitigation (no shop-binding in the signed content, no cross-check between the header shop and any signed claim) — likelihood is high given that this is precisely how `Registry.process`/`WebhookMetadata` are meant to be used.

### Recommendation
- Short term: Document, and better, enforce that `shop-domain` must be independently verified against the session/shop that is expected to be receiving the webhook (e.g. only accept webhooks for previously-registered shops with an active session) rather than trusting the header outright.
- Long term: Extend `Request#to_signable_string` (or add a companion check) so that `shop-domain`/`webhook_id` values are cryptographically bound into the verified payload, or have `Registry.process` cross-validate the header-derived `shop` against another trusted, HMAC-covered source before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own dev/test shop (`attacker.myshopify.com`), which is a normal, unprivileged action.
2. Attacker triggers a webhook event on their own shop (e.g. `orders/create`) and captures the raw POST body plus the genuine `X-Shopify-Hmac-Sha256` header sent by Shopify — this HMAC is valid because it's computed from `body + client_secret`, and the client_secret is the same for every shop using this app.
3. Attacker resends this exact body and HMAC header to the app's webhook endpoint, but replaces the `X-Shopify-Shop-Domain` header with `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` (`lib/shopify_api/utils/hmac_validator.rb`) returns `true` because the body/HMAC pair is genuine.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` and calls the app's handler, which processes attacker-controlled data believing it belongs to `victim-shop.myshopify.com`.
