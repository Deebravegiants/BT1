### Title
Webhook HMAC signs only the raw body and never binds `X-Shopify-Topic`/`X-Shopify-Shop-Domain`, enabling cross-topic and cross-tenant handler confusion - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely via `Utils::HmacValidator.validate(request)`, which validates the HMAC over `request.to_signable_string` — defined as just the raw body — and never incorporates the `topic` or `shop` headers into the signed material. Because the dispatch (`@registry[request.topic]`) and the shop attribution (`request.shop`) are taken straight from unauthenticated headers, an attacker who has ever received one genuinely signed webhook body (e.g., from their own dev-shop installation) can resend that exact body with a different `X-Shopify-Topic` (and/or `X-Shopify-Shop-Domain`) header and have it pass HMAC validation, routed to a different handler than the one that produced it.

### Finding Description
The claimed binding is: `topic_the_hmac_authenticates == topic_the_handler_believes_it_received`. Tracing the code shows this binding never holds:

- `Registry.process` calls `Utils::HmacValidator.validate(request)`, and on success looks up the handler purely by header: `handler = @registry[request.topic]&.handler`, then constructs `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`. [1](#0-0) 
- `Request#to_signable_string` returns `@raw_body` only — no topic, no shop, no webhook id are part of the signed string. [2](#0-1) 
- `HmacValidator.validate`/`validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the received HMAC — again, only the body is covered. [3](#0-2) 
- `Request#topic` and `Request#shop` are read directly from attacker-controlled headers with no cross-check against the signed content. [4](#0-3) 

Because the signature is a pure function of the body and the shared `api_secret_key`, and the same `api_secret_key` is used for HMACs across all shops and topics for a given app, any body+HMAC pair that was ever valid for topic A (e.g., a webhook the attacker legitimately received on their own installed dev shop) remains a valid `(body, hmac)` pair regardless of which `X-Shopify-Topic` or `X-Shopify-Shop-Domain` header is attached when it's replayed to the app's webhook endpoint. `Registry.process` will accept it, dispatch it to topic B's handler, and pass through an attacker-chosen `shop` value in `WebhookMetadata`, with no code path re-deriving or verifying topic/shop from the signed payload.

No existing guard closes this gap: `HmacValidator.validate` only checks body authenticity, not header authenticity; there is no `ShopValidator.sanitize!` call in this flow; `Registry.process` performs no comparison between the topic that was originally signed for and the topic in the current request (there is no such record to compare against, since topic was never signed).

### Impact Explanation
An attacker can cause an arbitrary registered `:http` webhook handler (topic B) to process a JSON body that was never produced for that topic, while also spoofing the `shop` field seen by that handler (since `shop` is likewise excluded from the signature). This is a cross-handler / cross-tenant confusion: handler B may act on attacker-influenced data structure and an attacker-chosen `shop` value, believing it authentically originated from Shopify for that topic/shop pair. Depending on what handler B does (e.g., writes to a database keyed by `shop`, triggers side effects, or performs authorization based on shape of the body), this can corrupt state for shops other than the attacker's own tenant. This matches the "cross-tenant access" Critical impact category. The attack is repeatable indefinitely and against any shop domain string, since `shop` is just a header value with no ownership check.

### Likelihood Explanation
Preconditions are low-cost for an unprivileged attacker: they only need to install the target app on their own development shop (something explicitly permitted by the threat model) and receive at least one legitimately signed webhook body for any topic. They then replay that exact `raw_body` with a forged `X-Shopify-Topic` (naming any topic B the app has registered — discoverable from docs/app behavior) and an arbitrary `X-Shopify-Shop-Domain`, sent directly to the app's public webhook endpoint. No secret material is required; the HMAC remains valid because it was never bound to those headers. The only variable factor is whether handler B's parsing of topic-A-shaped JSON causes meaningful impact, which is app-specific but plausible when handlers assume the type-safety implied by topic-based dispatch.

### Recommendation
Bind topic (and ideally shop) into the authenticated context rather than trusting headers post-hoc:
- Most directly, this mirrors Shopify's actual webhook verification design (HMAC only covers the raw body), so this is best mitigated at the app layer by having handlers strictly validate the exact expected schema/shape of `body` for their topic and reject unexpected shapes, and by not trusting `WebhookMetadata#shop` for authorization decisions without corroborating it against a known session/shop registration.
- Within the gem, consider documenting explicitly that `topic` and `shop` in `WebhookMetadata` are unauthenticated header values only protected implicitly by TLS/Shopify's honesty, not by the HMAC, so downstream handler authors do not assume topic/shop integrity.

```ruby
# test/webhooks/registry_topic_confusion_test.rb
require_relative "../test_helper"

module ShopifyAPITest
  module Webhooks
    class RegistryTopicConfusionTest < Test::Unit::TestCase
      def setup
        super
        ShopifyAPI::Webhooks::Registry.clear
        @body = '{"id":123,"note":"hello"}'
        @hmac = Base64.encode64(
          OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, @body)
        )
      end

      def test_topic_confusion_replay
        a_called = false
        b_called = false

        handler_a = TestHelpers::FakeWebhookHandler.new(->(data) { a_called = true })
        handler_b = TestHelpers::FakeWebhookHandler.new(->(data) {
          b_called = true
          # handler B expected a different shape, e.g. { "customer_id" => ... }
          assert_nil(data.body["customer_id"])
        })

        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "topic/a", path: "path_a", delivery_method: :http, handler: handler_a,
        )
        ShopifyAPI::Webhooks::Registry.add_registration(
          topic: "topic/b", path: "path_b", delivery_method: :http, handler: handler_b,
        )

        # Attacker legitimately received this signed body for topic/a on their own shop.
        headers_for_a = {
          "x-shopify-topic" => "topic/a",
          "x-shopify-hmac-sha256" => @hmac,
          "x-shopify-shop-domain" => "attacker-shop.myshopify.com",
        }
        ShopifyAPI::Webhooks::Registry.process(
          ShopifyAPI::Webhooks::Request.new(raw_body: @body, headers: headers_for_a)
        )
        assert(a_called)
        refute(b_called)

        # Attacker replays the SAME body+hmac with topic swapped to B and a spoofed victim shop.
        headers_for_b = {
          "x-shopify-topic" => "topic/b",
          "x-shopify-hmac-sha256" => @hmac,
          "x-shopify-shop-domain" => "victim-shop.myshopify.com",
        }
        ShopifyAPI::Webhooks::Registry.process(
          ShopifyAPI::Webhooks::Request.new(raw_body: @body, headers: headers_for_b)
        )
        assert(b_called) # handler B received a body it never authorized/produced
      end
    end
  end
end
```
This demonstrates that `HmacValidator.validate` returns `true` for both requests (same body/HMAC), while `Registry.process` dispatches to different handlers based purely on the unauthenticated `x-shopify-topic` header, and passes an attacker-chosen `shop` value through unchecked.           end

```ruby
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
```
