### Title
`describeWithdrawal` matches withdrawal status by `assetId` only, causing tx-hash/status swap between same-asset withdrawals in a batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves per-index withdrawal status via `findMatchingWithdrawal`, which matches only on `nep141:{near_token_id} === assetId` and ignores `destinationAddress` and `amount`. When a batch contains two withdrawals of the same `assetId` in a single NEAR intent, both indices resolve to the *same* (arbitrarily first) matching entry from the unsorted POA API response, so an integrator can be told withdrawal 0 completed with a `txHash` that actually corresponds to withdrawal 1's destination/amount, and vice versa.

### Finding Description
The equality that should hold is: for `describeWithdrawal({index: i, withdrawalParams: withdrawalParams[i], tx})`, the returned `txHash`/`status` must correspond to the on-chain outcome of the withdrawal whose `destinationAddress`/`amount` were signed at index `i`. Instead, the code guarantees only:

```
withdrawal.data.near_token_id === parseTokenFromAssetId(withdrawalParams[i].assetId)
```

`findMatchingWithdrawal` uses `Array.prototype.find`, which returns the *first* array element satisfying the predicate. Since `response.withdrawals` is explicitly documented and code-commented as unsorted ("Response list is unsorted, so we match by assetId instead of index" at line 318), when two withdrawals share the same `assetId`, both `describeWithdrawal(index=0)` and `describeWithdrawal(index=1)` calls will resolve to the exact same first matching array element — whichever the POA indexer happens to order first. There is no secondary matching on `destinationAddress` or `amount` to disambiguate.

The code even contains an explicit acknowledgment of this exact limitation in its own doc comment (lines 409-416), stating multiple withdrawals of the same token are "not supported," but no guard rejects or de-duplicates such batches upstream — `PoaBridge.supports`, `validateWithdrawal`, `createWithdrawalIntents`, and `IntentsSDK.processWithdrawal`/`waitForWithdrawalCompletion` (`sdk.ts`) place no restriction preventing a caller from submitting two `WithdrawalParams` entries with the same `assetId` but different `destinationAddress`/`amount` in one `processWithdrawal` batch call. Each entry is validated independently and turned into an independent intent primitive; nothing checks for duplicate `assetId` across the batch.

Attacker input: a caller (integrator forwarding user-supplied `WithdrawalParams[]`, or the user themselves) submits a batch `processWithdrawal` call with two `nep141:btc.omft.near` withdrawals to two distinct `destinationAddress` values. Both get signed in the same intent and settle in the same NEAR tx. On the POA bridge side, once both withdrawals process, `getWithdrawalStatus` returns both entries in an unspecified order. `describeWithdrawal(index=0)` and `describeWithdrawal(index=1)` both invoke `findMatchingWithdrawal` with the same `assetId`, both receiving `withdrawals.find(...)` — the identical first match — for both indices.

Existing guards do not prevent this: `validateAddress`/`compareAddresses` only check address format/self-transfer, not batch consistency; `supports()` ordering only picks the bridge, not the array entry; `FeeExceedsAmountError`/`getUnderlyingFee` deal with fee math, not identification; the intents contract's nonce/signature checks validate that the whole batch of intents was authorized as signed, but do not tie individual withdrawal report indices to individual `transfer_tx_hash` values — that binding exists only in this SDK's off-chain status-matching logic, which is broken.

### Impact Explanation
The integrator using `waitForWithdrawalCompletion`/`processWithdrawal` for a batch will receive a `destinationTx[0]` (and `[1]`) whose reported `txHash`/`status` can be swapped relative to the actual chain outcome for that index's signed `destinationAddress`/`amount`. This is a status/hash misreport: the integrator may credit destination-address-0's user based on a txHash that in fact paid destination-address-1, and vice versa — potentially causing wrongful credit or a stuck/duplicated reconciliation with no on-chain fix (funds correctly went to the addresses that were signed, but the report is wrong about which report maps to which). This matches the "High" category (status/hash misreport causing an integrator to credit incorrectly) as described in the audit's severity scale, since it is a report of the wrong txHash for a given index rather than funds routed to an unauthorized address.

### Likelihood Explanation
Preconditions are fully attacker-controlled and cheap: a batch withdrawal with two entries sharing the same `assetId` (same NEP-141 token) but different `destinationAddress`/`amount`, which the SDK does not reject anywhere in `createWithdrawalIntents`, `validateWithdrawal`, or `processWithdrawal`. It requires the POA API to return the two withdrawal entries, and the ordering to not coincide with the batch's index/address ordering — plausible since it's explicitly documented as unsorted. This is repeatable on every batch containing duplicate-asset withdrawals, not a one-off race.

### Recommendation
In `findMatchingWithdrawal` (or its caller `describeWithdrawal`), disambiguate matches by more than `assetId`: also compare `data.address` against `withdrawalParams.destinationAddress` (via `compareAddresses`) and, if still ambiguous, `data.amount` against the signed amount for that index. If ambiguity remains unresolved (e.g., two entries share asset, address, and amount), the SDK should refuse to report status for duplicate entries rather than silently picking the first array match, and should surface an explicit `AmbiguousWithdrawalMatchError` rather than mapping to a possibly-wrong record.

```ts
import { PoaBridge } from "../../poa-bridge";
import { poaBridge } from "@defuse-protocol/internal-utils";

test("describeWithdrawal misattributes txHash for duplicate-assetId batch", async () => {
  const bridge = new PoaBridge({ envConfig, xrplRpcUrls: [] });

  const withdrawal0 = { destinationAddress: "addrA", amount: 100n, assetId: "nep141:btc.omft.near" };
  const withdrawal1 = { destinationAddress: "addrB", amount: 200n, assetId: "nep141:btc.omft.near" };

  vi.spyOn(poaBridge.httpClient, "getWithdrawalStatus").mockResolvedValue({
    withdrawals: [
      { status: "COMPLETED", data: { near_token_id: "btc.omft.near", address: "addrB", amount: "200", transfer_tx_hash: "0xHASH_FOR_B" } },
      { status: "COMPLETED", data: { near_token_id: "btc.omft.near", address: "addrA", amount: "100", transfer_tx_hash: "0xHASH_FOR_A" } },
    ],
  });

  const result0 = await bridge.describeWithdrawal({
    index: 0, withdrawalParams: withdrawal0, tx: { hash: "near-tx" }, landingChain: "btc:mainnet",
  });
  const result1 = await bridge.describeWithdrawal({
    index: 1, withdrawalParams: withdrawal1, tx: { hash: "near-tx" }, landingChain: "btc:mainnet",
  });

  // Broken equality being tested:
  // Expected: result0.txHash === the entry whose data.address === "addrA" ("0xHASH_FOR_A")
  // Actual:   result0.txHash === first array match ("0xHASH_FOR_B")
  expect(result0.txHash).toBe("0xHASH_FOR_B"); // demonstrates misattribution (should be 0xHASH_FOR_A)
  expect(result1.txHash).toBe("0xHASH_FOR_B"); // both indices resolve to the same first match
});
```

```typescript
/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
