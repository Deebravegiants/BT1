### Title
Unchecked subtraction in `calc_take_pnl` panics on attacker-inflatable vault balances, permanently freezing pool funds - (File: `program/src/processor.rs`)

### Summary
`Processor::calc_take_pnl` computes the pool's "post pnl-take" invariant point (`x2`, `y2`) from the stored reference invariant `target_orders.calc_pnl_x/calc_pnl_y` and the pool's *current* token balances, then subtracts `x2` from `x1` and `y2` from `y1` using `.unwrap()` on `checked_sub` instead of returning a graceful error [1](#0-0) . Because `x1`/`y1` are derived directly from the live SPL token balances of the AMM's coin/pc vaults [2](#0-1) , and any unprivileged party can permanently and irreversibly change those balances with a plain SPL Token transfer directly to the public vault addresses (no AMM-side authorization is required to *receive* tokens), an attacker can skew the ratio between the live balances and the stale `target_orders.calc_pnl_x/y` reference enough that the rounded/truncated `integer_sqrt`-derived `x2`/`y2` exceeds `x1`/`y1`. When that happens the `unwrap()` on `checked_sub` panics.

### Finding Description
`calc_take_pnl` is invoked, unconditionally, from every state-mutating, unprivileged, user-reachable instruction that touches pool economics: `process_deposit` [3](#0-2) , `process_withdraw` [4](#0-3) , `process_withdrawpnl` [5](#0-4) , and `process_swap_base_in` / `process_swap_base_out` (via the same helper path used before executing the swap) [6](#0-5) .

Inside `calc_take_pnl`:
- `target.calc_pnl_x`/`calc_pnl_y` are a *stale* reference invariant point, only updated when this same function last succeeded [7](#0-6) .
- `x1`/`y1` are the *live* pool balances (vault SPL token account amounts minus already-accrued pnl), computed in `calc_total_without_take_pnl_no_orderbook` directly from `amm_pc_vault.amount` / `amm_coin_vault.amount` [2](#0-1) .
- `x2` is computed as `integer_sqrt(last_x * last_y * current_x / current_y)` and `y2 = x2 * y1 / x1` [8](#0-7) , both using truncating integer division and integer square root.
- `diff_x = x1.checked_sub(x2).unwrap()` and `diff_y = y1.checked_sub(y2).unwrap()` assume `x2 <= x1` and `y2 <= y1` always hold, with no fallback if the assumption is violated [9](#0-8) .

Any unprivileged actor can send an ordinary `spl_token::instruction::transfer` directly to the AMM's public `coin_vault`/`pc_vault` token accounts (their addresses are public account metadata, stored in `AmmInfo` and used unchanged by all instructions) — this requires no AMM-program authorization at all, since deposits into a token account do not need the receiving account's owner/authority to sign. This directly and *permanently* (on-chain, in a separate, already-finalized transaction) inflates `amm_coin_vault.amount` or `amm_pc_vault.amount`, which feeds `x1`/`y1` in every subsequent call to `calc_take_pnl`, while `target_orders.calc_pnl_x/y` remains fixed at the old reference point. Given the truncating integer-square-root and division used to derive `x2`/`y2`, sufficiently skewed ratios between the live balances and the stale reference can make `x2 > x1` or `y2 > y1`, causing the `unwrap()` to panic.

### Impact Explanation
Because the corrupting balance change is committed on-chain independently of the AMM instruction (a plain token transfer, not reverted by any later panic), every subsequent call into `Deposit`, `Withdraw`, `WithdrawPnl`, `SwapBaseIn`, and `SwapBaseOut` for that pool will re-enter `calc_take_pnl` with the same skewed inputs and panic identically. This permanently disables deposits, withdrawals, and swaps for the affected pool — a permanent freezing of all user and LP funds in that pool, satisfying the "concrete... permanent freezing of user or LP funds" bar. This is a directly reachable, unprivileged, single-instruction (token transfer) attack requiring no signer other than the attacker's own funded token account.

### Likelihood Explanation
Likelihood is High: the primitive needed (transferring tokens directly to a publicly known vault address) requires no special permission, no malicious validator, and no privileged signer — only knowledge of the pool's `coin_vault`/`pc_vault` pubkeys, which are public on-chain data. The only uncertainty is the exact numeric skew ratio required to push `x2`/`y2` past `x1`/`y1` given the specific rounding behavior of `integer_sqrt` and integer division in this codebase; I was not able to fully derive a concrete numeric example within this investigation (this would require executing/fuzzing `Calculator::calc_x_power` and `integer_sqrt` against the live formula), so likelihood should be validated with a fuzz test or unit test targeting `calc_take_pnl`.

### Recommendation
Replace the unchecked `.unwrap()` calls in `calc_take_pnl` (`program/src/processor.rs:213-214` and the surrounding chained `unwrap()`s) with saturating or checked arithmetic that returns `AmmError::CalcPnlError` (or a new dedicated error) when `x2 > x1` or `y2 > y1`, instead of panicking. This mirrors the pattern already used in `calc_total_without_take_pnl_no_orderbook`, which correctly uses `.ok_or(...)` instead of `.unwrap()` [10](#0-9) .

### Proof of Concept
1. Identify a live Raydium AMM pool and read `AmmInfo.coin_vault` / `AmmInfo.pc_vault` (public account keys).
2. As any unprivileged wallet holding the pool's coin (or pc) mint, submit a standard `spl_token::instruction::transfer` sending a large amount of that mint directly into the pool's `coin_vault` (or `pc_vault`) token account — no AMM program interaction, no authority check involved, this succeeds unconditionally.
3. Call any of `SwapBaseIn`, `SwapBaseOut`, `Deposit`, `Withdraw`, or `WithdrawPnl` on the pool. Each of these loads the now-inflated vault balance via `calc_total_without_take_pnl_no_orderbook` [2](#0-1)  and feeds it into `calc_take_pnl` [3](#0-2) .
4. If the skew is large enough that `x2 > x1` or `y2 > y1`, `checked_sub(...).unwrap()` at `program/src/processor.rs:213-214` returns `None`, and the BPF program panics, aborting the transaction.
5. Because step 2's balance change is already committed on-chain (it is a separate, successful transaction), every subsequent call from any user into the four affected instructions repeats the same panic, permanently freezing the pool.

Note: I could not, within this investigation, derive a concrete numeric skew ratio proving the `x2 > x1` / `y2 > y1` condition is reachable in practice (this depends on the precise rounding behavior of `integer_sqrt` and integer division in `Calculator::calc_x_power`); confirming exploitability would require unit-testing/fuzzing `calc_take_pnl` directly with adversarial vault-balance inputs.

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
