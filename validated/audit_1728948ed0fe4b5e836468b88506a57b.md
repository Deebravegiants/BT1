### Title
Webhook shop-domain spoofing due to HMAC not covering the `shop` field - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string exclusively from the raw HTTP body, while the `shop` (and `topic`/`webhook_id`) values are read directly from unauthenticated HTTP headers. `Registry.process` validates only that HMAC, then immediately forwards the header-derived `shop` to the app's handler, so the identity used by the app (`shop`) is never bound to the value that was actually signed (`raw_body`).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then hands the header-derived `shop` straight to the registered handler without any additional check that the `shop` header is consistent with the signed content or with an installed/known shop: [3](#0-2) 

`Utils::HmacValidator.validate` also only compares `verifiable_query.hmac` against a signature computed from `to_signable_string`, i.e. body-only for webhooks: [4](#0-3) 

Because Shopify signs webhook bodies for *every* shop that installs a given app using the same shared `api_secret_key` (the app's client secret), a `(raw_body, hmac)` pair that is valid for one merchant's shop is also a valid HMAC pair in isolation — the HMAC computation never incorporates which shop it came from. This breaks the intended identity binding: `shop header used by the app == shop that produced the signed body`. An attacker who controls one installed shop (an unprivileged merchant, not a privileged actor) can capture a genuine `(body, hmac)` pair delivered to their own shop, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` reports the event as originating from the victim shop.

### Impact Explanation
Any webhook handler that trusts `WebhookMetadata#shop` (e.g., to look up a per-shop session/access token, or to write/update per-tenant data keyed by shop) can be tricked into operating on the wrong tenant's context using attacker-supplied body content, resulting in cross-tenant data confusion/access — this matches the Critical "cross-tenant access" impact category, since the boundary crossed is the per-merchant tenant isolation that Shopify webhooks are supposed to guarantee.

### Likelihood Explanation
Any merchant who installs the app receives real webhooks with valid `(body, hmac)` pairs signed with the app's single shared secret. No privileged credentials, TLS interception, or leaked secrets are required — only the ability to install the app as an ordinary merchant and to send an HTTP request to the app's public webhook endpoint with a modified `shop` header, which is entirely within reach of an unprivileged internet user.

### Recommendation
Bind the shop identity into the HMAC verification path instead of trusting an unauthenticated header:
- Include the shop domain (and/or webhook id/topic) in the signable string, or
- After HMAC validation, cross-check the header `shop` against the shop associated with the specific webhook subscription/session the app expects for that HMAC-verified body, rejecting requests where they don't match.

### Proof of Concept
1. App developer's app is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both signed with the same `api_secret_key`.
2. Shopify sends a genuine webhook to the attacker's endpoint for `attacker-shop.myshopify.com`:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body B>`
   - Body: `B`
3. Attacker replays the exact same `body: B` and `x-shopify-hmac-sha256` value to the app's webhook endpoint but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` returns the same value; `Utils::HmacValidator.validate` recomputes HMAC over `B` (via `to_signable_string`, `lib/shopify_api/webhooks/request.rb:35-38`) and succeeds because the header isn't part of the signed content.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the handler with `shop: "victim-shop.myshopify.com"` and body `B`, even though `B` never originated from `victim-shop`.
