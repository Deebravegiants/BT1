## Title
Cancelled hardware-wallet signing requests can still resolve with a valid signature due to missing state-check on the success path — race condition analogous to the Dinari escrow-not-cleared bug (File: `features/hardware-wallets/src/module/hardware-wallets.ts`)

### Summary
`HardwareWallets` tracks an in-flight signing operation in the private field `#signingRequest`, and lets the UI call `cancelSigningRequest(id, fromUI)` to abort it [1](#0-0) . The completion path in `retrySigningRequest` awaits the actual device signing call and then unconditionally settles the caller's promise, without re-checking that the request wasn't cancelled while the device call was in flight [2](#0-1) . This mirrors the Dinari `DirectBuyIssuer` bug class: an asynchronous, unstoppable "operator" action (`takeEscrow` / here, the physical hardware signing) races against a cancellation that clears bookkeeping state (`getOrderEscrow` / here, `#signingRequest`) but does not prevent the in-flight action's result from being applied.

### Finding Description
`#signGeneric` creates a `SigningRequest` with `resolve`/`reject` bound to a single `pDefer()` promise and fires `retrySigningRequest(id)` without waiting for it [3](#0-2) .

`retrySigningRequest` performs:
```
const result = await request.sign({ device })
await this.#deleteSigningRequest(id)
request.resolve(result)
``` [4](#0-3) 
Notice that only the **error/catch** branch re-validates that `this.#signingRequest?.id === id` before proceeding [5](#0-4) ; the **success** branch has no such guard.

Meanwhile, `cancelSigningRequest` can run concurrently (e.g., triggered from the UI while the device prompt is still open):
```
await this.#deleteSigningRequest(id)
if (fromUI) {
  ... device.cancelAction() ...
}
request.reject(new UserRefusedError(!fromUI))
``` [1](#0-0) 

Because `#signingRequest` is cleared as soon as cancellation starts — before `device.cancelAction()` even resolves — the in-flight `await request.sign({ device })` call in `retrySigningRequest` (physically signing on the hardware device) is not aborted and is not re-checked against the current `#signingRequest` state before its result is committed. If the underlying device call finishes and calls `request.resolve(result)` before `cancelSigningRequest`'s `request.reject(...)` executes, the caller's promise settles with the signed transaction/message rather than a `UserRefusedError`, even though the UI already recorded/attempted a cancellation and cleared the signing-request atom (`hardwareWalletSigningRequestsAtom`) [6](#0-5) .

This is the direct analog of the escrow bug: `cancelOrder` in Dinari clears order state but not the outstanding escrow accounting, letting a stale `takeEscrow` transaction land and pull funds; here `cancelSigningRequest` clears `#signingRequest`/atom state but the outstanding, physically-irreversible device signing call is not gated, letting a "cancelled" signature still be produced and handed back to the caller.

### Impact Explanation
If this race resolves in favor of the in-flight sign, the wallet returns a valid signature for a transaction or message the user believed they cancelled. Depending on the caller (e.g., a dApp-initiated `signTransaction`/`signMessage` flow via `tx-signer`/`message-signer`), that signature could be broadcast or otherwise used, resulting in unauthorized signing/spending action taken against user intent — a direct wallet-compromise-adjacent impact (unauthorized transaction signing), not merely a UI inconsistency.

### Likelihood Explanation
This requires a timing race between the user cancelling (from UI) and the underlying hardware device call resolving — realistic when a user presses "Cancel" in the app around the same time they (or an already-queued button press on the physical device) approve the action on the device, or when `device.cancelAction()` fails to interrupt an in-progress USB/BLE exchange (the code already anticipates and swallows such failures at [7](#0-6) ). This is a plausible, non-malicious-operator scenario (ordinary user interacting with UI and physical device), fitting the required unprivileged-user threat model.

### Recommendation
Before calling `request.resolve(result)` in `retrySigningRequest`'s success path, re-check that the request has not been cancelled/superseded (i.e., `this.#signingRequest?.id === id`), mirroring the guard already present in the catch branch [8](#0-7) . If the request was cancelled, discard the result (and ideally surface/log that a signature was produced after cancellation) instead of resolving the caller's promise.

### Proof of Concept
1. Call `hardwareWallets.signTransaction(...)`, which starts `#signGeneric` → `retrySigningRequest(id)`, which begins `await request.sign({ device })` (device prompt shown to user).
2. Concurrently invoke `hardwareWallets.cancelSigningRequest(id, true)` from the UI; this clears `#signingRequest` and calls `device.cancelAction()`, then calls `request.reject(...)`.
3. If the underlying device signing operation (already committed to hardware, e.g., in `hw-ledger`/`hw-trezor` `signTransaction`) completes and returns a signature before step 2's `reject` fires — e.g., because `cancelAction()` fails to interrupt an already-approved device flow, per the comment on `HardwareWalletDevice.cancelAction` behavior [9](#0-8)  — then `retrySigningRequest` reaches line 238 and calls `request.resolve(result)`, which wins the race and returns the signed transaction to the original caller of `signTransaction`, despite the user having cancelled.

  cancelSigningRequest = async (id: string, fromUI: boolean) => {
    const request = this.#signingRequest
    this.#logger.debug(`Cancelling signing request for id: ${id}, fromUI: ${fromUI}`)
    if (request?.id !== id) {
      this.#logger.warn(`No signing request found for id: ${id}`)
      return
    }

    await this.#deleteSigningRequest(id)

    // Ensure we cancel the action on the device
    if (fromUI) {
      this.#logger.debug(`Cancelling signing request on device for id: ${id}`)
      try {
        const { device } = await this.#getSelectedDevice(request.walletAccount)
        await device.cancelAction()
        this.#logger.debug(`Succesfully cancelled signing request on device for id: ${id}`)
      } catch (error: any) {
        this.#logger.error(`Failed to cancel signing request on device for id: ${id}`, error)
      }
    }

    // Now reject the promise returned to the asset caller
    request.reject(new UserRefusedError(!fromUI))
  }
```

  #signGeneric = restrictConcurrency(
    async ({ baseAssetName, scenario, sign, walletAccount }: GenericSignParams) => {
      const id = randomBytes(16).toString('hex')
      this.#logger.debug(
        `Starting signing request for ${baseAssetName} with scenario: ${scenario} and id: ${id}`
      )
      const deferred = pDefer()

      // Track the signing request in the internal map
      // so the UI can retry & cancel if needed.
      this.#signingRequest = {
        id,
        baseAssetName,
        walletAccount,
        sign: async ({ device }) => {
          // Kick off the signing request to the UI
          await this.#updateSigningRequest({
            id,
            baseAssetName,
            scenario,
          })

          await device.ensureDeviceReady({ baseAssetName, walletAccount })
          return sign({ device })
        },
        resolve: deferred.resolve,
        reject: deferred.reject,
      }

      // We don't await for the signing request to complete here,
      // as the UI will handle it asynchronously.
      void this.retrySigningRequest(id)

      return deferred.promise
    }
  )
