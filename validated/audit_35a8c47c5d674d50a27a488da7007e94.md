## Analysis

The reported bug class — an unprotected swap executed as a side-effect of an ordinary user action, exploitable via sandwich attack because slippage/output isn't properly bounded relative to the caller's true cost — has a direct analog in `EvmHost.sol`'s native-token fee payment path, reachable by any unprivileged caller dispatching a message.

### Title
Unbounded, Deadline-less Uniswap Swap in `EvmHost.dispatch()`/`fundRequest()` Enables Sandwich Extraction and Permanent Loss of Excess Native Payment - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all convert user-supplied native token into `feeToken()` via `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. Any unprivileged caller triggers this swap directly with `msg.value`, using `block.timestamp` as the deadline (no real time-bound) and the entire `msg.value` as the implicit `amountInMax`, with no refund of unconsumed native token back to the caller.

### Finding Description [1](#0-0) 
In `dispatch(DispatchPost memory post)`, when `msg.value > 0`, the Host calls `swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp)` and never inspects or acts on the returned `amounts` array. The same pattern repeats in `dispatch(DispatchGet)` [2](#0-1)  and `fundRequest()` [3](#0-2) .

Two compounding issues exist here, mirroring the report's "swap during an unrelated operation with no minimum-out/slippage guard":

1. **`deadline = block.timestamp` provides no protection.** Because the deadline is evaluated at execution time rather than being a caller-chosen future bound, it always passes trivially — a block producer/searcher can hold, reorder, or sandwich the transaction with no risk of the swap reverting due to deadline. This is the same "swap embedded in an ordinary call flow with no real slippage bound" pattern the report describes for `_transfer()`.
2. **No refund of unconsumed native token.** `swapETHForExactTokens` refunds any leftover ETH to `msg.sender` of the router call — which is `EvmHost` itself, not the original transaction sender. Unlike `IntentGatewayV2.placeOrder()`, which explicitly refunds unspent native tokens back to the user after the identical `swapETHForExactTokens` call (`msgValue -= amounts[0]; ... _sendValue(msg.sender, msgValue);`) [4](#0-3) , `EvmHost.dispatch()`/`fundRequest()` contain no such logic. Any native token sent beyond what the swap actually consumes is silently retained by `EvmHost` with no accounting or recovery path for the user.

Combined, a sandwich attacker can front-run a `dispatch()`/`fundRequest()` call to inflate the pool price of `feeToken()`, forcing the exact-output swap to consume more of the user's `msg.value` than the fair-market amount to obtain the same fixed `post.fee`/`amount` of `feeToken()`. The attacker captures that price-impact spread as MEV profit (classic sandwich extraction), while any ETH the user intentionally over-provisioned as a safety margin against normal price movement is not attacker-extracted but is unrecoverably retained by the `EvmHost` contract due to the missing refund path — a permanent loss of user funds triggered on every native-token dispatch.

### Impact Explanation
Every unprivileged user or contract dispatching a POST/GET request or funding a request with native token is exposed. The victim either (a) loses value directly to a sandwiching MEV actor who manipulates the `feeToken()`/WETH pool price around the swap, or (b) permanently loses any native token sent in excess of the exact amount consumed by the swap, since `EvmHost` has no refund mechanism, unlike the sibling `IntentGatewayV2` contract which explicitly guards against this. This is a protocol-wide, unprivileged, reachable path (any `dispatch`/`fundRequest` call), matching the "permanent freezing/loss of funds" acceptance criteria.

### Likelihood Explanation
High. `dispatch()` and `fundRequest()` are core, permissionless, frequently-called entry points for every application built on `HyperApp`/`IDispatcher` paying with native token (per the documented "Native Token Payment" flow) [5](#0-4) . Because the docs themselves warn that off-chain `quote()`/`getAmountsIn()` estimates are imprecise and subject to slippage, users are naturally incentivized to send a safety margin of native token — precisely the margin that is destroyed or trapped by this flow.

### Recommendation
- Use a genuine future deadline supplied by the caller instead of `block.timestamp`.
- Capture the `amounts` array returned by `swapETHForExactTokens` and refund any unconsumed `msg.value` back to `_msgSender()`, exactly as already implemented in `IntentGatewayV2.placeOrder()`.
- Consider allowing the caller to supply an explicit `amountInMax` (rather than implicitly using the entire `msg.value`) so users can bound their exposure to sandwich-driven price impact.

### Proof of Concept
1. Attacker monitors mempool for a `dispatch()`/`fundRequest()` call paying with native token.
2. Attacker front-runs with a buy of `feeToken()` against the same Uniswap V2 pool, inflating its price relative to WETH.
3. Victim's transaction executes `swapETHForExactTokens(fee, [WETH, feeToken], address(this), block.timestamp)`; because `post.fee`/`amount` is fixed, the router now consumes more ETH from `msg.value` to obtain the same token amount, at the attacker-inflated price.
4. Attacker back-runs, selling `feeToken()` back for profit — the sandwich profit is extracted directly from the value the victim's swap consumed.
5. Separately (or additionally), any ETH the victim included beyond the swap's actual consumption is refunded by the router to `EvmHost`, not the victim, and there is no code path in `dispatch()`/`fundRequest()` to return it — it is permanently retained by the contract.

### Native Token Payment

For native token payments, dispatch directly and let the Host handle the Uniswap swap:

```solidity lineNumbers title="MyApp.sol"
contract MyApp is HyperApp {
    function sendMessageWithNative(
        bytes memory message,
        bytes memory dest,
        uint64 timeout,
        address to,
        uint256 relayerFee
    ) public payable returns (bytes32) {
        DispatchPost memory post = DispatchPost({
            body: message,
            dest: dest,
            timeout: timeout,
            to: abi.encode(to),
            fee: relayerFee,
            payer: msg.sender
        });
        
        // User must send enough native tokens to cover fees
        // The Host will swap native -> feeToken via Uniswap
        return IDispatcher(host()).dispatch{value: msg.value}(post);
    }
```
