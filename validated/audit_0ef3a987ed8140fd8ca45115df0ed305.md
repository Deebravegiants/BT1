### Title
Reentrant escrow drain via external call before balance decrement in `withdraw()` - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` on the Tron contracts variant violates checks-effects-interactions: it sends escrowed tokens/ETH to the beneficiary via a low-level `.call` *before* decrementing the corresponding `_orders[commitment][token]` balance. This is the same bug class as the referenced Circles `_groupMint` finding — state that should gate repeated payout is only updated *after* an external call that can trigger attacker-controlled code, allowing the escrow to be drained more than once for the same commitment.

### Finding Description
`withdraw()` is the internal function that releases escrowed order funds for both the `RedeemEscrow`/`RefundEscrow` paths (`onAccept`) and the cancel-from-source path (`onGetResponse`): [1](#0-0) 

For each token in the withdrawal request:
1. It checks `_orders[body.commitment][token] == 0` (existence check only, not decremented yet).
2. It performs the payout: `beneficiary.call{value: amount}("")` for native tokens, or a low-level `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` for ERC20s.
3. Only **after** that external call does it execute `_orders[body.commitment][token] -= amount;`.

`_filled[body.commitment] = beneficiary;` is set at the very top of `withdraw()`, which blocks a *direct* re-fill of the same order via `fillOrder`/`cancelOrder` (both check `_filled[commitment] != address(0)` and revert `Filled()`). However, that guard does not protect the per-token `_orders[...]` balance itself. Reachability:
- `onAccept()` dispatches straight into `withdraw()` for `RedeemEscrow`/`RefundEscrow` requests with **no `_filled` pre-check** at all before calling `withdraw`: [2](#0-1) 
- `onGetResponse()` (cancel-from-source path) only checks the storage-proof value length, not `_filled`, before calling `withdraw`: [3](#0-2) 

Because the beneficiary receives control (via `receive()`/fallback for native ETH, or via a malicious/callback-capable "ERC20" `transfer` implementation) *before* `_orders[commitment][token]` is decremented, a beneficiary that can trigger a second, independently-valid delivery for the same `commitment` (e.g. a distinct Hyperbridge-relayed message reaching `onAccept`/`onGetResponse` again — the host's own replay protection is keyed on the request/response hash, not on the order commitment) can cause `withdraw()` to run again while the balance check `_orders[commitment][token] == 0` still evaluates false (not yet decremented), releasing the same escrowed funds a second time.

This directly parallels the Circles `_groupMint` root cause: an external call (`safeBatchTransferFrom`/`.call`) precedes the state mutation that is supposed to make the operation single-use (`_mintAndUpdateTotalSupply` / `_orders[...] -= amount`), so reentrancy can multiply payouts from a single escrowed deposit.

### Impact Explanation
This is a fund-drain vulnerability in the escrow release path of the intents bridge on Tron: a malicious beneficiary/token can cause the gateway to pay out escrowed collateral more than once for the same order commitment, directly stealing funds from the gateway's escrow (theft of funds / unbacked release of escrow), which is explicitly in scope ("concrete theft ... of funds").

### Likelihood Explanation
Exploitability requires the attacker to control the `beneficiary` address (trivial — beneficiaries are attacker-supplied order fields) and to arrange for a second delivery targeting the same commitment to be triggerable mid-callback (e.g., racing the `RedeemEscrow` and `RefundEscrow`/cancel paths, or via `onGetResponse`, both of which lack a `_filled` check prior to invoking `withdraw`). This requires no privileged role — any user placing/cancelling/filling an order can attempt it, making it reachable from a single relayed message plus a crafted beneficiary contract.

### Recommendation
Apply checks-effects-interactions in `withdraw()`: decrement `_orders[body.commitment][token]` (and delete the tx-fee entry) **before** performing the external `.call`/`safeTransfer`, mirroring the fix already applied to `IntrinsicIntents._fillSameChain`/`_fillCrossChain` in the mainline EVM contracts (setting the guarding state before any external call). Additionally, add an explicit `_filled`/processed check at the top of `withdraw()` itself (not only in the calling functions) so any second invocation for the same commitment reverts regardless of entry point (`onAccept` vs `onGetResponse`), and prefer `SafeERC20.safeTransfer` (already imported via `using SafeERC20 for IERC20;`) instead of raw low-level `.call` with a manually decoded return value.

### Proof of Concept
Conceptual PoC (mirrors the Circles reentrancy PoC structure):
1. Attacker places a cross-chain order with `output.beneficiary` set to a malicious contract that, on receiving native ETH via `receive()`, triggers delivery of a second Hyperbridge message for the same order commitment (e.g., by structuring the order so both a `RedeemEscrow` fill-completion message and a `RefundEscrow` cancellation message become independently deliverable/relayable for the same commitment, or via a malicious "ERC20" `_orders`-escrowed token whose `transfer()` implementation calls back into the relayer/host to deliver a second pending message).
2. First delivery invokes `onAccept` → `withdraw(body, false)`. During the native-token `.call{value: amount}("")` to the malicious beneficiary (line 703), the beneficiary's fallback triggers the second delivery.
3. Second delivery again reaches `withdraw()` for the same `commitment`; `_orders[commitment][token]` has not yet been decremented (decrement occurs at line 710, after the call), so the `== 0` guard at line 700 still passes, and the beneficiary is paid out a second time before either decrement executes.
4. Net effect: escrow for one deposited order is paid out twice, draining the gateway of the duplicated amount.

Full exploit construction (crafting the two independently-valid relayable messages for the same commitment) would need to be built and executed against a forked/local Hyperbridge test harness to confirm exact message sequencing; this is recommended as a follow-up Foundry test analogous to `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol`, but targeted at `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
