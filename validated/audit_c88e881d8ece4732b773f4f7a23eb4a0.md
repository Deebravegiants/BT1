## Title
Webhook `shop` identity not covered by HMAC signature enables cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable material from the raw body only, while the `shop` (tenant) identity is read from a separate, unsigned HTTP header. `Registry.process` validates the HMAC and then hands the *unverified* `shop` value straight to the app's webhook handler. Any party that can obtain one valid `(raw_body, hmac)` pair for the app (e.g., a merchant who has the app installed and receives genuine webhooks) can replay that pair while swapping the `shop-domain` header to a victim shop, causing the app to process an authentic-looking webhook attributed to a shop the attacker does not own.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` verifies the request's `hmac` against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body: [2](#0-1) 

But `shop` (the tenant identifier) is parsed from a completely separate header that is never mixed into the signed material: [3](#0-2) 

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` to build the metadata object the host application's handler acts on, with no cross-check that the signed body actually originated for that shop: [4](#0-3) [5](#0-4) 

The equality the library implicitly (and incorrectly) assumes is:

`shop_the_handler_acts_on (X-Shopify-Shop-Domain header) == shop_that_the_HMAC_actually_authenticates (undefined — HMAC only authenticates body bytes)`

Because the webhook signing key (`Context.api_secret_key`) is the app's single `client_secret`, shared across *every* shop that installs the app, a valid `(body, hmac)` pair is not shop-specific — it only proves "this body was produced by something holding the app's secret" (in practice, Shopify itself, for any tenant). Nothing in `Request` or `Registry.process` ties that pair to the specific `shop-domain` header value that accompanies it.

### Impact Explanation
An attacker who legitimately installs the app on their own shop receives real webhooks (valid `raw_body` + `hmac` for the shared secret). Because the body content for many topics carries no shop-identifying field, the attacker can replay the exact same `raw_body`/`hmac` pair to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` for a victim shop. `HmacValidator.validate` still passes (it only checks the body bytes), and `Registry.process` dispatches the handler with `shop: <victim-shop>`. Any app logic keyed off `WebhookMetadata#shop` (e.g., updating per-shop settings, marking a shop uninstalled/reinstalled, disabling billing, revoking access) is executed against the wrong tenant — a cross-tenant integrity/authorization break, which meets the Critical "cross-tenant access" bar.

### Likelihood Explanation
Requires no secret material beyond what a normal, unprivileged app-installing merchant already legitimately possesses (their own valid webhook deliveries). Replaying an HTTP POST with a modified header to a public webhook endpoint is trivial. The only constraint is finding a webhook topic whose body payload doesn't itself embed a conflicting shop identifier, which is common (e.g., mandatory compliance topics, or minimal-body topics).

### Recommendation
Bind the authenticated shop identity into the material verified by the HMAC (or otherwise cryptographically bind the two), for example by requiring the caller to independently confirm the `shop-domain` header value matches a shop that the app has an active, previously-established session/install record for, and/or documenting/enforcing that `to_signable_string` must not be treated as covering `shop`, `topic`, or other headers so callers don't rely on them for authorization decisions without a secondary tenant check. Concretely: after HMAC validation, cross-verify `request.shop` against known/expected installed shops before invoking handlers, or ask Shopify's webhook contract to include the shop domain within the signed payload.

### Proof of Concept
1. Install the app on `attacker.myshopify.com`; capture a legitimate webhook delivery: header `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <H>`, body `B` (a topic/body with no shop-identifying content, e.g. a compliance/mandatory webhook).
2. Replay a POST to the same webhook endpoint with body `B` unchanged, HMAC header `<H>` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body as usual: `hmac` returns the digest from `<H>`, `to_signable_string` returns `B` — unaffected by the header change (`lib/shopify_api/webhooks/request.rb:11-13,35-38`).
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` with the app's `api_secret_key` and matches `<H>` — validation succeeds (`lib/shopify_api/utils/hmac_validator.rb:12-22`).
5. `Registry.process` builds `WebhookMetadata.new(... shop: request.shop ...)` with `shop == "victim.myshopify.com"` and invokes the app's handler (`lib/shopify_api/webhooks/registry.rb:188-200`), causing the handler to perform shop-scoped actions against `victim.myshopify.com` on the attacker's behalf.
