### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is read from unauthenticated headers, not bound by the HMAC — cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identity for a webhook delivery, but that value is parsed from the `X-Shopify-Shop-Domain` HTTP header rather than from the HMAC-signed payload. The HMAC computed by `Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`), so the shop-domain header — and equally `topic`, `webhook_id`, and `api_version` — can be modified by anyone able to submit a raw body/HMAC pair without invalidating the signature.

### Finding Description
The equality that should hold is: `shop authenticated by HMAC == shop delivered to the handler`. Instead:
- `HmacValidator.validate_signature` computes `HMAC(secret, request.to_signable_string)` and compares it to the `hmac` header [4](#0-3) .
- For webhook requests, `to_signable_string` is defined as just `@raw_body` [3](#0-2) , so the signature is a function of the JSON body alone.
- `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers that are outside the signed bytes [2](#0-1) .
- `Registry.process` validates only the body-based HMAC, then hands `request.shop` straight into `WebhookMetadata` and to the host app's handler as the trusted tenant identifier, with no cross-check that this shop actually owns the delivered body/signature pair [1](#0-0) .

Because the api_secret_key (HMAC key) is the same for every shop that installs a given app, any body+HMAC pair that is valid for one shop's webhook delivery is also a valid HMAC for the exact same body claimed to originate from a different shop — the shop header is never part of what's verified. This mirrors the `pricePerShare` analog: a value used downstream for a security-relevant decision (which tenant's data this webhook affects) is not covered by the check meant to authenticate it (the HMAC / oracle read), so a value the attacker controls (the shop header) is silently trusted.

### Impact Explanation
This breaks the tenant boundary the HMAC exists to enforce. An attacker who can obtain (or reuse) any single valid `raw_body` + `hmac` pair produced by the shared app secret — e.g. by installing the app on a shop they control and capturing a legitimate webhook delivery, or from any topic where the body content is attacker-influenced — can replay that exact body/HMAC to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` (and `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) headers to point at a victim shop. The host application's `WebhookHandler#handle` receives `WebhookMetadata` claiming the victim shop as the source and will act on it (e.g., write, delete, or redact data, or update the app's per-shop state) as if it were an authentic delivery for that victim — this is cross-tenant data manipulation without ever needing the victim's access token or credentials.

### Likelihood Explanation
Reaching this requires only: (1) the ability to install/run the app on an attacker-controlled shop (a normal, unprivileged action for any Shopify merchant/developer), (2) capturing one legitimate webhook body+HMAC from that installation (trivial — point the webhook at an attacker-controlled listener), and (3) replaying it to the app's public webhook receiver endpoint with a forged shop-domain header. No access token, `api_secret_key`, or TLS interception is required, since the gem only checks that the body matches *some* valid HMAC produced with the shared secret, not that the claimed shop is bound to that specific delivery.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the HMAC-signed material, or independently verify the shop header against a value derived from the signed payload (e.g., a `shop_id`/`shop_domain` embedded in the JSON body signed by Shopify) before trusting `request.shop` in `Registry.process`. At minimum, document loudly that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the host app against its own session/shop store before being used for any privileged action, and consider raising if the shop domain does not match an expected/whitelisted value for the topic being processed.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures the webhook delivery URL to an endpoint they control, capturing a real delivery: `raw_body = B`, header `X-Shopify-Hmac-Sha256 = H` (valid HMAC of `B` under the app's shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker POSTs to the victim-facing webhook endpoint of the same app instance with the identical `raw_body = B` and `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body [5](#0-4) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and matches `H` since only `B` is signed [6](#0-5) .
4. Validation succeeds; `handler.handle` is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: JSON.parse(B), ...)` [7](#0-6) , causing the host app to process attacker-supplied data as an authentic event from the victim shop.
