### Title
Withdrawal status/txHash misattribution via unvalidated positional index matching in Omni Bridge - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
`OmniBridge.describeWithdrawal` selects the transfer record to report on purely by array index into the Omni Bridge API's response for a NEAR transaction hash, without verifying that the selected transfer actually corresponds to the withdrawal being described (e.g. by recipient/destination address or token). The exact same bug class was previously identified and fixed in the sibling `PoaBridge` implementation (matching by `assetId` instead of `index`, see `packages/intents-sdk/CHANGELOG.md:596` — "Fix POA bridge withdrawal matching to use assetId instead of index" — and the accompanying regression test/comment in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:318-321,409-427`), but the equivalent fix was never applied to `OmniBridge`.

### Finding Description
In `describeWithdrawal`: [1](#0-0) 

the code does:
```ts
const transfer = (
    await this.omniBridgeAPI.getTransfer({ transactionHash: args.tx.hash })
)[args.index];
```

`args.index` is a purely local, per-route counter assigned by `createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`), based only on the order withdrawals appear in the caller-supplied `withdrawalParams` array for a given bridge route. It has no relationship to how the Omni Bridge indexer orders transfers for a given NEAR transaction hash in its `getTransfer` response.

The only validation performed afterward is `transfer.recipient == null` — there is no check that `transfer.recipient` equals `args.withdrawalParams.destinationAddress`, nor that `transfer.token_id`/asset matches `args.withdrawalParams.assetId`. This is precisely the pattern the `PoaBridge` code explicitly documents and fixes: [2](#0-1) [3](#0-2) 

For batch withdrawals (multiple different assets/destinations bridged via Omni Bridge in a single NEAR intent — a supported, documented SDK feature, see `packages/intents-sdk/README.md:541-548` and the RFC in `docs/design/rfc-batch-withdrawal-granular-control.md`), if the indexer returns transfers in an order that does not match the order the withdrawal intents were constructed in (e.g., ordering by processing/finalization time rather than submission order, which is plausible since different chains finalize at very different speeds — Solana ~2s vs Bitcoin ~1hr per the same README), `describeWithdrawal`/`watchWithdrawal` will report the wrong transfer's `txHash` and completion status for a given `WithdrawalIdentifier`.

### Impact Explanation
This breaks the equality "status/txHash reported == the on-chain outcome for *this* withdrawal." An integrator using `waitForWithdrawalCompletion` or `createWithdrawalCompletionPromises` (`packages/intents-sdk/src/sdk.ts:557-608`) for a batch of Omni Bridge withdrawals could receive Withdrawal A's promise resolving with Withdrawal B's destination `txHash`, or a withdrawal reported "completed" using a transfer meant for another recipient/asset entirely. Since integrators are documented to key off `promises[i]` to credit/refund specific users or assets (`packages/intents-sdk/README.md:635-639`, "Index correspondence: `promises[i]` corresponds to `withdrawalParams[i]`"), this can cause an integrator to credit/refund the wrong withdrawal, double-credit one destination while marking another (still-pending or failed) withdrawal as falsely completed, or attribute the wrong destination tx hash to a customer-facing receipt. This matches the "status or hash misreport making an integrator credit or refund twice" High-impact category.

### Likelihood Explanation
Reachable purely through the SDK's own documented multi-asset batch withdrawal flow — no malicious actor, admin, or third-party misbehavior is required. It only requires that the Omni Bridge indexer's `getTransfer` response ordering diverge from the request-submission order for a batch that produced more than one transfer in a single NEAR transaction, which is plausible given the indexer records `finalised`/`signed` events asynchronously per-chain. I could not verify from available files whether the Omni Bridge API contractually guarantees index-stable, submission-order results (no ordering documentation was found in the searched files), so the exact ordering guarantee of `omniBridgeAPI.getTransfer` remains unconfirmed from the code available in this repo.

### Recommendation
Match transfers to `WithdrawalIdentifier` by an identity that is invariant to array ordering — analogous to the `PoaBridge` fix — e.g., filter `getTransfer` results by `transfer.recipient === expectedOmniAddress(destinationAddress, chain)` and/or `transfer.token_id` matching the parsed asset, falling back to `pending` when no unambiguous match is found, rather than indexing positionally.

### Proof of Concept
Not independently reproducible from static analysis alone — the vulnerability depends on the Omni Bridge indexer's actual response ordering behavior for multi-transfer NEAR transactions, which is external and not verifiable from the SDK repository. The existing test `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.test.ts:515-572` ("returns correct transfer by index") only exercises the case where index ordering happens to match array ordering, and does not test/guard against out-of-order indexer responses — confirming the missing validation but not proving the indexer actually reorders results in production.

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
