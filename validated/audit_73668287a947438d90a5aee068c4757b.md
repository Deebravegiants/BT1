### Title
Unbounded `handle_unsigned` batch processing under a static declared weight enables block-time DoS - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet-ismp`'s permissionless `handle_unsigned` extrinsic executes an attacker-supplied `Vec<Message>` batch — containing unbounded `GetRequest.keys: Vec<Vec<u8>>` and `PostRequest.body: Vec<u8>` fields — under a fixed, size-independent declared weight, mirroring the Stirling-PDF pattern where an unvalidated numeric/size parameter (`fontSize`/`widthSpacer`) drives unbounded resource consumption regardless of the declared cost.

### Finding Description
`handle_unsigned` is annotated with a static weight function that ignores the actual message content: [1](#0-0) 

```
#[pallet::weight(weight())]
#[pallet::call_index(0)]
pub fn handle_unsigned(origin: OriginFor<T>, messages: Vec<Message>) -> DispatchResultWithPostInfo {
    ensure_none(origin)?;
    Self::execute(messages.clone())?;
    Ok(().into())
}
```

and [2](#0-1) 

```
fn weight() -> Weight {
    Weight::from_parts(300_000_000, 0)
}
```

`Message` and its variants carry unbounded, attacker-controlled collections: `GetRequest.keys: Vec<Vec<u8>>` [3](#0-2)  and `DispatchGet.keys`/`PostRequest.body` on the dispatch side [4](#0-3) . Neither the GET request's `keys` array length/size nor a batch's total number of `Message`s is bounded anywhere in the dispatch or handling path — the EVM dispatcher accepts an arbitrary `bytes[] keys` array with no length check [5](#0-4) , and the test suite itself demonstrates 100 GetRequests each carrying 256 keys processed through a single `handle_unsigned`/decompressed call [6](#0-5) .

Each `Message::Request`/`Message::Response` in the batch triggers `verify_membership`/`verify_non_membership` state-proof verification per key/commitment inside `handle_incoming_message` (see the per-request `state_machine.verify_membership(...)` loop pattern in `modules/ismp/core/src/handlers/request.rs`), so the real computational cost scales with `messages.len() * keys.len() * proof_size` — none of which factors into the declared `300_000_000` weight. Because `handle_unsigned` is unsigned, `validate_unsigned` itself calls `Self::execute(messages.clone())` to accept it into the pool, so a maliciously oversized-but-valid batch (large key counts backed by real proofs the attacker can legitimately obtain, since GET requests are permissionless) is fully computed once for pool admission and again at block-inclusion — under-costed both times relative to actual execution work.

This is compounded by `pallet-call-decompressor`, which lets an attacker submit a small zstd-compressed blob that decompresses (bounded only by `MaxCallSize` megabytes, not the substantive weight of the inner `Message` batch) into a large `handle_unsigned` call and dispatches it via `decode_and_execute` [7](#0-6) , amplifying the ratio between declared weight/wire size and actual node processing time.

### Impact Explanation
An attacker who dispatches (cheaply, from any permissionless EVM/substrate app) GET requests with very large `keys` arrays, or crafts oversized `Message` batches relayed as legitimate proofs, can get `handle_unsigned` accepted with a weight far below its true computational cost. Because Substrate block authors budget execution time by declared weight, a batch whose real cost exceeds the block's remaining weight budget (while reporting only `300_000_000`) causes block-authoring/import to take substantially longer than expected, risking missed block production, degraded finality, or authoring-node stalls — a Denial of Service on hyperbridge's core message-delivery pallet. This directly matches the "unable to deliver messages" acceptance criterion, since a validator/collator stalled processing an oversized batch cannot process other pending ISMP messages.

### Likelihood Explanation
Medium: the underlying data structures (`Vec<Message>`, `GetRequest.keys: Vec<Vec<u8>>`) are unbounded by design and reachable from any user who can dispatch a GET request through `EvmHost.dispatch(DispatchGet)` with no key-count/size limit, or from any relayer submitting `handle_unsigned` batches. Exploitation still requires the attacker to obtain valid state proofs for many keys/large bodies (costly but not prevented), and some runtimes (e.g. `IsmpCallFilter` on gargantua/nexus) restrict which messages pass through `handle_unsigned`, but they do not bound batch or key-array size.

### Recommendation
- Make `handle_unsigned`'s declared weight a function of the actual batch content (number of messages, cumulative key count, body/proof sizes) rather than a fixed constant, similar to how `pallet-call-decompressor` already bounds `encoded_call_size` against `MaxCallSize`.
- Introduce and enforce an explicit bound on `GetRequest.keys.len()` (and per-key size) at both dispatch (`EvmHost.dispatch`, `pallet_ismp` dispatcher) and handling (`handle_incoming_message`) time.
- Reject `handle_unsigned` batches whose message count or total key/proof size exceeds a configurable pallet constant, enforced in `validate_unsigned` before the expensive `execute()` call is attempted.

### Proof of Concept
Not independently executable from the index alone (no local devnet), but the exploit path is directly supported by existing code and test fixtures:
1. Dispatch a `GetRequest` (or many) via `EvmHost.dispatch(DispatchGet)` with a very large `keys` array (no length check exists in `EvmHost.sol` at [8](#0-7) ).
2. Obtain/relay a `GetResponse`/`RequestMessage` carrying this oversized `GetRequest` (the test at [6](#0-5)  constructs 100 such requests × 256 keys as a working fixture).
3. Submit as `pallet_ismp::Call::handle_unsigned { messages }` (optionally wrapped via `pallet_call_decompressor::decompress_call` to shrink wire size). The call's declared weight remains `Weight::from_parts(300_000_000, 0)` [2](#0-1)  regardless of batch size, while `Self::execute` performs full membership verification for every key in every message.
