### Title
Webhook shop-domain, topic, and webhook-id are trusted unauthenticated because the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from unauthenticated HTTP headers, while `Utils::HmacValidator.validate` only verifies the HMAC over the raw body (`to_signable_string` returns `@raw_body`). `Registry.process` forwards `request.shop` and `request.topic` directly into `WebhookMetadata`, which is delivered to the host app's handler as the tenant identifier, without any binding between the HMAC-verified bytes and those header-derived fields.

### Finding Description
`HmacValidator.validate` computes and compares the HMAC strictly over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw JSON body, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from HTTP headers that are never fed into the signable string: [2](#0-1) 

`Registry.process` validates only that HMAC, then blindly trusts `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the host application's handler: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no further validation, and is the only tenant/shop identifier the handler receives: [4](#0-3) 

This breaks the intended identity binding: `HMAC-verified(body) == HMAC-verified(shop, topic, webhook_id)` does not hold — the gem verifies the body's integrity but silently forwards the shop/topic/webhook_id headers as if they were equally authenticated. Concretely, since the HMAC is computed only from the body (a value fully controlled by whoever crafts the request, e.g. the operator of any shop with the app installed, or anyone who has captured one legitimate webhook payload+signature pair for a known topic/body from Shopify), an attacker can take a valid `(body, hmac)` pair and pair it with an arbitrary `X-Shopify-Shop-Domain` / `X-Shopify-Topic` / `X-Shopify-Webhook-Id` header set. `HmacValidator.validate` still returns `true` because it never looks at those headers, and `Registry.process` will hand the forged `shop`/`topic` straight to the handler as `WebhookMetadata`, causing the host application to attribute the (correctly signed) body to the wrong tenant/topic.

### Impact Explanation
This is a cross-tenant confusion vector: an app that keys any per-tenant logic (e.g., "look up shop X's order/customer state and apply the body payload to it") off `WebhookMetadata.shop` can be made to apply data belonging to shop A into shop B's context, because the gem itself provides no cross-check between the authenticated bytes and the header-derived shop/topic. This matches the "Critical - cross-tenant access" impact class: the identity binding between the signed payload and the claimed tenant is not enforced by the library, and the library is the trust boundary host apps rely on when calling `Registry.process`/`HmacValidator.validate`.

### Likelihood Explanation
Exploitation requires only a previously-observed valid `(body, hmac)` pair for the target topic (obtainable by the attacker's own shop receiving a real webhook for that topic, since payload structure/HMAC-secret is shared across all shops using the same app), plus the ability to POST to the app's public webhook endpoint with custom headers — both of which are available to any unprivileged user who can install/operate the app on a shop they control. No access to `api_secret_key`, access tokens, or privileged credentials is required.

### Recommendation
Bind the header-derived identity fields into the HMAC-verified surface, or otherwise cryptographically/contextually validate them before trusting them:
- Include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` if Shopify's HMAC scheme supports it, or
- Require host applications to cross-check `WebhookMetadata.shop` against their own registered/expected shop list before processing, and document this requirement prominently since the gem's `HmacValidator` does not perform that check itself, or
- Have `Registry.process` reject requests where the `shop` header does not match a shop for which the topic was actually registered/known to the app (tracked via the `Registration`s already stored in `@registry`).

### Proof of Concept
1. App has processed at least one legitimate webhook for `orders/create` from Shop A, giving the attacker (who controls Shop A) a known-valid `(raw_body, X-Shopify-Hmac-Sha256)` pair (this HMAC is valid for the app across all shops, since only `Context.api_secret_key` is used to compute it — no per-shop info is bound in).
2. Attacker resends that exact `raw_body` and `hmac` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged `shop` header successfully: [5](#0-4) 
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `raw_body` against the previously-valid hmac: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "orders/create", body: ...)` and processes the attacker's data as though it belongs to the victim shop.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
