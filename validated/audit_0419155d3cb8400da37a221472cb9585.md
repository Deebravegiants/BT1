### Title
Passphrase cache `maxTtl` hard cap is permanently bypassed after the first activity reset - ([File: features/application/src/modules/passphrase-cache.ts])

### Summary
The `PassphraseCache.get()` method in `features/application/src/modules/passphrase-cache.ts` is supposed to enforce two independent limits on how long a cached wallet passphrase can remain valid: a sliding idle-timeout (`ttl`, e.g. auto-lock timer) and an absolute hard cap (`maxTtl`, e.g. 60 minutes) that should force re-entry of the passphrase no matter how much activity occurs. Due to a logic flaw analogous to the arithmetic-truncation class of bug in the referenced report (a value that is supposed to bound/decay over time is silently reset instead of being properly accounted for), the `maxTtl` cap is only checked before the very first "activity" event, and is never enforced again afterwards.

### Finding Description
`PassphraseCache` stores four keys: `passphrase`, `addedAt`, `inactiveAt`, `ttl`. [1](#0-0) 

`get()` validates the cached passphrase like this: [2](#0-1) 

- If `inactiveAt` has never been set, the passphrase is valid only while `addedAt + maxTtl > Date.now()` — this is the intended hard cap.
- Once `inactiveAt` is set even a single time, the code switches to the `inactiveAt` branch permanently and only checks `inactiveAt + ttl > Date.now()`. It never again compares against `addedAt + maxTtl`.

`inactiveAt` is set by `scheduleClear()`, which is invoked every time the app goes idle or the auto-lock timer is restarted (`Application.unload()` and `Application.restartAutoLockTimer()`): [3](#0-2) [4](#0-3) [5](#0-4) 

`scheduleClear()` also reschedules the browser-extension alarm using the current `ttl` (not `maxTtl`): [6](#0-5) 

Because `restartAutoLockTimer()`/`unload()` can be triggered repeatedly by normal or scripted UI/extension activity (well within the `ttl` window, e.g. every 59 minutes with a 60‑minute `ttl`), `inactiveAt` keeps being refreshed to "now" before it ever expires. From that point on, `get()` only ever compares against the sliding `inactiveAt + ttl` window and the `addedAt + maxTtl` absolute cap is never consulted again — effectively making the "hard" session cap ineffective for as long as periodic activity continues, in the same way the audited contract's `noOfDays` calculation was silently reset every payment instead of accumulating properly against the real elapsed time.

### Impact Explanation
The cached plaintext passphrase is used by `Application.#autoUnlock()` to automatically unlock the wallet without user interaction: [7](#0-6) 

`maxTtl` exists precisely to force the wallet to require the passphrase again after an absolute maximum window, independent of how much "activity" happens (e.g. an attacker or malware repeatedly touching the extension/app to keep it "active"). With this bug, anyone who can trigger periodic activity signals (extension wake-ups, background timers, or scripted `restartAutoLockTimer` calls) on a device that has the extension/app already unlocked once can keep the plaintext passphrase cached and auto-unlocking indefinitely, well beyond the configured `maxTtl`, defeating the intended security control and enabling continued unauthorized wallet unlocking/signing if the device is later accessed.

### Likelihood Explanation
`restartAutoLockTimer()` and `unload()` are regular, unprivileged application-level calls exposed through the normal SDK/API surface (not a privileged or maintainer-only path), and are triggered by ordinary UI activity or extension lifecycle events. No special access is required beyond what any local user/attacker with access to the running extension/app instance already has, making the bypass straightforward to trigger unintentionally or deliberately.

### Recommendation
Always validate against the absolute cap regardless of the `inactiveAt` branch, e.g.:

```ts
async get() {
  const [passphrase, addedAt, inactiveAt, ttl] = ...

  if (passphrase) {
    const withinMaxTtl = addedAt + this.#maxTtl > Date.now()
    const withinIdleTtl = inactiveAt ? inactiveAt + ttl > Date.now() : true

    if (withinMaxTtl && withinIdleTtl) {
      return passphrase
    }
  }
  ...
}
```

This ensures the sliding idle window (`ttl`) and the absolute hard cap (`maxTtl`) are both enforced together, so repeated activity cannot indefinitely extend the cached passphrase lifetime past `maxTtl`.

### Proof of Concept
1. Unlock the wallet with a passphrase; `PassphraseCache.set()` stores `addedAt = Date.now()`, no `inactiveAt` yet, `maxTtl` = 60 minutes.
2. At `t = 10min`, trigger any normal activity that calls `Application.restartAutoLockTimer()` (or let the app `unload()`), which calls `scheduleClear()` → sets `inactiveAt = Date.now()` (t=10min).
3. Repeat step 2 every ~50 minutes (well within `ttl`) indefinitely — e.g. at t=59min, t=108min, t=157min, etc.
4. At `t = 200min` (well past `maxTtl` = 60 minutes from `addedAt`), call `get()`. Because `inactiveAt` was set, the code only checks `inactiveAt + ttl > Date.now()`, which is true, and the cached passphrase is returned — despite `addedAt + maxTtl` having elapsed long ago.
5. `Application.#autoUnlock()` uses this passphrase to silently unlock the wallet, bypassing the intended absolute session cap.
