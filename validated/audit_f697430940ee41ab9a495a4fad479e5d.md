### Title
Decimal-conversion helpers in `pallet-hyper-fungible-token` silently drop precision scaling when local decimals exceed ERC20 decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`convert_to_balance` and `convert_to_erc20` in the `hyper-fungible-token` pallet use `erc_decimals.saturating_sub(local_decimals)` to compute the scaling exponent between an EVM ERC20 amount and the local substrate balance. `register_token`/`update_token` enforce `config.decimals >= local_decimals` at registration time, which happens to make `saturating_sub` behave correctly for the registered path today — but the conversion functions themselves have no such guard and are the same class of "one-directional decimal math" bug as the reported `Auction::buy()` issue: they only scale correctly when `erc_decimals >= local_decimals`, and silently become a no-op (scaling factor of `10^0 = 1`) whenever that invariant does not hold, rather than computing the correct inverse scale.

### Finding Description
`convert_to_balance` divides the incoming U256 ERC20 amount by `10^(erc_decimals - local_decimals)` using `saturating_sub`: [1](#0-0) 

`convert_to_erc20` multiplies the outgoing local balance by the same saturating-subtracted exponent: [2](#0-1) 

Both functions assume `erc_decimals >= local_decimals` always holds. When it does not (`local_decimals > erc_decimals`), `saturating_sub` returns `0`, the exponent becomes `10^0 = 1`, and **no scaling is applied at all** instead of the mathematically required division/multiplication by `10^(local_decimals - erc_decimals)`. This is exactly the same root-cause pattern as the reported `Auction::buy()` bug: a price/amount conversion that only accounts for decimal differences in one direction and silently mishandles the other.

The pallet does guard the *registration* path against this by enforcing `config.decimals >= local_decimals`: [3](#0-2) [4](#0-3) 

so for tokens configured through `register_token`/`update_token`, `erc_decimals >= local_decimals` is currently guaranteed. However, this invariant is enforced only at the call sites in `lib.rs`, not inside `impls.rs` itself — the conversion functions are unconditionally reachable by any unprivileged user via `send()` (outbound) and via `on_accept`/`on_timeout` (inbound, driven by any relayed cross-chain message) on `module.rs`: [5](#0-4) [6](#0-5) [7](#0-6) 

A functions-level review shows there is no defensive check inside `convert_to_balance`/`convert_to_erc20` themselves guarding against `local_decimals > erc_decimals`; correctness for every call site depends entirely on the registration-time `ensure!` never being bypassed or changed. Given the fix pattern requested for the analogous `Auction::buy()` report is precisely "compute the correct scale factor in both directions instead of assuming one direction," this helper pair embodies the same latent defect: it is not a symmetric decimal-adjustment utility, it is a one-directional one masquerading as general-purpose, and its safety is an invariant maintained entirely outside the function by two `ensure!` calls in `register_token`/`update_token`.

### Impact Explanation
If the `erc_decimals >= local_decimals` invariant is ever violated for a registered token (e.g., a future runtime upgrade, a different `CreateOrigin` configuration, a governance token registration with different decimal assumptions, or a bug in a downstream caller that reuses these `pub fn` conversion helpers directly), the effect mirrors the reported bug exactly:
- Outbound `send()`: `convert_to_erc20` would fail to scale up the ERC20 amount, causing the destination `HyperFungibleToken` contract to mint/release **far less** than intended (value loss for the sender / permanent value destruction), or, depending on which side is smaller, an amount many orders of magnitude wrong.
- Inbound `on_accept`/`on_timeout`: `convert_to_balance` would fail to scale down/up the ERC20 amount to local balance decimals, causing the pallet to mint or refund an amount off by a factor of `10^(local_decimals - erc_decimals)` — this is an unbacked-mint / fund-freezing class of impact when it manifests, since the escrow on one side no longer matches the minted/refunded amount on the other.

Because this pattern is currently masked by the registration-time `ensure!`, the practical exploitability today depends on finding or forcing a state where that invariant is violated; it is not, at present, directly triggerable by only a single unprivileged transaction under the *current* registered-token configuration. This weakens the likelihood but does not eliminate the underlying code defect, which is a silent correctness trap for any future/alternate use of these public conversion functions.

### Likelihood Explanation
Medium. Exploitation under the *current* codebase requires a registered `(AssetId, StateMachine)` pair whose EVM decimals are lower than the local asset's decimals — which `register_token`/`update_token` currently reject. However:
- The conversion functions are `pub fn`s in `impls.rs`, reusable by any future extension of the pallet or runtime without re-deriving the invariant.
- The invariant is enforced in two separate places (`register_token`, `update_token`) rather than centrally in the conversion helpers, so a partial fix, a missed enforcement path, or a governance action that directly writes to `Precisions`/`NativeAssets` storage (bypassing the extrinsics) would silently reintroduce the bug with no compile-time or runtime safety net.
- Every mint/burn/transfer on both the outbound (`send`) and inbound (`on_accept`/`on_timeout`) cross-chain paths — reachable by any unprivileged signed account — depends on this arithmetic being correct.

### Recommendation
Make `convert_to_balance` and `convert_to_erc20` symmetric and self-defending rather than relying on an external invariant:
```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = if erc_decimals >= local_decimals {
        (value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))).to_string()
    } else {
        (value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))).to_string()
    };
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
This removes the dependency on the registration-time `ensure!` as the sole safety mechanism, and makes the helper correct regardless of how `Precisions` is populated in the future.

### Proof of Concept
Not runnable against the current registered-token state, since `register_token`/`update_token` currently reject `config.decimals < local_decimals` via the `ErcDecimalsBelowLocal` check [3](#0-2) . A unit test directly exercising the exported `convert_to_balance`/`convert_to_erc20` functions with `erc_decimals < local_decimals` demonstrates the defect in isolation:
```rust
// erc_decimals = 6 (e.g. USDC-style ERC20), local_decimals = 18 (substrate asset)
// Correct: scale UP by 10^12 when converting ERC20 -> local balance.
let erc_amount = U256::from(100_000_000u64); // 100 USDC, 6 decimals
let local: u128 = convert_to_balance(erc_amount, 6, 18).unwrap();
// Bug: saturating_sub(6,18) = 0 => divides by 10^0 = 1 => returns 100_000_000
// Correct expected value: 100_000_000 * 10^12 = 100_000_000_000_000_000_000
assert_ne!(local, 100_000_000_000_000_000_000u128); // demonstrates the missing scale-up
```
This is the same shape of proof used in the external report (compute expected vs. actual scaled amount and show the multi-order-of-magnitude discrepancy), applied to `convert_to_balance`/`convert_to_erc20` instead of `Auction::buy()`.
