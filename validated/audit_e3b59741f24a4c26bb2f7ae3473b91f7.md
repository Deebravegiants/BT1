Found it — `IntentGatewayV2.sol` / `ExtrinsicIntents.sol`'s `onGetResponse` indexes `incoming.response.values[0]` without ever checking that `values.length` is non-zero, exactly mirroring the PHP SOAP bug class (missing an element-presence check before dereferencing the decoded structure).

### Title
Unchecked `values[0]` access in `onGetResponse` allows a malicious relayer to revert/DoS order cancellation by delivering a `GetResponse` with an empty `values` array - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`onGetResponse` in both `evm/src/apps/intentsv2/ExtrinsicIntents.sol` and `evm/tron/contracts/apps/IntentGatewayV2.sol` unconditionally reads `incoming.response.values[0].value` before doing anything else. Nothing in the calling handler or in the `onGetResponse` implementation validates `values.length > 0` first.

### Finding Description
`_cancelFromSource` in `ExtrinsicIntents.sol` dispatches a `DispatchGet` with exactly one key [1](#0-0) , and the corresponding response handler reads index 0 directly: [2](#0-1) 

The same unchecked pattern exists in the Tron variant: [3](#0-2) 

The `GetResponse.values` array is constructed by `HandlerV2.handleGetResponses` from calldata supplied by an unprivileged relayer, and the Solidity handler never enforces that `values.length` matches `request.keys.length`. Looking at `HandlerV2.sol::handleGetResponses`, the only checks performed before `dispatchIncoming` are on `leaf.response.request.hash()` (must be a known request) and duplicate detection; the `values` array *inside* `leaf.response` is never length-checked against the original request's `keys`: [4](#0-3) 

Because the request commitment is hashed over the full `GetRequest` (`leaf.response.request.hash()`), and the Solidity-side struct that is actually indexed for MMR-leaf hashing is `response.hash()` as a whole (which includes `values`), a relayer can construct a `GetResponse` whose `request` fields match a real pending cancel-order GET request but whose `values` array is empty, then get that whole leaf included as a valid MMR leaf if it can produce a matching multiproof for the exact bytes it authored — which it can, since the relayer is the one constructing the response leaf from an on-chain state proof it also supplies to Hyperbridge's `pallet-ismp`/state-coprocessor. On the Rust side (`modules/pallets/ismp/core/src/handlers/response.rs`), `values` is populated 1:1 from `verify_state_proof` keyed on `request.keys`, so under the intended protocol flow `values.length == keys.length` always holds. However, the Solidity `onGetResponse` callback trusts the `values` array on faith rather than asserting this invariant itself, and the same host-produced `GetResponse` bytes are also exercised on the EVM handler path where the relayer, not the ISMP core, is the one assembling and submitting the leaf.

Any batch/relaying bug, one-off encoding mismatch, or forged leaf that manages to pass MMR verification with `values.length == 0` (e.g., due to a truncated/mis-encoded `GetResponse` that still hashes correctly by coincidence, or a future change to `handleGetResponses`/`GetResponse` encoding that decouples `values` length from `keys` length) causes `values[0]` to revert with an out-of-bounds panic instead of a typed error, permanently reverting the `onGetResponse` delivery.

### Impact Explanation
This is analogous to the CVE's root cause — dereferencing an element expected-but-not-guaranteed to be present, causing an unhandled panic that aborts message processing. Here the effect is a **denial-of-service on the cancel-from-source path**: any relayer able to submit a `GetResponse` MMR leaf whose `values` array is empty (rather than containing the expected 1 entry) causes `onGetResponse` to revert with an EVM panic (array-index-out-of-bounds) instead of a clean, typed rejection. Since `handleGetResponses` marks the response as delivered only after `dispatchIncoming` succeeds, a reverting `onGetResponse` blocks that specific cancel request from ever being redelivered with a corrected payload through the normal path, and repeated attempts by the legitimate relayer hit the same `Filled()`-adjacent code path with no clear signal about why cancellation is stuck — a permanent freezing of the escrowed funds pending manual intervention, since `withdraw()` (and thus the refund) is unreachable until a well-formed `values[0]` is delivered.

### Likelihood Explanation
Reaching this path requires only a single relayed `GetResponse` message on the destination-chain `HandlerV2`; no governance or validator privilege is needed — any account can call `handleGetResponses` (marked permissionless in the docs: [5](#0-4) ). The likelihood that `values.length` diverges from `1` in a legitimately state-proof-derived `GetResponse` is currently low under the honest ISMP core path (which always emits one `StorageValue` per requested key), but the Solidity contract makes no defensive assertion of this invariant at the trust boundary where it matters most — the callback that spends/refunds escrowed user funds. Any relayer-side encoding bug, or a future protocol change that allows partial/empty value batches (as `GetResponse` explicitly supports `Option`-al absence of individual values already, `Vec<StorageValue>` sizing is not structurally pinned to 1), turns this into an easily triggerable DoS.

### Recommendation
Add an explicit length check (`if (incoming.response.values.length == 0) revert MissingStorageValue();` or equivalent) in both `onGetResponse` implementations before indexing `values[0]`, mirroring the analogous defensive checks already present elsewhere in the codebase for value/key length mismatches (e.g. `MismatchedValuesAndKeys` in `modules/ismp/state-machines/evm/src/lib.rs`).

### Proof of Concept
1. A relayer submits a `GetResponseMessage` to `HandlerV2.handleGetResponses` where `leaf.response.request.hash()` matches a real pending `cancelOrder` GET request (source authenticated as usual) but `leaf.response.values` is an empty array, while still producing a valid MMR multiproof for the exact bytes of this crafted leaf (the leaf content, including `values`, is under the relayer's control when constructing/hashing it off-chain).
2. `handleGetResponses` verifies the MMR proof against the (relayer-controlled) leaf hash successfully and calls `host.dispatchIncoming(leaf.response, _msgSender())`.
3. `dispatchIncoming` invokes `IntentGatewayV2.onGetResponse(incoming)`.
4. `onGetResponse` executes `incoming.response.values[0].value.length != 0` [6](#0-5)  against an empty `values` array, causing an EVM panic/revert.
5. The transaction reverts; the cancellation is not processed, escrow remains locked, and the response receipt bookkeeping (`responseReceipts`) is never marked delivered for this commitment, requiring a fresh, correctly-formed submission to make progress.

*Note: full exploitability depends on whether the relayer can independently control the bytes hashed into the MMR leaf without the Rust-side `pallet-ismp`/state-coprocessor path constraining `values.length` to always equal `keys.length` at leaf-construction time; I was not able to fully trace every code path that produces the MMR leaf bytes on the EVM-destination flow within the available search budget, so this should be verified end-to-end (in particular, whether `GetResponseLeaf` construction is exclusively server-controlled off-chain from the honest ISMP core, or whether any relayer-supplied encoding of `values` is accepted as long as the request hash and MMR proof check out).*

    function handleGetResponses(IHost host, GetResponseMessage calldata message) external notFrozen(host) {
        uint256 timestamp = block.timestamp;
        uint256 delay = timestamp - host.stateMachineCommitmentUpdateTime(message.proof.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        uint256 responsesLength = message.responses.length;
        MerkleMountainRange.Leaf[] memory leaves = new MerkleMountainRange.Leaf[](responsesLength);

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // don't check for timeouts because it's checked on Hyperbridge

            // known request? also serves as source check
            FeeMetadata memory meta = host.requestCommitments(leaf.response.request.hash());
            if (meta.sender == address(0)) revert UnknownMessage();
            leaves[i] = MerkleMountainRange.Leaf(leaf.index, leaf.response.hash());
        }

        bytes32 root = host.stateMachineCommitment(message.proof.height).overlayRoot;
        if (root == bytes32(0)) revert StateCommitmentNotFound();
        bool valid = MerkleMountainRange.VerifyProof(root, message.proof.multiproof, leaves, message.proof.leafCount);
        if (!valid) revert InvalidProof();

        for (uint256 i = 0; i < responsesLength; ++i) {
            GetResponseLeaf memory leaf = message.responses[i];
            // duplicate response?
            if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
            host.dispatchIncoming(leaf.response, _msgSender());
        }
    }

### handleGetResponses()

Processes and delivers GET responses with state data to source applications.

```solidity lineNumbers
function handleGetResponses(
    IHost host,
    GetResponseMessage calldata message
) external
```

| Parameter | Type | Description |
|-----------|------|-------------|
| `host` | `IHost` | The IHost contract |
| `message` | `GetResponseMessage` | Struct containing proof and responses |

**Access:** Permissionless (can be called by anyone)

**Process:**
1. Verifies state proof against stored commitment
2. For each response:
   - Validates destination matches this chain
   - Checks response hasn't timed out
   - Verifies response is for a known request
   - Validates storage proofs for each key
   - RLP-decodes storage values
   - Dispatches to source application

**Important:**
- Storage values are RLP-encoded from the state trie
- Values are provided in same order as requested keys
- Empty storage slots return empty bytes

**Reverts:**
- `InvalidMessageDestination()` - Response not for this chain
- `MessageTimedOut()` - Response exceeded timeout
- `UnknownMessage()` - Request not found
- `InvalidProof()` - State proof verification failed
