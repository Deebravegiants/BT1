Confirmed root cause: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read directly from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only the HMAC over the body and then trusts `request.shop` to attribute the webhook to a tenant when invoking the handler [3](#0-2) .

### Title
Webhook shop attribution bypass via unsigned `shop-domain` header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The webhook HMAC verification in this gem authenticates only the raw request body; the `shop` value used to attribute the webhook to a specific merchant/tenant is read from an HTTP header that is never included in the HMAC-signed data. This breaks the identity binding `HMAC-verified bytes == data acted upon`, because the "shop" that the host application uses to route/attribute webhook data is disjoint from what was actually authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` via `to_signable_string`, which returns `@raw_body` only: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled straight from HTTP headers with no cryptographic binding to the signed payload: [4](#0-3) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` — which, per `to_signable_string`, checks only the body bytes against the app's `client_secret` — and then unconditionally trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler: [5](#0-4) 

Because a single app uses one `api_secret_key` across all installing shops, the HMAC for a given raw body is identical regardless of which shop it was originally sent for. An attacker who is a legitimate (unprivileged) installer of the app — i.e., an ordinary merchant with no special credentials — receives genuine webhook deliveries containing a valid `hmac-sha256` header for their own shop. They can replay that exact `raw_body` + `hmac-sha256` pair to the app's shared webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `Utils::HmacValidator.validate` will report success because it never inspects `shop`, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen value, causing the host application to process/attribute the (attacker-controlled-timing) payload as belonging to a different tenant.

### Impact Explanation
This crosses a tenant boundary: any app relying on `WebhookMetadata#shop` (or `request.shop`) — as the documented API instructs — to decide which merchant's data to update/delete/redact will act on behalf of a shop the attacker does not control. This matches "cross-tenant access" (Critical) because the identity binding the gem is supposed to provide (payload authenticated == shop attributed) is broken by design of `to_signable_string`.

### Likelihood Explanation
Likelihood is Medium-to-High for an app builder using this gem as documented: it requires only that the attacker (1) be a normal, unprivileged installer of the same app on any shop, so they can observe at least one genuine `(raw_body, hmac)` pair from Shopify's real webhook delivery, and (2) be able to POST to the app's public webhook endpoint with a forged `shop-domain` header, which is a standard unauthenticated HTTP capability — no `api_secret_key`, tokens, or TLS interception needed.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind `shop` to the verified payload, in `ShopifyAPI::Webhooks::Request#to_signable_string` / `HmacValidator`, so that `Registry.process` cannot attribute a validated payload to a shop that wasn't part of what was signed.

### Proof of Concept
1. App has one client_secret; two shops A (attacker-controlled) and B (victim) both install the app.
2. Shopify sends a real webhook to the app's shared endpoint for shop A with body `B_raw` and header `shopify-hmac-sha256: H = HMAC(secret, B_raw)`.
3. Attacker captures `(B_raw, H)` from their own delivery (e.g., via their own server logs — no interception of anyone else's traffic required).
4. Attacker POSTs to the same endpoint with body `B_raw`, `shopify-hmac-sha256: H` unchanged, but `shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this as valid; `Utils::HmacValidator.validate` returns `true` because `to_signable_string` only checks `B_raw` against `H`.
6. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the host app to apply `B_raw`'s effects under the victim shop's identity. [3](#0-2) [6](#0-5)
