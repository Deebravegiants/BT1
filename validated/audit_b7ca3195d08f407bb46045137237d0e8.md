## Analysis

The PBMAC1 bug class here is: **an integrity/authentication check counts credential material toward a security threshold without verifying that each unit of credential is unique/independent**, letting an attacker artificially inflate an insufficient number of genuine signers into what looks like a passing quorum.

The same pattern exists in Hyperbridge's BEEFY consensus verifiers — both the Rust light client used by `pallet-ismp` and the Solidity `EcdsaBeefy` contract — which are the components a relayer uses to post consensus/state updates that gate all downstream message delivery.

### Title
BEEFY supermajority check counts raw vote length instead of distinct authority signers, allowing quorum forgery with duplicated votes - (File: `modules/consensus/beefy/verifier/src/lib.rs`, `evm/src/consensus/EcdsaBeefy.sol`)

### Summary
`verify_mmr_update_proof` (Rust) and `verifyMmrUpdateProof` (Solidity) both derive the number of "signers" solely from `mmr.signed_commitment.signatures.len()` / `relayProof.signedCommitment.votes.length` and compare that raw count against the 2/3+1 supermajority threshold, before ever checking that the `(authorityIndex, signature)` entries refer to distinct authorities. [1](#0-0) [2](#0-1) 

### Finding Description
`verify_mmr_update_proof` builds `authority_leaves`/`authority_indices` by iterating every entry in `mmr.signed_commitment.signatures` and recovering the signer for each, with no deduplication of `sig.index`: [3](#0-2) 

The Solidity `EcdsaBeefy.verifyMmrUpdateProof` mirrors this exactly: `sigLen = relayProof.signedCommitment.votes.length` gates `checkParticipationThreshold`, and the same loop builds one `MerkleMultiProof.Leaf` per vote entry, again without rejecting repeated `authorityIndex` values: [4](#0-3) 

Because a valid ECDSA signature over a fixed commitment hash from one authority can be copied into the `votes`/`signatures` array multiple times (with the same `authorityIndex`), an attacker who controls (or has leaked) as few as one authority signing key can pad the vote array to any length, satisfying `checkParticipationThreshold`/`check_participation_threshold` (`len >= (2*total)/3 + 1`) without ever gathering a genuine supermajority. The subsequent merkle multi-proof check (`MerkleMultiProof.VerifyProof` / `rs_merkle::MerkleProof::verify`) only confirms that each claimed `(index, leaf)` pair is a real member of the authority set commitment — it does not by itself enforce distinctness of indices across the proof, so re-submitting the same valid `(index, leaf)` pair multiple times reconstructs the same (already-correct) root and passes. [5](#0-4) [6](#0-5) 

This is structurally identical to the PBMAC1 flaw: the check that is supposed to bound forgery probability/cost (an HMAC key length there, a supermajority-of-signers count here) is satisfied by *quantity* of low-quality/duplicated credential material rather than *distinct, independent* credentials, collapsing the intended security margin (2/3+1 of the full authority set) down to as little as one compromised signer.

### Impact Explanation
BEEFY consensus verification is the trust root for propagating relay-chain-finalized parachain state (and via it, MMR-anchored request/response commitments) into every downstream `EvmHost`/`HandlerV2` state-commitment update on both the pallet-ismp (Substrate) and EVM (`EcdsaBeefy`) sides. An attacker who can forge acceptance of a consensus update with far fewer than the required 2/3+1 authorities can smuggle an attacker-chosen MMR root and parachain header set into the trusted consensus state. From there, they can subsequently forge membership proofs for arbitrary ISMP requests/responses (forged message delivery), enabling unbacked minting in token-bridge apps, unauthorized app actions, or permanent freezing/draining of funds routed through Hyperbridge.

### Likelihood Explanation
Reachable from a single unprivileged relayer transaction: consensus proof submission is a normal, permissionless dispatch path (no special privilege required to submit a BEEFY update). The only precondition is possession of at least one valid signature from a member of the trusted authority set (e.g., a single leaked/compromised validator key, or one malicious validator) — a materially weaker requirement than genuinely collecting a 2/3+1 supermajority, mirroring the "high access complexity, no privileges" profile (AC:H, PR:N) of the source CVE.

### Recommendation
Before comparing against the supermajority threshold, deduplicate the `(authorityIndex)` set for both `verify_mmr_update_proof` (Rust) and `verifyMmrUpdateProof` (Solidity) — reject the proof if `signatures.len()` (or `votes.length`) does not equal the count of *distinct* `authorityIndex` values, mirroring the duplicate-participant guard already present in the Pharos verifier's `verify_validator_membership`. [7](#0-6) 

### Proof of Concept
1. Trusted BEEFY authority set has `N` authorities; supermajority threshold is `floor(2N/3)+1`.
2. Attacker obtains (via compromise/leak) one valid authority signing key and its `authorityIndex` `k`, and produces a valid ECDSA signature `sig_k` over a malicious `commitmentHash` (e.g., one carrying an attacker-chosen MMR root).
3. Attacker submits a BEEFY consensus proof whose `votes`/`signatures` array repeats the pair `(k, sig_k)` `floor(2N/3)+1` times.
4. `sigLen`/`signatures_length` equals `floor(2N/3)+1`, satisfying `checkParticipationThreshold`/`check_participation_threshold`. [8](#0-7) 
5. Each duplicated `(k, keccak256(authority_k))` leaf reconstructs the same, already-valid root, so `MerkleMultiProof.VerifyProof`/`rs_merkle::MerkleProof::verify` passes. [9](#0-8) 
6. The malicious MMR root/parachain state is accepted as the new trusted consensus state, from a single compromised authority instead of a genuine supermajority.

pub fn verify_mmr_update_proof<H: Keccak256 + EcdsaRecover + Send + Sync>(
	mut trusted_state: ConsensusState,
	mmr: MmrProof,
) -> Result<(ConsensusState, H256), Error> {
	let signatures_length = mmr.signed_commitment.signatures.len();
	let latest_height = mmr.signed_commitment.commitment.block_number;

	if trusted_state.latest_beefy_height >= latest_height {
		return Err(Error::StaleHeight {
			trusted_height: trusted_state.latest_beefy_height,
			current_height: latest_height,
		});
	}

	let commitment = mmr.signed_commitment.commitment.clone();

	// Pick the authority set the commitment claims to be signed under, then judge
	// participation against that set alone.
	let authority_set = if commitment.validator_set_id == trusted_state.current_authorities.id {
		&trusted_state.current_authorities
	} else if commitment.validator_set_id == trusted_state.next_authorities.id {
		&trusted_state.next_authorities
	} else {
		return Err(Error::UnknownAuthoritySet { id: commitment.validator_set_id });
	};

	if !check_participation_threshold(signatures_length as u32, authority_set.len) {
		return Err(Error::SuperMajorityRequired);
	}

fn verify_validator_membership(
	validator_set: &ValidatorSet,
	participants: &[BlsPublicKey],
) -> Result<(), Error> {
	let deduped: alloc::collections::BTreeSet<&[u8]> =
		participants.iter().map(|k| k.as_ref()).collect();
	if deduped.len() != participants.len() {
		return Err(Error::DuplicateParticipant);
	}
	if let Some(key) = participants.iter().find(|key| !validator_set.contains(key)) {
		return Err(Error::UnknownValidator { key: key.clone() });
	}
	Ok(())
}
