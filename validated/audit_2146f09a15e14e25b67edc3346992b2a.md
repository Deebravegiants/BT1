### Title
Webhook `shop`/`topic`/`webhook_id` headers are not bound to the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Registry.process` verifies the HMAC over the body alone and then dispatches the handler with the unverified header values, breaking the intended binding between "bytes cryptographically verified" and "bytes the handler acts on."

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
while `shop`, `topic`, and `webhook_id` are pulled straight from headers with no cryptographic coverage: [2](#0-1) 

`HmacValidator.validate` computes the signature exclusively over `to_signable_string` (i.e., the raw body): [3](#0-2) 

`Registry.process` calls only this body-based HMAC check, then builds `WebhookMetadata` from the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

The identity binding that should hold is: `bytes verified by HMAC == bytes the handler is told belong to a given shop/topic`. In this implementation that equality does not hold — only the body is verified, while the shop/topic/webhook-id attribution is taken on faith from headers.

### Impact Explanation
Any holder of one legitimately-signed (body, HMAC) pair for the app — e.g., a merchant who installed the app on their own store and observed a genuine webhook call to their own endpoint — can replay that exact body and HMAC header to the app's public webhook endpoint while substituting a different `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header. `HmacValidator.validate` will still pass because it only checks the body against the signature. The app's registered handler then receives `WebhookMetadata` claiming the data belongs to a different shop, which — depending on how the consuming application keys sessions/data off `WebhookMetadata#shop` — can lead to cross-tenant data confusion (e.g., writing/deleting data attributed to the wrong merchant, or triggering privileged app-uninstall/GDPR handlers for an arbitrary shop).

### Likelihood Explanation
This matches the documented Shopify webhook signing scheme (only the request body is HMAC-signed; header values are conventionally trusted because the platform is assumed to be the only sender). The exploit path is reachable by any unprivileged internet user who runs the app on their own store and can capture one valid webhook delivery — no `api_secret_key`, access token, or TLS interception is required. However, real-world exploitability is conditional on the consuming application actually trusting `WebhookMetadata#shop`/`#topic` for per-tenant authorization or routing without any additional verification, which is the documented/intended usage pattern of this API.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the signed payload verification path (e.g., include them in `to_signable_string`, or independently verify that the `shop` header corresponds to a shop for which the topic/webhook subscription was registered) so that the HMAC check covers everything the handler relies on, not just the raw body.

### Proof of Concept
1. Merchant A installs the app on `a.myshopify.com` and captures a genuine webhook delivery to their own endpoint: raw body `{"id":123}` with header `x-shopify-hmac-sha256: <valid-for-body>`.
2. Merchant A sends a forged POST to the app's public webhook route with the same body/HMAC but headers rewritten:
   - `x-shopify-shop-domain: b.myshopify.com` (victim shop)
   - `x-shopify-topic: app/uninstalled`
3. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) calls `Utils::HmacValidator.validate(request)`, which succeeds because only the (unchanged) body is checked.
4. The app's handler executes as if shop `b.myshopify.com` sent an `app/uninstalled` event, even though it never did.
