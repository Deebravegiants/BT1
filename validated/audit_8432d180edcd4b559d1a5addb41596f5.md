### Title
IntentGatewayV2 sweeps the shared CallDispatcher's *entire* balance instead of the amount it actually produced - (File: evm/src/apps/IntentGatewayV2.sol / evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`placeOrder`'s predispatch branch and `_execute`'s output-call sweep both read the **current total balance** of the single, globally-shared `CallDispatcher` contract (`IERC20(token).balanceOf(dispatcher)` / `dispatcher.balance`) and treat that whole amount as the proceeds of the current caller's dispatch, exactly like `EFLeverVault` trusted its own manipulable `address(this).balance` as the true flashloan-callback deposit amount.

### Finding Description
`_params.dispatcher` is one shared `CallDispatcher` instance for the entire gateway [1](#0-0) . In `placeOrder`, after the user-supplied `order.predispatch.call` is executed on the dispatcher, the code computes the sweep amount from `IERC20(token).balanceOf(dispatcher)` / `address(dispatcher).balance` — the dispatcher's *total* current balance, not the delta produced by this specific call — and sweeps that whole amount to the gateway: [2](#0-1) 
The same pattern recurs in `_execute`, used on every order fill with output calldata: it sweeps `dispatcher.balance` / `IERC20(token).balanceOf(dispatcher)` in full, again reading the shared contract's raw balance as ground truth: [3](#0-2) 

Because `CallDispatcher` is a single shared, publicly payable/ERC20-receivable contract used concurrently by unrelated `placeOrder`/fill calls (and its `dispatch` executes fully attacker-controlled `Call[]` data), any balance left on it — from a prior order's unswept dust, a partially-consumed predispatch/output call, or tokens/ETH sent to it directly by a third party — gets attributed to whichever order's sweep logic runs next. This is the same root-cause class as `EFLeverVault`: accounting decisions are derived from a shared/external contract's raw balance rather than from a verified, isolated per-call delta, so the value is manipulable by any party able to move funds to that shared address before the sweep executes.

### Impact Explanation
An attacker can donate tokens/ETH directly to the shared `CallDispatcher` (its `receive()` is unguarded) or race a legitimate order whose predispatch/output call leaves residual balance, then place their own low-value order immediately after. The sweep logic pulls the *entire* dispatcher balance — including funds that belong to someone else's in-flight or prior operation — into the attacker's `placeOrder` flow, where it is either credited toward `order.inputs[i].amount` (up to `requiredAmount`, i.e. the attacker gets escrow credit they didn't actually pay for) or logged as "dust" retained by the protocol at the expense of whoever the funds actually belonged to. This can misappropriate other users'/solvers' escrowed or transiting funds (unauthorized crediting of escrow, effectively unbacked order funding) — a direct fund-diversion path from a single `placeOrder`/fill transaction.

### Likelihood Explanation
High reachability: `placeOrder` and order fills with output calldata are the primary, permissionless, unprivileged entry points of `IntentGatewayV2`, callable by any user with a predispatch/output call and no special privileges. The shared dispatcher address is a fixed, known, publicly fundable contract, so triggering the race (donate then immediately call `placeOrder`/fill) requires only ordinary transaction ordering/timing, no special access.

### Recommendation
Track the dispatcher's balance immediately before dispatching the predispatch/output call and sweep only the **delta** produced by that specific dispatch (`balanceAfter - balanceBefore`), mirroring the non-predispatch branch's `balBefore`/`balanceOf(address(this))` pattern already used elsewhere in `placeOrder`. Alternatively, deploy a fresh, single-use dispatcher per order/fill (e.g., via CREATE2 keyed on the commitment) so no cross-order balance can ever be attributed to the wrong caller.

### Proof of Concept
1. Attacker sends 1 wei (or 1 unit of the input token) directly to the shared `CallDispatcher` address, or front-runs a pending `placeOrder` whose predispatch call under-consumes its transferred tokens, leaving residual balance `X` on the dispatcher.
2. Attacker calls `placeOrder` with `order.predispatch.call` set to a no-op/self-call and `order.inputs[i].amount = X` (or less).
3. In `placeOrder`, `balance = IERC20(token).balanceOf(dispatcher)` reads the *combined* balance (their own tiny transfer plus the pre-existing `X`), passes the `balance >= requiredAmount` check, and the full `balance` is swept to `address(this)`.
4. `order.inputs[i].amount` is set/credited using this inflated `received` value, crediting the attacker's order with funds they never actually transferred from their own account.
