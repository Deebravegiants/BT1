### Title
Webhook shop-domain identity not covered by HMAC allows cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `Utils::HmacValidator` validates the HMAC over that body alone. The `X-Shopify-Shop-Domain` header (`request.shop`) is never included in the signed material, yet `Registry.process` trusts `request.shop` verbatim and hands it to the app's handler via `WebhookMetadata`. This breaks the binding "shop authenticated == shop the webhook body is attributed to."

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which is exactly `@raw_body`, excluding the `shop`, `topic`, and `webhook-id` headers.

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` against `verifiable_query.hmac`: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (parsed straight from the unauthenticated header) to build `WebhookMetadata`, with no additional binding check that the shop is the one that actually owns/registered that webhook: [3](#0-2) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cross-check against the HMAC-protected body: [4](#0-3) 

Because the HMAC key (`api_secret_key`) and message (body only) are identical across every shop that has installed the same app, two different shops receiving webhooks with an identical body (e.g., an empty-body/`{}` topic, or any topic whose payload happens to be identical) produce the **identical** valid HMAC. An unprivileged attacker who legitimately installs the app on their own shop can capture a genuine `(body, hmac)` pair delivered to their own webhook endpoint, then replay that exact body and HMAC to the target app's webhook endpoint while spoofing the `X-Shopify-Shop-Domain` header to a victim shop's domain. `HmacValidator.validate` will pass (it never looked at the shop header), and `Registry.process` will invoke the app's handler believing the event originated from the victim shop.

The equality that should hold: `shop asserted in headers == shop cryptographically bound by the HMAC`. In this code it is: `shop asserted in headers != anything covered by the HMAC` — the header is fully attacker-controlled.

### Impact Explanation
This qualifies as cross-tenant access (Critical): an attacker with no access token, no `client_secret`, and no privileged relationship to the victim shop can cause the app to process a forged webhook event under the victim shop's identity. Depending on the handler's logic (e.g., `app/uninstalled`, subscription/billing state changes, GDPR compliance webhooks), this can corrupt or leak victim-tenant state, trigger unauthorized actions attributed to the victim shop, or desynchronize per-shop app state — all without any credential belonging to the victim.

### Likelihood Explanation
Likelihood is bounded by the attacker's need for a body that is identical (or attacker-influenceable to be identical) across shops. Many Shopify webhook topics carry shop-specific IDs in the body, which would make direct replay produce a mismatched but still-valid HMAC (the HMAC would validate for *some* body, but the body content itself, not the shop, decides what data is delivered — so the attacker is really replaying their own event data under the victim's name, which is still a cross-tenant integrity violation, not merely a no-op). Topics with sparse or attacker-controllable/predictable bodies (e.g., simple lifecycle webhooks) make this trivial. The attacker only needs to be a legitimate (if minimal) installer of the app on any shop, which is achievable by any unprivileged internet user for public apps.

### Recommendation
Bind the shop identity into the signed material actually verified, or cross-check `request.shop` against an independent trust anchor before invoking the handler:
- Include `shop`, `topic`, and `webhook_id` in the value verified by `HmacValidator` (this changes wire compatibility with Shopify's signing scheme, so alternatively):
- After HMAC validation, require callers/`Registry.process` to verify `request.shop` corresponds to a shop with an active, stored session/installation for this app (i.e., reject webhooks for shops that are not known/installed), closing the spoofing window even though the body-only HMAC is Shopify's own scheme.
- Document explicitly in `docs/usage/webhooks.md` that consumers MUST independently validate `data.shop` against their own installed-shop registry before trusting it, since the underlying HMAC does not cover it.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (any unprivileged internet user can install a public app).
2. Shopify sends a webhook (e.g. topic with an empty/near-empty body such as `{}`) to the attacker's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`.
3. Attacker captures `raw_body` and `X-Shopify-Hmac-Sha256`.
4. Attacker POSTs the exact same `raw_body` and `X-Shopify-Hmac-Sha256` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate`, which recomputes the HMAC over `raw_body` only — identical to the captured value — and passes.
6. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, i.e., the app believes this event genuinely originated from the victim shop, though it did not.
