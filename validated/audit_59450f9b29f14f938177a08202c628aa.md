Based on the investigation, the closest analog to the Pixelswap `pair_id`/`token_id` cross-validation bug — where two logically-linked fields are combined without validating that they actually correspond to the same authorized transaction — is in orb-core's signup-extension QR handling, where the orb picks between the *user's own* QR-supplied configuration and the *operator's* QR-supplied configuration without validating that they match, giving priority to the (lower-trust) user-supplied value.

### Title
Unvalidated correspondence between operator- and user-supplied `SignupExtensionConfig` allows a scanned user QR code to dictate arbitrary biometric-acquisition parameters - (File: src/plans/mod.rs)

### Summary
Similar to the Pixelswap issue where `PlaceOrder` trusted an attacker-supplied `token_id`/`pair_id` combination without validating they correspond to the same legitimate transaction, orb-core's `handle_user_qr_code` combines the operator's and the user's `signup_extension_config` fields with a simple `.or()` fallback that prefers the user-scanned value, without ever validating that the user-supplied `mode`/`parameters` correspond to (or are authorized by) the operator's config for that session.

### Finding Description
When both the operator QR code and the user QR code indicate `signup_extension()`, the orb selects the effective `SignupExtensionConfig` as follows: [1](#0-0) 
```
user_qr_code.signup_extension_config.as_ref().or(operator_data.qr_code.signup_extension_config.as_ref())
```
This means whenever the user-controlled QR string parses to a `Some(SignupExtensionConfig)`, that value — including `mode` and `parameters` — takes precedence, with no check that it matches what the operator authorized. The `mode`/`parameters` fields are parsed straight out of the free-form scanned string via `QR_CODE_SIGNUP_EXTENSION` regex and `SignupMode::parse`, both fully attacker-controlled inputs: [2](#0-1) [3](#0-2) 

The two configs (operator's and user's) are conceptually the "pair_id" and "token_id" of the original bug: only one entity (the operator) is supposed to authorize which acquisition mode/parameters are used, yet the code never cross-validates that the user-derived config equals or is consistent with the operator-derived one — it silently substitutes the user's value.

### Impact Explanation
`SignupMode` selects which biometric capture procedure runs (`PupilContractionExtension`, `MultiWavelengthExtension`, `Overcapture`, etc.), each of which changes what and how much biometric data is captured/stored, as seen in the capture-mode dispatch code referencing `signup_extension_config` in `src/plans/biometric_capture/mod.rs`, `focus_sweep.rs`, `mirror_sweep.rs`, and `overcapture.rs`. Because the user-scanned code can inject arbitrary `mode`/`parameters` values that override the operator's intended configuration, an unprivileged actor holding/printing a crafted QR code could force the orb into a data-acquisition mode not authorized by the operator, causing over-collection or mismatched biometric data acquisition/retention outside the operator-approved config.

### Likelihood Explanation
This path is only compiled under the `internal-data-acquisition` feature flag, so it is not part of the default consumer signup build; it is used for internal/research data-collection configurations. Within that build, the fallback logic is directly reachable by anyone able to present a crafted user QR code during a research signup session, requiring no privilege beyond being the unprivileged signup subject.

### Recommendation
- Short term: Validate that `user_qr_code.signup_extension_config` matches (or is a subset permitted by) `operator_data.qr_code.signup_extension_config` before using it; reject the signup extension flow on mismatch rather than silently preferring the user-supplied value.
- Long term: Treat the operator's QR code as the sole source of authorization for acquisition mode and parameters, using the user QR code only for `user_id`/consent-hash fields, consistent with the general principle of validating that all related identifiers/configs used in the same operation are mutually consistent.

### Proof of Concept
1. Build with `internal-data-acquisition` enabled.
2. As the user, present an operator QR code with `signup_extension` enabled and a benign config (e.g. `mode=Basic`).
3. Present a crafted user QR code string matching `QR_CODE_SIGNUP_EXTENSION` with `mode=Overcapture` and attacker-chosen `parameters`.
4. Observe in `handle_user_qr_code` (`src/plans/mod.rs:1060-1073`) that the user-supplied `Overcapture` config is selected over the operator's `Basic` config because of the `.or()` fallback, driving the biometric capture plan (`src/plans/biometric_capture/overcapture.rs`) with attacker-chosen parameters instead of the operator-authorized ones.

#[cfg(feature = "internal-data-acquisition")]
impl SignupMode {
    /// Parse SignupMode enum from string
    fn parse(mode: Option<&str>) -> Option<Self> {
        if let Some(mode) = mode {
            let val = u8::from_str_radix(mode, 16).ok()?;
            let mode = match val {
                0 => Self::Basic,
                1 => Self::PupilContractionExtension,
                2 => Self::FocusSweepExtension,
                3 => Self::MirrorSweepExtension,
                4 => Self::MultiWavelength,
                5 => Self::Overcapture,
                _ => return None,
            };
            tracing::warn!("Parsed signup mode {:?} from QR code - signup flow modified!", mode);
            Some(mode)
        } else {
            None
        }
    }
