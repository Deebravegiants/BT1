The `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop` is read from the `shopify-shop-domain` header, entirely outside the HMAC signature [2](#0-1) . `Registry.process` validates the HMAC over the request (i.e., over the body only) and then trusts `request.shop` to build `WebhookMetadata` dispatched to the app's handler [3](#0-2) .

### Title
Webhook tenant identity (`shop` domain) is not covered by the HMAC signature, allowing cross-tenant webhook forgery via body replay - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body alone, but resolves the tenant-identifying `shop` field from an unsigned HTTP header. `Registry.process` verifies the HMAC and then unconditionally trusts the header-derived `shop` to construct `WebhookMetadata` passed to the app's webhook handler. This breaks the identity binding: `shop` used to attribute/act on the payload != `shop` covered by the authenticated bytes.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` and HMAC-signs/compares that string using `Context.api_secret_key` [4](#0-3) . For webhook requests, `to_signable_string` is simply `@raw_body` [1](#0-0) . The `shop` accessor, however, is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header and is never included in the signed content [2](#0-1) .

Because the same `api_secret_key` (the app's `client_secret`) is used to sign every webhook sent to every shop that installs the app, any party who can obtain one genuine, validly-signed webhook delivery for *any* shop — trivially their own store, where they control the installed app and can trigger webhook events (e.g., `orders/create`) — possesses a `(raw_body, hmac)` pair that satisfies `HmacValidator.validate` regardless of which `shop-domain` header accompanies it. `Registry.process` validates the HMAC first, then immediately uses the (unsigned) `request.shop` to build the `WebhookMetadata` delivered to the app's handler [3](#0-2) .

An attacker can replay the captured body/HMAC pair to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop domain. `HmacValidator.validate` still returns true because it only checks the body, so `Registry.process` proceeds and invokes the handler with `shop: <victim-shop>` and `body: <attacker-controlled order data>`. Any host application logic that uses `WebhookMetadata#shop` as the tenant key (the intended and documented use of this field, per `docs/usage/webhooks.md`) will attribute attacker-supplied data to the victim tenant.

The equality the gem is supposed to guarantee is:
`shop bound by the authenticated bytes == shop the handler acts on`
but the gem instead delivers:
`shop bound by the authenticated bytes (none) != shop the handler acts on (attacker-controlled header)`

### Impact Explanation
This is a cross-tenant data-injection primitive: an attacker with a legitimate installation of the same app in their own store can forge a webhook delivery that the receiving app will process as belonging to a victim shop, since the shop identity is never covered by the cryptographic signature the gem verifies. This matches the High-severity "cross-tenant access" category, since the confidentiality/integrity boundary between merchant tenants is broken purely through this gem's own verification logic (`Utils::HmacValidator` + `Webhooks::Request`), with no access token, TLS interception, or social engineering required — only the ability to trigger one authentic webhook to the attacker's own shop and then replay it with a modified header.

### Likelihood Explanation
Likelihood is high for any app that installs across multiple untrusted merchants (the standard Shopify app-store model): every installer already has the ability to generate a validly-HMAC'd webhook body for their own shop and can immediately attempt cross-tenant replay against the shared endpoint.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook-id`) into the signed material, or independently verify the `shop-domain` header against a value tied to the signature — e.g., include the shop domain header in the HMAC computation, matching how `Auth::Oauth::AuthQuery#to_signable_string` incorporates `shop` into its signable string [5](#0-4) . Practically, since Shopify's actual webhook HMAC is computed server-side over the raw body only (this is Shopify's documented webhook signing scheme), the gem/consuming app should validate that the delivered `shop-domain` corresponds to an app installation the app has itself created/tracks (e.g. cross-check against stored sessions/webhook subscriptions) rather than trusting the header value on its own for tenant attribution.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body `B` and the `X-Shopify-Hmac-Sha256` header value `H` sent by Shopify (valid because `HMAC(client_secret, B) == H`).
2. Attacker crafts `B` to contain attacker-chosen order/customer data (they fully control their own store's data, so `B` can be shaped as desired).
3. Attacker sends the app's webhook endpoint a POST with body `B`, header `X-Shopify-Hmac-Sha256: H` (unchanged), but header `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Request.new` parses headers/body normally [6](#0-5) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [7](#0-6) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker-controlled parsed body>, ...)`, causing the app to process attacker-controlled data under the victim's tenant identity.
