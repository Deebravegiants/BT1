### Title
Webhook `shop` (and `topic`/`webhook_id`) header is not covered by the HMAC signature, allowing tenant impersonation in `Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC verification performed by `Utils::HmacValidator.validate` never covers the `shopify-shop-domain`, `shopify-topic`, or `shopify-webhook-id` headers. `Webhooks::Registry.process` nevertheless trusts these unauthenticated header values (in particular `request.shop`) and forwards them straight into `WebhookMetadata`, which is handed to the app's handler as the tenant identity for the event.

### Finding Description
The identity binding that should hold is:

`shop value cryptographically bound by the HMAC` == `shop value the handler acts on`

but the code produces:

`shop value NEVER covered by HMAC` -> `shop value the handler acts on`

`Request#to_signable_string` is defined as:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

and `HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string`, i.e. the raw body, using the app's `client_secret`: [2](#0-1) 

`request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` are all read straight from HTTP headers with no cryptographic binding to the body or to the HMAC: [3](#0-2) 

`Registry.process` validates only the body-derived HMAC, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id` to build the `WebhookMetadata` passed to the handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

Because the body and the shop-identifying header are verified/parsed independently — the HMAC check proves "this body was signed by our secret" but proves nothing about which shop sent it — any request whose body+hmac pair was legitimately produced for one shop (e.g. the attacker's own store, which they can freely install the app on and receive real signed webhooks for) can be replayed against the app's webhook endpoint with the `shopify-shop-domain` header swapped to a victim shop. The library's HMAC check still passes, and `Registry.process` hands the handler a `WebhookMetadata` claiming the event belongs to the victim shop.

### Impact Explanation
This crosses a tenant boundary using only the app's own valid webhook traffic that any merchant can trigger for their own store: the attacker never needs the `client_secret`, an access token, or any privileged credential, yet can make the app process/act on webhook data (e.g. `customers/data_request`, `shop/redact`, order/customer webhooks) under an arbitrary victim shop identity. Any host application that keys tenant-scoped actions (data lookups, redaction, session/token selection) off `WebhookMetadata#shop` as delivered by this gem is exposed to cross-tenant data access or corruption — meeting the Critical "cross-tenant access" bar.

### Likelihood Explanation
Likelihood is Low/Moderate: it requires the attacker to install the target app on a shop they control (readily achievable for any public app) and to intercept/replay one legitimately delivered webhook while modifying only the `shopify-shop-domain` (and optionally `shopify-topic`/`shopify-webhook-id`) header — no signature forgery or secret is needed since those fields are outside the signed data.

### Recommendation
Bind the shop (and ideally topic/webhook_id) to the HMAC verification, not just the raw body — e.g. include `shop`, `topic`, and `webhook_id` in the signable string, or independently verify the shop domain against a value already established for that merchant (installed shop list / stored session) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; Shopify delivers a legitimately signed webhook (e.g. `orders/create`) with body `B` and header `shopify-hmac-sha256: H = HMAC(client_secret, B)`.
2. Attacker replays the same `B`/`H` to the app's webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `@raw_body` only — matches `H`, validation succeeds.
5. `Registry.process` builds `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: parsed_body, ...)` and invokes the app's handler, which now believes this event/body originated from `victim-shop.myshopify.com`. [5](#0-4) [6](#0-5)
