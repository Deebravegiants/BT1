### Title
Truncating decimal-scaling division in `pallet-hyper-fungible-token`'s `on_accept`/`on_timeout` permanently burns dust-sized cross-chain transfers - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`pallet-hyper-fungible-token` scales ERC20-denominated amounts down to the local substrate asset's decimals by integer division in `convert_to_balance`. When the incoming ERC20 amount is smaller than `10^(erc_decimals - local_decimals)`, the division truncates to zero. The pallet does not check for this and proceeds to credit the beneficiary with `0` tokens while treating the message as successfully processed, so the tokens the user already burned/escrowed on the EVM side are permanently lost with no refund path.

### Finding Description
`convert_to_balance` performs a plain integer division to rescale an ERC20 `U256` amount down to the local asset's precision: [1](#0-0) 

This is called unconditionally in `on_accept` (message delivery from an EVM peer) and in `on_timeout` (refund path), with no floor/minimum check on the result: [2](#0-1) 

The resulting `amount` (which can be `0`) is then unconditionally minted or transferred to the beneficiary, and the message is treated as successfully accepted — there is no revert or rejection path for a zero-value delivery: [3](#0-2) 

The decimals mismatch this is meant to bridge is real and documented: `BridgeToken.sol` (an `HyperFungibleToken` deployment) explicitly states its EVM-side `decimals()` is 18 while the native pallet balance on nexus is 12, "so the pallet scales by 10^6 in both directions": [4](#0-3) 

Critically, the EVM side (`HyperFungibleToken.sol`) performs **no** decimal scaling on its own `send`/`onAccept` path — it burns/mints the raw `params.amount`/`message.amount` verbatim: [5](#0-4) 

So any user who calls `send()` on an EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` contract targeting a substrate destination with fewer decimals, and whose `amount` is smaller than `10^(erc_decimals - local_decimals)` (e.g., smaller than `10^6` wei for the documented BRIDGE token), will have their tokens burned on the EVM chain. When the message is delivered on the substrate side, `convert_to_balance` computes `amount = 0`, and the pallet happily "mints"/"transfers" zero tokens to the beneficiary, emitting `TokenReceived { amount: 0, .. }` as if the transfer succeeded. The burned EVM tokens are never recovered — there is no timeout (the message was accepted, not timed out) and no recovery mechanism.

The identical truncation issue exists in the `on_timeout` refund path: if a message times out, the refunded amount is recomputed via the same `convert_to_balance`, so a dust-sized transfer that times out would also refund `0`, compounding the loss.

This is the same bug class as the external report: an unbacked-scaling bug in a cross-chain token bridge where sub-minimum-denomination amounts get silently rounded to zero on the receiving side after the sender has already had funds locked/burned on the sending side, resulting in permanent, non-recoverable loss of funds.

### Impact Explanation
Any unprivileged user (or a relayer replaying/forwarding a legitimately signed but dust-sized transfer) can trigger permanent loss of the sender's bridged funds: tokens are burned/escrowed on the source chain, but zero tokens are credited on the destination chain, and the ISMP message is marked as successfully processed (not timed out), so there is no automatic refund path. This is a permanent freezing/loss-of-funds condition, matching the "concrete theft or permanent freezing of funds" acceptance criterion. While the per-incident amount is small (bounded by the decimals gap, e.g. up to `10^6 - 1` wei ≈ negligible fractions of a token for the documented 18-vs-12-decimal BRIDGE token), it applies to every asset pair registered through `register_token`/`update_token`, and a larger decimals gap (e.g., an 18-decimal EVM token bridged to a 6-decimal local asset, gap of `10^12`) makes the "dust" threshold far larger and the potential loss per transaction far more significant.

### Likelihood Explanation
Likelihood is moderate: any legitimate user (or automated integration/wallet) that computes amounts imprecisely, rounds, or intentionally probes with a small "test" transfer before bridging is naturally exposed, since the EVM contracts perform no client-side or on-chain minimum-amount validation and accept any nonzero `amount`. The pallet's `send()` extrinsic also has no minimum-amount check on the substrate-to-EVM direction (though that direction is not vulnerable to truncation since it scales up), but for the EVM-to-substrate direction (or between any two chains where the destination's local decimals are lower than the registered ERC decimals), any transfer under the scale factor triggers the bug deterministically and silently.

### Recommendation
In `convert_to_balance` (or its callers in `on_accept`/`on_timeout`), reject conversions that would truncate to zero when the input value is nonzero — return an error (e.g. `Error::<T>::AmountBelowMinimumDenomination`) instead of silently continuing with `amount = 0`. Additionally, consider enforcing a minimum sendable amount on the EVM `HyperFungibleToken`/`WrappedHyperFungibleToken` `send()` function by having it aware of (or querying) the destination's registered decimals/scale factor, so transfers smaller than the minimum representable unit on the destination revert before tokens are burned/escrowed on the source chain.

### Proof of Concept
1. Register a token via `register_token` with `native = false` (or use the native `BridgeToken` case) where the destination chain's `Precisions` entry records `erc_decimals = 18` and the local asset's decimals are `12` (a `10^6` scale gap), as documented in `evm/src/apps/BridgeToken.sol`.
2. On the EVM chain, a user calls `BridgeToken.send({ dest: nexus, to: recipient, amount: 500_000, ... })` (`500_000 < 10^6`). `HyperFungibleToken.send` burns `500_000` wei from the caller and dispatches an ISMP POST with `message.amount = 500_000` — no scaling occurs on the EVM side (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol:264-282`).
3. The message is delivered to `pallet-hyper-fungible-token::on_accept` on nexus. `erc_decimals = 18`, `decimals = 12`, so `convert_to_balance(500_000, 18, 12)` computes `500_000 / 10^6 = 0` (`modules/pallets/hyper-fungible-token/src/impls.rs:43-52`).
4. `on_accept` proceeds to transfer/mint `amount = 0` to the beneficiary and emits `TokenReceived { amount: 0 }` (`modules/pallets/hyper-fungible-token/src/module.rs:93-117`), without erroring.
5. Result: the user's `500_000` wei were burned on the EVM chain in step 2, but the beneficiary received `0` tokens on nexus in step 4. The funds are permanently lost with no revert, no timeout, and no recovery mechanism.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
