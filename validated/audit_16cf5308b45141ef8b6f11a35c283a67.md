### Title
Excess Native `msg.value` Sent To `EvmHost.dispatch()`/`fundRequest()` Is Permanently Stuck In The Contract - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` are all `payable` and forward the caller's entire `msg.value` to a Uniswap V2 (or wrapper) router via `swapETHForExactTokens{value: msg.value}(fee, ...)`. Any ETH left over after the swap is refunded by the router to its immediate caller — which is `EvmHost` itself, not the original end user. Because there is no unprivileged withdrawal path for this leftover ETH, any overpayment of native token by a user or app dispatching a message becomes permanently stuck in `EvmHost`.

In all three cases the entire `msg.value` is forwarded to the router (`amountInMax` is effectively `msg.value`, not the exact quoted amount), and only `post.fee`/`get.fee`/`amount` worth of `feeToken` is actually needed. When the configured router is the standard Uniswap V2 router, `swapETHForExactTokens` refunds unspent ETH to `msg.sender` — and since `EvmHost` itself calls the router, `msg.sender` in that context is the `EvmHost` contract address, not the original transaction sender (`_msgSender()`). The same refund-to-caller behavior is reproduced explicitly in the project's own router-compatible wrapper: [4](#0-3) 

`EvmHost` never captures or forwards this refund back to `_msgSender()`. Unlike `IntentGatewayV2`/`ExtrinsicIntents`, which explicitly track `msgValue` and refund unspent native tokens to the caller at the end of execution (e.g. `_sendValue(msg.sender, msgValue)` in `ExtrinsicIntents._fillCrossChain`), `EvmHost.dispatch`/`fundRequest` have no such refund logic: [5](#0-4) 

Once the ETH is refunded into `EvmHost`, the only sanctioned exit for native token is `withdraw()`, restricted to the privileged `hostManager` role (`IHostManager.withdraw`), which is not something the overpaying end user can invoke: [6](#0-5) 

### Impact Explanation
Any unprivileged party dispatching a POST/GET request through `EvmHost.dispatch()` (directly or via any `IApp`/gateway forwarding `msg.value`, e.g. `IntentGatewayV2`, `HyperFungibleToken.send`, `HyperbridgeLzEndpoint.send`) or calling `fundRequest()` with native token and slightly overpaying (common, since `quote()` is explicitly documented as unsafe to call on-chain due to sandwich-attack risk, so callers pad the sent value) will have the surplus native token permanently trapped in `EvmHost`. This is a direct, unrecoverable loss of user funds — a concrete freezing-of-funds impact reachable from a single unprivileged dispatch transaction.

### Likelihood Explanation
Very likely to occur in normal operation: the docs explicitly instruct developers to estimate fees off-chain (subject to slippage/sandwiching) and send `msg.value` with margin, and multiple production contracts (`IntentGatewayV2`, `HyperFungibleToken`/`WrappedHyperFungibleToken`, `HyperbridgeLzEndpoint`) forward arbitrary user-supplied `msg.value` straight into `EvmHost.dispatch`. Any deviation between quoted and actual on-chain swap price (due to normal price movement between quote and execution, or minor overestimation for safety) triggers the stuck-refund path.

### Recommendation
Track the actual ETH spent by the swap and refund any leftover to `_msgSender()` (not swallow it into `EvmHost` balance), mirroring the pattern already used in `ExtrinsicIntents._fillCrossChain`:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
uint256 spent = amounts[0];
if (msg.value > spent) {
    (bool success, ) = _msgSender().call{value: msg.value - spent}("");
    require(success, "refund failed");
}
```
Apply the same fix to `dispatch(DispatchGet)` and `fundRequest()`.

### Proof of Concept
1. User calls `EvmHost.dispatch{value: 1 ether}(post)` where `post.fee` only requires `0.5 ETH` worth of `feeToken` at current price.
2. `EvmHost` calls `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: 1 ether}(post.fee, path, address(this), block.timestamp)`.
3. The router spends only the ETH needed (e.g. `0.5 ETH`) and refunds the remaining `0.5 ETH` to `msg.sender` of that call, i.e. the `EvmHost` contract address (see `UniV3UniswapV2Wrapper.swapETHForExactTokens`, line 147: `msg.sender.call{value: refund}("")`).
4. `EvmHost.dispatch` returns without ever inspecting or forwarding this refund; the `0.5 ETH` now sits in `EvmHost`'s balance.
5. The original user has no function to reclaim it; only the privileged `hostManager` can call `withdraw()` to move native balance out of `EvmHost`.
