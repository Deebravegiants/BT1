Confirmed: the webhook HMAC (`Utils::HmacValidator.validate`) validates only against `to_signable_string`, which for `ShopifyAPI::Webhooks::Request` is the raw body [1](#0-0) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from unauthenticated HTTP headers [2](#0-1) , and `Registry.process` trusts `request.shop` (header value) as the tenant identity that gets forwarded to the handler once the body's HMAC checks out [3](#0-2) . The HMAC computation itself is `HMAC-SHA256(api_secret_key, raw_body)`, with the secret being the app's single `api_secret_key` shared across every shop that has installed the app [4](#0-3) .

### Title
Webhook shop-domain identity is not bound by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature Shopify sends with a webhook authenticates *body content* but never binds it to the `shop` (or `topic`/`webhook_id`) header. Since the same `api_secret_key` is used to sign webhooks for every shop that has installed a given app, a low-privileged attacker who has their own shop installed on the app can capture a legitimately-signed webhook (body + valid HMAC) from their own store and replay it against the app's public webhook endpoint with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` will still succeed because it only checks the body signature, and `Registry.process` will then dispatch the (attacker-controlled) payload to the app's handler tagged with the victim shop's identity via `WebhookMetadata.new(... shop: request.shop ...)`.

### Finding Description
The identity binding that should hold is:
`shop_the_HMAC_authenticates == shop_the_handler_acts_on`

In this gem it does not: the HMAC only authenticates `raw_body` [1](#0-0) , while `shop` is read unauthenticated from the header [5](#0-4) . `Registry.process` validates the HMAC, then unconditionally trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` passed to the app's handler [3](#0-2) . Because `api_secret_key` is the app-wide secret (not per-shop), any account that can install the app — including an attacker's own low-privilege store — can generate arbitrarily many validly-signed `(body, hmac)` pairs. Replaying one such pair with a forged `shop-domain` header produces a request that passes `HmacValidator.validate` yet is attributed to a shop the attacker does not control.

### Impact Explanation
This breaks the tenant boundary the gem is meant to enforce for webhook processing: an unprivileged installer of the app can make the app process attacker-chosen webhook bodies as if they originated from an arbitrary other shop, corrupting per-tenant application state, redaction/GDPR handling, or any business logic keyed off `WebhookMetadata#shop`. This matches the cross-tenant access impact category.

### Likelihood Explanation
Any actor able to install the (presumably public) app on a shop they control can trivially trigger real webhooks for that shop, capture the body and its valid `X-Shopify-Hmac-Sha256` header, and POST it to the app's public webhook endpoint with a modified `X-Shopify-Shop-Domain` header. No secret, token, or elevated privilege is required beyond ordinary app installation.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the specific installation the signature was generated for (e.g., verify the shop against the session/access-token record associated with that HMAC, or require an additional per-shop secret/mac component) before trusting `request.shop` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtaining a real webhook delivery: body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for the app's shared `api_secret_key`).
2. Attacker POSTs to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this fine (all required headers present) [6](#0-5) ; `HmacValidator.validate` succeeds because it only recomputes the HMAC over `B` [7](#0-6) .
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the app to act on victim-shop's behalf using attacker-supplied data [3](#0-2) .

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

        sig { params(signable_string: String, secret: String).returns(String) }
        def compute_signature(signable_string, secret)
          OpenSSL::HMAC.hexdigest(
            OpenSSL::Digest.new("sha256"),
            secret,
            signable_string,
          )
        end
