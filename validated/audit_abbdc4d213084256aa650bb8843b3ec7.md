### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC-signed material solely from the raw request body, but the `shop` (tenant) attribute that the app uses to route/process the webhook is read from a separate, unsigned HTTP header. Any party that possesses one validly-HMAC'd webhook body (e.g. a merchant who installed the app and received their own legitimate webhook) can resend that same body/HMAC pair while substituting a different `X-Shopify-Shop-Domain` header, and `Utils::HmacValidator.validate` will still report success, because it only checks the body bytes, not the shop binding.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a completely separate header and never enters the signed material: [2](#0-1) 

`Utils::HmacValidator.validate`/`validate_signature` compute and compare the HMAC only over `verifiable_query.to_signable_string` (the raw body), never touching `shop`: [3](#0-2) 

`Registry#process` validates the HMAC and then immediately trusts `request.shop` — taken straight from the unsigned header — to build the `WebhookMetadata` that is handed to the app's handler as the tenant context: [4](#0-3) 

The identity binding that should hold is:
`hmac_valid(body) == true` **should imply** `shop_header == the shop that actually produced/owns that body`.
In this implementation, `hmac_valid(body)` only proves the body bytes are unmodified from *some* HMAC'd request Shopify sent for *some* shop; it proves nothing about which shop the body/header pair currently claims. An attacker can freely swap the `shop` header while keeping the original body+HMAC, and the check still passes — the same bug class as the report's "verified vs. parsed length mismatch": one thing is checked (body signature), a different thing is actually acted upon (shop-scoped routing).

### Impact Explanation
This crosses a tenant boundary using no elevated privilege: any user who can install the app on their own store (i.e., an ordinary merchant/unprivileged internet user with respect to *other* tenants) receives genuinely HMAC-signed webhooks for their own shop. By replaying the exact body+HMAC with a modified shop-domain header pointed at a victim shop, they can make the app process arbitrary attacker-chosen webhook content (`orders/create`, `app/uninstalled`, GDPR `shop/redact`, etc.) as if it belonged to the victim shop. Depending on how the host application keys its data/session logic off `WebhookMetadata#shop`, this enables cross-tenant data injection, cross-tenant data deletion, or corruption of another merchant's records — matching the "Critical: cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires no secrets: no `api_secret_key`, no access token, and no privileged account are needed — only a normal, unprivileged install of the app to obtain one legitimate HMAC'd payload, plus the ability to POST to the app's public webhook endpoint with a forged (but otherwise valid-format) `X-Shopify-Shop-Domain`/`X-Shopify-Topic` header, both of which are ordinary, attacker-controllable HTTP headers.

### Recommendation
Include the shop (and ideally topic) in the value that is HMAC-verified, or otherwise cryptographically bind them to the signed body, e.g. by validating the shop domain against the session/shop the webhook subscription was registered for, or by additionally verifying `shop` through an independent authenticated channel (mirroring Shopify's platform-side webhook shop verification) before trusting `request.shop` in `Registry#process`. At minimum, `Utils::VerifiableQuery`/`HmacValidator` should not be reused for headers that are excluded from the signed payload without an explicit, separate integrity check on those headers.

### Proof of Concept
1. Attacker installs the app for `attacker-shop.myshopify.com` and configures a webhook subscription (e.g. `orders/create`).
2. Shopify sends a legitimate webhook to the app's endpoint with body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B`), and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this request (they are the intended recipient, so no interception needed) and resends the identical body `B` and header `X-Shopify-Hmac-Sha256: H`, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` recomputes the HMAC over `B` only, matches `H`, and returns `true`.
5. `Registry#process` proceeds and calls the app's registered handler with `shop: "victim-shop.myshopify.com"`, `body: parsed(B)`, causing the app to process attacker-controlled data as though it originated from the victim's shop. [5](#0-4)
