## Title
Unbounded infinite loop in GRANDPA `AncestryChain::ancestry()` via attacker-crafted `parent_hash` cycles — permissionless consensus-proof DoS - (File: `modules/consensus/grandpa/primitives/src/justification.rs`)

### Summary
The reported `nuxt-api-party` bug is a DoS caused by attacker-controlled input (`retry`) driving an internal routine into unbounded, ever-growing work with no termination guard. The Hyperbridge GRANDPA consensus verifier contains an analogous unbounded-work primitive: `AncestryChain::ancestry()` walks a `parent_hash` chain supplied entirely by the (permissionless) proof submitter, with no cycle detection and no bound on the number of hops, so a proof whose headers form a `parent_hash` cycle causes the walk to loop forever.

### Finding Description
`AncestryChain::ancestry` in `modules/consensus/grandpa/primitives/src/justification.rs` (lines 176-198) is:

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}

`H::hash()` is computed from the header's *content* (including its `parent_hash` field, which is just opaque bytes chosen by the submitter). Nothing constrains `parent_hash` to point at an ancestor that is actually closer to `base`. An attacker can therefore submit two (or more) headers `H1`, `H2` where `H1.parent_hash = hash(H2)` and `H2.parent_hash = hash(H1)` — a closed cycle entirely contained in the submitted header set, disjoint from the real chain and from `base` (the trusted `consensus_state.latest_hash`).

When `ancestry()` walks from an attacker-chosen `block` hash into this cycle, `current_hash` will never equal `base` (a legitimate, previously verified trusted hash the attacker cannot produce without breaking the hash function) and will never be missing from the map (every hash in the cycle is present), so the `while` loop never terminates. `route` grows without bound each iteration, and the loop consumes CPU indefinitely.

This mirrors the reported bug class exactly: an externally reachable, permissionless entry point accepts a parameter (here, the header set/ancestry graph, analogous to `retry`) that drives an internal algorithm into unbounded work with no upper bound or cycle guard.

### Impact Explanation
This code path is exercised by `verify_grandpa_finality_proof`, which is the core of the GRANDPA `ConsensusClient::verify_consensus` implementation (`modules/ismp/clients/grandpa/src/consensus.rs`), invoked whenever a relayer submits a GRANDPA consensus proof to the ISMP consensus-update dispatch path. Any relayer — an unprivileged network participant — can submit such a proof. Triggering the infinite loop hangs the executing thread/task indefinitely and grows an unbounded `Vec`, denying service to the node processing the message (validator/collator or off-chain worker/tesseract relayer process), which can stall consensus-state updates for the affected GRANDPA-based counterparty chain. This matches the "route unable to deliver messages" / full DoS criteria required by the validation rules.

### Likelihood Explanation
Likelihood is high: constructing two headers with mutually-referencing `parent_hash` fields requires no privileged access, no valid signatures over the cyclic headers themselves (only the justification's precommit signatures need to be valid; the `votes_ancestries`/`unknown_headers` entries feeding `AncestryChain` are otherwise just SCALE-decoded blobs), and no special timing — a single crafted consensus-proof submission suffices.

### Recommendation
Bound the `ancestry()` walk by the number of entries in the ancestry map (e.g., `for _ in 0..=self.ancestry.len()`) and return `Error::NotDescendent` if the walk exceeds that bound instead of looping unconditionally on `current_hash != base`. This guarantees termination regardless of adversarial `parent_hash` cycles while preserving correct behavior for genuine ancestry chains.

### Proof of Concept
1. Craft two headers `H1`, `H2` with arbitrary content except:
   - `H1.parent_hash = Blake2Hash(H2)` (SCALE-encoded hash of `H2`)
   - `H2.parent_hash = Blake2Hash(H1)`
2. Include `H1`, `H2` in `finality_proof.unknown_headers` (and/or a justification's `votes_ancestries`) of a submitted `ConsensusMessage` for the GRANDPA consensus client, with `target = H1` (i.e., `finality_proof.block = H1.hash()`), and a validly-signed commit/justification targeting `H1` (only the signature over the commit needs to validate against the current authority set — the cyclic headers merely need to be internally consistent-looking hash preimages).
3. Submit this consensus proof through the normal permissionless consensus-update dispatch (`ConsensusClient::verify_consensus` → `verify_grandpa_finality_proof` → `AncestryChain::ancestry(from, target.hash())`).
4. Because `H1`/`H2` form a closed cycle disjoint from `from` (`consensus_state.latest_hash`), `ancestry()` never terminates, hanging the processing thread and growing `route` without bound — a live Denial of Service against the node handling the message.
