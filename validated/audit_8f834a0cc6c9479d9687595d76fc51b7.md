### Title
Webhook shop-domain spoofing via HMAC that only covers the body, not the shop header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` proves nothing more than "this body byte-for-byte was HMAC-signed with `api_secret_key`." It does not bind the signature to the `shop`, `topic`, `api-version`, or `webhook-id` headers that `Registry.process` subsequently trusts and forwards to the host application's handler as `WebhookMetadata`.

### Finding Description
The `api_secret_key` used to compute/verify webhook HMACs is a single per-app secret shared across every shop that installs the app — it is not per-tenant. `HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received HMAC [3](#0-2) . For webhooks, `to_signable_string` is defined as just `@raw_body` [2](#0-1) ; the `shop`, `topic`, `webhook_id`, and `api_version` accessors all read directly from attacker-controllable HTTP headers with no cryptographic binding to the signed body [4](#0-3) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler with the header-derived, unauthenticated `shop` value baked into `WebhookMetadata` [1](#0-0) ; `WebhookMetadata#shop` is a plain `String` const with no further verification [5](#0-4) .

Equality that should hold but doesn't:
- Expected: `shop header bound in HMAC == shop header trusted by handler`
- Actual: `shop header trusted by handler` is fully attacker-controlled and independent of the HMAC, which only authenticates `raw_body`.

Because the secret is shared across all tenants of the app, a merchant who has legitimately installed the app (or anyone who can otherwise obtain one valid `(body, hmac)` pair emitted by Shopify for that app, e.g. by installing a free/trial version of the target app on their own store) can replay that exact body+HMAC pair to the app's webhook endpoint while substituting a victim's `X-Shopify-Shop-Domain` (and, for apps that branch on topic, `X-Shopify-Topic`) header. The signature still validates because the body is unchanged, but `Registry.process` hands the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` to select which tenant's data to write/mutate (a standard and encouraged pattern per this library's own docs) can be made to apply an attacker-supplied payload against a different merchant's data — i.e., cross-tenant access/write achieved purely by an unprivileged holder of a valid `(app secret, one legitimate webhook)` pair, without ever knowing another shop's access token or the app's `client_secret`. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only that the attacker be (or briefly become) a legitimate, unprivileged installer of the target app to harvest one genuine `(raw_body, hmac)` pair for a webhook topic they control the content of indirectly (e.g. `orders/create` on their own shop, or a mandatory GDPR topic), then replay it with a forged `shop` header to the target's public webhook endpoint. No secrets, tokens, or elevated privileges are needed beyond normal app installation, which any Shopify merchant can do.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` headers in the signed material verified by `HmacValidator`, or otherwise cryptographically/independently confirm that the `shop` header matches a shop the app has genuinely installed/authorized before dispatching to `WebhookHandler#handle`. At minimum, document (and ideally enforce in `Registry.process`) that `WebhookMetadata#shop` must be cross-checked by the host application against a known/authorized shop list — since it is not implicitly covered by the HMAC as currently implemented.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) to receive a genuine request with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-for-body>`, and body `B`.
2. Replay this exact `B` and `X-Shopify-Hmac-Sha256` to the app's public webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [6](#0-5) ; `HmacValidator.validate` succeeds because it only checks `B` against the shared `api_secret_key` [7](#0-6) ; `Registry.process` dispatches `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)` to the handler [1](#0-0) , which acts on victim's tenant using attacker-chosen data.
