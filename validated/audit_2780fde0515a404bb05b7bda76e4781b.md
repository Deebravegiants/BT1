### Title
Webhook `shop`/`topic`/`webhook-id` identity headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, while the `shop`, `topic`, and `webhook_id` values that the host application's handler actually acts on are taken from unauthenticated HTTP headers that are excluded from the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes the HMAC purely over `to_signable_string` and compares it to the `hmac` accessor: [2](#0-1) 

`Registry.process` gates handling only on this body-only HMAC check, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` (all sourced from headers, see `Request#shop`, `#topic`, `#webhook_id`) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding this breaks: `hmac == HMAC(body)` is verified, but the code acts on `shop-domain header == tenant identity`, an equality that is never checked. Because `shop-domain`, `topic`, and `webhook-id` are excluded from `to_signable_string`, an attacker who has legitimately received one genuinely-signed webhook (e.g. by installing the app on their own store, which any unprivileged merchant can do) can replay that exact signed body while swapping the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to a victim shop's domain. The HMAC still validates, since it never covered those headers, and `Registry.process` will happily hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
Any application built on this gem that keys per-tenant processing (billing state, data updates, uninstall/redact handling, order or customer records) off `WebhookMetadata#shop` is exposed to cross-tenant data injection: an attacker-controlled store can inject data attributed to a victim store's tenant, without ever compromising the victim's credentials, session, or the app's `client_secret`. This satisfies the "Critical – cross-tenant access" impact bar, since a boundary between tenants (whose event this webhook belongs to) is enforced entirely by an unauthenticated header rather than by the cryptographic signature the library exposes to callers as its authenticity guarantee.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate (but unprivileged, non-victim) merchant who installs the target app on their own store to receive at least one real signed webhook, and the ability to send arbitrary HTTP requests to the app's public webhook endpoint (which is internet-facing by design) — no access token, `api_secret_key`, or session of the victim is needed. The main mitigating factor is that this requires the host application to actually trust `WebhookMetadata#shop`/`#topic` for tenant-scoped effects without independently cross-checking it (e.g. against a known/installed shop list), which many integrations built directly on this gem's documented `Webhooks::Registry` API do, since the gem's own docs present `WebhookMetadata#shop` as the verified webhook source.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-covered signable string, or otherwise cryptographically bind them to the signed body (e.g., by requiring callers to additionally re-validate `shop` against an independently maintained list of installed/active shops before trusting `WebhookMetadata`). At minimum, document prominently that `WebhookMetadata#shop`, `#topic`, and `#webhook_id` are unauthenticated header values not covered by `Utils::HmacValidator.validate`, so implementers do not treat them as verified.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`). Shopify sends a request with body `B` and header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`.
2. Attacker intercepts/replays this exact request to the app's webhook endpoint, keeping body `B` and the HMAC header unchanged, but rewrites `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
3. `ShopifyAPI::Webhooks::Request.new` parses these headers into `shop`/`topic`/`webhook_id`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` — this still matches, since headers are never part of `to_signable_string`.
5. `Registry.process` proceeds and calls `handler.handle(data: WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body:, ...))`, causing the app to act on attacker-supplied data under the victim shop's identity.
