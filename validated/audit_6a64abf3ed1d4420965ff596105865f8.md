### Title
Webhook HMAC binds only the request body, not the `shop-domain` header, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable string from only the raw HTTP body [1](#0-0) , while the `shop` (tenant identifier) is read directly from the unauthenticated `shopify-shop-domain` / `x-shopify-shop-domain` header [2](#0-1) . `Registry.process` validates only `Utils::HmacValidator.validate(request)` (i.e. HMAC over the body) before dispatching the handler with `shop: request.shop` taken straight from that header [3](#0-2) . Because the app's `api_secret_key` used for the HMAC is a single shared per-app secret (not per-shop) [4](#0-3) , a valid `(body, hmac)` pair legitimately obtained from one shop's webhook can be replayed with the `shop-domain` header swapped to a different (victim) shop, and it will still pass validation.

### Finding Description
This mirrors the report's bug class: "a field acted on but not covered by the HMAC." The equality that should hold is:
`hmac == HMAC(secret, body || shop || topic || ...)` binding the shop identity to the signed payload.
Instead the actual check is:
`hmac == HMAC(secret, body)` — the `shop` value used later by `handler.handle(data: WebhookMetadata.new(..., shop: request.shop, ...))` is never part of the signed material [3](#0-2) .

An unprivileged attacker who owns/controls their own Shopify development store (which any internet user can create) can:
1. Trigger a legitimate webhook from their own store (Shopify signs it with the app's `api_secret_key`, which is shared across all shops installing the app).
2. Capture the raw body and its valid `X-Shopify-Hmac-Sha256` value.
3. Replay this exact `(body, hmac)` pair to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with a victim shop's domain.
4. `HmacValidator.validate` still succeeds because it only recomputes HMAC over `raw_body` [5](#0-4) , and `Registry.process` proceeds to invoke the app's handler believing the event originates from the victim shop [6](#0-5) .

This breaks the tenant-authentication boundary the gem is meant to provide to the host application: the `shop` value handed to `WebhookMetadata`/the handler is presented as verified but is in fact fully attacker-controlled and unauthenticated.

### Impact Explanation
Any app logic that trusts the gem's `WebhookMetadata#shop` to scope data writes/updates per tenant (a normal and expected usage pattern for this gem) can be tricked into attributing attacker-supplied webhook body content (from the attacker's own shop) to an arbitrary victim shop record. Depending on the topic/handler, this can mean cross-tenant data injection/corruption (e.g., poisoning a victim's cached order/product/customer state, or triggering redaction/compliance webhooks against the wrong shop). This matches the Critical "cross-tenant access" impact class, since it crosses the shop/tenant identity boundary that the HMAC signature is meant to enforce.

### Likelihood Explanation
Likelihood is constrained by the fact that the attacker cannot forge an arbitrary body (they don't have `api_secret_key`), so they must reuse `(body, hmac)` pairs derived from real webhooks triggered on their own store. However, they fully control what actions they perform in their own store (e.g., setting product titles, customer fields, order notes to attacker-chosen values) and can pick a topic they are mandatorily sent (e.g., `customers/data_request`, `shop/redact`) or any subscribed topic, then simply swap the shop header. No secret, token, or privileged access is required — only the ability to run an unprivileged action in one's own development store and to send an arbitrary HTTP POST to the app's public webhook endpoint.

### Recommendation
Bind the shop identity into the verified/signed context instead of trusting the raw header independently of the HMAC:
- Where feasible, verify the webhook against the specific shop's own signing context (Shopify supports per-app secret only, so the gem/app should cross-check `shop-domain` against an app-level allow-list of installed shops, e.g. by confirming a valid stored session/access token exists for that shop) before processing.
- At minimum, document in `lib/shopify_api/webhooks/request.rb` / `registry.rb` that `shop` from `WebhookMetadata` is not itself HMAC-verified and must be independently corroborated (e.g., against known installed shops) by host applications before being trusted as a tenant key.

### Proof of Concept
```ruby
# Attacker triggers a real webhook on their own installed shop "attacker.myshopify.com"
# Shopify sends (captured by attacker):
raw_body = '{"id": 1, "email": "attacker-controlled@example.com"}'
valid_hmac = "shopify-hmac-sha256 header value computed by Shopify with the app's shared api_secret_key"

# Attacker replays it to the app's webhook endpoint, swapping only the shop header:
headers = {
  "x-shopify-topic" => "customers/data_request",
  "x-shopify-hmac-sha256" => valid_hmac,       # unchanged, still matches HMAC(body, secret)
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# -> Utils::HmacValidator.validate(request) succeeds (lib/shopify_api/utils/hmac_validator.rb:12-22)
# -> handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...))
#    (lib/shopify_api/webhooks/registry.rb:188-199)
# The app's handler now processes attacker-controlled data as if it came from "victim-shop.myshopify.com".
```
