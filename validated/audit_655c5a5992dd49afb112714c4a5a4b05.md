### Title
Attacker pre-minted HyperSwap LP position captures a disproportionate share of graduation liquidity via the `_seedDirectMint` "below-band" fallback - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.finalizeGraduation` seeds the HyperSwap V2 TOKEN/LT pair for a graduating token. When the pair already has non-zero `totalSupply()` (i.e. an attacker has already called `pair.mint()` against a self-funded pre-seed before Phase 2 runs), and both reserves sit under `DIRECT_MINT_PRESEED_BPS` relative to the cached `(tokensForLP, ltFromPair)`, `_seedRebalancing` deliberately skips the rebalance swap and routes straight into `_seedDirectMint`, which just transfers the full `tokensForLP` / `ltFromPair` to the pair and calls `IUniswapV2Pair(pair).mint(lpLock)` [1](#0-0) [2](#0-1) . Because `totalSupply() != 0`, this `mint()` call runs the *standard* V2 formula `liquidity = min(amount0*supply/reserve0, amount1*supply/reserve1)`, not the first-liquidity branch that would key the LP purely off the deposited amounts — so the attacker's tiny pre-existing reserve/supply ratio, not the curve-close ratio, determines how much of the freshly-deposited, real liquidity (250M-tranche token + all curve-raised LT) is credited as LP versus donated as raw reserves to the pool the attacker already controls a share of.

### Finding Description
This is the same bug class as CVE-2021-41089 (Moby `docker cp`): an operation meant to safely place fresh, trusted content into a target silently inherits attacker-controlled state from that target (there, Unix permission bits carried over from a crafted archive entry; here, LP-share accounting carried over from a crafted, self-seeded `pair.totalSupply()`), widening what the attacker's pre-existing artifact is entitled to.

Root cause chain, entirely inside `packages/contracts/src/Bonding.sol`:
1. `finalizeGraduation` → `_seedUniswapV2Direct` → `_seedRebalancing` reads live `(r0, r1)` and `totalSupply()` from the *external, attacker-writable* HyperSwap pair [3](#0-2) .
2. If both `reserveToken` and `reserveLT` are under the `DIRECT_MINT_PRESEED_BPS` band relative to `tokensForLP`/`ltFromPair`, the code explicitly chooses to skip any rebalance and call `_seedDirectMint` "overpowering" the pre-seed [1](#0-0) .
3. `_seedDirectMint` transfers the full cached amounts to the pair and calls `pair.mint(lpLock)` unconditionally, with no check on `totalSupply()` at all — it is only used correctly for the true empty-pair regime (`totalSupply() == 0`, first-liquidity branch) and for this "attacker already has LP" fallback, which hits the *standard* mint formula instead [4](#0-3) .
4. The natspec itself acknowledges the resulting exposure ("the pre-existing LP's claim on the deposit stays bounded by `DIRECT_MINT_PRESEED_BPS`") [5](#0-4) , but that bound constrains only the *pre-seed reserve size* relative to `tokensForLP`/`ltFromPair`, not the attacker's resulting *share of the newly-minted LP* against the true value deposited — the standard `min()` V2 formula can still assign the attacker a share of the real 250M-token/LT deposit disproportionate to what they contributed, because reserve size and LP-share-per-dollar are decoupled once `totalSupply()` is nonzero and the ratio is off-curve.
5. `AGENTS.md` confirms this exact scenario class ("wrong-opening-price / LP-capture scenarios, attacker-no-profit... properties") was previously covered by `test/HostilePreSeed.t.sol` but that suite was deleted post-deployment and is "no longer enforced by automated tests" [6](#0-5) .

### Impact Explanation
An unprivileged attacker who front-runs an imminent `finalizeGraduation` by cheaply pre-minting a hostile LP position on the not-yet-existing/just-created HyperSwap pair can capture a share of the value the protocol deposits on every single token graduation (real curve-raised LT plus up to 250M tokens), i.e. permanent theft of trader/creator/protocol funds and an LP seeded away from the curve close price — both explicitly listed as qualifying impacts.

### Likelihood Explanation
`finalizeGraduation` is permissionless and its target address (`_ensureUniswapV2Pair`) is deterministically derivable ahead of time from `tokenAddress`/`lt` via the V2 factory, so any address can pre-create and pre-mint the pair before the keeper's Phase-2 call lands, especially since the keeper's ~60s window between `TokenGraduating` and `finalizeGraduation` is public via the `TokenGraduating` event [7](#0-6) . This is a routine, cheap MEV-style front-run on every graduation, not a rare edge case, and the regression suite that once asserted "attacker-no-profit" for exactly this shape has been removed.

### Recommendation
Never call `_seedDirectMint`'s unconditional `pair.mint(lpLock)` when `totalSupply() != 0`; for that case, always route through the router's `quote()`-based `addLiquidity` deposit (as regime 3's normal path does) so LP is minted proportional to actual deposit value, or explicitly reject/skim any pre-existing attacker LP supply before minting. Restore `test/HostilePreSeed.t.sol` (or an equivalent) asserting an upper bound on attacker LP-share-of-deposit-value, not merely on pre-seed reserve size.

### Proof of Concept
1. Attacker computes the deterministic HyperSwap pair address for `(tokenAddress, lt)` from `Bonding.uniswapV2Factory()`/`createPair`.
2. Attacker calls `factory.createPair(tokenAddress, lt)`, transfers a dust amount of `lt` and `tokenAddress` (obtained cheaply, e.g. by buying a tiny amount on the still-open curve) directly to the pair, and calls `pair.mint(attacker)` — this sets `totalSupply() > 0` with `reserveToken`/`reserveLT` both under `DIRECT_MINT_PRESEED_BPS` of the anticipated `tokensForLP`/`ltFromPair`.
3. Attacker (or anyone) calls `Bonding.triggerGraduation`/waits for the threshold-crossing buy to fire Phase 1, then calls the permissionless `Bonding.finalizeGraduation(tokenAddress)`.
4. `_seedRebalancing` detects both reserves under the band and calls `_seedDirectMint`, which transfers the full legitimate `(tokensForLP, ltFromPair)` to the pair and calls `pair.mint(lpLock)` against `totalSupply() != 0`, crediting LP by the standard `min(amount*supply/reserve)` formula skewed by the attacker's dust reserve/supply ratio.
5. Attacker's pre-existing LP tokens now represent a disproportionate claim on the pool's true value; attacker calls `removeLiquidity` on the router to redeem more value than they deposited, at the expense of the locked `LPLock` position.

(Note: I could not retrieve the concrete numeric value of `DIRECT_MINT_PRESEED_BPS` before running out of tool budget, so the exact magnitude of the captured share is unverified — this should be confirmed against `packages/contracts/src/Bonding.sol`'s constant definition and modeled against `test/TwoPhaseGraduation.t.sol`'s `DIRECT_MINT_PRESEED_BPS` cases before treating the severity as final.)
