### Title

Liquidation payout can be front-run and reduced without a minimum-seizure bound - (File: contracts/controller/src/positions/liquidation/plan.rs)

### Summary

`liquidate` accepts only the target account, offered debt payments, and a seizure mode; it has no minimum collateral-output, minimum collateral-value, or minimum-bonus parameter. [1](#0-0) 

The liquidation plan is rebuilt at execution from the account’s current debt, collateral, and health factor, and the health factor directly determines the liquidation bonus. [2](#0-1) [3](#0-2) 

An unprivileged account can therefore submit a partial liquidation or repayment before a victim liquidator’s transaction, improve the target’s health factor while keeping it below one, and cause the victim to receive less collateral for the same accepted debt repayment. [4](#0-3) 

### Finding Description

`process_liquidation` authenticates the liquidator but does not require ownership of the target account, making liquidation permissionless. [5](#0-4) 

The function constructs a fresh `LiquidationPlan` from the current account state at execution time. [6](#0-5) 

Planning rejects the liquidation only when the current health factor is at least one WAD; any lower health factor remains executable. [7](#0-6) 

The current health factor is included in the liquidation snapshot passed to the bonus calculation. [8](#0-7) 

`calculate_linear_bonus_with_target` raises the bonus as the health factor falls toward `hf_for_max_bonus`, so improving the health factor lowers the bonus used for the victim’s transaction. [9](#0-8) 

The resulting gross collateral seizure is calculated as `repay_usd * (1 + bonus)` and then split pro rata across collateral positions. [10](#0-9) 

A front-running partial liquidation reduces debt and removes collateral at the old bonus; when the applied bonus satisfies the health-factor-preserving bound, the account’s collateral-to-debt ratio and health factor increase or remain unchanged. [11](#0-10) 

A permissionless `repay` can likewise reduce the debt before the victim’s liquidation, directly raising `weighted_collateral / debt` without seizing collateral. [12](#0-11) 

Because the victim cannot encode an execution-time collateral floor, the transaction proceeds under the less favorable bonus rather than reverting. [1](#0-0) 

### Impact Explanation

The liquidator signs authorization for a debt-token payment based on the currently estimated bonus, but execution can occur after another unprivileged transaction changes that bonus. [13](#0-12) 

If the target remains liquidatable and the submitted payment remains within the new liquidation quote, the same debt amount is pulled while less collateral is seized. [14](#0-13) [10](#0-9) 

This is an economic loss of collateral to the liquidator: part of the expected liquidation payout is instead captured by the front-running liquidator or remains with the borrower after a debt repayment. [15](#0-14) 

The impact is bounded to the reduction in liquidation proceeds, but it can affect every liquidation whose health factor remains below one after the intervening transaction. [7](#0-6) 

### Likelihood Explanation

Both liquidation and ordinary debt repayment are callable by unprivileged addresses. [4](#0-3) 

A competing liquidator has a direct profit incentive to execute first because its partial liquidation receives collateral at the pre-change bonus. [10](#0-9) 

The attacker only needs to leave the account’s health factor below one so that the victim’s transaction still executes under the reduced bonus. [7](#0-6) 

Likelihood is highest for accounts close to the liquidation boundary or markets with a steep configured bonus curve, where a relatively small state change materially reduces the bonus. [9](#0-8) 

### Recommendation

Add an execution-time output constraint to `liquidate`, such as a minimum net seized amount per collateral asset or a minimum total seized USD value. [1](#0-0) 

Compute the fresh plan, apply measured repayments, scale the seizure for measured receipts, and revert if the resulting seizure is below the caller-provided floor before applying collateral withdrawals or share credits. [16](#0-15) 

A minimum accepted liquidation bonus can be added as a secondary guard, but it should not replace an output floor because pro-rata allocation, fees, rounding, and collateral caps also affect the net payout. [17](#0-16) 

### Proof of Concept

Consider a configured curve with target health factor `1.1`, maximum-bonus health factor `0.5`, full bonus factor, a blended liquidation proportion `p = 0.5`, base bonus `0`, and maximum bonus `100%`. [18](#0-17) 

Let the target initially have debt `D = $1,000`, collateral `C = $1,900`, and weighted collateral `W = $950`, so `HF = 0.95` and the bonus scale is `(1.1 - 0.95) / (1.1 - 0.5) = 0.25`. [19](#0-18) 

The initial bonus is therefore `25%`, and a victim planning to repay `$100` expects `$125` of collateral before liquidation fees. [10](#0-9) 

An attacker front-runs the victim with a `$131` liquidation, receiving approximately `$163.75` of collateral at the same `25%` bonus. [5](#0-4) 

After that liquidation, debt is approximately `$869`, collateral is approximately `$1,736.25`, weighted collateral is approximately `$868.125`, and `HF ≈ 0.999`, so the target is still liquidatable. [2](#0-1) 

The victim’s transaction now computes a bonus of approximately `16.83%`, so the same `$100` repayment yields only approximately `$116.83` of collateral instead of `$125`. [9](#0-8) [10](#0-9) 

The sequence is:

```rust
// Attacker observes victim's pending:
// liquidate(victim_liquidator, target, [(DEBT, 100)], Transfer)

// Front-run while HF and bonus are still favorable.
liquidate(attacker, target, [(DEBT, 131)], SeizeMode::Transfer);

// Victim transaction then executes at the recalculated HF/bonus.
liquidate(victim_liquidator, target, [(DEBT, 100)], SeizeMode::Transfer);
```

There is no `min_seized`, `min_seized_usd`, or `min_bonus_bps` argument that would make the victim’s transaction revert instead of accepting the reduced payout. [1](#0-0)

```rust
pub(crate) fn calculate_linear_bonus_with_target(
    env: &Env,
    hf: Wad,
    base: Bps,
    max: Bps,
    curve: &LiquidationCurve,
    target: Wad,
) -> Bps {
    if hf >= target {
        return base;
    }
    let scale = curve.bonus_scale(env, hf, target);

    let bonus_range = max.checked_sub(env, base);
    let bonus_increment = Wad::from(bonus_range.raw()).mul(env, scale).raw();
    let scaled_increment = curve.bonus_factor.apply_to(env, bonus_increment);
    Bps::from(
        base.raw()
            .checked_add(scaled_increment)
            .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow)),
    )
```
