Found a concrete analog: `TokenExchange.exchange_token` derives the request host directly from the JWT's `dest` claim without ever passing it through `Utils::ShopValidator.sanitize!`, and that unsanitized value is used to build the URL the gem posts `client_secret` to.

### Title
`TokenExchange.exchange_token` sends `client_secret` to an unsanitized host derived from the JWT `dest` claim - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes `dest_shop = jwt_payload.shop` (i.e., the raw `dest` claim of the session token, only stripped of the `https://` prefix) and uses it, unsanitized, as the `Session#shop` that `Clients::HttpClient` turns into the request host for the token-exchange POST — the same request body that includes `client_secret`. Unlike the sibling method `migrate_to_expiring_token` in the very same file, which calls `Utils::ShopValidator.sanitize!(shop)` before building the session, `exchange_token` never validates that `dest_shop` is a trusted Shopify domain.

### Finding Description
`JwtPayload#shop` is implemented as a bare string transform with no domain allow-listing: [1](#0-0) 

`TokenExchange.exchange_token` consumes this value directly to build the outbound session/host, with no call to `ShopValidator`: [2](#0-1) 

Contrast this with `migrate_to_expiring_token` in the same module, which explicitly sanitizes the shop before use: [3](#0-2) 

`Clients::HttpClient#initialize` builds the request's base URI straight from `session.shop`: [4](#0-3) 

The identity binding that should hold is: *the host that receives `client_secret` == a domain in `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`*. The library owns and enforces exactly this check elsewhere: [5](#0-4) [6](#0-5) 

`exchange_token` breaks this binding: it validates the JWT's *signature* (via `JwtPayload.new`) but never validates that the `dest` claim's *value* resolves to a trusted domain, before using that value as the network destination for a request carrying `client_secret`.

### Impact Explanation
If any code path in front of `exchange_token` allows the `dest` claim to be attacker-influenced (e.g., a compromised/rogue frontend, a proxy that mints or forwards session tokens with attacker data, or any host-app bug that lets a caller supply a token whose `dest` is not fully constrained to `*.myshopify.com`/`*.spin.dev`/etc. before the gem processes it), the gem will POST the app's `client_secret` and the subject `session_token` to that attacker-controlled host — an SSRF-with-credentials that leaks the app's `client_secret` and enables cross-tenant/account takeover. This is exactly the class of "host validated versus host that receives client_secret" identity-binding break called out as in-scope, and is analogous to the report's core lesson (a value that participates in privileged behavior is not defensively re-validated at the point of use).

### Likelihood Explanation
Moderate-to-low, since Shopify's own signing key protects the JWT from casual tampering (the JWT signature over `dest` is checked in `JwtPayload#initialize`). However, the gem's own defense-in-depth (`ShopValidator`) is applied inconsistently within the same module — present in `migrate_to_expiring_token`, absent in `exchange_token` — which is a genuine gap relative to the library's own established invariant, not merely a theoretical one. Any host application or intermediary that is less strict about how it obtains/passes the `session_token` string relies entirely on this gem to re-validate `dest`, and it currently doesn't.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, sanitize `dest_shop` through `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token`) before constructing `shop_session` and issuing the HTTP request, so the request host is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Obtain/construct a session token whose `dest` claim is not a `*.myshopify.com`/trusted domain (this requires a path where the token's `dest` is attacker-influenced prior to reaching this gem, e.g., a lenient host app or intermediary).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `JwtPayload#shop` returns the unsanitized `dest` value [7](#0-6) , which flows unchanged into `Session.new(shop: dest_shop)` and then into `HttpClient`'s `@base_uri = "https://#{api_host || session.shop}"` [4](#0-3) , causing the POST body containing `client_secret` [8](#0-7)  to be sent to that host instead of a verified Shopify domain.
