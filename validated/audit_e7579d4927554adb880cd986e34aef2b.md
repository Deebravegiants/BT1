The `MainEVMCircuitMin` circuit only constrains `message == Poseidon(messageSeed)` with `messageSeed` fully attacker-chosen, and the public inputs are just `outTimeStamp`, `calldataHash`, and the derived `message` [1](#0-0) . `formInputForCircom` routes to this minimal path whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0` [2](#0-1) , and `formInputEmporiumMin` only encodes `emporiumMessage`, `timeStamp`, and `calldataHash` as public signals [3](#0-2) , no amounts, tokens, nullifiers, or root/UTXO ownership are constrained at all.

### Title
Emporium Min-proof path allows unsigned, unaccounted arbitrary calls that drain Emporium's token holdings - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol, contracts/CircomDataBuilder.sol)

### Summary
When `erc20TokenAddresses.length == 0`, `formInputForCircom` selects `formInputEmporiumMin`, whose circuit only proves knowledge of a `messageSeed` producing `message`, with no constraint on ownership, tokens, or amounts. Combined with `EmporiumUpgradeable.verifyWallet` short-circuiting (no signature check) when `EmporiumStack.signerAddress == address(0)`, an attacker can submit an unsigned, fully attacker-controlled `EmporiumOperation[]` that is executed by `Emporium` as `msg.sender`, while both `Hinkal.transact`'s and `EmporiumUpgradeable.runAction`'s balance-accounting loops iterate the empty `erc20TokenAddresses` array and therefore verify nothing.

### Finding Description
The broken equality is: **assets Emporium can move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter`**. In the Min path this equality is `0 == 0` trivially, but the actual call performed by Emporium can move any token/balance it holds, since the accounting loop never inspects those tokens.

Path:
1. Attacker calls `Hinkal.transact` with `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `circomData.erc20TokenAddresses.length == 0`.
2. `performHinkalChecks` → `formInputForCircom` selects `formInputEmporiumMin`, producing public inputs consisting only of `emporiumMessage`, `timeStamp`, `calldataHash` [4](#0-3) . The corresponding circuit, `MainEVMCircuitMin`, only proves `message == Poseidon(messageSeed)` with `messageSeed` chosen freely by the attacker [5](#0-4) . This proof requires no UTXO ownership, no root membership, no nullifier, and constrains no amounts or token addresses.
3. `Hinkal.transact` proceeds to `_externalTransact`, which (because `circomData.erc20TokenAddresses.length == 0`) skips the deposit-transfer loop entirely and calls `IExternalActionV2(EmporiumUpgradeable).runAction(circomData, deltaAmountChanges)` with an empty `deltaAmountChanges` array [6](#0-5) .
4. In `EmporiumUpgradeable.runAction`, `stack = abi.decode(circomData.externalActionData.externalActionMetadata, (EmporiumStack))` is entirely attacker-controlled [7](#0-6) . `verifyWallet` returns immediately without any signature check when `stack.signerAddress == address(0)` [8](#0-7) .
5. The op loop then executes CASE 2 ("Stateless Interaction") for every op since `stack.signerAddress == address(0)`: `op.endpoint.call{value: op.value}(op.callData)`, blocked only for the `callHinkalWallet`/`doSendToRelay` selectors [9](#0-8) . This call is made with `msg.sender == address(EmporiumUpgradeable)`, so it can, for example, invoke `token.transfer(attacker, amount)` directly on any ERC20 for which Emporium holds a balance, or invoke `token.transferFrom(...)` if Emporium has been granted a standing allowance elsewhere (e.g., a partially-consumed router approval left over from a prior legitimate swap).
6. `getBalancesForArray(circomData.erc20TokenAddresses)` for `balancesBefore`/`balancesAfter` operates over an **empty array** because `erc20TokenAddresses.length == 0`, so the loop that computes `balanceChange` and reverts on `balanceChange < 0` (`BalanceChangeShouldBePositive`) never executes for the stolen token [10](#0-9) .
7. Back in `Hinkal.transact`, the outer balance/slippage-check loop also iterates `circomData.erc20TokenAddresses` (empty), so it likewise checks nothing [11](#0-10) .

No other guard catches this: `dimensionsCheck`/`checkOnchainCreation` don't inspect Emporium ops, `rootHashExists`/`insertNullifiers` are irrelevant since no nullifiers are spent, and `onlyAllowedRecipient` only requires `msg.sender == Hinkal`, which is satisfied since the call originates from `Hinkal.transact` itself.

The "6-decimal token" framing in the question doesn't materially change the exploit — the vulnerability is a complete absence of accounting (not a rounding/precision boundary issue), so it applies uniformly regardless of token decimals.

### Impact Explanation
An unprivileged attacker can drain any ERC20 (or ETH) balance held by the `EmporiumUpgradeable` contract — including funds left transiently by other users' in-flight multi-step operations, unswept dust, or tokens reachable via a standing approval Emporium granted to a router/spender — with zero accounting or signature requirement. This is direct theft of in-flight/shielded user funds routed through Emporium, matching **Critical** severity. It is repeatable for every unique `emporiumMessage` (each message can only be used once due to `usedMessages`, but the attacker can generate arbitrarily many).

### Likelihood Explanation
Preconditions: Emporium must hold some token/ETH balance or a standing token approval at the time of the attack — a state that legitimately occurs whenever any user's Emporium-routed operation leaves funds transiently in the contract (e.g., mid-multi-op flows, unconsumed router allowances, rounding dust). The attacker's cost is just gas plus generating one Groth16 proof for the trivial `MainEVMCircuitMin` circuit (feasible for anyone, no secret knowledge required). This makes the attack highly feasible and fully repeatable.

### Recommendation
- In `EmporiumUpgradeable.verifyWallet`, do not skip signature verification based solely on `signerAddress == address(0)`; instead require the Min/stateless path to only allow ops whose token effects are fully covered by `circomData.erc20TokenAddresses` (i.e., forbid the Min proof path when `stack.ops` is non-empty, or require `erc20TokenAddresses.length > 0` whenever ops perform arbitrary external calls).
- Alternatively, bind `stack`/`ops` (or their hash) into the Min circuit's public inputs so any executed operation is provably constrained, and have `runAction`/`Hinkal.transact` track balances for every token actually touched by `op.endpoint` calls, not just tokens listed in `erc20TokenAddresses`.
- Disallow `formInputEmporiumMin` from being used when `externalActionMetadata` decodes to any non-empty `ops` array with `signerAddress == address(0)`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `EmporiumUpgradeable` (as allowed recipient), a mock ERC20 with 6 decimals, and register the Min verifier for `HINKAL_EMPORIUM_ACTION_ID`.
2. Fund `EmporiumUpgradeable` directly with e.g. `1_000_000` units (1.0 token, 6 decimals) of the mock token (simulating leftover in-flight balance).
3. Construct `CircomData` with `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, and `externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: token, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1_000_000))})], ...}))`.
4. Generate a valid Groth16 proof locally for `MainEVMCircuitMin` with an attacker-chosen `messageSeed`, matching `calldataHash`/`timeStamp`/`emporiumMessage`.
5. Call `Hinkal.transact(a, b, c, dimensions, circomData)` from the attacker EOA.
6. Assert: `token.balanceOf(attacker)` increased by `1_000_000` and `token.balanceOf(Emporium)` decreased by `1_000_000`, while `circomData.erc20TokenAddresses.length == 0` and the accounting equality `balanceDif == amountChanges[i] + utxoAmount` in `Hinkal.transact` and `balanceChange < 0` check in `EmporiumUpgradeable.runAction` were never evaluated (loop bound is 0), proving the theft was entirely unaccounted.
