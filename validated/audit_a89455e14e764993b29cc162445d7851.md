## Analysis

**Equality claimed broken:** `msg.sender` of `DepositOnChainUtxosExternalAction.runAction` should always equal `Hinkal` (the only contract whose calls follow a `VerifierFacade.verifyProof` success), but with the stated precondition it can equal `EmporiumUpgradeable`, acting as a relay for a `CircomData` struct that was never fed into `verifyProof`.

**Trace:**
1. `Hinkal.transact` verifies the proof only for the **outer** `circomData` (the caller's own tx) via `hinkalHelper.performHinkalChecks` → `verifyProof` [1](#0-0) , then dispatches to `_externalTransact`, which calls `IExternalActionV2(externalAddress).runAction(circomData, deltaAmountChanges)` on the allow-listed action (Emporium) [2](#0-1) .
2. Inside `EmporiumUpgradeable.runAction`, the ops array comes from `abi.decode(circomData.externalActionData.externalActionMetadata, (EmporiumStack))` — raw attacker-supplied bytes [3](#0-2) . For a stateless op (`invokeWallet=false`), the only restriction is a selector check that blocks `callHinkalWallet`/`doSendToRelay`; any other target and calldata is executed via raw low-level call: `(success, err) = op.endpoint.call{value: op.value}(op.callData);` [4](#0-3) .
3. `DepositOnChainUtxosExternalAction.runAction` is guarded only by `onlyAllowedRecipient`, i.e. `isAllowedRecipient[msg.sender]` [5](#0-4) . If `EmporiumUpgradeable` is on that allow-list, `op.callData = abi.encodeWithSelector(runAction.selector, innerCircomData, innerDeltaAmounts)` is accepted with `msg.sender == EmporiumUpgradeable`, and `innerCircomData` is a completely attacker-fabricated struct that was never part of `verifyProof`'s public inputs — only the outer `circomData` (including the raw bytes of `externalActionMetadata`) was hashed and checked via `getHashedCalldata`/`calldataHash` [6](#0-5) . That hash check binds the *bytes*, not the semantic correctness of the embedded inner `CircomData`.
4. `DepositOnChainUtxosExternalAction.runAction` then pulls real tokens via `transferERC20TokenFrom(tokenAddress, userAddress, msg.sender, tokenTotal)` where `userAddress = innerCircomData.originalSender` is fully attacker-chosen and unconstrained by any signature/proof in this call [7](#0-6) .

**Why this is a genuine bypass:** the `onlyAllowedRecipient` guard's design intent is that `runAction` is only reachable after `Hinkal.transact` has run `verifyProof` against that exact `CircomData`. Once `EmporiumUpgradeable` is allow-listed on a second external action, it becomes an unrestricted relay: any `CircomData` struct the attacker places inside `op.callData` reaches `runAction` with `onlyAllowedRecipient` satisfied, but zero circuit constraints (`inTotal+amountChanges===outTotal`, nullifier checks, `originalSender==sender` binding) were ever applied to it. Only the ERC20 `transferFrom` allowance mechanics gate real fund movement — if the named `originalSender` address happens to have any standing ERC20 approval to `EmporiumUpgradeable`'s address, those funds move without their participation in this transaction, and the outer, genuinely-proof-verified `circomData`'s balance/UTXO bookkeeping in `Hinkal.transact` (lines 116–146) will self-consistently absorb the resulting balance delta into an on-chain UTXO credited to the attacker's own `stealthAddressStructure`, because Hinkal only checks its *own* before/after balance vs. the returned `utxoSet`, not how that balance change was internally produced [8](#0-7) .

**Important caveat / uncertainty:** the actual token movement still requires a real ERC20 allowance from some address to `EmporiumUpgradeable` specifically (not to `Hinkal`). I was unable to confirm from the indexed code whether any legitimate protocol flow causes ordinary users to grant such an approval directly to `EmporiumUpgradeable` (as opposed to `Hinkal`); if no such approval exists, this path only lets an attacker move their *own* already-approved funds, which by itself causes no economic loss to a third party, though it still constitutes a demonstrable proof-verification bypass (a `runAction` state change executed for a `CircomData` payload with no corresponding Groth16 proof).

### Title
Emporium stateless op can relay arbitrary `CircomData` to `DepositOnChainUtxosExternalAction.runAction`, bypassing proof verification - (contracts/external-actions/emporium/EmporiumStack.sol / EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s stateless branch executes an arbitrary low-level call from attacker-controlled `EmporiumOperation.callData` with only a selector blacklist for `callHinkalWallet`/`doSendToRelay`. If `EmporiumUpgradeable` is allow-listed on `DepositOnChainUtxosExternalAction`, this lets an attacker invoke `runAction` on that action with a fully attacker-fabricated `CircomData` that was never checked by `VerifierFacade.verifyProof`, causing real `transferERC20TokenFrom` calls keyed on an attacker-chosen `originalSender`.

### Finding Description
The broken equality is `msg.sender_of_runAction == Hinkal` (intended) vs. `msg.sender_of_runAction == EmporiumUpgradeable` (actual), while the `CircomData` argument used in that call is not the proof-checked outer struct but an independently attacker-crafted inner struct embedded in `op.callData`. The root cause is that `onlyAllowedRecipient` on `ExternalActionBaseV2`/`ExternalActionBaseUpgradeable` only checks `msg.sender` identity, and does not (and cannot) verify that the `CircomData` argument passed to it was the subject of a verified proof; that binding is only enforced once, transitively, by `Hinkal.transact` for the outermost call. `EmporiumUpgradeable.runAction`'s stateless branch forwards arbitrary bytes to arbitrary allow-listed endpoints via `op.endpoint.call{value: op.value}(op.callData)` [4](#0-3) , so once `EmporiumUpgradeable` is added to a second action's `isAllowedRecipient` map, that second action's proof-verification guarantee is void for calls arriving through Emporium.

### Impact Explanation
`DepositOnChainUtxosExternalAction.runAction` moves real ERC20 tokens via `transferERC20TokenFrom` based on an `originalSender` address and amounts that were never bound to any Groth16 proof [9](#0-8) . If any address has an outstanding ERC20 approval to `EmporiumUpgradeable`, an attacker can drain it in a single transaction wrapped inside their own unrelated, legitimately-proven Emporium transaction, with the stolen amount surfacing as a shielded UTXO credited to the attacker's own `stealthAddressStructure` because Hinkal's own balance-diff accounting in `transact` is self-consistent regardless of how the external action produced the balance delta. This is a proof-verification bypass enabling theft of user funds, matching Critical severity; it is repeatable against every address with a standing approval to `EmporiumUpgradeable`.

### Likelihood Explanation
Requires: (a) `EmporiumUpgradeable` be allow-listed as `isAllowedRecipient` on `DepositOnChainUtxosExternalAction` (stated precondition), and (b) a real ERC20 allowance from some address to `EmporiumUpgradeable`. Precondition (a) is an operator/governance configuration choice; precondition (b) depends on protocol UX that I could not fully confirm from the indexed code (no explicit flow was found where ordinary users approve `EmporiumUpgradeable` directly rather than `Hinkal`). Attacker cost is a single self-generated proof for a trivial legitimate transaction; no privileged role is required.

### Recommendation
Do not allow-list any relay contract (Emporium) as a valid `msg.sender` on other `IExternalActionV2` actions unless that relay itself enforces the same circuit-level guarantees. Alternatively, restrict Emporium's stateless-op `endpoint` to a denylist/allowlist of safe targets (excluding other `runAction` entrypoints), or require that `op.callData`'s target/selector cannot match any registered `IExternalActionV2.runAction` selector, mirroring the existing `callHinkalWallet`/`doSendToRelay` selector check.

### Proof of Concept
Hardhat test: deploy `Hinkal`, `EmporiumUpgradeable`, `DepositOnChainUtxosExternalAction` with `isAllowedRecipient[EmporiumUpgradeable]=true`; have a victim EOA `approve(EmporiumUpgradeable, amount)` on an ERC20; craft an outer, genuinely proof-verified `circomData`/proof for the attacker's own trivial Emporium tx whose `externalActionMetadata` decodes to an `EmporiumStack` with one stateless op: `endpoint = DepositOnChainUtxosExternalAction`, `callData = abi.encodeWithSelector(runAction.selector, innerCircomData, [0])` where `innerCircomData.originalSender = victim`, `erc20TokenAddresses=[token]`, and metadata `utxoAmounts=[[amount]]`. Assert: (1) the victim's token balance decreases by `amount` and `DepositOnChainUtxosExternalAction.runAction` executed successfully; (2) no proof/public input ever referenced `innerCircomData` (only the outer struct was passed to `verifyProof`); (3) the attacker's shielded balance/UTXO set increases by `amount` for `token`.
