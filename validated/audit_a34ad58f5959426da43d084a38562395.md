### Title
Webhook Tenant (`shop`) Identity Is Taken From an Unauthenticated Header, Not From the HMAC-Covered Payload - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
The report's underlying bug class is "a value is trusted/acted upon without validating that it is bound to the value that was actually authenticated." The closest analog in this gem is `ShopifyAPI::Webhooks::Request`: the HMAC signature only covers the raw request body, while the `shop` (tenant identity), `topic`, and `webhook_id` are read straight from unauthenticated HTTP headers and handed to the app's webhook handler as if they were verified.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are pulled from headers that are never part of the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` HMACs `verifiable_query.to_signable_string` (i.e. just the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` checks only that the body's HMAC is valid, then forwards the **header-derived, unauthenticated** `request.shop`, `request.topic`, and `request.webhook_id` straight to the app's handler as `WebhookMetadata`: [4](#0-3) 

The identity binding that is broken: `HMAC(body, api_secret_key) verified` should equal `shop the payload is attributed to`, but the gem never ties the verified body to the `shop-domain` header — they are two independent, uncorrelated inputs. Anything that authenticates the body says nothing about which header values accompanied it.

### Impact Explanation
A normal (unprivileged, non-app-owner) merchant can install the target app on their own store — no `api_secret_key`, access token, or other app credential is required. By interacting with their own store, they can obtain a genuine, correctly-signed webhook delivery (body + `hmac` header) for a topic the app subscribes to. Because the `shop-domain`, `topic`, and `webhook-id` headers are not covered by the signature, that same `(raw_body, hmac)` pair remains valid if replayed to the app's public webhook endpoint with a forged `shop-domain` header naming a different (victim) shop. `Utils::HmacValidator.validate` will still pass (it only checks the body), and `Registry.process` will hand the app's `WebhookHandler#handle` a `WebhookMetadata` whose `shop` is the attacker-chosen victim domain. Any app that uses `WebhookMetadata#shop` to select which merchant's stored session/access token or data record to act on (the gem's own documentation shows exactly this pattern) will now perform tenant-scoped writes/reads under the wrong tenant identity — a cross-tenant access/write vulnerability, which maps to the report's Critical impact bucket.

### Likelihood Explanation
Likelihood is moderate-to-high for a determined attacker: obtaining a self-signed legitimate webhook requires only installing the app on a store they control (no special privilege, no leaked secret), and forging headers on an HTTP POST to a public endpoint requires no special tooling. The main precondition is that the app-side handler trusts `WebhookMetadata#shop` as the tenant selector without independent corroboration — which is the pattern this gem's own webhook API surface encourages.

### Recommendation
Include the identity-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-signed material (or otherwise cryptographically bind them to the payload), or at minimum document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are **not** authenticated and must be cross-validated by the host app against known/expected values (e.g., only shops that have a stored, previously-established session) before being trusted for tenant selection.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers a subscribed webhook topic (e.g., `products/update`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify to the app's webhook endpoint.
2. Attacker replays the exact same body and `hmac` value to the same public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (it only checks the body against the HMAC), demonstrated by: [5](#0-4) 
4. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: attacker_controlled_body, ...)`, causing the host application to act on `victim-shop`'s tenant context using attacker-supplied data, even though nothing about `victim-shop.myshopify.com` was ever verified.
