### Title
`DelegateAction` (meta-transaction) signature omits any chain/fork discriminator, enabling cross-fork replay of relayed transactions - (File: `core/primitives/src/signable_message.rs`, `core/primitives/src/action/delegate.rs`)

### Summary
NEAR meta-transactions (NEP-366/NEP-611) let a user sign a `DelegateAction` off-chain and hand it to a relayer, who wraps it in an ordinary `SignedTransaction`. The bytes that are actually signed by the end user (`SignableMessage<DelegateAction>`) never include a chain/genesis/fork identifier equivalent to Ethereum's `chainid`. This is structurally the same bug class as the reported `LibTokenPermit::_buildDomainSeparator` issue: a signed authorization is portable to any chain that shares state/history with the one it was intended for, including a post-fork chain.

### Finding Description
The signed payload for a `DelegateAction` is constructed purely from `sender_id`, `receiver_id`, `actions`, `nonce`, `max_block_height`, `public_key`, plus a fixed NEP discriminant: [1](#0-0) 
and is hashed/signed with no reference to genesis hash, chain id, or any block hash: [2](#0-1) 

Regular NEAR `SignedTransaction`s at least reference a recent `block_hash`, which ties them to a specific chain's block history and bounds their validity window. `DelegateAction`, by contrast, is bound only by the signer's access-key nonce and a self-chosen `max_block_height`, both of which are pure integers with no chain-identifying material: [3](#0-2) 

Because access-key state (nonce) and block height are near-identical on both sides of a chain split immediately after a hard fork, a `SignedDelegateAction` produced before the fork remains fully valid and executable on both the original and the forked chain, exactly as `LibTokenPermit`'s domain separator (baked with a static `CHAIN_ID`) remains valid on both sides of an EVM fork. The relayer wrapping the delegate action pays gas on the transaction envelope, but the inner authorization itself carries no anchor to a specific network.

### Impact Explanation
If the NEAR network were to hard fork (e.g., a contentious upgrade or governance split, producing two live chains sharing genesis/history), any previously signed but not-yet-executed `SignedDelegateAction` could be submitted to both chains by a relayer (or by any party who intercepts it), executing the user's authorized actions (e.g., token transfers, contract calls with the sender's authority) twice — once per chain — even though the user only intended it once. This is an unauthorized/duplicated action execution on the "other" chain, matching the report's "signature replay attack in case of a hard fork" bug class. The severity is bounded by the value of actions a given `DelegateAction` can trigger (e.g., FT transfers, staking actions, function calls) and by whether relayers/wallets are careful to invalidate delegate actions after use — but the protocol offers no on-chain distinguishing mechanism between forks for this signature scheme.

### Likelihood Explanation
Requires an actual live hard fork of NEAR (two networks sharing the same historical state diverging), which is a rare but not unprecedented event for blockchains. Given such an event, exploitation is straightforward and requires no privileged access — merely resubmitting a previously observed `SignedDelegateAction` (or having a relayer that already possesses one) to the second chain. It is a lower-likelihood event overall since it depends on an external fork condition, but the vulnerable code path is directly reachable from a submitted transaction/relayer flow with no additional protocol changes needed.

### Recommendation
Incorporate a chain-identifying value (e.g., the genesis hash, or a protocol-defined `chain_id`) into the `SignableMessage`/`DelegateAction` structure so that the signed bytes are unique per chain, mirroring how EIP-712's domain separator should read `block.chainid` rather than a hardcoded constant. Concretely, add a `genesis_hash` (or similar) field to `DelegateAction`/`SignableMessage` construction in `core/primitives/src/action/delegate.rs` and `core/primitives/src/signable_message.rs`, and validate it against the actual chain's genesis hash during `validate_delegate_action_key` in `runtime/runtime/src/actions.rs`. This is a protocol-affecting NEP-366/611 change and should go through the normal protocol-feature versioning process.

### Proof of Concept
1. User Alice signs a `DelegateAction` (e.g., "transfer 1000 FT to Bob") using `SignableMessage::sign` off-chain, with `nonce = N`, `max_block_height = H` — as in `core/primitives/src/signable_message.rs` lines 97-107 and the test helper at lines 286-300.
2. A hard fork occurs at block height `< H`, producing chain A (original) and chain B (fork), both sharing Alice's access key at nonce `N-1` (i.e., her key has not yet used nonce `N` on either fork).
3. A relayer (or an observer who captured the `SignedDelegateAction` off-chain, e.g., via the relayer's mempool/API before the fork) wraps it in a `SignedTransaction` and submits it on chain A. `validate_delegate_action_key` (`runtime/runtime/src/actions.rs` lines 563-650) accepts it since nonce `N > N-1` and `N < max_block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`; Alice's actions execute.
4. The same relayer (or an unrelated party who has a copy of the identical `SignedDelegateAction` bytes) submits the identical `SignedDelegateAction` on chain B. Because chain B independently forked from the same pre-fork state, Alice's access key nonce is also `N-1` there, and `max_block_height` is still in range, so `validate_delegate_action_key` accepts it again — Alice's actions execute a second time on chain B, without her having authorized a second execution and with no protocol-level way to distinguish "chain A" from "chain B" in the signed bytes.

pub struct SignableMessage<'a, T> {
    pub discriminant: MessageDiscriminant,
    pub msg: &'a T,
}

#[derive(Debug, Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Hash)]
#[non_exhaustive]
pub enum SignableMessageType {
    /// A delegate action, intended for a relayer to included it in an action list of a transaction.
    DelegateAction,
    /// A delegate action with gas key support, intended for a relayer to include it in an action
    /// list of a transaction.
    DelegateActionV2,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum ReadDiscriminantError {
    #[error("does not fit any known categories")]
    UnknownMessageType,
    #[error("NEP {0} does not have a known on-chain use")]
    UnknownOnChainNep(u32),
    #[error("NEP {0} does not have a known off-chain use")]
    UnknownOffChainNep(u32),
    #[error("discriminant is in the range for transactions")]
    TransactionFound,
}

#[derive(thiserror::Error, Debug)]
#[non_exhaustive]
pub enum CreateDiscriminantError {
    #[error("nep number {0} is too big")]
    NepTooLarge(u32),
}

impl<'a, T: BorshSerialize> SignableMessage<'a, T> {
    pub fn new(msg: &'a T, ty: SignableMessageType) -> Self {
        let discriminant = ty.into();
        Self { discriminant, msg }
    }

    pub fn sign(&self, signer: &Signer) -> Signature {
        let bytes = borsh::to_vec(&self).expect("Failed to deserialize");
        let hash = hash(&bytes);
        signer.sign(hash.as_bytes())
    }
