### Title
Missing duplicate-input/output-token validation in Tron `IntentGatewayV2.placeOrder` allows repeated-token escrow-accounting corruption - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Skyward exploit's root cause was `redeem_skyward` accepting an unvalidated array parameter (`token_account_ids`) and looping over it without rejecting repeats, letting the attacker redeem the same balance multiple times within one transaction. Hyperbridge's main EVM `IntentGatewayV2`/`IntrinsicIntents` contract was patched against the structurally identical bug — repeated token entries in an order's `inputs`/`outputs` array corrupting a single shared accounting bucket — as shown by dedicated regression tests. The Tron-targeted copy of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, does not carry this fix.

### Finding Description
In the current (fixed) EVM contract, `placeOrder` explicitly reverts with `InvalidInput()` when an order's `inputs` or `outputs` array contains the same token address more than once, per the regression tests: [1](#0-0) [2](#0-1) 

These tests are explicitly labeled as regression tests for "same-chain partial fills over-release repeated input escrow" and "same-chain partial fills prematurely finalize repeated output legs" — i.e., the exact bug class where a repeated token id in an array corrupts a single shared escrow/fill-tracking bucket.

The Tron contract's `placeOrder`, however, escrows tokens by accumulating into `_orders[commitment][token]` with `+=` per input leg, with no check that `token` is unique across `order.inputs`: [3](#0-2) [4](#0-3) 

The only per-leg check is `order.inputs[i].amount == 0`, not duplicate detection: [5](#0-4) 

Both `cancelOrder` (same-chain, cross-source, cross-destination) and the settlement `withdraw()` function build/consume `WithdrawalRequest.tokens` directly from `order.inputs` — the same array that was never deduplicated at placement time: [6](#0-5) [7](#0-6) [8](#0-7) 

`withdraw()`'s per-entry guard is `if (_orders[body.commitment][token] == 0) revert UnknownOrder();` — a nonzero-balance check, not an amount-sufficiency check — before transferring the entry's full `amount` and only then decrementing the shared bucket: [9](#0-8) 

Because two or more `order.inputs` legs for the same token merge into one `_orders[commitment][token]` bucket at placement, and `withdraw()`/`cancelOrder` iterate the same un-deduplicated array again at redemption/refund time, this is structurally the same bug class as Skyward's `redeem_skyward`: an attacker-controlled array with repeated identifiers is processed entry-by-entry against a single shared balance instead of being validated for uniqueness up front.

### Impact Explanation
An order placer can craft `order.inputs` with repeated token entries so that escrow accounting for that token is merged. Depending on fee-reduction interplay (`reducedInputs` vs. raw `order.inputs` amounts used at withdrawal — `_orders` is credited with `reducedInputs[i].amount` but `withdraw()` is invoked with the original, undiscounted `order.inputs` amounts as `WithdrawalRequest.tokens`), a solver/filler or the order owner can redeem/refund more than the actual escrowed principal for that token from the shared bucket, or can prematurely exhaust a shared bucket meant to back multiple distinct legs, causing legitimate fill/cancel accounting to fail (`UnknownOrder`/underflow revert) or to release more value than was ever escrowed for that specific leg. This is a fund-theft / fund-freezing class of bug reachable by any user who can call `placeOrder` and subsequently `fillOrder`/`cancelOrder` — a fully unprivileged path.

### Likelihood Explanation
Medium-High. Placing an order with a duplicated token address requires no special privilege — it is a normal `placeOrder` call — and the discrepancy between fee-reduced escrow accumulation and full-amount withdrawal replay is a direct, deterministic contract-logic path, not a probabilistic race. The main EVM contract's own regression-test commit messages ("this previously merged into one escrow bucket," "shares one `_partialFills` bucket") confirm the underlying merge behavior was previously exploitable and had to be explicitly patched — evidence this is a real, previously-realized bug class in this codebase, just unpatched in the Tron variant.

### Recommendation
Port the duplicate-input/output-token rejection logic from the current `IntentGatewayV2.sol`/`IntrinsicIntents.sol` (the checks validated by `testRevert_PlaceOrder_DuplicateInputTokens` and `testRevert_PlaceOrder_DuplicateOutputTokens`) into `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, rejecting orders whose `inputs` or `output.assets` contain repeated token addresses before any escrow accounting occurs.

### Proof of Concept
1. User calls `placeOrder` on the Tron `IntentGatewayV2` with `order.inputs = [{token: USDC, amount: A1}, {token: USDC, amount: A2}]` and `order.fees > 0` (protocol-fee path), so `_orders[commitment][USDC] += reducedInputs[0].amount; _orders[commitment][USDC] += reducedInputs[1].amount;` merges into one bucket valued at `reducedA1 + reducedA2 < A1 + A2`. [4](#0-3) 
2. On fill/cancel, `withdraw()` is invoked with `body.tokens = order.inputs` (the original, non-fee-reduced, duplicated array), transferring `A1` then checking/decrementing the merged bucket, then attempting to transfer `A2` again against the same bucket. [8](#0-7) 
3. Because the bucket check is `== 0` (not an amount-sufficiency check) and the amount transferred is always the full, undiscounted leg amount, the two transfers can together exceed the true escrowed principal for that token/commitment, over-releasing funds relative to what was actually deposited, or corrupting later legitimate withdrawals for that bucket.

**Note on confidence**: I was not able to fully trace the Tron contract's `fillOrder`/cross-chain settlement path within the available tool budget to construct a fully numeric end-to-end drain (i.e., confirm the exact relationship between `reducedInputs` amounts and the `order.inputs` amounts passed to `withdraw()` in every code path, and whether Solidity's checked-arithmetic underflow reverts fully close the gap in all fee configurations). The core finding — that the Tron `placeOrder` lacks the duplicate-token rejection present and regression-tested in the main EVM contract — is confirmed directly from the code and is a strong, file/line-supported analog to the Skyward unvalidated-array-parameter bug class. A full exploit trace would benefit from a Devin session with code-execution/testing access to confirm exact numeric bounds under specific fee/amount configurations.
