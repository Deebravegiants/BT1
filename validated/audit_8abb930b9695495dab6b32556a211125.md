Confirmed: `AuthQuery#to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb:34-43`) includes `shop` in the signed payload, but `Webhooks::Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:35-38`) returns only `@raw_body` — the `shop-domain` header (`Request#shop`, lines 20-23) is never part of the HMAC-signed bytes, yet `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) passes `request.shop` straight into `WebhookMetadata` for the handler to trust as the tenant identity.

### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop spoofing on otherwise-valid webhook deliveries - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` but binds the HMAC only to the raw request body, while the shop-tenant identity (`shop-domain` header) that the rest of the gem/handler ecosystem treats as authoritative is carried in an HTTP header that is completely outside the signed bytes.

### Finding Description
`Webhooks::Request#to_signable_string` returns `@raw_body` and nothing else: [1](#0-0) 
Meanwhile `shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signed string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC only against `verifiable_query.to_signable_string` (i.e., the body) using `Context.api_secret_key`, which is the **same secret for every shop that has installed the app**: [3](#0-2) 

`Registry.process` accepts the request once this body-only HMAC check passes, then forwards the unauthenticated `request.shop` value straight to the handler as the tenant identity: [4](#0-3) 

Contrast this with `Auth::Oauth::AuthQuery`, where the shop *is* included in the signed string, so the shop-identity binding is cryptographically enforced there: [5](#0-4) 

Because `api_secret_key` is shared across all shops that install the same app (it is the app's own secret, not a per-shop secret), any shop that has legitimately installed the app receives genuine webhook deliveries with a valid `hmac-sha256` value computed only over the body. Since the header carrying `shop` is unsigned, a party that controls one installed shop can capture a legitimately-signed webhook body/HMAC pair from their own shop and re-submit it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `Utils::HmacValidator.validate` will still report the signature valid (it only checks the body), and `Registry.process` will hand the handler a `WebhookMetadata` claiming to be from the victim shop while carrying attacker-chosen body content.

This breaks the identity binding: `hmac-signed bytes == bytes acted upon` no longer holds for `shop`, i.e. `shop-authenticated (via HMAC) != shop stored/acted-upon (from header)`.

### Impact Explanation
Any downstream host application that uses `WebhookMetadata#shop`/`request.shop` (as the documented API instructs consumers to do — see `docs/usage/webhooks.md` and `Webhooks::WebhookHandler#handle` contract) to select which tenant's data record/session to mutate is exposed to cross-tenant data corruption or state confusion: an attacker who controls their own installed shop can craft webhook bodies (e.g. `app/uninstalled`, `orders/create`, `shop/update`, etc., depending on which topics the host app subscribes to) that carry a body-only valid HMAC, then relabel the `shop-domain` header to target a different, victim shop. Because the gem provides no cryptographic binding between the verified bytes and the shop value, the host application cannot distinguish this forgery from a legitimate webhook for the victim shop using only the APIs this gem exposes (`HmacValidator.validate` + `Request#shop`). This matches the Critical "cross-tenant access" impact category, since it can be used to spoof one shop's webhook traffic as another's from an unprivileged/merchant-level position that requires no access token, no `client_secret`, and no `api_secret_key` compromise — only participation as any installed shop.

### Likelihood Explanation
Likelihood is High for any app that has more than one installed shop (the normal deployment model for a public/multi-tenant Shopify app): the attacker only needs their own store's installation to legitimately receive a signed webhook body, then can replay it against the same public endpoint with a modified `shop-domain` header. No secret material needs to be extracted; the HMAC is deterministic and valid for the replayed body as-is.

### Recommendation
Include the shop-domain header (and/or `webhook_id`/`topic`) inside the bytes that are HMAC-verified, e.g. compute `to_signable_string` over a canonical concatenation of `shop-domain header + raw_body` (mirroring how `AuthQuery` includes `shop` in its signed string), or otherwise cryptographically bind the header-derived `shop` to the signed payload before handing it to the handler in `WebhookMetadata`. At minimum, document prominently that `Request#shop` is unauthenticated relative to the HMAC and must not be trusted for tenant selection without independent verification (e.g., cross-checking against a known/installed shop list) by the host application.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`.
2. Shopify sends a legitimate webhook to the app for `attacker-shop.myshopify.com`:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-topic: orders/create`
   - Body: attacker-controlled order payload (attacker owns the shop, so they choose the order content).
3. Attacker intercepts/replays this exact request to the app's public webhook endpoint but changes only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this; `Utils::HmacValidator.validate` calls `to_signable_string`, which is `@raw_body` only — the header change does not affect the computed signature, so validation passes: [1](#0-0) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` where `request.shop` is now `victim-shop.myshopify.com`, even though the signed content originated from the attacker's shop: [6](#0-5) 
6. Any host-side logic keyed off `data.shop` (session lookup, tenant record update, uninstall handling, etc.) now operates on the victim shop's identity using attacker-supplied body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
