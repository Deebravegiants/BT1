### Title
Opaque router payloads can smuggle wallet-draining token transfers into the caller’s signed authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary

Controller swap strategies forward caller-supplied opaque `swap` bytes to the configured router and authorize only the controller’s exact input-token transfer. [1](#0-0)  A poisoned route can make venue code reached below the router request additional `caller.require_auth()` token transfers; Soroban simulation records those transfers under the caller’s controller authorization, and signing that tree authorizes theft beyond the routed collateral. [2](#0-1) 

### Finding Description

`swap_collateral` accepts attacker-controlled `swap` bytes and calls `withdraw_and_swap_from_supply` with them. [3](#0-2)  The shared `swap_tokens` path obtains the configured router, snapshots only the controller’s input/output balances, authorizes one exact controller-to-router transfer, and forwards the opaque payload to `execute_strategy`. [4](#0-3) 

The controller’s authorization helper creates exactly one controller-contract token-transfer authorization with no nested invocations. [5](#0-4)  It does not restrict code reachable below the router or the route payload, and the controller’s later checks only bound controller-held input spend and require a positive controller output. [6](#0-5) 

A malicious route can therefore contain a pool or venue address whose code requests authorization from the original caller and transfers an unrelated wallet token to an attacker. [7](#0-6)  The recorded authorization tree places that unrelated `transfer(caller, attacker, amount)` beneath the caller’s `swap_collateral` invocation. [8](#0-7) 

### Impact Explanation

A victim who signs the poisoned authorization tree loses wallet tokens unrelated to the lending position while the swap still completes normally. [9](#0-8)  The repository’s live authorization test confirms that adding the simulated malicious child authorizes the entire wallet-token transfer. [10](#0-9) 

The same shape applies to every controller strategy that forwards route bytes, including `multiply`, `swap_debt`, and `repay_debt_with_collateral`, because they share the opaque-router settlement boundary. [11](#0-10) 

### Likelihood Explanation

This requires the victim to submit and sign a poisoned route, so it is not exploitable solely by sending a transaction without user authorization. [12](#0-11)  A compromised quote path, frontend, SDK output, or malicious route provider can construct the payload and corresponding signed auth tree without any privileged protocol role. [13](#0-12) 

The controller’s positive-output and solvency checks do not detect unrelated wallet-token transfers because they measure only the controller’s balances. [14](#0-13) 

### Recommendation

Do not allow route execution to introduce caller-authorized sub-invocations beyond the expected strategy input pull. Constrain executable routes to governance-allowlisted venue contracts and opaque bytes to a router ABI that cannot invoke arbitrary addresses. At minimum, require route decoding plus signed-auth-tree inspection that permits only the expected controller/token transfer children and rejects every other caller-authorized transfer before signing.

### Proof of Concept

1. Alice holds `WALLET_BALANCE` of a token that is not part of the lending swap. [15](#0-14) 
2. An attacker supplies a `swap_collateral` route whose venue contract calls `token.transfer(alice, attacker, WALLET_BALANCE)`. [7](#0-6) 
3. Alice calls `swap_collateral`; the controller withdraws collateral and forwards the poisoned bytes through `swap_tokens`. [3](#0-2) 
4. Simulation records the rogue wallet transfer as a child of Alice’s controller authorization. [16](#0-15) 
5. With the honest childless tree, the host rejects the transfer and preserves Alice’s wallet balance. [17](#0-16) 
6. With the simulated poisoned tree signed, the transfer succeeds, Alice’s wallet token balance becomes zero, and the attacker receives `WALLET_BALANCE`. [10](#0-9)

**File:** docs/explanation/threat-model.md (L154-165)
```markdown
That bound covers the controller's own grant only. The router calls the pool
and token addresses its payload names and keeps no allowlist of them, so a
route can put third-party code on the call stack below the caller's
authorization. A token transfer that such code makes from the caller is
recorded by an honest simulation as a child of the caller's authorization
entry, and it executes if the caller signs that tree. The loss is then the
caller's wallet, not the routed amount, and neither the payload minimum nor the
final risk gate bounds it. An honest swap strategy gives the caller no child
entry, and a direct router swap gives exactly one input transfer. A client must
decode the route it signs and refuse an authorization tree with any other
child. The direct `execute_strategy` path has the same exposure for every swap
user.
```
