### Title
Unrecovered Native-Token Overpayment Permanently Locked in EvmHost - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept native `msg.value` and swap it through UniswapV2 for the exact fee-token amount required (`post.fee`/`get.fee`/`amount`). Any leftover native token from the swap is refunded to the swap's caller — the `EvmHost` contract itself — not to the paying user, and the contract has no accounting variable, event, or withdrawal path to reclaim that leftover value. This mirrors the reported "Locked Funds Due to Non-Executable Proposals" bug class: the contract's internal accounting (`_requestCommitments`) tracks only the intended/requested amount, not the actual amount that ends up custodied in the contract, so any surplus becomes permanently stuck with no recovery mechanism.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest()`: [3](#0-2) 

Whenever `msg.value > 0`, the entire `msg.value` is forwarded to `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The standard UniswapV2 router semantics for `swapETHForExactTokens` are to consume only as much ETH as needed to produce exactly `amountOut` fee tokens and refund the unused ETH back to `msg.sender` of that call. Because `EvmHost` itself calls the router (not the end user), any refunded/unused ETH lands on the `EvmHost` contract's own balance rather than being returned to the paying user.

After the swap, the accounting only records the intended fee:
```solidity
_requestCommitments[commitment] = FeeMetadata({sender: post.payer, fee: post.fee});
```
There is no tracking of, or ability to reclaim, the leftover native value that accumulated on the contract. A search of `EvmHost.sol` for withdraw/sweep/collect functionality found no such mechanism.

This is structurally the same root cause as the Ajna finding: funds actually held by the contract (the un-refunded swap remainder) are not reflected in — and therefore cannot be recovered through — the contract's internal accounting/treasury (`_requestCommitments`), so they become permanently locked. One of the local UniswapV2 wrapper implementations makes this worse: `GnosisUniswapV2Wrapper.swapETHForExactTokens` forwards the *entire* `msg.value` (not just `amountOut`) as wrapped token to `msg.sender` (i.e., to `EvmHost`), guaranteeing any overpayment is trapped: [4](#0-3) 

### Impact Explanation
Any unprivileged user dispatching a POST/GET request or funding a request's relayer fee via native token can lose the difference between the `msg.value` supplied and the actual native cost of the swap. Because the exact ETH needed for a Uniswap V2 swap cannot be predicted with certainty ahead of execution (price movement between quote and execution, or users deliberately over-supplying `msg.value` as a safety margin), overpayment is a common, expected occurrence rather than an edge case. The excess funds are not returned to the user, not credited to protocol fees/treasury, and are unrecoverable by any existing function — a permanent freezing of user funds inside the `EvmHost` contract.

### Likelihood Explanation
High. This path is reachable from a single unprivileged transaction — the `dispatch()`/`fundRequest()` calls used for standard cross-chain messaging — and requires no malicious governance, admin, or relayer action. Slight overestimation of `msg.value` (a routine practice to avoid transaction reverts from Uniswap slippage) is sufficient to trigger permanent fund loss on every affected call.

### Recommendation
After the swap, refund any leftover native token to the original caller (`_msgSender()`/`post.payer`) rather than leaving it on the host balance, e.g. by checking `address(this).balance` delta before/after the swap and sending the difference back to the payer. Alternatively, use `swapExactETHForTokens` semantics that revert on insufficient input rather than accepting arbitrary excess `msg.value`, or explicitly track and expose a sweep function for any native token dust so it can be recovered by the protocol/users, matching the recommended fix pattern of crediting unaccounted funds back rather than letting them become stranded.

### Proof of Concept
1. Alice calls `EvmHost.dispatch(DispatchPost)` with `post.fee = 100` fee-token units and sends `msg.value = 1 ether` (a safety margin above the quoted swap cost).
2. `swapETHForExactTokens{value: 1 ether}(100, path, address(this), deadline)` executes; suppose only `0.4 ether` is actually needed to receive exactly 100 fee-token units. The router refunds the remaining `0.6 ether` — but that refund is sent to `msg.sender` of the swap call, which is the `EvmHost` contract, not Alice.
3. `_requestCommitments[commitment]` is set with `fee: 100`; the `0.6 ether` now sitting in `EvmHost`'s balance is untracked by any state variable.
4. No function in `EvmHost.sol` exists to withdraw or sweep this native balance back to Alice or to a protocol treasury — the `0.6 ether` is permanently locked in the contract.

        if (msg.value > 0) {
            address[] memory path = new address[](2);
            address uniswapV2 = _hostParams.uniswapV2;
            path[0] = IUniswapV2Router02(uniswapV2).WETH();
            path[1] = feeToken();
            IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
                amount, path, address(this), block.timestamp
            );
        } else {
            IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), amount);
        }

        FeeMetadata memory metadata = _requestCommitments[commitment];
        if (metadata.sender == address(0)) revert UnknownRequest();

        metadata.fee += amount;
        _requestCommitments[commitment] = metadata;

    function swapETHForExactTokens(uint256 amountOut, address[] calldata, address, uint256)
        external
        payable
        returns (uint256[] memory)
    {
        if (amountOut > msg.value) revert MsgValueLessThanExactAmount();

        (bool sent,) = WETH().call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IERC20(WETH()).safeTransfer(msg.sender, msg.value);

        uint256[] memory out = new uint256[](1);
        out[0] = msg.value;
        return out;
