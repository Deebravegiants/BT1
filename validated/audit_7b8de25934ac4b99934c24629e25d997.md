### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on replayed webhook payloads - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` value used by the host application to attribute the webhook to a tenant is read from the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) HTTP header, which is never included in the signed material. This breaks the identity binding `shop authenticated == shop used to process/dispatch the webhook`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#hmac` derives the signature to compare from the `hmac-sha256` header: [2](#0-1) 

`Request#shop`, which the host app is expected to use to look up the tenant/session, is read straight from the `shop-domain` header without ever being run through the HMAC check or through `ShopValidator`: [3](#0-2) 

The `hmac_validator`/`VerifiableQuery` abstraction used elsewhere in the gem (e.g. OAuth's `AuthQuery#to_signable_string`) explicitly folds `shop` into the signed string so shop cannot be swapped without invalidating the signature: [4](#0-3)  By contrast, the webhook `Request` class signs only the body, leaving `shop` (and `topic`, `webhook_id`, `api_version`) fully attacker-controllable header values that ride along with a validly-signed body.

Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-shop), any HMAC that validates for one shop's webhook payload also validates for the identical payload replayed with a different `shop-domain` header. An unprivileged attacker who can obtain one legitimate `(raw_body, hmac)` pair — for example from their own store's webhook delivery, which they are fully entitled to receive as an app installer — can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary victim `shop-domain` header. `HmacValidator`/`Request#hmac` will report the signature as valid (`OpenSSL.secure_compare` only checks the body digest), yet `request.shop` will return the attacker-chosen victim domain.

### Impact Explanation
Any host application that follows this gem's documented pattern of using `Webhooks::Request#shop` to identify which tenant/session a webhook belongs to (e.g., to look up that shop's session/access token, update local per-shop records, or trigger tenant-scoped side effects) can be tricked into acting on data intended for shop A while attributing it to shop B. This is a cross-tenant identity-confusion vector rooted entirely in this gem's `Request` class: the "authenticated" HMAC guarantees only body integrity, not which shop the body belongs to, yet the class exposes `shop` as if it were an authenticated field.

### Likelihood Explanation
Exploitation only requires the attacker to be a legitimate (if unprivileged) app installer capable of receiving one webhook for their own store — no access to the `api_secret_key`, access tokens, or elevated privileges is needed. Because the API secret is shared across all shops for a given app, the replay/relabel works against every other tenant of that same app, making this a low-effort, no-special-access attack once the attacker has any one valid webhook payload+HMAC pair from their own account.

### Recommendation
Include an identity-binding field (the `shop-domain` header, and ideally `topic`/`webhook_id`) in the signed material verified by `Request`, or otherwise cryptographically bind `shop` to the HMAC before it is trusted — mirroring the approach already used in `AuthQuery#to_signable_string`, which folds `shop` into the signable string. At minimum, document prominently that `Request#shop` is unauthenticated header data and must never be used for tenant attribution without an independent, out-of-band verification (e.g., looking up a pre-existing session for the returned shop and confirming its access token still works), and consider validating `shop` with `ShopValidator` plus cross-checking it against `topic`-specific expectations before any tenant-scoped action is taken.

### Proof of Concept
1. Attacker installs the target app on their own store (`attacker.myshopify.com`) and receives a legitimate webhook: `POST /webhooks` with body `B` and header `Shopify-Hmac-Sha256: H` (valid because `H = HMAC(api_secret_key, B)`), plus `Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the exact same request to the app's webhook endpoint but changes only the `Shopify-Shop-Domain` header to `victim.myshopify.com` (or any other shop that installed the same app), leaving `body=B` and `Shopify-Hmac-Sha256=H` untouched.
3. The app calls `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` and then `Utils::HmacValidator`/`request.hmac` comparison — validation passes because `to_signable_string` only checks `B` against `H`, which is unchanged. [2](#0-1) 
4. The host application, following the gem's intended usage, reads `request.shop` and obtains `"victim.myshopify.com"`, and performs a tenant-scoped action (e.g., session lookup, data mutation) against the victim shop using attacker-supplied body content — despite the HMAC verification having "succeeded." [3](#0-2)
