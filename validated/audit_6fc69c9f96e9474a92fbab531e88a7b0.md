### Title
Webhook `shop` identity is taken from an unauthenticated header that is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the authenticity of an incoming webhook by computing an HMAC over the raw request body only, while the `shop` (and `topic`/`api_version`/`webhook_id`) values that are handed to the application's webhook handler are read directly from HTTP headers that are excluded from that signature computation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `topic`, `api_version`, `webhook_id`) are read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed bytes: [2](#0-1) 

`Webhooks::Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)` — i.e. it checks `HMAC(raw_body, api_secret_key)` — and then immediately trusts `request.shop` (from the unsigned header) to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature exclusively from `verifiable_query.to_signable_string`, so for a `Webhooks::Request` object that is just the raw body — the `shop-domain` header plays no role in the signature: [4](#0-3) 

The binding this breaks, stated as an equality that should hold but doesn't:
`shop authenticated by HMAC` ≠ `shop used to select the tenant in WebhookMetadata`.

The `api_secret_key` used to compute the HMAC is a single, app-wide secret shared by every merchant who installs the app — it is not shop-specific. Consequently, any merchant who has installed the app on their own store can trigger a real webhook to their own endpoint (or otherwise obtain a validly-signed raw body for a given topic/body), capture the `raw_body` + `hmac-sha256` header, and then POST that identical body directly to the app's webhook endpoint again, substituting an arbitrary value in the `shop-domain` header (e.g., a victim's shop). Because the shop header is never part of `to_signable_string`, `HmacValidator.validate` still returns `true`, and `Registry.process` calls the app's handler with `shop: <attacker-chosen victim shop>` — a value that was never authenticated at all.

### Impact Explanation
This is a cross-tenant boundary violation (Critical): the app is architecturally required to trust `request.shop` from `WebhookMetadata#shop` as the identity of the merchant the webhook data belongs to (that's the only shop reference the library provides in this data flow), yet that value has no cryptographic binding to the actually-authenticated bytes. An attacker with their own legitimate app installation can cause the host application to process/store data (e.g. `orders/create`, `customers/data_request`, `app/uninstalled`, etc.) under a victim shop's identity, corrupting or exfiltrating cross-tenant data, or triggering GDPR/compliance webhook handlers against a shop they don't control.

### Likelihood Explanation
Likelihood is high for any attacker who is themselves a merchant/developer with the app installed (a very low bar — mandatory/compliance webhooks are sent to every installer). No `api_secret_key`, access token, or privileged account for the *victim* shop is required — the attacker only needs their own valid installation to obtain a correctly-signed body, then a trivial HTTP replay with a modified header value.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header value inside the HMAC-signed payload, or otherwise cryptographically bind the shop identity to the signed body (e.g., verify the shop against a shop-scoped secret/session, or require the signature to cover `shop-domain + raw_body`). At minimum, document that `WebhookMetadata#shop` is unauthenticated and must be cross-checked by the application against an installed-shop registry before being trusted for tenant selection.

### Proof of Concept
```ruby
# Attacker has legitimately installed the app on "attacker-shop.myshopify.com"
# and triggers/receives a real webhook, capturing:
raw_body = '{"id": 1, "note": "hello"}'
valid_hmac_b64 = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the SAME body/signature but swaps the shop header to a victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (only raw_body is checked),
#    and the app's handler is invoked with shop: "victim-shop.myshopify.com"
```
