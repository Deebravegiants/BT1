## Title
Cross-tenant webhook forgery via shop-domain header not bound to HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC-SHA256 signature computed over the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that the handler subsequently trusts and acts on are read from HTTP headers that are never included in the signed material [2](#0-1) . This breaks the identity binding `bytes_verified_by_hmac == bytes_acted_on`: the signature only proves the *body* came from Shopify, not which *shop* it is attributed to.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `hmac` is read from the `hmac-sha256` header [3](#0-2) [4](#0-3) . `Utils::HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, raw_body)` and compares it against the received value [5](#0-4) . Nothing in this comparison covers `shop`, `topic`, `webhook_id` or `api_version`.

`Registry.process` uses exactly those unauthenticated header-derived fields to build the `WebhookMetadata` passed to the app's handler:
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [6](#0-5) 

`request.shop` is read verbatim from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cross-check against the signed body [7](#0-6) . The documentation explicitly tells host applications to trust `data.shop` to route/attribute the webhook to a tenant (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), reinforcing that this field is expected to be an authenticated tenant identifier [8](#0-7) .

**Root cause / broken equality:** the gem verifies `hmac == HMAC(secret, raw_body)` but then acts on `shop = header["shop-domain"]`, where `header["shop-domain"] ⊄ raw_body` (i.e., the value used for tenant attribution is disjoint from the value the signature actually covers).

### Impact Explanation
Any party capable of causing a *legitimately signed* webhook body to exist for the app — e.g., any merchant who installs the app on their own store (a normal, unprivileged action any internet user can take) — can capture a body+HMAC pair that Shopify sends them, then replay the identical `raw_body`/`hmac-sha256` value to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` (and `topic`/`webhook-id`) header. `HmacValidator.validate` will accept it because the signature check only looks at the body, and the app's handler will process the payload as belonging to the spoofed shop. Depending on how the host app uses `data.shop` (e.g., looking up a stored session/access token for that shop and mutating data, or writing incoming data keyed by `data.shop`), this can lead to cross-tenant data injection/corruption — a genuine tenant-isolation break in a multi-tenant SaaS app, matching the "cross-tenant access" impact class.

### Likelihood Explanation
High: the only prerequisite is the ability to install the target app on one's own (attacker-controlled) Shopify store — something any internet user can do for a public app — in order to receive at least one legitimately-signed webhook body/HMAC pair, and then replay it with a forged shop header directly to the app's HTTP webhook endpoint (bypassing Shopify entirely). No possession of the app's `api_secret_key`, access tokens, or any privileged credential is required.

### Recommendation
Bind the tenant/topic identity to the authenticated bytes: include `shop`, `topic`, `webhook_id`, and `api_version` in the signed material (e.g., construct the signable string from a canonical representation of headers + body, or independently verify `shop`/`topic` against Shopify's Admin API/webhook subscription registration for the session prior to trusting them), or at minimum document/enforce that host applications must additionally verify that `data.shop` corresponds to a shop with a currently valid, stored session/webhook registration for that exact `webhook_id`/topic before acting on the payload.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, triggering a legitimate webhook, e.g. `orders/create`. Shopify sends:
   - Body: `{"id":1,...}`
   - Headers: `x-shopify-hmac-sha256: <valid HMAC over body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
2. Attacker captures the raw body and the `x-shopify-hmac-sha256` value (both attacker-observable, since it's their own webhook).
3. Attacker sends a new POST directly to the app's public webhook endpoint with the **same body and same HMAC header**, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses headers/body [9](#0-8) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body [1](#0-0) .
5. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker's own order body, and the host application processes/stores it as data belonging to the victim shop [6](#0-5) .

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
