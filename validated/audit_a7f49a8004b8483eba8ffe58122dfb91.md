### Title
Webhook HMAC covers only the raw body, allowing shop/topic/webhook_id to be forged independently of the verified signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` cryptographically authenticates the *body bytes* alone. However, `Registry.process` dispatches the handler and builds `WebhookMetadata` using `request.topic`, `request.shop`, and `request.webhook_id`, all of which are read straight from unauthenticated HTTP headers. The bytes verified (body only) are not the same as the bytes acted upon (headers + body), breaking the intended binding: `verified(bytes) == acted_upon(bytes)`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

Its `hmac` method decodes the `shopify-hmac-sha256` header, and `to_signable_string` returns only `@raw_body`. Header fields such as `topic`, `shop`, `api_version`, and `webhook_id` are parsed from HTTP headers but are never included in the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the received HMAC using `verifiable_query.hmac`: [3](#0-2) 

Since `to_signable_string` for `Request` is just `@raw_body`, only the body is authenticated. `Registry.process` then trusts the unauthenticated header-derived fields to route and label the event: [4](#0-3) 

The equality that should hold is: `hmac_authenticated_fields == fields_acted_on_by_handler_dispatch`. In practice: `hmac_authenticated_fields = {raw_body}` while `fields_acted_on_by_handler_dispatch = {raw_body, topic, shop, webhook_id, api_version}`. The `topic`, `shop`, and `webhook_id` are outside the HMAC boundary, exactly the "bytes verified versus bytes parsed" mismatch called out in scope: `request.topic` selects which handler runs, and `request.shop` is forwarded into `WebhookMetadata` and trusted by the app as the originating tenant, yet neither is bound to the signature that was actually validated.

Because a single app secret (`api_secret_key`) signs webhook bodies for *every* installed shop, any merchant who has installed the app and can trigger a webhook for their own store legitimately obtains a `(raw_body, valid_hmac)` pair signed with the app's shared secret. That merchant can then replay the identical body with a forged `x-shopify-shop-domain` header (pointing at a different tenant) and/or a forged `x-shopify-topic` header, and `HmacValidator.validate` will still return `true` because the signature check never inspected those headers. The app's webhook handler will process the event as if it legitimately originated from, and pertains to, the impersonated shop.

### Impact Explanation
This allows a merchant with app access on their own store to submit forged webhook deliveries that are misattributed to an arbitrary other shop domain via `request.shop`, since that field is never covered by the signature that is actually checked. Depending on how the host application's handler uses `WebhookMetadata#shop` (e.g., to look up/update per-tenant records, deauthorize, or process customer-data-erasure requests), this is a cross-tenant data integrity/authenticity issue: the app processes an event "as" tenant B while it was actually authored/triggered against tenant A's signed payload. It can also be used to relabel a legitimate topic (e.g., turning a benign body into a `shop/redact` or `customers/data_request` event) if the body happens to satisfy the target handler's `parsed_body` expectations, since `topic` routing is likewise unauthenticated.

### Likelihood Explanation
Medium: it requires the attacker to be an app-installing merchant able to receive at least one legitimately signed webhook from their own shop (a low bar — any topic they subscribe to), and requires them to control the HTTP request delivered to the app's webhook endpoint (trivial, since delivery is just an HTTP POST the attacker can craft directly instead of relying on Shopify's delivery). No access to `api_secret_key` or another shop's credentials is needed.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (in addition to the raw body) in the string that is HMAC-verified, or otherwise cryptographically bind these header values to the signed payload before they are used for dispatch/attribution in `Registry.process`. At minimum, document and enforce that `WebhookMetadata#shop`/`#topic` must not be treated as authenticated unless the transport (mTLS/IP allowlisting) independently guarantees origin, since the gem's own HMAC check does not cover them.

### Proof of Concept
1. App subscribes to webhook topic `orders/create` for shop `attacker-shop.myshopify.com`.
2. Attacker triggers a real order creation event and captures the legitimately delivered POST: raw body `B` and header `x-shopify-hmac-sha256: H` (valid, computed by Shopify with the app's `api_secret_key` over `B`).
3. Attacker sends a new POST to the app's webhook endpoint with the same body `B` and same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Request#hmac` reads `H`; `to_signable_string` returns `B`; `Utils::HmacValidator.validate` recomputes HMAC over `B` and matches `H` — validation passes (`lib/shopify_api/utils/hmac_validator.rb:12-31`, `lib/shopify_api/webhooks/request.rb:35-43`).
5. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged headers and invokes the handler as if the event genuinely originated from/pertains to `victim-shop.myshopify.com` (`lib/shopify_api/webhooks/registry.rb:188-200`).

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
