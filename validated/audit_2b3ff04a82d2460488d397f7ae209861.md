Audit Report

## Title
Cross-user response hijacking via unvalidated, client-controlled MessageID collision in gateway webapi capabilities handler - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
The gateway's legacy webapi-trigger request path keys pending caller callbacks in a shared in-memory map (`savedCallbacks`) using the `MessageID` field taken verbatim from the untrusted, client-supplied JSON-RPC request `ID`. Because the write to this map is an unconditional overwrite with no uniqueness or ownership check, a second request using the same `MessageID` as an in-flight request silently replaces the first caller's registered callback, and the DON's eventual response for that `MessageID` is delivered to whichever callback currently occupies the slot.

## Finding Description
`gateway.ProcessRequest` decodes the JSON-RPC request `ID` straight from the raw, unauthenticated request body [1](#0-0) , and this value becomes `msg.Body.MessageID` inside `JSONRPCCodec.DecodeJSONRequest` [2](#0-1) . The only server-side check on this ID is a length cap (`<=200` chars) [3](#0-2) ; there is no uniqueness enforcement.

`handler.HandleLegacyUserMessage` stores the caller's `Callback` in a shared `map[string]*savedCallback` keyed solely by this attacker-controlled `MessageID`, unconditionally overwriting any existing entry: [4](#0-3) . Critically, `msg.Validate()` only requires *a* valid ECDSA signature from *any* keypair over the message body — it does not check the signer against a per-workflow or per-caller allowlist, and the code explicitly flags this gap: `// TODO: apply allowlist and rate-limiting here` [5](#0-4) . This confirms the caller is genuinely unprivileged — any self-generated keypair can produce a valid signed request.

When the corresponding DON node later replies with that `MessageID`, `handleWebAPITriggerMessage` looks up and deletes whichever callback currently occupies that map slot and delivers the node's response to it, with no verification against the original requester: [6](#0-5) .

The existing test suite only verifies that invalid/error-path messages don't leave stale `savedCallbacks` entries [7](#0-6) ; there is no test covering same-ID overwrite from two concurrent valid callers. Notably, the newer v2 trigger handler (`http_trigger_handler.go`) explicitly detects and rejects duplicate in-flight request IDs with a `jsonrpc.ErrConflict` / "in-flight request" error [8](#0-7) , demonstrating that this exact collision class is a recognized concern that was fixed in the newer implementation but remains unaddressed in the legacy `capabilities/handler.go` path used by `MethodWebAPITrigger`.

## Impact Explanation
An unprivileged caller (anyone able to sign a message with a self-generated key — no allowlist or sender-binding check exists at this layer) who submits a `web_api_trigger` request with a `MessageID` colliding with another in-flight request can hijack that request's response, or cause the legitimate caller's callback to be silently evicted and time out. This maps to the "gateway request impersonation / cross-user response corruption" impact class in scope for Chainlink gateway components, since the response payload intended for one caller is delivered to another based purely on a spoofable identifier.

## Likelihood Explanation
Exploitability requires colliding the `MessageID` with another concurrently pending, legitimate request. With `defaultCallbackMaxAgeSec` of 120 seconds providing a wide race window [9](#0-8) , and no requirement that IDs be unpredictable (clients using fixed, sequential, or short IDs make this trivial to trigger, and an attacker can also simply race a shared/observable ID), likelihood is realistic for the legacy DON-ID-routed path. The gap is structural (no uniqueness/ownership check by design), not a one-off implementation slip, and the analogous class was already fixed in the newer v2 handler, confirming the risk is real and previously unaddressed here.

## Recommendation
Namespace `savedCallbacks` keys by both caller identity (e.g., verified `msg.Body.Sender`) and the client-supplied `MessageID`, or generate a server-side unique correlation ID independent of client input. Reject (rather than silently overwrite) writes when a collision on an in-flight ID is detected, mirroring the duplicate-request-ID rejection already implemented in `v2/http_trigger_handler.go`.

## Proof of Concept
1. Caller A sends a `web_api_trigger` request through the gateway with JSON-RPC `id = "X"`, signed with any private key; this registers `savedCallbacks["X"] = callbackA` via `HandleLegacyUserMessage` [4](#0-3) .
2. Before a DON node responds, Caller B (attacker, using a different self-generated key) sends another request with the same `id = "X"`; this overwrites `savedCallbacks["X"] = callbackB`.
3. A DON node responds with `MessageID = "X"`; `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackB`, deletes the entry, and delivers the response to attacker B instead of Caller A, whose request then times out [6](#0-5) .
4. This can be encoded as a Go unit test analogous to the existing `TestHandlerReceiveHTTPMessageFromClient` in `handler_test.go`, but with two `HandleLegacyUserMessage` calls using distinct signers and the same `MessageID` before invoking `HandleNodeMessage`, asserting that `cbA.Wait` times out while `cbB.Wait` receives the DON's response.

```go
func (g *gateway) ProcessRequest(ctx context.Context, rawRequest []byte, auth string) (rawResponse []byte, httpStatusCode int) {
	// decode
	jsonRequest, err := jsonrpc2.DecodeRequest[json.RawMessage](rawRequest, auth)
	if err != nil {
		return newError("", api.UserMessageParseError, err.Error())
	}
	msg, err := g.codec.DecodeJSONRequest(jsonRequest)
	if err != nil {
		return newError(jsonRequest.ID, api.UserMessageParseError, err.Error())
	}
	if len(jsonRequest.ID) > 200 {
		// Arbitrary limit to prevent abuse
		return newError(jsonRequest.ID, api.UserMessageParseError, "request ID is too long: "+strconv.Itoa(len(jsonRequest.ID))+". max is 200 characters")
	}
```

```go
func (*JSONRPCCodec) DecodeJSONRequest(request jsonrpc2.Request[json.RawMessage]) (*Message, error) {
	var msg Message
	err := json.Unmarshal(*request.Params, &msg)
	if err != nil {
		return nil, err
	}
	msg.Body.MessageID = request.ID
	msg.Body.Method = request.Method
	return &msg, nil
}
```

```go
func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
```
