### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by checking only that the HMAC over the raw body matches a signature computed with the app's shared `api_secret_key`. The `shop` value that is then handed to the host app's handler as the tenant identifier comes from the `x-shopify-shop-domain` HTTP header, which is never included in the signed material.

### Finding Description
`Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

`Utils::HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string`, and for a webhook `Request`, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

The `shop` accessor, by contrast, is read straight from the header and is never included in the HMAC computation: [3](#0-2) 

`HmacValidator.validate_signature` only hashes `verifiable_query.to_signable_string` (the body) with `Context.api_secret_key`: [4](#0-3) 

Because Shopify webhooks for a given app are all signed with the same shared `api_secret_key` (not a per-shop secret), the equality the library implicitly relies on is:
`HMAC(raw_body, api_secret_key) valid` ⇒ `shop header == the shop that actually sent this body`

That equality does not hold: the HMAC only proves "this body was signed by holder of the app's secret" (i.e., genuinely came from Shopify for *some* installation of this app), not "this body belongs to the shop named in the `shop-domain` header." Any merchant who legitimately installs the app on their own store receives real webhooks with a valid HMAC over the body. They can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still passes because it only checks the body, and `Registry.process` forwards `request.shop` (the attacker-controlled header) as the trusted tenant identifier to the app's handler.

Per the docs, host applications are told to treat `data.shop` as trustworthy shop identification once `Registry.process` succeeds: [5](#0-4) [6](#0-5) 

### Impact Explanation
This breaks the tenant-identity binding the gem is supposed to provide: `Registry.process` is the library's sole authentication gate for webhooks, and a successful `validate` result is meant to assure the caller both that the request came from Shopify and which shop it concerns. An attacker who controls one shop (their own, freely installable) can forge webhooks attributed to any other shop that also has the app installed, because the `shop` binding is not part of the authenticated payload. Depending on how the host app uses `data.shop` (e.g., to look up/store per-shop records, trigger `app/uninstalled` cleanup, fulfill orders, or grant/revoke access), this enables cross-tenant data manipulation using only the credentials of an unprivileged attacker who legitimately installed the app on their own store — this matches the "cross-tenant access" impact category.

### Likelihood Explanation
Medium-high: exploitation requires only that the attacker be able to install the target app on a shop they control (typical for public apps) and replay a captured raw body + `hmac-sha256` header with a modified `shop-domain` header to the app's public webhook endpoint. No secrets, tokens, or privileged access are required beyond ordinary app installation.

### Recommendation
Bind the shop identity into the authenticated material, e.g., include the `x-shopify-shop-domain` header (and/or `webhook-id`) in the string that is HMAC-verified, or independently verify that the shop in the header corresponds to a shop known to have this specific webhook/API-version/topic combination registered (e.g., cross-check against the `webhook-id` returned only to that shop's registration) before trusting `request.shop`. At minimum, update `HmacValidator`/`Request#to_signable_string` so the signature covers the shop-identifying header, not just the raw body.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, a legitimate store they control.
2. Shopify sends a genuine webhook (e.g. `orders/create`) to the app's endpoint with headers `x-shopify-hmac-sha256: <valid HMAC over raw_body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker captures the raw body and valid HMAC, then re-sends the identical body/HMAC pair to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the body against `Context.api_secret_key` (`lib/shopify_api/utils/hmac_validator.rb:26-31`, `lib/shopify_api/webhooks/request.rb:35-38`).
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), causing the host app to process this forged webhook as if it genuinely originated from the victim shop.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
