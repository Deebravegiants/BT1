Audit Report

## Title
`submit_finality_proof`/`submit_finality_proof_ex` charge linear O(p+v) weight for a justification-verification loop whose worst-case cost is O(p×v) - (File: bridges/primitives/header-chain/src/justification/verification/mod.rs)

## Summary
The dispatch weight for `submit_finality_proof_ex` is computed purely as a linear function of the number of precommits `p` and votes-ancestries `v`, via `T::WeightInfo::submit_finality_proof_weight(p, v)`. However, `JustificationVerifier::verify_justification` calls `AncestryChain::ancestry` for every precommit *before* validating its signature, and only calls `mark_route_as_visited` (which prunes traversed nodes from `unvisited`) after a signature check succeeds. This asymmetry allows an attacker to submit precommits with valid-looking authority IDs but invalid signatures, forcing full re-traversal of the ancestry chain for each one, producing true O(p×v) verification work against an O(p+v) charged weight.

## Finding Description
`submit_finality_proof_ex` weighs the call strictly from the encoded lengths of `justification.commit.precommits` and `justification.votes_ancestries`: [1](#0-0) 

That weight function (`submit_finality_proof`) is linear in both `p` and `v`: [2](#0-1) 

The verification loop in `verify_justification` iterates precommits, and for each one calls `chain.ancestry(...)` before checking the signature: [3](#0-2) 

`AncestryChain::ancestry` walks the `parents` map from the precommit's target hash toward `base`, and only short-circuits early if the current node was already visited (i.e., removed from `unvisited` by a prior *successful* vote's `mark_route_as_visited` call): [4](#0-3) 

Crucially, `mark_route_as_visited` is only invoked after `process_valid_vote`, i.e., only when the precommit's signature check succeeds: [5](#0-4) 

If the signature check fails, `process_invalid_signature_vote` is called and the loop `continue`s without ever marking the traversed route as visited, so the traversed nodes remain in `unvisited` and will be re-walked in full by any subsequent precommit targeting the same (or an overlapping) chain. This confirms the root-cause claim: visited-bookkeeping is gated on signature success rather than performed unconditionally during traversal.

The one constraint on attack scale is that duplicate/unknown authority votes are rejected before reaching the ancestry walk. In the production (strict) verifier used by the pallet, `process_known_authority_vote` rejects a precommit whose `signed.id` was already used (`DuplicateAuthorityVote`), and `process_unknown_authority_vote` rejects IDs not in the voter set: [6](#0-5) 

This means `p` (the number of precommits that can reach the costly `ancestry()` call with a distinct/known authority id) is bounded by the size of the authority set `N`, not solely by an arbitrary attacker-chosen count — but signature *validity* is checked *after* this authority-membership check and after the `ancestry()` call, so an attacker can still supply up to `N` precommits, each with a distinct known authority ID and a deliberately invalid signature, each forcing a full re-walk of the `v`-length ancestry chain. This yields true O(N×v) work, where the charged weight remains linear O(N+v).

The compensating "extra fee" mechanism only fires when `votes_ancestries_len` exceeds a soft, non-strict constant (`REASONABLE_HEADERS_IN_JUSTIFICATION_ANCESTRY`), and even then charges only the same linear weight formula as an extra fee — it does not model or charge for the quadratic blow-up: [7](#0-6) [8](#0-7) 

There is no dispatch-time hard cap on `p` or `v` independent of the transaction extension check, and the transaction-extension-based limit check is itself only exercised when `is_free_execution_expected` is set: [9](#0-8) 

## Impact Explanation
Any signed, unprivileged account can call `submit_finality_proof_ex` (gated only by `ensure_signed`, not by any special permission), and the actual work performed by `verify_justification` scales as O(N×v) in the worst case rather than the O(N+v) captured by the weight formula, where `N` is the (public, on-chain) size of the current GRANDPA voter set and `v` is the attacker-chosen number of ancestor headers in `votes_ancestries`. This is a genuine mismatch between charged weight and actual computational cost, matching the "weight accounting broken / underpriced execution" class of issue for a bridge/finality-verification pallet in the Polkadot SDK. The magnitude of the mismatch is bounded by the size of the authority set (typically tens to low hundreds of validators in production bridged chains, not unbounded thousands), which somewhat limits — but does not eliminate — the severity relative to an unbounded O(p×v) with p unconstrained.

## Likelihood Explanation
The attack requires only public information: the current voter set (`CurrentAuthoritySet`, on-chain) and a header one block ahead of `BestFinalized` (also public). Constructing `N` precommits with valid authority IDs but corrupted signatures, plus `v` chained ancestor headers, is a pure off-chain construction requiring no privileged access or third-party cooperation, and is repeatable on every call. The `strict` verifier's authority-uniqueness/knownness checks are confirmed insufficient to prevent the attack because they run *before* the (costly) ancestry walk and signature check, not to gate re-traversal cost.

## Recommendation
Perform the `unvisited`/visited bookkeeping for the ancestry route as part of (or immediately after) the traversal in `AncestryChain::ancestry`, independent of whether the owning precommit's signature later validates, so that the total traversal cost across all precommits is amortized O(v) rather than O(p×v). Alternatively (or additionally), reorder the checks so cheap signature verification happens before the more expensive ancestry walk, and/or adjust `WeightInfo::submit_finality_proof` to account for the worst-case quadratic cost bound by the authority-set size, and enforce a hard dispatch-time cap on `votes_ancestries_len` regardless of `is_free_execution_expected`.

## Proof of Concept
1. Initialize the pallet with a `CurrentAuthoritySet` of `N` known authorities.
2. Construct a `GrandpaJustification` whose `votes_ancestries` contains a long chain of `v` headers from `base` to `head`, and whose `commit.precommits` contains `N` entries, each using a distinct known authority `id` (to pass `process_known_authority_vote`) but with `signature` corrupted so `check_message_signature_with_buffer` fails, and each `target_hash` set to `head` (forcing a full O(v) walk per precommit via `AncestryChain::ancestry`, since none of these routes are ever marked visited due to the invalid signature).
3. Call `submit_finality_proof_ex` with this justification and measure/instrument the number of `parent_hash_of`/BTreeMap lookups performed inside `verify_justification`, comparing it against the linear estimate implied by `T::WeightInfo::submit_finality_proof(N, v)`; demonstrate the actual lookup count grows as N×v rather than N+v as N and v are varied independently.

	/// Returns a route if the precommit target block is a descendant of the `base` block.
	pub fn ancestry(
		&self,
		precommit_target_hash: &Header::Hash,
		precommit_target_number: &Header::Number,
	) -> Option<Vec<Header::Hash>> {
		if precommit_target_number < &self.base.number() {
			return None;
		}

		let mut route = vec![];
		let mut current_hash = *precommit_target_hash;
		loop {
			if current_hash == self.base.hash() {
				break;
			}

			current_hash = match self.parent_hash_of(&current_hash) {
				Some(parent_hash) => {
					let is_visited_before = self.unvisited.get(&current_hash).is_none();
					if is_visited_before {
						// If the current header has been visited in a previous call, it is a
						// descendent of `base` (we assume that the previous call was successful).
						return Some(route);
					}
					route.push(current_hash);

					*parent_hash
				},
				None => return None,
			};
		}

		Some(route)
	}

	fn mark_route_as_visited(&mut self, route: Vec<Header::Hash>) {
		for hash in route {
			self.unvisited.remove(&hash);
		}
	}

pub fn submit_finality_proof_limits_extras<C: ChainWithGrandpa>(
	header: &C::Header,
	proof: &justification::GrandpaJustification<C::Header>,
) -> SubmitFinalityProofCallExtras {
	// the `submit_finality_proof` call will reject justifications with invalid, duplicate,
	// unknown and extra signatures. It'll also reject justifications with less than necessary
	// signatures. So we do not care about extra weight because of additional signatures here.
	let precommits_len = proof.commit.precommits.len().saturated_into();
	let required_precommits = precommits_len;

	// the weight check is simple - we assume that there are no more than the `limit`
	// headers in the ancestry proof
	let votes_ancestries_len: u32 = proof.votes_ancestries.len().saturated_into();
	let is_weight_limit_exceeded =
		votes_ancestries_len > C::REASONABLE_HEADERS_IN_JUSTIFICATION_ANCESTRY;

	// check if the `finality_target` is a mandatory header. If so, we are ready to refund larger
	// size
	let is_mandatory_finality_target =
		GrandpaConsensusLogReader::<BlockNumberOf<C>>::find_scheduled_change(header.digest())
			.is_some();

	// we can estimate extra call size easily, without any additional significant overhead
	let actual_call_size: u32 =
		header.encoded_size().saturating_add(proof.encoded_size()).saturated_into();
	let max_expected_call_size = max_expected_submit_finality_proof_arguments_size::<C>(
		is_mandatory_finality_target,
		required_precommits,
	);
	let extra_size = actual_call_size.saturating_sub(max_expected_call_size);

	SubmitFinalityProofCallExtras {
		is_weight_limit_exceeded,
		extra_size,
		is_mandatory_finality_target,
	}
}

	pub fn check_obsolete_from_extension(
		call_info: &SubmitFinalityProofInfo<BlockNumberOf<T::BridgedChain>>,
	) -> Result<BlockNumberOf<T::BridgedChain>, Error<T, I>> {
		// do basic checks first
		let improved_by = Self::check_obsolete(call_info.block_number, call_info.current_set_id)?;

		// if submitter has NOT specified that it wants free execution, then we are done
		if !call_info.is_free_execution_expected {
			return Ok(improved_by);
		}

		// else - if we can not accept more free headers, "reject" the transaction
		if !Self::has_free_header_slots() {
			tracing::trace!(
				target: crate::LOG_TARGET,
				chain_id=?T::BridgedChain::ID,
				block_number=?call_info.block_number,
				"Cannot accept free header. No more free slots remaining"
			);

			return Err(Error::<T, I>::FreeHeadersLimitExceded);
		}

		// ensure that the `improved_by` is larger than the configured free interval
		if !call_info.is_mandatory {
			if let Some(free_headers_interval) = T::FreeHeadersInterval::get() {
				if improved_by < free_headers_interval.into() {
					tracing::trace!(
						target: crate::LOG_TARGET,
						chain_id=?T::BridgedChain::ID,
						block_number=?call_info.block_number,
						?improved_by,
						%free_headers_interval,
						"Cannot accept free header. Too small difference between submitted headers"
					);

					return Err(Error::<T, I>::BelowFreeHeaderInterval);
				}
			}
		}

		// let's also check whether the header submission fits the hardcoded limits. A normal
		// relayer would check that before submitting a transaction (since limits are constants
		// and do not depend on a volatile runtime state), but the ckeck itself is cheap, so
		// let's do it here too
		if !call_info.fits_limits() {
			return Err(Error::<T, I>::HeaderOverflowLimits);
		}

		Ok(improved_by)
	}

/// Extract finality proof info from the submitted header and justification.
pub(crate) fn submit_finality_proof_info_from_args<T: Config<I>, I: 'static>(
	finality_target: &BridgedHeader<T, I>,
	justification: &GrandpaJustification<BridgedHeader<T, I>>,
	current_set_id: Option<SetId>,
	is_free_execution_expected: bool,
) -> SubmitFinalityProofInfo<BridgedBlockNumber<T, I>> {
	// check if call exceeds limits. In other words - whether some size or weight is included
	// in the call
	let extras =
		submit_finality_proof_limits_extras::<T::BridgedChain>(finality_target, justification);

	// We do care about extra weight because of more-than-expected headers in the votes
	// ancestries. But we have problems computing extra weight for additional headers (weight of
	// additional header is too small, so that our benchmarks aren't detecting that). So if there
	// are more than expected headers in votes ancestries, we will treat the whole call weight
	// as an extra weight.
	let extra_weight = if extras.is_weight_limit_exceeded {
		let precommits_len = justification.commit.precommits.len().saturated_into();
		let votes_ancestries_len = justification.votes_ancestries.len().saturated_into();
		T::WeightInfo::submit_finality_proof(precommits_len, votes_ancestries_len)
	} else {
		Weight::zero()
	};

	SubmitFinalityProofInfo {
		block_number: *finality_target.number(),
		current_set_id,
		is_mandatory: extras.is_mandatory_finality_target,
		is_free_execution_expected,
		extra_weight,
		extra_size: extras.extra_size,
	}
}
