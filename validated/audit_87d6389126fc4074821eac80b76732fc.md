### Title
Webhook HMAC verification signs only the request body, letting an attacker with any valid (body, hmac) pair spoof the `shop-domain` identity - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC solely against that signable string [2](#0-1) . The `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers that are never included in the signed bytes [3](#0-2) , yet `Registry.process` passes `request.shop` directly into `WebhookMetadata` given to the app's handler after only checking the body HMAC [4](#0-3) .

### Finding Description
The identity binding that should hold is:
`shop header used by the handler == shop that Shopify actually signed the delivery for`

In practice, the gem only enforces:
`HMAC(secret, raw_body) == received_hmac`

The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers are not part of the signed payload and are trusted verbatim [5](#0-4) . Any actor who has received a legitimate webhook delivery for their own shop (e.g., by installing the target app on their own store, which is normal, unprivileged access) possesses a valid `(raw_body, hmac)` pair signed with the app's `client_secret`. Because the header carrying the shop identity is outside the signed bytes, that same `(raw_body, hmac)` pair remains valid if replayed with a different `shopify-shop-domain` header value. `Registry.process` will pass HMAC validation and hand the attacker-chosen shop value straight to the app's handler as `WebhookMetadata#shop` [6](#0-5) .

This mirrors the report's bug class: a request is authenticated at the byte level (HMAC covers only the body) but the identity field the application actually acts on (`shop`) is not bound to that authentication, breaking the equality between "the shop the signature was issued for" and "the shop the handler believes it is acting for."

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to select which tenant's data to read/write (a standard multi-tenant pattern) can be tricked into applying another merchant's webhook event under an attacker-controlled shop identifier, or vice versa — attributing a victim shop's data mutation to an attacker's own shop context. This is a cross-tenant identity confusion vulnerability reachable by any unprivileged actor who has installed the target app once on a store they control, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is limited but non-trivial: it requires the attacker to already have received at least one legitimate webhook delivery for a store they control (trivial — any developer/merchant can install the app), and requires the target app to key business logic off the unsigned `shop` field from `WebhookMetadata` rather than an independently verified value — which is the documented/expected usage pattern shown in the gem's own webhook handler examples.

### Recommendation
Include the `shop`, `topic`, `webhook_id`, and `api_version` header values in the signable string used for HMAC verification (or otherwise cryptographically bind them to the signed payload), so that tampering with any of these headers invalidates the signature, matching Shopify's documented webhook verification guidance of validating the header value against the raw body it was issued for.

### Proof of Concept
1. Install the target app (built with this gem) on attacker-controlled shop `attacker.myshopify.com`; capture one legitimate webhook delivery, including its raw body and the `X-Shopify-Hmac-Sha256` header — a valid signature over that body computed with the app's real `client_secret`.
2. Replay the exact same body + HMAC header to the app's webhook endpoint, but replace the `X-Shopify-Shop-Domain` header with `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers [7](#0-6) , and `HmacValidator.validate` succeeds because it only checks the unchanged body bytes [8](#0-7) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)` [9](#0-8) , causing the app to act on the victim shop's identity using attacker-supplied event data.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
