### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is trusted for tenant identification but is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body, then hands the app's handler a `WebhookMetadata` struct whose `shop` (and `topic`, `webhook_id`) fields are read straight from unauthenticated HTTP headers. Because the app-level `client_secret` used to sign webhooks is shared across every shop that installs the app, a malicious merchant can capture one of their own genuinely-signed webhooks and resend it to the app's endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop, producing a body whose HMAC still validates while the tenant identity the handler receives is forged.

### Finding Description
`Webhooks::Registry.process` does:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [4](#0-3) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`:
```ruby
def to_signable_string
  @raw_body
end
``` [5](#0-4) 

But `shop`, `topic`, `api_version`, and `webhook_id` are all parsed from HTTP headers, which are never fed into the signable string:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [6](#0-5) 

This is exactly the "field acted on but not covered by the HMAC" bug class: the equality the code implicitly assumes is `shop (header, used for tenant routing) == shop (that Shopify actually generated the signed body for)`, but nothing enforces that binding. Contrast this with the OAuth callback path, where `AuthQuery#to_signable_string` explicitly includes `shop` in the signed parameters that are HMAC-verified [7](#0-6) , showing the library's own pattern for correctly binding an identity field to the signature — a pattern not followed for webhook headers.

Because a single app's webhook signing secret (`client_secret`) is identical for all shops that install the app, any merchant who installs the app can obtain validly-signed webhook bodies for their own shop, then replay that exact body to the app's webhook endpoint while substituting a different shop's domain in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still returns `true` (the body/signature pair is untouched), and the handler receives `WebhookMetadata#shop` set to the attacker-chosen value.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to decide which tenant's data to update, delete, or synchronize (the documented and intended use, per `docs/usage/webhooks.md`-style patterns and the `WebhookMetadata` struct's design), this allows a low-privileged, legitimate-but-malicious merchant to inject forged data attributed to another merchant's shop, or overwrite/trigger redaction/compliance flows (e.g. `shop/redact`, `customers/redact`) against a shop they don't own. This is cross-tenant access/data confusion caused entirely by unprivileged interaction with the gem's own webhook-processing API — no access token, TLS interception, or credential leakage is required.

### Likelihood Explanation
Any merchant who installs the target app is, by definition, an unprivileged-but-authenticated party with respect to the app's multi-tenant boundary. They can trivially receive real signed webhooks for their own store (e.g. by triggering an `orders/create` event) and replay them with a modified `shop-domain` header using any HTTP client, since the header is not part of what's cryptographically bound. No secret material needs to be obtained — the replayed body/HMAC pair is valid as issued by Shopify itself.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signable representation used by `Webhooks::Request#to_signable_string`, or otherwise cryptographically bind them (e.g. verify HMAC over `headers + body` rather than body alone), so that tampering with these headers invalidates the signature. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and that host applications must independently confirm the shop is one they have an active, matching installation/session for before trusting the payload.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Attacker triggers a webhook (e.g. updates a product) and captures the raw POST body plus the `X-Shopify-Hmac-Sha256` header sent by Shopify to the app's registered webhook endpoint.
3. Attacker resends the identical raw body and HMAC header to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — validation succeeds because the body is byte-for-byte identical to what Shopify actually signed. [8](#0-7) 
5. `handler.handle` is invoked with `WebhookMetadata#shop == "victim-shop.myshopify.com"` even though the payload content belongs to the attacker's shop, letting the host application apply attacker-controlled data under the victim's tenant identity.
