### Title
Webhook `shop` Identity Not Bound to HMAC Signature Enables Cross-Tenant Data Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, while the `shop` (and `topic`) values used to attribute and route that payload are taken from unauthenticated HTTP headers. This mirrors the reported bug class: an identity/authorization-relevant field (`shop`) is acted upon by the application logic but is not covered by the cryptographic binding (the HMAC), letting an attacker decouple "who signed this data" from "who the data is attributed to."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` (and `topic`, `webhook_id`, `api_version`) are read directly from attacker-controllable HTTP headers, independent of the HMAC: [2](#0-1) 

`Registry.process` validates only the body/HMAC pair via `Utils::HmacValidator.validate(request)`, and then immediately builds `WebhookMetadata` using the unauthenticated `request.shop` and `request.topic` to dispatch to the merchant-specific handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely over `to_signable_string` (the body) using the app's single, shared `api_secret_key`: [4](#0-3) 

Because a multi-tenant app uses **one** `api_secret_key` for every installed shop, any party who has legitimately received one authentic `(raw_body, hmac)` pair for their own shop (e.g., a merchant who installed the app on their own store — an "unprivileged" party with respect to other tenants) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a different, victim shop. `HmacValidator.validate` will still pass, because the HMAC never covered the `shop` field, yet `Registry.process` will hand the handler a `WebhookMetadata` object claiming the payload came from the victim shop.

This is the same class of defect described in the report: the `permit` HMAC binds only part of the intended state transition (the `PermitSingle`/nonce), while a second identity-relevant action (`_FEE_RECEIVER_` transfer) is executed without being separately authorized — the signature does not cover everything that is subsequently trusted. Here the webhook HMAC binds only the body, while the `shop` identity that keys application-level tenant logic is trusted without being bound to that same signature.

### Impact Explanation
This breaks the identity binding `shop_that_signed_the_HMAC == shop_the_handler_believes_sent_it`. A host application's webhook handler (built per the documented `WebhookMetadata#shop` contract) typically uses this `shop` value to look up per-tenant data/sessions and apply the body's contents. An attacker can cause the app to process/attribute one tenant's legitimate webhook payload as if it belonged to a different, arbitrary tenant, corrupting per-tenant state or triggering tenant-scoped side effects for a shop that never sent that data — a cross-tenant integrity/confusion issue that maps to the "cross-tenant access" Critical category, since the isolation boundary between tenants (which the shared app secret is supposed to preserve per-shop via the `shop-domain` binding) is not actually enforced by this gem's HMAC validation.

### Likelihood Explanation
Any actor who can install the target app on at least one shop (a routine, unprivileged action available to any Shopify merchant) automatically receives genuinely-signed webhooks for that shop, since the same `api_secret_key` signs webhooks for every installation of the app. No `api_secret_key`, access token, or privileged access is required beyond this normal, low-barrier installation step, and the replay only requires rewriting one HTTP header, making this readily reachable.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the `shop` header to the signed body (e.g., by having `Registry.process` require the caller to supply/verify an expected shop and reject mismatches against a store-specific secret, or by deriving/confirming shop identity from a value that is itself covered by the signature). At minimum, document prominently that `request.shop` is unauthenticated and must not be trusted for tenant attribution without additional binding, and consider exposing a "verify webhook for expected shop" API that fails when the header shop cannot be corroborated by data inside the signed body.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`. The app is multi-tenant and uses a single `api_secret_key`.
2. Shopify sends a genuine webhook to the app for `attacker-shop.myshopify.com`, e.g. body `{"id":123,"note":"hello"}` with header `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures this `(raw_body, hmac)` pair (they legitimately received it) and resends it directly to the app's webhook endpoint, but changes only the header:
   `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only — unaffected by the header change — and the check passes: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: {"id":123,"note":"hello"}, ...)`, causing the app to process attacker-controlled data attributed to a shop the attacker does not control. [6](#0-5)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
