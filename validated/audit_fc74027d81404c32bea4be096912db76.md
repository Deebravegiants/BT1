## Title
Webhook `shop` (tenant) identity is trusted without HMAC coverage, enabling cross‑tenant webhook forgery — (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the shop identity taken from the `X-Shopify-Shop-Domain` header — a value that is never included in the HMAC computation. The binding "shop the signature vouches for" == "shop the handler acts on" does not hold, so any request whose body produces a valid signature can be attributed to an arbitrary shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is read straight from a header that has no relationship to the signature at all: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively from `to_signable_string`, i.e. from the body: [3](#0-2) 

`Registry.process` validates only this body-based HMAC and then immediately uses the unauthenticated `request.shop` value to build the tenant-scoped `WebhookMetadata` that is handed to the app's handler: [4](#0-3) 

Because the `api_secret_key` is a single shared secret for the whole app (identical for every shop that installs it, not per-tenant), any shop that has legitimately installed the app can obtain a validly-signed body/HMAC pair from its own genuine webhook deliveries. That same body+HMAC pair remains valid when replayed with the `X-Shopify-Shop-Domain` header changed to a victim shop's domain, because the header is outside the signed material. The identity equality that should hold —

`shop_covered_by_HMAC == shop_used_for(WebhookMetadata#shop passed to handler)`

— is broken: the left side is undefined (no shop is covered by the HMAC at all) while the right side is fully attacker-controlled.

### Impact Explanation
This crosses a tenant boundary: a party with access to any one shop's genuine webhook (a normal, unprivileged merchant/installer of the app) can produce a request that the gem will accept as authentic and dispatch to the app's webhook handler under a different shop's identity. Depending on how the host application keys off `WebhookMetadata#shop` (e.g., looking up a merchant record, writing data, revoking access on `app/uninstalled`, etc.), this can lead to cross-tenant data corruption or actions being taken against a merchant's data namespace without their consent — squarely a "cross-tenant access" class impact enabled purely by this gem's verification logic, which validates the payload but silently trusts an unauthenticated header for tenant attribution.

### Likelihood Explanation
Any user who can install the app on a shop they control (a low bar — Shopify apps can typically be installed on free development stores) automatically receives legitimately HMAC-signed webhook deliveries for their own shop. Replaying that payload with a modified `Shop-Domain`/`shopify-shop-domain` header against the app's public webhook endpoint requires no secret knowledge and no privileged access — only capturing/observing one's own webhook traffic, which is trivial since the attacker owns that shop.

### Recommendation
Bind the tenant identity into the value that is actually authenticated: either include the shop domain (and other identity-bearing headers) in the signed material used by `to_signable_string`, or independently corroborate `request.shop` against the app's own installation/session store (looked up by an identifier that is itself derived from data protected by the HMAC) before invoking the handler. At minimum, `Registry.process` should not treat `request.shop` as trusted merely because `Utils::HmacValidator.validate(request)` passed, since that validation never touches the shop field.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (any unprivileged user can do this on a dev store).
2. Attacker's shop legitimately triggers a webhook (e.g. `orders/create`) and captures the exact raw POST body `B` and its valid `X-Shopify-Hmac-Sha256` header `H`, both generated by Shopify using the app's shared `api_secret_key`.
3. Attacker sends a forged POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `B` — it succeeds because `H` was always valid for `B`. [4](#0-3) 
5. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the app to process/act on data as if it originated from `victim-shop`, despite the request never being authenticated for that shop.
