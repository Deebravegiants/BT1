### Title
On-chain use of Uniswap V2 spot price for native-fee dispatch is sandwichable, letting an attacker underpay bridging fees at the protocol/relayer's expense - (File: `sdk/packages/core/contracts/apps/HyperApp.sol`)

### Summary
`HyperApp.quote()` and the corresponding `EvmHost` native-fee path price the ETH-denominated dispatch fee directly off a live `IUniswapV2Router02.getAmountsIn` call. The protocol's own documentation explicitly flags this as sandwichable and says it must only be used off-chain, yet `dispatch{value: ...}` for native-fee payers ultimately performs the real swap on-chain against that same manipulable pool at transaction time.

### Finding Description
`HyperApp.quote(DispatchPost)` / `quote(DispatchGet)` compute the native (ETH) amount required for a dispatch fee by calling `IUniswapV2Router02(_uniswap).getAmountsIn(request.fee, path)` where `path = [WETH, feeToken]`: [1](#0-0) 

This is a single-block spot-price read of a Uniswap V2 pool's reserves — the same primitive the referenced Malt report abuses (manipulate the AMM, then have a dependent on-chain calculation execute against the distorted price). The project's own documentation confirms this exact risk and instructs integrators to never call it from a contract: [2](#0-1) 

Despite that warning being aimed at integrators querying it off-chain, the `EvmHost` itself performs the equivalent conversion on-chain when a user pays the dispatch fee in native token (`dispatch{value: cost}(...)`), and a fork test explicitly reconstructs the same `getAmountsIn` computation to compute a required `msg.value`: [3](#0-2) 

Because the amount of native token that must actually be swapped into `feeToken` for the relayer/protocol fee is derived from the pool's *current* reserves, an attacker who front-runs their own `dispatch` call with a large swap that moves the pool (e.g., dumping WETH into the fee-token pool to cheapen WETH in fee-token terms, or the reverse) can force the on-chain swap to convert their attached ETH into a smaller amount of `feeToken` than intended, or extract the pool's spread by back-running with the opposite trade. This mirrors the report's pattern precisely: manipulate the price feed an on-chain state-changing function trusts, execute the state-changing call at the distorted price, then reverse the manipulating trade to lock in profit — at the expense of the fee token holders/relayers/protocol who expected the fee to be priced at a fair market rate.

### Impact Explanation
A successful sandwich lets an unprivileged caller dispatch cross-chain POST/GET requests while paying a manipulated (artificially cheap) amount of native token relative to the `feeToken` fee actually owed, or otherwise extract value from the AMM pool that the Host relies on for pricing. Since relayers are paid out of the `fee` field in the `feeToken` denomination (per `docs/content/developers/network/relayer.mdx` and `pallet-ismp-relayer`), a systematically underpriced native-to-feeToken conversion reduces the effective relayer/protocol revenue collected per dispatch, or drains value from the Uniswap pool used for the conversion — a direct value-extraction vector reachable from a single permissionless `dispatch` transaction.

### Likelihood Explanation
Medium. It requires the attacker to have capital to move the specific Uniswap V2 pool used for `feeToken`/WETH pricing (often thin on the pairs Hyperbridge chooses, e.g. DAI/WETH on lower-liquidity destination chains), and flash-loan-based front-run/back-run infrastructure — well within reach of MEV searchers, exactly as in the referenced report. The severity depends on the liquidity depth of the configured `uniswapV2` pool per `HostParams.uniswapV2`.

### Recommendation
Do not perform the native→feeToken conversion against a live spot AMM price inside a single atomic transaction that an attacker controls the surrounding trades of. Options:
- Require the payer to pre-quote off-chain and pass a `maxNativeIn`/slippage bound, reverting if the on-chain swap would need more than that bound (already partly true via `swapETHForExactTokens`'s max-in slippage protection, but this only bounds the payer's own loss, not manipulation of the fee actually delivered).
- Use a TWAP or a volume-weighted internal price (as already implemented for same-token intents in `VWAPOracle`, see `evm/src/utils/VWAPOracle.sol`) rather than instantaneous `getAmountsIn`/`getAmountsOut` reserves for any conversion that occurs inside the same transaction as the triggering call.
- Alternatively, restrict/mark native-fee dispatch as an integrator-only, pre-quoted flow (fee token payment already bypasses this issue entirely, per `dispatchWithFeeToken`), and consider deprecating on-chain native dispatch given the docs already discourage on-chain use of `quote()`.

### Proof of Concept
1. Attacker identifies an EVM chain where `HostParams.uniswapV2` points to a low-liquidity WETH/`feeToken` pool.
2. Attacker flash-loans a large amount of WETH (or `feeToken`) and swaps it through the same pool to shift reserves, making WETH artificially cheap in `feeToken` terms.
3. In the same transaction (or the immediately following block), attacker calls `IDispatcher(host).dispatch{value: nativeAmount}(post)` where `nativeAmount` was computed/allowed against the manipulated reserves — as `EvmHost` will internally swap native for `feeToken` via the same router (`evm/src/core/EvmHost.sol`, confirmed by the router/path wiring in `HyperApp.quote` and `EvmHostForkTest.quote`), the attacker's `dispatch` is settled paying less native for the same `feeToken` fee amount than the pool's fair price would require.
4. Attacker reverses the initial swap, extracting the difference as profit and repaying the flash loan, leaving the protocol/relayer under-compensated (or the pool's LPs worse off) for the fee actually delivered — directly analogous to the referenced Malt "stabilize" sandwich, where a permissionless, price-dependent on-chain action is manipulated via a flash-loan sandwich for guaranteed profit at other participants' expense.

    /**
     * @dev returns the quoted fee in the native token for dispatching a POST request
     */
    function quote(DispatchPost memory request) public returns (uint256) {
        address _host = host();
        address _uniswap = IDispatcher(_host).uniswapV2Router();
        address[] memory path = new address[](2);
        path[0] = IUniswapV2Router02(_uniswap).WETH();
        path[1] = IDispatcher(_host).feeToken();
        return IUniswapV2Router02(_uniswap).getAmountsIn(request.fee, path)[0];
    }

    function testCanDispatchFundRequestWithNative() public {
        // dispatch request
        vm.prank(whaleAccount);
        bytes32 commitment = host.dispatch(
            DispatchPost({
                body: abi.encode(bytes32(0)),
                payer: whaleAccount,
                fee: 0,
                dest: StateMachine.evm(421614),
                timeout: 0,
                to: abi.encode(bytes32(0))
            })
        );
        assert(host.requestCommitments(commitment).sender == whaleAccount);
        assert(host.requestCommitments(commitment).fee == 0);

        // fund request
        vm.prank(whaleAccount);
        uint256 newfee = 10 * 1e18;
        host.fundRequest{value: quote(newfee)}(commitment, newfee);
        assert(host.requestCommitments(commitment).fee == newfee);

        // can't fund unknown requests
        uint256 cost = quote(newfee);
        vm.expectRevert(EvmHost.UnknownRequest.selector);
        vm.prank(whaleAccount);
        host.fundRequest{value: cost}(keccak256(hex"dead"), 10 * 1e18);
    }
