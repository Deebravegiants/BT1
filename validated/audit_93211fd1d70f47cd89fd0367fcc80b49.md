### Title
Stale-seed private key remains cached in `CachedSodiumEncryptor` and never invalidated on seed removal, allowing decryption of a removed seed's `WALLET_INFO` secure storage after `removeSeed`/`addSeed` - ([File: features/cached-sodium-encryptor/module/cached-sodium-encryptor.ts])

### Summary
`CachedSodiumEncryptor#getPrivateKey` caches derived private keys forever in an in-memory `Map`, keyed only by `seedId` + key components (`features/cached-sodium-encryptor/module/cache.ts`), and is never cleared on `wallet.removeSeed`/`removeManySeeds`. Since `EXODUS_KEY_IDS.WALLET_INFO` is in `ALLOWED_KEY_IDS` specifically because "secure storage is unlocked only once ... and never re-locked" (`features/cached-sodium-encryptor/module/cached-sodium-encryptor.ts:30-35`), once a seed's `WALLET_INFO` key has been cached, `decryptSecretBox({ seedId, keyId: WALLET_INFO })` for that seed keeps working forever within the process even after the underlying seed is removed from the keychain.

### Finding Description
`createUnlockEncryptedStorage` (`sdks/headless/src/unlock-encrypted-storage.js:12-21`) wires `encryptedStorage.unlock` to closures that call `cachedSodiumEncryptor.encryptSecretBox`/`decryptSecretBox` with the wallet's primary `seedId` and `EXODUS_KEY_IDS.WALLET_INFO`. The very first read/write to `WALLET_INFO`-encrypted storage triggers `#getPrivateKey` (`features/cached-sodium-encryptor/module/cached-sodium-encryptor.ts:54-63`), which:
1. Checks `#checkIfAllowed` (only `keyId`, not `seedId`, is checked against `ALLOWED_KEY_IDS`).
2. Computes `cacheKey = getCacheKey({ seedId, keyId })` — composed purely from `seedId`, `keyId.keyType`, `derivationAlgorithm`, `derivationPath`, `assetName` (`features/cached-sodium-encryptor/module/cache.ts:8-21`).
3. If not cached, calls `#derivePrivateKey` → `keychain.exportKey({ keyId, seedId, exportPrivate: true })` and stores the raw private key in `this.#cache` (a plain `Map`, never expired, never invalidated).

`wallet.removeSeed`/`removeManySeeds` (`features/wallet/module/wallet.js:173-193`) calls `keychain.removeSeeds`, which deletes the seed's masters from the keychain (`features/keychain/module/keychain.js:131-145`), so a *direct* `keychain.exportKey({ seedId, keyId })` call for a removed seed now throws `seed with id "<seedId>" is not initialized"` (confirmed in `features/wallet/module/__tests__/index.test.js:443-458`). However, `CachedSodiumEncryptor` is a completely separate long-lived instance with its own private `#cache` Map that is never notified of, or cleared on, seed removal. Because the cache lookup in `#getPrivateKey` short-circuits before ever calling `keychain.exportKey` again once an entry exists, a subsequent `decryptSecretBox({ seedId: <removedSeedA>, keyId: WALLET_INFO, data: oldCiphertext })` call bypasses the keychain entirely and returns the plaintext using the stale cached key — even though the keychain itself would now reject any fresh derivation for that `seedId`.

This matches the exact sequence in the question: `unlock(seedA)` (populates cache via `unlockEncryptedStorage`) → `removeSeed(seedA)` (keychain deletes seedA's masters, but cache is untouched) → `addSeed(seedB)`/`unlock(seedB)` (new primary seed) → `decryptSecretBox({ seedId: seedA, keyId: WALLET_INFO, data: oldCiphertext })` still succeeds and discloses seedA's prior `WALLET_INFO` plaintext (tx history, address cache, NFTs, etc.) using the cached key instead of throwing.

### Impact Explanation
This is a secret-disclosure bug: plaintext belonging to a removed/replaced seed remains decryptable indefinitely from within the running process via the `cachedSodiumEncryptor` module/API surface (also exposed as an RPC/API feature, `features/cached-sodium-encryptor/api/index.ts:8-17`, `sdks/headless/src/features/cached-sodium-encryptor-rpc/index.js`). Concretely, `WALLET_INFO`-encrypted secure-storage entries tied to a removed seed (tx history, address cache, NFT data, etc.) remain retrievable by anyone able to invoke `decryptSecretBox` with the stale `seedId`, violating the invariant that "secrets stay secret after seed removal."

### Likelihood Explanation
Preconditions are realistic and require no special privilege beyond code that can call the `cachedSodiumEncryptor` module/API (already exposed as a public IOC module/API and RPC feature) with an arbitrary `seedId`. It requires: (1) the target seed's `WALLET_INFO` key to have been derived/cached at least once (guaranteed by `unlockEncryptedStorage` running on every `unlock` for the primary seed, `sdks/headless/src/index.js:153-160`), and (2) the seed later being removed via `wallet.removeSeed`/import-triggered seed swap. No cryptographic secrets need to be leaked externally — the bug is entirely in-process cache lifecycle management, making it deterministically reproducible.

### Recommendation
Invalidate `CachedSodiumEncryptor`'s internal `#cache` entries (or the whole cache) whenever a seed is removed. Concretely: expose a cache-invalidation hook/method on `CachedSodiumEncryptor` (e.g., `invalidate(seedId)` or `clear()`), and call it from `wallet.removeManySeeds`/`removeSeed` (`features/wallet/module/wallet.js:173-193`) and from `keychain.removeSeeds` (`features/keychain/module/keychain.js:131-145`) for every removed `seedId`, or subscribe to a `remove-seed`/`removeSeeds` event to purge matching cache keys before the removal completes.

### Proof of Concept
Integration test (extending `features/wallet/module/__tests__/index.test.js` "removes a single seed" pattern, combined with `cached-sodium-encryptor.test.ts`):
1. Create `CachedSodiumEncryptor` wired to a real `keychain`; `addSeed(seedA)`.
2. Call `cachedSodiumEncryptor.encryptSecretBox({ seedId: seedIdA, keyId: WALLET_INFO, data })` to populate the cache and obtain `ciphertext`.
3. Call `wallet.removeSeed(seedIdA)` (or `keychain.removeSeeds([seedA])`) — assert `keychain.exportKey({ seedId: seedIdA, keyId: WALLET_INFO })` now throws `seed with id "..." is not initialized`.
4. Call `cachedSodiumEncryptor.decryptSecretBox({ seedId: seedIdA, keyId: WALLET_INFO, data: ciphertext })`.
   - Expected (secure) behavior: throws, matching keychain state.
   - Actual (buggy) behavior: resolves successfully and returns the original plaintext `data`, proving the stale cached key survives seed removal. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6)

export const ALLOWED_KEY_IDS = [
  // 'WALLET_INFO' is used for secure storage - everything that's not the seed/private keys. Examples: tx-history, address cache, nfts, etc.
  // for historical reasons, secure storage is unlocked only once during the runtime lifecycle of the application, and never re-locked.
  EXODUS_KEY_IDS.WALLET_INFO,
  EXODUS_KEY_IDS.FUSION,
]

export class CachedSodiumEncryptor {
  readonly #keychain: Keychain
  readonly #cache = new Map<string, Buffer>()

  constructor({ keychain }: Dependencies) {
    this.#keychain = keychain
  }

  async #derivePrivateKey({ keyId, seedId }: KeySource) {
    const { privateKey } = await this.#keychain.exportKey({ keyId, seedId, exportPrivate: true })
    return privateKey
  }

  #checkIfAllowed = ({ keyId }: KeySource) => {
    return ALLOWED_KEY_IDS.some((allowedKeyId) => KeyIdentifier.compare(allowedKeyId, keyId))
  }

  #getPrivateKey = restrictConcurrency(async (params: KeySource) => {
    assert(this.#checkIfAllowed(params), 'Key source not allowed for caching.')

    const cacheKey = getCacheKey(params)
    if (!this.#cache.has(cacheKey)) {
      this.#cache.set(cacheKey, await this.#derivePrivateKey(params))
    }

    return this.#cache.get(cacheKey)
  }) as (keySource: KeySource) => Promise<Buffer>

export const getCacheKey = ({ keyId, seedId }: CacheParams) => {
  const components = [
    seedId,
    keyId.keyType,
    keyId.derivationAlgorithm,
    keyId.derivationPath,
    keyId.assetName,
  ]

  return components
    .filter(Boolean)
    .map((component) => encodeURIComponent(component!))
    .join('/')
}
