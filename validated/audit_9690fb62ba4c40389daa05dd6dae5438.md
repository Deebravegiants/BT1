## Title
Insufficient Chainlink oracle round validation in `SimplexPaymaster._getOraclePrice` allows stale/incomplete round data to price gas payments - (File: `evm/src/utils/SimplexPaymaster.sol`)

### Summary
`SimplexPaymaster._getOraclePrice` reads Chainlink `latestRoundData()` but discards `roundId` and `answeredInRound` entirely, checking only that the answer is positive and that `updatedAt` is within `maxOracleAge`. This mirrors the reported bug class exactly: Chainlink's own integration guidance requires verifying `answeredInRound >= roundId` to detect carried-over/incomplete round answers, and this check is missing. [1](#0-0) 

### Finding Description
`_getOraclePrice` is the sole gate on native/token price feed data used to compute how much ERC-20 the permissionless paymaster charges a UserOperation sender for gas:

```solidity
function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
    (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();
    if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
    if (block.timestamp - updatedAt > maxOracleAge) {
        revert StaleOraclePrice(address(oracle), updatedAt);
    }
    ...
}
``` [2](#0-1) 

`roundId` and `answeredInRound` are both discarded via the tuple's blank slots. Per Chainlink's documented `AggregatorV3Interface`, when `answeredInRound < roundId` the round has not yet been officially answered and the value returned is carried over from a stale round — this can occur during oracle outages, sequencer/feed-provider disruptions, or during a round transition where `updatedAt` still nominally reflects a "recent enough" timestamp to pass the staleness bound, while the actual answer is not the round's true finalized value. This is precisely the condition the referenced external report calls out (`BondChainlinkOracle.sol#L135`), and the recommended fix (`require(answeredInRound >= roundId)`) is absent here.

This function underpins `_tokenPrice`, which is reachable by any address that submits a UserOperation through this permissionless ERC-4337 v0.8 paymaster: [3](#0-2) 

and is exposed directly to any external caller via `getTokenPrice`/`estimateTokenCost`: [4](#0-3) 

The contract's own docs confirm it is "Fully onchain, permissionless ... accepts ERC-20 stablecoins ... for gas payment," i.e., reachable by any unprivileged bandwidth purchaser (gas sponsee): [5](#0-4) 

### Impact Explanation
`_getOraclePrice` output directly determines `_tokenPrice`, which sets how many ERC-20 tokens are pulled from a UserOperation sender's balance via `PaymasterERC20`/Permit2 to cover gas. If a carried-over/incomplete round is accepted because `updatedAt` still falls within `maxOracleAge`, the paymaster can charge users based on an incorrect price — either overcharging depositors (loss of user funds) or undercharging (drain of the paymaster's EntryPoint deposit/treasury, since gas is fronted in native currency but repaid in mispriced ERC-20). Given `MAX_ORACLE_AGE` is configurable up to 7 days and stablecoin feeds are deployed with heartbeats up to 24h, the window in which a stale-but-"fresh-enough" round could be accepted (and abused) is non-trivial.

### Likelihood Explanation
This is not something an attacker can force at will — it depends on the underlying Chainlink feed entering a stuck/incomplete round state — but it is a well-known operational failure mode for Chainlink aggregators (and has occurred historically on several feeds). Because the paymaster is fully permissionless and this pricing path executes on every single UserOperation it sponsors, any oracle-side incident directly and immediately translates into mispriced gas payments across all users of the paymaster, with no additional safeguard beyond the (insufficient) staleness check.

### Recommendation
Restore all five return values from `latestRoundData()` and add the round-completeness check recommended by Chainlink and by the referenced report:

```solidity
(uint80 roundId, int256 answer, , uint256 updatedAt, uint80 answeredInRound) = oracle.latestRoundData();
if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
if (answeredInRound < roundId) revert StaleOraclePrice(address(oracle), updatedAt);
if (block.timestamp - updatedAt > maxOracleAge) revert StaleOraclePrice(address(oracle), updatedAt);
```

### Proof of Concept
1. A Chainlink price feed used by `SimplexPaymaster` (either `nativeOracle` or a registered token's `tokenOracle`) enters a round where the aggregator has not yet produced a fresh answer for the current `roundId` (`answeredInRound < roundId`), returning a carried-over answer whose `updatedAt` is still within `maxOracleAge`.
2. Any user submits a UserOperation using the Simplex paymaster's mode 0/1/2 gas sponsorship.
3. `_tokenPrice` → `_getOraclePrice` accepts the stale/incomplete round because only `answer > 0` and the `updatedAt` staleness bound are checked (`SimplexPaymaster.sol:662-668`).
4. The user's ERC-20 charge (via `estimateTokenCost`/`_erc20Cost` in the `postOp` flow) is computed from the incorrect price, resulting in over- or under-collection of tokens relative to the true market price and gas cost actually fronted by the paymaster.

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
