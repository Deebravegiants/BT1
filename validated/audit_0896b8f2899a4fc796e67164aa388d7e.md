This confirms the asymmetry: for OAuth callbacks, `shop` is part of the HMAC-signed payload via `AuthQuery#to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb:34-43`), but for webhooks, `Request#to_signable_string` only returns `@raw_body` (`lib/shopify_api/webhooks/request.rb:36-38`), while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers (`lib/shopify_api/webhooks/request.rb:16-33`) that are never included in the HMAC computation (`lib/shopify_api/utils/hmac_validator.rb:26-31`).

### Title
Webhook `shop`, `topic`, and `webhook_id` headers are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC over the raw request body, but the `shop-domain`, `topic`, `webhook-id`, and `api-version` values used to route and attribute the payload are taken from unauthenticated HTTP headers that are excluded from that HMAC.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` gates processing on `Utils::HmacValidator.validate(request)` [1](#0-0) . That validator recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` header value [2](#0-1) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — nothing else [3](#0-2) . Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled directly from HTTP headers with no relation to the signed bytes [4](#0-3) . These unverified values are then handed to the application's webhook handler as trusted identity/routing data: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))` [5](#0-4) .

This is a genuine asymmetry within the gem itself: for the comparable OAuth callback flow, `AuthQuery#to_signable_string` explicitly folds `shop` into the signed content (`code`, `host`, `shop`, `state`, `timestamp`) [6](#0-5) , so `shop` is cryptographically bound to the HMAC there. No equivalent binding exists for the webhook `shop` header. The equality that should hold — `shop value verified by HMAC == shop value delivered to the handler` — does not hold: the HMAC only proves `body bytes signed by Shopify's secret == raw_body`, while `request.shop` is an independent, attacker-controllable header.

### Impact Explanation
An attacker who legitimately owns/administers one Shopify store (or merely observes one valid webhook delivery, e.g., from their own dev store) obtains a valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key`. Because the header fields are outside the signed content, the attacker can replay that same body/HMAC pair to the app's webhook endpoint while substituting `x-shopify-shop-domain` with a victim shop's domain, and/or substituting `x-shopify-topic`/`x-shopify-webhook-id` with different values. `Utils::HmacValidator.validate` still returns `true` because only `raw_body` is checked, so `Registry.process` proceeds and delivers `WebhookMetadata` with `shop` set to the attacker-chosen victim domain to the host application's handler. Any host application that uses `data.shop` to scope tenant data (a very common Shopify app pattern) will attribute attacker-supplied body content to the victim tenant — a cross-tenant data injection/confusion condition using only the gem's own trusted-looking validation result.

### Likelihood Explanation
Any user who can install the app on a store they control (or intercept one legitimate delivery to any store) can harvest a valid `(body, hmac)` pair without needing the app's `api_secret_key`, an access token, or any privileged credential. Forging arbitrary header values on an HTTP POST is trivial. The only constraint is that `raw_body` must stay byte-identical to a previously observed valid delivery, which still allows meaningful topic/shop confusion (e.g., replaying a `customers/create` payload while relabeling it as belonging to a different shop).

### Recommendation
Include the identity-critical headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signed content for webhooks, or otherwise cryptographically bind them (e.g., re-deriving/confirming the `shop` from a source that Shopify signs, such as validating it against the session/shop the webhook was registered for). At minimum, `Utils::HmacValidator` should be extended so `Webhooks::Request#to_signable_string` incorporates the header values that `Registry.process` and downstream handlers rely on for tenant attribution, mirroring what `Auth::Oauth::AuthQuery` already does for `shop`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers any webhook (e.g., `orders/create`), capturing the raw POST body and its `x-shopify-hmac-sha256` header — both valid under the app's `api_secret_key`.
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
3. `Utils::HmacValidator.validate(request)` returns `true` (body unmodified) [7](#0-6) , so `Registry.process` proceeds and calls the host handler with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body content [8](#0-7) .
4. The host application, trusting `data.shop` per this gem's documented `WebhookMetadata` contract, stores/acts on the attacker's payload as if it belonged to the victim's store.
