Confirmed: the docs explicitly state that `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0) , and `data.shop` is documented as a trusted field the handler should key its logic on [2](#0-1) . However, `Request#hmac`/`to_signable_string` binds the HMAC only to `@raw_body`, never to the `shop-domain` header [3](#0-2) , and `Registry.process` validates the HMAC and then trusts `request.shop` to build `WebhookMetadata` without any additional binding [4](#0-3) .

#### Title
Webhook shop-domain header is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify" before invoking the app's handler [5](#0-4) . In reality only the raw body is authenticated; the `shop` value passed to the handler is taken verbatim from an HTTP header that is entirely outside the HMAC computation.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field [6](#0-5) . For webhook requests, `Request#to_signable_string` returns only `@raw_body` [7](#0-6) , while `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cryptographic tie to the signed bytes [8](#0-7) .

`Registry.process` validates the HMAC (`Utils::HmacValidator.validate(request)`), and then, without re-checking `request.shop` against anything, builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` and dispatches it to the app-supplied handler [4](#0-3) . The identity binding the gem's own documentation implies — "shop == the shop that produced this signed payload" — is never enforced in code; the HMAC only proves "body == what was signed with the app's `client_secret`," not "shop == the tenant this body belongs to."

Because a merchant can install the app on their own store and thereby obtain arbitrarily many genuinely-Shopify-signed `(raw_body, hmac)` pairs for topics whose body content they influence (e.g. `orders/create`, `products/update`, `app/uninstalled`), that attacker-controlled merchant can replay one of their own valid `(raw_body, hmac)` pairs to the app's public webhook endpoint while substituting the `shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` still passes (it never looked at the header), and `Registry.process` hands the handler a `WebhookMetadata` claiming to be from the victim shop while carrying attacker-chosen body content.

### Impact Explanation
Any host application that follows the documented contract — trusting `data.shop` from a processed webhook as the authenticated tenant identifier, as the gem's own usage docs instruct [2](#0-1)  — can be made to attribute attacker-controlled webhook data (order records, product updates, `app/uninstalled` events, etc.) to a different merchant's tenant. This is a cross-tenant data-integrity/authentication issue: the "verified" shop identity delivered by the gem is not actually bound to the HMAC that the gem itself computes and asserts as proof of Shopify origin.

### Likelihood Explanation
Exploitation requires only: (1) the attacker installs the target app on a shop they control (a normal, unprivileged action any merchant can take), (2) they capture one legitimate webhook `(raw_body, hmac)` pair delivered to their own configured endpoint (trivial, since they operate the receiving server or can proxy/log it), and (3) they replay it to the app's public webhook URL with a forged `shopify-shop-domain` header. No access to `client_secret`, no TLS interception, and no privileged Shopify credentials are needed — this is exactly the class of "field acted on but not covered by the HMAC" identity-binding break described in the report's bug class.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind `Request#shop` to the verified payload before it is exposed to handlers — analogous to including `shop`/`host` in `AuthQuery#to_signable_string` for OAuth callbacks [9](#0-8) . At minimum, document prominently that `data.shop` from `WebhookMetadata` is *not* covered by the HMAC and must be independently validated against a known/installed-shop list by the host application before being trusted.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and registers an `orders/create` webhook.
2. Attacker places an order to trigger a real Shopify webhook delivery, capturing the exact `raw_body` and the `shopify-hmac-sha256` value Shopify sent (both fully valid, since Shopify itself computed the HMAC with the app's real `client_secret`).
3. Attacker POSTs the same `raw_body` and `shopify-hmac-sha256` to the app's public webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` → `Utils::HmacValidator.validate(request)` returns `true` (body/HMAC pair is genuinely valid) [10](#0-9) ; `WebhookMetadata` is built with `shop: "victim-shop.myshopify.com"` [11](#0-10) ; the handler processes attacker-controlled order data as though it belongs to the victim's store.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
