### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook forgery via header substitution - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop` value taken from an HTTP header that was never part of the signed material, and hands that unauthenticated tenant identity to the app's webhook handler.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

but `Webhooks::Request#shop` is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of `to_signable_string`: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC only against `verifiable_query.to_signable_string` (i.e., the raw body): [3](#0-2) 

`Registry.process` then relies on this validation to authenticate the whole request, but forwards `request.shop` — the unsigned header value — directly to the app's registered handler as the tenant identity: [4](#0-3) 

This breaks the identity binding: `shop_authenticated_by_hmac` (implicitly "whatever body was signed") ≠ `shop_used_by_handler` (`request.shop`, read from a header that is never mixed into the HMAC computation). Any request whose raw body carries a valid HMAC for the configured `api_secret_key` will pass validation regardless of the `shop-domain` header value attached to that same request.

### Impact Explanation
Because `shop` is not part of the signed payload, an attacker who can obtain one validly-signed webhook body (for example, by triggering a real webhook delivery to their own installed app/shop, or by controlling body content that produces a fixed, replayable signature) can resend that exact body to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header. `Utils::HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` passes the attacker-chosen `shop` into `WebhookMetadata` unmodified. If the host application's handler uses this `shop` value to select the tenant record/session to act on (the documented purpose of `WebhookMetadata#shop`), the attacker can cause actions to be attributed to, or performed against, a shop they do not control — a cross-tenant impact.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP POST to the app's public webhook endpoint with attacker-controlled headers and a body for which the attacker already possesses a valid HMAC (e.g., a body they can replay from a legitimate delivery, or one that is otherwise predictable/replayable). No access token, `client_secret`, or privileged credential is needed — only network access to the endpoint, matching the "unprivileged internet user" threat model.

### Recommendation
Include the shop identifier (and ideally topic/webhook-id) inside the HMAC-covered material, or otherwise cryptographically bind `shop` to the verified payload before it is handed to `Registry.process`/handlers — e.g., verify that the shop domain matches a value embedded in and covered by the signed body, or require callers to separately authenticate the shop via a mechanism bound to the signature (similar to how `Auth::Oauth::AuthQuery#to_signable_string` includes `shop` explicitly).

### Proof of Concept
1. Attacker observes/replays a webhook body `B` and its valid `X-Shopify-Hmac-Sha256` signature `S` (computed by Shopify over `B` with the app's `api_secret_key`) — e.g., from a delivery to their own shop `attacker.myshopify.com`.
2. Attacker sends `POST /webhooks` to the target app with:
   - Header `X-Shopify-Hmac-Sha256: S`
   - Header `X-Shopify-Shop-Domain: victim.myshopify.com`
   - Header `X-Shopify-Topic: <topic>`
   - Body `B` (unchanged)
3. `Webhooks::Request.new` parses headers/body normally; `Utils::HmacValidator.validate` recomputes HMAC over `B` only and it matches `S`, so validation passes (`lib/shopify_api/utils/hmac_validator.rb:13-22`, `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` calls `handler.handle(data: WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed_body, ...))` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though `victim.myshopify.com` never sent or signed this request.
5. The host handler processes the event as if it legitimately originated from `victim.myshopify.com`, achieving cross-tenant impact.
