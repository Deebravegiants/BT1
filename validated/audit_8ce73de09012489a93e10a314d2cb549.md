### Title
Unchecked `Factory.getPair` lookup in `Zap._swapOnUniswapV2` lets a post-graduation trade dereference `address(0)`, permanently DoS-ing sells/buys on a graduated token - ([File: packages/contracts/src/Zap.sol])

### Summary
`ALPINE-CVE-2018-15859` is a class of bug where a lookup (`ExprResolveLhs`) can fail and return an invalid/NULL result, and the caller uses that result without checking, causing a crash. The same unchecked-lookup pattern exists in `Zap._swapOnUniswapV2`, which resolves the post-graduation HyperSwap pair via `Bonding.graduatedPair(tokenIn)`/`graduatedPair(tokenOut)` and immediately dereferences the result with `IUniswapV2Pair(pair).token0()` without ever checking `pair != address(0)`.

### Finding Description
`Router.sol`, `Router.previewBuy`, `Router.sell`, and `Router.graduate` all defensively check `if (pairAddr == address(0)) revert PairNotFound();` after a `factory.getPair` lookup [1](#0-0) , [2](#0-1) , [3](#0-2) . `Zap._swapOnUniswapV2`, however, resolves the graduated pair with the same lookup-may-fail pattern and skips the check entirely: [4](#0-3) 

`pair` is looked up from `bonding_.graduatedPair(tokenIn)` and falls back to `bonding_.graduatedPair(tokenOut)`; both reads are plain mapping getters that return `address(0)` on any lookup miss — see `Bonding.graduatedPair`: [5](#0-4) 

Critically, `Bonding.sol` never writes to `$.graduatedPair` in the excerpted graduation logic visible in this scan (the mapping is declared at [6](#0-5)  but only read via the public getter). If `finalizeGraduation`/`_prepareGraduationLiquidity` (not shown in the truncated read) fails to populate `graduatedPair[token]` for any already-`Lifecycle.Graduated` token — e.g. a race between `isGraduated()` flipping true and the pair-registration write, or any code path that marks lifecycle `Graduated` before the mapping write — `bonding_.graduatedPair(tokenIn)` and the fallback both return `address(0)`, and `_swapOnUniswapV2` immediately calls `IUniswapV2Pair(address(0)).token0()`, which reverts against an EOA with no bytecode (`address(0)` has no code), rather than surfacing a clean, checked "pair not found" error.

This is unprivileged-reachable: any trader calling `Zap.buy`/`Zap.sell`/`Zap.buyWithPermit`/`Zap.sellWithPermit` on a token that `Bonding.isGraduated(tokenAddress)` reports `true` for routes straight into `_buyOnUniswapV2`/`_sellOnUniswapV2` → `_swapOnUniswapV2` [7](#0-6) , [8](#0-7) .

### Impact Explanation
If `graduatedPair` is ever unpopulated (or desynced) for a token marked `Graduated`, every buy and sell for that token through `Zap` reverts unconditionally with no recovery path other than a contract upgrade, because `_swapOnUniswapV2` is the sole post-graduation trade venue exposed by `Zap` and it has no `address(0)` guard. That is a permanent freezing of trading funds/functionality for that token's holders (their tokens/LT become untradeable through the sanctioned entrypoint), which satisfies the "permanent freezing of trader funds" impact bar even though it manifests as a revert rather than silent fund transfer.

### Likelihood Explanation
Reaching the vulnerable line requires no privilege — any trader calling `Zap.buy`/`sell` on a graduated token exercises this exact code path. The likelihood of the *mapping actually being empty* depends on code not visible in this scan (the write site inside `finalizeGraduation`/`_prepareGraduationLiquidity`, which was truncated from the read tool output), so it cannot be conclusively proven here that `graduatedPair` is ever left unset for a `Graduated` token; it is asserted as the plausible root cause given the mapping's declaration and getter are present but no write site appeared in the read source. This uncertainty means the finding should be treated as a code-quality/defense-in-depth gap confirmed at the `Zap.sol` call site, with the exact trigger condition (an unset mapping entry) not fully verified against `Bonding.sol`'s graduation-finalization code, which exceeded the file read limit.

### Recommendation
Add an explicit zero-address check immediately after resolving `pair` in `Zap._swapOnUniswapV2`, mirroring the pattern already used in `Router.previewBuy`/`sell`/`graduate`:
```solidity
address pair = bonding_.graduatedPair(tokenIn);
if (pair == address(0)) pair = bonding_.graduatedPair(tokenOut);
if (pair == address(0)) revert PairNotFound();
```
Additionally, audit every write site of `_s().graduatedPair` in `Bonding.sol` to confirm it is set atomically with (or strictly before) the lifecycle flip to `Lifecycle.Graduated`, so `isGraduated(token) == true` is always accompanied by a non-zero `graduatedPair(token)`.

### Proof of Concept
1. Assume (pending verification against the non-truncated `Bonding.sol` graduation code) a state where `Bonding.isGraduated(token) == true` but `Bonding.graduatedPair(token) == address(0)` — e.g. due to a reentrant/edge ordering bug in the phase-2 finalize path, or an admin/keeper race not covered by this scan.
2. Any unprivileged trader calls `Zap.buy(token, usdcAmount, minTokensOut, referrer)` or `Zap.sell(token, tokenAmount, minUsdcOut)`.
3. `_buyInternal`/`_sellInternal` see `bonding_.isGraduated(tokenAddress) == true` and route into `_buyOnUniswapV2`/`_sellOnUniswapV2` → `_swapOnUniswapV2`.
4. `pair` resolves to `address(0)` from both `graduatedPair` lookups; `IUniswapV2Pair(address(0)).token0()` reverts with no informative error, and the trade permanently fails for every caller — the token becomes untradeable via `Zap` with no recovery short of a UUPS upgrade.

    function _swapOnUniswapV2(
        address tokenIn,
        address tokenOut,
        uint256 amountIn
    ) internal returns (uint256 amountOut) {
        Bonding bonding_ = _s().bonding;
        // `graduatedPair` is keyed by the launched token only; check `tokenIn`
        // first (sell direction) then fall back to `tokenOut` (buy direction).
        address pair = bonding_.graduatedPair(tokenIn);
        if (pair == address(0)) pair = bonding_.graduatedPair(tokenOut);

        bool inIsToken0 = IUniswapV2Pair(pair).token0() == tokenIn;
        // Quote from the pair so the output tracks its live fee instead of a
        // hardcoded rate, keeping `amountOut` consistent with the K-check.
        amountOut = IUniswapV2Pair(pair).getAmountOut(amountIn, tokenIn);

        IERC20(tokenIn).safeTransfer(pair, amountIn);

        (uint256 amount0Out, uint256 amount1Out) = inIsToken0 ? (uint256(0), amountOut) : (amountOut, uint256(0));
        IUniswapV2Pair(pair).swap(amount0Out, amount1Out, address(this), new bytes(0));
    }
