### Title
Webhook `shop` field is trusted from unsigned HTTP header while HMAC only covers `@raw_body` — cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `#shop` is read verbatim from the unsigned `shopify-shop-domain` header [2](#0-1) . `Registry.process` validates the HMAC over the body only and then passes `request.shop` straight into the handler's `WebhookMetadata`, so the shop is unauthenticated relative to the signature [3](#0-2) .

### Finding Description
The broken binding: `set(fields consumed by handler) = {shop, topic, webhook_id, api_version, body}` vs `set(fields inside to_signable_string) = {raw_body}` — `shop ∉ signable_string` even though `shop` is trusted downstream.

Code path: `Registry.process(request)` first calls `Utils::HmacValidator.validate(request)` [4](#0-3) . That validator, via `Utils::VerifiableQuery` mixed into `Request`, computes/compares an HMAC over `to_signable_string`, which is defined to just return `@raw_body` [5](#0-4) [1](#0-0) . None of the Shopify-supplied headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) are covered by the signature — they are parsed straight from `@headers` in `#shop`, `#topic`, `#webhook_id`, `#api_version` [6](#0-5) . After the HMAC check passes, `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` and hands it to the handler [7](#0-6) .

Root cause: the request constructor only validates presence of the required headers (`topic`, `hmac-sha256`, `shop-domain`) [8](#0-7) , it never binds their values into the signed material.

Attacker exploit: attacker installs the app on their own dev shop, receives one genuine webhook delivery (raw_body `B`, valid `hmac-sha256` `H(B)`, header `shopify-shop-domain: attacker-shop.myshopify.com`). Attacker then sends a crafted HTTP POST to the host app's shared webhook endpoint with the same body `B` and same `hmac-sha256` header `H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`. Because the HMAC only covers `B` and the shared secret hasn't changed, `HmacValidator.validate` returns true regardless of the header value. `Registry.process` then invokes the handler with `data.shop == "victim-shop.myshopify.com"` while `data.body` is attacker-controlled content from `B`, causing the host app to process/store attacker data under the victim's tenant.

No existing guard prevents this: `HmacValidator` only checks the raw body signature; `ShopValidator.sanitize!`/OAuth session logic is not invoked in the webhook path at all; there is no separate authentication of the `shop` header against the HMAC.

### Impact Explanation
This is a cross-tenant access vulnerability: an attacker-controlled webhook body, legitimately signed for their own shop, is accepted by the host app as if it originated from an arbitrary victim shop of the attacker's choosing. Since webhook handlers commonly write to victim-shop-scoped storage keyed by `WebhookMetadata#shop` (e.g., syncing orders, customer data, GDPR redaction records, app-uninstalled cleanup), this allows attacker-controlled data or actions to be attributed to and applied against any victim shop, without any interaction from the victim. It is repeatable against any victim shop domain the attacker chooses to type into the header, for every registered topic, matching the "Critical — cross-tenant access" category.

### Likelihood Explanation
Preconditions are minimal and match the documented, standard usage pattern: a shared webhook endpoint per topic across all merchants calling `Registry.process(request)` [3](#0-2) . The attacker only needs a free development shop to receive one real webhook delivery (any topic they register for) and the ability to send an arbitrary HTTP request with a spoofed `shopify-shop-domain` header — both fully within the unprivileged attacker capabilities defined. No secrets, tokens, or victim interaction are required. This is a highly feasible, repeatable, low-cost attack.

### Recommendation
Do not read `shop`, `topic`, `webhook_id`, or `api_version` from unauthenticated headers and treat them as trusted. At minimum, cross-check the `shopify-shop-domain` header against a shop known to be associated with the specific secret/session used to validate the HMAC (i.e., validate the HMAC using a per-shop secret/session context rather than a single shared secret, or otherwise bind the shop identity into the signed material before trusting it). Practically: have `Registry.process` require and use a shop-specific `access_token`/webhook secret associated with the shop asserted in the header when computing/verifying the HMAC, so a body signed for shop A cannot verify against shop B's claimed identity.

### Proof of Concept
```ruby
# test/webhooks/cross_tenant_spoof_test.rb
require "test_helper"

class CrossTenantWebhookSpoofTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(
      api_key: "key", api_secret_key: "secret", ..., # shared secret used by HmacValidator
    )
    @raw_body = '{"id":1,"malicious":"payload"}'
    @hmac = OpenSSL::HMAC.digest("sha256", "secret", @raw_body)
    @hmac_b64 = Base64.encode64(@hmac).strip
  end

  def build_request(shop_domain)
    ShopifyAPI::Webhooks::Request.new(
      raw_body: @raw_body,
      headers: {
        "shopify-topic" => "orders/create",
        "shopify-hmac-sha256" => @hmac_b64,
        "shopify-shop-domain" => shop_domain,
        "shopify-webhook-id" => "123",
        "shopify-api-version" => "2024-01",
      },
    )
  end

  def test_hmac_valid_regardless_of_shop_header
    attacker_request = build_request("attacker-shop.myshopify.com")
    victim_request   = build_request("victim-shop.myshopify.com")

    assert ShopifyAPI::Utils::HmacValidator.validate(attacker_request)
    assert ShopifyAPI::Utils::HmacValidator.validate(victim_request) # SAME body/hmac, different shop -> still valid
  end

  def test_registry_process_trusts_spoofed_shop
    received_shop = nil
    handler = Class.new do
      define_method(:handle) { |data:| received_shop = data.shop }
    end.new

    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "orders/create", delivery_method: :http, path: "/webhooks", handler: handler,
    )

    spoofed_request = build_request("victim-shop.myshopify.com")
    ShopifyAPI::Webhooks::Registry.process(spoofed_request)

    assert_equal "victim-shop.myshopify.com", received_shop
    # Proves: HMAC over raw_body validated, but `shop` handed to handler
    # is attacker-controlled/unauthenticated relative to that HMAC.
  end
end
```
Both assertions demonstrate that `to_signable_string` (== `@raw_body`) is invariant across the two requests, while `request.shop` (read from the header) differs and is nonetheless passed on as authenticated tenant identity to the handler — proving the binding `shop ∈ to_signable_string` does not hold.
