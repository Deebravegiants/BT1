### Title
Cached user QR-code authorization is reused across the `operator_qr_expiration_time` window without revalidation, allowing signup/enrollment to proceed on stale authorization - (File: src/plans/mod.rs)

### Summary
The `_repay` bug in the BendDAO report stems from a broader pattern: the protocol validates a precondition (approval) once, then later performs an irreversible action (debt repayment / NFT unlock) assuming that precondition still holds, without re-checking it at the moment the action is actually executed. If the precondition is revoked in the interim, the system either fails destructively or proceeds on stale trust. `orb-core` contains an analogous pattern in the signup/authorization flow: the validity of a user's QR-code/backend authorization (`backend::user_status::request`) is checked once and cached in the `QrCodes::Both` variant, then reused for a full signup attempt as long as the *operator* QR-code timestamp has not expired - with no re-verification of the *user*'s authorization at the point biometric capture/enrollment actually begins.

### Finding Description
In `src/plans/mod.rs`, `scan_remaining_qr_codes` (lines 788-868) decides whether to reuse previously scanned/validated QR data or perform a fresh scan+validation, based solely on the *operator* data's timestamp: [1](#0-0) 

When `qr_codes` is already `QrCodes::Both { operator_data, user_qr_code, user_data, user_qr_code_string }` and `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, the function immediately returns the previously cached `user_data` (the result of the earlier backend authorization check performed in `verify_user_qr_code`) as `ResolvedQrCodes`, without calling `backend::user_status::request`/`verify_user_qr_code` again: [2](#0-1) 

The cached `user_data` (containing `backend_iris_public_key`, `backend_face_public_key`, `self_custody_user_public_key`, `id_commitment`, etc., all supplied by the backend at the *original* scan time) then flows unchanged into `do_signup`, through `build_pcp`, `enroll_user`, and ultimately `signup_post::request`, which uses the operator QR-code, user QR-code and these stale keys/identity fields to complete the enrollment: [3](#0-2) [4](#0-3) 

The check that gates whether stale data is reused (`operator_data.timestamp.elapsed() < operator_qr_expiration_time`) is tied to the *operator's* QR scan time, not to any freshness guarantee on the *user's* authorization state. The `QrCodes::Both` cache is produced by `idle_scan_user_qr_code` (self-serve idle scanning flow) and stored via `QrCodes::with_user_qr_code`: [5](#0-4) 

Nowhere in this reused path is the user's authorization/consent re-checked against the backend before biometric capture and enrollment proceed. This mirrors the BendDAO root cause: a one-time validation of an external, revocable precondition is treated as durable for the remainder of a multi-step, security-relevant flow, and the code path that consumes the cached result performs no defensive re-validation immediately before the consequential action (in this case, biometric capture + identity enrollment, analogous to "unlocking the NFT").

### Impact Explanation
If a user's authorization is revoked or altered on the backend side (e.g., the backend later determines the user QR-code/session should no longer be valid, the user cancels/logs out of their session in the companion app, or the previously issued keys/identity commitment become stale) within the `operator_qr_expiration_time` window after the initial scan, the orb will still treat the cached `UserData` as authoritative and proceed straight into biometric capture and enrollment using the stale `id_commitment` / `self_custody_user_public_key` / backend keys. This can result in a signup being completed and bound to an identity/session that should have been invalidated - an unauthorized or misattributed signup, since the enrollment request sent via `signup_post::request` carries authorization material that is no longer guaranteed valid at the time of use.

### Likelihood Explanation
The likelihood depends on how long `operator_qr_expiration_time` is configured and how often the self-serve idle-scan cached path (`QrCodes::Both`) is exercised versus a fresh scan. Since this code path exists specifically to avoid redundant re-scans for UX reasons, it is reachable in normal self-serve operation (not a test-only or hardware-access path), and the condition purely depends on a time window rather than any privileged action, making it a realistic (if narrow, time-bounded) exposure rather than a purely theoretical one.

### Recommendation
Re-validate the user's authorization (`verify_user_qr_code`/`backend::user_status::request`) immediately before starting biometric capture/enrollment whenever the cached `QrCodes::Both` state is reused, rather than relying solely on the operator QR-code timestamp as a freshness proxy for the user's authorization. Alternatively, apply a separate, shorter freshness window specific to the user's authorization state, and re-check it at the exact point where the enrollment decision becomes irreversible (i.e., right before `enroll_user`/`signup_post::request` is invoked), so a mid-window revocation on the backend is honored rather than silently ignored.

### Proof of Concept
1. Configure the orb in self-serve mode with `self_serve_button = false`, so `idle_scan_user_qr_code` performs the initial user QR-code scan and validation, producing `QrCodes::Both { operator_data, user_qr_code, user_data, .. }` — see `src/plans/mod.rs:456-488`.
2. Simulate the backend invalidating the user's authorization (e.g., user cancels/logs out in companion app) shortly after this scan, but before `operator_data.timestamp.elapsed()` reaches `operator_qr_expiration_time`.
3. Call `do_signup` → `scan_remaining_qr_codes` with this cached `QrCodes::Both`; because the operator timestamp check passes, the function returns the stale `user_data` at `src/plans/mod.rs:796-805` with no additional backend call.
4. Biometric capture and `enroll_user` proceed using this stale, now-invalid authorization data, completing/attempting a signup that should have been blocked by the revocation.
