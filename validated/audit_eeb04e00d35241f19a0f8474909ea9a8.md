Audit Report

## Title
CORS `Access-Control-Allow-Origin` allowlist bypass via unanchored suffix match in `isAllowedOrigin` - ([File: core/services/gateway/network/httpserver.go])

## Summary
`isAllowedOrigin` in `core/services/gateway/network/httpserver.go` implements wildcard CORS origin matching by stripping the `*.` prefix from a configured entry (e.g. `*.remix.com` → `remix.com`) and then testing `strings.HasSuffix(originHost, allowedHost)` with no domain-label boundary check. [1](#0-0)  This allows any origin host that merely ends with the configured substring (e.g. `evilremix.com`) to satisfy an allowlist entry intended only for genuine subdomains of `remix.com`.

## Finding Description
The wildcard-host branch of `isAllowedOrigin` strips the literal `*.` and performs a raw suffix comparison rather than a separator-bounded comparison: [1](#0-0)  Because `strings.HasSuffix` operates on unstructured strings, `evilremix.com`, `attacker-remix.com`, and `notremix.com` all satisfy `strings.HasSuffix(originHost, "remix.com")`, despite not being subdomains of `remix.com`. This is invoked from `handleRequest`, the entry point for every incoming HTTP request to the Gateway's CORS-enabled server, which reflects the raw `Origin` header value into `Access-Control-Allow-Origin` when `isAllowedOrigin` returns true: [2](#0-1)  No other check (exact match, label-boundary check, or origin structural validation) exists in the function to close this gap; the exact-match branch above it only covers the non-wildcard case. [3](#0-2) 

## Impact Explanation
This is an unauthenticated, internet-facing endpoint (the Gateway HTTP server), and the flaw directly weakens a CORS security boundary intended to restrict which origins can read cross-origin JSON-RPC responses. An operator who configures `CORSAllowedOrigins = ["https://*.remix.com"]` to trust only genuine subdomains of a partner domain unintentionally also trusts any domain ending in the literal string `remix.com`, including domains with no actual relationship to the intended partner (e.g., `evilremix.com`). This maps to the "gateway request impersonation / allowlist bypass" impact category referenced in scope.

## Likelihood Explanation
Exploitation requires only that an operator configure a wildcard `CORSAllowedOrigins` entry (a documented, supported feature) and that an attacker register/control an arbitrary domain ending in the same suffix, which is trivial and low-cost. No credentials, privileged roles, or victim social engineering beyond a normal cross-origin browser request are needed, making the bug practically exploitable once an attacker knows or guesses the configured wildcard domain.

## Recommendation
Enforce a domain-label boundary in the wildcard branch, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    allowedHost = allowedHost[2:]
    if originHost == allowedHost || strings.HasSuffix(originHost, "."+allowedHost) {
        return true
    }
}
```
This ensures only `allowedHost` itself or genuine subdomains (`*.allowedHost`) match, rejecting suffix-only impostors like `evilremix.com`.

## Proof of Concept
1. Configure the Gateway with `CORSAllowedOrigins = ["https://*.remix.com"]` and `CORSEnabled = true`.
2. Send an HTTP request to the Gateway endpoint with header `Origin: https://evilremix.com`.
3. Observe `isAllowedOrigin` returns `true` per [1](#0-0) , and the response includes `Access-Control-Allow-Origin: https://evilremix.com` per [4](#0-3) .
4. A page hosted on `https://evilremix.com` can then use `fetch()`/XHR to read the Gateway's JSON-RPC response cross-origin, despite not being a genuine subdomain of `remix.com`.
