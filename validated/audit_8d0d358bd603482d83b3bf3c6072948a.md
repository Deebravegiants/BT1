### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw request body only, while the `shop` value that the gem hands to application webhook handlers is read from an unauthenticated HTTP header. This breaks the intended binding `hmac(secret, signed_bytes) == hmac_header` ⇒ `shop_header == originating_shop`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the signed bytes: [2](#0-1) [3](#0-2) 

`Utils::HmacValidator.validate` verifies only that the HMAC over `to_signable_string` (the raw body) matches the shared `api_secret_key`; it says nothing about the `shop` header: [4](#0-3) 

`Webhooks::Registry.process` trusts this unauthenticated `request.shop` value and forwards it directly to the application-supplied handler as the identity of the shop the event belongs to: [5](#0-4) 

Because the shared `api_secret_key` used to compute the HMAC is the same for every shop that has the app installed, any merchant who installs the app (an unprivileged actor with respect to other merchants of the same app) can trigger a legitimate webhook for their own shop, capture the resulting `(raw_body, hmac)` pair, and replay it to the app's public webhook endpoint with the `shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid), but `Registry.process` passes the attacker-controlled `shop` header value to the handler as if it were the victim's data. This is exactly the "field acted on but not covered by the HMAC" identity-binding break called out as in-scope: `shop_header` (acted upon) ≠ `shop_that_produced_hmac` (verified).

### Impact Explanation
Any downstream logic that keys per-tenant state (session lookup, order/customer records, GDPR redact/data-request processing, billing, feature flags, or webhook idempotency records) off `WebhookMetadata#shop` can be made to attribute one merchant's webhook payload to a different merchant's tenant. This is a cross-tenant data/identity confusion inside the app that trusts this gem's `shop` field as authenticated — matching the "cross-tenant access" Critical impact category, since an attacker (a legitimate but unprivileged installer of the app) can cause events to be processed under another shop's identity without ever needing that shop's credentials.

### Likelihood Explanation
Exploitability only requires: (1) installing the target app on an attacker-controlled shop (a normal, unprivileged action available to any merchant), (2) triggering any webhook topic already registered by the app (e.g., `orders/create`), and (3) replaying the captured body/HMAC to the app's public webhook URL with a modified `shop-domain` header — no secrets, tokens, or access to the victim shop are needed. This is straightforward and repeatable.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values into the signed material, or otherwise validate that the header-provided shop matches a shop known to have installed the app and is authorized to have produced this specific HMAC (e.g., by verifying the webhook subscription's registered secret/shop mapping, or by including the shop domain in `to_signable_string` if Shopify's webhook signing ever supports channel-bound secrets). At minimum, document that `WebhookMetadata#shop` is derived from an unauthenticated header and must not be treated as cryptographically bound to the HMAC-verified body, and encourage host apps to cross-check it against server-side webhook subscription state.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` (uses the same app `client_secret`/`api_secret_key` as every other installer).
2. Attacker performs an action that fires a subscribed webhook (e.g., creates an order), causing Shopify to POST to the app's webhook endpoint with body `B` and header `shopify-hmac-sha256: H = HMAC(api_secret_key, B)` and `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker intercepts/replays this exact request to the same endpoint but rewrites the header to `shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim.myshopify.com"...})` is constructed; `HmacValidator.validate` recomputes `HMAC(api_secret_key, B)` and it still equals `H`, so validation passes: [6](#0-5) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body: parsed_body, ...)`: [7](#0-6) 
6. The host application, trusting the gem's `shop` field as authenticated, processes attacker's order data as belonging to `victim.myshopify.com`.
