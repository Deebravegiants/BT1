Based on my analysis, here is the finding:

### Title
Donating launched Token directly to the curve `Pair` collapses the virtual-reserve gap and permanently bricks the final overflow-capped buy / supply-trigger graduation - ([File: packages/contracts/src/Router.sol])

### Summary
`Router._computeBuy`'s overflow-cap logic and the entire "virtual token reserve" design rely on the invariant `pair.tokenBalance() < reserveToken` holding at all times [1](#0-0) . This invariant is only preserved as long as the real token balance of the `Pair` moves exclusively through `Router.buy`/`sell`. Because the launched `Token` is a completely unrestricted ERC20 clone [2](#0-1) , any unprivileged holder can `transfer` tokens directly into the `Pair` address, which increases the *live* `tokenBalance()` without moving the *stored* `reserveToken`. This closes the constant 250M-token gap between the virtual reserve and the real balance, causing the final overflow-capped buy on that curve to revert.

### Finding Description
At launch, `Bonding._deployAndSeed` seeds the pair with `reserveToken = totalSupply` (1B) while transferring only `curveSupply = 750M` real tokens, leaving a constant `250M` gap between the pair's stored reserve and its real balance [3](#0-2) . Every subsequent `Router.buy`/`sell` moves `reserveToken` and the real ERC20 balance by the exact same `tokensOut`/`tokensIn`, so under normal trading the gap stays fixed at 250M and `tokenBalance() < reserveToken` always holds — this is exactly what `test_inv_virtualReserveAlwaysExceedsRealBalance` asserts [4](#0-3) .

Nothing in `Pair.sol` restricts direct `IERC20.transfer` calls into the pair — `Pair` only gates `mint`/`swap`/`transferAsset`/`transferToken` behind `onlyRouter` [5](#0-4) ; a raw ERC20 transfer of the launched `Token` bypasses this entirely and is exactly what the "donation-resistance" invariants are designed around for the *graduation* triggers [6](#0-5)  — but that resistance only protects `canGraduate`/`_prepareGraduationLiquidity`, not `Router._computeBuy`'s overflow-cap arithmetic.

Any address that has acquired ≥250M of the launched token (via ordinary curve buys — no privilege required) can `Token.transfer(pair, amount)` those tokens straight into the `Pair`. Because `tokenBalance()` is a live `balanceOf` read [7](#0-6) , this immediately inflates the real balance relative to the stored `reserveToken`, driving `reserveToken - tokenBalance()` to zero (or negative). The next buy large enough to need the overflow cap then hits:

```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
``` [8](#0-7) 

With the gap collapsed to exactly zero this reverts with the explicit `OverflowCapDegenerate` guard; if the donation overshoots the gap, `reserveToken - tokensOut` underflows and reverts with a raw arithmetic panic instead — either way `Router.buy` (and therefore `Bonding.buy`/`Zap.buy`) permanently reverts for any buy attempting to consume the remaining real supply. Since the last capped buy is precisely the buy that would drive `tokenBalance()` to `0` and fire the supply-side graduation trigger in `canGraduate` [9](#0-8) , that trigger becomes permanently unreachable for the affected token, and any trader trying to buy the tail of the curve is denied.

### Impact Explanation
- The token can never sell out through the buy path and can never reach `Bonding.canGraduate`'s supply trigger again — if the LT's USD-value trigger never independently crosses the threshold (flat/declining exchange rate), the token is permanently stuck in `Lifecycle.Curve`, the 250M `LP_RESERVE` tokens remain forever locked in `Bonding`, and the pool never gets its HyperSwap LP seeded.
- Every trader whose buy would need the overflow cap gets a hard revert instead of a capped fill, denying legitimate purchases of the last slice of curve supply.
- This is a permanent freezing of protocol state (graduation path, LP_RESERVE tokens, and remaining curve liquidity) for the targeted token, reachable purely with a plain ERC20 `transfer`, which the codebase's own invariant tests (`test_inv_virtualReserveAlwaysExceedsRealBalance`) assume can never happen but never actually test against donations.

### Likelihood Explanation
Reaching the trigger point requires only accumulating ≥250M of the launched token (obtainable via ordinary curve buys, no special role) and one plain `IERC20.transfer` call to the `Pair` address — no admin/router role, no upgrade, and no off-chain assumption is needed. The cost is bounded by the AMM price of buying up to 1/3 of the curve's real supply, which is comparable to (not a multiple of) organic buy volume the curve is designed to absorb, making this an economically realistic griefing vector against any specific token (e.g., a competitor's launch, or self-inflicted to keep a token permanently un-graduated).

### Recommendation
Do not trust the live `IERC20.balanceOf` read in `Router._computeBuy`'s overflow-cap branch. Track the real sellable balance in `Pair`'s own stored accounting (mirroring how `assetReserve`/`reserveToken` are already maintained) instead of `tokenBalance()`, or explicitly `skim`/exclude donation-inflated balance before computing the cap, so that direct transfers into the pair cannot shrink or invert the `reserveToken - realBalance` gap that the overflow-cap math depends on.

### Proof of Concept
1. Launch a token normally via `Bonding.launch`/`Zap.createToken` (curve seeded with `reserveToken = 1e9`, `tokenBalance() = 750,000,000e18`).
2. An attacker (or colluding traders) executes ordinary `Zap.buy`/`Bonding.buy` calls to accumulate `≥ 250,000,000e18` of the launched `Token` from the curve.
3. The attacker calls `Token.transfer(pairAddress, 250_000_000 ether)` directly (a plain unrestricted ERC20 transfer, bypassing `Bonding`/`Router`/`Zap` entirely).
4. `IPair(pair).tokenBalance()` now equals (or exceeds) the stored `reserveToken`.
5. Any subsequent buy sized to require the overflow cap (i.e., requesting more tokens than the currently real balance) calls `Router._computeBuy`, hits `cappedReserveToken = reserveToken - tokensOut`, and reverts with `OverflowCapDegenerate` (gap exactly closed) or an arithmetic-underflow panic (gap overshot) — for that token, this buy can never succeed again, and `Bonding.canGraduate`'s supply leg (`IPair(pair).tokenBalance() == 0`) can never be satisfied via the buy path.

        uint256 assetOut
