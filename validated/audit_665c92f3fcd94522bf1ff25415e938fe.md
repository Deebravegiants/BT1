## Answer

Yes — there is a genuine desync, but it does not come from "concurrent/retried" calls to the same ID racing each other (NEAR's synchronous receipt processing and the `insert()` guard in `create_staking_pool` already prevent that). The real desync comes from a mismatch between the **atomicity assumption baked into `on_staking_pool_create`** and the **actual (non-atomic) execution semantics of a batched multi-action `Promise`**.

### The mechanism

`create_staking_pool` optimistically inserts the new pool's ID into `staking_pool_account_ids` and then builds a *single* action-receipt Promise chaining `create_account()`, `transfer()`, `deploy_contract()`, and `function_call("new")`: [1](#0-0) 

On NEAR, actions inside one action receipt execute **sequentially and non-atomically**: if `create_account`, `transfer`, and `deploy_contract` succeed but the trailing `function_call("new")` panics (e.g. runs out of the fixed `gas::STAKING_POOL_NEW` budget, which is a constant regardless of attacher-supplied `owner_id`/`stake_public_key` size, or panics on some malformed-but-technically-valid input to the pool's `new`), the *earlier* actions' effects (account creation, the attached-deposit transfer, and the deployed code) are **not rolled back** — only the failing action's own effect is discarded. The receipt as a whole is reported to the `.then()` callback as failed.

`on_staking_pool_create` treats this failure as "nothing happened" and unconditionally:
1. Removes the ID from `staking_pool_account_ids`, and
2. Refunds the *entire* `attached_deposit` a second time from the factory's own balance to the original caller. [2](#0-1) 

The `else` branch (invoked whenever `is_promise_success()` is false) is exactly this rollback path used in the existing `test_create_staking_pool_rollback` test, which only exercises the case where the *whole* receipt cleanly fails (mocked as `PromiseResult::Failed`) — it never exercises the case where account creation/funding/deploy already succeeded before the trailing `function_call` failed: [3](#0-2) 

### Resulting state divergence

- On-chain: `staking_pool_account_id` now exists, is funded with the attacher's `attached_deposit`, has the staking-pool WASM deployed, but was never initialized (`new` never completed) and has **no access keys** (no `AddKey` action was ever issued) — so it is permanently unusable and unrecoverable.
- In the factory: `staking_pool_account_ids` no longer contains this ID (it was removed), so the factory believes the ID is free/never existed, even though the account physically exists.
- The factory additionally pays out a **second** refund of the deposit from its own balance, even though the original deposit was already spent transferring value into the now-stranded account — a double payment out of the factory's own operating funds.
- A retry with the same `staking_pool_id` will fail at `create_account` (account already exists) as the very first action in the new batch, so no further funds are lost on retry, but the original deposit remains permanently locked in the orphaned account forever, and the factory's registry stays desynced from the true on-chain state indefinitely.

This satisfies the "Permanent freezing/irrecoverable loss of funds in factory refund flows" and "accounting divergence" impact classes, since it is reachable by any unprivileged EOA simply calling `create_staking_pool()` with a deposit and standard parameters — no privileged role is required. Attaching more than `MIN_ATTACHED_BALANCE` just maximizes the amount that gets stranded/double-paid; it isn't strictly required to trigger the bug, but it increases the realized loss.

### Title
Non-atomic batched-action failure in `create_staking_pool` desyncs `staking_pool_account_ids` from on-chain state and causes stuck funds / double refund - (File: `staking-pool-factory/src/lib.rs`)

### Summary
`on_staking_pool_create`'s rollback branch assumes that a failed promise result means *none* of `create_account`/`transfer`/`deploy_contract`/`function_call("new")` took effect. On NEAR, actions within one receipt execute sequentially and are not rolled back as a unit — only the failing action (and those after it) are aborted. If the trailing `function_call("new")` fails after the account was already created, funded, and had code deployed, the factory incorrectly removes the ID from `staking_pool_account_ids` and pays the deposit out a second time, while the real on-chain account is permanently orphaned with the original deposit locked inside it (no init state, no access keys). [4](#0-3) 

### Finding Description
See mechanism above — the root cause is treating `is_promise_success()` over a multi-action `Promise` batch as an atomicity signal, when NEAR does not guarantee atomic rollback of earlier successful actions in the same receipt when a later action in that same receipt fails.

### Impact Explanation
Critical — permanent, unrecoverable loss of the attacher's deposited NEAR in the stranded account, plus a matching double-payment out of the factory's own balance, and permanent desync between `staking_pool_account_ids` and reality (the ID is marked free while an unusable account with locked funds occupies it forever).

### Likelihood Explanation
Medium — the trigger condition (last action in the batch failing after earlier ones succeed, e.g. gas exhaustion in the fixed `gas::STAKING_POOL_NEW` budget, or an assertion failure inside the pool's `new()`) is plausible and partly attacker-influenceable (e.g., inputs sized to push actual gas usage close to the fixed limit) without requiring any privileged access.

### Recommendation
Don't rely on `is_promise_success()` of the whole batched receipt to infer that no prior action (in particular `create_account`/`transfer`/`deploy_contract`) took effect. Either verify the created account's actual state (e.g., via a follow-up view/cross-contract check) before deciding to remove the ID and refund, or restructure pool creation so that `new` failures cannot leave a funded-but-uninitialized, keyless account (e.g., add a full access key controlled by a recovery path, or split creation into steps that can be safely detected/retried by checking on-chain existence rather than only trusting the aggregate promise result).

### Proof of Concept
1. Attacker calls `create_staking_pool(id, owner_id, stake_public_key, reward_fee_fraction)` with `attached_deposit` well above `MIN_ATTACHED_BALANCE`.
2. `staking_pool_account_ids.insert()` succeeds; a single batched `Promise` is dispatched: `create_account → transfer → deploy_contract → function_call("new")`.
3. Craft/observe a case where `create_account`, `transfer`, and `deploy_contract` succeed but `function_call("new")` fails (e.g. gas exhaustion under `gas::STAKING_POOL_NEW`, a fixed constant independent of actual input complexity).
4. Because the batch's terminal action failed, the receipt result reported to `on_staking_pool_create` is `Failed`, even though the sub-account now exists on-chain, funded and with code deployed.
5. `on_staking_pool_create` removes the ID from `staking_pool_account_ids` and refunds `attached_deposit` a second time to the predecessor from the factory's balance.
6. Verify: the account `staking_pool_id.factory` exists on-chain with locked balance and no access keys (permanently inaccessible), while `contract.get_number_of_staking_pools_created()` shows the ID as never created — confirming the registry/on-chain desync and the double payout.

    /// Callback after a staking pool was created.
    /// Returns the promise to whitelist the staking pool contract if the pool creation succeeded.
    /// Otherwise refunds the attached deposit and returns `false`.
    pub fn on_staking_pool_create(
        &mut self,
        staking_pool_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> PromiseOrValue<bool> {
        assert_self();

        let staking_pool_created = is_promise_success();

        if staking_pool_created {
            env::log(
                format!(
                    "The staking pool @{} was successfully created. Whitelisting...",
                    staking_pool_account_id
                )
                .as_bytes(),
            );
            ext_whitelist::add_staking_pool(
                staking_pool_account_id,
                &self.staking_pool_whitelist_account_id,
                NO_DEPOSIT,
                gas::WHITELIST_STAKING_POOL,
            )
            .into()
        } else {
            self.staking_pool_account_ids
                .remove(&staking_pool_account_id);
            env::log(
                format!(
                    "The staking pool @{} creation has failed. Returning attached deposit of {} to @{}",
                    staking_pool_account_id,
                    attached_deposit.0,
                    predecessor_account_id
                ).as_bytes()
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            PromiseOrValue::Value(false)
        }
    }
