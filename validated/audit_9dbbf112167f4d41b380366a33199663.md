### Title
Webhook shop-domain, topic, and webhook-id headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by checking only that the raw request body matches an HMAC computed with the app's `client_secret`. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values, which are taken verbatim from HTTP headers, are never included in the signed payload, yet they are trusted downstream to route the event and to identify which merchant it belongs to.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Compare this with `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string`, which folds `code`, `host`, `shop`, `state`, and `timestamp` into the signed string so that every one of those fields is bound to the signature: [2](#0-1) 

For webhooks, `shop`, `topic`, `webhook_id`, and `api_version` are instead read straight off HTTP headers with no cryptographic binding to the body that was actually signed: [3](#0-2) 

`Registry.process` validates only the HMAC of the body, then immediately trusts `request.topic` and `request.shop` (unauthenticated header values) to route the payload to a handler and construct `WebhookMetadata`: [4](#0-3) 

`WebhookMetadata.shop` is a plain `String` with no further verification, and host applications key their per-merchant business logic (e.g., "which shop's order was just created") directly off this field: [5](#0-4) 

The identity binding that should hold is:

`shop header value used by handler.handle == shop that legitimately produced the HMAC-signed body`

Because `HmacValidator.validate` (used identically for both OAuth and webhooks) only proves "this body was signed with our `client_secret`" and never binds the signature to the `shop-domain` header: [6](#0-5) 

...an attacker who is a legitimate, currently-installed merchant of the app can capture one of their own legitimately-signed webhook deliveries (body + HMAC, both valid because Shopify signed them for the attacker's own store) and resend that exact body/HMAC pair to the app's webhook endpoint with the `x-shopify-shop-domain` header changed to a *different* merchant's shop domain (and/or `x-shopify-topic` changed to a different registered topic). `Registry.process` will accept the HMAC (it's a byte-for-byte valid signature over the body), and the handler will run business logic attributing the attacker-controlled body to the victim shop, because `request.shop` is never checked against anything the signature actually covers.

### Impact Explanation
This is a cross-tenant data injection: within a single installed app, any merchant who receives real webhooks from Shopify can forge webhook deliveries that the app will process as belonging to any other merchant of that same app, since the shop identifier used to select/scope the processing is not part of the authenticated bytes. Depending on what the host application's `WebhookHandler#handle` does with `data.shop` and `data.body` (e.g., writing order/customer data, triggering fulfillment or refund workflows, updating per-shop settings), this can corrupt another tenant's data or trigger unintended actions under that tenant's identity — directly matching the "cross-tenant access" High/Critical impact category, since the app's HMAC/identity boundary between shops is bypassed using only material the attacker already legitimately possesses (their own valid webhook deliveries).

### Likelihood Explanation
Likelihood is high for any app using this gem's webhook processing as documented: an attacker needs no privileged credentials, `api_secret_key`, or access token — only their own status as an installed, unprivileged merchant who naturally receives legitimately-signed webhooks from Shopify for events on their own store. Replaying that body with a modified `shop-domain` (or `topic`/`webhook-id`) header is a trivial HTTP replay against the app's public webhook endpoint.

### Recommendation
Bind the `shop`, `topic`, and `webhook_id` header values into the HMAC-verified signable string (or otherwise cryptographically bind them, e.g., by validating `shop` against the specific webhook subscription that was registered for that topic/address), so that a valid signature can only be replayed for the exact shop/topic combination it was issued for. At minimum, `Registry.process` should cross-check `request.shop` against an expected/registered value before invoking a handler, rather than trusting the header outright once the body-only HMAC passes.

### Proof of Concept
1. App installs the handler shown in `docs/usage/webhooks.md` for topic `orders/create`, relying on `data.shop` to select the tenant's DB record.
2. Attacker, an installed merchant of shop `attacker.myshopify.com`, receives a legitimate webhook from Shopify: body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker POSTs the same body `B` and same HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `HmacValidator.validate` succeeds (per `lib/shopify_api/utils/hmac_validator.rb`, lines 12-22, it only recomputes over `to_signable_string`, i.e., the raw body) because the body/HMAC pair is unchanged and valid.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb`, lines 188-200) builds `WebhookMetadata` with `shop: "victim.myshopify.com"` and invokes the app's handler, which now processes attacker-controlled data as if it originated from the victim shop.

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
