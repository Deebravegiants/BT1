### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (tenant) attribute used downstream to identify which merchant a webhook belongs to is read from an HTTP header that is never included in the signed bytes. Because a single `api_secret_key` is shared across every shop that has the app installed, any actor who legitimately receives a genuine webhook for their own shop (i.e., any merchant who installs a public app) can replay that same body+HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain`/`Shopify-Shop-Domain` header for a victim shop, and `ShopifyAPI::Webhooks::Registry.process` will accept it as valid and dispatch it to the handler under the victim's identity.

### Finding Description
`Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

The `shop` attribute, however, is derived purely from an unauthenticated header: [2](#0-1) 

`Registry.process` verifies only `Utils::HmacValidator.validate(request)` (which checks the raw-body HMAC) and then immediately trusts `request.shop` as the tenant for the handler invocation, without any binding between the two: [3](#0-2) 

`HmacValidator.validate_signature` only compares the HMAC over `to_signable_string` (the body): [4](#0-3) 

This is the exact bug class from the report generalized: an identity field (`shop`, analogous to the collateral/loan identity in the original report) is acted upon (used to route/attribute the webhook to a tenant) without being covered by the same authenticity check (HMAC) that is presented as proving "the request did indeed come from Shopify" per this gem's own documentation: [5](#0-4) 

The broken binding, stated as an equality that should hold but doesn't:
`hmac_signed_bytes == bytes_that_determine_shop_identity`
Here, `hmac_signed_bytes = raw_body` but `shop_identity_bytes = header["shop-domain"]`, and the two are disjoint.

### Impact Explanation
Because `api_secret_key` is shared by the app across all of its installed shops, any merchant (an ordinary, unprivileged actor who can install a public Shopify app for free on a development/trial store) receives genuinely-HMAC-signed webhook bodies from Shopify for their own store. Since the HMAC never binds the `shop` header, that attacker can replay the identical `(raw_body, hmac)` pair to the target app's webhook endpoint while forging the `Shopify-Shop-Domain` header to name a victim shop. `Registry.process` will pass HMAC validation and invoke the app's handler with `WebhookMetadata#shop` set to the victim's domain, causing the app to process attacker-controlled webhook content as if it originated from another tenant — a cross-tenant data/identity confusion (e.g., the app could create, update, or delete records keyed by the forged shop, or trigger mandatory-compliance webhooks such as `customers/redact`/`shop/redact` against the wrong tenant).

### Likelihood Explanation
Requires only that the attacker install the app on a shop they control (a free/no-cost, unprivileged action for any internet user targeting a public app) and know the shape of a plausible webhook body for the topic they want to forge (which is often predictable/public, e.g. `orders/create` JSON schema). No access to the app's `client_secret`, no leaked credentials, and no privileged account are needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signable content, or otherwise cryptographically bind the declared shop to the signed body (e.g., by validating the target shop against a webhook-registration record before dispatch) rather than trusting `request.shop` merely because the body HMAC validated.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` (any user can do this for free).
2. Shopify sends a legitimately signed webhook, e.g. `orders/create`, to the app with body `B` and header `X-Shopify-Hmac-Sha256: H` (computed over `B` with the shared `api_secret_key`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker captures `(B, H)` and re-sends a new HTTP request to the same app webhook endpoint with the same `B` and `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-hmac-sha256" => H, ...})` is constructed and passed to `Registry.process`.
5. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`, per `to_signable_string` returning `@raw_body`.
6. The app's registered handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, causing the app to act on behalf of `victim-shop.myshopify.com` using attacker-supplied content.
