### Title
Webhook shop-domain attribution is not covered by the HMAC, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates the HMAC of an inbound webhook against the raw request body only, then dispatches the event to the host app's handler using the `shop` value read from an unauthenticated HTTP header. Because the `shop-domain` header is not part of the signed material, the binding `verified_hmac == (body, shop)` is not actually enforced — only `verified_hmac == body` is. An attacker who can obtain one validly-signed webhook body/HMAC pair (e.g., by installing the same public app on their own shop and receiving a real Shopify-signed webhook) can replay that exact body/HMAC pair to the target app's webhook endpoint while substituting an arbitrary `shop-domain` header value, causing the host app to process attacker-controlled data under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`to_signable_string` returns only `@raw_body` — none of the HTTP headers, including `shop`, are included in the signed string: [2](#0-1) [3](#0-2) 

`HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it to the received `hmac`: [4](#0-3) 

`Registry.process` only calls this HMAC check, then immediately trusts `request.shop` (sourced from the `shop-domain`/`x-shopify-shop-domain` header) as the shop identity handed to the app's handler: [5](#0-4) 

The intended identity binding is: *"this exact body, verified by HMAC, originated for this exact shop."* What is actually verified is only: *"this exact body was HMAC-signed by our secret at some point, for some shop."* The `shop` field that downstream `WebhookMetadata` and the app's handler act on is never cryptographically tied to the signature at all — exactly the "field acted on but not covered by the HMAC" pattern.

Since a single app uses one shared `client_secret`/`api_secret_key` across every merchant that installs it, any attacker who is themselves a legitimate merchant of the target app (or who can otherwise obtain one genuine signed webhook body, e.g. from their own store's installation) possesses a `(raw_body, hmac)` pair that is valid under the shared secret. Because the header is not part of the signed data, that same pair remains valid for any `shop-domain` header value the attacker chooses to send — including a victim's shop domain.

### Impact Explanation
This crosses a tenant boundary defined only by an unauthenticated header: the attacker (a normal, unprivileged user of the app — merely another merchant with the app installed) can cause the host application to attribute attacker-influenced webhook body content to a different shop's identity. Depending on how the host app keys per-shop state off `WebhookMetadata#shop` (which the docs advertise as the shop identity of the event and instruct handlers to key work off of, e.g. `perform_later(shop_domain: data.shop, ...)`), this can lead to cross-tenant data confusion/corruption — processing events, mutating stored per-shop state, or triggering per-shop side effects (uninstall cleanup, order/customer data ingestion, etc.) under a victim's shop identity without the victim's involvement. This matches the "cross-tenant access" Critical impact category, since the shop boundary — the fundamental multi-tenant isolation guarantee of the gem's webhook API — is not actually enforced by the cryptographic check the library performs.

### Likelihood Explanation
Requires only: (1) the app installed on any shop the attacker controls (a normal, unprivileged action any merchant can take), (2) capturing one real Shopify-delivered webhook body+HMAC for that shop, and (3) POSTing that same body/HMAC pair to the target app's webhook endpoint with a forged `shop-domain` header. No access to `client_secret`, tokens, or any privileged credential is needed — this is exactly the unprivileged-internet-user threat model in scope.

### Recommendation
Include the shop-domain (and ideally topic/webhook-id) in the HMAC-covered material, or independently bind the header-derived `shop` to a value the app has authenticated (e.g., cross-check against the shop that has an active, stored session/installation) before dispatching to the handler. At minimum, `Utils::VerifiableQuery#to_signable_string` for `Webhooks::Request` should not allow the `shop` field to be trusted as authenticated when it is disjoint from the signed bytes; document/enforce that consumers must not treat `WebhookMetadata#shop` as verified unless corroborated by stored per-shop state.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a normal signup, no privileged access needed).
2. Shopify delivers a real webhook to the attacker's endpoint: body `B`, header `x-shopify-shop-domain: attacker-shop.myshopify.com`, header `x-shopify-hmac-sha256: H` where `H = HMAC(secret, B)`.
3. Attacker replays the exact same `B` and `H` to the target app's own webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request#hmac` decodes `H`; `HmacValidator.validate` recomputes `HMAC(secret, B)` — matches, since `B` is unchanged — and `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, per: [6](#0-5) 
5. The host application's handler executes attacker-influenced logic under the victim shop's identity, with no indication that the shop attribution was never authenticated.
