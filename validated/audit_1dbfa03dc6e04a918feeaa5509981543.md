**Rationale:** The premise misunderstands how `AbilitySet` union works and does not correspond to any real Move ability-derivation code path.

`AbilitySet::SIGNER` is a constant set to `{Drop}` only (bit value `0x2`), and `union` is a plain bitwise OR: `Self(self.0 | other.0)`. A bitwise OR can never introduce a bit (e.g. `Store = 0x4`) that isn't already set in one of the two operands — it is mathematically impossible for `SIGNER.union(x)` to produce `has_store() == true` unless `x` itself already has `Store`. That is not a "bug," it's the definition of a set union; there is no code path where union "grants" an ability that neither input possessed. [1](#0-0) [2](#0-1) 

Additionally, struct ability derivation in the actual verifier/model code does not use `union` to combine a struct's declared abilities with its field abilities — it uses `intersect`, which is the opposite of union and can only remove abilities, never add them. This is exactly how signer-containing structs are prevented from gaining `Store`: `infer_struct_abilities` intersects the struct's declared abilities with the *meet* of its field/type-argument abilities, so any field lacking `Store` (like `signer`, whose ability set is `{Drop}` only) forces the resulting struct to lack `Store` as well. [3](#0-2) 

At the bytecode-verifier level, the same principle holds: `Signer` tokens are checked against `AbilitySet::SIGNER` and any type requiring `Store` for a signer-typed slot fails `assert_abilities`/`is_subset` checks, not a union pathway. [4](#0-3)  The runtime pack verification similarly checks that each field's abilities are a subset of the struct's (weakened, never strengthened) expected abilities. [5](#0-4) 

The submitted scenario ("union involving `AbilitySet::SIGNER` producing `has_store()` true") describes something the ability-set bit arithmetic categorically forbids, and no call path in the loader, verifier, or fungible-asset withdraw-capability code constructs abilities via a union that could smuggle `Store` onto a signer-typed value. There is no unprivileged entrypoint, no real custody boundary crossing, and no actual code defect identified — the question is a hypothetical built on a mathematically incorrect premise about how `union`/`has_store` behave.

    fn infer_struct_abilities(&self, qid: QualifiedId<StructId>, ty_args: &[Type]) -> AbilitySet {
        let (_, ty_params, struct_abilities) = self.struct_signature(qid);
        let ty_args_abilities_meet = ty_args
            .iter()
            .zip(ty_params)
            .map(|(ty_arg, param)| {
                let ty_arg_abilities = self.infer_abilities(ty_arg).1;
                if param.1.is_phantom {
                    // phantom type parameters don't participate in ability derivations
                    AbilitySet::ALL
                } else {
                    ty_arg_abilities
                }
            })
            .fold(AbilitySet::ALL, AbilitySet::intersect);
        // a struct has copy/drop/store if it's declared with the ability
        // and all it's fields have the ability
        // a struct has key if it's declared with key
        // and all fields have store
        let result = struct_abilities.intersect(ty_args_abilities_meet);
        if struct_abilities.has_ability(Ability::Key)
            && ty_args_abilities_meet.has_ability(Ability::Store)
        {
            result.add(Ability::Key)
        } else {
            result.remove(Ability::Key)
        }

#[cfg_attr(feature = "force-inline", inline(always))]
fn verify_pack<'a>(
    operand_stack: &mut Stack,
    field_count: u16,
    field_tys: impl Iterator<Item = &'a Type>,
    output_ty: Type,
) -> PartialVMResult<()> {
    let ability = output_ty.abilities()?;

    // If the struct has a key ability, we expect all of its field to
    // have store ability but not key ability.
    let field_expected_abilities = if ability.has_key() {
        ability
            .remove(Ability::Key)
            .union(AbilitySet::singleton(Ability::Store))
    } else {
        ability
    };
    for (ty, expected_ty) in operand_stack
        .popn_tys(field_count)?
        .into_iter()
        .zip(field_tys)
    {
        // Fields ability should be a subset of the struct ability
        // because abilities can be weakened but not the other
        // direction.
        // For example, it is ok to have a struct that doesn't have a
        // copy capability where its field is a struct that has copy
        // capability but not vice versa.
        ty.paranoid_check_abilities(field_expected_abilities)?;
        // Similar, we use assignability for the value moved in the field
        ty.paranoid_check_assignable(expected_ty)?;
    }
