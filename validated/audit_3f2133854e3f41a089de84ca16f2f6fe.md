### Title
Residual/stranded ERC20 balance in `ExternalActionSwap`/`LifiExternalAction` can be siphoned by any caller via crafted `externalActionMetadata` — theft of stranded or victim dust beyond declared `-deltaAmountChanges` (`contracts/external-actions/swaps/ExternalActionSwap.sol`, `contracts/external-actions/swaps/LifiExternalAction.sol`)

### Summary
`ExternalActionSwap.swap()` transfers exactly `-deltaAmountChanges[0]` of `inputToken` from `Hinkal` into the shared action contract, but never verifies that `callRouter` actually consumed that exact amount, nor does it sweep/refund any unconsumed `inputToken`. Because `LifiExternalAction.callRouter` grants the router an **unlimited** approval and measures `swappedAmount` only as the outputToken balance delta of the action contract around the router call, any ERC20 balance already sitting in the shared action contract (dust from rounding, partial fills, or another user's stranded input) can be swept by the router into `outputToken` during any subsequent caller's transaction and forwarded to that caller as a legitimate UTXO/withdrawal, exceeding what Hinkal actually sent them for that transaction.

### Finding Description
The invariant the protocol relies on is: *tokens the action consumes/produces in a tx == `-deltaAmountChanges` Hinkal sent it that tx*. In `_externalTransact` (`contracts/Hinkal.sol` lines 244-256), Hinkal sends exactly `uint256(-deltaAmountChanges[i])` of each negative-delta token to the external action, then calls `runAction`, whose return value (`utxoSet`) is later reconciled against Hinkal's own balance delta in `transact` (`contracts/Hinkal.sol` lines 96-146). Critically, this reconciliation only checks **Hinkal's own** balance change against `amountChanges[i] + utxoAmount` — it is tautologically satisfied by whatever the action actually transfers back to Hinkal, and says nothing about whether the amount the action *swapped* was proportional to what it was *sent*.

Inside `ExternalActionSwap.swap()` (`contracts/external-actions/swaps/ExternalActionSwap.sol` lines 44-102):
- `inputAmount = uint256(-deltaAmounts[0])` is computed and handed to `callRouter`.
- `callRouter` in `LifiExternalAction.sol` (lines 16-36) calls `approveUnlimited(inputToken, router)` and then `router.call(externalActionMetadata)` with **fully attacker-controlled calldata**. It measures `swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore`, i.e. it trusts whatever the router actually moved, with no check that the router consumed `inputAmount` of `inputToken` specifically.
- The function never checks the action's post-call `inputToken` balance, never refunds unspent `inputToken`, and never asserts that the router pulled exactly `inputAmount`.

Because the action contract (`LifiExternalAction`) is a **shared singleton** used across many users' transactions, any residual ERC20 balance parked in it — from rounding in the fee math (`inputAmount -= flatFee`, `swappedAmount - totalFee`), from partial fills by the router, or from a prior transaction that deliberately under-consumed its declared `inputAmount` — remains in the contract's balance indefinitely. Since `approveUnlimited` gives the router blanket approval over the action's entire token balance (not just the newly transferred amount), an attacker's own subsequent call can supply `externalActionMetadata` that directs the router to pull the *entire* current balance (stranded funds + their own small declared `inputAmount`) and swap all of it, while officially declaring only a tiny `-delta[0]` to Hinkal. The resulting `swappedAmount`/`amountToSendToHinkal` is entirely attacker-influenced and disconnected from the tiny amount Hinkal actually sent them, yet it is faithfully forwarded to the attacker as `outputToken` and wrapped in a UTXO (lines 95-101) that is fully validated by the (self-consistent, non-restrictive) Hinkal balance check.

None of the existing guards prevent this:
- `performHinkalChecks`, `verifyProof`, `rootHashExists` only validate proof/nullifier structure for the attacker's own declared inputs/outputs — they cannot see or constrain the action contract's internal token balance.
- The `balanceDif == amountChanges[i] + utxoAmount` check in `Hinkal.transact` only certifies that Hinkal's own balance moved by what was actually transferred — it does not certify that the swap's economic output was proportional to its declared input.
- `slippageValues[1]` is only a **floor**, not a cap, so it does not prevent the attacker from receiving more output than their declared input entitles them to.

### Impact Explanation
Any unprivileged caller who can trigger a swap through `LifiExternalAction`/`ExternalActionSwap` can extract any ERC20/ETH balance stranded in that shared action contract — whether from their own earlier crafted transaction or from dust left by other users' transactions — as a legitimate Hinkal UTXO or direct payout, without that value ever being reflected in the `-deltaAmountChanges` Hinkal sent them. When the stranded balance originates from another user's transaction, this is direct theft of shielded/in-flight user funds routed through the action contract (Critical). At minimum, even self-seeded residual laundering demonstrates the accounting hole is real and repeatable per transaction (limited only by how much residual currently sits in the shared contract).

### Likelihood Explanation
The attacker needs only: (1) ability to submit a normal Hinkal `transact` targeting the swap external action with a fully attacker-crafted `externalActionMetadata` (already an explicit attacker capability per the rules), and (2) some non-zero residual balance in the shared `LifiExternalAction` contract, which can be self-seeded in a prior attacker transaction (declare a large `-delta[0]`, craft metadata that only partially spends it) and then swept in a follow-up transaction — i.e., a self-sandwich requiring no privileged role and no cooperation from any other party. This is a fully feasible, repeatable, low-cost attack requiring only two ordinary Hinkal transactions.

### Recommendation
In `ExternalActionSwap.swap()` / `LifiExternalAction.callRouter`, enforce input-side conservation symmetrically to the output-side check: measure the action's `inputToken` balance before and after the router call and require the decrease equal exactly `inputAmount` (revert or refund any unconsumed input back to Hinkal so it is captured in `utxoSet`/`amountChanges` reconciliation). Additionally, avoid `approveUnlimited`; approve only the exact `inputAmount` needed per call so the router cannot pull any balance beyond what was explicitly sent for that transaction, and sweep/zero any leftover approval after the call.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `LifiExternalAction` with a mock router that supports arbitrary `.call` data to simulate partial fills (transfer only part of approved `inputToken`, mint/transfer `outputToken` back).
2. Tx A (seed residual): attacker calls `Hinkal.transact` with a swap action, declaring `amountChanges[0] = -1000` (input token). Craft `externalActionMetadata` so the mock router only pulls `1` wei of `inputToken`, minting a tiny amount of `outputToken` back — satisfying `slippageValues[1]`. Assert: `LifiExternalAction` contract now holds `999` residual wei of `inputToken`.
3. Tx B (sweep, same or different attacker): call `Hinkal.transact` again on the same action, declaring `amountChanges[0] = -1` (input token) — i.e., Hinkal only sends `1` wei to the action this time. Craft `externalActionMetadata` so the mock router pulls the **entire current balance** (`1000` wei, i.e., the newly sent `1` plus the `999` residual) of `inputToken` via the unlimited approval, swapping it for a proportional `outputToken` amount.
4. Assert the equality the question claims is broken: `outputToken received by attacker (via UTXO amountToSendToHinkal)` should equal `f(-deltaAmountChanges[0] sent in Tx B == 1 wei)`, but instead equals `f(1000 wei)` — i.e., attacker's payout in Tx B is derived from `1000`x the officially declared input, proving tokens leaving the action ≠ `-deltaAmountChanges` Hinkal sent it in that transaction.

    function swap(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) internal returns (UTXO[] memory utxoSet) {
        address inputToken = circomData.erc20TokenAddresses[0];
        uint256 inputAmount = uint256(-deltaAmounts[0]);

        if (inputToken == circomData.feeStructure.feeToken) {
            inputAmount -= circomData.feeStructure.flatFee;
        }

        address outputToken = circomData.erc20TokenAddresses[1];

        require(
            circomData.slippageValues[1] != 0,
            "swap output slippage floor not set"
        );

        require(
            block.timestamp <= circomData.timeStamp + SWAP_DEADLINE_WINDOW,
            "swap expired"
        );

        uint256 swappedAmount = callRouter(
            inputToken,
            inputAmount,
            outputToken,
            circomData.externalActionData.externalActionMetadata
        );

        uint256 relayFee = circomData.feeStructure.flatFee;

        uint256 hinkalFee = hinkalHelper.calculateRelayFee(
            swappedAmount,
            0,
            circomData.feeStructure.variableRate
        );

        if (circomData.feeStructure.feeToken == outputToken) {
            sendToRelay(circomData.relay, relayFee + hinkalFee, outputToken);
        } else {
            sendToRelay(
                circomData.relay,
                relayFee,
                circomData.feeStructure.feeToken
            );
            sendToRelay(circomData.relay, hinkalFee, outputToken);
        }

        uint256 totalFee = hinkalFee +
            (outputToken == circomData.feeStructure.feeToken ? relayFee : 0);
        uint256 amountToSendToHinkal = swappedAmount - totalFee;

        transferERC20TokenOrETH(outputToken, msg.sender, amountToSendToHinkal);

        utxoSet = new UTXO[](1);
        utxoSet[0] = UTXO({
            amount: amountToSendToHinkal,
            erc20Address: outputToken,
            stealthAddressStructure: circomData.stealthAddressStructure,
            timeStamp: block.timestamp
        });
    }

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }
