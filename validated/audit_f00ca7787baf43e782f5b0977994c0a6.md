### Title
Empty `erc20TokenAddresses` bypasses all Emporium/Hinkal balance-and-UTXO accounting, letting an attacker drain any token balance resident in `EmporiumUpgradeable` via an arbitrary op call - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` executes the attacker-supplied `stack.ops` (decoded independently from `externalActionMetadata`) unconditionally, but only reconciles balances/creates UTXOs for tokens present in `circomData.erc20TokenAddresses`. If that array is empty (a legal, dimension-consistent choice under `dimensionsCheck`), the ops still run and can call `endpoint.call{value}(callData)` as the Emporium contract itself, but neither `handleOut`'s `balanceChange <= 0` gate nor `Hinkal.transact`'s `balanceDif == amountChanges + utxoAmount` loop ever execute, since both iterate solely over the same empty array.

### Finding Description
Broken equality: "tokens leaving Emporium during op execution" should equal "0 counted in `utxoSet`/`balancesAfter - balancesBefore` accounting", but when `circomData.erc20TokenAddresses = []` the accounting side is vacuously 0 regardless of what actually left the contract.

Code path:
- `dimensionsCheck` in `contracts/HinkalHelper.sol` only enforces `circomData.erc20TokenAddresses.length == dimensions.tokenNumber` [1](#0-0) , with no minimum size — `tokenNumber = 0` is a legal dimension as long as a matching verifier exists for that size (the `emporium-min` style circuit implied by the question).
- `Hinkal.transact` computes `oldBalances`/`newBalances` and the conservation loop strictly `for (i < circomData.erc20TokenAddresses.length)` [2](#0-1) . With an empty array this loop, and hence the `balanceDif == amountChanges + utxoAmount` check, never runs.
- `_externalTransact` calls `IExternalActionV2(...).runAction(circomData, deltaAmountChanges)` where `deltaAmountChanges` is also sized by `erc20TokenAddresses.length` (i.e., empty) [3](#0-2) .
- Inside `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are computed over the same empty array (no-op), but the `stack.ops` loop that actually performs the calls is driven by `stack.ops.length`, decoded from `externalActionMetadata`, completely independent of `erc20TokenAddresses` [4](#0-3) .
- For a stateless op (`invokeWallet` false, or `stack.signerAddress == address(0)`), `verifyWallet` skips the EIP-712 signature check entirely and only marks the message used [5](#0-4) , then the op executes as `op.endpoint.call{value: op.value}(op.callData)` with Emporium as `msg.sender`, restricted only from calling `callHinkalWallet`/`doSendToRelay` selectors [6](#0-5) . An attacker can therefore encode `op.callData = token.transfer(attacker, amount)` to move any ERC20 balance currently held by Emporium to themselves.
- The post-loop accounting/UTXO-creation loop, and `handleOut`'s `balanceChange <= 0` early-return that normally sweeps surplus back to `msg.sender` [7](#0-6) , both iterate `circomData.erc20TokenAddresses` — with the array empty, they never execute for the drained token, so `utxoSet` stays empty and no revert (`BalanceChangeShouldBePositive`) can ever fire for that token.
- Back in `Hinkal.transact`, `utxoSet` is empty (consistent with `tokenNumber = 0`), so the conservation loop (which is empty anyway) trivially passes, and `insertNullifiers`/`insertCommitments` run over empty arrays too — leaving zero on-chain trace of the stolen value.

The code's own comment ("the only case when balanceChange can be < 0, when there were some funds on emporium before the call") acknowledges Emporium can legitimately hold residual token balance across transactions (e.g., dust from a partial swap, or a token produced by an op but omitted from a prior transaction's `erc20TokenAddresses`). Any such residual balance — belonging to whichever party's transaction left it there — is fully exposed to any subsequent attacker transaction using `erc20TokenAddresses = []`.

### Impact Explanation
Direct theft of any ERC20 (or ETH) balance resident in the `EmporiumUpgradeable` contract at attack time, with zero UTXO/nullifier/commitment trace and no possibility of Hinkal's own conservation check (`balanceDif == amountChanges + utxoAmount`) catching it, since that check is scoped to the same empty `erc20TokenAddresses` array. This is repeatable any time Emporium holds a non-zero balance of some token not listed by the attacker's chosen dimension, matching the Critical category ("direct theft of shielded or in-flight user funds").

### Likelihood Explanation
Precondition: Emporium must hold a non-zero balance of some token at the time of attack (from dust/partial-fill residue of a legitimate prior op, or from a token unintentionally excluded from a previous transaction's `erc20TokenAddresses`). Given the codebase explicitly anticipates this residual-balance state, and swap/DeFi-style ops routed through Emporium are exactly the kind of flow that can leave surplus tokens, this precondition is realistic. The attacker's own cost is just generating one valid zero-dimension proof and one `EmporiumOperation` calling `token.transfer`/similar — well within the capabilities of any unprivileged EOA who can build a proof and encode `externalActionMetadata`.

### Recommendation
Do not size the balance/UTXO reconciliation arrays purely from `circomData.erc20TokenAddresses`. Either (a) forbid `erc20TokenAddresses.length == 0` for any externalAction with non-empty `stack.ops`, or (b) require `runAction` to independently enumerate every token address touched by `stack.ops` (e.g., via a token allow-list check per op or a global sweep-back-to-zero invariant asserting Emporium's balance for any token is zero both before and after every `runAction`, regardless of whether that token appears in `erc20TokenAddresses`). Additionally, do not allow `verifyWallet` to skip signature checks while still permitting `op.endpoint.call` to arbitrary externally-supplied targets/data with Emporium as the caller.

### Proof of Concept
Foundry test plan:
1. Deploy Hinkal, HinkalHelper, EmporiumUpgradeable, and a mock ERC20 `X`.
2. Simulate a legitimate flow that leaves `X` balance stuck on Emporium (e.g., an op that receives `X` into Emporium but where the transaction's `erc20TokenAddresses` intentionally omits `X`), or directly `deal`/`mint` tokens to Emporium to model the residual-balance precondition.
3. Craft an attacker `CircomData` with `erc20TokenAddresses = []`, matching empty `amountChanges`, `slippageValues`, `onChainCreation`, `inputNullifiers`, `outCommitments`, `encryptedOutputs`, dimensions `tokenNumber = 0`, and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one stateless op: `endpoint = address(X)`, `callData = abi.encodeCall(IERC20.transfer, (attacker, stuckAmount))`.
4. Generate a valid proof for this zero-dimension circuit and call `Hinkal.transact`.
5. Assert: `X.balanceOf(attacker)` increases by `stuckAmount`; `Hinkal.transact` does not revert; no `UTXO`/commitment is emitted for `X`; the `balanceDif` loop in `Hinkal.transact` (bounded by the empty `erc20TokenAddresses`) never executes, i.e., there is no revert path and no accounting entry corresponding to the transferred value.

    function runAction(
        CircomData calldata circomData,
        int256[] calldata deltaAmountChanges
    ) external override onlyAllowedRecipient returns (UTXO[] memory) {
        EmporiumStack memory stack = abi.decode(
            circomData.externalActionData.externalActionMetadata,
            (EmporiumStack)
        );

        uint256[] memory balancesBefore = getBalancesForArray(
            circomData.erc20TokenAddresses
        );

        verifyWallet(stack, circomData);

        for (uint256 i = 0; i < stack.ops.length; i++) {
            EmporiumOperation memory op = stack.ops[i];

            bool success;
            bytes memory err;

            // CASE 1: Stateful Interaction
            if (op.invokeWallet && stack.signerAddress != address(0)) {
                (success, err) = IHinkalWallet(stack.signerAddress)
                    .callHinkalWallet(op.endpoint, op.callData, op.value);
            }
            // CASE 2: Stateless Interaction
            else {
                bytes4 selector = bytes4(op.callData);
                if (
                    selector == IHinkalWallet.callHinkalWallet.selector ||
                    selector == IHinkalWallet.doSendToRelay.selector
                ) {
                    revert UnauthorizedWalletCall();
                }

                (success, err) = op.endpoint.call{value: op.value}(op.callData);
            }

            if (!success) {
                revert CallFailed(err);
            }
