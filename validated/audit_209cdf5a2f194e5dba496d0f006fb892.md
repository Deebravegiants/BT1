### Title
Zero-value order outputs permanently freeze escrowed input funds in same-chain fills - (File: evm/src/apps/intentsv2/IntrinsicIntents.sol)

### Summary
`placeOrder` in `IntentGatewayV2.sol` never validates that individual `order.output.assets[i].amount` values are non-zero — only that `order.inputs.length != 0` is enforced [1](#0-0) , and inputs themselves are checked for zero amount [2](#0-1) . Because `order.output.assets` is user-supplied data with no minimum, an order can be placed with a zero-required output leg. When such an order is filled on the same chain, `_fillSameChain` silently skips that leg's escrow accounting while still marking the order fully filled, permanently trapping the corresponding escrowed input tokens with no way to withdraw them. This mirrors the referenced report's root cause: nothing stops a caller from "starting" a state transition (here, an order) with a zero-value leg, and the downstream logic proceeds as if the funds were properly handled.

### Finding Description
`_fillSameChain` iterates over each output leg and computes `totalRequired = order.output.assets[i].amount` and `remaining = totalRequired - alreadyFilled`. When `totalRequired == 0`, `remaining` is also `0`, so the loop hits: [3](#0-2) 
```
uint256 alreadyFilled = _partialFills[commitment][outputToken];
uint256 remaining = totalRequired - alreadyFilled;
if (remaining == 0 || solverAmount == 0) {
    if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
    continue;
}
```
`continue` skips the rest of the loop body for that index, so `escrowedInputs[i]` — pre-initialized to the zero-value default `TokenInfo({token: 0, amount: 0})` — is never populated with the real `order.inputs[i].token`/amount, and `isFullyFilled` is not downgraded to `false` (the `remaining > 0` branch only fires when `solverAmount == 0` and `remaining > 0`, which is false here since `remaining == 0`).

After the loop, if every output leg is either satisfied or has `totalRequired == 0`, `isFullyFilled` remains `true`, and the order is finalized: [4](#0-3) 
```
WithdrawalRequest memory body = WithdrawalRequest({
    commitment: commitment, tokens: escrowedInputs, beneficiary: ...
});
_withdraw(body, false, isFullyFilled);
if (isFullyFilled) {
    _execute(order, outputsLen);
    emit OrderFilled(...);
}
```
`_withdraw` is called with `finalize = true`, which immediately sets `_filled[body.commitment] = beneficiary` [5](#0-4) . Because `escrowedInputs[i]` for the zero-required leg is `{token: 0, amount: 0}`, the withdrawal loop's `if (amount == 0) continue;` skips it entirely [6](#0-5)  — the real escrowed balance recorded under `_orders[commitment][realInputToken]` (set at `placeOrder` time [7](#0-6) ) is never decremented and never transferred to anyone.

Once `_filled[commitment]` is non-zero, both `fillOrder` and `cancelOrder` are permanently blocked from acting on this commitment again: [8](#0-7) [9](#0-8) 
This leaves the user's originally escrowed tokens permanently stuck in the `IntentGatewayV2` contract with no remaining code path to release them — the exact "started with zero funds, no way to complete/recover" failure mode described in the reference report, except here the consequence is a confirmed fund freeze rather than a hypothetical revert.

### Impact Explanation
Any user who places a same-chain order containing a zero-amount output leg (either intentionally exploiting the gap, or accidentally, e.g. a UI/SDK bug that produces a zero output amount) creates an order whose full-fill path leaves the corresponding escrowed input tokens permanently locked once any solver fills it. This is a permanent freezing-of-funds condition reachable from a single unprivileged `placeOrder` + `fillOrder` transaction pair, with no admin or governance involvement, satisfying the "permanent freezing of funds" impact bar.

### Likelihood Explanation
Likelihood is high: the order placer fully controls `order.output.assets[i].amount` and there is no validation anywhere in `placeOrder` preventing a zero value; `fillOrder`/`_fillSameChain` do not reject zero-`totalRequired` legs, so any order with such a leg reaches the vulnerable code path on the very next fill, which requires only that any solver (or the order-placer's own account) calls `fillOrder`.

### Recommendation
In `placeOrder`, reject orders whose `order.output.assets[i].amount == 0` for any `i` (mirroring the existing zero-amount check already applied to inputs). Additionally, in `_fillSameChain`, ensure `escrowedInputs[i]` is always populated with `order.inputs[i].token`/its proportional amount even when a leg is skipped due to `totalRequired == 0`, so escrow accounting cannot silently diverge from what gets finalized in `_withdraw`.

### Proof of Concept
1. User calls `placeOrder` with a single input (e.g., 1000 USDC) and a single output leg where `order.output.assets[0].amount = 0`. `placeOrder` accepts this since only `order.inputs[i].amount == 0` is checked, not outputs [2](#0-1) . The 1000 USDC is escrowed under `_orders[commitment][usdc]` [7](#0-6) .
2. Any solver calls `fillOrder` with `options.outputs[0].amount = 0` (satisfying `token` match and requiring no payment since `totalRequired == 0`).
3. In `_fillSameChain`, `remaining == 0` causes `continue`, so `escrowedInputs[0]` stays `{token:0, amount:0}` and `isFullyFilled` remains `true` [10](#0-9) .
4. `_withdraw(body, false, true)` sets `_filled[commitment] = solver` but skips releasing the 1000 USDC because `escrowedInputs[0].amount == 0` [11](#0-10) .
5. `_orders[commitment][usdc]` still shows 1000 USDC escrowed, but `_filled[commitment] != address(0)` now blocks both `cancelOrder` and any further `fillOrder` call on this commitment — the 1000 USDC is permanently stuck in the `IntentGatewayV2` contract.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
