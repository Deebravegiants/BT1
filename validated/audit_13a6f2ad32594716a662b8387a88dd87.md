### Title
Username Enumeration via Timing Attack in Local Auth `/sessions` Login Endpoint - (File: `core/sessions/localauth/orm.go`)

### Summary
The chainlink node's local authentication `CreateSession` function contains the same short-circuit timing flaw described in the FileBrowser advisory (GHSA-43mm-m3h2-3prc): a fast database-lookup failure path for non-existent users versus a slow bcrypt-verification path for existing users, both reachable unauthenticated via the public `/sessions` login endpoint.

### Finding Description
The unauthenticated `POST /sessions` endpoint is handled by `SessionsController.Create`, which forwards the request directly to `AuthenticationProvider().CreateSession(ctx, sr)` [1](#0-0) .

For the local auth provider, `orm.CreateSession` first performs a `FindUser` DB lookup by email and returns immediately with an error if the user does not exist — no password verification of any kind occurs on this path: [2](#0-1) 

Only if the user is found does the code proceed to `utils.CheckPasswordHash`, which invokes bcrypt (`bcrypt.CompareHashAndPassword`), an intentionally slow, computationally expensive operation: [3](#0-2) [4](#0-3) 

This is structurally identical to the FileBrowser vulnerability: `err != nil` (user not found) short-circuits before the expensive bcrypt check ever runs, while `err == nil` (user found) unconditionally executes bcrypt regardless of whether the password is correct. Additionally, before `CreateSession` is even called, `SessionsController.Create` performs a separate DB lookup via `GetUserWebAuthn(ctx, sr.Email)` for every request [5](#0-4) , but this does not offset the bcrypt-induced timing gap since it runs for both valid and invalid emails.

The same anti-pattern is present in the LDAP and OIDC providers' local-admin fallback paths (`ldapAuthenticator.localLoginFallback`, `oidcAuthenticator.localLoginFallback`), which also perform a DB lookup that returns immediately on failure before ever reaching `utils.CheckPasswordHash` [6](#0-5) [7](#0-6) , though these are reached only after an upstream LDAP/OIDC bind failure and are secondary/lower-likelihood paths compared to the primary local-auth `/sessions` route.

### Impact Explanation
An unauthenticated remote attacker can measure response time differences on `POST /sessions` to distinguish "user not found" (fast, DB lookup only) from "user found, wrong password" (slow, DB lookup + bcrypt) responses. This allows enumeration of valid node operator/admin email addresses without any credentials, which:
- Narrows the target list for credential stuffing or brute-force password attacks against the Chainlink node's admin/operator API.
- Given that a compromised admin account on a Chainlink node can lead to configuration changes, job management, and key/fund-related operations, username enumeration meaningfully lowers the bar for a follow-on account-takeover attack chain.

This aligns with the CVSS vector in the original advisory (`AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N`) — confidentiality-only impact via information disclosure, no direct authentication bypass.

### Likelihood Explanation
High likelihood of exploitability: `/sessions` is unauthenticated and internet-facing wherever the node's operator UI/API is exposed, requires no user interaction, and the timing side channel (bcrypt vs. no bcrypt) is large and easily distinguishable using the same statistical calibration approach shown in the original PoC.

### Recommendation
Ensure a constant-time cost is paid regardless of whether the user exists, e.g. by always calling `utils.CheckPasswordHash` against a dummy/fixed bcrypt hash when `FindUser` fails, before returning the "invalid" response, so that the execution time for non-existent and existent usernames converges. Apply the same fix to the LDAP and OIDC `localLoginFallback` functions if they remain reachable pre-authentication.

### Proof of Concept
Using the PoC script from the original advisory (calibrate against random emails on `POST /sessions`, then measure per-candidate email time), an attacker would observe:
- Non-existent email: fast response (`FindUser` DB miss, immediate return) — [2](#0-1) 
- Existing email + wrong password: slower response (DB hit + bcrypt `CheckPasswordHash`) — [8](#0-7) 

Repeating requests to `/sessions` with a wordlist of candidate emails and comparing against the calibrated threshold reveals which emails correspond to real accounts, exactly as demonstrated against FileBrowser's `/api/login`.

// CheckPasswordHash wraps around bcrypt.CompareHashAndPassword for a friendlier API.
func CheckPasswordHash(password, hash string) bool {
	err := bcrypt.CompareHashAndPassword([]byte(hash), []byte(password))
	return err == nil
}
