### Title
Excess native token sent to `EvmHost.dispatch`/`fundRequest` is stranded in the contract instead of refunded to the caller - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` accept arbitrary `msg.value` and forward the *entire* `msg.value` into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)`, but never refund the leftover ETH the router returns to `EvmHost` after the swap.

### Finding Description
Each of these functions is `payable` and unprivileged — any user calling them can send more native token than needed to cover `post.fee` / `get.fee` / `amount`: [1](#0-0) [2](#0-1) [3](#0-2) 

`swapETHForExactTokens` only consumes as much ETH as the swap needs and refunds the rest to its immediate caller — which in this call chain is `EvmHost`, not the original user. Unlike other parts of the codebase that explicitly compute and refund unspent `msg.value` to `msg.sender` after the swap (e.g. `IntentGatewayV2.placeOrder` and `ExtrinsicIntents.fillOrder`, both of which subtract `amounts[0]`/`nativeFee` from `msgValue` and call `_sendValue(msg.sender, msgValue)`), `EvmHost`'s three native-token entry points have no such logic: [4](#0-3) [5](#0-4) 

Any overpayment beyond the exact fee-token cost is left as ETH balance on `EvmHost` and is not returned to the depositor. This is not a design decision documented anywhere in `EvmHost`'s NatSpec, which only says "Will revert if enough native tokens are not provided" — implying, but not delivering, exact-amount handling for overpayment.

### Impact Explanation
The stranded ETH is not simply "lost" into the void — it accumulates as `EvmHost`'s native balance, but the only path to move it out is `EvmHost.withdraw(WithdrawParams)`, gated by `restrict(_hostParams.hostManager)` and only reachable via a signed Hyperbridge governance message routed through `HostManager.onAccept`: [6](#0-5) [7](#0-6) 

For the individual user, this is a permanent loss of the excess funds sent (no self-service recovery/refund mechanism exists), and the funds become de-facto donated to protocol treasury/governance rather than being an exploitable "grab it first" bug for arbitrary third parties. Since `dispatch()`/`fundRequest()` are the core, most-used unprivileged entry points of the entire Hyperbridge protocol (used by every app dispatching a cross-chain message with native-token payment), any user misestimating fees (a real risk given the explicit warning in the docs about `quote()` being sandwich-attackable and meant only for off-chain estimation) permanently loses the difference on every call.

### Likelihood Explanation
High likelihood of occurring accidentally: front-ends estimate `msg.value` off-chain via `quote()`, and the documentation itself warns this estimate can be stale/inaccurate due to slippage and sandwiching, and recommends leaving margin. Anyone sending a safety margin above the exact quoted fee (a very common integration pattern to avoid reverts from price movement) will lose the difference to the contract with no refund path back to themselves.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.placeOrder` / `ExtrinsicIntents.fillOrder`: capture the `amounts` returned by `swapETHForExactTokens`, compute the unspent ETH remainder (`msg.value - amounts[0]`), and forward it back to `_msgSender()` via a low-level call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`.

### Proof of Concept
1. User calls `EvmHost.dispatch(post)` with `post.fee = X` and `msg.value = 2X` (a reasonable slippage buffer).
2. `swapETHForExactTokens{value: 2X}(X, path, address(this), ...)` executes; the router only needs, say, `1.1X` worth of ETH to buy `X` fee tokens, and refunds `0.9X` ETH back to `EvmHost`.
3. `EvmHost`'s ETH balance increases by `0.9X`; the user's transaction never receives this back.
4. Repeated over many callers, `EvmHost` accumulates ETH that is unreachable except by cross-chain governance action, and it is never returned to any of the original depositors.

    function withdraw(WithdrawParams memory params) external restrict(_hostParams.hostManager) {
        if (params.token == address(0)) {
            // this is safe because re-entrancy is mitigated before dispatching requests
            (bool sent,) = params.beneficiary.call{value: params.amount}("");
            if (!sent) revert WithdrawalFailed();
        } else {
            IERC20(params.token).safeTransfer(params.beneficiary, params.amount);
        }
        emit HostWithdrawal({beneficiary: params.beneficiary, amount: params.amount, token: params.token});
    }
