### Title
Token-donation underflow in `Router._computeBuy`'s overflow-cap branch permanently blocks the curve-draining buy and freezes a token's supply-trigger graduation - (File: `packages/contracts/src/Router.sol`)

### Summary
`Router._computeBuy` caps `tokensOut` at the pair's live `tokenBalance()` when the constant-product formula would exceed remaining real supply, then back-calculates `amountInUsed` via `cappedReserveToken = reserveToken - tokensOut`. This subtraction assumes `tokenBalance() <= reserveToken` always holds. Any unrelated wallet can violate that assumption for free by directly `transfer`-ing the launched `Token` into its own `Pair` (a plain ERC20 transfer, no permission needed), inflating `tokenBalance()` above the stored `reserveToken`. Once that state exists, every buy large enough to enter the overflow-cap branch causes `cappedReserveToken` to underflow and revert under Solidity 0.8's checked arithmetic — permanently DoS-ing the one buy that is supposed to drain the curve and fire the supply-trigger graduation.

### Finding Description
`Router._computeBuy` (used by `Router.buy`, called from `Bonding.buy`) is: [1](#0-0) 

The capping branch fires whenever the uncapped constant-product `tokensOut` exceeds `realBalance = pair.tokenBalance()`. It then sets `tokensOut = realBalance` and computes `cappedReserveToken = reserveToken - tokensOut`. This subtraction is only safe if `reserveToken >= realBalance`. In the protocol's honest state that invariant holds by construction — the virtual token reserve is always seeded above the real (curve-supply) balance [2](#0-1)  and is explicitly asserted as `pair.tokenBalance() < pair.tokenReserve()` in the test suite's invariant coverage [3](#0-2) .

However, `Token` is a plain ERC20 clone, and any wallet holding it can `transfer` it directly into the `Pair` contract, which only ever tracks its balance via live `IERC20.balanceOf` reads for `tokenBalance()` — never adjusting `reserveToken`. This is a documented, previously-exploited attack surface: a "donation attack" that inflates `tokenBalance()` above `reserveToken` was already found and partially fixed, but only inside `Bonding.previewLtUntilGraduation`'s off-chain preview/quote path: [4](#0-3) [5](#0-4) 

The guard added there — "Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg" (`if (realBalance >= reserveToken) return ltUntilThreshold;`) — was never mirrored into `Router._computeBuy`, which is the actual state-mutating execution path invoked by every real `buy()` call. `_computeBuy` still performs the unguarded `reserveToken - tokensOut` subtraction with no check that `tokensOut (== realBalance)` doesn't exceed `reserveToken`.

Because Solidity 0.8.24 uses checked arithmetic, the underflow does not silently wrap (unlike the C-level buffer/index overflow in CVE-2017-12108); instead it reverts. But the effect is analogous in class and impact: an attacker-controlled size value (the donated token balance) corrupts an arithmetic step that the protocol depends on to close out a bonding curve, turning a benign integer relationship into a hard revert on the one specific transaction — the graduation-triggering, curve-draining buy — that the whole two-phase-graduation design depends on being reachable.

### Impact Explanation
Once a wallet donates enough `Token` to the `Pair` to push `tokenBalance() > reserveToken`, every subsequent buy that is large enough for `_computeBuy`'s uncapped formula to exceed `realBalance` enters the capping branch and reverts with a `Panic(0x11)` underflow instead of completing. This permanently removes the only code path (`Router.buy`'s overflow cap) capable of ever draining the pair down to `tokenBalance() == 0`, which is one of the two independent graduation triggers [6](#0-5) . For any token whose reserve-asset exchange rate never crosses the USD graduation threshold (e.g. a flat/bear market — explicitly called out as the reason the supply trigger exists), the curve can be driven arbitrarily close to exhaustion but the final capping buy will always revert, permanently trapping:
- the remaining un-sold real tokens sitting in the `Pair`,
- the `LP_RESERVE` (250M tokens) parked in `Bonding` waiting for phase-2 seeding,
- and the LT raised by the curve so far, which can never be drained via `Router.graduate` because `_enterGraduating` is never reached.

This is a permanent freezing of trader, creator, and LP funds for the affected token, reachable by a single unprivileged wallet at the cost of the donated tokens (which can be bought cheaply on the same curve before donating).

### Likelihood Explanation
High. The precondition (`Token.transfer(pair, amount)`) is a direct ERC20 transfer explicitly listed as an in-scope reachable action, requires no special role, and costs only the price of acquiring enough tokens on the curve to donate back to the pair — well within a single unprivileged trader's budget. The triggering condition (a buy large enough to hit the overflow-cap branch) is exactly the kind of large/closing buy that legitimately occurs near graduation, so the bug fires opportunistically even without an attacker timing it, and can be deliberately forced by any wallet wanting to grief a specific token's graduation.

### Recommendation
Mirror the guard already present in `Bonding.previewLtUntilGraduation` into `Router._computeBuy`: before computing `cappedReserveToken = reserveToken - tokensOut`, check whether `realBalance >= reserveToken` (donation-inflated balance) and short-circuit to a safe, non-reverting behavior — e.g. treat the supply trigger as unreachable for that buy and fall back to the uncapped/quote path, or cap `tokensOut` using `min(realBalance, reserveToken)` consistently with the invariant the rest of the system assumes. Additionally, consider having `_graduate`'s existing `unsoldBurned` donation-cleanup logic run defensively earlier, or add a `Pair`-level guard that prevents `tokenBalance()` from being read as authoritative when it diverges from `reserveToken` in the wrong direction.

### Proof of Concept
1. Launch a token via `Bonding`/`Zap` normally; note `pairAddr`, `reserveToken` (virtual, e.g. 1B) and `realBalance` (curve supply, e.g. 750M).
2. As an unprivileged wallet, buy a large batch of the token via `Zap.buy`/`Bonding.buy` to accumulate real `Token` balance.
3. `IERC20(tokenAddress).transfer(pairAddr, amountDonated)` directly (no role required) with `amountDonated` large enough that `pair.tokenBalance() > reserveToken` (this is the same setup used by the existing regression test `test_donation_realBalanceExceedsReserveToken` [7](#0-6) , which confirms this state is reachable).
4. Have any wallet submit a buy sized so that `_computeBuy`'s uncapped `tokensOut` (from `reserveToken - k/newReserveAsset`) exceeds the now-inflated `realBalance` — i.e., a buy targeting the pair's near-exhaustion region.
5. `Router.buy` → `_computeBuy` sets `tokensOut = realBalance`, then evaluates `cappedReserveToken = reserveToken - tokensOut`; since `realBalance > reserveToken`, this reverts with a `Panic(0x11)` arithmetic underflow, aborting the transaction.
6. Because the donated `Token` balance is not reduced by ordinary trading (only `_graduate`'s `unsoldBurned` step removes it, which is unreachable while this bug blocks the capping buy), every future attempt at the curve-draining buy reverts the same way, permanently preventing supply-trigger graduation for this token whenever its USD trigger cannot independently be crossed.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }

    function previewLtUntilGraduation(
        address token_
    ) external view returns (uint256) {
        BondingStorage storage $ = _s();
        TokenInfo storage info = $.tokenInfo[token_];
        if (info.creator == address(0)) return 0;
        if (info.lifecycle != Lifecycle.Curve) return 0;

        address pair = info.pair;
        uint256 realBalance = IPair(pair).tokenBalance();
        if (realBalance == 0) return 0;

        (uint256 reserveToken, uint256 reserveAsset) = IPair(pair).getReserves();

        uint256 ltUntilThreshold = type(uint256).max;
        uint256 exchangeRate = IBounceLeveragedToken(info.ltAddress).exchangeRate();
        if (exchangeRate > 0) {
            uint256 realLtRaised = reserveAsset - _launchTimeVirtualLtReserve(token_, pair);
            uint256 thresholdRealLt = ($.graduationThresholdUsd * 1e18 + exchangeRate - 1) / exchangeRate;
            if (realLtRaised >= thresholdRealLt) return 0;
            ltUntilThreshold = thresholdRealLt - realLtRaised;
        }

        // Donation-inflated `realBalance`: supply trigger unreachable, defer to USD leg.
        if (realBalance >= reserveToken) return ltUntilThreshold;

        uint256 cappedReserveToken = reserveToken - realBalance;
        uint256 cappedReserveAsset = (IPair(pair).k() + cappedReserveToken - 1) / cappedReserveToken;
        uint256 ltUntilSupply = cappedReserveAsset - reserveAsset;

        return ltUntilSupply < ltUntilThreshold ? ltUntilSupply : ltUntilThreshold;
    }

        // `tokensOut = TOTAL_SUPPLY × ltIn / (virtual + ltIn)`, which crosses

        // full opening virtual reserve lands `tokensOut = 500M` — plenty of
        // headroom to push `realBalance > reserveToken` after the donation.

        vm.startPrank(drainer);

        vm.stopPrank();
        donatedTokens = Token(tokenAddr).balanceOf(drainer);
        vm.prank(drainer);
