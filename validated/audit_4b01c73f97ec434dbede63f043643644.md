### Title
Webhook shop identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, then trusts the unauthenticated `X-Shopify-Shop-Domain` header as the tenant identity passed to the app's handler. Because the shop field is never part of the signed payload, and the HMAC secret (`Context.api_secret_key`) is a single value shared across every shop that installs the app, any user who can obtain one valid `(raw_body, hmac)` pair — for example by installing the app on their own (even free/dev) store and observing a genuine webhook delivery — can replay that exact body with a forged `shop-domain` header claiming to be a different, victim shop. The signature check still passes because it never covered `shop`, so the app processes attacker-supplied data as if it belonged to the victim tenant.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from an attacker-controllable HTTP header with no cryptographic tie to the body or the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate`/`validate_signature` compute the signature purely from `to_signable_string` (i.e. the body) using the app-wide `Context.api_secret_key` — the same secret is used to validate webhooks for every shop that has ever installed the app, and it is entirely independent of which shop is claimed in the header: [3](#0-2) 

`Webhooks::Registry.process` performs the HMAC check and then immediately trusts `request.shop` as the tenant identity handed to the app's business logic, with no secondary verification that the shop is legitimately associated with this payload: [4](#0-3) 

The identity binding that should hold is: `hmac == HMAC(secret, body || shop)`, i.e. the shop the handler acts on should be cryptographically tied to the same bytes that were verified. Instead the gem verifies `hmac == HMAC(secret, body)` and separately parses `shop` from an unauthenticated header, so `verified_bytes != acted_on_identity` — the exact class of binding gap described in the vault report (a value used to drive business logic that isn't covered by the authenticity check).

### Impact Explanation
This breaks tenant isolation between all shops using the same app installation set. An attacker who installs the app on any shop they control (a low-privilege, self-service action requiring no special credentials) can capture one genuine webhook delivery (body + valid HMAC), then replay that identical body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `x-shopify-shop-domain`) header value for any other merchant's domain. The app's webhook handler executes with `shop` set to the victim's domain, so any handler logic keyed by shop (creating/updating records, triggering side effects, invalidating caches, writing to the victim's tenant data) is executed under the wrong, attacker-chosen tenant — a cross-tenant access/data-injection primitive.

### Likelihood Explanation
Likelihood is realistic: no secret material is required, only the ability to install the app on an attacker-owned shop (or to observe/replay any webhook payload, since none of the shop-scoping is cryptographically enforced). The HMAC secret is global to the app, not per-shop, so a value that is "legitimate" for the attacker's own shop is equally "valid" when replayed while claiming to be any other shop, because `shop` was never part of what was verified.

### Recommendation
Bind the shop identity into the authenticated payload before trusting it:
- Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed string (`to_signable_string`) so forged/replayed headers fail verification, or
- After HMAC verification, independently confirm that the `shop` claimed in the header actually corresponds to a shop with a currently valid, stored session/installation for this app, rejecting webhooks for shops that aren't recognized as active installations, and
- Reject cross-shop replays by tracking `webhook_id`/delivery uniqueness per shop.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` (free/dev store, no special privilege needed).
2. Trigger any webhook topic the app subscribes to (e.g. `orders/create`) on that shop and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header from the delivery.
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but change `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks the body against the shared `api_secret_key`.
5. `Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, causing the app to act on attacker data under the victim's tenant identity.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
