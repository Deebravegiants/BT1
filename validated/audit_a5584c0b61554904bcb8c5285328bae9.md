### Title
Local signup declared "Success" for app-centric (user-centric) signups without any backend confirmation - ([File: src/plans/mod.rs])

### Summary
In `Plan::do_signup`, when a QR/user-data payload sets `user_centric_signup = true` (and the operator config `ignore_user_centric_signups` is not set), the orb marks the signup's `enrollment_status` and `result.success` as `Success` purely from the locally computed `signup_reason`, without ever calling `self.enroll_user(...)` (the function that performs the actual `signup_post`/`signup_poll` backend request/confirmation cycle). This is the same bug class as the reported issue: an outcome ("shares minted" / "enrollment completed") is assumed to be non-zero/successful without validating that the authoritative external system (backend) actually confirmed it.

### Finding Description
`_deployFunds` in the reference report assumed `targetVault.deposit()` always returns a non-zero share count and never checked the return value, so the strategy could locally believe the deposit succeeded while receiving nothing in return.

The analogous pattern in this repo is in `do_signup`: [1](#0-0) 

```rust
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups
{
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(orb, debug_report, &capture, pipeline.as_ref(), signup_reason))
        .await
        .is_success()
};
```

For the non-user-centric branch, `enroll_user::run` actually performs and waits on the authoritative backend round trip: it POSTs the signup via `signup_post::request` and then polls `signup_poll::request` up to `POLL_STATUS_COUNT` times, only returning `Status::Success` once the backend explicitly reports `Status::Completed` with `success: true`: [2](#0-1) 

In the user-centric branch, none of that happens — `enrollment_status` is set to `Success` purely because the *local* `signup_reason` (derived only from local pipeline output and local `detect_fraud`) equals `SignupReason::Normal`: [3](#0-2) 

`signup_reason` here reflects only local biometric-pipeline success and local fraud heuristics — it carries no information about whether the backend has actually accepted, deduplicated, or committed the signup (which is exactly the check that `signup_post`/`signup_poll` perform in the non-user-centric path, e.g. detecting "Backend duplicates", "Backend inflight matches", "Backend detected fraud" as enumerated in `enroll_user.rs`): [4](#0-3) 

The comment on the config flag confirms the intent is to let the *app* submit the signup independently for user-centric flows: `ignore_user_centric_signups` — "Ignore app centric signup flag from the app and always perform an enrollment request", and `user_centric_signup` — "Whether the orb should perform app-centric signups": [5](#0-4) [6](#0-5) 

The `user_centric_signup` flag itself is attacker-influenced input: it is taken verbatim from `orb_qr_link::UserData`, part of the authenticated app-data payload returned via the user QR-code validation flow, and is only integrity-checked against a QR-embedded hash (`user_data.verify(user_data_hash)`) — not against any subsequent proof that the app will actually complete the backend submission: [7](#0-6) 

The critical gap: after setting `user_centric_signup = true`, the orb never verifies — via `orb_relay` or any other channel — that the app actually completed its independent backend submission before it locally records `debug_report.signup_successful()` and increments `main.count.signup.result.success.successful_signup`, and before returning `result.success = true` from `do_signup`: [8](#0-7) [9](#0-8) 

### Impact Explanation
If the app never completes its independent submission to the backend (e.g., the app crashes, the network drops after the orb-relay handshake, the user backs out of the app flow, or a malicious/modified app simply never calls the equivalent of `signup_post`/`signup_poll`), the orb still locally believes and records the signup as `Success`/`signup_successful`, exactly like the reference bug where the strategy believed it received vault shares when it received none. This is a misattributed-signup-completion state: the orb's own debug report, metrics, and `SignupResult.success` claim a completed, fraud-checked, duplicate-checked enrollment even though the authoritative backend check (duplicate detection, backend fraud detection, and actual credential/World ID issuance) never ran or never confirmed completion. Because `signup_reason` is derived only from local fraud heuristics (which can be skipped via `skip_fraud_checks` in dev builds, or simply not catch what backend-side deduplication would), this also creates a path for cross-signup state bleed / falsely-recorded successful signups without backend corroboration.

### Likelihood Explanation
`user_centric_signup` is a field the orb reads from data it validates as "authenticated app data," but the "authentication" only proves the *value came from the expected source's payload*, not that the app will subsequently and successfully complete its independent submission to the backend. Any interruption between the orb's local pipeline success and the app's completion of its own backend round trip (normal network conditions, app misbehavior, or a compromised/rogue companion app) will trigger this code path exactly as written, requiring no privileged access — only a normal signup flow reaching the `user_centric_signup = true` branch, which is the documented, supported path for "self-serve"/app-centric orbs.

### Recommendation
Do not assign `Success` to `enrollment_status`/`result.success` in the user-centric branch based solely on local `signup_reason`. Require an explicit backend or orb-relay confirmation (analogous to the `signup_poll` completion check in the non-user-centric path) that the app has actually submitted and the backend has actually accepted the signup before recording `enrollment_status(Success)` and incrementing success metrics. At minimum, gate the "Success" report on a positive acknowledgment channel (e.g., an orb-relay message from the app confirming backend acceptance) rather than purely on the orb's own local pipeline/fraud result.

### Proof of Concept
1. Configure/QR-provision a user-data payload where `user_centric_signup = true` in `orb_qr_link::UserData` (this is legitimately reachable in self-serve/app-centric deployments) `src/backend/user_status.rs:203-212`.
2. Complete a normal biometric capture and local pipeline so that `pipeline.is_some()` and local `detect_fraud` returns `false`, making `signup_reason == SignupReason::Normal` `src/plans/mod.rs:562-571`.
3. Prevent the companion app from ever completing its own submission to the backend (e.g., kill the app, disconnect network, or use a modified app that never calls the equivalent backend enrollment endpoint) after the orb-relay `AnnounceOrbId` handshake succeeds `src/plans/mod.rs:532-548`.
4. Observe that `do_signup` still executes the `user_centric_signup` branch, sets `debug_report.enrollment_status(enroll_user::Status::Success)`, calls `debug_report.signup_successful()`, increments `main.count.signup.result.success.successful_signup`, and returns `SignupResult { success: true, .. }` — despite no backend-side confirmation of a completed/deduplicated/fraud-checked enrollment ever occurring `src/plans/mod.rs:639-663`.

    fn report_signup_reason(
        success: bool,
        signup_reason: SignupReason,
        debug_report: &mut debug_report::Builder,
    ) {
        if signup_reason == SignupReason::Failure {
            tracing::info!("User enrollment failed due to a failure in the pipeline");
            debug_report.signup_orb_failure();
        } else if signup_reason == SignupReason::Fraud {
            tracing::info!("User enrollment failed due to fraud");
            debug_report.signup_fraud();

            dd_incr!("main.count.signup.result.success.successful_signup");
        } else {
            tracing::info!("User enrollment failed");
            debug_report.signup_server_failure();
        }
    }
