### Title
`convert_to_balance` truncates cross-chain amounts to zero/near-zero on decimal mismatch, permanently burning bridged funds - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s `convert_to_balance` helper, used by `on_accept`/`on_timeout` to convert an incoming EVM-denominated ERC20 amount into the pallet's local balance, performs an integer division that rounds down to zero for small amounts whenever the source ERC20 token has more decimals than the local asset. Because the EVM-side `HyperFungibleToken.send()` has already unconditionally burned/escrowed the sender's full amount before dispatch, a dust-sized transfer results in tokens irrecoverably destroyed on the source chain while the pallet mints/releases `0` on the destination.

### Finding Description
`convert_to_balance` scales an ERC20 `U256` value down to the local balance type by dividing by `10^(erc_decimals - local_decimals)`: [1](#0-0) 

This is invoked in `on_accept` (mint/release path) and `on_timeout` (refund path): [2](#0-1) 

For a realistic configuration such as `erc_decimals = 18` (the EVM `HyperFungibleToken` ERC20 default) and `local_decimals = 6` or `10` (a typical substrate asset), the divisor is `10^12` or `10^8`. Any incoming ERC20 amount smaller than that divisor computes to `0` after the division, and `U256::to_string().parse::<B>()` happily returns a zero balance rather than erroring.

The EVM side has no minimum-amount guard: `HyperFungibleToken.send()` burns the caller's exact `amount` and dispatches the message unconditionally — there is no `require`/`revert` on small amounts: [3](#0-2) 

The `Message.amount` (raw ERC20 units) is later abi-decoded and fed straight into `convert_to_balance` on the receiving pallet: [4](#0-3) 

So the sequence is: user calls `send()` on the EVM contract with a small `amount` (below the destination's decimal-scaling threshold) → EVM contract burns the full amount from the sender → ISMP dispatches the post request → destination pallet's `on_accept` decodes the message, computes `amount = 0` via `convert_to_balance`, and calls `NativeCurrency::transfer`/`Assets::mint_into` with `0`, which succeeds without any revert → the message is delivered successfully (`TokenReceived { amount: 0, .. }`), yet the sender's tokens that were burned on the source chain are never recovered.

The same rounding-to-zero risk applies on `on_timeout`'s refund path using the same helper, so a timed-out message for a dust amount also refunds `0` instead of the originally escrowed amount.

### Impact Explanation
Funds burned/escrowed on the source chain for a small-value transfer are permanently lost: nothing is minted/released on the destination, and the ISMP message still completes successfully (no revert, no retry path), so there is no recovery mechanism. This is a concrete, direct loss of user funds triggered purely by normal use of the `send()` extrinsic/contract call — no privileged actor is required, only a deployment where the registered `erc_decimals` and `local_decimals` for a token pair differ enough that a legitimate small transfer amount falls below the scaling divisor.

### Likelihood Explanation
Any dapp or user bridging a non-native, low-value, or dust amount through `HyperFungibleToken`/`WrappedHyperFungibleToken` into a chain where the local asset has materially fewer decimals than the registered `erc_decimals` (a normal, expected configuration difference — e.g. an 18-decimal EVM ERC20 bridged into a 6- or 10-decimal substrate asset) will trigger this. No malicious governance, admin, or relayer behavior is needed; it is a routine cross-chain send with an ordinary small amount, making the likelihood high for tokens/chains with this decimal profile.

### Recommendation
- Reject conversions that would round to zero: after computing the scaled amount in `convert_to_balance`, if the original `value` was nonzero but the result is `0`, return an error instead of silently succeeding, and propagate that error so `on_accept`/`on_timeout` reject/queue the message rather than completing with a zero-value transfer.
- Alternatively (or additionally), enforce a minimum transferable amount on the EVM `send()` path (and pallet `send()` extrinsic) equal to the smallest unit representable after decimal down-scaling for the configured destination, reverting the send before funds are burned/escrowed.
- Audit the `on_timeout` refund path with the same fix, since a truncated-to-zero refund has the identical fund-loss effect.

### Proof of Concept
1. Register a non-native asset with `Precisions::<T>::insert(asset_id, StateMachine::Evm(chain), 18)` (EVM token is 18-decimal) while the local asset (`T::Assets`) has `decimals() = 6`.
2. On the EVM side, a user calls `HyperFungibleToken.send({ amount: 500_000_000_000 /* 5e11, < 1e12 */, dest: <substrate chain>, ... })`. The contract burns `500_000_000_000` units from the sender and dispatches the ISMP POST.
3. On delivery, the pallet's `on_accept` runs `convert_to_balance(U256::from(500_000_000_000u128), 18, 6)`, which divides by `10^(18-6) = 10^12`, yielding `0`.
4. `Assets::mint_into(local_asset_id, &beneficiary, 0)` succeeds; `TokenReceived { amount: 0, .. }` is emitted. The sender's `500_000_000_000` (5e11) source-chain-denominated tokens are burned with no destination-side credit and no error is raised anywhere in the pipeline.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
