### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) headers are trusted for tenant identification without being covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` reads `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers, but `to_signable_string` — the value that `Utils::HmacValidator` actually verifies — is only the raw request body. `Registry.process` validates the HMAC and then forwards the header-derived `shop` value, unverified, to the app's webhook handler as the tenant identifier, exactly matching the "field acted on but not covered by the HMAC" bug class.

### Finding Description
`Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from HTTP headers that are never part of the signable string: [3](#0-2) 

`Registry.process` validates the HMAC (over the body only) and then unconditionally trusts `request.shop` — sourced from the untrusted header — as the tenant identity passed to the handler: [4](#0-3) 

The equality the gem is supposed to guarantee is: *"the shop whose secret validated this request" == "the shop the handler is told owns this event."* Because the HMAC only proves "a body byte-string was produced with this app's secret" and says nothing about which shop that body belongs to, an attacker who controls a shop that has the app installed can capture one of their own legitimately-signed webhook deliveries (valid `raw_body` + valid `hmac` for their own store) and replay it to the app's public webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header swapped to a victim shop's domain. HMAC validation still succeeds because the body and hmac are unchanged and headers aren't covered, but `WebhookMetadata#shop` now falsely asserts the victim shop's identity while `body` contains attacker-supplied content from their own store.

The gem's own documentation reinforces that this is exploitable-by-design confusion rather than a host-app misuse: it explicitly tells developers that `Registry.process` "will verify the request did indeed come from Shopify" and shows `data.shop` being used directly as the tenant key (`shop_domain: data.shop`) without any further verification step: [5](#0-4) [6](#0-5) 

### Impact Explanation
Any host application that follows the gem's documented pattern of keying per-tenant processing (data storage, job routing, state updates) off `data.shop` is exposed to cross-tenant data injection: an attacker who is themselves a legitimate merchant/app-installer (unprivileged internet user, no special credentials needed) can make the app apply attacker-controlled webhook body content under a victim shop's identity. Depending on the handler's logic (e.g., syncing order/customer/product records keyed by shop), this can corrupt or leak data across tenant boundaries — a cross-tenant access impact.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on an attacker-controlled shop (freely obtainable), (2) capturing one legitimately delivered webhook (raw body + HMAC header) for that shop, and (3) replaying it to the app's public webhook endpoint with the shop-domain header changed. No secret key, access token, or privileged account is needed — the gem itself never authenticates the header, only the body.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values in the HMAC-signable string (or otherwise cryptographically bind them to the body) so that `HmacValidator.validate` fails if any of these identity-bearing headers are altered independently of the signed body. At minimum, document loudly that `data.shop` is unauthenticated and must not be used as a tenant key without independent verification (e.g., cross-checking against an existing stored session for that shop before trusting the payload).

### Proof of Concept
1. Attacker creates/owns Shop A, installs the target app, and triggers a webhook (e.g., `orders/create`). Shopify sends a POST to the app's callback with `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: shop-a.myshopify.com`, and body `B` (attacker-influenced order data), where `H = HMAC(secret, B)`.
2. Attacker intercepts this exact request (e.g., via a local proxy since it's their own store), then re-sends `POST /callback/orders/create` to the app with the same body `B` and same `x-shopify-hmac-sha256: H`, but with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and compares to `H` — passes, since only the body is signed: [7](#0-6) 
4. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: B, ...)`, so the app processes attacker-supplied order data under the victim's tenant identity.

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
