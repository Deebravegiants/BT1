### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing tenant spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body. `Registry.process` trusts `request.shop` for tenant attribution after HMAC validation succeeds, even though that field was never part of the signed content.

### Finding Description
`Request#hmac` reads the signature from a header and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `Utils::HmacValidator.validate` verifies the HMAC purely against `to_signable_string`, i.e., the body: [2](#0-1) . `Registry.process` calls this validator and, if it passes, immediately trusts `request.shop` (sourced from the unauthenticated `shop-domain` header) to build `WebhookMetadata` passed to the app's handler: [3](#0-2) . The `shop` header is read independently of the signed payload: [4](#0-3) .

This breaks the intended identity binding: `HMAC-verified content == data trusted for tenant attribution`. In this gem, `HMAC-verified content == raw_body only`, while `data trusted for tenant attribution == shop-domain header`, which is disjoint from the signed bytes.

Because Shopify computes webhook HMACs using the app's single `client_secret` (shared across every shop that installs the app), any shop that has the app installed can generate a legitimately-signed `(raw_body, hmac)` pair for itself (e.g., by triggering a real event such as `orders/create`). An attacker who controls one installation of the target app can capture that valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still passes (it never inspected the header), and `Registry.process` dispatches the handler believing the event originated from the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: an attacker with access to one tenant's traffic can cause the application to process/attribute arbitrary attacker-controlled webhook payloads as if they came from a different, victim tenant. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up records, apply mutations, or trigger side effects keyed by shop), this can lead to cross-tenant data corruption or disclosure, matching the Critical "cross-tenant access" bucket.

### Likelihood Explanation
Medium: it requires the attacker to control (or install the target app on) at least one shop to legitimately mint a valid `(body, hmac)` pair, then send a raw HTTP request with a forged `shop-domain` header directly to the app's public webhook endpoint. No secrets, TLS interception, or privileged Shopify account access are needed beyond having any shop install the app — a capability normal external developers/merchants have.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) into the value that is cryptographically verified, or otherwise independently authenticate the shop domain — e.g., verify it against a stored, known set of shops that have valid sessions/access tokens for this app, rather than trusting the header purely because the body’s HMAC passed. At minimum, document that `WebhookMetadata#shop` is not authenticated by the HMAC and must be cross-checked against the app's own shop/session store before use.

### Proof of Concept
1. Install the target app on attacker-owned shop `attacker.myshopify.com`. Trigger a real webhook event (e.g., `orders/create`); Shopify sends a POST with body `B` and header `x-shopify-hmac-sha256: H` where `H = HMAC_SHA256(secret, B)`.
2. Capture this legitimate request `(B, H)`.
3. Replay the identical request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` re-computes `HMAC_SHA256(secret, B)` and it matches `H`, so validation succeeds [5](#0-4) .
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed_body, ...)`, even though the payload actually originated from the attacker's shop [6](#0-5) .
