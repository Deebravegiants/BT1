## Title
Duplicate `address(0)` rows in `erc20TokenAddresses` let a single `msg.value` satisfy two independent balance/`amountChanges` checks, minting shielded ETH without full backing - ([File: contracts/Hinkal.sol])

## Summary
`Hinkal.transact` snapshots `oldBalances`/`newBalances` once for the whole `erc20TokenAddresses` array and, for every index equal to `address(0)`, adds the single `msg.value` back into the per-row `balanceDif` formula (`newBalances[i] + msg.value - oldBalances[i]`). If two rows both hold `address(0)`, both rows independently compute `balanceDif == w` for the same `msg.value = w`, and `transferERC20TokenFromOrCheckETH` in `Transferer.sol` only checks `msg.value == _value` (never decrementing/consuming it), so both deposit legs pass with `amountChanges[i1] = amountChanges[i2] = w`, letting the circuit's public inputs claim `2w` of new shielded ETH value backed by only `w` wei received.

## Finding Description
The broken equality is: **total shielded ETH value credited across all output commitments == ETH actually received by the contract (`msg.value`)**.

Trace:
- `Hinkal.transact` (`contracts/Hinkal.sol:78-90`) takes `oldBalances`/`newBalances` snapshots via `getBalancesForArray`, which iterates `circomData.erc20TokenAddresses` and calls `getERC20OrETHBalance` per index. For `address(0)` this returns `address(this).balance`, the *same* value regardless of how many times `address(0)` appears in the array (since ETH already landed in the contract atomically with the call, before any code runs).
- `_internalTransact` (`contracts/Hinkal.sol:172-230`) loops over every index `i`; for each deposit leg (`deltaAmountChange > 0`) it calls `transferERC20TokenFromOrCheckETH(circomData.erc20TokenAddresses[i], externalAddress, address(this), amountChanges[i])`.
- `transferERC20TokenFromOrCheckETH` (`contracts/Transferer.sol:111-128`) for `address(0)` only does `require(msg.value == _value, ...)` and, since `_to == address(this)`, performs **no actual transfer**. Crucially `msg.value` is never consumed/decremented, so this check can pass repeatedly for multiple indices as long as each one's `amountChanges[i]` equals the same `msg.value`.
- Back in `transact`'s post-loop balance check (`contracts/Hinkal.sol:97-146`), for each `address(0)` row: `balanceDif = newBalances[i] + msg.value - oldBalances[i]`. Since no real ETH moved during `_internalTransact` for this deposit-to-self case, `newBalances[i] == oldBalances[i]` for every row, so `balanceDif == msg.value == w` for **every** `address(0)` row, not just one.
- The final `require(balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount, ...)` (internal-transact path has `utxoAmount == 0` since `utxoSet` is never populated when `externalActionId == 0`) reduces to `w == amountChanges[i]`. This holds independently and simultaneously for two distinct rows `i1` and `i2` both mapped to `address(0)`, each claiming `amountChanges = w`.
- `dimensionsCheck` and `checkOnchainCreation` in `contracts/HinkalHelper.sol:64-202` validate array *lengths* and the `onChainCreation`/`amountChanges` relationship, but **never check for duplicate token addresses** in `circomData.erc20TokenAddresses`. Nothing in `performHinkalChecks` rejects two rows both being `address(0)`.
- `amountChanges` is fed directly into the circuit's public input vector via `CircomDataBuilder.formInputForCircom`, and the circuit is expected to constrain `outTotal == inTotal + amountChanges[i]` per row/asset. Since the prover fully controls `circomData` (including which rows are `address(0)`) and can freely produce a proof with `amountChanges = [w, w]` across two rows for the same asset, the circuit-side per-row conservation constraint does not catch the double-counted deposit at the contract-accounting layer — the Solidity balance-diff check is what has actually failed here, independent of the circuit's own internal per-row bookkeeping.

Attacker's exact call: attacker deposits `w` wei via `Hinkal.transact`, submitting `circomData` where `erc20TokenAddresses = [address(0), ..., address(0), ...]` at two indices `i1, i2`, both with `onChainCreation[i1]=onChainCreation[i2]=false`, `amountChanges[i1]=amountChanges[i2]=w`, and out-commitments encoding `2w` of shielded ETH split across the two "asset rows" (both logically representing ETH). Existing guards (`performHinkalChecks`, `rootHashExists`, `verifyProof`, `insertNullifiers`, slippage checks) do not reference row-uniqueness of `erc20TokenAddresses`, so none of them block this.

## Impact Explanation
This mints `2w` of shielded ETH-denominated value for only `w` wei actually deposited into the contract — a direct instance of minting shielded value without backing, i.e., protocol insolvency where later legitimate shielded-ETH withdrawals cannot all be honored. This matches the **Critical** category ("minting shielded value without backing"). The attack is repeatable per transaction and scales with however many duplicate `address(0)` rows the attacker's chosen `dimensions.tokenNumber`/circuit allows.

## Likelihood Explanation
Preconditions are fully within attacker control: they choose `dimensions.tokenNumber` and `erc20TokenAddresses` content, generate their own valid Groth16 proof over these public inputs (they need only a circuit that permits >1 row for the same token address, which is not restricted anywhere in the Solidity layer), and pay `w` wei once. No privileged role, no relay collusion, and no reliance on other users' funds is required. The only real gate to feasibility is whether the deployed/verified circuit (out of scope: `contracts/verifiers/**`) actually permits the public-input vector to contain two rows referencing the same token address with independent positive `amountChanges` and still produce a valid proof — I was not able to fully inspect `circuits/MainEVMCircuit.circom`'s row-level constraints in this session to confirm whether the circuit itself enforces uniqueness of `erc20TokenAddresses` per row (this remains unverified due to time/tooling limits in this pass; a full check of `MainEVMCircum.circom` and any `OverflowPreventer`/`ForceEqualIfEnabled` uniqueness constraints would be needed to fully confirm the circuit does not already prevent duplicate-token rows).

## Recommendation
In `Hinkal.transact` / `dimensionsCheck`, explicitly reject duplicate entries in `circomData.erc20TokenAddresses` (e.g., require strictly increasing/sorted addresses, or an explicit uniqueness check) before performing the balance-diff and `amountChanges` reconciliation. Additionally, `transferERC20TokenFromOrCheckETH`'s `msg.value == _value` check should be replaced with a mechanism that tracks and consumes a running "remaining `msg.value`" total across all `address(0)` legs within one transaction, so a single `msg.value` cannot independently satisfy multiple deposit legs.

## Proof of Concept
Not fully verified in this pass — the described Hardhat fork PoC would need to: (1) confirm the deployed circuit accepts a public-input vector with `erc20TokenAddresses` containing `address(0)` at two indices with independent `amountChanges = [w, w]` and generate a valid Groth16 proof for it via snarkjs, (2) call `Hinkal.transact` sending exactly `w` wei, (3) assert both per-row `require`s in `transact`'s balance loop pass, (4) assert the two resulting shielded output UTXOs (each valued `w`) are both later spendable via a subsequent proof/nullifier, while `address(this).balance` only ever increased by `w`. This last step (confirming circuit acceptance of duplicate-row public inputs) could not be completed within this session's tool budget, so the finding's contract-level logic is confirmed but the end-to-end circuit-compatibility has not been empirically demonstrated here.     function _internalTransact(CircomData calldata circomData) private {
        bool hasPaidToRelay = false;
        for (uint64 i = 0; i < circomData.erc20TokenAddresses.length; i++) {
            int256 deltaAmountChange = _calculateDeltaAmount(circomData, i);

            if (deltaAmountChange > 0) {
                require(
                    circomData.externalActionData.externalAddress == msg.sender,
                    "Deposit should come from the sender"
                );
                transferERC20TokenFromOrCheckETH(
                    circomData.erc20TokenAddresses[i],
                    circomData.externalActionData.externalAddress,
                    address(this),
                    uint256(circomData.amountChanges[i])
                );
            } else {
                uint256 sumAbs = uint256(-deltaAmountChange);
                uint256 relayFee = 0;
                if (circomData.relay != address(0)) {
                    uint256 flatFee = circomData.feeStructure.feeToken ==
                        circomData.erc20TokenAddresses[i]
                        ? circomData.feeStructure.flatFee
                        : 0;

                    require(
                        sumAbs >= flatFee,
                        "Relay Fee is over withdraw amount"
                    );

                    uint256 recipientAmount = ((10000 -
                        circomData.feeStructure.variableRate) *
                        (sumAbs - flatFee)) / 10000;

                    relayFee = sumAbs - recipientAmount;

                    if (relayFee > 0) {
                        transferERC20TokenOrETH(
                            circomData.erc20TokenAddresses[i],
                            circomData.relay,
                            relayFee
                        );
                    }
                    hasPaidToRelay = true;
                }
                if (sumAbs - relayFee > 0) {
                    transferERC20TokenOrETH(
                        circomData.erc20TokenAddresses[i],
                        circomData.externalActionData.externalAddress,
                        sumAbs - relayFee
                    );
                }
            }
        }
        require(
            circomData.relay == address(0) || hasPaidToRelay,
            "relay not paid"
        );
    }

            require(

            if (_to != address(this)) {
