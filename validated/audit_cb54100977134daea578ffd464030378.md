### Title
Debt-value overflow during mandatory accrual permanently freezes a market - (File: common/src/rates/simulate.rs)

### Summary

**Severity: Medium.** A sufficiently large, highly utilized market can push `borrowed * borrow_index` beyond the `i128` range before the global borrow-index cap is reached, causing `accrue_step` to revert with `MathOverflow`. [1](#0-0)  Because interest accrual runs before every market mutation and the accrual timestamp is committed only after all chunks succeed, the market can no longer process withdrawals, repayments, borrows, liquidations, or index updates. [2](#0-1) [3](#0-2) 

### Finding Description

`Controller::supply` and `Controller::borrow` are reachable by an unprivileged caller with sufficient tokens and collateral. [4](#0-3)  Their pool mutations load the market through `synced_market`, which calls `interest::global_sync` before applying the requested operation. [3](#0-2) 

`global_sync` applies each elapsed accrual chunk through `accrue_step`. [5](#0-4)  Before calculating the next index, `accrue_step` materializes `borrowed * borrow_index` and `supplied * supply_index` through `scaled_to_original`. [6](#0-5)  `scaled_to_original` performs a checked `Ray` multiplication whose result must fit in `i128`; an unrepresentable result raises `MathOverflow`. [7](#0-6) [8](#0-7) 

The borrow index is capped only after calculating `old_index * interest_factor`, and the cap limits the index itself rather than the representable market value. [9](#0-8)  The configured index ceiling is `10^36` raw RAY units, while the safe index for a very large debt is lower because the debt-value result must remain below `i128::MAX`. [10](#0-9) 

After this state is reached, the failing chunk can never be skipped: `last_timestamp` is not advanced until every chunk completes. [11](#0-10)  Consequently, subsequent calls still attempt the same overflowing accrual and revert before any state transition that could reduce the scaled debt or supply. [12](#0-11) 

### Impact Explanation

All supplier and borrower funds in the affected market become permanently frozen because withdrawals and repayments must first execute the same overflowing accrual. [13](#0-12) [12](#0-11)  Liquidation cannot rescue the position because liquidation reaches pool repayment, withdrawal, or seizure paths that also sync the market first. [14](#0-13) [12](#0-11) 

Even the permissionless `update_indexes(caller, assets)` maintenance path cannot recover the market, because it delegates to pool index accrual after only authenticating the caller. [15](#0-14)  This satisfies permanent freezing of user funds and can also leave the market unable to resolve its debt normally.

### Likelihood Explanation

The attack requires an extraordinarily large position: for an 18-decimal asset, a one-billion-token deposit produces approximately `10^36` scaled shares at an index of one RAY, so debt near that scale overflows when the borrow index reaches roughly `170 * RAY`. [16](#0-15)  It also requires the market's configured caps and token supply to admit that exposure, sufficient collateral to open the borrow, and sustained high utilization to grow the index. [17](#0-16) 

The attacker sacrifices or risks substantial capital, so the most realistic occurrence may be an organically oversized whale market rather than a low-cost griefing attack. [18](#0-17)  The consequence is nevertheless permanent for every participant in the affected market once the numeric threshold is crossed.

### Recommendation

Enforce a market-value domain cap in addition to the global index cap. Before accrual, derive the maximum representable index from the current scaled totals, for example `floor(i128::MAX * RAY / borrowed)`, and clamp `new_borrow_index` at `min(MAX_BORROW_INDEX_RAY, max_representable_borrow_index)`; apply the equivalent cap to the supply index. [19](#0-18) 

At the derived cap, accrual should become a bounded no-interest state rather than panic, leaving `last_timestamp` able to advance and preserving repayment, withdrawal, and liquidation paths. [2](#0-1)  Add a regression test in which a large high-utilization market reaches the derived representable-value boundary before `MAX_BORROW_INDEX_RAY` and remains usable afterward.

### Proof of Concept

1. Assume hub asset `A` is a listed 18-decimal token whose configured caps admit `N = 1_000_000_000 * 10^18` base units, and hub asset `C` is listed as collateral.

2. An unprivileged attacker calls `Controller::supply(caller, 0, spoke_id, vec![(A, N), (C, required_collateral)])`, receiving account id `id`. [20](#0-19) 

3. The same attacker calls `Controller::borrow(caller, id, vec![(A, borrow_amount)], Some(caller))`, where `borrow_amount` creates approximately `9.8e35` scaled debt shares. [21](#0-20) 

4. While utilization remains high, anyone periodically calls `Controller::update_indexes(caller, vec![A])`; the controller delegates that list to pool accrual. [15](#0-14) 

5. Once the scaled debt approaches `9.8e35`, the safe borrow-index boundary is approximately `floor(i128::MAX * RAY / 9.8e35)`, or about `173.5 * RAY`; the next accrual evaluates `borrowed * borrow_index`, exceeds `i128::MAX`, and reverts. [6](#0-5) [7](#0-6) 

6. Because the failed accrual does not advance `last_timestamp`, every subsequent `update_indexes`, `withdraw`, `repay`, `borrow`, or `liquidate` attempts the same crossing chunk and reverts before its requested state change. [11](#0-10) [12](#0-11)

pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}

/// Applies one compound step of `delta_ms` to indexes and protocol revenue.

/// The arithmetic lives in [`accrue_step`], shared with the read-only
/// `simulate_update_indexes` so the view and the mutator cannot drift.

        env,
        cache.params(),
        cache.borrowed(),
        cache.supplied(),
        cache.borrow_index(),
        cache.supply_index(),
        delta_ms,
    );

/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Applies `interest_factor` to `old_index` to produce the new borrow index,
/// capped at `MAX_BORROW_INDEX_RAY`.
pub fn update_borrow_index(env: &Env, old_index: Ray, interest_factor: Ray) -> Ray {
    let new_index = old_index.mul(env, interest_factor);
    if new_index.raw() > MAX_BORROW_INDEX_RAY {
        return Ray::from(MAX_BORROW_INDEX_RAY);
    }
    new_index
}

/// Grows `old_index` by distributing `rewards_increase` over the total value
/// currently supplied (`supplied * old_index`). The division rounds down.
///
/// Returns `old_index` unchanged if `supplied` or `rewards_increase` is zero,
/// or if the total supplied value is zero. Clamps the result between
/// `old_index` (itself capped at `MAX_SUPPLY_INDEX_RAY`) and
/// `MAX_SUPPLY_INDEX_RAY`, so the returned index never decreases and never
/// exceeds the cap.
pub fn update_supply_index(env: &Env, supplied: Ray, old_index: Ray, rewards_increase: Ray) -> Ray {
    if supplied == Ray::ZERO || rewards_increase == Ray::ZERO {
        return old_index;
    }

    let total_supplied_value = supplied.mul(env, old_index);

    if total_supplied_value == Ray::ZERO {
        return old_index;
    }

    let new_value = total_supplied_value.checked_add(env, rewards_increase);
    let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());

    let bounded_old = old_index.raw().min(MAX_SUPPLY_INDEX_RAY);
    Ray::from(grown.min(MAX_SUPPLY_INDEX_RAY).max(bounded_old))
}
