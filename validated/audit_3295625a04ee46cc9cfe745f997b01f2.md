The `Registry.process` method dispatches to `handler.handle` with `shop: request.shop`, where `request.shop` comes directly from an HTTP header, and the only cryptographic check performed is `Utils::HmacValidator.validate(request)` which signs `request.to_signable_string` — defined as `@raw_body` only.### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values that the host app uses to route and process the event are taken from unauthenticated HTTP headers that are never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely via: [1](#0-0) 

which calls `Utils::HmacValidator.validate(request)`. That validator computes the signature over `request.to_signable_string`: [2](#0-1) 

and `Request#to_signable_string` is defined to be only the raw body bytes: [3](#0-2) 

However, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from HTTP headers, none of which are part of the signed string: [4](#0-3) 

`Registry.process` then passes `request.shop` straight into the `WebhookMetadata` struct that is handed to the app's `WebhookHandler#handle`, without any additional binding check between the verified body and the claimed shop: [1](#0-0) [5](#0-4) 

The identity binding that should hold is: `HMAC(secret, signed_bytes) == received_hmac` should imply `signed_bytes` authentically determines **every** field the app trusts, including `shop`. Instead the equality only covers `raw_body`, so:

`verified: raw_body` ≠ `acted_upon: {shop, topic, webhook_id, api_version, raw_body}`

Because a single app-wide `api_secret_key` (`Context.api_secret_key`) is shared across every shop that installs the app, any merchant who has installed the app on their own store can legitimately receive a validly-signed webhook (body + HMAC) for their own shop. That merchant can then replay the exact same `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header to claim it originated from a different, victim shop. `HmacValidator.validate` will still return `true`, because it only re-computes the HMAC over the raw body, which is unchanged and was genuinely signed by Shopify. The forged headers pass through untouched into the handler as `WebhookMetadata`.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged app user (any merchant who installed the app) can make the app process an event as if it belongs to a different tenant's shop, without needing that tenant's credentials, access token, or `client_secret`. Depending on how the host app's `WebhookHandler` uses `data.shop` (e.g., to look up/mutate per-shop state, to fulfill GDPR `customers/redact`/`shop/redact` mandatory webhooks, to invalidate sessions on `app/uninstalled`, or to update per-shop billing/subscription state), this can lead to cross-tenant data corruption, denial of service against another merchant (e.g., forging an `app/uninstalled` or redact event for a shop that never uninstalled), or state confusion between tenants — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires a normal, unprivileged relationship with the app: installing it on one's own store to receive at least one genuinely-signed webhook delivery, then replaying that body+HMAC pair with a forged shop-domain header via any HTTP client. No access token, `client_secret`, or `api_secret_key` is needed, and no special network position (TLS interception) is required since HTTP headers are fully attacker-controlled when crafting the replayed request. The main constraint is that the replayed body content must be plausible/acceptable to the target handler's business logic, which is trivial for topics with minimal/generic bodies such as `app/uninstalled`, `shop/redact`, `customers/redact`, or `customers/data_request`.

### Recommendation
Bind the shop (and other routing metadata) into the verified material instead of trusting bare headers:
- Include `shop-domain`, `topic`, and `webhook-id` in the HMAC-signed string (matching however Shopify computes it, or by additionally verifying these values against a table of expected values, e.g., cross-checking `shop-domain` against sessions/tokens known to the app for that specific webhook subscription).
- At minimum, document prominently that `WebhookHandler` implementations must not treat `data.shop` as authenticated on its own, and provide a stronger verification path (e.g., requiring hosts to correlate the webhook's `shop` against a previously registered/authorized shop record) before this metadata is used for any state-changing or tenant-scoping action.

### Proof of Concept
1. Attacker installs the app on `attacker.myshopify.com` and configures/receives a webhook (e.g., `app/uninstalled`, generic empty body `{}`), capturing the raw body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker crafts a new HTTP POST to the app's webhook endpoint with:
   - Same raw body bytes as captured.
   - Same `X-Shopify-Hmac-Sha256` header value as captured.
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (forged).
   - `X-Shopify-Topic` optionally forged if the topic string similarly isn't bound.
3. `ShopifyAPI::Webhooks::Registry.process` builds a `Request` from these headers/body and calls `Utils::HmacValidator.validate(request)`, per [6](#0-5) . Validation succeeds because `to_signable_string` is unchanged (still the original raw body).
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, per [7](#0-6) , causing the app to act on behalf of `victim-shop.myshopify.com` despite the event never having been sent by Shopify for that shop.
