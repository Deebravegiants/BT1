Audit Report

## Title
Node crash via nil pointer dereference in vault `GetPublicKey` gateway handler when `params` is null - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.handlePublicKeyGet` unmarshals `*req.Params` without checking for nil, unlike every other vault gateway method which is validated via `GatewayVaultRequestProcessor`'s per-method `req.Params == nil` checks before unmarshal. Sending a `vault_getPublicKey` JSON-RPC request with `params` omitted or `null` reaches this code path unauthenticated/unauthorized and dereferences a nil `*json.RawMessage`, causing a panic.

## Finding Description
In `HandleGatewayMessage`, `MethodSecretsCreate`/`Update`/`Delete`/`List` are routed through `h.requestProcessor.ProcessRequest`, whose handlers all explicitly guard `if req.Params == nil` before calling `json.Unmarshal(*req.Params, ...)` [7](#0-6) . `MethodPublicKeyGet`, however, is dispatched straight to `handlePublicKeyGet` [8](#0-7) , which unconditionally executes `json.Unmarshal(*req.Params, r)` with no nil check [3](#0-2) . If `req.Params` is `nil` (client omits or sends `null` for `params`), `*req.Params` panics with a nil pointer dereference before any authorization step runs.

The message is delivered from `gatewayConnector.readLoop`, which calls `handler.HandleGatewayMessage(ctx, ...)` in a dedicated per-gateway goroutine with no `recover()` wrapping the call [9](#0-8) . An unrecovered panic in that goroutine crashes the entire node process, since Go panics that aren't recovered terminate the whole program regardless of which goroutine they originate in.

## Impact Explanation
This is a denial-of-service against the node: a single malformed request crashes the node process (or at minimum permanently kills the gateway message-processing goroutine, since `readLoop` has no restart logic on panic and the `defer c.closeWait.Done()` would not save iteration). This matches "service unavailability or severe degradation under realistic attacker input," an in-scope Chainlink impact class for CRE/gateway node infrastructure. No confidentiality or integrity impact since the request is rejected pre-authorization and no secrets are exposed or mutated.

## Likelihood Explanation
High and trivially reproducible: no authentication, authorization, encryption key, or prior state is required. The `MethodPublicKeyGet` branch executes before `requestProcessor.ProcessRequest`/authorization is invoked for other methods, so any client able to reach the Gateway's vault endpoint (which forwards to node handlers) can trigger this with one crafted JSON-RPC request with `method: "vault_getPublicKey"` and no/`null` `params`.

## Recommendation
Add an explicit `if req.Params == nil { return h.errorResponse(ctx, gatewayID, req, api.UserMessageParseError, errors.New("request params must not be nil")) }` guard at the start of `handlePublicKeyGet`, mirroring the existing pattern in `processCreateSecretsRequest`/`processUpdateSecretsRequest`/`processDeleteSecretsRequest`/`processListSecretIdentifiersRequest`. Additionally, consider adding a `recover()` in `gatewayConnector.readLoop` (or in `HandleGatewayMessage` implementations generally) as defense-in-depth against future unchecked-dereference bugs in handler dispatch.

## Proof of Concept
1. Send a Gateway-forwarded JSON-RPC request that reaches `GatewayHandler.HandleGatewayMessage` on the node side with:
```json
{"jsonrpc":"2.0","id":"poc-1","method":"vault_getPublicKey"}
```
(`params` omitted, or `"params": null`.)
2. `HandleGatewayMessage` routes on `req.Method == vaulttypes.MethodPublicKeyGet` directly to `handlePublicKeyGet` [8](#0-7) .
3. `handlePublicKeyGet` executes `json.Unmarshal(*req.Params, r)` with `req.Params == nil`, panicking with a nil pointer dereference [10](#0-9) .
4. The panic propagates from the `readLoop` goroutine with no recovery, crashing the node process [9](#0-8) .

A Go unit test calling `GatewayHandler.HandleGatewayMessage` (or directly `handlePublicKeyGet`) with a `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` would deterministically reproduce the panic.

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
