### Title
Unbounded `Math.mulDiv` division in `_noFeeSwapInput` can revert on a hostile pre-seed, permanently bricking `finalizeGraduation` - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._noFeeSwapInput`, the closed-form rebalance-swap solver used by the hostile-mint-pre-seed defense in `finalizeGraduation`, computes `Math.mulDiv(reserveIn * reserveOut, targetN, targetD)` and takes its `sqrt`. `reserveIn`/`reserveOut` come directly from the attacker-influenceable HyperSwap V2 pair's live reserves, while `targetN`/`targetD` are the graduation's cached `tokensForLP`/`ltFromPair`. The function's own natspec acknowledges that if the final `.../targetD` result doesn't fit in `uint256`, `Math.mulDiv` reverts — and this is exactly the failure mode that occurs when a griefer front-runs a token whose graduation produces a very small `tokensForLP` or `ltFromPair` denominator and pre-seeds the HyperSwap pair with disproportionately large reserves on the numerator side. That revert propagates out of `_pairRebalance` → `_seedRebalancing` → `_seedUniswapV2Direct` → `finalizeGraduation`, which the project's own documentation states MUST NEVER revert under any pre-seed shape.

and passed straight into `_pairRebalance`/`_noFeeSwapInput` together with `targetN`/`targetD` set to `ltFromPair`/`tokensForLP` (or their inverse), with no upper bound relative to the reserves and no defensive `try/catch`: [4](#0-3) 

The project's own overflow-safety test explicitly documents that only "realistic" ranges (reserves ≤ `uint112.max`, targets ≤ `TOTAL_SUPPLY`, and only when `targetD` is picked large enough) are verified not to revert; it does not assert that *every* combination of live pool reserves and small graduation targets stays inside the safe envelope: [5](#0-4) 

Because the HyperSwap pair is permissionlessly creatable and mintable before `finalizeGraduation` runs (the documented "hostile mint pre-seed" attack surface — `AGENTS.md`'s three-regime defense exists precisely because of this), an attacker fully controls `reserveIn`/`reserveOut`, while `tokensForLP`/`ltFromPair` (the denominator in one of the two rebalance directions) can be made arbitrarily small by targeting a token whose graduation trips with a tiny curve raise (e.g. graduating almost immediately via the supply trigger with a very low LT exchange rate, so `ltFromPair` is dust, or via a curve that leaves `tokensForLP` near zero). Driving `reserveIn * reserveOut * targetN` far above `type(uint256).max * targetD` forces `Math.mulDiv` to revert unconditionally on every future call, with no fallback path — unlike the `s == 0` / `getAmountOut == 0` cases, which are deliberately caught and routed to `_seedDirectMint`, this overflow-revert has no catch.

### Impact Explanation
`finalizeGraduation` is the sole entry point that can move a token from `Lifecycle.Graduating` to `Lifecycle.Graduated`, mint the HyperSwap LP, and call `LPLock.recordLock`. If `_noFeeSwapInput` reverts unconditionally for a given token's cached `(tokensForLP, ltFromPair)` against the attacker's chosen pre-seed reserves, every subsequent call to `finalizeGraduation(token)` reverts identically (the pre-seed reserves and the cached graduation targets are both durable state), permanently bricking that token: trading stays frozen (`Lifecycle.Graduating`), the curve-raised LT (`ltFromPair`, drained from the pair into `Bonding` at phase 1) and the 250M `LP_RESERVE` tokens earmarked for LP remain stuck in `Bonding` forever, and no LP is ever locked. This is a permanent freezing of trader/creator/LP funds, directly matching the required impact bar, and mirrors the external report's DoS-via-overflow bug class.

### Likelihood Explanation
The attack requires only unprivileged, permissionless actions already explicitly acknowledged as reachable by the codebase's own threat model: creating the HyperSwap V2 pair via `factory.createPair`, transferring TOKEN/LT into it, and calling `pair.mint(attacker)` before `finalizeGraduation` runs — the same "Regime 3" mint pre-seed the existing defense is built to handle. The only added requirement versus the already-documented attack is picking a target token/timing where the cached `tokensForLP` or `ltFromPair` is small relative to the attacker's affordable pre-seed reserves, which is plausible for low-value or fast-graduating launches. This is a real gap in test coverage: the fuzz/stress tests for `_noFeeSwapInput` only probe "realistic" bounded inputs and do not fuzz the case of a small target denominator against large live V2 reserves, so the brick-resistance property is not actually proven for this input shape despite the natspec's confident framing.

### Recommendation
Bound the call so it can never revert regardless of caller-supplied reserves/targets: either (a) wrap the `Math.mulDiv`/`sqrt` computation in `_pairRebalance` in a low-level `try/catch`-equivalent (e.g. a staticcall to an external `mulDiv` helper, since internal reverts can't be caught directly) and treat failure the same as `s == 0` (fall back to `_seedDirectMint`), or (b) pre-clamp `reserveIn`/`reserveOut` fed into `_noFeeSwapInput` to a value that provably keeps `reserveIn * reserveOut * targetN / targetD` inside `uint256` for the smallest possible `targetD` the protocol can produce, falling back to the direct-mint path whenever the clamp would bind. Add fuzz coverage that pairs `uint112`-max-scale reserves against dust-scale `tokensForLP`/`ltFromPair` denominators to close this gap in `test/NoFeeSwapInput.t.sol`.

### Proof of Concept
1. Launch a token and drive it to graduation such that the cached `pendingGraduation[token]` has a very small `ltFromPair` (or `tokensForLP`) — achievable by graduating via the supply trigger with a low LT `exchangeRate`, minimizing the real LT raised, similar to the existing `test_hostilePreSeed_ltRichDust_opensAtCachedRatio` setup in `test/TwoPhaseGraduation.t.sol` but pushed to an extreme ratio instead of a dust-swap-skip case.
2. Before calling `finalizeGraduation`, front-run: `factory.createPair(token, lt)`, then `transfer` large TOKEN and LT balances into the pair at a ratio that keeps `reserveToken * ltFromPair` far from `reserveLT * tokensForLP` (so the rebalance branch, not the direct-mint fallback, is taken), sized so `reserveIn * reserveOut * targetN` exceeds `type(uint256).max * targetD`.
3. Call `bonding.finalizeGraduation(token)`. The internal `_noFeeSwapInput` call inside `_pairRebalance` reverts via `Math.mulDiv`'s internal overflow check, and this repeats on every subsequent call, leaving the token stuck in `Lifecycle.Graduating` indefinitely.

    function _noFeeSwapInput(
        uint256 reserveIn,
        uint256 reserveOut,
        uint256 targetN,
        uint256 targetD,
        uint256 maxSwap
    ) internal pure returns (uint256) {
        if (reserveIn == 0 || reserveOut == 0 || targetN == 0 || targetD == 0 || maxSwap == 0) {
            return 0;
        }
        uint256 product = Math.mulDiv(reserveIn * reserveOut, targetN, targetD);
        uint256 newIn = Math.sqrt(product);
        if (newIn <= reserveIn) return 0;
        uint256 s = newIn - reserveIn;
        return s > maxSwap ? maxSwap : s;
    }
