### Title
Unprivileged bandwidth purchases can grief-evict a victim app's paid subscription, blocking message delivery - (File: modules/pallets/bandwidth/src/lib.rs)

### Summary
`pallet-bandwidth` stores each `(app_chain, app)` allowance as a FIFO `BoundedVec<Subscription, MaxSubscriptions>` capped at 1024 entries. Any unprivileged caller can invoke `BandwidthManager.purchase()` on any source chain and target *any* `(app_chain, app)` pair, since the pallet keys the `Allowance` map by the payload's `app_chain`/`app` fields rather than by the caller's own identity. Pushing beyond the 1024-entry cap silently evicts the oldest subscription. An attacker can therefore pay to append enough throwaway subscriptions to a victim app's bucket to push the victim's own paid, still-live subscription out of the FIFO window, causing the `BandwidthGate` to reject the victim's subsequent messages.

### Finding Description
`push_subscription` implements the eviction: [1](#0-0) 

The cap and eviction semantics are also documented at the module and doc level: [2](#0-1) [3](#0-2) 

Crucially, the allowance is keyed by `app_chain`/`app` taken from the *purchase message payload*, not from `request.source`/the payer's identity — this is the documented "sponsorship" feature that lets anyone credit bandwidth for any app on any chain: [4](#0-3) 

This is functionally identical in structure to the ParaSpace bug: a balance/queue limit enforced per-identity (there, `NToken.balanceOf`; here, the 1024-entry FIFO per `(chain, app)`) that any unprivileged party can push objects into on behalf of a victim, without the victim's consent, to force out something the victim already legitimately holds. In ParaSpace, the attacker filled a victim's NFT balance slots with worthless (zero-liquidity) NFTs to block the victim from adding real collateral, right before liquidating them. Here, an attacker fills a victim app's subscription-list slots with fresh, minimal-tier subscriptions to evict the victim's actual paid, live subscription (`Allowance::mutate` removes index 0, the oldest, unconditionally once the list is full): [5](#0-4) 

Because eviction always removes the current head/oldest entry, an attacker who observes a victim app has just one (or few) live subscription(s) can guarantee its eviction deterministically: submit enough `purchase()` calls (up to `MAX_SUBSCRIPTIONS = 1024` minus the victim's current count) to fill the list, then one more push evicts the victim's entry — confirmed by the pallet's own test: [6](#0-5) 

Once evicted, the gate treats the app as unfunded and rejects its inbound requests: [7](#0-6) 

### Impact Explanation
A successful eviction forces `BandwidthGate::try_consume` into `GateError::NoAllowance` for the victim's future dispatches, i.e. "a route unable to deliver messages" for that app until it notices and re-purchases — one of the explicitly recognized high-impact categories for this program. The victim also permanently loses the unused, already-paid-for bytes of the evicted subscription (`SubscriptionEvicted { lost_bytes }`), a direct loss of paid-for service. Any app relying on the bandwidth gate (rather than the allowlist bypass) is a potential target, and the attacker needs no privileges beyond being a "bandwidth purchaser" — an explicitly in-scope, unprivileged role for this review.

### Likelihood Explanation
The attack is not free (each of the up to 1024 pushes requires paying the cheapest tier's price via `BandwidthManager.purchase()`), so it is not as trivially cheap as the ParaSpace zero-liquidity-NFT case, but it is fully deterministic, bounded in cost, and requires no special access — anyone can compute the exact number of purchases needed to overflow a target's list (`1024 - current_len + 1`) and drive an eviction on demand. The pallet's own doc comments acknowledge this only "in practice ... happens under pathological repeat-buy behavior," implying the eviction path is known but assumed benign under honest usage; it was not evaluated against a deliberate, paid griefing/DoS actor targeting a specific victim app, which is a realistic threat model for a shared, permissionless metering primitive.

### Recommendation
- Do not let an unrelated payer's purchase evict subscriptions purchased by (or attributable to) a different payer for the same `(app_chain, app)` — e.g., separate "self-funded" and "sponsored" sub-queues, or require the evicting purchase to be sized/authorized against the specific subscription being displaced.
- Alternatively, raise `MAX_SUBSCRIPTIONS` cost-effectively out of reach relative to realistic tier pricing, or rate/size-limit unsolicited sponsorship pushes per source per unit time, and/or refuse to evict subscriptions that still have significant remaining bytes/duration unless the pushing purchase itself pays for at least the same amount evicted, removing the free "displacement" externality.
- Emit `SubscriptionEvicted` alerts prominently enough that app operators can react before their entire bandwidth allowance is drained, and consider a minimum-remaining-bytes protection so a single victim purchase cannot be evicted en masse cheaply relative to what it originally paid.

### Proof of Concept
1. Victim app `V` (`app_chain = EVM-8453`, `app = V_ADDR`) buys one subscription via `BandwidthManager.purchase()`, landing as the sole entry in `Allowance(EVM-8453, V_ADDR)`.
2. Attacker repeatedly calls `BandwidthManager.purchase()` on any registered source chain, setting the purchase payload's `chain = EVM-8453` and `app = V_ADDR` (both attacker-controlled, per the sponsorship design) with the cheapest configured tier and `months = 1`, `1024` times.
3. Each purchase decodes and calls `push_subscription`, and once `Allowance(EVM-8453, V_ADDR).len() == MAX_SUBSCRIPTIONS`, the next push evicts index `0` — the victim's original subscription — emitting `SubscriptionEvicted` (pallet test `subscription_cap_evicts_oldest` demonstrates this exact FIFO-eviction mechanics using `force_credit`, which shares the same `push_subscription` path as `purchase`): [6](#0-5) 
4. `V`'s next dispatch through the ISMP router calls `BandwidthGate::try_consume(EVM-8453, V_ADDR, bytes)`, which now sees zero live subscriptions and returns `GateError::NoAllowance`, rejecting the message despite `V` having paid for bandwidth that was never exhausted.

//! # pallet-bandwidth
//!
//! Prepaid `(chain, app)` byte balances credited by tier purchases
//! from `BandwidthManager.sol`. Each purchase carries its own
//! `app_chain`, so any deployment can sponsor any app on any chain.
//!
//! Each `(chain, app)` row holds a FIFO list of [`Subscription`]s
//! (`BoundedVec`, capped at 1024). Every purchase appends a new
//! subscription with a fixed `expires_at`; expiry never extends and
//! same-tier repurchases don't stack — they queue. The gate drains
//! the oldest live subscription first; once empty it moves to the
//! next. Subscriptions that aren't reached before their expiry are
//! swept silently — what you paid for is yours only until it expires.
//! Pushes onto a full list evict the oldest entry and emit
//! [`Event::SubscriptionEvicted`].

		/// Append a fresh subscription with a fixed expiry. If the list
		/// is already at `MaxSubscriptions`, evict the oldest entry and
		/// emit [`Event::SubscriptionEvicted`] so the lost bytes are
		/// auditable. Returns the new subscription's `expires_at`.
		fn push_subscription(
			app_chain: &StateMachine,
			app: &AppKey,
			tier: TierIndex,
			bytes: BandwidthBytes,
			duration_secs: u64,
		) -> u64 {
			let now = <T as pallet_ismp::Config>::TimestampProvider::now().as_secs();
			let expires_at = now.saturating_add(duration_secs);
			let new_sub =
				Subscription { tier, remaining_bytes: bytes, expires_at, purchased_at: now };

			let evicted = Allowance::<T>::mutate(app_chain, app, |list| {
				let evicted = if list.len() == MAX_SUBSCRIPTIONS as usize {
					Some(list.remove(0))
				} else {
					None
				};
				// Capacity is now guaranteed; try_push can't fail.
				let _ = list.try_push(new_sub);
				evicted
			});

			if let Some(old) = evicted {
				Self::deposit_event(Event::SubscriptionEvicted {
					app_chain: *app_chain,
					app: app.clone(),
					tier: old.tier,
					lost_bytes: old.remaining_bytes,
				});
			}

			expires_at
		}

```text
## The Gate

Every non-purchase POST request from a registered source chain runs through `BandwidthGate::try_consume(source, app, bytes)`:

1. If the app is on the **allowlist** for that source, return `Ok` without touching the ledger.
2. Sweep expired subscriptions in place.
3. If no live subscriptions remain → `GateError::NoAllowance`.
4. Sum `remaining_bytes` across live entries. If the sum is short → `GateError::Insufficient { remaining, required }`. **No mutation happens in this case** — the caller can retry after a top-up.
5. Otherwise drain from the head until the requested bytes are satisfied. Pop entries that hit zero. Emit `BandwidthConsumed` with the post-deduct remaining.

The "no mutation on insufficient" property is load-bearing: it means a top-up race is safe — if a message arrives between when an app notices it's short and when the top-up lands, the message stays rejectable rather than half-consuming the subscription.

### Purchase messages skip the gate

The router uses `Pallet::is_purchase_message(request)` to identify a purchase from a registered manager (`request.source` is managed _and_ `request.from` matches the registered manager address). Purchase messages bypass the gate — otherwise a depleted app couldn't ever recharge.

## Sponsorship

The purchase message carries its own `chain` (the _credit chain_) which is **independent of the source chain** that sent the message. This means a buyer on Ethereum can credit an app on Base by dispatching a purchase whose payload sets `chain = "EVM-8453"`.

The pallet keys allowance storage by `(app_chain, app)` taken from the message body, not by `request.source`. The event `BandwidthCredited` carries both — `app_chain` (where the credit lands) and `paid_from` (where the payment came from) — so the cross-chain payer is auditable.

This is what makes the system multi-tenant friendly: a treasury on a single chain can sponsor bandwidth for an app deployed across many chains, without having to deploy `BandwidthManager` on each chain the app lives on.
```

/// The 1024-sub cap evicts the oldest entry. force_credit reuses the
/// same push path as purchase, so this also covers the purchase cap.
#[test]
fn subscription_cap_evicts_oldest() {
	new_test_ext().execute_with(|| {
		jump_to(T0);
		let cap = MAX_SUBSCRIPTIONS as u128;

		// Fill the list to exactly the cap. `bytes` encodes the index
		// so we can prove which one got evicted.
		for i in 0..cap {
			Bandwidth::force_credit(
				RuntimeOrigin::root(),
				ForceCreditParams {
					app_chain: APP_CHAIN,
					app: app_key(),
					tier: TIER1,
					bytes: i + 1,
					duration_secs: MONTH_SECS,
				},
			)
			.unwrap();
		}
		assert_eq!(sub_count(APP_CHAIN), cap as usize);
		assert_eq!(sub_at(APP_CHAIN, 0).unwrap().remaining_bytes, 1, "oldest is index 1");

		// One more push: evicts the oldest, appends the new one.
		Bandwidth::force_credit(
			RuntimeOrigin::root(),
			ForceCreditParams {
				app_chain: APP_CHAIN,
				app: app_key(),
				tier: TIER1,
				bytes: cap + 1,
				duration_secs: MONTH_SECS,
			},
		)
		.unwrap();

		assert_eq!(sub_count(APP_CHAIN), cap as usize, "still capped");
		assert_eq!(
			sub_at(APP_CHAIN, 0).unwrap().remaining_bytes,
			2,
			"former second-oldest is now front",
		);
		assert_eq!(
			sub_at(APP_CHAIN, (cap - 1) as usize).unwrap().remaining_bytes,
			cap + 1,
			"new sub is at the back",
		);
	});
}
