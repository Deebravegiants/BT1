### Title
`ExternalActionSwap.swap` lets attacker drain arbitrary stray ERC20 balances of `LifiExternalAction` by setting `feeStructure.feeToken` to a token outside the swap pair - ([File: contracts/external-actions/swaps/ExternalActionSwap.sol])

### Summary
`swap()` never validates that `circomData.feeStructure.feeToken` equals `inputToken` or `outputToken`, and never bounds `flatFee`. When `feeToken` is a third, unrelated token, `sendToRelay(circomData.relay, relayFee, circomData.feeStructure.feeToken)` pays the flat fee straight out of `LifiExternalAction`'s pre-existing balance of that token instead of out of the swap's own proceeds, and this transfer is completely invisible to `Hinkal.sol`'s post-call balance/slippage accounting because that accounting only iterates `circomData.erc20TokenAddresses` (the input/output pair).

### Finding Description
Equality that should hold: *every unit of value leaving `LifiExternalAction` in a `transact` call is either (a) accounted for in `circomData.erc20TokenAddresses`/`amountChanges`/`utxoSet` and checked by the `balanceDif == amountChanges[i] + utxoAmount` invariant in `Hinkal.transact`, or (b) legitimately sourced from the value the attacker just deposited/received in that same call.* This equality is broken.

In `swap()`:
```
if (inputToken == circomData.feeStructure.feeToken) {
    inputAmount -= circomData.feeStructure.flatFee;
}
...
if (circomData.feeStructure.feeToken == outputToken) {
    sendToRelay(circomData.relay, relayFee + hinkalFee, outputToken);
} else {
    sendToRelay(circomData.relay, relayFee, circomData.feeStructure.feeToken);
    sendToRelay(circomData.relay, hinkalFee, outputToken);
}
``` [1](#0-0) 

Neither `feeToken` nor `flatFee` is constrained relative to `inputToken`/`outputToken` anywhere in this function, in `HinkalHelper.dimensionsCheck`, or in the circuit-side checks reachable for a swap (`feeStructure` is only hashed into `calldataHash`, not semantically constrained). When the attacker sets `feeToken` to neither `inputToken` nor `outputToken`:
- `inputAmount` is NOT reduced by `flatFee` (full attacker input is swapped).
- `sendToRelay(relay, flatFee, feeToken)` pulls `flatFee` of `feeToken` from `LifiExternalAction`'s existing balance — a balance that was not created by this transaction (it comes from prior dust/rounding residue left by earlier swaps through the shared contract, e.g. LI.FI router slippage/leftover approvals, or any other token dust sitting on the contract).
- `Hinkal.transact`'s balance-equality loop (`contracts/Hinkal.sol`, lines 97-147) only checks `circomData.erc20TokenAddresses`, i.e. `[inputToken, outputToken]`; `feeToken` is a third address that never appears there, so the depletion of the shared/stray balance is never validated against any `amountChanges`/`slippageValues`/`utxoSet` entry. [2](#0-1) 

Attacker's exact call: submit `Hinkal.transact` (via any cooperating/whitelisted relay, who is paid normally and has no reason to refuse) with a valid proof for a `LifiExternalAction` swap whose `circomData.feeStructure.feeToken` is a token distinct from both `erc20TokenAddresses[0]` and `[1]`, and `flatFee` set to (up to) the observed on-chain balance of that token held by `LifiExternalAction`. The result: attacker's real input is fully swapped, attacker receives `swappedAmount - hinkalFee` (paying nothing toward `flatFee`), while the relay is paid `flatFee` sourced entirely from the contract's stray balance of an arbitrary third token — silently drained with no revert and no accounting trail.

### Impact Explanation
This is theft of protocol/relay-adjacent funds: value sitting in the shared `LifiExternalAction` contract (accumulated dust from unrelated prior swaps, or any token balance the contract happens to hold) is transferred out to satisfy an individual attacker's fee obligation, at zero cost to the attacker. This matches the High severity category "theft ... of protocol/relay fees," since the flat fee that should be funded by the attacker's own swap proceeds is instead funded by stray balances belonging to the contract/pool. The attack is repeatable for every unit of stray balance the contract accumulates in any ERC20 token, across every attacker who discovers dust before it's swept.

### Likelihood Explanation
Preconditions: (1) `LifiExternalAction` holds a nonzero balance of some ERC20 token not used as the swap's `inputToken`/`outputToken` — plausible given real-world DEX aggregator dust/rounding, and (2) a relay willing to submit the transaction, which requires no collusion since the relay is paid normally. `feeToken` and `flatFee` are entirely attacker-controlled with no on-chain bound, and reachable balances are queryable on-chain, so an attacker can precisely target the drainable amount. This is a low-cost, fully reachable, unprivileged path (only requires generating a valid proof for the attacker's own real UTXO spend and choosing calldata fields).

### Recommendation
In `ExternalActionSwap.swap`, require `circomData.feeStructure.feeToken == inputToken || circomData.feeStructure.feeToken == outputToken` (revert otherwise), and ensure any `flatFee` paid is provably sourced from `inputAmount`/`swappedAmount` computed in that same call (i.e., bound `flatFee` such that it can never exceed value generated within the transaction). Additionally, extend `Hinkal.transact`'s balance-diff accounting (or add an explicit check in the external action) to cover `feeStructure.feeToken` even when it lies outside `erc20TokenAddresses`, so no token balance change escapes the invariant check.

### Proof of Concept
Foundry test plan:
1. Deploy `LifiExternalAction` with a mock router; pre-seed the action contract with a residual balance of `TokenC` (simulating dust), e.g. `TokenC.mint(address(lifiAction), 1000e18)`.
2. Register a whitelisted relay and craft a valid `CircomData`/proof for a swap `TokenA -> TokenB` where `feeStructure.feeToken = address(TokenC)` and `feeStructure.flatFee = 1000e18` (or any nonzero value ≤ residual).
3. Call `Hinkal.transact(...)` as the whitelisted relay (`tx.origin == relay`).
4. Assert: `TokenC.balanceOf(address(lifiAction))` decreases by exactly `flatFee`, while none of the attacker's transferred/deposited tokens were `TokenC`; assert attacker's UTXO output equals `swappedAmount - hinkalFee` (i.e., attacker paid $0 of `flatFee`); assert this succeeds without any revert from `Hinkal.transact`'s balance-diff checks (proving `TokenC`'s depletion was never validated).
