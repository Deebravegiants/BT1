### Title
Webhook `shop-domain` header is trusted without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, but the `shop` (and `topic`/`webhook_id`) values that the library hands to the host application's webhook handler are read from unauthenticated HTTP headers. `HmacValidator.validate` only proves that the *body bytes* were signed with the app's secret; it proves nothing about which shop the signed body belongs to. This breaks the identity binding: `hmac_valid(body) == true` should imply `shop == the shop that produced this event`, but the gem allows `shop` to be swapped independently of the signed payload.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all parsed straight from HTTP headers, none of which participate in the signable string: [2](#0-1) 

`HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` header value: [3](#0-2) 

`Registry.process` gates on `HmacValidator.validate(request)` and then forwards `request.shop` (an unauthenticated header) directly to the app's handler as the tenant identifier: [4](#0-3) 

Because the signature covers only the JSON body, any request whose body+HMAC pair was legitimately produced by Shopify for **shop A** can be replayed to the same endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header changed to **shop B**. `HmacValidator.validate` still returns `true` (the body bytes and secret are unchanged), and `Registry.process` calls the handler with `data.shop == "shop B"`, `data.topic` and `data.webhook_id` also attacker-controlled from headers.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem lets an unprivileged actor decouple the cryptographically-verified body from the shop it is attributed to. A realistic path to a valid (body, HMAC) pair requiring no leaked secret: install the target public/embedded app on an attacker-controlled development store, and any webhook Shopify sends to that store (e.g. `app/uninstalled`, `customers/data_request`, `orders/create`) is a genuine Shopify-signed payload where the attacker fully controls the JSON body content (their own shop's data) and possesses a valid HMAC for it. Replaying that exact body+HMAC to the same webhook endpoint with the `shop-domain` header rewritten to a victim shop causes the host application (which trusts `WebhookMetadata#shop` because `HmacValidator.validate` passed) to process attacker-supplied data as if it originated from the victim's shop — e.g. injecting fabricated `orders/create` data attributed to another merchant, or triggering `app/uninstalled` cleanup logic for a shop that never uninstalled. This is a cross-tenant data/action integrity break stemming directly from this gem's `Webhooks::Request`/`HmacValidator` design, not from the host app ignoring documented behavior — the gem itself computes the signature over body-only and exposes `shop` as if it were verified.

### Likelihood Explanation
Reaching a valid signed payload requires only installing the target app on a store the attacker controls (a normal, unprivileged action available to anyone, since most Shopify apps can be installed on a free development store), then replaying the captured POST with a modified header — no access token, `api_secret_key`, or privileged account is needed. The webhook endpoint is a public HTTP endpoint by design.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook_id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the signed payload before it's handed to `WebhookMetadata`. Short of that, the gem's documentation/API should make explicit that `shop` returned by `Webhooks::Request` is unauthenticated and must be independently verified by the host application against its own shop/session record before being trusted for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (their own store). Shopify sends a legitimate webhook, e.g.:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of raw_body over api_secret_key>
x-shopify-shop-domain: attacker-shop.myshopify.com
Body: {"id": 1, "note": "malicious content", ...}
```
2. Attacker captures this exact `raw_body` and its valid `x-shopify-hmac-sha256` value (both are visible to them since it's their own store/app instance).
3. Attacker replays the identical request but rewrites the header:
```
x-shopify-shop-domain: victim-shop.myshopify.com
```
(all other bytes, including the HMAC value, unchanged).
4. `HmacValidator.validate` in [5](#0-4)  succeeds because it only re-hashes `@raw_body`.
5. `Registry.process` in [4](#0-3)  invokes the host handler with `shop: "victim-shop.myshopify.com"`, causing the attacker-authored body to be processed under the victim tenant's identity.

          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
