Audit Report

## Title
Outbound HTTP header denylist bypass via underscore/hyphen header-name conflation - ([File: core/services/gateway/network/httpclient.go])

## Summary
The gateway's outbound HTTP client blocks trust-sensitive headers (`Host`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Real-IP`, `Content-Length`, `Transfer-Encoding`, etc.) via `defaultBlockedHeaders`, but `validateHeaderNames` only lower-cases header names before an exact map lookup, never normalizing `_` vs `-`. An unprivileged workflow author submitting an `OutboundHTTPRequest` through the HTTP Action capability can bypass the denylist entirely by substituting underscores for hyphens (e.g. `X_Forwarded_For`), since the header is passed through unmodified into `http.Header.Add`, which canonicalizes case but does not fold underscores to hyphens.

## Finding Description
`defaultBlockedHeaders` documents an explicit intent to block IP/host/protocol-spoofing headers: [1](#0-0) 

`validateHeaderNames` enforces this list with only a `strings.ToLower` case fold, and no underscore/hyphen normalization, before doing an exact map lookup: [2](#0-1) 

This validation runs unconditionally in `Send` before the header is attached to the outbound `http.Request` via `Header.Add`, which canonicalizes case only, not underscore/hyphen form: [3](#0-2) [4](#0-3) 

The header values originate from an `OutboundHTTPRequest` sent by a workflow node through the gateway's HTTP Action handling path and are forwarded into `network.HTTPRequest.Headers`/`MultiHeaders` verbatim, with no additional header-name sanitization performed anywhere in `makeOutgoingRequest`: [5](#0-4) 

Because the check is a case-only exact string match, submitting `X_Forwarded_For` (or `Content_Length`, `Transfer_Encoding`, etc.) evades `blockedSet` lookup even though many HTTP-adjacent stacks (CGI-style header-to-env-var translation, and the class of bug documented in the referenced Django ASGI advisory) treat underscore and hyphen forms of a header name as equivalent. The denylist's stated purpose — preventing IP/host/protocol spoofing — is defeated for any downstream target exhibiting this conflation behavior.

## Impact Explanation
This is a genuine gap in the denylist logic that the code's own comments identify as security-critical (`// prevents IP spoofing`, `// prevents host header spoofing`, etc.), and it maps to the "gateway request impersonation" impact category: a workflow author can smuggle a header the gateway explicitly intends to block past validation. The severity is bounded by the fact that final exploitation additionally depends on the specific downstream target/proxy conflating underscore and hyphen forms of header names — this is not a universal behavior of all HTTP servers, so the practical blast radius depends on which third-party endpoints the workflow targets and whether those endpoints exhibit this conflation.

## Likelihood Explanation
Any workflow author capable of issuing an HTTP Action request (a normal, expected workflow capability) can trivially construct the bypass with zero additional privilege — it is a pure string-matching gap requiring no race condition or unusual environment, and it is fully reproducible.

## Recommendation
Normalize header names before denylist comparison in `validateHeaderNames` (e.g., replace `_` with `-`, or reject header names containing `_` outright) before the case-insensitive blocklist lookup, applied consistently in both `validateHeaders` and `validateMultiHeaders`.

## Proof of Concept
1. Issue an HTTP Action request from a workflow node with `MultiHeaders: {"X_Forwarded_For": ["10.0.0.1"]}` via `makeOutgoingRequest`. [5](#0-4) 
2. `httpClient.Send` invokes `validateMultiHeaders` → `validateHeaderNames`. [3](#0-2) 
3. `strings.ToLower("X_Forwarded_For")` = `"x_forwarded_for"`, absent from `blockedSet` (only `"x-forwarded-for"` is present), so validation passes. [6](#0-5) 
4. The header is added to the outgoing request via `r.Header.Add` and sent to the target host unmodified. [4](#0-3) 
5. A Go unit test asserting `validateHeaderNames([]string{"X_Forwarded_For"})` returns `nil` (no error) demonstrates the bypass directly against the existing `httpclient.go` logic.

// validateHeaderNames checks that none of the given header names are in the blocked list (case-insensitive).
func (c *httpClient) validateHeaderNames(names []string) error {
	blockedSet := make(map[string]struct{}, len(c.config.BlockedHeaders))
	for _, b := range c.config.BlockedHeaders {
		blockedSet[strings.ToLower(b)] = struct{}{}
	}
	for _, name := range names {
		if _, blocked := blockedSet[strings.ToLower(name)]; blocked {
			return fmt.Errorf("%w: HTTP header not allowed: %s", ErrBlockedRequest, name)
		}
	}
	return nil
}

func (c *httpClient) validateHeaders(headers map[string]string) error {
	return c.validateHeaderNames(slices.Collect(maps.Keys(headers)))
}

func (c *httpClient) validateMultiHeaders(multiHeaders map[string][]string) error {
	return c.validateHeaderNames(slices.Collect(maps.Keys(multiHeaders)))
}
