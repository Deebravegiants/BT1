## Title
Unauthenticated `/v2/resume/:runID` endpoint allows any unprivileged caller to complete/hijack a pending pipeline task run by guessing or leaking a UUID - ([File: core/web/pipeline_runs_controller.go])

## Summary
`PipelineRunsController.Resume` is registered in `core/web/router.go` on an explicitly unauthenticated route group (`unauthedv2.PATCH("/resume/:runID", prc.Resume)`), unlike every other `/v2` route which is wrapped in `auth.Authenticate(...)` with token/session/role checks. The handler accepts attacker-supplied `value`/`error` in the request body and, using only a bare UUID from the path as the "credential," calls `App.ResumeJobV2` to unblock and resume a suspended pipeline task run, injecting the caller's data into the pipeline.

## Finding Description
`BridgeTask.finalizeAndMarshalBridgeRequestData` embeds a callback URL `<bridgeResponseURL>/v2/resume/<taskUUID>` in outbound bridge/external-adapter requests when a task is `async=true` [1](#0-0) . The corresponding route is registered without any authentication middleware in `v2Routes`:

```go
unauthedv2 := r.Group("/v2")
prc := PipelineRunsController{app}
unauthedv2.PATCH("/resume/:runID", prc.Resume)
``` [2](#0-1) 

This stands in stark contrast to every other route registered afterward in the same function, all of which are wrapped in `authv2 := r.Group("/v2", auth.Authenticate(app.AuthenticationProvider(), auth.AuthenticateByToken, auth.AuthenticateBySession))` and further gated with `auth.RequiresAdminRole`/`RequiresEditRole`/`RequiresRunRole` for role-sensitive actions [3](#0-2) . The `Resume` handler itself parses only a UUID from the URL, decodes the attacker-controlled body into a `pipeline.ResumeRequest`, and calls `App.ResumeJobV2` directly, then logs the event as `audit.UnauthedRunResumed` [4](#0-3) . Downstream, `runner.ResumeRun` trusts the supplied value/error unconditionally to unblock and restart the pipeline [5](#0-4) .

The naming `UnauthedRunResumed` in `core/logger/audit/audit_types.go` (present but content not fully retrievable via the index) confirms this endpoint is intentionally designed to be unauthenticated by relying solely on UUID unguessability as the access control — there is no bridge-specific shared secret, HMAC, or IP allowlist check.

## Impact Explanation
This is a real, in-scope finding: an unauthenticated network endpoint accepts state-mutating input (arbitrary `value`/`error`) that directly controls pipeline execution output for the specific task run tied to the UUID, constituting "unauthorized job run" output manipulation — an impact class explicitly listed as in-scope (node API authentication bypass / unauthorized job run). The confirmed absence of any auth middleware on this specific route (verified directly in `router.go`, not merely inferred) satisfies the requirement to review existing auth middleware and show it insufficient — because there is none applied at all, by design.

## Likelihood Explanation
Exploitation requires no credential, role, or host access — only knowledge of a task run's UUID. UUIDv4 (122 bits of entropy) is not blindly guessable, so the realistic attack path is disclosure via logs, error messages, monitoring, or a race with the legitimate bridge/adapter observing/intercepting the outbound bridge request before it replies. This is consistent with how the report frames it: this is a "secrecy of an identifier" security model, not a broken-by-default vulnerability requiring zero information. The likelihood is non-trivial but conditioned on a leak of the UUID, which is realistic in practice (e.g., debug logging, request logging middleware) and is exactly the risk the `UnauthedRunResumed` audit event name is designed to flag/monitor for. This maps to a legitimate design tradeoff Chainlink made and documented via the explicit audit-log naming, but the underlying risk (any leaked resume UUID = full compromise of that task run's result with no secondary check) is a concrete, reproducible security weakness.

## Recommendation
Bind the resume action to bridge-specific authentication beyond the bare UUID — e.g., a per-request HMAC signed with the bridge's `OutgoingSecret`/`OutgoingToken` (mirroring the external initiator's `AuthenticateExternalInitiator` scheme), or require a shared secret header validated against the specific bridge configuration before `PipelineRunsController.Resume` calls `App.ResumeJobV2`.

## Proof of Concept
1. Configure a job with an `async=true` bridge task; on dispatch, the node sends a bridge request containing `responseURL: <bridgeResponseURL>/v2/resume/<taskUUID>` as shown in `core/services/pipeline/task.bridge.go` L364-374.
2. Obtain `<taskUUID>` via a leak vector (logging, network interception, monitoring dashboard, or timing race with the legitimate adapter).
3. Send `PATCH /v2/resume/<taskUUID>` with an attacker-chosen JSON body matching `pipeline.ResumeRequest`, with no Authorization/session cookie headers, directly to the node.
4. Verify in `router.go` that this route (`unauthedv2.PATCH("/resume/:runID", prc.Resume)`) bypasses the `auth.Authenticate` middleware applied to all sibling `/v2` routes — confirmed by direct code inspection at `core/web/router.go` L238-243 vs L245-248.
5. Observe `App.ResumeJobV2` is invoked and the pipeline resumes using the attacker-supplied value/error, with `audit.UnauthedRunResumed` logged, confirming the unauthenticated write path (`core/web/pipeline_runs_controller.go` L131-160, `core/services/pipeline/runner.go` L732-755).

**Note on scope/known-issue status:** I was not able to fully verify from the index whether this specific design (bare UUID-based bridge resume callback with no bridge secret) is a documented/accepted design tradeoff versus an unaddressed bug in Chainlink's threat model, or whether it has prior disclosure/acknowledgment history — `SECURITY.md` contains references to scope but its exact content on this endpoint could not be retrieved in full detail. Given the explicit, deliberate naming `audit.UnauthedRunResumed` in the shipped code, this strongly suggests the endpoint's lack of authentication is a known, intentional design decision by the Chainlink team (mitigated only by UUID secrecy and audit logging) rather than an oversight, which may affect eligibility under bounty rules excluding already-acknowledged/by-design behavior — this should be confirmed against the bounty program's specific known-issues list before treating it as a novel finding.

// Resume finishes a task and resumes the pipeline run.
// Example:
// "PATCH <application>/jobs/:ID/runs/:runID"
func (prc *PipelineRunsController) Resume(c *gin.Context) {
	taskID, err := uuid.Parse(c.Param("runID"))
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	rr := pipeline.ResumeRequest{}
	decoder := json.NewDecoder(c.Request.Body)
	err = errors.Wrap(decoder.Decode(&rr), "failed to unmarshal JSON body")
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}
	result, err := rr.ToResult()
	if err != nil {
		jsonAPIError(c, http.StatusUnprocessableEntity, err)
		return
	}

	if err := prc.App.ResumeJobV2(c.Request.Context(), taskID, result); err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

	prc.App.GetAuditLogger().Audit(audit.UnauthedRunResumed, map[string]any{"runID": c.Param("runID")})
	c.Status(http.StatusOK)

		Error: err,
	})

	}

	// TODO: Should probably replace this with a listener to update events

			defer cancel()
			if _, err := r.Run(ctx, &run, false, nil); err != nil {
				r.lggr.Errorw("Resume run failure", "err", err)
			}
			r.lggr.Debug("Resume run success")
		}()
	}
	return nil
}
