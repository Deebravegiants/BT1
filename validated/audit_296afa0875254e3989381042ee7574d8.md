### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header fields are not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes/verifies the webhook HMAC over the raw body only, but derives `shop`, `topic`, `webhook_id`, and `api_version` from separate, unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` as the tenant identity for the webhook handler without that value ever being part of the signed material.

### Finding Description
`Request#to_signable_string` returns `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` verifies the HMAC solely against this signable string using `OpenSSL.secure_compare` [2](#0-1) . Meanwhile, `Request#shop` (and `topic`, `webhook_id`, `api_version`) are read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header via `shopify_header`, entirely outside the HMAC computation [3](#0-2) .

`Registry.process` validates only that the HMAC matches the body, then immediately builds `WebhookMetadata` using `request.shop` as the authoritative tenant identifier and dispatches it to the app's handler: [4](#0-3) .

This breaks the intended identity binding: `HMAC(raw_body) == HMAC(raw_body)` is satisfied, but the equality that actually matters for tenant isolation — `shop_header == shop_the_HMAC_was_issued_for` — is never checked. Since a single `api_secret_key` is shared by the app across all shops, any party who legitimately receives one authentic webhook (e.g., an attacker running their own shop instance of the app) possesses a raw_body + HMAC pair signed with the app's shared secret. They can replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header for a victim shop, and the library will report it as an authentic webhook for the victim shop.

### Impact Explanation
This is a cross-tenant identity confusion: the webhook handler receives `data.shop` naming an arbitrary shop while the HMAC only proves the body was signed by the app's secret (not that it was signed *for* that shop). Depending on what the app does in its webhook handler (e.g., `shop/redact`, `customers/data_request`, uninstall/`app/uninstalled`, order/customer processing keyed by `data.shop`), this can trigger destructive or data-exposing actions attributed to a shop the attacker does not control, without the attacker ever needing the app's `client_secret` directly — they only need one legitimate webhook delivery from their own installation.

### Likelihood Explanation
Requires only that an attacker install the app on a shop they control (a normal, unprivileged path) to receive one authentic webhook, then replay its body+HMAC with a modified shop header. No `api_secret_key` compromise or TLS interception is needed. Any app relying on `data.shop` from `WebhookMetadata` for authorization or tenant-scoped state changes is exposed.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signed material verified against the HMAC (or otherwise cryptographically bind them), rather than trusting header values that are outside the HMAC's coverage. At minimum, document that consuming apps must independently verify `data.shop` against a known, previously-established session/tenant record before acting on it.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, obtains a genuine webhook delivery: raw body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`).
2. Attacker POSTs to the app's webhook endpoint with the same body `B`, same `H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` and it matches `H`, since it never used the shop header [5](#0-4) .
4. `Registry.process` proceeds and calls the handler with `data.shop == "victim-shop.myshopify.com"` and body `B` [6](#0-5) , even though `B` was never actually generated for that shop.
