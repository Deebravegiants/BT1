## Finding: Excess native token payment is not refunded to callers of `EvmHost.dispatch`/`fundRequest`

### Title
Overpaid native-token dispatch/funding fees are permanently stuck in `EvmHost` instead of being refunded to the caller - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` all accept `msg.value` as payment, forward the **entire** `msg.value` to `swapETHForExactTokens{value: msg.value}(fee, ...)`, but never account for or return any leftover native token to the original caller. This is the same root cause as the referenced Footium report: a payable entrypoint accepts "at least X" but silently keeps the excess instead of refunding it.

### Finding Description
In `dispatch(DispatchPost)`:
```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
``` [1](#0-0) 

The same pattern occurs in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

`IUniswapV2Router02.swapETHForExactTokens` refunds any unspent ETH back to `msg.sender` of that call — but that caller is `EvmHost` itself (since `EvmHost` invokes the router), not the original `_msgSender()`/EOA who called `dispatch`/`fundRequest`. Since `EvmHost` never forwards this router refund on to the original caller, any native token sent above the exact amount needed to cover `post.fee`/`get.fee`/`amount` becomes trapped in the `EvmHost` contract balance with no mechanism to return it to the payer.

This is confirmed by contrast with `IntentGatewayV2.placeOrder`, which performs the identical `swapETHForExactTokens` pattern but explicitly tracks `msgValue -= amounts[0]` and refunds the leftover to `msg.sender` at the end of the function: [4](#0-3) 

`EvmHost` has no equivalent refund step after any of its three payable native-token entrypoints.

### Impact Explanation
Any unprivileged user dispatching a POST/GET request through `EvmHost.dispatch`, or topping up a pending request's relayer fee via `fundRequest`, who overestimates the required native amount (e.g., due to price movement between quoting and execution, or simply passing a safety margin as recommended in the docs — "Estimate Fees Off-Chain... Only use it off-chain for frontend fee estimation") will permanently lose the excess ETH sent. This directly matches the "Users will lose assets" bug class, and unlike `IntentGatewayV2`/`ExtrinsicIntents`/`WrappedHyperFungibleTokenUpgradeable` (all of which correctly refund excess native tokens), the core `EvmHost` dispatch paths have no such protection.

### Likelihood Explanation
High likelihood in practice: the documentation itself instructs integrators to estimate fees off-chain and warns against on-chain `quote()` calls due to sandwich-attack risk, implicitly encouraging users/integrators to send a buffer of native token with their transaction. Any buffer above the exact swap requirement is lost. This applies to every single `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest` call funded with native token.

### Recommendation
Track the amount actually consumed by `swapETHForExactTokens` (its return value) and refund `msg.value - amountSpent` back to `_msgSender()` at the end of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder`:
```solidity
uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
    post.fee, path, address(this), block.timestamp
);
uint256 refund = msg.value - amounts[0];
if (refund > 0) {
    (bool sent, ) = _msgSender().call{value: refund}("");
    require(sent);
}
```

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchPost{fee: 10 feeToken, ...})` and sends `msg.value = 1 ether` as a safety buffer (per documented best practice) when only `0.1 ether` worth of ETH is actually needed to swap for `10` fee tokens.
2. `swapETHForExactTokens{value: 1 ether}(10, path, address(this), ...)` executes, spending only `~0.1 ether` and having the Uniswap router refund the remaining `~0.9 ether` back to `address(this)` (i.e., `EvmHost`), per Uniswap V2 Router semantics.
3. `EvmHost.dispatch` returns without any code path that forwards this `~0.9 ether` back to the user; it is absorbed into `EvmHost`'s balance permanently, with no admin/withdraw function shown in `EvmHost.sol`/`HostManager.sol` targeting native ETH refunds to specific payers.
4. Contrast with the analogous `IntentGatewayV2SameChainTest.testPlaceOrder_FeeSwap_RefundsExcessNativeToken` test, which verifies that `IntentGatewayV2.placeOrder` refunds excess ETH from an identical swap — no equivalent test or refund logic exists for `EvmHost.dispatch`/`fundRequest`. [5](#0-4)
