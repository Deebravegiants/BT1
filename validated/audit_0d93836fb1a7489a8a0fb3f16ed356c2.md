## Title
Webhook `shop-domain` Header Is Not Bound to the HMAC Signature, Enabling Cross-Tenant Replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the webhook's tenant identity (`shop`) from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature computed by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body (`to_signable_string` returns `@raw_body`). The `shop` header, `topic` header, and `webhook_id` header are never included in the signed content, so `Registry.process` trusts an unauthenticated header to route the (authenticated) body to a tenant-specific handler.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the raw JSON body is signed. `Request#shop` simply reads the `shop-domain` header without any cryptographic binding to that body: [2](#0-1) 

`Utils::HmacValidator.validate` verifies only `to_signable_string` (the body) against the computed HMAC: [3](#0-2) 

`Registry.process` accepts any request whose body-HMAC validates, then unconditionally forwards `request.shop` (the unauthenticated header) to the app's handler as the tenant identifier for that (validated) body: [4](#0-3) 

Because `Context.api_secret_key` is a single shared secret across every shop/merchant that has installed the app (not a per-shop secret), any legitimately-signed webhook body the attacker can obtain a valid `(body, hmac)` pair for (e.g., a webhook Shopify sent for the attacker's own store, or any other real, captured webhook for this app) can be resubmitted to the app's webhook endpoint with an arbitrary `shop-domain` header value. The signature still validates (it only checks the body against the shared secret), but the app will process that body as if it belongs to a different, victim shop — an identity/tenant-binding break: the HMAC authenticates "this body came from Shopify for *some* install of this app," not "this body + this shop are bound together."

This exactly matches the report's bug class: a field (`shop`, used to route/act on tenant-specific data) is acted upon by the consumer (`Registry.process` → handler) but is not covered by the integrity check (HMAC), just as the duplicate-membership fix required binding `member` identity checks that the original code omitted.

### Impact Explanation
This breaks the equality `shop_the_HMAC_authenticates == shop_the_handler_acts_on`. A host application's webhook handler commonly uses `data.shop` to look up the merchant's stored session/access token or to write/mutate merchant-scoped records. By replaying a validly-signed webhook body under a different `shop-domain` header, an attacker (who need not possess `api_secret_key`, only a captured legitimate webhook — including one for their own store) can cause the app to process data or trigger actions attributed to a different tenant, i.e., cross-tenant confusion. Depending on the handler logic in the host app, this can range from data leakage/corruption to processing mandatory-compliance webhooks (e.g., `shop/redact`, `customers/redact`) against the wrong shop.

### Likelihood Explanation
Requires no privileged credentials or TLS interception: the attacker only needs one previously-observed, validly-signed webhook payload for the app (trivially obtainable by installing the app on their own test store and capturing a real Shopify-delivered webhook) and the ability to POST to the app's public webhook endpoint with custom headers, which is normal HTTP client capability. The gem performs no additional binding to prevent this replay-with-relabeled-tenant attack.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, and ideally `api-version`) in the HMAC-signed material, or otherwise cryptographically bind them to the body (e.g., verify that Shopify's HMAC covers a canonical string containing headers + body, matching Shopify's documented behavior where the HMAC only protects the body but the delivery channel authenticity for headers must be separately trusted only over a verified, non-replayable channel). At minimum, `Registry.process` should not use `request.shop` for any authorization/session-lookup decision without additional verification that ties the specific shop to the specific signed payload (e.g., cross-check against an expected/whitelisted set of shop domains, or require correlation with a webhook_id no-replay cache).

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker-shop.myshopify.com` and lets it deliver a real webhook, e.g. `orders/create`, with body `B` and a Shopify-computed, validly-signed `hmac-sha256` header `H` (computed over `B` using the shared `api_secret_key`).
2. Attacker captures `(B, H)` from that legitimate delivery.
3. Attacker sends a forged POST to the app's webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <any>
   x-shopify-api-version: <any>

   B
   ```
4. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present).
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds even though `shop-domain` was changed.
6. The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-supplied data under the victim shop's identity.
