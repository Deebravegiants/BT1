## Analog Found

### Title
Front-running a single leaf in a `HandlerV2` POST/GET-response batch reverts the entire delivery transaction, enabling a batch-delivery DoS - ([File: evm/src/core/HandlerV2.sol])

### Summary
`HandlerV2.handlePostRequests` and `HandlerV2.handleGetResponses` accept an array of independent, MMR-proven leaves and, after verifying the multiproof, loop over every leaf and dispatch it. If **any single leaf** in that batch has already been delivered (i.e. a receipt already exists on the host), the loop `revert`s immediately with `DuplicateMessage()`, aborting the entire transaction rather than skipping just that leaf. This is the same bug class as the reported `AuctionFacet.buy()` issue: a batch of otherwise-independent operations is made atomic by a single revert path, so front-running one item denies the whole batch.

### Finding Description
In `handlePostRequests`:
```solidity
for (uint256 i = 0; i < requestsLen; ++i) {
    PostRequestLeaf memory leaf = request.requests[i];
    // duplicate request?
    if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
    host.dispatchIncoming(leaf.request, _msgSender());
}
``` [1](#0-0) 

and identically in `handleGetResponses`:
```solidity
for (uint256 i = 0; i < responsesLength; ++i) {
    GetResponseLeaf memory leaf = message.responses[i];
    // duplicate response?
    if (host.responseReceipts(leaf.response.request.hash()).relayer != address(0)) revert DuplicateMessage();
    host.dispatchIncoming(leaf.response, _msgSender());
}
``` [2](#0-1) 

Both functions are **permissionless** — anyone (a relayer or a self-relaying user, per the docs) can submit these calls, and `batchCall` composes several such calls atomically as well:
```solidity
function batchCall(bytes[] memory calls) external {
    uint256 len = calls.length;
    for (uint256 i = 0; i < len; ++i) {
        (bool success, bytes memory returnData) = address(this).delegatecall(calls[i]);
        if (!success) revert BatchCallFailed(i, returnData);
    }
}
``` [3](#0-2) 

Because the whole expensive MMR-multiproof verification and delivery loop is wrapped in one atomic call, a party who front-runs the honest submitter by delivering just one of the N leaves (e.g. via their own single-leaf `handlePostRequests` call, using a proof derivable from the same publicly known overlay root) causes the honest submitter's much larger batch transaction to revert entirely with `DuplicateMessage()` — even though the other N-1 messages are still perfectly valid and undelivered.

Notably, this is the exact opposite design decision made on the Substrate/pallet-ismp side of the protocol: there, `handlers::request::handle` and `handlers::response::handle` collect each per-request/response outcome into a `Vec` **without** propagating an early error via `?`, so a duplicate/failed item inside the batch is recorded as an event but does not abort delivery of the rest of the batch:
```rust
let result = msg.requests.into_iter().map(|request| { ... }).collect::<Vec<_>>();
Ok(MessageResult::Request { events: result, weight: total_weights })
``` [4](#0-3) 

The relayer/messaging layer itself is aware that batches containing an already-delivered duplicate revert on EVM destinations:
```rust
// A request can be parked more than once, on its own and inside a batch that
// failed later, and a batch carrying it twice reverts on the duplicate.
``` [5](#0-4) 

but that mitigation is only against *self-duplication inside one relayer's own batch* — it does not protect against a competing relayer or self-relaying user front-running one leaf of a batch built by someone else.

### Impact Explanation
An attacker can watch the mempool for a large `handlePostRequests`/`handleGetResponses` (or `batchCall`) transaction carrying many independent messages, then submit a cheap transaction that delivers just one of the included leaves first. The victim's transaction then reverts in its entirety with `DuplicateMessage()`, wasting the gas paid for verifying the multiproof and the entire batch. Because relaying is a competitive, permissionless activity — including self-relaying by end users to save fees — this degrades into a batch-delivery DoS: instead of atomically delivering N pending POST requests/GET responses in one shot, the victim is forced to fall back to delivering messages one at a time (at increasing total gas cost), directly matching the "buy multiple NFTs" analog where an attacker forces the legitimate actor to process items individually instead of in one batch. This can delay legitimate message delivery for the whole state route, i.e. "a route unable to deliver messages" as defined by the impact criteria.

### Likelihood Explanation
Likelihood is high: `handlePostRequests`/`handleGetResponses`/`batchCall` are fully permissionless functions with no access control (`notFrozen` is the only modifier), and any relayer or user can construct a valid single-leaf proof for any leaf whose overlay root/state commitment is already public on-chain, since MMR proofs for individual leaves are derivable from the publicly known root and leaf set. Batches are visible in the public mempool before inclusion, making front-running trivial with standard MEV tooling.

### Recommendation
Change the duplicate-check loop in `handlePostRequests` and `handleGetResponses` to `continue` past already-delivered leaves instead of reverting the whole call, mirroring the pallet-ismp behavior of recording per-item outcomes rather than aborting the batch:
```diff
 for (uint256 i = 0; i < requestsLen; ++i) {
     PostRequestLeaf memory leaf = request.requests[i];
-    if (host.requestReceipts(leaf.request.hash()) != address(0)) revert DuplicateMessage();
+    if (host.requestReceipts(leaf.request.hash()) != address(0)) continue;
     host.dispatchIncoming(leaf.request, _msgSender());
 }
```
Apply the same pattern to `handleGetResponses`.

### Proof of Concept
1. Alice observes 10 pending POST requests destined for the same chain and builds one `handlePostRequests` call bundling their MMR multiproof and all 10 leaves, and broadcasts the transaction.
2. Bob, monitoring the mempool, extracts a single-leaf proof for one of the same 10 requests (derivable from the same public overlay root) and submits his own `handlePostRequests` call with just that one leaf, paying much less gas, and gets it mined first.
3. When Alice's transaction executes, the loop at `evm/src/core/HandlerV2.sol:204-209` reaches Bob's already-delivered leaf, `host.requestReceipts(...)` is non-zero, and the call `revert DuplicateMessage()`s — Alice's entire transaction fails and none of the other 9 valid, still-undelivered requests are dispatched, even though they were perfectly deliverable.
4. Bob (or anyone) can repeat this for each of Alice's subsequent retries, forcing every batch to fail until Alice gives up batching and relays messages one at a time.

	let mut total_weights = Weight::zero();
	let result = msg
		.requests
		.into_iter()
		.map(|request| {
			let wrapped_req = Request::Post(request.clone());
			let mut lambda = || {
				let cb = router.module_for_id(request.to.clone())?;
				// Re-check the receipt right before dispatch. The up-front pass above
				// runs before any callback executes; a prior request's on_accept in
				// this same batch could have stored a receipt for this request
				// (directly or by re-entering the handler), and we must not invoke
				// on_accept a second time.
				if host.request_receipt(&wrapped_req).is_some() {
					Err(Error::DuplicateRequest { meta: wrapped_req.clone().into() })?
				}
				// Store request receipt to prevent reentrancy attack
				let signer = host.store_request_receipt(&wrapped_req, &msg.signer)?;
				let res = cb.on_accept(request.clone()).map(|weight| {
					total_weights.saturating_accrue(weight);

					let commitment = hash_request::<H>(&wrapped_req);
					Event::PostRequestHandled(RequestResponseHandled {
						commitment,
						relayer: signer,
					})
				});
				// Delete receipt if module callback failed so it can be timed out
				if res.is_err() {
					host.delete_request_receipt(&wrapped_req)?;
				}
				Ok(res)
			};

			let res = lambda().and_then(|res| res);
			res
		})
		.collect::<Vec<_>>();

	Ok(MessageResult::Request { events: result, weight: total_weights })
