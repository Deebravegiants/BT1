### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop-attribution spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `ShopifyAPI::Webhooks::Registry.process` validates the HMAC solely against that body. The `shop` (and `topic`/`webhook_id`) values, which are taken directly from unauthenticated HTTP headers, are never part of the signed data, yet they are trusted and handed to the app's webhook handler as the tenant identity for the event.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
only the `@raw_body` is included in the signable string. `Request#shop` simply reads the `shop-domain` header verbatim: [2](#0-1) 

`Registry.process` validates HMAC using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (body-only) and compares against `request.hmac`, then immediately builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` without any additional binding check: [3](#0-2) 

The identity binding that should hold is: `shop delivered to handler == shop the HMAC-signed bytes originated from`. Because the header carrying `shop` is excluded from the signed bytes, this binding does not hold — the signature only proves "some payload signed with the app's shared `client_secret`", not "this payload belongs to this shop." Since Shopify signs all webhooks for a given app with the same `client_secret` regardless of which shop triggered the event, a merchant/attacker who operates their own shop installed on the same app can capture a legitimate `(raw_body, hmac)` pair from an event on their own store, then replay it to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. The HMAC check still passes because it only re-computes the signature over the untouched body; the forged `shop` value flows straight through to `WebhookMetadata.shop`, which host applications use to look up sessions/records for the *victim* tenant, as documented: [4](#0-3) 

### Impact Explanation
This breaks the identity binding "shop authenticated by HMAC" vs. "shop the handler acts on" — a field acted upon (`shop`) is not covered by the HMAC. This enables cross-tenant confusion: an attacker who controls one legitimate shop on the app can make the app process webhook data (with a self-controlled, arbitrarily-shaped body/topic combination available to that shop) while attributing it to a different, victim shop, since `data.shop` is trusted by host applications to select which tenant's session/data to update. This matches the Critical "cross-tenant access" impact category, because the gem itself performs the signature check and asserts the tenant identity (`data.shop`) that downstream code relies on without covering it with the signature.

### Likelihood Explanation
Likelihood is constrained by the requirement that the attacker have access to at least one legitimate shop installation of the target app (to obtain a validly signed `(raw_body, hmac)` pair), which is realistic for any third-party app since app installation is generally open to any merchant. No leaked secrets, TLS interception, or privileged access is required — only a normal, unprivileged merchant account plus the ability to POST a modified HTTP header to the app's public webhook endpoint.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook_id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind them to the signed body (e.g., verify that the recipient's independently-known session/shop matches `request.shop` obtained through a channel authenticated by more than just the header). At minimum, document that consumers of `WebhookMetadata.shop` must not treat it as authenticated and must cross-check it against records established via the OAuth flow before using it to select tenant data.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` (attacker's own store) and receives a real webhook for topic `orders/create` from Shopify, e.g.:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid-hmac-of-raw-body>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: {"id": 1, ...attacker-controlled order fields...}
   ```
2. Attacker captures the raw body and the `x-shopify-hmac-sha256` value (both untouched — computed by Shopify over the shared `client_secret`).
3. Attacker replays the exact same body/HMAC to the app's webhook endpoint, but changes only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`.
4. `Request#hmac`/`Request#to_signable_string` only look at the body, so `Utils::HmacValidator.validate` in `Registry.process` returns `true` — see [5](#0-4) .
5. `WebhookMetadata.shop` is now `victim-shop.myshopify.com` even though the signed bytes never originated from that shop, and the host app's handler (per the documented pattern `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) processes/records the attacker-controlled body against the victim's tenant data.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
```
