### Title
Webhook shop-domain identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then unconditionally trusts the `shop`, `topic`, and `webhook_id` values pulled from unauthenticated HTTP headers and hands them to the app's handler as the tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, and `webhook_id` are read directly from HTTP headers without any cryptographic binding to the signed payload: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which computes `OpenSSL::HMAC.hexdigest` over `to_signable_string` (i.e. the body only) and then immediately constructs `WebhookMetadata` using `request.shop` taken from the unauthenticated header: [3](#0-2) [4](#0-3) 

This is structurally the same class of bug described in the external report: a value that is *acted on* (`returnAmount` incorporating `vest.claimed`; here, the `shop` identity used for tenant routing) is not the value that was actually *verified* (the vested/unclaimed balance; here, the HMAC-signed bytes, which cover only the body). The equality that should hold is:

```
verified(bytes signed by HMAC) == bytes the shop identity is derived from
```

In this code, that equality does not hold: `hmac` is computed over `@raw_body` alone, while `shop` (and `topic`/`webhook_id`) come from `@headers`, which are never included in `to_signable_string`. Consequently, once an attacker has captured any single legitimate webhook body+HMAC pair for one shop (e.g., a shop they operate as a merchant, or a webhook whose body is public/predictable, such as `shop/redact` boilerplate), they can replay that exact body and HMAC while substituting a different `shopify-shop-domain` header value. `Utils::HmacValidator.validate` will report success because it only checks the body's HMAC, and `Registry.process` will dispatch to the app's handler with `WebhookMetadata#shop` set to the attacker-chosen shop, not the shop that actually produced/authorized the payload.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (as documented and demonstrated in `docs/usage/webhooks.md` and the handler pattern in `registry.rb`) to key per-tenant data (e.g., "look up merchant record for `data.shop` and update it based on `data.body`") can be tricked into applying another shop's, or an attacker-controlled, webhook body under an arbitrary victim shop identity — a cross-tenant data confusion/write primitive achievable purely by an unprivileged internet user who can send HTTP requests to the app's webhook endpoint, without possessing the app's `client_secret`/`api_secret_key`. This matches the "cross-tenant access" Critical impact category, since the shop-authentication boundary (HMAC-verified body vs. header-derived tenant id) is broken.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid (body, HMAC) pair — trivial for topics whose body content the attacker controls or can predict/replay (their own shop's real webhooks, which they legitimately receive as a merchant/dev-store owner of the app), and then resend it with a forged `shop`-domain header to the app's public webhook endpoint. No possession of the app's secret is needed to perform the spoof itself, only a legitimately delivered webhook to replay. This is a moderately easy, realistic attack path for any developer/store owner who has the app installed.

### Recommendation
Bind the shop/topic/webhook identity into the material verified by the HMAC, or otherwise cryptographically tie the header-derived `shop` value to the session/tenant the app expects, e.g.:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (mirroring how OAuth's `AuthQuery` binds `shop` into its signable string), or
- After HMAC validation, require the caller to independently verify that `request.shop` matches a shop for which the app currently holds an active, previously-established session/subscription (i.e., don't allow `WebhookMetadata#shop` to introduce a new/foreign tenant based on header content alone), or
- Document explicitly and enforce in the library that `shop` is untrusted input that callers must corroborate against known installed-shop state before using it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs (or already has) the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery: body `B` and header `shopify-hmac-sha256: H` (valid HMAC of `B` under the app's secret), along with header `shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint using the same body `B` and same header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`. `Utils::HmacValidator.validate(request)` succeeds because it only hashes `B` (the raw body) against the secret — the header substitution is invisible to it: [5](#0-4) 
4. The registered handler receives `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: ..., ...)` and, if it uses `shop` to select/mutate tenant records, mutates or discloses data under the wrong (attacker-chosen) tenant identity — a cross-tenant confusion achieved without the app's `client_secret`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
