This confirms the finding: the gem's own documentation explicitly instructs developers to trust `data.shop` (`docs/usage/webhooks.md:14,25-26`) for tenant routing, while `ShopifyAPI::Webhooks::Registry.process` only validates the HMAC over the raw body, never binding it to the `shop-domain` header.### Title
Webhook `shop` domain used for tenant identification is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying an HMAC over the raw request body [1](#0-0) . The `shop-domain` header that the gem hands to every webhook handler as the tenant identifier is never included in that signature [2](#0-1) , so the binding "HMAC-authenticated request == the shop the payload is attributed to" does not hold.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate_signature` computes the HMAC exclusively over that signable string [4](#0-3) . Meanwhile `shop`, `topic`, and `webhook_id` are all read directly from unauthenticated request headers [5](#0-4) . `Registry.process` only checks the HMAC before dispatching, then constructs `WebhookMetadata` using `request.shop` taken straight from the header, with no cross-check that the body content actually corresponds to that shop [6](#0-5) . The gem's own documentation instructs integrators to trust `data.shop` for tenant routing/attribution (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`) [7](#0-6) .

Binding broken (equality that should hold but doesn't):
`shop-domain header used for tenant attribution == shop bound inside the HMAC-verified bytes`

Concretely: an attacker who controls any store where the app is installed can legitimately receive a validly-HMAC-signed webhook body for their own store. Because the signature covers only the raw JSON body and not the `shop-domain` header, that same `(raw_body, hmac)` pair remains valid when replayed to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim's shop. `HmacValidator.validate` will still succeed since it only recomputes over `@raw_body` [8](#0-7) , so the forged request passes verification and is dispatched to the handler labeled with the victim's shop.

### Impact Explanation
If a host application trusts `WebhookMetadata#shop` (as the documented usage pattern encourages) to decide which tenant's records to update/enqueue work for, an attacker can inject data attributed to a shop they do not control, causing cross-tenant data confusion (e.g., record IDs from the attacker's own store being processed under a victim shop's account). This matches the "High — cross-tenant access" / identity-binding-break category defined in scope (shop authenticated vs. shop used as an identifier).

### Likelihood Explanation
Requires only an attacker-controlled Shopify store where the app is installed (unprivileged, free/dev store), plus knowledge of the target victim's exact myshopify domain (public information) — no leaked secrets or privileged access are needed. Exploitation is a simple header rewrite/replay of a legitimately received webhook request.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is authenticated, e.g., by including the `x-shopify-shop-domain` header in the HMAC computation, or by having `Registry.process` independently verify that `request.shop` matches a shop known to have registered/received that specific webhook (e.g. cross-checked against an active session/installation record) before constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify sends a legitimately HMAC-signed webhook to the app:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC over raw body>
x-shopify-shop-domain: attacker.myshopify.com
x-shopify-webhook-id: ...

{"id": 1, "note": "malicious payload"}
```
3. Attacker replays the exact same body and HMAC, only changing the shop header:
```
POST /webhooks
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <same valid HMAC, unchanged>
x-shopify-shop-domain: victim-shop.myshopify.com
x-shopify-webhook-id: ...

{"id": 1, "note": "malicious payload"}
```
4. `Utils::HmacValidator.validate` in `lib/shopify_api/webhooks/registry.rb:190` re-validates only against `@raw_body` and succeeds, and the handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` despite the body never having originated from that shop.

Note: This mirrors Shopify's real-world webhook HMAC design (signature over raw body only), which is also present in the official platform, so the "root cause" is partly a design choice shared with the wider Shopify ecosystem rather than a coding defect unique to this gem's HMAC math; I cannot fully verify from this index alone whether Shopify's server-side webhook delivery pipeline itself already prevents cross-tenant header spoofing (e.g., mTLS/IP allow-listing outside this gem's control), which would mitigate real-world exploitability. This uncertainty should be validated further before treating this as a confirmed, actionable vulnerability in the gem itself.
