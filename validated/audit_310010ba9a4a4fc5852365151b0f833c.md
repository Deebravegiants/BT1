### Title
Missing domain separation in iris-code signature allows cross-signup replay - (File: `src/plans/enroll_user.rs`)

### Summary
The `make_signature` function that produces the "Iris code signature" submitted with every signup request hashes only `ORB_ID`, the user's QR `user_id`, and the iris/mask code material — it does not bind the signature to the `signup_id`, a timestamp, or any other per-attempt nonce. This is the same class of defect as a missing `DOMAIN_SEPARATOR()`: the signed payload lacks the contextual/domain binding needed to prevent a signature computed for one signup context from being valid for another.

### Finding Description
`make_signature` in `src/plans/enroll_user.rs` builds the signed digest purely from static identity/biometric fields: [1](#0-0) 

The digest includes `ORB_ID`, `user_qr_code.user_id`, `ir_net_version`, `iris_version`, and both eyes' iris/mask codes and code versions, then is signed via `secure_element::sign`. Notably absent are `signup_id`, `operator_qr_code`, a timestamp, or any other per-session/per-request nonce.

That signature is then submitted alongside a *separately supplied* `signup_id` (used only in the URL path, not part of the signed bytes) in the signup POST request: [2](#0-1) 

Because `signup_id` is not part of the signed payload, the digest computed by `make_signature` is not bound to the specific signup transaction it accompanies — it is bound only to `(ORB_ID, user_id, iris_version_fields, iris_code, mask_code)`. Any request carrying the same user QR data and iris/mask code bytes will produce (and accept) an identical signature regardless of which `signup_id` it is attached to.

This contrasts with the sibling signing path in `src/plans/personal_custody_package.rs`, where the signed `hashes.json` is derived from an `info_json` structure that explicitly includes `signup_id`, `signup_reason`, `orb_id`, `operator_id`, and `timestamp` (each with a salt) before being hashed and signed: [3](#0-2) [4](#0-3) 
That path correctly incorporates domain-separating context; the `enroll_user.rs` signature path does not.

### Impact Explanation
The iris-code signature is intended to attest, to the backend, that a specific Orb device cryptographically vouches for the (`user_id`, iris-code) pairing being submitted for a given signup. Without binding to `signup_id` (or any other per-attempt nonce), a signature valid for one signup transaction remains valid input for a different signup transaction as long as the same `user_id` and iris/mask code bytes are re-submitted. This weakens the intended non-replayability/uniqueness guarantee the signature is supposed to provide per the ERC2612-style domain-separation rationale, and could enable cross-signup replay/misattribution if the same signed data is resubmitted against a different `signup_id`.

### Likelihood Explanation
Exploiting this requires the ability to resend a previously observed signature+iris-code payload against a different `signup_id`, which in practice requires interception or replay capability on the request path between the Orb and the backend (e.g., a compromised or malicious network position, or software running with equivalent local access). It does not require breaking the underlying secure-element cryptographic signature itself — only that the signed bytes are not bound to the specific signup they are meant to authorize. The core issue — absence of `signup_id`/timestamp binding in `make_signature` — is confirmed directly from the code; whether the backend independently re-derives or checks `signup_id` binding elsewhere could not be verified from this repository alone, since backend verification logic is out of scope for `orb-core`.

### Recommendation
Include `signup_id` (and ideally a timestamp or monotonic nonce) in the `Context` hashed by `make_signature`, mirroring the domain-separation approach already used in `personal_custody_package.rs`'s `info_json` construction, so the resulting signature is cryptographically bound to the specific signup transaction it accompanies and cannot be replayed across different `signup_id` values.

### Proof of Concept
1. Complete a signup where `make_signature` computes `sig = sign(SHA256(ORB_ID || user_id || ir_net_version || iris_version || iris_code_left || mask_code_left || ... ))` for `signup_id = A`, as shown in `src/plans/enroll_user.rs:290-304`.
2. Observe that `signup_post::request` sends `sig` as a form field independent of `signup_id`, which only appears in the URL path (`src/backend/signup_post.rs:100-145`).
3. Resubmit the identical multipart form (same `signature`, `userId`, `codes`) to `/api/v2/signups/{B}` with a different `signup_id = B`.
4. Because the signed digest never included `signup_id`, the signature remains valid for the new `signup_id`, demonstrating the absence of domain separation between signup transactions.

fn make_signature(user_qr_code: &qr_scan::user::Data, pipeline: &Pipeline) -> Result<String> {
    let mut ctx = Context::new(&SHA256);
    ctx.update(ORB_ID.as_str().as_bytes());
    ctx.update(user_qr_code.user_id.as_bytes());
    ctx.update(pipeline.v2.ir_net_version.as_bytes());
    ctx.update(pipeline.v2.iris_version.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_left.iris_code_version.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.mask_code.as_bytes());
    ctx.update(pipeline.v2.eye_right.iris_code_version.as_bytes());
    let signed = secure_element::sign(ctx.finish())?;
    Ok(BASE64.encode(&signed))
}
