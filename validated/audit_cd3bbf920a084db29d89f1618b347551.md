### Title
Borrow-index accrual overflows i128 before `MAX_BORROW_INDEX_RAY` cap engages, permanently freezing every verb on the market - (File: contracts/pool/src/cache/scale.rs)

### Summary
The bug class in the report is an incorrect bound/constant that makes a core operation panic with an out-of-bounds / overflow condition instead of completing. XOXNO Lending has the same shape: the per-market borrow index is nominally capped at `MAX_BORROW_INDEX_RAY`, but the accrual path computes `supplied_shares × old_index` (`scaled_to_original` / `update_supply_index`) **before** the cap check can bite. On a whale-scale market the intermediate `i128` product overflows first, `mul_div` panics with `MathOverflow`, and — because every pool verb accrues indexes first — `update_indexes`, `withdraw`, `repay`, `liquidate`, `borrow`, and `flash_loan` all revert permanently. The index cap that is supposed to bound growth never engages, so the market is frozen forever at index values well below the cap.

### Finding Description
Interest accrual in the pool cache scales share quantities back to value with `x * index / RAY` arithmetic (`scaled_to_original`, invoked from `update_supply_index`/`update_borrow_index` in `contracts/pool/src/cache/scale.rs`). The in-repo stress test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs` (`a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`) demonstrates that with a large 18-decimal market (~10⁹ whole tokens supplied) at ~98% utilization on the XLM rate curve, the stored `borrow_index` is still far below `MAX_BORROW_INDEX_RAY` when `scaled_to_original` overflows `i128` and panics with `GenericError::MathOverflow` (`#33`). The `MAX_BORROW_INDEX_RAY`/`MAX_SUPPLY_INDEX_RAY` constants are calibrated to bound the *index*, but the actual overflow happens in the *value* computation `shares × index`, so the effective ceiling is `i128::MAX / total_shares` — a bound that shrinks as the market grows and is not the constant the code checks against. Once crossed, every subsequent accrual re-overflows: `try_withdraw_raw` and `try_repay` both fail with `MATH_OVERFLOW` in the test.

### Impact Explanation
Permanent freezing of all funds in the affected market: suppliers cannot withdraw, borrowers cannot repay, and liquidators cannot liquidate, because accrual runs at the top of every verb and deterministically panics. Bad-debt cleanup (`clean_bad_debt`/`recapitalize`) accrues too, so there is no recovery path. The test asserts `borrow_index < MAX_BORROW_INDEX_RAY` at failure, proving the configured cap never fires — the panic boundary, not the documented bound, governs.

### Likelihood Explanation
An unprivileged attacker reaches this with ordinary entrypoints: `supply` a very large amount of an 18-decimal, high-utilization market, `borrow` ~98% of it, then let per-millisecond accrual compound (or nudge it via `update_indexes`, which is permissionless). The preconditions are a whale-scale position and sustained high utilization on a steep rate curve — economically expensive but requiring no privilege, no leaked key, and no misconfiguration; caps must simply be lifted/high enough to admit the position, which `lift_caps` shows is within configured parameters. Likelihood is constrained by the capital and accrual time required, but once triggered the freeze is irreversible.

### Recommendation
Make the effective bound explicit instead of relying on the index constants: in `update_borrow_index`/`update_supply_index`, clamp the index to `min(cap, i128::MAX / total_shares)` *before* calling `scaled_to_original`, or compute the accrual via the widened `I256` path and saturate the index at the largest value that keeps `scaled_to_original` inside `i128` for the current `total_shares`. Alternatively cap share growth itself (`UNCONSTRAINED_CAP`-style bound at supply time) so `shares × MAX_BORROW_INDEX_RAY` can never overflow. Fix `docs/reference/formulas.md` which, per the test's own comment, states a bound that is wrong.

### Proof of Concept
The repo already contains an executable demonstration in `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`:

1. Build a market `BIG18` (18 decimals, `xlm_curve`) plus collateral market `COL`, with caps lifted.
2. `t.supply_raw(BOB, "BIG18", BILLION * 10i128.pow(18))`, then `t.borrow_raw(ALICE, "BIG18", 98% of principal)`.
3. Advance ledger time in yearly steps calling `try_update_indexes_for(["BIG18"])` — a permissionless call — until it returns `Err`.
4. The failure is `errors::MATH_OVERFLOW` thrown inside `scaled_to_original` during accrual, while `book.borrow_index < MAX_BORROW_INDEX_RAY` (cap never engaged).
5. Afterwards `try_withdraw_raw(BOB, "BIG18", 1)` and `try_repay(ALICE, "BIG18", 1.0)` both fail with `MATH_OVERFLOW` — the market is permanently frozen, consistent with the certora note that `update_supply_index` panics with `MathOverflow` once `supplied × old_index / RAY` leaves `i128` (`certora/common/spec/rates_rules.rs:316-320`).

This mirrors the advisory: a wrong/insufficient bound on a length/scale constant makes the operation panic on out-of-range arithmetic, except here the panic is not a one-shot revert — it permanently bricks every entrypoint that accrues the market.
