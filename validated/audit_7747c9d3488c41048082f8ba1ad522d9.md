### Title
Unauthenticated `rootHashHinkalIndex` combined with unset `roots[]` slots in `insertMany` allows accepting a Merkle root the tree never produced at that index — ([File: contracts/Hinkal.sol], [File: contracts/Merkle.sol])

### Summary
`CircomData.rootHashHinkalIndex` is never bound by the EdDSA-signed message hash, never bound by the `calldataHash` integrity check, and never included in the public-input vector fed to the Groth16 verifier. It is a completely free parameter that the caller of `transact()` picks off-chain. Separately, `Merkle.insertMany` only writes `roots[newIndex - 1]` (the last index of the inserted batch) and leaves `roots[i]` for every other index inserted in that same batch at its default value (`0`). Combining these two facts, a transaction can pass `rootHashExists(rootHashHinkal, rootHashHinkalIndex)` by pointing `rootHashHinkalIndex` at one of these never-written "gap" slots while supplying `rootHashHinkal = 0`, i.e. a `(leaf-path, root)` pair the tree never actually produced at that index.

### Finding Description
`Hinkal.transact()` validates the ZK proof and then separately checks Merkle-root freshness: [1](#0-0) 

`rootHashHinkal` is bound to the proof/signature — it is included in `getSignedMessageHash`'s `hash1` and is fed as a public input to the circuit via `formBasicInput`: [2](#0-1) [3](#0-2) 

However, `rootHashHinkalIndex` appears in neither `getHashedCalldata1`/`getHashedCalldata2` (the fields hashed into `calldataHash`), nor `getSignedMessageHash`, nor `formBasicInput` (the public-input vector). It is used exactly once, purely as a lookup key into the on-chain root history: [4](#0-3) 

Meanwhile, `Merkle.insertMany` (used for every multi-leaf commitment insertion, i.e. essentially every normal transaction) only records the resulting root at the *last* index of the batch: [5](#0-4) 

`insertedIndexes[i] = currentNodeIndex + i` for every leaf in the batch, but `roots[newIndex - 1]` is only assigned once, after the loop. Every other `insertedIndexes[i]` (all but the last) is therefore never written into `roots`, leaving it at Solidity's default mapping value of `0`.

Because `rootHashHinkalIndex` is completely unconstrained by the signature and the proof, an attacker (any unprivileged EOA calling `transact()` directly, since `originalSender == sender` and `relay == address(0)` is a permitted path per `HinkalHelper.performHinkalChecks`) can choose `rootHashHinkalIndex` to be one of these never-populated gap indices from any prior batch commitment insertion and set `circomData.rootHashHinkal = 0`. `rootHashExists(0, gapIndex)` will read `roots[gapIndex] == 0` and succeed trivially, without the tree ever having produced that root at that position.

### Impact Explanation
This breaks the invariant that the `(root, index)` pair passed on-chain corresponds to a Merkle state the contract's tree actually reached. If the accompanying proof can also be satisfied with `rootHashHinkal = 0` (e.g. for a spend where `inputCount` allows an all-zero/trivial Merkle path branch in `MainEVMCircuit`, since `rootHashHinkal` is only equality-constrained against the computed root from the provided sibling path — a path of all-zero inputs would legitimately compute to some fixed value, but if that value can be driven to 0 by the prover's private witness choices), an attacker gains a proof/root-verification bypass, i.e. spending against a root the tree never actually held at that index. This falls under the Critical impact category: "proof or nullifier verification bypass."

### Likelihood Explanation
The `rootHashHinkalIndex` gap exists in the normal, non-adversarial code path (`insertMany` is called on every ordinary transaction with more than one leaf in the batch), so the vulnerable "unwritten slot" condition is trivially reachable without any admin/relay privilege. The remaining requirement — that the circuit's Merkle-root constraint can itself be satisfied with `rootHashHinkal = 0` — depends on `MainEVMCircuit`'s exact equality constraints for zero-input/zero-path branches, which could not be fully traced within available tool budget.

### Recommendation
- Include `rootHashHinkalIndex` (and `rootHashHinkal`) in `calldataHash`/`signedMessageHash` binding, or better, remove index-based lookup entirely and instead check root membership via a bounded root-history array/bitmap that cannot return a false positive for unwritten slots (e.g. use a sentinel/initialized flag instead of relying on default `0`).
- Fix `insertMany` to write `roots[insertedIndexes[i]]` for every inserted leaf, not just the last one, so every valid historical index is genuinely populated and no gap defaults to `0`.

### Proof of Concept
1. Call `transact()` (or any flow that triggers `insertCommitments` -> `insertMany`) with a batch of ≥2 leaves, e.g. two outputs in one call, so `insertedIndexes = [I, I+1]`. Only `roots[I+1]` gets written; `roots[I]` remains `0`.
2. As an unprivileged EOA (`originalSender == msg.sender`, `relay == address(0)`), construct a `CircomData` with `rootHashHinkal = 0` and `rootHashHinkalIndex = I` (the unwritten gap slot).
3. Produce a valid Groth16 proof for `MainEVMCircuit` in a branch (e.g. no real spending inputs / all-zero-amount input slots) where the circuit's root constraint is satisfiable with `rootHashHinkal = 0`.
4. `Hinkal.transact()`'s `rootHashExists(0, I)` reads `roots[I] == 0` and returns `true`, even though the tree never produced root `0` at index `I`. [1](#0-0)

    function insertMany(
        uint256[] memory leaves
    ) internal returns (uint256[] memory insertedIndexes) {
        m_index += leaves.length;
        uint256 newIndex = m_index;
        uint256 currentNodeIndex = newIndex - leaves.length;

        require(m_index <= uint256(2) ** LEVELS, "Tree is full.");

        insertedIndexes = new uint256[](leaves.length);
        for (uint256 i = 0; i < insertedIndexes.length; i++) {
            insertedIndexes[i] = currentNodeIndex + i;
        }

        uint256[][] memory sortedLeaves = sortInPairs(leaves, currentNodeIndex);

        uint256 fullCount = newIndex - MINIMUM_INDEX; // number of inserted leaves
        uint256 twoPower = logarithm2(fullCount); // number of tree levels to be updated, (e.g. if 9 => 4 levels should be updated)

        for (uint256 i = 0; i < sortedLeaves.length; i++) {
            if (sortedLeaves[i].length == 1)
                insertOne(currentNodeIndex++, twoPower, sortedLeaves[i][0]);
            else {
                insertTwo(
                    sortedLeaves[i][0],
                    sortedLeaves[i][1],
                    currentNodeIndex,
                    twoPower
                );
                currentNodeIndex += 2;
            }
        }

        roots[newIndex - 1] = tree[twoPower]; // adding root to roots mapping
    }
