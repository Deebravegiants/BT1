This confirms the vulnerability class: the webhook HMAC signs only the raw body, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` fields — which are the identity fields the handler acts on — are taken from unauthenticated headers.

### Title
Webhook `shop-domain` header is trusted for tenant identity without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` only proves that the *body* bytes were signed by Shopify with the app's `api_secret_key`. It proves nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` values, which are read directly from HTTP headers and passed uninspected into the handler.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
``` [1](#0-0) 

`Utils::HmacValidator.validate` recomputes the HMAC over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns `@raw_body` only: [3](#0-2) 

while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers that are never included in the signed payload: [4](#0-3) 

These unauthenticated fields are then forwarded directly into the handler as trusted tenant identity:
```ruby
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [5](#0-4) 

The identity binding that should hold is: `shop authenticated by HMAC == shop the handler acts on`. Because the HMAC covers only the body, this equality is not enforced — the header-derived `shop` is unauthenticated relative to the cryptographic proof. Any request with a body+HMAC pair that was legitimately produced by Shopify (i.e., a genuine webhook delivered to the app for *some* shop using this app's shared `api_secret_key`) can be replayed with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header swapped to a different shop, or with `shopify-topic`/`shopify-webhook-id` altered, and `Utils::HmacValidator.validate` will still pass because it only re-derives the HMAC from the untouched body bytes.

### Impact Explanation
This breaks the tenant boundary the gem is documented to enforce for webhook processing: an unprivileged actor who can capture or receive one legitimate webhook delivery (e.g., by installing the same multi-tenant app on their own shop, which is normal, unprivileged app-install behavior, and observing webhooks Shopify sends them) can forge the shop attribution of that webhook to any other shop, and can also freely retarget `topic`/`webhook_id`/`api_version`. Host applications built on this gem's `WebhookMetadata` typically use `shop` to select which tenant's record to update (e.g., process an `orders/create` payload "as" a different merchant). This is a cross-tenant confusion vulnerability rooted in this gem's own signature-verification design, not merely a documented API being misused by the host app — the gem hands the host an already-"verified" request whose only truly authenticated field is the raw body.

### Likelihood Explanation
Medium-High: exploitation requires only (1) the ability to receive one legitimate webhook for the shared `api_secret_key` (trivial for any merchant who installs the target app on their own store — no privileged credentials needed) and (2) the ability to POST a crafted HTTP request with modified headers to the app's public webhook endpoint (also unprivileged). No access token, `client_secret`, or TLS interception is required.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the signed/verified payload, or otherwise cryptographically bind them to the body before trusting them — e.g., verify the HMAC over a canonical string that incorporates these header values, or require the host application to independently look up/verify the shop by a value derived from data that is inside the signed body rather than headers.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop and receives one
#    legitimate webhook delivery from Shopify:
#    headers:
#      x-shopify-topic: "orders/create"
#      x-shopify-hmac-sha256: "<valid-hmac-of-body>"
#      x-shopify-shop-domain: "attacker-shop.myshopify.com"
#      x-shopify-webhook-id: "..."
#    body: '{"id":1,...}'   # HMAC is valid for this exact body

# 2. Attacker replays the exact same body + hmac header, but swaps the
#    shop-domain header to a victim shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => "<same-valid-hmac-of-body>", # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "forged-id",
}
request = ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)

# 3. HmacValidator.validate(request) still returns true because it only
#    hashes @raw_body, never the shop-domain header:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The host app now processes attacker-controlled data attributed to victim-shop.
```
