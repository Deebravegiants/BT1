Investigation confirms a split result: `wallet.addSeed` **is** properly protected, but `wallet.updateSeed` is **not**.

- `addSeed` calls `#assertWalletIsUnlocked()` as its first statement [1](#0-0) , and this is proven by an existing test that asserts `addSeed` rejects with `/locked/` immediately after `wallet.lock()` [2](#0-1) . So the specific scenario posed in the question (`create()` → `lock()` → `addSeed()`) does **not** reproduce a vulnerability — the guard works as intended.
- However, `wallet.updateSeed` has **no** call to `#assertWalletIsUnlocked()` at all, unlike `addSeed` and `removeManySeeds`, which both call it before mutating state [3](#0-2) [4](#0-3) . It's directly exposed via the wallet API/RPC surface with no wrapper adding a lock check [5](#0-4) .

### Title
`wallet.updateSeed` mutates `seedMetadataAtom` while wallet is locked, missing `#assertWalletIsUnlocked` guard - ([File: features/wallet/module/wallet.js])

### Summary
`Wallet#updateSeed` directly writes to `#seedMetadataAtom` without first checking `#isLocked`, unlike sibling methods `addSeed` and `removeManySeeds` which both call `#assertWalletIsUnlocked()`. An unprivileged RPC caller can invoke `wallet.updateSeed({ seedId, label })` immediately after `wallet.lock()` (or before any `unlock()`), successfully mutating persisted seed metadata while the wallet is locked.

### Finding Description
`updateSeed` is defined as:
```js
updateSeed = async ({ seedId, label }) => {
  assert(seedId, 'missing seedId to update seed metadata')
  assert(label, 'missing label to update seed metadata')

  await this.#seedMetadataAtom.set((previous) => ({
    ...previous,
    [seedId]: { ...previous[seedId], label, dateUpdated: this.#clock.now() },
  }))
}
``` [3](#0-2) 

Compare this to `addSeed`, `removeManySeeds`, both of which begin with `await this.#assertWalletIsUnlocked()` [6](#0-5) [7](#0-6) . `#assertWalletIsUnlocked` reads `#isLocked` (set `true` in `lock()` and `false` in `unlock()`) and throws `'wallet is locked'` when locked [8](#0-7) , [9](#0-8) .

`updateSeed` is exposed unmodified on the public wallet API surface (`features/wallet/api/index.js`), so any caller with access to the wallet API/RPC (an unprivileged origin/dapp bridge invoking `exodus.wallet.updateSeed`) can call it directly whether the wallet is locked or unlocked [5](#0-4) . There is no origin/permission check inside `updateSeed` itself, and no other layer in this repo adds a lock check before delegating to it.

### Impact Explanation
This allows unauthorized mutation of persisted wallet state (`seedMetadataAtom`, backed by storage) while the wallet is locked, violating the "locked means locked" invariant explicitly enforced elsewhere in the same module (`addSeed`, `removeManySeeds`). This matches the "metadata mutation while locked" scoped impact called out in the question. It does **not** disclose secrets, enable signing, or bypass authentication — the mutated data is just a display label/`dateUpdated` timestamp — so the impact is limited to unauthorized state mutation, not key/secret compromise.

### Likelihood Explanation
Trivially reproducible: no special preconditions beyond a `seedId` (which is exposed via `getSeedMetadata`/`getPrimarySeedId` or is otherwise not secret) and the ability to call the wallet API/RPC method, which by design is meant to be usable pre-unlock in some flows. No privileged state, keys, or social engineering needed.

### Recommendation
Add `await this.#assertWalletIsUnlocked()` as the first statement in `updateSeed`, consistent with `addSeed` and `removeManySeeds`.

### Proof of Concept
```js
it('does not allow updating seed metadata while wallet is locked', async () => {
  await wallet.create()
  await wallet.unlock()
  const seedId = await wallet.addSeed({ mnemonic: otherMnemonic, label: 'Metamask Savings' })
  await wallet.lock()

  await expect(
    wallet.updateSeed({ seedId, label: 'Attacker-controlled label' })
  ).rejects.toThrow(/locked/)

  const metadata = await seedMetadataAtom.get()
  expect(metadata[seedId].label).toBe('Metamask Savings')
})
```
Expected today: this test **fails** because `updateSeed` succeeds and mutates `seedMetadataAtom` even while `wallet.isLocked()` is `true`, demonstrating the missing lock guard.

Note: the `addSeed` scenario described in the question (`create()` → `lock()` → `addSeed()`) is already correctly guarded and rejects with `'wallet is locked'` per existing test coverage [2](#0-1) ; no vulnerability exists there.
