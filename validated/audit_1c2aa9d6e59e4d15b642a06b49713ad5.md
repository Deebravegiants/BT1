### Title
Uniswap V2 spot-price manipulation in `EvmHost.dispatch()`/`fundRequest()` native-fee swap enables fee-token theft and dispatch griefing - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all convert native `msg.value` into the protocol `feeToken()` by calling `IUniswapV2Router02.swapETHForExactTokens` directly against the live, spot-priced Uniswap V2 pool configured in `_hostParams.uniswapV2`, with no TWAP, oracle cross-check, or slippage/price-deviation guard. Any unprivileged account that dispatches a POST/GET request or funds an existing request with native token pays a price set entirely by the pool's instantaneous reserves, which a same-block manipulator can move arbitrarily.

### Finding Description
In the dispatch paths: [1](#0-0) 
and in `fundRequest`: [2](#0-1) 
the host swaps `msg.value` of native token for an exact amount of `feeToken()` (`post.fee` / `get.fee` / `amount`) using `swapETHForExactTokens`, sourcing the exchange rate solely from the configured Uniswap V2 pair's current reserves — the same unprotected reserve-based pricing pattern flagged in the referenced Olympus/Sherlock report (`getTokenPrice` computing price from live reserves with no TWAP). The docs for the analogous `HyperApp.quote()` off-chain estimator explicitly acknowledge this class of risk ("uses Uniswap's `getAmountsIn`, making it vulnerable to sandwich attacks... do not call `quote()` in smart contract transactions"), confirming the team is aware `getAmountsIn`/reserve-derived swaps on this router are manipulable — yet the on-chain `dispatch`/`fundRequest` swap paths that unprivileged users actually execute with real funds carry no equivalent protection (no `amountInMax`, no minimum-out/maximum-in bound beyond `msg.value`, no oracle sanity check).

Any account can flash-loan/self-trade against the configured WETH/feeToken Uniswap V2 pool immediately before calling `dispatch{value: ...}` or `fundRequest{value: ...}` in the same block, skewing reserves so that:
- The ETH cost of acquiring the fixed `post.fee`/`get.fee`/`amount` feeToken output is inflated or deflated at will.
- Since `swapETHForExactTokens` refunds unspent ETH to the caller of the swap — which is `EvmHost` itself (it calls the router, not the original `_msgSender()`) — any manipulation that reduces or increases the actual ETH consumed relative to what the dispatching user provided does not get reconciled back to that user; the host either reverts (if the manipulated price exceeds `msg.value`, griefing legitimate dispatchers/relayer-fee funders) or silently retains any refunded ETH rather than returning it to `_msgSender()`.

### Impact Explanation
This is reachable by any unprivileged message dispatcher (anyone calling `IDispatcher(host).dispatch{value:...}(...)` per the documented `HyperApp` usage pattern) or by anyone funding an in-flight request's relayer fee via `fundRequest`. An attacker who manipulates the pool can:
1. Grief legitimate dispatch attempts by pricing the required feeToken fee artificially high relative to the sender's provided `msg.value`, causing reverts and preventing message dispatch (denial of the messaging path) at the moment of manipulation.
2. Extract value by manipulating the pool in their own favor before their own dispatch/fundRequest call, effectively obtaining `feeToken()` (the protocol's relayer-fee asset) at a manipulated, below-market native-token cost, which is a direct value-extraction vector against the swap counterparties (the AMM's other LPs, but funded implicitly at the expense of ETH the protocol itself expected to spend for the fee it commits to relayers) — the relayer fee amount (`post.fee`) recorded on-chain is fixed and paid out regardless of how cheaply the host acquired it, so the effective bounty economics anchoring relayer incentives can be undermined per-transaction.

This satisfies "a route unable to deliver messages" (griefing dispatch) and value-extraction criteria for the messaging/fee-accounting surface.

### Likelihood Explanation
Medium likelihood: exploitation requires the attacker to control (or be able to move) the Uniswap V2 pool paired for the host's `feeToken()`/WETH, which is feasible on any pool with moderate-to-low liquidity via a single large swap or flash loan within the same block as the victim's `dispatch`/`fundRequest` transaction (classic sandwich/flash-loan price manipulation), requiring no privileged role — matching the "unprivileged dispatcher" reachability required by scope.

### Recommendation
Do not derive the native-to-feeToken exchange rate from the live Uniswap V2 pool's spot reserves inside `dispatch`/`fundRequest`. Options:
- Require callers to supply the feeToken amount directly (already supported) and deprecate/remove the native-swap convenience path, or
- Bound the swap with a TWAP-derived or Chainlink-oracle-verified maximum acceptable native input (`amountInMax`) rather than trusting `msg.value` as the only ceiling, reverting on excessive deviation from the reference price, and
- Refund any unspent native token back to `_msgSender()` (not silently retained by `address(this)`) after the swap.

### Proof of Concept
1. Attacker identifies the Uniswap V2 pair configured as `_hostParams.uniswapV2` for `feeToken()`/WETH on the target EVM chain.
2. Attacker executes a large swap (optionally via flash loan) against that pair to skew reserves, making feeToken artificially cheap in ETH terms.
3. In the same block, attacker calls `IDispatcher(host).dispatch{value: v}(DispatchPost{... fee: F ...})` (per `evm/src/core/EvmHost.sol` lines 921-932); `swapETHForExactTokens` executes at the manipulated price and acquires `F` feeToken for far less ETH than the fair-market rate, with any unspent ETH retained by the host contract rather than refunded to the attacker/dispatcher.
4. Attacker reverses their initial swap to restore the pool and realize profit from the price differential, having obtained the protocol's fee-token commitment cheaply. Alternatively, an attacker griefs a victim's pending `dispatch`/`fundRequest{value:...}` call by pushing the price the other direction so the victim's provided `msg.value` becomes insufficient and their transaction reverts.         if (msg.value > 0) {
