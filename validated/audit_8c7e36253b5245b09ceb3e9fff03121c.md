### Title
Webhook HMAC signs only the raw body, letting an attacker replay a legitimate payload under a spoofed `shop-domain`/`topic` header for cross-tenant impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC that `Utils::HmacValidator.validate` checks in `Registry.process` never covers the `shop-domain`, `topic`, or `webhook-id` headers. Any actor who legitimately receives one signed webhook (by simply installing the app on their own, unprivileged shop) can replay that exact body+HMAC pair to the app's shared webhook endpoint while substituting a different `shop-domain` header, and the gem will treat it as an authentic webhook for the victim shop/topic.

### Finding Description
`HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw body: [2](#0-1) 

The `shop`, `topic`, and `webhook_id` accessors, however, are read straight from HTTP headers and are never part of the signed bytes: [3](#0-2) 

`Registry.process` validates only the body HMAC, then uses the *unauthenticated* `request.topic` to select the handler and forwards the *unauthenticated* `request.shop` into `WebhookMetadata`, which is the value host applications typically use to scope the mutation to a tenant: [4](#0-3) 

The identity binding that should hold is: `shop header used for tenant dispatch == shop bound by the signature`. Because the signature covers only the body, this equality does not hold — `shop`/`topic` can be swapped freely on any previously-observed valid `(body, hmac)` pair without invalidating the HMAC check.

### Impact Explanation
An unprivileged actor who installs the target app on their own store receives real webhooks (valid body + HMAC) addressed to the app's shared webhook endpoint. By resending that exact body/HMAC with the `shop-domain` header rewritten to a victim shop's domain (and/or the `topic` header rewritten to a more sensitive topic such as `customers/redact` or `app/uninstalled`), the request still passes `HmacValidator.validate`, and `Registry.process` dispatches the handler believing the event originates from and pertains to the victim shop. Any host application that trusts `WebhookMetadata#shop` for tenant scoping (the documented/expected usage) can be made to perform actions against the wrong tenant's data — a cross-tenant access impact.

### Likelihood Explanation
Reaching this path requires no access token, `api_secret_key`, or privileged account: any actor can install the app on a shop they control and capture one legitimate webhook delivery to their own endpoint config, then replay it against the app's public webhook receiver with edited headers. No TLS interception or credential theft is needed since the attacker's own shop's webhook is data they are entitled to receive.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` in the HMAC-signed material (or otherwise bind them cryptographically to the body), so that these headers cannot be swapped independently of the signed payload. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop and topic headers before the signature is validated in `Registry.process`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and configures/observes a webhook delivery to the app's HTTP endpoint, capturing the raw body `B` and header `x-shopify-hmac-sha256: H` (a valid signature for `B` under the app's `api_secret_key`).
2. Attacker sends a POST to the same webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` unchanged, but `x-shopify-shop-domain: victim-shop.myshopify.com` and `x-shopify-topic: customers/redact` (or any other registered topic).
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers, `HmacValidator.validate` succeeds because it only recomputes the HMAC over `B`, and `Registry.process` calls the `customers/redact` handler with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, causing the host app to act on the victim tenant using attacker-controlled body content.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
