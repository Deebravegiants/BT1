### Title
Webhook `shop` (and `topic`/`webhook_id`) header values are not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing on an otherwise validly-signed webhook - (File: `lib/shopify_api/webhooks/registry.rb`, `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` returns true, and then hands `request.shop` straight to the app's handler via `WebhookMetadata`. The HMAC, however, is computed only over the raw request body, not over the `shop-domain`, `topic`, or `webhook-id` headers, so those fields carry no cryptographic binding to the signed payload.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` verifies the HMAC solely against that signable string: [2](#0-1) 

`Registry.process` accepts the request purely on this body-only HMAC check, then forwards `request.shop` (an unauthenticated header) to the handler: [3](#0-2) 

`Request#shop`/`#topic`/`#webhook_id` are read directly from HTTP headers with no validation against the signed body: [4](#0-3) 

The binding that should hold is: `hmac == HMAC(secret, shop ‖ topic ‖ webhook_id ‖ body)`, i.e. the tenant identity (`shop`) should be part of what the signature authenticates. Instead the actual binding implemented is `hmac == HMAC(secret, body)`, i.e. `shop` is authenticated as "any value the sender chose to put in the header," not "the shop Shopify actually sent this event for." Before vs. after: before the request arrives, an attacker who can produce (or replay/capture) any legitimately-signed webhook body (e.g., from their own installed test shop, or one where the body/HMAC pair is otherwise observable) can resend it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop's domain; after processing, `HmacValidator.validate` still returns `true` (because it only checked the body), and the handler receives `data.shop == victim-shop.myshopify.com` even though that shop never sent the event.

This directly mirrors the reported bug class: a field (`shop`) that is acted upon (used as the tenant/session key by the handler) is not covered by the identity-binding check (HMAC), so the "authenticated shop" and the "shop actually associated with the signed bytes" can diverge.

### Impact Explanation
Downstream applications are documented to key their tenant logic directly off `data.shop` (see `docs/usage/webhooks.md`, where the example handler does `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`). Because the gem asserts the webhook is "verified" once HMAC passes, but `shop` is not part of what was verified, an attacker can cause the host application to process/attribute webhook data (order, GDPR, app-uninstall, product, etc. events, and their bodies) under an arbitrary victim shop identity of the attacker's choosing. Depending on how the host app uses `data.shop` (e.g., looking up which merchant's access token/session to act on, writing records keyed by shop, triggering per-tenant side effects), this can result in cross-tenant data confusion/write attribution — impact classified as cross-tenant access per the rules.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one validly-signed `(body, hmac)` pair — which is trivial to obtain since HMAC-signed webhook payloads are delivered over plaintext-visible HTTP POSTs to the app's public callback endpoint and the same secret is shared for all shops. An attacker who has their own shop install the app (a normal, unprivileged action available to anyone) can generate arbitrarily many valid `(body, hmac)` pairs for controlled bodies (via controlled test-shop resource content), then replay that exact body+hmac with a forged `shop-domain` header pointed at any other shop, since the gem never checks `shop` against the signature. No access token, `client_secret`, or privileged access is needed — only the ability to reach the app's public webhook endpoint, which is the whole point of webhooks.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` header values as part of the HMAC-signed material in `Webhooks::Request#to_signable_string` (or otherwise separately re-verify/bind them), instead of computing the signature over the raw body alone. Concretely, `to_signable_string` should incorporate the header values that the handler is going to rely on, or `Registry.process`/`HmacValidator` should reject the request if the shop domain isn't cryptographically tied to the payload. At minimum, documentation should make explicit that `data.shop` is **not** authenticated by the HMAC check and must not be trusted for tenant-scoping without an independent verification (e.g., cross-checking against a stored session for that webhook subscription/shop).

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimately Shopify-signed webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (where `H = HMAC-SHA256(api_secret_key, B)`), and header `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends an HTTP POST to the victim app's public webhook endpoint with the same body `B` and same `H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. In `Registry.process`, `Utils::HmacValidator.validate(request)` succeeds because it only recomputes `HMAC(secret, B)` and compares to `H`: [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, i.e., the app processes attacker-controlled body content under the victim shop's identity: [3](#0-2)
