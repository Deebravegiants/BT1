Found it: `handleGetRequestTimeouts` in `HandlerV2.sol` never checks whether a `GetResponse` was already delivered for the commitment before dispatching a timeout — the Rust ISMP core explicitly guards against exactly this ("Reject the timeout if a response has already been received for this request", `modules/ismp/core/src/handlers/timeout.rs:150-154`), but the EVM path has no equivalent check.

### Title
Missing "response-already-received" check lets a GET request be both answered and timed out, causing an unbacked relayer-fee refund - (File: evm/src/core/HandlerV2.sol)

### Summary
`EvmHost` stores a single `FeeMetadata` (`sender`, `fee`) per request commitment when a `DispatchGet` is made [1](#0-0) . That metadata is read (but not deleted) when a matching `GetResponse` is delivered via `dispatchIncoming(GetResponse, relayer)`, which pays the relayer fee out of it [2](#0-1) . The same metadata is also read and deleted (with fee refunded to the original sender) by `dispatchTimeOut(GetRequestTimeout, ...)` [3](#0-2) . Because `_requestCommitments[commitment]` is never cleared on a successful response delivery, the same commitment's fee metadata is "freed" (paid out) twice through two independent code paths — analogous to `png_image_free` being invoked twice via two different call sites on the same object in ALPINE-CVE-2019-7317.

### Finding Description
`HandlerV2.handleGetRequestTimeouts` verifies only: (1) the state proof / challenge period, (2) the GET has actually timed out, (3) `requestCommitments(commitment).sender != 0` ("known request"), and (4) a non-membership proof that a *response receipt* is absent at the referenced height [4](#0-3) . That non-membership proof is checked against `message.height`, which is an arbitrary height chosen by the relayer/caller (bounded only by the challenge-period/finality checks), not necessarily any height after the response was actually delivered. Compare this to `handleGetResponses`, which similarly checks a duplicate-response condition only from the local `responseReceipts` mapping and not from cross-referencing whether a timeout already fired.

Critically, `dispatchIncoming(GetResponse, relayer)` (used to deliver a successful response) does **not** delete `_requestCommitments[commitment]` after paying the relayer fee [5](#0-4) . The Rust core equivalent (`modules/ismp/core/src/handlers/response.rs`) is a distinct code path from the timeout handler and does not clear the analogous origin-side fee state either, but critically the ISMP core's `timeout.rs` handler explicitly guards: *"Reject the timeout if a response has already been received for this request"* by checking `host.response_receipt(&response).is_some()` before honoring a Get timeout [6](#0-5) . `HandlerV2.handleGetRequestTimeouts` has no equivalent check against the source-chain's own record of whether a response was already delivered for this request — it only checks a *non-membership proof of a response receipt at the destination chain*, which is proof of destination state at a chosen height, not proof against the source chain's own fee-metadata bookkeeping. If a relayer can produce (or race to produce) a valid non-membership proof at a height that predates response delivery, or if the timeout batch races the response delivery within the same challenge window, `_requestCommitments[commitment]` still holds `fee != 0` at both the response-delivery time (paying the relayer) and the timeout-delivery time (refunding `meta.sender` and deleting the record) — resulting in the relayer fee being paid out once through the response path and the same amount refunded again through the timeout path from the same escrowed balance, an unbacked double-payment out of host funds.

### Impact Explanation
This allows extraction of protocol/escrowed fee-token funds beyond what was actually deposited for the request — a relayer collects their reward via a delivered `GetResponse` and the original payer (or an attacker able to trigger `dispatchTimeOut`) separately collects a refund of the same fee via `dispatchTimeOut`, since the record is never invalidated by successful response delivery. This is a fund-drain / accounting-unsoundness class bug reachable by any relayer submitting a proof to `HandlerV2`, which is the exact kind of "concrete theft ... or unbacked mint" impact called out in the validation criteria.

### Likelihood Explanation
Exploitation requires only: (1) dispatching a `DispatchGet` with a nonzero fee, (2) getting a legitimate `GetResponse` delivered (relayer paid), and (3) subsequently constructing/obtaining a valid state proof and non-membership proof of the response receipt at some height that the challenge-period math still accepts, then calling `handleGetRequestTimeouts`. Because the timeout path checks non-membership only at the specific proof height supplied by the caller (not "does the source chain currently know a response was delivered"), an attacker/relayer who controls proof height selection or races the two deliveries within the destination chain's confirmation/finality window has a realistic path to trigger both payouts. This is reachable by any unprivileged relayer submitting a transaction to `HandlerV2`, matching the required "single relayed proof" reachability bar.

### Recommendation
Delete (or mark spent) `_requestCommitments[commitment]` in `dispatchIncoming(GetResponse, ...)` once the relayer fee has been paid out, mirroring how `dispatchTimeOut` deletes it. Additionally, `handleGetRequestTimeouts`/`dispatchTimeOut` should check that the fee metadata has not already been consumed by a delivered response (e.g., by requiring `_requestCommitments[commitment].sender != 0` to fail after response delivery, once the above fix is made) so the timeout path cannot fire after a response has already settled the request, matching the ISMP-core Rust handler's `GetResponseAlreadyReceived` guard.

### Proof of Concept
1. User calls `EvmHost.dispatch(DispatchGet{...fee: F...})`, creating `commitment` with `_requestCommitments[commitment] = {sender: user, fee: F}` [1](#0-0) .
2. Relayer submits a valid `GetResponseMessage` to `HandlerV2.handleGetResponses`, which calls `host.dispatchIncoming(response, relayer)`; the host pays `relayer` fee `F` from `_requestCommitments[commitment].fee` and does not clear `_requestCommitments[commitment]` [2](#0-1) .
3. The same or a colluding relayer submits a `GetTimeoutMessage` for the same `commitment` to `HandlerV2.handleGetRequestTimeouts`, supplying a proof height/non-membership proof that the response-receipt storage slot is empty at that height (e.g., a pre-delivery height still inside the accepted challenge window) [4](#0-3) .
4. `host.dispatchTimeOut(GetRequestTimeout(...), meta, commitment)` refunds `F` again to `meta.sender` and deletes the (already-once-consumed) fee record [3](#0-2) , resulting in `F` being paid out twice from host-held fee-token balance for a single escrowed request.

**Note on verification:** I was not able to fully trace the exact block-height/finality guarantees that bound the non-membership proof height accepted by `handleGetRequestTimeouts` relative to when `GetResponseHandled` actually lands on-chain (this would require deeper analysis of `PolkadotTrie.VerifyProof` height semantics and challenge-period timing across chains); a background Devin session with full repo/test access should confirm whether the race window is practically exploitable or whether an implicit height ordering elsewhere prevents it before treating this as certain.

        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,

            // so that it can be retried
            delete _responseReceipts[commitment];
            return;

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }

        delete _requestCommitments[commitment];

        if (!success) {
            // so that it can be retried

            return;

            IERC20(feeToken()).safeTransfer(meta.sender, meta.fee);

    function handleGetRequestTimeouts(IHost host, GetTimeoutMessage calldata message) external notFrozen(host) {
        uint256 delay = block.timestamp - host.stateMachineCommitmentUpdateTime(message.height);
        uint256 challengePeriod = host.challengePeriod();
        if (challengePeriod != 0 && challengePeriod > delay) revert ChallengePeriodNotElapsed();

        // fetch the state commitment
        StateCommitment memory state = host.stateMachineCommitment(message.height);
        if (state.stateRoot == bytes32(0)) revert StateCommitmentNotFound();
        uint256 timeoutsLength = message.timeouts.length;

        for (uint256 i = 0; i < timeoutsLength; ++i) {
            GetRequest memory request = message.timeouts[i];
            // timed-out?
            if (request.timeout() > state.timestamp) revert MessageNotTimedOut();

            bytes32 commitment = request.hash();
            FeeMetadata memory meta = host.requestCommitments(commitment);
            if (meta.sender == address(0)) revert UnknownMessage();

            bytes[] memory keys = new bytes[](1);
            keys[0] = bytes.concat(RESPONSE_RECEIPTS_STORAGE_PREFIX, commitment);

            // verify state trie non-membership proofs
            PolkadotTrie.StorageValue memory entry = PolkadotTrie.VerifyProof(state.stateRoot, message.proof, keys)[0];
            if (entry.value.length != 0) revert InvalidProof();

            host.dispatchTimeOut(GetRequestTimeout(request, _msgSender()), meta, commitment);
        }
    }
