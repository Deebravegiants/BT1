### Title
Webhook HMAC Validation Does Not Bind `shop`/`topic`/`webhook_id` Headers, Enabling Cross-Tenant Webhook Spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and passed straight into the handler as trusted identity data. This breaks the identity binding: `hmac == HMAC(body)` is validated, but `shop_used_by_handler == shop_the_hmac_was_issued_for` is never checked.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are entirely outside the signed content: [2](#0-1) 

`Utils::HmacValidator.validate` only verifies `hmac` against `to_signable_string` (i.e., the body), never touching `shop`/`topic`/`webhook_id`: [3](#0-2) 

`Registry.process` validates the HMAC and then forwards the unverified `request.shop` (and `topic`, `webhook_id`, `api_version`) directly to the app's handler as `WebhookMetadata`: [4](#0-3) 

The gem's own documentation instructs app developers to treat `data.shop` as the authoritative tenant identifier for post-processing (e.g., enqueuing a job keyed by `shop_domain: data.shop`): [5](#0-4) 

This is precisely the asymmetric-binding bug class described in the reference report: a field that is *acted on* (`shop`) is not covered by the same cryptographic check that is used to authenticate the message (`hmac` over `body` only). An unprivileged internet user who obtains any single valid `(raw_body, hmac)` pair signed with the app's secret — for instance, from a webhook legitimately delivered to their own store, which is public/observable to that tenant — can replay that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header (e.g., a victim shop). `HmacValidator.validate` will still return `true` because it never inspects `shop`, so `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain and `body` from the attacker's own legitimate webhook.

### Impact Explanation
Because the library actively documents `data.shop` as the field apps should use to route/store the resulting webhook data per-tenant, this asymmetry lets an attacker cause an app to associate one shop's payload/body with a different shop's identity, i.e., cross-tenant data confusion/injection: forged shop attribution using the app's own valid signing secret without ever needing to compromise that secret. This matches the Critical "cross-tenant access" impact category, since the boundary being crossed is exactly the tenant (shop) isolation boundary that HMAC validation is supposed to enforce.

### Likelihood Explanation
Likelihood is bounded by the need for the attacker to first obtain one genuine `(body, hmac)` pair signed by the target app's `api_secret_key`. This is achievable by any unprivileged user who can install/interact with the app on their own store (or otherwise observe a delivered webhook for a topic/body they control, e.g. `products/update` on their own shop), since that pair is fully valid Shopify-issued webhook data for the attacker's own tenant. No leaked credentials, TLS interception, or privileged access are required — solely observation of one's own webhook traffic plus a replay to the app's public webhook endpoint with a modified `shop-domain` header.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the material that is HMAC-verified, or otherwise independently verify that the `shop-domain` header corresponds to a shop for which this exact `(topic, webhook_id, body)` combination was actually registered/expected (e.g., cross-check against Shopify's `X-Shopify-Webhook-Id` uniqueness log keyed to the claimed shop, or require the consuming app to verify shop identity through a separate authenticated channel before trusting `data.shop`). At minimum, update documentation to explicitly warn that `data.shop` is derived from an unauthenticated header and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs/uses the victim app on their own shop `attacker-shop.myshopify.com` and receives a legitimate webhook for topic `products/update` with body `B` and valid header `x-shopify-hmac-sha256: H = HMAC_SHA256(secret, B)`.
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac: H...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(B) == H`, per [6](#0-5)  and [7](#0-6) .
4. `Registry.process` invokes the handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, per [8](#0-7) , causing the app to process the attacker's own webhook content as if it belonged to the victim shop.
