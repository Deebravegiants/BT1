### Title
External gate in the withdraw/settle path can permanently freeze user funds with no emergency escape - (File: contracts/pool/src/ops/withdraw.rs)

### Summary
`withdraw`, `borrow`, `claim_revenue`, and `SeizeMode::Transfer` liquidation all settle through an unconditional `token.transfer` from the pool. For issuer-gated assets the protocol explicitly supports (Liqvid RWA deal tokens modeled by `tests/test-harness/src/rwa_gated_token.rs`), the token's `transfer` reverts whenever the pool — or the counterparty — falls off the issuer allowlist or is frozen. The protocol has no `emergencyWithdraw`-style escape that skips the token leg or moves value without the gated transfer, so all funds in that market are frozen until an external third party chooses to re-admit the pool. This mirrors the Stargate finding exactly: an external call embedded in the exit path can revert on a state the protocol does not control, and there is no fallback path.

### Finding Description
`Pool::withdraw` reaches `ops::withdraw::apply`, which always ends in `cache.transfer_out(receiver, net_transfer)` — a raw SAC/token `transfer(pool -> receiver)` [1](#0-0) . The only special case is a zero-amount `try_transfer` whose failure is ignored [2](#0-1) . The gated token model requires both `from` and `to` to be allowlisted and unfrozen for `transfer` (zero amounts included), reverting with `AccountNotAllowed`/`AccountFrozen` otherwise [3](#0-2) .

The test `lqv_pool_removed_from_allowlist_after_deposits_blocks_exits_only` demonstrates the lock concretely: after `z.disallow(&z.pool)`, `try_withdraw` reverts and `SeizeMode::Transfer` liquidation reverts; only `SeizeMode::Credit` (share bookkeeping, no token leg) still works [4](#0-3) . Likewise `lqv_revenue_claim_needs_the_controller_and_accumulator_allowlisted` shows `claim_revenue` reverting when the controller/accumulator are not admitted [5](#0-4) . `claim_revenue` forwards tokens via `transfer_amount_measured` and panics if no accumulator is set [6](#0-5) .

There is no emergency exit: the pool has no owner callable "rescue" that bypasses the token leg, `withdraw`/`repay` carry no alternate settlement mode, and the docs' trust table lists no fallback for a reverting asset [7](#0-6) .

### Impact Explanation
Every token unit backing supply positions in a gated market becomes unwithdrawable the moment the issuer removes the pool (or freezes it) from its allowlist — all user collateral in that market is frozen for as long as the external gate stays closed, and Transfer-mode liquidations of bad debt in that collateral also stop, blocking the only remaining path to deleverage underwater accounts (Credit mode moves shares but the receiver still cannot exit). Unclaimed protocol revenue in the gated asset is likewise unclaimable. This matches the report's "deposit/withdraw reverts → staked funds locked" shape: the revert lives in an external call on the mandatory settlement path, and the protocol lacks the analog of Stargate's `emergencyWithdraw`.

### Likelihood Explanation
The trigger is external (issuer allowlist/freeze decision), identical in nature to the Stargate report's reliance on `set(0, 0)` by the staking admin. The protocol deliberately lists such gated collateral (dedicated harness, live integration script `tests/integration/live/liqvid_liquidation_live.py`), so the dependency is a real supported configuration, not hypothetical. The condition requires no attacker action and is reversible only at the issuer's discretion — a Medium-severity conditional fund freeze, same severity class as the source finding.

### Recommendation
Add an emergency settlement mode for exits that does not route through the gated token's `transfer` — e.g., an issuer-or-governance-flagged "credit-only" market state where `withdraw` burns supply shares and settles the claim internally (or to an allowlisted escrow/nominee), and liquidation is restricted to `SeizeMode::Credit`, so positions remain unwindable without the external call. Short of that, `claim_revenue` could tolerate a reverting forward leg (already partially guarded by measured receipt) and `withdraw` could offer an opt-in `SeizeMode::Credit`-style exit to a second account of the same owner. At minimum, document the dependency and gate listing of gated assets behind an explicit risk flag acknowledging the freeze window.

### Proof of Concept
1. Governance lists an issuer-gated asset (gate active, allowlist enforced on `transfer`, both directions) as a collateral market; the pool is allowlisted.
2. Alice supplies 10 units (`controller::supply`) and borrows against them — `open(z, "alice", 10, 5_800)` in `lqv_pool_removed_from_allowlist_after_deposits_blocks_exits_only`.
3. The issuer removes the pool from the allowlist (`z.disallow(&z.pool)`) — an action entirely outside the protocol.
4. Alice calls `withdraw(caller, account_id, [(key, 1)], None)`; `ops::withdraw::apply` reaches `cache.transfer_out`, the token's `transfer` reverts `AccountNotAllowed`, and the whole call aborts — her shares and the underlying are locked. Transfer-mode liquidation of her now-underwater position reverts identically, so the bad debt cannot be cleared by token settlement either [8](#0-7) . No entrypoint recovers the position without that external transfer, exactly as the Stargate wrapper lacked an emergency path around `_claimAssetRewards`.

Caveat: this rests on treating the issuer-allowlist dependency as in-scope. If the audit policy classifies issuer allowlisting as excluded "token semantics," there is no analogous in-protocol external call on a user exit path — the only other unconditional external calls (`flash_loan` receiver callback and repayment pull, `claim_revenue` accumulator forward) are either self-inflicted or admin-reroutable — and the finding should be rejected.

pub(crate) fn apply(

    receiver: &Address,
    is_liquidation: bool,
    entry: &PoolWithdrawEntry,
) -> (PoolPositionMutation, MarketStateSnapshot) {
    let outcome = accounting(env, is_liquidation, entry);

    if outcome.net_transfer == 0
        && (entry.action.position.scaled_amount > 0 || entry.action.amount == i128::MAX)
        && outcome.mutation.position.scaled_amount == 0
    {
        let _ = token::Client::new(env, &outcome.cache.params().asset_id).try_transfer(
            &env.current_contract_address(),
            receiver,
            &0,
        );
    } else {
        outcome.cache.transfer_out(receiver, outcome.net_transfer);
    }
    (outcome.mutation, outcome.snapshot)

/// The issuer removes the pool from the allowlist after deposits: every exit
/// reverts until it is restored, and Credit liquidation still settles.
#[test]
fn lqv_pool_removed_from_allowlist_after_deposits_blocks_exits_only() {
    let mut z = setup(1_000);
    let id = open(&mut z, "alice", 10, 5_800);
    let liquidator = z.user("liquidator");
    z.allow(&liquidator);
    z.disallow(&z.pool.clone());

    assert_eq!(
        z.try_withdraw("alice", id, 1, None),
        Err(contract_error(ACCOUNT_NOT_ALLOWED))
    );
    z.set_unit_price(80_000);
    let debt = z.debt_raw(id);
    assert_eq!(
        z.try_liquidate("liquidator", id, debt, SeizeMode::Transfer),
        Err(contract_error(ACCOUNT_NOT_ALLOWED))
    );
    let receiver = z
        .try_liquidate("liquidator", id, debt, SeizeMode::Credit(0))
        .unwrap();
    assert!(z.units(receiver) > 0);
    z.assert_units_conserved(&[id, receiver]);
}
