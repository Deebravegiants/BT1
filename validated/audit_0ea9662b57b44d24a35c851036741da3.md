### Title
A single invalid/timed-out/duplicate request in a batched `handlePostRequests` (or `handleGetResponses`) call reverts delivery of all other unrelated requests in the same batch - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2.handlePostRequests` and `HandlerV2.handleGetResponses` accept a *batch* of unrelated, independently-dispatched requests/responses (from possibly different senders) proved together in a single MMR multiproof, and loop over every leaf without isolating per-item failures. A single bad leaf (wrong destination, expired timeout, or already-delivered/duplicate) causes the whole call to `revert`, which — being invoked directly or via `IHandlerV2.batchCall`'s atomic delegatecall loop — reverts every other valid, unrelated request bundled in that same transaction.

### Finding Description
`handlePostRequests` iterates `request.requests` twice: first to check `dest` and timeout [1](#0-0) , then after MMR proof verification to check duplicates and dispatch [2](#0-1) . Any single leaf failing `dest` equality, timeout, or duplicate-receipt check triggers `revert InvalidMessageDestination()/MessageTimedOut()/DuplicateMessage()` for the *entire* call, aborting delivery of every other leaf in the batch. `handleGetResponses` has the identical pattern with `UnknownMessage()`/`DuplicateMessage()` [3](#0-2) .

This is reachable by an unprivileged relayer under normal, non-malicious operation: the relayer implementation explicitly groups multiple independent, unrelated `PostRequest`s from different original dispatchers into chunks and submits them as one `RequestMessage`/`handlePostRequests` call, proved once for the whole chunk [4](#0-3)  and [5](#0-4) . The batch-building code (`build_batch_inner_calls`/`generate_contract_calls`) constructs `PostRequestLeaf[]` directly from queried events without any per-leaf pre-filter for expiry/duplicate at the initial (non-retry) dispatch path [6](#0-5) . The retry path (`retries.rs`) does filter via `deliverable_requests`, implying the team is aware that stale/duplicate items are a real risk in batches, but the primary dispatch path does not guard against a race where one request in a chunk times out or gets delivered by a concurrent relayer between proof query and submission.

Additionally, `HandlerV2.batchCall` explicitly documents and tests atomic all-or-nothing semantics (`if (!success) revert BatchCallFailed(...)`) [7](#0-6) , and `testBatchCallRevertsAtomically` confirms a single bad inner call reverts the whole batch, discarding legitimate calls that would otherwise have succeeded [8](#0-7) .

This is directly analogous to the reported `FootiumAcademy.mintPlayers()` bug class: a batch call over a heterogeneous array of independent items where a single invalid element causes complete transaction failure for all valid elements, wasting gas and delaying/denying message delivery.

### Impact Explanation
Because a relayer's batch may contain requests/responses from many different unrelated senders/applications, one adversarial or merely unlucky request (e.g., an attacker deliberately dispatching a request with a very short timeout so it expires by the time the relayer's batch lands, or racing to deliver a duplicate via a separate transaction) can grief the entire batch, causing:
- Denial of delivery for all other, unrelated, valid POST requests / GET responses bundled in the same transaction, delaying cross-chain message delivery (a "route unable to deliver messages" scenario) until the relayer identifies and excludes the bad item and resubmits.
- Wasted gas for the relayer (which may reduce economic incentive to relay reliably) since MMR proof verification runs to completion before the revert.
- Potential recurring griefing: an attacker can repeatedly dispatch short-timeout requests to interleave with the relayer's batching window, stalling honest cross-chain delivery for that destination.

This does not directly cause theft or an unbacked mint, but it can cause a route/relayer to be unable to deliver messages for a time window, meeting the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Likelihood is moderate: the relayer code already batches unrelated events by `chunk_size` per destination in normal (non-adversarial) operation, so any race between proof generation and inclusion (a message timing out or being delivered by a competing relayer between when the batch is built and when it lands on-chain) will trigger this. An attacker can also proactively exploit it by dispatching a request with a timeout deliberately set to expire around the expected relay window, which the relayer's chunking may then bundle. No special privileges are required; only dispatching a normal cross-chain request is needed.

### Recommendation
Modify `HandlerV2.handlePostRequests` / `handleGetResponses` to skip and emit an event for individually invalid leaves (bad destination, timed out, duplicate/unknown) rather than reverting the whole transaction, while still enforcing that skipped leaves are excluded from the MMR-verified leaf set consistently, or split verification/dispatch so a per-leaf `try/catch`-like isolation is possible (e.g., use low-level calls per leaf post-proof-verification and continue on failure). Additionally, harden the relayer's primary dispatch path (not just `retries.rs`) to pre-filter requests for `receipt-already-exists` / `timed-out` before chunking into `handlePostRequests` calls, mirroring `deliverable_requests` used in the retry path.

### Proof of Concept
1. Relayer observes two unrelated `PostRequest`s (A, B) destined for the same chain and same destination-state-machine height and batches them into one `RequestMessage`/`PostRequestMessage` per `events.rs`/`tx.rs` chunking logic.
2. Before the relayer's transaction lands, request A's `timeoutTimestamp` elapses (attacker deliberately set a short timeout on A), or another relayer delivers A first (making its `requestReceipts` entry non-zero).
3. The relayer submits `handlePostRequests(host, {proof, requests: [A, B]})`.
4. In the destination-check loop, `if (timestamp >= leaf.request.timeout()) revert MessageTimedOut();` fires on A's leaf (or `DuplicateMessage()` fires in the dispatch loop) [9](#0-8) .
5. The entire call reverts — B, a perfectly valid and undelivered request, is not dispatched despite its proof being valid, and the relayer must detect A's failure, rebuild the batch without A, and resubmit, wasting gas and delaying B's delivery.

/// Regroup the requests that made it through into batches the destination can
/// take in one call, each proved once for the whole batch.
async fn batch_requests(
	ctx: &RetryContext,
	profitable: &[(PostRequest, Query)],
	height: StateMachineHeight,
) -> Result<Vec<Message>, anyhow::Error> {
	let dest_state_machine = ctx.dest.state_machine_id().state_id;
	let mut messages = vec![];

	for chunk in profitable.chunks(chunk_size(dest_state_machine)) {
		let (requests, queries): (Vec<_>, Vec<_>) = chunk.iter().cloned().unzip();
		let proof = ctx
			.hyperbridge
			.query_requests_proof(height.height, queries, dest_state_machine)
			.await?;

		messages.push(Message::Request(RequestMessage {
			requests,
			proof: Proof { height, proof },
			signer: ctx.dest.address(),
		}));
	}

	Ok(messages)
}
