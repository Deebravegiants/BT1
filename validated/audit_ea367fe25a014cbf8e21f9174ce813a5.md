### Title
On-device fraud detection is permanently disabled, causing unconditional fraud/liveness bypass - ([File: src/plans/mod.rs])

### Summary
The `detect_fraud` function, which is supposed to gate signup finalization on the result of on-device fraud detection, is a stub that unconditionally returns `false`. This means the `fraud_detected` state that should influence `signup_reason` (and consequently the enrollment path taken for a given user) can never actually be set to `true` by the orb's own fraud-detection logic, regardless of what the biometric pipeline observed.

### Finding Description
In `MasterPlan::do_signup`, the enrollment path computes: [1](#0-0) 
where `fraud_detected` is meant to switch `signup_reason` to `SignupReason::Fraud`. However, `detect_fraud` itself never performs any check—it always resolves to `Ok(false)`: [2](#0-1) 

This is analogous to the `isLpCreated` class of bug: a status/result variable that is supposed to gate subsequent logic (`buyTokens`/`sellTokens` should check `isLpCreated`; here, `enroll_user`/`build_pcp`/signup finalization should check `fraud_detected`) is never meaningfully computed or enforced. In the reported bug, the omission lets a caller stay in an earlier phase after the gating condition should have blocked it; here, the omission lets every signup proceed down the "no fraud detected" path (`SignupReason::Normal`) regardless of the true fraud/liveness state that the pipeline may have surfaced, because the check that should populate `fraud_detected` is dead code.

Since `signup_reason` also drives `enroll_user`, `build_pcp`, and downstream `signup_post::request` reasoning (e.g., `report_signup_reason`), the orb's local, independent fraud/liveness enforcement layer is entirely inert on any build using this code path. [3](#0-2) 

### Impact Explanation
This directly matches the allowed impact category "fraud/liveness bypass." An attacker attempting spoofed, replayed, or otherwise fraudulent biometric capture will never be flagged by orb-side fraud detection, since `detect_fraud` cannot return `true` under any circumstance. The orb relies solely on backend-side fraud checks (`signup_poll`) for detecting duplicates/fraud, entirely losing the defense-in-depth layer that on-device fraud detection was meant to provide.

### Likelihood Explanation
This is not a race condition or edge case — it is deterministic and triggers on every single signup that reaches the fraud-detection phase, making the likelihood of the bypass being exercised effectively certain whenever this build/branch is deployed with the biometric pipeline enabled (`skip_pipeline` disabled).

### Recommendation
Restore actual fraud-detection logic in `detect_fraud`, or at minimum ensure the function's contract accurately reflects and enforces the pipeline's fraud/liveness signals before finalizing `signup_reason`. If this stub is an intentional placeholder due to FOSS redaction of proprietary fraud-detection algorithms, this should be explicitly gated/documented, and any privileged build config should not silently disable fraud protections without an explicit flag (comparable to `skip_fraud_checks`) that operators/auditors can observe and control, rather than leaving a permanent no-op baked into the default execution path.

### Proof of Concept
1. Run `MasterPlan::do_signup` with `skip_fraud_checks` disabled (default) and a completed biometric pipeline.
2. Observe that `self.detect_fraud(...)` returns `Ok(false)` unconditionally at [4](#0-3) .
3. Consequently `fraud_detected` is always `false`, `signup_reason` is computed as `SignupReason::Normal` (assuming pipeline succeeded) irrespective of any fraud signal that a real fraud-detection implementation would have raised, and enrollment proceeds normally at [5](#0-4) .
