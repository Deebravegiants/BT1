### Title
Attacker-controlled scrypt cost parameters in imported metadata weaken or DoS passphrase-based blobKey decryption - ([File: libraries/secure-container/src/metadata.js], [File: libraries/secure-container/src/crypto.js], [File: libraries/seco-file/src/index.js])

### Summary
`seco-file`'s `read()` decrypts an untrusted, attacker-suppliable metadata blob and passes its embedded `scrypt.n/r/p` fields directly into `boxDecrypt`/`stretchPassphrase` with no bounds checking. An attacker who crafts an imported backup file can force the passphrase-derivation to run with degenerate parameters (fast brute-force) or pathological parameters (memory/CPU exhaustion), even though the user still supplies the correct passphrase.

### Finding Description
`read(file, passphrase)` in `libraries/seco-file/src/index.js` calls `decrypt(fileData, passphrase)` [1](#0-0) , which in `secure-container`'s `decrypt()` decodes the raw metadata bytes and immediately uses them: `const metadata = conMetadata.decode(fileObj.metadata); const blobKey = await conMetadata.decryptBlobKey(metadata, passphrase)` [2](#0-1) .

`metadata.decode()` only warns if the blob is larger than `METADATA_LEN_BYTES`; it performs no validation of the `scrypt.n`, `scrypt.r`, or `scrypt.p` fields, which are simply raw `UInt32BE` values from the struct [3](#0-2) .

`decryptBlobKey(metadata, passphrase)` forwards `metadata.scrypt` unchanged into `boxDecrypt` [4](#0-3) . `boxDecrypt` merges attacker-controlled `scryptParams` over the safe defaults (`{...createScryptParams(), ...scryptParams}`), so any `n/r/p` present in the metadata blob wins, and then calls `stretchPassphrase`, which invokes `scrypt(passphrase, salt, { N: n, r, p, dkLen: 32 }, 'buffer')` with no clamping or bounds check on `n`, `r`, `p` [5](#0-4) .

There is no code anywhere in `metadata.js`, `crypto.js`, or `seco-file/src/index.js` that enforces a minimum/maximum on `n`, `r`, or `p` before they reach the KDF. Since `n`, `r`, `p` are attacker-controlled `UInt32BE` fields decoded straight from an imported file, an attacker can set `n=1, r=1, p=1` to make key stretching trivially cheap, or set `n` near `2^31`/large `r` to cause enormous memory allocation (scrypt memory cost is proportional to `N*r*128` bytes) during the unlock/import flow.

### Impact Explanation
- **Weak parameters (n=1, r=1, p=1):** If an attacker can get a user to import a backup file with these degenerate scrypt parameters (e.g. via a "restore/import" flow using `seco-file`/`secure-container`), and the attacker also has or later obtains the resulting encrypted blob (e.g., by re-exfiltrating/observing the file, which is plausible since the attacker crafted it), the effective KDF work factor protecting the user's passphrase is reduced from `n=16384` (a intentional cost) to `n=1`, making offline brute-force of the passphrase against that specific artifact orders of magnitude cheaper. This directly undermines the intended "unlock strength is fixed by the wallet" invariant.
- **DoS parameters (n≈2^31):** Attempting to decrypt with an enormous `n` will cause the scrypt call to try to allocate gigabytes of memory or run for an extremely long time, freezing or crashing the process performing the import/unlock — a denial of service on the unlock/import flow.

This matches a KDF-misconfiguration / weakened-key-derivation class finding rather than direct secret disclosure, since the user's real passphrase is still required to eventually recover the blobKey.

### Likelihood Explanation
Feasible and fully reachable: the attacker only needs to supply a crafted `.seco`-format file (or equivalent metadata blob) that a victim imports via `read()`/`decrypt()`. No privileged access, existing keys, or malicious peer/node is required — this is exactly the "crafted metadata blob (imported backup)" scenario in the prompt. The code path from decoded bytes to `scrypt()` call has no intervening validation step, so it is deterministic and 100% reproducible.

### Recommendation
Enforce sane bounds on `scrypt.n`, `scrypt.r`, and `scrypt.p` immediately after `metadata.decode()` (or inside `decryptBlobKey`/`stretchPassphrase`) — e.g., require `n` to be a power of two within `[2^14, 2^20]`, `r` within a small fixed range (e.g., 1–16), and `p` within a small fixed range (e.g., 1–4), and reject/throw if the decoded metadata's scrypt params fall outside the wallet's approved set. Ideally, do not trust `n/r/p` from imported metadata at all for wallet-controlled backups and instead use a fixed, hardcoded configuration for the KDF.

### Proof of Concept
Unit/fuzz test plan (extending `libraries/secure-container/src/__tests__/metadata.test.js` style):
```js
test('decryptBlobKey should reject out-of-range scrypt params', async (t) => {
  const blobKey = randomBytes(32)
  const passphrase = 'open sesame!'
  const md = metadata.create()
  await metadata.encryptBlobKey(md, passphrase, blobKey)

  // Attacker tampers with scrypt params post-encryption, simulating an imported/crafted metadata blob
  const weakMd = { ...md, scrypt: { ...md.scrypt, n: 1, r: 1, p: 1 } }
  const dosMd = { ...md, scrypt: { ...md.scrypt, n: 2 ** 31, r: 8, p: 1 } }

  // Expected: implementation should reject/throw due to out-of-bounds scrypt cost params
  await t.rejects(() => metadata.decryptBlobKey(weakMd, passphrase), 'weak scrypt params should be rejected')
  await t.rejects(() => metadata.decryptBlobKey(dosMd, passphrase), 'excessive scrypt params should be rejected')

  // Current behavior (bug): both calls succeed / hang / OOM instead of throwing,
  // demonstrating no bounds enforcement exists on attacker-controlled scrypt.n/r/p.
})
```
Expected result today: `decryptBlobKey(weakMd, passphrase)` succeeds using `n=1` (trivial KDF cost), and `decryptBlobKey(dosMd, passphrase)` either hangs or exhausts memory — both confirming the missing bounds check.

export function createScryptParams(params = {}) {
  return { salt: randomBytes(32), n: 16_384, r: 8, p: 1, ...params }
}

// always returns 32 byte key
export async function stretchPassphrase(passphrase, { salt, n, r, p } = createScryptParams()) {
  const key = await scrypt(passphrase, salt, { N: n, r, p, dkLen: 32 }, 'buffer')
  return { key, salt }
}

export async function aesEncrypt(key, message) {
  if (key.length !== KEY_LEN) throw new Error('Unexpected key size for aes-256')
  const iv = randomBytes(IV_LEN_BYTES)
  const merged = await encryptGCM({ data: message, key, nonce: iv, format: 'buffer' })
  const blob = merged.subarray(0, -AUTH_TAG_LEN)
  const authTag = merged.subarray(-AUTH_TAG_LEN)
  return { authTag, blob, iv }
}

export async function aesDecrypt(key, blob, { iv, authTag }) {
  if (key.length !== KEY_LEN) throw new Error('Unexpected key size for aes-256')
  return decryptGCM({ data: Buffer.concat([blob, authTag]), key, nonce: iv, format: 'buffer' })
}

export async function boxEncrypt(passphrase, message, scryptParams) {
  const { key, salt } = await stretchPassphrase(passphrase, scryptParams)
  const { authTag, blob, iv } = await aesEncrypt(key, message)
  return { authTag, blob, iv, salt }
}

export async function boxDecrypt(passphrase, blob, { iv, authTag }, scryptParams) {
  scryptParams = { ...createScryptParams(), ...scryptParams }
  const { key } = await stretchPassphrase(passphrase, scryptParams)
  return aesDecrypt(key, blob, { iv, authTag })
}
