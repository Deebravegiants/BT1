### Title
`Oauth.validate_auth_callback` sends the app's `client_secret` to an unvalidated `shop` host, unlike every other OAuth grant helper - ([File: lib/shopify_api/auth/oauth.rb])

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the token-exchange request host directly from `auth_query.shop` via `auth_base_uri(shop)` and POSTs a body containing `Context.api_secret_key` to that host, without ever calling `Utils::ShopValidator.sanitize!` on the shop value. [1](#0-0) [2](#0-1) 

Every other credential-exchange entry point in this gem (`ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `TokenExchange.exchange_token`) explicitly validates the `shop` value with `Utils::ShopValidator.sanitize!` before using it to construct the request host that will receive `client_secret`. [3](#0-2) [4](#0-3) 

`Oauth.validate_auth_callback` is the one exception: `auth_query.shop` flows unvalidated into `auth_base_uri` and then into `HttpClient`, whose base URI is derived straight from `session.shop`. [5](#0-4) 

### Finding Description
The identity binding that should hold is: **the host that receives the app's `client_secret` == a host that has been through `ShopValidator` (i.e., a domain under `myshopify.com`/`shopify.com`/`myshopify.io`/`spin.dev`/`shop.dev`)**. [6](#0-5) 

In `validate_auth_callback`, that binding is broken: the `shop` value is only checked for HMAC integrity (i.e., it was part of what Shopify signed) via `Utils::HmacValidator.validate(auth_query)`, but the HMAC check only proves the query wasn't tampered with in transit - it does not prove the `shop` string is actually a Shopify-owned domain. [7](#0-6) 
The value is then fed directly into `auth_base_uri(shop)`, which builds `"https://#{shop}/admin"` with no further checks, and that URI becomes the destination for the POST containing `client_id`, `client_secret`, and `code`. [1](#0-0) [2](#0-1) 

Contrast this with `client_credentials.rb` and `refresh_token.rb`, both of which call `validated_shop = Utils::ShopValidator.sanitize!(shop)` and use `validated_shop` (not the raw input) to build the session/host used for the `client_secret`-bearing request. [8](#0-7) [9](#0-8) 

This is directly analogous to the reported bug class: a value (`shop`) that is treated as trustworthy for a security-critical routing decision (where to send `client_secret`) is validated only against a narrow property (HMAC-covered) instead of the property that actually matters (is it a real, trusted Shopify domain) - exactly the "host validated versus the host that receives the `client_secret`" pattern called out in the review rules.

### Impact Explanation
If `begin_auth` is ever invoked (directly by a host app, or via any flow where an app accepts a caller-supplied `shop` for `redirect_path`/callback construction) with a shop string that is not itself first passed through `ShopValidator`, and a callback later arrives with a matching HMAC (e.g., because host apps commonly pass through raw callback params from the request, as shown in the gem's own OAuth docs example that constructs `AuthQuery` straight from `request.parameters`), the resulting `client_secret`-bearing POST request is routed to `auth_base_uri(auth_query.shop)` with no domain allow-listing at the point where the secret is transmitted. [10](#0-9) 
Because this is the sole OAuth-callback code path lacking the `ShopValidator.sanitize!` call that the other three credential-exchange helpers all perform, it represents an SSRF-with-credentials risk class (the app's `client_secret` leaving the app toward a host not vetted as a genuine Shopify domain) at the exact place the review rubric flags as High severity ("SSRF with the app's credentials").

### Likelihood Explanation
Exploitation still requires the attacker-controlled/loosely-validated `shop` value to survive HMAC verification, i.e., it depends on how the host application sources and passes the `shop`/`auth_query` fields into `begin_auth`/`validate_auth_callback`. I could not fully trace how `begin_auth`'s own `shop` parameter is validated by callers within this codebase (no `ShopValidator` call exists in `oauth.rb` at all), nor find any additional guard elsewhere in `lib/shopify_api/auth/oauth.rb` that constrains `shop` before it reaches `auth_base_uri`. This makes the missing validation a clear, concrete code-level gap relative to the gem's own established pattern (used consistently in `client_credentials.rb`, `refresh_token.rb`, `token_exchange.rb`), even though full remote exploitability depends on host-application usage patterns that are outside this gem's own files.

### Recommendation
Apply the same `Utils::ShopValidator.sanitize!(shop)` check used in `client_credentials.rb`/`refresh_token.rb`/`token_exchange.rb` to `auth_query.shop` inside `Oauth.begin_auth` and `Oauth.validate_auth_callback` in `lib/shopify_api/auth/oauth.rb`, before it is used to construct `auth_base_uri` or any request host, and use the sanitized value (not the raw one) for the `client_secret`-bearing HTTP request.

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end

          session_params = T.cast(response.body, T::Hash[String, T.untyped]).to_h
          session = Session.from(shop: auth_query.shop,
            access_token_response: Oauth::AccessTokenResponse.from_hash(session_params))

          cookie = if Context.embedded?
            SessionCookie.new(
              value: "",
              expires: Time.now,
            )
          else
            SessionCookie.new(
              value: session.id,
              expires: session.expires ? session.expires : nil,
            )
          end

          { session: session, cookie: cookie }
        end

        private

        sig { params(shop: String).returns(String) }
        def auth_base_uri(shop)
          return "https://#{shop}/admin" unless defined?(DevServer) && shop.include?(".my.shop.dev")

          # For first-party apps in development only, we leverage DevServer to build the admin base URI
          admin_web = T.unsafe(Object.const_get("DevServer")) # rubocop:disable Sorbet/ConstantsFromStrings
            .new("admin-web")
          admin_host = admin_web.host!(nonstandard_host_prefix: "admin")
          shop_name = shop.split(".").first

          "https://#{admin_host}/store/#{shop_name}"
        end
