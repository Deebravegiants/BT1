## Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while `Registry.process` trusts the `shop-domain` header (exposed as `request.shop`) to identify which merchant/tenant a webhook belongs to. Because the HMAC never binds the `shop` value, and the HMAC secret (`api_secret_key`) is the app's single client secret shared across every shop that installs the app, any unprivileged user who installs the app on their own store can capture a validly-signed webhook body and replay it against the app's webhook endpoint with a forged `shop-domain` header pointing at a victim shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then forwards the unauthenticated `request.shop` value straight into the tenant-identifying `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirms this: it signs/verifies `verifiable_query.to_signable_string` (the body) against `Context.api_secret_key`, never touching `shop`: [4](#0-3) 

This breaks the binding: `hmac == HMAC(api_secret_key, raw_body)` should imply `shop == the shop that actually sent this payload`, but the equality only holds for `raw_body`, not for `shop`. Since `api_secret_key` is the app's single client secret shared by all installing shops (not a per-shop secret), any shop that has installed the app can generate a payload+HMAC pair that is valid for the shared secret. That attacker can then submit the same body/HMAC to the app's public webhook endpoint with `shop-domain` swapped to a victim's `myshopify.com` domain. `Utils::HmacValidator.validate` will report success (it only checks the body signature), and the handler executes business logic believing the event originated from the victim shop.

### Impact Explanation
This crosses a tenant boundary in an app built on this gem: an attacker-controlled webhook payload can be attributed to another merchant's shop, causing the app to write, delete, or otherwise process data as if it belonged to the victim tenant (cross-tenant access), which matches the "cross-tenant access" Critical impact category. Any handler logic keyed off `WebhookMetadata#shop` (order/customer sync, GDPR data handling, billing state, etc.) can be poisoned this way.

### Likelihood Explanation
Any developer/attacker can install the target app for free on their own development store to legitimately receive real webhooks (bodies + valid HMACs) signed with the app's shared `api_secret_key`. Replaying that captured body+HMAC to the same app's public webhook endpoint with a forged `shop-domain` header requires no credentials beyond network access to the endpoint, making this reachable by any unprivileged internet user who can install the app once.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signable string verified by the HMAC, or otherwise cryptographically bind the claimed shop to the signed payload before it is exposed via `request.shop`/`WebhookMetadata`. At minimum, document that host applications must independently verify `request.shop` against a known/installed-shop list before trusting it, since the gem's own HMAC check does not cover it.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store (`attacker.myshopify.com`), receiving genuine webhooks signed with the app's shared `api_secret_key`.
2. Attacker captures one such webhook's raw body and its `x-shopify-hmac-sha256` value (both valid, since HMAC = `HMAC-SHA256(api_secret_key, raw_body)`).
3. Attacker POSTs that same raw body and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `Registry.process` ( [5](#0-4) ) succeeds because it only checks the body.
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes the (attacker-controlled) event as if it belongs to the victim shop.
