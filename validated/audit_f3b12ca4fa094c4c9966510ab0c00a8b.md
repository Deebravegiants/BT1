## Title
Reentrancy via Checks-Effects-Interactions Violation in `withdraw()` — External Token Transfer Before Escrow Accounting Update - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` contains the exact reentrancy bug class described in the external report: an unprotected external call (`.call` to transfer native ETH or ERC-20 tokens) is executed *before* the corresponding escrow-accounting state (`_orders[commitment][token]`) is decremented, inside `withdraw()`. This is the same class of bug (external call precedes state updates in a loop) already identified, fixed, and regression-tested in the mainline EVM `IntentGatewayV2`/`IntentsBase._withdraw` implementation, but the fix was never backported to the Tron contract copy.

### Finding Description
In the mainline (fixed) implementation, escrow accounting is decremented *before* the external transfer: [1](#0-0) 

The Tron copy of the same logic instead performs the external call first and only decrements `_orders` afterward, for both the native-ETH and ERC-20 branches: [2](#0-1) 

This is invoked from both of the app's two `onlyHost` settlement callbacks — `onAccept` (RedeemEscrow/RefundEscrow) and `onGetResponse` (source-chain cancellation) — and from the user-callable, same-chain branch of `cancelOrder`: [3](#0-2) [4](#0-3) [5](#0-4) 

Additionally, unlike the mainline contract which uses `SafeERC20.safeTransfer`, the Tron path uses a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only checks the boolean call-success, not the returned ABI-encoded success value, which further widens what a maliciously crafted "token" contract supplied as an order input can do during the callback window opened by the CEI violation.

The mainline codebase has an explicit regression-test suite documenting that exactly this ordering (external transfer before marking/decrementing state) was a High severity finding that was fixed by moving `_filled[commitment] = msg.sender` and escrow decrements ahead of external calls: [6](#0-5) 

The `_filled[body.commitment] = beneficiary` write at the top of `withdraw()` does block the most direct re-entry into `cancelOrder`/the settlement callbacks for the *same* commitment, which limits (but per the codebase's own explicit historical precedent does not eliminate the class of risk) the practical severity relative to the mainline pre-fix bug. Still, the escrow-decrement-after-transfer ordering for `_orders[commitment][token]` itself is left unprotected within the token loop, which is precisely the pattern the project already treats as reportable and fixes elsewhere.

### Impact Explanation
`withdraw()` is the function that pays out escrowed user/solver funds on order settlement and cancellation for the Tron IntentGateway deployment. A beneficiary address is attacker-controlled in multiple reachable flows: the solver address in cross-chain fills (`RedeemEscrow`), and the order owner in same-chain cancellations. Any code path that reaches this function with attacker-influenced state (order composition, malicious "token" contracts registered as escrowed inputs, or malicious beneficiary contracts) inherits the risk of state manipulation mid-loop before the escrow ledger is updated, contrary to the checks-effects-interactions pattern the rest of the intents code enforces.

### Likelihood Explanation
Reachable directly by any unprivileged solver (via `fillOrder`/settlement) or order owner (via same-chain `cancelOrder`) without requiring governance, admin, or relayer privileges — the same actor classes that triggered the analogous, already-acknowledged High severity finding in the mainline contract.

### Recommendation
Backport the CEI fix from `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` to `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`: decrement `_orders[body.commitment][token]` before performing the native-ETH `.call` or ERC-20 transfer, and replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern with `SafeERC20.safeTransfer` to also enforce correct return-value handling.

### Proof of Concept
1. Attacker places a same-chain order via `placeOrder`, escrowing multiple input tokens, with `order.user = attacker` (a contract).
2. Attacker calls `cancelOrder(order, options)` on the same chain; this invokes `withdraw(body, true)`.
3. Inside `withdraw`, `_filled[commitment]` is set, then the loop begins; for the first token entry (e.g., native ETH), the raw `.call{value: amount}("")` transfers funds to the attacker contract *before* `_orders[commitment][token]` is decremented.
4. During the attacker contract's `receive()`/fallback, escrow state for that token (and any tokens not yet reached in the loop) is still unmodified — establishing the exact unsafe interaction-before-effect window that the project's own `IntrinsicIntentsReentrancyTest.sol` suite (`testReentrancy_FeeTheft`, `testReentrancy_EscrowTheft_MultiOutput`) was written specifically to close off in the mainline contract, but which remains open here.

    function cancelOrder(Order calldata order, CancelOptions calldata options) public payable {
        bytes32 commitment = keccak256(abi.encode(order));

        // order has already been filled
        if (_filled[commitment] != address(0)) revert Filled();

        address hostAddr = host();
        bytes32 currentChain = keccak256(IDispatcher(hostAddr).host());
        bytes32 orderSource = keccak256(order.source);
        bytes32 orderDest = keccak256(order.destination);
        bool isSameChain = orderSource == orderDest;

        if (isSameChain) {
            // Same-chain: validate locally and refund immediately
            // only owner can cancel
            if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

            if (orderSource != currentChain) revert WrongChain();

            WithdrawalRequest memory body =
                WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user});

            withdraw(body, true);

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }
