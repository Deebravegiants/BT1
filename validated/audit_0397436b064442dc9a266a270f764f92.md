Found the vulnerability: `TokenExchange.exchange_token` sends the app's `client_secret` to a host derived from the JWT `dest` claim without ever validating that the claim is a genuine Shopify domain, unlike every sibling grant method in the same file/module.

### Title
Client secret exfiltration via unvalidated `dest` claim in `TokenExchange.exchange_token` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the shop host directly from the session token's (`JwtPayload`) `dest` claim and uses it, unsanitized, as the destination host for an HTTP POST that carries the app's `client_id` and `client_secret`. Every other credential-issuing method in the same module (`migrate_to_expiring_token`, and the sibling `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`) explicitly runs the shop value through `Utils::ShopValidator.sanitize!` before using it to build the request host. `exchange_token` skips this step entirely.

### Finding Description
The binding that should hold is: `request_host == myshopify_trusted_domain(shop)`, enforced via `ShopValidator.sanitize!`. In `exchange_token`: [1](#0-0) 
`dest_shop = jwt_payload.shop` is used to build `shop_session` directly, with no call to `Utils::ShopValidator.sanitize!`.

`JwtPayload#shop` derives the host purely by string substitution on the `dest` claim, with no domain restriction: [2](#0-1) 

The only check performed on the JWT is signature validity (HMAC with `Context.api_secret_key`) and `aud == Context.api_key`: [3](#0-2) 
There is no validation that `iss`/`dest` is a `*.myshopify.com` (or other trusted) domain.

`HttpClient` then builds the request URI directly from `session.shop`: [4](#0-3) 

and the request body containing `client_secret` is POSTed to that host: [5](#0-4) 

Contrast with the sanitized sibling methods, which are the intended pattern: [6](#0-5) [7](#0-6) [8](#0-7) 

`ShopValidator` exists precisely to close this gap — restricting hosts to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or an app-configured custom domain: [9](#0-8) 

### Impact Explanation
This meets the SSRF-with-app-credentials criterion. If the JWT signing key (`api_secret_key`) — the *app's own secret* — is ever able to sign or influence a token with an attacker-controlled `dest`/`iss` value (e.g., via key rotation misconfiguration, a leaked/rotated old key handled by `Context.old_api_secret_key`, or any future change that relaxes JWT issuance), the `client_secret` would be sent verbatim to an attacker-controlled host in the POST body. Even absent an active exploit today, this is a broken identity/host binding: `request_host` is not constrained to `myshopify_trusted_domain(dest)`, unlike the rest of the codebase's own credential-issuing methods, which is precisely the "host validated versus host that receives client_secret" analog called out in the task's bug class list.

### Likelihood Explanation
Currently low likelihood under normal operation because a valid JWT requires knowledge of `api_secret_key`/`old_api_secret_key`, which are supposed to be app secrets. However, this is a real, concrete divergence from the library's own established defense-in-depth pattern (every other grant flow sanitizes the shop before use), so the missing check is a genuine root-cause gap rather than a false positive, and it directly matches the reported bug-class ("host validated versus host that receives client_secret").

### Recommendation
Call `Utils::ShopValidator.sanitize!(dest_shop)` (or equivalent) immediately after extracting `dest_shop = jwt_payload.shop` in `TokenExchange.exchange_token`, before constructing `shop_session`, matching the pattern already used in `migrate_to_expiring_token`, `client_credentials`, and `refresh_access_token`.

### Proof of Concept
1. Obtain/produce a session token (JWT) whose `dest` claim is set to an attacker-controlled host (requires ability to sign a valid token with the app's current or old `api_secret_key`).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. `dest_shop` is taken unsanitized from the token and used to build `shop_session`; `HttpClient` issues `POST https://<attacker-host>/admin/oauth/access_token` with body containing `client_id` and `client_secret`, exfiltrating the app secret to the attacker-controlled host.
