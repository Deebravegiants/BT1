### Title
Missing quality/liveness gate on iris template mask ratio allows degenerate iris codes to be signed and attested as valid signups - (File: src/plans/personal_custody_package.rs)

### Finding Description
The Python iris pipeline returns rich per-capture quality metadata in `template_property` (`visible_ratio`, `abnormal_mask_ratio`, `weighted_abnormal_mask_ratio`), parsed by `TemplateProperty` in `src/agents/python/iris/types.rs:143-157`. This data is attached to `Metadata` and surfaces only in `debug_report.iris_model_metadata` (`src/plans/mod.rs:1343-1346`) for observability — it is never read as a decision input anywhere in the repository (confirmed via full-repo search: it only appears in `types.rs`/`extracts.rs`).

The actual biometric-capture gate that decides whether a frame is used to build the iris template is `valid_capture = estimate.score >= IRIS_SCORE_MIN && ...` in `src/plans/biometric_capture/mod.rs:239-242`, where `score` is IR-Net's own sharpness/status/`valid_for_identification`-derived scalar (`calculate_selection_score`, `src/agents/python/ir_net.rs:305-308`). This score reflects sharpness and IR-Net's own eye/side classification, not the iris-extraction library's own occlusion/mask ratio computed later in the pipeline. `update_occlusion` (`src/plans/biometric_capture/mod.rs:667-690`) only drives a UI hint (`orb.ui.biometric_capture_occlusion`), it never blocks capture or downstream processing.

Once a frame passes that sharpness gate, `iris::Output::Estimate` → `IrisTemplate::iris_codes`/`mask_codes` are converted via `IrisCodeArray::from_base64` and immediately encoded into MPC shares by `GaloisRingIrisCodeShare::encode_iris_code`/`encode_mask_code` (`src/agents/python/iris/mod.rs:104-115`), with no check on the fraction of valid (non-masked) bits. `make_iris_code_shares_jsons` (`src/plans/personal_custody_package.rs:583-604`) only validates that the four share fields are `Some` — it performs no content/quality validation before serializing and signing them into the tier0 PCP. Finally, `detect_fraud` (`src/plans/mod.rs:1392-1406`) is a stub in this build: `// FOSS: WE HAVE DELETED ALL FRAUD CHECKS` followed by an unconditional `Ok(false)`, so no fail-closed fraud/liveness gate exists downstream either.

The result: an attacker who biases the physical presentation to occlude most of the iris while still producing a locally sharp/aligned central patch (satisfying IR-Net's `score`/`valid_for_identification`/`status==0`) can drive `visible_ratio` down and `abnormal_mask_ratio` up arbitrarily, yet still produce base64 strings that decode to the fixed `IrisCodeArray` bit-length and pass through unmodified to signed, uploaded iris-code shares.

### Impact Explanation
A degenerate/near-empty iris code share package can be packaged, hardware-signed (`sign(digest(&SHA256, &hashes_json))`, `personal_custody_package.rs:346`), and uploaded to the backend tier0/tier1 pipeline as though it were a normal, high-quality biometric capture. This maps to a liveness/fraud-bypass and attestation-forgery style impact: the Orb attests a signup was performed with a biometric capture that does not meet the intended quality bar, without a fail-closed backend or on-device rejection based on the iris library's own quality signals. Given that `detect_fraud` is entirely stubbed in this build, there is no compensating control downstream in the reachable code paths of this repository.

### Likelihood Explanation
The precondition is attacker control over the physical scene shown to the cameras (near-boundary occlusion, e.g. eyelid/eyelash occlusion, decorative contact lenses, printed occluders) which is explicitly permitted under the "scene shown to the cameras" scope, requires no privileged access, and is repeatable across signup attempts since the check that exists (`IRIS_SCORE_MIN`) is orthogonal to mask/visible-ratio.

### Recommendation
Add an explicit, fail-closed quality gate using `metadata.template_property.visible_ratio` / `abnormal_mask_ratio` (and equivalently `occlusion30`/`occlusion90`) before treating an `iris::EstimateOutput` as eligible for `encode_iris_code`/`encode_mask_code` or before `make_iris_code_shares_jsons` is called — e.g., reject/short-circuit the pipeline (mirroring the existing `data_error!`-style short-circuits in `build_pcp`, `src/plans/mod.rs:1653-1711`) whenever `visible_ratio` falls below a configured minimum, and restore real fraud/liveness checks in `detect_fraud` rather than the current unconditional `Ok(false)`.
