### Title
Webhook `shop` identity not covered by HMAC, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies only covers the raw request body (`to_signable_string` returns `@raw_body`). This breaks the binding "shop authenticated == shop the handler acts on": the HMAC proves the *body* came from Shopify with the app's secret, but it proves nothing about which shop the header claims to be from.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`. `Request#shop` is read straight from an unauthenticated header: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC over the request (i.e., over the body only) and then, without any further check that the `shop` header matches the identity implied by the signed payload, forwards `request.shop` to the handler as trusted tenant identity: [3](#0-2) 

Since the same `api_secret_key` is used for every shop installed on a given app, and the HMAC is computed only over the JSON body, any request with a **valid (body, hmac) pair** — for example one the attacker legitimately obtained from their own shop's install of the app, or one replayed/observed from any webhook delivery to that app — remains cryptographically valid no matter what `shop-domain` header value is substituted. The equality that should hold is:
`shop bound by the HMAC-signed payload == shop the handler is told to act on`
but in this gem the left side simply doesn't exist — the header is asserted, not authenticated.

The wiki docs explicitly instruct integrators to trust `data.shop` from the webhook metadata as the tenant key for background jobs (e.g., `shop_domain: data.shop`): [4](#0-3) 

This matches the codebase-hint pattern of "a field acted on but not covered by the HMAC."

### Impact Explanation
An attacker who controls one shop installation of a multi-tenant app (or who can capture/replay one valid webhook body+HMAC pair delivered to the app, e.g. from their own store) can submit that exact body/HMAC combination to the app's webhook endpoint while spoofing the `x-shopify-shop-domain` header to name a **different, victim shop**. Because `HmacValidator.validate` only checks the body against the secret, the forged request passes verification, and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim's shop domain. If the host application uses this shop value (as the docs recommend) to key per-tenant data, look up sessions, or trigger tenant-scoped side effects, this results in cross-tenant data injection/attribution — satisfying the "cross-tenant access" Critical-impact category.

### Likelihood Explanation
Exploitation requires the attacker to already have at least one valid (body, HMAC) pair signed with the app's secret. This is realistic in two ways: (1) an attacker who owns a shop that has installed the target app receives their own legitimately-signed webhooks and can immediately replay them with a modified `shop-domain` header, since the secret is shared across all tenants of the app, not per-shop; (2) a shop-scoped webhook could be replayed with a different shop header at any time (no `shop`-binding, no nonce/timestamp binding in `to_signable_string`). No possession of `api_secret_key`, access tokens, or privileged access is needed — only receipt of one legitimate webhook, which is expected in normal usage of a multi-tenant app.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-signed material, or otherwise cryptographically bind the `shop` header to the signature before trusting it. At minimum, `Request#to_signable_string` should incorporate the shop-domain header value so a mismatched/spoofed header invalidates the HMAC, and `Registry.process` should not treat `request.shop` as authenticated unless it was covered by the verified signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery with body `B` and header `x-shopify-hmac-sha256: H` (computed by Shopify over `B` using the app's shared `api_secret_key`).
2. Attacker replays a POST to the app's webhook endpoint with the same body `B` and the same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request; `HmacValidator.validate` calls `to_signable_string` (`= B`) and successfully verifies `H` against `api_secret_key`, since the shop header is not part of the signed string: [5](#0-4) 
4. `Registry.process` invokes the app's handler with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the payload was never sent by Shopify on behalf of that shop.
