### Title
Interest accrual overflows the RAY value domain and permanently freezes a large market - ([File: `common/src/rates/simulate.rs`])

### Summary
The pool’s mandatory accrual path converts aggregate scaled debt through `scaled_to_original(borrowed, borrow_index)`, which panics with `MathOverflow` when the RAY-denominated value exceeds `i128`. A sufficiently large market can therefore cross a non-recoverable arithmetic ceiling before `MAX_BORROW_INDEX_RAY` is reached. Because every market mutation calls `global_sync` before applying the requested operation, one successful accrual that leaves `borrowed * borrow_index / RAY > i128::MAX` permanently bricks subsequent `update_indexes`, `supply`, `borrow`, `withdraw`, `repay`, liquidation legs, revenue claims, and recapitalization for that market.

### Finding Description
`Controller::update_indexes` is permissionless after caller authorization and forwards the requested `HubAssetKey` list to the pool’s `update_indexes` entrypoint. [1](#0-0) [2](#0-1) 

The pool implementation loads each market and invokes `interest::global_sync`. [3](#0-2)  `global_sync` invokes `accrue_chunk` for each elapsed interval, and `accrue_chunk` delegates index calculation to `common::rates::accrue_step`. [4](#0-3) [5](#0-4) 

`accrue_step` first computes the current borrowed and supplied RAY values with `scaled_to_original`. [6](#0-5)  `scaled_to_original` calls `Ray::mul`, which evaluates `mul_div_half_up(scaled, index, RAY)`. [7](#0-6) [8](#0-7)  `mul_div_half_up` uses an `i128` fast path and otherwise an `I256` intermediate, but deliberately panics with `MathOverflow` if the final quotient does not fit `i128`. [9](#0-8) [10](#0-9) 

The panic happens before `accrue_step` reaches the borrow-index cap, and before `global_sync` reaches `mark_accrued`. Consequently, once the committed share total and index satisfy `borrowed * borrow_index / RAY > i128::MAX`, every later accrual retries the same overflowing multiplication against unchanged state. [11](#0-10) [12](#0-11) 

Every regular pool mutation shares this prerequisite: `synced_market` loads the market and calls `global_sync`, and `run_batch` is used by the owner-mediated pool operations called by controller supply, borrow, withdraw, repay, liquidation, revenue, and related flows. [13](#0-12) [14](#0-13)  The repository’s own regression test demonstrates that a one-billion-whole-token, 18-decimal market at sustained high utilization reaches this condition before `MAX_BORROW_INDEX_RAY`, after which both withdrawal and repayment return `MATH_OVERFLOW`. [15](#0-14) 

### Impact Explanation
This is permanent freezing of all funds and claims in the affected `(hub_id, asset)` market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot execute legs touching the market, and the permissionless keeper path cannot recover it because `update_indexes` itself hits the same panic. The pool token balance remains under contract control while the accounting layer can no longer load an accrued market state.

The condition is not merely a rejected oversized call argument: it arises from the product of two already-committed state variables, `borrowed` and `borrow_index`. No caller can pass a smaller amount to avoid the overflow because the multiplication happens before amount validation or position mutation.

### Likelihood Explanation
Likelihood is market- and liquidity-dependent. The attacker does not need privileged access, malformed input, leaked keys, or an oracle violation: an unprivileged address can create an account with `supply(caller, 0, spoke_id, assets)`, obtain sufficient collateral, call `borrow(caller, account_id, borrows, to)`, and later call `update_indexes(caller, assets)`. A single address can supply both the liquidity asset and separate collateral on accounts it owns.

The attack requires an extremely large listed market—on the order of `10^27` base units for an 18-decimal asset—plus borrowing sustained near the steep utilization segment for enough ledger time to raise the index beyond the `i128` value ceiling. On real assets with that scale, the issue is economically costly but does not require protocol compromise. Once reached, there is no user-level recovery path short of replacing the contract.

### Recommendation
Separate index safety from value safety:

1. Before computing `borrowed * borrow_index`, clamp or bound the product/value domain explicitly and transition the market into a recoverable no-accrual state rather than panicking.
2. Reorder `accrue_step` so the borrow index is capped before the value overflow can become persistent, or maintain accrued debt in a wider representation where the protocol can safely calculate and then clamp state transitions.
3. Add an invariant that admitted market scale and worst-case index growth cannot exceed `i128::MAX`, enforced dynamically before deposits or debt shares are minted.
4. Add an emergency path that can stamp `last_timestamp` or freeze only future interest while still permitting repayment, collateral withdrawal, liquidation, and bad-debt processing.
5. Keep the existing long-horizon test as a regression case, but change its expected outcome from permanent `MathOverflow` to a capped, recoverable accrual result.

### Proof of Concept
Concrete controller-call sequence:

```text
let debt_asset = HubAssetKey {
    hub_id: HUB_ID,
    asset: BIG18_TOKEN,
};

let collateral_asset = HubAssetKey {
    hub_id: HUB_ID,
    asset: COLLATERAL_TOKEN,
};

// One billion whole tokens of an 18-decimal listed asset.
let principal: i128 = 1_000_000_000 * 10_i128.pow(18);

// 1. Supply the liquidity asset. The same caller can use `account_id = 0`
//    to create the account.
let account_id = Controller::supply(
    caller,
    0,
    SPOKE_ID,
    vec![(debt_asset.clone(), principal)],
);

// 2. Supply sufficient collateral and borrow approximately 98% of the pool.
Controller::supply(
    caller,
    account_id,
    SPOKE_ID,
    vec![(collateral_asset, sufficient_collateral)],
);

Controller::borrow(
    caller,
    account_id,
    vec![(debt_asset.clone(), principal * 98 / 100)],
    None,
);

// 3. At a later ledger time, after high-utilization interest has advanced the
//    committed borrow index, any caller triggers the accrual.
Controller::update_indexes(
    caller,
    vec![debt_asset.clone()],
);
```

The final call succeeds for enough intervals to commit an index whose RAY debt value exceeds `i128::MAX`. On the next elapsed interval, `accrue_step` panics at the initial `scaled_to_original(state.borrowed, borrow_index)` calculation. Thereafter:

```text
Controller::withdraw(caller, account_id, vec![(debt_asset.clone(), 0)], None)
// reverts with MathOverflow before burning supply shares

Controller::repay(caller, account_id, vec![(debt_asset.clone(), amount)])
// reverts with MathOverflow before burning debt shares

Controller::liquidate(liquidator, account_id, debt_payments, seize_mode)
// reverts when the liquidation path syncs the same market

Controller::update_indexes(anyone, vec![debt_asset])
// reverts repeatedly; `last_timestamp` is never stamped
```

The committed regression test reaches precisely this terminal state: `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all return `MATH_OVERFLOW`, while the stored borrow index remains below `MAX_BORROW_INDEX_RAY`, proving that the value multiplication—not the configured index ceiling—is the root cause. [16](#0-15)

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }
```

```rust
/// Computes `x * y / d` rounded half up. Requires `x >= 0`, `y >= 0`, and `d > 0`; a
/// `debug_assert` checks this in debug builds. Panics with `GenericError::DivisionByZero` if
/// `d == 0`, and with `GenericError::MathOverflow` if any other precondition is violated or if
/// the result does not fit in `i128`.
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}
```

```rust
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```

```rust
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
```
