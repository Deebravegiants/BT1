### Title
Permanent market freeze from RAY debt-value overflow - ([File: common/src/rates/index.rs](common/src/rates/index.rs))

### Summary
A sufficiently large debt position can grow until `borrowed * borrow_index` exceeds `i128::MAX`, after which every operation that synchronizes the market reverts permanently. Because the overflow occurs before the borrow-index ceiling can take effect, the market loses repay, withdrawal, liquidation, and index-update functionality while user funds remain locked. [1](#0-0) 

### Finding Description
Every pool mutation loads the market and calls `interest::global_sync` before executing the requested action. [2](#0-1)  `global_sync` calls `accrue_step` for each elapsed chunk. [3](#0-2)  During accrual, `calculate_supplier_rewards` evaluates the previous and next total debt by multiplying the scaled debt by the old and new borrow indexes. [4](#0-3)  The fixed-point multiplication returns `MathOverflow` when the resulting RAY value does not fit in `i128`. [5](#0-4) 

Although `update_borrow_index` caps the index at `MAX_BORROW_INDEX_RAY`, that cap is applied only after `calculate_supplier_rewards` computes the unbounded total debt. [6](#0-5)  Consequently, `borrowed * borrow_index` can overflow before the index itself reaches its configured ceiling. [7](#0-6) 

The codebase explicitly demonstrates this state: a large 18-decimal market at sustained high utilization reaches the RAY-value ceiling before the index ceiling, and subsequent `update_indexes`, `withdraw`, and `repay` calls all revert with `MathOverflow`. [8](#0-7) 

### Impact Explanation
This permanently freezes the affected pool market. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot reduce bad debt, and even the permissionless `update_indexes` path cannot recover the market because all these paths accrue interest first. [9](#0-8) 

The result is permanent freezing of user funds and a contract unable to process the affected market. [10](#0-9) 

### Likelihood Explanation
A single unprivileged user can create the precondition through ordinary `supply` and `borrow` calls if the market admits a sufficiently large amount. The admitted token amount can approach `i128::MAX / 10^(27-d)`, while the later value computation must independently fit in RAY. [11](#0-10)  The demonstrated configuration uses a 1-billion-token, 18-decimal market and approximately 98% utilization; sustained interest then causes the debt-value product—not the index—to overflow. [12](#0-11) 

The attack requires substantial capital and time, but it does not require privileged calls, oracle manipulation, malformed input, or a leaked key.

### Recommendation
Keep total scaled debt and its unscaled value inside the arithmetic domain before allowing debt growth. At minimum:

- Track or derive the RAY-valued debt ceiling and reject `borrow`, `multiply`, `swap_debt`, `flash_position`, or other debt-minting flows that can exceed it at `MAX_BORROW_INDEX_RAY`.
- Apply the borrow-index cap before calculating accrued value, or calculate the accrual increment with an intermediate range that cannot trap market synchronization.
- Add an emergency catch-up path that can process the final accrual safely and mark the market saturated without requiring another overflowing multiplication.
- Add deployment-level validation that caps are safe for the asset decimals and maximum index, while retaining runtime enforcement rather than relying only on configuration.

### Proof of Concept
1. An attacker calls `supply` for a very large position in an 18-decimal market.
2. Using separate collateral, the attacker calls `borrow` to hold approximately 98% of that market’s liquidity as debt.
3. After enough elapsed time, the attacker—or any user—calls `update_indexes`.
4. Accrual reaches `calculate_supplier_rewards`, where `borrowed.mul(new_borrow_index)` exceeds `i128::MAX` and panics with `MathOverflow`. [1](#0-0) 
5. The borrow index remains below `MAX_BORROW_INDEX_RAY`, proving the ceiling did not prevent the value overflow. [13](#0-12) 
6. Subsequent `withdraw` and `repay` calls still run `global_sync` first and revert with the same `MathOverflow`, leaving the market permanently frozen. [9](#0-8)

fn checked_add_raw(env: &Env, a: i128, b: i128) -> i128 {
    a.checked_add(b)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);

    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
