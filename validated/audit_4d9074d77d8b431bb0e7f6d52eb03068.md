### Title
`Package::build` silently produces and signs an empty tier-2 custody payload when `backend_tier2_public_key` is `None` - ([File: src/plans/personal_custody_package.rs])

### Summary
In `Package::build`, when `backend_tier2_public_key` is `None`, `tier2_single_encrypted` is derived via `unwrap_or_default()`, producing an empty byte vector instead of an error. That empty payload is then wrapped, hashed into `hashes.json`, signed via `sign(digest(&SHA256, &hashes_json))`, and uploaded to the backend as tier-2 data indistinguishable from a properly encrypted payload.

### Finding Description
`Package::build` computes tier-2 custody data as follows: [1](#0-0) 

Specifically:
- `tier2_compressed` is built from `self.make_tier2(&mut tier2)` (face IR / thermal images).
- `tier2_single_encrypted = backend_tier2_public_key.map(|k| encrypt(tier2_compressed, &k)).unwrap_or_default()` — if `backend_tier2_public_key` is `None`, this becomes an **empty `Vec<u8>`**, discarding `tier2_compressed` entirely rather than erroring.
- `tier2_encrypted = encrypt(tier2_single_encrypted, self_custody_user_public_key)` — the empty payload is then encrypted again with the user's own key, producing a small but well-formed ciphertext blob that looks structurally valid.
- `digest(&SHA256, &tier2_encrypted)` is computed and inserted into `hashes.json` as `"tier_2"` via `make_hashes_json`.
- `hashes.json` is signed (`sign(digest(&SHA256, &hashes_json))`) and both `hashes.json`/`hashes.sign` are placed in `tier0`, while `tier2_encrypted` itself is returned and later uploaded as the tier-2 package by `plans/mod.rs`: [2](#0-1) 

Because `Credentials { backend_tier2_public_key: Option<PublicKey>, .. }` is `Option`, and `build()` performs no `ensure!`/`bail!` check that this is `Some` when `pcp_version >= 3`, a session in which the backend's `BackendKeys` response omits the tier-2 key results in a syntactically valid, signed tier-0/tier-2 package pair whose `tier_2` hash and signature attest to an empty ciphertext rather than "ABSENT_TIER" or an explicit error. Note that `make_hashes_json` does use the sentinel `ABSENT_TIER` for tiers 3-5 that are unconditionally unused, but tier_2 always receives a real-looking hash regardless of whether real data was ever encrypted into it.

### Impact Explanation
The Orb's own signature (via the secure element) is applied over a hash that misrepresents an empty/degraded tier-2 payload as legitimate encrypted custody data. This breaks the invariant that signed attestations must reflect the real state of biometric data uploaded to the backend: a consumer of `hashes.sign`/`hashes.json` (e.g., backend reconciliation or audit tooling) cannot detect that tier-2 is empty, since the signature is valid, the hash matches the produced (empty) ciphertext, and there is no `ABSENT_TIER` marker as there is for unused tiers 3-5. This is an attestation-integrity defect: signed custody metadata does not faithfully represent whether backend-authorized tier-2 encryption actually occurred.

### Likelihood Explanation
This is reachable whenever a signup session's backend response (`user_status::request` / `BackendKeys`) does not include tier-2 key material while `pcp_version >= 3` is otherwise selected for the credentials — no privileged access or key compromise is required, only a backend/session state where tier-2 keys are absent. The code path executes deterministically and unconditionally for every such build, making it fully repeatable.

### Recommendation
In `Package::build`, when `pcp_version >= 3`, explicitly require `backend_tier2_public_key.is_some()` and return an error (`bail!`/`ensure!`) if it is `None`, instead of silently defaulting via `unwrap_or_default()`. Alternatively, if a missing tier-2 key is an expected/valid state, explicitly write the `ABSENT_TIER` sentinel for `"tier_2"` in `make_hashes_json` rather than hashing an empty-payload ciphertext, so the signed attestation accurately reflects the absence of tier-2 data.

### Proof of Concept
Add a unit test alongside the existing `test_generate_dummy_personal_custody_package_v3` test in `src/plans/personal_custody_package.rs`:
1. Build `Credentials` with `pcp_version = 3` and `backend_tier2_public_key = None` (and `backend_tier2_encrypted_private_key = None`).
2. Call `Package::build()`.
3. Current behavior: `build()` returns `Ok((tier0, tier1, tier2))` where `tier2` is `encrypt(Vec::new(), self_custody_user_public_key)` and `hashes.json`'s `"tier_2"` entry is a valid-looking (non-`ABSENT_TIER`) hash, with `hashes.sign` verifying successfully over it.
4. Expected/fixed behavior: assert that `build()` returns `Err(_)`, or that `hashes.json`'s `"tier_2"` value equals the `ABSENT_TIER` sentinel string, so consumers can distinguish "no tier-2 data" from "tier-2 data present."
