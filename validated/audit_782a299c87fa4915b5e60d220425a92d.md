### Title
POA Bridge withdrawal status matches by `assetId` only, causing wrong-withdrawal hash/status misreport for batched same-token withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the completion status/tx hash of a specific withdrawal (identified by NEAR tx hash + `index`) by calling `findMatchingWithdrawal`, which ignores the `index`/destination/amount entirely and matches purely on `assetId`. When a single NEAR transaction contains more than one withdrawal of the same token (e.g., to different destination addresses), every `WithdrawalIdentifier` for that token in that tx will resolve to the same (first-found) API record, regardless of which one it actually corresponds to.

### Finding Description
`describeWithdrawal` is documented to distinguish withdrawals within one tx by `index`, but the actual matching function only checks the token id: [1](#0-0) 

```

	...
}

```
/**
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 */
function findMatchingWithdrawal(withdrawals, assetId) {
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```

The `WithdrawalIdentifier` explicitly carries an `index` intended to disambiguate multiple withdrawals produced by the same NEAR transaction (this is exactly how `OmniBridge.describeWithdrawal` and `HotBridge.describeWithdrawal` use `args.index`, see e.g. `omni-bridge.ts:694-698` `transfer = (await getTransfer(...))[args.index]`). The POA bridge implementation drops this disambiguation and returns the first withdrawal in the API response whose token matches, irrespective of which index was requested. The equality broken is: *"status/hash reported for withdrawal N" != "actual on-chain outcome of withdrawal N"*.

This is consumed by `watchWithdrawal`/`waitForWithdrawalCompletion` in `core/withdrawal-watcher.ts`, which treats a `"completed"` response with a `txHash` as authoritative proof that the specific withdrawal (by index) landed on-chain: [3](#0-2) 

### Impact Explanation
If a caller batches two withdrawals of the same POA-bridged token in one NEAR transaction (e.g., to two different destination addresses/amounts — a normal use case supported by `createWithdrawalIntents` for arrays of `withdrawalParams`), `describeWithdrawal` for index 1 can return the `COMPLETED` status and destination `transfer_tx_hash` belonging to index 0's withdrawal (or vice versa) as soon as either one settles. An integrator/relayer/UI polling `watchWithdrawal` for withdrawal #1 would then treat it as finalized with a tx hash that actually corresponds to a transfer to a different address/amount — i.e., a status/hash misreport that can cause an integrator to credit or finalize a withdrawal that never actually reached its intended destination, or to report the wrong destination tx hash for reconciliation. This matches the in-scope Critical/High category "a status or hash misreport making an integrator credit or refund twice" / funds reported delivered to an address that did not actually receive them, with no automatic recovery since the mismatch is silent (no error is thrown; a plausible looking `"completed"` result is returned).

### Likelihood Explanation
This requires only two withdrawals of the *same* token in a single NEAR transaction pointing to different destinations/amounts — a supported, unprivileged usage pattern (batch withdrawals via `createWithdrawalIntents`/`sdk.createWithdrawalCompletionPromises`), not an admin/relayer misbehavior. The code comment itself acknowledges "multiple withdrawals of the same token in a single transaction are not supported," confirming the root cause is real and reachable, not speculative — it merely requires the caller to submit such a batch.

### Recommendation
Match POA withdrawal status records using both `near_token_id` and a positional/ordering key that mirrors how the POA bridge assigns withdrawals within a transaction (e.g., sort withdrawals returned by the API in creation order and pair them by the same relative ordering with the requested `withdrawalParams` for that asset, or use a stronger identifier such as destination address + amount when available), instead of only `assetId`. At minimum, `findMatchingWithdrawal` should also verify `destinationAddress` (and ideally `amount`) match the requested `withdrawalParams` before returning a status as `"completed"`, and should throw/return `"pending"` rather than silently pairing an unrelated record when multiple same-asset withdrawals exist in one tx.

### Proof of Concept
1. Submit a single NEAR transaction with two POA-bridge withdrawal intents for the same `assetId` (e.g., `nep141:btc.omft.near`), one to `destinationAddressA` (index 0) and one to `destinationAddressB` (index 1).
2. Suppose only the withdrawal to `destinationAddressA` actually settles and the POA API returns one `COMPLETED` record with `near_token_id` matching that asset and `transfer_tx_hash = "hash-A"`.
3. Call `bridge.describeWithdrawal({ ..., index: 1, withdrawalParams: { assetId, destinationAddress: destinationAddressB, ... } })`.
4. `findMatchingWithdrawal` matches on `assetId` alone and returns the record for the A-withdrawal, so `describeWithdrawal` returns `{ status: "completed", txHash: "hash-A" }` even though the withdrawal to `destinationAddressB` may still be pending or failed — confirmed by the existing test `"matches withdrawal by assetId, not by index"` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts:1054-1111`, which demonstrates the matching ignores `index` (that test only shows a benign case of different asset types, but the underlying `findMatchingWithdrawal` logic equally applies — and fails to disambiguate — when two *same*-asset withdrawals exist in one tx).

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",

		};

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
