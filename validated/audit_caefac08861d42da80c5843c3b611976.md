### Title
Webhook `shop`, `topic`, and `webhook-id` headers are trusted for shop attribution but are not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches to the handler using `request.shop`, `request.topic`, and `request.webhook_id` — none of which are covered by that HMAC. This breaks the identity binding: `hmac_valid(body) == true` is treated as equivalent to `shop_header == actual_originating_shop`, but the two are independent values.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `hmac` is read straight from the `hmac-sha256` header: [2](#0-1) 

`Registry.process` validates only that HMAC-over-body: [3](#0-2) 

but then builds `WebhookMetadata` — the object handed to the app's handler — using `request.shop`, `request.topic`, and `request.webhook_id`, all of which come straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`) and are never included in `to_signable_string`: [4](#0-3) 

The equality the gem implicitly relies on is:
`HMAC-SHA256(api_secret_key, raw_body) valid` ⇒ `shop-domain header == shop that actually sent this body`

This equality does not hold. A holder of one *valid* signed webhook payload (body + HMAC) for a given topic can replay that exact body+HMAC pair to the app's endpoint while substituting arbitrary values for the `shopify-shop-domain`, `shopify-topic`, and `shopify-webhook-id` headers, and `Utils::HmacValidator.validate` will still return `true`, because it only recomputes the signature over `raw_body`.

### Impact Explanation
Any handler that trusts `WebhookMetadata#shop` to look up or act on a specific tenant's data (a very common pattern — e.g., "look up shop record by `data.shop`, then update/delete that shop's records using `data.body`") can be made to attribute a validly-signed payload to the wrong shop. Because a merchant can freely create their own dev/trial Shopify store, install the app, and trigger a webhook for their own store (thereby obtaining a body + HMAC pair that is fully valid for the secret), they can then replay it with the `shop-domain` header swapped to a victim shop. This is a cross-tenant identity-binding break: the gem is asserting authenticity of "who sent this" using a signature that does not cover the value used to establish "who". This matches the Critical category of cross-tenant access, since it lets one authenticated (low-privilege) tenant impersonate another tenant's webhook identity in code that relies on this gem's webhook processing API.

### Likelihood Explanation
Requires network reachability to the app's public webhook endpoint (the normal deployment for Shopify webhooks) and knowledge of one valid signed payload, obtainable trivially by any unprivileged user who installs the app on their own store and observes their own webhook deliveries. No access token, `client_secret`, or privileged account is required — only the ability to create a free/trial Shopify store and install the target app, which any internet user can do.

### Recommendation
Include `shop`, `topic`, and `webhook-id` (or at minimum `shop`) in the signable content the HMAC covers, or document/enforce that `WebhookMetadata#shop`/`#topic` must not be trusted for authorization decisions without an independent cross-check against the shop for which the webhook was registered (e.g., verifying the webhook id against the shop's registered subscriptions via the Admin API before acting). Alternatively, bind the header values into `to_signable_string` so `Utils::HmacValidator.validate` fails if they are tampered with.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and registers a webhook subscription (or triggers a mandatory one such as `customers/data_request`).
2. Shopify delivers a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-topic: customers/data_request`, `x-shopify-hmac-sha256: <valid HMAC over raw body B>`.
3. Attacker captures `raw_body B` and the valid `hmac-sha256` value (both attacker-observable, no secrets required).
4. Attacker sends a new POST to the same app endpoint with the *same* `raw_body B` and *same* `hmac-sha256` header, but with `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`).
5. `ShopifyAPI::Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only [1](#0-0)  and it matches, so `Registry.process` proceeds and calls the handler with `WebhookMetadata` whose `shop` is `victim.myshopify.com` even though the payload never actually originated from Shopify on behalf of that shop [5](#0-4) .
