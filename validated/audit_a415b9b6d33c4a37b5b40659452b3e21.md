### Title
Biometric enrollment changes are not detected when "fallback to device passcode" is enabled, allowing PIN/bio-auth bypass - (File: features/auth-mobile/module/auth.js)

### Summary
The `@exodus/auth-mobile` feature implements the exact HAL-08 mitigation (invalidating cached biometric credentials when the device's enrolled biometrics change) for the plain biometric-auth path, but not for the "fallback to device passcode" path. When a consumer enables biometric auth with `fallbackToDevicePin: true`, the trigger secret is protected with `ACCESS_CONTROL_USER_PRESENCE` instead of `ACCESS_CONTROL_BIOMETRY_CURRENT_SET`, so it is not invalidated when the device's biometric enrollment set changes.

### Finding Description
For plain biometric auth, `Auth#setBioAuth` stores the `AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY` secret with `accessControl: ACCESS_CONTROL_BIOMETRY_CURRENT_SET`, and `bio-auth.ios.js#authenticate` relies on that secret becoming unreadable (`value === undefined`) to detect biometric enrollment changes and force a `BiometryChangedError` + `disableBioAuth()`: [1](#0-0) [2](#0-1) 

However, when `enableBioAuth({ fallbackToDevicePin: true })` is used, the equivalent trigger secret (`AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY`) is protected with `ACCESS_CONTROL_USER_PRESENCE` rather than `BiometryCurrentSet`: [3](#0-2) 

`getBioAuthTrigger` checks the device-auth trigger first and returns early if it is truthy, before ever consulting the biometry-current-set-protected key: [4](#0-3) 

On iOS, `kSecAccessControlUserPresence` only requires *some* successful local authentication (Face ID, Touch ID, or device passcode) at unlock time — unlike `kSecAccessControlBiometryCurrentSet`, it does not get invalidated when the enrolled biometry set changes. This means that on the `fallbackToDevicePin` path, an attacker who gains temporary access to an unlocked device, adds their own Face ID/fingerprint in device Settings, and then opens the app can successfully retrieve the `deviceAuthTrigger` secret with their own new biometric — `authenticate()` in `bio-auth.ios.js` returns `true`, and the PIN/mnemonic-protecting logic never re-prompts for the original PIN. This is the exact bug class in HAL-08 report, but the app has only partially remediated it: the fix (`BiometryCurrentSet`) was applied to the default biometric-auth path but not to the newer "fallback to device passcode" path added in `feat: support fallback to device code in bio auth` (#14688).

### Impact Explanation
If an attacker with brief physical access to an unlocked device (with `fallbackToDevicePin` biometric auth enabled) enrolls their own biometric data, they can subsequently unlock the app's sensitive operations — e.g., viewing the mnemonic phrase or authorizing signing — using their own face/fingerprint, without ever knowing the user's PIN. This is a direct wallet-compromise vector consistent with the "unauthorized signing/secret disclosure" impact bar.

### Likelihood Explanation
Requires the app to have called `enableBioAuth({ fallbackToDevicePin: true })` (i.e., the user opted into "biometrics with passcode fallback") and requires an attacker to get brief physical access to an unlocked device to add a new biometric enrollment — a realistic "friend/family/thief with momentary access" scenario, matching the original report's threat model and likelihood rating.

### Recommendation
Use `ACCESS_CONTROL_BIOMETRY_CURRENT_SET` (or an equivalent explicit re-check of biometry enrollment state via `LAContext`) for the `AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY` as well, so that any change to the device's enrolled biometrics also invalidates the passcode-fallback trigger and forces `disableBioAuth()` + mandatory PIN re-entry, exactly as already done for the plain biometric path in `features/auth-mobile/module/auth.js`.

### Proof of Concept
1. In an app consuming `@exodus/auth-mobile`, call `exodus.auth.enableBioAuth({ fallbackToDevicePin: true })` after setting a PIN.
2. On the device, add a new Face ID/fingerprint enrollment (or reset and re-enroll biometrics) while unlocked.
3. Open the app; `bio-auth.ios.js#authenticate` calls `auth.getBioAuthTrigger()`, which returns the still-valid `deviceAuthTrigger` secret (protected only by `UserPresence`) via the newly enrolled biometric.
4. `authenticate()` returns `true` without ever throwing `BiometryChangedError`, granting access to sensitive operations without a PIN prompt.
