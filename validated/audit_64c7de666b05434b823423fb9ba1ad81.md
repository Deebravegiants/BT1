Webhook shop-domain attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body. The `shop` (tenant identity) that the request claims to be from — along with `topic`, `api_version`, and `webhook_id` — is read straight from unauthenticated HTTP headers and is never included in the signed data. The library then hands this unauthenticated `shop` value directly to the app's handler as trusted tenant context, breaking the intended binding `hmac == HMAC(body, shop, topic, secret)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) without any cryptographic tie to the signature: [2](#0-1) 

`Registry.process` validates the HMAC over that body-only signable string, then immediately trusts `request.shop` (and `request.topic`) as the tenant identity forwarded to the app-provided handler: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., it validates the body, not the shop/topic headers: [4](#0-3) 

The resulting `WebhookMetadata.shop` is documented and expected to be used by apps as the shop-domain for their persistence/session lookup layer (`shop_domain: data.shop`): [5](#0-4) [6](#0-5) 

**Equality that should hold but doesn't:** `hmac_header == HMAC(secret, body || shop || topic)` — in reality `hmac_header == HMAC(secret, body)` only, so `shop` (and `topic`) can be substituted freely by anyone who can produce a body+hmac pair that was valid for *any* shop using the same app/client secret.

**Attacker capability:** All shops that install the same app share the single app `client_secret` used to compute webhook HMACs (this is standard Shopify webhook signing — one secret per app, not per shop). An unprivileged merchant who installs the app on their own store (no special privilege beyond being an ordinary app user) receives genuine webhooks for their own shop, each with a valid `X-Shopify-Hmac-Sha256` signature computed over the raw body using the shared secret. Because the signature never binds to `X-Shopify-Shop-Domain`, that same (body, hmac) pair remains valid when replayed to the app's webhook endpoint with an arbitrary `X-Shopify-Shop-Domain` header claiming to be a different, victim shop.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: `Registry.process` is the library's authentication gate for webhooks, and its only job is to assure the app that "this webhook body really came from Shopify for shop X." Because `X` is unauthenticated, an attacker can cause the app to process attacker-supplied JSON as if it were a genuine webhook event for a victim shop of their choosing, while the "valid HMAC" check still passes. Depending on how the host app implements its handler (per the gem's own documented pattern of using `data.shop` to look up sessions/enqueue jobs), this enables cross-tenant data confusion/injection — meeting the Critical "cross-tenant access" bar, since it originates purely from a boundary defect in this gem's `Registry`/`Request`/`HmacValidator` trio, not from the host app deviating from documented usage.

### Likelihood Explanation
Requires only: (1) being an ordinary merchant who installs the target app (no leaked secrets, no privileged account, no TLS interception), and (2) capturing one legitimate webhook delivery to their own endpoint/or observing HMAC values from Shopify's webhook logs replay tooling. Constructing the forged request is a simple HTTP replay with one header changed. This is squarely an "unprivileged internet user" analog once the attacker has installed the app once, which app marketplaces allow by design.

### Recommendation
Include the tenant-identifying and message-defining headers (`shop-domain` at minimum, ideally `topic` and `webhook-id`) in the HMAC-signable string in `Request#to_signable_string`, or otherwise cryptographically bind the shop attribution to the signature so `HmacValidator.validate` fails if `shop`/`topic` are altered independently of the signed payload used by Shopify. Shopify's own webhook signing spec only signs the body, so a compensating control would be to require this gem to also verify `request.shop` against a signature computed over `"#{shop}\n#{raw_body}"` if such is supported, or clearly document/enforce that the host app must independently verify `shop` against its own known/authorized-shop list before trusting `WebhookMetadata.shop` — but doing this purely in the gem removes the shared risk for every consumer.

### Proof of Concept
1. Attacker installs the target app for `attacker-shop.myshopify.com` (ordinary merchant onboarding, no elevated privilege).
2. Shopify delivers a legitimate webhook to the app: body `B`, headers include `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: H = HMAC_SHA256(app_client_secret, B)`.
3. Attacker intercepts/observes this at their own endpoint (they legitimately receive it) and constructs a new POST to the app's webhook route with the same body `B`, the same header `X-Shopify-Hmac-Sha256: H`, but `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` builds a `Request` whose `to_signable_string` is still just `B`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC_SHA256(app_client_secret, B)` and finds it equals `H` — validation passes. [7](#0-6) 
6. The app's handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"`, even though the event actually originated from/for the attacker's own shop — a cross-tenant identity forgery entirely enabled by this gem's `Request`/`Registry`/`HmacValidator` implementation.
