### Title
Reducing `unStakingPeriod` via `updateHostParams` permanently bricks consensus updates on `EvmHost` - (File: evm/src/core/EvmHost.sol, evm/src/core/HandlerV2.sol)

### Summary
This is the same root-cause pattern as the referenced Kleidi Timelock finding: a mutable duration parameter is checked against a *pre-existing* timestamp using the *current* (post-update) value of that parameter, so a legitimate reduction of the parameter can make a previously-valid state instantly "expired," and — unlike the Timelock case — there is no way to recover because every subsequent attempt re-checks the same stale timestamp against the same lowered parameter.

### Finding Description
`HandlerV2.handleConsensus` gates every consensus update with:

```solidity
function handleConsensus(IHost host, bytes calldata proof) external notFrozen(host) {
    uint256 delay = block.timestamp - host.consensusUpdateTime();
    if (delay >= host.unStakingPeriod()) revert ConsensusClientExpired();
    ...
``` [1](#0-0) 

`host.consensusUpdateTime()` is only refreshed *after* this check passes, inside the same function (`host.storeConsensusState(verifiedState)` and the subsequent state writes) [2](#0-1) . `unStakingPeriod` is a `HostParams` field that can be updated live by cross-chain governance through `updateHostParams`/`updateHostParamsInternal`, which is restricted only to the `hostManager` and only enforces a floor of `1 days`:

```solidity
struct HostParams {
    ...
    uint256 unStakingPeriod;
    uint256 challengePeriod;
    ...
}
...
function updateHostParamsInternal(HostParams memory params) internal {
    ...
    if (1 days > params.unStakingPeriod) revert InvalidUnstakingPeriod();
    ...
    _hostParams.unStakingPeriod = params.unStakingPeriod;
``` [3](#0-2) [4](#0-3) 

There is no invariant check comparing the new `unStakingPeriod` to `block.timestamp - consensusUpdateTime()` (the elapsed delay since the last real consensus update). If governance legitimately lowers `unStakingPeriod` (e.g. to match a chain's actual, shorter unbonding period, or simply mis-estimates the current delay) such that the new value is smaller than the time already elapsed since the last successful consensus update, then the very next call to `handleConsensus` computes `delay >= unStakingPeriod` as true and reverts with `ConsensusClientExpired()` *before* `consensusUpdateTime()` can be refreshed. Because the check runs unconditionally at the top of the function on every call, and `consensusUpdateTime()` never advances (the revert happens before the state write), this condition can never be resolved — every future consensus submission, from any relayer, will revert identically forever. Compare this to `pallet-ismp`'s Rust equivalent `IsmpHost::is_expired`, which has an identical shape (`host_timestamp - last_update >= unbonding_period`) checked in `update_client` before consensus verification [5](#0-4) [6](#0-5) , and the docs explicitly acknowledge that once frozen for this reason "a new consensus client must be initialized" [7](#0-6) . On the EVM side there is no equivalent recreate-the-client escape hatch exposed through ordinary governance/relayer flows — `unStakingPeriod` bricking is terminal for that `EvmHost` deployment.

### Impact Explanation
Once `unStakingPeriod` is reduced below the actual elapsed delay since the last consensus update, `EvmHost.handleConsensus` becomes permanently unusable: no relayer can ever submit a new consensus proof again, because the check that gates state advancement compares against a `consensusUpdateTime()` that can never be refreshed. This freezes the state machine commitment pipeline entirely — `handlePostRequests`, `handleGetResponses`, and both timeout handlers all depend on `stateMachineCommitmentUpdateTime`/`stateMachineCommitment` values that stop advancing [8](#0-7) . This is a "route unable to deliver messages" condition, and worse, it is unrecoverable (permanent freeze) rather than merely delayed, since the same broken invariant is re-checked identically on every future attempt. All in-flight cross-chain messages, GET requests, escrow refunds via IntentGatewayV2, and future dispatches to/from this host become permanently stuck, constituting a permanent freezing-of-funds/unsound-state-commitment class impact.

### Likelihood Explanation
The precondition (governance reducing `unStakingPeriod`) is a normal, expected, non-malicious protocol-maintenance operation — `updateHostParams` is a documented governance capability with no safeguard tying the new value to the current elapsed delay. Any modest miscalculation of the actual unbonding period, or a legitimate protocol adjustment that doesn't perfectly account for relayer submission cadence, can trigger this. Given the sensitivity of timing-based governance changes (as demonstrated by the referenced Kleidi finding being escalated to Medium for the analogous scenario), and the complete lack of a bound check in `updateHostParamsInternal`, likelihood is non-negligible for a Medium-severity classification.

### Recommendation
In `updateHostParamsInternal`, require `params.unStakingPeriod` to be greater than the currently elapsed delay (`block.timestamp - consensusUpdateTime()`) before accepting the update, or immediately refresh `consensusUpdateTime()` on parameter update so no gap opens. Alternatively, decouple the "consensus expired" check from the strict single-shot revert: allow the update itself to proceed and only assert non-expiry on *reads* of already-stored data, rather than gating the ability to advance state that would resolve the expiry. As `pallet-ismp` docs already flag: absent a recreate-client path, any code path that can permanently prevent `consensusUpdateTime` from ever refreshing must be treated as bricking and guarded accordingly.

### Proof of Concept
1. Deploy `EvmHost` with `unStakingPeriod = 10 days`; last successful `handleConsensus` call sets `consensusUpdateTime = T0`.
2. Let `block.timestamp` advance to `T0 + 8 days` (normal operation, no update yet due — this is within the safe window).
3. Governance calls `updateHostParams` (via `HostManager.onAccept` → `EvmHost.updateHostParams`) with `unStakingPeriod = 5 days` (a legitimate parameter tightening, satisfying `1 days <= 5 days`) [9](#0-8) .
4. Any relayer calls `handleConsensus` with a fresh, valid proof: `delay = 8 days`, `unStakingPeriod = 5 days` → `delay >= unStakingPeriod` is `true` → reverts `ConsensusClientExpired()` [10](#0-9) .
5. `consensusUpdateTime()` is never updated because the revert happens before `host.storeConsensusState`/related writes. Every subsequent call, from any relayer, at any future timestamp, reverts identically (`delay` only grows). The host is permanently bricked with no recovery path.

	/// Check if the client has expired since the last update
	fn is_expired(&self, consensus_state_id: ConsensusStateId) -> Result<(), Error> {
		let host_timestamp = self.timestamp();
		let unbonding_period = self
			.unbonding_period(consensus_state_id)
			.ok_or(Error::UnnbondingPeriodNotConfigured { consensus_state_id })?;
		let last_update = self.consensus_update_time(consensus_state_id)?;
		if host_timestamp.saturating_sub(last_update) >= unbonding_period {
			Err(Error::UnbondingPeriodElapsed { consensus_state_id })?
		}

		Ok(())
	}

The `freeze_client` method is used to prove the existence of a consensus fault to an onchain consensus client. This message will be sent by offchain parties, colloquially known as _fishermen_ when they detect the existence of two conflicting views of the network backed by consensus proofs. This may arise from double signing or eclipse attacks. The consensus client after successfully verifying the validity of the conflicting views of the network will go into a frozen state. In this state it can no longer process new consensus messages as well as new requests & responses. Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead.
