### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw request body [1](#0-0)  while the shop identity used by the app (`request.shop`) is read from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is never included in the HMAC computation [2](#0-1) . `HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (the body) against the shared `api_secret_key` [3](#0-2) , then `Webhooks::Registry.process` trusts `request.shop` as the tenant identity handed to the app's handler without any additional binding [4](#0-3) .

### Finding Description
The identity binding that should hold is:

`shop header claimed by request == shop that produced/authorized the signed body`

but the gem's implementation only enforces:

`HMAC(body, api_secret_key) == received HMAC`

with the `shop-domain` header excluded from the signed material entirely. Since a Shopify app's `api_secret_key` is a single shared secret across **every merchant store that has the app installed** (it is not a per-shop secret), any merchant who installs the app can legitimately receive Shopify-signed webhooks for their own store. Because the `shop-domain` header sits outside the signed payload, that same attacker-controlled request (valid body + valid HMAC) can be replayed to the app's webhook endpoint with the `shop-domain` header swapped to point at a different, victim shop. `HmacValidator.validate` will still return `true` because it only recomputes the HMAC over `@raw_body` [1](#0-0) , and `Registry.process` will dispatch the (attacker-chosen) body content to the handler tagged with the (attacker-chosen) victim shop domain [4](#0-3) .

This is directly analogous to the reported bug class: an identity/sender check is performed against the wrong or incomplete data — here the "sender" identity (`shop`) is asserted via an unauthenticated header instead of being cryptographically bound to the payload that was actually verified.

### Impact Explanation
Any app built on this gem that keys business logic (data storage, entitlement checks, GDPR/data-request processing, uninstall handling, order/customer syncing, etc.) off `WebhookMetadata#shop` is exposed to cross-tenant confusion: an attacker who is a legitimate (but unprivileged, ordinary) merchant on their own store can make the host application process arbitrary attacker-chosen webhook bodies under the identity of any other shop domain of their choosing. Depending on how the host app uses the `shop` field, this can lead to cross-tenant data corruption, spoofed compliance/webhook events attributed to a victim shop, or state changes performed against the wrong tenant record — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app on an attacker-controlled store (a normal, unprivileged action available to any Shopify merchant/internet user), (2) triggering any webhook event to capture a valid `(raw_body, hmac)` pair signed with the app's shared secret, and (3) replaying that exact body/HMAC pair to the app's public webhook endpoint with a modified `shop-domain` header. No access to `api_secret_key`, access tokens, or any privileged credentials of the victim is required.

### Recommendation
Do not treat the `shop-domain` header as authoritative tenant identity based solely on the body HMAC. Either:
- Include the shop domain (and other identifying headers) in the signed material used for HMAC verification, or
- Cross-check the header-derived shop against a shop that is independently known to be legitimately installed (e.g., verify a stored session/access token exists for that shop) before treating `request.shop` as trusted, or
- Document explicitly (and enforce in the gem) that consuming applications must independently confirm shop identity (e.g., via GraphQL admin call using a session that this shop is known to have) before acting on `shop` from `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (no privileges beyond a normal merchant account needed).
2. Attacker triggers a webhook event (e.g. `orders/create`) on their own shop; Shopify POSTs to the app's webhook endpoint with:
   - body: `{"id": 1, ...attacker-controlled order data...}`
   - headers: `x-shopify-hmac-sha256: <valid HMAC of body, signed with the app's shared api_secret_key>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`
3. Attacker replays the exact same request to the same endpoint, only changing `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (== unchanged raw body) and matches the (unchanged) HMAC header [5](#0-4) .
5. The webhook handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: <attacker-controlled body>)` [6](#0-5) , causing the host application to process attacker-controlled data under the victim's tenant identity.
