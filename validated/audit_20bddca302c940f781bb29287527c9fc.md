### Title
Permissionless, uncapped `place_bid` lets an attacker stuff unbounded bid entries onto any commitment, DOSing bid discovery and phantom-order price aggregation - ([File: modules/pallets/intents-coprocessor/src/lib.rs])

### Summary
`pallet-intents-coprocessor::place_bid` is a signed-but-unprivileged extrinsic that inserts an entry into the `Bids` `StorageDoubleMap` keyed by `(commitment, filler)`, with no upper bound on how many distinct fillers can bid on the same commitment and no validation that the commitment corresponds to a real order. Every consumer that later reads "all bids for a commitment" — the `intents_getBidsForOrder` RPC, the SDK's storage fallback, and the phantom-order price aggregator — iterates that unbounded set with no cap, mirroring the `CollateralManager.getCollateralInfo` bug class: a permissionless caller inflates a per-ID collection that a legitimate reader must fully iterate.

### Finding Description
`place_bid` only checks that the same filler hasn't already bid on the commitment; it does not cap the total number of fillers per commitment and does not require the commitment to belong to an existing order: [1](#0-0) 

The `Bids` storage is an unbounded `StorageDoubleMap`: [2](#0-1) 

The comment on the indexer schema confirms this is by design and unrestricted: "place_bid accepts any commitment" - it need not reference a real `PhantomOrderV2` at all: [3](#0-2) 

Test coverage explicitly shows multiple independent fillers bidding on the same commitment with no cap enforced: [4](#0-3) 

Downstream, both the SDK and the node's own RPC unconditionally enumerate every entry for a commitment. The SDK's storage-fallback path calls `.entries(commitment)` and then issues one additional offchain lookup **per returned bid**, in parallel, with no limit: [5](#0-4) 

The phantom-order price aggregator (`aggregatePhantomBids`) fetches this same unbounded bid set for a live `PhantomOrderRegistered` commitment and loops over every bid, SCALE-decoding, extracting the ERC-7821 fill, and running ECDSA recovery / EIP-7702 delegation checks (RPC round-trips) on each one, **before** it can reject non-solver garbage: [6](#0-5) [7](#0-6) 

The comment on this very function even flags the trust boundary: "Anyone can submit a bid to the coprocessor, and every accepted quote moves the weighted median the rest of the protocol prices intents against" - but the *volume* of bids an attacker can submit is unbounded, which is the DOS vector, distinct from the (already-handled) authenticity check.

### Impact Explanation
- **Aggregation DOS / stale or missing price snapshots**: the aggregator retries a bounded number of times (`AGGREGATION_ATTEMPTS`) and, if it can't finish within that, throws and leaves the phantom order's window "unsnapshotted" - the protocol's own reference price for that leg is not published, and consumers are left seeing a stale rate rather than a computed one.
- **Filler/solver griefing**: any legitimate filler or client calling `getBidsForOrder`/`intents_getBidsForOrder` for a commitment an attacker targeted must pay the cost of enumerating and attempting to decode every garbage entry before reaching real bids, directly analogous to the referenced report's "lender might miss best borrow offer" - here a solver-selection UI/autopilot (`BidManager.selectAndExecuteBest`) iterating `bids.length` candidates can be swamped with unusable entries, delaying or preventing selection of the genuine best bid.
- Because `place_bid` accepts *any* commitment (not necessarily a real order), the attack surface is not limited to real phantom orders - an attacker can pre-seed bloat before an order is even generated, or target any known/predictable commitment.
- The deposit required per bid is refundable (`retract_bid` returns it), so the attacker's cost is only the temporary capital lock across as many sybil accounts as needed, not a burn - making sustained spam economically cheap for a well-capitalized attacker, exactly like the referenced report's "unnecessary expenses / loss-of-funds-adjacent" framing.

### Likelihood Explanation
High: `place_bid` is a normal signed extrinsic reachable by anyone with enough balance to pay the existential deposit and the (governance-set) `StorageDepositFee`, with no per-commitment cap and no requirement that the commitment be tied to a genuine order. Sybil accounts trivially bypass the one-bid-per-filler restriction. The affected read paths (RPC, SDK, aggregator) are core parts of the intents/phantom-order bid-discovery flow and are exercised on every live order.

### Recommendation
Bound the number of accepted bids per commitment (e.g. a `BoundedVec`/max-fillers cap enforced in `place_bid`, or reject new bids once a cap is reached and the deposit/quality bar isn't beaten out), and/or require the commitment to reference an actually-registered order (checked against `CurrentPhantomOrder` or an order registry) before accepting a bid, so arbitrary/fake commitments can't be spammed at all. On the read side, cap or paginate `entries(commitment)`/`intents_getBidsForOrder` results and perform cheap authenticity checks (nonce/signature binding) before any RPC-bound verification work, so garbage bids are dropped without incurring per-bid network round-trips in the aggregator.

### Proof of Concept
1. Attacker (or a set of sybil accounts) repeatedly calls `place_bid(commitment, user_op)` for a target commitment - either an active `PhantomOrderRegistered` commitment or an arbitrary/fake `H256` - with a minimal `user_op` payload, using a fresh `AccountId` for each call to bypass the one-bid-per-filler check in `place_bid`.
2. Each call only requires reserving `StorageDepositFee`, which is refunded later via `retract_bid`; no upper bound in `Bids::<T>` prevents thousands of such entries from accumulating under the same commitment.
3. A legitimate caller invokes `intents_getBidsForOrder`/`getBidsForOrder` for that commitment (e.g. the phantom-order aggregator running per interval, or a filler's own bid-discovery flow). The response set now contains thousands of attacker entries.
4. `aggregatePhantomBids` (or `BidManager.selectAndExecuteBest`) must decode and attempt to verify every entry before filtering it out, multiplying per-bid work (SCALE decode, ERC-7821 extraction, ECDSA recovery, EIP-7702 delegation RPC check) by the attacker-controlled bid count, exhausting the aggregation retry budget and leaving the order's price snapshot unpublished, or materially delaying legitimate solver selection.

		#[pallet::call_index(0)]
		#[pallet::weight(T::WeightInfo::place_bid())]
		pub fn place_bid(
			origin: OriginFor<T>,
			commitment: H256,
			user_op: BoundedVec<u8, ConstU32<1_048_576>>,
		) -> DispatchResult {
			let filler = ensure_signed(origin)?;

			// Validate user_op is not empty
			ensure!(!user_op.is_empty(), Error::<T>::InvalidUserOp);

			// Phantom orders have stricter rules: one bid per filler, no updates, and only
			// within the configured acceptance window after the order was registered. Every
			// chain's active order is checked, not just the most recently generated one.
			if let Some(active) = CurrentPhantomOrder::<T>::get() {
				if let Some((_, info)) = active.iter().find(|(c, _)| *c == commitment) {
					let window: BlockNumberFor<T> = Self::phantom_bid_window().into();
					ensure!(
						frame_system::Pallet::<T>::block_number() <= info.created_at_block + window,
						Error::<T>::PhantomOrderBidWindowClosed
					);
					ensure!(
						!Bids::<T>::contains_key(&commitment, &filler),
						Error::<T>::DuplicatePhantomBid
					);
				}
			}

			// If a bid already exists, unreserve the old deposit first
			if let Some(old_deposit) = Bids::<T>::get(&commitment, &filler) {
				<T as Config>::Currency::unreserve(&filler, old_deposit);
			}

			let deposit = Self::storage_deposit_fee();

			// Reserve the new deposit
			<T as Config>::Currency::reserve(&filler, deposit)
				.map_err(|_| Error::<T>::InsufficientBalance)?;

			// Store the bid in offchain storage
			let bid = Bid { filler: filler.clone(), user_op: user_op.to_vec() };
			let offchain_key = Self::offchain_bid_key(&commitment, &filler);
			offchain_index::set(&offchain_key, &bid.encode());

			// Store deposit amount in onchain storage for discoverability and accurate refunds
			Bids::<T>::insert(&commitment, &filler, deposit);

			Self::deposit_event(Event::BidPlaced { filler, commitment, deposit });

			Ok(())
		}

			}

async function isVerifiedSolverBid(params: {
	userOp: PackedUserOperation
	commitment: string
	sessionKey: HexString
	chainId: bigint
	solverAccounts: readonly string[]
	evmRpcUrl: string
	recoverSigner: RecoverBidSigner
	bidNonceKey: BidNonceKeyFn
	/** Cached per aggregation, so duplicate fillers and retries do not re-read the same answer. */
	isDelegated: DelegationReader
	logger?: AggregationLogger
}): Promise<boolean> {
	const {
		userOp,
		commitment,
		sessionKey,
		chainId,
		solverAccounts,
		evmRpcUrl,
		recoverSigner,
		bidNonceKey,
		isDelegated,
		logger,
	} = params
	const solver = userOp.sender

	const parsed = splitBidSignature(userOp.signature)
	if (!parsed) {
		logger?.warn({ solver, commitment }, "Rejecting phantom bid: malformed userOp signature")
		return false
	}

	// Cheap early-out ONLY. The prefix sits inside userOp.signature, which userOpHash excludes, so it
	// is attacker-mutable and must never be what binds a bid to an order — the nonce key below is.
	if (parsed.commitment.toLowerCase() !== commitment.toLowerCase()) {
		logger?.warn(
			{ solver, commitment, signedFor: parsed.commitment },
			"Rejecting phantom bid: signed for another order",
		)
		return false
	}

	// The authoritative binding, mirroring SolverAccount.validateUserOp on-chain. The nonce IS
	// covered by userOpHash, so a solver signature stays valid only for the (order, sessionKey) pair
	// its nonce key was derived from. `sessionKey` is read from the bid's own calldata, which is also
	// covered by userOpHash — so every operand here is signed, leaving nothing for a replay to swap.
	if (BigInt(userOp.nonce) >> 64n !== bidNonceKey(commitment as HexString, sessionKey)) {
		logger?.warn({ solver, commitment }, "Rejecting phantom bid: nonce does not bind order and session key")
		return false
	}

	// SolverAccount._rawSignatureValidation recovers over the bare userOpHash and requires the signer
	// to be the account itself, which under EIP-7702 is the sender EOA.
	const signer = await recoverSigner(userOp, ENTRY_POINT_V08_ADDRESS, chainId, parsed.solverSignature)
	if (!signer || signer.toLowerCase() !== solver.toLowerCase()) {
		logger?.warn({ solver, commitment, signer }, "Rejecting phantom bid: signature does not recover to the sender")
		return false
	}

	if (!(await isDelegated(evmRpcUrl, solver, solverAccounts))) {
		logger?.warn({ solver, commitment, solverAccounts }, "Rejecting phantom bid: sender is not a delegated solver")
		return false
	}

	return true
