Confirmed and documented: the gem explicitly tells app authors to trust `data.shop` (from `WebhookMetadata`) as the tenant identity for dispatching webhook work, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)` per `docs/usage/webhooks.md`. This is the intended, documented use of the library's own API, and the root cause is entirely inside this gem's `lib/shopify_api/webhooks/request.rb` and `lib/shopify_api/webhooks/registry.rb`.

### Title
Webhook `shop-domain` (and `topic`/`webhook_id`/`api_version`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, while the `shop-domain`, `topic`, `webhook-id`, and `api-version` values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates only the body signature and then dispatches the handler using these unauthenticated header values, breaking the equality: `shop authenticated by HMAC == shop acted upon by the handler`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding to the signed content [2](#0-1) .

`Registry.process` verifies only that HMAC via `Utils::HmacValidator.validate(request)`, which internally recomputes the HMAC over `to_signable_string` (the raw body only) and compares it to the `hmac` header [3](#0-2) . After that single check passes, `process` immediately trusts `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` and forwards them to the registered handler [4](#0-3) .

Because the app's `api_secret_key` is shared across every shop that installs the app (it is not per-shop), any merchant who installs the app on their own store is a legitimate recipient of genuine, correctly-signed webhook deliveries for their own shop. Such a merchant — an "unprivileged" actor with respect to *other* tenants of the same app — can capture one legitimate `(raw_body, hmac)` pair from a webhook Shopify sent them, then replay that exact body and HMAC value to the app's public webhook endpoint while substituting the `shopify-shop-domain` (and optionally `topic`/`webhook-id`) header to name a victim shop. `HmacValidator.validate` still succeeds because it only checks the body bytes, and `Registry.process` will call the app's handler with `WebhookMetadata.shop` set to the victim shop's domain.

This is a direct instance of the reported bug class: a field (`shop`) that is acted upon by downstream logic but not covered by the integrity check (the HMAC).

### Impact Explanation
This is Critical severity: it enables cross-tenant access. The gem's own documented usage pattern instructs handlers to key all per-tenant side effects — background jobs, data lookups, session retrieval — off `data.shop` [5](#0-4) . An attacker who is a legitimate but low-privilege installer of the app can forge the tenant identity of any webhook event they can replay, causing the host application to process, store, or act on data under another merchant's identity — the kind of tenant-boundary violation explicitly listed as Critical impact (cross-tenant access).

### Likelihood Explanation
Likely. No secret material beyond what a normal, legitimate app installer already legitimately receives (their own valid webhook deliveries) is required. Replaying a captured `raw_body`/`hmac` pair with a modified `shop-domain` header is a trivial HTTP request; the gem performs no comparison between the shop that was cryptographically authenticated and any other identity binding.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-covered `to_signable_string`, or otherwise cryptographically bind these values to the signed body — for example by requiring the caller to verify the `shop` returned by `Registry.process`/`WebhookMetadata` matches an out-of-band expected session before performing tenant-scoped actions. At minimum, document loudly that `data.shop` from `WebhookMetadata` is not itself covered by the HMAC and must not be trusted as the sole tenant-identity signal without additional verification (e.g., cross-checking against a stored, previously-verified session for that topic/webhook id).

### Proof of Concept
1. App merchant M installs App on shop `m-shop.myshopify.com`. Shopify delivers a legitimate webhook to the app's endpoint: body `B`, headers include `shopify-hmac-sha256: H` (valid HMAC of `B` with the app's `api_secret_key`) and `shopify-shop-domain: m-shop.myshopify.com`.
2. M (or anyone who can observe this traffic, e.g. via a tool they control that receives the webhook) resends an HTTP request to the same app webhook endpoint with the identical body `B` and identical `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation succeeds [6](#0-5) .
4. `handler.handle` is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed_body_of_B, ...)` [7](#0-6) , causing the host application to perform tenant-scoped work (per the documented pattern of `perform_later(shop_domain: data.shop, ...)`) attributed to `victim-shop.myshopify.com` even though the event never originated from that shop.
