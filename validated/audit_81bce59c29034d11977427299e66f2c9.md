### Title
Webhook `shop`, `topic`, and `webhook-id` are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`), `topic`, and `webhook_id` used by application webhook handlers directly from HTTP headers, while its `Utils::VerifiableQuery` implementation only signs/verifies the raw request body (`to_signable_string` returns `@raw_body`). Because the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across every merchant that installs the app, any unprivileged internet user who has installed the app on their own attacker-controlled shop can obtain a legitimately-signed `(body, hmac)` pair from a real webhook delivery, then replay that exact body/HMAC to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header changed to a victim shop. `Utils::HmacValidator.validate` will report success because it never binds the signature to the shop/topic/webhook-id headers, and `Registry#process` will hand the attacker-chosen `shop` value to the registered handler as if it genuinely originated from that tenant.

and the webhook request exposes the identity fields separately from the signed content: [2](#0-1) 

`shop`, `topic`, and `webhook_id` are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id` or their `x-` prefixed equivalents) that are fully controlled by whoever sends the HTTP request to the app's endpoint, while `to_signable_string` only returns `@raw_body`. `Registry#process` validates the HMAC and then dispatches the handler using the header-derived `shop`: [3](#0-2) 

The identity binding that should hold is: *the shop the HMAC signature was computed for* == *the shop the handler is told the event came from*. Because the HMAC is computed only over the JSON body and the app's `client_secret` is identical for all merchants installing the app, this equality is not enforced — `hmac(body, secret)` is valid regardless of which shop's headers accompany that body. An unprivileged user who installs the app on a shop they control receives real webhook deliveries with valid `(body, hmac)` pairs signed with the shared secret. They can capture one such delivery and re-POST it to the app's webhook endpoint, substituting `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`). `HmacValidator.validate` still succeeds (body unchanged), and `Registry.process` invokes the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is now the attacker-chosen victim domain.

### Impact Explanation
Any application handler that uses `WebhookMetadata#shop` to scope authenticated or tenant-sensitive operations (e.g., looking up/refreshing a stored session or access token for that shop, writing/deleting per-shop data, triggering side effects keyed by shop) can be made to act on behalf of, or attribute effects to, a victim tenant the attacker never had access to — a cross-tenant confusion enabled purely by this gem's header-vs-signature mismatch. This matches the "cross-tenant access" Critical impact category, since the gem itself provides no binding between the cryptographically verified content and the tenant identity it exposes to consuming code.

### Likelihood Explanation
Likelihood is high: the attacker only needs to be a legitimate, unprivileged installer of the target app on any shop (including a free/dev store they control) to obtain valid `(body, hmac)` pairs, since the signing secret is the app-wide `client_secret`, not shop-specific. No access token, leaked credential, or privileged access is required — only the ability to send arbitrary HTTP POSTs to the app's public webhook endpoint with attacker-controlled headers.

### Recommendation
Bind the identity headers into the signed payload before verifying (e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or require the consuming application to separately authenticate the shop via a stored, shop-specific webhook secret/session rather than trusting the `X-Shopify-Shop-Domain` header). At minimum, document prominently that `WebhookMetadata#shop`/`#topic`/`#webhook_id` are unauthenticated and must not be used for tenant-scoping decisions without additional verification.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; receive a legitimate webhook delivery with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(client_secret, B)`).
2. Replay to the app's webhook endpoint:
```
POST /webhooks HTTP/1.1
X-Shopify-Topic: orders/create
X-Shopify-Hmac-Sha256: H
X-Shopify-Shop-Domain: victim-shop.myshopify.com
X-Shopify-Webhook-Id: <any>

B
```
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` since it only checks `B` against `H`, as shown in `lib/shopify_api/webhooks/request.rb` (`to_signable_string` = `@raw_body`) and `lib/shopify_api/utils/hmac_validator.rb`.
4. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"`, even though the payload actually originated from the attacker's own shop, as shown in `lib/shopify_api/webhooks/registry.rb` lines 188-200.
