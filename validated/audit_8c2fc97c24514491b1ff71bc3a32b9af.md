### Title
Escrow balance decremented after external token transfer in `withdraw()`, violating checks-effects-interactions - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron variant of `IntentGatewayV2`, the internal `withdraw()` function — invoked from `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests and from `onGetResponse()` — transfers escrowed tokens to the beneficiary via a raw low-level `.call` **before** decrementing the `_orders[commitment][token]` escrow accounting mapping. This is the same class of bug as the reported `WithdrawLp` issue: the on-chain balance tracked for a pool of escrowed funds is not synchronized with the actual transfer at the moment funds leave custody, leaving a window where the escrow bookkeeping still reflects the pre-withdrawal amount while the tokens have already left the contract.

### Finding Description
`withdraw()` in the Tron `IntentGatewayV2.sol` performs the token/native transfer to `beneficiary` first, and only afterwards updates the escrow ledger: [1](#0-0) 

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <-- decremented AFTER external call
        unchecked { ++i; }
    }
    ...
```

This is the exact analog of the reported bug class: `market.lp_escrow_amount` in `exponent_core`'s `WithdrawLp` was not decremented alongside the transfer out of escrow, so state and true custody diverged. Here the sequencing is the inverse defect of the same category — the transfer executes while `_orders[commitment][token]` (the on-chain record of what is still escrowed for that order/token) still holds the pre-withdrawal value, and only after the external call succeeds is it reconciled.

Contrast this with the canonical, corrected EVM implementation in `IntentsBase.sol`, which decrements the escrow mapping *before* making the external transfer (checks-effects-interactions): [2](#0-1) 

```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();

_orders[body.commitment][token] = escrowed - amount;
if (token == address(0)) {
    _sendValue(beneficiary, amount);
} else {
    IERC20(token).safeTransfer(beneficiary, amount);
}
```

The Tron file diverges from this pattern, reintroducing the ordering hazard the effects-before-interactions convention exists to prevent. Because native-token beneficiaries are addresses supplied in the cross-chain `WithdrawalRequest` (attacker-controlled contracts can be named as `beneficiary`), the `.call{value: amount}("")` hands control to arbitrary code before `_orders[commitment][token]` is updated. A malicious beneficiary contract can re-enter the gateway (or another interoperating call path that reads `_orders`) while the escrow accounting still shows the original, undiminished balance for that commitment/token, mirroring the report's concern that stale escrow totals cause incorrect downstream distribution and — in the reentrant case here — can permit forged/duplicate redemption of the same escrowed balance.

### Impact Explanation
If a `RedeemEscrow`/`RefundEscrow` withdrawal names a malicious contract as beneficiary of the native-token leg, that contract's `receive()`/fallback can execute mid-loop while `_orders[commitment][token]` still reports the full escrowed amount. Since `withdraw()` is only guarded by `onlyHost` and the ISMP `authenticate()` dedup at the top of `onAccept`, and the only same-transaction reentrancy barrier is `_filled[body.commitment] = beneficiary` set before the loop begins (which prevents `authenticate` from admitting a second delivery of the *same* request but does not prevent a reentrant path that reads/acts on the still-inflated `_orders` mapping directly, e.g. via `onGetResponse` or any other function keyed off `_orders`), stale escrow accounting during the external call is a genuine unauthorized-state window. This can result in incorrect settlement of order funds and — depending on what other logic consults `_orders[commitment][token]` mid-call — double accounting/theft of escrowed funds, i.e. concrete theft or unsound accounting of user/solver escrow.

### Likelihood Explanation
The vulnerable code path is reached by any relayed cross-chain settlement message (`RedeemEscrow`/`RefundEscrow`) that the `onlyHost` + `authenticate()` gate accepts — this is a normal, permissionless part of order settlement triggered by a relayer delivering a proven ISMP post request, not a privileged action. Any user who places an order and is later selected as a fill beneficiary (or a solver claiming settlement) controls the beneficiary address in the underlying `Order`/`WithdrawalRequest`, so triggering the vulnerable ordering only requires normal use of the intents flow with a malicious contract as beneficiary for the native-asset leg.

### Recommendation
Reorder `withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` to follow checks-effects-interactions: decrement `_orders[body.commitment][token]` before performing the native `.call` or ERC-20 `transfer`, exactly as done in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`. Additionally consider replacing the raw `.call`-based ERC-20 transfer with `SafeERC20.safeTransfer` for consistency with the EVM implementation and to avoid silently accepting tokens with abnormal return-value semantics.

### Proof of Concept
Not independently executed; a concrete PoC would require: (1) placing a cross-chain order whose destination-chain fill/refund path targets a native-asset input with a malicious contract as `beneficiary`; (2) having that contract's `receive()` re-enter a function that reads `_orders[commitment][address(0)]` (or trigger `onGetResponse`/a second delivery path) during the `.call{value: amount}("")` in `withdraw()`, before line `_orders[body.commitment][token] -= amount;` executes; (3) observing that the escrow ledger still reports the pre-withdrawal amount during that reentrant window, enabling an additional withdrawal/action against funds already sent out. Full exploitation would need to be validated with the actual `authenticate()`/ISMP dedup logic and any other functions that consult `_orders` to confirm a reachable double-spend, which this review did not exhaustively trace due to the length of `authenticate()` and surrounding request-kind dispatch logic.
