This confirms the vulnerability clearly. In the tron `IntentGatewayV2.sol` `placeOrder` predispatch path, `_orders[commitment][token] += reducedInputs[i].amount` at line 441 credits escrow **unconditionally**, based only on `balance` observed *before* the sweep call (line 428), never re-checking that the sweep-back transfer actually delivered funds to `address(this)`. The sweep itself (lines 430-434) is a raw, non-`safeTransfer` `IERC20.transfer` call executed via `CallDispatcher.dispatch()`, which (per `evm/src/utils/CallDispatcher.sol` lines 59-60) only checks the low-level call's `success` boolean and never inspects the ERC20 return value. Any ERC20 whose `transfer()` signals failure by returning `false` instead of reverting (a documented "weird-ERC20" behavior) will pass `CallDispatcher`'s check silently, leave the tokens stuck on the dispatcher, yet the gateway still records the order as fully escrowed.

### Title
Unchecked ERC20 return value in `CallDispatcher`-routed sweep lets escrow accounting diverge from actual token balance, enabling insolvency/fund loss - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The predispatch-swap path of `placeOrder` sweeps input tokens from the shared `CallDispatcher` back to the `IntentGatewayV2` contract using a manually ABI-encoded `IERC20.transfer` call dispatched through `CallDispatcher.dispatch()`. `CallDispatcher.dispatch()` only checks that the low-level `.call()` did not revert; it never validates the ERC20 return value [1](#0-0) . The rest of the codebase consistently uses OpenZeppelin's `safeTransfer`/`safeTransferFrom` for every other token movement (`IntentsBase._withdraw`, `IntentGatewayV2.placeOrder`'s direct-escrow branch, `ExtrinsicIntents._fillCrossChain`, `IntrinsicIntents.fillOrder`, `WrappedHyperFungibleToken`), but this sweep path is the one exception, and it is combined with escrow accounting that never re-verifies the actual post-sweep balance.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder`, when an order has a `predispatch` call:
1. Predispatch assets are pulled from the user via `safeTransferFrom` to the `dispatcher` (`CallDispatcher`) — correctly using `safeTransferFrom` [2](#0-1) .
2. The dispatcher executes the arbitrary predispatch call.
3. To sweep the resulting input tokens back to the gateway, the code reads `balance = IERC20(token).balanceOf(dispatcher)` **before** the sweep, checks `balance < requiredAmount`, and unconditionally increments `_orders[commitment][token] += reducedInputs[i].amount` — the full expected escrow amount — without ever checking the gateway's actual balance *after* the sweep executes [3](#0-2) .
4. The sweep transfer itself is built as raw calldata (`abi.encodeWithSelector(IERC20.transfer.selector, address(this), balance)`) and executed via `ICallDispatcher(dispatcher).dispatch(abi.encode(transferCalls))` [4](#0-3) [5](#0-4) .
5. `CallDispatcher.dispatch()` performs `(bool success,) = to.call{value: call.value}(call.data); if (!success) revert CallFailed(...)` — it never decodes/validates the ERC20 boolean return, so a token that returns `false` (rather than reverting) on transfer failure "succeeds" from `CallDispatcher`'s perspective while moving zero tokens [6](#0-5) .

Because the accounting is not balance-delta-based here (unlike the parallel, safer, non-tron `evm/src/apps/IntentGatewayV2.sol` implementation, which recomputes `received = balanceOf(this) - balancesBefore[i]` after the sweep [7](#0-6) ), the tron gateway will register a full escrow entry in `_orders[commitment][token]` even though the tokens never physically arrived at the gateway contract. The `dust` calculation at line 437 is also based on the pre-sweep `balance`, not what was actually received, reinforcing the false accounting.

### Impact Explanation
`_orders[commitment][token]` is the sole bookkeeping structure `_withdraw()` uses to release escrow to fillers/solvers/refunds [8](#0-7) . If escrow is credited for tokens that never actually landed on the gateway (because the underlying ERC20's `transfer()` returned `false` instead of reverting during the sweep), the gateway's aggregate `_orders` liabilities for that token exceed its real ERC20 balance. When a solver fills and redeems that fabricated escrow, the resulting `safeTransfer` in `_withdraw` is paid out of the gateway's shared token balance — funds actually deposited by *other, unrelated* users/orders for the same token — draining their legitimately escrowed balances. This is a concrete insolvency/fund-theft vector reachable from a single `placeOrder` transaction using a "weird" ERC20 as predispatch/input token, and it can also permanently strand the honest depositor's own tokens on the `CallDispatcher` (no recovery path exists there).

### Likelihood Explanation
Requires the input token used in `predispatch.assets`/`order.inputs` to be an ERC20 that signals transfer failure via `false` return (documented as common on d-xo/weird-erc20, e.g. legacy tokens or ones with blacklist/pausable transfer gates) rather than reverting, and for that failure condition to be triggerable at sweep time (e.g. the gateway address being blacklisted, or the token temporarily paused). This is not universal to all ERC20s, but the protocol explicitly designs the intent gateways to be permissionless with arbitrary user-supplied token addresses, and the sibling non-tron implementation already anticipates and safely handles non-standard transfer semantics (fee-on-transfer) via balance-delta accounting — the tron variant omits that safety net for this one code path while every other transfer/escrow path in the codebase uses `safeTransfer`/`safeTransferFrom`, making this an inconsistency/regression rather than a fundamentally new risk category.

### Recommendation
Make the sweep-back transfer in `evm/tron/contracts/apps/IntentGatewayV2.sol::placeOrder` verify actual receipt before crediting escrow, matching the pattern already used in `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before the sweep `dispatch()` call, and after it, compute `received = balanceOf(this) - before`, then credit `_orders[commitment][token] += min(received, reducedInputs[i].amount)` (adjusting `order.inputs`/reverting on insufficient receipt) instead of unconditionally crediting `reducedInputs[i].amount`. Additionally, have `CallDispatcher.dispatch()` (or a dedicated safe-sweep helper) validate ERC20 return data using OpenZeppelin's `SafeERC20`/`Address.functionCall` semantics so that tokens returning `false` are treated as failures consistently with the rest of the codebase.

### Proof of Concept
1. Deploy (or use) an ERC20 `T` whose `transfer()` returns `false` (without reverting) whenever the recipient (the `IntentGatewayV2` proxy) is on an internal blacklist, or when paused — mirroring real-world tokens with this semantic.
2. Attacker places an order via `placeOrder` with `predispatch.call`/`predispatch.assets` set to move `T` into the `CallDispatcher`, and `order.inputs = [{token: T, amount: X}]`.
3. Before/during the predispatch call, arrange for `T.transfer(gateway, balance)` to return `false` (e.g., transiently pause `T`, or if `gateway` is blacklisted for that token instance the attacker deployed/configured).
4. `CallDispatcher.dispatch()` sees `success == true` (the call didn't revert) and returns normally; the tokens remain on `CallDispatcher`.
5. `placeOrder` nonetheless executes `_orders[commitment][T] += reducedInputs[i].amount`, crediting escrow for tokens the gateway does not actually hold.
6. Attacker (or colluding solver) fills the order; `_withdraw()` calls `IERC20(T).safeTransfer(beneficiary, amount)`, which succeeds by drawing on `T` balance the gateway holds from *other* users' legitimately escrowed orders — realizing theft/insolvency for those other depositors.
