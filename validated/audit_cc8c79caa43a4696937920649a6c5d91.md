### Title
Webhook `shop` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats an incoming webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, and then dispatches the handler using `request.shop`, which is read straight from the unauthenticated `shopify-shop-domain` HTTP header rather than from any HMAC-covered material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

while `Webhooks::Request#shop` is parsed from a header that is never fed into the signable string: [2](#0-1) 

`Registry.process` validates the HMAC and, on success, immediately trusts `request.shop` to build `WebhookMetadata` for the handler: [3](#0-2) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`: [4](#0-3) 

Because `to_signable_string` is just the raw body, the HMAC binds only `{body, api_secret_key}` — it does **not** bind `{body, shop}`. The `api_secret_key` is the app's single client secret shared across every merchant that installs the app; Shopify computes the exact same HMAC-SHA256 over the same body regardless of which shop it's for. Consequently:

- Authenticated invariant claimed by the docs: `data.shop` is described as "The shop domain of the webhook" and is used directly as a tenant key in the documented example (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`). [5](#0-4) 
- Actual invariant enforced by the gem: `hmac == HMAC(secret, body)`, with **no** cryptographic tie between that HMAC and the `shop` value that the handler receives.

**Equality that should hold but doesn't:** `shop_bound_by_hmac == shop_delivered_to_handler`. The gem only guarantees `body_bound_by_hmac == body_delivered_to_handler`; `shop` is out-of-band and attacker-controllable.

### Impact Explanation
An unprivileged internet user can install the target app on their own (attacker-controlled) shop — a normal, unprivileged action any Shopify merchant can perform. Shopify will deliver genuine webhooks to that installation, each correctly signed with the app's `api_secret_key` over the raw body, and carrying the attacker's own shop domain in the `shopify-shop-domain` header. Because that header is not part of the signed content, the attacker can capture such a request and replay it to the app's webhook endpoint after rewriting only the `shopify-shop-domain` (and, if desired, `webhook-id`/`topic`) headers to a victim shop's domain. `HmacValidator.validate` still passes because the body/HMAC pair is untouched, and `Registry.process` forwards `shop: <victim-shop>` to the handler, letting the attacker inject forged events (e.g., `app/uninstalled`, `orders/create`, `customers/data_request`) that the host application will process as if they came from the victim tenant. This is a cross-tenant boundary break, meeting the Critical bar (cross-tenant access via forged tenant identity) without requiring the app's secret, an access token, or any privileged account.

### Likelihood Explanation
Any merchant/developer can install the app on a shop they control to legitimately harvest correctly-signed webhook payloads, then replay them with a substituted shop header — no secret material or elevated access is needed. The only precondition is that the host application, following the gem's documented pattern, uses `data.shop` as the tenant key without independently re-verifying it (e.g., against its own list of installed shop IDs/webhook IDs), which is exactly the pattern shown in this gem's own documentation.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is HMAC-verified, or require host applications to cross-check `request.shop` against a per-shop webhook secret/registration record before trusting it. At minimum, update `Webhooks::Request#to_signable_string` (or add a secondary check in `Registry.process`) so that the shop domain cannot be swapped without invalidating the signature, and document explicitly that `data.shop` is not currently covered by the HMAC and must not be used as an authoritative tenant identifier on its own.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`.
2. Shopify sends a legitimately signed webhook, e.g.:
   ```
   POST /callback/orders/create
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: <valid HMAC of body B computed with app's api_secret_key>
   x-shopify-shop-domain: attacker-shop.myshopify.com
   Body: B
   ```
3. Attacker replays this exact request to the app's webhook endpoint, only changing the header:
   ```
   x-shopify-shop-domain: victim-shop.myshopify.com
   ```
   Body `B` and `x-shopify-hmac-sha256` are left untouched.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` (the raw body `B`) and the HMAC are unchanged (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:12-31`).
5. The handler is invoked with `WebhookMetadata` where `shop == "victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload never actually originated from or concerned that shop — a cross-tenant identity spoof.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
