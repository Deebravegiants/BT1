### Title
Front-running `Initialize2` permanently blocks (or hijacks) canonical pool creation for a market via deterministic AMM PDA squatting - (File: `program/src/processor.rs`)

### Summary
The `AmmInfo` account address (along with `target_orders`, `lp_mint`, `coin_vault`, `pc_vault`) is not passed in freely by the caller but is derived deterministically from the `market` account key alone via `get_associated_address_and_bump_seed(program_id, market_key, seed, program_id)` inside `generate_amm_associated_account` / `generate_amm_associated_spl_token` / `generate_amm_associated_spl_mint`. Because the derivation depends only on the publicly-known `market` pubkey (and the comment in the code explicitly notes the "market" account is not validated — "Just a seed for AMM account. Can be any account."), any unprivileged actor can call `Initialize2` first for a target market, permanently occupying that deterministic address before the legitimate pool creator's transaction lands.

### Finding Description
`process_initialize2` creates all pool-related accounts through `generate_amm_associated_account`, which checks ownership before creating: if the account's current owner is the system program it allocates/assigns it to the AMM program; otherwise it returns `AmmError::RepeatCreateAmm`. [1](#0-0) 

This is invoked for the `AmmInfo` account itself using `AMM_ASSOCIATED_SEED` and the `market_info` key as the sole seed input: [2](#0-1) 

Since the resulting PDA is fully deterministic from `program_id` + `market` pubkey + fixed seed bytes, and the `market` account is explicitly *not* required to be a genuine, unused OpenBook/Serum market (per in-code comment "Just a seed for AMM account. Can be any account."), the address that a legitimate deployer will use for a given market is fully predictable in advance — exactly analogous to the `WeightedIndex` report where the pool's address is predictable ahead of pool creation.

An attacker can submit their own `Initialize2` instruction referencing the same `market` key (with attacker-controlled mints, vaults, and minimal `init_coin_amount`/`init_pc_amount`) before the legitimate creator's transaction is confirmed. This succeeds in creating and initializing the `AmmInfo` account (and its associated vaults/lp mint/target orders) at the exact address the legitimate market operator intended to use, moving its owner away from the system program.

### Impact Explanation
Once the attacker's `Initialize2` lands first:
- The legitimate creator's subsequent `Initialize2` call for the same `market` permanently reverts with `AmmError::RepeatCreateAmm`, because the `AmmInfo`/vault/lp-mint accounts are no longer owned by the system program. [3](#0-2) 
- This is a **permanent** condition — the deterministic PDA for that market can never be reclaimed or reset by the legitimate party, permanently freezing the ability to launch the canonical Raydium AMM pool for that market.
- Worse, because the address is the expected canonical pool address for that market, downstream integrators, UIs, or users who trust "the Raydium pool for market X" could be led to interact with (and deposit funds into) the attacker-seeded pool instead of a legitimate one, since the attacker fully controls the pool's mints/vaults/initial ratio at creation time.

### Likelihood Explanation
Likelihood is low-to-moderate: it requires the attacker to know the target `market` pubkey before the legitimate `Initialize2` transaction is confirmed (e.g., by observing a pending transaction or by monitoring newly-listed OpenBook markets that are commonly known ahead of pool launch) and to race it with their own transaction referencing the same seeds/mints layout. This mirrors the exact "Impact: High / Likelihood: Low" characterization in the referenced report.

### Recommendation
Do not rely solely on a raw ownership check (`owner == system_program`) to gate creation of the deterministic AMM-associated accounts. Instead:
- Validate that the `market` account is a genuine, program-recognized OpenBook/Serum market before deriving/creating pool accounts from it, removing the "can be any account" allowance.
- Consider binding pool creation to additional creator-specific entropy (e.g., a creator-supplied nonce/salt in the PDA seeds) rather than purely `market`, so the resulting address cannot be pre-empted by an unrelated party.
- Alternatively, allow a legitimate market's original intended creator to reset/reclaim a squatted, low-value pool (e.g., one whose `init_coin_amount`/`init_pc_amount` fall below a sane minimum) rather than permanently failing.

### Proof of Concept
1. Attacker observes/derives a `market` pubkey that a legitimate operator intends to use for a Raydium pool (markets are public and typically known ahead of AMM launch).
2. Attacker computes the deterministic addresses for `AmmInfo`, `target_orders`, `lp_mint`, `coin_vault`, `pc_vault` using `get_associated_address_and_bump_seed(program_id, market, <SEED>, program_id)`, exactly as `generate_amm_associated_account`/`generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint` do. [4](#0-3) 
3. Attacker submits `Initialize2` for that `market` with attacker-owned mints/wallet and minimal `init_coin_amount`/`init_pc_amount`, landing before the legitimate creator's transaction.
4. Attacker's transaction succeeds: `amm.status` becomes `WaitingTrade`/`SwapOnly` and all associated accounts are owned by the AMM program. [5](#0-4) 
5. Legitimate creator's later `Initialize2` for the same `market` now fails at `generate_amm_associated_account` with `AmmError::RepeatCreateAmm`, permanently blocking the canonical pool for that market. [3](#0-2)
