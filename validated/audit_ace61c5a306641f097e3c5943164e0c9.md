### Title
Withdrawal of escrowed intent tokens can revert on underflow instead of capping to the available escrow - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw` releases escrowed order tokens to a beneficiary by subtracting the requested `amount` from the tracked `_orders[commitment][token]` balance without ever checking that `amount` does not exceed what is actually escrowed. It only guards against a fully-zeroed entry (`if (escrowed == 0) revert UnknownOrder();`), not against a partial mismatch. This mirrors the reported bug class: a withdrawal path with no cap/clamp to the actually-available balance, so a legitimate withdrawal request for slightly more than what remains reverts the whole delivery instead of settling for what is available.

### Finding Description
`_withdraw` is the single settlement path for `RedeemEscrow` and `RefundEscrow` cross-chain messages and for same-chain fills/cancels: [1](#0-0) 

The escrow amount released is taken directly from the amount encoded in the incoming `WithdrawalRequest`, not clamped to `_orders[commitment][token]`. When a cross-chain fill happens, `_fillCrossChain` builds this withdrawal body using `order.inputs` — the original, full input amounts declared at order placement — and dispatches it as the `RedeemEscrow` message to the source chain: [2](#0-1) 

Separately, the gateway's own test suite demonstrates that the amount actually escrowed at `placeOrder` time can be *less* than the raw `order.inputs` amount once a protocol fee is deducted (e.g. 990 USDC escrowed out of 1000 USDC declared, and a correctly-reduced amount must be supplied to `_withdraw` to redeem it without reverting): [3](#0-2) 

Because `_fillCrossChain` posts `order.inputs` (the pre-fee amount) rather than the fee-adjusted escrowed balance, the `RedeemEscrow` message dispatched to the source chain can request more than `_orders[commitment][token]` actually holds. On delivery, `_withdraw`'s `_orders[body.commitment][token] = escrowed - amount;` underflows and reverts (Solidity 0.8 checked arithmetic) instead of clamping to the available balance, exactly the failure mode the external report describes for a naive withdrawal against an external balance.

### Impact Explanation
Because the withdrawal amount is fixed inside the committed cross-chain POST request body, a relayer cannot alter it on retry — every redelivery attempt decodes the same `WithdrawalRequest.amount` and hits the same underflow revert. This can permanently strand the user's/solver's escrowed input tokens on the source chain: the order is already marked filled/cancelled on the destination side, but the source-chain escrow can never be released because every delivery of the settlement message reverts. This is a permanent freezing-of-funds condition reachable from an ordinary user/solver transaction (placing and filling a cross-chain intent order with a non-zero protocol fee), not requiring any malicious or privileged actor.

### Likelihood Explanation
This triggers whenever `protocolFeeBps` (or a destination-specific fee) is non-zero for a cross-chain order, which is an ordinary, expected configuration (the test suite explicitly exercises 10% protocol fees). Any solver performing a normal cross-chain fill on such an order would produce a `RedeemEscrow` request whose amount is inconsistent with the fee-reduced escrow, making this readily reachable rather than a contrived edge case.

### Recommendation
In `_withdraw` (`evm/src/apps/intentsv2/IntentsBase.sol`), clamp the requested amount to the tracked escrow before transferring/decrementing, mirroring the pattern recommended in the referenced report:
```solidity
uint256 escrowed = _orders[body.commitment][token];
if (escrowed == 0) revert UnknownOrder();
if (amount > escrowed) amount = escrowed;
_orders[body.commitment][token] = escrowed - amount;
```
Additionally, ensure `_fillCrossChain` (and `_cancelFromDest`/`_cancelFromSource`) encode the actual fee-adjusted escrowed amount in the `WithdrawalRequest` body rather than the raw `order.inputs` amount, so the two values stay consistent and a clamp is only ever a defensive backstop.

### Proof of Concept
1. Deploy `IntentGatewayV2` (cross-chain variant using `ExtrinsicIntents`) with a non-zero `protocolFeeBps` (e.g. 10%, as in `testProtocolFeeWith10Percent`).
2. User places a cross-chain order with `inputs = [1000 USDC]`; at placement, the protocol fee is deducted so `_orders[commitment][USDC] = 900 USDC` (illustrative) while `order.inputs[0].amount` remains `1000 USDC`.
3. A solver fills the order on the destination chain via `fillOrder`/`_fillCrossChain`, which dispatches `RedeemEscrow` with `tokens = order.inputs` i.e. amount `1000 USDC`.
4. When this message is delivered to the source chain's `onAccept` → `_withdraw`, `_orders[commitment][USDC] (900) - amount (1000)` underflows and reverts.
5. Every subsequent relayer redelivery of the same committed request decodes the same fixed `1000 USDC` amount and reverts identically, permanently freezing the 900 USDC still escrowed for that order.

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
