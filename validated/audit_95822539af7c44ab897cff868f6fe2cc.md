### Title
Webhook shop-tenant identity is trusted from an unauthenticated header, not from the HMAC-covered payload - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the `X-Shopify-Hmac-Sha256` signature, but that HMAC only covers the raw request body. The `shop` value that is subsequently used to attribute the event to a tenant is read directly from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) . `Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it with the value in the `hmac` header: [2](#0-1) . `Registry.process` only checks this body HMAC before dispatching the event: [3](#0-2) . The tenant identity handed to the app's handler, `request.shop`, is read straight from the `shop-domain` header with no cryptographic binding to that header: [4](#0-3) .

Critically, the HMAC secret used here (`Context.api_secret_key`) is the app's single `client_secret`, shared across every merchant/tenant that has installed the app — it is not shop-specific. This means the equality the code implicitly assumes:

`shop_bound_by_hmac == shop_used_for_tenant_attribution`

does not hold. The HMAC only proves "some shop that has installed this app sent this body with the app's shared secret." It proves nothing about which shop the `shop-domain` header claims to be.

### Impact Explanation
Because the secret is shared across all tenants, an unprivileged user who controls one shop that has installed the app can receive a legitimately HMAC-signed webhook for their own store (e.g. a webhook whose body content is generic/predictable, or one they can trigger repeatedly with different bodies), then replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to name a different, victim shop. `Registry.process` will validate the (unchanged) body HMAC successfully and will invoke the app's handler with `WebhookMetadata` claiming the event belongs to the victim tenant: [5](#0-4) . If the host application uses `data.shop` to select which tenant's records to update (a well-documented, expected use of the field per `docs/usage/webhooks.md`), this is a cross-tenant data-integrity/spoofing primitive — the confused-deputy pattern is directly analogous to the sysvar-account trust bug: an unvalidated identity carrier (the sysvar account / the shop header) is trusted as if it had passed the cryptographic check that was actually applied to a different piece of data (the instruction results / the raw body).

### Likelihood Explanation
Exploitation requires only being a legitimate merchant/tenant of the app (an "unprivileged" role relative to other tenants) capable of receiving at least one real webhook and capturing/replaying its raw body and signature while forging headers to the app's own publicly reachable webhook endpoint. No access to `api_secret_key`, tokens, or any privileged credential is required beyond what any installed merchant already has by virtue of having the app on their store.

### Recommendation
- Do not trust `request.shop` for tenant attribution unless it can be tied to the HMAC-verified payload. Prefer deriving/cross-checking the shop from a value embedded in and covered by the signed body (or use the webhook `body["shop_domain"]"`/resource identifiers that are actually part of the JSON payload) rather than an HTTP header.
- If continuing to rely on the header, cross-validate `shop-domain` against the shop associated with the specific `webhook_id` returned by Shopify's Admin API before trusting it for any write/read operation, or scope such checks to a session already known to belong to that shop.
- Document (and enforce in the gem, if feasible) that `WebhookMetadata#shop` is not itself part of the signed material and must not be used as the sole tenant-authorization key without additional verification.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the target app and triggers a webhook with generic content, e.g. `{}` for topic `some/topic`. The app receives:
   - `X-Shopify-Hmac-Sha256: <valid HMAC of "{}" using the app's shared client_secret>`
   - `X-Shopify-Shop-Domain: attacker.myshopify.com`
2. Attacker captures these headers/body (they legitimately received this webhook).
3. Attacker POSTs the same raw body `{}` to the app's public webhook endpoint again, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` while keeping the identical `X-Shopify-Hmac-Sha256` value (since the HMAC is computed only over the unchanged body).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because the signature check only inspects `@raw_body`, per `lib/shopify_api/utils/hmac_validator.rb:12-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
5. The app's handler executes with `WebhookMetadata.new(... , shop: "victim.myshopify.com", ...)`, per `lib/shopify_api/webhooks/registry.rb:198-199`, even though the request never actually originated from Shopify on behalf of `victim.myshopify.com`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
