### Title
Session ID Derived From an Unauthenticated, Predictable Cookie Value Enables Cross-Tenant Session Hijacking - (`lib/shopify_api/utils/session_utils.rb`)

### Summary
`ShopifyAPI::Utils::SessionUtils.current_session_id` derives the session lookup key from a raw, client-supplied cookie value with zero cryptographic verification, while the alternative embedded-app path derives the same kind of ID only from a signature-verified JWT. Because session IDs are deterministic strings built from the shop domain (and user id), an unauthenticated request can set the cookie itself and cause the calling application to resolve — and therefore act as — a completely different, victim tenant's session, breaking the binding `{authenticated shop} == {session acted upon}`.

### Finding Description
For embedded apps, `current_session_id` computes the session ID from a cryptographically signed JWT (`Auth::JwtPayload`, HS256-signed with `api_secret_key`), so the `shop`/`sub` claims used to build the ID are authenticated: [1](#0-0) 

For the cookie path (used for non-embedded apps, and as a fallback for embedded apps when no `shopify_id_token` is supplied), the method does nothing but echo back the raw cookie value as the session ID: [2](#0-1) 

The `SessionCookie` type that carries this value is a plain struct with no MAC/signature field at all: [3](#0-2) 

The value stored in that cookie is deterministic and predictable — it is exactly the `Session#id`, computed from the shop domain (and, for online sessions, the numeric user id) with no random or secret component: [4](#0-3) 

The documented integration pattern is to use this returned ID directly as the storage lookup key for the victim's persisted `Session` (which holds the real Shopify access token): [5](#0-4) 

The equality that should hold is: `session.shop == the tenant the current unauthenticated request actually belongs to`. Before the attack, this holds because the cookie was originally set by the gem itself after a validated OAuth callback (`session.id` from a genuine `Session`). After the attack, the attacker (any user able to set a cookie on their own browser, e.g. a malicious merchant of the same multi-tenant app) sets `shopify_app_session` to a *guessed/known* victim ID such as `offline_victim-shop.myshopify.com`, and `cookie_session_id`/`current_session_id` return that ID verbatim with no check that it was ever issued by this gem or belongs to the requester. Unlike the HMAC-validated OAuth/webhook paths or the signature-validated JWT path, this is a session identifier accepted with no authentication at all — exactly the "session id derived from unauthenticated bytes" bug class.

### Impact Explanation
If the host application follows the documented pattern (storage keyed by the ID returned from `current_session_id`), an attacker can force the lookup of another merchant's `Session` object, gaining access to that merchant's stored Shopify access token and using it to make Admin/GraphQL API calls as the victim shop. This is a cross-tenant access / session hijacking scenario (Critical), achieved without possessing any credential — the attacker only needs to know or guess a target's `*.myshopify.com` domain (and, for online sessions, a numeric user id), both of which are commonly discoverable.

### Likelihood Explanation
Likelihood is high for apps using the cookie-based session flow (the gem's own documented non-embedded flow, and the fallback path for embedded apps without a JWT): `offline_<shop>` and `<shop>_<user_id>` are simple, predictable formats, and shop domains are frequently public/guessable, especially for multi-tenant SaaS apps where any signed-up merchant can attempt to target another known merchant.

### Recommendation
- Short term: Do not treat the raw cookie value as a trusted session identifier. Sign/MAC the cookie value (e.g., HMAC with `api_secret_key`, as is already done for OAuth/webhook payloads) and verify that signature in `cookie_session_id`/`current_session_id` before returning it.
- Long term: Make the cookie-based session ID retrieval consistent with the JWT path by requiring a verifiable proof of the shop/session ownership (e.g., binding the cookie to a signed token) rather than an opaque, guessable string, and document this expectation clearly so host apps don't unknowingly use an unauthenticated value as a tenant-scoped lookup key.

### Proof of Concept
1. Attacker signs up their own store `attacker.myshopify.com` and installs the target app, learning that session IDs follow the pattern `offline_<shop>` (from `Auth::Session.from`, `lib/shopify_api/auth/session.rb:116`).
2. Attacker sets their browser cookie: `shopify_app_session=offline_victim-shop.myshopify.com` (a shop they do not own, but whose domain they know from public storefront branding).
3. Attacker calls the host app's endpoint (built on this gem's documented pattern) that does:
   ```ruby
   session_id = ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)
   # => "offline_victim-shop.myshopify.com" (returned as-is, per
   #    lib/shopify_api/utils/session_utils.rb:68-71 and the passing test
   #    test_non_embedded_app_current_session_id_returns_id_from_cookie)
   session = MyApp::SessionRepository.find(session_id)
   ```
4. The host app loads `victim-shop`'s persisted `Session` (with its real access token) and the attacker's subsequent request is executed by the gem's `HttpClient`/GraphQL client as that victim shop, using the victim's `access_token` header (`lib/shopify_api/clients/http_client.rb:28-32`).
