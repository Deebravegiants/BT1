### Title
Embedded NUL byte causes DonID truncation mismatch in Gateway node handshake authentication - (File: core/services/gateway/network/handshake.go)

### Summary
The Gateway's node connection handshake packs `DonID`/`GatewayID` into fixed-length byte fields using `StringToAlignedBytes`, which does not reject or strip embedded NUL (`0x00`) bytes despite its own comment stating the input "can't have any 0x0 characters." The signature is computed over these raw, un-validated bytes. When the same payload is later parsed with `AlignedBytesToString`, the string is truncated at the *first* NUL byte. This mirrors the OpenVPN CVE-2017-7522 root cause: a string embedded in a cryptographically-verified structure, containing a NUL byte, is interpreted differently by the value that gets signed/verified versus the value that gets used for identity/authorization decisions.

### Finding Description
`StringToAlignedBytes` simply `copy()`s the input into a fixed-size buffer with no validation: [1](#0-0) 

`AlignedBytesToString`, used to decode the same kind of buffer, truncates at the first zero byte: [2](#0-1) 

These are used asymmetrically in the node handshake protocol: `PackAuthHeader` packs `DonID`/`GatewayID` with `StringToAlignedBytes` (no NUL rejection), and the signature is computed over the full byte buffer via `ExtractSigner`, while `UnpackSignedAuthHeader` recovers `elems.DonID`/`elems.GatewayID` with `AlignedBytesToString` (NUL-truncating) for use in subsequent authorization checks (e.g., `ErrAuthInvalidDonID`): [3](#0-2) 

Because the signature is verified over the raw, un-truncated bytes (`data[:len(data)-HandshakeSignatureLen]`), an attacker-controlled node can produce a validly-signed auth header where the signed byte buffer contains `"attacker-don\x00victim-don-padding..."`, but the `DonID` value that the gateway subsequently uses for routing/authorization decisions is only `"attacker-don"` (truncated at the NUL). This creates a mismatch between what is cryptographically committed to and what is actually authorized/routed — the same class of confusion as an X.509 CN with an embedded NUL being interpreted differently by the signature-verifying code path versus the display/authorization code path in the CVE.

By contrast, the equivalent legacy-message validation in `api/message.go` was hardened against a related issue by explicitly rejecting NUL-*suffixed* IDs, showing this class of bug was already recognized as a risk in this codebase: [4](#0-3) 

However, that check only rejects a NUL character at the *end* of the string; it does not reject NUL bytes anywhere, and the handshake path (`network/handshake.go` / `network/common/utils.go`) has no equivalent check at all.

### Impact Explanation
This affects the internet-facing Gateway's node authentication handshake, which determines which DON a connecting node is authorized to act on behalf of. A NUL-truncation mismatch between the signed payload and the value used for authorization checks can lead to DonID confusion/spoofing at the handshake layer, potentially letting a connection be associated with, or routed for, a different DON identity than what was actually signed — an authentication/identity-confusion issue rather than a simple crash, but rooted in the same "trusted string with embedded NUL is parsed inconsistently" bug class as the CVE.

### Likelihood Explanation
Exploitability requires a party capable of establishing a node connection to the Gateway and controlling the `DonID` value in its signed auth header (i.e., an authenticated-but-otherwise-unprivileged connecting node, akin to the CVE's "authenticated remote attacker"). I was not able to fully trace, within the available tool budget, the exact downstream code in `connectionmanager.go`/`ConnectionAcceptor` that consumes `elems.DonID` from `UnpackSignedAuthHeader` to confirm whether the truncated value is used for a security-relevant routing/authorization decision (vs. only logging or non-security bookkeeping). This should be verified before treating the impact as confirmed exploitable.

### Recommendation
- Reject any DonID/GatewayID (and other identifiers packed via `StringToAlignedBytes`) containing embedded NUL bytes at construction/signing time, consistent with the existing intent documented in the code comment.
- Make `AlignedBytesToString` fail (return an error) rather than silently truncate when it encounters a NUL byte before the expected end of a variable-length field that hasn't been explicitly declared NUL-padded, or otherwise ensure the decoded string used for authorization exactly matches what was signed.
- Audit all call sites of `StringToAlignedBytes`/`AlignedBytesToString` (handshake packing/unpacking, and any other identity fields) for the same asymmetry.

### Proof of Concept
1. Craft a handshake auth header where `DonID = "attacker-don\x00" + padding` using `PackAuthHeader`.
2. Sign the full packed byte buffer with the attacker's private key (as `UnpackSignedAuthHeader`'s `ExtractSigner` call verifies over the raw bytes, this validates successfully).
3. Send this to the Gateway's `StartHandshake`. `UnpackSignedAuthHeader` will decode `elems.DonID` via `AlignedBytesToString`, truncating to `"attacker-don"` — a value that was never independently, cleanly signed over on its own, but is trusted for subsequent DonID-based authorization decisions.

(Note: full confirmation of a concrete authorization bypass requires reviewing how `elems.DonID` returned from `StartHandshake`/`UnpackSignedAuthHeader` is subsequently compared/enforced in `core/services/gateway/connectionmanager.go`, which I could not complete within the available investigation budget.)

func AlignedBytesToString(data []byte) string {
	idx := slices.IndexFunc(data, func(b byte) bool { return b == 0 })
	if idx == -1 {
		return string(data)
	}
	return string(data[:idx])
}

func PackAuthHeader(elems *AuthHeaderElems) []byte {
	packed := common.Uint32ToBytes(elems.Timestamp)
	packed = append(packed, common.StringToAlignedBytes(elems.DonID, HandshakeDonIDLen)...)
	packed = append(packed, common.StringToAlignedBytes(elems.GatewayID, HandshakeGatewayURLLen)...)
	return packed
}

func UnpackSignedAuthHeader(data []byte) (elems *AuthHeaderElems, signer []byte, err error) {
	if len(data) != HandshakeAuthHeaderLen {
		return nil, nil, fmt.Errorf("auth header length is invalid (expected: %d, got: %d)", HandshakeAuthHeaderLen, len(data))
	}
	elems = &AuthHeaderElems{}
	offset := 0
	elems.Timestamp = common.BytesToUint32(data[offset : offset+HandshakeTimestampLen])
	offset += HandshakeTimestampLen
	elems.DonID = common.AlignedBytesToString(data[offset : offset+HandshakeDonIDLen])
	offset += HandshakeDonIDLen
	elems.GatewayID = common.AlignedBytesToString(data[offset : offset+HandshakeGatewayURLLen])
	offset += HandshakeGatewayURLLen
	signature := data[offset:]
	signer, err = common.ExtractSigner(signature, data[:len(data)-HandshakeSignatureLen])
	return elems, signer, err
}
