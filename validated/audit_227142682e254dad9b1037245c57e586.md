### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signable string from the raw request body only, never including the `X-Shopify-Shop-Domain` (or `topic`/`api-version`/`webhook-id`) header values. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` to identify which tenant the webhook belongs to when invoking the app's handler.

### Finding Description
`Utils::HmacValidator.validate` recomputes an HMAC over `verifiable_query.to_signable_string` and compares it with the `hmac` value using `OpenSSL.secure_compare` [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) , while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers with no cryptographic binding to the signature [1](#0-0) .

This breaks the intended identity binding: `hmac_valid(body) == true` should imply `shop_header == shop_that_actually_sent(body)`, but the equality only ever holds for `hmac_valid(body)`, independent of `shop_header`. Because the app's `api_secret_key` is shared across all shops/installations of the app, any party that can obtain one legitimately-signed webhook body for the app (e.g., by installing the app on their own store and capturing a real webhook delivery, since HMAC-SHA256 over the body with the shared secret is identical regardless of which shop sent it) can resend that same body with an arbitrary `X-Shopify-Shop-Domain` header pointing at a victim shop. `Registry.process` only checks `Utils::HmacValidator.validate(request)` [5](#0-4)  and then dispatches to the handler using `request.shop` unchecked [6](#0-5) , so the forged shop attribution passes verification.

### Impact Explanation
An attacker who controls a genuine install of the app on any shop (their own) can forge webhook deliveries that the host application will process as belonging to a different, victim shop/tenant, since the shop attribution is not authenticated. Depending on how the host app's `WebhookHandler` implementations use `WebhookMetadata#shop` (e.g., to key session/token lookups, trigger uninstall/redact flows, or update per-shop state), this enables cross-tenant data corruption or actions taken against a shop the attacker does not control — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Exploitation requires only that the attacker be able to send arbitrary HTTP POST requests to the app's public webhook endpoint (unprivileged internet capability) and possess one validly-signed payload from any shop using the app (trivially obtainable by installing the app on their own store, which is normal, unprivileged app usage). No access to `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signed payload verification, e.g., include the shop domain header in `to_signable_string`, or independently verify that the shop asserted in the header matches an expected/authorized shop for the webhook subscription (such as by tracking webhook_id-to-shop associations from registration) before dispatching to handlers.

### Proof of Concept
1. Install the app on attacker-controlled shop `attacker.myshopify.com`; trigger any webhook (e.g. `orders/create`) and capture the raw request: body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(secret, B)`, and `secret` is the same for every shop using this app).
2. Replay a new POST to the app's webhook endpoint with the same body `B` and same `X-Shopify-Hmac-Sha256: H`, but change `X-Shopify-Shop-Domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: ...)` builds successfully [7](#0-6) ; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `B` against `H` [8](#0-7) .
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: ..., ...)` [6](#0-5) , causing the host app to process an attacker-controlled event as if it originated from the victim shop.
