### Title
Arbitrary stateless `EmporiumOperation` calls let any caller sweep leftover/stuck token balances held by the shared `EmporiumUpgradeable` contract - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction` executes user-supplied `EmporiumOperation` entries either through a per-user `HinkalWallet` (`invokeWallet == true`) or, when `stack.signerAddress == address(0)`, directly from the shared `EmporiumUpgradeable` contract's own context/balance with **no signature verification at all**. Its "balance equation" (`balanceChange = balancesAfter[i] - balancesBefore[i]`) is computed only over the specific `circomData.erc20TokenAddresses` array passed in the *current* transaction. Any ERC-20 balance that ends up sitting on the shared `EmporiumUpgradeable` contract from a prior interaction (dust/refund from a swap op, tokens not included in a previous call's `erc20TokenAddresses`, etc.) is invisible to that equation and stays on the contract indefinitely. Because stateless ops are unconstrained, any user can submit a trivial valid Hinkal transaction whose Emporium op is simply `token.transfer(attacker, token.balanceOf(address(emporium)))`, directly draining that leftover balance to themselves — exactly analogous to the GoodEntry `RangeManager.initRange` bug where refunded underlying tokens left in the contract could be swept via an unrelated `cleanup()` call.

### Finding Description
`runAction` snapshots balances only for the tokens listed in `circomData.erc20TokenAddresses` for *this* call, runs the ops, and diffs before/after to mint `UTXO`s back to `msg.sender`: [3](#0-2) 

The ops themselves, when `stack.signerAddress == address(0)`, are executed directly by `EmporiumUpgradeable` (`op.endpoint.call{value: op.value}(op.callData)`) with only a selector-blacklist for `callHinkalWallet`/`doSendToRelay` — otherwise arbitrary target and calldata: [4](#0-3) 

`verifyWallet` performs zero validation of the ops themselves when there is no signer address, only nonce-marking (`usedMessages`): [2](#0-1) 

Because `EmporiumUpgradeable` is a single shared contract used across all users (not a per-user vault — that role is played by `HinkalWallet`, only reached when `invokeWallet == true`), any residual ERC-20 balance left on it — e.g., a swap op that leaves an intermediate/refund token not tracked in that transaction's `erc20TokenAddresses`, or ETH/tokens accidentally sent — persists on-chain, unattributed to any UTXO, and outside the scope of the balance-equation check for the transaction that produced it. A later, completely unrelated caller can submit a valid Hinkal proof for their own (even zero-value) transaction, routed through Emporium, with a crafted stateless op such as `IERC20(dustToken).transfer(attacker, dustToken.balanceOf(address(emporium)))`. This call succeeds unconditionally (the loop only checks `success`), transferring out the dust directly — bypassing the `handleOut`/`balanceChange` bookkeeping entirely since the theft happens inside the op call itself, not through the UTXO-crediting path.

This breaks the intended equality that a user's credited/withdrawn value through `runAction` must correspond only to the value that user's own shielded inputs/deposits produced during their transaction (`balanceChange` should represent this-call value only) — instead, an attacker can extract value that belongs to the protocol / other users' stranded leftovers with no shielded backing at all.

### Impact Explanation
This allows unauthorised movement of assets held by the Emporium contract that were never entitled to the caller — a direct analog to "theft or permanent freezing of protocol/relay fees" / "executing calls or moving assets a wallet owner or prover never authorised" (High impact per the given rubric). Any leftover balance from complex multi-hop DeFi interactions run through Emporium (swap refunds, unswept intermediate tokens, mis-tracked `erc20TokenAddresses`) becomes permanently stealable by the next arbitrary caller, rather than being recoverable by its rightful owner or the protocol.

### Likelihood Explanation
Likelihood is meaningfully high for any deployment that uses Emporium for arbitrary DeFi calls (its whole purpose per the wiki's "Emporium: Arbitrary DeFi Execution" feature): any external call in `stack.ops` that doesn't perfectly consume/report every touched token (a very common occurrence with swap routers, LP refunds, reward claims, rounding) leaves stealable dust. No special privilege is needed — only a normal user's own valid Hinkal proof for their own (potentially trivial) transaction, since the ops content is completely free-form when `signerAddress == address(0)`.

### Recommendation
- Require `EmporiumUpgradeable` to sweep/settle its *entire* token balance (not just the tracked `circomData.erc20TokenAddresses`) after every `runAction`, or restrict stateless ops to a strict allow-list of endpoints/selectors that cannot move arbitrary ERC-20 balances out of the contract.
- Alternatively, disallow the `signerAddress == address(0)` (no-wallet, no-signature) execution path for calls whose `op.endpoint` is an ERC-20 token contract, or require the full audited whitelist for stateless targets, mirroring the mitigation pattern from the GoodEntry fix (sweep remaining balances back / add strict post-op balance checks so nothing is left unaccounted for on the shared contract).

### Proof of Concept
1. Any user's Emporium transaction (op #1 in some `stack.ops`) performs a swap/DeFi call whose external protocol refunds excess input token `X` back to `EmporiumUpgradeable` (`msg.sender` of that external call), and `X` is not included in that transaction's `circomData.erc20TokenAddresses` — the refund is invisible to the `balanceChange` loop and stays on the Emporium contract.
2. Attacker submits their own trivial, otherwise-valid Hinkal transaction (any small/zero-value shielded transact) routed to Emporium with `stack.signerAddress = address(0)` and a single op: `{endpoint: X, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, IERC20(X).balanceOf(address(emporium))))}`.
3. `verifyWallet` performs no check on op content since `signerAddress == address(0)`; the loop in `runAction` executes `X.transfer(attacker, dustAmount)` directly from the Emporium contract, succeeding and draining the dust to the attacker — entirely outside of, and unaccounted for by, the subsequent `handleOut` UTXO-crediting logic for the attacker's own declared `erc20TokenAddresses`.
