### Title
Permanent DoS / Front-Running of `LockupFactory::create()` via Predictable `owner_account_id`-Derived Account Salt — (File: `lockup-factory/src/lib.rs`)

### Summary
`LockupFactory::create()` derives the lockup contract's account name deterministically from `sha256(owner_account_id)` and nothing else, then uses it as the target of `Promise::new(..).create_account()` [1](#0-0) . Because the call is fully permissionless ("It allows any user to create and fund the lockup contract" / "Lockups can be funded from any account") [2](#0-1) , any unprivileged attacker who observes a pending `create()` transaction for a given `owner_account_id` in the mempool can front-run it with their own `create()` call for the same `owner_account_id`, controlling `vesting_schedule`, `release_duration`, and `whitelist_account_id`. This is the exact same root cause pattern as the referenced Joyn finding: a caller-visible value (there, `merkleRoot`; here, `owner_account_id`) is used unmodified as a unique deployment identifier/salt with no binding to `msg.sender` or a reservation step.

### Finding Description
`create()` computes:
```rust
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
``` [3](#0-2) 
and then attempts `create_account()` on that exact NEAR account name [4](#0-3) . Since `lockup_account_id` depends only on `owner_account_id` (a value the legitimate depositor must reveal on-chain to create the intended employee's lockup) and NEAR account names are globally unique and immutable once created, any address can be "claimed" by whoever's `create()` transaction lands first for that `owner_account_id`.

Unlike a legitimate collision, `create()` is public and unauthenticated — there is no check that `msg.sender`/`predecessor_account_id` is the foundation, the owner, or any other privileged party, and no commitment/reservation of the `owner_account_id` prior to submission. This mirrors the disclosed `SplitFactory.createSplit()` bug where `merkleRoot` alone was used as `salt`, allowing anyone to front-run and permanently squat the deterministic address.

### Impact Explanation
Because `owner_account_id` is a fixed identity (the employee/beneficiary's own account) that the real depositor cannot change, and the derived contract address depends solely on that identity, an attacker can:
1. Observe a pending, legitimate `create()` call for a target `owner_account_id` in the mempool.
2. Submit their own `create()` call for the same `owner_account_id` with a higher gas price and attacker-chosen `vesting_schedule` (e.g. `None`, stripping the vesting/termination guarantee entirely since `foundation_account_id` is only set `if vesting_schedule.is_some()` [5](#0-4) ), `release_duration`, or a malicious `staking_pool_whitelist_account_id`.
3. Cause the legitimate transaction's `create_account()` to fail (the account already exists), triggering the refund path in `on_lockup_create` [6](#0-5) , while the account name for that `owner_account_id` is now permanently occupied by the attacker's lockup with attacker-chosen (and potentially malicious/foundation-stripped) parameters.

Since the lockup account name is a pure function of `owner_account_id`, this occupation is irreversible through this factory — the intended beneficiary can never receive a lockup deployed by legitimate, correctly-configured parameters at that deterministic address again. This matches the in-scope impact: "Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in lockup release ... flows," and, via the stripped vesting/whitelist configuration, also the state-transition/authority-bypass impact for lockup flows.

### Likelihood Explanation
The attack requires only observing a public, unconfirmed `create()` transaction (any full mempool watcher can do this) and submitting a competing transaction with a higher gas/priority — no privileged role, keys, or trusted access are needed, satisfying the "strictly unprivileged, public entrypoint" requirement. The attacker's cost is limited to `MIN_ATTACHED_BALANCE` (3.5 NEAR) plus gas [7](#0-6) , which is modest relative to potential griefing/manipulation value, especially for high-value beneficiary accounts (e.g. team/investor lockups) whose `owner_account_id` is often known or predictable in advance.

### Recommendation
Bind the deployment address to the caller and/or add explicit reservation/authorization:
- Include `env::predecessor_account_id()` in the derivation of `lockup_account_id` (e.g. `sha256(predecessor_account_id || owner_account_id)`), so only the intended funder's transaction can produce that specific address, or
- Restrict `create()` to only be callable by the `foundation_account_id` (or another authorized funder) for a given `owner_account_id`, or
- Require a prior on-chain reservation/commitment of `owner_account_id` bound to `predecessor_account_id` before allowing `create_account()` to proceed.

### Proof of Concept
1. Foundation broadcasts `create({"owner_account_id":"alice.testnet", "vesting_schedule": Some(hash)})` intending to fund Alice's vesting lockup.
2. Attacker observes this pending transaction, computes the same `lockup_account_id = sha256("alice.testnet") + "." + factory_account`, and submits `create({"owner_account_id":"alice.testnet", "vesting_schedule": None})` with higher gas price and the minimum required deposit.
3. Attacker's transaction lands first, calling `create_account()` on `lockup_account_id` successfully and deploying a lockup contract with no vesting/foundation termination rights configured (`foundation_account_id: None` because `vesting_schedule.is_some()` is false) [5](#0-4) .
4. Foundation's original transaction's `create_account()` fails since the account already exists; `on_lockup_create` refunds the attached deposit [8](#0-7) , but the deterministic account for `owner_account_id = "alice.testnet"` is now permanently occupied with the attacker-chosen, vesting-free configuration.

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```
