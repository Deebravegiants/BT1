### Title
Front-runnable beneficiary redirect in `accumulate` lets an attacker strip the signed beneficiary and misdirect relayer fees - (File: `modules/pallets/relayer/src/accumulate.rs`)

### Summary
`Pallet::accumulate` is dispatched via an **unsigned extrinsic** carrying an attacker-visible `WithdrawalProof`. The proof's `beneficiary_details: Option<(beneficiary_address, signature)>` is the only mechanism binding the relayer's fee payout to a chosen beneficiary instead of the on-chain `delivery_address`. Because the extrinsic is unsigned and the proof (state proofs + optional beneficiary signature) is public before inclusion, anyone can strip the `beneficiary_details` field from the observed proof and resubmit an otherwise-identical `accumulate` call ahead of the relayer's own submission — exactly the "extract signature from mempool, use it (or omit it) to consume state before the original call lands" pattern in the referenced Aave `supplyWithPermit` report.

### Finding Description
`accumulate` validates the source/destination state proofs and determines `delivery_address` (the address that is cryptographically proven, via the destination receipt trie, to have delivered the requests) and `total_fee`. [1](#0-0) 

If the relayer wants the fee routed to a different account, it supplies `beneficiary_details`, whose signature is checked against a per-`(delivery_address, state_machine)` nonce, then the nonce is bumped and fees are credited to `beneficiary_address`: [2](#0-1) 

If `beneficiary_details` is absent, the same commitments are simply credited to `delivery_address` instead, and no nonce is touched: [3](#0-2) 

Because `accumulate` is unsigned and its full argument (`WithdrawalProof`, including the beneficiary signature) is visible in the transaction pool before inclusion, an attacker can:
1. Observe the relayer's pending `accumulate(withdrawal_proof)` call containing valid `source_proof`/`dest_proof` and a `beneficiary_details` signature redirecting the payout.
2. Re-encode and submit their own `accumulate(withdrawal_proof')` with the identical `commitments`, `source_proof`, `dest_proof`, but `beneficiary_details = None`, with higher priority/tip so it lands first.
3. Because commitment membership/claim state is derived purely from the state proofs (not from the caller), this attacker-submitted call passes all the same verification and marks the commitments `claimed = true`, crediting the fee to `delivery_address` rather than the relayer's intended `beneficiary_address`.
4. When the original, beneficiary-carrying `accumulate` call is mined afterward, `RequestCommitments` for those commitments are now `claimed`, so the filter step removes them and the call reverts with `MissingCommitments`: [4](#0-3) 

The nonce-binding comment explicitly documents that the nonce exists only to prevent *replay* of a beneficiary signature, not to prevent an attacker from *omitting* it entirely on a front-run: [5](#0-4) 

### Impact Explanation
This is a griefing/unauthorized-redirect bug on the relayer fee and reward accounting path explicitly in scope. It allows any unprivileged observer to override a relayer's authorized fee-beneficiary choice by racing the original transaction, causing the fee to land on `delivery_address` instead of the relayer-chosen `beneficiary_address`. Depending on why the relayer wanted the redirect (e.g., `delivery_address` is a hot/automation key not intended to accumulate value, or the relayer's operational security model assumes fees always land at the signed beneficiary), this can force funds onto an unintended account and break the redirect guarantee the nonce/signature scheme is meant to provide. I could not verify, within the available context, whether `delivery_address` retains full withdrawal control equivalent to `beneficiary_address` (i.e., whether this is fully recoverable via a later signed redirect) — the `withdraw_fees` implementation was not inspected in this session, so the exact permanence of the misdirection cannot be confirmed from the code shown here.

### Likelihood Explanation
High from a mechanics standpoint: `accumulate` is unsigned, so no signer state prevents replay/front-run submission, the proof data needed to reconstruct a stripped call is fully public once broadcast, and no commitment-level binding ties `beneficiary_details` to the specific commitments being claimed (an attacker only needs to observe one pending transaction and resubmit with higher priority).

### Recommendation
Bind `beneficiary_details` to the commitment set/claim itself (e.g., include the commitments or `delivery_address`+commitments hash inside the signed `beneficiary_message`, and reject `accumulate` calls that omit `beneficiary_details` when a signed redirect for those specific commitments is required), or require the redirect signature to be validated and applied atomically with the claim in a way that a beneficiary-less resubmission of the same proof cannot pre-empt it — e.g., make the beneficiary redirect a prerequisite validated before allowing an unsigned no-beneficiary claim of the same commitments, or move fee redirection to a signed, sequenced extrinsic rather than optional data on a permissionless unsigned call.

### Proof of Concept
Conceptual sequence (no on-chain harness was available in this session to fully execute):
1. Relayer R delivers a request and prepares `accumulate(WithdrawalProof { commitments, source_proof, dest_proof, beneficiary_details: Some((B, sig)) })` to redirect its fee to cold wallet `B`.
2. R broadcasts this unsigned extrinsic; it is visible in the pool.
3. Attacker A copies `commitments`, `source_proof`, `dest_proof` from R's pending call, sets `beneficiary_details: None`, and submits with a higher priority so it is included first.
4. A's call passes proof verification (state proofs are independent of caller identity), marks the commitments claimed, and credits `total_fee` to `delivery_address` (R's proven delivery key), per [3](#0-2) .
5. R's original call is included afterward; the already-claimed commitments are filtered out, leaving `withdrawal_proof.commitments` empty, and the call fails with `Error::<T>::MissingCommitments` per [4](#0-3) , so R's intended redirect to `B` never takes effect.

/// Signed payload authorising a beneficiary redirect on a specific source chain.
/// Including the relayer nonce alongside the state machine keeps the signature usable for
/// exactly one accumulate call on that chain, mirroring how `withdraw_fees` binds its signed
/// payload.
pub fn beneficiary_message(
	nonce: u64,
	state_machine: StateMachine,
	beneficiary: &[u8],
) -> [u8; 32] {
	sp_io::hashing::keccak_256(&(nonce, state_machine, beneficiary).encode())
}
