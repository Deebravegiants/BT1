### Title
SimplexPaymaster prices gas using Chainlink feeds without checking the L2 sequencer uptime status, permitting mispriced/stale prices during sequencer downtime or restart - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster` computes the ERC-20 price of gas from Chainlink `AggregatorV3Interface.latestRoundData()` feeds and only validates positivity and staleness against `maxOracleAge`. It never checks an L2 Sequencer Uptime feed, even though the paymaster is deployed on L2s (e.g. Base) where the sequencer can go down and, per Chainlink's guidance, prices can be stale or wrong for a grace period after the sequencer comes back up — exactly the bug class in the referenced report, but here there is no sequencer check at all (not even the "is up" check the report criticizes as incomplete).

### Finding Description
`_getOraclePrice` is the sole gate on oracle data used for pricing: [1](#0-0) 

It only reverts on `answer <= 0` or `block.timestamp - updatedAt > maxOracleAge`. It has no notion of an L2 sequencer uptime oracle, so it cannot detect that the underlying chain's sequencer was recently down and is restarting — the scenario the Chainlink L2 docs warn produces wrong prices even though `updatedAt` may look "fresh" relative to `maxOracleAge`.

This price feeds directly into `_tokenPrice`, which is used both to validate/prefund UserOps and to compute swap outputs when recycling fees: [2](#0-1) [3](#0-2) 

The deployment script's own comments confirm the paymaster targets L2s with heartbeat-based (not sequencer-uptime-based) staleness reasoning, and Base/Ethereum are explicitly named targets: [4](#0-3) 

No sequencer-status check exists anywhere in the repository outside of the Arbitrum rollup-proving code (`sequencer_batch_acc`, unrelated to Chainlink's uptime feed), confirming this gap is unaddressed for the paymaster's oracle path.

### Impact Explanation
Any unprivileged UserOp sender can trigger `fetchDetails`/`validate`/`_postOp`, all of which call into `_tokenPrice` → `_getOraclePrice`. During or shortly after a sequencer outage on the deployed L2, the Chainlink price feed can be reporting an incorrect price while still passing the `updatedAt` staleness check (the round may have been updated just before or right as service resumes, with the underlying price answer not yet reflecting the correct market rate). An attacker who anticipates or observes this window can submit UserOps priced with the stale/incorrect rate, obtaining gas sponsorship at a mispriced (potentially near-zero) token cost and draining the paymaster's `EntryPoint` deposit, or the `swapAndDeposit` fee-recycling path could execute swaps at a bad price. This is a concrete funds-drain/mispricing vector reachable from a single unprivileged transaction, matching the required "unbacked" cost/mint style impact.

### Likelihood Explanation
Sequencer downtime and restarts are a known, recurring operational event on rollups (Base, Optimism, Arbitrum have all had documented sequencer outages). Because the contract performs zero sequencer-status validation, every restart event is a window of exposure, and exploiting it only requires submitting an ordinary UserOp through the paymaster during that window — no privileged access or governance compromise needed.

### Recommendation
Add an L2 Sequencer Uptime Feed check (chain-appropriate `AggregatorV3Interface`) in `_getOraclePrice`, verifying both that `answer == 0` (sequencer up) and that `block.timestamp - startedAt` exceeds a configured grace period (e.g. 3600s) before trusting any price/gas computation, mirroring Chainlink's documented `_sequencer_up`-plus-grace-period pattern, and reverting (e.g. with a new `SequencerDown`/`GracePeriodNotOver` error) otherwise.

### Proof of Concept
1. Deploy `SimplexPaymaster` on an L2 (e.g. Base) with a Chainlink token/USD and native/USD feed as in `DeploySimplexPaymaster.s.sol`.
2. Simulate the chain's sequencer going down and coming back up; the underlying Chainlink price feed round is updated at restart but reports a value that has not caught up to the true market price (a known real-world occurrence, as `updatedAt` will be recent enough to pass `maxOracleAge`).
3. Because `_getOraclePrice` (`evm/src/utils/SimplexPaymaster.sol:662-676`) has no sequencer-uptime check, `_tokenPrice` returns the incorrect price.
4. An attacker submits a UserOp through `fetchDetails`/`validate`, which prices gas using this incorrect rate, paying far less token than the actual gas cost and draining the paymaster's `EntryPoint` deposit over repeated ops during the exposure window.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
