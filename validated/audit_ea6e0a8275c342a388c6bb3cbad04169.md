Confirmed: `ShopifyAPI::Auth::Oauth.validate_auth_callback` never calls `ShopValidator.sanitize!` on `auth_query.shop`, unlike `ClientCredentials.client_credentials`, `RefreshToken`, `TokenExchange`, and `Storefront`, which all sanitize the shop before constructing a `Session` or `HttpClient`. The HMAC validation in `HmacValidator.validate` only proves the callback's `shop` param bytes weren't tampered with in transit — it says nothing about normalization — so a validly-signed callback for `Attacker-Shop.MYSHOPIFY.com` passes HMAC and state checks, then flows unnormalized into `Session.new(shop: auth_query.shop)` at `lib/shopify_api/auth/oauth.rb:73`, `Clients::HttpClient.new(session: null_session, ...)` at `lib/shopify_api/auth/oauth.rb:81` (whose `@base_uri` at `lib/shopify_api/clients/http_client.rb:18` becomes `https://Attacker-Shop.MYSHOPIFY.com`), and `Session.from(shop: auth_query.shop, ...)` at `lib/shopify_api/auth/oauth.rb:97`, producing `session.id = "offline_Attacker-Shop.MYSHOPIFY.com"` instead of the sanitized `"offline_attacker-shop.myshopify.com"` that `ShopValidator.sanitize!` would have produced (lowercasing via `uri_from_shop_domain`'s `shop_domain.to_s.downcase.strip` at `lib/shopify_api/utils/shop_validator.rb:85`).

### Title
OAuth callback trusts un-sanitized `shop` for session identity and API host — case/format divergence from every other entry point - (File: lib/shopify_api/auth/oauth.rb)

### Summary
`validate_auth_callback` validates the HMAC and `state` on the raw `auth_query.shop` string but never runs it through `Utils::ShopValidator.sanitize!`, unlike `ClientCredentials`, `RefreshToken`, `TokenExchange`, and `Storefront`. This lets an attacker who legitimately installs an app on their own dev shop but sends the `shop` param with different case/whitespace produce a validly-HMAC'd callback whose resulting `Session.id` and `HttpClient` base URI never match the sanitized identity used everywhere else in the app.

### Finding Description
The binding claimed broken: `auth_query.shop (as validated by HMAC, byte-for-byte) == Utils::ShopValidator.sanitize!(auth_query.shop) (as used for session identity/host everywhere else)`.

In `validate_auth_callback` (`lib/shopify_api/auth/oauth.rb:60-113`), `Utils::HmacValidator.validate(auth_query)` (`lib/shopify_api/utils/hmac_validator.rb:12-22`) computes an HMAC over `to_signable_string` (`lib/shopify_api/auth/oauth/auth_query.rb:33-43`), which encodes `code, host, shop, state, timestamp` exactly as received — it validates integrity of the bytes, not their normalized form. Since Shopify signs the callback based on whatever `shop` value the app's authorize redirect built into the OAuth flow (attacker fully controls the `shop` string passed to `begin_auth`, since it's their own dev shop install), the attacker can complete a real OAuth install where the `shop` query param carries mixed case (e.g., `Attacker-Shop.MYSHOPIFY.com`). This value passes `HmacValidator.validate` and the `state` check untouched, then flows into `Auth::Session.new(shop: auth_query.shop)` (`lib/shopify_api/auth/oauth.rb:73`), `Clients::HttpClient.new(session: null_session, ...)` whose `@base_uri` becomes `https://#{session.shop}` (`lib/shopify_api/clients/http_client.rb:18`), and `Session.from(shop: auth_query.shop, ...)` (`lib/shopify_api/auth/oauth.rb:97`), which builds `id = "offline_#{shop}"` or `"#{shop}_#{associated_user.id}"` (`lib/shopify_api/auth/session.rb:114-117`) directly from the unsanitized string.

By contrast, `ClientCredentials.client_credentials` calls `validated_shop = Utils::ShopValidator.sanitize!(shop)` before constructing the session and `HttpClient` (`lib/shopify_api/auth/client_credentials.rb:25-26`), and `RefreshToken`/`TokenExchange`/`Storefront` do the same. `ShopValidator.sanitize!` lowercases and strips the shop (`shop_domain.to_s.downcase.strip` at `lib/shopify_api/utils/shop_validator.rb:85`), so the same physical shop produces different `Session#id` values depending on which entry point of the gem created the session — `oauth.rb` skips normalization entirely.

Existing guards don't stop this: `HmacValidator.validate` only checks byte-equality of the signed string against a recomputed HMAC — it has no normalization step. `state == auth_query.state` only checks the CSRF nonce. `Context.setup?`/`private?` don't touch shop format. There is no `ShopValidator.sanitize!` call anywhere in `oauth.rb`.

### Impact Explanation
An app's session-store lookup (keyed by the sanitized shop domain used by `ClientCredentials`, `RefreshToken`, embedded JWT `dest`/session token flows, or by the host app's own webhook `X-Shopify-Shop-Domain` normalization) will use `ShopValidator.sanitize!`-style lowercase/canonical shop strings, while the OAuth-callback-created session is keyed by whatever case Shopify happened to echo back in the `shop` query param. In practice Shopify typically returns the shop domain already lowercased, so exploitability depends on whether Shopify's callback echoes attacker-influenced casing — the gem's own code path provides no defense-in-depth against it, unlike every sibling auth flow in the same codebase. This is a real internal inconsistency/missing-normalization defect in this gem's code (`lib/shopify_api/auth/oauth.rb`), but I could not confirm from this repository's code alone whether Shopify's OAuth server itself would echo a non-canonical `shop` value in a validly HMAC-signed callback — that behavior is external to this gem and not verifiable from the code I have access to.

### Likelihood Explanation
Requires the host app to store/look up sessions keyed by a sanitized shop form obtained from another gem entry point (or its own normalization) while trusting `validate_auth_callback`'s session as-is, and requires Shopify's OAuth callback to actually echo a non-canonical `shop` string despite the app requesting a normalized one — the latter is outside this gem and unverified here.

### Recommendation
Call `Utils::ShopValidator.sanitize!(auth_query.shop)` in `validate_auth_callback` (`lib/shopify_api/auth/oauth.rb`) immediately after the HMAC/state checks, and use the sanitized value for `Auth::Session.new`, `Clients::HttpClient.new`, and `Session.from`, mirroring `ClientCredentials.client_credentials` (`lib/shopify_api/auth/client_credentials.rb:25-26`).

### Proof of Concept
A minitest + WebMock test would stub `https://attacker-shop.myshopify.com/admin/oauth/access_token` (the sanitized host), construct an `AuthQuery` with `shop: "Attacker-Shop.MyShopify.com"` and a correctly computed HMAC over that exact mixed-case string using `Context.api_secret_key`, call `Oauth.validate_auth_callback`, and assert `result[:session].id != Session.from(shop: ShopifyAPI::Utils::ShopValidator.sanitize!("Attacker-Shop.MyShopify.com"), access_token_response: ...).id`, while also asserting via WebMock that the actual HTTP request during `validate_auth_callback` was sent to host `Attacker-Shop.MyShopify.com` rather than the sanitized `attacker-shop.myshopify.com`. However, this PoC only demonstrates an internal library inconsistency; it does not by itself demonstrate that Shopify's real OAuth server would send back a non-canonical `shop` value in a genuinely signed callback, which is required to actually trigger this from an unprivileged internet attacker as scoped.
