### Title
Webhook `shop-domain` Header Not Covered by HMAC Signature, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, excluding the `shop-domain` header from the HMAC-verified data. `ShopifyAPI::Webhooks::Registry.process` trusts `request.shop` (derived from that unauthenticated header) when dispatching webhook data to the app's handler, even though the HMAC check only proves the *body* is authentic, not which shop it belongs to.

### Finding Description
The identity binding that should hold is:
`shop attributed to the webhook payload == shop that Shopify actually generated the HMAC for`

In `lib/shopify_api/webhooks/request.rb`: [1](#0-0) 
`shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, and `to_signable_string` — the value that gets HMAC-verified — is defined as `@raw_body` only, with no header data mixed in.

`Utils::HmacValidator.validate` (used by `Registry.process`) only checks that the `hmac` header matches a signature computed over `verifiable_query.to_signable_string`: [2](#0-1) 

Since `to_signable_string` is just the body, this proves the *body bytes* are authentic (came from someone holding `api_secret_key`), but it proves nothing about the `shop-domain` header. `Registry.process` nonetheless passes the unauthenticated `request.shop` straight to the app's handler as the tenant identifier: [3](#0-2) 

So the bytes that are cryptographically verified (`raw_body`) are not the bytes that are actually acted upon for tenant attribution (`shop` header). This is the exact "bytes verified vs. bytes parsed / field acted on but not covered by the HMAC" class of bug described in the external report (there, `_FEE_RATE_` was set/used in places the validation fix didn't reach; here, `shop` is used in a context the HMAC coverage doesn't reach).

### Impact Explanation
Any user who can obtain one validly-signed webhook body for a shop they legitimately control (e.g., a merchant installing the app on their own store and triggering an `orders/create`/`app/uninstalled` webhook with attacker-influenced body content) can replay that exact body+HMAC pair while substituting the `shop-domain` header for a different (victim) shop domain. Because the header is outside the signed data, `HmacValidator.validate` still returns `true`, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop. Any app logic keyed off `data.shop` (writing per-tenant records, triggering per-tenant side effects, cache/session invalidation, etc.) is then executed against the wrong tenant — a cross-tenant data/identity confusion, matching the "Critical - cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only the ability to send an HTTP request with attacker-chosen headers and an already-obtained legitimately-signed body (trivially obtainable by any developer who installs the app on a test/free shop and captures Shopify's real webhook POST). No access to `api_secret_key` or any privileged credential is required — only interception/replay of one's own legitimately delivered webhook with a substituted header, which is squarely an "unprivileged internet user" capability.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signable string used for HMAC verification, or otherwise bind the verified body to the shop it was issued for (e.g., verify the header value is embedded in the signed payload, mirroring how `ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` includes `shop` in its signed params). At minimum, `Registry.process` should re-derive/cross-check `shop` from data inside the verified body rather than trusting an unauthenticated header.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`) so Shopify sends a POST with a legitimate `x-shopify-hmac-sha256` computed over the raw body and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures the raw body and its valid HMAC.
3. Attacker replays the same body and HMAC to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` (lines 26-31) succeeds because it only checks the body against the HMAC.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` (lines 188-200) calls the handler with `shop: request.shop` == `"victim.myshopify.com"`, causing the app to process attacker-supplied data as if it belonged to the victim tenant.
