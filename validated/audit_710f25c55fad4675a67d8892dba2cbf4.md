## Title
`account::rotate_authentication_key` and `rotate_authentication_key_with_rotation_capability` sign a `RotationProofChallenge` with no `chain_id`, enabling cross-network signature replay for auth-key takeover - (File: `aptos-move/framework/aptos-framework/sources/account/account.move`)

### Summary
The external report's core custody invariant is: a signed authorization message must be bound to the specific chain/domain it is meant to execute on, or the signature can be replayed on a different chain to trigger the same privileged state change there. Aptos's `RotationProofChallenge`, used to authorize full authentication-key rotation (i.e., complete transfer of custody control over an account and everything it owns — APT, objects, fungible-asset stores, resource-account capabilities reachable via that key), omits `chain_id` from the signed struct, unlike sibling structs in the same file (`RotationCapabilityOfferProofChallengeV2`, `SignerCapabilityOfferProofChallengeV2`'s newer version, and `multisig_account`'s `MultisigAccountCreationMessage`) which explicitly add `chain_id` "to prevent cross-chain replay."

### Finding Description
`RotationProofChallenge` is defined as: [1](#0-0) 

Compare this to `RotationCapabilityOfferProofChallengeV2`, added specifically to fix a replay problem, whose comment states the `chain_id` field "prevents replaying the challenge message": [2](#0-1) 

`rotate_authentication_key` builds the `RotationProofChallenge` from only `sequence_number`, `originator` (address), `current_auth_key`, and `new_public_key` — no `chain_id`: [3](#0-2) 

The same struct (again without `chain_id`) is used to authorize delegated rotation via a rotation capability: [4](#0-3) 

Signature verification (`assert_valid_rotation_proof_signature_and_get_auth_key`) verifies the Ed25519/MultiEd25519 signature over the BCS-serialized `SignedMessage<RotationProofChallenge>` — the domain separation used is only the Move type name (`TypeInfo`), not the chain: [5](#0-4)  and [6](#0-5) . There is no `chain_id::get()` binding anywhere in this message construction or its verification path.

Because Aptos account addresses are deterministic functions of the public key alone (not the chain), the identical address, identical `sequence_number` (e.g., a fresh account at `0`), and identical `current_auth_key` can exist on two different Aptos networks (e.g., testnet and mainnet, or two different chain-id deployments). A `RotationProofChallenge` signed for use on one network is byte-for-byte valid and independently re-verifiable on another network sharing that state, since nothing in the signed payload, nor in `rotate_authentication_key`/`rotate_authentication_key_with_rotation_capability`, checks the executing chain's id against anything in the signed message.

### Impact Explanation
`rotate_authentication_key` and `rotate_authentication_key_with_rotation_capability` are the primary custody-control functions for an Aptos account: rotating the auth key transfers signing authority over all APT, fungible-asset stores, and any object/resource-account signer-capability access reachable from that account to whoever controls the new key. If an attacker can induce a victim to sign a `RotationProofChallenge` intended for one network context (e.g., a low-stakes/test environment, or a dApp/bridge on a different chain-id deployment sharing the same address-derivation scheme) and then replay that exact signed payload against the account on a higher-value network where the same address, current auth key, and sequence number happen to coincide, they can force or piggyback a key rotation that was not scoped to that network — a custody-control (authority) break rather than merely an event-log or cosmetic issue. This directly matches the "Custody Impact" gate: unauthorized takeover of account/asset control via a broken authority-binding invariant.

### Likelihood Explanation
This is a Medium-to-High likelihood issue conditioned on cross-network address/sequence-number collisions, which the codebase does not prevent and does not attempt to detect. Unlike the `MultisigAccountCreationMessage`/`RotationCapabilityOfferProofChallengeV2` structs where Aptos engineers explicitly recognized and fixed this exact class of bug by adding `chain_id`, `RotationProofChallenge` was left without it, indicating an inconsistent application of the chain-binding fix across otherwise-analogous signed-authorization structs in the very same module.

### Recommendation
Add a `chain_id: u8` field (via `chain_id::get()`) to `RotationProofChallenge`, matching the pattern already used in `RotationCapabilityOfferProofChallengeV2` and `multisig_account::MultisigAccountCreationMessage`, and update all call sites (`rotate_authentication_key`, `rotate_authentication_key_with_rotation_capability`, and their `.spec.move`/tests) to include and verify it.

### Proof of Concept
1. On Chain A (e.g., testnet, `chain_id = X`), create account `alice` with public key `pk_curr`, address derived from `pk_curr`, `sequence_number = 0`.
2. Construct and sign `RotationProofChallenge { sequence_number: 0, originator: alice_addr, current_auth_key: alice_addr, new_public_key: pk_new }` with both `sk_curr` (`cap_rotate_key`) and `sk_new` (`cap_update_table`), exactly as done in `rotate_authentication_key` at [3](#0-2) .
3. Submit this to `rotate_authentication_key` on Chain A — succeeds as intended.
4. If the same address (same `pk_curr`), same `sequence_number == 0`, and same `current_auth_key` exist on Chain B (`chain_id = Y`) — e.g., an account newly created there with the same public key before any transactions — replay the identical `cap_rotate_key`/`cap_update_table` byte blobs against `rotate_authentication_key` on Chain B. `assert_valid_rotation_proof_signature_and_get_auth_key` at [6](#0-5)  re-verifies successfully since nothing in the signed bytes differs by chain, rotating the Chain-B account's key to `pk_new` without an independent, chain-B-scoped authorization.

Note: I was unable to independently verify from the indexed code whether Aptos operationally guarantees no two live networks can ever share the same address+sequence-number+auth-key state (this would require infra/deployment knowledge outside the indexed source); the vulnerability is scoped strictly to the missing `chain_id` binding in the Move contract logic itself, which is the local, repo-provable root cause.

    fun assert_valid_rotation_proof_signature_and_get_auth_key(
        scheme: u8,
        public_key_bytes: vector<u8>,
        signature: vector<u8>,
        challenge: &RotationProofChallenge
    ): vector<u8> {
        if (scheme == ED25519_SCHEME) {
            let pk = ed25519::new_unvalidated_public_key_from_bytes(public_key_bytes);
            let sig = ed25519::new_signature_from_bytes(signature);
            assert!(
                ed25519::signature_verify_strict_t(&sig, &pk, *challenge),
                std::error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE)
            );
            ed25519::unvalidated_public_key_to_authentication_key(&pk)
        } else if (scheme == MULTI_ED25519_SCHEME) {
            let pk = multi_ed25519::new_unvalidated_public_key_from_bytes(public_key_bytes);
            let sig = multi_ed25519::new_signature_from_bytes(signature);
            assert!(
                multi_ed25519::signature_verify_strict_t(&sig, &pk, *challenge),
                std::error::invalid_argument(EINVALID_PROOF_OF_KNOWLEDGE)
            );
            multi_ed25519::unvalidated_public_key_to_authentication_key(&pk)
        } else {
            abort error::invalid_argument(EINVALID_SCHEME)
        }
    }
