### Title
`CallDispatcher.dispatch` has no caller restriction, letting anyone execute arbitrary calls with any funds it happens to hold - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
`CallDispatcher.dispatch(bytes)` is a public, unauthenticated entry point that executes an arbitrary attacker-supplied `Call[]` (`to`, `value`, `data`) from the `CallDispatcher`'s own address. It is meant to be invoked only as an internal step of `IntentGatewayV2.placeOrder`/`fillOrder` flows (predispatch/postdispatch), but the function itself performs no check on `msg.sender`, exactly mirroring the AAVE `executeOperation` bug class where a privileged-looking callback/dispatch entrypoint is reachable by anyone because the "who is allowed to trigger this" check is missing.

### Finding Description
`CallDispatcher.dispatch` decodes an ABI-encoded `Call[]` and, for each call, verifies only that `to` has code, then executes `to.call{value: call.value}(call.data)` using the dispatcher's own ETH/token balance: [1](#0-0) 

There is no modifier, no `onlyGateway`/`onlyOwner` check, and no verification of who called `dispatch` - unlike every other "trusted callback" surface in this codebase, which is careful to gate the caller (`onlyHost` on `HyperApp.onAccept`/`onGetResponse`, `restrict(msg.sender, _params.host)` on `HostManager.onAccept`, `CallerNotAsset` on `StreamingYieldVault.onTransferReceived`). Compare: [2](#0-1) [3](#0-2) 

`CallDispatcher` is a single, persistent, shared contract used by `IntentGatewayV2.placeOrder` for predispatch (swap-then-escrow) and by `IntentsBase._execute` for postdispatch (fill-then-act): [4](#0-3) [5](#0-4) 

During these flows tokens/ETH are transferred into the dispatcher, arbitrary order-supplied calldata is executed, and only the *known* input/output token balances are swept back out; anything else (dust, unswept intermediate swap balances, leftover approvals granted by the executed calls) can remain on the dispatcher between transactions: [6](#0-5) 

Because `dispatch()` accepts calldata to *any* contract with the dispatcher's own balance and has no caller restriction, any unprivileged account can call `CallDispatcher.dispatch()` directly at any time it holds a nonzero balance (native ETH sent via `receive()`, ERC-20 dust, or funds mid-flight due to reentrancy/race conditions) and route those funds to itself. This is the same root cause as the reported AAVE bug: a function that is only supposed to be reachable through a specific trusted orchestrator (there, the LendingPool calling back into `MarginTrading`; here, `IntentGatewayV2`/`IntentsBase` calling into `CallDispatcher`) has no check verifying the caller/initiator is that trusted orchestrator, so anyone can invoke it directly and exploit whatever value happens to be resident in the target contract.

### Impact Explanation
Any ETH or ERC-20 tokens resident on the `CallDispatcher` — dust left over from fee-on-transfer tokens, unswept surplus from predispatch/postdispatch swaps, or funds accidentally sent to its `receive()` — can be permissionlessly drained by any address, since `dispatch()` lets the caller execute an arbitrary call with the dispatcher's balance to any destination. This is concrete theft of funds belonging to the protocol/users routed through the shared `CallDispatcher`, satisfying the "concrete theft ... of funds" bar for a valid finding.

### Likelihood Explanation
`CallDispatcher` is a long-lived, shared contract reused across many orders (per the docs, dust is explicitly acknowledged as something that can accumulate and needs periodic sweeping). Any block where the dispatcher's balance is transiently or permanently nonzero — which the documented "DustCollected" and sweep logic imply happens routinely — is a window in which any address can call `dispatch()` first and redirect that balance. No special conditions (governance compromise, node compromise) are required; a single unprivileged transaction suffices.

### Recommendation
Restrict `CallDispatcher.dispatch` to only be callable by the authorized gateway/orchestrator contract(s) that are meant to drive it (e.g., an immutable `owner`/`gateway` address set at construction, checked with a `require(msg.sender == gateway)`), analogous to how `MarginTrading.executeOperation` should check `_initiator == address(this)`. If `CallDispatcher` must remain a shared, permissionless utility, ensure it never retains any residual balance across transactions (i.e., every call path that funds it must fully sweep 100% of any resulting balance—including of tokens not explicitly listed as inputs/outputs—back out within the same transaction), and add a caller allow-list keyed to the gateway instance(s) that legitimately use it.

### Proof of Concept
1. Any user calls `IntentGatewayV2.placeOrder` (or `fillOrder`'s postdispatch path) with predispatch/postdispatch calldata that leaves a small residual balance of an unlisted token, or excess ETH, on `CallDispatcher` (this is explicitly acknowledged behavior — dust that must be later swept).
2. Before that dust is swept elsewhere, an attacker directly calls `CallDispatcher.dispatch(abi.encode(Call[]))` with a `Call` whose `to` is the dust token (or a `to=attacker,value=<eth balance>` self-call) that transfers the dispatcher's balance to the attacker's address.
3. Since `dispatch()` performs no caller check, the call succeeds and the attacker receives the funds that were never theirs, with no interaction with the legitimate `IntentGatewayV2` flow required.

```text
The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.

### Postdispatch

The `call` field in `PaymentInfo` contains calldata to execute *after* the order is filled. This enables fill-then-act patterns — for example, output tokens received from the solver are routed through a DeFi protocol before reaching the beneficiary.

Execution timing differs by mode:

- **Same-chain**: Calldata executes only after the order is **fully filled**. Partial fills do not trigger calldata — only the final fill that completes the order executes it. This ensures all output tokens are available when the calls run.
- **Cross-chain**: Calldata executes **immediately** after the solver delivers output tokens to the beneficiary, before the settlement message is dispatched back to the source chain.

After execution, any tokens remaining in the `CallDispatcher` are swept back to the gateway and collected as dust (emitting `DustCollected` for each token). When postdispatch calldata is present, 100% of any surplus (solver overpayment) goes to the protocol rather than being split with the beneficiary — this prevents manipulation of surplus distribution through calldata side effects.
```
