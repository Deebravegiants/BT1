### Title
Unrestricted `GET /v2/external_initiators` discloses External Initiator `AccessKey` and `OutgoingToken` credentials to any authenticated 'view'-role user - (File: `core/web/router.go`)

### Summary
The `/v2/external_initiators` list endpoint is registered without any role check, while the sibling create/delete routes on the same resource require `RequiresEditRole`. Any authenticated user — including one with the lowest, "view-only" role — can enumerate all configured External Initiators and receive their `AccessKey` and `OutgoingToken` values in the response, which are credentials used to authenticate External-Initiator-triggered job runs and outgoing webhook callbacks.

### Finding Description
In `v2Routes`, the External Initiator routes are set up as: [1](#0-0) 

`POST` (create) and `DELETE` (destroy) require `auth.RequiresEditRole`, but `GET /external_initiators` (`eia.Index`) is wrapped only in `paginatedRequest`, inheriting solely the outer `authv2` group's authentication middleware, which merely requires a valid session/token — not a minimum role — per: [2](#0-1) 

`ExternalInitiatorsController.Index` performs no additional role/permission check itself before returning data: [3](#0-2) 

The returned `presenters.ExternalInitiatorResource` includes the initiator's `AccessKey` and `OutgoingToken`: [4](#0-3) 

This mirrors the RustFS bug class exactly: an admin-scoped configuration-listing capability (`ListRemoteTargetHandler` in RustFS / `ExternalInitiatorsController.Index` here) checks only that the caller is authenticated, not that the caller holds the elevated role required to manage that resource (replication-admin permission in RustFS / `edit`+ role here), and the listing response embeds credential material (`BucketTarget` remote access/secret keys in RustFS / `AccessKey`/`OutgoingToken` here).

The `RequiresRunRole`/`RequiresEditRole`/`RequiresAdminRole` role hierarchy is defined in `core/web/auth/auth.go`: [5](#0-4) 

showing `Index` deliberately omits any of these guards while `Create`/`Destroy` use `RequiresEditRole`, confirming the missing check is an inconsistency rather than an intended design (view-role users are not supposed to manage External Initiators per the mutating routes' guard).

### Impact Explanation
`AccessKey` (paired with the never-exposed `Secret`/`HashedSecret`) is one half of the credential pair used to authenticate External-Initiator-triggered job runs via the `X-Chainlink-EA-AccessKey`/`X-Chainlink-EA-Secret` headers, per `AuthenticateExternalInitiator`: [6](#0-5) 

`OutgoingToken` is a credential the node hands back for outbound EI webhook callbacks. A low-privilege ("view") authenticated user can enumerate every configured initiator's `AccessKey` and `OutgoingToken`, disclosing part of the credential material and full name/URL mapping for external integrations that a view-only user should have no visibility into, let alone the ability to exfiltrate.

### Likelihood Explanation
Any user who can authenticate to the node's web/API layer at all — regardless of role — can call `GET /v2/external_initiators`. No special conditions or race window are required, so exploitation is trivial for any credentialed low-privilege account (a very common tenant in multi-user Chainlink node deployments).

### Recommendation
Wrap `authv2.GET("/external_initiators", ...)` in `auth.RequiresEditRole` (matching the `Create`/`Destroy` routes on the same resource), or at minimum `auth.RequiresRunRole`, so that only users with sufficient privilege can list External Initiator credentials.

### Proof of Concept
1. Create a user with role `view` (`sessions.UserRoleView`).
2. Log in as that user to obtain a session cookie via `POST /sessions`.
3. Issue `GET /v2/external_initiators` with that session.
4. Observe the response contains `name`, `url`, `accessKey`, and `outgoingToken` for every configured External Initiator, despite the user having no `edit`/`run`/`admin` privileges — confirmed by the absence of any `auth.Requires*Role` wrapper on this route in `core/web/router.go:264` versus the `RequiresEditRole` wrapper present on the adjacent `Create`/`Destroy` routes at lines 265-266.

func (eic *ExternalInitiatorsController) Index(c *gin.Context, size, page, offset int) {
	ctx := c.Request.Context()
	externalInitiators, count, err := eic.App.BridgeORM().ExternalInitiators(ctx, offset, size)
	resources := make([]presenters.ExternalInitiatorResource, 0, len(externalInitiators))
	for _, initiator := range externalInitiators {
		resources = append(resources, presenters.NewExternalInitiatorResource(initiator))
	}

	paginatedResponse(c, "externalInitiators", size, page, resources, count, err)
}

// RequiresEditRole extracts the user object from the context, and asserts the user's role is at least
// 'edit'
func RequiresEditRole(handler func(*gin.Context)) func(*gin.Context) {
	return func(c *gin.Context) {
		user, ok := GetAuthenticatedUser(c)
		if !ok {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("not a valid session"))
			return
		}
		if user.Role == clsessions.UserRoleView || user.Role == clsessions.UserRoleRun {
			c.Abort()
			jsonAPIError(c, http.StatusUnauthorized, errors.New("Unauthorized"))
			return
		}
		handler(c)
	}
}
