### Title
Webhook shop identity spoofing – `shop` header not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, so the HMAC verification performed by `ShopifyAPI::Utils::HmacValidator.validate` in `ShopifyAPI::Webhooks::Registry.process` authenticates the *body bytes* but never authenticates the `shop-domain` header. That header is nonetheless the value handed to the app's `WebhookHandler` as the tenant identifier for the incoming event.

### Finding Description
The identity binding that should hold is: `shop header used to attribute webhook data == shop that the HMAC-signed payload was actually generated for`.

- `ShopifyAPI::Webhooks::Request#shop` reads the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header directly: [1](#0-0) 
- `ShopifyAPI::Webhooks::Request#to_signable_string` (used for HMAC verification) returns only `@raw_body` — no header, including `shop`, is part of the signed string: [2](#0-1) 
- `HmacValidator.validate_signature` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the body only) and compares it with the received `hmac` header: [3](#0-2) 
- `Registry.process` accepts the request once the body HMAC checks out, then constructs the tenant-attributed metadata straight from the unauthenticated `request.shop`: [4](#0-3) 

Because the `shop` field is "acted on" (used to identify which merchant/tenant the event belongs to) but is not covered by the HMAC, any request whose *body* carries a valid signature for the shared `api_secret_key` will be accepted regardless of which shop's header is attached to it. An unprivileged internet user who legitimately operates their own shop and has the app installed on it can trigger an event (e.g., `orders/create`) and thereby obtain from Shopify a fully valid `(raw_body, hmac)` pair signed with the app's shared secret. Nothing in this gem prevents that exact `(raw_body, hmac)` pair from being POSTed again to the same public webhook endpoint with the `shop-domain` header swapped to a victim shop's domain — the HMAC still validates because it never covered the header, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to the victim shop.

### Impact Explanation
This crosses a tenant boundary: it lets one merchant (attacker) inject data that the host application will process as if it came from a different merchant (victim), without ever needing the app's `api_secret_key`, an access token, or any credential belonging to the victim. Depending on how the host application implements its webhook handler (e.g., updating order/inventory/customer state, or storing PII) attributed to `WebhookMetadata#shop`, this enables cross-tenant data injection/corruption — matching the "cross-tenant access" impact category.

### Likelihood Explanation
The prerequisite (owning/installing the multi-tenant app on an attacker-controlled shop and triggering a real webhook event) is achievable by any ordinary merchant using the app — no privileged access, leaked secrets, or social engineering required. The remaining step — resending the exact same `(raw_body, hmac)` bytes to the app's public webhook endpoint with a different `shop-domain` header — is a purely mechanical HTTP replay that this gem's `Request`/`Registry` code does nothing to prevent, since the header is simply never part of what is cryptographically verified.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the header-derived attributes to the signed body before they are trusted and passed to `WebhookMetadata`. Shopify's own HMAC design signs only the body by convention, so the safer fix is to require the caller to independently authenticate the delivery (e.g., cross-check against the shop that owns the specific `webhook-id`, or maintain a mapping validated at webhook-registration time) rather than trusting the header verbatim.

### Proof of Concept
1. Attacker installs the target multi-tenant app on their own shop `attacker.myshopify.com` and configures a network capture proxy (or otherwise observes) requests reaching the app's public webhook endpoint (which is reachable from the internet by design).
2. Attacker performs an action (e.g., creates an order) that causes Shopify to deliver a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends an HTTP POST to the same endpoint with identical body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`: [5](#0-4) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: request.parsed_body, ...)`, causing the host application to process attacker-controlled data as if it originated from the victim's shop.
