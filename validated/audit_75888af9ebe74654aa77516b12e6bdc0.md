### Title
Withdraw instruction allows fully bypassing slippage protection via optional `min_coin_amount`/`min_pc_amount` - (File: `program/src/processor.rs`)

### Summary
The `Withdraw` instruction's slippage protection (`min_coin_amount`/`min_pc_amount`) is defined as `Option<u64>` and is only enforced when *both* values are explicitly supplied. When the withdrawal transaction omits them (a valid, unpack-supported instruction encoding), `process_withdraw` performs no minimum-received check at all, functionally equivalent to the Yearn adapter's hardcoded `maxLoss = 10_000` (100%) that removes all slippage protection on withdrawal.

### Finding Description
`WithdrawInstruction` carries `min_coin_amount: Option<u64>` and `min_pc_amount: Option<u64>`, and the unpacker only populates them if the instruction data is long enough (16 extra bytes); otherwise both default to `None`: [1](#0-0) 

In `process_withdraw`, the computed `coin_amount`/`pc_amount` (the user's proportional share of pool reserves after PnL adjustment) are only checked against the minimums if *both* options are `Some`: [2](#0-1) 

If a submitted transaction encodes only the 8-byte `amount` field (omitting the 16 bytes for `min_coin_amount`/`min_pc_amount`), `unpack` (tag `4`) happily produces `WithdrawInstruction { amount, min_coin_amount: None, min_pc_amount: None }`: [1](#0-0) 

The subsequent `if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()` guard is then false, so the transfer and burn proceed with **zero** minimum-output enforcement — structurally identical to the Yearn `maxLoss = 10_000` bug: the protective bound exists in the interface but can be trivially set to "no protection," and unlike `SwapBaseIn`/`SwapBaseOut` (which mandate `minimum_amount_out`/`max_amount_in` as non-optional fields), `Withdraw` makes the check opt-in.

### Impact Explanation
An unprivileged party who can influence transaction construction/submission for a withdrawing LP (e.g., a front-end, aggregator, or relayer building/omitting the optional fields, or any flow where the withdrawer's client does not populate them) can submit a withdraw with no slippage floor. Combined with a sandwich (front-run a large swap shifting the coin/pc ratio unfavorably, let the victim's withdraw execute at the skewed ratio, then back-run to restore the ratio and capture the delta), the withdrawing LP can receive materially less value than the pool's true ratio at submission time, transferring value to the attacker. This is a direct loss of LP funds.

### Likelihood Explanation
The vulnerable path is reachable via a single `Withdraw` instruction using standard, permissionless account inputs (the caller only needs to be the LP-token owner) — no privileged signer or non-default build is required. Whether it is exploited in practice depends on whether the transaction that specifies the withdraw omits the optional minimums, which is a supported and unauthenticated encoding of the instruction itself, so the underlying protection gap is entirely process-owned, not client-owned.

### Recommendation
Make `min_coin_amount` and `min_pc_amount` mandatory (non-optional) fields on `WithdrawInstruction`, mirroring the mandatory `minimum_amount_out`/`max_amount_in` fields already enforced in `SwapBaseIn`/`SwapBaseOut`, so that every withdraw transaction must carry an enforceable floor and the check in `process_withdraw` (lines 1779-1786) cannot be skipped by omission.

### Proof of Concept
1. Construct a `Withdraw` instruction (tag `4`) with only the 8-byte `amount` field, omitting the following 16 bytes for `min_coin_amount`/`min_pc_amount`.
2. `AmmInstruction::unpack` (program/src/instruction.rs:372-386) decodes this into `WithdrawInstruction { amount, min_coin_amount: None, min_pc_amount: None }`.
3. Front-run this transaction with a large swap that shifts the coin/pc ratio unfavorably for the withdrawer.
4. `process_withdraw` (program/src/processor.rs:1775-1804) sees `min_coin_amount.is_some() && min_pc_amount.is_some()` evaluate to `false` and skips the `ExceededSlippage` check entirely, transferring `coin_amount`/`pc_amount` computed from the manipulated pool ratio.
5. Back-run to restore the ratio, capturing the value difference at the withdrawer's expense.
