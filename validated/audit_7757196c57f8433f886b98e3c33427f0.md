### Title
Webhook shop/topic/webhook-id headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and are never part of the signed material. `Registry.process` accepts any request whose body/HMAC pair validates and then dispatches the handler using those unauthenticated header values, breaking the binding `hmac_verified_bytes == bytes_the_handler_trusts`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers with no cryptographic binding to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e. the body) against the HMAC: [3](#0-2) 

`Registry.process` then trusts `request.shop`, `request.topic`, and `request.webhook_id` unconditionally once the body-only HMAC check passes, and hands them to the app's handler: [4](#0-3) 

The identity binding that should hold is: `hmac_verified_bytes == bytes the handler trusts as the tenant/topic identity`. Here it does not — the HMAC verifies only the body, but `WebhookMetadata.shop`/`topic`/`webhook_id` (attacker-controlled headers) are trusted as if they were verified. Any party who has ever received one legitimate, validly-signed webhook body+HMAC pair for *their own* shop (any developer/merchant with a public/dev app installed can obtain this trivially) can replay that exact body+HMAC while substituting arbitrary `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` header values, since none of those fields invalidate the signature.

### Impact Explanation
This breaks the tenant/topic identity binding for the app's webhook processing pipeline: the receiving application will process the payload as if it originated from `shop` X for topic Y, when it actually only proves "some body was HMAC-signed by our own shared secret for shop A's original delivery." Depending on the handler's trust in `WebhookMetadata.shop`/`topic` (e.g., updating tenant-scoped records, triggering `shop/redact` or `customers/redact` compliance flows, uninstall cleanup, or billing/order state changes keyed by the spoofed shop), this enables cross-tenant data confusion/injection using only the attacker's own legitimately-received webhook traffic — no access token, no `client_secret`, and no direct access to the victim tenant is required. This satisfies the Critical bar of cross-tenant access via a broken identity binding.

### Likelihood Explanation
Likelihood is moderate-to-high in real deployments: any unprivileged internet user who can install a Shopify app (their own, or a public app they subscribe to) receives real, validly-HMAC'd webhook bodies for topics they control (e.g., `app/uninstalled`, `shop/redact`, or any topic with a fixed/predictable/empty body like `{}`). They can capture that body+HMAC pair once and replay it indefinitely against the same endpoint with forged shop/topic headers, since the library performs no additional binding, freshness, or per-shop check on those header fields before dispatch.

### Recommendation
Extend the webhook `to_signable_string`/verification path (or `Registry.process`) to bind `shop`, `topic`, and `webhook_id` into the value that is authenticated before they are trusted — e.g., verify the shop against a known/registered session for that HMAC-body pair, or require additional out-of-band authentication (mutual TLS, source IP allowlisting from Shopify, or a signed envelope covering headers) before dispatching to handlers keyed by these header values. At minimum, document and enforce that consuming apps must independently re-validate `shop` against their own installed-shop registry before trusting webhook payload attribution, and consider rejecting bodies that have already been seen for a different `shop`/`webhook_id` (replay detection).

### Proof of Concept
1. Attacker installs any Shopify app (their own dev app or a public app) on `attacker-shop.myshopify.com`.
2. Shopify delivers a legitimate webhook to the attacker's endpoint with a body such as `{}` (or any topic with a fixed/predictable body) and a valid `X-Shopify-Hmac-Sha256` computed by Shopify using the app's real `api_secret_key`.
3. Attacker captures this `(raw_body, hmac)` pair.
4. Attacker (or anyone with network access to the app's public webhook endpoint) resends this exact body/HMAC pair to the same endpoint but sets:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
   - `X-Shopify-Topic: shop/redact` (or another mandatory/sensitive topic)
   - `X-Shopify-Webhook-Id: <arbitrary>`
5. `Utils::HmacValidator.validate` succeeds because it only checks the body against the HMAC: [4](#0-3) 
6. The registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: "shop/redact", ...)`, causing the app to execute shop-scoped logic as if it were a genuine event for the victim shop, without the attacker ever needing the victim's credentials, access token, or the app's `client_secret`.
