## Title
Ignoring the boolean return value of low-level `transfer()` calls in `withdraw()` can silently fail while escrow accounting is finalized, permanently losing beneficiary funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` releases escrowed order funds to a beneficiary using a low-level `.call` to the ERC-20 `transfer` selector, but only checks that the *call itself* did not revert (`success`). It never inspects the ABI-encoded boolean return value that `transfer()` is supposed to return. Any ERC-20 implementation that returns `false` on failure instead of reverting will make `withdraw()` believe the transfer succeeded, while the internal escrow accounting is unconditionally decremented and the order is marked filled.

### Finding Description
`withdraw()` is the internal function invoked when a `RedeemEscrow` or `RefundEscrow` request is delivered via `onAccept`/`onGetResponse` after a relayed cross-chain proof [1](#0-0) . For each escrowed token it performs:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

`success` from a low-level `.call` is `true` whenever the callee executed without reverting — it says nothing about the ABI-encoded `bool` payload the ERC-20 standard requires `transfer()` to return. A perfectly standard-conformant, non-reverting token that returns `false` (rather than reverting) on a failed transfer will pass this check, exactly the "ignoring return value of `transfer()`" bug class from the report. Immediately after, regardless of whether tokens actually moved, the code decrements the escrow bookkeeping and marks the order filled:

```solidity
_orders[body.commitment][token] -= amount;
...
_filled[body.commitment] = beneficiary;
``` [3](#0-2) 

The same unchecked pattern is repeated for the transaction-fee payout in the same function [4](#0-3)  and for the governance-triggered `SweepDust` handler [5](#0-4) .

Note that the mainline `src/apps/IntentGatewayV2.sol`/`IntentsBase.sol` implementation uses OpenZeppelin's `SafeERC20.safeTransfer`, which correctly validates the return data [6](#0-5) ; the Tron fork diverges from this safe pattern and reintroduces the vulnerability.

### Impact Explanation
Because `_filled` and `_orders` are updated unconditionally once `success` is true, a silently-failed transfer permanently and irreversibly loses the escrowed funds for the intended beneficiary: the order is marked filled/redeemed so it can never be retried, yet the tokens never left the contract's balance for that beneficiary and are effectively stranded/inaccessible through the normal redemption path. This is a direct, unrecoverable loss-of-funds condition reachable purely by the normal relay of a `RedeemEscrow`/`RefundEscrow` proof — no privileged role is required.

### Likelihood Explanation
Triggering requires only that the escrowed input/output token used in an order return `false` on failure instead of reverting (a legitimate, standards-compliant ERC-20 behavior seen in several real-world tokens, and especially plausible in the Tron/TRC-20 ecosystem this contract targets, where token semantics are heterogeneous). Any solver/user selecting such a token as an order asset — or any edge case causing the token to return `false` (e.g., paused token, blacklist, transient balance mismatch) — reaches this path through the standard message-delivery flow.

### Recommendation
Replace the raw `.call` + `success`-only check with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (as already used elsewhere in this codebase), or explicitly decode and validate the returned boolean:
```solidity
(bool success, bytes memory data) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success || (data.length > 0 && !abi.decode(data, (bool)))) revert TransferFailed();
```
Apply the same fix to the fee-token payout and to `SweepDust`.

### Proof of Concept
1. A cross-chain order escrows `token` (an ERC-20 that returns `false` instead of reverting on failed transfer, e.g., due to a transient condition) via the standard `fillOrder`/escrow flow.
2. Hyperbridge delivers a `RedeemEscrow` request; `onAccept` calls `withdraw(body, false)` [1](#0-0) .
3. Inside `withdraw`, `token.call(...transfer...)` returns `(true, abi.encode(false))` — the call succeeds at the EVM level but the token itself signals failure.
4. `success` is `true`, so `if (!success) revert TransferFailed();` does not trigger; `_orders[...][token] -= amount;` and `_filled[commitment] = beneficiary;` execute anyway [7](#0-6) .
5. The beneficiary never receives the tokens, but the order is now permanently marked filled — the escrow can never be redeemed again, resulting in a permanent loss of the escrowed funds.
