This confirms the vulnerability class. The `HmacValidator` for webhooks signs only the raw request body (`to_signable_string` returns `@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled unauthenticated from HTTP headers and never enter the signable string.

### Title
Webhook HMAC signature does not bind the `shop` (or `topic`/`webhook_id`) identity fields, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `api_version`, and `webhook_id` are read straight from request headers with no cryptographic binding to that body via the HMAC. [1](#0-0) 

### Finding Description
`Registry.process` validates a webhook solely with `Utils::HmacValidator.validate(request)`, which computes `HMAC-SHA256(secret, request.to_signable_string)` and compares it to the `hmac` header value. [2](#0-1)  The `to_signable_string` implementation only covers `@raw_body`; it never includes `shop`, `topic`, `webhook_id`, or `api_version`. [3](#0-2) 

`HmacValidator.validate` merely recomputes the HMAC over `to_signable_string` and does a constant-time compare, without any awareness of headers. [4](#0-3) 

Because the app's `client_secret` (used as the HMAC key) is identical for every shop that installs the app, a body+HMAC pair that is valid for shop A's webhook delivery remains a *valid* HMAC when replayed with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header swapped to shop B. The gem happily accepts it — `Registry.process` dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` straight to the app's handler with the attacker-chosen `shop` value, unauthenticated. [5](#0-4) 

Expressed as the binding that is expected vs. what is actually checked:
- Expected: `hmac == HMAC(secret, body ‖ shop ‖ topic ‖ webhook_id)`
- Actual: `hmac == HMAC(secret, body)`, and `shop`/`topic`/`webhook_id` are trusted from unauthenticated headers.

An unprivileged actor who is a legitimate merchant using the same app (and therefore able to capture/replay their own genuinely-signed webhook deliveries, which any store owner can do by inspecting their own webhook endpoint traffic or delivery logs) can resend that exact body+HMAC to the app's public webhook endpoint while altering the shop-identifying header to any other shop domain. Because the signature check only covers the body, the forged request passes validation and the handler processes it as if it originated from the victim shop.

### Impact Explanation
This breaks the tenant isolation guarantee that the gem's webhook verification is supposed to provide: an app author calling `Registry.process`/`HmacValidator.validate` reasonably assumes that a passing HMAC check means the request — including which shop it is attributed to — is authentic and came from Shopify for that shop. Since `shop` is not covered, an attacker can inject data or trigger side effects (e.g., order/customer updates, GDPR redact triggers, inventory changes) attributed to an arbitrary victim shop, i.e., cross-tenant access/injection, without ever possessing the app's `client_secret` or any victim credentials.

### Likelihood Explanation
Requires only: (1) the attacker be a legitimate user of some shop that has the app installed (to obtain one authentically-signed body+HMAC pair, which is trivial to capture from their own webhook deliveries), and (2) the ability to POST directly to the app's public webhook endpoint with custom headers, which is unprivileged and requires no secret. This is a straightforward replay-with-header-substitution and does not depend on cryptanalysis or credential theft.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is verified, rather than trusting it purely from headers. Options:
- Extend `to_signable_string` to include `shop-domain`, `topic`, and `webhook-id` header values, forcing the HMAC to also cover them (as Shopify's docs also recommend explicit topic/shop verification against the app's own known-installed-shops list).
- At minimum, document/require that consumers of `WebhookMetadata` cross-check `shop` against their own database of installed shops before processing, and treat the header-derived `shop` as untrusted input until independently verified.

### Proof of Concept
1. App developer registers a handler for topic `orders/create` via `Registry.add_registration`.
2. Attacker (merchant on `attacker-shop.myshopify.com`, which has the app installed) receives a legitimate webhook delivery for their own store: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC(secret, B)`).
3. Attacker replays this exact `(B, H)` pair directly to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...spoofed shop...})` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B) == H`.
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the app processes/persists data as if it came from the victim shop. [6](#0-5) [7](#0-6)
