This confirms the vulnerability: the webhook `hmac` signature is computed only over the raw request body via `to_signable_string` returning `@raw_body` [1](#0-0) , while `shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to the signature [2](#0-1) . `Registry.process` validates only the HMAC of the body, then passes the attacker-controlled `request.shop` straight into the `WebhookMetadata` handed to the app's handler as the tenant identifier [3](#0-2) .

### Title
Webhook HMAC does not bind the `shop` tenant identifier, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` cryptographically authenticates the body but not the `shop-domain` header. `Registry.process` uses this unauthenticated header value as the tenant key (`request.shop`) passed to the app's webhook handler.

### Finding Description
`Request#hmac` is derived from the `X-Shopify-Hmac-Sha256` header and validated against `to_signable_string`, which is defined to be just `@raw_body` [4](#0-3) . The `shop` accessor simply reads the `shopify-shop-domain` (or `x-shopify-shop-domain`) header without any signature coverage [2](#0-1) .

`Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `to_signable_string` (the raw body) and secure-compares it to the received HMAC [5](#0-4) . If that passes, the handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` [3](#0-2) , where `shop` is the unauthenticated header value.

This is the same class of defect as the external report: a value used downstream as an identity/tenant binding (`shop`, analogous to `feeAmounts`) is excluded from the integrity check (`to_signable_string`/HMAC, analogous to the flash-loan repayment calculation), even though the check is presented as validating the whole request. The equality that should hold — `hmac_signed_content == content_used_for_tenant_attribution` — is broken because `shop` is outside `hmac_signed_content`.

Since a single app has one `api_secret_key` shared across every shop that installs it, any merchant that legitimately installs the app receives genuinely-signed webhooks for their own shop (valid HMAC over the body). That merchant, or anyone who can capture one such payload, can resend the identical body+HMAC to the app's webhook endpoint while substituting a different value in the `X-Shopify-Shop-Domain` header. The HMAC check still passes (it never looked at that header), and the app's handler executes with `shop` pointing at a victim tenant of the attacker's choosing.

### Impact Explanation
This breaks the shop-authenticated-vs-shop-used-as-tenant-key binding, enabling cross-tenant data corruption: if the app's webhook handler uses `WebhookMetadata#shop` to look up the merchant's stored session/access token or to write data keyed by shop (the documented usage pattern), an attacker-controlled body can be processed and persisted under an arbitrary victim shop identifier, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Any app that installs on at least one shop (an "unprivileged internet user" from Shopify's perspective — merely completing a normal, free app install) automatically obtains a validly HMAC-signed webhook body/signature pair for their own shop, which they can freely replay against the app's public webhook endpoint with a forged shop header — no `api_secret_key`, access token, or privileged access is required.

### Recommendation
- **Short term:** Include `shop` (and ideally `topic`, `webhook_id`) in the signed/verified content, or independently verify that `request.shop` corresponds to a shop for which the app holds an active session/installation before trusting it as a tenant key.
- **Long term:** Document that the webhook HMAC only covers the body, and require consumers of `WebhookMetadata#shop` to cross-check it against known installed shops rather than treating it as an authenticated value.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC(api_secret_key, B)`.
2. Attacker resends `POST /webhook` with the identical body `B` and header `H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — validation succeeds [6](#0-5) .
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled body `B`, and processes it as if it legitimately originated from the victim shop.
