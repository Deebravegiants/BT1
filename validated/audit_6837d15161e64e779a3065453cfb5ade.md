### Title
Removing a state machine from a consensus client's whitelist permanently locks escrowed relayer fees for its already in-flight requests - (File: modules/ismp/clients/grandpa/src/lib.rs, modules/ismp/core/src/handlers/timeout.rs)

### Summary
`pallet_ismp::Pallet::dispatch_request` escrows the sender's relayer fee and commits an outgoing request without ever checking whether the destination `StateMachine` is currently supported by any consensus client. Separately, every consensus-client whitelist (e.g. `ismp-grandpa`'s `SupportedStateMachines`, `tendermint`'s equivalent) can be shrunk unilaterally by its admin origin via `remove_state_machines`/`remove_supported_state_machine`. Once a destination is removed from the whitelist, `validate_state_machine` - which both the request-delivery path and, critically, the **timeout** path depend on - unconditionally fails for that state machine, so a request already dispatched to it can neither be delivered nor timed out. The escrowed fee, and any refund logic gated on the timeout handler, is then stuck forever, exactly mirroring the "wrong/stale allocation to a blacklisted chain locks funds" pattern in the referenced Derby report.

### Finding Description
`Pallet::<T>::dispatch_request` in `modules/pallets/ismp/src/dispatcher.rs` withdraws the payer's fee into `RELAYER_FEE_ACCOUNT` and stores the request commitment unconditionally - there is no check that `dispatch_post.dest`/`dispatch_get.dest` is a state machine currently tracked by any registered consensus client: [1](#0-0) 

The only place "is this destination supported" is enforced is deep inside message *handling*, via `validate_state_machine`, which is invoked for both incoming requests/responses and for **timeouts**: [2](#0-1) [7](#0-6) 

`validate_state_machine` resolves the consensus client and then calls `consensus_client.state_machine(id)`. Every consensus-client implementation gates this on an admin-controlled whitelist storage map, e.g. the GRANDPA client: [5](#0-4) 

and the whitelist itself is fully mutable by `RootOrigin`/`AdminOrigin` via `remove_state_machines` (GRANDPA) or `remove_supported_state_machine` (Tendermint), with no regard for outstanding in-flight requests to the removed chain: [4](#0-3) 

The refund of the escrowed fee only happens inside `on_request_timeout`, which is only ever invoked from the timeout handler after `validate_state_machine` succeeds: [6](#0-5) 

Putting this together: a user/module dispatches a `PostRequest` to some `StateMachine::Substrate(id)` (or any state machine), paying a non-zero fee that gets escrowed. If, before the request is delivered, the admin removes that `StateMachine` from the consensus client's whitelist (a legitimate, permissionless-from-the-request's-perspective admin action - e.g. because the counterparty chain is being deprecated, is misbehaving, or is simply pruned from the whitelist for unrelated reasons), then:
- Inbound delivery of the request fails `validate_state_machine` (`UnsupportedStateMachine`).
- The timeout path *also* fails the exact same `validate_state_machine` check, so the request commitment can never be deleted and `on_request_timeout` (the fee refund) can never run.

The request commitment and its escrowed fee are now stuck permanently in `RequestCommitments` with no code path able to clear them, unless the state machine is later re-added to the whitelist (which is not guaranteed and is not something the request's payer controls).

### Impact Explanation
Any relayer fee escrowed for a request whose destination is later de-whitelisted becomes permanently unrecoverable - the exact "funds locked without any path to resolution" class of bug from the reference report, but here reachable by any ordinary dispatcher (a pallet module, or `send_message`) simply because dispatch performs no destination-support validation and the whitelist removal path is entirely decoupled from in-flight-request accounting. This is a permanent freezing-of-funds bug affecting user/module funds, satisfying the Medium/High bar for concrete permanent fund loss.

### Likelihood Explanation
No attacker interaction beyond ordinary use is required: any module or account that calls `dispatch_request`/`send_message` for a fee-bearing request creates the exposure, and the admin whitelist removal is a normal, documented operational primitive ("They can always be re-added" implies removal without re-adding is an expected, supported state). The bug triggers deterministically whenever a whitelist removal happens while any request to that state machine is still pending, which is a realistic operational scenario (deprecating a standalone chain, adjusting supported destinations, incident response, etc.).

### Recommendation
Either:
1. Decouple the timeout path's non-membership proof verification from the destination consensus client's *current* whitelist membership - allow `validate_state_machine`/`state_machine()` lookups for timeout processing to succeed using the last-known consensus client association for that state machine (or record which consensus client verified the original dispatch and only require that specific historical association for timeout proofs), or
2. Before removing a state machine from a whitelist, require draining/timing-out (or force-refunding) all outstanding request commitments destined for that state machine, or
3. At minimum, provide a governance-gated emergency refund path that lets the admin/root origin force-delete a request commitment and refund its escrowed fee once its destination consensus client no longer serves that state machine, mirroring the Derby fix recommendation of letting a privileged actor correct stale state after de-listing.

### Proof of Concept
1. Module `M` on the host chain calls `dispatch_request(DispatchRequest::Post{ dest: StateMachine::Substrate(X), .. }, FeeMetadata{ payer, fee: F })` with `F > 0`; `modules/pallets/ismp/src/dispatcher.rs::dispatch_request` withdraws `F` from `payer` into `RELAYER_FEE_ACCOUNT` and stores the request commitment - no check that `Substrate(X)` is whitelisted.
2. Before the request is delivered/timed out, `RootOrigin` calls `ismp_grandpa::remove_state_machines(vec![StateMachine::Substrate(X)])` (`modules/ismp/clients/grandpa/src/lib.rs`), removing `X` from `SupportedStateMachines`.
3. A relayer submits either a `RequestMessage` (delivery) or, once the timeout timestamp has elapsed, a `TimeoutMessage::Post` for the request.
4. Both paths call `validate_state_machine(host, height)` → `consensus_client.state_machine(StateMachine::Substrate(X))` → `Err(GrandpaError::UnsupportedStateMachine(X))` (`modules/ismp/clients/grandpa/src/consensus.rs`), so `handle_incoming_message` fails for both delivery and timeout.
5. The request commitment and escrowed fee `F` remain in `RequestCommitments` forever; `on_request_timeout`'s refund logic (`modules/pallets/ismp/src/host.rs`) is never reached, and there is no other extrinsic that can delete this commitment or return `F` to `payer`.

	fn dispatch_request(
		&self,
		request: DispatchRequest,
		fee: FeeMetadata<T>,
	) -> Result<H256, anyhow::Error> {
		// collect payment for the request
		if fee.fee != Zero::zero() {
			T::Currency::transfer(
				&fee.payer,
				&RELAYER_FEE_ACCOUNT.into_account_truncating(),
				fee.fee,
				Preservation::Expendable,
			)
			.map_err(|err| IsmpError::Custom(format!("Error withdrawing request fees: {err:?}")))?;
		}

		let request = match request {
			DispatchRequest::Get(dispatch_get) => {
				let get = GetRequest {
					source: self.host_state_machine(),
					dest: dispatch_get.dest,
					nonce: self.next_nonce(),
					from: dispatch_get.from,
					keys: dispatch_get.keys,
					height: dispatch_get.height,
					context: dispatch_get.context,
					timeout_timestamp: if dispatch_get.timeout == 0 {
						0
					} else {
						<T::TimestampProvider as UnixTime>::now()
							.as_secs()
							.saturating_add(dispatch_get.timeout)
					},
				};
				Request::Get(get)
			},
			DispatchRequest::Post(dispatch_post) => {
				let post = PostRequest {
					source: self.host_state_machine(),
					dest: dispatch_post.dest,
					nonce: self.next_nonce(),
					from: dispatch_post.from,
					to: dispatch_post.to,
					timeout_timestamp: if dispatch_post.timeout == 0 {
						0
					} else {
						<T::TimestampProvider as UnixTime>::now()
							.as_secs()
							.saturating_add(dispatch_post.timeout)
					},
					body: dispatch_post.body,
				};
				Request::Post(post)
			},
		};

		let commitment = Pallet::<T>::dispatch_request(request, fee)?;

		Ok(commitment)
	}
