### Title
Webhook `shop` (and `topic`/`webhook-id`) header is trusted for tenant routing without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop`, `topic`, and `webhook_id` values used by the application to route and attribute the webhook are read from unauthenticated HTTP headers. This breaks the identity binding `HMAC-verified bytes == bytes acted on`, allowing a forged/replayed webhook to be attributed to an arbitrary shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are read straight from the incoming headers, none of which are part of the signed string: [2](#0-1) 

`Registry.process` validates the HMAC only against this `to_signable_string`, then dispatches the handler using `request.shop`/`request.topic` verbatim: [3](#0-2) 

Shopify apps use a **single shared `client_secret`/`api_secret_key`** for HMAC-signing webhooks across *all* shops that install the app (this is the same secret used everywhere in the gem, e.g. `Utils::HmacValidator.validate`): [4](#0-3) 

Because the signature covers only the JSON body and not the shop domain, an attacker who has received one legitimate webhook for *their own* shop (a valid `body` + `hmac-sha256` pair from Shopify) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop. The HMAC check in `Registry.process` still passes (body is unchanged, HMAC is valid for that body under the shared app secret), but `WebhookMetadata.shop` — the value the host application uses to look up/act on a specific tenant — is attacker-controlled and unauthenticated: [5](#0-4) 

This is precisely the "field acted on but not covered by the HMAC" / "shop authenticated versus shop used as tenant key" class of bug described in the report: the interface (`Request`/`Registry`) is internally consistent about validating *something*, but the thing it validates (raw body) is not the thing the business logic keys off of (shop domain header).

### Impact Explanation
An attacker (any merchant who has installed the app, or anyone who can intercept one legitimate webhook delivery) can forge a webhook that the host application will process as originating from a different, arbitrary shop. Depending on the handler logic (common patterns: `customers/redact`, `shop/redact`, order/customer data sync into per-shop storage keyed by `data.shop`), this can cause cross-tenant data corruption, spoofed redaction/compliance events, or injection of attacker-chosen data attributed to a victim shop — a cross-tenant integrity/confidentiality violation.

### Likelihood Explanation
Moderate-to-high: no `api_secret_key` or privileged access is required — only a legitimate app installation on any shop (which any merchant, including an attacker, can do) to obtain one valid `(body, hmac)` pair, which is then replayed with a modified shop header against the app's public webhook endpoint.

### Recommendation
Bind the trusted identity fields into the signed representation, e.g. include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or independently verify `shop` against the session/shop the app expects for that webhook subscription) instead of trusting the raw headers unconditionally once the body HMAC passes.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and lets Shopify deliver a legitimate webhook (e.g. `orders/create`) to the app's endpoint; captures `raw_body` and the `X-Shopify-Hmac-Sha256` header.
2. Attacker resends the identical `raw_body` and `X-Shopify-Hmac-Sha256` to the same endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the shared secret's HMAC.
4. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to process attacker-supplied data as if it came from the victim shop.
