### Title
Attacker-controlled route pool executes arbitrary token transfers under the caller's `require_auth` tree in controller strategy verbs - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
The controller's swap-based strategies (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `flash_position`-adjacent routing) pass a fully attacker/user-supplied `StrategySwap` XDR to the swap aggregator. The router keeps no allowlist of pool or token addresses: every hop `pool` address in the payload is invoked as a contract. Because the user-facing entry (`swap_collateral` etc.) performs `caller.require_auth()` at the root, any `token.transfer(victim, attacker, amount)` that a malicious pool contract makes inside the hop is recorded as a sub-invocation of the caller's own authorization entry and executes if the caller signs the tree — the analog of external control of the invoked target (CWE-73) producing an attacker-chosen side-effect (SSRF-shaped arbitrary call). The measured balance-delta guards in `swap_tokens` bound only the routed input/output, not wallet funds moved by rogue pool code.

### Finding Description
`swap_tokens` snapshots `token_in`/`token_out` balances, authorizes one exact transfer to the router via `authorize_transfer_as_current`, calls `router.execute_strategy`, then asserts `actual_spent <= amount_in` and positive measured output. None of this inspects *which* contracts the route touches. The router dispatches each hop to `hop.pool` with no venue/pool allowlist. In a controller strategy call, the account owner's `require_auth` is satisfied by the root invocation, so a rogue pool's `token::transfer(caller, attacker, x)` on an unrelated wallet token joins the caller's auth tree as a child and is enforceable if signed. This is proven by the harness test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`, which shows the stolen transfer recorded under the caller's `swap_collateral` entry and Alice's unlisted-token wallet balance fully drained to the attacker while the swap itself settled at fair value.

### Impact Explanation
Theft of user funds beyond the routed amount. A crafted `routeXdr` embedded in a `swap_collateral`/`multiply`/`swap_debt`/`repay_debt_with_collateral` call can drain any token balance of the signing account (the test moves `WALLET_BALANCE` of a token the protocol never listed). The protocol's own guards — `RouterOverspend`, `NoSwapOutput`, `min_out`, final solvency gates — all pass because the swap legs are fair; the loss is unbounded by any slippage parameter.

### Likelihood Explanation
Exploitation requires the victim to sign a route containing the attacker's pool contract and to sign an auth tree containing the extra child transfer — i.e., it needs a malicious/compromised quote or social-engineered XDR plus a wallet that signs without inspecting the recorded auth tree. The threat model documents that clients must decode the route and reject unexpected children, but nothing in the on-chain path enforces it; any unprivileged user can be targeted, and no privileged access is needed by the attacker.

### Recommendation
Bind the caller's authorization to the expected transfer set: have the controller's strategy verbs build the auth expectation themselves (e.g., pre-declare the permitted child invocations and/or pass a venue/pool allowlist or registry-indexed pool set to the router), and/or have the router restrict hop targets to governance-registered pool/token addresses so arbitrary contracts cannot be placed on the call stack beneath the user's signature. At minimum, the controller should document and enforce that a strategy auth tree may contain only the single input-transfer child.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `RogueHopPool::swap` calls `token.transfer(alice, attacker, WALLET_BALANCE)` during the hop; the recorded auth tree shows that transfer nested under Alice's `swap_collateral` entry, and the test asserts `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE` while the strategy completes successfully and deposits fair-value collateral. A production exploit is the same shape: deploy a pool contract that steals a chosen token, submit it inside a `StrategyPayload` asset registry as a hop target, and have the victim execute the route through `swap_collateral`.
