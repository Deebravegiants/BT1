### Title
Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` binds the HMAC check to the raw body only, while `shop` and `topic` are read straight from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then trusts these unauthenticated fields to route the webhook and to build the tenant-identifying `WebhookMetadata`, breaking the intended identity binding `{HMAC-verified bytes} == {bytes the app acts on}`.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) 

`to_signable_string` returns only `@raw_body` — it does not include `shop`, `topic`, `api_version`, or `webhook_id`, all of which are read directly from client-supplied HTTP headers via `shopify_header`: [2](#0-1) 

`HmacValidator.validate` (shared with OAuth) simply recomputes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac` field: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts the unauthenticated `request.shop` and `request.topic` to route to a handler and build the metadata passed to app code: [4](#0-3) 

Because the HMAC only binds the body, any actor who obtains one genuine `(raw_body, hmac)` pair signed by the app's shared secret can replay that exact body/HMAC to the app's webhook endpoint while freely rewriting the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers. `HmacValidator.validate` will still return `true` because those headers were never part of the signed content — the equality that should hold, `hmac-authenticated shop == shop the handler acts on`, is broken.

An unprivileged user can obtain such a pair without any privileged credential: as the merchant/owner of their own shop, they can register a webhook subscription (via the Admin API, using only their own shop's access token) pointing the callback URL at infrastructure they control. Shopify will deliver a genuine, correctly-HMAC-signed webhook to that endpoint using the app's shared secret. The attacker now holds a valid `(raw_body, hmac)` pair and can forward it to the real app webhook endpoint with a forged `shop-domain` header naming a victim shop (and/or a forged `topic` header), impersonating a different tenant's event.

### Impact Explanation
This breaks the shop/tenant identity binding used by every consumer of `WebhookMetadata.shop` and `Registry.process`'s topic-based dispatch, allowing an attacker who controls only their own shop's credentials to make the app process fabricated events "as" another shop or under another topic. Depending on how the host app's webhook handlers use `shop`/`topic` (e.g., updating per-shop state, triggering data deletion/redaction flows for `MANDATORY_TOPICS`, or writing to the wrong tenant's records), this yields cross-tenant confusion/access, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is realistic but bounded: the attacker needs to be an app-installing merchant (a normal, unprivileged app user) capable of registering their own webhook subscription with a callback they control — this uses only their own access token, not a victim's or the app's `client_secret`/`api_secret_key`. No network interception, TLS bypass, or privileged account is required. The remaining constraint is that the forged body must still be one the target handler accepts as plausible for the spoofed topic/shop, which is feasible for topics with attacker-influenceable or generic body shapes.

### Recommendation
Include `shop`, `topic`, `api_version`, and `webhook_id` in the value that is HMAC-verified, or otherwise cryptographically bind them (e.g., verify them against Shopify's per-request signature scheme, or require the host app to independently confirm the `shop-domain` header corresponds to a shop that actually has this webhook/topic registered) before trusting them in `Registry.process`/`WebhookMetadata`. At minimum, document prominently that `Request#shop` and `Request#topic` are NOT covered by the HMAC and must not be used for tenant-authorization decisions without additional verification (e.g., cross-checking against the shop that owns the registered webhook subscription).

### Proof of Concept
1. Attacker registers (or already has) an app-connected shop `attacker.myshopify.com` with a valid access token for that shop.
2. Attacker uses the Admin GraphQL API (their own token) to create a webhook subscription for topic `T1` with callback URL pointing to an attacker-controlled listener.
3. Shopify delivers a legitimate webhook to the attacker's listener: `raw_body = B`, header `X-Shopify-Hmac-Sha256 = HMAC(secret, B)`, `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: T1`.
4. Attacker POSTs the same `raw_body = B` and the same `X-Shopify-Hmac-Sha256` value to the real app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` and/or `X-Shopify-Topic: T2` (any topic registered in the app's `Registry`).
5. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `HmacValidator.validate(request)` succeeds because it only checks `HMAC(secret, B)`, which is unchanged.
6. `Registry.process` dispatches to the `T2` handler and builds `WebhookMetadata.new(topic: "T2", shop: "victim.myshopify.com", body: parsed(B), ...)`, causing the host app to act as if a genuine `T2` event occurred for `victim.myshopify.com`.
