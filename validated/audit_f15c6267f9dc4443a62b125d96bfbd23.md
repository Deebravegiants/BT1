Audit Report

## Title
`Deposit::refund_all` sends the entire multi-contributor native storage-deposit hold to the terminating transaction's origin, letting one contributor claim another's `NativeDepositOf` entry - (File: `substrate/frame/revive/src/exec.rs`, `substrate/frame/revive/src/deposit_payment.rs`)

## Summary
`Stack::do_terminate` calls `T::Deposit::refund_all(&contract_account, exec_config.funds(origin.account_id()?))`, and both the default `()` backend and the `PGasDeposit` backend implement `refund_all` by releasing the entire `StorageDepositReserve` hold to a single recipient, bypassing the per-contributor `NativeDepositOf` cap that every other refund path (`refund_on_hold`) enforces. Because contract termination has no per-caller ownership check at the pallet level, any account that reaches the terminate path (e.g. via a contract lacking its own access control on a terminate function) can receive, as the transaction origin, other unrelated contributors' recorded native deposits.

## Finding Description
`NativeDepositOf<T>` is documented to bound "how much native value the user can receive back from that contract's storage deposit," and `refund_on_hold` enforces this via `let contribution = NativeDepositOf::<T>::get(from, to); let native_requested = amount.min(contribution);` [1](#0-0) .

`refund_all`, in contrast, ignores this cap entirely and refunds the whole `balance_on_hold` to a single `dst` in both backends: the default backend [2](#0-1)  and the PGAS-backed backend, whose own doc comment states it "bypasses the per-payer `NativeDepositOf` cap ... so the full native hold goes to the terminator" [3](#0-2) .

`do_terminate` invokes `refund_all` with the transaction origin (not the specified `beneficiary`) as the recipient [4](#0-3) . The residual contract balance goes to `args.beneficiary` via a separate `Self::transfer` call, but the entire storage-deposit hold is paid to whichever account is `origin`.

`terminate_caller`, which schedules termination via the `System` precompile, checks only frame/parentage invariants (`delegate.is_none()`, `entry_point == Call`) — not caller identity relative to any deposit-owner concept [5](#0-4) . The pallet itself does not enforce that only a specific "owner" may terminate; that access control (if any) must be implemented by the contract itself. The referenced fixture `MultiContributorStorage.sol` demonstrates a contract with no such access control on its `terminate` function.

The repository's own test, `refund_all_drains_multi_contributor_native_hold`, confirms this exact behavior: ALICE and CHARLIE each grow storage (creating distinct nonzero `NativeDepositOf` entries), then ALICE alone terminates the contract specifying DJANGO as beneficiary, and ALICE's balance increases by at least the combined native hold (`alice_entry + charlie_entry`), while CHARLIE receives nothing [6](#0-5) .

The code comment on the PGAS `refund_all` explicitly frames this as an intentional design tradeoff: "The native cap only makes sense for partial refunds on a live contract; at termination there is one recipient and the contract is gone" [7](#0-6) . This shows the behavior is a deliberate simplification for the termination case rather than an oversight, but it does create a real accounting inconsistency: the `NativeDepositOf` invariant ("bounds how much native value the user can receive back") is silently violated at termination time, and whichever account happens to be the transaction origin for the terminate call receives all contributors' native deposits.

## Impact Explanation
This does allow one contributor to a shared contract to receive another contributor's recorded native storage deposit upon contract termination, which is a genuine break of the documented `NativeDepositOf` accounting invariant. However, the severity is bounded by two important considerations: (1) the funds redirected are always a existing storage deposit that was already locked against the *contract's* account, not funds arbitrarily removed from a victim's own free balance elsewhere — the "victim" contributor only loses out on a refund they were otherwise entitled to on termination, and (2) whether an attacker can actually reach the terminate path with an unprivileged, unauthorized signature depends entirely on whether the specific contract exposes an unprotected terminate entry point; the pallet's own `terminate_caller` does not add caller-identity restrictions, but this mirrors typical EVM `selfdestruct`/owner-pattern semantics where access control is a contract-author responsibility, not a protocol guarantee. The provided fixture (`MultiContributorStorage.sol`) is a test fixture with intentionally no access control, used specifically to exercise this documented behavior in the pallet's own test suite — it is not evidence that real-world/production contracts commonly expose unprotected terminate paths.

## Likelihood Explanation
Exploitation requires a contract that (a) accepts storage-deposit-funding calls from multiple distinct signers and (b) exposes a termination path (via the `System` precompile's `terminate`) without restricting the caller to a legitimate owner/admin. Condition (b) is a contract-design choice, not a pallet-level default; well-designed contracts implementing termination would gate it behind an owner check, as is standard practice for any function with `selfdestruct`-like effects in EVM-compatible environments. The reachability of this specific exploit is therefore contingent on third-party contract code failing to add access control to a highly consequential operation, which is a foreseeable but not universal condition.

## Recommendation
Document explicitly that `refund_all` intentionally settles the entire native hold to a single recipient at termination (as the existing code comment already partially does), and recommend/require that contracts implementing a terminate/self-destruct entry point via the `System` precompile add their own caller-authorization checks, since the pallet does not enforce per-contributor payout splitting at termination. If stronger protocol-level guarantees are desired, consider splitting `refund_all`'s payout pro-rata across `NativeDepositOf::iter_prefix(contract)` entries rather than paying the full hold to `origin`.

## Proof of Concept
The existing test `refund_all_drains_multi_contributor_native_hold` in `substrate/frame/revive/src/tests/deposit_payment.rs` already reproduces and asserts this behavior: ALICE and CHARLIE both contribute native deposits via `growStorage()`, ALICE alone calls `terminate(beneficiary=DJANGO)`, and ALICE's balance delta is shown to be `>= alice_entry + charlie_entry` while CHARLIE's balance is unaffected, confirming the full multi-contributor hold is paid to the terminating transaction's origin rather than split by contributor. 		from: &T::AccountId,
		dst: Funds<T::AccountId>,

		let reason = HoldReason::StorageDepositReserve;
		let amount = T::Currency::balance_on_hold(&reason.into(), from);
		if !amount.is_zero() {
			<Self as Deposit<T>>::refund_on_hold(reason, from, dst, amount)?;
		}
		Ok(amount)
	}

	/// Refunds the full native hold to `dst` ignoring the per-contributor cap, then settles the
	/// PGAS hold via [`Self::settle_pgas_refund`] (refunding `RefundPercent` to `dst` and burning
	/// the rest). The native cap only makes sense for partial refunds on a live contract; at
	/// termination there is one recipient and the contract is gone.
	///
	/// Note: callers must run inside a storage layer so partial state rolls back on error.
	fn refund_all(
		from: &T::AccountId,
		dst: Funds<T::AccountId>,
	) -> Result<BalanceOf<T>, DispatchError> {
		let to = match &dst {
			Funds::Balance(to) | Funds::TxFee(to) => *to,
		};
		let native = <() as Deposit<T>>::refund_all(from, dst)?;
		let reason = HoldReason::StorageDepositReserve;

		let pgas = Self::pgas_on_hold(reason, from);
		let pgas = Self::settle_pgas_refund(reason, from, to, pgas)?;
		Ok(native.saturating_add(pgas))
	}

	fn terminate_caller(&mut self, beneficiary: &H160) -> Result<(), DispatchError> {
		ensure!(self.top_frame().delegate.is_none(), Error::<T>::PrecompileDelegateDenied);
		let parent = self.frames_mut().nth(1).ok_or_else(|| Error::<T>::ContractNotFound)?;
		ensure!(parent.entry_point == ExportedFunction::Call, Error::<T>::TerminatedInConstructor);
		ensure!(parent.delegate.is_none(), Error::<T>::PrecompileDelegateDenied);

		let info = parent.contract_info();
		let trie_id = info.trie_id.clone();
		let code_hash = info.code_hash;
		let contract_address = T::AddressMapper::to_address(&parent.account_id);
		let beneficiary = T::AddressMapper::to_account_id(beneficiary);

		let parent_account_id = parent.account_id.clone();

		// balance transfer is immediate
		Self::transfer(
			&self.origin,
			&parent_account_id,
			&beneficiary,
			<Contracts<T>>::evm_balance(&contract_address),
			Preservation::Preserve,
			&mut top_frame_mut!(self).frame_meter,
			&self.exec_config,
		)?;

		// schedule for delayed deletion
		let args = TerminateArgs { beneficiary, trie_id, code_hash, only_if_same_tx: false };
		self.top_frame_mut().contracts_to_be_destroyed.insert(parent_account_id, args);

		Ok(())
	}

/// A contract whose storage was paid for by two different signers, both via the native
/// fallback path, can still be terminated. [`Deposit::refund_all`] bypasses the per-payer
/// [`NativeDepositOf`] cap (one recipient at termination, contract gone), so the full native
/// hold goes to the terminator and any PGAS hold is settled via `settle_pgas_refund`.
#[test_case(FixtureType::Solc)]
#[test_case(FixtureType::Resolc)]
fn refund_all_drains_multi_contributor_native_hold(fixture_type: FixtureType) {
	let (code, _) = compile_module_with_type("MultiContributorStorage", fixture_type).unwrap();
	ExtBuilder::default().build().execute_with(|| {
		Balances::set_balance(&ALICE, 100_000_000_000);
		Balances::set_balance(&CHARLIE, 100_000_000_000);

		let Contract { addr, account_id } =
			builder::bare_instantiate(Code::Upload(code)).build_and_unwrap_contract();

		assert_ok!(
			builder::bare_call(addr)
				.data(MultiContributorStorage::growStorageCall {}.abi_encode())
				.build()
				.result,
		);
		assert_ok!(
			BareCallBuilder::<Test>::bare_call(RuntimeOrigin::signed(CHARLIE), addr)
				.data(MultiContributorStorage::growStorageCall {}.abi_encode())
				.build()
				.result,
		);

		let alice_entry = NativeDepositOf::<Test>::get(&account_id, &ALICE);
		let charlie_entry = NativeDepositOf::<Test>::get(&account_id, &CHARLIE);
		assert!(alice_entry > 0);
		assert!(charlie_entry > 0);

		let hold: <Test as Config>::RuntimeHoldReason = HoldReason::StorageDepositReserve.into();
		let native_held = Balances::balance_on_hold(&hold, &account_id);
		let pgas_held = AssetsHolder::balance_on_hold(PGAS_ASSET_ID, &hold, &account_id);
		assert_eq!(pgas_held, 0, "every charge fell back to native");
		assert_eq!(native_held, alice_entry + charlie_entry);

		let alice_before = Balances::balance(&ALICE);
		assert_ok!(
			builder::bare_call(addr)
				.data(
					MultiContributorStorage::terminateCall { beneficiary: DJANGO_ADDR.0.into() }
						.abi_encode(),
				)
				.build()
				.result,
		);
		let alice_after = Balances::balance(&ALICE);

		assert!(get_contract_checked(&addr).is_none(), "contract should be gone");
		assert_eq!(
			Balances::balance_on_hold(&hold, &account_id),
			0,
			"the full multi-contributor native hold has been released",
		);
		// ALICE receives the full storage-deposit hold (her own + CHARLIE's). The actual delta
		// also picks up the code-upload deposit refund and any tx-level deposit accounting,
		// so it is at least `native_held`.
		assert!(
			alice_after.saturating_sub(alice_before) >= native_held,
			"expected ALICE balance delta >= {}, got {}",
			native_held,
			alice_after.saturating_sub(alice_before),
		);
	});
}
