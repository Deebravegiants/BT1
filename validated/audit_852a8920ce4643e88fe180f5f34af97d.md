### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant spoofing of webhook origin - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body, then passes an *unauthenticated* `shop` value (taken directly from the `X-Shopify-Shop-Domain` header) to the app's handler as the tenant identity. Any request whose body happens to match a previously-observed, validly-signed body can be replayed with an arbitrary `shop-domain` header and will pass HMAC verification, producing a `WebhookMetadata` object that falsely attributes the event to a victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are read straight from HTTP headers and are never included in the signed content: [2](#0-1) 

`Registry.process` validates only the HMAC of the body, then forwards `request.shop` (unauthenticated) to the handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate` confirms `hmac` is a valid signature over `to_signable_string` (i.e., the body only): [4](#0-3) 

This is the same bug class as the referenced report: a field that is *acted on* (here, `shop`, used by the handler as the tenant/session key) is not covered by the binding that is supposed to authenticate the request (the HMAC). In the AURA report, the delegatee/voting-power binding was broken because checkpointing skipped an unbound state; here, the shop-tenant binding is broken because the HMAC signature never covers the header that identifies the tenant. The gem's own documentation instructs handlers to trust `data.shop` directly as the shop domain for the event: [5](#0-4) 

### Impact Explanation
An unprivileged internet user who can install the app on their own shop receives genuinely Shopify-signed webhooks for that shop (valid `raw_body` + `hmac` computed by Shopify using the app's real `client_secret`). Because the signature never binds the body to the `shop-domain` header, the attacker can capture one such valid `(raw_body, hmac)` pair — trivial for topics with generic/empty or attacker-influenced bodies (e.g. `app/uninstalled`, `shop/redact`, or any custom topic whose payload the attacker can make identical across shops) — and replay it against the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and `X-Shopify-Webhook-Id`) header with a victim's shop domain. `Registry.process` will accept it as authentic because only the body is checked, and the handler will receive `WebhookMetadata` claiming the event belongs to the victim shop. If the host app trusts `data.shop` to select which tenant's session/data to act on (exactly as the shipped documentation example does: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), this enables cross-tenant confusion: triggering uninstall/redaction cleanup, disabling features, or corrupting state for a shop the attacker never installed the app on. This satisfies the "cross-tenant access" criterion for a Critical-impact finding.

### Likelihood Explanation
Likelihood is moderate: it requires the attacker to (1) be a legitimate (even trial) installer of the app to obtain at least one genuinely signed `(body, hmac)` pair, and (2) find or force a topic/body that is shop-independent or reproducible, then (3) know or guess the victim's `myshopify.com` domain (typically public/guessable). No access to `api_secret_key`, access tokens, or the victim's credentials is required — only the ability to replay an HTTP request with modified headers, well within the scope of an unprivileged internet user.

### Recommendation
Bind the tenant/topic identity into the authenticated payload rather than trusting unauthenticated headers:
- Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signable content, or
- After HMAC validation, cross-check `request.shop` against a known, previously-established session/shop record before acting on it, and document this requirement prominently, or
- At minimum, update `docs/usage/webhooks.md` to explicitly warn that `data.shop` is not authenticated by the HMAC and must be independently verified against stored session data before being used for any tenant-scoped action.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and registers for a topic whose payload is generic/empty (e.g. `app/uninstalled`), receiving a genuine webhook request:
   ```
   POST /webhook
   X-Shopify-Topic: app/uninstalled
   X-Shopify-Hmac-Sha256: <valid HMAC over body "{}" signed with real client_secret>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {}
   ```
2. Attacker replays the exact same body and HMAC to the app's webhook endpoint, but changes the header:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
3. `ShopifyAPI::Webhooks::Request.new` parses the modified headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because only the (unchanged) body is signed: [3](#0-2) 
4. The handler receives `WebhookMetadata.new(topic: "app/uninstalled", shop: "victim-shop.myshopify.com", ...)` and — following the documented pattern of trusting `data.shop` — performs the app-uninstall cleanup for `victim-shop`, even though that shop never uninstalled the app.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
