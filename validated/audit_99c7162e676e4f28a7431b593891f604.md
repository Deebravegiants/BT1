### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, but that validation only covers the raw request body — not the `shop` (or `topic`/`webhook_id`) header that the resulting `WebhookMetadata` exposes to the host application's handler. This breaks the identity binding `hmac_verified_bytes == data_acted_upon`, analogous to the OpenLeverage report's pattern of checking one value (spot price) while acting on a decision (liquidation) tied to a different, unverified value.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate_signature` computes the HMAC purely over that signable string and compares it against the `hmac` header: [2](#0-1) 

Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are read directly from unauthenticated HTTP headers, entirely independent of the HMAC computation: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build the `WebhookMetadata` object passed to the application's handler: [4](#0-3) 

`WebhookMetadata.shop` is the field host applications are explicitly documented to use as the tenant identifier when persisting/enqueuing webhook data: [5](#0-4) [6](#0-5) 

Because the api_secret_key is per-app (shared across every shop that installs the app) rather than per-shop, any unprivileged user can install the app on their own free/trial shop, receive a legitimately signed webhook (valid `raw_body` + `hmac`), and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g., pointing at a victim tenant). `HmacValidator.validate` still returns `true` since it only checks the (unchanged) body bytes against the shared secret — it never checks that the `shop` header matches the shop the HMAC was actually issued for.

Equality that should hold but doesn't: `shop_header_used_by_handler == shop_bound_by_hmac`. In reality the gem enforces only `hmac_verified_bytes == raw_body_bytes`, with `shop` entirely outside that check.

### Impact Explanation
This is a cross-tenant identity-binding failure (Critical): an attacker with a legitimate but unprivileged shop installation of the target app can forge webhook deliveries that the host application will attribute to a different, victim shop. Any handler logic keyed off `data.shop` (e.g., updating billing state, marking uninstalls, syncing order/product data, looking up the tenant's stored access token) can be triggered under a spoofed tenant identity, since the gem's own signature verification gives no protection to the `shop` claim.

### Likelihood Explanation
Likelihood is significant but bounded by two prerequisites: (1) the attacker must be able to become a real installer of the target app (trivial — any developer/trial store can install a public app), and (2) the attacker must be able to send raw HTTP requests directly to the app's webhook endpoint with custom headers (straightforward, since the endpoint is a public URL and this gem does not check source IP or any other origin-binding value). Given these are easily satisfiable by an "unprivileged internet user," and the gem provides no mitigation itself (it is entirely up to the host app to independently re-validate `shop`, which is undocumented as a requirement), the likelihood is moderate-to-high.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) values into the signature verification, or otherwise cryptographically tie them to the specific delivery: e.g., include the shop domain in the signable string, or require the host application to cross-check `data.shop` against an expected/registered shop before trusting the payload. At minimum, the gem's documentation and `WebhookMetadata` API should make explicit that `shop` is unauthenticated header data, not an HMAC-verified value, so host apps do not implicitly trust it as they are currently encouraged to.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` (a normal, unprivileged action available to any internet user with a Shopify dev/trial store).
2. Shopify sends a legitimately-signed webhook to the app's endpoint:
   ```
   POST /webhook
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   Body: {"id": 1, ...}
   ```
3. Attacker captures this exact `raw_body` + `X-Shopify-Hmac-Sha256` value.
4. Attacker replays the identical body/HMAC to the same endpoint but changes only the shop header:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
5. `ShopifyAPI::Utils::HmacValidator.validate` (via `Request#to_signable_string`, which only signs `raw_body`) returns `true`, since the body bytes are unchanged.
6. `Registry.process` builds `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` and invokes the host application's handler as if this event genuinely originated from the victim shop — see `lib/shopify_api/webhooks/registry.rb:188-199` and `lib/shopify_api/webhooks/request.rb:21-23`.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
