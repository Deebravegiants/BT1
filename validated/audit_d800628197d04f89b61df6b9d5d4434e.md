### Title
Emporium wallet-mode operations can leave withdrawn shielded funds stranded in `HinkalWallet` while `handleOut` reports zero UTXO, permanently freezing user funds - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
The reported bug class is a shares/value-accounting mismatch: value is moved out of the tracked pool by one code path, but the counter/equation used elsewhere to decide "how much value must be returned" is never updated to reflect that movement, so a later step under- or mis-counts the true balance. In `EmporiumUpgradeable.runAction`, the balance equation that produces the caller's returned UTXO is computed solely from balance deltas on the `Emporium` contract itself [1](#0-0) , while in "stateful" (wallet) mode the actual token custody and transfers happen inside `HinkalWallet`, a separate contract [2](#0-1) [3](#0-2) .

### Finding Description
`Hinkal._externalTransact` withdraws shielded value out of the pool and sends it to `circomData.externalActionData.externalAddress` (the `Emporium` contract), then calls `runAction`, treating whatever `UTXO[]` is returned as the "value that came back into the shielded system" [4](#0-3) . The overall balance equation in `Hinkal.transact` requires `balanceDif == amountChanges[i] + utxoAmount` on the Hinkal contract's own token balances [5](#0-4) , so `utxoAmount` (derived from Emporium's returned UTXOs) is the only accounting bridge back into the shielded pool.

Inside `Emporium.runAction`, when `op.invokeWallet` is true and a `stack.signerAddress` is set, the operation is executed by calling `IHinkalWallet(stack.signerAddress).callHinkalWallet(...)`, i.e. the arbitrary call (and any resulting token transfer, e.g. swap proceeds, EIP-1271-authorized withdrawal, or router payout) executes with `HinkalWallet` as `msg.sender`/recipient context, not `Emporium` [2](#0-1) . Yet the UTXO-out calculation only looks at `getBalancesForArray` on the `Emporium` contract before/after the loop of ops [6](#0-5) [7](#0-6) . If a wallet-mode operation causes an external counterparty (router, DEX, protocol) to pay out tokens directly to `HinkalWallet` rather than to `Emporium`, `balancesAfter[i] - balancesBefore[i]` on `Emporium` stays at (or near) zero for that token, so `handleOut` returns an empty UTXO for that token (`balanceChange <= 0` branch) [8](#0-7) . The value that left the shielded pool via `deltaAmountChanges[i] < 0` (already transferred by `Hinkal._externalTransact` into `Emporium`, then possibly forwarded/spent through wallet-invoked calls) is thus never reflected as returned value, exactly mirroring the reported bug's pattern: an operation moves value out of the tracked accounting unit (there: `total_shares` vs. actual vault shares; here: shielded-pool UTXO accounting vs. actual token custody split between `Emporium` and `HinkalWallet`) without updating the counter used by the equality check that gates subsequent value recognition.

`HinkalWallet` itself has no mechanism to sweep or forcibly return stray balances into the shielded-pool accounting except via `doSendToRelay`, which is restricted to paying the configured `relay` and is only invoked explicitly from `payRelayFees`/`sendToRelayFromWallet` [9](#0-8) . There is no generic "return residual token X to Hinkal/Emporium" call path, so if a wallet-invoked operation causes tokens to end up sitting in `HinkalWallet`'s own balance (as opposed to being spent entirely or forwarded back to Emporium within the same operation), those tokens are not represented by any UTXO and become permanently unreachable through the normal `transact` flow, since the balance equation on the Hinkal contract would fail to reconcile the missing amount as `slippageValues`/`amountChanges` unless the prover deliberately encodes a matching negative slippage/amountChange, in which case the user is knowingly authorizing loss — but if the prover assumes the operation always fully round-trips through Emporium (as `handleOut`'s balance tracking implicitly assumes), no on-chain check prevents a wallet-mode op from silently diverting funds to the wallet, breaking the equality `Σ shielded value withdrawn == Σ UTXO value returned`.

### Impact Explanation
This falls under "temporary or permanent freezing of user funds" and potentially "executing calls or moving assets a wallet owner or prover never authorised" — the shielded value withdrawn from the pool for an Emporium operation is not fully reconstituted into a shielded UTXO if the operation's payout lands on `HinkalWallet` instead of `Emporium`, and there is no generic recovery path for that stranded balance through the shielded-transact flow.

### Likelihood Explanation
This requires the wallet-mode path (`op.invokeWallet && stack.signerAddress != address(0)`) to be used with an external call whose token payout destination is the `HinkalWallet` address itself rather than being forwarded back to `Emporium` within the same call sequence (e.g., a partial-fill order, a router that pays the `msg.sender` of the sub-call, or an EIP-1271-gated protocol that treats `HinkalWallet` as the beneficiary). This is plausible given `HinkalWallet` implements `IERC1271` explicitly to be usable as a counterparty-recognized signer/beneficiary for external protocols [10](#0-9) , which is the whole purpose of the "stateful interaction" design. Whether this is exploitable in practice depends on the exact set of external protocols wired up via `EmporiumOperation.endpoint`/`callData` in production, which I could not fully verify from the indexed files (the concrete Emporium-op configurations/tests are out of scope and not fully visible in the index).

### Recommendation
Track and require reconciliation of `HinkalWallet`'s own token balances (not just `Emporium`'s) within `runAction` when wallet-mode ops are used — e.g., have `runAction` also snapshot `HinkalWallet`'s balances before/after the op loop and require that any residual balance increase on the wallet either be zero or be swept back to `Emporium` (or included in the `outUtxo` accounting) before returning, so the equality between shielded value withdrawn and shielded value returned always holds regardless of which contract (`Emporium` or `HinkalWallet`) momentarily custodies the funds.

### Proof of Concept
Not independently reproducible from the indexed contracts alone (no concrete `EmporiumOperation`/router integration test fixtures were available in the index to construct a working end-to-end script). The vulnerable pattern is demonstrated structurally by tracing: `Hinkal._externalTransact` (contracts/Hinkal.sol:244-261) → `Emporium.runAction` case-1 wallet dispatch (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:97-101) → balance-based `handleOut` accounting scoped only to `Emporium`'s own balances (contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol:122-170), with `HinkalWallet.callHinkalWallet` executing arbitrary calls that can direct payouts to the wallet itself (contracts/external-actions/emporium/HinkalWallet.sol:28-34) and no sweep-back mechanism besides the relay-only `doSendToRelay` (contracts/external-actions/emporium/HinkalWallet.sol:36-42). A concrete PoC would require deploying a mock external protocol whose payout targets `msg.sender` of the wallet call (i.e., `HinkalWallet`) to demonstrate the stranded balance and the resulting UTXO under-accounting.
