### Title
Cross-Tenant Webhook Forgery via Unauthenticated Shop-Domain Header - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, while the `shop` (and `topic`, `webhook_id`, `api_version`) values used to route and attribute the webhook to a tenant are read from HTTP headers that are never included in the signed payload. Any party that can obtain one genuine, validly-signed webhook for a shop they control can replay that body with a forged `shopify-shop-domain` header to make the host application process the event as if it belonged to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose contract requires `hmac` and `to_signable_string`. For webhooks, `to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from headers with no cryptographic linkage to the HMAC: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC and then forwards the header-derived `shop` (and `topic`) straight to the app's handler as trusted tenant identity: [3](#0-2) 

`HmacValidator.validate` confirms only that the *body* HMAC matches the app's `api_secret_key`/`client_secret` — it never binds the `shop` header into the signature: [4](#0-3) 

The identity binding the gem should enforce is:
`shop authenticated by HMAC == shop delivered to WebhookHandler#handle`

Because the signature covers only the body, this equality does not hold: an attacker who legitimately installs the public app on their own store (an unprivileged action any merchant can perform) receives real webhooks whose HMAC is computed with the app's single shared `client_secret` over the JSON body. Since the same `client_secret` signs webhooks for every shop that installs the app, the attacker can capture one such webhook, keep the body and HMAC bytes unchanged, and replace only the `X-Shopify-Shop-Domain` header value with a victim shop's domain before resending it to the app's webhook endpoint. `HmacValidator.validate` still succeeds because it never inspects the header, and `Registry.process` hands the handler a `WebhookMetadata` claiming the victim's `shop` with attacker-controlled `body`/`topic` semantics.

### Impact Explanation
This is a cross-tenant integrity/confidentiality break in a multi-tenant app: the host application's webhook handler (which typically updates per-shop records, e.g. `orders/create`, `app/uninstalled`, `customers/redact`) will act on the forged shop identity using attacker-supplied body content, without any credential belonging to the victim shop being required. This matches the "cross-tenant access" Critical impact category — an unprivileged, low-value tenant (their own store) is leveraged to inject or spoof state for an arbitrary other tenant merely by controlling HTTP headers on the replayed request.

### Likelihood Explanation
Likelihood is high for any publicly-installable app: installing the app on one's own store is the only prerequisite, which is by definition available to any unprivileged internet user. No access token, `client_secret`, or leaked credential is required — only reuse of the attacker's own genuine webhook deliveries and a header rewrite, both fully client-controlled.

### Recommendation
Bind the tenant-identifying and routing fields into the signed payload that `HmacValidator` verifies. `Request#to_signable_string` should incorporate `shop`, `topic`, `webhook_id`, and `api_version` (in addition to the raw body) so that any header tampering invalidates the HMAC, restoring the `shop authenticated == shop delivered to handler` equality. At minimum, document and/or enforce that the `shop` returned by `Request` should be cross-checked by the host application against the tenant context expected for the endpoint before being trusted for routing side effects.

### Proof of Concept
```ruby
# 1. Attacker installs the target public app on their own shop "attacker.myshopify.com"
#    and receives a genuine webhook, e.g. for topic "customers/create":
raw_body = '{"id":123,"email":"attacker@example.com"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)
headers = {
  "x-shopify-topic" => "customers/create",
  "x-shopify-hmac-sha256" => Base64.encode64(real_hmac), # genuine, computed by Shopify
  "x-shopify-shop-domain" => "attacker.myshopify.com",   # attacker rewrites this
  "x-shopify-webhook-id" => "any",
  "x-shopify-api-version" => "2024-01",
}

# 2. Attacker forges the shop-domain header to point at a victim tenant,
#    keeping the raw_body and hmac-sha256 header untouched:
headers["x-shopify-shop-domain"] = "victim-shop.myshopify.com"

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# 3. HmacValidator.validate(request) still returns true, because to_signable_string
#    only returns raw_body, and Registry.process forwards data.shop == "victim-shop.myshopify.com"
#    to the app's handler as if the event legitimately originated from the victim.
ShopifyAPI::Webhooks::Registry.process(request)
```
