### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` (tenant identity), `topic`, `webhook_id`, and `api_version` fields are taken from unauthenticated HTTP headers and handed unchecked to the app's webhook handler. This breaks the intended binding `hmac_signed_bytes == bytes_the_app_trusts_for_tenant_identity`, letting an attacker who can obtain any validly-signed webhook body (e.g. by installing the app on their own store) replay that same body/HMAC pair with a forged `shopify-shop-domain` header to impersonate a victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read directly from HTTP headers that are never included in the signed content: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)`, which calls `validate_signature`, comparing `computed_signature = HMAC(secret, verifiable_query.to_signable_string)` against the received HMAC: [3](#0-2) 

Because `to_signable_string` is body-only, this check only proves "the body bytes were produced/authorized by someone holding `api_secret_key`" — it proves nothing about which shop the request is attributed to. Yet immediately after this check passes, `Registry.process` builds `WebhookMetadata` directly from the unauthenticated `request.shop` header and passes it to the app's handler: [4](#0-3) 

`WebhookMetadata.shop` is a `const :shop, String` field consumed by any app-defined `WebhookHandler#handle`: [5](#0-4) 

This is exactly the "field acted on but not covered by the HMAC" analog: the equality that should hold is `hmac_verified_scope == fields_the_handler_trusts_for_tenant_attribution`, but in reality `hmac_verified_scope = {raw_body}` while `fields_the_handler_trusts = {shop, topic, webhook_id, api_version, body}`. `shop` — the single most security-critical field for a multi-tenant app — sits outside the verified scope.

### Impact Explanation
Any actor who can get one legitimately-signed webhook delivered for *any* shop (trivially achievable by installing the target app on an attacker-controlled development/trial store and subscribing to a webhook topic) captures a `(raw_body, hmac)` pair that is valid forever for that `api_secret_key`, independent of shop. The attacker can then POST that same body/HMAC to the app's webhook endpoint with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` dispatches to the handler with `WebhookMetadata#shop` set to the victim's domain. Any app that uses `data.shop` from the handler to look up/update per-tenant records (the documented and expected usage pattern) will act on the victim shop's data using attacker-controlled body content — a cross-tenant access/confusion issue, which meets the "cross-tenant access" Critical impact bar.

### Likelihood Explanation
Exploitation only requires: (1) the ability to become an app user on some shop (any developer/trial store, which most Shopify apps allow), (2) triggering one webhook delivery to capture a valid body+HMAC pair, and (3) sending a crafted HTTP POST with a spoofed `shop-domain` header directly to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or privileged accounts is needed, and the vulnerable code path (`HmacValidator.validate` + `Registry.process`) is exactly the gem's documented, intended usage for verifying inbound webhooks. This is fully reachable by an unprivileged internet user.

### Recommendation
Bind the tenant/routing metadata into the signed content, or otherwise cryptographically tie `shop`, `topic`, and `webhook_id` to the verified payload before they are trusted:
- Include `shop`, `topic`, and `webhook_id` in `Webhooks::Request#to_signable_string` (e.g., concatenate them with the body before HMAC comparison, mirroring how Shopify's `X-Shopify-Hmac-Sha256` is documented to cover the raw body — but since header spoofing is the risk, the library should surface a way for callers to assert the expected `shop`/`topic` against a separately-trusted source, or Shopify's webhook payload itself already contains `shop_domain`/`shop_id` fields that should be treated as the sole source of truth for tenant identity rather than the `shop-domain` header).
- At minimum, document loudly (and ideally enforce in code) that `WebhookMetadata#shop` must never be trusted as verified-by-HMAC, and that apps must cross-check it against the `shop_id`/`shop_domain` contained in the parsed JSON body wherever the topic's payload includes it.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and subscribes to a webhook topic (e.g. `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with headers `x-shopify-shop-domain: attacker.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC over body>`, and some JSON body `B`.
3. Attacker captures `B` and the valid HMAC value.
4. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with body `B`, the same valid `x-shopify-hmac-sha256`, but `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because `to_signable_string` only checks `B` [1](#0-0) .
6. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` [6](#0-5)  and, if the app trusts `data.shop` for tenant lookups, processes attacker-controlled data under the victim's tenant context.
