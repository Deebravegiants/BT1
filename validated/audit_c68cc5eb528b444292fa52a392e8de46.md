Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are trusted from unauthenticated headers while only the raw body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` only proves that the HTTP body was signed with the app's shared `api_secret_key`. The tenant-identifying field `shop` (as well as `topic`, `webhook_id`, and `api_version`) is read directly from HTTP headers (`x-shopify-shop-domain` / `shopify-shop-domain`) and is never covered by the HMAC. `Registry.process` forwards this unauthenticated `shop` value straight to the app's `WebhookHandler#handle` via `WebhookMetadata`, without any additional binding check between the signed payload and the claimed shop.

### Finding Description
- `HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac`. [1](#0-0) 
- For webhooks, `to_signable_string` is defined as just the raw body bytes, with no shop/topic/header binding: [2](#0-1) 
- `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from attacker-controllable HTTP headers, independent of the HMAC: [3](#0-2) 
- `Registry.process` validates the HMAC and then immediately trusts `request.shop` (and the other header-derived fields) to build the `WebhookMetadata` that is delivered to the app's handler: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop-attributed-to-handler == shop-that-produced-the-signed-body`. Because `api_secret_key` is a single, app-wide secret shared across *every* shop that installs the app (not a per-shop key), any unprivileged user can install the app on their own store (a normal, unprivileged action available to any Shopify merchant/developer), trigger a real webhook on that store, capture the legitimately-signed `(raw_body, hmac)` pair from their own shop, and then replay that identical body+HMAC to the app's webhook endpoint while substituting an arbitrary value in the `x-shopify-shop-domain` header (e.g., a victim's shop domain). `HmacValidator.validate` still succeeds because it only checks the body signature, and `Registry.process` reports the forged `shop` value to the handler as if it were authentic. Before vs. after: before, `request.shop` is merely an unverified header; after HMAC "validation," the code (incorrectly) treats it as trustworthy shop identity for the merchant.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to key per-tenant state (e.g., looking up which merchant's access token/session to use for follow-up API calls, updating a specific tenant's database record, or triggering shop-scoped business logic), an attacker can make the app act on/attribute a webhook payload to a shop they do not control. This is a cross-tenant identity-binding failure: the gem asserts a `shop` value to callers that is not actually authenticated by the HMAC, enabling cross-tenant data confusion/manipulation without needing the target's credentials — matching the Critical "cross-tenant access" impact category, since the vulnerable field (`shop`) is exactly the tenant boundary the HMAC is supposed to protect but does not cover.

### Likelihood Explanation
High likelihood of exploitability under the described scope: no privileged access, access tokens, or leaked secrets are required — only the ability to install the app on any (even attacker-owned) shop to obtain one valid `(body, hmac)` pair, after which the `shop` header can be freely rewritten on replay. The only prerequisite is that the host app relies on `data.shop` from `WebhookMetadata` for tenant-scoped actions, which is the documented/expected usage pattern of this gem's webhook handling API.

### Recommendation
Bind the identity headers into the HMAC-verified signable string, or otherwise cryptographically tie `shop`/`topic`/`webhook_id` to the signed body before exposing them to handlers. Concretely, change `Request#to_signable_string` to include a canonicalized representation of `shop`, `topic`, and `webhook_id` alongside `raw_body` (matching how `AuthQuery#to_signable_string` includes all identity fields in its signable string), and update `HmacValidator`/verification tests accordingly so header substitution invalidates the signature.

### Proof of Concept
1. Attacker installs the target app on their own Shopify store (`attacker.myshopify.com`), which is a normal unprivileged flow.
2. Attacker triggers any webhook subscribed by the app (e.g. `orders/create`) on their own store and captures the raw POST body and the `X-Shopify-Hmac-Sha256` header — both correctly signed with the app's single, shared `api_secret_key`.
3. Attacker replays that exact `(raw_body, hmac)` pair to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. In the gem:
   - `Request.new(raw_body:, headers:)` builds the request with `shop` = `"victim-shop.myshopify.com"`.
   - `HmacValidator.validate(request)` computes `HMAC(api_secret_key, raw_body)` and it matches, since raw_body/hmac are untouched.
   - `Registry.process(request)` calls `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))`, passing `shop: "victim-shop.myshopify.com"` to the app, even though the payload actually originated from `attacker.myshopify.com`. [4](#0-3)
