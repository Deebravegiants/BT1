### Title
Ticket-to-intent index mismatch in atomic multi-intent composition causes settlement status misreport - (File: packages/intents-sdk/src/intents/intent-executer-impl/intent-executer.ts)

### Summary
`IntentExecuter.signAndSendIntent` composes a caller's new intent with externally pre-signed `before`/`after` intents and submits them together via `publishIntents`, then picks the ticket for the *newly created* intent purely by positional index (`tickets[beforeCount]`), assuming the relay's response array preserves the same order as the submitted `multiPayloads` array. If that assumption doesn't hold, the SDK returns/tracks the wrong ticket for the caller's intent, causing `waitForIntentSettlement`/`getIntentStatus` to report the on-chain outcome of a different intent.

### Finding Description
`composeMultiPayloads` builds the submitted array as `[...before, newPayload, ...after]` [1](#0-0) , and the caller-facing documentation asserts "The execution order is guaranteed: before → new intent → after" [2](#0-1) .

The code then blindly indexes into the relay's returned ticket list to recover the ticket that corresponds to the newly-created intent:
```
const beforeCount = signedIntents?.before?.length ?? 0;
const newIntentTicket = tickets[beforeCount];
``` [3](#0-2) 

This positional mapping is only correct if `intentRelayer.publishIntents` returns `intent_hashes`/tickets in the exact same order the `multiPayloads` were submitted, and if the relay batch is genuinely atomic (i.e., all intents at that position are always processed as one unit, in order, never partially). The underlying relay call `parsePublishIntentsResponse` simply returns whatever `response.intent_hashes` array the relay gives back, with no re-validation that it matches the order or length of the request's `multiPayloads`/`signed_datas` [4](#0-3) . There is no assertion tying each returned hash back to the specific submitted payload (e.g., by comparing against `computeIntentHash` of each payload) — the SDK trusts index correspondence unconditionally.

This mirrors the reported bug class: SpokeConnector's permissionless `proveAndProcess` allows anyone to reorder message processing, and downstream logic that assumes a specific delivery order can be tricked into acting on the wrong message. Here, the SDK equivalently assumes a strict processing/response order for a batch of otherwise-independent, individually-valid signed intents (each intent is independently authorized by its own signer/nonce; nothing on-chain enforces they execute or get reported in the submitted array order), and uses that assumption to bind a caller-visible ticket to "the new intent" purely by array position.

### Impact Explanation
If the relay ever returns results not in strict correspondence with the request order (e.g., due to partial failures being filtered out, reordering, deduplication against already-processed intents via the "already processed" bypass path at `publishIntents.ts:61-63`, or future relay implementations that batch/dedupe), the SDK will hand the caller a ticket for a *different* intent than the one they think they're tracking. Callers use this ticket with `waitForSettlement`/`getIntentStatus` to decide whether their transfer/withdrawal succeeded — so this becomes a status misreport: a caller could believe their own new intent settled (and act on that, e.g., release goods, mark payment complete) when actually a `before`/`after` third-party intent settled, or vice-versa. This falls under "a status or hash misreport making an integrator credit or refund twice" per the impact criteria.

### Likelihood Explanation
Likelihood is bounded by relay behavior, which is an internal trust dependency of this SDK (the relay/response contract is treated as ground truth) — under the given rules this pushes toward "trust assumptions about external RPCs/relayer" being out of scope for the transport layer itself. However, the root cause sitting in this repo is that the SDK never validates order/length correspondence in code it controls, i.e. it does not verify `tickets.length === composedPayloads.length` nor re-derive each hash from its payload before trusting the index mapping. This is a concrete, reachable code path (any caller using `signedIntents.before`/`after`) rather than a theoretical one, so it warrants documentation/verification, though actual exploitation still requires the relay to violate its own ordering contract.

### Recommendation
Do not rely on positional indexing to recover the new intent's ticket. Instead:
1. Compute `computeIntentHash(multiPayload)` for the newly-signed intent (already done at line 90 for the `onBeforePublishIntent` hook) and match it directly against the relay's returned `intent_hashes`/tickets to find the correct ticket, failing loudly if no match is found.
2. Validate that `tickets.length === composedPayloads.length` before indexing, and throw/log a clear error otherwise instead of silently returning a possibly-wrong ticket.
3. Update the `SignedIntentsComposition` documentation to state clearly that "guaranteed order" refers only to the request payload ordering sent to the relay, not to any guarantee about response array ordering, unless the relayer interface is contractually specified to preserve order 1:1.

### Proof of Concept
1. Caller invokes `sdk.signAndSendIntent({ intents: [...], signedIntents: { before: [presignedA], after: [presignedC] } })`.
2. `composeMultiPayloads` submits `[presignedA, newPayload, presignedC]` to `intentRelayer.publishIntents` [5](#0-4) .
3. Suppose `presignedA` was already processed previously (e.g., resubmitted by another caller/race), triggering the relay's "already processed" branch, which still returns `Ok(response.intent_hashes)` [6](#0-5)  — if this response omits or reorders entries relative to the request (implementation not verified/enforced in this repo), `tickets[1]` (still assumed to be `newPayload`'s ticket) could actually correspond to `presignedC` or `presignedA`.
4. The SDK returns this ticket to the caller as the "new intent" ticket; `waitForSettlement`/`getIntentStatus` then reports the on-chain fate of a different intent than the one the caller actually created and cares about.

Note: I could not fully inspect the relay-side implementation of `solverRelayHttpClient.publishIntents` (its request/response ordering guarantees) within the indexed scope, so the exact conditions under which the relay could violate ordering are not directly provable from this codebase alone — the finding here is that the SDK code itself performs no defensive check against this class of mismatch.

function composeMultiPayloads(
	newPayload: MultiPayload,
	signedIntents?: SignedIntentsComposition,
): MultiPayload[] {
	if (!signedIntents) {
		return [newPayload];
	}

	const result: MultiPayload[] = [];

	// Add "before" intents first
	if (signedIntents.before && signedIntents.before.length > 0) {
		result.push(...signedIntents.before);
	}

	// Add the new payload
	result.push(newPayload);

	// Add "after" intents last
	if (signedIntents.after && signedIntents.after.length > 0) {
		result.push(...signedIntents.after);
	}

	return result;
}
