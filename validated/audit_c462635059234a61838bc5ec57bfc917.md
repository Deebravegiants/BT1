### Title
Fee-refund AMM quote/swap in `correct_and_deposit_fee` uses post-call pool price, letting a signed user self-sandwich their own transaction to drain `AssetConversion` pool reserves via inflated refunds - ([File: substrate/frame/transaction-payment/asset-conversion-tx-payment/src/payment.rs])

### Summary
`ChargeAssetTxPayment` withdraws the non-native fee asset in `prepare()` (via `withdraw_fee`, an actual AMM swap at price P1) and refunds the weight-overestimation surplus in `post_dispatch_details` -> `SwapAssetAdapter::correct_and_deposit_fee` (via `quote_price_exact_tokens_for_tokens` + `swap_exact_tokens_for_tokens`, price P2), where P2 is read from whatever pool reserves exist *after* the attacker's own dispatched `call` has executed. Because the dispatched `call` runs strictly between these two phases and is fully attacker-controlled, a signed user can include an AMM swap (or be an AMM swap itself) in the same extrinsic to deplete the native-asset reserve just before the refund leg executes, inflating the quoted/swapped refund amount and extracting value from the pool beyond what the fee-adjustment legitimately warrants.

### Finding Description
`ChargeAssetTxPayment::prepare` at [1](#0-0)  invokes `withdraw_fee`, which for non-native assets calls `T::OnChargeAssetTransaction::withdraw_fee` (`SwapAssetAdapter::withdraw_fee`) at [2](#0-1) . This quotes `asset_fee` via `quote_price_tokens_for_exact_tokens` and immediately executes a real `swap_tokens_for_exact_tokens`, which mutates the pool's reserves.

The runtime then dispatches the attacker's `call` — fully attacker-controlled content, e.g. a direct `AssetConversion::swap_exact_tokens_for_tokens` extrinsic or a `Utility::batch` containing one — which can further move the same pool's reserves (e.g., depleting the native-asset side while inflating the fee-asset side).

Only after the call completes does `post_dispatch_details` run [3](#0-2) , calling `SwapAssetAdapter::correct_and_deposit_fee` at [4](#0-3) . Here, `refund_asset_amount` is quoted via `S::quote_price_exact_tokens_for_tokens(A::get(), asset_id, refund_amount, true)` against the pool state *as it exists right now* (post-call), and then `S::swap_exact_tokens_for_tokens` is executed using that same quote as `amount_out_min` [5](#0-4) .

Because `get_amount_out` (underlying `quote_price_exact_tokens_for_tokens`) is convex in the reserve ratio — smaller native reserve and larger fee-asset reserve produce disproportionately more fee-asset output for a fixed native `refund_amount` — an attacker who depletes the native reserve of the same pool via their own dispatched call receives an inflated `refund_asset_amount`. The only caps present are `refund_asset_amount.is_zero()`, `F::can_deposit(...) == Success`, and the `max_output` (`reducible_balance` with `Preserve`) check inside `quote_price_exact_tokens_for_tokens` itself (see [6](#0-5) ) — none of which bound the refund relative to the *fair, unmanipulated* fee-equivalent, so the refund can approach the pool's entire reducible fee-asset balance (minus ED) for the cost of only the LP swap fee incurred while depleting the native reserve, plus a comparatively tiny `refund_amount` (bounded by the extension's weight-overestimation margin) fed back into the pool.

Existing protections that were reviewed and found insufficient: `can_deposit` only checks the receiving account can hold the asset, not that the amount is fair; `refund_asset_amount.is_zero()` only guards against a dead route, not a manipulated one; the `max_output` guard in `quote_price_exact_tokens_for_tokens` limits drainage to the reducible balance but does not prevent large single-transaction extraction. There is no TWAP/oracle, no minimum-price-impact guard, and no requirement that the refund conversion rate be consistent with the rate used at withdrawal time.

### Impact Explanation
An unprivileged signed account can extract fee-asset value from an `AssetConversion` pool's liquidity providers, beyond the fair native-fee-equivalent refund, by manipulating the pool's own reserves within the same extrinsic that pays fees through that pool. This is a fee/refund accounting asymmetry that allows underpriced (attacker-favorable) execution of the refund leg, directly harming pool LPs (non-privileged, ordinary users who provided liquidity), matching the scoped "underpriced execution / fee accounting asymmetry via price manipulation" impact.

### Likelihood Explanation
Preconditions are minimal and fully attacker-controlled: a signed origin, an existing `AssetConversion` pool for `(asset_id, native)`, and enough of `asset_id` (or native) capital to move the pool's reserves meaningfully within one transaction. No governance, proxy, or privileged calls are required — the manipulating swap can be the dispatched call itself or bundled via `pallet_utility::batch`. The attack is repeatable every block against any asset-conversion fee-asset pool, bounded only by the attacker's available capital and the pool's reducible balance/ED constraints, and by the size of the weight-overestimation refund margin (larger extension/call weight buffers increase the exploitable `refund_amount`).

### Recommendation
Do not let the refund leg re-price against the pool state mutated by the same transaction's dispatched call. Options: (1) cache the withdrawal-time exchange rate (or a bounded rate window) in `Pre`/`LiquidityInfo` and cap `refund_asset_amount` to what that rate would yield for `refund_amount`, rejecting/clamping any refund quote that deviates beyond a small tolerance; (2) require the refund swap to use a price derived independently of intra-block pool mutations (e.g., a TWAP or last-finalized-block reserve snapshot) rather than the live spot price; (3) bound `refund_asset_amount` to be no larger than a fraction of the originally withdrawn `fee_asset_amount` scaled by `refund_amount/fee_paid`, so the refund cannot exceed what a consistent single price would produce regardless of intervening pool activity.

### Proof of Concept
Rust integration test in `substrate/frame/transaction-payment/asset-conversion-tx-payment/src/tests.rs`:
1. Set up a pool for `asset_id` X / native with substantial liquidity via `setup_lp`.
2. Mint `asset_id` X to `caller`, and also to a "manipulator" balance for `caller` sufficient to perform a large swap.
3. Build `info` with `extension_weight` and a `call` that (a) is itself `AssetConversion::swap_exact_tokens_for_tokens` swapping a large amount of X for native on the same pool, or wrap it via `pallet_utility::batch_all` together with a trivial call.
4. Call `ChargeAssetTxPayment::from(tip, Some(asset_id)).validate_and_prepare(...)` to withdraw `fee_in_asset` at price P1; record `fee_in_asset` and pool reserves.
5. Dispatch the manipulating `call` directly (simulating in-extrinsic execution) to shift the pool's native reserve down and X reserve up; record reserves as (Rn2, Rx2).
6. Call `ChargeAssetTxPayment::post_dispatch_details(pre, &info, &post_info, len, &Ok(()))`.
7. Assert: `expected_token_refund_at_fair_price = AssetConversion::quote_price_exact_tokens_for_tokens` computed against the *pre-manipulation* reserves (Rn1, Rx1) for the same `refund_amount`, and assert the actual refund credited to `caller` (`Assets::balance(asset_id, caller)` delta) is materially greater than `expected_token_refund_at_fair_price`, demonstrating that `fee_in_asset - actual_refund != actual_fee` at any single consistent price, and that the excess corresponds to value drained from the pool's LP reserves (assert pool `asset_id` reserve decreased disproportionately relative to the tiny native `refund_amount` injected).

	fn withdraw_fee(
		who: &T::AccountId,
		_call: &T::RuntimeCall,
		_dispatch_info: &DispatchInfoOf<<T>::RuntimeCall>,
		asset_id: Self::AssetId,
		fee: Self::Balance,
		_tip: Self::Balance,
	) -> Result<Self::LiquidityInfo, TransactionValidityError> {
		if asset_id == A::get() {
			// The `asset_id` is the target asset, we do not need to swap.
			let fee_credit = F::withdraw(
				asset_id.clone(),
				who,
				fee,
				Precision::Exact,
				Preservation::Preserve,
				Fortitude::Polite,
			)
			.map_err(|_| InvalidTransaction::Payment)?;

			return Ok((fee_credit, fee));
		}

		// Quote the amount of the `asset_id` needed to pay the fee in the asset `A`.
		let asset_fee =
			S::quote_price_tokens_for_exact_tokens(asset_id.clone(), A::get(), fee, true)
				.filter(|asset_fee| !asset_fee.is_zero())
				.ok_or(InvalidTransaction::Payment)?;

		// Withdraw the `asset_id` credit for the swap.
		let asset_fee_credit = F::withdraw(
			asset_id.clone(),
			who,
			asset_fee,
			Precision::Exact,
			Preservation::Preserve,
			Fortitude::Polite,
		)
		.map_err(|_| InvalidTransaction::Payment)?;

		let (fee_credit, change) = match S::swap_tokens_for_exact_tokens(
			vec![asset_id, A::get()],
			asset_fee_credit,
			fee,
		) {
			Ok((fee_credit, change)) => (fee_credit, change),
			Err((credit_in, _)) => {
				defensive!("Fee swap should pass for the quoted amount");
				let _ = F::resolve(who, credit_in).defensive_proof("Should resolve the credit");
				return Err(InvalidTransaction::Payment.into());
			},
		};

		// Since the exact price for `fee` has been quoted, the change should be zero.
		ensure!(change.peek().is_zero(), InvalidTransaction::Payment);

		Ok((fee_credit, asset_fee))
	}
