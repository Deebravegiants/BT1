### Title
Webhook `shop` (and `topic`/`webhook-id`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop`, `topic`, and `webhook_id` fields used to authorize and route the webhook are read directly from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only verifies that the body bytes were signed with the app's shared `client_secret` — it never binds that signature to the shop-domain header the body is claimed to belong to. Any party capable of triggering a legitimately-signed webhook body (e.g., a merchant who installs the target app on their own store) can replay that valid `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header, and the library will treat it as a verified webhook for the victim shop.

### Finding Description
`RecordParser.readKeyValue()`'s bug class is "bytes verified vs. bytes parsed" / "a field acted on but not covered by the HMAC" — a value is trusted and acted upon beyond what was actually authenticated. The direct analog here is in the webhook verification pipeline:

- `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

- `shop`, `topic`, and `webhook_id` are parsed straight from attacker-controllable HTTP headers, with no cryptographic binding to the body or its HMAC: [2](#0-1) 

- `HmacValidator.validate`/`validate_signature` compute `HMAC(secret, verifiable_query.to_signable_string)` and compare against the received `hmac` header — this only proves the body bytes were signed by *some* installation of the app using the shared `client_secret`; it says nothing about which shop the body is "for": [3](#0-2) 

- `Registry.process` gates only on this body HMAC, then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build `WebhookMetadata` and dispatches it to the app's handler: [4](#0-3) 

The equality that should hold is: `shop authenticated by the HMAC == shop the handler is told this payload belongs to`. In reality, the HMAC authenticates only the byte-string `@raw_body` against the app's single shared secret; it is completely independent of the `shop-domain` header. Because every shop installation of a given app shares the same `client_secret`, a merchant who legitimately installs the app on Shop A receives real webhooks with valid `(body, hmac)` pairs signed under that shared secret. That merchant can then POST the identical `body`/`hmac` to the app's webhook endpoint while setting `shopify-shop-domain: shop-b.myshopify.com` (or `x-shopify-shop-domain`). `HmacValidator.validate` still returns `true` (the body signature is untouched), and `Registry.process` dispatches to the handler with `shop: "shop-b.myshopify.com"`, `WebhookMetadata` claiming data belongs to Shop B, even though Shop A produced/authorized it.

### Impact Explanation
This breaks the shop-identity binding that webhook handlers rely on to route side effects (e.g., updating a database record keyed by shop, revoking/granting entitlements, deleting data for `shop/redact`, triggering `customers/redact`/`customers/data_request` compliance flows) per shop. An attacker who only needs the ability to install the target app on their own (or any) store — an unprivileged action available to any Shopify user — can attribute arbitrary attacker-chosen webhook bodies (subject to whatever topic/body they can legitimately trigger for their own shop) to a victim shop of their choosing. Depending on how the host application's webhook handlers use `WebhookMetadata#shop`/`topic`/`webhook_id` (which is the intended and documented usage per `Webhooks::Registry.process`), this enables cross-tenant data confusion/corruption, spoofed compliance webhooks against a victim shop, or dispatch of privileged actions under another merchant's identity — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is High: exploitation requires no secrets, no privileged account, and no TLS interception — only the ability to install the app once (as any merchant can) to obtain a validly-signed body/hmac pair, then replay it to the same public webhook endpoint with a forged `shopify-shop-domain`/`x-shopify-shop-domain` header. The library provides no additional binding (e.g., HMAC over a canonicalized string including shop/topic, or a per-shop secret) to prevent this.

### Recommendation
Bind the shop (and topic/webhook_id where used for authorization decisions) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the specific installation:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise verify them against Shopify's own webhook delivery metadata) so `HmacValidator.validate` fails if any of these headers are altered relative to what was actually signed, or
- Require handlers/registry consumers to cross-check `request.shop` against an independently known/authorized shop for the topic before acting, rather than trusting the unauthenticated header outright.

### Proof of Concept
1. Install the vulnerable app on attacker-controlled `shop-a.myshopify.com`; trigger a real webhook (e.g., `orders/create`) and capture the raw POST: headers include `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: orders/create`, and some `raw_body`.
2. Replay the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but replace the header with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds successfully; `Utils::HmacValidator.validate(request)` returns `true` because it only checks `HMAC(secret, raw_body)`: [5](#0-4) 
4. `Registry.process(request)` dispatches to the registered handler with `shop: request.shop` == `"victim-shop.myshopify.com"`: [6](#0-5) 
5. The handler executes attacker-controlled `body`/`topic` logic believing it originated from and pertains to `victim-shop.myshopify.com`.

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
