### Title
Unchecked-length `copy_from_slice` into fixed-size buffer panics the token-bridge inbound handler on a crafted HFT message - (File: modules/pallets/hyper-fungible-token/src/module.rs)

### Summary
`HyperFungibleToken::on_accept` decodes an ABI-encoded `Message` from an inbound ISMP `PostRequest` and, when the message carries calldata with no signature and the source is non-EVM, copies the attacker-controlled `message.from` bytes into a fixed 32-byte array without checking its length first, unlike the sibling `to` field a few lines above which is length-checked. This mirrors the CVE-2025-54481 root cause: a length-prefixed attacker-controlled field is written into a fixed-size buffer without validating that its length matches the buffer size.

### Finding Description
In `on_accept`, the recipient (`message.to`) is safely handled with an explicit length check before any fixed-size copy: [1](#0-0) 

But later, when the decoded message carries optional calldata (`message.data`) and no embedded signature, the "from" bytes — which come straight from the attacker-supplied, ABI-decoded `Message.from` field — are copied into a fixed `[u8; 32]` buffer with **no length check**: [2](#0-1) 

`message` itself is decoded directly from the untrusted request body with no further validation of field lengths: [3](#0-2) 

`Vec<u8>::copy_from_slice` (and the analogous slice method used here) panics if the source and destination lengths differ. Since `message.from` is an attacker-controlled, arbitrarily-sized `bytes` field from the ABI-encoded `Message`, and only the EVM branch (`source.is_evm()`) is length-safe (it always takes the last 20 bytes via `H160::from_slice`), the non-EVM branch is unguarded: any `from_bytes.len() != 32` — including `0` — triggers a panic.

This is exactly the bug class from the CVE: a length-controlled attacker field (`v`/`len` in MFER's tag-3 branch) is written into a fixed buffer (`v[17]`) without validating `len` against the buffer's capacity. Here the "buffer" is `[u8; 32]` and the unchecked length is `from_bytes.len()`.

### Impact Explanation
`on_accept` is invoked by `pallet_ismp`'s message-dispatch path when handling an inbound `PostRequest` addressed to this module — i.e., via the unprivileged `handle_unsigned` extrinsic that any relayer can submit once they have a valid consensus/state proof for a request originating from a registered source contract. A panic raised deep inside dispatchable execution during WASM runtime execution is not converted into a normal `DispatchError`; it manifests as a runtime trap, which typically causes block execution/import for that block to fail. Because this trigger is fully attacker-controlled (a source-chain contract mapped via `ContractToAsset` can freely populate the `from` field of the abi-encoded message body it emits, with no relation to `msg.sender` enforced on-chain), a single relayed message can be crafted to induce a panic on every node that attempts to execute it — a "route unable to deliver messages" condition for the HFT token bridge and, in the worst case, a chain-halting DoS across validators processing the same block.

### Likelihood Explanation
High. Exploitation requires only: (1) a contract mapped in `ContractToAsset` for some non-EVM-destination pairing already exists in production configurations of HFT (any token bridge configured with a non-EVM/substrate destination handling calldata callbacks), and (2) the attacker (source-chain contract owner or anyone able to trigger it to emit a message) sets `Message.data` to a non-empty, decodable `SubstrateCalldata` with `signature: None`, and sets `Message.from` to any length other than 32 bytes (e.g., empty). No relayer collusion or privileged access is needed beyond the normal permissionless relay-and-prove path.

### Recommendation
Add an explicit length check on `from_bytes` before the `copy_from_slice`, mirroring the existing check on `to_bytes`:
```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    ...
} else {
    if from_bytes.len() != 32 {
        Err(HftError::InvalidRecipientLength(from_bytes.len()))?;
    }
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
```
Also audit `from_bytes.len() - 20` in the EVM branch just above — it underflows for `from_bytes.len() < 20`, which would panic in debug builds or wrap in release, producing an out-of-range slice index; that path should also validate length first.

### Proof of Concept
1. An attacker controls (or is) the EVM/non-EVM source contract registered for some `local_asset_id` under `ContractToAsset::<T>::get(source, from)`.
2. They cause a `PostRequest` to be dispatched to the destination Hyperbridge-token pallet whose `body` ABI-encodes a `Message` where:
   - `to` is a valid 20 or 32-byte recipient (so the initial checks pass),
   - `data` is a valid encoded `SubstrateCalldata { signature: None, runtime_call: <any encodable call> }`,
   - `from` is set to an arbitrary length ≠ 32 (e.g., empty bytes or 5 bytes), and `source` corresponds to a non-EVM state machine.
3. A relayer submits this request with a valid membership/consensus proof via `pallet_ismp::Call::handle_unsigned`, invoking `HyperFungibleToken::on_accept`.
4. Execution reaches `account.copy_from_slice(from_bytes)` with mismatched lengths, panicking mid-dispatch and disrupting block execution for any node that processes it — since ` [4](#0-3)  ` has no prior length guard.
