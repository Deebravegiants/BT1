## Title
Permanent DoS of large buys / curve sellout via direct Token donation inflating `Pair.tokenBalance()` above `reserveToken`, causing `Router._computeBuy`'s overflow-cap branch to underflow-revert - (File: `packages/contracts/src/Router.sol`)

### Summary
`Router._computeBuy` caps `tokensOut` at the pair's *live* ERC20 balance (`pair.tokenBalance()`) whenever the uncapped constant-product output would exceed it, then back-calculates `amountInUsed` from `reserveToken - tokensOut`. This subtraction silently assumes `tokenBalance() ≤ reserveToken` — an invariant that only holds under normal buy/sell trading, but is never enforced against a direct, permissionless ERC20 `transfer` of the launched `Token` straight into the `Pair` contract. An attacker who accumulates and donates enough tokens can push `tokenBalance()` above `reserveToken`, after which any buy whose uncapped output would exceed the (now inflated) real balance underflow-reverts with a Solidity Panic instead of gracefully capping.

### Finding Description
`Router._computeBuy` (called from `Router.buy`, `Router.getAmountOut`, and `Router.previewBuy`): [1](#0-0) 

```
uint256 realBalance = pair.tokenBalance();
if (tokensOut > realBalance) {
    tokensOut = realBalance;
    uint256 cappedReserveToken = reserveToken - tokensOut;   // <-- underflows if realBalance > reserveToken
    if (cappedReserveToken == 0) revert OverflowCapDegenerate();
    ...
}
```

`pair.tokenBalance()` is a live `IERC20.balanceOf` read, not the tracked `_pool.tokenReserve`: [2](#0-1) 

By design, `reserve0` (virtual, seeded at `totalSupply` = 1B) exceeds the real transferred `curveSupply` (750M) by a fixed 250M-token gap, and this gap is documented and tested to stay constant under ordinary buy/sell flow: [3](#0-2) 

That test only exercises the invariant via `_buy` calls — it never exercises a direct ERC20 donation of the launched `Token` to the pair, which is exactly the kind of permissionless, unprivileged action the launched `Token` supports (it is a standard ERC20 clone with no transfer restriction to the pair). If an attacker acquires ≥250M+1 tokens (via ordinary curve buys) and `transfer`s them directly to the `Pair` address, `tokenBalance()` is pushed above `reserveToken` while `_pool.tokenReserve` is untouched (only `Router`-gated `swap`/`transferToken` calls mutate `_pool`, and `Pair.swap`'s only integrity check is the K-floor, not a balance/reserve relationship): [4](#0-3) 

Once `realBalance > reserveToken`, any subsequent buy whose uncapped `tokensOut` exceeds `realBalance` (i.e., any buy large enough to hit the overflow-cap branch, which includes the final buy that would otherwise sell out the curve or trigger graduation) computes `tokensOut = realBalance` and then `reserveToken - tokensOut` underflows, reverting the entire buy transaction with an arithmetic Panic rather than the intended `OverflowCapDegenerate` custom error or a graceful cap.

### Impact Explanation
This breaks the supply-side graduation trigger and blocks large/closing buys on the affected curve:
- The docs explicitly flag the supply trigger (`tokenBalance() == 0`) as the fallback for "flat/bear markets where $9K [USD trigger] is never reached": [5](#0-4) 
- With the donation attack in place, that same "live balance never reaches an exhausted state cleanly" problem is compounded: any buy attempting to consume the remaining real supply now panics instead of capping, so the curve can neither complete its natural sellout nor gracefully trigger graduation via the overflow-cap path documented in `AGENTS.md`: [6](#0-5) 
- In a flat/bear-rate scenario (USD trigger never fires), this permanently strands the token in `Lifecycle.Curve` — it can never reach `Graduating`/`Graduated`, locking every trader's capital to a DEX-less bonding curve and denying creators/LPs the graduated liquidity venue. This is a permanent freeze of trader/creator/LP value, matching the required impact bar.

### Likelihood Explanation
The action required — buying a large chunk of tokens (feasible since the curve allows buys up to the full sellable supply, and `Router.buy`'s own overflow cap is what would normally let a whale complete a full buyout) and then issuing a plain `ERC20.transfer` of those tokens to the `Pair` address — is fully permissionless and requires no protocol role, only capital. It is more expensive than a griefing dust-donation (needs >250M tokens, i.e., a third of `curveSupply`), but it is entirely reachable by any funded trader or a competitor wanting to sabotage a specific token's graduation, and the resulting revert condition is persistent (tokens sent to the pair cannot be reclaimed by anyone, since `Pair.transferToken`/`transferAsset` are `onlyRouter`-gated and `Bonding` never sweeps donated Token out except during `_prepareGraduationLiquidity`, which itself cannot run because graduation can't be entered).

### Recommendation
`Router._computeBuy` should not derive `cappedReserveToken` from a live balance read without validating the `tokenBalance() ≤ reserveToken` precondition; either clamp `realBalance` to `min(realBalance, reserveToken)` before the subtraction, or use a saturating subtraction (as already done elsewhere in `Bonding.sol`, e.g. `_ltSwapInventory`) that reverts with the existing `OverflowCapDegenerate` error instead of an unguarded Panic. Additionally, consider having `_enterGraduating`/`_prepareGraduationLiquidity` (or the buy path) burn/sweep any Token balance donated to the pair before it can distort the overflow-cap math, mirroring the existing donation-burn behavior already applied at graduation time.

### Proof of Concept
1. Launch a token via `Zap.createToken`; let curve reserves start at `reserveToken = 1_000_000_000e18` (virtual), `tokenBalance() = 750_000_000e18` (curveSupply).
2. Attacker (or several colluding wallets) buys tokens via `Zap.buy`/`Bonding.buy` until they hold ≥ `250_000_001e18` tokens (this reduces `reserveToken` and `tokenBalance()` in lock-step, preserving the 250M gap).
3. Attacker calls `Token.transfer(pairAddress, 250_000_001e18)` directly — a plain ERC20 transfer, not through `Router`/`Bonding`. Now `pair.tokenBalance() > _pool.tokenReserve`.
4. Any subsequent trader calls `Zap.buy`/`Bonding.buy` with an amount large enough that the uncapped `tokensOut` from `_computeBuy` exceeds the (inflated) `realBalance` — this is exactly the code path meant to gracefully cap the closing buy. The `uint256 cappedReserveToken = reserveToken - tokensOut;` line underflows, and the entire buy transaction reverts with a Solidity arithmetic Panic (`0x11`), not `OverflowCapDegenerate`.
5. As long as the donated tokens remain in the pair (they are unrecoverable — no permissionless sweep exists pre-graduation), every buy attempting to consume near the remaining real supply reverts, and if the USD trigger never fires (flat/bear LT rate), the token can never reach `Lifecycle.Graduating`.

```text
    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
```
