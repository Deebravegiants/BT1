### Title
Webhook shop/topic identity spoofing via HMAC-unbound headers - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that `ShopifyAPI::Webhooks::Registry.process` uses to route and label the payload are read from unauthenticated HTTP headers. This breaks the identity binding between "bytes verified by the HMAC" and "identity fields acted on by the handler," letting anyone who can obtain one genuinely-signed webhook (e.g. by installing the app on their own store) relabel it as belonging to a different shop or a different topic.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`hmac`, `topic`, `shop`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers, none of which participate in the signed content: [2](#0-1) 

`HmacValidator.validate` only checks that `HMAC(secret, raw_body)` matches the `hmac` header — it never verifies that the `shop`, `topic`, or `webhook_id` headers correspond to the body that was actually signed: [3](#0-2) 

`Registry.process` trusts the header-derived `topic` to select the handler and the header-derived `shop` to construct `WebhookMetadata`, which is what the app's handler acts on (e.g. to look up/mutate the shop's data): [4](#0-3) 

The identity binding that should hold is:
`shop/topic authenticated by HMAC == shop/topic the handler acts on`

Because the HMAC only covers the body, this equality does not hold — an attacker who legitimately triggers any webhook for their own store (an ordinary unprivileged action, since anyone can install a public app on their own shop and cause it to fire a webhook) obtains a `(raw_body, hmac)` pair that is valid for *any* combination of `shop-domain`/`topic`/`webhook-id` headers they choose to send it with. Replaying that exact body+HMAC to the app's webhook endpoint with a different `x-shopify-shop-domain` (a victim's shop) or a different `x-shopify-topic` (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`) passes `HmacValidator.validate` and is delivered to the corresponding handler labeled as belonging to the victim shop or to an unrelated topic.

### Impact Explanation
This is a cross-tenant identity-binding failure: the gem allows the shop identity and topic used to select and populate the webhook handler to be attacker-controlled while the cryptographic check only proves body authenticity, not header authenticity. Depending on how the host app's handlers use `WebhookMetadata#shop` and `#topic` (e.g. to deactivate/delete a shop's data on `app/uninstalled` or `shop/redact`, or to key GDPR data-request handling), this enables cross-tenant data corruption/deletion or handler confusion attributed to a shop that never triggered the event — matching the Critical "cross-tenant access" impact class.

### Likelihood Explanation
Likelihood is high for any unprivileged attacker: obtaining a valid `(body, hmac)` pair requires only installing the target app on a shop the attacker controls (a normal, unprivileged workflow) and capturing one webhook delivery. No access to `api_secret_key`, tokens, or the victim's credentials is required — only the ability to POST to the app's public webhook endpoint with attacker-chosen headers.

### Recommendation
Bind the identity headers into the HMAC-verified content, or independently verify them out-of-band per delivery:
- Include `topic`, `shop-domain`, and `webhook-id` (in addition to the body) in `to_signable_string`, and validate them at the registry level before dispatch, or
- Cross-check the header-provided `shop` against records established during OAuth (e.g. an installed/known shop list) and reject webhooks whose `shop` was not previously registered/installed by this app, and
- Ideally, fetch the canonical topic/shop from Shopify's webhook delivery metadata rather than trusting client-supplied headers when constructing `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and triggers any webhook-eligible event (e.g. updates a product), causing Shopify to POST a legitimately HMAC-signed webhook to the app's endpoint with headers `x-shopify-topic: products/update`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, and a valid `x-shopify-hmac-sha256`.
2. Attacker captures the raw body and the `x-shopify-hmac-sha256` value (both are delivered to, or observable by, the shop owner).
3. Attacker replays the exact same raw body and HMAC value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: app/uninstalled` (or another sensitive topic registered by the app).
4. `HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `HMAC(secret, raw_body)`, ignoring the headers.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches to the handler for the spoofed topic with `WebhookMetadata.shop` set to `victim-shop.myshopify.com`, causing the app to act on the victim shop's identity using attacker-supplied body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
