### Title
Webhook `shop-domain` header is not covered by HMAC, enabling cross-tenant shop-attribution spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `#shop` (and `#topic`, `#webhook_id`, `#api_version`) are taken verbatim from unauthenticated HTTP headers. `Registry.process` trusts this header-derived `shop` when constructing `WebhookMetadata` passed to the app's handler, breaking the binding: `hmac-verified bytes == raw_body` while `shop attributed to event == header value` (unverified).

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to `verifiable_query.hmac` [1](#0-0) . For webhooks, `to_signable_string` returns only `@raw_body`, and `hmac` is parsed from the `X-Shopify-Hmac-Sha256` header; `shop`, `topic`, and `webhook_id` are read directly from other headers without being part of the signed content [2](#0-1) .

`Registry.process` only validates the HMAC over the body, then dispatches to the handler using `request.shop` — the unauthenticated header value — as the tenant identity in `WebhookMetadata` [3](#0-2) .

Because the HMAC secret (`Context.api_secret_key`) is per-app (shared across all shops installing that app), not per-shop, any request body/HMAC pair that is valid for one shop remains cryptographically valid regardless of which `shop-domain` header value is attached. An attacker who controls a shop that has installed the app (or who otherwise obtains one valid `(body, hmac)` pair from a real webhook delivery) can replay that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. `HmacValidator.validate` will still return `true` because it never inspects the header, and `Registry.process` will hand the host application a `WebhookMetadata` claiming the event belongs to a different shop than the one that actually produced the body.

### Impact Explanation
This breaks the identity binding between the cryptographically-verified content and the tenant identifier the host application uses to attribute the event (equivalent to: `shop authenticated` ≠ `shop stored/used as session key`). If the host application uses `WebhookMetadata#shop` to look up per-tenant records, credentials, or trigger tenant-scoped side effects (a documented, expected usage pattern in `docs/usage/webhooks.md`), an attacker can inject data or trigger actions attributed to a shop they do not control — a cross-tenant confusion/write primitive achieved without any of the excluded prerequisites (no access token, no `api_secret_key`, no privileged account needed beyond having their own shop install the app).

### Likelihood Explanation
Medium: the attacker needs a legitimately-installed shop of their own (already assumed by the app model) and the ability to capture and replay one valid webhook body+HMAC to the same endpoint with a modified header. No secrets are needed since only the header — never included in the signature — needs to change.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed content verification path, e.g., verify the caller-supplied `shop` header against an expected/registered shop for that delivery, or require the host application to independently confirm the header-derived shop against the session/tenant context before trusting `WebhookMetadata#shop`. At minimum, document prominently that `Request#shop` is not authenticated by the HMAC and must not be used as a sole tenant identifier.

### Proof of Concept
1. App has two installs: `attacker-shop.myshopify.com` and `victim-shop.myshopify.com`, both under the same app (same `api_secret_key`).
2. Trigger a real webhook from `attacker-shop` (e.g., `orders/create`), capturing `raw_body` and the resulting `X-Shopify-Hmac-Sha256` value from the legitimate delivery.
3. Replay the exact same `raw_body` and `hmac` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses successfully [4](#0-3) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against the (still-valid) HMAC [5](#0-4) .
5. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` for data that actually originated from `attacker-shop`, even though `victim-shop` never sent this event.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
