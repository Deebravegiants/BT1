### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC of the raw request body only, but the tenant identifier (`shop`) that is subsequently handed to the host application's handler is read from an unauthenticated HTTP header. This breaks the binding "shop that produced a validly-signed webhook" == "shop attributed to the processed webhook data."

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines its signable content as only the raw body: [1](#0-0) 

The `shop` accessor, by contrast, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is never part of the signed payload: [2](#0-1) [3](#0-2) 

`Registry.process` validates the HMAC over the body and, if it passes, dispatches the handler using `request.shop` as the tenant identity, with no additional check that this header matches the shop that actually produced the signed body: [4](#0-3) 

`HmacValidator.validate` confirms only that `hmac == HMAC-SHA256(secret, to_signable_string)`, i.e. it proves the body bytes were produced by the app's secret, but says nothing about which shop the header claims: [5](#0-4) 

Because the app's `api_secret_key` is shared across every merchant/shop that installs the app, any shop that has installed the app can legitimately receive a validly HMAC-signed webhook body from Shopify (e.g., for a generic/empty-body topic such as `shop/redact` or any payload whose exact bytes an attacker can predict or obtain from their own installation). The attacker — as an ordinary merchant who installed the app on their own store — can capture a genuine `(raw_body, hmac)` pair signed with the app's secret, then replay that exact body/HMAC to the app's webhook endpoint while substituting the `shopify-shop-domain` header with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will invoke the handler with `WebhookMetadata` (or equivalent) attributing the payload to the attacker-chosen victim shop.

The equality that should hold but doesn't:
`shop that cryptographically produced the signed bytes == shop value the handler receives`
In reality: `shop value the handler receives = unauthenticated request header`, independent of the HMAC-covered bytes.

### Impact Explanation
This allows a low-privilege actor (any merchant who can install the target app, which is the normal onboarding flow for a public Shopify app) to make the host application believe a webhook payload originated from a different shop than it actually did. Depending on how the host app uses `WebhookMetadata#shop` (e.g., to look up per-shop sessions/tokens, trigger data deletion, or update per-tenant state), this can lead to cross-tenant data corruption, spoofed compliance webhooks (e.g., falsely triggering `shop/redact` or `customers/redact` for a victim shop), or other cross-tenant confusion — matching the Critical "cross-tenant access" impact category, since the tenant boundary that the HMAC is meant to enforce is not actually bound to the shop field the application relies on.

### Likelihood Explanation
Likelihood is moderate: the attacker needs their own working installation of the target app (trivial for any public/dev app) to obtain a validly-signed body, and needs a topic/body whose bytes are attacker-controlled or predictable (several mandatory/compliance topics have simple, predictable JSON bodies). No access to `api_secret_key`, access tokens, or privileged accounts is required — only the ability to install the app as an ordinary merchant and send a crafted HTTP request to the app's public webhook endpoint.

### Recommendation
- Include the shop domain (and ideally topic/webhook id) inside the HMAC-signed material, or otherwise cryptographically bind the `shopify-shop-domain` header to the signed body before trusting it.
- At minimum, cross-check that the `shop` value used to build `WebhookMetadata` is consistent with a shop the receiving app actually expects/has an active session for, rather than trusting the header verbatim once the body-only HMAC passes.
- Document to consumers of this gem that `request.shop` is not authenticated by the HMAC and must not be used as a sole tenant-identity check.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development shop `attacker.myshopify.com`, obtaining the app's `api_secret_key` context indirectly by being able to trigger genuine webhooks (e.g., `shop/update`, `app/uninstalled`) to their own endpoint, capturing a valid `(raw_body, shopify-hmac-sha256)` pair.
2. Attacker sends this exact `raw_body` and `hmac` header to the victim app's public webhook endpoint, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` (lib/shopify_api/webhooks/registry.rb:190) succeeds because it only validates `raw_body` against the secret, per `to_signable_string` (lib/shopify_api/webhooks/request.rb:35-38).
4. `Registry.process` dispatches the registered handler with `shop: request.shop` == `"victim-shop.myshopify.com"` (lib/shopify_api/webhooks/registry.rb:198), even though the signed bytes were never produced for that shop, achieving cross-tenant webhook spoofing.

          received_signature = verifiable_query.hmac
