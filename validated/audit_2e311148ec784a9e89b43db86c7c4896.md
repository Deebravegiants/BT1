### Title
Webhook shop domain spoofing via HMAC that only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the request body's HMAC signature, then trusts the `shop` value taken from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header to identify which tenant the webhook belongs to. Because the HMAC signable string never includes the shop domain, an attacker who possesses one valid `(body, hmac)` pair (e.g., from a webhook Shopify legitimately delivered to their own store) can replay it against the app's webhook endpoint with an arbitrary `shop` header and have the app process it as belonging to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop` is read directly from a request header, entirely independent of the signable string: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC only over `to_signable_string`, i.e., only the body: [3](#0-2) 

`Registry.process` performs exactly one authenticity check — the HMAC — and then immediately hands the *unauthenticated* `request.shop` to the app's handler as the tenant identifier: [4](#0-3) 

The identity binding that should hold is:
`shop asserted to the handler == shop that produced/authorized the HMAC-signed body`

In fact the code only guarantees:
`hmac-authenticated bytes == raw body`
`shop asserted to the handler == value of an arbitrary, unauthenticated header`

These are not the same thing, so the binding is broken: any `shop` header value can be attached to a validly-HMAC'd body, and `Registry.process` cannot tell the difference.

This is exactly the report's bug-class pattern: "a field acted on but not covered by the HMAC." The gem's own documentation reinforces the false assumption, explicitly claiming that `Registry.process` "will verify the request did indeed come from Shopify": [5](#0-4) 

and that `data.shop` is simply "The shop domain of the webhook" with no caveat that it is unauthenticated: [6](#0-5) 

### Impact Explanation
Any app built on top of this gem that uses `data.shop` from the webhook handler to key merchant records, apply topic-specific side effects (e.g. `app/uninstalled` cleanup, `shop/update`, `customers/redact`) will act on the wrong tenant if an attacker can supply a replayed `(body, hmac)` pair with a forged `shop` header. This is a cross-tenant data-integrity/access issue: an attacker who is a legitimate merchant of the app on their own store (an unprivileged party with no special credentials, no `api_secret_key`, and no access token) can cause the app to process actions attributed to a victim shop simply by capturing one webhook legitimately sent to their own store and replaying it with a modified shop header.

### Likelihood Explanation
The webhook HTTP endpoint is a public, internet-facing route by design (Shopify must be able to POST to it), so no authentication barrier exists beyond the HMAC check that this flow performs. Any user who has installed the app on their own store can trivially capture a real, validly-signed webhook body/HMAC pair delivered to them (e.g. via browser devtools proxy or their own webhook receiver logs) and replay it with an altered `shop` header value, since headers are fully attacker-controlled on any HTTP request sent to the app.

### Recommendation
- Do not treat `request.shop` as authenticated. Either include the shop domain in the HMAC-signed value (not possible without changing Shopify's actual signing scheme, since Shopify itself only signs the body), or require host applications to cross-check `request.shop` against a shop for which the webhook topic/id was actually registered before trusting it.
- At minimum, update `docs/usage/webhooks.md` and the `WebhookMetadata`/`Request#shop` documentation to explicitly state that `shop` is derived from an unauthenticated header and must not be used as a sole tenant-identification mechanism without additional verification (e.g., correlating `webhook_id` against Shopify via the Admin API, or restricting processing to already-known/registered shops).
- Keep the validation as close as possible to where `shop` is consumed (i.e., in `Registry.process` before invoking the handler), per the "long term" recommendation in the referenced report, rather than silently trusting a header the HMAC never covers.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and registers for a webhook topic the app subscribes to (e.g. `app/uninstalled` or any topic with a fully predictable/attacker-influenced body).
2. Shopify delivers a legitimate webhook to the app's endpoint with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of body>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: <topic>`
   and some raw body `B`.
3. Attacker captures `(B, valid_hmac)` from this delivery (they can trivially do this since it's their own store/webhook endpoint).
4. Attacker sends their own POST request directly to the app's webhook route with the same raw body `B` and same `x-shopify-hmac-sha256` value, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Utils::HmacValidator.validate` succeeds because it only checks `B` against the HMAC, per [1](#0-0) .
6. `Registry.process` calls the registered handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)`, per [7](#0-6) , causing the host application to act as if the victim shop sent this webhook.
