### Title
`PoaBridge.findMatchingWithdrawal` matches by assetId only, cross-attributing status/txHash between two same-token withdrawals in one transaction - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`describeWithdrawal` resolves a specific `WithdrawalIdentifier` to a status by fetching all withdrawals for the NEAR transaction hash and then picking the first one whose `nep141:<near_token_id>` equals the requested `assetId`. When a single transaction contains two PoA-bridge withdrawals of the identical `nep141` asset (e.g., two `nep141:arb-0xaf88d065e77c8cc...omft.near` withdrawals to different destinations/amounts), both `WithdrawalIdentifier`s produce the same `findMatchingWithdrawal` result, so one of the two payouts is misreported with the other's status and `txHash`.

### Finding Description
The broken equality the code implicitly assumes is: *for a given `(tx.hash, assetId)` pair there is exactly one withdrawal record*, i.e. `withdrawal.data.near_token_id ⇔ WithdrawalIdentifier` is a bijection. This is false whenever a batch contains two withdrawal intents for the same `assetId` in one NEAR transaction.

Code path:
- `describeWithdrawal` (`poa-bridge.ts:313-343`) calls `getWithdrawalStatusWithRetry` which queries `poaBridge.httpClient.getWithdrawalStatus({ withdrawal_hash: args.tx.hash })` — scoped only by the NEAR tx hash, returning the *list* of all withdrawals produced by that transaction.
- `findMatchingWithdrawal` (`poa-bridge.ts:418-427`) then does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)`, matching purely by token id, **not** by destination address, amount, or intent index.
- The function's own doc comment (`poa-bridge.ts:409-417`) admits: *"multiple withdrawals of the same token in a single transaction are not supported"* — yet nothing in `supports()`, `validateWithdrawal()`, or the batch-building logic in `sdk.ts`/`createWithdrawalIdentifier` rejects or deduplicates such a batch. The SDK happily builds two `WithdrawalIdentifier`s (with distinct `index`, `destinationAddress`, `amount`) from the same `assetId`, submits them in one transaction, and later calls `describeWithdrawal` independently for each.
- Because `Array.prototype.find` always returns the *first* matching element, both identifiers resolve to the same underlying `withdrawal` record: same `status`, same `data.transfer_tx_hash`. If withdrawal #1 is `COMPLETED` and withdrawal #2 is still `PENDING` (or failed), both `WithdrawalIdentifier`s report `{status: "completed", txHash: <withdrawal#1's hash>}` even though only one of the two payouts actually landed.

None of the existing guards prevent this: `supports()` and `validateWithdrawal()` operate per-withdrawal and never check for assetId collisions across a batch; `getWithdrawalStatusWithRetry` is keyed by `tx.hash`, which is shared across all intents in the batch, so it can't disambiguate; `WithdrawalIdentifier.index` is preserved on the identifier object but is never used by `findMatchingWithdrawal` to distinguish entries.

### Impact Explanation
An integrator that calls `IntentsSDK.waitForWithdrawalCompletion` (or `describeWithdrawal`) for both identifiers in a same-token, same-tx batch will get a `completed` status and a `txHash` for a withdrawal that did not actually reach the destination it queried about. This can cause the integrator to release/credit funds for a payout that never completed, or to treat a stuck/failed withdrawal as done — a status/hash misreport that can lead to double-crediting or a stuck withdrawal being incorrectly closed out. This matches the "status or hash misreport making an integrator credit or refund twice" High-severity category.

### Likelihood Explanation
Preconditions: the batch must contain ≥2 PoA-bridge withdrawal intents for the exact same `nep141` `omft.near` assetId within a single NEAR transaction (arbitrary destination addresses/amounts allowed). Nothing in `supports()`/`validateWithdrawal()`/intent construction blocks this composition — an ordinary user (or an integrator forwarding user-controlled batch parameters) can construct such a batch at will and repeat it for every batch they submit, so it is fully attacker-controlled and repeatable. The only cost is constructing a batch with a duplicate token id, which is explicitly called out as unsupported in the code but not actually prevented.

### Recommendation
Either (a) reject batches containing more than one PoA-bridge withdrawal for the same `assetId` in `supports()`/withdrawal-batch validation until the POA API supports disambiguation, or (b) once the API supports it, match withdrawals to identifiers using a stable ordering (e.g., sort both the local withdrawal params and the API's returned withdrawals by amount, since fees are identical for same-token entries, as the code comment itself suggests) instead of matching by `assetId` alone.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
