Based on my investigation, the strongest local analog to the external "config parameter reduced after commitments" bug class is in the `MultisigAccountTimeLock` feature added to `multisig_account.move` — a custom Aptos-native addition (not present in upstream `aptos-core`) that lets owners bypass a transaction timelock once enough approvals ("override threshold") are collected.

### Title
Silent auto-clamping of `MultisigAccountTimeLock.override_threshold` on owner removal can prematurely satisfy the timelock-bypass condition for already-pending transactions - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

### Summary
`update_owner_schema` (invoked via `remove_owners`, `swap_owners`, `swap_owners_and_update_signatures_required`, and `update_signatures_required`) silently rewrites `MultisigAccountTimeLock.override_threshold` whenever the owner set shrinks below the currently configured override threshold, without inspecting the approval state of any already-pending multisig transactions.

### Finding Description
`override_threshold` is a security parameter meant to require an especially high number of owner approvals (higher than the ordinary `num_signatures_required`) before a pending transaction may bypass the timelock delay and execute immediately. When owners are removed, the function clamps the threshold down to the new (lower) owner count instead of preserving the originally configured security bar or re-validating in-flight transactions: [1](#0-0) 

This mirrors the external bug's core invariant violation exactly: an owner-modifiable configuration value (`max_slot` in the Kryptonite report, `override_threshold` here) is changed in place while state created under the old value (submitted bids / already-collected transaction approvals) is not re-validated against the new value. In the original report, bids became unreachable (a mild loss). Here, the analogous side effect is more severe from a custody-control standpoint: lowering `override_threshold` can cause a transaction that was created and partially approved under the old, higher bar to suddenly satisfy the new, lower bar for timelock bypass, undermining the very protection the timelock was designed to provide for multisig-held (and thus APT/asset-custody-relevant) funds.

The function only asserts `override_threshold > num_signatures_required` after clamping [2](#0-1) , but it never checks whether any currently pending transaction's approval count already meets or exceeds the newly-clamped value, nor does it re-timestamp/reset in-flight transactions.

### Impact Explanation
If confirmed by the execution-time check that compares a pending transaction's approval count to `override_threshold` (a code path I was not able to fully trace before the tool budget ran out — see Likelihood/Uncertainty below), an owner-removal transaction (which itself only requires the ordinary `num_signatures_required` votes to execute) could retroactively make a separate, already-pending and only partially-approved transaction eligible for immediate timelock-bypassed execution. Since multisig accounts are commonly used to control resource accounts, code objects, and pooled APT/fungible-asset custody, this could allow a transaction to move or reassign control of custodied assets sooner than the timelock's designed protection window, defeating the safeguard against a compromised or malicious owner rushing through a transaction before the other owners can react.

### Likelihood Explanation
This requires an owner (or a colluding minority of owners) to remove owners (a normal, sanctioned multisig operation) while a sensitive transaction is already pending with partial approvals — a plausible sequence, not requiring any privilege escalation beyond ordinary owner rights already scoped to threshold/owner management. However, I could not verify within the remaining budget the exact code that gates transaction execution against `override_threshold` versus current approvals, so I cannot fully confirm whether a pending transaction's approvals are re-checked live at execution time (which would make this exploitable) or only checked at approval time (which could make the impact merely a lowered future security bar rather than retroactively unlocking an existing pending transaction).

### Recommendation
When `override_threshold` is clamped down due to owner removal, the code should not just clamp silently; it should re-validate all currently pending transactions to ensure none of them already meet the new, lowered override threshold with fewer approvals than would have been required under the original configuration — e.g., by resetting each pending transaction's timelock start time, or by refusing to clamp the threshold below any pending transaction's approval progress until those transactions are resolved (executed or explicitly re-approved).

### Proof of Concept
Conceptual (not executed, due to remaining uncertainty about the execution-time check):
1. Configure `MultisigAccountTimeLock` with `override_threshold = 3` on a 3-owner multisig with `num_signatures_required = 2`.
2. Owner A creates a sensitive transaction (e.g., transferring custody of a resource account); it collects only 2 approvals (satisfies `num_signatures_required` but not `override_threshold`), so it must wait out the timelock.
3. Before the timelock elapses, the same or colluding owners submit and execute a `remove_owners` transaction reducing the owner set to 2, which triggers `update_owner_schema` to clamp `override_threshold` down to `option::some(2)`.
4. If the execution path re-checks override-bypass eligibility using the pending transaction's already-recorded 2 approvals against the now-clamped `override_threshold = 2`, the original sensitive transaction becomes immediately executable, bypassing the timelock it was originally subject to.

**Note on completeness:** I was unable, within the available tool budget, to locate and read the exact function that compares a pending transaction's approval count against `override_threshold` at execution time (the grep results pointed to matches in `multisig_account.move` but I could not retrieve and confirm that specific snippet before the iteration limit was reached). This step is necessary to conclusively prove that clamping retroactively affects already-pending transactions rather than only future ones. I recommend this be verified in a follow-up Devin session with full repository access before treating this as a fully confirmed, high/critical-severity finding.
