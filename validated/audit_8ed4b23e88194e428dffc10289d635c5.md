### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` by defining `to_signable_string` to return only `@raw_body`. `Registry.process` validates that HMAC against `request.hmac` (computed from the `hmac-sha256` header), but then trusts `request.shop`, `request.topic`, and `request.webhook_id` — all of which come straight from HTTP headers that are *not* part of the signed payload — when constructing the `WebhookMetadata` passed to the app's handler.

### Finding Description
`to_signable_string` for a webhook request is defined as: [1](#0-0) 
Only `@raw_body` is signed. Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately hands the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` to the consuming application's handler as trusted tenant/routing metadata: [3](#0-2) 

This breaks the identity-binding invariant `shop authenticated == shop acted on`. Because the same `api_secret_key` (the app's client secret) is shared across every shop that installs the app, an attacker who controls their own shop installation can:
1. Receive a legitimately signed webhook for their own shop (valid `hmac-sha256` header for a body they fully control, since they can trigger events like `orders/create` with attacker-chosen content on their own store).
2. Replay that request to the app's webhook endpoint while altering the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a victim shop.
3. `Utils::HmacValidator.validate` recomputes the HMAC only from `@raw_body`, which is unchanged, so `OpenSSL.secure_compare` succeeds: [4](#0-3) 
4. The handler receives `WebhookMetadata` claiming the (attacker-chosen) body originated from the victim shop, since `shop` is taken straight from the spoofed header.

This is exactly the "field acted on but not covered by the HMAC" identity-binding break: the byte range verified (`raw_body`) does not equal the byte range acted on (`shop` header used as tenant key).

### Impact Explanation
Any multi-tenant app built on this gem that keys per-shop data, uninstall/redact logic, or state transitions off `WebhookMetadata#shop` can be made to attribute attacker-controlled webhook content to an arbitrary victim shop domain, since the shop identifier is never covered by the signature. This is a cross-tenant identity-binding violation reachable by any unprivileged user who can install the app on their own store (no access token, secret, or privileged account required beyond ordinary app installation) — matching the High severity "cross-tenant access" category via a scope/identity check that is bound to the wrong data (body signed, tenant unauthenticated).

### Likelihood Explanation
Exploitation requires only that the attacker: (a) install the target app on a shop they control, (b) capture one legitimately signed webhook delivery for that shop, and (c) replay it with a modified `shop-domain` (and/or `topic`/`webhook-id`) header to the app's public webhook endpoint. No secrets are needed since the attacker never needs the `api_secret_key` itself — they only reuse a signature that Shopify computed for them. This is straightforward and repeatable, making likelihood high wherever an app trusts `WebhookMetadata#shop`/`topic`/`webhook_id` for authorization or data-partitioning decisions.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the signable payload used for HMAC verification (or otherwise cryptographically bind them, e.g., by validating the shop domain against the session/shop that installed the app before trusting header-derived values), so that `to_signable_string` covers every field the registry subsequently acts upon, not just the raw body.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. `orders/create`) with a body they fully control (order description, custom fields, etc.).
2. Shopify delivers this webhook to the app's endpoint with a valid `X-Shopify-Hmac-Sha256` header computed over that body using the shared `api_secret_key`.
3. Attacker intercepts/replays this exact request to the app's public webhook endpoint but rewrites `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (topic/webhook-id can also be altered).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `@raw_body` against the (unmodified) HMAC header — validation passes.
5. `handler.handle` is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)` even though the payload actually originated from, and was fully authored by, the attacker's own shop — a cross-tenant identity-binding break.
