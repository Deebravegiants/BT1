### Title
Direct LT donations to a bonding-curve `Pair` become permanently and irrecoverably locked, with no sweep/rescue path before or after graduation - (File: `packages/contracts/src/Pair.sol`, `packages/contracts/src/Router.sol`, `packages/contracts/src/Bonding.sol`)

### Summary
`Pair` tracks reserves in a separate stored `_pool` struct rather than live ERC20 balance, and only exposes withdrawal of its asset (LT) balance via `transferAsset`, gated `onlyRouter`. `Router` only calls `transferAsset` from two places — `sell()` (bounded by curve math) and `graduate()` (bounded by `Bonding._prepareGraduationLiquidity`'s exact `ltFromPair` amount, computed from *stored* reserves, not live balance). Any LT sent directly to the `Pair` address via a plain ERC20 `transfer` — before or after graduation — is excluded from every withdrawal path and becomes permanently stuck, mirroring the reported class of bug where the withdrawable-amount accounting (based on a tracked counter instead of the real balance) leaves real, undeposited-for-any-purpose tokens locked forever.

### Finding Description
`Pair.sol` maintains reserves in `_pool.tokenReserve` / `_pool.assetReserve`, updated only by `mint` and `swap` (both `onlyRouter`) — direct ERC20 transfers to the `Pair` change `IERC20(assetToken).balanceOf(address(this))` but never `_pool.assetReserve`: [1](#0-0) 

The only function capable of moving the pair's LT balance out is `transferAsset`, gated `onlyRouter`: [2](#0-1) 

`Router` exposes `transferAsset` through exactly two paths: `sell()` (curve math, bounded by the AMM formula) and `graduate()`, which transfers only the caller-supplied `amount` — not the live balance: [3](#0-2) 

`Router.graduate` is only ever invoked once per token, from `Bonding._prepareGraduationLiquidity`, with `amount = ltFromPair`, which is deliberately computed from the pair's *stored* reserves minus the launch-time virtual seed — explicitly excluding any live-balance donation: [4](#0-3) 

This design is intentional for "donation resistance" of the graduation trigger and LP-open price, and the code/docs acknowledge that donated LT "stays in the curve pair" and is reachable "only via `Pair.transferAsset`... gated by `Router`'s `BONDING_ROLE`": [5](#0-4) 

However, once `_enterGraduating` runs, the lifecycle flips to `Graduating`/`Graduated` and `Router.graduate()` is never callable again for that token (it is only reached from `_prepareGraduationLiquidity`, itself only reached once from `_enterGraduating`). After graduation, all trading moves to the external HyperSwap pool; the internal `Pair` is permanently retired but still holds any LT that was donated to it (pre- or post-graduation) with **zero on-chain path to ever move it out again** — `Pair` has no owner/admin sweep function, and `Router`/`Bonding` never call `transferAsset` a second time for a given token. This is functionally identical to the reported `BaseMilestone.withdrawAdmin` bug class: value that was never "reserved" for any specific purpose ends up permanently unreachable because the withdrawal/accounting logic is scoped to a fixed, pre-computed amount rather than the contract's actual token balance.

### Impact Explanation
Any LT transferred directly to a bonding-curve `Pair` address (by a trader mis-clicking, a bot attempting to "donate" to pump the curve, or any unrelated wallet) is permanently and irrecoverably lost — a genuine, concrete freezing of user funds with no recovery mechanism anywhere in the codebase (`Pair`, `Router`, `Bonding` all lack a sweep/rescue for this specific pool of stuck LT). Unlike `FeeVault`'s `sweepDonations()` (which explicitly recovers excess/donated USDC) or `Bonding.finalizeGraduation`'s `_sweepLTToOwner` (which recovers excess LT from the *graduation LP-seeding* flow), the curve `Pair` itself has no equivalent recovery path for its own donated LT, either pre- or post-graduation.

### Likelihood Explanation
Reachable by any unprivileged wallet with a single `IERC20(lt).transfer(pairAddress, amount)` call — no special permissions, timing, or coordination required. The `pairAddress` for any launched token is public (`Factory`/`Bonding.getTokenInfo`), so this can happen accidentally (fee-on-transfer confusion, copy-paste of the wrong recipient, or well-meaning "donation" attempts by traders) as well as deliberately.

### Recommendation
Add a permissionless sweep function to `Pair` (or route through `Router`, gated by `BONDING_ROLE`) that drains `assetToken.balanceOf(address(this)) - assetReserve` (and analogously for `tokenBalance` beyond `tokenReserve`) to a safe recipient (e.g. `FeeVault` or the protocol treasury), mirroring the pattern already used in `FeeVault.sweepDonations()` and `Bonding._sweepLTToOwner`. This preserves the existing donation-resistance guarantees for graduation triggering/pricing while ensuring stray/donated LT is not permanently destroyed.

### Proof of Concept
1. `Bonding.launch()` a token; its `Pair` address is public via `Factory.getPair`/`Bonding.getTokenInfo`.
2. An unrelated wallet calls `IERC20(lt).transfer(pairAddress, 1000e18)` directly (no approval/allowlist required — plain ERC20 transfer).
3. `Pair._pool.assetReserve` is unchanged (only `mint`/`swap` update it), so `IPair(pair).getReserves()` and `canGraduate()`'s USD-trigger calculation ignore the donated LT, exactly as documented.
4. The token trades normally and eventually graduates: `_enterGraduating` → `_prepareGraduationLiquidity` computes `ltFromPair` from stored reserves (excluding the donation) and calls `Router.graduate(token, ltFromPair)`, draining only the legitimate raised LT.
5. `finalizeGraduation` completes; `info.lifecycle` becomes `Lifecycle.Graduated`. `Router.graduate` can never be called again for this token (unreachable outside `Lifecycle.Curve`).
6. The donated `1000e18` LT remains in `Pair` forever — `Pair.transferAsset` is `onlyRouter`, and no remaining code path ever calls it for this token again. `assertTrue(IERC20(lt).balanceOf(pairAddress) >= 1000e18)` holds indefinitely with no owner/permissionless recovery call available anywhere in `Pair.sol`, `Router.sol`, or `Bonding.sol`.
