### Title
Removing a state machine from `HostParams.stateMachines` does not revoke its acceptance, so a de-whitelisted (e.g. compromised) counterparty chain keeps having its state commitments and messages accepted without new governance approval - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.updateHostParamsInternal` only ever *adds* entries to `_latestStateMachineHeight` when governance updates `HostParams.stateMachines`; it never clears the mapping entry for a state machine that is dropped from the new `stateMachines` array. Since acceptance of consensus state updates and downstream message processing is gated on `_latestStateMachineHeight[id] != 0` rather than on current membership in `_hostParams.stateMachines`, a state machine that governance has "removed" continues to be treated as authorized indefinitely, mirroring the reported bug class where a revoked privilege silently survives a removal action and can keep acting without a fresh proposal/time-delay.

### Finding Description
`updateHostParamsInternal` (the internal path shared by `updateHostParams`, callable only by the cross-chain-governed `hostManager`) processes the new `stateMachines` list purely additively: [1](#0-0) 

```solidity
// add whitelisted state machines
for (uint256 i = 0; i < stateMachinesLen; ++i) {
    // create if it doesn't already exist
    if (_latestStateMachineHeight[params.stateMachines[i]] == 0) {
        _latestStateMachineHeight[params.stateMachines[i]] = 1;
    }
}
```

There is no corresponding pass that zeroes `_latestStateMachineHeight` for state machine IDs that were present in the old `_hostParams.stateMachines` but are absent from the new `params.stateMachines`. The foundry test confirms this behavior is intentional/expected for the production `EvmHost`: [2](#0-1) 

and the special-cased `TestnetHost.updateHostParams` explicitly documents that clearing `_latestStateMachineHeight` for the new whitelist only happens on testnets, when called by `admin` — not by the governance-driven `hostManager` path that mainnet relies on: [3](#0-2) 

Downstream, `HandlerV2.handleConsensus` gates whether a new intermediate state (i.e., a new state commitment for a given state machine) is stored purely on this same non-zero height flag, not on membership of the current whitelist: [4](#0-3) 

```solidity
for (uint256 i = 0; i < intermediatesLen; i++) {
    IntermediateState memory intermediate = intermediates[i];
    uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
    if (latestHeight != 0 && intermediate.height > latestHeight) {
        ...
        host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
    }
}
```

Once a state machine's flag has been set to non-zero by an earlier `updateHostParams` call, no later `updateHostParams` call that omits that ID from `stateMachines` will reset it back to zero. Consequently, new state commitments for that "removed" chain keep being accepted and stored, and `handlePostRequests`/`handleGetResponses` (which rely on `host.stateMachineCommitment(...)` being populated) keep accepting proofs/messages sourced from that chain, exactly as if it were still whitelisted — with no new governance proposal, consensus verification bypass check, or explicit re-add.

This is the direct analog of the reported bug class: the "removal" action (dropping a state machine from `HostParams.stateMachines`) fails to clear the underlying authorization state (`_latestStateMachineHeight`), so the privilege silently persists/reactivates without requiring the fresh governance flow (a new `updateHostParams` dispatch through Hyperbridge) that is supposed to gate it.

### Impact Explanation
If governance ever needs to de-whitelist a state machine — for instance because its consensus client was compromised, its bridge peg was broken, or it needs to be quarantined for any security reason — the removal has no actual effect on the mainnet `EvmHost`. Messages, GET responses, and new state commitments from the "removed" chain continue to be accepted and dispatched to local `IApp` modules, defeating the intended security control and potentially enabling forged message delivery / unsound state acceptance from a chain governance believed to be cut off. This is a Medium-severity governance/authorization bypass since it requires no attacker action beyond an already-issued (and reasonably expected) governance removal.

### Likelihood Explanation
This triggers deterministically any time governance performs a `HostParams` update that drops a previously-whitelisted state machine ID from `stateMachines` — a legitimate, expected governance action (e.g., in response to an incident) — with no additional attacker capability required. It is easily reachable through the normal `updateHostParams`/`HostManager.onAccept` governance path documented in the codebase.

### Recommendation
In `EvmHost.updateHostParamsInternal`, compute the set difference between the old `_hostParams.stateMachines` and the new `params.stateMachines`, and explicitly `delete _latestStateMachineHeight[id]` (and any other per-state-machine bookkeeping such as stored commitments/`_stateMachineUpdateTime`, if desired) for every ID removed from the whitelist, mirroring what `TestnetHost` already does for the admin-triggered path, but applying it uniformly to the governance-triggered path used on mainnet.

### Proof of Concept
1. Governance calls `updateHostParams` with `stateMachines = [A, B]`. Both `_latestStateMachineHeight[A]` and `_latestStateMachineHeight[B]` become `1` (see `evm/src/core/EvmHost.sol:638-644`).
2. Relayers submit consensus/state proofs for `A`, advancing `_latestStateMachineHeight[A]` and storing state commitments via `HandlerV2.handleConsensus` (`evm/src/core/HandlerV2.sol:155-164`).
3. Governance later dispatches `updateHostParams` with `stateMachines = [B]` only (intending to remove `A`, e.g. after discovering `A`'s consensus was compromised). Per `evm/src/core/EvmHost.sol:638-644`, `_latestStateMachineHeight[A]` is left unchanged (non-zero).
4. A relayer submits a new consensus proof containing an intermediate state for `A`. `HandlerV2.handleConsensus` checks `latestHeight != 0` for `A`, which is still true, so the new commitment is stored and accepted (`evm/src/core/HandlerV2.sol:158-163`), exactly as if `A` were still whitelisted — despite governance's removal action never having been reverted or reproposed.

        HostParams memory params = host.hostParams();
        uint256[] memory stateMachines = new uint256[](2);
        stateMachines[0] = 2000;
        stateMachines[1] = 2001;
        params.stateMachines = stateMachines;

        // create a state commitment
        StateMachineHeight memory height = StateMachineHeight({height: 100, stateMachineId: 2000});

            height, StateCommitment({timestamp: 200, overlayRoot: bytes32(0), stateRoot: bytes32(0)})

        vm.prank(params.handler);

        // add the new state machine

        // should be unchanged

        // should be set to 1
        assert(host.latestStateMachineHeight(2001) == 1);
    }

    /**
     * @dev Updates the HostParams. Callable by either `hostManager`
     * (cross-chain governance) or the configured `admin`. When invoked by
     * the admin, resets `_latestStateMachineHeight` for each state machine
     * in `params.stateMachines` before applying the new params, mirroring
     * the prior testnet behavior that lived inside `EvmHost`.
     */
    function updateHostParams(HostParams memory params) external override {
        address caller = _msgSender();
        if (caller != _hostParams.hostManager && caller != _hostParams.admin) {
            revert UnauthorizedAction();
        }

        if (caller == _hostParams.admin) {
            uint256 whitelistLength = params.stateMachines.length;
            for (uint256 i = 0; i < whitelistLength; ++i) {
                delete _latestStateMachineHeight[params.stateMachines[i]];
            }
        }

        updateHostParamsInternal(params);
    }
