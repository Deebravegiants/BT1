### Title
Same-token batch withdrawal status/hash misreport due to matching by assetId instead of unique withdrawal — ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal` and the analogous `findMatchingWithdrawal` helper in `internal-utils` resolve a withdrawal's on-chain completion status by matching on `assetId` only, via `Array.prototype.find`, which returns the first entry whose `near_token_id` matches. When a batch withdrawal (`sdk.processWithdrawal`/`sdk.waitForWithdrawalCompletion` with a `WithdrawalParams[]`) contains two or more legs withdrawing the **same token** (same `assetId`) to different destinations/amounts in one NEAR intent transaction, every leg's `describeWithdrawal` call independently resolves to the *same first matching* withdrawal record from the POA bridge's response list.

### Finding Description
`createWithdrawalCompletionPromises` in `packages/intents-sdk/src/sdk.ts` creates one polling promise per withdrawal leg for a batch withdrawal, each of which calls `watchWithdrawal` → `bridge.describeWithdrawal` [1](#0-0) .

In `PoaBridge.describeWithdrawal`, the withdrawal is looked up in the (unordered) API response purely by `assetId`: [2](#0-1) 

and the matching function itself explicitly documents that it can't disambiguate multiple same-token withdrawals in one transaction: [3](#0-2) 

The same limitation, with the same caveat comment, exists independently in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`: [4](#0-3) 

Because `Array.find` returns only the first array element satisfying the predicate, if a NEAR intent transaction contains two withdrawals of `nep141:usdc.omft.near` (e.g., different destination addresses/amounts as part of a batch), both `describeWithdrawal` calls (index 0 and index 1) query the same `withdrawal_hash` (the intent tx hash) and both independently `find()` the *same* record — typically the first one the POA API happens to return, since the response is documented as unsorted. This breaks the equality that each withdrawal-completion promise should resolve with the destination tx hash/status *of that specific leg*; instead both legs can resolve to the identical `transfer_tx_hash`/`chain`, i.e., a status/hash misreport.

### Impact Explanation
This falls under "a status or hash misreport making an integrator credit or refund twice" (High). An integrator using `sdk.waitForWithdrawalCompletion`/`sdk.processWithdrawal` for a batch of same-token withdrawals (e.g., a batch payout splitting the same token to two recipients) would receive two `TxInfo` results carrying the same `destinationTxHash`. If the integrator marks each withdrawal as completed/credited based on this per-leg result (as the API is explicitly designed to allow via `createWithdrawalCompletionPromises`/`watchWithdrawals`, see the batch-withdrawal RFC), it could double-credit or misattribute completion of one leg using the transaction hash that actually belongs to the other leg, and the other leg's true completion (or failure) is never correctly observed.

### Likelihood Explanation
Likelihood is limited to the specific but foreseeable scenario of batch withdrawals containing two-or-more legs of the *same* `assetId` within one NEAR intent transaction. The SDK's public batch-withdrawal API (`WithdrawalParams[]`) does not prevent or warn callers against constructing such a batch, and the RFC in this repo (`docs/design/rfc-batch-withdrawal-granular-control.md`) is specifically about giving integrators granular per-leg tracking for batches — a use case where this ambiguity directly undermines correctness. This is explicitly a known, documented gap in the code (not a hypothetical), acknowledged by the authors in both copies of `findMatchingWithdrawal`.

### Recommendation
Disambiguate same-asset withdrawals within a batch instead of matching by `assetId` alone. As the code comments suggest, sort withdrawals returned by the POA API and the local `withdrawalParams`/index by amount (since relayer fees are equal for same token, relative amount ordering is preserved) or otherwise thread a per-leg discriminator (e.g., amount + destination address, or a nonce/leg-id round-tripped through the underlying transfer) through to `findMatchingWithdrawal`, so each `describeWithdrawal` call is guaranteed to resolve the correct leg rather than the first `assetId` match.

### Proof of Concept
1. Submit `sdk.signAndSendWithdrawalIntent` with `withdrawalParams: [ {assetId: "nep141:usdc.omft.near", amount: A, destinationAddress: addr1}, {assetId: "nep141:usdc.omft.near", amount: B, destinationAddress: addr2} ]` in one NEAR intent tx (`intentTx.hash = H`).
2. Call `sdk.waitForWithdrawalCompletion({ withdrawalParams: [...], intentTx })`, which internally issues two `describeWithdrawal` calls, both querying `getWithdrawalStatus({ withdrawal_hash: H })`.
3. Suppose the POA API returns `withdrawals = [{status: COMPLETED, near_token_id: "usdc.omft.near", transfer_tx_hash: "0xLEG1"}, {status: COMPLETED, near_token_id: "usdc.omft.near", transfer_tx_hash: "0xLEG2"}]` (order not guaranteed to match request order, per the code's own comment).
4. Both leg-0 and leg-1 `findMatchingWithdrawal` calls filter only on `assetId === "nep141:usdc.omft.near"` and both `Array.find` return the same first element `{transfer_tx_hash: "0xLEG1"}`.
5. Result: `waitForWithdrawalCompletion` resolves both promises with `destinationTxHash: "0xLEG1"`, even though leg 1's actual on-chain transfer was `0xLEG2` — an integrator crediting/refunding based on this per-leg hash would attribute or double-count the same destination transaction for two distinct withdrawal legs.

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
