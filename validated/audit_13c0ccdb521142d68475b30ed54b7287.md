Confirmed: the Tron variant of `IntentGatewayV2.placeOrder` computes `protocolFeeBps`/`reducedInputs`/`commitment` purely from the user-supplied `order.inputs[i].amount`, before any token transfer occurs, and then escrows that same nominal amount via `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` (non-predispatch path) or via the dispatcher sweep (predispatch path) without ever measuring the actual balance received.### Title
Tron `IntentGatewayV2.placeOrder` records escrow at nominal input amounts instead of actually-received balances, causing permanent freezing/insolvency for fee-on-transfer tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol:338-506`) computes the order commitment, protocol fee deduction, and the escrow ledger entry `_orders[commitment][token]` from the user-supplied nominal `order.inputs[i].amount`, then transfers tokens via `IERC20.safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` (or via the predispatch/dispatcher sweep path) without ever measuring the actual balance the contract received. This is exactly the bug class in the referenced report: for fee-on-transfer/deflationary tokens, the contract records more escrow than it actually holds.

### Finding Description
In the non-predispatch path: [1](#0-0) 
tokens are pulled with `safeTransferFrom` using the raw `order.inputs[i].amount`, and immediately afterward `_orders[commitment][token] += reducedInputs[i].amount` is credited using the same nominal (fee-adjusted-for-protocol-fee-only) amount — never the actual post-transfer balance delta.

In the predispatch path, the dispatcher-swept balance is checked only with `balance < requiredAmount` (reverting if less), but the escrow amount recorded is still `reducedInputs[i].amount` (the nominal figure), not the real dust-adjusted balance transferred to the gateway: [2](#0-1) 

This contrasts with the primary EVM `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol:230-329`), which was explicitly hardened against this exact issue: it snapshots balances before/after each transfer and mutates `order.inputs[i].amount` to the *actual received* amount before computing the commitment and escrow: [3](#0-2) 
That fix is validated by dedicated tests (`testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`, `testPlaceOrder_FeeOnTransferToken_WithProtocolFee`, `testPlaceAndFill_FeeOnTransferToken_RoundTrip`, `testPlaceOrder_FeeOnTransferToken_Predispatch`) in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2441-2686`.

The Tron fork, however, retains the vulnerable pattern: `_orders[commitment][token]` is credited with the nominal amount regardless of how many tokens actually landed in the contract.

### Impact Explanation
When `withdraw()` is later invoked (on cancel/refund or upon a cross-chain `RedeemEscrow`/`RefundEscrow` message), it unconditionally transfers `amount = body.tokens[i].amount` (which mirrors the over-recorded `_orders[commitment][token]` value) to the beneficiary: [4](#0-3) 
For any fee-on-transfer/deflationary ERC20 used as an order input on the Tron deployment, the contract will hold strictly less than the recorded escrow amount. This causes:
- Reverting/failed withdrawals for the affected order (denial of service / permanent freezing of the user's principal, since `token.call(...transfer...)` will fail once the contract's balance is insufficient), and
- More critically, insolvency across the shared escrow pool: other unrelated orders' legitimate escrow balances for the same token become undercollateralized once one fee-on-transfer order drains more than it deposited, since all orders share the same token balance in the contract. This can allow later withdrawers to succeed while earlier/other legitimate depositors' escrow becomes unredeemable — a permanent freezing of funds condition for at least one user, reachable directly via a single `placeOrder` call from an unprivileged user.

### Likelihood Explanation
Likelihood is high whenever the Tron IntentGatewayV2 deployment allows fee-on-transfer or rebasing/deflationary tokens as order inputs (nothing in the contract enforces standard, non-fee ERC20 semantics for allowed input tokens). Any ordinary user placing an order with such a token triggers the discrepancy — no privileged role or special condition is required, only a single `placeOrder()` transaction.

### Recommendation
Mirror the fix already applied to `evm/src/apps/IntentGatewayV2.sol`: snapshot the contract's (or dispatcher's) token balance immediately before and after each `transferFrom`/sweep, and use the measured delta — not the nominal `order.inputs[i].amount` — as the basis for (a) the escrow amount credited into `_orders[commitment][token]`, and (b) the value hashed into the commitment, applying protocol-fee deduction on top of the actual received amount rather than the nominal one.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` with a fee-on-transfer ERC20 (e.g., 1% fee) as a permitted input token, analogous to the `FeeOnTransferToken` test helper already present in `evm/tests/foundry/IntentGatewayV2SameChainTest.sol:2689-2730`.
2. User calls `placeOrder` with `inputs[0].amount = 1000e18`. Because Tron's `placeOrder` (`evm/tron/contracts/apps/IntentGatewayV2.sol:338-469`) does not measure actual received balance, `_orders[commitment][fot]` is credited with `1000e18` (minus only the protocol fee, if configured), while the contract's actual `fot.balanceOf(address(this))` is only `990e18`.
3. On successful fill/redemption or cancellation, `withdraw()` (`evm/tron/contracts/apps/IntentGatewayV2.sol:691-714`) attempts to transfer `1000e18` (minus protocol fee) to the beneficiary/solver — exceeding the contract's actual token balance, causing either a revert (locked funds for that order) or, if other orders' escrowed balances of the same token cover the shortfall, silent draining of other users' legitimately escrowed funds.
