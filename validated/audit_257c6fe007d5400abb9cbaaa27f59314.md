### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` signs only the raw body, while `shop` is read from the unauthenticated `x-shopify-shop-domain` header. `Registry.process` validates the HMAC over the body only, then blindly trusts `request.shop` to build the `WebhookMetadata` passed to the host app's handler, breaking the identity binding between "shop whose signature was verified" and "shop the handler is told the data belongs to."

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

The `shop` accessor, however, is derived directly from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never mixed into the signed payload: [3](#0-2) 

`Registry.process` validates the HMAC and then, without any further check that the `shop` header corresponds to the entity that actually produced/authorized the signed body, forwards `request.shop` straight into `WebhookMetadata` given to the application-supplied handler: [4](#0-3) 

The equality that should hold is: `shop the HMAC authenticates == shop the handler is told the payload belongs to`. Because the header is outside the signed bytes, an attacker who possesses any one valid `(raw_body, hmac)` pair (e.g., from their own shop's legitimately-received webhook, since webhook bodies/HMACs are not bound to a specific recipient endpoint or nonce beyond the topic/shop headers) can replay that exact body+HMAC while substituting a different `x-shopify-shop-domain` header value. `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload is for the attacker-chosen shop.

### Impact Explanation
Any host application that uses `data.shop` from `WebhookMetadata` to select which tenant/shop record to update (a documented and expected use of the field) can be made to attribute attacker-controlled webhook content to a different shop than the one that actually authorized it. This is a cross-tenant identity-binding bypass: the signature proves the bytes are unmodified from *some* valid Shopify-originated webhook, but not that they belong to the shop named in the header used for routing/attribution. This matches the Critical "cross-tenant access" impact category, since the attacker can inject data into or trigger tenant-scoped side effects for a victim shop's session using their own signed webhook body.

### Likelihood Explanation
This requires only unprivileged access to at least one valid `(raw_body, hmac)` pair Shopify sent for the attacker's own shop (or any other webhook the attacker can trigger/receive), plus the ability to replay a crafted HTTP POST to the app's webhook endpoint with a modified `shop-domain` header — no access token, `client_secret`, or privileged account is required. The only "unlikely condition" is that the host app must key tenant logic off `data.shop`, which is exactly what the field is documented/intended for.

### Recommendation
Bind the `shop` field into the signed material, or otherwise verify it out-of-band (e.g., compare the header value against a shop already associated with a known, previously-registered webhook subscription/session before trusting it), so that `HmacValidator.validate` fails whenever the `shop-domain` header does not match the shop that actually produced the signed body. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant routing without independent verification.

### Proof of Concept
1. Attacker owns/controls "attacker-shop.myshopify.com" and receives a legitimately signed webhook from Shopify: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B`), `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker sends `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com", "x-shopify-hmac-sha256" => H, ...})` to the app's webhook endpoint.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — validation passes. [5](#0-4) 
4. `handler.handle` is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though the signed body `B` never belonged to "victim-shop". [6](#0-5)
