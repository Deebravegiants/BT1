### Title
Webhook `shop-domain` header is not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, never including the `shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` validates only that HMAC and then unconditionally trusts `request.shop` as the authenticated tenant identifier delivered to the app's handler.

### Finding Description
`Request#to_signable_string` returns `@raw_body` exclusively: [3](#0-2)  while `Request#shop` is read straight from an attacker-controllable HTTP header with no cryptographic binding: [4](#0-3) .

`Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `to_signable_string` (the body) using the app's `client_secret` and compares it to the `hmac-sha256` header — the shop header plays no part in that computation, per `HmacValidator.validate_signature`: [5](#0-4) . Once validated, `request.shop` is forwarded, unauthenticated, straight into `WebhookMetadata` handed to the app's handler: [2](#0-1) .

This is the same bug class as the reference report: a value (`quotingToken`/here, `shop`) that is *used* to drive downstream tenant-scoped logic is not the value that the cryptographic check actually *covers* (`asset`/here, `raw_body`). The binding that should hold is:
`HMAC-verified(shop, body) == (shop, body) acted upon`
but the gem only enforces `HMAC-verified(body) == body acted upon`, while `shop` is taken from unauthenticated bytes.

Since the app's own `client_secret` is shared across every shop installed on the app (Shopify signs all webhooks for an app with the same secret, not a per-shop key), any merchant who installs the app and receives a single genuine webhook obtains a body+HMAC pair that is valid regardless of which shop domain header accompanies it. That merchant (an "unprivileged" actor relative to any other tenant of the same app) can then replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still returns `true` because the shop header was never part of the signed content, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated from the victim shop.

### Impact Explanation
This breaks the tenant-authentication boundary the gem is expected to provide to host applications: `data.shop` in a webhook handler is the only tenant signal the gem gives after "verifying" the request, but it carries no integrity guarantee. Any host application that uses `WebhookMetadata#shop` to decide which tenant's data to mutate, which stored access token to use for follow-up API calls, or which tenant-scoped queue/table to write into can be tricked into cross-tenant actions using attacker-supplied shop values, which is a cross-tenant access impact.

### Likelihood Explanation
Likelihood is high for any merchant/attacker who has installed the app at least once (a normal, unprivileged flow) — no leaked secrets or privileged accounts are required, only capturing one legitimately delivered webhook (trivial, since it's delivered to their own configured endpoint) and replaying it with a modified header, which any internet client can do since the HMAC never covers the header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) in the value that `Utils::HmacValidator` verifies, or otherwise cryptographically bind the tenant identity — e.g. by having `Request#to_signable_string` concatenate the shop header with the raw body, or by separately validating that the shop header matches a value derivable from the signed payload — before `Registry.process` propagates `request.shop` to handlers.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and configures the webhook endpoint normally.
2. Shopify delivers a genuine webhook: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` with the app's `client_secret`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays the exact same request to the app's webhook endpoint, but changes only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes the HMAC of `B` (unchanged) and confirms it matches `H` — validation passes, per `HmacValidator.validate_signature`.
5. `Registry.process` invokes the registered handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, letting the attacker inject a forged webhook attributed to a shop they do not control.
