This confirms the vulnerable pattern: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated HTTP headers [2](#0-1) . `Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop` (and `request.topic`) to construct the `WebhookMetadata` passed to the handler [3](#0-2) .

### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw request body only. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that identify *which merchant and event* the payload belongs to are read straight from HTTP headers and are never included in the signed material. Any party who can obtain one valid `(body, hmac)` pair signed with the app's shared `api_secret_key` — for example a merchant receiving genuine webhooks for their own store — can replay that exact body/HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header, and the signature will still validate.

### Finding Description
`Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string` to build the string that is HMAC'd and compared against the received signature [4](#0-3) . For webhooks, `Request#to_signable_string` returns `@raw_body` exclusively [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read straight from the (unsigned) `shopify-*`/`x-shopify-*` headers [2](#0-1) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` — i.e., that the body's HMAC matches the app's secret — and then dispatches to the topic's handler using `request.shop` as the tenant identity, with no additional binding between the authenticated bytes (body) and the header-derived shop/topic [3](#0-2) .

This breaks the identity binding: **bytes verified (body) ≠ bytes used to determine tenant/topic (headers)**. Since the app's `api_secret_key` is shared across *all* merchant shops using the app (a single client secret signs every shop's webhooks), any unprivileged user who is themselves a merchant with the app installed can capture a legitimately-signed webhook body+HMAC from their own store's traffic and re-POST it to the app's webhook endpoint with a forged `shopify-shop-domain` header naming a different (victim) shop and/or a different `shopify-topic`. The HMAC check in `Registry.process` still passes because it only re-validates the body against the secret, never that the body's actual content matches the claimed shop/topic in the headers.

### Impact Explanation
This qualifies as a Critical cross-tenant access issue: an unprivileged internet user (any merchant with the app installed) can cause the host application to process attacker-supplied, mislabeled webhook data attributed to an arbitrary victim shop. If the host app's webhook handlers key their tenant/session lookups off `WebhookMetadata#shop` (as documented and expected — see `Registry.process` passing `shop: request.shop` directly to the handler [5](#0-4) ), this can lead to writing/deleting/mutating data under the wrong tenant's record, or the reprocessing of a benign event as a spoofed mandatory-compliance webhook (e.g. `shop/redact`, `customers/redact`, `customers/data_request`) for a different shop, since these mandatory topics are also dispatched via the same `process` path without further binding checks [6](#0-5) .

### Likelihood Explanation
Requires only that the attacker (1) be a legitimate but unprivileged user of the app on their own shop (able to see legitimate webhook bodies/HMACs sent to their own endpoint or capture them in transit to their own infra), and (2) know/guess a valid replacement `shop-domain`/`webhook-id` header value for the target tenant. No access to `api_secret_key`, tokens, or the target's credentials is needed — the attacker reuses a genuine signature computed by Shopify with the app's shared secret over content they legitimately received. This is fully reachable through documented gem behavior (`Webhooks::Registry.process`), not something requiring the host app to misuse the library.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, and ideally `webhook_id`) in the signable string used for HMAC verification, or validate that these header values are consistent with data embedded in the body (many Shopify webhook payloads include a `myshopify_domain`)/otherwise establish a binding so that the authenticated bytes and the values used to route/attribute the event are the same. At minimum, document that `Registry.process` consumers must not trust `WebhookMetadata#shop`/`#topic` without an additional binding check.

### Proof of Concept
1. Attacker installs the target app on their own shop, `attacker-shop.myshopify.com`, and receives a legitimate webhook delivery, e.g. `orders/create` with body `B` and header `Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker POSTs to the app's public webhook endpoint (backed by `ShopifyAPI::Webhooks::Registry.process`) reusing body `B` and header `Shopify-Hmac-Sha256: H`, but sets `Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `Request#hmac` decodes `H`; `Utils::HmacValidator.validate` recomputes HMAC over `to_signable_string` (`B` only) and it matches, so `Registry.process` proceeds [7](#0-6) .
4. The registered handler for `orders/create` receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and the attacker-originated body, even though `victim-shop` never sent this webhook [5](#0-4) .
