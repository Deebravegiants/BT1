This confirms the vulnerability: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0)  while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers [2](#0-1) . `HmacValidator.validate` / `validate_signature` only checks `verifiable_query.hmac` against `to_signable_string` (the body), never binding the `shop` header into the signature [3](#0-2) . `Registry.process` then trusts `request.shop` directly and hands it to the app's handler as the tenant identifier after only checking the HMAC over the body [4](#0-3) , and the gem's own documentation instructs apps to use `data.shop` as the tenant/shop-domain key for downstream storage/queuing [5](#0-4) .

### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header is not covered by the HMAC signature, allowing cross-tenant shop-attribution of a validly-signed webhook body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from only the raw request body [1](#0-0) , while the `shop` field that `Registry.process` treats as the authenticated tenant identifier is read from an ordinary HTTP header that plays no part in the signature [6](#0-5) . This breaks the intended identity binding `shop that produced the HMAC == shop attributed to the payload by the handler`.

### Finding Description
`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header using `OpenSSL.secure_compare` [3](#0-2) . For webhooks, `to_signable_string` is simply `@raw_body` [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values used by the rest of the gem come from `shopify_header(...)` lookups on the raw headers hash, which is not authenticated in any way [2](#0-1) .

`Registry.process` validates only the body HMAC, then immediately builds `WebhookMetadata` from the unauthenticated `request.shop`, `request.topic`, `request.webhook_id`, and hands it to the app's handler [4](#0-3) . The gem's documentation explicitly tells integrators to key downstream work off `data.shop` (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) [5](#0-4) , i.e., the header value is trusted as the tenant key even though it was never part of what the HMAC covers.

Because the signature is computed over the body only, an unprivileged actor who controls (or previously received, e.g. via their own merchant shop) one validly-signed webhook body can resend it to the app's shared webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to point at a *different* shop, and `HmacValidator.validate` will still return `true`, since it never inspects the header. The app then processes the (attacker-chosen) body under the wrong tenant's identity.

### Impact Explanation
This crosses a tenant boundary in a multi-tenant app: any host application that follows this gem's own documented pattern of trusting `WebhookMetadata#shop` for tenant scoping (session/store lookup, data attribution, job queuing per shop) can be made to process a foreign-but-HMAC-valid payload as if it belonged to a different, victim shop, because the identity binding `shop-domain header == HMAC-signed content` does not hold. This is a cross-tenant access issue rooted entirely in this gem's `Request`/`HmacValidator`/`Registry` implementation, not in host misuse of an undocumented API.

### Likelihood Explanation
Exploitation requires only: (1) the attacker's own shop or any source of one legitimately-HMAC'd webhook body (attainable by any developer who installs their own instance of a Shopify app, or by intercepting/replaying a delivery), and (2) the ability to POST to the shared webhook endpoint with a modified `shop-domain` header — no `api_secret_key`, access token, or privileged account needed. Given that the header manipulation costs nothing extra once a valid body/HMAC pair is obtained, likelihood is not negligible for apps that serve multiple shops on one webhook route (the standard multi-tenant SaaS pattern this gem targets).

### Recommendation
Include the security-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable content, or otherwise cryptographically bind them (e.g., derive/verify `shop` against a value embedded in the signed body, or maintain a registry-side allow-list keyed by verified shop rather than trusting the header). At minimum, document that `shop` (and other headers) are unauthenticated and must not be used as a sole tenant-scoping key without additional server-side verification (e.g., cross-checking against the shop that the webhook was registered for/known access-token store).

### Proof of Concept
1. App is installed on `shop-a.myshopify.com` (attacker-controlled) and `shop-b.myshopify.com` (victim), both delivering webhooks to the same `/webhook` endpoint in a multi-tenant host app.
2. Attacker triggers a webhook on their own shop `shop-a`, capturing the raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` with the app's shared `api_secret_key`, which the attacker never needs to know).
3. Attacker replays the request to the host's webhook endpoint, keeping body `B` and header `H` unchanged, but sets `x-shopify-shop-domain: shop-b.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which validates `H` against `to_signable_string == B` only [7](#0-6)  — validation passes because the header change is irrelevant to the signature.
5. `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` is built with `shop == "shop-b.myshopify.com"` [8](#0-7) , and the host's handler processes attacker-supplied content `B` under victim shop `shop-b`'s identity, per the gem's documented handler pattern [9](#0-8) .
