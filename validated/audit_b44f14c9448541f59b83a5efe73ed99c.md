Interesting candidate: `evm/src/apps/intentsv2/ExtrinsicIntents.sol` `onAccept()` reads `incoming.request.body[0]` and slices `body[1:]` without checking `body.length > 0` first.## Finding: Unchecked index/length access on attacker-controlled cross-chain message body in `ExtrinsicIntents.onAccept`

### Title
Out-of-bounds index panic on empty POST request body in `onAccept` — analog of CVE-2019-3861's unchecked length/padding read — (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents.onAccept()` reads the discriminator byte of an incoming cross-chain message with `uint8(incoming.request.body[0])` and then slices `incoming.request.body[1:]` before performing *any* length validation or sender authentication [1](#0-0) . The equivalent pattern also appears in `onGetResponse()`, which indexes `incoming.response.values[0]` without checking the array is non-empty [2](#0-1) . This is the same bug class as ALPINE-CVE-2019-3861: a length-derived field (here, the array length backing `body`/`values`) is trusted implicitly by an indexing/slicing operation before the code validates that the buffer is long enough to contain it.

### Finding Description
`onAccept` is the `IApp` callback the `IHost`/`HandlerV2` dispatch path invokes for every POST request whose `dest` resolves to this module, once a state-membership proof over the source state machine has verified inclusion of the request [3](#0-2) . Dispatching a POST request is permissionless from any application module on any registered source state machine — nothing gates the shape of `body` before it reaches `onAccept`. The function immediately executes:

```solidity
RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
```

with no `require(incoming.request.body.length > 0)` guard. In Solidity ^0.8, an out-of-range array index reverts with a `Panic(0x32)` (array/slice out-of-bounds) rather than reading adjacent memory — the memory-safety guarantee is the compiler's, not the contract's. Critically, `_authenticate(incoming.request)` (the check that the sender module matches the registered gateway instance for the source chain) only runs *after* this unchecked read, for the `RedeemEscrow`/`RefundEscrow` branches [4](#0-3) . So the panic is reachable by *any* unauthenticated module dispatching a POST request with `dest` set to this contract and an empty (zero-length) `body` — no relationship to the registered gateway instance is required to trigger it.

`handlePostRequests` (`HandlerV2.sol`) verifies a Merkle multi-proof over a *batch* of leaves and, after the proof check, calls `host.dispatchIncoming(leaf.request, _msgSender())` in a loop for every leaf in that batch [5](#0-4) . If `dispatchIncoming` does not itself trap/catch the callee's revert (this repository snapshot did not surface the `EvmHost.dispatchIncoming` implementation to confirm either way), an attacker-crafted zero-length-body request colocated in the same batch as legitimate messages would cause the *entire* `handlePostRequests` transaction to revert, denying delivery of every other request bundled in that proof — a "route unable to deliver messages" condition triggerable by a single unprivileged dispatch from any source-chain module.

### Impact Explanation
At minimum this is a guaranteed, unauthenticated revert-DoS against a single delivery attempt to `ExtrinsicIntents` (any dispatcher can force `onAccept`/`onGetResponse` to panic by sending an empty body/empty values array). If `dispatchIncoming` propagates reverts rather than isolating them per-leaf (unverified in this pass), the same primitive escalates to blocking co-batched legitimate intent settlements (redemptions/refunds) from being delivered at all, i.e., a message-delivery-route denial — one of the explicitly in-scope impact categories.

### Likelihood Explanation
High for the isolated-DoS case: dispatching a POST request with an empty body to an arbitrary `dest` is a normal, permissionless operation available to any application on any connected state machine, requiring no privileged role, no compromised key, and no governance action. The batch-wide escalation's likelihood depends on `dispatchIncoming`'s error-handling semantics, which could not be confirmed in this pass.

### Recommendation
Add explicit length checks before indexing/slicing attacker-supplied variable-length buffers in `onAccept` and `onGetResponse`:
```solidity
if (incoming.request.body.length == 0) revert InvalidInput();
...
if (incoming.response.values.length == 0) revert InvalidInput();
```
and move `_authenticate` (or an equivalent length/sender check) ahead of any indexing operation. Additionally, verify that `EvmHost.dispatchIncoming` isolates each leaf's callback failure (e.g. via try/catch) so a single malformed/malicious message cannot revert an entire batched delivery.

### Proof of Concept
1. Any application module on a connected source state machine calls `IDispatcher(host).dispatch` with `dest` set to the `ExtrinsicIntents` contract address and `body = ""` (zero length), `from` set to anything (authentication is never reached).
2. Once Hyperbridge finalizes/proves this request, a relayer calls `HandlerV2.handlePostRequests` including this leaf (optionally batched with legitimate `RedeemEscrow`/`RefundEscrow` leaves for the same destination).
3. `host.dispatchIncoming` invokes `ExtrinsicIntents.onAccept(incoming)`; `uint8(incoming.request.body[0])` reverts with `Panic(0x32)`.
4. If `dispatchIncoming` does not catch this, the whole `handlePostRequests` call reverts, and none of the batched leaves (including legitimate ones) are delivered, marked, or receipted — the relayer must resubmit without the poisoned leaf, and the attacker can repeat this against every batch it can insert itself into.

**Note on completeness:** I was unable to locate/verify the `EvmHost.dispatchIncoming` implementation in this pass to confirm whether it isolates per-leaf reverts. That determines whether the impact is limited to a single failed delivery (still a valid but lower-severity finding) or escalates to blocking co-batched deliveries. This should be checked directly against `evm/src/host/EvmHost.sol` (or equivalent) before finalizing severity.
