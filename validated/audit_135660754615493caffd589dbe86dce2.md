## Analog Found

### Title
Single authorized-relayer gate on `IntentGatewayV2.onAccept`/`onGetResponse` can permanently freeze all escrowed order funds - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
The Infinex report shows that gating a fund-recovery action behind a single administrator-controlled signer, with no fallback path, lets that signer permanently block users from withdrawing their own funds. Hyperbridge's `IntentGatewayV2` has the same structural flaw: once armed, `onAccept` and `onGetResponse` — the only entry points that release escrowed order funds (fills, refunds, cancellations) and the only entry point that can *change* the authorized relayer — accept delivery from exactly one `_relayer` address, with no alternate path to update it.

### Finding Description
`ExtrinsicIntents._checkRelayer` runs before any message body is decoded and reverts for every caller except the currently stored `_relayer`: [1](#0-0) 

This check gates *every* `onAccept`/`onGetResponse` delivery, including ordinary escrow redemptions, refunds, and — critically — the governance `Execute` request that calls `setRelayer` to rotate the relayer itself: [2](#0-1) 

`setRelayer` is only reachable through an `Execute` post request delegatecalled from `onAccept` (`onlyHost`), and that `onAccept` call is itself subject to `_checkRelayer`: [3](#0-2) [4](#0-3) 

Consequently, once a `_relayer` is armed, the *only* account whose message delivery the contract will ever accept — for both user withdrawals and for changing the relayer itself — is that one address. There is no timeout, no fallback relayer, and no alternate authority (not even the host or governance) that can force a delivery through a different relayer. Test coverage confirms this behavior is by design and unconditional: any other relayer's delivery reverts and the escrow/refund/upgrade stays undelivered. [5](#0-4) [6](#0-5) 

If the sole authorized relayer becomes unavailable — key loss, operator shutdown, seizure/compulsion, or simple refusal to cooperate — there is no way for the protocol, governance, or users to recover: escrowed inputs from every pending cross-chain order (fills awaiting settlement, refunds, cancellations) are stuck forever, and the relayer itself cannot be rotated because rotating it requires a delivery from the very relayer that is unavailable.

### Impact Explanation
This is a permanent freeze of user funds reachable from an ordinary, unprivileged path: any user who places a cross-chain order via `placeOrder` has their input tokens escrowed pending a `WithdrawalRequest`/refund message delivered through `onAccept`. If the single authorized relayer withholds or is unable to submit that delivery, the escrowed funds for that order — and every other order on the gateway — become permanently unrecoverable, since no other account can substitute for the missing relayer, matching the "permanent freezing of funds" / "route unable to deliver messages" impact class.

### Likelihood Explanation
The relayer-allowlist gate is intentionally armed via governance (`setRelayer`/`migrate`) as the documented production configuration, so any live gateway that arms this gate is subject to the single-point-of-failure risk described above. The trigger condition — the designated relayer becoming unavailable or unwilling to relay — does not require any malicious action by governance or the admin; ordinary relayer downtime, key compromise, or infrastructure failure is sufficient, and the contract provides no self-recovery mechanism once armed.

### Recommendation
Add a fallback path that does not depend exclusively on the currently authorized relayer, e.g.: (1) allow the host/governance to rotate `_relayer` directly (bypassing `_checkRelayer`) rather than only through a message that must itself pass the same gate, or (2) add a timeout after which any relayer's delivery is accepted if the authorized relayer has not delivered within a bounded window, ensuring escrowed funds and the relayer configuration can always be recovered.

### Proof of Concept
1. Governance arms the gate via `migrate`/`setRelayer(next)`, authorizing relayer `R`.
2. A user calls `placeOrder`, escrowing input tokens in `IntentGatewayV2`.
3. A solver fills the order on the destination chain and the settlement/refund `PostRequest` is dispatched back to the source gateway.
4. Relayer `R` becomes unavailable (offline, compromised, or refuses to submit) and never calls `HandlerV2.handlePostRequests` for this message.
5. As shown by `testOnAcceptRejectsUnlistedRelayer` ( [5](#0-4) ), any other relayer's attempt to deliver the same message reverts with `Unauthorized`, leaving escrow untouched and the order unfinalized indefinitely — with no path to rotate `R` since `setRelayer` itself requires delivery through `R`.

     * @dev Once a relayer is set, rejects deliveries from anyone else before the body is read. The
     * host records the revert as undelivered, so the authorised relayer can resubmit. While unset,
     * every delivery passes: a proxy from before the gate stays open until `migrate` arms it.
     * @param relayer The account that submitted the message to the handler.
     */
    function _checkRelayer(address relayer) internal view {
        address authorised = _relayer;
        if (authorised != address(0) && relayer != authorised) revert Unauthorized();
    }
