## Analysis

The reported bug class — a value that changes application state while bypassing an integrity check bound to a *different* field — maps cleanly onto how this gem processes inbound Shopify webhooks. The webhook HMAC covers only the raw request body, while the `shop` identity used to route webhook data is taken from an unauthenticated HTTP header that the HMAC never signs.

### Root cause

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` is read from the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` only ever checks `verifiable_query.to_signable_string` against `verifiable_query.hmac` — i.e., body vs. body-signature: [2](#0-1) 

`Registry.process` validates that HMAC, then immediately trusts `request.shop` — sourced from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is **not** part of `to_signable_string` — to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) [4](#0-3) 

### Equality that should hold but doesn't

`shop` (bound by HMAC) should equal `shop` (used by the handler for tenant identification). In reality: `HMAC(secret, raw_body)` only binds `raw_body`; `shop-domain` header is a completely independent, unauthenticated field. Any request with a *body* that has a valid HMAC for the app's `client_secret` will pass `Registry.process`'s check regardless of what `shop-domain` header accompanies it.

### Why this is exploitable without the app's secret

The webhook-signing `client_secret` is the same for every shop that installs a given app — it is not shop-specific. An attacker can install the target app on their own (e.g., free development) store, trigger any webhook topic they like (e.g. `customers/create`), and legitimately receive a body + HMAC pair signed by the real Shopify servers using the app's `client_secret`. This raw body/HMAC pair is valid for *any* shop, because the signature never included the shop identity. The attacker then replays that exact `(raw_body, hmac)` to the app's public webhook endpoint while substituting `shopify-shop-domain: victim-shop.myshopify.com`. `Registry.process` still passes the HMAC check (only the body is checked) and dispatches to the handler with `shop: "victim-shop.myshopify.com"`, causing the app's webhook handler to act on/attribute attacker-controlled body content to the victim tenant — a cross-tenant identity break analogous to the reported "empty trade" flaw, where an unchecked field is used to move state despite a check that only covers a different field.

### Title
Webhook `shop-domain` identity is not bound by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating an HMAC over the raw request body via `ShopifyAPI::Utils::HmacValidator`, then trusts the `shopify-shop-domain` header — which is entirely outside the signed content — as the tenant identity forwarded to the app's handler.

### Finding Description
`Request#to_signable_string` returns `@raw_body` only, and `#hmac` and `#shop` are both read straight from HTTP headers with no cryptographic linkage between them. Since an app's webhook `client_secret` is shared across all shops that install the app, any store owner (including a free/dev store) can generate a genuinely-signed `(raw_body, hmac)` pair for arbitrary webhook content, then replay it to the app's public webhook endpoint with a forged `shopify-shop-domain` header pointing at a different, victim shop. `Registry.process` will accept it because `Utils::HmacValidator.validate` never inspects the shop header, and will invoke the registered handler with `WebhookMetadata#shop` set to the victim's domain. [3](#0-2) 

### Impact Explanation
The handler-supplied `shop` value is the primary tenant key most host apps use to fetch the victim's stored session/access token or write data scoped to that shop. Spoofing it lets an attacker inject attacker-chosen webhook content attributed to an arbitrary victim tenant, achieving cross-tenant data confusion/injection without ever needing the app's `client_secret`, access token, or any credential belonging to the victim.

### Likelihood Explanation
Exploitation only requires the ability to install the target app on any store (including a free development store) to legitimately obtain a valid `(body, hmac)` pair, then send a crafted HTTP request with a substituted `shop-domain` header to the app's known public webhook endpoint. No secrets, tokens, or privileged access to the victim are needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable content, or otherwise cryptographically bind the `shopify-shop-domain` header to the signature (e.g., verify it separately against a shop-webhook-secret, or require the caller to supply the expected shop and compare it against a lookup keyed by a value that *is* covered by the signature) before trusting it as the tenant identity passed to `WebhookMetadata`.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled store (`attacker-shop.myshopify.com`).
2. Trigger any subscribed webhook topic (e.g., update a product) so Shopify sends a webhook to the app's endpoint with a real `x-shopify-hmac-sha256` computed over the raw body using the app's `client_secret`.
3. Capture the raw body and HMAC header from this legitimate request (e.g., via a temporary logging endpoint or debug proxy under attacker's control).
4. Replay this exact `(raw_body, hmac)` pair as a new POST request to the app's public webhook endpoint, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against the HMAC and succeeds; it then invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the app to process attacker-controlled data as belonging to the victim tenant.
