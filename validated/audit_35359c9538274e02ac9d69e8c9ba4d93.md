## Title
Incorrect decimal scaling in `pallet-hyper-fungible-token` produces unbacked cross-chain mint when a registered asset's local decimals exceed the destination ERC20 decimals - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The external report describes a HoneyFactoryReader bug where a redundant decimal round-trip (18 → asset decimals → 18) truncates amounts to zero because integer division discards precision when the destination has fewer decimal places. The same underlying bug class — a decimal-scaling helper that behaves correctly only when the target has *more* decimals than the source, and silently degenerates into a no-op instead of scaling down when the target has *fewer* decimals — exists in `pallet-hyper-fungible-token`'s cross-chain amount conversion helpers.

### Finding Description
`convert_to_erc20` and `convert_to_balance` in `modules/pallets/hyper-fungible-token/src/impls.rs` are used to translate a local substrate balance into the ERC20-precision `U256` amount embedded in the outbound ISMP message (and vice versa on receipt): [1](#0-0) 

Both functions use `erc_decimals.saturating_sub(local_decimals)` as the scaling exponent:
- `convert_to_erc20` multiplies by `10^(erc_decimals - local_decimals)` — correct only when `erc_decimals >= local_decimals`. When `erc_decimals < local_decimals`, `saturating_sub` returns `0`, so the exponent becomes `10^0 = 1` and **no down-scaling is applied at all** — the raw, higher-precision local amount is passed through unchanged as if it were already in the (lower-precision) ERC20 scale.
- `convert_to_balance` divides by `10^(erc_decimals - local_decimals)` — correct only when `erc_decimals >= local_decimals`. When `erc_decimals < local_decimals` the same `saturating_sub` collapse occurs and **no up-scaling happens**, silently under-crediting the recipient.

This is called directly from the unprivileged `send` extrinsic: [2](#0-1) 

and from the `on_accept`/`on_timeout` handlers of the `IsmpModule` implementation: [3](#0-2) 

The pallet's own documentation states this conversion must work symmetrically for "10-decimal DOT on Polkadot vs 18-decimal DOT on Ethereum" style mismatches in either direction, and the `precision`/`Precisions` field is fully generic (`u8` per chain, set by `register_token`/`update_token`): [4](#0-3) 

The existing unit tests only exercise the `erc_decimals(18) > local_decimals(10)` direction: [5](#0-4) 

The opposite, equally valid configuration (a local asset registered with more decimals than its EVM counterpart, e.g. an 18-decimal local asset wrapping a 6-decimal ERC20 like USDC) is never tested and is silently broken.

### Impact Explanation
When a token is registered (via `register_token`/`update_token`, a normal non-malicious admin action reflecting a legitimate decimal mismatch) with `erc_decimals < local_decimals`:
- Any unprivileged user calling `send()` has their locked/burned local amount (in the higher local-decimal precision) forwarded **unscaled** as the ERC20 `amount` field of the outbound `Message`. The destination `HyperFungibleToken`/`WrappedHyperFungibleToken` contract will mint that raw number of tokens at its own (lower) decimal precision, inflating the minted amount by `10^(local_decimals - erc_decimals)` — an unbacked mint that lets an attacker drain the destination contract's token supply/liquidity by burning a tiny amount of the source asset.
- Symmetrically, `on_accept`/`on_timeout` under-credit local balances on the receiving side (fund loss for legitimate bridge users), since the ERC20 amount is never scaled up to the local asset's higher decimal precision.

This is a Medium/High severity issue: it can produce an unbacked mint of a bridged asset from a single unprivileged `send` extrinsic call whenever an asset is registered with this (valid, expected-to-be-supported) decimal configuration.

### Likelihood Explanation
Reachable by any signed account via the public `send` extrinsic — no privileged role is required to trigger the mis-scaling once an asset with `erc_decimals < local_decimals` exists in `Precisions`. Registering assets with differing/mismatched decimal counts across chains is an ordinary, documented, expected pallet operation (not a malicious-admin scenario), so this configuration is plausible for any asset whose local representation intentionally uses more decimal places than its EVM counterpart (e.g., wrapping a 6-decimal stablecoin as an 18-decimal local asset).

### Recommendation
Fix `convert_to_erc20` and `convert_to_balance` to scale in both directions correctly, e.g.:
```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```
and the mirror fix for `convert_to_balance`. Add tests covering both `erc_decimals > local_decimals` and `erc_decimals < local_decimals` cases.

### Proof of Concept
1. Register an asset via `register_token` with `local_decimals = 18` (e.g. a substrate `pallet-assets` token minted with 18 decimal places) and `Precisions::<T>::insert(asset_id, dest_chain, 6)` (destination ERC20 uses 6 decimals) — an ordinary, valid registration.
2. Call `send(origin, SendParams { asset_id, amount: 1_000_000_000_000_000_000 /* 1 token, 18 decimals */, destination: dest_chain, .. })` from any signed account. This burns/escrows 1 local token.
3. Inside `send`, `erc_decimals(6).saturating_sub(local_decimals(18)) == 0`, so `convert_to_erc20` returns `amount * 10^0 = 1_000_000_000_000_000_000` unchanged, instead of the correct `1_000_000` (1 token at 6 decimals).
4. The outbound `Message.amount` therefore encodes `1_000_000_000_000_000_000` raw units, which the destination `HyperFungibleToken` contract (expecting 6-decimal precision) will mint as `1_000_000_000_000` tokens (a 10^12 inflation) for burning a single local token — an unbacked mint reachable from one unprivileged `send` call.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
