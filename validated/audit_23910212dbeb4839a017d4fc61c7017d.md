### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unauthenticated headers while only the raw body is HMAC-covered, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` only ever authenticates the request body. The `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from HTTP headers (`shopify_header`) that are never included in the signable string and therefore never covered by the HMAC check.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` does: [1](#0-0) 
It calls `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`: [2](#0-1) 
That signable string is `@raw_body` only — it excludes `shop`, `topic`, and `webhook_id`, which are all sourced from attacker-controllable HTTP headers: [3](#0-2) 
and [4](#0-3) 

This breaks the intended identity binding `hmac-authenticated-bytes == bytes-used-for-tenant-attribution`. Concretely: `hmac(raw_body) == hmac(raw_body)` holds while `shop-domain-header(authenticated shop A) != shop-domain-header(claimed shop, attacker-supplied)`. The final dispatch trusts the header-derived `shop` for tenant attribution without it ever being covered by the signature: [1](#0-0) 

Because a merchant/app-installer (an "unprivileged internet user" relative to other tenants, but a legitimate owner of their own shop and its webhook secret-derived signatures for their own payloads) can capture a valid `(raw_body, hmac)` pair generated for their own shop's webhook delivery (the HMAC secret is the shared app `client_secret`, so any shop under the same app produces a validly-signed body), they can replay that same body+HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a different shop. `Utils::HmacValidator.validate` will still return `true` because it only checks the body bytes, not the header claiming which shop/topic they belong to.

### Impact Explanation
The webhook handler receives `WebhookMetadata` built directly from the unverified header value: [5](#0-4) 
Any host application that uses `data.shop` from this metadata to look up sessions, attribute webhook effects, or gate per-tenant logic (a normal integration pattern, and the one implied by this gem's own `WebhookMetadata.shop` field) will process attacker-chosen tenant data as if it came from a different, victim shop — a cross-tenant confusion enabled entirely inside this gem's HMAC validation logic, since the gem asserts the request is "verified" via `HmacValidator.validate` while leaving the shop/topic/webhook_id claims completely unauthenticated.

### Likelihood Explanation
Exploitation requires only that the attacker control a shop that has the target app installed (or capture one legitimate webhook delivery, since delivered webhook bodies for many topics are static/predictable or replayable), then perform a normal HTTP POST to the app's public webhook endpoint with swapped headers. No access token, `client_secret`, or privileged credential is needed — the HMAC computed by Shopify on the attacker's own legitimate webhook body remains valid regardless of which shop-domain header value is sent, since headers are outside the signed payload.

### Recommendation
Include the authenticated header values (`shop`, `topic`, `webhook_id`, `api_version`) in the value that is cryptographically bound to the HMAC check, or otherwise cross-validate them against a resolved, trusted record of the source shop before attribution/dispatch. At minimum, the gem should not present webhook `shop`/`topic` as validated fields once `HmacValidator.validate` returns true, since only the body is actually covered.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers/receives a legitimate webhook (e.g. `orders/create`) with raw body `B` and valid header `X-Shopify-Hmac-Sha256: H` (where `H = HMAC-SHA256(client_secret, B)`).
2. Attacker replays the exact same `(B, H)` to the target app's public webhook endpoint, but sets:
   - `X-Shopify-Shop-Domain: victim.myshopify.com`
   - `X-Shopify-Topic: orders/create`
   - `X-Shopify-Webhook-Id: <any>`
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...})` is constructed; `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and matches `H`, returning `true`. [6](#0-5) 
4. `Registry.process` proceeds and calls the app's handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed_body, ...)`, even though the body/data actually originated from the attacker's own shop. [5](#0-4) 

**Uncertainty note**: This analysis is based on the gem's webhook-processing code path (`lib/shopify_api/webhooks/**`); I did not find any additional server-side binding (e.g., IP allowlisting, mutual TLS, or shop-domain-in-signature) elsewhere in the in-scope library code that would close this gap. If such a control exists outside the indexed files, it was not visible to this search.
