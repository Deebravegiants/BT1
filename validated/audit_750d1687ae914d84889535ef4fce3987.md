### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by HMAC verification, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify," but the HMAC check only authenticates the raw request body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` values that are handed to the app's webhook handler as trusted identity/context are taken straight from unauthenticated HTTP headers, breaking the intended binding between "HMAC-verified sender" and "shop the payload is attributed to."

### Finding Description
`Registry.process` performs a single authenticity check: [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature only from `request.to_signable_string`: [2](#0-1) 

And `Webhooks::Request#to_signable_string` returns only the raw body — the `shop`, `topic`, `webhook_id`, and `api_version` accessors are all read directly from HTTP headers that are **not** part of the signed material: [3](#0-2) 

After the HMAC check passes, `Registry.process` builds the handler payload directly from these unauthenticated header values: [4](#0-3) 

The documented contract explicitly tells app developers to trust `data.shop` as "The shop domain of the webhook" once `process` succeeds: [5](#0-4) [6](#0-5) 

The identity binding the gem's own API promises — `hmac_verified(body) == shop_the_body_is_attributed_to` — does not hold, because the HMAC secret (`Context.api_secret_key`) is the app's single client secret shared across **every shop that installs the app**, not a per-shop secret. Any shop that installs the app can trigger an event, capture the resulting valid `(raw_body, hmac)` pair signed with the shared secret, and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header for a different, victim shop domain. `HmacValidator.validate` still succeeds because it never inspects those headers, and `Registry.process` forwards the attacker-chosen `shop` string straight into `WebhookMetadata` as if it were verified.

### Impact Explanation
This crosses a tenant boundary: an unprivileged merchant with their own valid app installation can cause the app to process webhook data while impersonating an arbitrary other shop domain, since the "verified" `shop` field handed to the handler is fully attacker-controlled while the HMAC still validates. Any app that keys per-tenant state, database writes, billing, or authorization decisions off `data.shop` (exactly as the documentation instructs) is exposed to cross-tenant data injection/corruption. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that follows this gem's documented webhook pattern verbatim: any shop can install the app (no special privilege needed), trigger one webhook-eligible event to obtain a validly-signed body, and replay it with modified shop/topic headers to the app's public webhook endpoint. No access token, client secret, or other credential of the victim is required — only the shared `api_secret_key`'s HMAC over attacker-controlled body content that the attacker legitimately obtained for their own shop.

### Recommendation
Extend the webhook signable string (or an additional server-side check) to bind the authenticated headers (`shop-domain`, `topic`, `webhook-id`) into the HMAC-verified material, or independently verify `shop` against the session/shop record the webhook claims to originate from (e.g., cross-check against a known installed-shop list) before trusting it in `WebhookMetadata`. At minimum, update `docs/usage/webhooks.md` to clarify that `data.shop`/`data.topic`/`data.webhook_id` are **not** cryptographically bound to the HMAC and must not be trusted as tenant identifiers without additional verification.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a legitimate, unprivileged install).
2. Attacker triggers an event (e.g., `orders/create`) on their own shop, capturing the raw webhook POST: body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC_SHA256(client_secret, B)`.
3. Attacker resends the exact same `(B, H)` pair to the app's public webhook endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
4. `HmacValidator.validate` recomputes `HMAC_SHA256(client_secret, B)` — identical to `H` — and returns `true` because it only ever hashes the body per `Webhooks::Request#to_signable_string`. [7](#0-6) 
5. `Registry.process` calls the handler with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: B, ...)`, and the app processes body `B` as if it belonged to `victim-shop.myshopify.com`. [8](#0-7)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
