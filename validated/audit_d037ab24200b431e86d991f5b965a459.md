### Title
Webhook shop-domain spoofing — HMAC validation covers only the request body, letting an attacker forge the tenant identity ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as fully authenticated once `Utils::HmacValidator.validate(request)` succeeds, then forwards `request.shop` — a value read straight from an HTTP header — to the app's handler as the authoritative tenant identifier. Because the HMAC signable string is only the raw body, the `shop-domain` header is never bound to the signature, so any bytes that produce a valid signature for *some* shop can be replayed with a different `shop-domain` header to make the library report an arbitrary victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns solely the raw body: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from unauthenticated headers: [2](#0-1) 

`HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` uses this as its sole authentication check, then immediately trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

The identity binding the library implies but does not enforce is:
`shop that produced/authorized this HMAC == request.shop passed to the handler`

In reality the equality only holds for `hmac == HMAC(secret, raw_body)`; `request.shop` (and `topic`/`webhook_id`) are parsed but never verified bytes, exactly the "bytes verified versus bytes parsed" mismatch class. Any unprivileged internet user who can install the app on a store they control (or who otherwise obtains one valid `(raw_body, hmac)` pair for any shop) can replay that same body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) header value for a victim shop. `Registry.process` will report success and hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body originated from the victim shop.

### Impact Explanation
Most host applications key their session/token lookup and business logic off `WebhookMetadata#shop` (e.g., to find the victim's stored access token, decrement inventory, mark an order paid, or write into the victim's per-tenant records) trusting that `Registry.process` already validated the request end-to-end. Because the shop identity is forgeable, an attacker can inject attacker-controlled webhook payloads that are processed under an arbitrary victim tenant's identity — a cross-tenant access impact (Critical, per the impact classification) since it lets one merchant's authenticated webhook traffic be relabeled as belonging to any other shop and drive tenant-scoped side effects (e.g., using the victim's stored credentials, corrupting victim data, or triggering per-shop business logic) without ever compromising that victim's credentials.

### Likelihood Explanation
Exploitation requires no privileged access, leaked secret, or the app's `client_secret`: any user capable of installing the app on a store (or otherwise triggering one legitimate webhook delivery for any shop, including their own) obtains a valid `(raw_body, hmac)` pair, since the signature never binds to the shop or topic. They can then freely replay that pair against the same public webhook endpoint with a forged `shop-domain` header, and the gem's own `Registry.process`/`HmacValidator.validate` will accept it as valid for the impersonated shop. This does not depend on the host app ignoring documented behavior — `process`'s contract is "validate then dispatch," and the shop field it dispatches is not part of what's validated.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the signable content, or otherwise cryptographically tie header-derived identity to the signed body, e.g. by validating that `shop` (and topic) embedded in the signed payload/body match the header values before trusting them, or by rejecting/flagging any handler dispatch where the header-derived shop cannot be corroborated against signed data. At minimum, document clearly that `request.shop`/`topic`/`webhook_id` are NOT covered by `HmacValidator.validate` and must be independently corroborated (e.g., against Shopify's Admin API) before being used as a tenant key.

### Proof of Concept
```ruby
# Attacker first triggers one legitimate webhook delivery for a shop they control
# and captures the raw body + shopify-hmac-sha256 header Shopify sent them.
legit_raw_body = '{"id":1,"note":"hello"}'
legit_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, legit_raw_body)

# Attacker replays the SAME body+hmac, but swaps the shop-domain header to the victim's shop.
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(legit_hmac),
  "shopify-shop-domain" => "victim-shop.myshopify.com", # <-- forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: legit_raw_body, headers: forged_headers)

# HmacValidator.validate only checks HMAC(secret, raw_body) == provided hmac -> succeeds
ShopifyAPI::Webhooks::Registry.process(request)
# -> handler.handle is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though the body/HMAC never originated from victim-shop.
``` [4](#0-3)
