### Title
Unchecked subtraction in `canGraduate()` panics and permanently bricks buy/sell on a token's curve - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding.canGraduate()` computes `realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair)` with a raw, unchecked `-` (Solidity 0.8 checked-arithmetic subtraction) rather than the saturating pattern used elsewhere in the same contract for the exact same quantity. `canGraduate` is not a side-path view — it is invoked unconditionally on *every* curve buy (`_executeBuy`), on *every* curve sell (`sell`), and by the permissionless `triggerGraduation`. If `assetReserve` ever dips below the launch-time virtual reserve, this subtraction panics (`Panic(0x11)`), and because it fires from inside the hot buy/sell path with no `try/catch`, every subsequent trade on that token reverts — the curve is permanently DoSed. This mirrors the alos-http bug class: an unchecked arithmetic op on attacker-influenceable state, reachable pre-handler on every request (here, on every trade), with no recovery mechanism once it fires.

### Finding Description
`canGraduate` at [1](#0-0)  reads:
```solidity
address pair = info.pair;
if (IPair(pair).tokenBalance() == 0) return true;

(, uint256 assetReserve) = IPair(pair).getReserves();
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
```
`_launchTimeVirtualLtReserve` recovers the launch-time virtual LT reserve as `Pair.k() / Token.TOTAL_SUPPLY()`, a constant baked in at `mint` [2](#0-1) . The subtraction assumes `assetReserve` (the live, mutable stored reserve) never drops below that constant. There is no saturating guard, unlike the pattern the same author explicitly applied to the identical quantity in `finalizeGraduation`: [3](#0-2) 
and in `_ltSwapInventory` / `_sweepLTToOwner` [4](#0-3) [5](#0-4) . Those comments explicitly state the intent is to "keep finalize from bricking on a Panic if any future code path... briefly violates the invariant" — proving the developers know this exact subtraction class can panic, yet the guard is missing on the two call sites that matter most: `canGraduate` and `previewLtUntilGraduation` [6](#0-5) .

`assetReserve` is not append-only: `Pair.swap` lets a sell shrink it via floored constant-product math with only a loose `+1` slack check [7](#0-6) , and `Router._computeSell` quotes `assetOut` using floor division against the pair's *original* immutable `k`, not a live-adjusted invariant [8](#0-7) . This is the same rounding-drift primitive the rules flag ("Pair.swap's `+1` K slack") — floor-division on sells systematically rounds in the seller's favor, and nothing recomputes or re-anchors `assetReserve` against the true real LT balance of the pair on each trade. A sequence of buys/sells that drifts stored `assetReserve` down to (or transiently below) `_launchTimeVirtualLtReserve` triggers the underflow the instant `canGraduate` is called — which happens automatically at the end of every buy via `_executeBuy` [9](#0-8)  and as a pre-check on every sell [10](#0-9) .

### Impact Explanation
Once the panic fires, the affected token's curve is permanently unusable: `Zap.buy`/`Zap.sell` (which call `Bonding.buy`/`Bonding.sell`, both of which call `canGraduate` unconditionally) revert for every future caller, `Zap.sell`'s pre-check (`bonding_.canGraduate(tokenAddress)` at [11](#0-10) ) also reverts, and `triggerGraduation` reverts too. There is no owner-level unbrick path — `assetReserve` is internal `Pair` storage with no admin setter. Every trader's tokens and LT sitting on the curve for that token become permanently frozen (cannot buy more, cannot sell, cannot force graduation), matching the required "permanent freezing of trader or creator funds" impact bar.

### Likelihood Explanation
The bug is reachable by any unprivileged trader simply buying/selling on a live curve — no privileged role, no upgrade, no oracle manipulation needed. The exact magnitude of rounding drift needed to trip the underflow (i.e., whether ordinary trading volume can realistically walk `assetReserve` down to the virtual-reserve floor within reasonable gas costs) could not be fully quantified analytically here; confirming the precise minimal attack sequence and gas cost would require a Solidity fuzz/invariant test (e.g., extending `packages/contracts/test/GraduationInvariants.t.sol`, which already references `_launchTimeVirtualLtReserve`). What is concretely established is that the guard is missing exactly where the developers themselves flagged it as necessary elsewhere in the same file.

### Recommendation
Apply the same saturating-subtraction pattern already used in `finalizeGraduation`/`_sweepLTToOwner`/`_ltSwapInventory` to `canGraduate` and `previewLtUntilGraduation`: `uint256 realLtRaised = assetReserve > virtualReserve ? assetReserve - virtualReserve : 0;`. Additionally, add an invariant/fuzz test asserting `assetReserve >= _launchTimeVirtualLtReserve(token, pair)` holds after any sequence of buys/sells, to catch the underlying rounding-drift issue in `Router._computeSell` / `Pair.swap`'s `+1` slack rather than only papering over the panic.

### Proof of Concept
Root-cause code path (no external repro executed; based on static analysis of the cited functions):
1. Attacker performs a sequence of buy → sell round trips on a freshly launched token's curve via `Zap.buy` / `Zap.sell`.
2. Each sell settles through `Router._computeSell`'s floor division and `Pair.swap`'s `+1`-slack K check, which permits `assetReserve` to drift downward relative to the immutable `_launchTimeVirtualLtReserve` floor.
3. Once `assetReserve < _launchTimeVirtualLtReserve(token, pair)`, the next call to `canGraduate(token)` — automatically invoked inside `Bonding._executeBuy` after any buy, or as a guard inside `Bonding.sell`/`Zap.sell` — executes `assetReserve - _launchTimeVirtualLtReserve(...)` and reverts with `Panic(0x11)` (arithmetic underflow).
4. All subsequent `Zap.buy`/`Zap.sell`/`Bonding.triggerGraduation` calls for that token revert identically, permanently freezing the market.
