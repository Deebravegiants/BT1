### Title
Stale `operator_qr_expiration_time` snapshot allows cached operator authorization to outlive backend-intended validity window across repeated signups - (File: `src/plans/mod.rs`)

### Summary
`MasterPlan::run` captures `operator_qr_expiration_time` (and `self_serve`) as a one-time snapshot before entering the perpetual signup loop. That stale value governs whether the previously-scanned operator QR code (`initial_qr_codes` / `OperatorData` with its cached `timestamp`, `location_data`, and permissions) is treated as still valid for gating entry into a new signup, for the entire lifetime of the orb process loop (`self.oneshot` is false in normal continuous operation). If the backend shortens `operator_qr_expiration_time` mid-session (e.g., to reduce the window an operator's credential should be trusted, due to operator being flagged, deactivated, or a policy change), the outer loop's `scan_initial_qr_codes`/`idle_wait_for_signup_request` will continue to accept the old, longer expiration window and will not force a re-scan/re-verification of the operator, letting a signup proceed to `do_signup` using a stale, no-longer-intended-to-be-trusted `OperatorData`.

### Finding Description
The root cause mirrors the reported Community.sol class of bug: a parameter (`operator_qr_expiration_time`, analogous to the APR) that should govern the validity of pre-existing cached state (`OperatorData`, analogous to the outstanding lent amount) is captured once and then reused unchanged across many subsequent operations, while a parallel code path (`do_signup`/`scan_remaining_qr_codes`) re-fetches the current value on every call. This creates two different "APR-like" expiration values being applied inconsistently to the same underlying cached operator authorization object within a single continuous orb run: the outer idle loop's gate uses the old value, `do_signup`'s inner gate uses the new value. ` [5](#0-4) `

Because `scan_initial_qr_codes` only rescans the operator when `ts.elapsed() > operator_qr_expiration_time` using the *stale* threshold, an operator QR whose authorization the backend intended to revoke/shorten will still be treated by the outer loop as fresh enough to skip re-scanning and go straight into `idle_wait_for_signup_request`, which then hands the same stale `OperatorData` into a brand new signup attempt. ` [2](#0-1) `

### Impact Explanation
This can lead to a new signup being authorized/attributed to an operator (via `OperatorData.location_data`, `qr_code`) whose authorization window the backend has since intentionally shortened. Since `OperatorData` feeds directly into `DebugReport::builder` (setting `operator_qr_code`, `location_data`) and into `personal_custody_package::Credentials.operator_qr_code`, a signup could be recorded/attributed under stale operator credentials/location for longer than the backend's currently configured trust window, constituting a misattributed-signup condition tied to operator authorization state that outlives its intended validity. ` [6](#0-5) ` ` [7](#0-6) `

### Likelihood Explanation
The orb runs `MasterPlan::run` continuously (non-oneshot) performing many signups back-to-back without restarting, so the one-time config snapshot at the top of `run` can become arbitrarily stale relative to backend config updates that arrive later via the periodic config-polling mechanism, while `do_signup`'s independent fresh read of the same field demonstrates the config is expected to be dynamic during a running session.

### Recommendation
Re-read `operator_qr_expiration_time` (and `self_serve`) from `orb.config.lock().await` fresh at the top of each loop iteration (immediately before calling `scan_initial_qr_codes` and `idle_wait_for_signup_request`), instead of hoisting a single snapshot before the loop, so the outer gating logic is always consistent with the value used inside `do_signup`/`scan_remaining_qr_codes`.

### Proof of Concept
1. Orb starts `MasterPlan::run`; backend config has `operator_qr_expiration_time = 1 hour`. This value is captured once at line 334. ` [8](#0-7) `
2. Operator scans their QR code; `initial_qr_codes` becomes `QrCodes::Operator { operator_data }` with `timestamp = t0`.
3. Several signups happen using this operator code (normal, intended behavior).
4. Backend detects an issue and updates config to `operator_qr_expiration_time = 1 minute` to force faster re-validation of operators.
5. `do_signup`'s next invocation reads the new 1-minute value and, inside `scan_remaining_qr_codes`, correctly determines the cached operator data (now `> 1 minute` old) is expired and would normally require rescanning. ` [9](#0-8) `
6. However, the *outer* loop's `scan_initial_qr_codes`/`idle_wait_for_signup_request` still uses the original 1-hour threshold (from step 1), so it does not force the operator to rescan before allowing the idle loop to accept a new user QR code and proceed toward `do_signup` — the stale `OperatorData` is passed along regardless, relying only on the inner check to catch it, and any code path or timing window where the inner/outer checks disagree lets the stale operator authorization continue to gate/attribute new signups beyond the backend's newly intended validity window.
