### Title
Webhook shop-domain identity is not covered by the HMAC, enabling cross-tenant webhook replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body [1](#0-0) , while the `shop` value that the library hands to the app's `WebhookHandler` is read from an unsigned HTTP header (`shop-domain`) that is never part of the signed payload [2](#0-1) . Because the HMAC secret (`Context.api_secret_key`) is a single, app-wide secret shared across every shop that installs the app (not a per-shop secret) [3](#0-2) , a valid `(raw_body, hmac)` pair obtained from any one legitimately-delivered webhook (e.g. one delivered to the attacker's own store, since anyone can install a public app on their own shop) remains cryptographically valid no matter which `shop-domain` header value is attached to the replayed request. This breaks the intended identity binding "shop authenticated == shop passed to the handler."

### Finding Description
`Utils::HmacValidator.validate` only verifies `to_signable_string`, which for `Webhooks::Request` is exactly the raw body [4](#0-3) . The `shop`, `topic`, and `webhook_id` accessors are all derived from HTTP headers that are never fed into the signable string and therefore never authenticated [5](#0-4) .

`Registry.process` performs the HMAC check and then immediately trusts `request.shop` as the tenant identity for the webhook, passing it straight into `WebhookMetadata` and to the host application's handler:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
  body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
``` [6](#0-5) 

`WebhookMetadata.shop` is a plain, unauthenticated `String` field consumed by every app-supplied `WebhookHandler#handle` implementation as the tenant/shop identity for the event [7](#0-6) .

Because `Context.api_secret_key` is a single app-level secret used to validate every shop's webhooks (as shown in both `HmacValidator` and the test fixtures, which compute the same HMAC using `ShopifyAPI::Context.api_secret_key` regardless of `shop`) [8](#0-7) , an attacker who can obtain one legitimately-signed `(body, hmac)` pair for any shop — trivially achievable by installing the app on their own store and capturing the webhook their own app endpoint receives — can resend that exact body/HMAC to the app's webhook endpoint while swapping the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header to a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the (unmodified) body against the (shared) secret; `Registry.process` then delivers `WebhookMetadata` with `shop` = the attacker-chosen victim domain to the host application.

### Impact Explanation
This crosses a tenant boundary: the library-provided authentication primitive (`Registry.process`/`HmacValidator.validate`) gives host applications a false guarantee that `shop` in `WebhookMetadata` is authenticated. Any host app that uses this library's webhook processing and trusts `data.shop` to select the tenant record, look up the tenant's stored access token, or write imported data will process/act on attacker-controlled data under a victim shop's identity — i.e., cross-tenant access/data confusion, which falls under the Critical "cross-tenant access" category defined for this scan.

### Likelihood Explanation
Moderate-to-high: no privileged credentials, TLS interception, or leaked secrets are required. All the attacker needs is to be an ordinary merchant/installer of the target app (an "unprivileged internet user" with respect to other tenants) to capture one valid webhook delivery for their own shop, then replay it with a modified header at the app's public webhook endpoint. The HMAC secret being shared across all shops for a given app is what makes the replay valid; this is a structural property of how `HmacValidator`/`Webhooks::Request` are implemented in this gem, not a host-application misuse.

### Recommendation
Bind the authenticated identity to the signed payload instead of trusting an unsigned header:
- Include the `shop-domain` (and ideally `webhook_id`/`topic`) header values in the data that is HMAC-verified, or otherwise cryptographically bind them to the payload, so that any modification of these headers invalidates the signature.
- Alternatively/additionally, cross-check `request.shop` against the shop associated with the session/token the host app expects for that webhook subscription before invoking the handler, and expose this validation as part of `Registry.process` rather than leaving it entirely to be inferred by host applications from an unauthenticated field.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and subscribes to a webhook topic (e.g. `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <hmac>`, and some JSON body `B`. The attacker records `B` and the valid `hmac`.
3. Attacker crafts a new HTTP POST to the same app webhook endpoint using the *same* body `B` and *same* `hmac` header, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Registry.process` is invoked with this forged `Request`:
   - `Utils::HmacValidator.validate(request)` succeeds because it only hashes `raw_body` (`B`) with the app's single `api_secret_key`, unaffected by the header change [4](#0-3) [9](#0-8) .
   - The handler is invoked with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)` [10](#0-9) .
5. The host application, trusting `data.shop` as authenticated, processes attacker-controlled data as if it originated from `victim-shop.myshopify.com`, causing cross-tenant data corruption/confusion.
