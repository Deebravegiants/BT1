This is exactly the finding: `Webhooks::Request#shop` is read from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, but `to_signable_string` (the bytes the HMAC actually signs) is only the raw request body: [1](#0-0) [2](#0-1) 

The HMAC is computed over `@raw_body` only, via `HmacValidator.validate`, which calls `verifiable_query.to_signable_string`: [3](#0-2) 

So `shop` (the tenant identity used by the host application to route/attribute the webhook to a merchant) is never part of the signed bytes. Any caller that can produce a body/HMAC pair signed with the app's secret (e.g., replaying a legitimately-received webhook payload+HMAC that Shopify sent for one shop) can attach an arbitrary `X-Shopify-Shop-Domain` header value, and `Request#shop` will return that attacker-chosen value while `hmac`/`to_signable_string` still validates successfully — because the header is parsed but never verified/bound by the signature.

**Binding broken (equality that should hold but doesn't):**
`shop` field acted upon by the host application == `shop` bytes covered by HMAC. In `Webhooks::Request`, `shop` is read from an unauthenticated header while the HMAC only covers `@raw_body`, so:
`hmac_verified(raw_body) == true` does **not** imply `shop == the tenant that actually owns this event`.

This matches the report's bug class ("a field acted on but not covered by the HMAC") applied to this gem's own webhook-verification primitive, `ShopifyAPI::Webhooks::Request`.

### Title
Webhook `shop` (tenant) claim is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` exposes a `shop` accessor sourced from the `X-Shopify-Shop-Domain` (or lowercase variant) HTTP header, but the HMAC verification performed via `Utils::HmacValidator.validate` only signs `@raw_body` (`to_signable_string`). The `shop` value is therefore unauthenticated even after `hmac` validation succeeds.

### Finding Description
`Request#initialize` merely checks for header presence, not correctness, and stores headers verbatim: [4](#0-3)  `shop` is then derived purely from that header dictionary: [1](#0-0) . Verification (`hmac`) is computed against the `hmac-sha256` header, and the signed payload returned by `to_signable_string` is only the raw body: [5](#0-4) [2](#0-1) . `HmacValidator.validate` compares `compute_signature(verifiable_query.to_signable_string, secret)` against the supplied `hmac`, with no reference to `shop` at all: [3](#0-2) . Consequently, an app that consumes `Request#shop` (e.g., the `Webhooks::Registry` dispatch flow, which is the documented usage pattern) trusts a tenant identifier that carries no cryptographic binding to the signed body, breaking the identity equality `verified_bytes == acted_upon_shop`.

### Impact Explanation
This is a cross-tenant data-integrity break: a host application processing a validly-signed webhook (HMAC checks out) can be made to attribute/act on the payload under an attacker-chosen `shop` value, since the `shop` claim is entirely separate from what is cryptographically verified. This satisfies the "cross-tenant access" criterion — an app could write/process data for shop B while believing (per this gem's own verified value) it originates from shop A, or vice versa, purely because the header is not bound to the signature.

### Likelihood Explanation
Exploitability requires an attacker to control HTTP headers on the request delivered to the app's webhook endpoint while the raw body + HMAC pair validates (this can occur through any request-forwarding/proxy path, header-order confusion, or a resent/relayed webhook payload with headers altered before reaching app code, since this gem performs no binding check). The gem provides no defense at all for this specific field, so likelihood depends only on the host environment allowing header tampering ahead of `Request.new`, which is a realistic deployment condition (proxies, load balancers, App frameworks merging headers) rather than a contrived one.

### Recommendation
Include `shop` (and ideally `topic`, `api_version`, `webhook_id`) in the signed material verified by `HmacValidator`, or independently validate the `shop` header value against Shopify's domain format and cross-check it against a known/authorized shop list before trusting it. At minimum, document that `Request#shop` is unauthenticated and must not be used for tenant routing without additional verification.

### Proof of Concept
1. Attacker (or a misconfigured intermediary) captures a legitimate webhook body+HMAC pair (any topic) originally sent for `shop-a.myshopify.com`.
2. Attacker resends the same raw body and `X-Shopify-Hmac-Sha256` header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed; `Utils::HmacValidator.validate(request)` succeeds because it only checks `raw_body` against the HMAC (`to_signable_string` returns `@raw_body`) — see [2](#0-1) .
4. The host application reads `request.shop` and obtains `"shop-b.myshopify.com"` — attributing shop A's verified webhook data to shop B — see [1](#0-0) .
