### Title
Webhook shop-domain identity used for tenant routing is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, then trusts the `shop`/`shop-domain` header — taken from an entirely separate, unauthenticated part of the request — as the tenant identity handed to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . Meanwhile, `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to the body or to the HMAC at all [3](#0-2) .

`Registry.process` performs exactly one check — `Utils::HmacValidator.validate(request)` — and if it passes, immediately forwards `request.shop` (the unauthenticated header) to the app's handler as the tenant identity for the webhook payload: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

The identity binding broken here is:
`shop used by the app to attribute/route webhook data` ≠ `shop bound by the value the HMAC actually authenticates (raw_body only)`.

Because the HMAC key (`Context.api_secret_key`) is the app's single `client_secret`, shared across every shop that installs the app, any tenant that legitimately receives one webhook (body + valid HMAC, e.g., for their own store) possesses a body/HMAC pair that remains cryptographically valid for the app's secret regardless of which shop it is replayed for. Nothing in `HmacValidator.validate` or `Registry.process` ties the `shop` header to the signed content, so an attacker-controlled shop-domain header can be swapped in during replay without invalidating the HMAC.

### Impact Explanation
This satisfies the required "field acted on but not covered by the HMAC" bug class: `shop` is acted upon (used to construct `WebhookMetadata` and passed to the app's handler for tenant-scoped processing) but is not covered by the signature verification. An attacker who is themselves a legitimate app-installing shop can capture one of their own real webhook deliveries (valid `raw_body` + valid `x-shopify-hmac-sha256`) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still returns `true` because it only checks the body/HMAC pair, and `Registry.process` will dispatch the (attacker-controlled) payload to the app's handler labeled as belonging to the victim tenant. Any app logic keyed off `WebhookMetadata#shop` (e.g., looking up the victim's session/access token, writing data under the victim's tenant record, or triggering tenant-scoped side effects) is invoked with data that was never authenticated as originating from that tenant — a cross-tenant data-integrity/confusion issue reachable without any credentials beyond running one's own shop.

### Likelihood Explanation
Likelihood is moderate-to-high: exploitation only requires being any shop that has installed the target app (no special privilege, no access-token theft, no TLS interception) and the ability to send an arbitrary HTTP POST with copied headers/body to the app's public webhook endpoint. Both the raw body and the valid HMAC are trivially obtainable by the attacker from their own webhook deliveries.

### Recommendation
Bind the tenant identity to the authenticated content: either (a) sign the `shop` (and `topic`/`webhook_id`) values together with the body before computing/verifying the HMAC (i.e., extend `Request#to_signable_string` to include the header fields that are trusted downstream), or (b) require the app layer to independently verify that `request.shop` corresponds to a shop for which a webhook was actually expected/registered (cross-check against a known session/shop registry) before acting on `WebhookMetadata#shop`. At minimum, document prominently that `HmacValidator.validate` authenticates only the body and that `shop`/`topic` header values must not be trusted as tenant identity without additional verification.

### Proof of Concept
```ruby
# Attacker legitimately installs the app on attacker-shop.myshopify.com
# and receives a real webhook delivery:
raw_body = '{"id":123,"note":"hi"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), app_client_secret, raw_body)

# Attacker replays the exact same body+hmac, but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled, unauthenticated
  "x-shopify-webhook-id" => "any",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# HmacValidator.validate(request) => true, because it only checks raw_body vs hmac
# handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...))
# The app now processes attacker-controlled data attributed to victim-shop.
