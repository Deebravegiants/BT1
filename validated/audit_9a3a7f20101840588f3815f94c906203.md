## Title
Webhook `shop`, `topic`, `webhook-id` and `api-version` identifiers are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC computed by `Utils::HmacValidator.validate` in `Registry.process` verifies the integrity of the JSON payload but never binds it to the `shop`, `topic`, `webhook-id`, or `api-version` values that are read straight from HTTP headers.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
returning only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers via `shopify_header`: [2](#0-1) [3](#0-2) 

`Registry.process` validates the request by calling `Utils::HmacValidator.validate(request)`, which only checks `verifiable_query.to_signable_string` (i.e., the raw body) against the HMAC header: [4](#0-3) [5](#0-4) 

After the HMAC check passes, `request.shop` (and `topic`, `webhook_id`, `api_version`) — none of which were part of the signed bytes — are forwarded verbatim into `WebhookMetadata` and handed to the host application's handler: [6](#0-5) 

The identity binding that should hold is: `bytes verified == bytes that determine tenant identity`. Here, `bytes verified = raw_body`, but `tenant identity (shop) = header value`, which is a disjoint, unauthenticated channel. Any party capable of producing a validly-signed webhook body for *any* topic/shop combination (e.g., a merchant who installs the app on their own shop and receives a genuine, correctly-HMAC'd webhook for their own tenant) can replay that same body with the `shopify-shop-domain` (or `x-shopify-shop-domain`) header swapped to a victim shop's domain. Because the signature only covers the body, `Utils::HmacValidator.validate` returns `true`, and `Registry.process` will call the host app's handler claiming the event happened for the victim's `shop`.

### Impact Explanation
This breaks the tenant boundary the library is supposed to enforce for webhook processing: a webhook legitimately generated for shop A can be replayed with a forged `shop` header claiming to be shop B, causing the host application's webhook handler to act on shop-B-scoped data using attacker-controlled/attacker-generated content. This is a cross-tenant confusion vulnerability rooted entirely in this gem's `Request`/`Registry` code — the HMAC secret (`Context.api_secret_key`) never needs to be known to the attacker for a body they could legitimately obtain a valid signature for (from their own shop's webhook deliveries).

### Likelihood Explanation
The attacker needs a valid HMAC-signed webhook body, which they can obtain by installing the app on their own shop (an unprivileged action for anyone able to install a public/development app) and capturing one of their own genuine webhook deliveries. They then only need to control (or MITM/replay to) the endpoint that calls `Registry.process`, substituting the `shop` header. No `api_secret_key` or access token needs to be stolen since the flaw is that the header is simply never covered by the signature at all.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (at minimum `shop` and `topic`) in the signable string used for HMAC verification in `Request#to_signable_string`, or otherwise cryptographically bind these header-derived identifiers to the signed payload before they are trusted and forwarded to `WebhookMetadata` in `Registry.process`.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g., `orders/create`), capturing the raw body and the valid `shopify-hmac-sha256` header Shopify computed over that body.
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` builds the request; `request.shop` returns `"victim.myshopify.com"` while `request.to_signable_string` still returns the untouched `raw_body`.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and matches (since body was untouched), returning `true`: [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim.myshopify.com", body: request.parsed_body, ...)`, causing the host app to process attacker-supplied data as if it originated from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

        end
