### Title
Freezing a consensus client via a permissionless fraud proof permanently strips all in-flight cross-chain funds for that route with no recovery path - ([File: modules/ismp/core/src/handlers/consensus.rs])

### Summary
`freeze_client` can be triggered by any unprivileged "fisherman" submitting a valid fraud proof for a consensus client. Once frozen, the client is documented as unrecoverable: "Frozen consensus clients cannot be unfrozen and a new consensus client must be initialized through the `create_client` method instead" [1](#0-0) . This mirrors the reported bug class (M-02/M-08 in the referenced report): disabling a component that still holds live user funds, with no graceful drain path, forces protocol operators into a catch-22 between accepting fund loss (freezing immediately) or accepting continued risk exposure (leaving a faulted client active).

### Finding Description
`freeze_client` is reachable by any permissionless fisherman submitting a `FraudProofMessage`: [2](#0-1) 

It sets an irreversible flag via `freeze_consensus_client`: [3](#0-2) 

`is_consensus_client_frozen` is checked in `update_client` before any new consensus state is accepted [4](#0-3) , and documentation confirms it also blocks new request/response processing: "In this state it can no longer process new consensus messages as well as new requests & responses" [1](#0-0) . There is no code path that unfreezes a `ConsensusStateId` — only `create_client` (a fresh trust root, presumably starting at a later height) is offered as "recovery" [1](#0-0) .

Because fishermen are intentionally permissionless ("Running fishermen should be permissionless and require no staking whatsoever") [5](#0-4) , this is an unprivileged, single-transaction action, analogous to the "disable the derivative" admin action in the referenced report but requiring no privilege at all here.

Any request/response that was already dispatched (e.g. tokens locked via `WrappedHyperFungibleToken.send`, an ISMP POST already committed on the source chain) but not yet relayed/delivered before the freeze becomes permanently stranded: the frozen client can no longer process the pending request/response, and the suggested remedy — creating a brand-new consensus client — trusts a fresh, later state and offers no mechanism to replay or prove the pre-freeze commitment against it. This is functionally identical to the SafEth situation: disabling the faulty component (the consensus client) after the fact makes any funds already "inside" it (in-flight/locked cross-chain transfers relying on it) irretrievable.

### Impact Explanation
Governance/fishermen face the same no-win choice described in the report:
1. Freeze the consensus client immediately upon detecting a fault → all in-flight locked/escrowed funds routed through that state machine become permanently unrecoverable (frozen forever, no unfreeze, no replay against the new client).
2. Delay freezing to let in-flight funds settle → the network remains exposed to the byzantine consensus fault for longer, risking forged state proofs and unbacked minting/theft in the interim.

Either path leads to concrete loss: guaranteed freezing of legitimate user funds, or continued exposure to fund theft via a known-byzantine consensus client. This satisfies "permanent freezing of funds" from a reachable, unprivileged action.

### Likelihood Explanation
Medium. Fraud proofs require genuine byzantine misbehaviour on a tracked chain to be submitted (an adversarial or faulted validator set), so it isn't purely at will by an attacker; however, once such a fault occurs, freezing is automatic/necessary and permissionless, and the fund-freezing side effect on all pending messages is unconditional and unavoidable by design as currently documented — no admin discretion or user-directed drain window exists.

### Recommendation
Before/atomically with freezing, or via a grace mechanism, allow in-flight requests/responses committed prior to the fraud height to still be resolved (either by permitting delivery against the pre-freeze committed state within their existing challenge/timeout window, or by providing an explicit timeout/refund path independent of the frozen consensus client). Alternatively, when creating a replacement consensus client for the same `ConsensusStateId`, carry forward or re-attest to still-pending state machine commitments so in-flight messages can still be proven and delivered/timed-out rather than being unconditionally abandoned.

### Proof of Concept
1. User calls `WrappedHyperFungibleToken.send` on chain A, locking tokens and dispatching a POST request; the request commitment is recorded and awaiting relay/delivery to chain B, whose consensus client `is_consensus_client_frozen(id) == false`. [6](#0-5) 
2. Before the request is relayed and delivered (or before it can time out and be refunded), a fisherman observes a genuine consensus fault on the tracked chain and submits `FraudProofMessage` via `freeze_client`. [2](#0-1) 
3. `freeze_consensus_client` permanently sets `FrozenConsensusClients::<T>::insert(client, true)` with no code path to clear it. [3](#0-2) 
4. All subsequent processing of requests/responses tied to that consensus state id is blocked; the only path forward is `create_client`, initializing a new trust root that does not retroactively cover the pending pre-freeze commitment, so the locked tokens on chain A can neither be delivered on chain B nor refunded via a timeout that depends on the same (now-frozen) verification path — resulting in a permanent freeze of the locked user funds.

**Uncertainty note:** I was not able to directly inspect the request/response handler code (e.g. `modules/ismp/core/src/handlers/request.rs`/`response.rs`) within the available iterations to confirm the exact code-level check that blocks post-freeze message processing (I relied on the explicit doc statement at `docs/content/protocol/ismp/consensus.mdx:200`). I also could not verify whether `create_client` permits re-using an existing `consensus_state_id` or whether any timeout/refund logic is decoupled from consensus-client-frozen checks. A deeper review of `modules/ismp/core/src/handlers/` and the timeout handling path would be needed to fully confirm the exact mechanics of fund unrecoverability versus a possible timeout-based refund that doesn't require the frozen client.

```rust
/// Freeze a consensus client by providing a valid fraud proof.
pub fn freeze_client<H>(host: &H, msg: FraudProofMessage) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	let consensus_client_id = host
		.consensus_client_id(msg.consensus_state_id)
		.ok_or_else(|| Error::Custom("Unknown Consensus State Id".to_string()))?;

	host.is_consensus_client_frozen(msg.consensus_state_id)?;

	let consensus_client = host.consensus_client(consensus_client_id)?;
	let trusted_state = host.consensus_state(msg.consensus_state_id)?;

	consensus_client.verify_fraud_proof(host, trusted_state, msg.proof_1, msg.proof_2)?;

	host.freeze_consensus_client(msg.consensus_state_id)?;

	host.store_consensus_update_time(msg.consensus_state_id, host.timestamp())?;

	Ok(MessageResult::FrozenClient(msg.consensus_state_id))
}
```
