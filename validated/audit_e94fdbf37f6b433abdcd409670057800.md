### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw webhook body, and `ShopifyAPI::Utils::HmacValidator.validate` in `lib/shopify_api/webhooks/registry.rb` verifies the HMAC exclusively against that body. The `shop-domain` header, which is read via `Request#shop` and forwarded unchanged into `WebhookMetadata#shop` for the app's handler, is never included in the signed payload. Because the app's `api_secret_key` is shared across all shops (it is the app's secret, not a per-shop secret), any merchant with the app installed on their own store can compute a valid `(body, hmac)` pair and then replay it to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` / `shopify-shop-domain` header for a victim shop. The signature still validates, and the forged shop identity is delivered to the host application's webhook handler as trusted data.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `#shop` simply reads the header without any cryptographic binding to the body: [2](#0-1) 

`HmacValidator.validate_signature` computes the signature purely from `verifiable_query.to_signable_string`: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build `WebhookMetadata`, which is handed to the app's handler as the authoritative shop identity for the event: [4](#0-3) 

The identity binding that should hold is: `shop asserted in the header == shop the HMAC actually authenticates`. Because the HMAC only covers `@raw_body`, this equality is never enforced — `HMAC(secret, body)` is identical regardless of what `shop-domain` header accompanies it. Any legitimate merchant with the app installed can generate a valid webhook (e.g., by triggering an event on their own store, since Shopify signs outgoing webhooks with the app's single shared `api_secret_key`, not a per-shop secret), capture the `(raw_body, hmac)` pair, and resend it to the app's public webhook callback URL with the `shop-domain` header changed to any victim shop domain. `Registry.process` will accept it as valid and route the attacker-controlled body to the handler tagged with the victim's shop, exactly as documented for handlers to consume via `data.shop`: [5](#0-4) 

Host applications built per the gem's own documented pattern trust `data.shop` to key their background processing (e.g., "`perform_later(topic: data.topic, shop_domain: data.shop, ...)`"), so this unauthenticated field directly drives which tenant's records get updated.

### Impact Explanation
This breaks the tenant boundary the HMAC is meant to enforce: `shop-domain header` should equal `shop authenticated by the HMAC`, but the gem only proves `body authenticity`, not `shop authenticity`. An attacker who is merely an unprivileged merchant using their own store (no `api_secret_key`, no victim access token, no privileged account required) can forge webhook deliveries that the host app will process as belonging to a different, victim shop, resulting in cross-tenant data injection/confusion in the host application's webhook processing pipeline.

### Likelihood Explanation
Likelihood is high: the only prerequisite is installing the app on an attacker-owned development/test store (a normal, unprivileged action), triggering any webhook event to obtain a valid `(body, hmac)` pair for the shared app secret, and replaying the request with a spoofed `shop-domain` header. No secrets, tokens, or elevated privileges belonging to the victim are needed.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the signed material, or independently verify that the `shop-domain` header corresponds to a shop the app currently has an active/expected session for before dispatching to handlers. At minimum, document that `WebhookMetadata#shop` is not cryptographically bound and must be independently validated by host applications before being used as a tenant key.

### Proof of Concept
1. Install the app on attacker-owned shop `attacker.myshopify.com`; trigger any subscribed webhook topic (e.g., `orders/create`) to receive a legitimate webhook POST with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Replay this exact request to the app's public webhook endpoint, keeping `raw_body = B` and `X-Shopify-Hmac-Sha256 = H` unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — validation succeeds because the shop header was never part of the signed data (`lib/shopify_api/webhooks/request.rb` lines 20-23, 35-38; `lib/shopify_api/utils/hmac_validator.rb` lines 26-31).
4. The handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed_body_of_B, ...)` (`lib/shopify_api/webhooks/registry.rb` lines 198-199), causing the host app to process attacker-controlled data under the victim shop's tenant identity.
