### Title
Unrestricted `CallDispatcher.dispatch` allows anyone to drain any ETH/ERC-20 balance temporarily or permanently held by the shared dispatcher - ([File: evm/src/utils/CallDispatcher.sol])

### Summary
Hyperbridge's `CallDispatcher` is a single, shared, address-controlled contract used by `IntentGatewayV2` (predispatch/postdispatch swap flows), `IntentsBase._execute`, `HyperFungibleToken.onAccept`, and `WrappedHyperFungibleToken.onAccept` to temporarily custody native ETH and ERC-20 tokens while arbitrary user-supplied calldata executes. Its `dispatch()` function has **no access control** — any external account can call it directly and instruct it to move whatever balance it currently holds to an attacker-chosen address. This mirrors the THORChain/Bifrost bug class: a routing/execution contract that is supposed to only move value on behalf of a validated, well-formed request instead allows an unauthorized caller to trigger a "capture" of value sitting in the contract.

### Finding Description
`CallDispatcher.dispatch` is declared with no modifier and no `msg.sender` restriction: [1](#0-0) 

This same contract instance (`_params.dispatcher`) is used as a temporary vault across multiple unrelated flows:

- `IntentGatewayV2.placeOrder`: predispatch assets (native ETH via `_sendValue`/raw call, ERC20 via `safeTransferFrom`) are sent to the dispatcher, arbitrary `order.predispatch.call` is executed on it, then only the tokens explicitly listed in `order.inputs[]` are swept back: [2](#0-1) 

- `IntentsBase._execute` (fill-time postdispatch): output calldata runs on the dispatcher, and only tokens listed in `outputsLen` are swept as "dust": [3](#0-2) 

- `HyperFungibleToken`/`WrappedHyperFungibleToken.onAccept`: cross-chain minted/unlocked tokens can be routed `to` the dispatcher, followed by `ICallDispatcher(_dispatcher).dispatch(message.data)` to run attacker-influenced (source-chain-embedded) calldata against the freshly credited balance: [4](#0-3) 

Because none of these flows guarantee that 100% of the value routed through the dispatcher is consumed or swept back (e.g., calldata that doesn't fully spend the minted/unlocked tokens, predispatch calls producing byproduct tokens not listed in `order.inputs`, or postdispatch calls producing tokens not listed in `output.assets`), any residual balance is left sitting in the `CallDispatcher`'s persistent storage/balance after the originating transaction completes. Since `dispatch()` has no caller restriction, **any unrelated third party** can subsequently call `CallDispatcher.dispatch()` directly with a `Call[]` payload that transfers that residual ETH or ERC-20 balance to an address of their choosing — with no relationship to any order, message, or authorization from the party who funded it.

This is the same root-cause pattern as the THORChain incident: a routing/execution component intended to move value only as part of a legitimate, well-formed operation instead lets an unauthorized actor directly trigger value movement out of the shared custody contract, because the contract that holds funds in transit performs no check on who is permitted to invoke it or for what committed operation.

### Impact Explanation
Any ETH or ERC-20 balance that ends up resting in the `CallDispatcher` — whether from a fee-on-transfer/rounding remainder not covered by the existing dust-sweep logic, an incompletely-consuming predispatch/postdispatch calldata payload, or an incompletely-consuming `onAccept` calldata payload for `HyperFungibleToken`/`WrappedHyperFungibleToken` — is directly stealable by any unprivileged address. Because the dispatcher is a single shared contract reused across all `IntentGatewayV2` orders and all `HyperFungibleToken`/`WrappedHyperFungibleToken` cross-chain deliveries on a chain, this is not an isolated, order-scoped risk: it is a shared attack surface where any dust or stuck balance from any user's flow becomes a bounty for the first attacker to call `dispatch()`. This satisfies "concrete theft ... of funds" and "unauthorized app action" from the validation criteria and is reachable from a single unprivileged, permissionless transaction (a direct call to `CallDispatcher.dispatch`).

### Likelihood Explanation
High. No privileged role, no proof, no cross-chain message, and no interaction with the intent/order lifecycle is required — the attacker only needs to observe (via standard on-chain balance monitoring) that the shared `CallDispatcher` address holds a nonzero ETH or token balance, then submit a single transaction calling `dispatch()` with a `Call[]` transferring that balance out. Given the variety of flows that route funds through this one contract (intents predispatch/postdispatch, HFT mint-and-call, WrappedHFT unlock-and-call), some nonzero residual balance is a realistic and recurring occurrence rather than a rare edge case.

### Recommendation
Restrict `CallDispatcher.dispatch` to only be callable by the specific, single trusted caller that funded the exact call batch being executed (e.g., require `msg.sender` to be an authorized gateway/app address set at construction, or make `CallDispatcher` non-shared/ephemeral per invocation so it never persists a balance between calls). At minimum, add an owner/allowlist check (`onlyGateway`/`onlyAuthorizedCaller`) so that arbitrary third parties cannot invoke `dispatch()` to move value the contract happens to be holding. Additionally, ensure every flow that routes value through the dispatcher (predispatch, postdispatch, `onAccept` calldata execution) exhaustively sweeps 100% of any token that could have been produced, not just the tokens explicitly enumerated in `order.inputs`/`order.output.assets`.

### Proof of Concept
1. Any legitimate user calls `IntentGatewayV2.placeOrder` (or triggers a `WrappedHyperFungibleToken`/`HyperFungibleToken` cross-chain delivery) whose predispatch/postdispatch/onAccept calldata does not consume 100% of the assets routed to the shared `CallDispatcher` (e.g., a swap that leaves rounding dust in a token not listed in `order.inputs`, or a partial-fill calldata payload).
2. That transaction completes; the unconsumed ETH/ERC-20 balance remains on the `CallDispatcher` contract's address.
3. An attacker, with no relationship to the original order/message, submits a transaction calling `CallDispatcher.dispatch(abi.encode(calls))` directly, where `calls` is a single `Call{ to: token, value: 0, data: abi.encodeWithSelector(IERC20.transfer.selector, attacker, balance) }` (or, for ETH, `Call{ to: attacker, value: balance, data: "" }`).
4. `CallDispatcher.dispatch` executes this call unconditionally — see [1](#0-0)  — transferring the residual balance to the attacker with no authorization check.

    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
