### Title
Fee-on-transfer token escrow accounting mismatch enables shared-pool insolvency and fund drainage - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron implementation of `IntentGatewayV2.placeOrder` credits an order's escrow ledger (`_orders[commitment][token]`) with the nominal, protocol-fee-reduced input amount rather than the amount the contract actually received from `safeTransferFrom`. For any ERC20 input token that charges its own transfer fee (fee-on-transfer/deflationary/"reflection" style tokens — the exact token class implicated in the FEG incident, where balance-tracking diverged from actual on-chain balances and was exploited via a flash loan), this creates a permanent gap between the gateway's recorded liabilities and its real token balance.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 
the contract calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then unconditionally records `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is `order.inputs[i].amount` minus only the protocol fee — it is never adjusted for what the contract actually received.

Contrast this with the audited EVM (`evm/src/apps/IntentGatewayV2.sol`) implementation, which explicitly snapshots the gateway's balance before and after each `safeTransferFrom` and mutates `order.inputs[i].amount` to the delta before it is used for the commitment/escrow, precisely to handle fee-on-transfer tokens: [2](#0-1) 
This same "actual received vs requested" reconciliation is verified extensively in the EVM test suite for `FeeOnTransferToken`: [3](#0-2) 

The Tron `placeOrder`'s predispatch branch does perform a `balance < requiredAmount` check against the dispatcher's actual balance (lines 416-446), but the plain (non-predispatch) escrow path at lines 450-468 has no such check at all — it blindly trusts `order.inputs[i].amount` even after calling `safeTransferFrom` on an attacker-supplied `token` address.

Since `_orders[commitment][token]` is a per-commitment ledger but the actual tokens sit in one shared contract balance (`address(this)`), inflating the ledger for one order without a matching real balance increase creates a "phantom balance" — the gateway now believes it holds more of `token` than it does, at the expense of whatever balance other users' orders have escrowed in that same token.

### Impact Explanation
This is a fund-loss bug reachable by any unprivileged user submitting a `placeOrder` transaction with a fee-on-transfer token as an input asset — no privileged role, admin, or governance action is required. Once the ledger is inflated:
- An order's cancellation (`cancelOrder` → `withdraw`) or destination-side fill/redemption pays out based on the recorded `_orders[commitment][token]` / `order.inputs` amount, not the contract's real balance. An attacker who places (and then cancels, or has filled) an order using a fee-on-transfer token can extract more tokens than they actually deposited, draining the shared pool at the expense of other legitimate users whose escrowed tokens are commingled in the same contract balance.
- This matches the FEG incident's root cause class: an accounting/balance-tracking divergence for a token with abnormal transfer semantics, exploitable within a single transaction flow to redeem more value than was actually deposited.

This meets the "concrete theft / permanent freezing of funds" bar in Validate, since honest users' escrow can become uncollectable once the shared balance is drained by the first attacker to cancel/redeem an inflated position.

### Likelihood Explanation
Any listed input token that charges a transfer fee (or is later found to, e.g., through a fee toggle by its own admin) triggers this on the very first `placeOrder` call — no special conditions, front-running, or governance compromise needed. The bug is a straightforward oversight relative to the parallel EVM implementation, which already implements the correct pattern, making the Tron divergence a clear, low-effort-to-trigger regression.

### Recommendation
Mirror the EVM implementation's pattern in the Tron `IntentGatewayV2.placeOrder` non-predispatch branch: snapshot `IERC20(token).balanceOf(address(this))` before and after each `safeTransferFrom`, and use the actual delta (not the nominal `order.inputs[i].amount`) both for the commitment hash and for the `_orders[commitment][token]` credit, exactly as already done for the predispatch path and in the reference EVM contract.

### Proof of Concept
1. Deploy a fee-on-transfer ERC20 (e.g., 1% fee on transfer) and have it accepted as a valid input asset for the Tron `IntentGatewayV2`.
2. Attacker calls `placeOrder` with `inputs[0] = {token: FOT, amount: 1000e18}` and no predispatch. `safeTransferFrom` moves only 990e18 into the gateway (1% burned/fee'd), but `_orders[commitment][FOT] += 990e18` (after only the protocol fee, not the token's own fee) is recorded as if ~990e18+ (or full 1000e18 if protocolFeeBps==0) was received — see lines 450-468.
3. Repeat with legitimate users' non-fee tokens or additional FOT orders sharing the same contract-held `FOT` balance.
4. Attacker cancels their order (`cancelOrder` → same-chain `withdraw`), which pays out based on the recorded (inflated) ledger amount, drawing down the shared `FOT` balance below what other orders are entitled to, leaving later legitimate cancellations/fills unable to be honored — realizing fund loss for other users.

Note: I was unable to view the full body of the Tron `withdraw`/`_withdraw` function within tool limits to cite the exact payout line, so the precise mechanics of the payout call could not be directly quoted; this should be verified against `evm/tron/contracts/apps/IntentGatewayV2.sol`'s `withdraw` implementation before remediation.

    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
