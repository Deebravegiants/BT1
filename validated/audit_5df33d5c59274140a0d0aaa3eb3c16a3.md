### Title
Withdrawal/recipient address `externalActionData.externalAddress` is never bound by the ZK proof or the on-chain "signed message", enabling front-run theft of a pending withdrawal - (File: contracts/Hinkal.sol, contracts/CircomDataBuilder.sol)

### Summary
`Hinkal.transact` verifies a Groth16 proof against a public-input vector built by `formBasicInput`, and additionally recomputes an EIP-712-style "signed message hash" via `getSignedMessageHash`. Neither the public-input vector nor the signed-message preimage includes `circomData.externalActionData` (in particular `externalAddress`), yet `_internalTransact`/`_externalTransact` use `circomData.externalActionData.externalAddress` directly as the destination of withdrawn/transferred funds. An unprivileged attacker who observes a valid, unmined `transact()` call can copy it, swap `externalAddress`, and resubmit with higher gas: the same proof and same public inputs still verify, but the funds go to the attacker.

### Finding Description
The equality that must hold is: *the address the contract pays out to == the address the circuit/prover committed to when the proof was generated*. Tracing the code shows this equality is never enforced:

- `formBasicInput` builds the exact `input[]` array passed to `verifyProof`; it contains `stealthAddressStructure`, `emporiumMessage`, `rootHashHinkal`, `getSignedMessageHash(...)`, `erc20TokenAddresses`, `amountChanges`, `inputNullifiers`, `timeStamp`, `outCommitments`, `calldataHash`, `H0x/H0y` — `externalActionData` is absent. [1](#0-0) 

- `getSignedMessageHash`, which is meant to bind the transaction to a signature checked inside the circuit, hashes `rootHashHinkal`, token addresses, `amountChanges`, `timeStamp`, nullifiers, `outCommitments`, `calldataHash`, `emporiumMessage`, and the stealth-address points — again, `externalActionData` is not part of the preimage. [2](#0-1) 

- `circomData.calldataHash` — the only field that, per `getHashedCalldata1`, actually hashes `externalActionData` — is taken **verbatim from calldata** and fed straight into the public-input vector and into `getSignedMessageHash`; `getHashedCalldata(circomData)` is never invoked anywhere in `Hinkal.sol` or `HinkalHelper.sol` to re-derive and check it against the submitted `circomData.externalActionData`. It is dead/unused validation logic. [3](#0-2) 

- In `Hinkal.transact`, `_internalTransact` uses `circomData.externalActionData.externalAddress` as both the deposit sender check and, critically, as the **withdrawal recipient** for funds whose *amount* is fixed by the proven `amountChanges[i]`, but whose *destination* is completely free: [4](#0-3) 

Because none of `verifyProof`'s public inputs, `getSignedMessageHash`, or any on-chain recomputation of `getHashedCalldata` constrain `externalAddress`, an attacker can take the exact `(a, b, c, dimensions, circomData)` tuple from a pending transaction, mutate only `circomData.externalActionData.externalAddress`, and resubmit. `verifyProof` still succeeds (identical `inputForCircom`), `rootHashExists` still succeeds, the balance-diff/slippage checks at lines 111-146 still succeed (they only check magnitude via `amountChanges`/`utxoAmount`, not destination), and `insertNullifiers` still consumes the original transaction's nullifiers — but `transferERC20TokenOrETH` now pays the attacker instead of the original submitter. If the attacker's copy lands first, the legitimate transaction later reverts on the duplicate-nullifier check, and the victim's funds are gone.

For the `_externalTransact` path, `externalAddress` is constrained to a registered `externalActionMap[externalActionId]` entry, so arbitrary redirection there is not possible — the vulnerability is isolated to the `_internalTransact` (plain withdraw/relay-fee) path where `externalActionId == 0`. [5](#0-4) 

### Impact Explanation
Direct theft of a victim's in-flight/shielded withdrawal: the attacker redirects the exact proven withdrawal amount to their own address by front-running or resubmitting a captured, still-valid transaction with a mutated `externalActionData.externalAddress`, while the nullifier still gets consumed against the victim's UTXO. This matches Critical severity ("direct theft of shielded or in-flight user funds ... proof or nullifier verification bypass") because the proof is accepted for state (the payout target) it never constrained. The attack is repeatable against any pending withdrawal transaction the attacker can observe in the mempool, and costs only gas plus a front-running bid.

### Likelihood Explanation
Preconditions: a `transact()` call for a plain internal withdrawal (`externalActionId == 0`, negative `deltaAmountChange`, i.e. a payout) must be visible before it's mined (public mempool, or a public relay endpoint that broadcasts the raw calldata before inclusion). The attacker needs no special privileges — any EOA can read mempool calldata and resubmit a modified copy with higher gas. This is a standard, low-cost front-running pattern and is fully repeatable for every future withdrawal transaction.

### Recommendation
Bind `externalActionData` (and specifically `externalAddress`) into a value that the circuit/signature actually constrains — e.g., include it directly in `formBasicInput`'s public-input vector, or actually invoke `getHashedCalldata(circomData)` on-chain and `require` it equals `circomData.calldataHash`, and additionally fold `calldataHash` (thus `externalActionData`) into `getSignedMessageHash`'s preimage so the circuit's signature check authenticates the recipient, not just the amounts/nullifiers.

### Proof of Concept
Foundry test plan:
1. Generate one valid proof/`circomData` for a plain withdrawal (`externalActionId == 0`, `amountChanges[i] < 0`, `externalActionData.externalAddress = victim`).
2. Submit tx A: `transact(a, b, c, dimensions, circomData)` with `externalAddress = victim` — do not mine yet.
3. Craft tx B: identical `a, b, c, dimensions`, identical `circomData` except `externalActionData.externalAddress = attacker`.
4. Mine tx B first. Assert: `verifyProof` returns true, `rootHashExists` passes, slippage/balance-diff checks at `Hinkal.sol` lines 111-146 pass, nullifiers are inserted, and `attacker` receives the withdrawn tokens.
5. Mine tx A second. Assert it reverts on duplicate-nullifier insertion, so `victim` receives nothing.
6. Assert the equality violated: `inputForCircom` (and `calldataHash`, `getSignedMessageHash` output) are bit-identical between tx A and tx B, while the actual on-chain effect (recipient of funds) differs — proving `externalActionData.externalAddress` is unconstrained by the proof/signature.
