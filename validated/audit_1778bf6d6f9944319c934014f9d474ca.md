### Title
Unbounded per-key state-proof verification before bandwidth metering in `GetRequestsWithProof` allows resource-exhaustion DoS - (File: `modules/pallets/state-coprocessor/src/impls.rs`)

### Summary
`pallet_state_coprocessor::handle_get_requests` accepts a `GetRequestsWithProof` payload containing an unbounded `Vec<GetRequest>`, each of which itself carries an unbounded `keys: Vec<Vec<u8>>` [1](#0-0) . For every request in the batch, the handler performs full merkle/trie membership verification via `verify_membership` and then `verify_state_proof` over every key, and only **after** all of that verification work is done does it consult the `BandwidthGate` to charge for the bytes consumed [2](#0-1) . This is the same bug class as the FastAsyncWorldEdit CVE: an unbounded, attacker-controlled size parameter ("Infinity"/large `keys`/`requests`) is used to drive expensive work before any resource accounting or rejection occurs.

### Finding Description
`handle_get_requests` runs source-proof membership verification for the whole batch of `requests` and then, in the response-proof loop, calls `dest_state_machine.verify_state_proof(&host, req.keys.clone(), state_root.state_root, &response)` for every request, iterating over every key in `req.keys` [3](#0-2) . Each key triggers trie-proof verification work (e.g. hashing and node-by-node validation in the underlying state machine's `verify_state_proof`, as seen for other state machines such as `modules/ismp/state-machines/pharos/src/lib.rs` and `modules/ismp/state-machines/evm/src/lib.rs`) [4](#0-3) .

Neither `GetRequest.keys` nor `GetRequestsWithProof.requests` is declared as a `BoundedVec` or checked against any maximum length before this expensive verification loop runs — no `MaxKeys`, `MaxRequestsPerBatch`, or similar bound was found anywhere in the codebase (a repo-wide grep for such constants only turned up bounds in the unrelated `BandwidthManager.sol`). The `BandwidthGate::try_consume` call, which is the only per-byte cost accounting mechanism, is deliberately placed *after* proof verification "so the value sizes are final," per the code's own comment [5](#0-4) . This means the gate cannot prevent the verification cost from being incurred — it can only refuse to pay a relayer for it after the fact.

This is reachable by the `handle_unsigned` extrinsic on `pallet-ismp`, which is explicitly documented as fee-less/permissionless ("This allows users execute ISMP datagrams for free. Use with caution.") and executes arbitrary submitted `Message`s, including responses/timeouts that could carry `GetRequestsWithProof`-shaped payloads through the state-coprocessor's own on-chain call surface [6](#0-5) . Test fixtures confirm `GetRequest.keys` can trivially be built with hundreds of 32-byte keys per request and up to a thousand requests per batch with no rejection at construction time [7](#0-6) , illustrating there is no structural limit stopping an attacker from submitting orders of magnitude more.

### Impact Explanation
An attacker who can get a `GetRequestsWithProof` (or equivalent) message processed — via a relayed message, an unsigned extrinsic, or any permissionless dispatch path that reaches `handle_get_requests` — can force validators/collators to perform an unbounded amount of trie-proof verification work (potentially thousands of keys × requests) before the runtime has any opportunity to reject the message for insufficient bandwidth or charge for the resources consumed. This is a resource-exhaustion (CWE-400) condition that can degrade or stall block production on the Hyperbridge chain, analogous to the FastAsyncWorldEdit advisory where an unbounded numeric input ("Infinity") drove unconstrained work before any check could reject it. Given this can affect consensus-critical extrinsic execution (block production/finality), the severity is Medium-to-High depending on the actual weight-metering enforced by the runtime's `#[pallet::weight]` annotations (which were not directly inspected in this pass).

### Likelihood Explanation
Likelihood is Medium: exploitation requires only constructing a message with a very large `keys`/`requests` vector and getting it into the message pipeline (e.g., via the free/unsigned `handle_unsigned` path or a relayed message), with no special privileges required. However, actual impact depends on how call weight is charged for this call in production runtimes (weight-based fee/DoS protection in Substrate could partially mitigate this if a sufficiently conservative worst-case weight is charged upfront) — this was not fully verified because the pallet's `#[pallet::call]`/weight definitions for the entry point invoking `handle_get_requests` were not located in this investigation.

### Recommendation
- Bound `GetRequestsWithProof.requests` and each `GetRequest.keys` with `BoundedVec`s tied to `Config::MaxRequestsPerBatch` / `Config::MaxKeysPerRequest` constants, rejected before any proof verification runs.
- Move (or duplicate) the `BandwidthGate::try_consume` check to run against a worst-case/declared byte estimate *before* `verify_membership`/`verify_state_proof` are invoked, so an unbandwidth-backed batch is rejected before expensive work is performed, not just left unpaid afterward.
- Ensure the dispatchable's declared `#[pallet::weight]` reflects the worst-case cost of the bound (not a fixed/underestimated weight), so weight-based DoS protections in the transaction pool/block builder are effective even before the runtime-level bound is reached.

### Proof of Concept
1. Construct a `GetRequestsWithProof` where `requests` contains `N` `GetRequest`s, each with `keys` containing `M` distinct 32/52-byte storage keys (there is no rejecting bound on either dimension, as confirmed by the 100-request × 256-key test fixtures in `pallet_call_decompressor.rs` which build and successfully decode/execute such payloads) [7](#0-6) .
2. Submit this payload through any path that reaches `pallet_state_coprocessor::handle_get_requests` (e.g., wrapped as a `Message` executed via `pallet_ismp::Pallet::execute`/`handle_unsigned`, which is explicitly fee-less) [6](#0-5) .
3. `handle_get_requests` will call `verify_membership` for the whole `N`-sized batch and then loop `N` times calling `verify_state_proof` with `M` keys each [8](#0-7) , performing `O(N*M)` trie-proof verifications, only failing/charging for bandwidth after all of that work is done [5](#0-4) .
