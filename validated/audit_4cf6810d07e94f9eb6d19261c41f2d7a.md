### Title
Fee-on-transfer/deflationary tokens allow escrow over-crediting in the Tron `IntentGatewayV2.placeOrder` - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder` computes the escrowed amount (`reducedInputs`) purely from the user-supplied `order.inputs[i].amount`, and in the non-predispatch path pulls tokens with a plain `safeTransferFrom` without ever measuring the actual balance received. For any pair token/ERC20 that charges a transfer fee (or is otherwise deflationary), the escrow ledger `_orders[commitment][token]` is credited for more than the tokens the contract actually holds, exactly analogous to the reported Olympus `SingleSidedLiquidityVault` issue where `amount_` is used for internal accounting instead of the actually-transferred balance.

### Finding Description
In `placeOrder`, `reducedInputs` (the amount stored on-chain per commitment) is derived only from `order.inputs[i].amount` minus the protocol fee — never from an observed balance: [1](#0-0) 

Then, in the non-predispatch escrow branch, the contract transfers tokens with a bare `safeTransferFrom` and immediately credits `_orders[commitment][token]` with `reducedInputs[i].amount` — without ever checking `balanceOf(address(this))` before/after the transfer: [2](#0-1) 

If `token` charges a transfer fee, the gateway actually receives `order.inputs[i].amount - fee`, but the escrow mapping is incremented by `reducedInputs[i].amount` (based on the full, pre-fee `order.inputs[i].amount`). This is the exact same root cause pattern as the referenced Olympus report: using the caller-supplied amount for internal bookkeeping instead of the balance actually transferred in.

Note the main EVM `IntentGatewayV2.sol` (non-Tron) was hardened against this exact issue — it snapshots `balBefore`, performs the transfer, and sets `order.inputs[i].amount = IERC20(token).balanceOf(address(this)) - balBefore` before computing `reducedInputs`/commitment: [3](#0-2) 

This fix was not ported to the Tron deployment, leaving it vulnerable.

Additionally, even the predispatch branch of the Tron contract computes `reducedInputs` from the nominal `order.inputs[i].amount` (line 362-370) rather than from the `balance` it later observes on the dispatcher (line 428), so the same under-collateralization can occur there too, though it is partially mitigated by the `balance < requiredAmount` revert check using the nominal `requiredAmount` rather than the fee-adjusted value.

### Impact Explanation
`_orders[commitment][token]` is the accounting record used later to release funds to a solver on `fillOrder`/escrow-redeem, or refund the user on cancellation/timeout. If this value is inflated beyond the token balance actually held by the contract, the gateway becomes insolvent for that token: legitimate solver payouts or refunds for other orders sharing the same token pool can fail or drain balances belonging to other users, since the contract believes it holds more of the fee-on-transfer token than it does. This is a direct fund-accounting/insolvency bug reachable by any unprivileged user simply by placing an order with a fee-on-transfer token as input — no special privileges required.

### Likelihood Explanation
Likelihood depends on the IntentGateway being deployed with support for fee-on-transfer/deflationary ERC20 tokens as order inputs on Tron. Since the codebase's own test suite explicitly demonstrates and expects fee-on-transfer token compatibility for the primary EVM `IntentGatewayV2` (see `evm/tests/foundry/IntentGatewayV2SameChainTest.sol` FOT tests), it indicates such tokens are within the expected threat model for this contract family, making the omission of the same protection on the Tron copy a realistic and directly triggerable issue whenever such a token is whitelisted/used as input.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: in the non-predispatch escrow branch, snapshot `balanceOf(address(this))` before `safeTransferFrom`, compute the actually-received amount as the post-transfer balance delta, and use that observed amount (not the nominal `order.inputs[i].amount`) as the basis for `reducedInputs` computation and for the `commitment` hash. Apply the analogous correction to the predispatch branch by deriving `reducedInputs` from the balance actually pulled onto the gateway/dispatcher rather than nominal input amounts.

### Proof of Concept
1. Deploy a 1%-fee ERC20 token (as in `FeeOnTransferToken` from `evm/tests/foundry/IntentGatewayV2SameChainTest.sol`) and register it as a valid input token on the Tron `IntentGatewayV2`.
2. User approves `intentGateway` for `1000e18` of the fee token and calls `placeOrder` with `order.inputs[0].amount = 1000e18` (no predispatch).
3. In `placeOrder`, `reducedInputs[0].amount` is computed as `1000e18 - protocolFee` (e.g. `1000e18` if `protocolFeeBps == 0`).
4. `IERC20(token).safeTransferFrom(msg.sender, address(this), 1000e18)` executes, but the gateway's actual balance only increases by `990e18` (1% fee taken).
5. `_orders[commitment][token] += reducedInputs[0].amount` credits `1000e18` even though the gateway only holds `990e18` of the token.
6. When a solver later fills the order and withdraws escrow, or the order is cancelled and refunded, the contract attempts to pay out `1000e18` from a pool that only received `990e18`, causing insolvency/underfunding that impacts other orders sharing the same token escrow.
