### Title
Arbitrary ERC1155 (and any `from == msg.sender`-gated) asset theft from Emporium via unauthenticated CASE-2 stateless calls - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction`'s CASE-2 "stateless" branch executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract, making Emporium itself `msg.sender` for that call [1](#0-0) . Since `Transferer` blindly accepts any ERC1155/ERC721 token into Emporium via unconditional `onERC1155Received`/`onERC1155BatchReceived` selectors [2](#0-1) , and the balance-diff accounting in `runAction`/`Hinkal.transact` only tracks `circomData.erc20TokenAddresses` (ERC20/ETH) [3](#0-2) [4](#0-3) , any unprivileged attacker can craft their own `transact()` call whose Emporium `EmporiumStack` op calls `vault1155.safeTransferFrom(Emporium, attackerEOA, id, amount, "")`, which passes ERC1155's `from == _msgSender()` check because Emporium is the caller, silently draining any ERC1155 balance held by Emporium regardless of who originally deposited it.

### Finding Description
Claimed equality: `ERC1155 balance of Emporium for (id) contributed by victim == redeemable only by victim's stealth address`.

This is false because Emporium never records any linkage between an ERC1155 receipt and a stealth address/UTXO — the only accounting Emporium performs is over the fungible `circomData.erc20TokenAddresses`/ETH balances before and after `runAction` [5](#0-4) . An ERC1155 token minted to Emporium by a victim's `vault1155.deposit(amount)` call (CASE-2, `op.endpoint.call` with `from = msg.sender = Emporium`) sits in Emporium's balance completely outside the private UTXO/merkle-tree system.

Exploit path:
1. Victim executes `transact()` with an Emporium `EmporiumStack.ops` entry calling `vault1155.deposit(amount)` (CASE-2, `stack.signerAddress == address(0)` so `verifyWallet` only marks `usedMessages` and returns early without any signature check) [6](#0-5) . This mints the ERC1155 receipt to `msg.sender = Emporium` because Emporium itself performs the low-level call.
2. Attacker — an unprivileged user who can generate proofs for their own UTXOs and call `Hinkal.transact()` (the only requirement is being a caller of a registered `externalActionMap` address, which any user satisfies by simply invoking `transact()` since Hinkal is the `onlyAllowedRecipient` caller of `runAction`) [7](#0-6) [8](#0-7)  — submits their own valid, unrelated CircomData/proof (e.g., zero `amountChanges` on an arbitrary ERC20) with `externalActionData.externalAddress = Emporium` and `externalActionMetadata` encoding an `EmporiumStack` with `signerAddress = address(0)` and one op: `{endpoint: vault1155, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC1155.safeTransferFrom, (Emporium, attackerEOA, id, amount, ""))}`.
3. `runAction` executes `op.endpoint.call(op.callData)` from Emporium; `vault1155.safeTransferFrom` checks `from == _msgSender()`, and since Emporium is the caller and `from = Emporium`, this passes trivially — no approval, no signature, no relation to the victim is required.
4. Because `vault1155` is not in `circomData.erc20TokenAddresses`, none of the balance-diff/slippage checks in `Hinkal.transact` (lines 78-114) or `runAction` (lines 122-151) observe or block this transfer.

Existing guards fail because: `performHinkalChecks`, `verifyProof`, `rootHashExists`, and the slippage/balance checks all operate over the attacker's own legitimate (and irrelevant) ERC20/UTXO inputs — none of them constrain arbitrary `EmporiumOperation.callData` targets or ERC1155/ERC721 assets, and `UnauthorizedWalletCall` only blocks `callHinkalWallet`/`doSendToRelay` selectors, not arbitrary third-party contract calls [9](#0-8) .

### Impact Explanation
Critical: theft of shielded/deposited value represented as ERC1155 (or any other asset gated only by `from == msg.sender`, e.g. ERC721 `transferFrom` by owner, ERC20 tokens without transferFrom-approval semantics) held by Emporium, stolen by any attacker regardless of who deposited it. This is direct, repeatable theft of user funds routed through Hinkal's Emporium external action, with the attacker paying only their own unrelated gas/proof cost per drain.

### Likelihood Explanation
Preconditions: Emporium must hold an ERC1155 (or similarly gated) balance, which happens whenever any user (victim or even the attacker previously) uses a CASE-2 op that mints/transfers such assets to Emporium — a normal, expected usage pattern given `Transferer` unconditionally accepts them. The attack costs the attacker only a standard `transact()` call with their own valid proof; no special privilege, victim cooperation, or victim signature is needed since `signerAddress = address(0)` bypasses EIP-712 signature verification entirely. Fully feasible and repeatable for every ERC1155/ERC721 balance sitting in Emporium.

### Recommendation
Restrict CASE-2 stateless `op.callData` to a strict allow-list of function selectors/targets (e.g., only swap/vault deposit functions that do not require `from == msg.sender`), or require `stack.signerAddress != address(0)` with the deposit contract/victim's explicit signature covering `ops` before allowing any state-changing call that could move assets already custodied by Emporium. Additionally, track and account for non-fungible/semi-fungible assets received by Emporium the same way ERC20/ETH balances are tracked (bind them to `stealthAddressStructure` via UTXO-like commitments), and disallow blind acceptance of ERC721/ERC1155 tokens (`onERC721Received`/`onERC1155Received`) unless the deposit is immediately linked to an outgoing UTXO commitment in the same transaction.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (proxy), and a mock `ERC1155` "vault" token with a `deposit(uint256 amount)` that mints `id=1` to `msg.sender` and standard OZ `safeTransferFrom`.
2. Register Emporium as `externalActionMap[id]` and as an allowed recipient.
3. Victim transaction (transact #1): construct `CircomData` with `externalActionData` pointing to Emporium, `externalActionMetadata` encoding `EmporiumStack{signerAddress: address(0), ops: [{endpoint: vault1155, invokeWallet:false, value:0, callData: abi.encodeCall(vault1155.deposit, (100))}]}`. Fund Emporium's underlying token balance so `vault1155.deposit` succeeds. Assert `vault1155.balanceOf(Emporium, 1) == 100`.
4. Attacker transaction (transact #2): from a fresh unprivileged EOA with its own unrelated valid dummy proof/UTXO (e.g., zero `amountChanges`), construct `CircomData` with the same Emporium external action, `EmporiumStack{signerAddress: address(0), ops: [{endpoint: vault1155, invokeWallet:false, value:0, callData: abi.encodeCall(vault1155.safeTransferFrom, (Emporium, attackerEOA, 1, 100, ""))}]}`.
5. Assert before: `vault1155.balanceOf(Emporium, 1) == 100 && vault1155.balanceOf(attackerEOA, 1) == 0`.
6. Assert after attacker's `transact()` call succeeds: `vault1155.balanceOf(Emporium, 1) == 0 && vault1155.balanceOf(attackerEOA, 1) == 100`, proving the equality `ERC1155 balance of Emporium (id=1) contributed by victim == redeemable only by victim's stealth address` is violated — the attacker, not the victim, redeemed it.
