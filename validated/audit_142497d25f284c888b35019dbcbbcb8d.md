Webhook `shop` field is trusted by the app but not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature verified by `ShopifyAPI::Utils::HmacValidator` is computed only over the raw request body. Any merchant who has legitimately installed the app (and therefore possesses one authentic, correctly-signed webhook delivery, signed with the app's shared `api_secret_key`) can replay that same body/HMAC pair while substituting the `shop-domain` header with a victim shop's domain. `Registry.process` accepts the request as valid and hands the attacker-controlled `shop` value straight to the app's webhook handler as an authenticated fact, breaking the identity binding `authenticated_bytes == trusted_shop_identity`.

### Finding Description
- `Request#hmac` reads the signature from the `hmac-sha256` header, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 
- `Request#shop` reads directly from the `shop-domain` header, which is not part of the signable string at all: [3](#0-2) 
- `HmacValidator.validate` verifies only `verifiable_query.to_signable_string` (the body) against the shared `api_secret_key`; it never touches `shop`: [4](#0-3) 
- `Registry.process` gates only on this HMAC check, then constructs `WebhookMetadata` using `request.shop` as the trusted tenant identifier and forwards it to the app-defined handler: [5](#0-4) 
- `WebhookMetadata#shop` is a plain `String` field with no further validation, and the documentation explicitly instructs integrators to treat `data.shop` as "The shop domain of the webhook" and use it to key their own data (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [6](#0-5) [7](#0-6) 

Because `api_secret_key` is one shared secret per app (not per shop), any tenant that has the app installed can generate one authentically-signed webhook (e.g. by triggering an event on their own store) and capture the `raw_body` + `hmac-sha256` value. The attacker can then send that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint again, but with the `shop-domain` header rewritten to a different (victim) shop. `HmacValidator.validate` still succeeds because it only checks the body's HMAC, and `Registry.process` will dispatch the payload to the handler tagged with the attacker-chosen `shop`, exactly as if Shopify itself had sent that event for the victim's store.

Equality broken: `hmac_verified(raw_body) == true` is treated as implying `trusted_shop == header_shop`, but the header `shop` is never part of the signed material, so `trusted_shop` and `header_shop` are independent.

### Impact Explanation
This is a cross-tenant identity-binding break: an app built on this gem, following its documented API exactly as shown in `docs/usage/webhooks.md`, will process a spoofed webhook as if it originated from a shop the attacker does not own or control. Any downstream logic that keys writes/lookups off `data.shop` (persisting order/product/customer data, updating settings, triggering shop-scoped side effects) can be poisoned with attacker-supplied content attributed to a victim tenant — a cross-tenant data-integrity/confidentiality violation reachable by any unprivileged internet user who merely has the app installed on one shop.

### Likelihood Explanation
Likelihood is high for any app that installs this gem and follows its documented webhook usage exactly as shown: any of the app's own merchants (an "unprivileged" tenant relative to other tenants) can trivially capture one authentic webhook body+HMAC (by triggering a webhook-generating action on their own store) and replay it with a forged `shop-domain` header using a normal HTTP client — no access to `api_secret_key`, access tokens, or any other credential is required beyond being a legitimate but unprivileged installer of the app.

### Recommendation
- Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signed material, or otherwise cryptographically bind them to the body, so signature validity implies the header-derived shop is authentic.
- At minimum, document and/or enforce in `Registry.process` that consumers must cross-check `request.shop` against the set of shops that have valid, currently-installed sessions/tokens for this app before trusting `WebhookMetadata#shop`, since the header is unauthenticated by this gem's own signature check.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; attacker triggers any subscribed webhook topic (e.g. `orders/create`) on their own store and captures the exact raw POST body and its `x-shopify-hmac-sha256` header value — both are valid because they were genuinely signed by Shopify with the app's shared `api_secret_key`.
2. Attacker resends an HTTP request to the app's webhook endpoint with:
   - the same `raw_body`
   - the same `x-shopify-hmac-sha256`
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - `x-shopify-topic` set to the desired topic
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `raw_body`: [8](#0-7) 
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built with `shop == "victim-shop.myshopify.com"` and passed to the app's handler, which — per the documented pattern — persists/acts on data keyed by `data.shop`, now poisoned with attacker content attributed to the victim tenant. [9](#0-8)
