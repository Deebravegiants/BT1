### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, allowing tenant-spoofed replay of a legitimately-signed webhook body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `Utils::HmacValidator.validate` verifies the HMAC against that body alone. The `shop`, `topic`, `webhook_id`, and `api_version` values that `Registry.process` uses to dispatch and attribute the webhook to a tenant are read directly from HTTP headers, which are never part of the signed material. An attacker who can obtain one authentic `(body, hmac)` pair from Shopify can replay it with an arbitrary `x-shopify-shop-domain` header and have it accepted as authentic for a different shop.

### Finding Description
`Utils::HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and does a constant-time compare against the request's `hmac` field. [1](#0-0) 

For webhooks, `to_signable_string` is defined as just the raw HTTP body (`@raw_body`), while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers and are not included in the signed string at all: [2](#0-1) 

`Registry.process` validates the HMAC of the request and then dispatches to a handler using `request.shop` (and `request.topic`) taken from the unauthenticated headers: [3](#0-2) 

This breaks the intended identity binding: **shop authenticated by the HMAC (which is silent on tenant identity) ≠ shop attributed to the webhook payload by `WebhookMetadata.shop`**. Contrast this with the OAuth flow's `AuthQuery`, where `shop` *is* explicitly included inside `to_signable_string` and therefore is bound by the HMAC: [4](#0-3) 

Because the webhook `Request`'s signable string omits `shop`/`topic`/`webhook_id`/`api_version`, the HMAC check only proves "Shopify (or holder of the secret) produced this exact body," not "this body belongs to this shop, this topic, or this webhook id." Any party capable of observing one legitimate `(raw_body, hmac)` pair (e.g., their own store's webhook delivery, which per Shopify's docs is delivered to a merchant/developer-controlled endpoint) can resend that exact body/HMAC pair to the same endpoint while substituting a different `x-shopify-shop-domain` value. `HmacValidator.validate` will still return `true` because the signature only ever covered the (unchanged) body, and `Registry.process` will hand the payload to the handler tagged with the attacker-chosen `shop`.

The `WebhookMetadata` struct that is delivered to the host application's handler carries this spoofed `shop`: [5](#0-4) 

Host applications are documented/expected to key their tenant data and session lookups (e.g., which shop's local database row to update, or which access token/session to associate with `customers/redact`, `shop/redact`, GDPR topics, order/customer create events, etc.) by `data.shop`, since that is the only tenant identifier the gem exposes in the metadata. Because this gem's own `HmacValidator` never binds `shop` to the signature, the trust boundary between "an authentic Shopify webhook body" and "the shop it is attributed to" is broken entirely inside this library, before it even reaches host application code — this is not a case of the host ignoring documented API, it's the gem asserting a shop identity that its own verification step never checked.

### Impact Explanation
This allows cross-tenant confusion at the point where the gem verifies and forwards webhook data: a request that is cryptographically valid only for shop A's payload can be delivered to the handler as if it belongs to shop B. Depending on how the host processes `data.shop` (which is the only field this gem's API surface offers for shop attribution), this can result in cross-tenant data corruption or disclosure — e.g., writing shop-A's order/customer payload into shop-B's tenant record, or triggering `shop/redact`/`customers/redact` processing against the wrong tenant. This falls under "cross-tenant access," matching the Critical impact category, because the binding broken is exactly `shop authenticated (by HMAC) == shop used for tenant/session identification` as called out in the report's identity-binding categories.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one authentic `(raw_body, hmac)` webhook pair, which is trivial to obtain — any merchant/developer running the app receives such pairs continuously through normal Shopify webhook delivery to their own registered endpoint. No access token, `api_secret_key`, or privileged credential is required; the attacker only needs to replay an HTTP POST with a substituted `shop-domain` header to the shared webhook endpoint. This is a realistic, unprivileged-internet-user-reachable path through the gem's own verification code, not a theoretical concern.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the request the same way `AuthQuery#to_signable_string` binds `shop` for OAuth. At minimum, `Webhooks::Request#to_signable_string` should not silently return only the body while `Registry.process` trusts unrelated, unauthenticated headers for dispatch and tenant attribution.

### Proof of Concept
1. Attacker installs/operates the app on their own shop (`attacker-shop.myshopify.com`) and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a webhook to the attacker's endpoint with a real body `B` and valid header `x-shopify-hmac-sha256: HMAC(secret, B)`.
3. Attacker resends the identical `B` and identical HMAC header to the same public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` from `to_signable_string` (which is just `B`) and it matches, so validation succeeds: [6](#0-5) 
5. `Registry.process` proceeds and calls the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body(B), ...)`: [7](#0-6) 
6. The host application processes attacker-controlled order/customer data as if it originated from `victim-shop.myshopify.com`, achieving cross-tenant data injection with no valid credentials for the victim shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
