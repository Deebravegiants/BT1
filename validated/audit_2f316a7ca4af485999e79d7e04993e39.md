This confirms the finding: `WebhookMetadata.shop` (used by host apps to key sessions/tenant data) is populated directly from `request.shop`, which reads the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, while the HMAC signature only covers the raw request body.### Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating only the HMAC over the raw request body, but the tenant identity (`shop`) it passes on to the host application's handler is read from an unauthenticated HTTP header. This breaks the intended binding: `shop verified by HMAC == shop acted upon`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed content: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC solely against `verifiable_query.to_signable_string` (i.e., the body), never against the shop header: [3](#0-2) 

`Registry.process` accepts the request once the body HMAC checks out, then constructs `WebhookMetadata` using the unauthenticated `request.shop` value and hands it to the host application's handler as the trusted tenant identifier: [4](#0-3) [5](#0-4) 

This is the exact bug class from the report generalized to an identity binding: the equality that should hold is `shop covered by HMAC == shop delivered to handler`, but here `shop covered by HMAC` is empty (only body bytes are signed) while `shop delivered to handler` is attacker-controlled header content. Compare this to `Auth::Oauth::AuthQuery#to_signable_string`, which *does* fold `shop` and `host` into the signed parameter set before HMAC validation, correctly binding those fields: [6](#0-5) 
The webhook path has no equivalent binding for `shop`.

### Impact Explanation
An unprivileged party who is able to obtain (or replay) any single valid `(raw_body, hmac)` pair signed with the app's `api_secret_key` — for example a webhook legitimately delivered to their own shop by Shopify, which they fully control the receipt of — can resend that same body/HMAC to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. Because `HmacValidator.validate` never inspects the shop header, the forged request passes verification, and `Registry.process` hands the host application a `WebhookMetadata` claiming the payload originated from the victim shop. Any host application that uses `WebhookMetadata#shop` to key session lookup, per-tenant data writes, or trust decisions (this is the documented purpose of the field, and the pattern shown throughout `docs/usage/webhooks.md` and the test suite) will process attacker-supplied data under a different tenant's identity — a cross-tenant data confusion inside a multi-tenant app's webhook pipeline. This matches the Critical "cross-tenant access" impact category in the rules.

### Likelihood Explanation
Exploitation does not require the `api_secret_key` or any privileged credential — it only requires an attacker to control one shop where the app is installed (or capture one legitimate webhook delivery), which is a normal unprivileged position for an "internet user" testing a public app. Webhook endpoints are unauthenticated public HTTP endpoints by design, and nothing in this gem restricts which shop-domain header may accompany a validly-HMACed body. Likelihood is Medium-High: the primitive (replay same body under a different shop header) is straightforward, though actual damage still depends on how a specific host application uses `WebhookMetadata#shop`.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook-id`) into the value verified by the HMAC, e.g., include the shop-domain header (and other identity-bearing headers) in `Webhooks::Request#to_signable_string`, or independently verify the shop header against a value derived from the signed body/session before trusting it. At minimum, document prominently that `WebhookMetadata#shop` is not covered by HMAC verification and must not be used as a sole tenant-identity source without additional validation (e.g., cross-checking against an already-known session for that topic).

### Proof of Concept
```ruby
# Attacker controls "attacker-shop.myshopify.com" and receives a legitimate webhook from Shopify:
raw_body = '{"id":123,"note":"hello"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
# (attacker obtains this hmac because it is delivered to their own store's webhook endpoint)

# Attacker replays the same body+hmac to the app's public webhook endpoint,
# but swaps the shop-domain header to a victim shop:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged, not covered by HMAC
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (only raw_body is checked)
# => handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: parsed attacker body, ...)
```
The host application's handler now believes attacker-controlled data legitimately originated from `victim-shop.myshopify.com`.
