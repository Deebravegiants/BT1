### Title
Webhook topic and shop identity are unauthenticated header values not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Request#initialize` only requires that `x-shopify-topic`, `x-shopify-hmac-sha256`, and `x-shopify-shop-domain` headers be *present*; it never binds their values to the HMAC signature. `Utils::HmacValidator.validate` (via `to_signable_string`) verifies only `@raw_body` [1](#0-0) , so `topic` and `shop` returned by the accessors are trusted purely from attacker-visible headers [2](#0-1) . Anyone who obtains one validly-signed webhook body (trivially, from their own installed development shop) can relabel it with an arbitrary `x-shopify-topic` and `x-shopify-shop-domain` and have `Registry.process` dispatch it to any registered handler under a forged shop identity, since only the raw body is HMAC-checked [3](#0-2) .

### Finding Description
The claimed invariant is: `HMAC(secret, raw_body) == received_hmac` implies `(topic, shop, raw_body)` as a triple is authentic and attributable to the shop named in `shop-domain`. Tracing the code shows this equality never holds for `topic` or `shop`:

- `Request#initialize` normalizes headers and only checks for the *presence* of `topic`, `hmac-sha256`, and `shop-domain` — it does not validate their contents or bind them to anything [4](#0-3) .
- `to_signable_string` returns `@raw_body` only [1](#0-0) , and `HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to `verifiable_query.hmac` [5](#0-4) . Neither `topic` nor `shop` participates in the signed material.
- `Registry.process` uses `request.topic` purely from the header to select the handler, and forwards `request.shop` (also purely from the header) into `WebhookMetadata` as the shop identity handed to the app's handler [3](#0-2) .
- No `ShopValidator.sanitize!` or equivalent check is applied to the webhook `shop-domain` header anywhere in this path — that utility is only used in the OAuth/token-exchange flows (`lib/shopify_api/auth/token_exchange.rb`, `client_credentials.rb`, `refresh_token.rb`), not in `Webhooks::Request` or `Registry`.

Attacker flow: create a development shop, install the app, trigger a real event (e.g. `products/create`) to receive one HMAC-valid `(raw_body, hmac)` pair from Shopify. Replay that exact body+HMAC to the app's public webhook endpoint, but substitute `x-shopify-topic: shop/redact` (or any other registered topic) and `x-shopify-shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` still passes because it only checks the untouched `raw_body`/`hmac` pair; `Registry.process` then dispatches to the handler registered for the forged topic and hands it a `WebhookMetadata` claiming the victim's shop identity [6](#0-5) . Any host-app handler that trusts `WebhookMetadata#shop` to look up a session/access token or take a destructive/administrative action (GDPR redact, uninstall cleanup, token revocation, etc.) will act against the wrong tenant using attacker-forged identity — breaking the SINGLE IDENTITY invariant since the shop attribute is not derived from any authenticated source.

### Impact Explanation
This allows cross-tenant confusion: an unprivileged attacker with only their own shop's valid signature can cause an app's webhook handlers to run under a topic and shop identity of their choosing, for any merchant domain string, without ever possessing that merchant's secret. Because handlers commonly use the `shop` field to fetch/act on that merchant's session or access token (e.g., mandatory GDPR/uninstall webhooks), this can drive actions against, or trigger token-management logic for, an arbitrary victim shop the attacker names — matching the "cross-tenant access" Critical category. It is fully repeatable per captured signed body and against any shop domain string the attacker chooses to type into the header.

### Likelihood Explanation
Low cost, no privileged secrets required: attacker only needs their own dev shop (freely creatable) and the ability to send arbitrary HTTP headers to the app's public webhook endpoint, both of which are explicitly in the unprivileged attacker's capability set. The precondition is that the host app's handler logic actually keys sensitive behavior off `WebhookMetadata#shop`/`#topic` without independent server-side confirmation — a common but not universal pattern for mandatory compliance webhooks. Feasibility is high; repeatability is unlimited (one captured signed body can be relabeled indefinitely).

### Recommendation
Bind `topic` and `shop-domain` (and ideally `webhook-id`) into the signable string / HMAC computation, or otherwise cryptographically bind them (e.g. Shopify's actual production behavior relies on TLS+trusted delivery from Shopify's servers, but this gem's abstraction should not present forgeable header values as trustworthy identity fields without documentation). At minimum, apply `ShopValidator.sanitize!` to `Request#shop` and document clearly that `Request#topic`/`Request#shop` are unauthenticated header echoes that consuming applications must not treat as verified identity beyond what `HmacValidator.validate` covers (raw body integrity only).

### Proof of Concept
```ruby
# test/webhooks/topic_shop_confusion_test.rb
require "test_helper"

class TopicShopConfusionTest < Test::Unit::TestCase
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.clear
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "products/create", delivery_method: :http, path: "/webhooks",
      handler: (@safe_handler = mock_handler),
    )
    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "shop/redact", delivery_method: :http, path: "/webhooks",
      handler: (@sensitive_handler = mock_handler),
    )
  end

  def test_relabelled_topic_and_shop_dispatch_with_same_hmac
    raw_body = '{"id":1}'
    hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), "secret", raw_body)
    )

    # Legitimately signed for products/create + attacker's own shop
    legit_headers = {
      "x-shopify-topic" => "products/create",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "attacker-dev.myshopify.com",
    }
    legit_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: legit_headers)
    assert ShopifyAPI::Utils::HmacValidator.validate(legit_request)

    # Same raw_body + same hmac, but relabelled topic/shop
    forged_headers = {
      "x-shopify-topic" => "shop/redact",
      "x-shopify-hmac-sha256" => hmac,
      "x-shopify-shop-domain" => "victim-shop.myshopify.com",
    }
    forged_request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

    # Binding under test: HMAC validity should not be independent of topic/shop
    assert ShopifyAPI::Utils::HmacValidator.validate(forged_request) # PASSES -> proves the break

    @sensitive_handler.expects(:handle).with(
      data: has_attributes(topic: "shop/redact", shop: "victim-shop.myshopify.com"),
    )
    ShopifyAPI::Webhooks::Registry.process(forged_request)
  end
end
```
Both `legit_request` and `forged_request` share identical `raw_body`/`hmac`, yet `HmacValidator.validate` returns `true` for both and `Registry.process` dispatches the *sensitive* handler under an attacker-chosen `shop` value — demonstrating the topic/shop identity is not bound to the authenticated content.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
