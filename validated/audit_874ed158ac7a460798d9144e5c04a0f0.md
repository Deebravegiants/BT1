Based on the code analysis, I found a genuine identity-binding gap in the webhook verification path.

### Title
Webhook `shop` (and `topic`/`webhook_id`) header trusted by `Registry.process` is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes/exposes the HMAC over the raw body only, while `shop`, `topic`, `webhook_id`, and `api_version` are read from HTTP headers that are never part of the signed payload. `Registry.process` validates only the body HMAC and then hands the unauthenticated header value of `shop` to the app's webhook handler as the authoritative tenant identity, breaking the equality `hmac_signed_bytes == bytes_acted_on`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `webhook_id`, `api_version` are all pulled from headers via `shopify_header`, none of which are included in `to_signable_string`: [2](#0-1) 

`Registry.process` validates the request solely with `Utils::HmacValidator.validate(request)` (i.e., only the body HMAC), and then immediately constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` header values, passing them to the app-supplied handler as trusted identity/routing data: [3](#0-2) 

`HmacValidator.validate` confirms it only ever signs/verifies `verifiable_query.to_signable_string`, so for a `Webhooks::Request` that check is body-only: [4](#0-3) 

Because `api_secret_key` is a single per-app secret shared across every shop that has installed the app (not a per-shop key), any tenant that has installed the app can compute (or simply replay) a body+HMAC pair that is valid for the shared secret, and then submit that exact body/HMAC to the app's webhook endpoint while freely setting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers to arbitrary values. `Request#initialize` only checks that the required headers are *present*, not that they are bound to the signed content: [5](#0-4) 

`HmacValidator.validate` will still return `true` because it recomputes and compares the HMAC over `@raw_body` alone, which the attacker did not alter.

### Impact Explanation
This breaks the binding `shop-header-authenticated == shop-value-acted-on` for any host application that follows the documented pattern of trusting `WebhookMetadata#shop`/`#topic`/`#webhook_id` returned from `Registry.process`/`WebhookHandler#handle` as the tenant/routing identity once `HmacValidator.validate` succeeds. A single compromised or malicious merchant install of the app can forge webhook deliveries that the app attributes to a *different* tenant (or a different topic than what was actually signed), enabling cross-tenant data injection/confusion in any handler that keys per-shop side effects (e.g., updating shop-specific state, triggering shop-scoped actions) off the unauthenticated `shop` field. This matches the Critical "cross-tenant access" impact category, since the HMAC check gives false assurance that the entire webhook (including its declared shop and topic) is authentic when in fact only the body bytes are.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must already control one legitimate installation of the target app (to obtain a body+HMAC pair valid under the shared `api_secret_key`) and must be able to reach the host application's webhook endpoint directly (bypassing Shopify's IP/TLS-authenticated relay, which this gem cannot enforce). Given those preconditions — realistic for any malicious/compromised merchant of a multi-tenant app — forging the header values is trivial since `Request` performs no cross-check between headers and signed body.

### Recommendation
Bind the identity-relevant headers into the HMAC-verified payload, or otherwise cryptographically or contextually re-verify `shop`/`topic`/`webhook_id` before trusting them in `WebhookMetadata`. Concretely, extend `Request#to_signable_string` (or add a secondary check in `Registry.process`) to incorporate `shop`, `topic`, and `webhook_id` so that `HmacValidator.validate` fails if any of these headers are altered independently of the signed body, closing the gap between what is verified and what is acted upon.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and receives a legitimate webhook delivery: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for shared `api_secret_key`), `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker replays the exact same `(B, H)` pair directly to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and/or a different `X-Shopify-Topic`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `raw_body` (`B`) only — matches `H` — validation passes: [6](#0-5) 
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is built from the attacker-controlled headers and dispatched to the app's handler as if it were an authentic webhook for `victim-shop.myshopify.com`: [7](#0-6)

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
