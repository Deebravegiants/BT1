### Title
Phantom bid aggregation weights and haircuts Uniswap V4 positions using live spot `sqrtPriceX96`, letting a manipulated pool skew the published intent price - (File: `sdk/packages/sdk/src/protocols/intents/uniswap-v4-position.ts`)

### Summary
`positionAmountOfToken()` / `getAmountsForLiquidity()` in `uniswap-v4-position.ts` value a solver's declared Uniswap V4 position using the pool's current `sqrtPriceX96` — a live spot price read at bid-aggregation time — with no TWAP or deviation check applied at this layer. This mirrors the reported `OmoOracle.getLiquidityAmounts()` bug class: liquidity/position value derived from `slot0`-style spot price is vulnerable to manipulation.

### Finding Description
`getAmountsForLiquidity` reproduces Uniswap's `LiquidityAmounts.getAmountsForLiquidity` math directly off a caller-supplied `sqrtPriceX96` [1](#0-0) , and `positionAmountOfToken` uses that function to compute how much of the leg's output token a solver's declared position is worth [2](#0-1) .

This valuation feeds directly into `runAggregation` in `phantom-aggregation.ts`, which reads a declared Uniswap V4 position via `memoizedV4Position` (one live on-chain read per position, reused per leg) and uses it to weight and price a solver's bid in the liquidity-weighted median that becomes the published, executable phantom order price [3](#0-2) . A quote backed by a declared V4 position is only discounted by a flat `UNISWAP_QUOTE_HAIRCUT_BPS` (10bps) intended to approximate pool-fee cost, not price-manipulation risk [4](#0-3) . Nowhere in this path is a TWAP consulted or a deviation guard enforced — the documented Simplex "Uniswap price guard" (`referencePrice`/`maxDeviationBps`) is a separate, opt-in mitigation that lives only in the solver-side Simplex funding/pricing config [5](#0-4) , and is not applied inside the SDK's `phantom-aggregation.ts` valuation/weighting path that determines the published median for the order.

The `venue-pricing-uniswap-v4-funded-pairs.md` flow doc corroborates that even the guarded Simplex path uses the "raw pool mid derived from `sqrtPriceX96`" with no execution-cost or size-impact term, and the guard only checks static-reference deviation, not liquidity/manipulation resistance [6](#0-5) .

### Impact Explanation
A colluding or malicious "solver" can flash-loan-manipulate a thinly liquid Uniswap V4 pool backing its declared position right before/within the bid window, inflating the spot `sqrtPriceX96` so that `positionAmountOfToken` reports outsized weight/value for its bid. Because the leg price is set by `weightedMedian` of backed quotes — and a bidder holding over half the leg's weight sets the published price verbatim [7](#0-6)  — inflating the declared position's weight can let an attacker dominate the median and force the published phantom-order price to a manipulated value that downstream `quoteIntent` callers and fillers treat as the tradeable market rate [8](#0-7) . This can result in intents being quoted/filled at an unbacked, manipulated exchange rate, causing fund loss for takers or the protocol's fee/reward accounting.

### Likelihood Explanation
Medium: requires the attacker to (a) control or collude with a solver account able to submit a verified phantom bid, and (b) manipulate a Uniswap V4 pool used as a declared position within the same block/window as the bid (feasible via flash loan against low-liquidity pools). The 10bps haircut and destination-chain output-token balance weighting reduce but do not eliminate the incentive, since the weight itself (not just the price) is derived from manipulable spot state.

### Recommendation
Use a time-weighted or otherwise manipulation-resistant price (e.g., Uniswap V4 pool TWAP oracle, or a deviation check against an external reference price such as the indexer's own aggregated rate) when computing `positionAmountOfToken`/`getAmountsForLiquidity` inside the phantom bid aggregation path, rather than relying solely on the instantaneous `sqrtPriceX96` read at aggregation time. Additionally, enforce the equivalent of Simplex's `referencePrice`/`maxDeviationBps` guard directly in `phantom-aggregation.ts` so a manipulated pool cannot influence the weighted median regardless of whether the aggregator is Simplex or another indexer consumer.

### Proof of Concept
1. Attacker deploys/uses a low-liquidity Uniswap V4 pool and holds a small position in it, then declares that position's `tokenId` in a phantom bid's `paymasterAndData` (`uniswapV4Positions`).
2. In the same block as bid submission, attacker flash-loan-swaps in the pool to move `sqrtPriceX96` far from the fair price.
3. `runAggregation` reads the position via `memoizedV4Position`, and `positionAmountOfToken` (using `getAmountsForLiquidity` at the manipulated `sqrtPriceX96`) reports an inflated output-token amount/weight for the bid [2](#0-1) .
4. The bid's inflated weight lets it dominate `weightedMedian`, and only a flat 10bps haircut is applied, not a manipulation check [9](#0-8)  (approx.).
5. The published `LiquidityPool.buyRate`/`sellRate`, derived from this median, is now skewed, and subsequent `quoteIntent` calls price real intents off the manipulated rate [8](#0-7) .

Note: I was unable to fully inspect `memoizedV4Position`'s exact on-chain read call (e.g., whether it calls `StateView.getSlot0` directly) due to tool-call limits reached before retrieving `UniswapV4LiquidityState.ts`/full `phantom-aggregation.ts` definition — this should be verified in a follow-up session to confirm there is no TWAP fallback already wired into that specific function.

export function getAmountsForLiquidity(params: {
	sqrtPriceX96: bigint
	sqrtRatioAX96: bigint
	sqrtRatioBX96: bigint
	liquidity: bigint
}): { amount0: bigint; amount1: bigint } {
	let { sqrtRatioAX96, sqrtRatioBX96 } = params
	const { sqrtPriceX96, liquidity } = params
	if (sqrtRatioAX96 > sqrtRatioBX96) [sqrtRatioAX96, sqrtRatioBX96] = [sqrtRatioBX96, sqrtRatioAX96]

	const amount0For = (from: bigint, to: bigint) => (liquidity * Q96 * (to - from)) / to / from
	const amount1For = (from: bigint, to: bigint) => (liquidity * (to - from)) / Q96

	if (sqrtPriceX96 <= sqrtRatioAX96) {
		return { amount0: amount0For(sqrtRatioAX96, sqrtRatioBX96), amount1: 0n }
	}
	if (sqrtPriceX96 < sqrtRatioBX96) {
		return {
			amount0: amount0For(sqrtPriceX96, sqrtRatioBX96),
			amount1: amount1For(sqrtRatioAX96, sqrtPriceX96),
		}
	}
	return { amount0: 0n, amount1: amount1For(sqrtRatioAX96, sqrtRatioBX96) }
}

## Uniswap price guards

Pool-based pricing trusts the live pool, which leaves the solver exposed to a manipulated, stale, or thin pool returning a bad quote. To bound that risk, give a position a **`referencePrice`** and **`maxDeviationBps`**. Whenever the pool quote on that chain drifts more than `maxDeviationBps` above or below the reference, the solver refuses to fill — the order is rejected before any bid is submitted.

`referencePrice` is expressed in **exotic tokens per USD**, the same units as the bid/ask curves. The two fields must be set together; omit both to leave the chain unguarded.

```toml lineNumbers
[vault.uniswapV4]
# referencePrice is the expected cNGN per USD;
# reject if the quote is more than 2% off.
# The two go together — one without the other is rejected.
[[vault.uniswapV4.positions]]
chain           = "EVM-8453"
tokenId         = "2087350"
referencePrice  = "1575"
maxDeviationBps = 200
```
