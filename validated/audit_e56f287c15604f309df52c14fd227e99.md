### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from only the raw request body, while the `shop` field that is later trusted and dispatched to the application's webhook handler is taken from an unauthenticated HTTP header. This breaks the identity binding `hmac_signed_bytes == data_acted_on`, letting an attacker who controls any legitimate Shopify shop replay a validly-signed webhook body under a different `shop-domain` header value, causing the host application to process the payload as belonging to a shop it did not originate from.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery` by computing `HMAC(secret, verifiable_query.to_signable_string)` and comparing it to `verifiable_query.hmac` [1](#0-0) .

For incoming webhooks, `ShopifyAPI::Webhooks::Request` implements `VerifiableQuery`:
- `hmac` is parsed from the `hmac-sha256` header.
- `to_signable_string` returns `@raw_body` only — it does not include `topic`, `shop-domain`, `api-version`, or `webhook-id`.
- `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from unauthenticated HTTP headers. [2](#0-1) 

`Registry.process` then validates the request using only this body-scoped HMAC, and — once it passes — forwards `request.shop` (the header value, never covered by the signature) directly to the registered handler as the tenant identity for the event: [3](#0-2) 

Because the HMAC only proves "this exact body was signed by Shopify with `api_secret_key`" and says nothing about which shop the body belongs to, an attacker who operates (or compromises) shop A can capture a genuine Shopify-signed webhook payload+HMAC delivered to shop A's own endpoint, then replay that identical `raw_body`/`hmac-sha256` pair to the shared app's webhook endpoint while substituting `shop-domain: victim-shop.myshopify.com`. `HmacValidator.validate` will still return `true` because it only re-hashes `raw_body`, and the handler will execute business logic (order/customer/app-uninstalled data, etc.) as if it belongs to `victim-shop`, i.e., cross-tenant data confusion driven entirely by an attacker-controlled, unauthenticated header field.

This is exactly the identity-binding class flagged in the report by analogy: a value ("shop") that is *acted upon* by the application is not part of the bytes actually covered by the cryptographic check, unlike the `StaticHyVM` bug where a critical property (contract existence) was assumed but never verified before trusting the call's result.

### Impact Explanation
This allows cross-tenant access/confusion: a party who legitimately controls one merchant's shop (an "unprivileged" actor relative to any other tenant of the app) can cause the host application to attribute webhook-driven actions/data to a different, unrelated shop by forging only an HTTP header, without needing the app's `client_secret` or any victim credentials. This matches the Critical "cross-tenant access" impact category, since the HMAC (the gem's only integrity guarantee for webhooks) is defeated for the purpose of shop attribution.

### Likelihood Explanation
Likelihood is moderate: the attacker must control (or briefly compromise) at least one shop that has the target app installed and receives at least one webhook whose body/signature can be replayed, and must be able to reach the app's webhook endpoint directly (bypassing Shopify's normal delivery) — both are realistic since Shopify webhook endpoints are plain public HTTP(S) endpoints and merchants routinely have shell/API access to their own shop. No secret material is required.

### Recommendation
- **Short term**: Include the identity/context fields (`shop`, `topic`, `webhook_id`, `api_version`) inside `to_signable_string`, or otherwise independently authenticate `shop` (e.g., require the caller to also verify shop domain format/allow-list plus rely on transport-level assurances from Shopify's IPs), so any header tampering invalidates the HMAC. Document clearly that `Registry.process` does not itself authenticate the `shop` header — the HMAC binds only the raw body — and require host apps to cross-check `request.shop` against a session/tenant record before trusting it.
- **Long term**: Audit all `VerifiableQuery` implementations (`AuthQuery`, `Request`) to ensure every field consumed by downstream logic is included in the signed payload, mirroring the general principle that any value relied upon for authorization/attribution must be inside the verified bytes.

### Proof of Concept
1. Attacker owns `attacker-shop.myshopify.com`, which has a target app installed, and captures a legitimate webhook delivery from Shopify to the app's webhook URL:
 - Body: `{"id":123,...}`
 - Headers: `x-shopify-hmac-sha256: <valid_hmac_of_body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`
2. Attacker resends the same body and the same `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `request.to_signable_string` (= raw body only) — matches, so validation passes [4](#0-3) .
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though the payload actually came from `attacker-shop`, causing the app to act on/store data under the wrong tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
