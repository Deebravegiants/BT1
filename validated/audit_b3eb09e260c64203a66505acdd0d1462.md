## Analog Found

### Title
Panic-on-mismatched-length write into a fixed 65-byte signature buffer during BEEFY proof decoding - (File: `evm/rust/src/conversions.rs`)

### Summary
The CVE describes a parser (`nhmldmx_init_parsing`) that writes attacker-influenced data into a fixed-size stack buffer without validating the source length first. The Hyperbridge codebase has the same bug-class pattern in the conversion that turns a Solidity-ABI-decoded BEEFY `Vote` into the internal `SignatureWithAuthorityIndex` type: it copies an attacker-controlled, variable-length `bytes` field into a fixed `[u8; 65]` array with `copy_from_slice` instead of a length-checked conversion.

### Finding Description
`Vote.signature` is a Solidity `bytes` field, decoded via `abi_decode_params` from data an unprivileged relayer submits as part of a BEEFY consensus proof. The conversion into the internal representation does: [1](#0-0) 

```rust
impl From<Vote> for SignatureWithAuthorityIndex {
    fn from(value: Vote) -> Self {
        let sig_bytes = value.signature.to_vec();
        let mut signature: TSignature = [0u8; 65];
        signature.copy_from_slice(&sig_bytes);
        ...
```

`Vec<u8>::copy_from_slice` into a fixed `[u8; 65]` array panics if `sig_bytes.len() != 65` — there is no prior length check, unlike sibling conversions in the same file that use `try_into().expect(...)` after an implicit length check via `TryInto` (e.g. authority-set id/version conversions), or the test helper at `modules/pallets/testsuite/src/tests/pallet_ismp_beefy.rs:159-161` which explicitly does `slice.try_into().expect("Signature should be 65 bytes long")` — still a panic, but at least a checked one with an explicit error path. Here the copy is unconditional.

This conversion is reached from the naive BEEFY proof path that decodes an attacker-supplied ABI payload and turns it into the internal `ConsensusMessage`/`Sp1BeefyProof` used by `verify_and_apply`: [2](#0-1) 

An unprivileged submitter of `submit_proof` (or any relayer/tesseract path constructing a `BeefyConsensusProof`/`SP1BeefyProof` from raw bytes) can set an authority `Vote.signature` field to any length other than 65 bytes and trigger the panic before any of the cryptographic/authority-set validation in `EcdsaBeefy.sol`/`beefy-consensus-proofs` runs.

### Impact Explanation
A panic during extrinsic dispatch inside a FRAME pallet call is not silently caught the way a `Result::Err` is — it aborts execution of the runtime call for that transaction. Depending on how the panic propagates through `handle_incoming_message`/`verify_and_apply` (called from `Pallet::submit_proof`), this can manifest as a failed/aborted block execution rather than a clean `DispatchError`, i.e. a denial-of-service against the BEEFY consensus-update path that other messages, mint/burn, and state-proof verification depend on to advance the trusted consensus height. This matches "a route unable to deliver messages" in the validation criteria.

### Likelihood Explanation
High: constructing an ABI-encoded `Vote` with a signature field of arbitrary length is trivial for any external submitter and requires no special privileges — the length mismatch is checked nowhere before `copy_from_slice` is called.

### Recommendation
Replace the unconditional `copy_from_slice` with a length-checked conversion (e.g., `TryInto<[u8; 65]>::try_into(sig_bytes.as_slice())`) that returns a decode error instead of panicking, mirroring the pattern already used elsewhere in this same file for other fixed-size fields, and propagate that error through the `BeefyConsensusProof`/`Sp1BeefyProof` conversion chain so malformed signatures are rejected with a typed error rather than aborting execution.

### Proof of Concept
1. Craft an ABI-encoded `BeefyConsensusProof` (or `SP1BeefyProof`) where one `Vote.signature` is set to a `bytes` value of length ≠ 65 (e.g., 0 or 64 bytes).
2. Submit it via `BeefyConsensusProofs::submit_proof` (or the equivalent relayer/tesseract call path) prefixed with `PROOF_TYPE_NAIVE`/`PROOF_TYPE_SP1` as shown in `modules/pallets/beefy-consensus-proofs/src/lib.rs:818-838`.
3. During `abi_proof.into()` conversion, `From<Vote> for SignatureWithAuthorityIndex` executes `signature.copy_from_slice(&sig_bytes)` at `evm/rust/src/conversions.rs:360`, which panics with a length-mismatch message before any cryptographic verification occurs.

**Caveat:** I could not fully trace, within the available index, whether this exact `From<Vote>` impl is the one invoked by the `.into()` call in `modules/pallets/beefy-consensus-proofs/src/lib.rs` (there may be an intermediate `ismp_abi`-crate conversion I could not view in full). The described bug pattern (unchecked `copy_from_slice` into a fixed array from attacker-controlled ABI `bytes`) is confirmed present in `evm/rust/src/conversions.rs`, but confirming the exact call graph would benefit from a full Devin session with complete repository access.
