Confirmed: `handlePostRequests` and `handleGetResponses` in `HandlerV2.sol` loop over all leaves in a batch and call `host.dispatchIncoming(...)` for each one, within a single transaction, with no per-call gas stipend.### Title
Unbounded gas forwarding on `EvmHost.dispatchIncoming`/`dispatchTimeOut` app callbacks allows a single malicious application to grief entire relayed batches - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatchIncoming` and `dispatchTimeOut` deliver incoming ISMP messages to destination `IApp` contracts using plain `.call(...)` with no explicit gas stipend, so essentially all remaining gas is forwarded to an arbitrary, attacker-controlled destination module. `HandlerV2.handlePostRequests` and `handleGetResponses` call these functions in a loop over every leaf in a single relayed batch. A malicious or misbehaving destination module can deliberately consume (nearly) all forwarded gas, causing the outer transaction to run out of gas before it can complete the remaining loop iterations, book-keeping, and event emissions — reverting the whole batch and blocking delivery of every other, legitimate message bundled in it. This is the same bug class as the Hats.sol finding: an unbounded external/static call whose gas consumption can be weaponized to deny service to unrelated functionality sharing the same call stack.

### Finding Description
`dispatchIncoming(PostRequest, address)` performs:
```solidity
(bool success,) = address(destination)
    .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));
``` [1](#0-0) 

The same unbounded-gas pattern repeats for `dispatchIncoming(GetResponse, address)`, `dispatchTimeOut(GetRequestTimeout, ...)`, and `dispatchTimeOut(PostRequestTimeout, ...)`: [2](#0-1) [3](#0-2) [4](#0-3) 

None of these calls specify a `gas(...)` limit, so per EVM semantics roughly 63/64 of all remaining gas is forwarded to `destination` (an address fully controlled by whoever registers/deploys an `IApp`, i.e. any relayed request's `to` field). A destination contract can implement `onAccept`/`onGetResponse`/`onPostRequestTimeout`/`onGetTimeout` to burn essentially all the gas it receives (e.g., an unbounded loop), which forces the low-level `.call` to fail with an out-of-gas condition that consumes the forwarded gas irrecoverably.

Crucially, these dispatch functions are invoked from inside a loop over an entire relayed batch in `HandlerV2`:
```solidity
for (uint256 i = 0; i < requestsLen; ++i) {
    ...
    host.dispatchIncoming(leaf.request, _msgSender());
}
``` [5](#0-4) 
and identically for GET responses: [6](#0-5) 

Because a single relayer transaction can bundle many independent messages (potentially to many different applications) via `handlePostRequests`/`handleGetResponses`, and these can further be composed via `IHandlerV2.batchCall` which delegatecalls multiple handler functions atomically and reverts the whole batch if any inner call fails: [7](#0-6) 

a single malicious application placed anywhere in the batch can consume enough gas in its callback to starve the remaining loop iterations of gas, causing an out-of-gas revert that unwinds the entire `handlePostRequests`/`handleGetResponses`/`batchCall` transaction — including all `dispatchIncoming` calls for well-behaved, unrelated applications that happened to be bundled in the same relay transaction.

This differs from the intentional "swallow individual failures" design documented for `dispatchIncoming` (a normal `revert` from `onAccept` is caught via `success` check and only that message's receipt is rolled back, allowing retry without affecting the rest of the batch — as described in `sdk/packages/core/docs/ai/flows/how-a-cross-chain-delivery-reaches-the-gateway-and-where-the.md`). That graceful-failure design is defeated by an out-of-gas attack, because an OOG inside a low-level call that also exhausts the *caller's* remaining gas propagates up as an OOG revert of the entire top-level transaction rather than a caught `success == false` — the same fundamental flaw the Hats.sol report described for its `staticcall`s.

### Impact Explanation
An attacker who deploys a malicious `IApp` module and receives (or times out) even one ISMP message can force any relayer's batch transaction that includes that message to fail with out-of-gas, as long as the transaction's remaining gas budget is exhausted by the malicious callback. This:
- Blocks delivery of all other legitimate POST requests / GET responses bundled in the same batch (`handlePostRequests`, `handleGetResponses`), causing denial of service for unrelated applications and users whose messages happen to be routed through the same relayer batch.
- Can be exploited repeatedly against any relayer that batches multiple pending messages together (a common gas-optimization / cost-amortization pattern, as evidenced by `HandlerV2.batchCall` and the relayer tooling in `tesseract/messaging/evm/src/tx.rs` building multi-message batches), effectively denying message delivery/route availability for the state machine pair until relayers stop batching the malicious app's messages with others.
- Constitutes a "route unable to deliver messages" condition as defined in scope, since legitimate cross-chain messages can be indefinitely delayed/held hostage by an attacker-controlled application contract that is itself a valid message recipient.

This qualifies as Medium severity: it does not directly steal funds but creates a reliable, low-cost griefing vector against message delivery availability, matching the accepted-impact category of "a route unable to deliver messages."

### Likelihood Explanation
Likelihood is moderate-to-high: any address can be the `to`/`from` of a POST or GET request/timeout that ends up being called via `dispatchIncoming`/`dispatchTimeOut` — the destination module identity is attacker-chosen data carried in the cross-chain message itself, not vetted by the host. No special privileges are required beyond being able to dispatch or receive a message destined to a malicious contract, and relayers routinely batch multiple pending messages together for gas efficiency (as shown by `HandlerV2.batchCall` and the relayer's batch-building logic), which is precisely the condition needed to make the DoS impact more than a single message's failure.

### Recommendation
Cap the gas forwarded to destination application callbacks in `EvmHost.dispatchIncoming` and `dispatchTimeOut` (e.g., `destination.call{gas: FIXED_APP_GAS_LIMIT}(...)`), sized generously enough for legitimate application logic but bounded so a malicious callee cannot exhaust the entire transaction's remaining gas. Additionally/alternatively, ensure the caller retains a guaranteed minimum gas reserve (checked via `gasleft()` before the call, per the "63/64 rule" mitigation pattern) so that even if the callee returns `false` due to running out of its allotted gas, the host has enough gas left to safely record the failure, delete/restore receipts, and continue processing the rest of the batch instead of reverting the whole transaction with an out-of-gas error.

### Proof of Concept
1. Attacker deploys `MaliciousApp` implementing `IApp.onAccept` (and/or `onGetResponse`, `onPostRequestTimeout`, `onGetTimeout`) that runs an unbounded/gas-heavy loop consuming essentially all gas forwarded to it.
2. Attacker gets a valid ISMP POST request dispatched with `to = MaliciousApp` (any state machine can dispatch a request to any destination address; the host does not restrict which addresses can be targeted).
3. A relayer collects this request together with N other legitimate, unrelated POST requests into one `PostRequestMessage` and submits `HandlerV2.handlePostRequests(host, message)` (optionally further wrapped in `batchCall` with `handleConsensus`).
4. Inside the loop at `HandlerV2.sol:204-209`, when the iteration for `MaliciousApp`'s request calls `host.dispatchIncoming(leaf.request, relayer)`, the unbounded `.call` at `EvmHost.sol:809-810` forwards ~63/64 of remaining gas to `MaliciousApp`, which burns it all.
5. The outer `handlePostRequests` transaction runs out of gas either inside the callback or in subsequent loop iterations/book-keeping, causing the entire transaction (and, if wrapped, the entire `batchCall`) to revert via `BatchCallFailed`/plain OOG.
6. All N legitimate requests bundled with the attacker's message fail to be delivered in that transaction, even though they had nothing to do with the malicious application, and must be re-relayed separately (at best) or are indefinitely delayed if relayers keep re-batching them together.
