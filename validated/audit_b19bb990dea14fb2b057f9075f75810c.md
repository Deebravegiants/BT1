### Title
Fee-on-transfer / deflationary SPL tokens silently drain pool reserves and allow unbacked LP minting during swap and deposit - (File: program/src/processor.rs)

### Summary
`process_swap_base_in`, `process_swap_base_in_v2`, `process_swap_base_out`, `process_swap_base_out_v2` and `process_deposit` all accept `user_source_info` / `user_destination_info` token accounts for arbitrary mints validated only against the pool's stored `coin_vault_mint`/`pc_vault_mint` — there is no restriction that the underlying SPL mint be a "plain-vanilla" token without transfer fees, and no verification that the amount actually credited to the AMM vault after a CPI transfer matches the amount that was used to compute swap output or LP mint amount.

### Finding Description
In every swap path the AMM computes the invariant-based output using the pool's current vault balances and the caller-declared `swap.amount_in`, e.g. [8](#0-7) . It then executes the inbound leg via a generic `spl_token::instruction::transfer` in `Invokers::token_transfer` ( [2](#0-1) ) and unconditionally sends the previously computed `swap_amount_out` from the opposite vault to the user ( [3](#0-2) ). If the source mint charges a transfer fee (either a legacy fee-on-transfer token or a Token-2022 mint with the `TransferFeeConfig` extension, both of which are SPL-compatible and satisfy the `Self::unpack_token_account`/mint checks used here — see [9](#0-8) ), the amount actually credited to `amm_coin_vault`/`amm_pc_vault` will be strictly less than `swap.amount_in`/`swap_in_after_deduct_fee`. The program never re-reads the vault balance after the inbound CPI to detect this shortfall before paying out `swap_amount_out`, so every such swap extracts more value from the pool than was deposited, progressively insolvent-izing the constant-product invariant that all other LPs and swappers rely on.

The identical pattern exists in `process_deposit`: `mint_lp_amount` (and the reserve bookkeping `target_orders.calc_pnl_x/y`) is derived from `deduct_coin_amount`/`deduct_pc_amount` ( [10](#0-9) ) before the `Invokers::token_transfer` calls move tokens into the vaults; if the coin or pc mint charges a transfer fee, the LP tokens minted overstate the tokens actually received, diluting/defrauding existing LPs (unbacked LP minting).

### Impact Explanation
This is direct, permissionless value extraction from LP funds: an attacker can create a pool (or use an existing pool with such a mint, since `CreatePool`/`Initialize2` performs no mint allow-listing) backed by a transfer-fee token, then repeatedly swap or deposit to drain the counter-asset vault or mint LP tokens unbacked by real deposits — both directly steal or permanently impair LP/pool funds, matching the "unbacked LP minting" / "insolvent pool accounting" impact bar.

### Likelihood Explanation
Reaching this requires only a single permissionless transaction — pool creation via `Initialize2` and swap/deposit instructions are all open to any signer with attacker-chosen token accounts; no privileged role is needed. Fee-on-transfer and Token-2022 transfer-fee tokens are common and increasingly used on Solana, making this trivially triggerable once such a pool exists.

### Recommendation
For every inbound transfer, capture the destination vault's token balance immediately before and after the CPI and use the actual delta (not the caller-supplied `amount_in`/`max_coin_amount`/`max_pc_amount`) for all downstream invariant, fee, and LP-mint calculations in `process_swap_base_in`, `process_swap_base_in_v2`, `process_swap_base_out`, `process_swap_base_out_v2`, and `process_deposit`. Alternatively/additionally, reject mints that are SPL Token-2022 with a `TransferFeeConfig`/`TransferHook` extension, or otherwise enforce that pools only support "plain" SPL tokens, consistent with the protocol's assumption that no fee-on-transfer tokens are used.

### Proof of Concept
1. Create a pool (`Initialize2`) where the pc (or coin) mint is a Token-2022 mint with a `TransferFeeConfig` extension charging, e.g., 5% on every transfer, or a legacy fee-on-transfer token.
2. Call `SwapBaseIn` with `amount_in = X`. The program computes `swap_amount_out` from `total_pc_without_take_pnl`/`total_coin_without_take_pnl` and the full `X` (minus only the protocol's own `swap_fee_numerator`) at [8](#0-7) .
3. `Invokers::token_transfer` moves `X` (minus protocol fee) from the user's source account, but the mint's transfer fee causes only `X * (1 - fee%)` to actually land in `amm_coin_vault`/`amm_pc_vault`.
4. The program still pays out the full previously computed `swap_amount_out` to the user from the opposite vault at [3](#0-2) .
5. Repeating this swap drains the opposite-side vault faster than the invariant intends, since each round-trip nets the attacker the fee-percentage difference at the expense of the pool/LPs.
