### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, meaning the HMAC computed by `Utils::HmacValidator.validate` covers the JSON body alone, not the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. Yet `Registry.process` trusts `request.shop` (read straight from the unauthenticated header) to identify which tenant the webhook belongs to when invoking the app's handler. This breaks the identity binding `signed_bytes == acted_upon_identity`: the bytes that are HMAC-verified (body only) are not the same bytes that determine which shop the data is attributed to (the header).

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares against `verifiable_query.hmac`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body, and `shop` is read from a separate header that participates in no cryptographic check: [2](#0-1) 

`Registry.process` validates the HMAC and then forwards `request.shop` verbatim to the app-supplied handler as the tenant identifier: [3](#0-2) 

Because the header is excluded from the signable string, a caller who already possesses one legitimate `(body, hmac)` pair — e.g., a real merchant who installed the app on their own shop and received a genuine webhook — can resend that exact body/HMAC combination while substituting an arbitrary `shopify-shop-domain` (or `x-shopify-shop-domain`) header. `HmacValidator.validate` still returns `true` because it never inspected the header, and the gem hands the handler a `WebhookMetadata` object whose `shop` field is fully attacker-controlled while `body` is genuine, signed data: [4](#0-3) 

This is the same class of defect as the `buy()` bug in the report: a value that is *acted upon* (the receiver / the shop) is not the same value that was *cryptographically verified* (the signature / the HMAC), letting an unprivileged caller substitute an identity of their choosing.

### Impact Explanation
Any downstream app that keys per-tenant behaviour off `data.shop` (looking up a session/access token, writing to a tenant-scoped database row, enqueuing a job scoped "for shop X") can be made to attribute another shop's data to an attacker-chosen shop domain, or attacker's own webhook data to a victim shop, purely because the gem does not bind the header used for routing to the signed payload. This is a cross-tenant confusion vector reachable by any user able to trigger a legitimate webhook for a shop they control (the standard entry point for an unprivileged/low-privilege attacker in a multi-tenant Shopify app), satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is Medium: the attacker needs to be a legitimate (even free-tier) install of the app on a shop they control to obtain one valid `(body, hmac)` pair, then simply replay it with a modified header value against the app's public webhook endpoint. No secret key, TLS interception, or privileged account is required — only the ability to trigger/capture one real webhook delivery, which the gem's own documented flow encourages developers to expose via `Registry.process`.

### Recommendation
Bind the `shop-domain` (and ideally `topic`/`webhook-id`) header into the signable payload verified by `HmacValidator`, or, at minimum, document/require that consuming applications independently verify `request.shop` against a known/installed-shop store before trusting `WebhookMetadata#shop`, rather than allowing the header to flow unchecked into the handler. If Shopify's wire protocol genuinely only signs the body (as it does for legitimate Shopify-origin requests), the gem should surface this explicitly so host apps do not conflate "HMAC valid" with "shop header trustworthy."

### Proof of Concept
1. App A is installed on `attacker.myshopify.com`; Shopify delivers a real webhook: body `{"id":1}}`, header `x-shopify-shop-domain: attacker.myshopify.com`, header `x-shopify-hmac-sha256: <valid HMAC over the body>`.
2. Attacker captures this request and resends it to the same webhook endpoint, changing only `x-shopify-shop-domain` to `victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses the tampered headers; `Utils::HmacValidator.validate` recomputes HMAC over the (unchanged) body and it matches, so `Registry.process` proceeds: [5](#0-4) 
4. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and the attacker's data, processing it as if it originated from the victim tenant.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
