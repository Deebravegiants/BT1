### Title
Webhook shop/topic identity spoofing via unsigned headers - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking the HMAC over the raw request body, but the `shop`, `topic`, `webhook_id`, and `api_version` values used to build the `WebhookMetadata` passed to the app's handler are read directly from HTTP headers that are **not** part of the signed content. Any party that can obtain one valid `(body, hmac)` pair signed with the app's `api_secret_key` — for example a merchant who legitimately installed the app and received one real webhook — can replay that pair with forged `shop-domain`/`topic` headers and have the host application process it as if it came from a different tenant/topic.

### Finding Description
`Utils::HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`, and for webhook requests that method returns just the raw body: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors are pulled straight from unauthenticated headers: [2](#0-1) 

`Registry.process` validates HMAC on the `request` object, then dispatches using `request.topic` for handler lookup and forwards `request.shop` (plus `webhook_id`/`api_version`) into `WebhookMetadata`, which the app's business logic consumes as the tenant identity for the event: [3](#0-2) 

Because the HMAC never covers `shop`, `topic`, `webhook_id`, or `api_version`, the binding "HMAC verified over (body, shop, topic)" ≠ "(body, shop, topic) acted upon by the handler" is broken. A `(body, hmac)` pair is valid for the app's secret regardless of which shop/topic it is presented with, since the secret is shared across all shops installed on the same app (as confirmed by `Context.api_secret_key`/`old_api_secret_key` usage in `HmacValidator`): [4](#0-3) 

### Impact Explanation
This is a cross-tenant confusion vector: an attacker who legitimately installs the app on their own shop (an unprivileged party relative to other tenants of the same app) receives real webhook deliveries and thus learns valid `(raw_body, hmac)` pairs for the app's `api_secret_key`. They can replay that exact body to the app's webhook endpoint while forging the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header to any value. `HmacValidator.validate` still passes because it never inspects those headers, and `Registry.process` forwards the attacker-controlled `shop` value into the handler as if it were verified — enabling cross-tenant data injection/confusion in any host application that trusts `WebhookMetadata#shop` as an authenticated tenant identifier (which is the intended and documented use of that field).

### Likelihood Explanation
Likelihood is meaningful but bounded: the attacker needs at least one legitimate app installation to obtain a valid `(body, hmac)` sample (trivial for any public app), and the impact depends on host applications trusting `WebhookMetadata#shop`/`#topic` without additional out-of-band verification — which is exactly what the gem's own webhook API contract implies is safe to do, since `Registry.process` labels the request as HMAC-"validated" before handing off shop/topic to the handler.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` (all Shopify-supplied, security-relevant fields) in the signable content used for webhook HMAC verification, or otherwise cryptographically bind them to the request (e.g., derive them only from a signed envelope) rather than trusting raw HTTP headers independently of the HMAC check.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and receives a legitimate webhook, capturing `raw_body = B` and `x-shopify-hmac-sha256 = H` (valid HMAC of `B` under the app's shared `api_secret_key`).
2. Attacker sends a new HTTP request to the app's webhook endpoint with the same `raw_body = B` and `x-shopify-hmac-sha256 = H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
3. `ShopifyAPI::Webhooks::Request.new` parses these headers unchanged; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H`, per `lib/shopify_api/utils/hmac_validator.rb` and `lib/shopify_api/webhooks/request.rb#to_signable_string`.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: B, ...)`, per `lib/shopify_api/webhooks/registry.rb` lines 188-200, causing the host app to process/attribute the event to a shop the attacker does not control.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
