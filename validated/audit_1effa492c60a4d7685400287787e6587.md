### Title
Webhook `shop` (tenant) identity is not bound to the HMAC, enabling cross-tenant webhook spoofing/replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` and `ShopifyAPI::Utils::HmacValidator` verify only the raw HTTP body against the app's shared `client_secret`, while the `shop` (tenant identity) header that is later trusted and forwarded to the host application's handler is completely excluded from the signed bytes. This breaks the intended equality: `shop_used_by_handler == shop_that_Shopify_actually_generated_the_signed_body_for`. Because the same `client_secret` is shared across every shop that installs an app, any unprivileged internet user who can get one legitimate webhook delivered to themselves (e.g. by installing the app on their own free development/trial store) can capture a valid `(raw_body, hmac)` pair and replay it to the app's webhook endpoint with an arbitrary, attacker-chosen `X-Shopify-Shop-Domain` header. The gem's validation still succeeds, and the forged shop value is handed to the app as if Shopify had certified it.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, and none of the Shopify headers (topic, shop-domain, webhook-id, api-version) are part of the signable string: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e. the raw body) and secure-compares it to the header value: [2](#0-1) 

`Registry.process` treats a passing HMAC check as full authentication of the request, then immediately forwards the **unauthenticated** `request.shop` value to the app's handler as the tenant identity: [3](#0-2) 

`shop` itself is read straight off the `shopify-shop-domain`/`x-shopify-shop-domain` header with no cross-check against the signed payload: [4](#0-3) 

This mirrors the report's bug class exactly: a field (`shop`) that is acted upon (used as the tenant key passed to `WebhookMetadata`/handler) is not covered by the HMAC that is supposed to authenticate the whole event. The gem's own docs reinforce the false assumption that the *entire request* is authenticated: "This will verify the request did indeed come from Shopify": [5](#0-4) 

Because Shopify signs webhooks with the app's single `client_secret` shared across *all* shops that install the app (not a per-shop secret), a `(raw_body, hmac)` pair that is valid for shop A is also byte-for-byte valid for shop B — the signature carries no shop binding whatsoever. Any user can become a legitimate, unprivileged "shop A" by installing the app themselves (or via any public dev-store install flow), then capture one real delivered webhook and replay it with a forged shop header.

### Impact Explanation
An attacker who legitimately installs the app on their own store (fully unprivileged w.r.t. any other merchant) can:
1. Trigger/capture a real webhook delivery to their own endpoint, obtaining a valid `(raw_body, x-shopify-hmac-sha256)` pair signed with the app's shared secret.
2. Replay that exact body+hmac to the app's webhook controller while setting `X-Shopify-Shop-Domain` to a victim shop's domain.
3. `ShopifyAPI::Webhooks::Registry.process` passes HMAC validation (body untouched) and calls the app's handler with `shop: victim-shop.myshopify.com`.

Depending on what the host app does with `WebhookMetadata#shop` (e.g. look up the victim's stored access token/session to act on their behalf, trigger uninstall/data-erasure flows tied to `app/uninstalled` or GDPR topics, or mutate victim-scoped records keyed by the spoofed shop), this results in cross-tenant confusion/action — the app is deceived into treating attacker-controlled event data as if it originated from a different, victim tenant. This matches the Critical "cross-tenant access" impact bucket, since the tenant boundary (`shop`) that gates which merchant's data/session the webhook event acts on is not actually authenticated by this gem.

### Likelihood Explanation
Likelihood is high for any app that: (a) allows self-service installs (most public Shopify apps do), and (b) uses the `shop` field from `WebhookMetadata` for anything privileged (token lookup, per-shop side effects) without independently re-validating it against a known/registered shop-secret pairing. No leaked credentials, TLS interception, or privileged account are required — only a normal, unprivileged install of the target app by the attacker on a shop they control.

### Recommendation
- Bind the trusted `shop` (and ideally `topic`/`webhook_id`) into the authenticated identity: after HMAC validation succeeds, require callers/host apps to check that `request.shop` matches a shop the app actually has an active installation/session for before treating the webhook as belonging to that tenant, and document this requirement clearly instead of implying the full request is verified.
- Update `docs/usage/webhooks.md` to explicitly state that only the raw body is HMAC-verified and that the `shop-domain` header is *not* cryptographically bound to the signature, so host apps know they must cross-validate it against their own shop/session store.
- Consider rejecting or flagging webhook processing when the `shop` header does not correspond to a shop with a known/registered webhook subscription tracked by the `Registry`.

### Proof of Concept
```ruby
# Attacker step 1: install target app on their own shop "attacker.myshopify.com"
# and receive a real webhook, e.g. for topic "orders/create".
# They capture the raw POST body and the X-Shopify-Hmac-Sha256 header Shopify sent.

captured_body = '{"id":123,"note":"hi"}'
captured_hmac = "base64-hmac-that-shopify-computed-with-the-shared-client_secret"

# Attacker step 2: replay the exact same body+hmac to the victim app's webhook
# endpoint, only changing the shop-domain header.
forged_headers = {
  "x-shopify-topic"        => "orders/create",
  "x-shopify-hmac-sha256"  => captured_hmac,   # still valid: HMAC only covers body
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com", # forged, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)

# HmacValidator.validate(request) => true, because it only checks captured_body vs secret.
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
# The host app now believes this attacker-controlled event genuinely came from the victim shop.
```

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
