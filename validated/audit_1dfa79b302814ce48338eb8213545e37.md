### Title
`updateHostParamsInternal` can never de-whitelist a state machine once it is added - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.updateHostParamsInternal` requires `params.stateMachines.length > 0` and, for every id in that array, only ever initializes `_latestStateMachineHeight[id]` from `0` to `1` if it was previously `0` — it never resets an existing entry back to `0`. This mirrors the `TrufVesting.setEmissionSchedule` bug class: a governance-controlled configuration that can be added/expanded but can never be removed once set, because the setter both rejects empty input and only performs additive writes.

### Finding Description
`HostParams.stateMachines` is the whitelist of state-machine ids whose state commitments this `EvmHost` accepts. The comment on `latestStateMachineHeight` makes the security invariant explicit: "If it returns 0, the state machine is unsupported." [1](#0-0) 

`updateHostParamsInternal`, which is the only path (`updateHostParams`, restricted to cross-chain governance via `hostManager`) that can change this whitelist, enforces `stateMachinesLen == 0 → revert InvalidStateMachinesLength()`, so governance can never submit an update that removes all entries, and the per-id loop only ever sets an entry from `0` to `1` — it never clears an id that is no longer in the new `params.stateMachines` list back to `0`: [2](#0-1) 

Just as `TrufVesting.setEmissionSchedule` disallows an empty array so an owner can never revert a category to "no schedule" (which the code treats specially via `maxAllocation`), `EvmHost.updateHostParamsInternal` disallows dropping a state machine from the effective accepted set: once `_latestStateMachineHeight[id]` becomes non-zero for some `id`, no later call to `updateHostParams` can ever bring it back to `0`, regardless of whether that `id` is included in the new `params.stateMachines` array. The stored array `_hostParams.stateMachines` is overwritten, but the actual authorization state (`_latestStateMachineHeight`), which is what other code paths are documented to check as the "is this state machine supported" flag, is append-only.

### Impact Explanation
This breaks the governance guarantee that a state machine's consensus/state acceptance can be revoked. If a state machine's consensus client is later found to be compromised, buggy, or malicious (e.g., a forged BEEFY/GRANDPA/SP1 proof path, a chain that needs to be sunset, or a chain onboarded by mistake), Hyperbridge governance has no on-chain mechanism via `updateHostParams` to de-authorize it on any `EvmHost` deployment — `_latestStateMachineHeight[id]` remains permanently non-zero once set. Depending on how downstream logic (handler/consensus verification, message delivery) treats a non-zero height as "supported," this can permanently prevent this host from ever fully cutting off a compromised source chain, i.e. a route that cannot be closed/disabled, which is a form of "route unable to deliver messages" being stuck in the wrong (always-open) state and an unauthorized/irrevocable app-level acceptance of a chain's state.

### Likelihood Explanation
Likelihood is high in practice: any time governance wants to remove a state machine from the accepted set (security incident, chain deprecation, mistaken addition) it will call `updateHostParams`/`updateHostParamsInternal`, and the mapping write will silently no-op for removed ids while the stored `stateMachines` array gives the false impression that the id was removed.

### Recommendation
Diff the previous `_hostParams.stateMachines` against the new `params.stateMachines` in `updateHostParamsInternal`, and explicitly reset `_latestStateMachineHeight[id]` to `0` for every id present in the old set but absent from the new set, in addition to the existing additive logic for newly added ids.

### Proof of Concept
1. Governance calls `updateHostParams` (via `hostManager`) with `stateMachines = [A, B]`. `_latestStateMachineHeight[A]` and `[B]` become `1`.
2. Chain `B`'s consensus is later compromised; governance calls `updateHostParams` again with `stateMachines = [A]`, intending to drop `B`.
3. `_hostParams.stateMachines` is now `[A]`, but `_latestStateMachineHeight[B]` remains `1` (never reset), because the loop at [3](#0-2)  only ever writes when the current value is `0`.
4. Any code path that gates acceptance on `latestStateMachineHeight(B) != 0` still treats `B` as supported, even though governance believed it had been removed. [4](#0-3) [3](#0-2)
