### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-binding field `shop` from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, but `to_signable_string` — the value that `Utils::HmacValidator.validate` actually verifies — only covers the raw request body. `Registry.process` accepts the request as authentic purely on the strength of `Utils::HmacValidator.validate(request)`, then forwards `request.shop` unauthenticated into `WebhookMetadata`, which is handed to the app's registered handler as the tenant identifier.

### Finding Description
This mirrors the root cause pattern in the referenced report: a value that downstream logic treats as authoritative (`userTokens` accounting / here, the `shop` tenant binding) is derived from data that is not actually covered by the cryptographic check that is supposed to guarantee its integrity.

Concretely:
- `Request#hmac` and `Request#to_signable_string` (`lib/shopify_api/webhooks/request.rb:11-13`, `35-38`) show the HMAC is computed/verified only over `@raw_body`.
- `Request#shop` (`lib/shopify_api/webhooks/request.rb:20-23`) reads `shop-domain`/`x-shopify-shop-domain` directly from `@headers`, which is attacker-controlled input to `Request.new(raw_body:, headers:)` and is never included in the signed content.
- `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) only checks `Utils::HmacValidator.validate(request)` — an HMAC over the body computed with the app's shared `api_secret_key` — and then immediately trusts `request.shop`, `request.topic`, etc. to build `WebhookMetadata` passed to the app-defined handler.

Because `Utils::HmacValidator.compute_signature` is keyed with the single, app-wide `Context.api_secret_key` (`lib/shopify_api/utils/hmac_validator.rb:16,34-40`) — the same secret is valid across *every* shop that has installed the app — a party that operates their own store installation of the app can legitimately receive one webhook delivery with a valid HMAC over some body, then replay that exact body to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `Utils::HmacValidator.validate` will still return `true` (the body/HMAC pair is untouched), and `Registry.process` will hand the handler a `WebhookMetadata` claiming the event originated from the victim shop.

This is the direct analog to the M-2 root cause: the code updates/uses a security-relevant field (`shop` binding, analogous to `userTokens`) using data that was never validated against the check meant to protect it (the HMAC, analogous to the `tokenAmount` delta check), breaking the intended identity equality `shop authenticated by HMAC == shop acted upon by the handler`.

### Impact Explanation
An app that uses `request.shop` from `WebhookMetadata` to select which tenant's data to mutate (a common and encouraged pattern, since the library exposes `shop` specifically for that purpose) can be tricked into performing actions attributed to, or against, a shop the attacker does not control — a cross-tenant boundary crossing purely because this gem exposes and forwards an unauthenticated field as if it were verified. This satisfies the "cross-tenant access" impact bucket in scope.

### Likelihood Explanation
Requires only: (1) attacker has (or can get) their own legitimate installation of the app (any developer/merchant can install a public app), (2) they can capture one webhook delivery body+HMAC for their own shop, and (3) they can send arbitrary HTTP requests directly to the app's public webhook endpoint (not through Shopify) with a forged `shop-domain` header. No access to `api_secret_key`, tokens, or Shopify infrastructure is needed — this is standard, well-known "header not covered by HMAC" replay behavior, reachable by any unprivileged internet user who can install the target app once.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) to the same integrity check as the body, or otherwise cross-verify the header-derived `shop` against a value the app already trusts (e.g., require the app to explicitly confirm the shop exists in its own session store before trusting `WebhookMetadata#shop`, and document loudly that `shop` is unauthenticated). At minimum, the library's documentation/API surface should not present `request.shop`/`WebhookMetadata#shop` as verified merely because `HmacValidator.validate` passed.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers/receives one webhook, e.g. body `{"id":1}` with a valid `x-shopify-hmac-sha256` computed by Shopify using the app's shared `client_secret`.
2. Attacker sends `POST /webhooks` directly to the app's endpoint with the identical `raw_body` and `hmac` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` from the forged header (`lib/shopify_api/webhooks/request.rb:20-23`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which only re-hashes `raw_body` (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`) — validation succeeds because the body/HMAC pair is untouched.
5. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` reporting `victim-shop.myshopify.com` as the event source, despite the attacker never having any credential tied to that shop. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
