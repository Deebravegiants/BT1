## Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`/`webhook_id`) values are read directly from unauthenticated HTTP headers. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` straight to the host app's handler as the tenant identity for the event, without that value ever being bound by the signature check.

### Finding Description
`to_signable_string` in `Request` returns only `@raw_body`: [1](#0-0) 

`shop` is read independently from the `shopify-shop-domain`/`x-shopify-shop-domain` header and is never part of the signed material: [2](#0-1) 

`Registry.process` validates HMAC on the request (i.e., only the body), then dispatches to the handler using `request.shop` taken from the header as the tenant/shop identity for the event: [3](#0-2) 

The equality the code implicitly assumes is:
`shop-domain header == shop that produced/authorized the signed body`

But the HMAC only proves:
`HMAC_verify(raw_body, client_secret) == true`

Because Shopify webhook signatures are computed with the app's `client_secret`, which is shared across every shop that has installed the app (not a per-shop secret), any shop that has installed the app can capture a legitimately-signed webhook delivered to it (valid body + valid HMAC using the shared secret) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a different (victim) shop's domain. Since the header is outside the signed payload, `Utils::HmacValidator.validate` in `hmac_validator.rb` still succeeds, and `Registry.process` will pass `WebhookMetadata.new(shop: <attacker-chosen shop>, ...)` to the host application's handler.

### Impact Explanation
This breaks the shop-domain/session binding that host applications rely on to route webhook data to the correct tenant. An app owner who has installed the app on their own store (no privileged Shopify credentials required beyond a normal install) can attribute forged/replayed event payloads to an arbitrary victim shop domain, resulting in cross-tenant data corruption or unauthorized actions taken against another merchant's tenant records — a Critical-severity cross-tenant access issue per the rules.

### Likelihood Explanation
Likelihood is high for any app that installs on multiple/any shop: the attacker only needs to be a normal merchant capable of installing the target app on their own store to receive validly-HMAC-signed webhook traffic, then replay it with a modified `shop-domain` header. No access token, `client_secret`, or privileged account is required.

### Recommendation
Include the `shop` domain (and ideally `topic`/`webhook_id`) in the HMAC-signable string, or independently verify that the shop domain in the webhook headers corresponds to a shop that is actually associated with the delivered `webhook_id`/subscription before dispatching to handlers, so that the shop identity used to route webhook data is cryptographically bound to the signed payload rather than trusted from an unauthenticated header.

### Proof of Concept
1. Attacker installs the target Shopify app on their own development/test store (`attacker.myshopify.com`), which is a normal, unprivileged action.
2. Shopify delivers a legitimate webhook to the app's registered endpoint with body `B` and header `x-shopify-hmac-sha256: HMAC(B, client_secret)` — valid because `client_secret` is shared across all installs of this app.
3. Attacker captures this `(B, HMAC)` pair and re-sends the same POST request to the app endpoint, but replaces `x-shopify-shop-domain: attacker.myshopify.com` with `x-shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) validates successfully because it only checks `to_signable_string` (the raw body), which is unchanged.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) calls the registered handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, causing the host application to process attacker-controlled data under the victim shop's tenant.
