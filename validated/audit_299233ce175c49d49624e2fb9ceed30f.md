## Title
Unchecked ERC-20/TRC-20 `transfer()` Return Value in Escrow Settlement — Silent Failure Permanently Freezes/Loses Escrowed Funds - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron deployment of `IntentGatewayV2` settles cross-chain and same-chain intent orders by making low-level `.call()` invocations to `IERC20.transfer.selector` and only checking the raw call-success flag, never the ABI-encoded boolean the ERC-20/TRC-20 `transfer()` function is supposed to return. On any token that returns `false` on failure instead of reverting (a very common pattern for TRC-20 tokens on Tron, including how many non-standard tokens behave), the contract treats a failed transfer as successful, permanently marks the order fulfilled/refunded, and decrements escrow bookkeeping — even though the beneficiary received nothing.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` is the internal function that releases escrowed tokens to a solver or refunds a user after Hyperbridge delivers a `RedeemEscrow`/`RefundEscrow` settlement message via `onAccept()`: [1](#0-0) 

and [2](#0-1) 

Both blocks use a raw low-level `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and only check `success` — the boolean indicating whether the *call itself* reverted, not whether the returned ABI-encoded data (the `bool` that `IERC20.transfer` returns) was `true`. Per the ERC-20 standard many tokens return `false` rather than reverting when a transfer cannot be completed (e.g. insufficient contract balance, paused, blacklisted recipient). On such tokens `success` is `true` while the transfer silently fails, so the code proceeds exactly as if the tokens moved.

The identical unchecked pattern also appears in the `SweepDust` handling within the same `onAccept()`: [3](#0-2) 

This is reachable by any relayer delivering a normal, unprivileged settlement message (`RedeemEscrow`/`RefundEscrow`, authenticated via `authenticate(incoming.request)` against a legitimate registered peer gateway) — no admin/governance privilege is required to trigger `withdraw()`; it fires for every ordinary order fill or cancellation.

By contrast, the primary EVM `IntentsBase.sol`/`IntentGatewayV2.sol` implementations consistently use OpenZeppelin's `SafeERC20.safeTransferFrom`/`safeTransfer` (e.g. `IERC20(token).safeTransferFrom(msg.sender, dispatcher, amount)` at [4](#0-3) ), confirming the Tron fork's raw `.call()` pattern is the outlier and unpatched analog of the reported bug class.

### Impact Explanation
When a token used in an order silently returns `false`:
- `withdraw()` still executes `_orders[body.commitment][token] -= amount;` and sets `_filled[body.commitment] = beneficiary;` (lines 693, 710), permanently marking the order as settled.
- The beneficiary/solver/user receives zero tokens for that leg, while the escrow accounting for that commitment is wiped out.
- Because the order is now marked filled/refunded, there is no remaining code path to retry or reclaim the escrowed balance — the tokens remain stuck in the contract with the accounting no longer reflecting they are owed to anyone, and the intended beneficiary permanently loses their entitled funds.
- The same applies to the `TRANSACTION_FEES` payout and the `SweepDust` treasury sweep, letting fee/dust distributions silently fail while state is finalized as if paid.

This is a concrete, permanent loss/freezing of user/solver funds in the intents settlement flow, medium-to-high severity given ordinary usage (no attacker action beyond using or bridging a non-reverting-style token is even required — a legitimate but non-standard token is sufficient).

### Likelihood Explanation
Likelihood is elevated specifically on Tron: TRC-20 token implementations commonly diverge from strict EIP-20 semantics (some historically don't revert on failure, or return no/partial data), and any order denominated in such a token that hits a transient failure condition (temporary insufficient liquidity path, blacklist, pause) will trigger the silent-failure path with no attacker interaction needed. It also requires no elevated privilege — the trigger is the standard, permissionless settlement delivery (`onAccept` called by the host for any correctly-proven cross-chain message).

### Recommendation
Replace all raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` usages in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()`'s token loop, the transaction-fee payout, and the `SweepDust` branch of `onAccept()`) with OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom`, which decodes and enforces the ERC-20 return value (and tolerates tokens that return no data), matching the pattern already used correctly in `evm/src/apps/IntentGatewayV2.sol` and `evm/src/apps/intentsv2/IntentsBase.sol`.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with a token `T` whose `transfer()` implementation returns `false` on failure instead of reverting (e.g., a mock TRC-20 that returns `false` when its internal balance check fails, mirroring real non-standard tokens).
2. Place an order escrowing `T` via `placeOrder`.
3. Arrange for `T`'s balance/allowance state such that the contract-held balance transiently cannot cover the `transfer(beneficiary, amount)` call inside `withdraw()` (or use a mock that simply returns `false` unconditionally for the test).
4. Trigger settlement: have the host call `onAccept()` with a valid `RedeemEscrow`/`RefundEscrow` request for the order's commitment.
5. Observe: `token.call(...)` returns `success = true` (the call did not revert) even though the encoded return data is `false`; the `if (!success) revert TransferFailed();` check does not trip.
6. Confirm `_orders[commitment][token]` is decremented to zero and `_filled[commitment]` is set to the beneficiary, while `T.balanceOf(beneficiary)` remains unchanged — the escrowed tokens are now unrecoverable through any exposed function.
