### Title
Webhook Topic/Shop/API-Version Headers Are Trusted for Tenant Routing but Not Covered by HMAC Verification - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then dispatches to a handler using the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers. Since none of these header fields are included in the HMAC-signed data, an attacker who possesses one valid `(raw_body, hmac)` pair can replay it with forged headers to make the request appear to originate from an arbitrary "shop" or "topic", breaking the identity binding `shop authenticated == shop acted upon`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read directly from HTTP headers, which are not part of the signed payload: [2](#0-1) 

`Registry.process` validates HMAC using `Utils::HmacValidator.validate(request)`, which internally calls `to_signable_string` (body only) — see `HmacValidator.validate_signature`: [3](#0-2) 

After that single check passes, `Registry.process` builds `WebhookMetadata` directly from the unauthenticated header-derived accessors and forwards it to the host application's handler: [4](#0-3) 

The binding that should hold is: **shop value authenticated by HMAC == shop value the handler acts on**. Because the HMAC covers only `raw_body`, this equality does not hold — `shop`/`topic`/`webhook_id`/`api_version` are "fields acted on but not covered by the HMAC."

### Impact Explanation
An unprivileged internet user who can obtain any single legitimate `(raw_body, x-shopify-hmac-sha256)` pair for the target app (e.g., by installing the app on their own test/attacker-controlled shop and receiving one real webhook) can resend that exact body/HMAC to the same webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) headers to point at a victim shop. `HmacValidator.validate` still succeeds because it only checks `raw_body` against the secret-derived signature, and `Registry.process` will invoke the registered handler believing the event, topic, and metadata belong to the victim tenant. Depending on how the host app's handler uses `WebhookMetadata#shop`/`#topic` (e.g., to look up or mutate per-shop records, trigger uninstall/redact cleanup, or update order/customer state), this allows cross-tenant event injection/spoofing — data or state belonging to one merchant can be attributed to another merchant's tenant context.

### Likelihood Explanation
Likelihood is meaningful but not trivial: the attacker must first obtain at least one genuine `(raw_body, hmac)` pair signed with the app's real `api_secret_key`. This is achievable without any privileged credentials by installing the (presumably public) app on an attacker-owned development shop, which is standard, unprivileged behavior for any Shopify Partner/developer account, and then triggering a webhook (e.g., `orders/create`) on that shop. No `api_secret_key`, access token, or victim credential is required.

### Recommendation
Include the security-relevant headers (`shop-domain`, `topic`, `api-version`, `webhook-id`) in the HMAC-signable content, or otherwise cryptographically bind them to the body (e.g., verify `shop` against session/state established during OAuth for that specific `topic`+body combination) so that headers cannot be swapped independently of the signed payload. At minimum, document/require host applications to treat `WebhookMetadata#shop` as untrusted unless independently corroborated, and provide a library helper that ties the verified body to the accompanying shop claim.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g. `orders/create`). Shopify sends a request with a body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker captures `B` and `H`.
3. Attacker sends a new HTTP POST to the app's public webhook endpoint with the same raw body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`).
4. `ShopifyAPI::Webhooks::Request.new` accepts the headers (only presence is checked, not value correctness) — [5](#0-4) .
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes HMAC over `B` — [6](#0-5) .
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"`, even though the payload actually originated from and describes `attacker-shop.myshopify.com`, demonstrating the cross-tenant identity mismatch.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
