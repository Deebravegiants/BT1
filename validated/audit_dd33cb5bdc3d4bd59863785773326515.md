### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then dispatches the handler using the `shop` value taken from the `X-Shopify-Shop-Domain` header — a field that is never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is instead read directly from the (unauthenticated) HTTP header, entirely independent of the HMAC-covered bytes: [2](#0-1) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the raw body) and compares it to the `hmac-sha256` header — it never binds `shop`, `topic`, or `api-version` headers into that computation: [3](#0-2) 

`Registry.process` then trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's handler, using only the HMAC check as its authentication gate: [4](#0-3) 

This breaks the identity binding that should hold: `hmac == HMAC(secret, raw_body)` should imply `shop == "the shop that produced raw_body"`, but the equality actually enforced is only `hmac == HMAC(secret, raw_body)`, with `shop` left as an independently-controlled, unauthenticated header value. Since the webhook HMAC secret (`client_secret`) is shared across every shop installation of the app (not per-shop), any actor able to trigger or capture a genuine webhook delivery for one shop they control (e.g., their own store on which the app is installed) obtains a body+HMAC pair that is valid for *any* shop attribution. Replaying that exact body/HMAC pair with the `X-Shopify-Shop-Domain` header rewritten to a victim merchant's domain passes `HmacValidator.validate` unchanged, and `Registry.process` will invoke the app's handler believing the event originated from the victim tenant — with a merchant-supplied topic (e.g. `customers/data_request`, `app/uninstalled`, `orders/create`) triggering the corresponding tenant-scoped side effects (e.g. GDPR data flows keyed by shop, app-uninstall cleanup, order/customer sync) against the wrong tenant.

### Impact Explanation
This is a cross-tenant attribution/impersonation vector: an attacker who legitimately controls one shop installation of the app can forge webhook events falsely attributed to another merchant, without ever knowing the app's `client_secret`. Any host application relying on `WebhookMetadata#shop` (as `Registry.process` explicitly surfaces it to handlers) to select which tenant's data/session/state to act on will act cross-tenant. This matches the "cross-tenant access" Critical impact bucket, since the trust anchor (HMAC) does not bind the identity field the framework hands to consumers as authoritative.

### Likelihood Explanation
Medium-to-High: exploitation only requires the attacker to operate one legitimate shop installation of the target app (a normal, low-privilege capability for any merchant/developer who installs a public or custom app) and the ability to intercept/replay an HTTP POST with modified headers — no access to `client_secret`, tokens, or the victim's infrastructure is needed. The gem provides no header-binding to prevent this replay-with-relabeled-tenant attack.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-covered signable string, or otherwise cryptographically bind the header-derived `shop` value to the delivery (e.g., concatenate `shop-domain header + raw_body` before hashing, matching what Shopify signs on the wire if it does, or validate `shop` against the session/webhook registration independently of the header). At minimum, document that `WebhookMetadata#shop` is unauthenticated and must not be trusted for tenant selection without additional verification (e.g. cross-checking against a known list of installed shop domains).

### Proof of Concept
1. App is installed on attacker-controlled shop `attacker.myshopify.com`; attacker triggers any webhook topic registered by the app (e.g. `app/uninstalled`), receiving a real Shopify-signed POST with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid HMAC over raw_body>`.
2. Attacker replays the exact same `raw_body` and `X-Shopify-Hmac-Sha256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`; since validation only recomputes HMAC over `request.to_signable_string` (`raw_body`), it passes: [5](#0-4) 
4. `request.shop` returns `"victim.myshopify.com"` from the forged header, and this is passed straight into `WebhookMetadata` given to the app's handler: [6](#0-5) 
5. The app's handler executes tenant-scoped logic (e.g. mandatory `customers/redact`/`app/uninstalled` processing) believing it originated from `victim.myshopify.com`, causing cross-tenant state corruption/impersonation despite a "valid" HMAC.
