## Title
Division-by-zero panic in `calc_take_pnl`/`calc_x_power` when a drained pool reserve normalizes to zero, permanently freezing deposits/withdrawals — (`program/src/processor.rs`, `program/src/math.rs`)

### Summary
`calc_take_pnl`, which runs on every `Deposit`, `Withdraw` (unless status is `WithdrawOnly`) and `WithdrawPnl` instruction, feeds the normalized pool reserves `x1`/`y1` into `Calculator::calc_x_power` and into a second unchecked division (`y2 = x2 * y1 / x1`). Both operations use raw `checked_div(..).unwrap()` with no fallback. Because `normalize_decimal_v2` truncates small raw reserve balances to `0` when `native_decimal > log10(sys_decimal_value)`, an attacker who drains one side of the pool via ordinary swaps down to a "dust" balance can force `x1` or `y1` to become exactly `0`, causing an unrecoverable divide-by-zero panic on every subsequent deposit/withdraw/withdrawpnl call — a state that is analogous to the Cosmos SDK groups-module “malicious proposal causes divide-by-zero and halts processing” bug class, except here it permanently DoSes the pool's deposit/withdraw path instead of halting a chain.

### Finding Description
`Calculator::calc_x_power` divides unconditionally by `current_y`: [1](#0-0) 

`calc_take_pnl` calls it with `current_x = x1`, `current_y = y1`, and later performs a second raw division by `x1`: [2](#0-1) 

`x1`/`y1` are computed from actual vault balances via `calc_total_without_take_pnl_no_orderbook` and then decimal-normalized: [3](#0-2) [4](#0-3) 

`normalize_decimal_v2` computes `val * sys_decimal_value / 10^native_decimal`. When the token's native decimal exponent exceeds `log10(sys_decimal_value)` (e.g. `coin_decimals = 9`, `sys_decimal_value = 10^6`, as used throughout the test fixtures), any raw reserve value below `1000` truncates to `0` due to integer division — even though the actual reserve is still non-zero. Both `x1` and `y1` are recomputed from the *current* on-chain vault amounts on every call: [5](#0-4) 

`calc_take_pnl` is invoked directly from `process_deposit`, `process_withdraw` (whenever `amm.status != WithdrawOnly`), and `process_withdrawpnl`: [6](#0-5) [7](#0-6) [8](#0-7) 

The swap instructions (`process_swap_base_in`/`_out`, and their v2 variants) are fully permissionless and let any unprivileged user push `total_coin_without_take_pnl` or `total_pc_without_take_pnl` arbitrarily close to zero via the constant-product formula in `swap_token_amount_base_in`/`_out`: [9](#0-8) 

There is no floor/minimum-reserve check preventing a swap from leaving one side's normalized value below the truncation threshold.

### Impact Explanation
Once an attacker (or even organic trading activity) drains one side of the pool down to a raw balance whose decimal-normalized value truncates to `0`, every subsequent `Deposit`, `Withdraw` (outside `WithdrawOnly` status) and `WithdrawPnl` instruction against that pool will panic inside `calc_take_pnl`/`calc_x_power` with a divide-by-zero. Since the underlying vault state that caused the truncation cannot be corrected by any permissionless instruction (deposits/withdraws are exactly the paths that panic), this permanently freezes LP withdrawals and further liquidity operations on the pool — a permanent freezing of LP funds, matching the required impact bar.

### Likelihood Explanation
The attack only requires standard, permissionless `SwapBaseIn`/`SwapBaseOut` transactions with attacker-chosen `amount_in`/`amount_out`, repeated to push a reserve down near dust levels — no privileged signer, no malicious validator, and no off-chain dependency is needed. Pools with low-liquidity or thinly-traded pairs, or pools whose decimal configuration (`coin_decimals`/`pc_decimals` vs `sys_decimal_value`) creates a large truncation threshold, are especially exposed, and thinning out one side of a constant-product pool via large swaps is an ordinary, unprivileged, single/few-transaction action.

### Recommendation
- Replace the `.unwrap()` calls in `Calculator::calc_x_power` (`program/src/math.rs:57-58`) and in `calc_take_pnl`'s `y2` computation (`program/src/processor.rs:208`) with checked operations that return a well-defined `AmmError` (e.g., `AmmError::CalcPnlError`) instead of panicking when the divisor is zero.
- Additionally, guard against `x1 == 0 || y1 == 0` explicitly before entering the pnl-taking branch, and/or enforce a minimum-reserve invariant in `swap_token_amount_base_in`/`_out` so that no swap can decrease the normalized reserve of either token below `1`.

### Proof of Concept
1. Initialize a pool where `coin_decimals = 9` and `sys_decimal_value = 10^6` (a configuration already used in the repo's own test fixtures, e.g. `amm.initialize(0, 0, 2, 9, 1000000, 1)`), giving a truncation threshold of `1000` raw coin units.
2. As any unprivileged user, repeatedly call `SwapBaseIn`/`SwapBaseOut` with attacker-chosen `amount_in`, buying out coin reserve until `amm_coin_vault.amount - amm.state_data.need_take_pnl_coin` (i.e., `total_coin_without_take_pnl`) is a raw value below `1000` (achievable by the constant-product formula in `swap_token_amount_base_in`, since reserves approach but never reach exact `0`, allowing arbitrarily small non-zero residuals).
3. Call `Deposit`, `Withdraw`, or `WithdrawPnl`. `y1 = normalize_decimal_v2(total_coin_without_take_pnl, 9, 1_000_000)` truncates to `0`.
4. `calc_take_pnl` calls `Calculator::calc_x_power(.., y1=0)`, hitting `checked_div(current_y).unwrap()` with `current_y = 0`, panicking the transaction and permanently blocking further deposit/withdraw operations on the pool.

        // must be use u256, because u128 may be overflow
        let x_power = last_x

            .unwrap()
            .checked_mul(current_x)
            .unwrap()
            .checked_div(current_y)
            .unwrap();

    }

    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }

    pub fn swap_token_amount_base_in(
        amount_in: U128,
        total_pc_without_take_pnl: U128,
        total_coin_without_take_pnl: U128,
        swap_direction: SwapDirection,
    ) -> U128 {
        let amount_out;
        match swap_direction {
            SwapDirection::Coin2PC => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (coin + amount_in) * (pc - amount_out) = coin * pc
                // => amount_out = pc - coin * pc / (coin + amount_in)
                // => amount_out = ((pc * coin + pc * amount_in) - coin * pc) / (coin + amount_in)
                // => amount_out =  pc * amount_in / (coin + amount_in)
                let denominator = total_coin_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_pc_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
            SwapDirection::PC2Coin => {
                // (x + delta_x) * (y + delta_y) = x * y
                // (pc + amount_in) * (coin - amount_out) = coin * pc
                // => amount_out = coin - coin * pc / (pc + amount_in)
                // => amount_out = (coin * pc + coin * amount_in - coin * pc) / (pc + amount_in)
                // => amount_out = coin * amount_in / (pc + amount_in)
                let denominator = total_pc_without_take_pnl.checked_add(amount_in).unwrap();
                amount_out = total_coin_without_take_pnl
                    .checked_mul(amount_in)
                    .unwrap()
                    .checked_div(denominator)
                    .unwrap();
            }
        }
        return amount_out;
    }
