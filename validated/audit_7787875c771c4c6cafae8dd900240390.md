Confirmed: the webhook HMAC signature only covers the raw request body (`to_signable_string` returns `@raw_body`), while the tenant identity (`shop-domain` header), `topic`, `webhook_id`, and `api_version` are read from unauthenticated request headers and passed straight into the handler without being part of the signed payload.

### Title
Webhook shop/topic identity not bound to HMAC, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC over the raw request body, but it then trusts the `shop-domain`, `topic`, `webhook-id`, and `api-version` values taken from unauthenticated HTTP headers when dispatching to the app's handler. Since the HMAC secret (`api_secret_key`/`client_secret`) is a single value shared by the app across *all* installed shops, any party who can obtain one genuine, validly-signed webhook body for their own tenant can replay that exact body with forged headers claiming a different shop or topic, and the signature will still validate.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `ShopifyAPI::Utils::HmacValidator.validate` computes `HMAC(secret, to_signable_string)` and compares it against the `hmac` value taken from the request [2](#0-1) . The `hmac`, `topic`, `shop`, `api_version`, and `webhook_id` accessors on `Request` are all pulled from HTTP headers that are not covered by that signature [3](#0-2) .

`Registry.process` only calls `Utils::HmacValidator.validate(request)` before dispatching, then builds `WebhookMetadata` directly from the unauthenticated `request.topic` and `request.shop`: [4](#0-3) 

The binding that should hold is: `bytes_covered_by_hmac == bytes_the_handler_acts_on`. Here that equality is broken — the HMAC only covers `raw_body`, while the handler acts on `shop` and `topic`, which are unauthenticated. Because the `api_secret_key` is one shared value for the whole app (not per-shop), a valid signature obtained via a legitimate webhook to one shop proves only "this body was HMAC'd by our app's secret," not "this event belongs to this specific shop/topic."

### Impact Explanation
This breaks the tenant boundary the gem is documented to provide: `Registry.process` is presented as the mechanism that "will verify the request did indeed come from Shopify" before invoking the shop-specific handler (see `docs/usage/webhooks.md`) [5](#0-4) . An attacker who is a legitimate merchant/tenant of the app (an "unprivileged" party relative to other tenants) can trigger a real webhook for their own shop, capture the `raw_body` + `x-shopify-hmac-sha256` pair, and resend it to the app's public webhook endpoint with a spoofed `x-shopify-shop-domain` (a victim tenant) and/or a different `x-shopify-topic`. The signature still validates because it never covered those fields, so the handler will process attacker-controlled data as if it came from the victim's shop — a cross-tenant access violation.

### Likelihood Explanation
Any app built on this gem that exposes an HTTP webhook endpoint following the documented pattern is affected, and no secret material is needed beyond having one legitimate shop installation of the target app (readily obtainable by any developer signing up for the app). Crafting the forged headers requires only a normal HTTP POST to the app's public webhook URL.

### Recommendation
Include the tenant/topic identity in the signed material, or otherwise cryptographically bind `shop`, `topic`, `webhook_id`, and `api_version` to the verified payload before use — e.g., have `VerifiableQuery#to_signable_string` for webhooks incorporate the shop/topic headers (matching how Shopify actually computes webhook HMACs only over the body, so instead the gem should independently confirm the shop the webhook claims to be for is one that has this app installed/known, and/or document and enforce that consumers must not trust `shop`/`topic` from webhook headers without additional verification against their own shop registry before acting on the payload).

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" with the app installed,
# and receives a genuine webhook for it:
raw_body = '{"id": 1, "malicious": "payload for victim"}'
hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)
# ^ attacker legitimately obtains this pair via their own shop's real webhook delivery

# Attacker now replays the same body+hmac, but claims it is for a different shop/topic:
forged_headers = {
  "x-shopify-topic" => "orders/create",          # topic attacker wants to trigger
  "x-shopify-hmac-sha256" => hmac,               # reused, still valid (body unchanged)
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # spoofed tenant
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# passes HmacValidator.validate (only checks raw_body) and invokes the
# orders/create handler with shop == "victim-shop.myshopify.com"
```

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
