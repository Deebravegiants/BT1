### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the merchant/tenant identity (`shop`) from an unauthenticated HTTP header, while the HMAC that `Registry.process` validates only covers the raw body. An attacker who controls a legitimately installed shop can capture a real, validly-signed webhook body+HMAC pair for their own store, then resend the identical body and HMAC to the app's webhook endpoint with a forged `x-shopify-shop-domain` header pointing at a victim shop. The signature still validates because it is computed only from `@raw_body`, so the application processes attacker-supplied data as if it originated from the victim tenant.

### Finding Description
`Request#shop` reads the tenant identity straight from the header: [1](#0-0) 
but `to_signable_string`, which is what gets HMAC-verified, only returns the raw body bytes: [2](#0-1) 
`Registry.process` validates the HMAC and then immediately trusts `request.shop` for dispatch to the handler: [3](#0-2) 

This breaks the intended binding `hmac_verified(shop, body) == true` down to `hmac_verified(body) == true` while `shop` is taken from an out-of-band, unsigned channel. Any user who can obtain one legitimately signed webhook for their own shop (a normal, unprivileged capability — every app installer receives real webhooks) can replay that exact body+HMAC pair with a different `shop-domain` header value, and the gem will report it as valid and pass the attacker-chosen `shop` on to the consuming application as authoritative tenant identity.

### Impact Explanation
This is a cross-tenant identity confusion: the application's webhook handler receives `WebhookMetadata` whose `shop` field is attacker-controlled despite the HMAC check passing, letting a malicious merchant inject or replay events attributed to another tenant (e.g., forging `orders/create`, `customers/data_request`, or other topic payloads as though they came from a victim's shop). Any app logic that keys session lookup, data writes, or GDPR/mandatory-webhook handling off `WebhookMetadata#shop` without independent verification is directly exposed to cross-tenant data corruption.

### Likelihood Explanation
The prerequisite — owning/installing the app on one's own shop to receive at least one real, correctly signed webhook — is trivial and requires no secrets, tokens, or privileged access; it's the same posture as any other merchant using the app.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook-id`) header values in the string that is HMAC-verified, or otherwise cryptographically bind them to the body before trusting them, so a forged header cannot be paired with a replayed valid body/HMAC.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the raw body and the `x-shopify-hmac-sha256` header Shopify sent.
2. Attacker replays this exact `raw_body` and `hmac` header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) — validation succeeds because the body is unchanged.
4. `handler.handle` is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: ..., ...)` — the app processes attacker-supplied data under the victim's tenant identity.
