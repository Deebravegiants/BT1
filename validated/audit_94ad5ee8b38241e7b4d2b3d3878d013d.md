### Title
Webhook HMAC does not cover the `shop-domain` identity field, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is never included in the HMAC signature that `HmacValidator`/`Registry` verify. Any actor who can obtain one validly-signed webhook body for the shared app secret (e.g., by installing the app on their own store) can replay that body with a forged `shopify-shop-domain` header, and the signature check will still pass because it only signs the raw body.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`, while `Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, entirely outside of what is HMAC-signed: [1](#0-0) [2](#0-1) 

`HmacValidator.validate` (used transitively by `Registry.process`) verifies the signature exclusively against `verifiable_query.to_signable_string`, i.e., the raw body, and never binds the `shop` attribute into the signed material: [3](#0-2) 

Test fixtures confirm the HMAC is computed only over the JSON body (`"{}"`), independent of the `shop-domain` header value: [4](#0-3) 

Handlers registered via `Registry.add_registration`/`Registry.process` receive `data.shop` as the trusted tenant identifier for dispatching business logic (as shown by the handler assertion `assert_equal(@shop, data.shop)`): [5](#0-4) 

The identity binding that should hold is:
`shop_bytes_verified_by_HMAC == shop_bytes_used_for_tenant_dispatch`

In this gem, the left side is empty (the HMAC never covers the shop) while the right side is the raw, attacker-controlled `shop-domain` header — the equality is never enforced, so the two can diverge.

### Impact Explanation
Because the signature only proves "this body was signed with the app's shared secret", not "this body belongs to shop X", any party able to capture one legitimately signed webhook payload (trivially available by installing the app on their own, attacker-controlled shop and observing an inbound webhook) can resubmit that exact body to the host application's webhook endpoint while substituting a victim shop's domain in the `shop-domain` header. `ShopifyAPI::Webhooks::Registry.process` will still validate successfully and dispatch the handler with the forged `shop`, causing the host application to attribute webhook data/events to the wrong tenant — a cross-tenant integrity violation (e.g., an `app/uninstalled` or `orders/paid` webhook attributed to a shop that never sent it), matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Likelihood is high for any app that accepts webhook installs from arbitrary merchants (the common integration pattern): the attacker only needs their own store to install the app once to harvest a validly signed body/HMAC pair, then can replay it indefinitely with any `shop-domain` value, since the header is not bound to the signature and is never re-validated against a known/expected tenant elsewhere in this gem.

### Recommendation
Include the shop identity (and other Shopify-controlled headers such as topic/api-version/webhook-id) in the HMAC-signed material, or otherwise cryptographically bind the `shop-domain` header to the signature before trusting it in `Request#shop`. Short term, document that consumers of `ShopifyAPI::Webhooks::Registry` must independently verify that the reported `shop` corresponds to a shop with an active, matching session/installation before acting on the payload. Long term, add a property test asserting that mutating the `shop-domain` header of an otherwise valid webhook causes HMAC validation to fail.

### Proof of Concept
1. Attacker installs the target app on their own Shopify store (`attacker.myshopify.com`) and receives a legitimate webhook, e.g. `orders/paid`, with headers `x-shopify-hmac-sha256: <valid_hmac>` and `x-shopify-shop-domain: attacker.myshopify.com`, and body `raw_body`.
2. Attacker resends the exact same `raw_body` and `hmac-sha256` header to the host app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. Host app calls `ShopifyAPI::Webhooks::Registry.process(request)`; `HmacValidator.validate` succeeds because it only checks `raw_body` against the shared secret (`lib/shopify_api/utils/hmac_validator.rb:12-31`), and the registered handler is invoked with `data.shop == "victim.myshopify.com"` even though the payload actually originated from the attacker's shop, per `Request#shop` reading directly from the unauthenticated header (`lib/shopify_api/webhooks/request.rb:20-23`).
