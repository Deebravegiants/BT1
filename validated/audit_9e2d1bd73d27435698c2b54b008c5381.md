## Title
Unvalidated JWT `dest` claim used as OAuth host in Token Exchange — SSRF carrying `client_secret` and `client_id` - (File: `lib/shopify_api/auth/token_exchange.rb`)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the destination host for the token-exchange HTTP request directly from the session token's `dest` claim without routing it through `Utils::ShopValidator.sanitize!`, unlike every other OAuth credential-exchange path in the gem (`client_credentials.rb`, `refresh_token.rb`, `token_exchange.rb`'s own `migrate_to_expiring_token`). This breaks the intended equality binding: *"the host that receives the app's `client_secret` == a Shopify-trusted domain"*.

### Finding Description
`exchange_token` takes `dest_shop = jwt_payload.shop`, which is computed in `JwtPayload#shop` as `@dest.gsub("https://", "")` [1](#0-0)  from the JWT's `dest` claim, which is only bounds-checked against `aud == Context.api_key` [2](#0-1) . There is no check that `dest`/`iss` is a `*.myshopify.com`/trusted Shopify domain.

That unvalidated `dest_shop` string is then used to build a live `Session` and `HttpClient`, and a request carrying the app's `client_id`/`client_secret` is sent to it: [3](#0-2) 

`HttpClient#initialize` builds the request URI directly from `session.shop` with no additional validation: [4](#0-3) 

Contrast this with the sibling method in the very same file, `migrate_to_expiring_token`, and with `ClientCredentials.client_credentials` / `RefreshToken.refresh_access_token`, which all call `Utils::ShopValidator.sanitize!(shop)` before constructing the session/host: [5](#0-4) [6](#0-5) [7](#0-6) 

`ShopValidator.sanitize!` is the gem's only mechanism to enforce "host == trusted Shopify domain" [8](#0-7) , but `exchange_token` never calls it on `dest_shop`.

Because the JWT is HS256-signed with the app's own `Context.api_secret_key`, this is not directly forgeable by an unprivileged internet user without the secret — the exploitability hinges on whether an app's own embedded frontend (or a malicious/compromised extension context that can obtain a validly-signed session token for an attacker-influenced `dest`) can supply an arbitrary `dest` value. Since Shopify itself issues these tokens and constrains `dest` to the requesting store's domain, this is a defense-in-depth gap rather than a directly attacker-triggerable bypass under normal operation — I could not find a code path in this gem (outside of Shopify's own token issuance, which is out of scope/unverifiable from this repo) that lets an unprivileged caller set an arbitrary `dest`.

### Impact Explanation
If `dest` could ever contain a non-Shopify host (e.g., via a bug elsewhere, a misissued/rogue token, or a supported "spin.dev"/custom domain edge case not covered by `ShopValidator`'s allow-list), `exchange_token` would perform an outbound HTTPS POST containing `client_id` and `client_secret` (the app's confidential credentials) to that attacker-controlled host — SSRF with credential exfiltration, matching the report's "High" bucket (SSRF with the app's credentials / credential leakage).

### Likelihood Explanation
Low-to-uncertain from an unprivileged-internet-user perspective within this gem alone: the `dest` claim is inside a signed JWT that only Shopify issues, and `JwtPayload` validates `aud` and signature/expiry. I was not able to find, within `lib/shopify_api/**` (excluding generated REST resources), a path that lets an external actor forge or otherwise control the `dest` claim without the `client_secret`. This weakens the analog to "defense-in-depth omission" rather than a proven, concretely exploitable bypass by an unprivileged internet user.

### Recommendation
In `TokenExchange.exchange_token`, validate `dest_shop` through `Utils::ShopValidator.sanitize!` (as already done in `migrate_to_expiring_token`, `client_credentials`, and `refresh_token`) before constructing the `Session`/`HttpClient`, so the host that receives `client_id`/`client_secret` is always provably bound to a trusted Shopify domain, closing the inconsistency with the rest of the OAuth surface.

### Proof of Concept
Could not be concretely demonstrated as an unprivileged-internet-user attack: it requires control over the `dest` claim of a JWT that only validates successfully when signed with the app's own `api_secret_key` (or `old_api_secret_key`). No path was found in the in-scope library code that allows an external actor to supply this claim without already possessing the secret, so this is reported as a code-level inconsistency/defense-in-depth gap discovered while mapping the report's "unchecked value trusted downstream" bug class onto this gem's identity-binding surfaces, not as a proven, independently exploitable vulnerability.
