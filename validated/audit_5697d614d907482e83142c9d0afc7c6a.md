### Title
Unsigned dispatch of arbitrary runtime calls using unauthenticated `from` bytes as origin - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`HyperFungibleToken::on_accept` decodes an incoming cross-chain `PostRequest` body into a `Message { from, to, amount, data }` and, when `data` is non-empty, decodes it further into a `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call }` and dispatches `runtime_call` on the destination chain [1](#0-0) . When `signature` is `None`, the dispatch origin is derived directly from the message's `from` bytes with no cryptographic check binding that account to the specific `runtime_call` being executed [2](#0-1) . This mirrors the ejs `renderFile` class of bug: an attacker-influenced field from the message body (`from`) is trusted to authorize a sensitive action (arbitrary call dispatch) without independently validating the binding between the claimed identity and the payload.

### Finding Description
`SubstrateCalldata.runtime_call` is fully attacker-controlled — it is SCALE-encoded arbitrary `T::RuntimeCall` bytes carried inside the ISMP request body, which itself originates from `SendParams.call_data: Option<Vec<u8>>` supplied by whoever calls the bridging entrypoint [3](#0-2) .

For the substrate-native branch of the `from` conversion, the pallet copies the raw `from_bytes` from the message body directly into a 32-byte `AccountId` and uses it as the dispatch origin when no signature is supplied:
```
} else {
    let from_bytes = message.from.as_ref();
    if source.is_evm() {
        T::EvmToSubstrate::convert(H160::from_slice(&from_bytes[from_bytes.len() - 20..]))
    } else {
        let mut account = [0u8; 32];
        account.copy_from_slice(from_bytes);
        account.into()
    }
};
``` [2](#0-1) 

The pallet only checks `BaseCallFilter::contains` before dispatch [4](#0-3) ; it does not verify that the entity identified by `from` actually produced or approved `runtime_call` unless a signature is separately supplied. The signature check, when present, only re-derives the payload hash from `(nonce, runtime_call)` and checks it against the *claimed* `beneficiary` computed from the same untrusted `from`/`to` fields [5](#0-4) , so the `None` branch is a deliberate "skip validation" fallback that only holds if the value placed into `message.from` on the sending side is unforgeable and always equals the true, cryptographically-verified initiator of the exact `SubstrateCalldata` — a property that the pallet itself cannot verify at the receiving end since `from` is opaque payload data authenticated only at the ISMP-request/contract-address level (`ContractToAsset` lookup), not per-field.

### Impact Explanation
If the sending side (an EVM contract or another chain's bridging module) ever permits `from` to diverge from the true, signature-verified initiator of `call_data` — for example, through a bridging path that is generic, upgraded, misconfigured, or itself has a validation gap — this code path lets an unprivileged token bridger cause the destination pallet to dispatch an arbitrary `RuntimeCall` as any account whose 32-byte identifier can be placed into `message.from`, bypassing the extrinsic-signature security model entirely. Because the call is dispatched with `RawOrigin::Signed(origin)` [6](#0-5) , this is equivalent to unauthorized-app-action / privilege escalation for whatever pallets are reachable through the runtime's `BaseCallFilter` (e.g. transfers, governance votes, staking operations) — a direct route to theft or freezing of funds belonging to the impersonated account.

### Likelihood Explanation
Exploitability depends entirely on whether the source-side encoder can be made to set `message.from` to a value not actually authorized to execute the paired `runtime_call`. I could not fully verify the Solidity/other-chain encoder (`sdk/packages/core/contracts/apps/HyperFungibleToken.sol`) enforces `from == msg.sender` in all code paths within the available index; this is the key open question left unresolved. The destination-side pallet code, however, unconditionally trusts `from` as an authorization credential whenever no signature is attached, which is the weak-input-validation root cause regardless of what the sender-side guarantees today — any future/alternate encoder path that does not tie `from` 1:1 to a validated signer reopens this into a full account-takeover primitive reachable from a single relayed cross-chain message.

### Recommendation
Do not use the `None`-signature branch to derive a dispatch origin directly from message-body bytes. Either require a signature (bound to `nonce` and `runtime_call`) unconditionally for any calldata execution, or, if the "no signature needed" self-authorization design is intentional, cryptographically prove at the destination that `from` matches the ISMP request's verified source-chain transaction sender (not just an opaque body field) before using it as a dispatch origin.

### Proof of Concept
1. A relayer submits a valid ISMP `PostRequest` from a registered `source` contract (satisfying the `ContractToAsset` lookup) whose ABI-encoded body sets `Message.from` to the 32/20-byte identifier of a *victim* account, and `Message.data` to a `SubstrateCalldata { signature: None, runtime_call: <arbitrary call, e.g. Balances::transfer_all to attacker> }`.
2. `on_accept` reaches the `data` branch, decodes `SubstrateCalldata`, takes the `signature.is_none()` path, and computes `origin` directly from `from_bytes` without any proof the victim authorized `runtime_call` [2](#0-1) .
3. `runtime_call.dispatch(RawOrigin::Signed(origin))` executes as the victim, subject only to `BaseCallFilter` [7](#0-6) .
