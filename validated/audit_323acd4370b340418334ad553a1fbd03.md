### Title
Withdraw slippage protection is silently skipped when `min_coin_amount`/`min_pc_amount` are omitted - (File: `program/src/processor.rs`)

### Summary
The `Withdraw` instruction accepts optional slippage-protection parameters (`min_coin_amount`, `min_pc_amount`). When a submitted instruction omits these optional fields, `process_withdraw` performs the LP burn and token transfers with **no** slippage check at all, exactly mirroring the GMX `DecreaseOrderUtils` bug where the minimum-output check is skipped on the path where no explicit protection parameter is supplied.

### Finding Description
`AmmInstruction::unpack` for the `Withdraw` tag (`4`) only sets `min_coin_amount`/`min_pc_amount` to `Some(..)` if the instruction data contains at least 16 extra bytes beyond `amount`; otherwise both are set to `None`: [1](#0-0) 

In `Processor::process_withdraw`, the resulting `coin_amount`/`pc_amount` (computed from the LP-to-token exchange rate after `calc_take_pnl` adjusts the pool reserves) are only checked against `min_coin_amount`/`min_pc_amount` when **both** are `Some`: [2](#0-1) 

If a caller submits `Withdraw` instruction data containing only the 8-byte `amount` field (i.e., omitting the 16 optional bytes), both `min_coin_amount` and `min_pc_amount` unpack to `None`, and the `if withdraw.min_coin_amount.is_some() && withdraw.min_pc_amount.is_some()` guard is never entered — the transfer and LP burn proceed at whatever `coin_amount`/`pc_amount` the current pool state (post `calc_take_pnl`) yields, with zero enforced slippage bound: [3](#0-2) 

This is directly analogous to the GMX report: a user-facing slippage-protection parameter exists in the instruction schema, but the program silently bypasses the check on a specific, reachable code path (here: omitting the optional fields) rather than enforcing it unconditionally.

### Impact Explanation
An LP withdrawing liquidity via a `Withdraw` instruction built without the optional min-amount fields receives no slippage protection whatsoever. This exposes the withdrawer to sandwich attacks: an attacker observing the pending `Withdraw` transaction can submit swaps immediately before it (skewing `total_pc_without_take_pnl`/`total_coin_without_take_pnl`, which directly feed `coin_amount`/`pc_amount` via `InvariantPool::exchange_pool_to_token`) and reverse the swap afterward, extracting value from the withdrawing LP with no on-chain check preventing it. This is a concrete loss of LP funds via a manipulable withdrawal price, reachable purely by an unprivileged actor observing/crafting transactions — no privileged signer or off-chain trust assumption is required.

### Likelihood Explanation
Any client (wallet, integrator, bot) that constructs the raw `Withdraw` instruction without appending the optional 16 bytes (e.g., relying on the minimal/legacy instruction encoding, or a bug/oversight in instruction-building code) will produce a withdrawal with zero slippage enforcement. Because the fields are `Option<u64>` and are silently treated as "no protection requested" rather than being mandatory, this is an easy and likely-to-occur misconfiguration, and it is trivially exploitable by any attacker monitoring the transaction pool who can front/back-run the affected withdrawal within the same or adjacent slot.

### Recommendation
Do not make slippage protection conditional on both fields being populated. Either (a) make `min_coin_amount`/`min_pc_amount` mandatory (non-`Option`) so every `Withdraw` instruction must specify a minimum, or (b) enforce the check whenever at least one of the two is `Some` (checking only the provided bound), so a partially-specified or entirely-unspecified slippage bound cannot silently disable protection for the withdrawer.

### Proof of Concept
1. Attacker observes a pending `Withdraw` transaction from a victim LP where the instruction data was built with only the `amount` field (8 bytes total payload after the tag byte), so `unpack` yields `min_coin_amount = None`, `min_pc_amount = None` per `program/src/instruction.rs` lines 372-386.
2. Attacker submits a swap (e.g., `SwapBaseIn`) immediately before the victim's transaction to shift `amm_pc_vault.amount`/`amm_coin_vault.amount`, which changes `total_pc_without_take_pnl`/`total_coin_without_take_pnl` computed in `process_withdraw` (`program/src/processor.rs` lines 1719-1724).
3. The victim's `Withdraw` executes: since `min_coin_amount.is_some() && min_pc_amount.is_some()` is `false`, the guard at lines 1780-1786 is skipped entirely, and the LP burn/transfer proceeds at the manipulated `coin_amount`/`pc_amount` (lines 1787-1812) regardless of how unfavorable it is.
4. Attacker submits a reverse swap immediately after to restore the pool price, having extracted value from the victim's withdrawal with no on-chain slippage guard having triggered.
