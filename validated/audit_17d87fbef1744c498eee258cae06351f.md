### Title
Webhook shop domain, topic, and API-version headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (`lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `ShopifyAPI::Utils::HmacValidator.validate` authenticates nothing but the bytes of the body. The `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, `X-Shopify-Api-Version`, and `X-Shopify-Webhook-Id` headers — which `ShopifyAPI::Webhooks::Registry.process` trusts to route the event and identify the tenant — are read directly from unauthenticated headers and never bound into the HMAC computation.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements the `Utils::VerifiableQuery` interface: [1](#0-0) 

Notice that `hmac` is read from the `hmac-sha256` header, but `to_signable_string` returns only `@raw_body` — it does not include `shop`, `topic`, `api_version`, or `webhook_id`. `HmacValidator.validate` then only proves that `raw_body` was signed with the app's secret: [2](#0-1) 

`Webhooks::Registry.process` uses this validation result as sole proof of authenticity, then dispatches the handler using the *unauthenticated* `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version`: [3](#0-2) 

This is the same bug class as the LOADW/STOREW report: a value that is acted upon (`request.shop`, used as the tenant identity passed to the handler) is not constrained/bound by the authenticity check (the HMAC only covers `raw_body`). The binding that should hold is:

`HMAC-valid(raw_body) ⇒ (shop, topic, webhook_id, api_version) are exactly the values Shopify intended for that body`

but the gem only proves `HMAC-valid(raw_body)`, leaving `shop`/`topic`/etc. completely attacker-controlled at the HTTP layer.

Because a given app's `client_secret` is shared across every shop that installs it, any user who installs the app on a shop they control legitimately receives real `(raw_body, hmac)` pairs signed with the app's secret. That same body/HMAC pair remains valid regardless of which shop header accompanies it, since the shop is never part of the signed content.

### Impact Explanation
An attacker who has installed the target app on a shop they control (something any unprivileged internet user can do for a public/embedded app) can:
1. Capture a legitimate `(raw_body, X-Shopify-Hmac-Sha256)` pair delivered to the app's public webhook endpoint for their own shop.
2. Replay a POST directly to the same public webhook endpoint, keeping the body and HMAC identical, but substituting `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) with a victim merchant's shop domain.
3. `HmacValidator.validate` still returns `true` because it only checks the body bytes, so `Registry.process` invokes the app's handler with `shop: <victim-shop>`.

The host application's webhook handler will process attacker-supplied data as if it originated from the victim shop — this is a cross-tenant identity-binding break reachable without the app's `client_secret`, without an access token, and without any credential belonging to the victim, satisfying the "Critical - cross-tenant access" impact bar.

### Likelihood Explanation
Webhook processing is a core, frequently-exercised flow for every app using this gem (`ShopifyAPI::Webhooks::Registry.process` is the documented entry point for all webhook delivery), and the only barrier to exploitation is installing the target app on an attacker-owned shop — something typically open to any internet user for public apps. Likelihood is high.

### Recommendation
Bind the tenant/routing metadata into the HMAC-verified content instead of trusting unauthenticated headers. At minimum, `Registry.process` should independently verify that `request.shop` corresponds to a session/shop actually known to belong to the webhook subscription being referenced (e.g., cross-check against the shop that the app registered the webhook for, using `webhook_id`), or the signable string should incorporate the shop domain and topic so a body signed for shop/topic A cannot be replayed as shop/topic B. Shopify's newer webhook verification guidance recommends validating `X-Shopify-Shop-Domain` against a known/expected store list per delivery, rather than trusting it merely because the raw body's HMAC checks out.

### Proof of Concept
1. Attacker installs the target multi-tenant app on `attacker-shop.myshopify.com` (a shop they control) and triggers a webhook event (e.g., `app/uninstalled`), causing Shopify to POST a `(raw_body, hmac)` pair to the app's public webhook endpoint, with headers:
   ```
   X-Shopify-Topic: app/uninstalled
   X-Shopify-Hmac-Sha256: <valid HMAC of raw_body>
   X-Shopify-Shop-Domain: attacker-shop.myshopify.com
   ```
2. Attacker captures `raw_body` and `X-Shopify-Hmac-Sha256` (e.g., by controlling their own logging proxy in front of their own store's traffic — no TLS interception of Shopify or the victim required).
3. Attacker sends a new POST directly to the app's public webhook URL with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but:
   ```
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` (`lib/shopify_api/webhooks/request.rb:10-38`) only look at the body, so `HmacValidator.validate` returns `true`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) invokes the handler with `shop: "victim-shop.myshopify.com"`, causing the host app to process a forged event attributed to a shop the attacker does not control.
