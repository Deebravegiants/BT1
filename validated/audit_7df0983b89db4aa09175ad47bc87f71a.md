### Title
Mid-signup config mutation causes inconsistent `ignore_user_centric_signups`/`self_serve` enforcement, enabling unauthorized enrollment or signup-state bleed - (File: `src/plans/mod.rs`, `src/brokers/observer.rs`)

### Summary
The reported bug class is "a mutable shared configuration value read at multiple disjoint points of a stateful, multi-step lifecycle, where a value change mid-lifecycle causes the later steps to act on a different assumption than the one made at the start, with no mechanism to keep the lifecycle internally consistent." In orb-core, `Config` is held behind a single `Arc<Mutex<Config>>` that is *overwritten wholesale* by a background task every `CONFIG_UPDATE_INTERVAL` while a signup is in progress, and `MasterPlan::do_signup` re-reads individual fields from that same shared `Config` at multiple separate points during one signup instead of freezing a single snapshot for the whole lifecycle.

### Finding Description
`DefaultPlan::config_update` in `src/brokers/observer.rs` runs on every tick and replaces the entire shared config object in place: [1](#0-0) 
This task runs concurrently with `MasterPlan::run`/`do_signup` — there is no coordination that pauses config downloads for the duration of an in-progress signup, and `signup_flag` (also present in the `Observer`) is not consulted by `config_update`.

`MasterPlan::do_signup` reads a config snapshot once at the very start of the signup via destructuring `*orb.config.lock().await`, capturing `self_serve`, `pcp_v3`, etc.: [2](#0-1) 
But later in the *same* signup it re-acquires the lock and reads fresh, independent values, e.g. `ignore_user_centric_signups` right before deciding whether to perform full backend enrollment or to short-circuit success based on local pipeline results: [3](#0-2) 
and `self_serve` again during `after_signup` to decide whether to notify the relay of `SignupEnded`: [4](#0-3) 

Because a backend config push (a legitimate, unprivileged/remote-config-driven event, not an operator/admin action inside the Orb) can land between the start-of-signup snapshot and these later reads, the signup can proceed with a `user_centric_signup` decision made under one `ignore_user_centric_signups` setting while the branch that actually determines whether "success" is credited to enrollment is evaluated under a different, freshly-fetched value. This is the same structural flaw as the `AgentFactory` bug: a value fixed at the start of a stateful record (the `Application`/here the in-flight signup) is instead re-read from mutable global state at each downstream use site, so an external mutation between those use sites desynchronizes the record's outcome from its original invariants.

### Impact Explanation
If `ignore_user_centric_signups` toggles from `false` to `true` mid-signup (or vice versa) due to a routine backend config refresh, `do_signup` can take the "user-centric" fast-success path (crediting `success = signup_reason == SignupReason::Normal` without actually calling `enroll_user`) even though the config value that governed the *decision to fetch/trust that branch* was different from the one governing whether the branch's crediting behavior is safe. This creates a state-bleed window where a signup's success/enrollment attribution no longer matches the single consistent policy the operator/backend intended for that signup, i.e., the enrollment outcome recorded for the signup ID does not correspond to any single coherent configuration the backend served, which is an inconsistency in exactly the class of impact called out in the report (misattributed outcome from stale/mutated shared state).

### Likelihood Explanation
`config_update` runs unconditionally on a fixed timer independent of `signup_flag ` state, and a full signup (`do_signup`) can easily span multiple `CONFIG_UPDATE_INTERVAL` ticks (biometric capture, AI pipeline inference, PCP building, and multi-tier upload all involve seconds of I/O and inference). This makes the race a routine occurrence under normal backend config-push cadence rather than a rare edge case, though it requires the backend to actually change `ignore_user_centric_signups` (or another config flag read at multiple call sites) between two reads in the same signup to materialize.

### Recommendation
Snapshot the entire `Config` once at `do_signup` entry (already partially done) and thread that single, immutable snapshot through all internal helper calls (`enroll_user` gating, `after_signup`, `after_biometric_capture`, etc.) instead of re-acquiring `orb.config.lock().await` at each site. Alternatively, have `DefaultPlan::config_update` in `src/brokers/observer.rs` defer applying a newly downloaded config while `signup_flag` is set (it already has access to `signup_flag`), applying it only once the in-flight signup completes, matching the "freeze then apply consistently" fix pattern recommended for the analog `AgentFactory` case (fixing the value at the object's creation instead of at each use site).

### Proof of Concept
1. Start a signup; `do_signup` captures `ignore_user_centric_signups = false` at entry (`src/plans/mod.rs:497-506`).
2. While biometric capture/pipeline execute (multi-second operation), the backend config endpoint is updated so that a subsequent poll from `DefaultPlan::config_update` (`src/brokers/observer.rs:187-205`) overwrites the shared `Config` with `ignore_user_centric_signups = true`.
3. `do_signup` reaches line 639 and now reads the *new* value (`true`), causing it to skip `enroll_user` and instead credit `success` purely based on local `signup_reason`, deviating from the policy in effect when the signup started.
4. No log, audit trail, or check reconciles the two different `Config` snapshots observed within one signup lifecycle.
