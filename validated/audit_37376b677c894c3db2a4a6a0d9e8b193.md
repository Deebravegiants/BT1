### Title
Unhandled Arithmetic-Panic in `calc_take_pnl` Causes Permanent Denial-of-Service, Freezing LP Deposits/Withdrawals - ([File: program/src/processor.rs])

### Summary
`Processor::calc_take_pnl` — invoked from `process_deposit`, `process_withdraw`, and `process_withdrawpnl` — performs a chain of `.checked_sub(...).unwrap()` operations on values derived from live vault token balances and a previously-cached "last k" checkpoint (`TargetOrders.calc_pnl_x/y`). An attacker who can widen the gap between the pool's cached checkpoint and its live vault balances (e.g., by sending SPL tokens directly into the AMM's vault accounts, which requires no special privilege) can make the internal `x2`/`y2` estimate exceed the live `x1`/`y1` values passed into the subtraction, triggering a Rust panic. Because every `Deposit`, `Withdraw`, and `WithdrawPnl` instruction calls this same function on the pool's persistent state, once this condition is triggered it reproducibly aborts subsequent calls, permanently freezing LP deposits, withdrawals, and PnL collection for the affected pool — directly analogous to the mongodb DoS advisory, where an unhandled exception on attacker-influenced input crashed application logic.

### Finding Description
`calc_take_pnl` gates on a coarse inequality check between raw pool amounts and restored-decimal "last pnl" values: [1](#0-0) 

If that (imprecise, integer-truncated) check passes, the function proceeds to compute `x2` via `calc_x_power`/`integer_sqrt` and `y2 = x2 * y1 / x1`, then subtracts them from the live normalized amounts using unchecked `.unwrap()`: [2](#0-1) 

The guarding inequality at line 190 compares products of raw pool balances against **restored-decimal** (`Calculator::restore_decimal`) reconstructions of the cached `calc_pnl_x`/`calc_pnl_y`, while the actual subtraction at lines 213–214 operates on **normalized** (`Calculator::normalize_decimal_v2`) values computed independently via multiply-then-integer-divide arithmetic in `U256`. These two code paths do not use identical rounding/order-of-operations, so the coarse check does not guarantee `x2 <= x1` and `y2 <= y1` in all cases — particularly when the live vault ratio has been pushed far from the cached checkpoint ratio, which is achievable because `amm_coin_vault`/`amm_pc_vault` balances (read via `unpack_token_account`) are ordinary SPL token accounts that anyone can credit directly with `spl_token::transfer`, bypassing the AMM's own deposit accounting: [3](#0-2) 

`Calculator::normalize_decimal_v2` and `restore_decimal` both use raw `checked_mul`/`checked_div` with `.unwrap()`, reinforcing that this whole computation path assumes success and has no recovery/error path for the subtraction underflow: [4](#0-3) 

This helper is not a leaf utility — it is on the hot path of every state-mutating LP operation:
- `process_deposit` calls `calc_take_pnl` before minting/burning LP tokens: [5](#0-4) 
- `process_withdraw`/`process_withdrawpnl` call the same function before releasing pc/coin to the LP: [6](#0-5) 

Once the pool's persistent on-chain `TargetOrders.calc_pnl_x/y` checkpoint is left in a state where this panic condition recurs (which it will, since the checkpoint is only updated inside this same function on successful completion), **every future Deposit, Withdraw, and WithdrawPnl transaction against that pool will panic and abort**, since the underlying account state that produces the mismatch persists across transactions.

### Impact Explanation
A successful trigger permanently blocks all LP-facing state mutations (`Deposit`, `Withdraw`, `WithdrawPnl`) for the affected pool, since they all route through the panicking `calc_take_pnl` call using persisted on-chain state that does not self-correct. This constitutes permanent freezing of LP funds already deposited in the pool — LPs can no longer withdraw their liquidity or accrued PnL through the normal instruction set. This satisfies the "permanent freezing of user or LP funds" bar.

### Likelihood Explanation
The precondition — inflating a vault's SPL token balance without going through the AMM's own Deposit path — requires only a standard `spl_token::transfer` to a publicly known vault address and no elevated privilege, signer authority beyond the attacker's own token account, or validator/off-chain assistance. The specific numeric conditions needed to make `x2 > x1` or `y2 > y1` depend on the pool's existing decimals/ratio and require some numerical analysis/trial by the attacker, which lowers ease of exploitation somewhat, but the reachable surface (single transaction, attacker-chosen token amount sent to a writable, publicly-known vault account) is fully within reach of any unprivileged actor.

### Recommendation
- Replace all `.unwrap()` calls inside `calc_take_pnl` (and the `normalize_decimal_v2`/`restore_decimal` helpers it depends on) with `checked_*` operations that propagate a proper `AmmError` (e.g., `CheckedSubOverflow`) instead of panicking.
- Align the gating inequality at `processor.rs:190-192` to use the exact same decimal-normalization path as the subsequent `x2`/`y2` computation so the guard is mathematically sound, or use saturating arithmetic with an explicit early return on out-of-range results.
- Add a recovery/reset path so that if the checkpoint (`TargetOrders.calc_pnl_x/y`) and live vault state ever diverge beyond safe bounds, `WithdrawPnl`/`Withdraw` can still complete (e.g., clamp pnl to zero) rather than permanently reverting.

### Proof of Concept
1. Create a pool with `Initialize2`, establishing an initial coin/pc ratio and a `TargetOrders.calc_pnl_x/y` checkpoint via the first successful `Deposit`.
2. As an unprivileged actor, issue a plain SPL Token `Transfer` instruction sending a large, disproportionate amount of one side's mint directly into the pool's `amm_coin_vault` (or `amm_pc_vault`) associated token account — no AMM instruction is required, only the vault's public address.
3. Submit a subsequent `Deposit` or `Withdraw` instruction. `process_deposit`/`process_withdraw` reads the now-skewed vault balances via `unpack_token_account`, computes `x1`/`y1` from them, and calls `calc_take_pnl` with the stale `TargetOrders` checkpoint.
4. If the skew is large enough that the coarse gating check at line 190 still passes but the finer-grained `x2`/`y2` estimate exceeds `x1`/`y1`, the `checked_sub(...).unwrap()` at line 213 or 214 panics, aborting the transaction.
5. Because the checkpoint was never updated (the panic occurs before line 245+ update logic), every subsequent `Deposit`/`Withdraw`/`WithdrawPnl` against this pool reproduces the same panic, permanently freezing LP funds in the pool.
