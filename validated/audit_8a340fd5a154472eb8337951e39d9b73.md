**Analysis:**

`ResourceGroupAdapter::get_resource_from_group_impl` requires `self.maybe_resource_group_view.is_none()` and asserts on it [1](#0-0) . The branch selection between forwarding to `maybe_resource_group_view` and using the local `group_cache` path is not a per-call dynamic choice — it is fixed once at construction time in `ResourceGroupAdapter::new`, where `maybe_resource_group_view` is filtered to `None` unless `group_size_kind == GroupSizeKind::AsSum` [2](#0-1) . Once an adapter instance exists, `get_resource_from_group` always takes the same branch for every call over its lifetime [3](#0-2) , so there is no way for the same `group_key`/`resource_tag` pair to be resolved via both paths within one adapter's lifetime, and thus no possibility of the two paths returning different bytes for the same tag within that instance.

The `set_group_view_forwarding` test cited in the question only demonstrates that a `ResourceGroupAdapter` can itself be wrapped as the `ResourceGroupView` for an outer adapter [4](#0-3) . That is intentional layered composition (e.g., block executor's view wrapping a base state view), not two independent, divergent data sources — the inner adapter is the single source of truth that the outer one forwards to, so both ultimately resolve to the same underlying `resource_view`/`group_cache` data rather than two independently-computed values for the same tag.

Since the adapter's forwarding decision is fixed at construction (driven by VM-internal `gas_feature_version` and `resource_groups_split_in_vm_change_set_enabled` configuration, not unprivileged transaction input), there's no attacker-controlled path that induces a call-order-dependent mismatch, and thus no custody-relevant balance/owner corruption for `FungibleStore`/`Object` resources.
