Confirmed: the webhook `shop` value is entirely outside the HMAC-signed payload.

### Title
Webhook `shop` tenant identity is not covered by the HMAC signature, allowing cross-tenant attribution forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)`, where the signable content is defined by `Request#to_signable_string` as just `@raw_body`. The `shop` attribute used to identify the tenant for the delivered event is read straight from the `x-shopify-shop-domain` HTTP header, which plays no part in the HMAC computation at all.

### Finding Description
The webhook processing pipeline is:
1. `Request#hmac` decodes the `X-Shopify-Hmac-Sha256` header value. [1](#0-0) 
2. `Request#to_signable_string` returns only the raw request body — no headers are included in the signed material. [2](#0-1) 
3. `Request#shop` is derived independently from the `shop-domain` header, entirely decoupled from the signed bytes. [3](#0-2) 
4. `Registry.process` verifies the HMAC over the body only, then immediately trusts `request.shop` as the tenant identity when dispatching to the handler. [4](#0-3) 

The broken identity binding, stated as an equality that should hold but doesn't:
`shop header value used for tenant attribution == shop value cryptographically bound by the HMAC`

Since the `shop-domain` header is never part of `to_signable_string`, the equality never has to hold for the signature to validate. Any request whose `raw_body` + `hmac` pair is a legitimately Shopify-signed pair (e.g., the merchant's own valid webhook payload for topic X, which the merchant will naturally receive for their own store) can be replayed verbatim to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a different (victim) shop domain. `HmacValidator.validate` will still succeed because it only recomputes the HMAC over `@raw_body`, and `Registry.process` then calls `handler.handle(data: WebhookMetadata.new(topic:, shop: request.shop, body:, ...))` with the attacker-controlled shop value.

### Impact Explanation
This is a cross-tenant identity-binding break: the library-provided guarantee that "a webhook whose HMAC validates belongs to the shop it claims to be from" does not hold, because `shop` is unauthenticated data. Any app that keys tenant-scoped side effects (data storage, entitlement changes, session/token lookups, redact/GDPR handling, order/inventory sync, etc.) off `WebhookMetadata#shop` as returned by this gem is exposed to forged cross-tenant events — e.g., an attacker with a legitimate account on their own shop can cause the app to record or act on data under a victim shop's identity, satisfying the Critical "cross-tenant access" impact category. Note this also affects the three mandatory compliance topics (`shop/redact`, `customers/redact`, `customers/data_request`) registered by `Registry`, which are commonly used to drive data deletion by shop. [5](#0-4) 

### Likelihood Explanation
No privileged credentials, `api_secret_key`, or access token are required. The attacker only needs to be an ordinary, unprivileged merchant/user of their own Shopify store to legitimately receive at least one real webhook (body + valid HMAC) for that store, and then replay the raw body with a swapped `shop-domain` header to the target app's public webhook endpoint. The gem's HMAC check offers no barrier to this because it does not cover the header at all.

### Recommendation
Bind the tenant identity into the signature verification, or otherwise cross-check it against a source of truth:
- If feasible, include the `shop-domain` (and `topic`) header values in the signable string alongside the raw body so HMAC validation fails on any mismatch, or
- At minimum, document/require that consuming applications cross-verify `request.shop` against a shop the app has an active, previously-established session/installation for (not merely "HMAC valid") before trusting it for tenant-scoped actions, mirroring the mitigation pattern of binding all security-relevant fields into the verified payload as done for `AuthQuery` in `lib/shopify_api/auth/oauth/auth_query.rb`, which signs `code`, `host`, `shop`, `state`, and `timestamp` together. [6](#0-5) 

### Proof of Concept
```ruby
# 1. Attacker legitimately owns "attacker-shop.myshopify.com" and has the app installed there.
#    Shopify delivers a real webhook to the app for that shop, e.g. orders/create:
raw_body = '{"id":1,"note":"legit order on attacker shop"}'
valid_hmac_b64 = "<value Shopify actually sent in X-Shopify-Hmac-Sha256 for the above body>"

# 2. Attacker replays the exact same raw_body/hmac pair, only changing the shop header:
headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => valid_hmac_b64,   # still validates: HMAC only signs raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, unauthenticated
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (only checks raw_body),
#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)) is invoked,
#    causing the app to process/store data attributed to victim-shop.myshopify.com.
``` [7](#0-6)
