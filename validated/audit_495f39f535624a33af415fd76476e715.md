Based on my investigation, I found a genuine structural analog to the GovernorCompatibilityBravo bug class in the ISMP GET-response handling path: the correspondence between requested `keys` and returned `values` in a `GetResponse` is silently broken by a `BTreeMap`-based implementation, similar to how an implicit array-index correspondence (`calldatas[i]` ↔ `signatures[i]`) silently broke down in the OpenZeppelin advisory.

### Title
GetResponse values may be silently reordered relative to requested keys via BTreeMap collection - ([File: modules/ismp/core/src/handlers/response.rs])

### Summary
The ISMP `handle` function for `ResponseMessage` builds each `GetResponse.values` array by calling `state_machine.verify_state_proof(...)`, which internally groups and returns results in a `BTreeMap<Vec<u8>, Option<Vec<u8>>>` [1](#0-0) . A `BTreeMap` iterates in ascending byte-order of its keys, not in the original order of `request.keys`. Documentation for both the EVM handler (`handleGetResponses`) and the `IApp` interface explicitly promises consumers that "Values are provided in same order as requested keys" [2](#0-1) [3](#0-2) , and best-practice guidance explicitly tells app authors to "Handle multiple keys in order" rather than match on the `key` field.

### Finding Description
`verify_state_proof` on the EVM state machine groups keys by contract address into a `BTreeMap`, resolves storage proofs per contract, and finally inserts `(key, value)` pairs into a `BTreeMap<Vec<u8>, Option<Vec<u8>>>` result map [4](#0-3) . The response handler then does:
```
let values = state_machine
    .verify_state_proof(host, keys, state.state_root, &proof)?
    .into_iter()
    .map(|(key, value)| StorageValue { key, value })
    .collect();
``` [5](#0-4) 

Because the map is a `BTreeMap`, `.into_iter()` yields entries sorted by the raw key bytes, not in the order the requester supplied `request.keys`. If an application dispatches a GET request with multiple keys whose lexicographic byte order differs from their semantic/intended order (e.g., querying two different contract slots, or two accounts whose addresses sort differently than the order the caller cares about), the resulting `values` array delivered to `on_response`/`onGetResponse` will not align positionally with the keys as originally submitted, even though `StorageValue` also carries the `key` field — many downstream consumers (per the documented best-practice "Handle multiple keys in order") index into `values[i]` assuming it corresponds to `keys[i]`, exactly the same implicit-array-correspondence assumption that GovernorCompatibilityBravo violated between `calldatas[i]` and `signatures[i]`.

The same-style non-membership check (`verify_non_membership`) and other verify_state_proof implementations (e.g. `substrate_evm.rs`) at least check `result_map.len() != keys_len` [6](#0-5) , but this only guards against missing entries, not against reordering — the length check passes even though ordering is wrong.

### Impact Explanation
Any `IIsmpModule`/`IApp` implementation that issues a multi-key GET request and relies on `values[i]` corresponding to `keys[i]` (as explicitly told to do by protocol documentation) can misattribute a storage value to the wrong logical key. Depending on the app's logic this can cause:
- Incorrect balance/state readings being attributed to the wrong account or asset, potentially unlocking funds, releasing escrow, or making a fill/cancel decision based on the wrong queried value.
- Unauthorized app actions triggered by state data misapplied to the wrong context.

This matches the "unauthorized app action" / "unsound state commitment consumption" impact class called for in the validation rules, reachable from a single relayed GET response with attacker-influenced (or merely multi-key) proof/keys ordering.

### Likelihood Explanation
This requires an application to dispatch a `GetRequest` with more than one key where the byte-lexicographic order differs from the intended logical order — a common scenario when querying multiple, unrelated storage slots or accounts in a single batched GET. I was not able to fully verify within this investigation whether any current in-repo application (`IntentGatewayV2`/`HyperGet.sol`) actually dispatches multi-key GET requests with order-sensitive consumption; `HyperGet.sol`'s example queries a single key, and `IntentGatewayV2`'s GET usage for order-status queries appeared to use a single key as well in the code I reviewed. The vulnerability is real at the protocol/handler level (the ordering guarantee documented is not actually provided by the implementation), but the concrete exploitability depends on whether any deployed app actually relies on `values[i]`/`keys[i]` positional correspondence for a multi-key query — I could not conclusively confirm such usage exists on the EVM app side within the available context, so likelihood should be treated as **conditional on downstream app behavior** rather than confirmed as directly and immediately exploitable in the current app set.

### Recommendation
Change `verify_state_proof` (and the response handler) to preserve the caller-supplied key order — e.g., return a `Vec<(Vec<u8>, Option<Vec<u8>>)>` or an `IndexMap`/ordered structure keyed by insertion order, or explicitly re-sort the resulting `StorageValue`s to match `request.keys`'s original ordering before constructing `GetResponse.values`. Update or add an explicit invariant test verifying that for multi-key GET requests, `response.values[i].key == request.keys[i]` for all `i`, and update documentation to either guarantee this or explicitly warn app authors to match on `key` rather than positional index (and fix any app that currently indexes positionally).

### Proof of Concept
Not directly demonstrable without live execution/testing infrastructure, but the code path is:
1. An app dispatches a GET request with `keys = [keyA, keyB]` where `keyA > keyB` in raw byte ordering, intending `values[0]` to answer `keyA`.
2. A relayer submits a valid `ResponseMessage` with a correct proof for both keys.
3. `verify_state_proof` returns a `BTreeMap` where `keyB` sorts before `keyA`; `.into_iter()` yields `[(keyB, valB), (keyA, valA)]`.
4. `GetResponse.values` is delivered to the app as `[StorageValue{keyB, valB}, StorageValue{keyA, valA}]`, i.e. reversed from the app's expected `[keyA-value, keyB-value]` ordering.
5. If the app indexes `values[0]` expecting it to be `keyA`'s value (per documented "same order as requested keys" behavior), it processes `valB` instead — a state-confusion analogous to GovernorCompatibilityBravo's `calldatas`/`signatures` misalignment.
