## Title
`SimplexPaymaster._getOraclePrice` allows an oracle staleness window (up to 7 days) far larger than the feed's deviation threshold, enabling mispriced ERC-20 gas payments - ([File: evm/src/utils/SimplexPaymaster.sol])

### Summary
`SimplexPaymaster._getOraclePrice` accepts a Chainlink price as valid as long as `block.timestamp - updatedAt <= maxOracleAge`, where `maxOracleAge` is a governance-configurable value bounded only by `MAX_ORACLE_AGE = 7 days`. This mirrors the GLPOracle finding: using the feed's heartbeat (or a value close to it) as the staleness cutoff is far too permissive, because Chainlink feeds actually update on a tight deviation threshold (e.g., 0.05%–0.5%) long before their heartbeat elapses. If the aggregator stalls or the configured `maxOracleAge` is set near the heartbeat, the paymaster will keep accepting a price that can have drifted materially from the real market price for the entire staleness window before reverting.

### Finding Description
`_getOraclePrice` is used to price both the native asset (ETH/BNB) and the ERC-20 token for every gas-sponsored `UserOperation`: [1](#0-0) 

The only staleness guard is `block.timestamp - updatedAt > maxOracleAge`, and `maxOracleAge` is a governance-settable parameter capped only by: [2](#0-1) [3](#0-2) 

`_setParams` enforces only `p.maxOracleAge != 0 && p.maxOracleAge <= MAX_ORACLE_AGE`, i.e. any value up to 7 days is permitted and there's no requirement that it be tied to the actual deviation threshold of the configured feed: [4](#0-3) 

This is the exact bug class from the reference report: the interval used to decide "is this price stale" is derived from (or bounded by) the feed's heartbeat, not from the feed's deviation threshold. A Chainlink feed with a 0.05%–0.5% deviation threshold updates every few seconds under normal volatility; accepting a price up to `maxOracleAge` (which can legitimately be configured close to the heartbeat, e.g. 24h) means that if the feed stalls (oracle malfunction, sequencer/L2 outage, congestion), the paymaster keeps computing `_tokenPrice`/`estimateTokenCost` off a price that can have drifted far from the true market price for the entire window, without reverting.

### Impact Explanation
`_tokenPrice` converts the native gas cost into ERC-20 token amount using the (possibly stale) native/USD and token/USD prices: [5](#0-4) 

Every `UserOperation` sponsored during a stale window is priced off the wrong exchange rate. If the native asset's real price has risen relative to the stale cached price, users are charged too little ERC-20 for the actual gas spent — this directly drains the paymaster's `EntryPoint` deposit/treasury funds over many operations, a concrete loss of protocol funds. Since bundlers naturally submit many ops during periods of high volatility (exactly when a feed is most likely to be temporarily stalled or lagging), the exposure window is not a rare edge case. This satisfies the "concrete theft ... of funds" bar because the paymaster is an unprivileged-reachable contract (any UserOperation submitter reaches `_tokenPrice`/`estimateTokenCost`/`_erc20Cost` through the standard ERC-4337 flow) and the staleness bound is a governance-configurable value whose maximum (7 days) is grossly disproportionate to any Chainlink deviation threshold.

### Likelihood Explanation
Likelihood is Medium: it requires either (a) a governance-configured `maxOracleAge` that is not conservative relative to the underlying feed's deviation threshold (plausible, since the contract's own comment acknowledges heartbeats "vary per chain ... up to 24h", suggesting operators are expected to size `maxOracleAge` to the heartbeat rather than the deviation threshold), or (b) an oracle stall/congestion event, which occurs periodically on every chain. No malicious actor is required; a benign relayer submitting normal UserOperations during a stale window is sufficient to trigger mispriced gas payments.

### Recommendation
Do not size `maxOracleAge` to the feed's heartbeat. Either hardcode a materially tighter staleness bound tied to each feed's actual deviation threshold (analogous to the reference report's recommendation of 3,600s for a 0.5%-deviation/1h-heartbeat feed rather than the full heartbeat), or add a secondary sanity check (e.g., bound the allowed price delta between consecutive `_getOraclePrice` calls, or clamp `maxOracleAge` well below `MAX_ORACLE_AGE` for volatile assets) so that governance cannot configure a staleness window that is safe only in the absence of deviation-based updates.

### Proof of Concept
1. Governance (or the initial deployer) configures `maxOracleAge` at or near the chain's actual Chainlink heartbeat for the native/USD feed (permitted by `_setParams`, up to 7 days per `MAX_ORACLE_AGE`).
2. The Chainlink aggregator stalls (sequencer outage, node failure, or simply the heartbeat interval elapsing without the deviation threshold being hit due to low but nonzero drift accumulation).
3. Real market price of the native asset moves materially away from the last reported `answer`, while `block.timestamp - updatedAt` remains `<= maxOracleAge`, so `_getOraclePrice` (`evm/src/utils/SimplexPaymaster.sol` lines 662-676) returns the stale value without reverting.
4. Any UserOperation routed through `_tokenPrice`/`estimateTokenCost`/`_erc20Cost` during this window is priced off the stale rate, causing the paymaster to under-charge (or over-charge) the ERC-20 amount relative to the actual native gas cost it pays the `EntryPoint`, draining paymaster funds over repeated operations.

```text
    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
```
