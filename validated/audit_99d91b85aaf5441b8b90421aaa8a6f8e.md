## Title
Unsynchronized `override_threshold` allows silent bypass of the multisig timelock protection - (File: aptos-move/framework/aptos-framework/sources/multisig_account.move)

## Summary
The `multisig_account` module implements an optional `MultisigAccountTimeLock` (V1) that lets owners require a waiting period before a transaction executes, unless an elevated `override_threshold` of approvals is reached [1](#0-0) . This timelock is meant to protect the multisig-controlled resource account (and any APT/assets it custodies) against fast, minimal-quorum execution — e.g. giving other owners time to react to a malicious or compromised subset of `num_signatures_required` owners, analogous to the price-oracle report's concern about a single trusted party unilaterally forcing a damaging state change. `can_execute_with_timelock` treats a transaction as immediately executable if `num_approvals >= override_threshold`, entirely skipping the elapsed-time check [2](#0-1) . Because `override_threshold` is stored independently of `num_signatures_required` and I could not confirm (given tool-call budget) that every code path which mutates `num_signatures_required` (`update_signatures_required`, `add_owners_and_update_signatures_required`, `swap_owners_and_update_signatures_required`, owner removal shrinking the owner set, etc.) re-validates or updates the existing `MultisigAccountTimeLock.override_threshold`, there is a strong risk that `num_signatures_required` can be raised to meet or exceed the previously-configured `override_threshold` without the timelock resource being adjusted or removed.

## Finding Description
The timelock invariant documented in the constant comment is: "the number of approvals required to bypass the timelock and execute immediately... Must be greater than the number of signatures required normally and less than or equal to the number of owners" [3](#0-2) [4](#0-3) . This is enforced (per `EINVALID_TIMELOCK_OVERRIDE_THRESHOLD`) only at the moment the timelock is created/updated. If `num_signatures_required` is later changed by an ordinary owner-approved multisig transaction (`update_signatures_required` or similar) to a value `>= override_threshold`, the invariant silently breaks: `can_execute_with_timelock` becomes trivially true as soon as ordinary quorum (`num_signatures_required`) is met, because `num_approvals >= num_signatures_required >= override_threshold` [5](#0-4) . The timelock resource (`MultisigAccountTimeLock`) still exists on-chain (giving observers/UIs the false impression that a delay protection is active), but the elapsed-time branch is never reached because the override branch short-circuits it first.

I attempted to inspect `update_signatures_required`/`update_owner_schema` directly to confirm whether they cross-check the stored `override_threshold`, but ran out of tool budget before reading that function body — this is the key unverified fact. If that function does not re-validate/adjust `override_threshold` whenever `num_signatures_required` changes, the break is confirmed and is unprivileged from the perspective of the timelock's own guarantee (it only requires ordinary owner quorum, not the elevated override quorum, to defeat the protection).

## Impact Explanation
If unsynchronized, any owner-quorum transaction that legitimately raises `num_signatures_required` (a routine governance action, not requiring override-level approvals) would retroactively neuter the timelock on all subsequent transactions, including ones executed by exactly `num_signatures_required` owners — the same "malicious/compromised subset" scenario the timelock exists to slow down. For a multisig account custodying APT, fungible assets, or resource/code-object control (module upgrade authority, freeze/mint refs, etc. per the custody-pivot criteria), this converts a "safety delay + escalation" custody control into a no-op, enabling immediate, unslowed transfer/upgrade/freeze actions by the minimum-quorum owner set. This is asset/control-custody relevant and would be High severity if confirmed, since it strips a documented protection against exactly the compromised-privileged-actor threat model without any explicit privileged action to disable the timelock.

## Likelihood Explanation
Likelihood depends entirely on whether `update_signatures_required` (and paths that shrink the owner list, thereby capping `override_threshold` implicitly against `owners.length`) revalidate the timelock's `override_threshold`. This is a plausible oversight because the timelock feature (`MultisigAccountTimeLock`) appears to be a newer addition layered on top of long-standing owner/threshold-management functions, and cross-module invariant maintenance across independently-evolved features is a common source of just this class of bug. I could not verify the actual behavior within the available tool budget.

## Recommendation
Confirm whether `update_signatures_required`, `add_owners_and_update_signatures_required`, `swap_owners_and_update_signatures_required`, `remove_owners`, and `swap_owners` re-check `exists<MultisigAccountTimeLock>(multisig_account)` and either abort, auto-adjust, or force-remove the timelock configuration whenever the new `num_signatures_required` (or shrunk owner count) would violate `override_threshold > num_signatures_required` and `override_threshold <= owners.length()`. If no such check exists, add one, mirroring the validation already done in `upsert_timelock_internal`.

## Proof of Concept
Conceptual (unverified without reading `update_signatures_required`'s body):
1. Owner creates a multisig account with `num_signatures_required = 2`, 5 owners, and configures `MultisigAccountTimeLock { timelock_period: 14 days, override_threshold: Some(4) }` — i.e., 2 approvals require waiting 14 days, but 4 approvals execute instantly.
2. The same 2-of-5 quorum submits and executes (after the 14-day wait, as intended) a routine transaction calling `update_signatures_required(5)` — now `num_signatures_required = 5`, equal to the previously-set `override_threshold`.
3. If `update_signatures_required` does not touch/validate `MultisigAccountTimeLock`, the timelock resource remains with `override_threshold = 4 < num_signatures_required = 5`.
4. All future transactions now satisfy `num_approvals >= override_threshold` the instant they satisfy ordinary quorum (5 approvals ≥ 4), so `can_execute_with_timelock` returns `true` immediately per [6](#0-5) , and the intended 14-day delay never applies again — despite the timelock resource still existing and appearing active to any auditor/UI checking for its presence.

This PoC cannot be marked as fully proven; it should be validated against the actual body of `update_signatures_required`/`update_owner_schema` in `aptos-move/framework/aptos-framework/sources/multisig_account.move`, which I was unable to read before the tool budget was exhausted.

    /// `drop` is safe here because this resource holds only primitives (no capabilities, no
    /// event handles). It's used so that `remove_timelock` can `move_from` without destructuring.
    /// Note that because on-chain transactions cannot realistically be executed in less than a
    /// second, the resolution of `creation_time_secs` is at-second granularity — setting/removing
    /// a timelock within the same on-chain second as a pending transaction's creation is not a
    /// concern in practice.

            /// Must be greater than the number of signatures required normally and less than or equal to the number of owners.

        }

    /// Return true if the transaction with given transaction id can be executed immediately, or it has to wait
    /// for the timelock to expire.
    inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }
