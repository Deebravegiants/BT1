### Title
Attacker-controlled route pool executes arbitrary contract calls under the caller's signed authorization tree, draining the caller's wallet - (File: contracts/swap-aggregator/src/venues/mod.rs)

### Summary
The swap-aggregator executes whichever `pool` address the caller-supplied `StrategyPayload` names for each hop, with no allowlist of pools, venues, or tokens. Any contract invoked inside a route hop runs on the call stack beneath the caller's `require_auth` entry (for lending strategies, beneath the controller's `swap_collateral`/`multiply`/`swap_debt`/`repay_debt_with_collateral` root). A malicious "pool" can therefore attach arbitrary token transfers — or any other contract call requiring the victim's authorization — as children of the caller's auth entry. When the caller signs the simulation-produced tree, the host executes those transfers, emptying any wallet token the victim holds. This is the direct analog of CVE-2019-12735: untrusted data embedded in content (the route XDR / the file's modeline) smuggles executable commands (`:source!` / a hostile pool call) that run with the privileges of the entity processing the content.

### Finding Description
- `dispatch_hop` (`contracts/swap-aggregator/src/venues/mod.rs`) resolves `hop.pool` purely from payload registry indices and calls the venue adapter against it; the contract keeps no allowlist of pools or tokens, only a fee-placement whitelist.
- The venue adapters self-authorize the router's own token pulls via `env.authorize_as_current_contract` (`venues/auth.rs`), but nothing prevents the called pool contract from issuing its own `token.transfer(victim, attacker, amount)` — which the Soroban host records as a sub-invocation under the victim's auth entry.
- The controller grants the router "one exact input-transfer invocation" (INV-STRAT-01, `docs/reference/invariants.md`), but that bound covers only the controller's grant, not the victim's auth root. `docs/explanation/threat-model.md` (lines 154–165) confirms: "a route can put third-party code on the call stack below the caller's authorization... The loss is then the caller's wallet, not the routed amount."
- The test `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs` demonstrates end-to-end that a route through `RogueHopPool` transfers Alice's entire unrelated wallet-token balance to the attacker once the recorded auth tree is signed (`assert_eq!(s.wallet(&s.alice), 0)` at line 224, and the enforcing-mode variant at lines 258–268).

### Impact Explanation
Theft of user funds beyond the routed amount. Unlike normal slippage risk, the attacker is not limited to the `total_in` the victim intended to swap: the rogue pool can transfer any token the victim owns, for any amount, since the victim's signature covers the whole invocation tree. Every strategy entrypoint that accepts `swap_xdr` (`multiply`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and direct `execute_strategy`) is a vector.

### Likelihood Explanation
A single unprivileged attacker deploys a malicious pool contract and serves or injects a poisoned `routeXdr` (e.g., via a compromised/malicious quote source or phishing front-end). Simulation "helpfully" returns the theft as a required child authorization; any client that signs the simulated tree without decoding it — which the threat model itself notes honest routes never produce — authorizes the drain. Requires victim signature on a tree containing the theft child, hence UI-dependent and rated no higher than High.

### Recommendation
Enforce an allowlist of pool/venue addresses in `dispatch_hop` (governance-managed, like the Blend pool approval in INV-STRAT-03), or bound the authorization scope by having the router perform hops under its own auth only and rejecting any hop whose callee emits a `require_auth` on an address other than the router. At minimum, enforce at the controller/SDK layer that signed auth trees contain exactly the expected input-transfer child and no others.

### Proof of Concept
See `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`: `RogueHopPool::swap` calls `token::Client::transfer(victim → attacker, amount)` inside the hop; `simulation_records_the_rogue_pool_wallet_transfer_under_the_callers_swap_collateral_entry` shows the theft recorded under Alice's `swap_collateral` auth entry and executed, leaving `wallet(alice) == 0` and `wallet(attacker) == WALLET_BALANCE`.
