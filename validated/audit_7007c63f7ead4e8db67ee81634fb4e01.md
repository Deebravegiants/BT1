## Title
Webhook `shop`, `topic`, `webhook_id`, and `api_version` values are trusted from unauthenticated headers while the HMAC only covers the raw body, enabling cross-tenant/topic impersonation - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's authenticity by validating an HMAC that is computed *only* over the raw request body, but then dispatches to a handler and constructs `WebhookMetadata` using the `shop`, `topic`, `webhook_id`, and `api_version` values taken from unauthenticated HTTP headers. Any attacker who can obtain one genuinely-signed `(body, hmac)` pair for their own store (which any Shopify merchant/partner can do, including via mandatory compliance webhooks such as `customers/redact`) can replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shop-domain` and/or `topic` headers, since those fields are never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from request headers, none of which are covered by `to_signable_string`: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string`, i.e. the body: [3](#0-2) 

`Registry.process` uses this HMAC check as the sole authenticity gate, then dispatches based on the unauthenticated `topic` header and forwards the unauthenticated `shop` header directly into `WebhookMetadata` handed to the app's business logic: [4](#0-3) 

This breaks the intended identity binding: `hmac_valid(body) == true` is treated as equivalent to `shop_header == authentic_source_shop AND topic_header == authentic_topic`, when in fact the signature makes no claim about either header. Because any Shopify merchant (including via free/dev stores) can generate a genuinely-signed `(body, hmac)` pair for the app (e.g. by placing an order to trigger `orders/create`, or by using a mandatory compliance topic like `customers/redact`/`shop/redact` which Shopify sends to *every* installed/registered app for that shop), the attacker fully controls a valid signed payload. They can then POST that same body and `hmac-sha256` header directly to the app's public webhook endpoint while freely setting the `shop-domain` header to a victim shop and/or the `topic` header to a different registered topic, since `Request#initialize` and `Registry.process` never re-validate these fields against the signed body.

### Impact Explanation
This is a cross-tenant identity/topic confusion vulnerability reachable by any unprivileged internet user who can create or already control a Shopify store: the shop identity bound into the app's webhook handling logic (`WebhookMetadata#shop`) can be forged to any victim shop domain, and the effective `topic` dispatched to handlers can likewise be forged to any topic the app has registered a handler for, all while passing the gem's own HMAC authenticity check. Depending on what the host application's webhook handlers do with `data.shop` and `data.topic` (e.g., update per-shop records, trigger data deletion/redaction flows, or process orders), this can result in cross-tenant data corruption/exposure or triggering of privileged/topic-specific logic under a spoofed shop identity — qualifying as Critical cross-tenant access.

### Likelihood Explanation
Likelihood is meaningfully high for a determined attacker: creating a free Shopify partner/dev store and installing or subscribing to any public app is trivial, and several compliance topics (`customers/redact`, `shop/redact`, `customers/data_request`) are sent by Shopify to apps regardless of typical install gating, giving attackers a straightforward path to a validly-signed body. The only additional step is a direct HTTP POST to the app's public webhook route with modified headers, which requires no secret knowledge at all.

### Recommendation
Bind the identity-relevant fields into the verified signature material instead of trusting bare headers: either canonicalize `shop`, `topic`, `webhook_id`, and `api_version` into `to_signable_string` alongside the body (matching how `Auth::Oauth::AuthQuery#to_signable_string` binds all relevant fields), or have `Registry.process` cross-check the `shop` header against the session/shop that legitimately owns the currently active registration before dispatching, and reject any topic header mismatch relative to what the signed body structurally represents.

### Proof of Concept
1. Attacker creates/owns Shopify store `attacker.myshopify.com` and installs the target app (or simply exists as a shop eligible for mandatory compliance webhooks).
2. Attacker triggers a webhook the app has registered for (e.g. places an order for `orders/create`, or waits for a mandatory `customers/redact` webhook). Shopify sends a POST to the app's webhook endpoint with a body `B` and header `x-shopify-hmac-sha256: HMAC(B, client_secret)` — genuinely valid.
3. Attacker captures `B` and the HMAC value (they control the receiving endpoint or can proxy/log it).
4. Attacker sends a new POST directly to the app's public webhook endpoint with the same body `B` and the same `x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or `x-shopify-topic: <other-registered-topic>`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against the HMAC — it never inspects the headers. The handler for the attacker-chosen topic then runs with `WebhookMetadata#shop == "victim-shop.myshopify.com"`. [4](#0-3) [5](#0-4)
