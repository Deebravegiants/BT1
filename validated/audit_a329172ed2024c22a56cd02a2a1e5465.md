### Title
Unverified `receiver` origin in `flash_loan` lets any caller force a fee-bearing flash loan on a third-party contract holding a pool allowance - (File: contracts/pool/src/ops/flash.rs)

### Summary
`controller::flash_loan` is permissionless: it calls `caller.require_auth()` but performs no authorization check on `receiver`. The pool then transfers principal to `receiver`, invokes `execute_flash_loan` on it, and pulls `amount + fee` back via `transfer_from(pool, receiver, pool, total_repayment)` gated only by the receiver's outstanding token allowance. Any unprivileged address can nominate any Wasm contract as `receiver`; if that contract holds a live allowance to the pool (the documented repayment mechanism), it is charged the flash-loan fee without ever authorizing the call. This is the XOXNO Lending analogue of CVE-2016-9902: the privileged context (the pool's allowance-backed pull) acts on an incoming "event" (the caller-chosen `receiver` argument) whose origin/consent is never verified.

### Finding Description
The call chain is:

1. `Controller::flash_loan` → `strategies::flash_loan::process_flash_loan` authenticates only `caller` via `require_authorized_caller` and passes `caller` as `initiator` plus the caller-supplied `receiver` to the pool (`contracts/controller/src/strategies/flash_loan.rs:22-32`).
2. `pool::flash::apply` requires `receiver` to be a Wasm contract (`require_wasm_receiver`), transfers `amount` to it, invokes `execute_flash_loan(initiator, asset, amount, fee, pool, data)`, then calls `collect_repayment` (`contracts/pool/src/ops/flash.rs:60-67`).
3. `collect_repayment` checks `asset.allowance(receiver, pool) >= amount + fee` and pulls via `transfer_from` — no `receiver.require_auth()` exists anywhere in the flow (`contracts/pool/src/ops/flash.rs:173-179`).

The victim receives `amount` and loses `amount + fee`, a net loss of `fee = flashloan_fee` bps of `amount` booked as protocol revenue (`book_fee`, `flash.rs:124-128`). Nothing in the flow proves `receiver` consented to this specific loan; the standing allowance — which receivers must grant to repay — is treated as blanket consent. The `initiator` argument delivered to the victim's callback is also fully caller-controlled, compounding the origin spoof.

### Impact Explanation
Theft of user funds: each forced call burns `fee` tokens from the victim contract (a contract that borrowed earlier and left residual allowance, or one with a longer-lived approval). The attack is repeatable up to the victim's remaining allowance, and works on any `is_flashloanable` market with `amount` up to the pool's cash reserves, so `fee` scales with pool liquidity. The victim cannot block it: it never signs the transaction, and even a well-behaved callback that re-approves only `amount + fee` still loses the fee.

### Likelihood Explanation
Exploitation requires a victim Wasm contract with an unexpired `receiver → pool` token allowance on a flashloanable asset. The SDK's own `approve_flash_repayment` uses next-ledger expiration, which narrows the window for receivers built on the recommended helper, but any receiver approving with a longer TTL — or an over-approval like the harness's `OverRepay` mode (`amount + fee + 1` in `mock/flash-loan-receiver/src/lib.rs:121-123`), which the pool deliberately permits per INV-FLASH-01 ("extra allowance is allowed") — is exposed for the allowance's lifetime. The attack is one permissionless call (`controller.flash_loan(caller, asset, amount, victim, data)`) with no capital requirement.

### Recommendation
Bind the receiver's consent into the call: either require `receiver.require_auth()` inside `pool::flash::apply`/`collect_repayment` before the payout, or have the controller pass an explicit receiver-signed authorization. At minimum, document that the pool's allowance check is not consent and that any receiver must use exactly-expiring, exactly-sized approvals — though the robust fix is authenticating `receiver` directly, since allowance lifetime is outside the protocol's control.

### Proof of Concept
```
1. Victim contract V previously took a flash loan and approved the pool for
   amount + fee with a multi-ledger expiration (or has any residual allowance A > 0
   on a flashloanable asset X).
2. Attacker calls controller.flash_loan(
       caller   = attacker,            // attacker signs; only this auth is checked
       asset    = X,
       amount   = min(A/(1+fee_bps), pool_cash(X)),
       receiver = V,                   // no auth required on V
       data     = arbitrary
   )
3. Pool transfers `amount` of X to V, invokes V.execute_flash_loan (which may
   even trap harmlessly after approving nothing new — attacker chooses amount
   ≤ existing allowance), then pulls `amount + fee` from V via transfer_from.
4. Net: V loses `fee`; pool books `fee` as revenue. Attacker repeats until
   allowance A is drained.
```
