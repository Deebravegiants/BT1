### Title
Overpaid native-token dust from Uniswap fee swaps is trapped in `EvmHost` instead of being refunded to the payer - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native ETH via `msg.value` and forward the *entire* `msg.value` into `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)` to buy an exact amount of `feeToken`. Any dust ETH left over from that swap is refunded by the Uniswap router to its immediate caller — which is `EvmHost` itself, not the original transaction sender — and none of these three functions ever forwards that refunded dust back to the user.

### Finding Description
In `evm/src/core/EvmHost.sol`: [1](#0-0)

All three call `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. The canonical `UniswapV2Router02.swapETHForExactTokens` implementation computes `amounts[0]` needed to buy exactly `fee` tokens and, if `msg.value > amounts[0]`, refunds the dust via `TransferHelper.safeTransferETH(msg.sender, msg.value - amounts[0])`. Since `EvmHost` is the caller of the router (not the end user), that dust refund lands back in `EvmHost`'s own balance — it is never forwarded to `_msgSender()`/`payer` who supplied the overpaid `msg.value`. None of the three functions checks `address(this).balance` before/after the swap or performs any `call{value: ...}` back to the user with the leftover amount.

This is the same root-cause bug pattern as the reported Avail issue: a function accepts more native currency than it strictly needs and never refunds the excess, permanently trapping user funds in the contract. The codebase's own `IntentGatewayV2` (`placeOrder`/`fillOrder`) explicitly implements this refund pattern (`_sendValue(msg.sender, msgValue)` after the swap) and has dedicated tests for it (`testPlaceOrder_RefundsExcessNativeToken`, `testPlaceOrder_FeeSwap_RefundsExcessNativeToken`) — confirming the project is aware overpayment refunds are required, yet `EvmHost.dispatch`/`fundRequest` lack this logic entirely. [4](#0-3) [5](#0-4) 

No withdrawal/rescue function exists in `EvmHost.sol` restricted to an admin to recover accidentally trapped ETH that would let users be manually reimbursed — the dust simply accumulates in the contract's balance with no path back to the payer.

### Impact Explanation
Any application or end user dispatching a POST/GET request or funding a relayer fee through `EvmHost` with native ETH (as documented and expected usage in `docs/content/developers/evm/messaging/post-requests.mdx` and `IDispatcher.sol`) will lose any ETH sent beyond the exact amount needed for the Uniswap swap. Because slippage and price movement between fee-estimation (`quote()`) and execution are unavoidable, users must send some buffer above the estimated fee to avoid the transaction reverting with `EXCESSIVE_INPUT_AMOUNT`/`INSUFFICIENT_OUTPUT_AMOUNT`-style errors — but that buffer, and any organic price improvement, is permanently lost rather than returned. This is a widespread, unprivileged, single-transaction path (every `dispatch{value: ...}` call and every `fundRequest{value: ...}` call), resulting in a direct and repeatable loss of user funds with no recovery mechanism. This qualifies as a Medium severity issue analogous to the reported Avail finding.

### Likelihood Explanation
High likelihood: this triggers on essentially every native-token-funded dispatch call, since callers must overestimate the required ETH to avoid reverts (per the documented guidance: "Estimating Fees ... estimate fees on the client side before users submit transactions" and the 2x buffer used by `HyperbridgeLzEndpoint.quote()` — see below), and Uniswap swap output amounts also fluctuate with pool state between quoting and execution. [6](#0-5) 

Notably, `HyperbridgeLzEndpoint.quote()` itself explicitly applies a 2x buffer on the native fee "to absorb the legacy deployed host's per-byte protocol fee," and its comment claims "Excess native is refunded by the uniswap router" — but as shown above, that refund actually goes to `EvmHost`, not to the end caller of `HyperbridgeLzEndpoint.send()`, meaning this documented assumption is incorrect and the excess is systematically lost for every LayerZero message relayed through the adapter with a native-fee buffer.

### Recommendation
In `EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()`, record `address(this).balance` before performing the `swapETHForExactTokens` call, and after the call, compute the leftover native balance and forward it back to `_msgSender()` (or the designated `payer`) via a safe ETH transfer, mirroring the pattern already used in `IntentGatewayV2._sendValue` and `WrappedHyperFungibleToken.send`. Alternatively, use `swapExactETHForTokens`-style logic paired with an exact-amount check, or explicitly limit and refund `msg.value - amounts[0]` after the swap.

### Proof of Concept
1. Alice calls `EvmHost.dispatch(DispatchPost{ fee: 100 feeTokenUnits, ... })` with `msg.value = 1 ether`, intending to overpay to guard against slippage.
2. Inside `dispatch`, `swapETHForExactTokens{value: 1 ether}(100, [WETH, feeToken], address(this), block.timestamp)` is called on the Uniswap router.
3. The router computes it only needs, say, `0.4 ether` worth of WETH to buy exactly 100 feeToken units; it refunds `0.6 ether` dust — but to `msg.sender` of the router call, which is `EvmHost`, not Alice.
4. `EvmHost.dispatch` returns normally, having spent only `0.4 ether` worth of value on Alice's behalf but keeping the refunded `0.6 ether` in its own balance permanently, with no code path to send it back to Alice.
5. Repeating this for every native-funded `dispatch`/`fundRequest` call across all users continuously accumulates trapped ETH in `EvmHost` with no recovery mechanism for the original payers.
