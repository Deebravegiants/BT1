### Title
Tron port of `IntentGatewayV2` omits the `nonReentrant` guard added to the canonical EVM contract, reopening the escrow/fee-theft reentrancy already fixed and regression-tested elsewhere - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The reported bug class — a low-level `.call{value: ...}` used to refund/pay out native ETH after state-mutating effects, exploitable via reentrancy — is exactly the vulnerability class that Hyperbridge's own EVM `IntentGatewayV2` contract already suffered from and had to fix. The fix (CEI ordering plus a `nonReentrant` modifier) is present and regression-tested in `evm/src/apps/IntentGatewayV2.sol`, but the parallel Tron deployment target at `evm/tron/contracts/apps/IntentGatewayV2.sol` does not carry the same protection.

### Finding Description
In the canonical EVM contract, `placeOrder`, `fillOrder`, and `cancelOrder` are all guarded with `nonReentrant`: [1](#0-0) [2](#0-1) [3](#0-2) 

This guard was specifically necessary because the fill logic pays native ETH to a caller-controlled `beneficiary` address via a raw call *before* all escrow bookkeeping settles, and a malicious beneficiary contract can re-enter on `receive()`. This exact attack — reentering during the ETH payout to steal escrowed transaction fees or drain multi-output escrow — is documented and defended against by a dedicated test suite: [4](#0-3) [5](#0-4) 

The fix relies on setting `_filled[commitment] = msg.sender` before the output-payment loop (CEI) in `IntrinsicIntents._fillSameChain`: [6](#0-5) [7](#0-6) 

The Tron contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, implements the same `placeOrder`/`fillOrder`/`withdraw` design (same ETH `.call{value: amount}` payout pattern, e.g. in `withdraw()`): [8](#0-7) 

However, unlike the mainline EVM implementation, `evm/tron/contracts/apps/IntentGatewayV2.sol` contains no `nonReentrant`/`ReentrancyGuard` usage anywhere in the file — confirmed by a full-file search that returned zero matches — and its `placeOrder` function is declared without the modifier: [9](#0-8) 

`placeOrder` on Tron performs multiple external calls (predispatch call dispatcher, Uniswap V2 fee swap, ERC20 transfers) prior to any native-ETH refund, all unguarded by a reentrancy lock, mirroring the same hazard the mainline contract had to patch.

### Impact Explanation
If the Tron `fillOrder` equivalent (not fully inspected in this pass, see Likelihood/uncertainty note below) follows the same order-of-operations as the pre-fix mainline contract — i.e., pays the beneficiary/solver native ETH via low-level call before finalizing `_filled`/escrow state — an attacker using a malicious beneficiary/solver contract could re-enter to steal escrowed transaction fees or multi-output escrow, exactly as demonstrated by `testReentrancy_FeeTheft` and `testReentrancy_EscrowTheft_MultiOutput` against the pre-fix mainline code. This is a direct theft-of-funds vector against user/solver escrowed tokens.

### Likelihood Explanation
High confidence that the reentrancy guard is absent (`nonReentrant`/`ReentrancyGuard` grep returned zero matches in `evm/tron/contracts/apps/**`, vs. 6 matches in the mainline `evm/src/apps/IntentGatewayV2.sol`). I was not able to fully re-inspect the Tron `fillOrder`/`_fillSameChain`-equivalent function body within the available tool budget to confirm whether it independently reproduces the CEI ordering (`_filled[commitment] = msg.sender` before the ETH payout loop) that the mainline contract added as a second layer of defense. The `withdraw()` function on Tron does set `_filled[body.commitment] = beneficiary` before its payout loop (CEI present there), but this doesn't establish whether the same ordering exists in the primary fill path. This is the key open uncertainty; if Tron's fill path also lacks the CEI fix, the vulnerability is directly exploitable, not merely theoretical.

### Recommendation
Add `ReentrancyGuard`/`nonReentrant` to `placeOrder`, `fillOrder`, and `cancelOrder` in `evm/tron/contracts/apps/IntentGatewayV2.sol`, mirroring `evm/src/apps/IntentGatewayV2.sol`. Additionally, audit `evm/tron/contracts/apps/IntentGatewayV2.sol`'s fill logic to confirm `_filled[commitment]` (or equivalent order-completion state) is written *before* any external native-ETH `.call` or ERC20 transfer to a caller-controlled beneficiary, matching the CEI pattern in `IntrinsicIntents._fillSameChain`. Port the `IntrinsicIntentsReentrancyTest.sol` regression suite to the Tron contract build to lock in the fix.

### Proof of Concept
Not independently reproduced against Tron's `fillOrder` in this pass due to tool-call exhaustion before the function body could be read. The proof-of-concept pattern to adapt is the existing `ReentrantBeneficiary` harness used against the mainline contract: [10](#0-9) 
A background engineer should read `evm/tron/contracts/apps/IntentGatewayV2.sol`'s fill/withdraw functions in full, confirm the absence of both the `nonReentrant` modifier and the CEI-ordered `_filled` write before payout, then adapt `testReentrancy_FeeTheft`/`testReentrancy_EscrowTheft_MultiOutput` to the Tron contract to demonstrate fund theft concretely.

    Order private storedOrder;
    FillOptions private storedOptions;
    bool private armed;
    bool private reentered;

    constructor(address payable _gateway) {
        gateway = IntentGatewayV2(_gateway);
    }

    /// @notice Pre-approve the gateway to pull an ERC-20 from this contract.
    function approveGateway(address token, uint256 amount) external {
        IERC20(token).approve(address(gateway), amount);
    }

    /// @notice Load the reentrant payload before the outer fill is triggered.
    function arm(Order calldata order, FillOptions calldata options) external {
        storedOrder = order;
        storedOptions = options;
        armed = true;
    }

    /// @notice Triggered by the ETH transfer inside the fill loop.
    ///         Attempts to re-enter fillOrder; with the CEI fix the call reverts
    ///         with Filled(), which propagates and fails the outer ETH transfer.
    receive() external payable {
        if (armed && !reentered) {
            reentered = true;
            gateway.fillOrder(storedOrder, storedOptions);
        }
    }
