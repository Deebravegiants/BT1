## Title
Webhook Shop Identity Spoofing via Unsigned `shop-domain` Header — ([File: lib/shopify_api/webhooks/request.rb])

### Summary
The webhook signature verification in this gem only binds the HMAC to the raw request body, while the `shop` identity attached to a processed webhook is read from an unsigned HTTP header. This breaks the identity binding `HMAC-covered bytes == shop attributed to the webhook`, letting an attacker who can produce one valid `(body, hmac)` pair for the app's shared secret relabel that payload as belonging to any other merchant.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

but `#shop` is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of the signed material at all: [2](#0-1) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) against the app's shared `Context.api_secret_key`: [3](#0-2) 

`ShopifyAPI::Webhooks::Registry.process` validates only this body HMAC, then trusts `request.shop` — the unsigned header — to build the `WebhookMetadata` that is handed to the host application's handler as the identity of the originating shop: [4](#0-3) 

Because `Context.api_secret_key` is the app's single client secret shared across every merchant installation (not a per-shop secret), any tenant that legitimately receives a real webhook (body + valid HMAC) for their own shop can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` will accept it because the HMAC only ever covered the body, and `Registry.process` will dispatch it to the app's handler labeled as coming from the victim shop. This is the same bug class as the reported issue: a field acted on (`shop`, used to attribute/act on tenant data) is not covered by the integrity check (the HMAC), so the "authenticated" identity and the identity actually used diverge — `shop_from_hmac_scope == body only` vs `shop_used_by_handler == unsigned header`.

### Impact Explanation
Any handler that uses `WebhookMetadata#shop` to key writes, cache invalidation, billing state, uninstall/GDPR processing, or other per-tenant side effects can be made to apply attacker-controlled (but HMAC-"validated") data to an arbitrary victim shop's tenant record, since the shop label is unauthenticated. This is a cross-tenant integrity/confusion issue reachable by any party that can obtain one valid webhook body/HMAC pair for the app (e.g., any installed merchant, or anyone who can observe/capture one legitimate webhook delivery) — no access token, `api_secret_key`, or privileged account is required.

### Likelihood Explanation
Webhook payloads for common topics (e.g., `app/uninstalled`, `shop/update`, `orders/create` for shared/mandatory topics) are routinely delivered to public app endpoints, and an app installed on any shop naturally receives real `(body, hmac)` pairs for that shop. Forging the `shop-domain` header on an HTTP POST to a public webhook endpoint requires no special access, making exploitation straightforward for anyone who controls (or can observe) one shop's webhook traffic to a shared app.

### Recommendation
Bind the shop identity into the signed material, or otherwise cryptographically tie the `shop-domain` header to the request before trusting it: e.g., include the shop domain in the HMAC computation, cross-check the header value against a shop-specific stored secret, or reconcile it against the value returned by Shopify's platform-level webhook verification (which ties delivery to a specific registered subscription) rather than trusting the raw header value used purely for attribution in `WebhookMetadata`.

### Proof of Concept
1. App is installed on shop `victim.myshopify.com` and shop `attacker.myshopify.com`, both webhooks signed with the same app `api_secret_key`.
2. Attacker's own shop receives a legitimate webhook: `raw_body = B`, `hmac header = H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker POSTs to the app's webhook endpoint with `raw_body: B`, `x-shopify-hmac-sha256: H` (both untouched/valid), but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(api_secret_key, B) == H` — succeeds since `B` and `H` are unmodified (`lib/shopify_api/utils/hmac_validator.rb:12-22`).
5. `Registry.process` builds `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` using the attacker-supplied `shop-domain` header (`lib/shopify_api/webhooks/registry.rb:198-199`), invoking the host app's handler as if the webhook came from `victim.myshopify.com`.
