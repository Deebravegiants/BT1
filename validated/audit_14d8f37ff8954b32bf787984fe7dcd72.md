### Title
Predictable offline session ID enables session fixation / cross-tenant session hijack in non-embedded OAuth flow - (File: lib/shopify_api/auth/session.rb, lib/shopify_api/auth/oauth.rb)

### Summary
For non-embedded apps, the OAuth callback stores the session's own id — computed as `"offline_#{shop}"`, a value derivable from the publicly known shop domain — as the plaintext value of the `shopify_app_session` cookie. Because this string carries no HMAC, random nonce, or other secret binding it to the specific browser/user that completed the OAuth grant, an attacker who knows (or guesses) a victim shop's domain can pre-set (fixate) that exact cookie value in their own browser, or in any browser sharing the app, and use it to retrieve the same stored `Auth::Session` (holding the merchant's access token) once the real merchant completes OAuth.

### Finding Description
`Auth::Oauth.validate_auth_callback` completes the OAuth handshake and, for non-embedded apps, builds the response cookie as `SessionCookie.new(value: session.id, expires: ...)` [5](#0-4) . The `session.id` here comes from `Session.from`, which for offline access tokens sets `id = "offline_#{shop}"` with no random component [1](#0-0) .

This id is the sole value that `SessionUtils.current_session_id`/`cookie_session_id` reads back out of the browser's cookie jar to resolve which stored session (and therefore which access token) a request is authorized to use: `cookies[Auth::Oauth::SessionCookie::SESSION_COOKIE_NAME]` is returned verbatim, unauthenticated and unverified [4](#0-3) .

The binding that should hold is: `cookie_value == session_id_bound_to_this_specific_authenticated_browser`. Instead the actual relation is `cookie_value == f(shop)`, i.e., a value computed purely from public information (the shop's domain) and reproducible by anyone, not tied to any secret nonce, HMAC, or the specific request/browser that performed OAuth. Any party who can write this cookie into a browser (session fixation via a sibling subdomain, an XSS on a co-hosted origin, a shared/public terminal, or simply predicting the value for a known target shop) can later present that browser's session to the app and be treated by `current_session_id` as the legitimate holder of the merchant's session, which is looked up by that plaintext id in whatever session storage backs the app (Redis/DB/etc., which is host-application supplied but keyed exactly by this id).

### Impact Explanation
This breaks the identity binding between "browser that completed the merchant's OAuth consent" and "party who can read the resulting session/access token," letting an unprivileged internet user who merely knows a target's `.myshopify.com` domain fixate or predict the session cookie value used to fetch that merchant's stored `Auth::Session`, including its `access_token`. This matches the "session fixation or forced OAuth completion" / cross-tenant access impact category, since the attacker effectively can pre-position themselves to receive the victim shop's session materials once the real OAuth flow finishes.

### Likelihood Explanation
Exploitability depends on the attacker being able to place or predict this specific cookie value in the target's browser (e.g., via a fixation vector on the app's domain, or a scenario where cookies aren't scoped tightly per-visit) and on the host application storing/keying offline sessions purely by this id without additional binding — both are plausible given the gem provides no randomness or secondary verification for the offline session id itself, and explicitly hands this predictable value to the client as the cookie contents.

### Recommendation
Do not derive the session cookie value from a deterministic, attacker-predictable function of the shop domain. Use a cryptographically random, unguessable session cookie value (e.g., `SecureRandom.uuid`/`SecureRandom.hex`) that is distinct from the internal storage key `"offline_#{shop}"`, and validate that value server-side against a mapping stored at OAuth completion time (analogous to how `state`/`nonce` is already checked in `begin_auth`/`validate_auth_callback`). Alternatively, sign the cookie value (HMAC with `api_secret_key`) so that its authenticity, not just its presence, is verified in `SessionUtils.cookie_session_id`.

### Proof of Concept
1. Attacker learns/guesses the target merchant's shop domain, e.g. `victim-shop.myshopify.com` (shop domains are not secret; they're used in installation URLs).
2. Attacker computes the deterministic offline session id: `"offline_victim-shop.myshopify.com"` — reproducing exactly what `Session.from` computes at [6](#0-5) .
3. Attacker sets the `shopify_app_session` cookie to this value in their own browser (or fixates it into a victim's browser via any available cookie-setting vector on the app's origin).
4. When the real merchant completes the non-embedded OAuth flow, `validate_auth_callback` stores/serves back exactly this same predictable value as the session cookie [5](#0-4) .
5. Any request presenting a `shopify_app_session` cookie equal to `"offline_victim-shop.myshopify.com"` will resolve, via `SessionUtils.cookie_session_id`, to the merchant's stored session and access token [4](#0-3) , without any proof that the requester is the browser that actually completed OAuth.
