Based on my investigation, I found a concrete analog in the Tron variant of the Intent Gateway's escrow settlement logic.

### Title
Unchecked low-level token transfer in `IntentGatewayV2.withdraw()` finalizes escrow release without confirming funds actually moved - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The CVE describes a heap use-after-free where a resource is referenced/finalized after (or without properly confirming) its state was correctly transitioned. The Hyperbridge Tron `IntentGatewayV2.withdraw()` function has a structurally analogous bug: it "frees" (decrements) escrow accounting and finalizes settlement state based only on whether the external call to a token contract *did not revert*, never checking the token's returned success boolean, and only *after* the external interaction rather than validating sufficiency beforehand.

### Finding Description
`withdraw()` is the internal settlement routine reached from `cancelOrder` (same-chain, permissionless to the order's own user), and from `onAccept`/`onGetResponse` (cross-chain settlement, gated `onlyHost` but ultimately triggered by any relayer delivering a proof for an order any user placed): [1](#0-0) 

For each escrowed token it does:
1. Checks only `_orders[body.commitment][token] == 0` (existence, not sufficiency).
2. Calls `token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount))` and treats `success` (the low-level call not reverting) as proof of a completed transfer — the returned `bool` from `transfer()` is never decoded or checked.
3. Only *after* that unchecked interaction does it decrement `_orders[body.commitment][token] -= amount` and, for fees, `delete _orders[body.commitment][TRANSACTION_FEES]`, then emits `EscrowReleased`/`EscrowRefunded`.

Contrast with the mainline EVM implementation, which uses `SafeERC20.safeTransfer` (which reverts on a false return) and decrements state *before* the external call: [2](#0-1) 

Any ERC20/TRC20 token that returns `false` on failure instead of reverting (a well-documented, common non-compliant token behavior) will cause `withdraw()` to treat a failed transfer as successful: the escrow bookkeeping is irreversibly "freed" (decremented/deleted) and the order is marked filled/refunded/fee-paid, while the beneficiary receives nothing. The same unchecked-`.call` pattern for token transfers appears again in `SweepDust` handling inside `onAccept`: [3](#0-2) 

### Impact Explanation
This causes permanent freezing/loss of escrowed user or protocol funds: once `_orders[commitment][token]` is decremented and `_filled[commitment]`/event state finalized, there is no retry path — the order is considered settled, so the actual tokens remain stuck in the contract while accounting says they were disbursed. This satisfies the "permanent freezing of funds" criterion for the token bridger / intents escrow path.

### Likelihood Explanation
The path is reachable by any user who places an order denominated in a token that doesn't strictly follow the boolean-return ERC20 convention (a class of tokens common enough that OpenZeppelin's `SafeERC20` exists specifically to guard against it), or via `onAccept`/`onGetResponse` settlement triggered by any relayer once such an order exists. No admin/governance privilege is required — only choosing/accepting such a token as an order input, which a normal solver or user interaction can do.

### Recommendation
Replace the raw `.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()` and the `SweepDust` branch of `onAccept()` with `SafeERC20.safeTransfer`, and decrement `_orders[...]` accounting before making the external transfer call (Checks-Effects-Interactions), matching the pattern already used in `evm/src/apps/intentsv2/IntentsBase.sol`.

### Proof of Concept
1. User places an order (`placeOrder`) using a non-standard TRC20/ERC20 token as `inputs[0].token`, one that returns `false` (rather than reverting) when a `transfer` fails (e.g., due to a paused state, blacklist, or crafted malicious token deployed by the order's own placer for a self-triggered cancel).
2. Before the order is filled, the user calls `cancelOrder` on the same chain; this routes to `withdraw(body, true)`: [4](#0-3) 
3. Inside `withdraw`, the token's `transfer` call executes without reverting but returns `false` (no tokens actually move).
4. `success` is `true` (call itself didn't revert), so `_orders[commitment][token] -= amount` proceeds, `_filled[commitment]` is already set, and `EscrowRefunded` is emitted — the order is permanently marked as settled while the tokens remain locked in the contract with no further recovery path.
