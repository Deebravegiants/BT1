### Title
Webhook `shop` (and other headers) are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value straight from an HTTP header, but the HMAC signature that `Utils::HmacValidator` verifies only covers the raw request body. Because the shop-domain header is never bound to the signed content, an attacker who legitimately owns a shop that has the app installed can capture one authentic (raw_body, hmac) pair from their own webhook delivery and replay it against the app's webhook endpoint while substituting a different `shopify-shop-domain` header value. The HMAC still validates (it only checks the body), yet `Registry.process` hands the forged shop identity to the app's handler as if it were authentic.

### Finding Description
The vulnerable equality that should hold is:

`shop value trusted by the handler == shop value cryptographically bound by the HMAC`

`Webhooks::Request#shop` simply reads an unauthenticated header: [1](#0-0) 

But `#to_signable_string`, which is what `HmacValidator` actually verifies, returns only the raw body — the shop/topic/webhook-id headers are excluded: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (an unauthenticated header) as the tenant identity passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the body) against `Context.api_secret_key`, which is the single shared app secret used to sign webhooks for *every* shop that installs the app — not a per-shop secret: [4](#0-3) 

Because the same `api_secret_key` signs webhooks for all merchants, and only the body bytes are bound to that signature, a malicious merchant who installs the app on their own store receives a legitimate `(raw_body, hmac)` pair. They can then replay that exact body/HMAC to the app's webhook receiver while swapping the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to name a victim shop. `Request` and `HmacValidator` accept it as fully valid, and `Registry.process` forwards `shop: <victim-shop>` to the handler, which typically uses that value to look up the victim's session/access token and apply the (attacker-controlled) webhook body to the victim's data.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for inbound webhooks — the same class of "identity used but not covered by the authentication check" bug as the reported `adjustMechRequesterBalances` issue, where a party identifier is acted upon without being tied to the authenticated caller. Here the `shop` field used to select the tenant context is not part of the authenticated data, enabling cross-tenant access/data injection, which maps to the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate merchant of the same app (a low bar for any public app) capable of triggering one webhook delivery to themselves and replaying the request with a modified header to the app's public webhook endpoint. No access token, `client_secret`, or privileged access is needed — only observation of one's own authentic webhook traffic, which is standard "unprivileged internet user" capability for anyone who installs the app.

### Recommendation
Bind the tenant/shop identity (and ideally topic/webhook-id) into the HMAC-signed material, or otherwise verify that the `shop` header correlates with an expected/registered shop for the delivered webhook before dispatching to handlers. At minimum, document and enforce in `Webhooks::Request#to_signable_string` that all identity-bearing headers relied upon by consumers (`shop`, `topic`, `webhook_id`) must not be trusted independently of the HMAC — e.g., verify shop membership against session storage before invoking the handler, rather than trusting the raw header value.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook: raw body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's shared `api_secret_key`), `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker resends the same `B` and `H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `B` against `H` — this passes because `to_signable_string` never includes the shop header: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and `body` fully attacker-controlled (from step 1), and acts on the victim shop's tenant data as if Shopify had authentically sent that payload for that shop.
