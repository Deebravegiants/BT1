### Title
Fee-on-transfer tokens cause escrow over-crediting / protocol insolvency in `IntentGatewayV2.placeOrder` (Tron) - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
In the Tron variant of `IntentGatewayV2.placeOrder`, the same-chain token-pull path uses `safeTransferFrom` for the user-specified `order.inputs[i].amount` but never measures the actual balance received by the contract. The escrow credited to the order (`_orders[commitment][token]`) is computed from the pre-transfer requested amount reduced only by the protocol fee, not from the tokens actually held. For any ERC20 with a transfer fee (or any deflationary/rebasing mechanic), the gateway receives less than what it credits to escrow, over-crediting the internal ledger relative to the real token balance.

### Finding Description
In the non-predispatch branch of `placeOrder`: [1](#0-0) 

tokens are pulled with `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and escrow is immediately incremented by `reducedInputs[i].amount`, which is derived earlier purely from `order.inputs[i].amount` minus the protocol fee, computed before any transfer occurs: [2](#0-1) 

No balance-before/after check is performed, so if the ERC20 token charges a transfer fee, the amount actually received by the contract is strictly less than `reducedInputs[i].amount` that gets written into `_orders[commitment][token]`. This mapping is later used to authorize withdrawals (via `cancelOrder`'s same-chain `withdraw` call and the destination-chain fill/settlement flow), so the contract promises to pay out more of that token than it actually holds.

This is the same root-cause class as the referenced Kairos `RepayFacet.checkedTransferFrom` bug: trusting the nominal transfer amount instead of verifying actual received balance for a token that can apply transfer fees.

Notably, the sibling production contract `evm/src/apps/IntentGatewayV2.sol` already fixes this exact issue by snapshotting balances before/after the transfer and mutating `order.inputs[i].amount` to the actual received amount before computing `reducedInputs`/commitment/escrow: [3](#0-2) 

The predispatch branch of the same Tron file is also inconsistent — it computes real `balance`/`dust` from the dispatcher's actual holdings [4](#0-3)  but still credits escrow using `reducedInputs[i].amount` (based on the originally requested, pre-fee amount) rather than the fee-adjusted `balance`, so the double-fee scenario validated in the EVM test suite (`testPlaceOrder_FeeOnTransferToken_Predispatch`) is not correctly handled on Tron either.

### Impact Explanation
Any unprivileged user can call `placeOrder` with a fee-on-transfer ERC20 as an input token. The contract will hold fewer tokens than it records in `_orders`, meaning the internal accounting across all orders for that token becomes inflated. When orders are later settled/withdrawn (`cancelOrder` → `withdraw`, or destination-side settlement), the contract can attempt to pay out more of that token than it physically holds — draining tokens escrowed for other, legitimate orders and causing insolvency/loss of funds for the protocol and other users. This matches High severity: concrete loss of funds via unbacked escrow accounting, reachable from a single unprivileged transaction.

### Likelihood Explanation
High likelihood: no privileged role is required — any user placing an order with a fee-on-transfer, deflationary, or rebasing ERC20 token triggers the mismatch deterministically on every such order. Fee-on-transfer tokens are common in the wild, and the bug requires no special conditions beyond selecting such a token as `order.inputs[i].token`.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure `balanceOf(address(this))` before and after each `safeTransferFrom` (and after the dispatcher sweep in the predispatch path) to determine the actual received amount, mutate `order.inputs[i].amount` to that value, and compute `reducedInputs`/the commitment/escrow credit from the actual received amount rather than the originally requested amount, applying the same logic to both the direct-transfer and predispatch branches in `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Deploy a 1%-fee ERC20 (`FeeOnTransferToken`, as used in the existing EVM test suite [5](#0-4) ) and mint balance to a user.
2. User approves the Tron `IntentGatewayV2` for `inputAmount = 1000e18` and calls `placeOrder` with that token as the single input (no predispatch).
3. `safeTransferFrom` moves `1000e18` requested, but due to the 1% fee the contract only receives `990e18` [6](#0-5) .
4. `_orders[commitment][token]` is nonetheless credited with `reducedInputs[i].amount` computed from the full `1000e18` (minus only the protocol fee) [7](#0-6) , i.e. escrow says ~`1000e18`-minus-protocol-fee is available, while the contract actually holds only `990e18`.
5. When this order (or others sharing the same token pool) is later withdrawn/cancelled, the contract attempts to pay out based on the inflated `_orders` ledger, exceeding its actual token balance and depleting funds belonging to other escrowed orders.

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
