The `Registry.process` method validates the webhook HMAC solely against the raw request body via `Request#to_signable_string`, which returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all read from unauthenticated headers [2](#0-1) . `Registry.process` forwards these unauthenticated header values directly into `WebhookMetadata`, which is handed to the app's `WebhookHandler#handle` [3](#0-2) [4](#0-3) .

### Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) header values are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated once `Utils::HmacValidator.validate(request)` succeeds [5](#0-4) . The HMAC, however, is computed over `to_signable_string`, which for `Webhooks::Request` is only the raw HTTP body [1](#0-0) . The `shop` value (and `topic`, `api_version`, `webhook_id`) are parsed straight from HTTP headers and are not part of the signed bytes [2](#0-1) . This breaks the equality the gem implicitly relies on: `bytes verified by HMAC == bytes used to identify the tenant`. In reality, `bytes verified (raw body) != bytes used for tenant identification (shop header)`.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string` and HMACs it, comparing against the `hmac` header/attribute using `OpenSSL.secure_compare` [6](#0-5) . For webhook requests, `to_signable_string` returns solely `@raw_body` [1](#0-0) , meaning the HMAC only proves that a valid Shopify-issued body+signature pair exists — it proves nothing about which shop, topic, webhook id, or API version was originally associated with that signed body.

`Registry.process` uses `request.topic` to look up a handler and then constructs `WebhookMetadata` using `request.shop`, `request.parsed_body`, `request.api_version`, and `request.webhook_id`, all taken from headers, and passes it to the registered handler [3](#0-2) . Since `shop` is not bound to the HMAC, a party who has captured (or otherwise obtained) any one genuine `(raw_body, hmac)` pair for a topic that is registered in the host app can resend it with an arbitrary `shopify-shop-domain` header value of their choosing, and the library will report it as fully validated and hand the forged shop identity to the app's webhook handler as if Shopify had asserted it.

### Impact Explanation
Because host applications are expected to trust `WebhookMetadata#shop` as the authenticated tenant identifier when persisting webhook data or triggering tenant-scoped side effects (e.g., updating merchant records, deleting data, or crediting/debiting resources keyed by shop), an attacker who can supply a valid `(body, hmac)` pair for any topic can make the library assert an arbitrary `shop` value for that payload. This is a cross-tenant identity binding break: `shop authenticated by the gem != shop the HMAC actually covers`, satisfying the Critical "cross-tenant access" impact category, since data intended for shop A can be attributed to shop B purely by header manipulation once a valid signed body is available.

### Likelihood Explanation
Exploitation requires obtaining at least one genuine raw body + HMAC pair for a topic the target app has registered a handler for (e.g., by operating one's own Shopify shop that is a customer of the target app, or replaying/observing a previously delivered webhook), then replaying it with a different `x-shopify-shop-domain` header. No knowledge of `api_secret_key` or the target's access tokens is required because the body/HMAC signature is being reused as-is, not forged from scratch — only the unauthenticated headers are altered. This is a realistic, low-privilege scenario for anyone who is themselves a merchant with the app installed.

### Recommendation
Bind `shop`, `topic`, `webhook_id`, and `api_version` into the HMAC-signable string (or otherwise cryptographically verify them, e.g. by cross-checking against a value obtained through an authenticated API call keyed by webhook id) instead of trusting header-only values that sit outside the signed payload in `Webhooks::Request#to_signable_string`.

### Proof of Concept
1. Attacker operates or has observed a legitimately delivered webhook for shop `victim-a.myshopify.com` with topic `orders/create`, capturing the exact raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` using the app's shared secret).
2. Attacker POSTs to the app's webhook endpoint with:
   - `x-shopify-hmac-sha256: H`
   - `x-shopify-topic: orders/create`
   - `x-shopify-shop-domain: victim-b.myshopify.com` (any other shop using the app)
   - body: `B`
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` and matches `H` successfully [5](#0-4) .
4. `WebhookMetadata.new(topic: "orders/create", shop: "victim-b.myshopify.com", body: JSON.parse(B), ...)` is constructed and passed to the app's handler as an authenticated event for `victim-b`, even though the payload actually originated from `victim-a` [7](#0-6) .
