### Title
Webhook shop/topic identity not covered by HMAC allows cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The reported bug class is a broken identity binding that lets an unprivileged actor act under someone else's identity because a value used to authorize/attribute an action is not the value actually verified. In `ShopifyAPI::Webhooks::Request`, only the JSON body bytes are covered by the HMAC signature, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — which are used downstream to select the handler and to attribute the event to a shop — are taken directly from unauthenticated HTTP headers.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `hmac` is computed from a `hmac-sha256` header [2](#0-1) . `shop`, `topic`, `webhook_id`, and `api_version`, however, are read straight from headers and are never part of the signed material [3](#0-2) .

`Utils::HmacValidator.validate` only re-computes the HMAC over `to_signable_string` (the body) and compares it to the supplied `hmac` [4](#0-3) . `Webhooks::Registry.process` calls this validator and, if it passes, dispatches directly using the unauthenticated `request.topic` to look up the handler and forwards the unauthenticated `request.shop` into the handler’s `WebhookMetadata` [5](#0-4) .

The equality that should hold is: `shop/topic verified by HMAC == shop/topic acted upon by the handler`. In practice the code enforces only `hmac(body) == hmac(body)` while `shop`/`topic` are trusted unconditionally from headers, so the two sides diverge — the identity attributed to the event is not the identity that was cryptographically verified.

### Impact Explanation
Because the app's `client_secret`/`api_secret_key` is shared across all shops that install the app, any actor who can obtain one valid `(body, hmac)` pair for the app (e.g., by installing the app on their own store and capturing a genuine webhook delivery, which Shopify will send to any installer) possesses a signature that is valid HMAC-wise regardless of which shop or topic header accompanies it. That actor can then replay the same body+hmac to the app's webhook endpoint while forging the `X-Shopify-Shop-Domain` and `X-Shopify-Topic` headers to claim a different shop or a different (even mandatory, e.g. `shop/redact`, `customers/redact`, `customers/data_request`) topic. Since `Registry.process` trusts these header-derived values for handler dispatch and for the `shop` attribute passed to the handler, this can cause the host application's webhook handler to execute business logic (e.g., data deletion, redaction, order/customer processing) attributed to the wrong tenant — a cross-tenant action driven entirely by unauthenticated header values that this gem itself resolves and forwards.

### Likelihood Explanation
Medium-to-High: exploitation requires only (1) the ability to install the target app on an attacker-controlled shop to legitimately harvest a body+hmac pair (freely available to any merchant/developer for public apps), and (2) sending a forged HTTP request with attacker-chosen headers and the captured body/hmac to the app's public webhook endpoint. No access to `api_secret_key`, tokens, or the victim's shop is needed — only observation of the gem's own trust boundary (`Utils::HmacValidator.validate` verifying only the body, `Registry.process` trusting header-derived `shop`/`topic`).

### Recommendation
Extend the HMAC-verifiable payload (or add a second signed binding) to include the `shop` domain and `topic`, not just the raw body, so that any change to these header-derived identity fields invalidates the signature. Alternatively, require `Registry.process` to cross-check `request.shop` against the shop that the app has on record as the recipient of the webhook (e.g., compare against the session/shop under which the corresponding webhook registration was created) before invoking the handler, rather than trusting the header value unconditionally.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a genuine webhook for topic `orders/create` with body `B` and header `x-shopify-hmac-sha256: H` (valid because `H = HMAC(api_secret_key, B)`, and the secret is shared across all installs of this app).
2. Attacker sends `POST /webhooks` to the app's endpoint with:
   - Body: `B` (unchanged)
   - Headers: `x-shopify-hmac-sha256: H` (unchanged), `x-shopify-shop-domain: victim.myshopify.com`, `x-shopify-topic: shop/redact` (or any other topic/shop of the attacker's choosing).
3. `Webhooks::Request.new` parses these headers into `shop`/`topic` [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `HMAC(secret, B) == H` [7](#0-6) .
5. `Registry.process` looks up the handler for the forged `shop/redact` topic and invokes it with `shop: "victim.myshopify.com"` [8](#0-7) , causing the host application to perform redaction/deletion logic attributed to a shop the attacker does not own — a cross-tenant action triggered purely through fields that were never covered by the HMAC.

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
