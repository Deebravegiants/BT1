### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC signature validated by `HmacValidator.validate` proves nothing about which shop (tenant) the webhook is claimed to be for. Because Shopify signs every shop's webhooks for an app with the same shared `client_secret`, any merchant that has the app installed can capture one of their own genuine webhook deliveries (valid body + valid HMAC) and replay it to the app's webhook endpoint with the `x-shopify-shop-domain`/`shopify-shop-domain` header rewritten to a different shop. The gem accepts this as authentic because the signature check never binds the signed bytes to the shop identity that is ultimately dispatched to the handler.

### Finding Description
`Request#hmac` and `Request#to_signable_string` only cover `@raw_body`: [1](#0-0) [2](#0-1) 

`shop` is read straight from an attacker-controllable header with no cross-check against the signed payload: [3](#0-2) 

`HmacValidator.validate` computes the signature only over `to_signable_string` (i.e., the body) and compares it to the supplied `hmac`, never touching `shop`: [4](#0-3) 

`Registry.process` treats HMAC success as full authenticity, then forwards `request.shop` (the unauthenticated header value) straight to the webhook handler as the tenant identity: [5](#0-4) 

The identity binding that should hold is:
`shop identity dispatched to handler (request.shop)` == `shop identity cryptographically bound inside the HMAC-signed bytes`

Before the attack: for a legitimate webhook, both sides are shop A (the HMAC covers a body Shopify generated for shop A, and the header also says shop A — they happen to agree only because Shopify controls both).

After the attacker's request sequence: a merchant who legitimately owns shop A triggers a real event (e.g., `orders/create`) to obtain a genuine `(raw_body, hmac)` pair signed with the app's shared secret. They then POST this same `raw_body`/`hmac` to the app's webhook endpoint but with the `shop-domain` header changed to shop B. `HmacValidator.validate` still returns `true` (the body/HMAC pair is untouched and valid), but `request.shop` now returns `"shop-b.myshopify.com"`. `Registry.process` dispatches the handler with `shop: "shop-b.myshopify.com"` even though the signed content actually originated from shop A. The equality is broken: the dispatched identity no longer matches the identity actually bound by the signature.

### Impact Explanation
This lets any merchant who can install the app (an "unprivileged" party relative to other tenants of the same app) forge webhook events that the app will process as if they came from an arbitrary other shop, since the `client_secret` used to sign webhooks is shared across all installations of the same app. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., looking up/updating per-shop records, or acting on mandatory compliance topics like `customers/data_request`, `customers/redact`, `shop/redact`), this enables cross-tenant data confusion or spoofed compliance/lifecycle events for a shop the attacker does not own — a cross-tenant access issue.

### Likelihood Explanation
Any user who can self-serve install the app on a shop (a very low privilege bar, typically no different from a normal merchant) already has the raw material needed: a real, validly-signed webhook body/HMAC pair from their own shop's traffic. Rewriting a single non-signed HTTP header and replaying the request is straightforward and requires no access to the `client_secret`, no TLS interception, and no privileged account.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cryptographically tie the `shop-domain` header to the signed payload before trusting it — e.g., include the `shop` (and other identifying headers) in `to_signable_string`, or cross-validate `request.shop` against the shop associated with the specific webhook subscription/topic before dispatching to a handler.

### Proof of Concept
1. Install the target app on shop A (`shop-a.myshopify.com`), a shop the attacker legitimately controls.
2. Trigger a real webhook event (e.g., create an order) and capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair sent by Shopify — both values are valid and signed with the app's shared `client_secret`.
3. Replay this exact `raw_body`/HMAC pair to the app's webhook endpoint, but set `x-shopify-shop-domain: shop-b.myshopify.com` (a shop the attacker does not control).
4. `ShopifyAPI::Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the HMAC.
5. `ShopifyAPI::Webhooks::Registry.process` invokes the registered handler with `shop: "shop-b.myshopify.com"`, causing the host application to process shop A's forged event under shop B's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
