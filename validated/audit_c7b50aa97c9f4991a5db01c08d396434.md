## Title
Webhook `shop-domain` and `topic` headers are trusted without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — which are handed to the app's webhook handler as trusted, tenant-identifying data — come from HTTP headers that are never included in the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers with no cryptographic binding to that signature: [2](#0-1) 

`Registry.process` validates only the HMAC over the raw body, then forwards the unauthenticated `shop`/`topic`/`webhook_id`/`api_version` header values straight to the app's handler as `WebhookMetadata`: [3](#0-2) 

The equality this breaks: the gem implicitly claims `hmac_valid(raw_body) == tenant_bound(shop, topic, raw_body)`, but in reality `hmac_valid` only proves knowledge of the shared secret for the *body bytes*; it proves nothing about which shop or topic header accompanied that body. This is structurally the same class of bug as the report's AaveV3 issue: a value that is *acted upon* (there: `amount`; here: `shop`/`topic`) is not the value that was actually *verified* (there: the bundler's real balance; here: the HMAC-signed bytes).

### Impact Explanation
Because Shopify signs webhook bodies with the app's shared secret and many webhook payloads for different shops/topics can be structurally identical or predictable (e.g., empty-body webhooks, or bodies with a fixed/guessable shape for a given topic), any entity able to obtain one genuine, validly-signed webhook delivery for *any* topic/shop pair (including their own store, which they can legitimately install the app on) can replay that exact `raw_body` while substituting an arbitrary `shopify-shop-domain` and/or `shopify-topic` header value. Since only `raw_body` is verified, `Utils::HmacValidator.validate(request)` still passes, and the handler receives attacker-chosen `shop`/`topic` values as if they were authentic. If the host application uses `WebhookMetadata#shop` to select which tenant's data/session to mutate (a very common pattern, since that's the field's entire purpose), this allows cross-tenant data manipulation using only a webhook signed for the attacker's own store — i.e., no access token, no `client_secret`, and no privileged account beyond being an ordinary merchant who installed the app.

### Likelihood Explanation
Exploitability depends on whether a webhook body for some topic is content-independent of the shop (e.g. topics with fixed/empty payloads, or where the attacker can influence body content, such as by setting shop metadata equal to another target's identifiers) and on the host app trusting `WebhookMetadata#shop`/`topic` without independently re-verifying tenant scope. This makes the bug reachable but the practical blast radius shop-dependent; still, the design flaw itself (header data excluded from the signed payload) is concrete and verifiable purely from library code.

### Recommendation
Include `shop`, `topic`, `webhook_id`, and `api_version` in the signable string used for HMAC verification (or otherwise cryptographically bind them, mirroring how `AuthQuery#to_signable_string` binds `code`, `host`, `shop`, `state`, and `timestamp`), so that tampering with any of these headers invalidates the signature:
```ruby
sig { override.returns(String) }
def to_signable_string
  "#{topic}#{shop}#{webhook_id}#{api_version}#{@raw_body}"
end
```

### Proof of Concept
1. Install the app on shop `attacker.myshopify.com` and capture a legitimate webhook delivery for a topic with a fixed/empty body, e.g. `orders/create` test payload `{}` with headers:
   - `shopify-hmac-sha256: <valid HMAC of "{}">`
   - `shopify-shop-domain: attacker.myshopify.com`
   - `shopify-topic: orders/create`
2. Replay the exact same body/HMAC to the app's webhook endpoint but replace the header:
   - `shopify-shop-domain: victim.myshopify.com`
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb:12-22`, which only checks `to_signable_string`, i.e. the raw body).
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: {}, ...)`, exactly as demonstrated at [3](#0-2) , even though this webhook was never actually sent by/about `victim.myshopify.com`.
