### Title
Webhook `shop-domain` (and other headers) are not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` (tenant identifier), `topic`, `api_version`, and `webhook_id` are all read from unsigned HTTP headers. Because `Registry.process` trusts `request.shop` for tenant attribution after validating only the body's HMAC, an attacker can take a legitimately-signed webhook payload (from any shop where the app is installed, including their own) and resubmit it to the app's webhook endpoint with a forged `shopify-shop-domain` header pointing at a victim shop. The signature check still passes because the header is not part of the signed data, causing the host app to process attacker-controlled data under the victim's tenant.

### Finding Description
The identity binding that should hold is: `shop` header used to route/attribute webhook data == `shop` bytes covered by the HMAC signature. In this gem that equality is broken.

`ShopifyAPI::Webhooks::Request#hmac` decodes the `hmac-sha256` header, and `#to_signable_string` returns only `@raw_body`: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled straight from HTTP headers via `shopify_header`, none of which are included in `to_signable_string`: [3](#0-2) [4](#0-3) 

`HmacValidator.validate` only recomputes the signature over `to_signable_string` (i.e., the body) and compares it to the `hmac` header — it never touches the shop/topic/version/webhook-id headers: [5](#0-4) 

`ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identifier passed to the app's handler: [6](#0-5) 

Because the HMAC only binds the body bytes, any party who obtains one valid `(raw_body, hmac)` pair — trivially available to any merchant with the app installed on their own store, since Shopify signs webhook bodies with the single shared `client_secret` for all shops — can replay that exact body+HMAC to the app's public webhook endpoint while substituting an arbitrary `shopify-shop-domain` header. The signature verification succeeds (it only checks the body), but `Registry.process` and the resulting `WebhookMetadata` attribute the payload to the attacker-chosen shop, not the shop that actually produced it. This is a direct break of the "shop authenticated vs. shop used as tenant key" binding and a "field acted on but not covered by the HMAC" instance.

### Impact Explanation
This allows an unprivileged user (any merchant that can install the app on a shop they control) to inject attacker-controlled webhook events into another merchant's tenant context inside the host application (e.g., faking `orders/create`, `app/uninstalled`, GDPR, or other webhook payloads as coming from a victim shop). Depending on how the host app's webhook handlers use `WebhookMetadata#shop`, this can lead to cross-tenant data corruption, unauthorized state changes, or triggering of tenant-specific side effects (e.g., de-provisioning, billing changes, data deletion) for a shop the attacker does not own — a cross-tenant access impact.

### Likelihood Explanation
Medium-to-High: the attacker needs no credentials belonging to the app or the victim — only a body+HMAC pair, which is obtainable from any shop where the app is installed (including a shop the attacker themselves installs the app on, since the HMAC secret is shared across all shops for a given app). The webhook endpoint is by design internet-reachable and unauthenticated aside from the HMAC check, so directly POSTing a forged request with a spoofed `shop-domain` header is straightforward.

### Recommendation
Include the `shop`, `topic`, `api_version`, and `webhook_id` header values in the HMAC-signed payload used by `to_signable_string` (or otherwise cryptographically bind them, e.g., signing the header set combined with the body), so that tampering with any of these identity-relevant fields invalidates the signature. At minimum, the `shop` value used for tenant attribution must be part of what is verified, not read from a header that sits entirely outside the HMAC computation.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (or otherwise obtains a genuine webhook delivery: body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`).
2. Attacker sends a POST directly to the app's webhook endpoint:
   ```
   POST /webhooks
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com   # forged
   Body: B
   ```
3. `ShopifyAPI::Webhooks::Request#hmac` reads `H`; `HmacValidator.validate` recomputes `HMAC-SHA256(client_secret, B)` and it matches `H`, so validation succeeds — the forged `shop-domain` header was never part of the check.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-supplied data under the victim shop's tenant context.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
