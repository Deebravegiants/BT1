### Title
Excess native-token fee overpayment is permanently stuck in `EvmHost`, with the loss amplified by Uniswap V2 price manipulation - ([File: evm/src/core/EvmHost.sol])

### Summary
`EvmHost.dispatch(DispatchPost)` and `EvmHost.dispatch(DispatchGet)` swap any attached `msg.value` for the exact fee-token amount via `IUniswapV2Router02.swapETHForExactTokens`, but pass `address(this)` (the Host) as the router call's `msg.sender` context and never check or refund unused ETH afterward. Because Uniswap V2's `swapETHForExactTokens` refunds excess ETH to whoever called the router — the `Host` contract itself, not the original dispatcher — any ETH sent beyond the exact amount needed becomes permanently stuck in the Host. The amount of "excess" is entirely a function of the live, unprotected Uniswap V2 spot price, which any unprivileged actor can manipulate (sandwich) around the `dispatch()` call to widen the gap and increase the amount trapped.

### Finding Description
In `dispatch(DispatchPost)`:
```solidity
if (msg.value > 0) {
    address[] memory path = new address[](2);
    address uniswapV2 = _hostParams.uniswapV2;
    path[0] = IUniswapV2Router02(uniswapV2).WETH();
    path[1] = feeToken();
    IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
        post.fee, path, address(this), block.timestamp
    );
}
``` [1](#0-0) 

The identical pattern exists in `dispatch(DispatchGet)`: [2](#0-1) 

`swapETHForExactTokens(amountOut, path, to, deadline)` computes the exact input required at the current pool reserves and, if `msg.value` exceeds that computed input, refunds the difference — but that refund goes to the router's caller, which in this call chain is the `EvmHost` contract, **not** the address that invoked `dispatch()`. `EvmHost` never reads back a returned "amounts spent" value, never computes or forwards a refund to `_msgSender()`, and has no `receive()`/`withdraw` path visible in this contract that would let a user reclaim the stranded ETH. The `deadline` is also hardcoded to `block.timestamp`, i.e. no real staleness protection, and there is no `amountInMax` cap distinct from `msg.value` — so the actual amount consumed is whatever the manipulated pool prices at that block, with the remainder simply orphaned inside the Host.

This is the reachable analog to the reported Curve pricing issue: instead of `get_virtual_price()` being read mid-reentrancy, here the price used to convert native token → fee token is read live off a manipulable Uniswap V2 pool with no oracle guard, no TWAP, and no slippage bound tied to the caller's expectations — and the docs even acknowledge quoting via this router is "vulnerable to sandwich attacks," but that warning only covers the off-chain `quote()` helper, not the on-chain swap actually executed inside `dispatch()`. [3](#0-2) 

### Impact Explanation
Any unprivileged user dispatching a POST/GET request with native-token payment (a routine, permissionless action reachable from a single transaction) can have ETH permanently locked in the Host contract whenever the live Uniswap V2 price differs from what they estimated off-chain via `quote()`. An attacker can sandwich the victim's `dispatch()` call — pushing the pool price so the swap consumes less ETH than the victim sent — to maximize the ETH orphaned in the Host on each dispatch. Because there is no code path shown that lets the Host or the original sender reclaim this ETH, this constitutes a permanent freezing-of-funds condition triggered from a single unprivileged dispatch transaction, which qualifies as at least a High-severity issue under the fund-loss/freezing criteria.

### Likelihood Explanation
High likelihood: `dispatch()` is the primary, permissionless entry point for all POST/GET message senders paying with native token (documented as the recommended path for "one-off transactions, user-facing apps"), so the vulnerable code executes on essentially every cross-chain send funded in ETH. Manipulating a Uniswap V2 pool's spot price via a sandwich is a well-understood, cheap, and repeatable attack available to any MEV searcher, requiring no special privileges — it is directly analogous to how the reported Curve issue is exploitable by any party interacting around a victim's transaction.

### Recommendation
After the `swapETHForExactTokens` call, capture the returned `amounts[0]` (actual ETH consumed) and explicitly refund `msg.value - amounts[0]` to `_msgSender()` (or `post.payer`), rather than relying on the router's refund semantics, which target the Host as caller. Additionally, enforce a caller-supplied `maxFee`/slippage bound instead of allowing `amountInMax` to implicitly equal the entire `msg.value`, and consider a TWAP-based or otherwise manipulation-resistant price source for the native→fee-token conversion.

### Proof of Concept
1. Attacker observes a pending `dispatch(DispatchPost)` call with `msg.value = X` intended to purchase `post.fee` fee-tokens.
2. Attacker front-runs with a large swap on the same Uniswap V2 pool that temporarily lowers the ETH price needed to obtain `post.fee` fee-tokens (or simply relies on natural pool drift between the victim's off-chain `quote()` estimate and on-chain execution).
3. Victim's `dispatch()` executes `swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)`; the router consumes `amountIn < X` and refunds `X - amountIn` ETH — but to `msg.sender` of the router call, i.e., the `EvmHost` contract itself.
4. Attacker back-runs to restore the pool price (extracting the sandwich profit as usual), while the leftover ETH remains in `EvmHost`'s balance with no accounted-for owner and no visible reclaim function in this contract, so it is permanently unrecoverable by the victim. [1](#0-0)
