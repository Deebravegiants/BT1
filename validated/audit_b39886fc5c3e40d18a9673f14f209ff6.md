### Title
Non-embedded OAuth session cookie is an unsigned, predictable session identifier, enabling session fixation / cross-tenant session hijacking - (File: lib/shopify_api/auth/oauth/session_cookie.rb, lib/shopify_api/utils/session_utils.rb)

### Summary
For the non-embedded Authorization Code Grant flow, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser session cookie's `value` to the raw, deterministic `Session#id` string (`"offline_#{shop}"` or `"#{shop}_#{associated_user.id}"`). `ShopifyAPI::Utils::SessionUtils.cookie_session_id` later trusts that exact cookie content as the authoritative lookup key for retrieving the stored session/access token, with no cryptographic signature binding the cookie to the OAuth exchange that created it.

### Finding Description
In `lib/shopify_api/auth/oauth.rb`, `validate_auth_callback` builds the cookie for the non-embedded flow directly from the session id: [1](#0-0) 

`Session.from` computes that id deterministically and predictably as `"offline_#{shop}"` for offline sessions or `"#{shop}_#{associated_user.id}"` for online sessions: [2](#0-1) 

The `SessionCookie` struct itself carries no signature or MAC — it is a plain `name`/`value`/`expires` tuple: [3](#0-2) 

`SessionUtils.current_session_id`/`cookie_session_id` then reads that cookie's raw value back out and returns it, unverified, as the session id the host application must use to fetch the stored access-token session: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: *session id trusted by the host application == session id that was actually authenticated by Shopify's OAuth grant for this browser*. Instead, because the cookie value is just the deterministic, unauthenticated string `"offline_#{shop}"` (or `"#{shop}_#{user_id}"`) with no HMAC/signature tying it to the specific OAuth completion that issued it, the binding collapses to: *session id trusted by the host application == whatever bytes are in an unauthenticated cookie the attacker's own browser sends*. `shop` domains are public (`{store}.myshopify.com`), and for offline sessions the id requires no secret information at all, so an attacker can simply set `shopify_app_session=offline_victim-shop.myshopify.com` in their own browser and have the host app (using this gem's `SessionUtils.current_session_id`) resolve and use the victim shop's stored offline session/access token.

### Impact Explanation
This is cross-tenant access: an unprivileged internet user can cause a host application built on this gem to authenticate their request as belonging to a different merchant's stored session (and its access token) purely by forging a cookie value, without ever completing OAuth for that shop or possessing any secret. This matches the "session id derived from unauthenticated bytes" analog and constitutes a Critical-class cross-tenant access issue as defined by the rules.

### Likelihood Explanation
Likelihood is high for any non-embedded app that follows this library's documented flow (`docs/usage/oauth.md`) and relies on `SessionCookie`/`SessionUtils.cookie_session_id` as designed: the offline session id requires knowledge of only the target shop's domain, which is not secret, and no additional cryptographic material is needed to construct a valid-looking cookie value.

### Recommendation
Do not use the raw, deterministic `Session#id` as the literal cookie value trusted for session lookup. Either sign/HMAC the cookie value (binding it to the api_secret_key and issuance time) and verify that signature in `SessionUtils`, or store only an opaque, cryptographically random token in the cookie that indirectly maps to the session id server-side, so the cookie content itself cannot be forged or replayed across tenants.

### Proof of Concept
1. Attacker knows (or discovers) the victim's shop domain `victim-shop.myshopify.com` (public information, e.g., visible in the app's install URL or storefront).
2. Victim previously completed OAuth so the host app persisted an offline session under id `offline_victim-shop.myshopify.com` (per `Session.from`, `lib/shopify_api/auth/session.rb:107-121`).
3. Attacker, in their own browser, sets the cookie `shopify_app_session=offline_victim-shop.myshopify.com` for the host application's domain.
4. The host application calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which (per `lib/shopify_api/utils/session_utils.rb:19-37,68-71`) returns `"offline_victim-shop.myshopify.com"` directly from the forged cookie with no verification.
5. The host app looks up and activates the victim's stored session/access token, and the attacker's subsequent API calls are executed with the victim merchant's Admin API access token.

      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
