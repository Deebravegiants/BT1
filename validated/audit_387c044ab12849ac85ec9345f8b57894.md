### Title

RAY accrual overflows total debt before the index cap and permanently freezes a whale market - (File: common/src/rates/simulate.rs)

### Summary

A market whose scaled debt or supply is large enough can make `borrowed * borrow_index` or `supplied * supply_index` overflow before the configured index ceiling is applied. Because every pool mutation accrues interest first and a failed accrual rolls back the timestamp update, the market thereafter rejects repayment, withdrawal, liquidation, recapitalization, and further index updates with `MathOverflow`. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description

`accrue_step` first converts scaled debt and scaled supply to their original values through `scaled_to_original`, then computes utilization, the next borrow index, rewards, and the next supply index. [1](#0-0)  `scaled_to_original` delegates to checked fixed-point multiplication, while `Ray::mul` reports overflow as `MathOverflow` rather than saturating. [4](#0-3) [5](#0-4) 

The index ceiling is not an effective guard against this condition: `update_borrow_index` clamps only the next index, while `calculate_supplier_rewards`, `update_supply_index`, and `supply_index_reward_shortfall` still multiply potentially very large share balances by the index. [6](#0-5) [7](#0-6) [8](#0-7)  Consequently, a market can cross the total-value `i128` ceiling while its stored borrow index remains below `MAX_BORROW_INDEX_RAY`. [9](#0-8) 

`global_sync` performs all interest chunks in memory and calls `mark_accrued` only after the loop completes. [2](#0-1)  When a chunk panics, the entire transaction reverts and `last_timestamp` remains stale, so the next attempt repeats the same overflowing computation. [10](#0-9)  Every pool leg loads an interest-synced market through `synced_market` or `load_leg`, so the failure is inherited by ordinary pool mutations. [3](#0-2) 

An unprivileged account can reach this state through the normal `supply` and `borrow` entrypoints, and any user can subsequently invoke market index accrual. [11](#0-10) [12](#0-11) 

### Impact Explanation

Once the product crosses the `i128` domain, suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize positions, and recapitalization cannot repair the book because all of those paths accrue first. [3](#0-2) [13](#0-12)  The regression scenario demonstrates that `update_indexes`, `withdraw`, and `repay` all fail with `MathOverflow` after the market crosses the RAY-value ceiling. [14](#0-13) 

This is permanent freezing of user funds rather than a rejected invalid input: the market remains in the same unaccrued state, and increasing the ledger timestamp cannot make the overflowing product fit again. [10](#0-9) [15](#0-14) 

### Likelihood Explanation

The trigger requires a very large listed market and enough outstanding debt for `scaled_debt * borrow_index` or `scaled_supply * supply_index` to approach `i128::MAX`, so it is not reachable on an ordinary small market. [16](#0-15)  Nevertheless, the path uses only public account operations and public accrual: supply a large permitted position, borrow it to sustained high utilization, allow the index to grow, then call `update_indexes`. [11](#0-10) [12](#0-11) 

No oracle manipulation, privileged key, leaked key, reentrancy, or malformed external call is required; the problematic state is produced by valid share balances and normal time-based accrual. [1](#0-0) [2](#0-1) 

### Recommendation

Apply a dynamic value ceiling before every share-to-value multiplication used by accrual. In particular, calculate the largest borrow index that keeps `borrowed * borrow_index / RAY` within `i128`, and similarly constrain the supply-side products before calling `update_supply_index` or `supply_index_reward_shortfall`. [17](#0-16) [7](#0-6) [8](#0-7) 

The effective index cap should be `min(MAX_BORROW_INDEX_RAY, floor(i128::MAX * RAY / borrowed_scaled_raw))`, with an equivalent bound for supply value, so interest stops accruing at the numeric boundary instead of making the market unrecoverable. [6](#0-5) [15](#0-14)  Add a regression test proving that a market approaching this boundary clamps accrual and still permits `repay`, `withdraw`, liquidation, and `clean_bad_debt` paths that must load the market. [3](#0-2) [18](#0-17) 

### Proof of Concept

1. Use an active 18-decimal market whose governance-configured caps admit approximately `1_000_000_000` whole tokens and whose rate curve reaches the steep high-utilization segment. [19](#0-18) 
2. From one owned account, call `supply` with `1_000_000_000 * 10^18` base units of the target asset, then supply sufficient collateral in another listed market. [20](#0-19) [21](#0-20) 
3. Call `borrow` for roughly 98% of the target market, producing scaled debt near `9.8e35` RAY. [22](#0-21) [21](#0-20) 
4. Advance ledger time and invoke the public `update_indexes` path for the market. [12](#0-11) [23](#0-22) 
5. Once the borrow index is high enough that `borrowed_scaled * borrow_index` exceeds `i128::MAX`, `accrue_step` panics before the index ceiling can save the market. [24](#0-23) [6](#0-5) 
6. The timestamp remains unaccrued, so subsequent `update_indexes`, `repay`, `withdraw`, and liquidation attempts repeat the same overflow. [10](#0-9) [25](#0-24) 

The repository already contains a reproduction of this boundary in `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`. [26](#0-25)

/// The cliff. A billion whole tokens is `1e36` raw ray; the value ceiling is
/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
