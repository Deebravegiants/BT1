## Analysis

The report's "missing docstrings" issue is a generic Solidity documentation gripe with no direct Move/Aptos analog. Reducing it to a custody invariant ("code must behave exactly as documented/expected, or reviewers/users can't verify safety"), I searched Aptos-native object/code-object flows for a case where the *actual* code diverges from its documented/asserted invariant in a way that breaks custody. The strongest candidate is a broken acyclicity invariant in the core `object::transfer` authorization logic.

### Title
Object ownership-transfer verification allows creating a permanent ownership cycle, causing non-recoverable loss of control over object-held assets and out-of-gas denial of `root_owner`-gated flows - (File: aptos-move/framework/aptos-framework/sources/object.move)

### Summary
`object::verify_ungated_and_descendant` only validates that the *destination*'s current owner chain eventually reaches the transferring signer; it never checks whether the object being moved is itself already part of that chain. By performing two ordinary, individually-authorized `object::transfer` calls in a specific order, any object owner can make two objects mutually own each other, producing a 2-cycle with no terminating account owner. This state is permanent: every future transfer attempt aborts via the depth bound, and the unbounded `root_owner()` walk (used by `code::publish_package` and `init::assert_may_self_initialize`) will loop until out of gas.

### Finding Description
`verify_ungated_and_descendant` [1](#0-0)  walks from `destination` upward until it reaches `owner`, bounded by `MAXIMUM_OBJECT_NESTING`. It never checks that the address of the *object currently being transferred* does not itself appear on that chain.

Consider signer `S` owning two directly-owned objects `A` and `B` (`allow_ungated_transfer = true`, the default set in `ObjectCore` at creation, see [2](#0-1) ):

1. `S` calls `object::transfer(S, A, to=B)`. `verify_ungated_and_descendant(S, B)` sees `B.owner == S` and passes trivially. `transfer_raw_inner` sets `A.owner = B` [3](#0-2) .
2. `S` calls `object::transfer(S, B, to=A)`. `verify_ungated_and_descendant(S, A)` walks `A.owner == B`, then `B.owner == S` — matches `S` within one hop, so it **passes**. `transfer_raw_inner` sets `B.owner = A`.

After step 2, `A.owner == B` and `B.owner == A`: a closed 2-cycle with no account root. Each individual transfer was validated against the state *before* it executed, so the check never sees the cycle it is about to complete.

This state is unrecoverable:
- Any further `object::transfer`/`transfer_to_object` involving `A` or `B` calls `verify_ungated_and_descendant`, which will never find `owner` in the cycle and will deterministically abort with `EMAXIMUM_NESTING` after 8 hops [4](#0-3) , permanently freezing ownership.
- `object::root_owner()`, which is used to gate custody-relevant operations, has **no** depth bound at all (unlike `owns()`, which is correctly bounded): [5](#0-4) . Calling it on `A`/`B` (or on anything nested under them) loops forever, aborting only via out-of-gas.
- `root_owner()` is load-bearing for code-object custody: `code::publish_package` calls it to record/verify the object's deploy owner for lazy self-initialization [6](#0-5) , and `init::assert_may_self_initialize` calls it to gate whether a module hosted on an object may obtain a signer for itself [7](#0-6) . If a code object (published via `object_code_deployment::publish`, whose `ManagingRefs`/`ExtendRef` and upgrade authority are tied to the object address) is drawn into such a cycle, any subsequent `publish_package`/`upgrade` call that reaches the lazy-init gate will hang and abort on gas, permanently locking upgrade/freeze authority for that code object, and by extension any assets or logic that depend on upgrading that module.

### Impact Explanation
Any two objects an actor legitimately owns can be turned into a self-referential pair that (a) can never again be transferred by anyone (owner reassignment is permanently blocked), and (b) will hang any code path relying on `root_owner()`, including framework-level code-object publish/upgrade gating. This is a genuine custody break: object ownership — and therefore control of any resources, fungible stores, or nested objects held under `A`/`B` — becomes permanently non-recoverable, satisfying "permanent lock or non-recoverable loss of object-held ... or code-object-held value." Because the primitive is in the base `object` module, it affects every protocol built on Aptos Objects (token objects, fungible-asset stores holding value under an object, code objects), not just a single application.

### Likelihood Explanation
The steps require only two ordinary, permissionless `object::transfer` entry-function calls by the legitimate current owner of both objects — no privileged capability, `TransferRef`, or protocol-specific bug is needed. This can be triggered directly by a user against their own objects (self-griefing, or as a vector to permanently disable a shared/vault/code object they still control at the time), or unknowingly by any protocol that transfers objects between other objects based on external/user-influenced ordering (e.g., a vault or marketplace that reparents NFTs/stores between object "buckets"). The bug is deterministic, requires no race condition, and reproduces on every attempt.

### Recommendation
Fix `verify_ungated_and_descendant` to also reject a destination chain that includes the object being transferred itself (cycle detection at transfer time), not just chains that fail to reach `owner` within the depth bound. Additionally, bound `root_owner()`'s traversal by `MAXIMUM_OBJECT_NESTING` (mirroring `owns()`) and treat an unresolved walk as an error rather than looping unboundedly, so that even if a legacy/pre-existing cycle is ever encountered, callers such as `code::publish_package` and `init::assert_may_self_initialize` fail fast with a clear abort instead of consuming all remaining gas.

### Proof of Concept
```
// Pseudocode, using aptos_framework::object as S:
let a_ref = object::create_object(signer::address_of(&s));
let b_ref = object::create_object(signer::address_of(&s));
let a = object::object_from_constructor_ref<ObjectCore>(&a_ref);
let b = object::object_from_constructor_ref<ObjectCore>(&b_ref);

// Step 1: A -> B (trivially valid: B is directly owned by s)
object::transfer(&s, a, object::object_address(&b));

// Step 2: B -> A (valid because A's chain currently resolves back to s via B)
object::transfer(&s, b, object::object_address(&a));

// Now object::owner(a) == object_address(b) and object::owner(b) == object_address(a).
// Any further transfer of a or b aborts with EMAXIMUM_NESTING.
// object::root_owner(a) or object::root_owner(b) loops forever (no bound), aborting only on out-of-gas.
```
This directly mirrors the existing unit tests in `object.move`/`init.move` (e.g. `self_init_blocked_when_owner_transferred`) but demonstrates that the transfer-time check itself, not just downstream consumers, fails to prevent the invalid state from being constructed in the first place.

    /// This checks that the destination address is eventually owned by the owner and that each
    /// object between the two allows for ungated transfers. Note, this is limited to a depth of 8
    /// objects may have cyclic dependencies.
    fun verify_ungated_and_descendant(owner: address, destination: address) {
        let current_address = destination;
        assert!(
            exists<ObjectCore>(current_address),
            error::not_found(EOBJECT_DOES_NOT_EXIST),
        );

        let object = borrow_global<ObjectCore>(current_address);
        assert!(
            object.allow_ungated_transfer,
            error::permission_denied(ENO_UNGATED_TRANSFERS),
        );

        let current_address = object.owner;
        let count = 0;
        while (owner != current_address) {
            count += 1;
            assert!(count < MAXIMUM_OBJECT_NESTING, error::out_of_range(EMAXIMUM_NESTING));
            // At this point, the first object exists and so the more likely case is that the
            // object's owner is not an object. So we return a more sensible error.
            assert!(
                exists<ObjectCore>(current_address),
                error::permission_denied(ENOT_OBJECT_OWNER),
            );
            let object = borrow_global<ObjectCore>(current_address);
            assert!(
                object.allow_ungated_transfer,
                error::permission_denied(ENO_UNGATED_TRANSFERS),
            );
            current_address = object.owner;
        };
    }
