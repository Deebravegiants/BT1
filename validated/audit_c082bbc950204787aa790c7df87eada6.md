### Title
Tron IntentGatewayV2 uses raw `block.number` for order cancellation deadline instead of the L2-safe `_blockNumber()` helper - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The main EVM IntentGatewayV2/ExtrinsicIntents implementation was hardened against exactly the GMX-style L1/L2 block-number confusion bug: order deadlines are compared using an internal helper `_blockNumber()` that queries the ArbSys precompile on Arbitrum instead of the raw `block.number` opcode (which returns the much-smaller L1 block height on Arbitrum). However, the parallel Tron port of the same contract, `evm/tron/contracts/apps/IntentGatewayV2.sol`, still performs the destination-side cancellation authorization check with the raw `block.number` opcode, not the safe helper.

### Finding Description
In the canonical implementation, `IntentsBase._blockNumber()` is documented and implemented specifically to avoid the "wrong block number on L2" bug class: [1](#0-0) 

This helper is correctly used for deadline checks in `fillOrder` and in `_cancelFromDest`: [2](#0-1) [3](#0-2) 

The test suite even explicitly documents and tests this exact GMX-style regression (an L2 deadline is unexpirable if raw `block.number`, i.e. Arbitrum's L1 height, is used): [4](#0-3) 

However, the Tron variant of the same `cancelOrder` logic, in the destination-chain cancellation branch, checks the deadline against the raw `block.number` opcode instead of any L2-safe equivalent: [5](#0-4) 

This file has no `_blockNumber()` helper, no `ARBITRUM_ONE`/`ARB_SYS` constant, and no ArbSys precompile reference at all — confirmed by grep across `evm/tron/**`, which returned zero matches for `ARBITRUM_ONE|_blockNumber|IArbSys|ARB_SYS`. If this Tron-ported contract (or a similarly-derived fork) is ever deployed to, or its logic reused as a template for, an Arbitrum-style Layer-2 chain where `block.number` returns an L1-anchored value rather than the L2 sequencing height that `order.deadline` is denominated in, the destination-side authorization gate `if (order.deadline >= block.number) { onlyOwner-check }` will behave incorrectly:

- `block.number` on such an L2 stays far below the L2-denominated `order.deadline` for a very long time (since L1 blocks accrue much slower than L2 blocks), so the "anyone may cancel after expiry" branch never opens even long after the order should have truly expired — freezing the ability for third parties/relayers to trigger legitimate post-expiry cancellations on behalf of the user.
- Conversely, if deadlines were denominated differently, the mismatch could also allow the "public cancel" branch to open prematurely, letting anyone other than the order owner cancel and reroute the `RefundEscrow` before genuine expiry, which given `_filled[commitment]` is set unconditionally in this branch, permanently blocks the legitimate owner from ever filling/cancelling the order themselves (a permanent freeze of the escrowed funds' correct redemption path).

### Impact Explanation
This directly maps to the reachable "token bridger / intent solver" surface named in scope: `IntentGatewayV2.cancelOrder` is a single unprivileged, user- or relayer-submitted transaction that gates escrow refund authorization and dispatch of the cross-chain `RefundEscrow` message. A wrong block-number source breaks the deadline invariant the contract's authorization model depends on, which can result in either a permanent freeze of legitimate cancellation rights or unauthorized destination-side order cancellation/refund routing by a non-owner before genuine expiry — both are concrete fund-freezing/authorization-bypass outcomes, consistent with the accepted High severity of the original GMX report (escalated specifically on "loss of funds"/incorrect-timing reasoning).

### Likelihood Explanation
Likelihood depends on whether the Tron contract (or code derived from it) is or will be deployed on an Arbitrum-style rollup where `block.number` diverges from the L2 sequencing height used to set `order.deadline`. The sibling `evm/src` implementation was deliberately patched with `_blockNumber()`/ArbSys handling specifically because such deployments are expected, and the accompanying comments/tests confirm this is a known, actively-guarded-against risk for this exact contract family. The Tron copy appears to be an un-synced fork that missed this fix, making the risk concrete for any Arbitrum-class deployment sharing this code path, though moderate since Tron itself does not have this L1/L2 issue — the risk materializes if this codebase is deployed to or reused on an Arbitrum-style chain.

### Recommendation
Port the `_blockNumber()` helper (with ArbSys precompile detection, as done in `evm/src/apps/intentsv2/IntentsBase.sol`) into `evm/tron/contracts/apps/IntentGatewayV2.sol`, and replace the raw `block.number` comparison in the `_cancelFromDest`-equivalent branch (and any other order-deadline check in this file) with the safe helper, mirroring the fix already applied to the canonical `evm/src` implementation.

### Proof of Concept
1. Deploy the Tron-variant `IntentGatewayV2.sol` contract logic (or a fork sharing this exact `cancelOrder` code) on an Arbitrum-style L2 where `order.deadline` is denominated in L2 block heights (as documented for the canonical implementation) but the `block.number` opcode returns the L1 block height.
2. A user places a cross-chain order with `deadline` set to a near-term L2 block height.
3. Time passes; on the real L2, many blocks are produced and the order is genuinely expired per L2 height, but `block.number` (L1 height) remains far below `order.deadline`.
4. `cancelOrder` on the destination chain evaluates `order.deadline >= block.number` as still true, so the "anyone may cancel" branch never opens — a third party or automated relayer cannot cancel on behalf of the user, effectively freezing the refund path for as long as the L1/L2 rate gap persists (potentially indefinitely, mirroring the original GMX ADL-block issue where L1-based tracking never catches up).

```text
    /**
     * @dev Returns the current block number of the host chain. Order deadlines are
     * denominated in the block heights Hyperbridge tracks for each state machine —
     * for Arbitrum chains that is the L2 block number, but the `block.number` opcode
     * there returns the approximate L1 block number, so the ArbSys precompile is
     * queried instead. The chain id check keeps the bytecode identical across all
     * chains, preserving the deterministic CREATE2 deployment addresses.
     * @return The chain-appropriate current block number.
     */
    function _blockNumber() internal view returns (uint256) {
        if (block.chainid == ARBITRUM_ONE || block.chainid == ARBITRUM_NOVA || block.chainid == ARBITRUM_SEPOLIA) {
            return IArbSys(ARB_SYS).arbBlockNumber();
        }
        return block.number;
    }
```

```text
    /// @dev On Arbitrum the gateway must read the L2 block number from the ArbSys precompile;
    /// the `block.number` opcode there returns the (much smaller) L1 block number, which would
    /// keep expired orders fillable forever.
    function testFillOrderExpiredOnArbitrumUsesArbSys() public {
        uint256 inputAmount = 1000 * 1e6;
        // A deadline denominated in Arbitrum L2 blocks, far above both the current
        // fork's block.number and any L1 block number.
        uint256 l2Deadline = 400_000_000;

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(usdc)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(uint256(uint160(user))),
            source: host.host(),
            destination: host.host(),
            deadline: l2Deadline,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        usdc.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Pretend we're on Arbitrum One: ArbSys reports an L2 block number past the deadline
        // while block.number (~L1 height on Arbitrum) remains far below it.
        vm.chainId(42161);
        vm.etch(address(100), hex"fe"); // Arbitrum precompiles expose 0xfe as their code
        vm.mockCall(address(100), abi.encodeWithSignature("arbBlockNumber()"), abi.encode(l2Deadline + 1));
        assertLt(block.number, l2Deadline);

        vm.startPrank(filler);
        dai.approve(address(intentGateway), type(uint256).max);

        TokenInfo[] memory solverOutputs = new TokenInfo[](1);
        solverOutputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 1000 * 1e18});

        vm.expectRevert(IntentsBase.Expired.selector);
        intentGateway.fillOrder(
            order, FillOptions({relayerFee: 0, nativeDispatchFee: 0, validUntil: 0, outputs: solverOutputs})
        );
        vm.stopPrank();
    }
```
