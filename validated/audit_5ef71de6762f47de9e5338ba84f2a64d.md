### Title
`VWAPOracle._normalizeAmount` overflows and reverts on attacker-supplied token decimals, DoSing spread recording for intent fills - (File: `evm/src/utils/VWAPOracle.sol`)

### Summary
`VWAPOracle.recordSpread` normalizes token amounts to 18 decimals by calling `_normalizeAmount`, which computes `amount * 10 ** (_decimals - 18)` (or divides) with no upper bound on `_decimals`. The output-side decimals are pulled directly from an untrusted external call, `IERC20Metadata(outputToken).decimals()` [1](#0-0) . Since an order's output token is attacker-controlled (any user can name an arbitrary ERC20 as the output asset of their own intent), a malicious token contract can return an inflated `decimals()` value (e.g. 96+), which makes `10 ** (_decimals - 18)` exceed `type(uint256).max` and revert under Solidity 0.8 checked arithmetic — exactly the same root cause pattern as the referenced Oracle.sol finding (unguarded decimals arithmetic assumed to stay within a "safe" range).

### Finding Description
`_normalizeAmount` is defined as: [2](#0-1) 

For `_decimals > 18`, the function computes `amount / (10 ** (_decimals - 18))`, and for the input side it's `amount * (10 ** (18 - _decimals))`. On the output side (`outputDecimals`), the value is not admin-configured — it is read live from the token contract itself via `IERC20Metadata(outputToken).decimals()` [1](#0-0) , with no bound checking, unlike the admin-set `_tokenDecimals` mapping used for the input side (which is also unbounded but is at least set through a permissioned/governance path via `_processTokenDecimalsUpdates`) [3](#0-2) . The existing test suite (`testInitWithHighDecimals`, `testHighDecimalsNormalization`) explicitly validates decimals up to 24 work fine, but nothing bounds decimals values above ~77, at which point `10 ** (_decimals - 18)` overflows `uint256` and the EVM reverts on the exponentiation, exactly mirroring the `36 - feedDecimals - tokenDecimals` unguarded arithmetic in the referenced Oracle.sol report.

Since `outputToken` in `recordSpread`'s `outputs[i].token` array is derived from order data supplied by an unprivileged user creating an intent (the party who defines the order's requested output asset), an attacker can name a custom malicious ERC20 contract with a `decimals()` function returning an oversized value (e.g. 200) as the output token of their own order.

### Impact Explanation
`recordSpread` is restricted to be called only by `_intentGateway` [4](#0-3) , indicating it is invoked synchronously as part of the intent-fill/settlement flow. If a filler attempts to fill an order whose output token is the malicious high-decimals contract, the call into `_normalizeAmount` for the output leg reverts, causing the entire `recordSpread` call — and by extension the enclosing fill transaction from the Intent Gateway — to revert. This can be used to grief/DoS fills of a specific order (and potentially any batch fill including it), a form of permanent freezing/blocking of an intent's settlement since every attempt to fill that order will hit the same revert.

### Likelihood Explanation
Likelihood is moderate-to-high: the only requirement is that the attacker deploys a trivial ERC20-like contract that hardcodes a `decimals()` return value beyond ~77, and names it as the output token of their own intent order. No privileged access, governance action, or malicious-admin assumption is needed — this is purely an unprivileged intent-creator/message path, consistent with the "intents escrow and bids" reachable surface.

### Recommendation
Cap `_decimals` used in `_normalizeAmount` (both for the admin-configured `_tokenDecimals` and for the live `IERC20Metadata(outputToken).decimals()` read) to a sane maximum (e.g. reject or clamp decimals > 36, similar to the original C4 finding's mitigation of branching normalization logic based on whether `feedDecimals + tokenDecimals` exceeds a safe bound). Concretely, validate `outputDecimals <= MAX_ALLOWED_DECIMALS` before calling `_normalizeAmount`, and revert with a clear, catchable error (or skip normalization/spread recording for that token) instead of letting the exponentiation overflow bubble up and revert the whole fill.

### Proof of Concept
1. Attacker deploys `EvilToken` implementing `IERC20Metadata` with `decimals()` returning `200`.
2. Attacker creates an intent order whose `output.assets` includes `EvilToken` as `outputToken`.
3. A filler attempts to fill the order; the Intent Gateway calls `VWAPOracle.recordSpread(commitment, sourceChain, inputs, outputs)` with `outputs[i].token = EvilToken`.
4. Inside `recordSpread`, `outputDecimals = IERC20Metadata(EvilToken).decimals() == 200` [1](#0-0) .
5. `_normalizeAmount(outputs[i].amount, 200)` executes `amount / (10 ** (200 - 18))` = `amount / (10 ** 182)` — but computing `10 ** 182` itself overflows `uint256` (max exponent for base 10 is 77) and reverts under Solidity 0.8 checked math [2](#0-1) .
6. The revert propagates through `recordSpread` and blocks the fill transaction, permanently preventing that order from settling as long as the malicious token is used.

    function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
    }
