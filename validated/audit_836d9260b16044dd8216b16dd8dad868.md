## Analysis

This is a valid analog. The Tron variant of `IntentGatewayV2` deliberately uses OpenZeppelin's `SafeERC20` (`using SafeERC20 for IERC20;`) for all inbound token pulls (`placeOrder`, `fillOrder`, `cancelOrder` fee payments), but the outbound settlement path in `withdraw()` bypasses `SafeERC20` and uses a raw low-level `call` that only checks that the call itself didn't revert — it never decodes/validates the returned boolean.

### Title
Unchecked ERC-20 return value in `IntentGatewayV2.withdraw()` allows silent transfer failure to be recorded as a successful escrow release - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`withdraw()`, the function that settles `RedeemEscrow`/`RefundEscrow` requests and releases user/solver escrow, moves tokens with a raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` and treats the operation as successful whenever the low-level call does not revert, without inspecting the returned `bool`. Everywhere else in the same contract (`placeOrder`, `fillOrder`, `cancelOrder`) the codebase correctly uses `SafeERC20.safeTransferFrom`/`safeTransfer`, which validates the ABI-decoded return value in addition to call success.

### Finding Description
`withdraw()` is invoked from `onAccept()` when a `RedeemEscrow` or `RefundEscrow` message is authenticated and delivered, and from `cancelOrder()`/`onGetResponse()` for same-chain refunds: [1](#0-0) 

For every non-native token in the withdrawal request, the code does:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
```
then unconditionally decrements `_orders[body.commitment][token] -= amount;` and, on finalize, marks the order `_filled[body.commitment] = beneficiary`.

Per the EVM `call` semantics, `success` is `true` as long as the callee doesn't revert — regardless of what boolean value (if any) the ERC-20 `transfer` function returns in its return data. Many real-world ERC-20 tokens return `false` on failure instead of reverting (the counterpart failure mode to USDT's "returns nothing" quirk cited in the source report). For such tokens, a failed transfer (e.g., due to a paused token, blacklist, or insufficient balance in an unusual edge case) will still show `success == true`, so `TransferFailed` never fires, escrow accounting is decremented, and the order is marked filled/refunded — even though the beneficiary never received the tokens.

This is the same root-cause class as the reported bug (non-standard ERC-20 return-value handling), but manifests as the inverse defect: instead of reverting on tokens with no return data, this code fails to detect failure on tokens that return `false`. The rest of the contract shows the developers know the correct fix (`SafeERC20`) — `withdraw()` and the `SweepDust` branch in `onAccept()` are the outliers that don't use it: [2](#0-1) [3](#0-2) 

By contrast, the canonical EVM `IntentGatewayV2` (`evm/src/apps/intentsv2/IntentsBase.sol`) uses `safeTransfer` for the equivalent release path: [4](#0-3) 

### Impact Explanation
Because `_orders[...]` is decremented and the order is marked filled/refunded regardless of whether tokens actually left the contract, a transfer that silently fails (returns `false`) results in: the escrowed balance being wiped from accounting while the tokens physically remain locked in the contract with no path to reclaim them (the commitment is already marked filled, so `UnknownOrder`/`Filled` guards block any retry), and the intended beneficiary (order owner, solver, or relayer fee recipient) permanently losing the funds they were owed. This is a permanent freezing/loss of funds in the intents escrow settlement path.

### Likelihood Explanation
Triggering this requires an input/output token used in an order to be one of the (uncommon but real) ERC-20 implementations that return `false` rather than reverting on failure. Any user placing an order chooses the input token, and any solver chooses the fill output token, so the attack surface is reachable without any privileged role — a user or solver can select such a token, or a token they control could be engineered to return `false` under attacker-chosen conditions to grief the settlement of their own or an interacting solver's escrow. Likelihood is Medium since it depends on the specific token's return-value behavior rather than being universally exploitable, matching the "Medium" severity of the original report.

### Recommendation
Use `SafeERC20.safeTransfer` (already imported and used via `using SafeERC20 for IERC20;` in this same file) inside `withdraw()` and the `SweepDust` branch of `onAccept()` instead of raw `token.call(...)` with only a `success` check, so both "no return data" and "returns false" failure modes are correctly detected and reverted.

### Proof of Concept
1. Deploy a token whose `transfer()` returns `false` (instead of reverting) when a transfer condition isn't met (e.g., a paused/blacklist-style token, or one deliberately crafted to return `false` when called from `IntentGatewayV2`).
2. Place and fill an order using this token as an input/output asset so it becomes escrowed under `_orders[commitment][token]`.
3. Trigger settlement (`RedeemEscrow`/`RefundEscrow` delivery or same-chain `cancelOrder`) so `withdraw()` executes; the crafted token's `transfer()` returns `false` but does not revert.
4. Observe `success == true` in `withdraw()`, so `TransferFailed` is not raised, `_orders[commitment][token]` is decremented, and `_filled[commitment]` is set — while the beneficiary's token balance is unchanged, permanently losing the escrowed amount.

        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }
