### Title
Unsigned cross-chain calldata lets an attacker dispatch arbitrary runtime calls as any account - (File: `modules/pallets/hyper-fungible-token/src/module.rs`)

### Summary
`Pallet::on_accept` in the `hyper-fungible-token` module ISMP handler decodes an untrusted, attacker-controlled `SubstrateCalldata` blob (embedded in `message.data`, itself part of the abi-decoded `Message` body of an incoming `PostRequest`) and, when `substrate_data.signature` is `None`, dispatches the enclosed `runtime_call` with `RawOrigin::Signed(origin)` where `origin` is derived directly from the attacker-supplied `message.from` bytes rather than from any authenticated identity.

### Finding Description
`on_accept` decodes the ABI body into `Message { from, to, amount, data }` [1](#0-0) , and if `message.data` is non-empty it SCALE-decodes it into `SubstrateCalldata { signature: Option<Vec<u8>>, runtime_call: Vec<u8> }` — both untrusted, attacker-controlled deserialization targets [2](#0-1) .

When `signature` is `Some`, the code correctly verifies an Ed25519/Sr25519/Ecdsa signature over `(nonce, runtime_call)` against the beneficiary's key before allowing dispatch [3](#0-2) .

However, when `signature` is `None`, the origin is derived purely from `message.from` — bytes that live inside the ABI-encoded body and are fully controlled by whatever contract/account calls the sending `HyperFungibleToken` contract on the source chain, not authenticated by any cryptographic proof of key ownership on the destination chain: [4](#0-3) 

That derived `origin` is then used to dispatch the fully attacker-controlled `runtime_call` (only gated by `BaseCallFilter`, which is a governance-wide allow/deny list, not an authorization check): [5](#0-4) 

The `Message.from` ABI field is defined as raw `bytes` in both the pallet's mirrored type [6](#0-5)  and the Solidity struct, i.e. it is caller-suppliable payload data embedded in the request body, not a value the ISMP host or protocol enforces to equal the true message sender. The only authentication actually performed on `on_accept` is that the *module* address (`from`/`source` in the `PostRequest`, i.e. the sending contract) is a registered token contract [7](#0-6)  — this says nothing about the identity encoded inside `message.from`.

This is the direct analog of CVE-2023-39680's bug class: untrusted data is deserialized (`SubstrateCalldata::decode`, then `T::RuntimeCall::decode`) and used to drive privileged execution — here, dispatching an arbitrary runtime extrinsic as an arbitrary account — without properly authenticating the deserialized content in the unsigned branch.

### Impact Explanation
Any unprivileged actor who can send a POST request through a registered HyperFungibleToken/WrappedHyperFungibleToken contract (which is by design permissionless — any user can invoke the bridge to send tokens with attached calldata) can craft `message.from` to equal the SS58/H160-derivable bytes of an arbitrary victim account and omit `signature`, causing the destination pallet to dispatch an arbitrary `RuntimeCall` as `RawOrigin::Signed(victim)`. Depending on what calls `BaseCallFilter` permits, this can enable unauthorized transfers, governance/proxy manipulation, or other privileged actions performed "as" any account on the destination chain — a direct theft-of-funds / unauthorized-app-action primitive reachable from a single token bridge transfer.

### Likelihood Explanation
High. The attacker only needs to call the standard cross-chain send path of the HyperFungibleToken bridge (a normal, unprivileged, permissionless entry point) with an ABI-encoded `Message.data` field containing a `SubstrateCalldata` with `signature: None` and a `from` value matching the target victim's account bytes. No relayer collusion, governance, or privileged role is required — only a valid proof that a legitimate cross-chain token message was sent, which any user can trigger for a message of their own crafting.

### Recommendation
Remove the unsigned/`None`-signature fallback path entirely, or require that `message.from` be independently verified as the true origin (e.g., always require a valid signature binding `runtime_call` to `message.from`/`beneficiary`, and never derive a dispatch origin from unauthenticated body bytes). At minimum, when `signature` is `None`, do not dispatch any `runtime_call` — treat calldata execution as requiring proof of key ownership in all cases.

### Proof of Concept
1. Attacker deploys/uses a standard call to the source-chain `HyperFungibleToken` contract to send a token transfer.
2. Attacker ABI-encodes the `Message` body with `to` = attacker's own beneficiary address, `amount` = arbitrary, and `data` = SCALE-encoded `SubstrateCalldata { signature: None, runtime_call: <SCALE-encoded call, e.g. Balances::transfer(attacker, victim_reserves)> }`.
3. Attacker sets the `from` field of the `Message` body to the raw bytes corresponding to a victim's H160/AccountId (this field is not checked against `msg.sender` by the destination pallet).
4. Relayer (or attacker acting as relayer) submits the standard PostRequest proof; `pallet-ismp` routes it to `hyper-fungible-token`'s `on_accept`.
5. Because `substrate_data.signature` is `None`, `on_module.rs:176-187` computes `origin` from the attacker-chosen `from` bytes and dispatches `runtime_call` as `RawOrigin::Signed(origin)` [8](#0-7) , executing the call as the victim account without their consent.
