### Title
SA-token Node-binding extras are trusted as genuine node-identity by DRA's `saAssociatedWithAllocatedNode`, enabling cross-node privilege escalation without kubelet/pod placement - ([File: pkg/registry/core/serviceaccount/storage/token.go])

### Summary
`TokenREST.Create` allows any caller with `create` on `serviceaccounts/token` and `get` on a `Node` object to mint a token whose `Subject` is a ServiceAccount but which carries `authentication.kubernetes.io/node-name`/`node-uid` extras identical to those set for a legitimately kubelet-scheduled pod. `pkg/registry/resource/utils.go`'s `saAssociatedWithAllocatedNode` (used by `AuthorizedForDeviceStatus`) treats the mere presence of a matching `NodeNameKey` extra as proof that the calling SA is "on" that node, without verifying the binding came from an actual pod scheduled there (which is the only case enforced by `plugin/pkg/admission/noderestriction/admission.go`'s `admitServiceAccount`). This lets an attacker holding token-creation rights for a DRA-driver SA spoof association with an arbitrary node.

### Finding Description
`TokenREST.Create` (`pkg/registry/core/serviceaccount/storage/token.go:211-221`) handles `BoundObjectRef.Kind == "Node"` by simply doing a `Get` on the named node and using its `UID`; this path is reachable for **any** SA the caller has `create serviceaccounts/token` rights on, with **no** requirement that the caller's own identity, pod, or node has any relationship to the target node - unlike the pod-bound path, which is additionally constrained at admission time by `plugin/pkg/admission/noderestriction/admission.go:672-723` (`admitServiceAccount`), which only fires for token requests originating from a node identity and enforces that the bound pod is scheduled on the requesting node.

`pkg/serviceaccount/claims.go:123-130` and the validator (`pkg/serviceaccount/claims.go:252-282`) then produce/consume a `Node` ref for such tokens exactly as they would for a genuinely pod-scheduled, kubelet-attested token, and `staging/src/k8s.io/apiserver/pkg/authentication/serviceaccount/util.go:46-51` defines the resulting `NodeNameKey`/`NodeUIDKey` extras that both binding paths populate identically.

`pkg/registry/resource/utils.go:277-300` (`saAssociatedWithAllocatedNode`), consumed by `AuthorizedForDeviceStatus` (`pkg/registry/resource/utils.go:150-181`), uses exactly these extras as a proxy for "this SA's identity is associated with node X," and if true, additionally tries the `associated-node-<verb>` RBAC permission (in addition to `arbitrary-node-<verb>`) when authorizing writes to `resourceclaims/driver` status. This function makes no distinction between a `NodeNameKey` populated via the admission-plugin-gated, kubelet-attested pod-binding path and one populated via the unrestricted, self-selectable `Kind: Node` binding path in `TokenREST.Create`. An attacker who can create a token for the DRA driver's SA can therefore choose `BoundObjectRef={Kind: Node, Name: <any-node>}` to obtain a token with `NodeNameKey=<any-node>`, and use it to satisfy `saAssociatedWithAllocatedNode` for a claim allocated to an arbitrary node the caller has no actual presence on.

### Impact Explanation
This is a Kubernetes-recognized "authorization/RBAC bypass via identity confusion" class of impact: RBAC design for DRA driver SAs that intentionally grants a narrower `associated-node-<verb>` permission (rather than the broader `arbitrary-node-<verb>`) relies on `NodeNameKey` as a hard per-node scoping signal. Because the signal can be self-chosen through the standalone Node-binding TokenRequest path, the scoping is defeated: an attacker (or a compromised/over-permissioned SA-token-issuer) can write `status.devices` (device health/allocation status) for `ResourceClaim`s bound to nodes it has no legitimate presence on, impersonating the DRA driver for an arbitrary node.

### Likelihood Explanation
Requires: (1) `create` on `serviceaccounts/token` for the specific SA that a cluster operator has granted `associated-node-*` RBAC for DRA driver status updates, and (2) `get` on the targeted `Node` object (a commonly and broadly granted read permission). Both are plausible, narrow, namespace-scoped grants rather than cluster-admin access, and the exploit is fully reproducible via a single `TokenRequest` API call plus a `ResourceClaim` status update - no timing races, no cluster state manipulation beyond object reads.

### Recommendation
`saAssociatedWithAllocatedNode` (or upstream token issuance) must distinguish tokens whose node binding was established via kubelet/node-restriction-attested pod scheduling from tokens that self-selected an arbitrary `Node` via the standalone `Kind: Node` `BoundObjectRef` path — e.g., by adding a distinct extra/claim key (or reusing the pod-bound-node marker) that is only ever set through the `ServiceAccountTokenPodNodeInfo` pod path, and never through the standalone `ServiceAccountTokenNodeBinding` path, then have `saAssociatedWithAllocatedNode` check that marker instead of the generic `NodeNameKey`.

### Proof of Concept
Integration test (extending `test/integration/auth/svcaccttoken_test.go` and `pkg/registry/resource/utils_test.go`):
1. Create SA `dra-driver-sa` and grant it RBAC: `resourceclaims/driver` verb `associated-node-update` for driver `my-driver` (but not `arbitrary-node-update`).
2. Grant a low-privileged test principal `create` on `serviceaccounts/token` for `dra-driver-sa` and `get` on all `Node` objects (minimal RBAC).
3. As the low-privileged principal, call `CreateToken(dra-driver-sa, BoundObjectRef={Kind:Node, Name:"victim-node", UID:<victim-node-uid>})`.
4. Assert the returned token, when reviewed via `TokenReview`, has `Extra["authentication.kubernetes.io/node-name"] == ["victim-node"]`.
5. Create a `ResourceClaim` with `status.allocation` pinned to `victim-node` via `NodeSelector` matching `metadata.name=victim-node`, allocated to driver `my-driver`, where the acting SA (`dra-driver-sa`) never had a pod scheduled on `victim-node`.
6. Using the minted token, attempt to update `status.devices` for that claim.
7. Expected (current, vulnerable) behavior: the update succeeds via `AuthorizedForDeviceStatus` -> `saAssociatedWithAllocatedNode` returning `true` and the `associated-node-update` RBAC check passing.
8. Expected (fixed) behavior: the update is rejected because the node association was never attested by kubelet/pod scheduling, only `arbitrary-node-update` (not granted) would apply.
