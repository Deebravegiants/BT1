### Title
Webhook `shop` and `topic` headers are trusted for tenant/handler dispatch without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then dispatches to the handler using the `shop` and `topic` values taken from HTTP headers that are never included in the signed payload. This breaks the intended identity binding `hmac-authenticated bytes == bytes acted on`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string using the app's single, shop-independent `Context.api_secret_key` [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` values, however, are read straight from attacker-controllable HTTP headers via `shopify_header` [3](#0-2) [4](#0-3) .

`Registry.process` validates the HMAC, then immediately uses `request.topic` and `request.shop` — both unsigned — to select the handler and populate `WebhookMetadata` passed to the host application's handler: [5](#0-4) 

Because the HMAC secret (`api_secret_key`) is a single value shared across every shop that has the app installed — not a per-shop secret — any body+HMAC pair that was genuinely produced by Shopify for *one* tenant's webhook (which an unprivileged merchant of shop A can trivially obtain, since they receive their own webhooks) remains a **valid** HMAC pair for the *same body* regardless of which `shop-domain`/`topic` header is attached. The signature proves "this body was HMAC'd with our api_secret_key" but proves nothing about which shop or topic it belongs to.

Equality that should hold but doesn't:
`shop authenticated by HMAC` ⇔ `shop acted upon by the handler`

In this code, the left side is undefined (the HMAC covers no shop identifier at all), while the right side is `request.shop`, an unauthenticated header value.

### Impact Explanation
An unprivileged holder of a genuine webhook body+HMAC pair for their own tenant (shop A) can replay that exact body to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header for shop B. `HmacValidator.validate` still returns `true` because it only checks the raw body against the shared secret. `Registry.process` then invokes the registered handler with `shop: "shop-b.myshopify.com"` and shop A's (attacker-controlled/attacker-known) body content. If the host application uses `WebhookMetadata#shop` to key persistence, cache invalidation, order/inventory updates, uninstall/GDPR actions, or session/session-store lookups (the intended and documented usage per `WebhookMetadata`), this results in cross-tenant data corruption or state confusion — one merchant's webhook traffic being attributed to and acted upon for a different merchant's account. This matches the Critical "cross-tenant access" impact category.

### Likelihood Explanation
This requires no leaked credentials, no access token, and no privileged access — the attacker only needs to be a merchant who has installed the target app (an ordinary, unprivileged position) to legitimately receive their own webhook deliveries, capture body+HMAC, and replay them with forged headers to the app's public webhook endpoint. All identity-relevant values (`shop`, `topic`) are ordinary HTTP headers with no cryptographic tie to the signed body, so likelihood of successful exploitation is high wherever the host app trusts `WebhookMetadata#shop`/`#topic` for tenant-scoped effects, which is the very purpose these fields are documented to serve.

### Recommendation
Bind the identity fields into the signature verification rather than trusting headers post-hoc:
- Include `shop`, `topic`, and `webhook_id` (or at minimum `shop`) in the value that is HMAC-verified, or
- Require callers (host apps) to independently confirm that `shop` matches a shop for which a legitimate installation/session exists before dispatch, and document/enforce this in `Registry.process` itself (e.g., raise unless the resolved shop has an active session), or
- Since Shopify's actual HMAC scheme only signs the body by design, `Registry.process` should not expose `shop`/`topic` as if they were verified data — rename/flag them as unauthenticated, and require the host app to fetch the canonical shop/topic via a secondary authenticated channel (e.g., cross-check against `webhook_id` via the Admin API) before trusting them for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target app on `shop-a.myshopify.com` (ordinary, unprivileged merchant action).
2. Attacker triggers/observes a legitimate webhook delivery to the app for `shop-a`, capturing the raw body `B` and the header `X-Shopify-Hmac-Sha256: H` (valid because `H = HMAC-SHA256(api_secret_key, B)`).
3. Attacker crafts a new POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (a victim tenant) and, if desired, a different `X-Shopify-Topic`.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/webhooks/request.rb`/`lib/shopify_api/utils/hmac_validator.rb` succeeds because it only checks `B` against `H` using the shared `api_secret_key` — it never inspects `shop-domain`.
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) dispatches to the handler with `shop: "shop-b.myshopify.com"`, causing the host application to process attacker-supplied/attacker's-own body content as if it originated from shop B.
