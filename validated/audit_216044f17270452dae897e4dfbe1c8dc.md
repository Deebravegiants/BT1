### Title
Frozen (paused) EvmHost permanently blocks `handlePostRequestTimeouts` / `handleGetRequestTimeouts`, trapping user-escrowed funds that can only be recovered via timeout - (File: `evm/src/core/HandlerV2.sol`)

### Summary
`HandlerV2` gates every incoming-message entrypoint — including the two timeout handlers — behind the same `notFrozen(host)` modifier used for request/response delivery. When the host's `FrozenStatus` is `Incoming` or `All`, users whose only recovery path is a timeout (e.g. an `IntentGatewayV2`/`ExtrinsicIntents` cross-chain `cancelOrder` GET request, or any app relying on `PostRequestTimeout`/`GetRequestTimeout` to release escrow) cannot process that timeout and reclaim their funds while the freeze is active, mirroring the reported pattern where `whenNotPaused` blocks the user's own exit/close action.

### Finding Description
`HandlerV2.handlePostRequestTimeouts` and `HandlerV2.handleGetRequestTimeouts` are both restricted by: [1](#0-0) [2](#0-1) [3](#0-2) 

This is the same modifier that gates `handlePostRequests` and `handleGetResponses`, i.e. normal incoming message delivery: [4](#0-3) [5](#0-4) 

The distinction matters: unlike normal message delivery (which resumes once the freeze is lifted and no funds are stuck in the interim, since messages just wait), a **timeout** is itself the *user's recovery mechanism* when a cross-chain call never got a response in time. For example, `IntentGatewayV2`/`ExtrinsicIntents._cancelFromSource` dispatches a `DispatchGet` request to verify an order was never filled and, if the destination never responds, the user's only way to unlock the escrowed input tokens is a `GetRequestTimeout` processed through `handleGetRequestTimeouts` → `host.dispatchTimeOut` → the app's `onGetTimeout` refund logic: [6](#0-5) 

If the admin freezes incoming messages (`FrozenStatus.Incoming` or `FrozenStatus.All`) for any period spanning the request's timeout window, the `notFrozen` check on `handleGetRequestTimeouts`/`handlePostRequestTimeouts` reverts with `HostFrozen()`, so the timeout cannot be dispatched during that window. Escrowed funds tied to that specific commitment remain locked until the freeze is lifted — and if the underlying request/state proof becomes unusable (challenge period boundaries, pruned state commitments, or the freeze persisting past the point where a fresh proof at a valid height can no longer be obtained), the recovery path can be permanently blocked, not merely delayed.

This is directly analogous to the reported Flatcoin issue: `executeClose()` guarded by `whenNotPaused` prevented a trader from closing (exiting) their position during a pause, causing potential fund loss; here `notFrozen` guards the exact mechanism (`handleGetRequestTimeouts`/`handlePostRequestTimeouts`) that lets a user *exit* a stuck cross-chain escrow via timeout.

### Impact Explanation
Any unprivileged user with an outstanding cross-chain request whose recovery depends on a timeout (intent order cancellation via `DispatchGet`, or any `IPostDispatcher`/`IDispatcher` consumer relying on `PostRequestTimeout`) can have their escrowed funds frozen for the duration of an admin-initiated `Incoming`/`All` freeze, and potentially indefinitely if the freeze outlives the provable timeout window (state commitment pruning / challenge-period constraints on proof height). This is a fund-freezing issue reachable by a normal user transaction (submitting a timeout with a valid proof), not requiring any malicious admin — the freeze itself is a legitimate emergency-pause feature whose side effect is blocking the only escape hatch.

### Likelihood Explanation
Likelihood is Medium: it requires the host to be frozen (`Incoming`/`All`) coincident with a pending timeout for a user's request. This is an intended emergency operational state, not attacker-triggered, but it is a normal, foreseeable condition (e.g., pausing after detecting an exploit elsewhere) that directly harms unrelated users trying to exit/cancel legitimate orders during the same window — exactly the scenario the referenced report calls out for `executeClose()`.

### Recommendation
Exempt timeout handlers (`handlePostRequestTimeouts`, `handleGetRequestTimeouts`) from the `notFrozen` incoming-freeze check, or introduce a narrower freeze status that blocks new incoming message *delivery* (which can carry malicious/forged payloads) while still allowing *timeout* processing (which only permits withdrawal of a user's own already-escrowed funds and cannot be exploited to forge new state). At minimum, ensure the freeze duration and proof-height/challenge-period accounting guarantee that a valid timeout proof remains obtainable after any freeze is lifted, so recovery is delayed rather than permanently lost.

### Proof of Concept
1. User calls `IntentGatewayV2.cancelOrder` (source-chain cross-chain path), which dispatches a `DispatchGet` request via `IDispatcher(hostAddr).dispatch(...)` — see `_cancelFromSource` in `evm/src/apps/intentsv2/ExtrinsicIntents.sol` lines 240–275.
2. The destination never responds (network delay, relayer inactivity, or destination congestion) so the GET request will time out.
3. Before the timeout window elapses, the host admin sets `FrozenStatus.Incoming` (or `All`) on `EvmHost` for an operational/emergency reason unrelated to this user.
4. A relayer/user attempts to call `HandlerV2.handleGetRequestTimeouts(host, message)` to release the user's escrow — the call reverts with `HostFrozen()` due to the `notFrozen(host)` modifier (`evm/src/core/HandlerV2.sol` lines 108–112, 293).
5. The user's escrowed input tokens remain locked for the duration of the freeze; if the freeze persists beyond the point where a fresh valid-height proof can still be produced (e.g., past challenge-period/state-pruning constraints), the funds cannot be recovered at all.

    function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
            dispatchWithFeeToken(request);
        }
    }
