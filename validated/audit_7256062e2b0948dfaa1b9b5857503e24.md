## Title
Missing contract-existence check in `EvmHost.dispatchIncoming(GetResponse)` / `dispatchTimeOut` lets a call to a destroyed or non-existent app forge a successful delivery, permanently locking escrowed funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatchIncoming(PostRequest)` explicitly guards against the well-known EVM quirk that low-level `call` returns `success = true` when the target account has no code, by checking `extcodesize` before invoking the destination's callback. However, the three sibling dispatch paths — `dispatchIncoming(GetResponse)`, `dispatchTimeOut(GetRequestTimeout)`, and `dispatchTimeOut(PostRequestTimeout)` — omit this check entirely, even though they perform the exact same pattern of an unchecked low-level `.call(...)` followed by fee transfers and permanent receipt deletion.

### Finding Description
In `EvmHost.sol`, the POST-request delivery path is hardened: [1](#0-0) 

Note the `extcodesize` check at lines 796-803 before the `.call` at line 809. This exists specifically because, per Solidity's own documentation, low-level `call` to a non-existent (or destroyed) account returns `success = true` as part of EVM design, which would otherwise let the host believe a nonexistent app "accepted" the request.

The three sibling functions lack this same guard: [2](#0-1) [3](#0-2) [4](#0-3) 

In each of these, `_bytesToAddress(...)` .call(...)` is invoked directly against the original request's `from` address without any `extcodesize` check. If that address has no code at delivery time (e.g., a destroyed contract, or a proxy/factory pattern where the deployed app was later removed), the call trivially returns `success = true`:
- The response/timeout receipt bookkeeping (`_responseReceipts`, `_requestCommitments`) is committed as permanently handled (lines 826-830, 862, 891) — the code explicitly documents the `!success` branch as the mechanism "so that it can be retried" (lines 835-839, 866-869, 895-899), meaning the success path is the point of no return.
- Protocol fees are paid out (`safeTransfer` to relayer or sender) as if the app's callback genuinely executed (lines 841-845, 872-875, 901-904).
- The corresponding `emit *Handled` events fire, signalling successful delivery to off-chain relayers/indexers.

Yet the app's actual `onGetResponse`/`onGetTimeout`/`onPostRequestTimeout` logic — which is exactly where state-dependent effects such as escrow release happen (see `IntentGatewayV2.onGetResponse` calling `withdraw(...)`) — never runs, because there is no code at the target address to execute it.

### Impact Explanation
Any Hyperbridge app (e.g. `IntentGatewayV2`, `HyperFungibleToken`) that dispatches a GET request or has a pending POST/GET request eligible for timeout is at risk if its deployed address loses its code before the response/timeout is delivered. Once the low-level call falsely "succeeds":
- The response/timeout is irreversibly marked as delivered/handled — the sole retry path (`delete`/re-store within the `!success` branch) is unreachable.
- Funds escrowed by that app pending the callback (e.g. intent escrow withdrawal gated on `onGetResponse`) become permanently unrecoverable, since the protocol believes delivery already completed successfully.
- Relayers or fee payers receive fee payouts for a delivery that never actually executed application logic, misrepresenting the on-chain state of message delivery — a forged delivery result.

This satisfies "permanent freezing of funds" and "forged message delivery" for a path reachable purely by relayed proofs submitted through the standard handler → `EvmHost` dispatch flow, with no privileged access required.

### Likelihood Explanation
Exploitation requires the `from`/target app account to have no code at the moment the response/timeout is relayed. While mainnet Ethereum post-Dencun (EIP-6780) restricts full code removal via `SELFDESTRUCT` to same-transaction creation, Hyperbridge is explicitly multi-chain (its `EvmHost` targets many different EVM-compatible chains, some of which may not enforce EIP-6780 semantics, or may use CREATE2 proxy patterns where an address is disassociated from code between dispatch and delivery). Given the asynchronous nature of the ISMP request/response lifecycle (requests can be outstanding for the full timeout window), the window in which an app's code could become unavailable is non-trivial on any chain lacking Dencun-style protections. Regardless of exact exploitation frequency, the code path is inconsistent with the already-implemented fix for the POST-request case, confirming the developers recognize this exact hazard class but failed to apply it uniformly.

### Recommendation
Add the same `extcodesize` existence check used in `dispatchIncoming(PostRequest)` (lines 795-803) to `dispatchIncoming(GetResponse)`, `dispatchTimeOut(GetRequestTimeout)`, and `dispatchTimeOut(PostRequestTimeout)` before performing the low-level `.call(...)`, treating a zero-code destination as delivery failure (preserving retryability) rather than success.

### Proof of Concept
1. App contract `A` calls `IDispatcher(host).dispatch(DispatchGet {...})`, becoming `request.from = A`, with a non-zero `fee`.
2. Before the GET response (or timeout) is relayed, `A`'s code becomes unavailable at its address (via `SELFDESTRUCT` on a chain that fully removes code, or via a proxy/factory redeploy pattern where the address temporarily has no code).
3. A relayer submits a valid consensus-proven `GetResponse` (or non-membership timeout proof) for the outstanding request; the handler invokes `EvmHost.dispatchIncoming(GetResponse, relayer)` (or `dispatchTimeOut`).
4. `_bytesToAddress(response.request.from).call(...)` at line 832 targets `A`, which has no code, so `success = true` is returned per EVM semantics, even though no `onGetResponse` logic executed.
5. `_responseReceipts[commitment]` is retained as set (line 827-830, never deleted since `success` is true), `IERC20(feeToken()).safeTransfer(relayer, fee)` pays out the fee (line 844), and `GetRequestHandled` is emitted (line 846) — all while `A`'s intended state transition (e.g., releasing escrowed intent funds) never occurred and can never be retried.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});

    function dispatchIncoming(GetResponse memory response, address relayer) external restrict(_hostParams.handler) {
        // replay protection
        bytes32 commitment = response.request.hash();
        _responseReceipts[commitment] = ResponseReceipt({
            relayer: relayer,
            responseCommitment: response.hash()
        });

        (bool success,) = _bytesToAddress(response.request.from)
            .call(abi.encodeWithSelector(IApp.onGetResponse.selector, IncomingGetResponse(response, relayer)));

        if (!success) {
            // so that it can be retried
            delete _responseReceipts[commitment];
            return;
        }

        // reward the relayer fee
        uint256 fee = _requestCommitments[commitment].fee;
        if (fee != 0) {
            IERC20(feeToken()).safeTransfer(relayer, fee);
        }
        emit GetRequestHandled({commitment: commitment, relayer: relayer});
    }
