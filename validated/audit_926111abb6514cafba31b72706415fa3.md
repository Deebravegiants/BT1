### Title
Webhook HMAC signature does not bind the `shop-domain` header, allowing cross-tenant shop spoofing via header substitution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes and verifies the webhook HMAC over the raw body only, while the `shop` value used by the host application for tenant identification is read from an HTTP header that is never covered by that signature. Any actor who possesses one genuinely-signed `(raw_body, hmac)` pair for the app (e.g., the operator of any shop that has installed the app) can resubmit that exact body/HMAC pair to the app's public webhook endpoint with a forged `x-shopify-shop-domain` (or `shopify-shop-domain`) header pointing at a different, victim shop. `ShopifyAPI::Utils::HmacValidator.validate` will report the signature as valid (because only the body bytes are checked), and `ShopifyAPI::Webhooks::Registry.process` will then hand the handler a `WebhookMetadata` object whose `shop` is the attacker-chosen value.

### Finding Description
The identity binding that should hold is:
`shop_value_trusted_by_handler == shop_that_actually_produced_and_signed_the_payload`

In this gem it instead holds only:
`hmac_valid == HMAC(api_secret_key, raw_body) == received_hmac`

with `shop` sourced independently and unauthenticated: [1](#0-0) 

`to_signable_string` returns only `@raw_body`: [2](#0-1) 

`shop` is parsed straight from a header with no cryptographic tie to the body or signature: [3](#0-2) 

The validator only ever hashes `to_signable_string` (the raw body), never any headers: [4](#0-3) 

`Registry.process` trusts this unauthenticated `shop` value and forwards it straight to the app's handler after only checking the body HMAC: [5](#0-4) 

Because the same `api_secret_key` is shared across every shop that installs the app, any tenant that legitimately receives one real webhook (with a valid `raw_body`/`hmac-sha256` pair) can capture that pair and replay it to the app's webhook endpoint while substituting the `shop-domain` header for any other installed shop. The HMAC check still passes since it only re-hashes the (unmodified) body, and the handler receives `data.shop` equal to the attacker-chosen victim shop.

### Impact Explanation
This breaks tenant isolation: the host application, following the gem's documented usage exactly (`ShopifyAPI::Webhooks::Registry.process`), will process/attribute the replayed webhook data (order, customer, GDPR, uninstall, etc.) as if it belongs to the victim shop, since `data.shop` is the only tenant identifier exposed by `WebhookMetadata` and it is unauthenticated. This is cross-tenant access/data confusion (an unprivileged app-installer forging events for a shop they don't control), which maps to the "Critical – cross-tenant access" impact tier.

### Likelihood Explanation
The prerequisite is modest: the attacker only needs to be one merchant who has installed the app (a normal, unprivileged tenant) so they can obtain at least one legitimately HMAC-signed webhook body from Shopify for their own shop. No knowledge of `api_secret_key` is required — they simply intercept/copy the raw request their own store already received and resend it to the public webhook endpoint with a different `shop-domain` header. The gem's `Utils::HmacValidator` and `Webhooks::Registry.process` provide no defense against this because neither the shop header nor topic/webhook-id headers are part of the signed payload.

### Recommendation
Bind the tenant identifier to the verified payload instead of trusting a header value independently:
- Include `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) in the signable string used for HMAC verification, or
- Cross-check `request.shop` against an out-of-band trusted source (e.g., require the caller to supply the expected shop and compare it, or validate the shop domain format/allow-list per app installation) before constructing `WebhookMetadata`.
Document that `data.shop` is not currently cryptographically bound to the signed body so integrators are aware of the current guarantee.

### Proof of Concept
1. Shop A installs the app and configures the webhook endpoint. Shopify sends a genuine webhook to the endpoint with body `B` and header `x-shopify-hmac-sha256: H = HMAC(api_secret_key, B)` and `x-shopify-shop-domain: shop-a.myshopify.com`.
2. Attacker (Shop A's owner, or anyone who can capture that one legitimate request) resends an HTTP request to the same endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: shop-b.myshopify.com` (the victim).
3. The host app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers))`.
4. `Utils::HmacValidator.validate` recomputes `HMAC(api_secret_key, B)`, which still equals `H`, so validation succeeds: [6](#0-5) 
5. The handler receives `WebhookMetadata.new(... shop: "shop-b.myshopify.com" ...)` even though the payload never actually originated from or was authorized for Shop B.
