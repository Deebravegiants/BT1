This confirms the vulnerable pattern. The gem's official documentation explicitly instructs host apps to trust `data.shop` as the tenant identifier (`perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` in `docs/usage/webhooks.md`), while `ShopifyAPI::Webhooks::Request#shop` reads directly from an unauthenticated header, and `HmacValidator` only signs the raw body.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` extracts the `shop` (tenant identifier) from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, but the HMAC signature that `ShopifyAPI::Utils::HmacValidator` checks only covers the raw request body. This breaks the identity binding `authenticated_sender == shop_header`: the body is cryptographically bound to the app's `client_secret`, but the shop attribution is not, so any user who can obtain one valid (body, HMAC) pair can relabel it as belonging to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over that signable string: [2](#0-1) 

The `shop` accessor, however, is read straight from an HTTP header with no cross-check against the HMAC-covered content: [3](#0-2) 

`Registry.process` validates only the HMAC, then forwards `request.shop` unmodified to the app's handler as the tenant identifier: [4](#0-3) 

Because the `client_secret`/HMAC key is shared by the app across every shop that installs it, any merchant who installs the app on their own store (an "unprivileged internet user" with respect to other tenants) can capture a genuine `(raw_body, hmac)` pair generated from real events on their own shop, then replay it to the app's webhook endpoint with the `x-shopify-shop-domain` header rewritten to a victim shop's domain. `HmacValidator.validate` still returns `true` because the body and HMAC are unchanged and valid, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the (attacker-controlled) body belongs to the victim shop: [5](#0-4) 

The gem's own documentation confirms the intended (and now broken) trust model — host apps are told to key their persistence/queuing directly off `data.shop`: [6](#0-5) 

### Impact Explanation
This is a cross-tenant identity-binding break: `shop_claimed_in_header == shop_that_actually_produced_the_signed_body` is never enforced. A malicious merchant installing the app can forge webhook deliveries "from" any other shop that also uses the app, causing the host application to process attacker-influenced event data (order/customer/product payloads whose content the attacker can partially control by acting on their own store) under a victim shop's tenant context. Depending on how the host app uses `data.shop` (record attribution, job routing, per-shop data writes, triggering per-tenant business logic), this can lead to cross-tenant data corruption or spoofed business events, matching the "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any multi-tenant app: no secrets, sessions, or elevated privileges are required — only the ability to install the app on one's own store (or use a development store) and capture one legitimate webhook delivery, then replay it with a modified header, which any external actor can do against a publicly reachable webhook endpoint.

### Recommendation
Bind the shop identity into the value that is verified. Either include the shop domain (and other routing headers) in the HMAC-signable string, cross-validate `shop` against a shop identifier embedded in the parsed body when available, or require the host app to independently authenticate the shop (e.g., by checking that the shop has an active, previously-established session/webhook registration) before trusting `data.shop` for tenant-sensitive operations. At minimum, document prominently that `data.shop` is not authenticated by the HMAC and must not be used as a sole tenant key.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and lets it register webhooks.
2. Shopify sends a legitimate webhook to the app: body `B`, header `x-shopify-hmac-sha256: H` (valid for `B` under the shared `client_secret`), `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker resends the same `B`/`H` to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate` succeeds (HMAC only covers `B`), so `ShopifyAPI::Webhooks::Registry.process` invokes the handler with `WebhookMetadata(shop: "victim.myshopify.com", body: B, ...)`, spoofing the tenant attribution as demonstrated by `lib/shopify_api/webhooks/registry.rb:188-199`.
