This is a direct analog to the reported bug class: a value that is verified/signed (HMAC over `to_signable_string`, i.e., `@raw_body` only) is not the same value that is trusted for identity/routing decisions (the `shop`, `topic`, and `webhook_id` headers, and the parsed body via `JSON.parse`).

### Title
Webhook `topic`/`shop`/`webhook_id` and parsed body are trusted without being covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over `@raw_body` only [1](#0-0) , while `topic`, `shop`, `webhook_id`, and `api_version` are all read directly from unauthenticated HTTP headers [2](#0-1) . `ShopifyAPI::Webhooks::Registry.process` validates only the HMAC of the raw body, then uses the header-derived `topic` to select a handler and passes the header-derived `shop` straight into the handler's `WebhookMetadata` as an authenticated tenant identifier [3](#0-2) .

### Finding Description
The identity binding that should hold is:
`bytes_verified_by_HMAC (raw_body) == bytes_relied_upon_for_authorization_decisions (topic, shop, webhook_id, parsed_body)`

In this gem, only `raw_body` is covered by `to_signable_string`/HMAC validation: [4](#0-3) 

But `topic`, `shop`, and `webhook_id` are pulled from separate, unsigned headers via `shopify_header`: [5](#0-4) 

`Registry.process` uses `Utils::HmacValidator.validate(request)` — which only checks `raw_body` against the HMAC secret — and then unconditionally trusts `request.topic` to route to a handler and `request.shop` to identify the tenant for that handler: [3](#0-2) 

Because the header value and the signed payload are never cross-checked (e.g., the HMAC is not computed over `shop-domain` + `topic` + `body`, and there's no explicit assertion that the body's shop/topic match the headers), the header-controlled `shop` and `topic` are an "identity" that the app trusts without it being covered by the same signature that authenticates the payload.

This mirrors the reported bug class precisely: "bytes verified versus bytes parsed" — an unprivileged network attacker who can reach the app's webhook endpoint (this is a public HTTP endpoint by design, no credential needed to send a request to it) can send an HTTP request with:
- A valid raw body and valid HMAC for that exact body (if the attacker somehow obtains a genuine webhook body+signature pair, e.g., by replaying a captured webhook, or if the `client_secret`-derived signature can otherwise be satisfied for a body they fully control — note this requires either replay of a legitimate previously-observed webhook or knowledge of the signing secret),
- but arbitrary `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, and `X-Shopify-Webhook-Id` headers that were never part of the signed material.

The most concretely reachable exploitation path (no secret needed) is **webhook replay across tenants/topics**: because the HMAC only binds the body, and the body alone (JSON payload) typically does not repeat the shop domain or topic, a webhook captured for shop A / topic `orders/create` can be replayed with modified `shop-domain` and/or `topic` headers, and it will pass HMAC validation (since the body is unchanged) yet be attributed by the host application to a different shop or dispatched to a different handler than the one Shopify actually intended.

### Impact Explanation
This crosses the "cross-tenant access" bar in the rules: an attacker who intercepts/replays one webhook delivery (e.g., from their own shop, which they legitimately receive, or one leaked in logs) can cause the gem to report a `WebhookMetadata` with an attacker-chosen `shop` (a different merchant's domain) and/or `topic` while still passing HMAC validation, since neither field is bound by the signature. Host applications built on top of this gem (as documented in `docs/usage/webhooks.md` and `BREAKING_CHANGES_FOR_V15.md`) are explicitly told to trust `data.shop` and `data.topic` as authenticated fields coming out of `Registry.process` [6](#0-5) . This can lead to data being written to/read for the wrong shop's tenant record — a cross-tenant confusion vulnerability.

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP endpoint (by design, Shopify calls back to a public URL), so any unprivileged internet user can send requests to it. Likelihood of the full cross-tenant impact depends on the attacker being able to obtain at least one valid (body, HMAC) pair for their own shop (a legitimate merchant using the app can trivially do this by triggering an event in their own store and capturing the request) and then replaying it with modified shop/topic headers. This makes it a very achievable "unprivileged user attacking their own app's tenant isolation" scenario, without needing the `client_secret`.

### Recommendation
Bind the security-critical routing/tenant fields into the signed material, or otherwise cryptographically/contextually verify them:
- Compute the HMAC over a canonical string that includes `shop-domain`, `topic`, and `webhook-id` in addition to `raw_body`, matching what the gem's callers expect to trust, OR
- Cross-check `request.shop` against the session/shop the webhook was registered for (i.e., look up an active session by `shop` and reject if a registration for `topic`/`shop` pair does not exist), OR
- At minimum, document/enforce webhook_id-based idempotency AND shop/topic consistency checks in `Registry.process`, rejecting reused `webhook_id`s and mismatched shop/topic combinations to close the replay path.

### Proof of Concept
1. As a merchant using the target app, trigger a webhook (e.g., `orders/create`) and capture the raw POST body and the `X-Shopify-Hmac-Sha256` header sent to the app's public webhook endpoint.
2. Replay this exact request to the same endpoint, but modify `X-Shopify-Shop-Domain` to a different shop's domain (or `X-Shopify-Topic` to a different registered topic) and change/reuse `X-Shopify-Webhook-Id`.
3. `ShopifyAPI::Webhooks::Registry.process` computes the HMAC solely from `raw_body` [1](#0-0)  — validation passes because the body is unchanged.
4. `Registry.process` looks up the handler by the attacker-supplied `topic` and constructs `WebhookMetadata` using the attacker-supplied `shop`, both taken straight from headers [3](#0-2) , and the host application's handler now processes data believing it came from a different tenant/topic than Shopify actually sent.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
