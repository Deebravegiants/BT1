### Title
Batch withdrawals matched by `assetId` instead of index causes status/hash cross-reporting for same-token withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`)

### Summary
When an intent contains multiple withdrawals of the same underlying token (via POA Bridge), `describeWithdrawal()`/`waitForWithdrawalCompletion()` resolve which withdrawal record to report by matching on `assetId` (`near_token_id`) only, ignoring the `index`/uniqueness of the specific withdrawal being polled. If two or more withdrawals in the same NEAR transaction share the same `assetId`, the caller polling for withdrawal A can receive the status and `transfer_tx_hash` that actually belong to withdrawal B.

### Finding Description
`PoaBridge.describeWithdrawal()` looks up the matching withdrawal by calling `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`, which does `withdrawals.find((w) => \`nep141:${w.data.near_token_id}\` === assetId)` — it never uses `args.index`, even though `WithdrawalIdentifier.index` exists specifically to disambiguate multiple withdrawals produced by the same NEAR transaction. [1](#0-0) [2](#0-1) 

The equivalent internal-utils helper `waitForWithdrawalCompletion()` has the identical limitation, matching purely on `WithdrawalCriteria.assetId` with no positional/amount disambiguation: [3](#0-2) [4](#0-3) 

The `WithdrawalIdentifier` type explicitly documents `index` as "Per-bridge withdrawal sequence number," confirming that the SDK's design intends per-withdrawal disambiguation within a single tx, which the POA matching logic fails to honor: [5](#0-4) 

Both code paths carry comments explicitly acknowledging the flaw ("Currently only matches by assetId... multiple withdrawals of the same token in a single transaction are not supported"), and there is an existing test proving the resulting behavior — `findMatchingWithdrawal` returns whichever array element happens to match the `assetId`, regardless of which specific withdrawal index the caller is polling for: [6](#0-5) 

The equality that breaks: "status/txHash reported for withdrawal N" should equal "the on-chain outcome of withdrawal N specifically," but instead it equals "the on-chain outcome of *some* withdrawal sharing the same assetId in that transaction." An integrator using `sdk.createWithdrawalCompletionPromises()` (which builds one `WithdrawalIdentifier` per withdrawal in a batch, differentiated by `index`) to track two same-token withdrawals to different destinations/amounts in one NEAR transaction would get cross-wired completion signals — e.g., withdrawal #0 (going to destination X) could be reported "completed" with `transfer_tx_hash` that actually belongs to withdrawal #1 (going to destination Y).

### Impact Explanation
This falls under the accepted High-impact category: "a status or hash misreport making an integrator credit or refund twice." An integrator polling per-withdrawal status via `describeWithdrawal`/`waitForWithdrawalCompletion` for a batch containing duplicate-asset withdrawals could mark the wrong withdrawal as completed and credit/release funds against the wrong destination-tx-hash pairing, or prematurely consider a withdrawal settled based on another withdrawal's outcome.

### Likelihood Explanation
Medium — it requires a batch of withdrawals within a single NEAR transaction that includes two or more withdrawals of the exact same underlying `assetId` (same token) via the POA route, which is a legitimate, unprivileged user/integrator flow (no malicious actor needed; the batch withdrawal API supports arbitrary combinations of withdrawal params, and nothing prevents specifying the same asset twice).

### Recommendation
Extend the POA Bridge's withdrawal status API usage (or client-side reconciliation) to disambiguate withdrawals sharing the same `assetId` within one transaction using `index`/amount ordering, as already anticipated in the code's own comment ("matching could be done by sorting both API results and withdrawal params by amount"). Until the POA API supports index-based matching, `describeWithdrawal`/`waitForWithdrawalCompletion` should reject or clearly flag ambiguous cases (multiple same-asset withdrawals in the same tx) rather than silently returning a match that may belong to a different withdrawal.

### Proof of Concept
1. Build a batch withdrawal intent with two POA-bridge withdrawals of the same `assetId` (e.g., `nep141:btc.omft.near`) but different `destinationAddress`/`amount`, at indices 0 and 1 in the same NEAR tx.
2. Call `sdk.createWithdrawalCompletionPromises()` (or directly `PoaBridge.describeWithdrawal`) for index 0.
3. The POA bridge API returns both withdrawal records for that tx hash (unsorted).
4. `findMatchingWithdrawal` (`poa-bridge.ts:418-427`) matches by `assetId` alone and returns whichever array entry satisfies `nep141:${near_token_id} === assetId` — this can be the entry corresponding to withdrawal index 1 instead of index 0, as directly demonstrated by the existing unit test `"matches withdrawal by assetId, not by index"` at `poa-bridge.test.ts:1054-1111`, which shows a `btc-tx-hash` result returned for a query whose only distinguishing criterion is `assetId`, with no verification against `index`.

```typescript
type WithdrawalStatusResponse = Awaited<
	ReturnType<typeof poaBridge.httpClient.getWithdrawalStatus>
>;

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
```
