### Title
Webhook HMAC signature does not bind `shop` (or `topic`), enabling cross-tenant shop-identity forgery via header substitution - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then trusts the `shop` (and `topic`) values taken from unauthenticated HTTP headers when dispatching to the app's handler. Because the shop identity is not part of the signed material, any party who possesses one valid `(body, hmac)` pair — trivially obtainable by any merchant/app-installer who can view webhooks delivered to their own store — can resend that exact body with a different `shopify-shop-domain` header and the signature will still verify, letting them make the app process/attribute the payload to an arbitrary shop.

### Finding Description
The identity binding that must hold is:
`shop_value_verified_by_hmac == shop_value_the_handler_acts_on`

In this gem, that equality is broken:

- `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it with `OpenSSL.secure_compare`: [1](#0-0) 

- For webhook requests, `to_signable_string` is defined to be **only the raw body**, excluding the `shop`, `topic`, `webhook_id`, and `api_version` headers entirely: [2](#0-1) 

- `Registry.process` validates the HMAC and then immediately trusts `request.topic` and `request.shop` — both sourced from headers never covered by the HMAC — to select the handler and construct `WebhookMetadata` passed to app code: [3](#0-2) 

- `request.shop` and `request.topic` are read straight from the `shopify-shop-domain` / `shopify-topic` headers with no cross-check against the signed body: [4](#0-3) 

Because `OpenSSL::HMAC.hexdigest(secret, raw_body)` depends only on `raw_body`, the same valid `(raw_body, hmac)` pair remains valid under `HmacValidator.validate` for **any** combination of `shop`/`topic` headers sent alongside it. This is the same root-cause pattern as the referenced report: a value the application acts on (there, `useUnderlying`; here, `shop`/`topic`) is decoupled from the value that was actually verified (there, the true underlying/asset relationship; here, the signed body only).

### Impact Explanation
This is a cross-tenant identity-binding break (Critical per the rubric): an unprivileged actor who legitimately receives webhooks for their own store (any app installer/merchant can do this — no secret, token, or TLS interception needed) can capture one `(body, hmac)` pair from their own shop's webhook traffic and replay it to the app's public webhook endpoint with a forged `shopify-shop-domain` header naming a different shop, and/or a forged `shopify-topic` header selecting a different handler. `Registry.process` will accept the HMAC (it only checks the body) and hand the attacker-controlled `shop`/`topic` values to the app's business logic via `WebhookMetadata`, causing the app to store or act on data under the wrong tenant's identity — a direct cross-tenant data-integrity/isolation violation for any application relying on this gem's webhook processing to key data by `shop`.

### Likelihood Explanation
High. No credentials, `api_secret_key`, access token, or TLS interception is required — only a genuine webhook delivery to the attacker's own (legitimately installed) shop, which every app installer receives by design. Constructing the replayed request is a simple HTTP call with substituted headers and the exact same body/HMAC.

### Recommendation
Include `shop`, `topic`, and `webhook_id`/`api_version` in the signed material verified against the request, or independently bind them (e.g., verify `shop` against the session/shop the webhook subscription was registered for) rather than trusting header values whose authenticity was never checked by the HMAC comparison in `Registry.process`.

### Proof of Concept
1. As a normal merchant, install the app and capture one legitimate webhook POST to the app's callback endpoint, noting the raw body `B` and its `x-shopify-hmac-sha256` value `H` (valid because `H = HMAC(secret, B)`).
2. Replay the exact same body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com` and (optionally) a different `x-shopify-topic`.
3. `HmacValidator.validate` (lib/shopify_api/utils/hmac_validator.rb) recomputes `HMAC(secret, B)`, matches `H`, and returns `true` since it never inspects the shop/topic headers.
4. `Registry.process` (lib/shopify_api/webhooks/registry.rb, lines 188-200) proceeds to invoke the handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, causing the app to process attacker-supplied data as if it originated from `victim-shop.myshopify.com`.
