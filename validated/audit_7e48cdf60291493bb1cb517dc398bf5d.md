### Title
Webhook shop-domain identity spoofing due to HMAC covering only the raw body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's HMAC signature and then trusts the `shop-domain` header value as the tenant identity passed to the app's handler. The HMAC signature, however, is computed only over the raw request body — the `shop-domain` header is never part of the signed material. Because the webhook HMAC secret is the app's single shared `api_secret_key` (identical for every shop that installs the app), any shop that legitimately installs the app can capture one of its own validly-signed webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to point at a victim shop, producing a request that still passes HMAC validation but reports an attacker-chosen tenant identity to the handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from the unauthenticated `shopify-shop-domain` (or `x-shopify-shop-domain`) header: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string` — i.e., the body only — and compares it to the `hmac` value: [3](#0-2) 

`Registry.process` checks this HMAC and, if it passes, unconditionally forwards `request.shop` (the unauthenticated header) to the registered handler as the tenant identity: [4](#0-3) 

The binding that is broken is:
`shop bound by HMAC (∅, since the body carries no shop identity and the header is unsigned) ≠ shop attributed to the request (WebhookMetadata#shop, taken from the unsigned header)`.

Because the same `api_secret_key` is used to sign webhook bodies for *every* shop that has installed the app, an attacker who legitimately installs the app on their own store obtains valid `(body, hmac)` pairs signed with the app's shared secret. Nothing in the signed material ties that pair to the attacker's own shop domain. The attacker can then send an HTTP request directly to the app's webhook endpoint, keeping the legitimately-signed `body`/`hmac-sha256` pair but substituting the `shop-domain` header with a victim shop's domain (or an arbitrary mandatory-topic shop, e.g. for `shop/redact` or `customers/redact`). `HmacValidator.validate` still returns `true` because it never inspected the header, and `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`.

### Impact Explanation
Any host application that uses `data.shop` from the webhook handler to select which merchant's session/access token to act on, which tenant's data to update, or which tenant to run mandatory compliance actions (`shop/redact`, `customers/redact`, `customers/data_request`) for, can be made to act on behalf of a shop the attacker does not control. This is a cross-tenant identity confusion vulnerability reachable by any unprivileged party who can install the app on their own store (a normal, low-privilege action) — it requires no access token, no leaked credential, and no access to the app's `client_secret`.

### Likelihood Explanation
The attacker only needs: (1) to install the target app on a store they control (a standard, self-service action any merchant can perform), (2) to trigger any webhook topic the app has registered for, capturing a legitimately-signed `(body, hmac)` pair, and (3) to send a forged HTTP request to the app's public webhook endpoint with a modified `shop-domain` header. All of this is achievable by an unprivileged internet user with no special access, making this straightforward to exploit against apps that trust `WebhookMetadata#shop`.

### Recommendation
Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the HMAC-signed material, or otherwise cryptographically bind the shop identity to the webhook payload before trusting it, so that the header cannot be altered independently of the signature. At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier by host applications, or cross-check it against a shop the app has an active session/webhook registration for.

### Proof of Concept
1. As an attacker, install the target Shopify app on `attacker-shop.myshopify.com` (a normal, unprivileged action).
2. Trigger any webhook topic the app subscribes to (e.g., `orders/create`) on `attacker-shop.myshopify.com`; capture the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sends — this HMAC is valid because it's signed with the app's shared `api_secret_key`.
3. Send a new HTTP POST directly to the app's webhook endpoint using the captured `body` and `X-Shopify-Hmac-Sha256` value unchanged, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` and any desired `X-Shopify-Topic` (e.g. `customers/redact`).
4. `Utils::HmacValidator.validate` returns `true` (per [3](#0-2) , it only checks the body), and `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` (per [4](#0-3) ), even though the payload actually originated from the attacker's own store.
