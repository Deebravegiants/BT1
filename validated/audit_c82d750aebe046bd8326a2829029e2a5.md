## Title
Webhook Shop-Domain Spoofing via HMAC Bypass (Cross-Tenant Webhook Injection) - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body. The `shop` value that identifies which tenant the webhook belongs to is taken from the `X-Shopify-Shop-Domain` HTTP header, which is never included in the signed bytes. Because the webhook signing secret (`api_secret_key`/`client_secret`) is shared across every shop that has installed the app, any merchant who has legitimately installed the app can capture one authentic `(body, hmac)` pair from their own store's webhook deliveries and replay it to the app's webhook endpoint with the `X-Shopify-Shop-Domain` header rewritten to a victim shop. The request passes HMAC validation and is dispatched to the app's handler tagged with the victim's shop, causing cross-tenant data injection.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature only over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns just the raw HTTP body: [2](#0-1) 

The `shop` accessor, however, is read directly and unauthenticatedly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic binding to the HMAC at all: [3](#0-2) 

`Registry.process` only checks the HMAC of the body before dispatching, and then constructs the metadata handed to the app's handler using the unverified `request.shop`: [4](#0-3) 

The binding that should hold is: `shop_header == shop_that_the_HMAC_authenticates`. In reality, the HMAC authenticates only the body bytes for a secret that is identical across all tenants of the app, so `shop_header` can be swapped freely by anyone who already possesses one valid `(body, hmac)` pair for any shop (including their own). This breaks the equality `authenticated_tenant == metadata.shop` delivered to the handler.

### Impact Explanation
This is a cross-tenant access vulnerability (Critical category): an unprivileged internet user who merely installs the target app on their own store (a normal, unprivileged action) can capture one valid webhook body+HMAC pair from their own shop's traffic, then forge arbitrary requests to the app's public webhook endpoint claiming to originate from any other shop by overwriting only the `X-Shopify-Shop-Domain` header, since it is not covered by the signature. Downstream app logic that trusts `WebhookMetadata#shop` (e.g., to select which merchant's data to update, to satisfy GDPR `shop/redact` handling, or to trigger merchant-specific business logic) will act on/attribute data to the wrong tenant using attacker-supplied body content, achieving cross-tenant data corruption/injection without ever needing the victim's or the app's credentials.

### Likelihood Explanation
Likelihood is high for any app builder using this gem's standard `Webhooks::Registry`/`Webhooks::Request` flow as documented: installing the app on any single shop (which any internet user can do for a public app) is enough to obtain a valid signed payload, and replaying it with a modified shop header is a trivial HTTP-level manipulation requiring no cryptographic capability.

### Recommendation
Include the tenant-identifying header (shop domain) in the HMAC-signed material, or independently verify that the `X-Shopify-Shop-Domain` header corresponds to a shop the app actually has an active session/installation for before trusting it in `WebhookMetadata`. At minimum, `Utils::VerifiableQuery`/`Webhooks::Request#to_signable_string` should incorporate the shop header into the signed string so tampering with it invalidates the HMAC, mirroring how `Auth::Oauth::AuthQuery#to_signable_string` binds `shop` into its signed params.

### Proof of Concept
```ruby
# Attacker installs the target app on their own shop "attacker.myshopify.com"
# and captures one legitimate webhook delivery, e.g. orders/create:
captured_body = '{"id":1,"note":"hello"}'
captured_hmac_b64 = "<value of X-Shopify-Hmac-Sha256 header from the captured request>"

# Attacker now replays it to the app's public webhook endpoint,
# only changing the shop-domain header to the victim shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac_b64, # unchanged, still valid because body is unchanged
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate passes (body unchanged),
#    handler.handle receives WebhookMetadata(shop: "victim-shop.myshopify.com", body: captured_body)
#    even though the payload never originated from victim-shop.
``` [5](#0-4)
