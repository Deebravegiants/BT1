### Title
Cross-tenant shop impersonation via webhook `shop-domain`/`topic` headers not covered by HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that are then handed to the app's handler as trusted identity/metadata come exclusively from HTTP headers, which are never included in the signed data (`to_signable_string` returns only `@raw_body`) [2](#0-1) . Because a Shopify app's `api_secret_key` (used to compute the HMAC) is a single, app-wide secret shared across every merchant/tenant that installs the app, a valid `(raw_body, hmac)` pair generated by one tenant's webhook remains a valid pair for that same body regardless of which shop it is replayed against.

### Finding Description
`HmacValidator.validate` calls `verifiable_query.to_signable_string`, and for webhook `Request` objects this only returns the raw body [3](#0-2) [4](#0-3) . The `shop`, `topic`, `webhook_id` and `api_version` accessors read straight from HTTP headers with no cryptographic binding to the body or to each other [5](#0-4) .

`Registry.process` uses `request.topic` to select the handler and passes `request.shop` directly into `WebhookMetadata`, which is delivered to the app's business logic as the tenant identity for the event [6](#0-5) .

Because the HMAC is computed with the single app-wide `api_secret_key` (not a per-shop secret) over the body alone, any unprivileged internet user who can install the target app on their own store (any merchant can install any public/dev app) can:
1. Trigger a legitimate webhook delivery for their own shop and capture the `(raw_body, x-shopify-hmac-sha256)` pair from the request the app receives.
2. Replay that exact `raw_body` and `hmac` to the app's webhook endpoint, but substitute the `x-shopify-shop-domain` header (and optionally `x-shopify-topic`) to name a victim shop.
3. `HmacValidator.validate` still succeeds because it only checks that the body matches the shared secret — it has no way to detect that the `shop-domain` header was swapped, since headers are outside the signed content.

This breaks the identity binding: `shop authenticated (by HMAC-over-body) == shop the handler acts on (from unauthenticated header)`. The equality the gem implicitly assumes — "the shop whose secret validated this event is the shop passed to the handler" — does not hold, because the HMAC never binds to any tenant-specific value.

### Impact Explanation
This allows cross-tenant impersonation of webhook events: an attacker-controlled shop can forge webhook deliveries that the host application believes originated from a victim shop (for topics with attacker-controllable/predictable/empty bodies, e.g. `app/uninstalled` or other topics with generic/empty payloads). Depending on how the host application's webhook handlers use `WebhookMetadata#shop` (e.g., to look up/delete a stored session, revoke access, or update tenant-specific state), this can lead to cross-tenant state corruption or a forced deauthorization/état change of a shop the attacker doesn't control — satisfying "cross-tenant access," a Critical-severity impact category.

### Likelihood Explanation
Exploitation requires only that the attacker can install the app themselves (any unprivileged Shopify merchant can install a public app) and capture the raw body/hmac from a real webhook delivered by Shopify to their own configured endpoint (feasible if the attacker controls or can intercept traffic to their own registered webhook endpoint, or if body content is deterministic/empty for a given topic). No access to the app's `api_secret_key`, access tokens, or victim credentials is required, matching the "unprivileged internet user" threat model. The main constraint is finding a webhook topic whose body is empty or attacker-predictable so the captured `(body, hmac)` pair is reusable verbatim; this is realistic for several Shopify webhook topics.

### Recommendation
Bind the tenant/shop and topic identity into the signed material, or otherwise cryptographically verify them:
- If Shopify's webhook signature does not cover headers (as documented), do not treat header-derived `shop`, `topic`, `webhook_id` as trusted identity without additional verification.
- Where possible, cross-check the `shop` header against an expected/registered shop for the delivery (e.g., verify the shop exists in the app's known-installed-shops list before dispatching) rather than trusting it implicitly.
- Consider including the shop domain in what is hashed/checked, or require handlers to independently verify shop context before performing sensitive/tenant-scoped actions, rather than relying solely on `WebhookMetadata#shop`.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`.
2. Configure/observe a webhook delivery for a topic with an empty or fixed body, e.g. raw body `{}`, and capture the resulting `x-shopify-hmac-sha256` header value sent by Shopify (computed with the app's shared `api_secret_key` over `{}`).
3. Send a forged HTTP request to the app's webhook endpoint with:
   - Body: `{}`
   - `x-shopify-hmac-sha256`: the captured valid HMAC
   - `x-shopify-shop-domain`: `victim.myshopify.com`
   - `x-shopify-topic`: any registered topic
4. `ShopifyAPI::Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) validates the HMAC successfully (it only checks the body) and dispatches to the handler with `shop: "victim.myshopify.com"`, even though the event never came from Shopify on behalf of that shop.
