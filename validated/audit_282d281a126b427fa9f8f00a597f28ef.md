### Title
Stale Operator Authorization Reused for up to 23 Hours Without Re-validation, Enabling Misattributed Signups - ([File: src/plans/mod.rs])

### Summary
The bond-slippage bug class in the referenced Dopex report is a case of a value validated at one point in time (the discount) being trusted and used later, after the underlying state it depended on may have already drifted. `orb-core` has the same root-cause pattern in its operator-QR authorization flow: an operator's validity/location, once confirmed by the backend at scan time, is cached in `OperatorData` and reused for every subsequent signup for up to `operator_qr_expiration_time` (23 hours by default) without ever re-confirming with the backend that the operator is still authorized.

### Finding Description
When an operator QR code is scanned, `verify_operator_qr_code` performs a one-time backend authorization check and returns `location_data`, which is stored together with a `timestamp: Instant::now()` inside `OperatorData`: [1](#0-0) 

That cached `OperatorData` is then reused across the master loop. `scan_initial_qr_codes` only re-scans/re-validates the operator when the cached timestamp has *elapsed past* `operator_qr_expiration_time`; otherwise it silently keeps the previously-validated data: [2](#0-1) 

Likewise, `scan_remaining_qr_codes` (called on every single signup attempt via `do_signup`) takes the same short-circuit path — as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, it reuses the operator authorization/location data as-is and jumps straight to scanning the user QR code, completely skipping any call to `verify_operator_qr_code`: [3](#0-2) 

The only branch that re-validates the operator against the backend is the fallback `_` arm, which is skipped whenever the cached data is still "fresh" by elapsed-time only: [4](#0-3) 

The expiration window itself defaults to 23 hours: [5](#0-4) 

This cached `location_data` and operator identity subsequently feed directly into the user QR validation request (`user_status::request`), which can use `operator_data.location_data.session_coordinates` or `operator_data.qr_code.user_id` to authorize the *user's* session against the backend: [6](#0-5) 

and into the final signup submission, where `operator_qr_code.user_id` is sent as the `distributorId` for every enrolled user during that whole window: [7](#0-6) 

Exactly like the Dopex bond-cost calculation, the state that was true "at validation time" (operator authorized, at this location) is not re-checked "at commit time" (every subsequent signup within the cache window), even though the backend's view of that operator (revoked, deactivated, relocated) can legitimately change during that window.

### Impact Explanation
Because the authorization/location check is not repeated per-signup, any number of unrelated users can be signed up and attributed to the same operator identity/location for up to 23 hours after a single backend check, even if that operator's authorization is revoked or the operator physically leaves in the meantime. This causes misattributed signups (wrong `distributorId`/location bound to the enrollment) and a state bleed across many independent signup sessions sharing one stale authorization decision, matching the Dopex root cause of "value validated once, trusted later, real-world state has since drifted."

### Likelihood Explanation
This path is reachable in normal, unprivileged operation of every orb: it is the default flow whenever more than one signup happens within `operator_qr_expiration_time` of an operator QR scan (self-serve mode explicitly relies on this reuse in `scan_initial_qr_codes`/`idle_scan_user_qr_code`, and default non-self-serve mode reuses it via `scan_remaining_qr_codes` inside `do_signup`, which runs on every button-press signup). No special privileges or hardware access are needed to trigger repeated signups within the cache window.

### Recommendation
Re-validate the operator's authorization/location with the backend (or at least re-check on a much shorter cadence, e.g., per-signup or per few minutes) rather than trusting the cached `OperatorData` purely based on elapsed wall-clock time up to a 23-hour ceiling. At minimum, add a periodic backend re-check independent of `operator_qr_expiration_time`, and invalidate the cache immediately when a backend-side revocation signal is available.

### Proof of Concept
1. Operator scans QR code once; `verify_operator_qr_code` succeeds and `OperatorData{ qr_code, location_data, timestamp }` is cached (`src/plans/mod.rs:849-853`).
2. Backend subsequently revokes/deactivates that operator or the operator's location legitimately changes.
3. Within the next `operator_qr_expiration_time` (up to 23 hours, `src/config.rs:443`), any number of new signups proceed through `scan_remaining_qr_codes`'s `QrCodes::Operator { operator_data } if operator_data.timestamp.elapsed() < operator_qr_expiration_time` branch (`src/plans/mod.rs:806-820`), which skips `verify_operator_qr_code` entirely and reuses the stale, now-invalid authorization/location data.
4. Each of these signups is submitted to the backend with the stale operator's `user_id` as `distributorId` (`src/backend/signup_post.rs:128`) and, depending on config, validated using the stale `location_data.session_coordinates` (`src/backend/user_status.rs:122-125`), resulting in signups misattributed to an operator whose authorization/location was no longer current.

    async fn scan_initial_qr_codes(
        &mut self,
        orb: &mut Orb,
        qr_codes: &mut QrCodes,
        self_serve: bool,
        operator_qr_expiration_time: Duration,
    ) -> Result<()> {
        if self_serve
            && qr_codes
                .operator_timestamp()
                .map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)
        {
            loop {
                let qr_capture_start = Instant::now();
                let operator_qr_code =
                    self.scan_operator_qr_code(orb, None).await?.expect("to never timeout");
                let Some(operator_qr_code) =
                    self.handle_magic_operator_qr_code(orb, operator_qr_code).await?
                else {
                    continue;
                };
                let Some((_, operator_location_data)) =
                    self.verify_operator_qr_code(orb, &operator_qr_code, qr_capture_start).await?
                else {
                    continue;
                };
                *qr_codes = QrCodes::Operator {
                    operator_data: OperatorData {
                        qr_code: operator_qr_code,
                        location_data: operator_location_data,
                        timestamp: Instant::now(),
                    },
                };
                break;
            }
        }
        Ok(())
    }
