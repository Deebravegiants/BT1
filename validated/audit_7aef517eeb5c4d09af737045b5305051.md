### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw` and `SweepDust` handling allows escrowed funds to be marked released/swept without an actual token transfer - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`IntentGatewayV2.withdraw()` and the `SweepDust` branch of `onAccept()` release escrowed ERC20 tokens using a raw low-level `.call()` to the token's `transfer` selector, checking only that the call did not revert (`success`) but never decoding and validating the returned boolean. Non-standard, non-reverting ERC20 tokens (e.g. ZRX-style tokens that return `false` on failure instead of reverting) will make `success == true` even though no tokens moved, letting the contract permanently mark escrow as spent/refunded while the beneficiary receives nothing.

### Finding Description
In `withdraw()`, escrowed tokens are transferred to the beneficiary via: [1](#0-0) 
and transaction fees are released with the same unchecked pattern: [2](#0-1) 

The same unsafe pattern appears in the `SweepDust` request handler: [3](#0-2) 

In all three call sites, `(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` treats the outer call's non-reverting execution as proof of a successful transfer. For ERC20 implementations that return `false` on insufficient balance or other failure conditions instead of reverting (the exact bug class cited in the analog report — ZRX and similarly-behaving tokens), `success` is `true` even though `token.transfer` returned `false` and no value was moved. Immediately after this unchecked call, `_orders[body.commitment][token] -= amount;` decrements internal accounting and `_filled[body.commitment] = beneficiary;` marks the order filled/redeemed, and for dust, `emit DustSwept(...)` fires unconditionally.

Contrast this with the escrow-side deposit logic elsewhere in the codebase, which correctly uses OpenZeppelin's `SafeERC20.safeTransferFrom` (which decodes and enforces the boolean return): [4](#0-3) 
The withdrawal/sweep path was not brought up to the same standard.

`withdraw()` is reachable from `onGetResponse`, which is invoked by the ISMP host on a permissionless relayed GET response used for `RefundEscrow`: [5](#0-4) 
and from the `RedeemEscrow`/`RefundEscrow` `onAccept` branch, both driven by relayed cross-chain messages that any relayer can deliver once a valid proof is supplied — this is the same class of externally-triggerable path as the original Cooler `transferFrom` issue, just on the withdrawal/payout side rather than the deposit side.

### Impact Explanation
If the escrowed or fee token is a non-reverting ERC20, a filler/solver's escrow can be marked `_filled`/redeemed and its internal accounting (`_orders[...][token] -= amount`) decremented, or dust marked as `DustSwept`, while the intended recipient receives zero tokens. This constitutes silent, permanent loss of the beneficiary's funds (the token remains stuck in the contract with no accounting path left to reclaim it, since the order slot has already been zeroed/decremented and `_filled` has been set), matching the "permanent freezing of funds" / unbacked accounting criteria.

### Likelihood Explanation
Likelihood depends on whether the token registered/whitelisted as escrow/fee token for a given `IntentGatewayV2` deployment can be a non-standard ERC20 that returns `false` rather than reverting. Since the intent-gateway design explicitly supports arbitrary ERC20 tokens as intent inputs/fees (as evidenced by fee-on-transfer token handling tests elsewhere in the suite), and there is no visible allow-list restricting to conforming tokens, the precondition is realistic for at least some deployments/token pairs, making this a real code-quality/security gap rather than a purely theoretical one.

### Recommendation
Replace all raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` patterns in `withdraw()` and the `SweepDust` handler with OpenZeppelin's `SafeERC20.safeTransfer`, consistent with the `safeTransferFrom` already used elsewhere in the same contract. This ensures both call-success and the ABI-decoded boolean return value (when present) are validated before mutating escrow accounting or emitting fulfillment/sweep events.

### Proof of Concept
1. Deploy `IntentGatewayV2` (tron variant) with a mock ERC20 token whose `transfer` function returns `false` on failure instead of reverting (mirroring ZRX's behavior), registered as an order input/fee token.
2. Create and fill an order such that `_orders[commitment][token]` is credited to the escrow.
3. Drain the gateway's balance of that token via any other mechanism (or use a token variant where `transfer` unconditionally returns `false` while emitting no revert), then trigger `withdraw()` via a relayed `RedeemEscrow`/`RefundEscrow` message.
4. Observe: `token.call(...)` returns `success = true` (the call executed without reverting) despite the encoded return data being `false`; the code proceeds to set `_filled[commitment] = beneficiary` and decrement `_orders[commitment][token]`, while the beneficiary's on-chain token balance is unchanged.
