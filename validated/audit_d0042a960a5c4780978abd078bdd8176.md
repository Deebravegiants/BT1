### Title
Webhook `shop` domain is trusted for tenant attribution without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC computed only over the raw request body, but then hands the app a `shop` value taken from an unauthenticated HTTP header. The gem documents `WebhookMetadata#shop` as the trusted "shop domain of the webhook" that apps use for tenant attribution (e.g. to look up sessions or route data), yet that field is never bound to the HMAC-verified bytes.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes the expected signature from `verifiable_query.to_signable_string` and compares it to the `hmac` field via `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `Webhooks::Request#to_signable_string` returns only `@raw_body`: [2](#0-1) 

Meanwhile, `Webhooks::Request#shop` is read from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header, which is not part of `to_signable_string` and is therefore not covered by the HMAC at all: [3](#0-2) 

`Registry.process` verifies only the HMAC over the body, then constructs `WebhookMetadata` directly from `request.shop` (the unauthenticated header) and passes it to the app's handler as the trusted tenant identifier: [4](#0-3) 

`WebhookMetadata#shop` is documented as the authoritative "shop domain of the webhook" that consuming apps are expected to use (e.g., to route the event to the correct tenant/session): [5](#0-4) [6](#0-5) 

This breaks the intended identity binding: `shop (HMAC-authenticated bytes) == shop (value the app acts on)`. The gem verifies the *body* bytes but hands out the *shop* from an entirely separate, unsigned channel (an HTTP header). Any request whose body produces a valid HMAC for the configured `api_secret_key` will pass `process`'s HMAC check regardless of what `x-shopify-shop-domain` header accompanies it — the header can be set to any value without affecting HMAC validation.

### Impact Explanation
This is a cross-tenant identity-binding break as defined in scope: "a field acted on but not covered by the HMAC." Applications built on this gem are told (per the gem's own documentation) that `data.shop` is safe to use for tenant routing/attribution once `Registry.process` succeeds. Since `shop` is not bound to the signed content, an attacker who can produce or replay any body+HMAC pair valid for the app's secret (e.g., a captured/replayed webhook delivery, or by exploiting any downstream component that forwards attacker-controlled headers while preserving a valid body/HMAC pair) can cause the webhook to be attributed to an arbitrary victim shop, leading to cross-tenant data confusion in the consuming application.

### Likelihood Explanation
Exploitation requires the ability to submit a request with a valid `hmac-sha256` header for some body signed with the app's real `api_secret_key`. In the normal case the header is set solely by Shopify's delivery infrastructure and the HMAC still ties the body to a legitimate Shopify-originated request, but the gem itself performs no work to bind the `shop` header to that signed payload, so the guarantee that `data.shop` is trustworthy rests entirely on infrastructure outside this gem, not on any check the gem performs. This is a real, provable root-cause gap in the gem's own code (not a documented API being ignored by the host app) — the field is officially exposed as authenticated when it is not.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values in the signable string used for HMAC verification of webhook requests, or otherwise cryptographically bind the header-derived `shop` to the verified body before constructing `WebhookMetadata`. At minimum, document explicitly that `WebhookMetadata#shop` is not covered by the HMAC and must not be treated as authenticated by itself.

### Proof of Concept
1. Configure `ShopifyAPI::Context` with a known `api_secret_key`.
2. Compute `hmac = Base64.encode64(OpenSSL::HMAC.digest("sha256", api_secret_key, raw_body))` for an arbitrary `raw_body` (e.g. `"{}"`).
3. Build headers with that valid `hmac`, `x-shopify-topic`, and an attacker-chosen `x-shopify-shop-domain` (e.g. `"victim-shop.myshopify.com"`) — differing from the shop that actually produced/owns the body content.
4. Call `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers))`.
5. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the HMAC as shown in [7](#0-6) , and the registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though that value was never verified against the signed bytes.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
