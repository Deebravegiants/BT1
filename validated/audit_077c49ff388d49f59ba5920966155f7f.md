## Title
Webhook `shop` (and `topic`/`api_version`/`webhook_id`) identity fields are not covered by the HMAC signature, allowing tenant-field spoofing on a validly-signed payload - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its signable content from the raw body only, while the `shop`, `topic`, `api_version`, and `webhook_id` values are read from HTTP headers that are never included in the HMAC computation. `Registry.process` validates only the body's HMAC and then forwards the unauthenticated `shop` header straight to the app's webhook handler, so the "shop" identity of an otherwise validly-signed webhook can be altered by anyone who controls the request headers.

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

Meanwhile `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled from headers, none of which feed into the signable string: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)`, i.e. it authenticates the raw body bytes, nothing else: [3](#0-2) 

`Registry.process` trusts this validation and then hands the caller's handler the header-derived, HMAC-unauthenticated `shop` (and other header fields) as if they were verified: [4](#0-3) 

This breaks the intended identity binding `signed_shop == delivered_shop`: the equality the HMAC is supposed to guarantee is `HMAC(body, secret) == received_hmac ⟹ (topic, shop, body) is authentic`, but in fact only `body` is bound by the signature. `shop`, `topic`, `webhook_id`, and `api_version` are attacker-controllable headers that ride along unauthenticated.

### Impact Explanation
Any party who can obtain one genuinely-signed webhook body+HMAC pair for their own shop (which any merchant/app installer legitimately receives) can resend that exact body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) header for a different, victim shop's domain. Since only the body is HMAC-checked, `Registry.process` will accept the forged request as valid and invoke the host app's handler with `WebhookMetadata#shop` set to the spoofed victim shop. If the host application uses this `shop` value to scope tenant data (a documented, expected usage — the whole purpose of exposing `shop` on `WebhookMetadata`), this crosses the tenant boundary, matching the Critical "cross-tenant access" impact category: data intended for shop A can be attributed to/processed under shop B's tenant context.

### Likelihood Explanation
Exploitation requires only network access to the app's public webhook endpoint and possession of one legitimately-signed webhook (trivially obtainable by installing the target app on an attacker-owned development store, which typically requires no special privilege). No `api_secret_key`, access token, or other Shopify-side secret is needed — the attacker reuses a signature they were legitimately given for a different body/header combination.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable content, or otherwise cryptographically bind them to the verified payload, so that `HmacValidator.validate` fails if any of these fields are altered relative to what Shopify actually signed. At minimum, document (and ideally enforce in the gem) that `WebhookMetadata#shop`/`#topic` are unauthenticated and must not be used by host apps for tenant scoping without an independent verification step.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook (e.g. `orders/create`) with body `B` and header `x-shopify-hmac-sha256: H = HMAC(secret, B)`.
2. Attacker resends a POST to the app's webhook endpoint with the same body `B` and same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` and `H`: [5](#0-4) 
4. The registered handler is invoked with `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: parsed_body, ...)`, even though Shopify never signed anything associating body `B` with `victim.myshopify.com`.
