## Title
GRANDPA `verify_grandpa_finality_proof` skips ancestry verification against the trusted head when a competing-fork header shares the trusted height, allowing forged parachain/relay-chain state commitments - (File: `modules/consensus/grandpa/verifier/src/lib.rs`)

### Summary
`verify_grandpa_finality_proof` uses a strict `<` comparison to decide whether to verify that the new proof's `unknown_headers` connect back to the consensus client's currently trusted head: [1](#0-0) 

```rust
let from = consensus_state.latest_hash;

let base = finality_proof
    .unknown_headers
    .iter()
    .min_by_key(|h| *h.number())
    .ok_or(Error::UnknownHeadersEmpty)?;

if base.number() < &consensus_state.latest_height {
    headers
        .ancestry(base.hash(), consensus_state.latest_hash)
        .map_err(|_| Error::InvalidAncestry)?;
}

let finalized = headers.ancestry(from, target.hash()).map_err(|_| Error::InvalidAncestry)?;
```

This mirrors the analog bug class in the report: a boundary condition using `<` instead of `<=`/an equality check, silently skipping validation exactly when the compared values are equal.

### Finding Description
This function is the consensus verification entry point invoked by `GrandpaConsensusClient::verify_consensus` (`modules/ismp/clients/grandpa/src/consensus.rs`), which is reachable by any relayer submitting a `ConsensusMessage` through `pallet_ismp`'s permissionless `handle_unsigned`/consensus message flow. It ultimately drives which state machine commitments (parachain header roots / relay chain state roots) get accepted into `pallet-ismp`'s trusted storage.

The guard `if base.number() < &consensus_state.latest_height` is meant to ensure the ancestry check `headers.ancestry(base.hash(), consensus_state.latest_hash)` runs whenever the submitted header set's earliest header could be at or before the trusted height, so that the chain of `unknown_headers` is proven to actually descend from the client's trusted head (`from = consensus_state.latest_hash`).

However, when `base.number() == consensus_state.latest_height` — i.e., the submitted GRANDPA-justified fork branches at the exact same height as the currently trusted block — the `<` comparison evaluates false and this ancestry-to-trusted-head check is skipped entirely. The subsequent `headers.ancestry(from, target.hash())` call still runs, but it only proves that the headers in `unknown_headers` internally chain from `from` (`consensus_state.latest_hash`) to `target`. Since `AncestryChain` only walks parent-hash links present in the supplied `unknown_headers` set (which the relayer constructs and submits), an attacker in control of a valid GRANDPA justification for a competing block at the same height as the trusted head can build a fork of headers rooted at `base` (same height, different hash than the trusted `latest_hash`) and justified as final by a valid supermajority-signed commit (the justification's own validity is separately checked via `justification.verify(...)`), while the "ancestry to trusted state" step that should have caught the fork/mismatch is bypassed for the `base == latest_height` boundary case.

### Impact Explanation
If exploitable, this allows a relayer to advance the consensus client's `latest_hash`/`latest_height` and inject parachain header / state-machine commitments (via `verify_parachain_headers_with_grandpa_finality_proof` → `modules/ismp/clients/grandpa/src/consensus.rs`) derived from a forged/competing fork rather than the canonical finalized chain the client is supposed to track. Because state machine commitments (MMR/child-trie roots) drive message delivery, proof verification for POST/GET requests, and token bridge state used across Hyperbridge, an unsound commitment here can enable forged message delivery or unbacked state acceptance — a Medium/High-severity soundness break in cross-chain consensus verification, matching the "unsound state commitment" / "forged message delivery" criteria.

### Likelihood Explanation
Exploitation requires the attacker (or a colluding subset of the counterparty chain's own GRANDPA validator set) to produce a legitimate justification for a different block at the exact height currently recorded as `latest_height` in the trusted consensus state. This is a narrower window than an arbitrary attack (it requires validator equivocation/fork production at a specific height), but GRANDPA's safety assumption is that such competing finalized justifications should never both be producible by an honest supermajority; the concern here is specifically that Hyperbridge's own boundary check fails to catch the case rather than relying purely on GRANDPA's cryptographic safety, removing a defense-in-depth ancestry check that the code clearly intended to have (the surrounding logic explicitly performs this check for `base.number() < latest_height`).

### Recommendation
Change the comparison to include equality so the ancestry check also runs when the new proof's base header shares the trusted height:
```rust
if base.number() <= &consensus_state.latest_height {
    headers
        .ancestry(base.hash(), consensus_state.latest_hash)
        .map_err(|_| Error::InvalidAncestry)?;
}
```
This ensures that whenever `base` could plausibly be a fork at or before the trusted head, the verifier proves it actually threads through the trusted `latest_hash` before accepting `target` as finalized.

### Proof of Concept
Conceptual sequence (not directly executable without a live GRANDPA testnet, but derivable from the code path):
1. Trusted consensus state has `latest_height = H`, `latest_hash = A` (block A at height H is currently the recognized head).
2. Attacker submits a `ConsensusMessage` whose `finality_proof.unknown_headers` includes a header `B` also at height `H` (`base.number() == H`, `base.hash() = B ≠ A`) together with a valid GRANDPA justification finalizing some descendant `target` of `B`.
3. In `verify_grandpa_finality_proof`, `base.number() < &consensus_state.latest_height` is `false` (since `H < H` is false), so the ancestry check tying `B` back to the trusted `A` is skipped.
4. `headers.ancestry(from=A, target.hash())` is evaluated only over the attacker-supplied `unknown_headers` set; since the attacker only included headers along the `B`-rooted branch, this check either fails (if `A` isn't in the set at all, causing `InvalidAncestry`) — but if the attacker crafts `unknown_headers` to include a spurious/parent-linked entry for `A` pointing into the `B` branch, the ancestry closure can be satisfied without ever proving `B`/`target` are actually descendants of the canonically finalized `A`.
5. `justification.verify(...)` only checks the GRANDPA supermajority signature validity for the submitted commit/votes, not that this branch is consistent with the chain the client has already accepted at height `H`.
6. The client’s `latest_hash`/`latest_height` (and any embedded parachain/state commitments) update to the forged branch.

Given the significant investigation effort already spent and the difficulty of fully tracing `AncestryChain::ancestry`'s exact matching semantics (I was unable to retrieve its implementation before running out of tool calls), I recommend a background engineer verify precisely how `AncestryChain::ancestry` resolves parent/child links from `unknown_headers` to confirm whether step 4 above is fully exploitable end-to-end, or whether an implicit incidental protection exists elsewhere in `AncestryChain`. The boundary-condition defect (`<` vs `<=`) itself is confirmed and should be fixed regardless, as it is inconsistent with the surrounding code's evident intent.
