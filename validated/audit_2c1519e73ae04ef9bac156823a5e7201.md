## Title
Pool initialization (`Initialize2`) can be front-run by an attacker to permanently deny/hijack the legitimate pool creation — (File: `program/src/processor.rs`)

### Summary
`process_initialize2` derives every state account needed for a pool (`AmmInfo`, LP mint, coin/pc vaults, `TargetOrders`) deterministically from the `market_info` public key, and the instruction can be invoked by *any* signer who supplies the accounts and a non-zero `init_coin_amount`/`init_pc_amount`. There is no check binding the call to a specific, pre-authorized creator. This is the same "empty-state race" bug class described in the referenced report: just like `LinearVesting.vestFor` reverts once `vest[user].amount != 0`, `process_initialize2` reverts once the deterministic `AmmInfo` PDA for a market is no longer `Uninitialized`. A griefer/attacker can front-run the legitimate creator's transaction with the same `market_info` account and permanently take over — or permanently deny — the pool for that market.

### Finding Description
`process_initialize2` computes the pool's associated accounts purely from `market_info.key` and the program ID: [1](#0-0) 

It then creates the `AmmInfo` account via `generate_amm_associated_account`, which fails only if the derived address is *already* owned by a non-system-program account: [2](#0-1) 

Right after account creation, the code checks the AMM's status: [3](#0-2) 

Both the `AlreadyInUse` status check and the "already owned" (`RepeatCreateAmm`) branch in `generate_amm_associated_account`/`generate_amm_associated_spl_token`/`generate_amm_associated_spl_mint` behave exactly like `vest[user].amount == 0` in the vesting report: the very first caller to successfully complete `Initialize2` for a given `market_info` permanently claims that market's pool, and every subsequent (including the intended, legitimate) `Initialize2` call for the same market reverts.

Critically, nothing restricts who may call `Initialize2`; only `user_wallet_info.is_signer` is required: [4](#0-3) 

The attacker fully controls `init_coin_amount`/`init_pc_amount`, i.e. the initial price ratio and lp_amount baseline, which subsequent `Deposit` calls must respect: [5](#0-4) [6](#0-5) 

Because `market_info` (an OpenBook/Serum market account) is public knowledge before the legitimate team's `Initialize2` transaction lands, an attacker can observe the mempool/anticipate the market and submit their own `Initialize2` for the same market with a negligible amount of tokens and an arbitrary skewed ratio, landing first.

### Impact Explanation
- The legitimate pool creator's transaction permanently reverts with `AmmError::AlreadyInUse` / `AmmError::RepeatCreateAmm`; because the `AmmInfo`/vault/mint PDAs for that market are single-use and derived solely from `market_info`, the intended pool for that market can never be created — a permanent denial-of-service, exactly mirroring "the vest would be denied" impact in the analog report.
- Beyond pure denial, the attacker becomes the pool's genesis initializer with full control over the initial coin:pc ratio (subject only to `amm_coin_vault.amount == 0`/`amm_pc_vault.amount == 0` checks, i.e., any non-zero amount is accepted). This is an unauthorized privileged effect: all subsequent `Deposit` LP-mint math is proportional to the ratio and `amm.lp_amount` set by whoever won the race, letting the attacker dictate the market's actual launch price and LP-accounting baseline for the token pair.

### Likelihood Explanation
`Initialize2` is a public, permissionless instruction reachable in a single transaction with attacker-chosen accounts (only needing minimal `coin`/`pc` token balances and the well-known `market_info`), so any observer of a pending pool launch (e.g., via mempool/public announcement of the market address) can front-run it deterministically.

### Recommendation
Bind pool creation authority to a specific expected creator (e.g., require the fee-payer/creator to match a value recorded by the market/config, or require a separate governance-approved "pool creation ticket" account) before allowing `process_initialize2` to succeed for a given `market_info`, so an arbitrary third party cannot win the race to initialize someone else's intended pool.

### Proof of Concept
1. Team A prepares to launch a Raydium pool for OpenBook market `M`, planning to call `Initialize2` with `market_info = M`, `init_coin_amount = 1_000_000`, `init_pc_amount = 5_000_000`.
2. Attacker observes market `M` is about to be used for a Raydium pool (market creation/pool launch is publicly known ahead of time) and submits their own `Initialize2` transaction referencing the same `market_info = M`, but with attacker-owned coin/pc token accounts and minimal amounts (e.g., `init_coin_amount = 1`, `init_pc_amount = 1`), and gets it included first.
3. `generate_amm_associated_account` succeeds for the attacker (PDA was still `system_program`-owned) at `program/src/processor.rs:804-814`; `amm.status` transitions away from `Uninitialized` at `program/src/processor.rs:843-847`, and the attacker's chosen ratio becomes the pool's baseline via `amm.initialize(...)` and `amm.lp_amount = liquidity` at `program/src/processor.rs:908-982`.
4. Team A's original `Initialize2` transaction now reverts with `AmmError::AlreadyInUse` (or `RepeatCreateAmm` if it lands even earlier in account creation) — the intended pool for market `M` can never be created, permanently denying Team A's launch, while the attacker holds the genesis LP position and dictated price ratio for market `M`.
