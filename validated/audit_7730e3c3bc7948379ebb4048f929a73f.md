### Title
Webhook `shop`, `topic`, and `webhook_id` headers are not covered by the HMAC signature, allowing cross-tenant spoofing of webhook metadata - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC of the raw request body, but the `shop`, `topic`, `api_version`, and `webhook_id` values that are passed on to the app's handler are taken from unauthenticated HTTP headers that are never included in the signed bytes.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` verifies the webhook using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` and compares it against the `hmac-sha256` header, and then immediately forwards `request.shop`, `request.topic`, `request.webhook_id`, and `request.api_version` to the registered handler without any further check: [2](#0-1) 

Those accessors read straight from the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, and `x-shopify-api-version` headers, none of which participate in the HMAC computation: [3](#0-2) 

The HMAC validator itself only ever hashes `verifiable_query.to_signable_string` (i.e., the body) against the secret: [4](#0-3) 

This breaks the identity binding: `shop header == shop that produced/authorized this signed payload`. An unprivileged internet user who owns any legitimate (e.g., free-trial) shop that has the app installed can capture a genuine webhook delivery for their own store — a valid `raw_body` + `hmac-sha256` pair, since they control what happens in their store and can trigger arbitrary webhook topics (e.g. `customers/create`) — and then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a victim shop's domain. `Registry.process` will accept this as valid because HMAC validation never inspects the header values, and the handler will receive `WebhookMetadata` claiming the payload came from the victim shop.

The library's own documentation instructs handler authors to trust `data.shop` as "The shop domain of the webhook" and use it directly (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), confirming this is the intended, documented use of a value that the gem itself does not authenticate: [5](#0-4) [6](#0-5) 

This is the direct analog of the M-01 report's bug class: a permissive check (HMAC validation) that answers "valid" while an attacker-controlled field acted upon downstream (`shop`) is not actually covered by that check.

### Impact Explanation
Any app built on this gem that (as documented) keys its per-tenant data updates, job dispatch, or webhook de-duplication off `WebhookMetadata#shop` (or `#topic`/`#webhook_id`) is exposed to cross-tenant data confusion: an attacker who controls one shop can inject data attributed to another merchant's shop into the host application, since the gem's `Registry.process` provides no guarantee that the authenticated body actually originated from the shop named in the header. This meets the "cross-tenant access" Critical impact bar, because the merchant-domain identity, which host apps are told they can rely on from `data.shop`, is not bound to the cryptographic proof the gem performs.

### Likelihood Explanation
Exploitation requires only: (1) the ability to install the app on any shop (including a free development/trial store, which is not a "privileged account" in the sense excluded by scope — it is standard unprivileged access available to any internet user who can create a Shopify partner/dev store), and (2) the ability to POST arbitrary bytes/headers to the app's public webhook endpoint, which is inherently internet-reachable. No access token, `api_secret_key`, or victim credentials are needed — the attacker reuses a signature Shopify itself generated for the attacker's own store's webhook traffic.

### Recommendation
Bind the shop (and ideally topic/webhook_id) to the HMAC-covered bytes, or otherwise cross-validate them out-of-band:
- Reject processing if `request.shop` was not the shop for which the recipient endpoint/tenant context expects the webhook (i.e., require the host app to pass the expected shop into `process` and compare it against the header only after successful HMAC validation), and/or
- Change `to_signable_string`/`HmacValidator` usage for webhooks so the header-derived `shop`, `topic`, and `webhook_id` are included in the value that is HMAC-verified, matching how `AuthQuery#to_signable_string` already binds `shop`, `host`, `code`, `state`, and `timestamp` together.
- At minimum, update `docs/usage/webhooks.md` to stop presenting `data.shop`/`data.topic` as trustworthy identifiers on their own, and clearly document that the gem does not cryptographically bind these header values to the signed body.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a store they own/control) and lets it register for a webhook topic, e.g. `customers/create`.
2. Attacker triggers that webhook by performing the corresponding action in their own store (e.g., creating a customer), causing Shopify to deliver a POST to the app's webhook endpoint with a legitimately computed `x-shopify-hmac-sha256` for that `raw_body`.
3. Attacker intercepts/replays this exact `raw_body` + `x-shopify-hmac-sha256` pair to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-webhook-id` to bypass de-duplication).
4. `ShopifyAPI::Webhooks::Registry.process` computes the HMAC over `raw_body` only [7](#0-6) , finds it valid, and invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: attacker's data, ...)` [8](#0-7) .
5. The host application, following the gem's documented pattern, processes/persists this data as though it were victim-shop's legitimate webhook data.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
