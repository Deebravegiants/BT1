Audit Report

## Title
Nil-Pointer Dereference Panic in Vault `GatewayHandler.handlePublicKeyGet` via Missing-Params JSON-RPC Request - (File: `core/capabilities/vault/gw_handler.go`)

## Summary
`GatewayHandler.handlePublicKeyGet` in `core/capabilities/vault/gw_handler.go` dereferences `*req.Params` without a nil check, unlike the sibling secrets-methods, which pass through `GatewayVaultRequestProcessor.ProcessRequest` first (which explicitly checks `req.Params == nil`). Since `MethodPublicKeyGet` is a designed-to-be-unauthenticated method both on the gateway side (`core/services/gateway/handlers/vault/handler.go`) and the node side, an unauthenticated JSON-RPC request that omits `params` reaches `handlePublicKeyGet` and panics the node process.

## Finding Description
`HandleGatewayMessage` routes based on `req.Method`. For `MethodSecretsCreate/Update`, `MethodSecretsDelete/List`, the request first goes through `h.requestProcessor.ProcessRequest`, whose implementation (`processCreateSecretsRequest`) explicitly guards `if req.Params == nil { return nil, InvalidVaultParamsError{...} }` before any handler touches `Params`: [1](#0-0) [2](#0-1) 

But `MethodPublicKeyGet` skips this pipeline entirely, calling `h.handlePublicKeyGet(ctx, gatewayID, req)` directly: [3](#0-2) 

`handlePublicKeyGet` unconditionally dereferences `req.Params`: [4](#0-3) 

On the gateway side, `HandleJSONRPCUserMessage` explicitly treats `MethodPublicKeyGet` as not requiring authorization/validation and forwards the request (via `newActiveRequest`/`fanOutToVaultNodes` → `SendToNode`) to nodes unmodified, with no check that `req.Params` is non-nil: [5](#0-4) 

Confirmed by direct code reading: there is no `req.Params == nil` guard anywhere on the `MethodPublicKeyGet` path (neither gateway-side nor node-side), while every other JSON-unmarshal call site on `*req.Params` in this file (`handleSecretsCreate`, `handleSecretsUpdate`, `handleSecretsDelete`, `handleSecretsList`) is reached only after the nil-params check in `requestProcessor.ProcessRequest`. This confirms the claim's root cause: a broken invariant that "all `*req.Params` dereferences are preceded by a nil check" is violated specifically for the one method (`MethodPublicKeyGet`) that bypasses authorization and is reachable by unauthenticated callers.

## Impact Explanation
This is a denial-of-service vulnerability: dereferencing a nil pointer in Go without a `recover()` in the call chain crashes the entire node process, not just the request handler. Because `MethodPublicKeyGet` is intentionally exempt from authorization on both the gateway (`handler.go` comment: "Public key requests don't require authorization") and would-be node-side validation, any unauthenticated actor reaching the Gateway's JSON-RPC endpoint can trigger it, causing repeatable node crashes. This maps to a legitimate in-scope DoS impact against a Chainlink node/DON participant.

## Likelihood Explanation
High. The trigger requires only a syntactically valid JSON-RPC request with `method` set to the public-key-get method name and the `params` field omitted (valid per JSON-RPC 2.0, since `params` is optional). No signature, JWT, or allowlist entry is needed, and the vulnerable code path is unconditionally reached because `MethodPublicKeyGet` bypasses the entire authorization/validation pipeline that protects the other methods.

## Recommendation
Add an explicit `req.Params == nil` check at the start of `handlePublicKeyGet` (returning an `api.UserMessageParseError`/`InvalidParamsError` response) mirroring the check already present in `GatewayVaultRequestProcessor.processCreateSecretsRequest`. Ideally, add a generic guard in `HandleGatewayMessage` before dispatching to any handler that unmarshals `*req.Params`, and apply the same fix to the gateway-side `handler.go` public-key-get path before forwarding to nodes.

## Proof of Concept
1. Construct a `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` (or send a raw JSON-RPC message `{"jsonrpc":"2.0","id":"1","method":"vault_getPublicKey"}` omitting `params`) to the Gateway's vault JSON-RPC endpoint / `HandleJSONRPCUserMessage`.
2. Because the public key is not cached (`getCachedPublicKey` returns `nil`), the gateway calls `h.newActiveRequest` and `h.handlePublicKeyGet(ctx, ar)`, which forwards the message unmodified to node(s) via `fanOutToVaultNodes` → `SendToNode`.
3. On the node, `GatewayHandler.HandleGatewayMessage` dispatches to `handlePublicKeyGet(ctx, gatewayID, req)`, which executes `json.Unmarshal(*req.Params, r)` with `req.Params == nil`, causing a nil-pointer dereference panic and crashing the node process.
4. A minimal Go unit test can be written in `core/capabilities/vault/gw_handler_test.go` calling `HandleGatewayMessage` with a `*jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` and asserting it does not panic (currently it would panic, confirming the bug), then verifying the fix returns a structured error response instead.
