### Title
Fee withdrawn from caller before queue capacity is verified, causing fund loss on `QueueFull` in `Pallet::do_place_order` - (File: polkadot/runtime/parachains/src/on_demand/mod.rs)

### Summary
In `do_place_order`, the spot price is computed from `order_status.traffic`, `T::Currency::withdraw` debits the caller, and `Revenue::<T>::mutate` records the payment, all *before* `order_status.queue.try_push(..)` is attempted to actually enqueue the order. Because `try_push` on a `BoundedVec` is the only capacity check performed (there is no upfront `ensure!(!queue.is_full())`), and because FRAME does not automatically roll back storage writes made by nested calls (`Currency::withdraw`, `Revenue::<T>::mutate`) just because an outer closure/dispatchable later returns `Err`, a `QueueFull` failure at the end of the sequence leaves the withdrawal and revenue bookkeeping committed while no order is enqueued.

### Finding Description
The relevant sequence inside `do_place_order` (reached from the public extrinsics `place_order_allow_death`, `place_order_keep_alive`, and `place_order_with_credits`) is:
1. Read `order_status.traffic` and derive `spot_price` from it.
2. Call `T::Currency::withdraw(&sender, spot_price, WithdrawReasons::FEE, existence_requirement)` — this is an unconditional, immediately-committed mutation of the Balances pallet's `Account` storage.
3. Record the withdrawn amount into `Revenue::<T>` via `Revenue::<T>::mutate(|revenue| { ... bounded_revenue.get_mut(0) ... })` — again an immediate, unconditionally-committed write.
4. Only after these two side effects does the code attempt `order_status.queue.try_push(..)`, which can fail with `Error::<T>::QueueFull` if the bounded queue is already at `on_demand_queue_max_size`.

The critical issue is that steps 2 and 3 are *not* protected by any storage-transaction guarantee tied to the eventual success of step 4. `StorageValue::mutate`/`try_mutate` on `OrderStatus::<T>` only governs whether the `OrderStatus` value itself is committed; it has no effect on other storage items mutated as side effects inside the same closure, such as `Balances::Account` (via `Currency::withdraw`) or `Revenue::<T>`. Unless the whole call path is wrapped in `#[transactional]`/`with_storage_layer`, FRAME does not provide implicit all-or-nothing semantics across an entire dispatchable — this is precisely why the `#[transactional]` attribute exists as an opt-in mechanism in Substrate. If `do_place_order` (or its callers) do not use this attribute around the full withdraw+enqueue sequence, a late-stage `QueueFull` error from `try_push` will propagate as the extrinsic's `DispatchError` while the earlier withdrawal and revenue accounting remain permanently applied.

No event is emitted for a failed order in this path (events are only deposited after a successful `try_push`), so from the chain's observable state, the caller's balance decreased and `Revenue` increased with zero corresponding order — an accounting desync exactly matching `bounded_revenue.get_mut(0)` accumulating without an offsetting `queue` entry.

### Impact Explanation
An unprivileged signed caller (or a proxy/multisig acting on their behalf) loses real DOT with no on-demand service rendered and no order recorded: `Currency::withdraw` burns/reallocates the funds into `Revenue::<T>` while the parachain never receives a scheduled block. This is a direct "fee charged, no order enqueued" fund-loss bug, not merely a UX inconvenience, and it can be triggered by ordinary contention for a nearly-full on-demand queue, not by any malicious construction of extrinsic data.

### Likelihood Explanation
This is fully triggerable by any user with sufficient balance and no special privileges:
- Precondition: `order_status.queue.len() == on_demand_queue_max_size - 1` (queue nearly full — a naturally occurring condition given normal on-demand demand or trivially engineered by the attacker placing `max_size - 1` orders themselves).
- Trigger: attacker submits `place_order_allow_death`/`place_order_with_credits` with sufficient `max_amount` while (in the same block, due to extrinsic ordering) another order fills the final queue slot first.
- The attacker's call reaches `try_push` after the withdraw/revenue steps have already executed, `try_push` fails with `QueueFull`, and the dispatchable returns `Err` while the withdrawal persists.
This requires no signature forgery, no origin confusion, and is reproducible deterministically in a unit test by pre-filling the bounded queue to `max_size` and then issuing one more `place_order_allow_death` call.

### Recommendation
Reorder the logic so that queue capacity is validated *before* any balance-affecting side effect: check `order_status.queue.len() < on_demand_queue_max_size` (or attempt the `try_push` against a scratch/dry-run first) prior to calling `T::Currency::withdraw` and `Revenue::<T>::mutate`. Alternatively/additionally, wrap the entire withdraw-then-enqueue sequence in `#[transactional]` (or `frame_support::storage::with_storage_layer`) so that any `Err` returned from within the closure atomically reverts all nested storage writes, including the Balances withdrawal and the `Revenue::<T>` update.

### Proof of Concept
Rust unit test in `polkadot/runtime/parachains/src/on_demand/tests.rs`:
1. Configure the mock runtime with `on_demand_queue_max_size = N` and fund an account `ALICE` with balance `B`.
2. Fill the on-demand queue to `N` entries via `N` successful `place_order_allow_death` calls from other funded accounts (or directly building `OrderStatus` to `len == N` for a focused unit test, while still exercising the same `do_place_order` code path for the final call).
3. Record `ALICE`'s balance and `Revenue::<T>` total before the final call.
4. Call `OnDemand::place_order_allow_death(RuntimeOrigin::signed(ALICE), max_amount, para_id)`.
5. Assert:
   - The call returns `Err(Error::<T>::QueueFull.into())`.
   - `Balances::free_balance(ALICE)` is **unchanged** from the pre-call value (currently expected to fail, proving the bug — balance will be reduced by `spot_price`).
   - `Revenue::<T>::get()` totals are **unchanged** (currently expected to fail).
   - `OrderStatus::<T>::get().queue.len()` remains `N` (order not enqueued).
   - No `OnDemandOrderPlaced` event was emitted. [1](#0-0)
