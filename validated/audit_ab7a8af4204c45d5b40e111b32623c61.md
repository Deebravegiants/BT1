**Analysis:**

The `ConnectResource` handler at [1](#0-0)  only invokes admission plugins that explicitly declare they handle `admission.Connect` via `admit.Handles(admission.Connect)`. The `PodSecurity` admission plugin is constructed with `admission.NewHandler(admission.Create, admission.Update)` [2](#0-1) , meaning `Handles(admission.Connect)` returns `false` by design — PodSecurity is intentionally never invoked for Connect requests, so there is no "bypass": it was never in the invocation path for exec/attach/portforward to begin with.

This is deliberate architecture, not an omission: PodSecurity enforces pod security standards at pod **creation/update** time against the persisted `PodSpec`. The `Connect` operation on `pods/exec`, `pods/attach`, `pods/portforward` does not create or mutate a `Pod` object — the `opts` object passed to `admission.NewAttributesRecord` is a `PodExecOptions`/`PodAttachOptions`/etc, not a pod spec [3](#0-2) . There is nothing for PodSecurity to re-evaluate on connect since the target pod was already admitted (and enforced) at its own create/update time.

Authorization for exec/attach/portforward is governed by RBAC verbs `get`/`create` (not a "connect" verb, which does not exist in Kubernetes RBAC), and this is separately enforced and tested, e.g. in `TestPodSubresourceAuth` [4](#0-3) . The premise that a "connect" RBAC verb exists distinct from `get`/`create` on subresources is inaccurate for this codebase.

Existing integration tests (`testPodConnectSubresource`, `testSubresourceProxy`) already confirm that admission plugins which *do* register for `Connect` are invoked as expected [5](#0-4) , demonstrating the admission-ordering mechanism works correctly for plugins that opt in. PodSecurity's deliberate non-registration for Connect is a scoping decision, not an admission-completeness defect, since it has no relevant object data to validate on a connect request to an already-admitted pod.
