Audit Report

## Title
Unauthenticated `/v2/resume/:runID` Endpoint Allows Duplicate/Replay Resume of an Already-Finished Pipeline Task Run - (File: core/services/pipeline/orm.go)

## Summary
The `PATCH /v2/resume/:runID` route is registered in the unauthenticated `unauthedv2` group and is handled by `PipelineRunsController.Resume`, which forwards an attacker-controlled `taskID` (UUID) and result value/error to `ResumeJobV2` → `ResumeRun` → `orm.UpdateTaskRunResult` without any auth check. `UpdateTaskRunResult`'s guard query filters only on the parent `pipeline_runs.state`, not on whether the specific `pipeline_task_runs` row already has `finished_at` set, and the follow-up `UPDATE pipeline_task_runs SET output=..., error=..., finished_at=...` is unconditional, allowing the same task-run UUID to be resumed/overwritten more than once while the parent run remains `running`/`suspended`.

## Finding Description
`v2Routes` places `unauthedv2.PATCH("/resume/:runID", prc.Resume)` outside of any `auth.Authenticate` middleware, in contrast to all other `/v2` endpoints, which are grouped under `authv2` with token/session authentication <cite repo="Alyssadaypin/chainlink--004" path="core/web/router.go" start="238-248" />. `PipelineRunsController.Resume` parses the `taskID` from the URL and decodes a JSON body into a `ResumeRequest`, then calls `prc.App.ResumeJobV2(ctx, taskID, result)` with no authorization check, only later logging an audit event named `UnauthedRunResumed` [1](#0-0) . `ResumeRun` calls `orm.UpdateTaskRunResult(ctx, taskID, Result{...})` and, if the returned `start` flag is true, relaunches the pipeline run [2](#0-1) . `UpdateTaskRunResult`'s `SELECT ... FOR UPDATE` query matches on `pipeline_task_runs.id = $1 AND pipeline_runs.state in ('running', 'suspended')` — it has no `finished_at IS NULL` filter on the task run itself — and the subsequent `UPDATE pipeline_task_runs SET output = $2, error = $3, finished_at = $4 WHERE id = $1` is unconditional and will overwrite a task run's result even if `finished_at` was already set by a prior legitimate resume call [3](#0-2) . As long as the parent pipeline run has other pending/async branches keeping its state at `running` or `suspended`, this query keeps matching for the same task-run ID across multiple calls.

## Impact Explanation
This allows an unauthenticated attacker who has learned or observed a pending async task-run UUID (which is embedded in the `responseURL` sent to external bridge/adapter callbacks) to overwrite an already-finished task run's `output`/`error` with a second, attacker-controlled `PATCH` request, and to trigger another restart of the pipeline (`start=true` path in `ResumeRun`) with corrupted values. This maps to an in-scope "unauthorized job run" / data-integrity impact — resubmitted/altered pipeline results can propagate into aggregation stages and downstream on-chain transaction tasks.

## Likelihood Explanation
The route requires no session, API key, or role — it sits entirely in `unauthedv2` [4](#0-3) . The only precondition is knowledge of a pending task-run UUID, which is disclosed to whichever external adapter handles an async bridge task via the `responseURL`, or observable by anyone able to see that callback in transit. This is realistic for a compromised/malicious external adapter or a network observer of the callback, and the exploit is trivially repeatable (multiple `PATCH` calls) as long as the parent run remains non-terminal.

## Recommendation
Add `AND pipeline_task_runs.finished_at IS NULL` to the `SELECT ... FOR UPDATE` guard in `UpdateTaskRunResult` so an already-finished task run cannot match again, and return a distinct error when no row matches so `ResumeJobV2`/`Resume` can reject duplicate/replayed resume calls with an appropriate HTTP status (e.g., 409 Conflict) instead of silently overwriting the prior result.

## Proof of Concept
1. Configure a webhook job with an async bridge task that receives a `responseURL` of the form `http://<node>/v2/resume/<taskUUID>`.
2. Send `PATCH /v2/resume/<taskUUID>` with a benign JSON body (`{"value": "..."}`) — the request succeeds, `pipeline_task_runs.finished_at` is set for that task, and (if it was suspended) the run resumes.
3. While the parent run is still `running`/`suspended` (e.g., due to other pending async branches), send a second `PATCH /v2/resume/<taskUUID>` with a different value.
4. Observe that the query in `UpdateTaskRunResult` at `core/services/pipeline/orm.go:282` matches again (since it never checks `finished_at`), and the unconditional `UPDATE` at line 289 overwrites the previously finished task run's `output`/`error`, and `ResumeRun` may trigger another pipeline restart — demonstrable via a Go unit test against `orm.UpdateTaskRunResult` calling it twice with the same `taskID` and asserting the second call succeeds and overwrites the row instead of erroring.
