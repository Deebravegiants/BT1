### Title
Permanent loss of unexpected/residual tokens received during Intent Gateway calldata execution ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
The externally reported bug describes a router that identifies itself as `msg.sender` when bridging via li.fi, and consequently loses any refunded or substitute token (e.g., li.fi's `nextToken`/`hToken`) that doesn't match the originally expected asset, because the router has no generic mechanism to recover balances of tokens it didn't explicitly anticipate. The Hyperbridge Intent Gateway (`IntentGatewayV2`/`IntentsBase`/`ExtrinsicIntents`/`IntrinsicIntents`) has an analogous pattern: it routes escrowed and output funds through an intermediary `CallDispatcher` contract that executes arbitrary, order-supplied calldata (swaps, DEX routes, "other DeFi primitives"), and afterward sweeps back to the gateway **only the specific token addresses declared in the order** (`order.inputs`, `order.predispatch.assets`, `order.output.assets`). Any other token balance left on the `CallDispatcher` as a result of the external interaction (slippage refunds, wrong-token returns, partial swap failures that don't revert, dust from multi-hop routes) is never recovered.

### Finding Description
`_execute()` in `IntentsBase.sol` dispatches the order's `output.call` through the `CallDispatcher`, then sweeps residual balances back to the gateway, but the sweep loop iterates only over `order.output.assets` — the enumerated set of expected output tokens: [1](#0-0) 

Similarly, in `IntentGatewayV2.placeOrder()`, the predispatch flow transfers assets to the `CallDispatcher`, executes arbitrary calldata (e.g., "user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap"), and then only pulls back the tokens matching `order.inputs`: [2](#0-1) 

The documentation explicitly confirms this is a generic composability feature reachable by any unprivileged order-placing user or filling solver — "solvers can route through DEXes, lending protocols, or other DeFi primitives as part of filling an order" — and states residual balances are swept "back to the gateway and collected as dust," but only for the declared asset set: [3](#0-2) 

If the external protocol invoked through arbitrary calldata (a Uniswap-style router, a bridge integration, or any other composed DeFi call) leaves the `CallDispatcher` holding a token that is *not* one of the pre-declared `inputs`/`output.assets` — for example due to slippage-triggered partial fills, liquidity exhaustion causing a substitute/wrapped token to be returned (directly analogous to li.fi's `nextToken`/`hToken` behavior described in the report), or any other unexpected token transfer back to the caller (`CallDispatcher`, which is the effective "router" identity for these calls) — that balance is permanently unaccounted for. The sweep logic has no fallback path that inspects or recovers arbitrary/unknown token balances, and no rescue or admin-only recovery function was found on `CallDispatcher.sol` in this investigation (only its `dispatch()` entrypoint was confirmed to exist; deeper inspection of the file was not completed before the tool budget was exhausted, so I cannot rule out an owner-only rescue function existing there — this should be verified directly).

### Impact Explanation
If confirmed that `CallDispatcher.sol` has no generic token-recovery mechanism, any token balance left on it outside the order's declared asset list becomes permanently frozen — unbacked by any protocol accounting and unreachable even via the gateway's governance-only `SweepDust` mechanism, since `SweepDust` operates on the gateway's own balance, not the `CallDispatcher`'s. This is a permanent freezing of user or solver funds triggered by ordinary interaction with third-party swap/DeFi protocols embedded in `predispatch`/`output.call`, which is a supported and advertised feature of the protocol.

### Likelihood Explanation
This is reachable by any unprivileged user placing an order with `predispatch.call` set, or any solver filling an order with `output.call` set — both are core, documented, non-privileged features of the Intent Gateway. The triggering condition (an external swap/route returning a token other than the exact declared asset, e.g., through slippage, partial execution, or substitute-token behavior in the integrated DEX/bridge) is a realistic, if not guaranteed, occurrence for any calldata that composes with external liquidity venues — the exact scenario the original li.fi report highlights for amarok/hop.

### Recommendation
Add a generic sweep/rescue path from `CallDispatcher` that is not limited to the order's declared token list — e.g., allow the calling gateway (or a governance-gated function) to sweep arbitrary ERC20/native balances left on the dispatcher after a call sequence completes, and emit a distinguishable event (e.g., `UnexpectedDustCollected`) so off-chain systems can track and eventually return these funds to the correct beneficiary rather than losing them permanently.

### Proof of Concept
Conceptual PoC (requires live-fork verification, not completed in this investigation):
1. User calls `IntentGatewayV2.placeOrder()` with `predispatch.call` encoding a call to an external swap venue whose slippage/liquidity conditions cause it to return a different token (or a partial amount that leaves a non-`order.inputs` token balance) to the `CallDispatcher`. [4](#0-3) 
2. The post-call sweep only pulls tokens matching `order.inputs[i].token`; the unexpected token balance remains on `CallDispatcher`.
3. Repeat for `output.call` on `fillOrder`, using `_execute()`'s sweep bounded to `order.output.assets`. [5](#0-4) 
4. Confirm (by inspecting `CallDispatcher.sol`, which could not be fully reviewed here due to tool-call exhaustion) whether any owner/governance function exists to recover this stranded balance; if none exists, the funds are permanently lost.

### Predispatch

The `predispatch` field in `Order` contains calldata to execute *before* escrowing inputs. The predispatch assets specified in `DispatchInfo.assets` are transferred to the `CallDispatcher`, the encoded calls are executed, and the resulting tokens are transferred back to the gateway for escrow. This enables swap-then-escrow patterns — for example, a user sends ETH which the `CallDispatcher` swaps to DAI on Uniswap, and the resulting DAI is escrowed as the order input.

### Postdispatch

The `call` field in `PaymentInfo` contains calldata to execute *after* the order is filled. This enables fill-then-act patterns — for example, output tokens received from the solver are routed through a DeFi protocol before reaching the beneficiary.

Execution timing differs by mode:

- **Same-chain**: Calldata executes only after the order is **fully filled**. Partial fills do not trigger calldata — only the final fill that completes the order executes it. This ensures all output tokens are available when the calls run.
- **Cross-chain**: Calldata executes **immediately** after the solver delivers output tokens to the beneficiary, before the settlement message is dispatched back to the source chain.

After execution, any tokens remaining in the `CallDispatcher` are swept back to the gateway and collected as dust (emitting `DustCollected` for each token). When postdispatch calldata is present, 100% of any surplus (solver overpayment) goes to the protocol rather than being split with the beneficiary — this prevents manipulation of surplus distribution through calldata side effects.
