### Title
Missing shop-domain allowlist validation in `TokenExchange.exchange_token` allows `client_secret` to be sent to an unvalidated host — ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the shop host directly from the JWT session token's `dest` claim and uses it, unsanitized, as the destination host for the OAuth token-exchange request that carries the app's `client_id`/`client_secret`. Every sibling credential-exchange method in the same file and module (`migrate_to_expiring_token`, `ClientCredentials.client_credentials`, `RefreshToken.refresh_access_token`, `Graphql::Storefront#initialize`) explicitly calls `Utils::ShopValidator.sanitize!(shop)` before building the request host, but `exchange_token` does not.

### Finding Description
`JwtPayload#shop` simply strips the `"https://"` prefix from the token's `dest` claim with no allowlist check: [1](#0-0) 

`exchange_token` takes that value directly as `dest_shop` and builds a `Session` from it, which is then used as the request host: [2](#0-1) 

The resulting `HttpClient` constructs the request origin straight from `session.shop`, with no domain restriction: [3](#0-2) 

Compare this to every other place in the codebase that turns a caller/token-derived `shop` string into a request host — all of them route the value through `Utils::ShopValidator.sanitize!`, which restricts the host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or a configured `myshopify_domain`: [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7) 

The binding that should hold is: `host that is validated as a trusted Shopify domain == host that receives client_id/client_secret`. In `exchange_token`, the host that is validated (implicitly, only via HS256 signature/`aud` check inside `JwtPayload`) is not the same check as the domain allowlist enforced everywhere else the gem sends `client_secret` — `JwtPayload` never calls `ShopValidator`, and `exchange_token` never calls it either. `TokenExchange.migrate_to_expiring_token`, sitting right next to `exchange_token` in the same file, demonstrates the pattern that was omitted.

### Impact Explanation
If the `dest` claim of a session token ever resolves to a host outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (e.g., through a proxy/dev setup, a misconfigured `myshopify_domain`, or any path where a token with attacker-influenced `dest` is accepted), `exchange_token` will POST the app's `client_id` and `client_secret` to that host — this is SSRF carrying the app's own long-lived credential, matching the "High – SSRF with the app's credentials" impact class. The missing check is a genuine, demonstrable code-path asymmetry versus the rest of the module, not a theoretical note.

### Likelihood Explanation
Exploitability is bounded by how strictly upstream (Shopify's session-token issuance) constrains the `dest` claim; within this gem's own code there is no defense-in-depth check, unlike every sibling function performing the same class of operation. This makes the gem's protection strictly weaker here than everywhere else it builds a credential-bearing request host from a `shop` value.

### Recommendation
In `ShopifyAPI::Auth::TokenExchange.exchange_token`, sanitize `dest_shop` the same way `migrate_to_expiring_token` does, e.g.:
```ruby
dest_shop = Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
before constructing `shop_session` and issuing the request that contains `client_id`/`client_secret`.

### Proof of Concept
1. Obtain/construct a validly HS256-signed session token whose `dest` claim is `"https://attacker.example"` (any path that yields a `JwtPayload` with `aud == Context.api_key` and a `dest` outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`).
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe (per `lib/shopify_api/clients/http_client.rb` lines 16-19) that the resulting `HttpClient` builds `@base_uri = "https://attacker.example"` and POSTs a body containing `client_id` and `client_secret` to `https://attacker.example/admin/oauth/access_token` — contrast with `migrate_to_expiring_token`, which would raise `ShopifyAPI::Errors::InvalidShopError` for the same input because it calls `ShopValidator.sanitize!` first.
