### Title
Free, repeated full re-execution of unsigned `handle_unsigned` ISMP messages during transaction-pool (re)validation enables resource-consumption DoS - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet_ismp::Call::handle_unsigned` is a fee-less, unsigned extrinsic whose `ValidateUnsigned::validate_unsigned` implementation runs the **entire** message-processing pipeline (`Self::execute(messages.clone())` → membership/non-membership proof verification, trie/child-trie walks, module dispatch) just to compute a priority/`provides` tag. Because Substrate re-invokes `validate_unsigned` on every transaction-pool (re)validation pass — on initial submission, on gossip receipt by every peer, and again on every new block for the tx's `longevity` window — a single unprivileged relayer submission with a large, unbounded `RequestMessage`/`ResponseMessage` batch and proof forces the full expensive verification to be **re-run from scratch many times** for the same submitted data, at zero cost to the submitter. This mirrors the libexpat bug class: a large payload that forces many full re-parsings/re-verifications rather than one bounded pass.

### Finding Description
`pallet_ismp::Pallet::<T>::validate_unsigned` (`modules/pallets/ismp/src/lib.rs:605-716`) is documented as allowing "users execute ISMP datagrams for free. Use with caution," and does exactly that: [1](#0-0) 

`Self::execute` (`modules/pallets/ismp/src/impls.rs:37-51`) runs `handle_incoming_message` for every message in the batch, which for `Message::Request`/`Message::Response` performs full membership-proof verification against a Merkle-Patricia/child trie (`modules/ismp/core/src/handlers/request.rs:86-93`, `modules/ismp/core/src/handlers/response.rs:78-114`, `modules/ismp/state-machines/substrate/src/lib.rs:126-176`) — i.e., decoding an attacker-supplied `Proof` and walking a trie proportional to its size: [2](#0-1) [3](#0-2) 

Unlike `pallet-beefy-consensus-proofs::submit_proof`, which bounds its proof to `BoundedVec<u8, T::MaxProofSize>` (`modules/pallets/beefy-consensus-proofs/src/lib.rs:127-129`, enforced at `MaxBeefyProofSize = 1_048_576` in `parachain/runtimes/nexus/src/lib.rs:1007-1008`), the `RequestMessage`/`ResponseMessage`/`Proof` types dispatched through `handle_unsigned` carry an **unbounded** `Vec<PostRequest>`/`Vec<GetRequest>` and an unbounded proof `Vec<u8>` (`modules/ismp/core/src/messaging.rs:116-147`). The only gate on unsigned submission is `ValidateUnsigned::validate_unsigned` itself — which is the function doing the expensive full-proof verification, not a cheap pre-check.

Because this heavy verification is embedded in `validate_unsigned` rather than gated behind a lightweight, size-bounded pre-check (as Substrate best practice recommends — expensive verification belongs in `on_initialize`/dispatch, with `validate_unsigned` kept O(1)/bounded), the same large payload gets fully re-verified:
- once by the local node on submission,
- once by every peer node that receives it over the network (each independently calls `validate_unsigned` before propagating further),
- and again on every block during the transaction's `longevity: 25` window as the pool revalidates queued unsigned transactions.

An attacker can maximize the cost per submission by padding `RequestMessage.requests`/`ResponseMessage.requests` and their proof with as many entries/trie nodes as fit in a block's `POV`/extrinsic size limit, since neither is capped by a `BoundedVec`.

### Impact Explanation
This is a network-wide, permissionless resource-consumption DoS: a single relayer-class actor (anyone able to submit an unsigned extrinsic to any node's RPC/mempool) can force every node in the network — collator, validator, and RPC nodes alike — to repeatedly perform expensive Merkle-Patricia trie verification against an unbounded proof, for free, and have that cost multiplied by every re-validation pass and every peer's independent gossip validation. Sustained submission of several such payloads can starve block-production nodes of CPU during transaction-pool maintenance, a route-unable-to-deliver-messages/availability impact matching the "resource consumption" class of the libexpat report, and satisfies the "Medium/High/Critical" and "unable to deliver messages" acceptance criteria.

### Likelihood Explanation
High. `handle_unsigned` is explicitly permissionless and fee-less by design (documented as "for free, use with caution"), reachable directly by any relayer/dispatcher without staking or signing, and the unbounded `Vec<PostRequest>`/proof fields are attacker-controlled with no chain-enforced upper bound comparable to `MaxProofSize` used elsewhere in the codebase (e.g., BEEFY proofs). No special timing or race condition is required — only submitting one oversized message batch.

### Recommendation
- Bound `RequestMessage.requests`, `ResponseMessage.requests`, and `Proof.proof` (and any nested consensus/fraud-proof payloads reachable via `handle_unsigned`) with `BoundedVec<_, MaxXxxSize>` enforced at the SCALE-decode boundary, mirroring `pallet-beefy-consensus-proofs::MaxProofSize`.
- Move the expensive verification (`Self::execute`) out of `validate_unsigned` into `pre_dispatch`/actual dispatch, and make `validate_unsigned` perform only cheap structural checks (bounds, hash-based `provides` tag) sufficient for pool prioritization/dedup, per Substrate's guidance that unsigned validation must be cheap and idempotent.
- Alternatively, charge a fee or require a bonded/staked signer for `handle_unsigned` batches above a small size threshold so the cost of verification is not fully externalized to network nodes.

### Proof of Concept
1. Craft a `RequestMessage` with the maximum number of `PostRequest` entries and a maximally-sized (but still within max extrinsic length) `Proof.proof` blob containing a deep/large Merkle-Patricia proof (unbounded `Vec<u8>`, no `MaxProofSize` cap exists for this path, unlike `pallet-beefy-consensus-proofs`).
2. Wrap it in `Message::Request` and submit via `Ismp::handle_unsigned` as an unsigned extrinsic to a full/RPC node.
3. Observe that `validate_unsigned` (`modules/pallets/ismp/src/lib.rs:614`) calls `Self::execute(messages.clone())`, fully re-decoding and re-verifying the trie proof, on: (a) the submitting node, (b) every peer node upon gossip, and (c) every block for up to `longevity = 25` blocks while the transaction remains queued and is revalidated — multiplying the verification cost by the number of validating nodes and revalidation rounds for a single, free submission.

*Note: I could not fully trace Substrate's generic transaction-pool revalidation cadence within this repo's index (it lives in the `polkadot-sdk`/`sc-transaction-pool` dependency, not in-repo), so the exact multiplier per block/peer is based on documented Substrate/Polkadot-SDK pool behavior rather than code found in this repository. Confirming the exact revalidation frequency would require inspecting the `sc-transaction-pool` crate directly, which is outside this indexed codebase — starting a Devin session with full filesystem access would allow verifying this precisely.*
