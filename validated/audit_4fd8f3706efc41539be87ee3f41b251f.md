### Title
Webhook `shop` domain is not covered by the HMAC signature, allowing cross-tenant shop-spoofing via replay - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats `request.shop` as a trusted identity for dispatching webhook data to the app's handler, but `request.shop` is read from the unauthenticated `x-shopify-shop-domain`/`shopify-shop-domain` header, and the HMAC that `Registry.process` validates only ever covers the raw request body [1](#0-0) . This is the analog of the Astaria bug class: a value that is *acted on* (the `shop` bound to the webhook payload/tenant) is not bound by the same integrity check (the HMAC) that protects the body.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and `#hmac` reads the signature straight from a header [2](#0-1) [3](#0-2) . `Utils::HmacValidator.validate` recomputes the HMAC over `to_signable_string` (i.e. the body only) and compares it to the received signature using `OpenSSL.secure_compare` [4](#0-3) . Crucially, `shop`, `topic`, `webhook_id`, and `api_version` — all read from separate headers — are never mixed into the signed string [5](#0-4) .

`Registry.process` then calls `Utils::HmacValidator.validate(request)` to authenticate the whole request, and immediately afterward builds `WebhookMetadata` using `request.shop`, `request.topic`, and `request.webhook_id` as if they were verified along with the body [6](#0-5) . The documented handler contract even tells app authors that `data.shop` is "The shop domain of the webhook", implying it is trustworthy once `process` succeeds, and typical usage keys application-side records off `data.shop` (see the documented example `perform_later(topic: data.topic, shop_domain: data.shop, ...)` in `docs/usage/webhooks.md`).

The equality that should hold but doesn't:
`shop_that_actually_produced(signed_body) == shop_attributed_to_the_request(request.shop)`

Because only the body is HMAC-bound, an attacker who owns any shop that has this same app installed can capture one legitimate webhook delivery (valid HMAC over the body, computed with the app's shared `api_secret_key`), then replay the identical `raw_body`/HMAC pair to the app's webhook endpoint while substituting a different `x-shopify-shop-domain` header value. `HmacValidator.validate` still succeeds (it never looks at the shop header), and `Registry.process` dispatches the (unchanged, attacker-controlled) body to the handler tagged with an attacker-chosen `shop` value.

### Impact Explanation
This is a cross-tenant identity-binding break: the webhook body's real origin shop and the `shop` value trusted by the handler can diverge under attacker control. In apps that use `data.shop` to select which merchant record/session to update (the pattern shown in this gem's own docs), an attacker with a legitimately installed instance of the app on their own store can inject data belonging to their shop into another shop's processing path (or vice versa — spoof arbitrary/unregistered shop domains entirely, since there's no check that the domain even exists or is one this app has a session for). This matches the "cross-tenant access" category.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker needs a valid app installation on at least one shop and the ability to replay the same raw body over a new HTTP request with a modified header — both are reachable by any "unprivileged internet user" who can install a public/free app on their own development or trial store, without needing the app's `api_secret_key`, an access token, or the victim's credentials. It does not require an OAuth completion or account takeover, only manipulation of an unauthenticated header on an otherwise-valid signed webhook delivery.

### Recommendation
Include the identity-relevant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string that `HmacValidator` verifies, or otherwise cryptographically bind them to the body's signature so that any header tampering invalidates the HMAC. At minimum, document that `data.shop` from a webhook is not itself part of the signed payload and that consuming applications must independently verify the shop against a known/authorized session before trusting it for tenant-scoped operations.

### Proof of Concept
1. Attacker installs the target app on `attacker.myshopify.com` and receives a legitimate webhook, e.g. body `{"id": 1, "note": "hello"}`, with headers:
   - `x-shopify-hmac-sha256: <valid HMAC of the body computed with the app's shared api_secret_key>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
   - `x-shopify-topic: orders/create`
2. Attacker resends the exact same body and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but changes the header to:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` accepts the headers [7](#0-6) , `Utils::HmacValidator.validate` recomputes the HMAC over the unchanged body and it matches [8](#0-7) , and `Registry.process` calls the handler with `WebhookMetadata` whose `shop` is `"victim-shop.myshopify.com"` even though the body never originated from that shop [9](#0-8) .
4. Any application logic keyed on `data.shop` (as shown in this gem's own `docs/usage/webhooks.md` example) now operates on attacker-controlled body content under the victim shop's identity.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
