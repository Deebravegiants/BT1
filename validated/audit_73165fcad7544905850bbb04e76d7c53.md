## Title
Unbounded `order.inputs` / `order.output.assets` array length in `IntentGatewayV2.placeOrder()` permanently freezes escrow via out-of-gas `withdraw()` — (File: `evm/src/apps/IntentGatewayV2.sol`, `evm/src/apps/intentsv2/IntentsBase.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
`placeOrder()` never bounds the number of distinct tokens a user can escrow in a single order. The escrowed tokens must later be released in a single mandatory loop — `_withdraw()` (main EVM path) or `withdraw()` (Tron path) — that iterates once per token performing a transfer. Because the token-array length is entirely attacker/user controlled at order-placement time and unbounded, an order can be crafted whose settlement loop exceeds the block gas limit, making both fill-settlement and refund/cancellation permanently revert — freezing the escrowed funds forever. This mirrors the reported YoloV2 bug class: an unbounded, attacker-controlled array is processed in a mandatory, un-capped loop that a later required step (winner draw / escrow release) cannot skip.

### Finding Description
`placeOrder()` in `evm/src/apps/IntentGatewayV2.sol` only checks that `order.inputs.length != 0`; there is no upper bound on `order.inputs.length` or `order.output.assets.length`: [1](#0-0) 

The same absence of a cap exists in the Tron variant: [2](#0-1) 

Every input token is escrowed in `_orders[commitment][token]` (one storage write per token, no length check): [3](#0-2) 

Settlement is unconditional: whenever the order is filled, refunded, or cancelled, `_withdraw()` iterates the full `body.tokens` array (which mirrors `order.inputs`), performing a transfer per token — this step is mandatory to release escrow and cannot be batched, skipped, or partially retried around one problematic index: [4](#0-3) 

The Tron contract's `withdraw()` has the identical unbounded loop, invoked from `onAccept` for both `RedeemEscrow` and `RefundEscrow` message kinds, and from `onGetResponse` for source-chain cancellation: [5](#0-4) [6](#0-5) [7](#0-6) 

No repo-wide constant bounds the number of tokens per order (`grep` for `MAX_INPUTS`/`MAX_OUTPUTS`/`MAX_TOKENS` returns no matches), and no check on `IsmpDispatcher`/`EvmHost` enforces a maximum request body size that would incidentally cap the array (`grep` for `maxRequestBodySize`/`BodyTooLarge` returns no matches). Since a user pays only normal ERC-20 transfer/approval gas at placement time (one `safeTransferFrom` per token, same loop cost as withdrawal), and can use many cheap/dust-value or even self-deployed minimal ERC-20 tokens, the attacker can cheaply construct an order with enough distinct tokens that the *release* loop in `_withdraw`/`withdraw` alone exceeds the destination chain's block gas limit.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any unprivileged intent user (an "unbounded message dispatcher" analog: intents escrow path):
- **Same-chain path**: `fillOrder` calls `_withdraw` directly to pay the solver and release escrow; if the loop cannot complete within a block, the order can never be filled, and its refund path (`cancelOrder` after deadline) hits the exact same unbounded loop, permanently freezing the escrowed inputs.
- **Cross-chain path**: settlement/refund arrives via ISMP `onAccept`/`onGetResponse`, which is a required, one-shot handler invocation (`RequestKind.RedeemEscrow`/`RefundEscrow`) — if `withdraw()` cannot complete, the ISMP message delivery itself reverts every time it's retried, and the corresponding escrow on the source chain is permanently stuck (the request can time out, but timeout refund likely calls the same iterate-and-transfer routine, hitting the identical wall).
- Because the destination beneficiary/solver has no way to shrink the token list after the fact (it is fixed by the commitment hash computed at `placeOrder` time), there is no recovery path once the order is placed with an oversized token list — this is unbacked, permanent freezing of user and/or solver funds, matching the Sherlock report's "attacker can DOS and LOCK users tokens" impact class.

### Likelihood Explanation
Any user can call `placeOrder()` permissionlessly with an arbitrarily long `order.inputs` (and `order.output.assets`) array — no allowlist, no minimum amount, and no token-count validation gates this call. Constructing many minimal ERC-20 tokens (or reusing existing low-decimals/dust tokens) to pad the array is cheap and well within normal user capability, making this trivially reachable without any privileged role, aligning with the "unprivileged... intent solver" reachability requirement.

### Recommendation
Enforce a maximum number of entries in `order.inputs`, `order.output.assets`, and `order.predispatch.assets` in `placeOrder()` (e.g., a small constant like 10–20), sized so that the worst-case `_withdraw`/`withdraw` loop (transfer + storage write per token) provably fits well under the target chains' block gas limits. Apply the identical bound in both `evm/src/apps/IntentGatewayV2.sol` and `evm/tron/contracts/apps/IntentGatewayV2.sol`, and reject orders exceeding it with `InvalidInput()`.

### Proof of Concept
1. Deploy N cheap ERC-20 tokens (or reuse existing dust tokens) where N is large enough that N `safeTransfer` calls exceed the destination chain's block gas limit (e.g., N ≈ 500+ depending on gas limit and per-transfer cost).
2. Call `placeOrder()` with `order.inputs` containing N distinct `TokenInfo` entries, each with a minimal approved amount; `placeOrder()` succeeds because there is no cap on `inputsLen` ( [8](#0-7) ).
3. A solver attempts `fillOrder()` (same-chain) or the cross-chain settlement message triggers `onAccept` → `withdraw()`/`_withdraw()`. The loop over `body.tokens`/`order.inputs` ( [9](#0-8) ) consumes more gas than the block gas limit, causing the transaction to always revert regardless of gas provided.
4. The user then attempts `cancelOrder()` after `deadline` to reclaim escrow via the refund path, which invokes the same unbounded `_withdraw`/`withdraw` loop and also reverts every time — the escrowed tokens are permanently locked in the `IntentGatewayV2` contract with no way to ever release them.

    function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        _filled[body.commitment] = beneficiary;

        // redeem escrowed tokens
        uint256 len = body.tokens.length;
        for (uint256 i; i < len;) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (_orders[body.commitment][token] == 0) revert UnknownOrder();

            if (token == address(0)) {
                (bool sent,) = beneficiary.call{value: amount}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
                if (!success) revert TransferFailed();
            }

            _orders[body.commitment][token] -= amount;
            unchecked {
                ++i;
            }
        }

        // redeem tx fees
        uint256 fees = _orders[body.commitment][TRANSACTION_FEES];
        if (fees > 0) {
            address feeToken = IDispatcher(host()).feeToken();
            (bool success,) = feeToken.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, fees));
            if (!success) revert TransferFailed();
            delete _orders[body.commitment][TRANSACTION_FEES];
        }

        if (isRefund) {
            emit EscrowRefunded({commitment: body.commitment});
        } else {
            emit EscrowReleased({commitment: body.commitment});
        }
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {

            uint256 amount = body.tokens[i].amount;
