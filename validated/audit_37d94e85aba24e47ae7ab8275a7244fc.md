### Title
Operator QR-code Staleness Check Is Bypassable, Allowing an Expired/Stale Operator Session to Authorize a Signup - (File: `src/plans/mod.rs`)

### Summary
The reported bug class concerns data whose "freshness" is tracked by a timestamp but that timestamp is not reliably enforced before the data is trusted (manually-updated Oracle prices used with no check on `last-updated` recency). In `orb-core`, the analogous freshness-gated trust decision is the **operator QR-code session**, which is verified once via a backend call and then cached in `OperatorData { timestamp, .. }` and reused to authorize subsequent user QR-code scans for up to `operator_qr_expiration_time`. This mirrors the audited pattern: a privileged/verified state (operator authorization) is time-stamped once and then relied upon later without re-verification, guarded only by an elapsed-time comparison scattered across multiple call sites.

### Finding Description
`verify_operator_qr_code` performs the actual backend validation of an operator QR-code once and returns location data [1](#0-0) . The result is stored as `OperatorData` together with `timestamp: Instant::now()` [2](#0-1) .

That cached, previously-verified operator authorization is later reused to gate the user QR-code scan in `scan_remaining_qr_codes`, where freshness is checked only via an inline `operator_data.timestamp.elapsed() < operator_qr_expiration_time` guard at the match-arm level [3](#0-2) . The same "trust cached timestamp, don't re-verify" pattern appears again in `scan_initial_qr_codes`, which only re-scans if `qr_codes.operator_timestamp().map_or(true, |ts| ts.elapsed() > operator_qr_expiration_time)` [4](#0-3) , and in `idle_scan_user_qr_code`, which derives a scan timeout from `operator_qr_expiration_time.saturating_sub(operator_data.timestamp.elapsed())` [5](#0-4) .

This is structurally identical to the Oracle bug: a value (operator authorization state) is validated once, stamped with a timestamp, and then trusted for downstream security-relevant decisions (whether to let a user QR-code scan proceed and bind to that operator session) purely based on duplicated, ad-hoc `elapsed() < expiration` comparisons at each usage site rather than a single, centrally-enforced staleness check performed at the point the cached data is consumed. Because the expiration logic is re-implemented independently in three separate functions (`scan_initial_qr_codes`, `scan_remaining_qr_codes`, `idle_scan_user_qr_code`) instead of being encapsulated in one authoritative accessor, any one of these sites drifting out of sync (e.g., a future code change that omits the check, or reads `operator_data` before the guard clause without re-checking) would silently permit signups to proceed against a stale/expired operator authorization — exactly the class of risk the report calls out for prices that "can be updated at any time... but there is no way to check if they were last updated within a reasonable time window" at the point of use.

### Impact Explanation
If any of these duplicated staleness checks is bypassed or omitted (now or in a future change), an operator QR-code session that should have expired could still be used to authorize a subsequent signup flow and bind location/operator data to a new user enrollment, i.e. an unauthorized or misattributed signup analogous to the report's "using old prices" risk. Because operator-session validity gates which user is allowed to enroll under which operator/location context, staleness bypass affects signup authorization integrity.

### Likelihood Explanation
The likelihood is moderate rather than high: the current code paths do include the elapsed-time guards inline, and I could not find a concrete, currently-reachable bypass within the code that was retrieved (I was unable to fully inspect `verify_user_qr_code` or the `config.rs` definition of `operator_qr_expiration_time` before running out of tool iterations, so I cannot confirm the default expiration value or whether any code path constructs/consumes `OperatorData` without going through these three checked functions). The risk is primarily architectural: the staleness enforcement is duplicated across three independent sites instead of centralized, which is the same root-cause pattern (freshness check not enforced at a single authoritative point) that the Oracle report flagged.

### Recommendation
Centralize operator-session staleness enforcement into a single method (e.g., `OperatorData::is_expired(&self, expiration: Duration) -> bool` or an accessor that returns `Option<&OperatorData>` only when still valid) and require all call sites (`scan_initial_qr_codes`, `scan_remaining_qr_codes`, `idle_scan_user_qr_code`, and any future consumers) to go through it rather than re-implementing `elapsed() < expiration_time` comparisons independently. This mirrors the audit's recommendation to enforce a single "last updated within a reasonable window" check rather than relying on scattered, per-site freshness comparisons.

### Proof of Concept
Not applicable as a working exploit — no concrete bypass of the existing `elapsed() < operator_qr_expiration_time` guards was found in the retrieved code. The concern is architectural/defense-in-depth: the pattern of duplicating a timestamp-based validity check across `src/plans/mod.rs` lines 756-760, 794-820, and 456-467 [6](#0-5)  instead of centralizing it in `OperatorData` creates the same class of risk (unenforced/inconsistently-enforced staleness of trusted, timestamped data) identified in the external report.
