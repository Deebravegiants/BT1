### Title
Webhook shop-domain identity not bound to HMAC signature enables cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by HMAC-validating only the raw request body, while the `shop` (tenant) identifier used downstream by the handler is read from an HTTP header that is never included in the signed material. An attacker who controls their own shop (a trivial, unprivileged action — installing the public app) can obtain a Shopify-signed `(body, hmac)` pair for their own store, then replay it to the app's public webhook endpoint with the `x-shopify-shop-domain`/`shopify-shop-domain` header swapped to any victim shop domain. The gem's `HmacValidator.validate` will accept the forged request because the signature check never covers the `shop` field.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is read straight from the (attacker-controlled) HTTP header, entirely independent of the signed payload: [2](#0-1) 

`HmacValidator.validate` computes and compares the HMAC purely against `verifiable_query.to_signable_string` (the body) and the app's shared `api_secret_key`: [3](#0-2) 

`Webhooks::Registry.process` validates only this body-bound HMAC, then forwards `request.shop` (the unauthenticated header) straight into the handler as the tenant identity for the event: [4](#0-3) 

The `api_secret_key` used to compute the webhook HMAC is a single app-level secret shared across every shop that installs the app — it is not shop-specific. Consequently, an attacker who installs the app on a shop they control receives real, correctly-signed webhooks `(body, hmac)` for their own store. Because `shop` is never part of the signed string, the attacker can replay that exact `(body, hmac)` pair against the app's public webhook endpoint while substituting the `shop-domain` header for any other merchant's `*.myshopify.com` domain. `HmacValidator.validate` still returns `true` (same secret, same body), so `Registry.process` dispatches the handler with `shop` set to the victim's domain even though the payload never originated from, or concerns, that shop.

This breaks the identity binding: `shop_verified_by_signature == shop_used_by_handler` does not hold — the signature verifies only the body, but the handler trusts the header as the tenant key.

### Impact Explanation
This is a cross-tenant access vector: a handler that looks up a session/shop record keyed by `request.shop` (the documented, intended usage of `WebhookMetadata#shop`) can be made to act on/impersonate a victim shop it was never authorized to touch, using data supplied by an attacker who merely installed the app on their own store. Depending on the webhook topic (e.g. `app/uninstalled`, `shop/redact`, `customers/data_request`, or any custom business webhook the host app subscribes to), this can trigger destructive or data-exfiltrating actions against an arbitrary victim tenant — satisfying the Critical "cross-tenant access" bar.

### Likelihood Explanation
Exploitation requires only: (1) installing the target app on a shop the attacker controls (public, unprivileged action for any public Shopify app), (2) capturing one legitimate webhook delivery to that shop, and (3) POSTing the same body+HMAC to the app's public webhook URL with a modified `shop-domain` header. No access token, `api_secret_key`, or privileged account is needed. The webhook endpoint is public by design (Shopify's delivery infrastructure must reach it over the internet), so nothing prevents an attacker from calling it directly.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header into the value that is authenticated, not just the raw body — e.g., have `Registry.process` (or `Request`) verify that the `shop-domain` header corresponds to a shop record/session already established for this specific webhook subscription (Shopify's admin API can be used to confirm the shop owns the `webhook_id`), or require host apps to cross-check `request.shop` against an independently stored expected shop for that `webhook_id`/subscription before trusting it. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be used as a sole tenant key without additional verification.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and lets it deliver a real webhook, e.g. for topic `orders/create`, capturing:
   - raw body `B`
   - header `x-shopify-hmac-sha256: H` (valid HMAC of `B` under the app's `api_secret_key`)
2. Attacker crafts a new HTTP POST to the app's public webhook endpoint with:
   - body: `B` (unchanged)
   - header `x-shopify-hmac-sha256: H` (unchanged)
   - header `x-shopify-shop-domain: victim-shop.myshopify.com` (modified)
   - header `x-shopify-topic`, `x-shopify-webhook-id` optionally modified as desired
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `to_signable_string` only covers `B`.
4. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and processes it as if `victim-shop` sent this event, even though it never did. [4](#0-3) [5](#0-4)

module ShopifyAPI
  module Webhooks
    class Request
      extend T::Sig
      include Utils::VerifiableQuery

      sig { override.returns(String) }
      def hmac
        Digest.hexencode(Base64.decode64(T.cast(shopify_header("hmac-sha256"), String)))
      end

      sig { returns(String) }
      def topic
        T.cast(shopify_header("topic"), String)
      end

      sig { returns(String) }
      def shop
        T.cast(shopify_header("shop-domain"), String)
      end

      sig { returns(String) }
      def api_version
        T.cast(shopify_header("api-version"), String)
      end

      sig { returns(String) }
      def webhook_id
        T.cast(shopify_header("webhook-id"), String)
      end

      sig { override.returns(String) }
      def to_signable_string
        @raw_body
      end

      sig { returns(T::Hash[String, T.untyped]) }
      def parsed_body
        JSON.parse(@raw_body)
      end

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
