### Title

Unvalidated swap routes can poison the caller’s authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary

`swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral` pass caller-controlled opaque route bytes to the configured router while running under the account caller’s root authorization. A malicious route hop can therefore execute arbitrary contract code below that authorization and request unrelated token transfers from the caller; if the caller signs the simulated authorization tree, those transfers execute even when the requested swap itself remains economically valid.

### Finding Description

`swap_collateral` authenticates `caller` and verifies that the caller owns or delegates the target account, but accepts `swap` as uninterpreted `Bytes`. [1](#0-0) 

The shared swap helper only snapshots the controller’s input and output token balances, authorizes the exact controller-to-router input transfer, and invokes `execute_strategy` with the attacker-influenced `swap` payload. [2](#0-1) 

After router execution, the controller checks only that the router did not overspend the controller-held input and that positive output was received; it does not constrain which contracts or authorization children the route may introduce. [3](#0-2) 

The route venue is not constrained to trusted pool code: a hop can invoke an arbitrary contract, which can in turn invoke `token.transfer(caller, attacker, amount)`. Soroban simulation records that nested transfer under the caller’s original authorization entry, and enforcing mode accepts it if the caller signs the resulting tree. [4](#0-3) 

This is the direct analog of the path-traversal bug class: attacker-controlled routing input escapes the intended swap path and reaches an unintended protected resource—the caller’s authorization for unrelated token transfers.

### Impact Explanation

A malicious route can steal tokens from a user’s wallet that are unrelated to the swap and outside the lending protocol’s accounting. The routed collateral amount, measured swap output, and final account risk can all remain valid, so the protocol-side balance checks do not bound the additional wallet transfer.

The impact is theft of user funds up to the victim’s balance of any token whose transfer can be represented in the signed authorization tree. The same exposure applies to controller strategies that accept route bytes, including `swap_collateral`, `swap_debt`, `multiply`, and `repay_debt_with_collateral`. [5](#0-4) 

### Likelihood Explanation

The attack requires the victim to submit or sign a malicious route and to approve the poisoned authorization tree produced by simulation. That precondition is plausible when routes are generated by a frontend, solver, aggregator response, or other off-chain route provider rather than independently decoded by the wallet.

The attacker does not need protocol privileges, leaked keys, compromised governance, or control of the configured router. They only need to supply a route that causes an unlisted hop contract to request a transfer from the caller while returning enough output for the controller’s post-conditions to pass.

### Recommendation

Constrain strategy routing so route-selected contracts cannot introduce unrelated authorization requirements. At minimum, simulate and display the complete authorization tree and reject any child invocation other than the expected controller-to-router input transfer; preferably enforce an allowlist of route venues or a router ABI that cannot invoke caller-selected arbitrary contracts. Client-side mitigation is still necessary because the controller cannot distinguish an intentionally approved nested transfer from a malicious one after the signature is supplied.

### Proof of Concept

1. Alice owns a lending account with USDC collateral and also holds an unrelated wallet token.
2. An attacker deploys a hop contract whose swap function calls:

   ```rust
   token::Client::new(&env, &wallet_token)
       .transfer(&alice, &attacker, &alice_balance);
   ```

   The analogous test hop performs exactly this caller-funded transfer. [6](#0-5) 

3. The attacker encodes a route naming that hop contract and causes Alice to invoke:

   ```text
   controller.swap_collateral(
       caller = Alice,
       account_id = AliceAccount,
       current = USDC hub asset,
       amount = swap input,
       new = ETH hub asset,
       swap = malicious encoded route,
   )
   ```

   `swap_collateral` authorizes Alice and reaches the shared router execution helper. [1](#0-0) 

4. The helper grants the router the exact controller-held input transfer and calls `execute_strategy(controller, amount_in, malicious_route)`. [7](#0-6) 

5. The malicious hop requests `wallet_token.transfer(Alice, attacker, AliceBalance)`. Simulation attaches that request as a child of Alice’s `swap_collateral` authorization. [8](#0-7) 

6. If Alice signs the returned tree, the unrelated wallet-token transfer executes while the swap can still return fair output and satisfy the controller’s positive-output and account-risk checks. [9](#0-8)
