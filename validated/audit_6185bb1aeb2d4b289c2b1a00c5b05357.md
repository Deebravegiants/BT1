### Title
Webhook shop identity spoofing via HMAC that only covers the raw body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw HTTP body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and then handed to the app's webhook handler as trusted tenant-identifying data. This breaks the binding: `hmac_valid(raw_body) == true` is treated as if it implied `shop_header == actual_source_shop`, but the two are independent.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are all pulled straight from HTTP headers with no cryptographic tie to the HMAC: [2](#0-1) 

`Registry.process` validates only the body/HMAC pair and, once that passes, forwards the caller-supplied `request.shop` verbatim into `WebhookMetadata`, which is the value app developers are expected to use to resolve the tenant (session/store) the event belongs to: [3](#0-2) 

`HmacValidator.validate` confirms only that `hexdigest(secret, raw_body)` matches the supplied HMAC — it never touches the shop header: [4](#0-3) 

The identity-binding equality the library implicitly relies on is:
`valid_hmac(raw_body) == true` should imply `shop_header == originating_shop`, but the code only guarantees the former, not the latter, because `shop-domain` is not part of `to_signable_string`.

### Impact Explanation
An unprivileged internet user who can obtain one legitimately-signed `(raw_body, hmac)` pair for a given topic (e.g., by installing/uninstalling the target app on their own free/dev shop, which is a normal unprivileged action, and capturing the webhook Shopify sends them) can replay that exact body to the app's public webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header pointing at a victim shop. Because the HMAC only covers the body, the forged request still passes `HmacValidator.validate`, and `Registry.process` calls the handler with `shop` set to the attacker-chosen victim domain. Any host application that uses `WebhookMetadata#shop` (the documented, intended way to know "which shop this event is for") to select per-tenant records — e.g. to invalidate/delete a session on `app/uninstalled`, or to write orders/customers data — will act on the wrong tenant's data. This is a cross-tenant access/integrity issue.

### Likelihood Explanation
Medium-to-High: webhook endpoints are public HTTP endpoints reachable without any Shopify session, access token, or `api_secret_key` knowledge from the attacker. The only prerequisite is capturing one valid signed payload for a topic whose body content is attacker-influenceable or generic enough to matter (e.g., `app/uninstalled` has a near-static body), which any merchant who installs the app can obtain for their own shop.

### Recommendation
Include the identity-bearing headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable material, or at minimum require the host application to compare `request.shop` against the shop stored in its own session/tenant record before trusting it — and document this requirement prominently, since the library currently exposes `request.shop` as if it were validated.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and then uninstalls it, causing Shopify to POST a real `app/uninstalled` webhook with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for secret `S`) to the app's webhook endpoint.
2. Attacker captures `(B, H)` (e.g., via a proxy they control, since the webhook is delivered to their own app installation callback if they run their own receiver, or via any endpoint they control that logs the raw request).
3. Attacker crafts a new HTTP POST to the app's real webhook endpoint with the same body `B` and the same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H`:
`OpenSSL.secure_compare(compute_signature(B, S), H) == true`
5. The app's handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and performs tenant-scoped logic (e.g., deleting `victim-shop`'s stored session/access token) even though the event never originated from Shopify for that shop.
