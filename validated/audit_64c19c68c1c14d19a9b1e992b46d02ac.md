### Title
Liquidation can accept debt repayment after all collateral has been seized - ([File: contracts/controller/src/positions/liquidation/plan.rs])

### Summary
`liquidate` can execute against an unhealthy account whose total collateral is zero, take the liquidator’s debt tokens, and award no collateral in return. `calculate_seized_collateral` returns an empty seizure list and zero `unbacked_usd` when `total_collateral <= 0`; because `unbacked_usd` is zero, `build_liquidation_plan` does not clear the planned repayment, and execution proceeds to pull the repayment before applying an empty seizure batch. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
Any account with outstanding debt and zero risk collateral remains liquidatable because the planner only requires `health_factor < Wad::ONE`. [4](#0-3) 

For such an account, `calculate_seized_collateral` immediately returns an empty vector and `Wad::ZERO` as `unbacked_usd`. [1](#0-0) 

The subsequent remediation in `build_liquidation_plan` only releases the repayment when `unbacked_usd > Wad::ZERO` and no collateral was seized. Because the zero-collateral branch reports zero, that condition is false and the positive repayment plan survives. [2](#0-1) 

`LiquidationPlan::validate` iterates over `self.seized` but does not require it to be non-empty, so an empty seizure plan is accepted. [5](#0-4) 

Execution then transfers each planned or offered debt amount from `liquidator` to the pool and submits the corresponding repayment actions. [6](#0-5) 

Only after repayment does `process_liquidation` apply seizures; in `SeizeMode::Transfer`, an empty seizure vector produces an empty withdrawal batch, so no collateral is paid to the liquidator. [7](#0-6) [8](#0-7) 

### Impact Explanation
A liquidator can lose the full amount of a submitted repayment while receiving zero collateral. The debt is nevertheless reduced by the pool repayment, meaning the liquidator donates funds to the borrower/protocol rather than purchasing collateral. [9](#0-8) 

This is especially relevant to liquidation races: a liquidator can estimate a profitable liquidation against collateral, but a competing transaction can first seize all remaining collateral while leaving residual bad debt. The first liquidator’s transaction still executes against the now-zero-collateral account and pays debt without an asset transfer back. [10](#0-9) [3](#0-2) 

The affected funds are user-owned debt tokens voluntarily authorized for liquidation, so this is theft/loss of user funds rather than protocol insolvency; severity is bounded by the repayment amount and requires a zero-collateral residual-debt state or a liquidation race. [11](#0-10) [12](#0-11) 

### Likelihood Explanation
A residual-debt, zero-collateral account is a natural consequence of insolvent liquidations: the insolvency path can seize all collateral while repaying only the collateral-backed portion of debt. [13](#0-12) [14](#0-13) 

No privileged action is needed to trigger the loss: `liquidate` is permissionless and only requires the liquidator’s authorization. [15](#0-14) 

The main prerequisite is that the target account reach zero total collateral while retaining debt, or that the liquidator’s transaction land after a competing liquidation has produced that state. [4](#0-3) [10](#0-9) 

### Recommendation
Reject a liquidation whose normalized repayment remains positive while `seized_collaterals` is empty. The zero-collateral branch should either report the entire `repayment.repay_usd` as unbacked so it is released, or the plan should explicitly revert when `seized_collaterals.is_empty() && repayment.repay_usd > Wad::ZERO`. [2](#0-1) [1](#0-0) 

### Proof of Concept
1. Create a borrow position that becomes severely unhealthy, with collateral worth less than debt.
2. A first liquidator performs a liquidation that seizes all collateral and repays only the collateral-backed amount, leaving residual debt and zero collateral.
3. A second liquidator calls `Controller::liquidate(liquidator, account_id, debt_payments, SeizeMode::Transfer)` with a positive payment on the residual debt.
4. `build_liquidation_plan` passes the health-factor check and computes the repayment normally. [16](#0-15) 
5. `calculate_seized_collateral` returns `([], 0)`, so the empty-seizure cleanup is skipped because `unbacked_usd == 0`. [10](#0-9) [2](#0-1) 
6. `apply_liquidation_repayments` transfers the liquidator’s debt tokens to the pool and repays the target debt. [17](#0-16) 
7. `apply_liquidation_seizures` receives an empty vector, builds an empty withdrawal batch, and the liquidator receives no collateral. [7](#0-6) [18](#0-17)

pub(crate) fn apply_liquidation_seizures(
    env: &Env,
    liquidator: &Address,
    account: &mut Account,
    seized: &Vec<SeizeEntry>,
    cache: &mut Context,
) {
    let mut entries: Vec<PoolWithdrawEntry> = Vec::new(env);
    for entry in seized.iter() {
        enforce_spoke_asset_flags(
            env,
            cache,
            account.spoke_id,
            &entry.hub_asset,
            FreezePolicy::SeizureLeg,
        );

        let position: AccountPosition =
            (&expect_invariant(env, account.supply_positions.get(entry.hub_asset.clone()))).into();
        entries.push_back(PoolWithdrawEntry {
            action: make_pool_action(&position, entry.amount, entry.hub_asset),
            protocol_fee: entry.protocol_fee,
        });
    }
    apply_withdraw_batch(
        env,
        account,
        liquidator,
        WithdrawKind::Liquidation,
        events::PositionAction::LiqSeize,
        &entries,
        cache,
    );
