The bug-class hint (a decision computed from data not bound by the authenticating signature) maps onto a genuine issue in the webhook processing path: the shop identity used for tenant routing is never covered by the HMAC that authenticates the webhook.### Title
Webhook shop identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, but that validator only verifies the raw request body against the shared `api_secret_key`. The `shop-domain` header — which is used unauthenticated as the tenant identity passed to the app's webhook handler — is never part of the signed material. This breaks the intended binding `shop authenticated by HMAC == shop delivered to handler`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`Utils::HmacValidator.validate` computes an HMAC over `verifiable_query.to_signable_string` (the raw body only) and compares it to the `hmac` header: [2](#0-1) 

`Registry.process` treats this body-only HMAC check as sufficient authentication for the *entire* request, then forwards the attacker-controllable `request.shop` header, unauthenticated, straight into the handler call as the tenant identity: [3](#0-2) 

Critically, `api_secret_key` (the HMAC key) is a single, app-wide secret shared by **every** shop that installs the app — it is not per-tenant. Any internet user can freely create their own Shopify development store, install the target (public) app on it, and thereby receive real, validly-HMAC-signed webhook deliveries for their own shop, computed with the very same app-wide secret. Because the `shop-domain` header is excluded from the signed bytes, that same attacker can capture one legitimately signed `(raw_body, hmac)` pair from their own store's webhook delivery, then replay it directly to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `Utils::HmacValidator.validate` will still succeed (it never looked at the header), and `Registry.process` will dispatch to the app's handler with `WebhookMetadata.new(shop: <victim-domain>, body: <attacker's own webhook body>, ...)`.

This is precisely the bug class described in the report: a value ("shop" identity) is *acted upon* by the trust decision but is not itself *covered by the HMAC* that produced that trust decision — analogous to using an edge price that was not yet updated by the very check meant to validate it.

### Impact Explanation
This is a cross-tenant integrity/impersonation issue: the host application receives a validly authenticated payload but attributes it to whichever shop the attacker names in an unauthenticated header. Any app that uses `WebhookMetadata#shop` to determine which tenant's records to update (order/product/customer data upsert, deletion, GDPR redaction flows, billing state changes, etc.) can be made to apply attacker-supplied webhook data under a victim tenant's identity, i.e., cross-tenant data corruption/injection, satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is high for any deployed multi-tenant app that is publicly installable (the normal Shopify app-store distribution model): the attacker only needs (1) a free store to install the target app on and receive one legitimate webhook, and (2) the ability to POST directly to the app's public webhook endpoint with a modified `shop-domain` header — both trivially available to any unprivileged internet user, requiring no leaked credentials, no access token, and no `api_secret_key` disclosure.

### Recommendation
Bind the shop identity to the authenticated payload before trusting it:
- Include the `shop-domain` (and ideally `topic`, `webhook-id`, `api-version`) header values in the signable string that is HMAC-verified in `ShopifyAPI::Webhooks::Request#to_signable_string`, matching them against a canonicalized form of the actual headers, or
- After HMAC validation, cross-check `request.shop` against an expected/registered shop context (e.g., verify the shop is a known installed tenant) before passing it to `WebhookMetadata`, and document that host apps must not treat `shop` alone as authenticated unless the gem binds it.

### Proof of Concept
1. Attacker creates a free Shopify development store and installs the target public app; the app registers a webhook (e.g. `orders/create`) pointing at its own endpoint.
2. Shopify delivers a webhook to the app for the attacker's own store:
   - Body: `{"id":1,...}` (attacker fully controls contents of their own store's order)
   - Headers: `x-shopify-hmac-sha256: <valid HMAC over body>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`.
3. Attacker captures this exact `(raw_body, hmac)` pair.
4. Attacker sends a POST directly to the same app's public webhook URL, keeping `raw_body` and `x-shopify-hmac-sha256` identical, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` succeeds because it only checks `raw_body` against the shared `api_secret_key`: [3](#0-2) 
6. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` and the attacker's chosen body, causing the host app to process/store attacker data under the victim tenant.
