### Title
Webhook HMAC covers only the raw body, not the `shop-domain` header, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` authenticates nothing but the JSON payload bytes. The `shop` (from the `x-shopify-shop-domain` header), `topic`, and `webhook_id` are read straight from unauthenticated headers and handed to the app's webhook handler as trusted tenant-identifying data. Because the webhook signing secret (`Context.api_secret_key`) is the same app-wide secret shared across every merchant that installs the app, any merchant who legitimately installs the app can capture a validly-HMAC'd `(body, hmac)` pair from their own store's webhook traffic and replay it with a forged `x-shopify-shop-domain` header pointing at a victim store. `Registry.process` will accept it as authentic.

### Finding Description
`Registry.process` is the sole authenticity gate for inbound webhooks: [1](#0-0) 

It only calls `Utils::HmacValidator.validate(request)`, which recomputes an HMAC over `request.to_signable_string` and constant-time-compares it to the `hmac` extracted from the `hmac-sha256` header: [2](#0-1) 

But `Request#to_signable_string` binds the signature to the body only: [3](#0-2) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are never part of the signed bytes: [4](#0-3) 

After `Utils::HmacValidator.validate` passes, `Registry.process` constructs the `WebhookMetadata` handed to the app's handler using the unauthenticated `request.shop`: [5](#0-4) 

The identity binding that should hold is: `shop that authorized/signed the webhook == shop attributed to the data by the handler`. Because only the body is signed, and the app's `api_secret_key` is identical for every shop that installs the app, this binding is broken: the HMAC only proves "some install of this app produced this exact JSON body", not "this specific shop produced it." Any merchant of a multi-tenant app can capture their own legitimate `(raw_body, hmac)` pair (e.g. from a webhook with a body they control or can predict — many webhook topics, like `app/uninstalled` or a custom `carts/update` with attacker-chosen cart data, allow the merchant to influence or observe the exact bytes) and resend it to the app's webhook endpoint with `x-shopify-shop-domain` set to a victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it never looks at that header, and the handler executes with `WebhookMetadata#shop` = victim's shop.

This is directly analogous to the reported issue: `SafeTransferLib` only checks a transfer succeeded but not that the target had code, letting `_balances[asset][...]` be credited using data that logically requires an out-of-band property (code existence) which was never checked; here, `HmacValidator` only checks that the body bytes are authentic but not that the `shop` attribute — which the handler uses to key merchant-specific state — was ever bound to that signature.

### Impact Explanation
This breaks the shop-authentication boundary between tenants of the same app (cross-tenant access), one of the explicitly allowed High/Critical impacts. Any app that uses `WebhookMetadata#shop` to decide which merchant's records to update, uninstall, purge, or reset (a normal and expected usage pattern for `orders/create`, `app/uninstalled`, `shop/redact`, `customers/data_request`, etc.) can be tricked into performing that action against an arbitrary victim shop, purely because the low-privilege attacker (any merchant who installed the app) knows the shared app secret's HMAC output for a body they legitimately received.

### Likelihood Explanation
Any user who installs a public/multi-tenant Shopify app becomes a valid "webhook sender" for that app's shared secret. Capturing one's own valid `(raw_body, hmac)` pair requires no privilege beyond having the app installed on one's own store, and replaying it to the app's public webhook endpoint with a modified header is trivial (no cryptographic secret needed). This is a realistic unprivileged-attacker path with a low bar to exploitation, contingent only on the host app trusting `WebhookMetadata#shop` for tenant-scoped actions, which is the gem's intended/documented usage.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values as part of the HMAC-signed content, or independently bind them: e.g., verify the `shop` value against a store the app has an active session/install record for using an independently-authenticated channel (not header-derived), or require the app to look up webhook subscriptions per-shop with per-shop derived secrets. At minimum, document prominently that `Request#shop` is not covered by the HMAC and must not be trusted for tenant attribution without an additional check (e.g., cross-referencing against a known list of installed shops before dispatching to per-shop logic).

### Proof of Concept
```ruby
# Attacker legitimately installs the app on attacker-shop.myshopify.com
# and receives (or triggers, for topics whose body they control) a webhook:
raw_body = '{"id":1}'
valid_hmac = OpenSSL::HMAC.digest(
  OpenSSL::Digest.new("sha256"),
  ShopifyAPI::Context.api_secret_key,  # shared app secret, same for every shop
  raw_body,
)

# Attacker replays the exact same body/hmac but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => passes HmacValidator.validate (only checks raw_body)
# => handler receives WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
``` [3](#0-2) [6](#0-5)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
