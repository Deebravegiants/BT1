### Title
Unbounded in-memory bid cache in `pallet-intents-coprocessor` RPC service allows memory exhaustion via mempool-observed `place_bid` extrinsics - (File: modules/pallets/intents-coprocessor/rpc/src/lib.rs)

### Summary
The Hyperbridge intents-coprocessor RPC service maintains an in-memory `BidCache` populated by watching the transaction pool for `place_bid` extrinsics, so that bids are visible over RPC before block inclusion. The cache is unbounded in the number of distinct order commitments tracked, the number of bids per commitment, and the size of the cached payloads, and is only pruned on a time-based TTL sweep, not a size cap — mirroring the Mattermost `/api/v4/redirect_location` bug class (CWE-400, caching large/unbounded items from attacker-controlled input).

### Finding Description
`BidCache::insert` stores an entry into a `HashMap<H256, OrderBids>` keyed by an attacker-supplied `commitment`, where each `OrderBids` holds an unbounded `Vec<BidEntry>` of `(filler, user_op)` byte vectors: [1](#0-0) 

This insert path is driven entirely from `run_bid_watcher`, which listens to the node's transaction-pool `import_notification_stream` and decodes any `ready_transaction` matching `place_bid` via `extract_bid`, then unconditionally calls `bid_cache.insert(commitment, filler, user_op)` for every such transaction it observes in the mempool — before the transaction is ever included in a block: [2](#0-1) 

The only cleanup mechanism is a periodic TTL sweep (`remove_expired`), which removes an entire `OrderBids` bucket only once its `first_seen` timestamp exceeds `ttl` — there is no cap on the number of distinct `commitment` keys, no cap on the number of `filler`/`user_op` entries per commitment, and no bound on the byte size of `filler` or `user_op`: [3](#0-2) 

Because `commitment`, `filler`, and `user_op` are all attacker-controlled fields of a signed `place_bid` extrinsic, and the cache is fed purely from transactions reaching "ready" status in the mempool (not from finalized/executed state), an unprivileged party can flood the pool with `place_bid` extrinsics carrying many distinct (fabricated) commitments and large `user_op` payloads. Each such transaction that becomes "ready" in any RPC-serving node's pool grows the in-memory cache, with no upper bound on total memory consumed and no requirement that the referenced order/commitment actually exist on-chain.

### Impact Explanation
This is a memory-exhaustion (resource consumption) vulnerability affecting any relayer/RPC node running the intents-coprocessor bid-watcher service, directly analogous to the Mattermost redirect_location caching bug (CWE-400, Availability impact). An attacker who can get transactions into a node's ready transaction pool — including nodes gossip-connected in the network, not necessarily the attacker's own peer — can drive unbounded heap growth on that node's RPC process, leading to denial of service for the intent-bidding RPC surface (`intents_getBidsForOrder`, `intents_subscribeBids`) and potentially the whole node process via OOM. This can disrupt fillers/bidders relying on this RPC for sub-second bid discovery, degrading the intents/solver ecosystem's liveness.

### Likelihood Explanation
Reaching this requires only submitting signed `place_bid` extrinsics that pass normal transaction-pool validation (valid signature, nonce, and fee payment) — no privileged role, governance, or admin access is needed. The attacker does not need the referenced `commitment` to correspond to a real order, nor does the bid need to ever be included in a block; simply entering the "ready" pool on a node running `run_bid_watcher` triggers a cache insert. Economic cost is limited to normal transaction fees (scaling with payload size and any existential deposit/nonce requirements), which is a real but not necessarily prohibitive cost for a sustained memory-exhaustion attack, particularly using many distinct signer accounts or large `user_op` payloads per transaction.

### Recommendation
- Bound `BidCache` by a maximum total size (bytes) and/or maximum number of distinct commitments and maximum bids per commitment, evicting oldest/least-relevant entries (e.g., LRU) once the cap is reached, in addition to the existing TTL sweep.
- Bound the size of `filler` and `user_op` accepted into the cache (reject/truncate oversized payloads before insertion), ideally mirroring an on-chain bound (e.g., a `BoundedVec` max length) enforced for the `place_bid` call itself so the mempool-observed data cannot exceed what will ever be valid on-chain.
- Consider validating that a `place_bid` transaction's `commitment` corresponds to a known/pending order before caching it, to prevent cache pollution with fabricated commitments.

### Proof of Concept
1. Deploy/observe a node running `run_bid_watcher` for `pallet-intents-coprocessor` alongside its RPC service.
2. From an unprivileged account (or many funded accounts), submit a stream of signed `place_bid(commitment, user_op)` extrinsics where `commitment` is a freshly randomized `H256` for each transaction (no real corresponding order) and `user_op` is a large byte vector.
3. Each transaction that becomes "ready" in the node's transaction pool triggers `extract_bid` + `bid_cache.insert` in [4](#0-3) , adding a new unbounded `HashMap` entry.
4. Repeating this at a rate faster than the `cleanup_interval` TTL sweep, or simply persisting entries within the TTL window across many distinct commitments, grows `BidCache`'s memory footprint without bound, as no size or count cap exists in `insert`/`remove_expired` [5](#0-4) .

	pub fn insert(
		&self,
		commitment: H256,
		filler: Vec<u8>,
		user_op: Vec<u8>,
	) -> Result<(), String> {
		let entry = BidEntry { filler: filler.clone(), user_op };

		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		let order = bids
			.entry(commitment)
			.or_insert_with(|| OrderBids { first_seen: Instant::now(), entries: Vec::new() });
		if let Some(existing) = order.entries.iter_mut().find(|e| e.filler == filler) {
			*existing = entry;
		} else {
			order.entries.push(entry);
		}
		Ok(())
	}

	pub fn get_bids(&self, commitment: &H256) -> Result<BTreeSet<RpcBidInfo>, String> {
		let bids = self.bids.read().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		Ok(bids
			.get(commitment)
			.map(|order| {
				order
					.entries
					.iter()
					.map(|e| RpcBidInfo {
						commitment: *commitment,
						filler: e.filler.clone(),
						user_op: e.user_op.clone(),
					})
					.collect()
			})
			.unwrap_or_default())
	}

	pub fn remove_expired(&self) -> Result<(), String> {
		let now = Instant::now();
		let mut bids = self.bids.write().map_err(|e| format!("BidCache lock poisoned: {e}"))?;
		bids.retain(|_commitment, order| now.duration_since(order.first_seen) < self.ttl);
		Ok(())
	}
}
