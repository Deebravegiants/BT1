## Finding

Shopify webhook requests bind the HMAC signature to the **raw body only**, not to the `shop` (or `topic`/`webhook-id`) headers that the library extracts and hands to application webhook handlers. An unprivileged attacker who can obtain any one valid `(raw_body, hmac)` pair (trivially available — e.g. from their own store's webhooks, which they legitimately receive) can replay that exact body/HMAC to a target app's webhook endpoint while forging the `X-Shopify-Shop-Domain` header to any other shop domain. The signature still validates, and the registered handler is invoked believing the payload originated from the spoofed shop.

### Title
Webhook `shop` identity is unauthenticated (not covered by HMAC), enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, so `Utils::HmacValidator.validate` only proves that the *body* bytes were HMAC-signed by Shopify — it proves nothing about the `shop`, `topic`, or `webhook-id` headers that `Registry.process` passes straight into the application's handler.

### Finding Description
`Webhooks::Registry.process` validates a webhook purely via `Utils::HmacValidator.validate(request)`: [1](#0-0) 

The HMAC check calls `verifiable_query.to_signable_string`, and for webhooks that method returns only `@raw_body`: [2](#0-1) 

`request.shop`, however, is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, with no cryptographic link to the signature: [3](#0-2) 

The mismatched binding is: **`hmac` authenticates `raw_body`**, but **the app acts on `request.shop`** — these are not the same set of bytes. `Registry.process` forwards this unauthenticated `shop` value directly into the handler's `WebhookMetadata`: [1](#0-0) 

Because only the body is signed, any attacker who has access to one legitimately-signed `(raw_body, hmac)` pair (e.g., a webhook delivered to their own shop) can POST that identical body/HMAC to the target app's webhook endpoint while setting an arbitrary `shop-domain` header. `HmacValidator.validate` will succeed since the body bytes are unchanged, and the handler will process the payload as if it came from the spoofed shop.

### Impact Explanation
This breaks the identity binding between "bytes verified" and "shop acted upon." Any host application that trusts `WebhookMetadata#shop` (e.g., to look up/route to that shop's stored session, apply the payload to that shop's records, or trigger shop-scoped side effects) can be made to act on forged data attributed to a shop the attacker doesn't control — a cross-tenant confusion vector matching the Critical "cross-tenant access" category, since the attacker is manufacturing a HMAC-valid request that is misattributed to an arbitrary target shop.

### Likelihood Explanation
Exploitation requires no credentials beyond internet access and a single legitimately-signed webhook body (an attacker's own store can produce one, since `api_secret_key` need not be known — only a valid signed body/HMAC pair, which any merchant automatically receives when their own store fires a webhook of a topic the app is subscribed to). The webhook endpoint is by definition internet-reachable and unauthenticated aside from the HMAC check.

### Recommendation
Do not treat `shop`, `topic`, or `webhook-id` headers as trusted merely because the body HMAC validates. At minimum, document (and ideally enforce) that consumers must independently confirm the `shop` header corresponds to a shop with an active/expected subscription/session before acting on webhook content, or extend the signable payload/verification to bind these headers cryptographically.

### Proof of Concept
1. Attacker's own shop (`attacker.myshopify.com`) sends the app a legitimate webhook: `raw_body = '{"id":1}'`, header `x-shopify-hmac-sha256 = HMAC(secret, raw_body)`, `x-shopify-shop-domain: attacker.myshopify.com`. This passes `HmacValidator.validate`.
2. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the same endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Webhooks::Registry.process` calls `HmacValidator.validate(request)` — validates true, since only `@raw_body` is checked (`Webhooks::Request#to_signable_string` at line 36-38).
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com", body: {"id"=>1} ...)`, causing the application to treat attacker-supplied data as originating from `victim-shop.myshopify.com`.
