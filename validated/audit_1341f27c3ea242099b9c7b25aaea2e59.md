### Analysis

**Equality claimed broken:** executions of signed payload `P` == 1, regardless of how many times an unprivileged caller resubmits it via `sendSignedIntents` or nested inside `signAndSendIntent`'s `signedIntents.before`.

**Trace of the code path:**

- `IntentsSDK.sendSignedIntents` forwards `args.multiPayloads` verbatim to `intentRelayer.publishIntents` with no tracking, hashing, or dedup of `P`. [1](#0-0) 
- `IntentExecuter.signAndSendIntent` composes `signedIntents.before`/`after` MultiPayloads with the newly signed one via `composeMultiPayloads`, which simply concatenates arrays with no nonce check. [2](#0-1) 
- Both paths ultimately call `IntentRelayerPublic.publishIntents`, which forwards `signed_datas` to `solverRelay.publishIntents` over HTTP. [3](#0-2) 

Nowhere in the SDK is there per-nonce bookkeeping — that is true. However, the actual single-execution guarantee for a signed intent is not supposed to live in this client-side SDK at all. It is enforced by the receiving system: the `intents.near` contract's nonce-consumption logic (a nonce, once consumed on-chain, can never be reused by that `signer_id`), and the relay itself already treats a resubmission of an already-settled payload as a no-op success rather than a second execution:

```
if (response.reason === "already processed") {
    return Ok(response.intent_hashes);
}
``` [4](#0-3) 

This shows the system's idempotency for a given `nonce`/payload is handled by the relay/contract layer ("already processed" ⇒ same hash returned, no re-execution), not by client-side deduplication. The SDK is stateless and has no shared state across independent method invocations to detect that the same `P` was submitted twice — nor does it need to, because:

1. The attacker described already possesses `P`, i.e., they already had the authority to create and sign that exact intent themselves in an earlier session. Resubmitting their own already-signed payload is not "manipulation" of a nonce/signer/recipient they didn't control — it's simply retrying their own transaction, which any RPC client can do.
2. Whether `P` executes zero, one, or more times purely depends on the intents.near contract's nonce-consumption check, which is explicitly out of scope ("defects inside intents.near ... with no path through this repo").
3. The rules also list "trust assumptions about external RPCs, the relayer, bridge APIs" as out of scope, and `publishIntents` (the relayer/HTTP layer) is precisely where "already processed" idempotency is asserted to already exist.

There is no code path here where the SDK causes a nonce, signer, receiver, amount, or fee to diverge from what was originally signed by the user — the "equality" (single execution) is preserved by the underlying protocol's own nonce enforcement, not by anything the SDK could or should replicate.

function composeMultiPayloads(
	newPayload: MultiPayload,
	signedIntents?: SignedIntentsComposition,
): MultiPayload[] {
	if (!signedIntents) {
		return [newPayload];
	}

	const result: MultiPayload[] = [];

	// Add "before" intents first
	if (signedIntents.before && signedIntents.before.length > 0) {
		result.push(...signedIntents.before);
	}

	// Add the new payload
	result.push(newPayload);

	// Add "after" intents last
	if (signedIntents.after && signedIntents.after.length > 0) {
		result.push(...signedIntents.after);
	}

	return result;
}
