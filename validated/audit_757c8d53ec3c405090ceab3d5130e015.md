Audit Report

## Title
CORS wildcard-origin allowlist bypass via missing domain boundary check - ([File: core/services/gateway/network/httpserver.go])

## Summary
The gateway's `httpServer.isAllowedOrigin` function strips the `*.` prefix from a configured wildcard CORS origin and then checks only `strings.HasSuffix(originHost, allowedHost)`, without verifying that the match starts at a subdomain boundary (preceded by a `.`) or equals the apex domain exactly. This allows an attacker who registers a domain that merely ends with the same character sequence as the allowed apex domain (e.g. `evilremix.ethereum.org` matching a `*.remix.ethereum.org` allowlist entry) to be treated as an allowed CORS origin.

## Finding Description
`isAllowedOrigin` is the sole gate for CORS origin reflection in `handleRequest`, which runs on every request to the gateway's internet-facing HTTP server: [1](#0-0) 

The vulnerable wildcard-matching logic strips the `*.` prefix and performs a raw suffix check with no boundary enforcement: [2](#0-1) 

For a configured entry `*.remix.ethereum.org`, `allowedHost` becomes `remix.ethereum.org`. Any `originHost` ending with that literal string passes the check, regardless of whether the preceding character is a `.` — so `evilremix.ethereum.org` or `notremix.ethereum.org` (attacker-registered domains with no actual subdomain relationship to `remix.ethereum.org`) satisfy `strings.HasSuffix`. The exact-match branch above it (`originHost == allowedHost`) does not protect against this since it only covers the no-subdomain case. There is no other validation layer between this function and the header being set: [3](#0-2) 

The existing test suite exercises wildcard matching and non-matching origins as a security-relevant contract, confirming this is intended to be a strict boundary rather than a cosmetic check, and that the current implementation does not correctly enforce it.

## Impact Explanation
If an operator configures a `*.example.com` wildcard CORS entry (a supported and documented pattern to permit only trusted subdomains), an attacker who registers any domain ending in the literal string `example.com` (e.g. `evilexample.com`) will have their origin reflected in `Access-Control-Allow-Origin`, along with permissive `Access-Control-Allow-Methods`/`Access-Control-Allow-Headers`. This lets a malicious site issue cross-origin browser requests against the gateway's user-facing API that the victim's browser will treat as permitted — a concrete gateway request impersonation / CORS allowlist bypass, which maps to the in-scope "allowlist bypass" / "gateway request impersonation" impact category.

## Likelihood Explanation
Exploitation requires only: (1) an operator using a `*.` wildcard CORS entry, a documented and tested configuration option, and (2) an attacker registering an inexpensive domain that shares a suffix with the trusted apex domain. No credentials, roles, or special access are needed — any unprivileged actor with a browser and a registered domain can attempt this. This is realistic and repeatable, not merely theoretical.

## Recommendation
Enforce a proper subdomain boundary check, e.g.:
```go
if strings.HasPrefix(allowedHost, "*.") {
    suffix := allowedHost[1:] // ".example.com"
    if originHost == suffix[1:] || strings.HasSuffix(originHost, suffix) {
        return true
    }
}
```
This ensures a match only succeeds when `originHost` equals the apex domain or is separated from the suffix by a literal `.`, closing the suffix-collision bypass.

## Proof of Concept
1. Configure `HTTPServerConfig.CORSAllowedOrigins` with `["https://*.remix.ethereum.org"]` and `CORSEnabled: true`.
2. Send an HTTP request to the gateway's configured path with header `Origin: https://evilremix.ethereum.org`.
3. Trace: `isAllowedOrigin` parses `originHost = "evilremix.ethereum.org"`, `allowedHost = "remix.ethereum.org"` after stripping `*.`; `strings.HasSuffix("evilremix.ethereum.org", "remix.ethereum.org")` returns `true`.
4. Observe the response contains `Access-Control-Allow-Origin: https://evilremix.ethereum.org`, `Access-Control-Allow-Methods: GET, POST, OPTIONS`, and `Access-Control-Allow-Headers: Content-Type` — a Go unit test analogous to the existing `TestHTTPServer_HandleRequest_CORSEnabled_FromAllowedOriginWildcards` in `core/services/gateway/network/httpserver_test.go`, but using an origin such as `https://evilremix.ethereum.org` against an allowlist of `["https://*.remix.ethereum.org"]`, demonstrates the bypass.

func (s *httpServer) isAllowedOrigin(origin string) bool {
	originScheme, originHost, originPort, err := s.splitURL(origin)
	if err != nil {
		s.lggr.Debug("error parsing origin URL", err)
		return false
	}
	for _, allowed := range s.config.CORSAllowedOrigins {
		// probably better to do this once when server starts and store it in a map
		// this is an easier solution so we don't have to apply more changes to the code
		// just need to be careful when specifying allowed origins in the config file
		allowedScheme, allowedHost, allowedPort, err := s.splitURL(allowed)
		if err != nil {
			s.lggr.Debug("error parsing allowed origin URL", err)
			continue
		}
		// skip if the scheme doesn't match at all
		if originScheme != allowedScheme {
			continue
		}
		// skip if the port doesn't match at all
		if originPort != allowedPort {
			continue
		}
		// check for exact host match (e.g., remix.com)
		if originHost == allowedHost {
			return true
		}
		// check for wildcard host match (e.g., *.remix.com)
		if strings.HasPrefix(allowedHost, "*.") {
			allowedHost = allowedHost[2:]
			if strings.HasSuffix(originHost, allowedHost) {
				return true
			}
		}
	}
	return false
}
