### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb, lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw body, then unconditionally trusts the `shopify-shop-domain` (or `x-shopify-shop-domain`) header as the tenant identity forwarded to the host application's handler. Because the app's `client_secret` (`api_secret_key`) is shared across every shop that has installed the app, and the HMAC signable string is only the raw body (not the shop header), a person who has installed the app on their own store—an ordinary, unprivileged action requiring no special access—can capture one of their own genuinely-signed webhook deliveries and resend it to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop. The HMAC still validates (it only signed the body), but `WebhookMetadata.shop` now falsely claims the victim's identity.

### Finding Description
The identity binding that should hold is: **shop-domain header == a value covered by the HMAC signature**. Instead:

- `Request#to_signable_string` returns only `@raw_body` [4](#0-3) , so `HmacValidator.validate` only proves the body was signed with `Context.api_secret_key`/`old_api_secret_key`, not that the `shop`, `topic`, `webhook_id`, or `api_version` headers are authentic. [5](#0-4) 
- `Registry.process` performs exactly this check and, on success, immediately builds `WebhookMetadata` using `request.shop`, `request.topic`, etc., taken straight from unauthenticated headers. [1](#0-0) 
- `api_secret_key` is the app's single client secret, identical for every merchant/shop using the app (it is not shop-specific), so any legitimately-installed merchant already possesses valid `(raw_body, hmac)` pairs that are valid webhook signatures for the app in general, not tied to their own shop identity.
- Because the shop header sits outside the signed payload, an attacker can take a genuine webhook they legitimately received (or any other webhook body Shopify would send them, e.g. `orders/create`) and replay it to the host app's webhook endpoint with `shopify-shop-domain` rewritten to a different, victim shop domain. `Registry.process` will accept it as valid and hand `WebhookMetadata` with the spoofed `shop` value to the host application's handler.

### Impact Explanation
Host applications built on this gem are expected to use `WebhookMetadata.shop` to determine which tenant/store the webhook data belongs to (e.g., looking up that shop's session, updating that shop's local records, or acting on mandatory GDPR topics like `customers/redact`/`shop/redact`). Since the shop identity is not bound to the signature, an attacker can cause the handler to process attacker-controlled body content under a victim shop's identity — a cross-tenant access/data-integrity issue directly reachable by any user who can install the app once and observe/replay a webhook, without needing the app's `client_secret` or any privileged credential.

### Likelihood Explanation
Likely and low-effort: obtaining a valid `(body, hmac)` pair requires only installing the app on a dev/trial store (an action any internet user can perform for public/dev apps), and only requires modifying an HTTP header, not forging any cryptographic value. The `Request` class only enforces presence of the shop header, never authenticity. [6](#0-5) 

### Recommendation
Bind the shop (and ideally topic/webhook_id) into the HMAC-signed material, or otherwise validate `request.shop` against session/tenant records the app trusts before dispatching to the handler. At minimum, `to_signable_string` should not be the sole authentication signal used to trust the `shop` header; the registry should cross-check that the shop the webhook claims to be from matches a shop that legitimately installed the app (e.g., verify against a stored, previously-authorized shop from OAuth) rather than trusting the header verbatim.

### Proof of Concept
1. Install the target Shopify app on an attacker-controlled dev store; trigger any webhook topic the app subscribes to (e.g., `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Replay that exact body/HMAC pair to the app's webhook endpoint, but set `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` [4](#0-3)  — validation succeeds since the body/secret pair is unchanged.
4. `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` is constructed with `shop == "victim-shop.myshopify.com"` [7](#0-6)  and passed to the host app's `handler.handle`, which now performs tenant-scoped logic (data storage, redaction, notifications, etc.) attributing it to the victim shop.
