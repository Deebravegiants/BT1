### Title
Excess validator transaction fees are silently destroyed when capped by `TransactionFeeConfig`, instead of being credited to the validator's stake pool - ([File: aptos-move/framework/aptos-framework/sources/stake.move])

### Summary
This is an Aptos-native analog of the ELFi bug class: value that is owed to one legitimate custody destination ("LpPool"/validator stake pool) is silently diverted away from that destination and permanently lost instead of being reconciled to the correct holder.

### Finding Description
Each epoch, the VM calls `stake::record_fee` (via `block::block_epilogue`) to record per-validator transaction fees collected during the epoch into `PendingTransactionFee.pending_fee_by_validator`, a map keyed by validator index that simply accumulates octas owed to each validator: [1](#0-0) 

During `update_stake_pool`, this pending fee is consumed once per epoch: the full owed amount `fee_octa` is read and *removed* from the map, but before being distributed it is unconditionally clamped to `fee_limit` (`max_fee_octa_allowed_per_epoch_per_pool` from `TransactionFeeConfig`): [2](#0-1) 

Only the clamped `fee_active`/`fee_pending_inactive` (derived from the capped `fee_octa`) are actually minted and merged into the stake pool: [3](#0-2) 

The portion of the fee above `fee_limit` is neither minted to the validator's stake pool, nor rolled over to the next epoch, nor routed to any other pool (e.g., a treasury, burn account, or carry-over ledger) — it is simply discarded because the entry was already `.remove()`d from `pending_fee_by_validator` before the cap was applied. This mirrors the ELFi bug: value that is unambiguously owed to a specific pool (the LpPool there, the validator stake pool here) ends up stranded/lost instead of being reconciled to that pool, because the code applies a cap/limit at the wrong point in the accounting flow (after the entitlement is already consumed) without preserving the remainder.

### Impact Explanation
This is a supply/custody accounting corruption: octas that transaction-fee payers already paid, and that the protocol's own bookkeeping (`PendingTransactionFee`) recorded as owed to specific validators, vanish with no path to recovery whenever a governance-configured per-epoch-per-pool fee limit is in effect and exceeded. Value is destroyed rather than routed to the correct holder (the validator's stake pool/its delegators), meeting the "permanent, non-recoverable loss of ... custody-held value" and "custody accounting corruption that moves value to the wrong holder or destroys recovery rights" criteria. This affects live APT staking rewards accounting at the framework level (mainnet-relevant), not just an isolated example contract.

### Likelihood Explanation
This triggers automatically, without any privileged or malicious actor, any epoch in which: (a) `TransactionFeeConfig`/`set_transaction_fee_limit_per_epoch_per_pool` is set to a limit lower than actual accumulated fees for a validator, and (b) `initialize_pending_transaction_fee`/fee-distribution feature is enabled. Since this is governance-configurable (`set_transaction_fee_limit_per_epoch_per_pool`), any legitimate attempt by governance to cap per-epoch fee payouts (e.g., to smooth rewards or prevent MEV-driven spikes) will unintentionally burn the excess rather than deferring or redistributing it — a systemic accounting bug rather than a rare edge case.

### Recommendation
When `fee_octa > fee_limit`, do not discard the excess. Either (a) leave the excess amount back in `pending_fee_by_validator` (re-`add` it) so it rolls over and is paid out in a future epoch once under the cap, or (b) explicitly route the excess to a well-defined pool (e.g., a protocol treasury/reserve) with corresponding accounting/events, mirroring how the ELFi fix recommends sending the full fee amount to the correct pool rather than dropping part of it.

### Proof of Concept
1. Governance calls `set_transaction_fee_limit_per_epoch_per_pool(fw, limit_octa)` with a small `limit_octa`. [4](#0-3) 
2. Over an epoch, the VM records fees for a validator via `record_fee` such that the accumulated `pending_fee_by_validator[validator_index]` exceeds `limit_octa` (e.g., heavy transaction activity produces `fee_octa = 1000` octa while `limit_octa = 100`).
3. On epoch change, `update_stake_pool` runs: it removes the full `1000` octa entry from `pending_fee_by_validator` (line 1881), clamps `fee_octa` to `100` (lines 1882-1884), splits it into `fee_active`/`fee_pending_inactive`, and mints/merges only `100` octa total into the validator's `StakePool`.
4. The remaining `900` octa that was already recorded as validator-owed is gone — not in the stake pool, not back in `pending_fee_by_validator`, not minted anywhere. Re-querying `pending_fee_by_validator` after this epoch shows no entry for the validator, confirming the 900 octa is unrecoverable.

Note: I was not able to trace, within the available index, the exact upstream call site that originally computes and burns the real APT from fee payers before calling `record_fee` (i.e., confirmation that `fee_amounts_octa` passed into `record_fee` always corresponds 1:1 to already-collected/burned real value rather than a purely notional accounting entry). If `record_fee`'s inputs are purely notional (to be freshly minted regardless), the "loss" is of newly-mintable rewards rather than already-collected payer funds; either way the corrupted accounting field (`pending_fee_by_validator` entry silently dropped) and broken invariant (validator-recorded fee entitlement must reach the validator's stake pool) hold under local code, so I'm reporting this as the strongest candidate found.

    public(friend) fun record_fee(
        vm: &signer,
        fee_distribution_validator_indices: vector<u64>,
        fee_amounts_octa: vector<u64>
    ) acquires PendingTransactionFee {
        // Operational constraint: can only be invoked by the VM.
        system_addresses::assert_vm(vm);

        assert!(
            fee_distribution_validator_indices.length() == fee_amounts_octa.length()
        );

        let num_validators_to_distribute = fee_distribution_validator_indices.length();
        let pending_fee = borrow_global_mut<PendingTransactionFee>(@aptos_framework);
        let i = 0;
        while (i < num_validators_to_distribute) {
            let validator_index = fee_distribution_validator_indices[i];
            let fee_octa = fee_amounts_octa[i];
            pending_fee.pending_fee_by_validator.borrow_mut(&validator_index).add(
                fee_octa
            );
