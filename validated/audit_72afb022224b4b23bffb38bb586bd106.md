### Title
`describeWithdrawal` reports Aurora Engine withdrawals as `completed` without checking whether the NEP-141 `ft_transfer_call` to the Aurora Engine / proxy token actually succeeded - ([File: packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts])

### Summary
`AuroraEngineBridge.describeWithdrawal` unconditionally returns `{ status: "completed", txHash: null }` with no inspection of the NEAR transaction receipts, even though the underlying `ft_withdraw` intent triggers an asynchronous `ft_transfer_call` to the Aurora Engine (or proxy token) contract that can fail (e.g. insufficient storage on the receiving contract) after the outer NEAR transaction has already returned success. This breaks the equality `status reported == outcome on chain`.

### Finding Description
`createWithdrawalIntents` in `packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts` (lines 105-118, via `createWithdrawIntentPrimitive` in `aurora-engine-bridge-utils.ts` lines 11-51) builds an `ft_withdraw` intent whose `receiver_id` is `auroraEngineContractId` (or `proxyTokenContractId`) with a `msg` payload. This is executed as an NEP-141 `ft_transfer_call`-style cross-contract call from the token contract to the Aurora Engine/proxy contract, which is asynchronous relative to the outer signed NEAR transaction. If that nested call fails (e.g. `ft_on_transfer` panics due to insufficient storage on the receiving proxy/Aurora Engine account — the scenario referenced in the prior questions), the NEP-141 token is refunded back via the resolve callback, and the transferred funds never leave the NEAR side to the virtual chain destination — while the outermost transaction result may already report success.

`describeWithdrawal` (lines 220-222) is:
```ts
async describeWithdrawal(): Promise<WithdrawalStatus> {
	return { status: "completed", txHash: null };
}
```
It takes no arguments and performs zero receipt inspection — not even using `this.nearProvider`, which is available on the class and used elsewhere (`estimateWithdrawalFee`) to query storage balances. Contrast this with `HotBridge.describeWithdrawal` (`hot-bridge.ts` lines 375-503), which actively checks withdrawal status via `getGaslessWithdrawStatus`, a bridge indexer, and API fallback before ever returning `completed`. `AuroraEngineBridge` has no equivalent check.

`watchWithdrawal` in `packages/intents-sdk/src/core/withdrawal-watcher.ts` (lines 33-53) trusts the bridge's `status.status === "completed"` value directly and resolves the poll — there is no independent verification of receipt outcomes at that layer either.

### Impact Explanation
An integrator polling `describeWithdrawal` (directly or via `watchWithdrawal`) receives `status: "completed"` as soon as the initial NEAR transaction hash exists, regardless of whether the nested `ft_transfer_call` to the Aurora Engine/proxy token contract ultimately succeeded or was refunded. This is a status misreport: the integrator may credit/clear the user's pending withdrawal as done while the funds never reached the destination virtual chain (they are refunded back into the NEAR-side balance instead). This matches the High-severity category "a status or hash misreport making an integrator credit or refund twice" (the funds can appear both as "withdrawn" to the integrator's records and remain available on NEAR to be withdrawn again).

### Likelihood Explanation
This requires the storage-deposit/quote guard in `estimateWithdrawalFee` to be bypassed or stale by the time the transfer executes (e.g., the receiving contract's storage state changes between fee estimation and execution, or another race/edge condition causes the nested transfer to fail) — a scenario already established as reachable per the "two questions above" referencing insufficient storage on Aurora Engine. No privileged access is needed: it only requires an ordinary withdrawal request under conditions where the nested cross-contract transfer fails after the outer NEAR tx succeeds. This is repeatable for every such failed Aurora Engine withdrawal.

### Recommendation
Update `describeWithdrawal` to accept the `WithdrawalIdentifier` (with `tx.hash`) and use `this.nearProvider` to fetch the transaction's receipts/outcomes, inspecting whether the nested `ft_transfer_call`/resolve receipt actually succeeded (no `FunctionCallError`, and that tokens were not refunded) before returning `completed`. If the resolve callback indicates a refund/failure, return `{ status: "failed", reason: ... }` (or `pending` while still resolving), mirroring the verification pattern already used in `HotBridge.describeWithdrawal`.
