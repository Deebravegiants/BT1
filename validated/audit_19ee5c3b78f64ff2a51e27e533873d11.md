Confirmed: for OAuth callback validation, `AuthQuery#to_signable_string` includes `shop` in the signed params [1](#0-0) , but for webhook processing, `Webhooks::Request#to_signable_string` only returns `@raw_body`, excluding the `shop` (and `topic`) header entirely from the HMAC computation [2](#0-1) .

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking `Utils::HmacValidator.validate(request)` [3](#0-2) , which calls `verifiable_query.to_signable_string` to compute the expected signature [4](#0-3) . For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` [2](#0-1) , meaning the `shop-domain` and `topic` HTTP headers are never part of the HMAC-signed material, even though they are read directly from attacker-controlled request headers [5](#0-4) .

### Finding Description
The identity binding that should hold is: `hmac == HMAC(secret, body || shop || topic)`, i.e., the shop the webhook claims to be from should be cryptographically bound to the signature, just as it is for `Auth::Oauth::AuthQuery`, where `shop` is explicitly included in `to_signable_string` [1](#0-0) . For webhooks, this binding is broken: `hmac == HMAC(secret, body)` only, and `shop`/`topic` are read straight from headers without any cryptographic tie to the signature [6](#0-5) . `Registry.process` passes this unverified `shop` value straight into `WebhookMetadata` handed to the app's handler as the trusted tenant identifier: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [7](#0-6) .

Because Shopify's real webhook signature only ever covers the raw body upstream, and this gem mirrors that by using `@raw_body` as the sole signable string, any request with a body/HMAC pair that is valid for shop A can be replayed with the `shop-domain` header changed to shop B, and it will still pass `HmacValidator.validate` — the validator has no way to detect the mismatch since `shop` was never part of what was signed.

### Impact Explanation
An unprivileged internet user who can obtain (or is themselves the merchant of) one legitimately signed webhook body/HMAC pair for their own shop can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain`/`shopify-shop-domain` header. `Registry.process` will accept it as valid (HMAC check passes) and dispatch it to the app's handler tagged with the attacker-chosen `shop`. If the host app trusts `WebhookMetadata#shop` (as the gem's own documentation instructs: "construct a `ShopifyAPI::Webhooks::Request`... call `Registry.process`... verify the request did indeed come from Shopify" [8](#0-7) ) to select which tenant's data to update/read, this enables cross-tenant data injection or disclosure — writing/mutating data under another merchant's `shop` identity using content the attacker controls (their own shop's payload body), which is a cross-tenant boundary break.

### Likelihood Explanation
Likelihood is moderate: the attacker needs one valid signed webhook for a shop they control (trivial — install/uninstall the app themselves on a dev store to trigger any webhook topic) and knowledge of the target `shop-domain` string (public, guessable `*.myshopify.com` names). No secret material is required, since the HMAC never covers the header being forged.

### Recommendation
Include `shop` (and ideally `topic`) in `Webhooks::Request#to_signable_string`, matching the pattern already used in `Auth::Oauth::AuthQuery#to_signable_string` [1](#0-0) , or otherwise cryptographically bind the shop header to the signed material so `HmacValidator.validate` rejects replays with a mismatched `shop-domain` header.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and triggers any webhook topic, capturing the raw request body and the `x-shopify-hmac-sha256` header sent by Shopify (both attacker-controlled/observable since it's their own shop).
2. Attacker sends a forged HTTP request to the app's webhook endpoint using the exact same raw body and HMAC header, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses `shop` from the forged header [6](#0-5) .
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (`@raw_body` only) and matches the header HMAC — validation succeeds despite the shop mismatch [4](#0-3) .
5. The app's handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and attacker-controlled body content, believing it originated from the victim shop.
