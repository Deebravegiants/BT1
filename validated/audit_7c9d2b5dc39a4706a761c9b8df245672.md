### Title
Webhook Shop Identity Spoofing via HMAC That Only Covers the Request Body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature exclusively from the raw request body, while the `shop` value used by `ShopifyAPI::Webhooks::Registry.process` to identify the tenant is read from an unauthenticated HTTP header. An attacker who legitimately receives webhooks for a shop they control (any merchant can install an app on their own store) can capture a validly-signed webhook and replay it with a forged `X-Shopify-Shop-Domain` header, causing the app to process attacker-controlled body data under an arbitrary victim shop's identity.

### Finding Description
`to_signable_string` in [1](#0-0)  returns only `@raw_body`. The `shop` accessor, however, is derived purely from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never part of the signed bytes: [2](#0-1) .

`HmacValidator.validate` verifies the signature against `to_signable_string` (i.e., body only) using `OpenSSL.secure_compare`: [3](#0-2) .

`Registry.process` trusts this validation and then forwards `request.shop` — the unauthenticated header value — directly into the `WebhookMetadata` passed to the app's handler as the tenant identity: [4](#0-3) .

This breaks the intended identity binding:
`verified_bytes (HMAC-signed raw_body)` ≠ `trusted_identity (request.shop header value passed to handler)`

Because the header is outside the signed payload, any bytes+HMAC pair that is valid for shop A's body remains valid when replayed with shop B's domain in the header — the HMAC only proves "this body was produced by Shopify for some shop that owns this app installation," not "this body belongs to the shop named in this header."

As documented, apps are expected to use `data.shop` to route/attribute the payload (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` in [5](#0-4) ), so this trust is exactly what downstream apps rely on.

### Impact Explanation
An attacker who installs the vulnerable app on their own (attacker-controlled) shop can generate legitimately-signed webhooks with attacker-chosen body content (e.g., by triggering `orders/create`, `customers/update`, etc. on their own store). They can then replay the same raw body and HMAC to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `Registry.process` will accept the signature as valid and hand the handler a `WebhookMetadata` claiming the data originated from the victim shop. Any app that persists or acts on webhook data keyed by `data.shop` (updating per-tenant records, triggering per-tenant side effects, billing, notifications, etc.) will attribute attacker-controlled data to a tenant the attacker does not control — a cross-tenant data injection/spoofing primitive.

### Likelihood Explanation
Exploitation requires only that the attacker be able to install the target app on a shop they control (the normal, unprivileged use case for any Shopify app) and be able to capture/replay one legitimate webhook HTTP request — no access to `api_secret_key`, access tokens, or the victim's credentials is required. This is a straightforward, mechanically reachable path through the gem's documented `Registry.process` / `Webhooks::Request` API.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) in the HMAC-signed content, or otherwise cryptographically bind the `shop` header to the signature before it is trusted, e.g.:
```diff
 def to_signable_string
-  @raw_body
+  "#{shop}\n#{@raw_body}"
 end
```
and update `Registry.process`/`HmacValidator` accordingly, or validate the `shop` value against Shopify's known shop format and cross-check it via an authenticated channel (e.g., re-deriving it from a value that is part of the signed body) rather than trusting the header alone.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com` (attacker's own store).
2. Trigger a webhook (e.g., `orders/create`) and capture the raw POST body and its `X-Shopify-Hmac-Sha256` header — both are valid per Shopify's normal webhook signing for `attacker.myshopify.com`.
3. Replay the request to the app's webhook endpoint, keeping body and HMAC header unchanged, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `@raw_body` against the HMAC — the shop header is never checked. `request.shop` returns `"victim.myshopify.com"`, and `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: attacker_controlled_body, ...)` is dispatched to the app's handler, which processes attacker-controlled content as if it belonged to the victim shop.
