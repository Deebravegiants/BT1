## Analysis

The reported Buffer Protocol bug is a signature-verification design flaw: a value (`market direction`) that gets *acted upon* is never actually bound inside the signed payload used to verify it later, allowing an attacker to substitute a different value after the fact while the "signature check" still nominally passes.

The direct analog in this gem is in the webhook HMAC verification path.

### Root cause

`ShopifyAPI::Webhooks::Request` extracts `shop` from an HTTP header, completely separate from the HMAC-covered content: [1](#0-0) [2](#0-1) 

`to_signable_string` — the only data that `HmacValidator` verifies — returns just `@raw_body`: [2](#0-1) 

`HmacValidator.validate` computes the signature purely from `to_signable_string` (i.e. the raw body) and compares it to the HMAC header: [3](#0-2) 

`Registry.process` trusts this validation, then forwards `request.shop` — the unauthenticated header value — straight to the app's handler as the tenant identity for the event: [4](#0-3) 

### The broken binding

`shop_in_HMAC_signed_payload == shop_delivered_to_handler`

This equality does **not** hold: the HMAC only authenticates `raw_body` bytes; the `shopify-shop-domain` (or `x-shopify-shop-domain`) header is never part of the signed string, so it can be swapped freely without invalidating the signature.

### Exploitation path

1. An attacker installs the target app on their own (attacker-controlled) shop `attacker.myshopify.com`, which is fully legitimate and requires no privileged access.
2. Shopify sends the attacker a genuine webhook: a `(raw_body, hmac)` pair, correctly signed with the app's real `api_secret_key`, and headers including `x-shopify-shop-domain: attacker.myshopify.com`.
3. The attacker replays this exact `raw_body` + `hmac` to the app's webhook endpoint, but rewrites the `x-shopify-shop-domain` header to `victim.myshopify.com`.
4. `HmacValidator.validate` recomputes the signature from `raw_body` only — it still matches, since the body is untouched. Validation passes.
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"` (attacker-controlled) and dispatches it to the host app's handler, even though the payload's HMAC never covered that identity.

If the host application uses `WebhookMetadata#shop` (as documented/intended usage) to look up the victim's stored session/access token to process the event (e.g., process an "order" payload as if it belongs to the victim, or update the victim's local record based on attacker-supplied body content), this is a cross-tenant confusion issue — the app processes attacker-controlled data attributed to another merchant's identity, entirely through this gem's own verification API, without needing any credentials beyond running a normal (non-privileged) Shopify shop.

### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body, so `HmacValidator.validate` never authenticates the `shopify-shop-domain` header. An attacker who legitimately receives a signed webhook for their own shop can replay the same body/HMAC pair while substituting a victim shop's domain in the header, and the gem's HMAC check will still report the request as valid.

### Finding Description
`Webhooks::Request#shop` is sourced purely from an HTTP header [1](#0-0) , while the HMAC signature that `HmacValidator` checks is computed only over `@raw_body` [2](#0-1) [5](#0-4) . Because the shop identity is never part of the signed content, it is not cryptographically bound to the validated payload, letting it be freely substituted after a genuine signature has been obtained for a different shop. `Registry.process` propagates this unauthenticated `shop` value directly to the app's webhook handler as the trusted tenant identifier [6](#0-5) .

### Impact Explanation
This crosses a tenant boundary: an unprivileged Shopify merchant (the attacker, installing the app on their own store) can cause the host application to process webhook data under a victim merchant's shop identity, since the "HMAC-validated" flag gives false assurance that the entire request — including the shop header — is authentic. Any host logic keyed off `WebhookMetadata#shop` (e.g., looking up the correct access token/session, or storing data against the correct tenant) can be tricked into attributing attacker-controlled content to another merchant, i.e., cross-tenant access.

### Likelihood Explanation
Likelihood is high: obtaining a signed webhook only requires installing the app on any shop the attacker controls (no leaked credentials, no `api_secret_key`, no privileged account needed). Forging the header is a simple HTTP request-crafting step, entirely within the capability of an unprivileged internet user interacting with the gem's public API.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) inside the HMAC-signed payload verification, or otherwise cryptographically bind the header-derived shop to the signed body — for example, by having `to_signable_string` incorporate the shop-domain header value, or by validating that the `shop` extracted matches an expected/allow-listed value tied to the session that originally registered the webhook, rather than trusting the header verbatim once body HMAC passes.

### Proof of Concept
1. Register the target app on `attacker.myshopify.com` and trigger any webhook event (e.g., `orders/create`).
2. Capture the resulting POST request Shopify sends to the app's webhook endpoint — note `raw_body`, `x-shopify-hmac-sha256`, and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Replay the identical `raw_body` and `x-shopify-hmac-sha256` to the same endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. Observe that `ShopifyAPI::Webhooks::Registry.process` accepts the request (`Utils::HmacValidator.validate` returns `true` since only `raw_body` is checked) and dispatches `WebhookMetadata` with `shop: "victim.myshopify.com"` to the app's handler, per [6](#0-5) .

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
