### Title
Supply-index accrual panics on i128 overflow once total supplied value exceeds the RAY ceiling, permanently freezing the market - (File: common/src/rates/index.rs)

### Summary
`update_supply_index` computes `total_supplied_value = supplied.mul(env, old_index)` with `Ray::mul`, which panics with `GenericError::MathOverflow` when the product `supplied * old_index` exceeds `i128::MAX`. Because every state-changing entrypoint accrues indexes first, once a market's supplied value crosses the `i128::MAX / RAY` (~170 billion whole-token) ceiling the panic bricks the market: no withdraw, repay, borrow, or liquidation can ever execute again. The `MAX_SUPPLY_INDEX_RAY` cap cannot engage because the panic happens on the value product before any cap comparison.

### Finding Description
The wasmtime advisory is a checked-arithmetic panic reachable by supplying an extremely large value. The analog in XOXNO Lending is the unchecked pre-check multiplication in `update_supply_index`:

```rust
// common/src/rates/index.rs
let total_supplied_value = supplied.mul(env, old_index);  // panics on i128 overflow
let new_value = total_supplied_value.checked_add(env, rewards_increase);
let grown = fp_core::mul_div_floor_saturating(env, new_value.raw(), RAY, supplied.raw());
```

`supplied` is a scaled RAY value. `Ray::mul` is `mul_div_half_up(x, y, RAY)`, which widens to `I256` only for the intermediate product but panics when the *result* doesn't fit `i128` — i.e., when `supplied * index / RAY > i128::MAX`. The same panic exists in `calculate_supplier_rewards` (`borrowed.mul(env, new_borrow_index)` at index.rs:80-81) and `apply_bad_debt_to_supply_index` (`supplied().mul(env, supply_index())` at contracts/pool/src/interest.rs:74).

`global_sync` in contracts/pool/src/interest.rs runs before every verb, and `update_indexes` is callable by any unprivileged address, so any user can both push the market toward the cliff (by supplying) and trigger the freeze once the state is there. The repo's own test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321-361) demonstrates the end state: after enough accrual, `try_update_indexes_for`, `try_withdraw_raw`, and `try_repay` all fail with `MATH_OVERFLOW`, while `borrow_index` is still below `MAX_BORROW_INDEX_RAY` — the index caps never get a chance to engage.

Unlike the adjacent `mul_div_floor_saturating` calls that deliberately fail open, `update_supply_index` fails closed on the raw multiplication, and the panic precedes any clamping at lines 43-44.

### Impact Explanation
Permanent freezing of funds. Once `supplied * supply_index > i128::MAX * RAY`, every call that accrues reverts, so suppliers cannot withdraw and borrowers cannot repay; liquidation and bad-debt cleanup also accrue first and hit the same panic. All token balances backing the market's supply positions are locked in the pool forever — a textbook permanent freeze, not a transient DoS.

### Likelihood Explanation
The ceiling is ~1.7e38 ray value (~170 billion whole tokens), and reaching it requires either a near-cap supply or years of index growth at high utilization — the harness test needs a billion-token position on the steep XLM curve plus multi-year drift. Caps (`max_cap_for_decimals`) admit exactly that ceiling, so an asset listed with a permissive cap and sustained high utilization can reach it without any privileged action beyond the initial listing parameters. The trigger itself is a single permissionless `update_indexes` call. The required market size makes this Medium rather than High, but it is fully on-chain, deterministic, and irreversible once crossed — there is no recovery path because the panic is on the entry of every verb.

### Recommendation
In `update_supply_index`, compute `total_supplied_value` via `try_mul_div_half_up` (or `mul_div_floor_saturating`) and short-circuit to returning `old_index` (or `MAX_SUPPLY_INDEX_RAY`) when the product overflows `i128`, mirroring the fail-open design already used by `calculate_scaled_cap` and `protocol_fee_shares`. Apply the same saturating treatment to `borrowed.mul(new_borrow_index)` in `calculate_supplier_rewards` and to `apply_bad_debt_to_supply_index` in `contracts/pool/src/interest.rs`, so index caps can still engage and exits remain possible. Alternatively, cap per-market `supplied` scaled shares at a value that keeps `supplied * MAX_SUPPLY_INDEX_RAY` inside `i128` at listing time via `require_cap_within_asset_domain`.

### Proof of Concept
1. List an 18-decimal asset with the steep XLM rate curve and lift supply/borrow caps to `max_cap_for_decimals(18)`.
2. BOB calls `supply(BIG18, 1_000_000_000 * 10^18)`; ALICE supplies COL collateral and calls `borrow(BIG18, 98%)` of it, with `max_utilization` disabled.
3. Advance time (the test shows the cliff arrives within a handful of years at 98% utilization on this curve).
4. Any unprivileged address calls `update_indexes`. `accrue_step` → `update_supply_index` computes `supplied.mul(old_index)` where `supplied * index / RAY > i128::MAX`, and panics with `MathOverflow` (contracts/pool/src/interest.rs:39-53, common/src/rates/index.rs:34).
5. Thereafter `withdraw(BOB, BIG18, 1)`, `repay(ALICE, BIG18, ...)`, `liquidate`, and `clean_bad_debt` all revert with the same `MathOverflow`, permanently locking all supplied funds. The index remains below `MAX_BORROW_INDEX_RAY`, proving the cap could not prevent the freeze. This is exercised verbatim by `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` in tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:321.
