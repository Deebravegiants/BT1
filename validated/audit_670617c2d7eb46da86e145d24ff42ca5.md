### Title
Non-embedded session lookup trusts an unauthenticated, predictable session-id cookie value as the tenant identity binding - (File: `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps (and as a fallback for embedded apps without a bearer token), `ShopifyAPI::Utils::SessionUtils.current_session_id` resolves "which shop/session to activate" purely from the plaintext value of the `shopify_app_session` cookie, with no cryptographic binding proving that value was actually issued by this gem's OAuth flow to this browser. Because the session id format is deterministic and derived only from public information (the shop's `.myshopify.com` domain), the identity binding `cookie value == session id legitimately minted for this browser` is never verified — it is only ever equal to itself by construction, never checked against anything server-side.

### Finding Description
During the authorization-code OAuth flow, `ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the browser cookie directly from the computed `session.id`: [1](#0-0) 

`session.id` is deterministic and derived only from the shop domain (and, for online sessions, the numeric Shopify user id): [2](#0-1) 

- Offline session id: `"offline_#{shop}"`.
- Online session id: `"#{shop}_#{associated_user.id}"`.

Both `shop` (`{name}.myshopify.com`) and, for many merchants, the associated user id are guessable/enumerable public or low-entropy values — nothing here is a secret.

Later, when resolving which session to use, `SessionUtils.current_session_id` (for non-embedded apps, or as the "fallback to session cookie" branch for embedded apps) simply returns the raw cookie bytes with no signature check: [3](#0-2) [4](#0-3) 

The `SessionCookie` struct itself carries no HMAC or signature over its `value` field: [5](#0-4) 

Compare this to the JWT-based path in the same class, `session_id_from_shopify_id_token`, where the session id is derived only after the token is cryptographically verified against `Context.api_secret_key` via `Auth::JwtPayload.new`: [6](#0-5) [7](#0-6) 

There is no equivalent binding for the cookie path: `cookie value == session id issued by this gem's own OAuth handshake to this specific browser` is never checked. The gem's documented pattern (`docs/usage/oauth.md`) instructs apps to take whatever `session.id` comes back from `cookie_session_id`/`current_session_id` and use it directly as the lookup key into the app's session store: [8](#0-7) 

Because the id space is small and predictable (`offline_{shop}`, `{shop}_{user_id}`), any party able to set/overwrite this cookie for the app's origin (e.g. cookie injection through a related subdomain, a misconfigured `Domain` attribute, header injection, or any other cookie-write primitive against the app's origin that is outside TLS interception/local access) can set the session-id cookie to the value for a **different, victim shop** and cause the host application — following exactly the pattern this gem documents — to retrieve and activate the victim shop's stored `access_token`, achieving cross-tenant access without ever presenting Shopify-issued credentials for that shop.

### Impact Explanation
This breaks the identity binding between "browser holding a cookie" and "shop that legitimately completed this gem's OAuth flow," enabling session fixation / cross-tenant session hijacking as classified under the "High - session fixation or forced OAuth completion" impact category. If successful, an attacker gains use of another merchant's `Session` (and therefore access token) through the host app that trusted the gem-provided `current_session_id` value verbatim.

### Likelihood Explanation
Exploitation requires only the ability to write/inject a cookie value for the app's origin (no `api_secret_key`, no access token, and no TLS interception is needed) plus knowledge of the target shop's `.myshopify.com` domain (public) and, for online sessions, the numeric Shopify user id (often low-entropy/enumerable). The gem provides no defense-in-depth (signature/HMAC) over the cookie value, so any cookie-write primitive against the origin is sufficient — moderate likelihood, gated on a cookie-injection primitive that is common in real deployments (subdomain cookie tossing, reverse-proxy header confusion, etc.).

### Recommendation
Bind the session cookie value to the OAuth transaction cryptographically instead of trusting the raw `session.id` string as a bearer token:
- Sign the cookie value (e.g. HMAC with `Context.api_secret_key`, similar to `Utils::HmacValidator`) and verify the signature in `SessionUtils.cookie_session_id` before returning it.
- Alternatively, store an opaque, high-entropy, unguessable session identifier as the cookie value (not the derived `offline_#{shop}` / `#{shop}_#{user_id}` string), so the identifier itself cannot be forged/predicted for another tenant.

### Proof of Concept
1. Attacker learns/enumerates a target shop's domain, e.g. `victim-shop.myshopify.com` (public information visible in storefront URLs, app listings, etc.).
2. Attacker obtains any cookie-write primitive against the app's origin (e.g. a subdomain under the same registrable domain that can set cookies without a `Domain` restriction, or a header-injection bug in an intermediary) and sets:
   `shopify_app_session=offline_victim-shop.myshopify.com`
3. Attacker requests an authenticated route in the victim's browser session (or their own browser, if the host app doesn't bind cookies to a browser session separately).
4. The host app calls `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `"offline_victim-shop.myshopify.com"` unchanged from `cookie_session_id`: [4](#0-3) 
5. Following the gem's documented pattern, the host app looks up and activates the stored `Session` for that id — which is the victim shop's access token — completing cross-tenant access, with the gem never having verified that this browser was the one that actually completed OAuth for `victim-shop`.

```ruby
            if shopify_id_token

              session_id_from_shopify_id_token(id_token: id_token, online: online)

          end
        end
```

```ruby
# typed: strict
# frozen_string_literal: true

module ShopifyAPI
  module Auth
    module Oauth
      class SessionCookie < T::Struct
        extend T::Sig

        SESSION_COOKIE_NAME = "shopify_app_session"

        const :name, String, default: SESSION_COOKIE_NAME
        const :value, String
        const :expires, T.nilable(Time)

        alias_method :eql?, :==
        sig { params(other: T.nilable(SessionCookie)).returns(T::Boolean) }
        def ==(other)
          return false unless other

          name == other.name &&
            value == other.value &&
            expires == other.expires
        end
      end
    end
```
