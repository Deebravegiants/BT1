### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the shop-tenant identity (`x-shopify-shop-domain` header) is read separately and trusted as-is by the handler dispatch in `ShopifyAPI::Webhooks::Registry.process`. This mirrors the M-9 bug class: a field that is *acted on* (the shop identity used to scope the webhook side effects) is not covered by the value that is cryptographically verified (the HMAC).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read from a separate, unsigned header: [2](#0-1) 

`HmacValidator.validate` verifies exactly and only `to_signable_string` (i.e., the body) against the secret: [3](#0-2) 

`Registry.process` accepts the request once the body's HMAC checks out, then dispatches to the handler using the *unauthenticated* `request.shop` value as the tenant identity, with no separate binding between the verified body and the claimed shop: [4](#0-3) 

Because the app's `api_secret_key` is shared across all shops that install the app (it is not a per-shop secret), any party who can obtain one valid `(body, hmac)` pair from a genuinely delivered Shopify webhook (e.g., by installing the app on their own store and receiving its webhooks) possesses a signature that is valid for that exact body **regardless of which shop domain is claimed in the `x-shopify-shop-domain` header**, since that header is never part of the signed content. Replaying the same body+HMAC pair to the app's webhook endpoint with a different `x-shopify-shop-domain` value (and optionally a different `x-shopify-topic`/`x-shopify-webhook-id`) passes `HmacValidator.validate` and is routed to the handler as if it originated from the victim shop.

The identity binding that should hold is:
`shop that the HMAC authenticates == shop the handler treats as the acting tenant`

but the actual binding realized by the code is:
`shop that the HMAC authenticates (none — HMAC covers body only) != shop used by WebhookMetadata for tenant-scoped handling`

### Impact Explanation
This breaks a tenant boundary: any handler that uses `WebhookMetadata#shop` to determine which merchant record/session to update, delete, or act on can be tricked into performing that action against an arbitrary shop chosen by the attacker, using data replayed from a webhook the attacker legitimately received for their own (or any) store. Depending on how the host application implements its webhook handler (a common pattern per this gem's own docs, e.g. `orders/create`, `app/uninstalled`, GDPR webhooks acting on shop-scoped data), this can result in cross-tenant data corruption, spoofed mandatory-webhook actions (e.g., forging `shop/redact` or `customers/redact` for a shop the attacker doesn't own), or other cross-tenant state changes — matching the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires the attacker to have received at least one legitimately signed webhook body for *some* shop using the target app (trivial — install the target app as a normal, unprivileged merchant on their own store, or observe/capture any webhook delivery), then replay that exact body with a forged `x-shopify-shop-domain`/topic header to the app's public webhook endpoint. No access to `api_secret_key`, access tokens, or the target shop is required. This is a realistic, unprivileged-attacker path.

### Recommendation
Include the tenant-identifying headers (`x-shopify-shop-domain`, and ideally `x-shopify-topic`/`x-shopify-webhook-id`) in the HMAC-signable content used by `Request#to_signable_string`, or otherwise cryptographically bind the shop claim to the verified payload before it is handed to `WebhookMetadata`/handlers. At minimum, document prominently that `request.shop` is not authenticated by `HmacValidator.validate` and that host applications must independently corroborate the shop against a known/installed-shop list before using it for tenant-scoped effects.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com` and registers a webhook (e.g. `orders/create`).
2. Shopify delivers a webhook to the app's endpoint with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker intercepts/records `(B, H)`.
4. Attacker sends a forged HTTP POST to the same webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged and still valid, since it only signs `B`), but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because it only checks `B` against `H`.
6. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches to the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the handler to act as though this webhook data legitimately belongs to `victim-shop.myshopify.com`.
