### Title
Priority/PriorityClassName/PreemptionPolicy on PodGroup and CompositePodGroup are only enforced on Create, allowing unauthorized mutation via Update - (File: `plugin/pkg/admission/priority/admission.go`)

### Summary
The `Priority` admission plugin's `Admit` function only invokes `admitPodGroup`/`admitCompositePodGroup` for `Create` operations and unconditionally returns `nil` for `Update` operations on `podgroups`/`compositepodgroups` resources. Because the corresponding update validation functions do not enforce immutability of the priority-related spec fields, a user with only `update` RBAC permission on a PodGroup/CompositePodGroup can set an arbitrary `Spec.Priority`, `Spec.PriorityClassName`, and `Spec.PreemptionPolicy` on Update without going through the PriorityClass resolution/consistency checks that Create enforces.

### Finding Description
`Admit` dispatches based on resource and operation: [1](#0-0) 

For `podGroupResource` and `compositePodGroupResource`, the guard logic (`admitPodGroup`/`admitCompositePodGroup`, which call `establishPriority` to resolve the priority class and reject mismatched `Priority`/`PreemptionPolicy` values) executes **only** `if operation == admission.Create`; any `Update` request bypasses the plugin entirely and returns `nil`: [2](#0-1) 

Compare this to `admitPod`, where the `Update` branch explicitly preserves `Priority`/`PreemptionPolicy` from the old object if unset, with an accompanying comment noting reliance on core Pod spec-update validation to prevent other mutations to these fields: [3](#0-2) 

However, for `PodGroup` and `CompositePodGroup`, no equivalent immutability check exists at either the admission or validation layer. `ValidatePodGroupUpdate` and `ValidateCompositePodGroupUpdate` only validate `ObjectMeta`, and never compare or restrict `Spec.Priority`, `Spec.PriorityClassName`, or `Spec.PreemptionPolicy` between old and new objects: [4](#0-3) [5](#0-4) 

As a result, a user permitted to `update` a `PodGroup`/`CompositePodGroup` they own (or otherwise have `update` RBAC on) can submit an update request setting `Spec.PriorityClassName` to any existing PriorityClass (including a high-value system-reserved class they could not directly reference in a way that gets validated) and/or setting `Spec.Priority` to an arbitrary integer value, since `establishPriority`'s create-only consistency check (which forbids client-supplied `Priority`/`PreemptionPolicy` values that don't match the resolved PriorityClass) is never re-applied on Update.

### Impact Explanation
This breaks the invariant that scheduling priority (which controls preemption and scheduling order, and can grant workloads elevated precedence over others in the cluster) can only be set through the vetted, admission-mediated Create path. An unprivileged tenant with `update` access to their own PodGroup/CompositePodGroup objects can silently escalate their workload's effective scheduling priority/preemption policy post-creation, bypassing the PriorityClass authorization model — matching the "Admission bypass -> control of a protected field/identity" impact class.

### Likelihood Explanation
Exploitation requires only the RBAC verb `update` on `podgroups`/`compositepodgroups` in the attacker's own namespace — a routine and minimally-scoped permission for workload owners, no cluster-admin or special privilege needed. It is fully repeatable via a standard `UPDATE` API call and gated behind the `GenericWorkload`/`CompositePodGroup` alpha feature gates being enabled (which must be true for these resources to exist at all).

### Recommendation
Extend `Admit` to also invoke `admitPodGroup`/`admitCompositePodGroup` (or an update-specific variant) on `admission.Update`, re-resolving/re-validating `Spec.Priority`, `Spec.PriorityClassName`, and `Spec.PreemptionPolicy` against the old object's values (mirroring the immutability preservation done for Pods), and/or add explicit immutability checks for these fields in `ValidatePodGroupUpdate`/`ValidateCompositePodGroupUpdate` in `pkg/apis/scheduling/validation/validation.go`.

### Proof of Concept
Unit test plan (table test in `plugin/pkg/admission/priority/admission_test.go` style):
1. Create a `PodGroup` with `Spec.PriorityClassName = "low-priority"`, letting admission resolve `Spec.Priority` accordingly via `admitPodGroup` on Create.
2. Submit an `Update` request via `p.Admit` with `a.GetOperation() == admission.Update`, `a.GetObject()` containing the same PodGroup but with `Spec.PriorityClassName` changed to `"high-priority"` (or `Spec.Priority` set to an arbitrary large int32) and `a.GetOldObject()` set to the original object.
3. Assert that `Admit` returns `nil` (no error) and that the resulting object's `Spec.Priority`/`Spec.PriorityClassName` reflect the attacker-supplied value rather than being rejected or reset to the original — confirming the create-only guard gap.
4. Repeat for `CompositePodGroup` via `admitCompositePodGroup`.
