### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing on replayed webhooks - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook as authenticated for a given shop once `Utils::HmacValidator.validate(request)` passes, and then forwards `request.shop` to the app's handler as trusted tenant metadata. However, the HMAC is computed only over the raw request body; the `shop-domain` header that identifies *which tenant* the webhook belongs to is never included in the signed bytes. This breaks the identity binding: `hmac_verified(body) == true` should imply `shop_header == shop_that_produced(body)`, but the code never enforces that equality.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`: [1](#0-0) 

`hmac` is read from the `hmac-sha256` header, and `to_signable_string` returns only `@raw_body`: [2](#0-1) 

The `shop` accessor is read straight from the `shop-domain` header with no cryptographic relationship to the body or the HMAC: [3](#0-2) 

`HmacValidator.validate` only verifies `verifiable_query.to_signable_string` (i.e. the raw body) against `verifiable_query.hmac`: [4](#0-3) 

`Registry.process` uses this single boolean result as the authenticity gate for the *entire* request, then immediately forwards the unauthenticated `shop` header to the handler as if it were validated: [5](#0-4) 

Because the signature check only binds the body, any request whose body+hmac pair is a real, previously-observed valid pair will pass `HmacValidator.validate` regardless of what `shop-domain` header accompanies it. An unprivileged internet user who has installed the app on their own store (or who can otherwise capture one legitimate webhook delivery for any shop) can take that captured `(raw_body, hmac)` pair and resend it to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header (or `shopify-shop-domain`) changed to a victim shop. `Registry.process` will accept it (HMAC over the unchanged body still validates) and hand `WebhookMetadata` to the app's handler with `shop:` set to the attacker-chosen victim domain, while `body`/`topic` still belong to the originally captured webhook.

This is precisely the identity-binding failure the report's bug class targets: "a field acted on but not covered by the HMAC." Here the acted-upon field is `shop`, and it is not part of the signed bytes at all.

### Impact Explanation
Any downstream app logic that trusts `WebhookMetadata#shop` (returned by this gem as an "authenticated" webhook) to select which merchant's session/access token/state to act on — the documented and expected usage pattern per `docs/usage/webhooks.md` — can be tricked into applying a legitimately-signed payload under an attacker-chosen shop identity. This is a cross-tenant confusion/access vector: data or side effects intended for shop A's webhook can be attributed to shop B purely by header manipulation, without needing the app's `client_secret` or any merchant's access token. This matches the "cross-tenant access" Critical impact category, since the gem's own signature-verification contract is what is broken (the library asserts the webhook is authentic without binding the tenant identifier it hands back to callers).

### Likelihood Explanation
Requires no credentials: the attacker only needs to have received (or otherwise obtained) one genuine `(body, hmac)` webhook pair, which is easy for any merchant that installs the app on their own shop, or via topics they can trigger themselves (e.g. `orders/create` on their own store). No knowledge of `api_secret_key` is needed since the body is replayed unmodified; only the `shop-domain` header is altered, and that header is outside the cryptographic boundary entirely. This is a straightforward HTTP replay with a header swap against the app's public webhook receiver.

### Recommendation
Include the shop domain (and topic/webhook-id, ideally) in the value that is HMAC-verified, or otherwise cryptographically/authoritatively bind the `shop-domain` header to the signed body before trusting it — e.g., look up the expected shop by an independent authenticated channel (webhook subscription registration record keyed by webhook id) rather than trusting a bare header, or require the host application to cross-check `shop` against a known/registered shop for that `webhook_id`/topic before acting. At minimum, document prominently that `WebhookMetadata#shop` is not covered by the HMAC and must not be trusted as an authenticated tenant identifier on its own.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`), capturing the exact raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker resends this exact `(raw_body, hmac)` pair to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses this into a `Request` whose `hmac` matches `to_signable_string` (`@raw_body` unchanged) using the app's real secret — because it's a genuine previously-issued signature.
4. `ShopifyAPI::Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which returns `true` since only the body is checked [6](#0-5) .
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` where `shop` is now `victim.myshopify.com` [7](#0-6) , despite the payload never having originated from that shop.
