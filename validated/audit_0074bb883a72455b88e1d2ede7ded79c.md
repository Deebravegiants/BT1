## Analog Finding

### Title
Division-by-zero panic in `calc_take_pnl` permanently freezes pool funds - (File: program/src/processor.rs)

### Summary
CVE-2016-10371 describes a LibTIFF function (`TIFFWriteDirectoryTagCheckedRational`) that hits an unchecked assertion and crashes when processing crafted, attacker-influenced numeric input. The analogous bug class in this codebase is an unchecked `unwrap()` on a fallible arithmetic operation (`checked_div`) that is reachable from ordinary, unprivileged user instructions and can be driven to a panicking state through normal pool activity, causing the transaction — and every subsequent transaction touching the affected code path — to abort.

### Finding Description
`Processor::calc_take_pnl` computes `y2` using `x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()`, where `x1` is the normalized, PnL-excluded total pc balance of the pool [1](#0-0) . `x1` is produced by `Calculator::normalize_decimal_v2(total_pc_without_take_pnl, ...)`, and `total_pc_without_take_pnl` is computed as `pc_amount.checked_sub(amm.state_data.need_take_pnl_pc)` in `calc_total_without_take_pnl_no_orderbook` [2](#0-1) . Because `need_take_pnl_pc` accumulates every time PnL is taken during swaps, it is entirely possible for it to equal the pc vault balance, making `total_pc_without_take_pnl == 0` and therefore `x1 == 0` — a value that is never explicitly validated before being used as a divisor.

`calc_take_pnl` is called directly from the unprivileged, user-reachable `process_deposit`, `process_withdraw`, and `process_withdrawpnl` handlers [3](#0-2) [4](#0-3) . Once `x1` reaches zero, `checked_div(x1)` returns `None`, and the subsequent `.unwrap()` triggers a Rust panic, aborting the instruction with no recoverable error path.

### Impact Explanation
Once the pool state reaches `total_pc_without_take_pnl == 0` (or the equivalent for the coin side), every call to `Deposit`, `Withdraw`, and `WithdrawPnl` on that pool will panic deterministically, because all three handlers invoke `calc_take_pnl` with the same stored `x1`/`y1` values before performing any state-changing transfer [5](#0-4) . Since none of the pool's own instructions can restore `total_pc_without_take_pnl` above zero once it collapses to zero (only `WithdrawPnl` reduces `need_take_pnl_pc`, and that call itself panics through the same path), LP holders lose the ability to ever withdraw their principal from the pool — a permanent freeze of LP funds, meeting the Medium/High bar for insolvent-pool/fund-freezing impact.

### Likelihood Explanation
Reaching `total_pc_without_take_pnl == 0` requires the PnL-take accounting (`need_take_pnl_pc`/`need_take_pnl_coin`) to catch up to the vault balance through ordinary swap activity, which is driven purely by swap volume and price movement — no privileged action or malicious validator is required, only a sequence of swaps executed by unprivileged actors through the standard `SwapBaseIn`/`SwapBaseOut` instructions. This makes the precondition realistically reachable, though it depends on specific, extreme pool-balance conditions rather than being trivially triggerable in one transaction.

### Recommendation
Replace the unchecked `checked_div(x1).unwrap()` (and the sibling `unwrap()` calls in `calc_take_pnl`) with explicit zero-checks that return a graceful `AmmError` (e.g., skip PnL-taking when `x1 == 0` or `y1 == 0`) instead of panicking, mirroring the `ok_or(AmmError::CheckedSubOverflow)` pattern already used in `calc_total_without_take_pnl_no_orderbook`.

### Proof of Concept
1. Repeated swaps against a pool push `amm.state_data.need_take_pnl_pc` up (via `calc_take_pnl`'s PnL-accrual branch) until it converges with `amm_pc_vault.amount`, driving `total_pc_without_take_pnl` to `0`.
2. Any subsequent call to `Deposit`, `Withdraw`, or `WithdrawPnl` computes `x1 = normalize_decimal_v2(0, ...) = 0` and invokes `calc_take_pnl`, which executes `x2.checked_mul(y1).unwrap().checked_div(x1).unwrap()` at [6](#0-5) , panicking on the `None` returned by division by zero.
3. Because all three entrypoints share the same stored pool state, the panic recurs on every future call, permanently freezing LP withdrawal for that pool.

```rust
    pub fn calc_total_without_take_pnl_no_orderbook<'a>(
        pc_amount: u64,
        coin_amount: u64,
        amm: &'a AmmInfo,
    ) -> Result<(u64, u64), AmmError> {
        let total_pc_without_take_pnl = pc_amount
            .checked_sub(amm.state_data.need_take_pnl_pc)
            .ok_or(AmmError::CheckedSubOverflow)?;
        let total_coin_without_take_pnl = coin_amount
            .checked_sub(amm.state_data.need_take_pnl_coin)
            .ok_or(AmmError::CheckedSubOverflow)?;
        Ok((total_pc_without_take_pnl, total_coin_without_take_pnl))
    }
```
