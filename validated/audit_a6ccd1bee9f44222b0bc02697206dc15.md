## Title
Webhook shop identity spoofing: HMAC signs only the raw body, not the `shop-domain`/`topic` headers used for tenant dispatch - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` implements `VerifiableQuery` but its `to_signable_string` returns only the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values are read directly from unauthenticated HTTP headers and are never part of the signed material.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers with no cryptographic binding: [2](#0-1) 

`Registry.process` validates the HMAC over that signable string (the body only) and then unconditionally trusts `request.topic` to select the handler and `request.shop` to build the data passed to the app's handler: [3](#0-2) 

The binding the gem should guarantee is: `shop header == shop that produced (body, hmac)`. Instead it only guarantees `hmac == HMAC(secret, body)`, independent of which shop or topic header accompanies that body.

Critically, the HMAC secret (`Context.api_secret_key`) is the **app-level client secret**, shared by every shop that installs the app — it is not a per-shop secret: [4](#0-3) 

Because any merchant can freely install a public app on their own store (an "unprivileged internet user" from the app's perspective), an attacker can:
1. Install the target app on their own shop (Shop A) and receive a legitimate Shopify webhook, obtaining a valid `(raw_body, hmac)` pair signed with the app's shared `api_secret_key`.
2. Replay that exact `raw_body` + `hmac` to the app's webhook endpoint, but substitute the `X-Shopify-Shop-Domain` header (and/or `X-Shopify-Topic`) with a victim shop's domain (Shop B).
3. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only, which still matches, so `Registry.process` accepts the request and dispatches `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` to the app's handler with `shop` claiming to be Shop B.

### Impact Explanation
This breaks the tenant-isolation guarantee the HMAC is supposed to provide: an attacker-controlled body and topic can be attributed to an arbitrary victim shop domain. Any host application logic that trusts `WebhookMetadata#shop`/`#topic` (e.g., to look up the victim's stored session/access token, apply data mutations, or process mandatory GDPR webhooks like `customers/redact`/`shop/redact`) will act on attacker-supplied data as if it originated from the victim shop — a cross-tenant access/identity confusion (Critical impact per the given rubric).

### Likelihood Explanation
The only prerequisite is the ability to install the target app on an attacker-controlled shop, something publicly available for any public Shopify app, and no privileged credentials, access tokens, or `api_secret_key` knowledge are required. Constructing the forged webhook only requires copying an already-received legitimate body/HMAC pair and altering plain HTTP headers, which is trivial and reliably reproducible.

### Recommendation
Include the `shop-domain` (and ideally `topic`) header value in the HMAC-signed material (`to_signable_string`), e.g. by binding the raw body together with the shop domain, or by independently verifying that the shop asserted in the header matches a shop the app has an active installation/session for before dispatching to a handler.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook: headers `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid-hmac-for-body>`, with some JSON body.
2. Attacker replays the identical raw body and `hmac` value to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (unaffected by the header change).
4. The handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"` and attacker-controlled body, even though the request never actually originated from `victim-shop.myshopify.com`.
