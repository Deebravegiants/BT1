## Title
Webhook `shop`/`topic` identity headers are not bound to the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw request body only, while the shop, topic, webhook id, and API version that are actually *acted on* by `Registry.process` are pulled from unauthenticated HTTP headers. Any actor who can obtain one valid `(raw_body, hmac)` pair — trivially available to anyone who can install the target app on their own shop — can replay that pair to the app's webhook endpoint while freely rewriting the `x-shopify-shop-domain` and `x-shopify-topic` headers. `HmacValidator.validate` still passes because it only re-derives the signature from the body, so the forged tenant/topic identity is delivered to the app's handler as if it were cryptographically verified.

### Finding Description
`Utils::HmacValidator.validate` computes the expected signature purely from `verifiable_query.to_signable_string` and compares it to the `hmac` field: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw HTTP body: [2](#0-1) 

But the `shop`, `topic`, `webhook_id`, and `api_version` accessors — the fields that determine *which tenant* and *which action* the webhook represents — are all read directly from HTTP headers that are completely outside the signed payload: [3](#0-2) 

`Registry.process` validates only the HMAC (i.e., only the body) and then dispatches using these unauthenticated header values as the trusted identity of the webhook: [4](#0-3) 

The equality the library implicitly relies on is:

`hmac_valid(body) == true` ⟹ `(shop, topic) is authentic`

but the actual guarantee provided is only:

`hmac_valid(body) == true` ⟹ `body is authentic`

`shop` and `topic` are never part of what is verified, so the binding between "verified bytes" and "acted-upon identity fields" is broken — precisely the class of bug flagged in the analog report, where `stop`/`isClosed` created a control that looked like it enforced a guarantee it never actually enforced.

### Impact Explanation
An unprivileged actor who can install the target Shopify app on a shop they control (a normal, unprivileged action — anyone can install a public/dev app on their own store) can trigger genuine webhook deliveries with attacker-chosen content (e.g. creating an order, updating a product) and capture the resulting `(raw_body, x-shopify-hmac-sha256)` pair via a proxy in front of their own webhook endpoint. Because the HMAC only covers the body, the attacker can replay that exact body+hmac pair to the app's webhook endpoint while substituting:
- `x-shopify-shop-domain` with a victim shop's domain, and/or
- `x-shopify-topic` with a different, more sensitive registered topic (e.g. `app/uninstalled`, `customers/redact`, `shop/redact`, `customers/data_request`).

`HmacValidator.validate` still returns `true` (body unchanged), so `Registry.process` will look up and invoke the handler as if Shopify itself had verified that this event genuinely originated from and pertains to the spoofed shop/topic. Depending on how the host application uses `WebhookMetadata#shop` (e.g. to look up/mutate per-tenant records, revoke sessions, or trigger data compliance workflows), this enables cross-tenant data corruption, forced compliance actions against a shop the attacker doesn't own, or injection of fabricated events attributed to another merchant — a cross-tenant boundary violation.

### Likelihood Explanation
Any developer/tester can freely install the app on their own store to legitimately obtain a valid `(body, hmac)` pair without needing `api_secret_key`, an access token, or any privileged access. Replaying the same bytes to the public webhook endpoint with modified headers is a standard HTTP-request-crafting exercise. The only prerequisite is knowledge of the app's public webhook URL, which is by design an internet-reachable endpoint. No secrets, TLS interception, or social engineering are required, making this moderately likely to be discoverable and exploitable in real deployments that trust `WebhookMetadata#shop`/`#topic` for tenant-sensitive logic.

### Recommendation
Do not treat `shop`, `topic`, `webhook_id`, or `api_version` headers as trusted merely because the HMAC over the body validated. Either:
1. Include these header values in the signable string used for HMAC verification (matching what Shopify actually authorizes for the delivery), or
2. Require callers to cross-check `request.shop` against a known/installed shop record (and `request.topic` against the topic the endpoint was registered for) before processing, and document this requirement prominently since the gem currently exposes these as if they were verified fields once `HmacValidator.validate` passes.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; register a webhook (e.g. `orders/create`) pointing to a proxy the attacker controls.
2. Trigger the event on `attacker.myshopify.com` (e.g., create an order) and capture the raw POST: `raw_body` plus `x-shopify-hmac-sha256`, `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker.myshopify.com`.
3. Replay the identical `raw_body` and `x-shopify-hmac-sha256` value to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com` (and/or change `x-shopify-topic` to another registered topic the attacker wants to trigger).
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb` returns `true` because only `raw_body` is checked.
5. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches the handler with `shop: "victim.myshopify.com"` and/or the attacker-chosen topic, even though the payload never actually came from or concerned that shop/topic.
