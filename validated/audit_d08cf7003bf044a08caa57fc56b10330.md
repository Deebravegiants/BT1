### Title
`rootHashHinkalIndex` is unconstrained by the proof and by `calldataHash`, allowing use of a stale/attacker-chosen root index paired with `rootHashHinkal` - (File: contracts/Hinkal.sol, contracts/MerkleBase.sol)

### Summary
`Hinkal.transact()` validates the Merkle root used by the proof via `rootHashExists(circomData.rootHashHinkal, circomData.rootHashHinkalIndex)`, but `rootHashHinkalIndex` is never bound to the zk-SNARK proof (it is not part of the public input vector built in `CircomDataBuilder.formBasicInput`/`formInputEmporiumMin`) nor to the `calldataHash`/`signedMessageHash` integrity checks in `CircomDataBuilder.getHashedCalldata1/2` and `getSignedMessageHash`. Only `rootHashHinkal` itself is checked against these commitments. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The proof-verification step feeds `circomData.rootHashHinkal` into the circuit's public input (`input[index++] = circomData.rootHashHinkal;`), so the SNARK constrains that the *value* of the root used inside the circuit equals `rootHashHinkal`. [4](#0-3)  Separately, the calldata-integrity check `getHashedCalldata(circomData) == circomData.calldataHash` (`performHinkalChecks` in `HinkalHelper.sol`) hashes only a specific enumerated subset of fields via `getHashedCalldata1`/`getHashedCalldata2`; `rootHashHinkal` and `rootHashHinkalIndex` are both absent from those two hash functions. [5](#0-4) [2](#0-1) 

After the proof and calldata checks pass, `Hinkal.transact()` performs the on-chain root check:
```solidity
require(
    rootHashExists(
        circomData.rootHashHinkal,
        circomData.rootHashHinkalIndex
    ),
    "Hinkal Root Hash is Incorrect"
);
``` [1](#0-0) 

`rootHashExists` in `MerkleBase.sol` simply checks `roots[_rootIndex] == _root` for any `_rootIndex` in range `[MINIMUM_INDEX, m_index)`. [6](#0-5)  Because the `roots` mapping stores a root snapshot at *every* insertion index (`roots[newIndex - 1] = tree[twoPower];` in `Merkle.insert`/`insertMany`), the same root hash value can legitimately be recorded at multiple different indices over the tree's history if the tree state repeats a hash (e.g., through appended zero-subtrees or repeated intermediate states) — or, more importantly, a caller can supply *any* `rootHashHinkalIndex` that happens to map to the specific `_root` value in `roots`, even if that root/index pair was never the one the off-chain prover actually built its Merkle path against. [7](#0-6) 

Since neither the circuit's public inputs nor `calldataHash` bind `rootHashHinkalIndex` to the proof, this parameter is a `CircomData` field that is acted upon (used to gate spend validity via `rootHashExists`) but sits entirely outside the equality checks that are supposed to make `CircomData` internally consistent with what was actually proven and signed off-chain.

### Impact Explanation
This does not directly enable minting or theft on its own because the *value* `rootHashHinkal` is still constrained equal between the circuit and calldata, and `roots[rootHashHinkalIndex]` must still equal that exact root value. The practical exploitable effect is narrow: an attacker/relay can freely choose *which* recorded index is asserted to match a given root, as long as some `roots[idx] == rootHashHinkal`. If the tree ever produces a repeated `tree[twoPower]` value across two different insertion indices (which is architecturally possible, e.g., padding with zero-hashes at low leaf counts producing identical partial roots after certain insert patterns), a proof generated against an older/different root state could be replayed under a different index, potentially confusing downstream consumers of `rootHashHinkalIndex` (if any off-chain indexing or invalidation logic relies on the index binding). This is best classified as a design gap rather than a demonstrated fund-theft path in the on-chain code reviewed.

### Likelihood Explanation
Low-to-uncertain. Exploiting this requires finding an actual root collision across two indices in the deployed Merkle tree (function of Poseidon hash structure and insertion pattern), which was not proven achievable within this review, and the on-chain `require(roots[_rootIndex] == _root)` still fully blocks any index whose stored root differs from the proven `rootHashHinkal`.

### Recommendation
Include `rootHashHinkalIndex` in the `calldataHash` computation (`getHashedCalldata1`/`getHashedCalldata2`) so that the index is cryptographically bound to the rest of the transaction data, and/or add `rootHashHinkalIndex` as an explicit circuit public input so the SNARK constrains the exact tree state (index) the private Merkle path was proven against, not merely the resulting root value.

### Proof of Concept
No concrete on-chain fund-theft PoC could be constructed from the reviewed contracts alone; a full PoC would require demonstrating an actual root collision at two distinct `m_index` values in `Merkle.sol`, which requires deeper analysis of the Poseidon-based incremental tree construction than the available files support. This is flagged as a structural equality gap (per the "field acted on but outside `calldataHash`/`signedMessageHash`/public-input vector" analog class) rather than a proven exploit.

    function rootHashExists(
        uint256 _root,
        uint256 _rootIndex
    ) public view returns (bool) {
        if (m_index == MINIMUM_INDEX) {
            return _root == 0;
        }
        if (_rootIndex < MINIMUM_INDEX || _rootIndex >= m_index) {
            return false;
        }
        return _root != 0 && roots[_rootIndex] == _root;
    }
```

    function insert(uint256 leaf) internal override returns (uint256) {
        uint256 newIndex = ++m_index;
        uint256 currentNodeIndex = newIndex - 1;

        require(m_index <= uint256(2) ** LEVELS, "Tree is full.");

        uint256 fullCount = newIndex - MINIMUM_INDEX; // number of inserted leaves
        uint256 twoPower = logarithm2(fullCount); // number of tree levels to be updated, (e.g. if 9 => 4 levels should be updated)

        uint256 prevHash = leaf;

        insertOne(currentNodeIndex, twoPower, prevHash);

        roots[newIndex - 1] = tree[twoPower]; // adding root to roots mapping
        return newIndex - 1;
    }
