## Title
Unchecked irrefutable enum-variant match on attacker-influenced trie proof data causes runtime panic in `fetch_trie_id_from_main_proof` - (File: `modules/ismp/state-machines/evm/src/substrate_evm.rs`)

### Summary
`fetch_trie_id_from_main_proof` decodes an `AccountInfo` value read out of a Merkle-Patricia trie proof and then destructures it with an irrefutable `let AccountType::Contract(contract_info) = account_info.account_type;` binding, with no `match`/`if let`/error path for any other `AccountType` variant.

### Finding Description
The function reads a value from a submitted (relayer-controlled) state proof, SCALE-decodes it into `AccountInfo`, and then unconditionally assumes the `account_type` field is the `Contract` variant: [1](#0-0) 

This mirrors the CVE-2018-15864 bug class: code assumes a lookup/decode always yields the expected shape (a "map that was never created" in xkbcommon vs. an `AccountType` that is not `Contract` here) and performs an unchecked access, causing a crash instead of a handled error. Every other decode/lookup failure in this same file is properly surfaced via `SubstrateEvmError` variants (`ContractInfoNotFound`, `AccountInfoDecodeError`, `ChildRootNotFound`, etc.), which highlights that this one path is the outlier — it has no error variant for "account is not a contract" and instead panics via an irrefutable-pattern binding.

`fetch_trie_id_from_main_proof` is called from `verify_state_proof`, which is the `StateMachineClient::verify_membership`/`verify_non_membership` implementation for the EVM-on-Substrate ("Revive") state machine used by pallet-ismp's request/response verification: [2](#0-1) 

This is reached from the unsigned, permissionless `handle_unsigned` extrinsic, which any relayer can submit with an arbitrary `Proof`: [3](#0-2) 

Because `main_proof` (the storage trie nodes) is attacker/relayer-supplied bytes forming a `SubstrateEvmProof`, and the target contract's `AccountInfo` in the referenced parachain's main trie is itself state on a chain the relayer does not control but can select which account/height/proof bytes to submit, an attacker can craft or select a proof for an address whose `AccountInfo.account_type` is not `Contract` (e.g. an externally-owned account or a future account-type variant) while still satisfying the trie root check. The trie membership check only validates that the bytes correspond to `key` under `root`; it does nothing to constrain that the decoded `account_type` is `Contract`.

### Impact Explanation
A successful trigger panics the runtime thread processing `handle_unsigned`/`execute`, i.e. state-proof verification for cross-chain message delivery (POST request/response membership and non-membership checks) on the Revive/Substrate-EVM state machine. Since `execute()` is invoked synchronously inside the unsigned extrinsic and calls into `handle_incoming_message` → `StateMachineClient::verify_membership`, an unhandled panic here aborts block execution for that transaction/collator, which can be used to repeatedly disrupt message delivery for any route that resolves to this state machine client — a denial-of-service against the relaying path (making a route "unable to deliver messages"), which is within the accepted impact criteria (route unable to deliver messages).

### Likelihood Explanation
Likelihood is high for any deployment that registers the Substrate-EVM (Revive) state machine client, since `handle_unsigned` is explicitly permissionless (`ensure_none(origin)`) and any relayer can supply an arbitrary `Proof` blob decoded as `SubstrateEvmProof`. The attacker only needs to reference an address whose `AccountInfo.account_type` in the target chain's real state is not `Contract` (trivial to find — any EOA), and construct/obtain the corresponding valid trie proof for that address's `AccountInfo` entry, which is public chain state, not secret. No privileged access is required.

### Recommendation
Replace the irrefutable pattern binding with an exhaustive `match`/`if let ... else` that returns a typed `SubstrateEvmError` (e.g. a new `NotAContract` / `UnexpectedAccountType` variant) when `account_type` is not `Contract`, consistent with the rest of the function's error handling:

```rust
let contract_info = match account_info.account_type {
    AccountType::Contract(c) => c,
    _ => return Err(SubstrateEvmError::NotAContract(key.to_vec())),
};
Ok(contract_info.trie_id)
```

Conceptual PoC (cannot be executed in this read-only analysis, but the code path is deterministic):
1. Identify (or construct in a test trie) an address `A` on the target Substrate-EVM chain whose `pallet_revive::AccountInfo::account_type` is *not* `AccountType::Contract` (e.g. a plain externally-owned account entry), and obtain a valid trie inclusion proof for the `AccountInfo` storage key of `A` at some finalized height/root already trusted via the registered consensus client.
2. Submit a `handle_unsigned` extrinsic with a `Request`/`Response` message whose `Proof.proof` SCALE-encodes a `SubstrateEvmProof { main_proof, storage_proof }` where `main_proof` is the collected proof nodes for `A`'s `AccountInfo` key (`contract_info_key(A)`), and where the query key set targets `A` (52-byte key form: `key.len() == 52` branch in `verify_state_proof`).

```rust
pub fn fetch_trie_id_from_main_proof<H: IsmpHost>(
	proof: &[Vec<u8>],
	root: H256,
	key: &[u8],
) -> Result<Vec<u8>, SubstrateEvmError> {
	let db = StorageProof::new(proof.to_vec()).into_memory_db::<BlakeTwo256>();
	let trie = TrieDBBuilder::<LayoutV0<BlakeTwo256>>::new(&db, &root).build();

	let val = trie
		.get(key)
		.map_err(|e| SubstrateEvmError::TrieError(format!("{:?}", e)))?
		.ok_or(SubstrateEvmError::ContractInfoNotFound)?;

	let account_info = AccountInfo::decode(&mut &val[..])
		.map_err(|_| SubstrateEvmError::AccountInfoDecodeError)?;

	let AccountType::Contract(contract_info) = account_info.account_type;

	Ok(contract_info.trie_id)
}
```
