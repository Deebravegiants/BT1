Confirmed: `Message.timeout()` treats `timeoutTimestamp == 0` as `type(uint64).max`, i.e. these governance messages **never expire**.

### Title
Stale IntentGatewayV2 governance updates (UpdateParams/NewDeployment/SweepDust) can be OOG-failed then replayed later to undo newer governance state - (File: evm/src/core/EvmHost.sol)

### Summary
Governance messages dispatched from Hyperbridge to `IntentGatewayV2.onAccept` (`UpdateParams`, `NewDeployment`, `SweepDust`) are sent with `timeoutTimestamp: 0`, which `Message.timeout()` maps to `type(uint64).max` — i.e. they never time out. `EvmHost.dispatchIncoming` writes the request receipt, forwards the call to the app's `onAccept`, and if that call fails for any reason (including running out of gas), it **deletes** the receipt "so it can be retried" rather than reverting the whole batch. Because `handlePostRequests` is permissionless and callers control the overall transaction's gas limit, anyone can deliberately under-fund a delivery so it fails deep inside `onAccept` due to out-of-gas, without reverting the outer transaction. The message is then left permanently replayable (no timeout, no receipt) and can be resubmitted later — after newer, legitimate governance updates have landed — with enough gas to succeed, silently reverting `_params`/`_destinationProtocolFees`/`_instances` to a stale, superseded value.

### Finding Description
`EvmHost.dispatchIncoming` performs the app callback via a raw, gas-unbounded `.call`: [1](#0-0) 

If `success` is false the receipt for that commitment is deleted and the function simply `return`s without reverting the outer `handlePostRequests` transaction: [2](#0-1) 

`HandlerV2.handlePostRequests` only rejects a request when `timestamp >= leaf.request.timeout()`: [3](#0-2) 

`Message.timeout()` converts `timeoutTimestamp == 0` into `type(uint64).max`, so a request dispatched with `timeoutTimestamp: 0` can never time out: [4](#0-3) 

Hyperbridge governance dispatches `NewDeployment`, `UpdateParams`, and `SweepDust` requests to `IntentGatewayV2` with exactly `timeoutTimestamp: 0` (visible throughout the test-suite constructions of these `PostRequest`s), and `IntentGatewayV2.onAccept` applies them unconditionally to `_params`, `_destinationProtocolFees`, and `_instances` whenever the caller is `hyperbridge`: [5](#0-4) 

There is no nonce, sequence number, or "supersedes older update" check on these governance calls — the handler simply overwrites state with whatever `ParamsUpdate`/`Deployment` payload is delivered, regardless of when that payload was originally produced relative to other, more recent governance updates.

The combination is directly analogous to the ECO L2 bridge report: an attacker (any address, since `handlePostRequests` is permissionless) can:
1. Wait for (or observe) a governance `UpdateParams`/`NewDeployment` message `M1` (old, soon to be superseded) proven against a valid state commitment.
2. Submit `handlePostRequests` for `M1` with a transaction gas limit calibrated so that `EvmHost.dispatchIncoming`'s `.call` to `IntentGatewayV2.onAccept` runs out of gas mid-execution. The sub-call fails, `success == false`, the receipt is deleted, and the outer transaction **does not revert**.
3. `M1`'s commitment is now available for replay indefinitely because `timeoutTimestamp == 0` never times out, and no receipt was recorded.
4. Time passes; Hyperbridge governance legitimately dispatches newer `M2`, `M3` messages that update `_params`/`_destinationProtocolFees`/`_instances` to current values, and they land successfully.
5. The attacker (or anyone) now resubmits `handlePostRequests` for the old `M1`, this time with sufficient gas. `dispatchIncoming` succeeds, and `IntentGatewayV2.onAccept` unconditionally overwrites `_params`/`_destinationProtocolFees`/`_instances` back to the stale values from `M1`, undoing all the intervening legitimate governance updates.

### Impact Explanation
This lets an unprivileged relayer/message-dispatcher force `IntentGatewayV2`'s critical protocol configuration (protocol fee bps, destination-specific fees, dispatcher/host addresses, price oracle, cross-chain gateway `_instances` mapping used for order routing/fee routing) back to an arbitrary older governance snapshot at a time of the attacker's choosing, indefinitely, since these messages never expire and receipts of failed deliveries are deleted rather than retained. Depending on which stale params get replayed, this can misroute funds (stale/incorrect `_instances` gateway addresses), apply incorrect protocol fees (potentially to the attacker's benefit or to grief the protocol/users), or reintroduce a decommissioned dispatcher/host/oracle address — a persistent governance-state integrity break reachable purely through permissionless message delivery.

### Likelihood Explanation
Exploitation only requires the ability to call `handlePostRequests` with a calibrated gas limit (fully within an ordinary user's control) and to later resubmit the same proof/message. No privileged role is needed; `handlePostRequests` and `dispatchIncoming`'s retry pathway are explicitly permissionless by design. The main precondition is that at least one governance update to `IntentGatewayV2` gets superseded by a subsequent one before the first is durably delivered — a realistic scenario for any protocol that periodically adjusts fees/deployments via cross-chain governance messages.

### Recommendation
- Add a monotonically increasing sequence number/nonce to `UpdateParams`/`NewDeployment`/`SweepDust` governance bodies and only apply an update if its sequence number is greater than the last applied one, so a stale message can never overwrite newer state even if replayed.
- Alternatively/additionally, give governance messages non-zero, bounded timeouts instead of `timeoutTimestamp: 0`, and/or have `EvmHost.dispatchIncoming` forward a capped, sufficient gas stipend to `onAccept` (and/or revert instead of silently allowing retry) so that intentionally-crafted OOG failures cannot be used to keep a message "alive" for later replay.

### Proof of Concept
1. Hyperbridge governance dispatches `M1 = UpdateParams(paramsA)` to `IntentGatewayV2` (`timeoutTimestamp: 0`).
2. Attacker calls `HandlerV2.handlePostRequests(host, proof(M1))` with `gasLimit` set such that, inside `EvmHost.dispatchIncoming`, the `.call` to `intentGateway.onAccept` for `M1` runs out of gas partway through applying `paramsA`. `success == false` → receipt deleted, outer tx succeeds (per `EvmHost.sol:809-816`). `M1` remains undelivered and un-timed-out.
3. Governance later dispatches and delivers `M2 = UpdateParams(paramsB)` normally; `IntentGatewayV2._params == paramsB`.
4. Attacker (or anyone) resubmits `handlePostRequests(host, proof(M1))` with adequate gas. `dispatchIncoming` succeeds; `IntentGatewayV2.onAccept` sets `_params = paramsA`, per `evm/tron/contracts/apps/IntentGatewayV2.sol:644-648`, silently reverting governance's `paramsB` update.

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
