### Title
RAY index-value overflow permanently freezes a large utilized market - (`common/src/rates/simulate.rs`)

### Summary
A market whose scaled supply or debt multiplied by its index exceeds `i128::MAX` makes accrual panic before the configured index ceiling can stop growth, permanently reverting `update_indexes`, repayments, withdrawals, liquidations, and other paths that synchronize the market. [1](#0-0) [2](#0-1) 

### Finding Description
`Controller::update_indexes(caller, assets)` is permissionless after caller authorization and forwards the supplied `Vec<HubAssetKey>` to the pool. [3](#0-2) [4](#0-3)   
Pool `update_indexes` loads each market and calls `interest::global_sync`, while every normal pool mutation also loads a synced market before applying its operation. [5](#0-4) [6](#0-5)   
Each accrual chunk first computes `borrowed * borrow_index` and `supplied * supply_index` in `scaled_to_original`, then updates the borrow index. [7](#0-6) [8](#0-7)   
`Ray::mul` resolves through `mul_div_half_up`, which panics with `MathOverflow` when the exact result cannot fit `i128`, even though the intermediate product is widened to `I256`. [9](#0-8) [10](#0-9)   
The borrow-index ceiling is applied only inside `update_borrow_index`, after this valuation step, so it does not prevent the market-total overflow that freezes accrual. [11](#0-10) [12](#0-11) 

### Impact Explanation
Once `scaled * index` exceeds the representable RAY-value domain, a later accrual cannot commit and the stored timestamp remains stale, making subsequent calls fail at the same or a worse point. [13](#0-12) [14](#0-13)   
Because `repay`, `withdraw`, `borrow`, `supply`, `seize_positions`, `recapitalize`, `claim_revenue`, and liquidation-related pool operations all synchronize before mutating, users cannot exit positions or reduce the overflowing totals through normal entrypoints. [6](#0-5) [15](#0-14)   
Even `update_params` cannot change the rate model to stop growth because it explicitly accrues under the old model before writing replacement parameters. [16](#0-15)   
The result is permanent freezing of supplier funds and trapped collateral in the affected market, with insolvency resolution also blocked because liquidation and bad-debt settlement require synced pool operations. [17](#0-16) [2](#0-1) 

### Likelihood Explanation
The trigger does not require privileged access at execution time: after normal supply and borrowing create a sufficiently large utilized book, any address can call `update_indexes(caller, vec![hub_asset])`. [3](#0-2) [5](#0-4)   
The admitted cap domain permits large positions, but the documentation acknowledges that valid caps and bounded indexes do not guarantee future accrued totals fit and that repayment or withdrawal can be blocked by value overflow. [18](#0-17)   
A repository regression test demonstrates a reachable configuration using an 18-decimal market at 98% utilization: repeated yearly accrual fails below `MAX_BORROW_INDEX_RAY`, after which both withdrawal and repayment return `MathOverflow`. [19](#0-18)   
The practical precondition is a very large market and sustained utilization over multiple accrual periods, so it is less likely than an ordinary rounding bug but does not rely on privileged behavior, malformed state, oracle manipulation, or an impossible entrypoint. [20](#0-19) [21](#0-20) 

### Recommendation
Calculate utilization and projected index bounds without requiring the full `scaled * index` market values to fit `i128`, or clamp indexes to the largest value representable for the current scaled totals before persisting them. [22](#0-21) [23](#0-22)   
Once the index cap or representable-value ceiling is reached, accrual should become a safe no-op instead of repeatedly evaluating overflowing totals, and the regression case should assert that `repay`, `withdraw`, and liquidation remain executable at that boundary. [11](#0-10) [24](#0-23) 

### Proof of Concept
1. In an admitted 18-decimal debt market with sufficient caps, an attacker supplies liquidity and supplies separate collateral, then borrows approximately 98% of that market through `Controller::borrow(caller, account_id, vec![(debt_asset, amount)], None)`. [25](#0-24) [26](#0-25) 
2. Allow ledger time to advance while utilization remains high, then any address submits `Controller::update_indexes(caller, vec![debt_asset])`. [3](#0-2) 
3. Accrual reaches a point where `borrowed * borrow_index` or `supplied * supply_index` no longer fits `i128`, and `mul_div_half_up` panics with `MathOverflow` before `last_timestamp` is committed. [27](#0-26) [10](#0-9) 
4. Subsequent `repay`, `withdraw`, and liquidation paths cannot reduce the position because each loads a synced market and repeats the overflowing accrual before processing the requested action. [6](#0-5) [28](#0-27)

```rust
pub(crate) fn synced_market(env: &Env, hub_asset: &HubAssetKey) -> Cache {
    let mut cache = Cache::load(env, hub_asset);
```

```rust
pub fn mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> i128 {
    // The zero check runs first so debug and release builds agree on a zero
    // divisor: both surface `DivisionByZero` rather than tripping the assert.
    require_nonzero_divisor(env, d);
    debug_assert!(
        x >= 0 && y >= 0 && d > 0,
        "mul_div_half_up: non-negative x, y and positive d"
    );
    try_mul_div_half_up(env, x, y, d)
        .unwrap_or_else(|| panic_with_error!(env, GenericError::MathOverflow))
}

/// Computes `x * y / d` rounded half up. Returns `None` if `x < 0`, `y < 0`, `d <= 0`, or the
/// result does not fit in `i128`.
pub fn try_mul_div_half_up(env: &Env, x: i128, y: i128, d: i128) -> Option<i128> {
    if x < 0 || y < 0 || d <= 0 {
        return None;
    }
    let half = d / 2;

    // Fast path: the biased product fits `i128`, so the whole computation is
    // native. `x * y + half` is non-negative here, so `/` is the floor the
    // widened path would produce.
    if let Some(biased) = x
        .checked_mul(y)
        .and_then(|product| product.checked_add(half))
    {
        return Some(biased / d);
    }

    let (x256, y256, d256) = to_i256_operands(env, x, y, d);
    x256.mul(&y256)
        .add(&I256::from_i128(env, half))
        .div(&d256)
        .to_i128()
}
```

```rust
pub(crate) fn global_sync(env: &Env, cache: &mut Cache) {
    if !cache.needs_accrual() {
        return;
    }

    let mut remaining = cache.elapsed_ms();
    while let Some(nonzero) = NonZeroU64::new(remaining) {
        let chunk = nonzero.get().min(MAX_COMPOUND_DELTA_MS);
        accrue_chunk(env, cache, chunk);
        remaining = remaining.saturating_sub(chunk);
    }

    cache.mark_accrued();
}
```

```rust
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );

    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
```
