Based on my review, the closest and strongest reachable analog to the wXTZ bug in the Hyperbridge codebase is in the shared `CallDispatcher` contract used by `HyperFungibleToken`, `WrappedHyperFungibleToken`, and `IntentGatewayV2`.

### Title
Permissionless `CallDispatcher.dispatch()` lets anyone claim tokens minted or escrowed to the shared dispatcher contract - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher` is a single, chain-wide shared contract referenced by `HyperFungibleToken`, `WrappedHyperFungibleToken`, `BridgeToken`, and `IntentGatewayV2` deployments for executing arbitrary calldata during cross-chain token delivery and order fulfillment. Its `dispatch()` function is `external` with no caller restriction and no notion of "who owns" the balance currently sitting in the contract, exactly analogous to the wXTZ finding where the token contract failed to check approvals when `from` was the contract itself, letting anyone claim tokens the contract held.

### Finding Description
`CallDispatcher.dispatch()` takes an ABI-encoded `Call[]` and blindly executes each call from the dispatcher's own context, with no `onlyGateway`/`onlyToken`/access-control check on `msg.sender`: [1](#0-0) 

`HyperFungibleToken.onAccept` mints tokens directly to the beneficiary (which the documentation explicitly instructs callers to set to the `CallDispatcher` address itself when the attached calldata needs to spend the bridged tokens), then invokes `ICallDispatcher(_dispatcher).dispatch(message.data)` with **no subsequent sweep** of any residual balance: [2](#0-1) 

The documentation confirms this "mint-to-dispatcher-then-execute" pattern and explicitly acknowledges that "the dispatcher contract holds tokens temporarily during execution": [3](#0-2) 

Because a single `CallDispatcher` instance is shared across every app that references it on that chain, and `dispatch()` is callable by anyone at any time, any tokens that are not perfectly and completely consumed by the attached `Call[]` (e.g., due to slippage on a swap, a partially-filled DEX order, calldata that doesn't route 100% of the minted/escrowed balance out, or simply an imprecise sender-provided calldata payload) remain sitting in the `CallDispatcher` after the triggering transaction completes. Since `dispatch()` performs no ownership/authorization check, any unrelated third party can subsequently call `CallDispatcher.dispatch()` with their own `Call[]` (e.g., an ERC20 `transfer` to themselves) and permanently claim that residual balance — the same "no approval/ownership check when funds are held by the contract itself" root cause identified in TOB-WXTZ-011.

By contrast, `IntentGatewayV2` mitigates this same risk in its own flows by always sweeping the dispatcher's **full** balance back to itself after every `dispatch()` call in `placeOrder`/`_execute`: [4](#0-3) 
— but `HyperFungibleToken.onAccept` and `WrappedHyperFungibleToken` have no equivalent sweep-back step, and even IntentGatewayV2's sweep only protects against dust created within its own atomic transaction, not dust left behind by a different app instance sharing the same `CallDispatcher`.

### Impact Explanation
Tokens minted by a `HyperFungibleToken`/`WrappedHyperFungibleToken` `onAccept` delivery, or any token temporarily routed through the shared `CallDispatcher` by any app, can be permanently stolen by an unrelated third party if the attached calldata does not perfectly drain the balance it created. This is a direct loss-of-funds vector reachable by a single relayed cross-chain message (an unprivileged token bridger's own `send()` with attached calldata, or a malformed/partially-effective calldata payload) — no privileged role is required to exploit it, only to observe a nonzero balance sitting in a public, unauthenticated contract.

### Likelihood Explanation
Any sender using the documented "mint-to-CallDispatcher-then-swap" pattern with realistic slippage tolerances, partial fills, or calldata that doesn't route every wei of the delivered token will leave dust behind. Given CallDispatcher is a public, well-known, unauthenticated contract address, monitoring it for a nonzero token balance and immediately calling `dispatch()` to sweep it is trivial and requires no special access — front-running bots already operate in this ecosystem (as evidenced by the MEV-aware bidding/paymaster infrastructure documented elsewhere in the repo).

### Recommendation
**Short term:** Restrict `CallDispatcher.dispatch()` (or add an `onBehalfOf`/authorized-caller variant) so that only the app which deposited tokens into it in the same transaction can invoke it, or require every app that mints/transfers into the dispatcher to sweep 100% of the resulting balance back to itself before returning control (as `IntentGatewayV2` already does), and add the same sweep-back to `HyperFungibleToken.onAccept`/`WrappedHyperFungibleToken`.

**Long term:** Avoid a single, permissionless, shared custody contract for arbitrary token holding across unrelated apps; instead scope call-execution contexts per-app-per-transaction (e.g., ephemeral per-call proxies or `delegatecall` from the app's own storage-isolated helper) so that no third party can ever observe or act on a balance that isn't theirs.

### Proof of Concept
1. A user calls `HyperFungibleToken.send()` on chain A with `to = CALL_DISPATCHER_ADDRESS` and `data` encoding a swap `Call[]` that spends slightly less than 100% of the bridged amount (e.g., an exact-output swap, or a swap with a minimum-out guard that leaves the remainder unswapped).
2. On chain B, a relayer delivers the message; `onAccept` mints the full `amount` to the `CallDispatcher`, then executes `data` via `dispatch()`. The swap consumes only part of the minted balance; the remainder stays in `CallDispatcher`.
3. Any third party (no special role, no approval) observes the nonzero token balance on the well-known `CallDispatcher` address and calls `CallDispatcher.dispatch()` directly with a `Call[]` containing an ERC20 `transfer(attacker, residualBalance)` call — this succeeds because `dispatch()` has no access control and `CallDispatcher` itself holds the tokens with no owner tracking.     function dispatch(bytes memory encoded) external {
```text
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
```

```text
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
```

```text
Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.

Existing `CallDispatcher` deployments are listed on the [contract addresses](/developers/evm/contract-addresses/mainnet) page.
```
