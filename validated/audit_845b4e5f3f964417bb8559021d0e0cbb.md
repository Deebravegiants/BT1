### Title
Signup-extension flag lets an unprivileged QR-code presenter bypass backend operator/user authorization entirely - ([File: src/plans/mod.rs])

### Summary
The external report describes a gateway that is supposed to be permissioned (single authorized operator) for subnet creation, but the code accepts the request without checking who the caller is, letting anyone register state that the system controls funds around. The orb-core analog is the "signup extension" code path: normal signups must be authorized by the backend via `verify_operator_qr_code` and `verify_user_qr_code`, but if the operator and user QR codes both carry a self-declared `signup_extension` flag, both authorization calls are skipped completely and the Orb proceeds straight into biometric capture, without any backend-side check that either QR code is a legitimate, registered operator/user.

### Finding Description
`MasterPlan::verify_operator_qr_code` normally calls the backend `operator_status::request` to validate an operator QR code. However, it short-circuits this authorization check entirely when the parsed QR data reports `signup_extension() == true`: [1](#0-0) 

Likewise, `MasterPlan::handle_user_qr_code` is supposed to call `verify_user_qr_code` (which hits the backend `user_status::request` endpoint) for every scanned user QR code. But if either the operator or the user QR code declares itself a `signup_extension`, and both provide a `signup_extension_config`, the function returns success immediately with a default, unauthenticated `UserData`, never calling `verify_user_qr_code`: [2](#0-1) 

The `signup_extension` flag and its `signup_extension_config` are attacker-controlled: they are simply fields parsed out of the plaintext QR-code string by `qr_scan::user::Data::try_parse`, and `qr_scan::operator::Data::try_parse` accepts any `user::Data`-shaped QR code (including one with `signup_extension` set) as a valid "operator" QR code as long as a config is present — no cryptographic signature or backend round-trip is required to produce a QR code that satisfies these conditions: [3](#0-2) 

The intended gating for this feature is the `internal-data-acquisition` Cargo feature, which filters out `signup_extension` QR codes when `self.data_acquisition` is `false`: [4](#0-3) 

But that filter is compiled out entirely (`#[cfg(feature = "internal-data-acquisition")]`) in builds that don't enable this feature, so the un-gated bypass in `handle_user_qr_code` (lines 1060–1083) and in `verify_operator_qr_code` (lines 1550–1557) remains fully reachable in any build that doesn't specifically compile with `internal-data-acquisition`. Downstream, `do_signup` treats a signup carrying `signup_extension_config` as automatically "successful" once capture completes, bypassing the normal enrollment/authorization pipeline: [5](#0-4) 

This mirrors the root cause in the external report exactly: a state-changing action (here, "authorize and start a signup session" rather than "register a subnet") that should require an authorization check against a trusted authority (the backend / gateway owner) is instead permissionless — gated only by a value the untrusted caller supplies itself (the `signup_extension` flag in the QR text vs. `msg.sender` claims in `register()`).

### Impact Explanation
Any person able to present two printed/displayed QR codes to the Orb's camera (no privileged operator credentials, no backend account, no cryptographic material) can force the Orb into a code path that skips both operator identity validation and user identity/session validation against the backend, while still triggering a real biometric capture and, depending on downstream handling of `signup_extension_config`, causing the Orb to report signup success and enter the data-acquisition/PCP pipeline. This breaks the signup-authorization trust boundary the backend is relied upon to enforce (`operator_status`/`user_status` checks exist specifically to ensure only legitimate, backend-registered operators/users trigger biometric capture and identity binding). Depending on how `signup_extension_config` values are subsequently consumed by data-acquisition machinery, this can result in unauthorized biometric capture/session creation attributed to a QR-code the attacker fully controls, since no backend-issued identity commitment or public key is ever obtained (`UserData::default()` is used).

### Likelihood Explanation
Likelihood is high in any build where the `internal-data-acquisition` Cargo feature is not enabled, since the guard that would normally reject `signup_extension` QR codes (lines 1019–1028) does not exist in the compiled binary, while the un-gated bypass logic in `verify_operator_qr_code` and `handle_user_qr_code` is unconditionally present. The QR-code format required to trigger it is plaintext and requires no secret, so it is trivially constructible by any external, unprivileged attacker with physical access to present a QR code to the Orb.

### Recommendation
Do not let a value self-declared in scanned QR-code content (`signup_extension`) skip the backend authorization calls (`operator_status::request`, `user_status::request`). Either:
1. Require that `signup_extension` QR codes still pass through backend validation (only skipping validation for a distinct, backend-verified "data acquisition" credential), or
2. Ensure the `signup_extension` bypass logic in `verify_operator_qr_code` and `handle_user_qr_code` is itself compiled only under the `internal-data-acquisition` feature (matching the filtering logic that already exists at lines 1011–1028), so production builds without that feature can never reach the bypass branches.

### Proof of Concept
1. Build/run orb-core without the `internal-data-acquisition` feature (the default/production configuration).
2. Craft an "operator" QR code string that parses via `qr_scan::user::Data::try_parse` into data where `signup_extension() == true` and `signup_extension_config` is `Some(...)` (format based on `qr_scan::user::Data`'s plaintext QR schema, analogous to `DUMMY_OPERATOR_QR_CODE = "userid:66ad4897-0ca7-4727-8365-ca808348e3cd:1"` but with the additional signup-extension fields set).
3. Present this QR code to the Orb as the "operator" QR code. Because `qr_code.signup_extension()` is true, `verify_operator_qr_code` (`src/plans/mod.rs:1551-1557`) returns success immediately, without any backend HTTP call.
4. Craft a second QR code with `signup_extension() == true` and a matching `signup_extension_config`, and present it as the "user" QR code. Because both operator and user QR codes report `signup_extension()`, `handle_user_qr_code` (`src/plans/mod.rs:1060-1073`) returns success immediately with `backend::user_status::UserData::default()`, again without calling `verify_user_qr_code`/hitting the backend.
5. The Orb proceeds to `biometric_capture` and, per `do_signup` (`src/plans/mod.rs:556-561`), marks the signup as successful once capture completes, having never validated either QR code against the backend's operator/user status endpoints.
