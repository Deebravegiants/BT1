### Title
`validateBchAddress` accepts checksum-invalid legacy P2PKH/P2SH addresses on regex match alone, unlike all other legacy Base58Check validators in the same module - ([File: packages/intents-sdk/src/lib/validateAddress.ts])

### Summary
`validateBchAddress` (packages/intents-sdk/src/lib/validateAddress.ts:214-225) treats any string matching `/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/` or `/^3[1-9A-HJ-NP-Za-km-z]{25,34}$/` as a valid legacy BCH address without ever base58-decoding it or verifying its embedded double-SHA256 checksum. Every other Base58Check validator in the same file (`validateBtcBase58Address`, `validateLitecoinBase58Address`, `validateDashAddress`, `validateTronBase58Address`) decodes the address and verifies `sha256(sha256(payload))` matches the trailing 4 checksum bytes. The BCH CashAddr branch (`validateBchCashAddr` → `verifyBchChecksum`) also correctly enforces a polymod checksum. Only the BCH legacy branch skips checksum verification entirely.

### Finding Description
The broken equality is: *"a string accepted by `validateBchAddress` encodes a real, checksum-valid legacy BCH destination."* For the CashAddr path this holds (enforced by `verifyBchChecksum`, validateAddress.ts:271-310). For the legacy path it does not — lines 216-221 only check character-class/length via regex and return `true` immediately, with no call to `base58.decode` or any checksum comparison.

Call path: `sdk.createWithdrawalIntents` → `PoaBridge.validateWithdrawal` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:181-188) calls `validateAddress(args.destinationAddress, assetInfo.blockchain)`; for `Chains.BitcoinCash` this dispatches to `validateBchAddress`. If it returns `true`, validation proceeds and later `createWithdrawIntentPrimitive` → `createWithdrawMemo` (packages/intents-sdk/src/bridges/poa-bridge/poa-bridge-utils.ts:28-49) embeds `destinationAddress` verbatim into `memo: "WITHDRAW_TO:<address>"` for legacy-form addresses (no `bitcoincash:` prefix to strip). A single bit/character flip in a real legacy BCH address (e.g. a mistyped middle character) still matches the base58-alphabet regex and passes `validateBchAddress`, so the corrupted address is embedded in the on-chain intent memo with no correction opportunity.

Note: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.test.ts` shows BCH withdrawal tests are currently commented out "until POA Bridge API supports BCH" (lines ~310-318, ~572-576), meaning the live POA Bridge token list likely doesn't yet list BCH assets, so `validateWithdrawal`'s subsequent `getCachedSupportedTokens`/`UnsupportedAssetIdError` check would currently block this route in production. However, this is an operational/API-side gate, not a code-level guard — the `validateBchAddress` code path itself is live, exported, reachable, and defective independent of the current external token list.

### Impact Explanation
If/when BCH is enabled on the PoA bridge (or via any other route/consumer of `validateAddress`/`validateBchAddress` with `Chains.BitcoinCash`), a single mistyped character in a legacy-form BCH address bypasses the SDK's own address-integrity guard and gets embedded verbatim into the `ft_withdraw` intent's `WITHDRAW_TO` memo that is submitted on-chain. This matches the Critical category: "funds delivered to a wrong address/chain/contract with no recovery" — a checksum-invalid legacy address is typically unspendable or misrouted, and once the intent is executed there is no on-chain correction mechanism.

### Likelihood Explanation
Preconditions: a BCH withdrawal route using `Chains.BitcoinCash` with a legacy-form (`1...`/`3...`) `destinationAddress`. Attacker cost is zero — this can occur from ordinary user typo/clipboard corruption, not even active attacker input; the caller simply supplies a slightly wrong string. It is fully reproducible and would trigger every time such a malformed legacy address is submitted, only gated today by BCH not yet being listed in the live PoA supported-token list (an external/operational state, not a code fix).

### Recommendation
In `validateBchAddress` (packages/intents-sdk/src/lib/validateAddress.ts), replace the regex-only legacy branch with a real Base58Check decode-and-checksum-verify step mirroring `validateBtcBase58Address`: decode via `base58.decode`, confirm 25-byte length, confirm version byte is `0x00` (P2PKH) or `0x05` (P2SH), and verify the trailing 4 bytes equal `sha256(sha256(payload)).subarray(0,4)`.

function validateBtcBase58Address(address: string): boolean {
	const decoded: Uint8Array = base58.decode(address);

	// version (1) + hash160 (20) + checksum (4) = 25 bytes
	if (decoded.length !== 25) return false;

	const version = decoded[0];
	// 0x00 = P2PKH mainnet, 0x05 = P2SH mainnet
	if (version !== 0x00 && version !== 0x05) return false;

	const payload = decoded.subarray(0, 21);
	const checksum = decoded.subarray(21, 25);
	const expectedChecksum = sha256(sha256(payload)).subarray(0, 4);

	for (let i = 0; i < 4; i++) {
		if (checksum[i] !== expectedChecksum[i]) return false;
	}
	return true;
}

export function validateBchAddress(address: string): boolean {
	// Legacy address format (same as Bitcoin)
	if (
		/^1[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(address) ||
		/^3[1-9A-HJ-NP-Za-km-z]{25,34}$/.test(address)
	) {
		return true;
	}

	// CashAddr format
	return validateBchCashAddr(address);
}

function createWithdrawMemo({
	receiverAddress,
	xrpMemo,
}: {
	receiverAddress: string;
	xrpMemo: string | undefined;
}) {
	// Strip "bitcoincash:" prefix from BCH CashAddr addresses
	const normalizedAddress = receiverAddress
		.toLowerCase()
		.startsWith("bitcoincash:")
		? receiverAddress.slice("bitcoincash:".length)
		: receiverAddress;

	const memo = ["WITHDRAW_TO", normalizedAddress];

	if (xrpMemo != null && xrpMemo !== "") {
		memo.push(xrpMemo);
	}

	return memo.join(":");
}
