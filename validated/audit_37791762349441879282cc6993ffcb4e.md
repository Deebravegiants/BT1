### Title
Permanent Curve-Freeze via Token Donation Blocking the Supply-Trigger Graduation Check - ([File: packages/contracts/src/Bonding.sol])

### Summary
Graduation from the bonding curve to the HyperSwap V2 pool is gated by two triggers: a USD-value trigger and a supply trigger defined as `IPair.tokenBalance() == 0` [1](#0-0) . Because `tokenBalance()` is a live `balanceOf` read rather than an internal reserve counter [2](#0-1) , any unprivileged holder can permanently defeat the exact-zero equality check by donating a trivial amount (as little as 1 wei) of the launched `Token` directly to the `Pair` contract via a plain ERC20 `transfer`, right before the curve would otherwise fully sell out.

### Finding Description
The dual-trigger design explicitly documents that the supply trigger is "donation-resistant in the opposite direction — token donations can only INCREASE the balance and can never satisfy `== 0`" [3](#0-2) . This property, framed as a defense against artificially forcing a *premature* graduation, has an unaddressed inverse consequence: it also means an attacker can indefinitely *prevent* a legitimate graduation for any token whose paired LT has a flat/stable exchange rate (so the USD trigger, `(storedAssetReserve − virtualLtReserve) × exchangeRate ≥ $9K`, never fires) [4](#0-3) .

`Router._computeBuy` caps `tokensOut` at `pair.tokenBalance()` (the real, donation-inflated balance) rather than at the internal `reserveToken` bookkeeping value [5](#0-4) . As the last real tokens on the curve approach exhaustion, an attacker front-runs (or simply times) the final draining buy with a `Token.transfer(pair, 1)` donation. This keeps `tokenBalance()` at 1 wei instead of 0 immediately after the drain, so `canGraduate()`'s supply check `tokenBalance() == 0` never evaluates true — and since the buy that would have exhausted supply is now capped at the (attacker-inflated) balance, no further whole-token buy can naturally reach exact zero either. The attacker can repeat this cheap donation (≈1 wei of token + gas) every time the balance nears zero, indefinitely holding the token in `Lifecycle.Curve`.

### Impact Explanation
While the token is stuck pre-graduation:
- The 250M `LP_RESERVE` tokens cached in `Bonding` for LP seeding, and all real LT raised by the curve, can never be moved into the HyperSwap TOKEN/LT pool via `_enterGraduating`/`finalizeGraduation`, permanently freezing that LP-bound capital.
- Traders and the token's creator can never realize the graduated, freely-tradable DEX market for the token — buys/sells remain confined to the internal AMM curve indefinitely, even though the curve is economically exhausted.
- This is a permissionless, cheap (sub-cent), and repeatable griefing vector reachable purely through direct ERC20 transfers to the `Pair` address, satisfying "permanent freezing of trader, creator or LP funds."

The severity is bounded by the fact that sells/redeems continue to function (holders are never prevented from exiting to LT/USDC), and the attack requires ongoing attention/timing to intercept the exact draining transaction each time supply approaches zero, rather than a single one-shot freeze.

### Likelihood Explanation
Medium. It requires: (a) an LT whose `exchangeRate()` stays flat long enough that the USD trigger never crosses $9K, and (b) the attacker to monitor and time a cheap donation against the specific buy that would otherwise zero out the pair's real token balance. This is realistic for a flat/bear-market token — which the protocol's own documentation calls out as exactly the scenario the supply trigger exists to handle [3](#0-2) , meaning the griefing path directly targets the fallback mechanism intended for that exact market condition.

### Recommendation
Change the supply trigger to be based on internal curve accounting (e.g., the `Pair`'s stored `tokenReserve` reaching the virtual-reserve floor, or comparing against `reserveToken - curveSupply` sold-out state) rather than a live, donation-inflatable `balanceOf` read. Alternatively, have `_prepareGraduationLiquidity`/the trigger check treat any balance at or below a small dust threshold (not strictly `== 0`) as satisfying the supply trigger, while still sweeping/burning the excess dust as is already done for donations during `_prepareGraduationLiquidity`.

### Proof of Concept
1. Launch a token against an LT with a fixed/near-fixed `exchangeRate()` (so the USD trigger $9K threshold is never reached).
2. Buy from the curve repeatedly until the pair's real token balance (`Pair.tokenBalance()`) approaches 1 wei of the final sale.
3. Before the final draining buy lands (or in the same block via a bundle), call `Token.transfer(pairAddress, 1)` from any wallet holding at least 1 wei of the launched token (trivially obtainable from any prior buy).
4. Execute the buy that would otherwise leave `tokenBalance() == 0`; because of the donation, `tokenBalance()` remains ≥ 1.
5. Observe `Bonding.canGraduate(token)` (supply leg) never returns true, and repeat the 1-wei donation before any subsequent buy that would otherwise zero the balance — the token remains permanently in `Lifecycle.Curve`, and the 250M `LP_RESERVE` plus raised LT stay frozen in `Bonding`/`Pair` indefinitely.

    function _computeBuy(
        address pairAddr,
        uint256 amountIn
    ) internal view returns (uint256 amountInUsed, uint256 tokensOut) {
        IPair pair = IPair(pairAddr);
        (uint256 reserveToken, uint256 reserveAsset) = pair.getReserves();
        uint256 k = pair.k();

        amountInUsed = amountIn;

        uint256 newReserveAsset = reserveAsset + amountInUsed;
        tokensOut = reserveToken - (k / newReserveAsset);

        uint256 realBalance = pair.tokenBalance();
        if (tokensOut > realBalance) {
            tokensOut = realBalance;
            uint256 cappedReserveToken = reserveToken - tokensOut;
            if (cappedReserveToken == 0) revert OverflowCapDegenerate();
            uint256 cappedReserveAsset = (k + cappedReserveToken - 1) / cappedReserveToken;
            amountInUsed = cappedReserveAsset - reserveAsset;
        }
    }
