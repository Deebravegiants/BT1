### Title
Webhook `shop-domain` (and `topic`/`webhook-id`) header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw HTTP body for HMAC verification, while the `shop`, `topic`, `webhook_id`, and `api_version` values used by `ShopifyAPI::Webhooks::Registry.process` to attribute and dispatch the webhook are taken from unauthenticated HTTP headers. Any actor who can obtain one valid `(raw_body, hmac)` pair (trivially, the operator of their own installed shop, who legitimately receives webhooks addressed to themselves) can resend that exact body/HMAC pair with a different `X-Shopify-Shop-Domain` header, and the gem will accept it as an authentic webhook for the spoofed shop.

### Finding Description
`Utils::HmacValidator.validate` recomputes the signature over `verifiable_query.to_signable_string` and compares it to the supplied `hmac`: [1](#0-0) 

For webhooks, `to_signable_string` returns only the raw body: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from HTTP headers, which are not part of the signed material at all: [3](#0-2) 

`Registry.process` validates the HMAC (i.e., that the *body* is authentic) and then unconditionally trusts `request.shop` (a header) to build `WebhookMetadata` and route it to the app's handler for that shop's tenant: [4](#0-3) 

This breaks the intended identity binding: `shop == the shop whose secret authenticated this payload`. In reality, the equality that holds is only `hmac == HMAC(body, secret)`; the `shop` header is never bound to that computation. Any header value can be substituted without invalidating the signature, so:

`authenticated_scope (bytes actually verified = raw_body)` ≠ `bytes acted on to select tenant (shop header)`

This matches the "bytes verified vs. bytes parsed/acted on" and "shop authenticated vs. shop stored/used as tenant key" bug class: the app never verifies that the `shop-domain` header genuinely corresponds to the shop that owns the secret which produced the HMAC.

### Impact Explanation
An unprivileged actor who runs their own installation of the target app (a normal, low-privilege position — no `api_secret_key`, access token, or leaked credential needed) legitimately receives real webhooks for their own shop, each with a valid `(body, hmac)` pair signed by the app's shared `api_secret_key`. Because the header is unauthenticated, that actor can replay the identical `(body, hmac)` to the app's webhook endpoint while substituting `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) with an arbitrary victim shop's domain. `Utils::HmacValidator.validate` still succeeds because it only checks the raw body, and `Registry.process` then dispatches the payload to the handler labeled with the attacker-chosen shop. Any app logic keyed on `WebhookMetadata#shop` (e.g., updating per-merchant records, honoring `customers/redact` or `shop/redact` semantics, crediting/debiting merchant-specific state) is executed under a victim tenant's identity using attacker-controlled data — a cross-tenant access/data-integrity break, which the rules classify as Critical impact.

### Likelihood Explanation
Likelihood is high for any app builder integrating this gem as documented: no secret, credential, or privileged access is required — only the ability to install the app on one's own shop (or otherwise capture one legitimate webhook delivery) and issue a crafted HTTP POST with substituted headers to the app's public webhook endpoint, which is the exact call path the gem exposes via `Registry.process`.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise cryptographically tie the header claims to the payload before trusting them:
- Include `shop`, `topic`, and `webhook_id` in `Request#to_signable_string` (mirroring what `Oauth::AuthQuery#to_signable_string` already does for OAuth), so `HmacValidator.validate` fails if any of these are altered.
- Alternatively/additionally, cross-check the header-derived `shop` against an independent source of truth (e.g., a shop allow-list configured at webhook-registration time) before invoking the handler in `Registry.process`.

### Proof of Concept
1. App merchant "attacker.myshopify.com" installs the target app and legitimately receives a real webhook, e.g. for `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid, since `H = HMAC_SHA256(api_secret_key, B)`), plus `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the exact same request to the app's webhook endpoint, keeping body `B` and `X-Shopify-Hmac-Sha256: H` unchanged, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` (`lib/shopify_api/utils/hmac_validator.rb`) recomputes `HMAC_SHA256(api_secret_key, B)`, which still equals `H`, so validation passes.
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) builds `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed(B), ...)` and calls the registered handler, which now processes attacker-controlled order data as if it belonged to `victim.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
