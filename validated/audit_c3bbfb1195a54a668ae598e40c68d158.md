## Title
Webhook `shop` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The `shop` (tenant) identity that is subsequently handed to the app's webhook handler comes from the `X-Shopify-Shop-Domain` header, which is never included in the signed payload. Any party capable of obtaining one valid `(body, hmac)` pair for the shared app secret — e.g. by installing the app on their own (attacker-controlled) development/trial store — can replay that exact body/HMAC pair while substituting an arbitrary `shop-domain` header, and the gem will report it as an authenticated webhook for that other shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` is read straight from the (attacker-controllable at the transport layer) `shopify-shop-domain`/`x-shopify-shop-domain` header, independent of the HMAC: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `verifiable_query.to_signable_string` (the body), so it never authenticates `shop`: [3](#0-2) 

`Webhooks::Registry.process` uses this same, unauthenticated `shop` value to build the `WebhookMetadata` object that is passed to the host application's handler — this is the value the app is expected to trust to identify which tenant the event belongs to: [4](#0-3) 

The binding the gem is supposed to guarantee is:
`hmac-verified request == request acted upon (including its shop)`

but in reality only `hmac-verified request body == request acted upon`, while `shop` is taken from an unauthenticated header. Because the webhook secret (`api_secret_key`) is shared across every shop that has the app installed (it is not per-shop), any store that installs the app — including one an attacker creates for themselves — will receive legitimate webhooks whose HMAC is valid under the same, single app secret. The attacker can capture a `(raw_body, hmac)` pair delivered to their own endpoint and replay it to the app's webhook endpoint with the `shop-domain` header changed to any other, victim shop that has installed the app. `Registry.process` will accept it as authentic (HMAC over body matches) and dispatch it to the handler tagged with the victim's shop domain, even though the body/content is fully attacker-controlled and the victim never sent this webhook.

### Impact Explanation
This breaks the multi-tenant identity boundary the gem is relied upon to enforce: an unprivileged party who merely has (or creates) any single valid app installation can forge webhook events attributed to an arbitrary other tenant (shop domain), without needing that tenant's access token, session, or the app's `client_secret`/`api_secret_key` directly. Any host application that uses `WebhookMetadata#shop` to select the tenant record/session against which the (attacker-controlled) `body` is applied — the intended and documented usage of this API — will perform cross-tenant writes/reads driven by forged data. This matches the "Critical - cross-tenant access" impact category, since the tenant boundary itself is what's compromised, driven purely by a gap in this gem's own signature-binding logic.

### Likelihood Explanation
Likelihood is high for any attacker willing to install the target app on a shop they control (Shopify development/trial stores are freely obtainable), since that is all that's required to obtain one valid `(body, hmac)` pair signed with the app's shared secret. No leaked credentials, TLS interception, or privileged access are needed — only the ability to send an HTTP POST to the app's public webhook endpoint with modified headers, which is inherent in how webhook endpoints are exposed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) into the value that is HMAC-verified, or otherwise cryptographically tie the authenticated body to the claimed shop domain before it is handed to consumers — e.g., include the `shop-domain` header in `to_signable_string`, or require host applications to cross-check `request.shop` against an independently maintained, previously-authenticated list of installed shop domains before trusting `WebhookMetadata#shop`. At minimum, the gem should document/enforce that `shop` is not authenticated by `HmacValidator.validate` so it is not relied upon as a trust boundary on its own.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, registering a webhook subscription that is delivered to the app's public webhook endpoint.
2. Shopify delivers a webhook to that endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)` — this is exactly what `ShopifyAPI::Webhooks::Request#hmac`/`#to_signable_string` will validate.
3. Attacker replays the exact same request (`raw_body = B`, `hmac-sha256 header = H`) to the same app endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (a shop that has separately installed the app).
4. `Utils::HmacValidator.validate` returns `true` (it only checks `B` against `H`), so `Registry.process` dispatches `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: parsed(B), ...)` to the handler — an event with attacker-controlled content is accepted as authentic for the victim's tenant.
