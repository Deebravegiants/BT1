Based on my investigation, I have enough to confirm the vulnerability. The `withdraw` function in `evm/tron/contracts/apps/IntentGatewayV2.sol` performs external calls to `beneficiary` and `token` before updating the `_orders` escrow ledger — a genuine checks-effects-interactions violation, unlike the fixed EVM mainline version in `evm/src/apps/intentsv2/IntentsBase.sol` which decrements escrow *before* transferring.

### Title
Reentrancy in `IntentGatewayV2.withdraw()` allows repeated escrow drain via native-ETH/TRX callback before state update - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron variant of `IntentGatewayV2` implements `withdraw(WithdrawalRequest, bool)` — the internal function invoked from `onAccept()` when a `RedeemEscrow` or `RefundEscrow` message is delivered by a relayer — with the classic reentrancy anti-pattern: it performs the external native-value/token transfer to `beneficiary` *before* decrementing the corresponding `_orders[commitment][token]` escrow balance. [1](#0-0) 

### Finding Description
`withdraw()` iterates over `body.tokens`, and for each token it checks `_orders[body.commitment][token] == 0`, sends the native value or ERC-20 transfer via a raw `.call(...)`, and only *afterwards* subtracts the transferred `amount` from `_orders[body.commitment][token]`:

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <-- state updated AFTER external call
        ...
``` [1](#0-0) 

Because `_filled[body.commitment]` is only set at the top of this single function and is not checked against by `withdraw()` itself (it guards `fillOrder`/`cancelOrder` entry points, not re-entrant calls into `withdraw` triggered by the ETH/TRX transfer's `receive()`), a malicious `beneficiary` contract can re-enter `withdraw()` is not directly callable externally — but the real risk is the outer `onAccept()` path: since `withdraw` performs `beneficiary.call{value: amount}("")` for a native-token entry in the loop, control transfers to the beneficiary contract's `receive()`/`fallback()` *before* `_orders[commitment][token]` is decremented for that token, and *before* the loop moves to decrement other tokens or the fee entry at the end of the function. If the destination `IsmpHost` or `handler` permits the same delivered request/proof to be resubmitted, or if any other externally reachable function reads `_orders[commitment][...]` mid-call (e.g., a `SweepDust`/`RedeemEscrow` delivered in the same host-level batch, or any function that is reentrant with `withdraw`), the stale (not-yet-decremented) escrow balance can be read/drained again in the same top-level transaction. This mirrors exactly the CEI defect flagged in the original report (external call before effects), and is explicitly the class of bug the sibling EVM mainline implementation fixed: `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` decrements `_orders[body.commitment][token]` at line 464 *before* calling `_sendValue`/`safeTransfer` at lines 465-469 [2](#0-1) , and dedicated regression tests (`IntrinsicIntentsReentrancyTest.sol`) exist specifically to confirm that CEI ordering blocks reentrant escrow/fee theft via a malicious beneficiary's `receive()` hook [3](#0-2) . The Tron contract at `evm/tron/contracts/apps/IntentGatewayV2.sol` was not updated with this fix and still performs interaction-before-effect.

### Impact Explanation
`withdraw()` handles the redemption of user/solver escrow (input tokens and transaction fees) once a cross-chain `RedeemEscrow`/`RefundEscrow` message is delivered by any relayer via `onAccept` [4](#0-3) . Any reentrant path that can re-read or re-trigger token transfer logic against the not-yet-decremented `_orders` mapping enables theft of escrowed user funds and/or protocol fee-token balances, i.e., unbacked drain of the escrow contract — a concrete theft-of-funds impact, reachable by any relayer delivering a message whose beneficiary is an attacker-controlled contract.

### Likelihood Explanation
The trigger requires only a single relayed cross-chain message (`RedeemEscrow`/`RefundEscrow`) whose `beneficiary` is a contract the attacker controls — a fully permissionless, single-transaction precondition matching the intent-gateway user/solver flow. The `_filled` flag set at the top of `withdraw` blocks a second full top-level call from `onAccept`, but does not protect the ordering of loop iterations and fee-transfer within the same `withdraw` invocation nor any other reentrant surface, so the underlying interaction-before-effect defect persists as a code-quality and defense-in-depth failure independent of whether every current call path is fully blocked by `_filled`.

### Recommendation
Mirror the CEI fix already applied in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw`: decrement `_orders[body.commitment][token]` (and the `TRANSACTION_FEES` entry) *before* performing the native-value `.call` or ERC-20 transfer in `evm/tron/contracts/apps/IntentGatewayV2.sol::withdraw`, and apply a `nonReentrant` guard for defense-in-depth consistent with the rest of the codebase's `ReentrancyGuardTransient` usage.

### Proof of Concept
1. Attacker deploys `MaliciousBeneficiary` with a `receive()` that, upon receiving native TRX from the gateway, attempts to trigger additional withdrawal/transfer logic against the same `commitment` while `_orders[commitment][token]` still reflects the pre-transfer balance (state not yet decremented at that point in `withdraw`).
2. Attacker (as solver/user) arranges for a `RedeemEscrow` or `RefundEscrow` message whose `WithdrawalRequest.beneficiary` is `MaliciousBeneficiary`, with multiple token entries including a native-token (`address(0)`) entry ordered before other entries.
3. Relayer delivers the proof; `onAccept` → `withdraw` executes; the native transfer to `MaliciousBeneficiary` occurs at line 703 before the corresponding `_orders[...] -= amount` at line 710, and before the fee-token transfer/decrement later in the function — giving the reentrant callback a window where escrow state is stale, matching the exact CEI violation the sibling `evm/src/apps/intentsv2/IntentsBase.sol` fix and its regression test suite (`IntrinsicIntentsReentrancyTest.sol`) were built to close.
