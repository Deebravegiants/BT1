### Title
Webhook `shop` (tenant) field is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body. The `shop` value that is subsequently trusted to identify the tenant for the handler is read from an HTTP header that is never included in the signed material, breaking the equality `HMAC-verified bytes == bytes used to establish tenant identity`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`#shop` is derived independently from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which plays no part in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)`, which calls `request.to_signable_string` (i.e., only the body) and `request.hmac`, then immediately dispatches to the handler using `request.shop` and `request.parsed_body` without any additional binding check between the two: [3](#0-2) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` using the app's `Context.api_secret_key`, which is the **same client_secret for every shop that installs the app**: [4](#0-3) 

Since the same secret signs webhooks for every installed shop, and the signature covers only the body (never the shop-domain header), a valid `(body, hmac)` pair genuinely produced by Shopify for one tenant (e.g., an attacker's own dev/test store, which they fully control and can trigger webhooks on) remains a **valid** signature for that identical body no matter what `shop` header accompanies it. `Registry.process` never checks that the `shop` header actually matches a shop this HMAC/body combination was generated for, because there is no cryptographic or app-level tie between them at all in this gem.

### Impact Explanation
An unprivileged attacker who is merely a legitimate installer of the target app on their own store can capture one authentic, correctly-signed webhook request (any topic triggered by their own store actions), then replay that exact `(raw_body, hmac header)` pair to the app's webhook endpoint while substituting an arbitrary victim shop domain in the `shop-domain` header. `HmacValidator.validate` will report success (the body/HMAC pair is genuinely valid for the app's `client_secret`), and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` with attacker-controlled `body`. Any host application that keys per-tenant side effects (order/customer/app-uninstall processing, data sync, GDPR redaction, billing state, etc.) off `WebhookMetadata#shop` as returned by this library will attribute attacker-controlled data to a shop the attacker does not own — a cross-tenant integrity/confidentiality violation reachable with no credentials beyond installing the app once on a store the attacker controls.

### Likelihood Explanation
Likelihood is limited by the need to first legitimately install the app once (or otherwise obtain one valid signed webhook and its body) to harvest a valid `(body, hmac)` pair, and then to be able to trigger network delivery to the app's endpoint with a forged shop header (feasible since webhook receiver endpoints are typically open, unauthenticated HTTP endpoints by design, and delivery does not require Shopify itself — any HTTP client can call the app's webhook route with attacker-chosen headers, as this gem parses headers directly from whatever the framework hands it). No `api_secret_key`, access token, or privileged account is required beyond the attacker's own store install.

### Recommendation
Include the tenant-identifying field (e.g., `shop` header value) inside the HMAC-signed material, or otherwise cryptographically bind the shop identity to the verified body (e.g., verify the shop is one this app installed and cross-check via a stored per-shop secret/session rather than the single shared `client_secret`), before trusting `Webhooks::Request#shop` in `Registry.process` / `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com`, triggers any webhook topic, and captures the raw POST: body `B` and header `X-Shopify-Hmac-Sha256: H` (a genuine signature computed with the app's shared `client_secret` over `B`, per `lib/shopify_api/utils/hmac_validator.rb`).
2. Attacker replays the identical `B` and `H` to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate(request)` recomputes HMAC over `to_signable_string` (`= B`) and compares against `H` — it matches because the signature never covered the shop header (`lib/shopify_api/webhooks/request.rb:20-38`).
4. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-200`) proceeds to call the handler with `shop: "victim-shop.myshopify.com"` and the attacker-controlled body, despite the request never having originated from or been signed for that shop.
