Audit Report

## Title
LDAP Authentication Bypass via Unauthenticated (Empty-Password) Bind - ([File: core/sessions/ldapauth/ldap.go])

## Summary
`ldapAuthenticator.CreateSession` and `TestPassword` authenticate a user solely based on whether `conn.Bind(dn, password)` returns `nil`, with no check that `password` is non-empty. [1](#0-0)  Per RFC 4513 §5.1.2, a bind with a non-empty DN and empty password is an "unauthenticated bind" that many LDAP servers accept as success without validating any credential, so this code path can grant a full session for any existing user email without knowing their password.

## Finding Description
`SessionsController.Create` binds the unauthenticated request body directly into `sessions.SessionRequest{Email, Password}` with no required validation on `Password`. [2](#0-1)  `SessionRequest.Password` carries no binding constraint. [3](#0-2) 

This flows into `ldapAuthenticator.CreateSession`, which builds the bind DN from the attacker-supplied email and calls `conn.Bind(searchBaseDN, sr.Password)`, checking only whether it returned an error: [1](#0-0)  If the target DN exists and the upstream LDAP server permits unauthenticated binds, `err` is `nil` even though `sr.Password` was empty. The code then proceeds to call `l.FindUser`, insert a row into `ldap_sessions` with the resolved real role, and emit `audit.AuthLoginSuccessNo2FA` — treating this as a fully authenticated login. [4](#0-3)  The local-admin fallback (`localLoginFallback`) is never reached in this flow since `returnErr` remains `nil`.

The same pattern exists in `TestPassword`, used during password-change re-authentication: `conn.Bind` result with `err == nil` is treated as password valid, with no empty-password guard. [5](#0-4) 

I confirmed there is no other layer (config validation, `LDAPClient`/`LDAPConn` wrapper, or `SessionRequest` binding tags) that rejects empty passwords before they reach `conn.Bind`: `client.go`'s `CreateEphemeralConnection` only performs the operator's own service-account bind to establish the connection, not the user credential check, and `LDAPConn.Bind` is a thin passthrough to the go-ldap library's simple bind. [6](#0-5) 

## Impact Explanation
An unauthenticated remote attacker who knows a valid user's email can authenticate as that user — including a node Admin — by submitting an empty password to `POST /sessions`, provided the operator's configured upstream LDAP server permits unauthenticated binds (the RFC-4513 default behavior unless the operator has explicitly hardened it). This results in full session/role impersonation using the real LDAP-derived role, i.e., an authentication and role bypass on the Chainlink node's web/API surface. The affected code path is only reachable in deployments that enable the optional LDAP auth provider (`AuthenticationProviderName: ldap`), so the local/default auth provider is unaffected. [7](#0-6) 

## Likelihood Explanation
The `POST /sessions` endpoint is public and requires no prior credential. [8](#0-7)  Exploitability is gated on the LDAP backend being enabled and on the specific upstream LDAP server's configuration permitting unauthenticated binds — this is an environment/deployment-dependent condition rather than a guaranteed default, but it is a well-documented RFC 4513 behavior that operators must explicitly disable (e.g., via `disallowUnauthenticatedBinds` on many LDAP servers) to avoid. Given LDAP auth is opt-in and the vulnerable code performs no defense-in-depth check, this is a legitimate, code-level authentication gap in the application itself, not merely a server misconfiguration issue — the application should never forward an empty credential as if it were a validated password check.

## Recommendation
In `core/sessions/ldapauth/ldap.go`, reject empty/blank passwords before calling `conn.Bind` in both `CreateSession` (check `sr.Password == ""`) and `TestPassword` (check `password == ""`), returning an authentication error immediately. As defense in depth, add `binding:"required"` to `SessionRequest.Password` in `core/sessions/session.go`.

## Proof of Concept
1. Enable the LDAP auth provider on a Chainlink node pointed at an LDAP server that permits unauthenticated binds (RFC 4513 default unless hardened).
2. Send `POST /sessions` with `{"email": "victim-admin@example.com", "password": ""}`.
3. `SessionsController.Create` forwards this to `ldapAuthenticator.CreateSession`, which calls `conn.Bind(dn, "")`; the LDAP server treats this as an unauthenticated bind and returns success.
4. The application creates a valid `ldap_sessions` row and session cookie bound to `victim-admin@example.com`'s real role, granting the attacker that user's session without knowing the actual password.
5. A Go unit test can mock `LDAPConn.Bind` to return `nil` for an empty-password call and assert `CreateSession` currently returns a valid session ID instead of an error, demonstrating the missing guard.

// CreateEphemeralConnection returns a valid, active LDAP connection for upstream Search and Bind queries
func (l *ldapClient) CreateEphemeralConnection() (LDAPConn, error) {
	conn, err := ldap.DialURL(l.config.ServerAddress())
	if err != nil {
		return nil, fmt.Errorf("failed to Dial LDAP Server: %w", err)
	}
	// Root level root user auth with credentials provided from config
	bindStr := l.config.BaseUserAttr() + "=" + l.config.ReadOnlyUserLogin() + "," + l.config.BaseDN()
	if err := conn.Bind(bindStr, l.config.ReadOnlyUserPass()); err != nil {
		return nil, fmt.Errorf("unable to login as initial root LDAP user: %w", err)
	}
	return conn, nil
}
