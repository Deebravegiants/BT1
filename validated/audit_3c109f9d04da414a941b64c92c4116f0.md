### Title
Webhook `shop` domain is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the request body, but the `shop` (and `topic`/`webhook_id`) values that are handed to the app's handler are taken directly from HTTP headers that are **not** included in the signed payload. This breaks the identity binding: `hmac_valid(body) == true` is treated as if it proves `shop_header == originating_shop`, when in fact those are two independent, unequal things.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are pulled straight from headers with no cryptographic protection: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (i.e. the raw body only) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` uses only that body-HMAC check as its authentication gate, then immediately builds `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` values and dispatches them to the app's handler as if they were verified: [4](#0-3) 

The identity binding the gem implicitly promises to the host application is:
`hmac_valid(body, secret) == true` implies `WebhookMetadata.shop == the shop that actually generated this webhook`.

In reality the binding that is enforced is only:
`hmac_valid(body, secret) == true` implies `body was produced using our shared secret at some point`,
with **no** guarantee that the `shop` header on this particular HTTP request is the shop that produced that body/HMAC pair.

Because the `client_secret`/`api_secret_key` is shared across every shop that installs the app (it is not per-tenant), any user who has legitimately installed the app on their own store receives real webhooks with a valid `(body, hmac)` pair signed with that same shared secret. That user can capture one such valid pair and replay it to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header to name a different, victim shop. `HmacValidator.validate` will still pass (it never looks at those headers), and `Registry.process` will call the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This is a cross-tenant identity-binding break: an attacker-controlled `shop` value is delivered to the host application's webhook handler carrying the credibility of a "verified" webhook, purely because the body's HMAC happened to be valid for *some* installation of the app. Any host application that uses `WebhookMetadata#shop` to select which tenant's session/access-token/database record to read, delete, or act on (a documented and expected usage pattern, since `shop` is the field the library exposes specifically for that purpose) can be tricked into applying attacker-supplied webhook data to a different merchant's tenant. This matches the "Critical - cross-tenant access" category, since it lets an unprivileged app installer forge webhook events that appear to originate from a shop they do not own or control.

### Likelihood Explanation
- Any user who can install the app on their own (even free/test) Shopify store automatically obtains at least one valid `(body, hmac)` pair for a webhook of their choosing (many webhook topics can be triggered directly by normal store actions, e.g. `orders/create`, `app/uninstalled`, `shop/update`).
- The webhook receiving endpoint is by design a public, unauthenticated HTTP endpoint (that is the entire point of webhooks), so replaying the captured request with a modified `shop` header requires no special access, credentials, or social engineering — only knowledge of the target's shop domain, which is often public.
- No mining, timing, or race condition is required, unlike the analog bug in the report; the exploit is a simple header substitution, making it straightforward for any unprivileged internet user with app access to attempt.
- Likelihood is tempered by the fact that impact depends on the host application actually keying tenant-sensitive operations off `WebhookMetadata#shop` without doing its own additional shop verification (e.g. cross-checking against a known/expected shop, or verifying the shop is one that has the app installed) — but the gem's public API and docs expose `shop` specifically for that consumption pattern, so this is a reasonably expected usage, not misuse of an undocumented feature.

### Recommendation
Bind the shop identity into the authenticated payload, e.g.:
- Include the `shop` (and ideally `topic`/`webhook-id`) header values in the HMAC-signed string that `HmacValidator` verifies, rather than signing only the raw body, so that tampering with those headers invalidates the signature; or
- Require/encourage the host app, and preferably do so within the gem itself, to verify that the `shop` header value corresponds to a shop for which the app holds an active session/installation before dispatching the handler, rather than trusting it implicitly once the body HMAC checks out.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and lets it register for a webhook topic (e.g. `orders/create`).
2. Attacker triggers that webhook (e.g. creates an order in their own store) and captures the raw HTTP request Shopify sends to the app's webhook endpoint, including the `X-Shopify-Hmac-Sha256` header and raw body.
3. Attacker replays this exact request to the app's public webhook endpoint, but changes only the `X-Shopify-Shop-Domain` header to `victim-shop.myshopify.com` (leaving body and HMAC untouched).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the HMAC of the unchanged body — validation succeeds.
5. The registered handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", topic: ..., body: <attacker's own order data>, ...)` and, if the host app uses `shop` to select or update per-tenant records, ends up applying the attacker's data under the victim shop's identity.

Note: Because this depends on how the host application consumes `WebhookMetadata#shop`, the exact downstream impact (e.g. data corruption, unauthorized state change) cannot be fully demonstrated purely within this gem — this is inherent to a library-level identity-binding gap and was confirmed at the code level (`request.rb`, `hmac_validator.rb`, `registry.rb`) rather than end-to-end in a full app deployment.
