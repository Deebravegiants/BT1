### Title
Status/tx-hash misattribution for batched PoA Bridge withdrawals of the same asset - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the completion status/tx hash of a specific withdrawal in a batch by matching on `assetId` alone, not on destination address, amount, or index. When a caller batches two or more withdrawals of the *same* `assetId` to *different* destination addresses in one intent, the bridge can report the wrong withdrawal's `txHash`/`status` for a given index.

### Finding Description
`createWithdrawalIdentifiers` (`packages/intents-sdk/src/core/withdrawal-watcher.ts:80-107`) assigns each withdrawal in a batch a per-bridge sequential `index`, and `PoaBridge.createWithdrawalIdentifier` stores that index in the `WithdrawalIdentifier` [1](#0-0) . However, `describeWithdrawal` never uses that `index` to disambiguate: it calls `findMatchingWithdrawal`, which is documented to only match by `assetId` [2](#0-1) :

```
NOTE: Currently only matches by assetId. This means multiple withdrawals
of the same token in a single transaction are not supported.
```

`describeWithdrawal` then returns whatever single matched withdrawal's status/`transfer_tx_hash` came back from the POA bridge indexer for *every* index that shares the same `assetId` [3](#0-2) . `watchWithdrawal` in the core watcher then reports that result as the completion of the specific withdrawal identified by `args.wid` (a specific `withdrawalParams`/index pair) [4](#0-3) .

Concretely: if a user (or an integrator on the user's behalf, unprivileged) submits a single intent with two `ft_withdraw` withdrawals for the same `assetId` (e.g. `nep141:usdc.omft.near`) to two different destination addresses A and B, `IntentsSDK.createWithdrawalCompletionPromises`/`waitForWithdrawalCompletion` will call `describeWithdrawal` separately for index 0 and index 1. Both calls hit `findMatchingWithdrawal`, which returns the *first* array element in the POA API response matching that `assetId` — regardless of which destination address or which of the two withdrawals it actually corresponds to. Because the POA API response order is not guaranteed to align with intent order (the code comment explicitly states the response list is unsorted), the withdrawal meant for destination B can be reported (with its real `txHash`) as the completion status of the withdrawal meant for destination A, and vice versa.

### Impact Explanation
This breaks the equality "status/txHash reported for withdrawal i == the actual on-chain outcome of withdrawal i." An integrator (exchange, custodial wallet, off-ramp) that relies on `waitForWithdrawalCompletion`/`describeWithdrawal` per-index results to mark a specific customer withdrawal as completed and release/credit funds could:
- Mark the wrong customer's withdrawal (to a different destination address) as completed, causing a double credit or incorrect settlement record for that customer.
- Falsely close out a withdrawal that was never actually sent to that customer's address, prompting release of funds elsewhere while the customer's own withdrawal request remains unresolved.

This matches the accepted impact class: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Reachable by any unprivileged user of the SDK who batches ≥2 withdrawals of the same `assetId` via the POA bridge route (the only precondition is having funds to withdraw the same token twice to different addresses — no privileged action by relayer/bridge/integrator required). Given the code's own comment acknowledging the limitation ("multiple withdrawals of the same token in a single transaction are not supported"), the condition is easy to trigger unintentionally as well (e.g., a user withdrawing the same stablecoin to two different exchange deposit addresses in one batch call), making likelihood moderate-to-high for integrators that support batch withdrawals through this SDK.

### Recommendation
Disambiguate matching in `findMatchingWithdrawal` using more than `assetId`: match on `assetId` + `destinationAddress` (+ `amount` if available) taken from `withdrawalParams`, and only fall back to positional/index matching after sorting both sides deterministically (e.g., by amount, as suggested in the existing code comment). Until POA's API provides a stable per-withdrawal correlation ID, `IntentsSDK` should reject or explicitly warn against batching multiple withdrawals of the same `assetId` through the POA bridge route rather than silently returning potentially misattributed statuses.

### Proof of Concept
1. Create a withdrawal batch: `withdrawalParams = [{assetId: "nep141:usdc.omft.near", amount: 100, destinationAddress: "A"}, {assetId: "nep141:usdc.omft.near", amount: 200, destinationAddress: "B"}]`.
2. Call `sdk.processWithdrawal`/`createWithdrawalCompletionPromises` for the batch; both entries route to `PoaBridge` and get indexes 0 and 1 via `createWithdrawalIdentifiers`.
3. Once the POA bridge indexer reports both withdrawals as `COMPLETED` (in arbitrary order relative to the intent), `describeWithdrawal({index:0,...})` and `describeWithdrawal({index:1,...})` both call `findMatchingWithdrawal(response.withdrawals, "nep141:usdc.omft.near")`, which — per its own documented behavior — returns the same element (`response.withdrawals.find(...)`, i.e., always the first matching element) for both calls, regardless of `index`.
4. As a result, `watchWithdrawal` reports the same `txHash` (and therefore the same on-chain destination) as the completion for both index 0 (destination A) and index 1 (destination B), even though only one of the two actual on-chain transfers matches that hash/destination — this is the misreport of status/txHash referenced in the finding. /**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}
