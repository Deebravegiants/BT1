### Title
PoA Bridge withdrawal status is matched only by `assetId`, causing wrong destination tx hash to be reported for batched same-token withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`createWithdrawalIdentifiers` assigns each withdrawal an `index` scoped per bridge route [1](#0-0) , but `PoaBridge.describeWithdrawal` never uses that `index` to disambiguate; it looks up the withdrawal purely by `assetId` via `findMatchingWithdrawal` [2](#0-1) . When a single NEAR transaction contains two or more withdrawal intents for the same token, both `WithdrawalIdentifier`s (index 0 and index 1) resolve to the *same* API record, so the caller reports the same destination tx hash / status for two logically distinct withdrawals.

### Finding Description
`findMatchingWithdrawal` intentionally ignores the withdrawal's position/index and returns the first API record whose `near_token_id` matches the `assetId` of the withdrawal being queried: [3](#0-2) . The comment above the function explicitly acknowledges that "multiple withdrawals of the same token in a single transaction are not supported" [4](#0-3) , but nothing in `createWithdrawalIntents`, `createWithdrawalIdentifier`, or the caller path (`createWithdrawalIdentifiers`) prevents or errors on this case — the index counter is simply incremented per bridge route without any check that the underlying assetId is unique [5](#0-4) .

The equality that should hold is: *the status/tx-hash reported for withdrawal #i must be the on-chain outcome of withdrawal #i specifically*. Because matching is done solely by `assetId` and the PoA API response list is unordered, `describeWithdrawal` for index 0 and index 1 (same token) both call `.find()` over the same `withdrawals` array and get the identical first match: [6](#0-5) . If the two withdrawals have different destination addresses/amounts but the same token, one of them is reported with the wrong `transfer_tx_hash`/status while the second withdrawal is left unmatched (and stays `pending` forever, since the matching record was already "claimed" by the first).

This is invoked through `watchWithdrawal`/`createWithdrawalCompletionPromises`, where the `status.txHash` is trusted directly as the on-chain outcome for that specific `WithdrawalIdentifier`: [7](#0-6) .

### Impact Explanation
This is a status/hash misreport scenario explicitly called out as in-scope impact ("a status or hash misreport making an integrator credit or refund twice"). An integrator that batches two withdrawals of the same PoA token (e.g., two BTC withdrawals to different addresses in one `sendWithdrawals`/intent transaction) and relies on the SDK's `describeWithdrawal`/`watchWithdrawal` result to confirm completion and to credit/reconcile the destination transaction could:
- Attribute the same destination tx hash to both withdrawals (double-crediting/reconciling one destination payment against two internal withdrawal records), or
- Have the second withdrawal remain stuck in `pending` indefinitely because its matching API record was already consumed by the first lookup, requiring manual intervention.

### Likelihood Explanation
This requires no malicious actor — it is triggered by an entirely legitimate, unprivileged usage pattern (a single caller batching two withdrawals of the same PoA-bridged token in one transaction), which the public `WithdrawalParams[]` / `createWithdrawalIntents` API does not prevent. The code comment shows the authors are aware this case is unhandled, but there is no validation guarding against it.

### Recommendation
Either:
1. Reject/validate at `createWithdrawalIntents`/`createWithdrawalIdentifiers` time when multiple withdrawal params for the same PoA-bridge `assetId` appear in a single batch, or
2. Extend `findMatchingWithdrawal` to disambiguate using the withdrawal's amount/index (as the existing comment suggests: sort both API results and withdrawal params by amount, since fees are equal for same token, so relative ordering is preserved) so that each `WithdrawalIdentifier.index` maps deterministically to a distinct API record.

### Proof of Concept
1. Build one NEAR transaction with two PoA-bridge `ft_withdraw` intents for the same token (e.g., `nep141:btc.omft.near`) to two different destination addresses/amounts, via `sdk.createWithdrawalIntents` for two `WithdrawalParams` entries.
2. Call `createWithdrawalIdentifiers` — this yields `wid` #0 and `wid` #1, both with `bridge.route === RouteEnum.PoaBridge` and identical `withdrawalParams.assetId`, per [8](#0-7) .
3. Once the PoA API reports both withdrawals as `COMPLETED` (two separate records with different `transfer_tx_hash` in `response.withdrawals`), call `bridge.describeWithdrawal` for both `wid`s.
4. `findMatchingWithdrawal` uses `Array.prototype.find`, which returns the first array element matching `nep141:${near_token_id} === assetId` for *both* calls, per [9](#0-8)  — both `wid` #0 and `wid` #1 receive the same `{status: "completed", txHash: <first record's transfer_tx_hash>}`, even though wid #1's real on-chain destination transaction is different (and its status query for `wid` #1's real tx hash is never surfaced).

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

		}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
