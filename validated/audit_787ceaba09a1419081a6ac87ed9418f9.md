Audit Report

## Title
Cross-dispatch-class corruption of `BlockWeight` via un-keyed `ExtrinsicWeightReclaimed` value - (File: cumulus/pallets/weight-reclaim/src/lib.rs)

## Summary
`frame_system::ExtrinsicWeightReclaimed` is a single, class-agnostic `StorageValue<T, Weight>` written at the end of `StorageWeightReclaim::post_dispatch_details` and consumed at the start of the next extrinsic's `post_dispatch_details`/`reclaim_weight`, but the consuming code always accrues the stored value into the *current* extrinsic's `info.class` rather than the class of the extrinsic that produced it. When a Normal-class extrinsic is immediately followed by an Operational-class extrinsic (or vice versa) in the same block, this causes weight to be moved between the `BlockWeight` per-class buckets incorrectly.

## Finding Description
In `cumulus/pallets/weight-reclaim/src/lib.rs`, `post_dispatch_details` reads the leftover value and reapplies it keyed only by the current extrinsic's class: [1](#0-0) 
and at the end of the same call the value is overwritten unconditionally for whatever class the current extrinsic happens to be: [2](#0-1) 

The same pattern exists in `frame_system::extensions::check_weight::CheckWeight::post_dispatch_details`, which delegates to `Pallet::<T>::reclaim_weight`, and the `weight_reclaim.rs` tests (`extrinsic_already_refunded_more_precisely`, `different_dispatch_class`) confirm the accrue/reduce logic is keyed by `info.class`.

However, this only matters if `ExtrinsicWeightReclaimed` retains a non-zero, meaningful value across an extrinsic boundary of *differing* class. Examining the actual write/consume sequence within a single extrinsic's `post_dispatch_details` call in `cumulus/pallets/weight-reclaim/src/lib.rs`:
1. At the *start* of a given extrinsic's `post_dispatch_details`, `already_reclaimed` is read — this is the value left by the *previous* extrinsic.
2. It is accrued back (undoing the previous extrinsic's final `put`), then `info.total_weight()` for the *current* extrinsic is subtracted, then `accurate_weight` for the current extrinsic is added back, all under the current extrinsic's class.
3. At the end, a fresh `accurate_unspent` for the *current* extrinsic is computed and stored.

This is indeed a genuine accrue/reduce/re-accrue "undo-then-redo" pattern operating on a class-agnostic global. If extrinsic A (Normal) computes and stores `accurate_unspent_A`, and extrinsic B (Operational) then reads `already_reclaimed = accurate_unspent_A` and does `current_weight.accrue(accurate_unspent_A, DispatchClass::Operational)`, the Operational bucket receives a credit that was actually earned against the Normal bucket. The corresponding `reduce(info.total_weight(), info.class)` in extrinsic B only reduces by extrinsic B's own `info.total_weight()`, not by the erroneous credit, so the net effect leaves an extra `accurate_unspent_A` permanently added to the Operational bucket relative to what it should be, while the Normal bucket lost that same amount when A's `post_dispatch_details` ran (since A's own reduce/accrue got undone by B without being redone against Normal).

The claim's citations are accurate representations of the code, and the mechanism described (interleaving of Normal/Operational extrinsics defeats the class-agnostic single-slot handoff) is a real, unaddressed assumption violation: the code assumes consecutive extrinsics share the class of the value left behind, which is not guaranteed since transaction-pool ordering is priority-based, not grouped by `DispatchClass`. There is no test in the repository exercising two *consecutive* extrinsics of different classes where the first leaves a non-zero `ExtrinsicWeightReclaimed` for the second to consume — the existing `different_dispatch_class` test in `weight_reclaim.rs` only tests a single extrinsic of Operational class with `ExtrinsicWeightReclaimed` starting at zero, which does not exercise the cross-class handoff scenario at all.

## Impact Explanation
This corrupts `frame_system::BlockWeight` per-class accounting, which enforces per-class block weight/PoV limits (Normal vs Operational reserved pool). Depending on ordering, this can understate consumed Normal weight (allowing the Normal class to exceed its intended budget) or overstate Operational consumption (spuriously exhausting the Operational reserved pool and denying legitimate priority transactions). This is a legitimate accounting-invariant violation in core weight/PoV bookkeeping, not merely a cosmetic issue, since `BlockWeight` directly gates admission of extrinsics into blocks.

## Likelihood Explanation
The precondition — a Normal-class extrinsic followed immediately by an Operational-class extrinsic (or vice versa) within the same block — is a common, unprivileged, naturally occurring transaction-pool scenario, since ordering is driven by priority rather than grouped by class. No special origin or governance access is required to trigger the sequencing; many ordinary runtime calls across parachains are marked Operational for priority/DoS-resistance reasons without requiring privileged origins. The magnitude of drift per occurrence is bounded by a single extrinsic's unspent-weight refund, but it is deterministic and repeatable every time such a class boundary with non-zero leftover occurs.

## Recommendation
Key `ExtrinsicWeightReclaimed` by `DispatchClass` (e.g., store it as a small map/array indexed by class, or store a `(Weight, DispatchClass)` tuple) so the undo step in both `frame_system::Pallet::reclaim_weight` and `StorageWeightReclaim::post_dispatch_details` accrues the leftover back into the class it was originally taken from. Alternatively, clear/reset `ExtrinsicWeightReclaimed` whenever the class of the current extrinsic differs from the class recorded with the stored value, preventing cross-class bleed-through.

## Proof of Concept
Extend `cumulus/pallets/weight-reclaim/src/tests.rs` (or `substrate/frame/system/src/extensions/weight_reclaim.rs`) with a test that runs two extrinsics back-to-back through the full `TxExtension` pipeline:
1. Extrinsic 1 (`DispatchClass::Normal`) with `post_info.actual_weight` lower than `info.total_weight()`, producing a non-zero `accurate_unspent` written into `ExtrinsicWeightReclaimed` and reducing the Normal bucket of `BlockWeight`.
2. Extrinsic 2 (`DispatchClass::Operational`) dispatched immediately after in the same block, with its own accurately measured proof size.
3. Assert that `BlockWeight::<T>::get().get(DispatchClass::Normal)` equals exactly extrinsic 1's own accurately measured consumption, and `BlockWeight::<T>::get().get(DispatchClass::Operational)` equals exactly extrinsic 2's own accurately measured consumption. Under current code, the Operational bucket will include `already_reclaimed` credit from extrinsic 1's Normal-class refund (or the Normal bucket will be shorted), demonstrating the cross-class leakage.
