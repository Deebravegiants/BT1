### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by verifying the HMAC over the raw request body, but the `shop` identifier that is handed to the app's webhook handler is read directly from the unauthenticated `x-shopify-shop-domain` header. The HMAC signature never binds the shop to the body, so any request whose body+HMAC pair is valid (for *any* shop, since the same `api_secret_key` signs every installation's webhooks) can be replayed with an arbitrary `shop-domain` header, letting the handler run business logic under a spoofed tenant identity.

### Finding Description
`ShopifyAPI::Webhooks::Request` derives the two values used for verification and dispatch independently:

- `hmac` is decoded from the `hmac-sha256`/`x-shopify-hmac-sha256` header.
- `to_signable_string` returns only `@raw_body`.
- `shop` is read straight from the `shop-domain`/`x-shopify-shop-domain` header, with no cryptographic tie to the body or the HMAC. [1](#0-0) [1](#0-0) 

`Registry.process` then validates only the body/HMAC pair via `Utils::HmacValidator.validate`, and immediately passes the unauthenticated `request.shop` value into `WebhookMetadata`, which is handed to the app's registered handler: [2](#0-1) 

`HmacValidator.validate` computes `HMAC(api_secret_key, raw_body)` and compares it to the received value — it never incorporates the shop domain, topic, or webhook id: [3](#0-2) 

Because a single app has one `api_secret_key` shared across every shop that installs it, the same secret produces a valid `HMAC(body)` regardless of which shop the body actually originated from. The binding the code implicitly assumes but never enforces is:

`request.shop` (used to attribute the webhook to a tenant) == the shop that Shopify actually generated `raw_body`/`hmac` for

Before the request sequence: an attacker who installs the target app on their own (fully legitimate, unprivileged) development shop receives real, correctly-signed webhooks (e.g. `orders/create`, `app/uninstalled`) with a valid `hmac-sha256` header computed over the body using the app's `api_secret_key`.

After the request sequence: the attacker resends that exact `raw_body` + `hmac-sha256` header to the app's public webhook endpoint, but substitutes `x-shopify-shop-domain` with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches the handler with `shop: "victim-shop.myshopify.com"` — a value the attacker fully controls and that was never covered by the signature.

### Impact Explanation
This breaks the tenant-isolation boundary the HMAC is supposed to enforce: the app's webhook handler executes as if authentic data arrived from an arbitrary victim shop chosen by the attacker, even though only the body's authenticity (not its origin shop) was actually verified. Depending on how the host application's handler uses `WebhookMetadata#shop` (e.g., looking up/mutating a stored session, or persisting attacker-attributed data against the victim's tenant record), this enables cross-tenant data confusion/tampering — an attacker-controlled tenant identity attached to attacker-controlled but "verified" webhook content.

### Likelihood Explanation
Any developer can install a Shopify app on a free development store (no privileged access needed), which is sufficient to obtain multiple genuinely-signed body/HMAC pairs from the target app. Replaying them against the same app's webhook endpoint with a forged shop-domain header requires no further secrets, only crafting an HTTP request — well within reach of an unprivileged internet user.

### Recommendation
Do not treat `shop-domain` (or `topic`/`webhook-id`) as trusted merely because the body HMAC validates. Where possible, cross-check the shop against a shop that is actually known to the app (e.g., an existing stored session for that shop, combined with webhook id/topic uniqueness tracking to reject replays), and document to consumers of `Webhooks::Request`/`Registry.process` that the shop header is not authenticated by the HMAC and must be corroborated independently (e.g., via stored session lookup and idempotency/webhook-id tracking) before being trusted as the request's tenant.

### Proof of Concept
1. Install the target app on an attacker-controlled development shop `attacker.myshopify.com`; capture a real inbound webhook, e.g. `orders/create`, with headers `x-shopify-hmac-sha256: <valid_hmac>`, `x-shopify-topic: orders/create`, `x-shopify-shop-domain: attacker.myshopify.com`, and raw body `B`.
2. Send a new HTTP request to the same app's webhook endpoint with the identical raw body `B` and identical `x-shopify-hmac-sha256` header, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only recomputes `HMAC(api_secret_key, B)` and compares it to the (unchanged) header value — it never inspects `shop`.
4. `Registry.process` builds `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: request.parsed_body, ...)` and invokes the app's handler as though `victim-shop.myshopify.com` sent that data, per [4](#0-3) .
