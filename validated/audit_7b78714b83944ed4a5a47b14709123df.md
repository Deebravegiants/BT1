### Title
Withdrawal status/tx-hash misreport via asset-only matching in POA Bridge status lookup - ([File: packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts])

### Summary
Both the low-level `waitForWithdrawalCompletion` helper and `PoaBridge.describeWithdrawal` resolve the on-chain outcome of a specific withdrawal by matching API results **only by `assetId`** (derived from `near_token_id`), ignoring the withdrawal's destination address, amount, or index. When a single NEAR transaction contains more than one withdrawal intent for the same asset (e.g. two `ft_withdraw` intents for `nep141:usdc.omft.near` with different destination addresses/amounts), the SDK can report the wrong withdrawal's `status`/`txHash` for the withdrawal the integrator is actually tracking.

### Finding Description
`findMatchingWithdrawal` in `waitForWithdrawalCompletion.ts` selects a withdrawal purely by asset identity: [1](#0-0) 

The same asset-only matching semantics are used in `PoaBridge.describeWithdrawal`, which is explicitly documented and unit-tested as matching "by assetId, not by index": [2](#0-1) [3](#0-2) 

The break in equality: the withdrawal record returned to the integrator (its `status` and `txHash`) is not guaranteed to correspond to the specific withdrawal identified by `(tx hash, index, destinationAddress, amount)` that the caller asked about — it is only guaranteed to share the same `assetId`. If a NEAR transaction bundles two `ft_withdraw`/`mt_withdraw` intents for the same token (one attacker-controlled destination, one legitimate destination), `withdrawals.find(...)` returns whichever entry the POA API lists first, regardless of which one actually matches the withdrawal the integrator is polling for.

### Impact Explanation
An integrator that calls `describeWithdrawal`/`waitForWithdrawalCompletion` per-withdrawal-index to decide when to credit a user or release funds could receive a `completed` status carrying the **transfer_tx_hash of a different withdrawal** (different destination address/amount) than the one it queried. This can cause the integrator to prematurely mark a legitimate withdrawal as completed (crediting/refunding based on an unrelated destination's tx hash), or attribute a completed transfer to the wrong withdrawal record. This falls under "a status or hash misreport making an integrator credit or refund twice" (High impact).

### Likelihood Explanation
Requires only that an unprivileged NEAR account submit a single transaction bundling two withdrawal intents for the same POA-bridged asset (fully permitted by the intents contract and this SDK, since nothing in `createWithdrawalIntents`/`PoaBridge.createWithdrawalIntents` prevents multiple same-asset withdrawals per transaction), then have an integrator track both indices concurrently. No cooperation from the relayer, bridge operator, or admin is needed — this is purely a client-side status-matching defect triggered by ordinary user-crafted transaction structure.

### Recommendation
Match POA withdrawal status records by a unique key that disambiguates multiple same-asset withdrawals within one transaction — e.g. correlate by `(tx_hash, near_token_id, destination address, amount)` or an explicit per-intent index/nonce returned by the POA API, rather than by `assetId` alone. If the POA API cannot currently disambiguate, the SDK should refuse to resolve status for ambiguous (multiple same-asset) cases rather than returning a possibly-mismatched record.

### Proof of Concept
1. Attacker submits one NEAR transaction with two `ft_withdraw` intents for `nep141:usdc.omft.near`: intent A to legitimate user's address for amount `X`, intent B to attacker's own address for amount `Y`.
2. Integrator calls `bridge.describeWithdrawal({ ..., index: 0, withdrawalParams: { assetId: "nep141:usdc.omft.near", destinationAddress: <legit address>, amount: X }, tx: { hash: <near-tx-hash> } })` to check completion of intent A.
3. `findMatchingWithdrawal` in `poa-bridge.ts`/`waitForWithdrawalCompletion.ts` only filters `withdrawals` by `near_token_id === "usdc.omft.near"`; if the POA API returns intent B's record first (e.g. because it settled first), the SDK returns `{ status: "completed", txHash: <intent B's tx hash> }` for the query that was meant to track intent A.
4. Integrator credits/marks intent A complete using a transaction hash that actually paid the attacker's address for a different amount, not the legitimate user's withdrawal.

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
