## Finding

### Title
Webhook HMAC verification excludes the `shop-domain` header, enabling cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from an HTTP header that is never included in the HMAC-signed payload. `ShopifyAPI::Webhooks::Registry.process` trusts this unauthenticated `shop` value to route and label the delivered data, breaking the binding between "bytes verified by HMAC" and "shop identity acted upon."

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body: [1](#0-0) 

Meanwhile `shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is not part of that signable string: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC only against `to_signable_string` (the body), never against the headers: [3](#0-2) 

`Registry.process` then trusts `request.shop` as the tenant identity for the handler call once the (header-independent) HMAC check passes: [4](#0-3) 

The identity binding this breaks: `HMAC-verified bytes == the same bytes the app trusts for tenant attribution`. Because the `shop-domain` header sits outside the signed bytes, the equality does not hold — the HMAC only proves "this body was signed with the app's client secret" (a secret shared across every shop that installs the app), it proves nothing about which shop the header claims to be.

### Impact Explanation
Any user who can obtain one legitimately-signed webhook (e.g., a merchant who has installed the app and receives real webhooks for their own store — an "unprivileged" tenant relative to other merchants) can replay the same `raw_body`/`hmac-sha256` pair while substituting an arbitrary `shop-domain` header for a victim shop. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` forwards the attacker-chosen `shop` value to the handler as if it were authenticated. Any host application that keys tenant records or side effects off `WebhookMetadata#shop` (the documented, intended usage per `docs/usage/webhooks.md`) can therefore have data attributed to, or triggered for, the wrong tenant — a cross-tenant integrity break using only the gem's documented API, no access token, no `api_secret_key`, and no privileged account required.

### Likelihood Explanation
Likely for any deployment that processes webhooks as documented, since obtaining one valid signed webhook is trivial for anyone able to install/use the app on their own store (or observe/capture one delivery), and crafting the replayed HTTP POST with a different `shop-domain` header requires no special access.

### Recommendation
Include the shop-domain (and ideally topic/api-version/webhook-id) in the HMAC-signable content, or otherwise cryptographically bind the header-derived `shop` value to the verified payload (e.g., require the body itself to carry/attest the shop, or validate the header against a Shopify-signed claim) before trusting `request.shop` in `Registry.process` and `WebhookMetadata`.

### Proof of Concept
1. As a merchant who has installed the app, capture a real, successfully-delivered webhook request: `raw_body` (e.g. `{"id":1,...}`) and its `X-Shopify-Hmac-Sha256` header value — both signed with the app's single shared `api_secret_key`.
2. Replay that exact `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but set `X-Shopify-Shop-Domain: victim-shop.myshopify.com` instead of the attacker's own shop domain.
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (`lib/shopify_api/webhooks/request.rb` lines 45-63), `Utils::HmacValidator.validate` returns `true` because it only checks `raw_body` against the secret (`lib/shopify_api/utils/hmac_validator.rb` lines 26-31), and `Registry.process` invokes the app's handler with `shop: request.shop` set to `"victim-shop.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb` lines 188-199) — even though that value was never covered by the signature.
