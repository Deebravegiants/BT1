### Title
Unvalidated swap venues can inject unauthorized token transfers into the caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
Controller strategy swaps narrowly authorize the controller’s input-token transfer, but the opaque route is executed by the configured aggregator and can contain caller-selected pool addresses. A malicious venue invoked through `swap_collateral`, `swap_debt`, `multiply`, or `repay_debt_with_collateral` can request an unrelated `token.transfer(victim, attacker, amount)`, causing simulation to add that transfer beneath the victim’s signed strategy authorization. If the victim signs the poisoned tree, the venue steals wallet funds while still returning enough swap output to satisfy the controller’s measured-output and account-risk checks. [1](#0-0) [2](#0-1) 

### Finding Description
`swap_tokens` authorizes only `token_in.transfer(controller, router, amount_in)` as the controller before calling `SwapAggregatorClient::execute_strategy(controller, amount_in, swap)`. [3](#0-2) 

The authorization protects the controller’s own invocation, but it does not constrain what the route-selected external pool asks from the original account owner whose signature authorized the controller entrypoint. A swap instruction’s `assets` registry contains pool and token addresses, and the instruction chooses the pool by registry index. [4](#0-3) [5](#0-4) 

The router dispatches that selected pool through a venue adapter and validates only the router’s measured input spend and positive output receipt. [6](#0-5) 

A malicious pool can therefore issue an unrelated token transfer that names the transaction signer as `from`; during simulation that call is represented as another child under the signer’s authorization tree, and under enforcing auth it executes when the signer accepts that tree. [7](#0-6) 

### Impact Explanation
This is theft of user funds beyond the declared swap input: the malicious venue can drain any unrelated token balance that the victim authorizes in the poisoned invocation tree while still delivering sufficient `token_out` for the strategy to pass. [8](#0-7) 

The controller’s `RouterOverspend`, positive-output, and final account-solvency checks do not bound transfers made from the victim’s wallet because they measure only controller balances and account state. [9](#0-8) 

### Likelihood Explanation
Exploitation requires the victim to submit a route containing the attacker’s pool and to sign the resulting expanded authorization tree. This is reachable by an unprivileged attacker who deploys the venue and supplies a syntactically valid strategy payload; no protocol role, leaked key, upgrade, or privileged parameter is required. [10](#0-9) [11](#0-10) 

The signer can prevent the loss by rejecting an authorization tree containing anything other than the expected input transfer, but the on-chain strategy checks themselves do not enforce that policy. [1](#0-0) 

### Recommendation
Restrict executable route venues and pool addresses to a governance-managed allowlist, or replace arbitrary pool dispatch with calls to fixed audited venue adapters bound to validated pool identities. At minimum, the signing interface and transaction construction path must decode the route and reject any simulated authorization tree containing sub-invocations beyond the single expected input transfer. [4](#0-3) [1](#0-0) 

### Proof of Concept
1. Victim owns lending account `A` with USDC collateral and also holds an unrelated wallet token `W`. [12](#0-11) 
2. Attacker deploys a contract `P` that implements the selected pool ABI. Inside `swap`, `P` accepts/pulls the routed input, returns a positive amount of `token_out` to the router, and also calls `W.transfer(victim, attacker, victim_balance)`. [13](#0-12) 
3. Attacker encodes a `StrategyPayload` whose `assets` registry contains USDC, `token_out`, `W` where needed, and `P`, with one swap instruction selecting `P`; `min_out` is set low enough for the malicious pool’s returned output to pass. [14](#0-13) [5](#0-4) 
4. Victim invokes `controller::swap_collateral(caller=victim, account_id=A, current=USDC, amount=X, new=token_out, swap=payload)`. The controller authorizes only its own `USDC.transfer(controller, router, X)` before entering `execute_strategy`. [3](#0-2) 
5. During simulation, `P`’s `W.transfer(victim, attacker, victim_balance)` is recorded as an additional sub-invocation under the victim’s authorization. If the victim signs that tree, enforcing execution transfers `W` to the attacker, the router’s measured input/output checks still pass, and the controller finalizes the account. [7](#0-6)

    let before_in = ctx.input_balance();
    let before_out = ctx.output_balance();

    match hop.venue {
        SwapVenue::Soroswap => soroswap::swap(&ctx),
        SwapVenue::Aquarius => aquarius::swap(&ctx, tokens_cache),
        SwapVenue::Phoenix => phoenix::swap(&ctx),
        SwapVenue::Sushi => sushi::swap(&ctx),
        SwapVenue::CometDex => comet::swap(&ctx),
    };

    let received = ctx
        .output_balance()
        .checked_sub(before_out)

        panic_with_error!(env, Error::ZeroOutput);

        .checked_sub(after_in)
        .unwrap_or_else(|| panic_with_error!(env, Error::InvalidAmount));
    if spent != amount_in {
        panic_with_error!(env, Error::InvalidAmount);

    /// Requires `sender` authorization. Pulls `total_in` of the input token, runs the
