### Title
Android biometric auth relies on an unguarded native API boolean instead of a hardware/Keystore-gated secret - (File: features/auth-mobile/module/bio/bio-auth.android.js)

### Summary
On Android, `@exodus/auth-mobile`'s `BioAuth.authenticate()` grants biometric approval purely based on the boolean resolved from `RNBiometrics.authenticate()`, with no cryptographic secret unwrap gating the result [1](#0-0) . This mirrors the HAL-17 bug class (trusting a native biometric evaluation API's return value rather than deriving success from an OS-enforced, hardware-backed secret release), except here it is present in production `authenticate()` logic itself rather than only in a third-party framework hook target.

### Finding Description
The iOS implementation correctly gates bio-auth success on retrieving a keychain secret (`bioAuthTrigger`/`deviceAuthTrigger`) that is protected with `ACCESS_CONTROL_BIOMETRY_CURRENT_SET` / `ACCESS_CONTROL_USER_PRESENCE`, so a successful `authenticate()` call is inseparable from actually decrypting a Secure-Enclave-gated value [2](#0-1) [3](#0-2) .

The Android implementation does not follow this pattern. `BioAuth.authenticate()` calls `RNBiometrics.authenticate({...})` and simply returns whatever boolean the native bridge resolves to, only reading `hasDeviceAuth` from the atom to decide whether to allow passcode fallback — no keystore secret is fetched, decrypted, or otherwise gated behind the biometric check [1](#0-0) . The `enableBioAuth`/`#setBioAuth` flow does store `AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY` with `accessControl: ACCESS_CONTROL_BIOMETRY_CURRENT_SET` [4](#0-3) , but the Android `BioAuth.authenticate()` module never consumes this trigger key — it never calls `auth.getBioAuthTrigger()` the way the iOS module does. Consequently, on Android the actual authentication decision is entirely delegated to the return value of one native API call, `RNBiometrics.authenticate()`, with no OS-level secret decryption tied to the biometric prompt in this code path.

This is structurally the same weakness flagged in HAL-17: an app-level boolean from a fingerprint/biometric evaluation function is trusted as the sole gate, which is exactly the class of check that tools like Objection/Frida target by hooking the native bridge method (`RNBiometrics.authenticate`) to force a `true` resolution regardless of the actual biometric outcome, on a compromised (rooted/instrumented) device.

### Impact Explanation
`hasBioAuth`/`shouldAuthenticate` gate access to "protectworthy resources such as the mnemonic phrase" per the feature's own documentation [5](#0-4) . If `bioAuth.authenticate()` returns `true` from a hooked/forced native return value on Android, whatever caller relies on this result (e.g., unlocking the wallet screen, gating a mnemonic reveal, or step-up auth for sensitive operations) treats the user as fully biometric-authenticated even though no legitimate biometric decision occurred. This is a concrete auth-bypass leading toward secret disclosure (mnemonic/seed) or unauthorized signing operations gated behind bio-auth.

### Likelihood Explanation
Exploitation requires an attacker with local, elevated access to the device (rooted Android + a runtime instrumentation framework such as Frida/Objection) to hook `RNBiometrics.authenticate` — the same attacker capability the original HAL-17 report assumes. This is a realistic and previously-demonstrated attacker model for mobile biometric bypass reports, distinct from a purely theoretical or self-inflicted scenario, and does not require any privileged operator/peer/node role.

### Recommendation
1. On Android, tie the success of `authenticate()` to release/decryption of a Keystore-protected secret gated with biometric-only access (e.g., `setUserAuthenticationRequired`/`BiometricPrompt.CryptoObject` or the existing `AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY` pattern already used for iOS), instead of trusting the raw boolean from `RNBiometrics.authenticate()`.
2. Mirror the iOS pattern: have Android's `BioAuth.authenticate()` call through `auth.getBioAuthTrigger()` (or an Android-equivalent secret fetch) so success is inseparable from actually unwrapping a hardware-backed secret.
3. Add integrity/anti-hooking checks (e.g., IOSSecuritySuite-equivalent library for Android, root/Frida detection) as defense-in-depth, per the original report's recommendation.

### Proof of Concept
1. On a rooted Android device with Frida/Objection attached to the target app.
2. Trigger the bio-auth flow that calls `exodus.auth.bio.trigger()` → `BioAuth.authenticate()` [1](#0-0) .
3. Hook `RNBiometrics.authenticate` (the native bridge call) to resolve with `true` regardless of actual fingerprint/face match, analogous to overriding `evaluatePolicy` on iOS in the original HAL-17 report.
4. Observe that `authenticate()` returns `true` and the app proceeds as if biometric authentication succeeded — no secret decryption or Keystore biometric gate is enforced in this code path to block the forged result.

import { BiometryChangedError } from '../utils/errors.js'

class BioAuth {
  #auth

  constructor({ auth }) {
    this.#auth = auth
  }

  authenticate = async () => {
    try {
      // loading the bioAuthTrigger will trigger the keychain security
      // if the user approves, it will succeed, if not it will throw
      const value = await this.#auth.getBioAuthTrigger()

      if (value === undefined) {
        await this.#auth.disableBioAuth()
        throw new BiometryChangedError()
      }

      return true
    } catch (e) {
      if (e instanceof BiometryChangedError) throw e

      return false
    }
  }

  #setBioAuth = async (on, { useDeviceAuth } = {}) => {
    if (!on) {
      await this.#keystore.deleteSecret(this.#key(AUTH_KEYSTORE_DEVICE_AUTH_KEY))
      await this.#keystore.deleteSecret(this.#key(AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY))
      await this.#keystore.deleteSecret(this.#key(AUTH_KEYSTORE_BIO_AUTH_KEY))
      await this.#keystore.deleteSecret(this.#key(AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY))
      return
    }

    const keyOpts = {
      accessible: ACCESSIBLE_WHEN_UNLOCKED_THIS_DEVICE_ONLY,
    }

    if (useDeviceAuth) {
      // Android and iOS handle `ACCESS_CONTROL_USER_PRESENCE` differently when device auth
      // is not enabled. This check ensures consistent behavior across platforms.
      const canAuth = await this.canUseDeviceAuth()
      if (!canAuth) {
        throw new DeviceAuthenticationUnavailableError()
      }

      await this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_DEVICE_AUTH_KEY), on, keyOpts)
      await this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_DEVICE_AUTH_TRIGGER_KEY), on, {
        ...keyOpts,
        accessControl: ACCESS_CONTROL_USER_PRESENCE, // This flag allows iOS to fallback to device pin.
      })
    } else {
      await this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_BIO_AUTH_KEY), on, keyOpts)
      await this.#keystore.setSecret(this.#key(AUTH_KEYSTORE_BIO_AUTH_TRIGGER_KEY), on, {
        ...keyOpts,
        accessControl: ACCESS_CONTROL_BIOMETRY_CURRENT_SET,
      })
    }
  }
