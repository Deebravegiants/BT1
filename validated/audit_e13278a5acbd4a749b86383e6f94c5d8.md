## Analysis

Confirmed root cause: `_instance()` in `IntentsBase.sol` resolves the gateway peer address *at the time an action executes*, not at the time an order was placed. `_addDeployment` (invoked via `onAccept`'s `NewDeployment` branch, itself gated only by requiring the source of the message be Hyperbridge/governance) unconditionally overwrites `_instances[keccak256(chain)]`: [1](#0-0) 

Every cross-chain settlement/cancellation path re-derives the peer address live from this same mutable mapping instead of pinning it at order-placement time:
- `_post` (used by both `RedeemEscrow` fill-settlement and `_cancelFromDest`'s `RefundEscrow`) sends `to: abi.encodePacked(_instance(order.source))`. [2](#0-1) 
- `_cancelFromSource` builds the GET-proof key against `_instance(order.destination)`. [3](#0-2) 
- `_authenticate` for incoming `RedeemEscrow`/`RefundEscrow` messages checks the sender against `_instance(request.source)`. [4](#0-3) 

### Title
Rotating a chain's registered gateway instance via `NewDeployment` permanently strands escrowed funds for orders placed against the old instance - ([File: evm/src/apps/intentsv2/IntentsBase.sol])

### Summary
`IntentGatewayV2`'s peer-registration mechanism (`Deployment`/`NewDeployment`) lets governance (re)point the `_instances[chain]` mapping to a new gateway address at any time, with no restriction preventing overwriting an existing, already-in-use registration. Because every cross-chain settlement/cancellation function resolves the peer address dynamically via `_instance(...)` at execution time rather than capturing it when the order was placed, orders that are in-flight at the moment of a legitimate re-registration (e.g. migrating to an upgraded/redeployed gateway on a given chain, correcting a bad initial registration, or adding the same chain under a new address after a redeploy) become undeliverable/unauthenticatable, freezing the user's escrowed input tokens indefinitely — mirroring the reported centralization risk where a normal admin/governance action (`unregisterDepository`) breaks redemption for balances that were already committed under the old configuration.

### Finding Description
`_addDeployment` is the only writer of `_instances`, and it performs an unconditional overwrite with no check that the chain is unregistered or that no active orders reference it:

```solidity
function _addDeployment(Deployment memory body) internal {
    _instances[keccak256(body.chain)] = body.gateway;
    emit DeploymentAdded({chain: string(body.chain), gateway: body.gateway});
}
``` [5](#0-4) 

Consider an order placed while `_instances[destChain] == OldGateway`. Before it settles, governance dispatches a `NewDeployment` request that updates `_instances[destChain] = NewGateway` (a routine operation — e.g. after upgrading/redeploying the destination gateway, or fixing a registration mistake):

1. **Fill/redeem path**: A solver fills the order on the destination and `_fillCrossChain` dispatches `RedeemEscrow` back to the source via `_post`, whose `to` field is `abi.encodePacked(_instance(order.source))`. If it is the *source*-chain registration that got rotated instead, the redeem message is sent to `NewGateway` on the source chain, not the `OldGateway` contract that actually holds the escrowed `_orders[commitment][token]` balance. `NewGateway`'s `_orders` mapping has no entry for that commitment, so `_withdraw` reverts with `UnknownOrder`, permanently failing delivery — the solver already paid the beneficiary but can never redeem the escrow, and the user's tokens sit frozen in `OldGateway` forever (no retry path exists once accepted-but-reverting, and no timeout/refund mechanism is defined for `RedeemEscrow`/`RefundEscrow` POSTs, unlike `HyperFungibleToken`'s `onPostRequestTimeout` re-mint). [6](#0-5) [7](#0-6) 

2. **Cancel-from-source path**: If instead the *destination*-chain registration is rotated, `_cancelFromSource` computes the GET storage key from `_instance(order.destination)` — now `NewGateway` — even though the order's actual fill state (if any) lives in `OldGateway`'s storage. The proof will read `NewGateway`'s (always-empty) `_filled` slot for that commitment, causing `onGetResponse` to treat every order as unfilled and refund escrow on the source regardless of the order's true fill status on `OldGateway` — enabling incorrect refunds (fund loss for a solver who filled the order at `OldGateway`) or, in the case where fill genuinely never happened, simply making the correct refund path structurally rely on the wrong contract by chance/coincidence. [8](#0-7) 

3. **Authentication path**: `_authenticate` on the receiving chain checks `_instance(request.source) != module`, i.e. it only accepts messages whose `from` equals the *currently* registered peer. Any `RedeemEscrow`/`RefundEscrow` message legitimately sent by the old peer contract (e.g. a message already in flight, or one that must be re-sent after a relayer retry) after rotation is rejected with `Unauthorized`, permanently blocking settlement for orders tied to the old contract. [4](#0-3) 

This is structurally identical to the UXD `UXDController`/`UXDRouter` issue: removing/rotating a registered counterpart (`unregisterDepository` ≈ `NewDeployment` overwrite) is a normal, non-malicious privileged action, yet it silently breaks redemption for balances/escrows that were already committed under the prior registration, with no migration or grace-period mechanism and no check for outstanding escrow before the rotation is allowed.

### Impact Explanation
Escrowed user input tokens can become permanently unrecoverable (frozen) once a chain's registered gateway instance is rotated while orders referencing that chain are still outstanding — because settlement/cancellation messages resolve the peer address dynamically rather than at order-commitment time. In the mismatched-authentication scenario, this also creates a path for a solver to lose funds (having delivered outputs but never receiving the escrowed input) or for a user to be refunded despite an order having actually been filled elsewhere. Given the amounts held in escrow by `IntentGatewayV2` deployments across chains, this is a Medium/High severity freezing-of-funds and fund-loss risk introduced by an entirely ordinary governance operation (registering a new/updated deployment for a chain), not requiring any malicious actor.

### Likelihood Explanation
`NewDeployment` re-registrations are an expected, routine governance operation (adding chains, migrating/upgrading a gateway deployment, correcting a misconfigured address) rather than an edge case. Any order that is placed, in-flight, or awaiting cancellation at the moment such a rotation occurs for its `source` or `destination` chain is affected — there is no order-level pinning of the counterpart address and no check in `_addDeployment` for outstanding escrow tied to the chain being re-registered.

### Recommendation
- Snapshot the resolved peer/gateway address into the `Order` (or into `_orders`/a side mapping keyed by commitment) at `placeOrder` time, and use that pinned address for all subsequent `_post`, GET-key construction, and `_authenticate` checks for that specific order, instead of re-resolving `_instance(...)` live.
- Alternatively, disallow overwriting an existing non-zero `_instances[chain]` entry via `NewDeployment` (require an explicit deprecation/migration step), and provide a drain/migration window during which both the old and new gateway addresses are accepted for authentication and settlement of orders that predate the rotation.
- Add a timeout/refund fallback for `RedeemEscrow`/`RefundEscrow` POST requests (mirroring `HyperFungibleToken.onPostRequestTimeout`) so that a delivery failure caused by a stale peer address does not permanently freeze the escrow.

### Proof of Concept
1. Governance registers `chainB`'s gateway as `GatewayB_v1` via `NewDeployment` (`_addDeployment`), setting `_instances[keccak256(chainB)] = GatewayB_v1`.
2. A user places a cross-chain order on `chainA` with `destination = chainB`; input tokens are escrowed in `IntentGatewayV2` on `chainA`.
3. Before the order is filled/cancelled, governance dispatches another `NewDeployment` for `chainA` (e.g., migrating `chainA`'s registration from `GatewayA_v1` to `GatewayA_v2`), updating `_instances[keccak256(chainA)] = GatewayA_v2` on the destination side.
4. A solver fills the order on `chainB`; `_fillCrossChain` calls `_post`, which sets `to: abi.encodePacked(_instance(order.source))` — now resolving to `GatewayA_v2`, not `GatewayA_v1` where the escrow actually lives.
5. The `RedeemEscrow` message is delivered to `GatewayA_v2` on `chainA`. `_withdraw` looks up `_orders[commitment][token]` on `GatewayA_v2`, finds it `== 0`, and reverts with `UnknownOrder` — the solver's redeem permanently fails while the user's escrowed tokens remain locked, unreachable, in `GatewayA_v1`.     function _cancelFromSource(Order calldata order, CancelOptions calldata options, bytes32 commitment) internal {
        if (order.user != bytes32(uint256(uint160(msg.sender)))) revert Unauthorized();

        if (options.height <= order.deadline) revert NotExpired();

        uint256 inputsLen = order.inputs.length;
        for (uint256 i; i < inputsLen;) {
            if (_orders[commitment][address(uint160(uint256(order.inputs[i].token)))] == 0) revert UnknownOrder();

            unchecked {
                ++i;
            }
        }

        bytes memory context =
            abi.encode(WithdrawalRequest({commitment: commitment, tokens: order.inputs, beneficiary: order.user}));

        bytes[] memory keys = new bytes[](1);
        keys[0] = bytes.concat(abi.encodePacked(_instance(order.destination)), _calculateCommitmentSlotHash(commitment));
        DispatchGet memory request = DispatchGet({
            dest: order.destination,
            keys: keys,
            timeout: 0,
            height: options.height,
            fee: options.relayerFee,
            context: context,
            payer: msg.sender
        });

        address hostAddr = host();
        if (msg.value > 0) {
            IDispatcher(hostAddr).dispatch{value: msg.value}(request);
        } else {
