### Title
Webhook Shop-Domain Identity Spoofing via HMAC That Only Covers the Raw Body - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely by checking `Utils::HmacValidator.validate(request)`, but the `Request#to_signable_string` used for that HMAC covers only the raw JSON body — never the `shop-domain` header. The `shop` value handed to the application's webhook handler is therefore never bound to the signature that was actually verified, breaking the identity equality `shop_authenticated == shop_used_for_tenant_lookup`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` computes/compares the signature against exactly that signable string: [2](#0-1) 

`Registry.process` uses this validation as the sole authenticity gate, then forwards `request.shop` — parsed straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header — to the application handler as the tenant identifier, with no cross-check against the HMAC-covered content: [3](#0-2) 

`Request#shop` is derived purely from an unauthenticated header: [4](#0-3) 

The `api_secret_key` used to sign webhooks is the app's single `client_secret`, shared across every merchant that installs the app — it is not a per-shop secret. Consequently, any unprivileged user who installs the app on their own store obtains a legitimately-signed `(body, hmac)` pair for their own tenant. Because the header carrying `shop` is excluded from the signed content, that same attacker can resend the identical body/HMAC to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` passes the spoofed `shop` value into `WebhookMetadata`, which host applications use to look up the victim's stored session/access token to act on the webhook.

Equality that should hold but doesn't: `shop_bound_by_hmac == shop_delivered_to_handler`. Before the request: both are the attacker's own shop and match. After the crafted request: the HMAC-covered bytes (body) still belong to the attacker's shop, but the `shop` delivered to the handler is the victim's — the two diverge despite validation passing.

### Impact Explanation
This lets a low-privilege actor (anyone who can install the app on a store they control) cause the application to process/act on a webhook while impersonating another merchant's shop identity. Since host applications commonly use the `shop` value from `WebhookMetadata` to fetch that shop's stored access token/session (the documented pattern for consuming webhooks in Shopify apps built on this gem), this enables cross-tenant impact: webhook side effects, data writes, or access-token usage occur under the victim's identity/session while driven entirely by attacker-supplied timing and body content.

### Likelihood Explanation
Likelihood is high for any multi-tenant app relying on this gem's webhook stack: the only prerequisite is installing the app on any shop (a normal, unprivileged onboarding action), capturing one legitimate webhook delivery for that shop, and replaying it to the app's public webhook endpoint with a different `shop-domain` header value. No secret material beyond what the attacker legitimately possesses for their own tenant is required.

### Recommendation
Include the shop domain (and other identity-relevant headers such as `webhook-id`/`api-version` if they influence handler behavior) inside the HMAC-signed content, or independently verify that `request.shop` corresponds to a shop with an active, known installation/session in the host application's session store before invoking the handler. At minimum, document prominently that `Request#shop` is unauthenticated and must be cross-checked by the caller against installed-shop state prior to trusting it for tenant-scoped operations.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; Shopify sends a real webhook, e.g. body `{"id":1}` with headers:
   - `x-shopify-hmac-sha256: <valid HMAC over body using shared api_secret_key>`
   - `x-shopify-shop-domain: attacker.myshopify.com`
2. Attacker captures this exact `(raw_body, hmac_header)` pair.
3. Attacker sends a new POST directly to the app's webhook endpoint with the identical `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new` parses the spoofed `shop` header; `Registry.process` calls `HmacValidator.validate(request)`, which only checks `raw_body` against the secret — it passes.
5. The registered handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", ...)` and performs tenant-scoped work (e.g., loading `victim.myshopify.com`'s stored session/access token) driven by attacker-controlled body content, as shown by the code paths cited above.
