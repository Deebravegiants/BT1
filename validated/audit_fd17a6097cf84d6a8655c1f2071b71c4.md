## Analysis Result

The Sherlock report's bug class — an owner-gated whitelist that fails to exclude dangerous selectors (`approve`, `increaseAllowance`) from a call-forwarding primitive — maps onto Hyperbridge's `CallDispatcher`, but in an inverted and more severe form: there is no whitelist at all, and the dispatcher is a single **shared** contract reused across every order/message on a given deployment.

### Title
Unrestricted, Shared `CallDispatcher` Allows Any User's Order to Grant Persistent Token Approvals That Drain Funds Deposited by Later, Unrelated Orders - (File: `evm/src/utils/CallDispatcher.sol`)

### Summary
`CallDispatcher.dispatch` executes any `(to, value, data)` triple supplied in an order's `predispatch`/`output.call` payload with zero restriction on target or selector [1](#0-0) , and the same dispatcher address is reused across all orders of a gateway deployment (`_params.dispatcher`) [2](#0-1) . Any unprivileged user placing an order can smuggle `IERC20(anyToken).approve(attacker, type(uint256).max)` into their own `predispatch.call` or `output.call`, at no cost to themselves, granting an attacker-controlled address a standing, unlimited allowance over the shared dispatcher for a token they don't even need to hold.

### Finding Description
`IntentGatewayV2.placeOrder` moves `predispatch.assets` into the dispatcher, executes the attacker-supplied `predispatch.call` unrestricted, and then sweeps back only the tokens listed in `order.inputs` [3](#0-2) . Likewise `IntentsBase._execute` runs `order.output.call` and only sweeps tokens enumerated in `order.output.assets` [4](#0-3) . Neither `dispatch()` nor these callers restrict the selectors or targets a call can invoke — the interface itself documents this as dispatch of "untrusted call(s)" [5](#0-4) .

Because `approve()` writes into the *token contract's* storage (`allowance[dispatcher][spender]`), not the dispatcher's own storage, it survives the dispatcher's per-transaction sweeps and persists indefinitely across unrelated future transactions. Any token the malicious order names in its calldata — regardless of whether that token appears in the order's own `inputs`/`outputs` — gets an attacker-approved spender on the shared dispatcher. The same shared-dispatcher risk applies to the `HyperFungibleToken`/`WrappedHyperFungibleToken` calldata-execution path, which explicitly warns users to use exact approvals "since the dispatcher contract holds tokens temporarily" — an acknowledgment that unlimited approvals through the dispatcher are unsafe, but nothing on-chain enforces it.

### Impact Explanation
Once the rogue allowance exists, the attacker can call `token.transferFrom(dispatcher, attacker, amount)` the moment any other, unrelated order causes that token to transiently sit on the dispatcher (e.g. another user's `predispatch.assets` transfer, or dust left over from an imprecise swap that isn't part of `order.inputs`/`output.assets` and therefore is never swept). This is concrete theft of funds belonging to other users/solvers, achievable by a single unprivileged `placeOrder`/`fillOrder` call with crafted calldata — no governance or admin compromise required.

### Likelihood Explanation
Likelihood is high: placing an order with arbitrary `predispatch.call`/`output.call` is a normal, permissionless, low-cost user action (dust amounts suffice to trigger execution), and the dispatcher's sweep logic never revokes approvals, only forwards named-token balances. The attacker does not need capital in the targeted token, only patience for a window where the dispatcher transiently holds it.

### Recommendation
- Have `CallDispatcher` (or the calling gateway) explicitly disallow/strip `approve`, `increaseAllowance`, `permit`, and similar allowance-granting selectors from user-supplied calldata, or
- Deploy a fresh, single-use `CallDispatcher` per order/message instead of a shared long-lived instance, and/or
- After every `dispatch()` call, force-reset (`approve(spender, 0)`) any allowances the dispatcher granted during that call before returning control, ensuring no allowance survives past the current transaction.

### Proof of Concept
1. Attacker submits `placeOrder` with `predispatch.assets = []` (or a trivial amount) and `predispatch.call = abi.encode([Call({ to: USDC, value: 0, data: abi.encodeWithSelector(IERC20.approve.selector, attacker, type(uint256).max) })])`.
2. `IntentGatewayV2.placeOrder` dispatches this call unmodified via `ICallDispatcher(dispatcher).dispatch(...)` [6](#0-5) ; USDC's `allowance[dispatcher][attacker]` is now `type(uint256).max`.
3. Any later, unrelated victim places an order whose `predispatch.assets` includes USDC — the moment `IERC20(USDC).safeTransferFrom(msg.sender, dispatcher, amount)` executes [7](#0-6) , the attacker's outstanding approval lets it pull those freshly-deposited USDC out via `transferFrom(dispatcher, attacker, amount)` before/at the point the gateway's own sweep call executes, or against any USDC dust the swap doesn't fully consume (which is never reclaimed since only `order.inputs` tokens are swept).

        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
