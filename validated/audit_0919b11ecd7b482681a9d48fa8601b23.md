The escrow-release math in the same-chain partial-fill path floors a cross-token ratio using raw, un-normalized token amounts — the same bug class as the H-2 report (dividing native-precision amounts of two different-decimal tokens and truncating to zero).

### Title
Same-chain partial-fill escrow release truncates to zero for decimal-mismatched input/output token pairs, allowing early fillers to be shortchanged - (`evm/src/apps/intentsv2/IntrinsicIntents.sol`)

### Summary
`_fillSameChain` computes the amount of escrowed input token to release to a partial filler as `(order.inputs[i].amount * fillAmount) / totalRequired`, where `order.inputs[i].amount` is denominated in the input token's native decimals and `fillAmount`/`totalRequired` are denominated in the output token's native decimals. [1](#0-0)  No decimal normalization is applied before this division, mirroring exactly the H-2 report's root cause: dividing a value scaled in one token's precision by a value scaled in another's, with no common 18-decimal basis.

### Finding Description
`fillOrder` on the `IntentGatewayV2` reaches `_fillSameChain`, an unprivileged, permissionless entry point any solver can call to partially fill a same-chain order. [2](#0-1)  For a non-final fill (`amountFilled != totalRequired`), the escrow released is:
```
escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
```
`order.inputs[i].amount` and `totalRequired`/`fillAmount` come from independently priced input and output legs of the order and are never normalized to a common decimal basis anywhere in this function or its caller. [3](#0-2)  Only the exact final fill (`amountFilled == totalRequired`) bypasses the ratio and pulls the literal remaining escrow balance, which is the mechanism that already exists to mop up rounding dust for the *last* filler. [4](#0-3)  Every non-final filler is exposed to the raw floor-division.

Given a pair like a low-decimal input token (e.g. 6-decimal USDC) escrowed against a high-decimal output token (e.g. 18-decimal token), a solver providing a small proportion of `totalRequired` output tokens can have `order.inputs[i].amount * fillAmount` truncate below `totalRequired`, yielding `escrowedAmount == 0`. The solver transfers real output tokens to the beneficiary (`beneficiaryTotal`) but receives zero escrowed input tokens in return, while `_partialFills` still records their `fillAmount` as consumed. The shortfall is not lost to the protocol — it silently accrues to whichever solver later completes the order via the exact-remaining-balance final-fill branch. [5](#0-4)  This is confirmed as a real, load-bearing dust concern by the project's own test suite, which specifically covers rounding dust when input has more precision than output (native ETH/DAI case) and asserts the final filler "should receive the remaining balance ... including rounding dust." [6](#0-5)  That fix only guarantees no *protocol-level* dust is stranded in the gateway; it does not protect an individual under-compensated intermediate filler, and does not address the case where the ratio itself floors entirely to zero for a legitimately-sized partial fill on a decimal-mismatched pair.

### Impact Explanation
An honest, unprivileged solver calling `fillOrder` to partially fill a decimal-mismatched order can deliver real output tokens to the beneficiary and receive zero (or systematically less) input-token escrow in return — a direct, permanent loss of funds for that solver, transferred instead to whichever solver happens to complete the order. This is concrete theft/misallocation of escrowed funds triggered by a single permissionless transaction, not a resource-only or cosmetic issue.

### Likelihood Explanation
Any order pairing a low-decimal token (6 decimals, e.g. USDC) as input against a high-decimal token (18 decimals) as output, filled in several partial tranches, can trigger this whenever a tranche's `fillAmount` is small enough relative to `totalRequired` that `order.inputs[i].amount * fillAmount / totalRequired` floors to zero or is materially under-valued. No attacker collusion is required — normal partial-fill usage by solvers unaware of the precision skew is sufficient, and the codebase already acknowledges rounding-dust behavior in this exact function via its own tests, showing the scenario is realistic and expected to occur in production-shaped inputs.

### Recommendation
Normalize both legs to a common precision (e.g., 18 decimals, using each token's `decimals()`) before computing the escrow-release ratio in `_fillSameChain`, analogous to the `_normalizeAmount` helper already used in `VWAPOracle.sol` [7](#0-6) , or alternatively perform the multiplication/division with extended precision (e.g., scale `order.inputs[i].amount` up before multiplying, and only scale back down after dividing) so intermediate partial fills round consistently and never zero out relative to the true fill fraction.

### Proof of Concept
1. User places a same-chain order: input = 1 unit of a 6-decimal token (`amount = 1`, i.e., 0.000001 tokens), output = 1,000,000 units of an 18-decimal token (`totalRequired = 1_000_000 * 1e18`... any large output amount).
2. Solver A calls `fillOrder` providing `fillAmount = 1` unit of output (far less than `totalRequired`), transferring that output token to the beneficiary.
3. `_fillSameChain` computes `escrowedAmount = (1 * 1) / totalRequired = 0` since `totalRequired` vastly exceeds the numerator. [4](#0-3) 
4. Solver A's `outputFills`/`escrowedInputs[i].amount` is `0` — they paid real output tokens and got nothing, while `_partialFills[commitment][outputToken]` still records their fill as consumed progress toward `totalRequired`.
5. A later Solver B who eventually completes the order to `amountFilled == totalRequired` collects the *entire* original escrow balance via the exact-balance branch, effectively absorbing what should have been Solver A's share. [8](#0-7)

    function _fillSameChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        bool isFullyFilled = true;

        TokenInfo[] memory escrowedInputs = new TokenInfo[](outputsLen);
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            uint256 alreadyFilled = _partialFills[commitment][outputToken];
            uint256 remaining = totalRequired - alreadyFilled;
            if (remaining == 0 || solverAmount == 0) {
                if (solverAmount == 0 && remaining > 0) isFullyFilled = false;
                continue;
            }
            uint256 fillAmount;

            uint256 beneficiaryShare = 0;
            uint256 protocolShare = 0;
            if (alreadyFilled == 0 && solverAmount > totalRequired) {
                fillAmount = totalRequired;
                (protocolShare, beneficiaryShare) =
                    _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);
            } else {
                fillAmount = solverAmount > remaining ? remaining : solverAmount;
            }

            uint256 amountFilled = alreadyFilled + fillAmount;
            _partialFills[commitment][outputToken] = amountFilled;
            uint256 beneficiaryTotal = fillAmount + beneficiaryShare;

            if (token == address(0)) {
                if (msgValue < beneficiaryTotal + protocolShare) revert InsufficientNativeToken();
                msgValue -= (beneficiaryTotal + protocolShare);
                // Inline, not `_sendValue`: this loop is at the via-ir stack limit.
                (bool sent,) = beneficiary.call{value: beneficiaryTotal}("");
                if (!sent) revert InsufficientNativeToken();
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, beneficiaryTotal);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }

            if (totalRequired > amountFilled) isFullyFilled = false;
            if (protocolShare > 0) emit DustCollected(token, protocolShare);

            uint256 escrowedAmount;
            if (amountFilled == totalRequired) {
                escrowedAmount = _orders[commitment][address(uint160(uint256(order.inputs[i].token)))];
            } else {
                escrowedAmount = (order.inputs[i].amount * fillAmount) / totalRequired;
            }
            escrowedInputs[i] = TokenInfo({token: order.inputs[i].token, amount: escrowedAmount});
            outputFills[i] = TokenInfo({token: outputToken, amount: fillAmount});

    /**
     * @notice Normalizes token amount to 18 decimals
     * @param amount The amount to normalize
     * @param _decimals The current decimals of the token
     * @return normalized The normalized amount (18 decimals)
     */
    function _normalizeAmount(uint256 amount, uint8 _decimals) private pure returns (uint256 normalized) {
        if (_decimals == 18) {
            return amount;
        } else if (_decimals < 18) {
            return amount * (10 ** (18 - _decimals));
        } else {
            return amount / (10 ** (_decimals - 18));
        }
    }
