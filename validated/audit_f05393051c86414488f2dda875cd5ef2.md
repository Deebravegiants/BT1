### Title
User-supplied swap routes can place arbitrary venue contracts inside the caller’s authorization tree - (File: contracts/controller/src/strategies/swap.rs)

### Summary
The lending controller accepts an opaque `StrategySwap` byte payload from the transaction caller and forwards it to the configured swap aggregator without decoding or constraining the venue addresses embedded in the route. `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, and `multiply` all authenticate the caller and then pass this caller-controlled route to the router. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
`StrategySwap` is defined only as `Bytes`; the controller does not expose a route-structure validation step or an allowlist of pools, venues, or other contracts that the route may invoke. [1](#0-0) 

For `swap_collateral`, the caller authenticates, proves owner-or-delegate authority, withdraws collateral into controller custody, and forwards the supplied `swap` bytes to the router. [4](#0-3) 

For `swap_debt`, the controller borrows the new debt asset into its own custody and passes the measured amount together with the caller-controlled route into `swap_tokens_or_passthrough`. [5](#0-4) 

`repay_debt_with_collateral` uses the same pattern: it withdraws collateral into controller custody and routes it through the supplied swap payload before repaying the account’s debt. [6](#0-5) 

`multiply` borrows into controller custody, optionally swaps an initial payment, and forwards both user-provided routes through the same router execution path. [7](#0-6) [8](#0-7) 

The router call itself is made through `SwapAggregatorClient::execute_strategy(controller, amount_in, swap)`, where `swap` is the caller-provided opaque payload. [9](#0-8) [10](#0-9) 

The controller’s protections are limited to token-flow accounting around the configured router: it authorizes one exact input transfer, rejects input overspend, refunds unspent input, and requires positive output. They do not identify which contracts the route causes the router to invoke. [11](#0-10) 

### Impact Explanation
A malicious route can place attacker-controlled venue or pool contracts on the call stack below a transaction that the account owner authorizes. Because these strategy entrypoints begin with `caller.require_auth()` and require owner-or-delegate authority, a crafted transaction can induce the user to sign a broader authorization tree than the intended swap and then transfer unrelated wallet assets to the attacker. [12](#0-11) [13](#0-12) 

The resulting loss is theft of user funds rather than merely a bad trade. The controller’s balance checks only cover the declared input and output tokens held by the controller; they do not bound transfers from the authorizing caller’s wallet that are attached to the caller’s authorization tree by malicious route code. [14](#0-13) 

### Likelihood Explanation
An unprivileged attacker can generate a valid-looking route payload naming an attacker-controlled venue and deliver it through an interface, copied route, compromised quote source, or phishing flow. The victim must sign the resulting authorization tree, so exploitation requires user signing rather than being fully permissionless, matching the reported bridge-address class’s “tricked into signing” threat model. [15](#0-14) 

The issue is amplified because all four state-changing strategy flows converge on the same opaque `swap` argument and configured router execution path. [16](#0-15) 

### Recommendation
Bind strategy execution to explicitly configured or otherwise cryptographically verified venue contracts rather than trusting arbitrary addresses encoded in user-supplied routes. On Soroban, this can be implemented by storing an immutable or governance-controlled venue registry outside the route payload and having routes select registry entries by identifier.

At a minimum, reject authorization trees that contain unexpected child invocations and make route decoding mandatory before signing. Clients should display every pool, token, and nested token transfer in the final simulated authorization tree and refuse any route containing unrelated caller-token transfers.

### Proof of Concept
1. The attacker deploys a contract exposing the function shape expected for a route venue.
2. The attacker constructs a `StrategySwap` payload that names that contract as a hop venue.
3. The victim invokes `swap_collateral(caller, account_id, current, amount, new, swap)` or another router-backed strategy with this payload. [2](#0-1) 
4. The controller authenticates `caller`, verifies account authority, withdraws or borrows the input asset into controller custody, and calls the configured router with the opaque payload. [4](#0-3) 
5. During route execution, the malicious venue contract runs inside the authorized invocation tree and requests a transfer of an unrelated token from `caller` to the attacker.
6. If the victim signs the simulated authorization tree containing that child transfer, the token transfer succeeds even though the controller’s own measured router input and output checks pass. [14](#0-13)

/// Passes matching assets through only with an empty route; otherwise swaps.
pub(crate) fn swap_tokens_or_passthrough(
    env: &Env,
    refund_to: &Address,
    token_in: &Address,
    amount_in: i128,
    token_out: &Address,
    swap: &StrategySwap,
) -> i128 {
    if token_in == token_out {
        assert_with_error!(env, swap.is_empty(), GenericError::InvalidPayments);
        amount_in
    } else {
        swap_tokens(env, refund_to, token_in, amount_in, token_out, swap)
    }
