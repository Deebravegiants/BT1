### Title
Unchecked-length `message.from` causes a Rust panic in `HyperFungibleToken::on_accept`, halting message delivery - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`Pallet::on_accept` in the hyper-fungible-token ISMP module reads `message.from` (an attacker/source-contract-controlled, arbitrary-length `bytes` field from an ABI-decoded cross-chain `PostRequest` body) and uses it to build an origin account for an embedded runtime call, but — unlike every other length-sensitive field in the same function (`message.to`, and the `on_timeout` counterpart's `from_bytes`) — it does **not** validate the length of `from_bytes` before slicing/copying it into a fixed-size buffer.

### Finding Description
In `on_accept` [1](#0-0) , when `message.data` is non-empty and decodes to `SubstrateCalldata` with `signature == None`, the code computes the dispatch origin from `message.from`:

```rust
let from_bytes = message.from.as_ref();
if source.is_evm() {
    T::EvmToSubstrate::convert(H160::from_slice(
        &from_bytes[from_bytes.len() - 20..],
    ))
} else {
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
}
``` [2](#0-1) 

- If `source.is_evm()` and `from_bytes.len() < 20`, `from_bytes.len() - 20` underflows `usize`, producing a huge start index and panicking with a slice-index-out-of-range error when the range is materialized.
- If `source` is not EVM (`else` branch) and `from_bytes.len() != 32`, `copy_from_slice` panics immediately (`"source slice length (N) does not match destination slice length (32)"`).

`message.from` is decoded straight from the attacker-influenced ABI payload of the source contract's `Message` struct (via `Message::abi_decode(&body)` at line 59) and is not constrained to any particular length anywhere before this point. This is exactly the bug class described in CVE-2024-50664 (gpac): a length field/variable-length attacker input is trusted to match a fixed-size buffer's expected size without an explicit bounds/length check before the buffer operation, leading to an out-of-bounds access.

By contrast, the codebase clearly knows the correct pattern and applies it consistently elsewhere in the very same file:
- `message.to` is validated for length `== 32` or `== 20` before use, with an explicit `HftError::InvalidRecipientLength` otherwise [3](#0-2) .
- The `on_timeout` handler applies the same defensive check to `from_bytes` before copying it [4](#0-3)  (visible in the earlier read as `InvalidSenderLength`).

The `on_accept` "calldata origin" branch is the one place this length check was omitted, leaving a directly attacker-reachable panic.

### Impact Explanation
This function is invoked from `on_accept`, which `pallet-ismp` calls when delivering a verified `PostRequest` to the registered `IsmpModule` (the hyper-fungible-token pallet) — i.e., it executes inside `handle_unsigned`/message-delivery dispatch, a path reachable by any relayer submitting a proven cross-chain message whose source contract is registered in `ContractToAsset`. A Rust panic during on-chain execution of an extrinsic in a `no_std` Substrate runtime (compiled with `panic = "abort"`) aborts the runtime call, which can abort block execution/import for that block — effectively making the affected route/channel unable to deliver messages (a denial of service on the ISMP message-delivery pipeline for that pallet/asset), matching the "route unable to deliver messages" acceptance criterion. Because this runs after the token mint/transfer step has already executed, a would-be attacker can also use the panic to make otherwise-successful minted transfers non-finalizable/replayable in a problematic way, depending on how the runtime handles panicking extrinsics (at minimum a reliable message-processing DoS for this module).

### Likelihood Explanation
High. The trigger requires only:
1. A source contract/address already whitelisted in `ContractToAsset` (an operational configuration, not a privileged bypass — any registered bridge integration is a valid, unprivileged sender of the underlying cross-chain message).
2. A `PostRequest.body` that ABI-decodes to a valid `Message` with non-empty `data` that SCALE-decodes as `SubstrateCalldata { signature: None, runtime_call }`.
3. A `from` field whose byte length is not 20 (when source is EVM) or not 32 (when source is non-EVM) — trivially constructible since `from` is an arbitrary `bytes` ABI field.

No signature, governance, or privileged role is required; a single relayed message from a registered application contract can trigger it.

### Recommendation
Validate `from_bytes.len()` the same way `to_bytes` and the `on_timeout` path already do, returning a typed error (e.g., extend `HftError` with `InvalidSenderLength`/reuse existing) instead of panicking:
```rust
let from_bytes = message.from.as_ref();
let origin_account = if source.is_evm() {
    if from_bytes.len() != 20 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?
    }
    T::EvmToSubstrate::convert(H160::from_slice(from_bytes))
} else {
    if from_bytes.len() != 32 {
        Err(HftError::InvalidSenderLength(from_bytes.len()))?
    }
    let mut account = [0u8; 32];
    account.copy_from_slice(from_bytes);
    account.into()
};
```

### Proof of Concept
1. Register a source contract/asset mapping via `ContractToAsset` for a given `source` state machine (standard integration setup).
2. Craft a `PostRequest` whose `body` ABI-decodes to `Message { to: <32 or 20 bytes>, amount: <valid>, data: <non-empty>, from: <e.g. 5 bytes> }`.
3. Encode `data` as `SubstrateCalldata { signature: None, runtime_call: <any allowed call> }`.
4. Relay the request through the standard ISMP proof-verification path so it reaches `Pallet::on_accept`.
5. Execution reaches the `else` branch of the `substrate_data.signature` match; with `source.is_evm()` and `from.len() == 5`, `from_bytes.len() - 20` underflows and the subsequent slice indexing panics (or, for a non-EVM source with `from.len() != 32`, `copy_from_slice` panics directly), aborting the extrinsic and disrupting message delivery for that module.
