### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-attribution spoofing for a validly-signed webhook body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body, while the `shop` value used by webhook handlers is read from a separate, unsigned HTTP header. Any request whose body carries a valid signature (e.g. a real webhook Shopify sent for the attacker's own shop) can be replayed with an arbitrary `shopify-shop-domain`/`x-shopify-shop-domain` header, and `ShopifyAPI::Webhooks::Registry#process` will still accept it and dispatch it to the handler tagged with the attacker-chosen shop.

### Finding Description
`Utils::HmacValidator.validate` signs/verifies `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns **only** `@raw_body`: [2](#0-1) 

But the tenant identity, `shop`, is derived independently from an HTTP header that is never fed into the signable string: [3](#0-2) 

`Registry#process` validates the HMAC over the body, then immediately trusts `request.shop` (from the unsigned header) to build the `WebhookMetadata` handed to the app's handler: [4](#0-3) 

This breaks the intended identity binding:
```
HMAC_valid(body, secret) == true  ⇏  shop == originating_shop
```
The equality that should hold — "the shop this webhook is attributed to" == "the shop whose HMAC-signed payload this actually is" — is not enforced, because the HMAC only binds bytes of the body, not the header field the gem/host app treats as the tenant key. Any actor who controls a shop that installs the app (an unprivileged internet user, from the app's perspective) can obtain a body + valid HMAC for their own shop by triggering any webhook event on their own store, then resend that same body/HMAC pair to the app's webhook endpoint with the `shopify-shop-domain` header changed to a victim shop domain. `HmacValidator.validate` will still return true (it only compares the body-derived signature), and `Registry#process` will call the app's handler with `WebhookMetadata(shop: <victim shop>, body: <attacker-controlled JSON>)`.

### Impact Explanation
This is a cross-tenant identity-binding failure inside the gem's own webhook-verification code path (not a host-application misuse). Any app built on this gem that trusts `WebhookMetadata#shop` returned by a successfully-`process`ed webhook (which is the documented/intended usage — see `lib/shopify_api/webhooks/webhook_handler.rb` and the registry flow) can be made to apply attacker-supplied, fully-controlled data (order/product/customer/app-lifecycle payloads, including `shop/redact`, `customers/redact`, `app/uninstalled`, etc.) under an arbitrary victim shop's identity, since the "verified" signature says nothing about which shop it came from. This satisfies the "cross-tenant access" criterion: an unprivileged user (an app-installing merchant/attacker) can cause the gem to authenticate a payload as belonging to a different tenant.

### Likelihood Explanation
Exploitation requires no secret material and no privileged access: the attacker only needs their own (or any) shop's legitimate webhook delivery (fully within their control, since they can trigger events like `orders/create` on their own store) and the ability to POST an HTTP request with a modified `shopify-shop-domain` header to the app's public webhook endpoint. No `client_secret` or access token is needed. This is a straightforward, repeatable attack against the gem's core webhook-verification primitive.

### Recommendation
Include the shop-identifying header (and topic/webhook-id, ideally) in the HMAC-signed material, or otherwise cryptographically bind `shop` to the signature — for example by having `to_signable_string` incorporate the `shopify-shop-domain` header value, or by requiring the caller to independently verify that the `shop` header corresponds to a known, previously-installed shop before trusting it. At minimum, document prominently that `Request#shop` is unauthenticated and must not be used as a trust boundary by host applications, since currently the gem's own API implies it is safe to use post-`process`.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# captures a real, validly-signed webhook Shopify sent them, e.g. for orders/create:
raw_body = '{"id":1,"...":"attacker-controlled fields"}'
valid_hmac_b64 = "<hmac Shopify computed with the app's real secret over raw_body>"

# Attacker now replays it against the app's public webhook endpoint,
# swapping only the shop-domain header to the victim:
headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => valid_hmac_b64,
  "shopify-shop-domain" => "victim-shop.myshopify.com",  # spoofed, not covered by HMAC
  "shopify-webhook-id" => "whatever",
  "shopify-api-version" => "2024-10",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)

# Passes: HmacValidator only checks raw_body against the secret.
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry#process will now invoke the app's handler with
# WebhookMetadata(topic: "orders/create", shop: "victim-shop.myshopify.com", body: parsed_body, ...)
# i.e. attacker-controlled data attributed to the victim shop.
```
