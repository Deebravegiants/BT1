Confirmed: this is a real, reachable identity-binding gap in the gem's own webhook verification path, not a host-app misuse issue.

### Title
Webhook tenant identity (`shop`, `topic`, `webhook_id`) is not covered by HMAC verification, enabling cross-tenant metadata spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then trusts unauthenticated HTTP headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) to build the `WebhookMetadata` object handed to the app's handler. Because the HMAC never covers those headers, any unprivileged internet user who can reach the app's public webhook endpoint can pair a validly-HMAC'd body (obtained from any webhook they can legitimately receive, e.g. from their own shop's install of the app) with attacker-chosen `shop-domain`/`topic`/`webhook-id` headers, and the request will still pass `HmacValidator.validate`.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from attacker-controllable HTTP headers with no cryptographic binding to the body: [2](#0-1) 

`Registry.process` uses exactly this HMAC check as the sole authentication gate, then forwards the unauthenticated header values into `WebhookMetadata`, which is what host applications use to key data by shop/tenant and dispatch by topic: [3](#0-2) 

The binding the gem implicitly claims to have verified is:
`hmac_valid(raw_body, api_secret_key) == true` ⟺ `(shop, topic, webhook_id, body) is authentic and attributable to that shop`

But the actual binding verified is only:
`hmac_valid(raw_body, api_secret_key) == true` ⟺ `raw_body bytes are authentic`

`shop`, `topic`, and `webhook_id` are parsed from headers that never enter the signable string, so they are effectively asserted, not verified — the same class of gap as trusting `signer_account_id` instead of the value actually bound to the security-relevant action.

### Impact Explanation
Any party capable of receiving a legitimately signed webhook for topic X on shop A (e.g., a competitor or malicious merchant who installs the very same public app) can capture that valid `(raw_body, hmac)` pair and replay it to the app's shared webhook endpoint with `x-shopify-shop-domain` rewritten to victim shop B and/or `x-shopify-topic` rewritten to a more sensitive topic. Because `Registry.process` only checks the HMAC over the body, this forged request passes verification and the handler receives `WebhookMetadata` claiming the data belongs to shop B / topic Y. Any handler logic that trusts `data.shop` for tenant-scoped writes/deletes (a normal and expected usage pattern per the gem's own webhook docs and `WebhookMetadata` shape) can be tricked into performing actions or persisting attacker-supplied data under another tenant's identity — a cross-tenant integrity/access issue.

### Likelihood Explanation
The webhook endpoint is by design a public, unauthenticated HTTP endpoint (Shopify webhooks are pushed over plain POST with only the HMAC as authentication) reachable by anyone who knows or guesses the app's webhook path. Obtaining one valid `(raw_body, hmac)` pair is trivial for any user who installs the app on their own shop and receives any webhook — no leaked secret, access token, or privileged account is required. This satisfies the "unprivileged internet user" and "no credential/social engineering" scoping constraints.

### Recommendation
Bind the tenant/topic identity into the signed material actually verified, or independently verify header-derived identity against the body / a trusted lookup before constructing `WebhookMetadata`:
- Include `shop-domain`, `topic`, and `webhook-id` in the string that `to_signable_string` returns (matching Shopify's actual signing behavior if it already includes them in a canonical form), or
- Require callers to look up/validate that the `shop` header corresponds to a session that this app installed and that the topic is one actually subscribed for that shop before trusting the metadata, or
- At minimum, document prominently in `WebhookMetadata`/`Registry.process` that `shop`, `topic`, and `webhook_id` are unauthenticated header values and must not be used for tenant-scoped authorization decisions without additional verification.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, capturing the raw POST body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` with the app's shared secret).
2. Attacker sends a POST to the app's public webhook endpoint with body `B`, header `x-shopify-hmac-sha256: H` (unchanged, still valid), but headers `x-shopify-shop-domain: victim.myshopify.com` and/or `x-shopify-topic: <sensitive-topic>` (renamed to any topic the app has a handler for).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `@raw_body` (`to_signable_string`) — validation succeeds because `B`/`H` are unchanged. [4](#0-3) 
4. The app's registered handler for that topic receives `WebhookMetadata.new(topic: "<sensitive-topic>", shop: "victim.myshopify.com", body: <attacker-controlled JSON>, ...)` and, following the normal expected usage pattern of keying persistence/authorization off `data.shop`, performs a tenant-scoped action attributed to `victim.myshopify.com` using attacker-controlled body content.
