### Title
Unprivileged third party can force an adverse liquidation-parameter restamp onto a victim's supply positions via dust supply or `update_account_threshold` — (File: contracts/controller/src/risk/params.rs)

### Summary
The Cilium bug class is "selector confusion": an attacker who controls deployable labels causes a workload to be matched by a different, less favorable policy than the one that should apply. The analog in XOXNO Lending is the cached per-position risk tuple (`loan_to_value`, `liquidation_threshold`, `liquidation_bonus`, `liquidation_fees`). Each `AccountPosition` is stamped with the spoke listing's tuple at creation and is only re-stamped on explicit refresh paths. Two of those paths — `supply` of that asset by *any* third party (`merge_supply_leg` → `refresh_supply_risk_params`) and the permissionless keeper entrypoint `update_account_threshold(caller, has_risks, account_ids)` — let an unprivileged attacker choose *which* policy vintage a victim's collateral is evaluated under, including applying a higher liquidation bonus or lower liquidation threshold the moment the health-factor gate permits.

### Finding Description
`update_account_threshold` is callable by any authenticated caller over arbitrary `account_ids` [1](#0-0) . For each supply leg it invokes `refresh_supply_risk_params`, which applies the full live listing tuple when the change "favors the liquidator" (lower `liquidation_threshold`, higher `liquidation_bonus`, or lower `liquidation_fees`) and the account's HF computed with the new LT stays ≥ 1.05 [2](#0-1) . Crucially, `merge_supply_leg` runs the same refresh when *anyone* supplies a dust amount of that asset into the victim's account — the harness test `a_stranger_can_tighten_when_the_account_clears_the_update_floor` shows a one-stroop `supply_to` by CAROL restamping ALICE's threshold from 8000 to 7000 [3](#0-2) .

Like the Cilium case, the victim's collateral is "selected" by a stricter policy than the one stamped at position creation: liquidation itself never refreshes the tuple [4](#0-3) , so an inactive borrower would keep the old (favorable) stamp indefinitely; the attacker forces the new stamp the instant the gate allows, including raising `liquidation_bonus`, which directly increases the collateral seized at a later liquidation.

### Impact Explanation
When governance posts an adverse listing edit (lower LT, higher bonus, lower fee), an attacker can apply it to every outstanding account whose post-change HF ≥ 1.05 before those accounts take any action. The victim's stored `liquidation_bonus` then prices all future liquidations, so the victim permanently loses the additional bonus percentage on seized collateral — a direct, attacker-triggered theft of the bonus delta that the victim could otherwise have deferred by not interacting. The unconditional LTV restamp additionally shrinks `ltv_collateral`, which can push `ltv_collateral < total_debt` and cause every `withdraw` that leaves debt to revert at `require_post_pool_risk_gates`, temporarily freezing the victim's remaining collateral. This is Medium severity: it requires a pending adverse listing change, but is permissionless and affects all eligible accounts.

### Likelihood Explanation
- Reachability: `supply` accepts third-party deposits (`supply_to`), and `update_account_threshold` requires only the caller's own auth over arbitrary `account_ids` — both fully unprivileged [5](#0-4) .
- The HF ≥ 1.05 gate limits the attack window, but the attacker can watch prices and fire the restamp at the exact moment the window opens, maximizing accounts caught — and for debt-free accounts no gate exists at all.
- Requires a governance `EditAssetInSpoke`/`edit_asset_in_spoke` that tightens the tuple; such edits are a normal protocol operation (see `liqvid-listing-params.md` restamp runbook).

### Recommendation
Gate third-party-triggered restamps to the account owner (or delegate): in `merge_supply_leg`, only run `refresh_supply_risk_params` for `FullTuple` when the supplier is the account owner; otherwise stamp only LTV or skip the refresh. Alternatively, restrict `update_account_threshold` to accounts that opt in, or at minimum never let a third-party refresh raise `liquidation_bonus` — apply bonus increases only on owner-initiated actions, mirroring the "fail closed" treatment already used for unresolved NFT owners.

### Proof of Concept
1. ALICE supplies 10,000 USDC and borrows 1.0 ETH (HF comfortably above 1.05).
2. Governance executes `EditAssetInSpoke` raising USDC `liquidation_bonus` by 500 bps and/or lowering `liquidation_threshold`.
3. Attacker CAROL calls `supply` of 1 stroop USDC to ALICE's account, or calls `update_account_threshold(carol, true, [alice_id])`.
4. `favors_liquidator` returns true and `clears_min_hf` passes, so ALICE's stored tuple is rewritten to the adverse listing — demonstrated by `test_update_account_threshold_propagates_adverse_tuple_to_healthy_account` and `a_stranger_can_tighten_when_the_account_clears_the_update_floor` [6](#0-5) .
5. When ALICE is later liquidated, the seized bonus is priced from the attacker-installed stamp, transferring the bonus delta to liquidators that ALICE would not have paid under her original stamp.

/// Detects a lower threshold or fee, or a higher bonus, than the stored tuple.
fn favors_liquidator(position: &AccountPosition, effective_config: &AssetConfig) -> bool {
    effective_config.liquidation_threshold.raw() < position.liquidation_threshold.raw()
        || effective_config.liquidation_bonus.raw() > position.liquidation_bonus.raw()
        || effective_config.liquidation_fees.raw() < position.liquidation_fees.raw()
}

/// Checks health factor >= 1.05 with this position's threshold replaced by `new_lt`.
fn clears_min_hf(
    env: &Env,
    cache: &mut Context,
    account: &Account,
    hub_asset: &HubAssetKey,
    position: &AccountPosition,
    new_lt: Bps,
) -> bool {
    let mut hypothetical = *position;
    hypothetical.liquidation_threshold = new_lt;
    let mut supply_positions = account.supply_positions.clone();
    supply_positions.set(hub_asset.clone(), (&hypothetical).into());
    let hf =
        calculate_account_risk_totals(env, cache, &supply_positions, &account.borrow_positions)
            .health_factor;
    hf >= Wad::from(THRESHOLD_UPDATE_MIN_HF_RAW)
}

pub(crate) fn update_account_threshold(
    env: &Env,
    caller: Address,
    has_risks: bool,
    account_ids: Vec<u64>,
) {
    validation::require_authorized_caller(env, &caller);

    let scope = if has_risks {
        RiskRefreshScope::FullTuple
    } else {
        RiskRefreshScope::LtvOnly
    };

    let mut cache = Context::new(env);

    for account_id in account_ids {
        cache.reset_spoke_context();
        sync_account_thresholds(env, account_id, scope, &mut cache);
    }
}

#[test]
fn test_update_account_threshold_propagates_adverse_tuple_to_healthy_account() {
    let mut t = LendingTest::new().standard_two_asset_dust_disabled();

    t.supply(ALICE, "USDC", 100_000.0);
    t.borrow(ALICE, "ETH", 1.0);

    let account_id = t.resolve_account_id(ALICE);
    let (_, bonus_before, _) = supply_risk_fields(&t, account_id, "USDC");
    let fee_before = supply_fee_bps(&t, account_id, "USDC");

    t.edit_asset_config("USDC", |c| {
        c.loan_to_value = 5_000;
        c.liquidation_threshold = 6_100;
        c.liquidation_bonus = bonus_before + 500;
        c.liquidation_fees = fee_before - 50;
    });

    t.update_account_threshold(true, &[account_id]);

    let (lt_after, bonus_after, ltv_after) = supply_risk_fields(&t, account_id, "USDC");
    assert_eq!(
        (
            ltv_after,
            lt_after,
            bonus_after,
            supply_fee_bps(&t, account_id, "USDC")
        ),
        (5_000, 6_100, bonus_before + 500, fee_before - 50),
        "a healthy account takes the whole tuple, same vintage"
    );
