### Title
Unbounded, fee-free cryptographic verification of `handle_unsigned` batches during `validate_unsigned` enables a resource-exhaustion DoS on Hyperbridge nodes - (File: modules/pallets/ismp/src/lib.rs)

### Summary
`pallet_ismp::Call::handle_unsigned` is an unsigned, feeless extrinsic that anyone can submit. Its `ValidateUnsigned::validate_unsigned` implementation does not perform a cheap, bounded sanity check before admitting the transaction to the pool — it calls `Self::execute(messages.clone())`, which runs the *full* message-handling pipeline (proof decoding, consensus/state proof cryptographic verification, MMR/trie verification) for every message in the batch, and the extrinsic's declared `Weight` is a static constant regardless of batch size or content.

### Finding Description
`handle_unsigned` is declared with a fixed weight: [1](#0-0) [2](#0-1) 

The weight annotation `weight()` returns a constant `Weight::from_parts(300_000_000, 0)` no matter how many `Message`s are in `messages: Vec<Message>`, and no matter how large or expensive each message's proof is (BEEFY/SP1 consensus proofs, MMR multiproofs with many leaves, Merkle/trie membership and non-membership proofs, etc.).

Crucially, before the extrinsic is even admitted to the pool (and before any fee is charged, since this is an unsigned call), `ValidateUnsigned::validate_unsigned` performs the *entire* execution: [3](#0-2) 

`Self::execute` iterates every message in the vector and calls `handle_incoming_message`, which dispatches to full cryptographic verification routines (`consensus::update_client`, `request::handle`, `response::handle`, `timeout::handle`): [4](#0-3) [5](#0-4) 

For consensus messages this reaches the BEEFY/SP1 verifier, which does expensive multi-signature and STARK/SNARK-adjacent verification work per submitted proof: [6](#0-5) 

There is no upper bound enforced on `messages.len()` (a plain `Vec<Message>`, not a `BoundedVec`), nor on the number of requests/leaves nested inside each message (`RequestMessage.requests: Vec<PostRequest>` etc., also unbounded `Vec`s): [7](#0-6) 

The pallet's own documentation states the design intent was that "malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic," but that filtering step itself is the expensive operation — it requires running full verification to determine validity, so a malicious relayer can submit large numbers of syntactically valid but ultimately-invalid (or maximally-sized) batches, each forcing every full/validating node on the network to perform the complete, unmetered cryptographic verification workload during pool validation (which runs repeatedly as the transaction propagates and is re-validated), for zero fee. This is directly analogous to CVE-2019-19886: crafted requests, cheap to construct, force disproportionate server-side (node-side) computation when sent in volume, degrading availability.

### Impact Explanation
This is reachable by any unprivileged actor (a "relayer" or arbitrary network participant) with zero cost — `handle_unsigned` is unsigned and, per the docs, executed "for free." An attacker can flood the network with maximally-sized `Vec<Message>` batches containing many nested `PostRequest`/`GetRequest`/`GetResponse` entries and/or expensive-to-verify consensus/state proofs. Because the extrinsic's weight is a hardcoded constant unrelated to the actual verification cost, and because `validate_unsigned` runs the real verification workload (not a cheap pre-check) on every node that receives the gossiped transaction, this can degrade block production and RPC responsiveness across Hyperbridge nodes — a network-wide, low-cost availability/DoS impact matching the "High" severity class of the reference CVE (unbounded resource consumption from crafted, high-volume requests). This does not directly cause fund loss but can render message delivery routes unable to process legitimate traffic in a timely manner (a route unable to deliver messages), which is explicitly in-scope for this analog class.

### Likelihood Explanation
High. No authentication, staking, deposit, or signature is required to submit `handle_unsigned`; it is explicitly designed to be free and open to any submitter. Constructing large-but-structurally-valid `Vec<Message>` batches with heavy nested proof data requires no special access — only knowledge of the SCALE-encoded `Message`/`RequestMessage`/`ConsensusMessage` formats, which are public. The only friction is normal p2p extrinsic size limits and pool longevity, but an attacker can submit many such transactions from many source addresses/peers in parallel.

### Recommendation
- Enforce hard bounds (e.g. `BoundedVec` with a small `MaxMessages`/`MaxRequestsPerMessage` limit) on `messages: Vec<Message>` and on nested `Vec<PostRequest>`/`Vec<GetRequest>`/`Vec<GetResponse>` fields so batch size cannot be attacker-inflated.
- Make the declared `Weight` for `handle_unsigned` proportional to the actual number/size of messages and proof bytes (benchmark-derived, not a flat constant), so `pallet_transaction_payment`/block weight accounting reflects true cost and `CheckWeight` can reject oversized batches before verification.
- In `validate_unsigned`, perform cheap structural/size checks (message count, proof byte-length caps, cross-message consistency) before invoking the full `execute()`/cryptographic verification path, so obviously oversized or malformed batches are rejected without paying the full verification cost.
- Consider rate-limiting or requiring a bonded/staked relayer identity for `handle_unsigned` submissions at the transaction-pool level to raise the cost of flooding.

### Proof of Concept
1. Construct a `pallet_ismp::Call::handle_unsigned { messages }` where `messages` contains the maximum number of `Message::Request(RequestMessage { requests: <many large PostRequest entries>, proof: <maximal MMR multiproof>, .. })` entries that fit within the extrinsic size limit.
2. Submit many such unsigned extrinsics concurrently from multiple peer connections (no signing key or balance needed).
3. Because `ValidateUnsigned::validate_unsigned` (modules/pallets/ismp/src/lib.rs:614-625) calls `Self::execute(messages.clone())` for every submission — running full MMR/trie proof verification via `handle_incoming_message` — before deciding whether to admit the transaction, each node in the network performs the full, unmetered verification workload for every submitted batch, at zero cost to the attacker, since the declared weight (`weight()`, a flat `300_000_000` regardless of batch content) never reflects or caps the true cost.

*Note: full verification of exact upper bounds on `Vec<Message>`/nested request-array sizes and any implicit extrinsic-length caps enforced elsewhere in the runtime (e.g. `BlockLength`/`system` pallet config) was not independently confirmed in this pass; a Devin session with full repo access could pin the exact size ceilings and produce a concrete benchmark showing the discrepancy between declared weight and actual execution time.*

pub fn handle_incoming_message<H>(
	host: &H,
	message: Message,
) -> Result<MessageResult, anyhow::Error>
where
	H: IsmpHost,
{
	match message {
		Message::Consensus(consensus_message) => consensus::update_client(host, consensus_message),
		Message::FraudProof(fraud_proof) => consensus::freeze_client(host, fraud_proof),
		Message::Request(req) => request::handle(host, req),
		Message::Response(resp) => response::handle(host, resp),
		Message::Timeout(timeout) => timeout::handle(host, timeout),
	}
}
