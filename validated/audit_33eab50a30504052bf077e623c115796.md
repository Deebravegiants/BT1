## Analog Found

### Title
Uniswap V3 pool price manipulation can force reverts of native-token `dispatch`/`fundRequest`/`openOrder` calls, causing denial-of-service to message and intent delivery - (File: `evm/src/utils/uniswapv2/UniV3UniswapV2Wrapper.sol`)

### Summary
`EvmHost` and `IntentGatewayV2` allow users to pay dispatch/relayer/order fees with native tokens, delegating to a "Uniswap V2 Router"-shaped `uniswapV2Router()` address. On chains without a native Uniswap V2 deployment, this role is filled by `UniV3UniswapV2Wrapper`, which internally performs an exact-output swap against a single Uniswap V3 pool using `IV3SwapRouter.ExactOutputSingleParams` with `amountInMaximum: msg.value` — the exact same pattern flagged in the referenced report. Any unprivileged actor can manipulate that V3 pool's price with a large trade to push the required input above the caller's supplied `msg.value`, causing the swap (and therefore the whole dispatch/fund/order transaction) to revert.

### Finding Description
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` all follow the same pattern: when `msg.value > 0`, they call `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. [1](#0-0) [2](#0-1) 

`IntentGatewayV2.openOrder()` does the same thing for order fee escrow when the user pays with native token. [3](#0-2) 

The `uniswapV2Router()` value returned by `EvmHost` is not necessarily a real Uniswap V2 router — on chains lacking one, `UniV3UniswapV2Wrapper` is deployed to expose the same interface while routing through Uniswap V3's `SwapRouter02` via `exactOutputSingle`, using a single hardcoded pool `fee` tier (`_params.maxFee`) and setting `amountInMaximum: msg.value`: [4](#0-3) 

This is structurally identical to the reported `InfiltrationPeriphery.sol` bug: an `ExactOutputSingleParams` swap whose `amountInMaximum` is capped by the caller's fixed payment. Any address can submit a large swap against that specific V3 pool (single fee tier, no TWAP protection) immediately before the victim's transaction to shift the price so that the required input to obtain `fee` (or `amount`) tokens exceeds the `msg.value` the victim supplied, causing Uniswap's router to revert with an "STE" (`amountInMaximum` exceeded) error and thus reverting the entire `dispatch`/`fundRequest`/`openOrder` call.

### Impact Explanation
An attacker can selectively grief specific users' time-sensitive native-token payments:
- Prevent a `PostRequest`/`GetRequest` dispatch (or a `fundRequest` top-up) from succeeding before a deadline, causing a message never to be sent, or a relayer fee bump to fail, potentially leading to lost/timed-out cross-chain messages — i.e., "a route unable to deliver messages."
- Prevent `IntentGatewayV2.openOrder()` from completing when the order fee is paid in native token, blocking users from placing intents before an order deadline, causing missed fills or fund lock-up in transient state.

This satisfies the acceptance bar of unsound message delivery guarantees for an unprivileged, single-transaction attack path (a large V3 swap), without any admin/governance/prover assumptions.

### Likelihood Explanation
Any account can submit a swap on the underlying Uniswap V3 pool used by `UniV3UniswapV2Wrapper` for the `WETH -> feeToken` pair; the wrapper targets a single fixed fee tier with no slippage buffer beyond the user-supplied `msg.value`, and no TWAP or price-limit protection (`sqrtPriceLimitX96: 0`) is applied by the wrapper. This makes manipulation straightforward and cheap for any pool without deep liquidity, and repeatable each time a targeted user attempts the same operation.

### Recommendation
- Allow callers to specify their own `amountInMaximum` (slippage tolerance) instead of implicitly using all of `msg.value`, and refund any unused native token.
- Consider using a TWAP-based price check or a maximum allowed price-impact/slippage bound when computing required swap input in `UniV3UniswapV2Wrapper`.
- Offer a fee-token-only payment path as the recommended flow (already documented) and clearly warn integrators that native-token payments on V3-wrapper chains are subject to sandwich/DoS risk, or add a keeper/backstop path allowing retried dispatch when native swap reverts.

### Proof of Concept
1. Chain X has no native Uniswap V2 router; `EvmHost.uniswapV2Router()` points to a deployed `UniV3UniswapV2Wrapper` backed by a single, thinly-liquid `WETH/feeToken` V3 pool at fee tier `maxFee`.
2. Alice wants to dispatch a POST request paying with native token: she sends `msg.value = X` expecting `swapETHForExactTokens` to yield `post.fee` feeTokens, per `EvmHost.dispatch()`. [1](#0-0) 
3. Mallory front-runs Alice's transaction with a large `exactInputSingle`/`exactOutputSingle` swap on the same V3 pool, moving the price so that obtaining `post.fee` feeTokens now requires more than `X` WETH.
4. `UniV3UniswapV2Wrapper.swapETHForExactTokens` forwards to `IV3SwapRouter.exactOutputSingle` with `amountInMaximum: msg.value (X)`; the swap reverts because `amountIn` needed exceeds `X`. [5](#0-4) 
5. Alice's entire `dispatch()` call reverts, and Mallory can repeat this each time Alice retries, indefinitely blocking her time-sensitive dispatch/fundRequest/openOrder call.

    function swapETHForExactTokens(uint256 amountOut, address[] calldata path, address recipient, uint256 deadline)
        external
        payable
        returns (uint256[] memory)
    {
        address weth = _params.WETH;
        if (path[0] != weth) revert InvalidWethAddress();

        (bool sent,) = weth.call{value: msg.value}("");
        if (!sent) revert DepositFailed();

        IV3SwapRouter.ExactOutputSingleParams memory params = IV3SwapRouter.ExactOutputSingleParams({
            tokenIn: weth,
            tokenOut: path[1],
            fee: _params.maxFee,
            recipient: recipient,
            amountOut: amountOut,
            amountInMaximum: msg.value,
            sqrtPriceLimitX96: 0
        });

        bytes memory swapCall = abi.encodeWithSelector(IV3SwapRouter.exactOutputSingle.selector, params);

        bytes[] memory data = new bytes[](1);
        data[0] = swapCall;

        bytes[] memory results = IMulticallExtended(_params.swapRouter).multicall(deadline, data);
        uint256 spent = abi.decode(results[0], (uint256));

        if (spent < msg.value) {
            uint256 refund = msg.value - spent;
            IWETH(weth).withdraw(refund);

            (bool success,) = msg.sender.call{value: refund}("");
            if (!success) revert RefundFailed();
        }
