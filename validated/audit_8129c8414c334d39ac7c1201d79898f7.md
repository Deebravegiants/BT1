### Title
Webhook Shop-Domain Header Not Covered by HMAC Allows Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` from the unauthenticated `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) HTTP header, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator` only covers the raw request body. Because a public app's webhook HMAC secret (`api_secret_key`) is shared across all shops that install the app, any shop owner who has installed the app can capture one of their own genuine, validly-signed webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` header changed to a different (victim) shop, producing a request that still passes `HmacValidator.validate` while `data.shop` now points at a shop the attacker doesn't control.

### Finding Description
`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it to the `hmac` field: [4](#0-3) 

For webhook requests, `to_signable_string` returns only the raw body, and `shop` is read straight from a header that is not part of that signed string: [5](#0-4) 

`Registry.process` validates only the HMAC of the body, then forwards `request.shop` unchecked into `WebhookMetadata` passed to the app's handler: [6](#0-5) 

This breaks the intended binding: **bytes verified by the HMAC (raw body) ≠ bytes the handler treats as the authenticated tenant identifier (`shop-domain` header)**. Since a public app's webhook signing secret is the app's single `client_secret`, shared across every shop that installs the app, any shop (including one controlled by an attacker who legitimately installed the app) can obtain a real, correctly-HMAC-signed webhook body/signature pair from Shopify for their own store, then replay that exact body+HMAC to the app's webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. `HmacValidator.validate` still returns `true` because it never inspects the header, and the handler receives `data.shop` equal to the victim's domain paired with attacker-controlled body content.

### Impact Explanation
This is a cross-tenant integrity/confidentiality break: the app's webhook handler is documented and expected to key all tenant-scoped work (persistence, background jobs, session lookups) off `data.shop` [7](#0-6) . An attacker who merely installs the app on their own store (no special privileges, no leaked secrets) can forge webhook events that appear to originate from a target shop, injecting attacker-chosen data (order/product/customer payloads, mandatory GDPR webhook bodies, etc.) attributed to another tenant. Depending on the host app, this can corrupt another merchant's data, trigger unauthorized actions on their behalf, or leak processing behavior across tenants — qualifying as cross-tenant access.

### Likelihood Explanation
Likelihood is high for any app relying solely on this gem's webhook processing as documented: the attacker only needs their own legitimate app installation (no credential theft, no TLS interception) to obtain a valid raw-body/HMAC pair, and then simple HTTP replay with a modified header to any exposed webhook endpoint.

### Recommendation
Include the shop domain (and ideally topic/webhook-id) inside the HMAC-covered signable string for webhook requests, or independently verify that the `shop-domain` header corresponds to a shop actually authorized/installed for this app (e.g., cross-check against known installed shop sessions) before trusting `data.shop` in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target public app on their own shop `attacker.myshopify.com`, and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for the app's shared `client_secret`).
2. Attacker replays the same request to the app's webhook endpoint but sets `X-Shopify-Shop-Domain: victim.myshopify.com`, keeping body `B` and header `H` unchanged.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over the raw body `B` — validation succeeds [8](#0-7) .
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim.myshopify.com", body: parsed(B), ...)` [9](#0-8) , causing the host app to process attacker-controlled data as if it belongs to `victim.myshopify.com`.
