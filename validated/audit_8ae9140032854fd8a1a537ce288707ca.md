## Title
JWT replay-protection check-then-act race allows the same trigger JWT to be replayed multiple times before `jti` is recorded - (File: core/services/gateway/handlers/capabilities/v2/workflow_metadata_handler.go)

## Summary
`WorkflowMetadataHandler.Authorize` checks a JWT's `jti` against the replay cache via `isReplay()` and only marks it as used via `recordUsage()` after signature verification and authorized-key checks succeed, rather than performing an atomic check-and-set. Concurrent requests carrying the identical signed JWT can all observe `isReplay() == false` before any of them calls `recordUsage()`, allowing each to pass authorization and be forwarded to the DON, producing multiple workflow executions from a single signed, supposedly single-use JWT.

## Finding Description
The unprivileged, internet-facing HTTP Trigger gateway path authenticates each request via `httpTriggerHandler.HandleUserTriggerRequest` -> `authorizeRequest` -> `WorkflowMetadataHandler.Authorize`: [1](#0-0) 

Inside `Authorize`, the sequence is: verify JWT signature, check replay status, look up authorized signer, and only then record usage: [2](#0-1) 

The replay cache implementation confirms `isReplay` and `recordUsage` are two independently-locked operations (`RLock`/`RUnlock` for read, separate `Lock`/`Unlock` for write), with no lock held across the full check-then-act window spanning JWT verification and authorized-key lookup: [3](#0-2) 

Because `isReplay` and `recordUsage` are separate critical sections rather than one atomic "claim jti" operation, any number of concurrent goroutines calling `Authorize` with the same token can all pass the `isReplay` check before the first one reaches `recordUsage`. There is no additional locking, per-`jti` mutex, or idempotency mechanism elsewhere in the call path (`resolveWorkflowID`, `checkRateLimit`, `sendWithRetries`) that would close this window.

## Impact Explanation
An external, unprivileged client holding one valid signed HTTP-trigger JWT can fire multiple concurrent POSTs to the gateway with the identical token/`jti` before the first request's `Authorize` call completes `recordUsage`. Each concurrent request independently passes authorization and is forwarded via `sendWithRetries` to the workflow DON, resulting in duplicate/unintended workflow executions triggered by a single signed authorization — a concrete unauthorized job run outcome, defeating the intended one-token-one-execution guarantee of the CRE HTTP Trigger.

## Likelihood Explanation
The race only requires the ability to send the same JWT concurrently — trivial to script for any external client with a single legitimate token, requiring no special network position, no operator/node privilege, and no non-default configuration. The existing sequential-replay test (`TestHttpTriggerHandler_HandleUserTriggerRequest`, "duplicate JWT token and request ID") only exercises the two calls sequentially and passes, confirming the sequential check works but not covering the concurrent race, which remains open.

## Recommendation
Make the JWT replay check-and-mark operation atomic: combine `isReplay` and `recordUsage` into a single method (e.g., `ClaimOnce(jti)` / `CheckAndSet(jti)`) that holds the cache's mutex across both the existence check and the write, returning whether the `jti` was already claimed, and have `Authorize` reject the request based on that single atomic result instead of two separately-locked calls.

## Proof of Concept
1. Obtain one validly-signed HTTP trigger JWT for a registered workflow (`req.Auth`), as constructed in `TestHttpTriggerHandler_HandleUserTriggerRequest_JWTAuthorization`.
2. Launch N goroutines that all call `handler.HandleUserTriggerRequest(ctx, req, callback, time.Now())` concurrently with the identical `req`/JWT (unlike the existing sequential test, dispatch them via `sync.WaitGroup` so `Authorize` calls overlap).
3. Because `isReplay` and `recordUsage` in `jwtReplayCache` are separately locked (lines 399-412), multiple goroutines can read `isReplay() == false` before any writes `recordUsage`, causing more than one goroutine to succeed and call `sendWithRetries`, verifiable by asserting `mockDon.SendToNode` is invoked for more than one full fan-out set for the same `jti`.

func (h *WorkflowMetadataHandler) Authorize(workflowID string, token string, req *jsonrpc.Request[json.RawMessage]) (*gateway.AuthorizedKey, error) {
	claims, signer, err := utils.VerifyRequestJWT(token, *req)
	if err != nil {
		h.lggr.Errorw("Failed to verify JWT", "error", err)
		return nil, err
	}

	if h.jwtCache.isReplay(claims.ID) {
		h.lggr.Warnw("JWT token has already been used", "workflowID", workflowID, "signer", signer.Hex(), "jti", claims.ID)
		return nil, errors.New("JWT token has already been used. Please generate a new one with new id (jti)")
	}

	keys, exists := h.authorizedKeys[workflowID]
	if !exists {
		h.lggr.Errorw("Workflow ID not found in authorized keys", "workflowID", workflowID)
		return nil, fmt.Errorf("workflow ID %s not found", workflowID)
	}
	key := gateway.AuthorizedKey{
		KeyType:   gateway.KeyTypeECDSAEVM,
		PublicKey: strings.ToLower(signer.Hex()),
	}
	if _, exists = keys[key]; !exists {
		h.lggr.Errorw("Signer not found in authorized keys", "signer", signer.Hex())
		return nil, fmt.Errorf("signer '%s' is not authorized for workflow '%s'. Ensure that the signer is registered in the workflow definition", signer.Hex(), workflowID)
	}
	h.jwtCache.recordUsage(claims.ID)

	return &key, nil
}

func (cache *jwtReplayCache) isReplay(jti string) bool {
	cache.mu.RLock()
	defer cache.mu.RUnlock()

	_, exists := cache.cache[jti]
	return exists
}

func (cache *jwtReplayCache) recordUsage(jti string) {
	cache.mu.Lock()
	defer cache.mu.Unlock()

	cache.cache[jti] = time.Now()
}
