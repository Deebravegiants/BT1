Audit Report

## Title
Cross-user response confusion via unauthenticated `MessageID` collision in gateway legacy callback map - ([File: core/services/gateway/handlers/capabilities/handler.go])

## Summary
The gateway's legacy WebAPI trigger flow stores per-request response callbacks in a shared map (`handler.savedCallbacks`) keyed solely by the client-supplied `MessageID`, with no check for an existing entry before insertion and no binding of the map key to the caller's identity. Any client able to produce a valid message signature (a trivial, unprivileged action — anyone can generate an ECDSA keypair and sign a message body) can choose an arbitrary `MessageID`, and if it collides with another in-flight request's `MessageID`, the second caller's callback silently overwrites the first's, causing the eventual DON response to be delivered to the wrong caller.

## Finding Description
`gateway.ProcessRequest` decodes the incoming request, validates the message's signature/structure via `msg.Validate()`, and for legacy DON-ID requests calls `h.HandleLegacyUserMessage(ctx, msg, callback)` with a caller-supplied callback object [1](#0-0) .

`HandleLegacyUserMessage` stores this callback in the shared `savedCallbacks` map keyed only by `msg.Body.MessageID`, with no check for whether an entry already exists for that key: [2](#0-1) 

Critically, `Message.Validate()` confirms the message is validly signed and derives `Body.Sender` from the signature, but this `Sender` value is never used as part of the `savedCallbacks` key or as an ownership check before the map write: [3](#0-2)  The only constraints on `MessageID` are length/null-byte checks — nothing enforces uniqueness or per-sender scoping [4](#0-3) .

When any DON node later responds with `MethodWebAPITrigger`, `handleWebAPITriggerMessage` looks up and deletes the callback purely by `MessageID` and delivers the response to whatever caller currently occupies that slot: [5](#0-4) 

This is corroborated by contrast with the node-side `responses` map in the outgoing connector handler, which explicitly rejects duplicate IDs to prevent this exact class of bug — a mitigation that is conspicuously absent in the legacy handler's callback map: [6](#0-5) 

Any client capable of self-signing a message (trivial, requires no special privilege or credential beyond generating an ECDSA key) can trigger `HandleLegacyUserMessage` with an arbitrary `MessageID` of its choosing, since the signature only proves who signed the message, not that the `MessageID` is unique or owned by that signer.

## Impact Explanation
If two unprivileged callers submit requests to the same DON with colliding `MessageID` values, the second caller's callback overwrites the first's in `savedCallbacks`. The eventual node response for that `MessageID` (which is actually correlated with the first caller's forwarded request/payload) is delivered to the second caller instead — an information disclosure of another party's trigger response — while the first caller's request either times out or never resolves (denial of that caller's request). This matches the "cross-user response corruption" in-scope impact category, since it is triggerable purely through the public gateway API by any client with a self-generated signing key, with no operator/admin access, malicious node, or malicious DON peer required.

## Likelihood Explanation
Exploitability is gated entirely on `MessageID` collision. An attacker can directly control this by choosing their own `MessageID`; the vulnerability is triggerable as soon as the attacker's chosen `MessageID` matches any other in-flight request's `MessageID` at the same DON — which requires either predictable/reused ID schemes on the client side or an attacker deliberately targeting a known/observed ID (e.g., replaying an ID seen elsewhere, or brute-forcing against a busy handler with up to `defaultMaxSavedCallbacks = 20000` concurrent slots and a 120-second default callback lifetime). The root-cause gap — missing duplicate/ownership check in `HandleLegacyUserMessage` — exists unconditionally at the gateway layer regardless of how "good" client-side ID generation practices are, and the fix (uniqueness check, as already implemented in `outgoing_connector_handler.go`) is trivial to add, indicating this is a genuine, currently-unmitigated code-level gap rather than a purely theoretical one.

## Recommendation
- In `HandleLegacyUserMessage`, reject the request (returning an error to the caller) if `h.savedCallbacks[msg.Body.MessageID]` already exists, mirroring the duplicate-check in `responses.new` in `outgoing_connector_handler.go`.
- Scope the `savedCallbacks` key by both `MessageID` and the signer-derived `Body.Sender` so that a collision cannot cross caller/session boundaries.
- Alternatively, have the gateway generate its own internal correlation ID for callback storage rather than trusting the client-supplied `MessageID` directly as the map key.

## Proof of Concept
1. Generate two distinct signing keys (Attacker and Victim) — no special privilege needed, this is fully self-service.
2. Victim sends a legacy request to `gateway.ProcessRequest` with `Body.Method = "web_api_trigger"`, `Body.DonID = <target DON>`, and `Body.MessageID = "X"`, signed with the Victim's key. This causes `HandleLegacyUserMessage` to insert `savedCallbacks["X"] = callbackVictim` and forward the request to all DON members (`core/services/gateway/handlers/capabilities/handler.go:411-420`).
3. Before any DON node responds, Attacker sends its own legacy request with the same `Body.MessageID = "X"` (any other body content) signed with the Attacker's key. `HandleLegacyUserMessage` overwrites `savedCallbacks["X"]` with `callbackAttacker` — no existing-entry check is performed.
4. A DON node responds with `MethodWebAPITrigger` and `MessageID = "X"` (in response to the Victim's original forwarded request). `handleWebAPITriggerMessage` looks up `savedCallbacks["X"]`, finds `callbackAttacker`, deletes the entry, and delivers the Victim's response data to the Attacker (`core/services/gateway/handlers/capabilities/handler.go:148-162`).
5. A Go unit/integration test can assert this directly: construct two `*handler` callbacks, call `HandleLegacyUserMessage` twice with the same `MessageID` from different signers, then call `HandleNodeMessage`/`handleWebAPITriggerMessage` and assert that the second (attacker's) callback receives the response intended for the first (victim's) request.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}

	r.mu.Lock()

		return nil, fmt.Errorf("already have response for id: %s", id)
	}

	// Buffered so we don't wait if sending
	ch := make(chan *api.Message, 1)
	r.chs[id] = ch
