### Title
Webhook `shop-domain`, `topic`, `api-version` and `webhook-id` headers are trusted for routing/handler dispatch without being covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC only over the raw request body, while the shop, topic, api-version and webhook-id are taken from unauthenticated HTTP headers and passed straight to the registered handler as trusted metadata.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 
while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from headers with no cryptographic binding to the HMAC at all: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then immediately trusts `request.topic` and `request.shop` to dispatch to a handler and construct `WebhookMetadata`: [3](#0-2) 

The binding that should hold is: `hmac == HMAC(secret, shop ‖ topic ‖ body)`, i.e. the identity of the shop/topic asserted to the handler should equal the identity actually authenticated by the HMAC. Instead, only `hmac == HMAC(secret, body)` is checked, and `shop`/`topic` are asserted independently of that proof. An attacker who can obtain any one valid `(body, hmac)` pair signed by the merchant's own secret (e.g., by triggering/observing a legitimate webhook for their own store, or via a delivery replay) can resubmit the same body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`) header for a different tenant. `HmacValidator.validate` will still pass because it only recomputes the signature over `@raw_body`: [4](#0-3) 

The handler then receives `WebhookMetadata` asserting the forged `shop`, and any app logic that uses that field to select which tenant's records to update, credit, or fulfill (a common integration pattern) will act on the wrong tenant using attacker-supplied identity.

### Impact Explanation
This breaks the shop-authenticated == shop-acted-upon identity binding for webhook processing, enabling cross-tenant data confusion inside apps that rely on `WebhookMetadata#shop` (as documented and demonstrated) to attribute an inbound event to the correct merchant. This matches the Critical/High "cross-tenant access" impact category since a merchant's own valid webhook traffic can be relayed to make the host app believe it originated from a different shop.

### Likelihood Explanation
Exploitation requires an attacker who can capture or generate at least one legitimately signed `(body, hmac)` pair for their own shop (trivial — they own that shop and can trigger webhooks such as `orders/create` on themselves) and then replay it to the app's public webhook endpoint with a forged `shop-domain` header, since the header is never included in the signed payload. No access token, `client_secret`, or privileged credentials are required — only network access to the app's public webhook URL, which is unauthenticated by design (Shopify relies solely on the HMAC to prove authenticity of the whole request).

### Recommendation
Bind the asserted shop/topic identity to the HMAC-verified payload rather than trusting separate headers: either (a) fetch the mandatory-topic/shop pairing from Shopify's Admin API using an established session for a given shop before acting on the payload, (b) reject/ignore the `shop` and `topic` headers unless they are echoed inside the HMAC-signed body, or (c) document explicitly that `WebhookMetadata#shop`/`#topic` are unauthenticated and must never be used for authorization or tenant selection without additional verification (e.g., matching against a shop domain independently known to the app for the webhook's registration).

### Proof of Concept
1. Attacker's own store (`attacker-shop.myshopify.com`) triggers a legitimate webhook, e.g. `orders/create`. Shopify sends:
```
x-shopify-topic: orders/create
x-shopify-hmac-sha256: <valid HMAC of body B>
x-shopify-shop-domain: attacker-shop.myshopify.com
body: B
```
2. Attacker resends the exact same body `B` and HMAC value to the app's public webhook endpoint, but sets:
```
x-shopify-shop-domain: victim-shop.myshopify.com
```
3. `HmacValidator.validate` recomputes the HMAC over `B` only [4](#0-3)  and succeeds, since the shop header was never part of the signed content.
4. `Registry.process` dispatches to the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` [5](#0-4) , causing the app to process attacker-controlled order data under the victim tenant's identity.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
