### Title
Webhook `shop` identity is not bound by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id` and `api_version` values that the library extracts and forwards to the app's `WebhookHandler` are read directly from HTTP headers and are never included in the HMAC-signed string [2](#0-1) .

### Finding Description
The binding that should hold is: `hmac_signed_bytes == bytes_that_determine_which_shop_the_webhook_is_processed_for`. In this gem it does not.

- `Webhooks::Request#hmac` reads the `hmac-sha256` header [3](#0-2) .
- `Webhooks::Request#to_signable_string` returns only `@raw_body` — nothing else [4](#0-3) .
- `Webhooks::Request#shop`, `#topic`, `#webhook_id`, `#api_version` are all pulled from headers that are entirely attacker-controlled and unauthenticated [5](#0-4) .
- `Utils::HmacValidator.validate` only checks that the computed HMAC of `to_signable_string` (the body) matches the supplied signature, using the app's single `api_secret_key` shared across every shop that installs the app [6](#0-5) .
- `Registry.process` validates the HMAC and then constructs `WebhookMetadata` using `request.shop` (the unauthenticated header value) verbatim, handing it to the app's handler as the trusted shop identity [1](#0-0) .

Because the app's `api_secret_key` is identical for every shop that installs the app (it is per-app, not per-shop), any attacker who can install the app on a shop they control can capture a legitimately-signed webhook (valid body + valid HMAC). They can then replay that exact body/HMAC pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or topic/webhook-id) header for a victim shop's domain. Since none of these header-derived fields are part of the signed bytes, the forged request passes `HmacValidator.validate` and the handler is invoked believing the event pertains to the victim shop.

### Impact Explanation
This breaks the tenant isolation the library implicitly promises: `hmac_valid? => this event genuinely originates from and concerns `shop`. Any app that uses `data.shop` from `WebhookMetadata` to select which merchant's record to update/delete (a very common pattern shown in this gem's own documentation) [7](#0-6)  can be tricked into applying another shop's webhook payload to an arbitrary victim shop identifier, e.g. forging `shop/redact`, `app/uninstalled`, or `customers/data_request` events for a shop the attacker doesn't control. This is a cross-tenant data-integrity/confusion issue reachable by any unprivileged internet user who can install the app once on a shop of their own.

### Likelihood Explanation
Likelihood is moderate-to-high: obtaining a valid `(body, hmac)` pair requires nothing more than installing the target app on any shop (including a free development store) and observing one webhook delivery, since the same `api_secret_key` signs webhooks for all shops. Replaying it against the app's public endpoint with a modified `Shop-Domain` header requires no additional secret.

### Recommendation
Do not trust `request.shop`/`request.topic`/`request.webhook_id` from headers as authenticated data. At minimum, document (and ideally enforce in the gem) that consuming apps must cross-check the header-derived `shop` against a shop that is actually known/installed, and that HMAC verification alone does not authenticate the shop, topic, or webhook id — only the body content. Longer term, consider whether `to_signable_string` can incorporate header values Shopify's HMAC scheme intends to protect, or emit an explicit warning/flag from `HmacValidator`/`WebhookMetadata` that these fields are unauthenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` (a store the attacker controls) and triggers any subscribed webhook topic (e.g., `app/uninstalled`).
2. Attacker captures the raw POST body and the `X-Shopify-Hmac-Sha256` header from that legitimate delivery. Since `HmacValidator` signs only `raw_body` with the app's single `api_secret_key` [4](#0-3) , this `(body, hmac)` pair is valid for any shop.
3. Attacker POSTs the same body and HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and optionally forges `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `Registry.process` calls `HmacValidator.validate(request)`, which succeeds because it only checks the body signature [8](#0-7) .
5. The app's handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` [9](#0-8)  and processes the attacker's forged payload as if it genuinely originated from and concerns the victim shop.
