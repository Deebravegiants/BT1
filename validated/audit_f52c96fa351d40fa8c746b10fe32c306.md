### Title
`convert_to_erc20`/`convert_to_balance` use `saturating_sub` for decimal deltas, silently skipping rescaling when local decimals exceed remote ERC20 decimals, enabling unbacked mint on the destination `HyperFungibleToken` contract - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s cross-chain amount conversion helpers scale a token amount between the local Substrate asset's decimals and the registered remote-chain (EVM) `erc_decimals`. Both helpers only ever *multiply* by `10^(erc_decimals.saturating_sub(local_decimals))` (or vice versa), and use `saturating_sub`, which clamps to `0` instead of dividing when the exponent would be negative. When a token's local decimals are greater than the `erc_decimals` recorded for a destination chain, the amount that should be divided down is instead passed through unscaled, producing a `Message.amount` that is inflated by `10^(local_decimals - erc_decimals)` and delivered to the counterpart EVM contract, which mints unconditionally on that raw value.

### Finding Description
`convert_to_erc20` is used in `Pallet::send` to compute the ERC20-denominated amount embedded in the outgoing `Message` that is dispatched to the destination chain's `HyperFungibleToken`/`BridgeToken` contract: [1](#0-0) 

This is called as: [2](#0-1) 

The `decimals` local variable is the local asset's own decimals (native `T::Decimals` or the `Assets` pallet's `decimals()`), and `erc_decimals` is the value stored in `Precisions` for `(asset, destination)`, set by `CreateOrigin` via `register_token`/`update_token`. `convert_to_erc20` computes:

```
U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
```

If `erc_decimals < local_decimals` (a perfectly ordinary, non-malicious configuration — e.g. a locally 18-decimal asset bridged to a 6-decimal ERC20 representation, the common case for stablecoins), `erc_decimals.saturating_sub(local_decimals)` clamps to `0`, so the multiplier is `10^0 = 1`. The function returns the *raw local-decimal amount unchanged*, instead of dividing it by `10^(local_decimals - erc_decimals)` as correct rescaling requires.

That erroneously-large `erc20_amount` is placed directly into the dispatched `Message.amount` field: [3](#0-2) 

On the destination chain, the EVM `HyperFungibleTokenImpl` mints exactly the amount encoded in the message with no independent decimal validation — it trusts the value from the ISMP message body: [4](#0-3) 

The exact same flawed pattern also exists in reverse for `convert_to_balance`, used on the receiving side (`on_accept`) and on `on_timeout` refunds, using `erc_decimals.saturating_sub(local_decimals)` as the divisor exponent — clamped to `0` (i.e. no division) when `erc_decimals < local_decimals`: [5](#0-4) [6](#0-5) 

This mirrors the reported `PerpDepository._rebalanceNegativePnlWithSwap` bug class exactly: an amount denominated at one decimal precision is passed through to a receiving contract/vault that expects a different precision, and the conversion helper fails to perform the required rescale in one of the two directions, inflating or deflating the transferred value by orders of magnitude (`10^n`).

### Impact Explanation
Any signed user can call the pallet's `send` extrinsic (unprivileged, reachable in a single transaction). For any registered token where `Precisions::<T>::get(asset, destination) < local asset decimals` (a legitimate, expected configuration whenever the local asset has more decimal precision than the destination ERC20 token — e.g. bridging an 18-decimal Substrate asset to a 6-decimal-styled EVM representation), the amount encoded into the outgoing message is not divided down as required. The destination `HyperFungibleToken`/`BridgeToken` contract mints the raw (unscaled) value, resulting in an unbacked mint on the EVM side inflated by `10^(local_decimals - erc_decimals)` relative to what was actually locked/burned on the source chain. This is a direct, protocol-level "unbacked mint" — the EVM-side supply exceeds the amount escrowed/burned on the substrate side by orders of magnitude, breaking the token-bridge's backing invariant and allowing extraction of value disproportionate to what was locked.

### Likelihood Explanation
High. It requires no privileged action beyond the ordinary, expected `register_token`/`update_token` configuration of decimals for a token pair where the local asset decimals are strictly greater than the destination `erc_decimals` — a completely normal and foreseeable configuration (most ERC20s use 6 or 8 decimals, while Substrate asset pallets commonly use 10, 12, or 18). Any holder of the local asset can trigger the bug by simply calling `send` to that destination.

### Recommendation
Fix `convert_to_erc20` and `convert_to_balance` to handle both directions of the decimal delta explicitly, rather than relying on `saturating_sub` to silently no-op when the exponent would be negative:

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}
```

and symmetrically for `convert_to_balance`. Add explicit unit tests for both `erc_decimals > local_decimals` and `erc_decimals < local_decimals` cases in both helpers.

### Proof of Concept
1. Register a local asset with `local_decimals = 18` (e.g. via `Assets::metadata` reporting 18 decimals) and configure `Precisions::<T>::insert(asset_id, dest_chain, 6)` (a normal, non-malicious 6-decimal ERC20 counterpart) via `register_token`.
2. A user calls `Pallet::send` with `amount = 1_000_000_000_000_000_000` (i.e., "1" token at 18 decimals), burning/locking that amount locally.
3. Inside `send`, `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes `erc_decimals.saturating_sub(local_decimals) = 0`, so it returns `1e18` unchanged (correct value should be `1e18 / 10^12 = 1_000_000`, i.e. "1" token at 6 decimals).
4. The dispatched `Message.amount = 1e18` is delivered to the destination `HyperFungibleToken` contract's `onAccept`, which calls `_mint(to, 1e18)` — minting `1e18` raw ERC20 units instead of the intended `1e6`, an inflation of `10^12`x relative to the 1 token actually locked on the source chain.
