Confirmed: the webhook `Registry.process` passes `request.shop` directly into the handler without that value ever being covered by the HMAC signature.### Title
Webhook shop identity (`Webhooks::Request#shop`) is not covered by the HMAC signature, enabling cross-tenant webhook data confusion - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then hands the handler a `WebhookMetadata` struct whose `shop` field is read from an HTTP header that is never included in the signed material. This breaks the intended binding `hmac_signed_bytes == identity_bytes_trusted`, since the identity (`shop`) is trusted independently of what was actually authenticated.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Webhooks::Request#shop` is derived purely from the `shopify-shop-domain` / `x-shopify-shop-domain` HTTP header, which is not part of the signable string: [2](#0-1) 

`Registry.process` validates the HMAC against `request` (i.e., against the body only) and, once that check passes, blindly forwards `request.shop` — an unauthenticated value — to the host application's handler as the tenant identity: [3](#0-2) 

The resulting `WebhookMetadata.shop` field is a plain `String` const with no further verification and is the only tenant identifier passed to `WebhookHandler#handle`: [4](#0-3) 

Because `shop` is acted upon by the handler but not covered by the HMAC, the equality the gem should guarantee — `hmac_verified(raw_body) ⇒ shop_header == the_shop_that_actually_produced(raw_body)` — does not hold. An unprivileged internet user who runs their own Shopify dev store using the vulnerable app receives genuinely HMAC-signed webhook payloads for their own store's data (a normal, unprivileged capability granted to any app installer). Since the HMAC only signs the body and not the `shop-domain` header, that user can replay the exact same body+HMAC to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. `Registry.process` will accept the HMAC (it matches the unmodified body) and dispatch the payload to the handler tagged with the attacker-chosen `shop`, rather than the shop that actually generated it.

### Impact Explanation
This is a cross-tenant identity-confusion primitive: a value used by the host application to select the tenant record to update/act on (via `WebhookMetadata#shop`) is fully attacker-controlled while the surrounding authenticity check (HMAC) never covers it. Depending on how a consuming app processes webhooks (e.g., updating orders/inventory/customer data keyed by `shop`), this allows an attacker who legitimately installed the app on their own store to inject data that is attributed to and processed under a different merchant's tenant — a cross-tenant access impact.

### Likelihood Explanation
Any developer/attacker can install the app on a free Shopify dev/trial store, causing Shopify to fire real, validly-signed webhooks to the app's endpoint. Because `Registry.process` verifies only `raw_body` via HMAC and independently trusts the `shop-domain` header, replaying the captured request with a modified header is a simple, deterministic HTTP replay — no cryptographic material needs to be forged. Exploitability is high for any host application that keys writes solely by `WebhookMetadata#shop`.

### Recommendation
Bind the trusted `shop` value to the signed material, or independently verify it against Shopify's identity for the signed payload — e.g., include `shop` (and `topic`/`webhook_id`) within the HMAC-signed string, or reject/flag requests where the header-derived shop cannot be corroborated by a second authenticated source. At minimum, document that consuming applications must not rely on `WebhookMetadata#shop` as a trusted tenant key without additional verification (e.g., cross-checking against a known installed-shop list tied to the currently active session/access token for that shop).

### Proof of Concept
1. Attacker installs the vulnerable app on their own store `attacker.myshopify.com`.
2. Shopify sends a legitimate webhook: body `B`, headers `shopify-hmac-sha256: HMAC(secret, B)`, `shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays the exact same body `B` and HMAC header to the app's webhook endpoint, but sets `shopify-shop-domain: victim.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `to_signable_string` (`= B`) against the unchanged HMAC: [5](#0-4) 
5. `Registry.process` dispatches `WebhookMetadata.new(shop: "victim.myshopify.com", body: parsed_body, ...)` to the handler, which processes attacker-controlled data under the victim's tenant identity: [6](#0-5)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
