## Title
Webhook HMAC does not bind the `shop`/`topic`/`webhook-id` identity, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while `shop`, `topic`, `api_version`, and `webhook_id` are read directly from unauthenticated HTTP headers. `Webhooks::Registry.process` treats a passing HMAC check as proof that the whole webhook—including the shop identity—is authentic, and hands `request.shop` straight to the app's handler as the tenant identifier. Because Shopify signs webhooks with the single, app-wide `api_secret_key` (the same secret is used for every shop that installs the app), any merchant who installs the app can obtain a body+HMAC pair that is valid for *any* other shop, by simply changing the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header before replaying the request.

### Finding Description
The HMAC verification path is:
```ruby
# lib/shopify_api/webhooks/request.rb
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [1](#0-0) 

```ruby
sig { returns(String) }
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [2](#0-1) 

`Utils::HmacValidator.validate` only compares the HMAC over `verifiable_query.to_signable_string`, i.e. the raw body: [3](#0-2) 

`Registry.process` uses this passing check to authorize dispatch and forwards the unauthenticated `shop` header on to the handler:
```ruby
def process(request)
  raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
  handler = @registry[request.topic]&.handler
  ...
  handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
    body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
end
``` [4](#0-3) 

The identity binding that should hold is:
`shop_that_the_signature_authenticates == shop_delivered_to_the_handler`

Because the signature covers only the body bytes, this equality does not hold: `hmac_valid(body)` is independent of the `shop-domain`/`topic`/`webhook-id` headers. Since Shopify apps use one shared `api_secret_key` across all installing shops, a merchant who installs the app on their own store can legitimately receive real webhook deliveries (valid body + valid HMAC signed with the app's shared secret). That attacker can then replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header (and optionally `X-Shopify-Topic`) with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` dispatches the handler with `WebhookMetadata#shop` set to the victim's domain, even though the payload was never produced by or for that shop.

### Impact Explanation
This breaks the shop/tenant identity binding at the core of the webhook trust model, letting one merchant (an "unprivileged" caller with respect to other tenants) inject attacker-controlled webhook payloads that appear to originate from a different shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to key per-shop data lookups, uninstall/deauthorize flows, GDPR redact-request handling, billing status changes), this is a cross-tenant data integrity/exfiltration vector — one of the explicit Critical-impact categories (cross-tenant access).

### Likelihood Explanation
The prerequisite is only that the attacker be a legitimate merchant of the same app (a normal, unprivileged install), which is trivial to obtain for any public Shopify app. No access to `api_secret_key`, TLS interception, or a privileged account is required — the attacker only needs their own genuine webhook deliveries, which they receive as part of ordinary app usage, and control over headers when replaying the HTTP request to the app's webhook endpoint.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is HMAC-verified, or otherwise require the host application to positively re-validate `request.shop` against a value it independently trusts (e.g., cross-check against the specific shop's session/store before using it), and document that `Webhooks::Request#shop`/`#topic`/`#webhook_id` are NOT authenticated by `HmacValidator.validate` — only the body is. Ideally, extend `to_signable_string` (or add a companion check) so that the shop domain header is included in what's verified, or require callers to match `request.shop` to the shop context under which they expect the specific `webhook_id`/subscription to be registered.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`, obtaining valid webhook deliveries signed with the app's shared `api_secret_key`, e.g. topic `customers/create` with body `B` and header `X-Shopify-Hmac-Sha256: H` (valid for `B`).
2. Attacker sends an HTTP request to the victim app's webhook endpoint with the same raw body `B` and same `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body` — validation succeeds. [5](#0-4) 
4. The handler is invoked with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, i.e., attacker-controlled body content is processed under the victim's shop identity. [6](#0-5)
