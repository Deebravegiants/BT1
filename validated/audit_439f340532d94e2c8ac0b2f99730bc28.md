### Title
Fee-on-transfer / non-standard ERC20 tokens cause XCM holding over-crediting in `ERC20Transactor` - (File: `cumulus/parachains/runtimes/assets/common/src/erc20_transactor.rs`)

### Summary
`ERC20Transactor::withdraw_asset_with_surplus` calls the ERC20 contract's `transfer()` and, upon a truthy boolean return, unconditionally credits the XCM holding with the **nominal requested `amount`** rather than the amount actually received by the `TransfersCheckingAccount`. This is structurally the same root cause as the reported ZKsync issue: trusting the requested/declared amount instead of verifying the actual balance delta after an external token transfer call.

### Finding Description
In `withdraw_asset_with_surplus` [1](#0-0) , the code:
1. Calls `IERC20::transferCall` for `amount` from the user to `TransfersCheckingAccount`.
2. On `is_success == true`, immediately constructs `AssetsInHolding::new_from_fungible_credit(what.id.clone(), Box::new(Erc20Credit(amount)))` — crediting the full declared `amount` into the XCM executor's holding register, without ever reading the ERC20 contract's `balanceOf(checking_account)` before/after the call to confirm the checking account actually received `amount`.

The `ERC20Matcher` type used by this transactor matches **any** local `AccountKey20` location [2](#0-1) , i.e. any contract address, not a permissioned allow-list of vetted tokens. `ERC20Transactor` is included in the live `AssetTransactors` tuple on Asset Hub Westend [3](#0-2) , and per the introducing PR doc, this is intended precisely so "asset ids of the form `{parents: 0, interior: X1(AccountKey20{key})}}` will be matched ... and the corresponding `transfer` function will be called in the smart contract whose address is `key`" [4](#0-3) . Any unprivileged user can deploy an arbitrary `pallet-revive` contract implementing a fee-on-transfer/deflationary `transfer()` (returning `true` while moving less than `amount`), then reference that contract's address in an XCM `WithdrawAsset`/reserve-transfer instruction.

Because the credited `Erc20Credit(amount)` in the XCM holding register is decoupled from the checking account's real ERC20 balance, any downstream use of that holding (e.g. `DepositAsset` to another account, cross-chain reserve transfer, or `ExchangeAsset`) treats phantom, unbacked balance as real. Symmetrically, `deposit_asset_with_surplus` [5](#0-4)  instructs the checking account to pay out the full nominal `amount` to a beneficiary without verifying the beneficiary's balance actually increased by `amount` (again vulnerable to fee-on-transfer draining the checking account faster than it was topped up), which can lead to the checking account being unable to back all outstanding credited holdings — an insolvency exactly analogous to the ZKsync `L1NativeTokenVault` bug.

### Impact Explanation
An unprivileged user can create fictitious ERC20 asset balances in the XCM system for a token they control, which the executor and any consuming logic (deposit to other accounts, reserve/pool operations, cross-chain transfers) treat as genuine. Repeated operations can also drain/desynchronize the shared `TransfersCheckingAccount`'s actual on-chain ERC20 balance relative to what the runtime believes is custodied, potentially causing later legitimate withdrawals for other holders of the same asset to fail or under/over pay. This is an accounting-integrity bug in a component explicitly designed to bridge arbitrary user-deployed ERC20 contracts into XCM.

### Likelihood Explanation
High for user-deployed contracts: `ERC20Matcher` places no restriction on which contract addresses are eligible — any `pallet-revive` contract address qualifies as an XCM-referenceable asset by construction [2](#0-1) . No admin registration or allow-listing step is evident from the transactor logic itself (it is a generic `MatchesFungibles` on the location shape, not an asset registry lookup). An attacker only needs to (a) deploy a contract with a `transfer()` that deducts a fee/burns part of the amount but still returns `true`, and (b) issue a standard XCM program (e.g. via `pallet_xcm::execute`/`transfer_assets`) referencing that contract as the asset.

### Recommendation
In `ERC20Transactor::withdraw_asset_with_surplus`, read the checking account's `balanceOf` immediately before and after the `transfer` call and credit `Erc20Credit` with the **actual observed delta**, not the requested `amount`; revert/error if the delta is less than requested (mirroring the ZKsync PoC's fix of checking `balanceAfter - balanceBefore == depositAmount`). Apply the same before/after balance check in `deposit_asset_with_surplus` for the beneficiary account before treating the deposit as fully successful, or explicitly document/enforce (via a curated `Matcher`/allow-list) that only vetted, standard-conforming ERC20 contracts (no fee-on-transfer, no rebasing) may be used with this transactor.

### Proof of Concept
1. Deploy a `pallet-revive` Solidity contract `FeeERC20` whose `transfer(to, amount)` burns `amount/10` and moves `amount - amount/10` to `to`, but still returns `true`.
2. Mint the attacker some `FeeERC20` balance.
3. Submit an XCM program via `pallet_xcm::execute`/`transfer_assets` with `WithdrawAsset` for asset `{parents:0, interior: AccountKey20{key: FeeERC20_address}}` and amount `A`.
4. Observe: `ERC20Transactor::withdraw_asset_with_surplus` returns `AssetsInHolding` credited with the full `A`, even though `TransfersCheckingAccount`'s real `FeeERC20` balance only increased by `A - A/10`.
5. Follow with `DepositAsset` to a beneficiary for the full `A` (or a cross-chain reserve transfer for `A`) — the beneficiary/destination is credited `A` units of an asset the checking account does not fully hold, demonstrating the accounting mismatch (exact reproduction requires wiring this up in `cumulus/parachains/runtimes/assets/asset-hub-westend` test harness with `pallet-revive` contract fixtures, analogous to `substrate/frame/revive/fixtures/contracts/external/openzeppelin/contracts/token/ERC20/ERC20.sol` as a base to modify).

Note: I was not able to fully verify at what other layers (e.g. asset registration/governance controls) might further restrict which ERC20 contracts can actually be referenced in production XCM configs for Asset Hub — the matcher itself imposes no such restriction, but if there is an additional out-of-band asset allow-listing enforced elsewhere in the runtime (not found in this scan), likelihood could be lower than assessed above.
