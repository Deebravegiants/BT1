### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented as verifying "the request did indeed come from Shopify" before handing off `shop`, `topic`, `webhook_id`, and `body` to the app's handler. In reality, the HMAC signature computed by `Utils::HmacValidator` only covers the raw request body — the `shop-domain` header that the gem hands to the app as the authenticated tenant identity is never part of the signed content.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) [2](#0-1) 

`to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from HTTP headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) and are never mixed into the signed string.

`Registry.process` validates only the body via HMAC and then trusts the header-derived `shop` value to build `WebhookMetadata`, which is handed to the app-defined handler as the authenticated tenant for that event: [3](#0-2) 

`WebhookMetadata.shop` is a plain `String` field with no cryptographic binding to the HMAC: [4](#0-3) 

The documentation for `Registry.process` explicitly claims the call "will verify the request did indeed come from Shopify": [5](#0-4) 

This is the breaking equality from the report's bug class: `shop authenticated` (the value host apps are told is verified and act on, `WebhookMetadata#shop`) ≠ `shop covered by HMAC` (empty — the signable string is only `@raw_body`). Any attacker who can obtain one genuine `(raw_body, hmac)` pair signed with the app's `api_secret_key` — trivially available to them if they are a merchant who installed the app and received a real webhook to their own endpoint — can replay that exact body+hmac to the app's public webhook endpoint while substituting the `shop-domain` (and `topic`/`webhook_id`/`api_version`) headers for a different, victim shop. `HmacValidator.validate` still passes because it only checks the (unmodified) body against the (unmodified) hmac: [6](#0-5) 

The app then processes attacker-supplied data believing it originated from the victim shop.

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged internet user who is merely one of the app's own (potentially malicious) installed merchants can forge webhook deliveries that appear, to the app's business logic, to originate from a different, arbitrary shop. Depending on the topic (e.g. `app/uninstalled`, `customers/data_request`, `shop/update`, `orders/*`), this can trigger data deletion, GDPR flows, entitlement changes, or state corruption for a shop the attacker does not control — no access token, `client_secret`, or TLS interception is required, since the exploit only needs one legitimately-received webhook (body+hmac pair) that the attacker replays with altered headers to the app's own public endpoint.

### Likelihood Explanation
Any app using webhooks is affected, since this is the core `shopify_api` verification path documented and used by every consumer. The prerequisite — being an installed merchant who receives at least one real webhook to inspect (or simply capturing their own webhook payload/HMAC from their own endpoint logs) — is trivial to satisfy for any attacker with a free development/trial store, and the header-forging replay requires no special access beyond making an HTTP POST to the app's own public webhook route.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or independently authenticate the shop identity before trusting it — e.g., cross-check the header-derived shop against a shop already known to have a valid, stored offline session/webhook subscription for that specific `webhook_id`, and/or include the shop domain as part of the signable string used in `Request#to_signable_string`/`HmacValidator` so that tampering with the `shop-domain` header invalidates the signature.

### Proof of Concept
1. App exposes `POST /callback/webhook` which calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body:, headers:))` exactly as documented.
2. Attacker installs the app on `attacker-shop.myshopify.com` and lets Shopify deliver one real webhook to the app; attacker captures the exact `raw_body` and `x-shopify-hmac-sha256` value from their own request logs (their own shop, no secret access needed).
3. Attacker sends a new POST to the same `/callback/webhook` route with:
   - the identical `raw_body` and `x-shopify-hmac-sha256` captured above,
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (arbitrary victim shop),
   - `x-shopify-topic`/`x-shopify-webhook-id` optionally changed.
4. `HmacValidator.validate` succeeds because it only checks `raw_body` against the reused hmac. `Registry.process` invokes the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to act as if the event came from the victim shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
