### Title
Duplicate `address(0)` entries in `erc20TokenAddresses` let a single `msg.value` deposit satisfy the balance equation twice, minting unbacked shielded ETH - (File: contracts/Hinkal.sol)

### Finding Description
The claimed broken equality is:

`msg.value backing == exactly one accounting term (amountChanges[i] + utxoAmount[i]) in the balance loop`

but if `erc20TokenAddresses` contains `address(0)` at two indices `i1` and `i2`, the loop in `Hinkal.transact` at [1](#0-0)  computes `balanceDif` identically for both indices, since `newBalances[i1]==newBalances[i2]` and `oldBalances[i1]==oldBalances[i2]` (both read `address(this).balance` at the same moment) and `msg.value` is added back identically each time. `oldBalances` is read at [2](#0-1)  *after* `msg.value` has already been credited to `address(this).balance` (payable-call semantics), so the `+ int256(msg.value)` term reintroduces the same deposited ETH into the equation a second time when the address is repeated.

The per-index requirement at [3](#0-2)  is evaluated independently for `i1` and `i2`:
`balanceDif == amountChanges[i] + utxoAmount[i]`

If no on-chain UTXO of `address(0)` is produced (`utxoAmount=0` for both, e.g. because the external action's ETH balance is untouched, or simply via the internal path `externalActionId==0`), both checks reduce to `msg.value == amountChanges[i1]` and `msg.value == amountChanges[i2]`. Both are individually satisfiable with `amountChanges[i1] = amountChanges[i2] = msg.value`, since nothing forces `erc20TokenAddresses` entries to be distinct — no dedup check exists in `dimensionsCheck` at [4](#0-3)  nor in `checkOnchainCreation`.

Even in the pure internal path, `_internalTransact` at [5](#0-4)  calls `transferERC20TokenFromOrCheckETH(address(0), ..., address(this), amountChanges[i])` for each duplicated index, which for ETH only asserts `msg.value == _value` (via [6](#0-5)  ) and performs no actual transfer since `_to == address(this)`. Calling this twice for `i1` and `i2` is consistent as long as `amountChanges[i1] == amountChanges[i2] == msg.value` — it never detects that the same ETH is being claimed twice.

Once both per-index requires pass, `amountChanges[i1]` and `amountChanges[i2]` are each independently constrained by the ZK circuit's `inTotal[i] + amountChanges[i] === outTotal[i]` relation per array slot (in `MainEVMCircuit.circom`), which treats each array index as an independent token slot and has no cross-index check that two slots referencing the same `erc20TokenAddresses[i] == address(0)` aren't both crediting new value from the same deposit. This lets the prover legitimately create two separate valid off-chain output commitments, each carrying `amountChanges = msg.value` worth of new shielded ETH, from a single real ETH deposit.

For the Emporium/LiFi-swap variant described in the question: if the attacker's external action doesn't move Emporium's own ETH balance (`balancesBefore[i]==balancesAfter[i]` for both duplicated indices in `EmporiumUpgradeable.runAction` at [7](#0-6) ), `handleOut` returns an empty UTXO for both (`balanceChange<=0` branch at [8](#0-7) ), so `utxoSet` contains no `address(0)` entries and the Hinkal-side `onChainCommitments` array bound is never exceeded — avoiding the out-of-bounds revert that *would* occur if both duplicated indices matched real UTXO entries in `utxoSet` (since `onChainCommitments` is sized to `utxoSet.length` and the inner match loop at [9](#0-8)  would attempt to write past that array when the same UTXO is matched by two duplicate indices).

None of `performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, or the `slippageValues`/balance requires reject duplicate `address(0)` entries or a repeated `msg.value` credit — they check array-length equality and per-index positivity, not cross-index token-address uniqueness.

### Impact Explanation
A single ETH deposit of value `V` can back two independent off-chain shielded UTXOs each worth `V`, doubling the shielded ETH supply relative to actual backing. This directly matches "minting shielded value without backing" (Critical, protocol insolvency), since redeeming both resulting UTXOs later would let the attacker withdraw `2V` in real ETH while only ever having deposited `V`, draining the pool's balance backing other users' funds. The attack is repeatable per transaction and scales linearly with the number of duplicate `address(0)` entries an attacker includes (limited only by `dimensions.tokenNumber`).

### Likelihood Explanation
The attacker needs no privileged role — only a valid ZK proof for a `CircomData` struct they fully control, including `erc20TokenAddresses` with `address(0)` repeated and `amountChanges` set consistently to `msg.value` at each repeated slot. This is achievable purely through the internal transact path with `externalActionId == 0` (no external action or router interaction required at all), making it low-cost and highly feasible; the LiFi/Emporium framing in the question is only one of several vectors, and not even the most direct one.

### Recommendation
In `Hinkal.transact`, before the balance-equation loop, enforce that `erc20TokenAddresses` entries are unique (e.g., require strictly increasing/sorted order, or explicit duplicate-detection), so `msg.value` (and any other balance delta) can only be attributed to a single index. Alternatively, compute the `msg.value` correction once globally (not per-index) and apply it to only the first occurrence of `address(0)`, or restructure the loop to operate over a deduplicated token set with per-token aggregated `amountChanges`.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, and a valid `Verifier` (or mocked verifier returning true) with `MockCircuit` dimension `tokenNumber = 2`.
2. Build `CircomData` with `erc20TokenAddresses = [address(0), address(0)]`, `amountChanges = [V, V]`, `onChainCreation = [false, false]`, `slippageValues = [0, 0]`, `externalActionData.externalActionId = 0` (internal path), valid `inputNullifiers`/`outCommitments` matching a locally generated proof satisfying `inTotal[i] + amountChanges[i] === outTotal[i]` for each `i`.
3. Call `hinkal.transact{value: V}(a, b, c, dimensions, circomData)`.
4. Assert: (a) `address(hinkal).balance` increased by exactly `V`; (b) two output commitments were inserted (`outCommitments[0]` and `outCommitments[1]`), each encoding value `V`; (c) sum of minted shielded UTXO value (`2V`) exceeds the actual ETH balance delta of Hinkal (`V`), proving unbacked minting.
5. Confirm the transaction does not revert on any of `performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, or the balance-equation requires.
