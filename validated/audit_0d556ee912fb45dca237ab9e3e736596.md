### Title
Predictable, unsigned session-id used as the non-embedded session cookie value enables cross-tenant session/token hijacking - (File: `lib/shopify_api/auth/oauth.rb`, `lib/shopify_api/utils/session_utils.rb`)

### Summary
For non-embedded apps, `ShopifyAPI::Auth::Oauth.validate_auth_callback` sets the browser's session cookie to the raw, deterministic `session.id` string (e.g. `"offline_{shop}"`), and `ShopifyAPI::Utils::SessionUtils.cookie_session_id` later trusts that exact cookie value, unvalidated, as the lookup key for the stored session/access token. Because the session id carries no entropy and is fully derivable from public information (the shop's domain), any unprivileged user can set this cookie themselves to a *different, victim* shop's id and have the host application's session repository (built exactly as this gem's own documentation instructs) hand back that victim shop's access token.

### Finding Description
In the authorization-code-grant flow, once the OAuth callback completes, the gem builds the browser cookie like this: [1](#0-0) 

For non-embedded apps the cookie `value` is literally `session.id`, and that id is a deterministic, guessable string built only from the shop domain (and user id for online sessions): [2](#0-1) 

Retrieval works the same way in reverse — the raw cookie bytes are returned unchanged as the "session id", with no signature check, no binding to the browser/OAuth transaction that created it, and no re-verification against Shopify: [3](#0-2) [4](#0-3) 

The gem's own documentation instructs host apps to persist and retrieve sessions purely by this id (`MyApp::SessionRepository.store_session(auth_result[:session])`, later `SessionRepository.retrieve_session_for_shop(shop)`), i.e. the session id is meant to double as the lookup key for the stored access token.

Contrast this with the actual OAuth `state` nonce, which *is* random and unguessable: [5](#0-4) 

The identity binding broken here is: `cookie value received == session id belonging to the current authenticated browser`. In reality, `cookie value received == any string the client chooses to send`, and because `offline_session_id(shop)` / `jwt_session_id(shop, user_id)` are pure deterministic functions of public data (myshopify domain names are public), an attacker's own unauthenticated browser can present `offline_{victim-shop}.myshopify.com` as its cookie and satisfy every check the gem performs (`cookie_session_id` simply echoes it back as valid).

### Impact Explanation
This crosses a tenant boundary: an attacker who has never installed the app and possesses only the victim shop's public myshopify domain can cause the host application (following this gem's documented pattern) to load and use the victim shop's stored access token for the attacker's own requests, i.e. cross-tenant access to Shopify Admin API data/functionality via another merchant's credentials.

### Likelihood Explanation
No secret material, access token, TLS interception, or privileged position is required — only the ability to set an arbitrary cookie value in one's own browser (trivial) and knowledge of a target shop's domain (public). The only mitigating factor is that this depends on the host application implementing session storage/retrieval exactly as this gem documents (id-only lookup with no additional binding), which is the pattern this gem's own docs recommend.

### Recommendation
- Do not use a deterministic, publicly-derivable string as the session cookie value/lookup key. Generate a separate random, unguessable session token for the cookie and store the actual `shop`/`access_token` behind that random token server-side, or HMAC-sign the cookie value with `api_secret_key` and verify the signature in `SessionUtils.cookie_session_id`/`current_session_id` before trusting it.
- At minimum, document loudly that `session.id` must never be treated as a secret/bearer value and that host applications must not use the raw cookie value as an unauthenticated database lookup key without an additional integrity check.

### Proof of Concept
1. App installs for `victim-shop.myshopify.com`; per the gem's documented flow, the host app persists a `Session` keyed by `session.id == "offline_victim-shop.myshopify.com"` and sets the same value as the (non-embedded) `SESSION_COOKIE_NAME` cookie, per [1](#0-0) .
2. Attacker, using their own unauthenticated browser (no cookie ever issued to them for this app), manually sets a cookie `SESSION_COOKIE_NAME=offline_victim-shop.myshopify.com`.
3. Attacker calls an app endpoint that resolves the current session via `ShopifyAPI::Utils::SessionUtils.current_session_id(nil, cookies, false)`, which returns `cookie_session_id(cookies)` unchanged: [6](#0-5) .
4. The host app's `SessionRepository.retrieve_session_for_shop`/`retrieve(id)`-style lookup (as shown in the gem's own docs/breaking-change notes) returns the victim's stored `Session`, including `access_token`, letting the attacker's request use the victim shop's credentials.
