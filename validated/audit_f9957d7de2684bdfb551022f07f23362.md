### Title
Unset/misconfigured CallDispatcher silently no-ops calldata execution in HyperFungibleToken's onAccept, permanently stranding bridged funds - (File: `sdk/packages/core/contracts/apps/HyperFungibleToken.sol`)

### Summary
`HyperFungibleToken.onAccept` (and the same pattern in `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, and `WrappedHyperFungibleTokenUpgradeable`) executes composable destination calldata via `ICallDispatcher(_dispatcher).dispatch(message.data)` whenever `message.data.length > 0`. `_dispatcher` is never validated to be non-zero in `configure()`, and because `dispatch()` returns nothing, Solidity's compiler-inserted `EXTCODESIZE` safety check for external calls (which only fires when a return value must be ABI-decoded) is skipped. A call to `ICallDispatcher(address(0)).dispatch(...)` therefore succeeds silently as a no-op instead of reverting, exactly mirroring the FeeBuyback pattern where a low-level call to an unchecked zero address "succeeds" without doing anything.

### Finding Description
`configure()` sets `_dispatcher` from caller-supplied `options.dispatcher` with no zero-address check: [1](#0-0) 

`onAccept` unconditionally mints to the beneficiary and then forwards calldata to whatever `_dispatcher` currently holds, without checking it is non-zero or has code: [2](#0-1) 

The documented composable pattern (transfer-and-swap, transfer-and-stake, transfer-and-deposit) requires the sender to set `to` (the mint recipient) to the `CallDispatcher` address itself, so the dispatcher can spend the freshly minted tokens: [3](#0-2) 

If `_dispatcher` is zero — either because `configure()` was called with `dispatcher: address(0)` (owner mistake/misconfiguration) or because the destination-chain deployment has not yet had `configure()` called with a live dispatcher while the source-chain `send()` is already reachable by users — then:
1. `_mint(beneficiary, message.amount)` still succeeds, crediting tokens to the address the sender designated as the `CallDispatcher` (per the documented pattern).
2. `ICallDispatcher(_dispatcher).dispatch(message.data)` is a call with no return type, so Solidity does not insert the `EXTCODESIZE` check normally added for interface calls that decode return data; the call to the zero address (an "empty account") returns success trivially.
3. `onAccept` completes normally and emits `Received` as if the composable execution succeeded.

The real `CallDispatcher.sol` implementation used elsewhere does check `extcodesize` and reverts with `NotContract`, but that check lives inside the dispatcher contract itself — it never runs here because the call never reaches a real dispatcher when `_dispatcher == address(0)`: [4](#0-3) 

Since the tokens were minted to the intended `CallDispatcher` address (a real, ordinary contract address chosen by the sender/off-chain tooling) rather than to `address(0)`, and `CallDispatcher.sol` exposes only `dispatch()` and a payable `receive()` — no sweep/rescue/withdraw function — any tokens or native value that land there without the accompanying `dispatch()` call actually executing become permanently unrecoverable. Because `onAccept` did not revert, the ISMP request is marked delivered (a receipt is written), so there is no timeout path back to the sender for a refund.

### Impact Explanation
This is a direct, unprivileged-user-reachable fund-freezing bug: any user (not a privileged/admin actor) can trigger it simply by calling `send()` with a non-empty `data` payload targeting a chain whose `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment currently has `_dispatcher == address(0)` (fresh deployment before `configure()`, or after an owner reconfiguration that zeroes/omits the dispatcher). The bridged principal is minted to the designated `CallDispatcher` address but the intended swap/stake/deposit calldata silently never executes, and because `CallDispatcher.sol` has no withdrawal mechanism, the funds are stuck there permanently. This satisfies "permanent freezing of funds" from a single dispatched cross-chain transfer.

### Likelihood Explanation
Likelihood is meaningful rather than purely theoretical: `configure()` is the only gate wiring `_dispatcher`, is called separately from chain-registration (`addChain`), and nothing in the on-chain code prevents `send()` with composable `data` from being quoted/dispatched cross-chain to a destination deployment whose dispatcher has not yet been configured, or has been reconfigured to zero. The bug requires no malicious admin action — it is triggered purely by an ordinary user constructing a `SendParams.data` payload (as explicitly instructed by the project's own documentation) against a destination in this state.

### Recommendation
- Require `options.dispatcher != address(0)` in `configure()` for `HyperFungibleToken`, `HyperFungibleTokenUpgradeable`, `WrappedHyperFungibleToken`, and `WrappedHyperFungibleTokenUpgradeable`.
- In `onAccept`, before calling `ICallDispatcher(_dispatcher).dispatch(...)`, explicitly check `_dispatcher != address(0)` (and/or `_dispatcher.code.length > 0`) and revert if the calldata cannot actually be executed, rather than silently minting and continuing. This restores the fail-closed behavior that `CallDispatcher.sol`'s own `NotContract` check provides for the sub-calls inside `dispatch()`, but currently cannot provide when the top-level call itself target a non-contract address.

### Proof of Concept
1. Deploy `HyperFungibleToken` and call `configure({host: HOST, dispatcher: address(0)})` (either the initial default before any `configure` call, or an owner who passes a zero dispatcher by mistake/misconfiguration).
2. From a source chain, a user calls `send({dest: DEST, to: abi.encodePacked(CALL_DISPATCHER_ADDR), amount: A, data: abi.encode(swapCalls)})` per the documented transfer-and-swap pattern, where `CALL_DISPATCHER_ADDR` is the real (but not yet wired-in) CallDispatcher address on `DEST`.
3. On `DEST`, the relayer delivers the POST request; `onAccept` runs, mints `A` tokens to `CALL_DISPATCHER_ADDR`, then calls `ICallDispatcher(address(0)).dispatch(message.data)`. This call returns `success` with no code executed (no `EXTCODESIZE` check emitted because `dispatch()` has no return value).
4. `onAccept` completes without reverting; `Received` is emitted; the ISMP request is recorded as delivered (no timeout/refund path).
5. The `A` tokens sit in the real `CallDispatcher` contract at `CALL_DISPATCHER_ADDR`, which has no `withdraw`/sweep function — they are permanently unrecoverable.

```text
    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
```

```text
## Calldata Execution

Both contracts support optional calldata execution on the destination chain via the `CallDispatcher`. By passing a non-empty `data` field in `SendParams`, the sender can trigger arbitrary contract calls on the destination chain immediately after tokens are minted or unlocked. This enables composable cross-chain workflows like transfer-and-swap (e.g., bridge USDC then swap to WETH via UniswapV2), transfer-and-stake, or transfer-and-deposit into a lending protocol — all in a single cross-chain operation.

The `data` field is an ABI-encoded `Call[]` array, where each `Call` specifies a target contract, a native value to forward, and the calldata to execute. On the destination chain, the HFT contract mints or unlocks tokens to the `to` address, then forwards the entire `data` payload to the `CallDispatcher`, which executes each call sequentially. If the calls need to spend the bridged tokens (e.g., approve then swap), set `to` to the `CallDispatcher` address so tokens are delivered directly to it.

For code examples, see the [HyperFungibleToken](/developers/evm/hyper-fungible-token/hyper-fungible-token#calldata-execution) and [WrappedHyperFungibleToken](/developers/evm/hyper-fungible-token/wrapped-hyper-fungible-token#calldata-execution) pages.

### Security

The `CallDispatcher` executes calls in its own context (not via `delegatecall`), so the HFT contract's storage is never at risk. If any call in the array reverts, the entire `onAccept` handler reverts — including the token mint/unlock. The request can then be retried by any relayer until the timeout expires. If no successful execution occurs before the timeout, the request times out and the sender is eligible for a refund on the source chain. Token approvals in the `Call[]` should use exact amounts rather than unlimited allowances, since the dispatcher contract holds tokens temporarily during execution.
```

```text
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }
```
