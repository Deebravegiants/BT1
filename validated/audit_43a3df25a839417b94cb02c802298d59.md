### Title
Webhook Shop/Topic Identity Not Covered by HMAC, With Independent Legacy/New Header Fallback Enabling Cross-Tenant Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body with the app's HMAC secret, while the tenant-identifying `shop`, `topic`, `webhook-id` and `api-version` values are read straight from HTTP headers that are not part of the signed payload. Because the webhook HMAC secret (`Context.api_secret_key`) is shared by every shop that installs the app, any unprivileged attacker who installs the app on their own (even free/dev) store can obtain one genuinely HMAC-valid webhook and then re-attribute it to an arbitrary victim shop by manipulating only the unsigned header, which the library trusts unconditionally as the source-of-truth "shop" identity passed to the app's webhook handler.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` therefore only ever proves that the *body bytes* were signed with the app secret — it says nothing about `shop`, `topic`, `webhook-id`, or `api-version`: [2](#0-1) 

Yet `Registry.process` uses the unauthenticated `request.shop` value directly to build the `WebhookMetadata` handed to the app's handler, with no independent check that the shop is bound to the signed content: [3](#0-2) 

`Request#shop`/`#topic`/`#webhook_id`/`#api_version` each independently resolve via `shopify_header`, which prefers the new `shopify-*` header over the legacy `x-shopify-*` header **on a per-field basis**: [4](#0-3) [5](#0-4) 

This per-field, dual-format lookup (introduced to support both header naming schemes, confirmed by the changelog entry and tests exercising both formats simultaneously) means the fields that determine *which shop the webhook is attributed to* are decoupled from the field that is actually authenticated (the body). An attacker who is a legitimate (unprivileged) installer of the app on their own store can capture one genuine, HMAC-valid webhook body/signature pair addressed to their own shop, then attach an additional `shopify-shop-domain` (or `shopify-topic`) header naming a different shop/topic — this passes `Utils::HmacValidator.validate` untouched (body unchanged) while `request.shop` now yields the attacker-chosen victim domain to the handler.

### Impact Explanation
This breaks the intended equality `authenticated_signer_identity == shop_passed_to_handler`. If a host application uses `WebhookMetadata#shop` from the gem to identify which merchant a webhook event pertains to (the documented and expected usage pattern, e.g. to look up that merchant's stored session/access token or write merchant-scoped data), an attacker can cause the app to process attacker-controlled webhook data under an arbitrary victim shop's identity — a cross-tenant identity confusion inside this gem's own webhook-authentication code path, not merely host-application misuse of an unrelated feature.

### Likelihood Explanation
Reachable by any unprivileged internet user: installing a public Shopify app on a free/development store is unprivileged, and once installed the attacker legitimately receives real webhooks (with valid HMAC, since the client secret is shared across all installs of the app) that they can replay to the app's public webhook endpoint with additional/adjusted headers. No access token, `client_secret`, or privileged account is required — only the ability to install the app once.

### Recommendation
- Bind the header-derived identity fields (`shop`, `topic`, `webhook-id`, `api-version`) into the HMAC-signed payload (or otherwise cryptographically bind them), rather than trusting raw headers independently of the signature.
- Collapse the legacy/new header lookup so that once one header name is chosen for a request, the same naming convention is used consistently for all fields, rejecting requests that mix formats for different fields.
- Document/enforce that host applications must additionally verify the resolved `shop` corresponds to an existing, previously-installed session before acting on webhook content, since the gem cannot itself guarantee shop authenticity from headers alone.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com`; app registers a webhook (e.g. `orders/create`).
2. Attacker triggers the webhook, capturing the real POST: body `B`, and legitimate `x-shopify-hmac-sha256: H` (valid because `H = HMAC(secret, B)`, `secret` shared by all installs), along with `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker re-sends this exact request to the app's public webhook endpoint but adds `shopify-shop-domain: victim.myshopify.com` (new-format header) while leaving `x-shopify-hmac-sha256` as the only HMAC header present.
4. `Utils::HmacValidator.validate` succeeds (body `B` is unchanged, `to_signable_string` only covers `B`) — see [1](#0-0) .
5. `Request#shop` resolves to `"victim.myshopify.com"` because `shopify_header("shop-domain")` prefers the new-format header — see [4](#0-3) .
6. `Registry.process` dispatches the handler with `WebhookMetadata` attributing attacker-controlled body `B` to `victim.myshopify.com` — see [3](#0-2) .
