## Title
Webhook shop/topic/webhook-id identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs and verifies only the raw request body against the `X-Shopify-Hmac-Sha256` header, while the `shop`, `topic`, `api_version`, and `webhook_id` values — all of which are read from unauthenticated HTTP headers — are handed unchanged to the app's webhook handler via `WebhookMetadata`. The binding "HMAC-verified bytes == the tenant-identifying fields acted upon" does not hold: the signature covers the body only, not the header-derived `shop` field that the host application uses to route/process the webhook per tenant.

### Finding Description
`Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)`: [1](#0-0) 

The HMAC check in `HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns **only the raw body** — none of the identity-bearing headers are part of the signed material: [3](#0-2) 

Yet `shop`, `topic`, `api_version`, and `webhook_id` are all read straight from attacker-visible/attacker-settable HTTP headers with no cryptographic binding to the body that was actually signed: [4](#0-3) 

After HMAC validation passes, these unauthenticated header values are forwarded verbatim to the registered handler: [5](#0-4) 

This is a direct analog of the reported bug class: the code checks that *some* bytes are authentic (the body/HMAC pair), but then acts on a different, unauthenticated field (the shop identity) as if it had been verified together with those bytes — exactly like Illuminate checking one balance while transferring funds tied to a different identity.

### Impact Explanation
Any party that can obtain one legitimately-HMAC-signed `(raw_body, hmac)` pair for the app (e.g., a merchant who has installed the app and receives their own genuine Shopify webhooks) can replay that exact body and HMAC to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`, `X-Shopify-Webhook-Id`) header for a different, victim shop. Because the signature never covered these headers, `HmacValidator.validate` still returns `true`, and the handler receives a `WebhookMetadata` claiming the payload originated from the victim shop. Any host application that uses `WebhookMetadata#shop` to select the tenant record/session to update (the standard pattern for processing `orders/*`, `customers/*`, `shop/redact`, etc.) will apply the attacker's payload to another merchant's data — a cross-tenant data-integrity/confusion vulnerability. This satisfies the "cross-tenant access" High-impact criterion.

### Likelihood Explanation
Exploitation requires only the ability to send an arbitrary HTTP request to the app's public webhook endpoint plus one previously-observed valid `(body, hmac)` pair, which is trivially obtainable by any merchant who installs the app (an unprivileged party with respect to other tenants). No access token, `client_secret`, or TLS interception is required, since the header fields are simply never authenticated.

### Recommendation
Include the tenant-identifying headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signed/verified material, or otherwise cryptographically bind them to the body before trusting them — e.g., compute the HMAC over a canonical string containing both the headers and the body, or independently verify `shop` against a known/registered store list before dispatching to handlers.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com`; Shopify sends a legitimate webhook: body `B`, headers `X-Shopify-Hmac-Sha256: H(B)`, `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Topic: orders/create`.
2. Attacker records `(B, H(B))`.
3. Attacker POSTs to the app's webhook endpoint with the same body `B` and HMAC header `H(B)`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Registry.process` → `HmacValidator.validate(request)` passes because only `B` is checked against `H(B)` (`lib/shopify_api/webhooks/request.rb` `to_signable_string`).
5. `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: JSON.parse(B), ...)` is passed to the app handler, which processes attacker-controlled data as belonging to `victim-shop`.
