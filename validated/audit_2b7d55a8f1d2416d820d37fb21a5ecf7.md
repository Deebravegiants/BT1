### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body [1](#0-0) , while the `shop` value that is handed to the app's `WebhookHandler` is read from an HTTP header (`x-shopify-shop-domain`/`shopify-shop-domain`) that is never included in the signed content [2](#0-1) . This breaks the intended identity binding `HMAC-verified(body) == (body, shop)` down to `HMAC-verified(body) == body`, letting an attacker attach an arbitrary `shop` value to an otherwise-valid `(body, hmac)` pair.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate` computes/compares the signature purely over that signable string [4](#0-3) . `Request#shop` is derived independently from the `shop-domain` header, entirely outside the HMAC computation [5](#0-4) . `Registry.process` validates the HMAC and then immediately forwards `request.shop` (the unauthenticated header) into `WebhookMetadata` and passes it to the app's handler as the trusted tenant identifier: `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` [6](#0-5) . The gem's own documentation instructs apps to trust `data.shop` as "The shop domain of the webhook" to route/scope work per shop [7](#0-6) , so this is the gem's documented, in-scope contract, not host misuse.

Because Shopify's own HMAC signature is only ever computed over the body, any unprivileged internet user who owns a development store can:
1. Trigger any webhook topic on their own store (any user can create a free Shopify dev store and register a webhook endpoint they control, or simply construct a JSON body such as `{}` and topic string themselves).
2. Capture a `(raw_body, hmac)` pair that is valid under the app's real `api_secret_key` (Shopify computes and sends this HMAC to their endpoint for their own shop's traffic — no secret is needed by the attacker to obtain it).
3. Replay that exact `raw_body` and `hmac` directly to the target app's public webhook endpoint, but with the `X-Shopify-Shop-Domain` header changed to the victim shop's domain.

`HmacValidator.validate` will succeed (the body/hmac pair is genuinely valid), and `Registry.process` will call the handler with `shop` equal to the attacker-chosen victim domain, even though the body content actually originated from the attacker's own shop.

### Impact Explanation
This directly enables cross-tenant access/confusion: the app is misled into attributing attacker-controlled webhook content to a victim shop it has no relationship to. Depending on how the host app implements its handler (per the gem's own documented usage pattern of keying data lookups/actions by `data.shop`), this can be used to inject or associate forged order/customer/product events into another merchant's account context, satisfying the Critical "cross-tenant access" impact category — achieved purely as an unprivileged internet user with no access token, `api_secret_key`, or privileged account required.

### Likelihood Explanation
Likelihood is high: obtaining a valid `(body, hmac)` pair requires nothing more than operating one's own free Shopify development store and registering the app (or replaying any publicly observable/guessable body such as `{}"`), then sending a normal unauthenticated HTTP POST to the target app's public webhook endpoint with a modified `shop-domain` header. No secrets, tokens, or privileged access are needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the HMAC-signed content, or otherwise cryptographically bind them to the signed body, before trusting them in `WebhookMetadata`. At minimum, `Request#to_signable_string` should incorporate the shop-domain header (and other identity-relevant headers) so that `HmacValidator.validate` fails if any of these fields are altered independently of the body signed by Shopify.

### Proof of Concept
1. Attacker registers/owns `attacker-shop.myshopify.com` and subscribes the target app to a webhook topic (e.g., `orders/create`).
2. Shopify sends a webhook to the app for `attacker-shop.myshopify.com` with body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker captures `B` and `H` (e.g., from their own server logs, or by using a trivially predictable body).
4. Attacker sends directly to the target app's public webhook endpoint:
   ```
   POST /webhooks/orders_create
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: H
   X-Shopify-Shop-Domain: victim-shop.myshopify.com
   Body: B
   ```
5. `HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H` [4](#0-3) .
6. `Registry.process` invokes the app's handler with `shop: "victim-shop.myshopify.com"` [8](#0-7) , causing the app to process attacker-controlled content under the victim's tenant identity.
