### Title
Locally-declared signup success bypasses backend enrollment verification for user-centric signups, enabling misattributed signup state - ([File: src/plans/mod.rs])

### Summary
The reported bug class is a missing state update that leaves the authoritative accounting/state out of sync with reality, causing token holders to receive an incorrect (lower) value that never reflected the true backend-collected fees. The analogous defect in orb-core is in `do_signup()`: for "user-centric" signups the orb never calls the backend enrollment verification path (`enroll_user`, which performs `signup_post`/`signup_poll` against the backend) and instead derives `success` purely from local, unverified orb state, so the signup's recorded "success" status is not actually backed by the backend's authoritative determination.

### Finding Description
In `src/plans/mod.rs`, `do_signup()` computes `signup_reason` from two local signals: whether the biometric `pipeline` produced `Some` output, and the result of `self.detect_fraud(...)`. [1](#0-0) 

`detect_fraud` in this build is a no-op that always returns `Ok(false)` (fraud checks were stripped from the FOSS build): [2](#0-1) 

Then, when `user_centric_signup` is `true` (a flag carried in `UserData` sourced from the app/backend session data) and `ignore_user_centric_signups` is not set, the orb **skips the call to `enroll_user`/backend signup verification entirely** and instead sets `success` directly from the locally computed `signup_reason`: [3](#0-2) 

Compare this to the non-user-centric path, where `enroll_user` is invoked, which performs the actual backend round-trip (`signup_post::request` followed by polling via `signup_poll::request`) — this is the only code path that lets the backend reject duplicate signups, inflight matches, legacy signups, or backend-detected fraud: [4](#0-3) 

Because the fraud-check function is neutered (`Ok(false)` unconditionally) and the user-centric branch never asks the backend anything, the only gate on `success` becomes "did the biometric pipeline produce output" — i.e., any completed capture is declared `Success` locally with `debug_report.signup_successful()` / `orb.ui.signup_success()`, with no backend confirmation that the identity is unique or otherwise not fraudulent. [5](#0-4) 

This mirrors the external report's root cause pattern precisely: a required state-synchronizing call to the authoritative system (there: `totalFunds +=` after fee collection; here: the backend enrollment/duplicate/fraud verification call) is missing on one code path, while it correctly exists on the sibling path (`enroll_user` for the non-user-centric branch) — producing a state (`enrollment_status`/`signup_status` = Success) that does not reflect the true, backend-validated outcome.

### Impact Explanation
The orb's local record (`debug_report.enrollment_status`, `signup_status`, `dd_incr!("main.count.signup.result.success.successful_signup")`, and the UI's `signup_success()`) is marked "Success" without any backend acknowledgment for user-centric signups, decoupled from whether the backend actually accepted/registered that identity. Since fraud detection is entirely disabled in this build, there is no orb-side backstop either. This is a misattributed-signup condition: the orb can report and record a successful, unique signup while the backend never validated uniqueness or fraud status for that specific enrollment, corresponding to the "misattributed signup" impact category.

### Likelihood Explanation
The vulnerable branch is reached whenever the backend-supplied session data sets `user_centric_signup = true` and the orb's config has not set `ignore_user_centric_signups`, which appears to be a normal, reachable production configuration (not a test-only or hardware-only path). No privileged access is required — an ordinary signup flow with this flag set triggers the divergence deterministically, since `detect_fraud` always returns `false` and pipeline success is the only remaining condition.

### Recommendation
For the user-centric signup path, do not synthesize `success` purely from local `signup_reason`. Either:
1. Always invoke the backend enrollment/verification call (`enroll_user`, i.e. `signup_post`/`signup_poll`) regardless of `user_centric_signup`, so the backend's authoritative duplicate/fraud determination is consulted before declaring success, or
2. If the app is truly responsible for completing enrollment in this mode, have the orb explicitly poll/verify the backend's own record of that signup's outcome before marking `enrollment_status`/`signup_status` as `Success`, rather than trusting local-only signals.

### Proof of Concept
1. Configure/observe a signup session where the app-supplied `UserData.user_centric_signup` is `true` and the orb config does not set `ignore_user_centric_signups` (default reachable state per `src/backend/user_status.rs` and `src/config.rs`).
2. Complete a biometric capture such that `biometric_pipeline` returns `Some(pipeline)` (any completed, non-erroring capture).
3. Observe that `detect_fraud` unconditionally returns `Ok(false)` [6](#0-5) , so `signup_reason = SignupReason::Normal`.
4. In `do_signup`, because `user_centric_signup && !ignore_user_centric_signups`, `enroll_user` (the only call that talks to the backend to check duplicates/fraud, see `src/plans/enroll_user.rs`) is never invoked; `success` is set to `true` purely from `signup_reason == SignupReason::Normal` [3](#0-2) .
5. `report_signup_reason` marks `debug_report.signup_successful()` and increments the success metric, and `ui_complete_signup` shows `signup_success()` — all without the backend ever confirming this specific enrollment attempt succeeded or was unique [7](#0-6) .
