### Title
Browser-side `OmniBridge.describeWithdrawal` reports the pending BTC `pending_sign_id` as a final "completed" txHash, which can later diverge from the true finalised transaction hash - (File: packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts)

### Summary
For UTXO-chain (BTC) withdrawals, `describeWithdrawal` branches on `typeof window !== "undefined"` and, when running in a browser, returns `transfer.utxo_meta?.pending_sign_id` as the withdrawal's final `txHash` with `status: "completed"`. The code's own comment acknowledges this hash "may change if the BTC transfer fails to be submitted," meaning the reported hash can diverge from `transfer.finalised?.transaction_hash`, the value used server-side.

### Finding Description
The broken equality: `txHash reported at status:"completed"` (browser path, `transfer.utxo_meta?.pending_sign_id`) should equal the eventual durable on-chain BTC transaction hash (`transfer.finalised?.transaction_hash`), but the code explicitly allows these to diverge.

Code path: [1](#0-0) . The comment directly preceding this branch states the root cause: [2](#0-1) 

Crucially, this "completed" status is treated as terminal by the polling logic that consumes `describeWithdrawal`: [3](#0-2)  — the poll loop exits immediately upon receiving `"completed"`, so there is no subsequent re-check that would catch a later change in `transfer.finalised.transaction_hash`. Once `watchWithdrawal` resolves with `pending_sign_id` as the hash, that value is handed back to the SDK caller/integrator as the final settlement hash for the withdrawal, with no mechanism to reconcile it against the eventual on-chain hash if BTC submission is retried with a different hash.

No existing guard (`validateAddress`, `compareAddresses`, `validateWithdrawal`, `supports()` ordering, `assert` checks) touches this status-reporting logic — those functions apply to withdrawal creation/validation, not to `describeWithdrawal`'s post-hoc status polling, so nothing prevents the divergence.

### Impact Explanation
An integrator polling from a browser context receives a `"completed"` status with `txHash = pending_sign_id` and, per the poll's terminal semantics, stops watching. If the underlying BTC broadcast subsequently fails and is resubmitted under a different `transaction_hash`, the integrator's recorded settlement hash is permanently stale/wrong — a status/hash misreport, matching the High severity category ("a status or hash misreport making an integrator credit or refund twice" class of impact, here manifesting as a wrong, non-reconciled hash requiring manual recovery). This is repeatable for every BTC-destined Omni withdrawal watched from a browser context whose initial signing attempt is later replaced.

### Likelihood Explanation
Preconditions: the SDK must run in a browser (`typeof window !== "undefined"`), the withdrawal must target a UTXO chain (BTC) via the Omni Bridge, and the underlying BTC submission must fail and be resubmitted with a different hash after the SDK has already reported `pending_sign_id`. The attacker/trigger here isn't an adversarial input crafted by an unprivileged actor — it is an inherent race in the bridge's own resubmission behavior, but the *reporting bug* (treating an admittedly volatile hash as final, with no re-verification) is a bridge-adapter defect in this repo, not a bridge-API/relayer trust issue, since the code's own comment identifies the volatility and the polling logic in `withdrawal-watcher.ts` (in this repo) is what discards the ability to detect it. Likelihood is "rare" per the comment itself but non-negligible for any BTC withdrawal volume, and is fully reproducible with mocked HTTP responses.

### Recommendation
In `describeWithdrawal`, for the UTXO/browser branch, either (a) do not report `status: "completed"` for `pending_sign_id`, using a distinct interim status (e.g., a "pending-finalisation" status) that keeps the poll active until `transfer.finalised?.transaction_hash` is available, or (b) if returning fast for UX reasons, have `watchWithdrawal`/the SDK explicitly continue polling in the background (or re-verify) after reporting a UTXO pending hash, and expose a follow-up mechanism so integrators can be notified if the finalised hash differs from the initially reported one.

### Proof of Concept
Vitest test in `omni-bridge.test.ts` style:
1. Stub `global.window = {}` to simulate browser environment.
2. Mock `omniBridgeAPI.getTransfer` to resolve with a transfer array where `transfer.recipient` is a BTC `OmniAddress`, `transfer.utxo_meta.pending_sign_id = "X"`, and `transfer.finalised.transaction_hash = "Y"` with `X !== Y`.
3. Call `bridge.describeWithdrawal({ ...wid, index: 0 })` and assert result is `{ status: "completed", txHash: "X" }`.
4. Separately, delete `global.window` (simulate server/BE) with the same mocked transfer and assert result is `{ status: "completed", txHash: "Y" }`.
5. Assert `X !== Y`, demonstrating the STATUS_TRUTH violation: the browser-reported "completed" `txHash` ("X") does not equal the durable on-chain hash ("Y") that the server-side path would report for the identical transfer state.
6. Additionally assert, via `watchWithdrawal` in `withdrawal-watcher.test.ts`, that once `describeWithdrawal` returns `{status:"completed", txHash:"X"}`, the poll resolves immediately with `{hash:"X"}` and never re-queries for `Y`, confirming no reconciliation occurs.
