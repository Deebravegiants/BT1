## Analysis

The Maple Finance report describes a CREATE2 self-destruct/redeploy attack where a signer approves an *address* believing it holds specific, audited bytecode, but an attacker swaps the code at that address between signing and execution, causing the signer's authorization to trigger unintended logic via a low-level call.

The Hinkal `EmporiumUpgradeable` contract has a directly analogous pattern: a wallet owner signs an EIP-712 `EmporiumStack` batch of `EmporiumOperation`s that reference target contracts purely by `address` (`op.endpoint`), with no commitment to the bytecode/`extcodehash` present at that address. [1](#0-0)  The signed hash only binds `endpoint`, `invokeWallet`, `value`, and `keccak256(callData)` — never the code that will actually execute at `endpoint` at settlement time. [2](#0-1) 

When `runAction` replays the signed ops, for "stateful" operations it has the user's `HinkalWallet` make a live `.call` to `op.endpoint`, executing whatever code currently resides there, as the wallet (`msg.sender == wallet`): [3](#0-2)  which is dispatched through `HinkalWallet.callHinkalWallet`: [4](#0-3) 

Because a batch (`EmporiumStack.ops`) can legitimately contain a token `approve` op followed by an op that calls a "router" endpoint (e.g. an approve-then-swap pattern), and the *only* thing anchoring `endpoint`'s identity in the signature is its address, an attacker who controls that endpoint address via CREATE2 can `selfdestruct` the originally-reviewed router bytecode and redeploy malicious bytecode at the same address after the user signs off-chain but before the relay submits the on-chain `transact`/`runAction` call. The malicious contract, invoked with `msg.sender == wallet`, can then call `token.transferFrom(wallet, attacker, allowance)` using the allowance the wallet just granted in the prior op of the same signed batch — moving the wallet's funds in a way the signer never authorized (they authorized calling "the router they reviewed," not the redeployed contract).

### Title
Emporium signed operations bind only to `endpoint` address, not its bytecode, enabling a Maple-style CREATE2 self-destruct/redeploy hijack of wallet-authorized calls - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction` executes a batch of `EmporiumOperation`s signed off-chain by a wallet owner via EIP-712. The signature commits to `op.endpoint` (an address), `invokeWallet`, `value`, and a hash of `callData`, but never to the bytecode/`extcodehash` present at `endpoint`. [1](#0-0)  For "stateful" ops, the user's `HinkalWallet` performs a live `.call` to that address as itself. [4](#0-3)  If the endpoint contract is destroyed and CREATE2-redeployed with malicious code between signature creation and on-chain settlement (the exact technique described in the Maple refinancer report), the signer's authorization is hijacked to run arbitrary logic in the wallet's calling context.

### Finding Description
A batch such as `[approve(router, amount) on token via wallet, swap-call to router via wallet]` is signed once by the wallet owner. `verifyWallet` only checks the EIP-712 signature over the ops' addresses/calldata hashes and a `deadline`/`maxFee`, never the deployed code at `endpoint`: [5](#0-4) 

If the attacker (who deployed the "router" contract the user reviewed and intends to approve) `selfdestruct`s it and uses CREATE2 to redeploy malicious code at the identical address before the relay lands the transaction, the second op in the already-signed, still-valid batch will call the new malicious bytecode as the wallet (`endpoint.call{value: op.value}(op.callData)` invoked from `HinkalWallet.callHinkalWallet`). The malicious contract, seeing `msg.sender == wallet`, can immediately call `IERC20(token).transferFrom(wallet, attacker, allowance)` using the allowance the first op in the same batch just granted, diverting the funds instead of performing the expected swap.

### Impact Explanation
This is theft of shielded/wallet-held user funds: the wallet owner authorized a specific interaction (e.g., swap through a reviewed router) but ends up authorizing an arbitrary `transferFrom` of their approved allowance to the attacker, executed under the wallet's own `msg.sender` identity — a wallet operation never actually authorized by the signer. This matches the "unauthorised asset movement" / "temporary or theft of user funds" impact class.

### Likelihood Explanation
Exploitation requires the attacker to control the deployment of an `endpoint` contract that the user will approve tokens to and call in the same signed batch (e.g., an unaudited or externally supplied "router"/integration contract), and to race a CREATE2 redeploy between signature creation and on-chain execution — mirroring the difficulty profile the Maple judges assigned Medium severity to. It does not require compromising the relay, admin, or prover, only monitoring the pending signed message and controlling the target contract's deployment address, satisfying the "unprivileged EOA" analog requirement.

### Recommendation
Bind the EIP-712 signature to the `extcodehash` of each `op.endpoint` at signing time (or require `endpoint` to be on an owner-managed allowlist of immutable, vetted contracts) and re-verify that hash inside `runAction` before performing the call, rejecting the operation if the deployed bytecode no longer matches what the signer approved.

### Proof of Concept
1. Attacker deploys `Router` at address `R` via CREATE2, containing benign swap logic; user reviews it off-chain.
2. User signs an `EmporiumStack` with ops `[approve(Token, R, amount) via wallet, call R.swap(...) via wallet]`, per `_hashEmporiumOps`/`EMPORIUM_OPERATION_TYPEHASH` which only encodes `R`'s address, not its code. [1](#0-0) 
3. Before the signed message is submitted, attacker `selfdestruct`s `R` and CREATE2-redeploys malicious code at the same address `R`, implementing `transferFrom(wallet, attacker, amount)` on invocation.
4. Relay submits the original signed `EmporiumStack`; `runAction` executes op[0] (approve succeeds normally), then op[1] calls `R` via `HinkalWallet.callHinkalWallet`, invoking the attacker's new code with `msg.sender == wallet`. [3](#0-2) 
5. The malicious code calls `Token.transferFrom(wallet, attacker, amount)`, draining the just-approved allowance instead of performing the swap, with the on-chain check only verifying balance deltas of `erc20TokenAddresses` tracked by `circomData`, not that `R`'s code matches what was reviewed.

    function _hashEmporiumOps(
        EmporiumOperation[] memory ops
    ) private pure returns (bytes32) {
        bytes32[] memory opHashes = new bytes32[](ops.length);
        for (uint256 i = 0; i < ops.length; i++) {
            opHashes[i] = keccak256(
                abi.encode(
                    EMPORIUM_OPERATION_TYPEHASH,
                    ops[i].endpoint,
                    ops[i].invokeWallet,
                    ops[i].value,
                    keccak256(ops[i].callData)
                )
            );
        }
        return keccak256(abi.encodePacked(opHashes));
    }
```

    function verifyWallet(
        EmporiumStack memory stack,
        CircomData calldata circomData
    ) internal {
        EmporiumStorageVars storage $ = _getEmporiumStorage();

        if ($.usedMessages[circomData.emporiumMessage]) {
            revert UsedMessage();
        }

        $.usedMessages[circomData.emporiumMessage] = true;

        if (stack.signerAddress == address(0)) {
            return;
        }

        bytes32 hashedMessage = _hashTypedDataV4(
            keccak256(
                abi.encode(
                    EMPORIUM_SIGNATURE_TYPEHASH,
                    circomData.emporiumMessage,
                    _hashEmporiumOps(stack.ops),
                    stack.maxFee,
                    stack.deadline
                )
            )
        );

        (address recoveredAddress, ECDSA.RecoverError err) = ECDSA.tryRecover(
            hashedMessage,
            stack.v,
            stack.r,
            stack.s
        );
        bool verified = err == ECDSA.RecoverError.NoError &&
            recoveredAddress == stack.signerAddress;
        if (!verified) {
            revert InvalidSignature();
        }

        if (block.timestamp > stack.deadline) {
            revert SignatureExpired();
        }

        if (circomData.feeStructure.flatFee > stack.maxFee) {
            revert FeeExceedsSignedMax();
        }
    }
```
