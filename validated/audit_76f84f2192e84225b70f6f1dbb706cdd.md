This confirms the vulnerability: `RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials` both call `Utils::ShopValidator.sanitize!(shop)` before using the shop to build the HTTP client that sends `client_secret`. `TokenExchange.exchange_token`, however, derives `dest_shop = jwt_payload.shop` directly from `JwtPayload#shop` and never passes it through `ShopValidator`, and `Oauth.validate_auth_callback` derives the session shop directly from `auth_query.shop` as well.

### Title
Unsanitized JWT `dest` claim used to build the OAuth token-exchange request host, bypassing `ShopValidator` and risking `client_secret`/session-token exfiltration - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` derives the request host for the `/admin/oauth/access_token` call solely from the `dest` claim of the caller-supplied session token, via `JwtPayload#shop`, and never runs it through `ShopifyAPI::Utils::ShopValidator.sanitize!`, unlike the sibling flows `RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials`, which explicitly call `Utils::ShopValidator.sanitize!(shop)` before constructing the same kind of request.

### Finding Description
`JwtPayload#shop` is computed as `@dest.gsub("https://", "")` [1](#0-0)  with no format/domain validation — the only integrity check performed in `JwtPayload#initialize` is `@aud == Context.api_key` [2](#0-1) ; `iss`, `dest`, and `sub` are accepted as-is from the decoded payload.

`TokenExchange.exchange_token` then uses this unsanitized value directly to build the outbound session and HTTP client that carries the app's `client_secret` and the raw `session_token`: [3](#0-2) 

`Clients::HttpClient#initialize` builds the request base URI directly from `session.shop` when no `api_host` override is configured: [4](#0-3) 

Contrast this with the two other grant flows in the same module, `RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials`, which both sanitize the caller-provided `shop` through `Utils::ShopValidator.sanitize!` — which restricts the resulting host to `TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) — before it is used to build the session/HTTP client: [5](#0-4) [6](#0-5) [7](#0-6) 

The identity binding that should hold is: **the host that receives the `client_secret`/`subject_token` in the token-exchange request must equal a value validated as a trusted Shopify domain**. In `TokenExchange.exchange_token`, the host is only "validated" in the weak sense of coming from a payload whose signature checks out and whose `aud` matches — it is never checked to be a `*.myshopify.com`/trusted Shopify domain shape via `ShopValidator`. This is the same class of bug as the ERC4626 report's root cause (a value is trusted for a security-critical computation without going through the guard that the codebase itself established elsewhere for equivalent inputs) — here, `RefreshToken` and `ClientCredentials` show the library's own established guard (`ShopValidator.sanitize!`) is skipped for `TokenExchange`.

### Impact Explanation
If the `dest` claim can carry a value that is not a proper trusted Shopify host (e.g. due to a caller integration bug, a proxy/relay of session tokens, or any code path that constructs/decodes a JWT payload without going through Shopify's own strict token issuance), `exchange_token` would send the app's `client_secret` and the bearer `subject_token` to a host taken verbatim from that claim. This matches the "Critical: theft or exfiltration of the app's client_secret" and "High: SSRF with the app's credentials" categories, since the request is made by the gem's own `HttpClient`, using the app's `client_secret`, to a caller-influenced host with no allow-listing.

### Likelihood Explanation
Exploitability is bounded by the fact that a legitimately-signed session token's `dest` claim is normally set by Shopify's own infrastructure and difficult for a remote unprivileged attacker to control directly. However, this is precisely the kind of gap `ShopValidator` was introduced to close for `RefreshToken` and `ClientCredentials` (per `CHANGELOG.md`'s 16.3.0 entry noting `ShopValidator` and the `dest`-claim-driven derivation for `TokenExchange`), and `TokenExchange` is the one flow of the three that omits the check, making it an inconsistency/regression relative to the gem's own established defense rather than a purely theoretical concern.

### Recommendation
Route `dest_shop` through `ShopifyAPI::Utils::ShopValidator.sanitize!` (mirroring `RefreshToken.refresh_access_token` and `ClientCredentials.client_credentials`) before constructing `shop_session` / the `Clients::HttpClient` in `TokenExchange.exchange_token`, so the destination host for a request carrying `client_secret` is provably restricted to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
1. Construct (or otherwise obtain) a session token whose `aud` matches `Context.api_key` but whose `dest` claim is set to an attacker-controlled or malformed host string.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: token, requested_token_type: ...)`.
3. Observe that `dest_shop = jwt_payload.shop` (raw `dest` minus `"https://"`) is used unsanitized to build `shop_session` and the `Clients::HttpClient`, whose `@base_uri = "https://#{session.shop}"` [4](#0-3)  — the app's `client_secret` and `subject_token` are then POSTed to `https://#{dest_shop}/admin/oauth/access_token`, unlike the equivalent `RefreshToken`/`ClientCredentials` flows which reject any host outside `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` via `sanitize!` before this point.
