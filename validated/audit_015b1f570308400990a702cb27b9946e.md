### Title
Creator fees permanently locked in FeeVault if the creator's address is blacklisted by USDC's issuer - (File: `packages/contracts/src/FeeVault.sol`)

### Summary
`FeeVault.claim()` pays out `creatorBalance[msg.sender]` via a direct `safeTransfer` to `msg.sender`, with no alternate recipient path and no owner-level rescue mechanism for the creator-balance mapping. If Circle blacklists the creator's address on USDC, `claim()` reverts permanently for that creator, and the associated `creatorBalance` entry — and any USDC backing it in the vault — becomes unrecoverable, exactly analogous to the referenced Taiko bridge report where a mint-allowance failure on the destination token permanently strands funds inside the bridge contract with no way to redirect the payout.

### Finding Description
`FeeVault.claim()` reads and zeroes `creatorBalance[msg.sender]`, then unconditionally transfers USDC to `msg.sender`: [1](#0-0) 

There is no parameter to specify an alternate recipient, and no owner-only sweep/rescue function exists for `creatorBalance` (only `claimProtocol()` for the protocol's own balance and `sweepDonations()` for unbacked surplus, neither of which touch a specific creator's accrued balance): [2](#0-1) 

USDC (Circle) can blacklist any address, causing every `transfer`/`transferFrom` to or from that address to revert unconditionally and indefinitely (this is the standard `FiatTokenV2` blacklist behavior referenced by the same class of external-stablecoin-restriction bug as the cited bridge report, just via `blacklist` instead of `minterAllowance`). Once a creator address is blacklisted, `$.usdc.safeTransfer(msg.sender, amount)` inside `claim()` will always revert for that creator, exactly as the cited report's `mint` call always reverts once the minting allowance is exhausted.

`Bonding.transferCreator` lets a creator hand off attribution for future accrual to a new address, but it does not touch the FeeVault's already-accrued `creatorBalance[oldCreator]` mapping — that balance is permanently keyed to the old (now-blacklisted) address and can never be claimed by anyone, including the new creator.

This mirrors the report's root cause precisely: a two-step flow (accrue now, pay out later via an external token call) where the payout call is gated by a condition on the *external* asset (USDC blacklist / minting allowance) that the vault cannot control, retry with different parameters, or reroute around.

### Impact Explanation
Any USDC accrued to a creator whose address later becomes blacklisted by Circle is permanently frozen inside `FeeVault` — a genuine, unrecoverable loss of creator funds, with no owner or protocol-level remediation path (`transferCreator` only redirects future fees, not the stuck balance). This is a direct funds-freezing bug reachable purely through the protocol's normal fee-accrual and claim flow.

### Likelihood Explanation
Requires an external event (USDC blacklisting the specific creator address), which is outside the creator's or an attacker's control and not something they can trigger at will — this keeps likelihood at Medium, matching the judged severity of the referenced Taiko finding, which also depended on an external condition (USDC minter-allowance exhaustion) rather than attacker-controlled input.

### Recommendation
Allow `claim()` to accept/redirect to an explicit recipient chosen by the creator ahead of being blacklisted, or add an owner-gated rescue function that can move a specific creator's stranded `creatorBalance` to a new address (mirroring the intent of `transferCreator`, but retroactively covering already-accrued balances) so that no creator's fees are permanently unclaimable.

### Proof of Concept
1. `depositor` (an allowlisted Zap) calls `FeeVault.accrue(token, creator, creatorAmount, protocolAmount, isBuy)` after transferring the USDC in, crediting `creatorBalance[creator]`.
2. Circle blacklists `creator`'s address on the USDC contract (external event, out of protocol control).
3. `creator` calls `FeeVault.claim()`; `$.usdc.safeTransfer(msg.sender, amount)` reverts because `msg.sender` is blacklisted — see the transfer call at: [1](#0-0) 
4. `Bonding.transferCreator` can reassign future fee attribution to a new address, but the already-accrued `creatorBalance[creator]` mapping entry in `FeeVault` is untouched and remains permanently claimable only by the blacklisted address — i.e., never.
5. The USDC backing that balance sits in the vault indefinitely with no owner rescue path (`claimProtocol`/`sweepDonations` only cover protocol balance and unbacked surplus, not a specific creator's backed balance).

    function claim() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.creatorBalance[msg.sender];
        if (amount == 0) revert NothingToClaim();
        $.creatorBalance[msg.sender] = 0;
        $.totalAccruedCreator -= amount;
        $.usdc.safeTransfer(msg.sender, amount);
        emit CreatorFeesClaimed(msg.sender, amount);
    }

    function claimProtocol() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        amount = $.protocolBalance;
        if (amount == 0) revert NothingToClaim();
        $.protocolBalance = 0;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit ProtocolFeesClaimed(feeTo_, amount);
    }

    /// @notice Sweep unbacked USDC (donations) to `feeTo`. Required because
    ///         direct USDC transfers would otherwise inflate `balanceOf` above
    ///         the accrual tally and silently mask the `accrue` underfund
    ///         check. Permissionless — funds always go to the admin-set `feeTo`.
    function sweepDonations() external nonReentrant returns (uint256 amount) {
        FeeVaultStorage storage $ = _s();
        uint256 backed = $.totalAccruedCreator + $.protocolBalance;
        uint256 balance = $.usdc.balanceOf(address(this));
        if (balance <= backed) revert NothingToClaim();
        amount = balance - backed;
        address feeTo_ = $.feeTo;
        $.usdc.safeTransfer(feeTo_, amount);
        emit DonationsSwept(feeTo_, amount);
    }
