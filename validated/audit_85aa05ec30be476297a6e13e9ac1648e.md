### Title
Webhook shop/topic attribution is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable content from the raw body only (`to_signable_string` → `@raw_body`), while `shop` and `topic` are read straight from HTTP headers that are excluded from the signed bytes. `Registry.process` trusts `request.shop`/`request.topic` for dispatch as soon as `Utils::HmacValidator.validate(request)` succeeds, so the identity binding "HMAC validates the body" is treated as if it also validated "HMAC validates which shop/topic this body belongs to" — it does not.

### Finding Description
`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, Context.api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` header value using `OpenSSL.secure_compare`: [4](#0-3) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body`: [5](#0-4) 

`shop` and `topic`, however, are pulled from the `shopify-shop-domain` / `shopify-topic` (or `x-shopify-*`) HTTP headers, which are not part of `to_signable_string` and therefore not covered by the HMAC at all: [6](#0-5) 

`Registry.process` performs exactly one check — that the body's HMAC is valid — and then hands `request.shop` and `request.topic` (unauthenticated header values) to the app's registered handler as trusted identity data: [7](#0-6) 

Crucially, `api_secret_key` is the app-level client secret, identical for every shop that installs the app — it is not per-shop. This means a legitimate, unprivileged merchant of shop A can:
1. Trigger any webhook event on their own store (or replay one Shopify already sent them), obtaining a genuine `raw_body` + valid `hmac-sha256` header signed with the app's shared secret.
2. Resend that exact `raw_body`/`hmac` pair to the app's webhook endpoint, but with `X-Shopify-Shop-Domain` changed to victim shop B's domain (and/or `X-Shopify-Topic` changed to a different topic).
3. `HmacValidator.validate` still succeeds, because the signature never covered `shop` or `topic`. The app's handler then processes attacker-supplied body content as if it were an authentic event for shop B.

This breaks the identity binding: `HMAC-verified(bytes) == HMAC-verified(bytes, shop, topic)` — the equality the app implicitly relies on when dispatching by `request.shop`/`request.topic` does not hold.

### Impact Explanation
This is a cross-tenant data-integrity/authentication issue: an unprivileged holder of any valid webhook signature (which every installed merchant automatically has for their own shop) can inject attacker-chosen event data attributed to an arbitrary victim shop into the app's business logic (e.g. `shop/redact`, `customers/data_request`, order/product update handlers), or replay/relabel events across topics the app trusts by `topic`. Depending on what the host application's registered `WebhookHandler` does with `data.shop`/`data.topic`/`data.body` (e.g. writing to per-shop storage, triggering GDPR redaction, granting entitlements), this can lead to cross-tenant data corruption or unauthorized actions taken against a victim merchant's data — matching the Critical "cross-tenant access" category.

### Likelihood Explanation
High. No secret material beyond what any installed merchant already legitimately possesses is required — the attacker only needs to be a normal installed user of the app on any shop, capture one of their own valid webhook deliveries, and replay it with a modified `shop-domain`/`topic` header to the app's public webhook endpoint.

### Recommendation
Include `shop`, `topic` (and ideally `webhook_id`/`api_version`) in the signed content, or otherwise cryptographically bind them to the request before trusting them for dispatch — e.g. compute the HMAC over a canonical string composed of the raw body plus these header values, and reject the webhook if that combined signature does not match. At minimum, document that host applications must independently correlate `shop`/`topic` against the endpoint they registered rather than trust these header values as authenticated.

### Proof of Concept
1. App registers a webhook handler for topic `orders/create` and shop A installs the app, triggering a real order-create webhook. Attacker (merchant of shop A) intercepts the raw POST: body `B`, header `X-Shopify-Hmac-Sha256: H` (valid for `B` under the app's `api_secret_key`), `X-Shopify-Shop-Domain: shop-a.myshopify.com`.
2. Attacker resends the identical `B`/`H` to the app's webhook endpoint, replacing the header with `X-Shopify-Shop-Domain: shop-b.myshopify.com` (victim shop B, also an app installer, but not the source of this data).
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only — identical to step 1 — so validation succeeds.
4. The handler executes `handler.handle(data: WebhookMetadata.new(topic: "orders/create", shop: "shop-b.myshopify.com", body: JSON.parse(B), ...))`, meaning shop A's order payload is processed and attributed to shop B inside the app, despite shop B never having sent or authorized this event.
