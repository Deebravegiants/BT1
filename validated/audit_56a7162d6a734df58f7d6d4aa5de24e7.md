## Finding

### Title
Webhook `shop` (and `topic`/`webhook_id`) identity fields are trusted from unauthenticated HTTP headers while the HMAC only covers the raw body, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop`, `topic`, `api_version`, and `webhook_id` values solely from HTTP headers, while the HMAC signature that `Registry.process` verifies is computed only over the raw request body. This breaks the binding between "the shop that was cryptographically authenticated" and "the shop the handler acts on," allowing anyone who can reach the app's public webhook endpoint to keep a validly-signed body but substitute an arbitrary `shop-domain` (or `topic`) header, causing the app to process attacker-chosen webhook data under a victim tenant's identity.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read directly from HTTP headers, none of which are part of the signed material: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` (the body) and compares it against the `hmac` header: [3](#0-2) 

`Registry.process` only checks this HMAC before dispatching the handler with `request.shop`, `request.topic`, etc., taken straight from the unauthenticated headers: [4](#0-3) 

The identity binding the library implicitly claims to provide is:
`shop_used_by_handler == shop_that_was_HMAC-authenticated`

In reality the equality holds only for `body == HMAC(body)`; `shop` (and `topic`/`webhook_id`) are parsed independently of the signature. Any client capable of POSTing to the app's public webhook route — an "unprivileged internet user" relative to any *other* merchant's tenant — can take a body/HMAC pair that is valid for their own shop (which they can legitimately obtain, since Shopify sends them real signed webhooks for their own store) and resend it to the same endpoint with the `x-shopify-shop-domain` header changed to a victim shop's domain. The HMAC still validates (it never covered the header), and `WebhookMetadata.new(shop: request.shop, ...)` is built with the attacker-controlled victim domain, so the handler runs as if the payload legitimately originated from the victim tenant.

### Impact Explanation
This is a cross-tenant identity-crossing bug: an attacker who is a legitimate merchant/installer of the app (an "unprivileged" party with respect to other merchants) can cause the host application's webhook handler to execute attacker-controlled body content attributed to an arbitrary victim shop, without needing the victim's credentials, access token, or `client_secret`. Depending on what the host app's webhook handler does with `data.shop` (e.g., updating per-shop billing state, order records, or triggering shop-scoped side effects), this can lead to cross-tenant data corruption or unauthorized actions performed against a victim's tenant — matching the "cross-tenant access" Critical-impact category, since the gem's own signature-verification contract is what's being defeated.

### Likelihood Explanation
Likelihood is High for any first-party attacker who has ever received (or can generate) one authentic webhook body+HMAC pair for their own shop — which is trivial, since installing the app or triggering any registered webhook topic produces one. No secret material beyond a normal webhook delivery is required, and the webhook receiving endpoint is by design a public, unauthenticated HTTP route (`docs/usage/webhooks.md`), so the request can be replayed with a modified header via any HTTP client.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) in the signed/verified material, or otherwise cryptographically bind them to the request before trusting `request.shop` for dispatch — e.g., verify that the `shop-domain` header matches an expected/registered shop for the delivery, or extend `to_signable_string` to fold in the identity headers Shopify itself covers via its delivery signing scheme, rather than trusting raw headers as the sole source of tenant identity.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and receives a real webhook
# for it, giving them a valid (body, hmac) pair signed with the app's
# api_secret_key (known only to Shopify + the app, but the *pairing* of
# shop -> hmac is never actually checked).

real_body = '{"id": 1, "note": "attacker controlled content"}'
real_hmac_header = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, real_body)
)

# Attacker now POSTs the same body+hmac to the shared endpoint but swaps
# the shop-domain header to a victim tenant.
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac_header,     # unchanged, still valid because HMAC never covered "shop"
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # attacker-controlled
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: real_body, headers: forged_headers)

# HmacValidator.validate(request) succeeds because it only checks HMAC(real_body).
# Registry.process then calls the handler with data.shop == "victim-shop.myshopify.com"
ShopifyAPI::Webhooks::Registry.process(request)
```
The handler executes believing the payload is an authentic webhook from `victim-shop.myshopify.com`, even though it never sent it, demonstrating the cross-tenant identity binding failure at `lib/shopify_api/webhooks/request.rb#L21-L23` and `lib/shopify_api/utils/hmac_validator.rb#L27-L31`.
