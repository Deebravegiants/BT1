### Title
Missing Slippage Floor Enforcement in `ExternalActionSwap.swap()` Allows Theft of Shielded Funds via Sandwich Attack - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`ExternalActionSwap.swap()` requires that a non-zero slippage floor (`circomData.slippageValues[1]`) be *present* in the proven/signed calldata, but the function never actually compares the realized swap output (`swappedAmount`) against that floor. The floor value is baked into `calldataHash`/`signedMessageHash` (so it can't be tampered with), yet it is never used to reject an under-priced execution, leaving an unprivileged attacker free to sandwich the router call and capture the difference.

### Finding Description
The `CircomData.slippageValues` field is committed to by the off-chain signer and is part of the integrity-protected calldata: it is hashed inside `getHashedCalldata1()` [1](#0-0) , which feeds `getHashedCalldata()` and is checked against `circomData.calldataHash` in `performHinkalChecks()` [2](#0-1) .

In `ExternalActionSwap.swap()`, the only use of `slippageValues[1]` is a non-zero presence check, and a deadline check on `timeStamp` is present, but there is no comparison of the actual DEX output against the floor: [3](#0-2) 

Specifically:
- `require(circomData.slippageValues[1] != 0, "swap output slippage floor not set");` only asserts the field is non-zero — it never checks `swappedAmount >= circomData.slippageValues[1]`.
- `swappedAmount` returned from `callRouter()` is used directly to compute fees and the amount sent to the shielded balance, with no floor comparison.

Because `slippageValues` is hashed into `calldataHash`/`signedMessageHash`, the value cannot be *altered* by a relayer — but that integrity check is meaningless here because the value is never *enforced* against the on-chain execution result. This is exactly the bug class in the report: calldata signed off-chain (including the trader's intended worst-case price) is processed on-chain without any check that the current market condition (the router's realized output) actually respects that signed intent.

### Impact Explanation
Any unprivileged actor (a MEV searcher) observing a pending `transact()` call that triggers `ExternalActionSwap.swap()` can sandwich the `callRouter()` execution: front-run to move the pool price unfavorably, let the Hinkal swap execute at a degraded price, then back-run to capture the extracted value. Since there is no on-chain enforcement of the signed slippage floor, the resulting `swappedAmount` — and therefore the amount credited to the user's shielded UTXO — can be arbitrarily lower than what the user authorized when signing, with the difference extracted by the attacker. This is a direct theft of user funds moving through the protocol's shielded pool, satisfying the Critical impact bar ("direct theft of shielded or in-flight user funds").

### Likelihood Explanation
High. No privileged role, admin key, or malicious relayer is required — only the presence of a public swap transaction in the mempool (or equivalent MEV visibility) and a liquid-enough pool to sandwich. The `SWAP_DEADLINE_WINDOW` (10 minutes) [4](#0-3)  means signed swap intents remain valid long enough for market movement or deliberate sandwiching, while the only "protection" field (`slippageValues[1]`) is checked for non-zero-ness only, not for adequacy.

### Recommendation
Enforce the committed slippage floor against the realized output before crediting the user, e.g.:
```solidity
require(
    swappedAmount >= circomData.slippageValues[1],
    "swap output below slippage floor"
);
```
placed immediately after `callRouter()` returns `swappedAmount`, in `contracts/external-actions/swaps/ExternalActionSwap.sol`. Additionally, consider tightening `SWAP_DEADLINE_WINDOW` and requiring the router call itself (via `externalActionMetadata`) to carry a `minAmountOut` consistent with `slippageValues[1]`.

### Proof of Concept
1. A user signs a Hinkal swap transaction off-chain with `circomData.slippageValues[1] = X` (their acceptable minimum output), producing a valid `calldataHash`/proof.
2. Relayer submits `Hinkal.transact()` → `_externalTransact()` → `ExternalActionSwap.swap()`.
3. Because the swap tx is public before/while pending, an attacker front-runs the DEX pool used by `callRouter()`, pushing the price so that the eventual `swappedAmount < X`.
4. `swap()`'s only check is `circomData.slippageValues[1] != 0` (true) and the timestamp deadline (still within `SWAP_DEADLINE_WINDOW`); it does **not** check `swappedAmount >= X`.
5. The under-priced `swappedAmount` is credited to the user's shielded balance (`amountToSendToHinkal`) minus fees; the attacker back-runs to realize the arbitraged profit, which came directly from the value the user should have received. [3](#0-2)
