## Verdict

The claim is confirmed by the code: `HandleLegacyUserMessage` in `core/services/gateway/handlers/capabilities/handler.go` performs only payload-shape, timestamp, and method-name checks, then saves a callback and fans the request out to every DON member, with an explicit `// TODO: apply allowlist and rate-limiting here` marking the gap. [1](#0-0)  The request is reachable directly from `gateway.ProcessRequest`, which requires only a validly-*signed* message (`msg.Validate()` checks signature length/format, not any allowlist/authorization) with a known `DonID`, before invoking `HandleLegacyUserMessage` — no authorization or rate-limit check occurs in this call path. [2](#0-1)  By contrast, the v2 `httpTriggerHandler.HandleUserTriggerRequest` explicitly calls `authorizeRequest` and `checkRateLimit` before forwarding. [3](#0-2) 

Key caveat I could not fully rule out: `msg.Validate()` requires a syntactically valid ECDSA signature (`Message.Validate` extracts a signer address from the signature via `ExtractSigner`), so the request must be signed — but signature validity alone does not restrict *who* may sign (any keypair works, since there's no allowlist check on the sender), which matches the reported gap. [4](#0-3)  This confirms the request is reachable by any actor capable of generating an ECDSA keypair and signing a JSON-RPC payload — i.e., an unprivileged actor with no special credential, since the gateway user-facing HTTP endpoint does not require registration or pre-authorization of the signing key for this legacy path.

Audit Report

## Title
Legacy Gateway user-message path (`HandleLegacyUserMessage`) processes trigger requests without allowlist or rate-limit checks - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
`handler.HandleLegacyUserMessage` accepts `MethodWebAPITrigger` requests from any user who can produce a self-signed message, validates only payload shape, timestamp freshness, and method name, and then unconditionally fans the request out to every DON member — explicitly skipping the allowlist/rate-limit enforcement performed by the newer v2 path (`httpTriggerHandler.HandleUserTriggerRequest`).

## Finding Description
The gateway's public HTTP entrypoint `gateway.ProcessRequest` routes any legacy-format message (one that carries a `DonID`) straight to `h.HandleLegacyUserMessage` after only calling `msg.Validate()`, which checks field lengths and that the signature can be parsed into a signer address — it does not check the signer against any registry, allowlist, or per-owner/workflow permission. [2](#0-1) [4](#0-3) 

Inside `HandleLegacyUserMessage`, the only checks performed are: payload unmarshals correctly, `Timestamp != 0`, message not older than `MaxAllowedMessageAgeSec`, and `msg.Body.Method == MethodWebAPITrigger`. [5](#0-4)  Immediately after these checks, an explicit `// TODO: apply allowlist and rate-limiting here` comment marks the omission, and the code proceeds directly to saving a callback and broadcasting the request to every DON member. [6](#0-5)  The only rate limiter instantiated in this handler (`h.nodeRateLimiter`) is applied solely to node→gateway `handleWebAPIOutgoingMessage` traffic, not to inbound user triggers. [7](#0-6) 

This is asymmetric with the parallel v2 trigger path, `httpTriggerHandler.HandleUserTriggerRequest`, which calls `h.authorizeRequest(...)` and `h.checkRateLimit(...)` before dispatching to a DON, and whose own documentation states that authentication/rate-limiting are core steps of its process flow. [3](#0-2) [8](#0-7) 

Existing "checks" in the legacy path — payload parse, timestamp, method-name, signature-format validation — do not substitute for authorization: they confirm the message is well-formed and recently created and signed by *some* key, but never verify that the signing key/owner is permitted to trigger the targeted workflow, nor do they bound the rate at which any given signer can do so.

## Impact Explanation
Any actor able to reach the gateway's public HTTP user-message endpoint and generate a self-signed `web_api_trigger` message can dispatch trigger requests to every member of the target DON without being checked against a workflow-registry allowlist or subjected to per-owner/per-workflow rate limiting. This maps to the in-scope "allowlist or quota bypass" / "unauthorized job run" impact categories: an attacker could trigger workflow executions they are not authorized to trigger, and/or flood DON nodes with unthrottled trigger traffic via this specific code path.

## Likelihood Explanation
The exploit requires no privileged role — only the ability to send a JSON-RPC request to the gateway's public user-facing HTTP port with a message containing a valid `DonID` and a self-generated ECDSA signature, which `gateway.ProcessRequest` and `Message.Validate()` accept from any signer. [2](#0-1) [4](#0-3)  The remaining uncertainty is operational/deployment-level: whether `MethodWebAPITrigger`/`HandleLegacyUserMessage` is still wired into an actively used, externally reachable gateway configuration in production, or is retained only for backward compatibility while traffic has moved to the v2 `httpTriggerHandler`. This cannot be fully resolved from the indexed code/config alone, but the code-level gap itself (missing authz/rate-limit calls, confirmed by the explicit TODO) is concrete and independently verifiable, and the routing logic in `gateway.go`/`multihandler.go` shows this legacy path remains a live, registered handler method with no additional gating layer in front of it.

## Recommendation
Add the same allowlist/authorization and rate-limiting enforcement used in `httpTriggerHandler.HandleUserTriggerRequest` (`authorizeRequest`, `checkRateLimit`) to `HandleLegacyUserMessage` before it saves the callback and fans the request out to DON members. Alternatively, if the legacy path is meant to be fully superseded by the v2 handler, disable/remove `MethodWebAPITrigger` routing to `HandleLegacyUserMessage` in production configurations.

## Proof of Concept
1. Construct a `TriggerRequestPayload` with a non-zero `Timestamp` within `MaxAllowedMessageAgeSec`.
2. Sign an `api.Message` with body `{Method: "web_api_trigger", DonID: <target-don>, Payload: <payload>}` using any freshly generated ECDSA keypair (via `Message.Sign`).
3. Wrap it into a JSON-RPC request per `common.ValidatedRequestFromMessage`/`ValidatedMessageFromReq` and POST it to the gateway's public HTTP endpoint, as exercised by `gateway.ProcessRequest`.
4. Observe that the request passes `msg.Validate()` and `HandleLegacyUserMessage`'s checks despite the signer having no prior relationship to the workflow/DON, and is broadcast to all `h.donConfig.Members` — demonstrating bypass of authorization/rate-limiting relative to the equivalent v2 flow.
5. Confirm via `core/services/gateway/handlers/capabilities/handler_test.go` and `core/services/gateway/gateway_test.go` existing test harnesses (`newSignedLegacyRequest`, `newGatewayWithMockHandler`) that no test currently asserts allowlist/rate-limit rejection for this path, corroborating the gap.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
