### Title
Withdrawal paths in the Tron IntentGatewayV2 use raw low-level `.call` for ERC/TRC-20 transfers without decoding the returned boolean, allowing silent transfer failures to be recorded as successful escrow releases — permanent loss of funds - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`evm/tron/contracts/apps/IntentGatewayV2.sol` releases escrowed input tokens, transaction fees, and swept dust via `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))`, checking only the low-level call's `success` bit and ignoring the ABI-encoded boolean return value. This is the same bug class as the Kairos report: ERC20 return-value semantics are handled incorrectly, but here in the opposite direction from `Erc20CheckedTransfer` — instead of reverting on tokens with no return value, this code silently accepts tokens that return `false` on failure without reverting. Since the escrow accounting (`_orders[commitment][token] -= amount`) is already decremented and the order is marked filled/refunded before this unchecked call, a token that returns `false` (rather than reverting) on a failed transfer results in tokens being permanently stuck in the gateway while the protocol's internal state believes they were already paid out.

### Finding Description
In `withdraw()`, called from `onAccept()` for `RedeemEscrow`/`RefundEscrow` requests (reachable by any relayer who submits a valid cross-chain ISMP message, i.e. an unprivileged message dispatcher/relayer path): [1](#0-0)

The same pattern recurs for the transaction-fee release and for `SweepDust`: [2](#0-1) [3](#0-2) 

`success` is only `false` if the call reverts or the target has no code; it is `true` whenever the token contract executes and returns *any* data (or none), including an ABI-encoded `false`. Many TRC20/ERC20-style tokens on Tron return `false` on failed transfers (e.g. blacklist checks, paused states, insufficient allowance corner cases in non-standard token implementations) instead of reverting. Because the escrow ledger (`_orders[commitment][token]`) is decremented and, for `finalize`/non-partial withdrawals, `_filled[commitment]` is set *before or independent of* verifying the actual token movement succeeded, a `false`-returning failure is indistinguishable from success to the contract: the beneficiary never receives funds, but the order is marked complete and the escrow slot is emptied, so there is no path to reclaim the tokens — they remain permanently locked in the gateway contract.

This directly contrasts with the fixed/production EVM path (`evm/src/apps/intentsv2/IntentsBase.sol`), which correctly uses OZ's `SafeERC20.safeTransfer` for all outbound transfers: [4](#0-3) 

The Tron variant of `IntentGatewayV2.sol` does not use `SafeERC20` for its outbound release calls, reintroducing the exact class of bug described in the external report (missing boolean-return checking on ERC20 transfers), just manifesting as a silent no-op instead of an unconditional revert.

### Impact Explanation
Total, unrecoverable loss of escrowed input tokens or transaction fees for solvers/beneficiaries on any TRC20 token that returns `false` instead of reverting on a failed `transfer`. Since `_orders[commitment][token]` is already decremented and the order finalized (`_filled[commitment] = beneficiary`), there's no compensating mechanism (no re-withdraw, no refund) — funds are stuck in the gateway contract forever. This satisfies "permanent freezing/loss of funds" for a reachable path (any relayer delivering a valid `RedeemEscrow`/`RefundEscrow` message triggers `withdraw`, and any user placing/filling an order using such a token is exposed).

### Likelihood Explanation
Medium-High: This only triggers on tokens whose `transfer` implementation returns `false` on failure rather than reverting — a documented, non-trivial-but-real subset of the ERC20/TRC20 ecosystem (the same class flagged in the original report, e.g. blacklist/pause-gated tokens). Given the intent gateway is designed to be permissionless with respect to token selection (any TRC20 can be used as an input/output/fee token), and the withdraw path is driven by relayer-submitted cross-chain messages rather than admin-controlled token allowlists, this is reachable in normal operation whenever such a token is used and a transfer legitimately fails (e.g., beneficiary become blacklisted between order placement and settlement, or a paused token).

### Recommendation
Replace the raw `token.call(abi.encodeWithSelector(IERC20.transfer.selector, ...))` pattern in `withdraw()`, the fee-release branch, and `_sweepDust`/`SweepDust` handling in `evm/tron/contracts/apps/IntentGatewayV2.sol` with OpenZeppelin's `SafeERC20.safeTransfer`, matching the already-correct implementation in `evm/src/apps/intentsv2/IntentsBase.sol`. `SafeERC20` decodes and validates the boolean return value in addition to checking call success, correctly handling both "no return value" and "returns false" failure modes.

### Proof of Concept
1. Deploy (or use) a TRC20 token whose `transfer()` returns `false` (rather than reverting) when the recipient is blacklisted/paused (a real, documented pattern among popular tokens).
2. User places a cross-chain order on the source-chain `IntentGatewayV2` (Tron) escrowing this token as input, or a solver fills using it as fee/output.
3. Solver fills the order on the destination chain and dispatches a `RedeemEscrow` message; a relayer delivers it to the Tron `IntentGatewayV2.onAccept`.
4. `withdraw()` decrements `_orders[commitment][token]`, marks `_filled[commitment] = beneficiary`, then calls `token.call(...transfer...)`. Because the beneficiary is blacklisted, the token contract executes without reverting and returns `false`.
5. `success` is `true` (call executed, no revert), so `TransferFailed` is never raised. The function returns as if the release succeeded, emitting `EscrowReleased`.
6. Beneficiary's token balance is unchanged, but the escrow accounting and order-filled state are already finalized — the tokens remain trapped in the `IntentGatewayV2` contract's balance with no future call path able to release them (mirroring the `LostFunds.testUnableToClaim` scenario from the referenced report, but inverted: here `success` masks the failure instead of `checkedTransfer` reverting).
