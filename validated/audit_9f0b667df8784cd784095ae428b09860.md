### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay — (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC over the raw request body only, while the `shop` (from the `X-Shopify-Shop-Domain` / `shopify-shop-domain` header) is read separately and handed to the app's webhook handler unauthenticated. Because the app's `api_secret_key` is shared across all shops that install the app, a merchant who has installed the app can capture a validly-signed webhook delivered to their own endpoint and replay it against the same endpoint with the `shop-domain` header rewritten to a victim shop. `ShopifyAPI::Webhooks::Registry.process` will accept it because the HMAC check only validates the body, not the shop binding, and will invoke the host app's handler with the attacker-chosen `shop` value.

### Finding Description
The `to_signable_string` method used for HMAC verification in `Request` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, by contrast, is read directly from the request header without any cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the HMAC (over the body) and then unconditionally trusts `request.shop`, passing it straight into `WebhookMetadata` for the handler to act on: [3](#0-2) 

`HmacValidator.validate` confirms the signature check is solely over `verifiable_query.to_signable_string` (the body), never incorporating `shop`: [4](#0-3) 

This breaks the intended identity binding: `HMAC(body, api_secret_key) valid` is treated as proof of `(topic, body, shop) all authentic`, when in fact `shop` is never part of the signed material. Since `api_secret_key` is the app's single `client_secret` shared by every shop that installs the app (not a per-shop secret), any one merchant who receives a legitimate webhook to their own callback URL possesses a body+HMAC pair that remains valid for that same app regardless of which shop the header claims. Replaying that captured `(body, hmac)` pair while substituting a different `shop-domain` header value passes `HmacValidator.validate` and reaches the handler with a forged `shop`.

### Impact Explanation
This is a cross-tenant identity confusion: the host application's webhook handler receives `data.shop` it trusts as authentic (because HMAC validation "passed"), but that value was never actually verified. Depending on how the host app uses `data.shop` (e.g., to look up the merchant's access token/session, write incoming order/customer data, or trigger per-shop business logic), an attacker-controlled shop value can cause data to be attributed to, or actions taken against, a shop the attacker doesn't control — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires the attacker to (1) have their own store install the app, legitimately receiving real webhooks with valid HMACs signed by the app's single `api_secret_key`, and (2) know or guess a target shop domain to substitute into the replayed request. Both are low-effort for any actor who can install the target app on their own trial/dev store — no privileged access, leaked secrets, or TLS interception is needed. Some webhook body contents are highly predictable/replayable (e.g., mandatory GDPR/compliance topics or low-entropy topics), increasing practicality.

### Recommendation
Bind the trusted request metadata (at minimum `shop`, and ideally `topic`) into the signable string used for HMAC verification, or otherwise cryptographically tie `shop` to the signature (e.g., verify the HMAC and separately confirm the shop the signature was computed for matches an expected/allow-listed shop that installed the app, sourced from an authenticated lookup rather than the raw header). Document clearly that host applications must not trust `data.shop` from `WebhookHandler#handle` without cross-checking it against their own installed-shop records.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, registering webhook endpoint `https://target-app.example.com/callback/orders/create`.
2. Shopify delivers a legitimate webhook to that URL with headers:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid HMAC of raw body under the app's shared api_secret_key>`
   - body: `{...}`
3. Attacker captures the raw body and the valid HMAC value.
4. Attacker resends the same body and HMAC to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `Request#hmac` decodes the same valid HMAC; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC — see `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:12-31`.
6. `Registry.process` invokes the host handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)` — see `lib/shopify_api/webhooks/registry.rb:198-199` — even though the HMAC never covered `shop`, resulting in the host application processing attacker-supplied data under the victim shop's identity.

          received_signature = verifiable_query.hmac
