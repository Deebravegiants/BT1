### Title
`Pallet::withdraw` zeroes a relayer's accrued `Fees` entry immediately after `dispatch_request` returns `Ok`, without any confirmation that the destination-side disbursement will ever succeed, permanently burning the relayer's reward on delivery failure - (File: modules/pallets/relayer/src/withdrawal.rs)

### Summary
`pallet-ismp-relayer`'s `withdraw` function reads a relayer's accumulated fee balance, dispatches an ISMP POST request instructing the destination chain's host manager (EVM) or `HYPERBRIDGE_MODULE_ID` (substrate) to pay out that amount, and then unconditionally zeroes the source-chain `Fees` entry. `dispatch_request` returning `Ok` only means the message was queued into Hyperbridge's outbound commitment tree — it is not proof that the destination ever executes the disbursement. This is analogous to the Sherlock M-1 finding: an accounting update (`accountRewardDebt` / here, `Fees`) is committed unconditionally even though the corresponding "reward transfer" (the destination-side payout) may fail, timeout, or never be delivered, so a relayer can permanently lose the reward they are entitled to.

### Finding Description
In `Pallet::withdraw` (`modules/pallets/relayer/src/withdrawal.rs`): [1](#0-0) 

the sequence is:
1. Build a `DispatchPost` targeting the destination's host manager / `HYPERBRIDGE_MODULE_ID` with a `WithdrawalParams`/`WithdrawalRequest` body instructing it to pay `available_amount` to `beneficiary_address`.
2. Call `dispatcher.dispatch_request(...)`, mapping only dispatch-level errors to `Error::<T>::DispatchFailed`.
3. Immediately zero the `Fees` entry via `Fees::<T>::insert(withdrawal_data.dest_chain, address.clone(), U256::zero())` — regardless of whether the message is ever delivered, whether the destination's handler executes successfully, or whether it times out.

As documented in the module's own comment block, "The on-chain effect is just dispatching the message; the destination chain settles the payout when the ISMP request is delivered there." That means there is a real window between the state-changing accounting update (zeroing `Fees`) and the actual reward transfer taking effect. There is no `IsmpModule` implementation in this pallet's `lib.rs` handling `on_timeout`/`on_response` for the withdrawal request commitment that would restore `Fees` if the destination rejects the message, if the destination's `host_manager`/`HYPERBRIDGE_MODULE_ID` handler reverts (e.g., insufficient escrowed fee-token balance, a paused/blacklisted disbursement path, or a malformed `WithdrawalParams` decode failure on the EVM side), or if the request times out before delivery. This mirrors exactly the root cause in the Sherlock report: state accounting is finalized optimistically, before/independently of confirmation that the value-transfer step actually succeeded.

### Impact Explanation
If the ISMP POST request carrying the withdrawal instruction fails to be executed on the destination (host manager reverts, times out, or is never delivered because relayers stop relaying it), the relayer's `Fees` balance on the source chain has already been irreversibly set to zero. There is no code path in this pallet that re-credits `Fees` upon timeout or failed delivery. The relayer thus permanently loses their earned fee — a direct, protocol-acknowledged class of value loss identical in mechanism to the referenced M-1 issue (accounting mutated before the actual transfer is guaranteed), and it results in a genuine, unrecoverable loss of relayer reward funds, which is a Medium-severity finding in the funds-accounting category this scan targets.

### Likelihood Explanation
This can be triggered by any relayer performing a normal reward withdrawal whenever the destination-side handling of the dispatched `WithdrawalRequest`/`WithdrawalParams` message fails or times out — a scenario that is realistic in cross-chain messaging (e.g., a temporarily under-funded fee-token escrow on the destination host manager, a paused destination contract, or a delivery timeout under network congestion). No malicious actor or privileged role is required; it is a normal-usage / normal-failure-mode path reachable by any unprivileged relayer calling `withdraw_fees`.

### Recommendation
Do not zero `Fees` synchronously with the outbound dispatch. Instead:
- Track the withdrawal as "pending" keyed by the request commitment returned from `dispatch_request`, and only zero (or decrement) `Fees` once a corresponding delivery confirmation (e.g., a response, or an explicit "settled" callback from the destination) is received.
- Implement an `IsmpModule` handler for `on_timeout` on the withdrawal request's commitment that re-credits the relayer's `Fees` if the destination never processes the disbursement.
- Alternatively, only debit `Fees` after receiving proof of successful destination-side execution, following the same pattern recommended in the referenced report of only mutating accounting state after confirmation of a successful transfer rather than optimistically before it.

### Proof of Concept
1. A relayer accumulates fees via `accumulate_fees`, populating `Fees::<T>::get(dest_chain, relayer_address)`.
2. Relayer calls `withdraw_fees` with a valid signature; `Pallet::withdraw` dispatches an ISMP POST (`WithdrawalRequest`/`WithdrawalParams`) to the destination's host manager / `HYPERBRIDGE_MODULE_ID`, then immediately sets `Fees::<T>::insert(dest_chain, address, U256::zero())` [2](#0-1) .
3. Suppose the destination's host manager fee-token balance is insufficient to disburse `available_amount`, or the request times out before delivery (no relayer relays it in time), or the destination contract is paused. The destination-side handler for the `WithdrawalRequest`/`WithdrawalParams` message fails to pay out the beneficiary.
4. Because no compensating `on_timeout`/failure handler exists in this pallet to re-credit `Fees`, the relayer's `Fees` entry remains permanently zero even though they never received their reward — a proven, unrecoverable loss of funds mirroring the referenced M-1 pattern.
