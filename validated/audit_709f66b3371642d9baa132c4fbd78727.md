### Title
Unbounded recursion in cross-chain `RuntimeCall` decoding causes relayer-triggered stack overflow / node crash - ([File: modules/pallets/hyper-fungible-token/src/module.rs])

### Summary
`Pallet::on_accept` in `hyper-fungible-token`'s `IsmpModule` implementation decodes an attacker-supplied, arbitrary-depth `RuntimeCall` using the plain, depth-unbounded `codec::Decode::decode` call at [1](#0-0) , instead of the depth-limited `decode_all_with_depth_limit` that the codebase itself already uses elsewhere for exactly this bug class. A relayer delivering a crafted cross-chain `PostRequest` with a deeply self-nested `RuntimeCall` (e.g. nested `Sudo`/`Utility::batch`/`Proxy` variants boxing an inner call) can drive the SCALE decoder's recursive descent past the node's stack limit, crashing the runtime — the same "unbounded recursion / stack consumption" bug class as CVE-2017-15595's crafted page-table stacking.

### Finding Description
The `on_accept` handler is reachable by any unprivileged relayer/token bridger who submits an ISMP `PostRequest` to the pallet's registered ISMP module id. When the request's ABI-decoded `Message.data` is non-empty, the pallet decodes `SubstrateCalldata` and then decodes the embedded `runtime_call` bytes directly into `T::RuntimeCall` with:

```rust
let runtime_call = T::RuntimeCall::decode(&mut &*substrate_data.runtime_call)
    .map_err(HftError::RuntimeCallDecodeError)?;
``` [1](#0-0) 

`RuntimeCall` is a recursive enum in any Substrate runtime that includes pallets like `pallet_sudo`, `pallet_utility`, or `pallet_proxy`, whose calls box an inner `RuntimeCall` (`Call::sudo { call: Box<RuntimeCall> }`, etc.). `parity-scale-codec`'s standard derived `Decode` implementation recurses once per nesting level with no depth bound, so a sufficiently deep chain of nested calls in `runtime_call` bytes will exhaust the call stack during decode and crash the node/runtime — before dispatch filtering, signature checks, or any other safeguard in the function even runs.

Critically, this codebase already recognizes and mitigates exactly this bug class elsewhere: `pallet-call-decompressor`'s `decode_and_execute` uses `decode_all_with_depth_limit(MAX_EXTRINSIC_DECODE_DEPTH_LIMIT, ...)` specifically to bound recursion when decoding an untrusted, attacker-supplied `RuntimeCall`: [2](#0-1) [3](#0-2) 

There is even a dedicated regression test in that pallet proving unbounded-recursion decoding is a real, previously-exploitable hazard for this exact `RuntimeCall` type: [4](#0-3) 

However, this depth-limited decode discipline was not applied to `hyper-fungible-token`, which is a separate, unprivileged, network-reachable ISMP entry point that decodes the identical `T::RuntimeCall` type from raw, relayer-controlled bytes with no depth bound and no size cap on `substrate_data.runtime_call` before decoding.

### Impact Explanation
A successful crafted payload crashes the validating/executing node process when the ISMP message is processed (either during off-chain unsigned validation/dispatch, or on-chain execution of `on_accept`), which is a denial-of-service against the chain's block production/relayer path — directly analogous to the Xen hypervisor crash from unbounded recursion in CVE-2017-15595. Because `on_accept` runs during normal ISMP message delivery (not behind any privileged gate), any relayer relaying a message destined for a chain running this pallet can trigger it, potentially halting or repeatedly crashing validator/collator nodes that execute the block, which is a High-severity availability impact on the messaging/token-bridge path.

### Likelihood Explanation
Likelihood is high: the attacker only needs to author a `PostRequest` whose ABI body decodes to a `Message` with non-empty `data`, and whose `data` decodes to a `SubstrateCalldata` with a `runtime_call` byte string encoding deeply nested boxed calls (no valid signature is even required if `substrate_data.signature` is `None`, since the decode-crash happens before dispatch or signature checks matter). The contract-to-asset mapping (`ContractToAsset`) only needs to exist for some registered token/chain pair, which is standard configuration for this pallet, not a privileged precondition for the attacker.

### Recommendation
Replace the unbounded `T::RuntimeCall::decode(...)` call in `on_accept` with a depth-limited decode (e.g. `decode_all_with_depth_limit` from `parity-scale-codec`, using the same or a similarly conservative `MAX_EXTRINSIC_DECODE_DEPTH_LIMIT` constant already defined in `pallet-call-decompressor`), and additionally bound the length of `substrate_data.runtime_call` before decoding to prevent oversized payloads from being processed at all.

### Proof of Concept
1. Construct a deeply nested `RuntimeCall`, e.g. `Sudo::sudo(Box::new(Sudo::sudo(Box::new(... N times ...))))`, with `N` large enough to exceed the default thread stack size when SCALE-decoded (the existing `decompress_stack_exhaustion_poc` test in `pallet_call_decompressor.rs` demonstrates this same nesting pattern with `N = 1000` against the identical `RuntimeCall` type [5](#0-4) ).
2. SCALE-encode the nested call to get `runtime_call_bytes`.
3. Encode `SubstrateCalldata { signature: None, runtime_call: runtime_call_bytes }` and place it as the `data` field of the ABI-encoded `Message` (matching the pattern used in `should_receive_asset_with_calldata` [6](#0-5) ), with `from` set to any 20-byte source address so the "no signature" branch is taken.
4. Submit this as the body of a `PostRequest` from a registered source contract/chain and call (or have a relayer deliver) `HyperFungibleToken::on_accept`.
5. Observe that `T::RuntimeCall::decode` at line 189 recurses without bound while parsing the nested call, exhausting the stack and crashing the node process — unlike the bounded-depth decode path in `pallet-call-decompressor`, which would cleanly reject the same payload with `ErrorDecodingCall`.
