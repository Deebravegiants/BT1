### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by verifying an HMAC over the raw request body, but the `shop` field it hands to the app's handler is taken from an unsigned header. Any party who can obtain one valid `(body, hmac)` pair for the app (e.g., by triggering a webhook on their own installed shop) can replay that pair with an arbitrary `x-shopify-shop-domain` header, causing the library to authenticate the webhook as coming from a different, victim shop.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are read from headers but are excluded from the signed string: [2](#0-1) 

`HmacValidator.validate`/`validate_signature` only recompute and compare the HMAC over `verifiable_query.to_signable_string` (i.e., the body), never over the shop/topic headers: [3](#0-2) 

`Registry.process` accepts the request once `HmacValidator.validate` passes, and then constructs `WebhookMetadata` directly from the unauthenticated `request.shop` value, passing it straight to the app's handler: [4](#0-3) 

The identity binding that is broken is: `shop field trusted by handler == shop field covered by HMAC`. In this codebase that equality does not hold — the HMAC only binds the body bytes to the app's single, app-wide `api_secret_key`; it says nothing about which shop the body is claimed to originate from. Because a Shopify app's webhook secret (`api_secret_key`) is shared across every shop that installs the app (it's not a per-shop secret), any shop that installs the app can generate a body+HMAC pair that is cryptographically valid for the app as a whole, then relabel it with a different shop's domain when replaying it to the app's webhook endpoint.

### Impact Explanation
This is a cross-tenant confused-deputy vector: an unprivileged merchant who has installed the app on their own store can forge a webhook payload/HMAC pair from a legitimate action in their own store, then swap the `x-shopify-shop-domain` (or `shopify-shop-domain`) header to point at a different, unrelated merchant's shop domain before replaying the request to the app's webhook receiver. `Registry.process` will accept it (HMAC validates against the body) and dispatch it to the app's handler with `shop` set to the victim's domain. If the host application's handler trusts `WebhookMetadata#shop` to look up/act on that shop's stored session or data (which is the documented usage pattern for webhook handlers), this allows cross-tenant data manipulation/injection using another merchant's identity, without ever possessing that merchant's credentials.

### Likelihood Explanation
Requires only that the attacker be an unprivileged internet user who can install the target app on any shop (self-installation, e.g., via a free trial or public app listing) to obtain a genuine body/HMAC pair, and then can send an arbitrary HTTP request to the app's public webhook endpoint with a modified shop-domain header — no access token, `api_secret_key`, or privileged account needed. The library itself provides no additional binding of shop-to-signature, so any host app that follows the documented `Registry.process`/`WebhookMetadata` flow inherits this gap.

### Recommendation
Bind the shop identity into the verified payload rather than trusting an unauthenticated header:
- Include the `shop-domain` (and ideally `topic`/`webhook_id`) header value in `to_signable_string`, or otherwise cross-check the header-derived shop against a value embedded in/derived from the signed body.
- Alternatively, document explicitly (and enforce in `Registry.process`) that host apps must independently verify the `shop` header against their own DB of installed shops for that specific webhook, rather than presenting it as pre-authenticated to `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own test shop `attacker-shop.myshopify.com`, obtaining valid webhook deliveries signed with the app's single `api_secret_key`.
2. Attacker captures a legitimate webhook POST — raw body `B` and header `x-shopify-hmac-sha256: HMAC_B` — computed as `OpenSSL::HMAC.hexdigest("sha256", api_secret_key, B)`, per `HmacValidator#compute_signature`.
3. Attacker replays the exact same body `B` and `HMAC_B` to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) recomputes the HMAC over `B` only, matches `HMAC_B`, and returns `true`.
5. `Webhooks::Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) proceeds and calls `handler.handle` with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, even though the payload was never actually sent by or authorized for `victim-shop.myshopify.com`.
