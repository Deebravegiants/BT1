## Title
Unlock/reactivate stake can move real stake pool coins without minting corresponding delegation-pool shares, causing untracked, unrecoverable stake — `buy_in_active_shares` / `buy_in_pending_inactive_shares` in `aptos-move/framework/aptos-framework/sources/delegation_pool.move`

### Summary
`delegation_pool.move` mirrors the exact anti-pattern described in the OtterSec report: it computes a coin amount to move on the *underlying* stake pool independently from the share amount that is supposed to represent ownership of it in the internal `pool_u64` accounting, and both quantities use floor division. When the derived share count floors to zero, the coin movement on the real stake pool still happens, but no shares are credited to any shareholder, permanently desyncing the tracked `total_coins` in the shares pool from the actual balance held by the resource account.

### Finding Description
In `unlock_internal` [1](#0-0) , the amount actually redeemed from `active_shares` is passed straight to the real stake pool via `stake::unlock(&retrieve_stake_pool_owner(pool), amount)` **unconditionally**, and only afterwards is `buy_in_pending_inactive_shares(pool, delegator_address, amount)` called to credit shares in the internal `pending_inactive` `pool_u64` pool for that same `amount`.

`buy_in_pending_inactive_shares` previews the share count first and silently returns 0 — without ever calling the underlying `buy_in` (which increments `total_coins`) — if that preview floors to zero: [2](#0-1) 

The same pattern exists symmetrically for `reactivate_stake` → `buy_in_active_shares`, which calls `stake::reactivate_stake(amount)` first and only afterwards tries to buy shares, again short-circuiting to a no-op when `new_shares == 0`: [3](#0-2) [4](#0-3) 

`amount_to_shares` uses `multiply_then_divide` = `mul_div(coins_amount, total_shares, total_coins)`, which floors to zero whenever `coins_amount * total_shares < total_coins` [5](#0-4) . This happens naturally whenever the destination pool (`pending_inactive` for unlock, `active` for reactivate) has appreciated so that each share is worth more than 1 coin — i.e., whenever the pool has accumulated any rewards at all, which is the normal, expected state of a delegation pool over time.

Concretely: if `pending_inactive_shares_pool.total_shares = 100` and `total_coins = 200` (share price = 2 coins/share), a delegator who redeems `amount = 1` coin from `active_shares` will have that 1 coin moved on the real stake pool (`stake::unlock(1)`), but `amount_to_shares(1) = 1*100/200 = 0`, so `buy_in_pending_inactive_shares` returns early and the `pending_inactive` `pool_u64.total_coins` is never incremented by that 1 coin. The delegator receives zero shares for it — no shareholder now owns a claim to that coin.

This breaks the module's own stated invariant that `total_coins`/`total_shares` in `pool_u64` accurately track the real stake pool balance: `calculate_stake_pool_drift` [6](#0-5)  computes drift as `stake::get_stake(...)` minus the pool's own tracked totals and attributes any positive difference to "rewards," which get redistributed pro rata to whichever shareholders happen to exist in that shares pool at the next synchronization — a different set of owners than the delegator who actually contributed the coin, or nobody at all if the pool is currently empty of shareholders.

### Impact Explanation
This is custody accounting corruption that silently reassigns value to the wrong holder (or to no holder, i.e., permanently unclaimable within the abstraction) without any privileged action — a normal, un-permissioned `unlock`/`reactivate_stake` call from any delegator can trigger it once the target shares pool has appreciated above unit price (any non-zero rewards history). The affected delegator's own coins are moved out of the bucket where they still have shares and into a bucket where they now have none, and are only recoverable indirectly (and only partially, pro rata) if other delegators later hold shares in that pool when the discrepancy is swept up as "rewards" during synchronization.

### Likelihood Explanation
Any active delegation pool that has earned rewards will have a share price above 1 for its `active`/`pending_inactive` pools, which is the common case for long-running validators. Any delegator performing a small `unlock` or `reactivate_stake` (e.g., dust amounts, or amounts chosen deliberately by an attacker to hit the rounding boundary) can trigger the zero-share branch. No special privileges, governance action, or race condition are required — a single unprivileged transaction suffices.

### Recommendation
Compute the coin amount to move on the underlying stake pool from the shares that will actually be credited, not independently of them (mirroring the report's remediation: derive the "balance" leg from the "share" leg, not vice versa). Concretely, in `unlock_internal`/`reactivate_stake`, compute `new_shares = amount_to_shares(amount)` first; if `new_shares == 0`, skip the `stake::unlock`/`stake::reactivate_stake` call as well (treat the whole operation as a no-op), instead of moving real stake and then discovering that no shares can represent it.

### Proof of Concept
1. Set up a delegation pool, have delegator A add stake and let the validator earn rewards until `pending_inactive_shares_pool` (after any prior partial unlock/withdraw cycle) has a share price > 1 coin/share (e.g., `total_shares = 100`, `total_coins = 200`).
2. Delegator A calls `unlock(delegator, pool_address, small_amount)` such that after `coins_to_transfer_to_ensure_min_stake` adjustment, `redeem_active_shares` returns a `coins_amount` (e.g., `1`) satisfying `coins_amount * pending_inactive_total_shares < pending_inactive_total_coins`.
3. Observe: `stake::unlock` moves `coins_amount` from active to pending_inactive on the real stake pool; `buy_in_pending_inactive_shares` returns `0` without calling `buy_in`, so `pending_inactive_shares_pool.total_coins` is unchanged.
4. On the next `synchronize_delegation_pool`, `calculate_stake_pool_drift` observes `stake::get_stake` pending_inactive exceeding the pool's tracked total by `coins_amount`, and this delta is distributed as "rewards" to whatever shareholders currently exist in the pending_inactive pool at that OLC — not necessarily delegator A — demonstrating the loss/misattribution of the original coin.

*Note: I was unable to execute this in a live Move test environment as part of this analysis; the trace above is based on static code review of the cited functions. A background Devin session with Move test tooling would be needed to run `unlock`/`reactivate_stake` under the described share-price conditions and confirm the exact numeric divergence end-to-end.*

    /// Buy shares into the active pool on behalf of delegator `shareholder` who
    /// deposited `coins_amount`. This function doesn't make any coin transfer.
    fun buy_in_active_shares(
        pool: &mut DelegationPool,
        shareholder: address,
        coins_amount: u64,
    ): u128 acquires GovernanceRecords {
        let new_shares = pool.active_shares.amount_to_shares(coins_amount);
        // No need to buy 0 shares.
        if (new_shares == 0) { return 0 };

        // Always update governance records before any change to the shares pool.
        let pool_address = get_pool_address(pool);
        if (partial_governance_voting_enabled(pool_address)) {
            update_governance_records_for_buy_in_active_shares(pool, pool_address, new_shares, shareholder);
        };

        pool.active_shares.buy_in(shareholder, coins_amount);
        new_shares
    }

    /// Return the number of new shares `coins_amount` can buy in `self`.
    /// `amount` needs to big enough to avoid rounding number.
    public fun amount_to_shares(self: &Pool, coins_amount: u64): u128 {
        self.amount_to_shares_with_total_coins(coins_amount, self.total_coins)
    }

    /// Return the number of new shares `coins_amount` can buy in `self` with a custom total coins number.
    /// `amount` needs to big enough to avoid rounding number.
    public fun amount_to_shares_with_total_coins(self: &Pool, coins_amount: u64, total_coins: u64): u128 {
        // No shares yet so amount is worth the same number of shares.
        if (self.total_coins == 0 || self.total_shares == 0) {
            // Multiply by scaling factor to minimize rounding errors during internal calculations for buy ins/redeems.
            // This can overflow but scaling factor is expected to be chosen carefully so this would not overflow.
            (coins_amount as u128) * (self.scaling_factor as u128)
        } else {
            // Shares price = total_coins / total existing shares.
            // New number of shares = new_amount / shares_price = new_amount * existing_shares / total_amount.
            // We rearrange the calc and do multiplication first to avoid rounding errors.
            self.multiply_then_divide(coins_amount as u128, self.total_shares, total_coins as u128)
        }
    }
