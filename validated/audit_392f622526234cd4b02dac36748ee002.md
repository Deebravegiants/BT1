### Title
Webhook shop identity is not covered by the HMAC signature, allowing cross-tenant shop-header spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read straight from HTTP headers that are **not** included in the signed payload. `ShopifyAPI::Webhooks::Registry.process` validates the HMAC and then hands `request.shop` straight to the registered handler as the authoritative tenant identifier, without any binding between the verified bytes (body) and the trusted identity field (shop domain).

### Finding Description
The webhook verification flow is:

1. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which checks the HMAC using `request.to_signable_string`. [1](#0-0) 
2. `Request#to_signable_string` returns only `@raw_body` — the shop domain, topic, webhook id, and API version headers are excluded from the signed content. [2](#0-1) 
3. `Request#shop` simply reads the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, which carries no cryptographic binding to the HMAC at all. [3](#0-2) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`, so downstream app code trusts `shop` as the tenant identity for that event, even though it was never verified. [4](#0-3) 

This breaks the equality the app relies on: `shop authenticated by HMAC == shop used to attribute/store the webhook event`. Concretely: `HMAC(raw_body, client_secret)` is valid ⇏ `shop-domain header` is authentic. An attacker who can obtain any one genuinely-signed webhook body (e.g., by installing the target app on their own store and receiving its own legitimate webhook, which is unprivileged, ordinary merchant behaviour) can replay that exact body to the app's webhook endpoint while substituting an arbitrary `shopify-shop-domain` header value. Since the signature check only re-hashes the untouched body, it will still pass, and the app will process the event as if it belonged to a different (attacker-chosen) shop.

### Impact Explanation
This is a cross-tenant identity confusion: the app's business logic (which typically uses `WebhookMetadata#shop` to look up the session/access token, update per-shop records, or trigger per-shop side effects) can be tricked into attributing a webhook payload to an arbitrary shop domain of the attacker's choosing. Depending on how the host app uses the `shop` value (common pattern: fetch the merchant's stored session by `shop` and act on their store), this enables cross-tenant data manipulation/leakage without needing the app's `client_secret`, an access token, or any privileged account — satisfying the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Any unprivileged user can install a public app on their own development/test store, capture the legitimately-HMAC'd webhook body for a controllable event (e.g., an order/product create on their own store, whose body content they can influence), and replay it against the app's webhook endpoint with a forged `shopify-shop-domain` header pointed at a victim shop. No secret material, TLS interception, or social engineering is required — the flaw is purely due to the header being excluded from the signed content.

### Recommendation
Include the shop domain (and topic/webhook id) in the bytes that are HMAC-verified, or otherwise cryptographically bind the header value to the signed body before it is trusted as tenant identity. Alternatively, cross-check the `shop` header value against an independently-verified source (e.g., a shop already known to be installed via a stored offline session) before allowing handlers to act on it.

### Proof of Concept
1. Install the app on attacker-controlled store `attacker.myshopify.com`; trigger any webhook the app subscribes to and capture the raw POST body and its valid `x-shopify-hmac-sha256` header (both computed by Shopify using the real `client_secret`, which the attacker never needs to know).
2. Replay that exact `raw_body` and `hmac-sha256` header to the app's webhook endpoint, but replace the `shopify-shop-domain` header with `victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/request.rb`/`registry.rb` succeeds because it only re-hashes `@raw_body`, which is unchanged. [5](#0-4) 
4. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` even though the payload actually originated from the attacker's own shop, causing the host application to process/attribute the event under the victim's identity. [4](#0-3)
