### Title
Phantom-order price weighting reads solver balances at floating chain head, letting a flash-inflated balance set the published exchange rate - (File: `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts`)

### Summary
The Hyperbridge intent system publishes a market rate (`PhantomOrderPriceSnapshotV2` → `LiquidityPool.buyRate`/`sellRate`) that real users' orders are quoted against. That rate is a `weightedMedian` of solver bids, where each bid's weight is the solver's live ERC-20 balance of the leg's output token, read at the current chain head rather than at any block committed to by the triggering on-chain event. A solver (an unprivileged, permissionless intent-solver role) can transiently inflate that balance — e.g. via a flash loan — immediately before the off-chain aggregation reads it, win more than half the leg's weight, and force the published median to equal its own quoted price. This is the same bug class as the referenced report's `YAxisVotePower.balanceOf`: a value that gates protocol-wide decisions is computed from an unprotected, instantaneously-manipulable on-chain balance/reserve read instead of a time-weighted or block-pinned one.

### Finding Description
`aggregatePhantomBids` in `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts` builds, per leg, a set of `{price, weight}` entries where the weight is fetched via `getBalance(destUrl, chain, outputToken, solver)`: [1](#0-0) 

Those weighted entries are reduced with `weightedMedian`, which is explicitly documented and tested to hand the published price verbatim to whichever bidder crosses 50% of the total weight: [2](#0-1) [3](#0-2) 

Crucially, the balance read backing this weight is **not pinned to any specific block**. The indexer's own wiring comment states this directly, contrasting the phantom-price sweep with the block-pinned inventory-refresh path used elsewhere: [4](#0-3) 

The design doc for this path independently confirms the weighting mechanism and its consequence: [5](#0-4) [6](#0-5) 

The resulting `medianPrice` is fed into `updateLiquidityPools`, which renormalizes it into the pool's `sellRate`/`buyRate`: [7](#0-6) 

Those pool rates are then the default source real users' orders are quoted against via the SDK's `indexed_rates` strategy: [8](#0-7) 

An attacker acting as an unprivileged solver can:
1. Submit a phantom bid naming an arbitrary price for a leg it wants to control.
2. Flash-loan (or otherwise momentarily acquire) a large balance of that leg's output token on the destination chain — the exact resource the weight reads.
3. Time the balance inflation to be present when the indexer's off-chain job (triggered by `PhantomBidWindowExhausted`, but executed asynchronously against the chain's *current head*, not a pinned block) performs the RPC balance read.
4. Win >50% of the leg's weight, causing `weightedMedian` to return its own named price verbatim as `medianPrice`, which then becomes the pool's published `buyRate`/`sellRate` for every subsequent user quote until the next snapshot.

This mirrors the report's core defect precisely: a value computed from an instantaneously-manipulable on-chain quantity (reserves in the original report, ERC-20 balance here) is used, unguarded by any time-weighting or block commitment, to set a protocol-wide, decision-driving number (voting power there, published market rate here).

### Impact Explanation
The published rate is not cosmetic — it is the default pricing input for real user orders quoted through `quoteIntent`'s `indexed_rates` strategy, and it also directly informs `PoolChainLiquidity`/`LiquidityPool` rows consumed across the indexer/SDK. A manipulated median lets an attacker:
- Publish a rate far off the true market price, causing legitimate users' orders to be under- or over-priced relative to fair value, and
- Potentially profit by having its own (or a colluding) fill executed against the rate it just set, extracting value at the expense of the counterparty or the pool's depth-weighted aggregate (`weightedRate`) that other consumers trust.

This is unauthorized manipulation of a protocol pricing primitive reachable by a single unprivileged actor (a solver bidding on a phantom order), leading to mispriced fills — a concrete value-extraction vector, matching the report's classification.

### Likelihood Explanation
Medium. The attack requires the attacker to (a) hold or flash-loan a large balance of the specific output token on the specific destination chain and (b) have that balance present at the moment the off-chain indexer job executes its RPC read against chain head — a timing window that is not deterministic to the outside observer but is well within reach of an automated bot watching for `PhantomBidWindowExhausted` and racing the indexer's read with a same-block flash loan. It requires per-token capital (or borrowing capacity) rather than governance-token capital, and the signature/verification layer (`isVerifiedSolverBid`) prevents bid spoofing but does nothing to protect the balance weight itself, exactly as the original report's mitigation-debate ("only a trusted EOA/still frontrunnable") applies here too.

### Recommendation
- Pin every balance/position read used for phantom-order weighting to a specific, previously-committed block height (e.g., the height at which `PhantomBidWindowExhausted` fired), the same way `blockReaders`/`inventoryReadContext` already pins event-driven reads. Do not read at floating chain head for anything that feeds a published price.
- Consider requiring the weighting balance to be observed over a short window (a mini-TWAP or multiple samples) rather than a single point-in-time read, so a single-block flash loan cannot dominate the weight.
- Add a maximum-weight-share cap per solver per leg so no single balance snapshot can set the price outright, forcing genuine liquidity depth across multiple solvers to move the median.

### Proof of Concept
1. Attacker registers/controls a delegated solver account and submits a signed phantom bid for leg L naming price `P` (favorable to itself) on chain `C`, output token `T`.
2. Shortly after (or racing) `PhantomBidWindowExhausted` fires on Hyperbridge for that order, attacker takes a flash loan of token `T` on chain `C`, moving a large balance into the solver's EOA.
3. The indexer's `aggregatePhantomBids` run (via `handlePhantomOrderPrices.handler.ts`) calls `getBalance(destUrl, C, T, solver)` at `C`'s current head — landing inside the attacker's flash-loan-inflated window — per `sdk/packages/sdk/src/protocols/intents/phantom-aggregation.ts:1479-1497`.
4. This weight makes the attacker's bid cross 50% of leg L's total weight; `weightedMedian` (`phantom-aggregation.ts:709-724`) returns `P` verbatim as `medianPrice`.
5. Attacker repays the flash loan in the same transaction/block, balance returns to normal.
6. `updateLiquidityPools` writes `P` (renormalized) into the pool's `sellRate`/`buyRate` (`liquidityPool.service.ts:135-143`), and subsequent `quoteIntent` calls using the `indexed_rates` strategy quote real users at the manipulated rate.

//
// Callers must not hand this an entry set whose weights are all zero: with nothing to weight by it
// can only pick a quote by position, and for an even-sized set that position is the upper of the
// two middles — so "the median" becomes "whoever quoted higher", settable by a solver holding no
// inventory at all. aggregatePhantomBids drops such legs instead of pricing them. The fallback
// below stays only so an unguarded caller gets a number rather than a crash; treat reaching it as
// a caller bug.
export function weightedMedian(entries: { price: bigint; weight: bigint }[]): bigint {
	const sorted = [...entries].sort((a, b) => (a.price < b.price ? -1 : a.price > b.price ? 1 : 0))
	const totalWeight = sorted.reduce((acc, e) => (e.weight > 0n ? acc + e.weight : acc), 0n)

	if (totalWeight === 0n) {
		return sorted[Math.floor(sorted.length / 2)].price
	}

	let cumulative = 0n
	for (const entry of sorted) {
		if (entry.weight <= 0n) continue
		cumulative += entry.weight
		if (cumulative * 2n >= totalWeight) return entry.price
	}
	return sorted[sorted.length - 1].price
}

2. Per leg, a solver's quote is weighted by **its balance of that leg's OUTPUT token on the destination chain** — the inventory that actually backs the leg. Zero-weight quotes are dropped entirely, not down-weighted: they never reach the median, `bidCount`, or the bidder list. 3. The leg's price is `weightedMedian` of the backed quotes — a **selection**, not a blend. It returns one bidder's exact integer, so a solver holding over half the leg's weight sets the published price verbatim, and the result can never be a value nobody quoted. `lowestPrice` and `highestPrice` are deliberately overwritten with the median so consumers cannot read an outlier bid as a tradeable bound.

export function poolRateFromQuote(
	medianPrice: bigint,
	resolved: Pick<ResolvedPoolLeg, "inDecimals" | "outDecimals">,
	standardAmount: bigint,
): bigint {
	const scale = 10n ** BigInt(POOL_RATE_DECIMALS - resolved.outDecimals)
	const inputUnit = 10n ** BigInt(resolved.inDecimals)
	return (medianPrice * scale * inputUnit) / standardAmount
}
