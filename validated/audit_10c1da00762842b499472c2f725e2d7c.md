### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` computes the HMAC-signable content from `@raw_body` only [1](#0-0) , while the merchant identity used by `Registry.process` to route and construct `WebhookMetadata` comes from the unauthenticated `shop-domain` header, exposed via `Request#shop` [2](#0-1) . This is the same class of bug as the SIZE report: a field that is *acted upon* (`shop`, used as the tenant identifier) is not *bound* by the HMAC that is supposed to authenticate the request.

### Finding Description
`Utils::HmacValidator.validate(request)` verifies only that `request.hmac` matches `HMAC-SHA256(secret, request.to_signable_string)` [3](#0-2) , and `Request#to_signable_string` returns the raw body verbatim [1](#0-0) . The `topic`, `shop-domain`, `api-version`, and `webhook-id` HTTP headers are read directly off the request and are **not** part of the signed content [4](#0-3) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and `request.topic`) to build the `WebhookMetadata` handed to the app's registered handler: [5](#0-4) 

`WebhookMetadata.shop` is a plain `String` field consumed by the app's `WebhookHandler#handle` implementation [6](#0-5)  as the tenant/session key for whatever action the webhook triggers (e.g., looking up the merchant's session, updating per-shop records, etc., per the gem's documented usage).

**Binding that should hold, but does not:**
`HMAC-verified(body)` ⇒ should imply `shop == the shop that produced that HMAC`. In reality: `HMAC(body)` is independent of `shop`, so `HMAC-verified(body) ∧ shop = X` holds for **any** `X` an attacker chooses to put in the `x-shopify-shop-domain` header, as long as `body` and its accompanying `hmac` were legitimately produced once (by any shop, including the attacker's own).

**Attack path (unprivileged internet user):**
1. Attacker installs the app on their own (free/dev) Shopify store — this is a normal, unprivileged action any internet user can perform once the app is publicly listed/installable.
2. Attacker's store generates a legitimate webhook: `raw_body` + `X-Shopify-Hmac-Sha256` computed by Shopify using the app's real `client_secret`. Attacker captures this request.
3. Attacker resends the same `raw_body` (thus same valid `hmac`) to the app's webhook endpoint, but overwrites `X-Shopify-Shop-Domain` to a victim shop's domain.
4. `HmacValidator.validate` still returns `true`, because the header is not part of `to_signable_string` [1](#0-0) .
5. `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` even though the body/hmac never touched the victim shop [7](#0-6) .

### Impact Explanation
The host application's webhook handler acts under the belief that "HMAC valid ⇒ this event genuinely originated from `shop`." Because `shop` is unauthenticated, an attacker can make the app process attacker-chosen (but validly-signed) webhook bodies while impersonating an arbitrary tenant. Depending on how the host app implements `WebhookHandler#handle` (which is the gem's own documented extension point, using exactly the fields the gem provides), this enables cross-tenant data confusion/injection — e.g., a fake `app/uninstalled`, `orders/create`, or GDPR webhook being attributed to a victim shop, corrupting per-tenant state, revoking/creating sessions for the wrong shop, or triggering shop-scoped side effects for a store the attacker does not own. This falls under the "cross-tenant access" class of Critical impact, since it defeats the shop-identity boundary the HMAC is supposed to guarantee.

### Likelihood Explanation
High feasibility: no privileged credentials, TLS interception, or leaked secrets are required. Any developer/attacker can install the target app on their own store (a normal, unauthenticated action for public apps) to obtain one genuinely HMAC-signed body, then replay it with a forged `X-Shopify-Shop-Domain` header. This requires only basic HTTP tooling.

### Recommendation
Bind the tenant identity into the authenticated material instead of trusting it, e.g.:
- Include `shop`, `topic`, and `webhook_id`/timestamp in the HMAC-signable string (would require a protocol change on Shopify's side), or, since headers can't be changed unilaterally by this gem:
- Cross-check `request.shop` against an independently verified source of truth (e.g., the shop stored for the given `webhook_id` at registration time, or a session lookup) before trusting it, and document clearly that `Request#shop`/`WebhookMetadata#shop` is **not** covered by the HMAC and must not be used as the sole tenant-identity source without additional verification.
- At minimum, surface this constraint prominently in `docs/` and in `WebhookMetadata`'s documentation so host apps do not use `shop` as an unguarded trust boundary.

### Proof of Concept
```ruby
# Attacker's own store install generates a legitimate signed webhook:
raw_body = '{"id": 1, "note": "attacker-controlled payload"}'
real_hmac = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays it, swapping only the shop-domain header (not covered by HMAC):
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => real_hmac,          # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged
  "x-shopify-webhook-id" => "any-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

ShopifyAPI::Utils::HmacValidator.validate(request) # => true, forgery succeeds

ShopifyAPI::Webhooks::Registry.process(request)
# handler.handle(data: WebhookMetadata(shop: "victim-shop.myshopify.com", body: attacker_body, ...))
```
This demonstrates that `Registry.process` accepts and routes an attacker-supplied `shop` claim as authenticated, purely because `Request#to_signable_string` never includes it [1](#0-0) [5](#0-4) .
