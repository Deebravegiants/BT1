### Title
Direct LT donations to a curve `Pair` are permanently and irrecoverably locked — no rescue path exists ([File: packages/contracts/src/Pair.sol], [File: packages/contracts/src/Router.sol])

### Summary
Any LT tokens sent directly to a `Pair` contract via a plain ERC20 `transfer` (rather than through `Zap.buy`/`Zap.sell`) become permanently stuck. Unlike the original Sherlock report — where over-sent stream funds could at least be recovered by calling `cancel()` — alt.fun's `Pair` and `Router` expose **no function at all**, privileged or not, that can withdraw an LT balance in excess of the pair's tracked reserves.

### Finding Description
`Pair.transferAsset` is the only function capable of moving the LT (`assetToken`) out of a `Pair`, and it is gated `onlyRouter`: [1](#0-0) 

`Router` exposes exactly two callers of `transferAsset`:
- `sell()`, which transfers only the `assetOut` computed by the AMM formula for the tokens sold: [2](#0-1) 
- `graduate()`, which transfers only the explicit `amount` passed by `Bonding` — deliberately excluding any donated/over-sent LT so the donation "stays put": [3](#0-2) 

The protocol's own documentation confirms this is a dead end: LT donated directly to a pair "stay[s] in the curve pair under the trust assumption that `BONDING_ROLE` is only ever held by `Bonding`" and is "reachable only via `Pair.transferAsset` which is gated by `Router`'s `BONDING_ROLE`" — but `Bonding` never calls `graduate()` with anything beyond the computed `ltFromPair`, so the excess is never drained: [4](#0-3) 

This is explicitly acknowledged as "unreachable" in the `Router.graduate` natspec itself, framed only as a trust assumption rather than an enforced on-chain guarantee: [5](#0-4) 

Contrast this with `FeeVault`, which has an explicit `sweepDonations()` escape hatch for USDC sent directly to the vault in excess of tracked balances: [6](#0-5) , and with `Bonding`'s post-graduation `_sweepLTToOwner` residue sweep for rebalance dust: [7](#0-6) . No equivalent mechanism exists for the `Pair` contract itself — there is no `Pair.sweep`, no owner-only rescue, and `graduate()`'s amount is always capped below the donation.

### Impact Explanation
Any LT accidentally or intentionally sent directly to a `Pair` (e.g., a user fat-fingering a `transfer` instead of calling `Zap.buy`, or any third party donating LT to "help" the curve) is permanently frozen with no possible recovery — not by the sender, not by the protocol owner, not even after graduation. This is strictly worse than the referenced report's bug, which at least had a `cancel()` escape valve; here there is zero recovery path under any circumstance. This satisfies the "permanent freezing of trader/creator funds" impact bar.

### Likelihood Explanation
Likelihood is moderate: this requires a user or third party to send LT directly to the `Pair` address instead of routing through `Zap`. This can happen from user error (copying the wrong recipient address, using a wallet's raw "send token" flow) or from someone deliberately trying to "top up" a curve they believe needs more liquidity. Given that `Pair` addresses are public and discoverable, and LT is a token users already frequently hold and transfer, this is a plausible unprivileged-actor mistake rather than a contrived edge case.

### Recommendation
Add an explicit sweep/rescue path for excess LT (and TOKEN) balance in a `Pair`, analogous to `FeeVault.sweepDonations()`: compute `assetBalance() - _pool.assetReserve` (and similarly for the token side) and allow a permissionless or owner-gated function to sweep the surplus to a safe destination (e.g., `feeTo`/protocol owner, or refund logic if the sender is identifiable via a donation-registration flow). At minimum, expose an owner-only rescue function on `Router`/`Bonding` that can call a new `Pair.rescueAsset`/`Pair.rescueToken` limited strictly to the excess-over-reserves amount, so donations don't require compromising the "donation resistance" invariants that intentionally exclude them from LP seeding and graduation triggers.

### Proof of Concept
1. A token launches via `Zap.createToken`, creating a `Pair` at address `P` holding virtual/real reserves per normal curve mechanics.
2. A trader (or anyone) calls `LT.transfer(P, X)` directly — a plain ERC20 transfer, bypassing `Zap`/`Router` entirely. `P`'s LT balance is now `reserve1 + X`.
3. Verify no path can recover `X`:
   - `Router.sell()` only ever transfers the AMM-computed `assetOut` for a specific `amountIn` of TOKEN — it cannot target the donated `X` directly. [2](#0-1) 
   - `Router.graduate()` is only invoked by `Bonding` with `amount = ltFromPair` (reserve1 minus the recovered virtual seed), which by construction excludes `X` — confirmed by the existing test `test_graduate_leavesDonationBehind`, which asserts the donation remains locked in the pair after graduation drains only the raised amount. [8](#0-7) 
   - There is no owner/admin rescue function on `Pair` or `Router` targeting `assetToken`/`launchedToken` balances.
4. `X` remains in `P` forever — unlike the referenced Stream bug, there is no `cancel()`-equivalent call that can ever return it to anyone.

```text
    /// @notice Transfer exactly `amount` of LT out of the pair to the caller.
    ///         Called by `Bonding._prepareGraduationLiquidity` during graduation
    ///         with `amount = stored assetReserve - virtualLtReserve` (i.e. the
    ///         real LT raised by the curve, excluding the virtual seed).
    /// @dev    Donation-resistant: passing an explicit `amount` instead of
    ///         draining `assetBalance()` ensures any LT that was donated
    ///         directly to the pair via `IERC20.transfer` is left behind and
    ///         excluded from LP seeding.
    ///
    ///         "Locked" here is a trust-assumption claim, not an on-chain
    ///         guarantee. `Pair.transferAsset` is gated by `onlyRouter`, and
    ///         `Router` only exposes it via this function and `sell`. Both
    ///         require `BONDING_ROLE`, which only `Bonding` holds. `Bonding`
    ///         in turn only calls `graduate` from
    ///         `_prepareGraduationLiquidity` — which is unreachable once the
    ///         token's lifecycle has flipped past `Curve`. So the leftover
    ///         is unreachable as long as (a) `BONDING_ROLE` is not granted
    ///         to any other address, and (b) future `Bonding` upgrades
    ///         preserve the lifecycle gate.
    function graduate(
        address token,
        uint256 amount
    ) external onlyRole(BONDING_ROLE) {
        address asset = assetTokenFor(token);
        address pairAddr = factory.getPair(token, asset);
        if (pairAddr == address(0)) revert PairNotFound();
        IPair(pairAddr).transferAsset(msg.sender, amount);
    }
```

```markdown
### Per-graduation LT isolation

`finalizeGraduation` snapshots `protectedLT = balanceOf(this) - p.ltFromPair` at the top: any LT in `Bonding` beyond this graduation's earmark is either another concurrent graduation's escrow (Phase 1 already moved it in via `Router.graduate`) or stray dust. Both must stay out of THIS graduation's LP and post-sweep.

That snapshot is plumbed through `_seedUniswapV2Direct` → `_seedRebalancing` → `_routerDepositAndDispose`, where the deposit allowance is capped at `balanceOf(this) - protectedLT`. Then a single `_sweepLTToOwner(lt, protectedLT)` at the end of `finalizeGraduation` sends only THIS graduation's rebalance residue to the protocol owner, leaving any concurrent-graduation escrow / stray dust untouched. Honest empty-pair graduations have no residue at the post-sweep so it's a no-op there.

Two scenarios this guards against:

- **Concurrent graduations on the same LT.** Two tokens A and B share an LT and both reach `Lifecycle.Graduating` before either finalizes (the keeper takes ~60s and popular LTs see overlap). Without `protectedLT`, A's finalize would treat the full balance as its own and either sweep B's escrow to the owner (bricking B's later finalize) or — for hostile-pre-seed graduations — deposit it into A's locked LP. With it, A only ever sees `ltFromPair_A` and B is preserved.
- **Cross-token LT residue.** Old residue or a misdirected transfer sitting in `Bonding` would otherwise be visible to `_routerDepositAndDispose`'s `balanceOf(this)` read and could be silently consumed into a future graduation's locked LP. With `protectedLT`, contamination stays in `Bonding` and the deposit only sees this graduation's earmark.

The auto-sweep emits `LTRescued(lt, owner, amount)` for indexer observability. The dedicated regression tests for these edge cases were removed alongside `HostilePreSeed.t.sol`; future changes to `finalizeGraduation` / `_routerDepositAndDispose` / `_sweepLTToOwner` should add targeted coverage if the behaviour is non-obvious from the unit-level tests in `TwoPhaseGraduation.t.sol`.
```
