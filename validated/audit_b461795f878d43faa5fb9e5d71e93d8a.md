### Title
Webhook `shop`/`topic`/`webhook_id` headers are not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, and `Utils::HmacValidator.validate` verifies the HMAC solely against that body. The `shop-domain`, `topic`, `webhook-id`, and `api-version` headers — which `ShopifyAPI::Webhooks::Registry.process` trusts to route and tenant-scope the webhook — are never part of the signed material.

### Finding Description
`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` and compares it with the provided `hmac` field [1](#0-0) . For webhook requests, `to_signable_string` is defined to return only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers via `shopify_header` [2](#0-1) . `Registry.process` validates only the HMAC of the body, then dispatches based on `request.topic` and forwards `request.shop` as the tenant identity into the handler's `WebhookMetadata` without any additional binding check [3](#0-2) .

This reproduces the exact bug class from the analog report: a field that is *acted upon* (the `shop` used to scope/attribute the webhook payload) is *not covered* by the cryptographic authentication (`hmac` over body only). The equality that should hold — `shop asserted by HMAC-signed material == shop used for tenant attribution` — does not hold, because the left side doesn't exist: no shop identity is signed at all.

### Impact Explanation
Any actor who can obtain one genuine, HMAC-valid webhook body/signature pair for *their own* shop (trivial: install the app on a free/dev store and receive one real webhook) can replay that exact body+HMAC to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header naming a victim shop. `HmacValidator.validate` will accept it (the body and secret haven't changed), and `Registry.process` will hand the attacker-chosen `shop` value to the app's handler as if the data genuinely originated from the victim tenant [3](#0-2) . Depending on the handler's logic (e.g., updating local records keyed by `shop`, triggering shop-scoped side effects), this enables cross-tenant data injection/attribution — a Critical-tier impact per the credential/tenant-boundary rules.

### Likelihood Explanation
Exploitation requires only a normal, unprivileged installation of the app (any internet user can install a Shopify app on a store they control) to harvest one legitimate signed body, and standard HTTP tooling to replay it with a modified header — no possession of `api_secret_key` or any elevated credential is needed, since the header is never part of the signed payload.

### Recommendation
Bind the tenant/routing identity into the authenticated material: include `shop`, `topic`, and `webhook_id` in `to_signable_string` (or otherwise cryptographically bind them, e.g. by looking up the expected shop from a server-side registration record rather than trusting the header), so that `HmacValidator.validate` fails if any of these values are altered independently of the body.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; capture one real webhook delivery: raw body `B`, and header `X-Shopify-Hmac-Sha256: H` (valid HMAC of `B` under the app's shared secret) — legitimately produced by Shopify at `lib/shopify_api/webhooks/request.rb` verification time.
2. Replay to the app's webhook endpoint the same `B`/`H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com` and `X-Shopify-Topic` to whatever topic is desired.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [4](#0-3) .
4. `Registry.process` dispatches the registered handler with `WebhookMetadata` carrying `shop: "victim.myshopify.com"` [3](#0-2) , causing the app to act on/attribute data to a shop the attacker does not control.
