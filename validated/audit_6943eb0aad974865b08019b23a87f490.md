### Title
Webhook `shop` domain is not covered by HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` attribute solely from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header [1](#0-0) , while the HMAC signature verified by `Utils::HmacValidator` is computed only over the raw request body via `to_signable_string`, which simply returns `@raw_body` [2](#0-1) . The header is never part of the signed payload.

### Finding Description
`Registry.process` validates the webhook exclusively by checking `Utils::HmacValidator.validate(request)`, which calls `verifiable_query.to_signable_string` (the raw body) against the HMAC header [3](#0-2) . Once validated, the code forwards `request.shop` — taken straight from the (unsigned) `shop-domain` header — into `WebhookMetadata.shop`, which is handed to the app's registered handler as the trusted tenant identifier [4](#0-3) [5](#0-4) .

This breaks the intended identity binding: `shop-header-authenticated == shop-header-bytes-covered-by-HMAC` is false. The HMAC only proves "this body byte sequence was produced with the app's secret"; it proves nothing about which shop-domain header accompanies it. Because the header is attacker-modifiable data in transit to the app's public webhook endpoint, and is not part of the signed content, any request with a body that has a valid signature (for *any* shop using the same app/secret) can be replayed with an arbitrary `shop-domain` header value and will still pass HMAC validation.

### Impact Explanation
An unprivileged internet user who controls their own shop with the app installed (a normal, legitimate installation) receives real webhooks whose HMAC is computed only over the JSON body using the app's shared `client_secret`. Because `shop` is not bound into the signature, that same attacker can replay the captured (body, hmac) pair to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header of a different, victim shop that also has the app installed. The request passes `HmacValidator.validate` and is delivered to the host application's handler tagged with the victim's shop domain via `WebhookMetadata.shop`. Any host logic that uses `data.shop` to look up sessions, attribute data, or trigger tenant-scoped side effects (a very common and encouraged pattern for this SDK, e.g. loading an offline session keyed by shop) will act as if the message genuinely originated from the victim tenant — a cross-tenant identity/data-attribution bypass.

### Likelihood Explanation
Exploitation only requires the attacker to install the app on their own store (self-service, no privileged access needed), capture one webhook delivery, and replay it with a modified header to the app's public webhook URL — a public endpoint by design. No access token, `client_secret`, or victim credentials are required, satisfying the report's severity bar of "cross-tenant access" through an identity-binding gap analogous to the referenced "trusted-but-unauthenticated field" bug class.

### Recommendation
Include the `shop-domain` header (and ideally `topic`/`webhook-id`) in the HMAC-signed material, or otherwise cross-check `request.shop` against a value derivable from the signed body/session before trusting it as the tenant identifier passed to `WebhookHandler#handle`. At minimum, document that host applications must independently verify shop identity (e.g., against an existing offline session) rather than trusting `WebhookMetadata.shop` as authenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; app registers a webhook (e.g. `orders/create`) to a public callback URL.
2. Attacker triggers or captures a legitimate webhook delivery: body `{"id":1}"`, header `x-shopify-hmac-sha256: <valid HMAC over body with app secret>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`.
3. Attacker resends the identical body and HMAC header to the same callback URL, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — this only checks the body/HMAC pair, which is unchanged and still valid [3](#0-2) , then invokes the handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` now returns `"victim-shop.myshopify.com"` [6](#0-5) .
5. The host application processes attacker-controlled webhook data as if it belongs to the victim's tenant.
