### Title
Permanent market freeze via RAY-value overflow in accrual before the borrow-index cap - ([File: contracts/pool/src/interest.rs](contracts/pool/src/interest.rs))

### Summary
CVE-2020-26566 is a remote, unauthenticated crash that kills the whole process via one crafted request. The analog in XOXNO Lending is not a per-request panic (Soroban reverts isolate that), but a state a permissionless caller can push the protocol into where *every* subsequent request on a market panics: a RAY-domain value overflow inside the interest-accrual step. Because every pool mutation accrues first (`interest::global_sync`), once `borrowed × borrow_index` overflows i128 the market is permanently bricked — no repay, withdraw, borrow, liquidation, or cleanup can ever execute on it again.

### Finding Description
`controller::update_indexes` is permissionless (`scripts/permissionless_entrypoints.txt:74`), and every controller verb (`supply`, `borrow`, `withdraw`, `repay`, `liquidate`, `clean_bad_debt`, `recapitalize`) routes through pool calls that run `Cache::load` → `interest::global_sync` (`contracts/pool/src/interest.rs:20-33`). Each chunk calls `accrue_step`, which computes utilization via `scaled_to_original(borrowed, borrow_index)` — a checked `RAY` multiply that panics with `MathOverflow` when the scaled debt value exceeds i128.

`update_borrow_index` clamps the index at `MAX_BORROW_INDEX_RAY` (10^36), but it multiplies *before* clamping and nothing bounds `borrowed × borrow_index`. On a large book (high-decimal asset, ~10^27 scaled units of debt) at sustained high utilization on a steep curve segment, the debt value overflows i128 while the index is still below its cap, so the cap never protects it. The committed test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` demonstrates exactly this: after enough years at 98% utilization, `update_indexes` panics with `MATH_OVERFLOW`, and `withdraw`/`repay` panic with the same error because they accrue first (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:316-361`). `docs/reference/formulas.md:432-437` acknowledges the cliff: "Value overflow can occur before the index ceiling and block repayment/withdrawal because those operations accrue first."

### Impact Explanation
Permanent freezing of funds for every supplier and borrower in the affected market, plus protocol insolvency mechanics: the pool's cash for that asset is locked, suppliers' shares can never be withdrawn, and borrowers can never repay (their collateral in other markets becomes permanently unseizable through normal liquidation of that debt leg). The attacker only needs to supply and borrow their own tokens — all permissionless — and wait; no privileged action is involved. Severity: Medium (high impact, high capital/time precondition).

### Likelihood Explanation
Requires an attacker (or organic growth) to build a book where scaled debt approaches `i128::MAX` — reachable with a high-decimal (18), low-unit-value token under lifted/huge caps — and to hold ~98% utilization for years at a steep rate segment, funded by the attacker's own borrow. Docs note caps "must account for plausible index growth," i.e., mitigation is operational, not enforced in code. A motivated attacker who supplies most of the book can satisfy both preconditions without anyone's cooperation, since `update_indexes` accrual timing is caller-controlled and each chunk reprices utilization at whatever the curve yields.

### Recommendation
Enforce a hard ceiling on scaled market totals: cap `borrowed`/`supplied` scaled shares at `i128::MAX / MAX_BORROW_INDEX_RAY` (i.e., the debt value can never overflow at the index cap) in `supply`/`borrow`/`create_strategy` entry checks, rather than relying on governance-set asset caps. Alternatively, saturate the borrow index at a lower effective ceiling chosen so the maximum admitted scaled debt cannot overflow, or make `accrue_step` clamp the accrued debt value instead of panicking.

### Proof of Concept
Reproduced by the in-repo test `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs::a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap`:

```rust
let principal = BILLION * 10i128.pow(18);          // whale supply, attacker's own funds
t.supply_raw(BOB, "BIG18", principal);             // permissionless supply
let debt = principal / 100 * 98;                   // 98% utilization
t.borrow_raw(ALICE, "BIG18", debt);                // permissionless borrow
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; } // permissionless accrual
}
// => Error(Contract, MATH_OVERFLOW) while borrow_index < MAX_BORROW_INDEX_RAY
// => try_withdraw_raw(BOB, ...) and try_repay(ALICE, ...) both panic: market frozen
```

Call path: `controller::update_indexes` → `pool::update_indexes` → `Cache::load` → `interest::global_sync` → `accrue_step` → `utilization` → `scaled_to_original` panics. The same panic is hit by every later `withdraw`/`repay`/`liquidate`/`clean_bad_debt` touching that market because each accrues first — a permanent, attacker-induced denial of service analogous to the crafted-request process kill of CVE-2020-26566.
