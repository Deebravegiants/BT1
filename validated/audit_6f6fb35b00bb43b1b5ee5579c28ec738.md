## Finding

The root cause: the Tron deployment of `IntentGatewayV2.placeOrder` credits escrow using the *requested* input amount (minus protocol fee) rather than the amount the contract *actually receives*, unlike the canonical EVM implementation which was explicitly hardened against this exact bug class.

### Title
Fee-on-transfer / deflationary `depositToken` inputs cause escrow over-crediting in Tron `IntentGatewayV2.placeOrder` - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
In the Tron contracts port of `IntentGatewayV2.placeOrder`, when a user places an order without a predispatch call, the gateway transfers input tokens with `safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` and then credits `_orders[commitment][token] += reducedInputs[i].amount`, where `reducedInputs[i].amount` is derived from the *requested* `order.inputs[i].amount` (minus protocol fee), not from the tokens actually received.

### Finding Description [1](#0-0) 

For a deflationary/fee-on-transfer `depositToken`, `safeTransferFrom` delivers `amount - transferFee` to the gateway, but the escrow ledger `_orders[commitment][token]` is still incremented by the full `reducedInputs[i].amount` computed from the pre-transfer `order.inputs[i].amount`: [2](#0-1) 

This is a direct regression against the canonical EVM `IntentGatewayV2.sol`, which was explicitly hardened to measure actual received balance and mutate `order.inputs[i].amount` accordingly before computing the commitment/escrow: [3](#0-2) 

The accompanying comment in the canonical version confirms the intended invariant that was dropped in the Tron port: [4](#0-3) 

The predispatch branch of the Tron contract does correctly bound dust via `balance - requiredAmount` checks against the dispatcher's real balance, but the common non-predispatch path (the one every plain `placeOrder` call without calldata takes) has no such check.

### Impact Explanation
Every order placed with a fee-on-transfer/deflationary token via the no-predispatch path records escrow liability for tokens the gateway never actually holds. This creates a solvency gap between aggregate `_orders[...]` liabilities and the gateway's real token balance. Later redemptions (`_withdraw` via `RedeemEscrow`/`fillOrder`/cancellation, in `IntentsBase._withdraw`) will pay out the inflated escrowed amount: [5](#0-4) 

Since escrow is a shared pool of `IERC20(token).safeTransfer` calls, later legitimate withdrawers for other commitments can find the contract has insufficient balance (reverted, funds frozen) while faster withdrawers effectively drain balance belonging to other users' escrowed deposits — a concrete theft/permanent-freezing-of-funds condition affecting the token bridge/intents escrow accounting.

### Likelihood Explanation
Any depositor can trigger this simply by using a fee-on-transfer or rebasing/deflationary ERC-20 as an order input token — no privileged role or governance action is required, and the no-predispatch path is the default, most common call path for `placeOrder`. On chains/tokens where such deflationary tokens exist (a known token class explicitly called out and already handled on the primary EVM deployment), exploitation requires only a single `placeOrder` transaction.

### Recommendation
Mirror the canonical EVM `IntentGatewayV2.sol` fix in the Tron contract: measure the gateway's token balance before and after `safeTransferFrom` in the non-predispatch branch, and derive `reducedInputs`/escrow credit from the actually-received amount (`balanceAfter - balanceBefore`) rather than the caller-supplied `order.inputs[i].amount`, consistent with lines 312-329 of `evm/src/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Deploy a 1% fee-on-transfer ERC-20 token `FOT` on the Tron-deployed `IntentGatewayV2`.
2. User calls `placeOrder` with `order.inputs = [{token: FOT, amount: 1000e18}]` and no predispatch call.
3. `safeTransferFrom` delivers only `990e18` FOT to the gateway (line 459), but `_orders[commitment][FOT]` is credited `990e18` only if there is 0% protocol fee and `reducedInputs[i].amount == order.inputs[i].amount`; more generally the credited amount is `order.inputs[i].amount * (10000 - protocolFeeBps)/10000` (e.g., `1000e18` at 0 bps), not `balanceAfter - balanceBefore` — i.e., the escrow is credited based on the pre-fee-on-transfer amount, exceeding actual gateway holdings by the token's transfer-fee percentage.
4. When the order is filled/redeemed, `_withdraw` attempts to `safeTransfer` the recorded escrow amount, exceeding what the gateway actually holds for that token, causing insolvency that either reverts other users' legitimate withdrawals or lets a faster claimant drain tokens escrowed for other commitments. The equivalent test suite (`evm/tests/foundry/IntentGatewayV2SameChainTest.sol`, e.g. `testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived`) explicitly validates the *correct* behavior only on the primary EVM contract, confirming no equivalent protection/tests exist for the Tron port's non-predispatch path.         address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {

            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            _orders[body.commitment][token] = escrowed - amount;

                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
