### Title
Post-launch LT exchange-rate depreciation lets curve-raised LT balloon past `uint112`, silently truncating the graduated HyperSwap V2 pair's reserves - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._deployAndSeed` bounds `virtualLtReserve` at launch to `type(uint112).max/4` because the eventually-graduated HyperSwap V2 pair stores reserves as `uint112` [1](#0-0) . That bound is sized against the launch-time `exchangeRate()` on the assumption that the real LT raised by the curve "peaks at 3× virtualLtReserve" [2](#0-1) . But the USD graduation trigger is evaluated with the *current*, not launch-time, `exchangeRate()`: `realLtRaised = assetReserve - virtualLtReserve; valueUsd = realLtRaised * exchangeRate() / 1e18 >= graduationThresholdUsd` [3](#0-2) . If the LT's `exchangeRate()` drops materially between launch and graduation (a leveraged token can lose most of its value quickly), the *raw LT-token* amount needed to reach the fixed `$9K` USD threshold grows well beyond the `3×`/`4×`-headroom assumption baked into the one-time launch check, so `assetReserve` (and thus `ltFromPair`) can exceed `type(uint112).max` by the time `_prepareGraduationLiquidity`/`finalizeGraduation` seeds the HyperSwap V2 pool.

### Finding Description
`_deployAndSeed` performs the only overflow guard in the whole graduation lifecycle, and it is a *launch-time* snapshot:
```solidity
uint256 exchangeRate = IBounceLeveragedToken(ltAddress).exchangeRate();
if (exchangeRate == 0) revert ZeroExchangeRate();
uint256 virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate;
if (virtualLtReserve > type(uint112).max / 4) revert ExchangeRateTooLow();
``` [1](#0-0) 

The comment explicitly frames the 4× headroom against the assumption that "the raised LT reserve peaks at 3 × virtualLtReserve (curve sell-out)" [2](#0-1) , i.e. it implicitly treats `exchangeRate()` as static from launch to graduation. In reality the graduation USD trigger recomputes `realLtRaised * exchangeRate()` with the *live* rate at the moment of the triggering buy or `triggerGraduation` call [3](#0-2) . Since the threshold is fixed in USD (`$9K`) but the LT is an externally-priced, rebasing/leveraged asset whose rate can fall sharply after launch, the number of raw LT tokens the curve must accumulate to hit that same USD value grows inversely with the rate drop — unboundedly in the worst case, since nothing re-checks the bound against the *current* rate before or during `_enterGraduating` → `_prepareGraduationLiquidity` → `Router.graduate`/`finalizeGraduation`:
```solidity
ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
if (ltFromPair > 0) { _s().router.graduate(tokenAddress, ltFromPair); }
tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
``` [4](#0-3) 

`ltFromPair` then flows into `_seedUniswapV2Direct`'s deposit leg, ultimately calling the HyperSwap V2 router's canonical `addLiquidity`, which mints against the pair's own `_update()` — where standard UniswapV2-fork pairs write `reserve0/reserve1 = uint112(balance0/balance1)` with a bare, unchecked cast (no `SafeCast`), silently wrapping any value above `2**112 - 1`. This mirrors CVE-2019-9210's root cause: a size/quantity that should have been bounds-checked at the point of use is instead validated once against a stale assumption, and when that assumption is violated the value is written into a storage slot too small to hold it, corrupting downstream state (here, the graduated pool's stored reserves) rather than merely reverting.

### Impact Explanation
A wrapped/truncated `uint112` reserve in the freshly-seeded HyperSwap V2 TOKEN/LT pool desynchronizes the pair's stored reserves from its real token balances. Any subsequent swap against that pair is priced off the wrapped (much smaller) reserve while the pool actually custodies the full, un-wrapped LT balance, letting a trader drain LT out of the pool for a fraction of its true value — permanent theft of the LP funds locked in `LPLock` (which has no rescue path in v1) and of the curve-raised value that was supposed to back the graduated pool. This satisfies "concrete theft ... of LP funds" and "an LP seeded away from the curve close price."

### Likelihood Explanation
No attacker action is required to trigger the underlying condition — normal, permissionless trading against `Bonding.buy`/`Zap.buy` accumulates `assetReserve`, and a market-driven decline in the paired LT's `exchangeRate()` (leveraged tokens are, by construction, exposed to rapid drawdowns) is enough to blow the raw-LT accumulation past the `4×` headroom that was only checked once, at launch, against the then-current rate. An attacker can also proactively pick/launch against an LT whose rate is already near the `type(uint112).max/4` launch-time ceiling and then simply wait for (or, if they have any influence over the LT's price feed, help along) a rate drop before the curve's USD threshold is hit, maximizing the raw-LT accumulation relative to the bound. Reaching `uint112` (~5.19e33 in 18-decimal terms) requires an extreme rate collapse, which bounds the realistic likelihood, but the guard as written provides no protection against exactly this scenario, which the code's own comments show the team anticipated protecting against (just at the wrong point in time).

### Recommendation
Re-validate the `uint112` bound at the point the LT amount is actually consumed for graduation/LP-seeding (`_prepareGraduationLiquidity`/`_enterGraduating`), using the *current* `exchangeRate()` and the *actual* accumulated `assetReserve`/`ltFromPair`, not just the launch-time snapshot. If `ltFromPair` (or `virtualLtReserve + ltFromPair`) would exceed `type(uint112).max` at seeding time, either cap the amount deposited into the HyperSwap pair (e.g. via `Router.buy`'s existing overflow-cap pattern, extended to the graduation LT leg) or revert/park the excess rather than allowing an unchecked amount to reach `addLiquidity`.

### Proof of Concept
Conceptual repro (would need to be run against `test/GraduationInvariants.t.sol`'s harness, which already has the exact helpers used here):
1. Launch a token against an LT with `exchangeRate()` set just under `VIRTUAL_LIQUIDITY_USD*1e18 / (type(uint112).max/4)` so `_deployAndSeed` passes.
2. Buy on the curve to accumulate `assetReserve` toward, but below, the USD threshold at the current rate (mirrors `_ltStageBeforeGraduation()` in `test/GraduationInvariants.t.sol`).
3. Call `lt.setExchangeRate(...)` to drop the rate sharply (simulating a leveraged-token drawdown) — analogous to how the existing invariant tests already flip `exchangeRate` up (`_ratePumpForStagedGraduation`) to trip the USD trigger early; here the rate is instead dropped so far that the *raw LT amount* required to still hit `$9K` balloons past `type(uint112).max`.
4. Submit one more buy (or call `bonding.triggerGraduation`) to cross the USD threshold; `_enterGraduating`/`_prepareGraduationLiquidity` computes `ltFromPair` at the now-huge raw-LT value.
5. `finalizeGraduation` seeds the HyperSwap V2 pair with this oversized `ltFromPair`; the mock/production pair's `_update` truncates it via `uint112(...)`, producing stored reserves inconsistent with the real balance, which a subsequent swap can exploit.

Note: full on-chain confirmation of the truncation step depends on the exact (out-of-scope) HyperSwap V2 pair bytecode's `_update` implementation, which could not be directly inspected in this repo (HyperSwap V2 itself is excluded from scope) — the alt.fun-side root cause (a stale, launch-time-only bound feeding an unguarded amount into `addLiquidity`) is confirmed in `packages/contracts/src/Bonding.sol`.

    function _prepareGraduationLiquidity(
        address tokenAddress
    ) internal returns (uint256 tokensForLP, uint256 ltFromPair, uint256 lpBurned, uint256 unsoldBurned) {
        address pairAddr = _s().tokenInfo[tokenAddress].pair;
        (uint256 tokenReserve, uint256 assetReserve) = IPair(pairAddr).getReserves();

        unsoldBurned = IPair(pairAddr).tokenBalance();
        if (unsoldBurned > 0) {
            Token(tokenAddress).burn(pairAddr, unsoldBurned);
        }

        ltFromPair = assetReserve - _launchTimeVirtualLtReserve(tokenAddress, pairAddr);
        if (ltFromPair > 0) {
            _s().router.graduate(tokenAddress, ltFromPair);
        }

        tokensForLP = assetReserve == 0 ? 0 : (ltFromPair * tokenReserve) / assetReserve;
        if (tokensForLP > LP_RESERVE) tokensForLP = LP_RESERVE;

        lpBurned = LP_RESERVE - tokensForLP;
        if (lpBurned > 0) {
            Token(tokenAddress).burn(address(this), lpBurned);
        }
    }
```
