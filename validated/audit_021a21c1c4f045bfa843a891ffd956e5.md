### Title
Webhook shop identity spoofing via unauthenticated `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `Utils::HmacValidator.validate` never covers the `shop-domain`, `topic`, or `webhook-id` headers. `Webhooks::Registry.process` nonetheless treats `request.shop` as the authenticated tenant identity and hands it straight to the app's handler. Because the app's `api_secret_key` used for HMAC signing is the same for every shop that installs the app, a merchant who legitimately receives a validly-signed webhook for their own shop can replay that exact `(body, hmac)` pair while substituting a different shop's domain in the header, and the library will accept it as authentic.

### Finding Description
The identity binding that should hold is: **shop authenticated by the HMAC == shop the handler is told the event belongs to**. That binding is broken here.

- `Request#to_signable_string` only returns `@raw_body`: [1](#0-0) 
- `shop` is read from an unauthenticated header with no cryptographic tie to the signed body: [2](#0-1) 
- `HmacValidator.validate` computes the signature purely from `to_signable_string`, i.e. the body, using the app-wide (not shop-specific) `Context.api_secret_key`: [3](#0-2) 
- `Registry.process` only checks that HMAC, then forwards the attacker-controlled `request.shop` (and `topic`, `webhook_id`) to the handler as trusted metadata: [4](#0-3) 

Since `api_secret_key` is shared across all shops for a given app (it is the app's client secret, not a per-shop key), any merchant who has installed the app can trigger a legitimate webhook to their own endpoint, capture the valid `(raw_body, x-shopify-hmac-sha256)` pair Shopify sent them, and resend it to the app with the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header replaced with a victim shop's domain. `HmacValidator.validate` still passes because it only re-derives the signature from the body, which is unchanged. The app then dispatches the event as if it came from the victim shop, with attacker-controlled body content.

### Impact Explanation
This crosses a tenant boundary: an app relying solely on this gem's webhook processing can be made to attribute attacker-controlled event data to a different, victim shop. Depending on how the host app uses `WebhookMetadata#shop` (e.g. to look up the shop's session/access token, update shop-scoped records, or trigger shop-scoped side effects), this enables cross-tenant data injection/corruption under another merchant's identity — a High severity cross-tenant access issue.

### Likelihood Explanation
Likelihood is high for any developer who has installed (or can install) the target app on their own shop, since that is the only prerequisite. No access token, `client_secret`, or privileged account is needed — only a normal, unprivileged install of the app, which is the standard entry point for any Shopify merchant.

### Recommendation
Bind the shop (and topic/webhook id) identity to the HMAC-verified payload instead of trusting unauthenticated headers: either include the `shop-domain` (and `topic`) in the signable string used for HMAC validation, or require the caller to cross-check `request.shop` against the shop resolved independently (e.g. via the session/store lookup keyed by an authenticated identifier) before invoking the handler.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com`.
2. Attacker triggers any webhook-eligible action (e.g. creates an order with attacker-controlled fields) so Shopify delivers a webhook POST to the app, signed with the app's shared `api_secret_key`. Attacker records the exact `raw_body` and `x-shopify-hmac-sha256` value.
3. Attacker resends this exact `raw_body`/`x-shopify-hmac-sha256` pair to the app's webhook endpoint, changing only:
   - `x-shopify-shop-domain: victim.myshopify.com`
4. `Utils::HmacValidator.validate` recomputes the HMAC from `raw_body` only [5](#0-4)  — it matches, since the body is untouched.
5. `Registry.process` invokes the handler with `shop: "victim.myshopify.com"` [6](#0-5) , causing the host application to process attacker-controlled body content under the victim shop's identity.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
