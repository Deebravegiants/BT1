### Title
Webhook `shop` domain header is not covered by the HMAC signature, allowing cross-tenant shop-identity spoofing of otherwise-valid webhook payloads - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely by HMAC-signing the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values are read from unauthenticated headers and are never included in the signed payload, so any request whose body+HMAC pair is valid for a given shop can be replayed with a different `x-shopify-shop-domain` header and will still pass verification, but be attributed to a different shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` value is pulled straight from the `x-shopify-shop-domain` / `shopify-shop-domain` header without any cryptographic binding to the body: [2](#0-1) 

`Registry.process` verifies the HMAC over `request.to_signable_string` (i.e. the body only) via `Utils::HmacValidator.validate`, and then hands `request.shop` — an unverified header — directly to the app's handler as authoritative tenant identity: [3](#0-2) [4](#0-3) 

The identity binding that should hold is:
`shop header value == shop that produced/authorized the signed body`

but the gem only proves:
`HMAC(body, api_secret_key) == received_hmac`

with no constraint tying the `shop-domain` header to that computation. This lets an attacker who possesses one legitimately-signed `(body, hmac)` pair — trivially obtainable by installing the app on their own store and receiving a real webhook — resend the exact same body and HMAC to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value (e.g. a victim merchant's domain). `Registry.process` will still validate the HMAC and dispatch to the handler with `WebhookMetadata#shop` set to the attacker-chosen domain, per the documented handler contract: [5](#0-4) 

Since host applications are documented to use `data.shop` as the tenant key for storing/acting on webhook data (as shown in the gem's own example, `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), this breaks the tenant isolation the HMAC check is meant to guarantee. [6](#0-5) 

### Impact Explanation
This enables cross-tenant confusion: an attacker who installs the app on their own shop (an unprivileged, standard merchant action requiring no special credentials, access token, or knowledge of `api_secret_key`) can capture a real webhook delivery for their own store and replay it against the same public webhook endpoint with the `shop-domain` header changed to a victim shop. The HMAC check still passes (it is only over the body), so the application processes attacker-controlled data as if it originated from — and applies it to — a different tenant. Depending on how the host app keys its data by `shop`, this can corrupt or leak data across tenants, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Likelihood is moderate to high: obtaining a valid `(body, hmac)` pair requires only installing the app on any shop (which any user can do for a public app) and capturing one real webhook delivery; no `api_secret_key`, access token, or privileged access is needed. The replay itself is a simple HTTP POST with a modified header against the app's public webhook route.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the signed material verified against the HMAC, or independently corroborate the `shop` header against a value derived from the (signed) webhook body/metadata before trusting it as the tenant identity. At minimum, document that `data.shop` from `WebhookMetadata` is not cryptographically bound to the payload and must not be used as the sole tenant key without additional verification (e.g., cross-checking against the shop associated with the resource IDs in the body via a separate authenticated API call).

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a subscribed webhook topic (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header from the real delivery.
2. Attacker replays the exact same body and HMAC header to the app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` parses the forged header; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (body only) and matches successfully (the body/HMAC pair is genuinely valid).
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, and the host application processes/stores the attacker's data under the victim shop's tenant record.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
