## Title
Cross-context HMAC signature reuse allows forging webhook requests for arbitrary shops/topics using OAuth callback signatures - ([File: lib/shopify_api/utils/hmac_validator.rb], [File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/auth/oauth/auth_query.rb])

### Summary
`Utils::HmacValidator` computes an HMAC-SHA256 over a `signable_string` using the shared `Context.api_secret_key`, with no domain separation between the different message types the gem signs/verifies. `Auth::Oauth::AuthQuery#to_signable_string` produces a URL-encoded key/value string, and `Webhooks::Request#to_signable_string` returns the raw HTTP body verbatim. Because both simply feed arbitrary bytes into the same keyed HMAC function, an attacker who legitimately obtains one type of signed message (an OAuth callback URL, which is delivered to the browser and is not secret) can replay those exact bytes as the body of a forged webhook POST. Since the webhook signature only covers the body — never the `shop-domain` or `topic` headers — the attacker can freely set those headers to impersonate any shop and any webhook topic while still passing HMAC validation.

### Finding Description
`HmacValidator.validate_signature` verifies signatures generically for any object satisfying `Utils::VerifiableQuery`: `computed_signature = compute_signature(verifiable_query.to_signable_string, secret)` compared against `verifiable_query.hmac`. [1](#0-0) 

`AuthQuery#to_signable_string` builds a query string from `code`, `host`, `shop`, `state`, `timestamp` — values that are returned to the browser as part of the OAuth redirect and are visible to whoever completes the flow (e.g. any merchant/developer installing the app on any shop): [2](#0-1) 

`Webhooks::Request#to_signable_string` simply returns the raw HTTP request body, and `hmac` reads only the `hmac-sha256` header — the `shop-domain` and `topic` headers used later for dispatch are never part of the signed material: [3](#0-2) 

`Webhooks::Registry.process` validates only the HMAC of the body, then dispatches to the handler using the unauthenticated `topic` and `shop` headers directly from the request: [4](#0-3) 

Because both `AuthQuery` and `Webhooks::Request` are HMAC'd with the exact same key (`Context.api_secret_key`) and the exact same algorithm (`OpenSSL::HMAC.hexdigest` with SHA-256, only differing in hex vs base64 encoding of the digest — a purely cosmetic difference the attacker can trivially convert), there is no cryptographic domain separation between "this is a signed OAuth callback" and "this is a signed webhook body." The intended equality that should hold is: *bytes verified by the webhook HMAC == bytes the handler trusts as originating from Shopify for a specific (shop, topic) pair*. Instead, the verified bytes can be any previously-observed HMAC'd payload from a *different* protocol context, and the (shop, topic) pair is taken from unauthenticated headers, breaking that equality — directly analogous to the `DOMAIN_TYPEHASH` finding, where signing a struct without full context-binding fields allowed a signature computed for one purpose to be replayed for another.

### Impact Explanation
An attacker who has ever completed (or observed) an OAuth authorization callback for the app — something any user can trigger by simply installing the app on any shop they control — obtains a `(code, host, shop, state, timestamp, hmac)` tuple signed with the app's `api_secret_key`. They can:
1. Reconstruct `signable_string = URI.encode_www_form({code:, host:, shop:, state:, timestamp:})` (deterministic, alphabetical order).
2. Convert the hex `hmac` to raw bytes and base64-encode it to match the webhook header format.
3. POST that exact body to the app's webhook endpoint with attacker-chosen `x-shopify-shop-domain` and `x-shopify-topic` headers (e.g., impersonating a victim shop for `app/uninstalled`, `shop/redact`, `customers/redact`, or any business-logic topic the app registers).

`Utils::HmacValidator.validate` will succeed because it only checks the body bytes, and `Registry.process` will invoke the app's handler with `WebhookMetadata` claiming an arbitrary `shop` and `topic` of the attacker's choosing. Handlers that key off `shop`/`topic` alone (mandatory compliance webhooks, deprovisioning, entitlement/billing webhooks) can be triggered against a shop the attacker does not control — a cross-tenant forgery that fits the Critical "cross-tenant access" impact category without requiring the app's secret, an access token, or any privileged credential.

### Likelihood Explanation
Likelihood is high: obtaining a valid OAuth callback tuple requires nothing more than installing the app once (an action available to any unprivileged internet user with a free Shopify dev shop), and the byte/format conversion needed to reuse it as a webhook body is trivial (hex→raw→base64). No secrets, tokens, or privileged access are needed — only knowledge of the gem's public signing scheme, which is documented behavior.

### Recommendation
Introduce domain separation so signatures from one protocol context cannot be replayed in another:
- Bind the HMAC to a context-specific prefix/domain identifier (e.g., include a constant string like `"oauth-callback"` or `"webhook"` in the signed material) so `AuthQuery` and `Webhooks::Request` signatures are never interchangeable.
- Include the security-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the webhook's signable material (or otherwise cryptographically bind them), rather than trusting them unauthenticated in `Webhooks::Request#shop`/`#topic`.
- Consider using distinct keys derived from `api_secret_key` per message type (e.g., via HKDF with a context label) instead of reusing the raw secret directly across all HMAC use cases in the gem.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and completes OAuth; the browser redirect includes `code`, `host`, `shop`, `state`, `timestamp`, `hmac` as visible query parameters (per `AuthQuery`, [5](#0-4) ).
2. Attacker computes `body = URI.encode_www_form({code:, host:, shop:, state:, timestamp:})` (same construction as `to_signable_string`).
3. Attacker computes `header_hmac = Base64.encode64([hmac].pack("H*"))` to convert the hex `hmac` value into the base64 raw-digest form expected by `Webhooks::Request#hmac` ( [6](#0-5) ).
4. Attacker sends `POST /webhooks` with body = `body`, headers `x-shopify-hmac-sha256: header_hmac`, `x-shopify-shop-domain: victim-shop.myshopify.com`, `x-shopify-topic: app/uninstalled`.
5. `Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `to_signable_string` (the body) against the same secret used to sign step 1's OAuth callback ( [7](#0-6) ). The handler is then invoked with `shop: "victim-shop.myshopify.com"` and `topic: "app/uninstalled"`, despite the attacker having no relationship to `victim-shop`.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end

            secret,
            signable_string,
          )
        end
