### Title
Unvalidated swap routes can steal unrelated user-wallet tokens through hidden authorization - ([File: contracts/controller/src/strategies/swap.rs])

### Summary
The controller accepts caller-supplied opaque `swap` bytes and forwards them to the configured swap router, while validating only the controller’s input spend and output receipt. A malicious route can therefore place attacker-controlled code below the victim’s `swap_collateral` authorization and request an unrelated `token.transfer(victim, attacker, amount)`; simulation records that transfer as a child authorization, and the transfer executes if the victim signs the poisoned tree.

### Finding Description
`swap_collateral` authorizes `caller`, verifies account ownership or delegation, and passes the caller-controlled `swap` argument into `withdraw_and_swap_from_supply` without inspecting its encoded venues. `swap_tokens` loads the configured router, authorizes only `token_in.transfer(controller, router, amount_in)` on behalf of the controller, and invokes `execute_strategy(controller, amount_in, swap)`. Afterward it rejects controller overspending and requires positive measured `token_out`, but neither check limits what route-selected contracts ask the original caller to authorize. The repository’s authorization-tree proof shows that a route-selected pool can call `token.transfer(victim, attacker, amount)`; recording mode attaches that call beneath the victim’s `swap_collateral` invocation, and enforcing mode executes it when the returned child authorization is signed.

### Impact Explanation
An attacker can steal token balances unrelated to the lending collateral being swapped. The protocol’s collateral accounting can still complete normally because the malicious venue only needs to return enough `token_out` for the post-swap risk and positive-output checks; the additional victim-wallet transfer is outside the controller balance delta being measured.

### Likelihood Explanation
Exploitation requires the victim to submit or sign a malicious route and then authorize the simulation-generated child transfer. This is a realistic phishing/frontend-risk path: the victim sees a valid collateral swap, while the signed authorization tree also contains an unrelated wallet-token transfer that neither the route’s minimum output nor the account solvency gate bounds.

### Recommendation
Do not allow route payloads to reach arbitrary venue contracts. Enforce a governance-managed venue allowlist or fixed adapter dispatch in the swap router, and reject route fields containing unapproved pool, token, or callback addresses. Clients should additionally refuse authorization trees containing anything other than the expected input transfer as a defense-in-depth measure, but user-side inspection should not be the protocol’s only protection.

### Proof of Concept
1. The victim owns lending account `account_id` with USDC collateral and also holds `wallet_token` unrelated to the protocol.
2. The attacker crafts `swap` bytes whose route reaches an attacker-controlled venue configured to execute `wallet_token.transfer(victim, attacker, wallet_token.balance(victim))`.
3. The attacker causes the victim to invoke:
   `controller.swap_collateral(victim, account_id, usdc_hub_asset, collateral_amount, eth_hub_asset, malicious_swap)`.
4. The controller checks the victim’s authorization and account authority, then forwards `malicious_swap` to the configured router.
5. Simulation records the venue’s unrelated transfer as a child of the victim’s `swap_collateral` authorization; signing that tree authorizes it.
6. The venue returns enough ETH output for `verify_router_output` and the final account checks to pass, while `wallet_token` is transferred from the victim to the attacker.
