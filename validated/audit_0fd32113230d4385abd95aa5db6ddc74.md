### Title
Webhook shop identity spoofing via HMAC that only covers the request body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` cryptographically authenticates the payload bytes but never binds the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers to that signature. `Webhooks::Registry.process` accepts the HMAC check as proof of authenticity for the whole request and then forwards the unauthenticated `request.shop` value straight into the handler, so the tenant identity used by the receiving app is not the value the signature actually protects.

### Finding Description
`Webhooks::Request` exposes `shop`, `topic`, `webhook_id`, and `api_version` purely from HTTP headers: [1](#0-0) 

But the signable string used for HMAC verification is only the raw body: [2](#0-1) 

`Webhooks::Registry.process` validates the HMAC and, on success, treats every header-derived field (including `shop`) as trustworthy, passing it into the handler's metadata: [3](#0-2) 

The equality this breaks is: `shop authenticated by HmacValidator.validate(request) == shop bound in the signed bytes`. In fact, the signed bytes only cover the JSON body — the `x-shopify-shop-domain` header (and `topic`/`webhook-id`/`api-version`) sit entirely outside the HMAC's integrity envelope. `Utils::HmacValidator.validate` calls `verifiable_query.to_signable_string`, which for `Webhooks::Request` is `@raw_body` alone: [4](#0-3) 

Because the shop-domain header is never part of the signed material, any request carrying a body+HMAC pair that is valid for the app's `client_secret` will pass validation regardless of which `shop-domain` header accompanies it. An attacker who legitimately receives one authentic webhook (with its valid body/HMAC pair, e.g. from their own store's app installation) can resend that exact body and HMAC to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` value. `Registry.process` will accept it as authentic and dispatch the handler with `WebhookMetadata#shop` set to the attacker-chosen domain instead of the domain the payload actually originated from.

### Impact Explanation
This is a cross-tenant identity-binding failure: the gem authenticates *content* but not *which shop the content is attributed to*, and it hands that unauthenticated attribution directly to app-level webhook handlers via `WebhookMetadata.new(... shop: request.shop ...)`. Any app logic keyed on `shop` (data deletion, entitlement changes, order/customer state updates, GDPR compliance webhooks, etc.) can be triggered under a victim shop's identity using a payload the attacker never actually received for that shop, i.e. cross-tenant access to another merchant's webhook processing pipeline.

### Likelihood Explanation
Low/Medium — exploitation requires the attacker to possess at least one legitimate, correctly-signed webhook body/HMAC pair (attainable by installing the app on their own store and capturing an authentic webhook delivery), and requires the target app to control-flow on `shop` from `WebhookMetadata` without independent verification. This mirrors the reported bug class where a value acted upon by downstream logic is not the value actually covered by the authenticity check, so the loss/impact only materializes under specific but realistic operating conditions.

### Recommendation
Include the shop-domain (and ideally topic and webhook-id) in the HMAC-signed material for `Webhooks::Request`, or otherwise cryptographically bind them, so that `Utils::HmacValidator.validate` cannot succeed for a body signed for one shop while claiming a different shop's domain. At minimum, document prominently that `WebhookMetadata#shop` is unauthenticated header data and must not be trusted for tenant routing without additional verification.

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com` and capture one legitimate webhook delivery: raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` using the app's `client_secret`).
2. Replay the request to the app's webhook endpoint, keeping `raw_body = B` and `x-shopify-hmac-sha256 = H`, but set `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "x-shopify-shop-domain" => "victim-shop.myshopify.com"})` is constructed successfully.
4. `Webhooks::Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only recomputes HMAC over `B` and succeeds because `to_signable_string` never included the shop header. [5](#0-4) 
5. The handler executes with `WebhookMetadata#shop == "victim-shop.myshopify.com"`, even though the authenticated body actually originated from `attacker-shop.myshopify.com`.
