### Title
Fisherman veto reset of `LatestStateMachineHeight` re-opens a lower, already-superseded state commitment for honest re-submission, extending its post-veto trust window past the intended challenge period - (File: modules/pallets/ismp/src/host.rs)

### Summary
CVE-2026-40622 is a "ghost domain" style bug in which a single unprivileged query causes a resolver to overwrite a stale/expired trust record (parent NS) with new data (child NS) that resets the record's TTL/trust window, letting the attacker keep an invalid delegation alive indefinitely. The reachable Hyperbridge analog is in the state-machine-commitment veto path: `delete_state_commitment` in `modules/pallets/ismp/src/host.rs` rolls `LatestStateMachineHeight` back to `PreviousStateMachineHeight` whenever the vetoed height happens to be the current latest height, re-opening that height for a fresh "honest" submission with a brand-new challenge-period clock, even though the underlying leftover queue bookkeeping (noted explicitly in the code's own comments) is inexact.

### Finding Description
`delete_state_commitment` [1](#0-0)  removes the bounded commitment/update-time entries for a vetoed height and, if that height is currently the latest, resets `LatestStateMachineHeight` back to the previous height. This is intentional to allow "honest updates" to re-fill that height. However, the comment on the same function admits the state-commitment queue bookkeeping is left inconsistent by design ("a veto costs that height one insertion of retention and permanently burns one queue slot... The stale entry then evicts the live commitment when it reaches the head") [2](#0-1) .

Once the height is reset, `update_client` in `modules/ismp/core/src/handlers/consensus.rs` will accept a new commitment for that same height because the "only allow heights greater than latest" and "skip duplicate" checks are evaluated against the now-rolled-back `LatestStateMachineHeight` [3](#0-2) . Crucially, `host.store_state_machine_update_time` is invoked unconditionally for this "new" (but height-reused) commitment [4](#0-3) , which restarts the `challenge_period` clock checked by `verify_delay_passed`/`validate_state_machine` in `modules/ismp/core/src/handlers.rs` [5](#0-4) . Because the stale queue slot from the vetoed height still lives in `StateCommitmentQueue` and will independently evict whichever commitment is currently occupying the head when it "reaches the head" (per the function's own comment), a live, freshly re-challenged commitment for a *later* height can be prematurely evicted by the leftover stale queue entry from the vetoed height, out of proper FIFO order with respect to real insertion recency.

This mirrors the ghost-domain root cause precisely: a single relayed message (a `ConsensusMessage`/state update, reachable by any unprivileged relayer since `handle_unsigned` is `ensure_none` [6](#0-5) ) causes an internal bookkeeping structure (the eviction queue and `LatestStateMachineHeight`) to be overwritten/extended in a way that decouples the "trust window" (challenge period / retention) from actual insertion order, letting a stale, already-superseded artifact silently displace a currently-relied-upon one.

### Impact Explanation
If the stale queue slot evicts a live `BoundedStateCommitments` entry for a height still within its challenge period or still needed for pending membership proofs, in-flight relayed requests/responses referencing that height will fail with `StateCommitmentNotFound`, and honest relayers cannot deliver messages for that state-machine height — a denial of message delivery ("route unable to deliver messages") caused entirely by unprivileged veto + re-submission traffic, not by any admin/governance/relayer misbehavior.

### Likelihood Explanation
Triggering requires: (1) a fisherman veto (a normal, permissionless fraud-proof path) on the current latest height for a state machine, and (2) at least one subsequent honest re-submission at that height, both of which are expected, permissionless, day-to-day protocol operations rather than privileged or adversarial-insider actions. The function's own inline comment confirms the inconsistency is a known, reproducible side effect of every such veto, not a rare edge case, making the precondition trivially satisfiable by any relayer/fisherman pair operating on a live state machine.

### Recommendation
Track the queue index associated with each height (or use a height→index map) so `delete_state_commitment` can precisely remove the vetoed height's queue slot instead of leaving a stale duplicate, and ensure `LatestStateMachineHeight` rollback and queue bookkeeping are updated atomically so eviction order always matches actual retention/challenge-period order.

### Proof of Concept
1. State machine `S` under consensus client `C` has latest committed height `H_n` with an active challenge period.
2. A fisherman submits a valid fraud proof vetoing height `H_n`; `delete_state_commitment` removes `H_n`'s bounded entries and rolls `LatestStateMachineHeight(S)` back to `H_{n-1}`, but leaves `H_n`'s original queue slot un-removed [7](#0-6) .
3. Any unprivileged relayer submits a legitimate `ConsensusMessage` re-establishing height `H_n` (now treated as "new" since latest is `H_{n-1}`); `update_client` stores a fresh commitment and fresh `state_machine_update_time` for `H_n`, restarting its challenge period [8](#0-7) .
4. Further honest consensus updates advance to `H_{n+1}`, `H_{n+2}`, etc., inserting new queue entries.
5. When the leftover stale `H_n` queue slot from step 2 reaches the eviction head (per the code's documented behavior), it evicts whatever live commitment currently occupies that slot — potentially the just-re-challenged `H_n` commitment or a later height sharing the slot — before its real challenge period/retention window would have expired, causing subsequent `state_machine_commitment` lookups in `request.rs`/`response.rs` handlers to fail for otherwise-valid, in-window proofs.

	fn delete_state_commitment(&self, height: StateMachineHeight) -> Result<(), Error> {
		// The height's entry in the state commitment queue is deliberately left
		// behind; locating it would mean scanning the queue, which is the per-insert
		// cost the queue exists to avoid. Usually its eviction is a no-op, but when
		// the vetoed height is the latest the reset below re-opens it for honest
		// resubmission, and the resubmitted height gets a *second* queue entry. The
		// stale entry then evicts the live commitment when it reaches the head —
		// one insertion before the live entry would have, since the resubmission
		// lands directly behind its stale twin. So a veto costs that height one
		// insertion of retention and permanently burns one queue slot. Both are
		// negligible against the configured caps; making it exact would need a
		// height -> index map on the insert path.
		BoundedStateCommitments::<T>::remove(height.id, height.height);
		BoundedStateMachineUpdateTime::<T>::remove(height.id, height.height);

		// technically any state commitment can be vetoed,
		// safety check that it's the latest before resetting it.
		if let Some(latest) = LatestStateMachineHeight::<T>::get(height.id) {
			if latest == height.height {
				// Reset back to the initial height to allow for honest updates
				let prev_height =
					PreviousStateMachineHeight::<T>::get(height.id).ok_or_else(|| {
						Error::Custom("Previous state machine height should exist".to_string())
					})?;
				LatestStateMachineHeight::<T>::insert(height.id, prev_height);
			}
		}
		Ok(())
	}

pub fn verify_delay_passed<H>(host: &H, proof_height: &StateMachineHeight) -> Result<bool, Error>
where
	H: IsmpHost,
{
	let update_time = host.state_machine_update_time(*proof_height)?;
	let delay_period = host
		.challenge_period(proof_height.id)
		.ok_or(Error::ChallengePeriodNotConfigured { state_machine: proof_height.id })?;
	let current_timestamp = host.timestamp();
	Ok(delay_period.as_secs() == 0 || current_timestamp.saturating_sub(update_time) > delay_period)
}
