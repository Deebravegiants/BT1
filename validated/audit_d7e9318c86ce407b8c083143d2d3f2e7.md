### Title
Unchecked ERC20 `transfer` return value in `IntentGatewayV2.withdraw`/`onAccept` (Tron variant) leads to accounting error and permanently locked escrowed tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2` releases escrowed order funds and dust via a raw low-level `.call()` to `IERC20.transfer`, checking only that the call did not revert (`success`) but never decoding/validating the boolean return value that `transfer` is supposed to return. This is the exact bug class from the report: a non-reverting `transfer` that returns `false` (or a non-standard ERC20 whose return data doesn't unwind on failure) will be treated as a successful transfer, while escrow accounting is unconditionally decremented, permanently freezing the underlying tokens in the contract and denying users/solvers their entitled funds.

### Finding Description
In `evm/tron/contracts/apps/IntentGatewayV2.sol`, `withdraw()` (called by `onAccept` for `RedeemEscrow`/`RefundEscrow`, and by `onGetResponse` for cancellations) performs: [1](#0-0) 

```solidity
if (token == address(0)) {
    (bool sent,) = beneficiary.call{value: amount}("");
    if (!sent) revert InsufficientNativeToken();
} else {
    (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
    if (!success) revert TransferFailed();
}

_orders[body.commitment][token] -= amount;
```

`success` here only reflects whether the low-level call reverted — it does not decode the returned `bool` from a standards-compliant `transfer()` implementation. Tokens that follow the ERC20 spec but return `false` on failure (instead of reverting) will make `token.call(...)` return `success = true` even though no tokens moved. Despite that, `_orders[body.commitment][token] -= amount;` unconditionally decrements the escrow accounting, marking the funds as "redeemed." The same unchecked pattern is used for the transaction-fee payout in the same function: [2](#0-1) 

and for `SweepDust` handling in `onAccept`: [3](#0-2) 

By contrast, the canonical (non-Tron) EVM implementation of the same logic in `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` correctly uses OpenZeppelin's `safeTransfer`, which reverts the whole transaction on a failed/false-returning transfer, so escrow accounting and actual token movement stay atomic and consistent: [4](#0-3) 

This confirms the Tron variant is a regression/divergence from the hardened pattern used elsewhere in the codebase, and matches the reported bug class precisely: an ERC20 transfer whose return value is not properly checked, permitting an accounting update (escrow decrement / `_filled` mark) to proceed as if the transfer succeeded when it did not.

### Impact Explanation
`withdraw()` is reached via a permissionless path: any relayer can deliver a proof-authenticated `RedeemEscrow`/`RefundEscrow` cross-chain message (via `onAccept`, gated only by `onlyHost` + message authentication, not by transfer correctness), or via the GET-response cancellation flow (`onGetResponse`). If the input/output token used in an order is a non-standard or misbehaving ERC20 (returns `false` instead of reverting on failure — e.g. due to insufficient allowance/balance edge cases, blocklists, paused states, or bespoke token logic), the beneficiary will not receive the tokens, yet:
- `_orders[commitment][token]` is decremented to zero (in the tron contract, the guard `if (_orders[...][token] == 0) revert UnknownOrder()` means this can only be retried once and will now revert as "unknown order" on any future attempt),
- `_filled[commitment]` is set, marking the order permanently as filled/refunded,
- there is no governance/owner path to re-trigger the transfer or recover the tokens (only `SweepDust`, which is for protocol-collected dust, not user escrow).

The result is a permanent freeze of the escrowed principal (and/or fee) tokens inside the `IntentGatewayV2` contract with no recovery mechanism — a direct loss of user/solver funds. This satisfies "permanent freezing of funds" per the validation criteria.

### Likelihood Explanation
Likelihood is dependent on the specific ERC20 token configured for a given order's input/output assets. Tokens that unconditionally revert on failure (most modern, audited tokens) are unaffected. However, Hyperbridge's Intent Gateway is designed to be permissionless and multi-token by nature (any ERC20 pairs can be specified in an order's `TokenInfo.token`), so it is reasonably foreseeable that at least one supported token on the Tron deployment does not strictly follow the "revert on failure" convention (e.g., returns `false` under certain conditions such as blocklisting, pausing, or fee-on-transfer edge cases). Given the scale of assets that flow through escrow (`placeOrder`/`fillOrder`) and that the flawed check is on the hot path of every single-token/native withdrawal and fee payout, even a low-probability per-transfer failure mode compounds into a real risk across the token's supported instances.

### Recommendation
Replace the raw `.call` + `success`-only check pattern in `evm/tron/contracts/apps/IntentGatewayV2.sol` (`withdraw()` and the `SweepDust` handling in `onAccept()`) with OpenZeppelin's `SafeERC20.safeTransfer`, mirroring what `evm/src/apps/intentsv2/IntentsBase.sol::_withdraw` already does:
```solidity
IERC20(token).safeTransfer(beneficiary, amount);
```
This ensures both call-level reverts and false-boolean returns cause the whole transaction (including the escrow/`_filled` state mutation) to revert atomically, preventing the accounting/transfer desync that leads to locked funds.

### Proof of Concept
1. Deploy a mock ERC20 whose `transfer()` returns `false` on a specific condition (e.g., if `to` is blocklisted) instead of reverting — a legal, spec-compliant implementation.
2. On the Tron `IntentGatewayV2`, a user calls `placeOrder` escrowing this token; `_orders[commitment][token] = amount`.
3. The order is filled cross-chain and a `RedeemEscrow` message is authenticated and delivered via `onAccept`, invoking `withdraw(body, false)`.
4. Set the beneficiary address to trigger the mock token's `false`-return condition. `token.call(...)` returns `(success=true, data=abi.encode(false))`; since only `success` is checked, execution proceeds.
5. `_orders[commitment][token] -= amount` sets escrow to zero and `_filled[commitment] = beneficiary` is recorded, while the beneficiary's token balance never increased.
6. Any retry reverts with `UnknownOrder()` since `_orders[commitment][token] == 0`; the tokens remain permanently locked in the `IntentGatewayV2` contract with no owner/governance withdrawal path for user escrow.
