### Title
No slippage/price-cap protection in `BandwidthManager.purchase()` lets governance tier-price updates overcharge in-flight buyers - (File: evm/src/apps/BandwidthManager.sol)

### Summary
`BandwidthManager.purchase()` charges the caller `tierPrice[tier] * months` (scaled to the fee token's decimals) read live from mutable storage at execution time, with no caller-supplied maximum price. `tierPrice[tier]` is updated asynchronously and unilaterally by governance via `SetTiers` messages delivered from `pallet-bandwidth` through `onAccept`. A buyer who computes an expected cost off-chain (e.g., from a `quote()`-style read) and submits `purchase()` has no way to bound what they will actually be charged if a `SetTiers` update lands between quoting and inclusion — exactly the same missing-slippage-protection bug class as the referenced Dopex `bond`/`bondWithDelegate` finding, where cost is computed from a mutable on-chain input at execution time with no user-specified cap.

### Finding Description
`purchase()` in `evm/src/apps/BandwidthManager.sol` reads the current tier price directly from the `tierPrice` mapping and pulls exactly that amount from the caller:

```solidity
uint256 price18d = tierPrice[tier];
if (price18d == 0) revert UnknownTier();

uint256 total18d = price18d * months;
...
uint256 amount = total18d / scale;

IERC20(feeToken).safeTransferFrom(msg.sender, address(this), amount);
``` [1](#0-0) 

`tierPrice[tier]` is not fixed at deployment — it is a governance-controlled variable updated via the `SetTiers` action handled in `onAccept`, driven by `pallet-bandwidth::dispatch_set_tiers` on Hyperbridge: [2](#0-1) [3](#0-2) 

The documented purchase flow explicitly instructs integrators to quote the price off-chain immediately before calling `purchase()`, with no mechanism to enforce that the on-chain execution charges no more than the quoted amount: [4](#0-3) 

Because `purchase()` takes no `maxAmount`/`maxPrice18d` parameter, and there is no check comparing the computed `amount` against any caller-supplied ceiling, a `SetTiers` update that raises `tierPrice[tier]` between the time a buyer signs/broadcasts their `purchase()` transaction and the time it is included will silently cause the buyer to pay more than they intended — the transaction does not revert, it simply debits the new (higher) price. This mirrors the Dopex root cause precisely: cost is derived from a mutable state variable (`bondDiscountFactor`/reserve there, `tierPrice[tier]` here) at execution time, with no way for the caller to cap total spend.

### Impact Explanation
A buyer intending to pay a specific, quoted amount for `months` of `tier` bandwidth can be charged a materially different (higher) amount if governance pushes a tier-price change (`SetTiers`) that lands in the same or an earlier block than the buyer's `purchase()` call. Because `IERC20.safeTransferFrom` pulls whatever `amount` the current price computes to (bounded only by the buyer's ERC-20 allowance, which is commonly set generously or to the quoted amount plus headroom), the buyer can lose funds relative to their expected cost with no recourse — the purchase still succeeds and cannot be reversed. This is a fund-loss/overcharge condition for an unprivileged bandwidth purchaser, consistent with the "Medium" severity assigned to the analogous Dopex finding (the buyer still receives *a* subscription, but not at the price/discount they budgeted for).

### Likelihood Explanation
This does not require any malicious actor — tier prices are expected to change over the life of the protocol via normal governance operations (the documentation describes `SetTiers` as an ordinary, expected admin/governance flow, not an attack). Any buyer who quotes off-chain and submits `purchase()` is exposed whenever a legitimate price update is in flight, which is a routine, low-friction occurrence rather than an edge case, making the likelihood of an unexpected overcharge non-negligible over the lifetime of a widely used `BandwidthManager` deployment.

### Recommendation
Add an explicit price-ceiling parameter to `purchase()`, e.g. `maxPrice18d`, and require `tierPrice[tier] <= maxPrice18d` (or equivalently bound the derived `amount`) before pulling funds, reverting otherwise. This gives buyers deterministic slippage protection analogous to the `maxRDPX`/`maxWETH` mitigation recommended for the Dopex `bond`/`bondWithDelegate` functions, without changing the existing governance-driven pricing model.

### Proof of Concept
1. Governance configures `tierPrice[TierOne] = P0` via `SetTiers`, delivered through `onAccept`.
2. A buyer calls the off-chain `quote()`/`tierPrice()` helper shown in the docs, computes `cost = P0 * months` (scaled to fee-token decimals), approves the manager for `cost`, and prepares/broadcasts `purchase(app, TierOne, months, chain)`. [5](#0-4) 
3. Before the buyer's transaction is included, governance dispatches a new `SetTiers` message raising `tierPrice[TierOne]` to `P1 > P0` (a normal, non-malicious admin operation as described in the bandwidth governance docs).
4. The buyer's `purchase()` transaction executes after the price update lands, so `price18d = tierPrice[TierOne] = P1`, and `amount = (P1 * months) / scale > cost` is pulled via `safeTransferFrom` — provided the buyer's ERC-20 allowance covers it (a common pattern is to approve for the quoted `cost` plus headroom, or an unlimited/`max` approval as shown in several SDK examples in this codebase).
5. The buyer receives the purchased bandwidth subscription but is charged more than the quoted/expected amount, with the transaction never reverting and no way to have capped their spend — the `purchase()` interface provides no parameter for this. Full on-chain confirmation of the exact `SetTiers` timing window relative to a `purchase()` call requires interactive testing (e.g. a Foundry test racing an `onAccept(SetTiers)` call against a pending `purchase()`), which was not runnable in this read-only review; the code-level absence of any max-price argument or check in `purchase()` was confirmed directly.
