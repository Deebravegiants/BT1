### Title
Access-key nonce reset on delete+recreate enables replay of previously-signed transactions - ([File: runtime/runtime/src/access_keys.rs])

### Summary
The reported CloudWalk bug is a "stale authorization survives reconfiguration" class: a counter/approval tied to an old owner set is not invalidated when the authorized set is reconfigured, letting an old signed approval satisfy a new threshold. The closest reachable analog in nearcore's unprivileged transaction-authorization path is the access-key nonce reseeding logic: when an access key is deleted and a new key is added under the *same* public key, the new key's nonce is reseeded from the current block height rather than continuing from the deleted key's last nonce, which the code's own documentation flags as required to "avoid replaying old transactions again."

### Finding Description
`AccessKey` nonce is the sole replay-protection mechanism for a given `(account_id, public_key)` pair. `docs/DataStructures/AccessKey.md` states explicitly: [1](#0-0) 
> "In some cases the access key needs to be recreated. If the new access key reuses the same public key, the nonce of the new access key should be equal to the nonce of the old access key. It's required to avoid replaying old transactions again."

However, `action_delete_key` in `runtime/runtime/src/access_keys.rs` unconditionally removes the access key from the trie via `delete_regular_key`, which only clears storage usage and does not persist the key's last nonce anywhere: [2](#0-1) 

When a new `AddKey` action is later submitted for the same public key, `add_regular_key` reseeds the nonce from `initial_nonce_value(block_height)`, i.e. `(block_height-1) * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, with no reference to any prior nonce that the deleted key may have had: [3](#0-2) 

Nonce validation (`verify_nonce`, `runtime/runtime/src/verifier.rs`) only enforces `tx_nonce > current_nonce` (Monotonic) or `tx_nonce == current_nonce + 1` (Strict), and an upper bound of `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER`, per `protocol-model/spec/accounts-keys.md`: [4](#0-3) 

This is structurally the same failure mode as the multisig bug: an account owner pre-signs a high-value transaction (analogous to the malicious owner's withdrawal transaction pre-approved with the "old" configuration), then triggers a key rotation (analogous to `configureOwners()`), and — because the new key's replay-protection state is not derived from the old key's state — the previously signed but unexecuted transaction can become valid again if the new key's reseeded nonce happens to be below the pre-signed transaction's nonce.

### Impact Explanation
If exploitable, this would allow replay/execution of a transaction that the account holder believed was invalidated when they rotated their access key (e.g., after suspecting a key compromise, a classic "hacked key" narrative identical to the one in the original report) — an unauthorized state/balance change executed with a key the user believes has been superseded.

### Likelihood Explanation
Exploitability depends on the reseeded nonce value from `initial_nonce_value(block_height)` being lower than a nonce the attacker chose for a pre-signed transaction under the old key. Since `initial_nonce_value` grows monotonically with block height and the maximum allowed nonce for a transaction is bounded to `block_height * ACCESS_KEY_NONCE_RANGE_MULTIPLIER` at signing time, an attacker who signs a transaction near the current per-block nonce ceiling and only replays it after a short number of blocks could have a pre-signed nonce that still exceeds the freshly reseeded value, since the new value is based on `(current_block_height - 1)`. I could not fully verify the exact window/feasibility bound (e.g., whether `NonceTooLarge`/upper-bound checks at submission time, or the specific gap between `(h-1)*M` for the delete/recreate block versus the originally allowed nonce ceiling `h_sign*M`, close this gap in all cases) without deeper reading of `verify_nonce` and `action_add_key`'s full interaction with `NonceMode`; this is a plausible but not fully proven timing-dependent condition.

### Recommendation
When adding a new access key under a public key that was recently associated with a deleted key for the same account, either (a) persist and reuse the last known nonce for that `(account_id, public_key)` pair (matching the documented invariant), or (b) require/derive the new key's seed nonce to be strictly greater than any nonce that could have been validly signed against the deleted key, closing the replay window described in `docs/DataStructures/AccessKey.md`.

### Proof of Concept
Not independently reproduced in this pass — this requires driving `action_delete_key`/`action_add_key` through the runtime with concrete block-height timing to confirm a produced reseeded nonce below a previously-signed high nonce transaction; recommend a Devin session with full repo/test access to construct and run this scenario against `runtime/runtime/src/access_keys.rs` and `runtime/runtime/src/verifier.rs`'s `verify_nonce`.

pub(crate) fn initial_nonce_value(block_height: BlockHeight) -> Nonce {
    // Set default nonce for newly created access key to avoid transaction hash collision.
    // See <https://github.com/near/nearcore/issues/3779>.
    (block_height - 1) * near_primitives::account::AccessKey::ACCESS_KEY_NONCE_RANGE_MULTIPLIER
}
