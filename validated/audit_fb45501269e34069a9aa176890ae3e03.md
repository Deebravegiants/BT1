## Title
Front-runnable lockup address allows unprivileged attacker to pre-create a victim's lockup contract with attacker-chosen vesting terms - (`lockup-factory/src/lib.rs`)

## Summary
The external Biconomy report describes a **counterfactual-address hijack**: the deployment address is computed without binding a critical parameter (the entrypoint) into the derivation/salt, so an unprivileged attacker can pre-deploy the contract at the pre-computed address using attacker-chosen initialization data instead of the legitimate one. `lockup-factory` has the same root cause: the deterministic lockup account address is derived only from `owner_account_id`, while security-critical initialization data — most importantly the `vesting_schedule` — is *not* bound into the address and is fully attacker-controllable through the public `create` entrypoint.

## Finding Description
`LockupFactory::create` computes the lockup account address deterministically from only the `owner_account_id`: [1](#0-0) 

Any unprivileged caller can invoke `create` for **any** `owner_account_id` and supply an arbitrary `vesting_schedule` (either a plaintext schedule or a private `VestingHash` whose preimage only the caller knows), together with only the `MIN_ATTACHED_BALANCE` (3.5 NEAR): [2](#0-1) 

There is no check binding the caller to the `owner_account_id`, nor any check that the vesting parameters match a schedule previously agreed/committed by the NEAR Foundation. The account creation, contract deployment, and `new()` initialization (which sets the lockup's `vesting_schedule`) all happen atomically in a single promise batch signed by the factory itself: [3](#0-2) 

Because the address `sha256(owner_account_id)[:20].<factory>` is fully predictable in advance (this is precisely how the NEAR Foundation is expected to pre-compute lockup addresses before funding them, analogous to the counterfactual wallet address in the original report), an attacker can front-run the Foundation's legitimate `create` call for a known/targeted `owner_account_id`:

1. Attacker calls `create(owner_account_id = "victim.near", vesting_schedule = <attacker-chosen, e.g. already fully-vested/no-cliff schedule>, ...)`, attaching only the minimum required deposit.
2. The account `<hash>.factory` is created and initialized with the attacker-chosen vesting terms; `foundation_account_id` is still forced to the real Foundation because it's taken from factory storage, not caller input, but the vesting schedule itself — the thing that actually gates when/how much is spendable — is attacker-controlled.
3. When the NEAR Foundation later submits its legitimate `create` call for the same `owner_account_id` with the intended real large deposit and real vesting schedule, `create_account` fails because the account already exists, the promise fails, and `on_lockup_create` refunds the deposit to the Foundation: [4](#0-3) 

The address is now permanently squatted with the attacker's vesting terms (e.g. everything already vested, or termination-hostile parameters), and the Foundation's normal creation flow can never succeed for that `owner_account_id`.

## Impact Explanation
This is reachable by any unprivileged account with a few NEAR tokens, through a fully public entrypoint (`create`), requiring no privileged role. The impact:
- **Unauthorized release of vested NEAR**: an attacker can force a victim's lockup contract to be instantiated with a vesting schedule that is already fully vested (or trivially satisfied), so once real funds later land on that account, they bypass the intended lock-up entirely — an accounting/authorization failure matching the "Unauthorized ... release of locked, vested ... NEAR" Critical category.
- **Irrevocable loss of vesting-termination control**: because the vesting schedule embedded at creation time is attacker-chosen and not what the Foundation intended, the Foundation permanently loses the ability to correctly terminate/claw back unvested tokens for that specific owner — matching the Critical "irrevocable loss ... in ... vesting termination ... flows" category.
- Even absent later funding, this permanently denies the legitimate `create` flow for that `owner_account_id` (griefing/DoS of the intended deployment), since the deterministic address is a one-time resource.

## Likelihood Explanation
Likelihood is high in any deployment scenario where lockup addresses are pre-computed off-chain (e.g., via `get_lockup_master_account_id`/hash derivation, mirroring how `getAddressForCounterfactualWallet` is used in the original report) before the Foundation sends the real funding transaction. Any observer who knows a target employee/investor's `owner_account_id` can front-run with a minimal 3.5 NEAR deposit; no special access or timing beyond ordinary transaction ordering/mempool visibility is required.

## Recommendation
- Require that `create` can only be called (or only take effect) when `predecessor_account_id` equals `owner_account_id`, or when signed/authorized by the Foundation account, closing the door to third-party front-running of a victim's address.
- Bind the vesting/lockup parameters (or a commitment/hash of them agreed upon in advance) into the address derivation, similar to including all critical init parameters in a CREATE2 salt, so that a mismatched initialization cannot occupy a victim's expected address.
- Alternatively, have the Foundation-driven, high-value creation flow perform an explicit `assert_eq!` check on the resulting contract's `vesting_schedule`/state right after creation and revert/flag if it doesn't match what was expected, rather than silently refunding on account-already-exists failures.

## Proof of Concept
1. Foundation intends to create a lockup for `owner_account_id = "victim.near"` with a 4-year vesting schedule with a 1-year cliff, and precomputes the address as `sha256("victim.near")[:20].<factory>`.
2. Before the Foundation's transaction lands, an attacker submits:
```
near call <factory> create '{
  "owner_account_id": "victim.near",
  "lockup_duration": "0",
  "vesting_schedule": {"VestingSchedule": {"start_timestamp":"0","cliff_timestamp":"0","end_timestamp":"1"}}
}' --accountId attacker.near --amount 3.5
```
This deploys the lockup contract at the pre-computed address with an already-fully-vested schedule.
3. The Foundation's later `create` call for the same `owner_account_id` fails at `create_account` (account exists), and `on_lockup_create` refunds the Foundation's deposit: [5](#0-4) 
4. Any funds subsequently transferred to that address are governed by the attacker-chosen (already fully vested) schedule instead of the intended one, and the Foundation can never re-create the intended lockup for `victim.near`.

    #[payable]
    pub fn create(
        &mut self,
        owner_account_id: ValidAccountId,
        lockup_duration: WrappedDuration,
        lockup_timestamp: Option<WrappedTimestamp>,
        vesting_schedule: Option<VestingScheduleOrHash>,
        release_duration: Option<WrappedDuration>,
        whitelist_account_id: Option<ValidAccountId>,
    ) -> Promise {
        assert!(env::attached_deposit() >= MIN_ATTACHED_BALANCE, "Not enough attached deposit");

        let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
        let lockup_account_id =
            format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());

        let mut foundation_account: Option<AccountId> = None;
        if vesting_schedule.is_some() {
            foundation_account = Some(self.foundation_account_id.clone());
        };

        // Defaults to the whitelist account ID given on init call.
        let staking_pool_whitelist_account_id = if let Some(account_id) = whitelist_account_id {
            account_id.into()
        } else {
            self.whitelist_account_id.clone()
        };

        let transfers_enabled: WrappedTimestamp = TRANSFERS_STARTED.into();
        Promise::new(lockup_account_id.clone())
            .create_account()
            .deploy_contract(CODE.to_vec())
            .transfer(env::attached_deposit())
            .function_call(
                b"new".to_vec(),
                near_sdk::serde_json::to_vec(&LockupArgs {
                    owner_account_id,
                    lockup_duration,
                    lockup_timestamp,
                    transfers_information: TransfersInformation::TransfersEnabled {
                        transfers_timestamp: transfers_enabled,
                    },
                    vesting_schedule,
                    release_duration,
                    staking_pool_whitelist_account_id,
                    foundation_account_id: foundation_account,
                })
                    .unwrap(),
                NO_DEPOSIT,
                gas::LOCKUP_NEW,
            )
            .then(ext_self::on_lockup_create(
                lockup_account_id,
                env::attached_deposit().into(),
                env::predecessor_account_id(),
                &env::current_account_id(),
                NO_DEPOSIT,
                gas::CALLBACK,
            ))
    }

    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
