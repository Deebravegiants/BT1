## Finding

### Title
Webhook shop/topic identity headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authentic once `Utils::HmacValidator.validate(request)` passes, but that validation only covers the raw request body — never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers that the handler is actually keyed on. This breaks the identity binding: `HMAC-verified bytes == raw_body` while `data acted on by the handler == shop/topic headers`, which are attacker-suppliable and never authenticated.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` gates entirely on this HMAC check and then builds `WebhookMetadata` straight from the unauthenticated headers: [2](#0-1) 

`HmacValidator.validate` computes `HMAC-SHA256(raw_body, api_secret_key)` and compares it to the `hmac` accessor, which is likewise derived only from the body-independent header value, not bound to `shop`/`topic`: [3](#0-2) [4](#0-3) 

Because `api_secret_key` is a single, app-wide secret shared across every shop that installs the app (it is not shop-specific), any unprivileged internet user who installs the app on their own (e.g., free development/partner) store can trigger a real webhook, capture its `(raw_body, hmac)` pair — which is valid Shopify-issued proof — and replay that exact body to the app's webhook endpoint while forging the `x-shopify-shop-domain`, `x-shopify-topic`, `x-shopify-webhook-id`, and `x-shopify-api-version` headers to claim they belong to a different, victim shop. `HmacValidator.validate` still returns `true` (it only checks the body bytes), so `Registry.process` dispatches the handler with attacker-chosen `shop`/`topic` values believed by the app to be authenticated: [5](#0-4) 

The gem's own documentation reinforces the false guarantee, telling integrators that calling `Registry.process` "will verify the request did indeed come from Shopify," implying the whole request (including the shop identity) is authenticated, when only the body is.

### Impact Explanation
This is a cross-tenant identity-binding break: the equality that should hold is `authenticated_secret_owner == shop_claimed_in_header`, but the gem only proves `HMAC(secret, body) == received_hmac`, with no linkage from the secret/signature to the shop or topic. A single unprivileged attacker who legitimately installs the app on any shop (including a free dev store) can forge webhook events attributed to any other shop the app serves, because the signing secret is shared and identity headers are excluded from the signed payload. Downstream apps built on `ShopifyAPI::Webhooks::WebhookHandler` (as shown in the gem's own usage docs) route/persist per-tenant business data — orders, customers, uninstall events — keyed off `data.shop`, so this permits cross-tenant data injection/corruption using only the forged `shop`/`topic` header value, satisfying the "cross-tenant access" impact bucket.

### Likelihood Explanation
Exploitation requires: (1) installing the target app on any shop the attacker controls (trivial, free, and available to any internet user for public/dev apps), (2) triggering one real webhook to capture a `(raw_body, hmac)` pair for a topic/body of interest, and (3) POSTing that pair to the same webhook endpoint with forged `shop`/`topic` headers. All three steps require no elevated privileges, no leaked credentials, and no access to the app's `client_secret` or another tenant's access token.

### Recommendation
Bind the identity headers into the signed material, or otherwise verify `shop`/`topic` out-of-band before trusting them: e.g., look up the `webhook_id`/shop pair against Shopify's Admin API (or a locally stored registration record) before dispatching the handler, and never treat `HmacValidator.validate` alone as proof that the claimed `shop-domain`/`topic` headers are trustworthy. At minimum, update the documentation to stop stating that `process` "verifies the request did indeed come from Shopify" for the *shop*/*topic* metadata, since only the body is authenticated.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop (`attacker.myshopify.com`) and registers a webhook (e.g. `orders/create`) pointing at the app's public callback URL.
2. Shopify delivers a legitimate webhook to the app with a valid `x-shopify-hmac-sha256` header computed over the JSON body using the app's shared `api_secret_key`.
3. Attacker captures the raw body and `hmac` header from this delivery.
4. Attacker sends their own POST request directly to the same app callback URL, reusing the captured `raw_body`/`hmac`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `x-shopify-topic`, e.g. `app/uninstalled`).
5. `ShopifyAPI::Webhooks::Registry.process` calls `HmacValidator.validate`, which succeeds because it only checks `raw_body` against `hmac` — both attacker-supplied and internally consistent — and then invokes the registered handler with `shop: "victim-shop.myshopify.com"`, causing the app to process a forged event as if it came from the victim's store.
