### Title
Webhook `shop` and `topic` identity accepted from unauthenticated headers while only the request body is HMAC-verified - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content solely from the raw request body, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to dispatch the webhook to the app's handler are read directly from HTTP headers that are never included in the HMAC computation. This breaks the identity binding `hmac-verified content == data acted on`, analogous to the report's root cause where a value the code acts on (transferred stETH amount) is not what was actually verified (requested amount).

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all pulled from headers, none of which are part of the signable string: [2](#0-1) 

`Registry.process` validates the HMAC (which only attests to the body bytes) and then unconditionally trusts the header-derived `request.shop` and `request.topic` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` confirms authenticity of `verifiable_query.to_signable_string` only — i.e., the body — using the app's shared `api_secret_key`: [4](#0-3) 

Because a single app's `api_secret_key` is shared across every shop that installs the app, any merchant who installs the app can generate their own store's activity and receive a genuine webhook delivery with a valid `X-Shopify-Hmac-Sha256` signature over an attacker-influenced body (e.g., a product/customer webhook whose JSON content is largely attacker-controlled data from their own store). The attacker can then replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and optionally `X-Shopify-Topic`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` because it only checks the untouched body bytes against the untouched HMAC, so `Registry.process` dispatches the forged event to the handler labeled as coming from the victim shop, via `WebhookMetadata#shop`.

This is the "shop authenticated versus the shop stored/acted upon" binding named in the rules: the shop identity the HMAC calculation actually authenticates (implicitly, "whoever holds the shared secret") is decoupled from the shop identity (`request.shop`) that the library hands to the host application's per-shop business logic.

### Impact Explanation
An unprivileged merchant (any user who can install the app, i.e., an "unprivileged internet user" relative to other tenants) can inject data into another tenant's webhook processing pipeline, since the `shop` field the handler receives is attacker-controllable independent of the verified signature. Depending on how the host app's handler keys its per-shop side effects off `WebhookMetadata#shop` (e.g., updating local records, triggering redact flows, revoking access), this enables cross-tenant data injection/corruption — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) that the attacker legitimately installs the same third-party app (no special privilege, no access to the app's `client_secret` or another shop's tokens), and (2) that they can trigger at least one webhook delivery whose body they substantially control, then replay it with a modified `Shop-Domain`/`Topic` header. No leaked credentials, TLS interception, or social engineering is needed — only the ability to intercept/replay one's own legitimately-received webhook HTTP request, a capability inherent to being the recipient endpoint operator's app under one's own store.

### Recommendation
Bind the header-derived identity fields (`shop`, `topic`, `webhook_id`, `api_version`) into the HMAC-signable content, or otherwise cryptographically tie the shop identity to the verified payload (e.g., compare `request.shop` against a shop identifier embedded in the verified JSON body, or require per-shop webhook secrets) before constructing `WebhookMetadata` and invoking the handler in `Registry.process`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com`.
2. Attacker triggers a webhook (e.g., `products/update`) whose JSON body content they control via their own store data.
3. Shopify delivers the webhook to the app's endpoint with headers `X-Shopify-Shop-Domain: attacker.myshopify.com`, `X-Shopify-Topic: products/update`, and a valid `X-Shopify-Hmac-Sha256` computed only over the raw body using the shared `api_secret_key`.
4. Attacker intercepts this HTTP request client-side (they control the receiving flow up to the app boundary is not needed — they simply craft/replay an HTTP request with the exact same body+HMAC pair) and resends it directly to the app's public webhook endpoint, changing only `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because the body and HMAC are unmodified; `request.shop` now returns `"victim-shop.myshopify.com"`.
6. The handler executes business logic believing the event originated from `victim-shop.myshopify.com`, using attacker-supplied body content.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
