Audit Report

## Title
View-role users can read Bridge/External Initiator `OutgoingToken`/`AccessKey` via unrestricted GET endpoints - (File: `core/web/router.go`)

## Summary
`GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, and `GET /v2/external_initiators` are wired with only `auth.Authenticate` (session or API-token check) and no `auth.RequiresEditRole`/`RequiresRunRole` wrapper, unlike the `POST`/`PATCH`/`DELETE` handlers for the same resources. The JSON presenters for these resources unconditionally return the plaintext `OutgoingToken` (bridges) and `AccessKey`/`OutgoingToken` (external initiators), so any authenticated user with the minimal `View` role can read these values.

## Finding Description
`v2Routes` registers `authv2.GET("/bridge_types", ...)`, `authv2.GET("/bridge_types/:BridgeName", ...)`, and `authv2.GET("/external_initiators", ...)` without any role-elevation middleware, while sibling write routes on the identical resources use `auth.RequiresEditRole`. [7](#0-6) 
`RequiresEditRole`/`RequiresRunRole` demonstrate that `UserRoleView` is treated as a restricted, lower-privilege role for other actions in the same controllers, so the omission on these three GETs is an inconsistency in the authorization scheme rather than an intentional "public read" design. [2](#0-1) 
`BridgeTypesController.Index`/`Show` and `ExternalInitiatorsController.Index` call presenters that serialize `OutgoingToken`/`AccessKey` directly from the DB row with no redaction logic. [8](#0-7) [9](#0-8) [3](#0-2) [4](#0-3) 
These tokens are generated as cryptographically random secrets at bridge/external-initiator creation time. [5](#0-4) [6](#0-5) 

## Impact Explanation
This is a confirmed missing-authorization / information-disclosure issue (CWE-862): a `View`-role account, which the codebase's own role hierarchy treats as strictly less privileged than `Edit`, can retrieve secret material (`OutgoingToken`, `AccessKey`) that the write-path gating suggests should not be readable by that role. However, I could not locate any code in the indexed portions of the pipeline/bridge-task/external-initiator-notify paths that consumes `BridgeType.OutgoingToken` to authenticate outbound requests — a repo-wide grep for `OutgoingToken` outside test/presenter/CLI files shows it only stored and returned via API, not injected into outbound HTTP headers. Because of this, the "attacker can impersonate the node to an external adapter" escalation claimed in the report is unverified and may not hold in this codebase revision; if the token is unused for outbound auth, the concrete impact is limited to unnecessary secret exposure via an authorization gap, not a fund-movement or impersonation vector. The missing role check itself is still a real, in-scope authorization defect.

## Likelihood Explanation
Any authenticated node user with the lowest (`View`) role, requiring no special privilege beyond a valid session or API token, can trigger this via a single unauthenticated-w.r.t.-role GET request. No race condition, timing, or complex chain is needed — it's directly reachable and repeatable.

## Recommendation
Wrap `GET /v2/bridge_types`, `GET /v2/bridge_types/:BridgeName`, and `GET /v2/external_initiators` with `auth.RequiresEditRole` (or a dedicated role check) to match the write-path gating, or strip `OutgoingToken`/`AccessKey` from the `Index`/`Show` presenters for `View`-role callers. Additionally, verify and document whether `OutgoingToken` is used anywhere for outbound request authentication; if it is unused, consider removing it or clarifying its purpose to avoid confusion about its sensitivity.

## Proof of Concept
1. Create a Chainlink node user with role `view`.
2. Authenticate as that user and call `GET /v2/bridge_types`, `GET /v2/bridge_types/<name>`, or `GET /v2/external_initiators`.
3. Observe the JSON response includes `outgoingToken` (and `accessKey` for external initiators) in plaintext, matching the route wiring in `core/web/router.go` (lines 263–273) and the presenter code cited above — confirmable via a Go handler integration test asserting a `view`-role session receives HTTP 200 (not 401/403) with these fields populated.

	if err != nil {

	}

	}
	if err != nil {
		jsonAPIError(c, http.StatusInternalServerError, err)
		return
	}

}
