### Title
Cleartext storage of session identifiers in the `sessions` table - ([File: core/sessions/localauth/orm.go])

### Summary
Chainlink's local authentication provider stores raw, unhashed session identifiers in the `sessions` database table and uses them directly for session lookups. Unlike API tokens (which are stored with a salted hash, `TokenHashedSecret`), the session ID that is placed in the user's browser cookie and used as the sole session-authentication bearer credential is persisted in the database in cleartext. This mirrors the TYPO3 CVE-2020-26228 bug class (CWE-312): the identifier itself is not exploitable directly, but if an attacker obtains read access to the database through any other vector (e.g. SQL injection, backup exposure, replica misconfiguration), they can read valid session IDs directly and use them to hijack any active node-operator session without any additional cracking or brute forcing.

### Finding Description
Session creation inserts the raw session ID generated by `sessions.NewSession()` directly into the `sessions` table: [1](#0-0) 

Authentication of subsequent requests looks the cookie-supplied session ID directly against the same cleartext column: [2](#0-1) 

The session ID is the literal value sent via the `AuthenticateBySession` gin middleware, extracted straight from the session cookie and passed to `AuthorizedUserWithSession`: [3](#0-2) 

By contrast, the codebase's own API token mechanism intentionally avoids storing the raw secret — it salts and hashes it (`TokenHashedSecret`) precisely to prevent the secret from being usable if the row is disclosed: [4](#0-3) 

This inconsistency — hashed API tokens vs. cleartext session IDs — is the exact bug class described in the TYPO3 advisory: the session identifier column can be read directly out of the database and reused to impersonate the session, with no secondary computation needed.

### Impact Explanation
If an attacker gains any form of read access to the Chainlink node's Postgres database (SQL injection in another endpoint, a misconfigured read replica, a leaked backup, or an internal actor with limited DB privileges), they can read the `sessions.id` column and immediately use that value as a valid session cookie to impersonate any logged-in node operator/admin — including performing privileged UI/API operations (job management, key management, bridge configuration) without needing the user's password or 2FA. This is a High-severity confidentiality/integrity impact analogous to the referenced advisory, contingent on a chained disclosure vector as the advisory itself notes.

### Likelihood Explanation
Exploitation requires a secondary vector granting DB read access — it is not directly exploitable from the network. This matches the CVSS vector of the reference advisory (`AC:H`), where cleartext storage of the session identifier is the enabling factor for account takeover once any database-read primitive exists elsewhere in the stack.

### Recommendation
Store only a hash (e.g., SHA-256) of the session identifier in the `sessions` table, similar to the existing `TokenHashedSecret` pattern used for API tokens in `core/sessions/session.go`. Compare incoming session IDs by hashing them before the `SELECT ... FROM sessions WHERE id = $1` lookup in `findValidSession`, so that database disclosure alone does not yield a directly usable session credential.

### Proof of Concept
1. An operator logs into the Chainlink node UI, causing `SessionsController.Create` to call `AuthenticationProvider().CreateSession`, which inserts the raw session ID into the `sessions` table (`core/sessions/localauth/orm.go:176`).
2. Assume an attacker obtains read access to the underlying database through any chained vulnerability (e.g., SQL injection elsewhere in the deployment, exposed backup/snapshot, or misconfigured replica access).
3. The attacker runs `SELECT id FROM sessions;` and copies a valid, unexpired session ID.
4. The attacker sets this value as the `clsession` cookie and sends any authenticated API request; `AuthenticateBySession` → `AuthorizedUserWithSession` validates it directly against the cleartext table and grants the attacker the victim's authenticated session (`core/web/auth/auth.go:55-71`, `core/sessions/localauth/orm.go:87-107`), without needing the victim's password or MFA.

// findValidSession finds an unexpired session by its ID and returns the associated email.
func (o *orm) findValidSession(ctx context.Context, sessionID string) (email string, err error) {
	if err := o.ds.GetContext(ctx, &email, "SELECT email FROM sessions WHERE id = $1 AND last_used + $2 >= now() FOR UPDATE", sessionID, o.sessionDuration); err != nil {
		o.lggr.Infof("query result: %v", email)
		return email, pkgerrors.Wrap(err, "no matching user for provided session token")
	}
	return email, nil
}

// updateSessionLastUsed updates a session by its ID and sets the LastUsed field to now().
func (o *orm) updateSessionLastUsed(ctx context.Context, sessionID string) error {
	_, err := o.ds.ExecContext(ctx, "UPDATE sessions SET last_used = now() WHERE id = $1", sessionID)
	return err
}

// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired, and update session's LastUsed field.
// AuthorizedUserWithSession will return the API user associated with the Session ID if it
// exists and hasn't expired, and update session's LastUsed field.
func (o *orm) AuthorizedUserWithSession(ctx context.Context, sessionID string) (user sessions.User, err error) {
	if len(sessionID) == 0 {
		return sessions.User{}, sessions.ErrEmptySessionID
	}

	email, err := o.findValidSession(ctx, sessionID)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	user, err = o.findUser(ctx, email)
	if err != nil {
		return sessions.User{}, sessions.ErrUserSessionExpired
	}

	if err := o.updateSessionLastUsed(ctx, sessionID); err != nil {
		return sessions.User{}, err
	}

	return user, nil
}

// AuthenticateBySession authenticates the request by the session cookie.
//
// Implements authMethod
func AuthenticateBySession(c *gin.Context, authr Authenticator) error {
	ctx := c.Request.Context()
	session := sessions.Default(c)
	sessionID, ok := session.Get(SessionIDKey).(string)
	if !ok {
		return auth.ErrorAuthFailed
	}

	user, err := authr.AuthorizedUserWithSession(ctx, sessionID)
	if err != nil {
		return err
	}

	c.Set(SessionUserKey, &user)

	return nil
}

// SetAuthToken updates the user to use the given Authentication Token.
func (u *User) SetAuthToken(token *auth.Token) error {
	salt := utils.NewSecret(utils.DefaultSecretSize)
	hashedSecret, err := auth.HashedSecret(token, salt)
	if err != nil {
		return pkgerrors.Wrap(err, "user")
	}
	u.TokenSalt = null.StringFrom(salt)
	u.TokenKey = null.StringFrom(token.AccessKey)
	u.TokenHashedSecret = null.StringFrom(hashedSecret)
	return nil
}
