## Analysis

CVE-2025-47869's root cause is a fixed/hardcoded size check performed once (based on a config-time assumption) that a later runtime-populated buffer can exceed. Alt.fun's structural analog is the launch-time `uint112` headroom check in `Bonding._deployAndSeed`, which validates `virtualLtReserve` against `type(uint112).max/4` using only the exchange rate at launch time, while the actual amount of raised LT needed to satisfy the fixed-USD graduation threshold is computed later using the *live* exchange rate. This mismatch between a size guarantee fixed at "declaration time" and data that grows at "runtime" is the same bug class as the XMLRPC struct member sized against a stale constant. ### Title
Launch-time `uint112` headroom check on `virtualLtReserve` uses a stale exchange rate, allowing normal LT depreciation to overflow HyperSwap V2's reserve slot and permanently brick graduation - ([File: packages/contracts/src/Bonding.sol])

### Summary
`Bonding._deployAndSeed` bounds `virtualLtReserve` to `type(uint112).max / 4` at launch, sized on the assumption (stated in its own comment) that "the raised LT reserve peaks at `3 * virtualLtReserve`". That 3× peak is only true if the LT's `exchangeRate()` at graduation equals the exchange rate at launch. But `canGraduate`/`_prepareGraduationLiquidity` compute the real LT needed to cross the fixed `graduationThresholdUsd` using the *current* `exchangeRate()`, not the launch-time one. Since the reserve asset is an explicitly volatile leveraged token, any decline in `exchangeRate()` between launch and graduation inflates the real raw-LT amount required to hit the same USD threshold, pushing the pair's total `assetReserve` (`virtualLtReserve + realLtRaised`) past `type(uint112).max` — the hard slot size HyperSwap V2 (a standard UniswapV2-shaped AMM) enforces on its reserves.

### Finding Description
At launch:
```
uint256 virtualLtReserve = (VIRTUAL_LIQUIDITY_USD * 1e18) / exchangeRate;
if (virtualLtReserve > type(uint112).max / 4) revert ExchangeRateTooLow();
``` [1](#0-0) 

`VIRTUAL_LIQUIDITY_USD` is a fixed `$3000` and `graduationThresholdUsd` is documented as `$9K` — a "3× peg" that is only preserved at the launch-time exchange rate: [2](#0-1) 

The graduation trigger, however, is evaluated with the *live* rate at every buy:
```
uint256 realLtRaised = assetReserve - _launchTimeVirtualLtReserve(token_, pair);
uint256 valueUsd = (realLtRaised * IBounceLeveragedToken(info.ltAddress).exchangeRate()) / 1e18;
return valueUsd >= $.graduationThresholdUsd;
``` [3](#0-2) 

If the LT's `exchangeRate()` at the time the $9K threshold is crossed is lower than it was at launch by a factor `F`, the raw `realLtRaised` needed to reach `$9K` scales up by `F`: `realLtRaised ≈ 3·virtualLtReserve_launch·F`. Total `assetReserve = virtualLtReserve_launch·(1 + 3F)`. At launch the check only guarantees `virtualLtReserve_launch ≤ type(uint112).max/4`, i.e. it assumes `F = 1` exactly (`1 + 3·1 = 4`) to stay within `type(uint112).max`. Any `F > 1` — i.e. any decline in the LT's exchange rate after launch, which is the LT's normal, expected behavior since it is explicitly a leveraged/volatile asset — pushes `assetReserve` above `type(uint112).max`.

That inflated `assetReserve` (minus the drained curve portion) then has to be seeded into the HyperSwap V2 pair during `finalizeGraduation`/`_prepareGraduationLiquidity`/`_seedUniswapV2Direct`, whose `mint`/`_update` path (standard UniswapV2 semantics) hard-reverts if either token balance exceeds `type(uint112).max`. Since `finalizeGraduation` is the only path that can release the curve's parked LT and the 250M `lpReserve` tokens held in `Bonding`, an assetReserve this large makes graduation permanently unable to complete.

### Impact Explanation
`finalizeGraduation` reverting forever traps: (1) all curve-raised LT drained via `Router.graduate` inside `_prepareGraduationLiquidity` before the LP-seeding call, and (2) the 250M `lpReserve` tokens parked on `Bonding` since launch, per the documented two-phase graduation design where `Bonding` "parks all curve-raised LT and 250M tokens... between phases." [4](#0-3)  Every trader who bought into that curve is also frozen out of the post-graduation exit path since the token can never reach `Graduated` lifecycle. This is a permanent freeze of trader, creator, and protocol funds — no unprivileged rescue path is described for a stuck curve of this kind.

### Likelihood Explanation
A creator only has to launch against an LT whose `exchangeRate()` is already low enough that `virtualLtReserve` sits near the `type(uint112).max/4` ceiling (nothing prevents this — `Bonding.launch` only rejects LTs that are `!ltExists` or push `virtualLtReserve` strictly over the cap). After that, ordinary leveraged-token price volatility over the curve's (potentially multi-day) life to reach the $9K threshold is enough to push the real exchange rate below the launch-time rate, which is sufficient to breach `uint112`. No attacker-controlled exotic input, reentrancy, or privileged call is required — only normal `Zap.buy` activity plus market movement of the LT it is paired against, both of which the contract already treats as expected, ordinary conditions.

### Recommendation
Re-validate the projected `assetReserve` against `type(uint112).max` at graduation time using the *current* exchange rate (not just at launch), or size the launch-time headroom against the worst-case exchange-rate excursion the paired LT can exhibit over the curve's expected lifetime, and provide a permissionless recovery/abort path (e.g., allow graduation to proceed by capping/redenominating the LP-seeded amount, or allow trapped curve funds to be distributed pro-rata to holders) if the projected reserve would exceed the DEX's `uint112` slot.

### Proof of Concept
1. Deploy an LT whose `exchangeRate()` is already low (e.g. via normal leverage/de-leverage over time), such that `virtualLtReserve` computed in `_deployAndSeed` lands just under `type(uint112).max/4`.
2. `Zap.createToken(...)` launches the curve against that LT; the launch-time check at `Bonding.sol:484` passes.
3. Over the life of the curve, the LT's `exchangeRate()` declines (normal leveraged-token volatility, no attacker action needed) before the curve accumulates enough LT to cross `graduationThresholdUsd` via `canGraduate` (`Bonding.sol:680-695`).
4. The buy that crosses the threshold triggers `_enterGraduating`; the resulting `assetReserve` now exceeds `type(uint112).max` because `realLtRaised` was computed at the depressed live rate.
5. Anyone calls the permissionless `finalizeGraduation(token)`; the LP-seeding call into HyperSwap V2 (`_seedUniswapV2Direct`/`pair.mint`) reverts on the `uint112` overflow check every time, permanently bricking graduation and freezing the drained curve LT plus the 250M `lpReserve` tokens on `Bonding`.
