## Title
Webhook shop/topic/webhook-id identity is not bound by the HMAC signature, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` fields — which are trusted downstream to identify *which merchant* the event belongs to — are read directly from unauthenticated HTTP headers and never included in the signed content.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled straight from headers with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only the body's HMAC via `Utils::HmacValidator.validate(request)`, and then forwards the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` fields straight into `WebhookMetadata` passed to the app's handler: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute the signature over `verifiable_query.to_signable_string` (the raw body only) using the app's single, shared `Context.api_secret_key`: [4](#0-3) 

Because the same `api_secret_key` is used for every shop that has installed the app, and the signature never covers `shop-domain`/`topic`/`webhook-id`, the equality the app implicitly relies on — `shop_authenticated_by_hmac == shop_used_by_handler` — does not actually hold. Any party that can obtain one valid `(raw_body, hmac)` pair (e.g., a merchant who installed the app on their own store and inspects the webhook their own store receives) can replay that exact body/hmac to the app's public webhook endpoint while swapping the `shop-domain`, `topic`, and `webhook-id` headers to any value of their choosing. The HMAC check still passes because it never inspected those headers, and the handler executes business logic believing the event originated from a different shop.

### Impact Explanation
This breaks the shop-identity binding that webhook signature verification is supposed to provide, letting a low-privilege user of the app (any merchant who has installed it) impersonate webhook events attributed to a different tenant (a different `shop-domain`) or a different topic/webhook id. Host applications commonly key their session/data lookups by the `shop` value from `WebhookMetadata`, so this yields cross-tenant data/event confusion — an attacker-controlled webhook body being processed under an arbitrary shop's identity.

### Likelihood Explanation
Exploitability only requires the attacker to install the app on a shop they control (an unprivileged internet user relative to other merchants) and capture one webhook body+hmac pair delivered to their own endpoint — no access to `api_secret_key`, access tokens, or privileged accounts is required. The forged replay request is a straightforward HTTP POST to the app's public webhook endpoint with modified headers.

### Recommendation
Include `shop`, `topic`, and `webhook_id` (and any other header field the handler trusts) in the HMAC-signable content in `Request#to_signable_string`, or otherwise cryptographically bind them (e.g., derive them only from a per-shop-verified channel) rather than trusting raw headers once the body-only HMAC passes.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; capture a legitimate webhook delivery, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid-hmac-of-body>`.
2. Send a new POST request to the app's webhook endpoint with the same body and same `x-shopify-hmac-sha256` value, but headers:
   - `x-shopify-shop-domain: victim.myshopify.com`
   - `x-shopify-topic: <topic of attacker's choice>`
   - `x-shopify-webhook-id: <arbitrary>`
3. `Utils::HmacValidator.validate` succeeds (it only checks the body), and `Registry.process` invokes the handler with `WebhookMetadata` claiming the event is from `victim.myshopify.com`, per `lib/shopify_api/webhooks/registry.rb:190-199`.

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
