### Title
Suppliers' funds are fully frozen once market utilization exceeds `max_utilization`, with no user-side exit path — (`File: contracts/pool/src/ops/withdraw.rs`)

### Summary
`withdraw` on the pool applies `require_utilization_below_max` to the post-withdraw market state for every normal (non-liquidation) withdrawal. Because a withdrawal shrinks `supplied`, it can only worsen utilization; once `borrowed / supplied` drifts above `max_utilization` — which any borrower can push to the cap and interest accrual then tips over — every withdrawal of every size reverts with `UtilizationAboveMax`. Suppliers' assets are locked in the pool until unrelated third parties (borrowers) voluntarily repay, mirroring the reported "funds stuck until a single external actor resumes cooperating" class.

### Finding Description
`accounting()` in `contracts/pool/src/ops/withdraw.rs` calls `gate_and_debit`, which enforces `guards::require_utilization_below_max` unless the call is a liquidation or a footprint-only close (`is_liquidation || empty_close`). The guard in `contracts/pool/src/guards.rs` asserts `borrowed.div_ceil(supplied) <= max_utilization` on the in-memory cache after shares were already burned. Since burning supply reduces `supplied`, a withdrawal can never lower utilization — so when utilization is already above `max_utilization`, the check fails for any nonzero amount, including a 1-unit withdrawal that leaves cash untouched in effect. `cache.debit_cash`/`require_reserves` also blocks oversized withdrawals, but that is proportional (a smaller amount succeeds); the utilization gate is an absolute fail-closed lock on all exits.

An unprivileged path reaches this state: a borrower calls `borrow` until `borrowed/supplied == max_utilization`, then accrual (`update_indexes` is permissionless; indexes grow via millisecond-chunked interest) raises `borrowed * borrow_index` past the cap. From that block onward, `controller::withdraw` → `pool::withdraw` reverts for every supplier. There is no supplier escape hatch: `liquidate` withdrawals skip the gate but require an underwater account; `repay` by third parties or borrowers is the only way back below the cap.

### Impact Explanation
Temporary freezing of funds: all suppliers of that (hub, token) market are unable to withdraw any amount for an unbounded duration, entirely dependent on borrowers choosing to repay — economically equivalent to the reported scenario where deposits sit locked in the contract while waiting on an external actor. Interest keeps accruing to borrowers' detriment, so rational borrowers may delay repayment if the borrow rate is favorable, extending the freeze.

### Likelihood Explanation
Reachable by any unprivileged borrower the moment a market operates near its `max_utilization` cap — a normal, intended operating condition for a well-utilized market. Accrual pushing utilization over the cap requires no action at all beyond the passage of time; `update_indexes` is permissionless. No privileged flags, oracle misbehavior, or misconfiguration needed.

### Recommendation
Apply the utilization gate only to entries (borrows, strategy debt mints) and exempt all user withdrawals, or compare the pre-withdraw utilization instead of post-withdraw so withdrawals that don't worsen the breach still settle. Alternatively, cap each withdrawal at the amount that keeps utilization at `max_utilization` rather than reverting.

### Proof of Concept
1. Alice calls `controller.supply` depositing 10_000 USDC into a market whose `max_utilization` is below `RAY::ONE`.
2. Bob supplies collateral and calls `borrow`, drawing USDC until `borrowed_ceil/supplied_floor == max_utilization` (permitted — the check is `<=`).
3. Time passes; `update_indexes` accrues borrow interest, so `borrowed.div_ceil(supplied) > max_utilization`.
4. Alice calls `withdraw` with `withdrawals = [(hub, USDC, 1)]` — even a 1-unit withdrawal. `resolve_close_or_partial` burns shares, `gate_and_debit` runs `require_utilization_below_max` (not liquidation, not `empty_close`), and the assert `borrowed.div_ceil(env, supplied) <= max_utilization` fails → `CollateralError::UtilizationAboveMax`. Every supplier withdrawal of any size reverts identically until a third party repays debt. [1](#0-0) [2](#0-1) [3](#0-2)

```rust
/// Enforces reserve, utilization, and solvency guards, then debits cash for
/// the net transfer. Liquidations and footprint-only closes skip utilization.
fn gate_and_debit(env: &Env, cache: &mut Cache, net_transfer: i128, skip_utilization_check: bool) {
    cache.require_reserves(net_transfer);

    if !skip_utilization_check {
        guards::require_utilization_below_max(env, cache);
    }
    guards::require_supply_for_debt(env, cache);
    cache.debit_cash(net_transfer);
}
```

```rust
pub(crate) fn require_utilization_below_max(env: &Env, cache: &Cache) {
    if cache.supplied() == Ray::ZERO || cache.params().max_utilization >= Ray::ONE {
        return;
    }

    let borrowed = cache.borrowed().mul_ceil(env, cache.borrow_index());
    if borrowed == Ray::ZERO {
        return;
    }
    let supplied = cache.supplied().mul_floor(env, cache.supply_index());
    assert_with_error!(
        env,
        supplied > Ray::ZERO && borrowed.div_ceil(env, supplied) <= cache.params().max_utilization,
        CollateralError::UtilizationAboveMax
    );
}
```
