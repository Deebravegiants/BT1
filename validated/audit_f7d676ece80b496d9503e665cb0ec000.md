### Title
Reused zero-supply LP-mint math lets a dust pre-seeded HyperSwap pair steal the graduation liquidity deposit - (File: packages/contracts/src/Bonding.sol)

### Summary
`Bonding._seedRebalancing`'s "below-band" branch reuses `_seedDirectMint` — a helper whose entire safety argument depends on `IUniswapV2Pair.totalSupply() == 0` — in a code path that is only reachable when `totalSupply() != 0` (an attacker has already minted a real, if dust-sized, LP position on the HyperSwap V2 pair). Because the underlying `UniswapV2Pair.mint` switches from the first-mint `sqrt(amount0*amount1)` formula to the proportional `min(amount0*totalSupply/reserve0, amount1*totalSupply/reserve1)` formula once `totalSupply()>0`, an attacker who pre-seeds an imbalanced dust position can force the huge, honest `(tokensForLP, ltFromPair)` graduation deposit to mint a near-worthless amount of LP to `LPLock`, while the attacker's own pre-existing LP shares are entitled to redeem a disproportionate share of the real reserves the deposit just created.

### Finding Description
`_seedUniswapV2Direct` branches on `IUniswapV2Pair(pair).totalSupply()`: [1](#0-0) 

- Regime 1 (`totalSupply() == 0`): calls `_seedDirectMint` directly. This is safe: V2's first-mint branch uses `sqrt(amount0*amount1)` on the caller-supplied amounts alone, so the deposited ratio *is* the price.
- Regime 3 (`totalSupply() != 0`, i.e. an attacker has already minted real LP): dispatches to `_seedRebalancing`.

Inside `_seedRebalancing`, when the pre-existing reserves are small enough on *both* sides (≤ `DIRECT_MINT_PRESEED_BPS` = 1 bp of `tokensForLP`/`ltFromPair`), the code takes a shortcut and calls the *same* `_seedDirectMint` helper instead of rebalancing: [2](#0-1) 

`_seedDirectMint` itself is documented and coded only for the empty-pair case: [3](#0-2) 

But at this call site `totalSupply() != 0` is guaranteed (it is the precondition that routed execution into `_seedRebalancing` in the first place). A standard `UniswapV2Pair.mint` computes:
```
liquidity = totalSupply == 0
    ? sqrt(amount0*amount1) - MINIMUM_LIQUIDITY
    : min(amount0*totalSupply/reserve0, amount1*totalSupply/reserve1)
```
so once `totalSupply()>0` the mint output is driven by the ratio of the *newly added* amounts to the *pre-existing reserves* set by the attacker, not by the deposited amounts alone. An attacker who chooses `reserve0`/`reserve1` to be maximally lopsided relative to the eventual `tokensForLP`/`ltFromPair` ratio (while staying under the 1 bp band on both sides so the shortcut still fires) can drive the `min()` down arbitrarily, so `finalizeGraduation` mints only a tiny `liquidity` to `LPLock` even though the pair's real token/LT balances just grew by the full graduation deposit. The attacker's own dust LP tokens, unaffected by this mint, now represent a large share of `totalSupply` and are redeemable against the pair's real (post-deposit) reserves via `burn`.

### Impact Explanation
This lets an unprivileged attacker who merely (a) creates the HyperSwap V2 `TOKEN/LT` pair ahead of graduation (permissionless on any standard V2 factory) and (b) seeds it with a tiny, self-funded, deliberately imbalanced mint, capture a disproportionate share of the entire graduation liquidity — the curve-raised LT plus 25% token allocation that is supposed to be locked for the community via `LPLock.recordLock`. By later calling `burn` on their small pre-existing LP position, the attacker extracts real LT/token value they never contributed, while `LPLock` ends up holding a locked position representing only a sliver of the actual pool. This is a direct theft of LP/protocol funds and an LP permanently seeded away from the intended curve-close price — squarely a Critical-severity, concrete-theft outcome matching the required "LP seeded away from the curve close price" / "unbacked token or LT payouts" impact classes.

### Likelihood Explanation
The precondition is reachable by any address with no special privileges: creating a HyperSwap V2 pair is permissionless, and obtaining a few units of the launched `Token` (buy on the still-open curve) and the paired LT (mint via BounceTech) to seed a dust position costs only a small, bounded amount (well under the 1 bp band, which for realistic `tokensForLP`/`ltFromPair` values still leaves headroom of many orders of magnitude above the V2 `MINIMUM_LIQUIDITY` floor). `finalizeGraduation` is permissionless and keeper-driven within seconds of `TokenGraduating`, but the attacker's pre-seed must simply exist *before* that call — trivially arranged by front-running or simply acting early, since the pair can be created and seeded at any point before the token graduates. No governance action, upgrade, or off-chain compromise is required.

### Recommendation
`_seedRebalancing`'s "below-band" shortcut must not call the zero-supply `_seedDirectMint` helper when `totalSupply() != 0`. Either (a) always take the rebalance-swap + `router.addLiquidity(min=1,min=1)` path in Regime 3 regardless of how small the pre-existing reserves are (accepting the documented negligible subsidy instead of a full proportional-mint exploit surface), or (b) add an explicit guard that computes the expected `min(amount*totalSupply/reserve)` liquidity before minting and reverts/falls back to a safe path if it would round to a value disproportionately smaller than the value being deposited (e.g., compare against the reserves-based expected share). At minimum, `_seedDirectMint` should assert `IUniswapV2Pair(pair).totalSupply() == 0` before transferring funds and calling `mint`, so a future refactor cannot silently reintroduce this same reuse bug.

### Proof of Concept
1. Attacker predicts/creates the HyperSwap V2 pair for `(token, lt)` via the standard `IUniswapV2Factory.createPair` before the token graduates.
2. Attacker buys a tiny amount of `token` on the still-open curve (`Zap.buy`) and mints a tiny amount of `lt` (BounceTech `mint`), then transfers both to the pair and calls `pair.mint(attacker)` directly, choosing amounts such that:
   - `reserveToken * 10_000 <= expectedTokensForLP * 1` and `reserveLT * 10_000 <= expectedLtFromPair * 1` (stays under `DIRECT_MINT_PRESEED_BPS`), and
   - `reserveToken : reserveLT` is deliberately far from the curve-close ratio the graduation will later use, with one side picked to be extremely small relative to its corresponding deposit amount.
   - This mint succeeds (satisfies V2's `MINIMUM_LIQUIDITY`), giving the attacker `T` LP tokens and setting `totalSupply() = T > 0`.
3. The token graduates normally (buys push it past `canGraduate`), caching `tokensForLP`/`ltFromPair` in `Bonding.pendingGraduation` via `_enterGraduating`.
4. Anyone calls `Bonding.finalizeGraduation(tokenAddress)`. `_ensureUniswapV2Pair` finds the attacker's pre-existing pair; `_seedUniswapV2Direct` sees `totalSupply() != 0` and enters `_seedRebalancing`; because both reserves are under the 1 bp band, it calls `_seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair)`.
5. `_seedDirectMint` transfers the full `tokensForLP`/`ltFromPair` into the pair and calls `pair.mint(lpLock)`. Since `totalSupply() = T != 0`, V2 computes `liquidity = min(tokensForLP*T/reserveToken, ltFromPair*T/reserveLT)`, which the attacker engineered to be minimal.
6. Attacker calls `pair.burn` (via the standard V2 pair) redeeming their `T` LP tokens against the pair's now-inflated real balances, extracting a disproportionate share of the deposited `tokensForLP`/`ltFromPair` — value that should have been exclusively locked in `LPLock` for the protocol/community.     /// @dev Transfer the full `(tokensForLP, ltFromPair)` to the pair and
    ///      `mint` the LP to `LPLock`, opening at the exact cached
    ///      curve-close ratio. Used by the empty-pair regime and as the
    ///      dust-pre-seed fallback in `_seedRebalancing` — against dust
    ///      reserves the V2 `min()` formula's donation to any pre-existing
    ///      LP is negligible (see `_seedUniswapV2Direct` natspec). Any TOKEN
    ///      remainder (a skimmed pure-donation pre-seed) is burned; the LT
    ///      remainder is left for `finalizeGraduation`'s `_sweepLTToOwner`
    ///      post-bookend.
    function _seedDirectMint(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair
    ) internal returns (uint256 liquidity) {
        IERC20(tokenAddress).safeTransfer(pair, tokensForLP);
        IERC20(lt).safeTransfer(pair, ltFromPair);
        liquidity = IUniswapV2Pair(pair).mint(_s().lpLock);
        uint256 leftoverToken = IERC20(tokenAddress).balanceOf(address(this));
        if (leftoverToken > 0) {
            Token(tokenAddress).burn(address(this), leftoverToken);
        }
    }

    function _seedRebalancing(
        address tokenAddress,
        address lt,
        address pair,
        uint256 tokensForLP,
        uint256 ltFromPair,
        uint256 protectedLT
    ) internal returns (uint256 liquidity) {
        (uint112 r0, uint112 r1,) = IUniswapV2Pair(pair).getReserves();
        bool tokenIs0 = IUniswapV2Pair(pair).token0() == tokenAddress;
        (uint256 reserveToken, uint256 reserveLT) = tokenIs0 ? (uint256(r0), uint256(r1)) : (uint256(r1), uint256(r0));

        // Below the band on BOTH sides, overpower the pre-seed with a direct
        // mint at the cached ratio: the rebalance swap is too coarse to reach
        // the ratio against such small reserves, and the pre-existing LP's
        // claim on the deposit stays bounded by `DIRECT_MINT_PRESEED_BPS`. A
        // side that is large relative to its LP target still takes the
        // rebalance path so it isn't donated under the empty-mint `min()`.
        if (
            reserveToken * BPS_DENOM <= tokensForLP * DIRECT_MINT_PRESEED_BPS
                && reserveLT * BPS_DENOM <= ltFromPair * DIRECT_MINT_PRESEED_BPS
        ) {
            return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
        }

        // Budget reads `balanceOf(this)` rather than `tokensForLP` /
        // `ltFromPair` so any skim donation contributes to the rebalance
        // and not only to `_routerDepositAndDispose`'s deposit.
        // Direction: pool TOKEN-rich vs target ⇒ swap LT in (TOKEN out).
        // Pool LT-rich ⇒ swap TOKEN in (LT out). Bounded by uint112 reserves
        // and curve-close-shape targets, both products fit in uint256.
        // When `_pairRebalance` returns false the seed is too small for any
        // swap to move the ratio (its fee-charging quote rounds to zero), so
        // the reserves are negligible against this graduation's inventory:
        // overpower them with a direct mint at the cached ratio rather than
        // letting the router deposit at the attacker's ratio. A swap that
        // does fire leaves the pool ≈ at target for the router deposit.
        if (reserveToken * ltFromPair > reserveLT * tokensForLP) {
            // Pool TOKEN-rich. tokenIn = lt, tokenOut = tokenAddress.
            // tokenInIs0 = (lt is token0) = !tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: lt,
                        tokenInIs0: !tokenIs0,
                        reserveIn: reserveLT,
                        reserveOut: reserveToken,
                        targetN: ltFromPair,
                        targetD: tokensForLP,
                        maxSwap: _swapBudget(_ltSwapInventory(lt, protectedLT))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        } else if (reserveToken * ltFromPair < reserveLT * tokensForLP) {
            // Pool LT-rich. tokenIn = tokenAddress, tokenInIs0 = tokenIs0.
            if (!_pairRebalance(
                    RebalanceParams({
                        pair: pair,
                        tokenIn: tokenAddress,
                        tokenInIs0: tokenIs0,
                        reserveIn: reserveToken,
                        reserveOut: reserveLT,
                        targetN: tokensForLP,
                        targetD: ltFromPair,
                        maxSwap: _swapBudget(IERC20(tokenAddress).balanceOf(address(this)))
                    })
                )) {
                return _seedDirectMint(tokenAddress, lt, pair, tokensForLP, ltFromPair);
            }
        }
        // else: pool already at curve-close ratio (rare — e.g. attacker
        // pre-seeded at exactly target). Skip swap, deposit directly.

        return _routerDepositAndDispose(tokenAddress, lt, protectedLT);
    }
