### Title
Pool creation does not reject coin/pc mints with a freeze authority, allowing permanent freezing of vault funds - ([File: program/src/processor.rs])

### Summary
The Solana analog of an ERC20 "pausable" token is an SPL mint with a non-null `freeze_authority`, which lets the mint's freeze authority freeze any token account for that mint (including the AMM's vaults), blocking all transfers from/to it. `Self::process_initialize2` checks the newly-created LP mint for a freeze authority but never checks the user-supplied `coin_mint`/`pc_mint` that back the pool's vaults.

### Finding Description
In `process_initialize2`, after unpacking `coin_mint` and `pc_mint` [1](#0-0) , the program only validates freeze authority on the LP mint it itself creates: [2](#0-1) 

It validates `delegate` and `close_authority` on the coin/pc vault token accounts [3](#0-2)  and [4](#0-3) , but there is no equivalent check that `coin_mint.freeze_authority` or `pc_mint.freeze_authority` is `None`. Any pool creator can therefore initialize a pool with an underlying coin or pc mint that has an active freeze authority (analogous to Yearn's pausable yTokens in the referenced report, or real-world tokens like USDC/USDT which retain freeze authorities on Solana).

Once such a pool is live, `Deposit`, `Withdraw`, `SwapBaseIn`, and `SwapBaseOut` all rely on unconditional `spl_token::instruction::transfer`/`transfer_with_authority` CPIs against the vault accounts [5](#0-4)  and [6](#0-5) , invoked from every swap/deposit/withdraw path, e.g. withdraw [7](#0-6)  and swap [8](#0-7) . If the mint's freeze authority freezes the coin or pc vault account, all of these SPL Token transfer instructions will fail on-chain (the SPL Token program rejects transfers on frozen accounts), permanently halting withdrawals and swaps for that pool while LP and swap funds remain locked inside the vault.

### Impact Explanation
This is a permanent freezing-of-funds condition for all LPs and traders of a pool created with a freezable mint: withdrawals, deposits, and swaps become impossible once the mint's freeze authority freezes the vault ATA. Unlike the `close_authority`/`delegate` checks that were clearly considered and enforced for vault accounts, no analogous check exists for the mint's `freeze_authority`, so the protocol has an inconsistent, incomplete defense against this exact class of risk it otherwise guards against.

### Likelihood Explanation
Likelihood depends on whether real freezable tokens are paired into pools; anyone (an attacker or the pool creator itself, or simply an ordinary user unaware of a token's freeze authority) can call `Initialize2` with any SPL mint of their choosing, since `Initialize2` is a fully unprivileged, permissionless instruction reachable from a single transaction. There is no mint allow-list enforced on-chain, so a malicious pool creator could also intentionally pair a token whose freeze authority they control (or collude with) to later freeze LP funds after attracting liquidity — a rug-pull vector without owning the actual token supply.

### Recommendation
Add symmetric checks in `process_initialize2` requiring `coin_mint.freeze_authority.is_none()` and `pc_mint.freeze_authority.is_none()` (reusing `AmmError::InvalidFreezeAuthority`), consistent with the existing `lp_mint.freeze_authority` check and the vault `close_authority`/`delegate` checks, to reject pool creation for freezable underlying tokens.

### Proof of Concept
1. Create/control an SPL mint `M` with `freeze_authority = attacker`.
2. Call `Initialize2` with `coin_mint = M` (or `pc_mint = M`); the program only checks `lp_mint.freeze_authority` [9](#0-8) , not `M`'s, so pool creation succeeds and users deposit liquidity/trade normally.
3. As the freeze authority of `M`, call SPL Token's `FreezeAccount` on the AMM's coin (or pc) vault token account (its address/owner are deterministic and public).
4. Any subsequent `Deposit`, `Withdraw`, `SwapBaseIn`, or `SwapBaseOut` touching that vault fails because the underlying `spl_token::instruction::transfer` CPI in `Invokers::token_transfer`/`token_transfer_with_authority` [10](#0-9)  is rejected by the SPL Token program for a frozen source/destination account, permanently locking LP and swap funds in the pool.

    /// Issue a spl_token `Transfer` instruction.
    pub fn token_transfer<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        owner: AccountInfo<'a>,
        deposit_amount: u64,
    ) -> Result<(), ProgramError> {
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            owner.key,
            &[],
            deposit_amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, owner, token_program],
            &[],
        )
    }

    /// Issue a spl_token `Transfer` instruction.
    pub fn token_transfer_with_authority<'a>(
        token_program: AccountInfo<'a>,
        source: AccountInfo<'a>,
        destination: AccountInfo<'a>,
        authority: AccountInfo<'a>,
        amm_seed: &[u8],
        nonce: u8,
        amount: u64,
    ) -> Result<(), ProgramError> {
        let authority_signature_seeds = [amm_seed, &[nonce]];
        let signers = &[&authority_signature_seeds[..]];
        let ix = spl_token::instruction::transfer(
            token_program.key,
            source.key,
            destination.key,
            authority.key,
            &[],
            amount,
        )?;
        solana_program::program::invoke_signed(
            &ix,
            &[source, destination, authority, token_program],
            signers,
        )
    }
