### Title
Webhook shop/topic identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
The `merge()` bug in the reference report is a "credential double-use" caused by allowing an unauthenticated/mismatched identity (a fresh token) to inherit the authority of an already-consumed credential without being covered by the invariant that should bind them together. The equivalent class of bug in this gem is: a field that is *acted on* by application logic is not covered by the cryptographic binding (HMAC) that is supposed to authenticate the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, and `webhook_id` fields, however, are read directly from unauthenticated HTTP headers and are never included in the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC of the raw body via `Utils::HmacValidator.validate`, and then forwards the *unauthenticated* `shop` value straight to the app's webhook handler: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC using `Context.api_secret_key`, which is the app's single, shop-independent client secret shared across every merchant that installs the app: [4](#0-3) 

Because the same `api_secret_key` produces a valid signature for *any* shop, and the `shop` header is excluded from `to_signable_string`, a party who legitimately installs the app on their own store (an unprivileged action) can capture one of their own genuinely-signed webhook deliveries (valid body + valid HMAC) and replay it to the app's webhook endpoint after substituting the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header with a victim shop's domain. The HMAC check still passes because it never covered those headers, yet `WebhookMetadata.shop` — which the app's handler trusts to select the tenant's data/session — now falsely asserts the victim shop.

This is the equality that is broken:
`shop_bound_by_HMAC == shop_used_by_handler` is assumed by the library's API but is actually `∅ == request.shop` (never checked).

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` (as returned by `Registry.process`) to select which merchant's session/data to act on — the pattern explicitly demonstrated in the gem's own test suite (`data.shop` in handler callbacks) — can be made to apply attacker-supplied webhook payloads to a different, victim tenant's context. This crosses the tenant boundary using only a signature that is valid across the whole app (not shop-scoped), qualifying as cross-tenant access.

### Likelihood Explanation
The prerequisite is low: an attacker only needs to install the target app on their own (attacker-controlled) store — a normal, unprivileged action any Shopify merchant/developer can take — in order to obtain one legitimately HMAC-signed webhook body/signature pair. No access token, `api_secret_key`, or victim credentials are required. Header spoofing on an HTTP POST is trivial.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string (or otherwise cryptographically bind them to the payload), or require the caller to independently corroborate the header-derived `shop` against a shop known to be associated with the signing secret before trusting `WebhookMetadata#shop` in handler logic.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`, triggering Shopify to send a legitimate webhook: body `B`, header `X-Shopify-Hmac-Sha256: HMAC(secret, B)`, header `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker replays this exact body `B` and HMAC header unmodified to the same app endpoint, but changes `X-Shopify-Shop-Domain` to `victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` object; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` (unchanged) with the app's `api_secret_key` (shop-independent) — see `lib/shopify_api/utils/hmac_validator.rb:26-31` and `lib/shopify_api/webhooks/request.rb:35-38`.
4. `Registry.process` invokes the app's handler with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"victim-shop.myshopify.com"` — see `lib/shopify_api/webhooks/registry.rb:198-199` — despite the payload actually originating from the attacker's own shop.
