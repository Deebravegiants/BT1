### Title
Webhook `shop` identity is not bound to the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by checking that the HMAC of the raw request body matches a signature computed with the app's `client_secret` [1](#0-0) . The `hmac`/`to_signable_string` implementation in `ShopifyAPI::Webhooks::Request` only signs `@raw_body`, never the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers [2](#0-1) . The verified `shop` field the app relies on for tenant identity is not part of the signed material.

### Finding Description
The identity binding that should hold is: `shop attributed to the webhook == shop whose event actually produced the HMAC-signed body`. In this gem that binding does not exist.

`Request#shop` is read directly from the `x-shopify-shop-domain`/`shopify-shop-domain` header with no cryptographic tie to the body [3](#0-2) . `HmacValidator.validate` computes the signature only from `verifiable_query.to_signable_string`, which for a webhook `Request` is just the raw body [4](#0-3) . Because every shop that installs the same app shares the same `client_secret`, any body that Shopify legitimately signed for shop A's own event (e.g., a webhook the attacker triggered on their own store, which they fully control and can host) carries a valid HMAC regardless of which shop header is attached to the HTTP request that delivers it to the app's endpoint.

An unprivileged internet user who has installed the app on their own shop can:
1. Trigger a webhook-eligible event on their own shop (e.g., `orders/create`) to obtain a body + valid `x-shopify-hmac-sha256` pair signed with the app's `client_secret`.
2. Replay that exact body/HMAC pair directly to the app's public webhook endpoint, substituting the `x-shopify-shop-domain` header with a victim shop's domain.
3. `Registry.process` accepts it — `Utils::HmacValidator.validate` passes because the body/HMAC pair is genuinely valid — and dispatches `WebhookMetadata.new(shop: request.shop, ...)` to the app's handler with the forged victim shop [5](#0-4) .

The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify" [6](#0-5)  and instructs handlers to key persistence and background jobs off `data.shop` [7](#0-6) , so a host app following the documented API has no way to know it must independently verify the shop is authorized/installed before trusting `data.shop`.

### Impact Explanation
This is a cross-tenant integrity/data-injection issue: an attacker who has installed the app on any shop can forge webhook events attributed to any other shop known to have installed the app, because the `shop` field trusted by every downstream handler is never bound to the signed bytes. Depending on the handler (e.g., updating local records keyed by `shop`, enqueuing shop-scoped jobs, `shop/redact` or `customers/data_request` compliance handling), this allows cross-tenant data corruption or disclosure without any credential belonging to the victim shop.

### Likelihood Explanation
The webhook endpoint is a public, unauthenticated HTTP route by design (Shopify calls it directly). Obtaining a valid signed body only requires the attacker to install the app on their own shop and trigger an event — no secrets, tokens, or privileged access to the victim are needed. The forged replay is a trivial header substitution.

### Recommendation
Bind the shop identity to the HMAC computation, or otherwise cryptographically/authoritatively verify that the `shop-domain` header matches the shop the webhook subscription actually belongs to (e.g., cross-check the `webhook_id`/subscription against a server-side record of which shop it was registered for, or require the app to look up and validate the installed shop before trusting `data.shop`). Shopify's own guidance for compliance webhooks explicitly recommends validating the shop against known installed shops before acting on webhook data.

### Proof of Concept
1. As an unprivileged user, install the target app on shop `attacker.myshopify.com` and register/receive an `orders/create` webhook. Capture the raw POST body and `x-shopify-hmac-sha256` header Shopify sent — this HMAC is valid because it is computed with the app's shared `client_secret` over the body only [8](#0-7) .
2. Send a new HTTP POST to the app's public webhook endpoint with the exact same body and `x-shopify-hmac-sha256`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `raw_body` only and succeeds [9](#0-8) .
4. The handler receives `WebhookMetadata` with `shop == "victim.myshopify.com"` and attacker-influenced `body`, even though the request never touched the victim's shop [10](#0-9) .
