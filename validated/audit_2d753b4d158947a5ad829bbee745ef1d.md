### Title
Webhook shop identity spoofing via HMAC that only covers the body, not the `shop-domain` header - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body. The `shop` (and `topic`, `webhook-id`) values that are then handed to the app's handler as trusted tenant-identifying metadata are read directly from HTTP headers that are **not** covered by the HMAC signature. Because a single app's `client_secret` is shared across every shop that installs the app, a valid `(body, hmac)` pair captured from one shop's own webhook delivery remains cryptographically valid when replayed with a different `shop-domain` header, letting an unprivileged app-installer spoof another tenant's shop identity in the data delivered to the app's webhook handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

and `#shop` is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates only that the HMAC over the body is correct, then forwards the header-derived, unauthenticated `shop` value into `WebhookMetadata` which the handler treats as the trusted tenant identity: [3](#0-2) 

`Utils::HmacValidator.compute_signature` signs with `Context.api_secret_key`, which is the same secret for *every* shop that has installed the app (it is the app's client secret, not a per-shop secret): [4](#0-3) 

The identity binding that is broken is: **shop authenticated (via HMAC over body, verified with the app-wide secret) ≠ shop acted upon (header value used to tag `WebhookMetadata.shop`, not covered by the HMAC)**. Since the HMAC never includes the `shop-domain` header, any two webhook deliveries for the same app that happen to carry byte-identical bodies (e.g., identical topic/payload shape, which is common for many webhook topics that don't embed the shop in the body) produce identical valid HMACs regardless of which shop the header claims to be from.

### Impact Explanation
An app installer (an unprivileged user with respect to other tenants of the same app) can capture a legitimate webhook Shopify sends to their own store, then replay that exact body+HMAC to the app's public webhook endpoint while substituting the `shop-domain` header of a different shop. Because `Registry.process` only checks the HMAC over the body — which is unaffected by the header — the check passes, and the app's handler receives `WebhookMetadata` claiming the payload originated from the victim shop. Any app logic that trusts `WebhookMetadata#shop` to scope data writes/reads (exactly as documented and intended by this gem's API) can therefore be tricked into associating attacker-controlled webhook content with another merchant's tenant, i.e., cross-tenant data confusion/injection.

### Likelihood Explanation
Any developer/merchant who can install the app on their own store already receives genuine, validly-signed webhook deliveries and can capture body+HMAC pairs at will using nothing more than their own store's install (no leaked credentials, no access token, no client secret needed). Replaying with a modified header requires only sending an HTTP request to the app's public webhook endpoint, which is by design internet-reachable.

### Recommendation
Bind the shop identity into the signature verification: either compute/verify the HMAC over a canonical string that includes the `shop-domain` (and other routing headers) rather than the body alone, or otherwise cryptographically tie the header-derived `shop` to the payload before constructing `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be trusted as tenant-authoritative without additional verification (e.g., comparing to session/shop records established via OAuth).

### Proof of Concept
1. Install the target app on `attacker-shop.myshopify.com`; wait for Shopify to deliver a genuine webhook (e.g. `orders/create`) with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Replay the request to the app's webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H` unchanged, but set `shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Utils::HmacValidator.validate(request)` in `lib/shopify_api/webhooks/registry.rb` line 190 returns `true` (HMAC only covers `B`), so `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed_body, ...)`, causing the app to act on attacker-supplied data as if it belonged to `victim-shop`.
