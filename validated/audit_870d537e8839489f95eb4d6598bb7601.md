### Title
Emporium Min-proof path lets an unprivileged caller run arbitrary, unsigned, unaccounted `EmporiumOperation`s from Emporium's identity - (File: `contracts/CircomDataBuilder.sol`, `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
When `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only forces the circuit to prove `message == Poseidon(messageSeed)` [1](#0-0) . Everything else in `CircomData` — including the entire `EmporiumStack` passed as `externalActionMetadata` — is uninspected by the proof. If the attacker sets `EmporiumStack.signerAddress == address(0)`, `EmporiumUpgradeable.verifyWallet` skips the EIP‑712 signature check entirely [2](#0-1) , and because `erc20TokenAddresses` is forced empty, both `Hinkal.transact`'s balance/slippage loop and `EmporiumUpgradeable.runAction`'s `balancesBefore/After` loop iterate zero times [3](#0-2) [4](#0-3) . The stateless op branch then executes `op.endpoint.call{value: op.value}(op.callData)` as Emporium with no signature and no balance accounting [5](#0-4) .

### Finding Description
Broken equality: "assets Emporium can move in this tx" should equal "assets accounted in `balancesBefore`/`balancesAfter`" (and, at the `Hinkal.transact` level, `balanceDif == amountChanges[i] + utxoAmount` for every token touched). With the Min path this equality is vacuously satisfied because the accounted-token set is empty by construction, while the actual set of assets an arbitrary `op.endpoint.call` can touch is unbounded.

Path: `Hinkal.transact` → `hinkalHelper.performHinkalChecks` → `CircomDataBuilder.formInputForCircom` selects `formInputEmporiumMin` because `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0` [6](#0-5) . `dimensionsCheck` only requires internal-consistency of lengths (`erc20TokenAddresses.length == dimensions.tokenNumber`, etc.) and does not forbid `tokenNumber == 0` for this action id [7](#0-6) . `buildVerifierId` derives a verifier id from `(tokenNumber=0, nullifierAmount=0, outputAmount=0, HINKAL_EMPORIUM_ACTION_ID)`, and a dedicated 3-input verifier (`VerifierEVMMin0v4`, matching `MainEVMCircuitMin`) is registered for exactly this combination, confirming this zero-token path is a supported, deployed configuration, not a theoretical corner case [8](#0-7) [9](#0-8) .

The proof itself only constrains `message = Poseidon(messageSeed)`, a value the attacker chooses freely off-chain; `calldataHash` and `timeStamp` are also attacker-supplied and merely checked for internal self-consistency via `getHashedCalldata` [10](#0-9) . Nothing in `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` inspects the contents of `externalActionData.externalActionMetadata` (the `EmporiumStack`).

`Hinkal._externalTransact` builds `deltaAmountChanges` with length `erc20TokenAddresses.length == 0`, so no funds are transferred into Emporium before the call, and calls `EmporiumUpgradeable.runAction` (allowed because `onlyAllowedRecipient` only checks `msg.sender == Hinkal`, which is satisfied by the normal call path) [11](#0-10) [12](#0-11) .

Inside `runAction`, `EmporiumStack` is decoded straight from attacker-controlled bytes [13](#0-12) . `verifyWallet` is called; with `stack.signerAddress == address(0)` it only marks `emporiumMessage` used and returns — **no signature is required at all** for this case [2](#0-1) . The ops loop then executes each `EmporiumOperation` as a raw external call from Emporium's own address, with the only restriction being that the stateless branch cannot call `callHinkalWallet`/`doSendToRelay` selectors — any other target/calldata/value is allowed [5](#0-4) . Because `erc20TokenAddresses` is empty, `balancesBefore`/`balancesAfter` are empty arrays, so no `BalanceChangeShouldBePositive` check or `handleOut` accounting is performed for any token or ETH the ops touch, and the outer `Hinkal.transact` loop that computes `balanceDif` is likewise empty. There is no invariant left in the call path that ties "what the ops did" to "what was declared/paid for."

Exploit flow: the attacker (1) picks an arbitrary `messageSeed`, computes `message = Poseidon(messageSeed)`, generates a valid `MainEVMCircuitMin` proof for it (no secrets required, purely self-chosen); (2) builds `CircomData` with `externalActionData = {externalAddress: Emporium, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{signerAddress: address(0), ops: [maliciousOp], ...})}`, `erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, matching `dimensions.tokenNumber = 0`; (3) sets `maliciousOp = {endpoint: victimToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.approve, (attacker, type(uint256).max))}`; (4) calls `Hinkal.transact(...)`. The call succeeds, and Emporium has now granted the attacker an unlimited allowance over `victimToken`, at zero cost and requiring no signature, no deposit, and no privileged role. Any tokens that later transit through Emporium in-flight during a legitimate user's swap (deposited into Emporium before its ops run, per `Hinkal._externalTransact`'s negative-`deltaAmountChanges` transfer) or any residual/idle balance Emporium holds can subsequently be pulled out by the attacker via a plain `transferFrom` call on the token contract, completely outside of Hinkal's accounting. The same crafted `(a,b,c, circomData)` tuple is also replayable on any other chain sharing the same Emporium/verifier deployment and an initial/empty Merkle root, since `formInputEmporiumMin`'s public inputs (`emporiumMessage`, `timeStamp`, `calldataHash`) contain no chain id and `usedMessages` is a per-chain mapping.

### Impact Explanation
This lets an unprivileged attacker execute arbitrary calls (including `approve`, `transferFrom`, or direct value-bearing calls) as Emporium's identity with zero economic accounting and zero authorization when `signerAddress == 0`. This can be used to (a) directly drain any ETH/token balance Emporium happens to hold, and (b) plant standing `approve` grants that let the attacker steal any user funds that later transit Emporium in-flight during legitimate swaps/wallet operations. This matches Critical severity: "direct theft of shielded or in-flight user funds" and "executing calls or moving assets... never authorised." It is repeatable per message nonce (bounded only by `usedMessages`, but each new `messageSeed` yields a fresh unused message, so it is repeatable indefinitely), and is further amplifiable via cross-chain replay of the same proof against separate Emporium deployments.

### Likelihood Explanation
Preconditions are minimal and fully within an unprivileged attacker's control: they only need to (1) generate a valid `MainEVMCircuitMin` proof for a self-chosen `messageSeed` (no secret UTXO/tree knowledge required), (2) know Emporium's registered `externalActionId`/address (public), and (3) craft the `EmporiumStack` bytes. No deposit, no relay, no admin role, and no victim cooperation are needed to reach and execute `runAction` with an unsigned, unaccounted op set. The only requirement for realizing direct fund theft (beyond planting approvals) is that Emporium holds or later handles token/ETH balance — which is a normal, expected operational state for an in-flight swap intermediary contract.

### Recommendation
- Do not allow `EmporiumStack.signerAddress == address(0)` (i.e., skip of signature verification) to be combined with the zero-token Min-proof path; require either a valid EIP-712 signature for every op set, or forbid the min-input path from invoking `runAction`'s op-execution loop at all.
- Bind `erc20TokenAddresses`/`amountChanges` (or an explicit "no value moves" commitment) into the circuit's public inputs even for the min path, or otherwise ensure `EmporiumUpgradeable.runAction`'s balance accounting cannot be structurally bypassed by supplying an empty token array.
- Have `formInputEmporiumMin` (or a stricter successor) constrain a hash/commitment of `externalActionMetadata` so that the proof actually authorizes the specific ops being executed, not just an arbitrary `message` preimage.
- Include `block.chainid` in the public inputs consumed by the min circuit to prevent cross-chain replay of the same proof/message.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as allowed recipient of Hinkal), register `HINKAL_EMPORIUM_ACTION_ID → Emporium` via `registerExternalAction`, register `VerifierEVMMin0v4` for `buildVerifierId({tokenNumber:0, nullifierAmount:0, outputAmount:0}, HINKAL_EMPORIUM_ACTION_ID)`.
2. Deploy a mock ERC20 `victimToken`, mint balance to an address representing "Emporium in-flight funds" (simulate by having a benign prior transaction leave `X` tokens in Emporium, or directly `victimToken.mint(address(emporium), X)` to model resting/idle balance).
3. Off-chain: pick `messageSeed`, compute `message = Poseidon(messageSeed)`; generate a real Groth16 proof for `MainEVMCircuitMin` with public inputs `(outTimeStamp, calldataHash)` matching the crafted `CircomData`.
4. Build `CircomData` with `erc20TokenAddresses = []`, `amountChanges = []`, `onChainCreation = []`, `slippageValues = []`, `externalActionData = {externalAddress: emporium, externalActionId: HINKAL_EMPORIUM_ACTION_ID, externalActionMetadata: abi.encode(EmporiumStack{signerAddress:address(0), ops:[{endpoint: address(victimToken), invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.approve,(attacker, type(uint256).max))}], maxFee:0, deadline:type(uint256).max})}`, valid `rootHashHinkal`/`rootHashHinkalIndex` pointing at an existing (e.g. empty-tree) root, `calldataHash` matching `getHashedCalldata`.
5. Call `hinkal.transact(a,b,c,dimensions,circomData)` from attacker EOA — assert it succeeds.
6. Assert `victimToken.allowance(address(emporium), attacker) == type(uint256).max`.
7. Call `victimToken.transferFrom(address(emporium), attacker, X)` from attacker — assert `victimToken.balanceOf(attacker) == X` and `victimToken.balanceOf(address(emporium)) == 0`, i.e., attacker gained Emporium's resting balance with no corresponding `amountChanges`/`balanceDif` ever being recorded by `Hinkal.transact` or `EmporiumUpgradeable.runAction`.
