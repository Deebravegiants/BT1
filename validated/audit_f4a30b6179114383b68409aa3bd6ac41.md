### Title
Unchecked-length signature copy into fixed-size array causes runtime panic on malformed BEEFY naive consensus proof - (File: evm/rust/src/conversions.rs)

### Summary
Confirmed by the tool outputs, `submit_proof` in `pallet-beefy-consensus-proofs` is a **signed but permissionless** extrinsic — "Proofs are submitted via signed extrinsics: the signer of the extrinsic is the reward payee" [1](#0-0) . Any account can submit a `PROOF_TYPE_NAIVE` proof, which is ABI-decoded and converted with `.into()` [2](#0-1) .

### Finding Description
The conversion chain from the naive BEEFY proof reaches `impl From<Vote> for SignatureWithAuthorityIndex`:
```
let sig_bytes = value.signature.to_vec();
let mut signature: TSignature = [0u8; 65];
signature.copy_from_slice(&sig_bytes);
``` [3](#0-2) 

`Vote.signature` is a Solidity `bytes` field (unconstrained length) decoded via `abi_decode_params` from fully attacker-controlled calldata [2](#0-1) , then converted into `ConsensusMessage` via `BeefyConsensusProof -> ConsensusMessage -> MmrProof -> RelayChainProof.signedCommitment.votes` [4](#0-3) . `copy_from_slice` panics if `sig_bytes.len() != 65` ("source slice length does not match destination length"), and there is no length check anywhere upstream of this conversion in the searched code.

This is the direct structural analog of the reported bug class: an untrusted, attacker-controlled length is used to populate a fixed-size buffer without a bounds/length check first, causing a crash. The codebase's own fix pattern elsewhere (e.g. `ByteVector<N>::decode` explicitly checking `bytes.len() != N` before use [5](#0-4) , and the `as_utf8_string` deserializer regression fix which replaced an unchecked `copy_from_slice` with a checked `try_into` after it "crashed the production node" [6](#0-5) ) confirms this exact panic pattern has previously caused production outages in this codebase, but the `Vote -> SignatureWithAuthorityIndex` conversion was not included in that hardening pass.

### Impact Explanation
A panic inside the runtime during `handle_incoming_message` execution (triggered from `submit_proof`) aborts the extrinsic's execution in a way that, depending on how panics propagate through FRAME dispatch, can disrupt block production/import for the coprocessor consensus route — effectively a denial-of-service against the BEEFY naive proof ingestion path used to deliver Hyperbridge messages, matching the "route unable to deliver messages" acceptance criterion. This mirrors the CVSS profile of the reference bug (Availability: High, no confidentiality/integrity impact).

### Likelihood Explanation
High: `submit_proof` is a permissionless, ordinarily-signed extrinsic reachable by anyone willing to pay (or in the case of a failed proof) a transaction fee; the `PROOF_TYPE_NAIVE` branch is explicitly a supported/allowed proof type [7](#0-6) , and constructing an ABI-encoded `Vote` with a `signature` field of any length other than 65 bytes requires no cryptographic capability — only crafting calldata.

### Recommendation
Replace the unchecked `copy_from_slice` in `From<Vote> for SignatureWithAuthorityIndex` with a length-checked conversion (e.g., `TryFrom`/`try_into` returning an error) analogous to the pattern already used in `evm/rust/src/conversions.rs` test helpers (`slice.try_into().expect(...)`) and in `ByteVector<N>::decode`, propagating a decode error instead of panicking, and ensure all call sites (`RelayChainProof -> MmrProof`, `BeefyConsensusProof -> ConsensusMessage`) surface it as a typed `Result` up through `verify_and_apply`/`do_submit_proof`.

### Proof of Concept
1. Craft ABI calldata for `pallet_beefy_consensus_proofs::submit_proof` with `proof[0] = PROOF_TYPE_NAIVE`.
2. ABI-encode a `BeefyConsensusProof` whose `relay.signedCommitment.votes[0].signature` is a `bytes` value of length ≠ 65 (e.g., 0 or 64 bytes) — `authorityIndex` and other fields can be arbitrary/zero since the panic occurs before signature verification.
3. Submit as a signed extrinsic from any account.
4. `verify_and_apply` -> `abi_decode_params::<BeefyConsensusProof>` succeeds (Solidity does not constrain `bytes` length) -> `.into()` -> `From<Vote> for SignatureWithAuthorityIndex` -> `signature.copy_from_slice(&sig_bytes)` panics.

Note: I was unable to fully trace how a Rust panic inside this specific pallet call propagates in the exact hyperbridge runtime configuration (whether it aborts only the extrinsic via `frame_support`'s panic-to-error boundary or affects block execution more broadly), since that runtime wiring was not part of the indexed/retrieved code. This should be verified in a live/test environment before finalizing severity.
