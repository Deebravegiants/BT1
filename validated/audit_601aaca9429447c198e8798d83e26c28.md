## Title
Cross-chain `IntentGatewayV2.withdraw()` on Tron reverts on a zero-escrow token, blocking legitimate escrow release/refund for the whole batch - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2` implements a batched, per-token escrow release/refund routine (`withdraw`) that reverts the entire call with `UnknownOrder()` if *any* token in the batch already has zero escrowed balance, rather than skipping that entry like the canonical EVM implementation does. This mirrors the Karak `slashAssets`/`handleSlashing` bug class: a batched operation that can legitimately contain a zero-value item fails atomically and blocks processing of every other (non-zero) item in the same batch.

### Finding Description
`withdraw()` in the Tron `IntentGatewayV2` iterates the `WithdrawalRequest.tokens` array and, for each entry, unconditionally checks: [1](#0-0) 

```solidity
for (uint256 i; i < len;) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (_orders[body.commitment][token] == 0) revert UnknownOrder();
    ...
    _orders[body.commitment][token] -= amount;
    unchecked { ++i; }
}
```

There is no `if (amount == 0) continue;` guard. Compare this to the canonical EVM implementation of the same routine (`_withdraw` in `IntentsBase.sol`), which explicitly skips zero-amount legs before touching escrow storage: [2](#0-1) 

The Tron `withdraw()` function is reachable from an unprivileged, message-driven path: it is invoked from `onAccept()` when a `RedeemEscrow`/`RefundEscrow` `PostRequest` arrives via ISMP (a cross-chain settlement message dispatched by a solver's `fillOrder` on the destination chain, or by a user's `cancelOrder`), and also directly from `onGetResponse()` for the cancel-from-source flow: [3](#0-2) [4](#0-3) 

A `WithdrawalRequest.tokens` array containing an already-zeroed token can legitimately arise:
- The cancel-from-source path (`_cancelFromSource`, same file) builds the `WithdrawalRequest.context` from the full `order.inputs` array — every input token the order originally declared — not filtered by current escrow balance: [5](#0-4) 
  If any one of those input tokens' escrow was already fully consumed (e.g. token already swept as dust, or reduced to exactly zero through some earlier partial operation, or a duplicate/zero-amount input token entry), that single zero entry causes `withdraw()` to revert with `UnknownOrder()` for the *entire* batch, even though the remaining input tokens still hold real, refundable escrow.
- More directly, any multi-token order (multiple `order.inputs`) where one input's escrow is legitimately/incidentally at zero at settlement time reproduces exactly the Karak pattern: one zero balance blocks release of every other token's real balance.

This differs from the main EVM `IntentGatewayV2`/`IntentsBase.sol` implementation, which was hardened with the `if (amount == 0) continue;` guard — the Tron contract is a divergent reimplementation that dropped this protection.

### Impact Explanation
When triggered, the entire cross-chain settlement message (`RedeemEscrow`/`RefundEscrow` `onAccept`, or the cancel-from-source `onGetResponse`) reverts. Since ISMP message delivery for a reverting `onAccept`/`onGetResponse` cannot be redelivered with different parameters (the request body is fixed by the original dispatch), this permanently freezes the escrowed input tokens for that order: the solver never receives the input tokens it is owed for a legitimate fill, and/or the user never receives a refund for a cancelled/expired order, with no in-protocol recovery path — matching "permanent freezing of funds" per the validation criteria.

### Likelihood Explanation
Medium: this requires a specific but not implausible state — a multi-input order where one input token's escrow balance is exactly zero at settlement/redemption time on the Tron deployment. This can occur from normal order construction (e.g., a token appearing in `order.inputs` whose full amount was already accounted for/dust-swept, or any code path that zeroes one entry's escrow ahead of the others), and any occurrence deterministically blocks the entire withdrawal for that commitment. It requires no attacker privilege beyond placing/settling an ordinary order.

### Recommendation
Add the same zero-amount/zero-escrow skip that `IntentsBase._withdraw` uses in the main EVM implementation:

```solidity
for (uint256 i; i < len;) {
    address token = address(uint160(uint256(body.tokens[i].token)));
    uint256 amount = body.tokens[i].amount;
    if (amount == 0) { unchecked { ++i; } continue; }
    if (_orders[body.commitment][token] == 0) revert UnknownOrder();
    ...
}
```
Align the Tron `IntentGatewayV2.withdraw()` implementation with `IntentsBase.sol`'s `_withdraw` to prevent one zero/exhausted escrow leg from blocking release of the remaining legs in the same withdrawal batch.

### Proof of Concept
1. Place a same-chain-source, cross-chain order on the Tron `IntentGatewayV2` with two input tokens, e.g. `inputs = [TokenA: 100, TokenB: 100]`, destined to another chain.
2. Through whatever path drives one input's escrow (`_orders[commitment][TokenA]`) to exactly `0` prior to settlement (e.g., a prior partial redemption/dust-sweep touching only TokenA, or an order deliberately crafted with a duplicate/zero-value TokenA leg alongside a real TokenB leg) while `TokenB` escrow remains `100`.
3. Solver fills the order on the destination chain; the resulting `RedeemEscrow` `PostRequest` (containing both `TokenA` and `TokenB` in `WithdrawalRequest.tokens`) is delivered to the Tron source chain via `onAccept`.
4. `withdraw()` iterates the tokens array; on hitting `TokenA` it evaluates `_orders[commitment][TokenA] == 0` → true → reverts with `UnknownOrder()`.
5. The entire `onAccept` call reverts. `TokenB`'s real escrow (100) is never released to the solver, and the message cannot be resubmitted with a different token list since the `PostRequest` body is fixed by the original dispatch — the escrow is permanently stuck.
