### Title
Excess native token payment for message dispatch fees is never refunded and becomes permanently stuck in `EvmHost` - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()` accept `msg.value` and forward it entirely to `swapETHForExactTokens{value: msg.value}(fee, path, address(this), block.timestamp)`. This is the exact same bug class as the referenced Footium report: the contract accepts any `msg.value >= requiredSwapCost` without checking or refunding the excess, and — unlike every other native-payment path in this codebase — has no logic to return the leftover ETH to the original caller.

### Finding Description
In `evm/src/core/EvmHost.sol`, `dispatch(DispatchPost)` (lines 921-932), `dispatch(DispatchGet)` (lines 974-985), and `fundRequest()` (lines 1031-1042) all follow the same pattern: [1](#0-0) 

```solidity
function dispatch(DispatchPost memory post) external payable notFrozen returns (bytes32 commitment) {
    if (msg.value > 0) {
        ...
        IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(
            post.fee, path, address(this), block.timestamp
        );
    } else if (post.fee > 0) {
        IERC20(feeToken()).safeTransferFrom(_msgSender(), address(this), post.fee);
    }
    ...
```

`swapETHForExactTokens` on Uniswap V2's router only spends what is needed to obtain `post.fee` output tokens and refunds any unspent ETH to the caller of the swap — but the caller of the swap is `EvmHost` itself (since `EvmHost` invokes the router with `{value: msg.value}`), not the original transaction sender (`_msgSender()`). The refunded ETH therefore lands in `EvmHost`'s own balance. Crucially, none of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` capture the router's returned `amounts` array or forward any leftover value back to `_msgSender()`. [2](#0-1) 

This is provably a deliberate anti-pattern that the rest of the codebase avoids: `IntentGatewayV2.placeOrder` (and `ExtrinsicIntents`, and `WrappedHyperFungibleTokenUpgradeable`) explicitly track the amount actually spent by the swap and refund the difference to the sender via `_sendValue`/native transfer: [3](#0-2) 

`EvmHost` implements no equivalent refund step, and grep of the file confirms there is no `withdrawNative`/sweep function that returns accumulated stray ETH to the payer — only ERC20 feeToken transfers exist for relayer/protocol fee flows. Any native ETH stuck in `EvmHost` from an over-supplied `msg.value` therefore has no path back to the original caller.

### Impact Explanation
Any application or user calling `EvmHost.dispatch()` / `fundRequest()` with native ETH (the documented, recommended payment method per `docs/content/developers/evm/messaging/post-requests.mdx` and `get-requests.mdx`) will lose any ETH sent beyond the exact swap cost required to acquire `post.fee`/`get.fee`/`amount` worth of `feeToken`. Since the exact ETH cost of a Uniswap swap is impossible to predict precisely ahead of time (due to slippage, MEV, and price movement between quote and execution), essentially every native-fee-paying dispatcher/relayer/HyperApp integrator that estimates a safety margin (as the SDK docs even recommend doing, e.g. "Apply a generous 2x buffer" in `HyperbridgeLzEndpoint.sol`) will have that buffer permanently trapped in `EvmHost` with no recovery mechanism — a direct, unbacked, protocol-wide loss of user funds.

### Likelihood Explanation
High likelihood: native-token fee payment is a first-class, documented feature (`Native Token Payment` sections in both `post-requests.mdx` and `get-requests.mdx`), and the pattern of over-supplying `msg.value` as a safety buffer is explicitly demonstrated/recommended elsewhere in this same codebase (`HyperbridgeLzEndpoint.quote` doubling the fee). Every single call to `dispatch()`/`fundRequest()` with `msg.value` set even slightly above the exact required swap input triggers permanent loss.

### Recommendation
Mirror the pattern already used in `IntentGatewayV2.sol`/`ExtrinsicIntents.sol`: capture the `amounts` array returned by `swapETHForExactTokens` in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, compute `msg.value - amounts[0]`, and refund the difference back to `_msgSender()` via a low-level call (as done via `_sendValue` in the intents contracts) before returning.

### Proof of Concept
1. A HyperApp calls `EvmHost.dispatch{value: X}(post)` where `X` is intentionally larger than the exact ETH needed to purchase `post.fee` feeToken (a common defensive practice, since exact swap cost cannot be known in advance due to price movement).
2. Inside `dispatch`, `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: X}(post.fee, path, address(this), block.timestamp)` executes: the router spends `amounts[0] < X` ETH and refunds `X - amounts[0]` ETH back to `msg.sender` of the router call, i.e., `EvmHost`.
3. `EvmHost.dispatch` never reads the swap's return value nor forwards any ETH back to the original caller; execution proceeds directly to building/emitting the `PostRequest`.
4. `X - amounts[0]` wei remains permanently in `EvmHost`'s balance. There is no `withdrawNative`, `sweep`, or `receive`-triggered accounting path in `EvmHost.sol` that returns this ETH to the original payer — it is a permanent, protocol-level loss of user funds, repeatable on every dispatch call with any overpayment.
