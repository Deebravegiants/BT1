This is confirmed non-vulnerable. The claim rests on a false premise: `createWithdrawalCompletionPromises()` does **not** derive identifiers from the flattened `intents` array produced by `signAndSendWithdrawalIntent()`. It calls `createWithdrawalIdentifiers()` which iterates over `withdrawalParams` directly (the original array, one entry per user-specified withdrawal) — completely independent of how many `IntentPrimitive`s each bridge emitted. [1](#0-0) 

Within `createWithdrawalIdentifiers`, each `withdrawalParams[i]` gets its own bridge lookup via `findBridgeForWithdrawal`/`bridge.supports()`, and a per-bridge-route counter (`indexes` map keyed by `bridge.route`) tracks the index used for `bridge.createWithdrawalIdentifier()`. This index is the position *within that bridge's own withdrawals*, not a position in the flattened intents array. For a batch with `withdrawalParams[0]` on PoA and `withdrawalParams[1]` on OmniBridge, each gets `index: 0` in its own bridge's counter, regardless of how many `IntentPrimitive`s each bridge's `createWithdrawalIntents()` emitted (1 for PoA, potentially more for OmniBridge with `storage_deposit`). [2](#0-1) 

Critically, `createWithdrawalCompletionPromises()` maps over `withdrawalParams.map((_, index) => ...)` and looks up `wids[index]` from the array produced by `createWithdrawalIdentifiers` — an array with exactly `withdrawalParams.length` entries, one-to-one, regardless of the intent primitive counts. There's no dependency on the flattened `intents` array length used in `signAndSendWithdrawalIntent()`. [3](#0-2) 

For OmniBridge specifically, `describeWithdrawal` uses `args.index` to index into `omniBridgeAPI.getTransfer({ transactionHash: args.tx.hash })[args.index]` — this is the bridge-specific transfer index on the destination chain API, not related to intent primitive count in the NEAR transaction. [4](#0-3) 

For PoA bridge, matching is done by `assetId` rather than index at all (`findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)`), further decoupling correctness from any intent array positional correspondence.

There's a dedicated unit test verifying exactly the scenario the question raises — mixed bridges producing different per-withdrawal identifier indices: [5](#0-4) 

This test (`"maintains separate index counters per bridge route"`) explicitly confirms that `wid.index` is tracked per bridge route, and index correspondence between `withdrawalParams[i]` and the eventual completion promise is maintained through the wids array position, not through the flattened intents array. The `signAndSendWithdrawalIntent()`'s `.flat()` on `intentsP` only affects what gets signed and published to NEAR — it has no bearing on how completion status is later attributed, because `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` always take the original `withdrawalParams` array (not intents) as their input and re-derive bridge identifiers fresh. [6](#0-5)

export async function createWithdrawalIdentifiers(args: {
	bridges: Bridge[];
	withdrawalParams: WithdrawalParams[];
	intentTx: NearTxInfo;
}): Promise<{ bridge: Bridge; wid: WithdrawalIdentifier }[]> {
	const indexes = new Map<string, number>();
	const results: { bridge: Bridge; wid: WithdrawalIdentifier }[] = [];

	for (const w of args.withdrawalParams) {
		const bridge = await findBridgeForWithdrawal(args.bridges, w);
		if (bridge == null) {
			throw new BridgeNotFoundError();
		}

		const currentIndex = indexes.get(bridge.route) ?? 0;
		indexes.set(bridge.route, currentIndex + 1);

		const wid = bridge.createWithdrawalIdentifier({
			withdrawalParams: w,
			index: currentIndex,
			tx: args.intentTx,
		});

		results.push({ bridge, wid });
	}

	return results;
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
