### Title
Unbounded, fee-free `handle_unsigned` batch re-executes full ISMP proof verification on every mempool validation - resource consumption DoS - (File: modules/pallets/ismp/src/lib.rs)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic accepts an arbitrary `Vec<Message>` and is validated via `ValidateUnsigned::validate_unsigned`, which calls `Self::execute(messages.clone())` — i.e. it runs the **entire** ISMP message-handling pipeline (state-machine/consensus lookups, Merkle/Trie membership and non-membership proof verification, and consensus-client checks for every message in the batch) with zero fee and no upper bound on the number of messages or the size of the batch, before the transaction is even included in a block. [1](#0-0) [2](#0-1) 

### Finding Description
This is the same bug class as CVE-2024-9358: an unauthenticated/free entry point (there, ThingsBoard's HTTP RPC API; here, an *unsigned* Substrate extrinsic) that performs expensive server-side work proportional to attacker-controlled input size, with no meaningful cost or bound gating that work.

`pallet-ismp` deliberately makes `handle_unsigned` free so relayers aren't charged for delivering messages, and relies entirely on transaction-pool validation to filter out garbage before it wastes resources:

> "Pallet ISMP uses unsigned transactions for executing cross-chain messages... This validity check ensures that the transaction can be successfully executed and contains valid proofs." [3](#0-2) 

But that "validity check" *is* full execution: `validate_unsigned` unconditionally calls `Self::execute(messages.clone())`, running `handlers::handle` for every `Message::Request`, `Message::Response`, `Message::Timeout`, and `Message::Consensus` entry in the batch: [4](#0-3) 

Each `Request`/`Response` message in the batch triggers, per entry: a duplicate-receipt storage read, timeout/destination checks, and — crucially — a full Merkle-Mountain-Range/Trie membership proof verification against the stored state-machine commitment (`state_machine.verify_membership(...)` / `verify_state_proof(...)`), which is the expensive cryptographic step: [5](#0-4) [6](#0-5) 

There is no `MaxMessages`/`BoundedVec` cap on `messages: Vec<Message>` in `handle_unsigned`'s signature, and no check that limits how many `PostRequest`/`GetRequest`/`Timeout` entries a single unsigned transaction may carry before this full-execution validation path runs: [7](#0-6) 

Because this is `ValidateUnsigned::validate_unsigned`, it executes on **every peer node** that receives the transaction over the network (standard Substrate transaction-pool gossip validation), not merely on the node that eventually includes it in a block. An attacker who crafts a large batch of syntactically well-formed but ultimately-invalid-or-worthless messages (e.g., proofs that are internally consistent enough to pass early checks but fail later, or messages against consensus states with expensive verification, such as BEEFY/SP1/GRANDPA/Tendermint clients) forces every node in the network to repeat this expensive verification work for free, with only a 25-block transaction longevity and no fee deterrent, and can resubmit new never-before-seen batches indefinitely (varying nonces/heights/signer bytes) to defeat the `provides`-tag dedup in the pool. [8](#0-7) 

The equivalent state-coprocessor pallet has the identical pattern: `validate_unsigned` calls `Self::handle_get_requests(message.clone())` (full state-proof verification) with no bound on `message.requests.len()`. [9](#0-8) 

Unlike the Solidity `HandlerV2.sol` analogs (`handlePostRequests`, `handleGetResponses`, etc.), which are gated by real EVM gas costs paid by the caller, the Substrate `handle_unsigned` path has no cost model applied at the point where the expensive work (proof verification) actually happens — the pool-validation call is unmetered relative to weight/fees, since fees are only charged (or not, since this call is free) after the call is dispatched, and `validate_unsigned` runs unconditionally on every propagation attempt.

### Impact Explanation
This does not itself steal or freeze funds, but it is a network-wide resource-consumption vector reachable by any unprivileged party submitting a single unsigned extrinsic/transaction. Since `validate_unsigned` performs full cryptographic proof verification (potentially chained across BEEFY/SP1/GRANDPA/Tendermint/Pharos consensus clients depending on which state machine the batch references) for every message in an unbounded `Vec<Message>`, and this runs on every relaying/full node in the network for free, an attacker can degrade throughput and increase CPU/verification load network-wide — a classic resource-consumption DoS matching the CVE-2024-9358 bug class ("manipulation leads to resource consumption... attack can be launched remotely... rather high complexity"). This can starve legitimate relayers' messages from timely inclusion, indirectly risking message timeouts and stalled cross-chain delivery routes.

### Likelihood Explanation
Reachable directly from a single unsigned, unauthenticated transaction submitted by anyone with network access to a node's RPC/p2p gossip — no privileged role, governance, or prior state is required. The batch size/content is entirely attacker-controlled, bounded only by the runtime's generic max-extrinsic-length parameter (a network-wide constant, not a per-message-type or per-ISMP-batch specific cap), so an attacker can pack many expensive-to-verify (but ultimately invalid/duplicate/worthless) messages into a single call and resubmit variants repeatedly.

### Recommendation
- Enforce an explicit, low `MaxMessages` (and/or `MaxRequestsPerMessage`) bound on `handle_unsigned`'s `Vec<Message>` and on `GetRequestsWithProof.requests` in `pallet-state-coprocessor`, checked before any proof verification is attempted in `validate_unsigned`.
- Consider performing cheap, non-cryptographic sanity/shape checks (duplicate detection, timeout checks, size limits) before invoking the full `execute`/`handle_get_requests` path inside `validate_unsigned`, so that batches failing basic sanity never reach expensive proof verification.
- Evaluate charging a small bond or weight-based cost specifically for the pool-validation execution path (not just block-inclusion dispatch), or otherwise rate-limit how often a given peer/signer bytes payload can trigger full `execute()` runs within the longevity window.

### Proof of Concept
1. An attacker crafts an unsigned `pallet_ismp::Call::handle_unsigned { messages }` where `messages` is a `Vec<Message>` containing many (e.g., thousands of) `Message::Request(RequestMessage { requests: [...many PostRequest entries...], proof, signer })` entries, each referencing a real but already-superseded or soon-to-fail state-machine height so the transaction is ultimately rejected, or with distinct `signer`/nonce bytes so each submission produces a unique `provides` tag and evades pool dedup (per the tag-uniqueness logic at `modules/pallets/ismp/src/lib.rs:647-699`).
2. The attacker gossips this transaction to the network. Every full node's transaction pool calls `ValidateUnsigned::validate_unsigned`, which calls `Self::execute(messages.clone())`, which for each request iterates `state_machine.verify_membership(...)` over the full Merkle proof (`modules/ismp/core/src/handlers/request.rs:86-93`).
3. Because the extrinsic is unsigned (free, no fee deduction) and has no batch-size cap, the attacker can repeat step 1–2 with fresh variants indefinitely at negligible cost to themselves, while every receiving node repeatedly performs full-batch proof verification for a transaction that is ultimately never included, consuming CPU cycles network-wide.

			// `provides` tag from the messages themselves so that distinct submissions
			// never collide in the transaction pool.
			//
			// A consensus message that doesn't advance a state machine (e.g. a
			// validator-set rotation during sync) previously mapped to an empty request
			// list via the catch-all arm. Every such message therefore produced an
			// identical `provides` tag and a fixed priority of 100, so the pool rejected
			// any two of them with "Priority is too low (100 vs 100)". Hashing the
			// consensus message (excluding the signer, so equivalent submissions from
			// different relayers dedupe) gives each update a unique tag.
			let mut has_consensus = false;
			let mut tags = messages
				.into_iter()
				.map(|message| match message {
					Message::Consensus(ConsensusMessage {
						consensus_proof,
						consensus_state_id,
						..
					}) => {
						has_consensus = true;
						vec![H256(sp_io::hashing::keccak_256(
							&(consensus_state_id, consensus_proof).encode(),
						))]
					},
					Message::FraudProof(FraudProofMessage { proof_1, proof_2, .. }) => vec![
						H256(sp_io::hashing::keccak_256(&proof_1)),
						H256(sp_io::hashing::keccak_256(&proof_2)),
					],
					Message::Request(RequestMessage { requests, .. }) => requests
						.into_iter()
						.map(|post| hash_request::<Pallet<T>>(&Request::Post(post.clone())))
						.collect::<Vec<_>>(),
					Message::Response(message) => message
						.requests()
						.iter()
						.map(|request| hash_request::<Pallet<T>>(request))
						.collect::<Vec<_>>(),
					Message::Timeout(message) => message
						.requests()
						.iter()
						.map(|request| hash_request::<Pallet<T>>(request))
						.collect::<Vec<_>>(),
				})
				.collect::<Vec<_>>();

			if tags.is_empty() {
				return Err(TransactionValidityError::Invalid(InvalidTransaction::Call));
			}

			let msg_hash = sp_io::hashing::keccak_256(&tags.encode()).to_vec();

## Transaction fees

Pallet ISMP uses unsigned transactions for executing cross-chain messages. This means all cross-chain messages received are executed for free as unsigned transactions. The upside to this is that it cannot be exploited as a spam vector, since the transaction pool will check if the submitted extrinsics are valid before they are included in the pool. This validity check ensures that the transaction can be successfully executed and contains valid proofs. Malformed messages or those with invalid proofs are filtered out by the transaction pool validation logic preventing unnecessary processing and potential network congestion.
