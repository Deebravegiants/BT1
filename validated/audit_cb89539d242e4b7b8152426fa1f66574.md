### Title
Excess native ETH sent to `dispatch()`/`fundRequest()` is permanently stuck in `EvmHost` with no recovery path - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` swap any `msg.value` sent by the caller into the exact fee-token amount required via `swapETHForExactTokens`, but never capture the swap's return value nor refund the unspent native token back to the caller. Because the router refunds unspent ETH to the account that invoked the swap — `EvmHost` itself, not the original transaction sender — any overpayment accumulates as native balance inside `EvmHost` with no function anywhere in the host/manager contracts to withdraw it.

### Finding Description
In `EvmHost.sol`, the payable dispatch functions all follow this pattern: [1](#0-0) 

and identically for `dispatch(DispatchGet)`: [2](#0-1) 

and `fundRequest`: [3](#0-2) 

In each case, `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(...)` is called with the *entire* `msg.value`, but the exact-output swap only consumes `post.fee`/`get.fee`/`amount` worth of ETH. Uniswap V2's `swapETHForExactTokens` refunds any leftover ETH to `msg.sender` of the swap call — which, from the router's perspective, is `EvmHost`, since `EvmHost` is the one invoking the router. The return value (`amounts[0]`, the amount actually spent) is discarded, and no code path refunds `msg.value - amounts[0]` to `_msgSender()` (the original caller of `dispatch`/`fundRequest`).

This is a real, exploitable gap in the same codebase, because the correct pattern already exists elsewhere: `IntentGatewayV2.placeOrder` explicitly captures the swap output and refunds the difference to the caller: [4](#0-3) 

`EvmHost` implements no equivalent logic. Furthermore, there is no `receive()`/withdraw function in `EvmHost.sol` for reclaiming stray native ETH; the only governance withdrawal path, `IHostManager.withdraw(WithdrawParams)` invoked through `HostManager.onAccept`, operates on the ERC-20 `feeToken()` balance, not native ETH: [5](#0-4) 

Since `EvmHost` (not `HostManager`) is the contract that actually receives the refunded ETH from the swap, and `HostManager`'s `receive()` is a separate contract, there is no mechanism — user-facing or governance — to recover the ETH stuck in `EvmHost`.

### Impact Explanation
Any unprivileged user who calls `dispatch()` (POST or GET) or `fundRequest()` with `msg.value` slightly larger than the exact fee-token cost of the swap (which is very easy to happen given ETH price volatility, slippage estimation, or simply rounding to a convenient decimal amount) permanently loses the difference. The funds are not burned but become inaccessible: they sit as native balance on `EvmHost` with no withdrawal function, no governance action, and no user-facing refund path. This is a permanent freezing-of-funds bug reachable from a single, ordinary transaction by any caller of the dispatch/fundRequest entry points — core, high-traffic bridge functions used by essentially every app built on Hyperbridge.

### Likelihood Explanation
High likelihood of occurrence: because the DEX swap price fluctuates and users/integrators typically pass a generous `msg.value` buffer to avoid reverts from `swapETHForExactTokens` reverting on insufficient input, overpayment is the common case rather than the exception. Every such overpayment permanently strands funds. This is a systemic issue affecting the three most frequently used payable entry points of `EvmHost`.

### Recommendation
Capture the `amounts` array returned by `swapETHForExactTokens` in all three functions (`dispatch(DispatchPost)`, `dispatch(DispatchGet)`, `fundRequest`) and refund `msg.value - amounts[0]` to `_msgSender()`, mirroring the pattern already implemented in `IntentGatewayV2.placeOrder` (`evm/src/apps/IntentGatewayV2.sol:383-397`). As a defense in depth, add an admin/governance-gated sweep function for stray native ETH already stuck in `EvmHost` from before the fix, similar to how `HostManager`/`IHostManager.withdraw` handles the fee token.

### Proof of Concept
1. Call `EvmHost.dispatch(DispatchPost)` with `post.fee = 1e6` (1 USDC-equivalent fee token) but `msg.value = 1 ether` (deliberately overpaying to guard against price movement/slippage).
2. `swapETHForExactTokens{value: 1 ether}(1e6, [WETH, feeToken], address(this), block.timestamp)` only spends the ETH-equivalent of `1e6` fee-token units; the router refunds the remainder (`1 ether - spent`) to `msg.sender`, which is `EvmHost`.
3. `EvmHost`'s ETH balance increases by the unspent amount; the original caller receives nothing back.
4. Inspect `EvmHost`'s contract balance (`address(host).balance`) after the call — it now holds the caller's excess ETH.
5. Attempt to locate any function on `EvmHost` or `HostManager` that can withdraw native ETH held by `EvmHost` — none exists; `IHostManager.withdraw` only moves `feeToken()` (ERC-20) balance per `HostManager.onAccept` (`evm/src/core/HostManager.sol:144-148`). The ETH is permanently stuck.
