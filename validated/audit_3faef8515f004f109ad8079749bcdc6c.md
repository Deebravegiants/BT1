### Title
Excess native token sent for cancel-flow relayer fees is permanently trapped in `EvmHost`, not refunded to the caller - (File: `evm/src/apps/intentsv2/ExtrinsicIntents.sol`)

### Summary
`ExtrinsicIntents._post()`, `_cancelFromSource()`, and `_cancelFromDest()` forward the caller's entire `msg.value` as the native fee argument straight into `EvmHost.dispatch()`, which internally swaps only the exact ETH needed to buy `post.fee` fee-tokens and lets any leftover ETH be refunded to *itself* (the host), not back to the caller. Unlike `IntentGatewayV2._placeOrder`/`_fillOrder`, which perform the ETH→feeToken swap themselves, measure the exact amount spent, and refund the remainder to the user, the cross-chain cancel paths in `ExtrinsicIntents` have no such reserve-and-refund logic, so any overpayment of native token by a user or relayer calling `cancelOrder` is permanently lost.

### Finding Description
`EvmHost.dispatch()` swaps `msg.value` for exactly `post.fee` fee-tokens via Uniswap and does not track or refund any leftover ETH to its caller: [1](#0-0) 

The Uniswap wrapper used for this swap explicitly refunds unspent ETH to `msg.sender` of the swap call — which, when invoked from `dispatch()`, is `EvmHost` itself, not the original caller of `dispatch()`: [2](#0-1) 

`ExtrinsicIntents._post()` passes whatever `nativeFee` it is given directly as `msg.value` to `dispatch()`, with no logic to capture or refund any unspent portion: [3](#0-2) 

Both cancel entry points pass the caller's *entire* `msg.value` as this native fee, rather than a precisely quoted amount: [4](#0-3) [5](#0-4) 

This is in direct contrast to the "optimal" pattern already implemented in `IntentGatewayV2._placeOrder`, where the swap is performed directly by the gateway (so it can capture the exact `amounts[0]` spent), the remaining `msgValue` is decremented, and any true leftover is refunded to `msg.sender` at the end of the function: [6](#0-5) 

Because there is no equivalent on-chain "quote" for cancel-fee native payment (unlike `quoteOrderFees()` used for `placeOrder`), and no refund path exists once `msg.value` is handed to `dispatch()`, any user or relayer who overestimates the native amount needed to cover `options.relayerFee` on `cancelOrder` will have the excess ETH permanently absorbed into `EvmHost`'s balance with no mechanism to reclaim it.

### Impact Explanation
This is a permanent freezing-of-funds bug reachable by any unprivileged user or relayer calling `cancelOrder` (both `_cancelFromSource` and `_cancelFromDest` paths) with native token payment. Any ETH sent beyond the exact amount required for the Uniswap swap into `post.fee` fee-tokens is irrecoverably stuck in `EvmHost`, since neither `EvmHost.dispatch()` nor `ExtrinsicIntents._post()` implement a reserve-and-refund mechanism analogous to the one used for `placeOrder`/`fillOrder`. This satisfies the "permanent freezing of funds" criterion.

### Likelihood Explanation
Likelihood is meaningfully high in practice: there is no on-chain quoting helper for the exact native cost of a cancel-relayer-fee swap (unlike `quoteOrderFees()` for order placement), so any caller who pads `msg.value` for safety margin, or who estimates fee cost slightly high due to price movement between quote and execution, will lose the excess. This requires no special privileges or malicious behavior — an honest user simply overestimating gas/fee cost triggers the loss.

### Recommendation
Apply the same reserve-and-refund pattern used in `IntentGatewayV2._placeOrder`/`_fillOrder` to `ExtrinsicIntents._post()`/`_cancelFromSource()`/`_cancelFromDest()`: perform the ETH→feeToken swap directly within `ExtrinsicIntents` (or have `EvmHost.dispatch()` return the actual amount spent and refund the difference to `_msgSender()`), and only pass the exact required native amount into `dispatch()`, refunding any true excess back to the original caller rather than letting it settle in `EvmHost`.

### Proof of Concept
1. A user calls `cancelOrder` on the destination chain, routed to `_cancelFromDest`, sending `msg.value = 1 ETH` intending to cover `options.relayerFee` (a fee-token amount) via native payment, but the actual ETH needed for the swap is only 0.1 ETH.
2. `_cancelFromDest` calls `_post(order, body, options.relayerFee, msg.value)` — passing the full 1 ETH as `nativeFee`. [7](#0-6) 
3. `_post` calls `IDispatcher(host()).dispatch{value: 1 ether}(request)`. [8](#0-7) 
4. Inside `EvmHost.dispatch()`, the router swaps only the ~0.1 ETH needed for `post.fee` fee-tokens; the remaining ~0.9 ETH is refunded by the router to `msg.sender`, which is `EvmHost` itself, not `ExtrinsicIntents` or the user. [1](#0-0) 
5. The user's 0.9 ETH overpayment is now permanently held in `EvmHost`'s balance with no code path returning it to the user.
