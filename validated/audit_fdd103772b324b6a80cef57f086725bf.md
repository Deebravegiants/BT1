### Title
Cross-chain solver escrow redemption sends funds to the solver's `msg.sender` address on the source chain, unreachable/misdirected for smart contract wallets - (File: evm/src/apps/intentsv2/ExtrinsicIntents.sol)

### Summary
`IntentGatewayV2` (via `ExtrinsicIntents::_fillCrossChain`) encodes the filling solver's `msg.sender` address — as observed on the **destination** chain — as the `beneficiary` for the `RedeemEscrow` message dispatched back to the **source** chain, where escrowed input tokens are then released to that same address via `IntentsBase::_withdraw`. This assumes the solver controls the identical address on both chains, which does not hold for smart contract wallets (Safe/AA wallets), whose deployed address can differ per chain or belong to an unrelated party.

### Finding Description
When a solver fills a cross-chain order on the destination chain, `_fillCrossChain` builds the redemption message with: [1](#0-0) 

using `_body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender))))`: [2](#0-1) 

This message is dispatched via `_post` to `order.source` (the original source chain): [3](#0-2) 

On the source chain, `onAccept` (via `IntentsBase::_withdraw`) decodes the `beneficiary` field directly as an address and transfers the escrowed input tokens to it: [4](#0-3) 

There is no mechanism for the solver to supply a distinct beneficiary address per chain — the contract unconditionally derives it from `msg.sender` on the destination chain and assumes it is a valid, controllable address on the source chain. If the solver uses a smart contract wallet (e.g., Gnosis Safe, ERC-4337 account) whose address differs across chains — or if the address on the source chain happens to correspond to an EOA or contract controlled by a different party — the escrowed tokens are sent to an address the original solver does not control on the source chain.

### Impact Explanation
If a solver's `msg.sender` address on the destination chain corresponds to an address controlled by a different, unrelated party on the source chain (a realistic scenario for CREATE2/counterfactual smart-contract wallets or coincidental EOA collisions), that third party gains control of the escrowed input tokens released via `RedeemEscrow`. Even absent malicious appropriation, if the solver's smart-contract wallet on the source chain is undeployed or has different signers, the redeemed tokens can become permanently inaccessible (frozen) to the solver. This is a direct theft/freezing-of-funds vector reachable purely from a solver calling `fillOrder`/`_fillCrossChain` on the destination chain — no privileged or governance action needed.

### Likelihood Explanation
Solvers frequently operate through smart contract wallets or automated bundlers (increasingly common in intent-based systems, including this protocol's own ERC-4337 bundler flow referenced in its docs) rather than plain EOAs, and such wallets commonly have different deployed addresses across chains. The bug requires no cooperation from an attacker beyond controlling an address on the source chain that coincides with the solver's destination-chain address (which, for CREATE2 wallets with chain-specific factory nonces or differing deployment states, is a foreseeable, not purely theoretical, condition) — making the likelihood credible rather than purely academic, though it does hinge on this specific wallet-address mismatch occurring.

### Recommendation
Allow solvers to explicitly specify a redemption beneficiary address per fill (analogous to how `order.output.beneficiary` is separately and explicitly provided rather than derived from `msg.sender`), instead of hard-coding `bytes32(uint256(uint160(msg.sender)))` as the `RedeemEscrow` beneficiary in `_fillCrossChain`. At minimum, document this constraint prominently and/or validate that the resolved beneficiary is not accidentally a contract with no known controller on the source chain, mirroring the mitigation pattern the report itself recommends (letting users/solvers designate a validated destination address rather than assuming address equivalence across chains).

### Proof of Concept
1. Solver Bob deploys a Safe multisig at address `0xAAA...` on Arbitrum (destination chain) via CREATE2.
2. Bob calls `fillOrder` on Arbitrum through his Safe, so `msg.sender == 0xAAA...`.
3. `_fillCrossChain` dispatches `RedeemEscrow` with `beneficiary = 0xAAA...` back to Ethereum (`order.source`).
4. On Ethereum, `0xAAA...` happens to be an EOA controlled by an unrelated third party Alice (different deployment nonce/salt led to address divergence, or simple collision with an existing EOA).
5. `onAccept` → `_withdraw` transfers the escrowed input tokens on Ethereum to `0xAAA...`, which Alice controls — Bob's earned escrow is stolen or, if `0xAAA...` is simply an undeployed/mismatched contract, permanently locked. [5](#0-4) [4](#0-3)

    function _fillCrossChain(Order calldata order, FillOptions calldata options, bytes32 commitment) internal {
        uint256 outputsLen = order.output.assets.length;

        _filled[commitment] = msg.sender;

        uint256 msgValue = msg.value;
        address beneficiary = address(uint160(uint256(order.output.beneficiary)));
        TokenInfo[] memory outputFills = new TokenInfo[](outputsLen);

        for (uint256 i; i < outputsLen; i++) {
            bytes32 outputToken = order.output.assets[i].token;
            if (options.outputs[i].token != outputToken) revert InvalidInput();

            address token = address(uint160(uint256(outputToken)));
            uint256 totalRequired = order.output.assets[i].amount;
            uint256 solverAmount = options.outputs[i].amount;

            if (solverAmount < totalRequired) revert InvalidInput();

            (uint256 protocolShare, uint256 beneficiaryShare) =
                _splitSurplus(solverAmount - totalRequired, order.output.call.length > 0);

            if (token == address(0)) {
                if (msgValue < solverAmount) revert InsufficientNativeToken();
                uint256 beneficiaryTotal = totalRequired + beneficiaryShare;
                _sendValue(beneficiary, beneficiaryTotal);
                msgValue -= (beneficiaryTotal + protocolShare);
            } else {
                IERC20(token).safeTransferFrom(msg.sender, beneficiary, totalRequired + beneficiaryShare);
                if (protocolShare > 0) {
                    IERC20(token).safeTransferFrom(msg.sender, address(this), protocolShare);
                }
            }
            if (protocolShare > 0) emit DustCollected(token, protocolShare);
            outputFills[i] = TokenInfo({token: outputToken, amount: totalRequired});
        }

        _execute(order, outputsLen);

        // Native dispatch fee only if the solver sent enough to cover it; else the fee token.
        uint256 nativeFee = options.nativeDispatchFee;
        if (nativeFee > msgValue) nativeFee = 0;
        msgValue -= nativeFee;
        _post(
            order,
            _body(RequestKind.RedeemEscrow, commitment, order.inputs, bytes32(uint256(uint160(msg.sender)))),
            options.relayerFee,
            nativeFee
        );

        // Refund any unspent native tokens to the solver.
        if (msgValue > 0) {
            _sendValue(msg.sender, msgValue);
        }

        emit OrderFilled({commitment: commitment, filler: msg.sender, outputs: outputFills, inputs: order.inputs});
    }

    function _withdraw(WithdrawalRequest memory body, bool isRefund, bool finalize) internal {
        address beneficiary = address(uint160(uint256(body.beneficiary)));
        if (finalize) _filled[body.commitment] = beneficiary;

        uint256 len = body.tokens.length;
        for (uint256 i; i < len; i++) {
            address token = address(uint160(uint256(body.tokens[i].token)));
            uint256 amount = body.tokens[i].amount;
            if (amount == 0) continue;

            uint256 escrowed = _orders[body.commitment][token];
            if (escrowed == 0) revert UnknownOrder();

            _orders[body.commitment][token] = escrowed - amount;
            if (token == address(0)) {
                _sendValue(beneficiary, amount);
            } else {
                IERC20(token).safeTransfer(beneficiary, amount);
            }
        }
