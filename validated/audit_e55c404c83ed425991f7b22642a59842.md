### Title
Shared Emporium singleton as `msg.sender`/`owner` in CASE 2 stateless calls lets any attacker steal residual vault shares (or any other unaccounted asset) parked at the Emporium address - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s CASE 2 branch executes `op.endpoint.call{value: op.value}(op.callData)` directly from the Emporium contract's own address, with no restriction on the callee or its parameters, and `verifyWallet` skips signature verification entirely when `stack.signerAddress == address(0)` [1](#0-0) [2](#0-1) . Because Emporium is a single persistent contract shared by all Hinkal users, any external protocol (e.g. an ERC4626 vault) that gates access with `msg.sender == owner` cannot distinguish between different Hinkal users when the call is routed through Emporium; whoever caused `owner`/receiver to be set to the Emporium address is indistinguishable on-chain from any later, unrelated caller. Combined with the fact that Emporium's post-call balance accounting only nets out tokens the caller explicitly listed in `circomData.erc20TokenAddresses` [3](#0-2) , any asset left at the Emporium address that isn't captured that way is permanently exposed to theft by any subsequent, unrelated `transact` call.

### Finding Description
Broken equality: `shares_owned_by_victim_stealth_address` (what should exist as a UTXO for the depositing user) should equal `shares_minted_to_receiver_in_deposit_call`. Instead, when a deposit-style CASE 2 op sets `receiver = emporium` and the vault-share token address is not included in that transaction's `circomData.erc20TokenAddresses`, the minted shares sit unaccounted at the Emporium contract's address indefinitely, because the balance-diff loop in `runAction` only samples the tokens in `circomData.erc20TokenAddresses` [4](#0-3) [5](#0-4) , and `dimensionsCheck`/`performHinkalChecks` never enforce that every token the external call actually touches is listed there [6](#0-5) .

Any later, entirely unrelated attacker `transact` can then include a CASE 2 op with `stack.signerAddress = address(0)` — which makes `verifyWallet` return immediately without checking any signature over the ops [2](#0-1)  — and call `vault.redeem(shares, attacker, emporium)` directly. Because CASE 2 executes `op.endpoint.call(...)` from the Emporium contract itself, `msg.sender == emporium == owner` trivially satisfies the vault's authorization check, with no allowance or signature required. Since `receiver = attacker` in the attacker's `redeem` call, the underlying assets flow straight to the attacker's wallet, bypassing Emporium's balance tracking entirely (no change is observed for that token in the attacker's own `balancesBefore`/`balancesAfter` diff, since the funds never touch Emporium).

The code explicitly anticipates persistent, carried-over balances at the Emporium address (see the comment "the only case when balanceChange can be < 0, when there were some funds on emporium before the call" [7](#0-6) ), confirming this is a real, reachable state and not merely theoretical.

None of the existing guards stop this: `onlyAllowedRecipient` only checks that the caller of `runAction` (Hinkal.sol) is registered, not what CASE 2 sub-calls can do [8](#0-7) ; `performHinkalChecks`/`dimensionsCheck`/`checkOnchainCreation` only validate array-length consistency and self-declared fields, never that all tokens touched externally are declared [9](#0-8) ; and `Hinkal.sol`'s balance-diff/slippage checks operate purely over the attacker's own self-chosen `circomData.erc20TokenAddresses` for their own transaction, so they cannot observe funds that bypass Emporium entirely [10](#0-9) .

### Impact Explanation
An attacker can steal any asset (vault shares, tokens, ETH) that ends up parked at the Emporium contract's address as a result of any user's prior CASE 2 operation whose target token wasn't declared in that transaction's `erc20TokenAddresses`. This is direct theft of user funds via an authorization bypass (`msg.sender == owner` collapses to the shared Emporium identity, with no signature requirement when `signerAddress == address(0)`), matching Critical severity (theft of shielded/backing user value, proof/authorization bypass). It is repeatable against every future victim who (or whose integration/build tooling) leaves value at the Emporium address without listing the corresponding token.

### Likelihood Explanation
Preconditions: (1) a victim's transact leaves a positive balance of some asset (e.g., vault shares) at the Emporium contract address, with that asset's address absent from `circomData.erc20TokenAddresses` for that transaction; (2) the asset is controlled by a contract using `msg.sender`/`owner`-based authorization (e.g., ERC4626 vaults, or any contract using approvals/ownership tied to the caller). No privileged role is needed — the attacker only needs to submit their own valid Hinkal proof for their own UTXOs and construct an `EmporiumStack` with `signerAddress = address(0)` and a CASE 2 op targeting the vault's `redeem`/`withdraw`. This is fully within an unprivileged attacker's capability as defined by the rules (crafting `CircomData`, deploying mock endpoints for PoC, choosing ordering).

### Recommendation
- Require every token/asset actually touched by CASE 2 (and CASE 1) op calls to be explicitly declared in `circomData.erc20TokenAddresses` and enforce that no un-declared token balance can change at the Emporium address (e.g., via allow-listing target contracts/selectors, or a strict post-call invariant that Emporium's balance of any non-declared token is unchanged).
- Do not allow completely unsigned/unauthenticated (`signerAddress == address(0)`) CASE 2 ops to make arbitrary external calls; require every op's `endpoint`/`callData` to be either allow-listed per integration or bound to a signature, regardless of `invokeWallet`.
- Avoid persistent balances of any user-relevant asset (including third-party vault shares) sitting at the shared Emporium address across transaction boundaries; require deposit-style external actions to sweep 100% of resulting balances out of Emporium within the same transaction for all tokens that could be minted/received, not only the declared list.

### Proof of Concept
Foundry test outline:
1. Deploy a mock ERC4626-style vault with `deposit(assets, receiver)` minting shares to `receiver`, and `redeem(shares, receiver, owner)` requiring `msg.sender == owner` (or allowance) and sending underlying assets to `receiver`.
2. Victim calls `Hinkal.transact` with a valid proof whose `CircomData.erc20TokenAddresses` includes only the underlying asset (not the vault share token), and an `EmporiumStack` CASE 2 op calling `vault.deposit(assets, emporium)`. Assert `vault.balanceOf(emporium) > 0` afterward and that no UTXO/commitment for the share token was ever created (since it isn't in `erc20TokenAddresses`).
3. Attacker, in an unrelated later `transact`, submits their own valid proof/UTXO with an `EmporiumStack` where `stack.signerAddress = address(0)` and a CASE 2 op calling `vault.redeem(shares, attacker, emporium)`.
4. Assert the call succeeds (no signature/authorization required), the underlying assets land in `attacker`'s wallet, `vault.balanceOf(emporium)` drops to 0, and none of the attacker's or victim's shielded UTXO commitments/nullifiers reflect this transfer — i.e., `balanceDif == amountChanges + utxoAmount` never captured the stolen value on either side.
