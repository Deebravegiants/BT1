### Title
Webhook `shop`, `topic`, `webhook-id` and `api-version` are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable payload from the raw body only, while the tenant-identifying `shop` (and `topic`/`webhook-id`/`api-version`) values are taken verbatim from HTTP headers that are never included in the signed data. `Registry.process` validates only the body's HMAC and then unconditionally trusts the header-derived `shop` to build the `WebhookMetadata` handed to the app's handler, breaking the intended binding `hmac_valid(body) ⇒ trust(shop)`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no cryptographic protection: [2](#0-1) 

`Registry.process` validates the HMAC over the body only, then immediately trusts `request.shop`/`request.topic`/`request.webhook_id`/`request.api_version` to build the metadata passed into the app-defined handler: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the HMAC exclusively over `verifiable_query.to_signable_string`, which for `Request` is the raw body — headers are never mixed into the signed string: [4](#0-3) 

This is structurally identical to the referenced bug class: two data channels feed a single downstream trust decision, but only one channel (`BASE_AGGREGATOR` staleness / the body's HMAC) is authenticated while the other (`WEETH_AGGREGATOR` staleness / the `shop`, `topic`, `webhook-id`, `api-version` headers) is not. The equality that should hold but does not is:

`hmac_valid(raw_body) == authenticated(shop_header)`

In reality `hmac_valid(raw_body)` says nothing about the `shop-domain` header's authenticity, since the header is outside the signed message.

### Impact Explanation
A multi-tenant app built on this gem uses `WebhookMetadata#shop` to attribute an incoming webhook event to a specific merchant/tenant (e.g., to look up that shop's session/access token, apply the payload to that tenant's records, or trigger tenant-scoped side effects). Because the HMAC only binds the body, any actor who has legitimately observed one valid `(body, hmac)` pair for their own shop (which they can obtain simply by having the app installed on their own store, since Shopify delivers real webhooks to the app's public endpoint) can resend the exact same body and HMAC while substituting an arbitrary `x-shopify-shop-domain` header. `Registry.process` will pass this HMAC check and dispatch the payload as if it originated from the victim shop, producing cross-tenant data injection/impersonation without ever needing the app's `client_secret`, an access token, or any privileged credential — matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is moderate-to-high in practice: it requires only that the attacker be able to send an HTTP POST to the app's public webhook endpoint (unauthenticated by design) with a body+HMAC pair they previously captured from a webhook delivered for their own shop, then change the shop header. No secret material, TLS interception, or social engineering is required — only observation of one's own legitimately-delivered webhook traffic, which is trivial for any merchant who installs the app.

### Recommendation
Bind the tenant-identifying headers into the signed message (or perform an independent authenticated correlation), for example by including `shop`, `topic`, and `webhook_id` in `Request#to_signable_string`, or by requiring the caller to look up/verify the claimed `shop` against a store of shops for which the webhook was actually registered before trusting it in `WebhookMetadata`. At minimum, document and enforce that `shop` must not be treated as authenticated by the HMAC check alone.

### Proof of Concept
1. Install the app on `shop-a.myshopify.com`; capture a legitimate webhook POST it receives, including its raw body `B` and header `x-shopify-hmac-sha256: H` (valid since `H = HMAC(secret, B)`).
2. Craft a new POST to the app's webhook endpoint with the same body `B` and the same header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: shop-b.myshopify.com` (a shop the attacker does not control).
3. `HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` succeeds because it only verifies `B` against `H`.
4. `Registry.process` in `lib/shopify_api/webhooks/registry.rb` dispatches the handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, causing the app to process/attribute the event to `shop-b` even though the payload never involved that tenant.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
