### Title
Precision loss from splitting a single multiplication into two floor-divisions in `calc-liquidity-rate` causes depositor yield to round down or to zero - (File: `mainnet/contracts/vault/v0-vault-stx.clar` and identical logic in `v0-vault-sbtc.clar`, `v0-vault-ststx.clar`, `v0-vault-ststxbtc.clar`, `v0-vault-usdc.clar`, `v0-vault-usdh.clar`)

### Summary
The reported Ajna bug is a generic "divide-then-multiply" precision-loss pattern. In the Zest vault contracts, `calc-liquidity-rate` performs the equivalent error: instead of computing the true rate as a single fused multiply-divide (`rate * util * (BPS - reserveFactor) / BPS^2`), it computes it as two sequential `mul-bps-down` calls, each flooring at `/BPS` before the next multiplication is applied. This throws away precision at each intermediate step, exactly analogous to dividing before multiplying in the referenced Ajna finding, and can make the resulting liquidity rate — the rate used to grow `lindex`, i.e. the interest actually distributed to depositors — round down to a smaller value than the mathematically correct rate, or to zero, even though the borrow-side index (`idx`) accrues the full, undiscounted interest from borrowers.

### Finding Description
`calc-liquidity-rate` is defined as: [1](#0-0) 

```
(define-private (calc-liquidity-rate (var-borrow-rate uint) (util-pct uint) (reserve-factor-bps uint))
  (let ((util-applied (mul-bps-down var-borrow-rate util-pct))
        (one-minus-rf (- BPS reserve-factor-bps)))
    (mul-bps-down util-applied one-minus-rf)))
```

with `mul-bps-down`: [2](#0-1) 

This is `(x*y)/BPS`, floored. The function computes the liquidity rate as `floor(floor(rate*util/BPS) * (BPS-rf)/BPS)` instead of the algebraically equivalent single-division form `floor(rate*util*(BPS-rf)/BPS^2)`. Because integer division floors at each intermediate step, the two-step computation always yields a value less than or equal to the correct single-division result, and can differ from it substantially (in extreme cases, the two-step result can be roughly half the mathematically correct value, or even zero when the true value would be nonzero).

This liquidity rate feeds directly into `next-liquidity-index`, which grows `lindex` — the index used to compute how much interest belongs to LP depositors (via `total-assets`/`convert-to-assets`): [3](#0-2) 

Meanwhile the borrow-side index `idx` (and thus `total-debt`, what borrowers actually owe) is computed from `var-borrow-rate` directly via `calc-multiplier-delta`, which is a single fused `mul-div-up`/`mul-div-down` and does not suffer this extra truncation: [4](#0-3) 

The identity that should hold is:
`interest accrued from borrowers (via idx growth) == interest distributed to depositors (via lindex growth) + reserve share`

Because `lindex` growth is computed through a doubly-truncated `calc-liquidity-rate`, while `idx` growth (and thus borrower debt) is computed with a single, more precise `mul-div-*`, this identity is broken: borrowers are charged the mathematically correct (higher-precision) interest, but depositors receive a systematically smaller (and in some periods zero) share of that same interest through `lindex`. The gap does not vanish into a rounding remainder held by the vault for later distribution — it is permanently lost from the `lindex` accrual for that period, since `lindex` is a monotonically-updated multiplicative index with no catch-up mechanism.

### Impact Explanation
This causes a persistent under-crediting of yield to LP/depositor shares relative to what borrowers actually pay in interest. In periods of low utilization or low borrow rate (common at protocol launch or in low-demand markets), the double floor-division can round the liquidity rate down to `0`, so `lindex` does not grow for that accrual period even though borrowers are still accruing debt via `idx`. Depositors permanently lose that period's yield — it is not deferred, since each `accrue` call captures the delta based on current state and moves `last-update` forward. This matches "High" impact under the given rubric: permanent freezing/loss of unclaimed yield for depositors, systemically and repeatedly (every low-rate/low-utilization accrual window), across every deployed vault (`vault-stx`, `vault-sbtc`, `vault-ststx`, `vault-ststxbtc`, `vault-usdc`, `vault-usdh`) since they all share this identical `calc-liquidity-rate`/`mul-bps-down` pattern.

### Likelihood Explanation
This requires no attacker action — it is a deterministic consequence of the vault's own `accrue` logic running under normal, expected market conditions (low utilization or low interest-rate regimes, which are common, especially for newly-launched or under-utilized vaults). Every call to `accrue` (triggered by any deposit, withdraw, borrow, or repay) recomputes and locks in the truncated liquidity rate, so the loss compounds naturally over the life of the vault with high likelihood.

### Recommendation
Replace the two sequential `mul-bps-down` calls in `calc-liquidity-rate` with a single fused multiply-divide over `BPS * BPS`, e.g. compute `mul-div-down(var-borrow-rate * util-pct, (BPS - reserve-factor-bps), BPS * BPS)` (guarding against overflow as needed), so that only one floor operation occurs instead of two, matching the precision of the borrow-side `idx` computation and preserving the interest-accrued-equals-interest-distributed identity.

### Proof of Concept
Using `BPS = 10000`:
- Let `var-borrow-rate = 199`, `util-pct = 101`, `reserve-factor-bps` such that `one-minus-rf = 9999`.
- Current (two-step) computation:
  - `util-applied = floor(199 * 101 / 10000) = floor(20099/10000) = 2`
  - `liquidity-rate = floor(2 * 9999 / 10000) = floor(19998/10000) = 1`
- Correct single-division computation:
  - `liquidity-rate = floor(199 * 101 * 9999 / 100000000) = floor(200,969,901 / 100,000,000) = 2`

The current implementation returns `1`, a 50% underestimate of the correct liquidity rate of `2`, directly reducing `lindex` growth (and hence depositor-owed interest) for that accrual period relative to what borrowers are simultaneously charged via `idx`, matching the same "division before completing multiplication" root cause as the referenced Ajna finding.
