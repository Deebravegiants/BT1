### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` identity used by `ShopifyAPI::Webhooks::Registry.process` entirely from the unauthenticated `x-shopify-shop-domain` HTTP header, while the HMAC signature validated by `Utils::HmacValidator` only ever covers the raw request body (`to_signable_string` returns `@raw_body`, nothing else). This breaks the binding "shop the webhook is attributed to == shop whose data is protected by the HMAC," allowing a valid signature computed for one shop's payload to be replayed against the app with a different `shop-domain` header, causing the app to process data as if it originated from another tenant.

### Finding Description
`ShopifyAPI::Auth::Oauth::AuthQuery#to_signable_string` deliberately includes `shop` in the signed string [1](#0-0) , showing the library's own design intent that identity-bearing fields must be part of the signed payload. `ShopifyAPI::Webhooks::Request`, however, implements `VerifiableQuery` by exposing `hmac` from the `hmac-sha256` header and `to_signable_string` as just `@raw_body` [2](#0-1) . The `shop`, `topic`, `api_version`, and `webhook_id` values are read straight from headers with no cryptographic binding to the signed body [3](#0-2) .

`Utils::HmacValidator.validate` verifies the HMAC strictly against `to_signable_string` (i.e., the body only) using the shared `Context.api_secret_key` [4](#0-3) . `Webhooks::Registry.process` then trusts the header-derived `request.shop` to build the `WebhookMetadata` passed to the app's handler, once the (body-only) HMAC check passes [5](#0-4) [6](#0-5) .

Because Shopify signs webhook deliveries for **all shops of an app using the same `api_secret_key`** (the app's shared client secret, not a per-shop secret), any (raw_body, hmac) pair that is genuinely valid for one shop's webhook delivery is *also* a valid HMAC for that same body under any other shop. A merchant who installs the app can register their own webhook subscription (via `webhookSubscriptionCreate`, using only their own store's access token — no app credentials required) pointing at an endpoint the merchant controls, thereby legitimately capturing a Shopify-generated `(raw_body, x-shopify-hmac-sha256)` pair for their own shop. The merchant can then replay that exact body/HMAC directly to the target app's public webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`) header to name a *different* victim shop. `HmacValidator.validate` will pass because it never inspects the shop header, and `Registry.process` will dispatch the forged payload to the handler tagged with the victim shop's identity.

### Impact Explanation
This is a cross-tenant boundary break: the app's webhook processing pipeline cannot distinguish "a genuinely signed body legitimately belonging to shop A" from "the same signed body maliciously relabeled as belonging to shop B." Depending on how a host app's `WebhookHandler#handle` implementation uses `data.shop` (e.g., to look up a stored session/access token and perform mutating actions, update local records, or trigger downstream automation for that shop), an attacker-controlled body can be injected into another tenant's data pipeline. This satisfies the Critical "cross-tenant access" impact category, since the gem's own webhook-authenticity guarantee is scoped only to the body, not the tenant the request claims to represent.

### Likelihood Explanation
The attacker capability required — installing the target app on their own shop and creating a self-directed webhook subscription via the standard Shopify Admin API using their own access token — is fully within reach of an ordinary, unprivileged merchant/user of the platform; it requires no leaked secrets, no TLS interception, and no privileged account. No other gem-level control (e.g., binding shop-domain into the signed content, or requiring the shop to be verified against a known/registered session) prevents this replay once the attacker holds one valid `(body, hmac)` pair for their own shop, so likelihood is high for any app relying solely on `ShopifyAPI::Webhooks::Registry.process`/`HmacValidator` as its webhook trust boundary.

### Recommendation
Bind the shop identity (and ideally topic/webhook id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the signed body, e.g. by including it in `to_signable_string`, or independently verifying that the reported `shop-domain` matches a shop for which the webhook subscription/id is actually registered before trusting `request.shop` in `Registry.process`. At minimum, document that `request.shop` is unauthenticated and must not be trusted for cross-tenant-sensitive actions without additional verification.

### Proof of Concept
1. Attacker (merchant of shop `attacker.myshopify.com`) installs the target app.
2. Attacker uses their own valid Admin API access token to run `webhookSubscriptionCreate` for topic `orders/create`, pointing the callback URL at a server they control.
3. Shopify delivers a webhook to the attacker's server: `raw_body = {...attacker order json...}`, header `x-shopify-hmac-sha256 = HMAC(api_secret_key, raw_body)`. Attacker captures both.
4. Attacker sends an HTTP POST directly to the real app's public webhook endpoint (e.g., `POST /callback/orders/create`) with the exact same `raw_body` and `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request#hmac`/`shop` read straight from headers [7](#0-6) ; `HmacValidator.validate` succeeds because it only checks the body signature [8](#0-7) .
6. `Registry.process` calls the handler with `WebhookMetadata.new(shop: "victim.myshopify.com", ...)`, and the app processes attacker-controlled data attributed to the victim shop [5](#0-4) .

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
