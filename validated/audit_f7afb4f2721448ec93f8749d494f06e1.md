### Title
Rollback of `_latestStateMachineHeight` to a hardcoded `1` on veto lets already-finalized state commitments be silently overwritten by later consensus proofs - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.deleteStateMachineCommitmentInternal` resets the monotonic height tracker `_latestStateMachineHeight[stateMachineId]` to a hardcoded constant `1` whenever the vetoed height happens to be the current latest, instead of restoring it to the actual previously-verified height. `HandlerV2.handleConsensus` relies entirely on `intermediate.height > latestHeight` to enforce that state commitments only ever move forward. Once the pointer collapses to `1`, this guard is effectively disabled for the whole range of previously-finalized heights, similar in spirit to the reported zkevm `binary.pil` bug where a value that must be pinned to a fixed value on "reset" (`cIn` on `RESET`) was instead left free for the prover to choose, letting an invalid statement be accepted as valid.

### Finding Description
`storeStateMachineCommitment` unconditionally overwrites `_stateCommitments[id][height]` for whatever height is passed in, and it is only ever called from `HandlerV2.handleConsensus` after checking: [1](#0-0) 

```
uint256 latestHeight = host.latestStateMachineHeight(intermediate.stateMachineId);
if (latestHeight != 0 && intermediate.height > latestHeight) {
    ... host.storeStateMachineCommitment(stateMachineHeight, intermediate.commitment);
}
```

This is the sole "reset" invariant protecting already-accepted state: any new intermediate state must be *strictly ahead* of the last one stored. The comment on `storeStateMachineCommitment` itself states `Assumes the state commitment is of the latest height.` [2](#0-1) 

However, `deleteStateMachineCommitmentInternal` (invoked from `deleteStateMachineCommitment`, restricted to `_hostParams.handler`, which is how fishermen veto fraudulent state commitments) resets the pointer to a fixed `1` rather than to the height that was actually verified before the vetoed one: [3](#0-2) 

```
function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
    StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitments[height.stateMachineId][height.height];
    delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
    // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
    if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
        _latestStateMachineHeight[height.stateMachineId] = 1;
    }
    ...
}
```

Contrast this with the equivalent Rust/pallet-ismp path, which correctly tracks and restores the *actual* previous height rather than a magic constant: [4](#0-3) 

The Solidity host never maintains an analogous `PreviousStateMachineHeight`. After a veto of the latest height, `_latestStateMachineHeight` becomes `1` — a value with no relationship to the chain's real prior verified height (which could be, e.g., 10,000,000). From that point on, `HandlerV2.handleConsensus`'s guard `intermediate.height > latestHeight` is satisfied by essentially *any* height the underlying `IConsensusV2` implementation reports as an intermediate state, including heights that were already legitimately finalized, already used to process post/get requests, or already relied upon for merkle proofs in `handlePostRequests`/`handleGetResponses`. This is exactly the "underconstrained reset" bug class: a value (`_latestStateMachineHeight`) that is supposed to be pinned to the trusted prior state on reset is instead left to an attacker-reachable range, letting a relayer submit a consensus proof (from `IConsensusV2.verify`, whose own internal `latestHeight`/authority-set bookkeping is independent of this host-side pointer) that legally advances *its own* internal state while re-emitting/overwriting an `IntermediateState` for a height already finalized on the host, silently replacing its `StateCommitment` (state root + overlay root).

### Impact Explanation
Overwriting `_stateCommitments[id][height]` for a height that message proofs have already been (or could still be) verified against breaks the core soundness property of the state-proof pipeline:
- `handlePostRequests`/get-response handlers verify merkle multi-proofs against `host.stateMachineCommitment(request.proof.height).overlayRoot` [5](#0-4) . If the `overlayRoot`/`stateRoot` at a previously-finalized height is replaced, a relayer could get requests processed against a *different* child-trie/state root than what was originally finalized for that height, i.e. forged message delivery or unauthorized reprocessing at a height whose data no longer matches on-chain history on the counterparty chain.
- Because the check is `latestHeight != 0`, this reopens the entire window `(1, originalLatestHeight]`, not just the vetoed height, for silent overwrite by any future consensus update that reports an intermediate at one of those heights.

This maps to "unsound state commitment" / "forged message delivery," reachable by any relayer submitting a `handleConsensus` proof after a (correct, honestly-triggered) veto event — no privileged action needed on the attacker's part beyond submitting a consensus proof through the normal permissionless relayer path.

### Likelihood Explanation
Triggering the precondition (a veto at the *current latest* height) is a normal, expected part of protocol operation — fishermen are meant to veto fraudulent commitments, and this is not itself an admin/governance action; `deleteStateMachineCommitment` is `restrict(_hostParams.handler)`, invoked by `HandlerV2` on behalf of the fisherman flow. Once that occurs, exploitation only requires a subsequent, otherwise-valid consensus proof (via BEEFY/SP1/GRANDPA/etc.) whose `IntermediateState[]` includes a height in the now-reopened window — something a relayer legitimately produces during normal syncing (e.g., BEEFY/GRANDPA proofs can include multiple intermediate parachain headers per update, or a relayer could deliberately request/replay an old but still consensus-valid header set covering an already-finalized height). No cryptographic break is needed; only the host-side bookkeeping is faulty.

### Recommendation
Track the true previous verified height per state machine (mirroring `PreviousStateMachineHeight` in `modules/pallets/ismp/src/host.rs`) and restore that value in `deleteStateMachineCommitmentInternal` instead of the hardcoded `1`:
- Add a `_previousStateMachineHeight[stateMachineId]` mapping, updated in `storeStateMachineCommitment` before overwriting `_latestStateMachineHeight`.
- In `deleteStateMachineCommitmentInternal`, when `_latestStateMachineHeight[id] == height.height`, restore `_latestStateMachineHeight[id] = _previousStateMachineHeight[id]` (with appropriate handling if none exists, e.g., only allow veto-driven resets when a valid prior height is known), so `HandlerV2.handleConsensus`'s `intermediate.height > latestHeight` guard cannot be satisfied by already-finalized heights.

### Proof of Concept
1. Host has state machine `S` with `_latestStateMachineHeight[S] = 1000` (legitimately finalized through prior consensus proofs, request/response proofs already processed against height 1000's commitment).
2. A fisherman correctly vetoes height `1000` via `deleteStateMachineCommitment` (handled through `HandlerV2`/host restricted path) because it was fraudulent. This sets `_latestStateMachineHeight[S] = 1` per `evm/src/core/EvmHost.sol:719-721`.
3. Foundry test `HostManagerTest`/`EvmHostTest` conventions confirm `storeStateMachineCommitment` directly sets `_latestStateMachineHeight` to whatever height is passed with no lower bound check other than the caller-side `intermediate.height > latestHeight` in `HandlerV2` [6](#0-5) .
4. A relayer submits a new (cryptographically valid, from the consensus client's perspective) `handleConsensus` proof whose `IntermediateState[]` includes height `500` (already finalized previously with a different `StateCommitment`, and already possibly used for message proofs). Since `latestHeight (1) != 0 && 500 > 1`, `storeStateMachineCommitment` is called and overwrites `_stateCommitments[S][500]` with a new, different commitment.
5. Any subsequent `handlePostRequests` call against `StateMachineHeight{S, 500}` now verifies merkle proofs against the newly-substituted `overlayRoot`, diverging from what was originally finalized — enabling forged or duplicate message delivery at that height.

Exact reproduction against the live contract bytecode/consensus-client wiring (e.g., confirming a concrete `IConsensusV2` implementation can emit an `IntermediateState` for an already-passed height) was not independently executed in this review; the described flow is derived directly from the code paths cited above.

        external

        _stateCommitments[height.stateMachineId][height.height] = commitment;

     * @dev Delete the state commitment at given state height.

    function deleteStateMachineCommitmentInternal(StateMachineHeight memory height, address fisherman) internal {
        StateCommitment memory stateCommitment = _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitments[height.stateMachineId][height.height];
        delete _stateCommitmentsUpdateTime[height.stateMachineId][height.height];
        // technically any state commitment can be vetoed, safety check that it's the latest before resetting it.
        if (_latestStateMachineHeight[height.stateMachineId] == height.height) {
            _latestStateMachineHeight[height.stateMachineId] = 1;
        }

        // track the fisherman responsible for rewards on hyperbridge through state proofs
        _vetoes[height.stateMachineId][height.height] = fisherman;

        emit StateCommitmentVetoed({
            stateMachineId: this.stateMachineId(_hostParams.hyperbridge, height.stateMachineId),
            stateCommitment: stateCommitment,
            height: height.height,
            fisherman: fisherman
        });
    }
