### Title
Webhook `shop-domain` header is not covered by the HMAC signature, enabling cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop` (and `topic`, `api_version`, `webhook_id`) from unauthenticated HTTP headers, while `Utils::HmacValidator.validate` only verifies the raw request body against the shared `api_secret_key`. The `shop` value handed to the app's webhook handler is therefore never cryptographically bound to the HMAC that "authenticates" the request.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are read straight from headers with no signature coverage: [2](#0-1) 

`HmacValidator.validate` computes the HMAC purely from `verifiable_query.to_signable_string` (i.e., the body) and the app's `api_secret_key`: [3](#0-2) 

`Registry.process` validates the HMAC and then dispatches to the handler using `request.shop` taken directly from the unsigned header: [4](#0-3) 

**Binding that should hold but doesn't:** `hmac == HMAC(api_secret_key, body ∥ shop)` — instead the gem only checks `hmac == HMAC(api_secret_key, body)`, so `shop` is fully attacker-controlled independent of the signature.

The `api_secret_key` used for webhook HMACs is a single per-app secret shared across every shop that has installed the app — it is not shop-specific. Any merchant who installs the app (an "unprivileged" tenant with respect to *other* merchants' data) legitimately receives correctly-signed webhooks for their own shop. Because the signature covers only the JSON body and not the `shop-domain` header, that merchant can capture a genuine `(raw_body, hmac)` pair from their own shop's webhook delivery, then replay it to the app's webhook endpoint with the `x-shopify-shop-domain` (or `shopify-shop-domain`) header rewritten to a victim shop's domain. `HmacValidator.validate` still succeeds because it re-derives the same HMAC from the same body, and `Registry.process` passes the forged `shop` straight into `WebhookMetadata`/the handler.

### Impact Explanation
This breaks the shop-authentication boundary the HMAC is meant to enforce: cross-tenant data can be attributed to, or acted upon, a shop the attacker does not control. Depending on how the host application's webhook handler uses `data.shop` (e.g., to look up the session/access token for the shop, update per-shop billing state, redact/write data, or trigger side effects keyed by shop), this enables cross-tenant access/confusion — one of the explicitly in-scope Critical impacts (cross-tenant access) driven entirely by this gem's own trust boundary.

### Likelihood Explanation
Any actor able to install the target app on their own store (a normal, unprivileged action for a public app) can obtain a validly-signed webhook body/HMAC pair for their own shop and immediately replay it against the same public webhook endpoint with a modified shop header — no access token, `api_secret_key`, or privileged access is required, satisfying the "unprivileged internet user" constraint.

### Recommendation
Include the shop domain (and ideally topic/api_version/webhook_id) in the signed material verified against the HMAC, or otherwise cryptographically bind the `shop-domain` header to the signature (e.g., verify it out-of-band against a known/expected shop for the endpoint, or require Shopify's newer signed webhook headers that cover more than the body). At minimum, document that `request.shop` must not be trusted without additional verification, and ideally have `HmacValidator`/`Request` refuse to validate unless the shop domain is included in the signable string.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any registered webhook (e.g., `orders/create`) for that shop; capture the raw POST body and the `x-shopify-hmac-sha256` header Shopify sends — this HMAC is valid because it's computed with the app's single shared `api_secret_key` over the body only.
3. Replay the identical body and HMAC header to the app's webhook endpoint, but set `x-shopify-shop-domain: victim.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `Digest.hexencode(...) == HMAC(api_secret_key, raw_body)`; `request.shop` returns `"victim.myshopify.com"` unchecked, and the handler is invoked with `WebhookMetadata` claiming the payload originated from `victim.myshopify.com`.           if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
