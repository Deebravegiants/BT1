Found a solid analog: the native-fee-swap inside `IntentGatewayV2.placeOrder` performs an on-chain Uniswap V2 swap for every order that pays its solver fee in native token, and it inherits the exact same "no real slippage/deadline protection" pattern flagged in the Sherlock report.

### Title
Unprotected Uniswap V2 fee-swap in `placeOrder` lets a sandwich bot overcharge users' native-token fee payment - ([File: evm/src/apps/IntentGatewayV2.sol])

### Summary
Every user that calls `placeOrder` and pays `order.fees` in the native token triggers an on-chain `swapETHForExactTokens` call to convert ETH into the Hyperbridge fee token. The swap's deadline argument is `block.timestamp`, which is always satisfied at execution time and therefore provides no protection against delayed/adversarially-ordered execution, and the only "slippage bound" is whatever `msg.value` the caller happened to send — a value the client computed from a stale, pre-transaction quote. This mirrors the Sherlock finding's root cause: an unprotected DEX action (`join`/`exit`/`swap`) executed on a user's behalf with no meaningful minOut/maxIn bound tied to the actual execution price.

### Finding Description
In `placeOrder`, when the order pays fees in native token: [1](#0-0) 

```solidity
if (order.fees > 0) {
    address feeToken = IDispatcher(hostAddr).feeToken();
    if (msgValue > 0) {
        address uniswapV2 = IDispatcher(hostAddr).uniswapV2Router();
        address WETH = IUniswapV2Router02(uniswapV2).WETH();
        address[] memory path = new address[](2);
        path[0] = WETH;
        path[1] = feeToken;
        uint256[] memory amounts = IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msgValue}(
            order.fees, path, address(this), block.timestamp
        );
        msgValue -= amounts[0];
    } else {
        IERC20(feeToken).safeTransferFrom(msg.sender, address(this), order.fees);
    }
    _orders[commitment][TRANSACTION_FEES] = order.fees;
}
```

`swapETHForExactTokens` is an exact-output swap: it buys the exact `order.fees` amount of fee token, spending however much ETH the pool's *current* price requires, up to the `msgValue` ceiling. Two problems compound:

1. **`deadline = block.timestamp`** is evaluated at execution time inside the same transaction, so it can never actually expire the swap — it offers zero protection against price movement between the moment the client quoted `nativeValue` off-chain and the moment the transaction lands. This is the identical documented client flow: `docs/content/developers/evm/intent-gateway/placing-orders.mdx` instructs callers to quote `nativeValue` via `quoteOrderFees()` before submission, and "unused native is refunded" — implying no on-chain freshness check exists beyond the caller's own stale quote.
2. **The only ceiling on input price is `msg.value`.** An attacker who front-runs the `placeOrder` transaction can push the WETH→feeToken pool price up (classic sandwich buy) so that the exact-output swap consumes more of the user's ETH for the same `order.fees` output than the client quoted, extracting the price impact from the user, then back-runs to sell and capture the difference. If `msgValue` doesn't cover the manipulated price the call reverts (griefing/DoS); if it does, the user silently overpays.

This exactly parallels the reported bug class (Balancer `join`/`exit`/`swap` calls with an unenforced/zero `minValueOut`/`maxValueIn`): a protocol-initiated DEX action on behalf of an ordinary user, gated only by a value the user supplied ahead of time from a stale off-chain quote, with no on-chain deadline enforcement.

### Impact Explanation
Any unprivileged user calling `placeOrder` with a native-token fee payment is exposed to sandwich extraction on the fee-swap leg. While the amount at risk (`order.fees`, a small relayer/gas-cost fee) is typically modest relative to the escrowed order inputs, it is real, unauthorized value extraction reachable from a single ordinary submitted transaction with no special conditions required — MEV searchers already scan mempools for exactly this pattern. It can also be weaponized as griefing/DoS: an attacker can force the swap to revert by moving the price beyond `msgValue`, wasting the user's gas and blocking order placement.

### Likelihood Explanation
High likelihood of opportunistic exploitation: `placeOrder` is the primary unprivileged entry point of the Intent Gateway, native-fee payment is a documented, first-class path (per `placing-orders.mdx`), and the vulnerable swap is unconditionally triggered whenever `msgValue > 0`. No special permissions or preconditions are needed by the attacker beyond mempool visibility and DEX liquidity to sandwich.

### Recommendation
- Replace `block.timestamp` with a real caller-supplied deadline parameter (e.g., part of `Order` or a new argument) so a delayed/replayed transaction can actually expire.
- Bound execution price explicitly: require the caller to pass an expected `maxNativeIn` (rather than relying on `msg.value` alone as an implicit, coarse cap) or fetch a fresh on-chain TWAP/oracle-derived bound before swapping, similar to how `SimplexPaymaster.swapAndDeposit` derives `amountOutMin` from Chainlink oracles.
- Consider letting large/fee-sensitive orders route the fee-token swap off-chain (client-side, pre-approved) instead of an on-chain exact-output swap embedded in `placeOrder`.

### Proof of Concept
1. User calls `quoteOrderFees()` off-chain, gets `nativeValue` for `order.fees` at the current WETH/feeToken pool price, and submits `placeOrder{value: nativeValue}(order, graffiti)`.
2. Attacker observes the pending transaction in the mempool and front-runs it with a large WETH→feeToken buy on the same Uniswap V2 pool, raising the effective ETH cost of `feeToken`.
3. The victim's `placeOrder` transaction executes `swapETHForExactTokens(order.fees, path, address(this), block.timestamp)`; because `block.timestamp` is evaluated at that same block it never reverts on staleness, and the swap either (a) consumes more of `msgValue` than the quote assumed, silently costing the user more ETH per fee token than quoted, or (b) reverts entirely if `nativeValue` was tight, wasting the user's gas.
4. Attacker back-runs with a sell to realize the sandwich profit extracted from the victim's swap. [1](#0-0) [2](#0-1) [3](#0-2)

### Decide how `order.fees` is paid

`order.fees` is the gas cost the solver spends on filling the order, denominated in the source chain's Hyperbridge fee token. For a cross-chain order it also covers the relayer that delivers the `RedeemEscrow` settlement message back to the source chain. It is not the protocol fee and it is not your wallet's transaction gas.

Quote it with `quoteOrderFees()` and set it on the order:

```typescript title="quote-order-fees.ts" lineNumbers
const { fees, nativeValue, feeToken } = await gateway.quoteOrderFees(order)
order.fees = fees
```

Then pick how it gets paid and confirm the wallet can cover it.

#### Native token

The placement transaction carries `nativeValue` extra wei, which the gateway swaps into the fee token through its configured router (unused native is refunded). Check the balance now; the placement step adds `nativeValue` to the transaction:

```typescript title="check-native-fee.ts" lineNumbers
const nativeBalance = await sourceChain.client.getBalance({ address: account.address })
if (nativeBalance < nativeValue) throw new Error("Insufficient native balance for the solver fee")
```

The wallet still pays normal transaction gas on top of this value.
