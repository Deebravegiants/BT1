### Title
Unbounded ancestry walk in GRANDPA finality verification can loop forever on a cyclic header set submitted in a relayed consensus proof - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
The GRANDPA light-client's `AncestryChain::ancestry` walks parent hashes from a `block` back to a `base` hash using a `while current_hash != base` loop that only terminates via a `None` lookup miss or reaching `base`. If the attacker-supplied `unknown_headers` set (part of the submitted `FinalityProof`/consensus message) contains a header whose parent-hash chain cycles among hashes that are all present in the map (e.g., a header's parent points back into the same set without ever equaling `base`), the loop never terminates and never returns `Err(NotDescendent)`, hanging the verifying node/runtime indefinitely — the same "wait forever due to unvalidated attacker-controlled input" root cause as CVE-2021-28484.

### Finding Description
`AncestryChain::ancestry` in `modules/consensus/grandpa/primitives/src/justification.rs` builds a `BTreeMap<Hash, Header>` from the caller-supplied `unknown_headers` (untrusted, attacker/relayer controlled) and then walks:

```rust
fn ancestry(&self, base: H::Hash, block: H::Hash) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
    let mut route = vec![block];
    let mut current_hash = block;
    while current_hash != base {
        match self.ancestry.get(&current_hash) {
            Some(current_header) => {
                current_hash = *current_header.parent_hash();
                route.push(current_hash);
            },
            _ => return Err(finality_grandpa::Error::NotDescendent),
        };
    }
    Ok(route)
}
``` [1](#0-0) 

This is the *only* exit path besides reaching `base`: a lookup miss. The `unknown_headers` in the proof are decoded directly from untrusted bytes and no cycle-detection or maximum-hop bound is applied before this traversal begins:

```rust
let first_headers = AncestryChain::<SubstrateHeader>::new(&first_proof.unknown_headers);
...
let first_chain = first_headers.ancestry(first_base.hash(), first_target.hash())...
``` [2](#0-1) 

Because the map is keyed by header hash, an attacker can submit a set of headers where every header hash referenced along the walk resolves via `Some(...)` (i.e., is present in the map) yet the chain of `parent_hash` values never lands on `base` and instead revisits hashes already seen — for example two headers `H1`, `H2` where `H1.parent_hash() == H2.hash()` and `H2.parent_hash() == H1.hash()`, both included in `unknown_headers`, with `base` chosen to be unreachable from either. Each iteration performs a valid `BTreeMap::get`, so the loop keeps returning `Some` forever, spinning the CPU without bound — never returning to the caller. This mirrors the Yubico advisory's root cause: a handler that keeps calling the same underlying primitive in a loop with no termination guarantee because the length/shape of attacker-supplied input was never validated for the property the loop assumes (finite descent to `base`).

### Impact Explanation
This function is invoked from `verify_fraud_proof` in the ISMP GRANDPA consensus client, which is reachable by submitting a fraud-proof/consensus message containing two `FinalityProof`s built from relayer/attacker-controlled `unknown_headers` and `justification` bytes:

```rust
let first_headers = AncestryChain::<SubstrateHeader>::new(&first_proof.unknown_headers);
...
let first_chain = first_headers.ancestry(first_base.hash(), first_target.hash())
    .map_err(|_| GrandpaError::InvalidAncestry)?;
``` [3](#0-2) 

A submitted proof that triggers an infinite loop here will hang the executing thread (or, if executed as part of on-chain/runtime dispatch, indefinitely consume block execution resources) processing that single message, blocking the GRANDPA consensus client from making further progress and denying service to the ISMP message pipeline that depends on it (dispatch/delivery of cross-chain messages relying on GRANDPA-finalized state). This is a route-unable-to-deliver-messages class of impact: a relayer or verifier stuck in this loop cannot process subsequent legitimate consensus updates or requests routed through the affected consensus client, which is a High-severity denial-of-service on the messaging pipeline, consistent with the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
The `unknown_headers` field of a `FinalityProof` is attacker/relayer-supplied SCALE-decoded data with no on-chain length or structural constraints preventing a cyclic parent-hash relationship among the submitted headers (the codebase does bound the SCALE-decoded proof's outer size elsewhere, e.g. `MaxProofSize` in other pallets, but no evidence was found that `unknown_headers`' shape is validated for acyclicity before the ancestry walk). Constructing two headers whose parent hashes point at each other (or at any hash cycle contained in the submitted set) is a straightforward, cheap, and fully attacker-controlled operation, requiring only a single malformed fraud-proof submission — directly analogous to the 0/1/2-byte trigger in the Yubico advisory.

### Recommendation
Bound the `ancestry` walk with an explicit maximum iteration count (e.g., the size of the `unknown_headers` map, since any valid acyclic chain can visit each header at most once) and return an error once that bound is exceeded, rather than relying solely on a `None` lookup to terminate. Alternatively, track visited hashes in a `HashSet`/`BTreeSet` during the walk and return `Err(NotDescendent)` immediately if a hash is revisited.

### Proof of Concept
1. Construct two headers `H1` and `H2` such that `H1.parent_hash() = H2.hash()` and `H2.parent_hash() = H1.hash()` (a two-node cycle), both included in `first_proof.unknown_headers`.
2. Set `first_proof.block = H1.hash()` (so `first_target = H1`), and choose `first_base` such that `first_base.hash()` is neither `H1.hash()` nor `H2.hash()` and is not present in `unknown_headers` at all (so the walk from `H1` can never reach it).
3. Submit this as part of a `verify_fraud_proof` call (or the equivalent path that constructs `AncestryChain::new(&first_proof.unknown_headers)` and calls `.ancestry(first_base.hash(), first_target.hash())`).
4. The `while current_hash != base` loop in `AncestryChain::ancestry` alternates `current_hash` between `H1.hash()` and `H2.hash()` forever, since both are present in `self.ancestry` and neither equals `base` — the call never returns, hanging the calling thread/verification indefinitely.
