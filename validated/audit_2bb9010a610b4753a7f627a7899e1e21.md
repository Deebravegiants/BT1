### Title
Webhook `shop` (and `topic`/`webhook_id`) header is trusted for tenant attribution without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies a webhook's HMAC before dispatching it to the app's handler, but the HMAC only signs the raw request body. The `shop-domain` header — which the gem exposes as `WebhookMetadata#shop` and which apps use to attribute the webhook to a specific merchant/tenant — is never included in the signed material. Because a single app's `api_secret_key` is shared across every shop that installs it, any merchant who legitimately receives one valid webhook can replay that exact body+HMAC pair to the app's public webhook endpoint while substituting a victim shop's domain in the `shop-domain` header, and the gem will accept it as authentic.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers and are not part of the signable string: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC over `verifiable_query.to_signable_string` only: [3](#0-2) 

`Registry.process` uses this validation as the sole authenticity check, then forwards `request.shop` (the unauthenticated header) straight into `WebhookMetadata`, which the app's handler uses to attribute the webhook to a tenant: [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `shop domain covered by the HMAC == shop domain the handler treats as the event's tenant`. Instead, the gem verifies `HMAC(raw_body)` but acts on `header["shop-domain"]`, which is disjoint from what was signed. The documentation explicitly tells developers this call "will verify the request did indeed come from Shopify" and shows `data.shop` being passed downstream (e.g., `perform_later(topic: data.topic, shop_domain: data.shop, ...)`), reinforcing the (false) assumption that `shop` is authenticated: [6](#0-5) [7](#0-6) 

### Impact Explanation
Because `api_secret_key`/`old_api_secret_key` are per-app, not per-shop, any merchant who has legitimately installed the app can obtain a valid `(raw_body, hmac)` pair from a real Shopify-originated webhook for their own store. That merchant can then POST the identical body/HMAC to the app's public webhook route with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header rewritten to a different, victim shop. The gem's HMAC check still passes (it never inspected the header), and the handler executes with `data.shop` equal to the attacker-chosen victim domain and `data.body` equal to attacker-controlled JSON. Depending on how the host app trusts `data.shop`/`data.topic`/`data.webhook_id` to select and mutate per-tenant records, this allows cross-tenant data injection/corruption or forged lifecycle events (e.g., forging an `app/uninstalled` for a shop the attacker does not own), which is a cross-tenant access issue.

### Likelihood Explanation
Exploitation only requires being (or becoming) an installed merchant of the target app to harvest one legitimate webhook, plus the ability to send an unauthenticated HTTP POST to the app's public webhook endpoint — no access token, session, or `client_secret` theft is required, and the webhook endpoint is by design internet-reachable and unauthenticated aside from the HMAC check.

### Recommendation
Bind the tenant-identifying fields into the signed material, or otherwise cryptographically verify `shop` against a known/active session before trusting it: e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string` (matching what Shopify actually signs is not possible since Shopify only signs the body, so the gem should instead require/encourage callers to cross-check `request.shop` against their own stored, previously-authenticated shop/session records before processing, and should update `docs/usage/webhooks.md` to make explicit that `HmacValidator` only authenticates body provenance for the app as a whole, not the asserted shop).

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker.myshopify.com` (a legitimate action any merchant can take for a public app).
2. Attacker triggers a webhook event on their own store (e.g., updates an order) and captures the resulting POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
3. Attacker sends a new POST to the app's webhook endpoint with the exact same body `B` and header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally forges `X-Shopify-Topic` / `X-Shopify-Webhook-Id`, also unauthenticated).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC(api_secret_key, B)` and matches `H` — validation passes.
5. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: JSON.parse(B), ...)` and performs tenant-scoped work under the victim's identity using attacker-supplied body content.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
