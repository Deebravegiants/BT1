### Title
Unauthenticated test-only setters `set_controller`/`set_price_aggregator` compiled behind `testing` feature can permanently brick or hijack the governance→controller wiring - (File: contracts/governance/src/deploy.rs)

### Summary
The bug class in the reference report is placeholder/test logic left in the production source that assigns wrong values to critical addresses (`freezerAddress = _projectAddress`). The direct analog in this codebase is the pair of test-only `#[contractimpl]` entry points `Governance::set_controller` and `Governance::set_price_aggregator` in `contracts/governance/src/deploy.rs`, which write the two most security-critical addresses in the system with **no authorization check whatsoever**, gated only by `#[cfg(any(test, feature = "testing"))]`.

### Finding Description [1](#0-0)  defines:

```rust
#[cfg(any(test, feature = "testing"))]
#[soroban_sdk::contractimpl]
impl Governance {
    pub fn set_controller(env: Env, addr: Address) {
        storage::set_controller(&env, &addr);
    }
    pub fn set_price_aggregator(env: Env, addr: Address) {
        storage::set_price_aggregator(&env, &addr);
    }
}
```

Unlike `execute_immediate` in `contracts/governance/src/timelock/testing.rs` (which at least enforces `require_auth` plus owner/`ORACLE_ROLE` checks, [2](#0-1) ), these two setters perform no `require_auth`, no owner check, and no timelock. Any address that can submit a contract invocation can overwrite:

- `storage::controller` — the address that `deploy_price_aggregator` pushes via `ControllerAdminClient::set_price_aggregator` ( [3](#0-2) ) and that every resolved controller admin operation targets through `env.invoke_contract(&operation.target, ...)`.
- `storage::price_aggregator` — the oracle hub address governance records.

Because `deploy_controller`/`deploy_price_aggregator` assert `!storage::has_controller(env)` / `!storage::has_price_aggregator(env)` ( [4](#0-3) ), a single call to `set_controller` permanently satisfies `has_controller`, so the legitimate deterministic deployment path is bricked forever and every subsequent timelocked controller operation is routed to the attacker-chosen address.

### Impact Explanation
If the governance wasm is ever built with `--features testing` (the feature exists precisely so test harnesses compile these entry points, e.g. `tests/test-harness`/`services/keeper` feature wiring), an unprivileged caller can:

1. Call `set_controller(attacker_contract)` before the real deployment — permanently blocking `deploy_controller` (`PoolAlreadyDeployed`), so the lending controller can never be wired in: the protocol is unable to operate and any pool funds sent in anticipation are frozen.
2. Point `price_aggregator` at a malicious contract, so governance-recorded oracle configuration and any cross-call into the aggregator go to attacker code.
3. Have all future controller-bound admin operations (`operation.target` resolution) delivered to the attacker contract, which can accept them silently while the real system is dead.

This is permanent freezing of funds / contract unable to operate — an accepted impact — reachable by a single unprivileged transaction.

### Likelihood Explanation
The vulnerability is latent: it only materializes if the `testing` feature is enabled in the deployed build — exactly the same "test code left in the codebase" precondition as the original rICO finding. It cannot be confirmed from source alone whether release builds enable the feature (the workspace `Cargo.toml` feature wiring was not fully verified), which is why this is a build-hygiene/production-readiness defect rather than a presently-exploitable bug. Medium severity: high impact, contingent likelihood.

### Recommendation
- Remove the `#[contractimpl]` test setters from the production crate entirely; inject controller/aggregator addresses in tests via storage manipulation or a separate test helper contract.
- At minimum, add `caller.require_auth()` + owner check, but the correct fix is deletion — test-only bypasses of the deploy invariant (`has_controller` gating) should not exist behind a feature flag.
- Add a build assertion/CI check that production wasm artifacts are compiled without `--features testing`.

### Proof of Concept
```rust
// Deployed governance wasm built with `--features testing`.
let gov = GovernanceClient::new(&env, &gov_address);

// Any unprivileged address:
gov.set_controller(&attacker_contract);   // no auth required -> succeeds
// Now has_controller() == true, so:
gov.schedule(/* DeployController op */);  // later executes deploy_controller
// -> panics GenericError::PoolAlreadyDeployed, forever.
// All controller-targeting admin ops now invoke attacker_contract.
```
