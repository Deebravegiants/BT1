### Title
Webhook `shop` (and `topic`) Header Not Bound by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, then trusts the `shop`, `topic`, `api_version`, and `webhook_id` values taken from HTTP headers that are never included in that signature. Any shop that has installed the app (an "unprivileged" tenant relative to other merchants) can capture one of its own legitimately-signed webhook deliveries and replay it to the app's webhook endpoint with a forged `shop-domain` header, since the app's HMAC secret (`api_secret_key`) is shared across every shop installation.

### Finding Description
The webhook `HmacValidator.validate` call only checks the HMAC against `Request#to_signable_string`, which is defined as the raw JSON body: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all pulled directly from headers with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC and then unconditionally forwards `request.shop` (and `request.topic`) to the caller's handler as the tenant identifier for the payload: [3](#0-2) 

Because Shopify signs webhooks with the single app-level `api_secret_key` (the same secret used for every shop that has the app installed) rather than a shop-specific key, a valid `hmac-sha256` value only proves "this body was signed by an entity holding this app's secret" — it proves nothing about which shop the header claims the payload came from. The equality the code implicitly (and incorrectly) assumes is:

`HMAC-valid(body) == (shop-domain header is authentic)`

but the actual guarantee provided by the HMAC is only:

`HMAC-valid(body) == (body was produced by holder of api_secret_key)`

Any merchant who installs the target app is such a holder-adjacent party in the sense that Shopify will produce a validly-signed webhook for that merchant's own store activity. That merchant can intercept their own webhook (body + valid HMAC), then resend the identical body/HMAC pair to the app's public webhook endpoint while substituting `shop-domain` (and/or `topic`) headers of a different, victim shop. `Utils::HmacValidator.validate` still returns `true` because it never inspects the headers, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload is for the victim shop.

### Impact Explanation
This breaks the tenant-authentication boundary the webhook handler relies on: application code built on this gem typically uses `WebhookMetadata#shop` to determine which merchant's data to create/update/delete. Forging that field lets an authenticated-but-unprivileged tenant (any shop with the app installed) inject or corrupt data attributed to another shop, i.e. cross-tenant access, which is explicitly listed as a Critical-severity outcome.

### Likelihood Explanation
Exploitation requires only that the attacker's own shop has installed the vulnerable app (a normal, unprivileged position — no leaked credentials, no `api_secret_key`, no privileged account needed) and the ability to capture/replay one webhook delivery to the same public endpoint, substituting headers. No secret material needs to be known or brute-forced, since the same valid HMAC/body pair is reused verbatim.

### Recommendation
Do not accept headers outside the HMAC's signed payload as authoritative for tenant identity. Either:
- Extend the signable string used in `Webhooks::Request#to_signable_string` (and the corresponding computation Shopify performs) to include `shop-domain`/`topic`, or
- Require callers to independently verify `request.shop` corresponds to a shop with an active, previously-established relationship/session for the specific `webhook_id`/topic before trusting it, and reject duplicate or mismatched deliveries.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) so Shopify delivers a body `B` with a valid `x-shopify-hmac-sha256` computed over `B` using the app's `api_secret_key`.
2. Attacker captures the raw POST: headers `x-shopify-topic`, `x-shopify-hmac-sha256`, `x-shopify-shop-domain: attacker.myshopify.com`, body `B`.
3. Attacker resends the exact same body `B` and the same `x-shopify-hmac-sha256` value to the app's public webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb` and `Request#to_signable_string`, only body is checked).
5. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_B, ...)`, causing the host application to act on `B`'s contents as though they originated from the victim shop.
