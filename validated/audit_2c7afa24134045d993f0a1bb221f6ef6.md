### Title
Webhook Processing Trusts Unauthenticated `shop-domain` Header Not Covered by HMAC, Enabling Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` is documented to "verify the request did indeed come from Shopify," but the HMAC only authenticates the raw request body — the `shop-domain`, `topic`, `api-version`, and `webhook-id` headers are read directly and passed to the app's handler without any binding to the signature. Because the client secret used to sign webhooks is shared across every shop that has installed the app, any merchant who installs the app can capture one of their own legitimately-signed webhook deliveries and replay it to the app's webhook endpoint with a forged `shop-domain` header, causing the app to process attacker-controlled webhook data under an arbitrary victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `api_version`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic tie to the signed payload: [2](#0-1) 

`HmacValidator.validate` only checks `verifiable_query.to_signable_string` (i.e. the body) against the computed HMAC: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC, then constructs `WebhookMetadata` directly from the unauthenticated `request.shop`/`request.topic` headers and hands it to the app's handler: [4](#0-3) 

The documentation explicitly tells integrators that `process` "will verify the request did indeed come from Shopify," and shows the resulting `data.shop` being used directly as the tenant identifier (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [5](#0-4) [6](#0-5) 

The binding that should hold is: `shop header == shop that the HMAC-signed body actually originated from`. In practice, the gem verifies `raw_body == HMAC(raw_body, client_secret)` but never verifies `shop header ⊆ signed content`. Since the app's `client_secret` is the same for every shop's webhooks (it is per-app, not per-shop), a single valid `(raw_body, hmac)` pair obtained from *any* shop that has installed the app remains valid regardless of which `shop-domain` header accompanies it.

### Impact Explanation
An unprivileged attacker who installs the target app on their own store (a normal, unprivileged action requiring no special access) receives genuinely Shopify-signed webhooks for their own shop. They can replay that exact `raw_body` + `hmac-sha256` header to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header value (e.g. a victim merchant's domain). `HmacValidator.validate` still passes because it only checks the body/secret pair, so `Registry.process` dispatches the attacker-controlled body to the app's handler tagged with the victim's shop. Any host application that trusts `data.shop` as authenticated tenant context (as the gem's own documentation instructs) will process fabricated data as if it originated from the victim's store — e.g., forging `orders/create`, `app/uninstalled`, or GDPR webhook payloads attributed to a shop the attacker does not control. This is a cross-tenant identity-binding break rooted entirely in this gem's webhook verification logic.

### Likelihood Explanation
Likelihood is high for any app that follows the documented webhook processing pattern: the attacker only needs to install the app in their own shop (an ordinary merchant action) to obtain one valid signed payload, then can freely swap the `shop-domain` header on replay. No access token, `client_secret`, or privileged access is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) claim into the value that is actually authenticated. Options include:
- Verify the `shop-domain` header against a known/expected shop tenant (e.g., only trust shops with an active installation record) before dispatching.
- Extend `to_signable_string` (or a companion check) to include the relevant headers so the HMAC covers `shop`, `topic`, and `webhook_id`, matching the guarantee documented in `docs/usage/webhooks.md`.
- At minimum, document loudly that `process` does not authenticate the `shop` header and that callers must independently confirm the shop is one they have an active session/installation for before trusting `data.shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com`.
2. Shopify sends a legitimately HMAC-signed webhook, e.g. `orders/create`, to the app's endpoint with headers:
   `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`, and body `B`.
3. Attacker captures `B` and the valid `hmac-sha256` value.
4. Attacker crafts a new HTTP POST to the same webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `HmacValidator.validate` (`lib/shopify_api/utils/hmac_validator.rb`) recomputes the HMAC over `B` using the app's `client_secret`; it matches, since the secret and body are unchanged — validation succeeds.
6. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:189-199`) builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` from the forged header and invokes the app's handler, which — per the gem's own documented usage pattern — treats `data.shop` as an authenticated tenant identifier and processes the attacker's payload as if it came from the victim shop.

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
