### Title
Webhook `shop` (and `topic`/`webhook_id`) identity is trusted from unauthenticated HTTP headers while the HMAC only covers the raw body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` verifies the HMAC over the raw request body only, but the shop identity used by consuming applications (`Request#shop`, sourced from the `X-Shopify-Shop-Domain` header) is never included in the signed material. This breaks the binding "field acted on == field covered by HMAC" that the report's bug class describes.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The HMAC validator (`Utils::HmacValidator.validate`) computes the signature purely over whatever `to_signable_string` returns for a `VerifiableQuery`: [2](#0-1) 

Meanwhile, `Request#shop`, `Request#topic`, and `Request#webhook_id` are all read directly from HTTP headers (`shop-domain`, `topic`, `webhook-id`) that are never part of the signed payload: [3](#0-2) 

This differs from the OAuth callback flow, where `AuthQuery#to_signable_string` explicitly includes `shop`, `host`, `code`, `state`, and `timestamp` in the signed string, so the shop identity is cryptographically bound to the HMAC: [4](#0-3) 

For webhooks, only the body bytes are authenticated. The `shop`, `topic`, and `webhook_id` values used by the host application to route the payload and determine "which merchant this event belongs to" are not covered by the same guarantee — a valid `X-Shopify-Hmac-Sha256` value only proves the body was signed by Shopify (or the shared secret holder); it says nothing about which shop header should accompany that specific body.

### Impact Explanation
This matches the "field acted on but not covered by the HMAC" identity-binding failure class. If any component in the request path (e.g., a proxy, load balancer, logging layer, or an attacker with legitimate access to trigger cross-account replays via `X-Forwarded-*`-style header injection) allows headers to be modified independent of the body, or if the host application ever receives two different webhook deliveries where only headers differ, `Utils::HmacValidator.validate(request)` returns `true` for a mixed message consisting of Shop A's signed body paired with Shop B's `shop-domain` header. Applications trust `Request#shop` post-validation to select the tenant/session for processing (this is the documented purpose of the field per `webhook_handler.rb`/`registry.rb`), so this is a cross-tenant data confusion vector: a webhook payload validated as "authentic" can be attributed to the wrong shop.

### Likelihood Explanation
Exploitability depends entirely on whether an attacker can influence the `shop-domain`/`topic`/`webhook_id` headers of a request independently from the (Shopify-signed) body reaching the app's webhook endpoint — for example, via a misconfigured reverse proxy that lets client-supplied headers override or duplicate the `X-Shopify-Shop-Domain` header, or an app framework that picks up the wrong header instance when both `shopify-*` and `x-shopify-*` variants are present (the code accepts either name via `shopify_header`, at line 69, taking the first non-nil, order-dependent value). This is a real but conditional path: it requires a header-injection primitive at the network/framework boundary rather than a pure gem-only exploit, so likelihood is moderate rather than trivially always exploitable purely within this gem's code.

### Recommendation
Include `topic`, `shop`, and `webhook_id` in the signed material used to validate the webhook, or otherwise cryptographically bind the shop identity to the payload before trusting `Request#shop` for tenant routing (e.g., cross-check the header-derived `shop` against the shop encoded in `parsed_body`, or require the host application to independently authenticate the shop via a known, previously-registered webhook endpoint per shop rather than trusting the header value after only a body-HMAC check). At minimum, document that `Request#shop`/`#topic`/`#webhook_id` are unauthenticated headers not covered by the HMAC, so consuming applications know not to treat header-shop as verified identity without additional checks (e.g., matching against `parsed_body["myshopify_domain"]` where legitimate topics carry it).

### Proof of Concept
1. Construct a webhook request whose `raw_body` is a legitimately Shopify-signed payload for `shop-a.myshopify.com` (valid `X-Shopify-Hmac-Sha256` for that exact body).
2. At the layer sitting in front of the Ruby app (proxy/load balancer/duplicate-header handling), swap or duplicate `X-Shopify-Shop-Domain` to `shop-b.myshopify.com` while leaving the body and HMAC header untouched.
3. `ShopifyAPI::Webhooks::Request.new(raw_body:, headers:)` is constructed; `Utils::HmacValidator.validate(request)` succeeds because `to_signable_string` only checks `raw_body`. [1](#0-0) 
4. The host application, trusting `request.shop` (line 21-23) as the validated tenant, processes/attributes the webhook event to `shop-b.myshopify.com` instead of `shop-a.myshopify.com`, resulting in cross-tenant data confusion despite HMAC validation reporting success.
