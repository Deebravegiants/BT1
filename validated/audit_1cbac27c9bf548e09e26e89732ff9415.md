### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity by HMAC-verifying only the raw request body, then blindly trusts the `X-Shopify-Shop-Domain` header (unauthenticated) as the tenant identity that is handed to the app's webhook handler. This breaks the binding "shop attributed to the webhook == shop the HMAC actually authenticates."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read directly from the `shopify-shop-domain` / `x-shopify-shop-domain` header, with no cryptographic binding to the body or to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC of the body only, then forwards `request.shop` straight to the app's handler as trusted tenant identity: [3](#0-2) 

`HmacValidator.validate` / `validate_signature` compute the signature purely from `verifiable_query.to_signable_string` (i.e., the body for webhooks) using the app's single, shop-agnostic `Context.api_secret_key`: [4](#0-3) 

Because the HMAC key is the app's `client_secret`, not a per-shop secret, and the header carrying the shop identity is excluded from the signed content, the equality the gem implicitly claims — `shop delivered to handler == shop that produced/authorized this HMAC-signed payload` — does not actually hold. Any body+HMAC pair that is valid for the app (e.g., one legitimately generated for the attacker's own shop, since the attacker can install the app on a store they control and receive/inspect real webhook deliveries) remains HMAC-valid when replayed with the `X-Shopify-Shop-Domain` header rewritten to a different (victim) shop domain. `Registry.process` will accept it and dispatch it to the handler labeled with the victim's shop, since only the body — not the shop header — is authenticated.

### Impact Explanation
This is a cross-tenant data-confusion vector: an app that keys per-shop actions/storage off `WebhookMetadata#shop` (the documented, primary way to know "which shop is this webhook for") can be made to process, store, or act on attacker-supplied content while attributing it to an arbitrary victim shop domain, without possessing that shop's access token or any special privilege. This matches the "Critical – cross-tenant access" impact bar: the identity binding (`shop` header) that determines tenant scope is never covered by the cryptographic check that is meant to authenticate the request.

### Likelihood Explanation
Any developer/attacker can install the target app on their own (unprivileged) Shopify store, obtain genuine `{raw_body, hmac}` webhook deliveries signed by the app's `client_secret`, and replay them to the app's public webhook endpoint with the `X-Shopify-Shop-Domain` header swapped to any target shop. `Registry.process` performs no additional check that the header matches a shop the HMAC is scoped to (there is none — the secret is shared across shops), so the request passes validation as-is.

### Recommendation
Do not treat `Request#shop` as a trusted, authenticated identifier on its own. Either:
- Include the shop domain in the signable content used for HMAC verification, or
- Require the caller to cross-check `request.shop` against a shop for which the app already holds an active/known session before invoking the handler (i.e., resolve tenant identity via the app's own session store, not the raw header) and document/enforce this in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-controlled store `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the delivered `raw_body` and `X-Shopify-Hmac-Sha256` header — both are valid because they're signed with the app's shared `client_secret`.
2. Replay the exact same body/HMAC to the app's webhook endpoint, but set the header:
```
X-Shopify-Shop-Domain: victim-shop.myshopify.com
```
3. `ShopifyAPI::Webhooks::Registry.process` (lib/shopify_api/webhooks/registry.rb:188-200) calls `Utils::HmacValidator.validate(request)`, which only checks `@raw_body` against the HMAC — it passes. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the payload actually originated from the attacker's own shop. [5](#0-4)
