### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing tenant-identity spoofing on replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/utils/hmac_validator.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, then hands the handler a `shop` value that is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` HTTP header — a field that is never included in the signed payload.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery` and defines: [1](#0-0) 
so only `@raw_body` is signed. The `shop` accessor is read straight from the (unsigned) header: [2](#0-1) 

`Utils::HmacValidator.validate` verifies `verifiable_query.to_signable_string` against `verifiable_query.hmac`, which for `Request` means only the body is checked: [3](#0-2) 

`Registry.process` accepts the request once the HMAC check passes, and immediately forwards `request.shop` (the unsigned header) to the handler as the tenant identifier, alongside the signed body: [4](#0-3) 

The identity binding that should hold is: `shop header == shop that produced/authorized this HMAC`. In reality the code only proves `HMAC(secret, raw_body) == received_hmac`; it proves nothing about which shop the header claims to represent. Because the app's `api_secret_key` is shared across *all* shops that install the app (it is not a per-shop secret), any user who controls a shop with the app installed receives legitimately-signed webhooks for that shop and can capture a valid `(raw_body, hmac)` pair. That pair remains valid under `HmacValidator.validate` no matter what value is placed in the `shop-domain` header, because the header is not part of `to_signable_string`. Replaying the captured body/HMAC to the app's public webhook endpoint with the `shop-domain` header rewritten to a victim shop's domain passes signature validation and is delivered to the handler as `WebhookMetadata.new(... shop: request.shop ...)` labelled with the victim's shop.

### Impact Explanation
Handlers built on top of this gem are documented to rely on `WebhookMetadata#shop` to select the tenant context (e.g., look up that shop's session/access token, write to that shop's records). An attacker who is merely an ordinary merchant with the app installed on their own store can forge the tenant label on an otherwise validly-signed webhook and cause the host application to process attacker-controlled webhook content under a different, victim shop's identity — a cross-tenant data-integrity/isolation break driven entirely by this gem's incomplete signature scope.

### Likelihood Explanation
Requires only: (1) installing the target app on an attacker-controlled shop (or otherwise obtaining one legitimately-signed webhook body/HMAC pair, since bodies for many topics are predictable/attacker-influenceable, e.g. `orders/create` after placing an order), and (2) the ability to POST to the app's public webhook endpoint with a modified header — no access to `api_secret_key`, tokens, or the victim shop is needed. This is fully reachable through the gem's own public `Registry.process`/`Webhooks::Request` API exactly as documented.

### Recommendation
Do not treat `Request#shop` as authenticated. Either (a) bind the shop identity into the signed payload validation path (e.g., require callers to pass the expected/registered shop and compare it, not merely echo the header), or (b) clearly document in `to_signable_string`/`HmacValidator` that only the body is authenticated and that `shop`, `topic`, `api_version`, and `webhook_id` headers are attacker-controllable metadata that must be independently corroborated (e.g., against a per-shop webhook registration record) before being used for tenant routing.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook (e.g. creates an order), capturing the raw POST body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(api_secret_key, B)`.
2. Attacker sends a new POST to the app's webhook endpoint reusing body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this, `Utils::HmacValidator.validate` recomputes `HMAC-SHA256(api_secret_key, B)` and it matches `H` (header changes don't affect `to_signable_string`), so `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) does not raise `InvalidWebhookError`.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: parsed(B), ...)` and processes attacker-supplied content as if it originated from the victim shop.
