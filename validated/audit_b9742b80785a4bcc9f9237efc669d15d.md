### Title
Double-entry token aliasing lets an attacker mint shielded UTXO value for two `erc20TokenAddresses` entries that resolve to a single real balance - (File: `contracts/Hinkal.sol :: transact`)

### Finding Description

The invariant that should hold is:

`sum over i of (real ERC20/ETH value newly received by Hinkal for erc20TokenAddresses[i]) == sum over i of (amountChanges[i] credited to off-chain UTXOs) + sum over i of (on-chain UTXO amounts minted for i)`

`Hinkal.transact` enforces this **per index**, not against a single canonical asset ledger. It snapshots balances with `getBalancesForArray(circomData.erc20TokenAddresses)` before and after running the internal/external action [1](#0-0) , then for every index `i` computes `balanceDif = newBalances[i] - oldBalances[i]` and requires `balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount` [2](#0-1) . Each index's real-value check is fully independent of every other index — nothing ties `erc20TokenAddresses[i]` to a unique underlying asset. The check simply trusts `balanceOf` (or `address(this).balance`) as returned by whatever contract address the attacker supplied at that index, via `getERC20OrETHBalance` in `contracts/Transferer.sol` [3](#0-2) .

The zk circuit side does not close this gap either: `erc20TokenAddresses[i]` is fed as a raw, per-index public input in `formBasicInput` [4](#0-3) , and the circuit's `inTotal + amountChanges === outTotal` constraint is evaluated independently for each token slot — there is no constraint anywhere that two different addresses in the array must correspond to two distinct real balances. The circuit has no notion of "real balance" at all; it only cares that nullifier/commitment sums for a slot match `amountChanges[slot]`, and the slot's identity is whatever address the prover (the attacker) chose to bind into the proof.

**Exploit path:** The attacker deploys a "double-entry" token pair `A` and `B` — two distinct contract addresses that both read/write a single shared balance ledger (e.g., both `balanceOf`/`transfer` delegate to one common storage contract). The attacker then:
1. Crafts `circomData.erc20TokenAddresses = [inputToken, A, B]`, with `A` set as the real LI.FI swap output token and `B` as the pure alias, and generates a legitimate proof (they fully control their own UTXO generation) that satisfies the circuit's per-index sum constraints for both `A` and `B`, each crediting an off-chain UTXO of value `V`.
2. Calls `Hinkal.transact` with `externalActionData.externalActionId` pointing at `LifiExternalAction`. `ExternalActionSwap.swap` executes the router call and transfers the swapped output (`outputToken = A`) back to Hinkal via `transferERC20TokenOrETH` [5](#0-4) . Because `A` and `B` share the same underlying ledger, this single real transfer of `V` tokens is reflected in `balanceOf(Hinkal)` for **both** `A` and `B`.
3. Back in `Hinkal.transact`, the loop sees `balanceDif[A] == V` and `balanceDif[B] == V`. `utxoSet` returned by `swap()` contains only one UTXO entry keyed to `outputToken = A` [6](#0-5) , so for index `B`, `utxoAmount = 0` and the check reduces to `balanceDif[B] == amountChanges[B]`, which the attacker satisfies by setting `amountChanges[B] = V` and having minted a matching off-chain commitment for token `B` in the proof.
4. Both checks pass. The vault has only received `V` real tokens once, but the transaction mints shielded UTXO value of `V` for token `A` **and** `V` for token `B` — `2V` of shielded claims backed by `V` of real assets.

**Why existing guards fail:** `performHinkalChecks`, `verifyProof`, `rootHashExists`, `insertNullifiers`, `onlyAllowedRecipient`, and `nonReentrant` all operate correctly and are not bypassed — none of them validate that distinct entries of `erc20TokenAddresses` correspond to distinct real assets. The slippage/balance equality check in `Hinkal.transact` is the only place doing real-value reconciliation, and it is index-scoped, so aliasing at the ERC20 layer defeats it entirely. This does not require reusing a stale proof with mutated calldata — the attacker generates one fresh, fully valid proof for the malicious index set; the vulnerability is a fundamental structural gap (no canonical/deduplicated asset model), not a proof-binding bypass.

### Impact Explanation

This lets an unprivileged attacker mint shielded UTXO value with only partial real backing, i.e., protocol insolvency: shielded claims outstanding exceed the vault's actual token holdings. The excess "phantom" UTXO (denominated in token `B`) can only be redeemed for real value later if/when other users deposit real balance into the same shared ledger (via token `A` or `B`), at which point the attacker's withdrawal effectively drains funds meant for other depositors. This is repeatable per swap call and scales with `V`, matching the Critical category "minting shielded value without backing (protocol insolvency)."

### Likelihood Explanation

Preconditions: the attacker must (a) deploy a custom token contract pair with shared underlying storage exposed at two addresses (fully within attacker capability, no privilege needed), (b) get that token whitelisted/usable as `erc20TokenAddresses` entries and as a LI.FI swap output (no on-chain allowlist for `erc20TokenAddresses` values was found), and (c) generate a valid proof themselves for their own UTXOs. All of this is achievable by an unprivileged EOA per the stated threat model. The attack is cheap (one swap transaction, no exotic griefing), and repeatable across multiple transactions to compound insolvency.

### Recommendation

Deduplicate and canonicalize `erc20TokenAddresses` accounting so real balance changes are attributed to unique underlying assets, not the caller-supplied address list. Options: (1) maintain balances keyed by a whitelisted/canonical token registry rather than raw `balanceOf` snapshots per array slot; (2) require `erc20TokenAddresses` to be strictly increasing/sorted and unique, and additionally verify tokens against an owner-curated allowlist so attacker-deployed aliasing tokens cannot be used at all; (3) bind the aggregate real balance delta to the aggregate `amountChanges + utxoAmount` sum only when token identity is provably unique (e.g., compare against `EXTCODEHASH`/registry entries), preventing two list entries from silently sharing one economic balance.

### Proof of Concept

Foundry test plan:
1. Deploy `SharedLedger` contract holding a `mapping(address=>uint256) balances`.
2. Deploy `TokenA` and `TokenB`, both ERC20-compatible facades whose `balanceOf`/`transfer`/`transferFrom` delegate to `SharedLedger`.
3. Deploy Hinkal stack (mocked verifier/circuit) and `LifiExternalAction` with a mock router that, on `callRouter`, mints/transfers `V` `TokenA` tokens to `msg.sender` (simulating swap output) by crediting `SharedLedger`.
4. Construct `circomData` with `erc20TokenAddresses = [inputToken, TokenA, TokenB]`, `amountChanges = [-inputAmount, V, V]`, matching nullifiers/commitments that satisfy the (mocked) verifier for both token slots.
5. Call `Hinkal.transact(...)`.
6. Assert: `TokenA.balanceOf(hinkal) - oldBalanceA == V` and `TokenB.balanceOf(hinkal) - oldBalanceB == V` (both true due to shared ledger) even though `SharedLedger` total credited is only `V`.
7. Assert total minted shielded UTXO value for tokens A+B == `2V` while `SharedLedger.balances[hinkal] == V`, demonstrating `sum(amountChanges bound to real balance) > actual real value received`, i.e., the claimed equality `balanceDif == amountChanges[i] + utxoAmount` holds per-index but the aggregate invariant `real value in == total shielded value minted` is broken.

    function getERC20OrETHBalance(
        address _erc20TokenAddress
    ) internal view returns (uint256) {
        if (_erc20TokenAddress == address(0)) {
            return address(this).balance;
        } else {
            IERC20 outToken = IERC20(_erc20TokenAddress);
            return outToken.balanceOf(address(this));
        }
    }

    function getBalancesForArrayMemory(
        address[] memory erc20TokenAddresses

            balances[i] = getERC20OrETHBalance(erc20TokenAddresses[i]);
