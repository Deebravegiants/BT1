### Title
Webhook shop-domain (tenant) is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` treats a webhook request as authenticated for a specific shop once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC signature only covers the raw request body — it never covers the `shop-domain` (or `topic`/`webhook-id`) header that is later trusted as the tenant identifier passed to the app's handler.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Utils::HmacValidator.validate` computes and compares the HMAC purely over that signable string (the body), using the app's shared `api_secret_key`: [2](#0-1) 

`Registry.process` gates on this HMAC check, then immediately builds `WebhookMetadata` using `request.shop`, which is read straight from the unauthenticated `shop-domain`/`x-shopify-shop-domain` header: [3](#0-2) [4](#0-3) 

The `api_secret_key` is a single shared secret for the whole app (not per-shop), so the same `(body, hmac)` pair is valid for every shop that has this app installed. Any merchant who installs the app — including on a free/dev store they control — legitimately receives real webhook deliveries with a valid `(raw_body, hmac)` pair signed with the app's `api_secret_key`. Because the `shop-domain` header is excluded from the signed bytes, that attacker can replay the exact same body/HMAC to the app's webhook endpoint while substituting the `shop-domain` header for a victim shop. `HmacValidator.validate` still passes (it only checks the body against the same shared secret), and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the victim's domain — the equality the app relies on, "the shop authenticated by the HMAC == the shop the handler acts on," does not hold, since the shop field is never part of the signed content in the first place.

This directly matches the analog bug class: an identity/tenant-binding field (`shop`) is acted upon by the handler but is not covered by the cryptographic check (HMAC) that is supposed to establish trust in the request — structurally the same class of bug as the NEAR contract fetching `chain` from an offset outside the verified/intended region.

The library's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," implying the tenant/shop attribution is trustworthy once HMAC passes, which is not actually true given the implementation: [5](#0-4) 

### Impact Explanation
This allows an unprivileged internet user (any merchant who can install the target app on their own store, which is the normal, unprivileged installation flow for a public app) to make the host application process attacker-controlled webhook bodies while impersonating an arbitrary victim shop domain of their choosing. Since webhook handlers in host apps (as shown in the gem's own example) key store lookups and business logic off `data.shop`, this enables cross-tenant data confusion/corruption for any consuming application that trusts the `shop` field from `WebhookMetadata` — a cross-tenant access impact.

### Likelihood Explanation
Reaching this only requires standard, unprivileged use of the app-installation flow (install app on attacker's own store, capture a legitimate webhook delivery) and then sending a crafted HTTP POST to the app's public webhook endpoint with a swapped header — no leaked credentials, TLS interception, or privileged access is needed.

### Recommendation
Bind the tenant/shop identity into the HMAC-verified content, or otherwise cryptographically tie the `shop-domain` header to the signed payload before it is used for handler dispatch. At minimum, `to_signable_string` (or a new signable representation) should incorporate the `shop-domain` and `topic` headers so a replay against a different shop fails HMAC validation. Alternatively, cross-check the shop against a known/registered shop list before dispatching to the handler.

### Proof of Concept
1. App A is installed on `attacker.myshopify.com` (attacker's own store) with the app's real `api_secret_key`.
2. Shopify sends a legitimate webhook to the app: body `B`, header `x-shopify-hmac-sha256: H` (valid HMAC of `B` with `api_secret_key`), header `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker replays this exact request to the app's public webhook endpoint but changes the header to `x-shopify-shop-domain: victim.myshopify.com`, keeping body `B` and hmac `H` unchanged.
4. `Utils::HmacValidator.validate` recomputes HMAC over `B` only (per `to_signable_string`) — the check succeeds because `B`/`H` are unchanged. [6](#0-5) 
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, and the host app processes/stores data as if it legitimately came from `victim.myshopify.com`. [7](#0-6)

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
