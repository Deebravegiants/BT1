### Title
Unbounded router allowance + attacker-controlled swap calldata lets a caller sweep stranded/refunded input tokens from `ExternalActionSwap` and mint them as their own output UTXO - (File: contracts/external-actions/swaps/ExternalActionSwap.sol, contracts/external-actions/swaps/LifiExternalAction.sol)

### Summary
`LifiExternalAction.callRouter` grants the LI.FI `router` an **unlimited** ERC-20 allowance via `approveUnlimited` and then executes fully attacker-supplied `externalActionMetadata` calldata against that router. [1](#0-0)  Because the amount the router actually pulls is encoded inside that attacker-controlled calldata rather than being constrained on-chain to `inputAmount`, and `swappedAmount` is measured only as the output-token balance delta over the call [2](#0-1) , any input token that has become stranded on the action contract (e.g., from a prior LI.FI partial refund that returns leftover input to the calling contract instead of the depositing user, since `swap()` never sweeps or returns `inputToken`, only `outputToken`) can be pulled into the swap and its resulting output captured by whoever triggers the next swap transaction.

### Finding Description
The broken equality: **"tokens leaving the action contract in tx T == -deltaAmountChanges Hinkal sent it in tx T."** In practice, the action contract's balance sourced into a swap is not bounded to what Hinkal transferred it this transaction; it is bounded only by whatever the router's unconstrained calldata decides to pull, up to `type(uint256).max` allowance.

Path:
1. `Hinkal.transact` → `_externalTransact` transfers `-deltaAmountChanges[i]` (i.e. `inputAmount`) of `inputToken` to the external action address, then calls `runAction`. [3](#0-2) 
2. `ExternalActionSwap.swap` computes `inputAmount = uint256(-deltaAmounts[0])` and calls `callRouter(inputToken, inputAmount, outputToken, externalActionMetadata)` — note `inputAmount` is never actually passed into or checked against the router call itself. [4](#0-3) 
3. `LifiExternalAction.callRouter` calls `approveUnlimited(inputToken, router)` (granting `type(uint256).max` allowance if not already large) and then `router.call(externalActionMetadata)` with metadata fully controlled by the attacker (per the rules, attacker controls `externalActionMetadata`). [2](#0-1) [5](#0-4) 
4. `swappedAmount` is computed purely as `getERC20OrETHBalance(outputToken) after - before`, i.e. it faithfully reports whatever came out of the router call, with no check that the *input* side consumed only `inputAmount`.
5. Back in `swap()`, the entire `swappedAmount` (minus fees) is forwarded to `msg.sender` (Hinkal) and wrapped into a fresh `UTXO` for the caller's `stealthAddressStructure`. [6](#0-5) 
6. Back in `Hinkal.transact`, the balance-diff / slippage checks only verify that Hinkal's own balance change equals `amountChanges[i] + utxoAmount` for the tokens it tracked — since the attacker's own zk proof freely sets `amountChanges`/UTXO amount to match whatever output they actually received, this check is trivially satisfied even though the extra value came from residual/stranded tokens belonging to no one in this transaction. [7](#0-6) 

Root cause: the action never enforces "amount pulled from this contract by the router == amount transferred to it this tx." An unlimited allowance plus arbitrary attacker calldata to a fixed but complex multi-facet router (LI.FI diamond) allows the attacker to encode a swap whose `fromAmount` exceeds what Hinkal actually funded, consuming any pre-existing balance of `inputToken` sitting in the action (whether from a partial/leftover refund of a previous swap, dust, or any other means by which token accumulates on that contract). None of `performHinkalChecks`, `verifyProof`, `rootHashExists`, or the balance/slippage requires in `Hinkal.transact` catch this, because they only reconcile Hinkal's own balance against the attacker's own self-consistent proof — they have no visibility into, or constraint on, the internal balance state of the external action contract.

### Impact Explanation
An unprivileged attacker can capture value that another party's transaction left stranded in the shared `ExternalActionSwap`/`LifiExternalAction` contract, converting it into their own shielded UTXO output — direct theft of in-flight/stranded protocol funds that were never counted against the attacker's own deposit. This matches "Critical: direct theft of shielded or in-flight user funds." The action is repeatable any time residual balance accumulates on the action contract (e.g., after any LI.FI swap that refunds unused input back to the contract rather than to the depositor).

### Likelihood Explanation
Preconditions: (1) the action contract must hold a stranded `inputToken` balance (plausible given LI.FI's own refund behavior for partial fills/leftover input, and the fact that `swap()` never sweeps or returns unused `inputToken`), and (2) the attacker must be able to craft LI.FI router calldata specifying a `fromAmount` larger than what they themselves funded via their deposit. Both are within the stated attacker capabilities (crafting `externalActionMetadata`, choosing `erc20TokenAddresses` ordering and `amountChanges`). Cost is limited to gas plus the minimal legitimate deposit needed to pass `slippageValues`/`swap output slippage floor` checks; the attacker does not need any privileged role.

### Recommendation
- Do not grant unlimited, persistent allowance to the router; approve exactly `inputAmount` before the call and reset to zero after, so the router can never pull more than what Hinkal transferred this transaction.
- Enforce on-chain that the router's actual pull of `inputToken` equals `inputAmount` (e.g., check `getERC20OrETHBalance(inputToken)` before/after the router call and require the decrease equals `inputAmount`), rejecting any excess consumption.
- Sweep/refund any leftover `inputToken` (and `outputToken`) balance back to the appropriate party at the end of each `swap()` call instead of allowing it to persist on the action contract between transactions.

### Proof of Concept
Foundry plan:
1. Deploy `Hinkal`, `LifiExternalAction` (with a mock LI.FI router), and seed a "victim" transaction that leaves a stranded `inputToken` balance on `LifiExternalAction` (simulate the router refunding excess input back to `LifiExternalAction` instead of forwarding it out, e.g. mock router partially swaps and returns leftover `inputToken`).
2. Assert `IERC20(inputToken).balanceOf(lifiAction) > 0` (residual captured).
3. As an unprivileged attacker, deposit a small amount of `inputToken`/generate a valid Hinkal proof for a swap using `erc20TokenAddresses = [inputToken, outputToken]`, `deltaAmountChanges[0] = -smallInputAmount`.
4. Craft `externalActionMetadata` for the mock router specifying `fromAmount = smallInputAmount + residualAmount` (pulling both the freshly transferred and stranded balance via the unlimited allowance).
5. Call `Hinkal.transact(...)`.
6. Assert: `swappedAmount` (and thus the attacker's minted UTXO amount) reflects the full residual + own-input swap, i.e., value leaving the action in this tx `>` `-deltaAmountChanges` Hinkal sent it this tx — violating the target invariant — and that `IERC20(inputToken).balanceOf(lifiAction)` drops to (near) zero while the attacker's new UTXO commitment encodes the inflated `outputToken` amount.

    function callRouter(
        address inputToken,
        uint256 inputAmount,
        address outputToken,
        bytes calldata externalActionMetadata
    ) internal override returns (uint256 swappedAmount) {
        uint256 balanceBefore = getERC20OrETHBalance(outputToken);

        if (inputToken == address(0)) {
            (bool success, ) = router.call{value: inputAmount}(
                externalActionMetadata
            );
            require(success, "LI.FI swap failed: native coin");
        } else {
            approveUnlimited(inputToken, router);
            (bool success, ) = router.call(externalActionMetadata);
            require(success, "LI.FI swap failed: erc-20 token");
        }

        swappedAmount = getERC20OrETHBalance(outputToken) - balanceBefore;
    }

    function swap(
        CircomData calldata circomData,
        int256[] calldata deltaAmounts
    ) internal returns (UTXO[] memory utxoSet) {
        address inputToken = circomData.erc20TokenAddresses[0];
        uint256 inputAmount = uint256(-deltaAmounts[0]);

        if (inputToken == circomData.feeStructure.feeToken) {
            inputAmount -= circomData.feeStructure.flatFee;
        }

        address outputToken = circomData.erc20TokenAddresses[1];

        require(
            circomData.slippageValues[1] != 0,
            "swap output slippage floor not set"
        );

        require(
            block.timestamp <= circomData.timeStamp + SWAP_DEADLINE_WINDOW,
            "swap expired"
        );

        uint256 swappedAmount = callRouter(
            inputToken,
            inputAmount,
            outputToken,
            circomData.externalActionData.externalActionMetadata
        );
