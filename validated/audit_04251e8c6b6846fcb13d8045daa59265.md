### Title
Webhook `shop` identity used by app handlers is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` authenticates only the raw HTTP body via HMAC, but exposes an unauthenticated `shop` (tenant identity) accessor that `ShopifyAPI::Webhooks::Registry.process` passes straight into the handler as the trusted tenant identifier.

### Finding Description
`Registry.process` validates a webhook request purely by checking `Utils::HmacValidator.validate(request)` and then forwards `request.shop` to the app's handler as the authoritative shop identity: [1](#0-0) 

`Request#to_signable_string`, which is the data actually covered by the HMAC, returns only `@raw_body` — it does **not** include the `shop`, `topic`, `webhook_id`, or `api_version` headers: [2](#0-1) 

Meanwhile, `Request#shop` simply reads the `x-shopify-shop-domain` (or `shopify-shop-domain`) HTTP header, which is attacker-controlled input on any public webhook endpoint: [3](#0-2) 

`HmacValidator.validate` computes the signature exclusively over `verifiable_query.to_signable_string` (the raw body) using the shared `api_secret_key`: [4](#0-3) 

This is the same bug class the external ERC report flags for `IAggregator`/`validateUserOpSignature`: a field that is *acted on* by the caller (here, the `shop` value used to attribute the webhook to a merchant) is not *covered* by the cryptographic check that is supposed to authenticate the message. The identity binding the gem implicitly relies on — `shop_claimed_in_header == shop_that_the_HMAC_actually_authenticates` — does not hold, because the HMAC authenticates only the body bytes, never the header.

### Impact Explanation
Any user who can install the app on their own store (a normal, unprivileged action) can trigger a real webhook delivery to the app and thereby obtain a body + `shopify-hmac-sha256` pair that is valid under the app's single shared `client_secret`. Because the signature does not bind the `shop` header, that same valid `(body, hmac)` pair can be replayed to the app's public webhook endpoint with the `x-shopify-shop-domain` header swapped to a victim shop's domain. `Registry.process` will pass HMAC validation and hand the handler a `WebhookMetadata` object whose `shop` field is the forged victim domain, while `body`/`topic`/`webhook_id` are still the attacker's own legitimate webhook data. Any app logic that trusts `WebhookMetadata#shop` as the tenant key (e.g., to look up per-shop settings, credentials, or to route stored data) can be tricked into associating attacker-controlled data with a different shop — a cross-tenant data-integrity/attribution break. This falls under the Critical category ("cross-tenant access") since no `api_secret_key`, access token, or leaked credential is required — only a normal app install by the attacker on their own shop.

### Likelihood Explanation
Likely exploitable by any unprivileged internet user who can install the target app (public apps allow free installation), which routinely happens for any Shopify app that offers a free/dev store install. No secret material, TLS interception, or privileged account is required — the attacker only needs to capture their own legitimate webhook traffic and replay it with a different `shop` header value against the app's public webhook endpoint.

### Recommendation
Bind the `shop` header (and ideally `topic`/`webhook_id`/`api_version`) into the value authenticated by the HMAC — e.g., by having `to_signable_string` incorporate the shop-domain header (matching how `AuthQuery#to_signable_string` binds `shop`), or by having consuming applications independently re-verify that the delivered `shop` corresponds to a shop that currently has this webhook subscription/app installation before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering a real webhook (e.g. `orders/create`) to the app's public webhook endpoint. They capture the exact raw request body `B` and the valid `shopify-hmac-sha256` header `H` (computed by Shopify using the app's shared `client_secret`).
2. Attacker replays an HTTP POST to the same public webhook endpoint with body `B` and header `shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H...})` is constructed by the host app from this request.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `request.to_signable_string` (`== B`) — this matches `H`, so validation **passes**.
5. The handler receives `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, attributing attacker-controlled webhook data to `victim-shop.myshopify.com` despite it never having sent this webhook — demonstrating the tenant-identity binding is not enforced by the signature.
