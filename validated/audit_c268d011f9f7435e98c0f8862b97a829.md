### Title
Fee-on-transfer / deflationary TRC20 tokens can permanently brick escrow withdrawal in Tron IntentGatewayV2 - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of `IntentGatewayV2.placeOrder()` credits the escrow ledger `_orders[commitment][token]` with the user-specified (fee-reduced-only-by-protocol-fee) amount instead of the amount actually received by the contract, unlike the mainline EVM `IntentGatewayV2.sol`, which measures actual balance deltas specifically to defend against fee-on-transfer tokens. If a deflationary/fee-on-transfer TRC20 token is used as an order input, the escrow accounting overstates the gateway's real token balance, and any subsequent `withdraw()` call (fill settlement or cancellation refund) will attempt to transfer more tokens than the contract actually holds, reverting and permanently freezing the escrowed input.

### Finding Description
In the non-predispatch branch of `placeOrder`, tokens are pulled via `safeTransferFrom` and the escrow mapping is incremented by the pre-computed `reducedInputs[i].amount` (order amount minus protocol fee) without verifying that this amount was actually received by the contract: [1](#0-0) 

Contrast this with the corresponding logic in the mainline (non-Tron) `IntentGatewayV2.sol`, which explicitly snapshots balance before and after the transfer and mutates `order.inputs[i].amount` to the actual delta, precisely to account for fee-on-transfer tokens: [2](#0-1) 

The predispatch branch of the Tron contract does compute a `dust` value from `balance - requiredAmount`, but this only accounts for the CallDispatcher-to-gateway leg; it still stores `reducedInputs[i].amount` (the originally intended amount) into escrow rather than the amount the *user's* initial `safeTransferFrom` into the dispatcher actually delivered when the input token itself is fee-on-transfer: [3](#0-2) 

When the order is later settled — either via cross-chain `onAccept` -> `withdraw()` or an equivalent same-chain fill/cancel path — the contract attempts to transfer the full recorded escrow amount to the beneficiary using a raw low-level call, decrementing `_orders[commitment][token]` by the same (overstated) amount: [4](#0-3) 

Because the contract's actual TRC20 balance for that token is strictly less than the sum of amounts recorded in `_orders`, the `token.call(...)` transfer will fail once the shortfall is reached, causing `withdraw()` to revert with `TransferFailed()`. Since `withdraw()` is the single code path used for both normal settlement (`RedeemEscrow`) and refund (`RefundEscrow`/cancellation), there is no way to ever release the escrowed balance for that commitment — the funds are permanently stuck.

### Impact Explanation
Any unprivileged user can place an order on the Tron `IntentGateway` using a fee-on-transfer TRC20 token as an input (TRON has numerous tax/deflationary TRC20 tokens). The resulting order's escrow bookkeeping will be inflated above the gateway's real token balance for that token. When a solver fills the order (or the user/anyone cancels it after deadline), the settlement message triggers `withdraw()`, which will revert due to insufficient actual balance versus the recorded escrow amount. This permanently freezes: (a) the user's escrowed input tokens (never refundable), and (b) blocks the solver from ever claiming input tokens they filled the order for, since the transfer that decrements `_orders` and pays the beneficiary can never succeed. This is a direct, unprivileged, permanent loss/freezing of user funds routed through Hyperbridge's IntentGateway — reachable purely by placing a single order.

### Likelihood Explanation
Likelihood is high on any TRON deployment because: (1) fee-on-transfer / tax tokens are common on TRON, (2) no allowlist prevents using such tokens as inputs, (3) the vulnerable code path (non-predispatch, direct `safeTransferFrom`) is the default/simplest order flow, and (4) the mainline EVM contract's test suite explicitly demonstrates the team is aware of and defends against this exact class of bug elsewhere, confirming the Tron contract is missing that mitigation.

### Recommendation
Mirror the fix already present in `evm/src/apps/IntentGatewayV2.sol`: measure the gateway's actual token balance before and after each `safeTransferFrom` call and use the measured delta (not the nominal `order.inputs[i].amount`) when computing `reducedInputs`/crediting `_orders[commitment][token]`. Apply the same balance-delta correction to the predispatch branch so that fee-on-transfer effects incurred on the *first* leg (user → CallDispatcher) are also captured, not just the CallDispatcher → gateway leg.

### Proof of Concept
1. Deploy a deflationary TRC20 token `FOT` with e.g. a 1% transfer fee (burned or redirected on every `transfer`/`transferFrom`), mirroring the `FeeOnTransferToken` mock already used in the EVM test-suite: [5](#0-4) 
2. User approves `IntentGatewayV2` (Tron) for `1000e18 FOT` and calls `placeOrder` with `inputs = [{token: FOT, amount: 1000e18}]` (no predispatch, no protocol fee for simplicity).
3. `safeTransferFrom` moves tokens; due to the 1% fee, the gateway's actual `FOT` balance increases by only `990e18`, but `_orders[commitment][FOT]` is set to `1000e18` (the full `reducedInputs[i].amount`): [6](#0-5) 
4. Order is filled/cancelled, triggering `withdraw()` with `body.tokens[i].amount = 1000e18` for `FOT`.
5. `withdraw()` attempts `token.call(transfer.selector, beneficiary, 1000e18)`, but the gateway only holds `990e18` — the transfer returns `false`/reverts, and `withdraw()` reverts with `TransferFailed()`: [7](#0-6) 
6. Every future attempt to settle or refund this commitment reverts identically — the escrowed `FOT` is permanently locked in the contract.

contract FeeOnTransferToken {
    string public name = "FeeOnTransferToken";
    string public symbol = "FOT";
    uint8 public decimals = 18;
    uint256 public totalSupply;
    uint256 public feeBps;

    mapping(address => uint256) public balanceOf;
    mapping(address => mapping(address => uint256)) public allowance;

    constructor(uint256 _feeBps) {
        feeBps = _feeBps;
    }

    function mint(address to, uint256 amount) external {
        balanceOf[to] += amount;
        totalSupply += amount;
    }

    function approve(address spender, uint256 amount) external returns (bool) {
        allowance[msg.sender][spender] = amount;
        return true;
    }

    function transfer(address to, uint256 amount) external returns (bool) {
        return _transfer(msg.sender, to, amount);
    }

    function transferFrom(address from, address to, uint256 amount) external returns (bool) {
        uint256 allowed = allowance[from][msg.sender];
        if (allowed != type(uint256).max) {
            allowance[from][msg.sender] = allowed - amount;
        }
        return _transfer(from, to, amount);
    }

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }
}
