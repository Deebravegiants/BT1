Confirmed: `Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , while `shop`, `topic`, `api_version`, and `webhook_id` are all pulled directly from unauthenticated HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) that are never fed into the HMAC computation [2](#0-1) . `Registry.process` only validates that the raw body's HMAC matches, then dispatches the handler using the header-derived `shop` value [3](#0-2) .

### Title
Webhook shop identity spoofing via unauthenticated header — `shop` not covered by HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) that is passed to the app's `WebhookHandler` exclusively from the `X-Shopify-Shop-Domain` HTTP header, while `HmacValidator.validate` only authenticates the raw request body via `to_signable_string`. The header is never part of the signed material, so the cryptographic proof of authenticity (that Shopify — the holder of `api_secret_key` — sent this payload) does not extend to the `shop` value the handler trusts to select which merchant's data to act on.

### Finding Description
`Utils::HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest` over `verifiable_query.to_signable_string` and compares it against the `hmac` field using `OpenSSL.secure_compare` [4](#0-3) . For webhook requests, `to_signable_string` returns only `@raw_body` [1](#0-0) ; the `shop`, `topic`, `webhook_id`, and `api_version` accessors instead read straight from HTTP headers with no cryptographic binding to that signature [2](#0-1) . `Registry.process` calls `HmacValidator.validate(request)` and, once it passes, dispatches to the registered handler passing `request.shop` and `request.parsed_body` untouched [3](#0-2) .

This breaks the identity binding: `shop header == authenticated tenant` does not hold. The equality that should be enforced is `HMAC(secret, signed_bytes)` covering `shop`, but instead only `raw_body` is covered — `signed_bytes ⊉ {shop}`. Anyone who possesses one genuinely-signed webhook body/HMAC pair for a topic (e.g., from their own shop, which they legitimately control and receive real webhooks for) can replay that exact `(body, hmac)` pair to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a different, victim tenant. The HMAC check still passes (it only checks the body), and the handler executes with `shop` set to the attacker-chosen victim domain.

### Impact Explanation
This crosses a tenant boundary using only material an unprivileged app user already legitimately possesses (their own valid webhook deliveries), yielding cross-tenant data confusion: the app's webhook handler will process a body intended for the attacker's shop as if it originated from the victim shop. Depending on how the host app persists/keys data from `WebhookMetadata#shop` (e.g., orders/customers/redact handling, GDPR `customers/data_request` / `shop/redact` processing), this can lead to cross-tenant data corruption or disclosure keyed to the wrong merchant, satisfying the "cross-tenant access" criterion.

### Likelihood Explanation
Requires only that the attacker operate one Shopify store with the app installed (a normal, unprivileged relationship) and be able to POST arbitrary headers to the app's public webhook receiving endpoint. No access to `api_secret_key` or any merchant's access token is needed — only a previously-received, genuinely-HMAC-signed body/signature pair replayed with a substituted shop header.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the signable string used for HMAC verification, or otherwise cryptographically bind the shop identity to the signed payload before it is trusted by handlers, mirroring how the OAuth `AuthQuery` binds `shop` into `to_signable_string` [5](#0-4) .

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and receives a legitimate webhook delivery for topic `orders/create`, capturing the raw body `B` and its valid `X-Shopify-Hmac-SHA256` header `H` (computed by Shopify over `B` with the app's `api_secret_key`).
2. Attacker sends a POST to the app's webhook endpoint with the same raw body `B`, the same header `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `Request.new(raw_body: B, headers: {...})` builds a request where `hmac` reproduces `H` and `to_signable_string` returns `B`; `HmacValidator.validate` passes because it only checks `B` against `H` [6](#0-5) .
4. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed body of B, ...)` [3](#0-2) , causing the app to process attacker-controlled webhook content under the victim's tenant identity.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
