### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) header fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so the HMAC signature validated by `Utils::HmacValidator.validate` covers exclusively the JSON body. All identity-bearing fields — most importantly `shop` (via the `x-shopify-shop-domain`/`shopify-shop-domain` header) — are read straight from unauthenticated HTTP headers and passed on, unverified, as the tenant identifier that host applications use to route/attribute the webhook.

### Finding Description
`Request#hmac` and `Request#to_signable_string` are defined as: [1](#0-0) [2](#0-1) 

`shop`, `topic`, `api_version`, and `webhook_id` are all pulled directly from request headers with no cryptographic binding to the body: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` compute the signature purely from `verifiable_query.to_signable_string`, i.e., only the body: [4](#0-3) 

`Registry.process` accepts the request once the (body-only) HMAC validates, and then constructs `WebhookMetadata` using the unauthenticated `request.shop` header value, which is handed to the app's handler as the trusted tenant identifier: [5](#0-4) [6](#0-5) 

The binding that is broken is: **`shop` field acted on by the handler == `shop` field authenticated by the HMAC**. In reality: `shop` header value (untrusted, attacker-controlled) is used as the tenant key, while the HMAC only authenticates the JSON body bytes. Documentation explicitly tells app authors to use `data.shop` as the shop/tenant identifier for downstream processing (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)`): [7](#0-6) 

Because a public app's webhook HMAC secret (`Context.api_secret_key`) is shared across every installing shop (it is the app's client secret, not a per-shop secret), any unprivileged developer can install their own app instance on a free/dev Shopify store, receive a legitimately signed webhook (`body`, `hmac`) pair for their own shop, and then replay that exact `(body, hmac)` pair to the victim app's webhook endpoint while substituting the `x-shopify-shop-domain` (or `shopify-shop-domain`) header with an arbitrary victim shop domain. `HmacValidator.validate` will still pass because it never inspects the header, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This breaks the tenant/shop authentication boundary that the gem is expected to preserve for the host application: the `shop` value that Shopify apps rely on to scope database writes, trigger per-tenant business logic, or fan out follow-up API calls, can be forged by any attacker with legitimate access to at least one shop (their own free/dev shop). This enables cross-tenant data injection — fabricated order/product/customer events can be attributed to a different, real merchant’s shop, potentially poisoning that merchant’s app-side state or triggering unwanted actions "on behalf of" that shop. This matches the Critical impact category of cross-tenant access.

### Likelihood Explanation
Likelihood is high for any public app: exploitation requires only (1) installing the app on any shop the attacker controls (trivial and free via Shopify dev stores) to legitimately obtain a `(body, hmac)` pair, and (2) sending a forged HTTP POST to the app’s public webhook URL with a substituted shop-domain header. No access token, `client_secret`, or privileged account is needed — the attacker only ever uses their own legitimately-issued webhook deliveries and the public webhook endpoint.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) values in the data that is HMAC-verified, or otherwise cryptographically bind them to the body before trusting them, e.g. by having the host application cross-check `request.shop` against a session/shop record it already trusts (not the header alone), or by having `Utils::HmacValidator`/`Request#to_signable_string` incorporate the shop header into the signable string when validating webhook requests. At minimum, document that `data.shop` on webhook processing is not authenticated by the HMAC and must be independently verified (e.g., against a list of shops that have this app installed) before being used for tenant-scoped actions.

### Proof of Concept
1. Attacker installs the target public app on their own (attacker-controlled) Shopify dev store `attacker-shop.myshopify.com`, and lets Shopify deliver a legitimate webhook, e.g. `orders/create`, capturing the raw body `B` and the `x-shopify-hmac-sha256` header `H` (computed by Shopify over `B` using the app's shared `api_secret_key`).
2. Attacker sends their own POST to the victim app's webhook endpoint:
   ```
   POST /webhooks HTTP/1.1
   x-shopify-topic: orders/create
   x-shopify-hmac-sha256: H
   x-shopify-shop-domain: victim-shop.myshopify.com
   x-shopify-webhook-id: <any>
   x-shopify-api-version: <any>

   B
   ```
3. `ShopifyAPI::Webhooks::Request.new` parses this successfully; `Utils::HmacValidator.validate` recomputes HMAC over `B` only (`Request#to_signable_string` at `lib/shopify_api/webhooks/request.rb:35-38`) and it matches `H`, so validation passes.
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the actual signer/owner of this payload was `attacker-shop.myshopify.com`. The host app now processes attacker-controlled webhook data as if it originated from the victim shop.
