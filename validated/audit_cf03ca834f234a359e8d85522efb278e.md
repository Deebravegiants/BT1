This confirms the documented, intended usage: the docs explicitly state `Registry.process` "will verify the request did indeed come from Shopify" (`docs/usage/webhooks.md` lines 125), and the handler receives `data.shop` as an authoritative tenant identifier for downstream actions (docs example: `perform_later(topic: data.topic, shop_domain: data.shop, ...)`). This confirms the `shop` field is treated as verified/authoritative by design, while the actual code only signs the raw body.

### Title
Webhook `shop-domain` (and `topic`/`webhook-id`/`api-version`) headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body. The `shop` (and `topic`, `webhook_id`, `api_version`) values that are handed to the app's handler as the trusted tenant/context identifiers come from unauthenticated HTTP headers that are never part of the signed content, breaking the intended binding: `hmac_valid(raw_body) == true` is treated as proof that `shop-domain header == genuine origin shop`, which is false.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `webhook_id`, and `api_version` accessors read directly from HTTP headers with no cryptographic linkage to the body or the HMAC: [2](#0-1) 

`Registry.process` validates only the body-derived HMAC, then immediately trusts `request.shop` (a header) as the tenant identity passed into the handler: [3](#0-2) 

Because `Utils::HmacValidator.validate` only checks `OpenSSL.secure_compare(computed_signature, hmac)` against `to_signable_string` (the body), and the body signature is computed the same way for every shop that shares this app's single `client_secret`, any two webhooks – regardless of which shop they were originally sent for – produce syntactically valid, HMAC-passing `Request` objects as long as the body bytes and HMAC pair were legitimately issued by Shopify at some point for this app. Nothing ties the `shop-domain` header to the specific body/HMAC pair.

The intended binding this breaks: `webhook shop-domain header == shop that Shopify actually generated this signed payload for`. The library treats the header as if it were covered by the signature (docs describe `process` as verifying "the request did indeed come from Shopify," and instruct handlers to key business logic off `data.shop`), but the code never establishes that equality.

### Impact Explanation
An unprivileged internet user who controls (or has installed) the same app on any shop — including a free/trial shop they fully control — receives genuinely Shopify-signed webhook deliveries (raw_body + valid HMAC, since the HMAC only depends on body bytes and the shared `client_secret`). They can capture one such `(raw_body, hmac)` pair and replay it to the app's public webhook endpoint while substituting the `shopify-shop-domain` header (and/or `shopify-topic`, `shopify-webhook-id`) for a victim shop domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` dispatches the handler with `shop: <victim shop>` and the attacker-chosen topic/body semantics believed to belong to that shop.

This crosses the tenant boundary that the app relies on this gem to enforce: the handler cannot distinguish this from a legitimate webhook for the victim shop. Depending on the topics the app subscribes to, this enables cross-tenant impacts such as:
- Forging mandatory GDPR topics (`shop/redact`, `customers/redact`, `customers/data_request`) against a victim shop, causing the app to redact/delete data it does not have consent to touch for that shop.
- Forging `app/uninstalled` for a victim shop to trigger session/token invalidation or cleanup logic for a shop that never uninstalled.
- Injecting attacker-controlled body content that the handler will process as if authored by/for the victim shop, since only bytes are verified while shop attribution is not.

This matches "cross-tenant access" from the Critical impact category, since it lets an attacker cause the app to take actions against a shop other than the one for which Shopify actually signed the payload.

### Likelihood Explanation
Likelihood is moderate-to-high: the attacker only needs a Shopify Partner/dev store to install the target app themselves (a trivial, unprivileged step), harvest one legitimately signed webhook delivery, and then send a crafted HTTP request directly to the app's public webhook endpoint with a substituted `shop-domain`/`topic` header — no access token, `client_secret`, or victim credentials are required. The vulnerable code path (`Registry.process` → `HmacValidator.validate` checking only `raw_body`) is exercised on every webhook delivery and is exactly the code documented as the app's webhook authenticity check.

### Recommendation
Bind the tenant/topic identity into the verified signable content, or otherwise validate it out-of-band:
- Include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string (this requires coordinating with Shopify's signing scheme, or alternatively)
- Require the app, after HMAC validation, to independently confirm that `request.shop` corresponds to a shop with an active session/installation for this app instance before trusting it, and reject/flag mismatches between the shop the app expects for a given `webhook_id`/registration and the header-provided `shop-domain`.
- At minimum, update documentation to make explicit that `shop`, `topic`, `webhook_id`, and `api_version` are unauthenticated header values and must not be trusted as tenant boundaries without additional verification by the host application.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` (a store they control) and lets the app register e.g. the `app/uninstalled` or `shop/redact` webhook topic.
2. Shopify delivers a legitimately signed webhook to the app's callback endpoint:
   ```
   POST /callback/shop/redact
   shopify-topic: shop/redact
   shopify-hmac-sha256: <valid HMAC over RAW_BODY using app client_secret>
   shopify-shop-domain: attacker-shop.myshopify.com
   RAW_BODY
   ```
3. Attacker captures `RAW_BODY` and `shopify-hmac-sha256` unchanged, and replays the same POST to the app's public endpoint, but with the header changed:
   ```
   shopify-shop-domain: victim-shop.myshopify.com
   ```
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `RAW_BODY` only [4](#0-3) ; validation passes because the body/HMAC pair is untouched.
5. `Registry.process` invokes the registered handler with `shop: "victim-shop.myshopify.com"` [5](#0-4) , causing the app to execute `shop/redact` (or whichever topic) logic against `victim-shop.myshopify.com`, a shop the attacker never had access to.
