### Title
Stale positive TTLCache entry allows `validateWithdrawal` to bypass low-storage-balance guard, misrouting funds to the intents contract - (File: `packages/intents-sdk/src/bridges/omni-bridge/omni-bridge.ts`)

### Summary
`OmniBridge.getCachedIntentsStorageBalance` only writes to `intentsStorageBalanceCache` when a freshly fetched balance is above `MIN_STORAGE_BALANCE_FOR_INTENTS_NEAR`, and reads from that cache unconditionally for up to 3000ms before re-fetching. Within that 3-second window, `validateWithdrawal` can pass the storage-balance safety check using a value that no longer reflects the real, now-insufficient on-chain balance.

### Finding Description
The broken equality is: "the storage balance value used to decide whether the withdrawal is safe" should equal "the intents contract's real, current available storage balance on the Omni Bridge contract at call time." The cache breaks this equality asymmetrically.

`getCachedIntentsStorageBalance` [1](#0-0)  reads `this.intentsStorageBalanceCache.get(INTENTS_STORAGE_BALANCE_CACHE_KEY)` and returns it immediately if present, without ever comparing it to a freshly-fetched value or invalidating on time-of-use. It only fetches from RPC (`getAccountOmniStorageBalance`) on a cache miss, and only stores the result back into the cache `if (intentsStorageBalance > MIN_STORAGE_BALANCE_FOR_INTENTS_NEAR)` — a genuinely low balance is never cached (so the next call would re-fetch), but a genuinely high balance is cached for the full 3000ms TTL.

`validateWithdrawal` then compares the cached/fetched value against the threshold: `if (intentsStorageBalance <= MIN_STORAGE_BALANCE_FOR_INTENTS_NEAR) throw new IntentsNearOmniAvailableBalanceTooLowError(...)` [2](#0-1) . Because the TTL is 3000ms, a passing value fetched at t=0 will still be returned and used to pass this check at any call up to t=3000ms, even if the real on-chain balance has meanwhile dropped below the threshold due to storage consumption from other concurrent withdrawals hitting `omni.bridge.near`'s NEP-141 storage_balance for `envConfig.contractID` (the intents contract account).

Exploit flow, exactly as described: call 1 (any user's `validateWithdrawal`) misses cache, fetches a passing balance, caches it for 3000ms. Real balance then drops below `MIN_STORAGE_BALANCE_FOR_INTENTS_NEAR` due to other withdrawals consuming storage deposit. Call 2 (an ordinary user's own withdrawal), within the 3-second window, hits the cache and reuses the stale high balance, passing the guard that should throw `IntentsNearOmniAvailableBalanceTooLowError`. The withdrawal proceeds, and per the explicit code comment, the resulting refund path sends funds to the intents contract account rather than the original withdrawing account — a misdirected, effectively unrecoverable transfer for that user.

No other guard in `validateWithdrawal` (address validation, `compareAddresses`, decimal/normalisation checks, fee assertions, UTXO fee logic) checks or depends on the storage balance; the check is a standalone, single-purpose guard, and its result is solely gated by this cache.

### Impact Explanation
This causes funds to be delivered to the wrong account (the intents contract, `envConfig.contractID`) instead of the withdrawing user's destination address, with no automatic recovery, matching the Critical severity category ("funds delivered to a wrong address/chain/contract with no recovery"). The affected party is any ordinary user whose withdrawal happens to fall within the ~3-second stale-cache window after a concurrent storage-balance-consuming event. This is repeatable any time storage balance is fluctuating near the threshold and multiple withdrawals overlap within the 3000ms TTL.

### Likelihood Explanation
Preconditions: at least one prior `validateWithdrawal` call cached a passing balance, and the real balance drops below the threshold within the following 3 seconds due to concurrent withdrawals' storage consumption — both are plausible under organic concurrent usage without any attacker action, since the trigger is ordinary call timing, not malicious input. No attacker cost or special privilege is needed; it's a race inherent to the caching design.

### Recommendation
Do not cache values that are used to gate an irreversible transfer decision, or drastically shrink the TTL / invalidate on write paths that consume storage. At minimum, treat the cache as a stale-safe optimization only for the "definitely passing" direction is insufficient here — the real fix is either to always fetch fresh storage balance for this specific safety check (removing the cache for `getCachedIntentsStorageBalance`), or to re-validate with a fresh RPC call immediately before executing the withdrawal.

	private async getCachedIntentsStorageBalance(): Promise<bigint> {
		const cached = this.intentsStorageBalanceCache.get(
			INTENTS_STORAGE_BALANCE_CACHE_KEY,
		);
		if (cached !== undefined) {
			return cached;
		}

		const storageBalance = await getAccountOmniStorageBalance(
			this.nearProvider,
			this.envConfig.contractID,
		);
		const intentsStorageBalance =
			storageBalance === null ? 0n : BigInt(storageBalance.available);

		if (intentsStorageBalance > MIN_STORAGE_BALANCE_FOR_INTENTS_NEAR) {
			this.intentsStorageBalanceCache.set(
				INTENTS_STORAGE_BALANCE_CACHE_KEY,
				intentsStorageBalance,
			);
		}

		return intentsStorageBalance;
	}
