### Title
Rounding-down in `convert-to-shares-preview` causes principal loss to depositors on every `deposit()` call - (File: `mainnet/contracts/vault/v0-vault-usdc.clar`, `v0-vault-sbtc.clar`, `v0-vault-stx.clar`, `v0-vault-ststx.clar`, `v0-vault-usdh.clar`, `v0-vault-ststxbtc.clar`)

### Summary
Every Zest vault's `deposit()` function takes the **full** `amount` of underlying from the depositor but mints shares equal to `(convert-to-shares-preview amount)`, which uses `mul-div-down` (floor division). Because the floor of `amount * total-supply / total-assets` is generally strictly less than the value that would convert back to `amount`, the depositor receives shares worth slightly less than what they deposited — this is the exact rounding pattern described in the referenced PoolTogether `AaveV3YieldSource.supplyTokenTo()` finding.

### Finding Description
The deposit flow in every vault (e.g. `v0-vault-usdc.clar`) is: [1](#0-0) 

```
(inkind (convert-to-shares-preview amount))
...
(try! (receive-underlying amount account))   ;; pulls FULL `amount` from user
(try! (ft-mint? zft inkind recipient))        ;; mints only rounded-down shares
(var-set assets (+ current-assets amount))
```

`convert-to-shares-preview` rounds down via `mul-div-down`: [2](#0-1) 

The paired conversion `convert-to-assets-preview` also rounds down: [3](#0-2) 

For a depositor who converts `amount → shares → assets` in immediate succession, the round-trip identity that should hold is:
```
convert-to-assets(convert-to-shares(amount)) == amount
```
Because both conversions floor toward zero, this identity generally fails:
```
convert-to-assets(convert-to-shares(amount)) <= amount
```
Yet the vault charges the user the **full, un-rounded** `amount` (via `receive-underlying amount account`) while crediting them only the rounded-down share count. This is structurally identical to the reported PoolTogether `AaveV3YieldSource.supplyTokenTo()` bug: the contract should only pull `(convert-to-assets-preview inkind)` from the user (the amount that actually corresponds to the shares minted), not the full requested `amount`. The residual difference (`amount - convert-to-assets-preview(inkind)`) is deposited into the vault's `assets` variable and backs `total-assets`, but no shares are minted for it — it silently accrues to all existing shareholders (dilutes/benefits them) at the depositor's expense.

As in the original report, the magnitude of the loss scales with:
- Low precision/decimals of the underlying asset (Zest's `sBTC` vault uses `DECIMALS u8` and satoshi-level share granularity, per `v0-vault-sbtc.clar`) [4](#0-3) 
- A high `total-assets / total-supply` ratio, which naturally grows over time as `total-assets-preview` compounds accrued interest via `total-debt`/`debt-preview` [5](#0-4) 
- High-value tokens like sBTC (satoshi-denominated), where even single-unit rounding represents meaningful value.

The `min-out`/slippage check in `deposit()` only protects against the caller receiving *fewer* shares than an off-chain expected minimum; it does not, and cannot, prevent this systemic rounding loss because the check compares `inkind` (the shares actually minted) against `min-out`, not against a fair, non-rounded expected value. [6](#0-5) 

### Impact Explanation
This causes a small but real loss of principal for every depositor on essentially every `deposit()` call across all six vaults (`v0-vault-stx`, `v0-vault-sbtc`, `v0-vault-ststx`, `v0-vault-usdc`, `v0-vault-usdh`, `v0-vault-ststxbtc`). While a single deposit's loss is typically dust-sized, it is a systemic, non-privileged, permissionless issue that: (a) transfers value from each depositor to existing shareholders without consent, and (b) compounds across a high volume of deposits over the life of the protocol. Under the stated impact taxonomy this is best characterized as a form of unclaimed-yield-equivalent value being permanently misallocated away from the depositor at deposit time (never credited as shares, never redeemable by them), which is a High-severity class of issue per the rules (theft/permanent loss of value that should have accrued to the user, as opposed to protocol insolvency).

### Likelihood Explanation
High likelihood — this triggers on **every** deposit into any vault where `total-assets-preview / total-supply-preview` is not exactly integer-aligned with `amount`, which is the common case once the vault has accrued any interest (the vaults compound continuously via `accrue`/`total-debt`). No privileged access or unusual conditions are required; it is a direct consequence of the vault's default math and is unconditionally reachable by any user calling `deposit()`.

### Recommendation
Mirror the PoolTogether fix: after computing `inkind` (the floored share amount), recompute the exact underlying amount that those shares represent via `convert-to-assets-preview inkind`, and only pull that (rounded) amount from the depositor via `receive-underlying`, crediting `assets` with that same rounded amount instead of the full requested `amount`. Alternatively, round `convert-to-shares-preview` up (ceiling) for deposits so the user is never shortchanged, while keeping `convert-to-assets-preview` for redemptions rounded down — this is the standard ERC-4626 "round in favor of the vault, but round shares up on mint/deposit and down on redeem/withdraw for the depositor" pattern.

### Proof of Concept
Using the general vault math (illustrated with `v0-vault-sbtc.clar`, `DECIMALS u8`): [7](#0-6) 

1. Assume after accrual `total-assets-preview = 2100` (satoshi) and `total-supply-preview = 1000` shares (i.e., the vault has accrued profit, `ta/ts` ratio = 2.1).
2. A user calls `deposit(4, min-out, recipient)`.
3. `inkind = convert-to-shares-preview(4) = mul-div-down(4, 1000, 2100) = floor(1.904) = 1` share.
4. The vault's `receive-underlying` pulls the **full 4** satoshi from the user via `(try! (receive-underlying amount account))`. [8](#0-7) 
5. The user is minted only 1 share. If they immediately `redeem(1, ...)`, `convert-to-assets-preview(1) = mul-div-down(1, 2100, 1001) ≈ 2` satoshi returned (post-deposit `ts=1001`).
6. Net result: user deposited 4 satoshi, can only redeem ~2 satoshi back — losing roughly half their deposit to the rounding gap, which is absorbed into `assets`/`total-assets` and thus benefits all other existing shareholders. [9](#0-8)
