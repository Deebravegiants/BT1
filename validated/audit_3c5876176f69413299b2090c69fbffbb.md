### Title
Race condition in `Wallet#addSeed` due to missing concurrency guard causes lost-update between `EXTRA_SEEDS_KEY` storage and `#seedMetadataAtom` - (File: `features/wallet/module/wallet.js`)

### Summary
`Wallet#addSeed` is exposed directly on `walletApi` and is not wrapped in `makeConcurrent`, unlike `create`/`import` which use `{ concurrency: 1 }`. Two concurrent `addSeed({mnemonic})` calls with different mnemonics can both read `#getExtraSeeds()` before either `#setExtraSeeds()` write completes, causing a classic read-modify-write lost update.

### Finding Description
`addSeed` reads the current extra seeds array via `#getExtraSeeds()`, pushes the new seed, and writes it back with `#setExtraSeeds(seeds)`, then separately updates `#seedMetadataAtom` [1](#0-0) . Because `addSeed` has no concurrency lock (contrast with `create`/`import`, which are explicitly wrapped with `makeConcurrent(..., { concurrency: 1 })` [2](#0-1) ), two overlapping calls, e.g. `addSeed({mnemonic: A})` and `addSeed({mnemonic: B})`, can both call `#getExtraSeeds()` and receive the same pre-update array before either has written back. The second `#setExtraSeeds(seeds)` write then overwrites the first, so only one of the two mnemonics survives in `EXTRA_SEEDS_KEY` storage [3](#0-2) .

However, `#seedMetadataAtom.set` uses a functional updater (`(previous) => ({ ...previous, [seedId]: {...} })`) [4](#0-3) , and the atom is created via `createStorageAtomFactory` with `isSoleWriter: true` [5](#0-4) . If this functional form serializes updates against each other, both metadata entries would end up written to `#seedMetadataAtom`, while `#setExtraSeeds` — which is a plain read-then-overwrite without a functional/merge form — would still lose one seed's underlying secret from `EXTRA_SEEDS_KEY`. That produces exactly the inconsistency the question describes: metadata references a seed whose secret material is missing from extra-seeds storage (or vice versa if ordering differs).

The final step, `this.#keychain.addSeed(data.seed)` [6](#0-5) , loads the seed into the live keychain regardless of what happened with persistent storage, meaning the "lost" seed remains signable for the current session even though it may not have been persisted to `EXTRA_SEEDS_KEY`. This is a genuine unaddressed race: no lock, mutex, `makeConcurrent`, sequencing, or transactional read-modify-write guard exists in `addSeed`, `#getExtraSeeds`, or `#setExtraSeeds` [3](#0-2) . No origin/auth check gates this beyond `#assertWalletIsUnlocked()` [7](#0-6) , which does not prevent concurrent invocation.

### Impact Explanation
This is a data-integrity/state-consistency bug rather than a key-disclosure or unauthorized-signing bug: no attacker gains access to secrets they shouldn't have, and no cross-origin/cross-account boundary is crossed. The practical effect is that a legitimately-added seed can silently disappear from persistent `EXTRA_SEEDS_KEY` storage after a race, while it (or its metadata) may still appear elsewhere in memory for the current session — leading to seed loss on next unlock (since `unlock()` re-derives keychain state purely from `#getExtraSeeds()` [8](#0-7) , a seed whose secret was dropped from storage would not be restored after re-lock/unlock, effectively becoming unrecoverable). This maps to a low/medium "state corruption / accidental fund-access loss" class of impact, not an unauthorized-signing or secret-disclosure vulnerability, since the "hide a seed while it remains signable" property only holds transiently until the wallet is locked/unlocked or the app restarts.

### Likelihood Explanation
Exploitation requires the ability to fire two `addSeed` RPC calls back-to-back with overlapping execution — feasible from an unprivileged, already-unlocked wallet context, since `addSeed` is reachable via `walletApi.addSeed` [9](#0-8)  and only requires the wallet to be unlocked, not any special privilege. However, this generally requires the attacker to control local RPC dispatch timing (e.g., a malicious dapp or script issuing two rapid overlapping calls), which is a real but narrow scenario dependent on the host app not otherwise serializing wallet-module RPC calls. Whether the host application's RPC bridge serializes calls to the same module method was not verified from available code, so the concurrency window in practice depends on that layer, which is outside `wallet.js`.

### Recommendation
Wrap `addSeed` (and ideally `removeManySeeds`, which has the same read-modify-write pattern over `#getExtraSeeds`/`#setExtraSeeds`) in `makeConcurrent(..., { concurrency: 1 })`, consistent with `create`/`import`, to serialize all extra-seed read-modify-write sequences and prevent lost updates.

### Proof of Concept
Integration test plan:
1. Set up a `Wallet` instance with a fake `keychain`, `seedStorage`, `unsafeStorage`, and `seedMetadataAtom`, unlock it.
2. Fire two concurrent calls: `Promise.all([wallet.addSeed({mnemonic: mnemonicA}), wallet.addSeed({mnemonic: mnemonicB})])`.
3. After both resolve, assert:
   - `EXTRA_SEEDS_KEY` storage (via `wallet.getExtraSeedIds()`) contains **both** seed IDs.
   - `wallet.getSeedMetadata()` contains metadata entries for **both** seed IDs, with no orphaned entries (metadata key without corresponding extra-seed entry, or vice versa).
4. Expected (buggy) result: one of the two seeds is missing from `EXTRA_SEEDS_KEY`/`getExtraSeedIds()` while `#seedMetadataAtom` may still list metadata for it (or the reverse), demonstrating the lost-update race, confirming the need for the `makeConcurrent` fix.

    await this.#assertWalletIsUnlocked()

    const seed = await mnemonicToSeed({ mnemonic, format: 'buffer', validate: false })
    const seedId = await getSeedId(seed)
    if (seedId === (await this.#primarySeedIdAtom.get())) {
      throw new Error('Seed already present')
    }

    const dateCreated = this.#clock.now()
    const data = { mnemonic, seed, dateCreated, compatibilityMode }
    const seeds = await this.#getExtraSeeds()
    if (seeds.length >= this.#maxExtraSeeds) {
      throw new Error('Maximum number of seeds reached')
    }

    if (seeds.some((seed) => seed.mnemonic === mnemonic)) {
      throw new Error('Seed already present')
    }

    seeds.push(data)
    await this.#setExtraSeeds(seeds)
    await this.#seedMetadataAtom.set((previous) => ({
      ...previous,
      [seedId]: { dateCreated, label, compatibilityMode },
    }))
