### Title
Webhook shop/topic identity not bound by HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `Utils::HmacValidator.validate` only proves the body's integrity. The `shop`, `topic`, and `webhook_id` values, which are taken straight from HTTP headers and then trusted to identify the tenant, are never included in the signed material. This breaks the binding `HMAC(secret, verified_bytes) == HMAC(secret, bytes_actually_acted_on)`, because `verified_bytes = raw_body` while `bytes_actually_acted_on = raw_body + shop_header + topic_header`.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 
which only returns `@raw_body`. The `shop`, `topic`, and `webhook_id` accessors read directly from HTTP headers without any cryptographic binding: [2](#0-1) 

`Utils::HmacValidator.validate` (used generically for both OAuth callbacks and webhooks via the `VerifiableQuery` interface) computes the HMAC over `to_signable_string` alone: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC, then dispatches to the app's handler using the unauthenticated `shop` and `topic` header values: [4](#0-3) 

`WebhookMetadata.shop` is exactly the field host applications use to scope data to a tenant: [5](#0-4) 

Consequently, a merchant/attacker who legitimately installs the app on their own store receives real, validly-signed webhook deliveries (body + `hmac-sha256` header) from the app for their own shop. Because the HMAC never covers the `shopify-shop-domain` or `shopify-topic` headers, that attacker can resend the exact same body/HMAC pair to the app's public webhook endpoint while substituting a different `shop-domain` header (a victim shop) and/or a different registered `topic` header. `HmacValidator.validate` will still return `true` because the body is unchanged, and `Registry.process` will hand the attacker-chosen body to the handler tagged with the victim's `shop`, causing the host application to associate/act on attacker-controlled data under another tenant's identity.

### Impact Explanation
This is a cross-tenant identity-binding break: the gem's own webhook-processing API (`Registry.process`) authenticates only the payload bytes but reports an unauthenticated `shop` (and `topic`) to the handler as if it were verified. Any application that follows the documented pattern of trusting `WebhookMetadata#shop` for tenant scoping (e.g., updating shop-level records, triggering redaction/data flows, or writing to a per-shop data store) can be made to process forged data under a different merchant's identity — a cross-tenant access primitive, without needing the app's `client_secret` or a leaked token.

### Likelihood Explanation
Requires an attacker who has legitimately installed the target app on their own store (a normal, unprivileged action available to any merchant) in order to obtain one validly-signed body/HMAC pair, then replay it against the app's public webhook endpoint with modified headers. No secrets, tokens, or elevated access are needed beyond installing the app once, so this is realistically reachable by an unprivileged internet-facing actor and matches the documented bug class (identity field acted upon but not covered by the authentication tag).

### Recommendation
Include the identity-binding headers (`shop`, `topic`, and ideally `webhook_id`) in the signed material that `HmacValidator` checks, or perform a secondary check in `Registry.process` that the `shop`/`topic` communicated in headers match values embedded in the verified body (Shopify webhook payloads for most topics include the shop/resource identifiers). At minimum, document and enforce that `WebhookMetadata#shop`/`#topic` are only as trustworthy as the header source, and provide a mechanism to bind them cryptographically to the HMAC so `Registry.process` cannot be tricked into cross-tenant dispatch via header substitution on a replayed, validly-signed body.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and configures/receives a real webhook, capturing the raw body `B` and its header `x-shopify-hmac-sha256: H` (computed by Shopify as `HMAC-SHA256(secret, B)`), per [6](#0-5) .
2. Attacker sends a new POST request to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` and/or a different `x-shopify-topic`.
3. The app calls `ShopifyAPI::Webhooks::Registry.process(request)`; `Utils::HmacValidator.validate(request)` recomputes `HMAC(secret, B)` and finds it equals `H`, so validation passes per [7](#0-6) .
4. The handler receives `WebhookMetadata.new(topic: <attacker-chosen>, shop: "victim-shop.myshopify.com", body: <attacker's own shop's data>, ...)` per [8](#0-7) , and the host app processes attacker-controlled data as if it belonged to `victim-shop.myshopify.com`.
