### Title
Webhook shop-domain header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body via `Utils::HmacValidator.validate` [5](#0-4) . The `shop` value handed to the app's `WebhookHandler` comes directly from the `shopify-shop-domain` HTTP header, which is never part of the signed material [2](#0-1) . Because the HMAC only binds `@raw_body`, an attacker who controls a legitimate merchant account for the app (i.e., an unprivileged, unauthenticated-to-other-tenants internet user relative to other merchants) can capture a genuine webhook delivery for their own shop — body + valid HMAC, computed with the app's shared `client_secret` — and replay that exact HTTP request to the app's public webhook endpoint while substituting the `shopify-shop-domain` header with a victim shop's domain. The signature still validates because the signature never covered the shop header, so the request is accepted and dispatched to the handler with the attacker's real, HMAC-authenticated body but a forged `shop` claim of the victim.

### Finding Description
The identity binding that is broken is: `shop header used by the app == shop bound by the HMAC signature`. In fact, `shop == ∅` under the signature, since `to_signable_string` returns only `@raw_body` [1](#0-0) .

- `Request#hmac` reads `shopify-hmac-sha256` from headers [6](#0-5) .
- `Request#shop` reads `shopify-shop-domain` from headers, unauthenticated [2](#0-1) .
- `HmacValidator.validate_signature` recomputes `HMAC-SHA256(secret, to_signable_string)` and compares it to the received hmac, but `to_signable_string` is only the raw JSON body — the shop header is excluded from the input to the HMAC [3](#0-2) .
- `Registry.process` gates entirely on this HMAC check and then constructs `WebhookMetadata` using `request.shop`, forwarding it as-is to the host app's handler, which typically uses `shop` as the tenant key to store/act on data (per the documented handler contract) [4](#0-3) .
- The library's own docs and tests confirm `data.shop` is expected to be trusted as the webhook's origin shop [7](#0-6) [8](#0-7) .

Since Shopify signs webhooks with the app-level `client_secret` (shared across every shop that installed the app), any merchant using the app can legitimately obtain a valid `(body, hmac)` pair for their own store, then replay it to the app's webhook endpoint with a different shop-domain header. The gem accepts this as authentic and hands the host application attacker-controlled body content falsely attributed to another tenant's shop.

### Impact Explanation
This is a cross-tenant access vulnerability: a malicious merchant can inject fabricated webhook events (e.g., `orders/create`, `customers/update`, app-uninstall/GDPR topics, etc.) that are attributed to a shop they do not own. Depending on how the host application keys data by `data.shop`, this can lead to cross-tenant data corruption, false triggering of tenant-scoped business logic, or injection of attacker-chosen JSON body content into another merchant's tenant record — satisfying the "cross-tenant access" Critical impact category, since the library itself provides no binding between the authenticated bytes and the shop identity it reports to the app.

### Likelihood Explanation
Likelihood is high for any installed-base app: exploitation requires only that the attacker be a legitimate (even free-tier) merchant of the target app, capable of receiving their own webhooks (trivial — install the app on a throwaway dev/store), and network access to the app's public webhook callback URL. No access token, `client_secret`, or privileged account is required — only ordinary use of the app as installed on the attacker's own shop.

### Recommendation
Bind the shop identity into the material that is HMAC-verified, or otherwise cross-check it against a value the app already trusts. Concretely, `WebhookMetadata`/`Registry.process` should not treat `request.shop` as authenticated on its own; the gem should either include the shop domain in `to_signable_string` (not possible without Shopify signing the header) or, more practically, expose an explicit call for host apps to verify `request.shop` against a shop this app already has a stored/active session for before trusting the body — and document clearly that `shop` from `ShopifyAPI::Webhooks::Request` is not itself covered by the HMAC and must not be trusted as a tenant key without corroboration.

### Proof of Concept
1. Attacker installs the target Shopify app on their own shop `attacker.myshopify.com` and registers for a webhook topic (e.g., `customers/update`).
2. Shopify delivers a webhook to the app's endpoint with headers including a valid `x-shopify-hmac-sha256` computed over the JSON body using the app's `client_secret`, and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Attacker captures this exact raw body and HMAC value.
4. Attacker crafts a new POST to the same public webhook endpoint, keeping `raw_body` and `x-shopify-hmac-sha256` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only hashes `@raw_body` [3](#0-2) .
6. `Registry.process` builds `WebhookMetadata.new(shop: request.shop, ...)` with `shop == "victim.myshopify.com"` [9](#0-8) , and invokes the app's handler, which processes attacker-controlled JSON content as though it originated from the victim's store.
