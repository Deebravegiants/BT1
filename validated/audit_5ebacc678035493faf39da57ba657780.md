### Title
Cross-chain amount conversion in `pallet-hyper-fungible-token` can silently round a real transfer down to zero - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`convert_to_balance` scales an incoming ERC20 `U256` amount down to the pallet's local `Balance` type by integer division. When the ERC20-side decimals exceed the local asset's decimals by enough, a small (but real, ERC20-side-nonzero) transfer amount truncates to `0` local balance units with no floor/zero check, exactly the rounding-to-zero class described in the external Lido report (`Lido.sol:522`, "burn zero shares").

### Finding Description
`convert_to_balance` in [1](#0-0)  computes:

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}
```

`erc_decimals` is always `>= local_decimals` because `update_token` enforces `config.decimals >= local_decimals` via `Error::<T>::ErcDecimalsBelowLocal` in [2](#0-1) . That means the divisor `10^(erc_decimals - local_decimals)` is always `>= 1`, and any incoming ERC20 amount smaller than that divisor floors to exactly `0`. The README documents that `on_accept` "maps the source contract back to a local asset ... scales the amount using `Precisions`, then mints (non-native) or releases from escrow (native) to the beneficiary" [3](#0-2) , i.e. this scaling function feeds directly into the mint/release path that credits the beneficiary. There is no check anywhere in the pallet (verified via grep for `amount == 0`/`is_zero`/`ZeroAmount` across the pallet sources) that rejects a converted amount of zero before minting/crediting.

On the EVM side, `HyperFungibleToken.send()` burns the caller's real ERC20-precision tokens unconditionally for any nonzero `amount` [4](#0-3) , and the message carries that raw ERC20 amount to the destination pallet. If the destination's `local_decimals` is far enough below `erc_decimals` (a legitimate, governance-set configuration difference), the destination pallet's `on_accept` will convert a real, already-burned/escrowed amount into `0` local balance and mint/release nothing to the beneficiary — the value is destroyed in transit with no revert, no event indicating failure, and no way to recover it (the source-side tokens are already burned, so there is no timeout-refund path once `on_accept` succeeds).

### Impact Explanation
This is a permanent loss of bridged funds: a user's tokens are burned/escrowed on the source chain (EVM `HyperFungibleToken`/`WrappedHyperFungibleToken`) but the destination `pallet-hyper-fungible-token` mints/releases `0` to the beneficiary once the ISMP message is delivered and `on_accept` succeeds — there is no timeout to trigger a refund because the message was accepted, not timed out. Funds are silently and irreversibly destroyed. This matches the "permanent freezing/loss of funds" acceptance bar via the token bridge mint/burn path.

### Likelihood Explanation
Reachable by any single unprivileged `send` transaction/extrinsic on either side of the bridge; no privileged action required. The only precondition is a decimals configuration where `erc_decimals - local_decimals` is large enough that a plausible dust-sized (but real) transfer amount is smaller than `10^(erc_decimals - local_decimals)` — a configuration entirely under the control of `CreateOrigin`/governance and not something a caller can be prevented from hitting once such a pair exists, since `send` has no minimum-amount check on either side.

### Recommendation
In `convert_to_balance` (or at its call site in `on_accept`), reject conversions that round the amount down to zero (return an error / revert the message as undeliverable) instead of silently minting/releasing zero, mirroring the recommended fix for the analogous Lido `burnShares` rounding issue: add an explicit `ensure!(converted_amount != 0, Error::<T>::AmountTooSmall)` before crediting the beneficiary. Consider similarly hardening `convert_to_erc20`/other decimal-adjustment helpers used at trust boundaries in the codebase (e.g. `adjustDecimalsFloor`/`adjustDecimals` in the SDK) with the same non-zero guarantee where they gate real value transfer.

### Proof of Concept
1. Governance registers a token pair where the local asset has `local_decimals = 6` and the EVM peer is configured with `erc_decimals = 18` (a 12-order-of-magnitude gap), satisfying `config.decimals >= local_decimals`.
2. A user calls `HyperFungibleToken.send()` on the EVM side with `amount = 1` (1 wei, in 18-decimal ERC20 units) — a nonzero, real amount that gets burned from the user's balance.
3. The ISMP message is delivered; `pallet-hyper-fungible-token::on_accept` calls `convert_to_balance(value = 1, erc_decimals = 18, local_decimals = 6)`, computing `1 / 10^12 = 0`.
4. The pallet mints/releases `0` to the beneficiary. The user's real ERC20-side tokens are gone; the beneficiary receives nothing; no revert, no refund path is triggered.
