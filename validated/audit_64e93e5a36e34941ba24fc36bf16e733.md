### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC computed by `Utils::HmacValidator` authenticates the *body* but not the `shop-domain` header. `Webhooks::Registry.process` nonetheless passes `request.shop` (parsed straight from that unauthenticated header) to the app's handler as the tenant identifier. An attacker who legitimately installs the app on their own shop can capture one of their own valid, HMAC-signed webhook deliveries and replay it with the `X-Shopify-Shop-Domain` header swapped to a victim shop, and the gem will report the (unmodified, still-valid) HMAC as verified while attributing the payload to the victim's shop.

### Finding Description
`Request#hmac` reads `hmac-sha256` from the headers, and `Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Registry.process` validates that HMAC and, if valid, immediately trusts `request.shop` (sourced from the `shop-domain`/`x-shopify-shop-domain` header) as the tenant for the webhook, forwarding it straight into the app's `WebhookMetadata`/handler: [2](#0-1) 

Because the `shop` field is never part of the signed content (`to_signable_string` only returns `@raw_body`), the equality the HMAC is supposed to guarantee — "the shop that receives this payload" == "the shop the HMAC was computed for" — does not hold. The HMAC only proves "the app's secret was used to sign this exact body"; it says nothing about which shop the body applies to. Since the app's `client_secret`/webhook secret is shared across all shops that install the app (not shop-specific), any shop with a live install can obtain validly-signed bodies, and the signature remains valid when the `shop-domain` header is swapped, because the header is outside the signed material.

This is the same bug class as the report's "field acted on but not covered by the signature" pattern (there: `tx.gasprice` was read at execution time instead of being locked/covered by the committed fee calculation; here: `shop` is read from an unauthenticated header instead of being bound into the HMAC).

### Impact Explanation
An attacker who is a legitimate (unprivileged) merchant/installer of the target app can:
1. Receive a genuine webhook for their own shop (valid `raw_body` + valid `hmac-sha256`).
2. Replay that exact body/HMAC pair to the app's webhook endpoint, substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain.
3. The gem's `HmacValidator.validate` still returns `true` (body unchanged), and `Registry.process` calls the app's handler with `shop: <victim-shop>`.

If the host application relies on this gem's `shop` field to scope any state-changing action (e.g., mandatory `customers/redact`, `shop/redact`, `app/uninstalled` handling, cache invalidation, entitlement changes), the attacker can inject forged events attributed to a shop they do not own — a cross-tenant integrity issue reachable without any credential belonging to the victim shop.

### Likelihood Explanation
Medium-to-High: exploitation only requires the attacker to be an ordinary user who has installed the app on some shop (no special privileges, no access to `api_secret_key`, no TLS interception). Capturing one's own valid webhook body/HMAC pair and replaying it with a different header value is trivial with a proxy or manual HTTP client.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the signed material, or otherwise authenticate the header out-of-band, e.g.:
- Compute the HMAC over a canonical string that includes the shop domain header value in addition to the raw body, or
- Require host applications to independently verify that `request.shop` matches an already-authenticated/installed shop record before trusting it, and document this requirement clearly, since `Webhooks::Registry.process` currently does not perform any such cross-check itself.

### Proof of Concept
```ruby
# Attacker owns shop "attacker.myshopify.com" and receives a legitimate webhook:
raw_body = '{"id":1}'
valid_hmac_b64 = Base64.encode64(
  OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
)

# Attacker replays the same body/hmac but swaps the shop-domain header:
forged_headers = {
  "shopify-topic" => "customers/redact",
  "shopify-hmac-sha256" => valid_hmac_b64,
  "shopify-shop-domain" => "victim-shop.myshopify.com", # not covered by HMAC
  "shopify-webhook-id" => "forged-id",
  "shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) returns true (raw_body unchanged),
#    handler.handle receives WebhookMetadata with shop: "victim-shop.myshopify.com"
``` [3](#0-2)
