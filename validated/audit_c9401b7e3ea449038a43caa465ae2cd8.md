Webhook `shop` attribution is not covered by the HMAC signature, allowing cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook by validating an HMAC over the raw request body only, but the tenant identity (`shop`) that the handler receives and acts on is read from an HTTP header that is never covered by that HMAC. This breaks the intended binding: `bytes verified` ≠ `bytes the shop attribution is derived from`.

### Finding Description
`ShopifyAPI::Webhooks::Request` implements `Utils::VerifiableQuery`, whose `to_signable_string` returns only `@raw_body`: [1](#0-0) 

The `shop` accessor, however, is derived purely from the unauthenticated `x-shopify-shop-domain` / `shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then forwards `request.shop` straight into `WebhookMetadata`, which is handed to the app's handler as the trusted tenant identifier: [3](#0-2) [4](#0-3) 

Critically, `Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` — i.e. the raw body — and compares it against the `hmac` header: [5](#0-4) 

Because Shopify signs webhooks with a single, app-wide `client_secret` shared across every installed shop (not a per-shop secret), a valid `(raw_body, hmac)` pair obtained from a webhook delivered for one shop remains cryptographically valid for that exact body regardless of which shop-domain header accompanies it. The `shop` field is never included in the signable string, so nothing prevents an attacker from re-submitting a legitimately-signed body while substituting an arbitrary victim `x-shopify-shop-domain` header value. The identity binding that should hold is:
`shop attributed to the processed event == shop that produced/authorized the signed bytes`
but the gem currently only enforces:
`hmac(raw_body, client_secret) == received_hmac`
with `shop` sourced from bytes outside that computation.

### Impact Explanation
This maps to the Critical "cross-tenant access" impact category: a caller who can obtain any one valid `(body, hmac)` pair (e.g., from a webhook fired for their own store, which they fully control and can trigger at will) can attribute that payload to any other merchant's `shop` domain when delivering it to the host application's webhook endpoint. Since `Registry.process` performs no comparison between the authenticated body and the shop header, and hands `request.shop` to the handler as trusted, host applications that follow the documented pattern (`data.shop`) and use it to select which merchant's records to update, enqueue jobs against, or attribute state changes to are exposed to forged, cross-tenant webhook events validated as authentic by this gem's own HMAC check.

### Likelihood Explanation
Likelihood is High for any attacker who can install/operate their own Shopify app installation against their own shop (the normal, unprivileged path to obtaining a signed webhook body+hmac pair with no special credentials), then replay that body to the app's public webhook endpoint with a modified shop header. No access to `api_secret_key`, access tokens, or the app owner's other credentials is required — only the ability to receive one's own genuine webhook and re-POST it.

### Recommendation
Bind the header-derived `shop` value into the authenticated signable content of webhook requests, or otherwise verify that the shop declared for processing matches a shop for which the request is legitimately expected (e.g., include `shop`, `topic`, and `webhook_id` in the HMAC-covered signable string, or require the caller to separately confirm the `shop-domain` header against a known/expected value before trusting `WebhookMetadata#shop`). At minimum, document and enforce that `Registry.process` must validate shop-header consistency, not just raw-body integrity, since the header is currently attacker-controllable independent of the HMAC.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` (or otherwise triggers any webhook delivery to themselves) and receives a genuine webhook request with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
2. Attacker replays the identical request to the app's webhook endpoint, keeping body `B` and header `x-shopify-hmac-sha256: H` unchanged, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses this into a `Request` whose `to_signable_string` is still `B` and whose `shop` is `"victim.myshopify.com"`.
4. `Utils::HmacValidator.validate(request)` recomputes `HMAC-SHA256(client_secret, B)`, which equals `H`, so validation succeeds: [6](#0-5) 
5. `Registry.process` calls the app's handler with `WebhookMetadata.new(... shop: "victim.myshopify.com" ...)`, causing the host application to process an attacker-supplied payload as if it originated from the victim shop.
