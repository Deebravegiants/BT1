### Title
Unvalidated relay-supplied leaf indices in BEEFY authority/parachain merkle-proof verification enable out-of-bounds indexing / proof-check bypass - ([File: modules/consensus/beefy/verifier/src/lib.rs])

### Summary
`verify_mmr_update_proof` and `verify_parachain_headers` build leaf-index arrays directly from attacker/relayer-controlled fields (`sig.index`, `para_header.index`) and pass them to `rs_merkle::MerkleProof::verify` without first checking that each index is less than the corresponding leaf-count bound (`authority_set.len`, `parachain_proof.total_leaves`). This mirrors the fbdev `bit_putcs*` bug class: an externally supplied index is used to address into a fixed-size structure without a bounds clamp/check before use.

### Finding Description
In `verify_mmr_update_proof`, for every signature in the relayed `mmr.signed_commitment.signatures`, the authority index is taken verbatim from the message and pushed into `authority_indices` with no range check: [1](#0-0) 

`authority_set.len` (the true authority-set size) is only used later as the `total_leaf_count` parameter to `merkle_proof.verify`, not as an upper bound for the indices collected in the loop: [2](#0-1) 

The same pattern exists in `verify_parachain_headers`, where `para_header.index` (also attacker/relayer supplied, part of the unsigned consensus message) is cast to `usize` and pushed unchecked before being handed to `merkle_proof.verify` alongside `parachain_proof.total_leaves`: [3](#0-2) 

`sig.index` is a `u32` field decoded straight from the unsigned/relayed BEEFY consensus message (`SignatureWithAuthorityIndex`): [4](#0-3) 

Nothing in `verify_mmr_update_proof` rejects an index `>= authority_set.len` (or, for parachains, `>= parachain_proof.total_leaves`) before it is passed to the Merkle-proof verification routine. This is the exact analog of the fbdev bug: the "glyph index" (here, the authority/parachain position) is derived from untrusted input and used to compute/verify positions in a fixed-size structure (the Merkle tree of `total_leaf_count` leaves) without a bound check against the actual leaf count. The codebase elsewhere demonstrates awareness of and fixes for precisely this bug class — e.g. the regression fix in `verify_mmr_leaf` for an unchecked `leaf_indices[0]` index that "previously panicked the runtime via the unchecked `[0]` index": [5](#0-4) 
and similar defensive bound checks added throughout the Pharos state-proof/SPV code for validator/proof-depth indices (`MAX_VALIDATORS`, `ProofTooDeep`, `nibble_at_depth` bounds): [6](#0-5) [7](#0-6) 

By contrast, the BEEFY authority-index and parachain-index paths lack an equivalent guard before indices are consumed by the external Merkle-proof verifier.

### Impact Explanation
`verify_mmr_update_proof` is the entry point for consensus-state updates in the BEEFY light client used by `pallet-ismp`/`EvmHost` to accept relay-chain finality and parachain header commitments, which downstream drive state/membership proof verification for cross-chain messages. If an out-of-range index either (a) panics the runtime while indexing into the internal Merkle-tree position arrays inside `rs_merkle::MerkleProof::verify`, this halts BEEFY consensus updates entirely — a route unable to deliver messages (denial of the light client). If instead the malformed index causes the proof-verification library to miscompute the expected root/position and incorrectly return `true` for a proof that does not actually cover the claimed authority/parachain leaf, this would let a malicious relayer forge acceptance of a BEEFY commitment or parachain header without the required supermajority of authorities actually having signed it — resulting in unsound consensus-state commitment and forged message delivery. Either outcome is reachable from a single relayed, unsigned BEEFY/parachain consensus message and requires no privileged role, satisfying the High severity bar.

### Likelihood Explanation
Any relayer permitted to submit BEEFY consensus messages controls `sig.index` and `para_header.index` fully; there is no on-chain re-derivation or bound check of these values prior to their use as Merkle-tree positions, so triggering the unchecked path only requires crafting a consensus message with an index at or beyond `authority_set.len`/`parachain_proof.total_leaves`. Because `check_participation_threshold` only compares the signature count (not indices) against the authority-set size, an attacker can satisfy the supermajority-count check while still injecting one or more out-of-range indices.

### Recommendation
Before pushing `sig.index` / `para_header.index` into `authority_indices` / `indexed_leaf_hashes`, validate `index < authority_set.len` (respectively `index < parachain_proof.total_leaves`) and reject the consensus message (e.g., `Error::InvalidAuthoritiesProof` / `Error::InvalidParachainProof`) if any index is out of range, mirroring the bound checks already applied elsewhere in the codebase (e.g., `MAX_VALIDATORS`, `ProofTooDeep`, the `leaf_indices.len() != 1` guard in `verify_mmr_leaf`).

### Proof of Concept
1. A relayer submits a `ConsensusMessage` whose `mmr.signed_commitment.signatures` includes enough valid signatures to pass `check_participation_threshold`, but at least one `SignatureWithAuthorityIndex.index` set to a value `>= trusted_state.current_authorities.len` (e.g., `u32::MAX`).
2. `verify_mmr_update_proof` builds `authority_indices` including this out-of-range value with no check, per: [8](#0-7) 
3. `merkle_proof.verify(..., &authority_indices, &authority_leaves, authority_set.len as usize)` is invoked with the malformed index, exercising the un-guarded downstream indexing/position computation in `rs_merkle`, matching the fbdev class of unchecked-index array access. The same construction applies to `ParachainProof.parachains[i].index` in `verify_parachain_headers`.

		let hashed_uncompressed = H::keccak256(&uncompressed);

		let mut eth_address = [0u8; 20];
		eth_address.copy_from_slice(&hashed_uncompressed.as_ref()[12..]);

		let authority_address_hash = H::keccak256(&eth_address);

		authority_leaves.push(authority_address_hash.into());
		authority_indices.push(sig.index as usize);
	}

	let merkle_proof = MerkleProof::<MerkleHasher<H>>::new(mmr.authority_proof.clone());

		&authority_indices,
		&authority_leaves,
		authority_set.len as usize,
	);
