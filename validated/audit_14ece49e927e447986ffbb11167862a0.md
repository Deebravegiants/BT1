### Title
Withdrawal status/txHash misreported across batched withdrawals of the same token (matched by assetId, ignoring index) - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves the on-chain status/hash for a specific withdrawal in a batch by matching the POA Bridge API response only on `assetId`, discarding the `index` field that uniquely identifies which withdrawal in the batch is being polled. When a caller withdraws the same token to two different destinations in a single NEAR transaction, both `WithdrawalIdentifier`s resolve to the same (first) matching entry in the API response, so the SDK reports the same status/txHash for both, even though they are two distinct on-chain transfers.

### Finding Description
`createWithdrawalIdentifier` builds a `WithdrawalIdentifier` that carries `index`, `withdrawalParams`, and `tx`: [1](#0-0) 

`describeWithdrawal` is invoked once per withdrawal index (see the batch orchestration in `sdk.ts`), but it only uses `args.withdrawalParams.assetId` to find the matching withdrawal in the bridge's response — `args.index` is never consulted: [2](#0-1) 

```
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): ... {
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}
``` [3](#0-2) 

`Array.prototype.find` always returns the first element satisfying the predicate. If the caller batches two withdrawals of the same token (same `assetId`) to different destination addresses in one NEAR tx (a normal, unprivileged usage pattern supported by `sdk.processWithdrawal`/`createWithdrawalCompletionPromises` for arrays of `WithdrawalParams`), both indices' `describeWithdrawal` calls hit the same underlying HTTP response and both resolve to the identical first-matching withdrawal entry — reporting the same `status` and the same `transfer_tx_hash` for what are actually two different on-chain outcomes (e.g., one destination’s transfer could be `COMPLETED` while the other is `PENDING` or `REFUNDED`).

The exact same limitation, with an identical comment acknowledging it, exists in the sibling implementation used by `waitForWithdrawalCompletion`: [4](#0-3) 

This breaks the equality the report's rules call out: "a status reported that is not the on-chain outcome." The code comment itself concedes the limitation but frames it purely as an unsupported feature rather than as a correctness hazard for concurrent/batched same-token withdrawals; the code silently returns a plausible-looking (but wrong) status instead of failing safely (e.g., asserting uniqueness or matching by amount/order).

### Impact Explanation
If an integrator relies on `describeWithdrawal`/`watchWithdrawal`/`waitForWithdrawalCompletion` per-index results to decide when funds have arrived at a specific destination, a batch of ≥2 withdrawals of the same token can cause:
- One destination's withdrawal to be reported `completed` with a `txHash` that actually belongs to the *other* destination's transfer (misdelivery of status/hash, i.e., wrong transfer attributed to a given `WithdrawalIdentifier`).
- An integrator crediting/settling based on this misreport before the actual on-chain transfer for that specific destination has occurred, or double-crediting because two logically distinct withdrawals appear to have "completed" via the same reported hash.

This matches the High severity bucket in the rules: "a status or hash misreport making an integrator credit or refund twice."

### Likelihood Explanation
Requires an unprivileged, ordinary usage pattern: an SDK user submits a batch withdrawal (`WithdrawalParams[]`) containing two or more entries with the same `assetId` but different `destinationAddress` via the POA bridge route. No attacker action or malicious external party is needed — normal batching of same-token payouts (e.g., paying out the same token to multiple users in one transaction) triggers it. The code path is reachable via `sdk.processWithdrawal`/`createWithdrawalCompletionPromises`, both of which accept arrays of `WithdrawalParams`.

### Recommendation
Match POA Bridge API withdrawal entries deterministically per index rather than solely by `assetId`. Options:
- Sort both `withdrawalParams` and API `withdrawals` by amount (as the existing code comment suggests) and pair them positionally when duplicate `assetId`s are present, or
- Track/require a unique correlation id per withdrawal in the outgoing intent (if the POA API/protocol supports it) and match on that, or
- If disambiguation isn't currently possible with the available data, explicitly detect duplicate-`assetId` entries in a batch and throw/refuse rather than silently returning a result for the wrong destination, and apply the same fix in `internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ {assetId: "nep141:usdc.omft.near", destinationAddress: A, amount: 100}, {assetId: "nep141:usdc.omft.near", destinationAddress: B, amount: 200} ] })`, producing one NEAR tx with two POA withdrawals of the same token.
2. `createWithdrawalCompletionPromises` builds two `WithdrawalIdentifier`s (`index: 0` for A, `index: 1` for B) and calls `watchWithdrawal` → `PoaBridge.describeWithdrawal` for each.
3. POA Bridge API returns both withdrawal records for the tx (e.g., A's entry `COMPLETED` with `transfer_tx_hash: "hashA"`, B's entry still `PENDING`).
4. `findMatchingWithdrawal` for **both** indices filters purely on `assetId === "nep141:usdc.omft.near"` and `Array.prototype.find` returns the **same first entry** (A's `COMPLETED`/`hashA`) for both index 0 and index 1.
5. Result: the SDK reports withdrawal to B as `completed` with `hashA`, even though B's actual transfer is still pending — as demonstrated conceptually by the existing test `"matches withdrawal by assetId, not by index"` in `poa-bridge.test.ts`, which only verifies single-destination matching and does not cover the duplicate-`assetId` batch case. 		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,

		if (withdrawal == null) {
			return { status: "pending" };
		}

			return { status: "pending" };

				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",

		};
	}

function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
