### Title
Asymmetric decimal scaling in `convert_to_balance`/`convert_to_erc20` causes silent under-crediting or unbacked over-minting when a local asset has more decimals than its registered EVM contract - ([File: modules/pallets/hyper-fungible-token/src/impls.rs])

### Summary
`pallet-hyper-fungible-token`'s decimal conversion helpers only scale in one direction. Both `convert_to_balance` and `convert_to_erc20` compute their exponent with `erc_decimals.saturating_sub(local_decimals)`, which silently becomes `0` whenever `local_decimals > erc_decimals`. In that configuration, incoming ERC20 amounts are credited 1:1 as local balance units (massive under-crediting), and outgoing local amounts are sent to the EVM side without being scaled down (massive over-inflation of the minted amount on the destination chain). This mirrors the reported BloomPool `_rwaScalingFactor` bug class: an unconditional/one-directional scaling factor applied to values of differing decimal precision, producing "severe mis-pricing" instead of a value-preserving conversion.

### Finding Description
`convert_to_balance` and `convert_to_erc20` are the sole precision-conversion primitives used on both the mint/credit path (`module.rs::on_accept`, `module.rs::on_timeout`) and the burn/send path (`lib.rs::send`): [1](#0-0) 

```rust
pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256,
    erc_decimals: u8,
    local_decimals: u8,
) -> Result<B, B::Err> {
    let dec_str = (value /
        U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
    .to_string();
    dec_str.parse::<B>()
}

pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
```

Both functions are correct only when `erc_decimals >= local_decimals` (the case exercised by `BridgeToken.sol`, where the ERC20 fixes `decimals()` at 18 while nexus's BRIDGE asset is 12 decimals, and by every unit test in `pallet_hyper_fungible_token.rs`, which uses `convert_to_erc20(SEND_AMOUNT, 18, 10)`). When a registered asset instead has *more* local decimals than the peer's EVM contract (`local_decimals > erc_decimals`, e.g. a local 18-decimal asset paired with a 6-decimal EVM token), `saturating_sub` clamps the exponent to 0, and no scaling is applied at all:

- On receive (`module.rs::on_accept`), the ERC20 amount (denominated in `erc_decimals`, e.g. 6) is credited directly as `local_decimals` (e.g. 18) units — the recipient is credited a value ~10^(local−erc) too small. [2](#0-1) 

- On send (`lib.rs::send`), the local balance (18 decimals) is passed straight to `convert_to_erc20` without being scaled down to the destination's 6-decimal representation, producing an ERC20 amount ~10^(local−erc) too large, which the peer `HyperFungibleToken.sol`/`WrappedHyperFungibleToken` will mint on the destination chain without any corresponding value being locked/burned on the source side. [3](#0-2) 

- The same broken helper is reused on the timeout/refund path (`module.rs::on_timeout`), so a failed dispatch would refund the wrong (deflated) amount to the original sender as well. [4](#0-3) 

`register_token`/`update_token` (via `TokenRegistration`/`ChainConfig`) accept an arbitrary `decimals: u8` per chain and store it in `Precisions`, with no validation constraining it to be `>=` the local asset's own decimals: [5](#0-4) 

There is no check anywhere in `lib.rs`/`module.rs` enforcing `erc_decimals >= local_decimals`, so nothing prevents an operator from registering (or misconfiguring) a token pairing where the local asset (e.g. a locally-issued 18-decimal fungible asset via `pallet-assets`) is bridged against an EVM contract declaring fewer decimals — a configuration that is entirely plausible for non-native/mint-burn assets registered through `register_token`, unlike the fixed, audited `BridgeToken.sol` deployment.

### Impact Explanation
This is a High/Critical-class issue depending on which direction is hit:
- **Unauthorized/unbacked minting**: when sending from the local chain (`local_decimals > erc_decimals`), the destination `HyperFungibleToken` contract mints an amount inflated by `10^(local_decimals - erc_decimals)`, creating tokens with no backing collateral on the source chain — a direct value-creation/insolvency bug in a token bridge mint path.
- **Permanent value loss for users**: when receiving into the local chain, users are credited `10^-(local_decimals - erc_decimals)` of what they sent, permanently freezing/losing the difference (the pallet_account still holds/escrowed or burned the correct amount on the sending side, but the receiving side mis-credits).
- The refund-on-timeout path also mis-refunds the sender by the same factor, compounding fund loss for the honest party in a timed-out transfer.

### Likelihood Explanation
Reachable by any governance-approved token registration that pairs a locally-issued asset with more decimals against an EVM contract of fewer decimals (a routine, expected configuration difference across chains — many ERC20s use 6 or 8 decimals while Substrate assets commonly use 10, 12, or 18). Once such a token is registered, every ordinary `send`/`on_accept`/`on_timeout` call for that asset triggers the mis-scaling — no attacker action beyond a normal cross-chain transfer is required. The only asset exempt is the specially hardcoded `BridgeToken.sol` (18 ERC decimals ≥ 12 local decimals), so the bug is latent for any other token pairing the generic pallet supports.

### Recommendation
Fix `convert_to_balance` and `convert_to_erc20` to handle both directions symmetrically, e.g.:
```rust
if erc_decimals >= local_decimals {
    value / 10^(erc_decimals - local_decimals)   // scale down to local
} else {
    value * 10^(local_decimals - erc_decimals)   // scale up to local
}
```
and the erc20 conversion should mirror this with multiplication/division swapped. Additionally, add a defensive check (or at minimum a test) covering `local_decimals > erc_decimals` configurations to prevent regression, and consider validating decimal compatibility (or documenting the constraint and enforcing it) at `register_token`/`update_token` time.

### Proof of Concept
1. Governance registers a local `pallet-assets` asset `X` with `decimals = 18` via `register_token`, pairing it to an EVM contract on chain `Evm(1)` with `ChainConfig { decimals: 6, .. }`. This is stored in `Precisions::<T>::get(X, Evm(1)) = 6`.
2. Alice calls `HyperFungibleToken::send` with `amount = 1_000_000_000_000_000_000` (1 whole token, 18dp). `erc_decimals=6`, `local_decimals=18`, so `convert_to_erc20` computes exponent `6u8.saturating_sub(18u8) = 0`, giving `erc20_amount = 1_000_000_000_000_000_000` (unchanged) instead of the correct `1_000_000` (1 token at 6dp).
3. The destination `HyperFungibleToken.sol` mints `1_000_000_000_000_000_000` raw units to the recipient — 10^12 times the correct amount — with only 1 token's worth of value locked/burned on the source chain, an unbacked mint of the wrapped asset. [6](#0-5) [3](#0-2)
