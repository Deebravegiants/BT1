## Analysis

Raydium's `Deposit` instruction computes `mint_lp_amount` from the pool's *pre-transfer* live vault balances (`total_coin_without_take_pnl` / `total_pc_without_take_pnl`) and the user's requested `max_coin_amount`/`max_pc_amount`, and only *afterwards* invokes the SPL transfer CPI to actually move `deduct_coin_amount`/`deduct_pc_amount` tokens into the vaults [1](#0-0) . The LP mint amount and the actual amount received are never reconciled against each other.I have sufficient context to answer now.

### Title
Fee-on-transfer tokens allow LP-share dilution / insolvent pool accounting via `Deposit` mint miscalculation - (File: `program/src/processor.rs`)

### Summary
Raydium's `Deposit` instruction computes the LP token mint amount (`mint_lp_amount`) from the pool ratio using `deduct_coin_amount`/`deduct_pc_amount` *as requested*, then transfers those exact requested amounts via `Invokers::token_transfer` CPI. If either the coin or pc mint is a fee-on-transfer SPL token, the amount actually credited to `amm_coin_vault`/`amm_pc_vault` will be less than `deduct_coin_amount`/`deduct_pc_amount`, but the LP tokens minted to the depositor are still calculated as if the full amount landed in the vault.

### Finding Description
In `Self::deposit` (`program/src/processor.rs`), the pool ratio (`total_coin_without_take_pnl`, `total_pc_without_take_pnl`) is read from the live vault balances at the start of the instruction via `unpack_token_account` [2](#0-1) . Based on this ratio and the caller-supplied `max_coin_amount`/`max_pc_amount`, the code computes `deduct_coin_amount`/`deduct_pc_amount` and `mint_lp_amount` via `InvariantPool::exchange_token_to_pool` *before* any tokens move [1](#0-0) .

Only afterward does the program execute the actual SPL transfers of `deduct_coin_amount` and `deduct_pc_amount` from the user's token accounts into the AMM vaults, followed immediately by minting `mint_lp_amount` LP tokens to the depositor: [3](#0-2) . There is no post-transfer balance check comparing the vault's actual balance delta to `deduct_coin_amount`/`deduct_pc_amount` before minting LP tokens — the program trusts that the full nominal amount arrived.

If the coin or pc mint is a fee-on-transfer token, `spl_token::instruction::transfer` (invoked in `Invokers::token_transfer`, `program/src/invokers.rs:148-168`) will deliver less than `deduct_coin_amount`/`deduct_pc_amount` to the vault, yet `mint_lp_amount` is minted as if the full nominal amount was deposited. This directly parallels the referenced Teller `CollateralManager` bug class: a virtual/assumed balance (`deduct_coin_amount`) diverges from the actual on-chain balance received, because the protocol performs its accounting/minting math using the pre-transfer nominal amount rather than validating the delta actually credited.

### Impact Explanation
Each such deposit mints LP tokens backed by less real value than assumed, diluting the claim of all other pre-existing LP holders and permanently degrading the coin/pc backing per outstanding LP token — an insolvent pool accounting condition and effectively unbacked LP minting. Because `target_orders.calc_pnl_x`/`calc_pnl_y` are also updated using the nominal `deduct_coin_amount`/`deduct_pc_amount` rather than the amount actually received [4](#0-3) , the pnl/target-orders bookkeeping also drifts from the real vault contents, compounding the inconsistency across subsequent swaps and withdrawals that rely on `Calculator::calc_total_without_take_pnl_no_orderbook`.

### Likelihood Explanation
This is reachable by any unprivileged liquidity provider submitting a single `Deposit` instruction with attacker-chosen accounts, provided the pool was created (via `Initialize2`) or already exists for a coin/pc mint that charges a transfer fee. No special privileges, validator collusion, or off-chain assumptions are required — only a fee-on-transfer mint being paired in a Raydium pool and a normal `Deposit` call.

### Recommendation
Read the vault token account balances both before and after the `token_transfer` CPI calls in `Self::deposit`, compute the *actual* deltas received (`post_balance - pre_balance`), and use those real deltas — not the nominal `deduct_coin_amount`/`deduct_pc_amount` — for the `mint_lp_amount` calculation and for updating `target_orders.calc_pnl_x`/`calc_pnl_y`. Alternatively, explicitly reject mints known to charge a transfer fee (checking the mint's `TransferFeeConfig` extension for Token-2022, and disallowing legacy fee-on-transfer wrapper tokens) before allowing them to be used as pool coin/pc mints in `Initialize2`.

### Proof of Concept
1. Create (or use an existing) Raydium pool where the `coin` mint is a fee-on-transfer SPL token (e.g., 5% fee on every transfer).
2. Attacker/LP calls `Deposit` with `base_side = 0`, `max_coin_amount = 1000`. The program computes `deduct_coin_amount = 1000` and a corresponding `mint_lp_amount` based on `total_coin_without_take_pnl` before any transfer [5](#0-4) .
3. `Invokers::token_transfer` moves the instruction, but the fee-on-transfer mint burns/redirects 5%, so only 950 tokens actually land in `amm_coin_vault` [6](#0-5) .
4. `Invokers::token_mint_to` still mints the full `mint_lp_amount` calculated for a 1000-token deposit [7](#0-6) .
5. The pool's real coin backing per LP token is now lower than accounted for; subsequent `Withdraw` calls compute `coin_amount`/`pc_amount` from the (now diluted) live vault balance [8](#0-7) , meaning honest, pre-existing LPs redeem less value than deposited, while the attacker's LP tokens were minted using an inflated nominal deposit amount — an insolvent-pool / unbacked-LP-minting condition.
