## Title
Emporium's unrestricted "Stateless Interaction" arbitrary call lets any prover drain undeclared token balances held by the shared Emporium contract - (File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`EmporiumUpgradeable.runAction`'s "Stateless Interaction" branch is the direct analog of the reported `callRestricted`-disabled-by-default bug: it lets the caller direct the shared `Emporium` contract to `.call` **any** `endpoint` with **any** `callData` (msg.sender = Emporium), with only two function selectors blacklisted, and no allowlist of callees at all.

### Finding Description
`runAction` decodes an attacker-controlled `EmporiumStack` straight out of `circomData.externalActionData.externalActionMetadata` [1](#0-0) . For every op that is not routed through a user's own `HinkalWallet` (`invokeWallet && signerAddress != 0`), it falls into "CASE 2: Stateless Interaction", where the only restriction is a selector blacklist for `callHinkalWallet`/`doSendToRelay`; any other `endpoint`/`callData` pair is executed unconditionally with `Emporium`'s own address as `msg.sender`:

```solidity
bytes4 selector = bytes4(op.callData);
if (selector == IHinkalWallet.callHinkalWallet.selector ||
    selector == IHinkalWallet.doSendToRelay.selector) {
    revert UnauthorizedWalletCall();
}
(success, err) = op.endpoint.call{value: op.value}(op.callData);
``` [2](#0-1) 

This is exactly the same "whitelist mechanism exists but is effectively off" pattern as the external report: instead of `callRestricted` defaulting to `false`, here the analog is that there is no allow-list of callable `endpoint`s at all — only two out of an unbounded selector space are denied.

The only safety net after the loop is a **per-declared-token** balance-equation check:
```solidity
int256 balanceChange = int256(balancesAfter[i]) - int256(balancesBefore[i]);
...
if (balanceChange < 0) revert BalanceChangeShouldBePositive();
``` [3](#0-2) 

This loop only iterates over `circomData.erc20TokenAddresses` — i.e. tokens the **attacker themselves chooses to declare**. Any token balance the shared `Emporium` contract holds that is *not* in that attacker-chosen list (dust left over from a previous user's swap/emporium action, an outstanding ERC20 `approve` granted to `Emporium` by another user's flow, protocol/relay fee remnants, etc.) is completely outside the equation Hinkal is supposed to enforce (`Hinkal.sol`'s balance-diff check is likewise scoped to `circomData.erc20TokenAddresses`) [4](#0-3) . Because `Emporium` is a single shared contract instance (not per-user) registered once in Hinkal via `registerExternalAction` [5](#0-4) , any value it holds outside of the currently-declared token set is fair game for theft by constructing a `Case 2` op such as `token.transfer(attacker, balance)` or `token.transferFrom(victim, attacker, amount)` if a stale approval exists.

While `calldataHash` binds the `EmporiumStack` bytes into the ZK-verified public input [6](#0-5) , this only proves the caller committed to whatever `EmporiumStack` they authored themselves — it does not constrain the `endpoint`/`callData` content in any way, so the attacker is free to target any contract/function they like.

### Impact Explanation
This breaks the equality that Hinkal is supposed to enforce ("every token balance change of an external action must equal what was declared and reflected in the minted UTXO"). Any residual balance/approval sitting on the shared `Emporium` contract — belonging to the protocol (relay fees) or to other users (dust, unswept approvals) — can be exfiltrated by any unprivileged caller without it being detected or backed by a burnt nullifier. This is theft of protocol/relay fees at minimum (High), and theft of other users' funds if a token/approval tied to their flow is present (Critical).

### Likelihood Explanation
Any address that can submit a normal Hinkal `transact` (even with a trivial/self-owned deposit) can route it through `Emporium` and supply an arbitrary `EmporiumStack`; no admin/relay/owner key is required, and the check that would prevent this (per-token balance equation) simply doesn't cover tokens the attacker chooses to omit from `circomData.erc20TokenAddresses`. Likelihood depends on `Emporium` actually holding an exploitable balance/approval at attack time, which is plausible given it's a shared, stateful contract interacting with arbitrary DeFi endpoints across many users' transactions.

### Recommendation
Restrict `endpoint` in the Stateless Interaction branch to an explicit allow-list (mirroring `onlyAllowedRecipient`/`setAllowedRecipients` already used elsewhere), and/or require that the post-call balance check iterate over **all** tokens the endpoint could plausibly touch (or snapshot/compare the full set of tokens the `EmporiumStack.ops` reference), not just the attacker-declared `circomData.erc20TokenAddresses`. Consider also disallowing arbitrary `endpoint` values entirely for the zero-signer path and requiring `endpoint` be part of a protocol-curated registry.

### Proof of Concept
1. Some prior legitimate transaction leaves `Emporium` holding a residual ERC20 balance or an outstanding `approve(Emporium, X)` from another user's flow (e.g., dust after a partial-fill swap, or an approval granted for a multi-step DeFi interaction).
2. Attacker performs a normal, self-funded `Hinkal.transact()` targeting the Emporium external action (`externalActionId` = Emporium's id), declaring only tokens they own in `circomData.erc20TokenAddresses` (e.g., a token they trivially deposit/withdraw amount `0`).
3. In `externalActionMetadata`, attacker encodes an `EmporiumStack` with `signerAddress = address(0)` (skips EIP-712 signature check entirely, per `verifyWallet`) and one `EmporiumOperation` with `invokeWallet = false`, `endpoint = <residual token address>`, `callData = abi.encodeWithSelector(IERC20.transfer.selector, attacker, residualBalance)` (or `transferFrom(victim, attacker, amount)` if an approval exists).
4. `runAction`'s Case 2 branch executes this call with `msg.sender == Emporium`, succeeding since neither selector is blacklisted.
5. The post-loop balance check only inspects the attacker's declared `circomData.erc20TokenAddresses`, which doesn't include the stolen token, so `balanceChange` for it is never computed and the transaction completes normally — attacker walks away with the residual/undeclared funds while the balance equation Hinkal enforces reports no discrepancy.
