## Analysis Result

I found a genuine reentrancy pattern in `withdraw()` that is analogous to a "use-after-free"-class bug (a resource — the escrowed order balance — is consumed via an external call *before* its ledger entry is invalidated, allowing the stale, not-yet-updated entry to be reused).

### Title
Reentrant native-token transfer in `IntentGatewayV2.withdraw()` allows draining escrowed order balance before ledger update - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
`withdraw()`, reachable from `onAccept` (called by the host on `RedeemEscrow`/`RefundEscrow` message delivery) and from local `cancel()`/select flows, performs `beneficiary.call{value: amount}("")` for native-token legs of an order **before** decrementing `_orders[body.commitment][token]`. This violates checks-effects-interactions: the "free" (debit) of the escrow slot happens only after the external call returns, so the stale (not-yet-decremented) value is still readable/usable during the callback.

### Finding Description [1](#0-0) 

```
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = ...;
    _filled[body.commitment] = beneficiary;
    for (... i < len ...) {
        ...
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();
        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");   // external call FIRST
            ...
        } else {
            (bool success,) = token.call(...transfer...);
            ...
        }
        _orders[body.commitment][token] -= amount;                 // debit happens AFTER
        ...
    }
```

`_orders[commitment][token]` is only decremented after the low-level `.call` returns. Because `beneficiary` can be an attacker-controlled contract (it's decoded directly from the message body/order as `body.beneficiary`), the receive/fallback hook on the native-token leg executes with `_orders[commitment][token]` still at its **full pre-withdrawal value**. `onAccept` has no `nonReentrant` guard, and `withdraw` is `internal` with no reentrancy lock of its own, so a reentrant call back into `onAccept`/`withdraw` (or any other externally reachable function touching the same commitment/order) during that callback sees stale, not-yet-freed accounting.

This is directly analogous to a "use-after-free": the escrow slot is logically supposed to be consumed atomically with the transfer, but the "free" (decrement) is deferred past the external call, so it can be "used" again while stale.

### Impact Explanation
If reentered before the decrement lands, an attacker-controlled beneficiary contract could trigger additional withdrawal logic against the same, still-full `_orders[commitment][token]` balance, resulting in transfer of more value than was actually escrowed for that order — direct theft of escrowed funds from the `IntentGatewayV2` contract. This affects escrow accounting for intents/orders reachable by any unprivileged relayer delivering a `RedeemEscrow`/`RefundEscrow` message (or by the order's own beneficiary triggering a same-chain path), matching the "intents escrow" attack surface explicitly in scope.

### Likelihood Explanation
Medium-High: the beneficiary address is attacker-controlled by construction (the order creator sets `order.user`/`body.beneficiary`), and delivery of `RedeemEscrow`/`RefundEscrow` is driven by permissionless relayers via `onAccept` — an unprivileged message dispatcher can trigger this path. Exploitability further depends on whether ERC-20 legs in the same loop or other order state provide a secondary reentry point that yields net-positive extraction (i.e., whether a second pass can extract more than what remains escrowed) — I could not fully trace all downstream effects of a reentrant call within the remaining budget, so the *exact* profitable reentry chain (which function to reenter, and whether cross-token double-spend inside the same `for` loop is possible) is not fully proven end-to-end.

### Recommendation
Apply checks-effects-interactions: decrement `_orders[body.commitment][token]` **before** issuing the native/ERC-20 transfer, and/or add a reentrancy guard (`nonReentrant`) around `withdraw`/`onAccept` for these request kinds.

### Proof of Concept
Not fully constructed — I verified the code ordering (external call before storage debit) via static reading of `evm/tron/contracts/apps/IntentGatewayV2.sol` lines 691-714, but did not have remaining tool budget to trace a complete, weaponized reentrancy call graph (e.g., confirming there's no reentrancy guard inherited from `HyperApp` or the host's `onAccept` dispatch path, and confirming a concrete profitable reentry target). This should be verified with a Foundry PoC that sets `beneficiary` to a malicious contract with a `receive()` that reenters `onAccept` for the same commitment before returning.

**Caveat on confidence:** This analog is a stretch from the original UAF CVE (memory corruption vs. Solidity storage-ordering/reentrancy), and I was not able to fully confirm the absence of a reentrancy guard inherited from `HyperApp` (base contract) nor rule out that `_filled[body.commitment]` being set at the top of `withdraw` prevents a meaningful double-payout via `UnknownOrder`/`Filled` checks elsewhere in the contract that I did not have iterations left to inspect. Treat this finding as requiring further verification before being treated as conclusively exploitable.
