### Title
Webhook `shop` (tenant) identity is not covered by the HMAC signature, allowing cross-tenant webhook data spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then unconditionally trusts the `X-Shopify-Shop-Domain` header (exposed as `Request#shop`) as the tenant identity passed to the app's handler. Because the shop header is not part of the signed payload, the binding "HMAC-verified bytes == the shop the data is attributed to" does not hold, letting anyone who can produce one valid (body, hmac) pair relabel that payload as belonging to a different shop.

### Finding Description
The docs state that `Registry.process` "will verify the request did indeed come from Shopify" [1](#0-0)  before invoking the handler with `data.shop` as the tenant identifier [2](#0-1) .

In `Registry.process`, the only check performed is the HMAC validation, after which the handler is invoked with `request.shop` taken straight from the request: [3](#0-2) 

`Request#hmac` is computed from a signed-with-secret header value, and `to_signable_string` returns only the raw HTTP body — the shop header is excluded from the signable string entirely: [4](#0-3) [5](#0-4) 

`HmacValidator.validate` / `validate_signature` only ever hashes `verifiable_query.to_signable_string` (the body, for webhooks) against the app's `api_secret_key`: [6](#0-5) 

The `api_secret_key` used to sign webhooks is the app's single shared client secret — identical for every shop that installs the app — not a per-tenant secret. Therefore any merchant who installs the app (an ordinary, unprivileged action for an "unprivileged internet user" relative to any *other* merchant's data) can trigger a real webhook to their own endpoint and obtain a body+HMAC pair that is valid under the app's shared secret. That attacker can then replay the exact same `raw_body` and `x-shopify-hmac-sha256` value to the app's public webhook endpoint while freely setting `x-shopify-shop-domain` (and `x-shopify-topic`, `x-shopify-webhook-id`, `x-shopify-api-version`) to any value, e.g. a victim shop's domain. `HmacValidator.validate` still returns `true` because it never inspects the shop header, and `Registry.process` calls the app's handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker's own body>, ...)`.

The binding that should hold but does not:
`HMAC-verified(shop_header) == shop attributed to the verified body`
Before the attack: `shop_header == "attacker-shop.myshopify.com"`, `hmac` is valid for that body.
After the attacker's replay: `shop_header == "victim-shop.myshopify.com"`, the same `hmac`/body pass verification unchanged — the equality is broken while `HmacValidator.validate` still reports success.

### Impact Explanation
This is a cross-tenant integrity/confusion issue reachable without any credentials, tokens, or the app's `api_secret_key` (the attacker only needs to be a legitimate, low-privilege installer of the app on their own store — a standard unprivileged capability). Any host application that follows this gem's documented pattern (`Registry.process` -> handler receives `data.shop`, `data.body`) and uses `data.shop` to decide which merchant/tenant record to create, update, or act on (a normal and expected usage per the gem's own documentation example `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) can be made to attribute attacker-controlled webhook content to an arbitrary victim shop. Depending on the webhook topic the app subscribes to, this enables cross-tenant data injection/corruption (e.g., forged `orders/create`, `customers/update`, `app/uninstalled`, or GDPR `customers_data_request` payloads attributed to a shop the attacker does not control), which matches the "cross-tenant access" high-impact category since it breaks the shop-tenant boundary the gem is responsible for enforcing during webhook processing.

### Likelihood Explanation
Likelihood is high: it requires no secrets, no privileged account, and no interception — only (1) installing the target app on any store the attacker controls (a normal onboarding flow) to harvest one valid `(body, hmac)` pair for a given topic, and (2) sending a forged HTTP request with a different `shop-domain`/`x-shopify-shop-domain` header value to the app's public webhook endpoint. Webhook endpoints are, by design, public unauthenticated HTTP endpoints reachable directly by any internet client, and this gem imposes no additional binding between the verified bytes and the shop header.

### Recommendation
Include the shop domain (and ideally topic/webhook id) inside the HMAC-covered signable content, or otherwise cryptographically bind the `shop-domain` header to the verified payload before it is handed to consumer handlers, e.g. verify that the `X-Shopify-Shop-Domain` reported for a given webhook corresponds to a shop with a stored, previously-established session/installation for the exact webhook subscription id (`webhook_id`) rather than trusting the header at face value in `Request#shop`/`Registry.process`.

### Proof of Concept
1. Attacker installs the vulnerable app on their own dev store `attacker-shop.myshopify.com` and registers a webhook topic the app subscribes to (e.g. `orders/create`).
2. Shopify sends a legitimate webhook to the app's endpoint with headers:
   `x-shopify-topic: orders/create`, `x-shopify-hmac-sha256: <valid HMAC over raw body B>`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, plus `webhook-id`/`api-version`.
3. Attacker captures raw body `B` and the valid `x-shopify-hmac-sha256` value (these are visible to them since it's their own store/webhook, e.g. via a request-logging proxy on their receiving endpoint).
4. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with the exact same body `B` and same `x-shopify-hmac-sha256`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses this successfully [7](#0-6) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because only body `B` is hashed [8](#0-7) ; the handler is invoked with `shop: "victim-shop.myshopify.com"` and the attacker's own body content [9](#0-8) .
6. Any app logic keyed off `data.shop` now processes attacker-supplied data as if it originated from the victim shop.

        sig { params(request: Request).void }
        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
