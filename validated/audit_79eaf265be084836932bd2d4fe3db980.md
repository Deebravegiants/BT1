### Title
Webhook shop-tenant attribution is not covered by the HMAC, allowing cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then trusts the unauthenticated `x-shopify-shop-domain` header to attribute the event to a tenant. Since the HMAC never binds the `shop` field, any holder of a single valid `(raw_body, hmac)` pair for the shared app `client_secret` can replay that exact body with a different `shop-domain` header and have the app process it as if it came from an arbitrary victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook by calling `Utils::HmacValidator.validate(request)`: [1](#0-0) 

`HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` value from the request: [2](#0-1) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` returns only `@raw_body`, while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers and are **not** part of the signed string: [3](#0-2) 

After the HMAC check passes, `process` builds `WebhookMetadata` directly from `request.shop` — the unauthenticated header — and hands it to the app's handler, which the documented usage pattern trusts as the tenant identity for downstream processing (e.g. enqueuing a job "for" that shop): [1](#0-0) [4](#0-3) [5](#0-4) 

The identity binding that should hold is: `hmac_valid(secret, request) == true` should imply `shop == the shop the request was actually generated for`. Because `shop` is excluded from `to_signable_string`, this equality does not hold — `hmac_valid` only proves the body was signed with the app's `client_secret` at some point, for some shop, not for the `shop` header presented in *this* request.

Any merchant who installs the app on their own store (an unprivileged, low-trust actor relative to other tenants of the same app) legitimately receives genuine `(raw_body, hmac)` pairs signed with the app's single shared `client_secret`. Because the signature is body-only, that attacker can resend the identical `raw_body` + `hmac` to the app's webhook endpoint while substituting `x-shopify-shop-domain` (or `shopify-shop-domain`) with an arbitrary victim shop domain. `HmacValidator.validate` still succeeds — it only checks that the body's HMAC matches, and does not verify the header claims — so `Registry.process` calls the handler with `WebhookMetadata.shop` set to the forged victim shop, causing the app to process/store attacker-controlled data under another tenant's identity.

### Impact Explanation
This breaks the tenant-isolation boundary the gem is supposed to enforce for webhook ingestion: an actor with no privileges on the victim shop can inject fabricated webhook events (arbitrary topic-appropriate body) that the host app will attribute to and act on for the victim shop, since `data.shop` (the only tenant discriminator available to the handler) is entirely attacker-controlled and not covered by the same signature that gates request acceptance. This satisfies the "cross-tenant access" criterion (Critical).

### Likelihood Explanation
Any user of an app built on this gem can trivially install the app on their own store to legitimately capture at least one real `(raw_body, hmac)` pair for a topic of their choosing, then replay it against the shared endpoint with a spoofed shop-domain header. No knowledge of `api_secret_key` is required — only a body/hmac pair the attacker legitimately obtained for their own tenant.

### Recommendation
Include `shop` (and ideally `topic`) in the signed material for webhook requests, or independently verify that the `shop` header corresponds to a shop the app has installed/has an active session for before trusting `WebhookMetadata.shop`, rather than deriving tenant identity purely from an unauthenticated header alongside a body-only HMAC.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker.myshopify.com" and
# legitimately receives a genuine webhook for topic "customers/create":
raw_body = '{"id":1,"email":"victim@example.com"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), api_secret_key, raw_body)
hmac_b64 = Base64.encode64(hmac)

# Attacker now replays the SAME body+hmac to the app's webhook endpoint,
# only changing the shop-domain header to the victim shop:
headers = {
  "x-shopify-topic" => "customers/create",
  "x-shopify-hmac-sha256" => hmac_b64,   # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged
  "x-shopify-webhook-id" => "forged-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => Utils::HmacValidator.validate(request) returns true, because
#    to_signable_string only returns raw_body; "shop" is never checked.
# => handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
#    is invoked, causing the host app to process attacker data as victim-shop data.
