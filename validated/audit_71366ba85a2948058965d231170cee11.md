### Title
Orb-Relay client responds to `RequestState` requests without validating message source, allowing signup state leakage to an unverified entity - (File: `orb-relay-client/src/client.rs`)

### Summary
The external report describes `pricePerShare` being trusted and used in a critical calculation (transfer amount) without a sanity/consistency check against its expected value, letting a bad or spoofed reading drain funds. The closest reachable analog in orb-core is `PollerAgent::main_loop` in `orb-relay-client/src/client.rs`, where an incoming message's claimed type (`RequestState`) is trusted to bypass the source-identity check (`src.id != self.config.dst_id`) that is otherwise enforced for every other inbound relay message, before returning the cached `last_message` (last signup/session state) back over the wire.

### Finding Description
In the connection main loop, incoming `RelayConnectResponse` payloads are handled as follows: [1](#0-0) 

The `else if src.id != self.config.dst_id` identity check is only reached when the payload does **not** match `self_serve::app::v1::RequestState`. If it does match, the code unconditionally replies with `self.last_message.clone()` — the most recent state message the orb sent to whatever session it was last bound to — without validating that `src` corresponds to the entity the connection was set up for (`self.config.dst_id`). This is exactly the "no sanity check on a value before it's used" pattern from the report: instead of validating the source before releasing state, the code takes the shortcut path for one message type and skips the check that exists specifically to reject unexpected/foreign senders.

`self.config.dst_id` is set to the value of `orb_relay_app_id`, obtained from the user's QR-code-derived `UserData` (`src/backend/user_status.rs`), which flows into `orb_relay_announce_orb_id` (`src/plans/mod.rs`) to create the `Client`: [2](#0-1) 

Because the `RequestState` branch skips the `src.id` check entirely, any relay peer able to reach this orb/session queue and send a message whose payload matches `RequestState` can trigger a resend of `last_message` (the current/most recent signup state for that queue) regardless of whether its `src.id` actually equals the expected `dst_id`.

### Impact Explanation
`last_message` reflects orb-side signup/session state (e.g., capture-trigger, capture-started, signup-ended messages) intended only for the app bound to this specific `session_id`/`orb_relay_app_id`. Skipping the source-identity check for this one message type breaks the same invariant enforced elsewhere in the loop and can leak in-progress signup state to an entity other than the legitimate paired app — a cross-signup state bleed as defined in scope, since state produced for one session/user can be disclosed to a requester that hasn't been validated as that session's counterpart.

### Likelihood Explanation
No privileged access is required: the attacker only needs the ability to send a message over the orb-relay channel that decodes as `self_serve::app::v1::RequestState` (an unprivileged, publicly-documented message type used by any app client, as shown in `orb-relay-client/src/bin/manual-test.rs`). The missing check is unconditional and always reachable on every iteration of `main_loop`, making the omission systematic rather than a rare edge case.

### Recommendation
Apply the same `src.id != self.config.dst_id` validation to the `RequestState`-matching branch before sending `last_message`, i.e., check the source identity first regardless of payload type, and only reply with cached state when the sender is confirmed to be the bound session peer.

### Proof of Concept
1. A relay client `A` connects as the orb with `dst_id` set to a specific `orb_relay_app_id`/session id.
2. A different relay client `B` (any peer able to reach the same relay queue with a different `src.id`) sends a `self_serve::app::v1::RequestState` payload.
3. In `main_loop`, the `if self_serve::app::v1::RequestState::matches(&payload).is_some()` branch is taken first, and `sender_tx.send(self.last_message.clone())` executes without ever comparing `src.id` to `self.config.dst_id`, unlike the `else if` branch immediately following it.
4. `last_message` (the orb's most recent state message for the bound session) is returned to `B`, even though `B`'s `src.id` was never validated against the expected `dst_id`. [3](#0-2)
