### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted from unauthenticated headers while the HMAC only covers the raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request body, then dispatches to a handler using `shop`, `topic`, `webhook_id`, and `api_version` values that are read directly from HTTP headers and are never covered by that HMAC.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`, and `Webhooks::Request#hmac` decodes the `shopify-hmac-sha256`/`x-shopify-hmac-sha256` header for comparison: [1](#0-0) [2](#0-1) 

The `shop`, `topic`, and `webhook_id` accessors are all pulled from separate, unsigned headers: [3](#0-2) 

`Registry.process` validates the HMAC (which only proves the *body* bytes were signed by holders of `api_secret_key`) and then uses the unauthenticated header-derived `request.topic` to select the handler and `request.shop` to populate the metadata passed to that handler: [4](#0-3) 

The identity binding broken is: `bytes verified (raw_body via HMAC)` ≠ `bytes/fields acted upon (shop, topic, webhook_id headers)`. Since `api_secret_key` is a single shared secret across every shop that installs the app (not shop-specific), any shop that legitimately installs the app receives real, validly-HMAC-signed webhook deliveries for its own data. That signed `(raw_body, hmac)` pair is portable: the same signed body can be resent with an arbitrary `shopify-shop-domain` and/or `shopify-topic` header, and `Registry.process` will still accept it because only the body is checked.

### Impact Explanation
An attacker who has installed the app on their own store (a low-privilege, ordinary Shopify merchant/unprivileged internet user relative to other tenants of the same app) can capture one of their own genuine webhook deliveries and resend it to the app's public webhook endpoint with the `shop-domain` header changed to a victim shop and/or the `topic` header changed to a different event type the body happens to satisfy. Because the gem hands `shop: request.shop` straight to the handler after only validating the body's HMAC, host applications following this gem's documented flow (`WebhookMetadata` built from `Registry.process`) will process/store the forged event as if it originated from the victim shop, resulting in cross-tenant data confusion/injection (e.g., orders, GDPR, app-uninstalled events attributed to a shop that never sent them).

### Likelihood Explanation
Medium: the attacker needs their own paid or dev-store installation of the target app (a routine, unprivileged action for any Shopify user) and the ability to POST to the app's known webhook endpoint. No secret key, session, or victim credential is required — only interception/replay of one's own legitimately signed webhook traffic.

### Recommendation
Bind the tenant/topic identity into the value that is actually HMAC-verified, or independently corroborate `request.shop`/`request.topic` against server-side state before dispatch:
- Require the host app (and ideally the gem's `Registry.process`) to check `request.shop` against a known/installed-shop list (e.g., an existing session for that shop) before invoking the handler, rather than trusting the header value unconditionally.
- Document/enforce that `topic` from the header must be cross-checked against the payload's actual structure/topic markers where feasible.
- Consider incorporating `shop-domain` and `topic` into the signable string used for HMAC verification if compatible with Shopify's webhook signing scheme, so header tampering invalidates the signature.

### Proof of Concept
1. Install the target Shopify app on attacker-controlled store `attacker.myshopify.com`. Shopify delivers a real webhook, e.g. `orders/create`, with body `B` and header `X-Shopify-Hmac-Sha256: H` computed over `B` using the app's shared `api_secret_key`.
2. Attacker resends the exact same `B` and `H` to the app's webhook endpoint, but with headers modified:
   ```
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: H            # unchanged, still valid for body B
   X-Shopify-Shop-Domain: victim.myshopify.com   # forged
   X-Shopify-Webhook-Id: <any>
   ```
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `B` against `H`.
4. The registered handler for `orders/create` is invoked with `WebhookMetadata` carrying `shop: "victim.myshopify.com"`, even though `victim.myshopify.com` never sent this event, demonstrating the cross-tenant confusion.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end
