### Title
Unchecked SIP-010 transfer boolean result in vault deposit/withdraw and market/treasury transfers - ([File: mainnet/contracts/vault/v0-vault-usdh.clar], [File: mainnet/contracts/vault/v0-vault-usdc.clar], [File: mainnet/contracts/market/v0-market-vault.clar], [File: mainnet/contracts/dao/dao-treasury.clar])

### Summary
The reported DODO issue is about `IERC20.transfer` calls whose boolean return value is never checked, so a token that returns `false` on failure (instead of reverting) silently "succeeds" from the caller's perspective while no value moves. The direct Clarity analog exists in every Zest vault's underlying-token transfer helpers. Deposits/withdrawals wrap the SIP-010 `transfer` call in `try!`, which only distinguishes `(ok x)` from `(err e)` — it does **not** assert that the wrapped boolean `x` is `true`. If the underlying token ever returns `(ok false)` on a failed transfer (a legal SIP-010 response, exactly analogous to ERC20 tokens that return `false` instead of reverting), the vault treats the transfer as fully successful.

`try!` in Clarity only inspects the outer `response` constructor: on `(ok bool)` it unwraps to the inner `bool` and continues execution; on `(err ...)` it aborts. It never asserts that the unwrapped `bool` is `true`. Because these functions immediately return `(ok true)` regardless of what value `try!` actually unwrapped, the caller of `receive-underlying`/`send-underlying` (deposit/withdraw/borrow/repay logic that updates the `assets` variable and mints/burns `zft` shares) has no way to detect that the underlying token reported `(ok false)`.

The same `try! (contract-call? ... transfer ...)` pattern, without checking the unwrapped boolean, recurs across the market vault and DAO treasury transfer paths (confirmed via grep matches in `mainnet/contracts/market/v0-market-vault.clar` and `mainnet/contracts/dao/dao-treasury.clar`), meaning the same class of unchecked-boolean-transfer risk is present anywhere the protocol moves its underlying/reward tokens.

This breaks the custody-versus-ledger identity: `real token balance held by vault == assets variable backing minted shares`. If `receive-underlying` returns `(ok true)` while the token itself returned `(ok false)` (no actual balance change), the vault increments `assets`/mints shares for a deposit that never arrived; symmetrically for `send-underlying` on withdrawal, a "successful" outbound transfer that actually failed would still decrement the internal ledger while leaving the tokens in the vault (or vice versa depending on where the false-return manifests), decoupling recorded assets from actual custody.

### Impact Explanation
If the underlying SIP-010 token used by any vault (or any token moved by the market/treasury contracts) ever returns `(ok false)` on a failed transfer rather than an `err` response, the vault would credit shares for value never received, or debit its ledger for value never sent — either directly enabling minting of shares backed by nothing (protocol insolvency / theft of principal from other depositors) or permanently freezing/burning obligations tied to a withdrawal that silently failed.

### Likelihood Explanation
Likelihood depends entirely on whether the specific underlying tokens integrated (`usdcx`, `usdh-token-v1`, `sbtc`, `ststx`, etc.) can ever legally return `(ok false)` instead of erroring on a failed transfer. SIP-010 does not prohibit this response shape, and the protocol's own custody functions provide no defense-in-depth against it — the vault code as written trusts `try!` to be sufficient, when it is not. This is a code-correctness gap in Zest's own contracts (not a third-party token bug) that would surface the moment any current or future integrated token exhibits this valid-but-unusual response pattern.

### Recommendation
In `receive-underlying`/`send-underlying` (and every other `contract-call? ... transfer` site flagged by the grep matches across vault, market, and dao-treasury contracts), explicitly assert the unwrapped boolean instead of relying on `try!` alone, e.g.:
```clarity
(asserts! (try! (contract-call? .usdc transfer amount account current-contract none)) ERR-TRANSFER-FAILED)
```

### Proof of Concept
1. Vault's underlying token implementation returns `(ok false)` for a `transfer` call that fails a balance/allowance-style internal check (a legal SIP-010 response).
2. A user calls deposit; `receive-underlying` executes `(try! (contract-call? ... transfer amount account current-contract none))`, which unwraps to `false` but is discarded, and the function still returns `(ok true)`.
3. The vault's deposit logic proceeds to mint shares / increase `assets` as if the underlying tokens were received, even though the vault's real token balance is unchanged.
4. Repeating this breaks `total real balance == assets ledger`, allowing shares to be minted against no real backing, which can be redeemed later by draining real deposits from other users. [1](#0-0) [2](#0-1)
