The active `g2::DealtPubKeyShare::try_from` path is generated purely from the `g2` macro invocation, deriving `DEALT_PK_SHARE_NUM_BYTES` from `dealt_pub_key::g2::DEALT_PK_NUM_BYTES`, which is itself bound to `G2_PROJ_NUM_BYTES` — never anything from `g1`. [2](#0-1)

So even in the counterfactual where a "G1-shaped" byte buffer is submitted, the size and validity checks are self-contained to the `g2` path and reject malformed inputs; there's no gating logic borrowed from a disabled `g1` module that could be bypassed.

Furthermore, even if such a parsing confusion could theoretically be forced, `DealtPubKeyShare`/`DealtPubKey` here live in `aptos-dkg`'s PVSS transcript logic, used for reconstructing dealt public keys during distributed key generation. This is not itself an asset-custody surface (object/resource-account ownership, FA store, multisig authority, etc.) reachable from an unprivileged transaction — it's cryptographic material handled internally by the DKG protocol, not general on-chain resource or object control. It does not meet the review's custody-impact gate criteria (owner/controller/balance/authority changes), so this would be rejected as out-of-scope even in the hypothetical case where the described type confusion were real.
