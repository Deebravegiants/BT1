### Title
`TokenExchange.exchange_token` accepts non-admin (checkout/customer-scoped) session tokens to mint full merchant access tokens - ([File: lib/shopify_api/auth/token_exchange.rb])

### Summary
`ShopifyAPI::Auth::JwtPayload` decodes and cryptographically verifies a Shopify session token's signature and `aud` (app API key) claim, but never validates the `iss` claim that indicates *which context* issued the token (Admin embedded app vs. Checkout UI Extension vs. other surfaces). `TokenExchange.exchange_token` then unconditionally uses the `dest` shop from *any* validly-signed token to perform a full OAuth Token Exchange, handing the app's `client_id`/`client_secret` to Shopify and receiving back a real online/offline Admin access token for that shop.

### Finding Description
`JwtPayload#initialize` only checks the token's HMAC signature and that `aud == Context.api_key`: [1](#0-0) 

It even implements an `admin_session_token?` helper that inspects `iss` for the `/admin` suffix, but that helper is used *only* to gate `shopify_user_id`, not to restrict what the token can be used for: [2](#0-1) [3](#0-2) 

Shopify issues session tokens (JWTs signed with the app's shared `client_secret`) to multiple untrusted-browser surfaces beyond the Admin embedded app iframe, including Checkout UI Extensions, which run in the browser of an ordinary, unauthenticated customer during checkout. The test fixtures in this repo confirm the two distinct issuer shapes are both valid, signed tokens: [4](#0-3) 

`TokenExchange.exchange_token` takes the `shop` binding for the privileged Token Exchange request purely from the token's `dest` claim, with no check that the token's `iss` proves it was minted for the Admin/backend-privileged context: [5](#0-4) 

This breaks the identity binding: `session_token.iss == "https://{shop}/admin"` (proof the token authorizes merchant-admin-level backend operations) is decoded but never enforced before the app's `client_secret` is spent to obtain a full merchant access token on `session_token.dest`'s behalf. Any session token bearer — including a customer who merely visited checkout and captured their own Checkout UI Extension session token — satisfies the only checks actually performed (valid signature + correct `aud`), and can therefore cause the host app's backend to hand back an Admin API access token (online or offline, per `requested_token_type`) for that shop.

Note the sibling helpers `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` route their `shop` parameter through `Utils::ShopValidator.sanitize!` for defense-in-depth domain validation, and `TokenExchange.migrate_to_expiring_token` does too — but `exchange_token`, which derives its `shop`/`dest` value from client-supplied JWT content rather than a trusted parameter, has no equivalent contextual check on the *issuer* of that JWT: [6](#0-5) [7](#0-6) 

### Impact Explanation
This allows scope/context escalation: a token minted for a customer-facing, low-privilege surface (Checkout UI Extension) can be replayed against the app's Token Exchange endpoint to obtain a genuine Admin API access token for the merchant's shop, using the app's own `client_secret`. This matches the "scope or expiry check bypass" / credential-issuance-abuse category — an unprivileged (customer) actor can cause exfiltration of a real merchant access token that they should never be entitled to.

### Likelihood Explanation
Any app that exposes a backend endpoint calling `TokenExchange.exchange_token(session_token: ...)` (the documented, recommended token-exchange flow) and passes through the raw ID token supplied by the frontend/extension without itself re-validating the issuer is exposed. Because Checkout UI Extensions run in a normal customer's browser, the session token is inherently accessible/interceptable by that same customer (an unprivileged internet user), making exploitation straightforward once such an endpoint exists.

### Recommendation
In `JwtPayload`, enforce (or expose a strict helper for callers to enforce) that `iss` ends with `/admin` for any privileged operation such as Token Exchange, and have `TokenExchange.exchange_token` reject tokens where `jwt_payload.admin_session_token?` is false, raising `Errors::InvalidJwtTokenError` before performing the OAuth token exchange call.

### Proof of Concept
1. A customer visits a merchant's storefront checkout where the app has a Checkout UI Extension installed; the extension calls Shopify's `idToken()` API and obtains a validly-signed JWT with `iss: "https://shop.myshopify.com/checkouts"`, `aud: <app client_id>`, `dest: "https://shop.myshopify.com"`.
2. The customer captures this token (e.g., via browser devtools/network inspection, since it is delivered to code running in their own browser).
3. The customer sends this token to the app backend's token-exchange endpoint (a route the app exposes per the documented Token Exchange flow), e.g. by directly crafting the HTTP request or via any client the app trusts.
4. The backend calls `ShopifyAPI::Auth::TokenExchange.exchange_token(session_token: captured_token, requested_token_type: OFFLINE_ACCESS_TOKEN)`.
5. `JwtPayload.new` succeeds (valid signature, correct `aud`); `admin_session_token?` is never checked. `exchange_token` proceeds to call `/admin/oauth/access_token` with the app's `client_id`/`client_secret` and receives a real offline Admin access token for `shop.myshopify.com`, which the backend then stores/returns — handing merchant-admin API access to a party who only ever had checkout-level (customer) trust.
