## Analysis

The reported bug class is a classic "identity binding break": a value that is *used* by security-sensitive logic is not the same value that was *cryptographically verified*. Looking for the strongest analog in this gem's `lib/shopify_api/**` (excluding generated REST resources), the webhook HMAC verification path fits this pattern exactly.

`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body — the HMAC signature computed and verified by `ShopifyAPI::Utils::HmacValidator` covers `@raw_body` alone, not any of the HTTP headers: [1](#0-0) [2](#0-1) 

Yet `request.shop`, which is read straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, is what `Registry.process` passes to the webhook handler as the tenant identifier: [3](#0-2) 

`HmacValidator.validate` only checks `verifiable_query.hmac` against `to_signable_string` (the body), never the shop header: [4](#0-3) 

### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook solely by validating the HMAC over the raw request **body** (`Request#to_signable_string` returns `@raw_body` only). The `shop` value handed to webhook handlers (`WebhookMetadata#shop`), however, comes from the unauthenticated `x-shopify-shop-domain` HTTP header, which is not part of the signed content. The binding the gem should guarantee — `hmac_verified_bytes == bytes_that_determine_tenant` — is broken: `body ⊆ hmac_verified_bytes` but `shop_header ⊄ hmac_verified_bytes`, while `shop_header` is exactly what identifies the tenant to the host application.

### Finding Description
Shopify signs the webhook body using the app's single shared `client_secret`/`api_secret_key` — the same secret is used for every shop that has the app installed. `HmacValidator.validate_signature` recomputes the HMAC over `verifiable_query.to_signable_string` (the raw body) and compares it to the `hmac-sha256` header. It never incorporates the `shop-domain` header into the signed material: [5](#0-4) 

Because the HMAC is keyed only to the body, any two webhook deliveries carrying the same body (e.g. an empty-body webhook, or any payload an attacker can also legitimately receive for their own shop) share the same valid signature. A merchant who has the app installed on their own shop can observe a legitimately-signed webhook (body + valid `hmac-sha256`), then replay that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. `HmacValidator.validate` still returns `true` (body signature matches), and `Registry.process` forwards `request.shop` — the attacker-controlled header — as the authenticated tenant identity to the handler: [3](#0-2) 

Any host application that uses `WebhookMetadata#shop` (as documented/intended) to look up the target shop's session, records, or to take shop-scoped action, will act on behalf of a shop the attacker does not control — a cross-tenant identity confusion caused entirely by this gem's verification not covering the field it later trusts.

### Impact Explanation
This crosses a tenant boundary using only material the attacker already legitimately possesses (their own valid webhook body+HMAC), without needing the app's `client_secret`, an access token, or any other credential — matching the "Critical: cross-tenant access" impact bar, since the host application is led to process/act on data as though it originated from a shop it did not.

### Likelihood Explanation
Exploitability only requires being a merchant with the vulnerable app installed (an "unprivileged internet user" from the app's perspective) who can trigger or observe one webhook delivery to their own shop, then replay it with a modified `shop-domain` header. No knowledge of the `api_secret_key` is needed because the signature check passes on the unmodified body.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-verified signable content, or otherwise cryptographically bind the shop domain to the verified payload (e.g., require it be embedded and hashed as part of `to_signable_string` in `lib/shopify_api/webhooks/request.rb`), so `Registry.process` cannot be handed a shop value that wasn't covered by the verified HMAC.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and receives a webhook with body `{}` and header `x-shopify-hmac-sha256: <valid-hmac-of-{}>`.
2. Attacker resends this exact body and HMAC to the app's webhook endpoint, replacing `x-shopify-shop-domain: attacker-shop.myshopify.com` with `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because only the body `{}` is checked.
4. The handler receives `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)` and performs shop-scoped action attributed to `victim-shop`, despite the request never having been authenticated for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
