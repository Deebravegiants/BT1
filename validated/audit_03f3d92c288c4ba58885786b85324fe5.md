Audit Report

## Title
Outbound HTTP response cache key omits WorkflowID, allowing cross-workflow response confusion - (File: core/services/gateway/handlers/capabilities/v2/response_cache.go)

## Summary
The gateway's HTTP-action response cache in `responseCache.Fetch`/`Set` keys cache entries by `gateway_common.OutboundHTTPRequest.Hash()`, which includes `WorkflowOwner` but omits `WorkflowID`, contradicting the package's own README claim that "Cache Key: Generated from workflow ID and request hash" and "Workflow Isolation: Cache entries are scoped by workflow ID." This means two distinct workflows sharing the same owner and issuing byte-identical HTTP requests (method, URL, headers, body) can read each other's cached responses.

## Finding Description
`responseCache.Fetch` and `Set` both compute `cacheKey := req.Hash()` [1](#0-0)  and `rc.cache[req.Hash()]` [2](#0-1) , with the struct comment explicitly documenting the hash as derived from "method, URL, headers, body, workflowOwner" — notably omitting `WorkflowID` [3](#0-2) . The test suite in `response_cache_test.go` confirms this behavior directly: `TestRequestHash` shows two requests differing only by `WorkflowID` produce the same hash [4](#0-3) , while requests differing by `WorkflowOwner` produce different hashes [5](#0-4) . This directly contradicts the package README, which documents "Workflow-scoped caching" and states cache entries are "scoped by workflow ID to prevent cross-workflow data leakage" [6](#0-5) [7](#0-6) . The `Hash()` implementation itself lives in the external `chainlink-common` module (`github.com/smartcontractkit/chainlink-common/pkg/types/gateway`) and is not vendored into this repo's index, so its exact implementation could not be directly inspected here, but its documented and tested behavior within this repo is unambiguous and consistent.

## Impact Explanation
This is a genuine logic bug: the code's actual behavior (owner-scoped, not workflow-scoped caching) diverges from its documented security guarantee (workflow isolation), and this is provable purely from first-party code and tests without needing the vendored `Hash()` source. However, the practical severity is constrained:
- The collision requires the **same `WorkflowOwner`** to already be the caller — the cache is not globally shared across arbitrary unprivileged actors, only across workflows the same owner controls/deploys.
- Exploitation additionally requires two workflows under the same owner to issue byte-for-byte identical outbound HTTP requests (method, URL, headers, body) within the cache TTL window, which is a data-shape coincidence, not something one workflow can force onto another's independent execution without owner-level coordination.
- There is no cross-owner leakage demonstrated or plausible from the cited code, since `WorkflowOwner` is part of the hash.

This still constitutes a documented-vs-actual isolation gap that a bounty triager would likely classify as low/informational rather than a high-impact cross-user response corruption, since the "cross-user" boundary (`WorkflowOwner`) is intact; only "cross-workflow" isolation for a single owner's own workflows is broken.

## Likelihood Explanation
Likelihood of accidental triggering is plausible in normal operation (e.g., an owner deploying multiple similar workflow versions using the same HTTP action template with identical parameters), but it is self-inflicted by the workflow owner rather than exploitable by a third party against another user's workflow.

## Recommendation
Include `WorkflowID` in `OutboundHTTPRequest.Hash()` (in the `chainlink-common` module) so cache keys are scoped per workflow, matching the README's documented guarantee. Update `TestRequestHash`'s "having different workflowID results in same Hash" test case in `core/services/gateway/handlers/capabilities/v2/response_cache_test.go` to assert a different hash instead, and correct or remove the misleading README claims if the owner-scoped behavior is intentional.

## Proof of Concept
1. In `response_cache_test.go`, construct `req1` and `req2` via `createTestRequest` with identical `Method`, `URL`, `MultiHeaders`, `Body`, and `WorkflowOwner`, but different `WorkflowID` values (as done in the existing `"having different workflowID results in same Hash"` subtest).
2. Call `req1.Hash()` and `req2.Hash()` — per the existing test, they are equal.
3. Call `cache.Set(req1, resp1)`, then `cache.Fetch(ctx, req2, fetchFn2, true)` before TTL expiry — `fetchFn2` will not be invoked and `resp1` will be returned instead, demonstrating the cross-workflow (same-owner) cache collision.
