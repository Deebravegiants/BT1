## Title
Unbounded `Addresses` (and `Topics` values) in `eth_getLogs` RPC filter enables JSON-RPC DoS - (File: `substrate/frame/revive/rpc/src/receipt_provider.rs`)

## Summary
`pallet-revive-eth-rpc`'s `EthRpcServerImpl::get_logs` forwards a caller-supplied `alloy_rpc_types::Filter` directly to `ReceiptProvider::logs()` with no limit on the number of addresses or per-topic hash values. `ReceiptProvider::logs()` loops over every address and every topic entry, calling `push_bind` once per value to build a dynamic SQL query, with the only length check (`MAX_LOG_RESULTS`) applied to the output rows, not the input filter size.

## Finding Description
`EthRpcServerImpl::get_logs` passes the `Filter` straight through without validation: [1](#0-0) . `ReceiptProvider::logs()` then iterates `filter.address` and each topic slot, binding one SQL parameter per entry with no upper bound before finally applying `MAX_LOG_RESULTS` only to the result limit: [2](#0-1) . By contrast, the `eth_subscribe("logs", …)` path explicitly bounds both addresses and topic values to 1000 entries per slot (max 4 slots) via `BoundedOneOrMany<Address, 1000>` and `BoundedVec<..., ConstU32<4>>`: [3](#0-2) . This confirms the codebase's designers recognized the need to bound filter cardinality for one entry point but omitted it for `eth_getLogs`, which uses the unbounded `alloy_rpc_types::Filter` type. The only remaining control is the generic RPC payload byte-size limit (`--rpc-max-request-size`), which is insufficient because compact 20-byte addresses/32-byte hashes allow packing large numbers of filter values well within typical MB-scale limits.

## Impact Explanation
An unauthenticated client can submit a single `eth_getLogs` request with a very large `address` array and/or many topic values, forcing the node to build and execute a correspondingly large dynamic SQL query (one bound parameter and string-formatting operation per value). Repeated requests can consume disproportionate CPU/query-planning time on the eth-rpc node's JSON-RPC server, degrading availability for legitimate RPC clients of that node. This is a real but node-local availability issue for the Ethereum-compatible RPC front-end of `pallet-revive`; it does not affect on-chain consensus or state.

## Likelihood Explanation
Any client with network access to a public `pallet-revive-eth-rpc` endpoint can trigger this with a single unauthenticated `eth_getLogs` call — no special privileges, governance, or trusted role required. Attack cost is low: one crafted JSON-RPC request containing a large but still byte-size-compliant address/topic array, and it is trivially repeatable.

## Recommendation
Enforce a maximum count on `filter.address` entries and on values within each topic slot inside `EthRpcServerImpl::get_logs` or at the top of `ReceiptProvider::logs()`, returning an RPC error when exceeded — mirroring the 1000-entry/4-slot bound already used for `eth_subscribe("logs", …)` via `BoundedOneOrMany`/`BoundedVec`, applied before the `QueryBuilder` loop runs.

## Proof of Concept
Send `eth_getLogs` with a `Filter` built via `Filter::new().address(vec![...])` populated with a large number (e.g., hundreds of thousands) of distinct addresses, as exercised at small scale in the existing multi-address test: [4](#0-3) . Scaling the address count up drives the unbounded loop at `receipt_provider.rs:776-798` to build and bind a correspondingly large SQL `IN (...)` clause with no cardinality check, consuming excess CPU/time per request while remaining within default JSON-RPC byte-size request limits.
