Audit Report

## Title
Legacy WebAPI Gateway Handler Lacks Allowlist and Rate-Limiting on User Trigger Requests - (File: `core/services/gateway/handlers/capabilities/handler.go`)

## Summary
`HandleLegacyUserMessage` in the legacy WebAPI capability handler performs only signature validation (via `msg.Validate()` at the gateway layer) and a staleness check before fanning a `web_api_trigger` request out to every DON member, with an explicit `// TODO: apply allowlist and rate-limiting here` comment confirming the intended check was never implemented. [1](#0-0)  Any actor who can generate an arbitrary ECDSA keypair, sign a well-formed `web_api_trigger` message, and submit it to the gateway's user-facing HTTP endpoint can trigger unbounded fan-out with no per-sender throttle.

## Finding Description
The gateway's `ProcessRequest` routes legacy requests (identified by a non-empty `DonID`) by decoding the JSON-RPC envelope, calling `msg.Validate()` (which only checks field lengths and recovers a signer address from an ECDSA signature — no allowlist lookup), then dispatching directly to `HandleLegacyUserMessage`: [2](#0-1)  `Message.Validate()` confirms only structural validity and signature recoverability, not membership in any allowlist: [3](#0-2) 

Inside `HandleLegacyUserMessage`, after payload decoding and a staleness check on `payload.Timestamp`, the code proceeds straight past the TODO comment to method validation and then unconditionally saves a callback and broadcasts to every DON member via `SendToNode`: [4](#0-3)  There is no per-sender/per-workflow allowlist or rate-limiter check anywhere in this path — the only rate limiter present in the file, `nodeRateLimiter`, gates the reverse direction (`handleWebAPIOutgoingMessage`, node→gateway traffic), not inbound user requests: [5](#0-4) 

By contrast, the newer v2 HTTP trigger path enforces `authorizeRequest` and `checkRateLimit` (backed by a `userRateLimiter`) before dispatching to nodes, demonstrating the project's own expected security model for user-submitted trigger messages: [6](#0-5) 

Since `Message.Sign` only requires an arbitrary ECDSA private key with no pre-registration, an attacker does not need any privileged credential — merely the ability to generate a keypair and reach the gateway's user endpoint — to pass `Validate()` and reach the unthrottled dispatch logic.

## Impact Explanation
Each valid-but-unthrottled request causes `SendToNode` to be called once per DON member, and inserts an entry into `h.savedCallbacks`, so a scriptable attacker can repeatedly submit distinct `web_api_trigger` messages (new `MessageID`/timestamp each time) with no gateway-side rejection, driving unbounded fan-out load onto every node in the DON and growth pressure on the callback map (bounded only by periodic pruning via `defaultMaxSavedCallbacks`/`defaultCallbackPruneIntervalSec`, not intake throttling). This is a resource-exhaustion/availability impact against the gateway and DON nodes, consistent with an unauthorized-load/DoS impact class rather than fund movement or key exfiltration.

## Likelihood Explanation
High feasibility: the only barrier is generating an ECDSA keypair (trivial, unprivileged) and crafting a valid, non-stale JSON payload — both fully within reach of any external client that can reach the gateway's user HTTP endpoint. The TODO comment left directly in the code path confirms this is a known, unaddressed gap rather than a compensating control implemented elsewhere in this file or at the `gateway.go` routing layer (confirmed by direct reading of `ProcessRequest`).

## Recommendation
Implement the allowlist and rate-limiting logic referenced by the TODO in `HandleLegacyUserMessage` before saving the callback and dispatching to `SendToNode`, mirroring the `authorizeRequest`/`checkRateLimit` pattern used in `core/services/gateway/handlers/capabilities/v2/http_trigger_handler.go`. At minimum, add a per-sender (recovered from `msg.Body.Sender`) or per-workflow token-bucket limiter, consistent with the `nodeRateLimiter` pattern already present in the same file for the reverse direction.

## Proof of Concept
1. Generate an arbitrary ECDSA keypair (no registration required).
2. Construct and sign a `web_api_trigger` `api.Message` with a fresh `MessageID` and current `Timestamp` (as done in `triggerRequest()` helper in `core/services/gateway/handlers/capabilities/handler_test.go`).
3. Submit the message repeatedly (e.g., in a tight loop with distinct `MessageID`s) via `gateway.ProcessRequest` / the gateway's user HTTP endpoint.
4. Observe that every request passes `msg.Validate()` and reaches `SendToNode` for all DON members with no rejection for rate-limit or allowlist reasons — unlike the v2 path's `TestHttpTriggerHandler_HandleUserTriggerRequest_RateLimiting`, which returns `jsonrpc.ErrLimitExceeded` once `userRateLimiter.AllowErr` denies the request.

func (m *Message) Validate() error {
	if m == nil {
		return errors.New("nil message")
	}
	if len(m.Signature) != MessageSignatureHexEncodedLen {
		return errors.New("invalid hex-encoded signature length")
	}
	if len(m.Body.MessageID) == 0 || len(m.Body.MessageID) > MessageIDMaxLen {
		return errors.New("invalid message ID length")
	}
	if strings.HasSuffix(m.Body.MessageID, NullChar) {
		return errors.New("message ID ending with null bytes")
	}
	if len(m.Body.Method) == 0 || len(m.Body.Method) > MessageMethodMaxLen {
		return errors.New("invalid method name length")
	}
	if strings.HasSuffix(m.Body.Method, NullChar) {
		return errors.New("method name ending with null bytes")
	}
	if len(m.Body.DonID) == 0 || len(m.Body.DonID) > MessageDonIDMaxLen {
		return errors.New("invalid DON ID length")
	}
	if strings.HasSuffix(m.Body.DonID, NullChar) {
		return errors.New("DON ID ending with null bytes")
	}
	if len(m.Body.Receiver) != 0 && len(m.Body.Receiver) != MessageReceiverLen {
		return errors.New("invalid Receiver length")
	}
	signerBytes, err := m.ExtractSigner()
	if err != nil {
		return err
	}
	m.Body.Sender = utils.StringToHex(string(signerBytes))
	return nil
}
