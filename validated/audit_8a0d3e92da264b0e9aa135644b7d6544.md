### Title
Webhook shop identity is trusted from an unauthenticated header while the HMAC only covers the request body - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body for HMAC verification, but the `shop`, `topic`, `webhook_id`, and `api_version` values used by `Registry.process` to build the `WebhookMetadata` passed to the app's business logic are taken from HTTP headers that are never part of the signed payload. The binding the gem should enforce — "the shop the handler acts on" == "the shop the signature attests to" — is broken.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

But `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers, which are entirely outside the HMAC computation: [2](#0-1) 

`Utils::HmacValidator.validate` recomputes the HMAC solely from `verifiable_query.to_signable_string` (i.e. the raw body) and compares it against `request.hmac`: [3](#0-2) 

`Registry.process` then uses this same, header-derived `request.shop` — never cross-checked against the signed body — to construct the `WebhookMetadata` object dispatched to the app's handler: [4](#0-3) 

This is exactly the "field acted on but not covered by the HMAC" pattern: the equality the gem is supposed to guarantee is `hmac_signed_bytes ⊇ {shop, topic}`, but in reality `hmac_signed_bytes == {raw_body}` while `{shop, topic}` are attacker-controllable header values with no cryptographic tie to the body or to each other. Any request whose body+HMAC pair is valid for the configured `api_secret_key` (i.e. any previously-observed genuine webhook delivery for the app) can be replayed to the app's single, shared webhook endpoint with an arbitrary `shopify-shop-domain` header substituted in, and `Utils::HmacValidator.validate` will still return `true` because it never inspects headers.

### Impact Explanation
Because the webhook endpoint is shared across all tenants (shops) of a multi-tenant app, and shop attribution is taken from an unauthenticated header, this breaks the shop-authenticated-vs-shop-acted-upon binding at the heart of multi-tenant isolation. A handler that trusts `WebhookMetadata#shop` (as the gem's own test suite and documented usage pattern encourage — see `handler.handle(data: WebhookMetadata.new(topic: ..., shop: request.shop, ...))`) can be made to process a payload while believing it originates from a different shop than the one whose data is actually in the body, enabling cross-tenant data injection/misattribution in the app built on top of this gem.

### Likelihood Explanation
Exploitation requires the attacker to already possess one valid `(raw_body, hmac)` pair for the app (e.g., from a webhook delivered for their own installed shop instance, or any other endpoint reachable to them), which is achievable without ever learning `api_secret_key`, since the HMAC check only validates body integrity and does not bind it to any particular shop or topic. The barrier is moderate (need one genuine signed sample), not "confidential-credential" high, and no privileged account, TLS interception, or social engineering is required — only the ability to send an HTTP POST to the app's public webhook route.

### Recommendation
Include the shop domain (and ideally the topic) in the signed payload construction that is compared to the HMAC — e.g. Shopify's webhook HMAC is computed over the exact raw body received, which is fine, but the *application-level* trust boundary should not conflate "signature is valid for this body" with "this body's out-of-band headers are trustworthy." Concretely:
- Verify the `shop-domain` header value is consistent with a shop your app has installed/tracks a valid session/webhook subscription for before dispatching to handlers, or
- Have `Registry.process` reject webhooks whose `shop-domain` header does not match a shop for which the currently configured `api_secret_key` is authoritative and for which the topic/body was actually generated (Shopify does not embed shop into the signed bytes, so the gem should treat the header shop as provisional and require callers/handlers to re-validate shop ownership before trusting it for tenant-scoped operations), and document this limitation explicitly for consumers of `WebhookMetadata#shop`.

### Proof of Concept
1. App registers a webhook handler via `ShopifyAPI::Webhooks::Registry.add_registration` and exposes a controller that calls `ShopifyAPI::Webhooks::Registry.process(request)` as documented.
2. Attacker obtains (through any means not requiring `api_secret_key` — e.g. a webhook delivery captured for a shop they control) one valid pair: `raw_body = "{...order payload...}"`, `hmac = <valid signature for that body under api_secret_key>`.
3. Attacker POSTs to the app's public webhook endpoint with the same `raw_body`/`x-shopify-hmac-sha256` header, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` instead of their own shop's domain.
4. `Utils::HmacValidator.validate` in `lib/shopify_api/utils/hmac_validator.rb:26-31` returns `true` (only the body is checked).
5. `Registry.process` (`lib/shopify_api/webhooks/registry.rb:188-199`) builds `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and dispatches it to the app handler, which now attributes attacker-controlled body content to the victim shop.
