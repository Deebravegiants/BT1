### Title
Missing `request.from` (module-id) validation in `onAccept` lets any Hyperbridge-chain sender impersonate the trusted pallet - ([File: evm/src/apps/BandwidthManager.sol])

### Summary
`BandwidthManager.onAccept` (and the "only-hyperbridge" branch of `ExtrinsicIntents.onAccept`) authorize privileged, fund-moving/config-changing actions by checking only that `PostRequest.source` equals the Hyperbridge state machine. Neither checks `PostRequest.from`, i.e. which specific pallet/module on that chain actually dispatched the message. This is directly analogous to CVE-2019-5773: the check validates the coarse "origin" (which chain) but not the fine-grained "origin" (which module on that chain) — same bug class as IndexedDB validating only that a request came from *some* renderer process without checking it came from the *correct* origin.

### Finding Description
`onAccept` in `evm/src/apps/BandwidthManager.sol:208-232` gates two privileged actions — `SetTiers` (price manipulation) and `Withdraw` (arbitrary token/native transfer to attacker-chosen `beneficiary`) — behind a single check: [1](#0-0) 

`request.source.equals(IDispatcher(_host).hyperbridge())` only proves the message came from the Hyperbridge state machine as a whole. It never checks `request.from` against `PALLET_BANDWIDTH_MODULE_ID` (`"BWMARKET"`), even though that constant is declared exactly for this purpose: [2](#0-1) 

Contrast this with the token-bridge apps in the same codebase, which correctly validate both the source chain *and* the specific sender module (`request.from`) before trusting an inbound message: [3](#0-2) 

The same missing-`from`-check pattern also appears in `ExtrinsicIntents.onAccept`'s Hyperbridge-privileged branch, which gates `NewDeployment`, `UpdateParams`, `SweepDust`, and `Execute` (a delegatecall into the current implementation, giving access to host-only functions): [4](#0-3) 

On the Substrate side, ISMP `PostRequest.from` is normally set by the dispatching pallet's fixed module id (e.g. `EXAMPLE_MODULE_ID.to_bytes()` in the docs' example dispatcher), not chosen freely by the extrinsic caller. That means the vulnerability is not "any user can forge `from`" — it's "any *other module/pallet* deployed on the Hyperbridge chain (or a future one, or one reachable via the router/proxy path) that can dispatch an ISMP Post request to this EVM contract's address will be accepted as if it were `pallet-bandwidth` or the intents coprocessor," since the destination contract enforces zero constraint on `from`.

### Impact Explanation
If a message reaches `BandwidthManager.onAccept` with `source == hyperbridge` and any `from` value, the contract will process `Withdraw`, transferring the specified `amount` of `token` (or native currency) to an attacker-chosen `beneficiary` — a direct theft of the escrowed treasury/fee-token balance held by `BandwidthManager`. `SetTiers` similarly lets a wrong sender permanently corrupt pricing. In `ExtrinsicIntents`, the analogous gap permits `Execute` (arbitrary delegatecall reachable through the proxy's implementation) or `NewDeployment`/`UpdateParams` to be triggered by any Hyperbridge-side sender that isn't the intended governance/coprocessor pallet, which can corrupt gateway configuration or facilitate escrow theft. This satisfies "concrete theft ... of funds" and "unauthorized app action."

### Likelihood Explanation
Exploitability depends on whether any other pallet, extrinsic, or the generic ISMP router/proxy path on the Hyperbridge/nexus chain can dispatch a `PostRequest` targeting these EVM contract addresses with a `from` different from the expected module id. I was not able to conclusively confirm from the index whether such a permissionless dispatch path currently exists in the nexus runtime (e.g., a generic user-facing "dispatch arbitrary ISMP message" extrinsic), so likelihood is uncertain without deeper runtime enumeration. However, the missing check is a genuine defense-in-depth gap relative to the codebase's own established pattern (every token-bridge `onAccept` validates `from`), and any future pallet or router misconfiguration that allows dispatching with an unexpected `from` would immediately be exploitable with no additional barrier.

### Recommendation
Add an explicit `request.from` check in `BandwidthManager.onAccept` against `PALLET_BANDWIDTH_MODULE_ID`, mirroring the pattern already used in `HyperFungibleToken.onAccept` and `WrappedHyperFungibleToken.onAccept`. Apply the same fix to the Hyperbridge-privileged branch of `ExtrinsicIntents.onAccept`/`IntentGatewayV2.onAccept` by validating `request.from` against the specific known coprocessor/governance module id, not just `request.source`.

### Proof of Concept
Conceptual (cannot be fully executed without confirming a reachable dispatcher on the Hyperbridge chain with attacker-influenced `from`):
1. Identify or introduce (via an existing generic ISMP-dispatch pallet on Hyperbridge, if one exists) a way to dispatch a `PostRequest` with `source = hyperbridge`, `to = <BandwidthManager address>`, and `from` set to any module id other than `"BWMARKET"`.
2. Set `body = abi.encodePacked(OnAcceptActions.Withdraw, abi.encode(Withdrawal({token: feeToken, beneficiary: attacker, amount: contractBalance})))`.
3. Relay through `HandlerV2.handlePostRequests` → `IHost.dispatchIncoming` → `BandwidthManager.onAccept`, which will pass the `request.source == hyperbridge` check and drain the treasury to `attacker`. [5](#0-4)
