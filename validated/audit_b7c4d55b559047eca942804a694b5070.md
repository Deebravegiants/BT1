### Title
Excess native-token payment to `EvmHost.dispatch()`/`fundRequest()` is refunded to the host contract instead of the caller, permanently freezing funds - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept `msg.value` and swap it for the exact required amount of `feeToken()` via `swapETHForExactTokens`. Because this is an *exact-output* swap, any leftover native token (`msg.value - amountSpent`) is refunded by the router/wrapper — but the refund is sent back to `msg.sender` **of the router call**, which is `EvmHost` itself (since `EvmHost` is the direct caller of the router), not to `_msgSender()` (the account/contract that actually paid the ETH). No code path afterwards forwards this leftover balance back to the original caller, so the excess ETH is permanently stranded in the `EvmHost` contract.

### Finding Description
In `dispatch(DispatchPost)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

`swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), ...)` requests exactly `post.fee` output tokens for the router, and pays for it with up to `msg.value` ETH. The wrapper implementations in this repo (e.g. `UniV3UniswapV2Wrapper.swapETHForExactTokens`, `UniV4UniswapV2Wrapper.swapETHForExactTokens`) correctly refund unspent ETH back to `msg.sender`: [4](#0-3) [5](#0-4) 

However, `msg.sender` in that context is `EvmHost` — the contract that called the router — not the account/app that called `EvmHost.dispatch()`. None of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` reads back the wrapper's refund and forwards it to `_msgSender()`. The excess native token therefore accumulates as trapped ETH balance inside `EvmHost`, with no code in this function (or found in the rest of `EvmHost.sol`) that returns it to the payer.

This is the direct structural analog of the reported `UniERC20.uniTransferFrom` bug: excess value supplied above the exact required amount is not returned to the sender, but ends up somewhere it should not (destination in the 1inch case; the intermediary host contract itself in this case) — resulting in silent, permanent loss of user funds.

By contrast, the intent-gateway contracts (`IntentGatewayV2.sol`, `ExtrinsicIntents.sol`) that call the Uniswap wrappers directly get their own refund correctly (since they are `msg.sender` to the wrapper) and subsequently forward any additional unspent `msgValue` back to `msg.sender`/the user: [6](#0-5) 
This confirms the pattern is understood and applied correctly elsewhere, but is missing specifically in `EvmHost`'s own `dispatch`/`fundRequest` entry points.

### Impact Explanation
Any external caller — including end users calling `dispatch()` directly, or integrator apps like `HyperbridgeLzEndpoint.send()` which forwards raw `msg.value` straight into `IDispatcher(_host).dispatch{value: msg.value}(request)`: [7](#0-6) 
— will lose any ETH sent above the exact amount consumed by the swap. Because `swapETHForExactTokens` is exact-output, overpayment is the expected/likely case (callers typically supply a buffer since they cannot know the exact router price at call time — the LZ endpoint's own `quote()` explicitly applies a 2x buffer expecting the excess to be refunded). This results in permanent freezing/loss of user funds with no recovery path visible in `EvmHost.sol`.

### Likelihood Explanation
High likelihood: this triggers on essentially every native-token-funded `dispatch()`/`fundRequest()` call where the caller doesn't supply the *exact* wei amount the AMM will consume — which is the normal, expected usage pattern (callers pad `msg.value` for slippage, as evidenced by `HyperbridgeLzEndpoint.quote()`'s explicit 2x buffer comment: "Excess native is refunded by the uniswap router"). No malicious actor or privileged role is required — it's triggered by an ordinary unprivileged relayer/app/user transaction.

### Recommendation
After the `swapETHForExactTokens` call in `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, compute the actual amount spent (as returned by the wrapper, or via before/after `address(this).balance` delta) and forward any remaining `msg.value` back to `_msgSender()` with a low-level `call`, following the same pattern already used correctly in `IntentGatewayV2.sol` (`_sendValue(msg.sender, msgValue)`).

### Proof of Concept
1. Deploy `EvmHost` with a configured `uniswapV2` router and `feeToken`.
2. An app (e.g. `HyperbridgeLzEndpoint`) calls `IDispatcher(host).dispatch{value: X}(post)` where `X` is intentionally padded above the AMM's actual required input for `post.fee` output tokens (as is normal/expected practice, per the LZ endpoint's own buffering logic).
3. Inside `dispatch`, `swapETHForExactTokens{value: X}(post.fee, path, address(this), ...)` spends only `Y < X` ETH and refunds `X - Y` to `msg.sender`, which is `EvmHost`.
4. `dispatch` returns without ever moving `X - Y` back to the original caller; `EvmHost`'s ETH balance permanently increases by `X - Y`, unreachable by the payer.
