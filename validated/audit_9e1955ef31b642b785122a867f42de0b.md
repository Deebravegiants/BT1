### Title
Optional (bypassable) slippage protection in `Deposit` and `Withdraw` instructions enables sandwich attacks - (File: program/src/instruction.rs, program/src/processor.rs)

### Summary
Unlike the four swap instructions (`SwapBaseIn`, `SwapBaseOut`, `SwapBaseInV2`, `SwapBaseOutV2`), which always decode a mandatory slippage bound and unconditionally enforce it, the `Deposit` and `Withdraw` instructions accept their slippage-protection fields (`other_amount_min`, `min_coin_amount`, `min_pc_amount`) as `Option<u64>` that are only populated if the caller includes the extra trailing bytes in the instruction data.

### Finding Description
For swaps, `minimum_amount_out`/`max_amount_in` are non-optional `u64` fields that are always compared against the computed output/input and rejected with `AmmError::ExceededSlippage` if violated: [1](#0-0) [2](#0-1) 

By contrast, the `Deposit` and `Withdraw` instructions decode their protective bounds only when extra trailing bytes are present in the instruction payload, otherwise the value defaults to `None`: [3](#0-2) 

The struct definitions confirm these fields are optional by design: [4](#0-3) 

Since an attacker submits their own transaction (or constructs the instruction data for any of these fields), any caller (or any front-end/integrator) that omits the trailing `other_amount_min`/`min_coin_amount`/`min_pc_amount` bytes causes the pool to skip the slippage check entirely for that add/remove-liquidity call — mirroring the root cause described in the external report, where `UniswapHandler` passed `0` as `amountOutMin`, always accepting any executed price. An MEV searcher watching the mempool can sandwich such an unprotected `Deposit`/`Withdraw` transaction: manipulate the coin/pc vault ratio immediately before and after the victim's transaction to force the LP token mint/burn math (and thus real underlying token amounts) to be computed at an unfavorable price, extracting value from the depositor or withdrawer.

### Impact Explanation
An LP performing `Deposit` or `Withdraw` without setting `other_amount_min`/`min_coin_amount`/`min_pc_amount` (i.e., relying on the default `None` path many clients/integrators may take, exactly as `UniswapHandler` relied on `0`) has no on-chain guarantee about the token amounts they receive or lock. A sandwiching attacker can shift the vault ratio before the call lands and revert it after, causing the victim to deposit disproportionately more of one token or receive fewer tokens back on withdrawal than the fair-price amount — a direct value transfer from LP to attacker, i.e. concrete loss of LP funds.

### Likelihood Explanation
This is reachable from a single unprivileged transaction with attacker-chosen accounts and instruction data (front-running a `Deposit`/`Withdraw` observed in the mempool with `SwapBaseIn`/`SwapBaseOut`), requiring no special privileges and no cooperation from the victim beyond calling the instruction without slippage protection — a realistic scenario since the check is opt-in rather than mandatory.

### Recommendation
Make slippage protection mandatory for `Deposit` and `Withdraw` (as it is for swaps): require `other_amount_min`/`min_coin_amount`+`min_pc_amount` to always be present in the instruction data and always enforce them, rather than allowing an `Option::None` path that silently skips the check.

### Proof of Concept
1. Attacker monitors mempool for a `Deposit` (or `Withdraw`) instruction whose data length matches the "no min amount supplied" case, i.e. `rest.len() < 8` for `Deposit` or `rest.len() < 16` for `Withdraw` per the unpack logic [3](#0-2) , meaning `other_amount_min`/`min_coin_amount`/`min_pc_amount` will resolve to `None` and no `ExceededSlippage` check will be applied downstream.
2. Attacker front-runs with a large `SwapBaseIn`/`SwapBaseOut` to skew the coin/pc vault ratio in the direction that will make the upcoming Deposit/Withdraw unfavorable to the victim.
3. Victim's `Deposit`/`Withdraw` executes at the skewed ratio with no `other_amount_min`/`min_coin_amount`/`min_pc_amount` protection.
4. Attacker back-runs with an opposite `SwapBaseIn`/`SwapBaseOut` to restore the ratio and realize profit, extracted from the victim's deposit/withdrawal.
