### Title
Controller authorization is bound to the stale stored `Account.owner`, not the live position-NFT owner — NFT transfer does not relocate the authority it authenticates - (File: contracts/controller/src/account.rs)

### Summary
The lending protocol represents each account as a position NFT whose `token_id` is the `account_id`, and the NFT's `owner_of` is documented as the account owner (`contracts/position-nft/src/contract.rs`, line 2). However, all funds-moving entrypoints on the controller (`process_withdraw`, `process_borrow`, `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, `multiply`, `migrate_from_blend`) authenticate via `require_owner_or_delegate`, which compares the caller against `account.owner` — a field frozen in the stored `Account` struct at account creation (`create_account`, `account.rs:64`) — rather than the NFT's current `owner_of`. This is the direct analog of the SAML signature-relocation bug: the "signature" (caller auth) is checked against a field that is not bound to the data it protects (the actual NFT ownership), so transferring the NFT leaves authorization attached to the *old* holder.

### Finding Description
`Account.owner` is set once in `create_account` (`account.rs:64-70`) and never resynchronized. The position NFT is a stock OpenZeppelin enumerable token (`contract.rs:132-133`) — its `transfer`/`transfer_from` update only NFT-side `Owner`/`Balance` entries and invoke no callback into the controller. Consequently:

- `require_owner_or_delegate` (`account.rs:130-140`) → `is_owner_or_delegate` (`account.rs:121`) returns true for `caller == account.owner`, i.e., the *original minter*, forever.
- A separate function, `require_account_owner` (`account.rs:143-148`), checks `storage::account_owner(env, account_id)` — the live NFT owner — and is used only by `renew_account` and `set_account_delegate`, confirming the codebase maintains two divergent notions of "owner".
- `process_withdraw` (`supply.rs:149-150`) and `process_borrow` (`debt.rs:42-43`) load the stored account and gate on `account.owner`, so after `position_nft.transfer(owner, buyer, token_id)` the *seller* still passes authorization while the *buyer* (NFT holder) does not. Delegates are likewise keyed under the stale owner via `get_delegates(env, account_id, owner)` (`account.rs:126`).

### Impact Explanation
Theft of user funds plus permanent freezing of funds:

- The previous NFT holder can `withdraw(account_id, withdrawals, to=Some(self))` — `to` is attacker-chosen (`supply.rs:145-152`) — draining all collateral of an account they already sold, or `borrow` to an arbitrary `to` (`debt.rs:38-47`) and leave the debt on the buyer's position.
- The legitimate new NFT owner cannot call `withdraw`, `borrow`, `swap_collateral`, or liquidation-receiver flows gated by `require_owner_or_delegate`, and cannot even `add_delegate`/`renew_account` against the stale `account.owner` path — their collateral and any unclaimed yield are locked while the ex-owner retains full control. Selling or moving a position (the entire purpose of the NFT wrapper) hands the buyer a key to a door that still opens only for the seller.

### Likelihood Explanation
An unprivileged user needs only: (1) own an account with collateral, (2) call `position_nft.transfer` to any address (a listed, in-scope entrypoint), and (3) as the original owner, call `withdraw` — no admin, no timing, no price manipulation. The divergence is structural: nothing in `process_supply`/`process_withdraw`/NFT `transfer` writes `account.owner`. Caveat: I could not read `storage/account.rs` contents to confirm whether `get_account` repopulates `owner` from the NFT contract on load rather than trusting the stored field; the Account struct's persisted `owner` field and the existence of a distinct `require_account_owner`/`storage::account_owner` check strongly indicate the stored value is authoritative, but if `get_account` re-resolves it from `owner_of`, this finding collapses to a non-issue and the auth path is consistent.

### Recommendation
Resolve ownership from a single source of truth. Either (a) have `storage::get_account` / `require_owner_or_delegate` consult the position NFT's `owner_of(account_id)` instead of the stored `account.owner` field, dropping `Account.owner` entirely; or (b) make NFT `transfer`/`transfer_from` call back into the controller to restamp `account.owner` and re-key delegate storage (`get_delegates`/`add_delegate` entries are stored per `(account_id, owner)` and would otherwise remain bound to the seller). Add a regression test: mint account → transfer NFT → assert new owner can `withdraw` and old owner reverts with `NotAuthorized`.

### Proof of Concept
1. Alice calls `supply(account_id=0, spoke_id=1, [(XLM, 1000)])`; controller mints NFT id `N` to Alice and stores `Account { owner: Alice, ... }` (`account.rs:62-70`, `supply.rs:51-63`).
2. Alice sells the position off-protocol and calls `position_nft.transfer(alice, bob, N)`. NFT `owner_of(N)` is now Bob; `account.owner` is still Alice — no hook updates it (`contract.rs:132-133` delegates to stock OZ transfer).
3. Bob calls `withdraw(account_id=N, withdrawals=[(XLM, 0 /*all*/)], to=bob)` → `require_owner_or_delegate` sees `caller=Bob != account.owner=Alice` → `NotAuthorized` (`supply.rs:149-150`, `account.rs:121-139`). Bob's funds are frozen.
4. Alice calls the same `withdraw` with `to=alice` → `caller == account.owner` → collateral is paid to Alice (`supply.rs:152-157`, `debt.rs` analog for `borrow` which can also mint unbacked debt onto Bob's NFT position). Alice retains full spend authority over a position she no longer owns.
