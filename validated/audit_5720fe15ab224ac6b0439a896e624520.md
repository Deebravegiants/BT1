### Title
Webhook Tenant/Topic Confusion via Unauthenticated Headers Outside HMAC Scope - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the `shop`, `topic`, `api_version`, and `webhook_id` values used to route and attribute the webhook are read directly from unauthenticated HTTP headers that are never included in the signed content. This breaks the identity binding `HMAC-authenticated bytes == the shop/topic the payload is attributed to`, letting anyone who can obtain one validly-signed webhook body (e.g. by triggering a webhook on their own, attacker-controlled shop, since all shops installed on an app share the same `client_secret`/HMAC key) replay that body to the app's webhook endpoint while forging the `shop-domain` (and `topic`) header to point at a victim shop.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes and compares an HMAC over `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` is defined as just the raw body: [2](#0-1) 

Meanwhile `shop`, `topic`, `api_version`, and `webhook_id` are all parsed straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the signature at all: [3](#0-2) 

`Registry.process` validates only the HMAC and then dispatches the (unauthenticated) `shop`/`topic`/`webhook_id` values straight to the host application's handler as trusted tenant/topic identity: [4](#0-3) 

Because Shopify signs webhook bodies with the app's single `client_secret` regardless of which installed shop triggered the event, a validly HMAC'd `(raw_body, hmac)` pair obtained from any shop using the app (including one the attacker controls) remains valid for **any** header combination the attacker chooses to send it with — the HMAC never covers `shop`, `topic`, `api_version`, or `webhook_id`. This lets an attacker replay a signed payload from their own shop while spoofing the `shop-domain` header to a victim shop's domain, causing the handler to process attacker-supplied data under a victim tenant's identity — a direct cross-tenant confusion, structurally analogous to the reported bug where a value (`totalVoting`) that determines financial/authorization outcomes is derived from unauthenticated/unbound state rather than the value that was actually verified.

### Impact Explanation
This crosses a tenant/authentication boundary: the handler is told a webhook came from shop X and asserts that identity to the rest of the application (e.g. triggering per-tenant side effects, provisioning, data updates) purely on the strength of an unauthenticated header, while the only cryptographically verified fact is "some shop on this app produced this exact byte sequence." This matches the "Manipulation ... resulting in ... cross-tenant access" / credential-boundary-crossing impact class.

### Likelihood Explanation
Exploitation requires the attacker to be able to trigger at least one legitimately signed webhook delivery to the target app (trivial if the app is installable by anyone, e.g. any merchant who installs the app can trigger webhooks for their own shop) and to be able to send an arbitrary HTTP POST to the app's public webhook endpoint with modified headers — both are unprivileged, internet-reachable actions requiring no access token, no `api_secret_key`, and no privileged account.

### Recommendation
Bind the tenant/topic identity into the authenticated content instead of trusting unauthenticated headers: include `shop`, `topic`, `api_version`, and `webhook_id` (or at minimum `shop` and `topic`) inside `to_signable_string` (or otherwise cryptographically bind them, e.g. by having the handler independently confirm the shop against a known/installed-shop store keyed by more than the raw header), so a payload signed for one shop/topic combination cannot be replayed under a different one.

### Proof of Concept
1. Install the app on an attacker-controlled shop `attacker.myshopify.com`. Trigger any webhook topic the app subscribes to (e.g. update a product) so Shopify sends a legitimately HMAC-signed webhook: `raw_body`, `X-Shopify-Hmac-Sha256`, `X-Shopify-Topic: products/update`, `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Capture `(raw_body, hmac)`.
3. Replay the exact same `raw_body` and `hmac` to the app's public webhook endpoint, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally change `X-Shopify-Topic` to another registered topic).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `raw_body` against `hmac` — it never inspects `shop` or `topic`: [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"`, processing attacker-controlled data attributed to the victim tenant.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

          end
        end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
