### Title
Webhook shop identity not covered by HMAC signature enables cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` signs only the raw request body when validating the Shopify webhook HMAC, while the tenant-identifying `shop` (and `topic`/`webhook_id`) values are read straight from unauthenticated HTTP headers. `Registry.process` trusts these header-derived values once the body signature checks out, so a legitimate app installer on one shop can replay a genuinely-signed webhook body while swapping the shop header to impersonate a different shop that uses the same app.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

while `shop`, `topic`, `api_version`, and `webhook_id` are pulled directly from HTTP headers with no cryptographic binding to the signed bytes: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the HMAC solely over `to_signable_string` (the body): [3](#0-2) 

`Registry.process` validates the HMAC and then unconditionally trusts `request.shop`/`request.topic` to dispatch the handler: [4](#0-3) 

This breaks the identity binding: `HMAC-validated bytes == raw_body` but `shop used for tenant routing == unauthenticated header`, an equality that should hold but does not. Any merchant that installs the app on their own store receives real Shopify-signed webhooks (signed with the app's shared `client_secret`, not a per-shop secret). Because the signature never covers the `shop-domain` header, that attacker can capture one legitimately-signed `(raw_body, hmac)` pair from their own shop and replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` header (and optionally `topic`/`webhook-id`) rewritten to name a victim shop that also installed the app. `HmacValidator.validate` still succeeds since it only checks body bytes, so `Registry.process` calls the registered handler with `WebhookMetadata.new(shop: request.shop, ...)` pointing at the victim tenant while carrying attacker-controlled body content.

### Impact Explanation
This crosses a tenant boundary without needing the app's `client_secret`, access token, or any privileged credential — only the ability to install the app on one's own store (i.e., an unprivileged internet user with respect to other merchants). The attacker can forge or replay webhook events (e.g., `orders/create`, `customers/data_request`, `app/uninstalled`) attributed to a shop they do not own, causing the host application to perform tenant-scoped side effects (data writes, deletions, notifications, session/token revocation flows) against the victim's tenant. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Exploitation requires no secret material: the attacker only needs to be a legitimate installer of the same public app on their own store (freely obtainable) and the ability to capture/replay one webhook body+HMAC pair while editing the shop header of the replayed HTTP request — both trivial for any external actor targeting a multi-tenant app built on this gem.

### Recommendation
Bind the shop identity (and topic/webhook id) into the signed material, or independently verify that `request.shop` corresponds to a shop session that the receiving app actually manages before dispatching the handler. At minimum, document and enforce that consumers of `Webhooks::Registry.process` must cross-check `request.shop` against a known/authorized shop list rather than trusting the header outright once HMAC-on-body succeeds.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` and receives a real webhook, e.g. body `{"foo":"bar"}` with header `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>` and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
2. Attacker resends the exact same body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks the (unchanged) body against the (unchanged) HMAC and returns `true` — see [5](#0-4) .
4. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: {"foo"=>"bar"}, ...)`, causing the host app to process attacker-controlled data as if it originated from `victim-shop.myshopify.com`.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
