### Title
`handle_unsigned` charges a fixed, batch-size-independent weight for arbitrarily large ISMP message batches, letting a single unsigned extrinsic starve block execution - ([File: modules/pallets/ismp/src/lib.rs])

### Summary
`pallet_ismp::Pallet::handle_unsigned` is declared with a *static* weight (`weight()` → `Weight::from_parts(300_000_000, 0)`), independent of how many `Message`s (and how many `PostRequest`/`GetResponse`/timeout entries inside each message) are submitted in the `Vec<Message>` payload. Because this call is unsigned (`ensure_none(origin)`), reachable by anyone (a relayer submitting a proof), and there is no visible bound on the number of requests/responses per message or messages per batch, an attacker can submit one call whose *declared* weight is trivial but whose *actual* execution cost (proof verification, hashing every request, dispatching to modules, storage child-trie writes) is far larger than what the runtime accounted for when building the block. ### Finding Description
`handle_unsigned` is the dispatchable that executes ISMP message batches for free, since it is meant to be validated purely by proof-checking in `validate_unsigned`, not by weight-based fees: [3](#0-2) 

Its weight annotation is a fixed constant regardless of `messages.len()` or the size of the individual `RequestMessage.requests` / `ResponseMessage.requests` / `TimeoutMessage` vectors carried inside those messages: [4](#0-3) 

The comment even acknowledges this is a placeholder ("Static weights because these should get overridden by the FeeHandler") but the `#[pallet::weight(weight())]` attribute is what `frame_system::CheckWeight` and the block builder actually use to reserve room in the block *before* execution — the real accrued weight (`total_weights` tracked inside `handlers::request/response/timeout`) is only used post-hoc for fee accounting via `T::FeeHandler::on_executed`, not to pre-emptively bound how much work the extrinsic is allowed to perform relative to the remaining block weight.

Execution itself does real per-item work with no visible cap on batch size: `Pallet::execute` maps `handle_incoming_message` over every message in the `Vec<Message>`, and each request/response handler (`modules/ismp/core/src/handlers/request.rs`, `response.rs`, `timeout.rs`) iterates every entry, hashing it, verifying membership/non-membership proofs, and invoking the destination module's callback: [5](#0-4) [6](#0-5) 

A search of `modules/ismp/core` turned up no `MaxRequests`/`BoundedVec` style cap on the number of requests per `RequestMessage`/`ResponseMessage`, nor on the number of `Message`s per `handle_unsigned` call — the only size gate found in the codebase is in the unrelated `pallet-call-decompressor`, which bounds total *compressed call bytes*, not the semantic batch size accepted directly by `pallet-ismp`'s own extrinsic.

This mirrors the CVE-2020-36311 bug class: in the kernel, `sev_vm_destroy` iterated over an attacker-influenced, effectively unbounded number of encrypted regions inside a single syscall whose accounted cost did not reflect the real work, causing a soft lockup. Here, a single unsigned `handle_unsigned` extrinsic can iterate over an attacker-controlled, effectively unbounded number of requests/responses while the runtime's weight accounting (used to decide how much of the block this call may consume before letting other extrinsics run) is a fixed constant that does not scale with that count.

### Impact Explanation
Because `CheckWeight`/the block-authoring logic reserve space based on the declared (fixed) weight rather than the true cost, a maliciously large but otherwise validly-proved batch can consume block execution time far beyond what was budgeted, at zero fee (the call is unsigned/free). This can:
- Cause the block to overrun its execution budget, risking block production stalls or the collator failing to finish the block in time (a chain-level denial-of-service analogous to the kernel soft lockup).
- Crowd out other pending ISMP messages from being included/processed in the same or following blocks, effectively making the message route "unable to deliver messages" for the affected window, since capacity is monopolized by one oversized, underpriced batch.

This does not directly enable theft or forged proofs (the proof/membership checks still apply per item), but it is a genuine availability threat to Hyperbridge's core message-delivery path (`pallet-ismp`'s `handle_unsigned`), which is the same "reachable by anyone (unprivileged relayer)" surface named in scope.

### Likelihood Explanation
Likelihood is moderate-to-high: submitting the extrinsic requires only valid consensus/state proofs and a set of requests/responses that pass `verify_membership`/`verify_non_membership` — an attacker with normal relayer capability can construct large batches of legitimately-proved but low-value or otherwise-controlled requests (e.g. many GET requests they control from a source chain) with no on-chain gate preventing an arbitrarily large `Vec<Message>` or `Vec<PostRequest>`/`Vec<GetRequest>` from being submitted in a single unsigned call. The `#[frame_support::transactional]` wrapper does not limit size, only atomicity.

### Recommendation
Make the declared `#[pallet::weight(...)]` for `handle_unsigned` scale with the actual batch shape (number of messages × per-message request/response count), similar to how `pallet_assets`'s `destroy_accounts`/`destroy_approvals` weights scale with their component counts, and/or enforce an explicit maximum on `messages.len()` and on the number of requests/responses per message (via `BoundedVec` or an explicit `ensure!` check) before proof verification and dispatch begin.

### Proof of Concept
Not independently reproduced (would need a running parachain node to observe actual block-time overrun); the structural evidence is:
1. `#[pallet::weight(weight())]` on `handle_unsigned` where `weight()` is a compile-time constant unrelated to `messages` size — `modules/pallets/ismp/src/lib.rs:370,727-730`.
2. `Pallet::execute` iterates `messages` with no length cap — `modules/pallets/ismp/src/impls.rs:40-51`.
3. Existing test files (`modules/pallets/testsuite/src/tests/pallet_call_decompressor.rs`) already construct batches with hundreds of `PostRequest`/`GetRequest` entries in a single `handle_unsigned` call for other test purposes, showing the batch shape is entirely attacker/relayer controlled and not rejected for size at that layer.

Note: I could not fully verify within the available context whether some upstream size limit exists elsewhere (e.g., at the P2P/transaction-pool layer restricting extrinsic byte size, which would partially mitigate this). This would need further confirmation in a live/full codebase review.

impl<T: Config> Pallet<T> {
	/// Execute the provided ISMP datagrams, this will short circuit if any messages are invalid.
	/// This also charges fee on valid message delivery
	pub fn execute(messages: Vec<Message>) -> Result<Vec<events::Event>, Error<T>> {
		let host = Pallet::<T>::default();

		let message_results = messages
			.iter()
			.map(|msg| handle_incoming_message(&host, msg.clone()))
			.collect::<Result<Vec<_>, _>>()
			.map_err(|err| {
				log::debug!(target: "ismp", "Handling Error {:#?}", err);
				Pallet::<T>::deposit_event(Event::<T>::Errors { errors: vec![err.into()] });
				Error::<T>::InvalidMessage
			})?;
