### Title
Unchecked ERC20 return value in escrow withdrawal allows silent transfer failure and permanent loss of escrowed funds - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The reported bug flags `transferFrom` instead of `safeTransferFrom` as unsafe because it does not verify the transfer actually succeeded for the recipient, risking permanent token loss. The Tron variant of `IntentGatewayV2` exhibits the analogous root cause for ERC20 escrow settlement: instead of using `SafeERC20.safeTransfer` (as the EVM sibling contract does), it performs a raw low-level `.call()` with the `IERC20.transfer` selector and only checks that the call itself did not revert — it never decodes/validates the returned boolean.

### Finding Description
In `withdraw()`, which is invoked from `onAccept()` when Hyperbridge delivers a `RedeemEscrow` or `RefundEscrow` message (an unprivileged, relayer-driven ISMP POST request), escrowed ERC20 tokens are released with:
```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
_orders[body.commitment][token] -= amount;
``` [1](#0-0) 

The same unsafe pattern is used for transaction-fee payout and for `SweepDust` handling in the same `onAccept()` function. [2](#0-1) [3](#0-2) 

`success` only reflects whether the external call reverted, not whether the token's `transfer` function returned `true`. Any ERC20 (or TRC20, since this file targets Tron) implementation that returns `false` on failure instead of reverting — a well-known non-compliant pattern still present on many deployed tokens — will cause this code to treat a failed transfer as successful. Immediately afterward the contract unconditionally decrements the internal escrow accounting (`_orders[body.commitment][token] -= amount;`) and marks the order filled (`_filled[body.commitment] = beneficiary;`), regardless of whether tokens actually moved. [4](#0-3) 

This mirrors the reported bug class: an unsafe token-movement primitive is used where the caller cannot confirm the operation truly delivered value, and the surrounding state is updated as if it did — leading to funds becoming unrecoverable. Contrast this with the standard EVM `IntentGatewayV2`/`IntentsBase._withdraw`, which correctly uses `SafeERC20.safeTransfer`, reverting on any non-compliant or failed transfer. [5](#0-4) 

### Impact Explanation
If a solver's/order's input or output token is a non-standard ERC20/TRC20 that returns `false` rather than reverting on failure (e.g., due to insufficient allowance/balance edge cases, blacklists, or pausable transfer logic), `withdraw()` will silently "succeed": the escrow ledger is decremented and the order is marked filled/refunded, but the beneficiary never receives the tokens. Because `_filled[commitment]` is set and the escrow slot is zeroed, there is no retry path — the tokens remain locked in the contract with no accounting entry pointing to them, resulting in permanent loss of user/solver funds. This satisfies the "permanent freezing/loss of funds" impact bar for a Medium-severity finding.

### Likelihood Explanation
`withdraw()` executes on every relayed `RedeemEscrow`/`RefundEscrow` ISMP message, i.e., on the ordinary settlement or cancellation path of every cross-chain intent order — a fully permissionless flow triggered by any relayer delivering a valid message once an order is created. No privileged role is required; the only precondition is that one of the escrowed tokens is a non-standard ERC20/TRC20 whose `transfer` returns `false` on failure instead of reverting, which is a realistic condition for tokens listed on Tron/TRC20 given the ecosystem's looser standard compliance.

### Recommendation
Replace the raw low-level `.call` + `success`-only check with `SafeERC20.safeTransfer` (already imported via `IERC20`/`SafeERC20` in this file) for all three sites: the input/output escrow release in `withdraw()`, the transaction-fee payout in `withdraw()`, and the `SweepDust` branch in `onAccept()`. This ensures the boolean return value (when present) is validated and reverts on any transfer that does not actually move value, consistent with the pattern already used in the EVM `IntentsBase._withdraw`.

### Proof of Concept
1. An order is created on the Tron `IntentGatewayV2` with an ERC20 input token `T` that is non-compliant (returns `false` on failed transfer rather than reverting) — e.g., a token that returns `false` if the contract itself is temporarily paused or blacklisted, without reverting.
2. A solver fills the order; Hyperbridge relays a `RedeemEscrow` message back to the source chain, invoking `onAccept` → `withdraw`.
3. At the moment of the call, token `T`'s `transfer` returns `false` (e.g., contract-level pause is toggled or the beneficiary is blacklisted) but does not revert.
4. `withdraw()` sees `success == true` (the call didn't revert), so it does not revert; it decrements `_orders[commitment][T]` and sets `_filled[commitment] = beneficiary`.
5. The beneficiary never received tokens `T`, and because escrow accounting has already been zeroed and the order marked filled, there is no code path to retry or recover the tokens — they are permanently stuck in the `IntentGatewayV2` contract.
