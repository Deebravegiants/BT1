### Title
Batch withdrawal completion status is matched by `assetId` only, causing tx-hash misreport / cross-crediting when a batch contains two withdrawals of the same token - ([File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts])

### Summary
`PoaBridge.describeWithdrawal()` resolves the completion status/`txHash` of a specific withdrawal inside a batch by matching the PoA relayer's unsorted withdrawal list solely on `assetId` (`nep141:<near_token_id>`), never on `destinationAddress` or `amount`. When `processWithdrawal`/`waitForWithdrawalCompletion` is used with a batch containing two withdrawals of the *same* token to two *different* destination addresses (a supported, documented use case for `WithdrawalParams[]`), each of the two `describeWithdrawal` calls returns the same match (typically the first same-asset entry found), so both withdrawals in the batch are reported as `completed` with the *same* `txHash`.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and its twin in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` locate the API-returned withdrawal record using only: [1](#0-0) 
and [2](#0-1) 

The internal-utils implementation even documents this explicitly as a known limitation: [3](#0-2) 

The SDK explicitly supports batches with multiple `WithdrawalParams` entries (see `createWithdrawalIdentifiers`, `waitForWithdrawalCompletion`, `processWithdrawal`), and nothing prevents two entries in the batch from sharing the same `assetId` while differing in `destinationAddress`/`amount` (e.g., withdrawing the same token to two different recipients in one intent). Because the equality that should hold — "the withdrawal record reported for withdrawal #i corresponds to *that specific* recipient/amount, not merely the same asset" — is never checked, `describeWithdrawal` and `waitForWithdrawalCompletion` (POA bridge path) will return the identical `txHash`/`completed` status for both withdrawals whenever the PoA relayer returns multiple same-asset entries, regardless of which one actually correlates to which destination.

### Impact Explanation
This breaks the "status/hash reported is not the on-chain outcome" equality called out in scope: an integrator using `waitForWithdrawalCompletion`/`processWithdrawal` for a batch of same-token withdrawals to different users would receive the same completion `txHash` for both withdrawal legs. A caller that credits/marks-as-settled based on this per-withdrawal result could end up crediting one destination's completion status to the other withdrawal, effectively reporting a withdrawal as completed when it is not (or duplicating the same transaction hash for two distinct payouts). This matches the "High - a status or hash misreport making an integrator credit or refund twice" category in scope.

### Likelihood Explanation
The scenario requires only that a batch withdrawal contains ≥2 entries with the same `assetId` (fully allowed by the public API and documented batch-withdrawal feature) and that the PoA relayer processes/returns them in a way where `findMatchingWithdrawal` picks the wrong entry (the code comment itself states "multiple withdrawals of the same token in a single transaction are not supported" by the matching logic). This is a normal caller-driven scenario, not one requiring a malicious relayer or admin — any integrator batching multiple withdrawals of the same token (e.g., paying out several users in USDT in one intent) can trigger it.

### Recommendation
Extend the matching criteria in both `findMatchingWithdrawal` implementations to disambiguate by `destinationAddress` and `amount` (and/or an index/nonce returned by the relayer) in addition to `assetId`, so each `WithdrawalIdentifier`/`WithdrawalCriteria` uniquely maps to a single relayer-reported withdrawal record. Until the relayer API provides a definitive per-leg identifier, the SDK should refuse to disambiguate (return "pending"/throw) rather than silently returning a possibly-wrong match, to avoid misreporting completion for the wrong recipient.

### Proof of Concept
1. Call `sdk.processWithdrawal({ withdrawalParams: [ { assetId: "nep141:usdt.tether-token.near", amount: 100n, destinationAddress: userA }, { assetId: "nep141:usdt.tether-token.near", amount: 200n, destinationAddress: userB } ] })`.
2. Both legs route through `PoaBridge` (same `assetId`), producing two `describeWithdrawal` calls with identical `withdrawalParams.assetId`.
3. The PoA relayer's `getWithdrawalStatus` response contains two `COMPLETED` records for `nep141:usdt.tether-token.near` (one per leg, with different `transfer_tx_hash`/`address`).
4. `findMatchingWithdrawal` (`w) => 'nep141:${w.data.near_token_id}' === criteria.assetId`) matches on asset only, so `.find()` returns the *first* matching record for both `describeWithdrawal` invocations — an integrator polling completion for userA's and userB's withdrawal both receive the same `txHash`, even though only one of the two on-chain payouts actually corresponds to that `txHash`.

function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}
