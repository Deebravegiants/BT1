## Analysis

The YON incident's core bug class — a token contract's `transferFrom` moving a different amount than the caller/protocol assumed, letting value be extracted without matching accounting — has a direct analog in Hyperbridge's `WrappedHyperFungibleToken` (and its upgradeable twin), which credits cross-chain messages with the *nominal* requested amount instead of the *actually received* amount when pulling the underlying ERC20 via `safeTransferFrom`.

The protocol team has already recognized and fixed this exact bug class elsewhere: `IntentGatewayV2` explicitly guards against non-standard `transferFrom`/fee-on-transfer behavior with a balance-before/after diff pattern, and has dedicated tests (`FeeOnTransferToken`) proving the fix. [1](#0-0) [2](#0-1) 

`WrappedHyperFungibleToken.send()` has no such guard: it calls `safeTransferFrom` for the exact nominal `params.amount`, then unconditionally dispatches an ISMP message crediting that same nominal `params.amount` to the destination chain's mint, regardless of how much the wrapper actually received. [3](#0-2) 

The same pattern repeats in the upgradeable variant. [4](#0-3) 

### Title
Unbacked cross-chain mint via nominal-amount accounting in `WrappedHyperFungibleToken.send()` when wrapping non-standard-transfer ERC20s - ([File: sdk/packages/core/contracts/apps/WrappedHyperFungibleToken.sol])

### Summary
`WrappedHyperFungibleToken.send()` (home-chain lock side of the HFT bridge) pulls the underlying ERC20 via `safeTransferFrom(msg.sender, address(this), params.amount)` and then dispatches a cross-chain `Message` crediting `params.amount` verbatim, without verifying that `params.amount` of tokens actually landed in the contract. Any underlying token whose `transferFrom` delivers less than the requested amount to the recipient (fee-on-transfer tokens, deflationary/burn-on-transfer tokens, or a token with a buggy/manipulable `transferFrom` such as YON) lets a caller mint more value on the remote `HyperFungibleToken` than was actually locked in escrow on the home chain.

### Finding Description
`send()` locks the underlying token and builds the dispatch body from `params.amount`, the value the caller supplied, not the delta actually received by the contract: [5](#0-4) 

Compare this to `IntentGatewayV2`, which was patched to record `balanceOf` before and after `safeTransferFrom` and use the observed delta for all downstream accounting (escrow, commitment hash, fee computation): [6](#0-5) 

`WrappedHyperFungibleToken` has no equivalent check anywhere in its `send()` path, and `onAccept`/`onPostRequestTimeout` unconditionally release/mint based on the message's stated `amount`: [7](#0-6) 

Because the destination-chain `HyperFungibleToken` mints purely based on the message body's `amount` field with no independent verification against actual locked value, any discrepancy introduced at the lock step directly becomes unbacked supply on the remote chain: [8](#0-7) 

### Impact Explanation
Each `send()` call against a wrapped token whose `transferFrom` delivers less than the nominal amount (fee-on-transfer/deflationary tokens, or a token with an exploitable `transferFrom` like the YON case) causes the wrapper to lock `amount - shortfall` while minting the full `amount` on the destination `HyperFungibleToken`. The minted tokens are freely transferable/redeemable on the destination chain, so the shortfall is a real, permanent loss for the escrow: subsequent legitimate `send()` calls back to the home chain (burn on destination, unlock on home) will eventually fail to find sufficient underlying balance in the wrapper, freezing or stealing other users' funds. This is a direct unbacked-mint / fund-drain path reachable by any unprivileged caller of `send()`, matching the accepted impact category ("unbacked mint" / "concrete theft or permanent freezing of funds").

### Likelihood Explanation
Reachability requires only that a `WrappedHyperFungibleToken` deployment wraps a token that doesn't transfer the full nominal amount via `transferFrom` — a common real-world category (fee-on-transfer tokens, tokens with rebasing/burn mechanics, or tokens with logic bugs like YON's). Given the documented general-purpose design ("Deploy this on the token's home chain where the canonical ERC20 supply lives") with no restriction to well-behaved tokens, and given the project already needed to fix the identical class of bug in `IntentGatewayV2`, the likelihood that some configured underlying token exhibits this behavior is non-trivial, and the exploit path itself requires no privilege beyond calling `send()`.

### Recommendation
Mirror the `IntentGatewayV2` fix in `WrappedHyperFungibleToken` (and its upgradeable variant): record `balanceOf(address(this))` before and after the `safeTransferFrom` call in `send()`, and use the observed delta — not `params.amount` — when building the dispatched `Message.amount`. Apply the same actual-received accounting on the WETH deposit branch if `IWETH.deposit` can ever short-deliver.

### Proof of Concept
1. Owner deploys `WrappedHyperFungibleToken` on the home chain and configures `underlying` to a fee-on-transfer ERC20 (e.g., 1% fee), per the documented configuration flow.
2. Attacker calls `send({dest, to: attackerAddressOnRemote, amount: 1000e18, ...})`.
3. `safeTransferFrom` pulls 1000e18 nominal but the wrapper's balance increases by only 990e18 due to the token's transfer fee.
4. `_buildDispatchPost` still encodes `Message.amount = 1000e18`.
5. On the remote chain, `HyperFungibleToken.onAccept` mints 1000e18 to the attacker, i.e., 10e18 more than was actually locked on the home chain.
6. Repeating this drains the wrapper's real underlying balance relative to total mintable claims, eventually preventing legitimate users from redeeming their bridged tokens on the home chain.

    function _transfer(address from, address to, uint256 amount) internal returns (bool) {
        uint256 fee = (amount * feeBps) / 10_000;
        uint256 received = amount - fee;
        balanceOf[from] -= amount;
        balanceOf[to] += received;
        // fee is burned
        totalSupply -= fee;
        return true;
    }

    function onAccept(IncomingPostRequest calldata incoming) public virtual override onlyHost whenNotPaused {
        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
    }
