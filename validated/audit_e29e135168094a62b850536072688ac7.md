### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes and validates the webhook HMAC over the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values that are handed to the host application's handler are taken verbatim from unauthenticated HTTP headers. Any party capable of obtaining one validly-signed webhook delivery (e.g., a merchant receiving webhooks for their own, legitimately-installed shop) can replay that body to the app's webhook endpoint while swapping the `x-shopify-shop-domain` header to a victim shop, and the request still passes HMAC validation.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate`/`validate_signature` compute the HMAC over `verifiable_query.to_signable_string` (the body) and compare it to the `hmac` header: [2](#0-1) 

Meanwhile `shop`, `topic`, `webhook_id`, and `api_version` are read straight from request headers with no cryptographic binding to the signed body: [3](#0-2) 

`Registry.process` only checks the HMAC (i.e., only that the body matches some valid signature for the app's shared `api_secret_key`), then forwards the unauthenticated `shop`/`topic`/`webhook_id`/`api_version` header values straight into `WebhookMetadata`, which is passed to the host app's handler: [4](#0-3) 

`WebhookMetadata` treats `shop` as authoritative tenant identity data for the handler: [5](#0-4) 

Because the webhook `api_secret_key` is shared by the app across **every** installed shop, a valid HMAC over a given body only proves "this body was signed by an entity that knows the app's shared secret" — it does not prove which shop produced it. Any merchant who has installed the app can capture one of their own legitimately-signed webhook deliveries (valid HMAC over that exact body) and re-POST the identical body to the app's webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`/`x-shopify-webhook-id`) header changed to a victim shop's domain. `HmacValidator.validate` will still succeed because it only checks the body bytes against the signature, and `Registry.process` will invoke the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain. This breaks the identity binding: *shop whose signature was verified* ≠ *shop value the host application relies on.*

### Impact Explanation
This is a cross-tenant identity-binding break: the gem hands the host application a `shop` value that was never authenticated by the HMAC, yet `Registry.process`'s successful HMAC check gives the appearance that the entire request (including `shop`) is verified. Host applications that use `WebhookMetadata#shop` to select which merchant record/session to update (a very common and Shopify-documented pattern) can be made to attribute attacker-supplied webhook data to another merchant's tenant, potentially triggering cross-tenant writes/side effects keyed off the spoofed shop.

### Likelihood Explanation
Requires only that the attacker be a legitimate (even free/trial) installer of the target app so they can generate at least one genuinely HMAC-signed webhook body, then replay it with a modified `shop` header — no access to `client_secret`, access tokens, or any other credential is needed, and no host-application misuse beyond the intended use of `WebhookMetadata#shop` is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`/`api_version`) values into the signed payload used for HMAC verification, or otherwise independently verify that the shop asserted in the header matches a shop known to have this webhook/topic registered (e.g., cross-check against the registered webhook id via the Admin API) before constructing `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop`/`topic`/`webhook_id` are unauthenticated header values and must not be trusted for tenant-selection without additional verification.

### Proof of Concept
1. App is installed on `attacker-shop.myshopify.com` and also on `victim-shop.myshopify.com`.
2. Attacker's shop receives a real webhook delivery, e.g. `orders/create`, with headers:
   - `x-shopify-hmac-sha256: <valid HMAC over raw body B>`
   - `x-shopify-shop-domain: attacker-shop.myshopify.com`
   - `x-shopify-topic: orders/create`
3. Attacker replays the exact same raw body `B` to the app's webhook endpoint, only changing:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` using the app's `api_secret_key` — it matches the header regardless of the `shop` header value: [6](#0-5) 
5. The handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled order payload>, ...)`, even though `victim-shop` never sent this webhook.
