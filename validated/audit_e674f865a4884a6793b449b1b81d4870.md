### Title
Ray-value overflow in `accrue_step` permanently freezes a market before the borrow-index cap engages - (File: common/src/rates/simulate.rs)

### Summary
`accrue_step` computes `borrowed * borrow_index` and `supplied * supply_index` with checked `Ray::mul` **before** `update_borrow_index` clamps the index to `MAX_BORROW_INDEX_RAY`. Once the product `scaled × index` exceeds `i128::MAX`, `scaled_to_original` panics with `MathOverflow` (error 33). Every state-mutating pool entrypoint runs `interest::global_sync` → `accrue_chunk` → `accrue_step` first, so from that moment on the market can never be touched again: no repay, no withdraw, no liquidation, no bad-debt cleanup, no `update_indexes`. The index cap intended to bound growth is never reached because the value multiplication panics first. This is the on-chain analog of CVE-2024-24989: a request to a code path crashes the worker — here, a permissionless call crashes *every* subsequent call to the market, permanently.

### Finding Description
In `common/src/rates/simulate.rs`, `accrue_step` begins with unchecked-growth value computations:

```rust
let borrowed_original = scaled_to_original(env, borrowed, borrow_index);   // line 60
let supplied_original = scaled_to_original(env, supplied, supply_index);   // line 61
```

`scaled_to_original` (`common/src/rates/scaling.rs:14`) is `scaled.mul(env, index)`, which panics on overflow. `calculate_supplier_rewards` (`common/src/rates/index.rs:80-83`) repeats the multiplication against `new_borrow_index`, and `update_supply_index` (`common/src/rates/index.rs:34`) multiplies `supplied * old_index` — all checked-mul panic sites.

The index clamp `MAX_BORROW_INDEX_RAY` lives in `update_borrow_index` (`common/src/rates/index.rs:13-19`), which runs *after* line 60 and cannot rescue line 80-81's multiplication either: a large `borrowed` scaled value overflows `borrowed * new_borrow_index` well before `new_borrow_index` reaches the cap.

`global_sync` (`contracts/pool/src/interest.rs:20-33`) is invoked unconditionally at the top of every market-mutating entrypoint (per `contracts/pool/README.md`: `entrypoint → Cache::load → interest::global_sync → mutate → guards → commit`). There is no code path that repays, withdraws, liquidates, cleans bad debt, or recapitalizes a market without first running this accrual. Once the market state crosses the Ray-value ceiling, every one of these calls panics — the freeze is permanent and unrecoverable, because no transaction can roll back time or shrink `borrowed`/`supplied` without itself passing through `global_sync`.

The repo's own harness proves this: `tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361` supplies ~`10^9 × 10^18` units, borrows at 98% utilization on the steep XLM curve, advances time, and observes `update_indexes` panic with `MathOverflow` while `borrow_index < MAX_BORROW_INDEX_RAY`; subsequent `withdraw` and `repay` calls panic identically.

### Impact Explanation
Permanent freezing of funds and a market unable to operate. Once the cliff is hit: suppliers cannot withdraw, borrowers cannot repay, liquidators cannot seize collateral, and the keeper's `update_indexes`/`claim_revenue`/`recapitalize` all revert. All tokens custodied in that market — every user's deposit plus unclaimed protocol revenue — are locked forever. Because each (hub, token) book is independent, the freeze is scoped to the poisoned market, but every asset in that market is lost to its owners.

### Likelihood Explanation
A single unprivileged address can drive a market there through `supply` and `borrow` alone: supply a large amount (raising `supplied` scaled shares), borrow to high utilization (raising the borrow rate so `borrow_index` compounds fastest per chunk). At the steep end of the kinked rate curve the index grows rapidly; the harness shows the value ceiling is reached before the index cap, so no safeguard intervenes. Two mitigating factors keep this from being trivial: it requires whale-scale capital (billions of units of an 18-decimal asset, or a proportionally smaller-but-still-large position over a longer horizon on a steeper curve) and accrual time — yet the attacker need only create the condition once; ordinary interest accrual does the rest, and no privileged or off-chain action can undo it. Notably, even *honest* market growth reaches the same cliff — the attacker merely accelerates an inevitable outcome for any large, high-utilization market.

### Recommendation
Cap the *value*, not just the index. Concretely:

- In `accrue_step`, compute `borrowed_original`/`supplied_original` with a saturating multiplication (or clamp `borrowed`/`supplied` against `i128::MAX / index`) so utilization/rate computation degrades gracefully instead of panicking.
- In `update_borrow_index`, additionally clamp so that `borrowed * new_borrow_index` stays within `i128::MAX` — i.e. bound `new_borrow_index ≤ i128::MAX / borrowed` when `borrowed > 0` — before returning. Same for `update_supply_index` against `supplied`.
- In `calculate_supplier_rewards`, cap `accrued_interest` at the representable maximum (saturating sub/mul) so the split into supplier rewards and protocol fee cannot trap the entry path.
- Provide a liveness fallback: a mutating path that accrues with the index pinned at its cap (index stays `MAX_BORROW_INDEX_RAY`, no further multiplication) so repay/withdraw/liquidate remain callable even at the ceiling — accrual should be idempotent once saturated rather than fatal.

### Proof of Concept
Reproduced by the existing harness test `a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap` (`tests/test-harness/tests/controller/large_positions_and_long_horizons.rs:320-361`), condensed:

```rust
let mut t = LendingTest::new()
    .with_market(big("BIG18", 18, xlm_curve()))
    .with_market(col())
    .with_max_utilization_disabled_all_markets()
    .build();
lift_caps(&t, "BIG18", 18);
lift_caps(&t, "COL", 7);
// Attacker (or whale) positions: huge supply + ~98% utilization borrow.
let principal = BILLION * 10i128.pow(18);
t.supply_raw(BOB, "BIG18", principal);
let debt = principal / 100 * 98;
t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
t.borrow_raw(ALICE, "BIG18", debt);

// Advance time until accrual overflows inside scaled_to_original.
loop {
    t.advance_time(YEAR_SECS);
    if let Err(e) = t.try_update_indexes_for(&["BIG18"]) { break e; }
}
// → Error(Contract, #33) MathOverflow, while borrow_index < MAX_BORROW_INDEX_RAY.

// Market is now permanently frozen — every verb accrues first:
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0),   errors::MATH_OVERFLOW);
// Same panic for liquidate, clean_bad_debt, flash_loan, claim_revenue, etc.
```

Attacker path on-chain: `controller.supply` (hub asset), `controller.supply` (collateral), `controller.borrow` near the utilization cap, then wait — or simply let honest accrual continue on any already-large high-utilization market. The panic in `scaled_to_original`/`calculate_supplier_rewards` permanently denies every subsequent entrypoint that calls `interest::global_sync`, freezing all custodied funds in that market.
