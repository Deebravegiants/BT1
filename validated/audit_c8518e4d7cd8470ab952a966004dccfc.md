## Analog Found

### Title
BEEFY supermajority threshold counts raw vote/signature array length without deduplicating repeated authority signatures, allowing a minority of validators to forge consensus finality - (File: evm/src/consensus/EcdsaBeefy.sol / modules/consensus/beefy/verifier/src/lib.rs)

### Summary
`EcdsaBeefy.sol#verifyMmrUpdateProof` and its Rust counterpart `verify_mmr_update_proof` compute the participation count directly from `relayProof.signedCommitment.votes.length` / `mmr.signed_commitment.signatures.len()` and immediately gate the 2/3+1 supermajority check on this raw length, before any check that the votes/signatures correspond to distinct authorities.

### Finding Description
`checkParticipationThreshold(sigLen, authoritySet.len)` is evaluated using `sigLen = relayProof.signedCommitment.votes.length` [1](#0-0) , and the analogous Rust path uses `signatures_length = mmr.signed_commitment.signatures.len()` gated the same way [2](#0-1) . Neither function checks that the `votes`/`signatures` array contains unique `authorityIndex`/`index` values (or unique recovered signer addresses) before counting them toward the supermajority. The subsequent per-vote loop recovers a signer address and pairs it with the vote's claimed `authorityIndex` to build merkle multi-proof leaves [3](#0-2) , and the Rust side builds the equivalent `authority_leaves`/`authority_indices` list without any duplicate-index filtering [4](#0-3) . A merkle multi-proof only proves that the *submitted* (index, leaf-hash) pairs exist in the tree; submitting the same authority's (index, signature) pair multiple times produces a set of leaves that are all valid members of the tree (since they're all the same real leaf), so `MerkleMultiProof.VerifyProof`/`merkle_proof.verify` will still succeed. This is structurally identical to the `QVBaseStrategy.reviewRecipients` bug: a single voter's ballot is tallied repeatedly into a counter that gates a critical state transition, because the code counts array length/increments instead of tracking a set of unique voters who have already been counted.

This directly contrasts with other consensus verifiers in the same codebase that were hardened against duplicate votes/keys, e.g. Pharos's `verify_validator_membership` explicitly rejects duplicate participant keys [5](#0-4) , GRANDPA justification verification relies on `finality_grandpa::validate_commit` rejecting `num_duplicated_precommits` [6](#0-5) , and Tendermint has an explicit `ensure_unique_addresses` guard against duplicate validator addresses [7](#0-6) . The ECDSA BEEFY path (both Solidity and Rust) is missing this equivalent duplicate-signer check.

### Impact Explanation
A relayer submitting a BEEFY consensus proof can duplicate a single (or a small handful of) validator's signature/authority-index entries in the `votes`/`signatures` array to inflate `sigLen`/`signatures_length` past the `(2/3 * total) + 1` supermajority threshold, while only a minority of the real authority set actually signed the commitment. Since `verifyMmrUpdateProof`/`verify_mmr_update_proof` is the core consensus verification gate that updates `trustedState.currentAuthoritySet`/`nextAuthoritySet` and accepts new MMR roots (from which all downstream parachain state commitments and ISMP messages are derived), this allows forged/premature consensus finality to be accepted by the light client, undermining the entire BEEFY security model and enabling forged message delivery or unsound state commitments across the bridge.

### Likelihood Explanation
Exploitation requires no special privilege beyond being able to submit a BEEFY consensus update (an unprivileged relayer action reachable by anyone dispatching a `verify()` call), and requires collusion/compromise of only a minority of the real validator set (fewer than 2/3+1) — the attacker just needs at least one or a few valid signatures to replicate across duplicate vote entries. This is a directly reachable, low-complexity path.

### Recommendation
Deduplicate votes/signatures by `authorityIndex` (or recovered signer address) before counting participation and before threshold checks, in both `EcdsaBeefy.sol#verifyMmrUpdateProof` and `modules/consensus/beefy/verifier/src/lib.rs#verify_mmr_update_proof`. Track seen `authorityIndex` values (e.g., via a bitmap since indices are bounded by authority set size) and reject the proof if a repeated index is found, mirroring the `DuplicateParticipant` check already used in the Pharos verifier.

### Proof of Concept
1. Trusted authority set has `N` validators requiring `(2N/3)+1` signatures for supermajority.
2. Attacker (or colluding minority) obtains valid signatures from only `k < (2N/3)+1` real authorities over a forged/premature commitment.
3. Attacker constructs `relayProof.signedCommitment.votes` (or `mmr.signed_commitment.signatures`) by repeating each of the `k` valid `(authorityIndex, signature)` pairs enough times so `sigLen >= (2N/3)+1`.
4. `checkParticipationThreshold(sigLen, authoritySet.len)` passes since it only checks array length [8](#0-7) .
5. The merkle multi-proof loop recovers the same `k` real authority addresses (duplicated) and builds `MerkleMultiProof.Leaf` entries for each duplicate; since each duplicate leaf/index pair genuinely exists in the authority-set merkle tree, `MerkleMultiProof.VerifyProof` succeeds [9](#0-8) .
6. The consensus client accepts the update, advancing `trustedState` and committing forged/unverified state, despite fewer than the required distinct 2/3+1 validators having actually signed.

/// Rejects a validator set that reuses the same address twice. Each address is a
/// hash of its public key, so a duplicate signals a set that was not built honestly.
fn ensure_unique_addresses(
	validators: &[cometbft::validator::Info],
) -> Result<(), VerificationError> {
	let unique = validators.iter().map(|v| v.address).collect::<BTreeSet<_>>();
	if unique.len() != validators.len() {
		return Err(VerificationError::ValidatorSetError(
			"duplicate validator address in set".to_string(),
		));
	}
	Ok(())
}
