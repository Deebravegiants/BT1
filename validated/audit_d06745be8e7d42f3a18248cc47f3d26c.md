Found the identity binding break: in `Webhooks::Registry.process`, the `shop` value handed to the webhook handler (`request.shop`, read from the `shopify-shop-domain`/`x-shopify-shop-domain` header) is never part of the HMAC-signed bytes.

### Title
Webhook `shop` domain is trusted from an unauthenticated header, not bound to the HMAC-signed body - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`Webhooks::Request#to_signable_string` returns only the raw body, so the HMAC signature covers the JSON payload but not the `shop-domain` header. `Registry.process` validates that HMAC and then passes the unauthenticated `request.shop` value straight to the app's handler as the tenant identifier.

### Finding Description
`Utils::HmacValidator.validate` computes and compares the signature over `verifiable_query.to_signable_string`, which for a webhook request is defined as: [1](#0-0) 
i.e. only `@raw_body`. The `shop` accessor is derived from a separate header, entirely outside the signed bytes: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` and then, once that passes, forwards `request.shop` (the header-derived value) as the tenant identifier to the host application's handler, with no equality check binding it to anything cryptographically signed: [3](#0-2) 

The identity binding that should hold is: `shop used to authorize/route data == shop covered by the HMAC signature`. Here it is `shop header (unauthenticated) != HMAC-signed body`. Because the body's HMAC is computed only over the raw JSON body, an attacker who has a valid, previously-observed `(body, hmac)` pair for their own shop can replay that exact body/hmac pair while substituting an arbitrary value in the `shopify-shop-domain` header. `HmacValidator.validate` still succeeds (it never inspects `shop`), and `Registry.process` will hand `WebhookMetadata` with the attacker-chosen `shop` to the host app's handler, believing the payload originated from that shop.

This mirrors the report's bug class: a field ("field acted on but not covered by the HMAC") — the routing/tenant identity — is trusted and acted upon without being part of the value that was actually integrity-checked.

### Impact Explanation
This is a cross-tenant identity confusion at the boundary this gem is responsible for: `Registry.process` is the exact function apps use to authenticate and route inbound webhooks, and it hands a spoofable `shop` value to application code as if it were verified. Depending on how the host app uses `WebhookMetadata#shop` (commonly to look up the tenant's session/access token or to attribute the payload to a merchant record), this enables cross-tenant data confusion/write using another shop's identity, which maps to the Critical "cross-tenant access" category.

### Likelihood Explanation
Exploitation requires the attacker to possess at least one legitimately-signed webhook body for their own shop (trivial — they can trigger their own shop's mandatory webhooks or any webhook topic on an app they've installed), and to be able to send an unauthenticated HTTP POST to the app's registered webhook endpoint with a forged `shopify-shop-domain` header — both preconditions available to any unprivileged internet user who has installed the app on at least one shop they control. No secrets are required.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header value in the signable string used for HMAC verification, or otherwise cryptographically bind the reported shop to the signed payload before it is exposed via `Request#shop` / passed to `WebhookMetadata`.

### Proof of Concept
1. Attacker's app instance receives (or attacker triggers) one legitimate webhook for `attacker-shop.myshopify.com` with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B`).
2. Attacker replays a raw HTTP POST to the app's webhook endpoint with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H})` is constructed; `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` [4](#0-3) [5](#0-4) 
4. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is called with `shop == "victim-shop.myshopify.com"` even though the payload/signature never referenced that shop, delivering attacker-controlled data attributed to the victim tenant. [6](#0-5)
