### Title
Webhook `shop` (and `topic`/`webhook-id`) attribution is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant-identifying `shop` value from an HTTP header (`x-shopify-shop-domain`/`shopify-shop-domain`), but the HMAC signature that `ShopifyAPI::Utils::HmacValidator` verifies is computed over the raw request body only. The `shop` field that the framework later trusts and hands to the app's webhook handler is never bound into the signed material, so a party who possesses one valid `(body, hmac)` pair for the shared `api_secret_key` can freely relabel which shop the payload is attributed to.

### Finding Description
`Registry.process` accepts a webhook only if `Utils::HmacValidator.validate(request)` succeeds: [1](#0-0) 

`HmacValidator` computes the signature strictly from `verifiable_query.to_signable_string`: [2](#0-1) 

For webhooks, `to_signable_string` returns only the raw body — it does not include the shop, topic, webhook id, or api version: [3](#0-2) 

But `shop` (along with `topic`, `webhook_id`, `api_version`) is read straight from unauthenticated headers and passed unchanged into the handler once HMAC validation passes: [4](#0-3) 

This is the same class of bug as the referenced report: the check verifies that *some* bytes are correctly signed with the shared secret (`permit2.permitTransferFrom` verifying only the signature), but a semantically critical field used afterward for attribution — `TokenPermissions.token` in the Vault case, `shop` here — is never included in what was actually verified. The equality the code implicitly assumes is:

`shop used by handler == shop that produced/authorized this signed body`

but what is actually proven is only:

`hmac == HMAC(api_secret_key, raw_body)`

with `shop` free for the caller to set to anything.

### Impact Explanation
Because `api_secret_key` is shared across every shop that installs a given (public) app, any merchant who has legitimately installed the app receives real webhook deliveries with a valid `(body, hmac)` pair computed under that same shared secret. That merchant — an unprivileged actor with respect to other tenants of the app — can capture one such request and replay it verbatim to the app's public webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop's domain. `HmacValidator.validate` will still succeed since it never inspected the header, and `Registry.process` will invoke the handler with `WebhookMetadata.new(shop: <victim-shop>, body: <attacker's own webhook body>, topic: ...)`. Depending on how the host application uses `data.shop` (e.g., to look up/mutate the victim's stored session, trigger `shop/redact`/`app/uninstalled` cleanup logic, or update victim records), this enables cross-tenant data corruption, forced data deletion, or state confusion attributed to a shop the attacker does not control — a cross-tenant boundary break.

### Likelihood Explanation
Exploitation requires only that the attacker be a legitimate (even free-tier) install of a public app that shares one `api_secret_key` across all installations, and the ability to send arbitrary HTTP requests to the app's public webhook callback URL — both of which are trivially satisfied by any unprivileged internet user who installs the target app once. No access token, `client_secret`, or privileged credential is needed.

### Recommendation
Include the tenant-identifying and semantically significant headers (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind `shop` to the signed body (e.g., require the handler/registry to cross-check the delivered `shop` against a shop derived from data inside the verified body, or maintain a mapping from webhook subscription id to expected shop). At minimum, document and enforce that `shop`/`topic` values passed to handlers are not to be trusted as authenticated unless independently corroborated.

### Proof of Concept
1. Attacker installs the target public app on their own shop `attacker.myshopify.com` and lets Shopify deliver a real webhook (e.g., `orders/create`) to the app's callback URL, capturing the exact raw body `B` and header `x-shopify-hmac-sha256: H` (`H = HMAC-SHA256(api_secret_key, B)`).
2. Attacker replays an HTTP POST to the same callback URL with the same body `B` and header `H`, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` accepts the forged headers, and `Utils::HmacValidator.validate` returns `true` because it only hashes `B`: [5](#0-4) 
4. `Registry.process` invokes the app's handler with `shop: "victim.myshopify.com"` and the attacker-controlled body, even though the actual Shopify-signed delivery was for `attacker.myshopify.com`.
