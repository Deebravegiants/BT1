### Title
Fee-charging failure in `pallet-ismp`'s `handle_unsigned` batch can atomically revert delivery of unrelated honest messages, letting an unprivileged signer grieve message delivery - (File: `modules/pallets/ismp/src/impls.rs`, `modules/pallets/ismp/src/fee_handler.rs`)

### Summary
`pallet-ismp`'s `execute()` first processes an entire batch of incoming ISMP messages (dispatching requests/responses, mutating `RequestCommitments`/`ResponseCommitments`, invoking app callbacks) and only afterwards charges the per-message fee to the account recovered from each message's attached signature. If that fee transfer fails for even one message in the batch, the whole extrinsic returns an error and, due to FRAME's transactional dispatch semantics, all storage effects from the batch — including the successful, unrelated messages bundled with it — are rolled back. There is no check that the fee-payer account can actually still afford `ExistenceRequirement::KeepAlive` at execution time versus whatever state it was in when the message was crafted/gossiped.

`ExistenceRequirement::KeepAlive` means the transfer fails if it would drop the payer's account below the existential deposit. Because this check runs *after* all the message side effects have already been computed for the batch, and `execute()` maps any `on_executed` error into `Error::<T>::ErrorChargingFee` which propagates out of the `handle_unsigned` dispatchable, a single crafted message whose signer account is drained (or reaped) between when a relayer builds/submits the batch and when it lands in a block will cause the extrinsic to fail. Because dispatchable calls in FRAME are wrapped in a storage transaction, a failing call rolls back *all* storage writes performed during it — including the request/response commitments for every other, unrelated, honest message batched in the same `handle_unsigned` call.

This mirrors the reported bug class exactly: no check is performed that the fee-paying account can sustainably cover the charge *before* the expensive processing runs, and the account's affordability can change between the time the message was prepared and the time it is actually executed. An attacker fully controls the "signer" keypair/account for their own crafted message (the signature is over the request payload, not over any externally-verified sender identity tied to their own transaction), so they can guarantee the account has just enough balance to pass `validate_unsigned` (transient, non-persisted) and then drain it (via a normal signed transfer in an earlier or same block) before `handle_unsigned` actually executes in a block, deterministically causing `ErrorChargingFee`.

### Impact Explanation
This is a route-availability/message-delivery denial: an unprivileged party who can get their own message bundled into (or racing within) a relayer's `handle_unsigned` batch can force the entire batch to fail and roll back, preventing legitimate, unrelated requests/responses from being delivered in that block. Since `pallet-ismp` batches messages for efficiency and relayers commonly submit multiple pending messages together, this can be used to repeatedly stall delivery of otherwise-valid cross-chain messages, which the scope explicitly treats as "a route unable to deliver messages" — a High-severity outcome for message-passing infrastructure.

### Likelihood Explanation
The attacker needs only: (1) a normal account capable of signing an arbitrary hash to be attached as `msg.signer` on a Request/Response message, and (2) the ability to drain that account's spendable balance below the existential deposit at the exact block in which the batch executes (e.g., via a concurrent extrinsic in the same block, or simply spending/reaping the account after crafting the signature). Because `validate_unsigned` re-executes `Self::execute(messages.clone())` transiently (its storage effects are not persisted at the mempool-validation stage) before the real dispatch, the timing window between "looked valid to the relayer/pool" and "executed on-chain" is exactly the attack window described in the original report, and 12-second-ish block slots give ample time to land the balance-draining transaction.

### Recommendation
Charge (or at least verify sufficient/affordable balance for) each message's fee-payer *before* performing the message's side effects, or make fee-charging per-message and non-atomic with the rest of the batch (e.g., only roll back the specific failing message's effects, not the whole batch), similar to the referenced fix pattern of checking payer affordability up front. Concretely, in `WeightFeeHandler::on_executed`/`execute()`, verify `T::Currency::reducible_balance`/`ensure_can_withdraw` for the recovered signer against the computed fee prior to committing any message's storage effects, and treat a failed transfer for one message as an isolated failure (e.g., skip/queue that message) rather than failing the entire `handle_unsigned` batch.

### Proof of Concept
1. Attacker generates an sr25519 keypair `K` and funds account `A = Address(K)` with exactly the existential deposit plus a hair more than the computed fee for a crafted `PostRequest`/`RequestMessage` whose `signer` is `K`'s signature over the request payload (as in `should_charge_fee_for_request`, `modules/pallets/testsuite/src/tests/pallet_ismp.rs:608-669`).
2. Attacker (or a colluding relayer) gossips this message alongside several legitimate, unrelated `RequestMessage`s in one `handle_unsigned` batch; `validate_unsigned` transiently executes `Self::execute()` and it looks valid (KeepAlive still satisfied at that instant since state changes from validation are not persisted).
3. Before the batch is actually included in a block, attacker submits an ordinary signed `Balances::transfer_all` from `A`, draining it below the existential deposit.
4. When the batch executes on-chain, `handle_incoming_message` processes all messages (including the legitimate ones), but `WeightFeeHandler::on_executed`'s `C::transfer(&A, &treasury, fee, KeepAlive)` fails for the attacker's message.
5. `execute()` returns `Err(Error::<T>::ErrorChargingFee)`, and FRAME rolls back the entire `handle_unsigned` call, discarding the commitments/dispatch of the legitimate bundled messages — they must be resubmitted, delaying or (if repeatedly targeted) denying delivery.
