### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, allowing cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0)  while the shop, topic, and webhook-id are read directly from unauthenticated HTTP headers [2](#0-1) . `Registry.process` verifies only the HMAC over the body via `Utils::HmacValidator.validate(request)` and then unconditionally trusts `request.shop`/`request.topic` to build the `WebhookMetadata` handed to the app's handler [3](#0-2) . This breaks the identity binding `shop authenticated == shop acted upon`: the HMAC authenticates the body bytes, but the tenant identifier (`shop`) that the app relies on to route/attribute the webhook is never part of the signed material.

### Finding Description
`HmacValidator.validate_signature` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it to the `hmac-sha256` header [4](#0-3) . For webhooks, `to_signable_string` is defined as just `@raw_body` [1](#0-0) . The `shop`, `topic`, `api_version`, and `webhook_id` accessors all come from HTTP headers that are completely outside this signed string [2](#0-1) .

`Registry.process` performs exactly one integrity check — the body HMAC — and then immediately trusts the header-derived `shop`/`topic` to dispatch to the app-registered handler:
```
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))
``` [5](#0-4) 

Because `(body, hmac)` pairs are not secret — they are delivered over the wire to the app's own public webhook endpoint on every legitimate Shopify delivery — any party who can observe one genuine delivery (e.g., via logs, an error-tracking/APM tool that captures request bodies, a proxy, or a webhook-forwarding/debugging service commonly used during development) can replay that exact `(body, hmac)` pair to the same endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. `HmacValidator.validate` will still pass because it only checks the body, and `Registry.process` will hand the app a `WebhookMetadata` claiming to be from the attacker-chosen shop, with the original (unrelated) shop's body content. This is the same class of defect described in the report: a field that downstream code acts on (`shop`, the tenant-binding identifier) is not covered by the cryptographic check (`HMAC` over `to_signable_string`), so "bytes verified" and "bytes/headers parsed and acted upon" diverge.

### Impact Explanation
This allows cross-tenant confusion: an app that uses `WebhookMetadata#shop` to key its own persistence/business logic (as the library's docs and tests demonstrate, e.g. attributing webhook data to `data.shop` [6](#0-5) ) can be made to process a replayed, cryptographically-"valid" webhook body under a victim shop's identity that it never actually sent, or vice versa — attributing one merchant's data to another merchant's record. This matches the Critical "cross-tenant access" impact category, since the gem provides no mechanism, nor documents any requirement, to bind the header-derived tenant identifier to the signed payload.

### Likelihood Explanation
Exploitation requires the attacker to have observed at least one legitimate `(raw_body, hmac)` pair for the target webhook endpoint (via logging, monitoring, tunneling/debug tools, or network exposure) and to be able to send an HTTP POST to the app's public webhook receiver — both are realistic for an unprivileged internet actor and do not require the `api_secret_key`, an access token, or any privileged account.

### Recommendation
Include the tenant-identifying headers (at minimum `shop-domain`, and ideally `topic`/`webhook-id`) in the HMAC-signed material, or independently verify that the `shop` header corresponds to a shop with an active, previously-established session/registration before trusting it in `WebhookMetadata`. At minimum, document that `WebhookMetadata#shop`/`#topic` are unauthenticated and must not be used as sole tenant-routing keys without additional verification.

### Proof of Concept
1. Capture (via logs/APM/tunnel) one legitimate webhook delivery to the app's webhook endpoint: raw body `B` and header `x-shopify-hmac-sha256: H` (valid for `B` under the app's secret), originally sent with `x-shopify-shop-domain: victim.myshopify.com`.
2. Replay an HTTP POST to the same endpoint with the identical body `B` and header `x-shopify-hmac-sha256: H`, but set `x-shopify-shop-domain: attacker-controlled-or-different-victim.myshopify.com` (and optionally a different `x-shopify-topic`).
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers without complaint [7](#0-6) ; `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [8](#0-7) ; `Registry.process` calls the app handler with `WebhookMetadata.shop` set to the forged shop domain and body `B` [5](#0-4) , demonstrating that the shop binding is not authenticated.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
