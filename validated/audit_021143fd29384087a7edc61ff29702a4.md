### Title
Webhook `shop` identity used for tenant routing is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes the webhook HMAC solely over the raw request body [1](#0-0) , while the `shop` value that `Registry.process` hands to the app's handler is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header, which is never included in the signed material [2](#0-1) .

### Finding Description
`Utils::HmacValidator.validate` verifies the request by recomputing the HMAC over `verifiable_query.to_signable_string` and comparing it to the `hmac` field [3](#0-2) . For webhooks, `to_signable_string` returns only `@raw_body` [1](#0-0) . `Registry.process` calls this validator and, on success, builds `WebhookMetadata` using `request.shop`, which is parsed purely from the (unsigned) `shop-domain` header [4](#0-3) [2](#0-1) .

This is exactly the bug class the report describes: a field that is *acted upon* (here, `shop`, used by the docs-recommended handler pattern for tenant routing, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)` [5](#0-4) ) is not part of the cryptographically bound data, breaking the equality: `shop used by handler == shop cryptographically bound in the signed request`.

Because a public app's `api_secret_key` is shared across every merchant that installs it, any unprivileged internet user can install the app on their own free development/test store, trigger a real event (e.g. `orders/create`), and capture a genuinely-signed `(raw_body, hmac)` pair from Shopify. Since the header carrying `shop-domain` is not part of the signed bytes, the attacker can replay that exact `(raw_body, hmac)` pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks the body), and `Registry.process` forwards `shop: "victim-shop.myshopify.com"` to the handler with attacker-controlled body content [4](#0-3) .

### Impact Explanation
If the host application follows the gem's own documented pattern and uses `data.shop` to select which tenant's session/data store to act on (exactly as shown in the gem's docs), an attacker who has never interacted with the victim's shop can inject forged, "HMAC-verified" webhook events attributed to that victim shop — a cross-tenant data-integrity/isolation break driven entirely by this gem's request-parsing and validation logic.

### Likelihood Explanation
The prerequisite (installing a public app on one's own store to receive a legitimately signed webhook) is a normal, unprivileged action available to any internet user, and crafting an HTTP request with a spoofed `shop-domain` header is trivial. The only work required by the attacker is triggering one event type they want to forge on the victim's behalf and having it match a topic/schema the app's handler doesn't otherwise sanity-check.

### Recommendation
Do not trust `shop-domain` (or any other header) that is outside the signed payload for tenant-identification purposes without independent verification. Either document explicitly and forcefully that `shop` is unauthenticated and must be cross-checked against a session/installation record before use, or have `Registry.process` require the caller to supply/verify the `shop` domain against a known/registered shop list before dispatching to the handler.

### Proof of Concept
1. Install the target public app (which uses this gem) on an attacker-owned development store `attacker-shop.myshopify.com`.
2. Trigger a webhook event (e.g., create an order) to receive a real webhook POST from Shopify with a valid `x-shopify-hmac-sha256` computed over the raw body [1](#0-0) .
3. Capture the raw body and valid HMAC header value.
4. Replay the identical raw body + HMAC header to the app's webhook endpoint, but replace `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
5. `HmacValidator.validate` passes (body unchanged) [6](#0-5) ; `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` and the attacker's body [4](#0-3) , causing the app to process a forged event as if it originated from the victim's shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
