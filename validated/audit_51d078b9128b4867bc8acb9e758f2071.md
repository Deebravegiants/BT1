### Title
Webhook `shop-domain` (and `topic`) headers are trusted for tenant identification but are not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, and `HmacValidator.validate` computes/compares the signature solely over that body. The `shop` (and `topic`) values that `ShopifyAPI::Webhooks::Registry.process` later uses to identify *which tenant* the webhook belongs to are read straight from HTTP headers that are never included in the HMAC computation.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

only the `@raw_body` is signed. The `shop` and `topic` accessors instead read straight from headers, which are never mixed into the signed material: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` as the tenant identity for dispatch, without any additional binding to the signed body: [3](#0-2) 

`HmacValidator.validate`/`validate_signature` confirm only that *some* valid `(secret, body)` pair produced the digest - they say nothing about which shop that pair was issued for: [4](#0-3) 

Because every shop that installs the app shares the same app-level `api_secret_key`, and the HMAC covers only the body, a `(raw_body, hmac)` pair that a merchant legitimately obtains for their **own** shop's webhook delivery remains valid when replayed with a forged `x-shopify-shop-domain` (and/or `x-shopify-topic`) header pointing at a different shop. The equality the code implicitly relies on - "shop claimed in the header" == "shop that produced this signed body" - is never actually checked; the gem only verifies "body integrity" == "signed by our secret".

### Impact Explanation
This breaks the tenant/shop binding for webhook processing: an attacker who has installed the app on their own shop (a low-privilege, "internet user" position relative to any other merchant's data) can capture a legitimate `(body, hmac)` pair from their own webhook deliveries and replay it against the app's webhook endpoint with a different `shop-domain` header. Any handler that keys behavior off `WebhookMetadata#shop` (e.g., looking up a session/store record, deciding which tenant's data to update) can be made to act as if the request came from a different shop - a cross-tenant confusion/spoofing primitive.

### Likelihood Explanation
Requires only an app install (any merchant can obtain this) plus the ability to send arbitrary HTTP requests to the app's public webhook endpoint with attacker-chosen headers - no access token, secret, or privileged account needed to mount the header-forgery step itself.

### Recommendation
Bind the tenant identity into the signed material or otherwise verify it out-of-band: e.g., require the caller to also present/verify the `webhook_id` against a subscription record tied to the expected shop, or include `shop`/`topic` in the value that is HMAC-verified before trusting them in `Registry.process`. At minimum, document that consumers of `WebhookMetadata#shop` must not treat it as cryptographically bound to the payload and must independently authorize the shop for the given `webhook_id`.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and triggers a real webhook (e.g., `products/create`) with a body they fully control.
2. Shopify sends the legitimate `x-shopify-hmac-sha256` for that exact body, computed with the app's shared `api_secret_key`.
3. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and/or a different `x-shopify-topic`).
4. `HmacValidator.validate` in `Registry.process` succeeds because it only checks the body against the secret; `WebhookMetadata.new(shop: request.shop, ...)` is built with the forged `victim-shop.myshopify.com`, and the handler processes attacker-controlled data as if it belonged to `victim-shop`.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
