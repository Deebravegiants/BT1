### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing shop-identity spoofing on a genuine webhook payload - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature only over the raw request body (`to_signable_string` returns `@raw_body`), while the `shop` accessor is read from the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) HTTP header, which is completely outside the HMAC-covered bytes.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

and `Request#shop` is derived purely from a header: [2](#0-1) 

`Utils::HmacValidator.validate` verifies the received `hmac` header against `to_signable_string` computed with the app's `api_secret_key`: [3](#0-2) 

Because `to_signable_string` returns only `@raw_body`, the `shop-domain` header (and `topic`, `webhook-id`, `api-version` headers) are never part of the signed material. The identity binding that should hold is:

`hmac == HMAC(secret, body ‖ shop)` for the shop the app subsequently keys its logic on

but the code actually enforces only:

`hmac == HMAC(secret, body)`

leaving `shop` unauthenticated relative to the signature. This is exactly the analog class called out in the rules: "a field acted on but not covered by the HMAC."

### Impact Explanation
An unprivileged actor who can install the app on their own (attacker-controlled) shop can receive a genuine webhook from Shopify for that shop, with a valid HMAC (computed only over the body, which the attacker does not need to forge — Shopify signs it for them). The attacker can then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header with a victim shop's domain. `Utils::HmacValidator.validate(request)` still returns `true`, because the signature check never inspected the header. Any downstream logic that trusts `request.shop` (e.g., `ShopifyAPI::Webhooks::Registry`, or the host app's handler) to select the session/access-token record to load or the tenant context to act in would then process a Shopify-signed payload under the wrong tenant identity — a cross-tenant confusion condition rooted in this gem's `Request`/`HmacValidator` contract.

### Likelihood Explanation
Requires only that the attacker is able to install the app on any shop (unprivileged, self-service in most embedded-app flows) and can send an arbitrary HTTP request with attacker-chosen headers and a captured body/HMAC to the app's public webhook endpoint. No access token, `client_secret`, or privileged account is needed — the attacker only needs a webhook that Shopify itself signs for them, then a header swap.

### Recommendation
Include the shop domain (and ideally the topic and webhook id) as part of `to_signable_string`, or otherwise cryptographically bind `shop` to the verified payload before it is trusted by callers (e.g., have `HmacValidator` validate a canonical string that concatenates body and shop-domain header, matching what is actually authorized to be trusted as `shop`).

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and configures a webhook subscription.
2. Shopify sends a legitimate webhook to the app: body `B`, headers include `X-Shopify-Hmac-SHA256: H` (valid for `B`) and `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`.
3. Attacker replays `POST /webhooks` with the same body `B` and same `X-Shopify-Hmac-SHA256: H`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {..., "shopify-shop-domain" => "victim-shop.myshopify.com", "shopify-hmac-sha256" => H})` is constructed, and `Utils::HmacValidator.validate(request)` returns `true` since only `B` is checked.
5. Any handler that keys off `request.shop` (`"victim-shop.myshopify.com"`) now processes an attacker-crafted event as if it originated from the victim's shop, having passed HMAC validation.
