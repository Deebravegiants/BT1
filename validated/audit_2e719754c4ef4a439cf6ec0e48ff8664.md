### Title
Unbounded borrow-index growth overflows RAY unscale and permanently freezes all market verbs — (File: contracts/pool/src/cache/scale.rs)

### Summary
The pool's interest accrual grows `borrow_index` until a multiplication inside the index unscale path overflows `i128` and panics. Because every controller verb accrues first (`update_indexes` is invoked before supply/withdraw/repay/borrow/liquidate), once the index crosses the overflow point the market is frozen permanently: no repayments, no withdrawals, no liquidations, no `clean_bad_debt`. The configured `MAX_BORROW_INDEX_RAY` cap never engages because the overflow happens inside the accrual arithmetic before the cap check is reached.

### Finding Description
The analog to CVE-2021-40565 (unchecked deref → crash → DoS) is an unchecked fixed-point multiplication that panics instead of degrading. In the RAY-scale machinery (`scaled_to_original` / `original_to_scaled` under `contracts/pool/src/cache/scale.rs`), accrued interest is computed as `scaled * index`. The borrow index compounds millisecond-chunked accrual with no early bound, so `scaled_amount * borrow_index` eventually exceeds `i128::MAX` and the host traps on `MathOverflow` before the code compares the index against `MAX_BORROW_INDEX_RAY`.

The protocol's own regression test proves the frozen end state: after the cliff, `update_indexes`, `withdraw`, and `repay` all revert with `MATH_OVERFLOW`, and the stored index is still below `MAX_BORROW_INDEX_RAY`, confirming the cap is dead code on this path. [1](#0-0) 

### Impact Explanation
Permanent freezing of funds and protocol insolvency for the affected (hub, token) book. Suppliers cannot withdraw, borrowers cannot repay, liquidators cannot liquidate, and `clean_bad_debt`/`recapitalize` accrue first and hit the same panic. All user funds in that book are unrecoverable — matching the accepted "permanent freezing of funds" impact.

### Likelihood Explanation
Low but non-zero and attacker-influenceable. The cliff needs the index to grow ~170x on a book whose total scaled debt is large (the test uses a 10-billion-unit, 18-decimal market at ~98% utilization on the steep XLM curve for many years). An unprivileged attacker cannot trigger it instantly, but sustaining high utilization is within any borrower's power, utilization curves are permissionless inputs via ordinary `borrow`, and the failure mode requires no privileged action. Because the panic is sticky (the oversized index is already committed), once reached it is irreversible.

### Recommendation
Bound the growth before the multiplication: check `index > MAX_BORROW_INDEX_RAY` (or the implied ceiling `i128::MAX / total_scaled`) using `checked_mul`/`checked_div` on the accrual path, and clamp/write the capped index rather than panicking. The cap must be enforced on the index value itself inside `accrue`, not after a `scaled * index` product that can overflow first. Alternatively saturate accrual at the index cap so downstream verbs continue to operate on a frozen-but-consistent index.

### Proof of Concept
Existing in-repo test demonstrates the freeze:

```rust
// tests/test-harness/tests/controller/large_positions_and_long_horizons.rs
t.supply_raw(BOB, "BIG18", principal);            // BILLION * 10^18
t.borrow_raw(ALICE, "BIG18", debt);               // ~98% utilization
// advance years until accrual panics:
assert_contract_error(failed, errors::MATH_OVERFLOW);
assert!(last.borrow_index < MAX_BORROW_INDEX_RAY); // cap never engaged
assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
``` [2](#0-1) 

An unprivileged sequence: supply large collateral → `borrow` to push utilization to the steep curve segment → let `update_indexes` compound until `scaled_to_original` overflows → every subsequent call on that book reverts forever.

Caveat: I could not re-verify the exact ordering of the cap check versus the unscale multiply inside `scale.rs`/accrual within the available iterations; the claim that the overflow precedes the cap rests on the test's assertion `last.borrow_index < MAX_BORROW_INDEX_RAY` at failure.

/// `i128::MAX`, 170 times that. At the XLM curve's steep segment the index
/// grows past 170x in a few years, and the next accrual panics inside
/// `scaled_to_original`. Every verb accrues first, so the market freezes:
/// no repay, no withdraw, no liquidation. The index cap never engages.
#[test]
fn a_whale_market_at_sustained_high_utilization_hits_the_ray_value_ceiling_before_the_index_cap() {
    let mut t = LendingTest::new()
        .with_market(big("BIG18", 18, xlm_curve()))
        .with_market(col())
        .with_max_utilization_disabled_all_markets()
        .build();
    lift_caps(&t, "BIG18", 18);
    lift_caps(&t, "COL", 7);
    let principal = BILLION * 10i128.pow(18);
    t.supply_raw(BOB, "BIG18", principal);
    let debt = principal / 100 * 98;
    t.supply_raw(ALICE, "COL", BILLION * 10_000_000 * 3);
    t.borrow_raw(ALICE, "BIG18", debt);

    let mut years = 0u32;
    let failure = loop {
        years += 1;
        assert!(
            years <= 40,
            "no cliff within 40 years; the bound in docs/reference/formulas.md is wrong"
        );
        t.advance_time(YEAR_SECS);
        if let Err(e) = t.try_update_indexes_for(&["BIG18"]) {
            break e;
        }
    };
    let failed: Result<(), soroban_sdk::Error> = Err(failure);
    assert_contract_error(failed, errors::MATH_OVERFLOW);
    let last = book(&t, "BIG18");
    assert!(
        last.borrow_index < MAX_BORROW_INDEX_RAY,
        "the index cap did not engage before the value overflow"
    );
    // The market is frozen: exits and repayments accrue first and hit the same panic.
    assert_contract_error(t.try_withdraw_raw(BOB, "BIG18", 1), errors::MATH_OVERFLOW);
    assert_contract_error(t.try_repay(ALICE, "BIG18", 1.0), errors::MATH_OVERFLOW);
    std::println!(
        "ray-value cliff reached after {years} years at 98 percent utilization on the XLM curve; last index x{:.1}",
        last.borrow_index as f64 / RAY as f64
    );
```
