### Title
Missing ERC20 return-value checks in Tron `IntentGatewayV2.withdraw()` and `onAccept` SweepDust path allow escrowed user funds to be marked settled without being transferred - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron-specific `IntentGatewayV2` contract redeems escrowed intent tokens using a raw low-level `.call()` to the ERC20 `transfer` selector and only checks that the *call itself* did not revert (`success`), never decoding/validating the boolean return value encoded in the returned data. This is the exact bug class described in the external report for `ERC20WrapperBundler`: any ERC20 implementation that returns `false` on failure instead of reverting (a valid, EIP-20-compliant behavior) will cause the gateway to treat the transfer as successful, decrement escrow accounting, and emit success events — while the tokens never leave the contract.

### Finding Description
`withdraw()` is the internal function invoked from `onAccept()` when Hyperbridge delivers a `RedeemEscrow` or `RefundEscrow` message (fill settlement / order refund) [1](#0-0) , and from `onGetResponse()` for the GET-based refund path. Inside `withdraw()`, ERC20 payouts are performed like this:

```solidity
(bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success) revert TransferFailed();
``` [2](#0-1) 

The same unchecked pattern is repeated for the transaction-fee payout in the same function [3](#0-2) , and for the `SweepDust` admin-triggered dust sweep inside `onAccept` [4](#0-3) .

`success` here only reflects whether the low-level call reverted; it does not decode the ABI-encoded `bool` that `IERC20.transfer` is supposed to return. A standards-compliant-but-non-reverting ERC20 (returns `false` instead of reverting on failure — e.g. paused tokens, blocklisted transfers, insufficient-balance edge cases in non-OpenZeppelin implementations) will make this call return `success = true` with returndata `abi.encode(false)`. The check `if (!success) revert TransferFailed()` will not fire, the code proceeds to decrement `_orders[body.commitment][token]` as if the beneficiary was paid, and emits `EscrowReleased`/`EscrowRefunded`, permanently losing track of the tokens that remain stuck in the gateway contract.

This directly parallels the reported `ERC20WrapperBundler.erc20WrapperDepositFor()/erc20WrapperWithdrawTo()` bug: the code checks that an external call did not revert but never validates the actual boolean success value returned by the token/wrapper, letting execution continue as if the transfer succeeded.

Notably, the non-Tron, primary EVM `IntentGatewayV2` implementation uses OpenZeppelin's `SafeERC20`/`IERC20` with `.safeTransfer`/`.safeTransferFrom` throughout (e.g. `evm/src/apps/IntentGatewayV2.sol`, `evm/tron/contracts/apps/IntentGatewayV2.sol:250,321,405,459` for inbound transfers), which correctly validates return data. The Tron variant, however, diverges specifically in the outbound escrow-redemption/dust-sweep paths (`withdraw()` and the `SweepDust` branch of `onAccept()`), reverting to raw `.call()` without decoding the boolean result.

### Impact Explanation
Escrow accounting (`_orders[commitment][token]`) is decremented and `_filled[commitment]` is marked regardless of whether tokens actually reached the beneficiary. Since Hyperbridge's cross-chain intents model relies on `withdraw()` being the sole path by which solvers/users are paid out of escrow, a token that returns `false` on failed transfer causes:
- Permanent loss/freezing of the escrowed funds for that order (they remain stuck in the `IntentGatewayV2` contract, unaccounted for, since `_orders` was already decremented and the commitment marked filled), and
- Any leftover balance becomes takeable by unrelated parties via the `SweepDust` admin path or accumulates as unassignable dust, meaning the intended beneficiary permanently loses their funds while the contract silently reports success (`EscrowReleased`/`EscrowRefunded`/`DustSwept` events fire as if the transfer succeeded).

This satisfies "permanent freezing of funds" for the affected order/token, reachable directly from a relayed cross-chain message settling an intent (`RedeemEscrow`/`RefundEscrow`) or a GET-response refund — both are permissionless, relayer-triggered paths (`onAccept`, `onGetResponse`) acting on user-submitted intents.

### Likelihood Explanation
Triggering requires only that the intent's input/output token be an ERC20 implementation that returns `false` rather than reverting on transfer failure — a behavior explicitly allowed by the ERC20 standard and common in some token implementations (e.g., certain wrapped/blocklist-capable tokens, some legacy tokens, or custom project tokens integrated as intent assets). Since `IntentGatewayV2` is a general-purpose intents/bridging gateway meant to support arbitrary tokens configured by users/solvers, and Tron's own ecosystem includes tokens with non-standard-but-compliant transfer semantics (e.g., TRC20 tokens historically diverging from strict OZ semantics), the likelihood that at least one supported asset exhibits this behavior is significant, and no privileged action is needed to trigger it — a normal order fill/refund flow is sufficient.

### Recommendation
Replace all raw `.call()` invocations of `transfer`/related token movement in the Tron `IntentGatewayV2.sol` (`withdraw()`'s token loop, its fee-token payout, and `onAccept`'s `SweepDust` branch) with `SafeERC20.safeTransfer`, which is already imported and used elsewhere in the same file (`using SafeERC20 for IERC20;`). This decodes and validates the boolean return value (or absence thereof) and reverts on failure, aligning the outbound payout paths with the same safety guarantee already applied to the inbound `safeTransferFrom` calls in this contract.

### Proof of Concept
1. Deploy a mock ERC20 whose `transfer(address,uint256)` returns `false` (does not revert) when, e.g., the recipient is blocklisted — mirroring the `ERC20WrapperNotReverting` pattern from the referenced report.
2. Configure this token as an order's input/output asset and place an intent via `placeOrder`, escrowing tokens into `IntentGatewayV2`.
3. Have Hyperbridge deliver a `RedeemEscrow`/`RefundEscrow` message (or trigger the GET-response refund) naming the blocklisted beneficiary, invoking `withdraw()` at [5](#0-4) .
4. Observe: `token.call(...)` returns `success = true` with encoded `false`; the `if (!success)` check passes; `_orders[body.commitment][token]` is decremented and `EscrowReleased`/`EscrowRefunded` is emitted, yet `token.balanceOf(beneficiary)` is unchanged and the tokens remain stranded in the `IntentGatewayV2` contract with no remaining accounting path to recover them for that beneficiary.
