### Title
Webhook shop-domain identity not covered by HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the `shop` used by application handlers from the `shop-domain` HTTP header, but the HMAC signature validated by `Utils::HmacValidator` only covers the raw request body, not this header. This breaks the identity binding: `shop_used_by_handler == shop_covered_by_hmac` is false.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `Request#shop` is read straight from the unauthenticated `shopify-shop-domain`/`x-shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the request purely via `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `to_signable_string` (i.e. the body only) and then immediately hands `request.shop` to the app's handler as the authoritative tenant identifier: [3](#0-2) 

`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it to the `hmac` header value — again, the shop header never enters this computation: [4](#0-3) 

Because the `api_secret_key` is the same for every shop the app is installed on, any legitimate webhook delivery (from any shop where the attacker has installed the app — a trivial, unprivileged action) produces a `(raw_body, hmac)` pair that is valid under the shared secret regardless of which shop's data it corresponds to. An attacker can capture one authentic `(body, hmac)` pair from their own shop and replay it to the app's webhook endpoint with an arbitrary `shopify-shop-domain` header set to a victim shop. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid), and `Registry.process` passes the forged `shop` value straight into `WebhookMetadata` for the handler: [5](#0-4) 

The equality that should hold — "the shop asserted in the identity-relevant field equals the shop whose bytes were actually verified by the HMAC" — is broken: the gem verifies bytes of the body but attributes the result to a header that was never part of what was verified.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` (the value the gem itself surfaces as "the shop this webhook is about") to key persistence, permissions, or business logic will process/store forged data under an attacker-chosen victim shop's identity — a cross-tenant data injection facilitated entirely by the gem's own trust decision (accepting the header-derived shop as validated once `HmacValidator.validate` succeeds). This satisfies the "cross-tenant access" criterion, since the tenant boundary (`shop`) that the gem hands to callers as verified is actually attacker-controlled.

### Likelihood Explanation
The only prerequisite is the ability to install the target app on at least one shop the attacker controls (a normal, unprivileged, self-service action — creating a free Shopify dev/partner store is enough) in order to receive one genuinely signed webhook delivery, then replaying that exact body over the webhook endpoint with a forged `shop-domain` header. No access token, `client_secret`, or privileged account is required — only observation of one legitimate webhook delivery to any store, which is by design delivered to the app's public endpoint.

### Recommendation
Include the shop-domain (and other identity-relevant headers such as `webhook-id`/`api-version`) in the signable material used for HMAC verification, or otherwise independently bind the header-derived `shop` to a value that is cryptographically covered by the signature before exposing it via `WebhookMetadata`. At minimum, `Utils::HmacValidator` should verify a canonical string that includes the shop domain, not just the raw body, so `Request#shop` cannot be substituted without invalidating the HMAC.

### Proof of Concept
1. Attacker creates a free Shopify development store `attacker.myshopify.com` and installs the target app, giving Shopify's servers the app's `api_secret_key`-derived legitimacy to deliver signed webhooks to the app's endpoint.
2. Attacker triggers any webhook event on `attacker.myshopify.com` (e.g., updates a product) and captures the raw POST: headers include `x-shopify-hmac-sha256: <H>` and `x-shopify-shop-domain: attacker.myshopify.com`, body `B`. `H = HMAC-SHA256(secret, B)` per `HmacValidator.compute_signature`.
3. Attacker resends the exact same body `B` and HMAC header `H` to the same webhook endpoint, but replaces `x-shopify-shop-domain` with `victim-shop.myshopify.com`.
4. `Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(secret, B) == H` → true, since `B` and `H` are unchanged and the shop header is not part of the signed content.
5. `Registry.process` invokes the registered handler with `WebhookMetadata.new(... shop: "victim-shop.myshopify.com" ...)`, causing the app to process attacker-supplied data attributed to `victim-shop.myshopify.com`.
