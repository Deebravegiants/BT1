### Title
POA Bridge withdrawal status matched only by `assetId`, causing wrong destination tx hash to be reported for batch withdrawals of the same token - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal()` resolves the completion status/destination tx hash of a specific withdrawal within a batch by matching only on `assetId` (`near_token_id`), not on the withdrawal's unique identity (e.g. index, destination address, or amount). When a single NEAR intent transaction contains **two or more withdrawals of the same underlying token** (e.g., to two different destination addresses/amounts), `findMatchingWithdrawal` returns the **first** entry in the POA API's unsorted list that matches the assetId for every caller, regardless of which of the batched withdrawals is actually being queried.

The `index` parameter that is part of the `WithdrawalIdentifier` (and was previously used, per the changelog entry "Fix POA bridge withdrawal matching to use assetId instead of index") is not used at all to disambiguate between multiple same-asset withdrawals in the batch.

### Impact Explanation
If a caller creates a batch withdrawal containing two or more withdrawals of the same POA-bridged asset (e.g., withdrawing the same token to two different destination addresses/amounts in one intent), `waitForWithdrawalCompletion`/`createWithdrawalCompletionPromises` can report the **wrong destination transaction hash** for one of the two withdrawals. An integrator relying on the SDK's per-withdrawal completion result to mark a specific withdrawal as settled (and to reconcile/credit/refund) could:
- mark the wrong withdrawal as completed with a tx hash that actually belongs to the sibling withdrawal, or
- report both entries as completed using the same tx hash, leading to double-crediting/refund-reconciliation errors downstream.

This matches the "High" impact category: a status/hash misreport that can cause an integrator to credit or refund based on incorrect completion data.

### Likelihood Explanation
Likelihood is limited by two factors: (1) it requires a batch of ≥2 withdrawals of the *same* POA-bridged asset in a single intent transaction (supported by the SDK's `processWithdrawal`/batch API, per README's "Batch Withdrawals" feature), and (2) the POA Bridge API itself does not currently expose enough data to disambiguate withdrawals of the same asset (per the code comment), so the flaw is inherent to any client using this endpoint, not just this SDK. Still, nothing in the SDK actively prevents or warns against constructing such a batch, so a legitimate integrator use case (e.g., withdrawing the same token to two recipients) can trigger it silently.

### Recommendation
- Reject/validate batches containing multiple withdrawals of the same `assetId` routed through the POA bridge until the POA API supports disambiguation, or
- Implement the documented fallback (sort both the API's withdrawal list and the local `withdrawalParams` by amount for same-asset entries) to restore correct order-based correlation, and
- Add a regression test covering a batch with two same-asset PoA withdrawals to ensure each index resolves to its own transfer hash.

### Proof of Concept
1. Call `sdk.processWithdrawal`/`createWithdrawalCompletionPromises` with `withdrawalParams = [ {assetId: "nep141:btc.omft.near", destinationAddress: A, amount: 100}, {assetId: "nep141:btc.omft.near", destinationAddress: B, amount: 200} ]` routed via PoA bridge, executed in one NEAR tx.
2. POA Bridge API's `getWithdrawalStatus({withdrawal_hash: tx.hash})` returns both withdrawal entries (unsorted) for that tx.
3. For each of the two SDK-side `describeWithdrawal` calls (index 0 and index 1), `findMatchingWithdrawal` filters purely by `nep141:btc.omft.near === assetId`, so both calls resolve to the **same first matching entry** from the API list (see `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427`), returning identical `transfer_tx_hash` for what are two distinct on-chain destination transfers.
4. An integrator polling both `TxInfo` results receives the same destination tx hash for withdrawals that went to different destination addresses/amounts, producing an incorrect completion record for at least one of them.

Note: I was not able to find any existing dedup/validation logic anywhere in `packages/intents-sdk` or `packages/internal-utils` that would prevent constructing such a same-asset batch, based on the searches performed (`createWithdrawalIdentifiers`, "duplicate"/"same asset"/"dedup" grep). This increases confidence the gap is unmitigated, though I could not exhaustively review every call site given tool-call limits.

	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

	public createWithdrawalCompletionPromises(
		params: CreateWithdrawalCompletionPromisesParams,
	): Array<Promise<TxInfo | TxNoInfo>> {
		const { withdrawalParams, intentTx, signal, logger } = params;

		const widsPromise = createWithdrawalIdentifiers({
			bridges: this.bridges,
			withdrawalParams,
			intentTx,
		});

		// Track the last promise per HOT bridge landing chain for sequential waiting.
		// HOT bridge processes withdrawals sequentially per chain with ~30s gaps,
		// so polling in parallel would cause later withdrawals to timeout.
		const hotChainLastPromise = new Map<Chain, Promise<TxInfo | TxNoInfo>>();

		return withdrawalParams.map(async (_, index) => {
			const wids = await widsPromise;
			const entry = wids[index];
			assert(entry != null, `Missing wid for index ${index}`);

			// Only apply sequential waiting for HOT bridge
			if (entry.bridge.route === RouteEnum.HotBridge) {
				const landingChain = entry.wid.landingChain;
				const previousPromise = hotChainLastPromise.get(landingChain);

				const sequentialPromise = (async () => {
					if (previousPromise) {
						// Wait for previous withdrawal to same chain to complete.
						// Use allSettled to continue even if previous fails.
						await Promise.allSettled([previousPromise]);
					}
					return watchWithdrawal({
						bridge: entry.bridge,
						wid: entry.wid,
						signal,
						logger,
					});
				})();

				hotChainLastPromise.set(landingChain, sequentialPromise);
				return sequentialPromise;
			}

			// Non-HOT bridges: parallel polling (existing behavior)
			return watchWithdrawal({
				bridge: entry.bridge,
				wid: entry.wid,
				signal,
				logger,
			});
		});
