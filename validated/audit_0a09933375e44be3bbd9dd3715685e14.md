## Finding: Webhook `shop`, `topic`, `webhook_id`, and `api_version` are trusted from unauthenticated headers while the HMAC only covers the raw body

### Title
Webhook signature does not bind `shop-domain`/`topic` headers, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content as only the raw request body, while `shop`, `topic`, `webhook_id`, and `api_version` are read directly from unauthenticated HTTP headers and then handed to app code as verified, trusted metadata. This is the "field acted on but not covered by the HMAC" analog: the identity-binding property `hmac == HMAC(secret, shop || topic || body)` that a webhook consumer needs is not what's actually enforced; only `hmac == HMAC(secret, body)` is checked.

### Finding Description
`Webhooks::Request#to_signable_string` returns solely `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled straight from headers, with no cryptographic binding to the signature: [2](#0-1) 

`Registry.process` validates only that signature, and then dispatches to the handler using the topic and shop taken from the same unauthenticated headers, presenting them as verified `WebhookMetadata`: [3](#0-2) 

`HmacValidator.validate` (shared with OAuth callback validation) simply recomputes the HMAC over `to_signable_string` and compares it, with no knowledge that `shop`/`topic` exist: [4](#0-3) 

Because a given app uses **one shared `client_secret`/`api_secret_key` across all shops that install it**, any merchant who has installed the app can legitimately receive a genuinely-signed webhook delivery (valid `raw_body` + valid HMAC) for their own shop. That merchant — an "unprivileged" party with respect to any *other* tenant's data — can replay the exact same `raw_body`/HMAC pair to the app's webhook endpoint while substituting a different value in the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header. The signature check in `HmacValidator.validate_signature` still passes because it never inspects those headers, yet `Registry.process` will hand the handler a `WebhookMetadata` claiming the payload originated `from` the victim shop: [5](#0-4) 

The binding that breaks, stated as an equality that should hold but doesn't:
`shop_claimed_by_header == shop_that_produced(raw_body, hmac)` — the library only proves `HMAC(secret, raw_body) == received_hmac`; it never proves the header-derived `shop`/`topic` were part of what was signed.

### Impact Explanation
Any app built on this gem that uses `request.shop` (or `request.topic`) from `WebhookMetadata` to key per-tenant data (e.g., "which merchant's order was created/updated", "which shop's data should this webhook update") can be tricked into attributing/ingesting one shop's event data under another shop's identity — a cross-tenant data-integrity/confusion issue. This satisfies the "cross-tenant access" criterion in the Critical impact bucket, since the tenant boundary (`shop`) is not authenticated at all, only body content is.

### Likelihood Explanation
Exploitability requires only: (1) being an app-installing merchant (no special privilege beyond ordinary tenant access, satisfying "unprivileged internet user"), (2) capturing one legitimately delivered webhook to their own endpoint, and (3) POSTing it again to the app's public webhook URL with a modified `shop-domain`/`topic` header. No possession of `api_secret_key` or any other party's credentials is needed, since the same signed body/HMAC pair is reused verbatim — no forgery of the HMAC itself is required.

### Recommendation
Bind the identifying fields into the signable content the library computes, or otherwise fail closed when they aren't self-consistent with the verified payload — e.g., include `shop`, `topic`, and `webhook_id` in `to_signable_string` if Shopify's webhook payload/headers support it, or require app developers to independently verify `shop` against their own webhook subscription registry (matching `webhook_id` to a specific shop/topic pair) rather than trusting the header value as pre-verified metadata once `HmacValidator.validate` returns `true`.

### Proof of Concept
1. Merchant M installs App on `m-shop.myshopify.com`; App receives a genuine webhook: `raw_body = B`, headers include `x-shopify-shop-domain: m-shop.myshopify.com`, `x-shopify-hmac-sha256: H` (valid, since `H = HMAC(secret, B)`).
2. M crafts a new HTTP request to the App's webhook endpoint with the same body `B` and same header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate(request)`, which recomputes `HMAC(secret, B)` and finds it equals `H` — validation passes: [6](#0-5) 
4. The handler is invoked with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, so the App processes M's own event data as though it belongs to `victim-shop.myshopify.com`.
