### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing shop-domain spoofing on otherwise-valid webhook payloads - ([File: lib/shopify_api/webhooks/request.rb](lib/shopify_api/webhooks/request.rb))

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `HmacValidator.validate` never authenticates the `X-Shopify-Shop-Domain` header. `Registry.process` nevertheless trusts `request.shop` (parsed straight from that unauthenticated header) as the tenant identity it hands to the app's webhook handler. This breaks the equality "shop authenticated by the HMAC" == "shop used as the tenant identifier delivered to the app," analogous to the NFTPool bug where a state-changing action (transfer) was not reflected in/verified against the tracking mapping (`ownerToId`).

### Finding Description
`HmacValidator.validate_signature` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it (via `OpenSSL.secure_compare`) to the `hmac` header value: [1](#0-0) 

For `ShopifyAPI::Webhooks::Request`, `to_signable_string` is defined as just the raw body: [2](#0-1) 

Meanwhile `shop` is read directly from the `x-shopify-shop-domain` / `shopify-shop-domain` header, with no cryptographic binding to the signed payload: [3](#0-2) [4](#0-3) 

`Registry.process` validates the HMAC and then forwards `request.shop` verbatim to the app's handler as the authoritative tenant identity for the event: [5](#0-4) 

By contrast, the OAuth `AuthQuery` (used for the install/callback HMAC) correctly folds `shop` and `host` into the signed string, so that identity is authenticated end-to-end: [6](#0-5) 

The webhook path has no equivalent binding: the signature only proves "this body byte sequence was produced with the shared `api_secret_key`" — it proves nothing about which shop the request claims to be from. Since the `api_secret_key` is shared across all shops that install the same app, any attacker who is themselves a legitimately-installed merchant (an unprivileged, non-attacker-controlled-secret actor with respect to any other tenant) can capture a validly-signed webhook payload for their own shop and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to a victim shop. `HmacValidator.validate` still returns `true` (only the body bytes are checked), and `Registry.process` passes the forged victim shop straight into `WebhookMetadata`, which host applications use to scope their tenant-specific processing (session lookup, data writes, etc.) — exactly the intended, documented use of `WebhookMetadata#shop`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to guarantee to host applications: a request that passes signature verification can carry an unauthenticated shop identity. Any host app that relies on `Registry.process`'s HMAC check plus `data.shop` (as intended/documented) to route or scope webhook processing per-shop can be made to process attacker-supplied body content under another shop's identity — a cross-tenant confusion originating entirely from this gem's own trust boundary (the signature does not cover the identity field it is meant to protect).

### Likelihood Explanation
Any user who can install the target app on their own shop (a normal, unprivileged action — no leaked secrets, no TLS interception, no social engineering) can obtain a validly HMAC-signed webhook body for events on their own shop and then directly POST it to the app's public webhook endpoint with a forged shop-domain header. No privileged credentials beyond normal app installation are required.

### Recommendation
Include the shop-identifying header (and ideally topic/webhook-id) in the HMAC-covered signable string for webhooks, or otherwise cryptographically bind `shop` to the verified payload, mirroring how `AuthQuery#to_signable_string` binds `shop`/`host` into its signed string.

### Proof of Concept
1. Merchant A installs the app on `attacker.myshopify.com`. Shopify sends a legitimately signed webhook: body `{"id":1}`, headers `x-shopify-hmac-sha256: <valid-hmac-of-body>`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker replays the exact same body and HMAC header to the app's webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: body, headers: headers)` is constructed; `request.shop` returns `"victim.myshopify.com"`.
4. `Registry.process(request)` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `request.to_signable_string` (the raw body) — this still matches, since the body and HMAC were untouched: [7](#0-6) 
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim.myshopify.com", body:, ...)`, i.e., attacker-controlled body content is delivered under the victim shop's identity despite no cryptographic proof that Shopify ever sent this event for `victim.myshopify.com`.
