Found a valid analog. The bug-class from the report ("a value used for one purpose is verified using bytes that don't cover it") maps directly onto Shopify's webhook processing pipeline in this gem, where the `shop` field that identifies the tenant is never covered by the HMAC that "validates" the request.

### Title
Webhook `shop` (and `topic`/`webhook-id`) header is trusted without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body, while `shop`, `topic`, `webhook_id`, and `api_version` are read straight from unauthenticated HTTP headers. `Webhooks::Registry.process` treats a successful `Utils::HmacValidator.validate(request)` as proof the *entire request* (including `shop`) is authentic, then hands `request.shop` to the host app's handler as trusted tenant identity. The equality the code implicitly assumes — "HMAC-verified bytes == the `shop` value acted on" — does not hold.

### Finding Description
`Request#to_signable_string` signs only the body: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are never part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string` (i.e. the body only) and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` gates the whole request on that single HMAC check, then constructs `WebhookMetadata` using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id` and passes it straight to the app's handler as if it were verified: [4](#0-3) 

Because the API secret key (`client_secret`) is the same for every shop that has the app installed, an unprivileged internet user can:
1. Install the target public app on their own (free/dev) Shopify store.
2. Trigger a real webhook (e.g. `products/update`, `orders/create`) with an attacker-controlled body, receiving a genuinely Shopify-signed `(body, hmac)` pair for their own shop.
3. Replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint, but with the `x-shopify-shop-domain` header rewritten to the victim shop's domain (and/or the topic/webhook-id headers changed).

`HmacValidator.validate` still succeeds because it only checks the body against the secret, so `Registry.process` accepts the request and calls the handler with `shop: <victim-shop>` and an attacker-controlled body content, even though that body never actually originated from — or was signed on behalf of — the victim shop.

The binding that should hold is:
`HMAC-verified bytes == (shop, topic, body) acted upon by the handler`
but in this implementation:
`HMAC-verified bytes == body only`, while `shop`/`topic`/`webhook_id` are taken from unauthenticated headers.

### Impact Explanation
This breaks the tenant-identity binding of the webhook pipeline: the gem hands the host application a `shop` value that appears authenticated (having passed `HmacValidator.validate`) but is not. Any host app that uses `WebhookMetadata#shop` to look up its stored per-shop session/access token, or to attribute the (attacker-controlled) body content to that shop's data, can be tricked into performing cross-tenant actions or ingesting forged data under another merchant's identity — matching the Critical "cross-tenant access" impact category, since the identity of the acting tenant is not bound to the verified bytes.

### Likelihood Explanation
Any unprivileged internet user who can install the target app on a store they control (trivial for public apps, and even for many private/custom apps in review) can obtain a validly-signed `(body, hmac)` pair and replay it with a forged `shop` header — no access token, `client_secret`, or credential leak is required, and the attack is purely a matter of crafting an HTTP request to the app's already-exposed webhook endpoint.

### Recommendation
Include the `shop`, `topic`, and `webhook_id` values in the signed material (or otherwise cryptographically bind them to the body before computing/verifying the HMAC), or document/require that host applications independently authenticate the `shop` header against a shop for which they hold an active, previously-established session before trusting `WebhookMetadata#shop`. At minimum, `Utils::HmacValidator` and `Webhooks::Registry.process` should not implicitly present `request.shop` as "verified" when only the body is covered by the signature.

### Proof of Concept
```ruby
# 1. Attacker installs the target app on their own shop "attacker.myshopify.com"
#    and triggers a webhook (e.g. products/update) with attacker-controlled body.
#    Shopify sends a legitimately signed request:
raw_body = '{"id":123,"title":"pwned"}'
hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body) # computed by real Shopify

# 2. Attacker replays the exact same body+hmac to the app's webhook endpoint,
#    but forges the shop header to point at a victim shop they do not own/control:
headers = {
  "x-shopify-topic" => "products/update",
  "x-shopify-hmac-sha256" => Base64.encode64(hmac),
  "x-shopify-shop-domain" => "victim-shop.myshopify.com",  # forged, unauthenticated
  "x-shopify-webhook-id" => "any-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Webhooks::Registry.process(request)
# => HmacValidator.validate(request) succeeds (only raw_body is checked),
#    handler.handle(data: WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...))
#    is invoked, and the host app now believes this attacker-crafted event
#    came from "victim-shop.myshopify.com".
```
