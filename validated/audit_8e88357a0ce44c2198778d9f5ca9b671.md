### Title
DoS via unbounded Borsh allocation when decoding untrusted `SignedTransaction` on JSON-RPC endpoints - (File: chain/jsonrpc/src/api/transactions.rs)

### Summary
The `ipfs/kubo` advisory describes a DoS where a malformed CAR file's length-prefixed fields cause `go-car` to allocate arbitrarily large buffers before validating that the claimed size matches actual available data, crashing nodes that call `ipfs dag import` on untrusted input. Nearcore has the same bug class reachable through its public JSON-RPC transaction-submission endpoints: `decode_signed_transaction()` Borsh-decodes an attacker-supplied byte blob with no upper bound on its size, whereas the equivalent P2P network path was deliberately hardened against exactly this attack.

### Finding Description
`decode_signed_transaction` in [1](#0-0)  base64-decodes the caller-supplied string and immediately calls `SignedTransaction::try_from_slice(&bytes)` with no size gate applied to `bytes` before deserialization. This function backs the `broadcast_tx_async`, `broadcast_tx_commit`, `send_tx`, and `tx` (status, when a signed tx is embedded) JSON-RPC methods, all reachable by any unauthenticated client, as documented in [2](#0-1) .

By contrast, the P2P network protocol code path for the exact same `SignedTransaction` type explicitly enforces a pre-decode size limit, with an accompanying comment describing the very attack this defends against: [3](#0-2) 
and the shared helper used to implement it: [4](#0-3) 

The regression test for the network path even documents the threat model explicitly: an oversized/inflated Borsh body must be rejected *before* decoding "so the inflated nested-action `Vec` is never materialized at decode time" — see [5](#0-4) . This confirms the maintainers know that a length-prefixed field (e.g., `Vec<Action>` or a `Vec<u8>` inside `DeployContractAction`/`FunctionCallAction` within `TransactionV0.actions`, see [6](#0-5) ) can force a large allocation purely from its encoded length header, independent of whether the remaining bytes in the buffer can actually satisfy that length.

The only bound protecting the JSON-RPC path is the generic HTTP body size limit (`RpcLimitsConfig::json_payload_max_size`, default 10 MB) applied via `RequestBodyLimitLayer` in [7](#0-6) . That limit only bounds the *encoded* request size — it does nothing to stop a small request whose internal length fields claim allocations far larger than the bytes actually present, which is precisely the amplification pattern in the referenced advisory.

### Impact Explanation
An attacker with no privileges (any client able to reach the public JSON-RPC port, default 3030) can submit a crafted, undersized base64 blob whose embedded Borsh length prefix for a nested `Vec` (e.g., transaction actions, function-call args, or contract-deploy code) claims a very large element count/byte length. Because the size check applied to the network-protocol path is absent here, `SignedTransaction::try_from_slice` can be induced to allocate memory proportional to the attacker-controlled length field rather than the actual request size, before any subsequent validation or size rejection can occur. Repeated requests can exhaust node memory and crash the RPC/validator process — a denial-of-service matching "node panic or unbounded resource use."

### Likelihood Explanation
High likelihood: `broadcast_tx_async`/`broadcast_tx_commit`/`send_tx` are core, publicly documented, unauthenticated JSON-RPC methods intended for exactly this kind of untrusted client input (any wallet or dApp can call them), and the vulnerable code path (`decode_signed_transaction`) is the very first thing executed on every call before any transaction validation.

### Recommendation
Apply the same defense used for the P2P path: bound the size of `bytes` (after base64 decoding) in `decode_signed_transaction` with `try_from_slice_with_limit` (or an equivalent inline check) using a limit consistent with `MAX_TRANSACTION_SIZE_BYTES`, before calling `SignedTransaction::try_from_slice`. Apply the same treatment to any other JSON-RPC/HTTP entry points that Borsh-decode untrusted client-controlled byte blobs directly (e.g., the Rosetta RPC hex-decoded Borsh deserialization in `chain/rosetta-rpc/src/utils.rs`).

### Proof of Concept
1. Construct a minimal `Vec<u8>`/`Vec<Action>`-bearing structure by hand where the 4-byte little-endian length prefix for a nested vector is set to a very large value (e.g., `u32::MAX`) while only a handful of actual trailing bytes are supplied — mirroring the shape of a `TransactionV0` with a `DeployContractAction { code: Vec<u8> }` whose declared `code` length vastly exceeds the bytes present.
2. Base64-encode this short byte sequence and POST it to `/` as:
```json
{"jsonrpc":"2.0","id":"dontcare","method":"broadcast_tx_async","params":["<base64 payload>"]}
```
3. `decode_signed_transaction()` (`chain/jsonrpc/src/api/transactions.rs:71-76`) base64-decodes and calls `SignedTransaction::try_from_slice` directly, with no size gate — unlike the network-protocol path, which would reject the same payload via `try_from_slice_with_limit` before decode. Sending many such small requests concurrently drives large allocation attempts on the RPC actor, consistent with the memory-exhaustion class described in the referenced go-car advisory.

```rust
/// Borsh-deserializes `T` from `bytes`, rejecting inputs larger than `limit`
/// before decoding so a maliciously inflated peer payload cannot force a large
/// allocation at decode time. Use this for any peer-supplied borsh blob whose
/// decoded form can be much larger than its wire size; `limit` must sit above
/// the largest legitimate encoding of `T` and well below the peer-frame cap.
/// Returns `io::Error` so it composes with the borsh-based proto decode sites.
pub fn try_from_slice_with_limit<T: BorshDeserialize>(bytes: &[u8], limit: usize) -> io::Result<T> {
    if bytes.len() > limit {
        return Err(io::Error::new(
            io::ErrorKind::InvalidData,
            format!("encoded size {} exceeds the limit of {limit} bytes", bytes.len()),
        ));
    }
    T::try_from_slice(bytes)
}
```
