### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) identity fields are trusted from unauthenticated HTTP headers, not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC of the raw request body [1](#0-0) . The `shop`, `topic`, `webhook_id`, and `api_version` values that get handed to the app's `WebhookHandler` are read straight from HTTP headers and are never part of the signed material.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [2](#0-1) , and `HmacValidator.validate`/`validate_signature` compute/compare the HMAC exclusively against that signable string using `Context.api_secret_key` [3](#0-2) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are pulled directly from the `shopify-shop-domain`/`x-shopify-shop-domain` (etc.) HTTP headers with no cryptographic binding to the body or to each other [4](#0-3) .

`Registry.process` uses the HMAC-validated body only to authenticate the request, then constructs `WebhookMetadata` straight from these unauthenticated header fields and dispatches it to the app's handler: [5](#0-4) 

`WebhookMetadata.shop` is a `const :shop, String` field intended to identify which merchant/tenant the event belongs to [6](#0-5) .

The binding that should hold is: `hmac == HMAC(secret, body || shop || topic || webhook_id)`, i.e., the tenant identity delivered to the handler should be cryptographically tied to the same signature that authenticates the message. Instead the actual binding is only `hmac == HMAC(secret, body)`, while `shop` (and the other identity headers) are accepted unauthenticated as long as *some* valid body+HMAC pair for the app's `client_secret` is presented.

Because a single Shopify app uses one `client_secret` (`api_secret_key`) shared across every shop that installs it, any merchant who has legitimately installed the app can capture a genuine webhook delivery (raw body + valid `x-shopify-hmac-sha256` value) that Shopify sent for their own store, and then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and/or `topic`/`webhook-id`) to name a different, victim shop. `HmacValidator.validate` still returns `true` because it only checks the body against the shared secret; `Registry.process` will then invoke the app's handler with `WebhookMetadata` claiming the event came from the victim shop's store. If the host application uses `data.shop` to select which merchant record/session to update, upsert order/customer data against, or trigger side effects (redaction handling, uninstall handling, order creation, etc.), the attacker achieves cross-tenant data injection under a spoofed shop identity, using only their own legitimate app installation.

### Impact Explanation
This crosses a tenant boundary using only an unprivileged install of the same app: no access token, `client_secret`, or victim credentials are required — only a single genuine webhook capture from the attacker's own shop. It matches the "Critical – cross-tenant access" bucket: the gem itself hands the host application an event object whose declared tenant (`shop`) is not bound to the authenticity check (`hmac`), enabling one tenant to make the app believe an event originated from another tenant.

### Likelihood Explanation
Likelihood is high for any app that registers HTTP webhook delivery via `ShopifyAPI::Webhooks::Registry`: capturing one's own legitimate webhook delivery (body + HMAC) is trivial for any merchant who installs the app, and replaying it with modified `shop`/`topic` headers requires no special access — only the ability to send an HTTP request to the app's public webhook endpoint, since the gem's own header-parsing (`shopify_header`) accepts either the legacy `x-shopify-*` or new `shopify-*` header set without any cross-check against the signed body.

### Recommendation
Include the tenant-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) in the signable string used for HMAC verification, or otherwise cryptographically bind them to the signed body (e.g., verify `shop` against a value independently known for the delivery, or require an additional per-shop secret/signature covering headers) before constructing `WebhookMetadata` and dispatching to the handler.

### Proof of Concept
1. App installs are per-shop but the webhook `client_secret` is shared across all shops for the app.
2. Attacker installs the app on their own shop (`attacker-shop.myshopify.com`) and triggers a real webhook, capturing the raw body `B` and the valid header `x-shopify-hmac-sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker sends a new HTTP request to the app's webhook endpoint with the same body `B` and header `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com` (and optionally a different `topic`).
4. `ShopifyAPI::Webhooks::Request.new` parses headers, `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` [7](#0-6) .
5. `Registry.process` builds `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed_body, ...)` and calls the app's `handler.handle(data:)` [8](#0-7) , causing the app to process the event as if it belongs to `victim-shop.myshopify.com`, even though the attacker never had any relationship with that shop.

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
