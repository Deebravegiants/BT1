### Title
Unrestricted swap-route contract invocation can attach arbitrary wallet-draining token transfers to the caller’s signed authorization tree - ([File: contracts/controller/src/strategies/swap.rs](contracts/controller/src/strategies/swap.rs))

### Summary
`swap_collateral`, `swap_debt`, and `repay_debt_with_collateral` accept caller-controlled opaque route bytes and forward them to the configured swap router. The router dispatches those bytes to payload-selected pool/token addresses without an allowlist, allowing a malicious route contract to execute arbitrary token calls underneath the caller’s `require_auth` context. If the victim signs the authorization tree produced by simulation, the malicious contract can transfer unrelated wallet tokens in addition to performing a valid swap.

### Finding Description
The controller exposes user-controlled `swap: Bytes` parameters on `swap_debt` and `swap_collateral` and passes them into `process_swap_debt` / `process_swap_collateral`. [1](#0-0) 

`StrategySwap` is opaque bytes interpreted by the swap router rather than a controller-validated route structure. [2](#0-1) 

Before router execution, the controller authorizes only one exact input-token transfer from itself to the router, but then invokes `execute_strategy` with the caller-supplied payload. [3](#0-2) 

The router executes decoded route operations and passes payload-selected `pool`, `token_in`, and `token_out` addresses to venue dispatch. [4](#0-3) [5](#0-4) 

Venue dispatch invokes the named pool contract and validates only the router’s token balance deltas; it does not establish that the pool is a trusted or previously registered venue contract. [6](#0-5) 

A malicious hop contract can therefore call an unrelated token’s `transfer(victim, attacker, amount)` while the victim’s controller authorization is on the call stack. The test double demonstrates this exact behavior through `UnlistedPoolRouter.execute_strategy`, which invokes `route.hop_pool.swap()`. [7](#0-6) 

The malicious pool then performs an attacker-selected wallet-token transfer. [8](#0-7) 

### Impact Explanation
This is theft of user funds outside the assets nominally involved in the lending operation. The malicious route can return a valid swap output, satisfy the controller’s positive-output and risk checks, and still move an unrelated wallet token to the attacker. [9](#0-8) 

The loss is not bounded by `amount_in`, `min_out`, account collateral, or final health checks because the malicious child transfer can name any token and amount held by the victim. The project’s own threat model states that neither the payload minimum nor the final risk gate bounds this loss. [10](#0-9) 

### Likelihood Explanation
An unprivileged attacker can deploy a malicious hop contract, encode it in a route, and induce a victim to execute `swap_collateral`, `swap_debt`, `repay_debt_with_collateral`, or `multiply` with that route. Transaction simulation records the malicious token transfer as a child of the victim’s controller authorization rather than as a separate obvious approval. [11](#0-10) 

The attack succeeds when the victim signs the simulated tree containing the extra transfer. Enforcing-mode tests show that the same route moves the victim’s wallet token once that child invocation is included in the signed authorization tree. [12](#0-11) 

Likelihood is constrained by the need for the victim to sign a poisoned authorization tree, but wallets and clients commonly render these nested invocations poorly, and the protocol accepts routes that can legitimately contain additional contract calls. This supports a High severity impact with a meaningful social-engineering/client-integration precondition.

### Recommendation
Do not permit route payloads to introduce arbitrary executable pool contracts under a lending authorization. Maintain an explicit governance-approved registry of venue/pool contract addresses and require every route hop to resolve to one of those registered addresses; reject user-supplied executable addresses not present in the registry.

Additionally, clients should simulate every strategy transaction, decode the complete route payload, and reject any authorization tree containing calls other than the single expected input transfer and known venue calls. A contract-side allowlist is still required because authorization-tree inspection is a client-side control and cannot reliably protect all callers.

### Proof of Concept
The repository contains a focused PoC in `tests/test-harness/tests/strategy/rogue_hop_pool_transfer_joins_caller_auth_tree.rs`.

1. Alice supplies USDC and holds `77_770_000_000` units of an unrelated wallet token. [13](#0-12) 
2. The attacker deploys `RogueHopPool` with Alice’s address, the unrelated wallet token, the attacker recipient, and the full wallet balance. [14](#0-13) 
3. A route encodes that pool, USDC input, ETH output, and a fair minimum output. [15](#0-14) 
4. Alice calls `swap_collateral`; the router invokes the attacker-controlled pool, which calls `wallet_token.transfer(Alice, attacker, WALLET_BALANCE)`. [16](#0-15) 
5. Simulation records that transfer as a child of Alice’s `swap_collateral` authorization. [17](#0-16) 
6. When Alice signs the poisoned tree, the entire unrelated wallet balance moves to the attacker while the expected ETH output is still deposited. [12](#0-11)
