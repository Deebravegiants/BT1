Based on my investigation, I found the closest analog in the `do_signup` flow: the `user_centric_signup` branch that entirely bypasses the authoritative backend enrollment/verification step, trusting a locally-controlled flag instead.

### Title
"App-centric" signup path bypasses backend enrollment verification, trusting a client-supplied flag as if it were an authoritative signup completion - (File: src/plans/mod.rs)

### Summary
In `MasterPlan::do_signup`, when `user_data.user_centric_signup` is `true` (a value taken directly from the QR-code-linked backend `user_status` response controlled by the app/user side of the flow) and the operator config `ignore_user_centric_signups` is `false`, the orb completely skips the call to `enroll_user` — the function that actually round-trips with the backend (`signup_post`/`signup_poll`) to authoritatively record and confirm the enrollment. Instead, `result.success`/`enrollment_status` is derived purely from the local `signup_reason` computed from local fraud/pipeline checks. This mirrors the reported bug class: an authoritative state transition (vault epoch end / enrollment completion) is expected to gate a dependent privileged action (staking rewards / enrollment success reporting), but a secondary code path relies on stale/locally-trusted state instead of re-validating against the authoritative source, letting a "should be expired/unconfirmed" condition still produce a privileged outcome.

### Finding Description [1](#0-0) 

When `user_centric_signup` is true, the code sets the enrollment status directly:
```
let success = if user_centric_signup && !orb.config.lock().await.ignore_user_centric_signups {
    debug_report.enrollment_status(match signup_reason {
        SignupReason::Normal => enroll_user::Status::Success,
        _ => enroll_user::Status::Error,
    });
    signup_reason == SignupReason::Normal
} else {
    Box::pin(self.enroll_user(...)).await.is_success()
};
```
Compare this to the `else` branch, which calls `enroll_user::Plan::run`, which performs `signup_post::request` and polls `signup_poll::request` in a retry loop to get an authoritative confirmation from the backend before declaring success: [2](#0-1) 

In the `user_centric_signup` branch, `enrollment_status`/`success` is set to `Success` purely because the *local* `signup_reason` (derived from `detect_fraud` and pipeline completion) equals `Normal` — with no backend confirmation call at all. `detect_fraud` itself is a stub with all fraud checks removed in this build (`// FOSS: WE HAVE DELETED ALL FRAUD CHECKS`), so `signup_reason` will essentially always resolve to `Normal` whenever the pipeline succeeds: [3](#0-2) 

The root cause parallel to the reported bug: the "authoritative epoch/enrollment state" (backend-confirmed signup) is supposed to gate whether a signup is reported as successful (analogous to the vault's real value after epoch end). But a separate, loosely-coupled path (the `user_centric_signup` shortcut, analogous to `StakingRewards`' independent `periodFinish`) doesn't check that authoritative state and instead reports success based on stale/local computation.

### Impact Explanation
If this local-only success determination is inconsistent with what the backend recorded (e.g., backend-side signup validation fails, is rejected, or the biometric data wasn't actually persisted/enrolled), the orb will still report `signup_successful` in telemetry/dbus and to the UI, and downstream flows treat the signup as legitimately completed without confirmation. This is a "cross-signup state bleed"/misattributed-signup risk: the local device declares an enrollment success that the backend never confirmed, producing a mismatch between the orb's belief of enrollment state and backend record of enrollment state.

### Likelihood Explanation
This path is gated by `user_data.user_centric_signup`, a field returned from the backend/app-controlled QR-link payload, and by the operator-level config flag `ignore_user_centric_signups` being `false` (the non-default path enabling this "app-centric" behavior). Given that fraud checks are stubbed out entirely in this build, the condition `signup_reason == SignupReason::Normal` is met whenever pipeline processing completes normally, making the shortcut highly likely to trigger whenever this feature flag combination is active.

### Recommendation
Remove or gate the `user_centric_signup` shortcut so that reported enrollment success always requires an authoritative round-trip confirmation from the backend (as in the `enroll_user` path), rather than relying solely on locally computed `signup_reason`. At minimum, verify the backend's own signup completion for the given `signup_id`/`user_id` before setting `enrollment_status(Success)`.

### Proof of Concept
Not independently reproducible from the indexed code alone (no test harness for this branch was found in the index); the vulnerable logic itself is directly cited above at [4](#0-3) . Full exploitation confirmation (e.g., whether operators can flip `ignore_user_centric_signups` and whether `user_centric_signup` is attacker-influenceable through the QR-link payload) would require inspecting the full backend `user_status`/QR-link contract, which the current index does not fully expose — a Devin session with full repo access would be needed to trace `orb_qr_link::UserData.user_centric_signup` origin and mutability end-to-end.
