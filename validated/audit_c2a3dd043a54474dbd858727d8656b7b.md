### Title
Permanent Loss/Freezing of Escrowed IntentGatewayV2 Funds When Beneficiary Is a Blacklistable ERC20 (USDT/USDC) and Gets Blocklisted - (File: evm/src/apps/intentsv2/IntentsBase.sol)

### Summary
`IntentsBase._withdraw`, invoked from `ExtrinsicIntents.onAccept` (RedeemEscrow / RefundEscrow) and `onGetResponse`, releases escrowed order tokens via a hardcoded `beneficiary` address that was encoded into the cross-chain `WithdrawalRequest` at order-fill/cancel time on a remote chain. If the escrowed token is a blacklist-capable ERC20 (USDT/USDC) and that beneficiary is later blocklisted by the token issuer, `IERC20(token).safeTransfer(beneficiary, amount)` reverts every time the message is redelivered, permanently freezing the escrow with no mechanism to redirect funds to another address.

### Finding Description
`_withdraw` decodes a `beneficiary` address that is fixed by whoever constructed the `WithdrawalRequest` on the remote/source chain (the solver address for `RedeemEscrow`, or `order.user`/`order.output.beneficiary` for `RefundEscrow`/cancellation) and unconditionally attempts an ERC20 transfer to it: [1](#0-0) 

This is called from `ExtrinsicIntents.onAccept` for both `RedeemEscrow` and `RefundEscrow` message kinds, and from `onGetResponse` for source-chain cancellations: [2](#0-1) 

Delivery of this `onAccept` call flows through `EvmHost.dispatchIncoming`, which uses a low-level `.call` and, on failure, deletes the request receipt so the message remains "deliverable" and can be retried by any relayer: [3](#0-2) 

Because the reverting condition (`beneficiary` blacklisted on the ERC20 token) is a property of the token issuer's off-chain blocklist and not of on-chain state that Hyperbridge or the relayer can influence, the message will **never** deliver successfully: every retry replays the identical `safeTransfer(beneficiary, amount)` call, which reverts identically forever. There is no code path in `IntentsBase`/`ExtrinsicIntents` allowing the beneficiary, the order owner, or governance to redirect the payout to a different address once the `WithdrawalRequest` has been dispatched — the beneficiary is baked into the cross-chain message body and cannot be altered after dispatch. Tests confirm the direct, unconditional transfer to the encoded beneficiary for both `RedeemEscrow` and `RefundEscrow` paths: [4](#0-3) [5](#0-4) 

This is the same root cause as the referenced report: a fixed recipient address hard-baked into a cross-chain-verified payload, combined with a blacklist-capable ERC20, produces a permanently undeliverable transfer with no escape hatch.

### Impact Explanation
Escrowed input tokens (e.g., USDC/USDT posted by the user at `placeOrder`) become permanently stuck in the `IntentGatewayV2`/`ExtrinsicIntents` contract:
- On `RedeemEscrow`, the solver who legitimately filled the order on the destination chain can never collect the escrowed input tokens if their receiving address is blacklisted on that token.
- On `RefundEscrow` (cancellation), the original user can never recover their escrowed principal if their address becomes blacklisted between order placement and cancellation.

Because neither retry (relayer redelivery) nor governance action in `ExtrinsicIntents.onAccept` provides any way to change the beneficiary of an already-dispatched `WithdrawalRequest`, this is a genuine permanent freezing-of-funds condition, not merely a temporary retryable failure.

### Likelihood Explanation
Requires: (1) escrowed input token is a blacklist-capable stablecoin such as USDT/USDC, which is an explicitly supported use case (test suite uses USDC as the input token throughout `IntentGatewayV2Test.sol`), and (2) the solver or user address becomes blacklisted after order placement/fill but before withdrawal settles. Given USDT/USDC's real-world use of blacklisting for sanctions/compliance/exploit-response reasons, and that solver/relayer addresses are exposed on-chain and could plausibly be flagged, this is a realistic (if not everyday) scenario for a protocol explicitly designed to move stablecoins cross-chain.

### Recommendation
Do not let a reverting token transfer to a fixed beneficiary permanently block escrow release:
- Wrap the `IERC20.safeTransfer` calls in `_withdraw` in a try/catch (or low-level `call` with success check), and on failure fall back to crediting the beneficiary's balance in an internal pull-based accounting structure (e.g., `_claimable[beneficiary][token] += amount`) that the beneficiary — or a delegate they nominate — can withdraw from with a different destination address.
- Alternatively, allow the beneficiary to pre-register or later update an alternate payout address that `_withdraw` consults if the primary transfer reverts, mirroring the pull-payment pattern used elsewhere in the codebase (e.g., `HyperbridgeLzEndpoint`'s `retryPayload`/stored-payload recovery) rather than a push transfer to an immutable address encoded in the original cross-chain message.

### Proof of Concept
1. User places a cross-chain order with `inputs = [USDC, amount]`, escrowing USDC in `IntentGatewayV2` on the source chain (`placeOrder`).
2. Solver fills the order on the destination chain; `_fillCrossChain` dispatches a `RedeemEscrow` `WithdrawalRequest{commitment, tokens: inputs, beneficiary: solver}` back to source chain.
3. Before the message is delivered, USDC's issuer blacklists the `solver` address (e.g., for an unrelated compliance reason).
4. The relayer delivers the message; `EvmHost.dispatchIncoming` calls `ExtrinsicIntents.onAccept` → `_withdraw` → `IERC20(usdc).safeTransfer(solver, amount)` reverts because `solver` is blacklisted.
5. `EvmHost.dispatchIncoming` catches the failed call, deletes the request receipt, and returns without reverting — the message is marked as retryable.
6. Any subsequent relayer redelivery of the identical message hits the identical revert, forever. The escrowed USDC is permanently trapped in `IntentGatewayV2`, since there is no function to change `beneficiary` for an already-dispatched `WithdrawalRequest`.

    function onAccept(IncomingPostRequest calldata incoming) external override onlyHost {
        _checkRelayer(incoming.relayer);
        RequestKind kind = RequestKind(uint8(incoming.request.body[0]));
        if (kind == RequestKind.RedeemEscrow || kind == RequestKind.RefundEscrow) {
            _authenticate(incoming.request);
            WithdrawalRequest memory body = abi.decode(incoming.request.body[1:], (WithdrawalRequest));
            return _withdraw(body, kind == RequestKind.RefundEscrow, true);
        }

        // only hyperbridge is permitted to perform these actions
        if (keccak256(incoming.request.source) != keccak256(IDispatcher(host()).hyperbridge())) revert Unauthorized();
        if (kind == RequestKind.NewDeployment) {
            _addDeployment(abi.decode(incoming.request.body[1:], (Deployment)));
        } else if (kind == RequestKind.UpdateParams) {
            _updateParams(abi.decode(incoming.request.body[1:], (ParamsUpdate)));
        } else if (kind == RequestKind.SweepDust) {
            _sweepDust(abi.decode(incoming.request.body[1:], (SweepDust)));
        } else if (kind == RequestKind.Execute) {
            Address.functionDelegateCall(ERC1967Utils.getImplementation(), incoming.request.body[1:]);
        }
    }

    function dispatchIncoming(PostRequest memory request, address relayer) external restrict(_hostParams.handler) {
        address destination = _bytesToAddress(request.to);
        uint256 size;
        assembly {
            size := extcodesize(destination)
        }
        if (size == 0) {
            // instead of reverting the entire batch, early return here.
            return;
        }

        // replay protection
        bytes32 commitment = request.hash();
        _requestReceipts[commitment] = relayer;

        (bool success,) = address(destination)
            .call(abi.encodeWithSelector(IApp.onAccept.selector, IncomingPostRequest(request, relayer)));

        if (!success) {
            // so that it can be retried
            delete _requestReceipts[commitment];
            return;
        }
        emit PostRequestHandled({commitment: commitment, relayer: relayer});
    }
