### Title
Emporium `runAction` allows theft of any ERC20/ETH balance held by Emporium that is outside the declared `erc20TokenAddresses` array - ([File: contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol])

### Summary
`EmporiumUpgradeable.runAction` executes an attacker-controlled list of `EmporiumOperation`s with no restriction on which contract (`op.endpoint`) or which token they touch, while the pre/post balance accounting (`balancesBefore`/`balancesAfter`) only iterates the caller-declared `circomData.erc20TokenAddresses`. Any ERC20 balance Emporium holds outside that declared array can be drained via a crafted stateless op (`signerAddress == address(0)`, no signature required), and neither `runAction`'s loop nor `Hinkal.transact`'s outer balance-diff loop will ever notice the outflow.

### Finding Description
The broken equality is value conservation on Emporium:
`sum(tokens leaving Emporium during the call) == -sum(deltaAmountChanges over circomData.erc20TokenAddresses)`

In `runAction`, `balancesBefore`/`balancesAfter` are computed strictly over `circomData.erc20TokenAddresses`: [1](#0-0) [2](#0-1) 

The ops loop makes arbitrary external calls to `op.endpoint` with `op.callData`, only forbidding the `callHinkalWallet`/`doSendToRelay` selectors in the stateless branch - nothing restricts `op.endpoint` to a token in `circomData.erc20TokenAddresses`, nor restricts the callData to only move the declared tokens: [3](#0-2) 

Critically, `verifyWallet` (the only integrity check on `stack.ops`) is a no-op when `stack.signerAddress == address(0)`: [4](#0-3) 
So for a "stateless" Emporium call, the attacker (who authors and proves their own `circomData`/`externalActionMetadata`) needs no signature at all to include arbitrary ops.

The reconciliation loop in `runAction` only accounts for the declared array, and any balance change on undeclared token `j` is simply invisible: [5](#0-4) 

The same blind spot exists one layer up in `Hinkal.transact`, whose slippage/balance-conservation checks also only iterate `circomData.erc20TokenAddresses`: [6](#0-5) 

Attacker's exact call: submit `Hinkal.transact` with `erc20TokenAddresses = [tokenA]`, `deltaAmountChanges[0] < 0` (a normal deposit into Emporium, handled by `Hinkal._externalTransact`'s pre-transfer), and `externalActionMetadata` decoding to an `EmporiumStack` whose `ops` include one legitimate op for `tokenA`, plus an extra stateless op `{endpoint: tokenJ, invokeWallet: false, callData: abi.encodeWithSelector(IERC20.transfer.selector, attacker, tokenJBalance)}`. Since `stack.signerAddress == address(0)`, no EIP-712 signature is checked for the ops array at all, so the attacker can freely add the malicious op. The `transfer` selector is not blacklisted, so the call executes and drains `tokenJ` from Emporium directly to the attacker. Neither `runAction`'s nor `Hinkal.transact`'s accounting loops (which only look at `[tokenA]`) detect this, so the transaction succeeds and the resulting `utxoSet`/nullifier/commitment bookkeeping is entirely consistent for `tokenA` while `tokenJ` silently disappears.

None of the listed guards prevent this: `performHinkalChecks`, `verifyProof`, `rootHashExists`, the slippage/balance `require`s, `insertNullifiers`, and `onlyAllowedRecipient` all operate only on the declared `erc20TokenAddresses`/proof-committed amounts for the tokens the attacker chose to declare; none of them enumerate or constrain the full set of tokens Emporium's `ops` are permitted to touch.

### Impact Explanation
Direct theft of any ERC20 (or ETH) balance residing in the Emporium contract that is not part of the attacker's currently declared token array - e.g., dust/residual balances left by other users' prior Emporium interactions, partially-consumed swap outputs, or forgotten fee-token remainders. This is theft of value that never belonged to the attacker and was never counted in the proof's public inputs or the on-chain accounting loops, matching the Critical category ("direct theft of ... in-flight user funds ... executing calls or moving assets ... never authorised"). The attack is repeatable for every distinct residual token/ balance Emporium ever accumulates, and costs the attacker only a normal Hinkal deposit transaction plus proof generation for their own UTXOs.

### Likelihood Explanation
Preconditions: Emporium must hold a non-zero balance of some token `j` not included in the attacker's declared `erc20TokenAddresses`, and the attacker must know its address (trivially discoverable by monitoring on-chain balances of the public Emporium contract). No privileged role is required - the attacker uses their own funds/UTXOs, their own proof, and a stateless op requiring no signature (`signerAddress == address(0)`). Feasibility is high wherever Emporium is used for multi-step DeFi interactions (swaps, LI.FI routes, etc.) that can leave behind slippage residue or unswept balances; the attacker only needs to wait for or induce such a residual balance.

### Recommendation
Restrict Emporium's op execution so it cannot move any ERC20/ETH other than the tokens declared in `circomData.erc20TokenAddresses` (e.g., maintain an explicit allow-list of tokens/endpoints per call, or require that any token balance change be reflected by enumerating the actual set of tokens touched and reconciling all of them, not just the declared subset). Additionally, require the EIP-712 signature check on `stack.ops` unconditionally (not skip it when `signerAddress == address(0)`), or otherwise cryptographically bind `externalActionMetadata` to the ZK-proved public inputs so an attacker cannot append arbitrary calls outside the audited/declared token set.

### Proof of Concept
Hardhat test plan:
1. Deploy Hinkal, HinkalHelper, EmporiumUpgradeable, register Emporium as external action, register it as `onlyAllowedRecipient`.
2. Fund Emporium with `tokenJ` balance (simulate residue via a normal prior Emporium interaction or a direct `transfer` to Emporium to represent dust).
3. As attacker, deposit `tokenA` via `Hinkal.transact` with `erc20TokenAddresses=[tokenA]`, valid proof for attacker's own UTXOs, `deltaAmountChanges[0]<0`.
4. Set `externalActionMetadata` to an `EmporiumStack` with `signerAddress = address(0)` and `ops = [ {endpoint: tokenA-related op...}, {endpoint: tokenJ, invokeWallet:false, value:0, callData: tokenJ.interface.encodeFunctionData("transfer",[attacker, tokenJBalance])} ]`.
5. Assert: transaction succeeds; `tokenJ.balanceOf(Emporium) == 0` after the call; `tokenJ.balanceOf(attacker)` increased by the full residual amount; the emitted `utxoSet`/on-chain commitments only reference `tokenA`, proving `tokenJ`'s outflow was never accounted for.
6. Assert the broken equality directly: compute `declaredOutflow = -deltaAmountChanges[0]` (tokenA only) vs. `actualOutflow = tokenA moved + tokenJBalance stolen`, showing `actualOutflow > declaredOutflow` while the transaction reverts nowhere.
