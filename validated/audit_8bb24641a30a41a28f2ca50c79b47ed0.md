## Analog Found

### Title
VWAP spread oracle truncates toward zero instead of flooring negative dividends, systematically overstating (best-casing) fillers' negative spreads - (File: `evm/src/utils/VWAPOracle.sol`)

### Summary
`VWAPOracle.spread()` computes a volume-weighted average spread for same-token intent fills using Solidity's native signed-integer division, which truncates toward zero rather than flooring. This is the exact bug class from the referenced report: dividing a value that can be negative by a positive denominator without correcting the rounding direction produces a result that is biased upward (less negative / closer to zero) whenever the division isn't exact — precisely the "doesn't round down for negative dividends" defect flagged in `_getUniswapTwapWei()`.

### Finding Description
`recordSpread()` accumulates `weightedSpreadSum` (an `int256` that is negative whenever a filler pays out less than it received) and `totalVolume` (`uint256`) per `(sourceChain, token)`: [1](#0-0) 

`spread()` then divides: [2](#0-1) 

`data.weightedSpreadSum / int256(data.totalVolume)` is a signed/positive integer division. In Solidity, division always truncates toward zero, not floor. When `weightedSpreadSum` is negative and not an exact multiple of `totalVolume`, the true (mathematically floored) result is more negative than what this division returns — the reported VWAP spread is biased toward being "less bad" than reality, i.e., rounded up instead of down for negative values, mirroring the salty-io `_getUniswapTwapWei()` tick-rounding defect precisely.

`recordSpread()` is only callable by the configured `_intentGateway` (`restrict(_intentGateway)`), but it is triggered on every same-token intent fill via `IntentGatewayV2.fillOrder()` — an action any unprivileged solver/filler can invoke by filling an order. Thus every filled same-token order pushes attacker-influenced `(amount, spread)` pairs into the cumulative state, and the filler fully controls the `inputs`/`outputs` amounts of their own fill (subject to the order's constraints), giving them influence over the exact remainder that triggers truncation bias.

### Impact Explanation
`VWAPOracle` implements `IIntentPriceOracle`, the protocol's designated on-chain reference for same-token fill spreads. Any downstream logic (current or future governance/risk tooling, fee/reward accounting, or automated anti-manipulation checks) that reads `spread()` to detect fillers systematically underpaying users receives a value that is biased toward appearing healthier than the true volume-weighted spread. A filler that structures fill sizes/spreads so that `weightedSpreadSum` is consistently non-exact-divisible by `totalVolume` can keep the reported spread pinned closer to zero than reality, masking value extraction from users and evading any spread-based safeguards, analogous to how the original bug let attackers manipulate the reported price to bypass liquidation/pricing safety checks.

### Likelihood Explanation
Every same-token order fill through `IntentGatewayV2.fillOrder()` calls `recordSpread()`; the rounding bias occurs on virtually all fills whose weighted-spread accumulation doesn't divide evenly by volume, which is the common case for arbitrary decimal amounts. No special privileges are required beyond normal filler participation.

### Recommendation
Match `int256` division rounding to floor semantics for negative dividends, e.g.:
```solidity
int256 rawSpread = data.weightedSpreadSum / int256(data.totalVolume);
if (data.weightedSpreadSum % int256(data.totalVolume) != 0 && data.weightedSpreadSum < 0) {
    rawSpread -= 1;
}
return rawSpread;
```
This mirrors the confirmed fix pattern from the referenced report (decrementing the truncated result by one when the numerator is negative and the division has a remainder).

### Proof of Concept
1. A filler fills two same-token orders for the same `(sourceChain, token)` such that `_updateCumulativeSpread` accumulates `weightedSpreadSum = -5`, `totalVolume = 3` (achievable by choosing input/output amounts producing a spread of `-500 bps` on `1e16` normalized volume units, or any combination yielding a non-exact-dividing negative sum).
2. `spread()` computes `-5 / 3` in Solidity == `-1` (truncated toward zero), whereas the mathematically correct floored VWAP is `-2`.
3. Any consumer reading `spread()` observes a spread of `-1` (appears less severe) instead of the true `-2`, understating the extent of value extracted from users by the filler — reproducible directly against `VWAPOracleTest.sol`'s existing negative-spread test harness (e.g. `testVWAPWithAllNegativeSpreads`) by choosing amounts that leave a nonzero remainder.         bytes32 chainHash = keccak256(sourceChain);
