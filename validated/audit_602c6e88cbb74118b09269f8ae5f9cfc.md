### Title
Onchain commitments for a double-entry (balance-aliased) token allow minting unbacked shielded UTXOs via an Emporium action - (File: contracts/Hinkal.sol / contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
`Hinkal.transact` and `EmporiumUpgradeable.runAction` both derive per-token accounting solely from `balanceOf` snapshots taken independently for each entry of `circomData.erc20TokenAddresses`, with no requirement that these addresses be distinct underlying assets. An attacker can deploy a token pair where a second address `B` mirrors the real balance of an actual token `A` for `balanceOf` purposes but has an independent, no-op/self-controlled `transfer`, causing both indices to observe the same real balance delta `d` and each independently satisfy `balanceDif == amountChanges[i] + utxoAmount(i)`, resulting in two shielded UTXOs (`d` for `A`, `d` for `B`) being committed to the tree while the vault only ever received `d` in real value.

### Finding Description
The invariant the protocol needs is: **real value entering the vault == sum(amountChanges) + sum(on-chain UTXO amounts)**, checked per-token index in `Hinkal.transact`:
```
balanceDif == (onChainCreation[i] ? 0 : amountChanges[i]) + utxoAmount(i)
``` [1](#0-0) 

`balanceDif` for each `i` is computed from `oldBalances`/`newBalances`, which are produced by `getBalancesForArray`, calling `balanceOf` once per array entry with no dedup/aliasing check: [2](#0-1) [3](#0-2) 

The same pattern (independent `balanceOf` snapshot per index, independent per-index `handleOut`) exists inside the external action itself: [4](#0-3) 

Neither `dimensionsCheck` nor `checkOnchainCreation` nor `performHinkalChecks` enforce that `erc20TokenAddresses` entries correspond to distinct/non-aliased assets — they only check array-length equality and per-index onChainCreation/amountChanges consistency: [5](#0-4) [6](#0-5) 

**Attacker's call:** Attacker deploys real token `A` and a second contract `B` whose `balanceOf(owner)` proxies to `A.balanceOf(owner)` (so for any owner, `B` always reports the same live balance as `A`), while `B.transfer`/`transferFrom` are attacker-controlled stubs that always return `true` without moving any real value. Attacker builds `circomData.erc20TokenAddresses = [A, B]`, and crafts an Emporium `externalActionMetadata` whose `ops` cause a real transfer of `d` units of `A` into the Emporium contract (e.g., an op that pulls `d` of `A` from an attacker-controlled endpoint). Because `B.balanceOf` mirrors `A`'s balance for every observed owner (Emporium and then Hinkal), both index `0` (`A`) and index `1` (`B`) observe an identical real balance delta `d` in `EmporiumUpgradeable.runAction` and again in `Hinkal.transact`. `handleOut` is invoked independently for `i=0` and `i=1`, each with `balanceChange = d`, producing:
- `UTXO(A, d)` — backed by a real transfer of `A`.
- `UTXO(B, d)` — created via `transferERC20TokenOrETH(B, Hinkal, d)`, which only calls attacker's no-op `B.transfer`; no real value moves.

Both UTXOs pass `Hinkal.transact`'s balance-diff equation because `balanceDif[0]==balanceDif[1]==d` (mirrored), and the attacker sets `amountChanges[0]=amountChanges[1]=0`, satisfying `d == 0 + d` for both indices independently. Both `OnChainCommitment`s are then inserted into the tree via `insertCommitments`: [7](#0-6) 

The circuit-side constraints (`inTotal + amountChanges === outTotal`, `OverflowPreventer`, etc.) operate purely on private amounts/nullifiers and do not constrain that two distinct `erc20TokenAddresses` public-input entries must reference economically distinct underlying assets — that link is exactly what the Solidity balance-diff check is supposed to (but fails to) enforce, because it trusts `balanceOf` per address without any cross-check for aliasing.

### Impact Explanation
The vault mints a fully spendable shielded UTXO of `d` units of "token `B`" with zero real backing, while having received only `d` of real value in total for the entire call. This is direct "minting shielded value without backing" — protocol insolvency — matching the Critical impact category. The attack is repeatable per call, bounded only by attacker's willingness to deploy new alias tokens, and each execution mints one full unbacked UTXO for every aliased entry added to `erc20TokenAddresses`.

### Likelihood Explanation
Preconditions are fully within reach of an unprivileged attacker: they can deploy arbitrary token contracts, act as their own depositor/relay-less sender (`originalSender == sender`, `relay == address(0)`), generate their own valid ZK proof for the corresponding private amounts/commitments (attacker fully controls all circuit inputs for their own UTXOs), and construct the Emporium `EmporiumStack` ops themselves (they can call any endpoint they want, including one they control to realize the real `A` transfer). No special role, oracle, or third party is needed. Cost is limited to gas and deployment of two toy contracts.

### Recommendation
Do not trust independent per-index `balanceOf` snapshots for accounting integrity. Require `erc20TokenAddresses` entries to be unique addresses (reject duplicates and disallow any address appearing to reference the same balance twice), and/or compute a single, unambiguous balance snapshot keyed by address with a `require` that all entries in `erc20TokenAddresses` are strictly increasing/sorted-unique. Additionally, consider constraining token addresses as part of the circuit's committed public inputs tied to whitelisted, protocol-known token contracts rather than arbitrary attacker-supplied addresses, to eliminate the aliasing/balance-mirroring vector entirely.

### Proof of Concept
Foundry test plan:
1. Deploy `RealToken` (standard ERC20) and `AliasToken` (`balanceOf(owner)` forwards to `RealToken.balanceOf(owner)`; `transfer`/`transferFrom` are no-op stubs returning `true`).
2. Deploy `EmporiumUpgradeable`, `Hinkal`, `HinkalHelper` per normal test harness setup; whitelist Emporium as external action.
3. Fund an attacker-controlled endpoint contract with `d` units of `RealToken`.
4. Craft `EmporiumStack.ops` with a single stateless op that pulls `d` `RealToken` from the endpoint into the Emporium contract.
5. Build `CircomData` with `erc20TokenAddresses = [RealToken, AliasToken]`, `amountChanges = [0,0]`, `onChainCreation = [true,true]`, `slippageValues = [0,0]`, generate a locally valid proof for two on-chain UTXOs of amount `d` each (no offchain commitments needed given `onChainCreation=true`).
6. Call `Hinkal.transact(...)`.
7. Assert: real `RealToken` balance delta of `Hinkal` == `d` (single real transfer), while `onChainCommitments` inserted into the tree total `2*d` in notional value (one `UTXO(RealToken, d)` and one `UTXO(AliasToken, d)`).
8. Assert the broken equality explicitly: `sum(onChainUTXOAmounts) (2d) != netRealTokenReceived (d)`, proving unbacked minting.

    function checkOnchainCreation(
        CircomData calldata circomData
    ) internal pure {
        bool isInternalTransaction = circomData
            .externalActionData
            .externalActionId == 0;

        for (uint i = 0; i < circomData.onChainCreation.length; i++) {
            if (circomData.onChainCreation[i]) {
                require(
                    !isInternalTransaction,
                    "onChainCreation not allowed for internal transactions"
                );
                require(
                    circomData.amountChanges[i] == 0,
                    "amountChanges must be zero when onChainCreation is true"
                );
                for (
                    uint j = 0;
                    j < circomData.inputNullifiers[i].length;
                    j++
                ) {
                    require(
                        circomData.inputNullifiers[i][j] == 0,
                        "inputNullifiers must be zero when onChainCreation is true"
                    );
                }
            }
        }
    }

                block.chainid,
                hinkalAddress,
                circomData
            );
    }
