### Title
Webhook shop/topic/id headers are not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the tenant-identifying `shop`, `topic`, and `webhook_id` values are read straight from HTTP headers that are never included in the signature. `ShopifyAPI::Webhooks::Registry.process` then trusts `request.shop` to route the payload to a handler without any additional verification, breaking the intended binding of "HMAC-verified bytes" == "bytes used to identify the tenant".

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are all pulled from HTTP headers instead of the signed body: [2](#0-1) 

`Registry.process` validates only the HMAC over the body, then dispatches using the unauthenticated `request.shop`/`request.topic`/`request.webhook_id` header values: [3](#0-2) 

The generic `HmacValidator.validate` confirms this: it only compares the HMAC against `verifiable_query.to_signable_string`, i.e. the body, and has no notion of headers at all: [4](#0-3) 

Because Shopify signs webhooks with the single, app-wide `client_secret` (`Context.api_secret_key`) shared across every shop that installs the app, a valid `hmac-sha256` value proves only "this body was signed by our app's secret" — it says nothing about which shop or topic the delivery is for. An attacker who can obtain one genuine, validly-signed webhook delivery (e.g., from their own store where the app is installed, or from any store they control) can resend the same body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain`, `X-Shopify-Topic`, or `X-Shopify-Webhook-Id` headers with arbitrary values. `HmacValidator.validate` will still pass because it never inspects headers, and `Registry.process` will hand the (attacker's own) body to the handler tagged with a forged `shop`.

This is precisely the identity-binding gap called out in the report's bug class: a field ("shop", the tenant discriminator) is *acted on* by the application logic but is not covered by the cryptographic check that is supposed to authenticate the request.

### Impact Explanation
Any host application built on this gem that uses `WebhookMetadata#shop` (or `#topic`) to key per-tenant data (e.g., "look up shop X's session/store record and act on it", or dispatch different business logic per topic) can be tricked into processing a webhook under an incorrect shop or topic. Because the shop identity is the tenant boundary throughout the rest of the gem (`Session#shop`, `SessionUtils`, etc.), this allows cross-tenant confusion: an attacker-controlled payload can be attributed to a victim shop's identity, and app-specific webhook handlers that trust `data.shop` will act on behalf of a shop the attacker doesn't own. This satisfies the "cross-tenant access" Critical impact bucket in this bug class.

### Likelihood Explanation
Exploitation requires only the ability to install/operate the same app on at least one shop (very low bar, and standard app testing/dev stores suffice), plus the ability to replay a captured HTTP request. No possession of `api_secret_key`, access tokens, or any special credential belonging to the victim is required — the attacker uses their own legitimately-signed body and simply forges headers, which the library performs no verification of.

### Recommendation
Include the tenant-identifying headers (`shop-domain`, `topic`, and ideally `webhook-id`) in the HMAC-signable content, or otherwise cryptographically bind them to the body (e.g., by having `to_signable_string` concatenate the relevant headers with the body before hashing) so that any header value that request-handlers rely on for identity is part of what `HmacValidator` verifies. At minimum, document explicitly that `shop`/`topic` are not authenticated and must be corroborated via other means (e.g., checking the caller's shop against known installed shops) before host apps use them as a tenant key.

### Proof of Concept
1. App is installed on `attacker.myshopify.com`.
2. Attacker triggers an event (e.g., `orders/create`) on their own store and captures the resulting webhook: raw body `B`, and headers including `X-Shopify-Hmac-Sha256: H` (valid for body `B` under the shared app secret) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
3. Attacker resends the same `POST` to the app's webhook endpoint with body `B` and header `X-Shopify-Hmac-Sha256: H` unchanged, but `X-Shopify-Shop-Domain: victim.myshopify.com` (and/or a different `X-Shopify-Topic`).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC over `B` only and matches `H` — passes. [3](#0-2) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload actually originated from the attacker's own store, letting the attacker inject cross-tenant events under a victim shop's identity.
