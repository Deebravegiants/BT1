## Title
`placeOrder`'s predispatch escrow crediting trusts an unverified token sweep instead of measuring actual tokens received - ([File: evm/tron/contracts/apps/IntentGatewayV2.sol])

### Summary
The Tron `IntentGatewayV2.placeOrder` predispatch flow escrows tokens into `_orders[commitment][token]` based on a *pre-transfer* balance snapshot of the `CallDispatcher`, without ever re-checking the gateway's own post-transfer balance. Any ERC20 whose `transfer()` call can return `true` (satisfying `CallDispatcher.dispatch`'s low-level `success` check) without actually moving the full reported balance lets an order placer credit phantom escrow that is later paid out of the shared pool of other users' legitimately escrowed funds — the exact "flashloan end result isn't controlled" bug class from the referenced Ajna report, applied to an escrow-crediting sweep instead of a loan-repayment check.

The check `balance < requiredAmount` is a **precondition** taken on the `CallDispatcher`'s balance *before* the sweep call executes, and the `_orders[commitment][token] += reducedInputs[i].amount` credit happens unconditionally, *before* `dispatch(abi.encode(transferCalls))` is even invoked and with no subsequent verification that `IERC20(token).balanceOf(address(this))` actually increased by the reported amount.

`CallDispatcher.dispatch` only checks the low-level `call.success` boolean, not the ERC20 return-data semantics of a well-behaved `transfer`: [2](#0-1) 

```solidity
function dispatch(bytes memory encoded) external {
    Call[] memory calls = abi.decode(encoded, (Call[]));
    ...
    (bool success, bytes memory result) = to.call{value: call.value}(call.data);
    if (!success) revert CallFailed(to, result);
}
```

Any token that reports success on `transfer()` while internally withholding accounting for some or all of the amount (blacklist logic, paused-transfer accounting bugs, a future upgrade that changes internal bookkeeping, or simply a non-standard ERC20 that returns `true` unconditionally) will pass both the `dispatch` success check and the pre-transfer `balance < requiredAmount` gate, yet leave the gateway's real token balance short of what was just credited to `_orders[commitment][token]`.

This is architecturally identical to the Ajna M-13 pattern: a value is moved out (to the dispatcher, then supposedly swept back), an external call executes in between (the predispatch calldata plus the arbitrary `transfer` call routed through `CallDispatcher`), and the invariant "the contract actually holds what it now believes it holds" is never re-verified with a balance-before/balance-after diff on `address(this)`. Notably, the sibling non-Tron implementation (`evm/src/apps/IntentGatewayV2.sol`) *does* perform this diff correctly (`balancesBefore[i]` captured on `address(this)`, then `received = IERC20(token).balanceOf(address(this)) - balancesBefore[i]`), confirming the Tron variant is missing the safety check that exists elsewhere in the same codebase for the same feature.

### Impact Explanation
`_orders[commitment][token]` is a shared escrow ledger drawn from by `_withdraw` when the order is later filled/settled, paying out of the gateway's aggregate token balance rather than a per-order sub-account: [3](#0-2) 

If an order placer credits phantom escrow via a misbehaving/upgraded token (or one deliberately deployed for this purpose, in the case of arbitrary-token orders), that credited amount is later paid out to the solver/beneficiary from real balances that belong to *other users'* escrowed orders in the same token — a direct theft of pooled funds, matching the "up to full loss of user's funds" impact rated Medium in the source report.

### Likelihood Explanation
Exploitation requires an order to use a token whose `transfer()` can report success without moving the full reported balance — this is a low-probability but realistic condition (proxy/upgradeable tokens changing internal accounting, blacklist-style tokens, or a griefer deploying a custom "arbitrary" input token accepted by the order flow), consistent with the "Medium" severity classification used in the original report. Any unprivileged user can place such an order themselves, so no privileged role is required to trigger it.

### Recommendation
Mirror the balance-diff pattern already used in `evm/src/apps/IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` before dispatching the sweep `transferCalls`, execute the sweep, then compute `received = balanceOf(address(this)) - before` and only credit `_orders[commitment][token] += min(received, reducedInputs[i].amount)` (adjusting `order.inputs`/dust accounting to the actually-received amount), rather than trusting the pre-sweep `balanceOf(dispatcher)` reading and an unconditioned credit.

### Proof of Concept
1. Deploy a malicious/misbehaving ERC20 `T` whose `transfer(to, amount)` always returns `true` but only actually moves a fraction of `amount` (or none) to `to`, simulating an upgraded token that silently withholds internal accounting for certain addresses.
2. User places an order with `order.predispatch.assets` containing `T` and `order.inputs` requiring `T` with `amount = X`, and a `predispatch.call` that is a no-op or trivial approve.
3. `placeOrder` transfers `X` of `T` to the `CallDispatcher`, `balanceOf(dispatcher) == X >= requiredAmount` passes, `transferCalls` is built to call `T.transfer(gateway, X)`.
4. `CallDispatcher.dispatch` calls `T.transfer(gateway, X)`; `T` returns `true` but only sends e.g. `0` tokens to the gateway.
5. `_orders[commitment][T] += reducedInputs[i].amount` is credited for the full `X` regardless, even though the gateway's real `T` balance did not increase.
6. A solver later fills the order and, on settlement, `_withdraw` pays out `X` of `T` to the solver from the gateway's pooled `T` balance — funds that came from *other* orders' legitimately escrowed `T`, resulting in those orders' escrow being under-collateralized/undeliverable.
