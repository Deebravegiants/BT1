## Analog Found

### Title
Unbounded BEEFY signature-recovery loop lets an unprivileged, feeless `handle_unsigned` submission force unbounded `secp256k1_recover` work per node - (File: `modules/consensus/beefy/verifier/src/lib.rs`)

### Summary
`verify_mmr_update_proof` iterates over every entry of `mmr.signed_commitment.signatures` — an ordinary `Vec<SignatureWithAuthorityIndex>` with no `BoundedVec`/max-length constraint at the type level (`modules/consensus/beefy/primitives/src/lib.rs:59-66`) — and performs an expensive `secp256k1_recover` + double `keccak256` for **every** entry before the cheap merkle-membership check that would actually validate the signatures against the trusted authority set. The only prior gate is `check_participation_threshold(signatures_length, authority_set.len)`, which enforces a supermajority *lower* bound; I could not confirm from the available code whether it also enforces an *upper* bound equal to `authority_set.len` or rejects duplicate `sig.index` values before the recovery loop runs.

### Finding Description

This verification path is reached through `ismp::messaging::Message::Consensus` submitted via `pallet_ismp::Call::handle_unsigned`, an **unsigned, feeless, permissionless** extrinsic: [2](#0-1) 

Critically, `ValidateUnsigned::validate_unsigned` fully executes `Self::execute(messages.clone())` — i.e. runs the entire signature-recovery loop — during **mempool validation**, before the extrinsic is even included in a block: [3](#0-2) 

The signatures vector itself carries no compile-time/decode-time cap: [4](#0-3) 

This mirrors CVE-2024-28182's bug class: expensive per-item cryptographic/decoding work is performed unconditionally for every attacker-supplied item in a batch, with the cheap rejection check (merkle membership proof) deferred until *after* all the costly work is done — exactly as nghttp2 kept decoding HPACK CONTINUATION frames (expensive state-sync work) for a stream already destined to be discarded, because no cap existed on the number of frames/items processed per logical unit.

### Impact Explanation
Every node in the network (both mempool-validating and block-producing) pays the full `secp256k1_recover` + double-hash cost for each entry an attacker places in `signatures`, without payment, since `handle_unsigned` is fee-free by design (documented explicitly: "This allows users execute ISMP datagrams for free. Use with caution."). A resubmission loop of oversized/duplicate-signature batches can be repeated indefinitely at zero cost to the attacker, degrading node CPU availability network-wide — a resource-exhaustion (DoS) impact on message delivery infrastructure, consistent with a Medium-severity finding, analogous to the CVE.

### Likelihood Explanation
Likelihood depends on facts I was unable to fully verify before running out of investigation budget:
- Whether `check_participation_threshold` (definition not located within the available index) also caps `signatures_length` at `authority_set.len`, which would bound the maximum multiplier of wasted work relative to a legitimate proof.
- Whether `sig.index` duplicates are rejected before the recovery loop (I found no such check in the shown code).

If `check_participation_threshold` only enforces the lower/supermajority bound (as its name and the surrounding comments suggest — "Fewer than the BEEFY supermajority threshold... signed the commitment" in `modules/consensus/beefy/verifier/src/error.rs:29-31`), then the vector length is effectively attacker-controlled up to the transaction/extrinsic size limit, and the finding stands at Medium likelihood. This uncertainty should be resolved by a maintainer/Devin session inspecting the exact body of `check_participation_threshold`.

### Recommendation
- Bound `signatures.len()` to at most `authority_set.len` (or a small constant multiple) before performing any `secp256k1_recover` calls, rejecting the message outright otherwise.
- Reject duplicate `sig.index` values up front (cheap `BTreeSet` insert check) before entering the recovery loop, so repeated identical signatures cannot be used to inflate work.
- Consider deferring/skipping full `execute()` inside `validate_unsigned` for consensus messages whose signature count already fails a cheap pre-check, so mempool validation cannot be turned into free, repeatable CPU-burning oracle calls.

### Proof of Concept
1. Construct a `ConsensusMessage` wrapping an `MmrProof` whose `signed_commitment.signatures` contains, e.g., 100,000 entries — either duplicated valid-format signatures or garbage 65-byte blobs, at index values covering (or not) 2/3+1 of the current authority set to pass `check_participation_threshold`.
2. Wrap it in `pallet_ismp::Call::handle_unsigned { messages: vec![Message::Consensus(msg)] }` and submit as an unsigned transaction to any Hyperbridge-connected node's RPC.
3. Observe that `ValidateUnsigned::validate_unsigned` runs `Self::execute` synchronously in the transaction-pool validation path, invoking `secp256k1_recover` and `keccak256` roughly 100,000 times, before ultimately failing the merkle-membership check (`InvalidAuthoritiesProof`) or succeeding if signatures are validly duplicated for real signers.
4. Because the call is unsigned/fee-less, the submission can be repeated indefinitely, amplifying CPU cost across every mempool-validating node with zero cost to the submitter.
