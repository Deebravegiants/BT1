### Title
Webhook shop-tenant identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` only binds the HMAC signature to the raw request body, while the `shop` (and `topic`/`webhook_id`/`api_version`) values that identify *which tenant* the webhook belongs to are taken verbatim from unauthenticated HTTP headers. `Registry.process` trusts these header-derived values to attribute the (HMAC-verified) body to a shop, without the shop itself ever being part of what was verified. This is the same class of bug as the reported finding: a field that is *acted on* (here, tenant attribution) is not covered by the authentication check that gives the data its trust (here, the HMAC).

### Finding Description
`HmacValidator.validate` verifies `verifiable_query.hmac` against `verifiable_query.to_signable_string`: [1](#0-0) 

For webhook requests, `to_signable_string` returns only the raw body — none of the identifying headers are included: [2](#0-1) 

`shop`, `topic`, `webhook_id`, and `api_version` are all read directly from HTTP headers (`shopify-shop-domain`, `shopify-topic`, etc.) with no cryptographic binding to the body that was actually signed: [3](#0-2) [4](#0-3) 

`Registry.process` validates only the HMAC over the body, then constructs a `WebhookMetadata` object using the unauthenticated `request.shop` header value and hands it to the app's handler as trusted tenant context: [5](#0-4) 

`WebhookMetadata.shop` is a plain `String` field with no further verification: [6](#0-5) 

The broken identity equality is:
```
shop_used_for_tenant_attribution (request.shop, header, unauthenticated)
   ==
shop_that_actually_produced_the_HMAC-signed_body (never checked)
```//
Before the attack, for a genuine Shopify-delivered webhook these two values coincide because Shopify itself sets both consistently. After the attack, an unprivileged attacker who legitimately owns their own shop can capture a real `(raw_body, hmac)` pair that Shopify sent for their own shop's webhook (any topic the app subscribes to, with attacker-influenced body content, e.g. `orders/create` on an order they place with attacker-controlled line-item/customer text fields), and replay that exact `raw_body` + `x-shopify-hmac-sha256` header to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) with a victim shop's domain. `HmacValidator.validate` still succeeds — it only checks the body against the secret, which is unchanged — but `Registry.process` now dispatches attacker-controlled body content into the app's per-shop handler logic labeled as the victim shop.

### Impact Explanation
This crosses the tenant boundary the gem is supposed to enforce: it allows one merchant (attacker, who legitimately installed the app on their own store) to inject data attributed to a different merchant's shop into the host application's webhook processing pipeline, without ever needing the app's `api_secret_key`. Depending on what the app does with `WebhookMetadata.shop` (e.g., looking up the victim's stored access token/session by shop, or writing data keyed by shop), this can lead to cross-tenant data confusion/injection — matching the "Critical: cross-tenant access" impact category, since the gem is the component responsible for asserting webhook authenticity and it fails to bind the claimed shop to the verified payload.

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must: (1) be a real, unprivileged merchant able to install the target app on their own store (normal, unprivileged action for public apps) and receive at least one genuine webhook whose body content they can influence, and (2) be able to send arbitrary HTTP requests with attacker-chosen headers to the app's publicly reachable webhook endpoint (its only job is to accept `POST` requests from the internet, so this is trivially possible). No secret key, TLS interception, or privileged access is required — only observing one legitimate webhook delivery to their own store and crafting a header-modified replay.

### Recommendation
Bind the tenant-identifying headers to the same value that is cryptographically verified. Concretely, include `shop`, `topic`, `webhook_id`, and `api_version` (or at minimum `shop`) in the signed string, or otherwise verify the header-derived shop against an independent trust anchor (e.g., cross-check `request.shop` against the shop associated with the session/registration the app expects for that webhook) before trusting it in `WebhookMetadata`. At minimum, document explicitly and prominently that `Request#shop`/`topic`/`webhook_id` are **not** authenticated by `HmacValidator.validate` and that host applications must independently verify shop identity before acting on webhook payloads keyed by `request.shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker-shop.myshopify.com`, subscribing the app to a webhook topic it processes (e.g. `orders/create`).
2. Attacker places an order whose body fields (e.g., note, custom attributes) they fully control, and captures the legitimate webhook delivery Shopify sends to the app, including the `X-Shopify-Hmac-SHA256` header and raw body.
3. Attacker replays the exact same raw body and `X-Shopify-Hmac-SHA256` value to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com` (and adjusts `X-Shopify-Topic`/`X-Shopify-Webhook-Id` as needed for the target handler).
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the (unchanged) raw body against the (unchanged) secret: [7](#0-6) 
5. The registered handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and `body` containing attacker-controlled content, believing it originated from the victim shop.
