Confirmed: the webhook `shop` field is documented as trusted tenant-identifying data (`docs/usage/webhooks.md` lines 12-16, 125-135), and the code path binds it directly into `WebhookMetadata` for the handler to act on, while the HMAC only covers the raw body.

### Title
Webhook shop-domain header is trusted for tenant identity but is not covered by the HMAC signature - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#shop` reads the tenant identity directly from the unauthenticated `X-Shopify-Shop-Domain` header, while `ShopifyAPI::Utils::HmacValidator.validate` only verifies the HMAC over the raw request body (`Request#to_signable_string` returns `@raw_body`). `ShopifyAPI::Webhooks::Registry.process` accepts any request whose HMAC matches the body, then passes the unauthenticated `shop` header straight into `WebhookMetadata`, which is the documented, trusted tenant identifier handed to the app's webhook handler.

### Finding Description
The identity binding broken is: `shop` value used by the handler to attribute webhook data to a tenant ≠ `shop` bytes actually covered by the HMAC signature.

- `Request#hmac` and `Request#to_signable_string` only bind the `hmac-sha256` header to `@raw_body`: [1](#0-0) 
- `Request#shop` is read straight off the `shop-domain` header with no cryptographic binding to the signed body: [2](#0-1) 
- `Registry.process` validates only the HMAC and then forwards `request.shop` unchanged into the handler payload: [3](#0-2) 
- The gem's own documentation instructs app authors to treat `data.shop` as the authoritative tenant identity for downstream processing (e.g., enqueuing per-shop jobs), with no instruction to cross-check it against the signed payload: [4](#0-3) 

Because the HMAC secret (`Context.api_secret_key`) is the app-level `client_secret`, shared across every shop that installs the app, any merchant who installs the app on their own store legitimately receives webhook deliveries with a valid `(body, hmac)` pair for that body. Since the `shop-domain` header is outside the signed content, that attacker can replay the exact same `raw_body` + `hmac-sha256` value to the app's public webhook endpoint while substituting a victim shop's domain in the `X-Shopify-Shop-Domain` header. `Registry.process` will accept it as authentic (the HMAC check still passes) and dispatch it to the handler labeled with the victim's shop, since nothing in this gem ties the `shop` header to the signed bytes.

### Impact Explanation
This breaks the tenant boundary: data an app treats as belonging to shop A can be injected and attributed to shop B purely by an unprivileged attacker who has legitimately installed the app once (which normal app installation flows freely permit). Depending on how the host app uses `data.shop` (e.g., to select a per-shop token/context, write to per-shop storage, or trigger per-shop side effects as shown in the docs' `perform_later(shop_domain: data.shop, ...)` example), this is a cross-tenant data-injection path reachable purely with a valid HMAC over attacker-controlled/replayed content.

### Likelihood Explanation
Requires no privileged credentials: the attacker only needs to be able to install the target app on a shop they control (the normal, unprivileged onboarding flow) to obtain one valid `(raw_body, hmac)` pair, then POST directly to the app's public webhook URL with a forged `shop-domain` header. No access to `api_secret_key`, tokens, or the target's credentials is needed.

### Recommendation
Include the `shop` (and ideally `topic`/`webhook_id`) header values in the HMAC-signable content, or otherwise cryptographically/contextually bind the `shop` identity to the verified payload before it is passed to the webhook handler, so the shop label cannot be swapped independently of the signed body.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and registers a webhook (e.g., `orders/create`).
2. Shopify delivers a webhook to the app with headers including `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, and some `raw_body`.
3. Attacker captures this exact `raw_body` and `X-Shopify-Hmac-Sha256` value.
4. Attacker sends a new HTTP POST directly to the app's public webhook endpoint with the same `raw_body` and `X-Shopify-Hmac-Sha256`, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
5. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `request.to_signable_string` (`@raw_body`) against the HMAC — this still succeeds.
6. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` and attacker-controlled body content, attributing forged/replayed data to the victim tenant. [3](#0-2) [1](#0-0)

If you want to register for an http webhook you need to implement a webhook handler which the `shopify_api` gem can use to determine how to process your webhook. You can make multiple implementations (one per topic) or you can make one implementation capable of handling all the topics you want to subscribe to. To do this simply make a module or class that includes or extends `ShopifyAPI::Webhooks::WebhookHandler` and implement the `handle` method which accepts the following named parameters: data: `WebhookMetadata`. An example implementation is shown below:

`data` will have the following keys
- `topic`, `String` - The topic of the webhook
- `shop`, `String` - The shop domain of the webhook
- `body`, `T::Hash[String, T.untyped]`- The body of the webhook
- `webhook_id`, `String` - The id of the webhook event to [avoid duplicates](https://shopify.dev/docs/apps/webhooks/best-practices#ignore-duplicates)
- `api_version`, `String` - The api version of the webhook

```ruby
module WebhookHandler
  extend ShopifyAPI::Webhooks::WebhookHandler

  class << self
    def handle(data:)
      puts "Received webhook! topic: #{data.topic} shop: #{data.shop} body: #{data.body} webhook_id: #{data.webhook_id} api_version: #{data.api_version}"
      perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)
    end
  end
end
