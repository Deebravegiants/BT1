## Title
Excess native `ETH` sent to `EvmHost.dispatch`/`fundRequest` is swallowed by the Host instead of being refunded to the caller - (File: `evm/src/core/EvmHost.sol`)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest()` all accept native token payment via `msg.value` and swap it for the fee token using Uniswap V2's `swapETHForExactTokens`. None of these functions validate that `msg.value` equals the amount actually required, nor do they forward any leftover ETH back to the original caller.

### Finding Description
In `EvmHost.dispatch(DispatchPost memory post)`: [1](#0-0) 

and identically in `dispatch(DispatchGet)`: [2](#0-1) 

and in `fundRequest`: [3](#0-2) 

Each of these forwards the entire `msg.value` to `IUniswapV2Router02.swapETHForExactTokens{value: msg.value}(exactOutAmount, path, address(this), block.timestamp)`. Uniswap V2's router implementation for `swapETHForExactTokens` only consumes the ETH needed to obtain the exact output token amount and refunds the unused ETH — but it refunds it to `msg.sender` **of the router call**, which in this case is `EvmHost` itself (since `EvmHost` is the direct caller of the router), not the original transaction sender (`_msgSender()`/`post.payer`). Any ETH sent beyond the exact quoted amount is therefore absorbed into the `EvmHost` contract's own balance rather than returned to the user who overpaid.

There is no explicit check anywhere in `dispatch`/`fundRequest` comparing `msg.value` against the quoted cost, and no logic to sweep the router's refund back to `_msgSender()` after the swap.

The only way to recover this stranded ETH is via `EvmHost.withdraw()`: [4](#0-3) 
which is restricted to `_hostParams.hostManager` — i.e., only reachable through cross-chain Hyperbridge governance (`HostManager.onAccept` `Withdraw` action), not by the user who overpaid: [5](#0-4) 

This means an unprivileged user calling `dispatch()` or `fundRequest()` with any native-token overpayment (e.g. from imprecise/off-chain fee estimation, since the docs explicitly warn `quote()` is unsafe to call on-chain due to sandwich-attack risk and must be estimated off-chain) permanently loses the excess ETH into protocol-controlled funds that get mixed with legitimate bridge revenue and require governance action to disburse — with no mechanism to attribute or return it to the specific overpaying account.

### Impact Explanation
This is a fund-loss issue reachable by any unprivileged caller of `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, or `fundRequest()` with native token payment. Excess `ETH` becomes indistinguishable from protocol fee revenue, is not recoverable by the affected user, and can only be extracted by governance via `withdraw()`, at which point it is disbursed to whatever beneficiary governance specifies — not the original overpaying user. Given that off-chain fee quoting (via `quote()`, explicitly documented as unsafe on-chain due to sandwich exposure) is the recommended flow, overpayment due to slippage/estimation drift between quoting and execution is a realistic and recurring occurrence, not a contrived edge case.

### Likelihood Explanation
High likelihood of occurrence in normal operation: any user/app who slightly overestimates the native fee (to guard against slippage in the Uniswap swap) when calling `dispatch()`/`fundRequest()` will lose the difference. No malicious actor coordination is required — it happens under normal usage patterns encouraged by the documentation itself.

### Recommendation
In `dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest()`, capture the ETH balance of the contract before and after the `swapETHForExactTokens` call (or read the return value `amounts[0]` from the swap), then refund `msg.value - amounts[0]` back to `_msgSender()` via a low-level call, mirroring the refund pattern already used elsewhere in the codebase (e.g. `ExtrinsicIntents._sendValue(msg.sender, msgValue)`): [6](#0-5) 

### Proof of Concept
1. A user wants to dispatch a POST request with `post.fee = 100e18` (fee token units) and calls `quote()` off-chain to estimate the required native amount, then adds a slippage buffer, e.g. sends `msg.value = 1.05 ETH` instead of the exact `1.0 ETH` needed.
2. User calls `EvmHost.dispatch{value: 1.05 ether}(post)`.
3. Inside `dispatch`, `IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: 1.05 ether}(100e18, path, address(this), block.timestamp)` executes, consumes only `1.0 ETH` for the exact `100e18` fee tokens, and refunds `0.05 ETH` to `msg.sender` of the router call — which is `EvmHost`, not the user.
4. `EvmHost`'s ETH balance is now `0.05 ETH` higher, with no record attributing it to the original user; the user's transaction returns successfully but they have lost `0.05 ETH` with no path to reclaim it except via Hyperbridge governance issuing a `withdraw()` to an arbitrary beneficiary of governance's choosing.

            // this is safe because re-entrancy is mitigated before dispatching requests
