### Title
Webhook `shop` field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating the HMAC over the raw request body, while the `shop` identity that is handed to the merchant's handler is read from an HTTP header that is never included in the signed content. Because the HMAC secret is a single app-wide `client_secret` shared by every shop that has installed the app, any merchant that has installed the app can capture one of their own legitimately-signed webhook deliveries and replay it to the app's webhook endpoint with the `shop-domain` header rewritten to point at a victim shop, causing the handler to process attacker-controlled data under the victim's tenant identity.

### Finding Description
The binding that should hold is:

`request.shop` used by the handler (`lib/shopify_api/webhooks/registry.rb:198`) `==` the shop cryptographically bound to the accepted HMAC.

`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw body: [1](#0-0) 

and `shop` is read straight from an unauthenticated header with no cryptographic tie to the body/HMAC: [2](#0-1) 

`Registry.process` verifies only `Utils::HmacValidator.validate(request)`, i.e. it checks `hmac(raw_body, Context.api_secret_key)`, then immediately trusts `request.shop` (and `request.topic`, `request.webhook_id`) to build the `WebhookMetadata` passed to the merchant's handler: [3](#0-2) 

`HmacValidator.validate` computes the signature purely from the `VerifiableQuery`'s `to_signable_string` and `Context.api_secret_key` (the single per-app secret, not a per-shop secret): [4](#0-3) 

Because `Context.api_secret_key` is one value for the whole app (shared by every installed shop), a valid `(raw_body, hmac)` pair obtained from a real webhook delivered to *any* shop that installed the app remains valid for *any* other `shop-domain` header value, since that header is outside the signed bytes. This is precisely the class of bug flagged in the report: a field that is acted upon (`shop`, used to route/attribute the webhook payload) is not covered by the integrity check (HMAC), so the "verified" identity and the "used" identity diverge.

### Impact Explanation
An attacker who is simply an ordinary, unprivileged merchant using the app (no access to `api_secret_key`, no access token, no TLS interception, no social engineering) can capture one authentic webhook (body + `X-Shopify-Hmac-Sha256`) delivered by Shopify for their own store, then send it to the app's public webhook endpoint again with the `X-Shopify-Shop-Domain` (or `Shopify-Shop-Domain`) header changed to a victim's `myshopify.com` domain and/or a different `Shopify-Topic`/`Shopify-Webhook-Id`. `HmacValidator.validate` still returns `true`, and the app's registered handler executes with `data.shop` set to the victim, `data.topic`/`data.body` fully attacker-controlled. Depending on how the host app trusts `WebhookMetadata#shop` (commonly used as the tenant key to look up/mutate merchant records, e.g. GDPR redact handlers, order/product sync handlers), this allows cross-tenant data injection or corruption attributed to a shop the attacker does not control — a cross-tenant access impact.

### Likelihood Explanation
Likelihood is meaningful but not trivial: it requires the attacker to (a) be able to install the target app on a shop they control to obtain at least one real signed webhook, and (b) know or discover the app's public webhook endpoint (typically fixed/known since it's part of the app's own registered callback URL). No secret material, elevated privileges, or network interception is required, only observation of one's own legitimately-received webhook and a replay with a modified header — well within reach of a normal merchant/unprivileged internet actor.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the value that is actually verified. For example, include `shop`, `topic`, and `webhook_id` in `to_signable_string` if Shopify's webhook HMAC scheme in use supports it, or — more robustly — have the host application independently verify that `request.shop` matches a shop that is known to have an active install/session before trusting `WebhookMetadata#shop`, and document that `Registry.process` callers must not rely on `shop`/`topic` headers as authenticated unless cross-checked against their own shop/session store.

### Proof of Concept
```ruby
# Attacker owns "attacker-shop.myshopify.com" and has installed the app,
# so Shopify legitimately delivers this webhook to the attacker's endpoint:
raw_body = '{"id":1,"note":"legit payload for attacker-shop"}'
valid_hmac_b64 = real_hmac_header_captured_from_shopify_delivery

# Attacker crafts a forged request to the SAME app endpoint, reusing the
# valid (body, hmac) pair but claiming to be the victim shop:
forged_headers = {
  "x-shopify-topic" => "customers/data_request",   # can also be swapped freely
  "x-shopify-hmac-sha256" => valid_hmac_b64,        # unchanged, still valid for raw_body
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # NOT covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
  "x-shopify-api-version" => "2024-01",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# Passes because HMAC only checks raw_body against Context.api_secret_key:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# Registry.process will now invoke the handler as if this legitimately came
# from "victim-shop.myshopify.com":
ShopifyAPI::Webhooks::Registry.process(request)
```
