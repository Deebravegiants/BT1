### Title
Unbounded `Vec<Message>` batch in `pallet_ismp::handle_unsigned` combined with a fixed, size-independent declared weight enables a free, network-wide DoS - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet-ismp`'s `handle_unsigned` extrinsic is permissionless, unsigned, and takes an unbounded `Vec<Message>` batch [1](#0-0) . Its declared weight is a constant, independent of the number or size of messages in the batch: `Weight::from_parts(300_000_000, 0)` [2](#0-1) . Because it is an unsigned transaction, `ValidateUnsigned::validate_unsigned` fully executes the entire batch (`Self::execute(messages.clone())`, which iterates and processes every message including MMR/state-proof verification) on every full node that receives the gossiped transaction, before any fee or meaningful weight has been charged [3](#0-2) . This mirrors the Spring Cloud Sleuth/Spring TX advisory pattern: a "specially crafted call" that is not properly bounded or instrumented, whose processing cost scales with attacker-controlled input while the framework meters it as fixed/cheap.

### Finding Description
`handle_unsigned` accepts `messages: Vec<Message>` with no bound on the number of messages or on nested collections within each message (e.g. `RequestMessage.requests: Vec<PostRequest>`, `GetRequest.keys: Vec<Vec<u8>>`) [1](#0-0) . There is no `MaxMessages`/`BoundedVec` constraint found anywhere in the pallet enforcing an upper limit on batch size before execution.

The pallet declares this call's weight via a hard-coded function that ignores the batch entirely:
```
fn weight() -> Weight {
    Weight::from_parts(300_000_000, 0)
}
``` [2](#0-1) 

Because `handle_unsigned` is dispatched with `ensure_none(origin)`, it must be validated through `ValidateUnsigned::validate_unsigned`, and that validation path unconditionally runs the full batch through `Self::execute`, the same function that performs consensus/state-proof verification, dedup checks, and dispatch for every message:
```
fn validate_unsigned(_source: TransactionSource, call: &Self::Call) -> TransactionValidity {
    ...
    let events = Self::execute(messages.clone()).map_err(|_| InvalidTransaction::BadProof)?;
    ...
}
``` [3](#0-2) 

`Self::execute` iterates `messages.iter().map(|msg| handle_incoming_message(&host, msg.clone()))`, doing full per-message work (state-machine validation, MMR/non-membership proof verification, hashing, router dispatch) for the entire batch [4](#0-3) . This full execution happens in `validate_unsigned`, which every node in the network runs when it receives the gossiped unsigned transaction (standard Substrate mempool validation semantics), and it happens again at block-execution time if included.

Since the call is unsigned there is no ordinary transaction fee paid up front, and the block-inclusion weight metering treats the call as costing only 300,000,000 (a small, fixed amount) no matter how many messages, requests, or nested proof elements are packed in. An attacker can therefore:
1. Construct a single `handle_unsigned` transaction whose `Vec<Message>` contains a very large number of `RequestMessage`/`TimeoutMessage`/`GetResponse` entries, each carrying maximal nested vectors (e.g., many `GetRequest.keys`), sized just under the extrinsic/byte length limit.
2. Craft the messages so they pass cheap early checks but fail late in verification (e.g., invalid but well-formed MMR/state proofs), maximizing wasted CPU per node before the transaction is ultimately rejected.
3. Broadcast the transaction (or re-broadcast slight variants, since the `provides` tag is content-based, allowing many distinct expensive batches to coexist in the pool) so every full node on the network repeatedly pays the real (unbounded) CPU cost of `Self::execute` in `validate_unsigned`, for free, with no economic cost to the attacker.

This is analogous to the CVE-2026-41708 bug class: an externally reachable, "free"/uninstrumented processing path whose cost is not bounded relative to attacker-supplied input, enabling denial of service.

### Impact Explanation
This directly threatens chain liveness (CWE-400, Availability: High in the referenced CVSS vector). Because validation of unsigned transactions happens on every full node in the network prior to any economic cost being imposed, an attacker can force sustained excess CPU consumption network-wide using a single crafted, unsigned, fee-free transaction repeated or varied cheaply. In the worst case this degrades block production and transaction propagation for the whole parachain, i.e., "a route unable to deliver messages" — one of the explicitly accepted impact categories.

### Likelihood Explanation
`handle_unsigned` is explicitly permissionless by design (documented as "This allows users execute ISMP datagrams for free. Use with caution.") [5](#0-4) , and any unprivileged actor able to submit a transaction to the network can reach it directly with a crafted `Vec<Message>`. No governance, admin, or relayer privilege is required — only the ability to author and gossip a transaction, which is the baseline threat model for this endpoint.

### Recommendation
- Bound the number of messages (and nested collections such as `keys`/`requests`) accepted by `handle_unsigned`, enforced before any expensive processing in `validate_unsigned`.
- Make the declared `Weight` for `handle_unsigned` scale with the actual size/content of the batch (e.g., proportional to `messages.len()` and to nested elements), so block-weight accounting reflects real cost and large batches cannot be included cheaply.
- Consider performing cheap, size/structure-based rejection (max messages, max nested lengths) in `validate_unsigned` prior to invoking `Self::execute`, to reduce the CPU cost imposed on every node validating a malicious transaction before it is rejected.

### Proof of Concept
1. Construct `messages: Vec<Message>` containing, e.g., thousands of `Message::Request(RequestMessage { requests: vec![... many PostRequest with large `body`/`to`/`from` fields ...], proof: <well-formed but invalid non-membership/state proof>, .. })`, sized to approach the runtime's max extrinsic length.
2. Submit as `Ismp::handle_unsigned(RuntimeOrigin::none(), messages)` via `create_unsigned` (as exercised in the existing test harness) [6](#0-5) .
3. Observe that every peer that receives the gossiped transaction executes the full `Self::execute` batch (proof verification for every request) inside `validate_unsigned` before the transaction is rejected for an invalid proof, at a declared cost of only `Weight::from_parts(300_000_000, 0)` regardless of the batch's real size [2](#0-1) .
4. Repeat/vary the batch content cheaply (changing content changes the `provides` tag, so the pool does not dedupe) to sustain elevated CPU load across the network at negligible cost to the attacker.
