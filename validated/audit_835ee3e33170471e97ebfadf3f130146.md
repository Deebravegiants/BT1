### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing tenant-identity spoofing in `ShopifyAPI::Webhooks::Registry.process` - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` (tenant identifier) that is later handed to the app's webhook handler is read from the unauthenticated `shopify-shop-domain` HTTP header. The HMAC verification therefore authenticates the *body* but not the *shop* binding, breaking the identity equality that the handler implicitly relies on: `hmac_verified(body) == shop_attributed_to(body)`.

### Finding Description
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely via `Utils::HmacValidator.validate(request)`, which in turn calls `request.to_signable_string` to compute the expected signature: [1](#0-0) [2](#0-1) 

`Webhooks::Request#to_signable_string` is defined to be just the raw HTTP body: [3](#0-2) 

However, `Request#shop` is pulled straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header, which is not part of the signed material at all: [4](#0-3) 

This `shop` value is then passed, unverified, directly into `WebhookMetadata` and delivered to the app's registered handler as the trusted tenant identifier: [1](#0-0) 

This mirrors the reported bug class: a field that is *acted upon* (here, `shop`, used by the handler to select/scope the tenant) is not *covered* by the integrity check (the HMAC covers only `@raw_body`). Contrast this with `Auth::Oauth::AuthQuery#to_signable_string`, which correctly includes `shop` in the signed parameters for the OAuth callback path: [5](#0-4) 

The webhook path has no equivalent binding of `shop` to the signature.

### Impact Explanation
Any client that possesses one valid `(raw_body, hmac)` pair for a given topic (e.g. any Shopify webhook payload it can legitimately observe, such as one delivered to its own installed shop, or any payload/HMAC pair that becomes available to it) can replay that exact body/HMAC combination while substituting an arbitrary `shopify-shop-domain` header. Because `HmacValidator.validate` only checks `raw_body` against `hmac`, the forged request passes validation unchanged, and the handler receives `WebhookMetadata#shop` set to the attacker-chosen value. If the host application uses `data.shop` to look up sessions, scope database records, or otherwise route/attribute the webhook payload to a tenant (as illustrated in the gem's own documentation, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`), this allows cross-tenant data injection/misattribution — an attacker can cause a payload to be processed under a victim shop's identity, or vice versa. This satisfies the "cross-tenant access" criterion for Critical impact, since the shop attribution — the tenant boundary — is not authenticated even though the mechanism (HMAC) exists specifically to authenticate the whole webhook request.

### Likelihood Explanation
Exploitability requires the attacker to obtain at least one valid `(body, hmac)` pair, which is realistic in several documented scenarios (e.g. an attacker's own shop installs the app and receives legitimately-signed webhooks with attacker-controlled body content and a valid HMAC for that body; the attacker then replays that exact body+hmac with a different `shop-domain` header at the same public webhook endpoint). No access token, `client_secret`, or `api_secret_key` is required — only network access to the app's public webhook callback URL and a single legitimately obtained signed payload.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the signed material verified against the HMAC, or otherwise cryptographically bind the `shopify-shop-domain` header to the signature before trusting it in `WebhookMetadata`. At minimum, `Webhooks::Request#to_signable_string` should incorporate the shop domain the same way `Auth::Oauth::AuthQuery#to_signable_string` incorporates `shop`, so that `HmacValidator.validate` fails if the shop header is altered independently of the raw body.

### Proof of Concept
1. App is registered for topic `orders/create` with a handler that forwards `data.shop` to internal processing (as documented):
```ruby
handler.handle(data:) # WebhookMetadata#shop == request.shop
```
2. Attacker (owning `attacker-shop.myshopify.com`, an installed instance of the app) receives a legitimate webhook:
   - `raw_body = '{"id":1,...}'`
   - `x-shopify-hmac-sha256 = <valid HMAC of raw_body>`
   - `x-shopify-shop-domain = attacker-shop.myshopify.com`
3. Attacker resends the identical `raw_body` and `x-shopify-hmac-sha256` to the app's public webhook endpoint but with:
   - `x-shopify-shop-domain = victim-shop.myshopify.com`
4. `Utils::HmacValidator.validate` recomputes the HMAC over `raw_body` only [3](#0-2)  — it matches, since the shop header was never part of the signed content.
5. `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` [6](#0-5) , causing the attacker-controlled payload to be processed/attributed under the victim tenant.

          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
