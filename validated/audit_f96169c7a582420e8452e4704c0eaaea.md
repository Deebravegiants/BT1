This confirms it — the docs explicitly say `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" and passes `data.shop` (the shop-domain header) to the handler as the trusted tenant identifier, and the reference implementation in the docs directly uses `data.shop` for tenant-scoped work (`perform_later(topic: data.topic, shop_domain: data.shop, ...)`). ### Title
Webhook shop/topic identity spoofing via unsigned headers — HMAC only covers raw body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` proves nothing about the `shop-domain`, `topic`, `webhook-id`, or `api-version` headers. `Registry.process` accepts any request whose body+HMAC pair is valid and then dispatches the handler using `request.shop` and `request.topic`, which are taken verbatim from unauthenticated headers.

### Finding Description
The identity binding that should hold is: `bytes verified by HMAC == fields the handler acts on`. Instead:
- HMAC-verified bytes: `@raw_body` only [1](#0-0) 
- Fields used to route/attribute the webhook to a tenant: `shop` and `topic`, read straight from HTTP headers with no cryptographic binding to the body [2](#0-1) 

`Registry.process` only checks `Utils::HmacValidator.validate(request)` (which validates `raw_body` against `hmac`) before dispatching the handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)`: [3](#0-2) 

Because the `X-Shopify-Shop-Domain`/`X-Shopify-Topic` headers are excluded from the signed content, any `(raw_body, hmac)` pair that is valid for one legitimate webhook delivery remains valid when replayed with a different `shop-domain` or `topic` header — the signature check still passes since it only re-hashes `raw_body`.

### Impact Explanation
An unprivileged internet user who can install the app on their own store (a normal, permission-less action for any public Shopify app) will receive at least one genuine webhook delivery to the app's public callback endpoint, i.e. one authentic `(raw_body, hmac)` pair signed with the app's `api_secret_key`. They can replay that exact body+HMAC to the same endpoint while substituting the `shop-domain` header with an arbitrary shop domain (any other merchant using the app) and/or a different `topic` header. `Registry.process` validates the HMAC successfully and invokes the handler with `data.shop` set to the attacker-chosen value, exactly as documented usage instructs host apps to trust it for per-tenant work (queuing jobs, updating records, etc., keyed by `shop_domain`). This lets an attacker inject webhook data that the host app attributes to a tenant it does not belong to — a cross-tenant data-confusion/injection primitive rooted entirely in this gem's `Request`/`Registry` code, matching the required "cross-tenant access" impact category.

### Likelihood Explanation
Requires only: (1) ability to install the target public app on an attacker-controlled store to harvest one valid HMAC'd body, and (2) sending a normal HTTP POST to the app's public webhook endpoint with modified headers — no secrets, TLS interception, or privileged access needed. This is a realistic, unprivileged-internet-user path.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` in the signable content used for HMAC validation (or otherwise cryptographically bind them to the verified body), so that spoofing/replaying with altered headers is detected. At minimum, document prominently that `request.shop`/`request.topic` are NOT covered by the HMAC and must not be trusted for tenant attribution without additional verification (e.g., cross-checking against the shop stored for the session/webhook subscription).

#    X-Shopify-Hmac-Sha256 header value from that delivery (their own traffic,

# 2. Attacker resends the identical body+hmac to the app's public webhook
#    endpoint, but swaps the shop-domain header to a victim shop.

  "x-shopify-hmac-sha256" => hmac_b64,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # not part of the signed content

# 3. HMAC validation passes because it only re-hashes raw_body:
ShopifyAPI::Utils::HmacValidator.validate(request) # => true

# 4. Registry.process dispatches the handler with data.shop == "victim-shop.myshopify.com",
#    even though this body never originated from Shopify for that shop.
ShopifyAPI::Webhooks::Registry.process(request)
