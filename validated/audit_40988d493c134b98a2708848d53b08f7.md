### Title
Emporium external action mints duplicate shielded UTXOs for double-entry-point tokens - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol`)

### Summary
`EmporiumUpgradeable.runAction()` credits the caller with new shielded UTXOs by taking a raw balance-diff (`balancesAfter[i] - balancesBefore[i]`) independently for every entry in `circomData.erc20TokenAddresses`, with no check that two different addresses in that array might read the very same underlying token balance (the "double entry point" pattern, e.g. legacy TrueUSD). Since the on-chain minting of the resulting UTXO is driven purely by this balance snapshot and not by the ZK proof, an attacker can list both entry-point addresses of such a token and receive two full-value shielded UTXOs for a single real balance increase.

### Finding Description
`runAction` snapshots balances once before executing the arbitrary op-stack and once after: [1](#0-0) [2](#0-1) 

It then loops per index `i` over `circomData.erc20TokenAddresses`, computes `balanceChange = balancesAfter[i] - balancesBefore[i]`, and for any positive change mints a brand-new UTXO with `amount = balanceChange` for `erc20TokenAddresses[i]`, which is later inserted into the Merkle tree as an on-chain commitment: [3](#0-2) [4](#0-3) 

The only defense against duplicate token slots is the circuit's pairwise-inequality check, which only compares the raw addresses for exact equality, not whether two distinct addresses alias the same underlying token storage: [5](#0-4) 

For a token slot with zero input UTXOs and zero `amountChanges`, the circuit only requires `inTotal + amountChanges[i] === outTotal`, which is trivially satisfied with `inTotal = amountChanges = outTotal = 0` — i.e. the user does not need to own or spend any real UTXO of that token to include it as a fresh slot: [6](#0-5) 

Because the emitted UTXO amount for these slots is derived solely from the on-chain balance diff (not from `outCommitments` verified by the proof), listing both address `A` and address `B` of a double-entry-point token in `erc20TokenAddresses` causes the single real balance increase `X` (from a swap performed inside the op-stack) to be read twice — once via `A`, once via `B` — producing two independent UTXOs of amount `X` each, i.e. `2X` of spendable shielded value backed by only `X` real tokens.

### Impact Explanation
This breaks the fundamental value-conservation invariant of the protocol: shielded value created in the tree must be backed 1:1 by tokens actually held by the contract. Here an attacker can mint `2X` (or more, with more aliasing addresses) of spendable shielded balance from a single `X`-token deposit/swap, i.e. unbacked minting of shielded value, which is explicitly listed as Critical impact.

### Likelihood Explanation
The attack requires a real-world ERC20 with multiple valid entry-point addresses to the same balance (rare, but such tokens have existed, e.g. legacy TrueUSD before the secondary entry was disabled) and requires that token/pair to be used inside an Emporium `runAction` op-stack, which any unprivileged EOA can construct (only `onlyAllowedRecipient` gates the external-action id, not the caller). No admin/relay privileges are needed; the attacker fully controls `circomData.erc20TokenAddresses`, `amountChanges`, and the op-stack calldata routed to Emporium.

### Recommendation
Deduplicate `erc20TokenAddresses` against real token identity rather than raw address equality where feasible (e.g. via a maintained allow-list of canonical token addresses, rejecting known dual-entry tokens), or restructure `runAction`'s balance accounting to snapshot/diff only unique underlying balances rather than per-slot-address diffs, matching the auditor's suggested "snapshot vs. balance" cross-check but applied per unique token rather than per listed address.

### Proof of Concept
1. Assume token `T` exposes two valid ERC20 entry points, addresses `A` and `B`, both reading/writing the same underlying balance mapping.
2. Attacker builds `circomData` for an Emporium `_externalTransact` call with `erc20TokenAddresses = [USDC, A, B]`.
   - USDC slot: valid proof spending `X` USDC of the attacker's own shielded balance (negative `amountChanges`), moved into Emporium for the swap.
   - `A` and `B` slots: zero input UTXOs, `amountChanges = 0`, satisfying `inTotal + amountChanges === outTotal` trivially with `outTotal = 0`.
3. The op-stack executes a swap that converts `X` USDC into `X` units of token `T` (received by the Emporium contract).
4. In `runAction`, `balancesBefore`/`balancesAfter` are queried via both `A.balanceOf` and `B.balanceOf`, both returning identical numbers since they share underlying storage: `balanceChange[A] = X`, `balanceChange[B] = X`.
5. `handleOut` is invoked for both indices, transferring `X` tokens to `msg.sender` via `A` and (redundantly, no-op transfer since same storage) via `B`, and creates two on-chain UTXOs of amount `X` each for `A` and `B`.
6. The attacker now holds two shielded UTXOs worth `X` each (`2X` total) backed by only `X` real tokens deposited/swapped once.
