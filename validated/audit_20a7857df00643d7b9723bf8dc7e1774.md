### Title
Webhook shop attribution is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable payload from the raw body only, while the `shop` (and `topic`/`webhook_id`) values that `ShopifyAPI::Webhooks::Registry.process` hands to the app's handler are read straight from unauthenticated HTTP headers. The binding "HMAC-verified bytes == shop the data is attributed to" does not hold, so an attacker who controls the delivery of a webhook request (e.g. a malicious merchant replaying their own legitimately-signed webhook body) can rewrite the `shop-domain` header to claim the payload belongs to a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

but `shop`, `topic`, and `webhook_id` are all parsed from headers that are never included in that signable string: [2](#0-1) 

`Registry.process` validates the HMAC and, if it matches, immediately trusts `request.shop` as the tenant identity for the event: [3](#0-2) 

`Utils::HmacValidator.validate` only recomputes the HMAC over `to_signable_string` (the body) and compares it to the `hmac` header — it never binds `shop` into the signature: [4](#0-3) 

The gem's own documentation asserts that `Registry.process` "will verify the request did indeed come from Shopify" and that the resulting `data.shop` is "The shop domain of the webhook" — implying full authenticity of the shop attribution, which is not actually the case: [5](#0-4) [6](#0-5) 

Because the app's HTTP framework passes `request.headers.to_h` (attacker-influenced when the transport does not itself pin the source, e.g. any proxy/relay in front of the webhook endpoint, or any actor able to submit an HTTP request carrying a previously-observed valid `(body, hmac)` pair) directly into `Webhooks::Request.new`, the equality that must hold — `hmac_verified_bytes == identity_used_for_dispatch` — is broken: the HMAC verifies the body, but the identity (`shop`) used to route/store/act on that body is taken from a completely unauthenticated header.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: data whose integrity is anchored to shop A's secret-signed body can be attributed to shop B simply by altering the `shopify-shop-domain` (or `x-shopify-shop-domain`) header, since that header is not part of the HMAC-covered bytes. A host application that uses `data.shop` from `WebhookMetadata` to scope database writes, cache keys, or job queues (as literally shown in the gem's own example handler, `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process/store attacker-supplied body content under an arbitrary victim shop identity — a cross-tenant data-integrity break reachable by any party capable of delivering a request with a previously valid `(body, hmac)` pair to the webhook endpoint.

### Likelihood Explanation
Any working webhook subscriber already possesses valid `(body, hmac)` pairs for their own shop's webhook deliveries (they receive them legitimately). Replaying that same body with a modified `shop-domain` header is a header-only manipulation and requires no access to the `client_secret` or any merchant credential — it only requires the ability to make an HTTP request to the app's public webhook callback route, which by design is unauthenticated aside from the HMAC check that this bug defeats.

### Recommendation
Bind the shop identity to the HMAC-verified material, e.g., include `shop-domain` (and `topic`/`webhook-id` as appropriate) in `to_signable_string`'s covered material, or independently confirm the header-derived `shop` matches an expected/registered shop before dispatching to the handler. At minimum, document that `data.shop` in `WebhookMetadata` is not authenticated by the HMAC and must be independently validated (e.g., against a known list of shops with active app installs) before being used for any tenant-scoping decision.

### Proof of Concept
1. A merchant "attacker.myshopify.com" receives a legitimate webhook delivery for their own shop: body `B`, `x-shopify-hmac-sha256: H = HMAC(client_secret, B)`, `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this request (e.g., from their own server logs, a proxy they control, or a request they self-issue by triggering an event in their own store) and resends it to the same webhook endpoint, unchanged except the header `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request#hmac` still decodes to `H`; `HmacValidator.validate` recomputes HMAC over `@raw_body` (`B`), which is unchanged, so the signature check passes: [7](#0-6) 
4. `Registry.process` calls the handler with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: parsed(B), ...)` — the attacker's own body content is now attributed to the victim shop in the host application.

          received_signature = verifiable_query.hmac
