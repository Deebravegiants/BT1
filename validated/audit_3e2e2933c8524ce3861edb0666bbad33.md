### Title
Webhook shop-domain header is not covered by the HMAC signature, allowing cross-tenant webhook forgery - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` computes the HMAC signature over the raw request body only, but the `shop` (tenant) identifier consumed by `ShopifyAPI::Webhooks::Registry.process` comes from an unsigned HTTP header. Because the app's webhook HMAC secret (`Context.api_secret_key`/`Context.old_api_secret_key`) is shared across every shop that installs the app, any shop that has installed the app can capture a genuine, validly-signed webhook body and hmac, then resubmit it to the app's webhook endpoint with the `shopify-shop-domain`/`x-shopify-shop-domain` header changed to a victim shop. The signature still validates because the header is never part of the signed content, so the request is processed and dispatched to the app's handler as if it came from the victim shop.

### Finding Description
`Utils::HmacValidator.validate` verifies `verifiable_query.to_signable_string` against the request's `hmac`: [1](#0-0) 

For webhooks, `Request#to_signable_string` returns only the raw request body: [2](#0-1) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all pulled straight from HTTP headers that are never included in the signed content: [3](#0-2) 

`Registry.process` validates only the HMAC of the request (i.e., of the body) and then trusts `request.shop`/`request.topic` to route and construct `WebhookMetadata` passed to the app's handler: [4](#0-3) 

The identity binding that should hold is:
`shop authenticated by HMAC` == `shop delivered to the handler as tenant identity (request.shop)`

Because the HMAC only binds the *body bytes*, not the `shopify-shop-domain` header, this equality does not actually hold — the header can be swapped without invalidating the signature. Since `Context.api_secret_key` is the single app-level secret shared by all shops that install the app (it is not a per-shop secret), any shop that has installed the app can generate a body+HMAC pair that is valid for the app, then relabel the `shop-domain` header to any other shop domain (including a victim shop that also installed the app) before delivering it to the app's public webhook endpoint. `Registry.process` will accept it and hand `WebhookMetadata.new(topic:, shop: request.shop, body:, ...)` to the handler as if it genuinely originated from the victim shop.

### Impact Explanation
This breaks the tenant boundary the webhook mechanism is supposed to guarantee: the library asserts to consuming apps that "if HMAC validates, this event genuinely came from `request.shop`." That assertion is false. An attacker who has legitimately installed the app on their own store can forge webhook payloads (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`) that the host application will process believing they originated from a different, victim shop. Depending on what the host app does with webhook data (writing records keyed by shop, triggering GDPR data actions, revoking access, updating billing state, etc.), this enables cross-tenant data corruption/injection — one of the explicitly in-scope Critical impacts (cross-tenant access).

### Likelihood Explanation
Exploitation requires only that the attacker control one shop with the app installed (a normal, unprivileged position for any developer/merchant that can install the app) and be able to receive/replay HTTP requests to the app's public webhook endpoint — no leaked secrets, no privileged account, and no interaction with the victim shop is required. The `api_secret_key` is shared per-app, not per-shop, so this is fully reachable by any unprivileged installer of the app.

### Recommendation
Bind the `shop` (and ideally `topic`/`api_version`) claims into the signed material, or otherwise cryptographically tie the header values to the signature, e.g.:
- Include the `shopify-shop-domain` header (and topic) in the signable string used by `HmacValidator`, so tampering with the header invalidates the HMAC, or
- Have `Registry.process`/`WebhookMetadata` cross-check `request.shop` against a shop the caller expects/owns (e.g. require the calling app to pass an expected shop and compare it), rather than trusting the header outright.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`; the app registers a webhook (e.g. `orders/create`).
2. Shopify delivers a webhook to the app with headers:
   `shopify-shop-domain: attacker-shop.myshopify.com`, `shopify-hmac-sha256: <valid-hmac-of-body>`, body `B`.
3. Attacker captures body `B` and its valid `shopify-hmac-sha256`, then re-sends the same body and HMAC to the app's webhook endpoint but sets `shopify-shop-domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` succeeds because it only checks `OpenSSL.secure_compare(computed_signature, hmac)` over `@raw_body`, which is unchanged: [5](#0-4) 
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)`, where `request.shop` is now `victim-shop.myshopify.com`: [4](#0-3) 
6. The host application processes attacker-controlled data as if it were an authentic event from the victim shop.

Note: this analysis is limited to the library's `lib/shopify_api/webhooks/**` and `lib/shopify_api/utils/**` code as retrieved; I could not inspect every possible host-app usage pattern of `WebhookMetadata#shop`, but the root cause (header not covered by the HMAC) is confirmed directly in `Request#to_signable_string` and `HmacValidator#validate_signature`.

          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
