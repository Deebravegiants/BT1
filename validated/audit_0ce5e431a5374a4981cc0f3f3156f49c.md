### Title
Webhook `shop-domain` Header Is Not Covered By HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (`lib/shopify_api/webhooks/request.rb`)

### Summary
The `Webhooks::Request` class computes its HMAC-signable string from the raw body only, while the `shop` (tenant identity), `topic`, and `webhook_id` fields are read straight from unauthenticated HTTP headers. `Registry.process` trusts `request.shop` as the tenant identity for dispatching webhook data to the host application's handler without that value ever being covered by the signature check.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are pulled directly from the `shopify-*`/`x-shopify-*` headers, which are not part of the signed payload: [2](#0-1) 

`Registry.process` validates only the HMAC over the body via `Utils::HmacValidator.validate(request)`, and then unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the app's registered handler: [3](#0-2) 

`HmacValidator.validate_signature` computes the HMAC purely over `verifiable_query.to_signable_string` (i.e., the raw body) and compares it to the `hmac` header value: [4](#0-3) 

This breaks the identity binding: `shop == request.shop` is treated as verified (bound to the HMAC-authenticated payload) when in fact `shop` is an independent, unauthenticated header that an attacker fully controls. Any body+HMAC pair that is valid for the app's secret (e.g., a genuine webhook delivered for the attacker's own shop after installing the app) remains valid when replayed with an arbitrary `shopify-shop-domain` header value, because the signature never covered that header.

### Impact Explanation
An attacker who can install the app on their own store (a normal, unprivileged action) receives genuine, correctly-HMAC-signed webhook deliveries from Shopify for their own body content. By replaying that exact body and HMAC to the host application's webhook endpoint while substituting the `shopify-shop-domain` header with a victim merchant's domain, the attacker causes `Registry.process` to pass `shop: <victim-domain>` to the host app's webhook handler as if the data legitimately originated from the victim shop. Depending on how the host application uses `WebhookMetadata#shop` (e.g., to look up/update the merchant's session, application state, or trigger shop-scoped side effects such as `shop/redact`, `customers/redact`, or order-processing logic), this enables cross-tenant data confusion/corruption attributable to the wrong merchant — a cross-tenant boundary violation stemming entirely from an identity field excluded from the HMAC.

### Likelihood Explanation
Reaching this requires only: (1) installing the app on an attacker-controlled shop to obtain a validly signed webhook body/HMAC pair, and (2) sending an HTTP POST to the app's public webhook endpoint with a forged `shopify-shop-domain` header. No access token, `api_secret_key`, or privileged account is required — both steps are available to any unprivileged internet user who can install the target app.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) header values into the signed material verified by `HmacValidator`, or otherwise independently authenticate the `shop-domain` header against the HMAC-signed body before using it as a tenant identifier in `WebhookMetadata`. At minimum, document and enforce that host applications must not derive tenant identity from `Webhooks::Request#shop` without additional verification.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a real webhook POST with body `B` and header `shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`.
2. Attacker replays the request to the app's webhook endpoint, keeping body `B` and header `shopify-hmac-sha256: H`, but sets `shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `HMAC(secret, B) == H`, per [4](#0-3) .
4. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: request.topic, shop: "victim-shop.myshopify.com", body: ..., ...)`, per [5](#0-4) , causing the host app to process attacker-controlled data under the victim shop's identity.
