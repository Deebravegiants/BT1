This confirms the finding: the documented contract explicitly tells app developers that `data.shop` is "The shop domain of the webhook" [1](#0-0)  — a trusted per-tenant identity field — while `Registry.process` only validates `Utils::HmacValidator.validate(request)` before handing `request.shop` straight to the handler, with no binding between the HMAC and the shop value [2](#0-1) .

### Title
Webhook `shop` identity field is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives the HMAC-verified signable content solely from the raw request body, while the `shop` (tenant) identity is read from an HTTP header that is never included in that signed content. This breaks the equality that should hold between "the shop the HMAC attests to" and "the shop the application trusts as the event's tenant."

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: `to_signable_string` → `@raw_body` [3](#0-2) . The `shop` accessor, by contrast, is read directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header without any cryptographic binding: `shop` → `shopify_header("shop-domain")` [4](#0-3) .

`HmacValidator.validate` computes the HMAC purely over `verifiable_query.to_signable_string` (the body) and compares it to the `hmac` header value: [5](#0-4) . It never touches `shop`.

`Registry.process` treats a passing HMAC check as proof of authenticity for the whole request, then forwards the unauthenticated `request.shop` value straight into `WebhookMetadata` handed to the app's handler: [2](#0-1) .

Because Shopify signs webhook bodies with the single app-wide `api_secret_key` (the same secret is used for every shop that installed the app), an attacker who legitimately installs/operates their own shop on the app receives real, validly-signed webhooks for their own shop. That attacker can capture one `(raw_body, hmac-sha256 header)` pair and replay it to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it only checks body bytes against the shared secret), so `Registry.process` calls the handler with `shop: <victim's domain>` and the attacker-controlled `body`.

The gem's own documentation instructs integrators to treat `data.shop` as an authenticated per-tenant identity key equivalent to what's used for session/data lookups: [6](#0-5) . Applications following this documented contract (e.g. `perform_later(topic: data.topic, shop_domain: data.shop, webhook: data.body)`) will process forged data as if it originated from the victim tenant.

### Impact Explanation
This breaks the equality `shop authenticated by HMAC == shop used as tenant key`, allowing an attacker holding a valid webhook signature for their own shop to forge webhook events attributed to any other shop known to the app (cross-tenant data injection). Depending on the handler logic (order creation, GDPR/customer data webhooks, app-uninstalled, etc.), this can lead to cross-tenant data corruption or processing of attacker-controlled payloads under a victim shop's identity — matching the "cross-tenant access" High-impact category.

### Likelihood Explanation
Requires only that the attacker control one shop that has installed the app (a normal, unprivileged capability for any Shopify merchant/developer), and the ability to send arbitrary HTTP requests to the app's public webhook endpoint with custom headers — both trivially available to an "unprivileged internet user" as defined in scope. No access token, `api_secret_key`, or privileged credentials are needed.

### Recommendation
Include the `shop-domain` header (and ideally `topic`, `api-version`, `webhook-id`) in the value that is HMAC-verified, or otherwise cryptographically bind the shop identity to the signed payload, e.g. by validating the HMAC over `"#{shop}\n#{topic}\n#{raw_body}"`-style canonical string instead of the raw body alone. Alternatively/additionally, document and enforce that the `shop` header value must be cross-checked by the caller against a shop registered/known to the app before being trusted as a tenant key, and consider computing/storing a per-shop-scoped HMAC context where feasible.

### Proof of Concept
1. Attacker installs the app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H` (valid for `HMAC-SHA256(api_secret_key, B) == H`).
2. Attacker replays the exact same request to the app's public webhook endpoint but changes only the `x-shopify-shop-domain` header to `victim-shop.myshopify.com`, keeping body `B` and signature `H` unchanged.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com", hmac-sha256: H})` is constructed; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes `HMAC-SHA256(api_secret_key, B)` and finds it equals `H` — validation passes, since `shop` is never part of the signed string (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The app's registered handler is invoked with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, exactly as if Shopify had sent this event for the victim shop, even though it originated from the attacker's own installation.
