### Title
Incorrect decimal scaling in `convert_to_erc20`/`convert_to_balance` can mint/credit wildly wrong cross-chain token amounts - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
`pallet-hyper-fungible-token` scales amounts between a local asset's decimals and the destination EVM contract's declared decimals using `saturating_sub`, which silently degrades to "no scaling" whenever the local decimals exceed the remote/erc decimals, instead of correctly scaling down. This is the same class of bug as the reported JOJO `DecimalMath` issue: an implicit, one-directional decimal assumption that produces wrong amounts whenever tokens do not share exactly the same, larger-than-or-equal-decimals relationship.

### Finding Description
The scaling helpers are: [1](#0-0) 

`convert_to_erc20(value, erc_decimals, local_decimals)` multiplies by `10^(erc_decimals.saturating_sub(local_decimals))`, and `convert_to_balance(value, erc_decimals, local_decimals)` divides by the same saturating-subtracted exponent. Both only work correctly when `erc_decimals >= local_decimals`. When `local_decimals > erc_decimals` (i.e., the local asset uses *more* decimal precision than the registered remote/ERC20 contract), `saturating_sub` returns `0`, so the exponent becomes `10^0 = 1` — meaning **no scaling is applied at all**, even though scaling in the opposite direction is required.

This is used on the outbound `send` path: [2](#0-1) 

and inbound `on_accept`/`on_timeout` paths: [3](#0-2) [4](#0-3) 

The pallet's own documentation confirms decimals can differ per (asset, chain) pair and are configured via `Precisions`/`register_token`, so this is not a theoretical edge case: [5](#0-4) 

The only in-repo example (`BridgeToken`) happens to configure `erc_decimals (18) > local_decimals (12)`, which is the direction that works correctly: [6](#0-5) 

But nothing in `register_token`/`update_token`/`update_asset_precision` enforces `erc_decimals >= local_decimals` for every configured chain; an asset can legitimately be registered with a local asset that has more decimals than the remote contract (e.g., a locally-issued 18-decimal asset bridged to a 6-decimal ERC20 representation).

### Impact Explanation
When `local_decimals > erc_decimals` for a configured chain:
- On `send`, the pallet escrows/burns the correct (small, properly-scaled) local amount, but computes an `erc20_amount` that is `10^(local_decimals - erc_decimals)` times *larger* than intended (no down-scaling applied) and dispatches this inflated amount to the destination EVM `HyperFungibleToken`/`BridgeToken` contract, which mints it as-is. This is an unbacked mint: the destination chain receives a token balance far exceeding what was locked/burned on the source chain, directly enabling value extraction/theft.
- On `on_accept`/`on_timeout` (inbound), the same missing division causes credited/refunded local amounts to be under-scaled by the same factor, causing permanent loss of value/funds mismatch for users receiving inbound transfers or refunds.

This qualifies as both an unbacked mint and a fund-loss issue depending on transfer direction, satisfying the "concrete theft or permanent freezing of funds, unbacked mint" bar.

### Likelihood Explanation
Likelihood depends on governance registering a token pair where the local asset has strictly more decimals than the destination chain's registered precision — a configuration explicitly supported by the pallet's design (`Precisions` is keyed per `(AssetId, StateMachine)` and can be any `u8` independently of local decimals) and not guarded against at registration time. Any operator who wires up an asset this way (e.g., a locally 18-decimal asset paired with a 6-decimals ERC20, mirroring common real-world token decimal mismatches like USDC) triggers the bug on every transfer in that direction, making it Medium-High likelihood in realistic deployments even though it requires a specific (but plausible and unguarded) decimals configuration.

### Recommendation
Fix both helpers to scale bidirectionally instead of relying on `saturating_sub`:

```rust
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
    if erc_decimals >= local_decimals {
        U256::from(value) * U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        U256::from(value) / U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    }
}

pub fn convert_to_balance<B: core::str::FromStr>(
    value: U256, erc_decimals: u8, local_decimals: u8,
) -> Result<B, B::Err> {
    let scaled = if erc_decimals >= local_decimals {
        value / U256::from(10u128.pow((erc_decimals - local_decimals) as u32))
    } else {
        value * U256::from(10u128.pow((local_decimals - erc_decimals) as u32))
    };
    scaled.to_string().parse::<B>()
}
```
Additionally, consider validating at `register_token`/`update_token`/`update_asset_precision` time (or with unit tests covering both directions) that decimal conversions round-trip without loss/inflation, and add explicit test coverage for `local_decimals > erc_decimals` configurations, which the current test suite (`BridgeTokenTest.t.sol`) does not exercise.

### Proof of Concept
1. Governance registers a local asset `X` with `local_decimals = 18` (via `pallet-assets` `Inspect::decimals`) and configures `Precisions::<T>::insert(X, DestChain, 6)` (i.e., the destination EVM `HyperFungibleToken` contract for `X` declares 6 decimals), per the documented per-chain `register_token`/`update_token` flow: [7](#0-6) 
2. A user calls `send` with `params.amount = 1_000_000_000_000_000_000` (1 token, 18 local decimals), which is correctly escrowed/burned locally.
3. `convert_to_erc20(1e18, erc_decimals=6, local_decimals=18)` computes exponent `6u8.saturating_sub(18) = 0`, so `erc20_amount = 1e18 * 10^0 = 1e18` instead of the correct `1e18 / 10^12 = 1_000_000` (1 token at 6 decimals): [8](#0-7) 
4. The dispatched `Message.amount` therefore carries `1e18` raw units to the destination contract, which mints that literal amount to the recipient — 10^12 times the intended value, i.e., an unbacked mint of value never escrowed on the source chain.

/// Converts an ERC20 U256 amount to a local balance type
///
/// Divides by 10^(erc_decimals - local_decimals) to scale down from ERC20 precision.
/// The target type must implement `FromStr`.
pub fn convert_to_balance<B: core::str::FromStr>(
	value: U256,
	erc_decimals: u8,
	local_decimals: u8,
) -> Result<B, B::Err> {
	let dec_str = (value /
		U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)))
	.to_string();
	dec_str.parse::<B>()
}

/// Converts a local u128 balance to an ERC20 U256 amount
///
/// Multiplies by 10^(erc_decimals - local_decimals) to scale up to ERC20 precision
pub fn convert_to_erc20(value: u128, erc_decimals: u8, local_decimals: u8) -> U256 {
	U256::from(value) * U256::from(10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32))
}
