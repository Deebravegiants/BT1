## Finding

### Title
Webhook `shop-domain` header is trusted for tenant identification but is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop` (and `topic`/`webhook_id`) values used to route and attribute the webhook to a specific merchant are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then unconditionally trusts `request.shop` when building the `WebhookMetadata` passed to the host application's handler, so the tenant-identifying field is never bound to the signature that is verified.

### Finding Description
`Utils::HmacValidator.validate` verifies the HMAC using `verifiable_query.to_signable_string`, and for `Webhooks::Request` that method returns only `@raw_body`: [1](#0-0) 

The `shop`, `topic`, `api_version`, and `webhook_id` accessors are all read straight from request headers, none of which participate in the signed content: [2](#0-1) 

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (and other header fields) to build the metadata object dispatched to the app's webhook handler, with no additional binding between the shop identity and the signed body: [3](#0-2) 

Because the webhook signing secret (`api_secret_key`/`client_secret`) is shared by the app across **all** shops that install it, any merchant that installs the app can legitimately receive genuine webhook deliveries containing valid `(body, hmac)` pairs for their own shop. That merchant can then replay the exact same `body`/`hmac` pair to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header value. `HmacValidator.validate` will still succeed because it only checks the body bytes against the secret, and `Registry.process` will hand the handler a `WebhookMetadata` claiming the data belongs to whatever shop the attacker put in the header — a shop the attacker does not control and for which they hold no access token. This breaks the equality that should hold: `shop authenticated by HMAC == shop acted upon by the handler`. In practice, `shop-domain` is acted upon (used for tenant attribution) but is not part of the bytes verified by the HMAC.

### Impact Explanation
This allows a low-privileged unprivileged app installer (any merchant that can install the app on their own store) to forge webhook events that the host application will attribute to a different, victim shop, without ever needing that victim's access token or the app's `client_secret`. Depending on how the host application persists webhook data keyed by `shop`, this enables cross-tenant data injection/corruption — matching the "cross-tenant access" Critical impact category, since one tenant can inject data attributed to another tenant's identity.

### Likelihood Explanation
Exploitability requires only that the attacker be able to install the app on a shop they control (a very low bar for any Shopify app) and be able to POST directly to the app's public webhook endpoint with modified headers — both of which are standard, unprivileged capabilities of any internet-connected merchant/app installer. No secrets, tokens, or elevated access are needed.

### Recommendation
Include the identifying headers (at minimum `shop-domain`, and ideally `topic`/`webhook_id`) in the HMAC-signable content, or otherwise cryptographically bind the shop identity to the verified payload before it is handed to a webhook handler, so that the shop attributed to a webhook cannot be altered independently of the verified signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers a webhook event (e.g., `orders/create`), capturing the raw body `B` and the valid header `x-shopify-hmac-sha256: H` that Shopify computed over `B` using the app's shared secret.
2. Attacker sends a direct POST to the app's webhook endpoint with the same body `B` and same `x-shopify-hmac-sha256: H`, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Utils::HmacValidator.validate` succeeds because it only checks `B` against `H` (see `to_signable_string`), and `Registry.process` dispatches a `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` to the handler, even though the request was neither sent by Shopify on behalf of that shop nor authorized by the victim in any way.
