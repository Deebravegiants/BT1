### Title
Webhook shop-domain and topic identity spoofing via unauthenticated headers - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `api_version`, and `webhook_id` from HTTP headers, none of which are included in the HMAC-signed payload. `Registry.process` validates only the raw body via `Utils::HmacValidator.validate(request)`, then hands a `WebhookMetadata` struct built from the unauthenticated headers to the host application's webhook handler, which uses `shop` as the tenant identifier.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , so `HmacValidator.validate` binds the HMAC solely to the body bytes [2](#0-1) . However, `Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from HTTP headers, entirely outside the signed content [3](#0-2) .

`Registry.process` checks the HMAC and then constructs `WebhookMetadata` using these unauthenticated header values, dispatching it to the registered handler: [4](#0-3) . The `WebhookMetadata` struct exposes `shop` as a first-class field for host applications to key their tenant data on [5](#0-4) .

Binding broken (equality that should hold but doesn't):
`shop_that_produced_and_signed_the_body == shop_header_used_to_route_the_data`

Because the app's `client_secret`/`api_secret_key` is shared across every shop that installs the app, any attacker can install the same app on their own (e.g. free development) store, trigger a webhook delivery, and capture a body + valid `X-Shopify-Hmac-Sha256` pair. Since the header `X-Shopify-Shop-Domain` is not part of the signed content, the attacker can replay the exact same body and valid HMAC to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` (and even `X-Shopify-Topic`) header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never inspected the header), and `Registry.process` invokes the handler with `shop: "victim-shop.myshopify.com"` even though the payload was produced by, and only ever authenticated against, the attacker's own shop.

### Impact Explanation
This crosses a tenant boundary: attacker-controlled webhook data (e.g., orders/customers/products the attacker fully controls on their own store) can be injected into the victim shop's tenant context inside the host application, since the gem hands the host app a `shop` value that was never cryptographically bound to the payload. Depending on how the host app trusts `WebhookMetadata#shop` (typical usage per `docs/usage/webhooks.md` is to key persistence/business logic off it), this enables cross-tenant data injection/corruption without any credentials belonging to the victim.

### Likelihood Explanation
Requires only: (1) the ability to install the target app on an attacker-controlled Shopify store (routine, especially for public apps), (2) the ability to send an arbitrary HTTP POST to the app's public webhook endpoint with attacker-chosen headers (trivial for an unprivileged internet user), and (3) capturing one legitimately-signed webhook body from the attacker's own shop. No secrets, tokens, or victim-side actions are required.

### Recommendation
Include the shop domain (and ideally topic/webhook id/api version) as part of the HMAC-signed content, or independently verify that the `X-Shopify-Shop-Domain` header corresponds to a shop session/installation the host app expects before trusting it, rather than exposing it as an implicitly-trusted field on `WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated and must not be used as sole tenant/routing keys without additional verification (e.g., cross-checking against an installed-shop allowlist).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker.myshopify.com` and triggers a webhook (e.g. `orders/create`) they fully control the content of.
2. Attacker captures the raw request body `B` and header `X-Shopify-Hmac-Sha256: H` sent by Shopify to the app's webhook endpoint (`H` is `HMAC-SHA256(api_secret_key, B)`, valid regardless of shop).
3. Attacker replays a POST to the same webhook endpoint with body `B`, `X-Shopify-Hmac-Sha256: H` (unchanged, still valid since it never covered headers) [1](#0-0) , but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` returns `true` [6](#0-5) , and `Registry.process` invokes the handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON>, ...)` [4](#0-3) , causing the host application to process attacker-controlled data under the victim's tenant identity.
