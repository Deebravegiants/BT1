### Title
Unbounded digest-count and digest-item-length fields in `Codec.DecodeHeader`/`decodeDigestItem` allow a relayed BEEFY parachain-header proof to trigger out-of-gas/DoS during consensus verification - (File: `evm/src/consensus/Codec.sol`)

### Summary
`Codec.DecodeHeader` and `Codec.decodeDigestItem` in `evm/src/consensus/Codec.sol` read SCALE compact-encoded length fields directly from an untrusted, attacker-supplied parachain header byte string and use them to size an in-memory array / slice a byte range, without first checking the claimed length against the amount of data actually remaining in the buffer. This mirrors the CVE-2019-11470 root cause: `ReadCINImage` trusted a claimed image size instead of checking it against the actual remaining file data, causing uncontrolled resource consumption.

### Finding Description
`DecodeHeader` decodes the digest count as a SCALE compact integer and immediately allocates a memory array of that size: [1](#0-0) 
`length` here comes straight from `ScaleCodec.decodeUintCompact(slice)`, which can encode values up to `2^32-1` (mode 2) or larger via mode 3, and is used directly as `new Digest[](length)` with no comparison to `slice.data.length - slice.offset`. Likewise, `decodeDigestItem` reads a length-prefixed digest payload and reads that many bytes via `Bytes.read`: [2](#0-1) 
The only bound enforced is inside `read`/`readByte`, which `require(self.offset + len <= self.data.length)`, so an oversized length eventually reverts — but only after the `for` loop in `DecodeHeader` has already begun iterating `length` times and, on each iteration, calling `Bytes.readByte(slice)` and (for consensus/seal/preruntime digests) `decodeDigestItem`. Because `length` is attacker-controlled and unbounded by any header-size sanity check before the loop starts, a caller can craft a `para.header` whose leading compact-int claims an enormous digest count (e.g. close to `2^32-1`), forcing the EVM to attempt a `Digest[]` allocation of that size and/or iterate that many times before the bounds check inside `readByte` finally reverts. This is the same "claimed size never checked against real remaining data before doing size-driven work" defect as the ImageMagick cineon parser. [3](#0-2) 

Reachability: `DecodeHeader` is called from `EcdsaBeefy.verifyParachainHeaderProof`, once per parachain header supplied in `ParachainProof.parachains`, itself reached from the externally callable `verify()` entrypoint of the BEEFY consensus client: [4](#0-3) [5](#0-4) 
The `proof` bytes (including each parachain's `header`) are ABI-decoded from calldata supplied by whoever submits the consensus update — an unprivileged relayer. `SP1Beefy.sol` similarly decodes `ParachainHeader[]` from calldata and hashes each header, though it does not call `Codec.DecodeHeader` directly in the excerpt seen.

### Impact Explanation
An unprivileged relayer submitting a BEEFY consensus update can craft a `para.header` whose SCALE-compact digest-count claims a very large value. Solidity's `new Digest[](length)` for a sufficiently large `length` either reverts immediately with an out-of-gas/allocation failure, or (for values that pass allocation but still exceed real header content) forces the verifier to loop and read bytes until the `require` in `Bytes.readByte`/`Codec.read` finally reverts. Either way this wastes the gas of whichever party pays for the transaction (the relayer, or in a batched/subsidized relay path, the protocol) and — more importantly — since `verify()` is a `pure` view-style function invoked as part of consensus-state update processing, a header engineered to always revert at this stage prevents that parachain's header from ever being finalized through this proof, denying legitimate state updates for the state machines whose commitments live in that MMR leaf batch until a differently-crafted proof is relayed. This is a resource-consumption / message-delivery-availability issue rather than fund theft, consistent with the Medium severity of the CVE analog.

### Likelihood Explanation
Likelihood is high for triggering the revert: any relayer can submit a consensus proof through `EcdsaBeefy.verify`, and crafting a header with an oversized SCALE compact-int digest count requires no privileged access — only knowledge of the SCALE encoding, which is public. The main mitigating factor is that Solidity's own gas metering and the `require` bound inside `read`/`readByte` will cause a revert relatively quickly (bounded by block gas limit) rather than allowing unbounded off-chain resource exhaustion as in the original ImageMagick case, so the practical impact is transaction-level DoS/gas-griefing rather than node-level resource exhaustion.

### Recommendation
Before allocating `Digest[]` in `DecodeHeader`, and before calling `Bytes.read(slice, length)` in `decodeDigestItem`, validate the claimed `length` against `slice.data.length - slice.offset` (i.e., the actual remaining bytes) and revert early with a clear error if the claim exceeds what the buffer can supply. This turns an expensive, allocation-then-revert path into a cheap, immediate rejection, matching the pattern used elsewhere in this codebase (e.g., `MAX_PROOF_DEPTH` bound checks in `modules/consensus/pharos/primitives/src/spv.rs` and the `MAX_VALIDATORS`/`InsufficientStorageValues` checks in `modules/consensus/pharos/verifier/src/state_proof.rs`) which explicitly check claimed counts/lengths against actual available data before doing size-driven work.

### Proof of Concept
1. Construct a `para.header` byte string that starts with the required 32+4+32+32 = 100 bytes of parent hash / block number compact-int / state root / extrinsics root, followed by a SCALE compact-int digest count encoded in mode 2 or 3 claiming a value close to `type(uint32).max` (or higher via mode-3 encoding), with no further bytes.
2. Submit this header as part of a `ParachainProof.parachains[i].header` in a call to `EcdsaBeefy.verify(previousState, proof)` (via the `HandlerV2`/consensus-update dispatch path an unprivileged relayer can reach).
3. Execution enters `verifyParachainHeaderProof` → `Codec.DecodeHeader`, which attempts `new Digest[](length)` for the attacker-chosen `length`, exhausting gas or reverting only after wasted computation, instead of failing fast on the mismatch between claimed digest count and actual remaining header bytes.

    /// @dev Reads `len` bytes from the slice at the current offset and advances the cursor.
    function read(ByteSlice memory self, uint256 len) internal pure returns (bytes memory) {
        require(self.offset + len <= self.data.length);
        if (len == 0) {
            return "";
        }
        uint256 addr = Memory.dataPtr(self.data);
        bytes memory slice = Memory.toBytes(addr + self.offset, len);
        self.offset += len;
        return slice;
    }

    /// @dev Reads a single byte from the slice at the current offset and advances the cursor.
    function readByte(ByteSlice memory self) internal pure returns (uint8) {
        require(self.offset + 1 <= self.data.length);

        uint8 b = uint8(self.data[self.offset]);
        self.offset += 1;

        return b;
    }
