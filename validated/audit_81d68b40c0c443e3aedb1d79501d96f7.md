## Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw request body only, while the `shop` attribute used by application code to attribute a webhook to a tenant is read from an HTTP header that is never included in that signed content. Because a single app-level `api_secret_key` signs webhooks for *every* installed shop, an attacker who controls one shop (any free/dev store can install a public app) can capture one genuinely-signed webhook and replay it to the app's webhook endpoint with the `shop-domain`/`x-shopify-shop-domain` header rewritten to a victim shop, while `Utils::HmacValidator.validate` still reports the signature as valid.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

The `shop` accessor is derived purely from an HTTP header, entirely independent of the signed content: [2](#0-1) [3](#0-2) 

`Registry.process` validates only the HMAC-over-body and then forwards `request.shop` unchanged to the host application's handler as the tenant identity for the event: [4](#0-3) 

`HmacValidator.validate`/`validate_signature` confirm the check is solely `OpenSSL.secure_compare(computed_signature, received_signature)` where `computed_signature` is derived from `to_signable_string` (body only) and the app's shared `api_secret_key`: [5](#0-4) 

This breaks the identity binding: `shop attributed to the event` != `shop whose secret/context actually produced the signed bytes`. The equality that should hold — `shop conveyed in the signed payload == shop used by the handler as tenant context` — does not, because `shop` is carried out-of-band in a header that is not part of `to_signable_string`. Contrast this with the OAuth callback path, where `shop` **is** part of the HMAC-covered query (`AuthQuery`), confirming the webhook path is inconsistent and under-covers this identity-bearing field: [6](#0-5) 

### Impact Explanation
Because `api_secret_key` is a single per-app secret shared across all shops that install the app (not per-shop), any unprivileged user who installs the app on their own store obtains a valid HMAC/body pair for arbitrary payload content they can trigger (e.g., by generating events in their own store). They can then replay that exact `(body, hmac)` pair to the app's public webhook endpoint while substituting the `shop-domain` header for a victim shop. `Registry.process` accepts it as valid and hands the handler a `WebhookMetadata` object whose `shop` field is attacker-controlled but whose `hmac` validation passed — allowing cross-tenant event injection (e.g., forged `orders/create`, `app/uninstalled`, `customers/data_request`, etc. attributed to a shop the attacker does not control). This matches the Critical "cross-tenant access" impact category, since the host application has no gem-provided mechanism to detect that the `shop` value is unauthenticated.

### Likelihood Explanation
Likelihood is high for any deployment that trusts `WebhookMetadata#shop` (as returned by this gem) to select tenant-specific state (session/access token lookup, per-shop database row, etc.) — this is the documented intended use of the field per `docs/usage/webhooks.md` and `WebhookHandler`. The only prerequisite is the attacker being able to install the target app on any store they control (a trivial, unprivileged action for public apps) and being able to POST directly to the app's public webhook endpoint, which is exposed to the internet by design so Shopify can deliver webhooks to it.

### Recommendation
Include the shop domain (and ideally topic/webhook id) as part of the HMAC-signed content, or otherwise cryptographically bind the header-derived identity fields to the signature before they are trusted by `Registry.process`/`WebhookMetadata`. At minimum, document prominently that `WebhookMetadata#shop` is not authenticated by the HMAC and must not be used as a sole tenant-selection key without additional verification (e.g., cross-checking against a shop that is already known to have this webhook subscription active).

### Proof of Concept
1. Attacker installs the target Shopify app on their own store `attacker.myshopify.com`, triggering a legitimate webhook, e.g. `orders/create`, delivered with body `B` and header `x-shopify-hmac-sha256: H` (valid HMAC of `B` using the app's shared `api_secret_key`), and `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker captures this request and replays it to the same webhook endpoint, unchanged except:
   - `x-shopify-shop-domain: victim.myshopify.com`
3. Server-side, `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: forged_headers)` is constructed; `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and it matches `H`, so validation passes. [7](#0-6) 
4. The handler receives `WebhookMetadata.new(topic: "orders/create", shop: "victim.myshopify.com", body: parsed_body, ...)` — a forged event attributed to a shop the attacker does not control, despite a "valid" signature.
