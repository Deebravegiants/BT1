### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating the HMAC over the raw request body only, but then hands the handler a `shop` value that is taken from an unauthenticated HTTP header. The HMAC-authenticated bytes and the tenant-identifying bytes are not the same thing, breaking the identity binding `hmac_verified_origin == request.shop`.

### Finding Description
`Registry.process` gates processing solely on:
```ruby
raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
...
handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))
``` [1](#0-0) 

`Utils::HmacValidator.validate` computes the signature over `verifiable_query.to_signable_string`, and for a webhook `Request` that method returns only the raw body:
```ruby
sig { override.returns(String) }
def to_signable_string
  @raw_body
end
``` [2](#0-1) 

Meanwhile `shop` (and `topic`, `webhook_id`, `api_version`) is read straight from HTTP headers with no cryptographic tie to the HMAC:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
``` [3](#0-2) 

The HMAC validator itself confirms only that `secret` produced `hmac` over the body bytes — it never touches the shop header:
```ruby
def validate_signature(verifiable_query, secret)
  received_signature = verifiable_query.hmac
  computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
  OpenSSL.secure_compare(computed_signature, T.must(received_signature))
end
``` [4](#0-3) 

Consequently `handler.handle` receives a `WebhookMetadata` whose `shop` field is asserted to be the tenant that the HMAC-authenticated body came from, but that binding is never checked: `shop` can be swapped for any value while keeping a body+HMAC pair that is valid for a *different*, attacker-controlled shop.

### Impact Explanation
Any merchant who installs the app (an "unprivileged" tenant relative to other merchants using the same app) legitimately receives real Shopify-signed webhooks for their own store — genuine `body` + `X-Shopify-Hmac-Sha256` pairs computed by Shopify using the app's secret. By replaying such a payload to the app's webhook endpoint with the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header changed to a victim shop's domain, the attacker gets the gem to report `Errors::InvalidWebhookError` — false, since HMAC still validates on the untouched body — and forward attacker-controlled webhook content attributed to a victim tenant to the handler. If the host application uses `WebhookMetadata#shop` to select which merchant record/session/access token to act on (the documented, expected usage pattern shown in `docs/usage/webhooks.md`), this is a cross-tenant data confusion / cross-tenant access vector requiring no leaked credentials, no elevated privileges — only that the attacker also be an app-installing merchant, which is the unprivileged baseline for a public commerce app.

### Likelihood Explanation
Any app that installs `shopify_api` and follows the documented webhook processing pattern (`ShopifyAPI::Webhooks::Registry.process`) is affected, since the gem itself never binds `shop` to the HMAC. Exploitation only requires a merchant to run the app on their own store (to legitimately obtain a valid signed payload) and forge/replay the shop-domain header — both of these are reachable by an ordinary, unprivileged app-installing user.

### Recommendation
Bind `shop` into the signed payload (e.g. verify it as part of `to_signable_string`, or require the caller to supply the authenticated shop out-of-band and cross-check it against a value covered by the HMAC) before trusting `request.shop`/`WebhookMetadata#shop` in `Registry.process`.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g. `orders/create`) to receive a body `B` with a valid `X-Shopify-Hmac-Sha256: H` (computed by Shopify using the app's real secret).
2. Replay `POST /webhook` with the same `raw_body = B`, same `x-shopify-hmac-sha256 = H`, but set `x-shopify-shop-domain: victim.myshopify.com`.
3. `Utils::HmacValidator.validate` returns `true` (it only checks `B` against `H`) — see `lib/shopify_api/utils/hmac_validator.rb:26-31`.
4. `Registry.process` calls `handler.handle` with `shop: "victim.myshopify.com"` even though the body actually originated from `attacker.myshopify.com` — see `lib/shopify_api/webhooks/registry.rb:188-199` and `lib/shopify_api/webhooks/request.rb:20-23,35-38`.
