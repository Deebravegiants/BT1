### Title
Denial of Service via Unbounded/Non-Terminating Loop in GRANDPA `AncestryChain::ancestry` Walk - (File: modules/consensus/grandpa/primitives/src/justification.rs)

### Summary
`AncestryChain::ancestry` walks a parent-hash chain built entirely from attacker-supplied `unknown_headers` inside a submitted GRANDPA `FinalityProof`/`ConsensusMessage`, without any cycle detection or visited-set bound. A relayer can craft two (or more) headers whose `parent_hash` fields point at each other, forming a cycle in the `BTreeMap<Hash, Header>` that backs the walk. When `ancestry()` is invoked on a path that enters this cycle without reaching `base`, the `while current_hash != base` loop never terminates, hanging the runtime call indefinitely. This is functionally the same bug class as the reported go-attestation issue — an attacker-controlled recursive/iterative structure walk with no depth/visited bound, driven by a single untrusted submission, causing denial of service — except here it manifests as an infinite loop rather than a stack overflow, with the same "verifier hangs / crashes" impact.

### Finding Description
`AncestryChain` is built directly from the `votes_ancestries`/`unknown_headers` vector supplied inside a `Message::Consensus` payload: [4](#0-3) 

Its core traversal has no protection against cycles: [5](#0-4) 

The map key for each header is `header.hash()` (a real cryptographic hash of the header's SCALE-encoded content), but the `parent_hash` *field value* inside each header is fully attacker-chosen — it is just part of the payload the attacker constructs before hashing. This lets an attacker build two headers `A` and `B` such that:
- `A.parent_hash = hash(B)`, and
- `B.parent_hash = hash(A)`

Both `A` and `B` are legitimate, self-consistent entries for the `BTreeMap` (keyed by their own real hash), so `AncestryChain::new` accepts them without complaint. There is no requirement anywhere before `ancestry()` runs that the header set forms an acyclic chain toward `base`, nor is there a "visited nodes" bound in the loop itself.

This walk is called from `verify_grandpa_finality_proof`, on the untrusted `unknown_headers` submitted by any caller of `handle_unsigned`: [6](#0-5) 

and again inside `GrandpaJustification::verify_with_voter_set`, walking from each precommit's target hash to the commit base, using the identical unbounded `ancestry()` call: [7](#0-6) 

If the walk's starting point (a precommit target, or the finality-proof `target`/`from`) is routed into the crafted cycle before reaching `base`, `current_hash` will oscillate between the cyclic hashes forever, since both are always present in the map and neither equals `base`. Because this executes inside on-chain runtime logic during transaction-pool validation (`validate_unsigned`) and dispatch (`handle_unsigned`), there is no cooperative yield point to interrupt it — the call spins until externally killed, hanging block-import/validation for that submission.

### Impact Explanation
`handle_unsigned` is explicitly a fee-free, permissionless unsigned extrinsic — "Execute the provided batch of ISMP messages for free with valid proofs" [8](#0-7) . A single crafted `Message::Consensus` carrying a GRANDPA/relay finality proof with a two-header hash cycle in `unknown_headers`/`votes_ancestries` is enough to drive the vulnerable node into an unbounded loop, both during transaction-pool `validate_unsigned` (before any fee is charged) and during actual block execution if included. This can stall transaction-pool validation and/or block execution on any node running the GRANDPA consensus client (used to bridge Polkadot/Kusama relay chains and standalone GRANDPA chains into Hyperbridge), which is a route-availability/liveness denial of service — messages cannot be delivered while the node is hung, matching the "route unable to deliver messages" acceptance criterion.

### Likelihood Explanation
Constructing the two colliding headers requires no cryptographic break: the attacker fully controls both headers' contents (including `parent_hash`) before hashing, so building a 2-cycle `A.parent_hash == hash(B)`, `B.parent_hash == hash(A)` is a straightforward, deterministic exercise, not a hash preimage attack. The only requirement is that these headers pass whatever minimal structural decoding validation exists (SCALE decode of `sp_runtime::generic::Header`), which imposes no semantic constraint on `parent_hash`. The attack is submittable as a normal unsigned extrinsic by anyone, with no signature or stake requirement, and no economic cost since the call is fee-free.

### Recommendation
In `AncestryChain::ancestry`, bound the walk with a visited-set (or a maximum iteration count equal to `self.ancestry.len() + 1`) and return `Error::NotDescendent` (or a new cycle-specific error) as soon as a `current_hash` is revisited, rather than looping until `current_hash == base`. Additionally, consider validating on construction that `unknown_headers` forms a strictly decreasing-by-number chain (GRANDPA ancestry should always move to strictly lower block numbers), which would reject any cycle structurally before the walk even begins.

### Proof of Concept
1. Construct header `B` with an arbitrary `parent_hash` placeholder, compute `hash(B)`.
2. Construct header `A` with `parent_hash = hash(B)`; compute `hash(A)`.
3. Rebuild `B` with `parent_hash = hash(A)` (fixing up any other fields as needed to keep `hash(B)` consistent, e.g., by iterating the construction so the two hashes are mutually consistent — trivial since both are pure functions of attacker-chosen bytes).
4. Submit a `Message::Consensus(ConsensusMessage { consensus_proof: <finality proof containing A, B in unknown_headers, with the commit/precommit target routed through A or B>, .. })` via `pallet_ismp::Call::handle_unsigned`.
5. Observe that `verify_grandpa_finality_proof` → `AncestryChain::ancestry` enters the `A ⇄ B` cycle and never returns, hanging `validate_unsigned`/execution for that submission.

	fn ancestry(
		&self,
		base: H::Hash,
		block: H::Hash,
	) -> Result<Vec<H::Hash>, finality_grandpa::Error> {
		let mut route = vec![block];
		let mut current_hash = block;
		while current_hash != base {
			match self.ancestry.get(&current_hash) {
				Some(current_header) => {
					current_hash = *current_header.parent_hash();
					route.push(current_hash);
				},
				_ => return Err(finality_grandpa::Error::NotDescendent),
			};
		}
		Ok(route)
	}
