### Title
Missing parameter validation in `IntentGatewayV2.setParams()` (Tron) allows deployer to set unbounded fee/surplus basis points, causing a hard, permanent freeze of the intents route - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron port of `IntentGatewayV2` exposes a one-time `setParams()` function that stores the supplied `Params` struct with no bounds checking, unlike the canonical EVM implementation of the same contract, which validates every field of `Params` (including `protocolFeeBps` and `surplusShareBps` against the 10,000 bps basis) before accepting them.

### Finding Description
In the mainline EVM `IntentGatewayV2`/`IntentsBase`, all parameter updates go through `_validateParams`, which explicitly bounds `protocolFeeBps` and `surplusShareBps` to `<= 10_000`/`< 10_000` and requires `host`/`dispatcher` to be contracts: [1](#0-0) 

Tests confirm this validation is enforced both on `initialize()` (the deployer-controlled setup path) and on governance `updateParams`: [2](#0-1) 

The Tron variant of the same contract, however, implements its one-time admin setup function `setParams()` with no validation at all — it simply overwrites `_params` and permanently zeroes out `_admin` so the function can never be called again: [3](#0-2) 

Because `_admin` is irreversibly cleared after the single call (line 309), there is no other function in this contract that can correct a bad `Params` value afterward (the file contains no `_validateParams`/governance `updateParams` counterpart reachable to fix it).

`_params.protocolFeeBps` is later used unchecked in `placeOrder()` to compute a "reduced" input amount: [4](#0-3) 

If `protocolFeeBps` is set above 10,000 (100%), then for any order input `protocolFee = originalAmount * protocolFeeBps / 10_000` exceeds `originalAmount`, and the subtraction `originalAmount - protocolFee` underflows. Since the contract targets Solidity `^0.8.24` with default checked arithmetic, this reverts unconditionally, meaning every single call to `placeOrder()` will revert as long as `protocolFeeBps > 10_000`.

### Impact Explanation
Because `setParams()` can be invoked only once and there is no recovery path to update `_params` afterward on this Tron deployment, a deployer/admin mistake (or a value that is technically "valid Solidity" but exceeds the intended basis-points range, exactly the situation flagged in the source report) permanently bricks the Tron `IntentGatewayV2` instance: `placeOrder()` (the only entry point for creating intents on that chain) reverts for every order, i.e., the route can never accept or deliver intents again. This falls squarely under "a route unable to deliver messages," a permanent denial of the intents escrow functionality with no way to remediate other than redeploying the whole contract (losing the `_instances`/routing configuration already established with peer chains).

### Likelihood Explanation
The bug is triggered by a single call from the deployer/admin address recorded in the constructor, using a `Params` value that is out-of-range relative to the documented and enforced basis-points semantics (`10000 = 100%`) used identically across the codebase (see the Solidity struct doc comments and the coprocessor's mirrored Rust type): [5](#0-4) 

Given that the canonical implementation already treats this as a real risk worth guarding against (and enforces it with `require`/`revert` checks and dedicated tests), the same misconfiguration risk exists on the Tron deployment but with no safety net — a single erroneous or malicious initial `setParams()` call permanently disables the gateway.

### Recommendation
Add the same validation used in `IntentsBase._validateParams` to the Tron `setParams()` function before assigning `_params = p`:
- `require(p.host != address(0) && p.host.code.length > 0)`
- `require(p.dispatcher != address(0) && p.dispatcher.code.length > 0)`
- `require(p.surplusShareBps <= 10_000)`
- `require(p.protocolFeeBps < 10_000)`
- `require(p.priceOracle == address(0) || p.priceOracle.code.length > 0)`

Alternatively, refactor the Tron contract to reuse `IntentsBase._validateParams` directly to keep both deployments' validation logic in sync.

### Proof of Concept
1. Deploy `IntentGatewayV2` (Tron variant) with `admin = deployer`.
2. `deployer` calls `setParams(Params({..., protocolFeeBps: 15000, surplusShareBps: 5000, ...}))` — this succeeds and zeroes `_admin`, since no bound is checked. [6](#0-5) 
3. Any user calls `placeOrder(order, graffiti)` with a nonzero input amount.
4. Inside `placeOrder`, `protocolFee = originalAmount * 15000 / 10000` exceeds `originalAmount`, causing `originalAmount - protocolFee` to underflow and revert under Solidity 0.8's checked arithmetic. [7](#0-6) 
5. Every subsequent call to `placeOrder` reverts identically; since `_admin` is already `address(0)`, `setParams` can never be called again to correct the value, permanently freezing the intents route on this deployment.

    function _validateParams(Params memory p) internal view {
        if (p.host == address(0) || p.host.code.length == 0) revert InvalidInput();
        if (p.dispatcher == address(0) || p.dispatcher.code.length == 0) revert InvalidInput();
        if (p.surplusShareBps > 10_000) revert InvalidInput();
        if (p.protocolFeeBps >= 10_000) revert InvalidInput();
        if (p.priceOracle != address(0) && p.priceOracle.code.length == 0) revert InvalidInput();
    }
