### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant shop spoofing on a validly-signed webhook body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity by computing an HMAC over the raw request body only (`to_signable_string` returns `@raw_body`). The `shop` identity that host applications use to attribute the webhook to a specific tenant is read from the unauthenticated `X-Shopify-Shop-Domain` header via `Request#shop`, which is never included in the signed bytes. This is the same class of bug as the reported analog: a field that is *acted on* (used as the tenant/session key by the consuming application) is not *covered by the authentication tag* (the HMAC), breaking the binding `hmac_verified_bytes == bytes_the_application_trusts_as_the_shop_identity`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` and `Request#topic` are pulled straight from HTTP headers with no relation to the signed payload: [2](#0-1) 

`Utils::HmacValidator.validate` only checks `verifiable_query.hmac` against `compute_signature(verifiable_query.to_signable_string, secret)` — i.e., it validates the body bytes, and returns `true`/`false` with no participation of `shop` or `topic`: [3](#0-2) 

Because `shop` (and `topic`) are outside the HMAC's scope, `HmacValidator.validate(request)` returning `true` only proves "this body was signed by Shopify with our secret" — it proves nothing about which shop the body came from. Any consuming application that trusts `request.shop` (as the gem's own accessor implies it should) once `HmacValidator.validate` passes is trusting an attacker-controlled, unauthenticated value for tenant attribution.

### Impact Explanation
This breaks the identity binding `hmac_authenticated_shop == shop_used_for_tenant_routing`. An attacker who can capture or predict one legitimately-signed webhook body/HMAC pair (e.g., by triggering a webhook for their own shop, or for any webhook whose body content is static/predictable such as `app/uninstalled` on a low-cardinality field set) can resend that exact body+hmac to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header value naming a victim shop. `HmacValidator.validate` still returns `true` because the header is not part of the signed bytes, and the host application — using this gem's documented `Request#shop` accessor as the "verified" shop — will process the event as if it authentically originated from the victim tenant. This is a cross-tenant confusion vector fitting the "cross-tenant access" impact category, since the gem hands the caller an unauthenticated value under the guise of a verified one.

### Likelihood Explanation
Exploitation requires the attacker to obtain at least one valid (body, hmac) pair signed with the app's `client_secret` — trivially available to any merchant who installs the app (they can trigger `app/uninstalled`, `shop/update`, or any webhook on their own store and capture the raw POST). No access to the `client_secret` itself, no TLS interception, and no privileged account is required beyond controlling one's own shop installation, which fits the "unprivileged internet user" threat model. The main variable is the entropy/uniqueness of the raw body across shops; for larger bodies with shop-specific data (e.g. embedded shop id/domain in the JSON), the attacker would need the domain field inside the body to also match, but this gem does not enforce that binding either — it never cross-checks the header shop against any shop_domain field carried in the body.

### Recommendation
Include the `X-Shopify-Shop-Domain` (and ideally `X-Shopify-Topic`) header values as part of the data that `HmacValidator` verifies, or, at minimum, document and enforce that `Request#shop` must not be trusted as an authenticated value unless the caller independently cross-checks it against the expected/registered shop for the session under which the webhook was expected. Concretely, change `Request#to_signable_string` (or add a second verification step) to bind the header-derived `shop` value into the signed material, or expose an API that fails closed unless the caller supplies the expected shop and the gem checks it against the header before exposing `shop`.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker.myshopify.com` and captures a legitimate webhook delivery, e.g. `app/uninstalled`, obtaining `raw_body` and header `X-Shopify-Hmac-Sha256: <hmac>`.
2. Attacker replays the exact `raw_body` and `X-Shopify-Hmac-Sha256` header to the victim app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. The host app calls:
```ruby
request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers)
ShopifyAPI::Utils::HmacValidator.validate(request) # => true, because HMAC only covers raw_body
request.shop # => "victim-shop.myshopify.com" (attacker-controlled, unauthenticated)
``` [4](#0-3) 
4. `HmacValidator.validate` returns `true` (per `lib/shopify_api/utils/hmac_validator.rb:12-31`), and any code path that trusts `request.shop` post-validation processes the event as belonging to `victim-shop.myshopify.com`, achieving cross-tenant confusion using only a self-service webhook the attacker legitimately received for their own store.

          end

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
