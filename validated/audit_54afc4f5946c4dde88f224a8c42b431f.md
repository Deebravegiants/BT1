This confirms the finding: the gem's own documentation (`docs/usage/webhooks.md:125`) explicitly states that `ShopifyAPI::Webhooks::Registry.process` "will verify the request did indeed come from Shopify" — i.e., the gem itself claims the HMAC verification authenticates the whole request, including the shop attribution, and instructs host apps to trust `data.shop` (`docs/usage/webhooks.md:14,26`) for tenant routing. This is the gem's documented API contract, so the gap is not "host app ignoring documented behavior" — it's the gem's own verification method failing to bind the field it advertises as verified.

### Title
Webhook HMAC only signs the raw body, allowing shop-domain spoofing / cross-tenant webhook injection - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `Utils::HmacValidator.validate` verifies solely the body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values consumed by `Registry.process` and handed to app handlers via `WebhookMetadata` come straight from unauthenticated HTTP headers and are never included in the signed content.

### Finding Description
`Registry.process` calls `Utils::HmacValidator.validate(request)` and, once it passes, immediately builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...)` from header-derived accessors [1](#0-0) . `Request#hmac` and `Request#to_signable_string` show that only the raw body is part of the signable string, while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from `shopify-*`/`x-shopify-*` headers with no cryptographic binding to that body [2](#0-1) .

The binding the gem claims to provide is: `shop_header == shop_that_the_secret_holder_actually_signed_for`. In reality only `body == body_that_was_signed` is checked; `shop` (and `topic`/`webhook_id`) are unauthenticated. The documentation instructs developers that `process` "will verify the request did indeed come from Shopify" and to trust `data.shop` for downstream routing [3](#0-2) , and lists `shop` as a verified field of `WebhookMetadata` [4](#0-3) .

Since `Context.api_secret_key`/`client_secret` is the same across every shop that has the app installed, any attacker who controls (or installs the app on) their own shop receives genuinely Shopify-signed webhook bodies with valid HMAC values computed with that shared secret. The attacker can replay that exact body and HMAC to the host app's webhook endpoint while substituting the `x-shopify-shop-domain` header for a victim shop. `HmacValidator.validate` still succeeds because it only checks the body against the shared secret [5](#0-4) , and `Registry.process` will invoke the app's handler with `data.shop` set to the forged victim domain [6](#0-5) .

### Impact Explanation
Because host applications are directed by this gem's documentation to key their tenant logic off `WebhookMetadata#shop` (session lookups, per-shop data writes, job enqueuing as shown in the doc example), an attacker-controlled shop can inject attacker-chosen webhook bodies that the host application will process as if they originated from an arbitrary victim shop. This is a cross-tenant access vector attributable to the gem's own verification routine, not to any misuse of undocumented behavior.

### Likelihood Explanation
Medium-to-high: the only prerequisite is that the attacker can install the target app on a shop they control (a normal, permitted action for any public app), then capture one Shopify-issued webhook (any topic) and replay it at the host's webhook endpoint with a modified shop-domain header. No access to the app's `client_secret` beyond what is already implicitly usable through the attacker's own legitimately signed webhook is required.

### Recommendation
Include the identifying headers (`shop-domain`, `topic`, `webhook_id`, `api_version`) in the signable content used by `HmacValidator`, or otherwise cryptographically bind them to the body before exposing `WebhookMetadata` to handlers. At minimum, update `to_signable_string` in `Request` to combine body and headers, and document that `shop`/`topic` are not verified fields if binding them is not feasible, so host applications do not misplace trust in `data.shop`.

### Proof of Concept
1. Attacker installs the target Shopify app on `attacker-shop.myshopify.com` and receives a legitimate webhook, e.g. body `{"id":1}` with header `x-shopify-hmac-sha256: <valid-hmac-of-body>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
2. Attacker POSTs the identical raw body and `x-shopify-hmac-sha256` value to the host app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `Registry.process` calls `HmacValidator.validate(request)` [7](#0-6) ; validation passes because it only checks `to_signable_string` (the raw body), which is unchanged and correctly signed with the shared `api_secret_key`.
4. The host handler receives `data.shop == "victim-shop.myshopify.com"` and `data.body` fully attacker-controlled, and processes/queues the action against the victim tenant's records, as shown in the documented handler pattern [8](#0-7) .

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. class WebhookController < ApplicationController

    )
    render json: {success: true}.to_json
  end
end
