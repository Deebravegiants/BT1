### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, but `Utils::HmacValidator.validate` only verifies the HMAC over the raw request body (`to_signable_string` returns `@raw_body`). The header that identifies *which shop* a webhook belongs to is never part of the signed payload, so anyone who can present a body+HMAC pair that is valid for the app's shared `api_secret_key` (e.g. a merchant who has that app installed on their own store and receives genuine webhooks) can re-submit that exact body/HMAC pair with an arbitrary `shop-domain` header and have `ShopifyAPI::Webhooks::Registry.process` accept it as coming from a different, victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request` exposes `shop` straight from the header, independent of the signed content: [1](#0-0) [2](#0-1) 

The HMAC-signable string used for verification is only the raw body: [3](#0-2) 

`HmacValidator.validate` computes `OpenSSL::HMAC.hexdigest(sha256, Context.api_secret_key, verifiable_query.to_signable_string)` and compares it against the received `hmac`, so it validates only the body bytes, never the `shop`, `topic`, `api-version`, or `webhook-id` headers: [4](#0-3) 

`Registry.process` trusts `request.shop` as the tenant identity and forwards it straight to the app's webhook handler once the (body-only) HMAC check passes: [5](#0-4) 

Crucially, `Context.api_secret_key` is a single, app-wide secret shared across every shop that has the app installed — it is not a per-shop secret: [6](#0-5) 

The broken binding is:
`HMAC(api_secret_key, raw_body) == valid` ⇏ `shop header == actual originating shop`

Because the signature is app-wide (not shop-scoped) and only covers the body, any tenant of a multi-tenant app that legitimately receives a genuine `(raw_body, hmac)` pair from Shopify for their own shop can replay that exact pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still returns `true` (the body/HMAC pair is genuinely valid for the app secret), and `Registry.process` will invoke the handler with `WebhookMetadata.shop` set to the attacker-chosen victim shop, along with the attacker's own webhook body.

### Impact Explanation
This crosses a tenant boundary within a single app installation: an unprivileged app user/merchant (who is simply a valid tenant, not a privileged operator, and does not need the app's `client_secret`/`api_secret_key` — they only need a webhook body+HMAC that Shopify legitimately sent to their own store) can cause the host application's webhook handler to process attacker-supplied webhook data under a different shop's identity. Depending on how the host app trusts `WebhookMetadata#shop` (e.g. to select the session/access token to act on, update tenant-scoped records, or trigger tenant-scoped side effects), this enables cross-tenant data manipulation — matching the Critical "cross-tenant access" category, since the root cause (the un-bound identity field) resides in this gem's `Webhooks::Request`/`HmacValidator`/`Registry.process` implementation rather than host-app misuse.

### Likelihood Explanation
Any merchant who installs the app receives genuine `(body, hmac)` pairs for their own shop's webhooks as part of normal operation — no special access, credential theft, or knowledge of `api_secret_key` is required. Forging the header requires only sending a raw HTTP POST with a different `X-Shopify-Shop-Domain` value and the previously-observed body/HMAC, which is trivial to script. The only barrier is that the attacker must already be a legitimate (if unprivileged) tenant able to receive at least one real webhook, which is a very low bar for any installed multi-tenant app.

### Recommendation
Bind the shop identity into the verified payload rather than trusting an unauthenticated header:
- Include `shop-domain` (and ideally `topic`, `api-version`, `webhook-id`) in the HMAC-signable string in `Webhooks::Request#to_signable_string`, or
- If Shopify's webhook HMAC scheme genuinely signs only the body (as is the real Shopify webhook spec), document that `Registry.process` callers must independently verify that `request.shop` corresponds to a shop with a valid, expected installation/session in the host app **before** trusting the body's contents for that shop — and make this an explicit, enforced check inside `Registry.process` rather than leaving it to be assumed by consuming apps.

### Proof of Concept
1. Shop A has the vulnerable app installed. Shopify sends a genuine webhook to the app for Shop A:
   ```
   POST /webhooks
   X-Shopify-Topic: orders/create
   X-Shopify-Hmac-Sha256: <valid HMAC of BODY under api_secret_key>
   X-Shopify-Shop-Domain: shop-a.myshopify.com
   Body: BODY
   ```
2. A user with access to Shop A's webhook traffic (e.g. the merchant themselves, or anything that can observe the request such as a shared logging/proxy layer) captures `BODY` and the valid `X-Shopify-Hmac-Sha256` value.
3. They replay the identical `BODY` and `X-Shopify-Hmac-Sha256` to the same app endpoint, but with:
   ```
   X-Shopify-Shop-Domain: shop-b.myshopify.com
   ```
4. `ShopifyAPI::Utils::HmacValidator.validate(request)` in `lib/shopify_api/utils/hmac_validator.rb` recomputes the HMAC over `request.to_signable_string` (which is only `BODY`), matches it against the supplied HMAC, and returns `true` — the header substitution is never checked.
5. `ShopifyAPI::Webhooks::Registry.process` in `lib/shopify_api/webhooks/registry.rb` proceeds and calls the app's handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", body: <Shop A's data>, ...)`, causing the app to process Shop A's (attacker-controlled) webhook content as if it belongs to Shop B.
