### Title
`do_cancel_named` silently skips `Retries` cleanup and `Preimages::drop` when invoked with `origin: None`, orphaning retry state and preimage holds - (File: substrate/frame/scheduler/src/lib.rs)

### Summary
`Pallet::do_cancel_named` only removes the `Retries<T>` entry and calls `T::Preimages::drop` inside the branch that checks `(Some(origin), Some(scheduled))`, meaning any caller of the internal `schedule::v3::Named::cancel_named(id)` trait method — which always calls `do_cancel_named(None, id)` — permanently orphans the `Retries` entry and leaves the preimage held/un-dropped, even though the task slot is cleared. This differs from the anonymous-task counterpart `do_cancel`, which unconditionally drops the preimage and removes `Retries` regardless of `origin`.

### Finding Description
Compare the two cancellation paths: [1](#0-0) 

`do_cancel` unconditionally executes `T::Preimages::drop(&s.call)` and `Retries::<T>::remove((when, index))` once a scheduled task is taken out of the agenda — the `origin` option is only used for the privilege check, not to gate cleanup.

`do_cancel_named`, however, nests the cleanup calls *inside* the same conditional block that performs the origin privilege check: [2](#0-1) 

```
if let Some(s) = agenda.get_mut(i) {
    if let (Some(ref o), Some(ref s)) = (origin, s.borrow()) {
        Self::ensure_privilege(o, &s.origin)?;
        Retries::<T>::remove((when, index));
        T::Preimages::drop(&s.call);
    }
    *s = None;
}
```

When `origin` is `None`, the outer `if let` still matches `Some(s)` (the slot is `Some`), but the inner tuple pattern `(Some(ref o), Some(ref s))` fails because `origin` is `None`. As a result:
- `Retries::<T>::remove((when, index))` is **never called**.
- `T::Preimages::drop(&s.call)` is **never called**.
- The slot is still cleared (`*s = None`) and `Lookup::<T>::remove` happens via `lookup.take()`.

`do_cancel_named(None, id)` is exactly the call made by the trait implementation used internally by other pallets (e.g. governance pallets that schedule/cancel named enactments through the `schedule::v3::Named` interface): [3](#0-2) 

Any pallet or code path that cancels a named scheduled call via this trait method (rather than the `cancel_named` extrinsic, which passes `Some(origin.caller())`) will leave a stale `Retries<T>` entry keyed at `(when, index)` in storage forever, and will never call `T::Preimages::drop`, so the call's preimage reference count is never decremented. Existing tests only assert `Lookup` is cleared after this call path (`scheduler_v3_named_cancel_named_works`), not `Retries` or preimage state, so this gap is untested.

Consequences of the orphaned `Retries` entry: if a future, unrelated task later occupies the same `(when, index)` slot (agenda slots are reused/appended as vectors), the stale `RetryConfig` will silently apply to that new, unrelated task the next time `service_task` runs `Retries::<T>::take((when, agenda_index))`, causing unexpected retry-driven rescheduling of a task that was never configured for retries.

The preimage leak means `T::Preimages::drop` is never invoked, so any deposit-locking behavior tied to preimage note/unnote (in `pallet-preimage`) is never released for that call, effectively freezing the depositor's bond indefinitely — a permanent, unprivileged-triggerable resource lock.

### Impact Explanation
This causes exactly the invariant violation cited in the question: `Retries`, `Lookup`, and preimage state desynchronize from `Agenda` after a named-task cancellation performed via the internal `Named::cancel_named` path. The concrete effects are (a) a permanently orphaned `Retries<T>` entry that can spuriously re-arm retries for a later, unrelated task placed at the same `(when, index)`, and (b) a permanently un-dropped preimage reference, freezing the original depositor's storage deposit. Both are silent (no error, no event indicating the leak) and unrecoverable through any public extrinsic, since there is no user-facing way to force-remove a `Retries` entry keyed to a slot that no longer holds the original named task, nor to force `Preimages::drop` on an orphaned reference.

### Likelihood Explanation
This is deterministic, not a true race — FRAME executes agenda servicing and extrinsics sequentially per block, so no true concurrency exists. The bug is triggered every single time `do_cancel_named` is invoked with `origin: None`, which happens on every call through the `schedule::v3::Named::cancel_named` trait implementation. Any pallet that schedules a named call with a retry configured (`set_retry_named`) and later cancels it through this trait method (as opposed to the `cancel_named` extrinsic) will hit this bug deterministically and reproducibly. I was not able to fully trace, within this session's tool budget, which specific unprivileged extrinsics in downstream pallets (e.g. `pallet-referenda`'s permissionless `nudge_referendum`) invoke this trait path in this exact repository snapshot — that call-site verification would require an additional Devin session with full-repo access.

### Recommendation
Move `Retries::<T>::remove((when, index))` and `T::Preimages::drop(&s.call)` outside the `origin`-gated privilege-check block in `do_cancel_named`, mirroring `do_cancel`'s unconditional cleanup, e.g.:
```rust
if let Some(s) = agenda.get_mut(i) {
    if let (Some(ref o), Some(ref s)) = (origin, s.borrow()) {
        Self::ensure_privilege(o, &s.origin)?;
    }
    if let Some(ref s) = s {
        Retries::<T>::remove((when, index));
        T::Preimages::drop(&s.call);
    }
    *s = None;
}
```
so cleanup always happens once a task is actually removed, independent of whether an origin check was requested.

### Proof of Concept
Rust unit test in `substrate/frame/scheduler/src/tests.rs`:
```rust
#[test]
fn cancel_named_via_trait_leaks_retry_and_preimage() {
    use frame_support::traits::schedule::v3::Named;
    new_test_ext().execute_with(|| {
        let call = RuntimeCall::Logger(LoggerCall::log { i: 42, weight: Weight::from_parts(10, 0) });
        let bound = Preimage::bound(call).unwrap();
        let name = [9u8; 32];

        Scheduler::do_schedule_named(name, DispatchTime::At(4), None, 127, root(), bound.clone()).unwrap();
        assert_ok!(Scheduler::set_retry_named(root().into(), name, 5, 1));
        assert_eq!(Retries::<Test>::iter().count(), 1);

        // Cancel via the internal trait path (origin: None), as used by other pallets.
        assert_ok!(<Scheduler as Named<_, _, _>>::cancel_named(name));

        // BUG: Retries entry is orphaned instead of being removed.
        assert_eq!(Retries::<Test>::iter().count(), 0, "Retries entry should be cleaned up but is leaked");
        // BUG: preimage was never dropped -> still available/held.
        assert!(!Preimage::is_requested(&bound.hash().unwrap_or_default()) /* adjust to actual preimage-state check */);
    });
}
```
Expected (current buggy behavior): `Retries::<Test>::iter().count()` remains `1` after cancellation, and the preimage remains held, both assertions fail — proving the desync described.
