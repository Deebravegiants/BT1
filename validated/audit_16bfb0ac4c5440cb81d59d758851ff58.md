Confirmed the finding. The `shop-domain` header is used as the tenant identifier passed to app webhook handlers, but it is never part of the HMAC-signed payload.### Title
Webhook shop-domain header is not covered by HMAC verification, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` verifies webhook authenticity using an HMAC computed only over the raw request body, while the tenant identifier (`shop`) is read from an unauthenticated HTTP header and handed to the host application's webhook handler unchanged.

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Request#shop` is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header with no cryptographic binding to the signature [2](#0-1) .

`Utils::HmacValidator.validate` computes `HMAC(api_secret_key, verifiable_query.to_signable_string)` and compares it to the `hmac` value, but never incorporates the `shop` header into the signed material [3](#0-2) . `Webhooks::Registry.process` only calls this HMAC check before dispatching to the app's handler, and passes `request.shop` straight through as the tenant identifier in `WebhookMetadata` [4](#0-3) . `WebhookMetadata.shop` is the only tenant-context field delivered to `WebhookHandler#handle` [5](#0-4) .

Critically, the HMAC secret (`Context.api_secret_key`, i.e. the app's `client_secret`) is identical for every shop that has installed the app — it is not shop-specific. This breaks the intended binding:
`shop asserted to handler == shop that the signature actually authenticates`
In reality the signature authenticates only the body bytes; the shop field is unauthenticated:
`HMAC-verified bytes (body only) ≠ tenant identity (shop header) trusted by the handler`

Any entity that has installed the app on **their own shop** (an unprivileged, legitimate merchant/tenant of the app — not requiring `api_secret_key` or any privileged credential) receives real, correctly-signed webhooks from Shopify for their own store. Because the signature covers only the body, that same signed body/HMAC pair remains valid regardless of which `shop-domain` header value accompanies it. The attacker can replay the captured body+HMAC to the app's webhook endpoint while substituting a different `shop-domain` header value (e.g., a victim shop they don't own), and `HmacValidator.validate` will still return `true`, and the handler will process the event as if it belongs to the victim shop.

### Impact Explanation
This is a cross-tenant identity binding break reachable by any unprivileged app installer, without needing the app's secret, a token, or social engineering — satisfying the Critical bar for "cross-tenant access." Depending on how the host application's `WebhookHandler#handle` uses `data.shop` (e.g., looking up/mutating per-shop records, triggering `shop/redact`, `customers/redact`, `app/uninstalled` side effects, cache invalidation, or session/data deletion keyed by shop), an attacker can inject fabricated events attributed to another tenant's shop, potentially causing data corruption, unauthorized state changes, or denial of the correct shop's data — all without needing to compromise the target shop or the app's credentials.

### Likelihood Explanation
Likelihood is moderate-to-high: any merchant who has legitimately installed the vulnerable app can obtain a valid signed webhook (their own shop simply receiving normal Shopify webhook traffic), then trivially replay it with a modified header to any endpoint the app exposes for webhook processing. No cryptographic secret needs to be recovered; the attacker only needs to control the header value in the forged HTTP request, which is standard HTTP replay/tampering, well within reach of any unprivileged internet user who is also an app tenant.

### Recommendation
Include the `shop` (and ideally `topic`, `webhook_id`, `api_version`) values in the HMAC-signed material, or otherwise cryptographically bind the shop domain to the payload before it is trusted, so that `to_signable_string` in `lib/shopify_api/webhooks/request.rb` reflects the full set of fields the application will act upon — not just the body. At minimum, document that consuming applications must independently verify `data.shop` against a shop the app has actually installed for/has an active session with, rather than trusting the header as authenticated tenant context.

### Proof of Concept
1. Attacker installs the vulnerable app on `attacker-shop.myshopify.com` and triggers any webhook topic (e.g. `orders/create`), receiving a genuine signed callback: `raw_body = B`, `x-shopify-hmac-sha256 = HMAC(client_secret, B)`, `x-shopify-shop-domain = attacker-shop.myshopify.com`.
2. Attacker resends the exact same `raw_body = B` and same HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new(raw_body: B, headers: {...shop-domain: "victim-shop.myshopify.com"...})` is constructed; `HmacValidator.validate` recomputes `HMAC(client_secret, B)` — unaffected by the header change — and it matches, so validation passes [6](#0-5) .
4. `Registry.process` invokes the app's handler with `WebhookMetadata(shop: "victim-shop.myshopify.com", body: B, ...)`, causing the application to act on data/state for `victim-shop.myshopify.com` even though the request never actually originated from or was signed on behalf of that shop.
