Confirmed: `ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, and the `shop-domain` header used by `#shop` is never included in the HMAC-signed content. This is the exact analog of the reported bug class: a field (`shop`) is acted upon by the consumer (`Registry.process` → `WebhookMetadata.new(shop: request.shop, ...)`) without being covered by the integrity check (HMAC) that is supposed to bind the request to its origin.

### Title
Webhook `shop-domain` identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw JSON body via `Utils::HmacValidator.validate(request)`, then trusts the `shop` value read from the `shopify-shop-domain`/`x-shopify-shop-domain` header to attribute the payload to a tenant. Because the header is never part of the signed material, any request with a valid `(body, hmac)` pair can be replayed with an arbitrary `shop-domain` header and will still pass validation, but be attributed to a different, attacker-chosen shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` is defined as: [1](#0-0) 
which returns only `@raw_body`. The `shop` accessor is derived purely from an unauthenticated header: [2](#0-1) 

`Registry.process` performs the HMAC check and then hands the header-derived `shop` value straight to the app's webhook handler without any further binding to what was actually signed: [3](#0-2) 

Since the HMAC secret (`Context.api_secret_key`) is the app's single shared client secret used for *every* installed shop (not a per-shop secret), any shop that has the app installed can legitimately receive a genuine `(raw_body, hmac)` pair for its own webhook traffic (e.g. by triggering `orders/create`, `shop/update`, `app/uninstalled`, etc. on their own store). That attacker-controlled shop can then replay the exact same `raw_body` and `hmac-sha256` header to the app's webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` only recomputes the signature over `raw_body` — it has no dependency on the `shop` header — so the forged request passes validation, and `Registry.process` invokes the handler with `shop: <victim shop>` carrying attacker-controlled body content.

The identity binding that should hold is:
`hmac == HMAC(api_secret_key, raw_body ‖ shop)` (or equivalent inclusion of `shop` in the signed content)

but the actual implementation only enforces:
`hmac == HMAC(api_secret_key, raw_body)`

leaving `shop` completely outside the authenticated boundary — the same class of gap as the referrer field in the external report being applied post-mint without being bound to the depositor's identity.

### Impact Explanation
This breaks the tenant-authentication boundary that `Registry.process` is meant to provide: an app relying on `WebhookMetadata#shop` to decide which merchant's data/state to update (a documented, expected usage pattern per `docs/usage/webhooks.md`) can be made to process attacker-supplied webhook bodies under a victim shop's identity — e.g. forging `app/uninstalled` or `shop/update` events, or injecting fabricated order/customer data attributed to a shop the attacker does not control. This is a cross-tenant access issue reachable by any shop that has installed the app, without needing the app's `api_secret_key`, an access token, or any privileged account.

### Likelihood Explanation
High. Exploitation only requires the attacker to install the target app on their own store (a normal, unprivileged flow) to obtain valid `(raw_body, hmac)` pairs, then send a single HTTP POST to the app's public webhook endpoint with a rewritten `shop-domain` header. No credential theft, TLS interception, or race condition is required.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the signed content verified against the HMAC, or otherwise cryptographically tie the header-derived tenant identity to the value Shopify actually signed, before it is passed to `WebhookMetadata`. At minimum, cross-check the `shop-domain` header against the shop associated with the currently installed/registered webhook subscription rather than trusting it implicitly.

### Proof of Concept
```ruby
# Attacker owns/installs the app on their-shop.myshopify.com and captures
# a real webhook the app sent for their own store:
captured_body = '{"id":123,"note":"legit order for their-shop"}'
captured_hmac = "<hmac header value Shopify computed over captured_body using the shared api_secret_key>"

# Attacker replays the same body+hmac but swaps the shop-domain header:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => captured_hmac,     # unchanged, still valid
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged tenant
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: captured_body, headers: forged_headers)

# Passes because HmacValidator only checks raw_body, not the shop header:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle(data: WebhookMetadata.new(topic: "orders/create",
#      shop: "victim-shop.myshopify.com", body: parsed(captured_body), ...))
# The app now believes attacker-controlled data belongs to victim-shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
