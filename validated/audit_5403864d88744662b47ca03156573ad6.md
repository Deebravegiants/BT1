### Title
Webhook shop-domain header is not covered by HMAC, allowing cross-tenant shop spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw body only, while the shop identity (`shop-domain` header) that the host application uses to attribute the webhook to a tenant is read from an unauthenticated HTTP header that is never included in the signed bytes. An attacker who owns any Shopify store can receive a legitimate, correctly-signed webhook for their own store and then replay that exact body+HMAC to the victim application's webhook endpoint while substituting an arbitrary `shop-domain` header. The signature check still passes because it never covered the shop field, so the request is processed as if it originated from the spoofed shop.

### Finding Description
`Request#to_signable_string` returns only the raw body: [1](#0-0) 

`shop`, `topic`, and `webhook_id` are parsed straight from attacker-controllable HTTP headers, independent of the signature: [2](#0-1) [3](#0-2) 

`Registry.process` only re-validates the HMAC against the body via `Utils::HmacValidator.validate(request)`, then hands `request.shop` straight to the handler as the trusted tenant identifier: [4](#0-3) 

`HmacValidator.validate_signature` compares the received HMAC against a signature computed over `verifiable_query.to_signable_string`, which — for webhooks — is just the body: [5](#0-4) 

Contrast this with `ShopifyAPI::Auth::Oauth::AuthQuery`, where every security-relevant field (`code`, `host`, `shop`, `state`, `timestamp`) is included in `to_signable_string` and therefore bound by the HMAC: [6](#0-5) 

This is the exact bug class from the report: a field that is acted upon (`request.shop`, used to attribute/process the webhook for a specific tenant) is not covered by the integrity check (the HMAC), so the binding `signed_shop == acted_on_shop` never holds — the acted-on shop is attacker-controlled while the signature only proves body integrity for *some* shop that legitimately sent it (the attacker's own shop).

**Attack sequence (equality broken):**
- Intended binding: `HMAC` proves `(shop, topic, webhook_id, body)` came from Shopify for that shop.
- Actual binding: `HMAC` only proves `body` came from Shopify for *some* shop (whichever originally received it).
- Attacker installs the app on a store they control (`attacker-shop.myshopify.com`), triggers any webhook topic the app subscribes to, and receives a genuinely Shopify-signed request `{headers: {shop-domain: attacker-shop, hmac: H}, body: B}` where `H = HMAC(secret, B)`.
- Attacker resends the same `body: B` and `hmac: H` to the app's webhook endpoint, but sets `shop-domain: victim-shop.myshopify.com`.
- `HmacValidator.validate` recomputes `HMAC(secret, B)` and it still matches `H`, since `shop-domain` was never part of the signed material.
- `Registry.process` looks up the handler by `topic` and invokes it with `WebhookMetadata` where `shop: "victim-shop.myshopify.com"` but `body: B` is attacker-controlled content that was signed for the attacker's own store.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: any application that trusts `request.shop` (or the `shop` field of `WebhookMetadata`) to select the tenant record/session to write into will process the attacker-supplied payload under an arbitrary victim shop identity, without ever needing that shop's credentials. Depending on the webhook topic and how the host app implements handlers (e.g. `orders/create`, `app/uninstalled`, `customers/data_request`, `shop/redact`), this can lead to cross-tenant data corruption, false data deletion/redaction for a shop that never triggered it, or injection of attacker-chosen data into another merchant's records — a cross-tenant access impact.

### Likelihood Explanation
Exploitation requires only an unprivileged internet user who can install the target app on any store (including a free/dev store they control) to receive one legitimately signed webhook, then replay it with a modified header to the same endpoint. No access token, `client_secret`, or privileged account is needed — only observation of one legitimate webhook delivery, which is trivially available to any app installer.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the signed material, or otherwise independently verify that the `shop-domain` header corresponds to the shop that Shopify actually signed the request for (e.g., include shop in `to_signable_string`, or require the host app to compare `request.shop` against the shop associated with the session/subscription that the webhook was registered under, not solely trust the header).

### Proof of Concept
1. Install the app on `attacker-shop.myshopify.com`; subscribe to any webhook topic.
2. Capture the resulting POST from Shopify: headers include `x-shopify-hmac-sha256: H`, `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-topic: T`, raw body `B`.
3. Send a new request to the same webhook endpoint with the identical `B` and `H`, but `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks `HMAC(secret, B) == H`: [4](#0-3) 
5. The handler executes with `shop: "victim-shop.myshopify.com"`, processing attacker-controlled body content attributed to the victim shop.
