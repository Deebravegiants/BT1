### Title
Webhook `shop` domain used for tenant routing is not covered by the HMAC signature - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw HTTP body, while `ShopifyAPI::Webhooks::Request#shop` (the value handed to application handlers as the tenant identifier) is read straight from the `shopify-shop-domain`/`x-shopify-shop-domain` header, which is never included in the HMAC-verified bytes. `Registry.process` validates the HMAC and then immediately forwards the unauthenticated `request.shop` value into the handler as the trusted tenant identity.

### Finding Description
`Utils::HmacValidator.validate` in [1](#0-0)  computes the signature over whatever `to_signable_string` returns for the `VerifiableQuery`. For webhooks, that method is: [2](#0-1) 

i.e. only `@raw_body` is bound by the signature. The `shop` accessor, however, is derived independently from a header: [3](#0-2) 

`Registry.process` verifies the HMAC and then constructs `WebhookMetadata` using `request.shop` as the authoritative tenant identity for the handler, without any additional check that this header value is consistent with anything actually covered by the signature: [4](#0-3) [5](#0-4) 

This is the same class of bug as the report: a field that is *acted on* (`shop`, used to route/attribute the payload to a tenant) is not part of the bytes that are cryptographically bound (`raw_body`). The identity binding that should hold is:
`HMAC-covered bytes == bytes that determine the tenant/session used by the handler`
but here `to_signable_string() (raw body only) != shop header (tenant identity)`.

### Impact Explanation
Because the header is excluded from the signed bytes, any request whose `raw_body` + `hmac` pair is valid for *some* shop can be replayed with the `shopify-shop-domain` header rewritten to a different shop domain, and `Registry.process` will still accept it (HMAC check only validates the body) and dispatch it to the handler tagged with the attacker-chosen `shop`. Any host application that uses `WebhookMetadata#shop` to look up the tenant/session (which is exactly what the library encourages, since it is the only shop value exposed by `Request`) will process attacker-controlled webhook content under a victim shop's identity — a cross-tenant integrity break.

### Likelihood Explanation
An attacker needs one valid `(raw_body, hmac)` pair, which they can obtain by triggering any real webhook event on a shop they control (e.g., installing the app on a free/dev store and generating an `orders/create` event), then replaying that exact body/HMAC to the app's webhook endpoint with the `shopify-shop-domain` header swapped for a victim shop. No secrets, tokens, or privileged access are required — only the ability to send an HTTP POST to the app's public webhook endpoint, which by design is unauthenticated apart from the HMAC.

### Recommendation
Bind the `shop` (and ideally `topic`, `webhook_id`, `api_version`) header values into the signed payload used for verification, or independently re-validate that `shop` corresponds to a shop with an active, known installation/session before dispatching to the handler. At minimum, document and enforce that `WebhookMetadata#shop` must be cross-checked against the app's own session store keyed by a value that is otherwise authenticated, rather than trusted directly from the header.

### Proof of Concept
1. Install the app on an attacker-controlled shop `attacker.myshopify.com` and let it deliver a legitimate webhook, capturing `raw_body` and the resulting `shopify-hmac-sha256` header (valid because it is computed only over the body with the app's real secret).
2. Replay the exact same `raw_body` and `hmac` to the app's webhook endpoint, but set `shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `raw_body` against `hmac` — this passes.
4. The handler receives `WebhookMetadata.new(..., shop: "victim.myshopify.com", body: <attacker's captured payload>, ...)`, and any host logic keyed on `data.shop` processes attacker-supplied data as if it came from the victim shop.
