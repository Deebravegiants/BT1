### Title
Webhook shop-domain header is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates a webhook by validating an HMAC that is computed over the raw request body only, but it then trusts the `shop-domain` header (exposed as `request.shop`) — which is completely outside the HMAC's coverage — as the tenant identity passed to the app's handler. Any party that can obtain one valid `(body, hmac)` pair signed with the app's own `client_secret` (e.g. by installing the app on their own store and receiving a legitimate webhook) can replay that exact body/HMAC pair to the app's public webhook endpoint while substituting an arbitrary `shop-domain` header, and the request still passes HMAC validation.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`ShopifyAPI::Utils::HmacValidator.validate` computes the HMAC exclusively over `verifiable_query.to_signable_string`, i.e. only the body for webhooks: [2](#0-1) 

`request.shop` is read directly from the (unauthenticated, HMAC-uncovered) `shop-domain` header: [3](#0-2) 

`Registry.process` validates the HMAC and then immediately forwards `request.shop` to the app's handler as the trusted tenant identity, with no cross-check that this shop is the one that actually produced the signed body: [4](#0-3) 

The resulting `WebhookMetadata.shop` is documented and expected to be used by host apps as "The shop domain of the webhook" for tenant-scoped processing: [5](#0-4) [6](#0-5) 

**Equality that is broken:** the gem implicitly asserts `hmac_valid(body) == true ⟺ shop_header_is_authentic`, but the HMAC signature only certifies `hmac_valid(body, secret) == true`; it says nothing about which shop the body actually originated from. Since a single app-level `client_secret` (`Context.api_secret_key`) is shared across every shop that installs the app, any shop that installs the app is handed valid `(body, hmac)` pairs for its own genuine events. Because the header is unauthenticated, that same attacker-controlled shop can:
1. Install the target app on its own store (or otherwise legitimately receive a webhook from Shopify for its own store), capturing a raw body and its valid `x-shopify-hmac-sha256` value.
2. Replay that exact `(raw_body, hmac)` pair to the app's public webhook endpoint, but change the `x-shopify-shop-domain` header to a victim shop that also uses the app.
3. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the shared secret — the header is never part of the signed data.
4. The app's handler receives `WebhookMetadata.new(shop: "<victim-shop>.myshopify.com", body: <attacker's own event body>, ...)` and, following the documented usage pattern, performs shop-scoped actions (writing/queuing data, updating records, invoking Admin API calls for that shop) using body content the attacker fully controls but attributed to another tenant.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for webhook processing: it lets an unprivileged holder of any valid app installation forge webhook events attributed to a different merchant's shop, causing the host application to act on/for a shop the attacker doesn't control, using attacker-chosen body content. This is a cross-tenant access primitive delivered entirely by an unprivileged internet-reachable request to the app's own webhook callback route, requiring no access token, no `client_secret`, and no privileged account — only a normal app installation on the attacker's own store to harvest one valid signed body.

### Likelihood Explanation
High for apps built on this gem's documented pattern: any app that installs across multiple merchants and relies on `WebhookMetadata.shop` (as shown in `docs/usage/webhooks.md`) for tenant-scoped side effects is exposed. The attack requires no secrets beyond what an ordinary merchant installing the app already receives (their own legitimate webhook traffic), and the webhook endpoint is by design internet-facing and unauthenticated aside from the HMAC.

### Recommendation
Include the header fields that establish tenant identity (`shop-domain`, and ideally `topic`, `webhook-id`, `api-version`) in the HMAC-signed material, or otherwise cryptographically bind the shop to the payload before trusting it (e.g., verify `request.shop` against the shop of the session/registration that the webhook was registered for, rather than trusting the raw header value once the body HMAC passes).

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` and receives a legitimate webhook `orders/create` POST with raw body `B` and valid header `x-shopify-hmac-sha256: H` (both computed by Shopify using the app's shared `client_secret`).
2. Attacker sends a new HTTP POST to the app's public webhook route with:
   - Body: `B` (unchanged)
   - Header `x-shopify-hmac-sha256: H` (unchanged)
   - Header `x-shopify-shop-domain: victim-shop.myshopify.com` (changed)
   - Header `x-shopify-topic: orders/create` (unchanged)
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which computes `HMAC(client_secret, B)` and compares it to `H` — this matches, so validation succeeds (per `lib/shopify_api/webhooks/request.rb:35-38` and `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. The app's registered handler is invoked with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", body: <attacker-controlled JSON from B>, ...)`, causing the host application to process attacker-controlled data under the victim shop's tenant context.
