Based on my investigation, the strongest analog is the operator QR-code re-authorization window in `src/plans/mod.rs`, where a previously validated operator's authorization is cached client-side (`OperatorData.timestamp`) and reused for subsequent signups purely based on an elapsed-time check, without re-querying the backend for the operator's current validity.

### Title
Stale cached operator authorization reused for signup approval within expiration window - (File: src/plans/mod.rs)

### Summary
`scan_remaining_qr_codes` and `scan_initial_qr_codes` reuse a previously validated `OperatorData` (containing the operator's validity/location data returned by `verify_operator_qr_code`) for any subsequent signup as long as `operator_data.timestamp.elapsed() < operator_qr_expiration_time` [1](#0-0) , with `operator_qr_expiration_time` defaulting to 23 hours [2](#0-1) . This mirrors the reported bug class: a security-relevant decision (operator authorization) is made from a locally cached snapshot of remote state whose accuracy decays with time, rather than being revalidated against the source of truth at the moment of use.

### Finding Description
`verify_operator_qr_code` performs a one-time backend check of operator validity (via `backend::operator_status::request`, which returns `Status.valid` and location data) [3](#0-2) . The result is stored as `OperatorData { qr_code, location_data, timestamp: Instant::now() }` [4](#0-3) . For every subsequent signup within the configured expiration window, the code branches purely on local elapsed time without re-checking backend validity: [5](#0-4) 

The same pattern appears in `scan_initial_qr_codes` for self-serve mode [6](#0-5) . This is structurally identical to the reported issue: a decision that should reflect current remote state (operator validity/permission) is instead derived from a cached value whose staleness is bounded only by a timer, not by actual confirmation from the backend.

### Impact Explanation
If an operator's authorization is revoked on the backend (e.g., due to detected fraud, policy violation, or account suspension) after the initial QR validation, the Orb will continue to accept that operator's cached authorization and allow them to run signups for up to the full expiration window (23 hours by default) without any backend re-check. This allows an operator who has just been de-authorized to continue authorizing signups — a misattributed/unauthorized-signup class impact, since signups are tied to an operator identity that the backend no longer considers valid.

### Likelihood Explanation
Likelihood is dependent on the window between backend revocation and cache expiration, and requires an operator who was valid at scan time to become invalid before the 23-hour cache expires — a plausible but not attacker-controlled scenario (this is an operational/trust-boundary gap rather than something a remote unprivileged attacker can directly trigger).

### Recommendation
Reduce reliance on purely time-based cache validity for security-relevant operator authorization; consider re-validating operator status against the backend at each signup (or more frequently) rather than only checking `operator_data.timestamp.elapsed() < operator_qr_expiration_time`, especially for signups that occur later within the caching window.

### Proof of Concept
1. Operator scans their QR code; `verify_operator_qr_code` succeeds and `OperatorData.timestamp` is set to `Instant::now()`.
2. Backend later revokes/invalidates that operator's status (e.g., fraud detected).
3. Within `operator_qr_expiration_time` (up to 23h), the Orb still satisfies `operator_data.timestamp.elapsed() < operator_qr_expiration_time` in `scan_remaining_qr_codes`, so it proceeds directly to `scan_user_qr_code` without re-invoking `verify_operator_qr_code`/`backend::operator_status::request`, allowing further signups under the now-invalid operator's authorization [7](#0-6) .
