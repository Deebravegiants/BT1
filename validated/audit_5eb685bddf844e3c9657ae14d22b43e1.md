### Title
Emporium Min-proof path lets an unprivileged caller run unaccounted arbitrary calls (e.g. `approve()`) from Emporium's identity - (File: contracts/CircomDataBuilder.sol, contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol)

### Summary
When `externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, `formInputForCircom` routes to `formInputEmporiumMin`, which only proves `message == Poseidon(messageSeed)` plus `timeStamp`/`calldataHash` binding — no root, no nullifiers, no amount accounting. `EmporiumUpgradeable.runAction` then executes attacker-supplied `EmporiumStack.ops` with `signerAddress == address(0)` (skipping EIP-712 signature verification) directly as `op.endpoint.call{value: op.value}(op.callData)`, while every balance-accounting loop (in both `EmporiumUpgradeable.runAction` and `Hinkal.transact`) iterates the empty `erc20TokenAddresses` array and therefore checks nothing.

### Finding Description
The invariant that should hold is: **assets/permissions Emporium's identity can grant or move in a transaction == assets accounted for in `balancesBefore`/`balancesAfter` (and in Hinkal's `balanceDif`/`amountChanges` equality)**. This is broken.

- `formInputForCircom` selects the minimal circuit whenever `erc20TokenAddresses.length == 0` for the Emporium action: [1](#0-0) 
- `formInputEmporiumMin` produces only 3 public signals: `emporiumMessage`, `timeStamp`, `calldataHash` — no `rootHashHinkal`, no `signedMessageHash`, no nullifiers/commitments, no `amountChanges`: [2](#0-1) 
- The corresponding circuit, `MainEVMCircuitMin`, only constrains `message <== Poseidon(1)([messageSeed])` and passes `outTimeStamp`/`calldataHash` straight through — it performs no Merkle-root check, no nullifier/signature verification, and places zero constraints on `externalActionMetadata`: [3](#0-2) 
- `Hinkal.transact` still calls `rootHashExists(circomData.rootHashHinkal, ...)`, but since no UTXOs are spent or created in this path, any historical (even stale) root satisfies this check trivially — it is unconstrained by the proof and irrelevant to the exploit: [4](#0-3) 
- Because `circomData.erc20TokenAddresses.length == 0`, the balance-accounting loop in `Hinkal.transact` that enforces `balanceDif == amountChanges + utxoAmount` never executes: [5](#0-4) 
- `EmporiumUpgradeable.runAction` decodes attacker-controlled `EmporiumStack` from `externalActionMetadata`, computes `balancesBefore`/`balancesAfter` over the same empty `erc20TokenAddresses` array (both empty, so the "accounted assets" side of the equality is always zero), calls `verifyWallet` (which, for `signerAddress == address(0)`, returns immediately without any signature check), then executes every op via `op.endpoint.call{value: op.value}(op.callData)`: [6](#0-5) [7](#0-6) 
- The only gate on `runAction` is `onlyAllowedRecipient`, which checks `msg.sender == Hinkal` — it does not restrict `op.endpoint` or require `signerAddress != 0`: [8](#0-7) 

**Attacker's exact call**: Any EOA calls `Hinkal.transact(a, b, c, dimensions, circomData)` where:
- `circomData.externalActionData.externalActionId == HINKAL_EMPORIUM_ACTION_ID`
- `circomData.erc20TokenAddresses == []` (empty)
- `circomData.externalActionData.externalActionMetadata = abi.encode(EmporiumStack({signerAddress: address(0), ops: [EmporiumOperation({endpoint: someToken, invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.approve, (attacker, type(uint256).max))})], ...}))`
- `a,b,c` is a valid Groth16 proof for `MainEVMCircuitMin`, self-generated by the attacker for their own chosen `messageSeed`, satisfying `message = Poseidon(messageSeed)` and matching `calldataHash = keccak(...)` computed over their crafted `circomData` (this hash-binding is checked in `performHinkalChecks`, but it does not constrain the *content* of `externalActionMetadata` to anything safe — it merely pins the calldata attacker already chose).

**Exploit flow**: The call passes `performHinkalChecks` (calldata hash matches by construction), `verifyProof` (a real, locally generated Groth16 proof for the trivial Min circuit), and `rootHashExists` (any valid historical root works since no UTXOs are touched). `EmporiumUpgradeable.runAction` then calls `IERC20(token).approve(attacker, type(uint256).max)` directly from Emporium's own address (`msg.sender` inside `op.endpoint.call` is the Emporium contract), granting the attacker unlimited allowance over any ERC20 balance Emporium currently holds. Since `erc20TokenAddresses` is empty, this allowance grant is invisible to every balance-based safety check on both the Emporium and Hinkal sides. In a follow-up transaction, the attacker calls `token.transferFrom(Emporium, attacker, balance)` to drain the tokens.

Why guards fail: `dimensionsCheck`, `checkOnchainCreation`, and `insertNullifiers`/`insertCommitments` operate on `inputNullifiers`/`outCommitments`/`onChainCreation`, all empty here and thus impose no constraint. `verifyProof` succeeds because the Min circuit genuinely has almost no constraints. `rootHashExists` succeeds trivially with a stale/arbitrary valid root because it is decoupled from any inclusion check in this path.

### Impact Explanation
An unprivileged attacker can force the Emporium contract to execute an arbitrary external call (e.g., `approve()`, or any other state-changing call to any contract) from Emporium's own address, with zero balance accounting and zero signature/authorization requirement (via `signerAddress == address(0)`). This directly allows theft of any ERC20 tokens (or ETH, via arbitrary `op.value`/`callData`) currently held by the Emporium contract — matching Critical: "direct theft of shielded or in-flight user funds." The attack is repeatable for any funds Emporium holds at any time (e.g., mid-flight funds temporarily routed through Emporium in other users' transactions, or funds intentionally parked there).

### Likelihood Explanation
- No privileged role is required; the attacker only needs to generate a proof for the trivial `MainEVMCircuitMin` circuit locally, which requires no knowledge of any UTXO, root, or other user's secret.
- Precondition: Emporium must hold some token/ETH balance at the time of attack (e.g., from another in-flight user transaction, prooflessDeposit routing, or leftover dust) — the exact window is attacker-uncontrolled but the `approve()` can be front-run/queued to fire whenever Emporium holds a target balance, and the drain step (`transferFrom`) can be executed at any later time since the allowance persists.
- Attacker cost is a single proof generation and one transaction; fully repeatable.

### Recommendation
Do not allow the Emporium Min-proof path to execute arbitrary `ops` calls with `signerAddress == address(0)` when `erc20TokenAddresses.length == 0`. Either (a) require `erc20TokenAddresses` to be non-empty (and their balances actually accounted) whenever `ops` contains calls capable of moving/approving value, (b) bind the circuit's public inputs to a hash of `externalActionMetadata` and the full token/amount vectors even in the Min case so no accounting is skippable, or (c) disallow `signerAddress == address(0)` entirely for stateless ops that touch arbitrary endpoints, restricting the Min path strictly to actions with no side effects on Emporium-custodied assets.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable` (as allowed recipient), and a mock ERC20 `TOKEN`.
2. Fund Emporium with `TOKEN.mint(emporium, 1000e18)` to simulate in-flight/parked balance.
3. As attacker EOA, build `CircomData` with `externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `externalActionMetadata = abi.encode(EmporiumStack{signerAddress:0, ops:[{endpoint: address(TOKEN), invokeWallet:false, value:0, callData: abi.encodeCall(IERC20.approve, (attacker, type(uint256).max))}]})`.
4. Generate a valid Groth16 proof for `MainEVMCircuitMin` locally with attacker-chosen `messageSeed`; compute `calldataHash` per `getHashedCalldata`.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from attacker.
6. Assert: `TOKEN.allowance(emporium, attacker) == type(uint256).max` (LHS: allowance granted; RHS should have been 0 — equality "assets accounted == assets moved" is broken since no `erc20TokenAddresses` entries exist to represent this token).
7. Call `TOKEN.transferFrom(emporium, attacker, 1000e18)` and assert attacker's balance increased by `1000e18` while Emporium's dropped to 0, with no `require` in `Hinkal.transact` or `EmporiumUpgradeable.runAction` ever reverting.
