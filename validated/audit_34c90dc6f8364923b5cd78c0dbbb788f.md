### Title
Missing enforcement of swap output slippage floor allows theft of shielded funds via unauthorised amount reduction - (File: `contracts/external-actions/swaps/ExternalActionSwap.sol`)

### Summary
`ExternalActionSwap.swap()` requires that a user-supplied minimum-output value (`circomData.slippageValues[1]`) is merely *non-zero*, but never checks that the actual amount returned by the router (`swappedAmount`) is greater than or equal to that value. The proof-bound `slippageValues` field is therefore decorative: it is committed into `calldataHash` / the public-input vector but has no effect on execution, so the output UTXO can be created with an arbitrarily smaller amount than the depositor authorised when generating the proof.

### Finding Description
The `swap` function performs: [1](#0-0) 

Only `circomData.slippageValues[1] != 0` is asserted — a trivially satisfiable condition (any relay/user can set it to `1`) — before calling `callRouter` and using whatever `swappedAmount` the router returns to build the resulting UTXO: [2](#0-1) 

There is no `require(swappedAmount >= uint256(circomData.slippageValues[1]), ...)`. Elsewhere in the codebase, `slippageValues` is validated only for array length via `dimensionsCheck` in `HinkalHelper.sol`: [3](#0-2) 

and it is bound into the calldata hash that the ZK proof commits to via `CircomDataBuilder`, but the on-chain code never enforces the semantic meaning of the field (a minimum acceptable output). Consequently, the amount actually credited into the user's shielded balance (`utxoSet[0].amount`) can be far lower than what the depositor authorised at proof-generation time, with no on-chain check to prevent it. Since `_externalTransact` in `Hinkal.sol` only verifies that the balance equation matches whatever amount was actually produced by the external action (real funds moved = committed UTXO amount), the balance equation itself is internally consistent — the bug is that the *amount* it commits to can be silently worse than authorised, because the floor the user set is never checked.

### Impact Explanation
This is functionally identical in class to the referenced Taiko report: a value (fee/amount) computed at execution time, potentially manipulated or degraded by conditions outside the depositor's control (front-running/sandwiching of the router call, or a malicious/compromised relay providing manipulated router metadata), is applied to the user's funds without the slippage protection the user explicitly encoded and proved for. This allows a relay or MEV actor to extract almost all of the swap output before it reaches the depositor's shielded balance — direct theft of in-flight (shielded) user funds, matching the Critical impact category ("direct theft of shielded or in-flight user funds").

### Likelihood Explanation
Likelihood is high: any relay executing `runAction`/`swap` can either pass adversarial `externalActionMetadata` to the router, or simply allow (or perform) a sandwich attack on the public router call, and the contract has no mechanism to detect or reject an output amount lower than the user intended. No special privileges beyond being a registered relay (already part of the normal transaction flow) are required.

### Recommendation
Enforce the floor in `ExternalActionSwap.swap()`:
```solidity
require(
    swappedAmount >= uint256(circomData.slippageValues[1]),
    "swap output below slippage floor"
);
```
placed after `callRouter` returns, so the transaction reverts (rather than silently crediting a diminished UTXO) whenever the router output falls below the user-authorised minimum.

### Proof of Concept
1. A user builds a proof/`circomData` for a swap with `slippageValues[1] = X` (intended minimum output).
2. The transaction is relayed. Before/while the relay calls `runAction` → `swap` → `callRouter`, the router trade is sandwiched (or the relay supplies unfavorable router calldata), so the router returns `swappedAmount << X`.
3. `swap()` only checked `slippageValues[1] != 0` beforehand; it does not compare `swappedAmount` to `X`, so execution proceeds.
4. `amountToSendToHinkal = swappedAmount - totalFee` is transferred and committed as the user's new shielded UTXO, which is materially less than the amount the user authorized/expected when constructing the proof, resulting in a loss of shielded value to MEV/relay extraction. [4](#0-3)
