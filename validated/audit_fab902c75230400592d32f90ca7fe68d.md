Audit Report

## Title
Vault gateway handler logs the full JSON-RPC request/response, including caller-supplied JWT auth tokens, into node logs at Debug/Info level - ([File: core/capabilities/vault/gw_handler.go])

## Summary
`GatewayHandler.HandleGatewayMessage` logs the entire incoming `jsonrpc.Request[json.RawMessage]` struct at Debug level and the outgoing response at Info level, without redacting the request's `Auth` field, which carries the caller's raw bearer/JWT token used by `jwtBasedAuth.AuthorizeRequest` to authenticate vault operations. This is inconsistent with the rest of the authorization pipeline (`authorizer.go`, `jwt_based_auth.go`), which deliberately logs only `"hasAuth", req.Auth != ""` rather than the raw token, confirming the codebase treats `Auth` as sensitive and this call site is an outlier that leaks it into the log sink.

## Finding Description
`jsonrpc.Request[T]` (from `chainlink-common/pkg/jsonrpc2`) has an exported `Auth` field populated by callers with their JWT, as shown across the codebase (e.g. `req.Auth = token` in `system-tests/lib/cre/vault/jwt_auth_test.go:70`, `req.Auth = mustMintVaultJWTForRequest(...)` in `system-tests/tests/smoke/cre/vault_don_test_helpers.go:417`, and consumed via `req.Auth` in `jwt_based_auth.go:189`). `AuthorizeRequest` uses `req.Auth` to validate the token and derive workflow/org identity [1](#0-0) .

Confirmed by direct inspection of `gw_handler.go`, `HandleGatewayMessage` logs the whole request struct via `reqLggr.Debugw("received message from gateway", "req", req)` [2](#0-1) , and later logs the whole response struct via `reqLggr.Infow("Sent message to gateway", "resp", response)` unconditionally on every successfully processed gateway message [3](#0-2) . No `String()`/`MarshalLogObject` override was found for `jsonrpc.Request`/`Response` types in this repository (search for these methods returned no matches), so structured/reflective zap logging will serialize the struct including its exported `Auth` field.

In sharp contrast, the authorization code that also handles `req.Auth` in the very same request flow explicitly avoids logging the raw value, instead logging only a boolean presence flag: `"hasAuth", req.Auth != ""` in `authorizer.go` [4](#0-3) . This demonstrates the project's own security discipline for this exact field, which `gw_handler.go`'s wholesale struct logging bypasses.

Test infrastructure independently corroborates that `Auth` is treated as sensitive on the wire: `outboundRequestWithoutAuth` strips `req.Auth` before marshaling to send over HTTP and instead sets it as an `Authorization: Bearer` header [5](#0-4) , and `sendVaultSignedOCRRequestToGateway` does the same [6](#0-5) . However, this stripping happens only on the client/test-helper side for the outbound wire payload — it does not touch the in-process `*jsonrpc.Request[json.RawMessage]` struct that `HandleGatewayMessage` receives and logs on the node side, so the node-side Debug log line is unaffected by this precaution.

## Impact Explanation
The `Auth` field is the caller's JWT bearer token authorizing vault secret create/update/delete/list operations for a specific workflow owner. Anyone with read access to the node's log output (`log.jsonl`, or any downstream log aggregation/shipping pipeline) can recover a still-valid JWT for a vault client and use it to impersonate that caller's identity within the token's validity window (subject to the digest-binding/replay-guard checks in `authorizer.go` and `jwt_based_auth.go`), or at minimum learn caller identity/authorization metadata that should remain confidential. This is a credential-disclosure-via-logging issue, which is a recognized bug class (mirroring CVE-2023-22447-style log-insertion issues), and it maps to an in-scope "key/secret exfiltration" impact category since the leaked value is a live authentication credential for vault operations, not merely non-sensitive metadata (which SECURITY.md explicitly excludes, e.g., "Server-side non-confidential information disclosure").

## Likelihood Explanation
Exploitation requires only ordinary, supported operation of the vault gateway handler: any legitimate vault client request will pass through `HandleGatewayMessage`, triggering the Debug log line whenever `Log.Level` is set to `debug` (a documented, standard node configuration), and the Info-level "Sent message to gateway" log line is emitted unconditionally on every successful request regardless of log level configuration. This means disclosure isn't a rare edge case but occurs under normal operation once an actor with any form of log access (local host access, log-shipping pipeline access) is in the picture — which the report itself frames as "privileged local/host access to the log sink," a precondition that is weaker than requiring node-operator or admin-role access to the vault system itself, since it only needs log-file/log-pipeline read access, not credentials to the vault API.

## Recommendation
- In `GatewayHandler.HandleGatewayMessage` (`core/capabilities/vault/gw_handler.go`), replace `Debugw("received message from gateway", "req", req)` and `Infow("Sent message to gateway", "resp", response)` with logging of only non-sensitive fields (method, requestID, gatewayID, `"hasAuth", req.Auth != ""`), consistent with the pattern already used in `authorizer.go`.
- Add a `MarshalLogObject`/`String()` redacting implementation on the shared `jsonrpc.Request`/`Response` types (or a wrapper type) in `chainlink-common/pkg/jsonrpc2` so future call sites cannot leak `Auth` by default via reflective struct logging.
- Add a regression test analogous to `TestVaultHandler_InvalidParamsDoesNotLogRawParams` that asserts no log entry emitted by `gw_handler.go` contains a raw JWT/`Auth` value.

## Proof of Concept
1. Configure a chainlink node running the vault capability's gateway connector with `Log.Level = 'debug'`.
2. As an unprivileged vault client, send a JSON-RPC vault request (e.g. `vault.secrets.list`) through the gateway with a valid JWT set in the `Auth` field of the in-process request struct that reaches `HandleGatewayMessage` on the node.
3. Inspect the node's structured log output: the `Debugw("received message from gateway", "req", req)` call at `core/capabilities/vault/gw_handler.go:182` will serialize `req`, including its `Auth` field containing the plaintext JWT, into the log record; the `Infow("Sent message to gateway", "resp", response)` call at line 231 is emitted on every successful request regardless of log level.
4. A Go unit test can assert this directly: construct a `*jsonrpc.Request[json.RawMessage]{Auth: "test-jwt-marker", ...}`, invoke `HandleGatewayMessage` with an observed test logger (`logger.TestObserved`), and assert that the log entries' `ContextMap()["req"]` (or its JSON-serialized form) contains the marker string — mirroring the structure of `TestVaultHandler_InvalidParamsDoesNotLogRawParams` in `core/services/gateway/handlers/vault/handler_test.go:1016-1058`, but targeting the `gw_handler.go` Debug/Info log lines instead.
