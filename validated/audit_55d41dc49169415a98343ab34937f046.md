This confirms the vulnerability: `ShopifyAPI::Webhooks::Registry.process` explicitly documents "This will verify the request did indeed come from Shopify" [1](#0-0)  and the handler is told `shop` is "the shop domain of the webhook" [2](#0-1) , i.e. the library's own contract treats `shop` as an authenticated field, when in fact only the raw body is HMAC-covered.

### Title
Webhook `shop-domain` header is trusted for tenant attribution but is not covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb, lib/shopify_api/webhooks/registry.rb, lib/shopify_api/utils/hmac_validator.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC over the raw request body, then unconditionally trusts the `shop-domain` (and `topic`, `webhook-id`, `api-version`) headers taken from the same request to build the `WebhookMetadata` passed to the app's handler. Because the signature never binds these headers, an attacker who can obtain one valid `(body, hmac)` pair for their own shop can replay that exact body/HMAC to the app's public webhook endpoint while substituting a different `shop-domain` header, causing the handler to process attacker-controlled data under a victim shop's identity.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate`/`validate_signature` compute and compare the HMAC exclusively against `verifiable_query.to_signable_string` [4](#0-3) . The `shop`, `topic`, `webhook_id`, and `api_version` accessors all read directly from unauthenticated HTTP headers [5](#0-4) .

`Registry.process` only checks `Utils::HmacValidator.validate(request)` before dispatching to the handler, then builds `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., with no separate check that the shop is the one the signature was actually produced for: [6](#0-5) .

The identity binding that is broken is:
`HMAC-verified(raw_body)` ⇏ `shop header used for tenant attribution == shop the signature was computed for`

Since the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is shared across all shops that install the app, any shop that installs the app can generate a legitimately-signed `(raw_body, hmac)` pair for itself (e.g. by triggering any webhook topic on its own store, or one it controls as a developer/partner test store), then resend that untouched body and HMAC to the app's public webhook endpoint with the `shop-domain` header (and optionally `topic`) rewritten to name a different, victim shop. `HmacValidator.validate` still succeeds because it never inspects the headers, so `Registry.process` will invoke the app's handler with `data.shop` equal to the victim's domain and `data.body` equal to attacker-chosen content.

This is a concrete violation of the equality the library's own documentation promises: processing "will verify the request did indeed come from Shopify" [1](#0-0)  and hands the handler a trustworthy `shop` field described as "the shop domain of the webhook" [7](#0-6) . In reality, only body authenticity is proven; shop attribution is not.

### Impact Explanation
Any application that uses `data.shop` from `WebhookMetadata` (exactly as the gem's own documented usage pattern does, e.g. `perform_later(topic: data.topic, shop_domain: data.shop, ...)` [8](#0-7) ) to key merchant-record updates will process attacker-controlled webhook content under an arbitrary victim shop's identity. This is a cross-tenant data-integrity/confusion issue: an unprivileged installer of the app can inject fabricated "events" attributed to any other merchant using the same app, with no need for the victim's or the app's real secrets — only their own valid signed body. This satisfies the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Likelihood is high for any app that (a) exposes a public HTTP endpoint for webhook processing (the documented pattern) and (b) is installed by more than one shop (any multi-tenant app). The attacker needs only to be a legitimate, unprivileged installer of the app on their own store (or use a free/partner development store) to obtain a validly-signed body/HMAC pair, then replay it with a modified header — no access to `api_secret_key`, access tokens, or the victim's credentials is required.

### Recommendation
Include the trust-relevant headers (`shop-domain`, `topic`, `webhook-id`, `api-version`) in the HMAC-covered signable string, or otherwise cryptographically bind the shop attribution to the signed payload, so that the shop asserted by `WebhookMetadata` cannot diverge from the shop for which the HMAC was actually computed. At minimum, document and/or enforce that `data.shop` must be cross-checked against a shop known to be currently installed/authorized for this app before use, since the gem currently provides no such binding itself.

### Proof of Concept
1. App is installed by both `attacker.myshopify.com` and `victim.myshopify.com`.
2. Attacker triggers a webhook topic on their own shop, capturing the exact `raw_body` Shopify sends and the accompanying `x-shopify-hmac-sha256` header — this HMAC is valid because it was legitimately computed by Shopify using the shared `api_secret_key`.
3. Attacker POSTs the same `raw_body` to the app's public webhook endpoint but sets `x-shopify-shop-domain: victim.myshopify.com` (and optionally a different `x-shopify-topic`) while keeping the original `x-shopify-hmac-sha256`.
4. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [9](#0-8) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unmodified) body against the (unmodified) HMAC [10](#0-9) .
5. The handler is invoked with `WebhookMetadata.new(topic: ..., shop: "victim.myshopify.com", body: attacker_controlled_body, ...)` [11](#0-10) , causing the app to act on attacker-chosen data as if it originated from the victim's shop.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
