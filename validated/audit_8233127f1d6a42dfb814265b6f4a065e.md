Audit Report

## Title
Silent `Workplan` update failure in `do_assign` (and `do_pool`) desynchronizes `Regions`/`Workplan` state - (File: substrate/frame/broker/src/dispatchable_impls.rs)

## Summary
`do_assign` calls `Self::utilize(...)`, which unconditionally removes the `Region` from `Regions` for `Finality::Final`, and then attempts `workplan.try_push(...)` into the bounded `Workplan` schedule, only writing back to storage `if ... .is_ok()`. If `try_push` fails because the bounded vector for that `(begin, core)` key is full, the function takes no error path: it still runs the `PotentialRenewals` bookkeeping and unconditionally emits `Event::Assigned`, then returns `Ok(())`. The identical unguarded pattern exists in `do_pool`.

## Finding Description
The code exactly matches what is claimed. `do_assign` in [1](#0-0)  retrieves the workplan, retains non-overlapping items, and does:
```rust
if workplan.try_push(...).is_ok() {
    Workplan::<T>::insert(&workplan_key, &workplan);
}
```
with no `else` branch and no error propagated. `Self::utilize` in [2](#0-1)  unconditionally calls `Regions::<T>::remove(&region_id)` and only reinserts the region if `finality == Finality::Provisional`, meaning for `Finality::Final` the region is gone regardless of whether the subsequent `Workplan` write succeeds. The `PotentialRenewals` update at [3](#0-2)  and the `Event::Assigned` emission at [4](#0-3)  both execute unconditionally, independent of the `try_push` outcome. `do_pool` has the identical unguarded pattern at [5](#0-4) . No `ensure!`/error return anywhere in `do_assign` catches a `try_push` failure, and the function's signature (`Result<(), Error<T>>`) always resolves to `Ok(())` on this path.

This is a genuine logic defect: a bounded-vector capacity failure is swallowed silently while side effects (region removal, event emission, renewal bookkeeping) proceed as if the operation fully succeeded.

## Impact Explanation
If the `Workplan` schedule for a given `(begin, core)` key is at capacity, an `assign` call consumes/destroys the caller's `Region` (for `Finality::Final`) without actually placing a corresponding `ScheduleItem`, while reporting success via `Event::Assigned`. This is a real state-desynchronization/loss-of-value bug: paid coretime is removed from `Regions` without being reflected in `Workplan`, and `PotentialRenewals` records may reference a workload that was never actually scheduled. This is an in-scope broker-pallet accounting defect, not merely theoretical, since the mechanism (bounded push, unconditional side effects) is unambiguous in the code.

## Likelihood Explanation
The exploit path (permissionless `interlace` + `assign` extrinsics) is achievable by any unprivileged region owner, and requires no privileged access, node behavior, or victim mistake. The only unconfirmed detail is the exact bound of the `Workplan`/`Schedule` bounded vector (`Config::MaxScheduleItems` or equivalent) — I was unable to fully locate and confirm this constant's value within the available search iterations, so the precise number of `interlace`+`assign` operations an attacker would need to perform to hit the bound is not verified. However, since `CoreMask` interlacing allows splitting a region into many independent mask slices (bounded only by mask bit-width), and the shared `Workplan` entry per `(begin, core)` is finite, filling it to capacity through repeated legitimate operations is plausible and requires no unusual timing — a determined attacker filling their own core's schedule, or two owners of the same core clashing, is a realistic scenario over enough repetitions.

## Recommendation
- Change `do_assign` and `do_pool` to propagate a hard error (e.g., `Error::<T>::WorkplanFull`) when `try_push` fails, causing the extrinsic to revert rather than silently continue.
- Perform the `Workplan` capacity check before calling `Self::utilize` (which removes the `Region`), or restore the `Region` on failure, so `Regions` and `Workplan` remain consistent.
- Gate the `PotentialRenewals` update and `Event::Assigned` emission on the `Workplan` push actually succeeding.

## Proof of Concept
Unit test outline in `substrate/frame/broker/src/tests.rs`:
1. Run `do_start_sales`, purchase a region covering a full core.
2. Repeatedly `do_interlace` the region into mask pieces and `do_assign` each with `Finality::Final` until the `Workplan` entry for `(begin, core)` reaches its bound (bound value needs confirmation from the pallet's `Config`/`Schedule` type).
3. Perform one additional `do_assign` call and assert:
   - The call returns `Ok(())`.
   - `Regions::<Test>::get(region_id)` is `None` (region consumed).
   - `Workplan::<Test>::get((begin, core))` does not contain the new `ScheduleItem`.
   - `Event::Assigned` was nonetheless emitted, demonstrating the state/event mismatch.
