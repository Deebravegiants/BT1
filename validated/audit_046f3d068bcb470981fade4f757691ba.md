### Title
Missing payer authentication in `HyperApp.dispatchWithFeeToken` allows arbitrary-address fee-token drain via `transferFrom` - (File: `sdk/packages/core/contracts/apps/HyperApp.sol`)

### Summary
`HyperApp.dispatchWithFeeToken` is the shared helper every Hyperbridge EVM application (bandwidth manager, intent gateway, hyper-fungible token wrappers, custom apps) is meant to reuse to pay dispatch fees in the fee token. It pulls `request.fee` from `request.payer` via `safeTransferFrom` without ever checking that `request.payer == msg.sender`. This is the same root cause as the referenced BribeVault finding: a privileged/queued transfer path trusts a caller-supplied address argument as the ERC20 source of funds instead of binding the pull to the actual transaction sender.

### Finding Description
`dispatchWithFeeToken(DispatchPost memory request)` and its `DispatchGet` overload do: [1](#0-0) 

Both branches execute `IERC20(feeToken).safeTransferFrom(request.payer, address(this), request.fee)` whenever `request.payer != address(this)`, with no assertion that `request.payer == msg.sender`. `request.payer` is simply a field of the `DispatchPost`/`DispatchGet` struct that the *calling application's own external function* populates before invoking this internal helper.

The Hyperbridge documentation explicitly instructs app developers to expose `payer` as a caller-supplied parameter rather than hardcoding `msg.sender`: [2](#0-1) 

Following this documented pattern (`function readRemoteState(bytes dest, bytes[] keys, address payer) public returns (bytes32)`), any external, unprivileged caller can invoke the dispatch-triggering function and pass an arbitrary third-party address as `payer`. As long as that victim address has ever granted an ERC20 allowance of the fee token to the app contract (a routine, expected action for anyone who previously used the app to pay fees), the caller can trigger `safeTransferFrom(victim, address(this), fee)` and consume the victim's approved balance to pay for the caller's own arbitrary dispatched message — exactly mirroring how `BribeVault.depositBribeERC20` let `DEPOSITOR_ROLE` pull an arbitrary `briber`'s approved tokens by supplying that address as a parameter instead of requiring `msg.sender`.

The two concrete production apps inspected in-repo (`BandwidthManager.purchase`, `IntentGatewayV2.placeOrder`) currently hardcode `payer: msg.sender` (or `address(this)`), so they are not directly exploitable today. The defect lives in the shared `HyperApp` base contract and its documented usage pattern: nothing in `dispatchWithFeeToken` itself enforces the safe invariant, so every future or third-party `HyperApp` that follows the documented example (or otherwise forwards a caller-chosen `payer`) inherits this exact "arbitrary approved-address drain" vulnerability class.

### Impact Explanation
Any user who has approved the fee token to a `HyperApp`-derived contract (a normal, encouraged workflow per the docs, since repeat use avoids re-approving) is exposed to having that entire approved allowance pulled by any unrelated third party who calls a `payer`-parameterized dispatch function with the victim's address, at zero cost to the attacker beyond gas. This is a direct theft of ERC20 fee-token funds from an unrelated account, satisfying "concrete theft of funds."

### Likelihood Explanation
Likelihood depends on whether a deployed `HyperApp` implementation exposes `payer` as an externally controllable parameter — the official SDK documentation actively recommends exactly this pattern for GET/POST dispatch helpers, making it likely that third-party or future first-party apps built against the documented API will reproduce the flaw. The core defect (missing `payer == msg.sender` check) exists unconditionally in the shared library function that all Hyperbridge apps depend on.

### Recommendation
In `HyperApp.dispatchWithFeeToken` (both `DispatchPost` and `DispatchGet` overloads), require `request.payer == msg.sender || request.payer == address(this)` before performing `safeTransferFrom`, so the helper can never be used to move tokens out of an address that isn't the actual caller. Update the documentation examples (`get-requests.mdx`, `post-requests.mdx`, `hyperapp.mdx`) to stop presenting an externally-supplied `payer` parameter as a safe pattern.

### Proof of Concept
1. Victim `V` calls a hypothetical `HyperApp`-derived contract `App` once, approving `App` to spend their fee token (a normal step recommended to amortize repeated approvals).
2. Attacker `A` calls `App.readRemoteState(dest, keys, V)` (or any similarly designed public function that forwards a caller-chosen `payer` into `DispatchGet.payer`).
3. Inside `dispatchWithFeeToken`, `request.payer` (`V`) `!= address(this)`, so `IERC20(feeToken).safeTransferFrom(V, address(this), request.fee)` executes, pulling `V`'s approved fee tokens to fund `A`'s own dispatched GET request.
4. `V` never authorized this specific transaction and receives no benefit; `A` obtains a paid-for cross-chain dispatch at `V`'s expense. [3](#0-2)

```text
    function dispatchWithFeeToken(DispatchPost memory request) internal returns (bytes32) {
        address hostAddr = host();
        address feeToken = IDispatcher(hostAddr).feeToken();
        if (request.payer != address(this)) IERC20(feeToken).safeTransferFrom(request.payer, address(this), request.fee);
        IERC20(feeToken).forceApprove(hostAddr, request.fee);
        return IDispatcher(hostAddr).dispatch(request);
    }
```

If your contract extends `HyperApp`, use the `dispatchWithFeeToken()` helper which handles all fee calculations and token approvals automatically:

```solidity lineNumbers title="MyApp.sol" icon="solidity"
contract MyApp is HyperApp {
    function readRemoteState(
        bytes memory dest,
        bytes[] memory keys,
        address payer
    ) public returns (bytes32) {
        bytes memory context = abi.encode(payer, block.timestamp);
        
        DispatchGet memory getRequest = DispatchGet({
            dest: dest,
            height: 0,
            keys: keys,
            timeout: 3600,
            fee: 0,
            context: context,
            payer: payer
        });
        
        // Automatically handles:
        // - Fee calculation
        // - Token transfer from payer
        // - Host approval
        // - Dispatch
        return dispatchWithFeeToken(getRequest);
    }
```
