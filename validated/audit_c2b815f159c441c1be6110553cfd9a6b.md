## Title
Unvalidated signature length causes panic-based denial of service in BEEFY `Vote` → `SignatureWithAuthorityIndex` conversion - (File: evm/rust/src/conversions.rs)

### Summary
CVE-2021-30472 is a stack-based buffer overflow in PoDoFo caused by `ComputeOwnerKey` copying attacker-controlled key bytes into a fixed-size buffer without validating the length first. The closest reachable analog in Hyperbridge is `evm/rust/src/conversions.rs:356-366`, where the `From<Vote> for SignatureWithAuthorityIndex` conversion copies an attacker-supplied `bytes` field into a fixed 65-byte array via `copy_from_slice` without checking its length beforehand.

### Finding Description
```rust
impl From<Vote> for SignatureWithAuthorityIndex {
	fn from(value: Vote) -> Self {
		let sig_bytes = value.signature.to_vec();
		let mut signature: TSignature = [0u8; 65];
		signature.copy_from_slice(&sig_bytes);
		SignatureWithAuthorityIndex {
			signature,
			index: value.authorityIndex.try_into().expect("authority index out of bounds"),
		}
	}
}
``` [1](#0-0) 

`Vote.signature` is a Solidity ABI `bytes` field (from `evm/src/consensus/Types.sol`), i.e., attacker-controlled and of arbitrary length when submitted as part of a BEEFY consensus proof. Rust's `copy_from_slice` requires the source slice length to exactly equal the destination (`65`); any mismatch triggers a panic rather than a buffer overflow, because Rust arrays are bounds-checked at runtime (unlike the C++ `PdfEncrypt.cpp` case, which lacked such a check entirely). This is the language-level mitigation that prevents true memory corruption, but the underlying root cause pattern — copying externally-controlled data into a fixed-size buffer without validating its length in advance — is structurally identical to the CVE.

This mirrors the exact defect class the codebase has already fixed elsewhere: `modules/utils/serde/src/lib.rs` explicitly documents and tests that a previous `copy_from_slice`-into-`[u8;4]` implementation panicked on untrusted RPC input and crashed a node's RPC worker thread [2](#0-1) [3](#0-2) . That fix replaced the unchecked copy with a length-checked `try_into()`. The BEEFY `Vote` conversion in `evm/rust/src/conversions.rs` was not brought in line with that pattern.

### Impact Explanation
If this conversion runs inside the BEEFY consensus verification path invoked from unprivileged submitted proofs (a relayer submitting a BEEFY consensus update), any vote signature that is not exactly 65 bytes causes an unrecoverable Rust panic. Depending on the panic-handling boundary (native process vs. a WASM/zkVM guest), this could abort the verifying process — a denial-of-service against the component validating consensus updates, potentially halting message delivery through the BEEFY consensus client until patched.

### Likelihood Explanation
I could not fully confirm from the available index whether this `From<Vote>` conversion is actually invoked on the hot path that processes untrusted, attacker-supplied BEEFY signatures before any length validation occurs (e.g., inside a signature-verification loop reachable from `verify_consensus`), or whether it is only used with data that has already been length-validated elsewhere (e.g., decoded via a fixed-size ABI type upstream). The repository's index has size limits and I was unable to retrieve the full call chain connecting `Vote` (Solidity-side struct in `Types.sol`) to this Rust conversion function, nor confirm whether `evm/rust` compiles to a zkVM guest (SP1) that receives untrusted proof bytes directly.

### Recommendation
Regardless of the exact reachability, replace the unchecked `copy_from_slice` with a fallible conversion (e.g., `signature.try_into().map_err(...)` or an explicit length check returning an error) so malformed vote signatures produce a typed decode error instead of a panic — consistent with the fix already applied to `as_utf8_string` in `modules/utils/serde/src/lib.rs`.

### Proof of Concept
Not fully verifiable from the indexed code alone. A concrete PoC would require confirming that `Vote.signature` values are attacker-controlled and unvalidated before reaching `From<Vote> for SignatureWithAuthorityIndex`; if so, submitting a BEEFY consensus proof containing a vote with a signature field of any length other than 65 bytes would trigger the panic.

**I recommend starting a Devin session with full repository access to trace the exact call path from the BEEFY consensus client entrypoint through to this conversion, in order to confirm reachability and precisely scope the fix**, since the ask-only index does not expose the complete call graph needed to make this determination with certainty.

	/// runs on untrusted RPC input, so it must never panic.
