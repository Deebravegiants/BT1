## Finding: Webhook `shop` identity is not bound to the HMAC signature [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

### Title
Webhook `shop` field is trusted by the handler but not covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only `@raw_body`, so `HmacValidator.validate` (`compute_signature(verifiable_query.to_signable_string, secret)`) authenticates the request body only. The `shop` accessor is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signed material. `Registry.process` still forwards `request.shop` directly into `WebhookMetadata` and passes it to the app's handler as the authoritative tenant identifier.

### Finding Description
`Request#shop` is derived purely from an HTTP header:
```ruby
def shop
  T.cast(shopify_header("shop-domain"), String)
end
```
while the HMAC that `Registry.process` checks is computed only over the raw JSON body (`to_signable_string` → `@raw_body`). The equality the gem implicitly claims to guarantee is:

`shop_used_by_handler == shop_that_actually_produced/authorized_the_signed_body`

but the code only proves `hmac(body, secret) == received_hmac`; it proves nothing about which shop the header names. Because the same `api_secret_key` is shared across every shop that installs the app, any body+HMAC pair Shopify ever issued for *any* shop (including a shop the attacker legitimately controls, e.g., a free dev/trial store) remains a valid signature for that body regardless of which `x-shopify-shop-domain` header accompanies it. An attacker who owns a shop that has this app installed can capture one of their own webhook deliveries (body + valid HMAC) and replay it to the app's webhook endpoint with the header changed to name a victim shop. `HmacValidator.validate` passes because it never looks at the header, and `Registry.process` builds `WebhookMetadata` with the attacker-chosen `shop` value, which the host handler is documented to trust as the source shop.

### Impact Explanation
If the host application uses `data.shop` from `WebhookMetadata` to select which tenant's record to mutate (a documented, encouraged usage pattern per `docs/usage/webhooks.md`), an attacker can cause writes/actions to be attributed to, or performed against, a shop they do not own — a cross-tenant confusion that breaks the shop-to-request binding the gem's own webhook API implicitly promises consumers.

### Likelihood Explanation
Exploitation requires only that the attacker control one shop with the app installed (freely obtainable, e.g., a Shopify partner dev/trial store) and be able to trigger a webhook whose body they influence (many webhook topics carry attacker-editable content, e.g. order notes/line items). No secret, access token, or privileged account is needed — only observation of one legitimate delivery to the attacker's own endpoint/shop.

### Recommendation
Bind the shop identity into the verified material: either include the `shop-domain` header in the signed payload used for HMAC comparison, or require callers to cross-check `request.shop` against a list of shops that have an active, expected webhook registration/session before trusting it in `Registry.process`/`WebhookMetadata`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop `attacker.myshopify.com`; trigger a webhook (e.g., `orders/create`) and capture the raw body `B` and its valid `x-shopify-hmac-sha256` header `H` (`HMAC-SHA256(api_secret_key, B) == H`).
2. Replay to the app's webhook endpoint:
```
POST /callback/orders/create
x-shopify-topic: orders/create
x-shopify-hmac-sha256: H
x-shopify-shop-domain: victim.myshopify.com
x-shopify-webhook-id: <any>

B
```
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only checks `HMAC(B, secret) == H` — succeeds.
4. The handler receives `WebhookMetadata.new(shop: "victim.myshopify.com", body: B, ...)` and acts as if the event genuinely originated from `victim.myshopify.com`.
