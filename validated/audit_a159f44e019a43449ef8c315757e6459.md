### Title
Unverified `signer` field in `RequestMessage`/`ResponseMessage` lets any relayer forge delivery attribution and steal or permanently freeze relayer rewards - (File: `modules/pallets/ismp/src/host.rs`)

### Summary
`pallet-ismp`'s `IsmpHost::store_request_receipt` / `store_response_receipt` implementation calls `extract_signer()` to derive the "delivering relayer" identity that gets committed on-chain in `RequestReceipts`/`ResponseReceipts`. `extract_signer` decodes the `signer` bytes supplied in the message as a `crypto_utils::verification::Signature` and calls `Signature::signer()`, which merely returns the embedded `public_key`/`address` field of the struct — it never calls `Signature::verify()` to check that the signature actually authenticates the message content. Any unprivileged submitter of `handle_unsigned` (an unsigned, permissionless extrinsic per the pallet's own documentation) can therefore attach a syntactically valid but cryptographically meaningless `Signature` naming an arbitrary address/public key, and that value is recorded as the "proven" delivering relayer, which is later trusted as ground truth by `pallet-ismp-relayer` for real fund transfers.

### Finding Description
`extract_signer` in `modules/pallets/ismp/src/host.rs`: [1](#0-0) 

is invoked from both receipt-storing paths that persist the delivering relayer's identity for every incoming `PostRequest`/`GetResponse`: [2](#0-1) 

`Signature::signer()` only extracts the caller-supplied identity field embedded in the `Signature` enum without validating the accompanying cryptographic signature bytes against the message; the actual verification routine, `Signature::verify()`, is a separate method that is never invoked here: [3](#0-2) [4](#0-3) 

Since `handle_unsigned` messages are processed as unsigned extrinsics reachable by anyone with valid state/consensus proofs (the proofs themselves are public and permissionless to fetch), the only "identity" attached to a delivery is this unverified `signer` field: [5](#0-4) 

This forged, unverified identity is then trusted downstream as the authoritative "delivering relayer" for real value transfers. `pallet-ismp-relayer::decode_receipt_relayer` decodes the substrate receipt bytes the same way (via `Signature::decode(...).signer()`, again with no `verify()` call at this layer either) and `process_outbound_request_delivery_claim` pays a treasury-funded reward to whoever's *separately supplied* signature recovers to match this recorded (and forgeable) value: [6](#0-5) [7](#0-6) 

This is directly analogous to CVE-2015-5310: a protocol response carries security-relevant data (there, GTK key material; here, relayer identity/key material) that downstream logic uses to make an authorization/attribution decision, but the code never verifies that the claimed security context (a real cryptographic signature) was actually established before trusting the embedded data.

### Impact Explanation
Because `RequestReceipts[commitment]`/`ResponseReceipts[commitment]` is a first-write, idempotent record (subsequent deliveries fail with `DuplicateRequest`/`DuplicateResponse`), an unprivileged attacker who observes/replays a legitimately provable cross-chain message can:
1. Submit it first with a forged `signer` naming an address they cannot access (garbage/unowned key), permanently freezing the relayer reward for that delivery, since `process_outbound_request_delivery_claim` and `accumulate_fees` both require a signature that recovers to exactly the value stored at first-write and no one can ever produce that signature (permanent loss of relayer funds), or
2. Submit it with a forged `signer` naming their own address, stealing the delivery/relayer attribution and the associated fee/reward from whoever actually should have won the "relay race," since no proof of key possession is required at write time.

Both outcomes are reachable from a single message delivered through the permissionless `handle_unsigned` dispatch path and directly cause theft or permanent freezing of relayer-incentive funds, satisfying the required Medium/High impact bar.

### Likelihood Explanation
`handle_unsigned` is explicitly designed to be callable by anyone with valid state/consensus proofs (that's the entire "permissionless relayer" model), and the state/consensus proof verification steps that gate delivery do not touch the `signer` field at all — it is bookkeeping metadata, decoded but never cryptographically checked at the point it's persisted. Constructing a syntactically valid `Signature::Evm`/`Signature::Sr25519`/`Signature::Ed25519` value naming an arbitrary target address requires no secret material. This makes exploitation straightforward for any actor capable of submitting an unsigned ISMP extrinsic (which is by design open to all).

### Recommendation
In `extract_signer` (and the parallel `decode_receipt_relayer` decode path in `pallet-ismp-relayer`), require `Signature::verify()` against the canonical message digest (e.g., the same `keccak_256(requests.encode())`/`keccak_256(responses.encode())` payload signed by legitimate relayers, as already done in `modules/pallets/messaging-incentives/src/lib.rs::relayer_for`) before accepting the embedded public key/address as the attributed relayer. Reject the message (or fall back to treating it as unattributed, ineligible for reward) if signature verification fails, rather than persisting an unverified identity into `RequestReceipts`/`ResponseReceipts`.

### Proof of Concept
1. Observe (or independently reconstruct) a legitimate `PostRequest`/`GetResponse` batch destined for a Hyperbridge-connected substrate chain, along with its valid membership/state proof (all public data, no special access needed).
2. Construct `RequestMessage { requests, proof, signer: Signature::Sr25519 { public_key: <attacker_or_victim_key>, signature: <arbitrary 64 bytes> }.encode() }` — note the signature bytes are never checked against `requests`.
3. Submit via `pallet_ismp::Pallet::handle_unsigned(RuntimeOrigin::none(), vec![Message::Request(msg)])`. Verification of proofs succeeds normally (as in `should_charge_fee_for_request`, which shows a completely random Sr25519 signature being accepted without failure: `modules/pallets/testsuite/src/tests/pallet_ismp.rs:618-661`).
4. `store_request_receipt` calls `extract_signer(&msg.signer)`, decodes the `Signature`, and returns `sig.signer()` = the attacker-chosen public key, which is written to `child_trie::RequestReceipts[commitment]` with no check that the attacker holds the corresponding private key.
5. Any later `claim_outbound_request_delivery_reward` or `accumulate_fees` call for this commitment is now permanently bound to whatever value was written in step 4 — payable only to whoever can sign as that key (the true relayer cannot, if the attacker chose a garbage/unowned key), demonstrating both the theft and freezing outcomes described above.

fn extract_signer(signer: &[u8]) -> Result<Vec<u8>, Error> {
	if signer.len() > 32 {
		Signature::decode(&mut signer.as_ref())
			.map(|sig| sig.signer())
			.map_err(|_| Error::SignatureDecodingFailed)
	} else {
		Ok(signer.to_vec())
	}
}

	/// verify the signature with the public key in the enum or optionally provide a public key
	/// to be used to verify the signature
	pub fn verify(
		&self,
		msg: &[u8; 32],
		public_key_op: Option<Vec<u8>>,
	) -> Result<Vec<u8>, anyhow::Error> {
		match self {
			Signature::Evm { signature, .. } => {
				if signature.len() != 65 {
					Err(anyhow!("Invalid Signature"))?
				}

				let mut sig = [0u8; 65];
				sig.copy_from_slice(&signature);
				let pub_key = sp_io::crypto::secp256k1_ecdsa_recover(&sig, msg)
					.map_err(|_| anyhow!("Signature Verification failed"))?;
				let signer = sp_io::hashing::keccak_256(&pub_key[..])[12..].to_vec();
				Ok(signer)
			},
			Signature::Sr25519 { signature, public_key } => {
				Self::verify_sr25519(signature, public_key, msg, &public_key_op)?;
				Ok(public_key_op.unwrap_or(public_key.clone()))
			},

impl<T: Config> Pallet<T> {
	/// Decode a proven `RequestReceipts[commitment]` value into the delivering
	/// relayer's bytes. EVM stores the address RLP encoded, substrate stores the
	/// signer bytes or a signature to recover the signer from. Used by both fee
	/// accumulation and the outbound request delivery claim.
	pub fn decode_receipt_relayer(state_id: StateMachine, raw: &[u8]) -> Result<Vec<u8>, Error<T>> {
		match state_id {
			s if crate::is_pharos(&s) =>
				if raw.len() == 32 {
					Ok(Address::from_slice(&raw[12..]).0.to_vec())
				} else {
					Err(Error::<T>::ProofValidationError)
				},
			s if s.is_evm() => {
				use alloy_rlp::Decodable;
				Ok(Address::decode(&mut &*raw)
					.map_err(|_| Error::<T>::ProofValidationError)?
					.0
					.to_vec())
			},
			s if s.is_substrate() => {
				use codec::Decode;
				let bytes =
					<Vec<u8>>::decode(&mut &*raw).map_err(|_| Error::<T>::ProofValidationError)?;
				Ok(if bytes.len() > 32 {
					Signature::decode(&mut &*bytes)
						.map_err(|_| Error::<T>::SignatureDecodingError)?
						.signer()
				} else {
					bytes
				})
			},
			_ => Err(Error::<T>::MismatchedStateMachine),
		}
	}
