Based on my investigation, there is a legitimate analog to the reported bug class in the webhook HMAC verification path of this gem.

### Title
Webhook Shop/Topic Identity Fields Are Not Covered by HMAC Verification, Enabling Cross-Tenant Webhook Spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request` exposes `shop`, `topic`, `api_version`, and `webhook_id` as plain, unauthenticated HTTP headers, while the HMAC that `Utils::HmacValidator` verifies is computed over the raw request body only. This is the same class of bug as the reported "asset index truncation": a value that is later trusted/acted upon (`shop`) is not actually covered by the check that is supposed to authenticate the request (the HMAC).

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, `#api_version`, and `#webhook_id` are all read straight from HTTP headers, independent of the body: [2](#0-1) 

`HmacValidator.validate_signature` computes the signature purely over `verifiable_query.to_signable_string` (i.e. the raw body) and compares it with `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` validates the HMAC, then immediately trusts `request.shop` (and `request.topic`) as the tenant identifier passed to the application's webhook handler, without any additional binding between the shop header and the signed body: [4](#0-3) 

Because the HMAC only proves "this body byte-sequence was produced with the app's secret at some point," and not "this body belongs to shop X," an unprivileged merchant who has legitimately installed the app on their own shop (and therefore genuinely receives real, validly-signed webhook deliveries for their own shop) can capture one such delivery (raw body + valid `x-shopify-hmac-sha256`) and replay it directly to the app's public webhook endpoint with the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header rewritten to point at a different, victim shop. `Utils::HmacValidator.validate` will still return `true` because it never inspects those headers, and `Registry.process` will hand the handler a `WebhookMetadata` claiming `shop: <victim-shop>` together with the attacker's own (valid) body. This breaks the identity binding: **shop authenticated by the HMAC (none, since headers aren't signed) versus shop used as the tenant/session key by the host application's handler**.

### Impact Explanation
Any host application that uses `WebhookMetadata#shop` from `ShopifyAPI::Webhooks::Registry` to select which merchant's session/store/data to update (a standard and encouraged pattern, since that's the only shop identifier the gem exposes to webhook handlers) can be tricked into writing/processing attacker-supplied webhook body content under a victim shop's identity. This is a cross-tenant integrity issue reachable by any unprivileged merchant that has installed the app — no `api_secret_key`, access token, or other privileged credential is required, since the attacker already legitimately possesses a validly HMAC-signed body/signature pair for their own shop.

### Likelihood Explanation
Likelihood is high for any integrator following the documented `Registry.process`/`WebhookMetadata` pattern, since the vulnerable trust boundary is baked into the gem's own webhook verification primitive (`HmacValidator` + `Request`) rather than depending on the host app diverging from documented usage. The only requirement is that the attacker controls an app installation (extremely low bar — any merchant can install a public app) and can send an HTTP request to the app's public webhook callback URL with custom headers, which is inherent to how webhook endpoints are exposed.

### Recommendation
Bind the shop (and ideally topic/webhook id) into the value that is actually verified by the HMAC, e.g. by including the `x-shopify-shop-domain` (and other identity-relevant headers) in the signable string alongside the raw body, or by requiring/validating that the shop domain is independently confirmed against a known installation record keyed by data embedded in the signed body before trusting `request.shop` for tenant routing.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com`, a legitimate but unprivileged installation.
2. Shopify delivers a real webhook to the attacker's endpoint, e.g. `orders/create`, with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker captures `(B, H)` and POSTs directly to the app's public webhook endpoint (the same endpoint used for all shops) with:
   - body `B` (unchanged)
   - `x-shopify-hmac-sha256: H` (unchanged, still valid because only body is signed)
   - `x-shopify-shop-domain: victim-shop.myshopify.com` (forged)
4. `Utils::HmacValidator.validate` returns `true` because `to_signable_string` only checks `B` against `H`. [5](#0-4) 
5. `Registry.process` invokes the handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: parsed(B), ...)`, causing the host app to process attacker-controlled data under the victim shop's tenant context. [6](#0-5)
