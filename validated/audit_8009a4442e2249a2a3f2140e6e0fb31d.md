### Title
Webhook `shop`, `topic`, and `webhook_id` are trusted for tenant/topic routing without being covered by the HMAC signature - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` extracts `shop`, `topic`, `webhook_id`, and `api_version` from unauthenticated HTTP headers, but `HmacValidator.validate` (called via `Registry.process`) only verifies the raw request body against the HMAC signature. The gem's own documentation states that `Registry.process` "will verify the request did indeed come from Shopify," yet the identity fields the handler relies on for tenant/topic dispatch are never bound to that signature.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id`, and `api_version` are read directly from the (non-signed) `shopify-*`/`x-shopify-*` headers: [2](#0-1) 

`Registry.process` validates only this body-only HMAC, then immediately trusts `request.shop` and `request.topic` to build the `WebhookMetadata` handed to the app's handler: [3](#0-2) 

This is the same bug class as the reported issue: a value that is *acted on* (here, the tenant-identifying `shop` field and the `topic` used for dispatch) is not covered by the cryptographic check that is supposed to bind it (the HMAC), while the code (and the docs) treat successful HMAC validation as proof of the full request's authenticity. The equality that should hold is:
`HMAC-covered bytes == bytes the handler uses to identify tenant/topic`
but instead: `HMAC-covered bytes (body only) ⊂ bytes used to route/identify (body + shop + topic + webhook_id + api_version)`.

The gem's own documentation reinforces the false guarantee, telling integrators that calling `Registry.process` "will verify the request did indeed come from Shopify" before invoking the handler with `data.shop`: [4](#0-3) [5](#0-4) 

### Impact Explanation
If an attacker who legitimately receives one authentic, HMAC-signed webhook payload (e.g. by having the app installed on their own shop) can cause that exact `raw_body` to be replayed to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`) header, `HmacValidator.validate` still returns `true` because it only checks the body bytes, and `Registry.process` will dispatch the handler believing the event originated from a different, victim shop. Since handlers commonly key persistence/processing (queueing jobs, updating tenant records) directly off `data.shop`, this is a cross-tenant identity-binding failure inside the gem's own trusted verification path, not a misuse of an undocumented API by the host app.

### Likelihood Explanation
Exploitation requires the attacker to obtain a genuine `(raw_body, hmac)` pair and be able to re-deliver it to the app's public webhook endpoint with modified headers. Because webhooks are pushed server-to-server from Shopify directly to the app's endpoint, an attacker normally cannot observe this traffic in transit without additional access (e.g., control of network path/logging on their own webhook consumption stack), which is why this analog should be treated as a design gap in the verification guarantee rather than a trivially remotely-exploitable bug. I could not find any place in the in-scope library code where `shop`/`topic`/`webhook_id` are additionally bound to the signature, and I could not find a documented caveat in `docs/usage/webhooks.md` warning integrators that these fields are unauthenticated — the doc's wording ("verify the request did indeed come from Shopify") is stronger than what the implementation guarantees.

### Recommendation
Bind `shop`, `topic`, and `webhook_id` into the value used for HMAC verification (e.g. by having `to_signable_string` also cover these header values, or by requiring the caller to supply/verify an expected shop and topic set), and correct the documentation in `docs/usage/webhooks.md` to state precisely what `HmacValidator.validate` does and does not authenticate.

### Proof of Concept
```ruby
# Attacker has legitimately received one authentic Shopify webhook for their own shop:
raw_body = '{"id":1}'
genuine_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_SECRET, raw_body)
# (This pair is only observable if the attacker can see their own webhook traffic.)

forged_headers = {
  "x-shopify-topic"        => "app/uninstalled",       # attacker-chosen topic
  "x-shopify-hmac-sha256"  => Base64.encode64(genuine_hmac), # unchanged, body unchanged
  "x-shopify-shop-domain"  => "victim-shop.myshopify.com",   # forged tenant
  "x-shopify-webhook-id"   => SecureRandom.uuid,
  "x-shopify-api-version"  => "2024-01",
}

req = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)
ShopifyAPI::Webhooks::Registry.process(req)
# HmacValidator.validate(req) still returns true (body-only check),
# and the handler is invoked believing the event came from "victim-shop.myshopify.com".
``` [6](#0-5)

          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,

        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
