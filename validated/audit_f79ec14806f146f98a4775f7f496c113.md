### Title
Unchecked fixed-size buffer copy from attacker-controlled BEEFY `Vote.signature` bytes panics the on-chain consensus-proof pallet - (File: `evm/rust/src/conversions.rs`)

### Summary
`pallet-beefy-consensus-proofs::verify_and_apply` accepts a raw, prover-submitted proof via a **signed extrinsic**, ABI-decodes it into Solidity-derived types, and converts those types into internal SCALE types before handing them to `pallet_ismp`'s `handle_incoming_message`. For the `PROOF_TYPE_NAIVE` path this conversion chain runs through `BeefyConsensusProof -> ConsensusMessage -> RelayChainProof -> MmrProof`, which maps each `Vote` in `signedCommitment.votes` through `impl From<Vote> for SignatureWithAuthorityIndex` [1](#0-0) . That conversion does:

```rust
let sig_bytes = value.signature.to_vec();
let mut signature: TSignature = [0u8; 65];
signature.copy_from_slice(&sig_bytes);
```

`value.signature` is an ABI-decoded dynamic `bytes` field (from the attacker-supplied proof), and its length is never validated before the fixed-size (65-byte) `copy_from_slice`. This is the direct analog of the CVE's bug class: parsing untrusted, length-prefixed input directly into a fixed-size buffer with no bounds/length check before the copy. `copy_from_slice` panics (rather than corrupting memory, since Rust is memory-safe) whenever `sig_bytes.len() != 65`.

### Finding Description
The call path is:
1. `pallet_beefy_consensus_proofs::Pallet::verify_and_apply(proof: &[u8])` reads the proof-type byte, then for `PROOF_TYPE_NAIVE`, ABI-decodes the remaining payload as `ismp_abi::ecdsa_beefy::BeefyConsensusProof` and immediately calls `.into()` to get `beefy_verifier_primitives::ConsensusMessage` [2](#0-1) .
2. That `From` impl walks: `BeefyConsensusProof -> ConsensusMessage` (`relay: message.mmr.into()`) [3](#0-2)  → `RelayChainProof -> MmrProof`, which maps `value.signedCommitment.votes.into_iter().map(Into::into).collect()` [4](#0-3)  → each `Vote -> SignatureWithAuthorityIndex` via the unchecked `copy_from_slice` shown above.
3. This conversion executes entirely inside the pallet call before any cryptographic verification takes place (verification happens later in `handlers::handle_incoming_message` → `BeefyConsensusClient::verify_consensus`).

Because `value.signature` comes straight from ABI-decoded attacker-controlled bytes, any signer can submit a `Vote` whose `signature` is not exactly 65 bytes and trigger a panic before any signature/authority checks run. Unlike other length-mismatch decode paths in this codebase (e.g. `beefy/verifier/src/lib.rs::verify_mmr_leaf`, `bsc/verifier/src/primitives.rs::parse_extra`, `sync-committee/verifier/src/lib.rs`, `grandpa/verifier`), which were explicitly hardened against attacker-controlled length/index mismatches with typed errors (several have comments describing exactly this class of prior panic bug being fixed), this particular EVM-ABI→SCALE conversion path retains the unchecked pattern.

### Impact Explanation
A panic raised while executing a pallet extrinsic inside runtime (Wasm) execution is not gracefully caught as a `DispatchError`; it traps runtime execution for that transaction. Since `verify_and_apply` is invoked from a normal **signed** extrinsic path (any account can submit a BEEFY consensus proof to earn the prover reward described in the pallet's own doc comments), an attacker can deterministically craft a malformed `Vote.signature` length and repeatedly submit it. Because block-authoring validators execute the same extrinsic deterministically, this can degrade or halt the BEEFY consensus-update pipeline that pallet-ismp relies on to advance parachain state commitments — i.e., a route becomes unable to deliver/verify new BEEFY-sourced messages, which is the accepted "route unable to deliver messages" impact class in the validation rules.

### Likelihood Explanation
High. The extrinsic (`verify_and_apply`) is explicitly designed to be called by any signed account (open incentive to submit proofs, per the pallet's own documentation) [5](#0-4) . No privileged role, governance, or specific node/peer position is required — a single crafted extrinsic with a `Vote.signature` field of any length other than 65 bytes reaches the unchecked `copy_from_slice` before any cryptographic gate.

### Recommendation
Replace the unchecked `copy_from_slice` in `impl From<Vote> for SignatureWithAuthorityIndex` (`evm/rust/src/conversions.rs:356-366`) with a fallible conversion (e.g. `TryFrom`/`try_into()` returning an error, mirrored by changing `MmrProof`'s `From<RelayChainProof>` and its callers to propagate a `Result`), rejecting any `Vote.signature` whose length is not exactly 65 bytes with a typed error surfaced through `pallet_beefy_consensus_proofs::Error::<T>::AbiDecodeFailed` (or a new dedicated variant) instead of panicking.

### Proof of Concept
1. Craft a `BeefyConsensusProof` ABI payload (Solidity `Vote[]` inside `signedCommitment.votes`) where at least one `Vote.signature` has length ≠ 65 (e.g., 0 or 64 bytes) — trivially constructible since `signature` is a dynamic `bytes` field with no on-chain length enforcement at the ABI-decode stage.
2. Prefix the payload with `PROOF_TYPE_NAIVE` and submit it via a signed extrinsic to `pallet_beefy_consensus_proofs::verify_and_apply`.
3. Execution reaches `Vote -> SignatureWithAuthorityIndex` conversion and panics on `signature.copy_from_slice(&sig_bytes)` before any BEEFY signature/authority-set verification occurs, since the ABI decode step itself does not constrain `signature` length.

*Note: full confirmation that this specific conversion path (as opposed to only the SP1/zk proof path, which was not reachable in the time available to fully trace) is exercised strictly via the signed, unprivileged `verify_and_apply` extrinsic relies on the code read above; a Devin session with full repo access could additionally confirm whether frame's Wasm executor treats this panic as a block-halting trap versus a contained dispatch failure in this specific runtime configuration.*
