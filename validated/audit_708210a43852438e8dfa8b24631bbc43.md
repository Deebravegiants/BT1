Audit Report

## Title
Cross-user response hijacking via unvalidated MessageID reuse in gateway legacy web-api-trigger handler - (File: core/services/gateway/handlers/capabilities/handler.go)

## Summary
The gateway's legacy web-api-trigger handler stores an in-flight user callback keyed solely by the client-supplied `MessageID`, with no uniqueness/ownership check against `Sender`, and unconditionally overwrites any existing entry for that key. Since `MessageID` is fully attacker-chosen (validated only for length/null-suffix), an unprivileged client can supply the same `MessageID` as a victim's concurrently in-flight request to hijack the DON's eventual response.

## Finding Description
`gateway.ProcessRequest` validates the incoming legacy `api.Message` only via `Message.Validate()`, which checks `MessageID` length (≤128 bytes) and null-byte suffix but performs no uniqueness or sender-binding check [1](#0-0) , then dispatches to `h.HandleLegacyUserMessage` [2](#0-1) .

In `HandleLegacyUserMessage`, the callback is stored in `h.savedCallbacks` keyed purely by `msg.Body.MessageID` with no existence check, silently overwriting any prior entry: [3](#0-2) .

When a DON node later responds, `handleWebAPITriggerMessage` looks up and deletes the callback by `MessageID` alone and delivers the response to whatever is currently stored there, without verifying that the responding node's message corresponds to the same sender that originally registered the callback: [4](#0-3) .

The identical unguarded-overwrite pattern exists in `handler.dummy.go`'s `HandleLegacyUserMessage`, confirming this is a systemic pattern rather than an isolated bug. The `handler` struct's map is declared as `map[string]*savedCallback`, confirming the key is a bare string with no sender component [5](#0-4) .

This contrasts with the newer v2 HTTP trigger handler, which explicitly rejects duplicate in-flight `requestID`s via a `setupCallback` conflict check (`ErrConflict`) rather than silently overwriting — demonstrating that the project itself treats this exact pattern as a bug needing a guard in the newer code path, while the legacy path referenced here still lacks it.

## Impact Explanation
An unauthenticated actor on the gateway's public endpoint can intercept another user's in-flight web-api-trigger response by colliding on `MessageID`, redirecting DON-computed output intended for the victim to the attacker's HTTP connection. This is a genuine cross-user response confusion issue affecting confidentiality/integrity of the gateway request/response channel, an in-scope impact class for this component.

## Likelihood Explanation
Exploitation requires no privilege beyond network access to the gateway endpoint and a valid signature over an attacker-chosen message (trivial, since attackers sign their own messages with their own keys). The only non-trivial requirement is winning a race window between the victim's request submission and the DON's response, and predicting/guessing the victim's `MessageID` value — feasible if IDs are low-entropy, sequential, or otherwise observable/predictable by the attacker, or if the attacker can flood many colliding IDs during the response window. This makes the likelihood realistic but conditioned on MessageID predictability and race-timing, which is disclosed transparently in the report as a caveat.

## Recommendation
- Scope `savedCallbacks` (and the equivalent map in `handler.dummy.go`) by `(Sender, MessageID)` instead of `MessageID` alone.
- In `HandleLegacyUserMessage`, reject the request if an entry already exists for the given key (mirroring the `ErrConflict` behavior in `v2/http_trigger_handler.go`'s `setupCallback`) instead of silently overwriting.
- In `handleWebAPITriggerMessage` (and the dummy handler's equivalent), verify that the node's response corresponds to the sender that originally created the saved callback before delivering the payload.

## Proof of Concept
1. Attacker submits signed message A with `MessageID = "collide-1"` to the gateway targeting a web-api-trigger DON; `HandleLegacyUserMessage` stores callback A at `savedCallbacks["collide-1"]` (`core/services/gateway/handlers/capabilities/handler.go:411-414`).
2. Before the DON responds to a victim's identical-`MessageID` request (or before/after, depending on race outcome), attacker resends colliding `MessageID = "collide-1"` signed by their own key, overwriting `savedCallbacks["collide-1"]` with their own callback.
3. When the DON responds with `MessageID = "collide-1"`, `handleWebAPITriggerMessage` (`handler.go:148-162`) looks up the map by `MessageID` only and delivers the response to whichever callback (attacker's or victim's) is currently stored, regardless of original sender — reproducible via a Go unit/integration test that calls `HandleLegacyUserMessage` twice with the same `MessageID` from different signers, then calls `HandleNodeMessage`/`handleWebAPITriggerMessage` and asserts which callback receives the response.

func (h *handler) handleWebAPITriggerMessage(ctx context.Context, msg *api.Message, nodeAddr string) error {
	h.mu.Lock()
	savedCb, found := h.savedCallbacks[msg.Body.MessageID]
	delete(h.savedCallbacks, msg.Body.MessageID)
	h.mu.Unlock()

	if found {
		// Send first response from a node back to the user, ignore any other ones.
		// TODO: in practice, we should wait for at least 2F+1 nodes to respond and then return an aggregated response
		// back to the user.
		codec := api.JSONRPCCodec{}
		return savedCb.SendResponse(handlers.UserCallbackPayload{RawResponse: codec.EncodeLegacyResponse(msg), ErrorCode: api.NoError})
	}
	return nil
}
