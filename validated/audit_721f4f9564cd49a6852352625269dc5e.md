## Title
Single invalid request in a relayer-batched `RequestMessage` reverts the entire `handle_unsigned` extrinsic, denying delivery of unrelated users' messages - (File: `modules/pallets/ismp/src/lib.rs`)

### Summary
`pallet_ismp::Pallet::handle_unsigned` is a free, permissionless (`ensure_none`) extrinsic that executes a `Vec<Message>` and is marked `#[frame_support::transactional]`, so any single invalid message anywhere in the call aborts and rolls back the whole batch. Within a single `Message::Request`, the relayer's own batching logic packs multiple *different senders'* `PostRequest`s into one `RequestMessage.requests` vector to amortize the MMR proof cost. The message handler validates every request in that inner vector in a loop and short-circuits with `Err` on the first failure (duplicate receipt, timeout, wrong destination, disallowed proxy), which propagates up through `execute()`'s `collect::<Result<Vec<_>,_>>()` and aborts the entire transactional extrinsic — including all the other, unrelated, still-valid requests bundled in the same batch. This is structurally the same bug class as CVE-2018-25098 (`executeUcacTx`): a single failing item in a batch blocks unrelated items from being processed, rather than being isolated.

### Finding Description
`handle_unsigned` dispatches the batch atomically: [1](#0-0) 

`execute()` maps every message through `handle_incoming_message` and short-circuits on the first `Err`, converting the whole call into `Error::InvalidMessage`: [2](#0-1) 

Inside a single `Message::Request`, `handlers::request::handle` iterates over `msg.requests` (a `Vec<PostRequest>`) and returns `Err` on the *first* request that already has a receipt, has timed out, or has an invalid destination — aborting processing of every other request in that same vector, even ones from unrelated senders: [3](#0-2) 

The relayer's own batching path deliberately groups multiple *different* users' pending `PostRequest`s into one `RequestMessage` to save proof/gas cost: [4](#0-3) 

Because `handle_unsigned`/`validate_unsigned` re-executes the same `execute()` logic for mempool validation, a batch is only accepted if it currently passes in full. But state can change between proof construction and inclusion (or an attacker can extract a single request commitment from the pending unsigned extrinsic — unsigned txs are visible pre-inclusion — and submit just that one request in its own free `handle_unsigned` call, landing first). Once any one request in the relayer's larger batch is delivered ahead of time (or times out, or otherwise becomes invalid), the whole batched extrinsic reverts via `#[frame_support::transactional]`, and none of the other unrelated, still-valid requests in that batch are delivered in that block.

This mirrors the EVM side's explicit fix for exactly this bug class: `EvmHost.dispatchIncoming` and `HyperbridgeLzEndpoint.onAccept` were both hardened so that one failing/reverting delivery does not block or brick delivery of others in the same call: [5](#0-4) [6](#0-5) 

No equivalent isolation exists for `pallet-ismp`'s `handle_unsigned` batch-of-requests path.

### Impact Explanation
An attacker (any unprivileged account, since `handle_unsigned` is free/unsigned) can grief the relaying of many unrelated users' cross-chain requests in a single batch by causing one entry in that batch to become invalid before the batch lands (front-running with the same request, or waiting for it to time out). Every other legitimate, otherwise-deliverable request bundled in the same `RequestMessage` fails to be delivered in that block and must be re-batched and resubmitted, delaying message delivery for a "route unable to deliver messages" scenario. This does not directly steal funds, but it is a repeatable, low-cost griefing vector that degrades liveness/availability of the messaging layer for arbitrary third-party users whose requests happen to be co-batched by a relayer.

### Likelihood Explanation
Likelihood is moderate: it requires observing a pending `handle_unsigned` extrinsic (or predicting a soon-to-time-out request) and racing a cheap unsigned transaction ahead of it — feasible for anyone monitoring the public mempool, and the transaction itself is free since `handle_unsigned` charges no fee. It does not require any privileged role, admin action, or governance compromise, and directly matches the "unprivileged relayer/dispatcher" reachable surface.

### Recommendation
Process each `PostRequest` inside a `RequestMessage.requests` independently (e.g., collect per-request results instead of short-circuiting on the first `Err`), so that one invalid/duplicate/timed-out request only fails that entry and does not abort or roll back the rest of the batch, consistent with how `EvmHost.dispatchIncoming` and `HyperbridgeLzEndpoint.onAccept` isolate per-message failures on the EVM side.

### Proof of Concept
1. A relayer builds a `RequestMessage` batching `PostRequest`s from users A and B via `batch_requests` and submits it as `handle_unsigned` (unsigned, visible pre-inclusion).
2. An attacker observes the pending extrinsic, extracts user A's request/proof pair, and submits a separate `handle_unsigned` containing only A's request, with higher/equal chance of inclusion first in the block.
3. Once A's request is delivered, the original batched extrinsic (still containing A + B) re-executes `handlers::request::handle`, hits `Error::DuplicateRequest` on A's entry inside the `for req in msg.requests.iter()` loop, and returns `Err` before B's request is dispatched.
4. `execute()`'s `collect::<Result<Vec<_>,_>>()` propagates the error, `#[frame_support::transactional]` rolls back the whole call, and B's otherwise-valid request is not delivered in that block, forcing the relayer to detect the failure and resubmit B alone later.

async fn batch_requests(
	ctx: &RetryContext,
	profitable: &[(PostRequest, Query)],
	height: StateMachineHeight,
) -> Result<Vec<Message>, anyhow::Error> {
	let dest_state_machine = ctx.dest.state_machine_id().state_id;
	let mut messages = vec![];

	for chunk in profitable.chunks(chunk_size(dest_state_machine)) {
		let (requests, queries): (Vec<_>, Vec<_>) = chunk.iter().cloned().unzip();
		let proof = ctx
			.hyperbridge
			.query_requests_proof(height.height, queries, dest_state_machine)
			.await?;

		messages.push(Message::Request(RequestMessage {
			requests,
			proof: Proof { height, proof },
			signer: ctx.dest.address(),
		}));
	}
