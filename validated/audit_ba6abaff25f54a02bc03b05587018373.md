### Title
Webhook `shop` (tenant identifier) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only returns the raw request body, so the HMAC verification performed by `Utils::HmacValidator` authenticates the body bytes only. [1](#0-0)  However, `Registry.process` extracts `shop`, `topic`, `webhook_id`, and `api_version` from unauthenticated HTTP headers and hands them to the app's `WebhookHandler` as trusted `WebhookMetadata` after only checking the HMAC succeeded. [2](#0-1)  The `shop` value used to identify the tenant is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` header and is never part of the signed content. [3](#0-2) 

### Finding Description
This mirrors the deflationary-token report's root cause pattern: an entity (there, transferred token amount; here, the `shop` field) is *acted upon* by downstream logic while the guard that is supposed to make it trustworthy (there, the pre/post balance check; here, the HMAC) does not actually cover it.

By contrast, the OAuth callback validator (`Auth::Oauth::AuthQuery`) does the correct thing: it includes `shop` inside the string that gets HMAC-signed, so a callback with a forged `shop` parameter fails verification. [4](#0-3)  The webhook `Request` class, which implements the same `Utils::VerifiableQuery` interface, does not follow this pattern — it signs only `@raw_body`, so `shop` is excluded from what the HMAC binds. [5](#0-4)  `Utils::HmacValidator.validate` simply computes `HMAC(secret, to_signable_string)` and compares it to the received `hmac`; it has no notion of "shop" at all. [6](#0-5) 

Critically, `Context.api_secret_key` (the value used as the HMAC key) is the app's single `client_secret`, shared across every shop that has installed the app — it is not a per-shop secret. [7](#0-6)  This means any merchant who has installed the app (an "unprivileged internet user" with respect to other tenants) can obtain a genuinely-signed webhook for their *own* shop (e.g., by creating/editing a resource that triggers a subscribed webhook, thereby fully controlling the raw body content within Shopify's schema), then replay that request to the app's webhook endpoint while swapping only the `x-shopify-shop-domain` header to name a victim shop. Because `to_signable_string` never includes `shop`, the HMAC still validates, and `Registry.process` builds `WebhookMetadata` using the attacker-supplied `shop` value and calls the app's `handler.handle(data:)` with it. [2](#0-1)  The equality that should hold — "shop bound in the signed payload" == "shop the handler acts on" — is broken: the library authenticates `body` but the handler acts on `shop`, a field it never verified against the signer's identity.

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` to select or scope the tenant record it updates (a documented, expected usage pattern of `WebhookHandler#handle`) can be made to write, delete, or process attacker-controlled body content under a victim shop's identity, since the shop attribution is fully unauthenticated. This is a cross-tenant data confusion/injection vector rooted entirely in this gem's own verification code, not in host-application misuse, because the gem is the component that (a) performs the HMAC check and (b) hands out the unauthenticated `shop` field as if it were part of the verified data.

### Likelihood Explanation
Exploitation requires only that the attacker control (or be able to install) one shop on the target app — a normal, unprivileged capability for any developer testing/using apps in the Shopify ecosystem — and the ability to send an arbitrary HTTP request with a forged `x-shopify-shop-domain` header to the app's public webhook endpoint, replaying a body they legitimately obtained a valid HMAC for. No access to `api_secret_key`, tokens, or victim credentials is needed.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the value that gets HMAC-verified, or otherwise cryptographically associate the `x-shopify-shop-domain` header with the signed body (e.g., include it in `to_signable_string`, similar to how `Auth::Oauth::AuthQuery` includes `shop`), and reject/flag any webhook whose header-derived shop cannot be tied to the verified signature.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and obtains a valid `access_token`/webhook subscription like any legitimate merchant.
2. Attacker triggers a subscribed webhook topic (e.g. `orders/create`) by creating an order with body content crafted to match whatever the app expects for a "victim" record (the raw JSON body is fully within the attacker's control since it's their own store's data).
3. Shopify sends the webhook to the app's endpoint with a correct `x-shopify-hmac-sha256` (computed over `raw_body` with the shared `api_secret_key`) and `x-shopify-shop-domain: attacker-shop.myshopify.com`.
4. Attacker replays this exact POST to the app's webhook endpoint, changing only the header `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
5. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes the HMAC over `@raw_body` only and succeeds, since the body is unchanged. [8](#0-7)  `Registry.process` then builds `WebhookMetadata.new(topic: request.topic, shop: request.shop, ...)` using the forged `shop` header and invokes the app's handler, which treats the payload as belonging to `victim-shop.myshopify.com`. [9](#0-8)

          received_signature = verifiable_query.hmac
