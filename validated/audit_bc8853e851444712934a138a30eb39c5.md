**Analysis:**

The premise is incorrect because `get_complete_result` is gated on `ledger_update_output`, not directly exposed right after `PartialStateComputeResult::new`: [1](#0-0) 

The method uses `self.ledger_update_output.get().map(...)` — it returns `None` unless the `ledger_update_output` `OnceCell` has already been set. In every call site (`block_executor/mod.rs::ledger_update` and `chunk_executor/mod.rs::update_ledger`), `set_state_checkpoint_output` is always invoked strictly before `set_ledger_update_output`: [2](#0-1) [3](#0-2) 

So by the time `get_complete_result()` can return `Some`, `state_checkpoint_output` is guaranteed to already be set — calling it "immediately after `PartialStateComputeResult::new`" (pre-checkpoint) is structurally impossible to produce a `Some` result; it will simply return `None`, and `expect_complete_result()` would panic rather than return a corrupted value.

Additionally, `execution_output` (which holds the actual write sets, including any `DispatchableTransferHook` writes) is immutable after VM execution completes; the state-checkpoint stage only computes state-summary/merkle roots derived from that same immutable `execution_output` — it does not independently "report" a different write-set value for the dispatch-hook field. There is no code path where checkpointing alters or re-derives the hook module address differently from what's in `execution_output`.

Finally, this is entirely internal executor pipeline sequencing logic (single-threaded per block, guarded by `OnceCell::set().expect(...)` which panics on double-set), not something reachable or influenced by an unprivileged transaction, package, view, authenticator, API, or proof input. It doesn't cross any custody boundary as required by the review scope.
