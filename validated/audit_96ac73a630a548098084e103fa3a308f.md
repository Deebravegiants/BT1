## Analysis

The reachable identity-binding gap is in the webhook receiver, not OAuth. The OAuth callback path (`ShopifyAPI::Auth::Oauth.validate_auth_callback` in `lib/shopify_api/auth/oauth.rb:60-113`) HMAC-covers `code`, `host`, `shop`, `state`, `timestamp` via `AuthQuery#to_signable_string` [1](#0-0) , so `shop` is bound to the signature there. The `JwtPayload` similarly binds `aud`/`dest` inside the JWT signature [2](#0-1) . Those paths are sound.

The webhook path is different: `Webhooks::Request#to_signable_string` returns only `@raw_body` [3](#0-2) , while `shop`, `topic`, `webhook_id`, and `api_version` are all read straight from HTTP headers that are never part of the HMAC-signed material [4](#0-3) . `Registry.process` validates only the body HMAC and then dispatches the handler using the unauthenticated `shop` header [5](#0-4) .

### Title
Webhook shop identity spoofing via unsigned `X-Shopify-Shop-Domain` header - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives `shop`, `topic`, `webhook_id`, and `api_version` from HTTP headers, but the HMAC signature validated by `ShopifyAPI::Utils::HmacValidator.validate` only covers the raw request body (`to_signable_string` returns `@raw_body`). `ShopifyAPI::Webhooks::Registry.process` accepts any request whose body HMAC validates with the app's `client_secret`, then trusts the unsigned `shop` header to build `WebhookMetadata` and route to the registered handler.

### Finding Description
The intended binding is: *the body validated by HMAC == the shop asserted for that body*. In practice the gem only proves "this body was HMAC'd with our `client_secret`" — it proves nothing about which shop the header claims to be from, since the header bytes are outside `to_signable_string`.

Because a single app's `client_secret` is shared across every shop that installs the app, any unprivileged internet user can install the target app on a shop they control (e.g., a free Shopify dev/partner store) and receive a batch of genuinely-signed webhooks from Shopify for their own shop (valid `hmac-sha256` header for a chosen body such as `orders/create`, `app/uninstalled`, etc.). Because the signature never covers `x-shopify-shop-domain`, `x-shopify-topic`, or `x-shopify-webhook-id`, the attacker can take that legitimately-signed body+HMAC pair and replay it directly to the app's public webhook endpoint while substituting the `shop-domain` header (and/or `topic`/`webhook-id`) with a victim shop's domain. `HmacValidator.validate` still passes because it only re-derives the signature from `@raw_body` [6](#0-5) [7](#0-6) , and `Registry.process` hands the forged `shop` straight to the handler [5](#0-4) .

Equality that should hold but doesn't: `hmac_signed_shop == request.shop`. What is actually checked: `hmac_signed_body == request.body`, with `request.shop` taken unauthenticated.

### Impact Explanation
This is a cross-tenant confusion vector: a host application that uses `WebhookMetadata#shop` to decide which tenant's data to mutate (e.g., process `app/uninstalled` to wipe a shop's stored session/data, or apply order/product webhook payloads to a shop record) can be made to apply an attacker-chosen, HMAC-valid payload against a victim shop identifier the attacker never legitimately received a webhook for. This satisfies the "cross-tenant access" high/critical impact bucket, since it lets an unprivileged attacker who merely installed the app on any shop cause the app to act on behalf of a different, victim tenant.

### Likelihood Explanation
Exploitation only requires: (1) ordinary ability to install the target app on any Shopify store (no special privilege, free dev stores are enough) to receive genuinely-signed webhooks, and (2) direct HTTP access to the app's public webhook endpoint to replay the captured body/HMAC with a swapped `shop-domain` header — both are unprivileged-internet-user actions with no need for the app's `client_secret`, an access token, or social engineering.

### Recommendation
Include the shop-identifying and topic/webhook-id headers in the HMAC-covered signable material (or otherwise cryptographically bind them, e.g. by including them in a canonicalized string used for signature verification), so that `Utils::HmacValidator.validate` fails if the `shop`, `topic`, or `webhook_id` are altered independently of the body. At minimum, `Webhooks::Request#to_signable_string` should incorporate `shop`, `topic`, and `webhook_id` alongside `@raw_body`.

### Proof of Concept
1. Install the target app on an attacker-controlled shop (`attacker.myshopify.com`) and enable a webhook topic such as `app/uninstalled`.
2. Capture the resulting webhook POST: raw body `B` and header `X-Shopify-Hmac-Sha256: H`, where `H = HMAC-SHA256(client_secret, B)`.
3. Replay a POST to the app's webhook endpoint with the same body `B` and header `H`, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and optionally adjust `X-Shopify-Topic`/`X-Shopify-Webhook-Id`).
4. `ShopifyAPI::Webhooks::Request#hmac` and `#to_signable_string` are unaffected by the header change, so `HmacValidator.validate` in `Registry.process` still returns true [8](#0-7) , and the handler executes with `shop: "victim.myshopify.com"` even though Shopify never sent this webhook for that shop.
