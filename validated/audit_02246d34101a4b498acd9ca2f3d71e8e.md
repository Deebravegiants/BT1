### Title
User-centric signup path bypasses backend enrollment/duplicate verification enforced by the standard signup path - (File: `src/plans/mod.rs`)

### Summary
`MasterPlan::do_signup` has two distinct code paths for finalizing a signup: the standard `enroll_user` path, which submits the signup to the backend and polls for the backend's uniqueness/fraud verdict, and a `user_centric_signup` path that determines success purely from local pipeline state without ever contacting the backend enrollment endpoint. Only the first path enforces the backend-side invariant (duplicate detection, in-flight match detection, backend fraud detection); the second path skips it entirely, mirroring the reported bug class where one privileged code path enforces an invariant while a parallel path bypasses it.

### Finding Description
In `do_signup`, after biometric capture and pipeline execution, the flow branches on `user_centric_signup`: [1](#0-0) 

When `user_centric_signup` is true (and `ignore_user_centric_signups` is not set), `success` is derived purely from the local `signup_reason` (i.e., whether the local biometric pipeline succeeded and local fraud detection - which is a no-op, see below - didn't flag it). The code explicitly synthesizes an `enroll_user::Status::Success`/`Error` without ever invoking `enroll_user`.

By contrast, the `else` branch calls `self.enroll_user(...)`, which drives `enroll_user::Plan::run`, submitting the signup via `signup_post::request` and then polling `signup_poll::request` in a loop: [2](#0-1) 

The comments in that polling loop make clear that this backend round-trip is where the actual invariant/uniqueness enforcement happens - it explicitly lists "Backend duplicates", "Backend inflight matches", and "Backend detected fraud" as reasons a signup is rejected server-side: [3](#0-2) 

The `user_centric_signup` branch never reaches this backend confirmation step at all, so none of these server-side invariant checks (duplicate/fraud detection) are applied before the Orb locally reports/records the signup as successful. This is structurally identical to the reported bug class: one path (`enroll_user`) is the sole enforcer of an invariant (uniqueness/fraud at the backend), while a second, equally-reachable path (`user_centric_signup`) is not subject to that enforcement, yet is treated as an equivalent, valid way to complete a signup.

Compounding this, local fraud detection itself is a stub that always returns `false`: [4](#0-3) 

so for the `user_centric_signup` branch, `signup_reason` will be `Normal` as long as the pipeline itself succeeds - there is no fraud/duplicate enforcement of any kind (neither local nor backend) gating that path.

### Impact Explanation
This allows a signup flagged as `user_centric_signup` to be recorded/treated locally as `SignupReason::Normal` / enrollment success, and to proceed to full PCP tier 0/1/2 upload, while completely bypassing the backend's duplicate-signup and fraud-detection invariant that the standard `enroll_user` path enforces for every other signup. This can lead to misattributed or duplicate signups being accepted as valid without the same fraud/duplicate checks other signups are subjected to, undermining the uniqueness invariant the enrollment backend is meant to guarantee.

### Likelihood Explanation
`user_centric_signup` is a normal field returned as part of the authenticated app/user QR data (`backend::user_status::UserData::user_centric_signup`) and is a supported production code path (app-centric vs. user-centric signup modes), not a debug/test-only flag. It is reachable in the standard signup flow whenever the backend returns this flag for a given user QR code, controlled by an `ignore_user_centric_signups` config toggle that defaults to allowing the bypass unless explicitly disabled: [5](#0-4) [6](#0-5) 

### Recommendation
Ensure the `user_centric_signup` path still performs (or is gated behind) the same backend-side duplicate/fraud enforcement that `enroll_user` performs, rather than deriving success solely from local pipeline state. At minimum, the Orb should not treat a user-centric signup as authoritative "success" without some backend confirmation equivalent to the `signup_poll` duplicate/fraud check, so both code paths are subject to the same invariant enforcement.

### Proof of Concept
1. Configure/obtain a user QR code whose backend-authenticated app data sets `user_centric_signup = true` (a supported, non-test production flag).
2. Complete biometric capture; ensure the local pipeline succeeds (fraud detection is a no-op per `detect_fraud`, so it will not block this).
3. In `do_signup`, since `user_centric_signup && !ignore_user_centric_signups`, the branch at `src/plans/mod.rs:639-645` sets `success = (signup_reason == SignupReason::Normal)` and reports `enroll_user::Status::Success` without ever calling `enroll_user`/`signup_post::request`/`signup_poll::request`.
4. The signup is thus marked as a successful enrollment locally and PCP data is uploaded, without the backend ever performing its duplicate/in-flight-match/fraud check that the standard path in `enroll_user.rs:157-176` relies on.
