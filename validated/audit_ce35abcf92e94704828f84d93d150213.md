### Title
Permissionless `CallDispatcher.dispatch()` allows theft of any ETH/token balance transiently or accidentally held by the shared dispatcher - (File: evm/src/utils/CallDispatcher.sol)

### Summary
`CallDispatcher` is a single, shared, unowned utility contract used by every `HyperFungibleToken`/`WrappedHyperFungibleToken` deployment (calldata execution on `onAccept`) and by `IntentGatewayV2`/`ExtrinsicIntents` (predispatch/postdispatch calldata) to run attacker/solver-supplied `Call[]` batches with tokens staged on it mid-transaction. Its `dispatch(bytes)` entry point is `external` with no caller restriction whatsoever.

### Finding Description [1](#0-0)  shows `dispatch` decodes a `Call[]` and low-level calls each target with the given value and calldata, with zero access control — any EOA or contract can invoke it directly, not just the apps that are supposed to own the flow. The contract also accepts arbitrary ETH via `receive() external payable {}` [2](#0-1) .

This dispatcher is intentionally shared and stateless-by-design: `HyperFungibleToken.onAccept` mints to a beneficiary then forwards `message.data` to it [3](#0-2) , and `IntentsBase._execute` / `IntentGatewayV2` stage escrowed/filled tokens on it before and after swaps [4](#0-3) [5](#0-4) . Deployments across the docs confirm one `CallDispatcher` address is reused by many apps and chains [6](#0-5) .

Because every legitimate flow briefly parks value on the dispatcher between its own `dispatch()` call and its own sweep-back `dispatch()` call, and because `receive()` accepts unsolicited ETH, any value that:
- is sent to the dispatcher directly (accidental transfer, or a griefer topping it up), or
- is left behind due to a partially-swept dust/rounding remainder from any app's sweep logic, or
- an attacker can otherwise cause to sit there even momentarily,

is stealable by anyone: an attacker just calls `CallDispatcher.dispatch()` directly with a `Call[]` that transfers the dispatcher's ETH/ERC20 balance to themselves. This is analogous to the POAP incident's root cause — a minting/administrative surface without proper caller authentication that anyone could invoke to move value out.

### Impact Explanation
The dispatcher is a shared component across all `HyperFungibleToken`/`WrappedHyperFungibleToken` deployments and every `IntentGatewayV2`/`ExtrinsicIntents` order that uses predispatch/postdispatch calldata on a given chain [7](#0-6) . Any ETH or ERC20 balance it holds outside of an in-flight, atomic call sequence — whether from accidental sends, dust, or a bug/edge case in any of its many callers' sweep logic — is permanently and trivially stealable by an unprivileged caller, meeting the "theft of funds" bar even though the impact is bounded to whatever balance transiently accrues on the dispatcher rather than the full escrow.

### Likelihood Explanation
Reachability requires no privilege: any address can call `dispatch()` directly, at any time, on the shared, well-known `CallDispatcher` address published in the contract-addresses docs [8](#0-7) . The `receive()` function guarantees the dispatcher can always be made to hold a stealable balance by anyone willing to send it ETH, and rounding/dust in the numerous sweep loops across `IntentsBase._execute`/`IntentGatewayV2` gives additional passive opportunities.

### Recommendation
Restrict `CallDispatcher.dispatch` to a caller allowlist (e.g., an `onlyAuthorizedCaller` modifier keyed to the set of `HyperFungibleToken`/`IntentGatewayV2`/`ExtrinsicIntents` deployments that are meant to use it), or make each app deploy/own its own dispatcher instance instead of sharing one permissionless singleton. Additionally consider rejecting unsolicited `receive()` ETH or sweeping/guarding any balance that persists between calls.

### Proof of Concept
1. Any user sends ETH directly to the known `CallDispatcher` address (accepted unconditionally via `receive()`), or dust is left over from a legitimate order's incomplete sweep.
2. Attacker calls `CallDispatcher.dispatch(abi.encode([Call({to: attackerContract, value: dispatcherBalance, data: ""})]))` directly — no `onlyHost`, no `onlyOwner`, no allowlist check exists in `dispatch()` [9](#0-8) .
3. The low-level `to.call{value: call.value}(call.data)` succeeds because `attackerContract` has code, moving the dispatcher's balance to the attacker.

    /**
     *  @dev reverts if the target is not a contract or if any of the calls reverts.
     */
    function dispatch(bytes memory encoded) external {
        Call[] memory calls = abi.decode(encoded, (Call[]));
        uint256 callsLen = calls.length;
        for (uint256 i = 0; i < callsLen; ++i) {
            Call memory call = calls[i];
            uint32 size;
            address to = call.to;
            assembly {
                size := extcodesize(to)
            }

            if (size == 0) {
                revert NotContract(to);
            }

            (bool success, bytes memory result) = to.call{value: call.value}(call.data);
            if (!success) revert CallFailed(to, result);
        }
    }

        PostRequest calldata request = incoming.request;

        bytes memory expectedSource = _supportedChains[request.source];
        if (expectedSource.length == 0) revert UnsupportedChain();
        if (keccak256(request.from) != keccak256(expectedSource)) revert UnauthorizedSource();

        Message memory message = abi.decode(request.body, (Message));
        address beneficiary = _toAddr(message.to);
        _mint(beneficiary, message.amount);

        if (message.data.length > 0) {
            ICallDispatcher(_dispatcher).dispatch(message.data);
        }

        emit Received({
            from: message.from,
            to: beneficiary,
            source: string(request.source),
            amount: message.amount
        });
