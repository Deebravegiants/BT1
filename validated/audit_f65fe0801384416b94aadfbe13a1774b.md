Based on my investigation, `SimplexPaymaster.sol` is the strongest reachable analog: gas payment (bandwidth purchase) via any registered ERC-20 depends entirely on `nativeOracle` and each token's `tokenOracle` (single Chainlink feed each), with no fallback source. If either feed goes stale or returns a non-positive answer, `_getOraclePrice` reverts, which cascades through `_tokenPrice` → `_fetchDetails` → `_validatePaymasterUserOp`, freezing gas payment for every UserOp that uses that token, for every user, until governance intervenes.

### Title
Single-oracle dependency in SimplexPaymaster freezes ERC-20 gas payment when the Chainlink feed is stale or invalid - (File: evm/src/utils/SimplexPaymaster.sol)

### Summary
`SimplexPaymaster` prices ERC-20 gas payment using exactly one Chainlink `AggregatorV3Interface` feed per side (native/USD and token/USD), with no secondary oracle or fallback pricing mechanism. A stale or invalid answer from either feed makes `_getOraclePrice` revert, which unconditionally reverts every UserOp validation that pays gas with that token.

### Finding Description
`_tokenPrice` calls `_getOraclePrice` for both `nativeOracle` and the per-token `cfg.tokenOracle`: [1](#0-0) 

`_getOraclePrice` reverts on non-positive answers or staleness beyond `maxOracleAge`: [2](#0-1) 

This is invoked from `_fetchDetails`, which is called during ERC-4337 validation for every UserOp using this paymaster: [3](#0-2) 

There is no alternate oracle, TWAP fallback, or cached-price fallback anywhere in the contract; `nativeOracle` and each `TokenConfig.tokenOracle` are the sole price sources for the entire ERC-20 gas-payment feature, as documented in the contract's own comment: "Price conversion uses two Chainlink feeds: token/USD and nativeAsset/USD." [4](#0-3) 

This mirrors the referenced report's bug class exactly: a project-critical function (`USSD.mintForToken`/`USSDRebalancer.rebalance()` in the external report; here, `_validatePaymasterUserOp`/gas payment in `SimplexPaymaster`) is entirely gated on data from a single oracle for each side of the price, with no backup source, so one oracle malfunction (feed halted, sequencer down, staleness threshold exceeded) disables the function for everyone.

### Impact Explanation
Any Chainlink feed disruption (a paused/deprecated feed, a chain-specific heartbeat outage, or a sequencer/oracle node failure) causes `latestRoundData` to return a stale `updatedAt` or non-positive `answer`. Once that happens, `_getOraclePrice` reverts for every call, so no UserOp can be validated with the affected token through this paymaster — freezing the "bandwidth purchase" (gas payment) path for all users of that token until governance replaces the oracle via a `RequestKind.RegisterToken`/`UpdateParams` governance round-trip (`onAccept`, relayed through Hyperbridge). This is a denial-of-service on an unprivileged, permissionless entry point with no self-healing mechanism and no redundancy.

### Likelihood Explanation
Chainlink feed staleness/outages are a realistic, externally-triggerable event (not attacker-controlled), and the contract's own `maxOracleAge` bound (up to `MAX_ORACLE_AGE` = 7 days per governance config) shows staleness is an anticipated failure mode, yet no fallback is implemented — only a revert. Any transient feed issue on either the native or the token oracle is sufficient to trigger the freeze, making likelihood moderate-to-high over the contract's operational lifetime.

### Recommendation
Introduce a secondary price source (e.g., a second independent Chainlink feed, a Uniswap TWAP fallback, or a last-known-good cached price with a bounded validity window) so that a single oracle's staleness or invalid answer does not unconditionally disable gas payment for a registered token. At minimum, allow governance to temporarily deactivate a token via the existing `DeactivateToken` path without requiring the oracle call itself to succeed, and/or expose a manual price-override governance action gated by the same `onAccept` authentication already used for `RegisterToken`/`UpdateParams`.

### Proof of Concept
1. Governance registers token `T` with `tokenOracle = O` via `RegisterToken`: `_registerToken` stores `TokenConfig{tokenOracle: O, ...}` (see `evm/src/utils/SimplexPaymaster.sol:392-397`).
2. Feed `O` (or `nativeOracle`) stops updating for longer than `maxOracleAge` (or the aggregator returns `answer <= 0`, e.g. during a Chainlink incident).
3. Any user submits a UserOp with `paymasterData` selecting token `T`; the EntryPoint calls `validatePaymasterUserOp` → `_validatePaymasterUserOp` → `super._validatePaymasterUserOp` → `_fetchDetails` → `_tokenPrice` → `_getOraclePrice(O, ...)`.
4. `_getOraclePrice` reverts with `StaleOraclePrice`/`InvalidOraclePrice` (as exercised by `testStaleOracleReverts`/`testNonPositiveOraclePriceReverts` in `evm/tests/foundry/SimplexPaymasterTest.t.sol:245-263`), causing the entire UserOp to fail validation.
5. This repeats for every UserOp attempting to pay gas in token `T` (or any token, since `nativeOracle` is shared) until governance intervenes — a full freeze of ERC-20 gas payment functionality with no automatic recovery.

    function _tokenPrice(TokenConfig memory cfg) internal view returns (uint256) {
        uint256 nativeUsd = _getOraclePrice(nativeOracle, nativeOracleDecimals);
        uint256 tokenUsd = _getOraclePrice(cfg.tokenOracle, cfg.tokenOracleDecimals);

        return (nativeUsd * (10 ** cfg.tokenDecimals) * (10_000 + markupBps)) / (tokenUsd * 10_000);
    }

    /// @dev Fetch a Chainlink price normalized to 8 decimals.
    ///      Reverts on stale or non-positive answers.
    function _getOraclePrice(AggregatorV3Interface oracle, uint8 oracleDecimals) internal view returns (uint256) {
        (, int256 answer,, uint256 updatedAt,) = oracle.latestRoundData();

        if (answer <= 0) revert InvalidOraclePrice(address(oracle), answer);
        if (block.timestamp - updatedAt > maxOracleAge) {
            revert StaleOraclePrice(address(oracle), updatedAt);
        }

        if (oracleDecimals < 8) {
            return uint256(answer) * (10 ** (8 - oracleDecimals));
        } else if (oracleDecimals > 8) {
            return uint256(answer) / (10 ** (oracleDecimals - 8));
        }
        return uint256(answer);
    }
