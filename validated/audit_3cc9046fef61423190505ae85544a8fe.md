Confirmed: the webhook HMAC signable string is only the raw body, while `shop`, `topic`, `webhook_id`, and `api_version` are all taken from unauthenticated HTTP headers and passed straight to the handler as trusted tenant-identifying data.### Title
Webhook `shop` (and `topic`/`webhook_id`) header is not covered by the HMAC, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw request body [1](#0-0) , while `Registry.process` trusts `request.shop`, `request.topic`, and `request.webhook_id`, which are read directly from unauthenticated `X-Shopify-*` headers [2](#0-1) , and hands them to the app's webhook handler as the tenant identity for that event [3](#0-2) . The HMAC (`Utils::HmacValidator.validate`) only proves the body byte content was produced by someone who knows `Context.api_secret_key`; it says nothing about which shop, topic, or webhook the body belongs to [4](#0-3) .

### Finding Description
The binding the library implicitly claims to guarantee is:

`request.shop (delivered to handler) == shop that actually originated the HMAC-signed payload`

But the actual check only verifies:

`HMAC(raw_body, api_secret_key) == received_hmac`

`shop-domain`, `topic`, and `webhook-id` headers are never included in `to_signable_string`, so they are "acted on but not covered by the HMAC."

For a public/multi-tenant Shopify app, `Context.api_secret_key` is the same for every installed shop — it is an app-level secret, not a per-shop secret. Any merchant who installs the app on their own store is a legitimate holder of valid `(raw_body, hmac)` pairs for webhooks Shopify sends to their shop (e.g. by triggering an `orders/create` or `app/uninstalled` webhook on their own store and capturing the raw POST). Because the HMAC only signs `raw_body`, the same `(raw_body, hmac)` pair remains valid regardless of which `shop-domain`/`topic`/`webhook-id` header accompanies it.

An attacker who controls their own shop-side webhook delivery (e.g. by proxying/replaying the HTTP request they legitimately received from Shopify, or by controlling network delivery of their own webhook) can therefore submit that same body+HMAC to the app's webhook endpoint with a forged `X-Shopify-Shop-Domain` header naming a victim shop, and `Registry.process` will accept it as HMAC-valid and dispatch it to the handler tagged with the victim's domain [5](#0-4) .

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce for the host application: webhook handlers built on top of this gem key their tenant-scoped side effects (updating shop records, marking apps uninstalled, processing GDPR redact requests, updating order/product state, etc.) off `WebhookMetadata#shop`, which this gem populates straight from the unauthenticated header. An attacker can inject arbitrary attacker-chosen payload content (any topic body they can legitimately generate for their own store) and have it attributed to any victim shop domain, achieving cross-tenant data injection/spoofing without ever needing the victim's or the app's access token. This matches the Critical bucket "cross-tenant access."

### Likelihood Explanation
Likelihood is bounded by the fact that the attacker must be able to supply a valid `(raw_body, hmac)` pair, which in the normal delivery path only Shopify's servers can produce for an arbitrary body. However, since `Context.api_secret_key` is shared across all shops of a public app, any merchant/attacker who installs the app on their own store becomes a valid oracle for `(raw_body, hmac)` pairs for their own store's webhook traffic, and the only field they need to change to attack another tenant is the unsigned `shop-domain` header. This is a realistic "unprivileged internet user" (any merchant able to install the app) path, not merely theoretical, but it does require the attacker to intercept/replay their own webhook delivery (e.g., via a controlled reverse proxy or by driving the actual HTTP request through their own infrastructure) rather than being trivially exploitable over the open internet with zero setup.

### Recommendation
Include `shop-domain`, `topic`, and `webhook-id` (in addition to the raw body) in the HMAC-signed payload used by `to_signable_string`, or otherwise cryptographically bind the shop domain to the signed bytes (e.g., verify the shop domain against a value derived from a signed/authenticated source, not merely an HTTP header) so that `HmacValidator.validate` fails if any of these attacker-controlled headers are altered independently of the body they were originally delivered with.

### Proof of Concept
```ruby
# Attacker installs the app on their own shop "attacker-shop.myshopify.com" and
# receives a legitimate webhook delivery for it, e.g.:
raw_body = '{"id":1,"note":"hello"}'
real_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), ShopifyAPI::Context.api_secret_key, raw_body)
encoded_hmac = Base64.encode64(real_hmac)

# Attacker replays this exact (raw_body, hmac) pair to the app's webhook endpoint,
# but swaps the shop-domain header to the victim's shop:
forged_headers = {
  "x-shopify-topic" => "orders/create",
  "x-shopify-hmac-sha256" => encoded_hmac,
  "x-shopify-shop-domain" => "victim-shop.myshopify.com", # forged, not covered by HMAC
  "x-shopify-webhook-id" => "attacker-chosen-id",
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# This succeeds because HmacValidator only checks raw_body against the shared api_secret_key:
ShopifyAPI::Webhooks::Registry.process(request)
# => handler.handle is invoked with WebhookMetadata(shop: "victim-shop.myshopify.com", ...)
#    even though the payload actually originated from the attacker's own shop.
```
