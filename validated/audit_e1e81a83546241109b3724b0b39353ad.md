### Title
`AuroraEngineBridge.describeWithdrawal` unconditionally reports `completed` without checking whether the Aurora Engine `FunctionCall` actually succeeded - ([File: packages/intents-sdk/src/bridges/aurora-engine-bridge/aurora-engine-bridge.ts])

### Summary
`AuroraEngineBridge.describeWithdrawal` is a zero-argument stub that always returns `{status: "completed", txHash: null}`, regardless of whether the `ft_withdraw` intent's `receiver_id` (`auroraEngineContractId` or `proxyTokenContractId`) actually accepted the NEP-141 transfer on its virtual-chain deposit logic. `watchWithdrawal` treats any `"completed"` response as final success and resolves the withdrawal promise, so a caller relying on the SDK's status has no way to detect a failed/reverted deposit into the virtual chain.

### Finding Description
The broken equality is: *reported SDK status* == *actual outcome of the cross-contract `ft_transfer_call` to `auroraEngineContractId`/`proxyTokenContractId`*.

`createWithdrawalIntents` builds an `ft_withdraw` intent whose `receiver_id` is the caller-controlled `routeConfig.auroraEngineContractId` (or `proxyTokenContractId`) and whose `msg` encodes the destination address [1](#0-0) . Executing this intent triggers a NEP-141 `ft_transfer_call` from `intents.near` to that receiver; the receiver's `ft_on_transfer` (and its `resolve_transfer` callback) run as subsequent NEAR receipts, asynchronous with respect to the original intent-publishing transaction. A NEAR transaction can report `SuccessValue` even though a downstream receipt in that same call chain later fails and the token amount is refunded — the outer transaction's success says nothing about whether the deposit into the virtual chain actually landed.

`describeWithdrawal` never inspects any of this: [2](#0-1) 

It takes no arguments and performs no NEAR RPC call, no receipt inspection, and no comparison against `args.tx.hash` or any indicator of the Aurora Engine deposit's true outcome. `watchWithdrawal` simply polls this method and, on `status === "completed"`, immediately resolves the withdrawal as done [3](#0-2) .

None of the existing guards intervene at this stage: `supports()` only checks `routeConfig.route` and asset standard [4](#0-3) ; `validateWithdrawal` only validates that the destination address is a well-formed Ethereum-style address [5](#0-4) . Neither checks whether the Aurora Engine contract will actually accept the deposit. There is no post-hoc receipt-status check anywhere in this bridge.

### Impact Explanation
An integrator that treats the SDK's `"completed"` status as ground truth for "funds landed on the virtual chain" will release the paired leg of a cross-chain flow (e.g., in an atomic-swap or bridging-forwarding integration) even when the Aurora Engine deposit reverted and the tokens were refunded back into the `intents.near` balance instead of reaching the destination virtual-chain address. This is a status misreport that can cause an integrator to credit/release funds it should not have, matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. It is fully repeatable on every VirtualChain-routed withdrawal, since the stub never varies its output.

### Likelihood Explanation
Preconditions are minimal and attacker-cost is low: any ordinary user can select the `VirtualChain` route with an `auroraEngineContractId`/`proxyTokenContractId` (from `routeConfig`, which per the audit's threat model is attacker/counterparty-supplied) and a destination address that passes the loose Ethereum-format check in `validateWithdrawal` but is rejected or causes `ft_on_transfer` to panic on the receiving contract's virtual-chain deposit logic. No special privileges, RPC compromise, or relayer misbehavior is needed — the divergence exists purely because `describeWithdrawal` is a stub with no verification logic at all.

### Recommendation
Implement `describeWithdrawal` to actually verify the deposit outcome: fetch the NEAR transaction/receipt (`args.tx.hash`) via `this.nearProvider`, inspect the full receipt chain for the `ft_transfer_call` to `auroraEngineContractId`/`proxyTokenContractId`, confirm the `ft_on_transfer`/`resolve_transfer` outcome indicates the token was accepted (not refunded), and only then return `{status: "completed", ...}`; otherwise return `{status: "failed", reason: ...}` (mirroring how `HotBridge`/`OmniBridge`/`PoaBridge` perform real status verification instead of stubbing).

### Proof of Concept
```ts
// aurora-engine-bridge.describeWithdrawal.test.ts
import { AuroraEngineBridge } from "./aurora-engine-bridge";

it("reports completed regardless of on-chain outcome", async () => {
  const bridge = new AuroraEngineBridge({
    envConfig: mockEnvConfig,
    nearProvider: mockNearProviderWhereFtTransferCallFailedAndWasRefunded, // mocked HTTP RPC only
  });

  const status = await bridge.describeWithdrawal(); // zero args, matches production call site
  // Broken equality demonstrated: reported status ("completed")
  // does NOT equal actual on-chain outcome (refunded/failed deposit).
  expect(status).toEqual({ status: "completed", txHash: null });
});
```
This test requires only mocking the NEAR RPC provider (HTTP) to simulate a transaction whose `ft_transfer_call` to the Aurora Engine contract was refunded/failed, and shows `describeWithdrawal` never consults that mock at all — it is unconditionally `"completed"`.

	async supports(
		params: Pick<WithdrawalParams, "assetId" | "routeConfig">,
	): Promise<boolean> {
		if (params.routeConfig == null || !this.is(params.routeConfig)) {
			return false;

		const assetInfo = parseDefuseAssetId(params.assetId);
		const isValid = assetInfo.standard === "nep141";

		if (!isValid) {
			throw new UnsupportedAssetIdError(
				params.assetId,
				"`assetId` does not match `routeConfig`.",
			);

	}
