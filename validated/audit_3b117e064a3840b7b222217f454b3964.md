### Title
`LockupFactory::create` derives lockup account deterministically from `owner_account_id` only, allowing front-running that permanently strips foundation vesting/termination control - (File: `lockup-factory/src/lib.rs`)

### Summary
### Finding Description
This is a valid analog of the Folks Finance `loanId` griefing report: an unprivileged, front-runnable identifier is used to claim a unique on-chain resource before the intended (legitimate) party's transaction lands, but here the consequence is worse than a simple revert - it results in an irrevocable loss of the Foundation's contractual clawback/termination rights, not merely griefing.

`LockupFactory::create` is a public, payable method callable by anyone with no caller/owner restriction: [1](#0-0) 

The target lockup account name is derived **solely** from `owner_account_id`:
```
let byte_slice = env::sha256(owner_account_id.as_ref().as_bytes());
let lockup_account_id = format!("{}.{}", hex::encode(&byte_slice[..20]), env::current_account_id());
```
This is fully deterministic and predictable by anyone who knows (or guesses) the target `owner_account_id`, and does not depend on `vesting_schedule`, `foundation_account_id`, or the caller's identity.

Whether the Foundation gets attached as a controlling party depends entirely on whether the caller supplies a `vesting_schedule`: [2](#0-1) 

And the lockup contract's own `new()` constructor enforces that `foundation_account_id` can only be set **if** a vesting schedule is present: [3](#0-2) 

Because `Promise::new(lockup_account_id).create_account()` can only succeed once per account name, whoever's `create()` transaction lands **first** for a given `owner_account_id` permanently determines the lockup's vesting/foundation configuration. Any unprivileged actor (including the intended `owner_account_id` itself, or a colluding third party) can front-run the Foundation's legitimate `create()` call - which would normally attach `vesting_schedule` and `foundation_account_id` - by submitting their own `create()` call first with `vesting_schedule = None`, `foundation_account_id = None`, and the minimum required deposit (`MIN_ATTACHED_BALANCE`). The Foundation's subsequent legitimate transaction for that same `owner_account_id` will fail on `create_account()` and be reverted with the deposit refunded via `on_lockup_create`: [4](#0-3) 

If the Foundation (unaware its factory `create()` call failed, or attempting to work around it) instead transfers the intended token allocation directly to the now-existing account, those funds land in a lockup contract that has `VestingInformation::None` and no `foundation_account_id`, meaning `terminate_vesting` (which requires `assert_called_by_foundation`) can never be invoked because there is no foundation configured, and the owner can withdraw the full balance once the (attacker-chosen, potentially very short) `lockup_duration`/`lockup_timestamp` passes, with no clawback possible.

### Impact Explanation
This maps to the "Critical: Permanent freezing, unrecoverable lock, or irrevocable loss of user or protocol funds in ... vesting termination ... flows" and "High: state-transition bypass in lockup ... flows that lets an unprivileged user perform actions beyond intended authority" categories. An unprivileged actor (potentially the intended employee/owner themselves) can permanently and irrevocably strip the Foundation's contractually-granted vesting termination rights over funds intended for a specific `owner_account_id`, before the Foundation's real deployment transaction executes. This is a genuine core-contracts root cause (not present only in the external Solidity report) reachable purely via the public `create` entrypoint on `lockup-factory/src/lib.rs`.

### Likelihood Explanation
Likelihood is high in any workflow where a third party (e.g. the NEAR Foundation) uses `lockup-factory` to deploy lockups on behalf of employees/grantees whose `owner_account_id` is known or predictable ahead of the on-chain transaction (e.g., announced/negotiated account names, or observed in the mempool as a pending transaction). Any unprivileged party — including the employee themselves — can precompute the deterministic address and race the legitimate creation transaction with a minimal-deposit, vesting-free `create()` call.

### Recommendation
Do not allow an unprivileged, arbitrary caller to determine or race to claim a lockup account for a given `owner_account_id`. Options: restrict `create()` (or at least the ability to omit `vesting_schedule`/`foundation_account_id`) to a privileged/foundation caller via `assert_called_by`-style checks; or incorporate a factory-controlled nonce/caller-restriction into the account derivation so the account name/config cannot be front-run by unprivileged callers before the intended privileged creation completes; or require the Foundation to explicitly co-sign/pre-register intended `owner_account_id` + vesting parameters before any public `create()` call is allowed to succeed for that name.

### Proof of Concept
Not independently reproduced (would require a live/local NEAR runtime), but the exploit trivially follows from the code:
1. Attacker (or the employee/owner in question) computes `lockup_account_id = sha256(owner_account_id)[..20] || "." || factory_account_id` off-chain — identical to the logic in `lockup-factory/src/lib.rs:119-121`.
2. Attacker calls `create(owner_account_id, lockup_duration, lockup_timestamp, vesting_schedule=None, release_duration, whitelist_account_id)` with `attached_deposit = MIN_ATTACHED_BALANCE`, before the Foundation's intended `create()` call (with a real `vesting_schedule`) is processed.
3. Attacker's `create_account()` promise succeeds first, deploying the lockup contract at the deterministic address with `VestingInformation::None` and no `foundation_account_id` (enforced by `lockup/src/lib.rs:216-233`).
4. The Foundation's later `create()` call for the same `owner_account_id` fails at `create_account()` (account already exists) and is refunded via `on_lockup_create`, per `lockup-factory/src/lib.rs:171-198`.
5. Any subsequent funds sent to that lockup account are permanently exempt from `terminate_vesting`, since `assert_called_by_foundation` in `lockup/src/foundation.rs:15-19` can never be satisfied (no foundation account configured), and no other API exists to retroactively attach a foundation/vesting schedule.

```rust
    pub fn on_lockup_create(
        &mut self,
        lockup_account_id: AccountId,
        attached_deposit: U128,
        predecessor_account_id: AccountId,
    ) -> bool {
        assert_self();

        let lockup_account_created = is_promise_success();

        if lockup_account_created {
            env::log(
                format!("The lockup contract {} was successfully created.", lockup_account_id)
                    .as_bytes(),
            );
            true
        } else {
            env::log(
                format!(
                    "The lockup {} creation has failed. Returning attached deposit of {} to {}",
                    lockup_account_id, attached_deposit.0, predecessor_account_id
                )
                    .as_bytes(),
            );
            Promise::new(predecessor_account_id).transfer(attached_deposit.0);
            false
        }
    }
```
