### Title
`findMatchingWithdrawal` matches by `assetId` only, so `describeWithdrawal` returns the wrong withdrawal's status/txHash for batches with repeated same-token withdrawals - (File: `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts`)

### Summary
`PoaBridge.describeWithdrawal` resolves each `WithdrawalIdentifier` by calling `getWithdrawalStatusWithRetry` (which fetches all withdrawals for the batch tx hash) and then `findMatchingWithdrawal`, which selects the first entry whose `nep141:<near_token_id>` equals the requested `assetId`. If a batch contains two or more withdrawals of the same token (same `assetId`) to different destinations/amounts, both `WithdrawalIdentifier`s resolve to the same (first-matching) entry, so an integrator can see `completed`/a `txHash` for a payout that actually went to the other destination.

### Finding Description
The broken equality: `describeWithdrawal(identifier_A).txHash` should correspond to the on-chain withdrawal whose destination/amount match `identifier_A.withdrawalParams`, not to whichever entry happens to match on `assetId` alone.

Code path:
- `describeWithdrawal` (`poa-bridge.ts:313-343`) calls `getWithdrawalStatusWithRetry(args)` which fetches **all** withdrawals for `args.tx.hash` (`poa-bridge.ts:352-358`) — a single POA transaction hash can bundle multiple withdrawal intents.
- It then calls `findMatchingWithdrawal(response.withdrawals, args.withdrawalParams.assetId)` (`poa-bridge.ts:319-322`, `418-427`), which does `withdrawals.find((w) => nep141:${w.data.near_token_id} === assetId)` — this only checks the token, never the destination address, memo, or amount.
- The function's own doc comment admits the limitation: *"multiple withdrawals of the same token in a single transaction are not supported"* (`poa-bridge.ts:409-417`).
- Nothing upstream (`supports()`, `validateWithdrawal()`, `createWithdrawalIntents()`) rejects batches with two withdrawals of the same `assetId`; the SDK builds and signs such batches without restriction.

Exploit flow: an integrator/user submits a batch withdrawal containing two `nep141:plasma.omft.near` withdrawals, one to destination X (amount 100) and one to destination Y (amount 50). Both produce `WithdrawalIdentifier`s with the same `assetId`. When polling completion via `waitForWithdrawalCompletion` → `describeWithdrawal`, `Array.prototype.find` returns the same underlying withdrawal record (e.g., the one for destination X, which completed) for **both** identifiers. The identifier for Y (which may still be pending, failed, or resolved to a different `transfer_tx_hash`) is reported as `completed` with X's `txHash`. An integrator relying on this status could credit the user for Y's withdrawal using X's proof, or believe both are done when only one has landed.

Existing guards do not prevent this: `validateAddress`/`compareAddresses` only validate a single destination against the token's own address, not cross-withdrawal disambiguation; `supports()` and `validateWithdrawal()` operate per-withdrawal-param and never inspect the whole batch for duplicate `assetId`s; there is no batch-level dedup/sort-by-amount fallback actually implemented (the comment only proposes it as a future TODO, not code).

### Impact Explanation
This is a status/hash misreport: the wrong `txHash` and `status` (`completed`) get attached to a `WithdrawalIdentifier` that does not correspond to that transfer. Any integrator (e.g., custodial exchange, off-ramp) that credits/refunds a user's off-chain balance based on `describeWithdrawal`/`waitForWithdrawalCompletion` output could credit the wrong recipient or double-report completion for a payout that hasn't landed at its real destination — matching the "status or hash misreport making an integrator credit or refund twice" High-severity category. This is repeatable for every batch containing ≥2 same-token withdrawals.

### Likelihood Explanation
Preconditions: attacker (an ordinary user or a counterparty whose params an integrator forwards) constructs/submits a withdrawal batch with two or more `nep141:plasma.omft.near` (or any POA token) withdrawal intents to different destinations. No special privilege or bridge misbehavior is required — this is purely an SDK-side matching bug exercised through normal, permitted batch composition. Feasibility is high (batch withdrawal is a supported feature per `docs/design/rfc-batch-withdrawal-granular-control.md`), and the bug triggers deterministically once `findMatchingWithdrawal` sees ≥2 entries with the same `near_token_id`.

### Recommendation
Disambiguate `findMatchingWithdrawal` by more than `assetId`: match on `assetId` plus destination address (and amount/memo where available) from `args.withdrawalParams`, or track withdrawals by a POA-side per-intent identifier if the API exposes one. At minimum, if multiple candidates match on `assetId`, either: (a) sort both the API withdrawals and the local batch's same-asset entries by amount (as the code comment proposes) and pair them positionally, or (b) throw/return an unresolvable status rather than silently picking the first match, and reject (or warn loudly) batch construction that contains duplicate `assetId`s until this is fixed.

### Proof of Concept
Vitest plan (mock only the HTTP client `poaBridge.httpClient.getWithdrawalStatus`):
1. Mock `getWithdrawalStatus` to return two withdrawal entries for the same `near_token_id` ("plasma"), e.g.:
   - Entry 1: `{ status: "COMPLETED", data: { near_token_id: "plasma.omft.near", transfer_tx_hash: "0xAAA", destination_address: "X", amount: "100" } }`
   - Entry 2: `{ status: "PENDING", data: { near_token_id: "plasma.omft.near", destination_address: "Y", amount: "50" } }`
2. Build two `WithdrawalIdentifier`s from the same batch tx hash, one with `withdrawalParams.destinationAddress = "X"` and one with `"Y"`, both `assetId = "nep141:plasma.omft.near"`.
3. Call `poaBridge.describeWithdrawal(identifierX)` and `poaBridge.describeWithdrawal(identifierY)`.
4. Assert the broken equality: both calls return `{ status: "completed", txHash: "0xAAA" }` (i.e. identical results), even though identifierY's real withdrawal is still `PENDING` with no `transfer_tx_hash`.
5. Expected fix behavior: `describeWithdrawal(identifierY)` should return `{ status: "pending" }` (matched correctly to entry 2), distinct from `identifierX`'s `completed`/`0xAAA` result.
