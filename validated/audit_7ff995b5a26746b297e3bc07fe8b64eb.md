### Title
POA Bridge withdrawal status/hash misreported for batched same-asset withdrawals - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves the destination status and transaction hash of a specific withdrawal (identified by NEAR tx hash + index) using `findMatchingWithdrawal`, which matches purely on `assetId` and ignores the withdrawal `index`, `amount`, and `destinationAddress`. When a single NEAR transaction contains more than one withdrawal of the same token (e.g. two `nep141:btc.omft.near` withdrawals to two different destination addresses, batched via `IntentsSDK.processWithdrawal`/`createWithdrawalIntents`), the function can return the wrong entry from the unsorted POA API response, causing the wrong `status`/`txHash` to be reported for a given `WithdrawalIdentifier`.

### Finding Description
`findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` (lines 409-427) is documented in its own comment as matching "only by assetId," explicitly stating that "multiple withdrawals of the same token in a single transaction are not supported": [1](#0-0) 

`describeWithdrawal` (lines 313-343) calls this matcher with only `args.withdrawalParams.assetId`, discarding `args.index`, `args.withdrawalParams.destinationAddress`, and `args.withdrawalParams.amount`, all of which are available on the `WithdrawalIdentifier`: [2](#0-1) 

The SDK explicitly supports batched withdrawals for multiple `WithdrawalParams` in one NEAR transaction (`sdk.createWithdrawalIntents` iterates bridges per withdrawal and each is tracked separately by index via `createWithdrawalIdentifier`). The POA API response list is documented in-code as "unsorted." Because the match key is only `assetId`, if two withdrawals in the same batch use the same token but different destination addresses/amounts, `Array.prototype.find` returns the **first** matching entry in API order for both `WithdrawalIdentifier`s (index 0 and index 1), so `watchWithdrawal`/`waitForWithdrawalCompletion` (in `packages/intents-sdk/src/core/withdrawal-watcher.ts`) can report withdrawal #1's completion status and destination `txHash` for withdrawal #0 (and vice-versa), breaking the equality that "the status/hash reported for withdrawal X" must be "the on-chain outcome of withdrawal X."

The equivalent function also exists in `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts` (lines 144-153), with the same assetId-only matching, used independently of index: [3](#0-2) 

### Impact Explanation
An integrator that submits a batched withdrawal containing two same-asset transfers to two different destination addresses (a valid, supported use case per the SDK's batch APIs) can receive a "completed" status carrying the wrong destination `txHash` for one of the withdrawal legs. Since integrators typically use the reported `txHash`/status to confirm delivery and release custody, credit an off-chain balance, or close a support ticket, a misattributed hash could cause an integrator to believe the wrong leg completed — potentially crediting/refunding a withdrawal that hasn't actually landed, or conversely treating a genuinely completed withdrawal as still pending because its status got attributed to a different index. This matches the "status or hash misreport making an integrator credit or refund twice" impact category. It does not itself move funds, but it corrupts the completion signal integrators rely on to release/credit funds.

### Likelihood Explanation
Likelihood is only realized when a caller batches ≥2 withdrawals of the **same** `assetId` in the same NEAR transaction/`processWithdrawal` batch, which is a legitimate, unprivileged, integrator-driven scenario (no malicious actor is required — it's an ordinary caller usage pattern the SDK does not prevent). The code comment itself acknowledges the API doesn't guarantee order and the SDK doesn't dedupe/validate against this case, so the condition can arise under normal operation rather than requiring an attacker.

### Recommendation
Extend `findMatchingWithdrawal` (in both `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts` and `packages/internal-utils/src/poaBridge/waitForWithdrawalCompletion.ts`) to disambiguate entries sharing the same `assetId` using additional fields returned by the POA API (e.g., `destinationAddress`/`address`, `amount`) combined with the withdrawal `index`, instead of matching on `assetId` alone. At minimum, when multiple candidates match the same `assetId`, either fail closed (return `pending`/throw an invariant error) rather than silently picking an arbitrary one, or require the caller to pass enough distinguishing criteria (destination address + amount) to guarantee a 1:1 match before reporting `completed`.

### Proof of Concept
1. Call `sdk.processWithdrawal`/`sdk.createWithdrawalIntents` with two `withdrawalParams` entries both using `assetId: "nep141:btc.omft.near"`, but `destinationAddress: "addrA"` for index 0 and `destinationAddress: "addrB"` for index 1, in a single batch (single NEAR tx).
2. The POA bridge processes both withdrawals; suppose withdrawal to `addrB` (index 1) completes first while `addrA` (index 0) is still pending.
3. Call `bridge.describeWithdrawal` for `WithdrawalIdentifier` at `index: 0` (destination `addrA`). Because `poaBridge.httpClient.getWithdrawalStatus` returns an unsorted `withdrawals` array and `findMatchingWithdrawal` only checks `nep141:${w.data.near_token_id} === assetId`, `Array.prototype.find` can return the entry for `addrB`'s completed withdrawal.
4. `describeWithdrawal` returns `{ status: "completed", txHash: "<addrB's tx hash>" }` for the `WithdrawalIdentifier` that actually corresponds to `addrA`, which is still pending — an integrator monitoring index 0 for `addrA` sees a "completed" status/hash that has nothing to do with `addrA`'s transfer. 	async describeWithdrawal(
		args: WithdrawalIdentifier & { logger?: ILogger },
	): Promise<WithdrawalStatus> {
		const response = await this.getWithdrawalStatusWithRetry(args);

		// Response list is unsorted, so we match by assetId instead of index
		const withdrawal = findMatchingWithdrawal(
			response.withdrawals,
			args.withdrawalParams.assetId,
		);

		if (withdrawal == null) {
			return { status: "pending" };
		}

		if (withdrawal.status === "PENDING") {
			return { status: "pending" };
		}

		if (withdrawal.status === "COMPLETED") {
			return {
				status: "completed",
				txHash: withdrawal.data.transfer_tx_hash,
			};
		}

		return {
			status: "failed",
			reason: withdrawal.status,
		};
	}

/**
 * Finds a withdrawal matching the given assetId.
 *
 * NOTE: Currently only matches by assetId. This means multiple withdrawals
 * of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: WithdrawalStatusResponse["withdrawals"],
	assetId: string,
): WithdrawalStatusResponse["withdrawals"][number] | undefined {
	// POA bridge only supports NEP-141 tokens. The API returns `near_token_id`
	// (e.g., "zec.omft.near") which we prefix with "nep141:" to match assetId format.
	// Note: `defuse_asset_identifier` cannot be used as it contains chain-native
	// format (e.g., "zec:mainnet:native") which differs from the assetId format.
	return withdrawals.find((w) => `nep141:${w.data.near_token_id}` === assetId);
}

/**
 * Finds a withdrawal matching the given criteria.
 *
 * NOTE: Currently only matches by assetId (near_token_id). This means multiple
 * withdrawals of the same token in a single transaction are not supported.
 * POA API doesn't currently support this case either. When support is added,
 * matching could be done by sorting both API results and withdrawal params by
 * amount (fees are equal for same token, so relative ordering is preserved).
 */
function findMatchingWithdrawal(
	withdrawals: types.WithdrawalStatusResponseOk["result"]["withdrawals"],
	criteria: WithdrawalCriteria,
):
	| types.WithdrawalStatusResponseOk["result"]["withdrawals"][number]
	| undefined {
	return withdrawals.find(
		(w) => `nep141:${w.data.near_token_id}` === criteria.assetId,
	);
}
