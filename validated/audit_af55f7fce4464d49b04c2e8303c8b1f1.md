### Title
Webhook `shop-domain` header is not covered by HMAC verification, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so `Utils::HmacValidator.validate` verifies body integrity but never binds the `shop-domain` header to the HMAC. `Registry.process` still trusts `request.shop` (taken straight from that unverified header) as the tenant identity handed to the app's webhook handler, breaking the equality `shop(HMAC-covered) == shop(acted upon)`.

### Finding Description
The webhook `Request` class implements `VerifiableQuery` and defines: [1](#0-0) 
`hmac` decodes the `X-Shopify-Hmac-Sha256` header, and `to_signable_string` returns only `@raw_body`. The `shop` accessor simply returns the `shop-domain` header value with no cryptographic binding.

`HmacValidator.validate_signature` computes the signature exclusively over `verifiable_query.to_signable_string` (the body) and compares it against the received HMAC: [2](#0-1) 

`Registry.process` gates handling on this HMAC check, but then forwards `request.shop` — the unauthenticated header — directly to the handler as the tenant identity: [3](#0-2) 

Because the app's `client_secret` is the same for every shop that installs the app, any shop under the attacker's control receives legitimate, correctly-HMAC-signed webhook deliveries whose HMAC is computed only from the JSON body. The attacker can capture (or fully script, since they control the store data that produces the body) one such `(raw_body, hmac)` pair from their own store, then replay that exact `(raw_body, hmac)` payload to the app's webhook endpoint while substituting an arbitrary `X-Shopify-Shop-Domain` header (e.g., a victim's `myshopify.com` domain). `HmacValidator.validate` still returns `true` since it never inspects the header, and `Registry.process` calls the handler with `WebhookMetadata.shop` set to the forged victim domain.

### Impact Explanation
This crosses a tenant boundary: the gem hands the app-level webhook handler a `shop` value that the attacker fully controls despite HMAC verification passing, letting a merchant/attacker who has installed the app on their own shop inject webhook events “as” an arbitrary other shop (cross-tenant data confusion/corruption in any app logic keyed by `data.shop`, e.g. session lookup, order/product writes, notification routing). This matches the Critical "cross-tenant access" category since the field an app relies on for tenant attribution (`shop`) is not part of the identity binding the gem enforces.

### Likelihood Explanation
Any developer who has installed the app on a shop they control can produce a valid `(body, hmac)` pair by triggering a real event (e.g. update a product) on their own store, then simply re-POST that captured body/HMAC to the app's public webhook endpoint with a different `shop-domain` header. No secret knowledge or privileged access is required beyond running a normal, unprivileged app install — a capability inherent to any Shopify Partner/dev-store account.

### Recommendation
Bind the shop identity into the value that is HMAC-verified, or otherwise cross-check the header-derived `shop` against a value obtained from a trusted, per-tenant source (e.g., look up the registered webhook subscription/session by `webhook_id` and compare its shop, or require the shop to match the shop associated with a previously stored session) before trusting `WebhookMetadata.shop` downstream. At minimum, document/require that the `shop-domain` header is untrusted for tenant attribution and that consuming apps must re-derive the shop from a securely obtained session rather than the webhook payload.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger any subscribed event so Shopify sends a webhook: capture `raw_body` and `X-Shopify-Hmac-Sha256` from the real request (both are fully attacker-influenced/known since the attacker owns the shop content and shares the app's `client_secret` across all installs).
3. Replay the exact same body and HMAC header to the app's webhook endpoint, but replace `X-Shopify-Shop-Domain` with `victim-shop.myshopify.com`.
4. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)` which passes (HMAC only covers the body), then invokes the handler with `WebhookMetadata.new(..., shop: "victim-shop.myshopify.com", ...)`, causing the app to process attacker-supplied data under the victim's tenant identity.
