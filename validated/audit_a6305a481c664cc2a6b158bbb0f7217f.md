### Title
SSRF / client_secret exfiltration via unsanitized `shop` in OAuth callback - (File: `lib/shopify_api/auth/oauth.rb`)

### Summary
`ShopifyAPI::Auth::Oauth.validate_auth_callback` builds the token-exchange request URL from `auth_query.shop` without ever passing it through `Utils::ShopValidator.sanitize!`, unlike the sibling flows `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token`, which explicitly validate the shop domain before using it. [1](#0-0) [2](#0-1) [3](#0-2) 

### Finding Description
The identity binding that should hold is: `shop` verified by `ShopValidator.sanitize!` == `shop` used to build the URL that receives `client_secret`. In `validate_auth_callback`, the HMAC check via `Utils::HmacValidator.validate(auth_query)` only proves `auth_query.shop`/`host`/`code`/`state`/`timestamp` were signed with the app's own `api_secret_key` — it does not prove that `shop` is an actual `*.myshopify.com` (or other trusted) domain. [4](#0-3) [5](#0-4)  The unsanitized `auth_query.shop` is then fed straight into `auth_base_uri(shop)`, which builds `"https://#{shop}/admin"`, and the client posts a body containing `client_secret: Context.api_secret_key` to that URL. [6](#0-5) [7](#0-6)  By contrast, both `ClientCredentials.client_credentials` and `RefreshToken.refresh_access_token` call `validated_shop = Utils::ShopValidator.sanitize!(shop)` and use `validated_shop` for the session used by the HTTP client, restricting the outbound host to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS` (`shopify.com`, `myshopify.io`, `myshopify.com`, `spin.dev`, `shop.dev`) or an app-configured `myshopify_domain`. [8](#0-7) 

### Impact Explanation
If a host application's OAuth callback controller ever constructs an `AuthQuery` where `shop` can diverge from a validated trusted domain (e.g. a shop value that legitimately reaches this code path but is not re-checked as a myshopify domain, such as through custom domain redirects, proxying, or code paths that reuse `validate_auth_callback` outside the exact Shopify-redirect flow), `client_secret` and the OAuth `code` are sent to an attacker-influenced host — this is SSRF with credential leakage of the app's `client_secret` to a non-Shopify origin (High/Critical depending on reachability).

### Likelihood Explanation
In the strict, textbook OAuth redirect flow, `shop` and the HMAC are both generated by Shopify using the shared secret, so a fully unprivileged attacker cannot forge `auth_query` end-to-end without the secret — matching the gem's documented API. However, the inconsistency itself is a real defect: this function is the only OAuth/token credential-sending path in the gem that omits the `ShopValidator.sanitize!` call present in the two structurally identical sibling flows (`client_credentials.rb`, `refresh_token.rb`), so any future or host-side code path that constructs `AuthQuery` from data not fully equivalent to Shopify's signed redirect (which the gem does not itself enforce beyond the HMAC) loses the domain-allowlist protection those other flows have. I could not find a code path in this gem where `AuthQuery.shop` is set from fully unauthenticated attacker input reaching `validate_auth_callback` directly — the missing validation is a defense-in-depth/consistency gap rather than a demonstrated end-to-end unprivileged bypass in the gem's own documented usage.

### Recommendation
Add `Utils::ShopValidator.sanitize!(auth_query.shop)` in `validate_auth_callback` before building `null_session`/`auth_base_uri`, mirroring `client_credentials.rb` and `refresh_token.rb`, so the shop domain used to receive `client_secret` is always constrained to `ShopValidator::TRUSTED_SHOPIFY_DOMAINS`.

### Proof of Concept
Not demonstrable as a fully unprivileged, credential-independent exploit within this gem alone: `auth_query.shop` in the legitimate flow is bound by the Shopify-computed HMAC over `to_signable_string` (`code, host, shop, state, timestamp`), which requires knowledge of `api_secret_key` to forge [9](#0-8) . The concrete, verifiable defect is the code asymmetry itself: `oauth.rb` sends `client_secret` to `auth_base_uri(auth_query.shop)` with no `ShopValidator` call [6](#0-5) , while `client_credentials.rb` and `refresh_token.rb` do call `Utils::ShopValidator.sanitize!(shop)` before doing the same [10](#0-9) [11](#0-10) .

        def validate_auth_callback(cookies:, auth_query:)
          unless Context.setup?
            raise Errors::ContextNotSetupError, "ShopifyAPI::Context not setup, please call ShopifyAPI::Context.setup"
          end
          raise Errors::InvalidOauthError, "Invalid OAuth callback." unless Utils::HmacValidator.validate(auth_query)
          raise Errors::UnsupportedOauthError, "Cannot perform OAuth for private apps." if Context.private?

          state = cookies[SessionCookie::SESSION_COOKIE_NAME]
          raise Errors::NoSessionCookieError unless state

          raise Errors::InvalidOauthError,
            "Invalid state in OAuth callback." unless state == auth_query.state

          null_session = Auth::Session.new(shop: auth_query.shop)
          body = {
            client_id: Context.api_key,
            client_secret: Context.api_secret_key,
            code: auth_query.code,
            expiring: Context.expiring_offline_access_tokens ? 1 : 0, # Only applicable for offline tokens
          }

          client = Clients::HttpClient.new(session: null_session, base_path: "/admin/oauth")
          response = begin
            client.request(
              Clients::HttpRequest.new(
                http_method: :post,
                path: "access_token",
                body: body,
                body_type: "application/json",
              ),
            )
          rescue ShopifyAPI::Errors::HttpResponseError => e
            raise Errors::RequestAccessTokenError,
              "Cannot complete OAuth process. Received a #{e.code} error while requesting access token."
          end
