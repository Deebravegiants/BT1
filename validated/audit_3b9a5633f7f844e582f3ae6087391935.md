### Title
Webhook Shop Attribution Not Covered by HMAC Signature Enables Cross-Tenant Webhook Spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw body only, while the `shop`, `topic`, `webhook_id`, and `api_version` values used to route and attribute the webhook are taken from unauthenticated HTTP headers. `Utils::HmacValidator.validate` only verifies that the *body* matches the HMAC, then `Registry.process` unconditionally trusts `request.shop` to build the `WebhookMetadata` handed to the app's handler. This breaks the identity binding `hmac_verified_bytes == bytes_used_for_shop_attribution`.

### Finding Description
`to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop`, `topic`, `webhook_id` and `api_version` are all read straight from headers with no cryptographic binding to the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC over the body, but then dispatches to the handler using `request.shop`, `request.topic`, and `request.webhook_id` verbatim — none of which were part of what was verified: [3](#0-2) 

`HmacValidator.validate` confirms this: it only checks `verifiable_query.to_signable_string` (the body) against the HMAC secret, never the headers: [4](#0-3) 

Because the app's `api_secret_key` (`client_secret`) is shared across every merchant installation of the app (it is not per-shop), any merchant who installs the app can legitimately receive a genuinely HMAC-signed webhook body for their own shop. That attacker-merchant can then replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and optionally `x-shopify-topic`/`x-shopify-webhook-id`) header with a victim shop's domain. `HmacValidator.validate` still succeeds because it only checks the body, and `Registry.process` will hand the (attacker-controlled) body to the handler tagged with the victim's shop. This is the same class of bug as the referenced report: a field ("shop"/attribution) is *acted upon* by the code but is *not covered* by the integrity check ("HMAC"), so the two get out of sync and identity/tenant attribution can be forged — `shop_verified_by_hmac == shop_used_for_dispatch` is false.

### Impact Explanation
This allows cross-tenant webhook spoofing: a malicious or compromised merchant (who has valid access to the shared app secret's HMAC via their own legitimate webhook deliveries) can cause the host application to process attacker-controlled webhook data attributed to a different shop. Depending on how the host app's handler uses `WebhookMetadata#shop` (e.g., to look up a session/tenant, trigger data mutations, or delete records "on behalf of" that shop), this can lead to cross-tenant data corruption or unauthorized actions performed against another merchant's data — matching the "cross-tenant access" impact category.

### Likelihood Explanation
Requires the attacker to be an app-installing merchant (not requiring `api_secret_key` leakage, TLS interception, or social engineering) who intercepts/records one of their own genuine webhook deliveries and replays it with a modified `shop-domain` header to the app's public webhook endpoint. This is a realistic, low-effort attack path reachable purely through this gem's own webhook verification logic.

### Recommendation
Include the shop domain (and ideally topic/webhook-id/api-version) in the HMAC-signable string, or otherwise cryptographically bind them to the verified payload, so that `Utils::HmacValidator.validate` fails if any of these routing/attribution headers are altered relative to what Shopify actually signed. At minimum, `to_signable_string` should incorporate the shop domain header alongside the raw body before verification in `lib/shopify_api/webhooks/request.rb`.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a legitimate webhook, e.g. `orders/create` with body `{"id":1}`, correctly signed as `HMAC(client_secret, "{\"id\":1}")` and header `x-shopify-shop-domain: attacker.myshopify.com`.
2. Attacker POSTs the identical body and HMAC header to the app's webhook endpoint, but sets `x-shopify-shop-domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Request.new` parses headers/body; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the HMAC (`lib/shopify_api/utils/hmac_validator.rb:12-31`; `lib/shopify_api/webhooks/request.rb:35-38`).
4. `Registry.process` invokes `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` with `shop == "victim.myshopify.com"` (`lib/shopify_api/webhooks/registry.rb:198-199`), even though the payload was never actually sent by Shopify for that shop.
