### Title
Legacy/unauthenticated user QR-code format allows misattributed signup binding via unverified `user_id` - ([File: src/plans/qr_scan/user.rs], [File: src/backend/user_status.rs], [File: src/backend/signup_post.rs])

### Summary
The reported `OmoRouter.transferFrom()` bug is caused by trusting a caller-supplied identity parameter (`from`) instead of deriving it from the authenticated caller. orb-core has an analogous trust-boundary defect in the legacy user-QR-code signup path: the `user_id` bound to a signup is taken directly from an unauthenticated, attacker-craftable QR-code string, with no cryptographic proof tying the presenter to that identity, and the backend response path explicitly allows proceeding without any `user_data_hash` verification for this format.

### Finding Description
`qr_scan::user::Data::try_parse` accepts three QR encodings. The legacy `QR_CODE_V2` format is matched purely by a regex against `userid:<uuid>:<data_policy>` and produces a `Data` with `user_data_hash: None`: [1](#0-0) 

In `backend::user_status::request`, when the backend does *not* return both `backend_keys` and `authenticated_app_data` (the self-custody/encryption keys), the code falls into the "old QR-code format" branch, which explicitly skips the `user_data_hash` verification (`verify()` call) that is otherwise mandatory: [2](#0-1) [3](#0-2) 

The only condition guarding this fallback is `qr_code.user_data_hash.is_some()` — since the legacy QR format never sets that field, this check is always trivially satisfied and the flow proceeds with `UserData` containing no cryptographic keys and `user_centric_signup: false`. That `user_id` (whatever value the presented QR encoded) then flows unmodified through `handle_user_qr_code` / `verify_user_qr_code` into the final signup request: [4](#0-3) 

and is submitted to the backend as the authoritative `userId` for the biometric enrollment, alongside the operator's `distributorId`: [5](#0-4) 

At no point in this legacy path is there proof that the person standing in front of the Orb (whose iris/face biometrics are actually captured) is the rightful owner of `user_id`. This mirrors the `OmoRouter.transferFrom(from, to, amount)` root cause: an actor identity (`from` / `user_id`) is accepted as untrusted external input and used to authorize/attribute a privileged operation, instead of being cryptographically bound to the entity performing the action.

### Impact Explanation
An attacker who crafts a QR code of the form `userid:<victim-uuid>:<data_policy>` (a plain regex-matched string requiring no signature, key, or backend-issued token) can present it to the Orb, complete their own biometric capture, and have the resulting Personal Custody Package/enrollment request submitted to the backend tagged with the victim's `user_id`. This is a concrete misattributed/unauthorized signup and identity-binding failure: the victim's account can be bound to biometric data that is not theirs (or vice versa, depending on backend-side account state), which is exactly the kind of cross-identity state-bleed impact analogous to the unauthorized `transferFrom` in the original report.

### Likelihood Explanation
Likelihood is high for any deployment path where the backend does not universally require the newer authenticated/self-custody QR format (`decode_qr` with `user_data_hash`) — i.e., wherever the legacy fallback branch in `user_status::request` is reachable (older app versions, accounts without self-custody keys provisioned, or backend responses lacking `backend_keys`/`authenticated_app_data`). No privileged access, credentials, or hardware access is required — only the ability to generate/print a QR code with an arbitrary UUID.

### Recommendation
Reject or fail closed on legacy QR codes lacking `user_data_hash` once cryptographic self-custody binding is available, or require the backend to always return `authenticated_app_data`/`backend_keys` and hash-verify the identity before allowing any biometric enrollment to be attributed to `user_id`. Do not allow the "old QR-code format" branch to silently pass through unauthenticated identity binding for current, non-legacy backend flows.

### Proof of Concept
1. Attacker obtains any victim UUID that matches the `userid:<uuid>:<data_policy>` format (this identifier is not secret and is commonly displayed/transmitted as part of normal app flows).
2. Attacker generates and prints/displays a QR code encoding `userid:<victim-uuid>:<data_policy>`.
3. Attacker approaches an Orb, scans the operator QR code as normal, then presents their crafted user QR code and completes their own iris/face capture.
4. `qr_scan::user::Data::try_parse` parses it via the `QR_CODE_V2` regex path with `user_data_hash: None`.
5. `backend::user_status::request` falls into the "old QR-code format" branch (no hash verification performed) and returns `UserData` with `user_centric_signup: false`.
6. `signup_post::request` submits the attacker's biometric-derived data with `userId: <victim-uuid>` to the backend, misattributing the signup. [6](#0-5)
