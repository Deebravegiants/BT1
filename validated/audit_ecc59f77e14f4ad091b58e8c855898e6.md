### Title
Webhook `shop`, `topic`, `api_version`, and `webhook_id` metadata are not covered by the HMAC signature, allowing cross-tenant identity spoofing on replayed webhooks - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook solely by HMAC-checking the raw request body, then hands the handler a `WebhookMetadata` struct built from unauthenticated HTTP headers (`shop`, `topic`, `webhook_id`, `api_version`). Because the HMAC signable string is only the raw body, none of those header-derived identity fields are bound to the signature that "authenticates" the request.

### Finding Description
`Webhooks::Registry.process` is the sole authorization gate for inbound webhooks: [1](#0-0) 

It calls `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string` and secure-compares it to the `hmac` header: [2](#0-1) 

For `Webhooks::Request`, `to_signable_string` returns only `@raw_body` — it does not include `shop`, `topic`, `webhook_id`, or `api_version`, all of which are parsed straight from attacker-controllable HTTP headers with no further validation: [3](#0-2) [4](#0-3) 

After the HMAC check passes, `process` builds the identity metadata handed to the host application's handler entirely from these unauthenticated headers: [5](#0-4) [6](#0-5) 

The binding that should hold is: `shop_HMAC-authenticated == shop_delivered-to-handler`. In this implementation that equality does not hold — the HMAC only proves "a raw body was signed with the app's shared `api_secret_key`" (which is common to every shop that has installed the app), while `shop` (and `topic`/`webhook_id`) are trusted verbatim from headers that are outside the signed scope. This is the same class of bug as the reported issue: a value that is *acted on* downstream (fee calculation there, tenant identity here) is not part of the value that was actually cryptographically verified.

### Impact Explanation
Because the app's `api_secret_key` is shared across all shops that install the app, any merchant/attacker who has installed the app can obtain a validly-HMAC'd webhook body for their own shop (e.g., by triggering an event on their own store, or via a partner-development store). They can then replay that request to the app's webhook endpoint while substituting the `x-shopify-shop-domain` (and/or `x-shopify-topic`, `x-shopify-webhook-id`) header with a different shop's domain. `HmacValidator.validate` still passes because it only checks the (unmodified) body, and `Registry.process` will still deliver a `WebhookMetadata` claiming to be from the victim shop. If the host application uses `data.shop` to select which stored session/access token to act on (a very common and Shopify-recommended pattern), this results in **cross-tenant confusion**: data or actions attributable to shop A can be attributed to/acted on shop B, or a handler can be tricked into looking up and using a different merchant's stored access token/session based on attacker-supplied `shop`.

### Likelihood Explanation
Exploitability requires: (1) the attacker controls or has access to at least one shop that has installed the target app (to obtain a validly-signed body/HMAC pair), and (2) the app's webhook endpoint is reachable to accept arbitrary headers with a replayed, previously-valid body/HMAC pair (no timestamp/topic/shop binding or replay protection exists in this HMAC check). Both conditions are realistic for any public or freemium Shopify app. Note this mirrors Shopify's own documented HMAC scheme (body-only signing), so the root cause is a broader identity-binding gap that this gem's API does nothing to close before handing data to the host handler.

### Recommendation
Bind the identity-critical fields into the signable string (or otherwise cryptographically or structurally verify them) before trusting them, e.g.:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string`, or
- Have `Registry.process` cross-check `request.shop` against an expected/registered shop for that webhook subscription, or reject metadata that isn't independently verifiable, and
- Document to consumers of `WebhookMetadata` that `shop` is not currently authenticated, so they can add their own verification (e.g., confirm the shop has an active, matching session) rather than blindly trusting it for access-token lookups.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com`; Shopify sends a webhook with body `B` and header `x-shopify-hmac-sha256: HMAC(secret, B)`.
2. Attacker captures this request and replays it to the app's webhook endpoint, changing only:
   - `x-shopify-shop-domain: victim-shop.myshopify.com`
   - (optionally) `x-shopify-topic`, `x-shopify-webhook-id`
   while keeping body `B` and the original HMAC header unchanged.
3. `Utils::HmacValidator.validate` recomputes `HMAC(secret, B)` (per `lib/shopify_api/utils/hmac_validator.rb` and `Webhooks::Request#to_signable_string` returning only `@raw_body`) and it matches — validation passes.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, even though the body actually originated from `attacker-shop.myshopify.com`, per `lib/shopify_api/webhooks/registry.rb` lines 189-199.
5. Any host-app logic keyed off `data.shop` (e.g., "look up victim-shop's access token and act on its behalf") now operates under attacker influence.

        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|

          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
