### Title
Consensus-incentives reward rate change applies retroactively to already-accrued, unpaid block spans — relayers underpaid or treasury overpaid - ([File: modules/pallets/consensus-incentives/src/impls.rs])

### Summary
`pallet-consensus-incentives` pays relayers for delivering ISMP consensus updates based on a per-state-machine `CostPerBlock` rate multiplied by the number of blocks the update advances since the last rewarded height. Governance can change `CostPerBlock` at any time via `update_cost_per_block`, and the reward for any span of blocks that has already elapsed but not yet been settled (i.e. delivered/rewarded) is computed using whatever rate is current at settlement time — not the rate that was in effect while those blocks were produced. This is the same class of bug as the Perennial finding: past accrual should be settled against the old rate before the rate changes; here it isn't.

### Finding Description
The reward calculation lives in `Pallet::calculate_reward` and `Pallet::process_message`: [1](#0-0) 

`calculate_reward` reads the *current* `StateMachinesCostPerBlock::<T>::get(state_machine_id)` value and multiplies it by `latest_height - baseline`, where `baseline` is the `LastRewardedHeight` watermark left over from the last successful reward: [2](#0-1) 

The dispatchable that changes the rate applies unconditionally and immediately, with no settlement of any pending/unrewarded block span beforehand: [3](#0-2) 

Because `LastRewardedHeight` only advances when a `ConsensusMessage` is actually delivered and processed through `on_executed`, the state-machine's remote height can advance for a long time (many blocks produced, no relayer has yet delivered/settled a consensus update) while `CostPerBlock` is changed one or more times by governance in between. When the next delivery finally lands and `process_message`/`calculate_reward` runs, it pays `(latest_height - baseline) * <current CostPerBlock>` for the *entire* unpaid span — including the sub-span of blocks that elapsed under the old rate. There is no per-segment accounting or settlement checkpoint tied to the rate change itself (only tied to delivery events).

This mirrors the reported Perennial bug exactly: a rate parameter (`makerRewardRate`/`longRewardRate`/`shortRewardRate` there, `CostPerBlock` here) governs reward accrual over an elapsed span, and changing the parameter is not preceded by settling the reward already accrued under the old rate. The `LastRewardedHeight` watermark plays the role of Perennial's "last settled version" — but it only advances on delivery, not on rate change, so a rate change silently reprices a backlog.

### Impact Explanation
- If governance lowers `CostPerBlock` (e.g., in response to token price appreciation or cost reduction), any relayer who already advanced the state machine under the old, higher rate but has not yet submitted the consensus proof that triggers settlement is retroactively underpaid for that span — a loss of the reward they earned/expected under the rate in force while they did the work.
- If governance raises `CostPerBlock`, the pending backlog is paid out at the new, higher rate for blocks that accrued under the old, lower rate — an unintended treasury drain (`T::TreasuryAccount` pays more BRIDGE/relayer-incentive tokens than governance intended when it set the old rate).
- Because delivery of consensus updates for slow-moving or infrequently-monitored state machines can lag significantly (there's no forced minimum settlement cadence), the size of the mispriced backlog is state-machine dependent and can be large, especially right after a `set_id` rotation or long dormancy, amplifying either the underpayment or the treasury drain.
- This is reachable by any relayer simply delivering a consensus proof (an unprivileged, permissionless action) — the vulnerability doesn't require a malicious actor, only a normal governance rate update landing between two ordinary relayer deliveries.

### Likelihood Explanation
Medium likelihood: `update_cost_per_block` is a normal governance operation expected to occur periodically as token economics change, and the `on_executed`/`process_message` settlement path is driven purely by whenever a relayer happens to deliver the next consensus proof, which is not synchronized with governance's rate changes. Any window where a `CostPerBlock` update happens while a state machine has an unsettled block span (which is the common case, since `LastRewardedHeight` lags `latest_height` between deliveries) triggers the mispriced payout.

### Recommendation
Before mutating `StateMachinesCostPerBlock`, settle any outstanding, unrewarded block span for every affected state machine at the old rate (or at minimum snapshot the effective rate alongside `LastRewardedHeight` so `calculate_reward` can split a spanning interval into old-rate and new-rate sub-segments using a rate-change height). Alternatively, force `update_cost_per_block` to also update `LastRewardedHeight` to the state machine's current latest known height (paying out the pending balance at the *old* rate first), ensuring the new rate only applies going forward from the update.

### Proof of Concept
1. Governance sets `StateMachinesCostPerBlock[SM] = 100` and a relayer delivers a consensus update advancing `SM` from height 0 to height 50 (via `on_executed` → `process_message` → `calculate_reward`), paying `50 * 100 = 5000` and setting `LastRewardedHeight[SM] = 50`.
2. The remote chain continues producing blocks; Hyperbridge's view of `SM`'s `latest_commitment_height` (via light-client/consensus tracking) advances to 150, but no relayer submits a new consensus message yet (delivery not yet triggered), so `LastRewardedHeight` stays at 50.
3. Governance calls `update_cost_per_block(SM, 10)` (rate cut) via `Pallet::update_cost_per_block` — no settlement occurs, `LastRewardedHeight` is untouched: [4](#0-3) 
4. A relayer now delivers the consensus proof covering the advance to height 150. `calculate_reward` computes `(150 - 50) * 10 = 1000` instead of the `(100 * 100) = 10000` that would reflect blocks 50-150 having elapsed mostly under the old rate — the relayer is paid 1000 instead of what would be owed if the rate cut had first settled the pre-existing backlog at 100/block.

	fn process_message(
		state_machine_height: StateMachineHeight,
		state_machine_id: StateMachineId,
		relayer_account: T::AccountId,
	) -> Result<(), Error<T>> {
		if let Some(block_cost) = StateMachinesCostPerBlock::<T>::get(state_machine_id) {
			let reward = Self::calculate_reward(&state_machine_id, block_cost)?;

			if reward.is_zero() {
				return Ok(());
			}

			T::Currency::transfer(
				&T::TreasuryAccount::get().into_account_truncating(),
				&relayer_account,
				reward,
				Preservation::Expendable,
			)
			.map_err(|_| Error::<T>::RewardTransferFailed)?;

			Self::deposit_event(Event::<T>::RelayerRewarded {
				relayer: relayer_account.clone(),
				amount: reward,
				state_machine_height,
			});

			T::ReputationAsset::mint_into(&relayer_account, reward.saturated_into())
				.map_err(|_| Error::<T>::ReputationMintFailed)?;

			LastRewardedHeight::<T>::mutate(state_machine_id, |watermark| {
				*watermark = Some(watermark.unwrap_or_default().max(state_machine_height.height));
			});
		}
		Ok(())
	}

	/// Calculate the reward for a message based on the state machine id
	fn calculate_reward(
		state_machine_id: &StateMachineId,
		block_cost: <T as pallet_ismp::Config>::Balance,
	) -> Result<<T as pallet_ismp::Config>::Balance, Error<T>> {
		let host = <T::IsmpHost>::default();
		let latest_height = host
			.latest_commitment_height(state_machine_id.clone())
			.map_err(|_| Error::<T>::CouldNotGetStateMachineHeight)?;
		let previous_height =
			host.previous_commitment_height(state_machine_id.clone()).unwrap_or_default();

		// Use the rewarded watermark as the baseline and fall back to the previous height until
		// the first reward is recorded for this chain. The watermark only moves forward, so a
		// height that is rolled back and later resubmitted is not paid for a second time.
		let baseline = LastRewardedHeight::<T>::get(state_machine_id).unwrap_or(previous_height);

		let blocks = latest_height.saturating_sub(baseline);

		let blocks_as_balance: <T as pallet_ismp::Config>::Balance = blocks.saturated_into();
		let reward = blocks_as_balance.saturating_mul(block_cost);

		Ok(reward)
	}

### Reward Mechanism

* **Trigger**: The incentive process is triggered when the `on_executed` hook from the `FeeHandler` trait is called. The pallet filters for `ConsensusMessage` types.
* **Relayer Identification**: The pallet cryptographically recovers the relayer's public key from the signature attached to the `ConsensusMessage` to identify who should receive the reward.
* **Reward Calculation**: The reward is calculated based on how much "progress" a consensus update represents. The formula is:
  
  ```latex
    Reward=(LatestHeight - PreviousHeight) * CostPerBlock
  ```
    * **LatestHeight & PreviousHeight**: These values are fetched from the `IsmpHost` and represent the latest and previously known heights of the remote state machine.
    * **CostPerBlock**: This is a configurable value stored in the `StateMachinesCostPerBlock` map that defines the reward amount per block for each state machine.
* **Reward Distribution**: The calculated reward amount is transferred from the `TreasuryAccount` to the identified relayer.
* **Reputation Minting**: Alongside the token reward, the pallet mints a `ReputationAsset` of the same value to the relayer as an on-chain record of their contributions.

### Dispatchable Functions

* `update_cost_per_block(origin, state_machine_id, cost_per_block)`: A privileged extrinsic used to set or update the reward cost per block for a given state machine.
