### Title
Webhook shop-domain identity is not bound by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` accepts a webhook as authentic once `Utils::HmacValidator.validate(request)` succeeds, but the HMAC only covers the raw request body — never the `shop`/`shop-domain` header that the gem hands to the app's handler as the trusted tenant identifier. An attacker who possesses one valid `(raw_body, hmac)` pair from any shop that has the app installed (e.g. their own store) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop, and the gem will still report the webhook as valid and hand it to the handler tagged with the victim's shop.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`shop` is read straight from an unauthenticated header and is never part of that signable string: [2](#0-1) 

`HmacValidator.validate_signature` computes the HMAC purely over `to_signable_string` (i.e. the body) and time-safe-compares it to the supplied `hmac`; it has no knowledge of, and does not bind, the shop header at all: [3](#0-2) 

`Registry.process` relies solely on this HMAC check before trusting `request.shop` and forwarding it, unmodified, to the app's handler as the authoritative tenant identity: [4](#0-3) 

The equality the gem is supposed to guarantee is:
`shop header value used by the handler == shop that the app secret's signature actually authenticates`

Because the signature authenticates only the body bytes, and the shop identity travels in a sibling header that is excluded from the signed material, this equality does not hold. An attacker can keep body+hmac fixed (both valid, both real, both signed by the app's real, shared `client_secret`) while swapping the shop header to any other shop domain, and `HmacValidator.validate` still returns `true`.

### Impact Explanation
All shops that install a given app share the same `api_secret_key`, so any merchant/attacker who can trigger even one legitimate webhook to their own shop obtains a `(raw_body, hmac)` pair that remains cryptographically valid regardless of which shop-domain header accompanies it. By replaying that pair to the app's webhook endpoint with the `shop-domain` header changed to a victim's domain, the attacker gets the gem to hand the app a `WebhookMetadata` object asserting the victim shop as the source. Depending on how the host app uses `data.shop` (e.g. `app/uninstalled`, `customers/redact`, `shop/redact`, or any topic that triggers per-shop state changes/session invalidation), this enables cross-tenant interference — forged mandatory-compliance events, forced session/token invalidation, or data manipulation attributed to a shop the attacker does not control. This matches the "cross-tenant access" class of Critical/High impact.

### Likelihood Explanation
Exploitation requires no privileged credentials, access tokens, or the app's `client_secret`: only (1) a normal, unprivileged install of the app on the attacker's own shop to harvest one legitimate `(body, hmac)` pair for any convenient topic, and (2) the ability to POST directly to the app's public webhook endpoint with a modified `shop-domain` header — an unauthenticated network capability any internet user has. The vulnerability is inherent to how `Request`/`HmacValidator`/`Registry` are wired together in this gem and does not depend on the host app ignoring documented behavior; the gem itself hands over an unauthenticated `shop` value as if it were authenticated.

### Recommendation
Bind the shop identity into the value that is cryptographically verified before it is trusted, e.g.:
- Reject/flag webhooks where `request.shop` is not a shop the app has an existing, previously-authenticated session/install record for (host-app responsibility), and/or
- Have `Registry`/`Request` require the caller to supply the expected shop (from the caller's own session lookup keyed by something the HMAC does authenticate, such as an embedded shop domain inside the signed payload) and assert equality against the header value before dispatching to the handler, raising `Errors::InvalidWebhookError` on mismatch.

### Proof of Concept
1. Install the target app on `attacker.myshopify.com`. Trigger any webhook topic the app subscribes to (e.g. `app/uninstalled`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header sent by Shopify — this HMAC is valid for that body under the app's shared `client_secret`.
2. Craft a new HTTP POST to the app's webhook endpoint using the exact same raw body and `X-Shopify-Hmac-Sha256` value, but set `X-Shopify-Shop-Domain: victim.myshopify.com` (and, if desired, `X-Shopify-Topic` matching the original since topic also isn't part of the signable string).
3. Send the request. `ShopifyAPI::Webhooks::Registry.process`:
   ```ruby
   raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)
   ```
   still passes because `HmacValidator.validate` only checks `raw_body` against the HMAC — the shop header is not part of that check (`lib/shopify_api/webhooks/request.rb:35-38`, `lib/shopify_api/utils/hmac_validator.rb:26-31`).
4. `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, ...))` is invoked with `shop == "victim.myshopify.com"` even though the payload/signature originated from `attacker.myshopify.com`'s install (`lib/shopify_api/webhooks/registry.rb:198-199`).
