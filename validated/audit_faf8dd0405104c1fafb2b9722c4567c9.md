## Title
IntentGatewayV2 (Tron) credits escrow using requested amount instead of actual tokens received, enabling insolvency with fee-on-transfer/deflationary ERC20 tokens - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron deployment of `IntentGatewayV2.placeOrder` computes the escrowed balance for each input token directly from the user-specified `order.inputs[i].amount` (reduced only by the protocol fee), and calls `IERC20(token).safeTransferFrom(msg.sender, address(this), order.inputs[i].amount)` without ever comparing the gateway's balance before and after the transfer. If the input token is fee-on-transfer, deflationary, or otherwise does not deliver the full nominal amount, the gateway credits itself (and the resulting escrow ledger `_orders[commitment][token]`) with more tokens than it actually received.

`reducedInputs[i].amount` is derived solely from `order.inputs[i].amount` minus the protocol fee percentage — it is never adjusted for the actual number of tokens the gateway ends up holding: [2](#0-1) 

The predispatch branch has the same flaw — it uses `balance` fetched from the dispatcher/gateway only to detect *excess* dust, but still stores `reducedInputs[i].amount` (the pre-transfer, requested amount) into escrow rather than what the contract actually retained: [3](#0-2) 

This is materially different from — and less safe than — the main EVM `IntentGatewayV2.sol` (`evm/src/apps/IntentGatewayV2.sol`), which explicitly snapshots `balanceOf(address(this))` before and after each transfer and mutates `order.inputs[i].amount` to the actual received amount before computing the commitment and crediting escrow: [4](#0-3) 

The Foundry test suite even documents and enforces this "actual received" invariant for the main contract with dedicated fee-on-transfer tests, confirming this is a recognized design requirement that the Tron variant fails to satisfy: [5](#0-4) 

Root cause: the Tron `IntentGatewayV2.placeOrder` assumes `transferFrom` always moves exactly the requested amount into the contract and never reconciles the escrow ledger (`_orders` mapping) against the gateway's real ERC20 balance — precisely the class of bug described in the external report for `Vault.vy`, where contract bookkeeping (deposit limit, share issuance) relies on the assumption that "the same set of tokens is transferred and received," which breaks for inflationary/deflationary tokens.

### Impact Explanation
Because `_orders[commitment][token]` (the escrow accounting ledger used later by `fillOrder`/redemption/refund/cancel logic) records more tokens than the gateway physically holds whenever a deflationary/fee-on-transfer ERC20 is used as an order input, the contract becomes under-collateralized for that order. Since escrow balances for different orders/tokens share the same pooled ERC20 balance in the gateway contract, this shortfall can be exploited or can accidentally cause insolvency that prevents legitimate solvers/users from withdrawing their rightfully escrowed funds from *other* orders using the same token — i.e., permanent freezing of funds and/or effective theft (a user or solver draining more tokens than deposited across multiple orders, at the expense of others), which meets the Critical/High severity bar for unsound state commitment / fund freezing.

### Likelihood Explanation
The likelihood is High for any deployment or governance decision that lists a fee-on-transfer, rebasing, or otherwise dynamic-balance ERC20 as a supported input asset on the Tron IntentGatewayV2 deployment. No privileged role is required to trigger it — this is reachable directly by an unprivileged user calling `placeOrder` with a fee-on-transfer token as input, exactly matching the required "single submitted transaction" reachability criterion.

### Recommendation
Mirror the mitigation already implemented in the main EVM `IntentGatewayV2.sol`: snapshot `IERC20(token).balanceOf(address(this))` (or the dispatcher's balance, in the predispatch case) immediately before and after each `safeTransferFrom`/sweep, and use the measured delta — not the caller-specified `order.inputs[i].amount` — as the basis for computing `reducedInputs`, the order commitment, and the amount credited into `_orders[commitment][token]`. Apply this consistently to both the direct-transfer and predispatch code paths in `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Admin/governance whitelists a fee-on-transfer ERC20 (e.g., 1% transfer tax) as a valid input token for the Tron `IntentGatewayV2`.
2. User calls `placeOrder` with `order.inputs[0] = {token: FOT, amount: 1000e18}`.
3. `IERC20(FOT).safeTransferFrom(msg.sender, address(this), 1000e18)` executes; due to the 1% fee, the gateway's actual balance only increases by `990e18`.
4. `_orders[commitment][FOT] += reducedInputs[0].amount`, where `reducedInputs[0].amount` is `1000e18` (minus protocol fee if any) — i.e., escrow records `~1000e18` even though the contract only holds `990e18`.
5. Repeating this with multiple orders progressively creates a growing gap between the sum of `_orders[...][FOT]` escrow entries and `IERC20(FOT).balanceOf(gateway)`.
6. Once total claims against `_orders` exceed the actual token balance, some legitimate order's solver/refund/withdrawal call reverts (funds frozen) or, depending on withdrawal ordering, earlier claimants can drain tokens that were meant to back other users' escrowed orders (funds effectively stolen from later claimants).

    /// @notice Escrow correctly reflects actual received amount for fee-on-transfer tokens.
    function testPlaceOrder_FeeOnTransferToken_EscrowMatchesReceived() public {
        // Deploy a 1% fee-on-transfer token
        FeeOnTransferToken fot = new FeeOnTransferToken(100); // 1% = 100 bps
        fot.mint(user, 10000 * 1e18);

        uint256 inputAmount = 1000 * 1e18;
        uint256 expectedReceived = inputAmount - (inputAmount * 100) / 10000; // 990

        TokenInfo[] memory inputs = new TokenInfo[](1);
        inputs[0] = TokenInfo({token: bytes32(uint256(uint160(address(fot)))), amount: inputAmount});

        TokenInfo[] memory outputAssets = new TokenInfo[](1);
        outputAssets[0] = TokenInfo({token: bytes32(uint256(uint160(address(dai)))), amount: 900 * 1e18});

        PaymentInfo memory output =
            PaymentInfo({beneficiary: bytes32(uint256(uint160(user))), assets: outputAssets, call: ""});

        Order memory order = Order({
            user: bytes32(0),
            source: "",
            destination: host.host(),
            deadline: block.number + 100,
            nonce: 0,
            fees: 0,
            session: address(0),
            predispatch: DispatchInfo({assets: new TokenInfo[](0), call: ""}),
            inputs: inputs,
            output: output
        });

        vm.startPrank(user);
        fot.approve(address(intentGateway), inputAmount);
        intentGateway.placeOrder(order, bytes32(0));
        vm.stopPrank();

        // Gateway should hold only what it actually received
        assertEq(
            fot.balanceOf(address(intentGateway)), expectedReceived, "Gateway balance should match received amount"
        );

        // Reconstruct the order as placeOrder would have mutated it
        order.user = bytes32(uint256(uint160(user)));
        order.source = host.host();
        order.nonce = 0;
        order.inputs[0].amount = expectedReceived;
        bytes32 commitment = keccak256(abi.encode(order));

        // Escrow should match actual received, not the user-specified amount
        assertEq(
            intentGateway._orders(commitment, address(fot)),
            expectedReceived,
            "Escrow should equal actual received amount"
        );
    }
