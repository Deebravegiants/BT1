This confirms the vulnerability. The `Registry.process` method validates the HMAC over `request.to_signable_string` (which is only `@raw_body`), but the `shop` value returned by `request.shop` comes from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header, which is never included in the signable string.### Title
Webhook tenant identity (`shop`) is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely via `Utils::HmacValidator.validate(request)`, which computes the HMAC over `request.to_signable_string`. For webhook requests, `to_signable_string` returns only the raw request body [1](#0-0) . The `shop` field, which is what the app's `WebhookHandler` uses to attribute the webhook payload to a specific merchant/tenant, is read straight from the `x-shopify-shop-domain`/`shopify-shop-domain` HTTP header and is never included in the HMAC-signed bytes [2](#0-1) .

### Finding Description
`HmacValidator.validate` computes `compute_signature(verifiable_query.to_signable_string, secret)` and compares it against the value returned by `verifiable_query.hmac` [3](#0-2) . For `Webhooks::Request`, `hmac` is parsed from the `hmac-sha256` header and `to_signable_string` is simply `@raw_body` [4](#0-3) [1](#0-0) . Neither `topic`, `shop`, `api_version`, nor `webhook_id` — all read from headers via `shopify_header` — participate in the signable string [5](#0-4) [6](#0-5) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` to build `WebhookMetadata` that is handed to the app's handler as the tenant identifier for the payload: [7](#0-6) . The `WebhookMetadata` struct exposes `shop` as the authoritative tenant key for the delivered `body` [8](#0-7) , and the gem's own documentation instructs consuming apps to use `data.shop` directly to route/attribute the webhook (e.g., `shop_domain: data.shop`) [9](#0-8) .

The identity binding that should hold is: **bytes cryptographically verified == bytes the app treats as authoritative for tenant attribution**. Here that breaks down to `HMAC-covers(raw_body) ≠ shop-used-for-tenant-attribution(header)`. A valid HMAC only proves the *body* originated from Shopify using the app's `api_secret_key`; it says nothing about which shop the header claims the event is for. Because a single app typically has one shared `api_secret_key` across all installed shops (multi-tenant), any party who can observe one legitimate webhook delivery for their own shop (e.g., inspecting their own server logs, or standing up their own webhook receiver endpoint registered on their own installation) obtains a `(raw_body, hmac)` pair that is valid forever for that exact body under the shared secret. They can then replay that exact `raw_body` + `hmac` to the target app's webhook endpoint while substituting the `x-shopify-shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looks at the header), and `Registry.process` calls the handler with `WebhookMetadata.new(shop: <attacker-chosen-value>, body: <original body>, ...)`, causing the app to process/store data under the wrong tenant.

### Impact Explanation
This crosses the tenant boundary the gem is meant to enforce: an unprivileged actor who merely has their own legitimate app installation (no special credentials, no access token, no `client_secret`, no session) can cause the webhook processing pipeline to attribute a signed-and-otherwise-legitimate payload to an arbitrary other shop. Any app relying on `data.shop`/`WebhookMetadata#shop` as an authenticated tenant key (as the gem's own docs instruct) is exposed to cross-tenant data confusion — e.g., a customer-data-request or order webhook being filed against the wrong merchant, or state keyed by shop being corrupted for a shop the attacker does not control. This matches the Critical "cross-tenant access" impact category since the shop identity — the tenant boundary — is forgeable independent of the cryptographic check.

### Likelihood Explanation
Likelihood is moderate-to-high for any attacker who has (or can obtain, e.g., via a free development store) a legitimate installation of the target app: they only need to capture one raw body + hmac pair from their own tenant's webhook traffic (visible in their own server's request logs/headers) and replay it with a different `shop` header value to the target's public webhook endpoint. No secret material, session, or privileged access is required — only observation of traffic they are already authorized to receive.

### Recommendation
Bind the header-derived, security-relevant fields into the HMAC-signed material rather than trusting them independently of the signature. Concretely: change `Webhooks::Request#to_signable_string` (and/or the validation strategy in `Registry.process`) so it incorporates `shop`, `topic`, and `webhook_id` alongside the raw body when computing/comparing the signature, or otherwise cryptographically bind the shop domain to the payload before trusting it. Until then, apps are effectively required to independently verify that `request.shop` corresponds to a shop with an active session/installation before acting on the payload, and this gem's `process` method should not present `shop` as if it were already authenticated by the HMAC check that precedes it.

### Proof of Concept
1. Attacker installs the target app on their own store `attacker-shop.myshopify.com` (any unprivileged merchant can do this) and registers a webhook, e.g. `orders/create`, per [10](#0-9) .
2. Shopify delivers a legitimate webhook to the attacker's own endpoint with headers including `x-shopify-hmac-sha256: <HMAC>` and `x-shopify-shop-domain: attacker-shop.myshopify.com`, and some `raw_body`.
3. Attacker replays the exact same `raw_body` and `x-shopify-hmac-sha256` value to the victim app's public webhook endpoint, but sets `x-shopify-shop-domain: victim-shop.myshopify.com`.
4. The app calls `ShopifyAPI::Webhooks::Registry.process(ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: headers))` as documented [11](#0-10) .
5. `Utils::HmacValidator.validate(request)` succeeds because it only checks the (unmodified) body against the (unmodified) HMAC [12](#0-11) .
6. `Registry.process` invokes the app's handler with `WebhookMetadata.new(topic: ..., shop: "victim-shop.myshopify.com", body: <attacker's own body>, ...)` [13](#0-12) , causing the app to process attacker-controlled content as if it belonged to the victim shop.
