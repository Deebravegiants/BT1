### Title
`GraphqlProxy.proxy_query` raises unhandled `TypeError`/`NoMethodError` instead of `Errors::InvalidGraphqlRequestError` when JSON body top-level value is not an Object - (File: `lib/shopify_api/utils/graphql_proxy.rb`)

### Summary
When the `Content-Type` is `application/json`, `proxy_query` calls `JSON.parse(body)` and then unconditionally indexes the result with `parsed_body["query"]` without verifying that the parsed value is a `Hash`. A request body such as `'[{"query":"..."}]'` or `'"foo"'` parses successfully as valid JSON but produces an `Array`/`String`, whose `[]` operator does not accept a `String` key, causing a raw `TypeError`/`NoMethodError` to propagate instead of the gem's sanitized `Errors::InvalidGraphqlRequestError`.

### Finding Description
The intended binding is: for any syntactically-valid-JSON `body` reaching `proxy_query` with `Content-Type: application/json`, the method must either succeed or raise a `ShopifyAPI::Errors` subtype — never an unhandled Ruby runtime error.

The code path is: [1](#0-0) 

`JSON.parse(body)` only guarantees the result is *some* valid JSON value (object, array, string, number, boolean, null) — it does not guarantee a `Hash`. The subsequent `parsed_body["query"]` assumes a `Hash`. If an attacker (who controls the raw request body of a GraphQL-proxy endpoint built on this gem, as documented in `docs/usage/graphql.md`) sends a body like `'[{"query":"{ shop { name } }"}]'` or `'"just a string"'` with `Content-Type: application/json`, `JSON.parse` returns an `Array` or `String`. Calling `["query"]` on an `Array` raises `TypeError: no implicit conversion from String to Integer` (and on other non-Hash JSON scalars, similarly a `NoMethodError`/`TypeError`), which is not rescued anywhere in `proxy_query` or its caller. This exception propagates up through the host application rather than the gem's own `Errors::InvalidGraphqlRequestError`, defined at [2](#0-1) .

None of the existing guards intercept this: `Context.private?`, `session.online?`, and the `content-type` case dispatch all pass normally for this payload; the code only checks `query.nil?` after the indexing operation has already executed and thrown.

### Impact Explanation
The direct effect is an unhandled exception surfacing in the host application instead of a gem-defined error class, which breaks the gem's documented sanitized-error contract at this boundary. Any caller code that expects to rescue only `ShopifyAPI::Errors::*` around `proxy_query` will fail to catch this exception, and if the host app's global crash/error handler logs the exception with a backtrace (a common Rails default), that could result in more verbose internal application details being written to logs than intended. This does not directly expose credentials, does not bypass authentication, and does not cross tenant boundaries; the attacker only affects requests that they themselves send through their own controlled endpoint, causing incorrect error typing/log noise for that single request. It does not rise to the "credential leakage into logs" bar because no secret value is placed in the exception message or backtrace — the leak, if any, is of stack trace structure, not of any token, secret, or session data.

### Likelihood Explanation
Trivial for an attacker who controls the raw body sent to a `proxy_query`-backed endpoint (i.e., the app developer's endpoint that forwards proxied GraphQL requests using this gem, as shown in `docs/usage/graphql.md`) — merely sending a JSON array or scalar instead of an object with `Content-Type: application/json` triggers it every time. However, this is not an attacker exploiting a security control weakness against a victim; it's a robustness/input-validation gap that only affects error-type fidelity for the attacker's own request.

### Recommendation
Validate that `parsed_body` is a `Hash` before indexing, e.g.:
```ruby
parsed_body = JSON.parse(body)
raise Errors::InvalidGraphqlRequestError, "Invalid JSON body for GraphQL proxy request." unless parsed_body.is_a?(Hash)
```
Also consider rescuing `JSON::ParserError` around `JSON.parse(body)` and re-raising as `Errors::InvalidGraphqlRequestError`, since malformed JSON already raises a raw `JSON::ParserError` today.

### Proof of Concept

# test/utils/graphql_proxy_test.rb (addition)
def test_raises_invalid_graphql_request_error_for_non_object_json_body
  session = ... # valid online session, as in existing tests
  headers = { "Content-Type" => "application/json" }
  body = '[{"query":"{ shop { name } }"}]'

  assert_raises(ShopifyAPI::Errors::InvalidGraphqlRequestError) do
    ShopifyAPI::Utils::GraphqlProxy.proxy_query(session: session, headers: headers, body: body)

Running this against current code demonstrates a `TypeError`/`NoMethodError` is raised instead of `Errors::InvalidGraphqlRequestError`, confirming the binding violation at [3](#0-2) .
