### Title
Unprivileged front-running of `SignedDelegateAction` nonce consumption grieves the intended relayer - (File: `runtime/runtime/src/actions.rs`)

### Summary
`validate_delegate_action_key()` persists (bumps) the sender's access-key nonce or gas-key nonce **before** the delegate action's inner actions are executed, and this function is reachable by any unprivileged account that wraps a copy of someone else's `SignedDelegateAction`/`SignedDelegateActionV2` in its own transaction as relayer. Because meta-transactions (NEP-366) are explicitly designed so *any* account can act as relayer for a `SignedDelegateAction`, and that structure is passed off-chain before being included on-chain, any party who obtains a copy of it (via the intended relayer's API, gossip, or mempool observation) can submit it first. This mirrors the Sherlock H-4 pattern where `checkOrder()` let any caller consume another party's presigned nonce, invalidating the order for the intended flow.

### Finding Description
`validate_delegate_action_key` in `runtime/runtime/src/actions.rs` checks the nonce/permission and then unconditionally commits the new nonce to the trie: [1](#0-0) 

This happens as a discrete step of processing `Action::Delegate`/`Action::DelegateV2` inside a receipt, separate from and prior to the actual execution success of the delegate's inner `actions` list. The docs confirm the nonce is meant to gate replay by "a relayer," not by a specific authorized relayer identity, and that the `SignedDelegateAction` is handed off-chain to a relayer to wrap and submit: [2](#0-1) [3](#0-2) 

Because there is no restriction tying submission of a given `SignedDelegateAction` to a specific relayer/predecessor account, any account that becomes aware of the signed payload (e.g. captured from the intended relayer's public submission endpoint, gossiped transaction data, or a dishonest secondary relayer) can construct its own outer `SignedTransaction` embedding the identical `SignedDelegateAction` and submit it to the network first. Once the block/chunk producer applies it, `validate_delegate_action_key` bumps the nonce as shown above. If the surrounding transaction is crafted so the delegate's inner actions subsequently fail (e.g., insufficient funds supplied by the malicious relayer, permission checks tuned to fail, etc.), the nonce increment nonetheless persists because it precedes and is independent of inner-action success. Test coverage validates this ordering/behavior explicitly (nonce updated unconditionally on the "everything is ok" pre-check path, independent of inner actions): [4](#0-3) 

The consuming test suite for gas-key delegate replays also demonstrates that a second submission of the same delegate action nonce fails with `DelegateActionInvalidNonce` once the nonce has been consumed — confirming that any first successful submission (regardless of actor) burns the nonce for all subsequent submitters, including the intended relayer: [5](#0-4) 

### Impact Explanation
An unprivileged account can grief a legitimate relayer's meta-transaction flow by front-running the inclusion of a `SignedDelegateAction`, consuming the sender's nonce without the sender's intended actions being reliably applied by the intended relayer. This can cause:
- Denial of service for the sender's intended action (their pre-signed request becomes permanently invalid once the nonce advances, requiring the sender to re-sign a new `DelegateAction` with a fresh nonce).
- Wasted gas/deposit cost for the legitimate relayer if their outer transaction is submitted after the griefer's, since it will fail with `DelegateActionInvalidNonce`.
This is a targeted griefing vector against specific users/relayers rather than a validator-level or protocol-wide safety violation; it does not cause token inflation, unauthorized state changes to balances beyond nonce state, or divergence, but it does allow unauthorized advancement of another account's access-key/gas-key nonce state by a party lacking the corresponding private key, causing legitimate presigned intents to fail.

### Likelihood Explanation
Likelihood is moderate: it requires (a) the attacker to obtain a copy of a `SignedDelegateAction` intended for a specific relayer (feasible if relayers expose it via public submission channels, or if a competing/malicious relayer receives it and chooses to grief rather than honor it), and (b) the attacker to submit it in a transaction before the intended relayer's transaction is included. No special privilege, validator role, or protocol bug beyond the general meta-transaction design is required — only an unprivileged account capable of submitting ordinary transactions.

### Recommendation
Consider binding a `SignedDelegateAction`'s validity/consumption to the transaction actually delivering its intended effect, e.g.:
- Roll back the nonce update transactionally with the inner actions' success/failure so partial or hostile relayer behavior cannot burn the nonce without delivering the delegate's intended actions, or
- Allow senders to optionally restrict/require a specific relayer (`predecessor_id`) for a given `DelegateAction`, closing the "anyone can relay" front-running surface for cases where users want relayer exclusivity.

### Proof of Concept
1. Sender `S` signs `DelegateAction { sender_id: S, receiver_id: R, actions: [...], nonce: N, public_key: pk_S }` and shares it off-chain with an intended relayer `Relayer_honest` (e.g., via HTTP submission endpoint).
2. Attacker `Relayer_evil` observes the same `SignedDelegateAction` (e.g., by querying/monitoring the relayer's public API or the mempool) and wraps it into its own `SignedTransaction` (`Action::Delegate(signed_delegate)`), submitting it to the network before `Relayer_honest`'s transaction lands.
3. On execution, `validate_delegate_action_key` (see `runtime/runtime/src/actions.rs:685-699`) validates and immediately commits the new nonce for `S`'s access key.
4. `Relayer_honest`'s later transaction embedding the identical `SignedDelegateAction` (same nonce `N`) is applied and fails with `ActionErrorKind::DelegateActionInvalidNonce { delegate_nonce: N, ak_nonce: N }`, as demonstrated by the replay test at `test-loop-tests/src/tests/gas_keys.rs:284-296`, confirming the nonce cannot be reused once consumed by any submitter.

**File:** docs/architecture/how/meta-tx.md (L40-52)
```markdown
With meta transactions, Alice can create a `DelegateAction`, which is very
similar to a transaction. It also contains a list of actions to execute and a
single receiver for those actions. She signs the `DelegateAction` and forwards
it (off-chain) to a relayer. The relayer wraps it in a transaction, of which the
relayer is the signer and therefore pays the gas costs. If the inner actions
have an attached token balance, this is also paid for by the relayer.

On chain, the `SignedDelegateAction` inside the transaction is converted to an
action receipt with the same `SignedDelegateAction` on the relayer's shard. The
receipt is forwarded to the account from `Alice`, which will unpacked the
`SignedDelegateAction` and verify that it is signed by Alice with a valid Nonce
etc. If all checks are successful, a new action receipt with the inner actions
as body is sent to `FT`. There, the `ft_transfer` call finally executes.
```

/// The struct a user creates and signs to create a meta transaction.
struct DelegateAction {
    /// Signer of the delegated actions
    pub sender_id: AccountId,
    /// Receiver of the delegated actions.
    pub receiver_id: AccountId,
    /// List of actions to be executed.
    ///
    /// With the meta transactions MVP defined in NEP-366, nested
    /// DelegateActions are not allowed. A separate type is used to enforce it.
    pub actions: Vec<NonDelegateAction>,
    /// Nonce to ensure that the same delegate action is not sent twice by a
    /// relayer and should match for given account's `public_key`.
    /// After this action is processed it will increment.
    pub nonce: Nonce,
    /// The maximal height of the block in the blockchain below which the given DelegateAction is valid.
    pub max_block_height: BlockHeight,
    /// Public key used to sign this delegated action.
    pub public_key: PublicKey,
}
