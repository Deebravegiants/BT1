### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the shop identity (`shop-domain` header) used by `ShopifyAPI::Webhooks::Registry.process` to route data to the host application's handler is read straight from an unauthenticated HTTP header, never included in the HMAC-signed content.

### Finding Description
`ShopifyAPI::Utils::HmacValidator.validate` computes `HMAC(secret, verifiable_query.to_signable_string)` and compares it with the value carried in the `hmac-sha256` header using `OpenSSL.secure_compare`: [1](#0-0) 

For webhooks, `to_signable_string` is defined to be the raw body only: [2](#0-1) 

The `shop` accessor, however, is derived from the `shopify-shop-domain`/`x-shopify-shop-domain` HTTP header, which is not part of the signed content at all: [3](#0-2) [4](#0-3) 

`Registry.process` validates only the body/HMAC pair and then dispatches `request.shop` (unverified) straight to the application handler as the tenant identifier: [5](#0-4) 

This is the same identity-binding break as the report's bug class: a field that is *acted on* (here, `shop`, used to attribute/route the webhook payload to a specific merchant/tenant) is not covered by the cryptographic check (the HMAC), while a different field (the body) is verified instead. The equality that should hold — `shop_bound_by_hmac == shop_used_for_routing` — never holds, because the HMAC binds only the body bytes, not the shop claim.

### Impact Explanation
Because the app's `client_secret`/`api_secret_key` is shared across all shops that install the app (it is not per-shop), any malicious merchant that has legitimately installed the app can capture a genuine webhook delivery for their own store (valid `raw_body` + valid HMAC). They can then replay the exact same body/HMAC pair to the app's public webhook endpoint while substituting the `shop-domain` header with a victim shop's domain. `HmacValidator.validate` still succeeds (it never looked at the header), and `Registry.process` forwards the forged shop identity to the handler, so the host application processes attacker-controlled data as if it belongs to a different tenant. This is a cross-tenant data injection/impersonation, matching the Critical "cross-tenant access" impact category.

### Likelihood Explanation
Any shop that installs the app (an unprivileged, ordinary merchant, requiring no access to the app's `client_secret`) can trigger this: they need only observe one webhook delivered to their own endpoint (which they legitimately receive) and resend it with an altered `shop-domain` header. No secret material or elevated privilege is required beyond normal app installation.

### Recommendation
Bind the shop identity into the signed content, or otherwise cryptographically verify that the `shop-domain` header matches the shop that legitimately owns the delivered webhook (e.g., cross-check against the session/shop the app expects and reject the header value as untrusted for anything but display, or require the host application to separately verify shop ownership via `SessionStorage` before trusting `request.shop`). At minimum, document explicitly that `request.shop` is not covered by the HMAC and must not be used for tenant routing/authorization decisions without independent verification.

### Proof of Concept
1. App installs on `attacker-shop.myshopify.com` and `victim-shop.myshopify.com` (both legitimate installs of the same app, sharing one `api_secret_key`).
2. Shopify delivers a genuine webhook to the attacker's shop:
   - Headers: `x-shopify-shop-domain: attacker-shop.myshopify.com`, `x-shopify-hmac-sha256: <valid HMAC of body>`
   - Body: `{"id": 1, ...}`
3. Attacker resends the identical body and HMAC header to the app's webhook endpoint, but changes `x-shopify-shop-domain` to `victim-shop.myshopify.com`.
4. `Utils::HmacValidator.validate(request)` in `Registry.process` (`lib/shopify_api/webhooks/registry.rb:190`) succeeds because it only checks `HMAC(secret, raw_body)`.
5. The handler is invoked with `WebhookMetadata.new(topic:, shop: "victim-shop.myshopify.com", body: attacker_body, ...)`, causing the host app to record/act on attacker data under the victim's tenant.
