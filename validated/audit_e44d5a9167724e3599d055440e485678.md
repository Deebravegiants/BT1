## Title
Webhook shop/topic/webhook-id headers are trusted by handlers without being covered by the HMAC signature, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body [1](#0-0) , and `Utils::HmacValidator` verifies the HMAC exclusively against that signable string [2](#0-1) . The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from HTTP headers (`shopify-shop-domain`, `shopify-topic`, `shopify-webhook-id`, `shopify-api-version`) and are never part of the signed payload [3](#0-2) . `Registry.process` passes these unverified header values directly to the merchant's webhook handler as the tenant-identifying `WebhookMetadata` [4](#0-3) .

### Finding Description
Shopify signs webhooks using the app's single `client_secret`, which is shared across every merchant that installs the app — it is not shop-specific. This means any merchant who has installed the app is able to receive genuinely-signed webhook deliveries for their *own* shop (a legitimate, unprivileged action requiring no special access).

The binding the gem should be enforcing is:
```
hmac_verifies(bytes_signed) == bytes_the_app_acts_on
```
but the code instead enforces:
```
hmac_verifies(raw_body) while shop/topic/webhook_id (bytes NOT signed) are trusted separately
```

Because `hmac` is computed only over `@raw_body` [1](#0-0)  and the validator only checks that string against the received signature [5](#0-4) , an unprivileged merchant who receives one authentic, HMAC-valid webhook for their own shop can replay the exact same body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain`, `x-shopify-topic`, and `x-shopify-webhook-id` headers with values belonging to a different (victim) shop. `HmacValidator.validate` still returns `true` because it only checks the body bytes [6](#0-5) , and `Registry.process` then dispatches the handler with the attacker-controlled `shop`/`topic` as if Shopify had certified them [7](#0-6) .

### Impact Explanation
Any app built on this gem that uses `WebhookMetadata#shop` or `#topic` to key tenant-scoped operations (which is exactly the pattern the gem's own docs/tests promote, e.g. asserting `data.shop`/`data.topic` in the handler in `test/webhooks/registry_test.rb`) is exposed to cross-tenant confusion: a malicious merchant can trigger the app to process data under another merchant's shop identity, or invoke mandatory-compliance topics (e.g. `shop/redact`, `customers/redact`) against a shop they do not own. This is a cross-tenant access vulnerability achieved without any access token, `client_secret`, or privileged credential — only a legitimately-received webhook from the attacker's own, currently-or-previously installed shop.

### Likelihood Explanation
Any merchant who installs the app can receive at least one genuine webhook (e.g. `app/uninstalled`, or any subscribed topic) with a valid HMAC for arbitrary JSON bodies they can influence somewhat via their store data, and then replay it with forged headers. No secret material is needed — only an HTTP client capable of resending intercepted headers, which is trivially available to any unprivileged internet user who is also an app merchant.

### Recommendation
Include the tenant/topic-identifying fields (`shop`, `topic`, `webhook_id`, `api_version`) in the HMAC-signable string, or otherwise cryptographically bind them to the verified body (e.g., require the body to embed and self-report the shop domain and compare against the header only after doing so, or use the header values solely as advisory/logging data rather than as the trust anchor for tenant identity). At minimum, document prominently that `WebhookMetadata#shop`/`#topic` are unauthenticated header values so integrators do not treat them as verified.

### Proof of Concept
1. App merchant A installs the app; Shopify sends a legitimate webhook with body `B`, headers `x-shopify-shop-domain: shop-a.myshopify.com`, `x-shopify-topic: app/uninstalled`, and a valid `x-shopify-hmac-sha256` computed over `B` with the app's `client_secret`.
2. Attacker (merchant A) intercepts this request and resends `B` with the same HMAC header unchanged, but replaces `x-shopify-shop-domain` with `shop-victim.myshopify.com` and/or `x-shopify-topic` with a different registered topic.
3. `ShopifyAPI::Webhooks::Request.new` parses the forged headers [8](#0-7) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because only `B` is checked [6](#0-5) .
4. The registered handler for that topic is invoked with `WebhookMetadata.new(topic: "app/uninstalled" (or attacker-chosen), shop: "shop-victim.myshopify.com", ...)` [9](#0-8) , causing the app to perform shop-victim-scoped actions (e.g., deleting local records, redacting data) that the attacker never had legitimate access to trigger.

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
