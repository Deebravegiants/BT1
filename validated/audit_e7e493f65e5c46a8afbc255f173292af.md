### Title
`flash_loan` pulls principal+fee via `transfer_from` from an attacker-chosen `receiver` that never authorizes the call — ([File: contracts/pool/src/ops/flash.rs](contracts/pool/src/ops/flash.rs))

### Summary
The bug class is "arbitrary `from` passed to `transferFrom`, gated only by a pre-existing allowance". In XOXNO Lending this shape exists in the pool's flash-loan settlement: `flash_loan`'s caller picks the `receiver` address, and the pool later executes `token.transfer_from(pool, receiver, pool, amount + fee)`. The `receiver` never calls `require_auth` for that pull — only its standing token allowance to the pool gates the transfer, exactly like `LibBondingCurve::deposit` pulling from an arbitrary `_recipient`.

### Finding Description
`ops::flash::apply` takes `receiver` as a caller-supplied argument, pays `amount` out to it, invokes `execute_flash_loan` on it with attacker-controlled `initiator`/`data`, and then settles via `collect_repayment`: [1](#0-0) 

```rust
assert_with_error!(
    env,
    asset.allowance(receiver, pool) >= terms.total_repayment,
    FlashLoanError::InvalidFlashloanRepay
);
asset.transfer_from(pool, receiver, pool, &terms.total_repayment);
```

The only guards on `receiver` are `require_wasm_receiver` (it must be a contract) and the allowance check — there is no proof that `receiver` consented to *this* flash loan. In Soroban, `transfer_from` authenticates the `spender` (the pool, satisfied via the pool's own invocation), not `from`. So any WASM contract that has granted — or inside its `execute_flash_loan` callback does grant — an allowance of at least `amount + fee` to the pool can be force-enlisted as the repayer by an arbitrary caller.

This is the same root cause as the reference issue: an input-controlled `from` address in an allowance-based pull, where the allowance was granted for the victim's own purposes, not for this invocation. The standard flash-receiver pattern (per `mock/flash-loan-receiver`) is to `approve(pool, amount + fee)` inside the callback; such a receiver — or one holding a stale/excess allowance — satisfies all checks.

### Impact Explanation
Theft of user/contract funds, bounded per call by the flash-loan fee but repeatable. The victim receives `amount` and is then debited `amount + fee`, a net loss of `fee` plus the gas/auth-tree exposure of a callback it never requested. An attacker can re-invoke `flash_loan` against the same victim while `allowance(victim, pool) >= amount + fee` and the victim's callback executes benignly under attacker-supplied `data`, draining `fee` per iteration (fees are booked as protocol revenue, so the attacker doesn't even need to profit directly — griefing/inventory-drain still qualifies). The attacker chooses `initiator` and `data`, so a receiver whose `execute_flash_loan` is permissionless (the documented integration shape) has no way to reject.

### Likelihood Explanation
Reachable by a single unprivileged address through the controller's `flash_loan` entrypoint — `receiver`, `amount`, and `data` are all caller-controlled. Preconditions: the victim must be a WASM contract exposing an `execute_flash_loan` that completes under adversarial `data` and that leaves `allowance(victim, pool) >= amount + fee`. Both hold for any honestly-implemented flash receiver that approves inside its callback (the intended pattern), and permanently for any contract carrying a stale pool allowance. Not every contract qualifies, and the per-call profit is only the fee — keeping this at Medium rather than High.

### Recommendation
Authenticate the payer instead of trusting caller-supplied `from`. Options:

- Require `receiver` (or `initiator` on its behalf) to authorize the repayment: e.g., have the receiver return/attest repayment inside `execute_flash_loan` and settle by `transfer(receiver → pool)` executed *from the callback's own frame* (the receiver authorizes its own transfer), rather than a pool-initiated `transfer_from`.
- Alternatively, record a hash/commitment: store `(receiver, initiator, amount, fee)` at payout time and require the callback to re-assert consent — but the clean fix matching the reference recommendation is to make the payer the authorizing party (`from.require_auth()` equivalent), i.e., drop `transfer_from` entirely and have the receiver push `amount + fee` via `transfer` inside its own callback, then assert `balance == balance_after_repayment`.

```diff
- assert_with_error!(env, asset.allowance(receiver, pool) >= terms.total_repayment, ...);
- asset.transfer_from(pool, receiver, pool, &terms.total_repayment);
+ // receiver pushes repayment from inside execute_flash_loan via its own authorized transfer
  require_balance(env, asset, pool, terms.balance_after_repayment);
```

### Proof of Concept
Test-harness sketch against the pool (victim = a WASM receiver that approves inside its callback, the standard integration):

```rust
// Victim receiver: canonical implementation — approves pool for amount+fee in the callback.
#[contractimpl]
impl VictimReceiver {
    pub fn execute_flash_loan(env: Env, _initiator: Address, asset: Address,
                              amount: i128, fee: i128, pool: Address, _data: Bytes) {
        token::Client::new(&env, &asset)
            .approve(&env.current_contract_address(), &pool, &(amount + fee), &ledger);
    }
}

#[test]
fn anyone_can_force_a_receiver_to_pay_the_flash_fee() {
    let attacker = Address::generate(&env);
    let victim = env.register(VictimReceiver, ());

    let pre = token.balance(&victim);

    // Attacker names the victim as receiver; victim never initiated or signed a loan.
    pool_client.flash_loan(&hub_asset, &attacker, &victim, &amount, &data);

    // Victim received `amount` then had `amount + fee` pulled without authorizing it:
    assert_eq!(token.balance(&victim), pre - expected_fee);
}
```

Note: I verified `collect_repayment`'s `transfer_from` and the caller-controlled `receiver` plumbing directly in `contracts/pool/src/ops/flash.rs`; I did not fully trace the controller-side `flash_loan` wrapper to confirm whether `initiator.require_auth()` is enforced — if the controller additionally requires `receiver` authorization before dispatching, the issue is mitigated and the finding should be downgraded accordingly.

/// Pulls principal + fee via `transfer_from` after verifying allowance.
fn collect_repayment(
    env: &Env,
    asset: &token::Client,
    pool: &Address,
    receiver: &Address,
    terms: &FlashTerms,
) {
    assert_with_error!(
        env,
        asset.allowance(receiver, pool) >= terms.total_repayment,
        FlashLoanError::InvalidFlashloanRepay
    );
    asset.transfer_from(pool, receiver, pool, &terms.total_repayment);
    require_balance(env, asset, pool, terms.balance_after_repayment);
}
