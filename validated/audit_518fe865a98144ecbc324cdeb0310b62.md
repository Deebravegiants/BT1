### Title
Webhook `shop` identity is not covered by the HMAC signature, allowing cross-tenant shop spoofing in `ShopifyAPI::Webhooks::Registry.process` - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, while the `shop` identity used by `Registry.process` to dispatch webhook data is read from the unauthenticated `X-Shopify-Shop-Domain` header. The HMAC verification therefore authenticates *that some bytes were signed with the app's shared secret*, but does not bind those bytes to the `shop` value that the application logic subsequently trusts and acts on.

### Finding Description
The identity binding that should hold is:
`shop value used by the webhook handler == shop value the HMAC signature was computed over`

In `lib/shopify_api/webhooks/request.rb`: [1](#0-0) 
`shop` is parsed straight from the `shopify-shop-domain` / `x-shopify-shop-domain` header with no cryptographic protection.

`to_signable_string`, which is what actually gets HMAC-verified, only ever returns the raw body: [2](#0-1) 

`Utils::HmacValidator.validate` computes the HMAC purely from `to_signable_string` (the body) and compares it to the `hmac` header: [3](#0-2) 

`Registry.process` validates only this body-bound HMAC, then immediately trusts `request.shop` (the unauthenticated header) to build the `WebhookMetadata` object that is handed to the app's webhook handler: [4](#0-3) 

Because the `api_secret_key` used for HMAC verification is a single app-wide secret (shared by every shop that has installed the app), and the signature is computed solely from the body, **any party who possesses one valid `(body, hmac)` pair signed by the app's secret can replay that pair with an arbitrary `shop-domain` header value and it will still pass `HmacValidator.validate`.** Such a valid pair is trivial for an unprivileged internet user to obtain: any merchant who installs the app receives correctly signed webhooks for their own shop and can capture the `raw_body` + `X-Shopify-Hmac-Sha256` header from any webhook Shopify sends to their own endpoint (e.g. via a debug proxy they control) — then replay it to the same endpoint with a different `X-Shopify-Shop-Domain` value.

### Impact Explanation
This breaks the tenant-isolation guarantee the HMAC check is meant to provide: the webhook consumer receives `WebhookMetadata(shop: <attacker-chosen shop domain>, body: <attacker's own previously-legit body>, topic: ..., webhook_id: ...)` with a signature that still validates. Any downstream logic keyed by `shop` (e.g., updating shop records, revoking data, triggering shop-specific side effects such as `customers/redact` / `shop/redact` mandatory compliance topics, cache invalidation, billing state changes) can be executed under a victim shop's identity that the attacker does not own — a cross-tenant identity confusion. This matches the report's bug class: an access-control/identity check ("this webhook truly originates for shop X") is satisfied by validating bytes that don't include the field ("shop") being trusted downstream.

The severity is bounded by what the specific host application does with `shop` in its webhook handler, but the gem-level guarantee — "if `HmacValidator.validate` returns true, the whole `Request` (including `shop`) can be trusted" — is false, and the gem provides no facility to bind `shop` into the signature or otherwise verify it, unlike the OAuth `AuthQuery` flow, which explicitly includes `shop` (and `host`) inside `to_signable_string`: [5](#0-4) 

### Likelihood Explanation
Likelihood is high for any app that has more than one shop installed (the normal case for any public Shopify app), since:
- No secret beyond a legitimately-received webhook payload is required.
- The attacker only needs control of one merchant/shop account with the app installed (an "unprivileged internet user" relative to other tenants).
- The header is fully attacker-controlled at the HTTP layer and is never re-derived from anything signed.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook_id`) into the value that is HMAC-verified, or otherwise cryptographically validate the header against the signed body, e.g.:
- Include the `shop-domain`, `topic`, and `webhook-id` headers in `to_signable_string` (mirroring how `AuthQuery#to_signable_string` includes `shop`/`host`), so any tampering with those headers invalidates the signature.
- Alternatively, document/require host apps to independently verify that the resolved `shop` corresponds to a shop actually known to have registered for that specific webhook/topic before trusting `WebhookMetadata#shop`.

### Proof of Concept
1. App has two shops installed: attacker-owned `attacker.myshopify.com` and victim `victim.myshopify.com`, sharing one app `api_secret_key`.
2. Shopify sends attacker a legitimate webhook for `attacker.myshopify.com`:
   - Headers: `X-Shopify-Topic: customers/redact`, `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`, `X-Shopify-Shop-Domain: attacker.myshopify.com`
   - Body: `{"customer": {...}}`
3. Attacker captures `raw_body` and the `hmac-sha256` header value (e.g., via a proxy under their control sitting in front of their own endpoint).
4. Attacker replays the identical `raw_body` and `hmac-sha256` header to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
5. `ShopifyAPI::Webhooks::Request.new` parses `shop` as `victim.myshopify.com`. [1](#0-0) 
6. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which recomputes HMAC only over `raw_body` — identical to the originally signed body — and passes. [6](#0-5) 
7. The handler is invoked with `WebhookMetadata(shop: "victim.myshopify.com", ...)`, despite the payload never having been generated or signed by/for the victim shop. [7](#0-6)
