### Title
Webhook `shop`/tenant identity is not covered by the HMAC signature, enabling cross-tenant webhook spoofing via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body, then hands the caller-supplied `shop-domain` header straight to the handler as the tenant identifier — without that header ever being included in the signed material.

### Finding Description
`Webhooks::Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `Utils::HmacValidator.validate` computes/compares the HMAC exclusively against that signable string [2](#0-1) . Meanwhile `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from unauthenticated HTTP headers (`shopify-shop-domain`/`x-shopify-shop-domain`, etc.) [3](#0-2) .

`Registry.process` validates the HMAC and then immediately trusts `request.shop` (the header value) as the tenant identity passed into the handler, with no cross-check that this shop is the one the signed body actually pertains to:
`raise Errors::InvalidWebhookError, ... unless Utils::HmacValidator.validate(request)` followed by `handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop, body: request.parsed_body, ...))` [4](#0-3) .

This breaks the intended identity binding:
`shop_bound_by_signature (covered by HMAC) == shop_used_for_tenant_dispatch (request.shop header)`

In reality: `shop_bound_by_signature = ∅` (the signature covers only body bytes) while `shop_used_for_tenant_dispatch = header value`, i.e. the two are never proven equal by this code.

### Impact Explanation
Because the HMAC is computed only from `@raw_body` and the app's `client_secret` (shared across every shop that installs the app), a valid `(body, hmac)` pair is not bound to any particular shop. An attacker who is a merchant with the app installed on their own shop (an "unprivileged" tenant with respect to other tenants) will legitimately receive webhook deliveries with valid `(body, hmac)` pairs for their own shop. They can capture such a pair and replay the exact same POST to the app's public webhook endpoint while substituting the `X-Shopify-Shop-Domain` header for a victim shop's domain. `HmacValidator.validate` still returns `true` (only the body is checked), and `Registry.process` dispatches the handler with `shop: <victim shop>` even though the payload was never signed for that shop. Any host application logic keyed on `WebhookMetadata#shop` (e.g., writing data, updating billing/subscription state, revoking access, marking uninstall) can be forced to operate against a shop the attacker does not control — a cross-tenant integrity violation.

### Likelihood Explanation
Webhook endpoints are, by design, public HTTP(S) endpoints that must accept unauthenticated POSTs from "Shopify" — the only gate is HMAC validity. Any app installer can generate at least one genuine `(body, hmac)` pair for their own shop (e.g., by triggering any subscribed event on their own store) and immediately replay it against the same endpoint with a forged shop header, requiring no secret, token, or elevated privilege — only network access to the endpoint, which is inherent to how webhooks work.

### Recommendation
Do not use header-derived `shop`, `topic`, `webhook_id`, or `api_version` as trusted values for dispatch without additional binding. Either (a) include the shop domain (and other identity-relevant fields) in the signable string used for HMAC computation so the signature binds the tenant to the payload, or (b) require the host application to independently corroborate `request.shop` against the topic-specific payload content (e.g., a shop/store identifier embedded in the JSON body) before trusting it for tenant-scoped side effects, and document this requirement prominently in `Webhooks::Request`/`Registry.process`.

### Proof of Concept
1. App installs on Shop A and Shop B, sharing one `client_secret`.
2. Shopify delivers a real webhook to the app for Shop A: body `B`, header `X-Shopify-Shop-Domain: shop-a.myshopify.com`, header `X-Shopify-Hmac-Sha256: H` where `H = HMAC-SHA256(client_secret, B)`.
3. Attacker (owner/operator of Shop A, or anyone able to observe this legitimate delivery) resends an HTTP POST to the same app webhook endpoint with the identical body `B` and identical `X-Shopify-Hmac-Sha256: H`, but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com`.
4. `Webhooks::Request.new` builds `request` from these headers/body; `Utils::HmacValidator.validate(request)` recomputes HMAC over `B` only and matches `H` — validation passes [5](#0-4) .
5. `Registry.process` proceeds and invokes the handler with `shop: "shop-b.myshopify.com"` even though the payload was signed and delivered for Shop A [4](#0-3) .

Note: I could not verify from the indexed files whether `docs/usage/webhooks.md` explicitly warns integrators to independently re-verify the `shop` claim against payload content before use; if such guidance exists and host apps are expected to perform this additional check themselves, this weakens (but does not eliminate) the gem-level root cause, since `Registry.process` itself performs no such corroboration.
