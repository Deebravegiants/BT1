Based on my investigation, I found a genuine custody-analog issue in a custom `MultisigAccountTimeLock` feature added to `multisig_account.move` in this fork. Note: this timelock/override feature does not exist in canonical upstream `aptos-core`, so I focused on it as fork-specific custom code.

### Title
Timelock override-threshold invariant is enforced only at set-time and not re-validated when `num_signatures_required` changes, allowing ordinary quorum to silently bypass the timelock - (File: `aptos-move/framework/aptos-framework/sources/multisig_account.move`)

### Summary
The custom multisig timelock feature is meant to force a mandatory delay (`timelock_period`) before a multisig transaction executes, unless a *supermajority* of owners (`override_threshold`, required to be strictly greater than `num_signatures_required`) approves it immediately. This bar is validated only when the timelock is first configured, not maintained as an invariant afterward.

### Finding Description
`upsert_timelock_internal` enforces the invariant `override_threshold > num_signatures_required` and `override_threshold <= owners.length()` only at the moment the timelock is created/updated: [1](#0-0) 

However, `num_signatures_required` can subsequently be changed independently through `update_signatures_required`, `add_owners_and_update_signatures_required`, and `swap_owners_and_update_signatures_required`, all of which route through `update_owner_schema` with no reference to `MultisigAccountTimeLock`: [2](#0-1) 

The actual bypass check compares live `num_approvals` against the stored `override_threshold`: [3](#0-2) 

If `num_signatures_required` is later raised (via ordinary owner quorum, itself subject to whatever timelock is in force at that time) to a value equal to or greater than `override_threshold`, then every future transaction that merely reaches the new (and now equal-to-or-above-override) `num_signatures_required` quorum automatically satisfies `override_threshold.is_some() && &num_approvals >= override_threshold.borrow()`, causing `can_execute_with_timelock` to return `true` unconditionally — the time-delay protection is silently and permanently nullified for a threshold that was never re-approved via the supermajority path the timelock was designed to require.

### Impact Explanation
Multisig accounts are resource accounts that can hold APT, fungible assets, and objects, and can be granted upgrade/freeze/transfer authority over code objects. The timelock/override mechanism is the custody safeguard intended to give other owners a reaction window before a highly privileged action (e.g., changing owners, rotating auth key, executing an asset-draining transaction) takes effect. Because the `override_threshold > num_signatures_required` invariant is not re-checked when `num_signatures_required` changes, a bare quorum of owners can collapse the two-tier security model into a single tier and cause all subsequent transactions approved by ordinary quorum to execute instantly, bypassing the intended time-delay custody control without ever mustering the higher supermajority the operator configured. This is a broken custody invariant (multisig-held value loses its "no leak of control faster than intended" guarantee) even though no cryptographic funds are directly stolen in this step.

### Likelihood Explanation
The path requires only owner-level actions already permitted in the multisig flow (approving an `update_signatures_required` transaction), no external attacker or privileged bypass is needed — this is exactly the "unprivileged root cause, broken invariant, corrupted control field" pattern requested. It reduces to a data-consistency bug rather than requiring any exotic conditions, making it straightforward for a subset of "normal" owners to trigger, whether accidentally through routine governance changes or intentionally by a malicious minority quorum. I was not able to fully read the body of `update_owner_schema` (file truncated at 1000 lines per read) to rule out an explicit re-validation there; this should be confirmed before treating this as fully proven.

### Recommendation
When `num_signatures_required` is updated via `update_owner_schema` (or any owners/threshold-changing entry function), if a `MultisigAccountTimeLock` exists for the account, re-validate that `override_threshold > new_num_signatures_required` (and `<= owners.length()`), either by aborting the update or by requiring the timelock to be explicitly reconfigured (e.g. auto-clearing/raising `override_threshold`) in the same transaction.

### Proof of Concept
1. Create a multisig account with 5 owners, `num_signatures_required = 3`.
2. Configure timelock via `create_with_owners_and_timelock`/`upsert_timelock` with `timelock_period = 7 days`, `override_threshold = Some(4)` (valid since `4 > 3`).
3. Owners submit and approve (with exactly 3 approvals, the normal quorum) an `update_signatures_required` transaction setting `new_num_signatures_required = 4`. This transaction itself must wait out the 7-day timelock (since 3 < 4 override), but eventually executes.
4. Now `num_signatures_required == override_threshold == 4`.
5. For any subsequent transaction, once 4 owners approve (the now-normal quorum), `can_execute_with_timelock` evaluates `num_approvals (4) >= override_threshold (4)` as true instantly — the 7-day delay never applies again, even though the operator's original design intended the delay to always apply unless the higher supermajority bar was met.     inline fun can_execute_with_timelock(multisig_account: address, sequence_number: u64, num_approvals: u64): bool {
        if (exists<MultisigAccountTimeLock>(multisig_account)) {
            let multisig_account_resource = &MultisigAccountTimeLock[multisig_account];
            let timelock = multisig_account_resource.timelock_period;
            let override_threshold = multisig_account_resource.override_threshold;

            // Get the pending transaction to check if the timelock has expired
            // Assume that the transaction has already been checked to exist and is valid
            let pending_transaction = get_transaction(multisig_account, sequence_number);

            // Use subtraction to avoid overflow (now_seconds() >= creation_time_secs is always true)
            let elapsed = now_seconds() - pending_transaction.creation_time_secs;

            // If the number of approvals meets the override threshold, or the timelock has expired, allow execution
            (override_threshold.is_some() && &num_approvals >= override_threshold.borrow()) || elapsed >= timelock
        } else {
            true
        }
    }

    fun upsert_timelock_internal(
        multisig_account: &signer,
        timelock_period: u64,
        override_threshold: Option<u64>,
    ) {
        let multisig_address = address_of(multisig_account);
        assert_multisig_account_exists(multisig_address);

        assert!(
            timelock_period >= MIN_TIMELOCK_PERIOD && timelock_period <= MAX_TIMELOCK_PERIOD,
            error::invalid_argument(EINVALID_TIMELOCK_DURATION)
        );

        let multisig_account_resource = &MultisigAccount[multisig_address];
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() > multisig_account_resource.num_signatures_required,
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );
        assert!(
            override_threshold.is_none() || *override_threshold.borrow() <= multisig_account_resource.owners.length(),
            error::invalid_argument(EINVALID_TIMELOCK_OVERRIDE_THRESHOLD)
        );

        if (exists<MultisigAccountTimeLock>(multisig_address)) {
            let multisig_account_resource = &mut MultisigAccountTimeLock[multisig_address];
            multisig_account_resource.timelock_period = timelock_period;
            multisig_account_resource.override_threshold = override_threshold;
        } else {
            move_to(multisig_account, MultisigAccountTimeLock::V1 {
                timelock_period,
                override_threshold,
            });
        }

        emit(TimelockUpdated {
            multisig_account: multisig_address,
            timelock_period,
            override_threshold,
        });
    }
