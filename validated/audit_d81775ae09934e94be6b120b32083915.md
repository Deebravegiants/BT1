## Analog Found

### Title
Optimistic, unvalidated pending-cost accounting in the Pending Transaction Queue causes legitimate `WithdrawFromGasKey`/gas-key transactions to be wrongly rejected with `NotEnoughGasKeyBalance` - (File: `chain/client/src/pending_transaction_queue.rs`, `runtime/runtime/src/verifier.rs`)

### Summary
The reported xERC4626 bug is a class of "cached aggregate subtracted by a value that can legitimately exceed it, causing a revert that blocks an otherwise-valid operation." The closest reachable analog in nearcore is the `PendingTransactionQueue` / `PendingConstraints` mechanism used to validate gas-key transactions before certification: a cached, optimistically-accumulated `paid_from_gas_key` value is subtracted from the real on-chain `gas_key_info.balance`, and the code explicitly assumes this subtraction can never underflow — an assumption that is not actually enforced.

### Finding Description
`PendingTransactionQueue::add_chunk_transactions` and `PendingTxSession::check_pending` add the full requested amount of every `WithdrawFromGasKey` action found in an included-but-uncertified chunk to `pending_gas_key_costs`/`session_gas_key_withdrawals`, with no check against the gas key's actual balance: [1](#0-0) [2](#0-1) 

This aggregate (`PendingConstraints.paid_from_gas_key`) is then used in `verify_and_charge_gas_key_tx_ephemeral` on the assumption stated directly in the comment — "gas key balance only changes through transactions that PTQ explicitly tracks, so pending should never exceed the balance": [3](#0-2) 

However, the real execution path for `WithdrawFromGasKey` can fail (e.g., the requested amount exceeds the actual gas key balance at execution time, or the key no longer exists), in which case the action is rejected via `checked_sub` and no balance is actually deducted: [4](#0-3) 

Because the pending-queue accounting reserves the *requested* amount unconditionally at chunk-inclusion time (not the amount that will actually be applied), and only releases it once the chunk is certified via `remove_certified_chunk_by_block_hash` (which subtracts the same originally-recorded value), any `WithdrawFromGasKey` transaction that is destined to fail at execution still inflates `paid_from_gas_key` for the entire uncertified window. During that window, `gas_key_info.balance.checked_sub(pending.paid_from_gas_key)` can legitimately underflow the tracked (but not real) commitment, causing the `else` branch to trigger and any other transaction signed with that gas key to be rejected with `NotEnoughGasKeyBalance`, even though the real, certified on-chain balance is sufficient.

### Impact Explanation
This does not directly steal or lose funds, but it can make a gas key's available balance temporarily unspendable/unusable — the exact "availability, not loss" impact class the original report was downgraded to Medium for. A user (or an adversary targeting a specific gas key they don't control, e.g. by racing a doomed `WithdrawFromGasKey` transaction into a chunk) can cause legitimate gas-key transactions on that same key to be spuriously rejected until the offending chunk is certified.

### Likelihood Explanation
This requires the "Spice"/pending-transaction-queue path (gated behind `protocol_feature_spice`) and gas keys (`ProtocolFeature::GasKeys`) to be active, and requires crafting a `WithdrawFromGasKey` transaction that will be included in a chunk but fail at execution (e.g., an amount slightly over the actual balance, submitted concurrently with another spending transaction). This is achievable by any account with a gas key of its own; no privileged/validator access is required.

### Recommendation
Only add a `WithdrawFromGasKey` amount to the pending aggregate if it can be validated against the currently known certified balance minus already-pending commitments at inclusion time, or reconcile/cap `paid_from_gas_key` against `gas_key_info.balance` (e.g., via `saturating_sub`/`min`) instead of asserting the invariant can never be violated, similar to how `paid_from_balance` already uses `saturating_sub` defensively in `verify_and_charge_tx_ephemeral`.

### Proof of Concept
1. Enable the `protocol_feature_spice` pending-transaction-queue path and gas keys.
2. Fund a gas key with balance `B`.
3. Submit `WithdrawFromGasKey(amount = B)` (tx A) and, in the same or an immediately following chunk before certification, submit a normal gas-key transaction costing `gas_cost` (tx B) that would normally succeed given balance `B`.
4. If tx A is arranged to fail execution (e.g., a concurrent transfer from the same key reduces the real balance below `B` first, or the key is deleted before execution), the pending queue still recorded `paid_from_gas_key += B` at inclusion time via `add_chunk_transactions`/`check_pending`.
5. Tx B's `verify_and_charge_gas_key_tx_ephemeral` computes `gas_key_info.balance.checked_sub(pending.paid_from_gas_key)`, which underflows, and tx B is rejected with `NotEnoughGasKeyBalance` even though the real balance is sufficient — mirroring Alice/Bob being unable to withdraw in the original report until the cycle (here, chunk certification) resolves.
