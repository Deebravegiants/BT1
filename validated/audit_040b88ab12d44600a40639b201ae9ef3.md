### Title
Webhook `shop-domain` header not covered by HMAC allows cross-tenant webhook data injection - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an incoming webhook solely by validating an HMAC computed over the raw request body, but the `shop` (tenant) identity that is handed to the application's webhook handler is read from an HTTP header that is never included in that HMAC computation. This is the same class of bug as the reported issue: a value that is *acted on* (here, the tenant/shop identifier used to scope webhook processing) is not covered by the same authenticity check (HMAC) that gates the rest of the payload, so the two can be desynchronized by an attacker.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw HTTP body: [1](#0-0) 

but `#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read directly from unauthenticated headers: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers `@raw_body`) and then dispatches to the handler using the header-derived `shop`, without ever verifying that `shop` was cryptographically bound to the signed body: [3](#0-2) 

`HmacValidator.validate` confirms the request carries a valid HMAC produced with `Context.api_secret_key`, but that only proves *some* legitimate webhook body was signed by Shopify with the app's secret — it says nothing about which shop the `x-shopify-shop-domain` header claims to be from, since that header is outside `to_signable_string`: [4](#0-3) 

The broken identity binding, expressed as an equality that the code fails to enforce:
`shop_bound_by_hmac(raw_body) == shop_used_by_handler(header)`

Because a single app-level `api_secret_key` is shared across every shop that installs the app, any tenant that legitimately receives webhooks for its own shop possesses a body+HMAC pair that is valid under the app's secret. That same `raw_body`/`hmac` pair remains HMAC-valid if replayed with the `x-shopify-shop-domain` header changed to a different (victim) shop, because the header is not part of the signed material. `Registry.process` will accept it and invoke the handler with `WebhookMetadata.new(... shop: request.shop ...)` pointing at the victim shop rather than the shop that actually produced the payload.

This mirrors the root cause pattern in the Solidity report: a state/identity value (`_userWstETH` there; `shop` here) is consumed by downstream logic without being re-derived or re-validated from the same trusted source (`updateStakedTokenBalance` there; the HMAC-covered payload here), letting an attacker with control of one legitimate "account" (address B / their own shop) inject stale/foreign data into another account's (A's / a victim shop's) processing path.

### Impact Explanation
Any application built on this gem that trusts `WebhookMetadata#shop` to scope tenant data (a documented, expected usage — the field exists specifically to let handlers know "which shop this webhook is about") can have webhook-driven state (order/customer/product data, uninstall/GDPR triggers, etc.) written into or removed from the wrong tenant's records by a party who is themselves a legitimate installed shop of the app. This is a cross-tenant data integrity/confusion issue reachable by any unprivileged shop owner using the app, without needing the app's `api_secret_key`, an access token, or any privileged credential of the victim tenant — only their own genuine webhook deliveries, which they already legitimately receive.

### Likelihood Explanation
Likelihood is moderate-to-high in real deployments: the attacker only needs to be an ordinary merchant using the target app (installing it satisfies "unprivileged internet user" relative to other tenants). They capture one real webhook their own shop receives (trivial — inspect their own webhook endpoint traffic or logs), then replay the identical body/HMAC with a forged `x-shopify-shop-domain` header at the app's public webhook endpoint. No secret material, no TLS interception, and no social engineering is required — only observation of one's own legitimately-received webhook.

### Recommendation
Bind the `shop` (and ideally `topic`/`webhook-id`) values into the HMAC-verified signable string, or independently verify that the shop header matches a shop the current secret/session is scoped to, before using `request.shop` to route or persist data:
- Include `shop`, `topic`, and `webhook_id` in `to_signable_string`, matching them against the actual signed value, or
- Have `Registry.process` cross-check `request.shop` against known/expected shops for this delivery via an out-of-band trusted channel (e.g., Shopify's `X-Shopify-Shop-Domain` combined with a per-shop secret if available) rather than trusting the header alone.

### Proof of Concept
1. App `MyApp` installs into `shopA.myshopify.com` and `shopB.myshopify.com`, sharing one `api_secret_key`.
2. Attacker (owner of `shopA`) receives a legitimate webhook: `raw_body = {"id": 1, "note": "..."}`, header `x-shopify-shop-domain: shopA.myshopify.com`, and a valid `x-shopify-hmac-sha256` computed only over `raw_body`.
3. Attacker resends the identical `raw_body`/`hmac` to the app's webhook endpoint but sets `x-shopify-shop-domain: shopB.myshopify.com`.
4. `HmacValidator.validate` succeeds because `to_signable_string` never included the shop header: [1](#0-0) 
5. `Registry.process` calls the registered handler with `WebhookMetadata.new(topic: ..., shop: "shopB.myshopify.com", body: parsed_body, ...)`: [5](#0-4) 
6. If `MyApp`'s handler updates or deletes `shopB`'s stored record with data from `shopA`'s webhook (a normal pattern for e.g. `orders/updated` handlers), tenant data isolation is broken.
