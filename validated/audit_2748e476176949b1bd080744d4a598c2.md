## Analog Found

### Title
Missing bit-length validation in ERC20↔local decimal scaling causes `u128::pow` overflow panic, permanently bricking token bridge message delivery - (File: `modules/pallets/hyper-fungible-token/src/impls.rs`)

### Summary
The `cosmossdk.io/math` advisory describes a class of bug where a numeric type's declared/validated bit-length does not match what a related type can actually represent, so downstream arithmetic in that "borrowed" width overflows and panics. The `hyper-fungible-token` pallet has the same class of defect: `register_token`/`update_token` only validate that `config.decimals >= local_decimals` but never bound the *difference* between them, even though the scaling arithmetic that difference feeds is done in `u128`, not the full-width `U256` the rest of the amount conversion uses.

### Finding Description
`convert_to_erc20` and `convert_to_balance` compute a scaling factor as `10u128.pow(erc_decimals.saturating_sub(local_decimals) as u32)`: [1](#0-0) 

`erc_decimals` (`config.decimals`, a `u8`, range 0–255) is only checked to be `>= local_decimals` at registration time — there is no upper bound on the difference: [2](#0-1) 

`u128` can only represent up to `10^38`; any registered token whose `erc_decimals - local_decimals` exceeds ~38 makes `10u128.pow(diff)` overflow. This mirrors the CVE's root cause exactly: the validation performed on one field (`decimals >= local_decimals`) does not match the actual bit-length limit of the type used downstream (`u128` scaling factor vs. the `U256` amounts the rest of the pipeline uses).

Once such a token is registered, every subsequent `on_accept` call — triggered by *any* relayer delivering a legitimate cross-chain POST for that asset — invokes `convert_to_balance`, which recomputes the same overflowing `10u128.pow(...)`: [3](#0-2) 

The same overflow is reachable on the outbound path any time a user calls `send()` for that asset, since `convert_to_erc20` performs the identical computation: [4](#0-3) 

If the runtime is built with overflow checks enabled (the common Substrate default for release Wasm), this is not a graceful `Result::Err` — it is a hard panic inside `on_accept`/`send`, distinct from every other failure path in this module which is properly wrapped in `HftError`.

### Impact Explanation
A panic inside `on_accept` for a given `(asset, chain)` pair makes every future inbound message for that route unprocessable (a route unable to deliver messages), and a panic inside `send()` blocks every future outbound transfer for that asset — a permanent denial-of-service on that bridge route, reachable by any ordinary relayer or user, not just the party that misconfigured the decimals. This satisfies the "route unable to deliver messages" impact class.

### Likelihood Explanation
Triggering the panic requires only a normal, non-malicious registration mistake (entering an EVM decimals value far above the local asset's decimals — plausible for high-precision ERC20s or fat-fingered entries, since nothing in `register_token`/`update_token` enforces a sane bound), followed by an ordinary relayer delivering a normal message or a normal user calling `send()`. No malicious governance action is needed — this is a validation gap, not a governance-abuse scenario.

### Recommendation
- Bound the accepted `decimals` delta at registration/update time (e.g., reject `config.decimals - local_decimals > 38`, or whatever the safe `u128`/target-type limit is).
- Perform the scaling in `U256` throughout instead of `u128::pow`, and use checked/saturating exponentiation with an explicit `Result` error instead of an unguarded `pow` call, consistent with the rest of the module's `HftError` handling.

### Proof of Concept
1. Governance (or an operator with `CreateOrigin`) calls `register_token` for a new asset with `local_decimals = 6` and `config.decimals = 60` for an EVM chain (passes the `config.decimals >= local_decimals` check with room to spare).
2. Any relayer delivers a valid ISMP POST for that asset to `on_accept`; `Precisions::get` returns `erc_decimals = 60`, and `convert_to_balance` computes `10u128.pow(54)`, which overflows `u128`.
3. With overflow checks enabled, this panics inside message handling, and the route is permanently unable to process any future message for that asset (and outbound `send()` calls hit the mirrored overflow in `convert_to_erc20`).

Note: I could not verify from the index whether the parachain runtime's release profile has `overflow-checks = true` enabled (this determines panic vs. silent wraparound); confirming this in the Cargo build configuration would strengthen the severity assessment. If overflow checks are disabled, the bug degrades to silent incorrect amount scaling (still a fund-accounting integrity issue) rather than a panic/DoS.
