### Title
Unauthenticated arbitrary call execution and total balance-accounting bypass in Emporium via zero-token Min-proof path - (File: `contracts/external-actions/emporium/upgradeable/EmporiumUpgradeable.sol` / `contracts/CircomDataBuilder.sol`)

### Summary
An attacker can call `Hinkal.transact` with `externalActionId == HINKAL_EMPORIUM_ACTION_ID` and `erc20TokenAddresses.length == 0`, forcing `formInputForCircom` to select `formInputEmporiumMin`, whose circuit (`MainEVMCircuitMin.circom`) only constrains `message == Poseidon(messageSeed)` — a trivially satisfiable, secret-free constraint. Combined with an `EmporiumStack` where `signerAddress == address(0)`, `EmporiumUpgradeable.verifyWallet` skips all signature verification, and `EmporiumUpgradeable.runAction`'s balance-accounting loops never execute because they iterate the (empty) `erc20TokenAddresses` array, letting the attacker execute arbitrary stateless calls (`op.endpoint.call{value: op.value}(op.callData)`) as Emporium with zero accounting anywhere in the call stack.

### Finding Description
The invariant the question asks to validate is: *assets Emporium can move in a tx == assets accounted in balancesBefore/balancesAfter*. This is broken as follows.

1. `formInputForCircom` in `contracts/CircomDataBuilder.sol` selects the minimal circuit whenever `externalActionId == HINKAL_EMPORIUM_ACTION_ID && erc20TokenAddresses.length == 0`: [1](#0-0) 
`formInputEmporiumMin` only feeds `emporiumMessage`, `timeStamp`, `calldataHash` to the circuit: [2](#0-1) 
and the circuit itself proves nothing about balances, nullifiers, or the `EmporiumStack` contents — only `message <== Poseidon([messageSeed])`: [3](#0-2) 
`calldataHash` is checked in `HinkalHelper.performHinkalChecks` to bind `externalActionData` (which contains the raw `EmporiumStack` bytes) to the proof, but since the attacker crafts the entire `CircomData` themselves and produces their own valid proof, they can put any `EmporiumStack` in `externalActionMetadata` and satisfy the hash check trivially — no secret or privilege is required for any of this. [4](#0-3) 

2. `dimensionsCheck` requires all array lengths to match `dimensions.tokenNumber`; with `tokenNumber == 0` all the length checks trivially pass with empty arrays, so nothing blocks the zero-token path. [5](#0-4) 

3. In `EmporiumUpgradeable.runAction`, `balancesBefore`/`balancesAfter` are computed via `getBalancesForArray(circomData.erc20TokenAddresses)`, and the post-loop accounting `for (uint256 i = 0; i < circomData.erc20TokenAddresses.length; i++)` never executes when the array is empty: [6](#0-5) 
Likewise in `Hinkal.transact`, the outer balance-diff/slippage/UTXO-accounting loop also iterates `circomData.erc20TokenAddresses.length`, i.e. zero times: [7](#0-6) 

4. `verifyWallet` returns immediately, skipping the EIP-712 signature check entirely, whenever `stack.signerAddress == address(0)`: [8](#0-7) 
With `signerAddress == 0`, `runAction`'s op loop takes the "Case 2: Stateless Interaction" branch and executes `op.endpoint.call{value: op.value}(op.callData)` directly from Emporium, blocking only the `callHinkalWallet`/`doSendToRelay` selectors — any other call is permitted: [9](#0-8) 

Putting this together: any unprivileged address can call `Hinkal.transact` with the Min-proof path, an `EmporiumStack{signerAddress: address(0), ops: [{endpoint: <any ERC20 or router>, invokeWallet:false, value:0, callData: transfer(attacker, allEmporiumBalance)}]}`, and drain any ERC20/ETH balance currently held by the `EmporiumUpgradeable` contract, with zero signature check and zero balance accounting anywhere in the transaction (`runAction`'s loops and `Hinkal.transact`'s loops are all length-0 no-ops). No existing guard (`performHinkalChecks`, `dimensionsCheck`, `checkOnchainCreation`, `verifyProof`, `rootHashExists`, the balance/slippage `require`s in `Hinkal.transact`) intercepts this, because they are all gated on `erc20TokenAddresses.length`, which the attacker sets to zero specifically to disable them.

### Impact Explanation
Direct theft of any funds resting in the `EmporiumUpgradeable` contract (ETH or ERC20) — this includes funds mid-transit in multi-step "stateful"/batched Emporium flows, dust/leftover balances from prior operations, or relay fees pending settlement. This is Critical: direct theft of shielded/in-flight user funds and execution of calls/movement of assets that no wallet owner or prover ever authorized (since `signerAddress == 0` deliberately bypasses the EIP-712 signature check that would normally authenticate the wallet owner). The attack is fully repeatable against any balance the contract accumulates and costs the attacker only gas and proof generation for a public-input-only ZK proof (no secrets needed).

### Likelihood Explanation
Preconditions: (1) `EmporiumUpgradeable` must hold a nonzero balance of some asset at attack time — plausible given its design as a persistent multi-step balance holder ("Stack" of ops, "Stateful Interaction" via wallet, relay-fee routing), and (2) the attacker must be a `onlyAllowedRecipient` caller of `runAction`, which is satisfied automatically since `Hinkal._externalTransact` (an unprivileged, permissionless entrypoint) is itself registered as an allowed recipient by design. Generating the Min-circuit proof requires no secret witnesses beyond a self-chosen `messageSeed`, making this trivially reproducible by any EOA. The exploit is repeatable every time Emporium accumulates a balance.

### Recommendation
- Require `verifyWallet` to always validate a signature/authorization regardless of `stack.signerAddress`, or disallow `signerAddress == address(0)` combined with the Min-proof/empty-token path.
- Do not allow the Min-circuit (`formInputEmporiumMin`) path to be paired with an `EmporiumStack` containing arbitrary, unauthenticated `ops`; either constrain `ops`/`endpoint`/`callData` inside the circuit's public inputs, or forbid stateless ops when `erc20TokenAddresses.length == 0`.
- Perform Emporium balance accounting independent of `erc20TokenAddresses.length` — e.g., require `erc20TokenAddresses` (or an explicit allow-list of tokens touched by `ops`) to be non-empty and to cover every asset an op could move, so `balancesBefore`/`balancesAfter` always reflects real transfers.

### Proof of Concept
Foundry test plan:
1. Deploy `Hinkal`, `HinkalHelper`, `EmporiumUpgradeable`, register Emporium as external action and as `onlyAllowedRecipient`.
2. Fund `EmporiumUpgradeable` directly with e.g. 10 ETH and 1000 USDC (simulating leftover/in-transit balance).
3. As an attacker EOA (no special role), construct `CircomData` with `externalActionData.externalActionId = HINKAL_EMPORIUM_ACTION_ID`, `erc20TokenAddresses = []`, `amountChanges = []`, `dimensions.tokenNumber = 0`, and `externalActionData.externalActionMetadata` = ABI-encoded `EmporiumStack{signerAddress: address(0), ops: [{endpoint: address(USDC), invokeWallet: false, value: 0, callData: abi.encodeCall(IERC20.transfer, (attacker, 1000e6))}, {endpoint: attacker, invokeWallet:false, value: 10 ether, callData: ""}]}`.
4. Generate a valid `MainEVMCircuitMin` proof for a self-chosen `messageSeed`, set `emporiumMessage = Poseidon(messageSeed)`, compute `calldataHash` matching `getHashedCalldata`.
5. Call `Hinkal.transact(a,b,c,dimensions,circomData)` from the attacker EOA.
6. Assert: `USDC.balanceOf(attacker)` increased by 1000e6 and `attacker.balance` increased by 10 ether, i.e. `balancesBefore == balancesAfter` checks in both `EmporiumUpgradeable.runAction` and `Hinkal.transact` were never invoked (0-length loops), proving the equality "assets moved == assets accounted" is violated and funds were stolen with no signature or balance check.
