### Title
Webhook `shop-domain` (and `topic`) headers are trusted for tenant/business-logic dispatch without being covered by the HMAC signature, enabling cross-tenant webhook forgery via replay - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw request body, so the HMAC that `Utils::HmacValidator` verifies binds solely to the body bytes. The `shop`, `topic`, `webhook_id`, and `api_version` values are read straight from unauthenticated HTTP headers and are never part of the signed payload, yet `Registry.process` uses `request.shop` and `request.topic` to route and label the webhook as belonging to a specific tenant.

### Finding Description
`Request#to_signable_string` is defined as: [1](#0-0) 

while `shop`, `topic`, `webhook_id`, and `api_version` are pulled from headers that are not part of that signable string: [2](#0-1) 

`HmacValidator.validate` computes the HMAC exclusively over `to_signable_string` (i.e., the raw body) and compares it to the `hmac` header using `OpenSSL.secure_compare`: [3](#0-2) 

`Registry.process` then trusts `request.shop` and `request.topic` for dispatch and hands them to the app's handler as authenticated facts about the webhook's origin: [4](#0-3) 

The identity binding this code implicitly claims is:
`shop_header == tenant_that_produced_the_signed_body`

But the HMAC only proves `body == HMAC(body, api_secret_key)`; it proves nothing about which shop header should accompany that body. Because a single app's `api_secret_key` is shared across every shop that installs the app, any actor who can trigger a legitimate webhook delivery for their own store (e.g., installing the app on a free/dev shop they control, or simply observing any webhook payload+signature pair sent to the endpoint) obtains a `(raw_body, hmac)` pair that is valid under the shared secret. That pair can then be replayed to the same endpoint with the `shop-domain` (and/or `topic`) header swapped to a victim shop, and `HmacValidator.validate` will still return `true`, because the header value never entered the signature computation.

### Impact Explanation
This breaks the tenant-authentication boundary that host applications rely on `ShopifyAPI::Webhooks::Request#shop` for. A handler that trusts `WebhookMetadata#shop` to scope data lookups, mutations, or GDPR/compliance actions (e.g., `shop/redact`, `app/uninstalled`) can be tricked into acting on/against a victim tenant using an attacker-controlled but validly-HMAC'd body, since the gem's own signature verification does not bind the `shop` claim. This is a cross-tenant confusion vulnerability reachable purely by posting HTTP requests to the app's public webhook endpoint — no access token, `api_secret_key`, or privileged account is required, only reuse of a signature the attacker legitimately obtained for any shop (including their own).

### Likelihood Explanation
Every app's webhook endpoint is, by design, a public unauthenticated HTTP endpoint that this gem is meant to protect purely via `HmacValidator.validate`. Obtaining one valid `(body, hmac)` pair is trivial for any developer/attacker who installs the target app on any shop they control and captures the resulting webhook delivery (or simply sniffs their own webhook traffic). Since the same `api_secret_key` signs webhooks for all installs of the app, the replay works against any other tenant. No timing race, MEV, or privileged access is needed — only the ability to send an HTTP POST with attacker-chosen headers and a previously-observed valid body+signature.

### Recommendation
Include the tenant/topic identity in the signed material, or otherwise cryptographically bind `shop-domain` and `topic` to the HMAC check — e.g., verify the header values against Shopify's own webhook delivery records/IP allowlist, or require the host app to independently confirm `shop` is one of its known-installed shops before trusting `WebhookMetadata#shop`. At minimum, document clearly that `Request#shop`/`#topic` are unauthenticated fields and must not be used for tenant-authorization decisions without additional verification.

### Proof of Concept
1. App `X` is installed on `attacker.myshopify.com` (attacker-controlled) and `victim.myshopify.com`.
2. Attacker triggers any webhook event on their own shop, capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — this HMAC is valid because it's computed with the app's single shared `api_secret_key`: [5](#0-4) 
3. Attacker POSTs the identical body to the app's webhook endpoint, keeping the captured `x-shopify-hmac-sha256` value but changing `x-shopify-shop-domain` to `victim.myshopify.com` (and/or `x-shopify-topic` to a more sensitive topic sharing the same body shape).
4. `Registry.process` calls `Utils::HmacValidator.validate(request)`, which passes because it only checks the body against the secret: [6](#0-5) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload never originated from Shopify for that shop, as shown by how metadata is constructed: [7](#0-6)

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
