### Title
Overpayment of native-token relayer fees is permanently lost — `EvmHost.dispatch`/`fundRequest` never refund unspent ETH from the Uniswap swap - (File: evm/src/core/EvmHost.sol)

### Summary
`EvmHost.dispatch(DispatchPost)`, `EvmHost.dispatch(DispatchGet)`, and `EvmHost.fundRequest` accept `msg.value` as an approximate native-token payment and swap it for the exact `feeToken` amount via `swapETHForExactTokens`, but never capture the returned `amounts[]` or refund the unspent portion of `msg.value` back to the caller.

### Finding Description
In `EvmHost.dispatch(DispatchPost)` [1](#0-0) , `EvmHost.dispatch(DispatchGet)` [2](#0-1) , and `EvmHost.fundRequest` [3](#0-2) , when `msg.value > 0` the code calls:

```solidity
IUniswapV2Router02(uniswapV2).swapETHForExactTokens{value: msg.value}(post.fee, path, address(this), block.timestamp);
```

Uniswap V2's `swapETHForExactTokens` only spends `amounts[0] <= msg.value` and refunds `msg.value - amounts[0]` dust ETH to its immediate caller via `TransferHelper.safeTransferETH(msg.sender, ...)`. Because `EvmHost` itself is the direct caller of the router (not the end user), that refund lands on the `EvmHost` contract's own balance — not back to the original transaction sender who overpaid. None of the three functions capture the `amounts` return value or forward any leftover ETH to `_msgSender()`/`post.payer`.

This is the same bug class as the referenced report (fee-check accepts `>=` with no handling of the excess), but here it is materially worse: it is not merely "the contract holds slightly more than required," it is a case where the protocol itself has no accounting or path to return the overpaid ETH to the user, and the excess is silently absorbed into the host contract's balance.

The codebase's own `IntentGatewayV2.sol` demonstrates the correct/expected pattern is being followed elsewhere but is missing here: it captures the swap output and explicitly refunds the remainder to `msg.sender` [4](#0-3) , and this refund behavior is explicitly unit-tested [5](#0-4) . `EvmHost`'s `dispatch`/`fundRequest` functions do not implement this same refund step.

### Impact Explanation
Any unprivileged dispatcher (an `IApp`/message-sending contract or an EOA calling `IDispatcher(host).dispatch{value: ...}(...)` directly) who cannot predict the exact Uniswap execution price at submission time and therefore sends a safety margin of native token (a normal, expected practice, and explicitly recommended in the docs' fee-estimation guidance [6](#0-5) ) will have the unspent portion of their ETH permanently stuck in `EvmHost` with no function to reclaim it. This is a direct, unbacked loss of user funds on every native-token dispatch/fundRequest call where the sent value exceeds the exact swap input — which will happen routinely given slippage/price movement between quote and execution.

### Likelihood Explanation
High likelihood: this is not an edge case requiring an attacker — it is triggered by normal usage. The docs explicitly instruct callers to estimate fees off-chain and warn that on-chain `quote()` is unreliable due to sandwich-attack risk, meaning users are expected to send a buffer above the exact required amount [6](#0-5) . Every such call loses the buffer amount permanently.

### Recommendation
Capture the `amounts` array returned from `swapETHForExactTokens` in `EvmHost.dispatch(DispatchPost)`, `dispatch(DispatchGet)`, and `fundRequest`, and refund `msg.value - amounts[0]` to `_msgSender()` (or the designated `payer`), mirroring the pattern already implemented in `IntentGatewayV2.placeOrder` [7](#0-6) .

### Proof of Concept
1. Caller invokes `IDispatcher(host).dispatch{value: 5 ether}(post)` where `post.fee` only requires ~0.01 ETH worth of feeToken at current Uniswap price.
2. `EvmHost.dispatch` executes `swapETHForExactTokens{value: 5 ether}(post.fee, path, address(this), block.timestamp)` [1](#0-0) .
3. The router spends only the required ETH and refunds the remaining ~4.99 ETH to `msg.sender` of the router call, which is the `EvmHost` contract itself (confirmed by Uniswap V2 Router semantics and validated behavior of the equivalent wrapper test asserting refunds return "to caller" [8](#0-7) ).
4. `EvmHost.dispatch` does not read the swap's return value nor forward any ETH back to the original caller; the ~4.99 ETH remains in `EvmHost`'s balance permanently, with no user-facing withdrawal mechanism.
