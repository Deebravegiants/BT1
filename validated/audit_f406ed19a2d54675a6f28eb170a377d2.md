### Title
`findMatchingWithdrawal` misattributes status/txHash across duplicate-token withdrawals in a batch - (File: packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts)

### Summary
`PoaBridge.describeWithdrawal` resolves each `WithdrawalIdentifier`'s status by matching PoA API results solely on `nep141:<near_token_id>`, via `Array.prototype.find`, which always returns the *first* array entry matching that assetId regardless of which of the two same-token withdrawals it actually belongs to. When a batch contains two withdrawals of `nep141:bera.omft.near` to different destinations, both `WithdrawalIdentifier`s resolve to the same (first-found) entry, so one destination's real completion/txHash gets reported for the other's identifier.

### Finding Description
The broken equality: `describeWithdrawal(identifier_A).txHash` should correspond to the withdrawal whose `destinationAddress`/`amount` match `identifier_A.withdrawalParams`, i.e. `withdrawal.destination == identifier.withdrawalParams.destinationAddress`. Instead, `findMatchingWithdrawal` in `packages/intents-sdk/src/bridges/poa-bridge/poa-bridge.ts:418-427` only checks `` `nep141:${w.data.near_token_id}` === assetId ``, with no comparison to destination address, amount, or index. Since `getWithdrawalStatusWithRetry` fetches all withdrawals under the same NEAR intent tx hash (`args.tx.hash`) via `poaBridge.httpClient.getWithdrawalStatus({ withdrawal_hash: args.tx.hash })` (poa-bridge.ts:352-358), when two withdrawals share the same `assetId` (`nep141:bera.omft.near`), `Array.prototype.find` returns the same first match for both `WithdrawalIdentifier`s produced by `createWithdrawalIdentifier` (poa-bridge.ts:295-311), regardless of `index`. The code comment at lines 409-417 explicitly documents this: "multiple withdrawals of the same token in a single transaction are not supported," yet nothing upstream (`supports`, `validateWithdrawal`, `sdk.ts`'s batch orchestration) rejects or deduplicates such batches — the SDK happily accepts and signs/sends a batch with two `bera.omft.near` withdrawals to two different addresses.

### Impact Explanation
This is a status/hash misreport: `IntentsSDK.waitForWithdrawalCompletion` and downstream `processWithdrawal` return, for each identifier, the `status`/`txHash` of the *wrong* physical payout. An integrator processing withdrawal index 0 (e.g., destination X) may see the `transfer_tx_hash` and `completed` status that actually belongs to the payout for index 1 (destination Y), or vice versa, potentially causing the integrator to prematurely credit/release funds for a withdrawal that hasn't actually completed, or to double-credit based on one real completion being reported to two logical withdrawal records. This matches the "status or hash misreport making an integrator credit or refund twice" High-severity category.

### Likelihood Explanation
Preconditions: an attacker (any unprivileged NEAR Intents user, or an integrator forwarding user-controlled `withdrawalParams`) must construct a batch withdrawal intent containing two or more entries with the identical `assetId = nep141:bera.omft.near` but different destination addresses/amounts. Nothing in `PoaBridge.supports`, `validateWithdrawal`, or `sdk.ts`'s batch handling blocks or deduplicates same-assetId entries — each item is validated independently. This is trivially reachable via `IntentsSDK.processWithdrawal`/`signAndSendWithdrawalIntent` with an array `withdrawalParams`, and is repeatable per batch.

### Recommendation
In `findMatchingWithdrawal`, disambiguate matches when multiple withdrawals share the same `assetId` by cross-checking `destinationAddress` (and `amount`) against the API's withdrawal payload fields, or reject/throw when duplicate-`assetId` ambiguity is detected instead of silently returning the first match. At minimum, `PoaBridge.supports`/`validateWithdrawal`/`sdk.ts` batch orchestration should detect and reject batches with duplicate `assetId` for the POA route until the API/matching logic supports disambiguation.

### Proof of Concept
Vitest plan (`poa-bridge.test.ts`):
1. Mock `poaBridge.httpClient.getWithdrawalStatus` to return two `withdrawals` entries for `near_token_id: "bera.omft.near"` — entry 0 with `data.transfer_tx_hash = "0xAAA"` (destination `addrX`), entry 1 with `data.transfer_tx_hash = "0xBBB"` (destination `addrY`), both `status: "COMPLETED"`.
2. Build two `WithdrawalIdentifier`s: `id0` with `withdrawalParams.destinationAddress = addrX`, `index=0`; `id1` with `withdrawalParams.destinationAddress = addrY`, `index=1`, both `assetId = "nep141:bera.omft.near"`, same `tx.hash`.
3. Call `bridge.describeWithdrawal(id0)` and `bridge.describeWithdrawal(id1)`.
4. Assert the broken equality directly: expect `result0.txHash === "0xAAA"` and `result1.txHash === "0xBBB"` (i.e., each resolves to its own destination's hash) — the current implementation fails this because both calls return `txHash: "0xAAA"` (the first array entry), demonstrating the misattribution.
