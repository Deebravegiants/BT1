### Title
Webhook `shop` (and `topic`/`webhook_id`) header values are trusted without being covered by the HMAC, enabling cross-tenant webhook spoofing - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC signature over the raw request body only, while the `shop` (and `topic`, `webhook_id`, `api_version`) values are read directly from unauthenticated HTTP headers. `Registry.process` validates the HMAC and then hands the *unverified* `shop` value straight to the host application's webhook handler as trusted tenant identity, breaking the intended binding `HMAC-verified data == data acted upon`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` (and `#topic`, `#webhook_id`, `#api_version`) are pulled directly from HTTP headers that are never included in the signable string: [2](#0-1) 

`Registry.process` validates the HMAC via `Utils::HmacValidator.validate(request)` — which, per `HmacValidator#validate_signature`, only compares against `to_signable_string` (i.e., the body) — and then immediately trusts `request.shop`, `request.topic`, and `request.webhook_id` to build the `WebhookMetadata` passed to the app's handler: [3](#0-2) [4](#0-3) 

The identity binding that should hold is: `shop bound by HMAC == shop the handler acts on`. Because the `shop-domain` header is excluded from the signable string, this equality does not hold — the gem only proves "this body was signed with the app's `client_secret`" and not "this body belongs to shop X". Since a single Shopify app's `client_secret` is shared across every merchant (tenant) that installs it, any merchant who receives a legitimately HMAC-signed webhook for their own shop can capture it and replay it against the app's webhook endpoint with the `X-Shopify-Shop-Domain` (and/or `X-Shopify-Topic`/`X-Shopify-Webhook-Id`) header altered to name a different shop. The HMAC still validates (it only covers the body, which was untouched), but `WebhookMetadata#shop` now falsely claims to be a different tenant.

### Impact Explanation
If the host application uses `WebhookMetadata#shop` to key session/data lookups (the documented and intended use of this field — see `WebhookMetadata` struct), a malicious merchant can inject data/events under another merchant's shop identity, achieving cross-tenant access/write within the host app. This matches the "cross-tenant access" Critical impact category.

### Likelihood Explanation
Likelihood is constrained: the attacker must already be a legitimate (if malicious) merchant of the app, in order to obtain a validly-signed body/HMAC for at least one webhook delivery, and must be able to send arbitrary HTTP requests directly to the app's webhook receiver endpoint (bypassing Shopify's delivery infrastructure), which most production deployments allow since the receiver is a public HTTP endpoint. It does not require the `client_secret`, an access token, or any credential the attacker shouldn't have. The mandatory topics (`shop/redact`, `customers/redact`, `customers/data_request`) are especially attractive targets since they carry sensitive/administrative semantics.

### Recommendation
Include `shop`, `topic`, and `webhook_id` in the value covered by the HMAC verification path, or otherwise cryptographically bind the header-derived tenant identity to the signed payload before it is exposed via `WebhookMetadata`. At minimum, document that `Registry.process`/`WebhookMetadata#shop` is not itself an authenticated tenant identifier and must be cross-checked by the host application against an independently established session/shop record before being trusted for tenant-scoped operations.

### Proof of Concept
1. Malicious merchant "shop-a.myshopify.com" installs the target app and, from the app's normal webhook flow, captures a valid webhook delivery for `orders/create` (or any topic), including its correctly computed `X-Shopify-Hmac-Sha256` header and raw body.
2. Attacker replays this exact body/HMAC pair directly to the app's public webhook endpoint but sets `X-Shopify-Shop-Domain: shop-b.myshopify.com` (and optionally a different `X-Shopify-Topic`, since that header is also outside the HMAC).
3. `Utils::HmacValidator.validate(request)` succeeds because it only re-computes/checks the HMAC of the unchanged raw body: [5](#0-4) 
4. `Registry.process` proceeds to call the registered handler with `WebhookMetadata.new(shop: "shop-b.myshopify.com", ...)`, i.e., the attacker-controlled shop value, even though the HMAC never authenticated that this payload belongs to `shop-b`: [6](#0-5) 
5. Any host-app logic keyed on `data.shop` (e.g., data deletion/redaction for `customers/redact`, order processing, session lookups) is executed against the wrong tenant, using attacker-supplied data.
