### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) fields are trusted from unauthenticated headers while the HMAC only covers the request body - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` validates a webhook's authenticity solely by checking the HMAC over the raw request body, but the `shop` domain that is subsequently handed to the app's handler (and used for tenant attribution) is read from an HTTP header that is not covered by that HMAC. This breaks the intended binding `hmac == HMAC(secret, body)` **and** `shop == the tenant that produced this HMAC-signed body`.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body, and `hmac` is derived from the `hmac-sha256` header: [1](#0-0) [2](#0-1) 

The `shop`, `topic`, `webhook_id`, and `api_version` fields are read straight from HTTP headers that are **not** included in `to_signable_string`, so they are never covered by the HMAC: [3](#0-2) 

`Registry.process` validates only the HMAC (over the body) and then constructs `WebhookMetadata` directly from `request.shop`, `request.topic`, etc., with no additional check that this shop actually matches the tenant whose secret/body produced the HMAC: [4](#0-3) 

Since `Utils::HmacValidator.validate` computes the signature purely from `verifiable_query.to_signable_string` (the raw body for webhooks) against `Context.api_secret_key`: [5](#0-4) 

...any request whose body is unchanged keeps a valid signature no matter what the `shopify-shop-domain` header says. An attacker who legitimately installs the app on their own store (an "unprivileged" merchant, not a privileged account of the target) will receive real, validly-signed webhook deliveries for their own shop. Because the signature check ignores the `shop` header entirely, the attacker can capture such a delivery and replay it to the app's public webhook endpoint with the `shopify-shop-domain` (and/or `shopify-topic`) header rewritten to name a victim shop. The HMAC still validates (body unchanged), yet `WebhookMetadata.shop` now reports the victim's domain to the app's handler, exactly matching the documented API surface: [6](#0-5) 

The documentation explicitly promises that `Registry.process` "will verify the request did indeed come from Shopify," but the verification only proves body integrity, not the identity of the shop the app attributes the payload to — an authentication-bypass on the tenant-binding, not just on the payload.

### Impact Explanation
This lets an attacker who controls one legitimate shop install cause an app to process attacker-supplied data under a different, victim shop's identity — a cross-tenant confusion/injection vulnerability. If the handler uses `data.shop` to select which merchant's records to update, deduplicate `webhook_id`s per shop, or otherwise gate access/state by shop, an attacker can poison or corrupt another tenant's data purely by controlling headers on a replayed, still-validly-HMAC'd request.

### Likelihood Explanation
Any developer who installs the app once obtains a real HMAC-signed webhook body/signature pair for their own shop. Replaying that exact body with a modified, uncovered `shopify-shop-domain` header to the app's public webhook URL is trivial and requires no knowledge of `api_secret_key` — likelihood is high given the endpoint is intentionally public-facing.

### Recommendation
Include the shop domain (and topic/webhook id) in the value that is signed and verified, or independently verify that `request.shop` corresponds to a shop that has an active, registered webhook subscription/session before trusting it in `WebhookMetadata`. At minimum, document/require callers to cross-check `data.shop` against known installed shops before acting on webhook data.

### Proof of Concept
1. Install the target app on attacker-controlled shop `attacker.myshopify.com`.
2. Trigger a webhook (e.g. `orders/create`) so Shopify delivers a POST to the app's webhook endpoint with body `B`, header `x-shopify-hmac-sha256: HMAC(secret, B)`, and `x-shopify-shop-domain: attacker.myshopify.com`.
3. Capture this raw request, then resend it directly to the app's public webhook endpoint, keeping body `B` and the HMAC header identical, but changing `x-shopify-shop-domain` to `victim.myshopify.com`.
4. `Utils::HmacValidator.validate` succeeds because it only checks `B` against the unchanged HMAC.
5. `Registry.process` builds `WebhookMetadata` with `shop: "victim.myshopify.com"`, and the app's handler (per the documented usage pattern) processes/attributes attacker-controlled body `B` as if it originated from `victim.myshopify.com`.

        def process(request)
          raise Errors::InvalidWebhookError, "Invalid webhook HMAC." unless Utils::HmacValidator.validate(request)

          handler = @registry[request.topic]&.handler

          unless handler
            raise Errors::NoWebhookHandler, "No webhook handler found for topic: #{request.topic}."
          end

          handler.handle(data: WebhookMetadata.new(topic: request.topic, shop: request.shop,
            body: request.parsed_body, api_version: request.api_version, webhook_id: request.webhook_id))
        end

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
```
