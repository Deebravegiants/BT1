Confirmed: the webhook HMAC in `lib/shopify_api/webhooks/request.rb` only covers `@raw_body` — the `shop` (and `topic`/`webhook-id`) fields are read from unauthenticated headers and are never part of `to_signable_string`.This confirms the vulnerability. `WebhookMetadata.shop` (`lib/shopify_api/webhooks/webhook_handler.rb:8`) is populated directly from `request.shop`, which comes from an unauthenticated header, and is handed to the app's `handle` method as trusted data — completing the tenant-confusion chain.

### Title
Webhook HMAC does not cover the `shop-domain` header, allowing cross-tenant impersonation of webhook payloads - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating an HMAC computed over the raw request body [1](#0-0) . The `shop` value that is subsequently trusted and forwarded to the app's handler is read from the `x-shopify-shop-domain` header, which is never included in the signed material [2](#0-1) .

### Finding Description
`Request#to_signable_string` returns only `@raw_body` [3](#0-2) , and `HmacValidator.validate`/`validate_signature` compute/compare the HMAC exclusively against that signable string using the app's single, shared `api_secret_key` [4](#0-3) . The `shop`, `topic`, and `webhook_id` accessors are read straight from HTTP headers with no cryptographic binding to the HMAC [5](#0-4) .

Because the same `api_secret_key` is shared across every shop that installs the app, any tenant that legitimately receives a webhook (with a valid body+HMAC pair addressed to their own shop) can replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `x-shopify-shop-domain` header for an arbitrary victim shop domain. `Registry.process` only checks `Utils::HmacValidator.validate(request)` [6](#0-5)  — it never verifies that the `shop` header is bound to the signed body — so the forged request passes validation. The handler then receives a `WebhookMetadata` whose `shop` field is taken directly from the attacker-controlled header [7](#0-6) , and constructs it from `request.shop` in `Registry.process` [8](#0-7) .

This breaks the identity binding: `shop asserted in the HTTP header != shop actually bound by the HMAC signature`. The gem's own tests reinforce that the HMAC is computed purely over the JSON body with no shop binding [9](#0-8) .

### Impact Explanation
An attacker who is a legitimate merchant of the target app (an unprivileged internet user relative to other tenants) can forge a webhook event attributed to any other shop that uses the same app, since the shop identity is not authenticated. Any host application that uses `data.shop` from `WebhookMetadata` to key per-tenant records, authorize writes, or trigger tenant-scoped side effects (the intended and documented usage pattern, per `docs/usage/webhooks.md`) will act on attacker-controlled data as if it originated from the victim shop — a cross-tenant access vulnerability.

### Likelihood Explanation
Any app developer testing/installing the app on their own store can obtain a valid signed webhook payload for their own shop, then trivially replay it with an altered `shop-domain` header against the app's public webhook endpoint. No secrets, tokens, or privileged access are required — only network access to the app's webhook callback URL, which is public by design.

### Recommendation
Include the `shop-domain` (and ideally `topic`/`webhook-id`) header values as part of the HMAC-signed material verified by `Request#to_signable_string`, or independently verify that the `shop` header matches a shop that is expected/registered for this specific webhook subscription before trusting it in `WebhookMetadata`.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and configures an HTTP webhook handler receiver they control (or captures the raw POST Shopify sends to their own endpoint).
2. Attacker records the raw JSON body `B` and the corresponding `X-Shopify-Hmac-Sha256` header `H` that Shopify computed using the app's shared `api_secret_key`.
3. Attacker sends a POST request directly to the target app's webhook processing route with:
   - body: `B` (unchanged)
   - `x-shopify-hmac-sha256`: `H` (unchanged)
   - `x-shopify-shop-domain`: `victim-shop.myshopify.com` (forged)
   - `x-shopify-topic`: unchanged or forged as desired
4. `ShopifyAPI::Webhooks::Request.new` accepts these headers [10](#0-9) ; `Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks `B` against `H` using the shared secret [1](#0-0) .
5. The registered handler is invoked with `WebhookMetadata.shop == "victim-shop.myshopify.com"` even though the payload content actually belongs to `attacker-shop.myshopify.com`, achieving cross-tenant data/event injection.

      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end
