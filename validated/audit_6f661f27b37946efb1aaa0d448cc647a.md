### Title
Webhook HMAC does not bind the shop domain, enabling cross-tenant webhook forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable string from the raw request body only, while `shop`, `topic`, `webhook_id`, and `api_version` are all read directly from unauthenticated request headers. `Webhooks::Registry.process` validates only that the body's HMAC is correct, then trusts the header-derived `shop` value to attribute the webhook to a tenant. This breaks the intended binding `HMAC(body) == HMAC(body, shop)`; the signature never covers the shop the data is attributed to.

### Finding Description
`Request#to_signable_string` returns just `@raw_body`: [1](#0-0) 

`Request#shop`, `#topic`, and `#webhook_id` are parsed straight from headers with no cryptographic tie to the body or the HMAC: [2](#0-1) 

`Registry.process` validates the HMAC using `Utils::HmacValidator.validate(request)` (which only checks `to_signable_string`, i.e. the body) and then immediately hands `request.shop` to the app's handler as the trusted tenant identifier: [3](#0-2) 

`HmacValidator.validate` confirms the body's integrity against the app's `api_secret_key`, but the signable string produced by `AuthQuery`/`Request` never incorporates `shop`: [4](#0-3) 

Because the shared `client_secret` is identical for every shop that installs a given (public) app, any shop that installs the app receives legitimate webhook deliveries with a valid `body`+`hmac` pair signed by the app's own secret. An attacker who controls such a shop can capture one of these deliveries and replay the exact same `body`/`hmac` pair while substituting the `X-Shopify-Shop-Domain` (or `shopify-shop-domain`) header with a victim shop's domain. `HmacValidator.validate` still passes (it only re-derives the HMAC from the body), and `Registry.process` will invoke the app's webhook handler believing the event originated from the victim shop.

The binding that should hold is:
`shop_the_handler_trusts == shop_that_the_HMAC_actually_authenticates`

Here it instead is:
`shop_the_handler_trusts == shop_header_value` (attacker-controlled, unauthenticated)
while
`shop_that_the_HMAC_actually_authenticates == "any shop able to produce a valid body/hmac pair with this app's secret"`

### Impact Explanation
This is a cross-tenant confusion vulnerability: an unprivileged attacker with access to only their own (attacker-owned) installation of a public app can make the host application process webhook data as though it belongs to a different merchant. Depending on how the host app's webhook handlers use `WebhookMetadata#shop` (e.g., to look up/update per-tenant records, revoke access tokens, sync inventory, or trigger uninstall/GDPR-erasure flows), this can lead to cross-tenant data corruption, unauthorized state changes against a victim shop's stored data, or triggering privileged flows (like `app/uninstalled` handling) against a shop the attacker does not control — all without ever needing the target's or the app's `api_secret_key`.

### Likelihood Explanation
Any public/multi-tenant app built on this gem shares one `client_secret` across all installs. An attacker only needs to install the app on a shop they control (trivial for public apps) to receive one legitimate webhook and observe a valid `(body, hmac)` pair, then replay it with a forged `shop-domain` header pointed at any target shop. No secrets, tokens, or privileged access are required — likelihood is high for any app that relies on `request.shop` from `Webhooks::Request` for tenant attribution, which is the gem's documented usage pattern (`WebhookMetadata` is built directly from `request.shop`).

### Recommendation
Bind the shop domain (and ideally topic/webhook id) into the value that is HMAC-verified, or otherwise cryptographically tie the header-derived `shop` to the authenticated body, e.g.:
- Have `Request#to_signable_string` incorporate `shop`/`topic` (this would require coordinating with Shopify's webhook delivery signing scheme), or
- At minimum, document/require that host apps independently verify the `shop` header value against their own record of shops with active webhook subscriptions/access tokens before trusting `WebhookMetadata#shop`, and/or add such a check inside `Registry.process` itself so the gem enforces it uniformly rather than leaving it to individual host apps.

### Proof of Concept
1. Attacker installs the target public app on `attacker-shop.myshopify.com` (a shop they control), and receives a legitimate webhook delivery, e.g. for `orders/create`, with headers:
   - `X-Shopify-Shop-Domain: attacker-shop.myshopify.com`
   - `X-Shopify-Hmac-Sha256: <valid-hmac-of-body>`
   - body: `{"id": 1, ...}`
2. Attacker captures `body` and `X-Shopify-Hmac-Sha256` unchanged, and replays a new HTTP POST to the app's webhook endpoint with the same body/HMAC but:
   - `X-Shopify-Shop-Domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only recomputes the HMAC over `request.to_signable_string` (the raw body) — this check passes because the body is unmodified. [3](#0-2) 
4. The handler is invoked with `WebhookMetadata.new(... shop: request.shop ...)` where `request.shop` is `"victim-shop.myshopify.com"`, taken straight from the attacker-controlled header, causing the app to process attacker-supplied data under the victim tenant's identity. [5](#0-4)
