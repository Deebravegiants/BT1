### Title
Arbitrary swap-route contract can add victim token transfers to the signed authorization tree - (File: `contracts/controller/src/strategies/swap.rs`)

### Summary

`swap_collateral`, `swap_debt`, and related strategy paths accept caller-supplied route bytes and invoke the configured router without binding that route to trusted venue contracts. The router resolves pool addresses from the payload and invokes them; malicious route code can therefore call `token.transfer(victim, attacker, amount)` while the victim’s authorization frame is active. Simulation records that transfer as a child of the victim’s signed authorization tree, and the host executes it if the victim signs the poisoned tree. This permits theft of unrelated wallet tokens beyond the collateral amount routed through the controller.

### Finding Description

`process_swap_collateral` authenticates `caller`, verifies account ownership or delegation, and then forwards the caller-controlled `swap` bytes into `withdraw_and_swap_from_supply`. [1](#0-0) 

`swap_tokens` authorizes only the controller’s exact input transfer to the router, but it then passes the opaque route to `router.execute_strategy`. [2](#0-1) 

Its post-call checks only compare the controller’s input and output token balances; they do not prevent route-selected code from making unrelated calls under the user’s authorization context. [3](#0-2) 

Inside the router, each decoded swap instruction reads its pool and token addresses from the caller-controlled `assets` registry and dispatches to a venue adapter. [4](#0-3) 

The Soroswap adapter directly invokes the route-selected `pool` contract’s `get_reserves` and `swap` functions. [5](#0-4) 

Because the router does not constrain `hop.pool` to an allowlist, an attacker can make that address a malicious contract. That contract can call a token transfer with `victim` as `from`; Soroban simulation places the requested authorization beneath the victim’s root invocation. The checked-in authorization test demonstrates that simulation records the rogue transfer and that enforcing mode executes it when the victim signs the resulting tree. [6](#0-5) [7](#0-6) 

### Impact Explanation

A malicious route can steal any token held by the victim’s wallet, not only the collateral amount supplied to `swap_collateral`. In the demonstrated sequence, Alice receives the expected swap output while an unrelated wallet token is transferred to the attacker. [8](#0-7) 

The same authorization-tree behavior applies to other user-supplied strategy routes that call `swap_tokens`, including `swap_debt` and debt repayment with collateral. [9](#0-8) 

This is theft of user funds. The controller’s measured input/output checks bound loss of routed collateral, but they do not observe or bound side effects against the signer’s wallet. [3](#0-2) 

### Likelihood Explanation

Exploitation requires the victim to invoke a strategy with an attacker-crafted route and sign an authorization tree containing the malicious child transfer; an attacker cannot force that signature solely by submitting the transaction. However, route construction is normally delegated to an off-chain quoter or frontend, and users are unlikely to decode every nested authorization produced by simulation. An unprivileged attacker can deploy the malicious pool, generate a route that produces a superficially valid swap, and encode the theft inside the signed tree.

The repository’s own threat model recognizes that routes have no venue allowlist and that route-selected code can add a caller-funded token transfer to the signer’s authorization tree. [10](#0-9) 

### Recommendation

Do not allow route payloads to select arbitrary venue contracts. Maintain an on-chain registry of approved pool or adapter targets, or use a fixed venue dispatch interface that cannot route through attacker-deployed pool addresses.

Until protocol-level restriction exists, wallets and quote builders must decode the simulated `SorobanAuthorizationEntry` tree and reject any children other than the exact expected token transfer. A controller-originated route should also compare the route’s decoded token and venue registry with the assets authorized by the operation rather than treating `swap` as opaque bytes.

### Proof of Concept

1. Victim owns a lending account with USDC collateral and also holds an unrelated wallet token.
2. Attacker deploys a malicious contract whose `swap` method calls:
   `token::Client::new(&env, &wallet_token).transfer(&victim, &attacker, &amount)`. [11](#0-10) 
3. Attacker supplies a route whose `pool` field is that contract and whose output is priced to satisfy the normal swap checks.
4. Victim calls:
   `controller.swap_collateral(victim, account_id, usdc_key, amount, eth_key, malicious_route)`. [12](#0-11) 
5. Simulation records a child invocation for `wallet_token.transfer(victim, attacker, amount)` beneath the victim’s `swap_collateral` authorization. [13](#0-12) 
6. If the victim signs that generated tree, the malicious transfer executes and the attacker receives the wallet token while the swap still deposits the expected output. [7](#0-6)
