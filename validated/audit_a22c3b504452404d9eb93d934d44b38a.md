### Title
Unchecked ERC20 boolean return value in `withdraw()`/`SweepDust` allows silent transfer failures to be treated as success on Tron - (File: evm/tron/contracts/apps/IntentGatewayV2.sol)

### Summary
The Tron variant of the `IntentGatewayV2` intents escrow contract redeems escrowed tokens and sweeps dust using a raw low-level `.call()` to the ERC20 `transfer` function, checking only that the call did not revert (`success`) but never decoding/validating the ERC20's returned boolean. Non-standard ERC20 tokens (including some deployed on Tron/TVM, and any token intentionally or accidentally returning `false` instead of reverting on failure) can cause this to record a token transfer as completed while the beneficiary receives nothing.

In each case, only the outer `bool success` from `.call()` is checked (i.e., that the call did not revert / target has code). The ABI-decoded boolean payload that ERC20 `transfer` returns to signal application-level failure is never inspected. Per the referenced report's bug class, ERC20 implementations are not required to revert on failure — many return `false` instead. Against such a token, `success` is `true` (the call executed without reverting) even though zero tokens moved.

Contrast this with the mainline EVM `IntentGatewayV2` (`evm/src/apps/IntentGatewayV2.sol`) and the `HyperFungibleToken`/`WrappedHyperFungibleToken` contracts, which consistently use OpenZeppelin's `SafeERC20.safeTransfer`/`safeTransferFrom` (which reverts on a `false` return), e.g.: [4](#0-3) 
The Tron fork deliberately drops `SafeERC20` in favor of raw `.call()` checks that omit the return-data validation, reintroducing the exact vulnerability class SafeERC20 is designed to prevent.

`withdraw()` is reached from the unprivileged `onGetResponse` path (cancel-order GET response) and from `RedeemEscrow`/`RefundEscrow` message handling in `onAccept`, both of which are triggered by relayed cross-chain messages/proofs that any relayer can submit once the underlying request/response is valid — i.e., this is reachable by an ordinary relayer/user completing the intents lifecycle, not just governance or admins. [5](#0-4) 

### Impact Explanation
If the input or fee token used in an order is a non-standard ERC20 (returns `false` rather than reverting on failure — e.g., due to insufficient allowance edge cases in some TVM token implementations, paused/blacklist states, or a malicious token registered by a user placing the order), `withdraw()` will:
- Decrement `_orders[body.commitment][token]` and mark `_filled[body.commitment] = beneficiary`, permanently closing out the order,
- while the beneficiary receives none of the escrowed tokens.

This results in permanent loss of the escrowed funds for the intended beneficiary (solver or user, depending on `isRefund`), since the order is marked filled/refunded and cannot be re-claimed. It also breaks the escrow's accounting invariant that `_orders` balances reflect tokens actually held versus distributed, which can cascade into fund-freezing or theft scenarios in combination with other flows relying on `_filled`/`_orders` state.

### Likelihood Explanation
Likelihood depends on the specific ERC20/TRC20 tokens configured as order inputs; not all tokens exhibit false-on-failure semantics, so this is not automatically triggerable against every token. However, because arbitrary tokens can be specified as `order.inputs[i].token` by the order placer (per `placeOrder`), and TVM/TRC20 tokens have historically diverged from strict EIP20 revert semantics, an attacker or unlucky integrator can readily select or construct a token that returns `false` on transfer failure, deterministically triggering silent fund loss on every withdrawal path for that token.

### Recommendation
Replace the raw `.call()` + `success`-only check with OpenZeppelin's `SafeERC20.safeTransfer` (as already used in the mainline EVM contracts), or explicitly decode and validate the returned boolean:
```solidity
(bool success, bytes memory data) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
if (!success || (data.length > 0 && !abi.decode(data, (bool)))) revert TransferFailed();
```
Apply this fix consistently to `withdraw()` (input-token and fee-token transfers) and the `SweepDust` handler in `evm/tron/contracts/apps/IntentGatewayV2.sol`.

### Proof of Concept
1. Order placer creates an order with `order.inputs[0].token` set to a TRC20 token contract that implements `transfer` to return `false` (instead of reverting) whenever, e.g., the contract is paused or a per-call condition fails, while still executing without reverting.
2. User calls `placeOrder`; tokens are escrowed via `safeTransferFrom` (mainline behavior) and recorded in `_orders[commitment][token]`.
3. Once the order is filled/cancelled cross-chain, a `RedeemEscrow`/`RefundEscrow` message (or GET response) triggers `withdraw()`.
4. The token's `transfer(beneficiary, amount)` call executes and returns `false` (e.g., token owner toggles a pause flag or the token has a bug/feature causing false-return) without reverting; `success` is `true` because the call itself did not revert.
5. `withdraw()` proceeds: `_orders[body.commitment][token] -= amount;` executes, and `_filled[body.commitment] = beneficiary;` is set, closing the order permanently.
6. The beneficiary's on-chain token balance is unchanged — the escrowed tokens remain stuck in the `IntentGatewayV2` contract with no code path to reclaim them, since the order is already marked filled.
