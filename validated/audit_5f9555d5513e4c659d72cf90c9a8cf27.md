### Title
Webhook HMAC in `HmacValidator.validate` signs only the raw body, never `topic` or `shop-domain`, letting a replayed webhook be relabeled to any topic/shop - ([File: lib/shopify_api/webhooks/request.rb], [File: lib/shopify_api/utils/hmac_validator.rb])

### Summary
`Request#to_signable_string` returns only `@raw_body` [1](#0-0) , and `HmacValidator.validate_signature` verifies the HMAC solely against that raw body with the app's shared `api_secret_key` [2](#0-1) . Because `topic`, `shop`, `api_version`, and `webhook_id` are pulled straight from unauthenticated headers and never mixed into the signed content [3](#0-2) , an attacker who legitimately receives one valid signed webhook (e.g., from their own installed dev shop) can replay the identical body/HMAC while freely rewriting the `shopify-topic` and `shopify-shop-domain` headers, and `Registry.process` will still accept and dispatch it [4](#0-3) .

### Finding Description
The claimed binding is: `hmac_valid(raw_body, api_secret_key) == true` should imply `(topic_header, shop_header)` are the authentic pair that Shopify associated with `raw_body`. In this gem that equality never holds because those header values are outside the signable string.

Trace:
- `Request#initialize` only checks that the three headers exist, not that they're consistent with the body [5](#0-4) .
- `to_signable_string` = `@raw_body` only [1](#0-0) .
- `HmacValidator.validate` computes `HMAC-SHA256(api_secret_key, raw_body)` and compares to the `hmac-sha256` header via `OpenSSL.secure_compare` [6](#0-5) . Nothing here touches `topic` or `shop`.
- `Registry.process` gates only on this body-only HMAC result, then trusts `request.topic` to select the handler and `request.shop` to populate `WebhookMetadata` passed to that handler [4](#0-3) .

`api_secret_key` is the app's single client secret shared across every shop that installs the app (it is not shop-specific), so any attacker who installs the app on their own shop can obtain a validly HMAC'd webhook body from Shopify. They can then POST that exact body/HMAC to the app's webhook endpoint while substituting `X-Shopify-Topic: customers/create` and `X-Shopify-Shop-Domain: victim.myshopify.com`. `HmacValidator.validate` still returns `true` because the body/HMAC pair itself is genuinely valid; the mismatched topic/shop headers are never checked against anything cryptographic. The handler registered for `customers/create` then receives an order-shaped body and `shop: "victim.myshopify.com"`, i.e., both the topic→schema binding and the shop→tenant binding are broken simultaneously.

None of the existing guards catch this: `HmacValidator.validate` only checks the body signature; there is no `ShopValidator.sanitize!` call in this flow; there is no comparison of `topic` or `shop` against any signed value; Sorbet's runtime typing only enforces that `topic`/`shop` are `String`, not that they are truthful.

### Impact Explanation
A host app that trusts `WebhookMetadata#shop` to select the tenant record to write to (a documented, expected usage pattern) can have attacker-controlled or wrongly-shaped data attributed to an arbitrary victim shop, i.e., cross-tenant data corruption/injection driven entirely by an unprivileged attacker who merely installed the app on their own store. This is repeatable per-request against arbitrary victim shop domains known to the attacker, matching the Critical "cross-tenant access" category.

### Likelihood Explanation
Preconditions are met by any unprivileged attacker: install the app on a dev/test shop (allowed by rules), trigger any webhook to capture a valid raw body + HMAC pair, then replay to the app's public webhook endpoint with rewritten `topic`/`shop-domain` headers. No secrets, no privileged access, and no TLS interception are required — this is a straight HTTP replay. The only host-app-side requirement is that a handler exists for the target topic and that it trusts `data.shop` / `data.body` shape, which is the standard, documented usage of this gem's `Registry`/`WebhookHandler` API.

### Recommendation
Bind `topic`, `shop`, `api_version`, and `webhook_id` into the authenticated context: either include these header values in `to_signable_string` (not possible without changing Shopify's own signing scheme) or, more practically, have `Registry.process` cross-check the declared `topic` against the merchant's actual webhook subscription registered for that endpoint path/shop, and validate that `parsed_body`'s shape matches the topic's expected schema before dispatch. At minimum, document prominently that host apps must not conflate `data.shop`/`data.topic` from `WebhookMetadata` with anything more trustworthy than the HMAC-verified body, and add a schema-per-topic validation hook in `Registry.process`.

### Proof of Concept
```ruby
# test/webhooks/registry_topic_shop_confusion_test.rb
require "test_helper"

class RegistryTopicShopConfusionTest < Minitest::Test
  def setup
    ShopifyAPI::Context.setup(api_key: "key", api_secret_key: "secret", ...)
    ShopifyAPI::Webhooks::Registry.clear
  end

  def test_replayed_body_with_forged_topic_and_shop_still_passes_hmac
    order_body = '{"id":123,"line_items":[]}' # legitimately signed for orders/create
    valid_hmac = Base64.strict_encode64(
      OpenSSL::HMAC.digest("sha256", "secret", order_body)
    )

    fake_customers_handler = Class.new do
      include ShopifyAPI::Webhooks::WebhookHandler
      attr_reader :received
      def handle(data:)
        @received = data
      end
    end.new

    ShopifyAPI::Webhooks::Registry.add_registration(
      topic: "customers/create", delivery_method: :http, path: "/wh", handler: fake_customers_handler
    )

    forged_request = ShopifyAPI::Webhooks::Request.new(
      raw_body: order_body,
      headers: {
        "x-shopify-topic" => "customers/create",       # forged topic
        "x-shopify-hmac-sha256" => valid_hmac,          # untouched, still valid
        "x-shopify-shop-domain" => "victim.myshopify.com", # forged shop
      },
    )

    ShopifyAPI::Webhooks::Registry.process(forged_request)

    # Binding check: topic dispatched to == "customers/create" but body schema == order payload
    refute fake_customers_handler.received.body.key?("first_name"),
      "handler received an order-shaped body under the customers/create topic"
    assert_equal "victim.myshopify.com", fake_customers_handler.received.shop
    # No exception was raised despite topic/body/shop mismatch -> HMAC validation alone is insufficient binding
  end
end
```

      sig { params(raw_body: String, headers: T::Hash[String, T.untyped]).void }
      def initialize(raw_body:, headers:)
        # normalize the headers by forcing lowercase, removing any prepended "http"s, and changing underscores to dashes
        headers = headers.to_h { |k, v| [k.to_s.downcase.sub("http_", "").gsub("_", "-"), v] }

        missing_headers = []
        ["topic", "hmac-sha256", "shop-domain"].each do |name|
          unless headers.key?("shopify-#{name}") || headers.key?("x-shopify-#{name}")
            missing_headers << "shopify-#{name} or x-shopify-#{name}"
          end
        end
        unless missing_headers.empty?
          raise Errors::InvalidWebhookError,
            "Missing one or more of the required HTTP headers to process webhooks: #{missing_headers}"
        end

        @headers = headers
        @raw_body = raw_body
      end

        def validate(verifiable_query)
          return false unless verifiable_query.hmac

          result = validate_signature(verifiable_query, Context.api_secret_key)
          if result || Context.old_api_secret_key.nil? || T.must(Context.old_api_secret_key).empty?
            result
          else
            validate_signature(verifiable_query, T.must(Context.old_api_secret_key))
          end
        end

        private

        sig { params(verifiable_query: VerifiableQuery, secret: String).returns(T::Boolean) }
        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
