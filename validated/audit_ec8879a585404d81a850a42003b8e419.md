### Title
Anyone can force a flash-loan `receiver` contract's standing token allowance to the pool to be spent via `transfer_from`, draining the receiver's balance in forced fees - (File: contracts/pool/src/ops/flash.rs)

### Summary
`pool::flash::apply` pays out principal to a caller-supplied `receiver`, invokes its `execute_flash_loan` callback, then `collect_repayment` pulls `principal + fee` out of `receiver` using the ERC20-style allowance mechanism (`asset.allowance(receiver, pool)` + `asset.transfer_from(pool, receiver, pool, total_repayment)`). The `receiver` is an arbitrary caller-supplied argument — the allowance owner never authorizes the flash loan. This is the same bug class as H-07: a third party can trigger spending of a victim's pre-approved allowance on a router-like contract. The only gate on `receiver` is `require_wasm_receiver` (must be a WASM contract), and the initiator's `require_auth` on `controller::flash_loan` proves nothing about the receiver.

### Finding Description
In `contracts/pool/src/ops/flash.rs`:

```rust
fn collect_repayment(env, asset, pool, receiver, terms) {
    assert!(asset.allowance(receiver, pool) >= terms.total_repayment);
    asset.transfer_from(pool, receiver, pool, &terms.total_repayment);
    require_balance(env, asset, pool, terms.balance_after_repayment);
}
```

`apply` first executes `asset.transfer(&pool, &receiver, &amount)` — the victim contract is *credited* `amount`, then `amount + fee` is pulled back via its allowance. Net effect on the victim: it loses `fee` tokens and is left holding `amount` it never asked for (which is pulled right back out — the net is exactly `-fee`).

The repayment flow itself *requires* receivers to grant the pool an allowance covering `principal + fee`. Any reusable flash-receiver integration contract that grants the pool an allowance larger than a single repayment, or that approves ahead of its callback (a natural pattern, since Soroban allowances also carry an expiration ledger and contracts may approve once for a window), leaves a residual `allowance(receiver, pool) > 0` that any unprivileged address can weaponize.

Attack path (single unprivileged EOA/contract as `initiator`):
1. Identify a WASM contract `X` with `allowance(X, pool) > 0` on a flashloanable asset (the allowance query is a public view).
2. Call `controller::flash_loan(initiator = attacker, receiver = X, amount = A, data = _)` on an asset where `A` is large (bounded by pool reserves and `allowance(X, pool) - fee`).
3. The pool transfers `A` to `X`, invokes `X.execute_flash_loan(...)` (which succeeds whenever `X`'s callback does not revert — e.g., a receiver that only validates `initiator == pool` or ignores unknown calls), then `collect_repayment` spends `A + fee` of `X`'s allowance.
4. `X` ends the call `fee` tokens poorer; the fee is booked as protocol revenue. Repeat until `X`'s balance or allowance is exhausted — each call burns `fee = A * flashloan_fee_bps / 10_000` of `X`'s funds.

Note that `require_balance` after the callback only checks the pool's own balance, so nothing constrains which contract is named as `receiver`. The flash-loan flag (`INV-FLASH-02` / `require_not_flash_loaning`) does not help either — it blocks reentry into controller position flows, not the choice of victim.

### Impact Explanation
Unprivileged, collateral-free theft of user funds: the victim contract loses `fee` tokens per invocation, paid to protocol revenue, without ever authorizing the flash loan. With a large victim allowance and repeated calls, the attacker can drain the victim's entire token balance in fee increments. Because the flash principal is borrowed and returned atomically, the attacker needs no capital. This is directly analogous to H-07: a stored allowance on a shared spender contract (the pool) is consumed at the behest of an unrelated caller who controls the `owner`-equivalent parameter (`receiver`).

### Likelihood Explanation
Medium likelihood. Preconditions: (a) a flashloanable market exists, (b) some WASM contract holds `allowance(X, pool) >= amount + fee` on that asset, and (c) `X.execute_flash_loan` does not revert for a foreign initiator. Condition (b) is realistic precisely because the protocol's repayment design *forces* receivers to keep allowances to the pool; any residual or ahead-of-time approval qualifies. Condition (c) holds for receivers whose callback validates only the caller being the pool or tolerates unknown `data`. No timing, governance, or price dependency is needed.

### Recommendation
Do not let the caller choose whose allowance is spent. Two options:

- Pull repayment from the `initiator` (the `require_auth`'d caller) instead of `receiver`: check `asset.allowance(initiator, pool)` / `transfer_from(pool, initiator, pool, ...)` after the callback, making the flash borrower — not an arbitrary third party — liable for `principal + fee`. The receiver would first return the principal to the initiator (or the initiator funds the repayment directly), mirroring the H-07 fix of binding `owner = msg.sender`.
- Alternatively, have the pool authorize a `transfer(receiver, pool, total_repayment)` inside `authorize_as_current_contract` scoped to the receiver's own callback invocation, or require the receiver to push repayment itself (measure balance delta instead of `transfer_from`), eliminating standing allowances to the pool entirely.

At minimum, document that `receiver` must never hold a standing allowance to the pool, since the current design makes any such allowance publicly spendable.

### Proof of Concept
1. Deploy/identify a WASM contract `X` that implements `execute_flash_loan` as a no-op (or permissive handler) and has previously called `token.approve(X, pool, LARGE, expiry)` — e.g., a reusable receiver integration.
2. Attacker calls `controller::flash_loan(initiator = attacker, receiver = X, hub_asset = flashloanable asset, amount = min(pool_reserves, LARGE - fee), data = empty)`.
3. Execution: pool → `X`: `+amount`; callback on `X` succeeds; `asset.allowance(X, pool) >= amount + fee` passes; `transfer_from(pool, X, pool, amount + fee)` debits `X`; pool balance check `balance_after_repayment = pre + fee` passes; `finalize` books `fee` as protocol revenue.
4. Result: `X` lost `fee` tokens; `balance(X) = X0 - fee`; `allowance(X, pool)` reduced by `amount + fee`. Repeat with remaining allowance until `X` is drained in fee increments — `X` never signed any auth for these calls.

Severity: **Medium** (conditional on a receiver contract holding residual allowance to the pool; loss is bounded per-call by the flash fee but is repeatable and requires no capital). [1](#0-0) [2](#0-1) [3](#0-2)

pub(crate) fn apply(
    env: &Env,
    hub_asset: HubAssetKey,
    initiator: Address,
    receiver: Address,
    amount: i128,
    data: Bytes,
) -> i128 {
    let mut cache = prepare(env, hub_asset, amount);
    require_wasm_receiver(env, &receiver);

    let pool = env.current_contract_address();
    let asset = token::Client::new(env, &cache.params().asset_id);
    let terms = terms(
        env,
        amount,
        cache.params().flashloan_fee,
        asset.balance(&pool),
    );

    asset.transfer(&pool, &receiver, &amount);
    require_balance(env, &asset, &pool, terms.balance_after_payout);
    invoke_receiver(
        env, &cache, &receiver, initiator, amount, terms.fee, &pool, data,
    );

    require_balance(env, &asset, &pool, terms.balance_after_payout);
    collect_repayment(env, &asset, &pool, &receiver, &terms);

    finalize(env, &mut cache, terms.fee);
    terms.fee
}

fn collect_repayment(
