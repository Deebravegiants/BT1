### Title
Webhook `shop-domain` header is not covered by the HMAC signature, allowing cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` derives the tenant identity (`shop`) from the `X-Shopify-Shop-Domain` HTTP header, but the HMAC signature it validates against only covers the raw request body. Any party that possesses one valid `(raw_body, hmac)` pair (e.g. a legitimate merchant who received a genuine webhook for their own shop) can resend that exact body/HMAC pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header. `Utils::HmacValidator.validate` will still succeed because it only re-computes the HMAC over the signable string, which is the body alone, and the forged shop is then handed to the app's handler as the trusted tenant.

### Finding Description
The identity binding that should hold is:
`shop asserted in Registry.process == shop covered by the verified HMAC`

`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`Request#shop` is read straight from the unsigned `shopify-shop-domain` header: [2](#0-1) 

`Registry.process` validates the HMAC (over body only) and then passes `request.shop` — sourced from the unauthenticated header — directly to the registered handler as the trusted tenant identifier: [3](#0-2) 

`Utils::HmacValidator.validate` performs a constant-time compare of the computed signature against the provided one, using `verifiable_query.to_signable_string`, which for webhooks is body-only: [4](#0-3) 

Before the attacker's request: for a genuine webhook, `shop-domain` header value equals the shop that Shopify actually sent the event for, and this equality is only true because Shopify controls both the header and the HMAC target consistently.

After the attacker's request: an attacker who has captured a valid `(raw_body, hmac)` pair (trivially available to them for their own shop, since webhook bodies are not secret and are delivered to app-controlled endpoints) can replay that same body/HMAC to the app's webhook endpoint with a different `shop-domain` header value. `HmacValidator.validate` still returns `true` because it never inspects the header, so `Registry.process` calls the handler with `WebhookMetadata.new(topic: ..., shop: request.shop, body: request.parsed_body, ...)` where `shop` is attacker-controlled and now diverges from the shop whose credentials/webhook actually produced the signed body.

This is a direct analog to the reported bug class: a field that is acted upon (`shop`, used as the tenant key for handler dispatch, similar to `inv.asset`/pointer identity in the Solidity report) is not covered by the integrity check (`HMAC`) that is supposed to bind it, exactly like `inPtr`/`outPtr` losing their binding to the correct order after the pointer recalculation bug.

### Impact Explanation
This breaks the tenant boundary enforced by the webhook subsystem: any handler that trusts `WebhookMetadata#shop` as the authenticated identity of the sending shop (e.g. to key data storage, apply mandatory `shop/redact` / `customers/redact` logic, or attribute the payload to a specific merchant record) can be made to process a valid, HMAC-passing payload under an attacker-chosen shop domain. This is cross-tenant data confusion/injection using a fully valid signature, matching the High-impact criterion for cross-tenant access.

### Likelihood Explanation
Exploitation requires only a body+HMAC pair, which is not secret — any merchant/app installer legitimately receives such pairs for their own shop and can freely replay them to the same public webhook endpoint with a modified header, since HTTP headers are entirely attacker-controlled on any request they send. No access token, `client_secret`, or privileged account is required — only the ability to send an HTTP POST to the app's public webhook endpoint, which is unprivileged-internet-reachable by design.

### Recommendation
Include the `shop` (and ideally `topic`, `api_version`, `webhook_id`) header values in the HMAC-signable content, or otherwise cryptographically bind the shop identity to the signed payload, so that `to_signable_string` cannot be satisfied by a replayed body under a different tenant header.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and receives a genuine webhook: raw body `B`, headers including `X-Shopify-Hmac-Sha256: H` (valid for `B`) and `X-Shopify-Shop-Domain: attacker.myshopify.com`.
2. Attacker resends the exact same `B` and `H` to the app's public webhook endpoint, but sets `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because `Request#to_signable_string` only checks `B` against `H`: [5](#0-4) 
4. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` even though the payload/signature never originated from or was verified for that shop.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
