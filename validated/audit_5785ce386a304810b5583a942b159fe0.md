### Title
Webhook shop identity not bound to HMAC signature allows cross-tenant spoofing - ([File: lib/shopify_api/webhooks/registry.rb])

### Summary
`ShopifyAPI::Webhooks::Registry.process` authenticates an inbound webhook solely by validating the HMAC over the raw request body, but the tenant identifier (`shop`) that gets handed to the app's webhook handler is read from an unsigned HTTP header. Because the HMAC secret (`api_secret_key`) is the app's single, shop-agnostic client secret, anyone who can obtain one legitimately-signed `(raw_body, hmac)` pair (e.g. by installing the app on their own store and triggering any webhook event) can replay that same body/signature to the app's public webhook endpoint while substituting an arbitrary `x-shopify-shop-domain` header. The signature still validates, and the app handler executes believing the payload came from the victim shop.

### Finding Description
`ShopifyAPI::Webhooks::Request#shop` is taken directly from the `shopify-shop-domain`/`x-shopify-shop-domain` header: [1](#0-0) 

The value that is actually HMAC-signed is only the raw body: [2](#0-1) 

`Registry.process` verifies the request using `Utils::HmacValidator.validate(request)`, which calls `to_signable_string` (i.e. `@raw_body`) and never touches `shop`, `topic`, or `webhook_id`: [3](#0-2) 

After this body-only check passes, `Registry.process` forwards the unauthenticated `request.shop` straight into `WebhookMetadata`, which is delivered to the app's handler as the trusted tenant identity: [4](#0-3) 

The HMAC secret used here is `Context.api_secret_key` — the app's single client secret, identical for every shop that installs the app, not a per-shop value: [5](#0-4) 

This creates an identity-binding break: `bytes cryptographically verified (raw_body signed with the app's shared secret) != shop identity trusted by the handler (unsigned shopify-shop-domain header)`. An attacker who legitimately controls one shop that has the app installed can capture a valid `(raw_body, hmac)` pair from any webhook delivered to them, then send an HTTP request directly to the app's webhook endpoint with that same body/hmac but an arbitrary victim `shopify-shop-domain` header. `HmacValidator.validate` still returns `true` because it only checks the body, and `Registry.process` calls the handler with `WebhookMetadata#shop` set to the attacker-chosen victim domain.

### Impact Explanation
This qualifies as cross-tenant access: an unprivileged internet user (any merchant able to install the app on their own store) can make the app process/act on data under an arbitrary victim shop's identity without ever obtaining that shop's access token. This is most severe for the mandatory compliance webhooks (`shop/redact`, `customers/redact`, `customers/data_request`, defined in `MANDATORY_TOPICS`) and any handler that keys data lookups/writes/deletes off `WebhookMetadata#shop` — the attacker can trigger destructive or data-disclosing operations scoped to a shop they do not control. [6](#0-5) 

### Likelihood Explanation
Likelihood is high for any app that has installed the gem's webhook processing and exposes an internet-facing webhook endpoint (the documented pattern). The attacker only needs their own legitimate installation of the target app on a shop they control to obtain a valid signed body once, then can replay it with a forged shop header indefinitely, since the signature check never binds to the shop header.

### Recommendation
Include `shop` (and ideally `topic`/`webhook_id`) in the value that is cryptographically authenticated, or otherwise cryptographically bind the shop-domain header to the signed body before trusting it in `WebhookMetadata`. At minimum, `Registry.process` should reject a webhook if the `shop` header does not correspond to a shop session/registration known to the app, rather than passing the raw header value through unauthenticated.

### Proof of Concept
1. Attacker installs the target app on `attacker-shop.myshopify.com` and triggers any registered webhook topic (e.g., `orders/create`), capturing the raw POST body and the `x-shopify-hmac-sha256` header Shopify sent — this HMAC is valid because it's computed with the app's shared `api_secret_key`.
2. Attacker resends the exact same body and `x-shopify-hmac-sha256` value directly to the app's public webhook endpoint, but replaces the header:
   `x-shopify-shop-domain: victim-shop.myshopify.com`
3. `ShopifyAPI::Webhooks::Request.new` accepts the request (all required headers present), and `Utils::HmacValidator.validate(request)` returns `true` since it only hashes `raw_body`.
4. `Registry.process` invokes the registered handler with `WebhookMetadata.new(shop: "victim-shop.myshopify.com", ...)`, causing the app to perform whatever action the handler implements (e.g., data deletion/export for a mandatory compliance topic) against the victim shop, despite the request never having been signed for that shop.
