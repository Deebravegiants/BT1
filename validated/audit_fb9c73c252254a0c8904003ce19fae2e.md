### Title
Webhook `shop`, `topic`, and `webhook_id` fields are trusted without HMAC coverage, enabling cross-tenant webhook spoofing - (File: lib/shopify_api/webhooks/request.rb)

### Summary
`ShopifyAPI::Webhooks::Registry.process` verifies an incoming webhook by validating an HMAC that covers only the raw request body, yet the `shop`, `topic`, and `webhook_id` values used to route and label the webhook to the app's handler come from unauthenticated HTTP headers that are never part of the signed bytes. This breaks the identity binding `HMAC-covered bytes == data trusted for tenant routing`, allowing a legitimate merchant on one shop to replay their own genuinely-signed webhook body while relabelling it as belonging to a different shop that has the same app installed, since the app's `api_secret_key` is shared across all tenants of the app.

### Finding Description
`ShopifyAPI::Webhooks::Request#to_signable_string` returns only the raw body: [1](#0-0) 

while `shop`, `topic`, and `webhook_id` are pulled straight from HTTP headers with no cryptographic binding to the HMAC: [2](#0-1) 

`HmacValidator.validate` only computes the signature over `to_signable_string` (the body), and compares it against the `hmac-sha256` header: [3](#0-2) 

`Registry.process` treats a passing HMAC check as proof the *entire request* (including `shop`) is authentic, then dispatches to the registered handler using the unauthenticated `request.shop`, `request.topic`, and `request.webhook_id`: [4](#0-3) 

The `WebhookMetadata` struct that host apps consume carries this unauthenticated `shop` field directly into application logic, as documented: [5](#0-4) [6](#0-5) 

Because a single `api_secret_key` (the app's `client_secret`) is shared across every merchant that installs the app, any merchant who has legitimately received a signed webhook for their own shop possesses a `(raw_body, hmac)` pair that is valid for *any* shop under the same app. Since `shop` is not part of the signed bytes, that merchant can resend the exact same body/HMAC pair to the app's webhook endpoint with the `shopify-shop-domain` header (and/or `shopify-topic`, `shopify-webhook-id`) changed to point at a different tenant. `Registry.process` will accept it as authentic and hand the forged `shop` value to the handler.

### Impact Explanation
This crosses the gem's own tenant boundary: `HmacValidator.validate` is the *only* authenticity check performed before the handler is invoked with attacker-influenced `shop`/`topic`/`webhook_id` values, none of which are covered by that check. A host app following the gem's documented pattern (`data.shop` used to key storage/business logic, as shown in the gem's own docs) will process/store data under the wrong tenant, satisfying "cross-tenant access" impact without needing any access token, `client_secret`, or privileged account — only requiring that the attacker be a legitimate but unprivileged merchant of the same app on some shop.

### Likelihood Explanation
Any merchant that installs a multi-tenant app built on this gem receives real webhook deliveries with valid HMACs for their own shop. Capturing one `(raw_body, hmac)` pair and replaying it with a modified `shop-domain` header requires no special access, no secrets, and no interaction with Shopify beyond normal app usage, making this readily exploitable by any unprivileged internet user who can install the app once.

### Recommendation
Bind `shop` (and ideally `topic`/`webhook_id`) into the HMAC verification, e.g. by including these header values in `to_signable_string`, or by independently verifying that `request.shop` matches an actively registered, known session/shop before dispatching to the handler. At minimum, document and enforce that host apps must cross-check `data.shop` against an existing, verified session for that shop before trusting it for tenant-scoped operations.

### Proof of Concept
```ruby
# Attacker is a legitimate but unprivileged merchant of the app on shop-a.myshopify.com
# They receive a real webhook delivery (captured raw body + valid HMAC) for their own shop:
raw_body = '{"id":123,"note":"hello"}'
valid_hmac = OpenSSL::HMAC.digest(OpenSSL::Digest.new("sha256"), APP_CLIENT_SECRET, raw_body)

# They replay the identical body+hmac to the app's webhook endpoint,
# but swap the shop-domain header to a victim tenant using the same app:
forged_headers = {
  "shopify-topic" => "orders/create",
  "shopify-hmac-sha256" => Base64.encode64(valid_hmac),
  "shopify-shop-domain" => "shop-b.myshopify.com", # victim tenant, not attacker's own shop
}

request = ShopifyAPI::Webhooks::Request.new(raw_body: raw_body, headers: forged_headers)

# HmacValidator.validate only checks raw_body against valid_hmac -> passes.
# Registry.process dispatches to the handler with data.shop == "shop-b.myshopify.com",
# even though the body/HMAC were never issued for shop-b.
ShopifyAPI::Webhooks::Registry.process(request)
```

## Process a Webhook

To process an http webhook, you need to listen on the route(s) you provided during the Webhook registration process, then when the route is hit construct a `ShopifyAPI::Webhooks::Request` and call `ShopifyAPI::Webhooks::Registry.process`. This will verify the request did indeed come from Shopify and then call the specified handler for that webhook. An example in Rails is shown below:

```ruby
class WebhookController < ApplicationController
  def webhook
    ShopifyAPI::Webhooks::Registry.process(
      ShopifyAPI::Webhooks::Request.new(raw_body: request.raw_post, headers: request.headers.to_h)
    )
    render json: {success: true}.to_json
  end
end
