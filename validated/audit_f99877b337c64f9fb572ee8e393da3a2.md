### Title
Archived collateral positions are interpreted as empty, enabling erroneous bad-debt socialization - ([File: contracts/controller/src/storage/account.rs])

### Summary
An expired or archived `SupplyPositions` entry is loaded as an empty map rather than distinguished from an account with no collateral. A permissionless `clean_bad_debt` call can then value the account’s collateral as zero while retaining its stored debt and socialize debt even though collateral shares still exist in the pool. [1](#0-0) [2](#0-1) 

### Finding Description
`get_account` loads `AccountMeta`, NFT ownership, and both position maps. [3](#0-2)  Missing metadata correctly rejects the account, but missing `SupplyPositions` or `BorrowPositions` is replaced with a newly initialized empty `Map`. [4](#0-3)  The same defaulting behavior applies when a persistent position-map entry has expired or been archived, because `persistent().get()` returns `None`. [5](#0-4) 

The permissionless `clean_bad_debt` path loads this reconstructed account and requires only that the debt map is nonempty. [6](#0-5)  It then computes totals from `account.supply_positions`, so an unavailable collateral map contributes zero collateral while surviving debt contributes its full value. [7](#0-6) [8](#0-7) 

Differential expiration is possible because account entries have independent persistent keys and user operations renew only the entries they read or write. [9](#0-8)  For example, owner-only delegate management authenticates through metadata but does not renew `SupplyPositions`, allowing metadata and debt state to remain live after collateral state becomes unavailable. [10](#0-9) [11](#0-10) 

### Impact Explanation
An attacker can cause an account’s existing collateral to be omitted from the bad-debt gate. [1](#0-0) [12](#0-11)  With collateral reported as zero and debt still present, `is_socializable_bad_debt(total_debt, total_collateral)` admits the account even though the omitted shares may exceed the dust threshold. [13](#0-12)  Cleanup then treats recoverable collateral-backed debt as unrecoverable bad debt, imposing an unnecessary loss on pool suppliers and stranding the account’s actual collateral claim. [2](#0-1) [14](#0-13) 

This satisfies protocol-insolvency and user-fund-loss impact because debt is written down without accounting for collateral that still exists in the pool but was omitted from the controller’s reconstructed position map. [7](#0-6) [15](#0-14) 

### Likelihood Explanation
The trigger requires an account whose collateral map has expired while its metadata and debt map remain readable. [16](#0-15)  This is feasible because each map is a separate persistent key, `renew_user_account` renews only keys currently present, and several authenticated account operations do not touch or renew both position maps. [9](#0-8) [17](#0-16) 

After that state occurs, any unprivileged address can submit `clean_bad_debt(caller, account_id)`; no owner, delegate, governance, or privileged authorization is required. [2](#0-1) [18](#0-17)  The attacker does not need to control the victim, predict a price, or exploit a privileged operation; the decisive condition is the missing collateral map being silently initialized as empty. [1](#0-0) 

### Recommendation
Do not default missing position-map storage to an empty map for accounts that otherwise exist. [19](#0-18)  Introduce explicit account-state reads that distinguish “never created” from “entry unavailable,” and make liquidation and bad-debt cleanup fail closed when a required account entry is unavailable. [20](#0-19) 

Keep position-map TTLs atomically coupled to account metadata by renewing all account keys whenever an account is authenticated or mutated. [21](#0-20) [9](#0-8)  Alternatively, consolidate account metadata and both position maps under one persistent entry or add an account-state marker whose expiration cannot diverge from position storage. [22](#0-21) 

### Proof of Concept
1. Create an account and supply collateral, then borrow so both `SupplyPositions(account_id)` and `BorrowPositions(account_id)` are nonempty. [23](#0-22) 
2. Renew or otherwise keep `AccountMeta(account_id)` and `BorrowPositions(account_id)` live while allowing `SupplyPositions(account_id)` to expire or become archived. [24](#0-23) 
3. As an unprivileged caller, invoke `Controller::clean_bad_debt(attacker, account_id)`. [2](#0-1) 
4. `storage::get_account` succeeds because metadata and NFT ownership resolve, while `get_supply_positions` returns an empty map for the unavailable collateral entry. [25](#0-24) 
5. `calculate_account_risk_totals` receives that empty supply map and the nonempty debt map, producing zero collateral and positive debt. [26](#0-25) [8](#0-7) 
6. The dust-capped bad-debt gate accepts the account and `execute_bad_debt_cleanup` socializes debt without considering the unavailable collateral shares. [27](#0-26)

    /// Permissionless: insolvent *and* collateral at or below the dust threshold.
    DustCapped,
    /// Owner-only: insolvent alone, with no cap on the collateral left behind.
    InsolventOnly,

/// Requires open debt and the selected insolvency gate, then cleans up the account.
fn socialize_bad_debt(env: &Env, account_id: u64, gate: BadDebtGate) {
    let mut cache = Context::new(env);
    let account = storage::get_account(env, account_id);

    assert_with_error!(
        env,
        !account.borrow_positions.is_empty(),
        CollateralError::DebtPositionNotFound
    );

    let totals = risk::calculate_account_risk_totals(
        env,
        &mut cache,
        &account.supply_positions,
        &account.borrow_positions,
    );

    let admits = match gate {
        BadDebtGate::DustCapped => {
            is_socializable_bad_debt(totals.total_debt, totals.total_collateral)
        }
        BadDebtGate::InsolventOnly => totals.total_debt > totals.total_collateral,
    };
    assert_with_error!(env, admits, CollateralError::CannotCleanBadDebt);

    bad_debt::execute_bad_debt_cleanup(env, &mut cache, account_id, &account, &totals);
}

/// Authenticates the NFT owner and updates delegates; grants require an active
/// manager. Emits an event only when the current owner's delegate list changes.
fn set_account_delegate(
    env: &Env,
    caller: &Address,
    account_id: u64,
    delegate: &Address,
    add: bool,
) {
    caller.require_auth();
    require_account_owner(env, account_id, caller);
    if add {
        // Reject dormant grants that could gain authority on later manager activation.
        assert_with_error!(
            env,
            storage::get_position_manager(env, delegate).is_some_and(|c| c.is_active),
            GenericError::NotAuthorized
        );
    }

    let changed = if add {
        storage::add_delegate(env, account_id, caller, delegate)
    } else {
        storage::remove_delegate(env, account_id, caller, delegate)
    };
