### Title
Unbounded solver-supplied `amount_in` in `DirectBridge.estimateWithdrawalFee` primary quote path lets a single solver overcharge the storage-deposit fee - (File: packages/intents-sdk/src/bridges/direct-bridge/direct-bridge.ts)

### Summary
`DirectBridge.estimateWithdrawalFee` computes the true NEAR storage cost locally (`feeAmount = minStorageBalance - userStorageBalance`) but then, for the primary (non-fallback) quote path, returns `FeeEstimation.amount = BigInt(feeQuote.amount_in)` straight from `getFeeQuote`/`solverRelay.getQuote` with no upper-bound sanity check. That unchecked `amount_in` later becomes the `-amount_in` leg of the signed `token_diff` intent in `createWithdrawalIntents`, directly debiting the user's withdrawal-token balance.

### Finding Description
The equality that should hold is: `FeeEstimation.amount` (tokens deducted from the user via the `token_diff` intent) ≈ market-fair cost of `feeAmount` NEAR (the storage deposit actually required), i.e. `amount_in ≈ feeAmount * price(feeAsset)/price(tokenAsset)` within a bounded slippage.

Tracing the code:
- `feeAmount = minStorageBalance - userStorageBalance` is computed locally and is the ground truth [1](#0-0) .
- The primary quote request is `exact_amount_out: feeAmount` (fixing `amount_out`, letting the solver dictate `amount_in`) [2](#0-1) .
- In `solverRelay.getQuote`, `matchesRequest` only verifies the *fixed* side (`amount_out === exact_amount_out`); the competed side (`amount_in`) is accepted as-is from any solver whose quote matches asset ids and the fixed amount [3](#0-2) .
- `sortQuotes` picks the *minimum* `amount_in` among all returned valid quotes for `exact_out` requests [4](#0-3) . This means an inflated quote from one malicious/buggy solver is only defeated if at least one other, honestly-priced solver also responds. If it is the sole (or best-ranked-but-still-inflated) responder, its `amount_in` is selected with no absolute sanity bound.
- Back in `direct-bridge.ts`, the result is returned unmodified: `amount: feeQuote ? BigInt(feeQuote.amount_in) : feeAmount` [5](#0-4) . Unlike the exact-in *fallback* branch of `getFeeQuote`, which explicitly checks `actualRatio > 1500n` (1.5x cap) against an oracle price before accepting the solver's quote [6](#0-5) , the primary exact-out path has **no equivalent cap check at all**.
- That unchecked `FeeEstimation.amount`/`quote` is then consumed by `createWithdrawalIntents`, which builds a signed `token_diff` intent debiting exactly `feeQuote.amount_in` of the user's withdrawal token [7](#0-6) .

Existing guards that were checked and do **not** prevent this:
- `matchesRequest` only pins the fixed side (`amount_out`), not the competed side (`amount_in`).
- The 1.5x ratio guard exists only in the `QuoteError` fallback branch, not in the primary exact-out branch.
- There is no `FeeExceedsAmountError`-style check comparing `feeEstimation.amount` to a bound derived from `feeAmount` for this route in `sdk.ts`/`direct-bridge.ts`.
- Multi-solver competition (`sortQuotes` picking the minimum) mitigates but does not eliminate the risk: it only protects against inflated quotes when a second, honest solver simultaneously answers the same request.

### Impact Explanation
If a solver returns an inflated `amount_in`, that exact value becomes the amount debited from the user's own signed `token_diff` intent when the withdrawal executes — i.e., real user funds, denominated in the withdrawal token, are swapped away for a storage deposit that costs a small fraction of that. This matches the "fee error draining a material share of the amount" Critical category: the debited amount is directly attacker(solver)-controlled and can be made arbitrarily large relative to the tiny real NEAR storage cost. It is repeatable on every `estimateWithdrawalFee`/withdrawal call for any NEP-141 token routed through `DirectBridge` (i.e., any near-native withdrawal that requires a storage deposit and isn't NEAR itself).

### Likelihood Explanation
Preconditions: destination account lacks sufficient NEAR storage balance for the token (`minStorageBalance > userStorageBalance`), the withdrawal asset isn't the native NEAR asset, and the solver-relay quote aggregator returns the malicious solver's quote as the winning (lowest `amount_in`) one — which happens whenever no competing solver undercuts it (thin liquidity, novel token, or collusion). No privileged access is needed; the actor is exactly the "permissionless solver answering a quote" defined as an in-scope unprivileged attacker. Cost to the attacker is just running a solver instance and answering relay quote requests, which is low. The exploit is repeatable per withdrawal.

### Recommendation
Add an oracle- or reference-price-based upper bound (e.g., the same `actualRatio`/1.5x-style cap already used in the fallback branch of `getFeeQuote`) to the primary exact-out quote path before accepting `feeQuote.amount_in`, and/or introduce a `FeeExceedsAmountError`-style check in `DirectBridge.estimateWithdrawalFee`/`IntentsSDK` comparing the returned `amount` against a sane multiple of the locally computed `feeAmount` converted at a fetched reference price, rejecting or re-quoting when exceeded.

### Proof of Concept
```ts
// direct-bridge.storageFee.test.ts (vitest)
import { describe, it, expect, vi } from "vitest";
// mock only HTTP-level dependencies:
// - getNearNep141MinStorageBalance -> returns e.g. 1_250_000_000_000_000_000_000n (near-standard min balance)
// - getNearNep141StorageBalance -> returns 0n (destination has none)
// - getFeeQuote (or solverRelay.getQuote under it) -> mocked to return
//     { amount_in: (feeAmount * 1000n).toString(), amount_out: feeAmount.toString(), ... }

it("accepts a solver quote 1000x larger than the real storage fee with no cap", async () => {
  const feeAmount = 1_250_000_000_000_000_000_000n; // minStorageBalance - userStorageBalance
  const inflatedAmountIn = (feeAmount * 1000n).toString();

  vi.mocked(getFeeQuote).mockResolvedValue({
    amount_in: inflatedAmountIn,
    amount_out: feeAmount.toString(),
    defuse_asset_identifier_in: "nep141:sometoken.near",
    defuse_asset_identifier_out: "nep141:wrap.near",
    quote_hash: "...",
  } as any);

  const bridge = new DirectBridge({ envConfig, nearProvider, });
  const estimation = await bridge.estimateWithdrawalFee({
    withdrawalParams: { assetId: "nep141:sometoken.near", destinationAddress: "newaccount.near", routeConfig: undefined },
  });

  // LHS: what the user is actually charged
  const chargedAmount = estimation.amount;
  // RHS: the real storage cost the fee is supposed to cover
  const trueFeeAmount = feeAmount;

  // Equality is broken: chargedAmount is 1000x trueFeeAmount, no cap enforced
  expect(chargedAmount).toBe(BigInt(inflatedAmountIn));
  expect(chargedAmount).toBeGreaterThan(trueFeeAmount * 10n); // no slippage bound exists

  // Downstream: the same inflated amount flows unmodified into the signed intent
  const intents = await bridge.createWithdrawalIntents({
    withdrawalParams: { assetId: "nep141:sometoken.near", amount: 10_000_000n, destinationAddress: "newaccount.near" } as any,
    feeEstimation: estimation,
  });
  const tokenDiff = intents.find(i => i.intent === "token_diff") as any;
  expect(tokenDiff.diff["nep141:sometoken.near"]).toBe(`-${inflatedAmountIn}`);
});
```

```typescript
function sortQuotes(
	quotes: Quote[],
	quoteKind: "exact_in" | "exact_out",
): Quote[] {
	return quotes.slice().sort((a, b) => {
		if (quoteKind === "exact_in") {
			// For exact_in, sort by `amount_out` in descending order
			if (BigInt(a.amount_out) > BigInt(b.amount_out)) return -1;
			if (BigInt(a.amount_out) < BigInt(b.amount_out)) return 1;
			return 0;
		}

		// For exact_out, sort by `amount_in` in ascending order
		if (BigInt(a.amount_in) < BigInt(b.amount_in)) return -1;
		if (BigInt(a.amount_in) > BigInt(b.amount_in)) return 1;
		return 0;
	});
```

```typescript
function matchesRequest(
	quote: Quote,
	quoteParams: GetQuoteParams["quoteParams"],
): boolean {
	if (
		quote.defuse_asset_identifier_in !==
			quoteParams.defuse_asset_identifier_in ||
		quote.defuse_asset_identifier_out !==
			quoteParams.defuse_asset_identifier_out
	) {
		return false;
	}

	// Only the side fixed by the request is verified; the other side is what the
	// solver competes on (max amount_out for exact_in, min amount_in for
	// exact_out). Compare as BigInt so formatting differences don't matter.
	if (quoteParams.exact_amount_in != null) {
		return BigInt(quote.amount_in) === BigInt(quoteParams.exact_amount_in);
	}
	return BigInt(quote.amount_out) === BigInt(quoteParams.exact_amount_out);
```
