Based on my review, this claim is confirmed. Note: `HandleLegacyUserMessage` uses a different path (`DecodeJSONRequest`), but the new JSON-RPC handler path (`HandleJSONRPCUserMessage`) for `MethodPublicKeyGet` forwards `req` directly to `ar.req` via `newActiveRequest`/`fanOutToVaultNodes` without ever validating or unmarshalling `req.Params` [1](#0-0) . This confirms the report's stated uncertainty: the gateway-side handler does **not** guarantee non-nil `params` before relaying `MethodPublicKeyGet` requests to nodes.

On the node side, `HandleGatewayMessage` dispatches `MethodPublicKeyGet` straight to `handlePublicKeyGet` bypassing `GatewayVaultRequestProcessor.ProcessRequest` (used for all other Vault methods) [2](#0-1) , and `handlePublicKeyGet` unconditionally dereferences `*req.Params` with no nil guard, unlike `processCreateSecretsRequest`, which explicitly checks `req.Params == nil` before use [3](#0-2) [4](#0-3) . I confirmed `gatewayConnector.readLoop` has no `recover()` around the handler dispatch — a grep for `recover()` in `core/services/gateway/connector/connector.go` returned zero matches, and the handler is invoked synchronously and unguarded [5](#0-4) .

Full end-to-end reachability from an unauthenticated HTTP client depends on the gateway's outer HTTP request-decoding layer (`api.JSONRPCCodec.DecodeRawRequest`/`DecodeJSONRequest`), which itself dereferences `*request.Params` when decoding the legacy `Message` wrapper [6](#0-5) . I was unable to fully trace how the outer HTTP-to-JSONRPC decoding boundary constructs the `jsonrpc2.Request[json.RawMessage]` that is eventually passed to `HandleJSONRPCUserMessage`, since `jsonrpc2.Request`/`DecodeRequest` live in the external `chainlink-common` module which is not indexed in this repo — so I cannot confirm with certainty whether that earlier layer already rejects a missing/null `"params"` field before `HandleJSONRPCUserMessage` is ever reached. This is the same gap the original report flagged and could not fully verify.

Given the code as written in this repo, the chain from `HandleJSONRPCUserMessage`'s public-key branch (no params validation) through to the node's `handlePublicKeyGet` (no nil check) through to the un-recovered `readLoop` goroutine is real and internally consistent with the claim: a `PublicKeyGet` request lacking `params` would panic in `handlePublicKeyGet` and crash the node process, since nothing in this codebase's visible logic intercepts a nil `Params` before that point.

Audit Report

## Title
Unvalidated nil `req.Params` dereference in Vault gateway `PublicKeyGet` path causes node-crashing panic - (File: core/capabilities/vault/gw_handler.go)

## Summary
`GatewayHandler.HandleGatewayMessage` routes `vaulttypes.MethodPublicKeyGet` directly to `handlePublicKeyGet` without going through `GatewayVaultRequestProcessor.ProcessRequest`, and `handlePublicKeyGet` dereferences `*req.Params` with no nil check, unlike every other Vault request path. On the gateway side, `HandleJSONRPCUserMessage`'s dedicated `MethodPublicKeyGet` branch also forwards the request to nodes without validating that `req.Params` is non-nil, so a request with omitted/null `params` can reach the node unmodified. Because the node's `gatewayConnector.readLoop` invokes handlers synchronously with no `recover()`, the resulting nil-pointer panic crashes the entire node process — a remote, pre-authentication denial-of-service.

## Finding Description
`HandleGatewayMessage` special-cases `vaulttypes.MethodPublicKeyGet` to skip `h.requestProcessor.ProcessRequest`, the validation/authorization pipeline used for all other Vault methods (`SecretsCreate/Update/Delete/List`), and calls `handlePublicKeyGet` directly. `handlePublicKeyGet` then executes `json.Unmarshal(*req.Params, r)` without first checking `req.Params == nil`, unlike `processCreateSecretsRequest`, which explicitly guards against nil params before unmarshalling.

On the gateway side, `HandleJSONRPCUserMessage`'s public-key branch intentionally skips the authorization/`ProcessRequest` pipeline ("Public key requests don't require authorization") and forwards the request object as-is to `fanOutToVaultNodes` via `newActiveRequest`, without unmarshalling or validating `req.Params` for this method. This means a client-supplied request with missing/null `params` is relayed unchanged to nodes.

On the node side, `gatewayConnector.readLoop` decodes the incoming JSON-RPC message and calls `handler.HandleGatewayMessage` synchronously in the goroutine with no `recover()` anywhere in the function, so any panic inside the handler chain propagates and crashes the process rather than being contained per-request.

## Impact Explanation
A remote, pre-authentication denial-of-service: any party able to reach the Gateway's public vault HTTP endpoint (or otherwise get a `MethodPublicKeyGet` message forwarded to a node) can crash the target node's process with a single malformed request, since `PublicKeyGet` is the only Vault method dispatched without going through the `Authorizer`/`GatewayVaultRequestProcessor` pipeline on either the gateway or node side. This maps to node-availability-impacting DoS, a recognized in-scope impact category.

## Likelihood Explanation
Very low effort: `PublicKeyGet` is intentionally unauthenticated by design (it only returns a public key), and the gateway-side handler code that processes it performs no params validation before relaying to nodes, so no allowlist membership, JWT, or workflow ownership is needed to trigger it. The main residual uncertainty — which I could not fully resolve because `jsonrpc2.Request`/`DecodeRequest` live in the external `chainlink-common` dependency not present in this repo's index — is whether the outermost HTTP decoding layer normalizes/rejects a missing `params` field before `HandleJSONRPCUserMessage` is invoked. Nothing in the code visible in this repository performs that check, so based on available evidence the path is reachable as described.

## Recommendation
Add an explicit `req.Params == nil` guard in `handlePublicKeyGet` (core/capabilities/vault/gw_handler.go) that returns a `UserMessageParseError` response instead of dereferencing a nil pointer, and add the same guard in the gateway-side `HandleJSONRPCUserMessage` `MethodPublicKeyGet` branch (core/services/gateway/handlers/vault/handler.go) before forwarding to nodes. Additionally, wrap the handler dispatch inside `gatewayConnector.readLoop` (core/services/gateway/connector/connector.go) with a `recover()` so that a panic in any single message handler cannot terminate the entire node process.

## Proof of Concept
1. Send a JSON-RPC request to the gateway's public vault HTTP endpoint with method `vault_publicKeyGet` and no `"params"` field (or `"params": null"`), with the cache empty (e.g. on node/gateway startup before the periodic cache refresh populates `cachedPublicKeyGetResponse`).
2. `handler.HandleJSONRPCUserMessage` (core/services/gateway/handlers/vault/handler.go, lines 404-420) takes the `MethodPublicKeyGet` branch, finds no cached key, and forwards the request unchanged via `fanOutToVaultNodes` to the DON nodes.
3. On a node, `gatewayConnector.readLoop` decodes the message and calls `GatewayHandler.HandleGatewayMessage`, which dispatches to `handlePublicKeyGet` (core/capabilities/vault/gw_handler.go, lines 364-368).
4. `json.Unmarshal(*req.Params, r)` dereferences a nil `*json.RawMessage`, panicking inside the un-recovered `readLoop` goroutine, crashing the node process.
5. A minimal Go unit test invoking `GatewayHandler.HandleGatewayMessage` with a `jsonrpc.Request[json.RawMessage]{Method: vaulttypes.MethodPublicKeyGet, Params: nil}` would reproduce the panic directly.

func (c *gatewayConnector) readLoop(gatewayState *gatewayState) {
	defer c.closeWait.Done()
	ctx, cancel := c.shutdownCh.NewCtx()
	defer cancel()

	for {
		select {
		case <-c.shutdownCh:
			return
		case item := <-gatewayState.conn.ReadChannel():
			var req jsonrpc.Request[json.RawMessage]
			err := json.Unmarshal(item.Data, &req)
			if err != nil {
				c.lggr.Errorw("parse error when reading from Gateway", "id", gatewayState.config.ID, "err", err)
				break
			}
			c.handlersMu.RLock()
			handler, exists := c.handlers[req.Method]
			c.handlersMu.RUnlock()
			if !exists {
				c.lggr.Errorw("no handler for method", "id", gatewayState.config.ID, "method", req.Method)
				break
			}
			// do not break on error. HandleGatewayMessage handles errors
			// by sending a response back to the Gateway.
			err = handler.HandleGatewayMessage(ctx, gatewayState.config.ID, &req)
			if err != nil {
				c.lggr.Warnw("failed to handle message from Gateway", "id", gatewayState.config.ID, "method", req.Method, "err", err)
			}
		}
	}
