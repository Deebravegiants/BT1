### Title
Webhook `shop` (and `topic`/`webhook_id`/`api_version`) headers are trusted without being covered by the HMAC, enabling cross-tenant webhook spoofing - (File: `lib/shopify_api/webhooks/request.rb`)

### Summary
`ShopifyAPI::Webhooks::Request#to_signable_string` only signs the raw HTTP body, while the tenant-identifying `shop` value (and `topic`, `webhook_id`, `api_version`) are read straight from unauthenticated HTTP headers and forwarded unchanged to the app's handler once the HMAC check on the body passes.

### Finding Description
`Utils::HmacValidator.validate` verifies a `VerifiableQuery`'s HMAC by computing `HMAC(secret, verifiable_query.to_signable_string)` and comparing it to the supplied `hmac` value. [1](#0-0) 

For webhooks, `to_signable_string` returns only `@raw_body`: [2](#0-1) 

But `shop`, `topic`, `webhook_id`, and `api_version` are all read from HTTP headers, which are never included in the signable string and therefore never covered by the HMAC: [3](#0-2) 

`Registry.process` validates only the body HMAC, then immediately trusts `request.shop` (a bare header value) as the tenant identity passed to the app-level handler: [4](#0-3) 

The identity binding the code implicitly assumes is:
`HMAC_valid(body) == true` implies `shop_header == shop_that_produced(body)`

This equality does not hold: the HMAC secret (`Context.api_secret_key`, the app's `client_secret`) is the same for every shop that has installed the app, and the signature is computed over the body alone. Any tenant that has installed the app can capture one of its own legitimately-signed webhook deliveries (valid body + valid HMAC) and replay that exact `raw_body`/`hmac-sha256` pair to the app's webhook endpoint while substituting an arbitrary `shop-domain` header (and `topic`/`webhook_id`/`api_version` headers) naming a different, victim tenant. `Utils::HmacValidator.validate` will still return `true`, because it never inspects the headers, and `Registry.process` will hand the forged `shop` value straight to the registered `WebhookHandler`.

### Impact Explanation
This breaks the tenant boundary the gem is supposed to enforce at the webhook ingestion point: an app that keys any per-shop side effect (data storage, billing, `shop/redact`/`customers/redact` compliance actions, sync jobs, etc.) off `WebhookMetadata#shop` as delivered by `Registry.process` can be made to attribute one tenant's webhook content to another tenant. This is a cross-tenant integrity/isolation break reachable by any unprivileged merchant that has installed the app (no access token, secret, or privileged account required beyond a normal install) — matching the "cross-tenant access" bucket for impact.

### Likelihood Explanation
Exploitation only requires: (1) installing the target app as an ordinary merchant (or otherwise receiving one legitimate webhook delivery for a controlled shop), (2) capturing the raw body and `hmac-sha256` header of a delivery, and (3) resending it to the app's webhook endpoint with a modified `shop-domain` (and related) header. No cryptographic secret is needed since the header fields are simply not part of what is signed.

### Recommendation
Bind the tenant/topic identity into the signed payload the library verifies for webhooks, e.g. include `shop`, `topic`, `webhook_id`, and `api_version` in `to_signable_string` (or otherwise cryptographically bind them), or require/document that consuming apps must independently verify `request.shop` against a known, previously-established session/installation record before trusting `WebhookMetadata#shop`, rather than treating body-HMAC success as proof of header authenticity.

### Proof of Concept
1. As attacker-shop `attacker.myshopify.com` (a legitimate app install), trigger a webhook delivery (e.g. `orders/create`) and capture the exact `raw_body` and `X-Shopify-Hmac-Sha256` header from the app's endpoint logs.
2. Resend an HTTP request to the same webhook endpoint with the identical `raw_body` and `X-Shopify-Hmac-Sha256`, but set `X-Shopify-Shop-Domain: victim.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which only hashes `@raw_body`, and the check passes: [5](#0-4) 
4. `Registry.process` invokes the app handler with `shop: request.shop` == `"victim.myshopify.com"`, even though the body actually originated from `attacker.myshopify.com`: [4](#0-3)

          received_signature = verifiable_query.hmac
          computed_signature = compute_signature(verifiable_query.to_signable_string, secret)
          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
        end
