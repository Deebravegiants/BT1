### Title
Webhook `shop`, `topic`, and `webhook_id` fields are not covered by the HMAC signature, allowing cross-tenant request forgery - ([File: lib/shopify_api/webhooks/request.rb])

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-verifiable signature only over the raw request body, while the `shop`, `topic`, `api_version`, and `webhook_id` values used downstream to route and attribute the webhook are read directly from unauthenticated HTTP headers that are never included in the signed material.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

`HmacValidator.validate` verifies the HMAC exclusively against this signable string: [2](#0-1) 

Meanwhile, `Request#shop`, `#topic`, `#webhook_id`, and `#api_version` are all read straight from HTTP headers with no cryptographic binding to the signature: [3](#0-2) 

`Registry.process` validates only the HMAC over the body, then dispatches the handler using these unauthenticated header-derived fields: [4](#0-3) 

The equality this breaks: the identity asserted to the application handler (`request.shop`, `request.topic`, `request.webhook_id`) is not equal to the identity actually covered by the cryptographic signature (`request.to_signable_string` == raw body only). Concretely: `sig_covers(request) == raw_body`, but `handler.handle` acts on `{topic, shop, webhook_id, api_version}` — none of which participate in `sig_covers`.

An attacker who can obtain any single valid `(raw_body, hmac)` pair for their own tenant (e.g., by installing the app on their own store and observing a webhook, or by triggering an event that generates a predictable/replayable body such as an empty `{}` payload) can replay that exact body and HMAC to the app's public webhook endpoint while substituting the `shop-domain`, `topic`, and `webhook-id` headers with a victim shop's identifiers. Since none of these headers are covered by the signature check, `Utils::HmacValidator.validate(request)` still succeeds, and `Registry.process` calls the registered handler with `WebhookMetadata` claiming the victim's `shop`/`topic`/`webhook_id` for attacker-controlled body content.

### Impact Explanation
If the host application (following this gem's own documented `WebhookMetadata`/`data.shop` contract) uses `data.shop` to look up per-tenant session/state or trusts `data.topic`/`data.webhook_id` for idempotency or routing decisions, this forgery lets an unprivileged attacker inject falsified webhook events attributed to a different merchant's shop — a cross-tenant integrity/confidentiality issue reachable without any credentials, matching the "Critical - cross-tenant access" impact category via forged tenant attribution.

### Likelihood Explanation
Webhook endpoints are necessarily public HTTP endpoints (Shopify itself must be able to POST to them without prior handshake), so any internet user can send requests to them. The only obstacle is obtaining one valid `(body, hmac)` pair, which is trivial for an attacker who is a merchant/developer on their own store (they can register a webhook to themselves and capture a legitimate payload+HMAC, e.g. for a topic with an empty or attacker-influenced body). This requires no `api_secret_key`, no leaked credentials, and no privileged account — only a normal, unprivileged relationship to some Shopify store.

### Recommendation
Bind the trust-sensitive header fields (`shop-domain`, `topic`, `webhook-id`, `api-version`) into the signed/verified material, or otherwise cryptographically tie them to the request before they are exposed via `WebhookMetadata`, e.g. by including them in `to_signable_string` (if Shopify's HMAC scheme supports it) or by requiring the host app to cross-check `shop` against a known/registered webhook subscription rather than trusting the header verbatim. At minimum, document prominently that these header-derived fields are unauthenticated and must not be trusted for tenant attribution without additional verification.

### Proof of Concept
1. Attacker installs the app on their own shop `attacker.myshopify.com` and registers a webhook for topic `X`.
2. Shopify sends a webhook to the app with body `B` and header `x-shopify-hmac-sha256: H`, where `H = HMAC-SHA256(secret, B)`. Attacker captures `(B, H)`.
3. Attacker (or anyone who can reach the public webhook endpoint) sends a POST to the same endpoint with body `B`, `x-shopify-hmac-sha256: H` (unchanged, still valid since it only covers `B`), but headers `x-shopify-shop-domain: victim.myshopify.com`, `x-shopify-topic: <victim-relevant topic>`, `x-shopify-webhook-id: <arbitrary>`.
4. `Registry.process` calls `Utils::HmacValidator.validate(request)` — succeeds because it only checks `B` against `H`. [5](#0-4) 
5. The handler receives `WebhookMetadata` with `shop: "victim.myshopify.com"` and processes body `B` as though it originated from the victim's store.
