### Title
Webhook `shop-domain`, `topic`, and `webhook-id` headers are not covered by the HMAC signature, enabling cross-tenant webhook forgery - (File: `lib/shopify_api/webhooks/request.rb`, `lib/shopify_api/webhooks/registry.rb`)

### Summary
`ShopifyAPI::Webhooks::Request` computes its HMAC-signable content from the raw body only, while the `shop`, `topic`, and `webhook_id` used by the app's business logic come from unauthenticated HTTP headers. `Webhooks::Registry.process` validates only the body signature and then hands the unauthenticated `shop` value straight to the app's handler, breaking the intended binding `shop_authenticated == shop_used_for_tenant_dispatch`.

### Finding Description
`Request#to_signable_string` returns only `@raw_body`: [1](#0-0) 

Meanwhile `shop`, `topic`, and `webhook_id` are read directly from HTTP headers, none of which are part of the signed content: [2](#0-1) 

`Registry.process` validates the HMAC (which only covers the body) and then trusts the header-derived `request.shop` to build the `WebhookMetadata` passed to the app's handler, without any check that `shop` was itself covered by the signature: [3](#0-2) 

`HmacValidator.validate` only compares `verifiable_query.hmac` against a signature computed over `to_signable_string`, i.e. the raw body: [4](#0-3) 

Because the app-level `api_secret_key` (`client_secret`) is the same across every shop that has installed the app, any merchant who has installed the app can capture a genuinely-signed webhook body+HMAC pair generated for their own shop, then replay that exact body/HMAC pair to the app's webhook endpoint while substituting the `shopify-shop-domain` (and `shopify-topic`/`shopify-webhook-id`) headers to claim the event originated from a *different* tenant. `HmacValidator.validate` still returns true because the signature check never inspects the header values, so `Registry.process` will dispatch the forged event to the handler as if it were a legitimate webhook for the victim shop.

The equality this breaks: `shop_covered_by_hmac == shop_used_to_attribute_webhook_data`. Before the request: both sides are expected to refer to the same, Shopify-verified tenant. After an attacker's crafted request: the HMAC-verified side is the (attacker-controlled) body, while the shop-attribution side is an arbitrary, attacker-chosen header value — the two are no longer bound together.

### Impact Explanation
This is a cross-tenant confused-deputy vulnerability: an unprivileged app user (any merchant with the app installed) can forge webhook events that the app processes as belonging to another merchant's shop, since the gem's own `Registry.process` dispatches on an HMAC-unverified `shop` field. Any downstream logic that uses `WebhookMetadata#shop` to select which tenant's data to create/update/delete is exposed to cross-tenant data corruption or disclosure.

### Likelihood Explanation
Exploitation only requires the attacker to be a normal user of the shared app (able to trigger any webhook on their own shop to obtain a valid body+HMAC pair) and the ability to send an HTTP POST to the app's webhook endpoint with modified headers — no access token, secret, or privileged account is required.

### Recommendation
Bind the shop (and ideally topic/webhook-id) into the signed payload verification, e.g. by requiring the app to pass the expected shop as part of validation, or by having `Registry.process` cross-check the header-derived shop against an independently trusted source (such as looking up the webhook subscription by `webhook_id` via the Admin API) before dispatching to handlers, rather than trusting the raw header value implicitly.

### Proof of Concept
1. Attacker installs the target app on their own shop `attacker-shop.myshopify.com` and triggers any webhook subscription (e.g. `orders/create`), capturing the raw POST body and the `X-Shopify-Hmac-Sha256` header Shopify sent.
2. Attacker replays the exact same raw body and HMAC header to the app's webhook endpoint, but sets `X-Shopify-Shop-Domain: victim-shop.myshopify.com`.
3. `ShopifyAPI::Webhooks::Registry.process` calls `Utils::HmacValidator.validate(request)`, which succeeds because it only checks the (unchanged) body against the (unchanged) HMAC: [3](#0-2) 
4. The handler receives `WebhookMetadata` with `shop: "victim-shop.myshopify.com"` even though nothing about that shop value was ever verified, causing the app to act on victim-shop's behalf using attacker-supplied body content.

        def validate_signature(verifiable_query, secret)
          received_signature = verifiable_query.hmac

          OpenSSL.secure_compare(computed_signature, T.must(received_signature))
