### Title
Reentrant escrow drain via check-then-external-call-then-state-update ordering in `IntentGatewayV2.withdraw()` (Tron variant) - (File: `evm/tron/contracts/apps/IntentGatewayV2.sol`)

### Summary
The Tron variant of `IntentGatewayV2` performs the escrow-release token/ETH transfer to the beneficiary **before** decrementing the `_orders[commitment][token]` escrow accounting, and neither `withdraw()` nor its public entry points (`cancelOrder`, `onAccept`, `onGetResponse`) are protected by a reentrancy guard. This is the same bug class as CVE-2023-34322 (XSA-438): a precaution ("check that escrow is non-zero") is performed, but the actual teardown of the resource (decrementing/clearing the escrow) happens too late — after control has already been handed to untrusted code (the beneficiary/token) that can re-enter and observe/consume the same escrowed balance again before it is retired.

### Finding Description
`withdraw()` in `evm/tron/contracts/apps/IntentGatewayV2.sol` (lines 691–730):

```solidity
function withdraw(WithdrawalRequest memory body, bool isRefund) internal {
    address beneficiary = address(uint160(uint256(body.beneficiary)));
    _filled[body.commitment] = beneficiary;

    uint256 len = body.tokens.length;
    for (uint256 i; i < len;) {
        address token = address(uint160(uint256(body.tokens[i].token)));
        uint256 amount = body.tokens[i].amount;
        if (_orders[body.commitment][token] == 0) revert UnknownOrder();

        if (token == address(0)) {
            (bool sent,) = beneficiary.call{value: amount}("");
            if (!sent) revert InsufficientNativeToken();
        } else {
            (bool success,) = token.call(abi.encodeWithSelector(IERC20.transfer.selector, beneficiary, amount));
            if (!success) revert TransferFailed();
        }

        _orders[body.commitment][token] -= amount;   // <-- state updated AFTER external call
        unchecked { ++i; }
    }
    ...
}
``` [1](#0-0) 

The "check" (`_orders[body.commitment][token] == 0`) verifies escrow exists, but the actual retirement of that escrow balance (`_orders[...] -= amount`) does not happen until after the external `.call` to `beneficiary` (native ETH/TRX path) or to an arbitrary ERC20 `token` contract. A malicious `beneficiary` address (reachable via `RequestKind.RefundEscrow`/`RedeemEscrow` in `onAccept`, or via `onGetResponse` after a cross-chain cancel) can re-enter `withdraw` — or any other state-mutating entry point — while the outer call is still in the loop, and observe the pre-decrement `_orders[body.commitment][token]` value, allowing the same escrow slot to be drained multiple times.

`cancelOrder()` in this file has **no `nonReentrant` modifier** [2](#0-1) , unlike the hardened `evm/src/apps/IntentGatewayV2.sol` version, which does apply `nonReentrant` on `cancelOrder` [3](#0-2) , and unlike `evm/src/apps/intentsv2/IntentsBase.sol`'s `_withdraw`, which decrements escrow **before** any external transfer (CEI-safe) [4](#0-3) . `onAccept` in the same Tron file routes untrusted-relayer-delivered `RedeemEscrow`/`RefundEscrow` requests straight into `withdraw()` [5](#0-4) , and `onGetResponse` does the same after a cross-chain cancel [6](#0-5) . Both call paths pass a solver/user-controlled `beneficiary` address into `withdraw`, giving an attacker full control over the reentrant callback (either via a malicious ERC20 `token.call` or a malicious `beneficiary.call{value}`).

The mainline EVM `evm/src/apps/intentsv2/*` code was already hardened against exactly this class of bug (see explicit CEI-fix comments and dedicated reentrancy regression tests in `IntrinsicIntentsReentrancyTest.sol`), but the parallel Tron contract at `evm/tron/contracts/apps/IntentGatewayV2.sol` still contains the pre-fix pattern with the checks-before-state-mutation-after-external-call ordering, and additionally lacks any `nonReentrant` guard.

### Impact Explanation
An attacker who is (a) a solver filling a cross-chain order and thus receiving a `RedeemEscrow`/`RefundEscrow` payload routed to `onAccept`, or (b) the recipient of a `withdraw()` call via `onGetResponse` after cancelling, can re-enter `withdraw` (or another state-mutating gateway function) during the native-ETH/TRX `.call` or the raw `token.call` to a malicious ERC20, and drain the same escrow slot multiple times before `_orders[commitment][token]` is decremented. This results in direct theft of escrowed user funds / unbacked withdrawal from the gateway's token reserves — concrete theft of funds, satisfying the "concrete theft ... of funds" bar.

### Likelihood Explanation
Reachable from a single relayed/dispatched message (`onAccept` with `RedeemEscrow`/`RefundEscrow`) or a single relayed GET response (`onGetResponse`), both of which are triggered by ordinary protocol participants (solvers/relayers) with no privileged role required. The beneficiary address embedded in the withdrawal request is attacker-controlled (it is the solver/filler or order user), so an attacker can deploy a malicious contract as beneficiary or a malicious ERC20 as the escrowed token to trigger the reentrant callback. No governance, admin, or node-compromise is required — this is directly reachable by an unprivileged relayer/solver, consistent with the required threat model.

### Recommendation
Apply the same fix already present in the mainline EVM contracts:
1. Decrement `_orders[body.commitment][token]` (checks-effects) **before** performing the external transfer (`.call` / `safeTransfer`) in `withdraw()`.
2. Add a `nonReentrant` guard (OpenZeppelin `ReentrancyGuard`) to `cancelOrder`, `onAccept`, and `onGetResponse` (or at minimum to `withdraw`) in `evm/tron/contracts/apps/IntentGatewayV2.sol`, matching `evm/src/apps/IntentGatewayV2.sol`.
3. Use `safeTransfer`/`safeTransferFrom` from `SafeERC20` instead of raw low-level `.call` with a manually checked selector, for consistency with the rest of the codebase and to avoid silent failures on non-standard tokens.
4. Port the reentrancy regression tests from `evm/tests/foundry/IntrinsicIntentsReentrancyTest.sol` to the Tron contract test suite.

### Proof of Concept
1. Deploy the Tron `IntentGatewayV2` and escrow a cross-chain order whose input token is a malicious ERC20 (or native TRX) with `beneficiary` = attacker-controlled contract.
2. Have the attacker's solver/relayer deliver a `RedeemEscrow` (or `RefundEscrow`) `PostRequest` via `onAccept`, or complete a cancel-from-source flow that lands in `onGetResponse`, targeting the attacker's escrow commitment.
3. Inside `withdraw()`, when the native `.call{value: amount}("")` (or the malicious ERC20's `transfer`) executes and control passes to the attacker's contract, have that contract re-enter the gateway (e.g., call `onAccept` again with the same `RedeemEscrow` body, or re-trigger `withdraw` through another exposed path) before `_orders[body.commitment][token] -= amount` executes.
4. Because `_orders[body.commitment][token]` still reflects the pre-decrement (full) escrow amount at the time of the reentrant check `_orders[body.commitment][token] == 0`, the reentrant call passes the check and triggers a second transfer of `amount` to the beneficiary, draining more than was ever escrowed for that order — repeatable up to gateway's available token balance for that asset, since no `nonReentrant` guard exists to block this.
